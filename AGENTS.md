# AGENTS.md — руководство для разработчиков и ИИ-агентов по тренажёру Go Workout

Go Workout — русскоязычный учебник-тренажёр по Go: **100 глав, 369 разделов, 7 666 задач** с теорией, пошаговым решением, компилируемым кодом, разбором механики рантайма, ловушками и вопросами с собеседований. С трека Б (2026-10-10) контент хранится в Markdown, а сайт собирает движок [html-textbook-engine](https://github.com/UnrealTemplier/html-textbook-engine) — так же, как в `go-textbook`.

## 🎯 1. Цель и аудитория

* **Аудитория:** уверенно-начинающие бэкенд-разработчики с опытом в C/C++, Python, PHP или JS, которые идут на позиции Middle / Senior / Staff Go Developer в российские технологические компании и BigTech (Яндекс, Ozon, Авито, Т-Банк, VK, Wildberries, Lamoda, Касперский).
* **Стиль:** живой, структурированный, инженерно строгий; глубокое погружение в компилятор, рантайм (планировщик GMP, трёхцветный GC, epoll/netpoller, аллокатор mcache/mcentral/mheap), сетевой стек, конкурентность и практики HighLoad / DevSecOps / Kubernetes.
* **7 сквозных траекторий** (Learning Paths) заданы в `book.toml` (`overlays`) и на главной: Core Go (главы 1–19), High-Concurrency & Network, Storage & Consistency, Distributed Systems, Observability & Reliability, Cloud-Native & Security, Go Internals & AI.

## 🗂️ 2. Структура репозитория

```text
go-workout/
├── sources/                 # Единственный источник правды контента (Markdown)
│   ├── 001. <Короткое имя главы>/
│   │   ├── 000. О главе.md                    # hero главы, «Об упражнениях главы», «Итог главы»
│   │   ├── 01. <Короткое имя раздела>/
│   │   │   ├── 00. О разделе.md               # H1 — полное название раздела, ниже описание (может быть пустым)
│   │   │   ├── 001. <Короткое имя задачи>.md  # H1 — полное название задачи
│   │   │   └── …
│   └── 100. …/
├── engine/                  # Копия ядра html-textbook-engine (не редактируется, § 5)
├── book.toml                # Настройки книги: заголовки из H1, индексные файлы, формулы, траектории, тексты главной
├── book/hooks.py            # Хук аудита: gofmt -e по всем блокам Go собранного сайта
├── tools/                   # Отчёты разового переноса (migration-report.md, visible-text-report.md, short-names.tsv, legacy-statement-notes.md)
├── fact-checks/             # Отчёты фактчека: fact-checks/<N>/<N>-<модель>-<роль>.md (§ 8)
├── .github/workflows/pages.yml  # CI: сборка → аудит → публикация на GitHub Pages
├── scripts/                 # REBUILD_ALL.sh / REBUILD_ALL.bat — полная проверка и пересборка; linux/*.sh, windows/*.bat — отдельные команды, см. scripts/README.md
├── requirements.txt         # markdown>=3.10,<3.11
├── favicon.ico / favicon.svg
├── AGENTS.md / README.md
└── dist/                    # Локальная сборка (в .gitignore; в Git не хранится)
```

* **Имена файлов и каталогов** — короткие (≤ 50 символов), без `:*?"<>|\/` и без `~`, точки или пробела на конце (`*~` скрыт `.gitignore`). Номер задаёт порядок в навигации. Полное название — только в первом `# …` файла: его движок делает заголовком страницы (`title_source = "h1"`).
* **Имя файла — это адрес страницы:** переименование меняет URL. Номера глав 1–100 неизменны (на них ссылаются тексты задач: «как мы разбирали в Главе 20…»); новые главы — только в конец.
* Индексные страницы `000. О главе.md` и `00. О разделе.md` (`index_file = '^0+\. '`) показывают список дочерних страниц и не входят в счётчик задач.

## 📝 3. Формат файла задачи

````markdown
# <Полное название задачи>

## Условие
<формулировка задачи>

### Исходная формулировка        ← только если краткая формулировка старого задачника отличалась

## Теория
## Решение по шагам
## Код решения
**`main.go`**

```go
package main
…
```

ℹ️ <пояснение к файлу>

## Под капотом
## Подводные камни
## На собеседовании
## Лучшие практики / ## Самопроверка / ## Тест-кейсы   ← есть не у всех задач
````

Пустые разделы не пишутся. Сворачивания ответов нет: страница задачи показывает всё.

### 3.1. Правила разметки (выяснены при переносе; нарушения ловят сборка и аудит)
* **Формулы:** строчные — `\(…\)`, выносные — `$$…$$`. Одиночный `$` — обычный текст (`$GOPATH`, `$(date)`, `$10`), формулой не станет. Внутри `\text{…}` подчёркивание экранируется: `\text{max\_applied\_token}` (иначе ошибка KaTeX).
* **Угловые скобки вне кода** пишутся `&lt;` (`print &lt;text>`), иначе браузер примет их за тег. В `` `коде` `` — как есть.
* **Сигнатуры Go вне кода** вида `Max[T any](a, b T)` пишутся с `\[` или в `` `коде` ``: иначе `[T any](a, b T)` станет ссылкой Markdown.
* **Блок кода в пункте списка** — ограда с отступом пункта (`indented_fences`); вне списка ограда начинается с начала строки.
* **Списки** могут идти сразу за строкой текста (`obsidian_lists`), вложенность — 2–4 пробела.
* **Wikilinks выключены** (`wikilinks = false`): `[[…]]` в тексте — это данные (`map[[2]int]T`), а не ссылки.

### 3.2. Требования к коду в решениях
| ❌ Нельзя | ✅ Надо | Почему |
| :--- | :--- | :--- |
| Псевдокод `// ... здесь логика` | Полный самодостаточный код с импортами и обработкой ошибок | Код копируют и сразу запускают |
| Игнорировать `if err != nil` | Обрабатывать ошибки: `fmt.Errorf("…: %w", err)`, лог или возврат | Пропуск проверки ошибки — критический антипаттерн на собеседованиях |
| `make(chan os.Signal)` без буфера | `make(chan os.Signal, 1)` | `signal.Notify` не блокируется и теряет сигнал, если горутина не успела встать на чтение |
| Копировать `sync.Mutex` по значению | Pointer receiver `(s *SafeStruct)` | Копия несёт состояние мьютекса: гонки и дедлоки (`go vet copylocks`) |
| Возвращать типизированный `nil` в `error` | Явно `return nil` | `(*MyError)(nil)` в интерфейсе даёт `err != nil == true` |

TAB в блоках кода на сайте выводятся четырьмя пробелами (так задумано). Каждый блок Go проверяется `gofmt -e` (хук аудита). Блоки `go.mod` и `go.work` помечены языком `go`, поэтому проверяются только блоки с `package`.

## ⚙️ 4. Сборка, аудит и публикация

Нужны Python ≥ 3.11 с `pip install -r requirements.txt`, Go (для `gofmt`) и, по желанию, Firefox (рантайм-проверки).

Каждая команда есть готовым скриптом в `scripts/` (`scripts/check.sh` — строгая сборка и аудит перед коммитом, `build`, `build-clean`, `build-chapter`, `audit-*`, `runtime-projection`, `tests`, `engine-sync`, `open-site`; `linux/*.sh` для Linux и macOS, `windows/*.bat` для Windows); `scripts/linux/menu.sh` / `scripts/windows/menu.bat` — меню со всеми командами. Полная проверка и пересборка одним запуском — `scripts/REBUILD_ALL.sh` / `scripts/REBUILD_ALL.bat`.

```bash
python3 -m engine.build --all --strict      # ~16 с: 8 136 страниц в dist/
python3 -m engine.audit --strict            # ссылки, якоря, ассеты, offline, имена файлов, gofmt -e
python3 engine/tools/runtime_projection.py dist --out /tmp/gw-runtime.json   # KaTeX и JS в Firefox, ~3 мин
```

* `--strict` превращает предупреждения сборки (незакрытые ограды, неизвестные выноски) в ошибки. Сейчас сборка и аудит проходят без предупреждений; рантайм: 4 910 формул и 276 выносных, 0 ошибок KaTeX, 0 ошибок JS.
* Сборщик не очищает `dist/`: после переименования файла соберите заново в чистый каталог (`rm -rf dist && python3 -m engine.build --all`).
* Сайт работает по `file:///` без сети: откройте `dist/index.html`. В среднем 47 КБ на страницу; общие `assets/nav-data.js` (1,9 МБ) и `assets/search-data.js` (3,4 МБ, только главная) кэшируются браузером.
* **Публикация:** `.github/workflows/pages.yml` на каждый push в `main` собирает сайт, запускает аудит и публикует `dist/` на GitHub Pages **только если сборка и аудит прошли**. Pull request проходит сборку и аудит без публикации. `dist/` не коммитится.

## 🔧 5. Движок

* `engine/` — копия ядра; источник правды — репозиторий `/home/ut/work/html-textbook-engine` (`github.com/UnrealTemplier/html-textbook-engine`). Здесь `engine/` **не редактируется**: исправление вносится в движок, выпускается версией и приходит командой `python3 -m engine.sync --from /home/ut/work/html-textbook-engine` (отдельный коммит `chore(engine): sync to vX.Y.Z`). Сборка сверяет `engine/.checksums.json` и предупреждает о локальных правках.

## ✅ 6. Как добавить или исправить задачу

1. Правьте файл в `sources/`. Новая задача — следующий номер в разделе (`NNN. Короткое имя.md`), полное название — в `# …`.
2. Соберите и проверьте: `python3 -m engine.build --all --strict && python3 -m engine.audit --strict`. Если менялись формулы — ещё рантайм-проекция.
3. Код решения запустите во временном каталоге вне репозитория.
4. Коммит — атомарный, с конвенциональным сообщением (`feat:`, `fix:`, `docs:`, `chore:`, `ci:`). `dist/` не коммитится.

Шаблон задания для агента:

```text
Добавь задачу в sources/<глава>/<раздел>/ по формату AGENTS.md § 3: Условие, Теория, Решение по шагам,
Код решения (полный компилируемый Go-код), Под капотом, Подводные камни, На собеседовании.
Собери (python3 -m engine.build --all --strict), прогони аудит (python3 -m engine.audit --strict), закоммить.
```

## 🔎 8. Фактчек

Фактическая точность глав проверяется многоролевым конвейером моделей (Scout, Alt, Judge, Blind spot, Fact check, Arbiter, Editor, Review). Каждая роль пишет отчёт `fact-checks/<N>/<N>-<модель>-<роль>.md`, где `N` — номер главы без ведущих нулей (`fact-checks/7/7-gemini-scout.md`). Промпты ролей в репозитории не хранятся (их держит владелец; версия от 2026-10-10 рассчитана на запуск из корня этого репозитория).

* Готовы скаут-отчёты глав 1–20. Они написаны до переноса в Markdown и несут блок «📌 Статус на 2026-10-10»: где теперь лежат задачи главы, во что превратились поля данных и что перенос уже исправил (пометки «✅ Статус на 2026-10-10» у кандидатов — например, испорченные формулы LaTeX).
* Отчёты — рабочие материалы, а не источник правды: правки вносит только редактор, в `sources/`, по проверенным находкам. Порядок коммитов главы: `docs(fact-check): add chapter N <роль> report` → `fix(chapter-NNN): apply fact-check corrections` (в теле — ID находок).
* Проверка после правок — `python3 -m engine.build --all --strict` и `python3 -m engine.audit --strict`; исправленный код собирается и запускается во временном каталоге.
