## 2. Находки

### A-01 — эталонный вывод задачи 026 неверен
- **Где:** `02. Указатели [N]T, unsafe.Sizeof_Alignof/026. Пузырьковая сортировка (Bubble Sort) массива строк.md`, блок «Терминал».
- **Цитата:** `# После сортировки: [C Go Rust TypeScript Kubernetes]`
- **Утверждение:** при запуске программы из того же файла выводится `[C Go Rust Kubernetes TypeScript]`. Ручная трассировка даёт то же: после первого прохода `Kubernetes` и `TypeScript` (обе длины 10) стоят в порядке `Kubernetes, TypeScript`; сортировка со строгим `>` стабильна и порядок равных элементов не меняет. Эталонный вывод в файле не получается ни одним корректным запуском.
- **Почему важно:** читатель сверяет результат с документом и решает, что ошибся сам; эталон выдуман.
- **Что проверить и где:** `go run main.go` в каталоге задачи. Исправить строку вывода. Заодно можно добавить замечание, что сортировка стабильна (это свойство, которое в задаче уместно назвать).
- **Тип:** код / факт.
- **Приоритет:** High.

### A-02 — ложный механизм в ответе на собеседовании (016)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/016. Динамическое заполнение матрицы 3x3 через формулу.md`, раздел «На собеседовании».
- **Цитата:** «Почему компилятор Go может автоматически развернуть циклы (Loop Unrolling) для маленьких массивов `[3][3]int`?» — «Потому что размер массива константен и мал … Разворачивание цикла устраняет накладные расходы…»
- **Утверждение:** gc в общем случае не разворачивает циклы. Проверка на Go 1.27.1: `go build -gcflags=-S` для функции, заполняющей `*[3][3]int` вложенными циклами, даёт ассемблер с обратными переходами: внешний цикл — `CMPQ CX, $3` / `JGE`, внутренний — `CMPQ BX, $3` / `JLT`. Цикл сохранён.
- **Почему важно:** на собеседовании это ответ с выдуманной оптимизацией компилятора; интервьюер его опровергнет, проверив ассемблер.
- **Что проверить и где:** `go build -gcflags=-S` на программе из блока «Код решения» 016 (или на функции `fill` из отчёта). Переформулировать ответ: компилятор не разворачивает такие циклы; константный размер позволяет проверки границ и адресацию без динамического пересчёта, но не разворот.
- **Тип:** факт / вывод.
- **Приоритет:** High.

### A-03 — категорическое «Нет» про кучу, опровергнутое кодом главы (007)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/007. Массив строк [3]string.md`, раздел «На собеседовании»; та же ошибка в «Под капотом» и в сравнении с кодом.
- **Цитата:** «Выделяется ли память в куче при объявлении `[3]string{"a", "b", "c"}` внутри функции?» — «Нет! Заголовки строк и сам массив располагаются на стеке функции…»
- **Утверждение:** ответ зависит от escape analysis, и категорическое «Нет» неверно. В самом решении массив передаётся в `fmt.Printf` как `...any`; `go build -gcflags=-m` выдаёт `languages escapes to heap` (и `uintptr(48) escapes to heap`). Копия массива уходит в кучу. Тот же эффект в 001 (`arr1 escapes to heap`, `arr2`, `arr3`) и в 021.
- **Почему важно:** это классический вопрос про стек и кучу; правильный ответ — «зависит от того, уходит ли ссылка или значение за пределы функции или в interface; проверяется `-gcflags=-m`». Категорическое «Нет» для любого массива засчитывают как ошибку.
- **Что проверить и где:** `go build -gcflags=-m` для блока «Код решения» 007. Переписать ответ: массив обычно на стеке, но попадает в кучу при боксинге в interface (в том числе при передаче в `fmt`), при возврате адреса или при захвате замыканием.
- **Тип:** факт / вывод.
- **Приоритет:** High.

### A-04 — стек как безусловное свойство массивов (001, 021)
- **Где:** 001 — `01. Инициализация, Zero Values, Value Semantics/001. Три способа инициализации массива.md`, «Под капотом»: «Массив выделяется единым непрерывным блоком на стеке.» 021 — `02. Указатели [N]T, unsafe.Sizeof_Alignof/021. Массив указателей [3]int и косвенная модификация.md`, «Под капотом»: «Эскейп-анализ может переместить переменные `x, y, z` в кучу, если их адреса покидают область видимости функции.»
- **Утверждение:** в 001 «выделяется на стеке» — неполно; в собственном решении `arr1, arr2, arr3` уходят в кучу из-за `fmt.Printf`. В 021 формулировка «может» подаёт как редкий случай то, что происходит в самом решении: `x, y, z moved to heap` и `ptrs escapes to heap` (`go build -gcflags=-m`).
- **Почему важно:** учебник формирует представление, что «массив = стек»; на практике переменная-массив часто не совпадает с его копией в interface.
- **Что проверить и где:** `-gcflags=-m` на обоих решениях. В 001 добавить оговорку; в 021 сказать прямо, что `fmt`-вызов переносит `x, y, z` в кучу.
- **Тип:** факт / вывод.
- **Приоритет:** Medium.

### A-05 — неверный механизм вычисления длины `[...]T` (012)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/012. Автовычисление размера массива компилятором.md`, «Под капотом».
- **Цитата:** «Синтаксический парсер AST подсчитывает количество узлов `ast.Expr` в списке инициализации и подставляет константу в определение `ast.ArrayType`.»
- **Утверждение:** парсер не подсчитывает элементы и не подставляет длину. Проверка `go/parser`: для `[...]int{1, 2, 3}` поле `ArrayType.Len` имеет тип `*ast.Ellipsis`. Длину вычисляет проверка типов (`go/types` / `types2`) по числу элементов литерала.
- **Почему важно:** это вопрос о фазах компилятора; учебник подменяет фазу.
- **Что проверить и где:** `go/parser` + `ParseFile` на `var a = [...]int{1,2,3}`, поле `Len`. Формулировку заменить на «длину вычисляет проверка типов».
- **Тип:** факт.
- **Приоритет:** Medium.

### A-07 — ложная «ошибка затенения» при повторном `:=` (003)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/003. Гарантия инициализации Zero Values.md`, «Подводные камни».
- **Цитата:** «Попытка повторной инициализации через `data := [5]int`: создаст затенение локальной переменной.»
- **Утверждение:** в той же области видимости, где уже объявлен `data`, это ошибка компиляции `no new variables on left side of :=` (проверено). Затенение возникает только во вложенном блоке (`if`, `for`, `{}`).
- **Почему важно:** учебник описывает не ту ошибку, а читатель, который встретит `no new variables`, не найдёт объяснения.
- **Что проверить и где:** `go build` на два `data := [5]int` подряд; переписать пункт с двумя случаями.
- **Тип:** факт.
- **Приоритет:** Medium.

### A-08 — «ошибка» `i <= j` в палиндроме (010)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/010. Проверка целочисленного массива на палиндром.md`, «Подводные камни».
- **Цитата:** «Неправильное условие выхода `i <= j` вместо `i < j`.»
- **Утверждение:** это не ошибка. С `i <= j` программа даёт те же результаты для `[1 2 3 3 2 1]` и `[1 2 3 4 2 1]` (проверено). Для нечётной длины средний элемент сравнивается сам с собой, что безвредно и лишь добавляет итерацию.
- **Почему важно:** ложная «ловушка» учит неверному различению и тратит внимание читателя.
- **Что проверить и где:** убрать пункт или заменить на реальную ловушку. Подходящий пример уже есть в 022: `i <= len(arr)` в обычном цикле по индексу даёт `panic: index out of range`. Для `i <= j` в палиндроме честно написать «лишняя итерация, не ошибка».
- **Тип:** факт.
- **Приоритет:** Medium.

### A-09 — неполный и смещённый ответ про копирование в `range` (022)
- **Где:** `02. Указатели [N]T, unsafe.Sizeof_Alignof/022. Классическое суммирование массива через C-style цикл с индексацией.md`, раздел «На собеседовании».
- **Цитата:** «Чем `for i := 0; i < len(arr); i++` эффективнее `for _, v := range arr` для массива `[1000]BigStruct`?» — «Прямая индексация `arr[i]` не копирует структуру `BigStruct` в промежуточную переменную.»
- **Утверждение:** неполно. По спецификации `range` по массиву с переменной значения вычисляет копию всего массива. Проверено: при `arr[2] = 100` внутри `for i, v := range arr` значение `v` на индексе 2 остаётся старым (3). Ответ должен называть копию массива, а не только копию элемента. Для `range &arr` и `range arr[:]` копии нет (проверено через указатель).
- **Почему важно:** это ровно тот механизм, который интервьюер проверяет; ответ даёт половину причины.
- **Что проверить и где:** программа из отчёта (`range arr` vs `range &arr`). Исправить ответ и сослаться на 027, где правило уже сформулировано верно.
- **Тип:** вывод / упущение.
- **Приоритет:** Medium.

### A-10 — термин «глубокое» для поверхностного копирования и сравнения (006, 013)
- **Где:** 006 — `01. Инициализация, Zero Values, Value Semantics/006. Значимая семантика (Value Semantics).md`, комментарий в коде: «Полное глубокое копирование массива a в b!». 013 — `01. Инициализация, Zero Values, Value Semantics/013. Comparable-семантика.md`, заголовок: «глубокое сравнение массивов одинаковой длины». Также «Pass by Value & Deep Copy» в `000. О главе.md` (раздел про содержание главы).
- **Утверждение:** Go копирует значение и сравнивает элементы поэлементно. Для элементов-указателей, срезов или строк копируется или сравнивается только сам заголовок или указатель, а не то, на что он указывает. Термин «deep copy» здесь неверен и в учебнике, где тема — семантика значений, вводит в заблуждение.
- **Почему важно:** именно здесь граница между значениями и ссылками; «глубокое» подсказывает читателю, что `[2]*int` копирует данные.
- **Что проверить и где:** добавить пример `[1]*int` (копия делит указатель, изменение через `*` видно в обоих) и заменить термин на «копирование значения (поверхностное для элементов-ссылок)».
- **Тип:** педагогика / факт.
- **Приоритет:** Medium.

### A-11 — ответ про несравнимость срезов и пробел в сравнении массивов (009)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/009. Сравнение массивов через ==.md`, раздел «На собеседовании»; «Теория» (пункт 1).
- **Цитата (ответ):** «…у срезов сравнение неоднозначно (…) и может приводить к зацикливанию на циклических структурах.»
- **Утверждение:** причина «зацикливание на циклических структурах» не подтверждена и не является основной. Официальное обоснование в Go FAQ («Why are map, slice, and function values not comparable?») — неоднозначность сравнения (поверхностное или глубокое, сравнение заголовков или содержимого). Сверить с FAQ перед тем, как оставлять такой ответ.
- **Пробел:** в «Теории» сказано, что массивы сравнимы «если их элементы сравнимы», но не сказано, что это проверяется во время выполнения. Проверено: `[1]any{[]int{1}} == [1]any{[]int{1}}` даёт `panic: runtime error: comparing uncomparable type []int`. Также `[1]float64{NaN} == [1]float64{NaN}` даёт `false`.
- **Почему важно:** на собеседовании спрашивают именно о сравнимости типов; «сравнимо» без оговорок об interface и NaN неполно.
- **Что проверить и где:** сверить обоснование с Go FAQ; добавить в «Подводные камни» пример с `any` и NaN.
- **Тип:** вывод / упущение.
- **Приоритет:** Medium.

### A-12 — «гарантирует отсутствие аллокаций в куче» (014)
- **Где:** `01. Инициализация, Zero Values, Value Semantics/014. Размер массива как часть сигнатуры типа.md`, раздел «На собеседовании».
- **Цитата:** «…Это гарантирует отсутствие аллокаций в куче, фиксированный размер и возможность использования хэша как ключа в `map`.»
- **Утверждение:** «гарантирует» неверно. Аллокации зависят от escape analysis: `[32]byte` уйдёт в кучу при передаче в `fmt` или при сохранении в interface (см. A-03). Остальные два свойства верны.
- **Что проверить и где:** `go build -gcflags=-m`; заменить «гарантирует» на «позволяет, если значение не уходит за пределы функции».
- **Тип:** вывод.
- **Приоритет:** Low.

### A-13 — «гарантированно прерывается» в Heartbleed (032)

- **Тип:** вывод.
- **Приоритет:** Low.

### A-14 — неполное «невозможна без создания среза» (014)

### A-15 — функция только для `[6]int`, условие говорит «массива» (010)

### A-17 — микроархитектурные и ABI-утверждения без проверки (008, 013, 016, 018, 027, 028, 029)
- **Где и цитаты:**
  - 008, «Под капотом»: «При вызове функции `CALL` рантайм копирует 40 байт.» Копирование делает код, который генерирует компилятор, а не рантайм.
  - 013, «Под капотом»: «`runtime.memequal` сравнивает память за один шаг.» Это вызов функции с циклом по байтам, а не один шаг.

## 3. Сквозные проблемы

- **Стек и куча (A-03, A-04, A-12).** Учебник несколько раз утверждает, что массивы «на стеке» или «не аллоцируют», и подкрепляет это ответами «Нет!» и «гарантирует». Собственные решения главы (`fmt.Printf` с массивами) опровергают эти утверждения. Нужна одна сквозная оговорка и проверка через `-gcflags=-m`.
- **Категорические ответы на собеседовании (A-02, A-03, A-09, A-12, A-13).** Ответы «ДА!», «Нет!», «гарантирует», «гарантированно» формулируют то, что зависит от условий. Стоит ввести правило: если ответ зависит от компилятора или версии, так и писать.
- **Не проверенные «под капотом» (A-17, A-18).** Ассемблерные и архитектурные детали часто не подтверждаются. Один общий проход по `-gcflags=-S` снял бы эту группу.
- **Терминология «глубокое» (A-10, A-11).** Во всей главе тема семантики значений, но термин «deep» используется неверно.
- **Тексты ошибок и версии (A-06, A-14).** Часть цитат устарела. Нужна привязка «текст зависит от версии Go» либо обновление текстов.
- **Эталонные выводы (A-01).** Один выдуманный вывод в 32 задачах. Остальные совпали с запуском, но стоит проверять все `Терминал` автоматически (как здесь).

## 4. Упущения главы

1. **Escape analysis и стоимость `fmt`-боксинга.** Глава должна хотя бы раз показать `go build -gcflags=-m` на одном примере: это связывает «стек» с реальным поведением.
2. **Копирование массива в `range` по значению.** Правило есть в 027, но без явной демонстрации. Пример с `arr[2] = 100` в теле цикла закрыл бы A-09 и тему «Значимой семантики».
3. **Сравнение массивов с interface и NaN.** См. A-11.
4. **Преобразование среза в массив** (`[3]int(s)`, Go 1.20; `(*[3]int)(s)`, Go 1.17). Важно для темы 014 и практики.
5. **Ограничение дженериков по длине.** Go не параметризует массив по `N`; стоит сказать об этом в 010 и 014.
6. **Современные функции.** `min`/`max` (Go 1.21, нужны в 028), `slices.Sort`, `slices.Equal`, `slices.Reverse`. Для учебника, который сам показывает ручные алгоритмы, достаточно упоминания в конце главы.
7. **Стабильность сортировки.** В 026 пузырёк стабилен; свойство стоит назвать, иначе эталонный вывод выглядит случайным (см. A-01).
8. **Крупные локальные массивы.** Compile-time порог, при котором локальный массив уходит в кучу, стоит упомянуть вместе с A-03; точное значение сверить в исходниках компилятора.
9. **Повторение.** 023 повторяет 008 (передача по значению и изоляция оригинала). Это не ошибка, но можно объединить.
