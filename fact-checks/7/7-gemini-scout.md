### 1. Упражнение 26: Неверный эталонный вывод (Wrong Expected Output), нарушение стабильности сортировки и противоречие со `step_by_step`
- **Раздел/Упражнение:** Упражнение 26 (`builder/gen_ch7_p2.py`, строки 517–578; `dist/007-massivy.html`, блок `ex-26`).

  ```go

      n := len(arr)
      for i := 0; i < n-1; i++ {
          for j := 0; j < n-i-1; j++ {
              if len(arr[j]) > len(arr[j+1]) {
                  arr[j], arr[j+1] = arr[j+1], arr[j]
              }
          }
      }
  }

  func main() {
      words := [5]string{"Kubernetes", "Go", "TypeScript", "C", "Rust"}
      BubbleSortByLength(&words)
      fmt.Printf("После сортировки: %v\n", words)
  }
  ```
  В блоке терминала указано:
  ```bash
  go run main.go
  # До сортировки:    [Kubernetes Go TypeScript C Rust]
  # После сортировки: [C Go Rust TypeScript Kubernetes]
  ```
- **Почему требует исправления:**
  1. **Неверный вывод:** Длины строк: `"Kubernetes"` = 10, `"TypeScript"` = 10. В коде используется строгое неравенство `len(arr[j]) > len(arr[j+1])`. Поскольку $10 > 10$ ложно (`false`), элементы с одинаковой длиной **никогда не меняются местами** (классическое свойство устойчивости Bubble Sort).      ```


  2. **Внутреннее противоречие со `step_by_step`:** В пункте 1 `step_by_step` (строка 527 `builder/gen_ch7_p2.py`) написано:
     *«1. Инициализируем массив `[5]string{"Go", "Kubernetes", "C", "Python", "Rust"}`»*.
     Однако в коде `main.go` массив инициализирован как `{"Kubernetes", "Go", "TypeScript", "C", "Rust"}`. В коде фигурирует `"TypeScript"`, а в шагах алгоритма — `"Python"`, начальный порядок также различается.
- **Необходимая проверка/тест:**
  Запуск `go run main.go` выдает:
  ```

  ```

### 2. Упражнения 26 и 31: Ошибочная ментальная модель: объявление параллельного присваивания «атомарным обменом» (Atomic swap)
- **Раздел/Упражнение:** Упражнение 26 (`builder/gen_ch7_p2.py`, строка 524) и Упражнение 31 (`builder/gen_ch7_p2.py`, строки 834, 854).
- **Фрагмент кода и текста:**
  В Упр. 26 (Theory):
  ```markdown
  - Атомарный обмен элементов на месте arr[j], arr[j+1] = arr[j+1], arr[j].
  ```
  В Упр. 31 (`main.go`, строка 834):
  ```go
  arr[i], arr[j] = arr[j], arr[i] // Атомарный swap на месте
  ```
- **Почему требует исправления:**
  1. В Computer Science и в рантайме Go термин **«атомарный» (atomic)** закреплен строго за неделимыми аппаратными операциями процессора (`LOCK CMPXCHG`, `atomic.Swap*`, `sync/atomic`), гарантирующими отсутствие гонок памяти и наблюдаемость промежуточных состояний другими потоками/горутинами.
  2. В Go параллельное кортежное присваивание (Tuple Assignment, §Assignments спецификации Go) вычисляется в два шага: сначала вычисляются адреса и значения всех выражений в правой части, затем они последовательно присваиваются переменным левой части с использованием временных стековых регистров.
  3. Эта операция **НЕ является аппаратно-атомарной и НЕ является потокобезопасной**. Если к `arr[i]` параллельно обратится другая горутина, произойдет Data Race и повреждение памяти.
  4. Формулировка «Атомарный swap» прививает учащимся грубо ошибочную ментальную модель, заставляя думать, что кортежный своп безопасен в конкурентном коде без мьютексов. Правильный термин — **«параллельное присваивание без временной переменной» (Tuple swap)**.
- **Необходимая проверка/тест:**
  Спецификация Go, раздел [Order of evaluations](https://go.dev/ref/spec#Order_of_evaluations) и [Assignments](https://go.dev/ref/spec#Assignments). Запуск `go test -race` на конкурентном вызове подтверждает гонку данных.
- **Приоритет:** **High**.

### 4. Упражнения 1, 2, 7: Категоричное утверждение «массив всегда выделяется на стеке без аллокаций в куче» игнорирует Escape Analysis
- **Раздел/Упражнение:** Упражнение 1 (Under the Hood, BigTech), Упражнение 2 (Under the Hood), Упражнение 7 (BigTech).
- **Утверждения в тексте:**
  - Упр. 1 (Under the Hood): *«Массив выделяется единым непрерывным блоком на стеке. `[5]int` занимает ровно 40 байт без служебных заголовков»*.
  - Упр. 1 (BigTech): *«`[...]int{1, 2}` создает статический массив `[2]int` на стеке (память $O(1)$ без аллокаций в куче)»*.
  - Упр. 7 (BigTech): *«Вопрос: Выделяется ли память в куче при объявлении `[3]string{"a", "b", "c"}` внутри функции? Ответ: Нет! Заголовки строк и сам массив располагаются на стеке функции...»*.
- **Почему требует проверки/исправления:**
  1. В Go компилятор определяет место размещения переменной (стек или куча) исключительно на основании **Escape Analysis (эскейп-анализа)**, а не на основании того, является ли тип массивом или срезом.
  2. Если массив передается аргументом в функцию, принимающую интерфейс `any` / `interface{}` (например, `fmt.Printf("%v\n", arr)` в коде решений упр. 1, 2, 7), массив упаковывается в интерфейс и **гарантированно утекает в кучу (escapes to heap)**!
  3. Аналогично, если берется адрес элемента массива и передается наружу (как в Упр. 2: `fmt.Printf("%p", &numbers[i])`), компилятор перемещает весь массив в кучу: `moved to heap: numbers`.
  4. Кроме того, массивы огромного размера (например, `[10000000]int`) превышают лимит размера стекового фрейма горутины и сразу аллоцируются в куче рантайма, даже если они не покидают область видимости.
  5. Для подготовки к собеседованиям уровня Middle+/Senior категоричный ответ «массив всегда создается на стеке без аллокаций» неверен и ведет к провалу на вопросах по оптимизации аллокаций памяти.
- **Необходимая проверка/тест:**
  Сборка с флагом эскейп-анализа: `go build -gcflags="-m" main.go` для кода Упр. 1 и Упр. 2:
  ```
  ./main.go:7:27: arr1 escapes to heap
  ./main.go:7:33: arr2 escapes to heap
  ./main.go:7:39: arr3 escapes to heap
  ./main.go:4:2: moved to heap: numbers
  ```
- **Приоритет:** **Medium**.

### 5. Упражнение 2: Неполное утверждение «`len(arr)` вычисляется на этапе компиляции и не требует инструкций в рантайме»
- **Раздел/Упражнение:** Упражнение 2 (`builder/gen_ch7_p1.py`, Theory, BigTech).
- **Утверждения в тексте:**
  - Theory: *«Функция `len(arr)` для массивов вычисляется на этапе компиляции (Compile-Time Constant) и не требует инструкций в рантайме»*.
  - BigTech: *«Вопрос: Является ли вызов `len(arr)` для массива `[100]int` функцией рантайма? Ответ: Нет! Для массивов `len(arr)` и `cap(arr)` являются константами времени компиляции (Compile-time Constants). Компилятор сразу подставляет число `100` в машинный код»*.
- **Почему требует проверки/исправления:**
  Согласно официальной спецификации Go ([Go Spec §Length and capacity](https://go.dev/ref/spec#Length_and_capacity)):
  > *"The expressions len(s) and cap(s) are constants if the type of s is an array or pointer to an array and the expression s does not contain channel receives or (non-constant) function calls; in this case s is not evaluated. Otherwise, invocations of len and cap are not constant and s is evaluated."*

  Если аргументом `len()` выступает вызов функции, возвращающей массив (`len(getArray())`), или чтение из канала (`len(<-ch)`), выражение **обязано вычисляться в рантайме** со всеми побочными эффектами (side effects). Попытка присвоить такой результат константе (`const L = len(getArray())`) приводит к ошибке компилятора: `len(getArray()) is not constant`. Безусловное утверждение в теории вводит в заблуждение относительно семантики языка.
- **Необходимая проверка/тест:**
  Код:
  ```go
  func f() [5]int { println("called"); return [5]int{} }
  const x = len(f()) // Ошибка: len(f()) is not constant
  ```
- **Приоритет:** **Medium**.

### 6. Упражнение 20: Упущение важной специфики `len` и `for range` для `nil`-указателя на массив `*[N]T`
- **Раздел/Упражнение:** Упражнение 20 (`builder/gen_ch7_p2.py`, Pitfalls, BigTech).
- **Текст в Pitfalls:**
  *«Передача `nil` указателя `var p *[5]int = nil; DoubleByPointer(p)`: вызовет `panic: runtime error: invalid memory address or nil pointer dereference`»*.
- **Почему требует проверки/исправления:**
  1. В Go работа с указателем на массив `*[N]T` содержит уникальную семантическую тонкость, являющуюся классической ловушкой на технических интервью:
     - Вызов `len(p)` для `var p *[5]int = nil` **НЕ ПАНИКУЕТ** и возвращает `5`, поскольку размер определяется типом;
     - Цикл `for i := range p` (только индекс) для `var p *[5]int = nil` **НЕ ПАНИКУЕТ** и корректно совершает ровно 5 итераций (0..4), так как рантайму не требуется разыменовывать указатель;
     - Паника возникает **только при попытке доступа к значению**: `arr[i]` (неявное разыменование `(*arr)[i]`) или в цикле со значениями `for i, v := range p`.
  2. В функции `DoubleByPointer(arr *[5]int)` цикл написан как:
     ```go
     for i := range arr {
         arr[i] *= 2
     }
     ```
     Здесь паникует именно строка `arr[i] *= 2`, а не сам заголовок цикла `for i := range arr`. Описание в Pitfalls и BigTech должно подчеркивать эту тонкость, иначе учащийся будет уверен, что любой `range` по `nil`-указателю на массив вызывает панику.
- **Необходимая проверка/тест:**
  ```go
  var p *[5]int = nil
  println(len(p)) // Выведет 5 без паники!
  for i := range p { println(i) } // Выведет 0 1 2 3 4 без паники!
  ```
- **Приоритет:** **Medium**.

### 7. Упражнения 9, 13, 30: Упущение не-сравнимых типов внутри массивов и рантайм-паник при сравнении `[N]any`
- **Раздел/Упражнение:** Упражнения 9, 13, 30 (`builder/gen_ch7_p1.py`, `builder/gen_ch7_p2.py`).
- **Утверждения в тексте:**
  - Упр. 9: *«Массивы в Go сравнимы операторами `==` и `!=`, если их элементы сравнимы»*.
  - Упр. 30: *«В Go ключом в `map[K]V` может быть только сравнимый тип (Comparable Type)... Массивы `[3]int` являются comparable -> их можно использовать как ключи»*.
- **Почему требует проверки/исправления:**
  1. Хотя условие «если их элементы сравнимы» упомянуто вскользь в Упр. 9, нигде в главе не приведены примеры того, что происходит, если элементы **не сравнимы**:
     - Массив срезов `[3][]int`, массив мап `[2]map[string]int` или функций `[2]func()` — **не являются comparable** и не компилируются при попытке сравнения `==` или использовании в качестве ключа map.
  2. Самая коварная ошибка в Go: **массив интерфейсов `[2]any`**. Он является синтаксически comparable на этапе компиляции, но если во время выполнения хотя бы в одном элементе окажется срез (`arr := [2]any{[]int{1}, "ok"}`), операция `arr1 == arr2` приведет к фатальной **runtime panic**:
     ```
     panic: runtime error: comparing uncomparable type []int
     ```
  3. Использование `[N]any` в качестве ключа map также приведет к краху программы при вставке такого ключа. Это важнейший аспект надежности высоконагруженных систем (Enterprise Reliability), который в главе полностью опущен.
- **Необходимая проверка/тест:**
  Спецификация Go ([Go Spec §Comparison operators](https://go.dev/ref/spec#Comparison_operators)).
- **Приоритет:** **Medium**.

### 8. Упражнение 28: Несоответствие условию задачи и преждевременное использование срезов `numbers[1:]`
- **Раздел/Упражнение:** Упражнение 28 (`sources/7. Массивы.md`, п. 28; `builder/gen_ch7_p2.py`, строки 630–690).
- **Условие задачи:** *«Поиск экстремумов: Заполните массив [10]int случайными числами. Напишите алгоритм, который находит минимальное и максимальное значения в этом массиве за один проход цикла»*.
- **Реализация в коде:**
  ```go
  numbers := [10]int{45, 12, 89, 3, 77, 92, 34, -5, 60, 18}
  minVal := numbers[0]
  maxVal := numbers[0]

  for _, n := range numbers[1:] {
      if n < minVal { minVal = n }
      if n > maxVal { maxVal = n }
  }
  ```
- **Почему требует проверки/исправления:**
  1. **Невыполнение части условия:** Массив не заполняется случайными числами (`rand.Intn` или `math/rand/v2`), а жестко зашит константным литералом. Хотя детерминизм полезен для тестов, в пояснении отсутствует комментарий о причине замены генератора случайных чисел на литерал.
  2. **Преждевременное использование среза:** В главе о массивах (Глава 7 предшествует Главе 8 «Слайсы») цикл использует выражение `numbers[1:]`. Для массива операция срезки `arr[1:]` неявно создает структуру заголовка среза (`SliceHeader`) на стеке. Методически правильнее и строже для темы массивов было бы итерироваться циклом с индексами `for i := 1; i < len(numbers); i++`.
  3. **Несоответствие описания в BigTech коду:** В вопросе с собеседования говорится о минимизации сравнений до $3N/2 - 2$ методом парного сравнения (Pairwise comparison), однако код решения реализует наивный алгоритм с $2(N-1) = 18$ сравнениями без пояснения разницы.
- **Приоритет:** **Medium**.

### 9. Упражнения 5 и 29: Платформозависимые допущения о разрядности `int` и выравнивании `int64`
- **Раздел/Упражнение:** Упражнение 5 (BigTech) и Упражнение 29 (Theory, BigTech).
- **Фрагменты текста:**
  - Упр. 5 (BigTech): *«Произойдет тихое беззнаковое/знаковое циклическое переполнение (Wrap Around) по модулю $2^{64}$ без генерации паники рантайма»*.
  - Упр. 29 (Theory): *«`unsafe.Alignof([100]int64)` = 8 байт»*.
- **Почему требует проверки/исправления:**
  1. В языке Go размер типа `int` является платформозависимым: на 32-битных архитектурах (386, arm, wasm) размер `int` равен 4 байтам (32 бита), и переполнение происходит по модулю $2^{32}$, а не $2^{64}$.
  2. Выравнивание `int64` на 32-битной архитектуре x86 (GOARCH=386) равно 4 байтам, а не 8 байтам.
  3. В технических материалах уровня Senior необходимо явно указывать контекст: *«на 64-битных платформах (amd64, arm64)»*, иначе утверждения фактологически неверны для 32-битных встраиваемых и WebAssembly систем.
- **Приоритет:** **Medium**.

### 11. Упражнения 2, 6, 21: Недетерминированные шестнадцатеричные адреса памяти в блоке терминала
- **Фрагмент:** В эталонном выводе терминала для Упр. 2, 6, 21 жестко зафиксированы виртуальные адреса памяти (например, `numbers[0] = 10 (адрес: 0xc0000b8000)`, `Массив a: ... (адрес: 0xc000014070)`).
- **Проблема:** При каждом новом запуске или на другой операционной системе из-за ASLR (Address Space Layout Randomization) и разного состояния рантайма базовые адреса стека/кучи будут иными (например, `0x38ca401a8000`). Хотя концептуально это демонстрирует шаг смещения (8 байт), новичков смущает буквальное несовпадение шестнадцатеричных цифр с выводом в книге. Рекомендуется либо добавить примечание о том, что адреса уникальны для каждого запуска, либо выводить относительное смещение (`uintptr(&arr[i]) - uintptr(&arr[0])`), как образцово сделано в Упр. 29.
- **Приоритет:** **Low**.

### 12. Упражнение 10: Неточное объяснение условия цикла в алгоритме проверки палиндрома
- **Фрагмент:** Pitfalls: *«Неправильное условие выхода `i <= j` вместо `i < j`»*.
- **Проблема:** Для массива четной длины (`[6]int`), используемого в задаче, указатели `i` и `j` стартуют с 0 и 5, сходясь к (1,4), затем (2,3), а на следующем шаге становятся (3,2). Ситуация `i == j` математически невозможна для массива четного размера! Для нечетного массива условие `i <= j` лишь выполнит одно лишнее безобидное сравнение центрального элемента с самим собой (`arr[mid] != arr[mid]`), что никогда не вернет `false`. Объявлять это критической ошибкой («Pitfall») некорректно.
- **Приоритет:** **Low**.

### 13. Упражнение 12: Небольшое расхождение между условием задачи и кодом решения
- **Фрагмент:** В условии сказано: *«Используй синтаксис `[...]int{10, 20, 30}`. Выведи длину массива»*. В коде решения объявлен массив из 6 элементов: `items := [...]int{10, 20, 30, 40, 50, 60}`.
- **Проблема:** Мелкое расхождение с исходным ТЗ.
- **Приоритет:** **Low**.

### 14. Упражнение 16: Упрощенное архитектурное утверждение об адресации x86-64 и инструкции `LEA`
- **Фрагмент:** Under the Hood: *«Инструкция `LEA` эффективно вычисляет линейный адрес ячейки за 1 такт CPU»*.
- **Проблема:** Для вычисления смещения в двумерной матрице `(i*3 + j)*8` требуется умножение на 3. В архитектуре x86-64 масштабные коэффициенты (scale) в адресации `[base + index*scale + disp]` ограничены степенями двойки: 1, 2, 4, 8. Умножение на 3 невозможно выполнить одной операцией адресации — компилятор генерирует `LEA rax, [rdi + rdi*2]` ($i + 2i = 3i$), после чего прибавляет `j` и масштабирует на 8. Утверждение является техническим упрощением.
- **Приоритет:** **Low**.

### 15. Упражнение 30: Реализационно-зависимое утверждение о хэшировании `aeshashbody`
- **Фрагмент:** Under the Hood: *«Хэш-функция вычисляет хэш от 24 байт массива `[3]int` напрямую через алгоритм `aeshashbody`»*.
- **Проблема:** Алгоритм `aeshashbody` используется рантаймом Go только на процессорах с аппаратной поддержкой инструкций AES (x86-64 с AES-NI или ARM64 с Crypto Extensions). На других платформах (RISC-V, MIPS, старые ARM) рантайм откатывается на программный `memhash`.
- **Приоритет:** **Low**.

## 💡 Важные упущения главы (Important Omissions)

Для учебника уровня Middle / Senior / Staff Go Developer в теме «Массивы» критически не хватает следующих фундаментальных тем:

1. **Приведение среза к массиву и указателю на массив (`Slice to Array Conversion`):**
   - В **Go 1.17** появилось преобразование среза в указатель на массив: `ptr := (*[4]byte)(slice)`.
   - В **Go 1.20** появилась прямая конвертация среза в значение массива с копированием: `arr := [4]byte(slice)`.
   - Если `len(slice) < N`, происходит паника в рантайме. Это важнейший мост между динамическими срезами и статическими массивами, постоянно применяемый при парсинге сетевых заголовков и криптографии (SHA-256 `[32]byte`).
2. **Индексированные (разреженные) литералы массивов (Keyed Composite Literals):**
   - Синтаксис `arr := [10]int{0: 1, 9: 99}` и `days := [...]string{Monday: "Пн", Tuesday: "Вт"}`.
   - Идиома BigTech: сопоставление iota-констант строковым именам через массивы фиксированной длины `[...]string{...}` со сложностью поиска $O(1)$ и нулевыми аллокациями вместо медленных `map` или громоздких `switch`.
3. **Оптимизация Bounds Check Elimination (BCE):**
   - Механизм устранения компилятором проверок выхода за границы массива в цикле.
   - Инспекция через флаг сборки `go build -gcflags="-d=ssa/check_bce"`.
   - Паттерн опережающей проверки (Early Bounds Check): фиктивное чтение `_ = arr[len-1]` перед циклом, снимающее проверки границ со всех итераций.
4. **Семантика цикла `for range` по массиву в Go 1.22:**
   - Почему `for i, v := range arr` копирует весь массив на стеке перед запуском цикла, а `for i := range arr` не копирует его.
   - Итерация по указателю `range &arr` как идиоматичный способ избежать копирования.
   - Новая семантика Go 1.22: изолированная область видимости переменной цикла на каждой итерации (Per-iteration variable scoping).
5. **Массивы нулевого размера `[0]T` и эффект выравнивания в структурах (Padding):**
   - Размер `unsafe.Sizeof([0]int{}) == 0`.
   - Специфика размещения нулевого поля в конце структуры: если поле размера 0 является последним полем структуры, компилятор добавляет паддинг (до 8 байт), чтобы указатель на следующее поле не выходил за пределы аллоцированного блока кучи.
