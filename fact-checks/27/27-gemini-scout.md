### G-03. Некорректный реляционный JOIN по совпадающим первичным ключам (`p.id = u.id`) в задаче ликвидации N+1
- **Где:** `sources/027. Реляционные базы данных (SQL и PostgreSQL)/04. Чистая архитектура Repository/152. Ликвидация проблемы N+1 запросов.md` → «## Код решения», `main.go` (строка 54)
- **Цитата:**
  ```sql
  SELECT u.id, u.name, p.id, COALESCE(p.title, "")
  FROM users u
  LEFT JOIN posts p ON p.id = u.id
  WHERE u.id <= 3
  ORDER BY u.id ASC;
  ```
- **Утверждение:** «Решение N+1: ровно 1 запрос с JOIN вместо сотен раундтрипов!», запрос связывает пользователей (авторов) с их опубликованными постами.
- **Почему проверить:** Условие соединения написано как `LEFT JOIN posts p ON p.id = u.id`. Это объединение первичного ключа таблицы постов (`posts.id`) с первичным ключом таблицы пользователей (`users.id`)!
  В реляционных базах данных посты связываются с автором через внешний ключ (Foreign Key): `p.user_id = u.id` (или `p.author_id = u.id`).
  При текущем условии `p.id = u.id` пост №1 привяжется к пользователю №1, пост №2 — к пользователю №2, независимо от того, кто реально является автором. Если у пользователя №1 написано 10 постов, он получит ровно 1 пост (с ID=1), а остальные 9 постов будут ошибочно приписаны пользователям с ID от 2 до 10. В учебнике по реляционным базам данных такая ошибка в фундаментальном SQL-запросе недопустима.
- **Что проверить и где:** Запустить SQL-запрос на реальной схеме с внешним ключом `posts.user_id`.
- **Тип:** код / факт
- **Приоритет:** High

### G-04. Потеря денег при переводе на несуществующий счет (123) и отсутствие проверки баланса (091)
- **Где:**
  - `sources/027. Реляционные базы данных (SQL и PostgreSQL)/04. Чистая архитектура Repository/123. Двусторонний межбанковский перевод.md` → «## Код решения», `main.go` (строки 57–60)
  - `sources/027. Реляционные базы данных (SQL и PostgreSQL)/03. Библиотеки sqlx, нативный драйвер pgx_v5/091. Имитация банковского перевода.md` → «## Код решения», `main.go` (строки 56–77)
- **Цитата:**
  - Задача 123: `// 2. Зачисление 
 _, err = tx.Exec("UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID) 
 if err != nil { return err } 
 return tx.Commit()`
  - Задача 091: `// Блокируем первый счет 
 _, err = tx.ExecContext(ctx, "SELECT balance FROM accounts WHERE id = $1 FOR UPDATE", firstLock) ... // Списание 
 _, err = tx.ExecContext(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID)`
- **Утверждение:** Код гарантирует атомарность банковского перевода, целостность балансов и защиту инварианта транзакции.
- **Почему проверить:**
  1. В задаче 123 шаг 1 (списание) корректно проверяет `RowsAffected`: `if n, _ := res1.RowsAffected(); n == 0 { return fmt.Errorf(...) }`. Однако шаг 2 (зачисление) **вообще не проверяет RowsAffected**! Если передан несуществующий счет получателя (`toID = 99999`), запрос `UPDATE accounts SET balance = balance + $1 WHERE id = 99999` выполняется успешно (`err == nil`), обновив 0 строк. Транзакция делает `tx.Commit()`, списывая деньги у отправителя в никуда. Ирония в том, что в блоке «На собеседовании» этой же задачи автор прямо спрашивает: *«Зачем проверять RowsAffected() при списании денег?»* и отвечает, что запрос возвращает `err == nil` при 0 обновленных строк — но сам забывает применить эту проверку к операции зачисления!
  2. В задаче 091 шаг 3 обещает: *«3. Проверим баланс и выполним списание/зачисление»*. Но в коде `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE` выполняется через `tx.ExecContext` — строки результата даже не сканируются в переменную! Баланс не проверяется вовсе, что позволяет списывать средства в бесконечный овердрафт при `balance < amount`. Более того, если `fromID == toID`, код дважды захватывает один и тот же ID и выполняет бессмысленный перевод самому себе.
- **Что проверить и где:** Запуск перевода с несуществующим `toID` в задаче 123; вызов перевода с суммой, превышающей баланс, в задаче 091.
- **Тип:** код / факт
- **Приоритет:** High

### G-18. Зависимость директивы `//go:embed` от внешних файлов миграций на диске при сборке (136)
- **Где:** `sources/027. Реляционные базы данных (SQL и PostgreSQL)/04. Чистая архитектура Repository/136. Встраивание миграций в бинарник через go.md` (строка 39)

## 3. Сквозные проблемы

1. **Масштабное дублирование однотипных тем (свыше 60 задач):** Глава перегружена повторяющимися вариациями транзакций с переводами (15 задач), вставками `RETURNING id` (5 задач), выборками `QueryRow` (5 задач), вызовами `CopyFrom` (5 задач) и `sqlx.Select` (5 задач) — см. [G-06](#g-06-массовое-взаимное-дублирование-задач-внутри-главы-11-крупных-кластеров-дублей). Это утомляет читателя и неоправданно раздувает объем книги.
2. **Имитация кода заглушками с `fmt.Println` вместо реальной реализации:** В задачах на сложные и ключевые темы (Testcontainers, TLS/SSL, сравнение GORM и sqlc, выбор goose и golang-migrate) авторы вместо реального кода оставили текстовые списки в `fmt.Println` (см. [G-02](#g-02-имитация-решений-заглушками-fmtprintln-с-полным-игнорированием-условий-задач), [G-07](#g-07-существенное-усечение-требований-в-задаче-финальный-босс-162)).
3. **Некомпилируемые файлы из-за забытых импортов:** Из-за добавления шаблонных импортов (`context`, `database/sql`, `time`) в задачи без реальной логики сразу 5 задач не проходят базовую компиляцию Go (см. [G-01](#g-01-ошибки-компиляции-в-5-задачах-из-за-неиспользуемых-импортов)).
4. **Систематическое игнорирование ошибок вызовов СУБД:** В десятках задач игнорируются ошибки `rows.Scan`, `tx.Commit`, `db.Exec`, `tx.Exec` (`_ = ...`), что прямо противоречит регламенту качества `AGENTS.md` § 3.2 (см. [G-15](#g-15-массовое-систематическое-подавление-ошибок-вызовов-databasesql)).
5. **Массовый сдвиг блока «Исходная формулировка» (156 задач):** В результате миграции старого задачника 156 из 163 задач получили чужие исходные формулировки от несвязанных упражнений (см. [G-16](#g-16-массовое-перемешивание-блоков-исходная-формулировка-по-всей-главе-156-задач)), что также привело к появлению битых ссылок на несуществующие номера упражнений (см. [G-17](#g-17-битые-ссылки-на-старые-номера-упражнений-в-блоке-исходная-формулировка-023-035-073-095)).

## 4. Упущения главы

Несмотря на рекордный размер главы (163 задачи), в ней полностью упущен ряд фундаментальных тем промышленной разработки высоконагруженных Go-сервисов с PostgreSQL:

1. **Обнаружение разорванных TCP-сокетов и механика `driver.ErrBadConn`:** В главе подробно настраиваются параметры пула (`SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime`), но нигде не раскрыто, как рантайм `database/sql` реагирует на сброс соединений межсетевым экраном (TCP silent drop / RST), как работает автоматический eviction "протухших" сокетов и почему вызовы `db.PingContext(ctx)` на старте недостаточны для защиты от периодических сетевых обрывов в Kubernetes.
2. **Бинарный протокол `pgx` и работа с составными/пользовательскими типами:** Драйвер `pgx/v5` известен поддержкой нативного бинарного формата через `pgtype.Map`. В главе нет примеров работы с перечислениями PostgreSQL (Enums `CREATE TYPE status AS ENUM (...)`), диапазонами (`tsrange`, `daterange`), составными типами (Composite Types) и кастомной регистрацией кодеков через `conn.TypeMap().RegisterType(...)`.
3. **Паттерн Transaction Manager / Unit of Work с вложенными транзакциями (Savepoints):** В главе есть упоминание сейвпоинтов в одной задаче, но отсутствует промышленная реализация интерфейса `TransactionManager`, позволяющего доменным сервисам открывать транзакции и управлять вложенными операциями (`SAVEPOINT` / `ROLLBACK TO SAVEPOINT`) без привязки бизнес-слоя к конкретному драйверу БД.
4. **Маршрутизация запросов при репликации (Read-Write Split):** В реальных HighLoad архитектурах запись направляется в Master (Primary), а чтение распределяется по Read-Only репликам. В главе нет ни одной задачи, раскрывающей паттерн разделения пулов соединений (`PrimaryPool` и `ReplicaPool`) или динамической маршрутизации запросов в зависимости от транзакционного контекста.
5. **Сетевое конвейерирование запросов (Query Pipelining в `pgx`):** Одной из ключевых архитектурных фич `pgx` является конвейеризация (Pipelining) — отправка пачки запросов без ожидания RTT ответа на каждый предыдущий. В главе этот механизм обойден стороной, хотя он дает многократный прирост пропускной способности в облачных и геораспределенных окружениях.
