## 🔴 Критический приоритет (High Priority)

### 1. Упражнение 57: Некомпилируемый код решения (`declared and not used`) и абсурдная логика `goto`
- **Раздел/Упражнение:** Упражнение 57 (`ex-57`, `builder/gen_ch5_p4.py`).
- **Заголовок/Задача:** «Осмысленное применение goto для выхода из многомерного поиска».
- **Фрагмент кода:**
  ```go
  func FindFirstNegativeMatrix(matrix [][]int) (int, int, int, bool) {
  	for rowIdx, row := range matrix {
  		for colIdx, val := range row {
  			if val < 0 {
  				// Осмысленное применение goto: мгновенный выход из двойного цикла
  				goto Found
  			}
  		}
  	}

  	return 0, 0, 0, false

  Found:
  	// Метка перехода
  	// Для чистоты кода извлекаем координаты первого отрицательного
  	for r, row := range matrix {
  		for c, v := range row {
  			if v < 0 {
  				return v, r, c, true
  			}
  		}
  	}
  	return 0, 0, 0, false
  }
  ```
- **Почему требует исправления:**
  1. **Код не компилируется:** В первом вложенном цикле переменные `rowIdx` и `colIdx` объявлены, но не используются внутри тела. Компилятор Go прерывает сборку с фатальной ошибкой:
     ```
     # command-line-arguments
     main.go:6:6: declared and not used: rowIdx
     main.go:7:7: declared and not used: colIdx
     ```
  2. **Абсурдная логика решения:** Алгоритм объявляет «осмысленное применение goto для выхода из двойного цикла», однако по метке `Found` запускает **точно такой же двойной цикл заново с самого начала матрицы**! Вместо того чтобы сохранить или сразу вернуть найденные `rowIdx`, `colIdx`, `val`, код выполняет повторный обход.
  3. **Несоответствие условию:** В условии задачи (`sources/5. Условные конструкции.md`, п. 57) сказано: *«goto: напишите алгоритм поиска первого отрицательного числа в срезе с использованием goto (аккуратно и осмысленно)»*. Решение же работает с матрицей `[][]int`, а не со срезом.
- **Необходимая проверка/тест:** `go run main.go` падает.
- **Решение:** Если демонстрируется выход из многомерного поиска, переменные `r, c, val` должны объявляться до цикла, либо цикл должен использовать именованный `break Label`, либо `goto` должен переходить на метку возврата, где эти переменные возвращаются. При этом `rowIdx` и `colIdx` должны быть использованы, либо заменены на `_`.
- **Приоритет:** **High**.

### 2. Упражнение 55: Неверный ожидаемый вывод (Wrong Expected Output) и ошибка подсчета гласных
- **Раздел/Упражнение:** Упражнение 55 (`ex-55`, `builder/gen_ch5_p4.py`).
- **Заголовок/Задача:** «Подсчет гласных букв в UTF-8 строке с помощью for range и switch».
- **Фрагмент кода и эталонный терминал:**
  ```go
  phrase := "Изучаем язык Go и высоконагруженный бэкенд!"
  count := CountVowels(phrase)
  fmt.Printf("Количество гласных букв: %d\n", count)
  ```
  В блоке терминала указано:
  ```bash
  go run main.go
  # Текст: "Изучаем язык Go и высоконагруженный бэкенд!"
  # Количество гласных букв: 16
  ```
- **Почему требует исправления:**
  Фактический запуск кода выводит:
  ```
  Количество гласных букв: 17
  ```
  Подсчет гласных по буквам:
  - `"Изучаем"`: **И, у, а, е** (4)
  - `"язык"`: **я, ы** (2)
  - `"Go"`: **o** (латинская, 1)
  - `"и"`: **и** (1)
  - `"высоконагруженный"`: **ы, о, о, а, у, е, ы** (7)  *(буква 'й' — согласная)*
  - `"бэкенд!"`: **э, е** (2)
  - **Итого:** $4 + 2 + 1 + 1 + 7 + 2 = 17$ гласных.
  В блоке терминала захардкожено число `16`. Это классическая ошибка «off-by-one», которая будет вводить в заблуждение студентов и автоматические тесты.
- **Необходимая проверка/тест:** Запуск `go run main.go` выдает 17.
- **Приоритет:** **High**.

### 3. Упражнение 48: Грубая логическая ошибка в валидаторе `checkCaps`
- **Раздел/Упражнение:** Упражнение 48 (`ex-48`, `builder/gen_ch5_p3.py`).
- **Заголовок/Задача:** «Логирование эффекта Short-Circuit при цепочке из трех булевых предикатов».
- **Фрагмент кода:**
  ```go
  func checkCaps(s string) bool {
  	fmt.Println("  [3] Вызов checkCaps...")
  	return strings.ToUpper(s) != strings.ToLower(s)
  }
  ```
- **Почему требует исправления:**
  Задача требует: *«проверяющие строку на длину, на наличие цифр и на наличие заглавных букв»*.
  Однако выражение `strings.ToUpper(s) != strings.ToLower(s)` проверяет не наличие заглавных букв, а **наличие хотя бы одной буквы алфавита, имеющей регистр**!
  Тест:
  - `checkCaps("abc")` возвращает `true` (т.к. `"ABC" != "abc"`), хотя в строке **нет ни одной заглавной буквы**!
  - `checkCaps("привет")` возвращает `true`, хотя заглавных букв нет.
  - `checkCaps("123!")` возвращает `false`.
  Студента обучают заведомо ложной логике валидации строк. Для проверки наличия заглавной буквы корректно использовать либо обход рун `unicode.IsUpper(r)`, либо `strings.ToLower(s) != s` (если приведение к нижнему регистру изменило строку, значит была хотя бы одна заглавная буква).
- **Необходимая проверка/тест:** `fmt.Println(checkCaps("abc"))` выдает `true`.
- **Приоритет:** **High**.

### 4. Упражнения 1 и 16: Ложные утверждения о синтаксисе компилятора Go и несуществующих warnings
- **Раздел/Упражнение:** 
  - Упражнение 1, блок теории (`builder/gen_ch5_p1.py`);
  - Упражнение 16, блок Pitfalls (`builder/gen_ch5_p1.py`).
- **Утверждения:**
  - Упр. 1: *«1. Круглые скобки вокруг условия `(x > 0)` **запрещены** (линтер и компилятор требуют `if x > 0`);»*
  - Упр. 16: *«Написание `if (isValid == true)`: компилятор выдаст предупреждение или ошибку синтаксиса скобок.»*
- **Почему требует исправления:**
  1. **Компилятор Go НЕ запрещает круглые скобки вокруг логического условия:** код `if (x > 0) { ... }` является полностью валидным с точки зрения Go Language Specification (раздел *If statements*). В грамматике `Expression` может быть заключено в круглые скобки: `(x > 0)` компилируется без ошибок.
  2. **Компилятор Go не генерирует предупреждений (warnings):** В философии Go отсутствует механизм warnings — код либо компилируется, либо выдает ошибку. Утверждение *«компилятор выдаст предупреждение»* в корне неверно и искажает архитектуру тулчейна Go.
  3. Круглые скобки удаляются утилитой `gofmt` (форматирование) и стилистическими линтерами, а не компилятором. Синтаксической ошибкой компилятора скобки становятся только если в них пытаются обернуть всё выражение вместе с инициализацией: `if (x := 1; x > 0)`, так как `;` недопустим внутри выражения в скобках.
- **Необходимая проверка/тест:** `echo 'package main; func main() { x := 1; if (x > 0) {} }' | go build -` компилируется с кодом 0 и без вывода в stderr.
- **Приоритет:** **High**.

### 6. Упражнение 40: Недостоверное утверждение о генерации Jump Table в компиляторе Go
- **Раздел/Упражнение:** Упражнение 40, блок Under the Hood (`builder/gen_ch5_p3.py`).
- **Утверждение:**
  *«Так как значения констант плотные (0, 1, 2, 3, 4), компилятор преобразует switch в Jump Table O(1).»*
- **Почему требует исправления:**
  В исходном коде компилятора Go (`cmd/compile/internal/walk/switch.go`, метод `tryJumpTable` для `exprSwitch`):
  ```go
  const minCases = 8   // have at least minCases cases in the switch
  const minDensity = 4 // use at least 1 out of every minDensity entries

  if len(cc) < minCases {
      return false // not enough cases for it to be worth it
  }
  ```
  Компилятор Go имеет жесткое ограничение: таблица переходов (Jump Table) для целочисленного `switch` строится **только при наличии как минимум 8 веток** (`minCases = 8`). Если веток меньше 8 (в задаче 40 их всего 5: 0, 1, 2, 3, 4), компилятор **никогда** не генерирует Jump Table, а строит бинарное дерево сравнений (Binary Search) со сложностью $O(\log N)$.
- **Необходимая проверка/тест:** Изучение `walk/switch.go` в стандартной библиотеке Go или ассемблерный листинг (`go tool compile -S`).
- **Приоритет:** **Medium**.

### 7. Упражнение 19: Неверное описание оптимизации строкового `switch` компилятором
- **Раздел/Упражнение:** Упражнение 19, блоки Under the Hood и BigTech (`builder/gen_ch5_p2.py`).
- **Утверждение:**
  *«Компилятор сортирует строковые литералы по значению хэша и длине, генерируя бинарный поиск с логарифмической сложностью O(log N) вместо наивного линейного перебора O(N).»*
- **Почему требует исправления:**
  Компилятор Go (`cmd/compile/internal/walk/switch.go`, функция `stringSearch`) **НЕ вычисляет хэши строк** для строкового `switch`! Хэширование строки в рантайме потребовало бы дорогостоящего вызова хэш-функции.
  Вместо этого компилятор применяет специальную схему:
  1. Группирует ветки по `len(str)` (сравнение длины строки — дешевая операция по полю `len` заголовка `string`).
  2. Для строк равной длины (при $\ge 4$ ветках) находит байтовый индекс `bestIdx`, максимально делящий множество кандидатов пополам, и строит дерево проверок по байту в знаковом диапазоне (для сохранения возможности CSE-слияния широких загрузок, issue #48222).
  Хэши типов (`_type.Hash`) используются компилятором исключительно в `Type Switch`, но не в строковом `switch`.
- **Необходимая проверка/тест:** `src/cmd/compile/internal/walk/switch.go`, строки 1213–1290.
- **Приоритет:** **Medium**.

### 8. Упражнение 46: Ошибочное утверждение о сложности $O(1)$ в пакете `unicode`
- **Раздел/Упражнение:** Упражнение 46, блок Under the Hood (`builder/gen_ch5_p3.py`).
- **Утверждение:**
  *«Пакет unicode использует сжатые таблицы диапазонов Unicode для O(1) классификации рун.»*
- **Почему требует исправления:**
  В пакете `unicode` (`src/unicode/letter.go`, функции `Is`, `is16`, `is32`) классификация рун по таблицам диапазонов `RangeTable` выполняется через **бинарный поиск** (`binary search over ranges`):
  ```go
  // binary search over ranges
  lo := 0
  hi := len(ranges)
  for lo < hi {
      m := int(uint(lo+hi) >> 1)
      ...
  }
  ```
  Сложность проверки руны в общем случае составляет $O(\log K)$, где $K$ — число интервалов диапазонов в таблице (для коротких таблиц — линейный поиск). Это не $O(1)$. Прямой доступ за $O(1)$ работает только для первых 256 символов (Latin-1 / ASCII fast-path).
- **Необходимая проверка/тест:** `src/unicode/letter.go`, функция `is16`.
- **Приоритет:** **Medium**.

### 9. Упражнение 9: Методическое противоречие в концепции обработки ошибок
- **Раздел/Упражнение:** Упражнение 9 (`ex-9`, `builder/gen_ch5_p1.py`).
- **Текст задачи и теории:**
  *«Напиши функцию Divide(a, b float64) (float64, error) и вызывай её через idiomatic if: if result, err := Divide(x, y); err != nil { ... } else { fmt.Println(result) }. Объясни, почему в Go принят именно такой стиль обработки ошибок.»*
- **Почему требует исправления:**
  Конструкция `if result, err := f(); err != nil { ... } else { ... }` **НЕ является идиоматичным стилем Go** для обработки ошибок. В сообществе Go и официальных Code Review Comments это считается антипаттерном («лесенка else», загоняющая полезную нагрузку в отступ).
  Идиомой Go является Guard Clause (Line of Sight):
  ```go
  result, err := Divide(x, y)
  if err != nil {
      // обработка ошибки и return
  }
  // использование result на основном уровне
  ```

## 💡 Важные упущения главы (Important Omissions)

Для курса уровня Middle → Senior / Staff Go Engineer в главе «Условные конструкции (if, switch)» критически не хватает следующих фундаментальных концепций:

1. **Typed nil vs Untyped nil в Type Switch (Один из топ-вопросов BigTech собеседований):**
   - Что произойдет при выполнении:
     ```go
     var p *int = nil
     var a any = p
     switch a.(type) {
     case nil:
         fmt.Println("nil")
     case *int:
         fmt.Println("*int")
     }
     ```
   - Программа выведет `*int`, а не `nil`! Ветка `case nil:` срабатывает **только** для нетипизированного `nil` (`any(nil)`), когда интерфейс не содержит ни типа, ни значения. Если интерфейс хранит типизированный указатель `(*int)(nil)`, его динамический тип равен `*int`. Это критический источник багов в production.
2. **Динамические (неконстантные) выражения в ветках `case` обычного `switch`:**
   - В отличие от языков C, C++, Java и C#, в Go ветки `case` **НЕ обязаны быть константами времени компиляции**!
   - В Go допустимы выражения: `switch x { case f(): case y + z: }`. Выражения вычисляются динамически сверху вниз в рантайме.
3. **Порядок вычисления и Short-Circuit в множественных `case A, B, C:`:**
   - В `case f(), g():` вычисление происходит строго слева направо. Если `f()` совпало со значением `switch`, функция `g()` **не вызывается вовсе**. Это важно при наличии сайд-эффектов.
4. **Компиляторная защита от дубликатов констант в `case`:**
   - Компилятор Go на этапе сборки пресекает наличие дублирующихся константных веток (`duplicate case 1 in switch`). При этом неконстантные ветки с одинаковыми значениями разрешены (выбирается первая).
5. **Строгие правила и ограничения `goto` в Go:**
   - В Упр. 57 используется `goto`, но не объяснены ключевые ограничения Go: оператор `goto` не имеет права перепрыгивать через объявление переменной в той же области видимости (`goto jumps over declaration`), и не может прыгать внутрь других блоков кода.
