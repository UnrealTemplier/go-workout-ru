## 2. Находки

### G-01. Массовое дублирование задач внутри главы (10 кластеров дублей)
- **Где:** `sources/025. HTTP-клиент/` (все разделы 01 и 02)
- **Цитата:** «В этом файле собраны уникальные упражнения по теме "HTTP-клиент (Запросы, заголовки, парсинг JSON)", отсортированные по возрастанию сложности.»
- **Утверждение:** Все задачи главы позиционируются как уникальные упражнения, развивающие навыки от простых к сложным.
- **Почему проверить:** Более 25 из 45 задач главы представляют собой почти дословные дубликаты друг друга с минимальными косметическими изменениями. Читатель вынужден многократно решать одни и те же кейсы:
  1. **Тюнинг пула Keep-Alive сокетов:** Задачи 008, 023, 043 — все три настраивают `MaxIdleConns`, `MaxIdleConnsPerHost`, `IdleConnTimeout` в `http.Transport`.
  2. **Опасности `http.DefaultClient` и таймауты:** Задачи 006, 007, 015, 028, 036 — пять задач повторяют одну и ту же мысль о `Timeout == 0` и инициализации безопасного `http.Client`.
  3. **Утечка сокетов и сброс в `io.Discard`:** Задачи 003, 013, 022, 033 — четыре задачи с одинаковым циклом запросов, оборачиванием в функцию и `io.Copy(io.Discard, resp.Body)`.
  4. **POST JSON полезной нагрузки:** Задачи 005, 011, 029 — три задачи сериализуют структуру в JSON и отправляют через `http.Post` / `http.NewRequest` с `application/json`.
  5. **Скачивание файла «на диск»:** Задачи 012 и 021 — обе обещают скачивание на диск без расхода памяти, и обе пишут в `bytes.Buffer`.
  6. **CookieJar сессии:** Задачи 016 и 042 — идентичный сценарий: `cookiejar.New(nil)`, запрос 1 ставит куку, запрос 2 читает куку.
  7. **Ретраи с Exponential Backoff:** Задачи 017 и 037 — две задачи реализуют одинаковый цикл повторов с `time.After(backoff)`, удвоением интервала и селектом с контекстом.
  8. **Разветвление потока через `io.TeeReader`:** Задачи 040 и 044 — обе используют `io.TeeReader` для записи в два `bytes.Buffer`.
  9. **Сборка Query-параметров:** Задачи 004, 019, 030 — дублирование работы с `url.Values` и `RawQuery`.
  10. **Потоковый JSON-парсинг:** Задачи 020 и 032 — обе декодируют ответ `GET` через `json.NewDecoder(resp.Body).Decode(&struct)`.
- **Что проверить и где:** Сопоставить условия и коды решений указанных задач; объединить повторяющиеся темы или заменить их на продвинутые сценарии (mTLS, `httptrace`, `io.Pipe`, streaming multipart).
- **Тип:** педагогика
- **Приоритет:** High

### G-02. Тихое отключение HTTP/2 в кастомном транспорте из-за отсутствия `ForceAttemptHTTP2: true`
- **Где:** `sources/025. HTTP-клиент/01. Базовые HTTP-запросы, таймауты, пулинг сокетов/007. Опасности http.DefaultClient в HighLoad.md` → «## Код решения», `main.go` (строки 36–47); `sources/025. HTTP-клиент/02. Промышленные паттерны/028. Архитектурный анализ рисков http.DefaultClient.md` → «## Код решения», `main.go` (строки 39–50)
- **Цитата:** `transport := &http.Transport{ Proxy: http.ProxyFromEnvironment, DialContext: (&net.Dialer{ Timeout: 2 * time.Second, KeepAlive: 30 * time.Second, }).DialContext, ...`
- **Утверждение:** Код конструирует эталонный production-клиент для высоконагруженных микросервисов.
- **Почему проверить:** В Go стандартный `http.Transport` автоматически включает поддержку HTTP/2 только при дефолтных параметрах. Если разработчик вручную задает поле `DialContext` (или `Dial`, `DialTLS`, `TLSClientConfig`), рантайм `net/http` **консервативно отключает HTTP/2** во избежание несовместимости, если явно не выставлен флаг `ForceAttemptHTTP2: true`. В коде обеих задач флаг отсутствует, из-за чего «продакшен-клиент» незаметно деградирует до HTTP/1.1 и теряет мультиплексирование потоков.
- **Что проверить и где:** Исходный код Go `src/net/http/transport.go` (комментарий к полю `ForceAttemptHTTP2`); вызов HTTPS эндпоинта с проверкой `resp.Proto` (вернет `HTTP/1.1` вместо `HTTP/2.0`).
- **Тип:** факт / код
- **Приоритет:** High

### G-03. Потоковое скачивание «на диск без расхода памяти» выполняется в `bytes.Buffer` в RAM
- **Где:** `sources/025. HTTP-клиент/01. Базовые HTTP-запросы.../012. Потоковое скачивание больших файлов на диск.md` (строки 49–57); `021. Прямое сохранение загружаемого файла через io.Copy.md` (строки 47–50); `02. Промышленные паттерны/038. Интерактивный прогресс-бар скачивания файла.md` (строка 69); `044. Одновременный вывод в консоль.md` (строка 53)
- **Цитата:** `var diskSimulator bytes.Buffer \n writtenBytes, err := io.Copy(&diskSimulator, resp.Body)` / `var fileOnDisk bytes.Buffer`
- **Утверждение:** «Реализуйте скачивание большого файла (например, видео или ISO-образа) с сохранением на диск через io.Copy, не загружая всё тело ответа в оперативную память», «с константной памятью O(1) RAM!».
- **Почему проверить:** Код решений задач 012, 021 и 044 объявляет локальную переменную `bytes.Buffer` и копирует весь входящий поток байтов прямо в оперативную память. Если пользователь попытается применить этот код для скачивания обещанного ISO-образа на 10 ГБ, приложение немедленно упадет по OOM (Out Of Memory). Задача 038 вообще отбрасывает байты в холостом `ProgressWriter.Write()`, не сохраняя файл ни на диск, ни в память. Для реальной демонстрации \(O(1)\) RAM необходимо использовать реальный файл на диске: `os.CreateTemp` или `os.Create("image.png")`.
- **Что проверить и где:** Запуск кода задач 012, 021, 038, 044; реализация `bytes.Buffer.Write` (динамическая аллокация в куче).
- **Тип:** код / условие↔решение
- **Приоритет:** High

### G-04. Прямая мутация `*http.Request` в методе `RoundTrip` нарушает контракт интерфейса
- **Где:** `sources/025. HTTP-клиент/02. Промышленные паттерны/034. Клиентский Middleware через переопределение.md` → «## Код решения», `main.go` (строки 45, 104)
- **Цитата:** `// Автоматически добавляем заголовок трассировки во все исходящие запросы \n req.Header.Set("X-Client-Trace-ID", "TRACE-UUID-998877")`
- **Утверждение:** Клиентский middleware модифицирует заголовки входящего `req *http.Request` напрямую перед передачей в базовый транспорт.
- **Почему проверить:** Согласно спецификации интерфейса `http.RoundTripper` в стандартной библиотеке Go: *«RoundTrip must not mutate the Request, other than by calling req.Body.Close()»*. Если запрос повторяется при ретрае или шарится между горутинами, прямая модификация мапы заголовков приводит к Data Race и непредсказуемым побочным эффектам. Более того, сам автор в разделе «Подводные камни» (строка 104) предупреждает: *«В RoundTrip нельзя модифицировать сам *http.Request без его клонирования (req.Clone(req.Context()))»*, однако в коде решения нарушает собственное предостережение.
- **Что проверить и где:** Документация интерфейса `http.RoundTripper` в `src/net/http/client.go`; запуск с флагом `-race` при параллельных запросах одного объекта `req`.
- **Тип:** код / педагогика
- **Приоритет:** High

### G-05. Серверный middleware (`http.Handler`, `statusRecorder`) ошибочно помещен в главу клиента с утечкой сокетов
- **Где:** `sources/025. HTTP-клиент/02. Промышленные паттерны/024. Логирующий Middleware для HTTP-сервера и клиента.md` → «## Код решения», `main.go` (строки 32–53, 74–75)
- **Цитата:** `type statusRecorder struct { ... } \n func LoggingMiddleware(next http.Handler) http.Handler { ... }` / `_, _ = http.Get(...) \n _, _ = http.Post(...)`
- **Утверждение:** Задача иллюстрирует работу Middleware в контексте главы 25 «HTTP-клиент».
- **Почему проверить:** 
  1. Архитектурно код полностью посвящен серверному middleware (`http.HandlerFunc`, оборачивание `http.ResponseWriter`), что является предметом Главы 26 («HTTP-сервер»). Клиентский middleware в Go строится исключительно на базе `http.RoundTripper` (что разбирается в задаче 034).
  2. В тестовом блоке клиента (строки 74–75) вызовы `http.Get` и `http.Post` вообще не вычитывают ответ и не вызывают `defer resp.Body.Close()`, допуская утечку сокетов прямо в главе, которая учит избегать утечек.
- **Что проверить и где:** Сопоставить тему задачи 024 с оглавлением главы 25 и главы 26; проверить закрытие `resp.Body` в строках 74–75.
- **Тип:** педагогика / код
- **Приоритет:** High

### G-06. Игнорирование ошибки сетевого запроса перед вызовом `resp.Body.Close()`
- **Где:** `sources/025. HTTP-клиент/01. Базовые HTTP-запросы.../016. Управление состоянием сессий с помощью CookieJar.md` (строки 66–70); `02. Промышленные паттерны/025. Установка кастомных HTTP-заголовков User-Agent.md` (строки 40–51); `02. Промышленные паттерны/042. Инициализация CookieJar и автоматическая передача.md` (строки 62–67)
- **Цитата:** `resp1, _ := client.Get(ts.URL + "/login") \n resp1.Body.Close()` / `r1, _ := client.Get(ts.URL + "/set") \n r1.Body.Close()`
- **Утверждение:** Сетевой запрос выполняется с подавлением ошибки `_`, после чего сразу вызывается `Body.Close()`.
- **Почему проверить:** Если запрос завершится сетевым сбоем (DNS lookup error, connection refused, таймаут), переменная `resp` будет равна `nil`. Немедленный вызов `resp1.Body.Close()` приведет к аварийной панике `panic: runtime error: invalid memory address or nil pointer dereference`. Это грубейшее нарушение правил надежности (`AGENTS.md` § 3.2). При этом в задаче 001 на собеседовании прямо подчеркивается: *«Почему проверка if err != nil должна идти ДО defer resp.Body.Close()? Ответ: resp будет равен nil, что приведет к фатальной панике»*. В задачах 016, 025 и 042 автор пренебрегает этим правилом.
- **Что проверить и где:** Запустить код задач 016, 025, 042 с некорректным URL сервера (например, `http://127.0.0.1:1`); убедиться в возникновении паники.
- **Тип:** код
- **Приоритет:** High

### G-07. Оборачивание `nil` ошибки через `%w` в цикле повторных попыток
- **Где:** `sources/025. HTTP-клиент/01. Базовые HTTP-запросы.../017. Отказоустойчивый HTTP-клиент с повторными.md` → «## Код решения», `main.go` (строки 55–57)
- **Цитата:** `if attempt == maxRetries { return nil, fmt.Errorf("исчерпаны все %d попыток: %w", maxRetries, err) }`
- **Утверждение:** При исчерпании лимита попыток возвращается информативная ошибка с цепочкой вызовов.
- **Почему проверить:** Если удаленный сервер отвечает HTTP 503 или 502, сетевой вызов `client.Do(req)` завершается успешно с `err == nil`. Код проверяет `if err == nil && resp.StatusCode < 500`. Так как статус 503, условие ложно, и на последней итерации `err` по-прежнему равен `nil`. В результате `fmt.Errorf("...: %w", err)` форматирует ошибку как `"исчерпаны все 3 попыток: %!w(<nil>)"`, полностью теряя код ответа сервера и ломая `errors.Unwrap`.
- **Что проверить и где:** Запустить `getWithRetry` против сервера, постоянно возвращающего 503; проверить текст ошибки и поведение `errors.Is`/`errors.As`.
- **Тип:** код
- **Приоритет:** Medium

### G-08. Ошибка подсчета байт (off-by-one) в ожидаемом выводе терминала и расхождение с условием
- **Где:** `sources/025. HTTP-клиент/01. Базовые HTTP-запросы.../002. Чтение тела HTTP-ответа (Response Body).md` (строки 5, 50, 65)
- **Цитата:** Условие: «выведи первые 100 байт в консоль»; Код: `limit := 60`; Вывод: `# [HTTP Body] Всего считано: 107 байт`
- **Утверждение:** Ожидаемый вывод сообщает о чтении 107 байт.
- **Почему проверить:**
  1. Тестовая строка `"Go is an open source programming language that makes it easy to build simple, fast, and reliable software."` в UTF-8 насчитывает ровно 106 байт. Реальный вывод программы — `Всего считано: 106 байт`. В ожидаемом выводе допущена ошибка off-by-one (107 байт).
  2. Условие прямо требует: *«выведи первые 100 байт в консоль»*, а в коде и шаге 3 задан лимит `limit := 60`.
- **Что проверить и где:** `len([]byte("Go is an open source programming language that makes it easy to build simple, fast, and reliable software."))` = 106.
- **Тип:** вывод / условие↔решение
- **Приоритет:** Medium

### G-09. Несоответствие ожидаемого размера multipart-файла реальному выводу
- **Где:** `sources/025. HTTP-клиент/01. Базовые HTTP-запросы.../014. Отправка multipart_form-data запроса с загрузкой.md` (строка 98)

- **Утверждение:** Ожидаемый вывод утверждает, что размер файла равен 78 байтам.
- **Почему проверить:** Передаваемая в коде строка `"Текст официального договора оказания услуг."` состоит из 39 русских символов (по 2 байта в UTF-8 = 78 байт) плюс 3 пробела (3 байта) и 1 точка (1 байт). Суммарная длина среза байт равна 82 байтам без точки или 81 байту с точкой (в коде: 81 байт). Реальный запуск программы выводит `Размер: 81 байт`. В ожидаемом выводе зафиксировано неверное число 78.
- **Что проверить и где:** Запуск `go run main.go` в задаче 014.
- **Тип:** вывод
- **Приоритет:** Low

### G-10. Недетерминированный вывод из-за случайного обхода `map` и потеря статус-кода
- **Где:** `sources/025. HTTP-клиент/02. Промышленные паттерны/041. Параллельный опрос 10 микросервисов со сбором.md` (строки 5, 82–85, 96)
- **Цитата:** `for k, v := range store.data { fmt.Printf(" -> %s = %s\n", k, v); break }`
- **Утверждение:** Терминал детерминированно обещает вывод первой записи: `-> http://127.0.0.1:.../service/1 = Response for /service/1`.
- **Почему проверить:**
  1. В Go итерация по мапе специально рандомизирована рантаймом. Конструкция `for ... range map { break }` возвращает псевдослучайный ключ. При запуске код выдает `/service/10`, `/service/7` или любой другой URL, что не соответствует тексту терминала.
  2. Условие требует: *«Соберите результаты (статус-коды и тела ответов) в потокобезопасную мапу»*. В реализации метод `store.Set` принимает только `string(body)`, а статус-код ответа полностью теряется.
- **Что проверить и где:** Запустить код задачи 041 несколько раз; сверить сигнатуру `SafeStore.Set` с условием.
- **Тип:** вывод / условие↔решение
- **Приоритет:** Medium

### G-12. Сравнение с `http.DefaultClient` полностью отсутствует в реализации

- **Утверждение:** Программа показывает разницу между поведением `http.DefaultClient` и кастомного клиента.

## 3. Сквозные проблемы

1. **Массовое взаимное дублирование задач:** 10 смысловых кластеров охватывают более 55% задач главы (см. [G-01](#g-01-массовое-дублирование-задач-внутри-главы-10-кластеров-дублей)). Разделы 1 и 2 содержат параллельные копии одних и тех же тем (пулинг сокетов, ретраи с backoff, сброс тела в `io.Discard`, таймауты `DefaultClient`, `CookieJar`, `io.TeeReader`).
2. **Имитация файловых операций в памяти (RAM):** В задачах 012, 021, 038, 044 вместо реальной файловой системы (`*os.File`, `os.CreateTemp`) для «сохранения на диск» используется `bytes.Buffer`, что создает иллюзию понимания потокового I/O, но в реальности потребляет гигабайты RAM (см. [G-03](#g-03-потоковое-скачивание-на-диск-без-расхода-памяти-выполняется-в-bytesbuffer-в-ram)).
3. **Игнорирование сетевых ошибок и опасный `resp.Body.Close()`:** В задачах 016, 024, 025, 042 ошибки вызовов `client.Get` / `client.Do` игнорируются через `_`, после чего немедленно вызывается `resp.Body.Close()`, что приводит к панике при любом сетевом сбое (см. [G-05](#g-05-серверный-middleware-httphandler-statusrecorder-ошибочно-помещен-в-главу-клиента-с-утечкой-сокетов), [G-06](#g-06-игнорирование-ошибки-сетевого-запроса-перед-вызовом-respbodyclose)).
4. **Подавление ошибок стандартных библиотечных вызовов:** Практически повсеместно в главе игнорируются ошибки `json.Marshal`, `json.NewDecoder().Decode()`, `io.ReadAll`, `io.Copy`, `url.Parse` (`_ = ...`), что нарушает стандарт надежности `AGENTS.md` § 3.2.
5. **Тихое замалчивание ошибок в параллельных горутинах:** В задачах 023, 039, 041 ошибки внутри рабочих горутин обрабатываются конструкцией `if err != nil { return }`. Ошибка не передается в канал, не логируется и не агрегируется, приводя к тихой потере данных.

## 4. Упущения главы

Глава 25 подробно рассматривает базовые запросы и параметры `http.Transport`, однако оставляет за рамками ключевые темы промышленной разработки клиентского сетевого стека в Go:

1. **Инспекция сетевого цикла через `net/http/httptrace` (`ClientTrace`):** В главе многократно утверждается, что соединение Keep-Alive «было переиспользовано» (задачи 008, 022, 033, 043), однако нигде не показан стандартный инструмент Go для доказательства переиспользования: `httptrace.ClientTrace{GotConn: func(info httptrace.GotConnInfo) { ... info.Reused ... }}`. Трассировка DNS, TLS и времени коннекта полностью отсутствует.
2. **Конфигурация TLS для микросервисов (`crypto/tls`):** В реальных HighLoad и Enterprise-системах клиент настраивает `tls.Config`: добавление доверенных корпоративных сертификатов (`RootCAs`), взаимная аутентификация клиентов (mTLS / Client Certificates через `Certificates: []tls.Certificate`), настройка версий `MinVersion: tls.VersionTLS13`. В главе тема TLS-конфигурации клиента отсутствует вовсе.
3. **Потоковая передача данных без буферизации через `io.Pipe`:** В вопросах собеседований задач 011 и 014 автор упоминает `io.Pipe` как идеальный способ передачи больших JSON и Multipart тел с \(O(1)\) памяти, однако практического упражнения с `io.Pipe(pr, pw)` в главе нет.
4. **Настройка HTTP/2 и HTTP/3 (QUIC):** Нет демонстрации тонкостей работы HTTP/2 (мультиплексирование, отмена стрима через `RST_STREAM`, настройка `golang.org/x/net/http2`).
5. **Прерывание медленной вычитки тела (Slowloris на клиенте):** Таймаут `client.Timeout` действует на всю операцию, но если требуется разделять таймаут на получение заголовков (`ResponseHeaderTimeout`) и таймаут на непрерывную вычитку чанков (`readTimeout` через контекст или кастомный ридер), в главе это не показано.
