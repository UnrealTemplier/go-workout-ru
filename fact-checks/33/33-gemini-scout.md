### G-01. Опечатка в имени метода и паника RUnlock незалоченного мьютекса
- **Где:** `01. Декомпозиция монолита, API Gateway/011. Паттерн CQRS.md` → ## Код решения, `cqrs_architecture_test.go`, строки 74–80
- **Цитата:** «s.readDB.mu.RUnlock()\n\tdefer s.readDB.RUnlock()\n\ts.readDB.mu.RLock()»
- **Утверждение:** Метод `ExecuteGetProductQuery` потокобезопасно читает из `readDB`.
- **Почему проверить:** Здесь сразу две грубейшие ошибки:
  1. В строке `defer s.readDB.RUnlock()` пропущено поле `.mu.` — тип `*ReadModelStore` не имеет метода `RUnlock`. Компилятор падает: `s.readDB.RUnlock undefined (type *ReadModelStore has no field or method RUnlock)`.
  2. В первой строке функции вызывается `s.readDB.mu.RUnlock()` ДО взятия блокировки `RLock()`! Даже если исправить опечатку, при первом же вызове рантайм Go выбросит фатальную панику: `fatal error: sync: RUnlock of unlocked RWMutex`.
  При этом в блоке терминала нарисован вывод `--- PASS: TestCQRSFlow (0.00s)`.
- **Что проверить и где:** `go test -v` на коде задачи.
- **Тип:** код / вывод

### G-15. Гонка данных и пробитие состояния Half-Open в CustomCircuitBreaker
- **Где:** `01. Декомпозиция монолита, API Gateway/018. Предохранитель Circuit Breaker.md` → ## Код решения, строки 84–95
- **Цитата:** «if cb.state == StateOpen {\n\tif now.Sub(cb.lastStateTime) > cb.cooldown {\n\t\tcb.state = StateHalfOpen\n...}\ncb.mu.Unlock()\n\nerr := action()»
- **Утверждение:** Реализован автомат состояний Closed, Open и HalfOpen с пропуском 1 пробного запроса.
- **Почему проверить:** Мьютекс `cb.mu.Unlock()` отпускается перед вызовом `action()`. В состоянии `HalfOpen` проверка `if cb.state == StateOpen` возвращает `false`. При конкурентных запросах сотни параллельных горутин одновременно пройдут в `action()`, обрушив лавину запросов на восстанавливающийся сервис вместо строго одного пробного запроса. Кроме того, в строке 145 поле `cb.state` читается в тесте без захвата мьютекса при потенциально параллельной работе (`go test -race`).
- **Что проверить и где:** Спецификация паттерна Circuit Breaker (Martin Fowler / Microsoft Cloud Patterns); запуск с `-race`.
- **Тип:** код / педагогика
- **Приоритет:** High

### G-16. Дедлок шины сообщений InMemoryMessageBroker при медленном подписчике
- **Где:** `02. Наблюдаемость (Prometheus, Jaeger, pprof), Docker/056. Событийно-ориентированная архитектура.md` → ## Код решения, строки 62–68
- **Цитата:** «func (b *InMemoryMessageBroker) Publish(event OrderCreatedEvent) {\n\tb.mu.Lock()\n\tdefer b.mu.Unlock()\n\tfor _, ch := range b.subscribers {\n\t\tch <- event\n\t}\n}»
- **Утверждение:** Потокобезопасная шина Pub/Sub сообщений.
- **Почему проверить:** Отправка в канал подписчика `ch <- event` выполняется синхронно под эксклюзивным локом `b.mu.Lock()`. Каналы подписчиков буферизированы всего на 10 элементов. Если один подписчик медленно вычитывает события, его буфер заполнится, горутина вызова `Publish` навсегда заблокируется на записи в канал, удерживая `b.mu.Lock()`. Вся шина, все другие издатели и новые подписчики дедлочатся навсегда.
- **Что проверить и где:** Сравнить с паттерном неблокирующего вещания в задаче 067 (`select case ch <- msg: default:`).

### G-17. Отмена контекста срывает компенсирующие транзакции Saga
- **Где:** `01. Декомпозиция монолита, API Gateway/008. Паттерн Saga.md` → ## Код решения, строки 72–80
- **Цитата:** «func (sm *SagaManager) rollback(ctx context.Context, completed []SagaAction) {\n...\n\t_ = action.Compensate(ctx)\n}»
- **Утверждение:** Корректный откат транзакций при сбое одного из шагов.
- **Почему проверить:**
  1. Если сбой шага произошел из-за истечения дедлайна или отмены родительского контекста (`ctx.Err() != nil`), передача того же `ctx` в `action.Compensate(ctx)` приведет к мгновенному падению всех компенсирующих действий с ошибкой `context canceled`! Для компенсаций необходим отвязанный контекст (`context.WithoutCancel(ctx)` в Go 1.21+ или свежий контекст с независимым таймаутом).
  2. Ошибка компенсации игнорируется: `_ = action.Compensate(ctx)` — нарушение правила `AGENTS.md` § 3.2 («Игнорировать if err != nil»).
- **Что проверить и где:** Go 1.21 `context.WithoutCancel`.
- **Тип:** код / педагогика
- **Приоритет:** High

### G-26. Фактическая ошибка: утверждение о немедленном SIGKILL при сбое Liveness Probe

## 4. Упущения главы

1. **Отсутствие практики генерации кода Protobuf/gRPC:**
   Хотя глава заявляет стек gRPC 1.22+, в ней нет ни одного примера запуска `protoc` или `buf generate` с флагами `--go_out` и `--go-grpc_out`. В задаче 082 даны только конфигурационные файлы `buf.yaml`.

2. **Отсутствие mTLS в коде:**
   В описании главы и условиях задач неоднократно упоминается взаимная аутентификация mTLS (Mutual TLS) между сервисами, однако ни в одной задаче нет кода настройки `credentials.NewTLS`, `tls.Config{ClientAuth: tls.RequireAndVerifyClientCert}` и загрузки клиентских/серверных сертификатов.

3. **Отсутствие распределенных блокировок (Distributed Locks):**
   Не рассмотрены паттерны распределенной синхронизации (Redis Redlock, etcd concurrency mutex / lease), критически важные для микросервисной архитектуры при предотвращении гонок между подами.

4. **Отсутствие реального клиента брокера сообщений:**
