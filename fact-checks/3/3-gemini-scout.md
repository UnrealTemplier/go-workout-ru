## Детальный реестр кандидатов для проверки

### 1. Упражнение 18: Невалидный код для статического анализатора (`go vet`) при выводе функции
* **Упражнение/Раздел:** Упражнение 18 («Инспекция типов переменных через спецификатор %T»).
* **Фрагмент кода:**
  ```go
  fn := func(x int) bool { return x > 0 }
  fmt.Printf("fn:  значение = %v, тип = %T\n", fn, fn)
  ```
* **Почему требует проверки:** Стандартный статический анализатор Go выдает ошибку:  
  `fmt.Printf format %v arg fn is a func value, not called`  
  В Go передача невызванной функции под спецификатор `%v` в `Printf` считается вероятной опечаткой программиста (ожидался вызов `fn(x)`). Код не пройдет валидацию в CI/CD при включенном `go vet`. Если требовалось вывести адрес функции, идиоматично использовать `%p`. Кроме того, адрес `0x48a240` в ожидаемом выводе является недетерминированным из-за ASLR.
* **Необходимые доказательства/тест:** Запуск `go vet` на файле упражнения.
* **Приоритет:** **High**

### 2. Упражнение 25: Ошибка `go vet` из-за спецификаторов в `fmt.Println`
* **Упражнение/Раздел:** Упражнение 25 («Экранирование строк и спецсимволов через спецификатор %q»).
* **Фрагмент кода:**
  ```go
  fmt.Println("--- Вывод через %s (интерпретированный): ---")
  fmt.Printf("%s\n\n", raw)

  fmt.Println("--- Вывод через %q (безопасный экранированный): ---")
  fmt.Printf("%q\n", raw)
  ```
* **Почему требует проверки:** `go vet` завершается с ошибками:  
  `ex_25.go:8:2: fmt.Println call has possible Printf formatting directive %s`  
  `ex_25.go:11:2: fmt.Println call has possible Printf formatting directive %q`  
  Анализатор Go запрещает использовать глаголы форматирования в функциях семейства `Print`/`Println`, так как это распространенная ошибка перехода с `Printf`. Для чистоты кода строки заголовков должны экранироваться (`%%s`), либо выводиться через `fmt.Println("--- Вывод через", "%s", "...")`.
* **Необходимые доказательства/тест:** Запуск `go vet test_25.go`.
* **Приоритет:** **High**

### 4. Упражнения 48 и 59: Ложное утверждение, что спецификатор ширины `%s` в `fmt` считает байты, а не руны
* **Упражнение/Раздел:** 
  - Упражнение 48 (раздел `pitfalls`)
  - Упражнение 59 (раздел `pitfalls`)
* **Фрагмент текста:**
  - Упр. 48: *«fmt.Sprintf рассчитывает ширину `%-12s` по байтам, а не по рунам. Для многобайтовых символов UTF-8 (русские буквы) ширина может незначительно сдвинуться при прямом использовании `%12s`. Для точного выравнивания UTF-8 используют функцию с `utf8.RuneCountInString`»*.
  - Упр. 59: *«В пакете `fmt` ширина `%16s` считает байты. Если в выводе важна абсолютная точность Unicode-символов, используют библиотеку `olekukonko/tablewriter`»*.
* **Почему требует проверки:** **Это грубая фактологическая ошибка.** Согласно официальной спецификации пакета `fmt`:  
  > *«Width and precision are measured in units of Unicode code points, that is, runes, or in bytes for %x when applied to a string or byte slice.»*  
  В стандартной библиотеке Go (`src/fmt/format.go`, метод `fmt_s`) ширина строки ВСЕГДА рассчитывается через подсчет рун (`utf8.RuneCount` / `utf8.RuneCountInString`).  
  Тест: `"Москва"` (6 рун, 12 байт) при `fmt.Sprintf("%10s", "Москва")` дополняется РОВНО 4 пробелами до 10 рун. Если бы ширина считалась по байтам, пробелы бы не добавились вовсе (12 >= 10). Сдвиг в терминале может возникать ТОЛЬКО для символов нулевой ширины (комбинируемые диакритики) или двойной ширины (CJK и некоторые эмодзи), но не для стандартной кириллицы!
* **Необходимые доказательства/тест:** Код Go `fmt.Sprintf("%10s", "Москва")`, исходники `src/fmt/format.go`.
* **Приоритет:** **High**

### 5. Упражнение 26: Ошибочный ожидаемый вывод и искажение правил пробелов в `fmt.Print`
* **Упражнение/Раздел:** Упражнение 26 («Отличие поведения fmt.Println и fmt.Print»).
* **Фрагмент кода и вывода:**
  ```go
  fmt.Print("Строка 1", "Строка 2", 100)
  ```
  Заявленный ожидаемый вывод в JSON:
  ```text
  # === Вызовы fmt.Print ===
  # Строка 1Строка 2 100Строка 3
  ```
  Фактический вывод рантайма Go:
  ```text
  === Вызовы fmt.Print ===
  Строка 1Строка 2100Строка 3
  ```
* **Почему требует проверки:** В ожидаемом выводе учебника стоит пробел перед `100` (`Строка 2 100`), а в реальности пробела НЕТ (`Строка 2100`).  
  Спецификация Go четко фиксирует правило:  
  > *«Spaces are added between operands when neither is a string.»*  
  Так как операнд `"Строка 2"` является строкой, условие «ни один операнд не является строкой» не выполняется, и пробел между ним и числом `100` НЕ вставляется. Ожидаемый результат в учебнике ошибочен и учит неверному пониманию `fmt.Print`.
* **Необходимые доказательства/тест:** Запуск `go run test_26.go`.
* **Приоритет:** **High**

### 6. Упражнение 32: Баг форматирования составного типа и искажение вывода
* **Упражнение/Раздел:** Упражнение 32 («Совместный вывод типа и значения через %T и %v»).
* **Фрагмент кода и вывода:**
  ```go
  func inspect(name string, val any) {
      fmt.Printf("%-10s -> Значение: %-15v | Тип: %T\n", name, val, val)
  }
  inspect("Срез", []int{10, 20, 30})
  ```
  Заявленный ожидаемый вывод:
  ```text
  # Срез       -> Значение: [10 20 30]      | Тип: []int
  ```
  Фактический вывод Go:
  ```text
  Срез       -> Значение: [10              20              30             ] | Тип: []int
  ```
* **Почему требует проверки:** В Go спецификаторы ширины для составных типов (`slice`, `array`) применяются РЕКУРСИВНО К КАЖДОМУ ЭЛЕМЕНТУ. Поэтому `%-15v` дополнил каждое число `10`, `20`, `30` пятнадцатью позициями. Ожидаемый вывод учебника был написан вручную в предположении, что срез форматируется целиком, что противоречит спецификации Go.
* **Необходимые доказательства/тест:** Спецификация Go `fmt`, фактический запуск программы.
* **Приоритет:** **High**

### 7. Упражнение 58: Критический баг опустошения Stdin при повторном вводе
* **Упражнение/Раздел:** Упражнение 58 («Интерактивное консольное меню с fmt.Scanln»).
* **Фрагмент кода:**
  ```go
  var choice int
  _, err := fmt.Scanln(&choice)
  if err != nil {
      fmt.Println("❌ Ошибка ввода: введите число 1, 2 или 3.")
      // Сбрасываем буфер ввода
      bufio.NewReader(os.Stdin).ReadString('\n')
      continue
  }
  ```
* **Почему требует проверки:** Создание `bufio.NewReader(os.Stdin)` прямо в теле цикла для «сброса буфера» — катастрофический антипаттерн.  
  1) `bufio.Reader` жадно вычитывает из системного дескриптора ядра до 4096 байт в свой внутренний буфер.  
  2) Если пользователь ввел несколько строк (например, скопировал пачку команд или программа запущена через пайп `echo -e "abc\n1"`), `ReadString` забирает только первую строку `\n`, а ВСЕ последующие данные остаются в буфере временного объекта `bufio.Reader`, который сборщик мусора уничтожает.  
  3) На следующей итерации `fmt.Scanln(&choice)` читает уже пустой `os.Stdin` и немедленно падает с ошибкой `EOF`.  
  *Ирония:* в Упр. 39 в разделе `pitfalls` прямо написано: *«Создание нового bufio.NewReader(os.Stdin) на каждый ввод внутри цикла: ридер буферизует 4 КБ данных... данные будут утеряны»*, а в Упр. 58 допущен именно этот баг.
* **Необходимые доказательства/тест:** Тест с передачей в stdin строки `"abc\n1\n"`. Вторая команда теряется, программа вылетает по `EOF`.
* **Приоритет:** **High**

### 8. Упражнение 23: Дефект мерцания и остаточных символов (Ghosting) при консольной анимации через `\r`
* **Упражнение/Раздел:** Упражнение 23 («Консольная ASCII-анимация с задержкой через time.Sleep»).
* **Фрагмент кода:**
  ```go
  frames := []string{
      "⏳ [=         ] Подготовка окружения...", // длина 38 символов
      "⏳ [====      ] Загрузка ядра...",       // длина 31 символ
      "⏳ [=======   ] Инициализация БД...",    // длина 34 символа
      "⏳ [==========] Сервис готов к работе!",  // длина 37 символов
  }
  for _, frame := range frames {
      fmt.Printf("\r%s", frame)
      time.Sleep(300 * time.Millisecond)
  }
  ```
* **Почему требует проверки:** Символ `\r` возвращает курсор в начало текущей строки, но **не стирает** символы в терминале. Так как первый кадр имеет длину 38 символов, а второй — всего 31 символ, последние 7 символов первого кадра (`"ения..."`) не затираются!  
  В реальном терминале пользователь видит:  
  `⏳ [====      ] Загрузка ядра...ения...`  
  В профессиональном CLI коде строки обязаны либо дополняться пробелами до максимальной ширины, либо сбрасываться ANSI-кодом очистки до конца строки: `\r\033[K` (Clear line from cursor to end).
* **Необходимые доказательства/тест:** Запуск кода в TTY-терминале Linux/macOS.
* **Приоритет:** **High**

### 9. Упражнение 5: Ошибочный ожидаемый вывод и путаница байт с символами
* **Упражнение/Раздел:** Упражнение 5 («Чтение полной строки с пробелами через bufio.Reader.ReadString»).
* **Фрагмент кода и вывода:**
  ```go
  cleanInput := strings.TrimSpace(input)
  fmt.Printf("Получено: [%s] (длина: %d символов)\n", cleanInput, len(cleanInput))
  ```
  Ожидаемый вывод:
  ```text
  # Введите ваше полное имя и должность: Иван Иванов Lead Go Engineer
  # Получено: [Иван Иванов Lead Go Engineer] (длина: 45 символов)
  ```
* **Почему требует проверки:**
  1) Число 45 не соответствует реальности. Для строки `"Иван Иванов Lead Go Engineer"` длина в байтах `len(...)` равна **38**, а число рун — **28**. Программа фактически напечатает: `(длина: 38 символов)`.  
  2) Называть `len(string)` «символами» — грубое искажение фундаментальной концепции Go. Функция `len()` для строк возвращает число **байт**. Для подсчета символов требуется `utf8.RuneCountInString()`.
* **Необходимые доказательства/тест:** Вызов `len()` и `utf8.RuneCountInString()` на контрольной строке.
* **Приоритет:** **High**

### 10. Упражнение 34: Ошибочный ожидаемый вывод длины строки
* **Упражнение/Раздел:** Упражнение 34 («Построчный буферизованный сканер bufio.Scanner»).
* **Фрагмент кода и вывода:**
  ```go
  line := scanner.Text()
  fmt.Printf("     Длина строки: %d символов\n", len(line))
  ```
  Ожидаемый вывод для `"Первый тестовый запрос"`:
  ```text
  #      Длина строки: 43 символов
  ```

### 11. Упражнение 17: Вымышленный текст ошибки `expected float`
* **Упражнение/Раздел:** Упражнение 17 («Сложение чисел из консоли с валидацией ввода»).

* **Почему требует проверки:** В Go парсер `fmt.Scan` делегирует разбор чисел с плавающей точкой функции `strconv.ParseFloat`. Реальная ошибка рантайма:

* **Необходимые доказательства/тест:** Запуск `fmt.Scan(&a, &b)` со строкой `"10 привет"`.

### 12. Упражнение 8: Несоответствие условию и обход ограничений `fmt.Sscanf`
* **Упражнение/Раздел:** Упражнение 8 («Парсинг форматированных строк через fmt.Sscanf»).
* **Фрагмент задания:**
  *«8. Используйте fmt.Sscanf для парсинга строки формата "Имя, возраст, рост" в соответствующие переменные.»* (запятые присутствуют).
* **Фрагмент кода:**


Если попытаться распарсить строку из условия `"Дмитрий, 28, 185.5"` по шаблону `"%s, %d, %f"`, `fmt.Sscanf` завершится ошибкой `input does not match format`. ### 14. Упражнение 29: Необъясненное использование built-in `println` (Stderr)
* **Упражнение/Раздел:** Упражнение 29 («Формирование строк в памяти без вывода на экран через fmt.Sprintf»).
* **Фрагмент кода:**

* **Необходимые доказательства/тест:** Запуск программы с перенаправлением `> out.txt`.
* **Приоритет:** **Medium**

### 15. Упражнения 10, 45, 47, 50, 61: Потеря данных при получении `io.EOF`
* **Упражнение/Раздел:** Упражнения 10, 45, 47, 50, 61 (интерактивные REPL и CLI-анкеты).
* **Фрагмент кода:**
  ```go
  input, err := reader.ReadString('\n')
  if err != nil {
      break
  }
  ```
* **Почему требует проверки:** Если входной поток завершается сигналом EOF без завершающего символа переноса строки `\n` (типичный случай при `echo -n "command" | app` или при вставке последней строки файла), `ReadString` возвращает прочитанный текст И ошибку `io.EOF`. При немедленном выходе `if err != nil { break }` последняя введенная пользователем команда отбрасывается без обработки. Корректный паттерн: сначала обработать `if len(input) > 0`, а затем `if err != nil`.
* **Необходимые доказательства/тест:** Передача данных в скрипт через `echo -n`.
* **Приоритет:** **Medium**

### 17. Упражнения 51 и 53: Важное упущение по интерфейсу `fmt.Stringer` (Pointer vs Value Receiver)
* **Упражнение/Раздел:** Упражнения 51 и 53 (реализация `fmt.Stringer` и `fmt.GoStringer`).
* **Почему требует проверки:** Методы объявлены на значении: `func (b Book) String() string`. В теории и подводных камнях отсутствует критически важный факт: если разработчик объявляет метод на указателе `func (b *Book) String() string`, то значение типа `Book` НЕ удовлетворяет интерфейсу `fmt.Stringer`. В результате вызов `fmt.Println(book)` напечатает `{...}` вместо строкового представления. Это источник 90% багов у начинающих Go-разработчиков при кастомизации вывода структур.
* **Приоритет:** **Medium**

## Резюме по итогам скаут-аудита

Глава 03 («Пакет fmt и консольный ввод-вывод») содержит богатый набор практических упражнений, однако при детальном техническом аудите выявлено:
1. **3 файла не проходят проверку линтером `go vet`** из-за некорректного использования спецификаторов в `fmt.Println` (Упр. 25, 44) и передачи невызванной функции под `%v` (Упр. 18).
2. **Фактологическая ошибка в теории:** Утверждение в Упр. 48 и 59 о том, что пакет `fmt` меряет ширину строк в байтах, а не в рунах, прямо противоречит исходному коду рантайма Go.
3. **Ошибки в ожидаемом выводе терминала:** В Упр. 26 (пробелы в `fmt.Print`), Упр. 32 (рекурсивное форматирование срезов), Упр. 5 и 34 (байты вместо символов).
4. **Критический runtime-дефект:** В Упр. 58 «сброс буфера» через одноразовый `bufio.NewReader` ворует последующие данные из дескриптора ввода ОС.
5. **Визуальный баг:** В Упр. 23 перезапись строки через `\r` оставляет обрывки символов более длинных предыдущих сообщений (ghosting).
