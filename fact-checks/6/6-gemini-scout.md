### 1. Упражнение 57: Логический баг форматирования вывода и расхождение с эталоном терминала
- **Раздел/Упражнение:** Упражнение 57 (`ex-57`, `builder/gen_ch6_p4.py`, `sources/6. Циклы.md`).
- **Заголовок/Задача:** «Пропуск остатка внутреннего цикла при j == 3 через continue OuterGrid».
- **Фрагмент кода:**
  ```go
  OuterGrid:
  	for i := 1; i <= 3; i++ {
  		fmt.Printf("Строка i = %d: ", i)
  		for j := 1; j <= 5; j++ {
  			if j == 3 {
  				fmt.Printf("[j=%d -> CUT!]", j)
  				continue OuterGrid // Сразу переходим к i++!
  			}
  			fmt.Printf("%d ", j)
  		}
  		fmt.Println()
  	}
  	fmt.Println("\nВсе строки обработаны.")
  ```
  В эталонном блоке терминала указано:
  ```bash
  go run main.go
  # Демонстрация continue OuterGrid (пропуск j > 2):
  # Строка i = 1: 1 2 [j=3 -> CUT!]
  # Строка i = 2: 1 2 [j=3 -> CUT!]
  # Строка i = 3: 1 2 [j=3 -> CUT!]
  # 
  # Все строки обработаны.
  ```
- **Почему требует исправления:**
  1. Инструкция `continue OuterGrid` передает управление непосредственно на шаг инкремента внешнего цикла `i++`.
  2. Из-за этого инструкция `fmt.Println()`, стоящая в конце тела внешнего цикла, **никогда не выполняется** ни для одной из итераций!
  3. Поскольку в строке `fmt.Printf("[j=%d -> CUT!]", j)` отсутствует символ новой строки `\n`, фактический вывод программы выглядит так:
     ```text
     Демонстрация continue OuterGrid (пропуск j > 2):
     Строка i = 1: 1 2 [j=3 -> CUT!]Строка i = 2: 1 2 [j=3 -> CUT!]Строка i = 3: 1 2 [j=3 -> CUT!]
     Все строки обработаны.
     ```
  4. Автор написал эталонный вывод вручную, ожидая перевод строки, но сам же продемонстрировал, что забыл о механике `continue OuterGrid`, который пропускает хвостовой код внешнего цикла.
- **Необходимое исправление:** Добавить символ `\n` в строку отсечения: `fmt.Printf("[j=%d -> CUT!]\n", j)`.
- **Приоритет:** **High**.

### 3. Упражнение 40: Ложное утверждение о запрете комментариев перед циклом компилятором Go
- **Раздел/Упражнение:** Упражнение 40 (`ex-40`, `builder/gen_ch6_p3.py`), блок Pitfalls.
- **Утверждение:**
  > *- Размещение комментариев или переменных между меткой и циклом `Outer: var x = 1; for ...` — вызовет ошибку компиляции.*
- **Почему требует исправления:**
  1. **Комментарии в Go НЕ вызывают ошибку компиляции:** Согласно спецификации Go (*Lexical elements: Comments*), комментарии полностью удаляются лексером на этапе токенизации и рассматриваются как пробельные символы (whitespace). Следующий код компилируется и работает абсолютно безупречно:
     ```go
     Outer:
         // Любой однострочный комментарий
         /* Любой многострочный
            блок комментариев */
         for i := 0; i < 3; i++ { ... }
     ```
  2. Ошибку компиляции вызывают **инструкции и объявления** (например, `var x = 1;` или `fmt.Println()`), так как метка привязывается к первому следующему за ней стейтменту (`LabeledStmt`). Если этот стейтмент не является `for`, `switch` или `select`, вызов `break Outer` приведет к ошибке компилятора: `invalid break label Outer`.
  3. Обучение разработчиков тому, что «комментарии вызывают ошибку компилятора», подрывает доверие к учебнику и создает ложное представление о работе компилятора Go.
- **Необходимое исправление:** Удалить упоминание комментариев: *«Размещение любых инструкций или объявлений переменных между меткой и циклом (например, `Outer: var x = 1; for ...`) вызовет ошибку компиляции `invalid break label`»*.
- **Приоритет:** **High**.

### 4. Упражнение 34: Ложные утверждения об «атомарности» параллельного присваивания и генерации `XCHG`
- **Раздел/Упражнение:** Упражнение 34 (`ex-34`, `builder/gen_ch6_p3.py`), комментарий в коде и блок Under the Hood.
- **Фрагмент кода и текст:**
  ```go
  arr[i], arr[j] = arr[j], arr[i] // Атомарный swap
  ```
  В блоке Under the Hood:
  > *SSA-генератор использует пару регистров для параллельного обмена значений `XCHG` / `MOVQ`.*
- **Почему требует исправления:**
  1. **Присваивание кортежа в Go НЕ является атомарным:** Согласно спецификации Go (*Order of evaluation: Assignments*), кортежное присваивание `a, b = b, a` выполняется в две фазы: вычисление адресов и значений операндов, а затем их последовательная запись. Никакой защиты от гонок данных (data race) или аппаратной атомарности здесь нет. Если другая горутина параллельно обращается к слайсу, возникнет data race. Называть это «атомарным swap» категорически недопустимо, особенно в курсе, готовящем к Middle/Senior собеседованиям.
  2. **Компилятор Go НЕ генерирует инструкцию `XCHG` для обычного swap:** Ассемблерный листинг `go tool compile -S` для функции `ReverseInPlace` генерирует 4 обычные инструкции перемещения данных:
     ```assembly
     MOVQ (AX)(CX*8), BX   // загрузка arr[i] в регистр BX
     MOVQ (AX)(DX*8), SI   // загрузка arr[j] в регистр SI
     MOVQ BX, (AX)(DX*8)   // сохранение в arr[j]
     MOVQ SI, (AX)(CX*8)   // сохранение в arr[i]
     ```
  3. Инструкция `XCHG` с операндом в памяти на архитектуре x86 автоматически блокирует шину памяти (неявный префикс `LOCK`), что приводит к сбросу конвейера процессора и колоссальной деградации производительности. Компилятор Go никогда не генерирует `XCHG` для обычных присваиваний без явного вызова пакета `sync/atomic`.
- **Необходимое исправление:** Убрать ложный комментарий `// Атомарный swap` (заменить на `// Обмен элементов через параллельное присваивание`) и убрать упоминание `XCHG` из Under the Hood.
- **Приоритет:** **High**.

### 5. Упражнение 50: Ложное утверждение об автоматической буферизации `os.Stdout` по переводу строки `\n`
- **Раздел/Упражнение:** Упражнение 50 (`ex-50`, `builder/gen_ch6_p4.py`), блок Under the Hood.
- **Утверждение:**
  > *Буферизация `stdout` с автоматическим сбросом по `\n`.*
- **Почему требует исправления:**
  1. Это классическое заблуждение программистов, пришедших из языка C (где функция `printf` использует построчно-буферизованный `stdout` из `stdio.h`).
  2. В языке Go дескриптор `os.Stdout` является обычным `*os.File`. Функции `fmt.Print`, `fmt.Println` и `fmt.Printf` **не имеют встроенной буферизации**: каждый их вызов немедленно транслируется в системный вызов ядра `write(2)` (или `writev`).
  3. В Go перевод строки `\n` **не инициирует никакой «автоматический сброс буфера»**, так как буфера в рантайме Go попросту нет. Если требуется буферизация, программист обязан явно обернуть дескриптор в `bufio.NewWriter(os.Stdout)` и вызвать `.Flush()`.
  4. Примечательно, что в Упражнении 31 того же модуля правильный факт уже приводился в BigTech-секции: *«Использовать bufio.NewWriter(os.Stdout)»*. Утверждение в Упр. 50 прямо противоречит Упр. 31 и вводит учащихся в заблуждение.
- **Необходимое исправление:** Заменить в Упр. 50: *«Каждый вызов fmt.Printf / fmt.Println производит прямой системный вызов write(2). Для высокопроизводительного вывода в цикле необходимо использовать буферизованный writer из пакета bufio»*.
- **Приоритет:** **High**.

### 6. Упражнение 30: Прямое смысловое противоречие между заданием и кодом решения
- **Раздел/Упражнение:** Упражнение 30 (`ex-30`, `builder/gen_ch6_p2.py`, `sources/6. Циклы.md`).
- **Заголовок/Задача:** «Поиск составных чисел в диапазоне 2..50 с выходом по метке OuterLoop».
- **Текст задачи:**
  > *Метка и break: во вложенном цикле поиска простых чисел **от 2 до 50** используйте метку outer для выхода из внешнего цикла при нахождении составного числа.*
- **Фрагмент кода решения:**
  ```go
  fmt.Println("Поиск первого составного числа > 30:")

  SearchOuter:
  	for n := 31; n <= 50; n++ {
  		for d := 2; d*d <= n; d++ {
  			if n%d == 0 {
  				fmt.Printf("Число %d составное (делится на %d)! Выход по метке.\n", n, d)
  				break SearchOuter
  			}
  		}
  		fmt.Printf("Число %d — простое\n", n)
  	}
  ```
- **Почему требует исправления:**
  1. Если запустить алгоритм от 2 до 50 (как требует текст задачи):
     - `n = 2` — простое;
     - `n = 3` — простое;
     - `n = 4` — составное ($4 = 2 \times 2$) $\rightarrow$ немедленный выход!

- **Необходимое исправление:** Синхронизировать условие задачи: *«...во вложенном цикле поиска чисел в диапазоне от 31 до 50 используйте метку для выхода...»*.

### 7. Упражнение 2: Противоречие заголовка, теории и фактической реализации (False "Without Allocations")
- **Раздел/Упражнение:** Упражнение 2 (`ex-2`, `builder/gen_ch6_p1.py`, `sources/6. Циклы.md`).
- **Заголовок:** «Проверка строки на палиндром методом двух указателей (Two Pointers) **без аллокаций**».
- **Фрагмент кода:**
  ```go
  func IsPalindrome(s string) bool {
  	// Очищаем от пробелов и приводим к нижнему регистру
  	var runes []rune
  	for _, r := range strings.ToLower(s) {
  		if unicode.IsLetter(r) || unicode.IsDigit(r) {
  			runes = append(runes, r)
  		}
  	}
      ...
  ```
- **Почему требует исправления:**
  1. Заголовок громко заявляет: **«без аллокаций»**.
  2. Однако первая же строчка функции делает `strings.ToLower(s)`, что аллоцирует в куче **новую строку** $O(N)$.

  4. При этом в блоке теории пункт 5 признает: *«Память: $O(1)$ для ASCII (или $O(N)$ при конвертации в []rune для Unicode)»*.
  5. В BigTech-блоке правильно отмечается, как пишется настоящий zero-allocation палиндром для UTF-8: обход с двух концов через `utf8.DecodeRuneInString` и `utf8.DecodeLastRuneInString` без создания среза рун.
  6. Называть реализацию с двойным выделением памяти алгоритмом «без аллокаций» технически некорректно.
- **Необходимое исправление:** Либо изменить заголовок (убрав слова «без аллокаций»), либо реализовать честный zero-allocation алгоритм со встречным декодированием рун из исходной строки.
- **Приоритет:** **High**.

### 10. Упражнение 29: Несоответствие шестнадцатеричного формата рун в терминале (`U+48` vs `U+0048`) и игнорирование глагола `%U`

## 🧩 Анализ критических пробелов темы (Missing Topics)

Несмотря на 64 упражнения, в главе полностью пропущены важнейшие темы работы с циклами в современном Go:

1. **`for i := range n` (Целочисленный range, Go 1.22+):**
   - Начиная с Go 1.22, синтаксис `for i := range 10` является официальным стандартом языка (итерирует от 0 до 9).
   - Форма `for range 10` позволяет выполнить блок кода ровно 10 раз без заведения переменной-счетчика.
   - **В главе нет ни одного упражнения на этот важнейший синтаксис!** Везде по старинке используется C-style `for i := 0; i < 10; i++`.
2. **Ловушка `break` внутри `switch` / `select` внутри цикла `for`:**
   - Самый частый источник багов у новичков и разработчиков, переходящих с других языков:
     ```go
     for {
         switch msg.Type {
         case "stop":
             break // ОШИБКА: прерывает switch, а не for! Цикл становится бесконечным!
         }
     }
     ```
   - Для выхода из цикла здесь **обязателен** `break LoopLabel`. В главе есть 6 задач на метки, но этой главной практической проблемы нет ни в одной из них.
3. **Range over Func / Пользовательские итераторы (`iter.Seq`, `iter.Seq2`, Go 1.23+):**
   - Go 1.23 ввел стандартизированные итераторы в `for range`. Учебник позиционируется до уровня Staff/Principal, но в главе о циклах механизм `iter.Seq` упоминается лишь вскользь в BigTech-ответе к Упр. 64. Нет ни одного примера создания собственного итератора через `yield`.
4. **Итерация по массиву через указатель (`for i, v := range &arr`):**
   - При `range arr` массив целиком копируется на стек.
   - Идиома `range &arr` позволяет обойти массив без копирования данных и без приведения к срезу `arr[:]`. Это популярный вопрос на собеседованиях в HighLoad.
5. **Прерывание «жадных» циклов (Loop Preemption & Cooperative Scheduling):**
   - Исторический баг Go < 1.14 (зависание рантайма и GC на пустом цикле `for {}`) и механизм асинхронного прерывания عبر сигналы ОС (`SIGURG`) на платформах Unix.
6. **Bounds Check Elimination (BCE) в циклах:**
   - Как компилятор устраняет проверки границ в `for i := 0; i < len(s); i++` и почему доступ к подэлементам `s[i]` иногда требует фиксации длины до цикла.
