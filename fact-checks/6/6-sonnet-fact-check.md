### G-01 — VERIFIED
- **Где / цитата:** `04…/057. Пропуск остатка внутреннего цикла при j == 3.md`, «Код решения»: `fmt.Printf("[j=%d -> CUT!]", j)` + `continue OuterGrid`.
- **Вердикт:** `continue OuterGrid` пропускает `fmt.Println()` в конце тела внешнего цикла; `\n` в `Printf` нет, три строки склеиваются. Блок «Терминал» показывает три отдельные строки — неверно.
- **Доказательство:** спецификация, «Continue statements»: `continue Label` начинает следующую итерацию помеченного цикла, минуя остаток его тела. Запуск (go1.27.1):
  ```

  Строка i = 1: 1 2 [j=3 -> CUT!]Строка i = 2: 1 2 [j=3 -> CUT!]Строка i = 3: 1 2 [j=3 -> CUT!]
  Все строки обработаны.
  ```
- **Предлагаемая правка:** `fmt.Printf("[j=%d -> CUT!]\n", j)`. Проверено запуском: вывод после правки в точности равен текущему блоку «Терминал» (три строки, пустая строка, «Все строки обработаны.»), блок менять не нужно.

### G-03 — VERIFIED
- **Где / цитата:** `03…/040. Синтаксис и правила именования меток Labeled Break.md`, «Подводные камни»: «Размещение комментариев или переменных между меткой и циклом `Outer: var x = 1; for ...` — вызовет ошибку компиляции».
- **Вердикт:** про комментарии — ложь. Про переменные — ошибка есть, но причина другая: объявление синтаксически допустимо после метки; ошибка возникает при `break Outer` («invalid break label»), либо если метка не использована («defined and not used»). Пункт теории 2 «Между меткой и циклом не может быть других инструкций» верен лишь в смысле «чтобы `break Label` был допустим, метка должна стоять непосредственно на `for`/`switch`/`select`».
- **Доказательство:** спецификация, «Lexical elements → Comments» (комментарии действуют как пробел) и «Labeled statements» / «Break statements». Запуск (`/tmp/gw-6-F40*`):
  - метка, затем `//` и `/* */`, затем `for` + `break Outer` → компилируется, печатает `0 0`;
  - метка, `var x = 1`, `for` + `break Outer` → `./main.go:11:11: invalid break label Outer`;
  - метка, `var x = 1`, без `break` → `./main.go:6:1: label Outer defined and not used`.
- **Предлагаемая правка:** заменить пункт на «Размещение любой инструкции или объявления между меткой и циклом (например, `Outer: var x = 1` и затем `for …`) делает `break Outer` недопустимым: `invalid break label Outer`. Комментарии на это не влияют».

### G-04 — VERIFIED
- **Где / цитата:** `03…/034. Разворот среза In-Place методом двух указателей.md`: комментарий в коде `// Атомарный swap`; «Под капотом»: «SSA-генератор использует пару регистров для параллельного обмена значений `XCHG` / `MOVQ`».
- **Вердикт:** присваивание кортежа не атомарно; `XCHG` не генерируется.
- **Доказательство:** спецификация, «Assignment statements» (операнды вычисляются, затем присваивания выполняются по порядку слева направо; никаких гарантий атомарности) и Go Memory Model. `go build -gcflags='-l -S'`: `ReverseInPlace` (amd64) — `MOVQ (AX)(CX*8), BX; MOVQ (AX)(DX*8), SI; MOVQ BX, (AX)(DX*8); MOVQ SI, (AX)(CX*8)`; для arm64 — четыре `MOVD` (две загрузки и два сохранения); `XCHG*` в функции нет (единственный `XCHGL AX, AX` в `main` — NOP-выравнивание). Две горутины, меняющие `arr[0], arr[1] = arr[1], arr[0]`, под `-race` дают `WARNING: DATA RACE`.
  Утверждение скаута «`XCHG` с памятью на x86 неявно блокирует шину» — известное свойство ISA, сверено с документацией Intel не было (**NOT CHECKED**), на вердикт не влияет.
- **Предлагаемая правка:** комментарий — `// Обмен элементов параллельным присваиванием`; «Под капотом» — «Компилятор раскладывает обмен на две загрузки и два сохранения (`MOVQ`); атомарности нет — при конкурентном доступе возникает data race».

### G-07 — VERIFIED
- **Где / цитата:** `01…/002. Проверка строки на палиндром методом двух.md`, заголовок «…без аллокаций»; код `strings.ToLower(s)` + `append(runes, …)`.
- **Вердикт:** реализация аллоцирует; заголовок неточен. Теория (п. 5) честно оговаривает «O(N) при конвертации в `[]rune`», «Под капотом» — «не создаёт перевёрнутых копий», что верно, но не отменяет `[]rune`.
- **Доказательство:** `testing.AllocsPerRun` (go1.27.1): «А роза упала на лапу Азора» — 3 аллокации, «Madam, I'm Adam» — 2, «Golang Workout» — 2; «топот» и «abcba» — 0 (для коротких входов компилятор размещает буфер `append` на стеке, поэтому «ровно две аллокации» не универсально). Проверенная версия без аллокаций (`utf8.DecodeRuneInString` / `utf8.DecodeLastRuneInString` + `unicode.ToLower`) на тех же пяти строках даёт 0 аллокаций и те же ответы.
- **Предлагаемая правка:** либо убрать «без аллокаций» из заголовка и сказать в теории «O(N) дополнительной памяти на `[]rune`», либо заменить реализацию на:
  ```go
  func IsPalindrome(s string) bool {
  	i, j := 0, len(s)
  	for i < j {
  		ri, si := utf8.DecodeRuneInString(s[i:j])
  		if !unicode.IsLetter(ri) && !unicode.IsDigit(ri) {
  			i += si
  			continue
  		}
  		rj, sj := utf8.DecodeLastRuneInString(s[i:j])
  		if !unicode.IsLetter(rj) && !unicode.IsDigit(rj) {
  			j -= sj
  			continue
  		}
  		if unicode.ToLower(ri) != unicode.ToLower(rj) {
  			return false
  		}
  		i += si
  		j -= sj
  	}
  	return true
  }
  ```
  (импорты `unicode`, `unicode/utf8`; `strings` не нужен; вывод `main` не меняется.)
