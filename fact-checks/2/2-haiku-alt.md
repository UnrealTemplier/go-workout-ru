### A-01 — `-race` «мгновенно падает»

- **Где:** `05. CLI Флаги, Подкоманды и Устранение Data Race/022. Воспроизведение и устранение Data Race.md`, раздел «Теория».
- **Цитата:** «С `-race`: программа мгновенно падает с точным стек-трейсом гонки.»
- **Утверждение:** детектор гонок не останавливает программу по умолчанию. Он печатает отчёт и продолжает работу, а в конце выходит с кодом 66.
- **Почему важно:** это учит неверной модели работы инструмента. Читатель будет искать «падение» там, где есть только отчёт в stderr, и может принять отсутствие падения за отсутствие гонки.
- **Что проверить и где:** запуск `go run -race` на программе из `03. …/012. Детектор состояний гонки…md` (счётчик с двумя горутинами). В песочнице: программа дошла до вывода `Итоговое значение: 2000`, затем напечатала `Found 3 data race(s)` и завершилась с `exit status 66`. Для остановки на первой гонке нужен `GORACE="halt_on_error=1"`, это стоит упомянуть.
- **Тип:** факт
- **Приоритет:** High

### A-02 — «statically linked» и «запустится на любом Linux» без оговорки про CGO

- **Где:** `03. Статанализ, Детектор Гонок и Форматы Бинарников/011. Кросс-компиляция под Linux x86_64 и инспекция заголовков ELF.md`, раздел «Терминал» и «На собеседовании».
- **Цитата (интервью):** «Это означает, что бинарник не содержит ссылок на динамические библиотеки … Он запустится на любом Linux-дистрибутиве (Ubuntu, Alpine, RHEL, Arch) с подходящей версией ядра без установки сторонних пакетов.»
- **Утверждение:** статическая сборка верна только при `CGO_ENABLED=0` или если программа не тянет cgo-пакеты. Команда из главы (`GOOS=linux GOARCH=amd64 go build …`) этого не задаёт. Программа с `net` при включённом CGO на Linux-хосте получается динамической.
- **Почему важно:** это прямой ответ на интервью, и он неверен для обычного сервера с `net` или `os/user`. Такой бинарник не запустится в `scratch` или на Alpine без musl-совместимости. Глава 025 использует `CGO_ENABLED=0`, но без связи с этим ответом.
- **Что проверить и где:** в песочнице программа с `import "net"`: `go build` даёт `ELF … dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2`; с `CGO_ENABLED=0` — `statically linked`. Для hello-world без cgo вывод из главы верен.
- **Тип:** факт, педагогика
- **Приоритет:** High

### A-03 — «бадди-аллокатор (tcmalloc-like)» в рантайме Go

- **Где:** `01. Базовая Компиляция, go run и go build/003. Компиляция в нативный исполняемый файл. go build.md`, раздел «На собеседовании».
- **Цитата:** «…многопоточный менеджер памяти с бадди-аллокатором (tcmalloc-like)…»
- **Утверждение:** аллокатор Go не является buddy-аллокатором. В `runtime/malloc.go` написано: «This was originally based on tcmalloc, but has diverged quite a bit», а слова buddy в файле нет. Он использует классы размеров и структуры mcache, mcentral и mheap, то есть основан на идее TCMalloc. Фраза сама себе противоречит.
- **Почему важно:** это ответ на собеседовании о внутреннем устройстве рантайма. Кандидат, который назовёт buddy-систему, получит минус на первом же уточняющем вопросе.
- **Что проверить и где:** `/usr/local/go/src/runtime/malloc.go`, строки 7–8; `grep -i buddy /usr/local/go/src/runtime/malloc.go` не даёт совпадений.
- **Тип:** факт
- **Приоритет:** High

### A-04 — `-race` не работает с `CGO_ENABLED=0`

- **Где:** `02. Кросс-компиляция и Установка через go install/005. Основы кросс-компиляции. переменные GOOS и GOARCH.md`, раздел «Подводные камни»; связанно: `03. …/012. Детектор состояний гонки…md`, `06. …/024. Автоматизационный сборочный скрипт CI_CD пайплайна.md` (шаг 3, `go test -v -race -cover ./...`).
- **Цитата:** «Всегда собирайте с `CGO_ENABLED=0`.»
- **Утверждение:** правило «всегда» конфликтует с `-race`. Go-тулчейн требует cgo для race-детектора. В песочнице `CGO_ENABLED=0 go run -race main.go` завершается с сообщением `go: -race requires cgo; enable cgo by setting CGO_ENABLED=1` и кодом 2. Глава нигде этого не упоминает.
- **Почему важно:** читатель, которому велели «всегда» отключать CGO, получит поломанный CI-шаг `go test -race`, если `CGO_ENABLED=0` стоит в окружении. Причина не будет ему понятна.
- **Что проверить и где:** `go run -race` с `CGO_ENABLED=0` на любой программе с горутинами. Добавить в 005 уточнение «кроме сборки с `-race`» и в 024 явный `CGO_ENABLED=1` для тестов.
- **Тип:** факт, упущение
- **Приоритет:** Medium

### A-05 — toolchain не кладётся в `$GOPATH/bin`

- **Где:** `01. Базовая Компиляция, go run и go build/001. Проверка версии Go и архитектура компилятора.md`, раздел «На собеседовании».
- **Цитата:** «…тулчейн Go автоматически скачает официальный бинарник Go 1.23 в `$GOPATH/bin` и прозрачно выполнит сборку на нем.»
- **Утверждение:** при переключении тулчейна (Go 1.21+) загруженный модуль `golang.org/toolchain` распаковывается в кэш модулей (`GOMODCACHE`), а не в `$GOPATH/bin`. В `cmd/go/internal/toolchain/select.go:357` написано: «Download and unpack toolchain module into module cache.»
- **Почему важно:** неверный путь в ответе на вопрос про новую возможность тулчейна. Также не упомянута переменная `GOTOOLCHAIN`, которая управляет поведением.
- **Что проверить и где:** `go env GOMODCACHE` и `GOTOOLCHAIN=go1.23.0 go version` в модуле с `go 1.23.0` в `go.mod` (нужна сеть), затем `ls $(go env GOMODCACHE)/golang.org/toolchain*`.
- **Тип:** факт
- **Приоритет:** Medium

### A-06 — вывод гонки в «Терминале» не соответствует коду и не воспроизводится

- **Где:** `03. Статанализ, Детектор Гонок и Форматы Бинарников/012. Детектор состояний гонки (Data Race Detector).md`, раздел «Терминал».
- **Цитата:** «Previous Write at 0x00c00001c0a8 by goroutine 7: main.main.func1() … main.go:13» и «Found 1 data race(s)».
- **Утверждение:** в примере `counter++` стоит на строках 14 и 21 кода (а не 13 и 20). Счётчик гонок недетерминирован: в запуске в песочнице найдено 3 гонки, а не 1. Строка `Итоговое значение: …` из программы в примере не показана; её значение зависит от чередования горутин (в запуске с `-race` получено 2000, но гарантии нет). Программа ждёт `time.Sleep(100 * time.Millisecond)`, что здесь выдано за синхронизацию и не объяснено.
- **Почему важно:** вывод выдан за точный и детерминированный. Читатель будет сверять свой вывод с книгой и решит, что его запуск неверен. `time.Sleep` как способ дождаться горутин — антипаттерн, который сама глава учит избегать (см. 022, `sync.WaitGroup`).
- **Что проверить и где:** запустить `go run -race main.go` из 012 несколько раз; заменить вывод на реальный или пометить его «пример, число гонок и значение могут отличаться»; заменить `time.Sleep` на `sync.WaitGroup`.
- **Тип:** код, педагогика
- **Приоритет:** Medium

### A-07 — `go build -o .` не даёт синтаксической ошибки

- **Где:** `02. Кросс-компиляция и Установка через go install/009. Кастомизация выходного имени бинарника через флаг.md`, раздел «Подводные камни».
- **Цитата:** «Если передать флаг `-o` без значения (`go build -o .`), компилятор выдаст синтаксическую ошибку флагов.»
- **Утверждение:** `.` — это значение флага. Go трактует существующий каталог как каталог вывода и кладёт туда бинарник с именем пакета. В песочнице `go build -o .` в модуле завершился с кодом 0 и создал исполняемый файл в текущем каталоге.
- **Почему важно:** ложная «ловушка» учит читателя тому, чего не существует. Реальная ловушка — путь, который не заканчивается на `/` и не существует, тогда Go создаёт файл с этим именем, а не каталог.
- **Что проверить и где:** `go build -o . ` в каталоге с `go.mod` и `package main`. Заменить пример на проверенный (например, `go build -o bin/ .` — с завершающим `/`).
- **Тип:** факт
- **Приоритет:** Medium

### A-08 — `go vet` приписан проверка непроверенных ошибок

- **Где:** `03. Статанализ, Детектор Гонок и Форматы Бинарников/013. Статический анализ и проверка антипаттернов.md`, раздел «Теория».
- **Цитата:** «В отличие от компилятора, `go vet` фокусируется на подозрительных конструкциях … Потерянный возврат ошибок;»
- **Утверждение:** `go vet` не сообщает о проигнорированной ошибке вызова вроде `os.Remove(...)`. Такую проверку делает `errcheck` (он есть в `golangci-lint`, который упомянут в интервью этого же раздела).
- **Почему важно:** читатель, который полагается на `go vet` в CI, пропустит непроверенные ошибки и будет уверен, что они проверены.
- **Что проверить и где:** в песочнице `os.Remove("nonexistent-file")` без проверки результата: `go vet ./...` даёт код 0. Убрать пункт из теории или заменить на «ошибки, которые проверяет errcheck (golangci-lint)».
- **Тип:** факт
- **Приоритет:** Medium

### A-09 — «Silent Memory Corruption» и «списание денег» при гонке на `int`

- **Где:** `05. CLI Флаги, Подкоманды и Устранение Data Race/022. Воспроизведение и устранение Data Race.md`, раздел «Теория».
- **Цитата:** «Без `-race`: программа может годами работать на проде, пока при пиковой нагрузке не произойдет повреждение памяти (Silent Memory Corruption), приводящее к списанию денег у чужого пользователя или панике в случайном месте.»
- **Утверждение:** гонка на `counter++` (`int`) даёт потерянные обновления, а не порчу памяти. Порча или «разорванное» значение возможны для составных значений (интерфейсы, слайсы, строки), а для `map` Go сам обнаруживает запись из двух горутин и падает с `fatal error: concurrent map writes`. Смешаны три разных эффекта.
- **Почему важно:** педагогическое искажение: читатель запомнит «гонка = повреждение памяти», а для счётчика это неверно. Для объяснения, почему нужен `-race`, достаточно потерянных обновлений и примера из 012.
- **Что проверить и где:** запустить пример с `counter++` из 012 без `-race` несколько раз и посмотреть, бывают ли потерянные обновления (меньше 2000). Заменить абзац на три конкретных случая: потерянное обновление, разорванное составное значение, `concurrent map writes`.
- **Тип:** педагогика, факт
- **Приоритет:** Medium

### A-10 — «в 2–4 раза быстрее» для `atomic` без обоснования

- **Где:** `05. CLI Флаги, Подкоманды и Устранение Data Race/022. Воспроизведение и устранение Data Race.md`, раздел «На собеседовании».
- **Цитата:** «…`atomic.AddInt64(&counter, 1)` работает в 2–4 раза быстрее мьютекса, так как не требует аллокации структуры блокировки и переключения контекста горутины.»
- **Утверждение:** цифра не подкреплена бенчмарком и зависит от платформы и конкуренции. Причина неверна: `sync.Mutex` не аллоцирует отдельный объект, это поле структуры (два поля `int32`). Быстрее atomic делает отсутствие CAS-захвата и очереди ожидания, а не «аллокация». Переключение горутины происходит только при конкуренции в мьютексе.
- **Почему важно:** на собеседовании цифра без бенчмарка и неверная причина выглядят как незнание. Также не сказано, что `atomic` защищает только одну переменную, а инвариант из нескольких полей требует мьютекса.
- **Что проверить и где:** `go test -bench` для `SafeCounter` и `atomic.Int64` на одной машине (бенчмарк не запускал). Переписать ответ без цифры, с причиной «нет захвата и очереди» и с оговоркой про несколько полей.
- **Тип:** факт, вывод
- **Приоритет:** Medium

### A-11 — задача требует сравнения «с/без `-race`», решение этого не показывает

- **Где:** `05. CLI Флаги, Подкоманды и Устранение Data Race/022. Воспроизведение и устранение Data Race.md`, разделы «Условие» и «Решение по шагам».
- **Цитата (условие):** «Создай data race (два горутины пишут в одну переменную без синхронизации). Запусти с `-race` и без него, сравни поведение.» / (решение, шаг 1): «Пишем программу с гонкой данных.»
- **Утверждение:** в разделе нет кода с гонкой и нет результата запуска «без `-race`». Показан только исправленный вариант (`main_fixed.go`) с выводом `100000`. Условие не выполнено, и это не объяснено.
- **Почему важно:** именно сравнение «работает / не работает» — основная учебная ценность задачи. Без него читатель не увидит, что без `-race` гонка может давать правильный на вид результат.
- **Что проверить и где:** добавить версию с `counter++` без мьютекса и два вывода (с `-race` и без). Проверить, как меняется итог от запуска к запуску без `-race`, и вписать наблюдаемое поведение (без выдуманных цифр).
- **Тип:** условие↔решение
- **Приоритет:** Medium

### A-12 — `init`: «строго в M0 до горутин» и пропущенный порядок инициализации

- **Где:** `04. Жизненный Цикл, Многофайловый main и Стриппинг/015. Хронология выполнения. функция init() vs main().md`, разделы «Теория» и «На собеседовании».
- **Цитата:** «Все функции `init()` исполняются строго последовательно в главном системном потоке `M0` (Main Thread) до запуска горутин пользовательского кода.»
- **Утверждение:** часть про M0 верна: `runtime/proc.go:189` вызывает `lockOSThread()` в `runtime.main` на время инициализации. Но `init` может сам запустить горутины, и они работают параллельно с остальными `init`, так что «до запуска горутин» не гарантировано. Глава также не говорит о порядке инициализации: сначала инициализируются пакетные переменные (с учётом зависимостей), затем `init` каждого файла в порядке, в котором их передал компилятор (обычно по имени файла). В одном файле может быть несколько `init`.
- **Почему важно:** тема главы — хронология запуска, и порядок `var` → `init` ключевой. Глава его не показывает.
- **Что проверить и где:** программа с `var a = f("var")`, двумя `init` в разных файлах и `go` в одном из `init`; `/usr/local/go/src/runtime/proc.go`, строки 183–190, для M0.
- **Тип:** упущение, вывод
- **Приоритет:** Medium

### A-13 — Zero Downtime: «одновременно» без гонки SIGTERM и эндпоинтов

- **Где:** `06. Graceful Shutdown, CI Скрипты и Docker Scratch/023. Graceful Shutdown.md`, раздел «На собеседовании».
- **Цитата:** «K8s посылает старому поду сигнал `SIGTERM` и одновременно удаляет его из эндпоинтов балансировщика Service.»
- **Утверждение:** это верно, но ответ на вопрос о Zero Downtime должен назвать следствие: удаление из эндпоинтов распространяется асинхронно, поэтому балансировщик ещё может присылать запросы уже остановленному поду. Практическое решение — `preStop`-хук с задержкой и readiness-проверка. `server.Shutdown` сам по себе этого не решает.
- **Почему важно:** на собеседовании по DevSecOps/Kubernetes это главный подвох вопроса. Ответ без него выглядит поверхностным.
- **Что проверить и где:** документация Kubernetes «Pod termination» (раздел о гонке между SIGTERM и обновлением эндпоинтов); добавить абзац в ответ.
- **Тип:** упущение, педагогика
- **Приоритет:** Medium

### A-14 — устаревшая версия Go (1.22)

- **Где:** `06. Graceful Shutdown, CI Скрипты и Docker Scratch/025. Многоэтапная Docker-контейнеризация.md`, `FROM golang:1.22-alpine AS builder` и раздел «Теория» («образ `golang:1.22-alpine` компилирует»). Также `01. Базовая Компиляция, go run и go build/001. ### A-16 — `go run -work` и очистка каталога

- **Где:** `01. Базовая Компиляция, go run и go build/002. Мгновенный запуск.md`, раздел «Под капотом».

- **Приоритет:** Low

### A-17 — `-o` передаётся «линкеру» напрямую

- **Где:** `02. Кросс-компиляция и Установка через go install/009. Кастомизация выходного имени бинарника через флаг.md`, раздел «Под капотом».

- **Тип:** факт
- **Приоритет:** Low

### A-20 — «неэкспортированная» функция, которая экспортирована

- **Где:** `04. Жизненный Цикл, Многофайловый main и Стриппинг/016. Многофайловый пакет main. main.go и utils.go.md`, раздел «Теория».

- **Утверждение:** `SayHi` начинается с заглавной буквы, то есть экспортирована. Пример иллюстрирует видимость внутри пакета для неэкспортированных имён, но выбрана экспортированная функция.

### A-21 — `-X` молча не работает с не-константной инициализацией

- **Где:** `05. CLI Флаги, Подкоманды и Устранение Data Race/021. Внедрение версии и времени сборки через -ldflags.md`, раздел «Подводные камни».
- **Утверждение:** `-X` переопределяет только строковую переменную с константной инициализацией. Если переменная инициализирована вызовом (например, `var Version = fmt.Sprint("dev")`), линкер ничего не меняет, и ошибки нет. Глава про это не пишет.

- **Что проверить и где:** собрать с `-X main.Version=…` для `var Version = fmt.Sprint("dev")` и проверить вывод; добавить в «Подводные камни».
- **Тип:** упущение
- **Приоритет:** Low

### A-22 — «`wg.Wait()` … программа завершится аварийно»

- **Где:** `05. CLI Флаги, Подкоманды и Устранение Data Race/022. Воспроизведение и устранение Data Race.md`, раздел «Подводные камни».
- **Цитата:** «Забыть вызвать `wg.Wait()`: функция `main()` завершится раньше горутин, и программа завершится аварийно или не выполнит работу.»
- **Утверждение:** выход из `main` не является аварией: паники нет, код возврата 0. Горутины прерываются без предупреждения.
- **Почему важно:** «аварийно» направляет к неверной диагностике: читатель будет искать панику и не найдёт её.
- **Что проверить и где:** заменить на «программа завершится с кодом 0, не дождавшись горутин».
- **Тип:** факт
- **Приоритет:** Low

### A-23 — «Промышленный» Graceful Shutdown не завершает процесс при ошибке сервера

- **Где:** `06. Graceful Shutdown, CI Скрипты и Docker Scratch/023. Graceful Shutdown.md`, раздел «Код решения».
- **Цитата (код):** `if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed { fmt.Printf("Ошибка сервера: %v\n", err) }`
- **Утверждение:** если порт занят, горутина лишь печатает ошибку, а `main` продолжает ждать сигнал. Процесс остаётся запущенным без сервера. Для «промышленного» примера это неверная модель. Стоит передавать ошибку в канал и завершать процесс.
- **Почему важно:** процесс, который живёт без сервера, маскирует сбой: оркестратор видит запущенный процесс, а запросы не обрабатываются.
- **Что проверить и где:** запустить два экземпляра на `:8080` и убедиться, что второй висит. Также упомянуть `signal.NotifyContext` (Go 1.16+) как более короткую запись.
- **Тип:** код, педагогика
- **Приоритет:** Low

### A-26 — накладные расходы `-race`: «2–3 раза»

## 3. Сквозные проблемы

- **Выводы «из терминала» не из реального запуска.** A-06 (012: номера строк, число гонок), A-24 (размеры образа), A-02 (статическая линковка при неуказанном CGO), A-14 (версия `go1.22.5`). Там, где вывод можно воспроизвести, он расходится с реальным. Рекомендация: все «Терминал»-выводы сверить запуском на Go актуальной версии и пометить версию.
- **CGO и `-race`.** A-02, A-04, A-27: правило «всегда `CGO_ENABLED=0`» (005) конфликтует с `-race` (012, 022, 024) и с ответом про статическую линковку (011). Нужна одна согласованная картина.
- **Механика рантайма и тулчейна «Под капотом».** A-03 (аллокатор), A-05 (toolchain), A-15 (`go install`), A-17 (`-o`/линкер), A-18 (Thumb). Каждый пункт по отдельности мелкий, но все вместе показывают, что раздел писался без проверки по исходникам.
- **Упрощения про `-race`, память и производительность.** A-01 («мгновенно падает»), A-09 («порча памяти»), A-10 («2–4 раза»), A-22 («аварийно»), A-26 («2–3 раза»). Читатель, который усвоит эти фразы, неверно поймёт, что детектор делает и чего стоит.

## 4. Упущения главы

Помимо находок выше, не хватает:

- **Флаги воспроизводимой и релизной сборки:** `-trimpath`, `-buildvcs`, `go version -m <бинарник>` (чтобы увидеть флаги и версию внутри файла). Глава про `-ldflags` и релизы без этого неполна.

- **`signal.NotifyContext`** (Go 1.16+) как современный способ перехвата сигналов — A-23.
- **Условие «Подводные камни» про CGO в 005** стоит сопроводить ссылкой на то, какие пакеты тянут cgo (`net`, `os/user`) — связано с A-02.
