## 2. Находки

### G-01. Невалидный синтаксис отрицательного просмотра вперед (Lookahead) в `go test -run`
- **Где:** `029. Модульное тестирование (Unit Testing) и Assertions/01. Основы testing.T, команды go test/031. Выборочный запуск тестов через флаг -run.md` → `## На собеседовании`
- **Цитата:** «Использовать отрицательное регулярное выражение с инверсией или отрицательным просмотром вперед, либо запустить `go test -run "^((?!TestSlow).)*$"`.»
- **Утверждение:** Утверждается, что с помощью Perl-совместимого отрицательного просмотра вперёд `(?!)` можно исключать медленные тесты из запуска `go test -run`.
- **Почему проверить:** Механизм фильтрации тестов в `go test` основан на стандартном движке регулярных выражений Go `regexp` (библиотека RE2). Спецификация синтаксиса RE2 принципиально не поддерживает опережающие и ретроспективные проверки (lookaround assertions: lookahead `(?!...)`, `(?=...)`, lookbehind `(?<!...)`, `(?<=...)`) ради гарантии линейного времени поиска $O(N)$ без катастрофического бектрекинга. Запуск команды `go test -run "^((?!TestSlow).)*$"` завершается аварийной ошибкой: `error parsing regexp: invalid or unsupported Perl syntax: (?!`. Рекомендовать такое на собеседовании или в учебнике недопустимо. Исключение тестов в Go идиоматично делается через `testing.Short()` / `-short`, через тэги сборки (`//go:build !slow`) или инверсию на уровне shell / тестовых пакетов.
- **Что проверить и где:** Запуск команды `go test -run "^((?!TestSlow).)*$"` в любом Go-пакете; документация `regexp/syntax` standard library.
- **Тип:** факт / код
- **Приоритет:** High

### G-03. Ложное утверждение о запрете и панике вложенных `t.Cleanup()`
- **Где:** `029. Модульное тестирование (Unit Testing) и Assertions/03. testify_suite, мокирование mock.Mock/095. Идиоматичное освобождение ресурсов.md` → `## На собеседовании`
- **Цитата:** «**Вопрос с собеседования:** «Можно ли вызывать t.Cleanup внутри другого t.Cleanup?»  
**Ответ:** Нет, регистрация нового cleanup внутри уже исполняющегося cleanup запрещена рантаймом пакета `testing` и приведет к панике.»
- **Утверждение:** Утверждается, что регистрация нового `t.Cleanup` внутри уже исполняющейся функции очистки запрещена и вызывает панику рантайма.
- **Почему проверить:** Утверждение полностью противоречит реализации в `src/testing/testing.go`. Внутри `testing.common`:
  ```go
  func (c *common) Cleanup(f func()) {
      c.mu.Lock()
      defer c.mu.Unlock()
      c.cleanups = append(c.cleanups, f)
  }
  ```
  При завершении теста цикл извлечения функций очистки работает по принципу стека (LIFO):
  ```go
  for len(c.cleanups) > 0 {
      fn := c.cleanups[len(c.cleanups)-1]
      c.cleanups = c.cleanups[:len(c.cleanups)-1]
      fn()
  }
  ```
  Если функция `fn()` вызывает `t.Cleanup(anotherFn)`, новый коллбэк безопасно добавляется в конец среза `c.cleanups` под мьютексом и на следующей итерации цикла успешно извлекается и исполняется. Никакой паники не происходит. Кандидат, давший такой ответ на собеседовании, покажет незнание стандартной библиотеки Go.
- **Что проверить и где:** Запуск теста с вызовом `t.Cleanup` внутри первого `t.Cleanup`; исходный код `src/testing/testing.go`.
- **Тип:** факт / педагогика
- **Приоритет:** High

### G-04. Неэкранированный квантификатор `+` в шаблоне запуска субтеста `-run`
- **Где:** `029. Модульное тестирование (Unit Testing) и Assertions/01. Основы testing.T, команды go test/004. Табличные тесты (Table-Driven Tests).md` → `## На собеседовании`

Для совпадения требуется экранирование: `go test -run "TestAddTableDriven/-5\+-7"`. Без экранирования команда выдаст `testing: warning: no tests to run`.
- **Что проверить и где:** Запуск `go test -v -run TestAddTableDriven/-5+-7` на коде упражнения 004.

### G-07. Подмена концепции каталога `testdata/` динамическим созданием во временной директории

### G-11. Устаревшие категоричные утверждения об обязательности `os.Exit` и запрете `defer` в `TestMain`
- **Где:** 
  - `sources/029. Модульное тестирование (Unit Testing) и Assertions/01. Основы testing.T, команды go test/012. Управление жизненным циклом тестов пакета.md` → `## Подводные камни`
  - `sources/029. Модульное тестирование (Unit Testing) и Assertions/03. testify_suite, мокирование mock.Mock/075. Инициализация пакета через TestMain.md` → `## Подводные камни`, `## Под капотом`
- **Цитата:** «Забыть вызвать `os.Exit(m.Run())`. Если функция `TestMain` завершится простым возвратом `return`, утилита `go test` посчитает тест незавершенным или некорректным.» (упр. 012).  
«Использовать `defer` для очистки внутри `TestMain`: вызов `os.Exit()` предотвратит выполнение любых `defer` в текущей функции! Очистка должна вызываться явно до `os.Exit`.» (упр. 075).
- **Утверждение:** Утверждается, что возврат из `TestMain` без `os.Exit` ломает прогон тестов, а отложенные функции `defer` принципиально невозможно использовать для Teardown в `TestMain`.
- **Почему проверить:** Начиная с Go 1.15 (август 2020 г.), сигнатура и поведение `TestMain` были официально обновлены: функция `TestMain` больше не обязана вызывать `os.Exit`. Если `TestMain` завершается обычным оператором `return`, тестовый бинарник самостоятельно вызывает `os.Exit` со статусом, возвращенным `m.Run()`.       defer teardown()

  Утверждение о фатальности отсутствия `os.Exit` устарело на 6 лет.
- **Что проверить и где:** Release Notes Go 1.15 (`testing` package: *TestMain is no longer required to call os.Exit*).
- **Тип:** устарело / факт
- **Приоритет:** Medium

### G-18. Некорректное объяснение сравнения приватных полей в `reflect.DeepEqual`

## 4. Упущения главы

1. **Контекст выполнения теста `t.Context()` (Go 1.24+):**  
   В Go 1.24 в `*testing.T` добавлен метод `t.Context()`, возвращающий `context.Context`, автоматически отменяемый при завершении теста или срабатывании таймаута. Это современный и важнейший паттерн для тестирования сетевых клиентов, gRPC и горутин без ручного создания `context.WithCancel`.
2. **Дедлайн выполнения теста `t.Deadline()` (Go 1.15+):**  
   Метод `t.Deadline() (deadline time.Time, ok bool)` позволяет тестам узнать, установлен ли флаг `-timeout` и сколько времени осталось до принудительного завершения процесса. Тема полезна для предотвращения зависания интеграционных тестов.
3. **Библиотека `google/go-cmp` (`cmp.Diff`):**  
   В промышленной разработке уровня BigTech (Google, Kubernetes, Docker) де-факто стандартом глубокого структурного сравнения является библиотека `github.com/google/go-cmp/cmp`. В отличие от `assert.Equal`, она генерирует понятные diff-отчёты в стиле unified diff, поддерживает фильтрацию приватных полей и кастомные трансформеры. Упоминание `cmp.Diff` как альтернативы `testify` необходимо для уровня Middle/Senior.
4. **Интерфейс `testing.TB` и кастомные ассершны:**  
   Отсутствует разбор написания универсальных хелперов, принимающих `testing.TB` (общий интерфейс для `*testing.T` и `*testing.B`), с обязательным вызовом `t.Helper()`.
5. **Взаимосвязь с Fuzzing (`testing.F`) и Benchmarks (`testing.B`):**  
   В вводной и заключительной частях главы нет явных навигационных ссылок на то, в каких последующих главах рассматриваются фаззинг и нагрузочное профилирование.
