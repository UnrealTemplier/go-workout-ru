## 🧭 1. Сводная оценка главы

Глава 18 содержит **100 упражнений** (200 кодовых блоков: 100 исходных файлов `main.go` и 100 блоков эмуляции терминала). Она охватывает базовые системные вызовы операционной системы и пакеты стандартной библиотеки Go: `os`, `io`, `bufio`, `path/filepath`, `encoding/binary`, `encoding/json`, `encoding/csv` и `encoding/gob`.

При сквозном техническом аудите цепочки **«Формулировка задачи → Ожидаемое ТЗ → Листинг решения → Объяснение рантайма → Терминальный вывод»** выявлены критические проблемы:
1. **Некомпилируемый код в двух упражнениях (Упр. 36 и Упр. 93)**: программы не собираются компилятором `go build` из-за неиспользуемых импортов (`"log"` и `"errors"`), что в Go является фатальной ошибкой компиляции.
2. **Сломанные и хронологически перевернутые перекрестные ссылки**:
   - В Упр. 48 задача требует *«переписать упр. 96 и 97»*, хотя упр. 96 и 97 посвящены совершенно другим темам и уже содержат `defer file.Close()`.

   - В Упр. 30 и Упр. 53 захардкожены фиктивные SHA256-хэши, не совпадающие с реальным хэшированием байт.

### 2.4. Упражнения 25, 34, 75, 83: Прямые математические и расчетные ошибки в терминальных блоках
- **Раздел / Упражнение:** Упражнения 25, 34, 75, 83 в `builder/chapter18_data.json`.
- **Факты расхождений кода и эталонного вывода:**
  1. **Упр. 25 (Длина UTF-8 строки):**
     - В коде: `n, err := f.WriteString("Привет, Go!\n")`
     - В коде: `fmt.Printf("Записано %d байт в файл %s\n", n, filename)`
     - Реальный вывод: `Записано 18 байт в файл greeting.txt` (6 букв «Привет» $\times 2$ байта = 12 Б + 6 байт ASCII `", Go!\n"` = 18 Б).
     - В терминале учебника: `# Записано 21 байт в файл greeting.txt`. Ошибка на 3 байта.
  2. **Упр. 34 (Подсчет слов утилитой wc):**
     - Текст: `"Go is an open source programming language\nthat makes it easy to build simple, reliable, and efficient software."`
     - Разбиение через `bufio.ScanWords` дает: 7 слов в строке 1 + 11 слов в строке 2 = **18 слов**.
     - В коде: `words, _ := countTokens(path, bufio.ScanWords)`
     - Реальный вывод: `-> Слов: 18`
     - В терминале учебника: `#  -> Слов:     17`. Ошибка счетчика слов на 1 слово.
  3. **Упр. 75 (Смещение Tail от конца файла):**
     - Текст: `"2026-09-02 12:00:00 Old Log Event\n2026-09-02 18:30:00 CRITICAL_PAYMENT_FAILURE_RETRY"` (длина 84 байта).
     - Вызов: `TailBytes(path, 40)` запрашивает последние **40 байт**.
     - Последние 40 байт строки: `" 18:30:00 CRITICAL_PAYMENT_FAILURE_RETRY"`.
     - В терминале учебника: `# 00 CRITICAL_PAYMENT_FAILURE_RETRY` (длина всего 33 байта!). Ошибка вычисления позиции курсора на 7 байт.
  4. **Упр. 83 (Размер файла при буферизованной записи):**
     - Формат строки: `line := fmt.Sprintf("EventID=%05d Status=SUCCESS Latency=0.45ms\n", i)`.
     - Длина одной строки: ровно 44 байта (`EventID=00001 Status=SUCCESS Latency=0.45ms\n`).
     - Всего пишется 10 000 строк. Итоговый размер: $10\,000 \times 44 = \mathbf{440\,000}$ байт.
     - В терминале учебника: `# Успешно записано 10000 строк через bufio.Writer. Размер: 420000 байт`.
     - Причина: автор скопировал шаблон из Упр. 29 (где строка была 42 байта и 1000 строк = 42 000 байт) и механически приписал ноль, не запустив код. Ошибка на 20 000 байт.
- **В чем проблема:** Все эти ошибки приводят к гарантированному падению автотестов сравнения терминального вывода и ставят под сомнение техническую компетентность учебных материалов.

### 3.4. Упражнение 18: Опасное заблуждение об «атомарности» `os.WriteFile`
- **Раздел / Упражнение:** Упражнение 18: [`builder/chapter18_data.json`](file:///home/ut/work/go-workout/builder/chapter18_data.json).

### 3.6. Упражнение 57: Продвижение уязвимости TOCTOU в качестве «паттерна безопасного чтения»
- **Раздел / Упражнение:** Упражнение 57: [`sources/18. Работа с файлами.md`](file:///home/ut/work/go-workout/sources/18.%20%D0%A0%D0%B0%D0%B1%D0%BE%D1%82%D0%B0%20%D1%81%20%D1%84%D0%B0%D0%B9%D0%BB%D0%B0%D0%BC%D0%B8.md#L123), [`builder/chapter18_data.json`](file:///home/ut/work/go-workout/builder/chapter18_data.json).
- **Фрагмент кода решения:**
  ```go
  func SafeRead(path string) ([]byte, error) {
      _, err := os.Stat(path)
      if err != nil {
          if os.IsNotExist(err) {
              return nil, fmt.Errorf("SafeRead: файл %q не найден", path)
          }
          return nil, fmt.Errorf("SafeRead: ошибка доступа: %w", err)
      }
      return os.ReadFile(path)
  }
  ```
- **В чем проблема:**
  1. Функция названа `SafeRead`, хотя она представляет собой классический антипаттерн **TOCTOU (Time-Of-Check to Time-Of-Use)**.
  2. Вызов `os.Stat` перед `os.ReadFile`:
     - Создает гонку данных: файл может быть удален или подменен символической ссылкой другим процессом между вызовами `os.Stat` и `os.ReadFile`.
     - Создает двойную нагрузку на диск: системный вызов `stat` выполняется дважды (один раз в `os.Stat`, второй раз внутри самого `os.ReadFile`).
  3. Идиоматичный Go-код никогда не проверяет существование файла перед открытием, а сразу вызывает `os.Open` / `os.ReadFile` и обрабатывает ошибку `errors.Is(err, fs.ErrNotExist)`.
  4. Хотя в секции Pitfalls автор кратко упоминает TOCTOU, сам факт подачи функции `SafeRead` как эталонного решения учит начинающих разработчиков опасному антипаттерну.
- **Необходимые проверки / источники:** CWE-367: Time-of-check Time-of-use (TOCTOU) Race Condition.

## 🔍 5. Важные пробелы и упущения (Omissions)

Для курса уровня Middle/Senior/Staff Go Developer в главе по файловым операциям и I/O критически недостает следующих тем:

1. **Абстракция виртуальной файловой системы `io/fs` и `os.DirFS` (Go 1.16+):**
   - Пакет `io/fs` определяет стандартный интерфейс `fs.FS` для работы с любыми файловыми системами (диск, zip-архив, память, S3).
   - `os.DirFS(dir)` позволяет изолировать файловые операции внутри конкретной директории, предотвращая выход за ее пределы.
   - Использование `fs.WalkDir` вместо устаревшего `filepath.Walk` почти не проиллюстрировано с точки зрения абстракций интерфейсов.
2. **Гарантии физической сохранности на диске: `file.Sync()` (`fsync(2)`) vs кэш ОС:**
   - Вызовы `file.Write()` или `bufio.Writer.Flush()` передают данные только в Page Cache ядра ОС.
   - При аварии питания или сбое сервера данные из Page Cache теряются.
   - Для транзакционных логов (WAL), баз данных и критических конфигов обязателен вызов `file.Sync()`. В главе этому не посвящено ни одного практического упражнения.
3. **Паттерн промышленной атомарной записи (Atomic Write):**
   - Золотой стандарт сохранения конфигураций в Go: запись во временный файл в той же директории (`os.CreateTemp(dir, ...)`), сброс `file.Sync()`, закрытие и атомарная замена через `os.Rename`.
   - Это гарантирует, что файл никогда не окажется битым или пустым при сбое. В курсе этот фундаментальный паттерн упоминается лишь теоретически, но отсутствует в виде практической задачи.
4. **Межпроцессные файловые блокировки (`flock` / `unix.Flock`):**
   - Блокировка доступа к файлу между несколькими процессами операционной системы (например, single-instance lock для демона или синхронизация CLI-утилит).
5. **Безопасность файловых путей: защита от Path Traversal и Zip Slip:**
   - Опасность конкатенации непроверенных путей из пользовательского ввода (`filepath.Join(root, userInput)` может позволить выйти в `/etc/passwd` через `../../`).
   - Валидация через `filepath.Clean` и проверка `strings.HasPrefix(target, root)`.
6. **Отображение файлов в память (`mmap`):**
   - Использование `syscall.Mmap` (или `golang.org/x/exp/mmap`) для быстрого чтения многогигабайтных файлов без системных вызовов `read` и без аллокаций памяти в куче (как это сделано в BoltDB и Prometheus TSDB).
7. **Пулинг буферов ввода-вывода (`sync.Pool`):**
   - В HighLoad I/O постоянное выделение `make([]byte, 32*1024)` в каждой горутине создает колоссальное давление на Garbage Collector.
   - Использование `sync.Pool` совместно с `io.CopyBuffer` — стандартный производственный прием.
