### 2.1. Упражнение 55: Некомпилируемый код — неиспользуемый импорт `errors` и игнорирование условий задачи
- **Раздел / Упражнение:** Упражнение 55 ([`sources/13. Структуры.md`](file:///home/ut/work/go-workout/sources/13.%20%D0%A1%D1%82%D1%80%D1%83%D0%BA%D1%82%D1%83%D1%80%D1%8B.md#L120), `builder/chapter13_data.json`, `dist/013-struktury.html`).
- **Фрагмент кода решения:**
  ```go
  package main

  import (
  	"errors"
  	"fmt"
  )

  type Employee struct {
  	Name string
  	age  int // Приватное поле
  }
  ...
  func (e *Employee) SetAge(newAge int) error {
  	if newAge < 18 || newAge > 75 {
  		return fmt.Errorf("недопустимый возраст сотрудника: %d (допустимо 18-75)", newAge)
  	}
  	e.age = newAge
  	return nil
  }
  ```

     ```text
     # command-line-arguments
     ./main.go:4:2: "errors" imported and not used
     ```
     Запуск программы через `go run` или `go test` аварийно падает.
  2. **Игнорирование ТЗ задачи:** Условие задачи явно гласит:  
     > *«Инкапсуляция (Геттеры и Сеттеры): Помести User в отдельный пакет. Сделай поле age с маленькой буквы (приватным). Напиши публичные методы Age() int (геттер) и SetAge(int) error (сеттер с валидацией).»*
     - Вместо типа `User` объявлен `Employee`.
     - Код не вынесен в отдельный пакет, а размещен в `package main`.
     - Внутри одного пакета неэкспортируемые поля полностью открыты для прямого чтения и записи (`emp.age = 10` сработает без ошибок), поэтому демонстрация инкапсуляции не состоялась.

### 2.2. Упражнение 48: Логический баг усечения буфера и ложный эталонный вывод программы
- **Раздел / Упражнение:** Упражнение 48 (`builder/chapter13_data.json`, `dist/013-struktury.html`).
- **Фрагмент кода решения и терминального вывода:**
  ```go
  func ProcessStream(rc io.ReadCloser) {
  	defer rc.Close()
  	buf := make([]byte, 32)
  	n, _ := rc.Read(buf)
  	fmt.Printf("Прочитано: %q\n", string(buf[:n]))
  }

  func main() {
  	stream := StreamWrapper{
  		Reader: strings.NewReader("Бинарные данные сессии"),
  		Closer: DummyCloser{},
  	}

  	// StreamWrapper автоматически реализует io.ReadCloser:
  	ProcessStream(stream)
  }
  ```
  Заявленный эталонный вывод в учебнике:
  ```text
  go run main.go
  # Прочитано: "Бинарные данные сессии"
  # Поток успешно закрыт
  ```
- **В чем проблема:**
  1. Строка `"Бинарные данные сессии"` в кодировке UTF-8 занимает **42 байта** («Бинарные» = 16 Б, пробел = 1 Б, «данные» = 12 Б, пробел = 1 Б, «сессии» = 12 Б; итого $16 + 1 + 12 + 1 + 12 = 42$ байта).
  2. Буфер чтения аллоцирован размером всего **32 байта**: `buf := make([]byte, 32)`.
  3. Функция выполняет ровно один нециклический вызов `rc.Read(buf)` и читает первые 32 байта.
  4. Первые 30 байт — это `"Бинарные данные "`. 31-й и 32-й байты — это двухбайтовая русская буква «с» (первая буква слова «сессии»).
  5. Фактический вывод программы при запуске:
     ```text
     Прочитано: "Бинарные данные с"
     Поток успешно закрыт
     ```
  6. Окончание слова «ессии» (оставшиеся 10 байт) никогда не считывается! Автор учебника не запускал код и наугад вписал полную строку в терминальный блок. Любой тест на совпадение вывода упадет с ошибкой несоответствия строк.
- **Необходимые проверки / источники:** Запуск `go run main.go` в среде упр. 48; проверка размера буфера (`len("Бинарные данные сессии") > 32`).

### 2.3. Упражнение 42: Математическая ошибка срезов UTF-8 и фальсификация побайтового вывода
- **Раздел / Упражнение:** Упражнение 42 (`builder/chapter13_data.json`, `dist/013-struktury.html`).
- **Фрагмент кода и ожидаемого терминального вывода:**
  ```go
  source := strings.NewReader("Привет, высоконагруженный мир Go!")
  counter := &CountingReader{Reader: source}

  buf := make([]byte, 16)
  for {
      n, err := counter.Read(buf)
      if n > 0 {
          fmt.Printf("Прочитано %d байт: %q\n", n, string(buf[:n]))
      }
      if err == io.EOF {
          break
      }
  }
  ```
  Ожидаемый вывод, зафиксированный в учебнике:
  ```text
  go run main.go
  # Прочитано 16 байт: "Привет, вы"
  # Прочитано 16 байт: "соконагруж"
  # Прочитано 16 байт: "енный мир "
  # Прочитано 11 байт: "Go!"
  # Всего прочитано байт: 59
  ```
- **В чем проблема:**
  1. Автор пособия посчитал символы вручную, исходя из ложного предположения, что 1 кириллический символ равен 1 байту!
  2. В кодировке UTF-8 каждый русский символ занимает **2 байта**.
  3. Проверим математику заявленного вывода:
     - `"Привет, вы"`: 8 кириллических букв ($8 \times 2 = 16$ Б) + запятая (1 Б) + пробел (1 Б) = **18 байт**. Буфер из 16 байт физически не может вместить 18 байт!
     - `"соконагруж"`: 10 кириллических букв = **20 байт** (в буфере 16 байт!).
     - `"енный мир "`: 8 кириллических букв (16 Б) + 2 пробела (2 Б) = **18 байт**.
     - `"Go!"`: 3 ASCII символа = **3 байта** (в эталоне написано `Прочитано 11 байт`).
  4. Фактический вывод реальной программы Go:
     ```text
     Прочитано 16 байт: "Привет, в"
     Прочитано 16 байт: "ысоконаг"
     Прочитано 16 байт: "руженный"
     Прочитано 11 байт: " мир Go!"
     Всего прочитано байт: 59
     ```
  5. Заявленный в учебнике лог полностью сфабрикован «из головы» и учит в корне неверной модели работы со строками и байтовыми срезами в Go.
- **Необходимые проверки / источники:** Запуск `go run main.go` для листинга упр. 42; `python3 -c 'print([len(s.encode("utf-8")) for s in ["Привет, вы", "соконагруж", "енный мир ", "Go!"]])'`.

### 2.4. Упражнение 53: Арифметическая ошибка байтовой длины UTF-8 строки в терминальном блоке
- **Раздел / Упражнение:** Упражнение 53 (`builder/chapter13_data.json`, `dist/013-struktury.html`).
- **Фрагмент кода и ожидаемого терминального вывода:**
  ```go
  c1 := Container{Data: "Привет, Go!"}
  ...
  case string:
      fmt.Printf("Строка длиной %d: %q\n", len(v), v)
  ```
  Ожидаемый вывод в учебнике:
  ```text
  go run main.go
  # Строка длиной 19: "Привет, Go!"
  # Числовое значение: 42 (удвоенное: 84)
  # Неизвестный тип данных: bool -> true
  ```
- **В чем проблема:**
  1. В Go функция `len(s)` для строки возвращает **количество байт**, а не количество рун (символов).
  2. Строка `"Привет, Go!"` состоит из:
     - 6 кириллических букв «Привет» ($6 \times 2 = 12$ байт);
     - запятая и пробел `, ` ($1 + 1 = 2$ байта);
     - 3 ASCII-символа `Go!` ($3$ байта).
     - Итого: $12 + 2 + 3 = 17$ байт.
  3. Фактический вывод программы:
     ```text
     Строка длиной 17: "Привет, Go!"
     ```
  4. В эталонном логе учебника ошибочно указано `19`. Это прямое расхождение между выполнением программы и описанием в курсе.
- **Необходимые проверки / источники:** `go run main.go` для упр. 53; `len("Привет, Go!")`.

### 3.3. Упражнение 6 (Under the Hood): Устаревшая ментальная модель передачи аргументов (стек ABI0 вместо регистров ABIInternal)
- **Раздел / Упражнение:** Упражнение 6 (`under_the_hood`).
- **Фрагмент текста:**  
  > *«`AgePerson` копирует 24 байта на стек, а `AgePersonPtr` передает 8-байтный адрес в регистре `RAX`.»*
- **В чем проблема:**

### 3.4. Упражнение 20 (Under the Hood): Некорректное утверждение о побайтовом сравнении структур через `memcmp`
- **Раздел / Упражнение:** Упражнение 20 (`under_the_hood`).
- **Фрагмент текста:**  
  > *«Для сравнимых структур компилятор генерирует побайтовое сравнение полей через `CMPQ` или `memcmp`.»*
- **В чем проблема:**
  1. В Go сравнение структур через `memcmp` (по всему непрерывному блоку памяти) **недопустимо**, если структура содержит байты выравнивания (padding) или поля с плавающей точкой (`float32`/`float64`).
  2. Байты паддинга не инициализируются и могут содержать произвольный мусор. Прямой `memcmp` дал бы ложное неравенство для двух логически равных структур. Сравнение `-0.0 == +0.0` также дает `true`, а `NaN == NaN` дает `false`.
  3. Компилятор Go генерирует **попарное сравнение значащих полей** (пропуская байты паддинга), либо автогенерируемую функцию равенства типа (`runtime.memequal` для безымянных типов без паддинга). Формулировка «побайтовое сравнение через memcmp» технически неточна и может ввести в заблуждение инженера, знакомого с низкоуровневым C.
- **Необходимые проверки / источники:** The Go Programming Language Specification (§Comparison operators); дизассемблер SSA-оптимизатора Go.

### 4.3. Упражнение 68 (Interview Q&A): Неполнота правила паддинга пустой структуры `struct{}` в конце
- **Раздел / Упражнение:** Упражнение 68 (`bigtech_interview`).
- **Фрагмент текста:**  
  > *«Если `struct{}` находится в конце структуры, компилятор добавляет 1 машинное слово (8 байт) Padding...»*
- **В чем проблема:** Компилятор добавляет паддинг не «всегда 8 байт», а дополняет размер структуры до границы её собственного максимального выравнивания (`align`). Например, для `struct { a byte; b struct{} }` размер равен **2 байтам** (1 байт данных + 1 байт паддинга), а для `struct { a int32; b struct{} }` размер равен **8 байтам** (4 байта данных + 4 байта паддинга). Утверждение об обязательном добавлении 8 байт справедливо только для структур с выравниванием по 8-байтной границе.

### 4.4. Упражнение 71: Терминологическая неточность: понятие «Method Overriding» в Go
- **Раздел / Упражнение:** Упражнение 71 (`title`, `theory`).
- **В чем проблема:** Заголовок упражнения гласит: *«Переопределение методов (Method Overriding)...»*. В объектно-ориентированном программировании Overriding подразумевает динамическую диспетчеризацию (vtable / virtual dispatch). В Go наследования нет: метод внешнего типа лишь статически затеняет (shadows) promoted-метод встроенного типа на этапе разрешения селекторов компилятором. Идиоматично называть это **Method Shadowing** (затенение методов), чтобы не формировать ложных ООП-ассоциаций у новичков.

## 🔍 5. Важные пробелы и упущения (Omissions)

Для глубокого освоения темы структур на уровнях Middle+ и Senior в главе критически не хватает следующих 5 тем:

1. **Ловушка нулевого поля `struct{}` в конце структуры и утечки памяти кучи (End-of-Struct Zero-Size Field Trap):**
   - Если пустое поле `struct{}` находится в самом конце структуры (`type S struct { x int64; y struct{} }`), рантайм Go вынужден добавлять хвостовой паддинг.
   - Зачем это делается: взятие адреса `&s.y` возвращает указатель, который не должен указывать за пределы выделенного блоку памяти в куче (`mspan`). Если бы паддинга не было, указатель ссылался бы на соседний объект кучи, что приводило бы к ложному удержанию памяти сборщиком мусора (GC memory leak) или крашу аллокатора. В главе об этом механизме нет практического примера.
2. **Идиома `noCopy` и детектор `copylocks` в `go vet`:**
   - Структуры, содержащие мьютексы (`sync.Mutex`), пулы или дескрипторы ресурсов, нельзя копировать по значению.
   - Общепринятый в стандартной библиотеке Go паттерн предотвращения копирования — внедрение маркерного типа `type noCopy struct{}` с пустыми методами `Lock()` и `Unlock()`. Это заставляет анализатор `go vet` автоматически предупреждать разработчика о случайном копировании структуры по значению (`copylocks`).
3. **Правила приведения типов структур (Identical Underlying Types & Struct Tag Conversions):**
   - Когда одну структуру можно явно привести к другой: `type T1 struct { X int }` и `type T2 struct { X int }` $\implies$ `T2(t1)` валидно.
   - Историческое нововведение **Go 1.8**: структуры с одинаковыми полями, но **разными структурными тегами**, теперь легально конвертируются друг в друга (`type T1 struct { X int \`json:"x"\` }; type T2 struct { X int \`db:"x"\` }; T2(t1)`). Этот фундаментальный нюанс спецификации языка не раскрыт.
4. **False Sharing (Cache Line Bouncing) в структурах под HighLoad:**
   - В высоконагруженных многопоточных системах два независимых поля одной структуры (например, счетчики чтения и записи), находящиеся в пределах одной 64-байтной кэш-линии процессора, вызывают постоянную инвалидацию кэша ядер (Cache line bouncing).
   - Способы решения: выравнивание по кэш-линии через `_ [56]byte` или системный пакет `golang.org/x/sys/cpu` (`cpu.CacheLinePad`).
5. **Эволюция структурных тегов: тег `omitzero` в Go 1.24 и обработка `null`/нулевых значений:**
   - Исторический дефект тега `omitempty`: он не умел корректно пропускать нулевые структуры (например, пустой `time.Time{}` сериализовался как `"0001-01-01T00:00:00Z"`).
   - В **Go 1.24** добавлен официальный тег `omitzero`, решающий эту проблему.
   - Разбор лучших практик представления опциональных полей: указатели `*string` vs типы вроде `sql.NullString` vs кастомные типы.
