### G-04. Подмена алгоритма: банальный Fixed Window выдан за Token Bucket Rate Limiter с ошибкой в HTTP-заголовке
- **Где:** `sources/028. Базы данных NoSQL и кэширование (Redis)/04. Распределенные блокировки Redlock, сессии, CQRS/113. Финальное испытание.md` → «## Условие», «## Теория», «## Код решения», `main.go` (строки 5, 13, 42–56, 73–78)
- **Цитата:** «Финальная интеграция промышленного Token Bucket лимитера в HTTP стэк Go» / `local current = redis.call('INCR', key) \n if current == 1 then redis.call('EXPIRE', key, 60) end` / `w.Header().Set("X-RateLimit-Remaining", strconv.FormatInt(remaining, 10))`
- **Утверждение:** Программа реализует промышленный алгоритм Token Bucket для защиты HTTP API от DDoS и флуда.
- **Почему проверить:**
  1. В Lua-скрипте реализован примитивный счетчик фиксированного окна: `INCR` + `EXPIRE 60`. В коде нет емкости корзины (capacity), скорости пополнения (refill rate) и дельты времени. Называть `INCR` с `EXPIRE` алгоритмом «Token Bucket» — грубая подмена понятий и дезинформация читателя.
  2. При превышении лимита (`current > limit`) Lua-скрипт возвращает `{0, current}`. Переменная `remaining` в Go принимает значение `current` (например, 11, 12...). В результате HTTP-клиенту возвращается заголовок `X-RateLimit-Remaining: 11` вместо `0`!
- **Что проверить и где:** Листинг `finalLimiterLua` и хэндлер `APIRateLimiter` в задаче 113; сравнение с настоящим алгоритмом Token Bucket из задачи 081.
- **Тип:** условие↔решение / факт / код
- **Приоритет:** High

### G-05. Опасное разрушение взаимного исключения в Distributed Lock с автопродлением (Watchdog)
- **Где:** `sources/028. Базы данных NoSQL и кэширование (Redis)/01. Подключение go-redis, базовые типы/023. Distributed Lock с фоновым автопродлением.md` → «## Код решения», `main.go` (строки 44, 57, 71)
- **Цитата:** `acquired, err := rdb.SetNX(ctx, lockKey, "worker_watchdog", lockTTL).Result()` / `_ = rdb.Del(context.Background(), lockKey).Err()` / `res, err := rdb.Expire(watchdogCtx, lockKey, lockTTL).Result()`
- **Утверждение:** Фоновый Watchdog надежно продлевает блокировку, предотвращая её потерю при долгой работе.
- **Почему проверить:** В коде значение блокировки захардкожено статической константой `"worker_watchdog"` (без уникального UUID процесса). Фоновая горутина вызывает слепой `rdb.Expire`, а `defer` вызывает слепой `rdb.Del`. Если ключ истечет из-за сетевой задержки или паузы GC, и ресурс будет захвачен другим воркером, данный Watchdog продлит ЧУЖОЙ ключ, а `defer` удалит ЧУЖОЙ ключ! В продакшене продление и снятие блокировки обязаны проверять соответствие UUID владельца через атомарный Lua-скрипт.
- **Что проверить и где:** Код `runWithLockWatchdog` в задаче 023; сравнение с предостережениями автора в задачах 019 и 096.
- **Тип:** код / педагогика
- **Приоритет:** High

### G-06. Дефект алгоритма Sliding Window Log на ZSET: схлопывание запросов при коллизии таймстемпов
- **Где:** `sources/028. Базы данных NoSQL и кэширование (Redis)/03. Транзакции MULTI_EXEC, конвейеры Pipeline/077. Rate Limiter на базе Sliding Window Log в Lua.md` → «## Код решения», `main.go` (строка 58)
- **Цитата:** `redis.call('ZADD', key, now, now)`
- **Утверждение:** Lua-скрипт реализует точный скользящий лог запросов в Sorted Set.
- **Почему проверить:** В Sorted Set значения `member` обязаны быть уникальными. Если два или более запроса поступают в течение одной и той же миллисекунды (норма при нагрузке свыше 1000 RPS), значение `now` совпадает. Вызов `ZADD key now now` просто перезапишет существующий member, не увеличив размер множества! В итоге `ZCARD` не увеличится, и параллельные запросы не будут учтены, допуская превышение лимита в разы. В качестве `member` необходимо использовать уникальное значение (`now .. ":" .. math.random()` или UUID).
- **Что проверить и где:** Строка 58 в задаче 077; документация по `ZADD` в Redis.
- **Тип:** код / факт
- **Приоритет:** High

### G-07. Некорректная логика Sliding Window в TxPipeline: раздувание ZSET и вечная блокировка при флуде
- **Где:** `sources/028. Базы данных NoSQL и кэширование (Redis)/03. Транзакции MULTI_EXEC, конвейеры Pipeline/090. Точный Sliding Window Log Rate Limiter на Sorted.md` → «## Код решения», `main.go` (строки 48–61)
- **Цитата:** `pipe.ZAdd(ctx, key, redis.Z{Score: float64(now), Member: fmt.Sprintf("%d", now)}) \n ... \n return cardCmd.Val() < s.limit, nil`
- **Утверждение:** Метод `Allow` атомарно проверяет лимит запросов и возвращает решение.
- **Почему проверить:** В `TxPipeline` все команды выполняются пакетно, поэтому `pipe.ZAdd` вызывается БЕЗУСЛОВНО до того, как код проверит `cardCmd.Val() < s.limit`. При флуде каждый заблокированный запрос записывается в ZSET. Коллекция бесконечно разрастается в памяти, а пользователь оказывается заблокирован на неопределенный срок, пока не прекратит слать запросы. Запись в ZSET должна производиться строго при соблюдении лимита (что требует Lua-скрипта, а не TxPipeline).
- **Что проверить и где:** Код `SlidingLogLimiter.Allow` в задаче 090.
- **Тип:** код / педагогика
- **Приоритет:** High

### G-17. Некорректная терминология: подмена Stale Read термином Dirty Read в задаче 115
- **Где:** `sources/028. Базы данных NoSQL и кэширование (Redis)/04. Распределенные блокировки Redlock, сессии, CQRS/115. Предотвращение Dirty Read.md` → Заголовок H1, «## Теория» (строки 1, 9)
- **Цитата:** `Предотвращение Dirty Read: атомарное обновление в БД и синхронная инвалидация в Redis` / `Проблема Грязного чтения (Dirty/Stale Read)`
- **Утверждение:** Чтение устаревших данных из кэша после фиксации изменений в реляционной БД является «грязным чтением» (Dirty Read).
- **Почему проверить:** В теории транзакций и стандарте SQL-92 **Dirty Read (грязное чтение)** имеет строгое математическое определение: чтение данных, записанных другой транзакцией, которая еще не зафиксирована (uncommitted) и может быть откатана (`ROLLBACK`). Чтение же устаревших данных из кэша после успешного коммита транзакции в БД называется **Stale Read (чтение устаревших данных)** или нарушением **Cache Consistency**. Подмена устоявшегося фундаментального термина базы данных вводит читателя в заблуждение перед системными собеседованиями.
- **Что проверить и где:** Стандарт ANSI SQL-92 (Isolation Levels); замена термина «Dirty Read» на «Stale Read / Рассинхронизация кэша».
- **Тип:** факт / педагогика
- **Приоритет:** Low

## 4. Упущения главы

1. **Client-Side Caching (RESP3, `CLIENT TRACKING`)**:  
   Начиная с Redis 6.0 и протокола RESP3, Redis поддерживает инвалидацию кэша на стороне клиента в памяти Go-процесса. Это фундаментальная архитектурная тема для HighLoad микросервисов, позволяющая снизить RTT до 0 мкс для горячих ключей. В главе тема отсутствует.
2. **Redis Sentinel и автоматический Failover**:  
   Тема Sentinel заявлена в общем описании главы (`000. О главе.md`), однако среди 115 задач нет ни одного практического упражнения с `redis.NewFailoverClient` и обработкой переключения мастера.
3. **Влияние персистентности на задержки (RDB CoW latency spikes, AOF appendfsync)**:  
   Не рассмотрены системные вопросы влияния фонового снапшота `BGSAVE` на задержки рантайма: системный вызов `fork()`, раздувание Copy-on-Write (CoW) памяти в ядре Linux, риск OOM Killer и деградация Event Loop при `appendfsync always`.
4. **Промышленный алгоритм Rate Limiting GCRA (Generic Cell Rate Algorithm)**:  
   При наличии 7 задач на Rate Limiting все они крутятся вокруг Fixed Window и ZSET. Не рассмотрен алгоритм GCRA (Leaky Bucket на таймстемпах), который требует константной памяти O(1) и одного ключа в Redis.
5. **Ограничения транзакций и кросс-слотовых операций в Redis Cluster (ошибка `CROSSSLOT`)**:  
   В кластере команды над несколькими ключами (`MGET`, `MSET`, `TxPipeline`, Lua) запрещены, если ключи попадают в разные хэш-слоты (`CROSSSLOT Keys in request don't hash to the same slot`). В главе нет практической демонстрации этой ошибки и её решения через Hash Tags (`{user:id}`).
6. **Опасность мутации разделяемого указателя в `singleflight.Group`**:  
   В задачах 067 и 075 метод `sf.Do` возвращает указатель `*User` или `string`. Если одна из ожидающих горутин мутирует полученный указатель, возникнет гонка данных (Data Race). Необходимо предостережение и возврат структуры по значению либо глубокое клонирование.
