### 2.1. Упражнения 64 и 97: Фундаментальное ложное утверждение — `defer fmt.Println(i)` якобы захватывает переменную по ссылке и выводит «двойки»
- **Раздел / Упражнение:** Упражнение 64 (`builder/chapter10_data.json`, `builder/gen_ch10_p3.py`) и Упражнение 97 (`builder/gen_ch10_p4.py`).
- **Фрагмент задачи / формулировки:**
  > Упр. 64 (Задача): «[Каверзный кейс]: Напиши цикл `for i := 0; i < 3; i++` с `defer fmt.Println(i)` внутри. **Объясни, почему выведутся двойки** (и как это исправить, передавая аргумент в функцию).»  
  > Упр. 97 (Задача): «Напиши функцию `DeferWithArgs()`. **Вызови `defer fmt.Println(i)` в цикле. Покажи, что все defer'ы выводят одно и то же значение (потому что `i` захватывается по ссылке в замыкание).** Исправь, передавая `i` как аргумент анонимной функции.»
- **В чем проблема:** Это грубейшая фактическая ошибка относительно модели выполнения Go, разрушающая базовое понимание рантайма у студентов:
  1. В Go аргументы любой функции, вызываемой через `defer funcName(arg)`, **вычисляются НЕМЕДЛЕННО (at evaluation time)** в момент достижения инструкции `defer` и копируются по значению!
  2. Вызов `defer fmt.Println(i)` в цикле `for i := 0; i < 3; i++` **НИКОГДА не выводит «двойки» и НИКОГДА не выводит одно и то же значение**! Во всех версиях Go (начиная с Go 1.0) этот код выводит строго:
     ```text
     2
     1
     0
     ```
     поскольку при `i=0` откладывается печать `0`, при `i=1` — `1`, при `i=2` — `2`, а при выходе стек LIFO печатает `2, 1, 0`.
  3. `defer fmt.Println(i)` **НЕ является замыканием** и **НЕ захватывает `i` по ссылке**! Захват по ссылке происходит *только* при создании анонимной функции без аргументов: `defer func() { fmt.Println(i) }()`.
  4. В упр. 64 в теории автор сам опровергает условие собственной задачи, заявляя: *«defer fmt.Println(i) вычисляет аргумент i немедленно в момент объявления (выведет 2 1 0)»*. Студент видит в задаче требование «объяснить, почему выведутся двойки», а в коде и консоли видит вывод `2, 1, 0`.
  5. В упр. 97 автор в задаче снова утверждает, что `defer fmt.Println(i)` захватывает `i` по ссылке, а в коде решения даже не показывает «ошибочный» вызов, а сразу пишет `defer func(val int) { ... }(i)`.
- **Необходимые проверки / источники:** Спецификация языка Go (The Go Programming Language Specification, §Defer statements): *"Each time a "defer" statement executes, the function value and parameters to the call are evaluated as usual and saved anew but the actual function is not invoked"*. Запуск `for i := 0; i < 3; i++ { defer fmt.Println(i) }`.

### 2.2. Упражнение 9: Грубая архитектурная ошибка — утверждение, что вещественные числа (`float64`) передаются в регистрах `RAX, RBX, RCX`
- **Раздел / Упражнение:** Упражнение 9, Секция 1 (`builder/gen_ch10_p1.py`, `under_the_hood`).
- **Фрагмент текста:**
  > «В архитектуре ABIInternal (Go 1.17+) до 9 целочисленных **и вещественных аргументов/результатов передаются напрямую через регистры CPU (RAX, RBX, RCX...)**.»
- **В чем проблема:** Фундаментальное искажение низкоуровневой архитектуры x86-64 и конвенции вызовов Go:
  1. Регистры `RAX`, `RBX`, `RCX`, `RDX`, `RSI`, `RDI`, `R8`, `R9`, `R10` являются **целочисленными регистрами общего назначения (General Purpose Registers)**. Процессор x86-64 физически не выполняет операции с плавающей точкой в регистрах `RAX/RBX/RCX`.
  2. В Go ABIInternal для архитектуры `amd64` определены две независимые группы регистров:
     - Целочисленные параметры / указатели: 9 регистров (`AX, BX, CX, DI, SI, R8, R9, R10, R11`).
     - **Вещественные параметры (`float32`, `float64`): 15 векторных SSE/SIMD-регистров (`X0` – `X14`)**!
  3. Дизассемблирование функции `CalcAll(a, b float64) (sum, diff, prod, quot float64)` через `go tool compile -S` наглядно показывает, что компилятор использует исключительно регистры `X0, X1, X2, X3, X4` и инструкции `ADDSD`, `SUBSD`, `MULSD`, `DIVSD`. Ни один из регистров `RAX/RBX/RCX` для передачи float64 не используется.
- **Необходимые проверки / источники:** Документация Go Internal ABI Specification (`cmd/compile/internal-abi.md`): раздел *"amd64 architecture: Floating-point registers X0 through X14"*.

### 3.1. Упражнение 65: Ошибочная ментальная модель работы памяти — утверждение о сохранении состояния «между кадрами стека»
- **Раздел / Упражнение:** Упражнение 65, Секция 3 (`builder/gen_ch10_p3.py`, `under_the_hood`).

### 3.2. Упражнение 6: Недостоверная рекомендация пакета `utf8string` для Extended Grapheme Clusters
- **Раздел / Упражнение:** Упражнение 6, Секция 1 (`builder/gen_ch10_p1.py`, `bigtech_interview`).
- **Фрагмент текста:**
  > «Для графемных кластеров требуются специализированные библиотеки (например **`golang.org/x/exp/utf8string`** или `uniseg`), так как комбинированные эмодзи состоят из нескольких рун...»
- **В чем проблема:** Пакет `golang.org/x/exp/utf8string` **НЕ умеет работать с графемными кластерами**! Согласно официальной документации Go: *"Package utf8string provides an efficient way to index strings by rune rather than by byte"*. Он оперирует исключительно отдельными рунами (`rune` / Code Points). При попытке развернуть флаг страны, эмодзи с тоном кожи или составную графему (например, `é` = `e` + `\u0301`) пакет `utf8string` разорвет кластер точно так же, как стандартный `[]rune`. Для графемных кластеров необходимы специализированные парсеры правил UAX #29 (например, `github.com/rivo/uniseg`).
- **Необходимые проверки / источники:** Документация `golang.org/x/exp/utf8string`; Unicode Standard Annex #29.

## 🔍 4. Кандидаты с низким приоритетом (Low Priority)

### 4.1. Упражнение 32: Некорректная терминология — `.(type)` назван «утверждением типа» (Type Assertion)
- **Фрагмент:** *«...и примените утверждение типа `.(type)`»*.
- **В чем проблема:** Согласно спецификации языка Go, `x.(T)` — это **Type Assertion**, а конструкция `switch x.(type)` — это **Type Switch Guard**. Синтаксис `.(type)` не является утверждением типа и синтаксически запрещен в любых выражениях, кроме `switch`.

### 4.2. Упражнение 94: Игнорирование ошибки в рекурсивном шаге `prev, _ := SafeFactorial(n - 1)`
- **Фрагмент:** В коде функции `SafeFactorial(n int) (int64, error)` рекурсивный вызов написан как: `prev, _ := SafeFactorial(n - 1)`.
- **В чем проблема:** Подавление возвращаемой ошибки через бланк-идентификатор `_` в функции, предназначенной обучать надежной обработке ошибок (`Safe...`), формирует плохую привычку игнорирования ошибок при рекурсии.

### 4.3. Упражнение 15: Устаревшее утверждение о вызове `memmove` при передаче массива в 40 байт
- **Фрагмент:** *«При вызове функции процессор выполняет memmove для копирования 5 * 8 = 40 байт на стек»*.
- **В чем проблема:** Для структур и массивов малого размера компилятор Go генерирует inline-инструкции `MOVUPS` (векторные инструкции SSE) или прямые перемещения регистров, не вызывая тяжелую функцию рантайма `runtime.memmove`.

### 4.4. Упражнение 50: Отсылка к устаревшему `reflect.SliceHeader`
- **Фрагмент:** *«Прямая передача дескриптора SliceHeader»*.
- **В чем проблема:** Типы `reflect.SliceHeader` и `reflect.StringHeader` официально признаны устаревшими (deprecated) начиная с Go 1.20 в пользу `unsafe.Slice` и `unsafe.String`. В современных материалах следует ссылаться на 24-байтный внутренний дескриптор среза (`internal slice struct: ptr, len, cap`).

### 4.5. Упражнение 98: Антипаттерн захвата мьютекса в интервью
- **Фрагмент:** *«Ответ: func LockAndUnlock(mu *sync.Mutex) func() { mu.Lock(); return mu.Unlock }; defer LockAndUnlock(&mu)()*».
- **В чем проблема:** В идиоматичном коде Go захват мьютекса внутри вспомогательной функции считается антипаттерном, так как размывает ответственность за критическую секцию и скрывает от линтеров (`go vet`) анализ парности вызовов блокировки. Каноничный паттерн: явный `mu.Lock()` перед `defer mu.Unlock()`.

### 4.6. Упражнение 13: Несоответствие регистра имени `adder` vs `Adder`
- **Фрагмент:** В условии задачи указано имя `adder(a int)`, а в коде решения объявлено экспортируемое имя `func Adder(a int)`.

### 4.7. Упражнения 16 и 56: Абсолютно идентичные дубликаты задачи `Divide`
- **Фрагмент:** В обоих упражнениях формулировка задачи полностью совпадает: `Divide(a, b float64) (float64, error)`. В упр. 56 решение адаптировали под Sentinel Error, но задача в опроснике была полностью скопирована.

## 🧩 5. Важные пробелы и упущения (Important Omissions)

Для исчерпывающего курса уровня Senior / Staff в Главе 10 не хватает 6 фундаментальных тем работы функций в современном рантайме Go:

1. **Поведение `panic(nil)` и тип `*runtime.PanicNilError` (Go 1.21+):**  
   В Go до версии 1.21 вызов `panic(nil)` приводил к тому, что `recover()` возвращал `nil`, создавая опасную ситуацию: программа находилась в состоянии паники, но стандартная проверка `if r := recover(); r != nil` считала, что паники не было! Начиная с Go 1.21, рантайм трансформирует `panic(nil)` в панику со специальным типом `*runtime.PanicNilError`. Это классический сложный вопрос на BigTech-собеседованиях, полностью отсутствующий в главе при наличии 8 задач на `panic/recover`.

2. **Строгое правило спецификации о вызове `recover()` только непосредственно из `defer`:**  
   Спецификация языка прямо запрещает косвенный вызов: если функция `recover()` вызвана внутри вспомогательной функции, которую вызвал `defer` (например, `defer func() { myHelper() }()`, где внутри `myHelper` вызван `recover()`), она гарантированно вернет `nil` и паника не будет перехвачена. Это тонкое правило спасет часы отладки в production.

3. **Невозможность перехвата фатальных ошибок рантайма и пропуск `defer` при `os.Exit` / `log.Fatal`:**  
   В курсе необходимо наглядно показать на практике, что `defer` **не защищает** от:
   - Вызова `os.Exit()` и `log.Fatal()`;
   - Конкурентной паники внутри чужой горутины (`go func() { panic(...) }()` убивает весь процесс);
   - Фатальных сбоев рантайма: `fatal error: concurrent map writes`, Stack Overflow, Out of Memory.

4. **Эволюция реализации `defer`: Open-Coded Defers (Go 1.14+):**  
   Глава практически везде упоминает только стек `_defer` и выделение структур рантайма. Однако с Go 1.14 компилятор для функций с числом отложенных вызовов $\le 8$ (без циклов) использует открытый код (Open-Coded Defers): отложенные функции встраиваются прямо в точки возврата с битовой маской, снижая накладные расходы на `defer` с 35 нс до $\approx 0.2$ нс.

5. **Директивы инлайнинга компилятора (`//go:noinline`, `//go:inline`):**  
   Инлайнинг функций — ключевая оптимизация компилятора Go. В главе не продемонстрировано, как проанализировать бюджет инлайнинга (`go build -gcflags="-m=2"`) и как директива `//go:noinline` предотвращает встраивание функций при бенчмаркинге и профилировании.

6. **Итераторы функций в Go 1.23+ (`iter.Seq`, `iter.Seq2`):**  
   Начиная с Go 1.23, функции получили статус стандартных генераторов последовательностей через `for x := range mySeq`. Сигнатуры `func(yield func(T) bool)` представляют собой важнейшее расширение функциональных возможностей современного Go.
