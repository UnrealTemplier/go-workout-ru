### 2.1. Упражнение 1: Вымышленный AST-узел компилятора `ONIT` и ложное утверждение об идентичности узлов
- **Раздел / Упражнение:** Упражнение 1, Секция «Под капотом» (`builder/chapter11_data.json`, `under_the_hood`).
- **Фрагмент текста:**
  > «В компиляторе Go `new(T)` и `&T{}` компилируются в идентичные AST-узлы `ONIT` и обрабатываются одинаково аллокатором памяти рантайма (`runtime.newobject`).»
- **В чем проблема:** Двойная фактическая ошибка в описании архитектуры компилятора Go (`cmd/compile`):
  1. **Узла `ONIT` в компиляторе Go не существует и никогда не существовало.** Это полная терминологическая галлюцинация.
  2. В синтаксическом дереве (AST/IR) компилятора Go:
     - `new(T)` транслируется в оператор **`ir.ONEW`** (`/src/cmd/compile/internal/escape/expr.go:148`);
     - `&T{}` транслируется в оператор **`ir.OPTRLIT`** (pointer literal) либо `ir.OADDR` составного литерала (`ir.OSTRUCTLIT`).
  3. Эти конструкции **НЕ являются идентичными AST-узлами**. До этапа SSA и генерации промежуточного представления компилятор обрабатывает их принципиально разными ветками логики (в `ir.OPTRLIT` создается неявная временная переменная, которая инициализируется полями литерала, а затем берется её адрес).
- **Необходимые проверки / источники:** Исходный код компилятора Go: `/src/cmd/compile/internal/ir/node.go`, `/src/cmd/compile/internal/escape/utils.go` (строка 193: `if (n.Op() == ir.ONEW || n.Op() == ir.OPTRLIT)`).

### 2.3. Упражнение 19: Полное невыполнение технического задания задачи + неактуальность бага для Go 1.22+
- **Раздел / Упражнение:** Упражнение 19 (`sources/11. Указатели.md`, `builder/chapter11_data.json`).
- **Фрагмент задачи:**
  > «Продемонстрируйте ошибку захвата адреса переменной цикла `for range`: слайс указателей на элементы среза, все указывают на последний элемент. Исправьте, копируя переменную.»
- **В чем проблема:** Тройное несоответствие технического задания, реализации и рантайма Go:
  1. **Ошибка не продемонстрирована:** В коде решения ошибочный вариант с `&v` вообще не написан. Студенту сразу дан готовый правильный код через взятие адреса по индексу `&numbers[i]`.
  2. **Требование задачи проигнорировано:** Задача требует: *«Исправьте, копируя переменную»* (классический паттерн `val := v; pointers = append(pointers, &val)`). В коде решения переменная не копируется, используется индексная адресация `&numbers[i]`.
  3. **Изменение семантики языка в Go 1.22+:** Начиная с Go 1.22 (RFC `loopvar`), переменные цикла `for range` создаются заново на каждой итерации. Код:
     ```go
     for _, v := range numbers {
         pointers = append(pointers, &v)
     }
     ```
     в современных версиях Go (включая Go 1.22, 1.23, 1.24 и текущую тестовую 1.27) **больше не приводит к тому, что все элементы указывают на последний элемент**! Они получают независимые адреса и выводят `10, 20, 30`. Формулировка задачи описывает поведение старых версий Go (< 1.22) как безусловную истину, без уточнения версии или флагов компиляции.
- **Необходимые проверки / источники:** Запуск `pointers = append(pointers, &v)` на `go1.22+`, Go Release Notes Go 1.22 (Loop variable scoping).

### 2.4. Упражнение 37: Смешение вывода компилятора `-gcflags="-m"` и рантайма `go run` в терминальном блоке
- **Раздел / Упражнение:** Упражнение 37 (`builder/chapter11_data.json`, `dist/011-ukazateli.html`).
- **Фрагмент кода терминала:**
  ```text
  go build -gcflags="-m" main.go
  # ./main.go:6:2: moved to heap: val
  # ./main.go:12:12: ... argument does not escape
  go run main.go
  # Указатель на значение из кучи: 0xc000018030 -> 777
  ```

- **В чем проблема:**
  1. Кодовый блок в `chapter11_data.json` содержит исполняемый Go-код функции `GetLocalPointer()`.

### 2.5. Упражнение 36: Устаревший факт об анализаторе `go vet (loopclosure)` и недетерминированный вывод горутин
- **Раздел / Упражнение:** Упражнение 36 (`builder/chapter11_data.json`, `dist/011-ukazateli.html`).
- **Фрагменты:**
  - Вопрос с собеседования: *«Какой линтер находит гонки данных при захвате переменных цикла? Ответ: Встроенный детектор гонок `go run -race` и анализатор `go vet` (проверка `loopclosure`).»*
  - Терминальный блок:
    ```text
    # Обработан элемент: C
    # Обработан элемент: A
    # Обработан элемент: B
    ```
- **В чем проблема:**
  1. **Устаревшее утверждение о `go vet`:** Проверка `loopclosure` в `go vet` в Go 1.22+ была отключена для кода с версией языка `go >= 1.22`, поскольку переменные цикла теперь создаются per-iteration. `go vet` больше не находит в этом коде ошибок.   2. **Недетерминированный вывод представлен как эталон:** В коде запускаются 3 горутины без синхронизации порядка вывода. Порядок выполнения горутин случаен. Хардкод последовательности `C, A, B` в терминальном блоке вводит учащихся в заблуждение, будто рантайм Go гарантирует именно такой порядок (при нашем тестовом прогоне вывод был `C, B, A`).
- **Необходимые проверки / источники:** `go vet` на цикле с замыканием в Go 1.22+, документация пакета `cmd/vet`.

### 3.3. Упражнение 34: Отсутствие валидации типов и неизбежная паника в рефлексивной мутации
- **Раздел / Упражнение:** Упражнение 34 (`builder/chapter11_data.json`).
- **Фрагмент кода:**
  ```go
  func SetReflect(ptr any, newVal any) {
      val := reflect.ValueOf(ptr)
      if val.Kind() != reflect.Pointer || val.IsNil() {
          return
      }

      elem := val.Elem()
      if elem.CanSet() {
          elem.Set(reflect.ValueOf(newVal))
      }
  }
  ```
- **В чем проблема:**
  1. Функция позиционируется как универсальный механизм изменения значения переменной любого типа через `reflect`.
  2. Однако в коде проверяется только `val.Kind() != reflect.Pointer` и `elem.CanSet()`. Проверка соответствия типа `newVal` типу целевого элемента `elem` полностью отсутствует!
  3. Если вызвать `SetReflect(&count, int64(99))` (где `count` имеет тип `int`), произойдет фатальная неперехваченная паника:
     `panic: reflect.Set: value of type int64 is not assignable to type int`.
  4. Обучающий код должен демонстрировать безопасную работу с рефлексией через `reflect.ValueOf(newVal).Type().AssignableTo(elem.Type())`.
- **Необходимые проверки / источники:** Документация пакета `reflect`, метод `Value.Set`.

### 3.5. Массовый хардкод адресов памяти `%p` в 13+ упражнениях главы

## 💡 4. Кандидаты с низким приоритетом (Low Priority)

### 4.1. Упражнение 10: Формулировка задачи содержит синтаксически невалидную конструкцию `&int{}`
- **Раздел / Упражнение:** Упражнение 10 (`sources/11. Указатели.md`, `builder/chapter11_data.json`).
- **Фрагмент задачи:** *«Создайте переменные через `new(int)` и `&int{}` (для структур `&Person{}`), объясните разницу.»*
- **В чем проблема:** Запись `&int{}` в Go является синтаксической ошибкой компиляции (`invalid composite literal type int`). Составные литералы `&T{...}` применимы только к структурам, массивам, срезам и мапам. Для примитивных типов взятие адреса от литерала запрещено. В коде решения автор правильно написал `new(int)` и `&Person{}`, но упоминание `&int{}` в условии дезориентирует новичков.

### 4.2. Упражнение 12: Чрезмерно упрощенная ассемблерная модель в Under the Hood
- **Раздел / Упражнение:** Упражнение 12 (`under_the_hood`).
- **Фрагмент текста:** *«Двойное разыменование компилируется в две инструкции косвенной адресации `MOVQ (AX), BX; MOVQ (BX), CX`»*.
- **В чем проблема:** Функция `Allocate(pp **int, val int)` выполняет выделение памяти в куче: `*pp = new(int); **pp = val`. Дизассемблирование через `go tool compile -S` показывает, что здесь генерируется вызов аллокатора `runtime.mallocgcTinySC2`, проверка барьера записи GC (`CMPL runtime.writeBarrier`) и вызов `runtime.gcWriteBarrier2`. Описание этого сложного рантайм-процесса как двух тривиальных инструкций `MOVQ` сильно искажает реальную работу сборщика мусора и аллокатора при мутации указателей.

### 4.3. Упражнение 8: Устаревший тип `SliceHeader` в секции Under the Hood
- **Раздел / Упражнение:** Упражнение 8 (`under_the_hood`).
- **Фрагмент текста:** *«Изменяется только поле Len в структуре SliceHeader, память кучи не освобождается...»*.
- **В чем проблема:** Начиная с Go 1.20 тип `reflect.SliceHeader` официально объявлен устаревшим (deprecated) из-за проблем с безопасностью указателей при сборке мусора. В современных материалах уровня Middle+/Senior рекомендуется использовать термин «внутреннее представление среза (runtime slice struct)» или `unsafe.Slice`.

### 4.4. Упражнение 38: Неидиоматичный неологизм `Zeroify`
- **Раздел / Упражнение:** Упражнение 38 (`builder/chapter11_data.json`).
- **В чем проблема:** Именование функции `Zeroify(val *int)` не соответствует идиомам стандартной библиотеки Go. Общепринятые идиоматичные названия для сброса значения по указателю в Go — `Reset(val *int)` или `Clear(val *int)`.

## 🔍 5. Важные пробелы и упущения (Omissions)

Для курса, ориентированного на позиции Middle/Senior/Lead Go Developer в ведущих технологических компаниях, в главе об указателях критически не хватает следующих фундаментальных тем:

1. **Атомарные операции с указателями: `sync/atomic.Pointer[T]` (Go 1.19+):**
   - Указатели в конкурентном коде подвержены состояниям гонки (Data Race) и частичной записи адреса.
   - В Go 1.19 появился типобезопасный дженерик-контейнер `atomic.Pointer[T]`, ставший стандартом для lock-free обновления конфигураций и кэшей без мьютексов. В главе об этом нет упоминания.
2. **Основы пакета `unsafe` и граница между `unsafe.Pointer` и `uintptr`:**
   - В главе используется только `unsafe.Sizeof`. Однако ключевой вопрос любого Senior-собеседования по указателям — почему `uintptr` не защищает объект от сборщика мусора, и почему преобразование `uintptr(p)` нельзя сохранять в промежуточную переменную перед обратным кастом в `unsafe.Pointer`.
3. **Влияние указателей на сборщик мусора (Pointer bitmaps / `noscan` spans):**
   - В HighLoad-системах указатели — главный источник оверхеда на фазе маркировки GC (Mark Phase). Объекты без указателей аллоцируются в span-классах `noscan` и пропускаются сборщиком мусора. Это фундаментальная причина отказа от указателей в горячих путях обработки данных.
4. **Указатели на пустые структуры `struct{}` и поведение `runtime.zerobase`:**
   - Вопрос BigTech в упр. 30 упоминает `zerobase`, но практического упражнения нет. Поведение `a := struct{}{}; b := struct{}{}; fmt.Println(&a == &b)` наглядно иллюстрирует разницу между стеком и кучей в рантайме Go.
5. **Влияние инлайнинга функций (Compiler Inlining) на escape-анализ:**
   - Побег переменной в кучу зависит от инлайнинга. Если функция `NewObject()` заинлайнена компилятором в вызывающий контекст, переменная может остаться на стеке, даже если из функции возвращался указатель. Без директивы `//go:noinline` демонстрация escape-анализа неполна.
