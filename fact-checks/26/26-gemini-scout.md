### G-02. Паника рантайма `adding nil Certificate to CertPool` и сфабрикованный вывод в триплете задач mTLS (099, 127, 143)
- **Где:** 
  - `sources/026. HTTP-сервер, REST API и Middleware/03. Продвинутые сетевые протоколы/099. Mutual TLS (mTLS).md` → «## Код решения», `main.go` (строки 42–54)
  - `sources/026. HTTP-сервер, REST API и Middleware/04. Архитектура HighLoad/127. Mutual TLS (mTLS) с жестким требованием.md` → «## Код решения», `main.go` (строки 35–41)
  - `sources/026. HTTP-сервер, REST API и Middleware/04. Архитектура HighLoad/143. Mutual TLS (mTLS) в Zero-Trust архитектурах.md` → «## Код решения», `mtls_zero_trust.go` (строки 34–40)
- **Цитата:** 
  ```go
  server := httptest.NewUnstartedServer(...)
  serverCert := server.Certificate()
  caPool := x509.NewCertPool()
  caPool.AddCert(serverCert)
  ```
- **Утверждение:** Программы демонстрируют эталонную настройку mTLS-сервера и клиента, завершаясь выводом `[mTLS Handshake Success] Статус: 200` или `Zero-Trust mTLS Handshake Passed`.
- **Почему проверить:** Все три задачи представляют собой дословные копии одной и той же фатальной ошибки:
  1. Сервер создается через `httptest.NewUnstartedServer()`. До вызова `server.StartTLS()` поле `server.TLS` не инициализировано сертификатом, и метод `server.Certificate()` возвращает **`nil`**.
  2. Стандартный метод Go `caPool.AddCert(cert *x509.Certificate)` в `crypto/x509/cert_pool.go` содержит жесткую проверку: `if cert == nil { panic("adding nil Certificate to CertPool") }`.
  3. В результате все три программы аварийно завершаются на старте паникой `panic: adding nil Certificate to CertPool`.
  4. При этом в блоках терминала всех трех задач приведен фиктивный успешный вывод HTTP 200, который в реальности никогда не мог быть получен.
- **Что проверить и где:** Запуск кода любой из задач 099, 127, 143; исходники `crypto/x509/cert_pool.go` (строка 186) и `net/http/httptest/server.go`.
- **Тип:** код / вывод
- **Приоритет:** High

### G-03. Паника разыменования nil-указателя (`SIGSEGV`) и сфабрикованный терминальный вывод в задаче 148 (Hijacking)
- **Где:** `sources/026. HTTP-сервер, REST API и Middleware/04. Архитектура HighLoad/148. Низкоуровневый Hijacking TCP-соединения.md` → «## Код решения», `main.go` (строки 48–60)
- **Цитата:** 
  ```go
  // Сервер:
  _, _ = bufrw.WriteString("RAW_PROTOCOL_V1\n")
  // Клиент:
  resp, _ := http.Get(server.URL)
  defer resp.Body.Close()
  ```
- **Утверждение:** Клиент через `http.Get` считывает сырые данные перехваченного TCP-соединения: `[Client Read]: RAW_PROTOCOL_V1`.
- **Почему проверить:** 
  1. Сервер после вызова `Hijack()` начинает сразу писать в сокет сырые байты бинарного/текстового протокола `"RAW_PROTOCOL_V1\n"` без предварительной отправки валидного HTTP-статуса (`HTTP/1.1 200 OK\r\n\r\n`).
  2. Клиентский метод `http.Get` ожидает валидный HTTP-ответ. Получив `"RAW_PROTOCOL_V1\n"`, HTTP-парсер возвращает ошибку `malformed HTTP response "RAW_PROTOCOL_V1\\n"`, а переменная `resp` остается равной **`nil`**.
  3. Поскольку код решения игнорирует проверку ошибки и сразу выполняет `defer resp.Body.Close()`, программа падает с паникой и ошибкой сегментации: `panic: runtime error: invalid memory address or nil pointer dereference [signal SIGSEGV: segmentation violation]`.
  4. Терминальный вывод `[Client Read]: RAW_PROTOCOL_V1` сфабрикован.
- **Что проверить и где:** Запуск `go run main.go` в задаче 148.
- **Тип:** код / вывод
- **Приоритет:** High

### G-06. Псевдо-RateLimiter без пополнения токенов (задача 072) и утечка памяти по IP-адресам (задача 041)
- **Где:** 
  - `sources/026. HTTP-сервер, REST API и Middleware/02. Защита сервисов/072. Rate Limiter Middleware.md` → «## Код решения», `main.go` (строки 35–55)
  - `sources/026. HTTP-сервер, REST API и Middleware/02. Защита сервисов/041. IP-based Rate Limiter Middleware на алгоритме.md` → «## Код решения», `main.go` (строки 72–90)
- **Цитата:** 
  - Задача 072: `func (l *SimpleLimiter) Allow() bool { for { cur := l.available.Load(); if cur <= 0 { return false }; if l.available.CompareAndSwap(cur, cur-1) { return true } } }`
  - Задача 041: `type IPRateLimiter struct { mu sync.RWMutex; clients map[string]*TokenBucket }`
- **Утверждение:** Задача 072 реализует алгоритм Token Bucket для ограничения 10 rps. Задача 041 реализует промышленный IP Rate Limiter.
- **Почему проверить:** 
  1. В задаче 072 структура `SimpleLimiter` инициализирует счетчик значением `burst` (в тесте 2) и умеет только **декрементировать** его. В коде вообще отсутствует пополнение токенов по времени (rate refill)! Это не Rate Limiter, а одноразовый квотер: после первых 2 запросов сервер навсегда блокирует абсолютно все последующие запросы ошибкой 429. При этом условие требовало использовать пакет `golang.org/x/time/rate`.
  2. В задаче 041 структура `IPRateLimiter` складывает лимитеры всех приходящих IP-клиентов в мапу `clients map[string]*TokenBucket`, из которой записи **никогда не удаляются**. При открытом доступе в интернет любой сканер IP-адресов быстро вызовет неограниченный рост памяти процесса (Memory Leak / DoS).
- **Что проверить и где:** Проанализировать код метода `Allow()` в задаче 072 и отсутствие фоновой очистки мапы в задаче 041.
- **Тип:** код / логика
- **Приоритет:** High

### G-08. Состояние гонки (Data Race) в Heartbeat-мониторе WebSocket (задача 102)
- **Где:** `sources/026. HTTP-сервер, REST API и Middleware/03. Продвинутые сетевые протоколы/102. Heartbeat механизм в WebSocket.md` → «## Код решения», `ws_heartbeat.go` (строки 38–67)
- **Цитата:** 
  ```go
  type HeartbeatMonitor struct {
      lastPong time.Time
  }
  // В горутине Start:
  if time.Since(m.lastPong) > timeout { ... }
  // В методе HandlePong:
  m.lastPong = time.Now()
  ```
- **Утверждение:** Код реализует потокобезопасный механизм контроля активности соединения через Ping/Pong.
- **Почему проверить:** 
  1. Поле `m.lastPong` имеет тип `time.Time` (структура из трех полей).
  2. Горутина таймера в методе `Start()` регулярно производит чтение `m.lastPong` без блокировки мьютекса или атомиков.
  3. Метод `HandlePong()` из другой горутины производит запись `m.lastPong = time.Now()`.
  4. Детектор гонок Go (`go run -race`) фиксирует состояние гонки: `WARNING: DATA RACE Write at ... by main goroutine: Previous write at ... by goroutine 8`. Чтение неатомарной структуры `time.Time` в момент записи может приводить к разорванным чтениям времени (torn read).
- **Что проверить и где:** Запуск `go run -race sources/026.../102...md`.
- **Тип:** код
- **Приоритет:** Medium

### G-11. Дефект шторма запросов в состоянии HalfOpen у Circuit Breaker (задача 133)
- **Где:** `sources/026. HTTP-сервер, REST API и Middleware/04. Архитектура HighLoad/133. Реализация паттерна Circuit Breaker.md` → «## Код решения», `circuit_breaker.go` (строки 66–75)

### G-12. Потеря тела запроса при ретраях без `GetBody` и блокирующий `time.Sleep` (задача 155)
- **Где:** `sources/026. HTTP-сервер, REST API и Middleware/04. Архитектура HighLoad/155. Умная клиентская обертка с повторными попытками.md` → «## Код решения», `main.go` (строки 47–71)

- **Утверждение:** Универсальная обертка над HTTP-клиентом для повтора запросов при сетевых ошибках и 5xx статусах.

### G-14. Уязвимость Path Traversal и утечка временных файлов при загрузке multipart (задача 034)
- **Где:** `sources/026. HTTP-сервер, REST API и Middleware/01. Основы HTTP-сервера, маршрутизация Go 1.22/034. Прием и сохранение файлов.md` → «## Код решения», `main.go` (строки 46–68)

- **Утверждение:** Безопасный промышленный обработчик загрузки файлов с сохранением на диск.

- **Что проверить и где:** Спецификация `http.Request.ParseMultipartForm`; эксплуатация `filepath.Join` с `../`.

## 4. Упущения главы

1. **Защита от переполнения памяти через `http.MaxBytesReader`:**
   В главе о REST API и микросервисах ни в одной задаче не продемонстрирован критический производственный паттерн ограничения размера тела запроса (`r.Body = http.MaxBytesReader(w, r.Body, maxBytes)`). Все задачи парсинга JSON читают `r.Body` без лимитов, подвергая сервис риску OOM при атаках.
2. **Современный механизм обратного прокси `httputil.ReverseProxy.Rewrite` (Go 1.20+):**
   В Go 1.20 стандартная библиотека представила хук `Rewrite`, призванный заменить устаревший и подверженный уязвимостям с заголовками `Director`. В главе 26 все задачи проксирования и балансировки (053, 115, 140, 147) используют устаревший `Director`.
3. **Разворачивание оберток ResponseWriter через `http.ResponseController` (Go 1.20+):**
   При написании кастомных `ResponseWriter` (для захвата статус-кода и размера в задачах 030, 045) обертка скрывает интерфейсы `http.Flusher` и `http.Hijacker`. Начиная с Go 1.20 для решения этой проблемы стандартизирован метод `Unwrap() http.ResponseWriter` и тип `http.ResponseController`. В главе этот фундаментальный механизм полностью упущен.
4. **Тюнинг серверных таймаутов `ReadHeaderTimeout` против Slowloris:**
   Стандартный линтер `gosec` ругается на создание `http.Server` без `ReadHeaderTimeout`. Установка `ReadTimeout` блокирует долгие стримы (SSE и WebSockets), поэтому в реальных HighLoad-сервисах настраивают именно `ReadHeaderTimeout`. В главе этому не уделено должного внимания.
5. **Cleartext HTTP/2 (`h2c`) на реальных библиотеках:**
   Внутреннее межсервисное взаимодействие в Kubernetes по h2c — важнейшая тема для Senior-разработчиков, однако в задаче 151 она заявлена и не раскрыта.
