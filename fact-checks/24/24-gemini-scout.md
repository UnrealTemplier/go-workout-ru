### G-03. Падение `net.LookupPort("udp", "dns")` на Linux и сфабрикованный терминальный вывод
- **Где:** `024. Низкоуровневая сеть (TCP и UDP)/02. Промышленные сетевые протоколы/060. Преобразование сетевых имен сервисов в номера.md` → ## Код решения (`main.go`, строки 31–43) и ## Терминал (строка 57)
- **Цитата:** В коде: `services := []string{"http", "https", "ssh", "smtp", "dns"}`. В терминале: `-> Сервис dns    (udp) = Порт 53`.
- **Утверждение:** Код преобразует имя сервиса `"dns"` для сети `"udp"` в порт 53 и выводит его в терминал.
- **Почему проверить:** В базе данных сервисов IANA (`/etc/services` на Linux/macOS) порт 53 зарегистрирован под служебным именем `domain`, а не `dns` (`domain 53/tcp`, `domain 53/udp`). - **Что проверить и где:** Запуск кода на Linux/macOS; проверка файла `/etc/services` (`grep -E "\b53/(tcp|udp)" /etc/services`); документация функции `net.LookupPort`.

### G-07. Антипаттерн блокирующего сетевого вывода `conn.Write` под глобальным `sync.Mutex` в чатах
- **Где:** 
  - `sources/024. Низкоуровневая сеть (TCP и UDP)/01. Фундамент сетевых сокетов/015. Многопользовательский TCP-чат с броадкастом.md` (строки 42–54)
  - `01. Фундамент сетевых сокетов/017. Потокобезопасный TCP-чат с рассылкой сообщений.md` (строки 42–54)
  - `01. Фундамент сетевых сокетов/032. Сетевой широковещательный чат.md` (строки 38–47)
- **Цитата:** 
  ```go
  func (s *ChatServer) Broadcast(sender net.Conn, msg string) {
  	s.mu.Lock()
  	defer s.mu.Unlock()
  	for conn := range s.clients {
  		if conn != sender {
  			_, _ = conn.Write([]byte(formatted))
  		}
  	}
  }
  ```
- **Утверждение:** Решения позиционируются как канонические и потокобезопасные TCP чат-серверы.
- **Почему проверить:** Вызов `conn.Write()` является потенциально блокирующей сетевой операцией (заполненный сокетный буфер ОС, медленный или зависший клиент). Выполнение `conn.Write()` внутри критической секции под `s.mu.Lock()` приводит к тому, что один медленный клиент намертво замораживает весь сервер: ни один другой клиент не может отправить сообщение, подключиться или отключиться. В задаче 015 в «Подводных камнях» прямо указано, что это критический антипаттерн, но в самом коде решений 015, 017 и 032 написан именно он.
- **Что проверить и где:** Листинги `Broadcast` в задачах 015, 017, 032; паттерн Actor/Channel hub с per-client буферизованными каналами (как в задаче 049).
- **Тип:** код / педагогика
- **Приоритет:** High

### G-08. Инвертированное объяснение влияния `TCP_NODELAY` и умалчивание о дефолте в Go
- **Где:** `024. Низкоуровневая сеть (TCP и UDP)/02. Промышленные сетевые протоколы/041. Настройка низкоуровневых параметров TCP Keep-Alive.md` → ## Подводные камни (строка 95) и ## Код решения (строка 41)
- **Цитата:** «Отключение TCP_NODELAY при отправке миллионов однобайтовых пакетов увеличит накладные расходы на сетевые заголовки (40 байт заголовка на 1 байт данных).»
- **Утверждение:** Автор утверждает, что *отключение* `TCP_NODELAY` увеличивает накладные расходы на заголовки при частой мелкой отправке, и вызывает `_ = tcpConn.SetNoDelay(true)`.
- **Почему проверить:** 
  1. Утверждение вывернуто наизнанку: алгоритм Нагла как раз предотвращает отправку 40-байтных заголовков на 1 байт данных, буферизуя мелкие порции. Соответственно, именно *отключение* алгоритма Нагла (т.е. установка `TCP_NODELAY = true`) приводит к шквалу мелких пакетов с огромными накладными расходами.
  2. В стандартной библиотеке Go для всех TCP-сокетов (`net.Dial`, `net.Listen`) флаг `NoDelay` по умолчанию **уже равен `true`** (`go doc net.TCPConn.SetNoDelay`: *"The default is true (no delay)"*). Вызов `tcpConn.SetNoDelay(true)` является чистым no-op.
- **Что проверить и где:** `go doc net.TCPConn.SetNoDelay`; RFC 896 (Nagle's Algorithm); исходники Go `src/net/tcpsock.go`.
- **Тип:** факт / код
- **Приоритет:** Medium

### G-10. Путаница между прикладным HTTP-заголовком `Host` и TLS-расширением SNI
- **Где:** `024. Низкоуровневая сеть (TCP и UDP)/01. Фундамент сетевых сокетов/004. Сырой низкоуровневый TCP HTTP-клиент с ручным.md` → ## На собеседовании, строка 124
- **Цитата:** «Вопрос с собеседования: "Зачем в HTTP/1.1 обязателен заголовок Host..." Ответ: Для Virtual Hosting (SNI): на одном физическом IP-адресе и порту 80/443...»
- **Утверждение:** Ответ объединяет понятия Virtual Hosting по HTTP-заголовку `Host` и TLS SNI.
- **Почему проверить:** Это разные механизмы разных уровней стека. HTTP-заголовок `Host` (RFC 7230/9112) передается на прикладном уровне (L7) внутри HTTP-запроса (в открытом виде или внутри установленного TLS-туннеля). SNI (Server Name Indication, RFC 6066) — расширение протокола TLS криптографического/сессионного уровня (L5/L6), передаваемое в `ClientHello` *до* расшифровки трафика для выбора X.509-сертификата. На порту 80 (чистый HTTP, о котором идёт речь в задаче) никакого SNI нет.
- **Что проверить и где:** RFC 6066 §3 (Server Name Indication); RFC 9112 §7.2 (Host).
- **Тип:** факт / педагогика
- **Приоритет:** Medium

### G-12. Искусственное усечение сетевых ошибок `*net.OpError` в эталонных терминальных блоках

- **Что проверить и где:** Запуск кода задач 025 и 034; метод `Error()` структуры `net.OpError`.

- **Приоритет:** Medium

### G-13. Лишний перевод строки в выводе и платформа-зависимый `exec.Command("echo")` на Windows

- **Цитата:** Код: `cmd.CombinedOutput() ... conn.Write(output); conn.Write([]byte("\n---END---\n"))`. Терминал: только `[Command Result] Hello_From_Agent`.
- **Утверждение:** В терминале ожидается одна строка ответа.
- **Почему проверить:**
  1. Команда `echo` в Linux уже завершает вывод символом `\n`. Запись `\n---END---\n` добавляет дополнительный пустой кадр перед маркером конца. Клиент считывает его и печатает пустую строку: `[Command Result] \n`. Терминальный вывод учебника не совпадает с реальным запуском.
  2. В ОС Windows утилита `echo` не является исполняемым файлом (это встроенная команда `cmd.exe`). Вызов `exec.Command("echo", ...)` на Windows аварийно завершится с ошибкой `exec: "echo": executable file not found in %PATH%`.
- **Что проверить и где:** Запуск кода задачи 038 на Linux и Windows.
- **Тип:** вывод / код
- **Приоритет:** Medium

## 4. Упущения главы

Материал главы ориентирован на бэкенд-разработчиков уровня Middle/Senior, однако в ней полностью отсутствуют ключевые промышленные концепции низкоуровневой сети в Go:

1. **Современный пакет `net/netip` (Go 1.18+):**
   - Полное отсутствие практических задач на `netip.Addr`, `netip.AddrPort`, `netip.Prefix`. В промышленном коде `net.IP` признан устаревшим из-за постоянных аллокаций в куче и мутабельности. Вся глава 24 построена на устаревшем `net.IP`.
2. **Низкоуровневая настройка сокетов до `bind`/`listen` через `net.ListenConfig` и `Control` (`syscall.RawConn`):**
   - Опции сокетов, которые критически важно выставлять *до* привязки порта (`SO_REUSEPORT` для балансировки соединений между процессами ядра, `SO_REUSEADDR`, `TCP_DEFER_ACCEPT`, `SO_BINDTODEVICE`), вообще не рассмотрены. В главе показан лишь поздний тюнинг уже принятых соединений (`*net.TCPConn`).
3. **Unix Domain Sockets (IPC):**
   - В главе полностью отсутствуют сокеты `net.Listen("unix", ...)` и `net.Dial("unix", ...)`, являющиеся стандартом высокопроизводительного локального взаимодействия микросервисов, sidecar-контейнеров (Envoy, Service Mesh, Docker daemon, Kubelet).
4. **Zero-Copy передача данных (`splice`, `sendfile`):**
   - Не раскрыта механика оптимизации передачи данных в рантайме Go: когда и при каких условиях `io.Copy` использует системный вызов `splice(2)` между сокетами TCP или `sendfile(2)` из файла в сокет без копирования в пространство пользователя.
5. **Архитектура надёжного Broadcast/Fan-Out с изоляцией медленных клиентов (Slow Consumers):**
   - Вместо опасного блокирующего цикла под мьютексом не показана промышленная модель с очередями отправки, детекцией переполнения буфера сокета и принудительным отключением зависших пиров.
