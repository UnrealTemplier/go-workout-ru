### 2.1. Упражнение 60: Фактическая ошибка — тестовая зависимость якобы помечается как `// indirect`
- **Раздел / Упражнение:** Упражнение 60, Секция 4 (`builder/section4.py`).
- **Фрагмент задачи / кода:**
  > «Создай модуль, добавь зависимость github.com/stretchr/testify (только для тестов). **Убедись, что она попадает в go.mod с директивой // indirect.** Затем напиши тест с assert.Equal и запусти go test.»
- **В чем проблема:** Это грубая фактическая ошибка относительно того, как работает тулчейн Go Modules. Любой пакет, напрямую импортируемый в любом исходном файле модуля — включая тестовые файлы `*_test.go` (например, `calc_test.go`), — считается **прямой зависимостью (direct dependency)** текущего модуля. При запуске `go mod tidy` в `go.mod` генерируется запись:
  ```text
  require github.com/stretchr/testify v1.10.0
  ```
  без какого-либо комментария `// indirect`! Директивой `// indirect` помечаются только транзитивные зависимости (косвенные подбиблиотеки, такие как `yaml.v3`, `davecgh/go-spew`, `pmezard/go-difflib`). Студент физически не сможет выполнить требование задачи «убедись, что она попадает с директивой // indirect».
- **Необходимые проверки / источники:** Спецификация Go Modules Reference, раздел *"Direct and indirect requirements"*. Простой тест: инициализировать модуль, создать `main_test.go` с импортом `github.com/stretchr/testify/assert`, выполнить `go mod tidy` и проверить `go.mod`.

### 2.2. Упражнение 49: Ложная модель работы `go mod tidy` при неиспользуемом импорте
- **Раздел / Упражнение:** Упражнение 49, Секция 4 (`builder/section4.py`).
- **Фрагмент задачи / кода:**
  > Задача: «Очистка зависимостей: **Удалите из кода main.go использование библиотеки uuid, но оставьте её в импортах. Выполните команду go mod tidy.** Посмотрите, как изменились файлы go.mod и go.sum.»  
  > Теория: «Команда go mod tidy анализирует AST-дерево. Если импорт не используется ни в одном файле пакета (или если удалить саму строку импорта), go mod tidy полностью удалит запись require github.com/google/uuid...»
- **В чем проблема:** Полноценный разрыв между поведением Go и формулировкой задачи. `go mod tidy` сканирует AST на уровне деклараций импортов (`import "..."`), но **НЕ производит проверку используемости символов внутри тел функций** (typechecking). Если оставить строку `import "github.com/google/uuid"`, то:
  1. `go mod tidy` считает библиотеку нужной, **НЕ удаляет** её из `go.mod` и `go.sum`, а наоборот, скачивает и закрепляет.
  2. Сборка `go build` упадет с ошибкой компилятора: `imported and not used: "github.com/google/uuid"`.
  При этом в коде решения авторы сами удалили строку импорта (`// "github.com/google/uuid" — удален за ненадобностью`), что прямо противоречит формулировке задачи («но оставьте её в импортах»).
- **Необходимые проверки / источники:** Запуск `go mod tidy` на файле с объявленным, но не вызываемым `import "github.com/google/uuid"`.

### 2.3. Упражнение 40: Невозможность сборки бинарника из `package api` через `go build`
- **Раздел / Упражнение:** Упражнение 40, Секция 3 (`builder/section3.py`).
- **Фрагмент задачи / кода:**
  > Текст задачи в `sources/1. Пакеты и модули.md`:  
  > «Создай модуль mymod **с пакетом api. Сделай go build для получения исполняемого файла.** Затем сделай go install. Найди, куда установился бинарник (GOBIN, GOPATH).»
- **В чем проблема:** Фундаментальное правило компилятора Go: команда `go build` создает исполняемый бинарник **только и исключительно для пакетов `package main`** с точкой входа `func main()`. Для библиотечного пакета `package api` команда `go build` компилирует исходники во временную память для проверки типов, но **не создает никакого исполняемого файла на диске**! Команда `go install` для `package api` кэширует скомпилированный объектный архив в `GOCACHE`, но не помещает ничего в `$GOBIN`.  
  В `builder/section3.py` авторы были вынуждены тихо подменить условие задачи («1. Создаем модуль mymod с package main»), а в Pitfalls написать: «Запуск go install в папке библиотеки (где объявлен package api, а не package main) не создаст бинарник в $GOBIN». Задача в исходном опроснике ставит невыполнимое требование.
- **Необходимые проверки / источники:** `go help build`, `go help install`. Спецификация языка Go: Program execution, package main.

### 2.4. Упражнение 83: Переопределение шортката `-h` в `pflag` ломает вызов встроенной справки `--help`
- **Раздел / Упражнение:** Упражнение 83, Секция 6 (`builder/section6.py`).
- **Фрагмент задачи / кода:**
  ```go
  pflag.StringVarP(&host, "host", "h", "127.0.0.1", "Хост сервера")
  ```
- **В чем проблема:** В библиотеке `pflag` однобуквенный флаг `-h` по умолчанию жестко ассоциирован со встроенным флагом справки `--help`. При ручной регистрации строкового флага с шорткатом `"h"` флаг справки перезаписывается. При попытке пользователя вызвать справку стандартным способом:
  ```bash
  go run . -h
  ```
  программа аварийно падает:
  ```text
  flag needs an argument: 'h' in -h
  exit status 2
  ```
  Иронично, что в этом же самом упражнении в блоке Pitfalls автор пишет: «Коллизия однобуквенных флагов: назначение одной и той же буквы -h для двух разных флагов вызовет панику при регистрации». Автор предупреждает о коллизии `-h`, но сам назначает букву `'h'` параметру `host`, ломая вызов справки.
- **Необходимые проверки / источники:** Запуск `go run . -h` с кодом упражнения 83; документация `spf13/pflag` по обработке флага справки `help`.

### 3.1. Упражнение 9: Неверная ментальная модель работы Unicode — разворот по `[]rune` ломает составные эмодзи и диакритические знаки
- **Раздел / Упражнение:** Упражнение 9, Секция 1 (`builder/section1.py`).
- **Фрагмент задачи / кода:**
  > «Приведение `[]rune(s)` выполняет декодирование UTF-8 байтов в рантайме Go ... Это гарантирует корректную работу с любыми Unicode-символами и эмодзи.»
- **В чем проблема:** Это распространенное, но технически неверное заблуждение. `rune` в Go представляет один кодовый пункт Unicode (Code Point, `int32`). Однако сложные символы в человеческих языках и эмодзи состоят из нескольких рун (Extended Grapheme Clusters):
  - Буква с диакритикой `é` (U+0065 + U+0301). При развороте по рунам акцент оторвется от `e` и упадет на предыдущую букву.
  - Эмодзи с тоном кожи: 👍🏽 (U+1F44D + U+1F3FD). При развороте модификатор цвета окажется впереди жеста, ломая рендеринг.
  - Флаги стран: 🇷🇺 (два Regional Indicator символа). При развороте превращаются в зеркальный флаг 🇺🇷.
  - Семьи / составные эмодзи: 👨‍👩‍👧‍👦 (последовательность рун через ZWJ U+200D).
  Утверждение, что `[]rune` «гарантирует корректную работу с любыми эмодзи», учит студентов ошибочной концепции. Для правильной работы с графемами необходимы библиотеки нормализации (например, `golang.org/x/text/unicode/norm` или `rivo/uniseg`).
- **Необходимые проверки / источники:** Unicode Standard Annex #29 (Unicode Text Segmentation); тест `Reverse("👍🏽")`.

### 3.2. Упражнение 62: Неполнота директив `go.mod` — упущены `retract`, `toolchain` и `tool`
- **Раздел / Упражнение:** Упражнение 62, Секция 5 (`builder/section5.py`).
- **Фрагмент задачи / кода:**
  > «В файле go.mod поддерживаются ровно 5 ключевых директив: 1. module, 2. go, 3. require, 4. replace, 5. exclude.»
- **В чем проблема:** Утверждение «ровно 5 директив» устарело и является неполным:
  1. `retract` (появилась в Go 1.16) — официальный механизм отзыва ошибочных или критически уязвимых версий модуля автором.
  2. `toolchain` (появилась в Go 1.21) — механизм автоматического переключения версии компилятора Go в зависимости от требований модуля.
  3. `tool` (появилась в Go 1.24) — директива для декларативного управления исполняемыми инструментами разработки (линтеры, генераторы кодов).
  Для учебника уровня Senior/Staff игнорирование `retract` и `toolchain` является существенным упущением.
- **Необходимые проверки / источники:** Go Modules Reference: `retract`, `toolchain`, `tool` directives.

### 3.3. Упражнения 26 и 42: Недостоверные утверждения о гарантиях порядка `init()` и работе планировщика
- **Раздел / Упражнение:** Упражнения 26, 42, Секции 2 и 3 (`builder/section2.py`, `builder/section3.py`).
- **Фрагмент задачи / кода:**
  > «Файлы внутри одного пакета компилируются и инициализируются в лексикографическом (алфавитном) порядке имен файлов!»  
  > В интервью: «Рантайм выполняет их строго в одном основном потоке ОС до запуска планировщика для пользовательского кода. Однако горутина не начнет реально исполняться, пока текущий поток инициализации не передаст управление или не завершится инициализация пакета.»
- **В чем проблема:**
  1. Спецификация языка Go (Go Language Specification, §Package initialization) **НЕ гарантирует** лексикографический порядок как языковую инварианту:
     > «To ensure reproducible initialization behavior, build systems are encouraged to present multiple files belonging to the same package in lexical file name order to a compiler.»  
     Это рекомендация сборочной системе, а не закон спецификации. Если передать компилятору файлы вручную (`go run b.go a.go`), `b.go` выполнится раньше `a.go`. Завязываться на алфавитный порядок файлов в архитектуре — архитектурный антипаттерн.
  2. Планировщик Go **УЖЕ запущен** во время вызова `init()`, поскольку функция `runtime.main` сама исполняется как горутина. Если внутри `init()` запустить `go func()` и заблокироваться на чтении из канала, запущенная горутина немедленно подхватывается другим системным потоком планировщика (M) и отрабатывает в параллели, разблокируя `init()`.
- **Необходимые проверки / источники:** The Go Programming Language Specification: Package initialization; исходный код рантайма `src/runtime/proc.go`.

### 3.4. Упражнение 86: Прямое противоречие между кодом бенчмарка и предостережением о Dead Code Elimination
- **Раздел / Упражнение:** Упражнение 86, Секция 6 (`builder/section6.py`).
- **Фрагмент задачи / кода:**
  > Код бенчмарка:
  > ```go

  > Блок Pitfalls: «Компилятор может вырезать вызов функции внутри бенчмарка через Dead Code Elimination, если результат никуда не сохраняется. Принято присваивать результат глобальной переменной пакета.»

Однако в коде собственного решения автор сам пишет `_ = ConcatPlus(...)` и `_ = ConcatBuilder(...)`! Каноничный паттерн: `var resultSink string` на уровне пакета и `resultSink = ConcatBuilder(...)` внутри цикла.
- **Необходимые проверки / источники:** Go standard library benchmarks (`bytes_test.go`, `strings_test.go`).

### 3.5. Упражнение 66: Задача требует воспроизвести уязвимость в `govulncheck`, а решение показывает пустой отчет

  > Задача: «Создай модуль с уязвимой зависимостью. Запусти govulncheck (или go list -m -json all | nancy sleuth). Проанализируй результат.»  
  > Решение: в терминале выводится «No vulnerabilities found. Your code is safe!».
- **В чем проблема:** Упражнение не доведено до конца. Студент не видит главного: как именно выглядит реальный отчет `govulncheck` (вывод уязвимости `GO-202X-XXXX`, трассировка стека вызовов до уязвимой функции, разница между вызываемым кодом и неиспользуемой уязвимой библиотекой).
- **Необходимые проверки / источники:** Добавление тестовой уязвимой зависимости (например, `golang.org/x/crypto v0.0.0-20201221181555-eec23a3978ad` с известным CVE) и демонстрация реального отчета.

### 3.6. Упражнение 36: Неработоспособный локальный пример с двумя мажорными версиями `v1` и `v2`
- **Раздел / Упражнение:** Упражнение 36, Секция 3 (`builder/section3.py`).
- **Фрагмент задачи / кода:**
  > В `app/main.go`:
  > ```go
  > import (
  >     mathv1 "example.com/mathlib"
  >     mathv2 "example.com/mathlib/v2"
  > )
  > ```
- **В чем проблема:** Модули с доменными путями `example.com/mathlib` не существуют на удаленном сервере. Чтобы этот код скомпилировался локально, в `app/go.mod` необходимы директивы `replace` для обеих версий, либо использование `go.work`. Ни манифеста `go.mod`, ни инструкций по локальной связке авторы не предоставили. Студент при копировании кода получит ошибку `cannot find module providing package example.com/mathlib`.
- **Необходимые проверки / источники:** Проверка компиляции проекта с мультимодульным semver.

### 3.7. Упражнение 58: Устаревший паттерн `golang.org/x/exp/constraints` вместо стандартного `cmp.Ordered` и встроенных `min/max`
- **Раздел / Упражнение:** Упражнение 58, Секция 4 (`builder/section4.py`).
- **Фрагмент задачи / кода:**
  > Текст задачи: «Импортируй golang.org/x/exp/constraints и создай generic-функцию Min и Max для числовых типов.»
- **В чем проблема:** Начиная с Go 1.21:
  1. `min()` и `max()` стали **встроенными функциями языка** (built-in functions), доступными везде без каких-либо импортов.
  2. Ограничение `constraints.Ordered` было стабилизировано и перенесено в стандартную библиотеку как **`cmp.Ordered`**.
  В теории упражнения об этом упомянуто, однако код решения по-прежнему учит писать велосипеды через экспериментальный `golang.org/x/exp/constraints`. Для курса 2026 года идиоматично показывать `cmp.Ordered` и встроенные `min/max`.
- **Необходимые проверки / источники:** Go 1.21 Release Notes: package `cmp`, built-ins `min` and `max`.

### 3.8. Упражнение 77: Запуск `net/http/pprof` на `http.DefaultServeMux` без защиты
- **Раздел / Упражнение:** Упражнение 77, Секция 6 (`builder/section6.py`).
- **Фрагмент задачи / кода:**
  ```go
  http.ListenAndServe("localhost:6060", nil)
  ```
- **В чем проблема:** Передача `nil` во втором аргументе использует глобальный `http.DefaultServeMux`. Если в сервисе есть другие вызовы `http.Handle` или запускается боевой сервер с `nil`, роуты pprof (`/debug/pprof/`) могут случайно утечь на боевой публичный порт. В промышленном коде для отладочного сервера всегда создают отдельный изолированный экземпляр `mux := http.NewServeMux()` или используют специализированные обертки.
- **Необходимые проверки / источники:** OWASP Go Security Guide: pprof exposure risks.

### 4.5. Упражнение 43: Прямые системные вызовы при `CGO_ENABLED=0` на macOS
- **Фрагмент:** Утверждается, что Go при `CGO_ENABLED=0` всегда генерирует системные вызовы напрямую к ядру. На macOS (`darwin`) начиная с Go 1.12 это не так: Go всегда динамически линкуется с `libSystem.dylib`, так как Apple не гарантирует стабильность номеров системных вызовов ядра XNU.

### 4.6. Упражнение 55: Имя пакета и имя директории
- **Фрагмент:** Утверждается, что «имя пакета в коде должно совпадать с именем последней директории». Это строгое соглашение (convention), но не требование компилятора. Компилятор разрешает иметь `package mypkg` в папке `utils`.

### 4.7. Упражнение 24: `math/rand` vs `math/rand/v2`
- **Фрагмент:** В коде используется старый пакет `math/rand` с глобальным генератором. Начиная с Go 1.22, рекомендуется использовать пакет `math/rand/v2` (первый v2-пакет в стандартной библиотеке Go).

## 🧩 5. Важные пробелы и упущения (Important Omissions)

Для учебника уровня Middle+ / Senior / Staff в Главе 1 критически не хватает нескольких фундаментальных тем:

1. **Go Workspaces (`go.work`) — полное отсутствие практических упражнений:**  
   Появившийся в Go 1.18 механизм рабочих пространств позволяет одновременно разрабатывать несколько связанных модулей без модификации файлов `go.mod` (без временных директив `replace`). В главе это упомянуто лишь вскользь в одном ответе на собеседовании. Необходима практическая задача на `go work init` и `go work use`.
2. **Директива `retract` в `go.mod` (Go 1.16+):**  
   Отзыв сломанных версий библиотек — стандартный процесс в открытом исходном коде и enterprise-разработке. Тема полностью отсутствует.
3. **Автоматический менеджмент версий компилятора через `toolchain` (Go 1.21+):**  
   Директива `toolchain` управляет тем, какой компилятор запускается при сборке проекта. Не освещена.
4. **Стандартное чтение метаданных сборки через `runtime/debug.ReadBuildInfo()`:**  
   В упражнении 88 рассматривается только устаревший подход с флагами линкера `-ldflags "-X main.version=..."`. Начиная с Go 1.18, компилятор сам встраивает VCS-хэш коммита и статус dirty в бинарник, что читается через стандартную библиотеку.
5. **Black-Box тестирование пакетов (`package foo_test`):**  
   В Go принято тестировать публичный интерфейс пакета через внешний тестовый пакет в той же папке (`package utils_test`), исключая доступ к внутренним деталям. В упражнениях по тестированию этот фундаментальный подход не упомянут.
