### Кандидат 1: Фатальная ошибка компиляции в листинге решения — преобразование нетипизированной константы с плавающей точкой в `int`
* **exercise/section:** Упражнение #9 «Матрица явных преобразований типов (Type Casting)» (`main.go`, строка 12) / Генератор: `builder/gen_ch4_p1.py`
* **claim / code fragment:**  
  В коде эталонного решения для демонстрации отсечения дробной части написано:
  ```go
  var truncatedInt int = int(99.99) // Дробная часть отсекается -> 99
  ```
  И в ожидаемом выводе терминала указано:
  ```bash
  # 1. Числа:  i=42 -> f=42.00, float=99.99 -> int=99
  ```
* **why it needs checking:**  
  Данный код **гарантированно не компилируется** ни в одной версии компилятора Go!  
  Ошибка компилятора:
  ```text
  ./main.go:12:29: cannot convert 99.99 (untyped float constant) to type int
  ```
  **Причина:** Согласно Спецификации языка Go (*The Go Programming Language Specification*, раздел *Conversions between numeric types* / *Constant conversions*):
  > *"A constant value x can be converted to type T if x is representable by a value of T."*
  
  Литерал `99.99` является нетипизированной константой с плавающей точкой (*untyped floating-point constant*). Так как `99.99` имеет ненулевую дробную часть, оно **не может быть представлено** целочисленным типом `int`. Компилятор прерывает сборку на этапе проверки типов.  
  Для отсечения дробной части число обязано быть **переменной**, а не нетипизированной константой:
  ```go
  val := 99.99
  var truncatedInt int = int(val) // Компилируется: отсечение в рантайме
  ```
  В текущем виде учащийся получает неработающий пример.
* **evidence/test/source needed:**  
  Команда `go run main.go`; Спецификация Go (раздел Conversions); проверка через `cmd/compile`.
* **priority:** **High**

### Кандидат 2: Грубое искажение ментальной модели системы типов — отождествление Defined Type с Type Alias и утверждение о «необходимости каста для псевдонимов»
* **exercise/section:**  
  1. Упражнение #81 «Создание пользовательского типа type MyInt int и явное приведение» (`builder/gen_ch4_p5.py`)
  2. Упражнение #15 «Пользовательские определенные типы (type Celsius float64) и строгая типизация» (`builder/gen_ch4_p1.py`)
* **claim / code fragment:**  
  - В условии Упр. #81 утверждается:  
    *«Создание своих типов: Создай тип-псевдоним `type MyInt int`. Создай переменную этого типа и попробуй сложить её с обычным `int`. **Пойми, зачем нужно явное приведение типов даже для псевдонимов**.»*
  - В условии Упр. #15 утверждается:  
    *«Создайте **псевдоним типа** `type Celsius float64` и используйте его для переменных, демонстрируя строгую типизацию.»*
* **why it needs checking:**  
  Это фундаментальная теоретическая ошибка, обучающая студентов диаметрально неверной картине мира системы типов Go:
  1. Синтаксис `type MyInt int` и `type Celsius float64` в Go создает **новый определенный тип (Defined Type)**, а НЕ псевдоним (Type Alias)!
  2. Настоящий псевдоним типа (Type Alias) объявляется **со знаком равенства `=`** (введен в Go 1.9):  
     `type MyInt = int`  
     `type Celsius = float64`
  3. Для настоящего псевдонима (Type Alias) **НИКОГДА НЕ ТРЕБУЕТСЯ** явное приведение типов! Псевдоним полностью тождественен базовому типу:
     ```go
     type MyInt = int
     var a MyInt = 50
     var b int = 50
     sum := a + b // ИДЕАЛЬНО КОМПИЛИРУЕТСЯ БЕЗ КАСТА!
     ```
  Фраза в условии *«Пойми, зачем нужно явное приведение типов даже для псевдонимов»* не просто путает термины — она прямо противоречит тому, ради чего псевдонимы типов были добавлены в язык Go (бесшовный рефакторинг кодовых баз без кастов). В блоке Pitfalls Упр. #81 автор сам упоминает `type MyInt = int`, однако условие задачи сформулировано с ошибкой.
* **evidence/test/source needed:**  
  Go Spec (*Type identity*, *Type declarations*, *Alias declarations*); Go 1.9 Release Notes (*Type Aliases*).
* **priority:** **High**

### Кандидат 3: Провал демонстрации неточности вещественных чисел из-за Compile-Time Constant Folding (Программа печатает `true (ОШИБОЧНО!)`)
* **exercise/section:** Упражнение #86 «Сравнение вещественных чисел (0.1 + 0.2 == 0.3) и функция AlmostEqual с эпсилон» (`builder/gen_ch4_p5.py`)
* **claim / code fragment:**  
  Код программы:
  ```go
  func main() {
      a := 0.1 + 0.2
      b := 0.3

      fmt.Printf("a = %.20f\n", a)
      fmt.Printf("b = %.20f\n\n", b)

      fmt.Printf("1. Прямое сравнение (a == b): %t (ОШИБОЧНО!)\n", a == b)
      fmt.Printf("2. Безопасное AlmostEqual:   %t (КОРРЕКТНО!)\n", AlmostEqual(a, b, 1e-9))
  }
  ```
  Ожидаемый вывод (в задачнике):
  ```bash
  # a = 0.30000000000000004441
  # b = 0.29999999999999998890
  # 
  # 1. Прямое сравнение (a == b): false (ОШИБОЧНО!)
  # 2. Безопасное AlmostEqual:   true (КОРРЕКТНО!)
  ```
* **why it needs checking:**  
  Реальный запуск этого кода выдает:
  ```text
  a = 0.29999999999999998890
  b = 0.29999999999999998890

  1. Прямое сравнение (a == b): true (ОШИБОЧНО!)
  2. Безопасное AlmostEqual:   true (КОРРЕКТНО!)
  ```
  **В чем причина сбоя:**  
  Автор не учел механику нетипизированных констант в Go!  
  В выражении `a := 0.1 + 0.2` операнды `0.1` и `0.2` — это константные литералы. Компилятор Go вычисляет `0.1 + 0.2` **на этапе компиляции с произвольной точностью ($\ge 256$ бит)** (*Constant Folding*), получая точное число `0.3`.  
  Затем переменные `a` и `b` получают одинаковое значение `float64(0.3)`. Поэтому `a == b` в рантайме возвращает **`true`**!  
  Программа вместо демонстрации погрешности IEEE 754 печатает бессмыслицу:  
  `1. Прямое сравнение (a == b): true (ОШИБОЧНО!)`.  
  Чтобы продемонстрировать проблему IEEE 754 в рантайме, переменные обязаны складываться в рантайме:
  ```go
  x := 0.1
  y := 0.2
  a := x + y // runtime IEEE 754 addition -> 0.30000000000000004
  b := 0.3
  ```
* **evidence/test/source needed:**  
  Тестовый запуск `go run`; Go Spec (*Constant expressions*); сравнение значений на x86-64.
* **priority:** **High**

### Кандидат 4: Ложное утверждение об оптимизации компилятором переполнения со знаком (перенос C/C++ UB-семантики в Go) и некорректная рекомендация `math/bits.Add`
* **exercise/section:** Упражнение #60 «Безопасное сложение целых чисел SafeAdd с проверкой переполнения» (`builder/gen_ch4_p3.py`)
* **claim / code fragment:**  
  1. В разделе **Pitfalls**:  
     *«Попытка проверить `if a + b < a`: после того как переполнение уже произошло, оптимизатор компилятора может посчитать такое условие недостижимым и вырезать его. Всегда проверяйте границы ДО сложения (`a > Max - b`).»*
  2. В ответе на собеседовании (**BigTech Interview**):  
     *«Вопрос: Как пакет math/bits позволяет аппаратно проверять переполнение?  
     Ответ: Функции bits.Add(x, y, carry) возвращают сумму и бит переноса (Carry Flag) напрямую из регистра процессора за 1 машинный такт.»*
* **why it needs checking:**  
  Здесь допущены две серьезные технические ошибки:
  1. **В Go знаковое целочисленное переполнение НЕ является Undefined Behavior (UB)!**  
     В C/C++ знаковое переполнение — это UB, и GCC/Clang действительно имеют право вырезать проверку `a + b < a`. Но в Спецификации языка Go (*The Go Programming Language Specification*, раздел *Arithmetic operators* / *Integer overflow*) прямо зафиксировано:
     > *"For signed integers, the operations +, -, \*, /, and << may legally overflow and the resulting value exists and is deterministically defined by the signed integer representation, the operation, and its operands... **A compiler may not optimize code under the assumption that overflow does not occur. For instance, it may not assume that x < x + 1 is always true.**"*  
     Компилятор Go **не имеет права** вырезать такую проверку как «недостижимую»! Настоящая причина, почему `if a + b < a` некорректна для знаковых чисел — это отрицательные числа: если `b < 0`, то `a + b < a` выполняется штатно без всякого переполнения.
  2. **`math/bits.Add` работает только с беззнаковыми `uint`, а не знаковыми `int`!**  
     Сигнатура функции: `func Add(x, y, carry uint) (sum, carryOut uint)`. Она возвращает Carry Flag (`CF`). При знаковом сложении переполнение фиксируется флагом Overflow Flag (`OF`), а не `CF`! Например, при сложении положительных чисел `math.MaxInt64 + 1` бит переноса `CF == 0`, но происходит знаковое переполнение (`OF == 1`). Предлагать `bits.Add` для проверки знакового сложения технически безграмотно.
* **evidence/source needed:**  
  Go Spec (Integer overflow); документация `math/bits.Add`; поведение флагов x86 ALU (`OF` vs `CF`).
* **priority:** **High**

     Ответ: `-math.MaxFloat64` ($\approx -1.79 \times 10^{38}$).»*
* **why it needs checking:**  
  1. В стандартном пакете `math` **не существует символа `math.MinFloat32`**!

  `go doc math.MinFloat32`; `src/math/const.go`; стандарт IEEE 754 для binary64.

### Кандидат 6: Ложное объяснение невозможности создания константных массивов через «динамическую аллокацию в куче»
* **exercise/section:** Упражнение #108 «Запрет константных срезов и мап и паттерн безопасного доступа через копирование» (`builder/gen_ch4_p6.py`)
* **claim / code fragment:**  
  В условии задачи:  
  *«TASK: Создай константный массив (или слайс-литерал) через const — получи ошибку. Объясни, почему в Go нельзя создать константу-слайс или константу-мапу.»*  
  В блоке теории:  
  *«1. Слайсы и мапы требуют динамической аллокации памяти в куче (Heap Allocation) в рантайме;  
  2. Константы обязаны разрешаться статически на этапе компиляции без участия рантайма...»*
* **why it needs checking:**  
  Объяснение содержит фактическую ошибку касательно **массивов (arrays)**:
  - Условие задачи требует попробовать объявить константный **массив** (`[3]int`), а не только слайс.
  - Массив в Go — это размерный тип (Value Type) фиксированной длины. Массив фиксированного размера **НЕ требует динамической аллокации памяти в куче в рантайме** (он может размещаться на стеке или в секции данных бинарника).
  - Причина отсутствия `const [3]int` в Go заключается вовсе не в куче, а в сознательном решении авторов языка ограничить систему констант исключительно скалярными примитивами (числа, строки, булевы флаги, руны) ради простоты компилятора и семантики сравнений. Объяснение через «кучу» формирует неверное понимание природы массивов в Go.
* **evidence/source needed:**  
  Rob Pike, *Constants* (The Go Blog); Go Language Specification (Constants).
* **priority:** **Medium**

### Кандидат 7: Фантазийный терминальный вывод в задаче на побитовый сдвиг `uint8` (`<< 2`)
* **exercise/section:** Упражнение #29 «Побитовые операции над uint8 (&, |, ^, <<, >>)» (`builder/gen_ch4_p2.py`)
* **claim / code fragment:**  
  В коде решения:
  ```go
  var a uint8 = 0b00001100 // 12
  fmt.Printf("a << 2:  %08b (Сдвиг влево на 2 -> * 4)\n", a<<2)
  ```
  В ожидаемом терминальном выводе заявлено:
  ```bash
  # a << 2:  00000000 (Сдвиг влево на 2 -> * 4) [переполнение старших бит: 48]
  ```
* **why it needs checking:**  
  Реальный вывод программы:
  ```text
  a << 2:  00110000 (Сдвиг влево на 2 -> * 4)
  ```

  В ожидаемом выводе откуда-то взялось `00000000` и пометка о вымышленном «переполнении старших бит». Студент при сверке вывода видит расхождение своего терминала с эталоном.
* **evidence/test/source needed:**

### Кандидат 8: Парадокс сравнения `float32` — расхождение реального вывода (`true`) с эталонным (`false`)
* **exercise/section:** Упражнение #68 «Сравнение точности float32 vs float64 и проблема 0.1 + 0.2 != 0.3» (`builder/gen_ch4_p4.py`)
* **claim / code fragment:**  
  В коде:
  ```go

  sum32 := a32 + b32
  fmt.Printf("float32: 0.1 + 0.2 = %.10f (равно 0.3? %t)\n", sum32, sum32 == 0.3)
  ```
  В ожидаемом выводе в задачнике записано:
  ```bash

  ```
* **why it needs checking:**  
  Реальная программа на Go печатает:
  ```text
  float32: 0.1 + 0.2 = 0.3000000119 (равно 0.3? true)
  ```
  **Почему это происходит:**  
  В выражении `sum32 == 0.3` операнд `0.3` — это нетипизированная константа. По правилам Go она приводится к типу левого операнда, то есть `float32(0.3)`.

  Поэтому для `float32` в Go это выражение оценивается как **`true`**!  
  Автор упражнения механически перенес результат `false` из `float64` в блок `float32`, создав ложный ожидаемый вывод.
