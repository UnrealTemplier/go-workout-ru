### G-07. Фатальный сбой жизненного цикла транзакции `sqlmock` в задачах 037 и 059 из-за `t.Cleanup`
- **Где:**
  - `sources/030. Мокирование и интеграционное тестирование/02. Мокирование БД (go-sqlmock), miniredis/037. Мокирование транзакций (Begin, Commit, Rollback).md` → `order_repo_test.go`
  - `sources/030. Мокирование и интеграционное тестирование/02. Мокирование БД (go-sqlmock), miniredis/059. Имитация дедлока в транзакции.md` → `tx_deadlock_test.go`
- **Цитата:**
  ```go
  t.Cleanup(func() {
      _ = tx.Rollback()
  })
  ...
  // Проверка выполнения всех моков
  if err := mock.ExpectationsWereMet(); err != nil {
      t.Errorf("не все ожидания sqlmock были выполнены: %v", err)
  }
  ```
- **Утверждение:** Тесты успешно проходят (`PASS`), корректно закрывая транзакции через отложенный хук `t.Cleanup`.
- **Почему проверить:**
  Хуки `t.Cleanup` выполняются строго **после** выхода из тела тестовой функции. При этом вызов проверки ожиданий `mock.ExpectationsWereMet()` расположен в самом конце тела функции `Test...`.
  В результате получается фатальный конфликт:
  1. В момент вызова `mock.ExpectationsWereMet()` тело функции ещё не завершено, и отложенный `tx.Rollback()` в `t.Cleanup` ещё **не вызвался**. Ожидание `mock.ExpectRollback()` остаётся невыполненным, и `ExpectationsWereMet()` возвращает ошибку: `there is a remaining expectation which points to: ExpectedRollback`.
  2. После возврата из функции вызывается `t.Cleanup`, который делает `tx.Rollback()`, но транзакция уже считается завершённой или незапланированной, вызывая ошибку драйвера `sqlmock: call to Rollback on transaction was not expected`.
  Тест падает с `FAIL` в 100% запусков! Терминальный вывод `PASS` в обеих задачах сфабрикован. Для исправления вызов `mock.ExpectationsWereMet()` обязан регистрироваться в `t.Cleanup` *после* регистрации отката транзакции (в LIFO порядке).
- **Что проверить и где:** Запуск `go test` в задачах 037 и 059.
- **Тип:** код / вывод
- **Приоритет:** High

### G-08. Ошибка преобразования руны `rune('0'+10) == ':'` приводит к рантайм-падению теста в задаче 105
- **Где:** `sources/030. Мокирование и интеграционное тестирование/03. Testcontainers в продакшене, Golden Files/105. Комплексный тест: Redis кэш + Postgres БД.md` → `integration_flow_test.go` (строки 49 и 80)
- **Цитата:**
  Строка 49: `key := "user:cache:" + string(rune('0'+id))`
  Строка 80: `if val, ok := manager.cacheData["user:cache:10"]; !ok { t.Fatalf("Данные не попали в кэш после первого запроса!") }`
- **Утверждение:** При поиске пользователя с `id = 10` ключ сохраняется в кэш под именем `"user:cache:10"`.
- **Почему проверить:**

  Тест падает в рантайме. Вывод в терминале с `--- PASS: TestIntegrationUserFlow` сфабрикован. Необходимо использовать `fmt.Sprintf("user:cache:%d", id)` или `strconv.Itoa(id)`.
- **Что проверить и где:** Запуск `go test .` в папке задачи 105.

### G-12. Инвертированная логика таймаута и ошибочное использование `http.ErrHandlerTimeout` в клиенте (задача 024)
- **Где:** `sources/030. Мокирование и интеграционное тестирование/01. Ручные моки.../024. Имитация медленного ответа с context.WithTimeout.md` → `client.go` (строки 42–47)
- **Цитата:**
  ```go
  if !os.IsTimeout(err) && !errors.Is(err, http.ErrHandlerTimeout) {
      fmt.Printf("Неожиданная ошибка: %v\n", err)
  } else {
      fmt.Println("Запрос корректно отменен по таймауту!")
  }
  ```
- **Утверждение:** Код корректно детектирует клиентский таймаут при отмене запроса по контексту.
- **Почему проверить:**
  1. Функция `os.IsTimeout` предназначена для ошибок операционной системы и ввода-вывода файлов. Клиентский `http.Client.Do` при истечении контекста возвращает ошибку типа `*url.Error`, оборачивающую `context.DeadlineExceeded`.
  2. `http.ErrHandlerTimeout` — это серверная ошибка, которую возвращает `http.TimeoutHandler` сервера при зависании обработчика; клиентский запрос её **никогда не возвращает**.

## 3. Сквозные проблемы

1. **Систематическая фиктивность раздела Testcontainers (`G-09`):**
   Раздел 03 называется «Testcontainers в продакшене, Golden Files», а во вводном файле `000. О главе.md` читателю обещаются настоящие Docker-контейнеры для PostgreSQL, Redis, Kafka, MinIO и паттерн `WithReuse`. На практике в коде решений задачи 033, 067, 071, 072, 073, 074, 084, 092, 105 реальные вызовы `testcontainers-go` вырезаны и заменены на in-memory словари (`map[string]...`) с комментариями «в проде здесь был бы контейнер». Это полностью ломает заявленную тему раздела.

2. **Подмена заявленных инструментов мокирования на самодельные заглушки (`G-10`, `G-22`):**
   В условиях и заголовках прямо требуются библиотеки `gomock` (`EXPECT()`, `DoAndReturn()`, `Times()`) и `gomonkey`, однако в коде решений автор упорно уклоняется от их использования, реализуя ручные мок-структуры на чистом Go или подменяя глобальные переменные пакета.

3. **Сфабрикованный терминальный вывод в упавших и некомпилируемых задачах (`G-01`–`G-08`, `G-13`):**
   Блоки вывода терминала `bash` содержат сфабрикованный отчёт `--- PASS: Test...`, в то время как реальный запуск кода завершается ошибками компилятора (`imported and not used`, `undefined`, невалидное имя теста со строчной буквы в 092) или фатальными падениями в рантайме (ошибка `rune('0'+10) == ':'` в задаче 105, невыполненные ожидания `sqlmock` из-за `t.Cleanup` в задачах 037 и 059).

4. **Нарушение автономности кода по `AGENTS.md` § 3.2 (`G-11`):**
   В задачах 003, 004, 006, 011, 012, 038 приведён только файл `*_test.go`, который тестирует отсутствующие доменные сущности. Запустить такой код локально невозможно без ручного дописывания недостающих структур.

5. **Некорректная интеграция `sqlmock` с транзакциями (`G-07`):**
   Паттерн вызова `t.Cleanup(func() { _ = tx.Rollback() })` при наличии синхронной проверки `mock.ExpectationsWereMet()` в теле теста является антипаттерном, гарантированно приводящим к падению теста.

## 4. Упущения главы

1. **Реальный запуск Docker-контейнеров через `testcontainers-go`:**
   В главе о Testcontainers отсутствуют работающие примеры настройки контейнеров с реальным ожиданием готовности (`wait.ForListeningPort`, `wait.ForLog`), маппингом динамических портов (`MappedPort`), монтированием скриптов инициализации (`WithInitScripts`) и переиспользованием контейнеров через `WithReuse`.
2. **Мокирование сетевых вызовов gRPC через `bufconn`:**
   Тестирование микросервисов в Go опирается на gRPC. В главе полностью отсутствует стандартный промышленный паттерн тестирования gRPC-сервисов в памяти без открытия реальных TCP-сокетов с помощью пакета `google.golang.org/grpc/test/bufconn`.
3. **Контрактное тестирование (Contract Testing / CDC):**
   Тема контрактного тестирования сведена к единственному файлу с in-memory мапой (`G-15`). Отсутствуют инструменты Consumer-Driven Contract Testing (например, Pact Go или OpenAPI contract testing).
4. **Полноценный `testify/suite` с жизненным циклом:**
   В главе упоминается `testify/mock`, но практически не раскрыт `testify/suite` — стандартный каркас интеграционных тестов в Go с методами `SetupSuite`, `TearDownSuite`, `SetupTest`, `TearDownTest`.
5. **Настоящие миграции БД в тестах:**
   В задачах 068 и 097 тема миграций сымитирована строковыми логами. Отсутствует реальный запуск миграторов (`golang-migrate` или `goose`) против тестовой базы данных с проверкой миграций «вверх» и «вниз» (`Up` / `Down`).
6. **Нагрузочные тесты с `testing.B`:**
   Задача 088 заявляет нагрузочное микротестирование с `testing.B`, но решает задачу обычным `testing.T`. В главе нет разбора `b.RunParallel`, бенчмаркинга пулов соединений и профилирования аллокаций памяти (`b.ReportAllocs()`).
