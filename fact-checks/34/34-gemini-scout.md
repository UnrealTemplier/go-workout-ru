### G-15. Некорректная валидация длины строки через `len()` (байты вместо рун UTF-8) в задаче 023
- **Где:** `01. Основы GraphQL, Schema-First/023. Декларативная валидация схемы через директивы.md` → `## Код решения`, `constraint_directive_test.go`
- **Цитата:** `if rule.MinLength > 0 && len(val) < rule.MinLength {\n\treturn fmt.Errorf("длина поля (%d)...`
- **Утверждение:** Функция валидирует минимальную и максимальную длину строки в символах.
- **Почему проверить:** В Go встроенная функция `len(val)` возвращает количество байт в UTF-8 представлении строки, а не количество символов (рун). Для кириллицы (в тесте используется строка `"Константин"`) каждый символ занимает 2 байта (20 байт вместо 10). Строка `"Я"` имеет `len` = 2, поэтому пройдет проверку `MinLength = 2`, хотя в ней всего 1 символ. Необходимо использовать `utf8.RuneCountInString(val)`.
- **Что проверить и где:** `sources/034. GraphQL/01. Основы GraphQL, Schema-First/023. Декларативная валидация схемы через директивы.md`.
- **Тип:** код
- **Приоритет:** Medium

### G-16. Устаревшее утверждение о том, что GraphQL сервер «всегда возвращает HTTP 200 OK» в задаче 056
- **Где:** `03. Кастомные скаляры, директивы/056. Спецификация HTTP ответов GraphQL.md` → `## Условие`, `## Теория`, `## Под капотом`
- **Цитата:** «в отличие от REST, GraphQL-сервер всегда должен возвращать HTTP-статус 200 OK... Единственные случаи, когда GraphQL сервер возвращает статус, отличный от 200: HTTP 400 Bad Request — если тело запроса не является валидным JSON»
- **Утверждение:** Спецификация GraphQL требует всегда отдавать HTTP 200 OK, кроме случая синтаксически невалидного JSON.
- **Почему проверить:** Согласно официальной спецификации **GraphQL-over-HTTP** (принятой GraphQL Working Group), при ошибках статической валидации документа (неизвестное поле, несоответствие типов аргументов) или синтаксических ошибках GraphQL-запроса сервер **ОБЯЗАН** возвращать статус диапазона 4xx (как правило, `400 Bad Request`). Если выполнение завершается ошибкой корневого non-null поля без поля `data`, также допускаются статусы 4xx/5xx. Утверждение о «всегда 200 OK» является устаревшим мифом.
- **Что проверить и где:** Спецификация GraphQL-over-HTTP, раздел "Status Codes".
- **Тип:** факт
- **Приоритет:** Medium

## 3. Сквозные проблемы главы

1. **Некомпилируемый код и фиктивный терминальный вывод (`G-01`, `G-02`, `G-03`, `G-04`, `G-05`, `G-07`, `G-08`):**
   В 5 задачах код не компилируется стандартным компилятором Go из-за неиспользуемых импортов (`context`, `strings`) или необработанных переменных (`errs`). При этом во всех этих задачах в блоке «Терминал» приведены фиктивные логи `PASS` с детальным выводом, который физически не мог быть сгенерирован данным кодом. В задачах 052 и 061 вывод в терминале содержит вымышленные значения (сдвиг даты на сутки, фиктивный SHA-256 хэш).

2. **Профанация паттерна DataLoader и подмена батчинга простым кэшем (`G-13`, `G-10`, `G-11`, `G-12`):**
   Ключевая инженерная тема главы — решение проблемы N+1 запросов через DataLoaders. Однако в задачах 037 и 049 под видом DataLoader реализован тривиальный синхронный кэш на `map`: вызов `Load(key)` не накапливает ключи в пачку, а немедленно делает одиночный запрос к «базе». В задаче 030 батчинг сводится к передаче среза из 100 элементов вручную. Ни одна задача не показывает, как настоящий DataLoader агрегирует запросы от десятков независимых конкурентных горутин резолверов в рантайме `gqlgen`.

3. **Колоссальное расхождение между условием и решением в комплексных задачах (`G-10`, `G-11`, `G-12`):**
   В задачах повышенной сложности (074, 075, 078) условие ставит масштабную задачу (построение e-commerce платформы, федеративного шлюза, гибрида со стримингом gRPC и WebSocket), но в решении приводится 15–30 строк простого мок-кода со структурами в памяти. В задаче 075 шлюз вместо федеративной маршрутизации выполняет синхронный цикл по заказам, самостоятельно порождая N+1.

4. **Массовое структурное дублирование задач (`G-23`):**
   Глава содержит 78 задач, однако почти треть из них дублирует базовые тривиальные механики (по 4–5 задач на `createUser`, `Time scalar`, `Playground`, `Node`). Это размывает фокус и снижает ценность учебника для аудитории Middle / Senior / Staff.

## 4. Упущения главы

Для учебника уровня Middle / Senior / Staff Go Developer в BigTech в Главе 34 отсутствуют критически важные темы:

1. **Реальная кодогенерация и связка с `gqlgen generate`:**
   В 95% задач студенту предлагается вручную писать структуры и интерфейсы резолверов (`type QueryResolver interface`), что противоречит реальному пайплайну gqlgen, где интерфейсы и DTO строго генерируются инструментом из SDL.
2. **Интеграция DataLoader в сгенерированные резолверы gqlgen:**
   Нет демонстрации того, как вызов `dataloader.Load(ctx, id)` связывается с механизмом `thunk` (ленивых вычислений) или блокирующим ожиданием каналов в параллельно исполняемых полях GraphQL.
3. **Двунаправленная пагинация Relay (Backward Pagination):**
   В задаче 036 реализована только прямая пагинация (`first` / `after`). Не показана реализация `last` / `before`, обратная сортировка и корректный расчёт метаданных `hasPreviousPage` / `startCursor`.
4. **Маскирование и презентация ошибок в продакшене (Error Masking & Presenter):**
   Не раскрыта практика использования `graphql.DefaultErrorPresenter` и `RecoverFunc`: как скрывать внутренние ошибки PostgreSQL / gRPC от внешних клиентов, логируя реальную ошибку в Sentry/OpenTelemetry и возвращая клиенту безопасный `INTERNAL_SERVER_ERROR` с `trace_id`.
5. **Subscriptions поверх HTTP (Server-Sent Events / SSE — `graphql-sse`):**
   В современных стандартах GraphQL Working Group всё чаще отказываются от WebSockets в пользу Server-Sent Events (SSE) через HTTP/2. Тема SSE для GraphQL Subscriptions в главе не упомянута вовсе.
6. **Загрузка бинарных файлов (GraphQL Multipart Request Spec):**
   Загрузка файлов (`graphql.Upload`) упомянута лишь вскользь в блоке «На собеседовании» задачи 013, но практической реализации загрузки файлов через multipart/form-data в главе нет.
7. **Ограничение глубины запросов (Query Depth Limiting):**
   В задаче 062 разобран только расчет сложности по очкам (Complexity). Ограничение глубины синтаксического дерева (Depth Limiting) не реализовано.
