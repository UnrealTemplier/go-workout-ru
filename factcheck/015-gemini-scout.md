  type InMemoryUserRepository struct {
      mu    sync.RWMutex
      users map[int]*User
  }

  func (r *InMemoryUserRepository) Create(u *User) error {
      m.mu.Lock()         // ❌ Ошибка: переменная m не определена! Получатель назван r
      defer m.mu.Unlock() // ❌
      r.users[u.ID] = u

  func (r *InMemoryUserRepository) FindByID(id int) (*User, error) {
      m.mu.RLock()         // ❌ Ошибка: переменная m не определена!
      defer m.mu.RUnlock() // ❌

      }

  }

  func main() {
      lc := &LoggingCounter{}
      lc.AddAll([]string{"1", "2"} == nil) // ❌ Грубейшая ошибка типов!

### 2.7. Упражнение 20: Подмена задания и потеря каверзного кейса Method Set ($T$ vs $*T$)
- **Раздел / Упражнение:** Упражнение 20 (`sources/15. ООП в Go.md`, `builder/chapter15_data.json`).
- **Текст задачи:**
  > «[Каверзный кейс]: Создай интерфейс Geometry с методом Area(). Попробуй присвоить переменной типа Geometry значение Rectangle (а не указатель). Пойми, почему метод Scale не входит в интерфейс для значения (Method Sets: *T включает методы T и *T, а T включает только методы T).»
- **Фрагмент кода решения:**
  ```go
  type Transformer interface {
      Scale(factor float64)
  }

  type Rectangle struct {
      Width, Height float64
  }

  func (r *Rectangle) Scale(factor float64) {
      r.Width *= factor
      r.Height *= factor
  }

  func main() {
      var t Transformer = &Rectangle{10, 5} // ✅ Успех
      t.Scale(2.0)
      fmt.Println("Трансформация выполнена успешно!")
  }
  ```
- **В чем проблема:**
  1. Задача сформулирована для разбора классической ловушки Method Sets: почему значение `Rectangle{...}` **не удовлетворяет** интерфейсу, требующему метод с pointer receiver (`Scale`), в то время как указатель `&Rectangle{...}` удовлетворяет.
  2. Однако автор решения:
     - переименовал интерфейс в `Transformer`;
     - удалил метод `Area()`;
     - сразу передал указатель `&Rectangle{10, 5}`;
     - **полностью удалил отрицательный пример** (попытку присвоить значение `var t Transformer = Rectangle{10, 5}`) и объяснение ошибки компилятора (`cannot use Rectangle literal as Transformer: Scale method has pointer receiver`).
  3. В итоге «каверзный кейс» превратился в банальный успешный запуск с указателем. Студент не видит того поведения компилятора, ради которого создавалось упражнение.
- **Необходимые проверки / источники:** The Go Programming Language Specification, §Method sets.

### 3.1. Упражнения 3, 5, 21, 32, 60, 63, 64, 78, 87, 93, 94, 105: Антипаттерн «инкапсуляции в одном пакете main»
- **Раздел / Упражнение:** 12 упражнений главы (упр. 3, 5, 21, 32, 60, 63, 64, 78, 87, 93, 94, 105).
- **Суть проблемы:**
  1. В условиях всех этих задач явным образом требуется:
     - *«вынесите её в отдельный пакет counter, чтобы поле было действительно приватным для main»* (упр. 5);

  2. Однако в **100% решений весь код помещен в один-единственный файл с `package main`**.
  3. В языке Go границы видимости идентификаторов (Public/Private) работают **строго на уровне пакетов**, а не структур или классов. Внутри одного пакета `main` любая функция имеет полный прямой доступ к любым неэкспортируемым полям (`balance`, `value`, `secretCode`, `member`).

### 3.2. Упражнение 62: Нерабочий сценарий обхода приватности через `unsafe.Offsetof` на приватном поле чужого пакета
- **Раздел / Упражнение:** Упражнение 62 (`builder/chapter15_data.json`).
- **Текст задачи:** *«Попробуйте изменить приватное поле структуры из другого пакета с помощью пакета unsafe и пакета reflect...»*
- **Фрагмент кода решения:**
  ```go
  ptr := (*int)(unsafe.Pointer(uintptr(unsafe.Pointer(&c)) + unsafe.Offsetof(c.secretCode)))
  *ptr = 9999
  ```
- **В чем проблема:**
  1. Код использует `unsafe.Offsetof(c.secretCode)`.

  3. Чтобы обойти границу внешнего пакета через `unsafe`, требуется либо знать смещение статически (вычислить размер предшествующих полей), либо использовать обход флагов `reflect.Value.flag` (сброс флага `flagRO`).
  4. Кроме того, пакет `reflect` вообще не задействован в решении, вопреки ТЗ задачи.

### 3.3. Упражнения 1 и 45: Терминологическая ошибка — подмена Defined Type понятием «алиас»
- **Раздел / Упражнение:** 
  - [`sources/15. ООП в Go.md#L7`](file:///home/ut/work/go-workout/sources/15.%20%D0%9E%D0%9E%D0%9F%20%D0%B2%20Go.md#L7) (Упр. 1)
  - [`sources/15. ООП в Go.md#L97`](file:///home/ut/work/go-workout/sources/15.%20%D0%9E%D0%9E%D0%9F%20%D0%B2%20Go.md#L97) (Упр. 45)
- **Фрагмент текста:**
  - **Упр. 1:** *«Методы для неконкретных типов **(алиасов)**: Создайте кастомный тип на базе встроенного: `type MyDuration int`...»*
  - **Упр. 45:** *«Изучите **"Aliasing" типов**. Создайте тип `type MyInt int` и добавьте к нему метод...»*
- **В чем проблема:**
  1. Синтаксис `type MyDuration int` объявляет **новый определенный тип (Defined Type)**, а НЕ псевдоним/алиас (Type Alias)!
  2. Псевдоним (Type Alias) в Go объявляется строго через знак равенства: `type MyDuration = int` (начиная с Go 1.9).
  3. Принципиальная разница: на Defined Type (`type MyDuration int`) объявлять методы **разрешено**, а на Type Alias для базового типа (`type MyDuration = int`) объявлять методы **запрещено компилятором** (`cannot define new methods on non-local type int`).
  4. Называние определенного типа «алиасом» путает студентов (аналогичная ошибка фиксировалась в Главе 12).
- **Необходимые проверки / источники:** The Go Programming Language Specification, §Type identity and §Alias declarations.

### 3.4. Упражнение 38: Продвижение опасного антипаттерна встраивания `*sync.Mutex`
- **Раздел / Упражнение:** Упражнение 38 (`builder/chapter15_data.json`, `sources/15. ООП в Go.md`).
- **Фрагмент текста и кода:**
  > «Объясни, почему встраивается именно `*sync.Mutex`, а не `sync.Mutex`.»
  ```go
  type SafeCounter struct {
      *sync.Mutex // Указатель на мьютекс
      val         int
  }
  func NewSafeCounter() *SafeCounter {
      return &SafeCounter{Mutex: &sync.Mutex{}}
  }
  ```
- **В чем проблема:**
  1. Автор преподносит встраивание `*sync.Mutex` как рекомендуемую практику. В производственном коде Go это считается **двойным антипаттерном**:
     - **Утечка инкапсуляции:** методы `Lock()` и `Unlock()` становятся частью публичного API структуры `SafeCounter`. Любой внешний клиент структуры может вызвать `c.Lock()` и организовать deadlock в сервисе;
     - **Опасность nil pointer dereference:** нулевое значение структуры `var c SafeCounter` содержит `nil`-указатель на мьютекс. Первый же вызов `c.Inc()` или `c.Lock()` приведет к фатальной панике рантайма.
  2. Идиоматичный подход в Go: мьютекс объявляется как **неэкспортируемое значение** `mu sync.Mutex`. Нулевое значение структуры `sync.Mutex` валидно и готово к использованию сразу, без явного вызова конструктора и лишних аллокаций в куче.
- **Необходимые проверки / источники:** Go Code Review Comments (Synchronous Methods, Receiver Types).

## 🔍 5. Важные пробелы и упущения (Omissions)

Для исчерпывающего курса уровня Middle/Senior/Staff по ООП в Go критически не хватает следующих фундаментальных тем:

1. **Официальные правила выбора получателя (Value vs Pointer Receiver Guidelines):**
   - В стандарте Go Code Review Comments сформулированы жесткие критерии:
     1. **Правило консистентности:** если у типа хотя бы один метод требует pointer receiver, все методы этого типа должны иметь pointer receiver;
     2. **Некопируемые типы:** структуры, содержащие `sync.Mutex`, `sync.WaitGroup`, каналы или типы из `atomic`, обязаны использовать строго pointer receiver;
     3. **Размер структуры:** структуры размером больше нескольких машинных слов выгоднее передавать по указателю, чтобы избежать копирования на стек.
   - Этот фундаментальный алгоритм выбора в главе не систематизирован в виде матрицы решений.
2. **Структуры нулевого размера `struct{}` с методами и `runtime.zerobase`:**
   - Пустые структуры `struct{}` занимают 0 байт памяти и в рантайме Go все ссылаются на глобальную переменную `runtime.zerobase`.
   - Возможность объявлять методы на пустых структурах для реализации чистых маркеров (Stateless Services, Visitor, State pattern) без аллокаций памяти — ключевой паттерн микросервисов.
3. **Встраивание интерфейсов в структуры для частичного мокирования (Partial Interface Mocking):**
   - Паттерн `type PartialReader struct { io.Reader }` позволяет переопределить только один метод интерфейса, делегируя остальные встроенной реализации.
   - Это стандартный подход в тестах и middleware в Go, который заменяет громоздкие Mock-библиотеки. В главе он упоминается вскользь, но не разобран как паттерн тестирования.
4. **Девиртуализация (Devirtualization) и инлайнинг методов компилятором Go:**
   - Компилятор Go (`cmd/compile`) анализирует вызовы интерфейсов: если компилятор может статически доказать конкретный тип объекта (Static Type Resolution), вызов через `itab` девиртуализируется в прямой вызов функции и может быть заинлайнен. Механика влияния этого на производительность в HighLoad не раскрыта.
5. **Аллокации памяти при боксинге значений в интерфейс (`any`) и побег в кучу:**
   - Присвоение переменной базового типа (`int`, `float64`) или компактной структуры переменной типа `any` или интерфейсу требует упаковки (boxing). В результате значение почти всегда сбегает в кучу (Heap Allocation). Понимание цены полиморфизма в Go критично для Senior-инженера.
