### 2.1. Упражнение 30: Баг затирания именованного возвращаемого значения в `defer` + подделка ожидаемого терминального вывода
- **Раздел / Упражнение:** Упражнение 30, «Deferred Error Handling и откат транзакций при ошибке» ([`builder/chapter17_data.json`](file:///home/ut/work/go-workout/builder/chapter17_data.json), [`dist/017-obrabotka-oshibok.html#ex-30`](file:///home/ut/work/go-workout/dist/017-obrabotka-oshibok.html#ex-30)).
- **Фрагмент кода и терминала:**
  ```go
  func ExecuteTransaction(amount int) (txID int, err error) {
      fmt.Println("[TX] Начало транзакции")
      txID = 1001

      defer func() {
          if err != nil {
              fmt.Printf("[TX #%d] Ошибка (%v) -> Выполнен ROLLBACK!\n", txID, err)
          } else {
              fmt.Printf("[TX #%d] Успех -> Выполнен COMMIT!\n", txID)
          }
      }()

      if amount <= 0 {
          err = errors.New("сумма перевода должна быть больше нуля")
          return 0, err
      }

      return txID, nil
  }
  ```
  Ожидаемый терминальный вывод в курсе:
  ```text
  go run main.go
  # Вывод:
  # [TX] Начало транзакции
  # [TX #1001] Успех -> Выполнен COMMIT!
  # [TX] Начало транзакции
  # [TX #1001] Ошибка (сумма перевода должна быть больше нуля) -> Выполнен ROLLBACK!
  ```
- **В чем проблема:**
  1. **Семантика именованных возвращаемых значений Go:** В сигнатуре функции объявлены именованные переменные `(txID int, err error)`. При вызове `return 0, err` компилятор Go сначала вычисляет аргументы оператора `return` и присваивает их именованным переменным: `txID = 0; err = err`. И только **после этого** запускает функции из цепочки `defer`!
  2. **Реальный вывод рантайма Go:** Поскольку `txID` был затерт нулем (`0`), внутри `defer` при ошибке печатается:
     ```text
     [TX #0] Ошибка (сумма перевода должна быть больше нуля) -> Выполнен ROLLBACK!
     ```
  3. **Подделка терминального блока:** В ожидаемом терминальном выводе курса автор вручную прописал `[TX #1001]`, скрыв этот дефект.
  4. **Методический вред:** Упражнение призвано научить студентов паттерну отката ресурсов через `defer`. Вместо этого студенты получают неработающий код, где идентификатор транзакции в логе отката равен `0`, а в учебнике нарисован `1001`. Это прививает ложное понимание порядка вычисления выражений в `return` и выполнения `defer`.
  5. **Правильное исправление:** Либо возвращать `txID, err` (`return txID, err`), либо использовать голый `return`, либо не затирать `txID`, либо передавать `txID` параметром в отложенную функцию: `defer func(id int) { ... }(txID)`.
- **Необходимые проверки / источники:** Запуск `go run main.go` для кода упр. 30; The Go Programming Language Specification (§"Return statements", §"Defer statements").

- **Раздел / Упражнение:** Упражнение 58, «Конкурентная обработка ошибок: сбор из горутин через канал и sync.WaitGroup» ([`builder/chapter17_data.json`](file:///home/ut/work/go-workout/builder/chapter17_data.json), [`dist/017-obrabotka-oshibok.html#ex-58`](file:///home/ut/work/go-workout/dist/017-obrabotka-oshibok.html#ex-58)).
- **Фрагмент кода и терминала:**
  ```go
  func worker(id int, errCh chan<- error, wg *sync.WaitGroup) {
      defer wg.Done()
      if id%2 == 0 {
          errCh <- fmt.Errorf("воркер #%d: сбой обработки данных", id)
          return
      }
      fmt.Printf("Воркер #%d успешно завершил задачу\n", id)
  }

  func main() {
      // Запуск 5 параллельных воркеров
      for i := 1; i <= numWorkers; i++ {
          wg.Add(1)
          go worker(i, errCh, &wg)
      }
      ...
  }
  ```
  Ожидаемый терминальный вывод:
  ```text

  Воркер #3 успешно завершил задачу
  Воркер #5 успешно завершил задачу
  Обнаружены ошибки при параллельном выполнении:
  воркер #2: сбой обработки данных
  ```

- **В чем проблема:**
  1. Вызовы `fmt.Printf` внутри нечетных воркеров 1, 3, 5 выполняются конкурентно в независимых горутинах без какой-либо координации порядка.

### 2.4. Упражнение 3 (и вся глава): Самая опасная и частая ошибка в Go («типизированный nil в интерфейсе error») отсутствует в исполняемом коде
- **Раздел / Упражнение:** Упражнение 3 (а также общее содержание Главы 17).
- **Фрагмент текста теории / Pitfalls упр. 3:**
  > «Критическая ловушка типизированного nil: если функция возвращает `*AppError` равный `nil`, а сигнатура возврата объявлена как `error`, то `err != nil` вернет `true`! Всегда возвращайте литерал `nil`, если ошибки нет.»
- **В чем проблема:**
  1. Этот баг — абсолютный рекордсмен по количеству инцидентов в продакшене и самый популярный вопрос на собеседованиях по Go любого уровня (от Junior до Staff). Механика толстого указателя интерфейса `iface { tab: *itab, data: unsafe.Pointer }`: при возврате типизированного указателя `(*MyError)(nil)` поле `tab` хранит тип `*MyError`, поэтому интерфейс `error` **НЕ равен `nil`**.
  2. В теории, UTH и Pitfalls упр. 3 эта механика описана словами на «отлично».
  3. **Однако во всех 58 практических упражнениях главы нет ни одной строчки кода, где этот кейс предлагалось бы воспроизвести, отладить или исправить!**
  4. В коде упр. 3 функция `validateUser` сразу возвращает правильный литерал `nil`:
     ```go
     func validateUser(age int) error {
         if age < 18 { return &AppError{...} }
         return nil // правильный литерал, бага нет
     }
     ```
  5. В результате студент читает предупреждение, но не «проживает» баг руками в кодовой среде. Курс уровня BigTech обязан содержать отдельное практическое упражнение с заданием: «Исправьте баг ложного срабатывания проверки `if err != nil` при возврате неинициализированного указателя на кастомную ошибку».
- **Необходимые проверки / источники:** Поиск по всей главе конструкций с присваиванием `nil` типизированному указателю ошибки; Go FAQ: *"Why is my nil error value not equal to nil?"*.

### 3.1. Упражнение 20: Антипаттерн повторного открытия файла, TOCTOU и утечка неэкранированной ошибки
- **Раздел / Упражнение:** Упражнение 20, «Оборачивание системных ошибок ввода-вывода os.Open» ([`builder/chapter17_data.json`](file:///home/ut/work/go-workout/builder/chapter17_data.json)).
- **Фрагмент кода:**
  ```go
  func ReadFileConfig(path string) ([]byte, error) {
      file, err := os.Open(path)
      if err != nil {
          return nil, fmt.Errorf("не удалось прочитать конфиг: %w", err)
      }
      defer file.Close()
      return os.ReadFile(path)
  }
  ```
- **В чем проблема:**
  1. **Двойное открытие файла:** Функция открывает файл через `os.Open(path)`, удерживает дескриптор `file` в открытом состоянии, а затем вызывает `os.ReadFile(path)`, которая внутри себя вызывает `os.Open` **второй раз**!
  2. **Утечка дескриптора на время чтения:** Дескриптор первого открытия удерживается в ядре ОС до завершения второго открытия и чтения.
  3. **Состояние гонки (TOCTOU — Time-of-check to time-of-use):** Между первым `os.Open` и последующим `os.ReadFile` файл на диске может быть удален, перемещен или перезаписан другим процессом.
  4. **Нарушение темы упражнения:** Если `os.Open` успешен, но `os.ReadFile` падает (например, ошибка чтения с носителя, превышение квоты или динамическое изменение прав), функция возвращает ошибку от `os.ReadFile` **сырой, без контекста и без оборачивания в `%w`**!
  5. **Идиоматичное исправление:**
     - Вариант А: читать из открытого файла через `io.ReadAll(file)`.
     - Вариант Б: сразу вызывать `data, err := os.ReadFile(path)` и оборачивать ошибку через `fmt.Errorf("не удалось прочитать конфиг: %w", err)`.
- **Необходимые проверки / источники:** Исходный код `os.ReadFile` (`src/os/file.go`); CWE-367 (Time-of-check Time-of-use Race Condition).

### 3.2. Упражнение 29: Плейсхолдер `...` вместо реального стектрейса в ожидаемом терминальном выводе
- **Раздел / Упражнение:** Упражнение 29, «Перехват критической паники через defer и recover на верхнем уровне» ([`builder/chapter17_data.json`](file:///home/ut/work/go-workout/builder/chapter17_data.json)).
- **Фрагмент терминального блока:**
  ```text
  go run main.go
  # Вывод:
  # Старт обработки запроса...
  # [RECOVER] Перехвачена паника: критическая ошибка: обращение к неинициализированной памяти
  # [RECOVER] Ответ клиенту: HTTP 500 Internal Server Error
  # [STACKTRACE]:
  # ...
  # Сервер продолжает стабильную работу после перехвата паники!
  ```
- **В чем проблема:**
  1. В коде решения вызывается `fmt.Printf("[STACKTRACE]:\n%s\n", string(debug.Stack()))`.
  2. Функция `debug.Stack()` выводит реальный многострочный стек вызовов горутины, включающий внутренние функции рантайма (`runtime/debug.Stack`, `runtime.panic`), абсолютные пути к файлам на машине студента и адреса памяти `+0xa5`.
  3. Реальный вывод не содержит строки `...`. Любой автотест или сопоставление вывода завершится ошибкой.
  4. Для учебного кода рекомендуется либо нормализовать вывод (например, вывести только первую строку стектрейса `strings.Split(string(debug.Stack()), "\n")[0]`), либо оформить многоточие как комментарий `# ... (стектрейс опущен для краткости)`.

### 3.4. Упражнение 44: Ложная ментальная модель отмены операции в паттерне `RunWithTimeout`
- **Раздел / Упражнение:** Упражнение 44, «Таймаут операции через context.WithTimeout и context.DeadlineExceeded» ([`builder/chapter17_data.json`](file:///home/ut/work/go-workout/builder/chapter17_data.json)).
- **Фрагмент текста и кода:**
  - Текст задачи: *«Отменяй операцию по таймауту и возвращай `context.DeadlineExceeded`»*.
  - Сигнатура функции:
    ```go
    func RunWithTimeout(timeout time.Duration, op func() error) error {
        ctx, cancel := context.WithTimeout(context.Background(), timeout)
        defer cancel()

        done := make(chan error, 1)
        go func() {
            done <- op()
        }()

        select {
        case err := <-done:
            return err
        case <-ctx.Done():
            return ctx.Err() // context.DeadlineExceeded
        }
    }
    ```
- **В чем проблема:**
  1. Сигнатура аргумента `op func() error` **не принимает `context.Context`**!
  2. Сама операция `op` внутри горутины никак не знает об истечении таймаута и **не отменяется**. Она продолжает бесконтрольно выполняться в фоне, тратить процессорное время, удерживать сокеты или выполнять долгие SQL-запросы в БД.
  3. Функция `RunWithTimeout` отменяет **только ожидание ответа вызывающей стороной**, но не саму операцию. Называть это «отменой операции» — фундаментальная концептуальная ошибка, создающая у будущих разработчиков иллюзию безопасности.
  4. Идиоматичный паттерн в Go требует передачи контекста в сигнатуру исполняемой операции: `op func(ctx context.Context) error`.
- **Необходимые проверки / источники:** Go Blog: "Go Concurrency Patterns: Context"; "Context cancellation and goroutine leak prevention".

### 3.5. Упражнения 11 vs 14 vs 32: Рассинхронизация Value-Receiver vs Pointer-Receiver для одной и той же структуры `ValidationError`
- **Раздел / Упражнение:** Упражнения 11, 14, 32 ([`builder/chapter17_data.json`](file:///home/ut/work/go-workout/builder/chapter17_data.json)).
- **Фрагменты объявлений структуры:**
  - **Упр. 11:**
    ```go
    type ValidationError struct { FieldName string; Value any }
    func (e ValidationError) Error() string // Value receiver
    ```
  - **Упр. 14:**
    ```go
    type ValidationError struct { Field string; Code string }
    func (e *ValidationError) Error() string // Pointer receiver
    ```
  - **Упр. 32:**
    ```go
    type ValidationError struct { FieldName string; ErrMsg string }
    func (e *ValidationError) Error() string // Pointer receiver
    ```
- **В чем проблема:**
  1. В рамках одной главы структура с одним и тем же именем `ValidationError` объявляется трижды с тремя взаимоисключающими наборами полей (`FieldName/Value`, `Field/Code`, `FieldName/ErrMsg`).
  2. Но еще важнее: в упр. 11 метод `Error()` объявлен на значении (`(e ValidationError)`), а в упр. 14 и 32 — на указателе (`(e *ValidationError)`).
  3. Если в упр. 14 попытаться извлечь структуру из упр. 11 через стандартный шаблон `var valErr *ValidationError; errors.As(err, &valErr)`, то **`errors.As` вернет `false`**! Потому что в ошибку было завернуто значение `ValidationError`, а `valErr` ищет тип `*ValidationError`.
  4. Это одна из самых коварных ловушек при работе с `errors.As`, однако в главе несогласованность между упражнениями подается случайно, без объяснения разницы в поведении `errors.As` для value- и pointer-типов.
- **Необходимые проверки / источники:** Тест сопоставления типов в `errors.As` для value- и pointer-ресиверов.

## 🔍 5. Важные пробелы и упущения (Omissions)

Для курса, ориентированного на уровень Middle/Senior/Staff в технологических компаниях, в Главе 17 не хватает следующих фундаментальных тем:

1. **Практический тренажер по типизированному `nil` (`Typed Nil Error Trap`):**
   - Самый коварный антипаттерн в экосистеме Go (`func f() error { var p *CustomError = nil; return p }` -> `err != nil` равен `true`).
   - Тема упомянута в теории упр. 3, но ни разу не отрабатывается студентом в практическом коде.
2. **Множественный глагол `%w` в `fmt.Errorf` (Go 1.20+):**
   - Начиная с Go 1.20, `fmt.Errorf` официально поддерживает несколько спецификаторов `%w`:
     ```go
     return fmt.Errorf("read: %w; parse: %w", err1, err2)
     ```
   - Результирующая ошибка реализует метод `Unwrap() []error`, аналогично `errors.Join`. В главе этот факт полностью опущен.
3. **Новая типобезопасная функция `errors.AsType[E error]` (Go 1.24+):**
   - В Go 1.24 добавлена дженерик-функция `errors.AsType[E error](err error) (E, bool)`, которая полностью устраняет риск паники от некорректного указателя в `errors.As` и делает код лаконичным.
4. **Реализация кастомных методов `Is(target error) bool` и `As(target any) bool`:**
   - В стандартной библиотеке (например, `os.ErrExist`, `syscall.Errno`) структуры могут самостоятельно определять правила эквивалентности или приведения типов. В главе эти методы упоминаются вскользь в UTH, но нет ни одного упражнения на их реализацию.
5. **Несовместимость `errors.Unwrap` и `errors.Join`:**
   - Вызов `errors.Unwrap(joinErr)` **всегда возвращает `nil`**, поскольку `joinError` реализует метод `Unwrap() []error`, а не `Unwrap() error`. Это частая причина багов при миграции на Go 1.20+, требующая отдельного разбора.
6. **Оркестрация параллельных ошибок через `golang.org/x/sync/errgroup`:**
   - В упр. 58 показан ручной сбор ошибок через канал и `sync.WaitGroup`. В современном production Go стандартом является `errgroup.WithContext(ctx)`, который автоматически отменяет контекст при первом сбое.
7. **Трассировка стека без паники (Stack Traces в структурированных ошибках):**
   - Ошибки стандартной библиотеки Go не содержат стектрейса. В корпоративном Go для этого используют захват кадров вызова через `runtime.Callers` / `runtime.CallersFrames`, либо библиотеки уровня `cockroachdb/errors` / `xerrors`.
