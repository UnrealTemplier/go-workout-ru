### 2.1. Упражнение 09: Грубая фактическая ошибка в Pitfalls — утверждение о синтаксической ошибке при `go build -o .`
- **Раздел / Упражнение:** Упражнение 9 («Кастомизация выходного имени бинарника через флаг go build -o»), блок Pitfalls.
- **Фрагмент текста:**
  > «Если передать флаг `-o` без значения (`go build -o .`), компилятор выдаст синтаксическую ошибку флагов.»
- **В чем проблема:** Это прямое искажение фактического поведения тулчейна Go:
  1. В команде `go build -o .` флаг `-o` передается **со значением**: аргументом флага является точка `.`, обозначающая текущую рабочую директорию.
  2. Согласно официальной спецификации `go help build`:
     > *«If the named output is an existing directory or ends with a slash or backslash, then any resulting executables will be written to that directory.»*
  3. Команда `go build -o .` **успешно компилирует проект, завершается с кодом 0** и сохраняет бинарник в текущий каталог под его стандартным именем! Никакой синтаксической ошибки компилятор не выдает.
  4. Синтаксическая ошибка флагов (`flag needs an argument: -o`) возникает только при реальном пропуске значения: `go build -o`. Называть точку «отсутствием значения» и обещать падение компилятора — грубая фактическая ошибка в учебном материале.
- **Необходимые проверки / источники:** Выполнить в терминале `mkdir /tmp/test && cd /tmp/test && go mod init test && echo 'package main; func main(){}' > main.go && go build -o . && echo $?`. Проверить документацию `go help build`.
- **Приоритет:** **High**

Компиляция, сборка и запуск.md`](file:///home/ut/work/go-workout/sources/2.%20%D0%9A%D0%BE%D0%BC%D0%BF%D0%B8%D0%BB%D1%8F%D1%86%D0%B8%D1%8F,%20%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B0%20%D0%B8%20%D0%B7%D0%B0%D0%BF%D1%83%D1%81%D0%BA.md#L49).
- **Фрагмент задачи:**
  > «Вставь в бинарник информацию о версии через -ldflags: `-X main.Version=1.2.3 -X main.BuildTime=$(date)`. Выведи эти переменные при запуске.»


Автор решения в `builder/chapter2_data.json` понял эту проблему и обошел её, заранее подготовив дату без пробелов (`NOW=$(date -u +"%Y-%m-%dT%H:%M:%SZ")`) и добавив кавычки `-X 'main.BuildTime=$NOW'`, а в Pitfalls написал про необходимость экранирования. Однако само задание в опроснике `sources/2.md` осталось с заведомо сломанной командой.
- **Необходимые проверки / источники:** Запуск `go build -ldflags "-X main.Version=1.2.3 -X main.BuildTime=$(date)"` на любой Linux-машине.

### 2.4. Упражнение 11 & Упражнение 25: Опасное заблуждение о «гарантированной статической линковке» Go под Linux
- **Раздел / Упражнение:** Упражнение 11 (BigTech-интервью) и Упражнение 25 (Dockerfile).
- **Фрагмент текста:**
  > В Ex 11: «Что означает надпись statically linked в выводе утилиты file для Go-бинарника? Ответ: Это означает, что бинарник не содержит ссылок на динамические библиотеки (.so / .dll) и содержит весь рантайм внутри себя. **Он запустится на любом Linux-дистрибутиве (Ubuntu, Alpine, RHEL, Arch) с подходящей версией ядра без установки сторонних пакетов.**»
- **В чем проблема:** Это одно из самых коварных заблуждений, с которым сталкиваются Junior/Middle-разработчики при деплое в Kubernetes:
  1. При нативной компиляции на хосте Linux (`go build .`) переменная `CGO_ENABLED` по умолчанию **включена (`CGO_ENABLED=1`)**.
  2. Стандартные пакеты `net` (DNS resolver) и `os/user` на Linux при включенном CGO используют системный `glibc` (`getaddrinfo`).
  3. В результате на хосте Linux бинарник собирается **динамически слинкованным** (`dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2`).
  4. Если такой бинарник скопировать в образ Alpine Linux (где используется `musl libc` вместо `glibc`) или в `FROM scratch`, он аварийно упадет при старте с ошибкой:  
     `/bin/sh: ./app: not found` (ядро не может найти интерпретатор динамического линкера).
  5. Go-бинарник под Linux становится по-настоящему статическим **только при явном `CGO_ENABLED=0`** (либо при кросс-компиляции с другой ОС, где cgo отключается автоматически, либо с билд-тегами `-tags 'netgo,osusergo'`). Ответ на собеседовании обязан делать на этом жесткий акцент, иначе студенты сформируют неверную модель деплоя.
- **Необходимые проверки / источники:** `go env CGO_ENABLED` на Linux; `ldd <binary>`, собранный без `CGO_ENABLED=0`; документация пакета `net`.
- **Приоритет:** **High**

### 2.5. Упражнение 25: Продакшен-антипаттерны в multi-stage Dockerfile — хардкод `GOARCH=amd64` и отсутствие `/etc/passwd` в `scratch`
- **Раздел / Упражнение:** Упражнение 25 («Многоэтапная Docker-контейнеризация: от Alpine к 5 МБ Scratch»).
- **Фрагмент кода Dockerfile:**
  ```dockerfile
  RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build \
      -ldflags="-s -w -X main.Version=v1.0.0" \
      -o /bin/server .

  FROM scratch
  COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
  COPY --from=builder /usr/share/zoneinfo /usr/share/zoneinfo
  COPY --from=builder /bin/server /server

  USER 65534:65534
  ```
- **В чем проблема:**
  1. **Хардкод `GOARCH=amd64`:** В современном облачном мире (где до 40% инстансов работают на ARM64 — AWS Graviton, Apple Silicon, серверы Ampere) жесткое прописывание `GOARCH=amd64` внутри Dockerfile ломает сборку на машинах разработчиков с macOS (M-series) и в multi-arch пайплайнах `docker buildx`. При сборке на ARM-хосте контейнер получит x86-64 бинарник и упадет с `exec format error`. Идиоматичный подход Docker BuildKit:
     ```dockerfile
     ARG TARGETOS TARGETARCH
     RUN CGO_ENABLED=0 GOOS=${TARGETOS} GOARCH=${TARGETARCH} go build ...
     ```
  2. **Отсутствие файла `/etc/passwd` в образе `scratch`:**  
     Директива `USER 65534:65534` задает числовой UID, поэтому сам Docker запускает процесс без ошибки. Однако образ `scratch` абсолютно пуст — в нем **нет файла `/etc/passwd`**. Если Go-приложение или любая сторонняя библиотека вызовет стандартную функцию `os/user.Current()` или попытается определить домашнюю директорию пользователя, вызов упадет с паникой или ошибкой:  
     `user: unknown user 65534`.  
     В промышленном стандарте DevSecOps на этапе сборщика генерируют минимальный файл учетной записи (`echo "nobody:x:65534:65534:Nobody:/:/sbin/nologin" > /tmp/passwd`) и копируют его в `scratch`: `COPY --from=builder /tmp/passwd /etc/passwd`.
  3. В команде сборки отсутствует обязательный флаг `-trimpath`, оставляя в бинарнике пути к директориям временного сборочного контейнера `/app/...`.
- **Необходимые проверки / источники:** Сборка образа на Apple M1/M2/M3 через `docker build`; вызов `user.Current()` внутри контейнера `FROM scratch` без `/etc/passwd`.
- **Приоритет:** **High**

### 3.1. Упражнение 01: Искажение механизма Toolchain Switching (Go 1.21+) — каталог загрузки
- **Раздел / Упражнение:** Упражнение 1, блок BigTech-интервью.
- **Фрагмент текста:**
  > «Если в файле `go.mod` указана версия `go 1.23.0`, а на вашей машине установлен `go1.21.0`, тулчейн Go автоматически скачает официальный бинарник Go 1.23 **в `$GOPATH/bin`** и прозрачно выполнит сборку на нем.»
- **В чем проблема:** Это техническая неточность в описании архитектуры Toolchain Management (GOTOOLCHAIN).
  Тулчейн Go **никогда не скачивает компиляторы в `$GOPATH/bin`**! Директория `$GOPATH/bin` предназначена исключительно для исполняемых файлов пользовательских утилит, установленных через `go install`. Если бы тулчейн помещал туда свои бинарники, это замусоривало бы пользовательский `$PATH` и вызывало конфликты версий.
  В действительности тулчейны загружаются как стандартные модули в **кэш модулей (`GOMODCACHE`)**:  
  `$GOPATH/pkg/mod/golang.org/toolchain@v0.0.1-go1.23.0.../bin/go`. Управление запуском осуществляется специальной прокси-оберткой `gotoolchain` в рантайме.
- **Необходимые проверки / источники:** Официальная документация Go: [Go Toolchains (`go.dev/doc/toolchain`)](https://go.dev/doc/toolchain), раздел *"Downloads"*.
- **Приоритет:** **Medium**

### 3.2. Упражнение 02: Ложное утверждение о поведении флага `go run -work`
- **Раздел / Упражнение:** Упражнение 2, блок Under the Hood.
- **Фрагмент текста:**
  > «Если запустить команду с флагом отладки `go run -work main.go`, Go выведет путь к временной сборочной директории: `WORK=/tmp/go-build123456789/b001/`. Внутри этого каталога создается скомпилированный бинарник exe/main. **После завершения процесса go run автоматически очищает этот каталог.**»
- **В чем проблема:** Прямое противоречие документации тулчейна.
  Смотрим `go help build`:
  > `-work: print the name of the temporary work directory and do not delete it when exiting.`
  Смысл флага `-work` ровно в том, чтобы **ЗАПРЕТИТЬ** автоматическую очистку каталога `WORK`, давая инженеру возможность зайти в него после завершения команды и исследовать сгенерированные файлы пакетов (`.a`), ассемблерные листинги и скомпонованный бинарник. Без флага `-work` каталог удаляется; с флагом `-work` — сохраняется на диске. Утверждение учит прямо противоположному поведению.
- **Необходимые проверки / источники:** `go help build | grep -A 2 -- "-work"`; запуск `go run -work main.go` и проверка существования папки `/tmp/go-build*` после выхода.
- **Приоритет:** **Medium**

### 3.3. Упражнения 12 & 22: Умолчание о жесткой зависимости флага `-race` от CGO и архитектуры процессора
- **Раздел / Упражнение:** Упражнения 12 и 22, блоки Theory / Pitfalls.
- **Фрагмент текста:**
  > В Ex 12: «Флаг `-race` включает встроенный в компилятор Go детектор гонок ThreadSanitizer...»  
  > В Ex 22: «Скомпилируй программу с race detector: go run -race...»
- **В чем проблема:** Ни в одном из двух упражнений не упомянуто фундаментальное ограничение:
  1. Детектор гонок ThreadSanitizer написан на C++ и скомпилирован в рантайм. Поэтому для работы флага `-race` **в обязательном порядке требуется включенный CGO (`CGO_ENABLED=1`) и установленный в системе C-компилятор (gcc/clang)**!
  2. Если разработчик или CI-скрипт запускает `CGO_ENABLED=0 go test -race ./...` (что часто делают по ошибке, ориентируясь на рекомендации статической сборки), тулчейн немедленно падает:  
     `go: -race requires cgo; enable cgo by setting CGO_ENABLED=1`.
  3. Флаг `-race` **не поддерживается на 32-битных архитектурах** (`linux/386`, `linux/arm`, `windows/386`), а также при обычной кросс-компиляции без настроенного C-кросс-компилятора.
  В учебнике уровня Senior/Staff отсутствие упоминания связи `-race` и `CGO_ENABLED=1` — критический пробел, ведущий к поломкам CI.
- **Необходимые проверки / источники:** `CGO_ENABLED=0 go build -race .`; Go Documentation: *Data Race Detector*.
- **Приоритет:** **Medium**

### 3.4. Упражнение 13: Разрыв практической цепочки — отсутствие Go-кода в задании на `go vet`
- **Раздел / Упражнение:** Упражнение 13 («Статический анализ и проверка антипаттернов через go vet»).
- **Фрагмент задачи и кода:**
  > Задача: «Проверь свой код на ошибки и неправильные паттерны с помощью go vet ./....»

- **В чем проблема:** Упражнение является «пустышкой». Студенту не на чем запустить `go vet`, чтобы своими глазами увидеть реальный диагностический вывод статического анализатора. Задание декларирует обучение `go vet`, но оставляет студента с пустой командой.

### 3.5. Упражнение 15: Недостоверная ментальная модель о невозможности исполнения пользовательских горутин в `init()`
- **Раздел / Упражнение:** Упражнение 15, блок BigTech-интервью.
- **Фрагмент текста:**
  > «Все функции `init()` исполняются строго последовательно в главном системном потоке M0 (Main Thread) **до запуска горутин пользовательского кода**.»
- **В чем проблема:** Формулировка «до запуска горутин пользовательского кода» формирует неверную ментальную модель работы рантайма.
  Планировщик Go инициализируется функцией `schedinit()` **до** вызова инициализаторов пакетов, а функция `runtime.main` сама уже выполняется как горутина. Если разработчик внутри функции `init()` запускает горутину:
  ```go
  func init() {
      go worker()
  }
  ```
  эта пользовательская горутина **будет немедленно запланирована и начнет реально выполняться** на параллельных системных потоках (M), если функция `init()` заблокируется (например, на чтении из канала или сетевом вызове). Горутины пользовательского кода могут исполняться параллельно с `init()`.
- **Необходимые проверки / источники:** Запуск программы с чтением из канала внутри `init()`, куда пишет запущенная в `init()` горутина (`go func() { ch <- "ok" }()`). Исходный код рантайма `src/runtime/proc.go`.
- **Приоритет:** **Medium**

### 3.6. Упражнение 19: Упущена главная коварная ловушка пакета `flag` при разборе булевых аргументов
- **Раздел / Упражнение:** Упражнение 19 («Парсинг аргументов CLI через стандартный пакет flag»), блок Pitfalls.
- **Фрагмент текста:**
  > «Использование двойного тире `--` и одинарного `-`: стандартный пакет `flag` принимает оба варианта (`-name` и `--name`), но не поддерживает короткие объединенные флаги (как `-vcf`).»
- **В чем проблема:** Автор отметил очевидное отсутствие GNU-объединения флагов, но полностью упустил **самую опасную ловушку пакета `flag`**, на которой спотыкаются даже опытные инженеры:
  Для булевых флагов (`flag.BoolVar`, `flag.Bool`) синтаксис со пробелом **НЕ поддерживается**:
  - Если пользователь запустит программу:
    ```bash
    ./app -verbose false
    ```
    пакет `flag` установит переменную `verbose` в **`true` (!)**, а значение `"false"` посчитает **первым позиционным аргументом** (`flag.Args()[0]`)!
  - Единственный способ передать значение `false` булевому флагу в стандартном пакете — использовать знак равенства: `-verbose=false` или `--verbose=false`.
  Это поведение является источником скрытых багов в скриптах автоматизации и должно быть подробно разобрано в разделе Pitfalls.
- **Необходимые проверки / источники:** Документация `go doc flag`: раздел *"Command line flag syntax"*; тест `go run main.go -verbose false`.
- **Приоритет:** **Medium**

### 3.7. Упражнение 04: Неполный алгоритм именования выходного бинарника при сборке
- **Раздел / Упражнение:** Упражнение 4, блок Under the Hood.
- **Фрагмент текста:**
  > «Имя выходного файла берется из директивы `module <name>` в `go.mod` (последний сегмент пути).»
- **В чем проблема:** Это упрощение не соответствует алгоритму компилятора:
  1. Согласно `go help build`, имя выходного файла берется из **последнего компонента пути импорта компилируемого пакета (package import path)**, а не из директивы `module`!
  2. Если в модуле `example.com/platform` собирается подпакет `cmd/worker`:
     ```bash
     go build ./cmd/worker
     ```
     выходной бинарник будет называться **`worker`**, а вовсе не `platform`!
  3. Имя совпадает с именем модуля только в частном случае — когда пакет `main` находится непосредственно в корневом каталоге модуля.
  4. При компиляции списка файлов (`go build main.go utils.go`) бинарник называется по имени **первого файла** (`main`).
- **Необходимые проверки / источники:** `go help build`; сборка субпакета `go build ./cmd/worker`.
- **Приоритет:** **Medium**

### 3.8. Упражнение 24: Конфликт окружения в скрипте CI (`go test -race` vs `CGO_ENABLED=0`)
- **Раздел / Упражнение:** Упражнение 24 («Автоматизационный сборочный скрипт CI/CD пайплайна»).
- **Фрагмент кода `ci.sh`:**
  ```bash
  # 3. Запуск тестов
  go test -v -race -cover ./...

  # 4. Сборка релизного бинарника
  CGO_ENABLED=0 go build -ldflags="-s -w" -o bin/server .
  ```
- **В чем проблема:** На шаге 3 вызывается `go test -race`. Как показано в замечании 3.3, детектор гонок требует `CGO_ENABLED=1`. На шаге 4 вызывается `CGO_ENABLED=0 go build`.
  Если в CI-окружении (например, в Docker-образе сборщика или через глобальный `go env -w CGO_ENABLED=0`) переменная `CGO_ENABLED` выставлена в 0, скрипт аварийно упадет на шаге 3 с ошибкой `go: -race requires cgo`. В профессиональном скрипте CI необходимо явно задавать окружение для каждого шага: `CGO_ENABLED=1 go test -race ...` на шаге тестов и `CGO_ENABLED=0 go build ...` на шаге сборки артефакта.
- **Необходимые проверки / источники:** Запуск `ci.sh` при `export CGO_ENABLED=0`.
- **Приоритет:** **Medium**

### 4.2. Упражнение 03: Некорректная терминология — аллокатор Go назван «бадди-аллокатором (tcmalloc-like)»
- **Раздел / Упражнение:** Упражнение 3, блок BigTech-интервью.
- **Фрагмент:** «многопоточный менеджер памяти с бадди-аллокатором (tcmalloc-like)».
- **В чем проблема:** TCMalloc и производный от него аллокатор рантайма Go (`mcache`/`mcentral`/`mheap`) — это **slab / size-class аллокаторы** с разделенными списками свободных блоков (segregated free lists). ### 4.3. Упражнение 08: Жесткая привязка к `$GOPATH/bin` без учета переменной `GOBIN`

### 4.5. Упражнение 23: Использование устаревшего API обработки сигналов вместо `signal.NotifyContext` (Go 1.16+)
- **Раздел / Упражнение:** Упражнение 23 («Graceful Shutdown»).

- **В чем проблема:** Начиная с Go 1.16 стандартная библиотека предоставляет идиоматичную функцию `signal.NotifyContext`:

## 🧩 5. Важные пробелы и упущения (Important Omissions)

Для главы «Компиляция, сборка и запуск» курса уровня Senior / Staff критически не хватает нескольких фундаментальных тем:

1. **Флаг `-trimpath` (Go 1.13+) — основа воспроизводимых сборок и DevSecOps:**  
   По умолчанию Go зашивает в бинарник абсолютные файловые пути хоста (например, `/home/runner/work/backend/...`). Флаг `-trimpath` удаляет пути файловой системы, гарантируя байт-в-байт воспроизводимость сборок (Reproducible Builds) и защищая внутреннюю инфраструктуру от утечки путей в стек-трейсах паник.
2. **Билд-теги и ограничения компиляции `//go:build` (Go 1.17+):**  
   В главе бегло упомянуты суффиксы файлов (`file_linux.go`), но полностью отсутствуют упражнения на официальные директивы `//go:build`:
   - Условная сборка по тегам: `//go:build integration`, `//go:build pro`;
   - Логические выражения: `//go:build linux && !cgo`, `//go:build amd64 || arm64`.  
   Это ключевой механизм изоляции платформенного и тестового кода в enterprise-проектах.
3. **Механика сборочного кэша (`GOCACHE`, `go clean -cache`, `go build -a`):**  
   Go славится скоростью компиляции благодаря content-addressed кэшированию. Нет упражнений на инспекцию `go env GOCACHE`, понимание инвалидации кэша и принудительную пересборку всех пакетов через флаг `-a`.
4. **Интроспекция компилятора через `-gcflags` (Escape-анализ и ассемблер):**  
   Senior-инженеру необходимо уметь инспектировать решения компилятора:
   - `-gcflags="-m"` — отчет об escape-анализе (утечки в кучу) и инлайнинге функций;
   - `-gcflags="-S"` — вывод ассемблерного листинга Plan 9;
   - `-gcflags="-N -l"` — отключение оптимизаций для предсказуемой отладки в Delve.
5. **Чтение метаданных сборки без `-ldflags` через `runtime/debug.ReadBuildInfo()` (Go 1.18+):**  
   В Упражнении 21 показан только старый метод с `-ldflags -X`. Начиная с Go 1.18 тулчейн автоматически вшивает Git-хэш коммита (`vcs.revision`), дату (`vcs.time`) и статус изменений (`vcs.modified=true`). Программа может прочитать их в рантайме без ручной передачи флагов сборки.
6. **Утилиты инспекции бинарников (`go version -m`, `go tool nm`, `go tool objdump`):**  
   Как узнать, с какими зависимостями и флагами скомпилирован чужой бинарник? Команда `go version -m ./app` выводит полную спецификацию `go.mod` прямо из скомпилированного файла. Утилиты `nm` и `objdump` позволяют исследовать символы и машинный код.
7. **Статическая сеть на Linux без CGO (`-tags 'netgo,osusergo'`):**  
   Как заставить пакет `net` использовать чистый Go DNS-резолвер при `CGO_ENABLED=1`.
