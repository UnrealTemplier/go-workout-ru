### 1.1. Упражнение 42: Фатальная ошибка компиляции в эталонном решении (невозможность каста `string` к `uintptr` и неиспользуемая переменная)
* **Раздел / Упражнение:** Упражнение 42 «Эксперимент с переаллокацией: наблюдение за изменением &s[0] при росте с 2 до 10 элементов» (`dist/008-slaysy.html` [L4420-4436](file:///home/ut/work/go-workout/dist/008-slaysy.html#L4420-L4436), `builder/chapter8_data.json` [L996](file:///home/ut/work/go-workout/builder/chapter8_data.json#L996)).
* **Фрагмент кода решения:**
  ```go
  func main() {
      s := make([]int, 0, 2)
      var prevAddr uintptr

      for i := 1; i <= 10; i++ {
          s = append(s, i)
          currAddr := uintptr(fmt.Sprintf("%p", &s[0])[2:]) // адрес первого элемента
          _ = currAddr

          reallocMark := ""
          if i == 1 || cap(s) != len(s)-1 {
              // Отслеживаем смену адреса
          }
          fmt.Printf("Итерация #%2d -> Адрес &s[0]: %p | len: %2d | cap: %2d %s\n",
              i, &s[0], len(s), cap(s), reallocMark)
      }
  }
  ```
* **В чем проблема:**
  Код **не компилируется ни в одной версии компилятора Go**. Попытка запуска `go run .` падает с фатальными ошибками проверки типов:
  ```text
  ./main.go:7:6: declared and not used: prevAddr
  ./main.go:11:47: cannot convert fmt.Sprintf("%p", &s[0])[2:] (value of type string) to type uintptr
  ```
  1. **Невозможное приведение типов:** Согласно Спецификации языка Go (*Conversions*), строковый срез `string` невозможно напрямую привести к целочисленному типу `uintptr` через выражение `uintptr(...)`. Строки в Go конвертируются только в `[]byte`, `[]rune` или производные строковые типы. Для парсинга шестнадцатеричной строки потребовался бы `strconv.ParseUint`, а для прямого взятия целочисленного адреса в Go используется `uintptr(unsafe.Pointer(&s[0]))`.
  2. **Неиспользуемая переменная:** Переменная `var prevAddr uintptr` объявлена на строке 7 и нигде не используется, что вызывает безусловную ошибку компилятора Go `declared and not used`.
  3. **Сфабрикованный вывод:** В блоке терминала указан готовый вывод с пометками `(СМЕНА АДРЕСА!)`, тогда как авторский код никогда не мог быть запущен и скомпилирован.
* **Необходимые проверки / источники:** Запуск `go run main.go`; Спецификация языка Go (разделы *Conversions*, *Declarations and scope rules*).
* **Приоритет:** **High**

### 1.2. Упражнение 18: Паразитная строка `append(s, 0)` переаллоцирует срез (`cap = 10` вместо 5) и опровергает собственную теорию
* **Раздел / Упражнение:** Упражнение 18 «Удаление элемента по индексу через трюк со слиянием append(s[:i], s[i+1:]...)» (`dist/008-slaysy.html` [L2531-2542](file:///home/ut/work/go-workout/dist/008-slaysy.html#L2531-L2542), `builder/chapter8_data.json` [L420](file:///home/ut/work/go-workout/builder/chapter8_data.json#L420)).
* **Фрагмент кода решения и ожидаемого вывода:**
  ```go
  func main() {
      s := []int{1, 2, 3, 4, 5}
      fmt.Printf("До удаления:    %v | len = %d, cap = %d\n", s, len(s), cap(s))

      indexToRemove := 2 // Удаляем число 3

      // Трюк с append:
      s = append(s, 0)[:len(s)] // демонстрация
      s = append(s[:indexToRemove], s[indexToRemove+1:]...)

      fmt.Printf("После удаления: %v | len = %d, cap = %d\n", s, len(s), cap(s))
  }
  ```
  Заявленный вывод в задачнике:
  ```bash
  # До удаления:    [1 2 3 4 5] | len = 5, cap = 5
  # После удаления: [1 2 4 5] | len = 4, cap = 5
  ```
* **В чем проблема:**
  1. В код решения случайно попала черновая строка `s = append(s, 0)[:len(s)] // демонстрация`.
  2. Исходный срез `s` имел `len = 5, cap = 5`. Вызов `append(s, 0)` выходит за пределы емкости 5 и **вызывает полную переаллокацию в куче с удвоением емкости до `cap = 10`**!

  4. В результате последующего удаления `append(s[:2], s[3:]...)` реальный запуск программы выводит:
     ```text
     После удаления: [1 2 4 5] | len = 4, cap = 10
     ```
  5. **Противоречие теории:** В разделе *Under the hood* автор пишет:  
     *«Элементы 4, 5 сдвигаются на 1 позицию влево в том же базовом массиве. Память не перевыделяется.»*  
     Но из-за паразитной строки память **уже была перевыделена**, базовый массив сменился, а заявленный в терминале `cap = 5` сфабрикован вручную и не совпадает с реальной работой кода (`cap = 10`).
* **Необходимые проверки / источники:** Запуск `go run main.go`; инспекция емкости `cap(s)`.

* **Раздел / Упражнение:**  
  1. Упражнение 50 «Ловушка утечки памяти (Memory Leak) при взятии маленького среза big[:2]» (`dist/008-slaysy.html` [L5085-5120](file:///home/ut/work/go-workout/dist/008-slaysy.html#L5085-L5120), `builder/chapter8_data.json` [L1172](file:///home/ut/work/go-workout/builder/chapter8_data.json#L1172)).

  ```go
  func main() {

      _ = getSmallSafe()

      runtime.GC()

  ```
  Заявленный вывод в Упр. 50:
  ```bash

  # Память после getSmallLeaky: 7936 КБ (8 МБ удерживаются в памяти!)
  ```
  Заявленный вывод в Упр. 58:
  ```bash
  # Память после SafeTail:  120 КБ (1 МБ освобожден!)
  # Память после LeakyTail: 1144 КБ (1 МБ заблокирован в памяти!)
  ```
* **В чем проблема:**
  1. Код **не удерживает ссылку на возвращаемый срез**! Результат вызова `_ = getSmallLeaky()` и `_ = LeakyTail()` немедленно отбрасывается в пустой идентификатор `_`.

  6. Чтобы действительно продемонстрировать утечку памяти, срез **обязан сохраняться в живую переменную**, достижимую после вызова `runtime.GC()` (например, через `keep := getSmallLeaky()` с последующим `runtime.KeepAlive(keep)` или печатью `keep[0]`).

### 1.5. Упражнение 66: Скрытая порча памяти (Memory Corruption) и антипаттерн в `Union(s1, s2)` через `range append(s1, s2...)`
* **Раздел / Упражнение:** Упражнение 66 «Объединение двух срезов Union(s1, s2) без дубликатов с сохранением порядка» (`dist/008-slaysy.html` [L6423-6435](file:///home/ut/work/go-workout/dist/008-slaysy.html#L6423-L6435), `builder/chapter8_data.json` [L1506](file:///home/ut/work/go-workout/builder/chapter8_data.json#L1506)).
* **Фрагмент кода решения:**
  ```go
  func Union(s1, s2 []int) []int {
      seen := make(map[int]struct{})
      result := make([]int, 0, len(s1)+len(s2))

      for _, v := range append(s1, s2...) {
          if _, exists := seen[v]; !exists {
              seen[v] = struct{}{}
              result = append(result, v)
          }
      }
      return result
  }
  ```
* **В чем проблема:**
  1. **Скрытая мутация данных вызывающей стороны (Side Effect):** Конструкция `range append(s1, s2...)` крайне опасна. Если срез `s1` имеет запас емкости (`cap(s1) >= len(s1) + len(s2)`), вызов `append(s1, s2...)` **НЕ аллоцирует новый массив**, а перезаписывает элементы базового массива `s1` за пределами его длины!
  2. **Тест на порчу данных:**
     ```go
     a := make([]int, 2, 4)
     a[0], a[1] = 1, 2
     b := []int{3, 4}
     _ = Union(a, b)
     // Память a за пределами длины повреждена: a[:4] теперь содержит [1, 2, 3, 4]!
     ```
  3. **Лишняя аллокация в куче:** Если у `s1` нет запаса емкости, `append(s1, s2...)` создает временный срез размером `N + M` в куче исключительно для того, чтобы пройти по нему циклом, создавая лишнюю нагрузку на GC.
  4. **Идиоматичное решение:** Два последовательных цикла `for _, v := range s1` и `for _, v := range s2`, либо использование `slices.Concat` (Go 1.22+).
* **Необходимые проверки / источники:** Запуск теста со срезом `a := make([]int, 2, 4)`; замер аллокаций через `testing.B` / `-benchmem`.
* **Приоритет:** **High**

### 1.6. Файлы генераторов `gen_ch8_p1..3.py`: Неэкранированные `\n` ломают компиляцию 56 из 74 упражнений
* **Раздел / Упражнение:** Исходные Python-скрипты генерации `builder/gen_ch8_p1.py`, `builder/gen_ch8_p2.py`, `builder/gen_ch8_p3.py`.
* **Фрагмент кода:**
  В тройных строках Python:
  ```python
  "code": """package main

  import "fmt"

  func main() {
      fmt.Printf("Массив arr:       %v\n", arr)
  }"""
  ```
* **В чем проблема:**
  1. В файлах `gen_ch8_p1.py`, `p2.py`, `p3.py` строковые блоки заданы как обычные тройные кавычки `"""..."""` без префикса `r` (raw string) и без экранирования `\\n`.
  2. Интерпретатор Python при импорте превращает комбинацию `\` и `n` в байт перевода строки (ASCII 10).

### 1.7. Упражнение 22: Скрытая порча памяти вызывающего кода в `InsertShift` при наличии запасной емкости среза
* **Раздел / Упражнение:** Упражнение 22 «Вставка элемента в середину среза (`InsertShift`)» (`builder/chapter8_data.json`, блок exercise #22; `dist/008-slaysy.html`).
* **Фрагмент кода решения:**
  ```go
  func InsertShift(s []int, index, value int) []int {
      s = append(s, 0)              // расширяем длину на 1
      copy(s[index+1:], s[index:]) // сдвигаем хвост вправо
      s[index] = value
      return s
  }
  ```
* **В чем проблема:**
  1. **Скрытая мутация базового массива вызывающего кода:** Если переданный срез `s` имеет запасную ёмкость (`cap(s) > len(s)`), вызов `append(s, 0)` **не выделяет новый массив**. Вместо этого он записывает `0` прямо в ячейку базового массива, следующую за `len(s)`.
  2. **Конкретный пример порчи данных:**
     ```go
     b := make([]int, 5, 10) // cap > len!
     copy(b, []int{10, 20, 30, 40, 50})
     result := InsertShift(b, 2, 99)
     // result  → [10 20 99 30 40 50]  (правильно)
     // b[:6]   → [10 20 99 30 40 50]  (ПОРЧА! базовый массив b изменён)
     // b       → [10 20 99 30 40]     (срез b видит «старую» длину, данные за ней повреждены)
     ```
  3. **Что написано в теории упражнения:** Раздел «Подводные камни» упоминает лишь «лишнюю аллокацию». Фактический сайд-эффект мутации базового массива вызывающего кода полностью отсутствует в объяснении.
  4. **Идиоматичное безопасное решение:** Использование `slices.Insert` (Go 1.21+) или клонирование перед вставкой `s = slices.Clone(s)`.
* **Необходимые проверки / источники:** Запуск теста `b := make([]int, 5, 10); InsertShift(b, 2, 99)` и проверка `b[:cap(b)]`; аналогичная проблема задокументирована в §1.5 (Упр. 66) данного брифа.
* **Приоритет:** **High**

### 2.2. Упражнение 17: Искажение концепции `zerobase` — отображение `Data: 0x0` для пустого среза `[]int{}` и ошибка в версии deprecation `reflect.SliceHeader`
* **Раздел / Упражнение:** Упражнение 17 «Утилита InspectSlice: глубокая печать SliceHeader» (`dist/008-slaysy.html` [L2425-2465](file:///home/ut/work/go-workout/dist/008-slaysy.html#L2425-L2465), `builder/chapter8_data.json` [L398](file:///home/ut/work/go-workout/builder/chapter8_data.json#L398)).
* **Фрагмент кода и вывода:**
  ```go
  func InspectSlice(name string, s []int) {
      var ptr uintptr
      if len(s) > 0 {
          ptr = uintptr(unsafe.Pointer(&s[0]))
      } else if cap(s) > 0 {
          ptr = uintptr(unsafe.Pointer(unsafe.SliceData(s)))
      }
      fmt.Printf("[%s] Data: 0x%x | Len: %d | Cap: %d | isNil: %t | Val: %v\n",
          name, ptr, len(s), cap(s), s == nil, s)
  }
  ```
  Вывод в терминале:
  ```bash
  # [sEmpty] Data: 0x0 | Len: 0 | Cap: 0 | isNil: false | Val: []
  ```
* **В чем проблема:**  
  1. Из-за условия `else if cap(s) > 0` пустой срез `sEmpty := []int{}` (у которого `len == 0` и `cap == 0`) вообще не попадает ни в одну ветку, и `ptr` остается равным 0 (`0x0`).

  3. На самом деле в рантайме Go пустой срез `[]int{}` имеет **ненулевой указатель данных**, указывающий на глобальный маркер `runtime.zerobase` (например, `0x593fc0`). Именно поэтому `sEmpty != nil`.
  4. Если бы автор написал типобезопасный `ptr = uintptr(unsafe.Pointer(unsafe.SliceData(s)))`, программа наглядно показала бы реальный ненулевой адрес `zerobase`.
  5. В блоке *BigTech Interview* утверждается: *«reflect.SliceHeader объявлен устаревшим (deprecated) в Go 1.21»*. Это неверно: тип был официально объявлен deprecated **в Go 1.20** (одновременно с появлением `unsafe.SliceData`).
* **Необходимые проверки / источники:** Запуск `unsafe.SliceData([]int{})`; Go 1.20 Release Notes.
* **Приоритет:** **Medium**

  1. Функция `slices.Compact` удаляет **только смежные** (соседние) дубликаты, аналогично Unix-утилите `uniq`. Она **не является** функцией глобальной дедупликации.
  2. Для несортированного среза: `slices.Compact([]int{1, 2, 1, 3, 2})` вернёт `[1 2 1 3 2]` — без изменений!
  3. В данном упражнении результат корректен **только потому**, что перед `Compact` выполняется `slices.Sort`. Комментарий `(уникальные элементы!)` создаёт ложное впечатление, что `Compact` сам выполняет глобальную дедупликацию, а не что уникальность обеспечивает предшествующая сортировка.
  4. Теоретический текст упражнения правильно говорит «смежных», но финальный комментарий терминала противоречит этой точности и формирует неверную ментальную модель.
* **Необходимые проверки / источники:** Документация `slices.Compact`; запуск `slices.Compact([]int{1, 2, 1, 3, 2})`.
* **Приоритет:** **Low**

### 3.7. Упражнение 8: Упрощённое утверждение об оптимизации `append(s1, s2...)` в одну операцию `memmove`
* **Раздел / Упражнение:** Упражнение 8, раздел теории «Под капотом» (`dist/008-slaysy.html`, `builder/chapter8_data.json` блок #8).
* **Фрагмент:** *«Компилятор оптимизирует `append(s1, s2...)` в одну операцию `runtime.memmove`»*
* **В чем проблема:**
  1. Утверждение верно только в **одном** частном случае: когда ёмкость `s1` достаточна для вмещения всех элементов `s2` (`cap(s1) >= len(s1)+len(s2)`). В этом случае рантайм действительно выполнит один `memmove`.
  2. Если ёмкости недостаточно, `append` сначала вызывает `runtime.growslice` (которая вызывает `runtime.mallocgc` для выделения нового буфера), и лишь затем — `memmove`. Это **три отдельные операции**, а не одна.
  3. Формулировка «в одну операцию» является обобщением, некорректным для случая реаллокации, — а именно этот случай является типичным при конкатенации срезов.
* **Необходимые проверки / источники:** `src/runtime/slice.go`, функция `growslice`; `go tool compile -S` для инспекции сгенерированных инструкций.
* **Приоритет:** **Low**

### 3.8. Упражнение 25: Чрезмерно упрощённое описание работы `runtime.memmove` (`REP MOVSQ` + `dst < src`)
* **Раздел / Упражнение:** Упражнение 25, раздел теории «Под капотом» (`dist/008-slaysy.html`, `builder/chapter8_data.json` блок #25).
* **Фрагмент:** *«`runtime.memmove` выполняет векторные инструкции `REP MOVSQ` с проверкой `dst < src`»*
* **В чем проблема:**
  1. Реализация `runtime.memmove` в Go (Plan 9 Assembly, `src/runtime/memmove_amd64.s`) является многоветвевой и зависит от размера копируемого блока и выравнивания:
     - малые размеры (1–16 байт): прямые `MOV` инструкции;
     - средние размеры: `SSE2` / `AVX` регистры (`MOVUPS`, `VMOVDQU`);
     - крупные размеры: `REP MOVSQ` или векторные цепочки;
     - при перекрытии регионов: обратное копирование (`std; rep movsq; cld`).
  2. Утверждение «`REP MOVSQ` с проверкой `dst < src`» описывает только один из путей исполнения. Реальный критерий выбора — не только направление, но и размер блока, выравнивание, наличие/отсутствие перекрытия.
  3. Описание `dst < src` относится к логике **определения направления копирования при перекрытии** (а не к `REP MOVSQ` как таковой), что создаёт путаницу в объяснении.
* **Необходимые проверки / источники:** `src/runtime/memmove_amd64.s`; `go tool objdump`.
* **Приоритет:** **Low**

## 💡 5. Критические пробелы и упущенные темы современного Go (Omissions)

1. **Встроенная функция `clear(slice)` (Go 1.21+):**  
   В языке появился важнейший встроенный примитив `clear(s)`, зануляющий элементы среза в диапазоне его длины без изменения емкости. В главе нет ни одного практического упражнения на работу с `clear()`.
2. **Функция `slices.Concat` (Go 1.22+):**  
   Официальный безопасный способ объединения срезов, исключающий сайд-эффекты и порчу памяти, возникающие при `append(s1, s2...)`.
3. **Конкурентность и гонки данных (Concurrency & Data Races):**  
   Срезы в Go не являются потокобезопасными. Параллельный `append` из нескольких горутин без мьютекса приводит к потере элементов и тихой порче памяти. Тема потокобезопасности срезов полностью опущена.
4. **Конструирование среза из сырого указателя `unsafe.Slice` (Go 1.17+):**  
   Для системного программирования и CGO функция `unsafe.Slice((*T)(ptr), len)` является современным стандартным способом создания срезов, заменившим опасные манипуляции с дескрипторами.
