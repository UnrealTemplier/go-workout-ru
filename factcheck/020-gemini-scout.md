### 2.2. Упражнения 48 и 110: Ложное утверждение о перехвате `Unlock()` и `RUnlock()` через `recover()` — в Go это невосстановимый фатальный сбой рантайма (`fatal error`)
- **Раздел / Упражнение:** 
  - Упражнение 48 (`builder/gen_ch20_p2.py`): *«Ловушки Mutex: паника при Unlock незаблокированного мьютекса и дедлок при повторном Lock»*
  - Упражнение 110 (`builder/gen_ch20_p3.py`, `bigtech_interview`): *«Многопоточный кэш с раздельными блокировками RLock и Lock»*
- **Фрагмент кода и текста (Упр. 48):**
  ```go
  func demoUnlockPanic() {
      var mu sync.Mutex

      defer func() {
          if r := recover(); r != nil {
              fmt.Printf("[1. ПЕРЕХВАЧЕНА ПАНИКА]: %v\n", r)
          }
      }()

      fmt.Println("Попытка вызвать Unlock() без предварительного Lock()...")
      mu.Unlock() // Паника: sync: unlock of unlocked mutex
  }
  ```
  И сфабрикованный терминальный блок:
  ```bash
  # Вывод:
  # Попытка вызвать Unlock() без предварительного Lock()...
  # [1. ПЕРЕХВАЧЕНА ПАНИКА]: sync: unlock of unlocked mutex
  # 2. Первый Lock() успешно захвачен.
  # 3. Попытка повторного Lock() вернула: false (мьютекс уже занят этой же горутиной)
  # 4. Мьютекс освобожден.
  ```
  **В Упр. 110 (`bigtech_interview`):**
  > «**Вопрос:** Что произойдет, если горутина вызовет RUnlock() дважды?  
  > **Ответ:** Произойдет паника `panic: sync: RUnlock of unlocked RWMutex`, так как внутренний счетчик читателей станет отрицательным.»
- **В чем проблема:** Фундаментальное искажение архитектуры надежности и обработки ошибок в Go:
  1. В рантайме Go ошибочный вызов `Unlock()` на незаблокированном `sync.Mutex` вызывает **не панику**, а невосстановимую фатальную ошибку рантайма:
     ```text
     fatal error: sync: unlock of unlocked mutex
     goroutine 1 [running]:
     internal/sync.fatal(...)
     exit status 2
     ```
  2. Аналогично, двойной `RUnlock()` на `sync.RWMutex` вызывает:
     ```text
     fatal error: sync: RUnlock of unlocked RWMutex
     goroutine 1 [running]:
     sync.fatal(...)
     exit status 2
     ```
  3. Внутренняя функция `fatal()` в пакете `sync` вызывает `runtime.throw()`. Фатальные ошибки рантайма (fatal runtime errors) в Go принципиально **НЕ ПЕРЕХВАТЫВАЮТСЯ через `recover()`**! Они немедленно печатают стектрейс всех горутин и аварийно завершают процесс операционной системы с кодом 2.
  4. Следовательно, в Упр. 48:
     - Блок `recover()` никогда не срабатывает.
     - Строка `[1. ПЕРЕХВАЧЕНА ПАНИКА]` никогда не печатается.
     - Вторая функция в `main` (`demoDoubleLockDeadlock`) никогда не вызывается.
     - Вывод в блоке «Терминал» полностью вымышлен автором.
  5. Студенту прививается опаснейшая иллюзия, будто баги блокировок и двойные `Unlock` можно изолировать в HTTP middleware через `recover()`. На собеседованиях Senior Go разработчиков вопрос *"В чем разница между panic и fatal error при ошибках sync.Mutex"* является классическим фильтром квалификации.
- **Необходимые проверки / источники:** Исходный код `src/sync/mutex.go` (`fatal("sync: unlock of unlocked mutex")`), `src/sync/rwmutex.go` (`fatal("sync: RUnlock of unlocked RWMutex")`). Запуск тестового файла с `recover()` и `mu.Unlock()`.

### 2.5. Упражнение 12: Грубая фактическая ошибка — утверждение, что `sync.WaitGroup` якобы «реализует интерфейс sync.Locker»
- **Раздел / Упражнение:** Упражнение 12 (`builder/gen_ch20_p1.py`, поле `under_the_hood`).
- **Фрагмент текста:**
  > «`sync.WaitGroup` реализует интерфейс `sync.Locker` и содержит поле `noCopy`, которое статически проверяется утилитой `go vet`.»
- **В чем проблема:** 
  1. Интерфейс `sync.Locker` в стандартной библиотеке Go определен предельно строго:
     ```go
     type Locker interface {
         Lock()
         Unlock()
     }
     ```
  2. Структура `sync.WaitGroup` **НЕ ИМЕЕТ** методов `Lock()` и `Unlock()`! Её публичные методы — `Add(delta int)`, `Done()` и `Wait()`.
  3. Попытка присвоить `&sync.WaitGroup{}` интерфейсу `sync.Locker` не компилируется компилятором Go:
     ```text
     cannot use &sync.WaitGroup{} as sync.Locker value in variable declaration:
     *sync.WaitGroup does not implement sync.Locker (missing method Lock)
     ```
  4. Механика поля `noCopy` устроена иначе: фиктивный неэкспортируемый тип `type noCopy struct{}` реализует методы `Lock()` и `Unlock()`, являясь индикатором для анализатора `copylocks` в `go vet`. Сам `sync.WaitGroup` интерфейс `sync.Locker` не реализует ни прямо, ни косвенно.
- **Необходимые проверки / источники:** `src/sync/mutex.go` (`type Locker`), `src/sync/waitgroup.go`. Попытка компиляции `var _ sync.Locker = &sync.WaitGroup{}`.

### 3.1. Упражнения 11, 18, 21: Семантика переменной цикла в Go 1.22+: код Упр. 18 не воспроизводит баг, вывод первой половины скрыт в терминале
- **Раздел / Упражнение:** Упражнения 11, 18, 21 (`builder/gen_ch20_p1.py`).
- **Фрагмент кода (Упр. 18):**
  ```go
  func main() {
      var wg sync.WaitGroup

      fmt.Println("--- Демонстрация проблемы замыкания ---")
      for i := 0; i < 5; i++ {
          wg.Add(1)
          // ОШИБКА: захват i по ссылке (в коде до Go 1.22 все выведут 5)
          go func() {
              defer wg.Done()
              fmt.Printf("Небезопасный захват: %d\n", i)
          }()
      }
      wg.Wait()

      fmt.Println("\n--- Исправление с явной передачей аргумента ---")
      for i := 0; i < 5; i++ {
          wg.Add(1)
          go func(safeVal int) {
              defer wg.Done()
              fmt.Printf("Безопасная копия: %d\n", safeVal)
          }(i)
      }
      wg.Wait()
  }
  ```
  И блок терминала:
  ```bash
  go run main.go
  # Вывод:
  # --- Исправление с явной передачей аргумента ---
  # Безопасная копия: 0
  # Безопасная копия: 1
  # Безопасная копия: 2
  # Безопасная копия: 3
  # Безопасная копия: 4
  ```
- **В чем проблема:** 
  1. Начиная с Go 1.22, семантика переменных цикла `for` изменилась фундаментально: переменные цикла создаются заново на каждой итерации (Per-iteration loop variable scoping).
  2. Запущенный на современном Go код первого цикла **НЕ ВЫВОДИТ ВСЕ 5**! Он выводит обычные числа от 0 до 4 в произвольном порядке, как и исправленный цикл! Детектор гонок (`-race`) на этом коде также молчит.
  3. Автор задачи увидел, что на современном Go первой ошибки не происходит, и решил проблему просто: **вырезал весь вывод первого цикла из блока терминала**! В терминале отображается только вывод второй половины (`Безопасная копия:`).
  4. Учащийся, запустив код на Go 1.22+, увидит идентичный вывод для обоих циклов и не поймет, в чем же состояла историческая ошибка.
  5. Для воспроизведения бага замыкания на современных версиях Go необходимо объявлять переменную до цикла: `var i int; for i = 0; i < 5; i++ { ... }`.
- **Необходимые проверки / источники:** Go 1.22 Release Notes: *Loop variable scoping*. Запуск теста на компиляторе Go 1.22+.

### 3.2. Упражнения 89 vs 57: Искажение истории рантайма на 10 мажорных релизов — Starvation Mode в `sync.Mutex` появился в Go 1.9+, а не в Go 1.19+

### 3.3. Упражнение 89: Некорректная ментальная модель — двухпоточная симуляция "Priority Inversion" не является инверсией приоритетов
- **Раздел / Упражнение:** Упражнение 89 (`builder/gen_ch20_p3.py`).
- **Фрагмент задачи и кода:**
  > Задача: *«Напиши программу с "priority inversion" (симуляция): высокоприоритетная горутина ждёт мьютекс, захваченный низкоприоритетной.»*
  В коде решения запускаются всего две горутины: первая блокирует мьютекс и спит 30 мс, вторая пытается захватить мьютекс и ждет.
- **В чем проблема:** 
  1. Классическая инверсия приоритетов (Priority Inversion, как на марсоходе Mars Pathfinder) в Computer Science принципиально требует **трех** участников:
     - Низкоприоритетная задача $L$ захватывает ресурс $R$.
     - Высокоприоритетная задача $H$ хочет захватить ресурс $R$ и блокируется.
     - **Среднеприоритетная задача $M$**, которой не нужен ресурс $R$, вытесняет $L$ по процессору. Из-за этого $L$ не может завершить работу и отдать ресурс, в результате чего $M$ косвенно блокирует критически важную задачу $H$.
  2. Ситуация, где одна задача держит мьютекс, а вторая ждет — это обычное взаимное исключение (Mutual Exclusion / Contention), а не инверсия приоритетов. В коде Упр. 89 среднеприоритетной горутины нет вообще.
  3. Учебник преподает искаженное понимание системного термина.
- **Необходимые проверки / источники:** Silberschatz, Galvin — *Operating System Concepts* (Priority Inversion).

### 3.5. Упражнение 54: Неточное утверждение о жизненном цикле объектов в `sync.Pool`
- **Раздел / Упражнение:** Упражнение 54 (`builder/gen_ch20_p2.py`, поле `bigtech_interview`).
- **Фрагмент текста:**
  > «Начиная с Go 1.13, **объекты живут минимум два полных цикла GC** (механизм `poolVictim`).»
- **В чем проблема:** 
  1. В механизме `poolVictim`, внедренном в Go 1.13, при запуске фазы Stop-The-World сборщика мусора объекты из `poolVictim` уничтожаются, а текущие объекты из `poolLocal` перемещаются в `poolVictim`.
  2. Если объект был помещен в пул незадолго до начала первого цикла GC, он перемещается в `victim`, а при следующем цикле GC (если не был извлечен через `Get()`) — удаляется.
  3. Таким образом, невостребованный объект живет **не более** двух циклов GC (а точнее — от одного до двух циклов GC).
  4. Формулировка *«живут минимум два полных цикла GC»* переворачивает математическую границу с ног на голову: объект никак не может гарантированно пережить два полных цикла GC без вызова `Get()`.
- **Необходимые проверки / источники:** `src/sync/pool.go` (комментарии к `poolVictim` и `poolCleanup()`).

## 🧩 5. Важные пробелы и упущения (Important Omissions)

1. **Полное отсутствие примитивов `sync.OnceFunc`, `sync.OnceValue`, `sync.OnceValues` (Go 1.21+)**:
   - При наличии рекордных **8 упражнений на `sync.Once`** в главе ни разу не упомянуты современные функции-хелперы из Go 1.21:
     - `sync.OnceValue[T](f func() T) func() T` — идиоматичный потокобезопасный синглтон с возвращаемым значением.
     - `sync.OnceValues[T, error](f func() (T, error)) func() (T, error)` — синглтон с возвратом значения и ошибки.
   - В современном промышленном Go ручной вызов `once.Do` для инициализации значений считается устаревшим бойлерплейтом по сравнению с `sync.OnceValue`.
2. **Отсутствие методов `Swap`, `CompareAndSwap`, `CompareAndDelete` в упражнениях на `sync.Map` (Go 1.20+)**:
   - В практических упражнениях на `sync.Map` используются только старые методы (`Load`, `Store`, `Delete`, `LoadOrStore`). Современные методы атомарной замены и условного удаления упомянуты лишь мельком в вопросе к собеседованию.
3. **Отсутствие контраста семантики `defer` при `os.Exit()` vs `runtime.Goexit()` vs `main()` return**:
   - В главе подробно изучается `runtime.Goexit()` (Упр. 47) и `main()` exit, но не показано принципиальное отличие от `os.Exit()`: при вызове `os.Exit()` рантайм Go немедленно завершает процесс без раскрутки стека и **не выполняет ни одного defer** ни в одной горутине.
4. **Отсутствие демонстрации паники `sync: WaitGroup misuse: Add called concurrently with Wait`**:
   - Паника отрицательного счетчика показана в Упр. 14 и 41, но критическая ошибка параллельного вызова `wg.Add()` во время выполнения `wg.Wait()` (когда счетчик уже стал равен 0) не продемонстрирована на практике.
5. **Отсутствие идиоматичного шаблона Semaphore на буферизованном канале `make(chan struct{}, N)`**:
   - В Главе 20 при рассмотрении лимитирования параллелизма в Упр. 121 автор создал наколенную структуру `LimitedErrGroup`, но не показал классический, общепринятый в экосистеме Go идиоматичный паттерн семафора на буферизованном канале.
