### 2.2. Упражнение 22: Состояние гонки данных (Data Race) на счетчике `h.dropped++` в многопоточном ядре
- **Раздел / Упражнение:** Упражнение 22, метод `Handle` структуры `AsyncHandler` ([`builder/chapter19_data.json`](file:///home/ut/work/go-workout/builder/chapter19_data.json)).
- **Фрагмент кода решения:**
  ```go
  func (h *AsyncHandler) Handle(ctx context.Context, r slog.Record) error {
      // Клонируем запись для безопасной передачи между горутинами
      recCopy := r.Clone()

      select {
      case h.queue <- recCopy:
          return nil
      default:
          // Буфер переполнен (Drop to protect throughput)
          h.dropped++ // <-- DATA RACE! Незащищенная мутация разделяемого состояния
          return nil
      }
  }
  ```
- **В чем проблема:**
  1. Согласно спецификации и контракту пакета `log/slog` (документация интерфейса `slog.Handler`):
     > *"A Handler may be called simultaneously from multiple goroutines..."*
     Метод `Handle` обязан быть строго потокобезопасным (`thread-safe`). Логгеры в реальных бэкендах вызываются параллельно из десятков тысяч горутин, обрабатывающих HTTP/gRPC запросы.
  2. Поле `h.dropped int64` является обычным целочисленным полем структуры, не защищенным мьютексом. Операция `h.dropped++` в Go не является атомарной (на ассемблере x86-64/ARM64 это последовательность `MOV` -> `ADD` -> `MOV`).
  3. При возникновении нагрузки, когда очередь `h.queue` заполняется (именно в этот момент и срабатывает ветка `default`), параллельные горутины начинают одновременно выполнять `h.dropped++`. Детектор гонок Go (`go run -race`) фиксирует критический **DATA RACE**, что в боевых условиях ведет к потере подсчета отброшенных логов и повреждению памяти на 32-битных архитектурах.
  4. Для счетчика отброшенных сообщений необходимо использовать атомарный примитив `atomic.Int64` (из пакета `sync/atomic`) либо `atomic.AddInt64(&h.dropped, 1)`.
- **Необходимые проверки / источники:** `go run -race` при одновременном вызове `logger.Info` из 10 горутин при заполненном буфере; Документация `log/slog.Handler`.
- **Приоритет:** **High**

### 2.3. Упражнения 12 и 19: Нарушение контракта `slog.Handler` — незаметная потеря контекста при вызовах `logger.With` и `logger.WithGroup`
- **Раздел / Упражнение:** 
  - Упражнение 12 («Кастомный slog.Handler для автоматического извлечения контекстных полей»), [`builder/chapter19_data.json`](file:///home/ut/work/go-workout/builder/chapter19_data.json)
  - Упражнение 19 («Интеграция slog с OpenTelemetry: Trace ID и Span ID корреляция»), [`builder/chapter19_data.json`](file:///home/ut/work/go-workout/builder/chapter19_data.json)
- **Фрагмент кода решений:**
  ```go
  // Упражнение 12:
  type ContextInjectHandler struct {
      slog.Handler // Встраивание (embedding) базового хендлера
  }

  func (h *ContextInjectHandler) Handle(ctx context.Context, r slog.Record) error {
      if reqID, ok := ctx.Value(CtxRequestID).(string); ok && reqID != "" {
          r.AddAttrs(slog.String("request_id", reqID))
      }
      return h.Handler.Handle(ctx, r)
  }
  // Методы WithAttrs и WithGroup НЕ РЕАЛИЗОВАНЫ!
  ```
- **В чем проблема:**
  1. В соответствии с официальным руководством по написанию кастомных обработчиков `slog` (*Writing a handler for slog*, Jonathan Amsterdam):
     > *"If a Handler wraps another Handler, it must implement `WithAttrs` and `WithGroup` by delegating to the underlying handler, and wrapping the result."*
  2. Поскольку структуры `ContextInjectHandler` и `OtelTracingHandler` просто встраивают `slog.Handler`, компилятор Go продвигает (method promotion) методы `WithAttrs` и `WithGroup` из внутреннего базового хендлера (например, `*slog.JSONHandler`).
  3. Что происходит, когда разработчик создает дочерний логгер для модуля:
     ```go
     moduleLogger := logger.With("module", "billing")
     ```
     Вызывается метод `h.Handler.WithAttrs(...)`, который возвращает обычный `*slog.JSONHandler`! Новая обертка `*ContextInjectHandler` **НЕ создается**!
  4. В результате дочерний `moduleLogger` **навсегда теряет инъекцию `request_id`, `user_id`, `trace_id` и `span_id`**! Логи из всех подмодулей перестают коррелироваться с трейсами, а ошибка проявляется скрытно, без паник и предупреждений компилятора.
  5. В коде обязательна реализация:
     ```go
     func (h *ContextInjectHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
         return &ContextInjectHandler{Handler: h.Handler.WithAttrs(attrs)}
     }
     func (h *ContextInjectHandler) WithGroup(name string) slog.Handler {
         return &ContextInjectHandler{Handler: h.Handler.WithGroup(name)}
     }
     ```
- **Необходимые проверки / источники:** Вызов `logger.With("service", "api").InfoContext(ctx, "test")` на листингах упр. 12 и 19 (показывает, что `request_id` и `trace_id` пропадают из JSON); *Writing a handler for slog*, Go Blog / GitHub slog guide.
- **Приоритет:** **High**

- **Фрагмент кода и ожидаемого терминального вывода:**

  ```go
  func main() {
      baseJSON := slog.NewJSONHandler(os.Stdout, nil)
      sampler := &ProbabilisticHandler{next: baseJSON, sampleRate: 0.10} // 10%
      logger := slog.New(sampler)

      fmt.Println("--- Симуляция 1000 запросов: экономия 90% трафика логов ---")
      logger.Info("Сэмплированный лог 10%", "sample_rate", 0.1) // <-- ВЫЗЫВАЕТСЯ РОВНО ОДИН РАЗ!
  ```

  5. Для демонстрации сэмплирования в `main` необходимо было либо запустить цикл из 1000 итераций и вывести счетчик пропущенных логов, либо зафиксировать сид генератора случайных чисел, либо использовать детерминированный счетчик (как в упр. 16).

    > *«Не создавайте новый `slog.New` внутри каждого метода — сохраните `*slog.Logger` в структуре `AppLogger`!»*
  - При этом в листинге решения автор пишет:

    ```go
    }

    func (l *AppLogger) Debug(msg string, args ...any) {

    func (l *AppLogger) Info(msg string, args ...any) {

        slog.New(l.handler).Warn(msg, args...) // <-- АНТИПАТТЕРН!
    }

    func (l *AppLogger) Error(msg string, args ...any) {
        slog.New(l.handler).Error(msg, args...) // <-- АНТИПАТТЕРН!
    }
    ```
- **В чем проблема:**
  1. Прямое самопротиворечие: код решения буквально воспроизводит вредный антипаттерн, от которого сам же предостерегает обучающегося в блоке «Подводные камни».
  2. Вызов `slog.New(l.handler)` при каждом обращении к `Debug`, `Info`, `Warn` и `Error` создает новый объект указателя `*slog.Logger` в куче, порождая паразитные аллокации памяти и нагрузку на GC при миллионных RPS.
  3. Кроме того, поле `minLevel slog.Level` в методах структуры `AppLogger` вообще никак не проверяется! Вся фильтрация переложена на `l.handler`.
  4. Правильная реализация: хранить `logger *slog.Logger` в поле структуры `AppLogger` и вызывать методы напрямую: `l.logger.Info(msg, args...)`.
- **Необходимые проверки / источники:** Сопоставление полей `code_blocks` и `pitfalls` упражнения 65 в `builder/chapter19_data.json`.
- **Приоритет:** **Medium**

- **В чем проблема:**

### 3.4. Упражнение 20: Платформенная несовместимость с ОС Windows (`syscall.SIGUSR1`) и зависающая горутина
- **Раздел / Упражнение:** Упражнение 20 («Управление уровнем логирования через системный сигнал SIGUSR1»), [`builder/chapter19_data.json`](file:///home/ut/work/go-workout/builder/chapter19_data.json).
- **Фрагмент кода решения:**
  ```go
  func setupSignalLogLevel(levelVar *slog.LevelVar) {
      sigCh := make(chan os.Signal, 1)
      signal.Notify(sigCh, syscall.SIGUSR1) // <-- Windows: undefined: syscall.SIGUSR1

      go func() {
          for range sigCh {
              ...
          }
      }()
  }
  ```
- **В чем проблема:**
  1. В ОС Windows пользовательские сигналы POSIX `SIGUSR1` и `SIGUSR2` отсутствуют на уровне ядра. Попытка скомпилировать этот код на Windows (`GOOS=windows go build`) приводит к ошибке компилятора: `undefined: syscall.SIGUSR1`.
  2. В `main` сигнал операционной системы физически не посылается (`syscall.Kill` не вызывается). Автор сымитировал отправку сигнала простым ручным вызовом `levelVar.Set(slog.LevelDebug)`.
  3. В результате функция `setupSignalLogLevel` фактически бесполезна: сигнальный канал `sigCh` никогда ничего не получает, а запущенная фоновая горутина `go func()` навечно зависает в памяти (Goroutine Leak).
  4. В учебнике для кроссплатформенности необходимо либо использовать build-теги (`//go:build !windows`), либо демонстрировать динамическое изменение уровня через HTTP-хендлер (как в упр. 1), либо использовать стандартный сигнал `syscall.SIGHUP` с оговоркой об ОС.
- **Необходимые проверки / источники:** Компиляция с флагом `GOOS=windows go build main.go`; Документация пакета `os/signal`.
- **Приоритет:** **Medium**
