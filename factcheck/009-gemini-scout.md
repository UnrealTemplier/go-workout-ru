### 1.1. Упражнение 58: Фатальная фактологическая ошибка в демонстрации Map Memory Leak — код освобождает память, а эталонный вывод сфабрикован
- **Раздел / Упражнение:** Упражнение 58 (`ex-58`, `builder/gen_ch9_p4.py`, `builder/chapter9_data.json`).
- **Заголовок / Задача:** «Утечка памяти в мапах (Map Memory Leak): почему delete не возвращает RAM и решение через пересоздание».
- **Фрагмент кода и ожидаемый вывод:**
  ```go
  func main() {
      printMem("1. Начальное состояние")

      // 1. Создаем мапу и заполняем 10 000 элементов по 8 КБ каждый
      heavyMap := make(map[int][1000]int)
      for i := 0; i < 10000; i++ {
          heavyMap[i] = [1000]int{i}
      }
      printMem("2. После заполнения 10k элементов")

      // 2. Удаляем ВСЕ элементы через delete:
      for i := 0; i < 10000; i++ {
          delete(heavyMap, i)
      }
      printMem("3. После delete ВСЕХ элементов (ПАМЯТЬ НЕ ОСВОБОДИЛАСЬ!)")

      // 3. ПРАВИЛЬНОЕ РЕШЕНИЕ: пересоздание мапы
      heavyMap = nil
      printMem("4. После heavyMap = nil и GC (ПАМЯТЬ ПОЛНОСТЬЮ ОСВОБОЖДЕНА!)")
  }
  ```
  В блоке терминала заявлено:
  ```bash
  go run main.go
  # 1. Начальное состояние                 -> Занято памяти:     0 МБ
  # 2. После заполнения 10k элементов       -> Занято памяти:    85 МБ
  # 3. После delete ВСЕХ элементов (ПАМЯТЬ НЕ ОСВОБОДИЛАСЬ!) -> Занято памяти:    85 МБ
  # 4. После heavyMap = nil и GC (ПАМЯТЬ ПОЛНОСТЬЮ ОСВОБОЖДЕНА!) -> Занято памяти:     0 МБ
  ```
- **В чем проблема:**
  Реальный запуск кода выводит:
  ```text
  1. Начальное состояние              -> Занято памяти:     0 МБ
  2. После заполнения 10k элементов   -> Занято памяти:    78 МБ
  3. После delete ВСЕХ элементов (ПАМЯТЬ НЕ ОСВОБОДИЛАСЬ!) -> Занято памяти:     0 МБ
  4. После heavyMap = nil и GC (ПАМЯТЬ ПОЛНОСТЬЮ ОСВОБОЖДЕНА!) -> Занято памяти:     0 МБ
  ```
  Код **полностью опровергает тезис упражнения прямо на глазах студента**! Память **ОСВОБОДИЛАСЬ** до 0 МБ уже на шаге 3, а надпись гласит «ПАМЯТЬ НЕ ОСВОБОДИЛАСЬ!».
  
  **Причины происходящего (внутреннее устройство рантайма Go):**
  1. **Лимит размера значения в бакете (`maxElemSize = 128`):** В рантайме Go (`src/runtime/map.go` и `internal/runtime/maps`), если размер ключа или значения превышает 128 байт, значение **не размещается инлайн в бакете/группе**, а аллоцируется отдельно в куче, а в мапе хранится лишь косвенный указатель (`*[1000]int`). Когда вызывается `delete(heavyMap, i)`, слот обнуляется (`typedmemclr`), указатель на массив зануляется. При вызове `runtime.GC()` сборщик мусора видит, что массивы больше недостижимы, и **освобождает все 78 МБ данных**! В мапе остаются лишь служебные бакеты, которые для 10k элементов весят всего около 200 КБ (~0 МБ).
  2. **Анализ живости переменных компилятора (Liveness Analysis):** Переменная `heavyMap` после цикла `delete` больше нигде не используется (присваивание `heavyMap = nil` — это dead store). Поэтому для GC внутри `printMem` объект `heavyMap` уже считается мертвым!
- **Необходимые проверки / источники:** Запуск `go run scratch/test_ch9/main_58.go`. См. также исходный код `src/runtime/map.go` константу `maxElemSize = 128` и книгу Teiva Harsanyi *"100 Go Mistakes"*, Mistake #28: *"Maps and memory leaks"*.
- **Решение:** Чтобы корректно продемонстрировать эффект неудаляемых бакетов:
  1. Использовать значения размером $\le 128$ байт (например, `int` или `[128]byte`) и количество элементов порядка 1 000 000 (чтобы именно сами бакеты занимали десятки мегабайт памяти).
  2. Обязательно вызвать `runtime.KeepAlive(heavyMap)` или обратиться к `len(heavyMap)` после шага 3, чтобы компилятор не утилизировал мапу раньше времени.
- **Приоритет:** **High**.

### 1.4. Упражнение 11: Неверная ментальная модель `append` для срезов в мапе и формулировка задачи
- **Раздел / Упражнение:** Упражнение 11 (`ex-11`, `builder/gen_ch9_p1.py`, `builder/chapter9_data.json`).
- **Заголовок / Задача:** «Хранение срезов в мапе `map[string][]int`: ловушка потери append и обязательное переприсваивание».
- **Фрагмент формулировки задачи (`sources/9. Мапы.md`, п. 11):**
  > «Создай мапу `map[string][]int` (значение — слайс). Добавь элементы: `m["nums"] = append(m["nums"], 1)`. **Покажи, что если append вызывает реаллокацию, мапа не увидит новые элементы** (потому что слайс в мапе — это struct data, и она не обновляется автоматически). Исправь через переприсваивание.»
- **В чем проблема:**
  Формулировка задачи транслирует фундаментальное заблуждение о модели памяти Go:
  1. Утверждается, что мапа «не увидит новые элементы, *если append вызывает реаллокацию*».
  2. Это в корне неверно: мапа **НЕ увидит новые элементы ДАЖЕ ЕСЛИ реаллокации НЕ БЫЛО**!
     Если сделать:
     ```go
     s := m["nums"] // Скопирован SliceHeader{Data, Len: 1, Cap: 10}
     s = append(s, 2) // Реаллокации НЕТ! Data тот же, s.Len = 2.
     ```
     Значение в мапе `m["nums"]` по-прежнему имеет дескриптор `SliceHeader{Data, Len: 1, Cap: 10}`. Чтение `m["nums"]` вернет срез длины 1! Второй элемент не виден, хотя базовый массив изменился.
  3. Более того, первая фраза задачи сама себе противоречит: `m["nums"] = append(m["nums"], 1)` — это и есть переприсваивание, при котором мапа **всегда видит** новые элементы. Проблема возникает только при операциях над промежуточной переменной (`s := m["k"]; s = append(s, ...)`).
- **Решение:**
  Скорректировать формулировку задачи и блока Theory: четко объяснить, что мапа хранит копию 24-байтного дескриптора `SliceHeader`, и любая модификация длины `Len` через локальную переменную теряется независимо от реаллокации базового массива `Data`.
- **Приоритет:** **High**.

### 1.5. Упражнение 35: Грубая фактическая ошибка — объявление внутренней функции рантайма `runtime.mapclear` «системным вызовом» (Syscall)
- **Раздел / Упражнение:** Упражнение 35 (`ex-35`, `builder/gen_ch9_p3.py`, `builder/chapter9_data.json`).
- **Заголовок / Задача:** «Сравнение ручной очистки через delete в цикле и встроенной функции clear(m)».
- **Фрагмент текста Theory:**
  > «**Go 1.21+:** `clear(m)` — специализированная встроенная операция `runtime.mapclear`, **очищающая бакеты за один системный вызов**.»
- **В чем проблема:**
  Функция `runtime.mapclear` — это обычная внутренняя функция рантайма Go, выполняющаяся в пространстве пользователя (**User Space**). Она обнуляет память бакетов и сбрасывает счетчики `hmap.count = 0`.
  Она **НЕ производит никаких системных вызовов к ядру ОС** (system calls: `sys_write`, `sys_mmap` и т.д.)!
  Называть обнуление структур данных в пользовательской куче «системным вызовом» — грубая терминологическая ошибка, недопустимая для курса, готовящего разработчиков уровня Senior / Staff.
- **Необходимые проверки / источники:** Исходный код `src/runtime/map.go` (функция `mapclear`).
- **Решение:** Заменить «системный вызов» на «внутреннюю операцию рантайма Go» или «быстрое векторное зануление памяти бакетов».
- **Приоритет:** **High**.

### 2.1. Недетерминированный вывод терминала в 7 упражнениях (Ex 13, 15, 33, 39, 47, 51, 61, 62)
- **Раздел / Упражнение:** Упражнения 13, 15, 33, 39, 47, 51, 61, 62.
- **В чем проблема:**
  Рантайм Go намеренно рандомизирует порядок обхода мап в `for ... range m` при помощи псевдослучайного выбора начального бакета (`fastrand()`).
  В упражнениях 13 (слова), 15 (руны), 51 (отделы и сотрудники), 61 (расписание), 62 (города) код обходит мапы напрямую без предварительной сортировки ключей, однако в эталонных блоках вывода зафиксирован строгий, «идеальный» порядок.
  - **Упр. 15:** вывод символов зафиксирован строго по порядку их первого появления в строке («П», «р», «и», «в»...), тогда как `for r, count := range counts` выводит руны в случайном порядке.
  - **Упр. 51:**
    ```go
    // Фактический запуск:
    Отдел #101: [Дмитрий Сергей Иван] // случайный порядок слайса из-за range по мапе!
    Отдел #103: [Ольга]
    Отдел #102: [Анна]
    // Ожидаемый вывод:
    Отдел #101: [Иван Дмитрий Сергей]
    Отдел #102: [Анна]
    Отдел #103: [Ольга]
    ```
  - **Упр. 61:** группы и дни недели выводятся в непредсказуемом порядке.
- **Решение:** Либо отсортировать ключи перед выводом (сделав вывод детерминированным), либо явно указать в блоке терминала комментарий: `# Порядок строк может отличаться из-за рандомизации map в Go`.
- **Приоритет:** **Medium**.

### 2.2. Повреждение формул и спецсимволов из-за неэкранированных управляющих символов Python (Escape Sequence Corruption)
- **Раздел / Упражнение:** Упражнения 2, 4, 9, 42, 49, 55, 56, 60.
- **Фрагменты текста:**
  - Упр. 2, 4, 9, 42, 49, 55, 56: `$ightarrow$` вместо $\rightarrow$ (`\rightarrow`).
  - Упр. 60 (Under the Hood): `$2^{45}  pprox 3.5 	imes 10^{13}$` вместо `$2^{45} \approx 3.5 \times 10^{13}$`.
- **В чем проблема:**
  В файлах `builder/gen_ch9_p*.py` многострочные строки были объявлены без префикса сырых строк `r"""..."""`.
  В результате:
  - `\r` превратился в ASCII 13 (возврат каретки) + оставшаяся строка `ightarrow`;

  - `\t` превратился в символ табуляции + `imes`.
  В сгенерированном HTML (`dist/009-mapy.html`) эти поврежденные строки отображаются пользователю в готовом тексте.
- **Решение:** Добавить префикс сырых строк `r"""..."""` во всех генераторах `builder/gen_ch9_p*.py` и пересобрать HTML.
- **Приоритет:** **Medium**.

### 2.4. Устаревшая фактологическая база: полное игнорирование архитектуры Swiss Tables (SwissMap) из Go 1.24+
- **Раздел / Упражнение:** Упражнения 3, 7, 18, 22, 33, 50, 53, 58 (блоки Theory и Under the Hood).
- **В чем проблема:**
  Во всей главе 09 внутреннее устройство хэш-таблиц Go объясняется **исключительно по устаревшей модели Go 1.0–1.23**:
  - бакеты `bmap` с 8 слотами;
  - 8-байтный массив `tophash`;
  - связные списки переполнения (overflow buckets);
  - коэффициент загрузки строго 6.5 (`loadFactor = 6.5`);
  - эвакуация бакетов `runtime.evacuate`.
  
  Однако, начиная с **Go 1.24**, стандартный рантайм Go перешел на архитектуру **Swiss Tables** (`internal/runtime/maps`):
  1. Группы слотов с контрольными байтами (`ctrlEmpty`, `ctrlDeleted`, H2-хэш из 7 бит).
  2. Векторные SIMD-инструкции (SSE2 / AVX2 / ARM NEON), проверяющие совпадение сразу по всей группе слотов за 1 процессорную инструкцию.
  3. Отсутствие цепочек overflow-бакетов; более плотная упаковка.
  4. Новый порог расширения `maxAvgGroupLoad = 7` (фактор заполнения 7/8 = 87.5% вместо 6.5/8 = 81.25%).
  
  Хотя старая модель `hmap/bmap` до сих пор часто звучит на собеседованиях по инерции, отсутствие даже упоминания Swiss Tables в современном учебнике для Senior/Staff-разработчиков делает теоретическую базу неполной и архаичной.
- **Решение:** Ввести в Under the Hood и BigTech четкое разграничение: классическая архитектура Go 1.0–1.23 (`hmap`/`bmap`/`tophash`/6.5) vs современная архитектура Go 1.24+ (Swiss Tables / группы слотов / SIMD-контрольные байты / фактор 7/8).
- **Приоритет:** **Medium**.

### 2.5. Ошибочное утверждение в Ex 56: «Если обе мапы равны nil -> равны»
- **Раздел / Упражнение:** Упражнение 56 (`ex-56`, `builder/gen_ch9_p4.py`).
- **Заголовок / Задача:** «Собственная функция глубокого сравнения двух мап DeepEqualMaps(m1, m2)».
- **Фрагмент текста Theory:**
  > «**Алгоритм глубокого сравнения двух мап:**
  > 1. Если `len(m1) != len(m2)` $\rightarrow$ мапы не равны ($O(1)$ отсечение);
  > 2. **Если обе мапы равны `nil` $\rightarrow$ равны;**
  > 3. Для каждого ключа...»
- **В чем проблема:**
  1. В коде предложенной функции `EqualMaps` пункта 2 **вообще нет**:
     ```go
     func EqualMaps[K, V comparable](m1, m2 map[K]V) bool {
         if len(m1) != len(m2) { return false }
         for k, v1 := range m1 {
             v2, ok := m2[k]
             if !ok || v1 != v2 { return false }
         }
         return true
     }
     ```
  2. Более того, эта функция возвращает `true` для аргументов `(nil, make(map[string]int))`, поскольку `len(nil) == 0` и `len(empty) == 0`.
  3. В теории не объясняется важнейшая BigTech-разница: стандартная функция `maps.Equal` считает `nil`-мапу и пустую мапу `make(map[K]V)` **равными**, тогда как `reflect.DeepEqual` считает их **не равными** (`false`), потому что сравнивает типы и указатели заголовков.
- **Решение:** Привести теорию в соответствие с кодом и добавить разъяснение семантики `maps.Equal` vs `reflect.DeepEqual`.
- **Приоритет:** **Medium**.

### 2.6. Несоответствие типов в условии Упражнения 16: ожидается `0`, а возвращается пустая строка `""`
- **Раздел / Упражнение:** Упражнение 16 (`ex-16`, `sources/9. Мапы.md`, п. 16).
- **Заголовок / Задача:** «Указатель как ключ: `map[*Point]string`».
- **Фрагмент текста задачи:**
  > «Запиши значение по первому указателю, а попытайся прочитать по второму. **Изучи, почему вернется 0 (адреса-то разные!)**.»
- **В чем проблема:**
  В решении создается `map[*Point]string`. При промахе по ключу строковая мапа возвращает **пустую строку `""`**, а вовсе не `0`! Автор исходного опросника держал в голове `map[*Point]int`, а в решении использовал `string`.
- **Решение:** Исправить в условии фразу «почему вернется 0» на «почему вернется zero value (пустая строка для string или 0 для int)».
- **Приоритет:** **Medium**.

### 2.7. Скрытая утечка памяти при использовании `float64` с `NaN` в качестве ключей мапы
- **Раздел / Упражнение:** Упражнение 34, раздел Pitfalls.
- **В чем проблема:**
  В Pitfalls упражнения 34 сказано: *«Использование float64 с NaN в качестве ключа: math.NaN() != math.NaN(), такой ключ невозможно прочитать обратно!»*.
  Однако не раскрыто главное катастрофическое последствие для продакшена: каждый вызов `m[math.NaN()] = v` добавляет **новую неудаляемую запись** в мапу! Поскольку `NaN != NaN`, ключ невозможно ни прочитать обратно через `m[k]`, ни удалить через `delete(m, k)`. Единственный способ избавиться от таких ключей — полная очистка `clear(m)` или обход через `range`. Это частая причина скрытых утечек памяти в высоконагруженных сервисах телеметрии и ML.
- **Решение:** Дополнить предупреждение в Pitfalls и BigTech информацией о невозможности вызова `delete()` по `NaN`.
- **Приоритет:** **Medium**.

## 🔍 5. Критические пробелы курса по теме (Omissions)

Для курса, ориентированного на позиции Senior / Staff / Tech Lead в ведущие российские технологические компании, в Главе 09 критически не хватает следующих фундаментальных тем:

1. **Архитектурный сдвиг рантайма: Swiss Tables в Go 1.24+:**
   - Переход со связных бакетов `hmap`/`bmap` на плоские швейцарские таблицы (`internal/runtime/maps`).
   - Механизм контрольных байтов (Control Bytes): 7 бит H2-хэша, маркеры `ctrlEmpty` (`0b10000000`) и `ctrlDeleted` (`0b11111110`).
   - Использование SIMD-инструкций (SSE2/AVX2/NEON) для параллельного поиска в группе из 8 слотов за 1 процессорный такт.
2. **Продвинутая конкурентность: `sync.Map` vs `sync.RWMutex` vs Sharded Concurrent Map:**
   - В каких редких случаях эффективен `sync.Map` (Append-only кэши, непересекающиеся ключи)?
   - Почему под интенсивной записью `sync.Map` деградирует (блокировка на `dirty` мапе)?
   - Паттерн **Sharded Map** (шардирование по хэшу на 32–256 шардов с независимыми `sync.RWMutex`), используемый во всех HighLoad-библиотеках (`orcaman/concurrent-map`, `allegro/bigcache`).
3. **Глубокий бенчмаркинг влияния преаллокации (`make(map[K]V, hint)`):**
   - Отсутствует практическое упражнение с `testing.B`, наглядно показывающее разницу во времени и количестве аллокаций памяти между `make(map[int]int)` и `make(map[int]int, 1_000_000)` (предотвращение эвакуаций и роста дерева бакетов).
4. **Обход ограничения Comparable: составные ключи и хэширование:**
   - Реальные паттерны использования несравнимых типов (срезов, структур со срезами) в качестве ключей мапы:
     - Сериализация в байтовую строку / hex;
     - Хэширование через `xxhash` / `fnv64` / `sha256` в `[32]byte` или `uint64`.
5. **Современные функции пакета `maps` (Go 1.21+): `maps.DeleteFunc` и `maps.EqualFunc`:**
   - `maps.DeleteFunc(m, func(k, v) bool)` — идиоматичный способ отфильтровать мапу по предикату без ручных циклов.
   - `maps.EqualFunc` — сравнение мап со сложными значениями (например, содержащими вложенные срезы).
6. **Влияние типов мапы на Garbage Collector (`noscan` бакеты):**
   - Если ни ключ, ни значение мапы не содержат указателей (например, `map[int]int`, `map[int][64]byte`), рантайм Go помечает память бакетов флагом `noscan`. Сборщик мусора **вообще не сканирует содержимое такой мапы**, что устраняет паузы GC (STW) даже при хранении сотен миллионов элементов в RAM.
   - Если же значением является указатель `map[int]*Struct` или строка/срез `map[int]string`, GC обязан просканировать каждый элемент, что резко увеличивает CPU-нагрузку на сборку мусора.
