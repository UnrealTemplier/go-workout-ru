### 2.1. Упражнение 106: Грубая фактическая ошибка в условии задачи — утверждение о сравнимости слайсов через `==`
- **Раздел / Упражнение:** Упражнение 106 (`sources/16. Дженерики.md`, `builder/chapter16_data.json`, `dist/016-dzheneriki.html`).
- **Фрагмент формулировки задачи:**
  > *«Напиши функцию `AreEqual[T comparable](a, b T) bool`. **Используй её для сравнения двух слайсов (слайсы сравнимы через `==`, если их элементы сравнимы).**»*
- **В чем проблема:** Это грубейшая фактическая дезинформация о семантике языка Go, прямо противоречащая спецификации:
  1. В спецификации языка Go (The Go Programming Language Specification, §Comparison operators) однозначно закреплено:
     > *"Slice, map, and function types are not comparable. However, as a special case, a slice, map, or function value may be compared to the predeclared identifier nil."*
  2. Слайсы в Go **НИКОГДА не сравнимы через оператор `==`**, даже если тип их элементов является `comparable`!
  3. Попытка вызвать `AreEqual(s1, s2)` для срезов `[]int` или `s1 == s2` вызывает фатальную ошибку компилятора Go:
     ```text
     invalid operation: s1 == s2 (slice can only be compared to nil)
     []int does not satisfy comparable
     ```
  4. Автор при подготовке решения сам столкнулся с этой ошибкой компиляции, поэтому в коде решения написал функцию `EqualSlices[T comparable](s1, s2 []T) bool`, где перебирает элементы по индексам в цикле:
     ```go
     for i := range s1 {
         if !AreEqual(s1[i], s2[i]) { return false }
     }
     ```
  5. Однако формулировка задачи осталась неисправленной! Студент читает официальное утверждение автора курса, что *"слайсы сравнимы через `==`, если их элементы сравнимы"*, пробует применить `AreEqual` напрямую к двум слайсам и получает ошибку компиляции. Это формирует полностью неверную ментальную модель типовой системы Go.
- **Необходимые проверки / источники:** Спецификация Go (§Comparison operators); попытка компиляции `AreEqual([]int{1}, []int{1})`.
- **Приоритет:** **High**

### 2.3. Упражнение 87: Невыполнимое ТЗ из-за ограничений языка Go — метод `Off` опущен в решении
- **Раздел / Упражнение:** Упражнение 87 (`sources/16. Дженерики.md`, `builder/chapter16_data.json`, `dist/016-dzheneriki.html`).
- **Фрагмент формулировки задачи:**
  > *«Реализуй `EventEmitter[T any]` — `map[string][]func(T)`. Методы: `On(event string, handler func(T))`, **`Off(event string, handler func(T))`**, `Emit(event string, data T)`. **Обработай удаление handler'а во время итерации.**»*
- **В чем проблема:** 
  1. В языке Go функции являются **несравнимыми типами** (`funcs are not comparable`). Попытка сравнить два функциональных значения `h == handler` для поиска нужного элемента в срезе приводит к ошибке компилятора:
     ```text
     invalid operation: h == handler (func can only be compared to nil)
     ```
  2. Реализовать метод с сигнатурой `Off(event string, handler func(T))` стандартными средствами Go **невозможно**, если только не использовать небезопасную рефлексию через `reflect.ValueOf(handler).Pointer()` (что ненадежно для замыканий) или не возвращать целочисленный идентификатор/токен подписки (`SubscriptionID`).
  3. Автор курса осознал эту проблему в момент написания кода и просто **полностью удалил метод `Off`** из решения, а также проигнорировал требование *«Обработай удаление handler'а во время итерации»*.
  4. Студент получает невыполнимое техническое задание, а в "правильном" решении видит только методы `On` и `Emit`.
- **Необходимые проверки / источники:** Листинг упр. 87 в `builder/chapter16_data.json`; спецификация Go (§Comparison operators).
- **Приоритет:** **High**

### 2.5. Конфликт версий и зависимостей: ТЗ требует отсутствующий в стандартной библиотеке пакет `constraints`
- **Раздел / Упражнение:** Упражнения 1, 4, 5, 9, 35, 50, 71, 96, 125, 130 (`sources/16. Дженерики.md` и `builder/chapter16_data.json`).
- **Фрагменты задач:**
  - *«Обобщённая функция `Min[T constraints.Ordered](a, b T) T`...»* (упр. 1)
  - *«Изучите пакет `constraints`. Используйте `constraints.Integer` вместо `Ordered`...»* (упр. 9)
  - *«Реализуй `BinarySearchTree[T constraints.Ordered]`...»* (упр. 71)
  - *«Реализуй `PriorityQueue[T constraints.Ordered]`...»* (упр. 96)
  - *«Создайте параметризованную структуру `Matrix[T constraints.Integer]`...»* (упр. 125)
  - *«Обобщённая min-куча `Heap[T constraints.Ordered]`...»* (упр. 130)
- **В чем проблема:**
  1. В Go 1.18 типы ограничений временно размещались в экспериментальном внешнем модуле `golang.org/x/exp/constraints`.
  2. При релизе Go 1.21 в стандартную библиотеку был добавлен ТОЛЬКО пакет `cmp` с ограничением `cmp.Ordered`. Пакет `constraints` в стандартную библиотеку **так и не вошел**, а типы `constraints.Integer`, `constraints.Signed`, `constraints.Float` в stdlib отсутствуют до сих пор.
  3. В кодовой базе решений автор молча заменил `constraints.Ordered` на `cmp.Ordered`, а целочисленные ограничения начал заново вручную объявлять через `type Integer interface { ~int | ... }`.
  4. Однако в текстах условий задач сохранились жесткие требования использовать пакет `constraints` и его типы `constraints.Integer` / `constraints.Ordered`. Если студент попытается написать `import "constraints"`, он получит ошибку компиляции:
     ```text
     cannot find package "constraints" in any of: ...
     ```
  5. В курсе нигде не объясняется эта важнейшая историческая деталь перехода Go 1.18 → 1.21.
- **Необходимые проверки / источники:** Документация Go 1.21 Release Notes (пакет `cmp`); пакет `golang.org/x/exp/constraints`.
- **Приоритет:** **High**

### 3.3. Упражнение 24: Грубая терминологическая ошибка — подмена `defined types` понятием `aliased types`
- **Раздел / Упражнение:** Упражнение 24 (`sources/16. Дженерики.md` и `builder/chapter16_data.json`).
- **Фрагмент формулировки задачи:**
  > *«Создайте свой кастомный constraint. Например, `type Number interface { ~int | ~float64 }`. Объясните, зачем нужен символ тильды `~` (tilde) и **как он разрешает использование кастомных типов (aliased types)**.»*
- **В чем проблема:**
  1. В спецификации Go существует строгое разграничение между **Type Alias** (`type MyInt = int`, со знаком равенства `=`) и **Defined Type** (`type MyInt int`, без знака равенства).
  2. Псевдоним типа (Type Alias) вообще **НЕ требует тильды `~`**! Поскольку `MyInt` является точной копией `int`, он удовлетворяет ограничению `type Number interface { int | float64 }` даже без символа `~`.
  3. Символ тильды `~` в Go 1.18+ был введен исключительно для **определяемых (пользовательских) типов (Defined Types)**, чей базовый тип (`underlying type`) совпадает с указанным.
  4. Называние определяемых типов `aliased types` — грубая терминологическая ошибка, прививающая студентам ложное понимание модели типов Go.
- **Необходимые проверки / источники:** Спецификация языка Go (§Type declarations, §Alias declarations, §Type parameter declarations).
- **Приоритет:** **Medium**

### 3.4. Упражнения 29, 57, 95: Утечка памяти (GC Liveness Leak) в реализации `Stack.Pop()`
- **Раздел / Упражнение:** Упражнения 29, 57, 95 (`builder/chapter16_data.json`).
- **Фрагмент кода реализации метода Pop:**
  ```go
  func (s *Stack[T]) Pop() (T, bool) {
      if len(s.items) == 0 {
          var zero T
          return zero, false
      }
      lastIdx := len(s.items) - 1
      val := s.items[lastIdx]
      s.items = s.items[:lastIdx] // <--- ВНИМАНИЕ: память не занулена!
      return val, true
  }
  ```
- **В чем проблема:**
  1. Классическая ловушка сборщика мусора в Go при работе со срезами: уменьшение длины среза `s.items[:lastIdx]` оставляет старое значение в ячейке `s.items[lastIdx]` базового массива вплоть до емкости `cap`.
  2. Если `Stack[T]` параметризован указателями (`*User`), строками или структурами с дескрипторами, сборщик мусора GC **не может освободить удаленный объект из памяти**, так как ссылка на него продолжает жить в базовом массиве среза.
  3. Примечательно, что в **упр. 60 (Очередь Queue)** и в **упр. 90 (Кольцевой буфер)** автор курса правильно занулил память (`q.items[0] = zero`, `r.buf[head] = zero`) и даже похвалил себя в "Under the hood". Но в трех реализациях `Stack` (упр. 29, 57, 95) забыл это сделать, оставив скрытую утечку памяти (хотя в упр. 95 стек тестируется на структурах `User`).
- **Необходимые проверки / источники:** Сравнение реализации `Stack.Pop` и `Queue.Dequeue` в `builder/chapter16_data.json`.
- **Приоритет:** **Medium**

### 3.5. Упражнение 52: Ложное утверждение о времени вычисления `unsafe.Sizeof(val)` внутри дженериков
- **Раздел / Упражнение:** Упражнение 52, Секция "Under the hood" (`builder/chapter16_data.json`).
- **Фрагмент текста:**
  > *«`unsafe.Sizeof(val)` вычисляется во время компиляции.»*
- **В чем проблема:**
  1. Согласно спецификации языка Go (The Go Programming Language Specification, §Package unsafe):
     > *"The expressions unsafe.Alignof, unsafe.Offsetof, and unsafe.Sizeof are constant expressions of type uintptr if the type argument does not depend on a type parameter. If the type argument depends on a type parameter, the expression is not a constant expression."*
  2. Внутри универсальной функции `func PrintAny[T any](val T)` тип аргумента `val` зависит от параметра типа `T`. Поэтому `unsafe.Sizeof(val)` **НЕ является константой времени компиляции**!
  3. Значение размера определяется рантаймом через структуру словаря типов (`.*dict`), передаваемого при вызове функции. Утверждение в UTH ложно.
- **Необходимые проверки / источники:** Спецификация языка Go (§Package unsafe); дизассемблирование через `go tool compile -S`.
- **Приоритет:** **Medium**

### 3.6. Упражнение 86: Устаревшее утверждение о поведении `sync.Pool` при сборке мусора
- **Раздел / Упражнение:** Упражнение 86, Секция "Under the hood" (`builder/chapter16_data.json`).
- **Фрагмент текста:**
  > *«`sync.Pool` сбрасывается каждым циклом Garbage Collection.»*
- **В чем проблема:**
  1. Это устаревший факт времен Go 1.12. Начиная с версии Go 1.13, в рантайм `sync.Pool` был внедрен механизм **victim cache** (`poolVictim`).
  2. При запуске GC объекты из пула не уничтожаются мгновенно, а перемещаются в victim cache. Если они повторно запрашиваются до следующего цикла GC, они возвращаются обратно без повторных аллокаций.
  3. Утверждение, что пул начисто вычищается каждым циклом GC, технически неверно уже более 10 версий Go.
- **Необходимые проверки / источники:** Исходный код `src/sync/pool.go` (структура `poolVictim`, Go 1.13+ release notes).
- **Приоритет:** **Medium**

### 3.7. Упражнение 65: Семантически некорректная реализация `Result[T].Unwrap()`
- **Раздел / Упражнение:** Упражнение 65 (`builder/chapter16_data.json`).
- **Фрагмент кода реализации метода Unwrap:**
  ```go
  func (r Result[T]) Unwrap() T { return r.value }
  ```
- **В чем проблема:**
  1. Концепция `Result[T]` пришла из Rust, Swift и Scala. По контракту типа метод `Unwrap()` вызывается только тогда, когда разработчик абсолютно уверен в успешности операции. Если результат содержит ошибку (`IsErr()`), метод `Unwrap()` **ОБЯЗАН запаниковать** (`panic(r.err)`).
  2. В коде упр. 65 метод `Unwrap()` при наличии ошибки просто молча возвращает нулевое значение `r.value` (`zero value`), полностью игнорируя ошибку!
  3. Для безопасного извлечения с дефолтным значением существует метод `UnwrapOr(def T)`. Реализация `Unwrap` без паники при ошибке лишает тип `Result` его фундаментального свойства — защиты от неявного использования некорректного состояния.
- **Необходимые проверки / источники:** Документация Rust `Result::unwrap`; семантика монадных контейнеров.
- **Приоритет:** **Medium**

## 🧩 5. Пробелы, упущения и нераскрытые аспекты (Critical Omissions)

1. **Миф о «полной мономорфизации» vs реальная архитектура GCShape Stenciling со словарями рантайма:**
   - В нескольких упражнениях (упр. 42, 56, 75, 83, 103, 106, 119, 125, 129) утверждается, что Go компилирует дженерики «с мономорфизацией без оверхеда, как C++».
   - На самом деле Go применил уникальный гибридный подход: **GCShape Stenciling with Runtime Dictionaries**. Для всех указательных типов (`*int`, `*string`, `*MyStruct`), имеющих одинаковую разметку для сборщика мусора (`go.shape.*`), компилятор генерирует **ровно одну общую функцию**, передавая скрытым нулевым аргументом указатель на словарь типа (`.*dict`). Это спасает Go от раздувания бинарников (binary bloat), но создает микрооверхед на чтение методов через словарь. Курс обязан объяснить эту механику, а не повторять штампы о C++.
2. **Ловушка `comparable` с интерфейсами в Go 1.20+ (Runtime Panic):**
   - До Go 1.20 тип `any` не удовлетворял ограничению `comparable`. В Go 1.20 это ограничение ослабили: теперь `comparable` допускает интерфейсные типы.
   - Но если интерфейсная переменная в рантайме содержит несравнимый тип (например, срез `[]int`), операция `a == b` внутри `func Equal[T comparable](a, b T)` вызывает **панику во время выполнения (`runtime panic: comparing uncomparable type`)**! Это одна из самых коварных ловушек современного Go, которую часто спрашивают на собеседованиях Senior/Staff уровней. В главе она не раскрыта.
3. **Глубокая архитектурная причина запрета generic-методов на структурах:**
   - В упр. 66 и 84 констатируется факт запрета `func (s *Stack[T]) Map[U any]()`. Однако инженерная причина не объяснена: разрешение generic-методов сделало бы невозможным построение таблиц методов интерфейсов (`itab`) во время компиляции, так как число инстанциаций метода могло бы стать бесконечным или зависеть от других пакетов в рантайме.
4. **Интерфейсы с объединениями типов как Type Constraints vs Value Types:**
   - Не объяснено ключевое правило спецификации Go: интерфейс, содержащий объединение типов (`type Number interface { int | float64 }`), является **General Interface** и может использоваться **ТОЛЬКО как ограничение параметра типа**. Его категорически запрещено использовать как тип обычной переменной (`var x Number` вызовет ошибку `cannot use type Number outside a type constraint`).
5. **Дженерики и итераторы (Go 1.23+ `iter.Seq[V]`, `iter.Seq2[K, V]`):**
   - Начиная с Go 1.23, в язык встроена стандартная поддержка итераторов через дженерик-типы `iter.Seq[V]` и `iter.Seq2[K, V]`, а пакеты `slices` и `maps` получили функции `All()`, `Values()`, `Collect()`. В главе по дженерикам уровня Middle+ этот современный стандарт полностью отсутствует.
6. **Влияние дженериков на Escape Analysis (побег памяти в кучу):**
   - Не показано, как прохождение аргументов через параметры типов влияет на инлайнинг (`inlining`) и анализ побега памяти.
