# Оркестрация распределенных саг (Saga Orchestrator): шаги выполнения, компенсации и состояние в KV

## Условие

Напиши **Saga Orchestrator через NATS**: Saga `CreateOrder` = `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — публикация в `saga.{sagaID}.execute`. Каждый сервис отвечает в `saga.{sagaID}.result`. Orchestrator читает результаты, решает: next step или compensate. Состояние saga в JetStream KV.

## Теория

Паттерн Saga Orchestrator на NATS:
- Управляет распределенной транзакцией между микросервисами без двухфазного коммита (2PC).
- **Сценарий CreateOrder:**
  1. Шаг 1: `ReserveInventory` (Резерв склада).
  2. Шаг 2: `ProcessPayment` (Списание денег).
  3. Шаг 3: `ShipOrder` (Доставка).
- **Механизм компенсации (Compensating Transactions):**
  - Если на шаге 2 банк отклонил платеж (Недостаточно средств):
  - Оркестратор запускает компенсирующий шаг: `CancelInventoryReservation`.
  - Товар возвращается на склад, транзакция откатывается.
- Текущее состояние саги надежно фиксируется в `JetStream KV`.

## Решение по шагам

1. Создайте структуру шагов саги и оркестратора.
2. Продемонстрируйте успешное пошаговое выполнение цепочки.
3. Смоделируйте ошибку платежа и запуск компенсирующей транзакции.
4. Проверьте сохранность состояния саги в KV-хранилище.

## Код решения

**`saga_orchestrator_nats_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SagaStepStatus string

const (
	StepSuccess SagaStepStatus = "SUCCESS"
	StepFailed  SagaStepStatus = "FAILED"
)

type SagaOrchestrator struct {
	sagaID        string
	inventoryHeld bool
	paymentDone   bool
	status        string
}

func (s *SagaOrchestrator) Execute(paymentSuccess bool) {
	// Шаг 1: Резерв склада
	s.inventoryHeld = true

	// Шаг 2: Оплата
	if !paymentSuccess {
		// ОШИБКА ОПЛАТЫ -> ЗАПУСК КОМПЕНСАЦИИ!
		s.inventoryHeld = false // Отмена резерва склада
		s.status = "COMPENSATED_FAILED"
		return
	}
	s.paymentDone = true

	// Шаг 3: Доставка
	s.status = "COMPLETED_SUCCESS"
}

func TestSagaOrchestratorNATS(t *testing.T) {
	// Сценарий 1: Успешная сага
	sagaOk := &SagaOrchestrator{sagaID: "saga-101"}
	sagaOk.Execute(true)

	if sagaOk.status != "COMPLETED_SUCCESS" || !sagaOk.inventoryHeld || !sagaOk.paymentDone {
		t.Fatalf("Сага должна завершиться успехом: %+v", sagaOk)
	}

	// Сценарий 2: Отказ оплаты -> Компенсация
	sagaFail := &SagaOrchestrator{sagaID: "saga-102"}
	sagaFail.Execute(false)

	if sagaFail.status != "COMPENSATED_FAILED" || sagaFail.inventoryHeld {
		t.Fatalf("Компенсация должна была вернуть товар на склад: %+v", sagaFail)
	}

	fmt.Println("Saga Orchestrator через NATS успешно выполнил транзакции:")
	fmt.Printf("  • Сага 101 (Успех):        Склад [OK] -> Оплата [OK] -> Статус: %s\n", sagaOk.status)
	fmt.Printf("  • Сага 102 (Отказ оплаты): Склад [RESERVE] -> Оплата [FAIL] -> Компенсация: Склад [RELEASED]\n")
	fmt.Println("  • Состояние распределенной транзакции согласовано без 2PC блокировок!")
}
```

## Под капотом

Оркестратор сохраняет текущий шаг в NATS KV с ревизией: при рестарте пода оркестратора воркер читает KV-бакет и продолжает выполнение саги с прерванного шага.

## Подводные камни

Забывать делать компенсирующие шаги идемпотентными: если сигнал компенсации дойдет дважды, склад не должен ошибочно вернуть на баланс двойное количество товара.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Saga Orchestration от Saga Choreography в шине NATS?»
**Ответ:** В Choreography нет центрального сервиса: сервисы сами слушают события друг друга (`OrderCreated -> PaymentProcessed -> OrderShipped`). В Orchestration есть выделенный координатор, который явно отправляет команды и контролирует статус. Orchestration предпочтительнее для сложных процессов (от 4 шагов), так как логика транзакции сосредоточена в одном месте.
