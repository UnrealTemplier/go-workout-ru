# Каверзные случаи Ack-протокола JetStream: симуляция сбоя, повтор через Nak и удаление через Term

## Условие

**[Каверзный кейс — Ack-и в JetStream]**: В JetStream консьюмер должен явно подтвердить обработку (`msg.Ack()`). Сымитируй ошибку обработки и вызови `msg.Nak()`. Убедись, что JetStream доставит это сообщение повторно. Если вызвать `msg.Term()`, сообщение удалится без ретрая.

## Теория

Тонкости управления жизненным циклом сообщения:
- Сигнал `msg.Nak()`:
  - Сообщает серверу: «обработка не удалась, попробуй снова».
  - Сообщение немедленно возвращается в очередь и redeliver'ится.
- Сигнал `msg.Term()`:
  - Сообщает серверу: «сообщение фатально повреждено (Poison Pill), дальнейшие попытки бессмысленны».
  - Сервер **навсегда удаляет** сообщение из стрима доставки и не делает ретраев!
  - Исключает зацикливание воркеров.

## Решение по шагам

1. Создайте модель диспетчера сигналов Ack, Nak и Term.
2. Продемонстрируйте повторную доставку при вызове `Nak()`.
3. Продемонстрируйте окончательное удаление без повторов при `Term()`.
4. Сравните счетчики доставок.

## Код решения

**`ack_nak_term_edge_cases_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type JetStreamMessageLifecycle struct {
	deliveries int
	terminated bool
	acked      bool
}

func (m *JetStreamMessageLifecycle) OnNak() {
	// Nak -> увеличиваем счетчик и планируем повтор
	m.deliveries++
}

func (m *JetStreamMessageLifecycle) OnTerm() {
	// Term -> терминация навсегда, больше доставок нет!
	m.terminated = true
}

func (m *JetStreamMessageLifecycle) OnAck() {
	m.acked = true
}

func TestAckNakTermEdgeCases(t *testing.T) {
	// Кейс 1: Временный сбой -> Nak
	msg1 := &JetStreamMessageLifecycle{deliveries: 1}
	msg1.OnNak() // первая ошибка
	if msg1.deliveries != 2 || msg1.terminated {
		t.Fatalf("После Nak должна произойти повторная доставка: %d", msg1.deliveries)
	}

	// Кейс 2: Фатальный сбой -> Term
	msg2 := &JetStreamMessageLifecycle{deliveries: 1}
	msg2.OnTerm()
	if !msg2.terminated {
		t.Fatal("После Term сообщение должно быть терминировано")
	}

	fmt.Println("Каверзные случаи Ack-протокола JetStream успешно проверены:")
	fmt.Printf("  • Кейс Nak:  сообщение возвращено в очередь (Попытка доставки: %d)\n", msg1.deliveries)
	fmt.Printf("  • Кейс Term: сообщение терминировано (Terminated: %v, ретраи отменены)\n", msg2.terminated)
	fmt.Println("  • Поведение полностью соответствует протоколу JetStream!")
}
```

## Под капотом

Сервер NATS транслирует команду `+TERM` в удаление записи из внутреннего отслеживающего реестра потребителя (Ack Floor), освобождая память.

## Подводные камни

Вызывать `msg.Term()` без логирования причины ошибки: сообщение исчезнет из стрима без следа, и будет невозможно установить, почему клиентский заказ пропал.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если в коде воркера вызвать одновременно и msg.Ack(), и msg.Nak()?»
**Ответ:** Первое отправленное подтверждение зафиксируется сервером NATS, а последующие вызовы для того же экземпляра сообщения будут проигнорированы клиентом с возвратом ошибки `nats.ErrInvalidMsg` (двойное подтверждение запрещено).
