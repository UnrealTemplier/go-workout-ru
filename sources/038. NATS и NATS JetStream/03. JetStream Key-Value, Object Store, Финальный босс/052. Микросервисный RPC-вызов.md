# Микросервисный RPC-вызов: клиентский запрос nc.Request и серверная отправка ответа в тему reply

## Условие

**[Request/Reply (RPC)]**: Реализуй микросервисный вызов: один сервис отправляет запрос (`nc.Request`) и ждет ответа. Второй сервис подписан на subject, обрабатывает запрос и шлет ответ (`nc.PublishMsg` с `reply` subject).

## Теория

Протокол синхронного RPC взаимодействия в микросервисах:
- Сервис-клиент:
  - `msg, err := nc.Request("user.get_profile", []byte("usr-991"), 2*time.Second)`
- Сервис-сервер:
  - Подписан на `user.get_profile`.
  - Извлекает `m.Reply` (там указан временный инбокс клиента).
  - Формирует ответ и вызывает `nc.Publish(m.Reply, responseBytes)`.
- Клиент разблокируется и десериализует ответ.
- Работает полностью асинхронно на транспортном уровне!

## Решение по шагам

1. Создайте структуру RPC-сообщения с темой ответа.
2. Смоделируйте отправку запроса клиентом.
3. Смоделируйте генерацию ответа сервером в тему `reply`.
4. Проверьте разблокировку клиента и получение результата.

## Код решения

**`microservice_rpc_flow_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RPCMessagePacket struct {
	Subject string
	ReplyTo string
	Data    string
}

func HandleUserQuery(packet RPCMessagePacket) (replySubject string, responseData string) {
	if packet.Subject == "user.get_profile" && packet.Data == "usr-991" {
		return packet.ReplyTo, `{"name":"Алексей","tier":"VIP"}`
	}
	return packet.ReplyTo, `{"error":"not_found"}`
}

func TestMicroserviceRPCFlow(t *testing.T) {
	inbox := "_INBOX.client_reply_9988"
	clientReq := RPCMessagePacket{
		Subject: "user.get_profile",
		ReplyTo: inbox,
		Data:    "usr-991",
	}

	targetSub, respPayload := HandleUserQuery(clientReq)

	if targetSub != inbox || respPayload != `{"name":"Алексей","tier":"VIP"}` {
		t.Fatalf("Ошибка RPC ответа: %s -> %s", targetSub, respPayload)
	}

	fmt.Println("Микросервисный RPC-вызов через NATS успешно выполнен:")
	fmt.Printf("  • Клиентский вызов: nc.Request(\"%s\", \"%s\")\n", clientReq.Subject, clientReq.Data)
	fmt.Printf("  • Сервер ответил в: %s\n", targetSub)
	fmt.Printf("  • Тело ответа:      %s\n", respPayload)
}
```

ℹ️ Синхронный RPC-вызов с маршрутизацией ответа в тему m.Reply

## Под капотом

Метод `msg.Respond(data)` в Go SDK — это удобная обертка над `nc.Publish(msg.Reply, data)` с дополнительной проверкой наличия темы ответа.

## Подводные камни

Вызывать `msg.Respond` при пустом `msg.Reply`: если сообщение было отправлено через обычный `Publish`, а не `Request`, поле `msg.Reply` будет пустым, и вызов `Respond` вернет ошибку `ErrNoReply`.

## На собеседовании

**Вопрос с собеседования:** «Как в NATS Request/Reply обнаружить, что на тему вообще никто не подписан (No Responders)?»
**Ответ:** Начиная с NATS 2.2, если в теме нет активных подписчиков, брокер не ждет истечения таймаута, а мгновенно возвращает клиенту служебный пакет с заголовком `Nats-Status: 503` (`ErrNoResponders`), что позволяет клиенту моментально узнать об отсутствии обработчика.
