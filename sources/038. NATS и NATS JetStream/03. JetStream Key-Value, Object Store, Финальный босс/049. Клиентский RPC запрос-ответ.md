# Клиентский RPC запрос-ответ: первый ответивший подписчик и таймаут nc.Request

## Условие

Используйте request-reply: клиент отправляет запрос (`nc.Request`) и получает ответ от первого ответившего подписчика в течение таймаута.

## Теория

Семантика First-Response в паттерне Request/Reply:
- Если на тему `service.ping` подписано 5 инстансов микросервиса:
  - При отправке `nc.Request("service.ping", nil, timeout)`:
  - Все подписчики получат запрос.
  - Клиент принимает ответ от **первого же ответившего** инстанса!
  - Остальные запоздавшие ответы брокер NATS автоматически отбрасывает.
- Позволяет строить сценарии с выбором самого быстрого обработчика (Race for Lowest Latency).

## Решение по шагам

1. Создайте модель гонки ответов между двумя сервисами.
2. Продемонстрируйте фиксацию ответа от самого быстрого сервиса.
3. Проверьте корректное игнорирование медленных ответов.
4. Убедитесь в соблюдении таймаута ожидания.

## Код решения

**`first_response_rpc_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type FirstResponseSession struct {
	receivedResponse string
}

func (s *FirstResponseSession) HandleReplies(replies []string) {
	if len(replies) > 0 {
		s.receivedResponse = replies[0] // Первый ответивший выигрывает!
	}
}

func TestFirstResponseRPC(t *testing.T) {
	session := &FirstResponseSession{}

	// Сервер 1 ответил за 5 мс, сервер 2 за 20 мс
	replies := []string{"FastNode: pong (5ms)", "SlowNode: pong (20ms)"}
	session.HandleReplies(replies)

	if session.receivedResponse != "FastNode: pong (5ms)" {
		t.Fatalf("Должен быть выбран первый быстрый ответ: %s", session.receivedResponse)
	}

	fmt.Println("NATS Request/Reply (First-Response) успешно выполнен:")
	fmt.Printf("  • Принятый ответ: «%s»\n", session.receivedResponse)
	fmt.Println("  • Клиент мгновенно разблокирован, медленный ответ отброшен брокером!")
}
```

## Под капотом

Клиент NATS регистрирует внутреннюю подписку с лимитом `AutoUnsubscribe(1)`: сразу после получения одного первого сообщения клиент автоматически отсылает серверу команду `UNSUB`.

## Подводные камни

Забывать объединять отвечающие сервисы в `QueueGroup`: если не использовать очередь, все 5 инстансов будут параллельно выполнять одну и ту же тяжелую работу (например, расчет заказа). Если нужен один исполнитель — обязательна Queue Group!

## На собеседовании

**Вопрос с собеседования:** «Когда паттерн First-Response используется намеренно без Queue Groups?»
**Ответ:** При распределенном поиске по географически распределенным кэшам или DNS-резолверам (Hedging Requests): запрос отправляется трем репликам сразу, а используется результат той ноды, которая ответила быстрее всех, что срезает хвост задержки (p99 latency).
