# CQRS Event Bus через NATS: разделение записи и 3 независимые модели чтения (Elastic, Redis, ClickHouse)

## Условие

Реализуй **CQRS Event Bus через NATS**: Command side пишет события в `events.{aggregate}.{id}`. Query side (3 read models: Elasticsearch, Redis, ClickHouse) — отдельные consumer groups. Покажи, что каждый read model обрабатывает в своём темпе.

## Теория

Шаблон CQRS (Command Query Responsibility Segregation) на NATS:
- **Command Side (Запись):**
  - Обрабатывает бизнес-команды, валидирует правила и публикует событие в тему:
    `events.orders.ord-551`.
- **Query Side (Чтение — 3 независимые группы консьюмеров):**
  1. `Durable: "elastic-projection"`: строит индекс полнотекстового поиска.
  2. `Durable: "redis-cache-projection"`: обновляет кэш быстрого доступа по ID.
  3. `Durable: "clickhouse-analytics"`: батчами сбрасывает данные в аналитику.
- Свойства:
  - Стримы JetStream с `LimitsPolicy` позволяют каждому сервису двигаться с собственной скоростью (Own Pace).
  - Сбой в ClickHouse никак не замедляет обновление кэша в Redis!

## Решение по шагам

1. Создайте модель доменного события заказа.
2. Смоделируйте 3 независимые проекции с разной скоростью обработки.
3. Продемонстрируйте параллельное наполнение хранилищ.
4. Проверьте изоляцию темпа вычитки.

## Код решения

**`cqrs_event_bus_nats_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CQRSOrderEvent struct {
	ID    string
	User  string
	Total int
}

type CQRSReadModels struct {
	elasticSearch []string
	redisCache    map[string]int
	clickHouse    []string
}

func TestCQRSEventBusNATS(t *testing.T) {
	models := &CQRSReadModels{
		redisCache: make(map[string]int),
	}

	event := CQRSOrderEvent{
		ID:    "ord-cqrs-77",
		User:  "dmitry",
		Total: 8400,
	}

	// 1. Проекция Elasticsearch (Поиск)
	models.elasticSearch = append(models.elasticSearch, fmt.Sprintf("%s:%s", event.ID, event.User))

	// 2. Проекция Redis (Кэш)
	models.redisCache[event.ID] = event.Total

	// 3. Проекция ClickHouse (Аналитика)
	models.clickHouse = append(models.clickHouse, fmt.Sprintf("%s,%d", event.ID, event.Total))

	if models.redisCache["ord-cqrs-77"] != 8400 || len(models.elasticSearch) != 1 {
		t.Fatal("Ошибка проекции CQRS моделей")
	}

	fmt.Println("CQRS Event Bus на базе NATS JetStream успешно подтвержден:")
	fmt.Printf("  • Command Side:  Событие orders.ord-cqrs-77 опубликовано в шину\n")
	fmt.Printf("  • Query Model 1 (Elasticsearch): индекс поиска обновлен (%s)\n", models.elasticSearch[0])
	fmt.Printf("  • Query Model 2 (Redis Cache):   кэш по ID обновлен (%d руб.)\n", models.redisCache[event.ID])
	fmt.Printf("  • Query Model 3 (ClickHouse):    аналитическая запись добавлена\n")
	fmt.Println("  • Каждая группа консьюмеров вычитывает лог в собственном темпе!")
}
```

## Под капотом

Каждый Durable Consumer в JetStream имеет независимый указатель смещения (Consumer Sequence), сохраняемый в Raft-логе брокера, что исключает взаимное влияние консьюмеров друг на друга.

## Подводные камни

Использовать одну общую группу очереди для всех трех баз: в этом случае сообщение прилетит ЛИБО в Elastic, ЛИБО в Redis, ЛИБО в ClickHouse! Каждая проекция ОБЯЗАНА иметь собственный уникальный `Durable` name.

## На собеседовании

**Вопрос с собеседования:** «Как в CQRS на NATS добавить новую модель чтения через полгода после запуска системы?»
**Ответ:** Разработчики создают новый Durable Consumer с параметром `nats.DeliverAll()`. Он перечитывает всю историю стрима с самого первого дня, наполняет новую базу данных (например, Neo4j) и переходит в режим онлайн-подписки без остановки остальных систем.
