# Сквозная настройка JetStream: декларация стрима, отправка сообщений и pull-чтение с подтверждением

## Условие

Настройте JetStream: создайте stream с хранением сообщений и consumer с явным подтверждением (pull-based). Отправьте сообщения в stream, затем прочитайте их консюмером с подтверждением.

## Теория

Полный цикл работы с JetStream в Go:
1. `js, _ := nc.JetStream()`: получение контекста.
2. `js.AddStream(&nats.StreamConfig{Name: "ORDERS", Subjects: []string{"orders.*"}})`: создание персистентного хранилища.
3. `js.AddConsumer("ORDERS", &nats.ConsumerConfig{Durable: "worker-pull", AckPolicy: nats.AckExplicitPolicy})`: объявление консьюмера.
4. `js.Publish("orders.created", data)`: надежная запись.
5. `sub.Fetch(batchSize)` \(\to\) обработка \(\to\) `msg.Ack()`: подтверждение успешной фиксации.

## Решение по шагам

1. Создайте модель связки Стрим -> Консьюмер -> Подтверждение.
2. Опубликуйте 3 сообщения в стрим.
3. Вычитайте сообщения через Pull Consumer.
4. Подтвердите обработку каждого сообщения и убедитесь в очистке очереди.

## Код решения

**`end_to_end_jetstream_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FullJetStreamPipeline struct {
	streamStorage []string
	ackedMessages []string
}

func (p *FullJetStreamPipeline) Publish(msg string) {
	p.streamStorage = append(p.streamStorage, msg)
}

func (p *FullJetStreamPipeline) ConsumeAndAck() int {
	count := 0
	for _, m := range p.streamStorage {
		// Обработка и Ack
		p.ackedMessages = append(p.ackedMessages, m)
		count++
	}
	p.streamStorage = nil // Сообщения удалены после подтверждения (WorkQueue)
	return count
}

func TestEndToEndJetStream(t *testing.T) {
	pipeline := &FullJetStreamPipeline{}

	// Публикуем 3 заказа
	pipeline.Publish("order-101")
	pipeline.Publish("order-102")
	pipeline.Publish("order-103")

	if len(pipeline.streamStorage) != 3 {
		t.Fatal("Стрим должен содержать 3 сообщения")
	}

	// Вычитываем и подтверждаем
	processed := pipeline.ConsumeAndAck()

	if processed != 3 || len(pipeline.streamStorage) != 0 || len(pipeline.ackedMessages) != 3 {
		t.Fatalf("Ошибка конвейера: processed=%d, remaining=%d", processed, len(pipeline.streamStorage))
	}

	fmt.Println("Сквозной конвейер NATS JetStream успешно завершил цикл:")
	fmt.Printf("  • Опубликовано в стрим: 3 заказа\n")
	fmt.Printf("  • Вычитано и Acked:    %d заказов\n", processed)
	fmt.Printf("  • Остаток в стриме:     %d (Очередь полностью обработана)\n", len(pipeline.streamStorage))
}
```

ℹ️ Сквозной цикл: создание стрима, публикация, pull-вычитка и фиксация Ack

## Под капотом

Протокол JetStream связывает воедино стрим лога и метаданные консьюмера: сервер отслеживает прогресс каждого воркера по номеру последовательности (Sequence Tracker).

## Подводные камни

Забывать указывать `AckPolicy: nats.AckExplicitPolicy`: в политике `AckNone` брокер считает сообщение подтвержденным сразу в момент отправки в сеть, что лишает систему отказоустойчивости.

## На собеседовании

**Вопрос с собеседования:** «Каковы преимущества явного разделения концепций Stream и Consumer в NATS JetStream?»
**Ответ:** В Kafka топик и группа жестко связаны партициями. В NATS JetStream Stream — это персистентное хранилище (Message Store), а Consumer — это независимое представление (View) над стримом с собственными фильтрами тем, политикой подтверждения и скоростью вычитки. К одному стриму можно подключить десятки разнородных консьюмеров (Push, Pull, WorkQueue, Ephemeral).
