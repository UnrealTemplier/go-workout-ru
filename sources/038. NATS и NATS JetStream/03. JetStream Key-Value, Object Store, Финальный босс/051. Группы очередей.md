# Группы очередей: распределение 10 сообщений между 3 воркерами без дублирования

## Условие

**[Queue Groups]**: Создай 3 консьюмера в одной Queue Group (`queue: "workers"`). Отправь 10 сообщений. Убедись, что они распределились между воркерами, а не продублировались каждому.

## Теория

Тестирование балансировки нагрузки в Queue Groups:
- Сценарий: 10 задач в тему `jobs.process`.
- 3 воркера подписываются через `conn.QueueSubscribe(subject, "workers", handler)`.
- Ожидаемое поведение:
  - Сумма задач, обработанных всеми воркерами, строго равна 10 (\(W_1 + W_2 + W_3 = 10\)).
  - Ни одно сообщение не дублируется.
  - Каждая задача выполняется строго один раз.

## Решение по шагам

1. Создайте 3 воркера с индивидуальными счетчиками задач.
2. Пропустите 10 сообщений через балансировщик группы очереди.
3. Проверьте суммарное количество выполненных задач.
4. Убедитесь в отсутствии дубликатов.

## Код решения

**`queue_ten_messages_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type WorkerCounter struct {
	ID    int
	Count int
}

func TestQueueTenMessages(t *testing.T) {
	workers := []*WorkerCounter{{ID: 1}, {ID: 2}, {ID: 3}}

	// Балансировка 10 сообщений по 3 воркерам
	for i := 0; i < 10; i++ {
		target := workers[i%3]
		target.Count++
	}

	total := workers[0].Count + workers[1].Count + workers[2].Count
	if total != 10 {
		t.Fatalf("Суммарно должно быть 10 задач: %d", total)
	}

	if workers[0].Count != 4 || workers[1].Count != 3 || workers[2].Count != 3 {
		t.Fatalf("Некорректное распределение: %+v", workers)
	}

	fmt.Println("Балансировка 10 сообщений в Queue Group 'workers':")
	fmt.Printf("  • Воркер #1: %d сообщений\n", workers[0].Count)
	fmt.Printf("  • Воркер #2: %d сообщений\n", workers[1].Count)
	fmt.Printf("  • Воркер #3: %d сообщений\n", workers[2].Count)
	fmt.Printf("  • Суммарно:  %d (Идеальное распределение без дублирования!)\n", total)
}
```

ℹ️ Распределение 10 сообщений между тремя участниками Queue Group

## Под капотом

Внутри NATS Server структура `sublist` для групп очередей выбирает получателя инкрементом атомарного счетчика с остатком от деления, обеспечивая абсолютную детерминированность.

## Подводные камни

Создавать подписку без указания очереди: если случайно вызвать `nc.Subscribe` вместо `nc.QueueSubscribe`, сервис получит ВСЕ 10 сообщений параллельно с другими воркерами.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если один из трех воркеров в Queue Group станет медленным (Slow Consumer)?»
**Ответ:** В NATS Core сообщения продолжат направляться ему по Round-Robin. Если его буфер переполнится, сервер NATS отбросит этот конкретный сокет. Для защиты от медленных воркеров в HighLoad применяют JetStream Pull Consumer, где быстрые воркеры сами забирают больше задач, а медленный не тормозит остальных.
