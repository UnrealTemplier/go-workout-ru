# Батчинг запросов в Pull Consumer: пакетная вычитка до 10 сообщений с таймаутом MaxWait 1s

## Условие

**[Pull Consumers]**: Создай Pull Consumer. Напиши код, который батчит (batch) запросы: запрашивает до 10 сообщений или ждет 1 секунду (`Fetch(10, nats.MaxWait(1*time.Second))`).

## Теория

Механика тайм-аутов в Pull Batching:
- Вызов `sub.Fetch(10, nats.MaxWait(1 * time.Second))`:
  - Если в стриме уже есть 10 сообщений \(\to\) вызов возвращается **немедленно**, отдав 10 сообщений.
  - Если в стриме всего 3 сообщения \(\to\) сервер ждет до 1 секунды появления остальных. По истечении секунды метод возвращает те 3 сообщения, которые успели прийти!
  - Идеальный баланс между эффективным батчингом и низкой задержкой.

## Решение по шагам

1. Создайте структуру симулятора вызова `Fetch` с таймаутом `MaxWait`.
2. Смоделируйте мгновенный возврат при полном батче.
3. Смоделируйте возврат частичного батча по истечении таймаута.
4. Проверьте отсутствие зависания вызова.

## Код решения

**`pull_batch_timeout_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type BatchFetchResult struct {
	Messages []string
	Waited   time.Duration
}

func SimulateFetchWithTimeout(available int, reqCount int, maxWait time.Duration) BatchFetchResult {
	if available >= reqCount {
		// Полный батч отдается мгновенно
		msgs := make([]string, reqCount)
		for i := 0; i < reqCount; i++ {
			msgs[i] = fmt.Sprintf("msg-%d", i+1)
		}
		return BatchFetchResult{Messages: msgs, Waited: 0}
	}

	// Частичный батч отдается по истечении maxWait
	msgs := make([]string, available)
	for i := 0; i < available; i++ {
		msgs[i] = fmt.Sprintf("msg-%d", i+1)
	}
	return BatchFetchResult{Messages: msgs, Waited: maxWait}
}

func TestPullBatchTimeout(t *testing.T) {
	// Сценарий 1: Доступно 15 сообщений (запрос 10) -> Мгновенный возврат
	resFull := SimulateFetchWithTimeout(15, 10, 1*time.Second)
	if len(resFull.Messages) != 10 || resFull.Waited != 0 {
		t.Fatalf("Полный батч должен отдаваться мгновенно: %+v", resFull)
	}

	// Сценарий 2: Доступно 3 сообщения (запрос 10) -> Возврат по таймауту 1 сек
	resPartial := SimulateFetchWithTimeout(3, 10, 1*time.Second)
	if len(resPartial.Messages) != 3 || resPartial.Waited != 1*time.Second {
		t.Fatalf("Частичный батч должен ждать maxWait: %+v", resPartial)
	}

	fmt.Println("Батчинг запросов через Fetch(10, MaxWait) успешно подтвержден:")
	fmt.Printf("  • Полный батч (10/10):    возвращен мгновенно (Задержка: %v)\n", resFull.Waited)
	fmt.Printf("  • Неполный батч (3/10):   возвращен по таймауту (%v)\n", resPartial.Waited)
	fmt.Println("  • Никаких бесконечных блокировок потока, ресурсы утилизируются оптимально!")
}
```

ℹ️ Пакетная вычитка с мгновенным возвратом полного батча и отсечкой по MaxWait

## Под капотом

Сетевой протокол JetStream использует специальный заголовок `Nats-Pending-Messages` во фреймах выдачи, сообщая клиенту, сколько еще сообщений ожидает в стриме.

## Подводные камни

Обрабатывать батч в 100 сообщений последовательно в одном потоке: если каждое сообщение требует 100 мс, суммарное время составит 10 секунд, что может превысить `AckWait`. Используют параллельную обработку внутри батча через `sync.WaitGroup`.

## На собеседовании

**Вопрос с собеседования:** «Как в JetStream запустить чтение бесконечного потока пачек без постоянного создания новых таймеров в цикле Fetch?»
**Ответ:** Использовать метод `sub.FetchBatch(10, ...)` или современный API JetStream 2.10+ `consumer.Consume(handler)`. Метод `Consume` автоматически поддерживает оптимальное количество in-flight запросов к брокеру в фоне, избавляя от ручного управления циклами `Fetch`.
