# Модель Fire-and-Forget в Core NATS: демонстрация безвозвратной потери сообщений в оффлайне

## Условие

**Core NATS (Fire and Forget)**: Подключись к NATS. Запусти консьюмера `nc.Subscribe("updates", handler)`. В другой горутине сделай `nc.Publish("updates", data)`. Останови консьюмера, сделай Publish, снова запусти консьюмера. Убедись, что сообщение потеряно навсегда (Core NATS не хранит данные).

## Теория

Природа Fire-and-Forget в NATS Core:
- NATS Core спроектирован по принципу максимальной простоты и скорости:
  - Брокер никогда не пишет сообщения на диск и не держит их в оперативной памяти для будущих подписчиков.
  - Если в момент публикации в теме `updates` нет ни одного слушателя:
    - Брокер мгновенно уничтожает сообщение.
    - Никаких ошибок продюсеру не возвращается.
  - При перезапуске консьюмер начнет получать только те события, которые будут опубликованы ПОСЛЕ его подключения.

## Решение по шагам

1. Создайте модель брокера Core NATS с переключателем активности подписчика.
2. Проверьте успешное получение сообщения активным подписчиком.
3. Отключите подписчика и опубликуйте второе сообщение.
4. Подключите подписчика снова и убедитесь, что второе сообщение потеряно навсегда.

## Код решения

**`core_fire_and_forget_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FireAndForgetBroker struct {
	activeSubscriber func(string)
}

func (b *FireAndForgetBroker) Publish(data string) (delivered bool) {
	if b.activeSubscriber != nil {
		b.activeSubscriber(data)
		return true
	}
	// Подписчика нет -> сообщение уничтожается навсегда!
	return false
}

func TestCoreFireAndForget(t *testing.T) {
	broker := &FireAndForgetBroker{}
	var received []string

	// 1. Консьюмер активен
	broker.activeSubscriber = func(data string) {
		received = append(received, data)
	}

	d1 := broker.Publish("Message #1 (Консьюмер ONLINE)")
	if !d1 || len(received) != 1 {
		t.Fatal("Сообщение 1 должно быть доставлено")
	}

	// 2. Консьюмер ОСТАНОВЛЕН
	broker.activeSubscriber = nil
	d2 := broker.Publish("Message #2 (Консьюмер OFFLINE)")
	if d2 {
		t.Fatal("Сообщение 2 не должно быть доставлено")
	}

	// 3. Консьюмер снова запущен
	broker.activeSubscriber = func(data string) {
		received = append(received, data)
	}

	d3 := broker.Publish("Message #3 (Консьюмер снова ONLINE)")
	if !d3 || len(received) != 2 {
		t.Fatal("Сообщение 3 должно быть доставлено")
	}

	fmt.Println("Поведение Fire-and-Forget в Core NATS успешно подтверждено:")
	fmt.Printf("  • Сообщение #1 (Online):  ДОСТАВЛЕНО\n")
	fmt.Printf("  • Сообщение #2 (Offline): ПОТЕРЯНО НАВСЕГДА (В логе отсутствует)\n")
	fmt.Printf("  • Сообщение #3 (Online):  ДОСТАВЛЕНО\n")
	fmt.Printf("  • Итого у консьюмера:     %v\n", received)
	fmt.Println("  • Core NATS не хранит историю сообщений, для персистентности необходим JetStream!")
}
```

## Под капотом

В функции маршрутизации NATS Core при отсутствии совпадений в дереве подписок (sublist) буфер сетевого пакета освобождается немедленно (`return without forwarding`), не сохраняясь ни в каких внутренних структурах.

## Подводные камни

Полагаться на то, что NATS Core «подождет секундочку», пока под в Kubernetes перезагрузится: Core NATS уничтожает сообщение в ту же наносекунду, когда сокет консьюмера закрылся.

## На собеседовании

**Вопрос с собеседования:** «В чем фундаментальная разница архитектурной философии NATS Core и Apache Kafka?»
**Ответ:** Kafka спроектирована как распределенный лог фиксации (Commit Log First): любое сообщение обязано быть записано на диск до доставки. NATS Core спроектирован как сверхскоростной сетевой коммутатор сообщений (Message Dialtone / Fast Network Fabric): его цель — доставить байты между сокетами в оперативной памяти с минимальной наносекундной задержкой, а персистентность отдана опциональному модулю JetStream.
