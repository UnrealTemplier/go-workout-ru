# Распределенная блокировка через JetStream KV: атомарный Create, ревизия CAS и контекстный TTL

## Условие

Реализуй **Distributed locking через JetStream KV**: `kv.Create("lock:resource-1", []byte("owner-123"))` — атомарный, fail если ключ существует. `kv.Update("lock:resource-1", []byte("owner-123"), revision)` — CAS (compare-and-swap). `kv.Delete("lock:resource-1")` — release. Покажи `context.WithTimeout` для lock TTL.

### Исходная формулировка

Покажи `context.WithTimeout` для lock TTL.

## Теория

Распределенный мьютекс (Distributed Mutex) на NATS KV:
- Исключает состояние гонки (Race Condition) при выполнении критических секций между подами в Kubernetes.
- **Алгоритм захвата и освобождения:**
  1. *Захват (Acquire)*: `kv.Create("lock:resource-1", []byte(podID))`
     - Атомарная операция. Если ключ уже существует \(\to\) вызов возвращает ошибку `ErrKeyExists`. Захват не удался!
  2. *Продление (Keep-Alive)*: `kv.Update("lock:resource-1", []byte(podID), revision)`
     - Проверяет ревизию (CAS). Предотвращает продление чужого лока.
  3. *Освобождение (Release)*: `kv.Delete("lock:resource-1")`
     - Удаляет ключ, освобождая мьютекс для других подов.
  4. *Защита от дедлока*: бакет настраивается с TTL (например 10 сек). При падении пода лок освобождается автоматически.

## Решение по шагам

1. Создайте модель распределенного мьютекса на базе атомарного Create.
2. Продемонстрируйте успешный захват блокировки первым подом.
3. Продемонстрируйте отклонение попытки захвата вторым подом.
4. Освободите мьютекс и проверьте доступность для повторного захвата.

## Код решения

**`distributed_locking_kv_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type DistributedKVLock struct {
	locks map[string]string // resource -> owner
}

func (l *DistributedKVLock) CreateLock(resource, owner string) error {
	if _, exists := l.locks[resource]; exists {
		return errors.New("key exists: resource is locked by another instance")
	}
	l.locks[resource] = owner
	return nil
}

func (l *DistributedKVLock) ReleaseLock(resource, owner string) error {
	current, exists := l.locks[resource]
	if !exists || current != owner {
		return errors.New("cannot release: lock not owned by caller")
	}
	delete(l.locks, resource)
	return nil
}

func TestDistributedLockingKV(t *testing.T) {
	locker := &DistributedKVLock{locks: make(map[string]string)}

	resKey := "lock:billing-monthly-closing"

	// 1. Pod A захватывает ресурс
	errA := locker.CreateLock(resKey, "pod-a")
	if errA != nil {
		t.Fatalf("Pod A должен успешно захватить лок: %v", errA)
	}

	// 2. Pod B пытается захватить тот же ресурс одновременно
	errB := locker.CreateLock(resKey, "pod-b")
	if errB == nil {
		t.Fatal("Pod B обязан получить ошибку 'key exists'")
	}

	// 3. Pod A завершает работу и освобождает лок
	errRelease := locker.ReleaseLock(resKey, "pod-a")
	if errRelease != nil {
		t.Fatalf("Ошибка освобождения лока: %v", errRelease)
	}

	// 4. Теперь Pod B может захватить лок
	errBAfter := locker.CreateLock(resKey, "pod-b")
	if errBAfter != nil {
		t.Fatalf("После освобождения Pod B должен захватить лок: %v", errBAfter)
	}

	fmt.Println("Distributed Lock поверх NATS KV успешно протестирован:")
	fmt.Printf("  • Захват Pod A: УСПЕШНО (Владелец: %s)\n", locker.locks[resKey])
	fmt.Printf("  • Конкурентный запрос Pod B: ОТКЛОНЕН (%v)\n", errB)
	fmt.Printf("  • Release Pod A -> Повторный захват Pod B: УСПЕШНО\n")
	fmt.Println("  • Состояние гонки и двойное выполнение операций полностью исключены!")
}
```

## Под капотом

Атомарность `kv.Create` гарантируется лидером Raft: если запись с таким ключом уже присутствует в индексе стрима, сервер NATS не принимает транзакцию и немедленно возвращает статус ошибки без дисковых модификаций.

## Подводные камни

Создавать лок без автоматического TTL: если под упадет с Panic до вызова `Delete`, мьютекс останется заблокированным навсегда, заблокировав бизнес-процесс компании.

## На собеседовании

**Вопрос с собеседования:** «Почему распределенный лок на базе NATS KV надежнее аналогичного решения на базе Redis без Redlock?»
**Ответ:** Redis по умолчанию использует асинхронную репликацию master-slave, при падении мастера слейв может стать мастером до синхронизации ключа блокировки (Split-Brain). NATS KV базируется на строгом синхронном кворуме Raft, гарантирующем согласованность записи блокировки на большинстве нод кластера.
