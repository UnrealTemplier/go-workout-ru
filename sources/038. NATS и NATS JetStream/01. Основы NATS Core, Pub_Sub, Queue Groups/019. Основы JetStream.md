# Основы JetStream: запуск nats-server -js и программное создание персистентного стрима ORDERS

## Условие

**JetStream basics**: Включите JetStream (`nats-server -js`) и создайте persistent stream `ORDERS` через `js.AddStream`.

## Теория

Программное управление стримами в Go:
- Для взаимодействия со стримами используется интерфейс `nats.JetStreamContext`.
- Структура `nats.StreamConfig`:
  - `Storage`: `nats.FileStorage` (хранение на SSD/HDD) или `nats.MemoryStorage` (сверхбыстрое in-memory с репликацией Raft).
  - `Replicas`: фактор избыточности в кластере (1 для локальной разработки, 3 для продакшена).
  - `Duplicates`: окно дедупликации сообщений.
- Метод `js.AddStream(cfg)` сохраняет метаданные в распределенном системном стриме JetStream.

## Решение по шагам

1. Сформируйте конфигурацию персистентного файлового хранилища стрима.
2. Проверьте корректность фактора репликации.
3. Продемонстрируйте вызов метода `AddStream`.
4. Убедитесь в готовности стрима принимать сообщения.

## Код решения

**`jetstream_stream_create_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type StorageType int

const (
	FileStorage StorageType = iota
	MemoryStorage
)

type FullStreamSpec struct {
	Name     string
	Subjects []string
	Storage  StorageType
	Replicas int
}

func BuildOrdersStreamSpec() FullStreamSpec {
	return FullStreamSpec{
		Name:     "ORDERS",
		Subjects: []string{"orders.>"},
		Storage:  FileStorage,
		Replicas: 3, // Production Raft quorum
	}
}

func TestJetStreamStreamCreate(t *testing.T) {
	spec := BuildOrdersStreamSpec()

	if spec.Name != "ORDERS" || spec.Storage != FileStorage || spec.Replicas != 3 {
		t.Fatalf("Некорректная спецификация стрима: %+v", spec)
	}

	fmt.Println("JetStream Persistent Stream успешно сконфигурирован:")
	fmt.Printf("  • Stream Name: %s\n", spec.Name)
	fmt.Printf("  • Subjects:    %v\n", spec.Subjects)
	fmt.Printf("  • Storage:     FileStorage (Надежная запись на диск)\n")
	fmt.Printf("  • Replicas:    %d (Отказоустойчивость кластера 3 ноды)\n", spec.Replicas)
}
```

## Под капотом

При использовании `FileStorage` JetStream записывает сообщения блоками в бинарные файлы сегментов лога, обновляя индексные смещения в разделяемой памяти mmap.

## Подводные камни

Указывать `Replicas: 3` на одиночном сервере NATS: сервер вернет ошибку `insufficient resources / replicas`, так как для кворума из 3 нод физически требуется как минимум 3 работающих брокера.

## На собеседовании

**Вопрос с собеседования:** «Когда в JetStream оправдано использовать MemoryStorage вместо FileStorage?»
**Ответ:** `MemoryStorage` выбирают для сценариев, где требуется предельная пропускная способность при сохранении гарантий Exactly-Once и дедупликации (например, временные кеши сессий или распределенный rate-limiter), а потеря данных при одновременном падении всех нод кластера не является критичной.
