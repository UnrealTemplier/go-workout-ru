# Географическая и предметная иерархия субъектов: orders.us.electronics и селективные подписки

## Условие

Реализуй **Subject hierarchies и wildcards**: публикуй на `"orders.us.electronics"`, `"orders.eu.books"`. Подпишись на `"orders.>"` (получит всё), `"orders.us.>"` (только US), `"orders.*.electronics"` (electronics в любом регионе). Покажи гибкость routing'а.

## Теория

Проектирование иерархии тем (Subject Hierarchy Design):
- Стандарт корпоративного именования тем: `<домен>.<регион>.<категория>.<действие>`.
- Примеры гибкой фильтрации:
  - `orders.>` — глобальный аудит и сбор аналитики (получает абсолютно все заказы мира).
  - `orders.us.>` — региональный процессинг заказов США.
  - `orders.*.electronics` — специализированный сервис гарантийного обслуживания электроники любого континента.
- Маршрутизация выполняется на брокере без необходимости написания кастомных роутеров.

## Решение по шагам

1. Создайте структуру маршрутизатора с поддержкой шаблонов тем.
2. Зарегистрируйте трех слушателей: глобального (`orders.>`), регионального (`orders.us.>`) и товарного (`orders.*.electronics`).
3. Опубликуйте заказ `orders.us.electronics`.
4. Проверьте, какие подписчики получили событие.

## Код решения

**`subject_hierarchy_routing_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type RouterSubscriber struct {
	Name    string
	Pattern string
	Count   int
}

func (s *RouterSubscriber) TryReceive(subject string) {
	pTokens := strings.Split(s.Pattern, ".")
	sTokens := strings.Split(subject, ".")

	matched := true
	for i, pt := range pTokens {
		if pt == ">" {
			matched = true
			break
		}
		if i >= len(sTokens) || (pt != "*" && pt != sTokens[i]) {
			matched = false
			break
		}
	}
	if matched && (len(pTokens) == len(sTokens) || pTokens[len(pTokens)-1] == ">") {
		s.Count++
	}
}

func TestSubjectHierarchyRouting(t *testing.T) {
	subAll := &RouterSubscriber{Name: "Глобальный Аудит", Pattern: "orders.>"}
	subUS := &RouterSubscriber{Name: "Регион США", Pattern: "orders.us.>"}
	subElec := &RouterSubscriber{Name: "Сервис Электроники", Pattern: "orders.*.electronics"}

	subs := []*RouterSubscriber{subAll, subUS, subElec}

	// Публикуем заказ электроники из США
	eventSubject := "orders.us.electronics"
	for _, s := range subs {
		s.TryReceive(eventSubject)
	}

	if subAll.Count != 1 || subUS.Count != 1 || subElec.Count != 1 {
		t.Fatalf("Все 3 подписчика обязаны получить orders.us.electronics: %+v", subs)
	}

	// Публикуем книги из Европы
	eventEU := "orders.eu.books"
	for _, s := range subs {
		s.TryReceive(eventEU)
	}

	// subAll должен иметь 2, subUS — 1, subElec — 1
	if subAll.Count != 2 || subUS.Count != 1 || subElec.Count != 1 {
		t.Fatalf("Некорректная фильтрация для orders.eu.books: %+v", subs)
	}

	fmt.Println("Иерархическая маршрутизация NATS успешно подтверждена:")
	fmt.Printf("  • Событие 'orders.us.electronics' получено: Всеми тремя сервисами!\n")
	fmt.Printf("  • Событие 'orders.eu.books' получено:       Только глобальным аудитом (orders.>)\n")
}
```

## Под капотом

Маршрутизация NATS не зависит от формата полезной нагрузки: брокер анализирует только байты темы в заголовке фрейма, что обеспечивает задержку маршрутизации менее 50 наносекунд.

## Подводные камни

Использовать разделители `/` вместо `.` (по аналогии с MQTT): в NATS единственным стандартом разделителя токенов является символ точки `.`.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество Subject-маршрутизации NATS перед Topic Exchanges в RabbitMQ?»
**Ответ:** В RabbitMQ для маршрутизации требуется явно объявлять Exchange, создавать очереди и настраивать связки (Bindings). В NATS маршрутизация полностью динамическая и декларативная: брокер не требует предварительной настройки роутинга, всё определяется паттернами подписок.
