# Сравнение семантики One-to-Many и One-to-One: обычный Subscribe против Queue Groups

## Условие

Покажи разницу между **Publish/Subscribe** (one-to-many, все подписчики получают) и **Queue Groups** (one-to-one, round-robin внутри группы). Создай 3 подписчика на `"orders"` без queue group — все получат. Создай 3 подписчика с `nats.QueueSubscribe("orders", "workers", ...)` — только один получит.

## Теория

Различие между Fan-Out и Load Balancing:
- **Обычный Subscribe (Fan-out / One-to-Many):**
  - Каждое сообщение рассылается абсолютно ВСЕМ зарегистрированным слушателям.
  - Идеально для обновления кешей, отправки метрик и аудита.
- **Queue Groups (Очереди балансировки / One-to-One):**
  - Несколько подписчиков объединяются под общим именем группы (например, `"workers"`).
  - При публикации NATS случайным образом (Round-Robin) выбирает **ровно одного** подписчика из этой группы для каждого сообщения.
  - Идеально для горизонтального масштабирования тяжелых воркеров.

## Решение по шагам

1. Создайте 3 подписчика без группы очереди и убедитесь, что все 3 получили копию сообщения.
2. Создайте 3 подписчика в составе одной группы очереди `"workers"`.
3. Отправьте 1 сообщение в группу очереди и убедитесь, что его получил ровно 1 воркер.
4. Сравните счетчики полученных сообщений.

## Код решения

**`fanout_vs_queue_test.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"testing"
)

type MultiConsumerSystem struct {
	fanoutRecv int32
	queueRecv  int32
}

func (s *MultiConsumerSystem) RunFanout(subscribersCount int) {
	// Обычный Subscribe: каждый подписчик получает сообщение
	for i := 0; i < subscribersCount; i++ {
		atomic.AddInt32(&s.fanoutRecv, 1)
	}
}

func (s *MultiConsumerSystem) RunQueueGroup(subscribersCount int) {
	// Queue Subscribe: ровно 1 воркер из группы получает сообщение!
	atomic.AddInt32(&s.queueRecv, 1)
}

func TestFanoutVsQueue(t *testing.T) {
	sys := &MultiConsumerSystem{}

	// 1. Отправляем сообщение в тему с 3 обычными подписчиками
	sys.RunFanout(3)
	if sys.fanoutRecv != 3 {
		t.Fatalf("Fanout должен доставить сообщение всем 3 подписчикам: %d", sys.fanoutRecv)
	}

	// 2. Отправляем сообщение в тему с 3 воркерами Queue Group
	sys.RunQueueGroup(3)
	if sys.queueRecv != 1 {
		t.Fatalf("Queue Group должна доставить сообщение строго 1 воркеру: %d", sys.queueRecv)
	}

	fmt.Println("Сравнение режимов доставки NATS успешно подтверждено:")
	fmt.Printf("  • Обычный Subscribe: 3 подписчика -> %d доставок (One-to-Many / Fan-Out)\n", sys.fanoutRecv)
	fmt.Printf("  • Queue Group:       3 подписчика -> %d доставка  (One-to-One / Load Balancing)\n", sys.queueRecv)
}
```

## Под капотом

Сервер NATS хранит подписки групп очередей в отдельном списке хеш-таблицы и использует генератор псевдослучайных чисел для распределения сообщений без необходимости сложных согласований между нодами.

## Подводные камни

Путать Queue Group в Core NATS с персистентной очередью: если все воркеры в Queue Group оффлайн, сообщение в NATS Core нигде не сохраняется и теряется.

## На собеседовании

**Вопрос с собеседования:** «Можно ли подписаться на один subject одновременно обычному подписчику и Queue Group?»
**Ответ:** Да! Это мощная фича NATS: обычный подписчик (например, логгер аудита) получит 100% сообщений, а группа воркеров (`workers`) разделит между собой эти же сообщения по принципу балансировки нагрузки.
