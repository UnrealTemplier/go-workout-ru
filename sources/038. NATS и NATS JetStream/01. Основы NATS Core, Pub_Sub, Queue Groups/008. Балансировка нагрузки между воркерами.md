# Балансировка нагрузки между воркерами: паттерн Queue Group workers и распределение задач

## Условие

Создайте **Queue Group**: несколько воркеров подписываются на одну тему с `Queue: "workers"`, и каждое сообщение получает только один из них (load balancing).

## Теория

Горизонтальное масштабирование сервисов через Queue Groups:
- В микросервисной архитектуре требуется распределять тяжелые фоновые задачи (например обработку видео, генерацию PDF или списание денег).
- Синтаксис Go-клиента:
  `nc.QueueSubscribe("tasks.process", "workers", func(m *nats.Msg) { ... })`
- Свойства:
  - NATS равномерно распределяет сообщения между всеми запущенными подами в Kubernetes.
  - Если под падает, NATS мгновенно исключает его из пула балансировки без задержек.
  - Если поднимается новый реплика-под, он мгновенно начинает получать свою долю задач.

## Решение по шагам

1. Создайте симулятор балансировщика группы очереди.
2. Подключите 3 воркера под именем группы `"workers"`.
3. Отправьте пакет из 9 сообщений.
4. Проверьте, что каждое сообщение было доставлено ровно 1 воркеру.

## Код решения

**`queue_group_load_balancing_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type WorkerNode struct {
	ID    int
	Tasks []string
}

type QueueGroupLoadBalancer struct {
	workers []*WorkerNode
	cursor  int
}

func (b *QueueGroupLoadBalancer) Dispatch(task string) {
	targetWorker := b.workers[b.cursor]
	targetWorker.Tasks = append(targetWorker.Tasks, task)
	b.cursor = (b.cursor + 1) % len(b.workers) // Round-Robin
}

func TestQueueGroupLoadBalancing(t *testing.T) {
	w1 := &WorkerNode{ID: 1}
	w2 := &WorkerNode{ID: 2}
	w3 := &WorkerNode{ID: 3}

	lb := &QueueGroupLoadBalancer{workers: []*WorkerNode{w1, w2, w3}}

	// Отправляем 9 задач
	for i := 1; i <= 9; i++ {
		lb.Dispatch(fmt.Sprintf("task-%d", i))
	}

	total := len(w1.Tasks) + len(w2.Tasks) + len(w3.Tasks)
	if total != 9 || len(w1.Tasks) != 3 || len(w2.Tasks) != 3 || len(w3.Tasks) != 3 {
		t.Fatalf("Нарушение балансировки: w1=%d, w2=%d, w3=%d", len(w1.Tasks), len(w2.Tasks), len(w3.Tasks))
	}

	fmt.Println("Балансировка в Queue Group 'workers' успешно подтверждена:")
	fmt.Printf("  • Воркер #1: обработал %d задач\n", len(w1.Tasks))
	fmt.Printf("  • Воркер #2: обработал %d задач\n", len(w2.Tasks))
	fmt.Printf("  • Воркер #3: обработал %d задач\n", len(w3.Tasks))
	fmt.Println("  • Ни одна задача не продублировалась, нагрузка распределена идеально!")
}
```

ℹ️ Round-Robin балансировка задач между воркерами в составе Queue Group

## Под капотом

Сервер NATS выбирает сокет получателя внутри группы за \(O(1)\) по указателю кольцевого списка, обеспечивая нулевые задержки балансировки даже при тысячах воркеров.

## Подводные камни

Использовать разные имена групп очередей на разных воркерах: если один под напишет `Queue: "worker"`, а второй `Queue: "workers"`, они будут считаться двумя независимыми группами и КАЖДОЕ сообщение будет отправлено в обе группы!

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Queue Groups в NATS от Consumer Groups в Kafka?»
**Ответ:** В Kafka партиция жестко закрепляется за одним консьюмером (если партиций 3, а воркеров 5, то 2 воркера простаивают). В NATS Queue Groups нет концепции партиций: задачи балансируются по отдельным сообщениям, поэтому 100 воркеров могут эффективно разбирать поток задач из одной темы без привязки к числу партиций.
