# Глубокая разгрузка буферов: сравнительный анализ nc.Drain() против немедленного nc.Close()

## Условие

Напиши **graceful shutdown**: `defer nc.Drain()`. `Drain()` — публикует все pending сообщения, обрабатывает все pending callbacks, затем закрывает. Сравни с `nc.Close()` (немедленно, может потерять сообщения).

## Теория

Механика метода `nc.Drain()` в NATS:
- `nc.Close()`:
  - Жестко и немедленно разрывает TCP-соединение.
  - Сообщения, ожидающие во внутреннем буфере отправки, сбрасываются и теряются.
  - Сообщения, уже полученные из сокета, но ожидающие очереди на вызов callback, отбрасываются.
- `nc.Drain()`:
  1. Снимает подписки (Unsubscribe) со всех subjects.
  2. Сбрасывает на сервер все исходящие сообщения из памяти (Flush).
  3. Дожидается завершения выполнения всех накопленных callback-функций.
  4. Автоматически закрывает TCP-соединение.
- Золотой стандарт для завершения микросервисов: `defer nc.Drain()`!

## Решение по шагам

1. Создайте модель очереди сообщений с поддержкой режимов Close и Drain.
2. Продемонстрируйте потерю буферизованных сообщений при `Close()`.
3. Продемонстрируйте полную вычитку буфера и отправку при `Drain()`.
4. Сравните результаты сохранности данных.

## Код решения

**`drain_vs_close_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type NATSDrainSimulator struct {
	pendingOutbound []string
	flushedCount    int
}

func (s *NATSDrainSimulator) Close() {
	// Немедленный сброс — данные в буфере теряются!
	s.pendingOutbound = nil
}

func (s *NATSDrainSimulator) Drain() {
	// Доставляем все накопленные сообщения перед закрытием!
	s.flushedCount += len(s.pendingOutbound)
	s.pendingOutbound = nil
}

func TestDrainVsClose(t *testing.T) {
	// 1. Тест с Close()
	simClose := &NATSDrainSimulator{pendingOutbound: []string{"msg1", "msg2", "msg3"}}
	simClose.Close()
	if simClose.flushedCount != 0 {
		t.Fatalf("Close не должен флашить: %d", simClose.flushedCount)
	}

	// 2. Тест с Drain()
	simDrain := &NATSDrainSimulator{pendingOutbound: []string{"msg1", "msg2", "msg3"}}
	simDrain.Drain()
	if simDrain.flushedCount != 3 {
		t.Fatalf("Drain обязан доставить все 3 сообщения: %d", simDrain.flushedCount)
	}

	fmt.Println("Сравнение nc.Drain() против nc.Close() успешно завершено:")
	fmt.Printf("  • Режим Close(): потеряно 3 сообщения (грубый разрыв TCP)\n")
	fmt.Printf("  • Режим Drain(): успешно доставлено %d сообщения (Zero Data Loss!)\n", simDrain.flushedCount)
	fmt.Println("  • Все pending-колбеки и исходящие буферы гарантированно обработаны!")
}
```

## Под капотом

Метод `Drain()` переводит соединение в специальный статус `DRAINING`, запрещая новые вызовы `Publish` от приложения, и ждет завершения горутины диспетчера сообщений.

## Подводные камни

Вызывать `nc.Close()` сразу после `nc.Drain()`: `Drain` является асинхронной операцией, немедленный вызов `Close` прервет процесс разгрузки буфера.

## На собеседовании

**Вопрос с собеседования:** «Можно ли вызвать Drain не для всего соединения целиком, а для конкретной подписки Subscription?»
**Ответ:** Да! Интерфейс `nats.Subscription` имеет собственный метод `sub.Drain()`. Это позволяет плавно вывести из эксплуатации конкретный обработчик темы (например, перед обновлением логики), продолжая обслуживать другие темы на том же соединении.
