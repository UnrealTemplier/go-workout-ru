# Базовый шаблон Pub/Sub: независимая публикация в тему orders.new и асинхронное получение

## Условие

Реализуйте простейший **Pub/Sub**: один клиент публикует сообщение в тему `orders.new`, другой подписывается и получает его.

## Теория

Шаблон Publish/Subscribe в NATS:
- Продюсер (Publisher) отправляет сообщение в субъект `orders.new`.
- Консьюмер (Subscriber) регистрирует функцию обратного вызова (callback).
- При получении сообщения сервером NATS он мгновенно находит всех активных подписчиков на `orders.new` и копирует байты в их буферы сокетов.
- Подписчики полностью изолированы: продюсер не знает о количестве и статусе подписчиков.

## Решение по шагам

1. Создайте структуру заказа с идентификатором и суммой.
2. Зарегистрируйте подписчика на тему `orders.new`.
3. Опубликуйте сериализованный заказ в тему.
4. Проверьте получение заказа подписчиком без искажений.

## Код решения

**`pubsub_orders_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"testing"
)

type OrderCreated struct {
	OrderID string  `json:"order_id"`
	Amount  float64 `json:"amount"`
}

type EventBus struct {
	mu   sync.Mutex
	subs map[string][]func([]byte)
}

func NewEventBus() *EventBus {
	return &EventBus{subs: make(map[string][]func([]byte))}
}

func (b *EventBus) Subscribe(subject string, handler func([]byte)) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.subs[subject] = append(b.subs[subject], handler)
}

func (b *EventBus) Publish(subject string, payload []byte) {
	b.mu.Lock()
	defer b.mu.Unlock()
	for _, h := range b.subs[subject] {
		h(payload)
	}
}

func TestPubSubOrders(t *testing.T) {
	bus := NewEventBus()

	var received OrderCreated
	var wg sync.WaitGroup
	wg.Add(1)

	// Подписчик на тему orders.new
	bus.Subscribe("orders.new", func(data []byte) {
		_ = json.Unmarshal(data, &received)
		wg.Done()
	})

	// Публикатор
	order := OrderCreated{OrderID: "ord-771", Amount: 14500.50}
	bytes, _ := json.Marshal(order)
	bus.Publish("orders.new", bytes)

	wg.Wait()

	if received.OrderID != "ord-771" || received.Amount != 14500.50 {
		t.Fatalf("Ошибка данных заказа: %+v", received)
	}

	fmt.Println("Базовый Pub/Sub успешно протестирован:")
	fmt.Printf("  • Тема:       orders.new\n")
	fmt.Printf("  • Заказ:      %s\n", received.OrderID)
	fmt.Printf("  • Сумма:      %.2f руб.\n", received.Amount)
}
```

## Под капотом

Сервер NATS хранит подписки в префиксном дереве (Radix Tree / Trie). Поиск совпадений для темы выполняется за \(O(K)\), где \(K\) — длина темы, вне зависимости от миллионов активных подписчиков.

## Подводные камни

Блокировать горутину обработчика `nc.Subscribe` долгими сетевыми вызовами: по умолчанию все сообщения одной подписки обрабатываются в одной горутине, долгое выполнение приведет к переполнению входящего буфера (`Slow Consumer`).

## На собеседовании

**Вопрос с собеседования:** «Что происходит с медленным подписчиком (Slow Consumer) в NATS Core?»
**Ответ:** Если входящий буфер подписчика переполняется выше лимита (по умолчанию 65536 сообщений или 10 МБ), сервер NATS принудительно разрывает соединение с клиентом и возвращает ошибку `Slow Consumer Dropped`, чтобы не задерживать доставку другим клиентам.
