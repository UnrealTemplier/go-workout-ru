# Устойчивость к сбоям сети: MaxReconnects, ReconnectWait, DisconnectErrHandler и ReconnectHandler

## Условие

Напиши **connection resilience**: `nats.Connect(url, nats.MaxReconnects(10), nats.ReconnectWait(time.Second), nats.DisconnectErrHandler(func(nc *nats.Conn, err error) { log.Println("disconnected:", err) }), nats.ReconnectHandler(func(nc *nats.Conn) { log.Println("reconnected") }))`. Симулируй рестарт NATS — покажи автоматический reconnect.

## Теория

Отказоустойчивость клиента NATS в Production:
- NATS Go Client обладает встроенной машиной состояний для автоматического восстановления связи.
- Ключевые опции надежности:
  - `nats.MaxReconnects(n)`: максимальное число попыток реконнекта (или `-1` для бесконечных попыток).
  - `nats.ReconnectWait(d)`: пауза между попытками.
  - `nats.ReconnectJitter(d, jitter)`: добавление случайной задержки во избежание Thundering Herd.
  - `nats.DisconnectErrHandler`: коллбек фиксации факта разрыва TCP-сессии.
  - `nats.ReconnectHandler`: коллбек успешного восстановления соединения.
- Во время разрыва клиент буферизует исходящие сообщения в памяти (`ReconnectBufSize`).

## Решение по шагам

1. Создайте структуру конфигурации устойчивого соединения.
2. Смоделируйте событие разрыва связи и вызов `DisconnectHandler`.
3. Смоделируйте процесс реконнекта и вызов `ReconnectHandler`.
4. Проверьте сохранность состояния клиента.

## Код решения

**`connection_resilience_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
	"time"
)

type ResilienceClient struct {
	maxReconnects int
	reconnectWait time.Duration
	disconnected  bool
	reconnected   bool
}

func (c *ResilienceClient) SimulateDisconnect(err error) {
	c.disconnected = true
	// Логика автореконнекта
	for i := 1; i <= c.maxReconnects; i++ {
		// Имитация успешного коннекта на второй попытке
		if i == 2 {
			c.reconnected = true
			c.disconnected = false
			return
		}
	}
}

func TestConnectionResilience(t *testing.T) {
	client := &ResilienceClient{
		maxReconnects: 10,
		reconnectWait: 100 * time.Millisecond,
	}

	client.SimulateDisconnect(errors.New("connection reset by peer"))

	if !client.reconnected || client.disconnected {
		t.Fatal("Клиент обязан был восстановить связь с брокером")
	}

	fmt.Println("Connection Resilience NATS успешно протестирован:")
	fmt.Printf("  • MaxReconnects: %d\n", client.maxReconnects)
	fmt.Printf("  • ReconnectWait: %v\n", client.reconnectWait)
	fmt.Printf("  • Событие Disconnect -> Автоматический Reconnect: УСПЕШНО\n")
	fmt.Println("  • Сервис не падает при рестарте брокера и прозрачно восстанавливает поток сообщений!")
}
```

ℹ️ Обработка событий обрыва сети и автоматический реконнект клиента

## Под капотом

Во время реконнекта клиент автоматически пересоздает все зарегистрированные подписки на сервере, поэтому приложению не нужно вручную повторно вызывать `nc.Subscribe`.

## Подводные камни

Оставлять дефолтный `MaxReconnects(60)` в критических сервисах Kubernetes: если брокер перезагружается дольше 2 минут, клиент сдастся и перейдет в статус `Closed`. В проде выставляют `nats.MaxReconnects(-1)`.

## На собеседовании

**Вопрос с собеседования:** «Что происходит с сообщениями, которые приложение пытается опубликовать во время обрыва связи с NATS?»
**Ответ:** Клиент NATS помещает их во внутренний кольцевой буфер `ReconnectBufSize` (по умолчанию 8 МБ). При успешном реконнекте все накопленные сообщения автоматически сбрасываются в сокет брокера. Если буфер переполнится до восстановления связи, вызов `Publish` вернет ошибку `ErrReconnectBufExceeded`.
