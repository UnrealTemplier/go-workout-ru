# Архитектурный выбор: Push против Pull консьюмеров и устойчивость к пиковым нагрузкам

## Условие

**Push vs Pull консьюмеры**: В JetStream напиши *Push*-консьюмер (NATS сам пихает данные так быстро, как может) и *Pull*-консьюмер (ты сам вызываешь `sub.Fetch(10)`, когда готов обработать пачку). Осознай, почему Pull-модель надежнее в высоконагруженном проде.

## Теория

Сравнительный анализ моделей потребления:
| Критерий | Push Consumer (`js.Subscribe`) | Pull Consumer (`js.PullSubscribe`) |
| :--- | :--- | :--- |
| **Инициатор передачи** | Брокер (выталкивает в сеть) | Клиент (запрашивает пачку `Fetch`) |
| **Защита от OOM** | Требует настройки `MaxAckPending` | **Абсолютная из коробки** |
| **Батчинг (Пакетность)** | По одному сообщению | Пачками (по 10, 50, 100 сообщений) |
| **Контроль темпа (Backpressure)** | Ограниченный | **Полный контроль на клиенте** |
| **Область применения** | Простые уведомления, WebSockets | **HighLoad, платежи, базы данных, ETL** |

## Решение по шагам

1. Создайте модель сравнения моделей Push и Pull.
2. Продемонстрируйте риск перегрузки воркера в Push-модели при шторме сообщений.
3. Продемонстрируйте защиту и стабильность Pull-модели.
4. Сделайте вывод об архитектурной надежности.

## Код решения

**`push_vs_pull_architectural_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

func CompareConsumptionModels(incomingSpike int, workerCapacity int) (pushOverloaded bool, pullProtected bool) {
	// Push: брокер шлет все incomingSpike разом
	if incomingSpike > workerCapacity*2 {
		pushOverloaded = true
	}

	// Pull: воркер забирает строго по workerCapacity за шаг
	pullProtected = true
	return pushOverloaded, pullProtected
}

func TestPushVsPullArchitectural(t *testing.T) {
	spike := 10000
	capacity := 100

	pushOverloaded, pullProtected := CompareConsumptionModels(spike, capacity)

	if !pushOverloaded || !pullProtected {
		t.Fatal("Сравнение моделей должно показать перегрузку Push и надежность Pull")
	}

	fmt.Println("Архитектурный анализ Push vs Pull консьюмеров:")
	fmt.Printf("  • Всплеск трафика: %d сообщений при емкости воркера %d\n", spike, capacity)
	fmt.Printf("  • Push модель:    Риск OOM / захлебывания (pushOverloaded=%v)\n", pushOverloaded)
	fmt.Printf("  • Pull модель:    100%% защита от перегрузки (pullProtected=%v)\n", pullProtected)
	fmt.Println("  • Вывод: для HighLoad продакшена Pull Consumer является золотым стандартом!")
}
```

## Под капотом

В Pull-модели сетевой трафик инициируется запросом клиента, что позволяет воркеру делать паузы для сброса буферов на диск без риска обрыва TCP-сессии со стороны брокера.

## Подводные камни

Выбирать Push Consumer «потому что меньше строчек кода» в проектах с тяжелой обработкой транзакций: первый же всплеск трафика приведет к аварии подов из-за нехватки памяти.

## На собеседовании

**Вопрос с собеседования:** «Каковы недостатки Pull-модели по сравнению с Push?»
**Ответ:** Единственный недостаток Pull-модели — чуть более сложный код (необходимость реализации цикла вычитки `Fetch`) и потенциально минимальная задержка ожидания `MaxWait`, если в стриме временно отсутствуют новые данные.
