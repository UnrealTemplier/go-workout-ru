# Архитектурные границы применимости NATS: задержка до 1 мс, сильные стороны и антипаттерны

## Условие

**Когда использовать NATS**: Ultra-low latency (<1ms), простой pub/sub, request/reply, service discovery. Не подходит для persistence (без JetStream) и сложных роутингов.

## Теория

Сравнительный архитектурный анализ NATS в ландшафте очередей:
| Критерий | NATS (Core + JetStream) | Apache Kafka | RabbitMQ |
| :--- | :--- | :--- | :--- |
| **Сетевая задержка** | **Субмиллисекундная (<1 мс)** | Средняя (2–10 мс) | Низкая (1–3 мс) |
| **Сложность развертывания** | **1 статический бинарник Go** | Высокая (Кластер, JVM/KRaft) | Средняя (Erlang рантайм) |
| **Встроенный K/V и S3** | **Да (KV Store, Object Store)** | Нет (только лог) | Нет |
| **Сложная маршрутизация** | Только темы и подстановочные знаки | Только топики и партиции | **Очень богатая (Exchange Bindings)** |
- **Когда выбирать NATS:** Микросервисный RPC, Ultra-Low Latency телеметрия, Service Discovery, Edge/IoT, легковесные очереди.
- **Когда NATS не подходит:** Сложная трансформация сообщений в брокере, тяжелая аналитика Big Data с SQL (для этого лучше Kafka + Spark/Flink).

## Решение по шагам

1. Создайте матрицу критериев выбора систем обмена сообщениями.
2. Проверьте рекомендацию NATS для микросервисного RPC с задержкой <1 мс.
3. Проверьте рекомендацию RabbitMQ для сложной маршрутизации заголовков.
4. Сформируйте итоговый архитектурный вердикт.

## Код решения

**`nats_architecture_matrix_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SystemRequirements struct {
	MaxLatencyMS      float64
	NeedsSingleBinary bool
	NeedsExchangeEx   bool
}

func ChooseBroker(req SystemRequirements) string {
	if req.NeedsExchangeEx {
		return "RabbitMQ"
	}
	if req.MaxLatencyMS < 1.0 && req.NeedsSingleBinary {
		return "NATS (Core + JetStream)"
	}
	return "Apache Kafka"
}

func TestNATSArchitectureMatrix(t *testing.T) {
	natsReq := SystemRequirements{
		MaxLatencyMS:      0.5,
		NeedsSingleBinary: true,
		NeedsExchangeEx:   false,
	}

	decision := ChooseBroker(natsReq)
	if decision != "NATS (Core + JetStream)" {
		t.Fatalf("Ожидался выбор NATS: %s", decision)
	}

	fmt.Println("Архитектурный выбор брокера успешно подтвержден:")
	fmt.Printf("  • Требования: задержка <1 мс, один бинарник Go, KV хранилище\n")
	fmt.Printf("  • Решение:    %s\n", decision)
	fmt.Println("  • Границы применимости и преимущества NATS полностью обоснованы!")
}
```

## Под капотом

Сервер NATS потребляет менее 20 МБ оперативной памяти в простое и стартует за 5 миллисекунд, что делает его идеальным для бессерверных сред и встраивания в IoT-устройства.

## Подводные камни

Пытаться реализовать тяжелый Data Lake прямо внутри NATS: для долговременного хранения петабайтов данных используют специализированные распределенные хранилища (ClickHouse, HDFS, S3).

## На собеседовании

**Вопрос с собеседования:** «Почему ведущие технологические компании внедряют NATS в дополнение к существующей Kafka?»
**Ответ:** NATS заменяет тяжелый сервисный межсетевой экран (Service Mesh) для синхронного общения микросервисов внутри кластера и на границе Edge/IoT с субмиллисекундной скоростью, а Kafka остается центральной шиной для тяжелой аналитики, Data Warehouse и долговременного Event Sourcing.
