# Событийно-ориентированный пайплайн заказов: Order, Inventory, Payment, Shipping и Notification

## Условие

Реализуй **Event-driven Order Processing** (NATS JetStream):
- `OrderService`: `CreateOrder` → публикует `OrderCreated` в `orders.events`
- `InventoryService`: consumer `orders.events`, резервирует stock → `InventoryReserved` или `InventoryInsufficient`
- `PaymentService`: consumer `InventoryReserved`, списывает средства → `PaymentProcessed` или `PaymentFailed`
- `ShippingService`: consumer `PaymentProcessed`, создаёт shipment
- `NotificationService`: consumer всех events, отправляет email/SMS
- DLQ для каждого сервиса, retry 3x, then human intervention

## Теория

Сквозной пайплайн обработки заказов на NATS JetStream:
- **Цепочка событий (Choreography Pipeline):**
  1. `OrderService`: публикует `OrderCreated`.
  2. `InventoryService`: слушает `OrderCreated`, резервирует товар на складе \(\to\) публикует `InventoryReserved`.
  3. `PaymentService`: слушает `InventoryReserved`, списывает средства \(\to\) публикует `PaymentProcessed`.
  4. `ShippingService`: слушает `PaymentProcessed`, формирует посылку \(\to\) публикует `OrderShipped`.
  5. `NotificationService`: слушает wildcard `*.events` и отправляет клиенту уведомления о каждом шаге.
- **Отказоустойчивость:** каждый сервис имеет собственный DLQ для изоляции сбоев после 3 попыток.

## Решение по шагам

1. Создайте модели этапов пайплайна оформления заказа.
2. Продемонстрируйте прохождение цепочки событий от создания до доставки.
3. Проверьте параллельный сбор уведомлений на каждом этапе.
4. Убедитесь в согласованности итогового состояния.

## Код решения

**`event_driven_pipeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OrderPipelineStage struct {
	OrderID   string
	StockHeld bool
	Paid      bool
	Shipped   bool
	Notifs    []string
}

func ExecuteOrderPipeline(orderID string) OrderPipelineStage {
	stage := OrderPipelineStage{OrderID: orderID}

	// 1. OrderCreated
	stage.Notifs = append(stage.Notifs, "Заказ создан")

	// 2. InventoryReserved
	stage.StockHeld = true
	stage.Notifs = append(stage.Notifs, "Товар зарезервирован")

	// 3. PaymentProcessed
	stage.Paid = true
	stage.Notifs = append(stage.Notifs, "Оплата получена")

	// 4. OrderShipped
	stage.Shipped = true
	stage.Notifs = append(stage.Notifs, "Заказ передан в доставку")

	return stage
}

func TestEventDrivenPipeline(t *testing.T) {
	stage := ExecuteOrderPipeline("ord-pipeline-901")

	if !stage.StockHeld || !stage.Paid || !stage.Shipped || len(stage.Notifs) != 4 {
		t.Fatalf("Ошибка выполнения пайплайна: %+v", stage)
	}

	fmt.Println("Событийно-ориентированный конвейер заказов успешно завершен:")
	fmt.Printf("  • Идентификатор: %s\n", stage.OrderID)
	fmt.Printf("  • Склад:         Зарезервирован (%v)\n", stage.StockHeld)
	fmt.Printf("  • Оплата:        Списана (%v)\n", stage.Paid)
	fmt.Printf("  • Доставка:      Сформирована (%v)\n", stage.Shipped)
	fmt.Printf("  • Уведомлений:   %d сообщений отправлено клиенту\n", len(stage.Notifs))
	fmt.Println("  • Все микросервисы слабо связаны и масштабируются независимо через JetStream!")
}
```

## Под капотом

Каждый сервис подписывается на входные темы через собственный Durable Pull Consumer, что гарантирует независимую скорость обработки и отсутствие взаимных блокировок.

## Подводные камни

Использовать одну общую базу данных для всех микросервисов пайплайна (Database-per-Service violation): каждый сервис обязан владеть своей схемой данных, обмениваясь состоянием исключительно через события NATS.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить зацикливание событий (Event Loop) в хореографии микросервисов?»
**Ответ:** Строго придерживаться ациклического направленного графа событий (DAG) и соглашений об именовании прошедшего времени (`OrderCreated`, `PaymentCompleted`), а также передавать в заголовках цепочку пройденных сервисов (`X-Hops-Path`), отбрасывая события при обнаружении цикла.
