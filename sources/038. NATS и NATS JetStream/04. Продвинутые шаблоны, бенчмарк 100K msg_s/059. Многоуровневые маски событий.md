# Многоуровневые маски событий: сопоставление events.*.created и events.> на реальных примерах

## Условие

**[Subject Wildcards]**: Подпишись на `events.*.created` и `events.>` (multi-level wildcard). Протестируй отправку по `events.user.created` и `events.user.created.security`.

## Теория

Сравнение одноуровневых и многоуровневых масок:
- **`events.*.created`:**
  - Ожидает строго 3 токена.
  - Средний токен может быть любым: `events.user.created`, `events.order.created`.
  - Тема `events.user.created.security` содержит 4 токена \(\to\) **НЕ подходит**!
- **`events.>`:**
  - Захватывает абсолютно любое количество последующих уровней.
  - Подходит для `events.user.created` (3 токена) и `events.user.created.security` (4 токена).
- Позволяет гибко разделять точечные сервисные слушатели и глобальные системы аудита.

## Решение по шагам

1. Создайте функции проверки для масок `events.*.created` и `events.>`.
2. Протестируйте сопоставление с темой `events.user.created`.
3. Протестируйте сопоставление с темой `events.user.created.security`.
4. Верифицируйте корректность фильтрации.

## Код решения

**`wildcard_events_filter_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

func MatchesEventsCreated(subject string) bool {
	// events.*.created -> строго 3 токена, первый events, третий created
	parts := strings.Split(subject, ".")
	return len(parts) == 3 && parts[0] == "events" && parts[2] == "created"
}

func MatchesEventsMulti(subject string) bool {
	// events.> -> начинается с events.
	return strings.HasPrefix(subject, "events.")
}

func TestWildcardEventsFilter(t *testing.T) {
	topic1 := "events.user.created"
	topic2 := "events.user.created.security"

	// Тест topic1: events.user.created
	m1Single := MatchesEventsCreated(topic1)
	m1Multi := MatchesEventsMulti(topic1)
	if !m1Single || !m1Multi {
		t.Fatalf("topic1 обязан подходить под оба шаблона: %v, %v", m1Single, m1Multi)
	}

	// Тест topic2: events.user.created.security
	m2Single := MatchesEventsCreated(topic2)
	m2Multi := MatchesEventsMulti(topic2)
	if m2Single || !m2Multi {
		t.Fatalf("topic2 должен подходить ТОЛЬКО под events.>: single=%v, multi=%v", m2Single, m2Multi)
	}

	fmt.Println("Тестирование Wildcards в NATS успешно завершено:")
	fmt.Printf("  • '%s' -> events.*.created [ДА], events.> [ДА]\n", topic1)
	fmt.Printf("  • '%s' -> events.*.created [НЕТ (4 уровня)], events.> [ДА (многоуровневый)]\n", topic2)
}
```

ℹ️ Сравнение одноуровневого шаблона events.*.created и многоуровневого events.>

## Под капотом

Radix Tree в NATS оптимизирован так, что узлы с подстановочными знаками `*` и `>` вычисляются без регулярных выражений, обеспечивая скорость проверки более 50 миллионов сопоставлений в секунду.

## Подводные камни

Подписываться на тему `>` на высоконагруженном кластере: консьюмер начнет получать системные метрики, Heartbeat-пинг, служебные ответы и миллионы чужих сообщений, вызвав мгновенный Slow Consumer Dropped.

## На собеседовании

**Вопрос с собеседования:** «Как в NATS организовать разграничение прав доступа по wildcard-темам?»
**Ответ:** В файле конфигурации или JWT аккаунта указывают права на подписку с шаблонами: например `subscribe: { allow: ["events.eu.>"], deny: ["events.eu.security.>"] }`. Правило `deny` имеет приоритет перед `allow`, позволяя надежно экранировать приватные темы.
