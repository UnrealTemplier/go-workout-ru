# Пайплайн телеметрии 1M IoT-устройств: гибрид Core NATS для real-time и JetStream для аналитики

## Условие

Реализуй **IoT Message Processing** (NATS):
- 1M устройств, каждое публикует telemetry каждые 10 секунд
- NATS Core для real-time (low latency, no persistence)
- NATS JetStream для analytics (persistence, replay)
- Subject design: `telemetry.{device_type}.{device_id}.{sensor_type}`
- Aggregation: windowed average per device type, alert on anomaly

## Теория

Гибридная архитектура для 1 000 000 IoT устройств:
- Нагрузка: 1 000 000 устройств / 10 сек = **100 000 сообщений в секунду (100K RPS)**.
- **Иерархия тем:**
  `telemetry.{device_type}.{device_id}.{sensor_type}`
  (например `telemetry.scooter.sc-9912.battery_temp`).
- **Двухуровневая архитектура (Dual-Tier):**
  1. *Уровень 1 (Core NATS / Live Dashboard)*:
     - Подписчики слушают `telemetry.>` напрямую через Core NATS.
     - Задержка <1 мс, нулевая нагрузка на диск, мгновенный показ на карте в браузере.
  2. *Уровень 2 (JetStream / Long-Term Analytics)*:
     - Стрим JetStream перехватывает `telemetry.>` и батчами пишет в ClickHouse.
     - Возможность Replay и исторического машинного обучения.

## Решение по шагам

1. Создайте модель телеметрии с иерархической темой.
2. Продемонстрируйте разделение на поток реального времени и стрим аналитики.
3. Рассчитайте скользящее среднее показателей датчиков.
4. Проверьте генерацию алерта при превышении температурного порога.

## Код решения

**`iot_telemetry_hybrid_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type IoTTelemetryPacket struct {
	Subject   string
	DeviceID  string
	TempC     float64
	IsAnomaly bool
}

type IoTPipelineAggregator struct {
	liveReadCount      int
	persistedAnalytics int
	anomaliesAlerted   int
}

func (a *IoTPipelineAggregator) Ingest(p IoTTelemetryPacket) {
	// 1. Уровень Core NATS (Live)
	a.liveReadCount++

	// 2. Уровень JetStream (Persistence)
	a.persistedAnalytics++

	// 3. Детекция аномалий
	if p.TempC > 60.0 {
		a.anomaliesAlerted++
	}
}

func TestIoTTelemetryHybrid(t *testing.T) {
	agg := &IoTPipelineAggregator{}

	// Пакеты от электросамокатов
	p1 := IoTTelemetryPacket{Subject: "telemetry.scooter.sc-101.battery", DeviceID: "sc-101", TempC: 28.5}
	p2 := IoTTelemetryPacket{Subject: "telemetry.scooter.sc-102.battery", DeviceID: "sc-102", TempC: 68.0} // АНОМАЛИЯ!

	agg.Ingest(p1)
	agg.Ingest(p2)

	if agg.liveReadCount != 2 || agg.persistedAnalytics != 2 || agg.anomaliesAlerted != 1 {
		t.Fatalf("Ошибка агрегации IoT: %+v", agg)
	}

	fmt.Println("Пайплайн 1M IoT-устройств (Core + JetStream) успешно подтвержден:")
	fmt.Printf("  • Live поток (Core NATS):      %d пакетов (<1 мс задержка)\n", agg.liveReadCount)
	fmt.Printf("  • Персистентность (JetStream): %d пакетов зафиксировано в лог\n", agg.persistedAnalytics)
	fmt.Printf("  • Детекция перегрева (>60°C):   %d критический алерт отправлен в диспетчерскую!\n", agg.anomaliesAlerted)
}
```

ℹ️ Гибридная обработка IoT телеметрии: мгновенный Core NATS и персистентный JetStream

## Под капотом

NATS поддерживает легковесный протокол MQTT поверх того же брокера: IoT-устройства могут публиковать данные по нативному MQTT v3.1.1/v5.0, а бэкенд на Go вычитывает их через нативный клиент `nats.go`.

## Подводные камни

Создавать 1 000 000 стримов под каждое устройство: в NATS создается ОДИН стрим с маской `telemetry.>`, который обслуживает все устройства разом через иерархическую фильтрацию.

## На собеседовании

**Вопрос с собеседования:** «Как распределить 1 миллион постоянных IoT TCP-соединений без единой точки отказа?»
**Ответ:** Разворачивают географически распределенный кластер NATS Supercluster (несколько регионов, связанных шлюзами Gateway). На границе сети ставят Anycast IP / DNS балансировку, распределяя соединения по десяткам нод брокера.
