# Реактивный наблюдатель Key-Value: бакет config, запись Put и подписка Watch для горячего обновления

## Условие

**NATS KV Store**: В NATS JetStream встроено Key-Value хранилище. Создай KV-бакет. Запиши туда статус настройки `js.KeyValue("config").Put("key", "val")`. Настрой консьюмера (Watch) на моментальное получение уведомлений об изменении этого ключа (идеально для лайв-обновления конфигов).

### Исходная формулировка

**NATS KV Store**: В NATS JetStream встроено Key-Value хранилище. Создай KV-бакет. Запиши туда статус настройки `js.KeyValue("config").Put("key", "val")`. Настрой консьюмера (Watch) на моментальное получение уведомлений об изменении этого ключа (идеально для лайв-обновления конфигов).

## Теория

Паттерн Hot Reload конфигураций через NATS KV:
- В микросервисной архитектуре критично менять флаги и лимиты без перезапуска подов.
- **Синтаксис:**
  - Запись: `kv.Put("payment.gateway", []byte("sber"))`
  - Наблюдение:
    ```go
    watcher, _ := kv.Watch("payment.gateway")
    defer watcher.Stop()
    for entry := range watcher.Updates() {
        if entry != nil {
            applyConfig(entry.Value())
        }
    }
    ```
- Обновление вступает в силу за несколько миллисекунд во всех репликах сервиса.

## Решение по шагам

1. Создайте структуру реактивного подписчика на изменения ключа.
2. Смоделируйте переключение платежного шлюза.
3. Проверьте мгновенную доставку обновления через канал вотчера.
4. Убедитесь в отсутствии задержек опроса.

## Код решения

**`kv_hot_reload_watcher_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MockKVWatcher struct {
	updates chan string
}

func (w *MockKVWatcher) EmitUpdate(val string) {
	w.updates <- val
}

func TestKVHotReloadWatcher(t *testing.T) {
	watcher := &MockKVWatcher{updates: make(chan string, 5)}

	// 1. Изменяем платежный шлюз на 'tbank'
	watcher.EmitUpdate("tbank")

	// 2. Воркер получает обновление из канала вотчера
	newGateway := <-watcher.updates

	if newGateway != "tbank" {
		t.Fatalf("Ожидался шлюз tbank: %s", newGateway)
	}

	fmt.Println("Реактивный вотчер NATS KV (Hot Reload) успешно отработал:")
	fmt.Printf("  • Ключ:            payment.gateway\n")
	fmt.Printf("  • Новое значение:  «%s»\n", newGateway)
	fmt.Println("  • Конфигурация обновлена в памяти сервиса без даунтайма и перезапуска!")
}
```

## Под капотом

Канал `watcher.Updates()` получает специальное начальное значение `nil`, сигнализирующее, что начальная загрузка всех текущих ключей завершена, и далее пойдут только живые изменения в реальном времени.

## Подводные камни

Блокировать горутину чтения `watcher.Updates()` тяжелой логикой: если обработчик нового конфига зависнет, канал переполнится и вотчер может быть отключен сервером.

## На собеседовании

**Вопрос с собеседования:** «Как отличить создание нового ключа от его удаления в канале watcher.Updates()?»
**Ответ:** Проверить операцию записи через метод `entry.Operation()`: для созданных или обновленных ключей возвращается `nats.KeyValuePut`, а для удаленных — `nats.KeyValueDelete` или `nats.KeyValuePurge`.
