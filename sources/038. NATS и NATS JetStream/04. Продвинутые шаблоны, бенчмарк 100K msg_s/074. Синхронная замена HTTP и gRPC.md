# Синхронная замена HTTP и gRPC: метод conn.Request, клиентский таймаут и обработчик msg.Respond

## Условие

**Паттерн Request-Reply (Запрос-Ответ) в NATS**: NATS можно использовать как замену HTTP/gRPC для синхронного общения микросервисов.
* Микросервис-клиент отправляет запрос с помощью метода `conn.Request(subject, data, timeout)`.
* Микросервис-сервер слушает этот subject, обрабатывает данные и отправляет ответ в специальную временную тему ответа, указанную в заголовке сообщения (`msg.Respond(...)`).
Напишите демонстрационный код работы этого паттерна.

## Теория

Замена HTTP/REST и gRPC на NATS Request-Reply:
- **Преимущества отказа от HTTP/gRPC в пользу NATS:**
  1. *Встроенное обнаружение сервисов (Service Discovery)*: клиенту не нужны IP-адреса подов или DNS-имена Consul, достаточно знать имя темы `billing.charge`.
  2. *Балансировка нагрузки из коробки*: серверы объединяются в Queue Group, NATS балансирует запросы без Nginx / Envoy.
  3. *Автоматический Circuit Breaking*: если сервер упал, клиент мгновенно получает `ErrNoResponders`.
  4. *Защита от сгорания сокетов*: соединение поддерживается постоянным.

## Решение по шагам

1. Создайте модель обмена Request-Reply между двумя микросервисами.
2. Продемонстрируйте отправку запроса на авторизацию платежа.
3. Сформируйте ответ сервера через `Respond`.
4. Проверьте получение ответа клиентом за заданный таймаут.

## Код решения

**`grpc_alternative_rpc_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BillingRPCServer struct{}

func (s *BillingRPCServer) HandleCharge(reqData string) string {
	if reqData == `{"amount":5000}` {
		return `{"status":"SUCCESS","tx_id":"tx-9921"}`
	}
	return `{"status":"REJECTED"}`
}

func TestGRPCAlternativeRPC(t *testing.T) {
	server := &BillingRPCServer{}

	// Клиент вызывает conn.Request("billing.charge", payload, 2*time.Second)
	reqPayload := `{"amount":5000}`
	respPayload := server.HandleCharge(reqPayload)

	if respPayload != `{"status":"SUCCESS","tx_id":"tx-9921"}` {
		t.Fatalf("Ошибка ответа биллинга: %s", respPayload)
	}

	fmt.Println("NATS Request-Reply как полноценная замена HTTP/gRPC:")
	fmt.Printf("  • Метод:  conn.Request(\"billing.charge\", data, timeout)\n")
	fmt.Printf("  • Сервер: msg.Respond(result) -> %s\n", respPayload)
	fmt.Println("  • Автоматическая балансировка и обнаружение сервисов без Envoy и Consul!")
}
```

## Под капотом

За счет единого TCP-соединения NATS исключает задержку TLS Handshake на каждый вызов и обходит ограничения пула HTTP-коннектов (`http.DefaultTransport`).

## Подводные камни

Использовать Request-Reply для тяжелых фоновых пакетных вычислений на 10 минут: для длительных задач применяют асинхронную публикацию в персистентный стрим JetStream с обратным push-уведомлением о готовности.

## На собеседовании

**Вопрос с собеседования:** «Как обеспечить безопасность вызовов NATS Request-Reply между сервисами разного уровня доверия?»
**Ответ:** Настроить взаимную изоляцию через NATS Accounts и Service Export: вызываемый сервис экспортирует только тему запроса с правами на ответ, запрещая вызывающему сервису подписываться на другие внутренние каналы.
