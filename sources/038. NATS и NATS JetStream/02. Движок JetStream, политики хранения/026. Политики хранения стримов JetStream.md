# Политики хранения стримов JetStream: LimitsPolicy, InterestPolicy и WorkQueuePolicy

## Условие

Настройте **retention policy** для stream: `limits` (max messages/bytes/age), `interest` (хранить пока есть подписчики), `work queue` (каждое сообщение доставляется одному consumer).

## Теория

3 фундаментальные политики хранения (Retention Policies) в JetStream:
1. **LimitsPolicy (по умолчанию — аналог Kafka):**
   - Сообщения хранятся в стриме до достижения физических лимитов: `MaxMsgs`, `MaxBytes`, `MaxAge`.
   - Факт чтения консьюмерами НЕ влияет на удаление данных.
   - Идеально для логов аудита, Event Sourcing и исторической аналитики.
2. **InterestPolicy:**
   - Сообщение хранится до тех пор, пока ВСЕ активные подписчики стрима не подтвердят его чтение.
   - Как только последний подписчик сделал Ack \(\to\) сообщение удаляется.
3. **WorkQueuePolicy (аналог RabbitMQ / SQS):**
   - Сообщение удаляется из стрима сразу же, как только **хотя бы один** консьюмер подтвердил его (`Ack`).
   - Идеально для очередей задач.

## Решение по шагам

1. Создайте спецификацию политик хранения JetStream.
2. Смоделируйте поведение LimitsPolicy при достижении порога возраста.
3. Смоделируйте поведение WorkQueuePolicy при первом подтверждении.
4. Сравните условия очистки лога.

## Код решения

**`retention_policies_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RetentionKind string

const (
	PolicyLimits    RetentionKind = "Limits"
	PolicyInterest  RetentionKind = "Interest"
	PolicyWorkQueue RetentionKind = "WorkQueue"
)

func EvaluateRetentionEviction(policy RetentionKind, ackCount int, totalSubscribers int) bool {
	switch policy {
	case PolicyWorkQueue:
		// Удаляется после первого же Ack
		return ackCount >= 1
	case PolicyInterest:
		// Удаляется только когда ВСЕ подписчики подтвердили
		return ackCount >= totalSubscribers
	case PolicyLimits:
		// Удаляется только по таймеру/байтам, Ack не удаляет сообщение из стрима!
		return false
	default:
		return false
	}
}

func TestRetentionPolicies(t *testing.T) {
	// 1. WorkQueue: 1 Ack удаляет сообщение
	if !EvaluateRetentionEviction(PolicyWorkQueue, 1, 3) {
		t.Fatal("WorkQueue должна удалять сообщение после 1 Ack")
	}

	// 2. Interest: 1 Ack из 3 НЕ удаляет
	if EvaluateRetentionEviction(PolicyInterest, 1, 3) {
		t.Fatal("Interest не должна удалять сообщение, пока не подтвердят все 3")
	}
	// Interest: 3 Ack из 3 удаляет
	if !EvaluateRetentionEviction(PolicyInterest, 3, 3) {
		t.Fatal("Interest обязана удалить сообщение после подтверждения всеми 3")
	}

	// 3. Limits: Ack никогда не удаляет сообщение
	if EvaluateRetentionEviction(PolicyLimits, 3, 3) {
		t.Fatal("Limits не удаляет сообщение по факту Ack")
	}

	fmt.Println("Политики хранения (Retention Policies) NATS JetStream успешно проверены:")
	fmt.Printf("  • LimitsPolicy:    сохраняет данные независимо от Ack (Модель Kafka)\n")
	fmt.Printf("  • InterestPolicy:  удаляет, когда ВСЕ активные подписчики завершили обработку\n")
	fmt.Printf("  • WorkQueuePolicy: удаляет СРАЗУ после первого успешного Ack (Модель RabbitMQ)\n")
}
```

## Под капотом

При WorkQueuePolicy JetStream немедленно освобождает указатель на сообщение в Raft-индексе, минимизируя размер лога и использование оперативной памяти.

## Подводные камни

Использовать WorkQueuePolicy при наличии нескольких независимых микросервисов: первый сервис, вызвавший `Ack`, удалит сообщение, и второй сервис его никогда не получит. Для нескольких независимых групп сервисов используют `LimitsPolicy`.

## На собеседовании

**Вопрос с собеседования:** «Какая политика удаления (Discard Policy) применяется при переполнении стрима в режиме Limits?»
**Ответ:** Существует 2 политики: `DiscardOld` (по умолчанию — старые сообщения вытесняются новыми, как в кольцевом буфере) и `DiscardNew` (сервер отклоняет публикацию новых сообщений с ошибкой `ErrStreamMaxMsgs`, защищая исторические данные).
