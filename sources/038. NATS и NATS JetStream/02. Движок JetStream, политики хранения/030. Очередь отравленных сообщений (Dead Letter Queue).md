# Очередь отравленных сообщений (Dead Letter Queue): параметр MaxDeliver 3, DiscardOld и изоляция сбоев

## Условие

Напиши **Dead Letter Queue (DLQ)**: в Stream Config: `MaxDeliver: 3`. Consumer с `nats.MaxDeliver(3)`. При 3 неудачных попытках — сообщение идёт в `DeadLetterPolicy{Policy: nats.DiscardOld, MaxSamples: 100}`. Или ручной: `m.Nak()` с `m.Header.Set("Nats-Last-Consumer", "...")`, после 3 `Nak` — `m.Term()` + публикуй в `"orders.dlq"`.

## Теория

Изоляция фатальных сбоев через DLQ в JetStream:
- Опасность Poison Pill: если в очередь попало поврежденное сообщение, воркер падает, сообщение переотправляется, следующий воркер падает \(\to\) вся система выходит из строя (Cascading Crash).
- **Решение через MaxDeliver:**
  - В конфигурации Consumer задается лимит: `MaxDeliver: 3`.
  - JetStream отслеживает число доставок `NumDelivered`.
  - После 3 неудачных попыток:
    - Сообщение автоматически снимается с доставки.
    - В ручном режиме воркер проверяет `meta.NumDelivered >= 3`:
      вызывает `m.Term()` и пересылает сообщение в стрим `orders.dlq` с заголовком причины ошибки.

## Решение по шагам

1. Создайте структуру счетчика доставок сообщения.
2. Проверьте превышение лимита `MaxDeliver: 3`.
3. Терминируйте сообщение через `Term()`.
4. Опубликуйте копию в топик `orders.dlq` для аудита.

## Код решения

**`jetstream_dlq_router_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DLQMessage struct {
	OriginalID string
	Attempts   int
	FailReason string
}

type ConsumerDLQHandler struct {
	dlqTopic []DLQMessage
}

func (h *ConsumerDLQHandler) HandleWithDLQ(msgID string, deliveryCount int, failErr error) (terminated bool) {
	const MaxDeliver = 3

	if deliveryCount >= MaxDeliver {
		// Превышен лимит попыток -> терминируем и изолируем в DLQ!
		h.dlqTopic = append(h.dlqTopic, DLQMessage{
			OriginalID: msgID,
			Attempts:   deliveryCount,
			FailReason: failErr.Error(),
		})
		return true // Вызываем m.Term()
	}
	return false // Вызываем m.Nak()
}

func TestJetStreamDLQRouter(t *testing.T) {
	handler := &ConsumerDLQHandler{}
	errValidation := fmt.Errorf("invalid json payload: unexpected EOF")

	// Попытки 1 и 2 -> Nak
	isTerm1 := handler.HandleWithDLQ("poison-msg-77", 1, errValidation)
	isTerm2 := handler.HandleWithDLQ("poison-msg-77", 2, errValidation)

	if isTerm1 || isTerm2 || len(handler.dlqTopic) != 0 {
		t.Fatal("Попытки 1 и 2 должны уходить в ретрай")
	}

	// Попытка 3 -> Изоляция в DLQ!
	isTerm3 := handler.HandleWithDLQ("poison-msg-77", 3, errValidation)

	if !isTerm3 || len(handler.dlqTopic) != 1 {
		t.Fatalf("Сообщение обязано быть изолировано в DLQ на 3 попытке")
	}

	dlqEntry := handler.dlqTopic[0]
	if dlqEntry.OriginalID != "poison-msg-77" || dlqEntry.Attempts != 3 {
		t.Fatalf("Некорректная запись в DLQ: %+v", dlqEntry)
	}

	fmt.Println("Изоляция отравленного сообщения в DLQ JetStream успешна:")
	fmt.Printf("  • ID сообщения:    %s\n", dlqEntry.OriginalID)
	fmt.Printf("  • Число попыток:   %d (Лимит MaxDeliver=3)\n", dlqEntry.Attempts)
	fmt.Printf("  • Причина ошибки:  %s\n", dlqEntry.FailReason)
	fmt.Println("  • Сообщение удалено из основного стрима и перенаправлено в orders.dlq!")
}
```

## Под капотом

В JetStream параметр `MaxDeliver` проверяется сервером на лету: при достижении лимита сервер NATS больше никогда не включит это сообщение в выдачу `Fetch`, защищая воркеры от падений.

## Подводные камни

Забывать настраивать мониторинг и алертинг на появление сообщений в стриме DLQ: сообщения будут копиться в DLQ незамеченными, если на них нет дашборда в Grafana.

## На собеседовании

**Вопрос с собеседования:** «Каковы лучшие практики повторной обработки (Redrive) сообщений из Dead Letter Queue в NATS?»
**Ответ:** Для DLQ создают отдельный утилитарный микросервис Redrive Tool. После исправления бага в коде или обновления зависимостей инженер запускает команду переотправки, которая вычитывает сообщения из `orders.dlq` и публикует их обратно в основной стрим `orders`.
