# Пакетное чтение через Pull-подписку: метод js.PullSubscribe и обработка пакетами

## Условие

Создайте **consumer** с `js.PullSubscribe` и обрабатывайте сообщения батчами (pull-based consumption).

## Теория

Пулл-модель потребления (Pull-Based Consumption):
- В традиционной Push-модели брокер сам «выталкивает» сообщения клиенту. Если наплыв слишком велик, консьюмер захлебывается (OOM).
- В Pull-модели **клиент сам контролирует поток**:
  - `sub, _ := js.PullSubscribe("orders.>", "batch-worker")`
  - Когда воркер готов к работе, он вызывает `msgs, _ := sub.Fetch(batchSize, timeout)`.
  - Забирает строго столько сообщений, сколько может обработать прямо сейчас.
  - Обеспечивает абсолютную защиту от перегрузки (Zero OOM guarantee).

## Решение по шагам

1. Создайте структуру Pull-консьюмера с буфером стрима.
2. Смоделируйте пакетную вычитку пачки из 5 сообщений через `Fetch(5)`.
3. Обработайте полученный срез сообщений.
4. Проверьте контроль над скоростью потребления.

## Код решения

**`pull_batch_consumption_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MockPullSubscription struct {
	streamQueue []string
}

func (s *MockPullSubscription) Fetch(batchSize int) []string {
	if len(s.streamQueue) == 0 {
		return nil
	}
	if len(s.streamQueue) < batchSize {
		batchSize = len(s.streamQueue)
	}
	batch := s.streamQueue[:batchSize]
	s.streamQueue = s.streamQueue[batchSize:]
	return batch
}

func TestPullBatchConsumption(t *testing.T) {
	sub := &MockPullSubscription{
		streamQueue: []string{"msg-1", "msg-2", "msg-3", "msg-4", "msg-5", "msg-6", "msg-7"},
	}

	// 1. Забираем первый батч размером 3
	batch1 := sub.Fetch(3)
	if len(batch1) != 3 || batch1[0] != "msg-1" {
		t.Fatalf("Некорректный батч 1: %v", batch1)
	}

	// 2. Забираем второй батч размером 3
	batch2 := sub.Fetch(3)
	if len(batch2) != 3 || batch2[0] != "msg-4" {
		t.Fatalf("Некорректный батч 2: %v", batch2)
	}

	// В стриме остался 1 элемент
	if len(sub.streamQueue) != 1 {
		t.Fatalf("В стриме должен остаться 1 элемент: %d", len(sub.streamQueue))
	}

	fmt.Println("Pull-based пакетное чтение сообщений успешно выполнено:")
	fmt.Printf("  • Батч 1 (3 сообщения): %v\n", batch1)
	fmt.Printf("  • Батч 2 (3 сообщения): %v\n", batch2)
	fmt.Printf("  • Остаток в стриме:      %d сообщение\n", len(sub.streamQueue))
	fmt.Println("  • Консьюмер полностью контролирует скорость и объем потребления!")
}
```

## Под капотом

При вызове `Fetch` клиент отправляет серверу служебную команду запроса с указанием количества сообщений и таймаута: сервер NATS отсылает запрошенную пачку и ждет подтверждений.

## Подводные камни

Забывать обрабатывать ошибку `nats.ErrTimeout`: если в стриме нет новых сообщений до истечения `MaxWait`, `Fetch` вернет ошибку таймаута, которую нужно трактовать как штатное отсутствие данных.

## На собеседовании

**Вопрос с собеседования:** «Почему NATS JetStream 2.10+ рекомендует Pull Consumers для всех новых проектов вместо Push Consumers?»
**Ответ:** Pull Consumers обеспечивают горизонтальную масштабируемость, исключают перегрузку клиентов при всплесках трафика, поддерживают гибкий батчинг и динамическое масштабирование количества воркеров в Kubernetes без необходимости предварительного согласования сетевых очередей на брокере.
