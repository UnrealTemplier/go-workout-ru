# Гарантия доставки At-Least-Once: подтверждение msg.Ack и восстановление после падения воркера

## Условие

Реализуйте **at-least-once delivery**: после обработки сообщения вызывайте `msg.Ack()`. Если воркер упал до ack — сообщение будет redelivered.

## Теория

Семантика At-Least-Once в распределенных системах:
- Гарантирует: ни одно сообщение не будет потеряно, но отдельные сообщения могут быть доставлены более одного раза при авариях.
- Правило реализации:
  1. Читаем сообщение из JetStream.
  2. Выполняем бизнес-логику (сохранение в БД, вызов внешнего API).
  3. **ТОЛЬКО ПОСЛЕ УСПЕШНОЙ ЗАПИСИ В БД** вызываем `msg.Ack()`.
  4. Если в процессе записи в БД произошел сбой — воркер падает, `Ack` не уходит, брокер переотправляет задачу другому воркеру.

## Решение по шагам

1. Создайте модель обработки транзакции с отложенным подтверждением.
2. Продемонстрируйте вызов `Ack` строго после успешной записи в хранилище.
3. Смоделируйте ошибку записи в базу данных.
4. Проверьте отсутствие ложного подтверждения при сбое.

## Код решения

**`at_least_once_flow_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type DatabaseRecord struct {
	ID   string
	Data string
}

func ProcessTransactionAtLeastOnce(id, data string, dbFail bool) (saved bool, ackSent bool, err error) {
	// 1. Попытка записи в базу данных
	if dbFail {
		return false, false, errors.New("database connection timeout")
	}

	// Запись успешна!
	saved = true

	// 2. Отправка подтверждения в брокер
	ackSent = true
	return saved, ackSent, nil
}

func TestAtLeastOnceFlow(t *testing.T) {
	// Сценарий 1: Успешная транзакция
	saved1, ack1, err1 := ProcessTransactionAtLeastOnce("tx-1", "success-payload", false)
	if !saved1 || !ack1 || err1 != nil {
		t.Fatalf("Транзакция 1 должна быть подтверждена: %v", err1)
	}

	// Сценарий 2: Сбой БД -> Ack не отправляется!
	saved2, ack2, err2 := ProcessTransactionAtLeastOnce("tx-2", "corrupt-payload", true)
	if saved2 || ack2 || err2 == nil {
		t.Fatalf("При ошибке БД Ack категорически запрещен: saved=%v, ack=%v", saved2, ack2)
	}

	fmt.Println("Гарантия At-Least-Once доставки успешно подтверждена:")
	fmt.Printf("  • Транзакция 1: БД [OK] -> msg.Ack() [ОТПРАВЛЕН]\n")
	fmt.Printf("  • Транзакция 2: БД [ERROR: %v] -> msg.Ack() [НЕ ОТПРАВЛЕН]\n", err2)
	fmt.Println("  • Сообщение 2 будет автоматически переотправлено брокером после тайм-аута!")
}
```

ℹ️ Строгий порядок: вызов msg.Ack() исключительно после подтверждения записи в БД

## Под капотом

Если клиент аварийно отключается (TCP RST), сервер JetStream не ждет истечения полного таймера `AckWait`, а может сразу вернуть неподтвержденные сообщения в пул доступных для других воркеров.

## Подводные камни

Вызывать `msg.Ack()` в начале функции обработчика («чтобы не забыть»): при падении воркера в теле функции сообщение уже помечено удаленным, и бизнес-транзакция будет безвозвратно потеряна.

## На собеседовании

**Вопрос с собеседования:** «Какое требование накладывает семантика At-Least-Once на логику консьюмеров?»
**Ответ:** Логика консьюмеров обязана быть **идемпотентной** (Idempotent Consumer). Поскольку сообщение может быть доставлено повторно при сбоях сети или падениях воркеров, обработка дубликата не должна приводить к повторному списанию денег или созданию лишних записей в базе данных.
