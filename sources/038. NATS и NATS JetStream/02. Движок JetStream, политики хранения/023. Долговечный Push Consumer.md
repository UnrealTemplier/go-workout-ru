# Долговечный Push Consumer: опции Durable processor-1, ManualAck и повторная доставка при сбое

## Условие

Напиши **Push Consumer**: `sub, _ := js.Subscribe("orders.>", func(m *nats.Msg) { ... }, nats.Durable("processor-1"), nats.ManualAck())`. Обработай сообщение, затем `m.Ack()`. Покажи, что без `Ack` сообщение redeliver'ится.

## Теория

Механика Durable Push Consumer с подтверждениями:
- Опции:
  - `nats.Durable("processor-1")`: консьюмер сохраняется на сервере NATS под постоянным именем.
  - `nats.ManualAck()`: автоматическое подтверждение отключено. Приложение ОБЯЗАНО явно вызвать `msg.Ack()`.
- Сценарий сбоя (Failure Handling):
  - Если воркер получил сообщение, но упал (panic, OOM, потеря питания) ДО вызова `m.Ack()`:
  - По истечении таймера подтверждения (`AckWait`, default 30 секунд):
  - JetStream автоматически **доставит это сообщение повторно** (Redelivery) любому живому консьюмеру этой группы!
  - Обеспечивает строгую семантику At-Least-Once.

## Решение по шагам

1. Создайте модель Durable-консьюмера с отслеживанием неподтвержденных сообщений.
2. Сымитируйте падение воркера без вызова `Ack`.
3. Запустите таймер повторной доставки.
4. Убедитесь, что сообщение было повторно доставлено и успешно подтверждено.

## Код решения

**`durable_push_redelivery_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type JetStreamRedeliveryTracker struct {
	deliveredCount int
	isAcked        bool
}

func (t *JetStreamRedeliveryTracker) Dispatch() {
	t.deliveredCount++
}

func (t *JetStreamRedeliveryTracker) Ack() {
	t.isAcked = true
}

func (t *JetStreamRedeliveryTracker) TriggerRedeliveryOnTimeout() bool {
	if !t.isAcked {
		t.deliveredCount++ // Повторная доставка!
		return true
	}
	return false
}

func TestDurablePushRedelivery(t *testing.T) {
	tracker := &JetStreamRedeliveryTracker{}

	// 1. Первая доставка воркеру
	tracker.Dispatch()

	// Воркер упал до вызова Ack!
	if tracker.isAcked {
		t.Fatal("Ack не должен быть вызван")
	}

	// 2. Истек AckWait -> брокер переотправляет сообщение
	redelivered := tracker.TriggerRedeliveryOnTimeout()
	if !redelivered || tracker.deliveredCount != 2 {
		t.Fatalf("Ожидалась повторная доставка: %d", tracker.deliveredCount)
	}

	// 3. Новый воркер успешно обработал и подтвердил
	tracker.Ack()

	// Повторная попытка переотправки после успешного Ack
	redeliveredAfterAck := tracker.TriggerRedeliveryOnTimeout()
	if redeliveredAfterAck || tracker.deliveredCount != 2 {
		t.Fatalf("После Ack повторная доставка не должна происходить: %v", redeliveredAfterAck)
	}

	fmt.Println("Durable Push Consumer & Redelivery успешно протестированы:")
	fmt.Printf("  • Durable Name:       processor-1\n")
	fmt.Printf("  • Попытка 1:          Воркер упал без Ack\n")
	fmt.Printf("  • Попытка 2 (Redeliv): Доставлено повторно -> Успешный Ack!\n")
	fmt.Println("  • Потери сообщения не произошло, гарантия At-Least-Once соблюдена!")
}
```

## Под капотом

Счетчик доставок передается в служебных метаданных каждого сообщения: метод `m.Metadata()` возвращает структуру `nats.MsgMetadata` с полями `NumDelivered` и `Sequence`.

## Подводные камни

Забывать указывать `nats.ManualAck()`: по умолчанию в некоторых версиях SDK подписка может подтверждать сообщение автоматически ДО вызова вашего обработчика, что нарушает At-Least-Once.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если обработка сообщения в воркере занимает дольше дефолтного AckWait (например 2 минуты вместо 30 секунд)?»
**Ответ:** Вызывать метод `m.InProgress()` каждые 20 секунд. Этот вызов сообщает серверу NATS: «я еще работаю над сообщением, не делай redelivery», продлевая таймер ожидания подтверждения на значение `AckWait`.
