# Выделенный стрим для ручного разбора: настройка Dead Letter стрима и аудит сбойных заказов

## Условие

Настройте **dead letter queue**: сообщения, которые не удалось обработать после N попыток, отправляются в отдельный stream для ручного разбора.

## Теория

Архитектура промышленного стрима разбора инцидентов (Incident Resolution Stream):
- Для изоляции сбойных сообщений создается отдельный стрим:
  - Имя: `ORDERS_DLQ`.
  - Темы: `orders.dlq.>`.
  - Retention: `LimitsPolicy` (хранить 30 дней для аудита).
  - Storage: `FileStorage`.
- Сообщение сохраняет оригинальные заголовки, тело, а также служебный заголовок `Nats-Failure-Stack`.
- Инженеры техподдержки используют веб-интерфейс или скрипты для инспекции и ручного исправления данных.

## Решение по шагам

1. Создайте спецификацию отдельного стрима `ORDERS_DLQ`.
2. Смоделируйте отправку сообщения с оригинальными метаданными и трассировкой сбоя.
3. Проверьте сохранность атрибутов в хранилище DLQ.
4. Убедитесь в изоляции сбоев от основного потока.

## Код решения

**`dedicated_dlq_stream_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DedicatedDLQStreamConfig struct {
	Name     string
	Subjects []string
	MaxAge   string
}

type DLQIncidentRecord struct {
	OrderID   string
	ErrorCode string
	RawBody   string
}

func CreateDedicatedDLQStream() DedicatedDLQStreamConfig {
	return DedicatedDLQStreamConfig{
		Name:     "ORDERS_DLQ",
		Subjects: []string{"orders.dlq.>"},
		MaxAge:   "720h", // 30 дней хранения для инженеров техподдержки
	}
}

func TestDedicatedDLQStream(t *testing.T) {
	cfg := CreateDedicatedDLQStream()

	incident := DLQIncidentRecord{
		OrderID:   "ord-bad-009",
		ErrorCode: "ERR_SCHEMA_MISMATCH",
		RawBody:   `<xml>broken legacy format</xml>`,
	}

	if cfg.Name != "ORDERS_DLQ" || cfg.Subjects[0] != "orders.dlq.>" {
		t.Fatalf("Некорректная конфигурация стрима DLQ: %+v", cfg)
	}

	fmt.Println("Выделенный стрим Dead Letter Queue успешно сконфигурирован:")
	fmt.Printf("  • Имя стрима: %s\n", cfg.Name)
	fmt.Printf("  • Темы:       %s\n", cfg.Subjects[0])
	fmt.Printf("  • Хранение:   %s (30 дней)\n", cfg.MaxAge)
	fmt.Printf("  • Зарегистрирован инцидент: Заказ %s [%s]\n", incident.OrderID, incident.ErrorCode)
}
```

ℹ️ Декларация выделенного стрима ORDERS_DLQ для длительного хранения сбойных заказов

## Под капотом

Стрим DLQ изолирован на уровне дисковых файлов: запись инцидентов в `ORDERS_DLQ` не создает contention за блокировки диска с основным стримом `ORDERS`.

## Подводные камни

Устанавливать `WorkQueuePolicy` для стрима DLQ: если первый попавшийся скрипт прочитает сообщение и сделает Ack, сообщение исчезнет до того, как инженеры успеют провести ручной аудит.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить переполнение стрима DLQ при массовом сбое upstream сервиса (миллионы ошибок в минуту)?»
**Ответ:** Настраивают лимит `MaxMsgs` или `MaxBytes` со стратегией `DiscardOld`, а в приложении консьюмера включают Circuit Breaker: если процент ошибок превышает 50%, консьюмер временно приостанавливает вычитку основного стрима, предотвращая лавинообразное наполнение DLQ.
