# Управление повторными попытками через Nak: явный отказ от обработки и отложенный Redelivery

## Условие

Используйте **Nak** для явного отказа от обработки (сообщение будет redelivered позже).

## Теория

Семантика сигнала Nak (Negative Acknowledgement):
- Когда сервис обнаруживает временную проблему (например, внешний платежный шлюз вернул HTTP 503 или локальный диск временно переполнен):
  - Не нужно ждать 30 секунд истечения `AckWait`.
  - Воркер немедленно вызывает `msg.Nak()`.
  - Сервер JetStream сразу возвращает сообщение в очередь стрима для повторной доставки.
- Это сокращает время простоя обработки и освобождает ресурсы текущего воркера.

## Решение по шагам

1. Создайте обработчик с ветвлением по доступности внешнего ресурса.
2. Смоделируйте временный сбой и вызов `msg.Nak()`.
3. Проверьте возврат сообщения в статус ожидания повторной доставки.
4. Убедитесь в успешной обработке при повторе.

## Код решения

**`nak_retry_flow_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ServiceDependency struct {
	isAvailable bool
}

func ProcessWithNak(dep ServiceDependency) (action string) {
	if !dep.isAvailable {
		// Внешний сервис недоступен -> явный отказ Nak!
		return "NAK_SENT"
	}
	// Успешная обработка
	return "ACK_SENT"
}

func TestNakRetryFlow(t *testing.T) {
	dep := ServiceDependency{isAvailable: false}

	// 1. Первая попытка — зависимость лежит
	action1 := ProcessWithNak(dep)
	if action1 != "NAK_SENT" {
		t.Fatalf("Ожидался NAK: %s", action1)
	}

	// 2. Вторая попытка — зависимость восстановилась
	dep.isAvailable = true
	action2 := ProcessWithNak(dep)
	if action2 != "ACK_SENT" {
		t.Fatalf("Ожидался ACK: %s", action2)
	}

	fmt.Println("Явный отказ от обработки (Nak) успешно отработал:")
	fmt.Printf("  • Попытка 1: Сбой зависимости -> msg.Nak() (Быстрый возврат в стрим)\n")
	fmt.Printf("  • Попытка 2: Зависимость поднялась -> msg.Ack() (Успешное завершение)\n")
	fmt.Println("  • Никаких лишних задержек AckWait, система мгновенно среагировала!")
}
```

## Под капотом

При получении команды `-NAK` сервер NATS инкрементирует счетчик `NumDelivered` для данного сообщения и мгновенно делает его доступным для `Fetch` запросов других клиентов.

## Подводные камни

Вызывать `Nak` без задержки на постоянных ошибках (например, ошибка валидации схемы): это вызовет мгновенный шторм повторных вызовов (Tight Retry Loop), который перегрузит процессор сервиса.

## На собеседовании

**Вопрос с собеседования:** «Чем вызов msg.Nak() отличается от ситуации, когда воркер просто ничего не делает и выходит по таймауту?»
**Ответ:** Вызов `msg.Nak()` явно и мгновенно сообщает брокеру об отказе, не дожидаясь истечения таймаута `AckWait` (который обычно составляет 30 секунд). Это сокращает общую задержку повторной доставки до миллисекунд.
