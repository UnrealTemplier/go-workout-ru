# Inbox в Redis: идемпотентное отслеживание сообщений через SET NX EX

## Условие

46. **Inbox в Redis**: Для Redis используйте Redis SET с `NX` (set if not exists) для idempotent message tracking.

### Исходная формулировка

**Inbox в Redis**: Для Redis используйте Redis SET с `NX` (set if not exists) для idempotent message tracking.

## Теория

Когда сервис обрабатывает десятки тысяч некритичных событий в секунду (например, сбор кликов, просмотры товаров, обновление аналитических счетчиков), создание транзакции в реляционной СУБД на каждое сообщение создаст чрезмерную нагрузку на дисковый I/O. В таких сценариях высокоскоростной Inbox реализуется в памяти Redis.

Команда Redis `SET inbox:<message_id> 1 NX EX <ttl_seconds>` атомарно:
1. Проверяет, существует ли ключ `inbox:<message_id>`.
2. Если ключа нет (`NX` — Not Exists), устанавливает его со значением `1` и временем жизни `EX` (TTL).
3. Возвращает `OK` (в Go `redis.Nil == false`), что сигнализирует: это первое появление сообщения.
4. Если ключ уже существует, команда возвращает nil, что означает дубликат.
TTL гарантирует автоматическую очистку памяти без необходимости запуска Pruning Daemon.

## Решение по шагам

1. Сформируйте ключ дедупликации `inbox:msg:<message_id>`.
2. Вызовите команду `rdb.SetArgs(ctx, key, 1, redis.SetArgs{Mode: 'NX', TTL: 24 * time.Hour})`.
3. Если команда вернула ошибку `redis.Nil` (ключ уже был), залогируйте дубликат и завершите обработку.
4. Если ключ успешно установлен — выполните полезную работу.
5. Продемонстрируйте фильтрацию повторных вызовов.

## Код решения

**`redis_inbox.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// Mock Redis клиента с поддержкой атомарного SET NX EX
type MockRedisClient struct {
	mu   sync.Mutex
	data map[string]time.Time // key -> expiration
}

func NewMockRedisClient() *MockRedisClient {
	return &MockRedisClient{data: make(map[string]time.Time)}
}

// SetNXEX атомарно устанавливает ключ, если его еще нет, с временем жизни TTL
func (r *MockRedisClient) SetNXEX(ctx context.Context, key string, ttl time.Duration) (bool, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	now := time.Now()
	// Проверяем наличие неистекшего ключа
	if exp, exists := r.data[key]; exists && now.Before(exp) {
		return false, nil // Ключ уже есть (Duplicate)
	}

	// Устанавливаем новый ключ с TTL
	r.data[key] = now.Add(ttl)
	return true, nil // Успешно установлен (Fresh message)
}

type HighThroughputConsumer struct {
	redis *MockRedisClient
	ttl   time.Duration
}

func NewHighThroughputConsumer(redis *MockRedisClient, ttl time.Duration) *HighThroughputConsumer {
	return &HighThroughputConsumer{redis: redis, ttl: ttl}
}

func (c *HighThroughputConsumer) ConsumeMessage(ctx context.Context, msgID, payload string) {
	key := fmt.Sprintf("inbox:msg:%s", msgID)

	isFirstTime, err := c.redis.SetNXEX(ctx, key, c.ttl)
	if err != nil {
		fmt.Printf("[Error] Redis failure: %v\n", err)
		return
	}

	if !isFirstTime {
		fmt.Printf("[Redis Inbox] Duplicate message '%s' rejected by SET NX (Already processed)\n", msgID)
		return
	}

	// Бизнес-логика для первого поступления
	fmt.Printf("[Redis Inbox] Fresh message '%s' accepted! Processing payload: %s\n", msgID, payload)
}

func main() {
	redisClient := NewMockRedisClient()
	consumer := NewHighThroughputConsumer(redisClient, 24*time.Hour)
	ctx := context.Background()

	msgID := "kafka-click-id-5555"

	fmt.Println("=== 1. Processing first arrival ===")
	consumer.ConsumeMessage(ctx, msgID, `{"user_id": 42, "button": "buy_now"}`)

	fmt.Println("\n=== 2. Immediate duplicate arrival (broker retry) ===")
	consumer.ConsumeMessage(ctx, msgID, `{"user_id": 42, "button": "buy_now"}`)

	fmt.Println("\n=== 3. Another message arrival ===")
	consumer.ConsumeMessage(ctx, "kafka-click-id-5556", `{"user_id": 99, "button": "add_cart"}`)
}
```

ℹ️ Команда SET NX EX атомарно проверяет и занимает ключ дедупликации с автоматическим TTL

```bash

[Redis Inbox] Fresh message 'kafka-click-id-5555' accepted! Processing payload: {"user_id": 42, "button": "buy_now"}

=== 2. Immediate duplicate arrival (broker retry) ===
[Redis Inbox] Duplicate message 'kafka-click-id-5555' rejected by SET NX (Already processed)

=== 3. Another message arrival ===
```

## Под капотом

Redis выполняет команду `SET key val NX EX ttl` в едином однопоточном цикле событий (Event Loop), что исключает любые состояния гонки между параллельными воркерами Go. Задержка операции составляет суб-миллисекунды (обычно 0.1–0.3 мс в локальной сети).

## Подводные камни

1. Redis не является частью транзакции вашей основной БД: если Redis зафиксировал ключ, а последующая запись в БД консьюмера упала, повторная доставка сообщения будет заблокирована Redis, что приведет к потере обновления данных.
2. Эвикция ключей при нехватке памяти: при политике `allkeys-lru` или `volatile-lru` Redis может вытеснить ключ раньше истечения TTL, если закончится RAM.

## На собеседовании

Вопрос: Когда следует применять Inbox в Redis, а когда Transactional Inbox в PostgreSQL?
Ответ: Redis Inbox применяется для систем с колоссальным RPS (метрики, кликстрим, уведомления, аналитика), где допустим редкий процент сбоев и потеря одного события не критична. Для финансовых проводок, списания балансов и изменения статусов заказов обязан использоваться Transactional Inbox в PostgreSQL в одной ACID-транзакции с бизнес-таблицей.
