# Каверзный кейс: падение сети после отправки в брокер и природа гарантии At-Least-Once

## Условие

42. **[Каверзный кейс — Дубликаты (At-least-once)]**: Relay Worker отправил сообщение в Kafka, но сеть упала до того, как Worker успел сделать `UPDATE processed = true`. При рестарте Worker отправит это сообщение *повторно*. Объясни, почему Outbox гарантирует *At-least-once* (минимум один раз), а не *Exactly-once* (ровно один раз).

### Исходная формулировка

**[Каверзный кейс — Дубликаты (At-least-once)]**: Relay Worker отправил сообщение в Kafka, но сеть упала до того, как Worker успел сделать `UPDATE processed = true`. При рестарте Worker отправит это сообщение *повторно*. Объясни, почему Outbox гарантирует *At-least-once* (минимум один раз), а не *Exactly-once* (ровно один раз).

## Теория

Двухфазный коммит между реляционной СУБД и брокером сообщений невозможен без распределенного координатора (XA-транзакций, которые крайне медленны и не поддерживаются большинством брокеров). Следовательно, физическое взаимодействие Relay Worker состоит из двух несвязанных сетевых действий:
1. Сетевой запрос к брокеру: `Publish(msg)`.
2. Сетевой запрос к БД: `UPDATE outbox SET processed = true`.

Если шаг 1 завершился успешно (сообщение записано в журнал брокера), но в интервале между шагами 1 и 2 сервер упал по `SIGKILL`, произошел сбой сети или таймаут базы данных — запись в Outbox останется со статусом `processed = false`. После рестарта новый воркер прочитает ту же запись и отправит ее снова. Это доказывает, что чистый паттерн Outbox дает только **At-Least-Once** доставку.

## Решение по шагам

1. Создайте запись события в Outbox (`processed = false`).
2. В воркере сымитируйте отправку сообщения в брокер.
3. Сымитируйте падение процесса (Crash) до выполнения `UPDATE processed = true`.
4. Запустите новый экземпляр воркера (Recovery).
5. Продемонстрируйте, что брокер получил дубликат одного и того же события.

## Код решения

**`at_least_once_crash.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type BrokerStorage struct {
	mu       sync.Mutex
	messages []string
}

func (b *BrokerStorage) Push(msg string) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.messages = append(b.messages, msg)
}

type DBRecord struct {
	ID        string
	Payload   string
	Processed bool
}

func SimulateRelayCycle(record *DBRecord, broker *BrokerStorage, crashBeforeUpdate bool) bool {
	fmt.Printf("[Relay] Fetching pending outbox row: %s\n", record.ID)

	// Шаг 1: Успешная отправка в брокер
	broker.Push(record.Payload)
	fmt.Printf(" -> [Broker] Message %s written to topic partition log!\n", record.ID)

	// Шаг 2: Симуляция аварии
	if crashBeforeUpdate {
		fmt.Printf(" -> [CRASH] Network disconnected / Pod OOM killed before DB UPDATE! Outbox row remains Processed=false\n")
		return false
	}

	// Шаг 3: Обновление статуса в БД
	record.Processed = true
	fmt.Printf(" -> [DB] Successfully executed UPDATE outbox SET processed=true WHERE id=%s\n", record.ID)
	return true
}

func main() {
	broker := &BrokerStorage{}
	outboxRow := &DBRecord{
		ID:        "evt-payment-888",
		Payload:   `{"payment_id": "pay-888", "amount": 100}`,
		Processed: false,
	}

	fmt.Println("=== Iteration 1: Worker crashes after broker ack, before DB update ===")
	SimulateRelayCycle(outboxRow, broker, true)

	fmt.Println("\n=== Iteration 2: Worker restarts and retries unprocessed rows ===")
	SimulateRelayCycle(outboxRow, broker, false)

	fmt.Println("\n=== Final State Analysis ===")
	fmt.Printf("Outbox row in DB: ID=%s, Processed=%t\n", outboxRow.ID, outboxRow.Processed)
	fmt.Printf("Total messages received by Broker: %d\n", len(broker.messages))
	for i, m := range broker.messages {
		fmt.Printf(" Broker Msg #%d: %s\n", i+1, m)
	}
}
```

ℹ️ Демонстрация неизбежного возникновения дубликата при падении процесса между брокером и БД

## Под капотом

Проблема невозможности распределенного Exactly-Once между несвязанными системами описана в классической теореме о двух генералах (Two Generals' Problem). Любая распределенная коммуникация по ненадежному каналу связи гарантирует либо At-Least-Once (при повторах), либо At-Most-Once (без повторов).

## Подводные камни

1. Попытка переставить шаги местами: `UPDATE processed = true` затем `Publish()`. В этом случае при падении сообщение потеряется навсегда (At-Most-Once), что для финансов и заказов недопустимо.
2. Отсутствие Inbox у консьюмера: без дедупликации клиент получит двойное списание средств.

## На собеседовании

Вопрос: Почему Kafka рекламирует Exactly-Once Semantics (EOS), но при Outbox все равно возникают дубликаты?
Ответ: Kafka EOS работает строго в контуре 'Kafka-to-Kafka' (между Kafka Streams или transactional producer/consumer). На границе между сторонней базой данных PostgreSQL и брокером Kafka транзакция Kafka не координируется с локальной транзакцией PostgreSQL. Поэтому сквозной Exactly-Once достигается только связкой Outbox + Inbox.
