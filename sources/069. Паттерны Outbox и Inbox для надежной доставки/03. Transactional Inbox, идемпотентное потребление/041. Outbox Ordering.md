# Outbox Ordering: гарантия порядка событий по Aggregate ID через Partition Key

## Условие

41. **Outbox Ordering.**: Гарантируйте порядок событий для одного aggregate: partition key в Kafka = `aggregate_id` (например, `order_id`). Покажите, что события `OrderCreated`, `OrderPaid`, `OrderShipped` приходят в том же порядке. Объясните, почему глобальный порядок всех событий — невозможен и не нужен.

### Исходная формулировка

**Outbox Ordering.**: Гарантируйте порядок событий для одного aggregate: partition key в Kafka = `aggregate_id` (например, `order_id`). Покажите, что события `OrderCreated`, `OrderPaid`, `OrderShipped` приходят в том же порядке. Объясните, почему глобальный порядок всех событий — невозможен и не нужен.

## Теория

В распределенных системах понятие единого глобального времени (Global Clock) и глобального строгого порядка всех событий системы невозможно без огромной задержки и блокировок (теорема CAP/PACELC). Однако в реальном бизнесе глобальный порядок не требуется: событие изменения профиля пользователя \(A\) никак не зависит от оплаты заказа пользователем \(B\).

Необходим **порядок в рамках сущности (Causal Ordering / Aggregate Ordering)**:
1. В таблице Outbox каждое событие содержит `aggregate_id` (например, `order_id`).
2. Relay Worker при отправке в Kafka указывает `Record.Key = aggregate_id`.
3. Kafka хэширует ключ (`murmur2(key) % num_partitions`) и гарантированно направляет все события этого заказа в одну и ту же партицию.
4. Внутри одной партиции Kafka гарантирует строгий FIFO порядок доставки.

## Решение по шагам

1. Сформируйте последовательность событий для агрегата: `Created` -> `Paid` -> `Shipped`.
2. Рассчитайте партицию назначения по формуле `hash(aggregate_id) % numPartitions`.
3. Убедитесь, что все события с одинаковым `aggregate_id` попали в одну и ту же партицию в строгом порядке.
4. Продемонстрируйте консьюмер, который читает партицию последовательно без нарушения бизнес-статусов.

## Код решения

**`outbox_ordering.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
)

type Event struct {
	EventID     string
	AggregateID string
	EventType   string
	Sequence    int
}

type PartitionQueue struct {
	PartitionID int
	Messages    []Event
}

type KafkaClusterMock struct {
	numPartitions int
	partitions    map[int]*PartitionQueue
}

func NewKafkaClusterMock(numPartitions int) *KafkaClusterMock {
	cluster := &KafkaClusterMock{
		numPartitions: numPartitions,
		partitions:    make(map[int]*PartitionQueue),
	}
	for i := 0; i < numPartitions; i++ {
		cluster.partitions[i] = &PartitionQueue{PartitionID: i}
	}
	return cluster
}

func (k *KafkaClusterMock) CalculatePartition(key string) int {
	hasher := fnv.New32a()
	_, _ = hasher.Write([]byte(key))
	hashVal := hasher.Sum32()
	return int(hashVal) % k.numPartitions
}

func (k *KafkaClusterMock) Publish(event Event) {
	partID := k.CalculatePartition(event.AggregateID)
	q := k.partitions[partID]
	q.Messages = append(q.Messages, event)
	fmt.Printf("[Producer] Sent %s (seq: %d) for Aggregate '%s' -> Partition #%d\n",
		event.EventType, event.Sequence, event.AggregateID, partID)
}

func main() {
	cluster := NewKafkaClusterMock(4) // 4 партиции в топике

	orderAEvents := []Event{
		{EventID: "e1", AggregateID: "order-alpha", EventType: "OrderCreated", Sequence: 1},
		{EventID: "e2", AggregateID: "order-alpha", EventType: "OrderPaid", Sequence: 2},
		{EventID: "e3", AggregateID: "order-alpha", EventType: "OrderShipped", Sequence: 3},
	}

	orderBEvents := []Event{
		{EventID: "e4", AggregateID: "order-beta", EventType: "OrderCreated", Sequence: 1},
		{EventID: "e5", AggregateID: "order-beta", EventType: "OrderCancelled", Sequence: 2},
	}

	fmt.Println("=== Publishing Events to Kafka with Aggregate Key ===")
	for _, ev := range orderAEvents {
		cluster.Publish(ev)
	}
	for _, ev := range orderBEvents {
		cluster.Publish(ev)
	}

	fmt.Println("\n=== Verifying Partition Contents and FIFO Order ===")
	for pID := 0; pID < cluster.numPartitions; pID++ {
		q := cluster.partitions[pID]
		if len(q.Messages) == 0 {
			continue
		}
		fmt.Printf("Partition #%d contains %d messages:\n", pID, len(q.Messages))
		for _, msg := range q.Messages {
			fmt.Printf("   -> Seq %d: %s (Aggregate: %s)\n", msg.Sequence, msg.EventType, msg.AggregateID)
		}
	}
}
```

ℹ️ События одного агрегата всегда распределяются в одну партицию с гарантией порядка

## Под капотом

Kafka брокер гарантирует строгий порядок смещений (Offset 0, 1, 2, ...) строго в рамках одной партиции. Между разными партициями порядок не определен. Привязка `partition_key = aggregate_id` обеспечивает маршрутизацию жизненного цикла заказа строго в один поток чтения консьюмера.

## Подводные камни

1. Изменение количества партиций в топике Kafka на лету: при изменении числа партиций функция хэширования `hash(key) % N` распределит новые события того же агрегата в другую партицию, нарушив хронологию.
2. Многопоточная обработка внутри консьюмера без шардирования: если воркер читает партицию и раздает задачи в пул горутин без группировки по `aggregate_id`, `OrderShipped` может обогнать `OrderCreated`.

## На собеседовании

Вопрос: Почему глобальный порядок событий в распределенных системах считается антипаттерном?
Ответ: Чтобы обеспечить строго глобальный порядок, всю систему пришлось бы свести к одной-единственной партиции и одному потоку потребителя. Это полностью уничтожает горизонтальное масштабирование (throughput). Поэтому индустриальный стандарт — партиционирование по бизнес-ключам (Aggregate ID).
