# Очистка Inbox-таблицы: Pruning Daemon и управление размером дедупликационного окна

## Условие

44. **Очистка Inbox-таблицы (Pruning Daemon)**: Если хранить ID всех обработанных сообщений в таблице `inbox_events` бесконечно, её размер вырастет до гигабайт, что замедлит проверку уникальности. Напишите фоновую задачу-чистильщик (Pruning Daemon) в Go, которая раз в сутки удаляет из таблицы `inbox_events` записи старше 7 дней, гарантируя, что мы защищены от дубликатов в рамках недельного окна повторов.

### Исходная формулировка

**Очистка Inbox-таблицы (Pruning Daemon)**: Если хранить ID всех обработанных сообщений в таблице `inbox_events` бесконечно, её размер вырастет до гигабайт, что замедлит проверку уникальности. Напишите фоновую задачу-чистильщик (Pruning Daemon) в Go, которая раз в сутки удаляет из таблицы `inbox_events` записи старше 7 дней, гарантируя, что мы защищены от дубликатов в рамках недельного окна повторов.

## Теория

Таблица `inbox_events` накапливает записи со скоростью всего входящего потока сообщений. При 10 млн сообщений в сутки за год таблица разрастется до миллиардов строк, что приведет к раздуванию B-Tree индексов, падению эффективности кэша памяти (`shared_buffers`) и замедлению вставок.

В реальных системах дубликаты сообщений от брокера могут приходить только в пределах окна повторов (Retry Window): от нескольких секунд до нескольких дней (максимальный TTL сообщений в Kafka обычно равен 7 дням). Следовательно, хранить записи старше 7 дней бессмысленно — брокер физически не сможет доставить более старое сообщение.

Фоновый процесс Pruning Daemon выполняет удаление порциями (Chunked Deletion), чтобы не блокировать таблицу монопольным локом и не перегружать транзакционный журнал.

## Решение по шагам

1. Сформулируйте условие удаления: `processed_at < NOW() - INTERVAL '7 days'`.
2. Настройте периодический таймер (`time.NewTicker(24 * time.Hour)`).
3. Выполняйте удаление небольшими пачками (`LIMIT 1000`), чтобы избежать длительных блокировок.
4. Логируйте количество удаленных устаревших записей.

## Код решения

**`inbox_pruning_daemon.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type InboxEntry struct {
	EventID     string
	ProcessedAt time.Time
}

type InboxStore struct {
	mu      sync.Mutex
	entries map[string]InboxEntry
}

func NewInboxStore() *InboxStore {
	return &InboxStore{
		entries: make(map[string]InboxEntry),
	}
}

func (s *InboxStore) PruneOldRecords(olderThan time.Duration, limit int) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	threshold := time.Now().Add(-olderThan)
	deleted := 0

	for id, entry := range s.entries {
		if entry.ProcessedAt.Before(threshold) {
			delete(s.entries, id)
			deleted++
			if deleted >= limit {
				break
			}
		}
	}

	return deleted
}

func (s *InboxStore) Count() int {
	s.mu.Lock()
	defer s.mu.Unlock()
	return len(s.entries)
}

type PruningDaemon struct {
	store        *InboxStore
	retention    time.Duration
	pruneTicker  *time.Ticker
	stopChan     chan struct{}
}

func NewPruningDaemon(store *InboxStore, retention time.Duration, interval time.Duration) *PruningDaemon {
	return &PruningDaemon{
		store:       store,
		retention:   retention,
		pruneTicker: time.NewTicker(interval),
		stopChan:    make(chan struct{}),
	}
}

func (d *PruningDaemon) Start(ctx context.Context) {
	go func() {
		fmt.Printf("[Pruning Daemon] Started. Retention window: %v\n", d.retention)
		for {
			select {
			case <-ctx.Done():
				return
			case <-d.stopChan:
				return
			case <-d.pruneTicker.C:
				totalDeleted := 0
				for {
					// Chunked deletion (пачками по 500 записей)
					n := d.store.PruneOldRecords(d.retention, 500)
					totalDeleted += n
					if n == 0 {
						break
					}
				}
				if totalDeleted > 0 {
					fmt.Printf("[Pruning Daemon] Pruned %d expired entries. Remaining active inbox size: %d\n",
						totalDeleted, d.store.Count())
				}
			}
		}
	}()
}

func (d *PruningDaemon) Stop() {
	d.pruneTicker.Stop()
	close(d.stopChan)
}

func main() {
	store := NewInboxStore()
	now := time.Now()

	// Добавим старые записи (возраст 8 дней)
	for i := 1; i <= 3; i++ {
		id := fmt.Sprintf("old-msg-%d", i)
		store.entries[id] = InboxEntry{
			EventID:     id,
			ProcessedAt: now.Add(-8 * 24 * time.Hour),
		}
	}

	// Добавим свежие записи (возраст 1 час)
	for i := 1; i <= 2; i++ {
		id := fmt.Sprintf("fresh-msg-%d", i)
		store.entries[id] = InboxEntry{
			EventID:     id,
			ProcessedAt: now.Add(-1 * time.Hour),
		}
	}

	fmt.Printf("Initial total inbox records: %d\n", store.Count())

	// Запуск демона с retention = 7 дней и тикером 20мс для теста
	daemon := NewPruningDaemon(store, 7*24*time.Hour, 20*time.Millisecond)
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	daemon.Start(ctx)

	time.Sleep(50 * time.Millisecond)
	daemon.Stop()

	fmt.Printf("Final verified inbox records: %d (Only fresh messages preserved)\n", store.Count())
}
```

ℹ️ Удаление устаревших записей пачками предотвращает разрастание дедупликационной таблицы

## Под капотом

В больших СУБД удаление через `DELETE FROM inbox WHERE processed_at < ...` порождает проблему мертвых строк (Dead Tuples) и раздувания таблиц (Table Bloat). В продакшене таблицу `inbox_events` разбивают на партиции по дням (`PARTITION BY RANGE (processed_at)`). Тогда удаление старых данных выполняется мгновенно с помощью `DROP TABLE inbox_events_2026_08_30`, что занимает 0 миллисекунд и не нагружает автовакуум (VACUUM).

## Подводные камни

1. Запуск одного огромного `DELETE FROM inbox_events WHERE processed_at < NOW() - INTERVAL '7 days'`: это повесит эксклюзивную блокировку на миллионы строк и забьет диск WAL логами.
2. Retention window меньше времени ретраев брокера: если Dead Letter Queue ретраит упавшие сообщения в течение 14 дней, а Inbox чистится через 7 дней, повторное сообщение будет ошибочно воспринято как новое.

## На собеседовании

Вопрос: Как выбрать оптимальное время хранения записей в таблице Inbox?
Ответ: Retention Time таблицы Inbox должен быть строго больше максимального времени жизни сообщений в брокере (Kafka `log.retention.hours` или RabbitMQ TTL) плюс максимальное время обработки в Dead Letter Queue. Если Kafka хранит топик 7 дней, retention Inbox настраивается минимум на 8–10 дней.
