### Исходная формулировка

**CDC-based Outbox (без polling).**: Настройте Debezium на таблицу `outbox`. Покажите, что relay больше не нужен — PostgreSQL WAL → Kafka Connect → Kafka Topic напрямую. Сравните latency: polling (500 мс) vs CDC (<100 мс). Объясните trade-off: сложность инфраструктуры vs простота кода.

## Теория

Традиционный опрос базы данных (Polling) создает постоянную паразитную нагрузку на СУБД: каждую секунду воркер выполняет `SELECT FOR UPDATE SKIP LOCKED`, блокируя строки и нагружая диск. Архитектура CDC (Change Data Capture) полностью устраняет поллинг:

1. Бизнес-сервис выполняет обычную транзакцию: вставляет заказ и строку в `outbox_events`.
2. PostgreSQL записывает транзакцию в Write-Ahead Log (WAL) на диске.
3. Сервис Debezium (или легковесный Go-воркер на базе `pglogrepl`) подключается через Replication Protocol (логический слот репликации).
4. Как только транзакция фиксируется (`COMMIT`), Debezium мгновенно вычитывает бинарный поток изменений WAL и публикует событие в Kafka Topic с задержкой 10–50 миллисекунд.
В Go-коде сервиса больше не нужно писать и поддерживать сложный Relay Worker.

## Решение по шагам

1. Напишите конфигурационный JSON коннектора Debezium для таблицы `outbox_events`.
2. Смоделируйте пайплайн WAL Streamer на Go, читающий события изменения таблицы.
3. Сравните метрики задержки доставки Poller (500 мс) против CDC (<50 мс).

## Код решения

**`debezium_cdc_outbox.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// Конфигурация коннектора Debezium PostgreSQL Connector:
// {
//   "name": "outbox-connector",
//   "config": {
//     "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
//     "plugin.name": "pgoutput",
//     "database.hostname": "postgres-master",
//     "table.include.list": "public.outbox_events",
//     "transforms": "outbox",
//     "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
//     "transforms.outbox.route.topic.replacement": "${routedByValue}.events"
//   }
// }

type WALChangeRecord struct {
	LSN       uint64
	Table     string
	Operation string // INSERT, UPDATE, DELETE
	RowData   map[string]interface{}
	Timestamp time.Time
}

type MockWALStreamer struct {
	changes chan WALChangeRecord
}

func (s *MockWALStreamer) StreamChanges(ctx context.Context) <-chan WALChangeRecord {
	return s.changes
}

func main() {
	walStreamer := &MockWALStreamer{changes: make(chan WALChangeRecord, 10)}
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	// Запуск Debezium / CDC Consumer
	go func() {
		for change := range walStreamer.StreamChanges(ctx) {
			latency := time.Since(change.Timestamp)
			fmt.Printf("[CDC Event Router] LSN: %d | Op: %s | Table: %s\n", change.LSN, change.Operation, change.Table)
			fmt.Printf(" -> Extracted Outbox Payload: %v\n", change.RowData["payload"])
			fmt.Printf(" -> Routed directly to Kafka Topic '%s' in %v (Zero Polling Overhead!)\n\n",
				change.RowData["aggregate_type"], latency)
		}
	}()

	fmt.Println("=== 1. Business Service commits transaction to PostgreSQL ===")
	commitTime := time.Now()

	// Имитация записи в WAL движком PostgreSQL
	walStreamer.changes <- WALChangeRecord{
		LSN:       1024880,
		Table:     "outbox_events",
		Operation: "INSERT",
		RowData: map[string]interface{}{
			"id":             "evt-wal-101",
			"aggregate_type": "orders",
			"payload":        `{"order_id": "ord-wal-77", "status": "CREATED"}`,
		},
		Timestamp: commitTime,
	}

	time.Sleep(50 * time.Millisecond)

	fmt.Println("=== Architecture Trade-offs: Poller vs CDC ===")
	fmt.Println("| Параметр               | Outbox Poller (Go Worker) | CDC (Debezium / WAL)    |")
	fmt.Println("|------------------------|---------------------------|-------------------------|")
	fmt.Println("| E2E Latency            | 500 ms - 2 sec            | 10 - 50 ms              |")
	fmt.Println("| Нагрузка на СУБД (CPU) | Высокая (постоянный SELECT)| Нулевая (чтение с диска)|")
	fmt.Println("| Сложность кода         | Средняя (горутины, локи)  | Нулевая (нет воркера)   |")
	fmt.Println("| Инфраструктура         | Простая (только Go и БД)  | Высокая (Kafka Connect) |")
}
```

ℹ️ CDC Debezium транслирует события напрямую из WAL без написания кода ретранслятора

## Под капотом

Debezium использует модуль `pgoutput` логического декодирования PostgreSQL. СУБД переводит бинарный журнал WAL в поток логических сообщений (BEGIN, INSERT, COMMIT). Так как чтение WAL происходит последовательно с диска, на кэш буферов данных (`shared_buffers`) не оказывается никакого влияния.

## Подводные камни

1. Переполнение диска при остановке Debezium: если коннектор Debezium упал, PostgreSQL не может удалить старые сегменты WAL, так как слот репликации не продвигается. Если диск заполнится на 100%, PostgreSQL аварийно остановится (Panic).
2. Рост сложности эксплуатации: требуется отдельный кластер Kafka Connect, мониторинг lag слотов репликации.

## На собеседовании

Вопрос: Что такое Debezium Outbox Event Router SMT и какую задачу он решает?
Ответ: Это плагин Single Message Transform для Kafka Connect. Он автоматически перехватывает записи из таблицы `outbox`, извлекает из строки колонки `aggregate_type` и `payload`, формирует Kafka Record с ключом `aggregate_id` и отправляет событие в топик `${aggregate_type}.events`, избавляя разработчиков от написания сервиса маршрутизации.
