# Inbox vs Application-level Deduplication: сравнение надежности СУБД против скорости Redis

## Условие

54. **Inbox vs application-level deduplication:**
    * Inbox: reliable, но требует БД
    * Application-level (Redis): faster, но Redis может потерять данные
    Используйте Inbox для critical messages, Redis для high-volume non-critical.

### Исходная формулировка

**Inbox vs application-level deduplication:**
* Inbox: reliable, но требует БД
* Application-level (Redis): faster, но Redis может потерять данные
Используйте Inbox для critical messages, Redis для high-volume non-critical.

## Теория

При проектировании слоя дедупликации инженеры выбирают между двумя фундаментальными подходами:

1. **Transactional Inbox (в реляционной СУБД):**
   - Механизм: таблица `inbox` в той же БД, коммит в единой ACID-транзакции.
   - Плюсы: 100% математическая гарантия консистентности, нет риска рассинхронизации между кэшем и БД.
   - Минусы: повышенный дисковый I/O, нагрузка на соединения СУБД, пропускная способность обычно до 5 000–10 000 оп/сек.
   - Применение: биллинг, платежи, складские остатки, юридические договоры.

2. **Application-Level Deduplication (в Redis):**
   - Механизм: `SETNX` с TTL в оперативной памяти Redis.
   - Плюсы: суб-миллисекундная задержка, пропускная способность 100 000+ оп/сек.
   - Минусы: Redis не участвует в ACID-транзакции с БД. При аварии репликации Redis (асинхронная репликация) или сбое записи в БД после установки ключа в Redis возможны потери или дубли.
   - Применение: сбор логов, метрик, кликов, отправка push-уведомлений, телеметрия.

## Решение по шагам

1. Спроектируйте абстрактный интерфейс `Deduplicator`.
2. Реализуйте `PostgresInboxDeduplicator` для критических транзакций.
3. Реализуйте `RedisInboxDeduplicator` для высоконагруженных некритических потоков.
4. Продемонстрируйте маршрутизацию событий в зависимости от уровня критичности (Severity Level).

## Код решения

**`dedup_strategy.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type EventPriority int

const (
	PriorityCritical EventPriority = iota // Финансы, Заказы -> Postgres Inbox
	PriorityHighVolume                    // Клики, Метрики -> Redis
)

type Deduplicator interface {
	IsDuplicate(ctx context.Context, key string) (bool, error)
}

// 1. Transactional Inbox (Reliable, DB-backed)
type PostgresInboxDeduplicator struct {
	mu    sync.Mutex
	table map[string]bool
}

func (p *PostgresInboxDeduplicator) IsDuplicate(ctx context.Context, key string) (bool, error) {
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.table[key] {
		return true, nil
	}
	p.table[key] = true
	return false, nil
}

// 2. High-speed Redis Deduplicator (Faster, In-memory)
type RedisDeduplicator struct {
	mu    sync.Mutex
	cache map[string]bool
}

func (r *RedisDeduplicator) IsDuplicate(ctx context.Context, key string) (bool, error) {
	r.mu.Lock()
	defer r.mu.Unlock()
	if r.cache[key] {
		return true, nil
	}
	r.cache[key] = true
	return false, nil
}

type HybridDispatcher struct {
	dbDeduplicator    Deduplicator
	redisDeduplicator Deduplicator
}

func (d *HybridDispatcher) RouteAndProcess(ctx context.Context, eventID string, priority EventPriority, payload string) {
	var dedup Deduplicator
	var strategyName string

	if priority == PriorityCritical {
		dedup = d.dbDeduplicator
		strategyName = "PostgreSQL Transactional Inbox (Guaranteed ACID)"
	} else {
		dedup = d.redisDeduplicator
		strategyName = "Redis SETNX (Sub-millisecond In-Memory)"
	}

	isDup, err := dedup.IsDuplicate(ctx, eventID)
	if err != nil {
		fmt.Printf("[Error] Deduplication check failed: %v\n", err)
		return
	}

	if isDup {
		fmt.Printf("[%s] Duplicate rejected for event %s. No-Op.\n", strategyName, eventID)
		return
	}

	fmt.Printf("[%s] Event %s processed successfully: %s\n", strategyName, eventID, payload)
}

func main() {
	dispatcher := &HybridDispatcher{
		dbDeduplicator:    &PostgresInboxDeduplicator{table: make(map[string]bool)},
		redisDeduplicator: &RedisDeduplicator{cache: make(map[string]bool)},
	}
	ctx := context.Background()

	fmt.Println("=== 1. Processing Critical Financial Event (Postgres Inbox) ===")
	dispatcher.RouteAndProcess(ctx, "pay-evt-100", PriorityCritical, `{"amount": 50000, "action": "charge"}`)
	dispatcher.RouteAndProcess(ctx, "pay-evt-100", PriorityCritical, `{"amount": 50000, "action": "charge"}`)

	fmt.Println("\n=== 2. Processing High-Volume Clickstream Event (Redis Fast Dedup) ===")
	dispatcher.RouteAndProcess(ctx, "click-evt-999", PriorityHighVolume, `{"banner_id": 44, "user": "u-1"}`)
	dispatcher.RouteAndProcess(ctx, "click-evt-999", PriorityHighVolume, `{"banner_id": 44, "user": "u-1"}`)
}
```

ℹ️ Гибридный подход: надежный Inbox для критических данных и быстрый Redis для телеметрии

## Под капотом

Сравнение накладных расходов: операция `INSERT` в PostgreSQL требует прохождения через парсер SQL, планировщик, MVCC блокировки, запись в WAL и ожидание `fsync`. Операция `SET NX EX` в Redis выполняется за несколько инструкций процессора прямо в хэш-таблице RAM без блокировок таблиц.

## Подводные камни

1. Использование Redis для финансовых проводок: при перезапуске инстанса Redis (или репликации с лагом) ключ может пропасть, вызвав повторное списание денег.
2. Использование Transactional Inbox для сбора 100 000 кликов в секунду: база данных ляжет от перегрузки диска WAL.

## На собеседовании

Вопрос: Что произойдет, если мы сделаем `SETNX` в Redis, а последующий коммит в PostgreSQL упадет?
Ответ: Возникнет состояние рассинхронизации: Redis считает, что сообщение уже обработано, а в базе данных бизнес-изменения отсутствуют. При повторной доставке сообщения брокером Redis заблокирует его как дубликат, и бизнес-действие никогда не выполнится. Поэтому для критических транзакций Redis недопустим.
