# Inbox Deduplication: составной уникальный ключ UNIQUE(event_id, consumer_name)

## Условие

38. **Inbox Deduplication.**: Добавьте unique constraint `UNIQUE(event_id, consumer_name)`. При повторном получении — игнорировать. Покажите, что разные consumers (OrderService и AnalyticsService) могут обработать один event_id независимо.

### Исходная формулировка

**Inbox Deduplication.**: Добавьте unique constraint `UNIQUE(event_id, consumer_name)`. При повторном получении — игнорировать. Покажите, что разные consumers (OrderService и AnalyticsService) могут обработать один event_id независимо.

## Теория

В событийно-ориентированных архитектурах один и тот же топик брокера (например, `orders.events`) читают несколько независимых микросервисов: `InventoryService`, `BillingService`, `AnalyticsService` и др. Если все сервисы используют общую базу данных или один консьюмер разделяет Inbox между несколькими логическими воркерами, простой уникальный индекс по `event_id` приведет к тому, что первый сервис обработает событие, а второй сервис посчитает его дубликатом и проигнорирует.

Для изоляции обработки используется составной ключ:
`CONSTRAINT uq_inbox_event_consumer UNIQUE(event_id, consumer_name)`.
Это гарантирует, что каждый независимый обработчик (Consumer Group) зафиксирует факт обработки события строго для себя, не блокируя коллег.

## Решение по шагам

1. Спроектируйте таблицу Inbox с составным первичным ключом `(event_id, consumer_name)`.
2. Реализуйте структуру консьюмера, хранящую имя сервиса (`consumer_name`).
3. Смоделируйте поступление одного и того же `event_id` в `OrderNotificationService` и `AnalyticsService`.
4. Убедитесь, что оба сервиса успешно обработали первичное сообщение.
5. Сымитируйте повторную доставку того же `event_id` в `OrderNotificationService` и убедитесь, что сработала дедупликация.

## Код решения

**`inbox_multi_consumer.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type InboxRecord struct {
	EventID      string
	ConsumerName string
	Status       string
}

type DatabaseStorage struct {
	mu    sync.Mutex
	inbox map[string]InboxRecord // key: eventID + ":" + consumerName
	logs  []string
}

func NewDatabaseStorage() *DatabaseStorage {
	return &DatabaseStorage{
		inbox: make(map[string]InboxRecord),
	}
}

func (db *DatabaseStorage) TryInsertInbox(eventID, consumerName string) (bool, error) {
	db.mu.Lock()
	defer db.mu.Unlock()

	compositeKey := eventID + ":" + consumerName
	if _, exists := db.inbox[compositeKey]; exists {
		// Unique constraint violation
		return false, nil
	}

	db.inbox[compositeKey] = InboxRecord{
		EventID:      eventID,
		ConsumerName: consumerName,
		Status:       "PROCESSED",
	}
	db.logs = append(db.logs, fmt.Sprintf("[%s] Processed event %s", consumerName, eventID))
	return true, nil
}

type ConsumerService struct {
	name string
	db   *DatabaseStorage
}

func NewConsumerService(name string, db *DatabaseStorage) *ConsumerService {
	return &ConsumerService{name: name, db: db}
}

func (c *ConsumerService) HandleMessage(ctx context.Context, eventID, payload string) error {
	inserted, err := c.db.TryInsertInbox(eventID, c.name)
	if err != nil {
		return err
	}

	if !inserted {
		fmt.Printf("[%s] Event %s already processed by this consumer. Skipping execution (Deduplicated).\n",
			c.name, eventID)
		return nil
	}

	fmt.Printf("[%s] Successfully executed business logic for event %s (payload: %s)\n",
		c.name, eventID, payload)
	return nil
}

func main() {
	db := NewDatabaseStorage()
	ctx := context.Background()

	orderConsumer := NewConsumerService("OrderBillingConsumer", db)
	analyticsConsumer := NewConsumerService("AnalyticsConsumer", db)

	eventID := "evt-global-999"
	payload := `{"order_id": "ord-777", "amount": 2500}`

	fmt.Println("=== 1. First Consumer (Billing) processes event ===")
	_ = orderConsumer.HandleMessage(ctx, eventID, payload)

	fmt.Println("\n=== 2. Second Consumer (Analytics) processes the SAME event ===")
	_ = analyticsConsumer.HandleMessage(ctx, eventID, payload)

	fmt.Println("\n=== 3. Retry delivery of the SAME event to First Consumer (Billing) ===")
	_ = orderConsumer.HandleMessage(ctx, eventID, payload)

	fmt.Println("\n=== Storage Audit Logs ===")
	for _, l := range db.logs {
		fmt.Println(" - " + l)
	}
}
```

ℹ️ Составной ключ гарантирует независимую обработку для каждого сервиса

## Под капотом

Индекс `B-Tree` в PostgreSQL по двум колонкам `(event_id, consumer_name)` строит композитные ключи. Порядок колонок имеет значение: если первой идет `event_id`, СУБД может быстро находить все сервисы, обработавшие данный `event_id`, а также выполнять точечную проверку по обоим полям. Размер B-Tree индекса составляет O(N) от числа доставок.

## Подводные камни

1. Использование только `event_id` как Primary Key в общем хранилище: второй сервис получит UniqueViolation и пропустит обработку чужого события.
2. Передача неконсистентного `consumer_name`: если имя сервиса генерируется динамически с номером пода (напр. `consumer-pod-xyz`), после перезапуска пода дубликаты перестанут определяться.

## На собеседовании

Вопрос: Почему в микросервисной архитектуре у каждого сервиса должна быть своя изолированная база данных, включая Inbox?
Ответ: Паттерн Database-per-Service исключает распределенные транзакции и общие точки отказа. Когда у сервиса своя БД, его таблица `inbox` хранит только события данного сервиса, и ее первичным ключом является просто `event_id`. Составной ключ `(event_id, consumer_name)` применяется внутри сервиса, если один сервис запускает несколько независимых бизнес-обработчиков одного и того же топика.
