# Transactional Inbox: реализация консьюмера с полями message_id и processed

## Условие

48. **[Transactional Inbox]**: На стороне консьюмера создай таблицу `inbox` (поля: `message_id`, `processed`). При получении сообщения из Kafka, консьюмер сначала делает `INSERT INTO inbox (message_id) VALUES (...)` в рамках бизнес-транзакции.

### Исходная формулировка

**[Transactional Inbox]**: На стороне консьюмера создай таблицу `inbox` (поля: `message_id`, `processed`). При получении сообщения из Kafka, консьюмер сначала делает `INSERT INTO inbox (message_id) VALUES (...)` в рамках бизнес-транзакции.

## Теория

Классическая схема таблицы Transactional Inbox содержит минимальный набор полей:
```sql
CREATE TABLE inbox (
    message_id VARCHAR(128) PRIMARY KEY,
    processed BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```
Поле `processed` позволяет отличать стадии обработки, если консьюмер использует двухфазную модель: 1) регистрация события (`processed = false`), 2) обработка асинхронным воркером, 3) фиксация (`processed = true`).

В синхронной схеме `processed` устанавливается в `true` в момент коммита бизнес-транзакции. Если бизнес-логика падает, вся транзакция откатывается (`ROLLBACK`), и запись `message_id` исчезает из `inbox`, что позволяет следующей повторной доставке из брокера попытаться обработать событие заново.

## Решение по шагам

1. Спроектируйте модель `InboxRecord` с полями `MessageID`, `Processed`, `CreatedAt`.
2. В методе `HandleKafkaMessage` откройте транзакцию.
3. Выполните `INSERT INTO inbox (message_id, processed) VALUES (?, true)`.
4. В случае ошибки дубликата отмените транзакцию и завершите вызов успешно.
5. Выполните бизнес-действие и закоммитьте транзакцию.

## Код решения

**`inbox_fields_consumer.go`**

```go
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"sync"
	"time"
)

type InboxRecord struct {
	MessageID string
	Processed bool
	CreatedAt time.Time
}

type MockDB struct {
	mu     sync.Mutex
	inbox  map[string]InboxRecord
	points map[string]int
}

func NewMockDB() *MockDB {
	return &MockDB{
		inbox:  make(map[string]InboxRecord),
		points: make(map[string]int),
	}
}

func (db *MockDB) ProcessLoyaltyEvent(ctx context.Context, msgID, userID string, addPoints int) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// BEGIN TRANSACTION
	// Шаг 1: Проверка первичного ключа в inbox
	if _, exists := db.inbox[msgID]; exists {
		// ROLLBACK & ACK: событие уже обработано
		return sql.ErrNoRows // Используем как маркер "Duplicate detected"
	}

	// Шаг 2: Вставка в inbox
	db.inbox[msgID] = InboxRecord{
		MessageID: msgID,
		Processed: true,
		CreatedAt: time.Now().UTC(),
	}

	// Шаг 3: Бизнес-логика (начисление баллов)
	db.points[userID] += addPoints
	// COMMIT TRANSACTION
	return nil
}

type LoyaltyConsumer struct {
	db *MockDB
}

func (c *LoyaltyConsumer) OnKafkaMessage(ctx context.Context, msgID, userID string, points int) {
	err := c.db.ProcessLoyaltyEvent(ctx, msgID, userID, points)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			fmt.Printf("[Kafka Consumer] Message %s is a duplicate! Acking to broker without changes.\n", msgID)
			return
		}
		fmt.Printf("[Kafka Consumer] Error: %v\n", err)
		return
	}

	fmt.Printf("[Kafka Consumer] Message %s processed! User %s awarded +%d loyalty points.\n",
		msgID, userID, points)
}

func main() {
	db := NewMockDB()
	consumer := &LoyaltyConsumer{db: db}
	ctx := context.Background()

	msgID := "kafka-msg-loyalty-888"
	userID := "usr-vip-007"

	fmt.Println("=== Delivery 1 ===")
	consumer.OnKafkaMessage(ctx, msgID, userID, 100)
	fmt.Printf("User points: %d\n\n", db.points[userID])

	fmt.Println("=== Delivery 2 (Duplicate) ===")
	consumer.OnKafkaMessage(ctx, msgID, userID, 100)
	fmt.Printf("User points: %d (Strictly unchanged)\n", db.points[userID])
}
```

ℹ️ Таблица inbox с полями message_id и processed обеспечивает строгий фильтр дубликатов

**`output.txt`**

```bash

[Kafka Consumer] Message kafka-msg-loyalty-888 processed! User usr-vip-007 awarded +100 loyalty points.
User points: 100

=== Delivery 2 (Duplicate) ===
[Kafka Consumer] Message kafka-msg-loyalty-888 is a duplicate! Acking to broker without changes.
User points: 100 (Strictly unchanged)
```

## Под капотом

Первичный ключ `PRIMARY KEY (message_id)` создает B-Tree индекс в реляционной базе данных. Поиск и проверка наличия ключа выполняются за время \(O(\log N)\). Благодаря транзакционной изоляции, блокировка уникальности строки удерживается до момента вызова `COMMIT`.

## Подводные камни

1. Забытый `defer tx.Rollback()`: в случае возникновения ошибки или паники в коде транзакция останется открытой, что приведет к исчерпанию соединений с СУБД.
2. Перехват всех ошибок без разбора: если `INSERT` упал из-за обрыва соединения с БД или дисковой ошибки, нельзя считать это дубликатом! Сообщение должно быть возвращено в брокер (Nack/Retry).

## На собеседовании

Вопрос: Зачем в таблице Inbox может понадобиться поле `response_payload` (или `result`)?
Ответ: Если консьюмер является частью синхронного RPC или Saga с ответом (Request-Reply), при повторном запросе ему нужно не просто проигнорировать выполнение, но и вернуть клиенту тот же самый результат, который был получен в первый раз. В этом случае `response_payload` кэширует готовый ответ.
