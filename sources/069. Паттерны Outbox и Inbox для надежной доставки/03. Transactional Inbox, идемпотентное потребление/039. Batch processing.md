# Batch processing: пакетная выборка и транзакционная отправка событий Outbox Poller

## Условие

39. **Batch processing**: Poller читает batch messages и обрабатывает их в одной транзакции (если бизнес-логика позволяет).

### Исходная формулировка

**Batch processing**: Poller читает batch messages и обрабатывает их в одной транзакции (если бизнес-логика позволяет).

## Теория

Построчная обработка сообщений из таблицы Outbox (`SELECT 1 ... UPDATE 1`) неэффективна: на 10 000 сообщений в секунду база будет загружена миллионами транзакционных коммитов и блокировок строк. Паттерн Batch Processing группирует выборку и обновление:
1. Воркер выбирает пачку из \(N\) записей (например, \(N = 100\)) с помощью:
`SELECT id, topic, payload FROM outbox WHERE processed = false ORDER BY id ASC LIMIT 100 FOR UPDATE SKIP LOCKED;`
2. Воркер отправляет пачку в брокер (используя пакетный продюсер брокера).
3. После подтверждения брокера выполняется один пакетный SQL-запрос:
`UPDATE outbox SET processed = true, sent_at = NOW() WHERE id = ANY($1);`.
Это снижает нагрузку на WAL и транзакционный лог базы данных на порядок.

## Решение по шагам

1. Определите размер батча (`batchSize = 100`).
2. Выполните выборку пачки записей из Outbox.
3. Сформируйте массив сообщений и отправьте пачку в брокер одним пакетным вызовом.
4. Соберите список идентификаторов успешно отправленных событий (`ids`).
5. Выполните единый SQL `UPDATE` по списку ID в рамках одной транзакции.

## Код решения

**`batch_outbox_poller.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxRow struct {
	ID        int64
	Topic     string
	Payload   string
	Processed bool
}

type BatchBroker interface {
	PublishBatch(ctx context.Context, topic string, payloads []string) error
}

type MockBatchBroker struct {
	mu           sync.Mutex
	totalBatches int
	totalMsgs    int
}

func (b *MockBatchBroker) PublishBatch(ctx context.Context, topic string, payloads []string) error {
	b.mu.Lock()
	defer b.mu.Unlock()

	b.totalBatches++
	b.totalMsgs += len(payloads)
	fmt.Printf("[Broker Batch Publish] Topic: '%s', Messages in batch: %d\n", topic, len(payloads))
	return nil
}

type OutboxBatchPoller struct {
	storage   []*OutboxRow
	broker    BatchBroker
	batchSize int
	mu        sync.Mutex
}

func NewOutboxBatchPoller(broker BatchBroker, rows []*OutboxRow, batchSize int) *OutboxBatchPoller {
	return &OutboxBatchPoller{
		storage:   rows,
		broker:    broker,
		batchSize: batchSize,
	}
}

func (p *OutboxBatchPoller) PollAndFlush(ctx context.Context) (int, error) {
	p.mu.Lock()
	defer p.mu.Unlock()

	// 1. SELECT ... LIMIT batchSize
	var batch []*OutboxRow
	for _, row := range p.storage {
		if !row.Processed {
			batch = append(batch, row)
			if len(batch) == p.batchSize {
				break
			}
		}
	}

	if len(batch) == 0 {
		return 0, nil
	}

	// 2. Группировка по топикам для эффективной отправки
	topicPayloads := make(map[string][]string)
	idsToAck := make([]int64, 0, len(batch))
	for _, r := range batch {
		topicPayloads[r.Topic] = append(topicPayloads[r.Topic], r.Payload)
		idsToAck = append(idsToAck, r.ID)
	}

	// 3. Отправка в брокер
	for topic, payloads := range topicPayloads {
		if err := p.broker.PublishBatch(ctx, topic, payloads); err != nil {
			return 0, fmt.Errorf("failed to batch publish to %s: %w", topic, err)
		}
	}

	// 4. Batch UPDATE в локальной базе
	fmt.Printf("[DB Batch Update] UPDATE outbox SET processed = true WHERE id IN (%v)\n", idsToAck)
	for _, r := range batch {
		r.Processed = true
	}

	return len(batch), nil
}

func main() {
	var rows []*OutboxRow
	for i := int64(1); i <= 7; i++ {
		rows = append(rows, &OutboxRow{
			ID:        i,
			Topic:     "customer.events",
			Payload:   fmt.Sprintf(`{"user_id": %d, "action": "login"}`, 1000+i),
			Processed: false,
		})
	}

	broker := &MockBatchBroker{}
	poller := NewOutboxBatchPoller(broker, rows, 3)
	ctx := context.Background()

	fmt.Println("=== Starting Batch Polling Iterations ===")
	iteration := 1
	for {
		flushed, err := poller.PollAndFlush(ctx)
		if err != nil {
			panic(err)
		}
		if flushed == 0 {
			fmt.Println("All messages processed!")
			break
		}
		fmt.Printf("Iteration %d completed: %d messages sent.\n\n", iteration, flushed)
		iteration++
		time.Sleep(10 * time.Millisecond)
	}

	fmt.Printf("Summary: Processed %d messages across %d broker batches.\n",
		broker.totalMsgs, broker.totalBatches)
}
```

ℹ️ Пакетная выборка и обновление сокращают количество обращений к БД и брокеру

## Под капотом

С точки зрения дисковой подсистемы PostgreSQL (WAL), один коммит транзакции на пачку из 100 записей вызывает одну операцию синхронизации `fsync` вместо ста. Это увеличивает пропускную способность сервиса ретрансляции с 500 сообщений/сек до 20 000+ сообщений/сек на стандартном SSD.

## Подводные камни

1. Слишком большой размер батча (например, 10 000 записей): длительная отправка может превысить сетевой таймаут или заблокировать слишком много строк в БД, мешая другим транзакциям.
2. Частичный сбой внутри батча: если из 100 сообщений брокер вернул ошибку на 50-м, нужно либо откатить весь батч (с повторной отправкой первых 50 как дубликатов), либо точечно помечать только подтвержденные ID.

## На собеседовании

Вопрос: Как правильно обрабатывать частичный сбой при асинхронной пакетной отправке в Kafka?
Ответ: Использовать Kafka Producer Callback или канал доставок `deliveryChan`. Каждое сообщение ассоциируется со своим ID из Outbox. Воркер ожидает ответы от брокера с таймаутом. Идентификаторы сообщений, получивших подтверждение смещения (offset), собираются в слайс `successIDs` и обновляются в БД, а отклоненные сообщения остаются необновленными и уходят в следующую попытку.
