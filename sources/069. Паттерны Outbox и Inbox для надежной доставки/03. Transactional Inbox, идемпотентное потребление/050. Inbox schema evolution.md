# Inbox schema evolution: версионирование payload для обратной совместимости консьюмера

## Условие

50. **Inbox schema evolution**: Поддерживайте versioning в payload для backward compatibility.

### Исходная формулировка

**Inbox schema evolution**: Поддерживайте versioning в payload для backward compatibility.

## Теория

Микросервисы развиваются независимо: продюсер может обновиться до версии 2 (добавив новые поля в JSON), в то время как часть консьюмеров все еще работает на версии 1. При эволюции схемы сообщений консьюмер должен обеспечивать обратную совместимость (Backward Compatibility).

Для этого каждое событие снабжается метаданными:
```json
{
  "event_id": "uuid-123",
  "schema_version": 2,
  "payload": { ... }
}
```
Консьюмер использует диспетчеризацию по номеру версии или единый DTO с опциональными полями, выполняя миграцию формата на лету до передачи в бизнес-логику.

## Решение по шагам

1. Определите структуру события с полем `SchemaVersion int`.
2. Создайте структуры для версий 1 (`OrderV1Payload`) и 2 (`OrderV2Payload`).
3. Реализуйте функцию адаптера `NormalizeToCurrentVersion(rawJSON, version)`.
4. Убедитесь, что консьюмер одинаково успешно обрабатывает как старые сообщения v1, так и новые v2.

## Код решения

**`schema_evolution.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Envelope struct {
	EventID       string          `json:"event_id"`
	SchemaVersion int             `json:"schema_version"`
	Payload       json.RawMessage `json:"payload"`
}

type OrderV1 struct {
	OrderID     string  `json:"order_id"`
	Customer    string  `json:"customer"`
	TotalAmount float64 `json:"total_amount"`
}

type OrderV2 struct {
	OrderID      string  `json:"order_id"`
	CustomerID   string  `json:"customer_id"`
	CustomerName string  `json:"customer_name"`
	TotalAmount  float64 `json:"total_amount"`
	Currency     string  `json:"currency"`
}

// Каноническая внутренняя модель сервиса (Current Domain Model)
type CanonicalOrderEvent struct {
	OrderID      string
	CustomerID   string
	CustomerName string
	TotalAmount  float64
	Currency     string
}

func ParseAndNormalize(data []byte) (*CanonicalOrderEvent, error) {
	var env Envelope
	if err := json.Unmarshal(data, &env); err != nil {
		return nil, fmt.Errorf("failed to unmarshal envelope: %w", err)
	}

	switch env.SchemaVersion {
	case 1:
		var v1 OrderV1
		if err := json.Unmarshal(env.Payload, &v1); err != nil {
			return nil, err
		}
		// Миграция со старой схемы v1 к текущей: подставляем дефолтные значения
		return &CanonicalOrderEvent{
			OrderID:      v1.OrderID,
			CustomerID:   "legacy-cust",
			CustomerName: v1.Customer,
			TotalAmount:  v1.TotalAmount,
			Currency:     "RUB", // Дефолт для старой версии
		}, nil

	case 2:
		var v2 OrderV2
		if err := json.Unmarshal(env.Payload, &v2); err != nil {
			return nil, err
		}
		return &CanonicalOrderEvent{
			OrderID:      v2.OrderID,
			CustomerID:   v2.CustomerID,
			CustomerName: v2.CustomerName,
			TotalAmount:  v2.TotalAmount,
			Currency:     v2.Currency,
		}, nil

	default:
		return nil, fmt.Errorf("unsupported schema version: %d", env.SchemaVersion)
	}
}

func main() {
	rawV1Msg := []byte(`{
		"event_id": "evt-001",
		"schema_version": 1,
		"payload": {
			"order_id": "ord-v1-100",
			"customer": "Ivan Ivanov",
			"total_amount": 1500.50
		}
	}`)

	rawV2Msg := []byte(`{
		"event_id": "evt-002",
		"schema_version": 2,
		"payload": {
			"order_id": "ord-v2-200",
			"customer_id": "cust-888",
			"customer_name": "Petr Petrov",
			"total_amount": 2700.00,
			"currency": "USD"
		}
	}`)

	fmt.Println("=== Parsing Legacy Event (Version 1) ===")
	e1, err := ParseAndNormalize(rawV1Msg)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Normalized V1 -> OrderID: %s, Cust: %s, Total: %.2f %s\n\n",
		e1.OrderID, e1.CustomerName, e1.TotalAmount, e1.Currency)

	fmt.Println("=== Parsing Current Event (Version 2) ===")
	e2, err := ParseAndNormalize(rawV2Msg)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Normalized V2 -> OrderID: %s, Cust: %s (ID: %s), Total: %.2f %s\n",
		e2.OrderID, e2.CustomerName, e2.CustomerID, e2.TotalAmount, e2.Currency)
}
```

ℹ️ Паттерн Envelope + Schema Versioning гарантирует плавную эволюцию протоколов событий

**`output.txt`**

```bash
=== Parsing Legacy Event (Version 1) ===
Normalized V1 -> OrderID: ord-v1-100, Cust: Ivan Ivanov, Total: 1500.50 RUB

=== Parsing Current Event (Version 2) ===
Normalized V2 -> OrderID: ord-v2-200, Cust: Petr Petrov (ID: cust-888), Total: 2700.00 USD
```

ℹ️ Обе версии событий успешно приведены к единой внутренней доменной модели

## Под капотом

Вместо самописного версионирования в JSON, Enterprise-системы используют Protobuf или Apache Avro в связке с Confluent Schema Registry. Schema Registry валидирует совместимость (`FULL`, `BACKWARD`, `FORWARD`) еще на этапе отправки продюсером, гарантируя, что ни один консьюмер не упадет с ошибкой десериализации.

## Подводные камни

1. Удаление или переименование полей в новых версиях: ломает старых консьюмеров (Breaking Change). Поля можно только добавлять как опциональные.
2. Отсутствие обработки неизвестных версий: если продюсер выпустил v3, а консьюмер не знает о ней, он должен отправлять сообщение в Dead Letter Queue или корректно логировать алерт.

## На собеседовании

Вопрос: В чем разница между Backward Compatibility и Forward Compatibility событий?
Ответ:
- Backward Compatibility: новый консьюмер способен читать старые события, записанные в Kafka несколько месяцев назад.
- Forward Compatibility: старый консьюмер способен безопасно игнорировать новые неизвестные поля событий от нового продюсера без падения.
