# Outbox + Inbox Chain: сквозная распределенная цепочка Service A → Kafka → Service B → Service C

## Условие

45. **Outbox + Inbox Chain.**: Реализуйте цепочку: Service A (Outbox) → Kafka → Service B (Inbox → Business Logic → Outbox) → Kafka → Service C (Inbox). Покажите end-to-end trace: `order_id` propagates через все события. Объясните, как `correlation_id` помогает в логировании.

### Исходная формулировка

**Outbox + Inbox Chain.**: Реализуйте цепочку: Service A (Outbox) → Kafka → Service B (Inbox → Business Logic → Outbox) → Kafka → Service C (Inbox). Покажите end-to-end trace: `order_id` propagates через все события. Объясните, как `correlation_id` помогает в логировании.

## Теория

В реальных микросервисных архитектурах промежуточные сервисы выступают одновременно и консьюмерами, и продюсерами. Например, Сервис Склада (`Service B`) слушает событие `OrderCreated` от `Service A`, резервирует товар и публикует событие `InventoryReserved` для Сервиса Доставки (`Service C`).

Чтобы обеспечить абсолютную надежность на всем пути следования, `Service B` объединяет Inbox и Outbox в одной локальной транзакции:
```sql
BEGIN;
  INSERT INTO inbox (event_id) VALUES ($1); -- дедупликация входящего события
  UPDATE stock SET qty = qty - 1 WHERE item_id = $2; -- бизнес-логика
  INSERT INTO outbox (topic, payload) VALUES ('inventory.events', $3); -- генерация исходящего события
COMMIT;
```
Для сквозной наблюдаемости (Observability) через заголовки сообщений передается `correlation_id`.

## Решение по шагам

1. Задайте структуру сквозного конверта сообщения с `event_id`, `correlation_id`, `payload`.
2. Service A: создает заказ и пишет `OrderCreated` в свой Outbox.
3. Service B: читает `OrderCreated`, дедуплицирует через Inbox, обновляет склад и пишет `InventoryReserved` в свой Outbox.
4. Service C: читает `InventoryReserved`, дедуплицирует через Inbox и формирует отгрузку.
5. Продемонстрируйте распространение сквозного `correlation_id` на всех этапах.

## Код решения

**`outbox_inbox_chain.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type ChainMessage struct {
	EventID       string
	CorrelationID string
	Topic         string
	Payload       string
}

type SimpleBroker struct {
	mu     sync.Mutex
	queues map[string][]ChainMessage
}

func NewSimpleBroker() *SimpleBroker {
	return &SimpleBroker{queues: make(map[string][]ChainMessage)}
}

func (b *SimpleBroker) Send(msg ChainMessage) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.queues[msg.Topic] = append(b.queues[msg.Topic], msg)
}

func (b *SimpleBroker) Receive(topic string) []ChainMessage {
	b.mu.Lock()
	defer b.mu.Unlock()
	msgs := b.queues[topic]
	b.queues[topic] = nil
	return msgs
}

// Service A (Order Service): Outbox
type ServiceA struct {
	broker *SimpleBroker
}

func (a *ServiceA) CreateOrder(orderID, correlationID string) {
	fmt.Printf("[Service A - Orders] Transaction: Insert Order %s + Outbox Event (Correlation: %s)\n",
		orderID, correlationID)
	// Outbox Relay отправляет в брокер
	a.broker.Send(ChainMessage{
		EventID:       "evt-order-1",
		CorrelationID: correlationID,
		Topic:         "orders.created",
		Payload:       fmt.Sprintf(`{"order_id": "%s"}`, orderID),
	})
}

// Service B (Warehouse Service): Inbox + Business + Outbox
type ServiceB struct {
	broker *SimpleBroker
	inbox  map[string]bool
	stock  map[string]int
}

func NewServiceB(b *SimpleBroker) *ServiceB {
	return &ServiceB{
		broker: b,
		inbox:  make(map[string]bool),
		stock:  map[string]int{"item-1": 100},
	}
}

func (s *ServiceB) ProcessOrders() {
	msgs := s.broker.Receive("orders.created")
	for _, msg := range msgs {
		fmt.Printf("[Service B - Warehouse] Received %s (Correlation: %s)\n", msg.EventID, msg.CorrelationID)

		// Единая транзакция: Inbox + Stock + Outbox
		if s.inbox[msg.EventID] {
			fmt.Println(" -> [Duplicate Ignored] Already processed.")
			continue
		}
		s.inbox[msg.EventID] = true
		s.stock["item-1"] -= 1

		// Исходящее событие в Outbox
		outEvent := ChainMessage{
			EventID:       "evt-stock-res-1",
			CorrelationID: msg.CorrelationID, // Сквозная трассировка сохраняется
			Topic:         "inventory.reserved",
			Payload:       `{"order_id": "ord-99", "status": "RESERVED"}`,
		}
		s.broker.Send(outEvent)
		fmt.Printf(" -> [Service B Committed] Reserved stock and sent outbox event %s\n", outEvent.EventID)
	}
}

// Service C (Delivery Service): Inbox
type ServiceC struct {
	broker *SimpleBroker
	inbox  map[string]bool
}

func NewServiceC(b *SimpleBroker) *ServiceC {
	return &ServiceC{broker: b, inbox: make(map[string]bool)}
}

func (s *ServiceC) ProcessDelivery() {
	msgs := s.broker.Receive("inventory.reserved")
	for _, msg := range msgs {
		fmt.Printf("[Service C - Delivery] Received %s (Correlation: %s)\n", msg.EventID, msg.CorrelationID)
		if s.inbox[msg.EventID] {
			fmt.Println(" -> [Duplicate Ignored] Already scheduled delivery.")
			continue
		}
		s.inbox[msg.EventID] = true
		fmt.Printf(" -> [Service C Committed] Scheduled courier delivery for Correlation: %s\n", msg.CorrelationID)
	}
}

func main() {
	broker := NewSimpleBroker()
	srvA := &ServiceA{broker: broker}
	srvB := NewServiceB(broker)
	srvC := NewServiceC(broker)

	_ = context.Background()
	corrID := "trace-uuid-abcdef-12345"

	fmt.Println("=== 1. Service A triggers Order Creation ===")
	srvA.CreateOrder("ord-99", corrID)

	fmt.Println("\n=== 2. Service B processes Order and emits Stock Reserved ===")
	srvB.ProcessOrders()

	fmt.Println("\n=== 3. Service C processes Stock Reserved and Schedules Delivery ===")
	srvC.ProcessDelivery()

	fmt.Println("\n=== 4. End-to-End Trace Verification ===")
	fmt.Printf("Correlation ID '%s' successfully propagated across all 3 services.\n", corrID)
}
```

ℹ️ Сквозная цепочка микросервисов с сохранением Correlation ID

## Под капотом

Паттерн объединения Inbox и Outbox в промежуточном микросервисе называется 'Listen to Yourself' или 'Saga Step Coordinator'. Атомарный коммит входного Inbox, бизнес-таблицы и выходного Outbox превращает промежуточный сервис в абсолютно надежный автомат состояний без риска рассинхронизации.

## Подводные камни

1. Генерация нового Correlation ID в промежуточном сервисе: это ломает сквозную трассировку в системах мониторинга (Jaeger, OpenTelemetry, ELK).
2. Публикация в брокер до фиксации транзакции Inbox/Outbox: если публикация в `Service C` удалась, а локальный коммит в `Service B` упал, возникнет призрак события (Phantom Event).

## На собеседовании

Вопрос: В чем разница между `event_id`, `correlation_id` и `causation_id` в распределенной цепочке событий?
Ответ:
- `event_id`: уникальный идентификатор конкретного единичного события (UUID).
- `correlation_id`: идентификатор всего сквозного бизнес-процесса от первого HTTP-запроса клиента до конца.
- `causation_id`: идентификатор непосредственного родительского события (`event_id`), реакцией на которое стало текущее событие. Связка этих трех ID позволяет строить точное дерево вызовов распределенного графа.
