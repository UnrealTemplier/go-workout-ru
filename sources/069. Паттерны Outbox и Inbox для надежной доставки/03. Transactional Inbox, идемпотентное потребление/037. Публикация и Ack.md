# Публикация и Ack: строгий порядок подтверждения брокера до обновления Outbox

## Условие

37. **[Публикация и Ack]**: Relay Worker читает записи, отправляет их в Kafka/RabbitMQ. Только *после* успешного ответа от брокера он делает `UPDATE outbox SET processed = true WHERE id = ...`.

### Исходная формулировка

**[Публикация и Ack]**: Relay Worker читает записи, отправляет их в Kafka/RabbitMQ. Только *после* успешного ответа от брокера он делает `UPDATE outbox SET processed = true WHERE id = ...`.

## Теория

Критическое правило паттерна Transactional Outbox гласит: статус события в локальной базе ни в коем случае нельзя помечать как `PROCESSED` до получения подтверждения доставки от брокера сообщений. В Kafka подтверждением является получение синхронного ответа `ProducerRecord` с метаданными partition/offset (при `acks=all`), а в RabbitMQ — получение подтверждения `Publisher Confirm` (`ack`).

Если воркер обновит запись `processed = true` до сетевого вызова, а отправка в брокер завершится ошибкой (network partition, OOM брокера), сообщение навсегда исчезнет из бизнес-процесса (тихая потеря данных). Если же воркер успешно отправил сообщение в Kafka, но упал до выполнения `UPDATE`, сообщение останется `processed = false` и будет отправлено повторно при рестарте. Это формирует базовую гарантию At-Least-Once.

## Решение по шагам

1. Извлеките порцию непомеченных сообщений из таблицы Outbox.
2. Для каждого события вызовите метод отправки `broker.Publish(ctx, event)`.
3. Дождитесь возврата ошибки или подтверждения (Ack) от брокера.
4. Только при `err == nil` выполните `UPDATE outbox SET processed = true, sent_at = NOW() WHERE id = $1`.
5. При ошибке отправки оставьте запись необновленной и увеличьте счетчик попыток `retry_count`.

## Код решения

**`relay_ack.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type OutboxEvent struct {
	ID        string
	Topic     string
	Payload   string
	Processed bool
	SentAt    *time.Time
}

type MessageBroker interface {
	PublishWithAck(ctx context.Context, topic, payload string) (partition int32, offset int64, err error)
}

type MockKafkaProducer struct {
	mu           sync.Mutex
	offsetSeq    int64
	shouldFailOn string
}

func (p *MockKafkaProducer) PublishWithAck(ctx context.Context, topic, payload string) (int32, int64, error) {
	p.mu.Lock()
	defer p.mu.Unlock()

	if payload == p.shouldFailOn {
		return 0, 0, errors.New("kafka: network timeout / leader not available")
	}

	p.offsetSeq++
	return 0, p.offsetSeq, nil
}

type OutboxRelayWorker struct {
	events []*OutboxEvent
	broker MessageBroker
	mu     sync.Mutex
}

func NewOutboxRelayWorker(broker MessageBroker, events []*OutboxEvent) *OutboxRelayWorker {
	return &OutboxRelayWorker{
		events: events,
		broker: broker,
	}
}

func (w *OutboxRelayWorker) ProcessBatch(ctx context.Context) error {
	w.mu.Lock()
	defer w.mu.Unlock()

	for _, event := range w.events {
		if event.Processed {
			continue
		}

		fmt.Printf("[Relay] Sending event %s to topic '%s'...\n", event.ID, event.Topic)
		part, off, err := w.broker.PublishWithAck(ctx, event.Topic, event.Payload)
		if err != nil {
			fmt.Printf(" -> [Broker Error] Failed to publish event %s: %v (Skip DB UPDATE!)\n", event.ID, err)
			// Прерываем или пропускаем без пометки processed = true
			continue
		}

		// Только после подтверждения брокера фиксируем отправку в БД
		now := time.Now().UTC()
		event.Processed = true
		event.SentAt = &now
		fmt.Printf(" -> [Ack Received] Partition %d, Offset %d. DB UPDATE outbox SET processed = true for %s\n",
			part, off, event.ID)
	}

	return nil
}

func main() {
	producer := &MockKafkaProducer{shouldFailOn: "order_corrupted_payload"}

	events := []*OutboxEvent{
		{ID: "evt-101", Topic: "orders", Payload: "order_created_101", Processed: false},
		{ID: "evt-102", Topic: "orders", Payload: "order_corrupted_payload", Processed: false},
		{ID: "evt-103", Topic: "orders", Payload: "order_created_103", Processed: false},
	}

	worker := NewOutboxRelayWorker(producer, events)
	ctx := context.Background()

	fmt.Println("=== Executing Outbox Relay Batch ===")
	_ = worker.ProcessBatch(ctx)

	fmt.Println("\n=== Final Outbox State in DB ===")
	for _, ev := range events {
		fmt.Printf("Event %s: Processed=%t, SentAt=%v\n", ev.ID, ev.Processed, ev.SentAt != nil)
	}
}
```

ℹ️ Пометка processed=true выполняется строго после получения partition/offset от брокера

 -> [Ack Received] Partition 0, Offset 1. DB UPDATE outbox SET processed = true for evt-101

## Под капотом

Сетевой цикл ожидания подтверждения брокера называется round-trip time (RTT). Если отправлять события строго по одному синхронно, пропускная способность воркера упирается в сетевой RTT. В высоконагруженных системах воркер отправляет пачку асинхронно с `ProduceAsync` и накапливает канал с результатами `deliveryChan`. Когда все Ack для пачки получены, выполняется массовый `UPDATE outbox SET processed=true WHERE id = ANY($1)`.

## Подводные камни

1. Пометка `processed = true` до вызова `Publish`: при падении сети бизнес-событие теряется навсегда.
2. Игнорирование ошибки ответа брокера: если метод вернул ошибку, но воркер поймал панику или забыл проверить `err`, запись может быть ошибочно помечена как отправленная.

## На собеседовании

Вопрос: Что произойдет, если брокер принял сообщение и записал в реплики, но при отправке Ack клиенту сетевой пакет потерялся?
Ответ: Relay Worker получит таймаут или ошибку EOF и не обновит запись в Outbox. При следующем цикле он отправит это же сообщение повторно. Это фундаментальная природа семантики At-Least-Once в распределенных сетях, которая требует обязательной дедупликации (Transactional Inbox) на стороне консьюмера.
