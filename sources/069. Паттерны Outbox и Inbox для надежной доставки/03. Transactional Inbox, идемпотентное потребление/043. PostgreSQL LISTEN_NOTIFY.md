# PostgreSQL LISTEN/NOTIFY: реактивная Push-модель ретранслятора Outbox

## Условие

43. **Listen/Notify (Push модель)**: Поллинг каждую секунду грузит базу. Улучши воркер. Используй PostgreSQL `LISTEN outbox_channel`. В триггере таблицы `outbox_events` после инсерта делай `NOTIFY outbox_channel`. Твоя горутина проснется мгновенно и отправит событие в брокер без холостых поллингов!

### Исходная формулировка

**Listen/Notify (Push модель)**: Поллинг каждую секунду грузит базу. Улучши воркер. Используй PostgreSQL `LISTEN outbox_channel`. В триггере таблицы `outbox_events` после инсерта делай `NOTIFY outbox_channel`. Твоя горутина проснется мгновенно и отправит событие в брокер без холостых поллингов!

## Теория

Поллинг по таймеру (`time.Sleep(1 * time.Second)`) имеет фундаментальный компромисс между задержкой (Latency) и нагрузкой на СУБД (CPU, Disk I/O, лог транзакций):
- При частом опросе (10 мс) база данных 99% времени выполняет пустые `SELECT` запросы.
- При редком опросе (1–5 сек) возрастает задержка доставки событий бизнес-системы.

PostgreSQL предоставляет встроенный pub/sub механизм межпроцессного взаимодействия `LISTEN/NOTIFY`:
1. На таблицу `outbox_events` вешается триггер `AFTER INSERT FOR EACH ROW EXECUTE FUNCTION notify_outbox()`.
2. В триггере вызывается `PERFORM pg_notify('outbox_channel', NEW.id::text)`.
3. Go-воркер удерживает отдельное постоянное соединение через драйвер `github.com/jackc/pgx/v5` и слушает `conn.WaitForNotification()`.
4. Воркер просыпается мгновенно (задержка < 1 мс) только при наличии реальных данных.

## Решение по шагам

1. Спроектируйте SQL-триггер и функцию вызова `pg_notify`.
2. Реализуйте канал уведомлений в Go (`chan string`).
3. В горутине слушайте уведомления через `select` между `notificationChan` и фоновым таймером безопасности (Fallback Ticker).
4. При получении сигнала обработайте событие без задержки.

## Код решения

**`listen_notify_relay.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// SQL триггер для демонстрации:
// CREATE OR REPLACE FUNCTION notify_outbox_event() RETURNS TRIGGER AS $$
// BEGIN
//     PERFORM pg_notify('outbox_channel', NEW.id::text);
//     RETURN NEW;
// END;
// $$ LANGUAGE plpgsql;
// CREATE TRIGGER trg_outbox_notify AFTER INSERT ON outbox_events
// FOR EACH ROW EXECUTE FUNCTION notify_outbox_event();

type NotificationChannel struct {
	ch chan string
	mu sync.Mutex
}

func NewNotificationChannel() *NotificationChannel {
	return &NotificationChannel{
		ch: make(chan string, 100),
	}
}

func (n *NotificationChannel) Notify(eventID string) {
	n.ch <- eventID
}

func (n *NotificationChannel) Listen() <-chan string {
	return n.ch
}

type PushRelayWorker struct {
	notifyChan *NotificationChannel
}

func NewPushRelayWorker(nc *NotificationChannel) *PushRelayWorker {
	return &PushRelayWorker{notifyChan: nc}
}

func (w *PushRelayWorker) Run(ctx context.Context) {
	fmt.Println("[Worker] Subscribed to PostgreSQL channel 'outbox_channel'. Waiting for Push events...")

	// Резервный таймер безопасности на случай потери нотификации при сбое сети
	fallbackTicker := time.NewTicker(5 * time.Second)
	defer fallbackTicker.Stop()

	for {
		select {
		case <-ctx.Done():
			fmt.Println("[Worker] Shutting down reactive relay.")
			return

		case eventID := <-w.notifyChan.Listen():
			start := time.Now()
			fmt.Printf("[Worker NOTIFY WAKEUP] Received push notification for event %s! Immediate dispatch.\n", eventID)
			// Имитация быстрой выборки и отправки
			time.Sleep(2 * time.Millisecond)
			fmt.Printf(" -> Event %s sent to Kafka in %v (Zero idle polling latency!)\n", eventID, time.Since(start))

		case <-fallbackTicker.C:
			fmt.Println("[Worker Fallback Poll] Safe periodic check for orphaned records...")
		}
	}
}

func main() {
	notifyChan := NewNotificationChannel()
	worker := NewPushRelayWorker(notifyChan)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	go worker.Run(ctx)

	time.Sleep(50 * time.Millisecond)

	fmt.Println("\n=== Business Service inserts new order into DB with trigger NOTIFY ===")
	notifyChan.Notify("evt-push-1001")

	time.Sleep(50 * time.Millisecond)

	fmt.Println("\n=== Business Service inserts second order ===")
	notifyChan.Notify("evt-push-1002")

	time.Sleep(100 * time.Millisecond)
	cancel()
	time.Sleep(20 * time.Millisecond)
}
```

ℹ️ Push-модель обеспечивает суб-миллисекундную реакцию без холостой нагрузки на СУБД

## Под капотом

Команда `pg_notify` передается через сигнальный протокол PostgreSQL бэкенда на сокет клиента. Уведомление отправляется только тогда, когда транзакция с `INSERT` успешно зафиксирована (`COMMIT`). Если транзакция откатилась (`ROLLBACK`), уведомление клиенту не отправляется, что предотвращает чтение 'грязных' данных.

## Подводные камни

1. Потеря уведомлений при разрыве TCP соединения: очередь `NOTIFY` в PostgreSQL хранится в памяти и не персистентна. Если воркер перезапускался в момент отправки, он потеряет сигнал. Поэтому гибридный воркер обязан совмещать `LISTEN` с редким fallback-поллингом (например, раз в минуту).
2. Ограничение размера payload: в `pg_notify` размер строки сообщения ограничен 8000 байтами. В нотификацию передается только ID события, а не весь JSON payload.

## На собеседовании

Вопрос: Почему LISTEN/NOTIFY не заменяет полноценный CDC (Debezium/WAL) в HighLoad системах?
Ответ: При тысячах транзакций в секунду буфер `LISTEN/NOTIFY` в PostgreSQL может переполниться, вызывая ошибку `queue full`. Кроме того, `LISTEN` требует выделенного постоянного соединения на каждый поток, что не дружит с PgBouncer в режиме Transaction Pooling. Поэтому для HighLoad используется чтение WAL (CDC).
