# Transactional Inbox: идемпотентный приём сообщений с атомарной транзакцией БД

## Условие

40. **Transactional Inbox: идемпотентный приём сообщений.**: Сервис-подписчик получает сообщение из брокера, проверяет наличие `message_id` в таблице `inbox`. Если сообщение уже обработано — игнорирует. Если нет — вставляет запись в `inbox` и выполняет бизнес-логику в одной транзакции БД.

### Исходная формулировка

**Transactional Inbox: идемпотентный приём сообщений.**: Сервис-подписчик получает сообщение из брокера, проверяет наличие `message_id` в таблице `inbox`. Если сообщение уже обработано — игнорирует. Если нет — вставляет запись в `inbox` и выполняет бизнес-логику в одной транзакции БД.

## Теория

Паттерн Transactional Inbox является парным зеркальным отражением Transactional Outbox. Он гарантирует, что даже при получении нескольких идентичных копий сообщения брокера (At-Least-Once), бизнес-состояние потребителя будет изменено строго один раз (Effectively Exactly-Once).

Алгоритм работы консьюмера в одной транзакции:
```sql
BEGIN;
-- Шаг 1: попытка вставить ID события в таблицу inbox
INSERT INTO inbox (message_id, created_at) VALUES ($1, NOW());
-- Шаг 2: если возник конфликт уникальности (duplicate) -> ROLLBACK и ACK брокеру
-- Шаг 3: если вставка успешна -> выполнение бизнес-логики
UPDATE accounts SET balance = balance + $2 WHERE id = $3;
COMMIT;
```
Если база данных упадет посреди транзакции, откатятся и бизнес-изменения, и запись в Inbox.

## Решение по шагам

1. Откройте транзакцию `tx, err := db.BeginTx(ctx, nil)`.
2. Выполните вставку `INSERT INTO inbox (message_id) VALUES (?)`.
3. Обработайте ошибку: если это `ErrDuplicateKey`, выполните `tx.Rollback()` и верните nil (сообщение заакано).
4. Выполните обновление бизнес-таблиц (`UPDATE ...`).
5. Выполните `tx.Commit()` и подтвердите смещение консьюмера в Kafka (`Ack`).

## Код решения

**`transactional_inbox.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

var ErrDuplicateMessage = errors.New("inbox: duplicate message")

type MockTx struct {
	inboxRef   map[string]time.Time
	balanceRef map[string]int
	pendingMsg string
	pendingBal map[string]int
	committed  bool
	rolledBack bool
}

func (tx *MockTx) InsertInbox(msgID string) error {
	if _, exists := tx.inboxRef[msgID]; exists {
		return ErrDuplicateMessage
	}
	tx.pendingMsg = msgID
	return nil
}

func (tx *MockTx) AddBalance(accountID string, delta int) {
	tx.pendingBal[accountID] += delta
}

func (tx *MockTx) Commit() error {
	if tx.rolledBack {
		return errors.New("tx: already rolled back")
	}
	if tx.pendingMsg != "" {
		tx.inboxRef[tx.pendingMsg] = time.Now().UTC()
	}
	for acc, delta := range tx.pendingBal {
		tx.balanceRef[acc] += delta
	}
	tx.committed = true
	return nil
}

func (tx *MockTx) Rollback() {
	tx.rolledBack = true
}

type BankingDatabase struct {
	mu       sync.Mutex
	inbox    map[string]time.Time
	balances map[string]int
}

func NewBankingDatabase() *BankingDatabase {
	return &BankingDatabase{
		inbox:    make(map[string]time.Time),
		balances: make(map[string]int),
	}
}

func (db *BankingDatabase) Begin() *MockTx {
	db.mu.Lock()
	return &MockTx{
		inboxRef:   db.inbox,
		balanceRef: db.balances,
		pendingBal: make(map[string]int),
	}
}

func (db *BankingDatabase) EndTx(tx *MockTx) {
	db.mu.Unlock()
}

type Consumer struct {
	db *BankingDatabase
}

func (c *Consumer) ProcessPaymentEvent(ctx context.Context, msgID, accountID string, amount int) error {
	tx := c.db.Begin()
	defer c.db.EndTx(tx)

	// Шаг 1: Атомарная попытка занять слот в Inbox
	err := tx.InsertInbox(msgID)
	if err != nil {
		if errors.Is(err, ErrDuplicateMessage) {
			tx.Rollback()
			fmt.Printf("[Consumer] Message %s is a DUPLICATE! Rolled back transaction. Ack broker.\n", msgID)
			return nil // Возвращаем nil, чтобы консьюмер заакал дубликат
		}
		tx.Rollback()
		return fmt.Errorf("failed to check inbox: %w", err)
	}

	// Шаг 2: Выполнение бизнес-логики в рамках той же транзакции
	tx.AddBalance(accountID, amount)

	// Шаг 3: Коммит всей связки
	if err := tx.Commit(); err != nil {
		return fmt.Errorf("commit failed: %w", err)
	}

	fmt.Printf("[Consumer] Successfully processed msg %s: Account %s credited with +%d\n",
		msgID, accountID, amount)
	return nil
}

func main() {
	db := NewBankingDatabase()
	db.balances["acc-444"] = 1000
	consumer := &Consumer{db: db}
	ctx := context.Background()

	msgID := "kafka-evt-uuid-777"
	accountID := "acc-444"
	amount := 500

	fmt.Println("=== 1. First Delivery of Payment Event ===")
	_ = consumer.ProcessPaymentEvent(ctx, msgID, accountID, amount)
	fmt.Printf("Balance after step 1: %d\n\n", db.balances[accountID])

	fmt.Println("=== 2. Duplicate Delivery of Exact Same Event (Network Retry) ===")
	_ = consumer.ProcessPaymentEvent(ctx, msgID, accountID, amount)
	fmt.Printf("Balance after step 2 (MUST NOT CHANGE): %d\n", db.balances[accountID])
}
```

ℹ️ Бизнес-логика и запись в Inbox выполняются в единой транзакции БД

## Под капотом

Связка `INSERT INTO inbox` и `UPDATE balance` в рамках одной локальной транзакции опирается на WAL и MVCC. Если вставка в Inbox падает по `unique_violation`, транзакция переводится в состояние ошибки (aborted) и ни одно изменение баланса не станет видимым для других транзакций (изоляция Read Committed).

## Подводные камни

1. Отправка Ack до фиксации транзакции БД: если консьюмер заакает брокер, а `tx.Commit()` упадет, сообщение будет потеряно.
2. Вызов внешних сетевых API внутри транзакции `tx`: если внутри вызывать внешний эквайринг, соединение с БД будет заблокировано на секунды, исчерпывая пул `MaxOpenConns`.

## На собеседовании

Вопрос: Почему нельзя сначала сделать `SELECT processed FROM inbox WHERE id = ?`, а затем `INSERT`?
Ответ: Из-за состояния гонки (Race Condition). Если два пода консьюмера получат копии сообщения одновременно, оба выполнят `SELECT` и увидят, что записи нет, после чего оба выполнят бизнес-логику. Только ограничение уникальности (`UNIQUE constraint`) на уровне СУБД спасет от двойного списания.
