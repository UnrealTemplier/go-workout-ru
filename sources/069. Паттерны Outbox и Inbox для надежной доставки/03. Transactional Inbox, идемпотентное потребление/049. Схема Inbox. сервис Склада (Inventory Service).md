# Схема Inbox: сервис Склада (Inventory Service) с DDL таблицей inbox_events

## Условие

49. **Схема Inbox**: Переходим в сервис Склада (Inventory Service), который слушает Kafka. Создай таблицу `inbox_events (event_id UUID PRIMARY KEY, processed_at TIMESTAMP)`.

### Исходная формулировка

**Схема Inbox**: Переходим в сервис Склада (Inventory Service), который слушает Kafka. Создай таблицу `inbox_events (event_id UUID PRIMARY KEY, processed_at TIMESTAMP)`.

## Теория

Для сервиса Склада (Inventory Service) надежность списания товарных остатков критична: повторная обработка события `OrderPaid` приведет к двойному резервированию товара на складе, что вызовет искусственный дефицит (Out of Stock). DDL-схема таблицы дедупликации:
```sql
CREATE TABLE inbox_events (
    event_id UUID PRIMARY KEY,
    event_type VARCHAR(64) NOT NULL,
    processed_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_inbox_processed_at ON inbox_events (processed_at);
```
Индекс по `processed_at` необходим для эффективной работы ночного сборщика мусора (Pruning Daemon).

## Решение по шагам

1. Напишите DDL скрипт создания `inbox_events` и структуру `InboxEvent` в Go.
2. Реализуйте метод склада `ReserveInventory(ctx, eventID, itemID, count)`.
3. В рамках одной транзакции вставьте запись в `inbox_events` и выполните `UPDATE items SET stock = stock - count`.
4. Продемонстрируйте защиту от двойного списания товара.

## Код решения

**`inventory_inbox.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type InboxEvent struct {
	EventID     string
	EventType   string
	ProcessedAt time.Time
}

type InventoryStore struct {
	mu     sync.Mutex
	inbox  map[string]InboxEvent
	stocks map[string]int
}

func NewInventoryStore() *InventoryStore {
	return &InventoryStore{
		inbox: make(map[string]InboxEvent),
		stocks: map[string]int{
			"item-gpu-4090": 10,
		},
	}
}

func (s *InventoryStore) ReserveInventory(ctx context.Context, eventID, itemID string, qty int) (bool, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверка первичного ключа event_id в таблице inbox_events
	if _, exists := s.inbox[eventID]; exists {
		// Дубликат обнаружен
		return false, nil
	}

	// 2. Проверка остатка на складе
	currentStock := s.stocks[itemID]
	if currentStock < qty {
		return false, fmt.Errorf("insufficient stock for item %s: available %d, requested %d", itemID, currentStock, qty)
	}

	// 3. Атомарное обновление остатка и фиксация в inbox_events
	s.stocks[itemID] = currentStock - qty
	s.inbox[eventID] = InboxEvent{
		EventID:     eventID,
		EventType:   "OrderPaidEvent",
		ProcessedAt: time.Now().UTC(),
	}

	return true, nil
}

func main() {
	store := NewInventoryStore()
	ctx := context.Background()

	eventID := "uuid-evt-payment-4090"
	itemID := "item-gpu-4090"

	fmt.Printf("Initial Warehouse Stock for %s: %d\n\n", itemID, store.stocks[itemID])

	fmt.Println("=== 1. Kafka delivers OrderPaidEvent (Reserve 2 GPUs) ===")
	reserved, err := store.ReserveInventory(ctx, eventID, itemID, 2)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Reservation result: %t. Remaining stock: %d\n\n", reserved, store.stocks[itemID])

	fmt.Println("=== 2. Kafka re-delivers EXACT SAME OrderPaidEvent (Network glitch) ===")
	reserved, err = store.ReserveInventory(ctx, eventID, itemID, 2)
	if err != nil {
		panic(err)
	}
	if !reserved {
		fmt.Printf("Reservation result: %t -> DUPLICATE EVENT FILTERED BY INBOX! Stock is NOT deducted.\n", reserved)
	}
	fmt.Printf("Final Warehouse Stock for %s: %d\n", itemID, store.stocks[itemID])
}
```

ℹ️ Таблица inbox_events сервиса Склада гарантирует, что товар спишется строго один раз

**`output.txt`**

```bash

=== 1. Kafka delivers OrderPaidEvent (Reserve 2 GPUs) ===
Reservation result: true. Remaining stock: 8

=== 2. Kafka re-delivers EXACT SAME OrderPaidEvent (Network glitch) ===
Reservation result: false -> DUPLICATE EVENT FILTERED BY INBOX! Stock is NOT deducted.
Final Warehouse Stock for item-gpu-4090: 8
```

ℹ️ Остаток склада остался равен 8, повторный запрос успешно отфильтрован

## Под капотом

Использование типа `UUID` для первичного ключа в PostgreSQL занимает 16 байт по сравнению с текстовым `VARCHAR(36)`. Это уменьшает размер таблицы и индекса более чем в 2 раза, увеличивая плотность страниц буферного пула СУБД.

## Подводные камни

1. Генерация случайных UUID v4: приводит к фрагментации страниц B-Tree индекса при высокой нагрузке. В современных высоконагруженных сервисах рекомендуется использовать `UUIDv7`, сортируемый по времени.
2. Отсутствие индекса по `processed_at`: при выполнении `DELETE ... WHERE processed_at < $1` СУБД будет выполнять тяжелый `Seq Scan` (полное сканирование таблицы).

## На собеседовании

Вопрос: Почему UUIDv7 предпочтительнее UUIDv4 в качестве первичного ключа таблиц Inbox и Outbox?
Ответ: UUIDv7 содержит 48-битный timestamp в старших байтах. При вставке новые строки всегда дописываются в конец B-Tree индекса (sequential append). Это предотвращает деградацию производительности, расщепление страниц (page splits) и фрагментацию памяти, характерные для случайных UUIDv4.
