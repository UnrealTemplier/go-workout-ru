# Outbox + Inbox сквозная демонстрация: эффективная семантика Exactly-Once

## Условие

53. **Outbox + Inbox сквозная демонстрация.**: Реализуйте сценарий: Сервис A записывает событие в Outbox, ретранслятор отправляет в Kafka, Сервис B получает через Inbox, обеспечивая ровно-однократную (effective exactly-once) обработку.

### Исходная формулировка

**Outbox + Inbox сквозная демонстрация.**: Реализуйте сценарий: Сервис A записывает событие в Outbox, ретранслятор отправляет в Kafka, Сервис B получает через Inbox, обеспечивая ровно-однократную (effective exactly-once) обработку.

## Теория

В распределенных системах чистого Exactly-Once на физическом сетевом уровне не существует. Однако связка двух паттернов: **Transactional Outbox на стороне Producer** + **Transactional Inbox на стороне Consumer** порождает архитектурное свойство, называемое **Эффективной Однократностью (Effectively Exactly-Once Processing)**.

Цепочка взаимодействия:
1. Сервис A атомарно сохраняет заказ и событие в Outbox (защита от Dual Write).
2. Relay отправляет событие в Kafka с повторами при сбоях (At-Least-Once транспорт).
3. Kafka может содержать дубликаты из-за падений сети или ребалансировки консьюмеров.
4. Сервис B встречает дубликаты таблицей Inbox и отсекает их в рамках транзакции БД.
Результат: состояние всей распределенной системы меняется так, будто каждое сообщение передавалось ровно один раз.

## Решение по шагам

1. Реализуйте сервис OrderService (Producer) с таблицей Outbox.
2. Реализуйте Relay Worker с повторами.
3. Смоделируйте ненадежный брокер Kafka, намеренно дублирующий сообщения.
4. Реализуйте сервис PaymentService (Consumer) с таблицей Inbox.
5. Продемонстрируйте полное прохождение сценария со сбоями и проверку итогового состояния.

## Код решения

**`e2e_outbox_inbox.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type EventEnvelope struct {
	ID        string
	Topic     string
	Payload   string
	Timestamp int64
}

// 1. Брокер с симуляцией сбоев и дубликатов
type UnreliableKafka struct {
	mu       sync.Mutex
	messages []EventEnvelope
}

func (k *UnreliableKafka) SendWithDuplicates(env EventEnvelope, duplicateTimes int) {
	k.mu.Lock()
	defer k.mu.Unlock()
	for i := 0; i < duplicateTimes; i++ {
		k.messages = append(k.messages, env)
	}
}

// 2. Сервис A: Outbox Producer
type ServiceA struct {
	outbox []EventEnvelope
}

func (a *ServiceA) CreateOrder(orderID string) EventEnvelope {
	event := EventEnvelope{
		ID:      "evt-order-created-999",
		Topic:   "orders",
		Payload: fmt.Sprintf(`{"order_id": "%s", "status": "CREATED"}`, orderID),
	}
	a.outbox = append(a.outbox, event)
	fmt.Printf("[Service A - Orders] Order %s saved to DB and Outbox (Event: %s)\n", orderID, event.ID)
	return event
}

// 3. Сервис B: Inbox Consumer
type ServiceB struct {
	inbox       map[string]bool
	ordersSeen  map[string]int // Сколько раз обработан заказ
	totalExecs  int
}

func NewServiceB() *ServiceB {
	return &ServiceB{
		inbox:      make(map[string]bool),
		ordersSeen: make(map[string]int),
	}
}

func (b *ServiceB) HandleKafkaMessage(env EventEnvelope) {
	// Атомарная проверка Inbox
	if b.inbox[env.ID] {
		fmt.Printf("[Service B - Billing] DUPLICATE DETECTED for Event %s! Filtered by Inbox. ACK broker.\n", env.ID)
		return
	}

	// Фиксация в Inbox + Бизнес-логика
	b.inbox[env.ID] = true
	b.ordersSeen[env.Payload]++
	b.totalExecs++
	fmt.Printf("[Service B - Billing] Fresh Event %s processed! Executed business logic for %s\n",
		env.ID, env.Payload)
}

func main() {
	broker := &UnreliableKafka{}
	serviceA := &ServiceA{}
	serviceB := NewServiceB()
	_ = context.Background()

	fmt.Println("=== Phase 1: Service A saves Order and publishes via Outbox ===")
	event := serviceA.CreateOrder("ord-777")

	fmt.Println("\n=== Phase 2: Network Glitch! Broker receives and duplicates event 3 times ===")
	broker.SendWithDuplicates(event, 3)
	fmt.Printf("Broker contains %d messages for event %s\n", len(broker.messages), event.ID)

	fmt.Println("\n=== Phase 3: Service B consumes messages from Kafka ===")
	for i, msg := range broker.messages {
		fmt.Printf("\n--- Processing message delivery #%d ---\n", i+1)
		serviceB.HandleKafkaMessage(msg)
	}

	fmt.Println("\n=== Phase 4: Final E2E Verification ===")
	fmt.Printf("Total Deliveries from Broker: %d\n", len(broker.messages))
	fmt.Printf("Total Business Executions in Service B: %d\n", serviceB.totalExecs)
	fmt.Printf("Effective Semantics Achieved: EXACTLY-ONCE!\n")
}
```

ℹ️ Сквозная демонстрация связки Outbox + Inbox с фильтрацией тройной доставки

## Под капотом

Данная архитектура реализует математический принцип идемпотентного моноида: \(f(f(x)) = f(x)\). Сколько бы раз функция обработки не вызывалась с одним и тем же аргументом, результирующее состояние базы данных остается эквивалентным однократному вызову.

## Подводные камни

1. Надежда на то, что Kafka сама обеспечит Exactly-Once без Inbox: как только консьюмер пишет в стороннюю БД, гарантии Kafka EOS заканчиваются.
2. Использование разных ID: если продюсер на каждый ретрай генерирует новый `event_id`, Inbox консьюмера посчитает их разными событиями. `event_id` должен быть детерминированным.

## На собеседовании

Вопрос: Возможно ли построить отказоустойчивую микросервисную систему без двухфазного коммита (2PC)?
Ответ: Да, именно связка паттернов Transactional Outbox + At-Least-Once Broker + Transactional Inbox является мировым стандартом построения event-driven систем без тяжелых и блокирующих 2PC (XA) транзакций.
