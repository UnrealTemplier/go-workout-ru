## Теория

Промышленная таблица `outbox` должна быть полностью самодостаточной для любого брокера сообщений. SQL-схема миграции:
```sql
CREATE TABLE outbox (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type VARCHAR(64) NOT NULL,
    aggregate_id VARCHAR(128) NOT NULL,
    partition_key VARCHAR(128) NOT NULL,
    event_type VARCHAR(128) NOT NULL,
    payload JSONB NOT NULL,
    headers JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    sent_at TIMESTAMPTZ NULL,
    error_count INT NOT NULL DEFAULT 0
);
CREATE INDEX idx_outbox_unprocessed ON outbox (created_at ASC) WHERE sent_at IS NULL;
```
**Зачем `partition_key` отдельно от `aggregate_id`?**
В 90% случаев они совпадают (например, `order_id`). Однако при высокой кардинальности или связанных сущностях требуется группировка: например, для сущности `OrderItem` (где `aggregate_id = item_id`) в качестве `partition_key` должен выступать `order_id` или `customer_id`, чтобы все позиции одного заказа гарантированно попали в одну и ту же партицию Kafka в строгом хронологическом порядке.

## Код решения

**`outbox_schema.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

type OutboxEntry struct {
	ID           string            `json:"id"`
	AggregateType string           `json:"aggregate_type"`
	AggregateID  string            `json:"aggregate_id"`
	PartitionKey string            `json:"partition_key"`
	EventType    string            `json:"event_type"`
	Payload      json.RawMessage   `json:"payload"`
	Headers      map[string]string `json:"headers"`
	CreatedAt    time.Time         `json:"created_at"`
	SentAt       *time.Time        `json:"sent_at,omitempty"`
	ErrorCount   int               `json:"error_count"`
}

func NewOrderItemEvent(orderID, itemID, eventType string, payloadObj interface{}, traceID string) (*OutboxEntry, error) {
	rawPayload, err := json.Marshal(payloadObj)
	if err != nil {
		return nil, err
	}

	return &OutboxEntry{
		ID:            "uuid-v7-generated-001",
		AggregateType: "order_item",
		AggregateID:   itemID,  // Уникальный ID позиции заказа
		PartitionKey:  orderID, // Партиционируем по родительскому OrderID!
		EventType:     eventType,
		Payload:       rawPayload,
		Headers: map[string]string{
			"traceparent":    traceID,
			"content-type":   "application/json",
			"x-service-name": "order-service",
		},
		CreatedAt:  time.Now().UTC(),
		SentAt:     nil,
		ErrorCount: 0,
	}, nil
}

func main() {
	payload := map[string]interface{}{
		"item_id": "item-ram-32gb",
		"price":   12000,
		"qty":     2,
	}

	entry, err := NewOrderItemEvent("order-xyz-777", "item-ram-32gb", "OrderItemAdded", payload, "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01")
	if err != nil {
		panic(err)
	}

	marshaled, _ := json.MarshalIndent(entry, "", "  ")
	fmt.Println("=== Generated Outbox Entry for Database Insert ===")
	fmt.Println(string(marshaled))

	fmt.Println("\n=== Partition Key Routing Check ===")
	fmt.Printf("Aggregate ID: %s (Entity Identifier)\n", entry.AggregateID)
	fmt.Printf("Partition Key: %s (Kafka Target Partition)\n", entry.PartitionKey)
	fmt.Printf("Conclusion: All items of order '%s' will land in the exact same Kafka partition.\n", entry.PartitionKey)
}
```

ℹ️ Разделение Aggregate ID и Partition Key обеспечивает строгий порядок связанных сущностей

## Под капотом

Индекс с предикатом `WHERE sent_at IS NULL` называется Partial Index (частичный индекс). Он индексирует только неотправленные строки. Поскольку 99.9% записей в Outbox уже отправлены (`sent_at IS NOT NULL`), размер такого индекса в оперативной памяти составляет несколько килобайт даже при миллионах записей в таблице.

## Подводные камни

1. Хранение `payload` в виде `TEXT` вместо `JSONB`: невозможно использовать валидацию схемы и частичные обновления в БД.
2. Отсутствие поля `headers`: при интеграции с брокером теряются метаданные OpenTelemetry, tenant ID и токены безопасности.

## На собеседовании

Вопрос: Почему частичный индекс `WHERE sent_at IS NULL` лучше, чем булево поле `WHERE processed = false`?
Ответ: Поле `sent_at TIMESTAMPTZ` решает сразу две задачи: служит индикатором факта отправки (NULL / NOT NULL) и фиксирует точный физический момент отправки для аудита и расчета метрик задержки доставки (Relay Latency SLA).
