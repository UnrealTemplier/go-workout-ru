# Transactional Outbox — фундаментальный закон: категорический запрет Dual Write в распределенных системах

## Условие

72. **Transactional Outbox — это must have.**: Никогда не делайте dual write (БД + Kafka) без Outbox. Это guaranteed source of inconsistency.

### Исходная формулировка

**Transactional Outbox — это must have.**: Никогда не делайте dual write (БД + Kafka) без Outbox. Это guaranteed source of inconsistency.

## Теория

Главный инженерный вывод всей главы: **Паттерн Dual Write (одновременная запись в БД и брокер) — это архитектурная ошибка!**

Код вида:
```go
func CreateOrder(order Order) error {
    err := db.Insert(order)
    if err != nil { return err }
    return kafka.Publish('orders', order)
}
```
обречен на рассинхронизацию данных. В распределенной среде обязательно произойдет один из сценариев:
1. БД закоммитила заказ, но Kafka вернула таймаут -> заказ создан, но склад никогда не получит событие (тихая потеря данных).
2. Вы попытались сначала отправить в Kafka, а затем в БД -> Kafka приняла сообщение, но БД упала с ошибкой -> склад зарезервировал товар под несуществующий заказ (фантомное событие).

**Единственное надежное решение — Transactional Outbox:**
Запись бизнес-сущности и запись события производятся **строго в одной локальной транзакции ACID**. Это фундаментальный стандарт надежности современной бэкенд-разработки.

## Решение по шагам

1. Напишите код-демонстрацию неизбежного краха наивного Dual Write.
2. Напишите эталонную промышленную реализацию с Transactional Outbox.
3. Сравните поведение обеих систем при возникновении сетевого сбоя.
4. Сформулируйте архитектурный манифест надежности сообщений.

## Код решения

**`dual_write_vs_outbox.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

// === АНТИПАТТЕРН: НАИВНЫЙ DUAL WRITE ===
type NaiveDualWriteService struct {
	mu     sync.Mutex
	db     map[string]string
	broker []string
}

func (s *NaiveDualWriteService) CreateOrder(id string, simulateKafkaCrash bool) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Шаг 1: Запись в БД (Успешно)
	s.db[id] = "CREATED"
	fmt.Printf("[Naive Dual Write] Order %s saved to DB!\n", id)

	// Шаг 2: Запись в Kafka (Сбой сети)
	if simulateKafkaCrash {
		fmt.Printf(" -> [FATAL ERROR] Kafka network timeout! Message lost!\n")
		return errors.New("kafka unavailable")
	}

	s.broker = append(s.broker, id)
	return nil
}

// === ЭТАЛОН: TRANSACTIONAL OUTBOX ===
type OutboxService struct {
	mu     sync.Mutex
	db     map[string]string
	outbox []string
	broker []string
}

func (s *OutboxService) CreateOrderTx(id string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Единая ACID транзакция базы данных
	s.db[id] = "CREATED"
	s.outbox = append(s.outbox, id)
	fmt.Printf("[Transactional Outbox] Order %s + Event saved in ONE DB Transaction! (100%% Consistency)\n", id)
	return nil
}

func (s *OutboxService) RelayWorkerFlush(simulateKafkaCrash bool) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if len(s.outbox) == 0 {
		return
	}

	if simulateKafkaCrash {
		fmt.Printf(" -> [Relay Retry] Kafka down! Outbox events remain safely in DB. No data lost!\n")
		return
	}

	for _, item := range s.outbox {
		s.broker = append(s.broker, item)
		fmt.Printf(" -> [Relay Success] Delivered %s to Kafka! Marked outbox as sent.\n", item)
	}
	s.outbox = nil
}

func main() {
	_ = context.Background()

	fmt.Println("=== SCENARIO 1: The Failure of Naive Dual Write ===")
	naive := &NaiveDualWriteService{db: make(map[string]string)}
	_ = naive.CreateOrder("ord-bad-001", true)
	fmt.Printf("State Inconsistency: Order in DB: %s, Message in Kafka: %v (SILENT DATA LOSS!)\n\n",
		naive.db["ord-bad-001"], naive.broker)

	fmt.Println("=== SCENARIO 2: The Reliability of Transactional Outbox ===")
	outbox := &OutboxService{db: make(map[string]string)}
	_ = outbox.CreateOrderTx("ord-good-002")

	fmt.Println("\n--- Relay Attempt 1 (Kafka network partition) ---")
	outbox.RelayWorkerFlush(true)
	fmt.Printf("Events safely preserved in Outbox: %d\n", len(outbox.outbox))

	fmt.Println("\n--- Relay Attempt 2 (Kafka restored) ---")
	outbox.RelayWorkerFlush(false)
	fmt.Printf("Final Verification: Order in DB: %s, Message in Kafka: %v (ZERO LOSS!)\n",
		outbox.db["ord-good-002"], outbox.broker)
}
```

ℹ️ Сравнение доказывает, что Dual Write гарантирует рассинхронизацию, а Outbox обеспечивает надежность

## Под капотом

Паттерн Transactional Outbox опирается на аксиому распределенных систем: две независимые распределенные системы с раздельными транзакционными механизмами не могут быть согласованы без промежуточного персистентного журнала изменений. Этим журналом выступает таблица `outbox` в локальной СУБД.

## Подводные камни

1. Доверие наивному коду Dual Write: в разработке он работает, а в продакшене приводит к расхождениям на миллионы рублей.
2. Попытка откатить базу после сбоя брокера: `if err := kafka.Send(); err != nil { db.Delete(order) }` — если сервер упадет перед `db.Delete`, заказ навсегда останется 'потерянным'.

## На собеседовании

Вопрос: Что вы ответите на собеседовании на вопрос: 'Как в вашем сервисе отправляются события в Kafka при создании заказа?'
Ответ: 'Мы категорически не используем Dual Write. В рамках единой локальной ACID-транзакции мы сохраняем заказ и формируем событие в таблице Transactional Outbox. Ретранслятор (Debezium CDC или фоновый воркер) асинхронно вычитывает события и передает их в Kafka с гарантией At-Least-Once. На стороне консьюмеров мы используем Transactional Inbox для дедупликации, что в совокупности обеспечивает сквозную семантику Effectively Exactly-Once'.
