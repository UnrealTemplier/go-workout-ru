# Relay с Exponential Backoff и Dead Letter Queue (DLQ): изоляция сбойных событий

## Условие

55. **Relay с Backoff и DLQ.**: Если Kafka недоступен, relay должен использовать exponential backoff для failed записей, не блокируя другие events. При `error_count > 10` — перемещать в `outbox_dlq`. Реализуйте отдельный обработчик DLQ с алертом.

### Исходная формулировка

**Relay с Backoff и DLQ.**: Если Kafka недоступен, relay должен использовать exponential backoff для failed записей, не блокируя другие events. При `error_count > 10` — перемещать в `outbox_dlq`. Реализуйте отдельный обработчик DLQ с алертом.

## Теория

Если одно из событий в Outbox содержит поврежденный payload, превышает максимальный размер сообщения Kafka (`max.message.bytes = 1MB`) или пытается записаться в несуществующий топик, наивный воркер застрянет на этой строке навсегда (Head-of-Line Blocking), заблокировав обработку миллионов других событий.

Архитектура отказоустойчивого ретранслятора включает:
1. Поле `retry_count INT DEFAULT 0` и `next_retry_at TIMESTAMPTZ DEFAULT NOW()` в схеме `outbox`.
2. Выборка только готовых к повтору записей: `WHERE processed = false AND next_retry_at <= NOW()`.
3. Экспоненциальная задержка: `next_retry_at = NOW() + (2^retry_count * 500ms)`.
4. При превышении порога (`retry_count >= 10`): событие вытесняется в таблицу `outbox_dlq` с отправкой критического алерта дежурному инженеру (PagerDuty / Telegram).

## Решение по шагам

1. Определите структуру события Outbox с полями `RetryCount`, `NextRetryAt`, `LastError`.
2. Реализуйте алгоритм вычисления Exponential Backoff с ограничением (Cap).
3. При достижении `MaxRetries = 3` перемещайте событие в слайс DLQ.
4. Продемонстрируйте обработчик DLQ, который логирует фатальную ошибку и шлет алерт.

## Код решения

**`relay_dlq.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"math"
	"sync"
	"time"
)

type OutboxMessage struct {
	ID          string
	Payload     string
	RetryCount  int
	NextRetryAt time.Time
	LastError   string
}

type DLQMessage struct {
	OriginalID string
	Payload    string
	MovedAt    time.Time
	FinalError string
}

type OutboxWorkerWithDLQ struct {
	mu         sync.Mutex
	outbox     map[string]*OutboxMessage
	dlq        []DLQMessage
	maxRetries int
}

func NewOutboxWorkerWithDLQ(maxRetries int) *OutboxWorkerWithDLQ {
	return &OutboxWorkerWithDLQ{
		outbox:     make(map[string]*OutboxMessage),
		maxRetries: maxRetries,
	}
}

func (w *OutboxWorkerWithDLQ) CalculateBackoff(retryCount int) time.Duration {
	base := 100 * time.Millisecond
	mult := math.Pow(2, float64(retryCount))
	backoff := time.Duration(float64(base) * mult)
	if backoff > 2*time.Second {
		backoff = 2 * time.Second
	}
	return backoff
}

func (w *OutboxWorkerWithDLQ) SendToBroker(msg *OutboxMessage) error {
	// Симуляция: сообщение 'poison_pill' фатально падает всегда
	if msg.Payload == "poison_pill" {
		return errors.New("kafka: message size exceeds broker limit 1048576 bytes")
	}
	return nil
}

func (w *OutboxWorkerWithDLQ) ProcessOutbox(ctx context.Context) {
	w.mu.Lock()
	defer w.mu.Unlock()

	now := time.Now()
	for id, msg := range w.outbox {
		if now.Before(msg.NextRetryAt) {
			continue // Сообщение ждет истечения интервала Backoff
		}

		err := w.SendToBroker(msg)
		if err == nil {
			fmt.Printf("[Relay Worker] Successfully sent event %s\n", id)
			delete(w.outbox, id)
			continue
		}

		// Обработка сбоя
		msg.RetryCount++
		msg.LastError = err.Error()

		if msg.RetryCount >= w.maxRetries {
			// Перемещение в Dead Letter Queue
			fmt.Printf("[CRITICAL ALERT] Event %s exceeded max retries (%d)! Moving to DLQ: %v\n",
				id, w.maxRetries, err)
			w.dlq = append(w.dlq, DLQMessage{
				OriginalID: id,
				Payload:    msg.Payload,
				MovedAt:    time.Now(),
				FinalError: err.Error(),
			})
			delete(w.outbox, id)
		} else {
			delay := w.CalculateBackoff(msg.RetryCount)
			msg.NextRetryAt = time.Now().Add(delay)
			fmt.Printf("[Relay Worker] Event %s failed (attempt %d). Scheduled retry in %v\n",
				id, msg.RetryCount, delay)
		}
	}
}

func main() {
	worker := NewOutboxWorkerWithDLQ(3)
	ctx := context.Background()

	// Добавляем обычное событие и "ядовитую пилюлю" (poison pill)
	worker.outbox["evt-ok"] = &OutboxMessage{ID: "evt-ok", Payload: "valid_order", NextRetryAt: time.Now()}
	worker.outbox["evt-bad"] = &OutboxMessage{ID: "evt-bad", Payload: "poison_pill", NextRetryAt: time.Now()}

	fmt.Println("=== Iteration 1 ===")
	worker.ProcessOutbox(ctx)

	fmt.Println("\n=== Iteration 2 (Fast forward 250ms) ===")
	time.Sleep(250 * time.Millisecond)
	worker.ProcessOutbox(ctx)

	fmt.Println("\n=== Iteration 3 (Fast forward 500ms) ===")
	time.Sleep(500 * time.Millisecond)
	worker.ProcessOutbox(ctx)

	fmt.Println("\n=== DLQ Contents Inspection ===")
	for _, item := range worker.dlq {
		fmt.Printf("DLQ Entry -> ID: %s, Error: %s\n", item.OriginalID, item.FinalError)
	}
	fmt.Printf("Remaining Outbox Queue size: %d\n", len(worker.outbox))
}
```

ℹ️ Экспоненциальный бэкофф и изоляция ядовитых сообщений в DLQ предотвращают Head-of-Line Blocking

## Под капотом

Использование индекса `CREATE INDEX idx_outbox_retry ON outbox (next_retry_at) WHERE processed = false` позволяет воркеру выбирать готовые к повтору записи через сканирование верхушки индекса без обхода всей таблицы.

## Подводные камни

1. Постоянный мгновенный ретрай без задержки (Busy Loop): воркер начнет бомбардировать БД и Kafka, сжигая 100% CPU ядра.
2. Бесшумный дроп сообщений: удаление сбойного события без записи в DLQ приведет к безвозвратной утере транзакции клиента.

## На собеседовании

Вопрос: Как организовать безопасную ручную переотправку (Reprocessing) событий из DLQ?
Ответ: DLQ реализуется как отдельная таблица с метаданными ошибки. В интерфейсе админки или через CLI утилиту инженер исправляет причину сбоя (увеличивает лимит брокера, корректирует payload) и выполняет команду `ReplayDLQ(id)`, которая атомарно возвращает запись в основную таблицу `outbox` со сброшенным `retry_count = 0`.
