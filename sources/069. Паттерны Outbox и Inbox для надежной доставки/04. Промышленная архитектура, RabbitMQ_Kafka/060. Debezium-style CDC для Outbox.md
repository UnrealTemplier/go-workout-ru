# Debezium-style CDC для Outbox: эмуляция стриминга логической репликации PostgreSQL

### Исходная формулировка

**Debezium-style CDC для Outbox (эмуляция).**: Вместо ручного ретранслятора, используйте логическую репликацию PostgreSQL (как в упражнениях 673-675), чтобы читать изменения таблицы `outbox` напрямую и отправлять в брокер. Сравните с опросом таблицы по таймеру.

## Теория

Логическая репликация PostgreSQL (Logical Replication) основана на чтении журнала упреждающей записи (WAL). Когда сервис выполняет `INSERT INTO outbox_events`, СУБД формирует бинарные записи в WAL. Сервис ретрансляции подключается как Logical Replication Client (используя слот репликации):

```text
PostgreSQL App -> INSERT INTO outbox_events -> WAL Log
                                                │
                                     (Replication Slot pgoutput)
                                                ▼
                                     CDC Streamer (pglogrepl)
                                                │
                                                ▼
                                           Kafka Topic
```
Преимущества перед поллингом:
1. Задержка (Latency) падает с сотен миллисекунд до единиц миллисекунд.
2. Нулевая нагрузка на индексы таблицы и пул соединений СУБД (нет частых `SELECT`).
3. Невозможно пропустить событие при сбое воркера — слот репликации хранит LSN курсор.

## Решение по шагам

1. Спроектируйте структуру WAL записи репликации (`WALMessage`, `LSN`).
2. Смоделируйте стример логической репликации с подтверждением позиции (Standby Status Update).
3. Реализуйте трансляцию изменений в Kafka.
4. Продемонстрируйте мгновенную обработку событий без холостого ожидания.

## Код решения

**`cdc_replication_emulator.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type LogicalWALRecord struct {
	LSN       uint64
	Relation  string
	Action    string // 'I' - Insert, 'U' - Update, 'D' - Delete
	Columns   map[string]string
	CreatedAt time.Time
}

type MockReplicationSlot struct {
	walStream chan LogicalWALRecord
	ackedLSN  uint64
}

func (s *MockReplicationSlot) Stream() <-chan LogicalWALRecord {
	return s.walStream
}

func (s *MockReplicationSlot) AckLSN(lsn uint64) {
	s.ackedLSN = lsn
	fmt.Printf(" -> [Postgres Slot Updated] Acknowledged LSN: %d (PostgreSQL may now reclaim WAL segment)\n", lsn)
}

type CDCStreamer struct {
	slot *MockReplicationSlot
}

func (c *CDCStreamer) Run(ctx context.Context) {
	fmt.Println("[CDC Streamer] Connected to Postgres Replication Slot 'outbox_cdc_slot'...")
	for {
		select {
		case <-ctx.Done():
			return
		case record := <-c.slot.Stream():
			latency := time.Since(record.CreatedAt)
			fmt.Printf("[CDC Event] Read LSN %d from WAL! Action: %s on %s\n",
				record.LSN, record.Action, record.Relation)
			fmt.Printf(" -> Publishing to Kafka: %s (Delivery latency: %v)\n",
				record.Columns["payload"], latency)

			// Подтверждение продвижения слота репликации
			c.slot.AckLSN(record.LSN)
		}
	}
}

func main() {
	slot := &MockReplicationSlot{walStream: make(chan LogicalWALRecord, 10)}
	streamer := &CDCStreamer{slot: slot}

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	go streamer.Run(ctx)
	time.Sleep(20 * time.Millisecond)

	fmt.Println("\n=== 1. App executes INSERT INTO outbox_events in PostgreSQL ===")
	now := time.Now()
	slot.walStream <- LogicalWALRecord{
		LSN:      55001234,
		Relation: "public.outbox_events",
		Action:   "I",
		Columns: map[string]string{
			"id":      "evt-cdc-01",
			"payload": `{"event": "UserRegistered", "email": "user@example.com"}`,
		},
		CreatedAt: now,
	}

	time.Sleep(50 * time.Millisecond)

	fmt.Println("\n=== 2. App executes another INSERT ===")
	slot.walStream <- LogicalWALRecord{
		LSN:      55001290,
		Relation: "public.outbox_events",
		Action:   "I",
		Columns: map[string]string{
			"id":      "evt-cdc-02",
			"payload": `{"event": "EmailVerificationSent", "email": "user@example.com"}`,
		},
		CreatedAt: time.Now(),
	}

	time.Sleep(50 * time.Millisecond)
	fmt.Printf("\nFinal Slot State: Confirmed LSN = %d\n", slot.ackedLSN)
}
```

ℹ️ Логическая репликация вычитывает WAL на лету и продвигает позицию LSN

## Под капотом

Драйвер `github.com/jackc/pglogrepl` взаимодействует с PostgreSQL по протоколу Streaming Replication. Клиент отправляет сообщение `StandbyStatusUpdate` с текущим значением `WriteLSN` и `FlushLSN`. Это освобождает дисковое пространство в папке `pg_wal`.

## Подводные камни

1. Неподтвержденный LSN: если CDC воркер читает сообщения, но не шлет `StandbyStatusUpdate`, PostgreSQL не сможет очистить WAL файлы и диск заполнится до 100%.
2. Падение слота при миграциях схемы: изменение структуры таблицы без обновления плагина декодирования может прервать репликацию.

## На собеседовании

Вопрос: Что произойдет с логическим слотом репликации при Failover реплики PostgreSQL на новый Master?
Ответ: До PostgreSQL 17 логические слоты репликации не реплицировались автоматически на Standby-ноды. При переключении мастера слот терялся, и требовалось использовать утилиты синхронизации (например, pg_failover_slots) или пересоздавать слот заново с риском повторной вычитки WAL.
