# Очистка (Garbage Collection): Cron-джоба удаления устаревших PROCESSED записей

## Условие

66. **Очистка (Garbage Collection)**: Таблицы Outbox и Inbox растут бесконечно. Напиши Cron-джобу (на `time.Ticker`), которая раз в сутки делает `DELETE FROM outbox_events WHERE status = 'PROCESSED' AND created_at < NOW() - INTERVAL '7 days'`.

### Исходная формулировка

**Очистка (Garbage Collection)**: Таблицы Outbox и Inbox растут бесконечно. Напиши Cron-джобу (на `time.Ticker`), которая раз в сутки делает `DELETE FROM outbox_events WHERE status = 'PROCESSED' AND created_at < NOW() - INTERVAL '7 days'`.

## Теория

В высоконагруженной системе таблица Outbox без сборки мусора за месяц разрастется на сотни миллионов строк. Это приведет к:
1. Падению производительности запросов выборки неотправленных сообщений.
2. Раздуванию дискового пространства и замедлению создания бэкапов (`pg_dump`).

Реализация Garbage Collector в Go:
- Запуск по расписанию через `time.Ticker`.
- Удаление строго пачками (`LIMIT 1000` в цикле), чтобы не вызывать долгих блокировок и не заполнять буфер транзакций.
- Удаление только тех записей, чей статус подтвержден (`status = 'PROCESSED'`), а возраст превышает безопасный порог (7 дней).

## Решение по шагам

1. Реализуйте метод безопасного пакетного удаления `PurgeProcessedBatch(olderThan, limit)`.
2. Настройте периодический таймер очистки `time.NewTicker`.
3. Запустите цикл удаления до тех пор, пока возвращаются удаленные строки.
4. Залогируйте общее число очищенных строк.

## Код решения

**`outbox_gc.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxRow struct {
	ID        int64
	Status    string
	CreatedAt time.Time
}

type OutboxDatabase struct {
	mu   sync.Mutex
	rows map[int64]OutboxRow
}

func (db *OutboxDatabase) DeleteOldProcessedBatch(olderThan time.Duration, limit int) int {
	db.mu.Lock()
	defer db.mu.Unlock()

	threshold := time.Now().Add(-olderThan)
	deleted := 0

	// Эмуляция SQL:
	// DELETE FROM outbox_events
	// WHERE id IN (
	//     SELECT id FROM outbox_events
	//     WHERE status = 'PROCESSED' AND created_at < NOW() - INTERVAL '7 days'
	//     LIMIT 1000
	// );
	for id, r := range db.rows {
		if r.Status == "PROCESSED" && r.CreatedAt.Before(threshold) {
			delete(db.rows, id)
			deleted++
			if deleted >= limit {
				break
			}
		}
	}
	return deleted
}

type OutboxGCJob struct {
	db       *OutboxDatabase
	interval time.Duration
	maxAge   time.Duration
}

func (gc *OutboxGCJob) RunOnce(ctx context.Context) int {
	totalPurged := 0
	batchSize := 2 // Для наглядного теста пачками по 2 записи

	for {
		deleted := gc.db.DeleteOldProcessedBatch(gc.maxAge, batchSize)
		totalPurged += deleted
		if deleted < batchSize {
			break
		}
	}
	return totalPurged
}

func main() {
	db := &OutboxDatabase{rows: make(map[int64]OutboxRow)}
	now := time.Now()

	// 1. Старые обработанные записи (10 дней назад) -> ПОДЛЕЖАТ УДАЛЕНИЮ
	for i := int64(1); i <= 5; i++ {
		db.rows[i] = OutboxRow{ID: i, Status: "PROCESSED", CreatedAt: now.Add(-10 * 24 * time.Hour)}
	}

	// 2. Старая, но НЕОБРАБОТАННАЯ запись -> НЕЛЬЗЯ УДАЛЯТЬ!
	db.rows[6] = OutboxRow{ID: 6, Status: "PENDING", CreatedAt: now.Add(-10 * 24 * time.Hour)}

	// 3. Свежая обработанная запись (1 день назад) -> НЕЛЬЗЯ УДАЛЯТЬ!
	db.rows[7] = OutboxRow{ID: 7, Status: "PROCESSED", CreatedAt: now.Add(-1 * 24 * time.Hour)}

	fmt.Printf("Initial total records in Outbox table: %d\n", len(db.rows))

	gc := &OutboxGCJob{
		db:     db,
		maxAge: 7 * 24 * time.Hour,
	}

	ctx := context.Background()
	fmt.Println("\n=== Executing Outbox Garbage Collection Job ===")
	purged := gc.RunOnce(ctx)

	fmt.Printf("Purged expired PROCESSED records: %d\n", purged)
	fmt.Printf("Remaining records in Outbox table: %d\n\n", len(db.rows))

	fmt.Println("=== Remaining Records Inspection ===")
	for id, r := range db.rows {
		fmt.Printf("Row #%d: Status=%s, Age=%v\n", id, r.Status, now.Sub(r.CreatedAt).Round(time.Hour))
	}
}
```

ℹ️ Пакетное удаление записей по расписанию предотвращает разрастание таблицы Outbox

**`output.txt`**

```bash

=== Executing Outbox Garbage Collection Job ===
Purged expired PROCESSED records: 5
Remaining records in Outbox table: 2

=== Remaining Records Inspection ===
Row #6: Status=PENDING, Age=240h0m0s
Row #7: Status=PROCESSED, Age=24h0m0s
```

ℹ️ Удалены только устаревшие PROCESSED записи, PENDING и свежие строки сохранены

## Под капотом

Массовое удаление через `DELETE` в PostgreSQL не освобождает физическое место на диске, а лишь помечает кортежи как мертвые (Dead Tuples). Освобождение страниц диска для повторного использования производится процессом `autovacuum`. Регулярная очистка небольшими батчами позволяет автовакууму успевать очищать страницы без блокировок.

## Подводные камни

1. Удаление без проверки статуса (`WHERE created_at < ...`): если ретранслятор простаивал из-за сбоя сети, чистильщик удалит неотправленные события клиентов.
2. Выполнение одного гигантского `DELETE` без LIMIT: транзакция заблокирует таблицу и исчерпает лимит блокировок памяти.

## На собеседовании

Вопрос: Почему в HighLoad системах для таблиц Outbox и Inbox предпочитают партиционирование вместо `DELETE`?
Ответ: Потому что `DELETE` нагружает процессор СУБД, порождает терабайты WAL и требует постоянной работы автовакуума. При партиционировании по дням очистка выполняется командой `DROP TABLE outbox_2026_08_01`, которая мгновенно удаляет файл партиции с файловой системы за 0 миллисекунд.
