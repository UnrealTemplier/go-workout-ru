# Атомарный Inbox: проверка уникальности через sql.Tx и бизнес-логика резервирования

## Условие

56. **Атомарный Inbox (Дедупликация)**: Брокеры могут доставить событие дважды (At-Least-Once). При получении сообщения из Kafka, открой `sql.Tx`. 1) Сделай `INSERT INTO inbox_events (event_id)`. Если ловишь ошибку `UniqueViolation` (событие уже было) — делай `Rollback`, `Ack` брокеру и игнорируй. 2) Если ок, делай бизнес-логику (резервируй товары). 3) `tx.Commit()`.

## Теория

Стандартный паттерн обработки сообщений консьюмера в Go с использованием пакета `database/sql`:
```go
tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
if err != nil { return err }
defer tx.Rollback()

_, err = tx.ExecContext(ctx, `INSERT INTO inbox_events (event_id) VALUES ($1)`, eventID)
if err != nil {
    if isPgUniqueViolation(err) {
        // Дубликат: откатываем tx и подтверждаем Ack брокеру
        return nil
    }
    return err // Реальная ошибка БД -> Nack брокеру для ретрая
}
// Бизнес-логика
if err := reserveStock(ctx, tx, orderID); err != nil { return err }
return tx.Commit()
```
Такая последовательность действий математически гарантирует, что резерв товара спишется строго один раз.

## Решение по шагам

1. Реализуйте функцию эмуляции распознавания ошибки `UniqueViolation`.
2. Откройте транзакцию через интерфейс хранилища.
3. Попробуйте вставить `event_id` в `inbox_events`.
4. При конфликте ключа выполните `tx.Rollback()` и верните `nil`.
5. При успешной вставке спишите остаток и закоммитьте.

## Код решения

**`atomic_inbox_reservation.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

var ErrSQLUniqueViolation = errors.New("pq: duplicate key value violates unique constraint inbox_events_pkey")

type AtomicStore struct {
	mu     sync.Mutex
	inbox  map[string]bool
	stock  int
	active bool
}

func NewAtomicStore(initialStock int) *AtomicStore {
	return &AtomicStore{
		inbox: make(map[string]bool),
		stock: initialStock,
	}
}

type ConsumerTx struct {
	store       *AtomicStore
	pendingID   string
	stockDelta  int
	isDuplicate bool
}

func (s *AtomicStore) BeginTx() *ConsumerTx {
	s.mu.Lock()
	return &ConsumerTx{store: s}
}

func (tx *ConsumerTx) InsertInbox(eventID string) error {
	if tx.store.inbox[eventID] {
		tx.isDuplicate = true
		return ErrSQLUniqueViolation
	}
	tx.pendingID = eventID
	return nil
}

func (tx *ConsumerTx) DeductStock(qty int) error {
	if tx.store.stock < qty {
		return errors.New("out of stock")
	}
	tx.stockDelta += qty
	return nil
}

func (tx *ConsumerTx) Commit() error {
	defer tx.store.mu.Unlock()
	if tx.pendingID != "" {
		tx.store.inbox[tx.pendingID] = true
	}
	tx.store.stock -= tx.stockDelta
	return nil
}

func (tx *ConsumerTx) Rollback() {
	tx.store.mu.Unlock()
}

func HandleKafkaEvent(ctx context.Context, store *AtomicStore, eventID string, qty int) error {
	tx := store.BeginTx()

	// Шаг 1: Попытка занять запись в Inbox
	err := tx.InsertInbox(eventID)
	if err != nil {
		if errors.Is(err, ErrSQLUniqueViolation) {
			tx.Rollback()
			fmt.Printf("[Consumer] Event %s already exists in inbox. Rollback Tx & ACK Kafka (Deduplicated).\n", eventID)
			return nil
		}
		tx.Rollback()
		return err
	}

	// Шаг 2: Бизнес-логика резервирования
	if err := tx.DeductStock(qty); err != nil {
		tx.Rollback()
		return fmt.Errorf("business error: %w", err)
	}

	// Шаг 3: Фиксация транзакции
	if err := tx.Commit(); err != nil {
		return err
	}

	fmt.Printf("[Consumer] Event %s committed: reserved %d items. Remaining stock: %d\n",
		eventID, qty, store.stock)
	return nil
}

func main() {
	store := NewAtomicStore(50)
	ctx := context.Background()

	eventID := "uuid-kafka-evt-4455"

	fmt.Println("=== Delivery 1: Fresh message arrives ===")
	_ = HandleKafkaEvent(ctx, store, eventID, 5)

	fmt.Println("\n=== Delivery 2: Duplicate message arrives (Broker redelivery) ===")
	_ = HandleKafkaEvent(ctx, store, eventID, 5)

	fmt.Printf("\nFinal Inventory Status: Available Stock = %d (Expected 45)\n", store.stock)
}
```

ℹ️ Уникальный ключ в транзакции гарантирует атомарность и защиту от повторного списания

```bash
[Consumer] Event uuid-kafka-evt-4455 committed: reserved 5 items. Remaining stock: 45

=== Delivery 2: Duplicate message arrives (Broker redelivery) ===
[Consumer] Event uuid-kafka-evt-4455 already exists in inbox. Rollback Tx & ACK Kafka (Deduplicated).

```

## Под капотом

Когда две горутины параллельно пытаются выполнить `INSERT INTO inbox_events (event_id)` с одинаковым ключом, PostgreSQL блокирует вторую транзакцию на уровне строки индекса. Как только первая транзакция делает `COMMIT`, вторая немедленно получает ошибку `SQLSTATE 23505` (unique_violation).

## Подводные камни

1. Возврат ошибки в брокер при дубликате: если вернуть ошибку из хэндлера Kafka/RabbitMQ, брокер выполнит NACK и отправит сообщение снова, создав бесконечный цикл.
2. Удержание блокировки слишком долго: бизнес-логика внутри транзакции должна быть минимальной.

## На собеседовании

Вопрос: Почему важно делать `Rollback()` перед отправкой Ack брокеру при обнаружении дубликата?
Ответ: Если транзакция упала с `unique_violation`, в PostgreSQL она переходит в статус `aborted`. Любые последующие запросы в этой транзакции вызовут ошибку. Явный `Rollback()` мгновенно освобождает соединение с базой данных и возвращает его в пул `sql.DB`.
