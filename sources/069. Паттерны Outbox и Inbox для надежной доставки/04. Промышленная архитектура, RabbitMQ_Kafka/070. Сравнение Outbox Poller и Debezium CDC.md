# Сравнение Outbox Poller и Debezium CDC: инженерные компромиссы и матрица выбора

## Условие

## Теория

Выбор между Outbox Poller и CDC — одно из ключевых архитектурных решений при проектировании микросервисов:

1. **Outbox Poller (Опрос базы данных):**
   - **Архитектура:** Go-воркер с таймером выполняет `SELECT ... FOR UPDATE SKIP LOCKED`.
   - **Преимущества:** Минимальная инфраструктура (нет Kafka Connect, Debezium, ZooKeeper/KRaft), весь код написан на Go и легко тестируется модульными тестами, независимость от прав суперпользователя в БД.
   - **Недостатки:** Задержка доставки (от 200 мс до 2 сек), постоянная нагрузка на дисковый I/O и пул соединений СУБД.
   - **Рекомендация:** Стартапы, MVP, внутренние админки, системы с нагрузкой до 500 RPS.

2. **CDC (Change Data Capture / Debezium):**
   - **Архитектура:** Чтение WAL логов СУБД через порт репликации.
   - **Преимущества:** Задержка доставки < 20 мс, нулевая нагрузка на исполнение SQL запросов, идеальное масштабирование.
   - **Недостатки:** Высокая сложность эксплуатации кластера Kafka Connect, риск переполнения диска при застревании слота.
   - **Рекомендация:** Enterprise, HighLoad (>5 000 RPS), финансовые биржи, стриминг событий в реальном времени.

package main

import (
	"fmt"
	"time"
)

type BenchmarkResult struct {
	Strategy       string
	AvgLatency     time.Duration
	DBQueryOverhead string
	InfraComplexity string
	RecommendedFor  string
}

func main() {
	results := []BenchmarkResult{
		{
			Strategy:        "Outbox Poller (Go Ticker)",
			AvgLatency:      500 * time.Millisecond,
			DBQueryOverhead:  "High (Constant SELECT FOR UPDATE)",
			InfraComplexity:  "Low (Single Go binary, standard DB user)",
			RecommendedFor:   "SaaS, Startups, < 1000 RPS",
		},
		{
			Strategy:        "CDC (Debezium / pglogrepl)",
			AvgLatency:      8 * time.Millisecond,
			DBQueryOverhead:  "Zero (Reads WAL from OS cache)",
			InfraComplexity:  "High (Kafka Connect, Replication Slots)",
			RecommendedFor:   "Enterprise, HighLoad, > 5000 RPS",
		},
	}

	fmt.Println("=== Architectural Evaluation: Outbox Poller vs Debezium CDC ===")
	for i, res := range results {
		fmt.Printf("\n[%d] %s:\n", i+1, res.Strategy)
		fmt.Printf(" - End-to-End Latency:  %v\n", res.AvgLatency)
		fmt.Printf(" - Database Overhead:   %s\n", res.DBQueryOverhead)
		fmt.Printf(" - Infra Complexity:    %s\n", res.InfraComplexity)
		fmt.Printf(" - Best Suited For:     %s\n", res.RecommendedFor)
	}

	fmt.Println("\nEngineering Rule of Thumb:")
	fmt.Println("Start with Outbox Poller. Migrate to CDC only when database CPU/IO metrics demand it.")
}

## Под капотом

Poller создает нагрузку вида Read Amplification (коэффициент усиления чтения): даже если в системе нет новых заказов, воркер каждые 500 мс опрашивает БД. CDC является чистой Push-моделью: нет новых записей — нет ни единого байта трафика.

## Подводные камни

1. Преждевременная оптимизация (Premature Optimization): внедрение Debezium и Kafka Connect на старте проекта, когда нагрузка составляет 5 запросов в минуту.
2. Использование Poller с миллисекундным интервалом (`10ms`): это гарантированно перегрузит пул соединений СУБД.

## На собеседовании

Вопрос: Как плавно мигрировать с Outbox Poller на CDC без простоя системы (Zero Downtime)?
Ответ: Создается таблица Outbox. На первом этапе ее читает Poller. Когда нагрузка вырастает, разворачивается Debezium коннектор. На время переключения Poller плавно останавливается, а Debezium запускается со слотом репликации. Так как на стороне консьюмеров работает Transactional Inbox, любые возможные пересечения событий будут безопасно отсечены.
