# Сквозной пайплайн в RabbitMQ: интеграция Outbox и Inbox с эмуляцией разрывов сети

## Условие

62. **[Outbox + Inbox вместе]**: Соедини систему: Сервис A пишет в свою БД + Outbox. Публикует в RabbitMQ. Сервис B читает из RabbitMQ, пишет в свою БД + Inbox, обрабатывает. Сымитируй падение сети везде, где можно. Убедись, что данные не теряются и не дублируются.

### Исходная формулировка

**[Outbox + Inbox вместе]**: Соедини систему: Сервис A пишет в свою БД + Outbox. Публикует в RabbitMQ. Сервис B читает из RabbitMQ, пишет в свою БД + Inbox, обрабатывает. Сымитируй падение сети везде, где можно. Убедись, что данные не теряются и не дублируются.

## Теория

В RabbitMQ протокол доставки AMQP 0-9-1 использует механизм ручных подтверждений `basic.ack` и `basic.nack`:

1. **Producer Side (Service A):**
   - Заказ и событие сохраняются в БД `A`.
   - Воркер публикует в RabbitMQ с включенными `Publisher Confirms`.
   - При падении сети брокер не пришлет подтверждение — воркер повторит отправку.

2. **Consumer Side (Service B):**
   - Консьюмер получает сообщение с флагом `autoAck = false`.
   - Открывает транзакцию в БД `B`.
   - Пытается сделать `INSERT INTO inbox`.
   - Если дубликат: `tx.Rollback()`, вызов `ch.Ack(deliveryTag, false)`.
   - Если успех: бизнес-логика, `tx.Commit()`, вызов `ch.Ack(deliveryTag, false)`.
Даже если сеть упадет между `tx.Commit()` и `ch.Ack()`, повторная доставка будет безопасно отсечена Inbox.

## Решение по шагам

1. Спроектируйте шину сообщений RabbitMQ с очередью и механизмом `Ack` / `Nack`.
2. На стороне Сервиса А реализуйте публикацию с обработкой сбоя сети.
3. На стороне Сервиса Б реализуйте обработку с `autoAck = false` и проверкой Inbox.
4. Сымитируйте падение сети на этапе отправки Ack и убедитесь в надежности.

## Код решения

**`rabbitmq_outbox_inbox.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type AMQPDelivery struct {
	DeliveryTag uint64
	MessageID   string
	Body        string
	Redelivered bool
}

type MockRabbitQueue struct {
	mu       sync.Mutex
	messages []AMQPDelivery
	tagSeq   uint64
}

func (q *MockRabbitQueue) Publish(msgID, body string) {
	q.mu.Lock()
	defer q.mu.Unlock()
	q.tagSeq++
	q.messages = append(q.messages, AMQPDelivery{
		DeliveryTag: q.tagSeq,
		MessageID:   msgID,
		Body:        body,
	})
}

func (q *MockRabbitQueue) Redeliver(d AMQPDelivery) {
	q.mu.Lock()
	defer q.mu.Unlock()
	d.Redelivered = true
	q.messages = append(q.messages, d)
}

// Сервис B: Consumer с Inbox
type ConsumerServiceB struct {
	mu          sync.Mutex
	inbox       map[string]bool
	ordersCount int
}

func NewConsumerServiceB() *ConsumerServiceB {
	return &ConsumerServiceB{inbox: make(map[string]bool)}
}

func (b *ConsumerServiceB) HandleDelivery(d AMQPDelivery, simulateNetworkDropAfterCommit bool) bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	fmt.Printf("[RabbitMQ Consumer] Received DeliveryTag=%d (MsgID: %s, Redelivered: %t)\n",
		d.DeliveryTag, d.MessageID, d.Redelivered)

	// Шаг 1: Проверка Inbox
	if b.inbox[d.MessageID] {
		fmt.Printf(" -> [Inbox Duplicate] MsgID %s already processed. Calling basic.ack without execution.\n", d.MessageID)
		return true // Успешный ack дубликата
	}

	// Шаг 2: Бизнес-логика и фиксация в БД B
	b.inbox[d.MessageID] = true
	b.ordersCount++
	fmt.Printf(" -> [DB Commit] Order processed! Total orders in DB: %d\n", b.ordersCount)

	// Шаг 3: Симуляция падения сети до basic.ack
	if simulateNetworkDropAfterCommit {
		fmt.Printf(" -> [CRASH] Network disconnected before basic.ack! RabbitMQ will redeliver message!\n")
		return false
	}

	fmt.Printf(" -> [AMQP Ack] basic.ack sent to RabbitMQ broker.\n")
	return true
}

func main() {
	queue := &MockRabbitQueue{}
	consumer := NewConsumerServiceB()
	_ = context.Background()

	msgID := "msg-amqp-order-555"
	payload := `{"order_id": "ord-555", "item": "laptop"}`

	// Сервис A публикует событие
	queue.Publish(msgID, payload)

	fmt.Println("=== 1. First Attempt: Consumer processes message, but crashes before ACK ===")
	delivery := queue.messages[0]
	acked := consumer.HandleDelivery(delivery, true)

	if !acked {
		// RabbitMQ возвращает неподтвержденное сообщение в очередь
		queue.Redeliver(delivery)
	}

	fmt.Println("\n=== 2. Redelivery: RabbitMQ resends message with redelivered=true ===")
	redelivery := queue.messages[1]
	_ = consumer.HandleDelivery(redelivery, false)

	fmt.Println("\n=== Final Verification ===")
	fmt.Printf("Total processed orders: %d (Expected: 1)\n", consumer.ordersCount)
	fmt.Printf("Total inbox entries: %d (Expected: 1)\n", len(consumer.inbox))
}
```

ℹ️ RabbitMQ консьюмер с ручным подтверждением (basic.ack) защищен от повторной обработки через Inbox

## Под капотом

В протоколе AMQP при разрыве TCP соединения не подтвержденные сообщения (`unacked`) автоматически возвращаются брокером в начало очереди с выставлением флага `redelivered = true`. Без Inbox это приводит к гарантированному дублированию бизнес-действий.

## Подводные камни

1. Включение `autoAck = true`: сообщение удаляется из брокера в момент отправки в сокет, при аварии воркера до записи в БД данные теряются безвозвратно.
2. Вызов `basic.reject(requeue=true)` при дубликате: приведет к бесконечному шторму повторов в RabbitMQ.

## На собеседовании

Вопрос: Что произойдет, если в RabbitMQ очередь забита сообщениями с redelivered=true из-за падений консьюмера?
Ответ: Это симптом Poison Message. Для защиты настраивается Dead Letter Exchange (DLX) и счетчик повторов `x-delivery-count` (в Quorum Queues). При превышении лимита брокер автоматически перемещает сбойное сообщение в очередь недоставленных.
