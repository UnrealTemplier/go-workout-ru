# CDC вместо Polling: чтение WAL через pglogrepl и отправка в Kafka без блокировки таблиц

## Условие

65. **[Высокая сложность — CDC вместо Polling]**: Опрос (`SELECT ... WHERE processed=false`) нагружает БД. Вместо Relay Worker используй CDC (Change Data Capture, `pglogrepl`). При INSERT в `outbox` PostgreSQL генерирует WAL-запись. Воркер читает WAL и отправляет в Kafka. Изучи библиотеку `github.com/riferrei/srclient` или Debezium.

### Исходная формулировка

**[Высокая сложность — CDC вместо Polling]**: Опрос (`SELECT ... WHERE processed=false`) нагружает БД. Вместо Relay Worker используй CDC (Change Data Capture, `pglogrepl`). При INSERT в `outbox` PostgreSQL генерирует WAL-запись. Воркер читает WAL и отправляет в Kafka. Изучи библиотеку `github.com/riferrei/srclient` или Debezium.

## Теория

При росте нагрузки до десятков тысяч заказов в секунду поллинг базы данных исчерпывает ресурс дисковой подсистемы. Паттерн Transaction Log Mining (CDC на базе библиотеки `github.com/jackc/pglogrepl`) переводит архитектуру на чтение бинарного WAL-лога:

1. В `postgresql.conf` выставляется `wal_level = logical` и `max_replication_slots = 10`.
2. Создается публикация: `CREATE PUBLICATION outbox_pub FOR TABLE outbox;`.
3. Go-сервис открывает репликационное соединение через `pgconn.Connect(ctx, 'replication=database')`.
4. В цикле вызывается `pglogrepl.ReceiveMessage(ctx)`.
5. При получении `pglogrepl.InsertMessage` воркер десериализует кортеж (Tuple) и отправляет событие в Kafka.
Нагрузка на СУБД нулевая — чтение происходит напрямую из файлового кэша операционной системы.

## Решение по шагам

1. Смоделируйте структуру декодированного WAL сообщения `WALTuple`.
2. Реализуйте парсер бинарного потока `pglogrepl.InsertMessage`.
3. Сформируйте Kafka Producer Record с ключом и телом сообщения.
4. Продемонстрируйте вызов `SendStandbyStatusUpdate` для подтверждения прочитанного LSN.

## Код решения

**`pglogrepl_cdc.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type LSN uint64

type WALTuple struct {
	XID       uint32
	CurrentLSN LSN
	Table     string
	Columns   map[string]string
}

type MockReplicationConn struct {
	mu          sync.Mutex
	streamChan  chan WALTuple
	standbyLSN  LSN
}

func (c *MockReplicationConn) ReceiveMessage(ctx context.Context) (WALTuple, error) {
	select {
	case <-ctx.Done():
		return WALTuple{}, ctx.Err()
	case msg := <-c.streamChan:
		return msg, nil
	}
}

func (c *MockReplicationConn) SendStandbyStatusUpdate(lsn LSN) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.standbyLSN = lsn
	fmt.Printf(" -> [StandbyStatusUpdate] Sent LSN: %d to PostgreSQL Master\n", lsn)
}

type CDCRelayService struct {
	conn   *MockReplicationConn
	kafka  chan string
}

func (s *CDCRelayService) Start(ctx context.Context) {
	fmt.Println("[CDC Engine] Listening to PostgreSQL Logical Replication stream (Publication: outbox_pub)...")
	for {
		tuple, err := s.conn.ReceiveMessage(ctx)
		if err != nil {
			return
		}

		if tuple.Table == "outbox" {
			topic := tuple.Columns["aggregate_type"] + ".events"
			key := tuple.Columns["partition_key"]
			payload := tuple.Columns["payload"]

			fmt.Printf("[CDC Engine] Captured WAL INSERT: LSN=%d | Table=%s\n", tuple.CurrentLSN, tuple.Table)
			fmt.Printf(" -> Producing to Kafka: Topic=%s, Key=%s, Payload=%s\n", topic, key, payload)

			s.kafka <- payload

			// Продвигаем позицию LSN в PostgreSQL
			s.conn.SendStandbyStatusUpdate(tuple.CurrentLSN)
		}
	}
}

func main() {
	conn := &MockReplicationConn{streamChan: make(chan WALTuple, 5)}
	kafkaQueue := make(chan string, 5)

	cdc := &CDCRelayService{conn: conn, kafka: kafkaQueue}
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	go cdc.Start(ctx)
	time.Sleep(20 * time.Millisecond)

	fmt.Println("=== PostgreSQL Engine: Transaction commits INSERT into outbox ===")
	conn.streamChan <- WALTuple{
		XID:        99104,
		CurrentLSN: 7788100,
		Table:      "outbox",
		Columns: map[string]string{
			"aggregate_type": "payments",
			"partition_key":  "cust-123",
			"payload":        `{"payment_id": "pay-001", "status": "CONFIRMED"}`,
		},
	}

	time.Sleep(50 * time.Millisecond)
	fmt.Printf("\nVerification: Received %d message in Kafka queue.\n", len(kafkaQueue))
}
```

ℹ️ Чтение потока логической репликации pglogrepl без выполнения SQL SELECT запросов

## Под капотом

Библиотека `pglogrepl` реализует клиентский протокол `walsender`. Движок СУБД передает поток байт через плагин `pgoutput`. Преимущество в том, что в таблице `outbox` не требуется обновлять статус (`UPDATE outbox SET processed=true`), что исключает генерацию Dead Tuples (мертвых строк).

## Подводные камни

1. Забытый вызов `SendStandbyStatusUpdate`: СУБД считает, что клиент отстал, и сохраняет гигабайты WAL на диске.
2. Падение воркера без сохранения LSN: при перезапуске поток начнется с последнего подтвержденного LSN, поэтому консьюмер в Kafka обязан иметь Transactional Inbox для фильтрации повторов.

## На собеседовании

Вопрос: Почему при использовании CDC из таблицы Outbox можно вообще не хранить поле `processed`?
Ответ: Потому что прогресс чтения отслеживается не полем в таблице, а курсором LSN в слоте репликации СУБД. Строки в таблице `outbox` просто вставляются (`INSERT`), а фоновый процесс периодически удаляет старые партиции таблицы по таймстампу.
