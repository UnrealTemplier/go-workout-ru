# Связка Inbox + Outbox: сквозная семантика Exactly-Once на уровне бизнес-логики

## Условие

71. **Inbox + Outbox combo**: Producer использует Outbox для publishing, Consumer использует Inbox для consuming. Это даёт end-to-end exactly-once semantics (на уровне бизнес-логики).

### Исходная формулировка

**Inbox + Outbox combo**: Producer использует Outbox для publishing, Consumer использует Inbox для consuming. Это даёт end-to-end exactly-once semantics (на уровне бизнес-логики).

## Теория

Связка паттернов Inbox и Outbox образует законченный контур надежности распределенной системы:

```text
┌─────────────────────────┐           ┌────────────────────────────────┐
│   PRODUCER SERVICE      │           │      CONSUMER SERVICE          │
│  ┌───────────────────┐  │           │  ┌──────────────────────────┐  │
│  │ Local ACID Tx:    │  │           │  │ Local ACID Tx:           │  │
│  │ - Insert Order    │  │           │  │ - Insert Inbox (Dedup)   │  │
│  │ - Insert Outbox   │  │           │  │ - Update Inventory/Debit │  │
│  └─────────┬─────────┘  │           │  └──────────────▲───────────┘  │
│            ▼            │           │                 │              │
│      Outbox Relay       │           │           Consumer Loop        │
└────────────┬────────────┘           └─────────────────┼──────────────┘
             │                                          │
             ▼           At-Least-Once Broker           │
             └─────────► [ Kafka / RabbitMQ ] ──────────┘
```
Producer гарантирует, что сообщение никогда не потеряется при сбое БД или сети (No Lost Events). Broker обеспечивает надежную транспортировку (At-Least-Once). Consumer гарантирует, что повторы брокера никогда не исказят баланс или состояние (No Duplicate Execution). В результате достигается сквозная семантика **Effectively Exactly-Once**.

## Решение по шагам

1. Спроектируйте законченную модель распределенной транзакции между двумя сервисами.
2. Смоделируйте отправку через Outbox и приём через Inbox.
3. Инжектируйте серию сетевых сбоев (потери ответов, повторы, дубли).
4. Подтвердите инвариант: конечное состояние бизнес-данных абсолютно консистентно.

## Код решения

**`full_combo_e2e.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

// Общая шина сообщений (транспорт At-Least-Once)
type MessageBus struct {
	mu       sync.Mutex
	messages []BusMessage
}

type BusMessage struct {
	ID      string
	Payload string
}

func (b *MessageBus) Publish(m BusMessage) {
	b.mu.Lock()
	defer b.mu.Unlock()
	// Симуляция сетевых аномалий: доставка с дублированием!
	b.messages = append(b.messages, m, m)
}

// 1. PRODUCER: Order Service с Outbox
type OrderProducer struct {
	mu     sync.Mutex
	orders map[string]int
	outbox []BusMessage
	bus    *MessageBus
}

func (p *OrderProducer) PlaceOrder(orderID string, amount int) {
	p.mu.Lock()
	// Единая транзакция: Order + Outbox
	p.orders[orderID] = amount
	msg := BusMessage{
		ID:      "evt-order-" + orderID,
		Payload: fmt.Sprintf(`{"order_id": "%s", "amount": %d}`, orderID, amount),
	}
	p.outbox = append(p.outbox, msg)
	p.mu.Unlock()

	// Outbox Relay отправляет в шину
	p.bus.Publish(msg)
	fmt.Printf("[Producer] Order %s placed (Outbox Event %s published with retries)\n", orderID, msg.ID)
}

// 2. CONSUMER: Billing Service с Inbox
type BillingConsumer struct {
	mu            sync.Mutex
	inbox         map[string]bool
	totalRevenue  int
	executedCount int
}

func (c *BillingConsumer) Consume(m BusMessage) {
	c.mu.Lock()
	defer c.mu.Unlock()

	// Единая транзакция: Inbox + Revenue Update
	if c.inbox[m.ID] {
		fmt.Printf("[Consumer] Event %s rejected by Inbox. Duplicate skipped.\n", m.ID)
		return
	}

	c.inbox[m.ID] = true
	c.totalRevenue += 500
	c.executedCount++
	fmt.Printf("[Consumer] Event %s committed. Total Revenue: %d\n", m.ID, c.totalRevenue)
}

func main() {
	bus := &MessageBus{}
	producer := &OrderProducer{
		orders: make(map[string]int),
		bus:    bus,
	}
	consumer := &BillingConsumer{
		inbox: make(map[string]bool),
	}
	_ = context.Background()

	fmt.Println("=== Executing E2E Transaction: Order -> Outbox -> Bus -> Inbox -> Billing ===")
	producer.PlaceOrder("ord-777", 500)

	fmt.Println("\n=== Processing Messages from Broker (Containing Injected Duplicates) ===")
	for _, msg := range bus.messages {
		consumer.Consume(msg)
	}

	fmt.Println("\n=== Final Consistency Verification ===")
	fmt.Printf("Producer Orders: %d\n", len(producer.orders))
	fmt.Printf("Consumer Revenue: %d (Expected: 500)\n", consumer.totalRevenue)
	fmt.Printf("Consumer Executions: %d (Expected: 1)\n", consumer.executedCount)
	fmt.Println("Status: System achieved 100% Effectively Exactly-Once Semantics!")
}
```

ℹ️ Сквозная демонстрация связки Outbox и Inbox с защитой от дублирования

## Под капотом

Связка Outbox + Inbox переносит гарантии надежности с ненадежного сетевого уровня на локальный уровень надежности транзакционных СУБД. Реляционная СУБД с WAL логом является математически строгим автоматом состояний, гарантирующим сохранность данных.

## Подводные камни

1. Реализация только одной половины: Outbox без Inbox приводит к дублированию платежей при сбоях сети; Inbox без Outbox приводит к потере событий при падении продюсера.
2. Генерация недетерминированных ID: если продюсер не привязывает ID события к ID заказа, дедупликатор Inbox не сможет связать повторы между собой.

## На собеседовании

Вопрос: Почему архитектура Outbox + Inbox стала де-факто стандартом микросервисов в мировом BigTech?
Ответ: Потому что она устраняет необходимость в медленных, блокирующих и хрупких 2PC (двухфазных) транзакциях. Она полностью изолирует сбои компонентов: даже если Kafka лежит 2 часа, продюсер продолжает принимать заказы в БД, а после восстановления брокера воркеры автоматически доставят все события без единой потери и без дублирования.
