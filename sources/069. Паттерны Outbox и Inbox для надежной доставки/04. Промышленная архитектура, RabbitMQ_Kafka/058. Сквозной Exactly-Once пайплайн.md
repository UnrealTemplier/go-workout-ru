# Сквозной Exactly-Once пайплайн: стресс-тестирование с тройной повторной доставкой сообщений

### Исходная формулировка

**Сквозной Exactly-Once пайплайн**: Объедините ваши наработки: Сервис А (БД + Outbox) -> Kafka -> Воркер Б (Inbox + БД). Протестируйте систему: сымитируйте сетевой сбой (отправьте одно и то же сообщение в Kafka 3 раза подряд). Убедитесь, что на стороне Сервиса Б бизнес-данные обновились строго один раз, а в таблице `inbox_events` осталась только одна запись.

## Теория

Полный цикл распределенного сквозного тестирования (End-to-End Stress Test) подтверждает корректность архитектуры:
1. **Producer Side:** Сервис А в локальной транзакции выполняет `INSERT INTO orders` и `INSERT INTO outbox`.
2. **Transport Layer:** Outbox Relay отправляет событие. Из-за эмуляции сетевых сбоев брокер дублирует сообщение 3 раза.
3. **Consumer Side:** Воркер Б получает 3 сообщения, пытается записать их в `inbox_events` и изменить баланс клиента.
4. **Verification:**
   - Баланс клиента изменился строго на 1 транзакцию.
   - В таблице `inbox_events` ровно 1 запись.
   - В логах консьюмера зафиксированы 1 успех и 2 подавленных дубликата.

## Решение по шагам

1. Соберите компоненты Producer, Outbox Relay, Network Broker и Consumer.
2. Создайте заказ на стороне Producer.
3. Отправьте событие в брокер с принудительным троекратным дублированием.
4. Запустите цикл обработки Consumer.
5. Проверьте assert-условиями равенство единице числа бизнес-мутаций.

## Код решения

**`e2e_stress_pipeline.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type Event struct {
	ID        string
	AccountID string
	Amount    int
}

type BankDatabase struct {
	mu          sync.Mutex
	inboxEvents map[string]bool
	balances    map[string]int
	auditTrail  []string
}

func NewBankDatabase() *BankDatabase {
	return &BankDatabase{
		inboxEvents: make(map[string]bool),
		balances:    make(map[string]int),
	}
}

func (db *BankDatabase) ProcessDeposit(ctx context.Context, ev Event) (bool, error) {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Атомарная проверка Inbox
	if db.inboxEvents[ev.ID] {
		// Duplicate detected!
		return false, nil
	}

	// 2. Вставка в Inbox + изменение баланса
	db.inboxEvents[ev.ID] = true
	db.balances[ev.AccountID] += ev.Amount
	db.auditTrail = append(db.auditTrail, fmt.Sprintf("Credited %d to account %s", ev.Amount, ev.AccountID))
	return true, nil
}

func main() {
	db := NewBankDatabase()
	targetAccount := "ACC-DEPOSIT-999"
	db.balances[targetAccount] = 1000

	depositEvent := Event{
		ID:        "evt-deposit-tx-777",
		AccountID: targetAccount,
		Amount:    500,
	}

	// Симуляция сетевого сбоя: 3 доставки одного и того же события
	eventStream := []Event{depositEvent, depositEvent, depositEvent}

	fmt.Printf("Initial Account Balance: %d\n", db.balances[targetAccount])
	fmt.Printf("Simulating 3 duplicate deliveries of Event %s...\n\n", depositEvent.ID)

	ctx := context.Background()
	for i, ev := range eventStream {
		applied, err := db.ProcessDeposit(ctx, ev)
		if err != nil {
			panic(err)
		}
		if applied {
			fmt.Printf("Delivery #%d: SUCCESS! Applied deposit +%d\n", i+1, ev.Amount)
		} else {
			fmt.Printf("Delivery #%d: DUPLICATE! Filtered by inbox_events constraint. ACK broker.\n", i+1)
		}
	}

	fmt.Println("\n=== Final Verification Results ===")
	fmt.Printf("Final Account Balance: %d (Expected: 1500)\n", db.balances[targetAccount])
	fmt.Printf("Total Records in inbox_events: %d (Expected: 1)\n", len(db.inboxEvents))
	fmt.Printf("Total Entries in Audit Trail: %d (Expected: 1)\n", len(db.auditTrail))

	if db.balances[targetAccount] != 1500 || len(db.inboxEvents) != 1 {
		panic("VERIFICATION FAILED! State corruption detected.")
	}
	fmt.Println("All assertions passed! Effectively Exactly-Once semantics verified.")
}
```

ℹ️ Сквозной стресс-тест подтверждает сохранение инварианта баланса при тройной доставке

## Под капотом

С точки зрения теории распределенных вычислений, данная цепочка реализует свойство At-Least-Once Delivery на транспортном уровне в комбинации с Idempotent Consumer на прикладном уровне, что в совокупности дает математическую семантику Exactly-Once Execution.

## Подводные камни

1. Несинхронизированный доступ к разделяемой памяти в тестах: запуск без мьютексов может создать видимость успеха, но упасть в рантайме под `-race`.
2. Случайный ID при ретраях: если продюсер пересоздает `event.ID` на каждом ретрае, тест упадет.

## На собеседовании

Вопрос: В чем разница между Exactly-Once Processing и Exactly-Once Delivery?
Ответ: Exactly-Once Delivery (ровно одна физическая передача пакета по проводам) в ненадежных IP-сетях физически невозможна из-за падений узлов и таймаутов (Two Generals Problem). Exactly-Once Processing — это прикладное свойство системы, гарантирующее, что эффект от многократной доставки сообщения эквивалентен однократному исполнению благодаря идемпотентности и Inbox.
