## Теория

Паттерн Transaction Log Tailing (описанный Крисом Ричардсоном в 'Microservices Patterns') — это наивысшая ступень эволюции Transactional Outbox. В отличие от опросного воркера (Polling Publisher), система хвоста журнала (Log Tailer) не выполняет ни единого SQL-запроса к таблицам базы данных.

Архитектурное сравнение:
1. **Polling Publisher (Go Worker):**
   - Периодический `SELECT ... FOR UPDATE SKIP LOCKED`.
   - Высокая конкуренция за строки, нагрузка на CPU и диск СУБД, задержка от сотен миллисекунд до секунд.
2. **Transaction Log Tailing (Debezium / Kafka Connect):**
   - Подключается к движку СУБД через порт репликации.
   - Читает физические сегменты WAL последовательно с диска.
   - Задержка: 5–20 мс.
   - Нагрузка на исполнение SQL транзакций: 0%.

## Код решения

**`log_tailer.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type WALEntry struct {
	CommitLSN uint64
	Table     string
	Payload   string
	Timestamp time.Time
}

type LogTailerDaemon struct {
	walPipeline chan WALEntry
	kafkaTopic  string
}

func (d *LogTailerDaemon) Start(ctx context.Context) {
	fmt.Println("[Log Tailer] Attached to Transaction Log (WAL). Zero SQL queries executed against DB engine.")
	for {
		select {
		case <-ctx.Done():
			return
		case entry := <-d.walPipeline:
			latency := time.Since(entry.Timestamp)
			fmt.Printf("[WAL Tailing Event] LSN: %d | Direct WAL read latency: %v\n", entry.CommitLSN, latency)
			fmt.Printf(" -> Pushed to Kafka [%s]: %s\n\n", d.kafkaTopic, entry.Payload)
		}
	}
}

func main() {
	walPipe := make(chan WALEntry, 10)
	daemon := &LogTailerDaemon{
		walPipeline: walPipe,
		kafkaTopic:  "financial.orders.v1",
	}

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	go daemon.Start(ctx)
	time.Sleep(20 * time.Millisecond)

	fmt.Println("=== Client executes regular business INSERT in PostgreSQL ===")
	start := time.Now()

	// Движок БД при коммите скидывает запись в WAL
	walPipe <- WALEntry{
		CommitLSN: 8819200,
		Table:     "outbox_events",
		Payload:   `{"order_id": "ord-wal-999", "amount": 10000}`,
		Timestamp: start,
	}

	time.Sleep(50 * time.Millisecond)
	fmt.Println("=== Log Tailing Summary ===")
	fmt.Println("No SELECT queries, no table locks, zero dead tuples created.")
}
```

ℹ️ Transaction Log Tailing читает журнал транзакций напрямую без исполнения SQL

## Под капотом

Движок PostgreSQL при записи в WAL использует кольцевой буфер в памяти (`wal_buffers`). Log Tailer часто успевает вычитать данные прямо из оперативной памяти до того, как они будут физически сброшены на медленный диск.

## Подводные камни

1. Опасность падения слота: если репликационный слот застрянет, диск СУБД переполнится.
2. Усложнение инфраструктуры: требует настройки Debezium, Zookeeper/KRaft, Kafka Connect и прав SUPERUSER/REPLICATION в БД.

## На собеседовании

Вопрос: Что эффективнее для HighLoad: 10 воркеров с SELECT SKIP LOCKED или 1 Debezium коннектор?
Ответ: 1 Debezium коннектор на порядки эффективнее. 10 воркеров создают 10 постоянных подключений, соперничают за блокировки B-Tree индексов и порождают миллионы операций `UPDATE`, нагружая диск. Debezium использует всего одно репликационное соединение и читает поток WAL линейно.
