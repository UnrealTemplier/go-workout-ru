# Outbox table: проектирование канонической схемы таблицы исходящих событий

### Исходная формулировка

**Outbox table**: Создайте таблицу `outbox` в той же БД, что и бизнес-данные:
```sql
CREATE TABLE outbox (
    id UUID PRIMARY KEY,
    aggregate_id UUID,
    aggregate_type VARCHAR,
    event_type VARCHAR,
    payload JSONB,
    created_at TIMESTAMP,
    processed BOOLEAN DEFAULT FALSE
);
```

## Теория

Проектирование таблицы `outbox` требует строгого соблюдения правил оптимизации реляционных баз. Канонические поля таблицы:
1) `id UUID PRIMARY KEY` — глобальный уникальный идентификатор события, используемый потребителями как Idempotency Key;
2) `aggregate_id UUID` — идентификатор сущности (например, `order_id`), используемый как ключ партиционирования в Kafka (Kafka Record Key) для сохранения строгого порядка событий по сущности;
3) `aggregate_type VARCHAR` — имя агрегата (`Order`, `User`, `Account`);
4) `event_type VARCHAR` — имя доменного события (`OrderCreated`, `PaymentReceived`);
5) `payload JSONB` — полезная нагрузка события;
6) `created_at TIMESTAMP` — временная метка;
7) `processed BOOLEAN DEFAULT FALSE` — статус обработки. Для исключения полнотабличного сканирования обязателен частичный индекс: `CREATE INDEX idx_outbox_unprocessed ON outbox (created_at) WHERE processed = FALSE`.

## Решение по шагам

## Код решения

**`outbox_schema.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

// DDL создания таблицы в PostgreSQL:
const OutboxDDL = `
CREATE TABLE IF NOT EXISTS outbox (
    id UUID PRIMARY KEY,
    aggregate_id UUID NOT NULL,
    aggregate_type VARCHAR(64) NOT NULL,
    event_type VARCHAR(128) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    processed BOOLEAN NOT NULL DEFAULT FALSE
);

-- Частичный индекс для быстрого поиска необработанных записей (Hot Queue)
CREATE INDEX IF NOT EXISTS idx_outbox_unprocessed 
ON outbox (created_at ASC) 
WHERE processed = FALSE;
`

type OutboxEntity struct {
	ID            string          `json:"id"`
	AggregateID   string          `json:"aggregate_id"`
	AggregateType string          `json:"aggregate_type"`
	EventType     string          `json:"event_type"`
	Payload       json.RawMessage `json:"payload"`
	CreatedAt     time.Time       `json:"created_at"`
	Processed     bool            `json:"processed"`
}

func main() {
	fmt.Println("=== POSTGRESQL OUTBOX SCHEMA DDL ===")
	fmt.Println(OutboxDDL)

	// Пример создания инстанса события
	rawPayload := json.RawMessage(`{"order_id":"b3c7-1234","amount":450.0}`)
	evt := OutboxEntity{
		ID:            "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
		AggregateID:   "b3c7-1234-5678-90ab-cdef12345678",
		AggregateType: "Order",
		EventType:     "OrderCreated",
		Payload:       rawPayload,
		CreatedAt:     time.Now().UTC(),
		Processed:     false,
	}

	bytes, _ := json.MarshalIndent(evt, "", "  ")
	fmt.Printf("Serialized Outbox Record:\n%s\n", string(bytes))
}
```

## Под капотом

Частичный индекс (`WHERE processed = FALSE`) является ключевой оптимизацией PostgreSQL. Поскольку 99.9% записей в таблице со временем становятся `processed = TRUE`, обычный B-Tree индекс разросся бы до сотен гигабайт. Частичный индекс индексирует ТОЛЬКО необработанные строки (обычно от нескольких штук до сотен записей), поэтому он полностью помещается в RAM (Shared Buffers) и сканируется за микросекунды.

## Подводные камни

1. Отсутствие типа JSONB: хранение полезной нагрузки как `TEXT` лишает возможности валидации синтаксиса JSON на уровне СУБД.
2. Бесконечный рост таблицы Outbox: обработанные строки со временем должны архивироваться или удаляться пакетами по расписанию (Housekeeping / Purging Job).

## На собеседовании

Вопрос: Зачем в схеме Outbox поле `aggregate_id`, если уже есть первичный ключ `id`?
Ответ: Поле `aggregate_id` используется как Partition Key в Apache Kafka. Kafka гарантирует строгое сохранение порядка сообщений (FIFO) только внутри одной партиции. Публикуя все события по конкретному заказу (`OrderCreated`, `OrderPaid`, `OrderCancelled`) с одним и тем же ключом `aggregate_id`, мы гарантируем их попадание в одну партицию и последовательную обработку консьюмерами.
