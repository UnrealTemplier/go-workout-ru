# Проблема Dual Write: глубокий анализ race condition и математика рассинхронизации

### Исходная формулировка

**[Проблема Dual Write]**: Напиши код, который делает `db.Exec("INSERT INTO orders...")`, а затем `kafka.Send(...)`. Сымитируй крах программы между этими двумя строками. Объясни, почему заказ в БД есть, а сообщения в Kafka нет.

## Теория

В распределенных вычислениях операция, состоящая из двух сетевых или дисковых действий, не может быть атомарной без общего консенсуса. Рассмотрим временную шкалу выполнения:
$$t_0: \text{App} \to \text{DB: INSERT (Success)}$$
$$t_1: \text{OS kills App (SIGKILL)}$$
$$t_2: \text{App} \to \text{Kafka: Send (NEVER CALLED)}$$
Поскольку коммит в базу данных уже произошел в момент времени \(t_0\), данные стали персистентными. Но событие в момент \(t_2\) не было отправлено. В итоге система находится в состоянии частичного отказа (Partial Failure). Потребители событий никогда не получат уведомления, что приведет к финансовым и операционным убыткам.

## Решение по шагам

1. Реализуйте функцию `SimulateDirectDatabaseAndBrokerWrite`.
2. Выполните успешную вставку в базу данных.
3. Запрограммируйте безусловный крах (Panic / Termination) перед отправкой в Kafka.
4. В функции `main` перехватите панику через `recover()` и проанализируйте финальное состояние БД и брокера.
5. Сформулируйте математический вывод о недопустимости такого подхода в HighLoad системах.

## Код решения

**`dual_write_math_proof.go`**

```go
package main

import (
	"fmt"
)

type OrdersTable struct {
	records map[string]string
}

type KafkaTopic struct {
	messages []string
}

func ProcessDirectOrder(db *OrdersTable, kafka *KafkaTopic, orderID, customer string) {
	// 1. Успешная фиксация в реляционной базе данных
	db.records[orderID] = customer
	fmt.Printf("[PostgreSQL] Transaction committed! Row inserted: OrderID=%s, Customer=%s\n", orderID, customer)

	// Имитация фатального падения рантайма (SIGKILL, Kernel Panic, Out of Memory)
	fmt.Println("[RUNTIME CRASH] Unexpected panic occurred between DB Commit and Kafka Send!")
	panic("fatal error: runtime killed abruptly")

	// 2. Отправка в Kafka — никогда не будет выполнена!
	kafka.messages = append(kafka.messages, orderID)
	fmt.Printf("[Kafka] Message sent for %s\n", orderID)
}

func main() {
	db := &OrdersTable{records: make(map[string]string)}
	kafka := &KafkaTopic{}

	// Вызываем уязвимый обработчик с защитой recover для аудита
	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("[Safety Catch] Intercepted panic: %v\n", r)
			}
		}()
		ProcessDirectOrder(db, kafka, "order-uuid-404", "Ivan Petrov")
	}()

	// Проверка целостности данных
	fmt.Println("\n=== SYSTEM CONSISTENCY AUDIT ===")
	fmt.Printf("Database records count: %d (Order %s is PRESENT)\n", len(db.records), "order-uuid-404")
	fmt.Printf("Kafka messages count:   %d (Kafka is EMPTY)\n", len(kafka.messages))
	fmt.Println("CONCLUSION: Direct Dual Write fundamentally violates distributed transaction integrity.")
}
```

ℹ️ Математическое доказательство неизбежности рассинхронизации при наивной двойной записи

## Под капотом

Фундаментальная причина кроется в независимости журналов транзакций. PostgreSQL имеет свой собственный Write-Ahead Log (WAL), а Apache Kafka — свой собственный Commit Log. Без внешнего распределенного менеджера транзакций невозможно синхронизировать момент сброса на диск (fsync) двух независимых физических накопителей.

## Подводные камни

1. Попытка исправить проблему горутиной `go kafka.Send()`: асинхронная горутина еще более подвержена потере событий при рестарте пода Kubernetes, так как процесс завершится до выполнения горутины.
2. Отсутствие мониторинга потерянных сообщений.

## На собеседовании

Вопрос: Является ли Transactional Outbox единственным решением проблемы Dual Write?
Ответ: Существует два основных архитектурных решения: 1) Transactional Outbox (с Poller или CDC Debezium); 2) Event Sourcing — когда само доменное событие является единственным источником истины, а база данных формируется как материализованное представление (Read Model / Projections).
