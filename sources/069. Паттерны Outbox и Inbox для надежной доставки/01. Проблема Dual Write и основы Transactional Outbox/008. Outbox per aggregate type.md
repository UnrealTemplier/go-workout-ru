# Outbox per aggregate type: шардирование Outbox-таблиц для снижения Lock Contention

## Условие

8. **Outbox per aggregate type**: Для high-volume систем создайте отдельные outbox tables per aggregate type (`orders_outbox`, `users_outbox`) для снижения contention.

### Исходная формулировка

**Outbox per aggregate type**: Для high-volume систем создайте отдельные outbox tables per aggregate type (`orders_outbox`, `users_outbox`) для снижения contention.

## Теория

В сверхнагруженных системах (High-Throughput / десятки тысяч RPS) единая таблица `outbox` становится узким местом из-за конкуренции блокировок (Lock Contention) на уровне страниц СУБД, индекса B-Tree и буферов WAL. Запись событий заказов, платежей, отзывов и пользователей в одну таблицу приводит к тому, что воркеры вычитки конкурируют с бизнес-транзакциями. Архитектурное решение — шардирование Outbox по типам агрегатов (Table Partitioning / Dedicated Outbox Tables):
1) `orders_outbox` — обслуживает высокочастотные события заказов;
2) `payments_outbox` — обслуживает финансовые транзакции;
3) `users_outbox` — обслуживает редкие события профилей.
Каждая таблица имеет собственный выделенный пул воркеров, независимые индексы и изолированные транзакции.

## Решение по шагам

1. Создайте интерфейс `OutboxRouter`, маршрутизирующий запись в нужную таблицу по имени агрегата.
2. Реализуйте структуры `OrderOutbox` и `UserOutbox`.
3. Организуйте независимые пулы опроса для каждого типа агрегата.
4. Докажите, что всплеск нагрузки в `orders_outbox` не замедляет обработку `users_outbox`.
5. Продемонстрируйте параллельную работу двух очередей в `main`.

## Код решения

**`outbox_per_aggregate.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type Event struct {
	ID        string
	Payload   string
	Processed bool
}

type DedicatedOutboxTable struct {
	name   string
	mu     sync.Mutex
	events []Event
}

func NewDedicatedTable(name string) *DedicatedOutboxTable {
	return &DedicatedOutboxTable{name: name}
}

func (t *DedicatedOutboxTable) Insert(id, payload string) {
	t.mu.Lock()
	defer t.mu.Unlock()
	t.events = append(t.events, Event{ID: id, Payload: payload})
	fmt.Printf("[%s] Inserted event %s\n", t.name, id)
}

func (t *DedicatedOutboxTable) PollAndProcess(workerID string) {
	t.mu.Lock()
	defer t.mu.Unlock()

	unprocessed := 0
	for i := range t.events {
		if !t.events[i].Processed {
			t.events[i].Processed = true
			unprocessed++
		}
	}
	if unprocessed > 0 {
		fmt.Printf("[%s Worker %s] Processed %d events independently.\n", t.name, workerID, unprocessed)
	}
}

func main() {
	// Две независимые таблицы для исключения contention
	ordersOutbox := NewDedicatedTable("orders_outbox")
	usersOutbox := NewDedicatedTable("users_outbox")

	var wg sync.WaitGroup
	wg.Add(2)

	// Симуляция одновременной активности
	go func() {
		defer wg.Done()
		ordersOutbox.Insert("ord-evt-1", "order 1 created")
		ordersOutbox.Insert("ord-evt-2", "order 2 paid")
		ordersOutbox.PollAndProcess("OrdersPoller-1")
	}()

	go func() {
		defer wg.Done()
		usersOutbox.Insert("usr-evt-1", "user registered")
		usersOutbox.PollAndProcess("UsersPoller-1")
	}()

	wg.Wait()
	fmt.Println("All dedicated outbox streams executed with zero cross-table lock contention.")
}
```

ℹ️ Шардирование таблиц Outbox по типам агрегатов для изоляции блокировок и масштабирования

**`output.txt`**

```bash
[orders_outbox] Inserted event ord-evt-1
[orders_outbox] Inserted event ord-evt-2
[users_outbox] Inserted event usr-evt-1
[orders_outbox Worker OrdersPoller-1] Processed 2 events independently.
[users_outbox Worker UsersPoller-1] Processed 1 events independently.
All dedicated outbox streams executed with zero cross-table lock contention.
```

ℹ️ Вывод: события разных сущностей обрабатываются в изолированных очередях

## Под капотом

На физическом уровне СУБД раздельные таблицы хранятся в разных файлах диска (different filenodes). Операции записи и коммита в `orders_outbox` не конкурируют за страницы оперативной памяти (Shared Buffers) и исключают блокировки на уровне страниц индексов B-Tree (Index Page Contention), позволяя ядрам процессора работать параллельно без ожидания spinlock.

## Подводные камни

1. Слишком мелкое дробление: создание отдельной таблицы под каждый подтип события приведет к тысячам открытых файловых дескрипторов и усложнению миграций СУБД.
2. Усложнение кода поллеров: вместо одного общего процесса требуется оркестрация нескольких пулов воркеров.

## На собеседовании

Вопрос: Когда следует переходить от единой таблицы Outbox к разделению по агрегатам?
Ответ: Когда мониторинг СУБД фиксирует `LWLock: buffer_mapping` или `Lock: tuple` на таблице `outbox`, а TPS (transactions per second) сервиса превышает 5,000–10,000. Разделение по агрегатам снимает бутылочное горлышко и позволяет масштабировать воркеры независимо.
