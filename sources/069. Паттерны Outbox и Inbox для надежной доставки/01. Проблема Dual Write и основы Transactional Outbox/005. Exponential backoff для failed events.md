# Exponential backoff для failed events: защита от перегрузки брокера и шторма ретраев

## Условие

5. **Exponential backoff для failed events**: Для events, которые fail repeatedly, используйте exponential backoff (не пытайтесь публиковать их каждые 100ms).

### Исходная формулировка

**Exponential backoff для failed events**: Для events, которые fail repeatedly, используйте exponential backoff (не пытайтесь публиковать их каждые 100ms).

## Теория

Если брокер сообщений (Kafka, RabbitMQ) испытывает перегрузку или кратковременно недоступен, а Outbox Poller будет долбить его запросами каждые 50–100 мс для каждой проблемной записи, возникает классический каскадный сбой (Thundering Herd / Retry Storm). Брокер окончательно падает под лавиной повторных запросов. Для устранения этой проблемы применяется алгоритм экспоненциальной задержки с джиттером (Exponential Backoff with Full Jitter): время паузы перед следующей попыткой вычисляется как \(T_{wait} = \min(T_{max}, T_{base} \times 2^{retry}) + \text{jitter}\). Количество попыток и время следующей попытки `next_attempt_at` персистируются в строке таблицы Outbox.

## Решение по шагам

1. Добавьте в схему Outbox поля `retry_count INT` и `next_attempt_at TIMESTAMP`.
2. Реализуйте функцию расчета экспоненциального интервала с ограничением максимума.
3. При сбое публикации обновляйте `retry_count = retry_count + 1` и сдвигайте `next_attempt_at`.
4. В выборку poller'а добавьте условие `WHERE next_attempt_at <= NOW()`.
5. Продемонстрируйте экспоненциальный рост пауз между попытками.

## Код решения

**`exponential_backoff.go`**

```go
package main

import (
	"fmt"
	"math"
	"math/rand"
	"time"
)

type OutboxRow struct {
	ID            int
	EventID       string
	RetryCount    int
	NextAttemptAt time.Time
}

// CalculateBackoff вычисляет интервал по формуле: min(maxBackoff, base * 2^retries) + jitter
func CalculateBackoff(retryCount int, base time.Duration, maxBackoff time.Duration) time.Duration {
	multiplier := math.Pow(2, float64(retryCount))
	backoff := time.Duration(float64(base) * multiplier)
	if backoff > maxBackoff {
		backoff = maxBackoff
	}

	// Full Jitter (рандомизация от 0 до backoff)
	jitter := time.Duration(rand.Int63n(int64(backoff/2 + 1)))
	return backoff + jitter
}

func HandleFailedPublish(row *OutboxRow) {
	row.RetryCount++
	delay := CalculateBackoff(row.RetryCount, 100*time.Millisecond, 10*time.Second)
	row.NextAttemptAt = time.Now().Add(delay)

	fmt.Printf("[Poller Retry] Event %s failed (Attempt %d). Next retry scheduled in %v (at %s)\n",
		row.EventID, row.RetryCount, delay.Round(time.Millisecond), row.NextAttemptAt.Format("15:04:05.000"))
}

func main() {
	rand.Seed(42) // Детерминированный сид для наглядности вывода
	row := &OutboxRow{ID: 1, EventID: "evt-fail-99"}

	fmt.Println("=== SIMULATING EXPONENTIAL BACKOFF ON REPEATED FAILURES ===")
	for attempt := 1; attempt <= 5; attempt++ {
		HandleFailedPublish(row)
	}
}
```

ℹ️ Расчет Exponential Backoff с Full Jitter для защиты брокера от шторма повторов

## Под капотом

Без джиттера (Jitter) все события, упавшие одновременно (например, при перезагрузке брокера), будут иметь синхронные интервалы \(2^n\) и придут на брокер ровно в одну миллисекунду, порождая регулярные спайки нагрузки (Resonance Effect). Добавление Full Jitter равномерно распределяет нагрузку во времени, сглаживая очередь сетевых запросов.

## Подводные камни

1. Задержка в памяти без персистенции `next_attempt_at`: если хранить задержку в `time.Sleep()`, то при падении воркера таймер сбросится, и после рестарта воркер снова начнет бомбардировать брокер.
2. Отсутствие Dead Letter Queue (DLQ): бесконечный backoff для безнадежно битого сообщения (Poison Pill) будет засорять таблицу Outbox вечно.

## На собеседовании

Вопрос: Почему важно ограничивать максимальный порог задержки `maxBackoff` (например, 30 или 60 секундами)?
Ответ: Если не ограничить backoff, то после 15–20 попыток задержка превысит несколько суток. Даже если сетевая проблема в брокере решилась за 5 минут, событие не будет отправлено еще неделю. Ограничение `maxBackoff` гарантирует разумное время реакции системы на восстановление инфраструктуры.
