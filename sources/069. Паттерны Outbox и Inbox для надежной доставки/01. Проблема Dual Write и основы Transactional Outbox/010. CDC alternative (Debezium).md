# CDC alternative (Debezium): стриминг Outbox-событий из WAL напрямую в Kafka без поллинга

## Условие

10. **CDC alternative (Debezium)**: Вместо poller используйте Debezium для CDC (Change Data Capture) из outbox table в Kafka. Debezium читает WAL/binlog и публикует changes.

### Исходная формулировка

**CDC alternative (Debezium)**: Вместо poller используйте Debezium для CDC (Change Data Capture) из outbox table в Kafka. Debezium читает WAL/binlog и публикует changes.

## Теория

Традиционный Polling Publisher (опрос базы через `SELECT ... FOR UPDATE SKIP LOCKED`) имеет недостатки: постоянные запросы к СУБД создают паразитную нагрузку на диск и CPU, а минимальная задержка (Latency) ограничена интервалом поллинга (100–500 мс). Change Data Capture (CDC) с использованием Debezium — это современный BigTech-стандарт. Debezium подключается к PostgreSQL как клиент логической репликации (Logical Decoding Plugin `pgoutput`), напрямую вычитывает журнал предзаписи (Write-Ahead Log / WAL) и с субмиллисекундной задержкой публикует строки из таблицы `outbox_events` в топики Apache Kafka. При этом база данных вообще не тратит ресурсы на выполнение SQL-запросов `SELECT` и `UPDATE`.

## Решение по шагам

1. Спроектируйте конфигурацию Debezium Outbox Event Router (Transform SMT).
2. Реализуйте структуру модели события для Debezium CDC.
3. Напишите эмулятор консьюмера событий, генерируемых Debezium из WAL.
4. Покажите, как SMT `io.debezium.transforms.outbox.EventRouter` извлекает `payload` и направляет его в топик по `aggregate_type`.
5. Продемонстрируйте обработку стрима изменений в `main`.

## Код решения

**`debezium_cdc_outbox.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

// DebeziumOutboxSMTConfig демонстрирует конфигурацию Kafka Connect Debezium Outbox Event Router
const DebeziumOutboxSMTConfig = `
{
  "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
  "plugin.name": "pgoutput",
  "database.hostname": "postgres-master",
  "database.dbname": "orders_db",
  "table.include.list": "public.outbox",
  "transforms": "outbox",
  "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
  "transforms.outbox.table.fields.additional.placement": "event_type:header:eventType",
  "transforms.outbox.route.topic.replacement": "${routedByValue}.events"
}
`

// DebeziumWALPayload эмулирует структуру CDC-события из WAL
type DebeziumWALPayload struct {
	Op        string          `json:"op"` // 'c' = Create (INSERT)
	Timestamp int64           `json:"ts_ms"`
	After     WALOutboxRecord `json:"after"`
}

type WALOutboxRecord struct {
	ID            string          `json:"id"`
	AggregateType string          `json:"aggregate_type"`
	AggregateID   string          `json:"aggregate_id"`
	EventType     string          `json:"event_type"`
	Payload       json.RawMessage `json:"payload"`
}

func ProcessDebeziumStream(rawWALEvent []byte) {
	var cdcMsg DebeziumWALPayload
	if err := json.Unmarshal(rawWALEvent, &cdcMsg); err != nil {
		fmt.Printf("Decode error: %v\n", err)
		return
	}

	if cdcMsg.Op == "c" {
		// Debezium Event Router автоматически маршрутизирует событие в Kafka
		topic := fmt.Sprintf("%s.events", cdcMsg.After.AggregateType)
		fmt.Printf("[Debezium CDC Engine] Captured INSERT from WAL!\n"+
			" -> Target Kafka Topic: %s\n"+
			" -> Kafka Record Key:  %s\n"+
			" -> Header EventType:   %s\n"+
			" -> Event Payload:      %s\n",
			topic, cdcMsg.After.AggregateID, cdcMsg.After.EventType, string(cdcMsg.After.Payload))
	}
}

func main() {
	fmt.Println("=== DEBEZIUM CDC OUTBOX ARCHITECTURE ===")

	// Симулируем сырое событие репликации WAL, вычитанное Debezium
	walJSON := `{
		"op": "c",
		"ts_ms": 1725621485000,
		"after": {
			"id": "c1f7-uuid-99",
			"aggregate_type": "Order",
			"aggregate_id": "ord-8812",
			"event_type": "OrderCreated",
			"payload": {"customer":"alice","amount":3200.0}
		}
	}`

	ProcessDebeziumStream([]byte(walJSON))
}
```

ℹ️ Стриминг изменений из WAL в Kafka с помощью Debezium Outbox Event Router SMT

## Под капотом

PostgreSQL Logical Decoding использует протокол потоковой репликации `walsender`. Debezium не опрашивает СУБД: сервер Postgres сам отправляет бинарные дельты изменений WAL через постоянное TCP-соединение. Модуль трансформации SMT (Single Message Transformation) распаковывает строку таблицы `outbox`, берет `aggregate_id` как ключ Kafka, кладет `payload` в тело сообщения и отбрасывает служебные метаданные, отправляя в топик чистый бизнес-ивент.

## Подводные камни

1. Переполнение диска слотом репликации (Replication Slot): если Debezium упадет или отключится, Postgres не сможет удалять сегменты WAL с диска, что при высоком RPS переполнит диск за считанные часы. Обязателен параметр `max_slot_wal_keep_size`.
2. Засорение таблицы Outbox: Debezium только читает события, но не удаляет их. Требуется периодический Sweeper.

## На собеседовании

Вопрос: Что лучше в продакшене: собственный Poller с `SKIP LOCKED` или Debezium CDC?
Ответ: Poller проще в разработке и развертывании (не требует Kafka Connect кластера и прав REPLICATION в БД). Однако при объемах выше 5,000 TPS Poller начинает создавать высокую утилизацию I/O и лаг. Debezium обеспечивает близкую к нулю задержку (<5 мс) и нулевую дополнительную нагрузку на дисковую подсистему СУБД.
