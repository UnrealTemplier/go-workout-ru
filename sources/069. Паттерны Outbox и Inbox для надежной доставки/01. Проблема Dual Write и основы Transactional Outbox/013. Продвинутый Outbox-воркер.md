## Теория

В высоконагруженных микросервисах (RPS > 10,000) единый последовательный Outbox Poller становится узким горлышком всей системы. Если один воркер успевает обрабатывать 500 сообщений в секунду, а сервис генерирует 5,000, в таблице Outbox накапливается колоссальный лаг. Продвинутая архитектура Outbox-воркера использует пул конкурентных воркеров (Worker Pool), каждый из которых работает в отдельной горутине или поде. Запрос `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 100` позволяет СУБД атомарно раздавать разные пакеты задач воркерам без ожидания и взаимоблокировок, обеспечивая линейное горизонтальное масштабирование.

## Решение по шагам

1. Спроектируйте структуру параллельного воркера `OutboxWorkerPool`.
2. Реализуйте функцию транзакционной вычитки `FetchAndLockBatch(ctx, limit)` с `SKIP LOCKED`.
3. Запустите 3 параллельных горутины воркеров с общим контекстом.
4. Продемонстрируйте, как 300 событий мгновенно разбираются тремя воркерами по 100 штук.
5. Реализуйте graceful shutdown пула воркеров.

## Код решения

**`advanced_skip_locked_worker.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type OutboxTask struct {
	ID      int
	Payload string
	Locked  bool
	Done    bool
}

type ThreadSafeOutboxRepository struct {
	mu    sync.Mutex
	tasks []*OutboxTask
}

func NewOutboxRepo(count int) *ThreadSafeOutboxRepository {
	repo := &ThreadSafeOutboxRepository{}
	for i := 1; i <= count; i++ {
		repo.tasks = append(repo.tasks, &OutboxTask{
			ID:      i,
			Payload: fmt.Sprintf("event-data-%03d", i),
		})
	}
	return repo
}

// FetchBatchSkipLocked эмулирует SQL SELECT ... FOR UPDATE SKIP LOCKED LIMIT batchSize
func (r *ThreadSafeOutboxRepository) FetchBatchSkipLocked(limit int) []*OutboxTask {
	r.mu.Lock()
	defer r.mu.Unlock()

	var batch []*OutboxTask
	for _, t := range r.tasks {
		if len(batch) >= limit {
			break
		}
		if !t.Done && !t.Locked {
			t.Locked = true
			batch = append(batch, t)
		}
	}
	return batch
}

func (r *ThreadSafeOutboxRepository) MarkBatchProcessed(batch []*OutboxTask) {
	r.mu.Lock()
	defer r.mu.Unlock()
	for _, t := range batch {
		t.Done = true
		t.Locked = false
	}
}

func worker(ctx context.Context, id int, repo *ThreadSafeOutboxRepository, counter *atomic.Int32, wg *sync.WaitGroup) {
	defer wg.Done()

	for {
		select {
		case <-ctx.Done():
			return
		default:
			batch := repo.FetchBatchSkipLocked(100)
			if len(batch) == 0 {
				return // Задачи исчерпаны
			}

			fmt.Printf("[Worker #%d] Claimed batch of %d tasks (First ID: %d, Last ID: %d)\n",
				id, len(batch), batch[0].ID, batch[len(batch)-1].ID)

			// Эмуляция отправки в брокер Kafka
			time.Sleep(30 * time.Millisecond)

			repo.MarkBatchProcessed(batch)
			counter.Add(int32(len(batch)))
		}
	}
}

func main() {
	totalTasks := 300
	repo := NewOutboxRepo(totalTasks)

	var totalProcessed atomic.Int32
	var wg sync.WaitGroup

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	fmt.Println("=== STARTING PARALLEL ADVANCED OUTBOX WORKER POOL ===")
	numWorkers := 3
	for w := 1; w <= numWorkers; w++ {
		wg.Add(1)
		go worker(ctx, w, repo, &totalProcessed, &wg)
	}

	wg.Wait()
	fmt.Printf("\n=== SUMMARY ===\nTotal outbox tasks processed: %d / %d across %d parallel workers!\n",
		totalProcessed.Load(), totalTasks, numWorkers)
}
```

## Под капотом

Запрос `SELECT id, payload FROM outbox_events WHERE status = 'pending' ORDER BY id ASC LIMIT 100 FOR UPDATE SKIP LOCKED` работает по B-Tree индексу. СУБД ставит эксклюзивную блокировку строки (`XMAX` в PostgreSQL). Если другой воркер обращается к СУБД в ту же миллисекунду, планировщик запросов Postgres мгновенно пропускает строки, заблокированные первым воркером, и начинает захват со 101-й строки. Время ожидания блокировки равно нулю.

## Подводные камни

1. Отсутствие сортировки `ORDER BY id ASC`: без детерминированного порядка воркеры будут хаотично захватывать строки из разных концов таблицы, что нарушит порядок событий и вызовет фрагментацию страниц.
2. Длинные сетевые операции внутри транзакции СУБД: если воркер удерживает транзакцию `BEGIN ... FOR UPDATE` во время медленного сетевого запроса к Kafka (3 секунды), он держит открытым соединение в PostgreSQL. Необходимо быстро вычитать и пометить `status = 'in_progress'`, закрыв транзакцию, либо настроить короткий тайм-аут.

## На собеседовании

Вопрос: Что произойдет с заблокированными строками `FOR UPDATE SKIP LOCKED`, если воркер упадет до коммита?
Ответ: Как только TCP-соединение воркера с PostgreSQL оборвется, СУБД автоматически откатит незавершенную транзакцию и снимет все блокировки строк. При следующем опросе любой другой свободный воркер снова увидит эти строки и возьмет их в обработку. Это гарантирует надежное самовосстановление системы.
