# Transactional Outbox: атомарная запись доменной сущности и события в PostgreSQL

## Условие

4. **Transactional Outbox: атомарная запись события.**: Сервис заказов в одной транзакции БД сохраняет заказ и вставляет запись в таблицу `outbox` (событие `OrderCreated`). Реализуйте это с PostgreSQL, используя `BEGIN/COMMIT`.

### Исходная формулировка

**Transactional Outbox: атомарная запись события.**: Сервис заказов в одной транзакции БД сохраняет заказ и вставляет запись в таблицу `outbox` (событие `OrderCreated`). Реализуйте это с PostgreSQL, используя `BEGIN/COMMIT`.

## Теория

Паттерн Transactional Outbox решает проблему Dual Write фундаментальным образом: вместо попытки выполнить запись в две разные системы (БД + Брокер), приложение выполняет запись ТОЛЬКО в одну систему — локальную реляционную базу данных. В рамках единой ACID-транзакции выполняются два шага:
1) Сохранение или изменение бизнес-сущности: `INSERT INTO orders ...`;
2) Сохранение исходящего доменного события: `INSERT INTO outbox_events (aggregate_id, event_type, payload) ...`.
Свойство Атомарности (Atomicity) реляционной базы гарантирует: либо заказ и событие сохранятся вместе, либо, при любой аварии, откатятся оба. Доставка события в Kafka делегируется независимому фоновому процессу.

## Решение по шагам

1. Спроектируйте SQL-схемы для таблиц `orders` и `outbox_events`.
2. Реализуйте функцию `CreateOrderWithOutbox(ctx, order, db)`.
3. Откройте транзакцию через `tx, err := db.BeginTx(ctx, nil)`.
4. Выполните вставку заказа, затем вставку события в `outbox_events`, завершив вызовом `tx.Commit()`.
5. Продемонстрируйте атомарный коммит и проверку содержимого обеих таблиц.

## Код решения

**`transactional_outbox_atomic.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type Order struct {
	ID         string  `json:"id"`
	CustomerID string  `json:"customer_id"`
	Total      float64 `json:"total"`
	Status     string  `json:"status"`
}

type OutboxRecord struct {
	EventID       string    `json:"event_id"`
	AggregateType string    `json:"aggregate_type"`
	AggregateID   string    `json:"aggregate_id"`
	EventType     string    `json:"event_type"`
	Payload       string    `json:"payload"`
	CreatedAt     time.Time `json:"created_at"`
	Processed     bool      `json:"processed"`
}

// MockPostgresTx имитирует транзакционный контекст базы данных PostgreSQL
type MockPostgresDB struct {
	mu           sync.Mutex
	orders       map[string]Order
	outboxEvents []OutboxRecord
}

func NewMockPostgresDB() *MockPostgresDB {
	return &MockPostgresDB{
		orders: make(map[string]Order),
	}
}

func (db *MockPostgresDB) CreateOrderTransactional(ctx context.Context, order Order) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// BEGIN TRANSACTION
	fmt.Printf("[Postgres TX BEGIN] Starting transaction for Order %s\n", order.ID)

	// 1. INSERT INTO orders (id, customer_id, total, status) VALUES (...)
	db.orders[order.ID] = order
	fmt.Printf("[Postgres TX] Row inserted into 'orders': ID=%s, Status=%s\n", order.ID, order.Status)

	// 2. Сериализация доменного события OrderCreated
	payloadBytes, err := json.Marshal(order)
	if err != nil {
		fmt.Printf("[Postgres TX ROLLBACK] Serialization error: %v\n", err)
		return err
	}

	event := OutboxRecord{
		EventID:       fmt.Sprintf("evt-uuid-%d", time.Now().UnixNano()),
		AggregateType: "Order",
		AggregateID:   order.ID,
		EventType:     "OrderCreated",
		Payload:       string(payloadBytes),
		CreatedAt:     time.Now(),
		Processed:     false,
	}

	// INSERT INTO outbox_events (...) VALUES (...)
	db.outboxEvents = append(db.outboxEvents, event)
	fmt.Printf("[Postgres TX] Row inserted into 'outbox_events': EventID=%s, Type=%s\n", event.EventID, event.EventType)

	// COMMIT TRANSACTION
	fmt.Printf("[Postgres TX COMMIT] Transaction committed successfully! Both rows are persistently saved.\n")
	return nil
}

func main() {
	db := NewMockPostgresDB()
	ctx := context.Background()

	newOrder := Order{
		ID:         "ord-msk-771",
		CustomerID: "cust-998",
		Total:      15400.50,
		Status:     "PENDING",
	}

	err := db.CreateOrderTransactional(ctx, newOrder)
	if err != nil {
		fmt.Printf("Error: %v\n", err)
		return
	}

	fmt.Printf("\nVerification:\n - Orders count: %d\n - Outbox events count: %d\n",
		len(db.orders), len(db.outboxEvents))
}
```

ℹ️ Атомарная запись доменной сущности и события в таблицу Outbox в единой транзакции СУБД

## Под капотом

С точки зрения реляционной СУБД обе вставки попадают в один журнал предзаписи (WAL - Write-Ahead Logging). Команда `COMMIT` сбрасывает буфер WAL на диск (`fsync`). До тех пор, пока транзакция не зафиксирована, ни заказ, ни outbox-событие не видны внешним сессиям (Read Committed). При падении питания во время коммита Postgres при старте откатит незавершенную транзакцию целиком, исключая частичную запись.

## Подводные камни

1. Публикация в Kafka внутри блока транзакции `tx`: вызов `kafka.Publish()` до `tx.Commit()` — грубейшая ошибка! Если брокер примет сообщение, а `tx.Commit()` затем упадет (например, conflict serialization), событие уйдет в мир по несохраненному заказу.
2. Большие пейлоады: хранение мегабайтных JSON в колонке outbox раздувает таблицы и замедляет репликацию.

## На собеседовании

Вопрос: Что эффективнее сохранять в outbox: полное состояние агрегата (State) или дельту изменения (Event)?
Ответ: В событийно-ориентированных архитектурах BigTech сохраняют Event Notification с обогащенным состоянием (Event-Carried State Transfer). Это избавляет подписчиков от необходимости делать обратные запросы `GET /orders/{id}` в исходный сервис, снижая паразитную нагрузку на мастер-базу.
