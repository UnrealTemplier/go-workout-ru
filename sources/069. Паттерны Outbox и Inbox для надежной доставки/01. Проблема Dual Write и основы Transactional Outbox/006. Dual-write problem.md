### Исходная формулировка

**Dual-write problem.**: Напишите код, который «сначала INSERT в БД, потом Publish в Kafka». Сымитируйте crash между двумя операциями. Покажите, что заказ создан, но событие не отправлено (или наоборот). Объясните, почему распределённые транзакции (XA) между БД и Kafka — антипаттерн.

## Теория

Имитация аварии процесса (Crash Simulation) наглядно раскрывает механику Dual Write. Любая компьютерная система подвержена трем типам сбоев: падение приложения (Crash), падение сети (Network Partition) и задержка ответа (Slow/Hanging dependency). Если код спроектирован как:
`1. db.InsertOrder()` -> `CRASH!` -> `2. kafka.Publish()`
то заказ физически сохранен в СУБД, но процесс умер до вызова Kafka. Попытка решить это через распределенные транзакции (XA Transactions / WS-AtomicTransaction) в современной микросервисной архитектуре признана антипаттерном: протокол XA требует удержания блокировок строк на обеих сторонах до получения фазы Commit, что при малейших сетевых задержках обрушивает RPS системы в тысячи раз и блокирует пул соединений.

## Решение по шагам

1. Реализуйте структуру `OrderService` с имитацией краха процесса через флаг `simulateCrash`.
2. Выполните коммит заказа в базу данных.
3. Сэмулируйте падение процесса (Panic / Return error) ровно перед вызовом продюсера.
4. Продемонстрируйте результат: заказ присутствует в БД, брокер пуст.
5. Проанализируйте архитектурные последствия инцидента.

## Код решения

**`crash_simulation_dual_write.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type MemoryDB struct {
	orders []string
}

func (db *MemoryDB) Insert(orderID string) {
	db.orders = append(db.orders, orderID)
	fmt.Printf("[DB Storage] Order %s saved and COMMITTED to storage.\n", orderID)
}

type KafkaBus struct {
	messages []string
}

func (k *KafkaBus) Send(event string) {
	k.messages = append(k.messages, event)
	fmt.Printf("[Kafka Bus] Event '%s' published to cluster.\n", event)
}

func CreateOrderVulnerable(db *MemoryDB, kafka *KafkaBus, orderID string, crashBeforeKafka bool) error {
	// Шаг 1: Запись в БД
	db.Insert(orderID)

	// Симуляция падения пода (SIGKILL / OOMKilled / Crash)
	if crashBeforeKafka {
		fmt.Println("[CRASH EVENT] >>> POD KILLED BY OOM-KILLER BEFORE KAFKA CALL! <<<")
		return errors.New("process terminated unexpectedly")
	}

	// Шаг 2: Отправка в Kafka
	kafka.Send(fmt.Sprintf("OrderCreated:%s", orderID))
	return nil
}

func main() {
	db := &MemoryDB{}
	kafka := &KafkaBus{}

	fmt.Println("=== ATTEMPTING ORDER CREATION WITH MID-FLIGHT CRASH ===")
	err := CreateOrderVulnerable(db, kafka, "order-999-crash", true)
	if err != nil {
		fmt.Printf("[Process Status] Crash handled: %v\n\n", err)
	}

	// Аудит состояния
	fmt.Printf("Audit Report:\n - Orders in DB: %v\n - Events in Kafka: %v\n", db.orders, kafka.messages)
	if len(db.orders) > 0 && len(kafka.messages) == 0 {
		fmt.Println("[FATAL DISCREPANCY] The order exists in DB, but Kafka never received it! Downstream services will starve.")
	}
}
```

ℹ️ Симуляция краха пода между записью в базу и отправкой в Kafka

## Под капотом

Антипаттерн XA в микросервисах терпит крах из-за блокирующей фазы Prepare: координатор транзакций посылает запрос `PREPARE` во все базы. Если координатор упадет после `PREPARE`, но до `COMMIT`, базы данных НЕ ИМЕЮТ ПРАВА снять блокировки со строк самостоятельно (In-Doubt State). В результате таблицы остаются заблокированными часами, требуя ручного вмешательства DBA.

## Подводные камни

1. Иллюзия надежности try-catch: никакой блок обработки ошибок не спасает от аварийного `SIGKILL` или обесточивания сервера.
2. Надежда на синхронный RPC: вызов HTTP/gRPC другого сервиса вместо брокера имеет точно такую же уязвимость Dual Write.

## На собеседовании

Вопрос: Почему именно Outbox стал индустриальным стандартом решения Dual Write вместо XA-транзакций?
Ответ: Потому что Outbox превращает распределенную задачу в строго локальную задачу СУБД. Локальные транзакции PostgreSQL/MySQL отработаны десятилетиями и обладают максимальной производительностью. А сетевая доставка выносится в асинхронный фоновый конвейер с гарантией At-Least-Once.
