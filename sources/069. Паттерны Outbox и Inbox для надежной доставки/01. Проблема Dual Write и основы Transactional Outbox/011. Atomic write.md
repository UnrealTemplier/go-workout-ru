# Atomic write: атомарное обновление доменных данных и вставка события в единой транзакции

## Условие

11. **Atomic write**: В одной транзакции обновляйте бизнес-данные и вставляйте event в outbox:
    ```go
    tx.Begin()
    tx.Exec("UPDATE orders SET status = 'paid' WHERE id = $1", orderID)
    tx.Exec("INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ($1, $2, $3)", orderID, "OrderPaid", payload)
    tx.Commit()
    ```

### Исходная формулировка

**Atomic write**: В одной транзакции обновляйте бизнес-данные и вставляйте event в outbox:
```go
tx.Begin()
tx.Exec("UPDATE orders SET status = 'paid' WHERE id = $1", orderID)
tx.Exec("INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ($1, $2, $3)", orderID, "OrderPaid", payload)
tx.Commit()
```

## Теория

Гарантия согласованности Outbox зиждется на одном постулате: любая мутация доменной модели (`INSERT`, `UPDATE`, `DELETE`) ОБЯЗАНА сопровождаться вставкой соответствующего события в таблицу `outbox` в рамках той же транзакции базы данных. Если разработчик обновит статус заказа (`UPDATE orders SET status = 'paid'`), но забудет вставить событие в `outbox`, либо сделает это в отдельной сессии БД, свойство атомарности будет нарушено. Применение паттерна Unit of Work или Repository-метода `Save(entity, events...)` гарантирует неразрывность этих двух операций.

## Решение по шагам

1. Реализуйте метод `MarkOrderAsPaid(ctx, orderID)` с использованием транзакции `database/sql`.
2. Выполните `UPDATE orders SET status = 'paid'`.
3. Выполните `INSERT INTO outbox (aggregate_id, event_type, payload)`.
4. Добавьте проверку `tx.Rollback()` в `defer` для перехвата любых ошибок.
5. Продемонстрируйте корректный коммит и консистентность обеих записей.

## Код решения

**`atomic_order_update.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"sync"
)

type InMemoryDBMock struct {
	mu           sync.Mutex
	orderStatus  map[string]string
	outboxEvents []string
}

func (db *InMemoryDBMock) AtomicPayOrder(ctx context.Context, orderID string, payload string) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Атомарное обновление бизнес-данных
	db.orderStatus[orderID] = "paid"
	fmt.Printf("[DB TX] Step 1: UPDATE orders SET status = 'paid' WHERE id = '%s'\n", orderID)

	// 2. Атомарная запись события в outbox
	eventRecord := fmt.Sprintf("OrderPaid:%s:%s", orderID, payload)
	db.outboxEvents = append(db.outboxEvents, eventRecord)
	fmt.Printf("[DB TX] Step 2: INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ('%s', 'OrderPaid', ...)\n", orderID)

	// 3. Коммит
	fmt.Printf("[DB TX COMMIT] Both operations successfully persisted atomically!\n")
	return nil
}

func main() {
	db := &InMemoryDBMock{
		orderStatus: map[string]string{"ord-555": "created"},
	}

	ctx := context.Background()
	payload := "{\"payment_method\":\"mir\",\"amount\":5400.0}"

	fmt.Println("=== EXECUTING ATOMIC BUSINESS WRITE + OUTBOX INSERT ===")
	_ = db.AtomicPayOrder(ctx, "ord-555", payload)

	fmt.Printf("\nFinal State:\n - Order Status: %s\n - Outbox Events: %v\n",
		db.orderStatus["ord-555"], db.outboxEvents)
}
```

ℹ️ Идиоматическое атомарное обновление сущности и создание outbox-события в одной транзакции

## Под капотом

В Go для надежного управления транзакцией используется канонический шаблон:
`tx, err := db.BeginTx(ctx, nil)`
`defer tx.Rollback()` // Безопасный rollback при панике или раннем выходе
`// ... запросы tx.ExecContext ...`
`return tx.Commit()` // Если Commit успешен, последующий Rollback в defer вернет sql.ErrTxDone и будет проигнорирован.

## Подводные камни

1. Забытый `defer tx.Rollback()`: при возникновении паники или возврате ошибки до коммита соединение останется в 'подвешенной' транзакции, блокируя пул соединений.
2. Выполнение запросов через `db.Exec` вместо `tx.Exec`: распространенная опечатка, из-за которой запрос выполняется вне транзакции.

## На собеседовании

Вопрос: Что произойдет, если база данных вернет `Serialization Error (40001)` при попытке коммита транзакции?
Ответ: Вся транзакция откатится, включая и обновление заказа, и запись в outbox. Приложение обязано перехватить код ошибки 40001 и повторить выполнение всей транзакции целиком с экспоненциальным backoff. Консистентность не нарушается, так как частичных записей не происходит.
