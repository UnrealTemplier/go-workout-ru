# Polling strategy: конкурентный опрос Outbox через SELECT FOR UPDATE SKIP LOCKED

## Условие

2. **Polling strategy**: Используйте `SELECT ... FOR UPDATE SKIP LOCKED` для конкурентного polling без блокировок.

### Исходная формулировка

**Polling strategy**: Используйте `SELECT ... FOR UPDATE SKIP LOCKED` для конкурентного polling без блокировок.

## Теория

При реализации паттерна Polling Publisher (Outbox Poller) фоновые воркеры опрашивают таблицу outbox для вычитки необработанных событий. Если запущено несколько реплик воркера (горизонтальное масштабирование), наивный запрос `SELECT * FROM outbox WHERE processed = false LIMIT 50` приведет к тому, что все воркеры выберут одни и те же строки. Стандартный `FOR UPDATE` заблокирует второй воркер до завершения первого, создавая сериализацию и блокировки. Решение корпоративного уровня — использование конструкции `SELECT ... FOR UPDATE SKIP LOCKED`. Она указывает СУБД моментально пропускать любые строки, которые уже заблокированы другими параллельными транзакциями. Это обеспечивает параллельную обработку пачек без ожидания и без состояния гонки.

## Решение по шагам

1. Опишите схему таблицы Outbox со статусом обработки `is_locked`.
2. Смоделируйте конкурентную выборку `SKIP LOCKED` через эмуляцию транзакционных локов строк.
3. Запустите два параллельных воркера (Worker A и Worker B).
4. Докажите, что воркер B мгновенно получает непересекающуюся порцию данных, пропуская строки воркера A.
5. Продемонстрируйте параллельную обработку в `main`.

## Код решения

**`skip_locked_polling.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxMessage struct {
	ID        int
	Payload   string
	Processed bool
	LockedBy  string // Эмуляция row-level блокировки FOR UPDATE
}

type MockOutboxTable struct {
	mu   sync.Mutex
	rows []*OutboxMessage
}

func NewMockOutboxTable() *MockOutboxTable {
	table := &MockOutboxTable{}
	for i := 1; i <= 6; i++ {
		table.rows = append(table.rows, &OutboxMessage{
			ID:      i,
			Payload: fmt.Sprintf("order-event-#%d", i),
		})
	}
	return table
}

// SelectForUpdateSkipLocked эмулирует поведение SQL SELECT ... FOR UPDATE SKIP LOCKED LIMIT batchSize
func (t *MockOutboxTable) SelectForUpdateSkipLocked(workerID string, batchSize int) []*OutboxMessage {
	t.mu.Lock()
	defer t.mu.Unlock()

	var selected []*OutboxMessage
	for _, row := range t.rows {
		if len(selected) >= batchSize {
			break
		}
		// Пропускаем обработанные или заблокированные другими воркерами строки (SKIP LOCKED)
		if !row.Processed && row.LockedBy == "" {
			row.LockedBy = workerID
			selected = append(selected, row)
		}
	}
	return selected
}

func (t *MockOutboxTable) CommitBatch(workerID string, msgs []*OutboxMessage) {
	t.mu.Lock()
	defer t.mu.Unlock()
	for _, m := range msgs {
		m.Processed = true
		m.LockedBy = ""
		fmt.Printf("[DB COMMIT] Worker %s committed row ID=%d as PROCESSED\n", workerID, m.ID)
	}
}

func runWorker(ctx context.Context, id string, table *MockOutboxTable, wg *sync.WaitGroup) {
	defer wg.Done()
	// Захват батча из 3 строк с пропуском заблокированных
	batch := table.SelectForUpdateSkipLocked(id, 3)
	fmt.Printf("[Worker %s] Selected %d rows: ", id, len(batch))
	for _, m := range batch {
		fmt.Printf("ID=%d ", m.ID)
	}
	fmt.Println()

	// Эмуляция сетевой отправки в Kafka
	time.Sleep(50 * time.Millisecond)

	// Завершение транзакции и коммит
	table.CommitBatch(id, batch)
}

func main() {
	table := NewMockOutboxTable()
	var wg sync.WaitGroup
	wg.Add(2)

	fmt.Println("=== CONCURRENT POLLING WITH SKIP LOCKED ===")
	// Запуск двух параллельных воркеров
	go runWorker(context.Background(), "Worker-ALPHA", table, &wg)
	go runWorker(context.Background(), "Worker-BETA", table, &wg)

	wg.Wait()
	fmt.Println("=== ALL OUTBOX EVENTS PROCESSED CONCURRENTLY WITH ZERO CONFLICTS ===")
}
```

ℹ️ Конкурентный опрос таблицы Outbox несколькими воркерами через SKIP LOCKED

## Под капотом

В PostgreSQL механизм `SKIP LOCKED` работает на уровне MVCC и блокировок кортежей (Tuple Locks). Когда транзакция встречает кортеж с флагом `HEAP_XMAX_COMMITTED` или активной блокировкой другого backend, сканер индекса/таблицы не ждет освобождения лока (в отличие от обычного `FOR UPDATE`), а мгновенно переходит к следующей записи. Это полностью исключает Deadlocks между воркерами на уровне СУБД.

## Подводные камни

1. Запрос `SKIP LOCKED` без `LIMIT`: воркер заблокирует абсолютно все строки в таблице, лишив смысла параллелизацию.
2. Опрос без частичного индекса: запрос `WHERE processed = false` обязан поддерживаться частичным индексом `CREATE INDEX ON outbox(id) WHERE processed = false`, иначе база будет делать Seq Scan.

## На собеседовании

Вопрос: Почему `SKIP LOCKED` лучше использования хэш-шардирования (`WHERE id % 4 = worker_id`)?
Ответ: Хэш-шардирование статично: если один воркер зависнет или упадет, его четверть сообщений застрянет в очереди, в то время как другие воркеры будут простаивать. `SKIP LOCKED` реализует динамическую балансировку (Work Stealing): живые воркеры мгновенно разбирают доступную работу пропорционально своей скорости.
