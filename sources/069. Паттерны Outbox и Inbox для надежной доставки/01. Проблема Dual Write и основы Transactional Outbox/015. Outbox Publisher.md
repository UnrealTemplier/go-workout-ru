# Outbox Publisher: ретранслятор событий с гарантией доставки At-Least-Once

## Условие

15. **Outbox Publisher (ретранслятор событий).**: Напишите фоновый процесс (горутина), который читает неотправленные записи из `outbox`, публикует их в брокер (Kafka/RabbitMQ) и помечает как отправленные в БД. Гарантируйте at-least-once семантику.

### Исходная формулировка

**Outbox Publisher (ретранслятор событий).**: Напишите фоновый процесс (горутина), который читает неотправленные записи из `outbox`, публикует их в брокер (Kafka/RabbitMQ) и помечает как отправленные в БД. Гарантируйте at-least-once семантику.

## Теория

Outbox Publisher (ретранслятор) — это связующий мост между базой данных и брокером сообщений. Для обеспечения строгой семантики At-Least-Once ретранслятор соблюдает золотое правило последовательности:
1) Прочитать неотправленную запись из базы;
2) Отправить сообщение в брокер и дождаться подтверждения (Broker ACK);
3) И ТОЛЬКО ПОСЛЕ подтверждения от брокера обновить запись в БД: `UPDATE outbox SET processed = true`.
Если ретранслятор упадет на шаге 1 — ничего не отправлено. Если упадет на шаге 2 — брокер не подтвердил запись. Если упадет между шагом 2 и 3 — сообщение в брокер уже ушло, но статус в базе остался `false`. После перезапуска ретранслятор повторит отправку. Сообщение может быть продублировано, но НИКОГДА не будет потеряно (No Message Loss Guarantee).

## Решение по шагам

1. Создайте структуру `RelayMessage` со статусом `Processed`.
2. Реализуйте метод `PublishAndAcknowledge(msg)`.
3. Симулируйте сетевой сбой подтверждения коммита в БД.
4. Докажите, что при перезапуске ретранслятор повторно отправляет сообщение, подтверждая At-Least-Once.
5. Продемонстрируйте логирование жизненного цикла события.

## Код решения

**`at_least_once_relay.go`**

```go
package main

import (
	"context"
	"fmt"
)

type OutboxEntry struct {
	ID        string
	Topic     string
	Payload   string
	Processed bool
}

type KafkaBroker struct {
	receivedMessages []string
}

func (k *KafkaBroker) Send(topic, payload string) error {
	k.receivedMessages = append(k.receivedMessages, payload)
	fmt.Printf("[Kafka Broker ACK] Accepted message for topic '%s': %s\n", topic, payload)
	return nil
}

type EventRelay struct {
	db     []*OutboxEntry
	broker *KafkaBroker
}

func (r *EventRelay) RelayNext(crashAfterPublish bool) {
	for _, entry := range r.db {
		if entry.Processed {
			continue
		}

		fmt.Printf("[Relay] Found unprocessed Outbox Entry %s\n", entry.ID)

		// 1. Отправка в брокер с ожиданием ACK
		err := r.broker.Send(entry.Topic, entry.Payload)
		if err != nil {
			fmt.Printf("[Relay ERROR] Broker send failed: %v\n", err)
			return
		}

		// Симуляция падения процесса до коммита в БД
		if crashAfterPublish {
			fmt.Println("[CRASH] Relay process died before updating DB status!")
			return
		}

		// 2. Пометка в БД как отправленное
		entry.Processed = true
		fmt.Printf("[Relay DB] Entry %s marked as PROCESSED\n", entry.ID)
	}
}

func main() {
	broker := &KafkaBroker{}
	entry := &OutboxEntry{
		ID:        "evt-relay-01",
		Topic:     "billing-events",
		Payload:   "{\"invoice_id\":9901}",
		Processed: false,
	}

	relay := &EventRelay{
		db:     []*OutboxEntry{entry},
		broker: broker,
	}

	// Итерация 1: Отправка прошла, но процесс упал до коммита в БД
	fmt.Println("=== ITERATION 1: Publish succeeds, but DB commit crashes ===")
	relay.RelayNext(true)

	// Итерация 2: Рестарт ретранслятора
	fmt.Println("\n=== ITERATION 2: Relay restarts and re-processes uncommitted entry ===")
	relay.RelayNext(false)

	fmt.Printf("\nBroker Total Messages Received: %d\n", len(broker.receivedMessages))
	fmt.Println("Result: Exactly At-Least-Once! Message was duplicated in broker, but NEVER lost.")
}
```

ℹ️ Ретранслятор событий Outbox с гарантией отсутствия потерь сообщений (At-Least-Once)

## Под капотом

Принцип At-Least-Once гарантирует математическую полноту множества доставленных событий: \(S_{\text{delivered}} \supseteq S_{\text{committed}}\). Ни одно зафиксированное в БД событие не может быть пропущено. Дублирование на сетевом уровне считается нормальным поведением распределенной системы, ответственность за дедупликацию возлагается на Transactional Inbox на стороне подписчика.

## Подводные камни

1. Изменение порядка (пометка `processed = true` ДО отправки в Kafka): если сначала пометить строку как обработанную, а отправка упадет, событие будет потеряно навсегда (At-Most-Once / Data Loss).
2. Игнорирование таймаутов брокера: сетевой вызов в брокер обязан иметь строгий контекстный тайм-аут.

## На собеседовании

Вопрос: Почему в архитектуре надежных платежей выбирают At-Least-Once, а не At-Most-Once?
Ответ: При At-Most-Once сообщение теряется безвозвратно — клиент оплатил заказ, но система не зафиксировала оплату. При At-Least-Once сообщение доставляется повторно, но благодаря ключу идемпотентности консьюмер просто отфильтрует дубликат. At-Least-Once в сочетании с идемпотентностью обеспечивает прикладной Exactly-Once.
