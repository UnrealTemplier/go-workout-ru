## Теория

Функция создания заказа `CreateOrder` со встроенным Transactional Outbox — эталонный кирпичик надежной микросервисной архитектуры. Ключевые инженерные принципы реализации:
1) Передача `context.Context` во все вызовы `BeginTx`, `ExecContext`, `Commit`;
2) Использование `defer tx.Rollback()`: гарантирует закрытие транзакции в случае непредвиденных паник;
3) Сериализация заказа в канонический JSONB в памяти приложения до выполнения запросов;
4) Генерация детерминированного `event_id` и заполнение `aggregate_id = order.ID`;
5) Возврат понятной доменной ошибки при сбое любого из шагов.
Такой подход превращает распределенный риск потери данных в надежную локальную ACID-транзакцию.

## Решение по шагам

1. Опишите сигнатуру функции `CreateOrder(ctx context.Context, db *sql.DB, order Order) error`.
2. Откройте транзакцию с проверкой ошибки.
3. Выполните `INSERT INTO orders`.
4. Выполните `INSERT INTO outbox_events` со статусом `PENDING`.
5. Вызовите `tx.Commit()` и подтвердите 100% гарантию целостности.

## Код решения

**`create_order_atomic_outbox.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"sync"
	"time"
)

type CustomerOrder struct {
	ID        string  `json:"id"`
	UserID    string  `json:"user_id"`
	TotalCost float64 `json:"total_cost"`
	Status    string  `json:"status"`
}

type OutboxRow struct {
	EventID   string
	OrderID   string
	Status    string
	Payload   string
	CreatedAt time.Time
}

type EnterpriseDatabaseMock struct {
	mu           sync.Mutex
	orders       map[string]CustomerOrder
	outboxEvents map[string]OutboxRow
}

func NewEnterpriseDB() *EnterpriseDatabaseMock {
	return &EnterpriseDatabaseMock{
		orders:       make(map[string]CustomerOrder),
		outboxEvents: make(map[string]OutboxRow),
	}
}

// CreateOrder демонстрирует каноническую транзакционную функцию
func (db *EnterpriseDatabaseMock) CreateOrder(ctx context.Context, order CustomerOrder) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// Шаг 1: Проверка контекста
	if err := ctx.Err(); err != nil {
		return err
	}

	// Сериализация заказа для полезной нагрузки события
	payloadBytes, err := json.Marshal(order)
	if err != nil {
		return fmt.Errorf("marshal order payload: %w", err)
	}

	// BEGIN TRANSACTION
	fmt.Printf("[SQL BEGIN] Starting ACID transaction for Order %s\n", order.ID)

	// Шаг 2: INSERT INTO orders (id, user_id, total_cost, status)
	db.orders[order.ID] = order
	fmt.Printf("[SQL EXEC] INSERT INTO orders (id, user_id, total_cost, status) VALUES ('%s', '%s', %.2f, '%s')\n",
		order.ID, order.UserID, order.TotalCost, order.Status)

	// Шаг 3: INSERT INTO outbox_events (status='PENDING', payload=...)
	eventID := fmt.Sprintf("evt-%s", order.ID)
	outboxEntry := OutboxRow{
		EventID:   eventID,
		OrderID:   order.ID,
		Status:    "PENDING",
		Payload:   string(payloadBytes),
		CreatedAt: time.Now(),
	}
	db.outboxEvents[eventID] = outboxEntry
	fmt.Printf("[SQL EXEC] INSERT INTO outbox_events (event_id, order_id, status, payload) VALUES ('%s', '%s', 'PENDING', ...)\n",
		eventID, order.ID)

	// COMMIT
	fmt.Println("[SQL COMMIT] Transaction committed with 100% consistency guarantee!")
	return nil
}

func main() {
	db := NewEnterpriseDB()
	ctx := context.Background()

	order := CustomerOrder{
		ID:        "ord-uuid-2026-msk",
		UserID:    "user-victor-77",
		TotalCost: 18900.00,
		Status:    "CREATED",
	}

	fmt.Println("=== EXECUTING CREATE ORDER WITH TRANSACTIONAL OUTBOX ===")
	err := db.CreateOrder(ctx, order)
	if err != nil {
		fmt.Printf("Error: %v\n", err)
		return
	}

	fmt.Printf("\nVerification:\n - Order persisted: %s (Total: %.2f)\n - Outbox Event: %s (Status: %s)\n",
		db.orders[order.ID].ID, db.orders[order.ID].TotalCost,
		db.outboxEvents["evt-"+order.ID].EventID, db.outboxEvents["evt-"+order.ID].Status)
}
```

## Под капотом

На уровне WAL-журнала PostgreSQL обе операции `INSERT` связываются одним идентификатором транзакции (XID). Запись фиксируется на диск атомарно. Если сервер отключится от питания прямо во время выполнения `tx.Commit()`, восстановление после сбоя (Crash Recovery) применит правило REDO/UNDO: если чекпоинт коммита есть в WAL — обе строки появятся в таблицах; если чекпоинта нет — обе строки будут стерты без следа.

## Подводные камни

1. Вызов внешних сетевых сервисов внутри транзакции: сетевые вызовы удерживают лок строк и пул соединений СУБД, снижая пропускную способность сервиса.
2. Разделение на две независимые транзакции: `tx1.Commit()` для заказа и `tx2.Commit()` для outbox разрушают атомарность и возвращают систему к проблеме Dual Write.

## На собеседовании

Вопрос: Как убедиться, что транзакционный Outbox не создает задержки для пользователя при ответе на HTTP-запрос?
Ответ: Запись в таблицу `outbox_events` — это быстрый локальный `INSERT` в память/WAL СУБД, занимающий менее 1 миллисекунды. Сразу после коммита клиент получает `HTTP 201 Created` или `202 Accepted`. Вся тяжелая сетевая работа по передаче сообщения в брокер вынесена в асинхронный фоновый поток, благодаря чему задержка ответа клиенту минимальна.
