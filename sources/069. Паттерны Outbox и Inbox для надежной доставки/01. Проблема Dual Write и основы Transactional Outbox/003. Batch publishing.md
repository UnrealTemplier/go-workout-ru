# Batch publishing: пакетная вычитка и публикация событий в брокер для максимального Throughput

## Условие

3. **Batch publishing**: Poller читает batch events (например, 100) и публикует их в Kafka одним batch для эффективности.

### Исходная формулировка

**Batch publishing**: Poller читает batch events (например, 100) и публикует их в Kafka одним batch для эффективности.

## Теория

Построчная публикация каждого события из Outbox (Single Message Publishing) в условиях HighLoad крайне неэффективна: отправка 10,000 событий по одному требует 10,000 сетевых раунд-трипов к брокеру, что ограничивает пропускную способность сотнями сообщений в секунду из-за RTT. Паттерн Batch Publishing объединяет чтение и отправку в пакеты (например, по 100–500 событий): 1) Poller за один SQL-запрос считывает пачку `LIMIT 100`; 2) Пакет отправляется в брокер одним составным сетевым запросом (Kafka Produce Batch Request); 3) После подтверждения всех сообщений пакета от брокера (Leader Ack) в СУБД выполняется один пакетный `UPDATE outbox SET processed = true WHERE id IN (...)`. Это поднимает RPS в десятки раз.

## Решение по шагам

1. Создайте структуру события `EventRecord` с полезной нагрузкой.
2. Реализуйте метод `FetchBatch(limit int)` для выборки массива событий.
3. Реализуйте метод `PublishBatch(events []*EventRecord)` с пакетной отправкой в Kafka Producer.
4. Выполните пакетный коммит статуса `processed = true` через `WHERE id = ANY(...)`.
5. Продемонстрируйте замер производительности пакетной публикации.

## Код решения

**`batch_publishing.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type OutboxItem struct {
	ID        int
	Topic     string
	Payload   string
	Processed bool
}

type KafkaBatchProducerMock struct{}

func (k *KafkaBatchProducerMock) ProduceBatch(items []*OutboxItem) error {
	// Эмуляция единого сетевого запроса ProduceRequest с компрессией (Snappy/zstd)
	fmt.Printf("[Kafka Broker] Received Produce Batch of %d records in a single network round-trip!\n", len(items))
	return nil
}

type BatchPoller struct {
	storage  []*OutboxItem
	producer *KafkaBatchProducerMock
}

func (p *BatchPoller) ProcessNextBatch(ctx context.Context, batchSize int) int {
	var batch []*OutboxItem
	for _, item := range p.storage {
		if !item.Processed {
			batch = append(batch, item)
			if len(batch) >= batchSize {
				break
			}
		}
	}

	if len(batch) == 0 {
		return 0
	}

	// 1. Пакетная отправка в брокер
	start := time.Now()
	_ = p.producer.ProduceBatch(batch)

	// 2. Пакетное обновление статуса в базе (эмуляция UPDATE outbox SET processed = true WHERE id = ANY($1))
	for _, item := range batch {
		item.Processed = true
	}
	fmt.Printf("[Outbox DB] Batch of %d records marked as PROCESSED in %v\n", len(batch), time.Since(start))
	return len(batch)
}

func main() {
	var items []*OutboxItem
	for i := 1; i <= 100; i++ {
		items = append(items, &OutboxItem{
			ID:      i,
			Topic:   "payment-events",
			Payload: fmt.Sprintf("{\"charge_id\":%d}", i),
		})
	}

	poller := &BatchPoller{
		storage:  items,
		producer: &KafkaBatchProducerMock{},
	}

	fmt.Println("=== EXECUTING BATCH PUBLISHING ===")
	processed := poller.ProcessNextBatch(context.Background(), 100)
	fmt.Printf("Total processed in batch: %d events.\n", processed)
}
```

ℹ️ Пакетная вычитка и отправка событий в брокер для оптимизации сетевого обмена

**`output.txt`**

```bash
=== EXECUTING BATCH PUBLISHING ===
[Kafka Broker] Received Produce Batch of 100 records in a single network round-trip!
[Outbox DB] Batch of 100 records marked as PROCESSED in 1.2ms
Total processed in batch: 100 events.
```

ℹ️ 100 сообщений переданы за один сетевой вызов с минимальными накладными расходами

## Под капотом

В сетевом протоколе Kafka Produce API пакет сообщений сжимается единым блоком (RecordBatch) с использованием zstd или Snappy. Сжатие целого батча дает коэффициент компрессии до 80%, так как JSON-структуры событий содержат много повторяющихся ключей. Пакетный `UPDATE ... WHERE id = ANY($1)` выполняется в PostgreSQL за единичный цикл обращения к WAL.

## Подводные камни

1. Слишком большой размер батча: батч на 10,000 записей может превысить лимит `max.request.size` брокера Kafka (по умолчанию 1 МБ), и запрос будет отклонен `RecordTooLargeException`.
2. Частичный сбой батча: если из 100 сообщений упало одно, простой код может пометить все 100 как необработанные, что вызовет повторную отправку первых 99 сообщений (дубликаты).

## На собеседовании

Вопрос: Что делать, если при пакетной публикации 99 сообщений доставлены, а 100-е вернуло ошибку партиции?
Ответ: Современные продюсеры Kafka (например, `confluent-kafka-go` или `segmentio/kafka-go`) возвращают индивидуальные Delivery Report по каждому сообщению в батче. Poller должен помечать `processed = true` ТОЛЬКО для тех `id`, чей delivery status завершился успехом, а неудавшееся сообщение оставлять для повтора.
