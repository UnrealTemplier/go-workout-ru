# Debezium setup: настройка коннектора к PostgreSQL и семантика At-Least-Once

## Условие

### Исходная формулировка

**Debezium setup**: Настройте Debezium connector для PostgreSQL outbox table. Изучите at-least-once semantics.

## Теория

Интеграция Debezium с PostgreSQL требует конфигурирования через REST API Kafka Connect. Ключевые параметры коннектора:
1) `plugin.name: pgoutput` — использование стандартного плагина логического декодирования Postgres (встроен в PG 10+);
2) `slot.name: debezium_outbox_slot` — именованный слот репликации в СУБД;
3) `publication.name: dbz_publication` — подписка на публикацию Postgres (`CREATE PUBLICATION dbz_publication FOR TABLE outbox;`);
4) `tombstones.on.delete: false` — запрет отправки нулевых payload при удалении строк.
Семантика доставки: Debezium гарантирует доставку класса **At-Least-Once**. Если коннектор упадет, после перезапуска он возобновит чтение WAL с последней подтвержденной позиции (LSN), что приведет к повторной отправке событий, не закоммиченных в Kafka. Потребители обязаны быть идемпотентными.

## Решение по шагам

1. Составьте конфигурационный JSON для регистрации коннектора Debezium.
2. Опишите команды инициализации PostgreSQL (`wal_level = logical`, `CREATE PUBLICATION`).
3. Реализуйте симуляцию повторной отправки (At-Least-Once delivery) при падении Debezium воркера.
4. Продемонстрируйте дедупликацию сообщений по `id` на стороне консьюмера.
5. Проанализируйте работу механизма в `main`.

## Код решения

**`debezium_setup_config.go`**

```go
package main

import (
	"fmt"
	"sync"
)

// SQL скрипт подготовки PostgreSQL для Debezium:
const PostgresInitScript = `
-- 1. Включение логической репликации в postgresql.conf:
-- wal_level = logical
-- max_wal_senders = 10
-- max_replication_slots = 10

-- 2. Создание публикации для таблицы outbox
CREATE PUBLICATION dbz_outbox_pub FOR TABLE outbox;
`

type ConsumerWithDeduplication struct {
	mu            sync.Mutex
	processedUIDs map[string]bool
	successCount  int
}

func (c *ConsumerWithDeduplication) HandleEvent(eventID, payload string) {
	c.mu.Lock()
	defer c.mu.Unlock()

	// Защита от At-Least-Once дублей Debezium
	if c.processedUIDs[eventID] {
		fmt.Printf("[Consumer DEDUP] Event %s already processed. Ignoring duplicate delivery!\n", eventID)
		return
	}

	c.processedUIDs[eventID] = true
	c.successCount++
	fmt.Printf("[Consumer ACTION] Event %s processed successfully: %s\n", eventID, payload)
}

func main() {
	fmt.Println("=== POSTGRESQL CONFIGURATION FOR DEBEZIUM ===")
	fmt.Println(PostgresInitScript)

	consumer := &ConsumerWithDeduplication{processedUIDs: make(map[string]bool)}

	eventID := "evt-unique-uuid-101"
	payload := "{\"order_id\":\"ord-77\",\"status\":\"confirmed\"}"

	// Первая доставка события коннектором Debezium
	fmt.Println("--- Delivery Attempt 1 (Normal Stream) ---")
	consumer.HandleEvent(eventID, payload)

	// Сбой воркера Kafka Connect и перезапуск -> повторная отправка того же LSN (At-Least-Once)
	fmt.Println("\n--- Delivery Attempt 2 (Debezium Replay after Crash) ---")
	consumer.HandleEvent(eventID, payload)

	fmt.Printf("\nTotal unique events executed: %d (Expected: 1)\n", consumer.successCount)
}
```

## Под капотом

Слот репликации (`pg_replication_slots`) хранит значение `confirmed_flush_lsn`. Debezium сдвигает LSN в Postgres только после того, как Kafka вернет подтверждение (Producer Ack) на запись батча. Если Kafka Connect упадет посреди отправки, LSN в Postgres останется старым, и при старте коннектор начнет чтение с неотправленного места. Это математически гарантирует отсутствие потерь, но неизбежно порождает дубликаты на границе сбоя.

## Подводные камни

1. Неверная настройка `wal_level`: если в `postgresql.conf` оставить дефолтный `wal_level = replica`, Debezium не сможет декодировать изменения и упадет с ошибкой при запуске.
2. Создание публикации `FOR ALL TABLES`: публикация всех таблиц перегрузит коннектор служебным трафиком.

## На собеседовании

Вопрос: Почему ни одна распределенная система на базе Debezium и Kafka не может гарантировать Exactly-Once без дедупликации на консьюмере?
Ответ: По теореме FLP и фундаментальным свойствам двухгенерального протокола, в условиях ненадежной сети невозможно отличить упавший сетевой пакет подтверждения (Ack) от упавшего процесса. Поэтому брокеры гарантируют At-Least-Once. Exactly-Once достигается только в связке: `At-Least-Once Delivery + Idempotent Processing (Inbox/Unique Constraint)`.
