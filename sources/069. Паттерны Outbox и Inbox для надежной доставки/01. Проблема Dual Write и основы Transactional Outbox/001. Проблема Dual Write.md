# Проблема Dual Write: рассинхронизация реляционной БД и брокера сообщений

## Условие

1. **Проблема dual write**: Покажите проблему: `db.UpdateOrder()` + `kafka.Publish(OrderUpdated)` — если Kafka unavailable, БД обновлена, но event не отправлен. Inconsistency.

### Исходная формулировка

**Проблема dual write**: Покажите проблему: `db.UpdateOrder()` + `kafka.Publish(OrderUpdated)` — если Kafka unavailable, БД обновлена, но event не отправлен. Inconsistency.

## Теория

Проблема двойной записи (Dual Write Problem) — фундаментальная уязвимость распределенных систем. Она возникает всякий раз, когда приложению необходимо атомарно изменить состояние двух независимых хранилищ: например, зафиксировать изменение строки в PostgreSQL и опубликовать доменное событие в Apache Kafka. Поскольку локальная транзакция СУБД и сетевой вызов в брокер не объединены общим координатором транзакций, любой сетевой сбой, аварийное завершение процесса (SIGKILL, OOM, падение ноды) или недоступность брокера между шагом 1 (`db.Commit()`) и шагом 2 (`kafka.Publish()`) приводит к системной рассинхронизации: заказ в базе данных обновлен, но downstream-сервисы (биллинг, склад, аналитика) никогда не узнают об этом.

## Решение по шагам

1. Создайте структуру хранилища заказов с методом `UpdateOrder`.
2. Создайте структуру `KafkaClientMock` с эмуляцией временного или постоянного сбоя сети.
3. Реализуйте наивную функцию `NaiveUpdateOrderAndPublish`, выполняющую сначала коммит в БД, а затем сетевую отправку в Kafka.
4. Сымитируйте сбой брокера и продемонстрируйте факт разрушения согласованности (Database modified, Event lost).
5. Продемонстрируйте логирование ошибки в консоли.

## Код решения

**`dual_write_problem.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

type Order struct {
	ID     string
	Status string
}

type OrderDatabase struct {
	mu     sync.Mutex
	orders map[string]Order
}

func (db *OrderDatabase) UpdateOrderStatus(id, newStatus string) error {
	db.mu.Lock()
	defer db.mu.Unlock()
	order, exists := db.orders[id]
	if !exists {
		return errors.New("order not found")
	}
	order.Status = newStatus
	db.orders[id] = order
	fmt.Printf("[DB COMMIT] Order %s successfully updated to status: %s\n", id, newStatus)
	return nil
}

type KafkaProducerMock struct {
	unavailable bool
}

func (k *KafkaProducerMock) Publish(topic, key, payload string) error {
	if k.unavailable {
		// Эмуляция недоступности брокера (Kafka broker unavailable, network partition)
		return errors.New("kafka error: dial tcp 10.0.0.12:9092: connect: connection refused")
	}
	fmt.Printf("[KAFKA PUBLISH] Topic: %s, Key: %s, Payload: %s\n", topic, key, payload)
	return nil
}

// NaiveUpdateOrderAndPublish демонстрирует уязвимость Dual Write
func NaiveUpdateOrderAndPublish(ctx context.Context, db *OrderDatabase, kafka *KafkaProducerMock, orderID, status string) error {
	// Шаг 1: Успешное обновление локальной БД
	if err := db.UpdateOrderStatus(orderID, status); err != nil {
		return fmt.Errorf("db update failed: %w", err)
	}

	// Шаг 2: Отправка события в шину (точка отказа)
	err := kafka.Publish("order-events", orderID, fmt.Sprintf("{\"status\":\"%s\"}", status))
	if err != nil {
		fmt.Printf("[CRITICAL ERROR] Kafka publish failed: %v\n", err)
		// БД уже закоммичена! Откатить закоммиченную транзакцию невозможно.
		return fmt.Errorf("dual write inconsistency: db updated, but event lost: %w", err)
	}

	return nil
}

func main() {
	db := &OrderDatabase{
		orders: map[string]Order{
			"ord-100": {ID: "ord-100", Status: "PENDING"},
		},
	}
	kafka := &KafkaProducerMock{unavailable: true} // Брокер лег!

	fmt.Println("=== DEMONSTRATING DUAL WRITE FAILURE ===")
	err := NaiveUpdateOrderAndPublish(context.Background(), db, kafka, "ord-100", "PAID")
	if err != nil {
		fmt.Printf("[Application Error] %v\n\n", err)
	}

	// Проверяем состояние БД
	db.mu.Lock()
	fmt.Printf("State of Order in DB: ID=%s, Status=%s\n", db.orders["ord-100"].ID, db.orders["ord-100"].Status)
	fmt.Println("Result: Database has status 'PAID', but Kafka never received the event! System is INCONSISTENT.")
	db.mu.Unlock()
}
```

## Под капотом

С точки зрения теории распределенных систем, попытка выполнить запись в БД и в очередь без 2PC нарушает атомарность (Atomicity). Если попытаться инвертировать порядок (сначала `kafka.Publish()`, а затем `db.Commit()`), возникает обратная и еще более опасная проблема: брокер отправит событие, подписчики начнут списывать склад и отправлять товар, а локальная транзакция СУБД упадет из-за дедлока или ошибки диска. В итоге покупатель получит посылку по заказу, которого физически нет в БД!

## Подводные камни

1. Попытка компенсировать сбой Kafka в блоке `if err != nil { db.Revert() }`: если в этот момент упадет сам процесс (SIGKILL), откат не выполнится, и база останется рассинхронизированной.
2. Упование на синхронные сетевые вызовы: сеть ненадежна по определению (Fallacies of Distributed Computing).

## На собеседовании

Вопрос: Почему нельзя использовать двухфазный коммит (2PC / XA) между PostgreSQL и Apache Kafka?
Ответ: Apache Kafka концептуально не поддерживает протокол XA/2PC с внешними СУБД. Кроме того, даже если бы поддерживала, протокол 2PC является блокирующим: при сетевом сбое транзакция удерживала бы блокировки строк в Postgres на время сетевых таймаутов, что моментально парализовало бы весь сервис под нагрузкой (исчерпание max_connections и каскадный отказ).
