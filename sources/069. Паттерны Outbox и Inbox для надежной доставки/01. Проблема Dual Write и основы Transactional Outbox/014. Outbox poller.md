# Outbox poller: фоновый процесс периодического опроса и таймерный диспетчер

## Условие

14. **Outbox poller**: Отдельный процесс (или горутина) читает unprocessed events из outbox и публикует их в Kafka.

### Исходная формулировка

**Outbox poller**: Отдельный процесс (или горутина) читает unprocessed events из outbox и публикует их в Kafka.

## Теория

Outbox Poller реализуется как долгоживущий фоновый процесс (Background Daemon / Worker Service). Он не должен непрерывно грузить базу в плотном цикле (Busy Waiting / 100% CPU loop). Идиоматический диспетчер опроса на Go использует `time.Ticker` или адаптивный интервал: если в текущей итерации найдено полное количество строк (`len(batch) == limit`), следующий опрос выполняется немедленно (Back-to-Back Polling) для быстрого выгребания очереди; если пачка пуста, воркер 'засыпает' на настроенный интервал тикера (например, 200–500 мс). Обязательна поддержка Graceful Shutdown по сигналу контекста.

## Решение по шагам

1. Создайте структуру `OutboxPollerDaemon` с полями тикера, репозитория и Kafka продюсера.
2. Реализуйте бесконечный цикл `select` с прослушиванием каналов `ctx.Done()` и `ticker.C`.
3. Добавьте логику адаптивного поллинга (мгновенный повтор при полной пачке).
4. Реализуйте безопасную остановку воркера с завершением текущей пачки (Drain phase).
5. Продемонстрируйте работу поллера в `main`.

## Код решения

**`outbox_poller_daemon.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type EventMsg struct {
	ID      int
	Payload string
}

type OutboxPollerDaemon struct {
	pollInterval time.Duration
	batchSize    int
	queue        []EventMsg
	mu           sync.Mutex
}

func NewPoller(interval time.Duration, batchSize int) *OutboxPollerDaemon {
	p := &OutboxPollerDaemon{
		pollInterval: interval,
		batchSize:    batchSize,
	}
	// Инициализируем тестовые события
	for i := 1; i <= 5; i++ {
		p.queue = append(p.queue, EventMsg{ID: i, Payload: fmt.Sprintf("order_%d", i)})
	}
	return p
}

func (p *OutboxPollerDaemon) PollBatch() []EventMsg {
	p.mu.Lock()
	defer p.mu.Unlock()

	if len(p.queue) == 0 {
		return nil
	}

	end := p.batchSize
	if end > len(p.queue) {
		end = len(p.queue)
	}

	batch := p.queue[:end]
	p.queue = p.queue[end:]
	return batch
}

func (p *OutboxPollerDaemon) Start(ctx context.Context) {
	ticker := time.NewTicker(p.pollInterval)
	defer ticker.Stop()

	fmt.Println("[Poller Daemon] Started background poll loop...")

	for {
		select {
		case <-ctx.Done():
			fmt.Println("[Poller Daemon] Received shutdown signal. Draining and exiting gracefully...")
			return
		case <-ticker.C:
			for {
				batch := p.PollBatch()
				if len(batch) == 0 {
					break // Очередь пуста, ждем следующего тика
				}

				fmt.Printf("[Poller] Published %d events to Kafka: ", len(batch))
				for _, msg := range batch {
					fmt.Printf("#%d ", msg.ID)
				}
				fmt.Println()

				// Если пачка была полной, сразу опрашиваем следующую без ожидания тикера
				if len(batch) < p.batchSize {
					break
				}
			}
		}
	}
}

func main() {
	poller := NewPoller(100*time.Millisecond, 2)
	ctx, cancel := context.WithTimeout(context.Background(), 350*time.Millisecond)
	defer cancel()

	poller.Start(ctx)
	fmt.Println("[Main] Poller process finished.")
}
```

ℹ️ Фоновый демон Outbox Poller с тикером, адаптивным циклом и Graceful Shutdown

```bash
[Poller] Published 2 events to Kafka: #1 #2 
[Poller] Published 2 events to Kafka: #3 #4 
[Poller] Published 1 events to Kafka: #5 
[Poller Daemon] Received shutdown signal. Draining and exiting gracefully...
[Main] Poller process finished.
```

## Под капотом

Использование `time.NewTicker` вместо `time.Sleep` защищает от утечек таймеров в рантайме Go. Адаптивный цикл (`if len(batch) == limit { continue }`) позволяет мгновенно откачивать всплески нагрузки без искусственных задержек, снижая latency доставки до предела сетевого интерфейса.

## Подводные камни

1. Забытый `defer ticker.Stop()`: незакрытый тикер не собирается сборщиком мусора до завершения программы.
2. Блокировка канала `ctx.Done()` долгими сетевыми вызовами: отправка в брокер обязана принимать контекст `ctx`.

## На собеседовании

Вопрос: Что делать, если при перезапуске пода поллер начинает отправлять события, которые уже отправил предыдущий под?
Ответ: Это стандартная ситуация в распределенных системах (At-Least-Once delivery). Чтобы минимизировать дублирование, поллер должен коммитить статус `processed = true` сразу после подтверждения каждого батча. А на стороне подписчиков обязателен Transactional Inbox с дедупликацией по уникальному `id` события.
