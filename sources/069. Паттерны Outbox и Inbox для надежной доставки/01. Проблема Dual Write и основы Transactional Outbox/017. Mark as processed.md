# Mark as processed: фиксация успешной публикации и оптимизация удаления строк

## Условие

17. **Mark as processed**: После успешной публикации в Kafka помечайте events как `processed = TRUE`.

### Исходная формулировка

**Mark as processed**: После успешной публикации в Kafka помечайте events как `processed = TRUE`.

## Теория

После того как продюсер Kafka подтвердил прием сообщения (ACK от лидера или ISR кворума), Outbox Poller обязан зафиксировать этот факт в реляционной базе данных. Существует две стратегии фиксации:
1) Soft Mark: `UPDATE outbox SET processed = TRUE, processed_at = NOW() WHERE id = $1` — сохраняет историю для аудита и дебага, но требует частичного индекса и периодической очистки (Purging);
2) Immediate Delete: `DELETE FROM outbox WHERE id = $1` — таблица остается компактной (Zero-Bloat), но теряется аудит отправленных сообщений на стороне источника.
В BigTech финтех-системах стандартом является Soft Mark с партиционированием по дням (`RANGE (created_at)`), что позволяет мгновенно удалять старые партиции через `DROP TABLE` без блокировки живой базы.

## Решение по шагам

1. Реализуйте метод `MarkProcessed(ctx, eventID)` в структуре хранилища.
2. Продемонстрируйте обновление флага `processed = TRUE` и отметки времени `processed_at`.
3. Убедитесь, что частичный индекс автоматически исключает обновленную строку из выборки.
4. Реализуйте фоновую процедуру очистки (Purge Job) записей старше 7 дней.
5. Проверьте корректность работы в `main`.

## Код решения

**`mark_processed_and_purge.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxEventRecord struct {
	ID          string
	Processed   bool
	ProcessedAt *time.Time
	CreatedAt   time.Time
}

type OutboxStoreWithCleanup struct {
	mu     sync.Mutex
	events map[string]*OutboxEventRecord
}

func (s *OutboxStoreWithCleanup) MarkAsProcessed(id string) {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	if rec, exists := s.events[id]; exists {
		rec.Processed = true
		rec.ProcessedAt = &now
		fmt.Printf("[Outbox DB] Event %s marked processed = TRUE (ProcessedAt: %s)\n",
			id, now.Format("15:04:05.000"))
	}
}

// PurgeOldProcessedEvents эмулирует фоновый джоб удаления старых записей:
// DELETE FROM outbox WHERE processed = TRUE AND processed_at < NOW() - INTERVAL '7 days';
func (s *OutboxStoreWithCleanup) PurgeOldProcessedEvents(olderThan time.Duration) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	cutoff := time.Now().Add(-olderThan)
	deleted := 0

	for id, rec := range s.events {
		if rec.Processed && rec.ProcessedAt != nil && rec.ProcessedAt.Before(cutoff) {
			delete(s.events, id)
			deleted++
		}
	}
	return deleted
}

func main() {
	store := &OutboxStoreWithCleanup{
		events: make(map[string]*OutboxEventRecord),
	}

	eventID := "evt-audit-77"
	store.events[eventID] = &OutboxEventRecord{
		ID:        eventID,
		Processed: false,
		CreatedAt: time.Now(),
	}

	// 1. Пометка после успешной публикации в Kafka
	fmt.Println("=== STEP 1: MARK AS PROCESSED ===")
	store.MarkAsProcessed(eventID)

	// 2. Симуляция старой записи (30 дней назад)
	oldID := "evt-old-30d"
	oldTime := time.Now().Add(-30 * 24 * time.Hour)
	store.events[oldID] = &OutboxEventRecord{
		ID:          oldID,
		Processed:   true,
		ProcessedAt: &oldTime,
		CreatedAt:   oldTime,
	}

	// 3. Запуск Purge Job
	fmt.Println("\n=== STEP 2: RUNNING PURGE JOB ===")
	purged := store.PurgeOldProcessedEvents(7 * 24 * time.Hour)
	fmt.Printf("Purge finished: %d old archived records deleted from database.\n", purged)
	fmt.Printf("Remaining events in store: %d (Recent record %s preserved for audit!)\n",
		len(store.events), eventID)
}
```

ℹ️ Фиксация статуса processed = TRUE и периодическая пакетная очистка устаревших строк

## Под капотом

Команда `UPDATE outbox SET processed = true` создает новую версию строки (Tuple) в PostgreSQL из-за архитектуры MVCC (Append-only storage). Старая версия строки помечается как мертвая (Dead Tuple). Для предотвращения раздувания таблиц (Table Bloat) необходимо настроить агрессивный автовакуум для таблицы outbox: `ALTER TABLE outbox SET (autovacuum_vacuum_scale_factor = 0.05, autovacuum_vacuum_cost_limit = 1000)`.

## Подводные камни

1. Забытый `VACUUM` / Purge: при 10 миллионах событий в сутки таблица без очистки займет сотни гигабайт и парализует производительность дисковой подсистемы.
2. Вызов `DELETE FROM outbox` одним гигантским запросом: удаление 1,000,000 строк одним `DELETE` заблокирует таблицу и забьет диск логами отката. Удалять нужно пачками: `LIMIT 5000`.

## На собеседовании

Вопрос: Как очищать Outbox-таблицу при экстремальном объеме 100 млн событий в сутки без нагрузки на autovacuum?
Ответ: Применяется партиционирование таблиц PostgreSQL по дням (`PARTITION BY RANGE (created_at)`). Вместо тяжелого построчного `DELETE` ежедневный крон выполняет мгновенную DDL-команду `DROP TABLE outbox_y2026_m09_d01;`. Удаление партиции занимает ровно 1 миллисекунду, не нагружает диск и не создает мертвых кортежей MVCC.
