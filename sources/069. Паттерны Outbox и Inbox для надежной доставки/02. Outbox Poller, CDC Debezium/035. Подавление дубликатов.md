# Подавление дубликатов: skip already processed и фиксация оффсетов

## Условие

35. **Если есть — skip (already processed)**: Реализуйте безопасный пропуск повторно пришедших сообщений без выполнения побочных эффектов с подтверждением в брокер.

### Исходная формулировка

Если есть — skip (already processed)

## Теория

Подавление дубликатов (Duplicate Suppression) — важнейший шаг в обеспечении стабильности консьюмера. Когда проверка Inbox показывает, что сообщение уже было успешно обработано ранее (`already processed`), система обязана соблюсти три критических правила:
1) Никаких побочных эффектов (No Side Effects): не производить начислений, не слать push-уведомлений, не списывать товары;
2) Никаких паник и ошибок: дубликат — это не авария, а штатное поведение сети At-Least-Once;
3) Обязательный коммит оффсета (Acknowledge): брокер сообщений обязан получить подтверждение, чтобы продвинуть указатель чтения дальше.

## Решение по шагам

1. Создайте обработчик с метрикой `deduplicated_events_total`.
2. При обнаружении дубликата увеличивайте счетчик метрики дедупликации.
3. Подтверждайте оффсет брокеру.
4. Смоделируйте поступление дубликатов и проверьте значение счетчика.
5. Продемонстрируйте вывод в консоли.

## Код решения

**`skip_already_processed.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
)

type DuplicateSuppressor struct {
	processedRegistry map[string]bool
	dedupMetricsCount atomic.Int64
}

func (s *DuplicateSuppressor) HandleMessage(msgID string, actionFunc func()) {
	// Проверка наличия в Inbox
	if s.processedRegistry[msgID] {
		// ПРОПУСК: Дубликат обнаружен
		s.dedupMetricsCount.Add(1)
		fmt.Printf("[DEDUP SKIP] Message %s already processed. Skipping side effects. Prometheus metric incremented.\n", msgID)
		// Подтверждаем оффсет в Kafka
		fmt.Printf("[Kafka Offset] Commit Ack sent for duplicate %s\n\n", msgID)
		return
	}

	// Первичная обработка
	s.processedRegistry[msgID] = true
	fmt.Printf("[Processing] Executing side effects for brand new message %s...\n", msgID)
	actionFunc()
	fmt.Printf("[Kafka Offset] Commit Ack sent for new message %s\n\n", msgID)
}

func main() {
	suppressor := &DuplicateSuppressor{
		processedRegistry: make(map[string]bool),
	}

	msgID := "kafka-msg-order-44"

	sideEffectCalled := 0
	action := func() {
		sideEffectCalled++
		fmt.Println(" -> [SMS Service] Sent SMS: 'Your order has been paid!'")
	}

	fmt.Println("=== DEMONSTRATING DUPLICATE SUPPRESSION ===")

	// Первая доставка
	suppressor.HandleMessage(msgID, action)

	// Вторая доставка (дубликат брокера)
	suppressor.HandleMessage(msgID, action)

	// Третья доставка (еще один дубликат)
	suppressor.HandleMessage(msgID, action)

	fmt.Printf("Total SMS Sent: %d (Expected: 1)\n", sideEffectCalled)
	fmt.Printf("Total Duplicates Suppressed: %d\n", suppressor.dedupMetricsCount.Load())
}
```

ℹ️ Подавление дубликатов сообщений с инкрементом метрики и подтверждением оффсета

## Под капотом

Метрика Prometheus `consumer_deduplicated_messages_total` позволяет DevOps-инженерам в реальном времени оценивать стабильность брокера. В нормальном состоянии процент дубликатов составляет менее 0.01%. Если график дедупликации подскакивает до 20–30%, это сигнализирует о нестабильности консьюмер-группы (частые ребалансировки) или сетевом флаппинге продюсеров.

## Подводные камни

1. Забытый коммит оффсета при пропуске: брокер снова и снова будет присылать пропущенное сообщение.
2. Паника при дубликате: если приложение паникует при встрече дубликата, консьюмер упадет в бесконечный CrashLoopBackOff.

## На собеседовании

Вопрос: Что произойдет, если консьюмер выполнит `Ack` в брокере, но база упадет во время следующего сообщения?
Ответ: Оффсет в Kafka коммитится только ПОСЛЕ успешного коммита транзакции текущего сообщения. Если база упадет, транзакция откатится, оффсет закоммичен не будет, и после рестарта консьюмер заново перечитает упавшее сообщение, восстанавливая консистентность.
