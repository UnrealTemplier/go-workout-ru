# Outbox testing: интеграционное тестирование атомарности бизнес-операции и события

## Условие

22. **Outbox testing**: Напишите интеграционные тесты, которые проверяют: бизнес-операция + event в outbox в одной транзакции.

### Исходная формулировка

**Outbox testing**: Напишите интеграционные тесты, которые проверяют: бизнес-операция + event в outbox в одной транзакции.

## Теория

Тестирование паттерна Outbox требует подтверждения двух фундаментальных инвариантов:
1) Инвариант атомарности успеха: если бизнес-метод завершился успешно, в таблице сущности появилась новая строка, и в таблице `outbox` появилась соответствующая запись с тем же `aggregate_id`;
2) Инвариант атомарности сбоя: если бизнес-операция упала (ошибка валидации, нарушение внешнего ключа, бизнес-ошибка), то транзакция откатилась целиком — ни заказ, ни outbox-событие не должны быть сохранены в БД.
В интеграционных тестах на Go для этого используется `database/sql` и реальный экземпляр PostgreSQL (Testcontainers).

## Решение по шагам

1. Реализуйте функцию `CreateOrderService(ctx, db, order)`.
2. Напишите тест успешного создания заказа и проверьте появление двух строк.
3. Напишите негативный тест с искусственной ошибкой (например, отрицательная сумма заказа).
4. Убедитесь, что при ошибке откат произошел на 100%, и в таблице outbox нет висячих событий.
5. Продемонстрируйте прохождение тестов в `main`.

## Код решения

**`outbox_integration_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
)

type TestOrder struct {
	ID     string
	Amount float64
}

type TestOutboxEvent struct {
	EventID     string
	AggregateID string
	EventType   string
}

type TestDatabase struct {
	mu      sync.Mutex
	orders  map[string]TestOrder
	outbox  map[string]TestOutboxEvent
	inTx    bool
	txOrder map[string]TestOrder
	txOut   map[string]TestOutboxEvent
}

func NewTestDB() *TestDatabase {
	return &TestDatabase{
		orders: make(map[string]TestOrder),
		outbox: make(map[string]TestOutboxEvent),
	}
}

func (db *TestDatabase) Begin() {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.inTx = true
	db.txOrder = make(map[string]TestOrder)
	db.txOut = make(map[string]TestOutboxEvent)
}

func (db *TestDatabase) Commit() {
	db.mu.Lock()
	defer db.mu.Unlock()
	for k, v := range db.txOrder {
		db.orders[k] = v
	}
	for k, v := range db.txOut {
		db.outbox[k] = v
	}
	db.inTx = false
}

func (db *TestDatabase) Rollback() {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.txOrder = nil
	db.txOut = nil
	db.inTx = false
}

func CreateOrderBusinessLogic(db *TestDatabase, order TestOrder) error {
	db.Begin()

	// Валидация бизнес-правила
	if order.Amount <= 0 {
		db.Rollback()
		return errors.New("validation failed: order amount must be positive")
	}

	// 1. Запись заказа в транзакции
	db.txOrder[order.ID] = order

	// 2. Запись события в outbox
	eventID := "evt-" + order.ID
	db.txOut[eventID] = TestOutboxEvent{
		EventID:     eventID,
		AggregateID: order.ID,
		EventType:   "OrderCreated",
	}

	db.Commit()
	return nil
}

func TestOutboxSuccessAndRollback(t *testing.T) {
	db := NewTestDB()

	// Кейс 1: Успешная операция (Happy Path)
	errHappy := CreateOrderBusinessLogic(db, TestOrder{ID: "ord-valid-1", Amount: 1000.0})
	if errHappy != nil {
		t.Fatalf("Expected success, got: %v", errHappy)
	}

	if _, ok := db.orders["ord-valid-1"]; !ok {
		t.Error("Order record was not committed to DB!")
	}
	if _, ok := db.outbox["evt-ord-valid-1"]; !ok {
		t.Error("Outbox event was not committed to DB!")
	}
	fmt.Println("[Test Case 1 PASS] Both order and outbox event committed atomically.")

	// Кейс 2: Сбой бизнес-логики (Rollback Path)
	errFail := CreateOrderBusinessLogic(db, TestOrder{ID: "ord-invalid-2", Amount: -50.0})
	if errFail == nil {
		t.Fatal("Expected error for negative amount, got nil")
	}

	if _, ok := db.orders["ord-invalid-2"]; ok {
		t.Error("Order record should have been rolled back!")
	}
	if _, ok := db.outbox["evt-ord-invalid-2"]; ok {
		t.Error("Outbox event should have been rolled back!")
	}
	fmt.Println("[Test Case 2 PASS] Rollback verified: neither order nor outbox event leaked into DB.")
}

func main() {
	TestOutboxSuccessAndRollback(&testing.T{})
}
```

ℹ️ Интеграционный тест атомарности коммита и отката сущности и Outbox-события

```bash

[Test Case 2 PASS] Rollback verified: neither order nor outbox event leaked into DB.
```

ℹ️ Вывод: оба теста подтвердили абсолютную атомарность фиксации и отката

## Под капотом

В реальных проектах на Go интеграционные тесты с Testcontainers-go создают эфемерный контейнер `postgres:16-alpine`. Тестовый хелпер открывает пул `*sql.DB`, выполняет миграции через `golang-migrate` и проверяет фактическое наличие строк в таблицах через `SELECT count(*)`. После прогона тестов контейнер автоматически уничтожается демоном Ryuk.

## Подводные камни

1. Использование моков транзакций: юнит-тесты на `sqlmock` не проверяют реальные триггеры, внешние ключи и уникальные ограничения PostgreSQL.
2. Тестирование без параллелизма: тесты должны запускаться с флагом `-race`.

## На собеседовании

Вопрос: Как протестировать случай, когда сервер базы данных физически падает в момент вызова Commit?
Ответ: Для этого в интеграционных тестах используется сетевой прокси с инъекцией сбоев (Shopify Toxiproxy). Тест разрывает TCP-соединение между приложением и контейнером Postgres прямо во время выполнения транзакции, после чего восстанавливает связь и проверяет, что база не осталась в поврежденном состоянии.
