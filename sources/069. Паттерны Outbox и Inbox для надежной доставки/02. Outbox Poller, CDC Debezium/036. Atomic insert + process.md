# Atomic insert + process: промышленная реализация идемпотентной транзакции консьюмера

## Условие

36. **Atomic insert + process**: В одной транзакции:
    ```go
    tx.Begin()
    tx.Exec("INSERT INTO inbox (message_id, payload) VALUES ($1, $2) ON CONFLICT DO NOTHING", msgID, payload)
    if tx.RowsAffected() == 1 {
        // Process message
        processOrder(msg)
    }
    tx.Commit()
    ```

### Исходная формулировка

**Atomic insert + process**: В одной транзакции:
```go
tx.Begin()
tx.Exec("INSERT INTO inbox (message_id, payload) VALUES ($1, $2) ON CONFLICT DO NOTHING", msgID, payload)
if tx.RowsAffected() == 1 {
    // Process message
    processOrder(msg)
}
tx.Commit()
```

## Теория

Паттерн Atomic Insert + Process объединяет все требования к надежному консьюмеру в единую лаконичную и отказоустойчивую конструкцию. В рамках одной транзакции БД выполняются:
1) Попытка вставки строки в таблицу `inbox` с клаузой `ON CONFLICT (message_id) DO NOTHING`;
2) Анализ результата: если `RowsAffected() == 1`, сообщение получено впервые. Внутри этой же транзакции выполняются все мутации бизнес-данных (изменение баланса, статуса заказа, остатка на складе);
3) Если `RowsAffected() == 0`, сообщение является дубликатом, бизнес-код не выполняется;
4) Транзакция коммитится, и консьюмер подтверждает оффсет в Kafka.
Эта схема исключает состояние гонки даже при одновременной доставке дубликатов на 10 разных серверов.

## Решение по шагам

1. Реализуйте функцию `ConsumeAndProcessOrder(ctx, db, msg)`.
2. Откройте транзакцию через `db.BeginTx(ctx, nil)`.
3. Выполните `INSERT INTO inbox ... ON CONFLICT DO NOTHING`.
4. При `RowsAffected == 1` вызовите функцию мутации доменных данных.
5. Зафиксируйте транзакцию и выведите статус выполнения.

## Код решения

**`atomic_inbox_processor.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type DBTransactionMock struct {
	mu           *sync.Mutex
	inbox        map[string]bool
	orders       map[string]string
	rowsAffected int64
}

func (tx *DBTransactionMock) Exec(query string, msgID string) {
	// Эмуляция INSERT INTO inbox (message_id) VALUES ($1) ON CONFLICT DO NOTHING
	if tx.inbox[msgID] {
		tx.rowsAffected = 0
		return
	}
	tx.inbox[msgID] = true
	tx.rowsAffected = 1
}

func (tx *DBTransactionMock) RowsAffected() int64 {
	return tx.rowsAffected
}

type OrderConsumerService struct {
	mu     sync.Mutex
	inbox  map[string]bool
	orders map[string]string
}

func NewConsumerService() *OrderConsumerService {
	return &OrderConsumerService{
		inbox:  make(map[string]bool),
		orders: make(map[string]string),
	}
}

func (s *OrderConsumerService) ConsumeAndProcessOrder(ctx context.Context, msgID, orderID string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// BEGIN TRANSACTION
	tx := &DBTransactionMock{
		mu:     &s.mu,
		inbox:  s.inbox,
		orders: s.orders,
	}

	fmt.Printf("[Consumer DB] Executing INSERT INTO inbox for %s ON CONFLICT DO NOTHING...\n", msgID)
	tx.Exec("INSERT INTO inbox...", msgID)

	if tx.RowsAffected() == 1 {
		// Первичная доставка: выполняем бизнес-логику
		fmt.Printf(" -> [Business Execution] First time message! Updating order %s to 'COMPLETED'\n", orderID)
		tx.orders[orderID] = "COMPLETED"
	} else {
		// Дубликат: подавляем выполнение
		fmt.Printf(" -> [Duplicate Ignored] RowsAffected=0: Message %s was already processed. No-Op.\n", msgID)
	}

	// COMMIT TRANSACTION
	fmt.Printf("[Consumer DB COMMIT] Transaction successfully committed for message %s\n\n", msgID)
	return nil
}

func main() {
	service := NewConsumerService()
	ctx := context.Background()

	msgID := "kafka-offset-7788"
	orderID := "ord-xyz-900"

	fmt.Println("=== STEP 1: Process fresh incoming message ===")
	_ = service.ConsumeAndProcessOrder(ctx, msgID, orderID)

	fmt.Println("=== STEP 2: Process duplicate delivery of the exact same message ===")
	_ = service.ConsumeAndProcessOrder(ctx, msgID, orderID)

	fmt.Printf("Final Verification:\n - Order %s status: %s\n - Total Inbox records: %d\n",
		orderID, service.orders[orderID], len(service.inbox))
}
```

ℹ️ Промышленная реализация Atomic Insert + Process в одной транзакции консьюмера

## Под капотом

Паттерн Atomic Insert + Process минимизирует количество сетевых раунд-трипов к базе данных. Вместо двух отдельных запросов (`SELECT ...` затем `INSERT ...`) выполняется один запрос, который одновременно проверяет наличие и вставляет строку при отсутствии. Это снижает время удержания соединения к СУБД в 2 раза.

## Подводные камни

1. Долгие операции в блоке `if tx.RowsAffected() == 1`: если внутри транзакции вызывать тяжелые сторонние сервисы по HTTP, транзакция будет висеть, блокируя пул соединений.
2. Забытый `tx.Commit()`: без коммита транзакция откатится, и сообщение будет обрабатываться снова.

## На собеседовании

Вопрос: Что делать, если внутри `processOrder(msg)` происходит обращение к нереляционному ресурсу (например, отправка в S3)?
Ответ: Сторонние ненадежные действия не могут быть частью локальной ACID-транзакции. В этом случае применяется зеркальный Outbox: сервис консьюмера в той же транзакции обновляет заказ, пишет в Inbox и пишет задачу на выгрузку в S3 в свою локальную таблицу Outbox, обеспечивая сквозную надежность всей цепочки.
