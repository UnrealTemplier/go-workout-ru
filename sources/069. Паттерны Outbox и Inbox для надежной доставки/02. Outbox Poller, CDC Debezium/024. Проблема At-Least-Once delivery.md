# Проблема At-Least-Once delivery: неизбежность сетевых дубликатов на стороне подписчика

## Условие

24. **Проблема at-least-once delivery**: Kafka/RabbitMQ гарантируют at-least-once delivery. Message может быть доставлен дважды. Consumer должен быть идемпотентным.

### Исходная формулировка

**Проблема at-least-once delivery**: Kafka/RabbitMQ гарантируют at-least-once delivery. Message может быть доставлен дважды. Consumer должен быть идемпотентным.

## Теория

Любой масштабируемый распределенный брокер сообщений (Kafka, RabbitMQ, NATS JetStream, SQS) работает по модели доставки **At-Least-Once** (минимум один раз). Дубликаты возникают естественным образом в трех сценариях:
1) Producer Retry: продюсер отправил сообщение, брокер записал его в лог, но ответ ACK потерялся из-за сетевого сбоя. Продюсер повторяет отправку, создавая вторую копию в топике;
2) Consumer Rebalance: консьюмер потребил сообщение и обработал бизнес-логику, но упал до того, как закоммитил свой оффсет в Kafka. Другой консьюмер группы перечитывает партицию и получает сообщение повторно;
3) Network Timeout: таймаут подтверждения приводит к ретрансляции сообщения брокером.
Потребитель (Consumer) ОБЯЗАН быть идемпотентным, иначе повторная доставка приведет к двойным списаниям.

## Решение по шагам

1. Создайте структуру входящего сообщения `IncomingMessage` с полями `MessageID` и `Payload`.
2. Смоделируйте консьюмер без защиты от дубликатов и покажите ошибку двойного списания.
3. Добавьте в консьюмер проверку дедупликации по `MessageID`.
4. Докажите, что повторное получение того же `MessageID` не вызывает повторных финансовых операций.
5. Продемонстрируйте работу в `main`.

## Код решения

**`at_least_once_consumer_problem.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type PaymentMessage struct {
	MessageID string
	AccountID string
	Amount    float64
}

// Уязвимый консьюмер (без дедупликации)
type VulnerableConsumer struct {
	balance float64
}

func (c *VulnerableConsumer) Process(msg PaymentMessage) {
	c.balance -= msg.Amount
	fmt.Printf("[Vulnerable Consumer] Debited $%.2f. Current balance: $%.2f\n", msg.Amount, c.balance)
}

// Идемпотентный надежный консьюмер
type IdempotentConsumer struct {
	mu           sync.Mutex
	balance      float64
	processedIDs map[string]bool
}

func NewIdempotentConsumer(initialBalance float64) *IdempotentConsumer {
	return &IdempotentConsumer{
		balance:      initialBalance,
		processedIDs: make(map[string]bool),
	}
}

func (c *IdempotentConsumer) Process(msg PaymentMessage) {
	c.mu.Lock()
	defer c.mu.Unlock()

	// Проверка на дубликат по MessageID
	if c.processedIDs[msg.MessageID] {
		fmt.Printf("[Idempotent Consumer DEDUP] MessageID %s already processed! Ignoring duplicate. Balance safe: $%.2f\n",
			msg.MessageID, c.balance)
		return
	}

	c.processedIDs[msg.MessageID] = true
	c.balance -= msg.Amount
	fmt.Printf("[Idempotent Consumer] Debited $%.2f for MsgID %s. New balance: $%.2f\n",
		msg.Amount, msg.MessageID, c.balance)
}

func main() {
	msg := PaymentMessage{
		MessageID: "kafka-msg-uuid-999",
		AccountID: "acc-user-42",
		Amount:    500.0,
	}

	fmt.Println("=== 1. VULNERABLE CONSUMER (DOUBLE CHARGE DISASTER) ===")
	vuln := &VulnerableConsumer{balance: 1000.0}
	vuln.Process(msg) // Доставка 1
	vuln.Process(msg) // Доставка 2 (Сетевой ретрай брокера)
	fmt.Printf("Result: User balance lost $1000 instead of $500! (Balance: $%.2f)\n\n", vuln.balance)

	fmt.Println("=== 2. IDEMPOTENT CONSUMER (AT-LEAST-ONCE SAFE) ===")
	idem := NewIdempotentConsumer(1000.0)
	idem.Process(msg) // Доставка 1
	idem.Process(msg) // Доставка 2 (Сетевой ретрай брокера)
	fmt.Printf("Result: Exactly-Once semantics achieved! Final balance: $%.2f\n", idem.balance)
}
```

## Под капотом

В протоколе Apache Kafka при вызове `commitSync()` оффсеты сохраняются во внутренний топик `__consumer_offsets`. Если ребалансировка партиции (Rebalance) произошла до коммита оффсета, новый владелец партиции начнет чтение с последнего закоммиченного оффсета. Это означает, что сообщения, обработанные предыдущим консьюмером за последние 1–3 секунды, будут неизбежно доставлены повторно.

## Подводные камни

1. Использование in-memory мапы для дедупликации в продакшене: при рестарте пода мапа сотрется, и повторное сообщение приведет к дублированию. Дедупликация должна опираться на СУБД (Inbox) или Redis.
2. Дедупликация только по телу сообщения: разные заказы могут иметь одинаковую сумму и одинаковый состав.

## На собеседовании

Вопрос: Можно ли включить `enable.idempotence = true` в Kafka и отказаться от дедупликации на консьюмере?
Ответ: Нет! `enable.idempotence = true` защищает ТОЛЬКО от дубликатов между Kafka Producer и Kafka Broker. Она никак не защищает от дубликатов между Kafka Broker и Consumer при ребалансировке или сбоях сети. Дедупликация на стороне консьюмера строго обязательна.
