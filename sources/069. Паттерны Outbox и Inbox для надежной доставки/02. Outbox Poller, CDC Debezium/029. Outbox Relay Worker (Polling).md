# Outbox Relay Worker (Polling): периодический опрос с SELECT FOR UPDATE SKIP LOCKED

## Условие

29. **Outbox Relay Worker (Polling)**: Напиши фоновую горутину, которая раз в секунду делает `SELECT * FROM outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED` (чтобы воркеры не мешали друг другу).

### Исходная формулировка

**Outbox Relay Worker (Polling)**: Напиши фоновую горутину, которая раз в секунду делает `SELECT * FROM outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED` (чтобы воркеры не мешали друг другу).

## Теория

Фоновый воркер Outbox Relay Worker с запросом `FOR UPDATE SKIP LOCKED` — надежная рабочая лошадка транзакционной доставки. Он не требует внешней инфраструктуры (Kafka Connect, Debezium, Zookeeper) и работает на любых совместимых СУБД (PostgreSQL 9.5+, MySQL 8.0+, Oracle 11g+). Горутина запускается с интервалом 1 секунда, открывает локальную транзакцию, захватывает порцию `PENDING` записей, передает их продюсеру и переводит статус в `PUBLISHED`. Параллельные экземпляры воркера в других подах никогда не блокируются и не конкурируют за одни строки.

## Решение по шагам

1. Спроектируйте структуру воркера с каналом остановки `stopChan`.
2. Реализуйте метод транзакционного чтения `SELECT * ... FOR UPDATE SKIP LOCKED`.
3. Обработайте пачку сообщений и переведите статус в `PUBLISHED`.
4. Запустите две параллельные горутины воркеров.
5. Продемонстрируйте отсутствие конфликтов при разборе задач.

## Код решения

**`relay_worker_skip_locked.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxRowItem struct {
	ID      int
	Status  string
	Locked  bool
	Payload string
}

type DatabaseMockEngine struct {
	mu   sync.Mutex
	rows []*OutboxRowItem
}

func (db *DatabaseMockEngine) QuerySkipLocked(workerName string, limit int) []*OutboxRowItem {
	db.mu.Lock()
	defer db.mu.Unlock()

	var batch []*OutboxRowItem
	for _, r := range db.rows {
		if len(batch) >= limit {
			break
		}
		// WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED
		if r.Status == "PENDING" && !r.Locked {
			r.Locked = true
			batch = append(batch, r)
		}
	}
	return batch
}

func (db *DatabaseMockEngine) CommitPublished(workerName string, batch []*OutboxRowItem) {
	db.mu.Lock()
	defer db.mu.Unlock()

	for _, r := range batch {
		r.Status = "PUBLISHED"
		r.Locked = false
		fmt.Printf("[%s] Event ID=%d successfully PUBLISHED and committed in DB.\n", workerName, r.ID)
	}
}

func StartWorkerGoroutine(ctx context.Context, name string, db *DatabaseMockEngine, wg *sync.WaitGroup) {
	defer wg.Done()
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			fmt.Printf("[%s] Worker stopped.\n", name)
			return
		case <-ticker.C:
			batch := db.QuerySkipLocked(name, 2)
			if len(batch) == 0 {
				continue
			}

			fmt.Printf("[%s] Locked %d events for processing...\n", name, len(batch))
			time.Sleep(50 * time.Millisecond) // Эмуляция Kafka publish
			db.CommitPublished(name, batch)
		}
	}
}

func main() {
	db := &DatabaseMockEngine{
		rows: []*OutboxRowItem{
			{ID: 1, Status: "PENDING", Payload: "order-1"},
			{ID: 2, Status: "PENDING", Payload: "order-2"},
			{ID: 3, Status: "PENDING", Payload: "order-3"},
			{ID: 4, Status: "PENDING", Payload: "order-4"},
		},
	}

	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(2)

	fmt.Println("=== STARTING 2 PARALLEL OUTBOX RELAY WORKERS (SKIP LOCKED) ===")
	go StartWorkerGoroutine(ctx, "Worker-1", db, &wg)
	go StartWorkerGoroutine(ctx, "Worker-2", db, &wg)

	wg.Wait()
	fmt.Println("All pending events published without collisions.")
}
```

## Под капотом

СУБД использует механизм флагов в заголовке кортежа (Tuple Header). При `FOR UPDATE` в поле `t_infomask` проставляются биты `HEAP_XMAX_EXCL_LOCK`. Опция `SKIP LOCKED` заставляет планировщик пропускать строки с активным `XMAX`, не помещая транзакцию в очередь ожидания блокировки (Lock Wait Queue).

## Подводные камни

1. Забытый `LIMIT`: запрос без ограничения заблокирует всю таблицу целиком.
2. Падение воркера при долгой сетевой операции: удерживание блокировки дольше таймаута `idle_in_transaction_session_timeout` приведет к принудительному разрыву соединения сервером Postgres.

## На собеседовании

Вопрос: Почему нельзя использовать `FOR UPDATE NOWAIT` вместо `SKIP LOCKED`?
Ответ: `NOWAIT` при встрече заблокированной строки немедленно прерывает транзакцию с ошибкой `could not obtain lock on row`. Это вызовет лавину исключений и сбоев у параллельных воркеров. `SKIP LOCKED` работает мягко: он просто переходит к следующей свободной строке, обеспечивая непрерывность конвейера.
