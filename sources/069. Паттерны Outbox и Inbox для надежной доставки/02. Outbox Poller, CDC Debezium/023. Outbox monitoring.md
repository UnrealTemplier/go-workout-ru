# Outbox monitoring: мониторинг Outbox Lag, счетчики необработанных событий и алертинг

## Условие

23. **Outbox monitoring**: Мониторьте lag: количество unprocessed events в outbox. Алерт, если lag растёт.

### Исходная формулировка

**Outbox monitoring**: Мониторьте lag: количество unprocessed events в outbox. Алерт, если lag растёт.

## Теория

В архитектуре Transactional Outbox критически важен мониторинг задержки (Outbox Lag). Outbox Lag определяется как количество записей в таблице, которые еще не были опубликованы в брокер. Если Outbox Lag монотонно растет, это означает:
1) Падение или зависание Outbox Poller / Debezium;
2) Недоступность брокера сообщений (Kafka broker downtime);
3) Скорость генерации событий превышает пропускную способность ретранслятора.
Метрики Prometheus:
- `outbox_unprocessed_count` (Gauge) — число строк с `processed = false`;
- `outbox_oldest_event_age_seconds` (Gauge) — возраст старейшего необработанного события (`EXTRACT(EPOCH FROM (NOW() - min(created_at)))`). Алерт в Alertmanager срабатывает при `outbox_oldest_event_age_seconds > 60`.

## Решение по шагам

1. Спроектируйте структуру экспортера метрик `OutboxMetrics`.
2. Напишите SQL-запрос для вычисления количества и возраста старейшей записи.
3. Реализуйте сбор метрик с интервалом 5 секунд.
4. Настройте проверку пороговых значений (Alert Thresholds: > 1000 строк или возраст > 2 мин).
5. Продемонстрируйте срабатывание алерта при искусственном замедлении воркера.

## Код решения

**`outbox_monitoring.go`**

```go
package main

import (
	"fmt"
	"time"
)

type OutboxTelemetry struct {
	UnprocessedCount int64
	OldestEventAge   time.Duration
}

type TelemetryCollector struct {
	warningLagThreshold int64
	alertAgeThreshold   time.Duration
}

func (c *TelemetryCollector) CheckMetrics(t OutboxTelemetry) {
	fmt.Printf("[Prometheus Scrape] outbox_unprocessed_events=%d, outbox_oldest_age=%v\n",
		t.UnprocessedCount, t.OldestEventAge.Round(time.Second))

	// Правило 1: Превышение максимального количества
	if t.UnprocessedCount > c.warningLagThreshold {
		fmt.Printf(" [ALERT WARNING] HighOutboxQueueLength: %d unprocessed messages! Poller may be throttled.\n",
			t.UnprocessedCount)
	}

	// Правило 2: Событие зависло дольше SLA
	if t.OldestEventAge > c.alertAgeThreshold {
		fmt.Printf(" [ALERT CRITICAL] HighOutboxLagDuration: Oldest event is waiting for %v! PagerDuty fired!\n",
			t.OldestEventAge.Round(time.Second))
	}
}

func main() {
	collector := &TelemetryCollector{
		warningLagThreshold: 500,
		alertAgeThreshold:   60 * time.Second,
	}

	fmt.Println("=== SCENARIO 1: Healthy System State ===")
	collector.CheckMetrics(OutboxTelemetry{
		UnprocessedCount: 25,
		OldestEventAge:   450 * time.Millisecond,
	})

	fmt.Println("\n=== SCENARIO 2: Poller Stalled / Kafka Outage ===")
	collector.CheckMetrics(OutboxTelemetry{
		UnprocessedCount: 1420,
		OldestEventAge:   185 * time.Second, // 3 минуты задержки!
	})
}
```

ℹ️ Мониторинг Outbox Lag и возраста старейшего события с генерацией критических алертов

## Под капотом

Оптимальный SQL-запрос для сбора метрик лага в PostgreSQL:
`SELECT count(*), COALESCE(EXTRACT(EPOCH FROM (NOW() - min(created_at))), 0) `
`FROM outbox WHERE processed = FALSE;`
Благодаря частичному индексу `ON outbox (created_at) WHERE processed = FALSE` СУБД мгновенно находит минимальную дату по началу B-Tree индекса за \(O(1)\) без сканирования всей таблицы.

## Подводные камни

1. Мониторинг только количества строк: при низком ночном трафике в очереди может быть всего 1 строка, но если она зависла на 5 часов, бизнес парализован. Возраст старейшего события — главная метрика.
2. Выполнение запроса метрик слишком часто (раз в 100 мс): метрики скрейпятся Prometheus раз в 15 секунд.

## На собеседовании

Вопрос: Какой алерт важнее при мониторинге Outbox: по количеству записей или по времени задержки?
Ответ: По времени задержки (`oldest_event_age`). Всплеск количества записей может быть штатной ситуацией (например, запуск промо-акции), с которой воркеры справятся за пару минут. Но если даже одна запись не отправляется более 2 минут, это однозначный сигнал сбоя (зависший коннектор или ядовитое сообщение).
