## Теория

Идемпотентное потребление (Idempotent Consumer Pattern) — это зеркальная половина паттерна Transactional Outbox. Если Outbox решает проблему надежности на стороне отправителя, то Inbox решает проблему дубликатов на стороне получателя. Каждое входящее сообщение брокера сопровождается уникальным идентификатором `message_id` (UUID или Hash). Консьюмер выполняет четырехфазный протокол:
1) Проверка наличия `message_id` в хранилище обработанных сообщений;
2) Если сообщение новое — атомарное выполнение доменной логики и фиксация `message_id`;
3) Если сообщение дубликат — пропуск (No-Op);
4) Подтверждение оффсета в Kafka (`commitSync`).

## Код решения

**`idempotent_consumer_flow.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type EventMessage struct {
	MessageID string
	Payload   string
}

type ConsumerInbox struct {
	mu           sync.Mutex
	processed    map[string]bool
	actionsCount int
}

func (c *ConsumerInbox) ProcessEvent(ctx context.Context, msg EventMessage) {
	c.mu.Lock()
	defer c.mu.Unlock()

	// 1. Проверка наличия message_id в inbox
	if c.processed[msg.MessageID] {
		fmt.Printf("[Inbox Check] Message %s already processed. Skipping business action.\n", msg.MessageID)
		fmt.Printf("[Kafka Commit] Committing offset for duplicate message %s\n\n", msg.MessageID)
		return
	}

	// 2. Если нет — фиксируем в inbox и выполняем логику
	c.processed[msg.MessageID] = true
	c.actionsCount++
	fmt.Printf("[Inbox Insert + Execute] Executing business logic for %s (Action #%d: %s)\n",
		msg.MessageID, c.actionsCount, msg.Payload)

	// 3. Коммит оффсета
	fmt.Printf("[Kafka Commit] Offset committed successfully for message %s\n\n", msg.MessageID)
}

func main() {
	inbox := &ConsumerInbox{processed: make(map[string]bool)}
	ctx := context.Background()

	msg := EventMessage{
		MessageID: "msg-order-created-991",
		Payload:   "{\"order_id\":\"ord-991\",\"amount\":3500.0}",
	}

	fmt.Println("=== DEMONSTRATING 4-PHASE IDEMPOTENT CONSUMPTION ===")

	// Попытка 1: Первичная обработка
	fmt.Println("--- Delivery 1 (Original) ---")
	inbox.ProcessEvent(ctx, msg)

	// Попытка 2: Сетевой ретрай брокера
	fmt.Println("--- Delivery 2 (Broker Network Retry) ---")
	inbox.ProcessEvent(ctx, msg)

	// Попытка 3: Ребалансировка группы консьюмеров
	fmt.Println("--- Delivery 3 (Consumer Rebalance Replay) ---")
	inbox.ProcessEvent(ctx, msg)

	fmt.Printf("Total business actions executed: %d (Expected: 1)\n", inbox.actionsCount)
}
```

ℹ️ Четырехфазный цикл идемпотентного потребления с фиксацией оффсетов

## Под капотом

Обязательным условием является коммит оффсета брокера ДАЖЕ при обнаружении дубликата! Если при обнаружении дубликата вернуть ошибку или пропустить `commitSync()`, брокер будет считать, что сообщение не обработано, и станет доставлять его повторно бесконечно, блокируя движение партиции (Head-of-Line Blocking).

## Подводные камни

1. Несинхронный коммит оффсета: `commitAsync()` без обработки ошибок может скрыть сбой коммита.
2. Выполнение побочных эффектов (отправка email) до фиксации в Inbox: если внешнее API вызвано, а транзакция БД упала, email уйдет повторно.

## На собеседовании

Вопрос: Что делать, если два потока параллельно получили два одинаковых дубликата одного сообщения?
Ответ: Если проверка выполняется наивно в два шага (`SELECT` -> `INSERT`), оба потока увидят, что записи нет, и оба выполнят бизнес-логику (Race Condition). Защиту обеспечивает только атомарный `INSERT ... ON CONFLICT DO NOTHING` в реляционной СУБД с проверкой `rows_affected == 1`.
