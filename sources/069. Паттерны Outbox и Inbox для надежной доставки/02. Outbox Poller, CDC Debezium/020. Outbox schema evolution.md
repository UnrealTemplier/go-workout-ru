# Outbox schema evolution: версионирование схем событий в полезной нагрузке

## Условие

20. **Outbox schema evolution**: При изменении event schema поддерживайте versioning в payload (`{"version": 2, "data": {...}}`).

### Исходная формулировка

**Outbox schema evolution**: При изменении event schema поддерживайте versioning в payload (`{"version": 2, "data": {...}}`).

## Теория

В распределенной событийно-ориентированной архитектуре продюсеры и консьюмеры эволюционируют независимо. Релиз новой версии микросервиса заказов не должен приводить к падению консьюмеров аналитики или биллинга из-за изменения контракта JSON (Schema Drift). Паттерн Schema Evolution требует явного указания версии структуры события. В полезную нагрузку включается конверт метаданных: `{"schema_version": 2, "payload": {...}}`. Консьюмеры используют фабрику десериализации (Polymorphic JSON Unmarshaler), которая по номеру версии выбирает соответствующую Go-структуру или выполняет повышающую трансформацию (Upcasting).

## Решение по шагам

1. Создайте структуру базового конверта `EventEnvelope` с полем `SchemaVersion int`.
2. Опишите две версии структуры данных заказа: `OrderPayloadV1` и `OrderPayloadV2`.
3. Реализуйте полиморфный парсер `ParseEvent(rawJSON []byte)`.
4. Реализуйте Upcaster: автоконвертацию старого формата V1 в канонический V2.
5. Продемонстрируйте корректную обработку событий обеих версий.

## Код решения

**`schema_evolution.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
)

// Общий конверт события
type EventEnvelope struct {
	SchemaVersion int             `json:"schema_version"`
	EventType     string          `json:"event_type"`
	Data          json.RawMessage `json:"data"`
}

// Версия 1: Старый формат (имя покупателя единой строкой)
type OrderPayloadV1 struct {
	OrderID      string  `json:"order_id"`
	CustomerName string  `json:"customer_name"`
	Amount       float64 `json:"amount"`
}

// Версия 2: Новый формат (имя разделено на First/Last, добавлена валюта)
type OrderPayloadV2 struct {
	OrderID   string  `json:"order_id"`
	FirstName string  `json:"first_name"`
	LastName  string  `json:"last_name"`
	Amount    float64 `json:"amount"`
	Currency  string  `json:"currency"`
}

// ConsumerUpcaster приводит любые версии к канонической современной V2
func ProcessEventWithUpcasting(rawJSON []byte) (*OrderPayloadV2, error) {
	var env EventEnvelope
	if err := json.Unmarshal(rawJSON, &env); err != nil {
		return nil, err
	}

	switch env.SchemaVersion {
	case 1:
		var v1 OrderPayloadV1
		if err := json.Unmarshal(env.Data, &v1); err != nil {
			return nil, err
		}
		fmt.Printf("[Consumer Upcaster] Detected V1 event. Upcasting to V2 model...\n")
		// Конвертация V1 -> V2
		return &OrderPayloadV2{
			OrderID:   v1.OrderID,
			FirstName: v1.CustomerName,
			LastName:  "",
			Amount:    v1.Amount,
			Currency:  "RUB", // Дефолтное значение для легаси записей
		}, nil

	case 2:
		var v2 OrderPayloadV2
		if err := json.Unmarshal(env.Data, &v2); err != nil {
			return nil, err
		}
		fmt.Printf("[Consumer Direct] Detected native V2 event.\n")
		return &v2, nil

	default:
		return nil, fmt.Errorf("unsupported schema version: %d", env.SchemaVersion)
	}
}

func main() {
	// Событие версии 1 от старого инстанса продюсера
	v1JSON := []byte(`{
		"schema_version": 1,
		"event_type": "OrderCreated",
		"data": {"order_id": "ord-v1-100", "customer_name": "Алексей Смирнов", "amount": 2500.0}
	}`)

	// Событие версии 2 от нового продюсера
	v2JSON := []byte(`{
		"schema_version": 2,
		"event_type": "OrderCreated",
		"data": {"order_id": "ord-v2-200", "first_name": "Елена", "last_name": "Попова", "amount": 4200.0, "currency": "RUB"}
	}`)

	fmt.Println("=== DEMONSTRATING EVENT SCHEMA EVOLUTION ===")
	res1, _ := ProcessEventWithUpcasting(v1JSON)
	fmt.Printf("Parsed V1 Result: OrderID=%s, Name='%s', Currency=%s\n\n",
		res1.OrderID, res1.FirstName, res1.Currency)

	res2, _ := ProcessEventWithUpcasting(v2JSON)
	fmt.Printf("Parsed V2 Result: OrderID=%s, Name='%s %s', Currency=%s\n",
		res2.OrderID, res2.FirstName, res2.LastName, res2.Currency)
}
```

ℹ️ Версионирование полезной нагрузки событий Outbox и механизм Upcasting

## Под капотом

В архитектуре корпоративных шин данных эволюция схем регламентируется Schema Registry (Confluent Schema Registry / Karapace). Вместо текстового JSON часто используется Protobuf или Avro. Первые 5 байт каждого сообщения содержат Magic Byte (0x00) и 4 байта Schema ID, что позволяет сериализаторам автоматически проверять правила обратной совместимости (Backward/Forward Compatibility).

## Подводные камни

1. Удаление обязательных полей: удаление поля без переходного периода приведет к панике старых консьюмеров.
2. Изменение семантики существующего поля: изменение типа поля с `int` на `string` без смены версии схемы ломает парсинг.

## На собеседовании

Вопрос: Что такое Upcaster в архитектуре событий и где он должен выполняться?
Ответ: Upcaster — это чистая функция трансформации данных из версии \(N\) в версию \(N+1\). Он выполняется в приложении консьюмера сразу после чтения из брокера и до передачи данных в доменную модель. Это позволяет писать доменную бизнес-логику так, словно все события в системе имеют исключительно новейший формат.
