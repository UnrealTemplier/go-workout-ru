# Exactly-once с Outbox: разграничение зон ответственности публикации и обработки

## Условие

26. **Exactly-once с Outbox.**: Покажите, что Kafka может доставить сообщение дважды (producer retry). Consumer должен быть идемпотентным (см. Inbox). Объясните, что Outbox гарантирует exactly-once *публикацию* (атомарность с БД), но exactly-once *обработку* требует Idempotency/Inbox.

### Исходная формулировка

**Exactly-once с Outbox.**: Покажите, что Kafka может доставить сообщение дважды (producer retry). Consumer должен быть идемпотентным (см. Inbox). Объясните, что Outbox гарантирует exactly-once *публикацию* (атомарность с БД), но exactly-once *обработку* требует Idempotency/Inbox.

## Теория

Распространенное заблуждение начинающих инженеров: «Раз мы внедрили Outbox, теперь у нас Exactly-Once во всей системе». Это фундаментально неверно! Необходимо четко разграничивать две фазы:
1) **Phase 1: Exactly-Once Publishing (Гарантия публикации)** — обеспечивается паттерном Transactional Outbox. Событие гарантированно записывается в базу ровно тогда и только тогда, когда закоммичены бизнес-данные. Нет потери событий и нет фантомных событий;
2) **Phase 2: At-Least-Once Transport (Транспортный уровень)** — сеть и брокер Kafka доставляют сообщение потребителю минимум один раз (возможны дубликаты при retry продюсера или ребалансировке);
3) **Phase 3: Exactly-Once Processing (Гарантия обработки)** — обеспечивается исключительно паттерном Transactional Inbox на стороне консьюмера. Без Inbox вся система откатывается к аномалиям дублирования.

## Решение по шагам

1. Смоделируйте сквозной пайплайн: Источник (Outbox) -> Транспорт (Kafka At-Least-Once) -> Приемник (Inbox).
2. Покажите атомарную генерацию одного события в источнике.
3. Сымитируйте сетевое раздвоение пакета брокером (2 одинаковых сообщения в сети).
4. Покажите, как Transactional Inbox на приемнике отсекает дубликат, обеспечивая end-to-end Exactly-Once.
5. Подведите архитектурный итог.

## Код решения

**`exactly_once_duality.go`**

```go
package main

import (
	"fmt"
	"sync"
)

// Phase 1: Source Service with Outbox
type OrderServiceSource struct {
	outboxEvents []string
}

func (s *OrderServiceSource) CreateOrder(orderID string) string {
	// Атомарно сохраняем заказ и событие (Exactly-Once Publication)
	eventID := fmt.Sprintf("evt-uuid-%s", orderID)
	s.outboxEvents = append(s.outboxEvents, eventID)
	fmt.Printf("[Phase 1: Source Outbox] Order %s and Event %s committed to DB (Exactly-Once Publication).\n",
		orderID, eventID)
	return eventID
}

// Phase 3: Destination Consumer with Inbox
type BillingServiceDestination struct {
	mu           sync.Mutex
	inboxTable   map[string]bool
	debitCounter int
}

func (d *BillingServiceDestination) Consume(eventID string, amount float64) {
	d.mu.Lock()
	defer d.mu.Unlock()

	// Проверка Inbox
	if d.inboxTable[eventID] {
		fmt.Printf("[Phase 3: Consumer INBOX] Duplicate detected for EventID: %s! Skipping action.\n", eventID)
		return
	}

	// Транзакционная обработка и запись в Inbox
	d.inboxTable[eventID] = true
	d.debitCounter++
	fmt.Printf("[Phase 3: Consumer ACTION] Business operation executed for EventID: %s (Debit #%d: $%.2f)\n",
		eventID, d.debitCounter, amount)
}

func main() {
	source := &OrderServiceSource{}
	dest := &BillingServiceDestination{inboxTable: make(map[string]bool)}

	fmt.Println("=== DEMONSTRATING EXACTLY-ONCE PUBLISHING VS EXACTLY-ONCE PROCESSING ===")

	// Фаза 1: Источник публикует ровно 1 событие через Outbox
	eventID := source.CreateOrder("ord-707")

	// Фаза 2: Сеть / Брокер дублирует сообщение (At-Least-Once Delivery)
	fmt.Println("\n[Phase 2: Network Transport] Network glitch caused Kafka producer retry! 2 identical deliveries sent:")

	// Доставка 1
	dest.Consume(eventID, 1500.0)

	// Доставка 2 (Дубликат)
	dest.Consume(eventID, 1500.0)

	fmt.Printf("\nFinal Verification:\n - Total Events Published: %d\n - Business Actions Executed: %d\n",
		len(source.outboxEvents), dest.debitCounter)
	fmt.Println("CONCLUSION: Outbox gave Exactly-Once Publication. Inbox gave Exactly-Once Processing!")
}
```

ℹ️ Разграничение Exactly-Once публикации (Outbox) и Exactly-Once обработки (Inbox)

## Под капотом

Сквозной Exactly-Once семантики в распределенной сети не существует как единого протокола. Это иллюзия, создаваемая слаженной работой трех рубежей обороны: 1) Атомарный коммит Outbox в источнике; 2) Детерминированный UUID сообщения, неизменный при ретраях; 3) Уникальный индекс `PRIMARY KEY (message_id)` в таблице Inbox приемника.

## Подводные камни

1. Генерация нового `event_id` при каждом ретрае отправки: если ретрай сгенерирует новый UUID, Inbox консьюмера посчитает его новым независимым сообщением и спишет деньги повторно.
2. Упование на Kafka Streams Exactly-Once: встроенный EOS Kafka работает только внутри одного Kafka-кластера и не распространяется на внешние реляционные базы данных.

## На собеседовании

Вопрос: Гарантирует ли паттерн Transactional Outbox сам по себе, что потребитель получит сообщение ровно один раз?
Ответ: Нет! Outbox гарантирует только то, что сообщение не потеряется и будет атомарно зафиксировано с БД. Сам процесс ретрансляции (Poller/Debezium) работает с гарантией At-Least-Once. Потребитель обязательно получит дубликаты при сбоях сети или рестартах воркеров. Для защиты на стороне потребителя строго необходим Transactional Inbox.
