# Cleanup old events: периодическая пакетная очистка и архивация Outbox-событий

## Условие

21. **Cleanup old events**: Периодически удаляйте processed events старше N дней (например, 30 дней) для предотвращения роста таблицы.

### Исходная формулировка

**Cleanup old events**: Периодически удаляйте processed events старше N дней (например, 30 дней) для предотвращения роста таблицы.

## Теория

Без регулярной очистки (Purging / Archival) таблица `outbox` быстро превращается в терабайтное хранилище исторического мусора. В высоконагруженных сервисах (1000 записей/сек) за месяц генерируется более 2.5 миллиардов строк. Попытка удалить их наивным запросом `DELETE FROM outbox WHERE sent_at < NOW() - INTERVAL '30 days'` приведет к катастрофе: запрос заблокирует таблицу на часы, переполнит буфер блокировок и диск транзакционными логами. Промышленная очистка выполняется строго пачками с использованием `LIMIT` и пауз между итерациями (Chunked Purging), либо через механизм секционирования таблиц (Table Partitioning).

## Решение по шагам

1. Спроектируйте алгоритм порционной очистки `PurgeInChunks(ctx, db, chunkSize, olderThan)`.
2. Выполняйте удаление порциями по \(N\) строк через подзапрос `WHERE id IN (SELECT id ... LIMIT 500)`.
3. Добавьте микропаузу (`time.Sleep(10ms)`) между пачками для разгрузки диска и репликации.
4. Завершайте цикл, когда количество удаленных строк станет меньше `chunkSize`.
5. Продемонстрируйте работу очистки в консоли.

## Код решения

**`chunked_outbox_cleanup.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxRowData struct {
	ID        int
	Processed bool
	CreatedAt time.Time
}

type LargeOutboxTableMock struct {
	mu   sync.Mutex
	rows []*OutboxRowData
}

func (t *LargeOutboxTableMock) DeleteChunk(olderThan time.Time, limit int) int {
	t.mu.Lock()
	defer t.mu.Unlock()

	deleted := 0
	var remaining []*OutboxRowData

	for _, r := range t.rows {
		if deleted < limit && r.Processed && r.CreatedAt.Before(olderThan) {
			deleted++ // Удаляем строку
		} else {
			remaining = append(remaining, r)
		}
	}
	t.rows = remaining
	return deleted
}

// PurgeProcessedInChunks выполняет безопасную пакетную очистку без блокировки СУБД
func PurgeProcessedInChunks(ctx context.Context, table *LargeOutboxTableMock, chunkSize int, retention time.Duration) int {
	cutoff := time.Now().Add(-retention)
	totalDeleted := 0

	fmt.Printf("[Cleanup Job] Starting chunked purge for records older than %s (ChunkSize: %d)...\n",
		cutoff.Format("2006-01-02"), chunkSize)

	for {
		select {
		case <-ctx.Done():
			fmt.Println("[Cleanup Job] Aborted by context timeout.")
			return totalDeleted
		default:
			// DELETE FROM outbox WHERE id IN (
			//   SELECT id FROM outbox WHERE processed = TRUE AND created_at < $1 LIMIT $2
			// );
			deleted := table.DeleteChunk(cutoff, chunkSize)
			totalDeleted += deleted
			fmt.Printf(" -> Purged chunk of %d rows. (Total so far: %d)\n", deleted, totalDeleted)

			if deleted < chunkSize {
				fmt.Println("[Cleanup Job] Cleanup cycle complete. No more obsolete records.")
				return totalDeleted
			}

			// Микропауза для предотвращения I/O троттлинга реплик
			time.Sleep(20 * time.Millisecond)
		}
	}
}

func main() {
	table := &LargeOutboxTableMock{}
	oldDate := time.Now().Add(-40 * 24 * time.Hour) // 40 дней назад

	// Наполняем таблицу 250 старыми записями
	for i := 1; i <= 250; i++ {
		table.rows = append(table.rows, &OutboxRowData{
			ID:        i,
			Processed: true,
			CreatedAt: oldDate,
		})
	}

	fmt.Printf("Initial Outbox rows count: %d\n", len(table.rows))
	deleted := PurgeProcessedInChunks(context.Background(), table, 100, 30*24*time.Hour)
	fmt.Printf("Final rows count: %d (Purged: %d)\n", len(table.rows), deleted)
}
```

ℹ️ Пакетная очистка устаревших записей Outbox пачками по 100 строк с микропаузами

```bash

[Cleanup Job] Starting chunked purge for records older than 2026-08-07 (ChunkSize: 100)...
 -> Purged chunk of 100 rows. (Total so far: 100)
 -> Purged chunk of 100 rows. (Total so far: 200)
 -> Purged chunk of 50 rows. (Total so far: 250)

```

## Под капотом

Запрос `DELETE FROM outbox WHERE id IN (SELECT id FROM outbox WHERE processed = true AND created_at < $1 LIMIT $2)` ставит короткую эксклюзивную блокировку только на удаляемый чанк (например, 1000 строк). Микропауза между итерациями позволяет процессору контрольных точек (Checkpointer) и фоновому процессу WAL writer сбросить грязные страницы на диск, не создавая дискового троттлинга для основной бизнес-нагрузки.

## Подводные камни

1. Удаление без проверки `processed = true`: удаление необработанных событий из-за ошибки в дате приведет к безвозвратной потере бизнес-данных!
2. Игнорирование задержки репликации (Replication Lag): непрерывный `DELETE` миллионов строк создает огромный поток WAL, из-за чего реплики для чтения отстанут от мастера на гигабайты.

## На собеседовании

Вопрос: Почему для сверхбольших объемов Outbox выбирают партиционирование вместо порционного DELETE?
Ответ: Механизм `DELETE` в PostgreSQL физически не освобождает место на диске — он лишь помечает кортежи мертвыми, требуя последующего тяжелого `VACUUM FULL`. Партиционирование по датам (`PARTITION BY RANGE`) позволяет выполнить команду `DROP TABLE outbox_p2026_08`, которая мгновенно освобождает дисковые блоки на уровне файловой системы без участия vacuum и без генерации объема в WAL.
