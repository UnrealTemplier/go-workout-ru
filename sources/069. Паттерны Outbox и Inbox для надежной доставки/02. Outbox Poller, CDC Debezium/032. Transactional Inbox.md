# Transactional Inbox: вставка в Inbox и атомарная обработка нового сообщения

## Условие

32. **Если нет — вставьте в inbox и обработайте**: Реализуйте логику: при отсутствии записи в таблице Inbox атомарно вставьте message_id и выполните бизнес-обработку.

### Исходная формулировка

Если нет — вставьте в inbox и обработайте

## Теория

Сценарий обработки нового сообщения (First-Time Delivery) в Transactional Inbox требует неразрывного объединения записи в Inbox и изменения доменных таблиц. Код консьюмера открывает транзакцию `tx, _ := db.BeginTx(ctx, nil)`:
1) `INSERT INTO inbox (message_id, created_at) VALUES ($1, NOW())`;
2) `UPDATE balances SET amount = amount + $2 WHERE user_id = $3`;
3) `tx.Commit()`.
Если на любом этапе происходит сбой (ошибка соединения, дедлок СУБД, падение пода), вся транзакция откатывается: запись из Inbox исчезает, а баланс не меняется. Это оставляет сообщение в состоянии 'необработанное', что позволяет безопасно повторить его обработку при следующем ретрае Kafka.

## Решение по шагам

1. Спроектируйте транзакционный метод `ProcessNewMessage(ctx, msg)`.
2. Выполните вставку `message_id` в локальную таблицу `inbox`.
3. Выполните начисление баланса в таблице `accounts`.
4. Зафиксируйте обе операции вызовом `Commit()`.
5. Продемонстрируйте корректный коммит обеих таблиц в `main`.

## Код решения

**`inbox_atomic_insert_process.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type AccountStorage struct {
	mu       sync.Mutex
	inbox    map[string]bool
	balances map[string]float64
}

func (s *AccountStorage) AtomicProcessIncoming(ctx context.Context, msgID, userID string, depositAmount float64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// BEGIN TRANSACTION
	fmt.Printf("[DB TX BEGIN] Starting transaction for incoming message %s\n", msgID)

	// 1. Вставка в inbox
	s.inbox[msgID] = true
	fmt.Printf("[DB TX] INSERT INTO inbox (message_id) VALUES ('%s') -> OK\n", msgID)

	// 2. Бизнес-логика: начисление средств
	s.balances[userID] += depositAmount
	fmt.Printf("[DB TX] UPDATE accounts SET balance = balance + %.2f WHERE user_id = '%s' (New Balance: $%.2f)\n",
		depositAmount, userID, s.balances[userID])

	// 3. COMMIT TRANSACTION
	fmt.Println("[DB TX COMMIT] Both Inbox and Account Balance committed atomically!")
	return nil
}

func main() {
	storage := &AccountStorage{
		inbox:    make(map[string]bool),
		balances: map[string]float64{"user-alice": 200.0},
	}

	ctx := context.Background()
	msgID := "kafka-evt-deposit-881"

	fmt.Println("=== PROCESSING FIRST-TIME MESSAGE IN TRANSACTIONAL INBOX ===")
	_ = storage.AtomicProcessIncoming(ctx, msgID, "user-alice", 500.0)

	fmt.Printf("\nFinal State:\n - User Balance: $%.2f (Expected: $700.00)\n - Inbox contains '%s': %v\n",
		storage.balances["user-alice"], msgID, storage.inbox[msgID])
}
```

ℹ️ Атомарная фиксация входящего сообщения в Inbox и изменение бизнес-баланса

## Под капотом

Транзакция в СУБД объединяет запись в таблицу Inbox и обновление баланса в один атомарный блок WAL. Даже если процесс аварийно завершится в момент выполнения `Commit()`, база данных гарантирует, что запись в Inbox не появится без обновления баланса, и наоборот. Это исключает частичные сайд-эффекты.

## Подводные камни

1. Запись в Inbox ПОСЛЕ коммита бизнес-логики: если процесс упадет между ними, баланс пополнится, а отметки в Inbox не будет. При ретрае брокера произойдет повторное пополнение.
2. Раздельные соединения БД: использование разных `db.Exec()` без транзакции `tx` разрушает атомарность.

## На собеседовании

Вопрос: Что произойдет, если база данных вернет Deadlock при вызове `AtomicProcessIncoming`?
Ответ: Транзакция автоматически откатится СУБД. Консьюмер перехватывает ошибку дедлока, НЕ коммитит оффсет в Kafka и повторяет транзакцию с короткой случайной паузой (Jittered Backoff). При повторе транзакция завершится успешно.
