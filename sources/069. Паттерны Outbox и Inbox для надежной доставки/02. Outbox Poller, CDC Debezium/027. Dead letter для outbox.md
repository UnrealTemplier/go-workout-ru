# Dead letter для outbox: изоляция безнадежных событий и эскалация алертов

## Условие

27. **Dead letter для outbox**: После N failures (например, 10) помечайте event как `dead_letter = TRUE` и алертите.

### Исходная формулировка

**Dead letter для outbox**: После N failures (например, 10) помечайте event как `dead_letter = TRUE` и алертите.

## Теория

В практике эксплуатации систем обмена сообщениями встречаются события, которые невозможно отправить ни при каких обстоятельствах: поврежденная схема данных, превышение максимального размера сообщения в брокере (`RecordTooLargeException`), фатальная ошибка десериализации (Poison Pill). Если Outbox Poller будет бесконечно повторять отправку такого 'ядовитого' события, он навсегда заблокирует очередь сообщений по данному агрегату (Head-of-Line Blocking). Паттерн Dead Letter Outbox решает эту проблему: если счетчик попыток превышает пороговое значение (\(N \ge 10\)), событие помечается как `dead_letter = TRUE`, исключается из основного цикла поллинга, а дежурной смене отправляется критический PagerDuty/Telegram алерт для ручного анализа инцидента.

## Решение по шагам

1. Добавьте в таблицу Outbox колонку `dead_letter BOOLEAN DEFAULT FALSE`.
2. В цикле поллера проверяйте условие `if event.Retries >= 10`.
3. Переводите событие в статус Dead Letter и фиксируйте причину сбоя.
4. Инициируйте отправку алерта в систему мониторинга.
5. Продемонстрируйте изоляцию ядовитого сообщения в `main`.

## Код решения

**`outbox_dead_letter.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type OutboxMessageItem struct {
	ID         string
	Payload    string
	Retries    int
	DeadLetter bool
	ErrorLog   string
}

type DeadLetterSupervisor struct {
	maxRetries int
}

func (s *DeadLetterSupervisor) HandleDispatch(msg *OutboxMessageItem, dispatchFunc func(string) error) {
	if msg.DeadLetter {
		fmt.Printf("[DLQ Bypass] Event %s is in DEAD LETTER state. Skipped by poller.\n", msg.ID)
		return
	}

	err := dispatchFunc(msg.Payload)
	if err != nil {
		msg.Retries++
		msg.ErrorLog = err.Error()
		fmt.Printf("[Poller Fail] Attempt %d/10 failed for %s: %v\n", msg.Retries, msg.ID, err)

		if msg.Retries >= s.maxRetries {
			msg.DeadLetter = true
			fmt.Printf("\n>>> [CRITICAL DLQ ESCALATION] Event %s exceeded %d retries! Marked DEAD_LETTER = TRUE. <<<\n",
				msg.ID, s.maxRetries)
			s.triggerAlert(msg)
		}
	}
}

func (s *DeadLetterSupervisor) triggerAlert(msg *OutboxMessageItem) {
	fmt.Printf("[PagerDuty Alert] P1_INCIDENT: Outbox Poison Pill detected! EventID=%s, Error='%s'\n\n",
		msg.ID, msg.ErrorLog)
}

func main() {
	supervisor := &DeadLetterSupervisor{maxRetries: 3} // Для наглядности лимит 3

	// "Ядовитое" сообщение, вызывающее постоянный отказ брокера
	poisonEvent := &OutboxMessageItem{
		ID:         "evt-poison-999",
		Payload:    "CORRUPTED_OVERSIZED_BINARY_PAYLOAD",
		Retries:    0,
		DeadLetter: false,
	}

	alwaysFail := func(payload string) error {
		return errors.New("kafka error: RecordTooLargeException (size exceeds max.request.size)")
	}

	fmt.Println("=== SIMULATING POISON PILL IN OUTBOX ===")
	for i := 1; i <= 4; i++ {
		supervisor.HandleDispatch(poisonEvent, alwaysFail)
	}

	fmt.Printf("Final Event Status:\n - DeadLetter: %v\n - Total Retries: %d\n - Is blocking queue: NO\n",
		poisonEvent.DeadLetter, poisonEvent.Retries)
}
```

ℹ️ Изоляция ядовитого события в Dead Letter Outbox после превышения лимита ретраев

## Под капотом

Индекс поллера обязан отфильтровывать мертвые записи: `CREATE INDEX idx_outbox_active ON outbox(id) WHERE processed = FALSE AND dead_letter = FALSE`. Благодаря этому предикату как только флаг `dead_letter` становится `TRUE`, строка физически исчезает из индекса поллера. Поллер мгновенно переходит к следующим здоровым событиям, ликвидируя эффект Head-of-Line Blocking.

## Подводные камни

1. Слишком низкий лимит ретраев (\(N=2\)): кратковременный сетевой сбой (flapping) отправит сотни вполне здоровых сообщений в DLQ.
2. Отсутствие механизма повторного запуска (DLQ Replay): после устранения проблемы администратор должен иметь возможность сбросить статус: `UPDATE outbox SET dead_letter = FALSE, retries = 0 WHERE id = $1`.

## На собеседовании

Вопрос: Что делать, если событие попало в Dead Letter в таблице Outbox: дропать или хранить?
Ответ: Категорически нельзя удалять! В финансовых и enterprise-системах потеря события означает невыполненный заказ или расхождение балансов. Запись хранится в DLQ со всеми метаданными ошибки. Инженер исправляет причину сбоя (например, увеличивает лимит размера сообщения в брокере) и запускает через Admin API процедуру безопасного повторного воспроизведения (Replay).
