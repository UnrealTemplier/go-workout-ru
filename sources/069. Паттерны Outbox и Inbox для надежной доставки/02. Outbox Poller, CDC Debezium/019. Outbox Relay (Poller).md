# Outbox Relay (Poller): интервальный опрос, индекс (sent_at, id) и накладные расходы

## Условие

19. **Outbox Relay (Poller).**: Реализуйте отдельный процесс, который каждые 500 мс читает `outbox WHERE sent_at IS NULL`, отправляет в Kafka, обновляет `sent_at`. Объясните, почему polling — простой, но создаёт нагрузку на БД, и как индекс на `(sent_at, id)` помогает.

### Исходная формулировка

**Outbox Relay (Poller).**: Реализуйте отдельный процесс, который каждые 500 мс читает `outbox WHERE sent_at IS NULL`, отправляет в Kafka, обновляет `sent_at`. Объясните, почему polling — простой, но создаёт нагрузку на БД, и как индекс на `(sent_at, id)` помогает.

## Теория

Outbox Relay — самый прямолинейный и надежный способ доставки событий из таблицы в брокер. Каждые \(N\) миллисекунд фоновый воркер выполняет `SELECT id, payload FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100`. Накладные расходы поллинга заключаются в том, что даже когда в системе нет новых заказов, воркер непрерывно бомбардирует СУБД запросами (Idle Query Overhead), создавая лишние чтения из буферного пула. Чтобы этот запрос не приводил к последовательному чтению всей таблицы (Seq Scan), создается составной индекс `CREATE INDEX idx_outbox_unsent ON outbox (sent_at, id) WHERE sent_at IS NULL`. Такой частичный индекс содержит указатели только на неотправленные строки, делая поиск мгновенным (Index Scan за 0.1 мс).

## Решение по шагам

1. Спроектируйте SQL-схему Outbox с полем `sent_at TIMESTAMP WITH TIME ZONE NULL`.
2. Создайте составной частичный индекс на `(sent_at, id)`.
3. Реализуйте структуру `RelayWorker` с тикером 500 мс.
4. Выполните цикл: чтение -> отправка в Kafka -> `UPDATE outbox SET sent_at = NOW() WHERE id = $1`.
5. Продемонстрируйте исполнение в `main`.

## Код решения

**`outbox_relay_sent_at.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxRecord struct {
	ID      int
	Payload string
	SentAt  *time.Time
}

type RelayDatabase struct {
	mu      sync.Mutex
	records []*OutboxRecord
}

func (db *RelayDatabase) FetchUnsent(limit int) []*OutboxRecord {
	db.mu.Lock()
	defer db.mu.Unlock()

	var unsent []*OutboxRecord
	for _, r := range db.records {
		if r.SentAt == nil {
			unsent = append(unsent, r)
			if len(unsent) >= limit {
				break
			}
		}
	}
	return unsent
}

func (db *RelayDatabase) MarkSent(id int) {
	db.mu.Lock()
	defer db.mu.Unlock()
	now := time.Now()
	for _, r := range db.records {
		if r.ID == id {
			r.SentAt = &now
			fmt.Printf("[DB Update] Outbox record ID=%d marked sent_at=%s\n", id, now.Format("15:04:05.000"))
			return
		}
	}
}

type KafkaPublisherMock struct{}

func (k *KafkaPublisherMock) Publish(payload string) error {
	fmt.Printf("[Kafka Publish] Sent event to cluster: %s\n", payload)
	return nil
}

func RunRelay(ctx context.Context, db *RelayDatabase, kafka *KafkaPublisherMock, interval time.Duration) {
	ticker := time.NewTicker(interval)
	defer ticker.Stop()

	fmt.Printf("[Relay] Polling loop started with interval %v...\n", interval)

	for {
		select {
		case <-ctx.Done():
			fmt.Println("[Relay] Shutting down poller...")
			return
		case <-ticker.C:
			batch := db.FetchUnsent(10)
			if len(batch) == 0 {
				continue // Нет новых записей
			}

			for _, rec := range batch {
				if err := kafka.Publish(rec.Payload); err == nil {
					db.MarkSent(rec.ID)
				}
			}
		}
	}
}

func main() {
	db := &RelayDatabase{
		records: []*OutboxRecord{
			{ID: 1, Payload: "order_created_101", SentAt: nil},
			{ID: 2, Payload: "order_created_102", SentAt: nil},
		},
	}
	kafka := &KafkaPublisherMock{}

	ctx, cancel := context.WithTimeout(context.Background(), 600*time.Millisecond)
	defer cancel()

	RunRelay(ctx, db, kafka, 250*time.Millisecond)
}
```

## Под капотом

Индекс `CREATE INDEX ON outbox(id) WHERE sent_at IS NULL` занимает минимальный объем, так как содержит только активные неотправленные события. Когда выполняется `sent_at = NOW()`, PostgreSQL автоматически удаляет ссылку на кортеж из частичного индекса. В результате размер индекса всегда стремится к нулю, обеспечивая субмиллисекундный `Index Scan` независимо от общего размера таблицы (даже если в ней 50 миллионов исторических записей).

## Подводные камни

1. Полнотабличное сканирование (Seq Scan) без частичного индекса: если забыть `WHERE sent_at IS NULL` в определении индекса, запрос по огромной таблице быстро истощит дисковый I/O.
2. Блокировки таблицы при плотном поллинге: интервал менее 50 мс приведет к высокой утилизации CPU СУБД.

## На собеседовании

Вопрос: Почему поле `sent_at TIMESTAMP NULL` предпочтительнее булевого `is_sent BOOLEAN`?
Ответ: Поле `sent_at` дает два колоссальных преимущества: 1) Содержит точное время фактической отправки, что критически важно для расчета Outbox Lag и аудита инцидентов; 2) Позволяет легко организовать очистку: `DELETE FROM outbox WHERE sent_at < NOW() - INTERVAL '14 days'`.
