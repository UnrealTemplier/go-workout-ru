# Transactional Inbox: идемпотентный потребитель и обработка дубликатов через Rollback

## Условие

33. **Transactional Inbox (Идемпотентный потребитель)**: Даже при использовании Outbox брокеры сообщений (такие как Kafka) гарантируют доставку только класса At-Least-Once (минимум один раз), что приводит к дублированию сообщений на стороне приемника. Реализуйте паттерн Transactional Inbox. На стороне принимающего сервиса:
    * При получении сообщения из брокера откройте транзакцию в БД.
    * Попробуйте вставить ID сообщения в таблицу `inbox_events` (`INSERT INTO inbox_events (message_id) VALUES ($1)`).
    * В рамках этой же транзакции выполните обновление бизнес-данных.
    * Если вставка ID сообщения упала по нарушению уникальности ключа (уникальный индекс по `message_id`), сделайте откат (`Rollback`) всей транзакции, проигнорировав дубликат.

### Исходная формулировка

## Теория

Паттерн Transactional Inbox — это высший стандарт надежности для консьюмеров сообщений. Он опирается на уникальное математическое свойство первичного ключа: в реляционной таблице не может существовать двух строк с одинаковым `PRIMARY KEY (message_id)`. При получении дубликата запрос `INSERT INTO inbox_events (message_id) VALUES ($1)` вызывает ошибку нарушения уникальности (`UniqueViolation / error 23505`). Консьюмер мгновенно перехватывает эту ошибку, вызывает `tx.Rollback()` и отправляет брокеру подтверждение (`Ack`), гарантируя, что бизнес-операция не будет выполнена повторно ни при каких обстоятельствах.

## Решение по шагам

1. Создайте структуру хранилища с эмуляцией ограничения уникальности первичного ключа.
2. Реализуйте транзакционную функцию с перехватом ошибки `ErrUniqueViolation`.
3. При успехе вставки выполните бизнес-действие и закоммитьте транзакцию.
4. При ошибке уникальности выполните Rollback и подтвердите оффсет в Kafka.
5. Продемонстрируйте обработку повторной доставки сообщения в `main`.

## Код решения

**`transactional_inbox_rollback.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

var ErrUniqueViolation = errors.New("pq: duplicate key value violates unique constraint 'inbox_events_pkey'")

type EnterpriseStore struct {
	mu           sync.Mutex
	inboxKeys    map[string]bool
	userBalance  float64
	actionsCount int
}

func (s *EnterpriseStore) HandleIncomingMessage(ctx context.Context, msgID string, amount float64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// BEGIN TRANSACTION
	fmt.Printf("[DB BEGIN] Opening transaction for incoming message: %s\n", msgID)

	// 1. Попытка вставки ID в inbox_events (PRIMARY KEY)
	if s.inboxKeys[msgID] {
		// ROLLBACK при дубликате
		fmt.Printf("[DB ROLLBACK] %v for message %s\n", ErrUniqueViolation, msgID)
		fmt.Printf("[Kafka ACK] Acknowledging duplicate message %s to Kafka (No business side effects!)\n\n", msgID)
		return nil // Игнорируем дубликат, подтверждая брокеру
	}

	// 2. Вставка успешна -> выполняем обновление бизнес-данных
	s.inboxKeys[msgID] = true
	s.userBalance += amount
	s.actionsCount++

	// 3. COMMIT
	fmt.Printf("[DB COMMIT] Business operation committed! Deposited $%.2f. New Balance: $%.2f\n",
		amount, s.userBalance)
	fmt.Printf("[Kafka ACK] Acknowledging processed message %s to Kafka.\n\n", msgID)
	return nil
}

func main() {
	store := &EnterpriseStore{
		inboxKeys:   make(map[string]bool),
		userBalance: 1000.0,
	}
	ctx := context.Background()
	msgID := "kafka-record-offset-5555"

	fmt.Println("=== DEMONSTRATING TRANSACTIONAL INBOX UNIQUE CONSTRAINT PATTERN ===")

	// Первая доставка (успех)
	fmt.Println("--- Attempt 1: First delivery ---")
	_ = store.HandleIncomingMessage(ctx, msgID, 250.0)

	// Вторая доставка (сетевой дубликат брокера)
	fmt.Println("--- Attempt 2: Duplicate delivery ---")
	_ = store.HandleIncomingMessage(ctx, msgID, 250.0)

	fmt.Printf("Final Verification:\n - Balance: $%.2f (Expected: $1250.00)\n - Operations Count: %d\n",
		store.userBalance, store.actionsCount)
}
```

ℹ️ Transactional Inbox с защитой уникальным индексом и автоматическим Rollback дубликатов

## Под капотом

В PostgreSQL код ошибки нарушения уникальности равен `23505`. Драйвер `lib/pq` или `pgx` возвращает структуру `*pgconn.PgError{Code: '23505'}`. Консьюмер проверяет `if pgErr.Code == '23505' { tx.Rollback(); return nil }`. Это исключает любые состояния гонки даже при одновременной обработке дубликатов на разных серверах.

## Подводные камни

1. Возврат ошибки в брокер при дубликате: если вернуть `err` из консьюмера, брокер решит, что сообщение не обработано, и снова отправит его. Дубликат должен подтверждаться успешным `Ack`.
2. Отсутствие уникального индекса в схеме БД: без `PRIMARY KEY` таблица примет дубликат.

## На собеседовании

Вопрос: Почему схема Transactional Inbox считается наиболее надежной в мировой практике микросервисов?
Ответ: Потому что она опирается на физические гарантии ACID реляционной СУБД. Никакие программные мьютексы, распределенные блокировки Redis или фильтры в оперативной памяти не дают такой математической надежности от дублирования, как атомарный коммит и ограничение уникальности первичного ключа базы данных.
