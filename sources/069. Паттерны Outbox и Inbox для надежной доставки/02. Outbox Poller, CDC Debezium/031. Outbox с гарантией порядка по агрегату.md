# Outbox с гарантией порядка по агрегату: строгий FIFO-стриминг через Kafka Partition Key

## Условие

31. **Outbox с гарантией порядка по агрегату.**: Доработайте Outbox: обеспечьте, что события по одному агрегату (например, `order_id`) публикуются строго в том порядке, в котором они были записаны.

### Исходная формулировка

**Outbox с гарантией порядка по агрегату.**: Доработайте Outbox: обеспечьте, что события по одному агрегату (например, `order_id`) публикуются строго в том порядке, в котором они были записаны.

## Теория

В распределенных бизнес-процессах порядок событий имеет решающее значение: событие `OrderPaid` не может быть обработано раньше, чем `OrderCreated`, а `OrderCancelled` не может обогнать `OrderPaid`. Гарантия сохранения порядка по агрегату (Causal Ordering per Aggregate) строится на двух правилах:
1) На уровне СУБД: события сортируются по монотонно возрастающему идентификатору `ORDER BY id ASC` или составному ключу `(aggregate_id, sequence_number ASC)`;
2) На уровне Kafka: в качестве `Record Key` всегда передается `aggregate_id`. Хэш-функция партиционирования (`murmur2(key) % num_partitions`) гарантирует, что абсолютно все события конкретного заказа попадут в одну и ту же партицию топика, где они будут записаны и прочитаны строго последовательно (FIFO).

## Решение по шагам

1. Опишите схему событий с полями `AggregateID` и монотонным `SequenceNumber`.
2. Реализуйте структуру `OrderedOutboxQueue` с гарантией сортировки по агрегату.
3. Смоделируйте вычисление партиции Kafka по `AggregateID`.
4. Докажите, что события одного заказа всегда попадают в одну партицию в строгом хронологическом порядке.
5. Проверьте вывод в консоли.

## Код решения

**`ordered_aggregate_outbox.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sort"
)

type AggregateEvent struct {
	ID             int
	AggregateID    string // OrderID
	SequenceNumber int    // 1: Created, 2: Paid, 3: Shipped
	EventType      string
}

func CalculateKafkaPartition(key string, totalPartitions int) int {
	hasher := fnv.New32a()
	_, _ = hasher.Write([]byte(key))
	return int(hasher.Sum32() % uint32(totalPartitions))
}

func main() {
	totalPartitions := 4

	// События двух разных заказов в базе
	events := []AggregateEvent{
		{ID: 1, AggregateID: "order-AAA", SequenceNumber: 1, EventType: "OrderCreated"},
		{ID: 2, AggregateID: "order-BBB", SequenceNumber: 1, EventType: "OrderCreated"},
		{ID: 3, AggregateID: "order-AAA", SequenceNumber: 2, EventType: "OrderPaid"},
		{ID: 4, AggregateID: "order-BBB", SequenceNumber: 2, EventType: "OrderPaid"},
		{ID: 5, AggregateID: "order-AAA", SequenceNumber: 3, EventType: "OrderShipped"},
	}

	// Сортировка по порядку записи (Strict Sequence FIFO)
	sort.Slice(events, func(i, j int) bool {
		return events[i].ID < events[j].ID
	})

	fmt.Println("=== STREAMING ORDERED OUTBOX EVENTS TO KAFKA PARTITIONS ===")
	for _, e := range events {
		partition := CalculateKafkaPartition(e.AggregateID, totalPartitions)
		fmt.Printf("[Outbox Dispatcher] Event #%d: Aggregate=%s (Seq=%d, Type=%-12s) -> Mapped to Kafka Partition [%d]\n",
			e.ID, e.AggregateID, e.SequenceNumber, e.EventType, partition)
	}

	fmt.Println("\nCONCLUSION: All events for order-AAA are guaranteed to arrive in partition [1] in strict sequence!")
}
```

ℹ️ Гарантия строгого порядка событий по агрегату через Kafka Partition Key

## Под капотом

Apache Kafka гарантирует порядок ТОЛЬКО в пределах одной партиции. Если передать `key = null`, брокер распределит сообщения по принципу Round-Robin по всем партициям. В этом случае событие `OrderPaid` из партиции 2 может быть вычитано раньше, чем `OrderCreated` из партиции 0. Использование `aggregate_id` в качестве ключа сообщения устраняет эту проблему на уровне архитектуры протокола.

## Подводные камни

1. Несколько воркеров обрабатывают события одного агрегата параллельно: если воркер 1 взял `OrderCreated`, а воркер 2 параллельно взял `OrderPaid`, воркер 2 может отправить событие в Kafka раньше.
2. Изменение количества партиций: добавление партиций в топик Kafka на лету меняет хэш-маппинг, из-за чего новые события старого агрегата могут уйти в другую партицию.

## На собеседовании

Вопрос: Как обеспечить строгий порядок в Outbox при работе пула параллельных воркеров?
Ответ: Применяется шардирование воркеров по хэшу `aggregate_id` или партиционирование таблицы outbox. Либо запрос вычитки группирует события по агрегату: воркер берет блокировку на уровне `aggregate_id` (`SELECT ... WHERE aggregate_id = $1 FOR UPDATE`), гарантируя, что все события одной сущности отправляются строго одним потоком.
