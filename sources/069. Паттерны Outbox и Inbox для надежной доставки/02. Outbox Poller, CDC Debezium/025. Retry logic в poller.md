# Retry logic в poller: безопасная обработка ошибок публикации и защита порядка

## Условие

25. **Retry logic в poller**: Если Kafka publish failed, не помечайте event как processed. Retry на следующей итерации.

### Исходная формулировка

**Retry logic в poller**: Если Kafka publish failed, не помечайте event как processed. Retry на следующей итерации.

## Теория

При возникновении ошибки во время отправки события в брокер (сетевой таймаут, переполнение буфера брокера, ошибка аутентификации SASL) Outbox Poller обязан строго соблюдать политику обработки ошибок:
1) Запись НЕ помечается как `processed` и остается со статусом `pending` (или `sent_at = NULL`);
2) Увеличивается счетчик попыток `retries = retries + 1`;
3) Сохраняется текст ошибки `last_error` и обновляется время следующей попытки `next_attempt_at`;
4) Если для данного агрегата требуется сохранение строгого порядка событий (FIFO Ordering), обработка последующих событий этого же агрегата должна быть приостановлена до успешной отправки текущего.

## Решение по шагам

1. Создайте структуру события с полями `Retries`, `LastError` и `Processed`.
2. Реализуйте метод `PublishWithRetry(event, broker)`.
3. Смоделируйте две неудачные попытки отправки и одну успешную.
4. Убедитесь, что статус `Processed = true` выставляется ТОЛЬКО после реального успеха.
5. Проверьте вывод жизненного цикла в консоли.

## Код решения

**`poller_retry_logic.go`**

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

type OutboxEventModel struct {
	ID        string
	Payload   string
	Retries   int
	LastError string
	Processed bool
}

type FlakyBrokerMock struct {
	attemptsLeft int
}

func (b *FlakyBrokerMock) Produce(payload string) error {
	if b.attemptsLeft > 0 {
		b.attemptsLeft--
		return errors.New("kafka cluster rebalancing: leader not available")
	}
	fmt.Printf("[Broker OK] Successfully written to partition: %s\n", payload)
	return nil
}

func ProcessEventAttempt(evt *OutboxEventModel, broker *FlakyBrokerMock) {
	fmt.Printf("[Poller Attempt %d] Trying to publish event %s...\n", evt.Retries+1, evt.ID)

	err := broker.Produce(evt.Payload)
	if err != nil {
		evt.Retries++
		evt.LastError = err.Error()
		// ВАЖНО: processed остается FALSE!
		fmt.Printf("[Poller FAIL] Error: %v. Event remains UNPROCESSED for next cycle.\n\n", err)
		return
	}

	// Успешная отправка
	evt.Processed = true
	evt.LastError = ""
	fmt.Printf("[Poller SUCCESS] Event %s marked as PROCESSED = TRUE.\n\n", evt.ID)
}

func main() {
	event := &OutboxEventModel{
		ID:        "evt-ord-retry-1",
		Payload:   "{\"order_id\":404,\"status\":\"pending\"}",
		Processed: false,
	}

	broker := &FlakyBrokerMock{attemptsLeft: 2} // Первые 2 попытки упадут

	fmt.Println("=== DEMONSTRATING POLLER RETRY LOGIC ===")

	// Итерация 1 (сбой)
	ProcessEventAttempt(event, broker)
	time.Sleep(50 * time.Millisecond)

	// Итерация 2 (сбой)
	ProcessEventAttempt(event, broker)
	time.Sleep(50 * time.Millisecond)

	// Итерация 3 (успех)
	ProcessEventAttempt(event, broker)

	fmt.Printf("Final Event State:\n - Processed: %v\n - Total Retries: %d\n",
		event.Processed, event.Retries)
}
```

ℹ️ Безопасная логика ретраев в Outbox Poller с сохранением статуса ошибки

## Под капотом

Если упавшая запись останется без задержки, poller будет бесконечно крутить ее в цикле, не давая обрабатываться другим событиям в батче. Для изоляции проблемных записей в запросе выборки используется условие `WHERE processed = false AND next_attempt_at <= NOW()`. Это позволяет отложить упавшую запись и немедленно продолжить обработку остальных здоровых событий.

## Подводные камни

1. Пометка `processed = true` при получении ошибки таймаута: фатальная потеря данных!
2. Отсутствие алерта при превышении порога попыток: если `retries > 10`, запись должна привлечь внимание инженера.

## На собеседовании

Вопрос: Что произойдет, если в Outbox лежат 3 события по одному заказу: Create, Pay, Cancel, и Pay упал с ошибкой?
Ответ: Если отправить Cancel раньше, чем Pay, нарушится причинно-следственная связь (Causal Ordering). Для событий одного агрегата (`aggregate_id`) отправка последующих событий строго блокируется до успешного завершения предыдущего. Для разных агрегатов события отправляются параллельно и независимо.
