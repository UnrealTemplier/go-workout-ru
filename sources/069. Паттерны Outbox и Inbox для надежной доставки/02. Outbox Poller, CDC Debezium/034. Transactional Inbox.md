# Transactional Inbox: проектирование DDL схемы и семантика ON CONFLICT DO NOTHING

## Условие

34. **Transactional Inbox: схема.**: В consumer-сервисе создайте таблицу `inbox`. При получении события из Kafka: `BEGIN; INSERT INTO inbox (event_id, ...) ON CONFLICT DO NOTHING; IF inserted THEN обработка; COMMIT;`. Объясните, как это защищает от дублей и обеспечивает at-least-once обработку ровно один раз.

### Исходная формулировка

**Transactional Inbox: схема.**: В consumer-сервисе создайте таблицу `inbox`. При получении события из Kafka: `BEGIN; INSERT INTO inbox (event_id, ...) ON CONFLICT DO NOTHING; IF inserted THEN обработка; COMMIT;`. Объясните, как это защищает от дублей и обеспечивает at-least-once обработку ровно один раз.

## Теория

В современных СУБД (PostgreSQL 9.5+, SQLite 3.24+) конструкция `INSERT INTO inbox (...) ON CONFLICT (event_id) DO NOTHING` позволяет объединить проверку и вставку в один атомарный SQL-запрос без генерации ошибки в журнал базы. Схема таблицы:
`CREATE TABLE inbox (`
`    event_id UUID PRIMARY KEY,`
`    handler_name VARCHAR(64) NOT NULL,`
`    received_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()`
);
При выполнении запроса СУБД возвращает количество затронутых строк (`RowsAffected`): если `RowsAffected == 1` — сообщение уникально, консьюмер выполняет бизнес-логику; если `RowsAffected == 0` — сообщение уже обрабатывалось, консьюмер делает мгновенный No-Op коммит.

## Решение по шагам

1. Спроектируйте каноническую DDL-схему таблицы `inbox`.
2. Реализуйте метод `ConsumeWithOnConflict(eventID, handler)`.
3. Проверяйте `RowsAffected`: при 1 — выполняйте бизнес-код, при 0 — пропускайте.
4. Зафиксируйте транзакцию через `Commit()`.
5. Продемонстрируйте работу механизма в `main`.

## Код решения

**`inbox_on_conflict_schema.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

// Каноническая схема DDL для PostgreSQL:
const InboxDDL = `
CREATE TABLE IF NOT EXISTS inbox (
    event_id UUID PRIMARY KEY,
    handler_name VARCHAR(64) NOT NULL,
    received_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);

-- Индекс для фоновой очистки старых записей
CREATE INDEX IF NOT EXISTS idx_inbox_received_at ON inbox(received_at);
`

type MockSQLDriver struct {
	mu         sync.Mutex
	inboxTable map[string]bool
}

// ExecOnConflict эмулирует:
// INSERT INTO inbox (event_id, handler_name) VALUES ($1, $2) ON CONFLICT (event_id) DO NOTHING;
func (d *MockSQLDriver) ExecOnConflict(eventID, handler string) int64 {
	d.mu.Lock()
	defer d.mu.Unlock()

	if d.inboxTable[eventID] {
		// Конфликт: строка уже есть, ничего не делаем
		return 0 // RowsAffected = 0
	}

	d.inboxTable[eventID] = true
	return 1 // RowsAffected = 1 (Успешно вставлено)
}

func ProcessKafkaEvent(eventID, payload string, db *MockSQLDriver) {
	fmt.Printf("[Kafka Consumer] Received event %s\n", eventID)

	// BEGIN TRANSACTION
	rowsAffected := db.ExecOnConflict(eventID, "OrderPaymentHandler")

	if rowsAffected == 1 {
		// Первичная доставка: выполняем полезную работу
		fmt.Printf(" -> [Business Logic] RowsAffected=1: Processing order payment for %s\n", payload)
	} else {
		// Дубликат: подавляем выполнение
		fmt.Printf(" -> [DEDUP] RowsAffected=0: Event %s already recorded in Inbox. Skipping business logic!\n", eventID)
	}

	// COMMIT TRANSACTION
	fmt.Printf("[Kafka Offset Commit] Committing offset for event %s\n\n", eventID)
}

func main() {
	fmt.Println("=== CANONICAL INBOX DDL SCHEMA ===")
	fmt.Println(InboxDDL)

	db := &MockSQLDriver{inboxTable: make(map[string]bool)}
	eventID := "evt-uuid-charge-99"

	fmt.Println("=== ITERATION 1: Fresh Event ===")
	ProcessKafkaEvent(eventID, "{\"charge\": 990.0}", db)

	fmt.Println("=== ITERATION 2: Network Duplicate ===")
	ProcessKafkaEvent(eventID, "{\"charge\": 990.0}", db)
}
```

## Под капотом

Конструкция `ON CONFLICT (event_id) DO NOTHING` работает без генерации ошибки в лог базы данных, что исключает засорение логов PostgreSQL ложными ошибками `duplicate key`. СУБД на уровне механизма `ExecInsert` проверяет уникальный индекс; если запись уже есть, операция прерывается со статусом `CommandComplete('INSERT 0 0')`, возвращая `RowsAffected() == 0`.

## Подводные камни

1. Забытое поле `handler_name`: если один топик слушают несколько разных независимых консьюмеров внутри одного сервиса, `event_id` заблокирует второго консьюмера. Составной ключ должен быть `PRIMARY KEY (event_id, handler_name)`.
2. Игнорирование проверки `RowsAffected`: если выполнить `INSERT ... ON CONFLICT` и не проверить возвращаемое число строк, бизнес-код выполнится дважды.

## На собеседовании

Вопрос: Чем отличается `ON CONFLICT DO NOTHING` от `INSERT` с перехватом ошибки 23505?
Ответ: `ON CONFLICT DO NOTHING` не приводит к отмене всей транзакции. При обычном `INSERT` ошибка уникальности переводит транзакцию в статус `current transaction is aborted, commands ignored until end of transaction block`. При `ON CONFLICT DO NOTHING` транзакция остается валидной и может продолжить выполнение других запросов или корректно закоммититься.
