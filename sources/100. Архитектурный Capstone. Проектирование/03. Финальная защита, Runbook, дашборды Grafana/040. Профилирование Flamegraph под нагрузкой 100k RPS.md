# Профилирование Flamegraph под нагрузкой 100k RPS (pprof analysis)

## Условие

Оснастите микросервисы профилированием net/http/pprof на выделенном внутреннем порту: снятие профилей CPU Flamegraph и профилей кучи под нагрузкой 100 000 RPS, выявление скрытых аллокаций памяти и устранение узких мест.

### Исходная формулировка

**Профилирование Flamegraph под нагрузкой 100k RPS (pprof analysis)**: Снимите и проведите углубленный анализ флеймграфов CPU и профилей аллокаций памяти (`go tool pprof -http`) при подаче 100 000 RPS: выявление неявных аллокаций в горячих путях кода, устранение накладных расходов рефлексии в JSON-сериализации и оптимизация работы сетевых буферов.

## Теория

Под экстремальной нагрузкой догадки об узких местах ошибочны. Единственный источник истины — **pprof профилирование**:
1. **CPU Profile & Flamegraph**:
   - Сэмплирует стек вызовов каждые 10 мс через таймер ядра ОС.
   - Чем шире вершина на Flamegraph, тем больше тактов процессора сжигает данная функция.
2. **Heap Profile**:
   - `inuse_space`: объем живой памяти прямо сейчас.
   - `alloc_space`: суммарный объем выделенной памяти за время теста (главный драйвер пауз GC).

## Решение по шагам

Подключите анонимный импорт `_ "net/http/pprof"`.
Вынесите диагностический сервер на отдельный внутренний порт `:6060`.
Опишите команды запуска визуализатора `go tool pprof -http`.
Проверьте доступность эндпоинта.

## Код решения

**`pprof_diagnostics.go`**

```go
package main

import (
	"fmt"
	_ "net/http/pprof"
)

func StartDiagnosticServer(port string) {
	fmt.Printf("[pprof]: Диагностический эндпоинт доступен на localhost%s/debug/pprof/\n", port)
	fmt.Println("Команды снятия профилей:")
	fmt.Println("1. CPU:    go tool pprof -http=:8081 http://localhost" + port + "/debug/pprof/profile?seconds=30")
	fmt.Println("2. Память: go tool pprof -http=:8082 http://localhost" + port + "/debug/pprof/heap")
}

func main() {
	StartDiagnosticServer(":6060")
}
```

## Под капотом

pprof в Go имеет малый оверхед в режиме простоя (< 0.5% CPU) и около 2-3% во время снятия 30-секундного профиля, что позволяет безопасно профилировать в проде под миллионной нагрузкой.

## Подводные камни

Открытие эндпоинтов `/debug/pprof` на публичном порту API-шлюза — критическая уязвимость безопасности.

## На собеседовании

В чем разница между alloc_objects и inuse_objects в pprof heap?
Ответ: alloc_objects показывает общее число созданных объектов за все время. Высокий alloc_objects при низком inuse_objects указывает на 'эффект молотилки' памяти (Churn), перегружающий сборщик мусора. inuse_objects показывает только живые объекты в памяти в данный момент.
