# Тестирование устойчивости к OOM Killer под пиковым давлением памяти

## Условие

Протестируйте поведение рантайма Go при приближении к жесткому лимиту памяти: активация GOMEMLIMIT, учащение циклов Garbage Collector и динамический троттлинг запросов для предотвращения аварийного завершения контейнера операционной системой (OOMKilled).

### Исходная формулировка

**Тестирование устойчивости к OOM Killer под пиковым давлением памяти**: Смоделируйте лавинообразный всплеск нагрузки: проверьте поведение рантайма Go при приближении к пороговому значению `GOMEMLIMIT`. Докажите, что агрессивный триггер сборщика мусора и активация адаптивного троттлинга запросов на уровне API-шлюза предотвращают завершение процесса операционной системой по сигналу SIGKILL (OOM).

## Теория

В контейнерах Kubernetes задается лимит cgroup: `resources.limits.memory: 2Gi`.
При превышении на 1 байт ядро Linux присылает `SIGKILL (exit code 137, OOMKilled)` без graceful shutdown.
**Защита через GOMEMLIMIT**:
1. Лимит cgroup: 2048 МБ.
2. В рантайме Go задается `GOMEMLIMIT = 1840 МБ` (90% от лимита контейнера).
3. 200 МБ резервируются на структуры ОС, стек потоков и оверхед Go рантайма.
4. При приближении к 1800 МБ GC Pacer учащает циклы сборки мусора, удерживая процесс ниже порога OOM Killer.

## Решение по шагам

Определите структуру `MemoryPressureGuard`.
Вызовите `debug.SetMemoryLimit` с запасом в 10% от cgroup лимита.
Объясните механику работы GC Pacer при пиковом давлении памяти.
Проверьте установку лимита.

## Код решения

**`oom_pressure_guard.go`**

```go
package main

import (
	"fmt"
	"runtime/debug"
)

type MemoryPressureGuard struct {
	limitBytes int64
}

func NewMemoryPressureGuard(limitMB int64) *MemoryPressureGuard {
	limit := limitMB * 1024 * 1024
	debug.SetMemoryLimit(limit)
	return &MemoryPressureGuard{limitBytes: limit}
}

func main() {
	guard := NewMemoryPressureGuard(1024)
	fmt.Printf("MemoryPressureGuard: установлен потолок рантайма Go = %d МБ\n", guard.limitBytes/1024/1024)
	fmt.Println("Рантайм Go агрессивно запустит сборку мусора, предотвращая SIGKILL от OOM Killer.")
}
```

## Под капотом

Если доступная память все равно исчерпана, рантайм Go активирует Assist Allocations, заставляя горутину-мутатор помогать сборщику мусора очищать память.

## Подводные камни

Установка GOMEMLIMIT слишком близко к физическому лимиту приведет к OOMKilled до завершения цикла GC.

## На собеседовании

Что такое 'GC Thrashing' и как GOMEMLIMIT от нее защищает?
Ответ: GC Thrashing возникает, когда объем постоянно живых объектов в куче почти равен лимиту памяти: сборщик мусора запускается непрерывно, сжигая 100% CPU. GOMEMLIMIT ограничивает долю процессорного времени сборщика мусора (максимум 50% CPU).
