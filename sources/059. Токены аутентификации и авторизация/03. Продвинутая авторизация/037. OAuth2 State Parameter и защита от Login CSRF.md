# OAuth2 State Parameter и защита от Login CSRF

## Условие

Всегда используйте криптографически случайный `state` параметр для защиты от CSRF. Без state ваш OAuth flow уязвим.

### Исходная формулировка

**OAuth2 state parameter**: Всегда используйте криптографически случайный `state` параметр для защиты от CSRF. Без state ваш OAuth flow уязвим.

## Теория

Параметр **`state` (RFC 6749 Section 10.12)** является обязательным элементом защиты от критической уязвимости **OAuth Login CSRF (Cross-Site Request Forgery)**.

### В чем заключается атака OAuth Login CSRF?
1. Атакующий начинает OAuth-логин в легитимный сервис (например, Spotify или онлайн-банк) через аккаунт Google атакующего.
2. На этапе редиректа браузера атакующего с кодом авторизации (`/callback?code=attacker_code`) атакующий **перехватывает и останавливает запрос**, не обменивая код.
3. Атакующий заманивает жертву на вредоносную страницу, которая заставляет браузер жертвы выполнить запрос:
   `GET https://bank.example.com/oauth/callback?code=attacker_code`
4. Если бэкенд банка не проверяет `state`, сервер банка обменяет `attacker_code` на токен и привяжет сессию жертвы к **аккаунту атакующего**!
5. Жертва считает, что зашла в свой банк, вводит реквизиты кредитной карты или загружает конфиденциальные документы, которые моментально становятся доступны атакующему.

### Как `state` нейтрализует угрозу:
- Перед редиректом на `/authorize` клиент генерирует криптографически случайный токен (минимум 128 бит энтропии).
- Токен сохраняется в браузере пользователя во временной защищенной сессионной куке (`HttpOnly`, `SameSite=Lax`, `Secure`).
- Тот же токен передается в query-параметре `state` в запросе к серверу авторизации.
- Сервер авторизации обязан вернуть ровно этот `state` без изменений в редиректе на `/callback`.
- Бэкенд клиента сверяет: `query.Get("state") == cookie.Value`. Если значения не совпадают или кука отсутствует — запрос немедленно блокируется.

## Решение по шагам

1. Создайте защищенную функцию генерации криптографически случайного `state`.
2. Реализуйте хэндлер `/login`, сохраняющий `state` в куку `oauth_state` и формирующий редирект.
3. Реализуйте хэндлер `/callback`, проверяющий совпадение `state` из URL с кукой через `subtle.ConstantTimeCompare`.
4. Удалите куку `oauth_state` сразу после проверки (одноразовость).
5. Продемонстрируйте блокировку CSRF-атаки, когда атакующий отправляет запрос с чужим `state`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/base64"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

// GenerateRandomState создает криптографический nonce (32 байта)
func GenerateRandomState() (string, error) {
	b := make([]byte, 32)
	if _, err := io.ReadFull(rand.Reader, b); err != nil {
		return "", err
	}
	return base64.RawURLEncoding.EncodeToString(b), nil
}

// LoginHandler — начало OAuth потока
func LoginHandler(w http.ResponseWriter, r *http.Request) {
	state, err := GenerateRandomState()
	if err != nil {
		http.Error(w, "Ошибка генерации state", http.StatusInternalServerError)
		return
	}

	// Сохраняем state в защищенную куку с коротким TTL (5 минут)
	http.SetCookie(w, &http.Cookie{
		Name:     "oauth_state",
		Value:    state,
		Path:     "/callback",
		MaxAge:   300,
		HttpOnly: true,
		Secure:   true,
		SameSite: http.SameSiteLaxMode, // Обязательно Lax для внешних редиректов!
	})

	authURL := fmt.Sprintf("https://idp.example.com/oauth/authorize?client_id=my_client&response_type=code&state=%s", state)
	http.Redirect(w, r, authURL, http.StatusFound)
}

// CallbackHandler — обработка возврата от IdP
func CallbackHandler(w http.ResponseWriter, r *http.Request) {
	receivedState := r.URL.Query().Get("state")
	code := r.URL.Query().Get("code")

	if receivedState == "" || code == "" {
		http.Error(w, "Отсутствуют обязательные параметры", http.StatusBadRequest)
		return
	}

	cookie, err := r.Cookie("oauth_state")
	if err != nil || cookie.Value == "" {
		http.Error(w, "CSRF обнаружен: отсутствует oauth_state кука!", http.StatusForbidden)
		return
	}

	// Защита от timing-атак при сравнении строк
	if subtle.ConstantTimeCompare([]byte(receivedState), []byte(cookie.Value)) != 1 {
		http.Error(w, "CSRF атака заблокирована: state не совпадает с сессией!", http.StatusForbidden)
		return
	}

	// Очищаем куку после успешного использования (one-time use)
	http.SetCookie(w, &http.Cookie{
		Name:     "oauth_state",
		Value:    "",
		Path:     "/callback",
		MaxAge:   -1,
		HttpOnly: true,
	})

	w.WriteHeader(http.StatusOK)
	_, _ = fmt.Fprintf(w, "Успешная валидация state! Код авторизации: %s принят к обмену.", code)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/login", LoginHandler)
	mux.HandleFunc("/callback", CallbackHandler)

	ts := httptest.NewServer(mux)
	defer ts.Close()

	// 1. Легитимный пользователь инициирует вход
	reqLogin, _ := http.NewRequest("GET", ts.URL+"/login", nil)
	wLogin := httptest.NewRecorder()
	LoginHandler(wLogin, reqLogin)

	cookie := wLogin.Result().Cookies()[0]
	redirectLocation := wLogin.Header().Get("Location")
	fmt.Println("=== 1. Клиент инициировал логин ===")
	fmt.Printf("Выставлена Cookie: %s=%s\n", cookie.Name, cookie.Value)
	fmt.Printf("Redirect URL:      %s\n\n", redirectLocation)

	// 2. Легитимный возврат: state в query совпадает с кукой
	reqCallbackGood, _ := http.NewRequest("GET", ts.URL+"/callback?code=good_code_123&state="+cookie.Value, nil)
	reqCallbackGood.AddCookie(cookie)
	wCallbackGood := httptest.NewRecorder()
	CallbackHandler(wCallbackGood, reqCallbackGood)
	fmt.Println("=== 2. Легитимный возврат (Valid State) ===")
	fmt.Printf("HTTP Status: %d, Ответ: %s\n\n", wCallbackGood.Code, wCallbackGood.Body.String())

	// 3. Атака Login CSRF: жертве подсунули запрос с чужим кодом и чужим state
	reqCallbackCSRF, _ := http.NewRequest("GET", ts.URL+"/callback?code=attacker_code_666&state=attacker_state_fake", nil)
	reqCallbackCSRF.AddCookie(cookie) // У жертвы в куке ее собственный state, а в query — атакующего!
	wCallbackCSRF := httptest.NewRecorder()
	CallbackHandler(wCallbackCSRF, reqCallbackCSRF)
	fmt.Println("=== 3. Атака Login CSRF (State mismatch) ===")
	fmt.Printf("HTTP Status: %d, Ошибка: %s\n", wCallbackCSRF.Code, wCallbackCSRF.Body.String())
}
```

## Под капотом

Почему кука state обязана иметь флаг `SameSite=Lax`, а не `SameSite=Strict`? При `SameSite=Strict` браузер **не отправит** куку, если переход на страницу происходит с другого домена (внешний 302-редирект от IdP `accounts.google.com` на `myapp.com/callback`). В результате пользователь получит ошибку авторизации. `SameSite=Lax` разрешает отправку кук при top-level навигации методом `GET`, что идеально подходит для OAuth callback, при этом надежно защищая от межсайтовых POST-запросов.

## Подводные камни

1. **Статический или детерминированный state:** Использование в качестве state хеша от `user_id` или фиксированной строки делает защиту фиктивной: атакующий легко предскажет значение.
2. **Отсутствие привязки к браузеру:** Если state проверяется только на сервере авторизации (например, «сервер помнит, что выдал этот state»), но не привязан к сессии конкретного браузера через куку, атакующий может получить валидный state в своей сессии и передать жертве.
3. **Хранение в LocalStorage:** При редиректе на внешний IdP страница выгружается из памяти, а при возврате SPA может не успеть прочитать LocalStorage до вызова API.

## На собеседовании

**Вопрос с собеседования:** Что произойдет, если в архитектуре с микросервисами бэкенд не использует сессионные куки (stateless architecture), но обязан защититься от OAuth Login CSRF через параметр state?
**Ответ:** В stateless-архитектуре параметр `state` формируется в виде криптографически подписанного или зашифрованного токена (Encrypted State / Signed JWT):
1) Бэкенд генерирует случайный nonce и подписывает его HMAC-ключом сервера вместе с таймстемпом: `state = Base64URL(nonce + "." + exp + "." + HMAC(nonce + exp, secret))`.
2) Чтобы привязать state к конкретному пользователю без кук сессии, в HMAC подмешивается хеш временного анонимного идентификатора устройства/TLS-отпечатка.
3) При возврате на `/callback` бэкенд проверяет валидность HMAC-подписи и срок жизни таймстемпа. Это исключает необходимость серверного хранилища состояний.
