# Refresh Token Rotation в OAuth2

## Условие

Автоматически обновляйте access tokens и обрабатывайте refresh token revocation.

### Исходная формулировка

**Refresh token rotation в OAuth2**: Автоматически обновляйте access tokens и обрабатывайте refresh token revocation.

## Теория

Спецификация **OAuth 2.0 Security BCP (Best Current Practice)** требует обязательного использования **Refresh Token Rotation (RTR)** для всех приложений.

### Уязвимость классических статичных Refresh токенов:
В классическом OAuth 2.0 Refresh Token был долгоживущим (месяцы или годы) и многоразовым. Если атакующий похищал Refresh токен (из скомпрометированного приложения или перехваченного хранилища), он получал вечный доступ к аккаунту жертвы в обход короткого срока жизни Access токена!

### Механизм Refresh Token Rotation (RTR):
1. При каждом обращении к эндпоинту `/token?grant_type=refresh_token` старый Refresh Token **немедленно инвалидируется**.
2. Клиенту возвращается совершенно новый `access_token` и новый одноразовый `refresh_token`.
3. **Автоматическое обнаружение кражи (Token Family / Replay Detection):**
   - Все токены сессии объединяются в семью (`Token Family ID`).
   - Если сервер авторизации фиксирует попытку использовать **уже инвалидированный (старый)** Refresh Token, это означает, что произошла кража: либо атакующий использовал токен раньше жертвы, либо жертва пытается войти после того, как атакующий провернул ротацию!
   - Сервер фиксирует инцидент безопасности и **немедленно аннулирует ВСЮ семью токенов** (все активные access и refresh токены этой сессии), принудительно разлогинивая пользователя на всех устройствах.

## Решение по шагам

1. Создайте модель данных для сессии с `FamilyID`, текущим валидным `CurrentToken` и списком аннулированных токенов.
2. Реализуйте ротацию: выпуск нового токена и перевод старого в статус инвалидированного.
3. Реализуйте детекцию повторного использования: если предъявлен ранее использованный токен — отозвать всю семью.
4. Продемонстрируйте корректную последовательную ротацию токенов.
5. Продемонстрируйте перехват атаки повторного использования и полную блокировку сессии.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"io"
	"sync"
	"time"
)

type TokenFamily struct {
	FamilyID       string
	UserID         string
	CurrentToken   string
	ConsumedTokens map[string]time.Time // токены, которые уже были успешно ротированы
	IsRevoked      bool
}

type TokenService struct {
	mu       sync.Mutex
	families map[string]*TokenFamily // FamilyID -> Family
	tokenMap map[string]string       // RefreshToken -> FamilyID
}

func NewTokenService() *TokenService {
	return &TokenService{
		families: make(map[string]*TokenFamily),
		tokenMap: make(map[string]string),
	}
}

func generateToken(prefix string) string {
	b := make([]byte, 16)
	_, _ = io.ReadFull(rand.Reader, b)
	return fmt.Sprintf("%s_%s", prefix, hex.EncodeToString(b))
}

// IssueInitialSession создает новую семью токенов при логине
func (s *TokenService) IssueInitialSession(userID string) (accessToken, refreshToken string) {
	s.mu.Lock()
	defer s.mu.Unlock()

	familyID := generateToken("fam")
	refreshToken = generateToken("rt")
	accessToken = generateToken("at")

	family := &TokenFamily{
		FamilyID:       familyID,
		UserID:         userID,
		CurrentToken:   refreshToken,
		ConsumedTokens: make(map[string]time.Time),
		IsRevoked:      false,
	}

	s.families[familyID] = family
	s.tokenMap[refreshToken] = familyID
	return accessToken, refreshToken
}

// RotateToken выполняет одноразовую ротацию Refresh токена
func (s *TokenService) RotateToken(oldRefreshToken string) (newAccess, newRefresh string, err error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	familyID, exists := s.tokenMap[oldRefreshToken]
	if !exists {
		return "", "", errors.New("неизвестный refresh токен")
	}

	family := s.families[familyID]

	// 1. Проверка: семья уже была отозвана
	if family.IsRevoked {
		return "", "", errors.New("сессия полностью заблокирована из-за подозрительной активности")
	}

	// 2. ДЕТЕКЦИЯ ПОВТОРНОГО ИСПОЛЬЗОВАНИЯ (REPLAY ATTACK)
	if _, wasConsumed := family.ConsumedTokens[oldRefreshToken]; wasConsumed {
		// КРИТИЧЕСКИЙ ИНЦИДЕНТ: Кто-то пытается использовать старый токен!
		family.IsRevoked = true // Отзываем ВСЮ семью немедленно!
		return "", "", fmt.Errorf("SECURITY ALERT: Обнаружено повторное использование токена %s! Вся семья %s аннулирована!", oldRefreshToken, familyID)
	}

	// 3. Проверка: передан ли текущий валидный токен
	if family.CurrentToken != oldRefreshToken {
		family.IsRevoked = true
		return "", "", errors.New("рассинхронизация токенов: сессия аннулирована")
	}

	// 4. Успешная ротация: переводим старый токен в статус использованных
	family.ConsumedTokens[oldRefreshToken] = time.Now()
	newRefresh = generateToken("rt")
	newAccess = generateToken("at")

	family.CurrentToken = newRefresh
	s.tokenMap[newRefresh] = familyID

	return newAccess, newRefresh, nil
}

func main() {
	svc := NewTokenService()

	// 1. Первичная авторизация пользователя
	at1, rt1 := svc.IssueInitialSession("usr_alice_42")
	fmt.Println("=== 1. Успешный логин пользователя ===")
	fmt.Printf("Access Token 1:  %s\n", at1)
	fmt.Printf("Refresh Token 1: %s\n\n", rt1)

	// 2. Легитимное обновление токена (первая ротация)
	at2, rt2, err := svc.RotateToken(rt1)
	if err != nil {
		panic(err)
	}
	fmt.Println("=== 2. Первая ротация (Легитимный клиент) ===")
	fmt.Printf("Access Token 2:  %s\n", at2)
	fmt.Printf("Refresh Token 2: %s (rt1 теперь инвалидирован!)\n\n", rt2)

	// 3. Атака злоумышленника: попытка повторного использования перехваченного rt1
	fmt.Println("=== 3. Атака Replay: Злоумышленник пытается использовать старый rt1 ===")
	_, _, errReplay := svc.RotateToken(rt1)
	fmt.Printf("Результат: %v\n\n", errReplay)

	// 4. Проверка: легитимный клиент пытается использовать свой rt2
	fmt.Println("=== 4. Попытка легитимного клиента обновить rt2 после инцидента ===")
	_, _, errVictim := svc.RotateToken(rt2)
	fmt.Printf("Результат: %v (Клиент защищен, сессия принудительно завершена!)\n", errVictim)
}
```

## Под капотом

Почему обнаружение повторного использования (Replay Detection) гарантирует безопасность? Если токен был похищен по сети, либо жертва, либо хакер сделает запрос на ротацию первым. Тот, кто придет вторым, неизбежно предъявит уже использованный (старый) токен. Сервер авторизации не знает, кто из них легитимный пользователь, поэтому единственно безопасная стратегия нулевого доверия (Zero Trust) — мгновенно уничтожить всю семью токенов и заставить пользователя пройти повторную MFA-аутентификацию.

## Подводные камни

1. **Проблема параллельных запросов (Race Conditions):** При открытии веб-приложения 5 параллельных запросов могут одновременно обнаружить истечение access token и инициировать 5 запросов ротации с одним и тем же refresh token. Без буфера задержки (Grace Period 10–30 секунд) сервер ошибочно примет параллельные запросы за Replay-атаку и разлогинит пользователя.
2. **Бесконечный рост списка consumed токенов:** Запись каждого использованного токена без TTL переполнит базу данных. Использованные токены должны храниться ровно столько, сколько составляет максимальный срок жизни сессии.
3. **Хранение токенов в открытом виде:** В базе данных Refresh токены должны храниться исключительно в виде хешей SHA-256.

## На собеседовании

**Вопрос с собеседования:** Как решить проблему «ложного срабатывания» RTR (Refresh Token Rotation), когда из-за нестабильной мобильной сети клиент отправил запрос на ротацию, сервер выдал новую пару, но сетевой пакет с ответом потерялся по дороге к клиенту?
**Ответ:** Реализуется паттерн **Grace Period (Окно терпимости):**
1) При успешной ротации токена \(RT_1 \to RT_2\) сервер помечает \(RT_1\) как устаревший, но сохраняет ссылку на выданный \(RT_2\) с тайм-аутом Grace Period (например, 15–30 секунд).
2) Если в течение этого 15-секундного окна клиент повторно присылает \(RT_1\) (потому что мобильный HTTP-клиент сделал Retry после таймаута сети), сервер не паникует и не блокирует семью, а повторно возвращает **тот же самый уже сгенерированный \(RT_2\)**.
3) Если же \(RT_1\) придет после истечения Grace Period — это квалифицируется как стопроцентная Replay-атака, и сессия немедленно отзывается.
