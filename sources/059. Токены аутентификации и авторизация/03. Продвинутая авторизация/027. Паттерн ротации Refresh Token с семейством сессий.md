# Паттерн ротации Refresh Token с семейством сессий (Token Family)

## Условие

Реализуйте хранение refresh tokens в БД с полями `token_hash`, `family_id`, `issued_at`, `expires_at`, `revoked`. При обмене refresh → access выдавайте новую пару, инвалидируйте старую. Объясните, как обнаружить кражу токена.

### Исходная формулировка

**Refresh Token Rotation.**: Реализуйте хранение refresh tokens в БД с полями `token_hash`, `family_id`, `issued_at`, `expires_at`, `revoked`. При обмене refresh → access выдавайте новую пару, инвалидируйте старую. Объясните, как это защищает от replay-атак и parallel refresh.

## Теория

Простая замена одного refresh-токена на другой недостаточна для надежного противодействия краже учетных данных.

### Концепция Token Family (Семейство токенов / RFC 6749 BCP):
Когда пользователь авторизуется, создается **Семейство токенов (`family_id` / UUID)**, представляющее конкретный сеанс на одном устройстве.
Каждый refresh-токен в рамках сеанса образует последовательную генеалогическую цепочку:
$$R_1 \rightarrow R_2 \rightarrow R_3 \rightarrow \dots$$

### Механизм обнаружения кражи (Compromise Detection):
Представьте, что злоумышленник украл токен \(R_2\) из базы данных браузера или через MITM:
1. **Сценарий А (Легитимный пользователь опережает вора):**
   - Легитимный пользователь обращается к `/auth/refresh` с токеном \(R_2\).
   - Сервер помечает \(R_2\) как `revoked = true` и выдает токен \(R_3\).
   - Позже атакующий пытается использовать украденный токен \(R_2\).
   - **Срабатывание детектора:** Сервер видит, что токен \(R_2\) **уже был использован ранее (Replay Attack)**! Это гарантирует факт компрометации!
   - **Меры безопасности:** Сервер не просто отклоняет запрос, а **НЕМЕДЛЕННО ИНВАЛИДИРУЕТ ВСЕ ТОКЕНЫ В РАМКАХ ДАННОГО `family_id`** (включая \(R_3\)). Злоумышленник теряет доступ, а легитимного пользователя просят войти заново по логину и паролю.

## Решение по шагам

1. Создадим модель `RefreshToken` с полями `TokenHash`, `FamilyID`, `IssuedAt`, `ExpiresAt`, `Revoked`.
2. Реализуем хранилище `TokenFamilyStore` на базе `sync.Mutex`.
3. Напишем функцию `RotateRefreshToken(rawToken)`.
4. Реализуем обнаружение кражи: если `record.Revoked == true`, отзываем всё семейство `FamilyID`.
5. Продемонстрируем сценарий атаки с аннулированием всего сеанса.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"time"
)

type RefreshToken struct {
	TokenHash string
	FamilyID  string    // Уникальный ID цепочки сессии устройства
	UserID    string
	IssuedAt  time.Time
	ExpiresAt time.Time
	Revoked   bool
}

type TokenFamilyStore struct {
	mu     sync.Mutex
	tokens map[string]*RefreshToken // hash -> record
}

func NewTokenFamilyStore() *TokenFamilyStore {
	return &TokenFamilyStore{tokens: make(map[string]*RefreshToken)}
}

func hashToken(raw string) string {
	h := sha256.Sum256([]byte(raw))
	return hex.EncodeToString(h[:])
}

// IssueNewFamily выпускает первый токен нового семейства при первичном логине
func (s *TokenFamilyStore) IssueNewFamily(userID string) (string, string) {
	familyID := fmt.Sprintf("fam_%d", time.Now().UnixNano())
	rawToken := generateRandomString(32)
	h := hashToken(rawToken)

	s.mu.Lock()
	s.tokens[h] = &RefreshToken{
		TokenHash: h,
		FamilyID:  familyID,
		UserID:    userID,
		IssuedAt:  time.Now(),
		ExpiresAt: time.Now().Add(30 * 24 * time.Hour),
		Revoked:   false,
	}
	s.mu.Unlock()

	return rawToken, familyID
}

// RotateToken выполняет ротацию с обнаружением компрометации
func (s *TokenFamilyStore) RotateToken(oldRawToken string) (string, error) {
	oldHash := hashToken(oldRawToken)

	s.mu.Lock()
	defer s.mu.Unlock()

	record, exists := s.tokens[oldHash]
	if !exists {
		return "", errors.New("token not found")
	}

	// ОБНАРУЖЕНИЕ КРАЖИ ТОКЕНА (Compromise Detection)!
	if record.Revoked {
		// Кто-то повторно использует уже отозванный токен!
		// Немедленно аннулируем ВСЕ токены этого семейства!
		revokedCount := 0
		for _, t := range s.tokens {
			if t.FamilyID == record.FamilyID {
				t.Revoked = true
				revokedCount++
			}
		}
		return "", fmt.Errorf("🚨 КРИТИЧЕСКАЯ УГРОЗА: зафиксирована кража токена! Все %d токенов семейства '%s' отозваны!",
			revokedCount, record.FamilyID)
	}

	// Помечаем старый токен как отозванный
	record.Revoked = true

	// Выпускаем новый токен в том же семействе
	newRaw := generateRandomString(32)
	newHash := hashToken(newRaw)

	s.tokens[newHash] = &RefreshToken{
		TokenHash: newHash,
		FamilyID:  record.FamilyID,
		UserID:    record.UserID,
		IssuedAt:  time.Now(),
		ExpiresAt: time.Now().Add(30 * 24 * time.Hour),
		Revoked:   false,
	}

	return newRaw, nil
}

func generateRandomString(bytesLen int) string {
	b := make([]byte, bytesLen)
	_, _ = rand.Read(b)
	return hex.EncodeToString(b)
}

func main() {
	store := NewTokenFamilyStore()

	fmt.Println("=== 1. Первичный вход: создание Token Family ===")
	r1, familyID := store.IssueNewFamily("usr_4492")
	fmt.Printf("Семейство:  %s\n", familyID)
	fmt.Printf("Токен R1:   %s...\n\n", r1[:16])

	// 2. Легитимный пользователь обновляет сессию R1 -> R2
	fmt.Println("=== 2. Легитимная ротация сессии: R1 -> R2 ===")
	r2, err := store.RotateToken(r1)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Токен R2:   %s...\n\n", r2[:16])

	// 3. Злоумышленник украл старый токен R1 и пытается обновить его!
	fmt.Println("=== 3. Атака: злоумышленник пытается использовать старый R1 ===")
	_, attackErr := store.RotateToken(r1)
	fmt.Printf("Результат детектора кражи:\n%v\n\n", attackErr)

	// 4. Проверяем, что даже новый токен легитимного пользователя R2 теперь заблокирован
	fmt.Println("=== 4. Проверка состояния сессии легитимного пользователя (R2) ===")
	_, userErr := store.RotateToken(r2)
	fmt.Printf("Попытка использования R2 легитимным пользователем:\n%v\n", userErr)
	fmt.Println("(Пользователь принудительно разлогинен и защищен от несанкционированных действий вора)")
}
```

## Под капотом

В реляционных СУБД (PostgreSQL) таблица создается со схемой:
```sql
CREATE TABLE refresh_tokens (
    token_hash VARCHAR(64) PRIMARY KEY,
    family_id UUID NOT NULL,
    user_id UUID NOT NULL,
    revoked BOOLEAN NOT NULL DEFAULT FALSE,
    expires_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_family_id ON refresh_tokens(family_id);
```
Транзакция ротации использует `SELECT ... FOR UPDATE` для блокировки строки. Если `revoked = true`, выполняется каскадный отзыв `UPDATE refresh_tokens SET revoked = true WHERE family_id = $1`.

## Подводные камни

1. **Удаление старых токенов вместо пометки `revoked = true`:** Если удалять старый токен из базы при ротации, то при атаке повторного воспроизведения сервер вернет `token not found`, и система **никогда не узнает, что токен был украден**! Хранить использованные токены необходимо до истечения срока их годности.
2. **Отсутствие фонового клинера:** Удаляйте записи, у которых `expires_at < NOW()`, чтобы база не разрасталась до гигабайт.
3. **Гонки параллельных запросов:** Несколько параллельных вкладок браузера могут одновременно запросить refresh. Предусмотрите короткий Grace Period (10–15 секунд) для параллельных обращений.

## На собеседовании

**Вопрос с собеседования в Wildberries/Ozon:** «Как в архитектуре аутентификации работает механизм обнаружения кражи токенов (Compromise Detection) с использованием Token Families?»
**Ответ:** Каждому сеансу присваивается идентификатор семейства `family_id`. При обновлении токена старый токен не удаляется из БД, а помечается как использованный (`revoked = true`). 
Если в систему поступает запрос с токеном, который уже помечен как использованный, это означает, что один и тот же токен предъявляется во второй раз — произошло повторное использование украденных учетных данных. 
В этот момент срабатывает детектор компрометации: система немедленно аннулирует абсолютно все токены данного `family_id`. В результате атакующий лишается доступа, а легитимный пользователь принудительно отправляется на повторный ввод пароля с уведомлением о попытке взлома.
