# OAuth2 Authorization Code Flow

## Условие

Реализуйте полный flow: redirect на провайдера → получение code → обмен на access/refresh token → использование access token.

### Исходная формулировка

**OAuth2 Authorization Code Flow**: Реализуйте полный flow: redirect на провайдера → получение code → обмен на access/refresh token → использование access token.

## Теория

Протокол **OAuth 2.0 (RFC 6749)** — отраслевой стандарт делегирования авторизации. Ключевой сценарий для веб-приложений с бэкендом — **Authorization Code Grant** (трехсторонний поток с участием Клиента, Владельца ресурса и Сервера авторизации).

Архитектура потока разделена на два канала передачи данных:
1. **Front-Channel (Небезопасный канал через браузер пользователя):**
   - Клиент перенаправляет браузер на `/authorize` с параметрами: `client_id`, `redirect_uri`, `response_type=code`, `scope`, `state`.
   - Сервер авторизации аутентифицирует пользователя и запрашивает согласие (Consent).
   - В случае согласия сервер авторизации возвращает браузер редиректом на `redirect_uri` с одноразовым временным кодом (`code`) и тем же `state`.
2. **Back-Channel (Безопасный прямой канал сервер-сервер через TLS):**
   - Бэкенд клиента отправляет прямой HTTP POST-запрос на `/token` сервера авторизации, передавая `code`, `client_id`, `client_secret` и `redirect_uri`.
   - Сервер авторизации валидирует код (проверяя срок жизни ~30–60 секунд и одноразовость) и учетные данные клиента, после чего возвращает JSON с `access_token` и `refresh_token`.

**Почему код авторизации передается через Front-Channel, а токены — строго через Back-Channel?**
Если бы сам `access_token` возвращался во Front-Channel (как это делалось в устаревшем и небезопасном Implicit Flow), токен оседал бы в истории браузера, логах прокси-серверов, заголовках Referer и был бы доступен вредоносному JavaScript при XSS. Одноразовый короткоживущий `code` бесполезен для атакующего без знания `client_secret`, хранящегося строго на бэкенде клиента.

## Решение по шагам

1. Создайте структуры для токенов, кодов авторизации и профиля пользователя.
2. Реализуйте тестовый Сервер Авторизации с эндпоинтами `/authorize` и `/token`.
3. Реализуйте Бэкенд Клиента с эндпоинтами `/login` (инициация потока) и `/callback` (прием кода и обмен на токены).
4. Продемонстрируйте полный цикл: редирект, выдача кода, server-to-server обмен кода на `access_token` и `refresh_token`.
5. Продемонстрируйте запрос к защищенному API ресурса с заголовком `Authorization: Bearer <access_token>`.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
	"sync"
	"time"
)

// AuthServer — симулятор OAuth2 сервера авторизации
type AuthServer struct {
	mu           sync.Mutex
	codes        map[string]AuthCode
	clients      map[string]string // client_id -> client_secret
	validTokens  map[string]string // access_token -> user_id
}

type AuthCode struct {
	UserID      string
	ClientID    string
	RedirectURI string
	ExpiresAt   time.Time
}

type TokenResponse struct {
	AccessToken  string `json:"access_token"`
	TokenType    string `json:"token_type"`
	ExpiresIn    int    `json:"expires_in"`
	RefreshToken string `json:"refresh_token,omitempty"`
}

func NewAuthServer() *AuthServer {
	return &AuthServer{
		codes:       make(map[string]AuthCode),
		clients:     map[string]string{"client-app-123": "secret-xyz-789"},
		validTokens: make(map[string]string),
	}
}

// Эндпоинт /token сервера авторизации
func (as *AuthServer) HandleToken(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Метод не поддерживается", http.StatusMethodNotAllowed)
		return
	}

	clientID := r.FormValue("client_id")
	clientSecret := r.FormValue("client_secret")
	code := r.FormValue("code")
	grantType := r.FormValue("grant_type")

	as.mu.Lock()
	defer as.mu.Unlock()

	// 1. Валидация клиента
	secret, ok := as.clients[clientID]
	if !ok || secret != clientSecret {
		http.Error(w, `{"error":"invalid_client"}`, http.StatusUnauthorized)
		return
	}

	if grantType != "authorization_code" {
		http.Error(w, `{"error":"unsupported_grant_type"}`, http.StatusBadRequest)
		return
	}

	// 2. Валидация и одноразовое потребление кода
	authCode, exists := as.codes[code]
	if !exists || time.Now().After(authCode.ExpiresAt) || authCode.ClientID != clientID {
		http.Error(w, `{"error":"invalid_grant"}`, http.StatusBadRequest)
		return
	}
	delete(as.codes, code) // Код ОБЯЗАН быть одноразовым!

	// 3. Выпуск токенов
	accessToken := fmt.Sprintf("at_%s_%d", authCode.UserID, time.Now().UnixNano())
	refreshToken := fmt.Sprintf("rt_%s_%d", authCode.UserID, time.Now().UnixNano())
	as.validTokens[accessToken] = authCode.UserID

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(TokenResponse{
		AccessToken:  accessToken,
		TokenType:    "Bearer",
		ExpiresIn:    3600,
		RefreshToken: refreshToken,
	})
}

func main() {
	as := NewAuthServer()
	authServerMux := http.NewServeMux()
	authServerMux.HandleFunc("/token", as.HandleToken)
	ts := httptest.NewServer(authServerMux)
	defer ts.Close()

	// 1. Инициация потока: сохранение кода на сервере авторизации
	authCodeValue := "sec_code_abc_999"
	as.mu.Lock()
	as.codes[authCodeValue] = AuthCode{
		UserID:      "usr_42",
		ClientID:    "client-app-123",
		RedirectURI: "https://myclient.com/callback",
		ExpiresAt:   time.Now().Add(60 * time.Second),
	}
	as.mu.Unlock()

	fmt.Println("=== 1. Front-channel: Сервер вернул редирект с кодом авторизации ===")
	fmt.Printf("Redirected code: %s, state: state_csrf_token_1\n", authCodeValue)

	// 2. Back-channel: Бэкенд клиента делает POST /token
	fmt.Println("\n=== 2. Back-channel: Бэкенд клиента обменивает code на токены ===")
	formData := url.Values{
		"grant_type":    {"authorization_code"},
		"code":          {authCodeValue},
		"client_id":     {"client-app-123"},
		"client_secret": {"secret-xyz-789"},
		"redirect_uri":  {"https://myclient.com/callback"},
	}

	resp, err := http.Post(ts.URL+"/token", "application/x-www-form-urlencoded", strings.NewReader(formData.Encode()))
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("HTTP Status: %d\n", resp.StatusCode)

	var tokenRes TokenResponse
	if err := json.Unmarshal(body, &tokenRes); err != nil {
		panic(err)
	}
	fmt.Printf("Access Token:  %s\n", tokenRes.AccessToken)
	fmt.Printf("Refresh Token: %s\n", tokenRes.RefreshToken)
	fmt.Printf("Expires In:    %d секунд\n", tokenRes.ExpiresIn)

	// 3. Попытка повторного использования кода (Replay Attack)
	fmt.Println("\n=== 3. Проверка защиты от повторного использования кода авторизации ===")
	resp2, _ := http.Post(ts.URL+"/token", "application/x-www-form-urlencoded", strings.NewReader(formData.Encode()))
	defer resp2.Body.Close()
	body2, _ := io.ReadAll(resp2.Body)
	fmt.Printf("Повторный обмен того же кода -> HTTP Status: %d, Body: %s\n", resp2.StatusCode, string(body2))
}
```

## Под капотом

На уровне спецификации OAuth 2.0 сервер авторизации обязан связывать одноразовый `code` с `client_id` и `redirect_uri`, переданными на шаге `/authorize`. Если на шаге `/token` клиент передает иной `redirect_uri` или подменяет `client_id`, сервер обязан отвергнуть запрос. Время жизни кода рекомендуется устанавливать не более 60 секунд. Более того, секция 4.1.2 RFC 6749 предписывает: если сервер обнаруживает попытку повторного использования кода, он должен не просто отказать, но и по возможности аннулировать все ранее выданные по этому коду токены, так как произошла компрометация канала.

## Подводные камни

1. **Отсутствие client_secret проверки:** Публичные клиенты (SPA/мобильные приложения) не могут безопасно хранить `client_secret`. Использование классического code flow без PKCE для публичных клиентов приводит к перехвату кода другими приложениями на устройстве.
2. **Утечка кода через Referer:** Если страница успешной авторизации на сайте клиента содержит внешние ресурсы (картинки, скрипты аналитики), браузер отправит URL с `?code=...` в заголовке `Referer`.
3. **Неодноразовый код:** Если бэкенд забывает удалять код авторизации из хранилища сразу после проверки, возникает уязвимость к Replay-атакам.

## На собеседовании

**Вопрос с собеседования:** Почему в OAuth 2.0 Authorization Code Flow для Confidential Client код авторизации имеет время жизни 30–60 секунд, а не сутки, и почему он передается через браузер, а access token — строго напрямую?
**Ответ:** Браузер является ненадежной средой выполнения (Front-Channel): URL попадает в историю переходов, закладки, логи прокси-серверов и заголовок Referer. Если бы токен передавался через браузер, любая XSS-уязвимость или вредоносный плагин мгновенно похитили бы долгоживущий доступ. Короткоживущий код минимизирует окно атаки: даже если атакующий перехватит `code`, он не сможет обменять его на `access_token` без аутентификации на сервере авторизации через `client_secret`, который хранится исключительно во внутренней памяти защищенного бэкенда (Back-Channel).
