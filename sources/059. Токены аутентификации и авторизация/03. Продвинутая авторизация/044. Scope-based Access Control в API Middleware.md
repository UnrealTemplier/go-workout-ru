# Scope-based Access Control в API Middleware

## Условие

Реализуйте middleware, который извлекает scopes из токена (OAuth2) и проверяет требуемые scopes для endpoint (`read:users`, `write:posts`). Объясните разницу между scopes (что разрешено делать) и claims (кто пользователь).

### Исходная формулировка

**Scope-based access control.**: Реализуйте middleware, который извлекает scopes из токена (OAuth2) и проверяет требуемые scopes для endpoint (`read:users`, `write:posts`). Объясните разницу между scopes (что разрешено делать) и claims (кто пользователь).

## Теория

В современных системах авторизации критически важно разграничивать два фундаментальных понятия: **Claims** и **Scopes**.

### Claims vs Scopes:
- **Claims (Утверждения об идентификации):** Отвечают на вопрос *«Кто субъект?»* (Identity & Attributes). Примеры: `sub: "usr_991"`, `email: "alice@ya.ru"`, `org_id: "corp_1"`, `department: "finance"`. Claims принадлежат пользователю.
- **Scopes (Делегированные полномочия):** Отвечают на вопрос *«Что клиентскому приложению разрешено делать от имени пользователя или сервиса?»* (Authorization Grant). Примеры: `read:users`, `write:posts`, `billing:charge`. Scopes принадлежат контексту токена.

Например: Пользователь Алиса может обладать полными правами администратора в системе (`role: "admin"` — это Claim), но стороннему плагину календаря она делегировала только доступ на чтение событий (`scope: "read:calendar"`). Даже если запрос делает админ, если токен не содержит `write:calendar`, API обязано отклонить модификацию!

### Стандарты HTTP для Scope Middleware:
- При отсутствии токена возвращается **HTTP 401 Unauthorized** с заголовком:
  `WWW-Authenticate: Bearer error="invalid_token"`
- При наличии валидного токена, но недостаточности scopes возвращается **HTTP 403 Forbidden** с заголовком по **RFC 6750 Section 3.1**:
  `WWW-Authenticate: Bearer error="insufficient_scope", scope="write:posts"`

## Решение по шагам

1. Создайте структуру контекста авторизации с коллекцией предоставленных скоупов.
2. Реализуйте функцию-декоратор `RequireScopes(required ...string)` для защиты HTTP маршрутов.
3. Реализуйте проверку наличия всех требуемых скоупов в токене (логическое И).
4. Продемонстрируйте возврат статуса 403 с заголовком `WWW-Authenticate: Bearer error="insufficient_scope"`.
5. Продемонстрируйте успешное выполнение запроса при наличии всех прав.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

type contextKey string

const AuthContextKey contextKey = "auth_claims"

type AuthContext struct {
	Subject string
	Scopes  map[string]bool
}

// DummyTokenAuthMiddleware имитирует парсинг токена и извлечение scopes
func DummyTokenAuthMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		authHeader := r.Header.Get("Authorization")
		if !strings.HasPrefix(authHeader, "Bearer ") {
			http.Error(w, `{"error":"unauthorized"}`, http.StatusUnauthorized)
			return
		}

		token := strings.TrimPrefix(authHeader, "Bearer ")
		var scopes []string
		var sub string

		// Имитация декодирования разных тестовых токенов
		switch token {
		case "read_only_token":
			sub = "usr_reader"
			scopes = []string{"read:users", "read:posts"}
		case "admin_token":
			sub = "usr_admin"
			scopes = []string{"read:users", "write:posts", "delete:posts"}
		default:
			http.Error(w, `{"error":"invalid_token"}`, http.StatusUnauthorized)
			return
		}

		scopeMap := make(map[string]bool)
		for _, s := range scopes {
			scopeMap[s] = true
		}

		ctx := context.WithValue(r.Context(), AuthContextKey, &AuthContext{
			Subject: sub,
			Scopes:  scopeMap,
		})
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

// RequireScopes — middleware для проверки необходимых привилегий (RFC 6750)
func RequireScopes(requiredScopes ...string) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			authCtx, ok := r.Context().Value(AuthContextKey).(*AuthContext)
			if !ok || authCtx == nil {
				w.Header().Set("WWW-Authenticate", `Bearer error="invalid_token"`)
				http.Error(w, `{"error":"unauthorized"}`, http.StatusUnauthorized)
				return
			}

			// Проверяем наличие всех требуемых скоупов (AND logic)
			var missing []string
			for _, required := range requiredScopes {
				if !authCtx.Scopes[required] {
					missing = append(missing, required)
				}
			}

			if len(missing) > 0 {
				w.Header().Set("WWW-Authenticate", fmt.Sprintf(`Bearer error="insufficient_scope", scope="%s"`, strings.Join(requiredScopes, " ")))
				w.Header().Set("Content-Type", "application/json")
				w.WriteHeader(http.StatusForbidden)
				_, _ = fmt.Fprintf(w, `{"error":"forbidden","missing_scopes":%q}`, missing)
				return
			}

			next.ServeHTTP(w, r)
		})
	}
}

func main() {
	mux := http.NewServeMux()

	// Публичный защищенный маршрут на чтение
	readHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"data":["user1","user2"]}`))
	})
	mux.Handle("/users", DummyTokenAuthMiddleware(RequireScopes("read:users")(readHandler)))

	// Маршрут на запись, требующий write:posts
	writeHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"status":"post_created"}`))
	})
	mux.Handle("/posts/create", DummyTokenAuthMiddleware(RequireScopes("write:posts")(writeHandler)))

	ts := httptest.NewServer(mux)
	defer ts.Close()

	// 1. Попытка создания поста с read-only токеном
	fmt.Println("=== 1. Попытка записи с токеном read_only_token ===")
	req1, _ := http.NewRequest("POST", ts.URL+"/posts/create", nil)
	req1.Header.Set("Authorization", "Bearer read_only_token")
	resp1, _ := http.DefaultClient.Do(req1)
	fmt.Printf("HTTP Status:        %d (Forbidden)\n", resp1.StatusCode)
	fmt.Printf("WWW-Authenticate:   %s\n", resp1.Header.Get("WWW-Authenticate"))
	resp1.Body.Close()

	// 2. Чтение списка пользователей с read-only токеном
	fmt.Println("\n=== 2. Попытка чтения с токеном read_only_token ===")
	req2, _ := http.NewRequest("GET", ts.URL+"/users", nil)
	req2.Header.Set("Authorization", "Bearer read_only_token")
	resp2, _ := http.DefaultClient.Do(req2)
	fmt.Printf("HTTP Status:        %d (OK)\n", resp2.StatusCode)
	resp2.Body.Close()

	// 3. Создание поста с токеном admin_token
	fmt.Println("\n=== 3. Попытка записи с токеном admin_token ===")
	req3, _ := http.NewRequest("POST", ts.URL+"/posts/create", nil)
	req3.Header.Set("Authorization", "Bearer admin_token")
	resp3, _ := http.DefaultClient.Do(req3)
	fmt.Printf("HTTP Status:        %d (Created)\n", resp3.StatusCode)
	resp3.Body.Close()
}
```

## Под капотом

RFC 6750 предписывает: при ошибке недостаточных прав сервер ОБЯЗАН вернуть код статуса HTTP 403 Forbidden и включить атрибут `scope` в заголовок ответа `WWW-Authenticate`, перечислив все скоупы, необходимые для выполнения данного запроса. Это позволяет клиентским SPA или мобильным приложениям динамически запросить у пользователя согласие (Incremental Consent / Step-up authorization) на выдачу недостающих прав без необходимости полного перезапуска сессии.

## Подводные камни

1. **Смешение Scopes и Permissions в БД:** Scopes ограничивают доступ приложения-клиента, но не заменяют проверку прав на уровне бизнес-логики (например, токен имеет `write:posts`, но может ли этот конкретный пользователь редактировать пост чужого автора? Это задача ABAC/ACL, а не Scope Middleware).
2. **Пробельные разделители:** По стандарту RFC 6749 скоупы передаются в токене строкой через пробел: `"read:users write:posts"`. Попытка парсить их через запятую приведет к сбою авторизации.
3. **Возврат 401 вместо 403:** Если токен валиден, но прав недостаточно, возврат 401 приведет к зацикливанию клиента (клиент решит, что токен протух, попытается его обновить и повторит тот же 401). При нехватке прав должен возвращаться строго 403.

## На собеседовании

**Вопрос с собеседования:** В крупной финансовой организации пользователь с правами Super Admin вошел в систему через мобильное приложение. При попытке перевести средства со счета компании запрос был заблокирован с ошибкой 403 Insufficient Scope. Почему так произошло и в чем архитектурная цель такого поведения?
**Ответ:** Это фундаментальный принцип разделения **Subject Identity (Пользователь)** и **Client Authorization Grant (Приложение)**:
1) Пользователь обладает максимальными правами (`role: admin`), но мобильный клиент был авторизован только на просмотр балансов (`scope: read:accounts`).
2) Финансовый перевод требует скоупа повышенной опасности `write:transfer`, который выдается только при использовании аппаратного токена или биометрии на доверенном корпоративном рабочем месте (Step-up Authentication).
3) Это предотвращает кражу денег в ситуации, если телефон администратора был похищен или скомпрометирован трояном: отсутствие опасного скоупа в токене мобильного клиента надежно блокирует вредоносную операцию.
