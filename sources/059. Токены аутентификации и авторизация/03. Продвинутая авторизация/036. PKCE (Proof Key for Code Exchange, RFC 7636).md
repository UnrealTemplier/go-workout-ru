# PKCE (Proof Key for Code Exchange, RFC 7636)

## Условие

Добавьте PKCE в ваш OAuth2 flow (обязателен для SPA и mobile приложений, рекомендуется для всех). Используйте S256 метод.

### Исходная формулировка

**PKCE (Proof Key for Code Exchange)**: Добавьте PKCE в ваш OAuth2 flow (обязателен для SPA и mobile приложений, рекомендуется для всех). Используйте S256 метод.

## Теория

Спецификация **PKCE (Proof Key for Code Exchange by OAuth Public Clients, RFC 7636)** была разработана для устранения критической уязвимости: **Authorization Code Interception Attack**.

В мобильных приложениях (iOS/Android) и SPA (Single Page Applications) клиент считается **публичным (Public Client)**: злоумышленник может декомпилировать приложение и извлечь любой встроенный `client_secret`. Кроме того, мобильные ОС регистрируют Custom URL Schemes (например, `myapp://oauth-callback`). Если вредоносное приложение зарегистрирует ту же схему, операционная система может передать URL с кодом авторизации вредоносному приложению!

**Механика PKCE (метод S256):**
1. **Генерация verifier:** Клиент генерирует криптографически стойкую случайную строку `code_verifier` длиной от 43 до 128 символов из набора `[A-Z, a-z, 0-9, "-", ".", "_", "~"]`.
2. **Вычисление challenge:** Клиент вычисляет SHA-256 хеш от `code_verifier` и кодирует его в Base64URL без заполнения:
   $$\text{code\_challenge} = \text{BASE64URL-ENCODE}(\text{SHA256}(\text{code\_verifier}))$$
3. **Запрос авторизации (/authorize):** Клиент передает `code_challenge` и `code_challenge_method=S256`. Сервер сохраняет challenge вместе с выданным кодом авторизации.
4. **Обмен кода (/token):** Бэкенд клиента отправляет исходный `code_verifier`. Сервер авторизации вычисляет SHA256 от присланного verifier и сравнивает с сохраненным challenge.

Если вредоносное приложение перехватило `code`, оно не сможет обменять его на токены, так как не знает исходный `code_verifier`, сгенерированный в памяти легитимного клиента! Метод `plain` запрещен современным BCP (OAuth 2.1 Security Best Current Practice).

## Решение по шагам

1. Реализуйте функцию генерации криптостойкого `code_verifier`.
2. Реализуйте функцию вычисления `code_challenge` методом `S256`.
3. Смоделируйте хранение challenge на сервере авторизации при выдаче кода.
4. Реализуйте проверку `code_verifier` на эндпоинте `/token`.
5. Продемонстрируйте отказ сервера при попытке обмена кода без verifier или с неверным verifier.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/base64"
	"errors"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
	"sync"
)

// GenerateCodeVerifier создает криптографический verifier (43-128 символов)
func GenerateCodeVerifier() (string, error) {
	b := make([]byte, 32) // 32 байта энтропии -> 43 символа base64url
	if _, err := io.ReadFull(rand.Reader, b); err != nil {
		return "", err
	}
	return base64.RawURLEncoding.EncodeToString(b), nil
}

// ComputeCodeChallengeS256 вычисляет code_challenge = Base64URL(SHA256(verifier))
func ComputeCodeChallengeS256(verifier string) string {
	h := sha256.Sum256([]byte(verifier))
	return base64.RawURLEncoding.EncodeToString(h[:])
}

// ServerPKCE имитирует сервер авторизации с поддержкой RFC 7636
type ServerPKCE struct {
	mu            sync.Mutex
	authCodes     map[string]PKCECodeRecord
}

type PKCECodeRecord struct {
	Challenge       string
	ChallengeMethod string
	ClientID        string
}

func (s *ServerPKCE) IssueCode(clientID, challenge, method string) (string, error) {
	if method != "S256" {
		return "", errors.New("поддерживается исключительно метод S256")
	}
	s.mu.Lock()
	defer s.mu.Unlock()

	code := "auth_code_" + base64.RawURLEncoding.EncodeToString([]byte(challenge[:8]))
	s.authCodes[code] = PKCECodeRecord{
		Challenge:       challenge,
		ChallengeMethod: method,
		ClientID:        clientID,
	}
	return code, nil
}

func (s *ServerPKCE) HandleToken(w http.ResponseWriter, r *http.Request) {
	code := r.FormValue("code")
	verifier := r.FormValue("code_verifier")

	s.mu.Lock()
	record, exists := s.authCodes[code]
	if exists {
		delete(s.authCodes, code) // одноразовое потребление
	}
	s.mu.Unlock()

	if !exists {
		http.Error(w, `{"error":"invalid_grant","error_description":"Неверный код"}`, http.StatusBadRequest)
		return
	}

	// Проверка PKCE
	expectedChallenge := ComputeCodeChallengeS256(verifier)
	if subtle.ConstantTimeCompare([]byte(expectedChallenge), []byte(record.Challenge)) != 1 {
		http.Error(w, `{"error":"invalid_grant","error_description":"PKCE verifier mismatch"}`, http.StatusBadRequest)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	_, _ = w.Write([]byte(`{"access_token":"at_pkce_success_valid_token","token_type":"Bearer","expires_in":3600}`))
}

func main() {
	server := &ServerPKCE{authCodes: make(map[string]PKCECodeRecord)}
	mux := http.NewServeMux()
	mux.HandleFunc("/token", server.HandleToken)
	ts := httptest.NewServer(mux)
	defer ts.Close()

	// 1. Клиент генерирует пару PKCE
	verifier, err := GenerateCodeVerifier()
	if err != nil {
		panic(err)
	}
	challenge := ComputeCodeChallengeS256(verifier)

	fmt.Println("=== 1. Генерация PKCE параметров на клиенте ===")
	fmt.Printf("Code Verifier  (секрет клиента): %s (длина %d)\n", verifier, len(verifier))
	fmt.Printf("Code Challenge (отправляется в /auth): %s\n\n", challenge)

	// 2. Шаг /authorize: клиент получает код, сервер запоминает challenge
	code, err := server.IssueCode("mobile_app_ios", challenge, "S256")
	if err != nil {
		panic(err)
	}
	fmt.Printf("Сервер выдал Auth Code: %s\n\n", code)

	// 3. Злоумышленник перехватил code, но не знает verifier
	fmt.Println("=== 2. Атака: Вредоносное приложение пытается обменять code без verifier ===")
	badData := url.Values{"code": {code}, "code_verifier": {"wrong_guess_verifier_string_123"}}
	// Создаем второй код для атаки, чтобы не сжечь первый
	attackCode, _ := server.IssueCode("mobile_app_ios", challenge, "S256")
	badData.Set("code", attackCode)
	respBad, _ := http.Post(ts.URL+"/token", "application/x-www-form-urlencoded", strings.NewReader(badData.Encode()))
	defer respBad.Body.Close()
	fmt.Printf("Ответ сервера на атаку: HTTP Status %d (Запрос заблокирован!)\n\n", respBad.StatusCode)

	// 4. Легитимный клиент обменивает code с правильным verifier
	fmt.Println("=== 3. Легитимный клиент отправляет правильный code_verifier ===")
	goodData := url.Values{"code": {code}, "code_verifier": {verifier}}
	respGood, _ := http.Post(ts.URL+"/token", "application/x-www-form-urlencoded", strings.NewReader(goodData.Encode()))
	defer respGood.Body.Close()
	fmt.Printf("Ответ сервера легитимному клиенту: HTTP Status %d (Токен получен!)\n", respGood.StatusCode)
}
```

## Под капотом

RFC 7636 строго регламентирует кодирование: `code_challenge` обязан передаваться в формате Base64URL без паддинга (`=`). Использование стандартного Base64 приведет к ошибкам роутинга и парсинга URL-параметров из-за символов `+`, `/` и `=`. При валидации на сервере вычисленный challenge и сохраненный challenge должны сравниваться с помощью `subtle.ConstantTimeCompare`, исключая timing-атаки по утечке времени частичного совпадения байт.

## Подводные камни

1. **Использование code_challenge_method=plain:** Метод plain передает сам verifier без хеширования. Если запрос авторизации логируется провайдером или прокси, verifier утекает так же, как и код, полностью нивелируя защиту PKCE. Метод plain запрещен OAuth 2.1.
2. **Недостаточная энтропия verifier:** Генерация verifier через `math/rand` позволяет восстановить seed и вычислить verifier. Использовать строго `crypto/rand`.
3. **Хранение verifier в LocalStorage SPA:** Если SPA сохраняет verifier в незащищенный LocalStorage до редиректа, любой XSS-скрипт может прочитать его.

## На собеседовании

**Вопрос с собеседования:** Почему в спецификации OAuth 2.1 механизм PKCE стал обязательным даже для Confidential Clients (бэкенд-сервисов с защищенным client_secret), хотя изначально создавался только для Public Clients?
**Ответ:** 1) **Защита от подмены кода авторизации (Authorization Code Injection):** В распределенных системах и при использовании мульти-арендных IdP атакующий может подставить валидный код от одного клиента в callback другого. PKCE связывает запрос авторизации (`/authorize`) с обменом токенов (`/token`) уникальным сессионным секретом `code_verifier`, генерируемым на каждую операцию. 2) **Унификация архитектуры:** Единый строгий протокол исключает ошибки конфигурации, когда публичный клиент случайно регистрируется как конфиденциальный или когда разработчики забывают включить PKCE на клиентах.
