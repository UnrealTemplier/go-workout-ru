# Сторонние ограничения (Third-Party Caveats) в Macaroons

## Условие

Создайте macaroon с third-party caveat (должен быть discharge от другого сервиса). Это распределенная авторизация без central database.

### Исходная формулировка

**Third-party caveats**: Создайте macaroon с third-party caveat (должен быть discharge от другого сервиса). Это分布式 authorization без central database.

## Теория

Одной из самых мощных концепций в архитектуре Macaroons являются **сторонние ограничения (Third-Party Caveats)**.

### Проблема классической авторизации:
Если микросервис хранилища файлов хочет потребовать от пользователя прохождения двухфакторной аутентификации (2FA) или подтверждения оплаты:
- Хранилищу приходится делать сетевой вызов к сервису 2FA или сервису биллинга при каждом обращении.
- Это создает жесткую связность (coupling) и единую точку отказа.

### Как работают Third-Party Caveats:
1. **Первичный сервис (Target Service):** Добавляет в токен ограничение, которое может удовлетворить **только внешний сервис** (например, Сервис 2FA). Ограничение шифруется общим секретом между Target Service и 2FA Service.
2. **Клиент:** Получает токен, видит стороннее ограничение, обращается к сервису 2FA и проходит проверку.
3. **Разрешение (Discharge Macaroon):** Сервис 2FA выдает клиенту дополнительный подтверждающий токен — **Discharge Macaroon**.
4. **Предъявление:** Клиент отправляет на Target Service связку: **Основной Macaroon + Discharge Macaroon**.
5. **Оффлайн проверка:** Target Service проверяет оба токена **локально без каких-либо сетевых запросов к сервису 2FA**!

## Решение по шагам

1. Создадим структуру стороннего ограничения с идентификатором третьей стороны (`ThirdPartyLocation`).
2. Реализуем функцию добавления стороннего ограничения, зашифрованного общим секретом сервисов.
3. Смоделируем сервис 2FA, выпускающий Discharge Macaroon после подтверждения кода.
4. Разработаем верификатор, проверяющий связку основного токена и discharge-токена.
5. Продемонстрируем успешный доступ при наличии обоих токенов и отказ при отсутствии подтверждения от 2FA.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"fmt"
)

// ThirdPartyCaveat описывает ограничение, требующее подтверждения от стороннего сервиса
type ThirdPartyCaveat struct {
	Location string // URL стороннего сервиса (например, "auth.2fa.service")
	Ticket   []byte // Зашифрованный контекст для третьей стороны
}

type DistributedMacaroon struct {
	ID        string
	Signature []byte
	Caveats   []ThirdPartyCaveat
}

// TargetService управляет целевым ресурсом
type TargetService struct {
	rootKey    []byte
	sharedKey  []byte // Общий симметричный ключ между TargetService и 2FAService
}

// IssueToken выпускает токен с обязательным требованием 2FA от стороннего сервиса
func (s *TargetService) IssueToken(userID string) *DistributedMacaroon {
	h := hmac.New(sha256.New, s.rootKey)
	h.Write([]byte(userID))
	sig := h.Sum(nil)

	// Шифруем требование общим ключом с сервисом 2FA
	hTicket := hmac.New(sha256.New, s.sharedKey)
	hTicket.Write([]byte("require:2fa_verified"))
	ticket := hTicket.Sum(nil)

	m := &DistributedMacaroon{
		ID:        userID,
		Signature: sig,
		Caveats: []ThirdPartyCaveat{
			{Location: "https://auth.2fa.corp", Ticket: ticket},
		},
	}
	return m
}

// TwoFactorService эмулирует сторонний сервис двухфакторной аутентификации
type TwoFactorService struct {
	sharedKey []byte
}

// IssueDischarge проверяет 2FA код пользователя и выпускает подтверждающий токен (Discharge)
func (s *TwoFactorService) IssueDischarge(ticket []byte, smsCode string) ([]byte, error) {
	if smsCode != "777-123" {
		return nil, fmt.Errorf("invalid 2fa code")
	}

	// Выпускаем криптографическое доказательство успешного 2FA
	h := hmac.New(sha256.New, s.sharedKey)
	h.Write(ticket)
	h.Write([]byte("status=discharged_ok"))
	return h.Sum(nil), nil
}

// VerifyAll производит локальную оффлайн проверку всей связки токенов
func (s *TargetService) VerifyAll(m *DistributedMacaroon, dischargeToken []byte) (bool, error) {
	if len(m.Caveats) > 0 && dischargeToken == nil {
		return false, fmt.Errorf("missing discharge token for third-party caveat")
	}

	// Проверяем Discharge Token от 2FA сервиса локально (без сети!)
	expectedDischargeH := hmac.New(sha256.New, s.sharedKey)
	expectedDischargeH.Write(m.Caveats[0].Ticket)
	expectedDischargeH.Write([]byte("status=discharged_ok"))
	expectedDischarge := expectedDischargeH.Sum(nil)

	if subtle.ConstantTimeCompare(dischargeToken, expectedDischarge) != 1 {
		return false, fmt.Errorf("discharge token verification failed (2fa proof invalid)")
	}

	return true, nil
}

func main() {
	sharedSecret := []byte("SharedSecretBetweenTargetAnd2FA2026")
	targetSvc := &TargetService{rootKey: []byte("TargetRootKey"), sharedKey: sharedSecret}
	twoFASvc := &TwoFactorService{sharedKey: sharedSecret}

	// 1. Сервер ресурсов выдает токен с требованием 2FA
	macaroon := targetSvc.IssueToken("user_alice")
	fmt.Println("=== 1. Выдан Macaroon с Third-Party Caveat ===")
	fmt.Printf("Требуется подтверждение от: %s\n\n", macaroon.Caveats[0].Location)

	// 2. Попытка обратиться к ресурсу БЕЗ discharge токена
	fmt.Println("=== 2. Попытка доступа без подтверждения 2FA ===")
	_, errWithout2FA := targetSvc.VerifyAll(macaroon, nil)
	fmt.Printf("Результат: ❌ %v\n\n", errWithout2FA)

	// 3. Клиент идет в 2FA сервис, вводит СМС и получает Discharge Macaroon
	fmt.Println("=== 3. Клиент проходит 2FA и получает Discharge Macaroon ===")
	discharge, err := twoFASvc.IssueDischarge(macaroon.Caveats[0].Ticket, "777-123")
	if err != nil {
		panic(err)
	}
	fmt.Printf("Discharge токен получен: %x...\n\n", discharge[:8])

	// 4. Клиент предъявляет оба токена целевому сервису
	fmt.Println("=== 4. Проверка связки токенов на целевом сервисе (Offline!) ===")
	ok, err := targetSvc.VerifyAll(macaroon, discharge)
	fmt.Printf("Результат проверки: ✅ Доступ разрешен=%t (ошибка: %v)\n", ok, err)
}
```

## Под капотом

Сторонние ограничения используют концепцию связывания ключей (Ticket Binding). 
Первичный сервис генерирует случайный ключ \(K_v\) и шифрует его публичным или симметричным ключом третьей стороны. 
Третья сторона расшифровывает \(K_v\), проверяет условие (например, 2FA/оплату) и выпускает подтверждающий токен (Discharge), запечатанный ключом \(K_v\). 
Первичный сервис проверяет разрядку без сетевого синхронного вызова к третьему сервису, обеспечивая полную автономность.

## Подводные камни

1. **Утечка общего ключа:** Ключ между Target и Third-party сервисом должен быть уникален для каждой пары сервисов.
2. **Replay атака разрядки:** Токен Discharge обязан содержать временную метку экспирации.
3. **Разрастание размера связки токенов:** Передача нескольких Macaroons увеличивает размер HTTP-заголовка.

## На собеседовании

**Вопрос с собеседования в Google/Яндекс:** «Как концепция Third-Party Caveats в Macaroons позволяет реализовать распределенную авторизацию без централизованной базы данных?»
**Ответ:** Целевой сервис может включить в токен требование, зашифрованное ключом стороннего сервиса (например, сервиса проверки биометрии или платежного шлюза). 
Клиент самостоятельно обращается к стороннему сервису, выполняет необходимое действие и получает подтверждающий токен — **Discharge Macaroon**. 
Затем клиент предъявляет оба токена целевому сервису. Целевой сервис проверяет математическую связь между основным токеном и discharge-токеном **локально в оперативной памяти**, не обращаясь по сети ни к базе данных, ни к стороннему сервису. Это обеспечивает абсолютную масштабируемость и устойчивость к сетевым сбоям (zero network latency authorization).
