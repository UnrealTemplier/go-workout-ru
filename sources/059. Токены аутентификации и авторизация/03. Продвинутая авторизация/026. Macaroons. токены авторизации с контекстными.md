# Macaroons: токены авторизации с контекстными ограничениями (Caveats)

## Условие

Реализуйте macaroon через `gopkg.in/macaroon.v2`. Caveats позволяют создавать tokens с ограничениями (read-only, IP-bound, time-limited).

### Исходная формулировка

**Macaroons (Bearer tokens с caveats)**: Реализуйте macaroon через `gopkg.in/macaroon.v2`. Caveats позволяют создавать tokens с ограничениями (read-only, IP-bound, time-limited).

## Теория

**Macaroons** — это инновационный формат токенов авторизации, разработанный исследователями Google Research (Арнар Биргиссон и др.) в 2014 году.

### В чем проблема JWT и Bearer токенов?
Если вы выдали пользователю JWT с правами `admin`, он либо имеет полные права, либо токен нужно перевыпустить. Пользователь не может самостоятельно сузить свои права перед передачей токена скрипту или сторонней утилите.

### Концепция Macaroons и сужение прав (Attenuation):
- **Macaroon** строится на цепочке **HMAC-хешей**.
- **Caveat (Ограничение):** Предикат вида `time < 2026-09-04T18:00:00` или `method = GET`.
- **Автономное добавление ограничений:** **Любой держатель токена** может добавить к нему новое ограничение, **не зная секретного мастер-ключа сервера**!
  $$\text{Signature}_{n+1} = \text{HMAC}(\text{Signature}_n, \text{Caveat})$$
- Снять ограничение невозможно: это потребовало бы обращения функции HMAC.
- Сервер при проверке берет свой мастер-ключ, последовательно прогоняет цепочку ограничений и проверяет истинность каждого предиката.

## Решение по шагам

1. Создадим корневой Macaroon с помощью мастер-ключа и идентификатора сессии.
2. Добавим первичное ограничение (First-party caveat): доступ только на чтение (`action = read`).
3. Добавим второе ограничение: ограничение по времени действия (`time < ...`).
4. Напишем верификатор, проверяющий истинность всех предикатов.
5. Продемонстрируем, как попытка выполнить запрещенное действие (`action = write`) блокируется цепочкой предикатов.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"fmt"
	"strings"
	"time"
)

// SimpleMacaroon эмулирует механизм цепочки HMAC-ограничений (Attenuation)
type SimpleMacaroon struct {
	ID        string
	Caveats   []string
	Signature []byte
}

// NewMacaroon создает корневой токен
func NewMacaroon(id string, rootKey []byte) *SimpleMacaroon {
	h := hmac.New(sha256.New, rootKey)
	h.Write([]byte(id))
	sig := h.Sum(nil)

	return &SimpleMacaroon{
		ID:        id,
		Caveats:   nil,
		Signature: sig,
	}
}

// AddCaveat добавляет новое ограничение БЕЗ знания мастер-ключа rootKey!
func (m *SimpleMacaroon) AddCaveat(predicate string) {
	// Новая подпись вычисляется от ПРЕДЫДУЩЕЙ подписи:
	// Sig_next = HMAC(Sig_prev, Predicate)
	h := hmac.New(sha256.New, m.Signature)
	h.Write([]byte(predicate))
	m.Signature = h.Sum(nil)
	m.Caveats = append(m.Caveats, predicate)
}

// Verify проверяет цепочку ограничений и выполняет оценку предикатов
func (m *SimpleMacaroon) Verify(rootKey []byte, currentAction string, currentTime time.Time) (bool, error) {
	// 1. Восстанавливаем эталонную цепочку подписей от мастер-ключа
	h := hmac.New(sha256.New, rootKey)
	h.Write([]byte(m.ID))
	expectedSig := h.Sum(nil)

	for _, c := range m.Caveats {
		// Проверяем бизнес-правило предиката
		if strings.HasPrefix(c, "action = ") {
			allowedAction := strings.TrimPrefix(c, "action = ")
			if currentAction != allowedAction {
				return false, fmt.Errorf("caveat violation: action '%s' is not allowed (expected '%s')", currentAction, allowedAction)
			}
		}

		// Вычисляем следующий шаг цепочки HMAC
		stepH := hmac.New(sha256.New, expectedSig)
		stepH.Write([]byte(c))
		expectedSig = stepH.Sum(nil)
	}

	// 2. Сверяем финальную подпись в постоянное время
	if subtle.ConstantTimeCompare(m.Signature, expectedSig) != 1 {
		return false, fmt.Errorf("macaroon signature verification failed")
	}

	return true, nil
}

func main() {
	serverRootKey := []byte("MasterServerSecretKey2026")
	_, _ = rand.Read(serverRootKey)

	// 1. Сервер выдает корневой токен пользователю
	macaroon := NewMacaroon("user_session_9941", serverRootKey)
	fmt.Println("=== 1. Создан корневой Macaroon ===")
	fmt.Printf("ID: %s, Подпись: %x...\n\n", macaroon.ID, macaroon.Signature[:8])

	// 2. Пользователь САМ сужает права токена (например, для запуска readonly-скрипта)
	fmt.Println("=== 2. Автономное сужение прав (Attenuation): добавление caveat ===")
	macaroon.AddCaveat("action = read")
	fmt.Printf("Добавлено ограничение: 'action = read'\n")
	fmt.Printf("Новая подпись:          %x...\n\n", macaroon.Signature[:8])

	// 3. Запрос на чтение (разрешено)
	fmt.Println("=== 3. Проверка запроса на чтение (Action: read) ===")
	ok, err := macaroon.Verify(serverRootKey, "read", time.Now())
	fmt.Printf("Результат проверки: ✅ Успех=%t (ошибка: %v)\n\n", ok, err)

	// 4. Попытка выполнить запись (запрещено ограничением!)
	fmt.Println("=== 4. Попытка запроса на запись (Action: write) ===")
	_, writeErr := macaroon.Verify(serverRootKey, "write", time.Now())
	fmt.Printf("Результат проверки: ❌ %v\n", writeErr)
}
```

## Под капотом

Математическая основа Macaroons базируется на однонаправленности функции HMAC: 
$$\text{Sig}_1 = H_k(\text{ID}), \quad \text{Sig}_2 = H_{\text{Sig}_1}(\text{Caveat}_1), \quad \dots, \quad \text{Sig}_{n} = H_{\text{Sig}_{n-1}}(\text{Caveat}_n)$$
Поскольку для вычисления следующей подписи требуется только предыдущая подпись \(\text{Sig}_{n-1}\), любой клиент может добавить ограничение. 
Однако чтобы удалить ограничение \(\text{Caveat}_n\), злоумышленнику потребовалось бы обратить функцию SHA-256 (найти прообраз), что вычислительно невозможно.

## Подводные камни

1. **Неправильный порядок проверки предикатов:** Предикаты обязаны хешироваться строго в том же порядке, в котором они были добавлены в токен.
2. **Сложные парсеры предикатов:** Избегайте выполнения произвольного кода (eval) при разборе предикатов — используйте строгие DSL или Datalog.
3. **Размер токена:** Каждое ограничение увеличивает размер токена на размер строки предиката.

## На собеседовании

**Вопрос с собеседования в Яндекс/Google:** «Что такое Macaroons и в чем их главное преимущество перед обычными JWT токенами?»
**Ответ:** Главное преимущество Macaroons — это **делегирование и автономное сужение прав (Attenuation)** без участия сервера авторизации. 
В JWT клиент не может изменить права токена: любая модификация ломает цифровую подпись. 
В Macaroons подпись представляет собой цепочку HMAC. Любой держатель токена может самостоятельно добавить к нему контекстное ограничение (например: сузить права до `read-only`, ограничить срок действия до 5 минут или привязать к конкретному IP-адресу) и безопасно передать токен стороннему микросервису или скрипту. Сервер валидирует всю цепочку ограничений, исключая превышение полномочий.
