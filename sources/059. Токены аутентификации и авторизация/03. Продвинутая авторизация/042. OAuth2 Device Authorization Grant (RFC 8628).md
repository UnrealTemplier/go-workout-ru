# OAuth2 Device Authorization Grant (RFC 8628)

## Условие

Реализуйте flow для CLI/SmartTV устройств, где пользователь вводит код на другом устройстве.

### Исходная формулировка

**OAuth2 Device Authorization Grant**: Реализуйте flow для CLI/SmartTV устройств, где пользователь вводит код на другом устройстве.

## Теория

Спецификация **Device Authorization Grant (RFC 8628)** создана для устройств с ограниченным или отсутствующим механизмом ввода (Smart TV, медиаприставки, умные колонки, CLI-утилиты терминала), которые не имеют полноценного веб-браузера.

### Механика Device Flow:
1. **Запрос устройства (/device/code):**
   Устройство отправляет POST-запрос с `client_id` на сервер авторизации.
2. **Ответ сервера:**
   Сервер возвращает:
   - `device_code`: длинная криптостойкая случайная строка (секрет устройства).
   - `user_code`: короткий человекочитаемый код (например, `WDJB-MJHT` или 8 цифр).
   - `verification_uri`: ссылка, куда пользователь должен перейти (`https://auth.example.com/activate`).
   - `interval`: минимальный интервал опроса в секундах (например, 5 сек).
   - `expires_in`: время жизни кодов (обычно 10–15 минут).
3. **Действия пользователя:**
   Устройство отображает пользователю: *«Перейдите на https://auth.example.com/activate и введите код WDJB-MJHT»* (или показывает QR-код). Пользователь заходит с телефона или ноутбука и подтверждает вход.
4. **Опрос сервера устройством (Polling /token):**
   Устройство периодически отправляет POST-запросы на `/token` с параметрами `grant_type=urn:ietf:params:oauth:grant-type:device_code` и `device_code`.
   - Пока пользователь не подтвердил вход, сервер возвращает HTTP 400: `{"error": "authorization_pending"}`.
   - Если устройство опрашивает слишком часто, сервер возвращает: `{"error": "slow_down"}`.
   - Как только пользователь подтвердил вход в браузере, очередной опрос возвращает `access_token` и `refresh_token`!

## Решение по шагам

1. Создайте структуры данных для хранения состояния кодов устройств.
2. Реализуйте эндпоинт `/device/code` для регистрации устройства и выдачи пары кодов.
3. Реализуйте эндпоинт `/token`, возвращающий `authorization_pending` до момента подтверждения.
4. Реализуйте эндпоинт подтверждения `/activate`, где пользователь активирует `user_code`.
5. Смоделируйте работу CLI-клиента: запуск, ожидание подтверждения в фоне и получение токена.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
	"sync"
	"time"
)

type DeviceSession struct {
	DeviceCode string
	UserCode   string
	Approved   bool
	ExpiresAt  time.Time
}

type DeviceAuthServer struct {
	mu       sync.Mutex
	sessions map[string]*DeviceSession // device_code -> session
	userMap  map[string]*DeviceSession // user_code -> session
}

func NewDeviceAuthServer() *DeviceAuthServer {
	return &DeviceAuthServer{
		sessions: make(map[string]*DeviceSession),
		userMap:  make(map[string]*DeviceSession),
	}
}

// 1. Эндпоинт /device/code
func (s *DeviceAuthServer) HandleDeviceCode(w http.ResponseWriter, r *http.Request) {
	b := make([]byte, 16)
	_, _ = io.ReadFull(rand.Reader, b)
	deviceCode := hex.EncodeToString(b)
	userCode := fmt.Sprintf("%04d-%04d", time.Now().UnixNano()%10000, (time.Now().UnixNano()/10000)%10000)

	session := &DeviceSession{
		DeviceCode: deviceCode,
		UserCode:   userCode,
		Approved:   false,
		ExpiresAt:  time.Now().Add(10 * time.Minute),
	}

	s.mu.Lock()
	s.sessions[deviceCode] = session
	s.userMap[userCode] = session
	s.mu.Unlock()

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]interface{}{
		"device_code":      deviceCode,
		"user_code":        userCode,
		"verification_uri": "https://example.com/activate",
		"expires_in":       600,
		"interval":         1,
	})
}

// 2. Эндпоинт /token (Polling клиентом)
func (s *DeviceAuthServer) HandleToken(w http.ResponseWriter, r *http.Request) {
	deviceCode := r.FormValue("device_code")

	s.mu.Lock()
	session, exists := s.sessions[deviceCode]
	s.mu.Unlock()

	if !exists || time.Now().After(session.ExpiresAt) {
		http.Error(w, `{"error":"expired_token"}`, http.StatusBadRequest)
		return
	}

	if !session.Approved {
		http.Error(w, `{"error":"authorization_pending"}`, http.StatusBadRequest)
		return
	}

	// Авторизовано! Удаляем сессию и отдаем токен
	s.mu.Lock()
	delete(s.sessions, deviceCode)
	delete(s.userMap, session.UserCode)
	s.mu.Unlock()

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]interface{}{
		"access_token": "at_tv_device_success_token_42",
		"token_type":   "Bearer",
		"expires_in":   3600,
	})
}

// 3. Эндпоинт /activate (Пользователь подтверждает код в браузере)
func (s *DeviceAuthServer) ApproveUserCode(userCode string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	session, exists := s.userMap[userCode]
	if !exists || time.Now().After(session.ExpiresAt) {
		return false
	}
	session.Approved = true
	return true
}

func main() {
	server := NewDeviceAuthServer()
	mux := http.NewServeMux()
	mux.HandleFunc("/device/code", server.HandleDeviceCode)
	mux.HandleFunc("/token", server.HandleToken)
	ts := httptest.NewServer(mux)
	defer ts.Close()

	// Шаг 1: CLI утилита делает запрос на получение кодов
	resp, _ := http.Post(ts.URL+"/device/code", "application/x-www-form-urlencoded", nil)
	var initData map[string]interface{}
	_ = json.NewDecoder(resp.Body).Decode(&initData)
	resp.Body.Close()

	deviceCode := initData["device_code"].(string)
	userCode := initData["user_code"].(string)
	uri := initData["verification_uri"].(string)

	fmt.Println("=== 1. CLI Устройство запросило авторизацию ===")
	fmt.Printf("Перейдите на: %s\n", uri)
	fmt.Printf("Введите код:   %s\n\n", userCode)

	// Шаг 2: Имитация фонового подтверждения пользователем через 50 мс
	go func() {
		time.Sleep(50 * time.Millisecond)
		fmt.Println(">>> [Пользователь открыл телефон и ввел код в браузере!]")
		server.ApproveUserCode(userCode)
	}()

	// Шаг 3: CLI опрашивает сервер (polling)
	fmt.Println("=== 2. CLI начинает поллинг сервера ===")
	for attempt := 1; attempt <= 5; attempt++ {
		form := url.Values{"device_code": {deviceCode}, "grant_type": {"urn:ietf:params:oauth:grant-type:device_code"}}
		tResp, _ := http.Post(ts.URL+"/token", "application/x-www-form-urlencoded", strings.NewReader(form.Encode()))
		body, _ := io.ReadAll(tResp.Body)
		tResp.Body.Close()

		if tResp.StatusCode == http.StatusOK {
			fmt.Printf("Попытка #%d -> УСПЕХ! Ответ: %s\n", attempt, string(body))
			break
		} else {
			fmt.Printf("Попытка #%d -> Сервер ожидает: %s\n", attempt, string(body))
		}
		time.Sleep(30 * time.Millisecond)
	}
}
```

## Под капотом

RFC 8628 специально разделяет `device_code` и `user_code`:
1. `user_code` должен быть максимально коротким и удобным для ввода с экранной клавиатуры пульта телевизора (алфавит Base20 без визуально похожих символов `0/O`, `1/I/l`).
2. `device_code` обладает высокой криптографической энтропией (128+ бит), что исключает возможность угадывания токена третьими лицами в процессе поллинга. Сервер обязан контролировать лимиты частоты опроса (`rate limiting`), увеличивая интервал при частых запросах через ошибку `slow_down`.

## Подводные камни

1. **Слишком сложный user_code:** Использование символов разного регистра или спецсимволов превращает ввод кода с пульта ТВ в невыполнимую задачу для пользователя.
2. **Отсутствие ограничения попыток ввода user_code:** Из-за короткой длины `user_code` уязвим к перебору (brute-force). Сервер обязан блокировать IP-адрес после 3–5 неверных попыток ввода.
3. **Игнорирование интервала:** Если клиент опрашивает сервер чаще установленного поля `interval`, сервер должен отвечать кодом ошибки `slow_down`, а клиент обязан увеличить задержку на 5 секунд.

## На собеседовании

**Вопрос с собеседования:** Каким образом Google и GitHub защищают эндпоинт активации Device Flow (`/activate`) от перебора коротких пользовательских кодов (user_code)?
**Ответ:** 1) **Специфический алфавит:** Использование кодировки Base20 (только согласные буквы `BCDFGHJKLMNPQRSTVWXZ` и цифры), что дает \(20^8 \approx 25.6 \times 10^9\) комбинаций при коде из 8 символов. 2) **Короткий TTL:** Код действителен строго 10–15 минут. 3) **Строгий Rate Limiting на эндпоинте ввода:** Максимум 5 попыток ввода с одного IP/сессии пользователя с нарастающей капчей (reCAPTCHA/hCaptcha). Это делает вероятность случайного подбора математически пренебрежимо малой (\(< 10^{-7}\)).
