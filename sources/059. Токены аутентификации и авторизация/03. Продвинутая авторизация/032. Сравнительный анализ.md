# Сравнительный анализ: Server-Side Sessions против Stateless JWT

## Условие

Реализуйте сессии в Redis с `session_id` в `HttpOnly; Secure; SameSite=Strict` cookie. Сравните с stateless JWT: возможность мгновенной инвалидации (logout), размер cookie, проблема с масштабированием stateful-сервисов.

### Исходная формулировка

**Server-side sessions vs JWT.**: Реализуйте сессии в Redis с `session_id` в `HttpOnly; Secure; SameSite=Strict` cookie. Сравните с stateless JWT: возможность мгновенной инвалидации (logout), размер cookie, проблема с масштабированием хранилища. Объясните, когда что использовать.

## Теория

Выбор между **Server-Side Sessions (Redis)** и **Stateless JWT** — одно из ключевых архитектурных решений при проектировании бэкенда:

### Сравнительный анализ:

| Критерий | Server-Side Sessions (Redis) | Stateless JWT |
| :--- | :--- | :--- |
| **Мгновенная инвалидация (Logout)** | **Мгновенно (\(O(1)\) `DEL`)** | Невозможно без создания Blacklist |
| **Размер в HTTP-заголовке** | **~44–64 байта** | **800–2500 байт** |
| **Зависимость от хранилища** | Требует Redis / БД | **Полный Stateless** (автономно) |
| **Масштабирование на 500+ сервисов** | Нагрузка на кластер Redis | **Идеально** (локальная валидация) |
| **Конфиденциальность данных** | **100% данных на сервере** | Данные видны клиенту (Base64) |
| **Сложность криптографии** | Минимальная (`crypto/rand`) | Высокая (ротация ключей, JWKS) |

### Архитектурный вердикт:
- **Для веб-браузеров (B2C / Web UI):** Рекомендуются **Server-Side Sessions** в защищенных Cookie (`HttpOnly; Secure; SameSite=Strict`).
- **Для межсервисного взаимодействия (M2M / Mobile API):** Рекомендуются **короткоживущие JWT/PASETO токены (10–15 минут)**.

## Решение по шагам

1. Создадим бенчмарк-сравнение размера Cookie для Server-Side Session и JWT.
2. Смоделируем сценарий Logout и замерим статус блокировки.
3. Проанализируем нагрузку на сеть при 100 000 RPS.
4. Разработаем гибридную архитектуру: Cookie Session на Gateway \(\rightarrow\) Stateless JWT внутри контура.
5. Сформулируем архитектурные рекомендации.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"encoding/hex"
	"fmt"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

func main() {
	rsaKey, _ := rsa.GenerateKey(rand.Reader, 2048)

	// 1. Session ID для Redis
	rawSession := make([]byte, 32)
	_, _ = rand.Read(rawSession)
	sessionID := hex.EncodeToString(rawSession)
	sessionCookie := fmt.Sprintf("session_id=%s; Path=/; HttpOnly; Secure; SameSite=Strict", sessionID)

	// 2. JWT с типичными enterprise claims
	claims := jwt.MapClaims{
		"sub":         "usr_109283",
		"email":       "architect@megacorp.ru",
		"roles":       []string{"developer", "billing_viewer", "k8s_operator"},
		"permissions": []string{"git:push", "pods:read", "logs:export"},
		"exp":         time.Now().Add(24 * time.Hour).Unix(),
		"iss":         "https://auth.megacorp.ru",
		"aud":         "https://api.megacorp.ru",
	}
	jwtObj := jwt.NewWithClaims(jwt.SigningMethodRS256, claims)
	jwtStr, _ := jwtObj.SignedString(rsaKey)
	jwtCookie := fmt.Sprintf("auth_token=%s; Path=/; HttpOnly; Secure; SameSite=Strict", jwtStr)

	fmt.Println("=== СРАВНИТЕЛЬНЫЙ АНАЛИЗ: Server-Side Session vs Stateless JWT ===")
	fmt.Printf("1. Размер Session Cookie: %4d байт\n", len(sessionCookie))
	fmt.Printf("2. Размер JWT Cookie:     %4d байт\n", len(jwtCookie))
	fmt.Printf("JWT Cookie больше в %.1f раз!\n\n", float64(len(jwtCookie))/float64(len(sessionCookie)))

	// Расчет нагрузки на сеть
	rps := 50000.0 // 50 000 RPS
	sessionTrafficMBs := (float64(len(sessionCookie)) * rps) / (1024 * 1024)
	jwtTrafficMBs := (float64(len(jwtCookie)) * rps) / (1024 * 1024)

	fmt.Printf("Сетевой трафик заголовков при 50 000 RPS:\n")
	fmt.Printf("- Server Sessions: %6.1f МБ/сек (%4.1f ГБ/час)\n", sessionTrafficMBs, sessionTrafficMBs*3.6)
	fmt.Printf("- Stateless JWT:   %6.1f МБ/сек (%4.1f ГБ/час)\n", jwtTrafficMBs, jwtTrafficMBs*3.6)
	fmt.Printf("Переплата за сетевой трафик JWT: +%.1f ГБ в час!\n\n", (jwtTrafficMBs-sessionTrafficMBs)*3.6)

	fmt.Println("Итог архитектурного выбора:")
	fmt.Println("• Web UI / Браузеры: Используйте Server-Side Sessions в Redis (мгновенный logout, компактность).")
	fmt.Println("• Внутренние микросервисы: Используйте короткоживущие JWT/PASETO (автономия, нет нагрузки на Redis).")
}
```

## Под капотом

В крупных технологических компаниях (Яндекс, Netflix, Ozon) применяется **гибридный паттерн (BFF / Token Exchange)**:
1. Клиент браузера общается с API Gateway (BFF — Backend for Frontend) по компактной `HttpOnly` Cookie с Redis Session ID.
2. При поступлении запроса API Gateway за 0.2 мс извлекает сессию из локального Redis и генерирует короткоживущий внутренний JWT/PASETO (на 2–5 минут).
3. Внутренние микросервисы общаются между собой по Stateless токену, не нагружая центральный Redis запросами.

## Подводные камни

1. **Хранение мегабайтов данных в сессии Redis:** Сессия должна содержать только базовые идентификаторы (`user_id`, `role`). Не превращайте сессию в кэш бизнес-сущностей.
2. **JWT без ротации и блэклиста в банковских системах:** Требования регуляторов (ЦБ/PCI-DSS) требуют возможности принудительного разлогина.
3. **Отсутствие защиты от CSRF при Cookie сессиях:** Всегда устанавливайте `SameSite=Strict` или `SameSite=Lax`.

## На собеседовании

**Вопрос с собеседования в Ozon/Т-Банк:** «Как решить проблему масштабирования: Redis Sessions создают нагрузку на хранилище, а Stateless JWT нельзя мгновенно отозвать и они раздувают сетевой трафик?»
**Ответ:** Применяется гибридный архитектурный паттерн **BFF (Backend for Frontend) с конвертацией токенов на API Gateway**:
1. На внешнем периметре (между браузером и Gateway) используются компактные Server-Side сессии (32 байта) в защищенных Cookie с хранением в Redis-кластере. Это обеспечивает мгновенный отзыв при логауте, защиту от XSS и минимальный размер трафика.
2. При входе в закрытый периметр API Gateway проверяет сессию в Redis и выпускает ультра-короткоживущий асимметричный JWT (на 1–2 минуты) для внутренних сервисов.
3. Внутренние микросервисы валидируют JWT локально и автономно, не создавая нагрузки на Redis. В случае блокировки сессии на Gateway новые внутренние JWT перестают выпускаться, и в течение 60 секунд доступ полностью прекращается во всех микросервисах.
