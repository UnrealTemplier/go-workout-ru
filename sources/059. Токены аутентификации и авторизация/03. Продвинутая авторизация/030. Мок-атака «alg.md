# Мок-атака «alg: none» на парсер JWT и регрессионное тестирование

## Условие

Напиши мок-атаку на JWT: вручную создай токен с заголовком `{"alg":"none"}` и пустой подписью. Убедись, что строгий валидатор (`jwt.Parse` с проверкой метода) отклоняет его.

### Исходная формулировка

**[Каверзный кейс — alg=none]**: Напиши мок-атаку на JWT: вручную создай токен с заголовком `{"alg":"none"}` и пустой подписью. Убедись, что строгий валидатор (`jwt.Parse` с проверкой метода) отклоняет его.

## Теория

В корпоративных системах безопасности для предотвращения случайного возврата уязвимостей в продакшн (Security Regression) внедряются автоматические регрессионные тесты на базе `testing.T`.

Тест обязан проверять не только стандартную строку `{"alg":"none"}`, но и различные мутации, использовавшиеся в реальных эксплойтах:
1. Вариант с верхним регистром: `{"alg":"NONE"}`.
2. Вариант с инверсией регистра: `{"alg":"nOnE"}`.
3. Вариант с пробелами: `{"alg": "none "}`.
4. Отсутствие подписи: `header.payload.` (с точкой).
5. Полное отсутствие третьей части: `header.payload` (без точки).

Строгий валидатор обязан отклонить **100% подобных мутаций**.

## Решение по шагам

1. Создадим тестовый набор мутаций токенов с алгоритмом `none`.
2. Напишем эталонную защищенную функцию валидации `StrictVerifyJWT(tokenStr, secret)`.
3. Запустим прогон всех тест-кейсов.
4. Убедимся, что каждый вредоносный токен гарантированно отклоняется с ошибкой.
5. Зафиксируем результат в формате таблицы аудита.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/base64"
	"fmt"

	"github.com/golang-jwt/jwt/v5"
)

// StrictVerifyJWT производит бескомпромиссную проверку токена
func StrictVerifyJWT(tokenStr string, secret []byte) bool {
	token, err := jwt.Parse(tokenStr, func(t *jwt.Token) (any, error) {
		// Строго типизированная проверка метода
		if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
			return nil, fmt.Errorf("disallowed algorithm: %v", t.Header["alg"])
		}
		return secret, nil
	},
		// Жесткий белый список методов
		jwt.WithValidMethods([]string{"HS256"}),
	)

	return err == nil && token.Valid
}

func craftNoneToken(algVariant string, withTrailingDot bool) string {
	headerJSON := fmt.Sprintf(`{"alg":"%s","typ":"JWT"}`, algVariant)
	payloadJSON := `{"sub":"evil_attacker","role":"admin"}`

	hB64 := base64.RawURLEncoding.EncodeToString([]byte(headerJSON))
	pB64 := base64.RawURLEncoding.EncodeToString([]byte(payloadJSON))

	if withTrailingDot {
		return hB64 + "." + pB64 + "."
	}
	return hB64 + "." + pB64
}

func main() {
	secret := []byte("StrictMasterSecretKey2026")

	// Тестовые векторы атак 'alg: none'
	testCases := []struct {
		name            string
		alg             string
		withTrailingDot bool
	}{
		{"Классический 'none' с точкой", "none", true},
		{"Классический 'none' без точки", "none", false},
		{"Верхний регистр 'NONE'", "NONE", true},
		{"Смешанный регистр 'nOnE'", "nOnE", true},
		{"Заголовок 'None'", "None", true},
	}

	fmt.Println("=== Регрессионное тестирование защиты от атаки 'alg: none' ===")
	allBlocked := true

	for i, tc := range testCases {
		badToken := craftNoneToken(tc.alg, tc.withTrailingDot)
		isValid := StrictVerifyJWT(badToken, secret)

		status := "🛡️ ЗАБЛОКИРОВАН (Успех)"
		if isValid {
			status = "🚨 ПРОПУЩЕН (Критическая уязвимость!)"
			allBlocked = false
		}

		fmt.Printf("[%d] %-30s -> %s\n", i+1, tc.name, status)
	}

	fmt.Println("\n--- Итог аудита безопасности ---")
	if allBlocked {
		fmt.Println("✅ Все векторы атаки 'alg: none' успешно отражены!")
	} else {
		fmt.Println("❌ Внимание! Обнаружена брешь в валидаторе токенов!")
	}
}
```

## Под капотом

Опция `jwt.WithValidMethods([]string{"HS256"})` выполняет сравнение со списком строк. Любая строка `none`, `NONE` или `nOnE` не совпадает с `HS256`. 
Кроме того, проверка приведения типов `t.Method.(*jwt.SigningMethodHMAC)` гарантирует, что даже если в парсер проникнет неизвестный объект метода, он не сможет пройти верификацию.

## Подводные камни

1. **Пропуск юнит-тестов безопасности в CI/CD:** Атаки `alg: none` и Algorithm Confusion обязаны быть покрыты тестами в пайплайне автоматической сборки.
2. **Использование сторонних парсеров без проверки ошибок:** Игнорирование ошибки `err` при вызове `jwt.Parse` гарантирует пропуск поддельного токена.
3. **Отсутствие проверки `token.Valid`:** Флаг `token.Valid` должен проверяться всегда.

## На собеседовании

**Вопрос с собеседования в Касперский/Т-Банк:** «Как написать юнит-тест в Go для гарантии того, что сервис никогда не пропустит неподписанный токен alg: none?»
**Ответ:** Необходимо сформировать тестовую матрицу токенов с алгоритмом `none` (с различными вариациями регистра `none`, `NONE`, `nOnE` и структуры без завершающей подписи) и запустить проверку через функцию валидации сервиса. Тест должен с помощью `assert.False(t, token.Valid)` и `assert.Error(t, err)` подтвердить, что во всех случаях валидатор возвращает ошибку и флаг валидности равен `false`. Включение такого теста в CI/CD блокирует появление уязвимости при обновлении зависимостей.
