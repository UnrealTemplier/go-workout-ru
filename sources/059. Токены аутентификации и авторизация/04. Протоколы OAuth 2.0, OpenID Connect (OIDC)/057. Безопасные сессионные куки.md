# Безопасные сессионные куки (HttpOnly, Secure, SameSite=Strict)

## Условие

Если ты не используешь токены (у тебя монолит и браузер). Напиши хендлер, который ставит сессионную куку. Установи флаги: `HttpOnly: true` (недоступно из JS/XSS), `Secure: true` (только HTTPS) и `SameSite: http.SameSiteStrictMode` (защита от CSRF).

### Исходная формулировка

**Безопасные Session Cookies**: Если ты не используешь токены (у тебя монолит и браузер). Напиши хендлер, который ставит сессионную куку. Установи флаги: `HttpOnly: true` (недоступно из JS/XSS), `Secure: true` (только HTTPS) и `SameSite: http.SameSiteStrictMode` (защита от CSRF).

## Теория

Для традиционных веб-приложений (серверный рендеринг HTML, монолиты, админ-панели) использование **сессионных кук (Session Cookies)** архитектурно превосходит JWT:
- **Мгновенная инвалидация:** Сессия хранится в Redis/PostgreSQL на сервере. При выходе (Logout) запись удаляется из базы мгновенно.
- **Минимальный размер заголовка:** Браузер передает только короткий идентификатор (32 байта случайности), а не килобайты claims.
- **Встроенная защита браузера:** Браузер изолирует куку аппаратно и криптографически через флаги безопасности.

### Флаги максимальной защиты сессионной куки:
1. **`HttpOnly: true`:**
   Полностью блокирует чтение куки через JavaScript (`document.cookie`). Даже если сайт подвергнется XSS-атаке, злоумышленник не сможет украсть сессионный токен.
2. **`Secure: true`:**
   Браузер отправляет куку **исключительно** по зашифрованному протоколу HTTPS. Предотвращает перехват в открытых сетях Wi-Fi.
3. **`SameSite: http.SameSiteStrictMode`:**
   Кука отправляется **только** в запросах, инициированных с того же самого домена (Same-Site). Никакие внешние ссылки, iframe или поддельные формы с сайтов злоумышленников куку не передадут, что полностью ликвидирует угрозу **CSRF (Cross-Site Request Forgery)** без необходимости CSRF-токенов в формах!
4. **Префикс `__Host-`:**
   Спецификация RFC 6265bis Cookie Prefixes: имя куки начинается с `__Host-`. Это принуждает браузер требовать: `Secure=true`, `Path=/` и отсутствие поддоменного доступа (`Domain` не задан), защищая от DNS-спуфинга поддоменов!

## Решение по шагам

1. Создайте защищенную функцию генерации криптографического Session ID (32 байта `crypto/rand`).
2. Реализуйте хэндлер `/auth/login`, устанавливающий куку с префиксом `__Host-` и строгими флагами.
3. Реализуйте middleware проверки сессии в хранилище.
4. Реализуйте хэндлер `/auth/logout`, очищающий сессию и выставляющий куку с `MaxAge: -1`.
5. Продемонстрируйте корректность всех флагов безопасности в HTTP-ответе.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

const SessionCookieName = "__Host-session_id"

type SessionStore struct {
	mu       sync.RWMutex
	sessions map[string]string // sessionID -> userID
}

func NewSessionStore() *SessionStore {
	return &SessionStore{sessions: make(map[string]string)}
}

func (s *SessionStore) Create(userID string) (string, error) {
	b := make([]byte, 32) // 256 бит энтропии
	if _, err := io.ReadFull(rand.Reader, b); err != nil {
		return "", err
	}
	sessionID := hex.EncodeToString(b)

	s.mu.Lock()
	s.sessions[sessionID] = userID
	s.mu.Unlock()
	return sessionID, nil
}

func (s *SessionStore) Delete(sessionID string) {
	s.mu.Lock()
	delete(s.sessions, sessionID)
	s.mu.Unlock()
}

// LoginHandler выполняет аутентификацию и установку безопасной куки
func LoginHandler(store *SessionStore) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// Допустим, проверка логина и пароля прошла успешно
		userID := "usr_accountant_42"

		sessionID, err := store.Create(userID)
		if err != nil {
			http.Error(w, "Ошибка сессии", http.StatusInternalServerError)
			return
		}

		// Установка куки высшего уровня безопасности по RFC 6265bis
		cookie := &http.Cookie{
			Name:     SessionCookieName,
			Value:    sessionID,
			Path:     "/",                       // Обязательно для __Host-
			MaxAge:   3600 * 8,                  // 8 часов
			HttpOnly: true,                      // Защита от кражи через XSS
			Secure:   true,                      // Строго по HTTPS
			SameSite: http.SameSiteStrictMode,   // Полная защита от CSRF
		}
		http.SetCookie(w, cookie)

		w.WriteHeader(http.StatusOK)
		_, _ = fmt.Fprintf(w, "Авторизация успешна. Сессия создана для %s", userID)
	}
}

// LogoutHandler мгновенно инвалидирует сессию
func LogoutHandler(store *SessionStore) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if cookie, err := r.Cookie(SessionCookieName); err == nil {
			store.Delete(cookie.Value)
		}

		// Очистка куки в браузере
		http.SetCookie(w, &http.Cookie{
			Name:     SessionCookieName,
			Value:    "",
			Path:     "/",
			MaxAge:   -1, // Браузер немедленно удалит куку
			HttpOnly: true,
			Secure:   true,
			SameSite: http.SameSiteStrictMode,
		})

		w.WriteHeader(http.StatusOK)
		_, _ = fmt.Fprint(w, "Сессия успешно завершена.")
	}
}

func main() {
	store := NewSessionStore()
	mux := http.NewServeMux()
	mux.HandleFunc("/login", LoginHandler(store))
	mux.HandleFunc("/logout", LogoutHandler(store))

	ts := httptest.NewServer(mux)
	defer ts.Close()

	// 1. Вход в систему: проверка выставленной куки
	reqLogin, _ := http.NewRequest("POST", ts.URL+"/login", nil)
	recLogin := httptest.NewRecorder()
	LoginHandler(store)(recLogin, reqLogin)

	cookies := recLogin.Result().Cookies()
	var sc *http.Cookie
	for _, c := range cookies {
		if c.Name == SessionCookieName {
			sc = c
			break
		}
	}

	fmt.Println("=== 1. Проверка флагов безопасности сессионной куки ===")
	fmt.Printf("Имя куки (Префикс __Host-): %s\n", sc.Name)
	fmt.Printf("HttpOnly (Защита от XSS):   %v\n", sc.HttpOnly)
	fmt.Printf("Secure (Только по HTTPS):    %v\n", sc.Secure)
	fmt.Printf("SameSite:                   StrictMode (%v)\n", sc.SameSite == http.SameSiteStrictMode)
	fmt.Printf("Path:                       %s\n", sc.Path)
	fmt.Printf("MaxAge:                     %d сек\n\n", sc.MaxAge)

	// 2. Выход из системы: проверка очистки куки
	reqLogout, _ := http.NewRequest("POST", ts.URL+"/logout", nil)
	reqLogout.AddCookie(sc)
	recLogout := httptest.NewRecorder()
	LogoutHandler(store)(recLogout, reqLogout)

	logoutCookies := recLogout.Result().Cookies()
	fmt.Println("=== 2. Проверка удаления куки при Logout ===")
	fmt.Printf("Кука очищена (MaxAge == -1): %v\n", logoutCookies[0].MaxAge == -1)
	fmt.Printf("Количество активных сессий в хранилище: %d\n", len(store.sessions))
}
```

## Под капотом

Что дает спецификация префиксов кук `__Host-` (RFC 6265bis)?
В стандартной модели браузера сайт `subdomain.example.com` может установить или перезаписать куку для домена `example.com` (Cookie Tossing Attack). Если хакер захватит контроль над забытым поддоменом, он может подсунуть жертве поддельный session_id.
Префикс `__Host-` принудительно активирует внутреннюю проверку браузера:
1. Кука должна быть получена только по безопасному каналу HTTPS (`Secure`).
2. Кука не может содержать атрибут `Domain` (привязана строго к конкретному FQDN хоста).
3. Атрибут `Path` обязан быть равен `/`. Если хотя бы одно условие нарушено, браузер молча отклоняет куку.

## Подводные камни

1. **Использование SameSite=Strict при внешних редиректах:** Если пользователь переходит по ссылке из корпоративной почты на ваш сайт, при `SameSite=Strict` сессионная кука не отправится, и пользователь увидит страницу входа вместо нужного документа. Для сценариев внешних переходов используют `SameSite=Lax`.
2. **Недостаточная энтропия Session ID:** Использование `math/rand` или автоинкрементных ID из БД позволяет злоумышленнику угадывать чужие сессии. Необходим `crypto/rand` с длиной не менее 128 бит (16 байт).
3. **Session Fixation:** Если не регенерировать Session ID в момент успешного входа пользователя в систему, атакующий может заранее навязать жертве известный session_id.

## На собеседовании

**Вопрос с собеседования:** В каких случаях для браузерного SPA приложения архитектурно правильнее использовать сессионные куки SameSite=Strict + BFF (Backend-For-Frontend), чем хранить JWT/Access Token в LocalStorage браузера?
**Ответ:** Практически **во всех корпоративных и финансовых системах**:
1) **Абсолютная защита от кражи токенов при XSS:** Любой токен в LocalStorage/SessionStorage доступен из JavaScript. Если в SPA просочится XSS-уязвимость (через зараженный npm-пакет), токен будет мгновенно украден. Сессионная кука с `HttpOnly` физически недоступна из JS.
2) **Паттерн BFF (Backend-For-Frontend):** Браузер общается с BFF-шлюзом через защищенную `SameSite=Strict` сессионную куку. Сам BFF хранит access/refresh токены во внутренней защищенной памяти Redis и прозрачно подставляет их при обращении к микросервисам бэкенда.
