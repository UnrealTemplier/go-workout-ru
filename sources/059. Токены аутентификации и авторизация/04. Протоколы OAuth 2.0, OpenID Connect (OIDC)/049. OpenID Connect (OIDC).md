# OpenID Connect (OIDC): Разделение Аутентификации и Авторизации

## Условие

OAuth2 дает только токен для API. OIDC дает стандартизированный профиль юзера. Используй `github.com/coreos/go-oidc`. Настрой провайдера (например, Google), получи ID Token, валидируй его подписи (через публичные ключи Google) и распарси Email и Имя юзера.

### Исходная формулировка

**OpenID Connect (OIDC)**: OAuth2 дает только токен для API. OIDC дает стандартизированный профиль юзера. Используй `github.com/coreos/go-oidc`. Настрой провайдера (например, Google), получи ID Token, валидируй его подписи (через публичные ключи Google) и распарси Email и Имя юзера.

## Теория

Фундаментальное концептуальное различие между **OAuth 2.0** и **OpenID Connect (OIDC)**:
- **OAuth 2.0 — это протокол АВТОРИЗАЦИИ (Делегирования прав):**
  Сервер возвращает `access_token`. Этот токен предназначен для вызова API ресурса. В спецификации OAuth 2.0 нет понятия «пользователь», нет формата токена и нет стандартного способа узнать имя или email того, кто выполнил вход!
- **OpenID Connect (OIDC) — это слой АУТЕНТИФИКАЦИИ (Идентификации личности):**
  Построен поверх OAuth 2.0. Добавляет специальный скоуп `openid` и стандартизированный токен **ID Token** (всегда в формате JWT), содержащий профиль пользователя (`sub`, `name`, `email`, `picture`).

### Архитектура библиотеки `go-oidc`:
В экосистеме Go де-факто стандартом является библиотека `github.com/coreos/go-oidc/v3/oidc`. Она выполняет:
1. `oidc.NewProvider(ctx, issuer)`: обращение к `/.well-known/openid-configuration` и получение адреса JWKS.
2. `provider.Verifier(&oidc.Config{ClientID: clientID})`: создание потокобезопасного валидатора, который автоматически скачивает ключи с Google JWKS, проверяет подписи RSA/ECDSA, парсит claims и сверяет `exp`/`iss`/`aud`.

## Решение по шагам

3. Продемонстрируйте валидацию ID Token с извлечением стандартизированных полей `name`, `email`, `email_verified`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"encoding/base64"
	"encoding/json"
	"fmt"
	"math/big"
	"net/http"
	"net/http/httptest"
	"strings"
	"time"
)

// StandardOIDCProfile описывает стандартный профиль OIDC пользователя
type StandardOIDCProfile struct {
	Subject       string `json:"sub"`
	Email         string `json:"email"`
	EmailVerified bool   `json:"email_verified"`
	Name          string `json:"name"`
	Picture       string `json:"picture"`
}

// OIDCMockServer имитирует полный цикл провайдера Google OIDC
type OIDCMockServer struct {
	PrivKey *rsa.PrivateKey
	KeyID   string
	URL     string
}

func NewOIDCMockServer() *OIDCMockServer {
	priv, _ := rsa.GenerateKey(rand.Reader, 2048)
	return &OIDCMockServer{
		PrivKey: priv,
		KeyID:   "google_key_2026_01",
	}
}

// IssueIDToken создает подписанный ID Token
func (s *OIDCMockServer) IssueIDToken(clientID string, profile StandardOIDCProfile) string {
	headerJSON, _ := json.Marshal(map[string]string{
		"alg": "RS256",
		"typ": "JWT",
		"kid": s.KeyID,
	})

	claimsMap := map[string]interface{}{
		"iss":            s.URL,
		"sub":            profile.Subject,
		"aud":            clientID,
		"exp":            time.Now().Add(1 * time.Hour).Unix(),
		"iat":            time.Now().Unix(),
		"email":          profile.Email,
		"email_verified": profile.EmailVerified,
		"name":           profile.Name,
		"picture":        profile.Picture,
	}
	claimsJSON, _ := json.Marshal(claimsMap)

	seg1 := base64.RawURLEncoding.EncodeToString(headerJSON)
	seg2 := base64.RawURLEncoding.EncodeToString(claimsJSON)
	toSign := seg1 + "." + seg2

	hashed := sha256.Sum256([]byte(toSign))
	sig, _ := rsa.SignPKCS1v15(rand.Reader, s.PrivKey, 0, hashed[:])
	seg3 := base64.RawURLEncoding.EncodeToString(sig)

	return toSign + "." + seg3
}

func main() {
	server := NewOIDCMockServer()
	mux := http.NewServeMux()

	// JWKS эндпоинт
	mux.HandleFunc("/oauth2/v3/certs", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		nB64 := base64.RawURLEncoding.EncodeToString(server.PrivKey.N.Bytes())
		eB64 := base64.RawURLEncoding.EncodeToString(big.NewInt(int64(server.PrivKey.E)).Bytes())

		_ = json.NewEncoder(w).Encode(map[string]interface{}{
			"keys": []map[string]string{
				{
					"kty": "RSA",
					"use": "sig",
					"alg": "RS256",
					"kid": server.KeyID,
					"n":   nB64,
					"e":   eB64,
				},
			},
		})
	})

	ts := httptest.NewServer(mux)
	defer ts.Close()
	server.URL = ts.URL

	clientID := "my-awesome-corp-app.apps.googleusercontent.com"

	// 1. Выпуск OIDC ID Token при успешном логине
	profile := StandardOIDCProfile{
		Subject:       "google_user_1029384756",
		Email:         "senior.architect@yandex.ru",
		EmailVerified: true,
		Name:          "Алексей Смирнов",
		Picture:       "https://lh3.googleusercontent.com/a/photo_123",
	}

	idToken := server.IssueIDToken(clientID, profile)
	fmt.Printf("=== 1. Получен OIDC ID Token ===\n%s\n\n", idToken)

	// 2. Валидация подписи и парсинг профиля
	parts := strings.Split(idToken, ".")
	payloadBytes, _ := base64.RawURLEncoding.DecodeString(parts[1])
	sigBytes, _ := base64.RawURLEncoding.DecodeString(parts[2])

	hash := sha256.Sum256([]byte(parts[0] + "." + parts[1]))
	errSig := rsa.VerifyPKCS1v15(&server.PrivKey.PublicKey, 0, hash[:], sigBytes)
	if errSig != nil {
		panic("Подпись RSA не сошлась!")
	}

	var parsedProfile StandardOIDCProfile
	_ = json.Unmarshal(payloadBytes, &parsedProfile)

	fmt.Println("=== 2. Профиль пользователя извлечен из ID Token ===")
	fmt.Printf("ID (sub):         %s\n", parsedProfile.Subject)
	fmt.Printf("ФИО:              %s\n", parsedProfile.Name)
	fmt.Printf("Email:            %s (Подтвержден: %v)\n", parsedProfile.Email, parsedProfile.EmailVerified)
	fmt.Printf("Аватар URL:       %s\n", parsedProfile.Picture)
}
```

## Под капотом

В спецификации OIDC существует два способа доставки профиля пользователя:
1. **Внутри ID Token:** Если размер утверждений невелик (базовые `email`, `name`), эмитент упаковывает их прямо в полезную нагрузку JWT ID токена.
2. **Через эндпоинт `/userinfo`:** Если профиль содержит объемные данные (списки групп Active Directory, номера телефонов, адреса), клиент использует полученный `access_token` для отдельного вызова `GET /userinfo` с заголовком `Authorization: Bearer <access_token>`. Эндпоинт возвращает стандартизированный JSON профиля пользователя.

## Подводные камни

1. **Использование ID Token для вызова API:** ID Token предназначен **исключительно для клиента** (чтобы приложение знало, кто залогинился). Отправлять `id_token` в качестве Bearer токена на другие микросервисы — грубая ошибка архитектуры. Для вызовов API должен использоваться `access_token`.
2. **Доверие неподтвержденному email:** Поле `email_verified` может быть `false` (например, пользователь зарегистрировался, но еще не перешел по ссылке из письма). Объединение аккаунтов по неподтвержденному email ведет к захвату чужих аккаунтов!
3. **Отсутствие проверки scheme в issuer:** Использование `http://` вместо `https://` делает проверку уязвимой для перехвата трафика.

## На собеседовании

**Вопрос с собеседования:** Почему в highload системах запрещено отправлять `access_token` на эндпоинт `/userinfo` при каждом входящем запросе пользователя, и как OIDC решает эту проблему масштабирования?
**Ответ:** Вызов эндпоинта `/userinfo` на каждый HTTP-запрос создает жесткую сетевую зависимость от стороннего провайдера (Google/Okta): при 100 000 RPS к вашему бэкенду возникнет 100 000 внешних HTTP-запросов к Google, что приведет к мгновенному исчерпанию лимитов (Rate Limit 429) и деградации Latency.
OIDC решает эту проблему за счет **ID Token**: вся первичная идентификационная информация (`sub`, `email`, `name`) уже упакована в криптографически подписанный JWT. Бэкенд валидирует подпись токена локально в памяти через публичный ключ из JWKS (за доли микросекунды) без единого внешнего сетевого вызова!
