# Refresh Токены: Хранение SHA-256 хеша в БД и защита от компрометации

## Условие

Архитектурная задача. Access Token (PASETO) живет 15 минут. Refresh Token — это просто случайная строка на 64 символа (crypto/rand). Храни в БД не сам Refresh Token, а его *хэш* (например, SHA-256 или bcrypt). При получении Refresh Token от клиента, хэшируй его и ищи в БД. Если БД украдут — хакеры не смогут сгенерировать новые Access токены!

### Исходная формулировка

Если БД украдут — хакеры не смогут сгенерировать новые Access токены!

## Теория

Хранение **Refresh токенов в открытом виде в базе данных — критическая архитектурная уязвимость**.

### Сценарий атаки при открытом хранении:
Если злоумышленник получает доступ к резервной копии базы данных (SQL Injection, утечка бэкапа из S3, инсайдер), он получает активные долгоживущие Refresh токены сотен тысяч пользователей. Атакующий может годами генерировать валидные Access токены от имени любого пользователя системы!

### Архитектурный паттерн: Хранение SHA-256 хешей (Token Hashing Pattern)
1. **Генерация:** Сервер генерирует криптографически стойкую случайную строку длиной 64 символа (256 бит энтропии из `crypto/rand`).
2. **Отдача клиенту:** Клиент получает исходный сырой токен \(RT_{\text{raw}}\).
3. **Сохранение в БД:** В базе данных сохраняется **строго односторонний хеш**:
   $$\text{TokenHash} = \text{SHA-256}(RT_{\text{raw}})$$
   Вместе с хешем сохраняются `user_id`, `expires_at`, `family_id` и `created_at`.
4. **Валидация:**
   Когда клиент отправляет токен на ротацию:
   - Сервер вычисляет \(\text{SHA-256}(RT_{\text{client}})\).
   - Сервер выполняет поиск записи в БД по вычисленному хешу.
5. **Результат:**
   Если база данных будет скомпрометирована, злоумышленники увидят только необратимые хеши. Из-за высокой энтропии токена (256 бит) восстановить исходный \(RT_{\text{raw}}\) методом перебора (rainbow tables/brute-force) математически невозможно!

## Решение по шагам

1. Создайте структуру записи токена в БД с полем `TokenHash`.
2. Реализуйте функцию создания refresh токена с отдачей открытого токена клиенту и сохранением SHA-256 в хранилище.
3. Реализуйте функцию валидации и ротации, хеширующую входящий токен перед поиском.
4. Продемонстрируйте успешную ротацию токена.
5. Продемонстрируйте дамп базы данных, подтверждающий отсутствие открытых токенов.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
	"io"
	"sync"
	"time"
)

type RefreshSessionRecord struct {
	TokenHash string    // SHA-256 хеш сырого токена (индекс в БД)
	UserID    string    // Владелец токена
	FamilyID  string    // Семья токенов для RTR
	ExpiresAt time.Time // Срок жизни
	IsRevoked bool      // Статус отзыва
}

type SecureTokenDB struct {
	mu      sync.RWMutex
	records map[string]*RefreshSessionRecord // TokenHash -> Record
}

func NewSecureTokenDB() *SecureTokenDB {
	return &SecureTokenDB{records: make(map[string]*RefreshSessionRecord)}
}

// hashToken вычисляет SHA-256 от сырого токена
func hashToken(raw string) string {
	h := sha256.Sum256([]byte(raw))
	return hex.EncodeToString(h[:])
}

// IssueRefreshToken выпускает токен: сырой отдается клиенту, хеш пишется в БД
func (db *SecureTokenDB) IssueRefreshToken(userID, familyID string) (rawToken string, err error) {
	b := make([]byte, 32) // 256 бит криптографической случайности
	if _, err := io.ReadFull(rand.Reader, b); err != nil {
		return "", err
	}
	rawToken = hex.EncodeToString(b) // 64 символа hex
	tokenHash := hashToken(rawToken)

	record := &RefreshSessionRecord{
		TokenHash: tokenHash,
		UserID:    userID,
		FamilyID:  familyID,
		ExpiresAt: time.Now().Add(30 * 24 * time.Hour), // 30 дней
		IsRevoked: false,
	}

	db.mu.Lock()
	db.records[tokenHash] = record
	db.mu.Unlock()

	return rawToken, nil
}

// ConsumeAndRotate проверяет токен по хешу и выполняет безопасную ротацию
func (db *SecureTokenDB) ConsumeAndRotate(presentedRawToken string) (newRawToken string, err error) {
	presentedHash := hashToken(presentedRawToken)

	db.mu.Lock()
	defer db.mu.Unlock()

	record, exists := db.records[presentedHash]
	if !exists {
		return "", errors.New("неверный refresh токен")
	}

	if record.IsRevoked || time.Now().After(record.ExpiresAt) {
		return "", errors.New("токен отозван или срок его действия истек")
	}

	// Инвалидируем использованный токен (RTR)
	delete(db.records, presentedHash)

	// Выпускаем новый токен в рамках той же семьи
	b := make([]byte, 32)
	_, _ = io.ReadFull(rand.Reader, b)
	newRawToken = hex.EncodeToString(b)
	newHash := hashToken(newRawToken)

	db.records[newHash] = &RefreshSessionRecord{
		TokenHash: newHash,
		UserID:    record.UserID,
		FamilyID:  record.FamilyID,
		ExpiresAt: time.Now().Add(30 * 24 * time.Hour),
		IsRevoked: false,
	}

	return newRawToken, nil
}

func main() {
	db := NewSecureTokenDB()

	// 1. Логин пользователя: выпуск первого токена
	rawToken1, err := db.IssueRefreshToken("usr_security_officer_42", "fam_001")
	if err != nil {
		panic(err)
	}
	fmt.Println("=== 1. Выпущен Refresh Token для клиента ===")
	fmt.Printf("Сырой токен клиента (длина %d): %s\n\n", len(rawToken1), rawToken1)

	// 2. Инспекция базы данных: что видит злоумышленник при утечке бэкапа?
	fmt.Println("=== 2. Дамп базы данных (внутреннее состояние) ===")
	for hash, rec := range db.records {
		fmt.Printf("Хранящийся TokenHash: %s\nUser ID:              %s\nСырой токен в БД:     ОТСУТСТВУЕТ (Защита от утечки!)\n\n",
			hash, rec.UserID)
	}

	// 3. Клиент производит ротацию
	rawToken2, err := db.ConsumeAndRotate(rawToken1)
	if err != nil {
		panic(err)
	}
	fmt.Println("=== 3. Успешная ротация токена ===")
	fmt.Printf("Новый сырой токен клиента: %s\n\n", rawToken2)

	// 4. Попытка использования старого токена
	_, errOld := db.ConsumeAndRotate(rawToken1)
	fmt.Println("=== 4. Попытка использовать старый токен ===")
	fmt.Printf("Результат: %v\n", errOld)
}
```

## Под капотом

Почему для Refresh токенов достаточен быстрый алгоритм SHA-256, а для паролей пользователей обязателен медленный Argon2id или bcrypt?
Пароли пользователей придумываются людьми: они имеют малую энтропию (обычно 30–40 бит) и легко перебираются по словарям при быстром хешировании.
Refresh токен генерируется криптографическим генератором ядра ОС (`crypto/rand`) и содержит **256 бит истинной случайности**. Пространство поиска составляет \(2^{256}\) вариантов. Даже совокупная мощность всех суперкомпьютеров планеты не способна найти коллизию или прообраз для случайной 256-битной строки за время жизни Вселенной!

## Подводные камни

1. **Использование MD5 или SHA-1:** Устаревшие алгоритмы хеширования с известными коллизиями. Использовать строго SHA-256 или SHA-512.
2. **Логирование сырого токена в момент выпуска:** Если при логине сервер пишет сырой токен в Kibana или Jaeger трейсы, безопасность сводится к нулю.
3. **Отсутствие индекса по TokenHash:** Поле `token_hash` в БД должно иметь индекс `UNIQUE`, обеспечивая поиск записи за \(O(1)\) и исключая дубликаты.

## На собеседовании

**Вопрос с собеседования:** Почему в архитектуре HighLoad для хранения хешей Refresh токенов выбирают Redis, а не реляционную базу данных PostgreSQL?
**Ответ:** 1) **Скорость валидации (\(O(1)\) in-memory):** При миллионах пользователей проверка хеша в Redis занимает менее 1 миллисекунды без создания нагрузки на диск primary-базы.
2) **Нативная поддержка TTL:** В Redis записи токенов создаются с автоматическим удалением через команду `EXPIRE`, что исключает необходимость запуска тяжелых периодических cron-скриптов очистки старых записей (`DELETE FROM refresh_tokens WHERE exp < NOW()`), нагружающих таблицы БД.
3) **Атомарность ротации:** Команды ротации реализуются через атомарные Lua-скрипты, исключая гонки данных при параллельных запросах.
