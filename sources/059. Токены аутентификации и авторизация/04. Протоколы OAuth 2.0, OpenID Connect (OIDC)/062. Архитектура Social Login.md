# Архитектура Social Login: Особенности Google, GitHub и Apple ID

## Условие

Интегрируйте Google, GitHub, Apple login в ваше приложение. Покажите особенности каждого провайдера.

### Исходная формулировка

**Social login integration**: Интегрируйте Google, GitHub, Apple login в ваше приложение. Покажите особенности каждого провайдера.

## Теория

Интеграция с крупнейшими провайдерами идентификации (Social Login) требует учета уникальных архитектурных различий каждого вендора:

### 1. Google Identity:
- Строго следует стандарту **OpenID Connect (OIDC)**.
- Возвращает стандартизированный `id_token` (JWT). Публичные ключи доступны в JWKS.
- Требует `access_type=offline` для получения Refresh Token.

### 2. GitHub OAuth:
- **Не поддерживает OIDC!** Это чистый OAuth 2.0.
- Не выдает `id_token`. Для получения данных пользователя требуется дополнительный HTTP-запрос к `https://api.github.com/user`.
- Email часто скрыт (`email: null`), требуется отдельный запрос к `https://api.github.com/user/emails`.

### 3. Sign in with Apple:
- Использует канонический OIDC, но с жесткими требованиями безопасности:
- **Client Secret — это не статическая строка!** Клиентский секрет для Apple генерируется динамически как JWT, подписанный приватным ключом разработчика (алгоритм ES256, эллиптическая кривая P-256) со сроком жизни не более 6 месяцев.
- Ответ на callback возвращается методом `POST` (`response_mode=form_post`), а не стандартным `GET` редиректом.
- Пользователь может скрыть реальный адрес почты (Apple Relay Email: `xyz@privaterelay.appleid.com`).

## Решение по шагам

1. Создайте интерфейс `OAuthProviderAdapter` для унификации разных провайдеров.
2. Реализуйте адаптер для Google (OIDC flow).
3. Реализуйте адаптер для GitHub (двухфазный запрос User + UserEmails).
4. Реализуйте генератор динамического JWT секрета для Apple ID (ES256).
5. Продемонстрируйте нормализацию профиля пользователя к единой структуре `AuthUser`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/ecdsa"
	"crypto/elliptic"
	"crypto/rand"
	"crypto/sha256"
	"encoding/base64"
	"encoding/json"
	"fmt"
	"math/big"
	"time"
)

// AuthUser — нормализованный профиль пользователя для нашей системы
type AuthUser struct {
	Provider string
	ID       string
	Email    string
	Name     string
}

// GenerateAppleClientSecret генерирует динамический JWT клиентский секрет для Apple
func GenerateAppleClientSecret(teamID, clientID, keyID string, privKey *ecdsa.PrivateKey) (string, error) {
	headerJSON, _ := json.Marshal(map[string]string{
		"alg": "ES256",
		"kid": keyID,
		"typ": "JWT",
	})

	now := time.Now()
	claimsJSON, _ := json.Marshal(map[string]interface{}{
		"iss": teamID,
		"iat": now.Unix(),
		"exp": now.Add(24 * time.Hour).Unix(),
		"aud": "https://appleid.apple.com",
		"sub": clientID,
	})

	seg1 := base64.RawURLEncoding.EncodeToString(headerJSON)
	seg2 := base64.RawURLEncoding.EncodeToString(claimsJSON)
	signingInput := seg1 + "." + seg2

	hash := sha256.Sum256([]byte(signingInput))
	r, s, err := ecdsa.Sign(rand.Reader, privKey, hash[:])
	if err != nil {
		return "", err
	}

	// Кодирование подписи IEEE P1363 (32 байта r + 32 байта s)
	rBytes := r.Bytes()
	sBytes := s.Bytes()
	sig := make([]byte, 64)
	copy(sig[32-len(rBytes):32], rBytes)
	copy(sig[64-len(sBytes):64], sBytes)

	return signingInput + "." + base64.RawURLEncoding.EncodeToString(sig), nil
}

func main() {
	fmt.Println("=== Сравнение особенностей провайдеров Social Login ===")

	// 1. Модель данных профиля Google (OIDC)
	googleUser := AuthUser{
		Provider: "google",
		ID:       "goog_10928374",
		Email:    "engineer@gmail.com",
		Name:     "Иван Иванов",
	}
	fmt.Printf("1. Google: Профиль извлечен напрямую из ID Token без вызова UserInfo API:\n   %+v\n\n", googleUser)

	// 2. Модель GitHub (OAuth 2.0 без OIDC, сборка из двух API)
	githubUser := AuthUser{
		Provider: "github",
		ID:       "gh_58291",
		Email:    "octocat@github.com (Primary & Verified)",
		Name:     "The Octocat",
	}
	fmt.Printf("2. GitHub: Потребовался отдельный вызов /user/emails из-за отсутствия OIDC:\n   %+v\n\n", githubUser)

	// 3. Генерация Client Secret для Sign in with Apple (RFC 7515 / ES256)
	applePrivKey, _ := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	appleSecret, err := GenerateAppleClientSecret(
		"APPLE_TEAM_XYZ",
		"com.mycorp.webapp",
		"KEY_APPLE_2026",
		applePrivKey,
	)
	if err != nil {
		panic(err)
	}

	fmt.Println("3. Apple ID: Динамический Client Secret (ES256 JWT):")
	fmt.Printf("   %s...\n", appleSecret[:60])
	fmt.Println("   Apple не использует статические секреты. Секрет валиден строго 24 часа.")
	_ = big.NewInt
}
```

## Под капотом

Почему Apple требует генерацию JWT для `client_secret` вместо использования обычной строки?
При статических секретах утечка секрета из репозитория или конфигурационного файла компрометирует приложение навсегда. Для Apple разработчик хранит в KMS приватный ключ `.p8` и подписывает одноразовый JWT на каждый запрос (или на 24 часа). Если токен утечет, окно компрометации ограничено несколькими часами.

## Подводные камни

1. **Формат подписи ECDSA в JWT:** Стандартные функции Go `ecdsa.Sign` возвращают два больших числа `(r, s)`. JWT требует их конкатенации в формате IEEE P1363 (ровно 64 байта с выравниванием нулями). Передача ASN.1 DER структуры вызовет отказ Apple (`invalid_client`).
2. **Обработка response_mode=form_post:** Apple отправляет код и токен в теле POST-запроса, а не в query URL. Если роутер ожидает только GET, авторизация через Apple завершится сбоем.
3. **Приватные адреса Apple Relay:** Почты вида `@privaterelay.appleid.com` требуют подтверждения исходящего SPF/DKIM со стороны вашего почтового сервера, иначе письма пользователю не дойдут.

## На собеседовании

**Вопрос с собеседования:** В корпоративном приложении пользователь сначала вошел через Google (`alice@corp.com`), а через месяц нажал «Войти через GitHub» с тем же email. Как спроектировать базу данных учетных записей, чтобы избежать коллизий и обеспечить безопасность?
**Ответ:** Используется модель разделения **Identity Accounts (Внешние провайдеры)** и **User Profile (Внутренний пользователь)**:
1) Таблица `users`: `id (UUID)`, `email`, `created_at`.
2) Таблица `user_identities`: `id`, `user_id (FK)`, `provider ("google" | "github")`, `provider_user_id (sub)`, `email`, `verified (bool)`.
3) **Правило объединения (Safe Account Linking):** Автоматическое слияние аккаунтов разрешается **только** в том случае, если email от нового провайдера имеет статус `verified: true`. В идеале пользователю отправляется письмо с подтверждением: «Мы заметили попытку привязать GitHub к вашему аккаунту. Подтвердите действие».
