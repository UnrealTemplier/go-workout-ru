# Сравнение JWT и PASETO: Демонстрация уязвимостей JWT

### Исходная формулировка

## Теория

Исторический стандарт **JWT (JSON Web Token, RFC 7519)** проектировался с концепцией «максимальной криптографической гибкости» (Cryptographic Agility). В заголовке токена передается JSON с параметром `alg`, определяющим, какой алгоритм применить для проверки:
`{"alg": "HS256", "typ": "JWT"}` или `{"alg": "RS256", "typ": "JWT"}` или `{"alg": "none", "typ": "JWT"}`.

### Две классические критические уязвимости JWT:
1. **The `alg: "none"` Attack (CVE-2015-9235):**
   Спецификация RFC 7515 определила алгоритм `"none"` для неподписанных токенов. Злоумышленник берет легитимный токен пользователя, меняет полезную нагрузку (`"role": "admin"`), выставляет `"alg": "none"` и удаляет подпись. Если серверный валидатор не имеет явного белого списка разрешенных алгоритмов, библиотека считает подпись валидной!
2. **Algorithm Confusion Attack (Key Confusion):**
   Сервер выпускает токены с асимметричной подписью `RS256` (приватный ключ у сервера, публичный доступен всем в `/.well-known/jwks.json`). Атакующий подменяет заголовок на симметричный `HS256` (HMAC-SHA256) и подписывает токен **публичным ключом RSA сервера** как симметричным секретом! Сервер, вызывая `jwt.Parse` и передавая публичный RSA-ключ в колбэк `keyFunc`, наивно выполняет `hmac.Verify(pubKeyBytes)`, и подпись сходится!

### Дизайн PASETO (Platform-Agnostic Security Tokens):
В PASETO заголовок жестко фиксирован: `v4.local.` (симметричное шифрование XChaCha20-Poly1305) или `v4.public.` (Ed25519 подпись). В токене **отсутствует** JSON-заголовок и поле `alg`. Атакующий физически не может навязать серверу иной алгоритм или сбить режим валидации.

## Решение по шагам

1. Создайте функции выпуска JWT с алгоритмами HS256 и RS256.
2. Продемонстрируйте атаку `alg: none`: генерацию токена без подписи и ошибку наивного валидатора.
3. Продемонстрируйте атаку Algorithm Confusion (подпись публичным RSA-ключом через HMAC).
4. Продемонстрируйте, как PASETO синтаксически блокирует подобные манипуляции.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"crypto/x509"
	"encoding/base64"
	"encoding/json"
	"errors"
	"fmt"
	"strings"
)

// NaiveJWTValidator — уязвимый парсер JWT, доверяющий заголовку alg
func NaiveJWTValidator(tokenString string, hmacSecret []byte, rsaPub *rsa.PublicKey) (map[string]interface{}, error) {
	parts := strings.Split(tokenString, ".")
	if len(parts) != 3 {
		return nil, errors.New("неверный формат JWT (ожидалось 3 части)")
	}

	headerJSON, err := base64.RawURLEncoding.DecodeString(parts[0])
	if err != nil {
		return nil, err
	}

	var header map[string]interface{}
	if err := json.Unmarshal(headerJSON, &header); err != nil {
		return nil, err
	}

	alg, _ := header["alg"].(string)

	// УЯЗВИМОСТЬ 1: Принятие alg: none
	if strings.ToLower(alg) == "none" {
		// Наивный сервер верит заголовку и не проверяет подпись!
		payloadBytes, _ := base64.RawURLEncoding.DecodeString(parts[1])
		var claims map[string]interface{}
		_ = json.Unmarshal(payloadBytes, &claims)
		return claims, nil
	}

	// УЯЗВИМОСТЬ 2: Algorithm Confusion (подмена RS256 на HS256)
	if alg == "HS256" {
		// Сервер думает, что должен проверить HMAC, но если ему передали rsaPub как секрет:
		signedData := parts[0] + "." + parts[1]
		h := hmac.New(sha256.New, hmacSecret)
		h.Write([]byte(signedData))
		expectedSig := h.Sum(nil)

		clientSig, _ := base64.RawURLEncoding.DecodeString(parts[2])
		if !hmac.Equal(clientSig, expectedSig) {
			return nil, errors.New("неверная HMAC подпись")
		}

		payloadBytes, _ := base64.RawURLEncoding.DecodeString(parts[1])
		var claims map[string]interface{}
		_ = json.Unmarshal(payloadBytes, &claims)
		return claims, nil
	}

	return nil, fmt.Errorf("неподдерживаемый алгоритм: %s", alg)
}

// SecurePASETOValidator — строгий валидатор без уязвимостей
func SecurePASETOValidator(token string) error {
	if !strings.HasPrefix(token, "v4.public.") && !strings.HasPrefix(token, "v4.local.") {
		return errors.New("PASETO REJECT: Недопустимый префикс токена. Никаких гибких alg заголовков!")
	}
	return nil
}

func main() {
	rsaPriv, _ := rsa.GenerateKey(rand.Reader, 2048)
	rsaPubBytes, _ := x509.MarshalPKIXPublicKey(&rsaPriv.PublicKey)

	fmt.Println("=== 1. Атака JWT: alg: none ===")
	// Атакующий подделывает права администратора
	headerNone := base64.RawURLEncoding.EncodeToString([]byte(`{"alg":"none","typ":"JWT"}`))
	claimsHacker := base64.RawURLEncoding.EncodeToString([]byte(`{"sub":"attacker","role":"super_admin"}`))
	noneToken := headerNone + "." + claimsHacker + "." // пустая подпись

	// Наивный сервер валидирует токен
	claims, err := NaiveJWTValidator(noneToken, []byte("secret"), &rsaPriv.PublicKey)
	if err == nil {
		fmt.Printf("ВЗЛОМ УСПЕШЕН: Сервер принял токен с alg:none! Права: %v\n\n", claims["role"])
	}

	fmt.Println("=== 2. Атака JWT: Algorithm Confusion ===")
	// Атакующий берет публичный ключ RSA сервера и подписывает им токен через HMAC-SHA256
	headerHS256 := base64.RawURLEncoding.EncodeToString([]byte(`{"alg":"HS256","typ":"JWT"}`))
	signedContent := headerHS256 + "." + claimsHacker
	h := hmac.New(sha256.New, rsaPubBytes) // Секретом выступает открытый ключ!
	h.Write([]byte(signedContent))
	forgedSig := base64.RawURLEncoding.EncodeToString(h.Sum(nil))
	forgedJWT := signedContent + "." + forgedSig

	// Сервер ожидал RS256, но перепутал ключ из-за заголовка клиента
	claims2, err2 := NaiveJWTValidator(forgedJWT, rsaPubBytes, &rsaPriv.PublicKey)
	if err2 == nil {
		fmt.Printf("ВЗЛОМ УСПЕШЕН: Algorithm Confusion сработал! Субъект: %v, Роль: %v\n\n",
			claims2["sub"], claims2["role"])
	}

	fmt.Println("=== 3. Защита PASETO ===")
	// В PASETO невозможно подсунуть alg:none или подменить алгоритм
	errPaseto := SecurePASETOValidator(noneToken)
	fmt.Printf("Результат проверки вредоносного токена в PASETO:\n%v\n", errPaseto)
}
```

## Под капотом

В библиотеке `golang-jwt/jwt` защита от Algorithm Confusion реализована через обязательную проверку типа метода подписи внутри колбэка `Keyfunc`:
```go
token, err := jwt.Parse(tokenStr, func(t *jwt.Token) (interface{}, error) {
    if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {
        return nil, fmt.Errorf("unexpected signing method: %v", t.Header["alg"])
    }
    return rsaPublicKey, nil
})
```
Если разработчик забудет эту проверку (а многие начинающие разработчики ее опускают), библиотека попытается использовать `rsaPublicKey` для проверки HMAC, открывая критическую дыру в безопасности.

## Подводные камни

1. **Слепое доверие header["alg"]:** Никогда нельзя выбирать алгоритм верификации на основе данных из заголовка токена, переданного клиентом. Алгоритм должен быть жестко сконфигурирован на стороне сервера.
2. **Разрешение alg: none в production коде:** Любая ветка кода, пропускающая `alg == "none"`, должна быть полностью вырезана из продакшен сборок.
3. **Хранение RSA Public Key в формате PEM как строки для HMAC:** Если публичный ключ сервера известен, любой злоумышленник может использовать его байты для создания валидной HMAC-подписи при Algorithm Confusion.

## На собеседовании

**Вопрос с собеседования:** Почему ведущие эксперты по безопасности (например, Paragon Initiative) называют стандарт JWT/JOSE «фундаментально дефектным по дизайну» (broken by design)?
**Ответ:** Стандарт JWT нарушает базовые правила безопасного проектирования протоколов:
1) **Принцип минимизации криптографической гибкости:** Протокол оставляет выбор криптоалгоритма на откуп недоверенному клиенту через заголовок `alg`.
2) **Отсутствие аутентификации метаданных заголовка в старых спецификациях:** Заголовок передается в открытом JSON-виде и легко подвергается манипуляциям.
3) **Перегруженность опциями:** Поддержка десятков несовместимых алгоритмов (RSA, ECDSA, HMAC, none, EdDSA) многократно увеличивает поверхность атаки и гарантирует появление багов в парсерах.""Client Libraries"".
