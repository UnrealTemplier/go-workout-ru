# Refresh Token Rotation: Детекция повторного использования и отзыв сессий

## Условие

Реализуйте механизм: при использовании refresh token выпускается новый access token и новый refresh token, старый инвалидируется. Обнаружьте повторное использование refresh token и отзовите все токены пользователя.

### Исходная формулировка

**Refresh Token Rotation.**: Реализуйте механизм: при использовании refresh token выпускается новый access token и новый refresh token, старый инвалидируется. Обнаружьте повторное использование refresh token и отзовите все токены пользователя.

## Теория

Механизм **Refresh Token Rotation (RTR)** с детекцией повторного использования (Replay Detection) — обязательный стандарт безопасности OAuth 2.0 Security BCP.

### Анатомия атаки и защита:
1. **Токен украден:** У пользователя Алисы похищен активный `Refresh Token 1` (\(RT_1\)).
2. **Атакующий использует \(RT_1\):** Атакующий отправляет \(RT_1\) на сервер. Сервер считает его легитимным, инвалидирует \(RT_1\) и выдает атакующему \(RT_2\).
3. **Жертва пытается использовать \(RT_1\):** Спустя некоторое время легитимный клиент Алисы отправляет тот же самый \(RT_1\).
4. **Срабатывание Replay Detection:**
   - Сервер видит: токен \(RT_1\) уже был использован ранее!
   - Сервер понимает, что один токен попал в руки двум сторонам.
   - Сервер **немедленно аннулирует всю сессию (Token Family)**: и \(RT_1\), и выданный злоумышленнику \(RT_2\)!
   - Сессия пользователя завершается, а в SIEM отправляется алерт о компрометации учетной записи.

### Паттерн Grace Period (Защита от сетевых сбоев):
В мобильных сетях ответ с \(RT_2\) может потеряться из-за обрыва связи. Поэтому сервер дает короткое окно (10–15 секунд), в течение которого повторный запрос с \(RT_1\) возвращает **тот же самый \(RT_2\)**, не считая это атакой. Но по истечении этого окна любой запрос с \(RT_1\) расценивается как кража!

## Решение по шагам

1. Создайте структуру сессии с историей использованных токенов и таймстемпами.
2. Реализуйте метод `RotateRefreshToken` с проверкой валидности и статуса использования.
3. Реализуйте Grace Period (окно толерантности) для безопасной обработки повторных мобильных запросов.
4. Реализуйте детектор кражи: если предъявлен токен старше Grace Period — уничтожить всю сессию пользователя.
5. Продемонстрируйте сценарий кражи токена и автоматическую блокировку доступа злоумышленнику.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"io"
	"sync"
	"time"
)

type SessionFamily struct {
	FamilyID     string
	UserID       string
	ActiveToken  string
	History      map[string]time.Time // токен -> время когда он был ротирован
	GraceTokens  map[string]string    // старый токен -> выданный взамен новый токен
	Revoked      bool
}

type TokenStoreRTR struct {
	mu       sync.Mutex
	sessions map[string]*SessionFamily // FamilyID -> Session
	tokenIdx map[string]string         // Token -> FamilyID
}

func NewTokenStoreRTR() *TokenStoreRTR {
	return &TokenStoreRTR{
		sessions: make(map[string]*SessionFamily),
		tokenIdx: make(map[string]string),
	}
}

func cryptoRandomID(pfx string) string {
	b := make([]byte, 16)
	_, _ = io.ReadFull(rand.Reader, b)
	return fmt.Sprintf("%s_%s", pfx, hex.EncodeToString(b))
}

// IssueNewSession создает новую семью токенов при авторизации
func (s *TokenStoreRTR) IssueNewSession(userID string) (string, string) {
	s.mu.Lock()
	defer s.mu.Unlock()

	famID := cryptoRandomID("fam")
	rt := cryptoRandomID("rt")
	at := cryptoRandomID("at")

	family := &SessionFamily{
		FamilyID:    famID,
		UserID:      userID,
		ActiveToken: rt,
		History:     make(map[string]time.Time),
		GraceTokens: make(map[string]string),
		Revoked:     false,
	}

	s.sessions[famID] = family
	s.tokenIdx[rt] = famID
	return at, rt
}

// RotateRefreshToken выполняет безопасную ротацию токена
func (s *TokenStoreRTR) RotateRefreshToken(presentedToken string) (newAt, newRt string, err error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	famID, exists := s.tokenIdx[presentedToken]
	if !exists {
		return "", "", errors.New("токен не найден в реестре")
	}

	family := s.sessions[famID]

	// 1. Проверка блокировки всей семьи
	if family.Revoked {
		return "", "", errors.New("SECURITY REJECT: Данная сессия заблокирована из-за подозрения на кражу токенов")
	}

	// 2. ДЕТЕКЦИЯ ПОВТОРНОГО ИСПОЛЬЗОВАНИЯ (REPLAY DETECTION)
	rotatedAt, wasRotated := family.History[presentedToken]
	if wasRotated {
		const gracePeriod = 2 * time.Second // 2 секунды для демонстрации

		// Проверяем Grace Period (мобильный retry при потере пакета)
		if time.Since(rotatedAt) <= gracePeriod {
			cachedNewRt := family.GraceTokens[presentedToken]
			fmt.Printf(">>> [Grace Period]: Повторный запрос в окне %v. Возвращаем существующий %s\n", gracePeriod, cachedNewRt)
			return "at_cached_valid", cachedNewRt, nil
		}

		// ИСТЕК GRACE PERIOD -> КРАЖА ТОКЕНА!
		family.Revoked = true // Аннулируем ВСЮ семью!
		return "", "", fmt.Errorf("CRITICAL SECURITY BREACH: Попытка повторного использования токена %s! Вся семья сессий %s немедленно отозвана!",
			presentedToken, famID)
	}

	// 3. Проверка: является ли токен активным
	if family.ActiveToken != presentedToken {
		family.Revoked = true
		return "", "", errors.New("нарушение последовательности токенов: сессия аннулирована")
	}

	// 4. Успешная ротация
	newRt = cryptoRandomID("rt")
	newAt = cryptoRandomID("at")

	family.History[presentedToken] = time.Now()
	family.GraceTokens[presentedToken] = newRt
	family.ActiveToken = newRt
	s.tokenIdx[newRt] = famID

	return newAt, newRt, nil
}

func main() {
	store := NewTokenStoreRTR()

	// 1. Вход пользователя
	at1, rt1 := store.IssueNewSession("usr_engineer_99")
	fmt.Printf("=== 1. Первичная выдача сессии ===\nAccess:  %s\nRefresh: %s\n\n", at1, rt1)

	// 2. Первая ротация (Легитимный клиент обновляет токен)
	at2, rt2, err := store.RotateRefreshToken(rt1)
	if err != nil {
		panic(err)
	}
	fmt.Printf("=== 2. Успешная ротация токена ===\nAccess:  %s\nRefresh: %s (rt1 переведен в статус использованных)\n\n", at2, rt2)

	// 3. Мобильный Retry в рамках Grace Period (сеть моргнула)
	fmt.Println("=== 3. Проверка Grace Period (мгновенный повтор) ===")
	_, rtGrace, _ := store.RotateRefreshToken(rt1)
	fmt.Printf("Результат Grace Period: Токен возвращен без паники (%s == %s)\n\n", rtGrace, rt2)

	// 4. Проходит время (Grace Period истек)
	fmt.Println("Ждем 2.1 секунды для истечения Grace Period...")
	time.Sleep(2100 * time.Millisecond)

	// 5. Атакующий пытается применить украденный старый токен rt1
	fmt.Println("=== 4. Атака злоумышленника устаревшим токеном rt1 ===")
	_, _, errAttack := store.RotateRefreshToken(rt1)
	fmt.Printf("Результат: %v\n\n", errAttack)

	// 6. Проверка: может ли теперь кто-либо использовать rt2?
	fmt.Println("=== 5. Попытка использования токена rt2 после тревоги ===")
	_, _, errBlocked := store.RotateRefreshToken(rt2)
	fmt.Printf("Результат: %v\n", errBlocked)
}
```

## Под капотом

В распределенной системе реализация Token Family в Redis строится на базе Redis Hashes и транзакций `WATCH`/`MULTI`/`EXEC` или Lua-скриптов. Атомарность критически важна: при конкурентных запросах проверка наличия токена в истории и выпуск нового токена должны выполняться как единая неделимая операция, исключающая состояние гонки (Race Condition).

## Подводные камни

1. **Отсутствие Grace Period:** Приведет к лавинообразным жалобам пользователей мобильного приложения («Меня постоянно выбивает из аккаунта при переходе из Wi-Fi в LTE»).
2. **Неограниченное время жизни Token Family:** Вся семья токенов обязана иметь жесткий Absolute Expiration (например, 30 дней). Нельзя позволять сессии жить бесконечно, даже при непрерывной ротации.
3. **Хранение Refresh токенов в открытом виде:** В БД должны храниться строго SHA-256 хеши токенов.

## На собеседовании

**Вопрос с собеседования:** Что такое Sliding Expiration и Absolute Expiration для Refresh токенов, и как их правильно комбинировать в банковских приложениях?
**Ответ:** 1) **Sliding Expiration (Скользящее окно):** При каждой активности и ротации токена срок жизни продлевается на фиксированный интервал \(\Delta t\) (например, на 7 дней). Если пользователь не открывал приложение неделю — сессия истекает.
2) **Absolute Expiration (Абсолютный предел):** Жесткая дата окончания жизни сессии (например, строго 30 дней с момента первого ввода пароля и SMS-кода), которая **никогда не сдвигается** при ротациях.
Комбинация: токен живет по скользящему окну, но не дольше абсолютного предела. По истечении абсолютного срока пользователя в обязательном порядке просят повторно ввести пароль и пройти двухфакторную аутентификацию (2FA).
