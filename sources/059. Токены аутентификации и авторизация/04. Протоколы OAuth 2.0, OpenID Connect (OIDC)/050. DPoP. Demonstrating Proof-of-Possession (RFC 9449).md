# DPoP: Demonstrating Proof-of-Possession (RFC 9449)

## Условие

Реализуйте упрощённый DPoP: JWT, подписанный ключом клиента (Ed25519), содержащий `htm` (HTTP method) и `htu` (URI). Сервер проверяет подпись и привязку к запросу. Объясните, как это защищает от theft bearer token (токен не работает без приватного ключа клиента).

### Исходная формулировка

**DPoP (Demonstrating Proof-of-Possession).**: Реализуйте упрощённый DPoP: JWT, подписанный ключом клиента (Ed25519), содержащий `htm` (HTTP method) и `htu` (URI). Сервер проверяет подпись и привязку к запросу. Объясните, как это защищает от theft bearer token (токен не работает без приватного ключа клиента).

## Теория

Исторически классический токен доступа в OAuth 2.0 является **Bearer Token (Токеном на предъявителя)**: любой субъект, перехвативший токен (через MITM, утечку в логах, вредоносный proxy или XSS), может использовать его для доступа к ресурсам жертвы.

Спецификация **DPoP (Demonstrating Proof-of-Possession at the Application Layer, RFC 9449)** решает проблему кражи токенов на уровне протокола приложения:
- Токен доступа криптографически привязывается к **приватному ключу конкретного клиента** (Sender-Constrained Token).
- На каждый HTTP-запрос к защищенному API клиент генерирует короткоживущий эфемерный JWT-токен подтверждения владения (DPoP Proof) и передает его в заголовке `DPoP: <jwt>`.

### Структура DPoP Proof:
1. **Заголовок:** `{"typ": "dpop+jwt", "alg": "EdDSA", "jwk": { <публичный ключ клиента> }}`.
2. **Payload:**
   - `htm`: точный HTTP метод текущего запроса (`"POST"`, `"GET"`).
   - `htu`: канонический URI текущего запроса (`"https://api.corp.com/payments"`).
   - `iat`: время генерации доказательства.
   - `jti`: уникальный одноразовый UUID запроса (защита от Replay).
3. **Подпись:** вычисляется приватным ключом клиента.

Сервер сверяет:
- Совпадает ли `htm` с `r.Method`, а `htu` — с `r.URL.Path`?
- Не устарел ли `iat` (\(\pm 60\) сек)?
- Не использовался ли данный `jti` ранее?
- Совпадает ли отпечаток публичного ключа JWK с отпечатком `jkt`, вшитым в Access Token?

Даже если злоумышленник перехватит `access_token`, он бесполезен без закрытого ключа клиента, хранящегося в защищенной памяти Secure Enclave / TPM!

## Решение по шагам

1. Сгенерируйте пару ключей клиента Ed25519.
2. Реализуйте функцию клиента `CreateDPoPProof(method, uri, privKey, pubKey)`.
3. Реализуйте серверный HTTP-Middleware, проверяющий заголовок `DPoP`.
4. Реализуйте защиту от Replay атак через проверку одноразовости `jti`.
5. Продемонстрируйте блокировку запроса при несовпадении HTTP-метода или повторной отправке того же доказательства.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/ed25519"
	"crypto/rand"
	"encoding/base64"
	"encoding/hex"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"time"
)

type DPoPHeader struct {
	Typ string  `json:"typ"`
	Alg string  `json:"alg"`
	JWK JWKData `json:"jwk"`
}

type JWKData struct {
	Kty string `json:"kty"`
	Crv string `json:"crv"`
	X   string `json:"x"` // публичный ключ Ed25519 в base64url
}

type DPoPClaims struct {
	Jti string `json:"jti"`
	Htm string `json:"htm"`
	Htu string `json:"htu"`
	Iat int64  `json:"iat"`
}

// CreateDPoPProof генерирует заголовок подтверждения владения (RFC 9449)
func CreateDPoPProof(method, uri string, priv ed25519.PrivateKey, pub ed25519.PublicKey) (string, error) {
	b := make([]byte, 16)
	_, _ = io.ReadFull(rand.Reader, b)
	jti := hex.EncodeToString(b)

	header := DPoPHeader{
		Typ: "dpop+jwt",
		Alg: "EdDSA",
		JWK: JWKData{
			Kty: "OKP",
			Crv: "Ed25519",
			X:   base64.RawURLEncoding.EncodeToString(pub),
		},
	}

	claims := DPoPClaims{
		Jti: jti,
		Htm: method,
		Htu: uri,
		Iat: time.Now().Unix(),
	}

	headerJSON, _ := json.Marshal(header)
	claimsJSON, _ := json.Marshal(claims)

	seg1 := base64.RawURLEncoding.EncodeToString(headerJSON)
	seg2 := base64.RawURLEncoding.EncodeToString(claimsJSON)
	toSign := seg1 + "." + seg2

	sig := ed25519.Sign(priv, []byte(toSign))
	seg3 := base64.RawURLEncoding.EncodeToString(sig)

	return toSign + "." + seg3, nil
}

// DPoPMiddleware проверяет корректность доказательства DPoP
type DPoPMiddleware struct {
	mu       sync.Mutex
	jtiCache map[string]time.Time
}

func NewDPoPMiddleware() *DPoPMiddleware {
	return &DPoPMiddleware{jtiCache: make(map[string]time.Time)}
}

func (m *DPoPMiddleware) Verify(r *http.Request) error {
	proof := r.Header.Get("DPoP")
	if proof == "" {
		return errors.New("отсутствует заголовок DPoP")
	}

	parts := strings.Split(proof, ".")
	if len(parts) != 3 {
		return errors.New("неверный формат DPoP proof")
	}

	headerBytes, _ := base64.RawURLEncoding.DecodeString(parts[0])
	claimsBytes, _ := base64.RawURLEncoding.DecodeString(parts[1])
	sigBytes, _ := base64.RawURLEncoding.DecodeString(parts[2])

	var h DPoPHeader
	var c DPoPClaims
	_ = json.Unmarshal(headerBytes, &h)
	_ = json.Unmarshal(claimsBytes, &c)

	// 1. Проверка заголовка
	if h.Typ != "dpop+jwt" || h.Alg != "EdDSA" {
		return errors.New("неверный тип или алгоритм DPoP")
	}

	// 2. Восстановление публичного ключа клиента
	pubBytes, err := base64.RawURLEncoding.DecodeString(h.JWK.X)
	if err != nil || len(pubBytes) != ed25519.PublicKeySize {
		return errors.New("невалидный JWK ключ клиента в DPoP proof")
	}
	clientPubKey := ed25519.PublicKey(pubBytes)

	// 3. Проверка подписи запроса
	signedData := parts[0] + "." + parts[1]
	if !ed25519.Verify(clientPubKey, []byte(signedData), sigBytes) {
		return errors.New("криптографическая подпись DPoP не сошлась!")
	}

	// 4. Проверка метода и URI
	if r.Method != c.Htm {
		return fmt.Errorf("метод не совпадает: запрос %s, DPoP %s", r.Method, c.Htm)
	}
	if r.URL.Path != c.Htu {
		return fmt.Errorf("URI не совпадает: запрос %s, DPoP %s", r.URL.Path, c.Htu)
	}

	// 5. Проверка возраста доказательства (±60 сек)
	now := time.Now().Unix()
	if now-c.Iat > 60 || c.Iat-now > 60 {
		return errors.New("DPoP proof устарел")
	}

	// 6. Защита от повторного использования (Replay JTI)
	m.mu.Lock()
	defer m.mu.Unlock()
	if _, seen := m.jtiCache[c.Jti]; seen {
		return errors.New("DPoP JTI Replay detected: доказательство уже было использовано!")
	}
	m.jtiCache[c.Jti] = time.Now()

	return nil
}

func main() {
	clientPub, clientPriv, _ := ed25519.GenerateKey(rand.Reader)
	verifier := NewDPoPMiddleware()

	apiHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if err := verifier.Verify(r); err != nil {
			http.Error(w, fmt.Sprintf("DPoP Error: %v", err), http.StatusUnauthorized)
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"success","balance":100500}`))
	})

	ts := httptest.NewServer(apiHandler)
	defer ts.Close()

	// 1. Легитимный вызов с корректным DPoP доказательством
	proof, _ := CreateDPoPProof("GET", "/api/balance", clientPriv, clientPub)
	req1, _ := http.NewRequest("GET", ts.URL+"/api/balance", nil)
	req1.Header.Set("Authorization", "DPoP some_mock_access_token")
	req1.Header.Set("DPoP", proof)

	resp1, _ := http.DefaultClient.Do(req1)
	body1, _ := io.ReadAll(resp1.Body)
	resp1.Body.Close()
	fmt.Printf("=== 1. Легитимный DPoP запрос ===\nHTTP Status: %d, Ответ: %s\n\n", resp1.StatusCode, string(body1))

	// 2. Атака подмены метода: злоумышленник пытается использовать то же доказательство для POST
	reqBadMethod, _ := http.NewRequest("POST", ts.URL+"/api/balance", nil)
	reqBadMethod.Header.Set("DPoP", proof)
	respBad, _ := http.DefaultClient.Do(reqBadMethod)
	bodyBad, _ := io.ReadAll(respBad.Body)
	respBad.Body.Close()
	fmt.Printf("=== 2. Атака подмены метода (POST вместо GET) ===\nHTTP Status: %d, Ошибка: %s\n\n", respBad.StatusCode, string(bodyBad))

	// 3. Replay-атака: повторная отправка идентичного DPoP доказательства
	reqReplay, _ := http.NewRequest("GET", ts.URL+"/api/balance", nil)
	reqReplay.Header.Set("DPoP", proof)
	respReplay, _ := http.DefaultClient.Do(reqReplay)
	bodyReplay, _ := io.ReadAll(respReplay.Body)
	respReplay.Body.Close()
	fmt.Printf("=== 3. Replay-атака тем же токеном proof ===\nHTTP Status: %d, Ошибка: %s\n", respReplay.StatusCode, string(bodyReplay))
}
```

## Под капотом

Спецификация RFC 9449 требует: при выпуске DPoP Access токена сервер авторизации вычисляет криптографический отпечаток открытого ключа клиента (**JWK SHA-256 Thumbprint, RFC 7638**):
`jkt = base64url(sha256(canonical_jwk))`.
Этот хеш запекается внутрь access token в клейм `cnf.jkt` (Confirmation Claim). Когда ресурсный сервер получает запрос, он сверяет: совпадает ли JWK из заголовка `DPoP` с хешем `cnf.jkt` из `access_token`. Если хакер украл `access_token`, он не может создать валидный `DPoP` заголовок, так как не имеет закрытого ключа, соответствующего этому `jkt`.

## Подводные камни

1. **Неограниченное время жизни доказательства:** DPoP proof должен быть действителен считанные секунды (обычно 10–60 секунд). Долгоживущие доказательства открывают окно для Replay атак.
2. **Несвоевременная очистка JTI:** Без вытеснения устаревших `jti` оперативная память сервера будет исчерпана. Хранить `jti` нужно ровно в течение окна допустимого устаревания `iat`.
3. **Игнорирование схемы URI:** Параметр `htu` должен строго нормализоваться, исключая относительные ссылки и query-параметры.

## На собеседовании

**Вопрос с собеседования:** Чем стандарт DPoP (RFC 9449) превосходит mTLS (Mutual TLS Client Certificate Authentication, RFC 8705) в архитектурах с мобильными клиентами и микросервисами?
**Ответ:** 1) **Работа на уровне L7 (Application Layer):** mTLS требует терминации TLS-сертификатов клиента на периметре (L4/L7 Ingress/Load Balancer), что крайне сложно настраивать в CDN (Cloudflare) и облачных балансировщиках (AWS ALB). DPoP передается в стандартном HTTP-заголовке и прозрачно проходит сквозь любые прокси. 2) **Совместимость с мобильными ОС и SPA:** Мобильные браузеры и веб-клиенты плохо поддерживают установку клиентских TLS-сертификатов. DPoP реализуется чисто программно на Web Crypto API или CryptoKit за счет встроенных ключей устройства.
