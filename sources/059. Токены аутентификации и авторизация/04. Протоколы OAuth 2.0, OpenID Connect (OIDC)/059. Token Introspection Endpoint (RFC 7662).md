# Token Introspection Endpoint (RFC 7662)

## Условие

Реализуйте валидацию opaque access tokens через introspection endpoint (RFC 7662).

### Исходная формулировка

**Token introspection endpoint**: Реализуйте валидацию opaque access tokens через introspection endpoint (RFC 7662).

## Теория

В корпоративных системах с повышенными требованиями к безопасности часто используются **Opaque Tokens (Непрозрачные токены)** вместо JWT:
- Opaque токен представляет собой случайную строку криптографической энтропии (например, 256-битный случайный hex).
- В самом токене нет никакой информации о пользователе или правах доступа.
- Спецификация **OAuth 2.0 Token Introspection (RFC 7662)** описывает стандартизированный протокол, с помощью которого Ресурсный Сервер обращается к Серверу Авторизации для проверки статуса токена.

### Протокол интроспекции:
1. Защищенный API получает запрос: `Authorization: Bearer op_token_xyz123`.
2. API отправляет POST-запрос на эндпоинт интроспекции Сервера Авторизации:
   ```http
   POST /oauth/introspect HTTP/1.1
   Host: auth.example.com
   Authorization: Basic <ресурсный_сервер:секрет>
   Content-Type: application/x-www-form-urlencoded

   token=op_token_xyz123&token_type_hint=access_token
   ```
3. Сервер Авторизации возвращает JSON:
   - Если токен активен:
     `{"active": true, "scope": "read write", "client_id": "client_1", "sub": "usr_42", "exp": 1741100000}`.
   - Если токен отозван, просрочен или не существует:
     `{"active": false}`.

## Решение по шагам

1. Создайте структуру данных активного токена на сервере авторизации.
2. Реализуйте эндпоинт `/oauth/introspect` по стандарту RFC 7662 с проверкой прав ресурсного сервера.
3. Реализуйте клиентское middleware на ресурсном сервере с локальным кэшированием результатов интроспекции (TTL 30 секунд).
4. Продемонстрируйте валидацию активного токена.
5. Продемонстрируйте мгновенный отказ в доступе после отзыва токена в хранилище.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
	"sync"
	"time"
)

type TokenMeta struct {
	Active    bool   `json:"active"`
	Scope     string `json:"scope,omitempty"`
	ClientID  string `json:"client_id,omitempty"`
	Subject   string `json:"sub,omitempty"`
	ExpiresAt int64  `json:"exp,omitempty"`
}

// AuthServerIntrospect симулирует сервер авторизации RFC 7662
type AuthServerIntrospect struct {
	mu     sync.RWMutex
	tokens map[string]TokenMeta
}

func (s *AuthServerIntrospect) HandleIntrospect(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}

	token := r.FormValue("token")

	s.mu.RLock()
	meta, exists := s.tokens[token]
	s.mu.RUnlock()

	w.Header().Set("Content-Type", "application/json")

	// Если токен не найден или просрочен — возвращаем active: false
	if !exists || time.Now().Unix() > meta.ExpiresAt {
		_ = json.NewEncoder(w).Encode(map[string]bool{"active": false})
		return
	}

	meta.Active = true
	_ = json.NewEncoder(w).Encode(meta)
}

// ResourceServerValidator валидирует токены через интроспекцию
type ResourceServerValidator struct {
	introspectURL string
}

func (v *ResourceServerValidator) ValidateToken(token string) (*TokenMeta, error) {
	form := url.Values{"token": {token}}
	resp, err := http.PostForm(v.introspectURL, form)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()

	var meta TokenMeta
	if err := json.NewDecoder(resp.Body).Decode(&meta); err != nil {
		return nil, err
	}

	return &meta, nil
}

func main() {
	authServer := &AuthServerIntrospect{
		tokens: map[string]TokenMeta{
			"opaque_tok_alpha_777": {
				Scope:     "reports.view users.export",
				ClientID:  "analytics_worker",
				Subject:   "usr_lead_analyst",
				ExpiresAt: time.Now().Add(10 * time.Minute).Unix(),
			},
		},
	}

	mux := http.NewServeMux()
	mux.HandleFunc("/oauth/introspect", authServer.HandleIntrospect)
	ts := httptest.NewServer(mux)
	defer ts.Close()

	validator := &ResourceServerValidator{introspectURL: ts.URL + "/oauth/introspect"}

	// 1. Проверка активного токена
	fmt.Println("=== 1. Интроспекция активного токена ===")
	meta1, err := validator.ValidateToken("opaque_tok_alpha_777")
	if err != nil {
		panic(err)
	}
	fmt.Printf("Active:    %v\n", meta1.Active)
	fmt.Printf("Subject:   %s\n", meta1.Subject)
	fmt.Printf("Scopes:    %s\n\n", meta1.Scope)

	// 2. Администратор отзывает токен (Instant Revocation)
	fmt.Println("=== 2. Администратор отзывает токен из базы ===")
	authServer.mu.Lock()
	delete(authServer.tokens, "opaque_tok_alpha_777")
	authServer.mu.Unlock()

	// 3. Повторная интроспекция отозванного токена
	meta2, _ := validator.ValidateToken("opaque_tok_alpha_777")
	fmt.Printf("Active:    %v (Токен мгновенно заблокирован!)\n\n", meta2.Active)

	// 4. Интроспекция заведомо фейкового токена
	fmt.Println("=== 3. Интроспекция несуществующего токена ===")
	meta3, _ := validator.ValidateToken("fake_random_string_999")
	fmt.Printf("Active:    %v\n", meta3.Active)
	_ = io.ReadAll
	_ = strings.Contains
}
```

## Под капотом

Согласно RFC 7662, эндпоинт интроспекции обязан быть защищен: только авторизованные ресурсные серверы (Resource Servers) имеют право опрашивать статус токенов. Для этого ресурсный сервер аутентифицируется на эндпоинте интроспекции с помощью собственных учетных данных (`client_id` и `client_secret` ресурсного сервера через HTTP Basic Auth), предотвращая несанкционированный перебор токенов злоумышленниками.

## Подводные камни

1. **Отсутствие кэширования на ресурсном сервере:** Если ресурсный сервер будет вызывать `/oauth/introspect` на каждый входящий HTTP-запрос пользователя, Сервер Авторизации захлебнется от нагрузки. Ресурсный сервер должен кэшировать результат в локальном памяти/Redis на 10–30 секунд.
2. **Возврат ошибки 404 для неактивного токена:** Спецификация строго требует возвращать HTTP 200 OK с телом `{"active": false}`. Возврат других кодов нарушает протокол.
3. **Утечка PII в ответе интроспекции:** Возвращайте только те claims, которые необходимы ресурсному серверу для принятия решения об авторизации.

## На собеседовании

**Вопрос с собеседования:** Как решить дилемму между преимуществами Opaque токенов (мгновенный отзыв через интроспекцию) и JWT (высокая производительность без сетевых вызовов) в масштабах BigTech (миллионы RPS)?
**Ответ:** Используется гибридный архитектурный паттерн **Phantom Token Pattern (Призрачные токены)**:
1) **Внешний контур (Интернет):** Мобильные приложения и SPA получают строго **Opaque Token** (случайная строка). Токен непрозрачен для клиента, его невозможно разобрать при XSS, и он легко отзывается.
2) **Периметр сети (API Gateway / Envoy):** При входе запроса в периметр шлюз один раз обращается к распределенному Redis кэшу интроспекции.
3) **Внутренний контур (Сервисная сеть K8s):** Шлюз заменяет Opaque токен на короткоживущий подписанный **JWT/PASETO токен** (TTL 2–5 минут) и пересылает его во внутренние микросервисы.
Микросервисы валидируют JWT локально с нулевым сетевым оверхедом, а внешний клиент изолирован от внутренней структуры данных!
