# JWKS (JSON Web Key Set, RFC 7517): Кэширование и Key Rotation

## Условие

Получайте public keys провайдера через JWKS endpoint. Кэшируйте их, обновляйте по расписанию и по kid miss.

### Исходная формулировка

**JWKS (JSON Web Key Set)**: Получайте public keys провайдера через JWKS endpoint. Кэшируйте их, обновляйте по расписанию и по kid miss.

## Теория

Стандарт **JWKS (JSON Web Key Set, RFC 7517)** представляет собой коллекцию криптографических публичных ключей, опубликованных сервером авторизации по эндпоинту `/.well-known/jwks.json`.

### Проблема производительности и доступности:
Если валидирующий микросервис будет делать сетевой HTTP-запрос к `jwks.json` на каждый входящий запрос пользователя, возникнут критические проблемы:
1. Катастрофический рост Latency (десятки миллисекунд сетевого RTT).
2. Зависимость от доступности IdP: если сервер авторизации перезагружается, все микросервисы перестают принимать трафик.
3. Исчерпание сетевых сокетов и лимитов вызовов.

### Архитектура промышленного JWKS менеджера:
1. **In-Memory Caching:** Ключи хранятся в потокобезопасной хэш-таблице `map[kid]*PublicKey` с регулярным фоновым обновлением (Background Refresh) каждые 1–12 часов.
2. **On-Demand Refresh по «kid miss»:** Если в токен зашит новый `kid`, отсутствующий в локальном кэше (сервер авторизации начал ротацию ключей), менеджер немедленно запрашивает свежий JWKS.
3. **Защита от DoS (Throttling / Cooldown):** Чтобы злоумышленник не мог организовать DoS атаку на IdP, отправляя токены с поддельными случайными `kid`, повторные внеплановые запросы разрешаются с задержкой (Cooldown, например, не чаще 1 раза в 10 секунд).

## Решение по шагам

1. Создайте структуры для десериализации набора ключей JWKS (RFC 7517).
2. Реализуйте структуру `JWKSManager` с кэшем в оперативной памяти и защитой от гонок данных.
3. Реализуйте метод `GetKey(kid string)`, выполняющий поиск в кэше и принудительное обновление при промахе (`kid miss`).
4. Добавьте Cooldown-лимитер для предотвращения флуда эндпоинта провайдера.
5. Продемонстрируйте корректную работу: штатный поиск из кэша, обнаружение нового ключа и защиту от флуда несуществующими kid.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type JWKItem struct {
	Kid string `json:"kid"`
	Kty string `json:"kty"`
	Alg string `json:"alg"`
	Use string `json:"use"`
	N   string `json:"n"`
	E   string `json:"e"`
}

type JWKSResponse struct {
	Keys []JWKItem `json:"keys"`
}

// JWKSManager — потокобезопасный кэш публичных ключей
type JWKSManager struct {
	mu           sync.RWMutex
	jwksURL      string
	keys         map[string]JWKItem
	lastFetched  time.Time
	cooldown     time.Duration
	fetchCount   int
}

func NewJWKSManager(url string, cooldown time.Duration) *JWKSManager {
	return &JWKSManager{
		jwksURL:  url,
		keys:     make(map[string]JWKItem),
		cooldown: cooldown,
	}
}

// FetchKeys обновляет кэш ключей с сервера
func (m *JWKSManager) FetchKeys() error {
	m.mu.Lock()
	defer m.mu.Unlock()

	// Защита от спама запросами (Cooldown)
	if time.Since(m.lastFetched) < m.cooldown && len(m.keys) > 0 {
		return errors.New("rate-limit: cooldown еще активен, повторный запрос заблокирован")
	}

	resp, err := http.Get(m.jwksURL)
	if err != nil {
		return err
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return fmt.Errorf("bad status: %d", resp.StatusCode)
	}

	var jwks JWKSResponse
	if err := json.NewDecoder(resp.Body).Decode(&jwks); err != nil {
		return err
	}

	newKeys := make(map[string]JWKItem)
	for _, k := range jwks.Keys {
		newKeys[k.Kid] = k
	}

	m.keys = newKeys
	m.lastFetched = time.Now()
	m.fetchCount++
	return nil
}

// GetKey возвращает ключ по kid, обновляя кэш при промахе (kid miss)
func (m *JWKSManager) GetKey(kid string) (*JWKItem, error) {
	// 1. Fast Path: Чтение из кэша памяти под RLock
	m.mu.RLock()
	key, exists := m.keys[kid]
	m.mu.RUnlock()

	if exists {
		return &key, nil
	}

	// 2. Slow Path: Kid Miss! Пробуем обновить кэш
	fmt.Printf(">>> [Kid Miss]: Ключ %q не найден в кэше. Запрашиваем JWKS...\n", kid)
	if err := m.FetchKeys(); err != nil {
		return nil, fmt.Errorf("ошибка обновления ключей: %w", err)
	}

	// 3. Повторный поиск после обновления
	m.mu.RLock()
	defer m.mu.RUnlock()
	key, exists = m.keys[kid]
	if !exists {
		return nil, fmt.Errorf("ключ с kid=%q отсутствует в обновленном JWKS", kid)
	}

	return &key, nil
}

func main() {
	// Сервер с динамическим списком ключей
	currentKeys := []JWKItem{
		{Kid: "key_v1", Kty: "RSA", Alg: "RS256", Use: "sig"},
	}
	var serverMu sync.Mutex

	mockJWKS := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		serverMu.Lock()
		defer serverMu.Unlock()
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(JWKSResponse{Keys: currentKeys})
	}))
	defer mockJWKS.Close()

	mgr := NewJWKSManager(mockJWKS.URL, 500*time.Millisecond)

	// 1. Первичное получение key_v1
	k1, err := mgr.GetKey("key_v1")
	if err != nil {
		panic(err)
	}
	fmt.Printf("=== 1. Получен ключ из JWKS ===\nKid: %s, Alg: %s\n\n", k1.Kid, k1.Alg)

	// 2. Повторный вызов: чтение из оперативной памяти без сетевого вызова
	k1Cached, _ := mgr.GetKey("key_v1")
	fmt.Printf("=== 2. Повторное чтение ===\nKid: %s, Сетевых запросов выполнено: %d\n\n",
		k1Cached.Kid, mgr.fetchCount)

	// 3. Сервер авторизации провел ротацию и добавил новый ключ key_v2
	serverMu.Lock()
	currentKeys = append(currentKeys, JWKItem{Kid: "key_v2", Kty: "RSA", Alg: "RS256", Use: "sig"})
	serverMu.Unlock()

	// Ждем окончания кулдауна
	time.Sleep(600 * time.Millisecond)

	// 4. Поступает токен с новым kid: срабатывает On-Demand Refresh
	k2, err := mgr.GetKey("key_v2")
	if err != nil {
		panic(err)
	}
	fmt.Printf("=== 3. Успешный On-Demand Refresh ===\nНайден новый ротированный ключ: %s\n\n", k2.Kid)

	// 5. Атака спама фейковыми kid: блокируется кулдауном
	_, errFake := mgr.GetKey("fake_attacker_kid_999")
	fmt.Printf("=== 4. Попытка запроса несуществующего ключа ===\nОшибка: %v\n", errFake)
}
```

## Под капотом

В библиотеках промышленного уровня (например, `github.com/MicahParks/keyfunc`) фоновое обновление реализуется через паттерн Singleflight (`golang.org/x/sync/singleflight`). Если при одновременном наплыве 10 000 параллельных горутин поступит токен с новым `kid`, только одна горутина отправит HTTP-запрос к эндпоинту JWKS, а остальные 9 999 подождут ее завершения, что исключает эффект Thundering Herd.

## Подводные камни

1. **Отсутствие ограничения частоты запросов (Rate Limit):** Если сервер авторизации отвечает с задержкой, спам несуществующими `kid` подвесит все воркеры микросервиса.
2. **Блокировка всего сервиса при падении IdP:** Если сетевой запрос завершается ошибкой, менеджер обязан сохранять старые ключи в кэше, чтобы валидировать токены, подписанные до сбоя.
3. **Парсинг без проверки `use: "sig"`:** В JWKS могут публиковаться ключи для шифрования (`use: "enc"`). Использование ключа шифрования для проверки подписи недопустимо.

## На собеседовании

**Вопрос с собеседования:** Как предотвратить атаку DoS на микросервис, когда атакующий отправляет миллионы запросов с токенами, содержащими случайные UUID в поле `kid`?
**Ответ:** 1) **Circuit Breaker и Rate Limiter на Refresh:** Ограничить количество внеплановых обновлений JWKS жестким лимитом (например, не более 1 раза в 15 секунд).
2) **Отрицательный кэш (Negative Caching):** Запоминать несуществующие `kid` в LRU-кэше с коротким TTL (30 секунд), чтобы не повторять сетевой запрос на один и тот же фейковый `kid`.
3) **Fallback на асинхронный воркер:** Внеплановое обновление инициируется в фоновой горутине, а текущий запрос с неизвестным `kid` сразу отклоняется со статусом 401 Unauthorized.
