# Token Revocation Endpoint (RFC 7009) для мгновенного отзыва

## Условие

Реализуйте revocation endpoint (RFC 7009) для immediate invalidation tokens.

### Исходная формулировка

**Token revocation endpoint**: Реализуйте revocation endpoint (RFC 7009) для immediate invalidation tokens.

## Теория

Спецификация **OAuth 2.0 Token Revocation (RFC 7009)** регламентирует стандартный эндпоинт `/oauth/revoke`, позволяющий клиенту явно отозвать ранее выданный токен (Access Token или Refresh Token) при выходе пользователя из аккаунта (Logout) или удалении приложения.

### Ключевые требования безопасности RFC 7009:
1. **Метод запроса:** Строго HTTP POST с телом `application/x-www-form-urlencoded`.
2. **Параметры:**
   - `token`: значение отзываемого токена.
   - `token_type_hint` (опционально): подсказка серверу (`access_token` или `refresh_token`) для оптимизации поиска в БД.
3. **Правило ответа (Security Requirement):**
   Если токен был успешно отозван ИЛИ если токен не существовал/уже был отозван ранее, сервер **ОБЯЗАН вернуть HTTP 200 OK**!
   **Почему?** Если сервер будет возвращать 404 Not Found на несуществующие токены, злоумышленник сможет использовать эндпоинт отзыва как оракул для сканирования и подбора валидных токенов пользователей (Token Enumeration / Timing Oracle)!
4. **Каскадный отзыв:** При отзыве `refresh_token` сервер обязан автоматически аннулировать все зависимые `access_token`, выданные в рамках данной сессии.

## Решение по шагам

1. Создайте хранилище активных токенов с привязкой access к refresh токену.
2. Реализуйте эндпоинт `/oauth/revoke` по спецификации RFC 7009.
3. Обеспечьте возврат HTTP 200 OK даже для недействительных или несуществующих токенов.
4. Реализуйте каскадное удаление зависимых access токенов при отзыве refresh токена.
5. Продемонстрируйте невозможность дальнейшего использования токена после вызова `/oauth/revoke`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
	"sync"
)

type RevocationServer struct {
	mu           sync.Mutex
	accessTokens map[string]string // accessToken -> sessionID
	refreshMap   map[string]string // refreshToken -> sessionID
}

func NewRevocationServer() *RevocationServer {
	return &RevocationServer{
		accessTokens: make(map[string]string),
		refreshMap:   make(map[string]string),
	}
}

// HandleRevoke реализует спецификацию RFC 7009
func (s *RevocationServer) HandleRevoke(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}

	token := r.FormValue("token")
	hint := r.FormValue("token_type_hint")

	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Поиск и отзыв токена
	var targetSessionID string

	if hint == "refresh_token" {
		targetSessionID = s.refreshMap[token]
		delete(s.refreshMap, token)
	} else if hint == "access_token" {
		targetSessionID = s.accessTokens[token]
		delete(s.accessTokens, token)
	} else {
		// Если подсказка не указана — ищем во всех реестрах
		if sess, ok := s.refreshMap[token]; ok {
			targetSessionID = sess
			delete(s.refreshMap, token)
		} else if sess, ok := s.accessTokens[token]; ok {
			targetSessionID = sess
			delete(s.accessTokens, token)
		}
	}

	// 2. Каскадный отзыв всей сессии при отзыве refresh токена
	if targetSessionID != "" && hint == "refresh_token" {
		for at, sess := range s.accessTokens {
			if sess == targetSessionID {
				delete(s.accessTokens, at)
			}
		}
	}

	// 3. ТРЕБОВАНИЕ RFC 7009: Всегда возвращаем HTTP 200 OK!
	// Сервер не должен раскрывать, существовал ли токен, чтобы исключить enumeration атаки.
	w.WriteHeader(http.StatusOK)
}

func (s *RevocationServer) IsTokenActive(at string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	_, exists := s.accessTokens[at]
	return exists
}

func main() {
	srv := NewRevocationServer()

	// Создаем сессию пользователя
	sessionID := "sess_alice_999"
	at := "at_active_secret_token_111"
	rt := "rt_active_refresh_token_222"

	srv.accessTokens[at] = sessionID
	srv.refreshMap[rt] = sessionID

	mux := http.NewServeMux()
	mux.HandleFunc("/oauth/revoke", srv.HandleRevoke)
	ts := httptest.NewServer(mux)
	defer ts.Close()

	fmt.Println("=== 1. Состояние до отзыва ===")
	fmt.Printf("Access токен активен: %v\n\n", srv.IsTokenActive(at))

	// 2. Клиент нажимает Logout и отзывает refresh_token
	fmt.Println("=== 2. Клиент вызывает /oauth/revoke для Refresh токена ===")
	form := url.Values{
		"token":           {rt},
		"token_type_hint": {"refresh_token"},
	}
	resp1, _ := http.Post(ts.URL+"/oauth/revoke", "application/x-www-form-urlencoded", strings.NewReader(form.Encode()))
	fmt.Printf("HTTP Status отзыва: %d (OK по стандарту RFC 7009)\n", resp1.StatusCode)
	resp1.Body.Close()

	// Проверяем каскадный отзыв
	fmt.Printf("Access токен активен после отзыва Refresh токена: %v (Каскадно удален!)\n\n", srv.IsTokenActive(at))

	// 3. Отзыв несуществующего или уже отозванного токена
	fmt.Println("=== 3. Отзыв несуществующего токена (защита от сканирования) ===")
	formGhost := url.Values{"token": {"non_existent_token_666"}}
	resp2, _ := http.Post(ts.URL+"/oauth/revoke", "application/x-www-form-urlencoded", strings.NewReader(formGhost.Encode()))
	fmt.Printf("HTTP Status для фантомного токена: %d (Сервер не раскрыл статус!)\n", resp2.StatusCode)
	resp2.Body.Close()
}
```

## Под капотом

Почему RFC 7009 требует возврат HTTP 200 даже на мусорные токены?
Если бы сервер возвращал 200 для найденных токенов и 404 для ненайденных, злоумышленник мог бы запустить распределенный брутфорс токенов: отправлять случайные строки в `/oauth/revoke` и по коду ответа понимать, какие токены реально существуют в базе данных жертвы. Ответ 200 OK делает эндпоинт слепым оракулом (Blind Sink).

## Подводные камни

1. **Возврат 404 Not Found:** Прямое нарушение стандарта RFC 7009, создающее уязвимость Token Enumeration.
2. **Разрешение вызова без клиентской авторизации:** Эндпоинт отзыва обязан валидировать `client_id` и `client_secret` вызывающего приложения, гарантируя, что клиент имеет право отзывать именно свои токены.
3. **Отсутствие каскадной очистки:** Отзыв refresh token без аннулирования активного access token оставляет злоумышленнику окно доступа до истечения `exp`.

## На собеседовании

**Вопрос с собеседования:** Если в системе используются Stateless JWT токены (которые не хранятся в БД), как реализовать их немедленный отзыв через эндпоинт /oauth/revoke?
**Ответ:** Для Stateless JWT применяется паттерн **Distributed Blacklist (Распределенный черный список) в Redis**:
1) При вызове `/oauth/revoke` сервер извлекает из JWT уникальный идентификатор `jti` (JWT ID) и оставшееся время жизни \(\Delta t = \text{exp} - \text{now}\).
2) Сервер сохраняет `jti` в Redis команду: `SETEX blacklist:jti:<id> <delta_t> 1`.
3) Запись в Redis живет ровно столько, сколько оставалось жить самому токену, после чего удаляется по TTL автоматически, не переполняя память.
4) Middleware на защищенных API проверяет: `EXISTS blacklist:jti:<id>`. Если ключ есть — доступ блокируется со статусом 401 Unauthorized.
