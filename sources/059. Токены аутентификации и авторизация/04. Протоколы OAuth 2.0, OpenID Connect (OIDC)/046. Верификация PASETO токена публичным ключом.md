# Верификация PASETO токена публичным ключом и извлечение Claims

## Условие

Проверь PASETO токен публичным ключом. Извлеки claims. Объясни, почему PASETO безопаснее JWT (нет гибкости в выборе алгоритма, устраняет уязвимости с `alg`).

## Теория

Процесс валидации токена **PASETO v4.public** гарантирует криптографическую целостность и аутентичность утверждений (Claims) с использованием цифровой подписи **Ed25519 (RFC 8032)**.

### Математическая схема верификации:
1. **Проверка префикса:** Токен обязан начинаться строго со строки `v4.public.`.
2. **Разделение полезной нагрузки и подписи:**
   - После декодирования Base64URL последние 64 байта отделяются как цифровая подпись \(S\) (в Ed25519 подпись имеет строго фиксированную длину 64 байта).
   - Все предшествующие байты являются сериализованной полезной нагрузкой \(M\) (JSON claims).
3. **Канонизация через PAE:**
   Вычисляется канонический байтовый массив:
   $$\text{DataToVerify} = \text{PAE}(\text{"v4.public."}, M, \text{Footer})$$
4. **Криптографическая проверка:**
   Вызывается `ed25519.Verify(publicKey, DataToVerify, S)`.
   Если подпись верна, полезная нагрузка десериализуется в структуру `Claims`, и проверяются бизнес-ограничения (срок годности `exp`, допустимый эмитент `iss` и т.д.).

### Почему PASETO безопаснее JWT:
- **Zero Alg Agility:** В токене нет поля `alg`. Вызывающая сторона строго знает: для проверки `v4.public` нужен `ed25519.PublicKey` и ничего другого.
- **Иммунитет к парсинг-багам:** В JWT заголовок парсится **до** проверки подписи, что открывает путь к DoS и инъекциям в JSON-парсер. В PASETO подпись проверяется над сырыми байтами до парсинга JSON!

## Решение по шагам

1. Создайте структуру строго типизированных утверждений `AppClaims`.
2. Реализуйте функцию верификации `VerifyAndParseV4Public`.
3. Реализуйте проверку стандартных полей `exp` (срок жизни) и `nbf` (not before).
4. Продемонстрируйте корректный парсинг валидного токена и извлечение кастомных полей.
5. Продемонстрируйте отказ при повреждении подписи или полезной нагрузки.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/ed25519"
	"crypto/rand"
	"encoding/base64"
	"encoding/binary"
	"encoding/json"
	"errors"
	"fmt"
	"strings"
	"time"
)

// PAE (Pre-Authentication Encoding)
func pae(pieces ...[]byte) []byte {
	buf := make([]byte, 8)
	binary.LittleEndian.PutUint64(buf, uint64(len(pieces)))
	out := append([]byte{}, buf...)
	for _, p := range pieces {
		lenBuf := make([]byte, 8)
		binary.LittleEndian.PutUint64(lenBuf, uint64(len(p)))
		out = append(out, lenBuf...)
		out = append(out, p...)
	}
	return out
}

type AppClaims struct {
	Issuer      string   `json:"iss"`
	Subject     string   `json:"sub"`
	Audience    string   `json:"aud"`
	Expiration  int64    `json:"exp"`
	Permissions []string `json:"permissions"`
	TenantID    string   `json:"tenant_id"`
}

// VerifyAndParseV4Public верифицирует токен и возвращает claims
func VerifyAndParseV4Public(token string, pubKey ed25519.PublicKey) (*AppClaims, error) {
	const header = "v4.public."
	if !strings.HasPrefix(token, header) {
		return nil, errors.New("неверный формат токена: отсутствует префикс v4.public.")
	}

	payloadRaw, err := base64.RawURLEncoding.DecodeString(strings.TrimPrefix(token, header))
	if err != nil {
		return nil, fmt.Errorf("base64 decode error: %w", err)
	}

	if len(payloadRaw) < ed25519.SignatureSize {
		return nil, errors.New("длина токена меньше размера подписи Ed25519")
	}

	// Отсекаем последние 64 байта подписи
	payloadLen := len(payloadRaw) - ed25519.SignatureSize
	payload := payloadRaw[:payloadLen]
	signature := payloadRaw[payloadLen:]

	// Верифицируем Ed25519 подпись над PAE(header, payload, footer)
	expectedPae := pae([]byte(header), payload, []byte(""))
	if !ed25519.Verify(pubKey, expectedPae, signature) {
		return nil, errors.New("криптографическая подпись Ed25519 невалидна!")
	}

	// Только ПОСЛЕ успешной крипто-проверки парсим JSON
	var claims AppClaims
	if err := json.Unmarshal(payload, &claims); err != nil {
		return nil, fmt.Errorf("json unmarshal error: %w", err)
	}

	// Проверка срока жизни токена
	if time.Now().Unix() > claims.Expiration {
		return nil, errors.New("срок действия токена истек (token expired)")
	}

	return &claims, nil
}

// IssueTokenHelper вспомогательная функция генерации токена
func IssueTokenHelper(claims AppClaims, privKey ed25519.PrivateKey) string {
	header := "v4.public."
	b, _ := json.Marshal(claims)
	m := pae([]byte(header), b, []byte(""))
	sig := ed25519.Sign(privKey, m)
	combined := append(b, sig...)
	return header + base64.RawURLEncoding.EncodeToString(combined)
}

func main() {
	pubKey, privKey, _ := ed25519.GenerateKey(rand.Reader)

	legitClaims := AppClaims{
		Issuer:      "https://id.cloud.corp",
		Subject:     "usr_lead_developer",
		Audience:    "microservice_inventory",
		Expiration:  time.Now().Add(15 * time.Minute).Unix(),
		Permissions: []string{"repo:read", "repo:push"},
		TenantID:    "tenant_fintech_01",
	}

	token := IssueTokenHelper(legitClaims, privKey)
	fmt.Printf("=== 1. Выпущенный PASETO токен ===\n%s\n\n", token)

	// 2. Успешная валидация
	claims, err := VerifyAndParseV4Public(token, pubKey)
	if err != nil {
		panic(err)
	}
	fmt.Println("=== 2. Извлеченные и проверенные Claims ===")
	fmt.Printf("Subject:     %s\n", claims.Subject)
	fmt.Printf("Tenant ID:   %s\n", claims.TenantID)
	fmt.Printf("Permissions: %v\n", claims.Permissions)
	fmt.Printf("Expires In:  %d сек\n\n", claims.Expiration-time.Now().Unix())

	// 3. Попытка валидации просроченного токена
	expiredClaims := legitClaims
	expiredClaims.Expiration = time.Now().Add(-1 * time.Hour).Unix()
	expiredToken := IssueTokenHelper(expiredClaims, privKey)
	_, errExp := VerifyAndParseV4Public(expiredToken, pubKey)
	fmt.Printf("=== 3. Проверка просроченного токена ===\nРезультат: %v\n", errExp)
}
```

## Под капотом

Золотое правило безопасной криптографии: **Cryptographic Verification Before Data Parsing**. В уязвимых реализациях JWT библиотека сначала десериализует JSON заголовка, чтобы понять, какой алгоритм использовать, и только потом проверяет подпись. Это делает парсер уязвимым к эксплойтам переполнения памяти, quadratic parsing DoS и инъекциям. В PASETO схема проверки строго фиксирована, и полезная нагрузка превращается в объект структуры Go только после того, как `ed25519.Verify` вернул истину.

## Подводные камни

1. **Проверка времени без учета задержек (Clock Skew):** Серверы в кластере могут иметь небольшую рассинхронизацию по NTP. Полезно добавлять допустимое окно leeway (1–2 минуты) для проверки `exp`.
2. **Игнорирование проверки Audience:** Если микросервис принимает токен без проверки поля `aud`, токен, выданный для безобидного сервиса аналитики, может быть использован для авторизации в сервисе биллинга!
3. **Хранение изменяемого состояния:** Не помещайте в токен баланс счета или статус бана, так как токен нельзя изменить после выпуска. Токен должен содержать только неизменяемые факты идентификации.

## На собеседовании

**Вопрос с собеседования:** В распределенной системе из 50 микросервисов используется PASETO v4.public. Как организовать обновление публичных ключей Ed25519 без остановки сервисов (Zero Downtime Key Rotation)?
**Ответ:** 1) **Key ID (kid) в Footer:** В PASETO незашифрованный footer используется для передачи идентификатора ключа: `v4.public.<payload>.<footer_with_kid>`. 2) **Пул доверенных ключей (Key Ring):** Микросервисы загружают из защищенного репозитория или KV-хранилища (Consul/etcd) набор активных публичных ключей: `map[string]ed25519.PublicKey`. 3) **Двухфазная ротация:** При выпуске нового ключа \(K_2\) он сначала добавляется во все микросервисы. Сервер авторизации продолжает подписывать токен ключом \(K_1\). Спустя сутки, когда все поды обновили конфигурацию, эмитент переключается на подпись \(K_2\). Еще через сутки старый ключ \(K_1\) выводится из эксплуатации.
