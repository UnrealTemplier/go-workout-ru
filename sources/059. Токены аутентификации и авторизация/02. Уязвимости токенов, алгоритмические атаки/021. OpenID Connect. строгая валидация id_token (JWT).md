# OpenID Connect: строгая валидация id_token (JWT)

## Условие

Реализуйте проверку JWT id_token от Google/Auth0: валидация iss, aud, exp, nonce. Извлеките claims (sub, email, email_verified). Объясните, чем id_token отличается от access_token.

### Исходная формулировка

**OIDC: проверка id_token.**: Реализуйте проверку JWT `id_token` от Google/Auth0: валидация `iss`, `aud`, `exp`, `nonce`. Извлеките claims (`sub`, `email`, `email_verified`). Объясните, чем `id_token` отличается от `access_token`.

## Теория

В протоколе **OpenID Connect (OIDC Core 1.0)** токен идентификации (**`id_token`**) представляет собой цифровой паспорт пользователя, подписанный провайдером идентификации (IdP — Google, Keycloak, Яндекс ID).

### Обязательные проверки безопасности `id_token` (RFC 7519 / OIDC Core):
1. **`iss` (Issuer Identifier):** Обязан в точности совпадать с каноническим URL провайдера (например, `https://accounts.google.com`). Защищает от подмены поставщика.
2. **`aud` (Audience):** Обязан содержать `client_id` нашего зарегистрированного веб-приложения. Если токен был выпущен для мобильного приложения или чужого сервиса, наш сервер обязан его отклонить!
3. **`exp` (Expiration Time):** Текущее системное время сервера обязано быть строго меньше `exp` (с учетом небольшого допустимого сдвига часов clock skew \(\le 1\) мин).
4. **`nonce`:** Случайная одноразовая строка, переданная клиентом при первичном запросе авторизации. Защищает от атак повторного воспроизведения (Replay Attacks).

### Различие `id_token` и `access_token`:
- **`id_token`:** Предназначен **исключительно для клиентского приложения**. Содержит информацию о том, **КТО** авторизовался (`sub`, `email`, `name`).
- **`access_token`:** Предназначен **для ресурсного API сервера**. Служит пропуском и сообщает, **ЧТО** клиент имеет право делать (`scopes: read:photos`). Клиент не должен декодировать access_token.

## Решение по шагам

1. Создадим структуру стандартных claims OIDC: `OIDCIDTokenClaims` с `iss`, `aud`, `exp`, `sub`, `email`, `nonce`.
2. Реализуем функцию `ValidateIDToken(rawToken, expectedIssuer, expectedClientID, expectedNonce)`.
3. Проверим выполнение всех 4 обязательных критериев OIDC.
4. Продемонстрируем успешный разбор профиля пользователя.
5. Покажем сценарии атак: подмена audience и атака повтора с неверным `nonce`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"crypto/subtle"
	"errors"
	"fmt"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

type OIDCIDTokenClaims struct {
	Issuer        string `json:"iss"`
	Audience      string `json:"aud"`
	Subject       string `json:"sub"`
	Email         string `json:"email"`
	EmailVerified bool   `json:"email_verified"`
	Nonce         string `json:"nonce"`
	jwt.RegisteredClaims
}

// ValidateIDToken производит строгую валидацию id_token по спецификации OIDC Core 1.0
func ValidateIDToken(tokenStr string, pubKey *rsa.PublicKey, expectedIssuer, expectedClientID, expectedNonce string) (*OIDCIDTokenClaims, error) {
	var claims OIDCIDTokenClaims

	token, err := jwt.ParseWithClaims(tokenStr, &claims, func(t *jwt.Token) (any, error) {
		if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {
			return nil, fmt.Errorf("unexpected alg: %v", t.Header["alg"])
		}
		return pubKey, nil
	}, jwt.WithValidMethods([]string{"RS256"}))

	if err != nil {
		return nil, fmt.Errorf("jwt verification error: %w", err)
	}

	if !token.Valid {
		return nil, errors.New("token signature is invalid")
	}

	// 1. Валидация Issuer (iss)
	if claims.Issuer != expectedIssuer {
		return nil, fmt.Errorf("issuer mismatch: expected %s, got %s", expectedIssuer, claims.Issuer)
	}

	// 2. Валидация Audience (aud) - критично против подделок токена чужих приложений!
	if claims.Audience != expectedClientID {
		return nil, fmt.Errorf("audience mismatch: expected %s, got %s", expectedClientID, claims.Audience)
	}

	// 3. Валидация Expiration (exp)
	if time.Now().After(claims.ExpiresAt.Time) {
		return nil, fmt.Errorf("id_token expired at %s", claims.ExpiresAt.Time)
	}

	// 4. Валидация Nonce (защита от атак повторного воспроизведения)
	if subtle.ConstantTimeCompare([]byte(claims.Nonce), []byte(expectedNonce)) != 1 {
		return nil, fmt.Errorf("nonce mismatch: replay attack detected")
	}

	return &claims, nil
}

func main() {
	rsaKey, _ := rsa.GenerateKey(rand.Reader, 2048)

	expectedIssuer := "https://accounts.google.com"
	expectedClientID := "my-app-client-id-54321.apps.googleusercontent.com"
	sessionNonce := "secure_random_nonce_9981"

	// 1. Выпуск легитимного ID Token от Google
	validClaims := OIDCIDTokenClaims{
		Issuer:        expectedIssuer,
		Audience:      expectedClientID,
		Subject:       "google_user_sub_10928374",
		Email:         "lead.security@company.com",
		EmailVerified: true,
		Nonce:         sessionNonce,
		RegisteredClaims: jwt.RegisteredClaims{
			ExpiresAt: jwt.NewNumericDate(time.Now().Add(1 * time.Hour)),
			IssuedAt:  jwt.NewNumericDate(time.Now()),
		},
	}

	tokenObj := jwt.NewWithClaims(jwt.SigningMethodRS256, validClaims)
	tokenStr, _ := tokenObj.SignedString(rsaKey)

	fmt.Println("=== 1. Успешная валидация легитимного OIDC id_token ===")
	profile, err := ValidateIDToken(tokenStr, &rsaKey.PublicKey, expectedIssuer, expectedClientID, sessionNonce)
	if err != nil {
		panic(err)
	}

	fmt.Printf("✅ Идентификация пройдена успешно!\n")
	fmt.Printf("- Sub (уникальный ID): %s\n", profile.Subject)
	fmt.Printf("- Email пользователя:  %s (Подтвержден: %t)\n\n", profile.Email, profile.EmailVerified)

	// 2. Симуляция атаки Replay (подмена или повторное использование чужого nonce)
	fmt.Println("=== 2. Симуляция Replay Attack (неверный nonce) ===")
	_, replayErr := ValidateIDToken(tokenStr, &rsaKey.PublicKey, expectedIssuer, expectedClientID, "different_stolen_nonce")
	fmt.Printf("Результат проверки nonce:\n❌ %v\n", replayErr)
}
```

## Под капотом

Параметр `nonce` генерируется клиентом при формировании URL авторизации `AuthCodeURL` и сохраняется в защищенную HTTP-only Cookie сессии. 
Когда IdP возвращает пользователя с кодом авторизации, клиент обменивает код и сверяет `nonce` из расшифрованного `id_token` со значением из Cookie. Если злоумышленник перехватит старый `id_token`, он не сможет воспроизвести атаку, так как в текущей сессии сгенерирован новый случайный `nonce`.

## Подводные камни

1. **Идентификация пользователя по полю `email` вместо `sub`:** Внешний пользователь может изменить свой email у провайдера, а старый email может быть повторно зарегистрирован другим лицом. В качестве неизменяемого внешнего ID всегда используйте `sub` (Subject).
2. **Пропуск валидации `email_verified`:** Если `email_verified == false`, почта не проверена, и злоумышленник может завладеть аккаунтом жертвы.
3. **Отсутствие проверки `aud`:** Пропуск проверки `aud` позволяет авторизоваться токеном, выданным совершенно другому сайту.

## На собеседовании

**Вопрос с собеседования в Яндекс/Ozon:** «В чем принципиальное функциональное отличие id_token от access_token в спецификации OpenID Connect, и почему опасно передавать access_token вместо id_token на фронтенд для аутентификации?»
**Ответ:** 
- **`id_token`** предназначен строго для клиента (клиентского приложения). Он является структурированным криптографическим паспортом (JWT), содержащим поле `aud` (равное client_id приложения) и подтверждающим факт успешной проверки личности пользователя провайдером.
- **`access_token`** предназначен для ресурсных API серверов (например, Google Drive API или внутренний Orders API) для авторизации прав доступа к ресурсам.
Опасность: `access_token` не содержит информации о том, для какого клиента он был выпущен. Если вредоносное приложение получит `access_token` пользователя от того же провайдера, оно сможет отправить этот токен вашему бэкенду, и без проверки `aud` сервер сочтет пользователя авторизованным, что приведет к компрометации аккаунта (Confused Deputy Problem).
