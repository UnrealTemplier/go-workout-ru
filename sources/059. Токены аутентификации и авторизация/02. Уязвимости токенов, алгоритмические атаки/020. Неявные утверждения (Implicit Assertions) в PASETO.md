# Неявные утверждения (Implicit Assertions) в PASETO

## Условие

Добавьте в токен данные, которые аутентифицируются, но не включаются в payload (например, IP-адрес, user agent).

### Исходная формулировка

**PASETO implicit assertions**: Добавьте в токен данные, которые аутентифицируются, но не включаются в payload (например, IP-адрес, user agent).

## Теория

Одной из уникальных инноваций спецификации **PASETO v3 / v4** является механизм **неявных утверждений (Implicit Assertions)**.

В традиционном JWT, если вы хотите привязать токен к клиенту:
- Вам приходится явно сохранять IP-адрес и User-Agent **внутрь payload токена**.
- Это раздувает размер токена на сотни байт и раскрывает IP-адрес пользователя всем участникам цепочки.

### Принцип работы Implicit Assertions:
1. Данные окружения (IP-адрес клиента, User-Agent, Tenant ID) **НЕ включаются в сам токен** и **НЕ передаются клиенту**.
2. Однако они передаются в криптографический аутентификатор (AEAD AAD) в момент создания токена!
3. При каждом обращении сервер восстанавливает контекст текущего HTTP-запроса (читает реальный `r.RemoteAddr` и `r.UserAgent()`) и передает их в качестве Implicit Assertion в функцию проверки.
4. **Защита от кражи сессии:** Если злоумышленник перехватит токен и попытается отправить его со своего IP-адреса или другого браузера, проверка подлинности Poly1305 немедленно завершится фатальным сбоем, хотя злоумышленник даже не поймет, почему токен не работает!

## Решение по шагам

1. Создадим структуру контекста клиента: `ClientContext` с полями `IP` и `UserAgent`.
2. Реализуем генерацию токена с передачей контекста клиента в качестве неявного утверждения.
3. Проверим токен при совпадении контекста (тот же IP и браузер).
4. Смоделируем атаку: злоумышленник отправляет украденный токен с другого IP-адреса.
5. Убедимся, что проверка токена проваливается из-за несовпадения криптографического контекста.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"io"
	"time"

	"golang.org/x/crypto/chacha20poly1305"
)

// IssueTokenWithAssertion шифрует токен, криптографически связывая его с контекстом клиента
func IssueTokenWithAssertion(key, payload []byte, clientIP, userAgent string) ([]byte, error) {
	aead, err := chacha20poly1305.NewX(key)
	if err != nil {
		return nil, err
	}

	nonce := make([]byte, chacha20poly1305.NonceSizeX)
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, err
	}

	// Implicit Assertion: IP и User-Agent криптографически замешиваются в AAD,
	// но НЕ попадают в тело токена!
	implicitAssertion := fmt.Sprintf("v4.local.assert:ip=%s;ua=%s", clientIP, userAgent)

	ciphertext := aead.Seal(nonce, nonce, payload, []byte(implicitAssertion))
	return ciphertext, nil
}

// VerifyTokenWithAssertion проверяет токен против текущего контекста запроса
func VerifyTokenWithAssertion(key, token []byte, currentIP, currentUserAgent string) ([]byte, error) {
	aead, err := chacha20poly1305.NewX(key)
	if err != nil {
		return nil, err
	}

	if len(token) < chacha20poly1305.NonceSizeX {
		return nil, fmt.Errorf("token too short")
	}

	nonce := token[:chacha20poly1305.NonceSizeX]
	ciphertext := token[chacha20poly1305.NonceSizeX:]

	// Формируем ожидаемое неявное утверждение из текущего HTTP-запроса
	expectedAssertion := fmt.Sprintf("v4.local.assert:ip=%s;ua=%s", currentIP, currentUserAgent)

	plaintext, err := aead.Open(nil, nonce, ciphertext, []byte(expectedAssertion))
	if err != nil {
		return nil, fmt.Errorf("сессия недействительна для данного клиента (IP или User-Agent не совпали!)")
	}

	return plaintext, nil
}

func main() {
	key := make([]byte, 32)
	_, _ = rand.Read(key)

	sessionPayload := []byte(`{"user_id":"alice_chief_officer","role":"vip"}`)

	legitIP := "198.51.100.42"
	legitUA := "Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36"

	// 1. Легитимная выдача токена
	token, err := IssueTokenWithAssertion(key, sessionPayload, legitIP, legitUA)
	if err != nil {
		panic(err)
	}

	fmt.Println("=== 1. Выдача токена с Implicit Assertion (Привязка к IP/UA) ===")
	fmt.Printf("Токен успешно выдан (размер: %d байт)\n", len(token))
	fmt.Printf("Привязан к IP: '%s'\n\n", legitIP)

	// 2. Легитимный запрос от того же пользователя
	fmt.Println("=== 2. Проверка токена от легитимного клиента ===")
	data, err := VerifyTokenWithAssertion(key, token, legitIP, legitUA)
	if err != nil {
		panic(err)
	}
	fmt.Printf("✅ Успешная аутентификация! Полезная нагрузка:\n%s\n\n", string(data))

	// 3. Атака: перехват токена злоумышленником с другим IP-адресом
	attackerIP := "203.0.113.99"
	attackerUA := "Python-requests/2.31.0"

	fmt.Println("=== 3. Попытка использования украденного токена с чужого IP ===")
	_, attackErr := VerifyTokenWithAssertion(key, token, attackerIP, attackerUA)
	fmt.Printf("Результат проверки токена атакующего:\n❌ %v\n", attackErr)
}
```

## Под капотом

Механизм AAD в схеме AEAD позволяет аутентифицировать произвольные байты, не включая их в результат шифрования. 
Poly1305 вычисляет полиномиальный хэш по модулю \(2^{130}-5\) от структуры `len(AAD) || AAD || len(Ciphertext) || Ciphertext`. 
Если хотя бы один байт в строке `ip=...;ua=...` отличается на стороне проверяющего, итоговый тег аутентификации Poly1305 не сойдется, и метод `Open` вернет ошибку до попытки дешифрования.

## Подводные камни

1. **Динамические мобильные IP-адреса:** У пользователей сотовой связи (LTE/5G) IP-адрес может меняться каждые несколько минут при переключении базовых станций. Привязка строгого IP может приводить к ложным разлогинам. Рекомендуется привязывать подсеть `/24` или ASN/Device Fingerprint.
2. **Прокси и заголовок X-Forwarded-For:** При использовании `r.Header.Get("X-Forwarded-For")` злоумышленник может подделать заголовок. Читайте IP только от доверенного реверс-прокси.
3. **Несогласованный формат строки утверждения:** Строка утверждения на стороне выпуска и стороне проверки обязана побайтово совпадать.

## На собеседовании

**Вопрос с собеседования в Касперский/Ozon:** «Что такое неявные утверждения (Implicit Assertions) в современных токенах и какую проблему они решают лучше, чем claims в JWT?»
**Ответ:** Неявные утверждения — это данные контекста безопасности (IP-адрес клиента, User-Agent, ID арендатора, отпечаток TLS-сертификата), которые передаются в алгоритм AEAD как дополнительные аутентифицированные данные (AAD), но **не включаются в тело токена**. 
Преимущества перед claims JWT:
1. **Компактность:** Размер токена не увеличивается, экономя сетевой трафик.
2. **Приватность:** Данные не видны клиенту и не передаются по сети.
3. **Защита от Replay/Session Hijacking:** Если токен украден, злоумышленник не сможет применить его со своего устройства или IP, так как криптографическая проверка на сервере опирается на контекст входящего сетевого соединения.
