# OAuth2 Authorization Code Flow с защитой через PKCE

## Условие

Реализуйте клиентское веб-приложение: endpoint `/auth` (редирект на IdP), `/callback` (обмен code на token). Добавьте PKCE (`code_verifier`/`code_challenge`). Объясните, зачем PKCE при отсутствии client_secret.

### Исходная формулировка

**OAuth2 Authorization Code + PKCE.**: Реализуйте клиентское веб-приложение: endpoint `/auth` (редирект на IdP), `/callback` (обмен code на token). Добавьте PKCE (`code_verifier`/`code_challenge`). Объясните, зачем PKCE при отсутствии client secret (SPA, мобильные приложения).

## Теория

В мобильных приложениях (iOS/Android) и браузерных Single Page Applications (SPA на React/Vue) **невозможно безопасно скрыть `client_secret`**: любой пользователь может декомпилировать APK-файл или открыть вкладку Source в браузере и извлечь секрет.

Без секрета классический Authorization Code Flow уязвим к **перехвату кода авторизации (Authorization Code Interception Attack)**: вредоносное приложение регистрирует на устройстве ту же Custom URL Scheme (`myapp://oauth/callback`) и перехватывает код авторизации из редиректа браузера.

### Решение: PKCE (Proof Key for Code Exchange / RFC 7636)
PKCE заменяет статический `client_secret` динамическим одноразовым криптографическим секретом:
1. **Генерация Verifier:** Клиент генерирует случайную строку `code_verifier` (от 43 до 128 символов криптографической энтропии).
2. **Вычисление Challenge:** Клиент вычисляет SHA-256 хэш:
   $$\text{code\_challenge} = \text{Base64URL}(\text{SHA-256}(\text{code\_verifier}))$$
3. **Запрос авторизации (`/auth`):** Клиент отправляет `code_challenge` и `code_challenge_method=S256` на сервер IdP. Сам `code_verifier` остается на клиенте!
4. **Обмен токена (`/callback`):** Клиент отправляет полученный `code` вместе с открытым `code_verifier`.
5. **Проверка на сервере:** IdP вычисляет SHA-256 от `code_verifier` и сверяет его с ранее полученным `code_challenge`. Если перехватчик украл `code`, он не знает `code_verifier` и не сможет получить токен!

## Решение по шагам

1. Создадим генератор `code_verifier` и функцию расчета `code_challenge` (S256).
2. Реализуем эндпоинт `/auth`: генерация PKCE пары, сохранение `verifier` в сессии, формирование ссылки редиректа.
3. Реализуем эндпоинт `/callback`: извлечение кода, отправка запроса обмена с `code_verifier`.
4. Смоделируем сервер провайдера авторизации (IdP) с валидацией PKCE.
5. Продемонстрируем, как попытка обменять код без правильного verifier завершается отказом.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/base64"
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
)

// GeneratePKCE создает пару code_verifier и code_challenge (RFC 7636)
func GeneratePKCE() (verifier, challenge string, err error) {
	b := make([]byte, 32)
	if _, err = rand.Read(b); err != nil {
		return "", "", err
	}
	verifier = base64.RawURLEncoding.EncodeToString(b)

	h := sha256.Sum256([]byte(verifier))
	challenge = base64.RawURLEncoding.EncodeToString(h[:])
	return verifier, challenge, nil
}

type MockOAuthProvider struct {
	issuedCodes map[string]string // code -> code_challenge
}

func (p *MockOAuthProvider) IssueCode(challenge string) string {
	code := "auth_code_xyz987"
	p.issuedCodes[code] = challenge
	return code
}

func (p *MockOAuthProvider) ExchangeToken(code, verifier string) (string, error) {
	expectedChallenge, exists := p.issuedCodes[code]
	if !exists {
		return "", fmt.Errorf("invalid code")
	}

	// Вычисляем SHA-256 от предъявленного verifier
	h := sha256.Sum256([]byte(verifier))
	computedChallenge := base64.RawURLEncoding.EncodeToString(h[:])

	// Сверяем с сохраненным при инициализации challenge
	if subtle.ConstantTimeCompare([]byte(expectedChallenge), []byte(computedChallenge)) != 1 {
		return "", fmt.Errorf("PKCE validation failed: code_verifier does not match challenge")
	}

	delete(p.issuedCodes, code) // Одноразовое использование!
	return "access_token_super_secure_pkce_token_2026", nil
}

func main() {
	idp := &MockOAuthProvider{issuedCodes: make(map[string]string)}

	// 1. Клиент инициирует поток авторизации PKCE
	verifier, challenge, err := GeneratePKCE()
	if err != nil {
		panic(err)
	}

	fmt.Println("=== 1. Инициация потока OAuth2 с PKCE (RFC 7636) ===")
	fmt.Printf("Code Verifier (секрет клиента):   %s\n", verifier)
	fmt.Printf("Code Challenge (отправлен в IdP): %s\n\n", challenge)

	// Формируем URL для редиректа браузера
	authURL := fmt.Sprintf("https://idp.example.com/oauth/authorize?client_id=my-spa&response_type=code&code_challenge=%s&code_challenge_method=S256",
		url.QueryEscape(challenge))
	fmt.Printf("Ссылка авторизации:\n%s\n\n", authURL)

	// IdP выпускает код авторизации, привязанный к challenge
	code := idp.IssueCode(challenge)
	fmt.Printf("Пользователь дал согласие. Браузер вернул code: '%s'\n\n", code)

	// 2. Легитимный клиент обменивает code на token, предъявляя verifier
	fmt.Println("=== 2. Легитимный обмен токена клиентом ===")
	token, err := idp.ExchangeToken(code, verifier)
	if err != nil {
		panic(err)
	}
	fmt.Printf("✅ Токен успешно получен: %s\n\n", token)

	// 3. Симуляция атаки: вредоносное приложение перехватило code, но НЕ знает verifier!
	stolenCode := idp.IssueCode(challenge)
	attackerFakeVerifier := "attacker_guessed_random_verifier_string_12345"

	fmt.Println("=== 3. Попытка взлома: перехват кода без знания code_verifier ===")
	_, attackErr := idp.ExchangeToken(stolenCode, attackerFakeVerifier)
	fmt.Printf("Результат атаки перехвата:\n❌ %v\n", attackErr)
}
```

## Под капотом

Спецификация RFC 7636 строго предписывает использовать метод `code_challenge_method=S256`. 
Устаревший метод `plain` (где challenge равен verifier без хэширования) признан небезопасным в OAuth 2.1 и не допускается современными провайдерами. Хэширование SHA-256 необратимо (pre-image resistance), что гарантирует: даже перехватив HTTP-запрос `/auth` с `code_challenge`, атакующий математически не сможет восстановить исходный `code_verifier`.

## Подводные камни

1. **Использование метода `plain`:** Метод `plain` передает verifier открытым текстом, уничтожая защиту при перехвате первого запроса. Используйте только `S256`.
2. **Недостаточная длина verifier:** Длина verifier должна составлять от 43 до 128 символов. 32 случайных байта в Base64URL дают ровно 43 символа.
3. **Хранение verifier в незащищенном виде:** Verifier должен сохраняться в памяти сессии клиента и очищаться сразу после обмена на токен.

## На собеседовании

**Вопрос с собеседования в Wildberries/Ozon:** «Почему расширение PKCE стало обязательным в стандарте OAuth 2.1 даже для конфиденциальных бэкенд-клиентов с client_secret?»
**Ответ:** Изначально PKCE создавался для публичных клиентов (SPA и мобильных приложений), неспособных скрыть секрет. Однако в практике эксплуатации бэкенд-систем выяснилось, что PKCE также защищает от атак подмены кода (Authorization Code Injection) и кражи кодов из журналов прокси-серверов. В OAuth 2.1 использование PKCE стало обязательным для абсолютно всех типов клиентов, обеспечивая криптографическую привязку запроса авторизации к запросу обмена токена.
