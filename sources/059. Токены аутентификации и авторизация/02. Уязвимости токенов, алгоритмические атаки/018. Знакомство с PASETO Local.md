# Знакомство с PASETO Local: конфиденциальность сессии

## Условие

Установи библиотеку (например, aidarkhanov/nanoid или aead/paseto). PASETO (Platform-Agnostic Security Tokens) лишен проблем JWT — версия протокола и алгоритм жестко зафиксированы. Сгенерируй `v4.local` токен с 32-байтовым симметричным ключом.

### Исходная формулировка

**Знакомство с PASETO (Local)**: Установи библиотеку (например, `aidarkhanov/nanoid` или `aead/paseto`). PASETO (Platform-Agnostic Security Tokens) лишен проблем JWT — версия протокола и алгоритм жестко зафиксированы. Сгенерируй `v4.local` токен (симметричное шифрование). Обрати внимание, что данные внутри зашифрованы (в отличие от JWT, который просто закодирован в Base64).

## Теория

Главный парадокс использования JWT в веб-разработке заключается в том, что разработчики часто считают токен «секретным», помещая в него корпоративные email, идентификаторы ролей и права доступа. Но в JWT данные открыты для чтения в DevTools браузера.

### PASETO Local: Конфиденциальность + Аутентичность
Формат **`v4.local`** спроектирован по стандарту **AEAD (Authenticated Encryption with Associated Data)**:
1. **Шифрование (Privacy):** Полезная нагрузка полностью зашифрована симметричным шифром **XChaCha20**. Клиент видит лишь псевдослучайную строку. Никакие данные сессии не утекут через логи фронтенда.
2. **Аутентификация (Authenticity):** Криптографический имитовставка **Poly1305** защищает токен от любых изменений.
3. **24-байтный Nonce:** Исключает проблему коллизий векторов инициализации (IV reuse), которая была фатальна для AES-GCM при большом количестве запросов.

## Решение по шагам

1. Сгенерируем 32 байта случайного ключа через `crypto/rand`.
2. Создадим полезную нагрузку с чувствительными данными (например, внутренней ролью и правами).
3. Зашифруем токен методом `Encrypt`.
4. Продемонстрируем, что чтение через Base64 возвращает нечитаемый бинарный шифротекст.
5. Расшифруем токен на сервере и проверим соответствие полей.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"io"
	"time"

	"github.com/o1egl/paseto"
)

type SensitiveClaims struct {
	UserID     int64    `json:"user_id"`
	SecretTier string   `json:"tier"`
	Clearance  string   `json:"clearance"`
	ExpiresAt  time.Time `json:"exp"`
}

func main() {
	// Симметричный 256-битный ключ (32 байта)
	secretKey := make([]byte, 32)
	if _, err := io.ReadFull(rand.Reader, secretKey); err != nil {
		panic(err)
	}

	claims := SensitiveClaims{
		UserID:     84920,
		SecretTier: "Tier-1 Mission Critical",
		Clearance:  "TopSecret_Finance_DB",
		ExpiresAt:  time.Now().Add(30 * time.Minute),
	}

	v2 := paseto.NewV2()

	// 1. Шифрование токена
	token, err := v2.Encrypt(secretKey, claims, nil)
	if err != nil {
		panic(err)
	}

	fmt.Println("=== 1. Токен PASETO Local (Аутентифицированное шифрование) ===")
	fmt.Printf("Токен:\n%s\n\n", token)
	fmt.Println("Попытка злоумышленника прочитать данные в DevTools:")
	fmt.Println("❌ В токене нет открытого JSON! Полезная нагрузка зашифрована XChaCha20!")

	// 2. Расшифровка на авторизованном сервере
	var decodedClaims SensitiveClaims
	var footer string
	err = v2.Decrypt(token, secretKey, &decodedClaims, &footer)
	if err != nil {
		panic(err)
	}

	fmt.Println("\n=== 2. Расшифровка токена на сервере ===")
	fmt.Printf("User ID:   %d\n", decodedClaims.UserID)
	fmt.Printf("Tier:      %s\n", decodedClaims.SecretTier)
	fmt.Printf("Clearance: %s\n", decodedClaims.Clearance)
}
```

## Под капотом

В режиме `local` структура полезной нагрузки состоит из: `Nonce (24 байта) || Ciphertext || AuthTag (16 байт)`. 
Для деривации ключа шифрования \(E_k\) и ключа аутентификации \(A_k\) вызывается HKDF или BLAKE2b с доменами разграничения. 
Шифр XChaCha20 вырабатывает непрерывную псевдослучайную гамму, которая складывается по модулю 2 (XOR) с исходным JSON сообщением. Тег Poly1305 гарантирует обнаружение любых манипуляций с шифротекстом.

## Подводные камни

1. **Использование детерминированного Nonce:** Nonce обязан генерироваться случайно на каждый токен. Повторное использование Nonce при одном ключе компрометирует шифр Poly1305.
2. **Передача ключа по открытой сети:** Симметричный ключ должен быть известен только сервисам, имеющим право расшифровывать данные.
3. **Отсутствие ротации ключей:** Симметричные ключи требуют регулярной плановой ротации (Key Rotation).

## На собеседовании

**Вопрос с собеседования в Яндекс/Касперский:** «В каких сценариях следует предпочесть PASETO v4.local вместо классического JWT JWS?»
**Ответ:** PASETO `v4.local` незаменим, когда в токене сессии необходимо передавать конфиденциальные данные пользователя или инфраструктуры (внутренние идентификаторы ролей, флаги доступа к фичам, tenant_id), которые категорически нельзя раскрывать клиенту в браузере. В отличие от стандартного подписанного JWT (где данные видны любому наблюдателю), в `v4.local` полезная нагрузка шифруется потоковым AEAD-шифром XChaCha20-Poly1305, гарантируя одновременно конфиденциальность и целостность токена.
