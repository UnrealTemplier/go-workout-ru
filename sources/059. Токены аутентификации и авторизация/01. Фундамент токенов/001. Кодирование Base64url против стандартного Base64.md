# Кодирование Base64url против стандартного Base64

## Условие

Покажите разницу между standard и URL-safe кодированием. Почему для токенов в URL/Cookie нужен именно base64url (без `+`, `/`, `=`)?

### Исходная формулировка

**Base64url vs Base64**: Покажите разницу между standard и URL-safe кодированием. Почему для токенов в URL/Cookie нужен именно base64url (без `+`, `/`, `=`)?

## Теория

При передаче бинарных криптографических данных (хешей, цифровых подписей, токенов) в веб-протоколах используется кодирование Base64. Однако стандартный алфавит **RFC 4648 §4 (Standard Base64)** создает критические проблемы совместимости:

### Проблемы Standard Base64 в вебе:
1. **Символ `+` (плюс):** В URL-параметрах (`query string`) и форматах `application/x-www-form-urlencoded` символ `+` декодируется веб-серверами как пробел (` `). В результате токен искажается и цифровая подпись перестает сходиться.
2. **Символ `/` (слэш):** Является зарезервированным разделителем путей в URL (`path delimiter`). При передаче токена в строке адреса сервер воспринимает его как вложенный путь роутера.
3. **Символ `=` (паддинг/заполнение):** Служит разделителем параметров в Query String (`key=value`) и заголовках Cookie. В некоторых парсерах наличие знака `=` приводит к обрезке значения.

### Решение: Base64url (RFC 4648 §5 / RFC 7515):
- Заменяет `+` на дефис `-`.
- Заменяет `/` на подчеркивание `_`.
- **Полностью отбрасывает паддинг `=`** (Raw URL Encoding).

В Go для токенов аутентификации (JWT, PASETO, OAuth2 code) всегда используется кодировщик **`base64.RawURLEncoding`**.

## Решение по шагам

1. Создадим срез байт с тестовой бинарной энтропией, генерирующей символы `+`, `/` и паддинг `=` в стандартном Base64.
2. Закодируем срез с помощью `base64.StdEncoding`.
3. Закодируем тот же срез через `base64.RawURLEncoding`.
4. Продемонстрируем, как стандартная строка Base64 ломает URL при передаче через `url.QueryEscape` / `url.QueryUnescape`.
5. Убедимся, что `RawURLEncoding` передается без искажений и не требует экранирования.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/base64"
	"fmt"
	"net/url"
)

func main() {
	// Бинарные байты, которые при Base64 дают символы '+', '/' и '='
	// 0xfb, 0xff, 0xbf -> в Base64 дают "+/++"
	sampleBytes := []byte{0xfb, 0xff, 0xfe, 0x11, 0x22}

	// 1. Стандартный Base64 (RFC 4648 §4)
	stdEncoded := base64.StdEncoding.EncodeToString(sampleBytes)

	// 2. Безопасный URL-Base64 без паддинга (RFC 4648 §5 / JWT Standard)
	rawUrlEncoded := base64.RawURLEncoding.EncodeToString(sampleBytes)

	fmt.Println("=== 1. Сравнение алфавитов кодирования ===")
	fmt.Printf("Исходные байты:     % x\n", sampleBytes)
	fmt.Printf("Standard Base64:    %s (содержит '+' и '=')\n", stdEncoded)
	fmt.Printf("Raw URL Base64:     %s (заменено на '-' и без '=')\n\n", rawUrlEncoded)

	fmt.Println("=== 2. Проблема передачи Standard Base64 в URL ===")
	// Имитируем передачу в Query String: ?token=<stdEncoded>
	// По стандарту URL decode заменяет '+' на пробел ' '!
	unescapedQuery, _ := url.QueryUnescape(stdEncoded)
	fmt.Printf("После url.QueryUnescape:\n")
	fmt.Printf("Результат:          %s\n", unescapedQuery)

	// Попытка декодировать испорченный токен
	_, err := base64.StdEncoding.DecodeString(unescapedQuery)
	fmt.Printf("Ошибка декодирования: %v (токен поврежден!)\n\n", err)

	fmt.Println("=== 3. Надежность RawURLEncoding в веб-протоколах ===")
	// URL decode никак не меняет символы '-' и '_'
	safeUnescaped, _ := url.QueryUnescape(rawUrlEncoded)
	decodedBytes, err := base64.RawURLEncoding.DecodeString(safeUnescaped)
	if err != nil {
		panic(err)
	}

	fmt.Printf("После URL decode:   %s\n", safeUnescaped)
	fmt.Printf("Успешно декодировано: % x (100%% совпадение!)\n", decodedBytes)
}
```

## Под капотом

Стандартный Base64 использует 64 символа: `A-Z` (26), `a-z` (26), `0-9` (10), `+` (1) и `/` (1). 
Алгоритм `base64.RawURLEncoding` производит побитовое смещение 6 бит на символ, подставляя символы из модифицированной таблицы, где 62-й символ — `-` (дефис, ASCII 45), а 63-й символ — `_` (подчеркивание, ASCII 95). 
При этом метод `Raw` отключает вывод символа паддинга `=`, уменьшая размер токена на 1–2 байта и исключая разрыв парсинга в cookie-заголовках HTTP.

## Подводные камни

1. **Путаница между `URLEncoding` и `RawURLEncoding`:** `base64.URLEncoding` заменяет `+` и `/`, но **оставляет символ `=`** в конце. Спецификация JWT (RFC 7519) и OAuth2 строго требуют отсутствия паддинга, поэтому вызов `base64.URLEncoding` может вызвать ошибку валидации во внешних шлюзах (Kong, Envoy).
2. **Ручное добавление паддинга:** Если сторонняя библиотека требует паддинг, рассчитывайте недостающие байты: `len % 4 == 2 -> "=="`, `len % 4 == 3 -> "="`.
3. **Мнение, что Base64 — это шифрование:** Base64 — это лишь метод кодирования бинарных данных в ASCII. Любой пользователь может раскодировать payload токена без ключа.

## На собеседовании

**Вопрос с собеседования в Яндекс/Авито:** «Почему в спецификации JWT и OpenAPI для токенов авторизации строго зафиксирован Base64URL без паддинга, а не обычный Base64?»
**Ответ:** Стандартный Base64 содержит символы `+`, `/` и знак заполнения `=`. В протоколе HTTP символ `+` в Query String интерпретируется как пробел, символ `/` конфликтует с URI-маршрутизацией, а знак `=` служит разделителем параметров в Cookie и строках запроса. Base64URL заменяет `+` на `-`, `/` на `_` и отбрасывает `=`, гарантируя безопасную передачу токена в HTTP-заголовках, строке адреса (URL) и Cookie без искажений и накладных расходов на дополнительный url-encode.
