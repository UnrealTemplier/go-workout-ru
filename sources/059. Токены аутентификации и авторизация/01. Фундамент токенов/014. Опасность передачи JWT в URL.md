# Опасность передачи JWT в URL и безопасное хранение в HttpOnly Cookie

## Условие

Покажите, как JWT в URL попадает в логи nginx/прокси, в Referer header. Используйте HttpOnly Cookie для веб-приложений.

### Исходная формулировка

**JWT в URL/Cookie — опасность**: Покажите, как JWT в URL попадает в логи nginx/прокси, в Referer header. Используйте HttpOnly Cookie для веб-приложений.

## Теория

Передача токенов аутентификации через параметры адреса (**URL Query String**: `https://app.com/dashboard?token=eyJ...`) — одна из грубейших и самых распространенных архитектурных ошибок:

### Векторы утечки токенов из URL:
1. **Логирование на всех уровнях (HTTP Access Logs):**
   - Все обратные прокси (Nginx, HAProxy, Envoy, Ingress-контроллеры) по умолчанию логируют полный URL запроса.
   - Токен пользователя навсегда оседает в открытом виде в текстовых файлах `/var/log/nginx/access.log`, отправляется в Elasticsearch/Kibana и становится доступен десяткам системных администраторов.
2. **Утечка через заголовок Referer:**
   - Если пользователь, находясь на странице с токеном в URL, кликнет на любую внешнюю ссылку, браузер отправит полный адрес вместе с токеном стороннему сайту в заголовке `Referer`.
3. **История браузера и экраны пользователей:** Токен сохраняется в истории браузера и отображается в строке URL.

### Отраслевой стандарт: HttpOnly Cookie
Токены должны передаваться в заголовке `Cookie` со строгими атрибутами:
- **`HttpOnly`:** Блокирует доступ к cookie со стороны клиентского JavaScript (`document.cookie`), полностью предотвращая кражу сессии через XSS-атаки!
- **`Secure`:** Гарантирует передачу cookie исключительно по шифрованному HTTPS-протоколу.
- **`SameSite=Strict` (или `Lax`):** Предотвращает отправку cookie при межсайтовых запросах, надежно защищая от CSRF-атак.

## Решение по шагам

1. Смоделируем HTTP-запрос с токеном в URL и покажем строку, попадающую в журнал Nginx access.log.
2. Продемонстрируем утечку токена через заголовок `Referer`.
3. Реализуем безопасную установку токена в `http.Cookie` со всеми атрибутами защиты.
4. Разработаем Middleware, считывающий токен из Cookie, а не из URL.
5. Проверим корректность работы безопасного механизма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

// InsecureURLHandler демонстрирует утечку токена в логи
func InsecureURLHandler(w http.ResponseWriter, r *http.Request) {
	token := r.URL.Query().Get("token")

	// Эмулируем запись в /var/log/nginx/access.log
	nginxLogLine := fmt.Sprintf(`192.168.1.10 - - [%s] "%s %s %s" 200 %d "%s" "%s"`,
		time.Now().Format("02/Jan/2006:15:04:05 -0700"),
		r.Method, r.RequestURI, r.Proto, len(token),
		r.Header.Get("Referer"), r.UserAgent(),
	)

	fmt.Printf("[NGINX ACCESS LOG УТЕЧКА]:\n%s\n\n", nginxLogLine)
	fmt.Fprintf(w, "Привет, токен получен из URL!")
}

// SetSecureAuthCookie устанавливает токен с максимальным уровнем защиты
func SetSecureAuthCookie(w http.ResponseWriter, token string) {
	cookie := &http.Cookie{
		Name:     "auth_token",
		Value:    token,
		Path:     "/",
		Expires:  time.Now().Add(15 * time.Minute),
		HttpOnly: true,                  // Защита от XSS: JS не может прочитать токен!
		Secure:   true,                  // Только HTTPS!
		SameSite: http.SameSiteLaxMode,  // Защита от CSRF атак!
	}
	http.SetCookie(w, cookie)
}

// SecureCookieAuthMiddleware извлекает токен строго из защищенной Cookie
func SecureCookieAuthMiddleware(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		cookie, err := r.Cookie("auth_token")
		if err != nil || cookie.Value == "" {
			http.Error(w, "Unauthorized: missing or invalid secure cookie", http.StatusUnauthorized)
			return
		}

		// В логах отображается только путь без параметров:
		cleanLog := fmt.Sprintf(`192.168.1.10 - - [%s] "%s %s %s" 200`,
			time.Now().Format("02/Jan/2006:15:04:05 -0700"),
			r.Method, r.URL.Path, r.Proto,
		)
		fmt.Printf("[БЕЗОПАСНЫЙ NGINX ЛОГ (нет токена)]:\n%s\n", cleanLog)

		next(w, r)
	}
}

func main() {
	sampleJWT := "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NSJ9.secretSignature"

	// 1. Демонстрация опасной передачи через Query String
	fmt.Println("=== 1. Опасная передача токена в строке URL ===")
	insecureReq := httptest.NewRequest(http.MethodGet, "/dashboard?token="+sampleJWT, nil)
	insecureReq.Header.Set("Referer", "https://google.com")
	insecureReq.Header.Set("User-Agent", "Mozilla/5.0")
	w1 := httptest.NewRecorder()
	InsecureURLHandler(w1, insecureReq)

	// 2. Демонстрация безопасной передачи через HttpOnly Cookie
	fmt.Println("=== 2. Безопасная установка HttpOnly Cookie ===")
	w2 := httptest.NewRecorder()
	SetSecureAuthCookie(w2, sampleJWT)

	setCookieHeader := w2.Header().Get("Set-Cookie")
	fmt.Printf("Заголовок Set-Cookie:\n%s\n\n", setCookieHeader)

	// 3. Проверка через SecureCookieAuthMiddleware
	secureReq := httptest.NewRequest(http.MethodGet, "/dashboard", nil)
	secureReq.AddCookie(&http.Cookie{Name: "auth_token", Value: sampleJWT})
	w3 := httptest.NewRecorder()

	protectedHandler := SecureCookieAuthMiddleware(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Успешный вход в защищенную систему!")
	})
	protectedHandler(w3, secureReq)
}
```

## Под капотом

Когда браузер встречает директиву `HttpOnly` в ответе сервера, движок JavaScript (V8 в Chrome, SpiderMonkey в Firefox) изолирует cookie в закрытом хранилище уровня C++. Свойство `document.cookie` вернет пустую строку или строку без `auth_token`, делая токен недосягаемым для внедренных XSS-скриптов. 
Директива `SameSite=Lax` предотвращает отправку cookie при кросс-доменных POST-запросах с чужих сайтов, защищая от CSRF.

## Подводные камни

1. **Передача токенов в WebSocket URL (`/ws?token=...`):** Поскольку стандартный JS WebSocket API в браузерах не позволяет кастомизировать заголовки, разработчики часто передают токен в Query String. Безопасное решение: использовать одноразовые тикеты (Ticket/Nonce exchange) на 10 секунд.
2. **Забытый флаг `Secure`:** Без флага `Secure` cookie может передаться по открытому HTTP-соединению при случайном переходе по ссылке.
3. **Отсутствие префикса `__Host-`:** Для максимальной защиты используйте префикс `__Host-auth_token`, привязывающий cookie строго к текущему домену без поддоменов.

## На собеседовании

**Вопрос с собеседования в Т-Банк/VK:** «Где в браузере безопаснее всего хранить сессионный токен пользователя: в localStorage или в HttpOnly Cookie? Обоснуйте риски обоих подходов.»
**Ответ:** 
- **`localStorage` (ОПАСНО):** Доступен любому JS-коду на странице. Любая XSS-уязвимость (в коде проекта или в любой из сотен npm-зависимостей) позволяет атакующему мгновенно украсть токен вызовом `localStorage.getItem('token')` и отправить его на свой сервер.
- **`HttpOnly Cookie` (РЕКОМЕНДОВАНО):** Браузер автоматически отправляет cookie в заголовках запроса, но запрещает доступ к ней через JavaScript. Это полностью защищает от XSS-кражи. Единственный риск cookie — атаки CSRF, которые надежно устраняются флагами `SameSite=Strict` или `SameSite=Lax` и CSRF-токенами.
