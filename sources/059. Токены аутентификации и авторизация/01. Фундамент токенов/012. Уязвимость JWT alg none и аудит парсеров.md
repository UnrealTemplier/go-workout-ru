# Уязвимость JWT «alg: none» и архитектурный аудит парсеров

## Условие

JWT позволяет клиенту самому указывать алгоритм подписи. Возьми библиотеку JWT. Создай токен, где в заголовке указано `"alg": "none"`, и удали подпись. Напиши "наивный" валидатор, который доверяет алгоритму из заголовка токена, и покажи, как поддельный токен обходит аутентификацию.

### Исходная формулировка

**Уязвимость JWT "alg: none"**: JWT позволяет клиенту самому указывать алгоритм подписи. Возьми библиотеку JWT. Создай токен, где в заголовке указано `"alg": "none"`, и удали подпись. Напиши "наивный" валидатор, который доверяет алгоритму из заголовка, и убедись, что он пропустит этот фейковый токен. (Всегда жестко задавай алгоритм при валидации JWT!).

## Теория

Исторический корень уязвимости **`alg: none` (CVE-2015-9235)** лежит в архитектурной концепции стандарта **RFC 7515 (JWS)**, где заголовок токена передается в открытом виде от клиента к серверу и содержит директиву о том, **как именно сервер обязан проверять цифровую подпись**.

Если код проверки полагается на заголовок входящего сообщения:
1. Атакующий перехватывает токен с низкими правами (`"role": "guest"`).
2. Заменяет полезную нагрузку на `{"sub": "root", "role": "admin"}`.
3. В заголовке указывает `"alg": "none"`.
4. Стирает криптографическую подпись после второй точки (оставляя формат `header.payload.`).
5. «Наивный» валидатор читает заголовок, видит алгоритм `none` и принимает решение, что криптографическая проверка не требуется, доверяя неподписанным данным.

Для предотвращения этой катастрофической ошибки в Go используется паттерн **Строгого Серверного Белого Списка (Strict Server-Side Whitelisting)**.

## Решение по шагам

1. Сформируем токен с `"alg": "none"` вручную с помощью `base64.RawURLEncoding`.
2. Реализуем уязвимый обработчик `VulnerableAuthMiddleware`, доверяющий заголовку.
3. Продемонстрируем, как нелегитимный запрос успешно проходит авторизацию с правами root.
4. Напишем защищенный обработчик `PatchedAuthMiddleware` с принудительной проверкой алгоритма.
5. Протестируем атаку на защищенном коде и зафиксируем отказ в доступе.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/base64"
	"encoding/json"
	"errors"
	"fmt"
	"strings"

	"github.com/golang-jwt/jwt/v5"
)

// VulnerableValidator наивно доверяет методу из заголовка
func VulnerableValidator(tokenStr string, secret []byte) (jwt.MapClaims, error) {
	token, err := jwt.Parse(tokenStr, func(t *jwt.Token) (any, error) {
		// ОШИБКА: если алгоритм none, возвращается nil, и библиотека считает токен валидным!
		if t.Method == jwt.SigningMethodNone {
			return jwt.UnsafeAllowNoneSignatureType, nil
		}
		return secret, nil
	})

	if err != nil {
		return nil, err
	}

	if claims, ok := token.Claims.(jwt.MapClaims); ok && token.Valid {
		return claims, nil
	}
	return nil, errors.New("invalid token")
}

// PatchedValidator жестко блокирует любые токены, кроме ожидаемого HS256
func PatchedValidator(tokenStr string, secret []byte) (jwt.MapClaims, error) {
	token, err := jwt.Parse(tokenStr, func(t *jwt.Token) (any, error) {
		// ЗАЩИТА: проверяем конкретный тип структуры алгоритма
		if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
			return nil, fmt.Errorf("forbidden algorithm: %v", t.Header["alg"])
		}
		return secret, nil
	},
		// Дополнительно блокируем на уровне парсера
		jwt.WithValidMethods([]string{"HS256"}),
	)

	if err != nil {
		return nil, fmt.Errorf("rejected: %w", err)
	}

	if claims, ok := token.Claims.(jwt.MapClaims); ok && token.Valid {
		return claims, nil
	}
	return nil, errors.New("invalid token")
}

func main() {
	serverSecret := []byte("ProductionSecretHMACKey2026")

	// 1. Формируем поддельный токен с alg: none
	hdrJSON := `{"alg":"none","typ":"JWT"}`
	payJSON := `{"sub":"root_admin","role":"superuser"}`

	hB64 := base64.RawURLEncoding.EncodeToString([]byte(hdrJSON))
	pB64 := base64.RawURLEncoding.EncodeToString([]byte(payJSON))

	// Обратите внимание на завершающую точку без подписи:
	maliciousToken := hB64 + "." + pB64 + "."

	fmt.Println("=== 1. Тестирование уязвимого валидатора (VulnerableValidator) ===")
	claims, err := VulnerableValidator(maliciousToken, serverSecret)
	if err == nil {
		fmt.Println("🚨 АТАКА УСПЕШНА! Уязвимый сервер авторизовал неподписанный токен!")
		fmt.Printf("Выдан доступ пользователю: %v (Роль: %v)\n\n", claims["sub"], claims["role"])
	}

	fmt.Println("=== 2. Тестирование защищенного валидатора (PatchedValidator) ===")
	_, patchErr := PatchedValidator(maliciousToken, serverSecret)
	if patchErr != nil {
		fmt.Printf("🛡️ АТАКА ЗАБЛОКИРОВАНА: %v\n", patchErr)
	}
}
```

## Под капотом

Константа `jwt.UnsafeAllowNoneSignatureType` в библиотеке `golang-jwt` была введена специально для того, чтобы разработчики не могли случайно включить поддержку `none`. Если ее вернуть в `Keyfunc`, библиотека отключает сверку подписи.
Защищенный валидатор `WithValidMethods` проверяет `m == token.Method.Alg()` до запуска какого-либо парсинга полезной нагрузки, возвращая статус ошибки `ErrSignatureInvalid`.

## Подводные камни

1. **Возврат `nil` ошибки для `none`:** Никогда не возвращайте `jwt.UnsafeAllowNoneSignatureType` в продакшн-сервисах.
2. **Пропуск точки в конце:** Токен с `alg: none` обязан содержать вторую точку (`header.payload.`), иначе библиотека забракует его как `malformed token`.
3. **Использование сторонних непроверенных JWT библиотек:** Некоторые устаревшие пакеты на GitHub до сих пор поддерживают `none` по умолчанию.

## На собеседовании

**Вопрос с собеседования в Касперский/Яндекс:** «Почему спецификация JWS вообще включила алгоритм "none", и к каким системным последствиям это привело?»
**Ответ:** Алгоритм `"none"` был включен в RFC 7515 для узких сценариев передачи данных по уже защищенным на транспортном уровне каналам (например, Mutual TLS), где криптографическая подпись считалась избыточной нагрузкой на CPU. 
Однако перенос контроля над проверкой подписи на сторону клиента привел к фундаментальной уязвимости: атакующие смогли подделывать учетные данные, отключая проверку на уязвимых серверах. В современной веб-разработке алгоритм `none` категорически запрещен, а в новых протоколах (PASETO) отказ от подписи невозможен на уровне спецификации.
