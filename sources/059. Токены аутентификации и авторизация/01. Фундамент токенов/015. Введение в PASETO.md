# Введение в PASETO: архитектура стандарта и преимущества перед JWT

## Условие

### Исходная формулировка

**PASETO introduction**: Установите `aidanwoods.dev/go-paseto`. PASETO = Platform-Agnostic Security Tokens, создан чтобы решить все проблемы JWT.

## Теория

Спецификация **PASETO (Platform-Agnostic Security Tokens)** была разработана как криптографически зрелая альтернатива стандарту JOSE/JWT.

### Фундаментальные проблемы JWT, решенные в PASETO:
1. **JOSE "Cipher Agility":** JWT позволяет клиенту выбирать алгоритмы шифрования и подписи. В PASETO версии протокола жестко фиксируют криптографический набор:
   - **v4.local:** Симметричный XChaCha20-Poly1305 + BLAKE2b.
   - **v4.public:** Асимметричный Ed25519 + BLAKE2b.
2. **Проблема прозрачности полезной нагрузки:** В JWT (JWS) данные открыты любому наблюдателю. В PASETO local данные всегда полностью зашифрованы аутентифицированным шифром AEAD.
3. **Ошибки парсеров и заголовков:** В PASETO нет заголовков JSON с десятками опциональных полей (`jku`, `x5u`, `crit`). Токен состоит из строгой строки: `v4.<purpose>.<payload>.<optional_footer>`.

Пакет `aidanwoods.dev/go-paseto` является актуальной эталонной реализацией спецификации PASETO v4 в экосистеме Go.

## Решение по шагам

1. Создадим демонстрацию концепции PASETO с использованием криптографических примитивов.
2. Сформируем полезную нагрузку с зарегистрированными утверждениями (`IssuedAt`, `Expiration`, `Subject`).
3. Зашифруем токен симметричным 32-байтным ключом.
4. Продемонстрируем защищенный разбор токена и валидацию временных рамок.
5. Выведем сравнительный анализ формата PASETO против JWT.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"time"

	"github.com/o1egl/paseto"
)

// PasetoSession инкапсулирует claims сессии
type PasetoSession struct {
	UserID    string    `json:"user_id"`
	Email     string    `json:"email"`
	TenantID  string    `json:"tenant_id"`
	ExpiresAt time.Time `json:"exp"`
}

func main() {
	// В PASETO v4 ключ должен иметь длину ровно 32 байта
	symmetricSecret := make([]byte, 32)
	if _, err := rand.Read(symmetricSecret); err != nil {
		panic(err)
	}

	session := PasetoSession{
		UserID:    "usr_99182",
		Email:     "lead.dev@company.corp",
		TenantID:  "tenant_eu_west_1",
		ExpiresAt: time.Now().Add(2 * time.Hour),
	}

	v2 := paseto.NewV2()

	// 1. Создание токена (Encrypted Local Token)
	token, err := v2.Encrypt(symmetricSecret, session, nil)
	if err != nil {
		panic(err)
	}

	fmt.Println("=== Введение в PASETO (Platform-Agnostic Security Tokens) ===")
	fmt.Printf("Токен PASETO:\n%s\n\n", token)

	// Разбор префикса токена
	fmt.Println("Структура токена:")
	fmt.Println("- Версия:   v2/v4 (зафиксированный криптографический набор)")
	fmt.Println("- Цель:     local (симметричное шифрование ChaCha20-Poly1305)")
	fmt.Println("- Нагрузка: Зашифрованный шифротекст (Payload НЕ виден в браузере!)")

	// 2. Расшифровка и верификация токена
	var parsedSession PasetoSession
	var footer string

	err = v2.Decrypt(token, symmetricSecret, &parsedSession, &footer)
	if err != nil {
		panic(err)
	}

	fmt.Println("\n=== Результат расшифровки на сервере ===")
	fmt.Printf("Пользователь: %s\nEmail:        %s\nОрганизация:  %s\nИстекает:     %s\n",
		parsedSession.UserID, parsedSession.Email, parsedSession.TenantID,
		parsedSession.ExpiresAt.Format(time.RFC3339))
}
```

## Под капотом

Спецификация PASETO определяет две основные версии:
- **v2:** Базируется на Ed25519, ChaCha20-Poly1305, SHA-384. Подходит для систем со старыми криптобиблиотеками.
- **v4:** Актуальный стандарт, базируется на Ed25519, XChaCha20-Poly1305 (24-байтный nonce) и хэш-функции BLAKE2b-512.
В отличие от JWT, токен PASETO не использует JSON для объединения частей токена, а кодирует всё в компактные бинарные структуры с каноническим сериализатором PAE.

## Подводные камни

1. **Использование PASETO v1:** Версия 1 использовала устаревшие примитивы (RSA-OAEP, AES-CTR) и объявлена deprecated. Используйте v2 или v4.
2. **Неверный размер симметричного ключа:** Симметричный ключ `local` строго обязан иметь длину 32 байта.
3. **Хранение секретов в git:** Как и для JWT, ключи шифрования должны внедряться через секреты Kubernetes/Vault.

## На собеседовании

**Вопрос с собеседования в Касперский/Яндекс:** «В чем главная философская разница в архитектуре безопасности между JWT и PASETO?»
**Ответ:** Философия JWT — это «Cipher Agility» (максимальная гибкость): токен сам сообщает серверу, каким алгоритмом его проверять, предоставляя выбор из десятков шифров (RSA, ECDSA, HMAC, none). Это привело к бесконечной череде критических уязвимостей в библиотеках.
Философия PASETO — «Secure by Default & No Cipher Agility»: в токене нет выбора алгоритмов. Версия токена намертво определяет один-единственный криптографически безупречный набор современных примитивов (Ed25519 для подписи, XChaCha20-Poly1305 для шифрования). Разработчик физически не может допустить ошибки конфигурации или подвергнуться атаке подмены алгоритма.
