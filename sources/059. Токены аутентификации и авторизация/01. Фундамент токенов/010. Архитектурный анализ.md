# Архитектурный анализ: почему JWT не подходит для сессий

## Условие

Покажите, почему JWT плохи как сессионные токены (нельзя отозвать без state, большие по размеру, leak в логах).

### Исходная формулировка

**JWT не для sessions**: Покажите, почему JWT плохи как сессионные токены (нельзя отозвать без state, большие по размеру, leak в логах).

## Теория

Маркетинговый миф о «бессерверных сессиях на stateless JWT» привел к серьезным проблемам безопасности в тысячах веб-приложений. 

### Почему JWT не подходит для управления сессиями пользователей (User Sessions):

1. **Невозможность мгновенного отзыва (No Immediate Revocation):**
   - Если учетная запись пользователя скомпрометирована, украден ноутбук или администратор заблокировал пользователя, выданный JWT **продолжает оставаться валидным до истечения поля `exp`**.
   - Чтобы отозвать JWT досрочно, бэкенд вынужден внедрять **Blacklist / Revocation List** (например, в Redis). Но как только вы внедряете Redis для проверки каждого входящего токена, **вся концепция Stateless уничтожается**: вы вернулись к классическим stateful-сессиям, но с худшей реализацией!

2. **Огромный размер токена (Network & Bandwidth Bloat):**
   - Классический Session ID (например, 32-байтный случайный токен) занимает ~44 байта Base64.
   - JWT токен со списком ролей, скоупов и подписью RSA занимает **от 1 до 4 Килобайт**.
   - При 10 000 HTTP-запросов в секунду передача 3 КБ JWT в каждом заголовке `Authorization` или `Cookie` генерирует **сотни гигабайт паразитного сетевого трафика в день**!

3. **Утечки в логах и сторонних сервисах (Leaking):**
   - JWT часто передают в Query-параметрах URL или Cookie без флага `HttpOnly`, что приводит к утечке токена в HTTP Access Logs, proxy-серверы и заголовки `Referer` сторонних сайтов.

## Решение по шагам

1. Сравним размер классического случайного Session ID и стандартного корпоративного JWT.
2. Продемонстрируем проблему отзыва: покажем, что без централизованного хранилища отозвать JWT невозможно.
3. Смоделируем сценарий экстренной блокировки пользователя администратором.
4. Разработаем гибридный Session Manager на Go: Stateful Session в Redis/памяти против Stateless JWT.
5. Сделаем обоснованные инженерные выводы о правильных областях применения обоих подходов.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"encoding/hex"
	"fmt"
	"sync"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

// SessionStore эмулирует классическое stateful хранилище сессий (Redis/PostgreSQL)
type SessionStore struct {
	mu       sync.RWMutex
	sessions map[string]int64 // sessionToken -> userID
}

func NewSessionStore() *SessionStore {
	return &SessionStore{sessions: make(map[string]int64)}
}

func (s *SessionStore) CreateSession(userID int64) (string, error) {
	b := make([]byte, 32)
	if _, err := rand.Read(b); err != nil {
		return "", err
	}
	token := hex.EncodeToString(b) // 64 hex символа
	s.mu.Lock()
	s.sessions[token] = userID
	s.mu.Unlock()
	return token, nil
}

func (s *SessionStore) RevokeSession(token string) {
	s.mu.Lock()
	delete(s.sessions, token) // Мгновенный отзыв!
	s.mu.Unlock()
}

func (s *SessionStore) ValidateSession(token string) (int64, bool) {
	s.mu.RLock()
	uid, ok := s.sessions[token]
	s.mu.RUnlock()
	return uid, ok
}

func main() {
	rsaKey, _ := rsa.GenerateKey(rand.Reader, 2048)

	// 1. Создаем классический Session Token (Opaque Token)
	sessionStore := NewSessionStore()
	opaqueToken, _ := sessionStore.CreateSession(1001)

	// 2. Создаем JWT с типичными корпоративными claims
	jwtClaims := jwt.MapClaims{
		"sub":         "1001",
		"email":       "architect@company.ru",
		"roles":       []string{"user", "billing_admin", "devops"},
		"permissions": []string{"read:users", "write:deploy", "manage:billing"},
		"exp":         time.Now().Add(24 * time.Hour).Unix(),
		"iss":         "auth.company.corp",
		"aud":         "api.company.corp",
	}
	jwtObj := jwt.NewWithClaims(jwt.SigningMethodRS256, jwtClaims)
	jwtString, _ := jwtObj.SignedString(rsaKey)

	fmt.Println("=== 1. Сравнение накладных расходов сети (Размер в байтах) ===")
	fmt.Printf("Opaque Session ID:  %4d байт  (Токен: %s...)\n", len(opaqueToken), opaqueToken[:16])
	fmt.Printf("Корпоративный JWT:  %4d байт  (Токен: %s...)\n", len(jwtString), jwtString[:16])
	fmt.Printf("JWT больше в %.1f раз! При 10M запросах/сутки это гигабайты избыточного трафика!\n\n",
		float64(len(jwtString))/float64(len(opaqueToken)))

	fmt.Println("=== 2. Сценарий экстренного отзыва (Revocation) при взломе ===")
	fmt.Println("Администратор нажимает кнопку 'Заблокировать пользователя и отозвать все сессии'...")

	// Отзываем Session ID
	sessionStore.RevokeSession(opaqueToken)
	_, validOpaque := sessionStore.ValidateSession(opaqueToken)
	fmt.Printf("Проверка Session ID после отзыва: валиден = %t (Доступ мгновенно заблокирован!)\n", validOpaque)

	// Проверяем JWT
	parsedJWT, _ := jwt.Parse(jwtString, func(t *jwt.Token) (any, error) {
		return &rsaKey.PublicKey, nil
	})
	fmt.Printf("Проверка Stateless JWT после блокировки: валиден = %t (ПРОБЛЕМА: доступ РАЗРЕШЕН еще 24 часа!)\n\n",
		parsedJWT.Valid)

	fmt.Println("Вывод архитектора: JWT идеален для короткоживущих межсервисных токенов (15 минут), но опасен для сессий браузера.")
}
```

## Под капотом

В распределенной системе с классическим Session ID запрос к Redis `GET session:<token>` по прямому TCP/in-memory занимает ~0.3–0.5 мс, а удаление `DEL session:<token>` выполняется мгновенно и атомарно.
Попытка эмулировать отзыв JWT через сохранение списка отозванных токенов (`JTI Blacklist`) требует проверки Redis при каждом запросе, полностью лишая JWT статуса stateless, но сохраняя проблему огромного размера токена.

## Подводные камни

1. **Большой срок жизни JWT (`exp > 1 hour`):** Выпуск JWT сессии на 30 дней без механизма ротации — грубейшая ошибка безопасности.
2. **Хранение JWT в localStorage:** В отличие от кук с `HttpOnly`, токен в localStorage доступен любому JavaScript на странице, делая его легкой добычей для XSS.
3. **Хранение критических прав в JWT:** Если права пользователя изменились с 'admin' на 'banned', пользователь останется админом до истечения времени токена.

## На собеседовании

**Вопрос с собеседования в Яндекс/Авито:** «Почему крупные высоконагруженные компании отказываются от использования JWT в качестве сессионных токенов для браузеров в пользу Opaque Session ID?»
**Ответ:** 
1. **Невозможность мгновенной инвалидации:** При компрометации аккаунта, смене пароля или блокировке службой безопасности отозвать чистый JWT невозможно до истечения срока `exp`. Внедрение блэклиста в Redis превращает JWT в обычную сессию, нивелируя его преимущества.
2. **Накладные расходы на трафик (Network Bloat):** JWT с подписью и ролями весит 1–3 КБ против 32–64 байт для Session ID. В сервисах с миллионами RPS это терабайты лишнего трафика.
3. **XSS уязвимость:** Сессионный Cookie с флагами `HttpOnly`, `Secure` и `SameSite=Strict` защищен от кражи через JavaScript, в то время как JWT в Single Page Application часто неверно сохраняют в LocalStorage.
