# Реализация JWKS endpoint и middleware проверки токенов по kid

## Условие

Реализуйте endpoint `/.well-known/jwks.json`, который отдаёт публичные ключи в формате JWK. Напишите middleware, который загружает JWKS, кэширует и проверяет JWT подпись по `kid` (key ID) из header.

### Исходная формулировка

**JWKS endpoint.**: Реализуйте endpoint `/.well-known/jwks.json`, который отдаёт публичные ключи в формате JWK. Напишите middleware, который загружает JWKS, кэширует и проверяет JWT подпись по `kid` (key ID) из header.

## Теория

Стандарт **RFC 7517 (JSON Web Key / JWK)** и **JWKS (JSON Web Key Set)** определяет формат публикации открытых ключей аутентификации через публичный HTTP эндпоинт:
```text
GET /.well-known/jwks.json
```

### Формат структуры JWKS:
```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "auth-key-2026-v1",
      "n": "u1... (модуль RSA в Base64URL)",
      "e": "AQAB"
    }
  ]
}
```

### Архитектура валидации в микросервисах:
1. Микросервис API шлюза или ресурсного сервера не хранит локальные ключи и не имеет доступа к БД пользователей.
2. При старте сервис скачивает набор ключей с сервера авторизации и кэширует их в оперативной памяти (с TTL, например, 1 час).
3. При входящем HTTP-запросе с заголовком `Authorization: Bearer <token>`:
   - Из заголовка JWT извлекается идентификатор ключа `kid`.
   - В кэше JWKS находится соответствующий публичный ключ `*rsa.PublicKey`.
   - Если ключ с таким `kid` отсутствует (возможно, произошла плановая ротация), кэш принудительно инвалидируется и скачивается свежий JWKS.
   - Выполняется криптографическая проверка подписи токена.

## Решение по шагам

1. Сгенерируем пару ключей RSA и создадим структуру JWK (RFC 7517) с полями `kty`, `kid`, `use`, `n`, `e`.
2. Реализуем HTTP-обработчик `HandleJWKS` (`/.well-known/jwks.json`).
3. Разработаем клиентский менеджер `JWKSCache` с потокобезопасным кэшированием публичных ключей.
4. Создадим HTTP Middleware `AuthJWKSMiddleware`, проверяющий входящий токен по `kid` из кэша.
5. Протестируем успешную авторизацию валидным токеном и отклонение токена с неизвестным `kid`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"encoding/base64"
	"encoding/json"
	"fmt"
	"math/big"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

// JWKKey описывает один открытый ключ стандарта RFC 7517
type JWKKey struct {
	Kty string `json:"kty"` // "RSA"
	Kid string `json:"kid"` // Key ID
	Use string `json:"use"` // "sig"
	Alg string `json:"alg"` // "RS256"
	N   string `json:"n"`   // Modulus (Base64URL)
	E   string `json:"e"`   // Exponent (Base64URL)
}

type JWKSResponse struct {
	Keys []JWKKey `json:"keys"`
}

// ExportRSAPublicToJWK конвертирует *rsa.PublicKey в JWK
func ExportRSAPublicToJWK(kid string, pub *rsa.PublicKey) JWKKey {
	nBytes := pub.N.Bytes()
	eBytes := big.NewInt(int64(pub.E)).Bytes()

	return JWKKey{
		Kty: "RSA",
		Kid: kid,
		Use: "sig",
		Alg: "RS256",
		N:   base64.RawURLEncoding.EncodeToString(nBytes),
		E:   base64.RawURLEncoding.EncodeToString(eBytes),
	}
}

// JWKSCache управляет потокобезопасным кэшем открытых ключей
type JWKSCache struct {
	mu   sync.RWMutex
	keys map[string]*rsa.PublicKey
}

func NewJWKSCache() *JWKSCache {
	return &JWKSCache{keys: make(map[string]*rsa.PublicKey)}
}

func (c *JWKSCache) Set(kid string, key *rsa.PublicKey) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.keys[kid] = key
}

func (c *JWKSCache) Get(kid string) (*rsa.PublicKey, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	k, ok := c.keys[kid]
	return k, ok
}

func main() {
	// 1. Инициализация сервера авторизации с RSA-ключом
	rsaPrivateKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		panic(err)
	}
	keyID := "auth-service-2026-v1"
	jwk := ExportRSAPublicToJWK(keyID, &rsaPrivateKey.PublicKey)

	// Эмулируем HTTP эндпоинт /.well-known/jwks.json
	jwksHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(JWKSResponse{Keys: []JWKKey{jwk}})
	})
	jwksServer := httptest.NewServer(jwksHandler)
	defer jwksServer.Close()

	fmt.Println("=== 1. Эндпоинт JWKS активен ===")
	fmt.Printf("JWKS URL: %s\n", jwksServer.URL)
	jwksJSON, _ := json.MarshalIndent(JWKSResponse{Keys: []JWKKey{jwk}}, "", "  ")
	fmt.Printf("Ответ JWKS:\n%s\n\n", string(jwksJSON))

	// 2. Инициализация кэша на стороне ресурсного микросервиса
	cache := NewJWKSCache()
	cache.Set(keyID, &rsaPrivateKey.PublicKey)

	// 3. Выпуск легитимного токена с заголовком 'kid'
	tokenObj := jwt.NewWithClaims(jwt.SigningMethodRS256, jwt.MapClaims{
		"sub":  "usr_lead_architect",
		"role": "admin",
		"exp":  time.Now().Add(1 * time.Hour).Unix(),
	})
	tokenObj.Header["kid"] = keyID // Добавляем Key ID в заголовок токена!

	signedToken, err := tokenObj.SignedString(rsaPrivateKey)
	if err != nil {
		panic(err)
	}

	// 4. Валидация токена через JWKS кэш по 'kid'
	keyFunc := func(t *jwt.Token) (any, error) {
		if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {
			return nil, fmt.Errorf("unexpected method: %v", t.Header["alg"])
		}
		rawKid, ok := t.Header["kid"].(string)
		if !ok || rawKid == "" {
			return nil, fmt.Errorf("missing kid in token header")
		}

		pubKey, found := cache.Get(rawKid)
		if !found {
			return nil, fmt.Errorf("key with kid '%s' not found in jwks cache", rawKid)
		}
		return pubKey, nil
	}

	fmt.Println("=== 2. Проверка токена по kid из кэша JWKS ===")
	parsedToken, err := jwt.Parse(signedToken, keyFunc, jwt.WithValidMethods([]string{"RS256"}))
	if err != nil {
		panic(err)
	}

	fmt.Printf("Токен успешно проверен: %t\n", parsedToken.Valid)
	if claims, ok := parsedToken.Claims.(jwt.MapClaims); ok {
		fmt.Printf("Субъект: %s, Роль: %s\n\n", claims["sub"], claims["role"])
	}

	// 5. Попытка проверки токена с неизвестным kid
	tokenBadKidObj := jwt.NewWithClaims(jwt.SigningMethodRS256, jwt.MapClaims{"sub": "intruder"})
	tokenBadKidObj.Header["kid"] = "unknown-kid-999"
	badKidToken, _ := tokenBadKidObj.SignedString(rsaPrivateKey)

	_, badErr := jwt.Parse(badKidToken, keyFunc, jwt.WithValidMethods([]string{"RS256"}))
	fmt.Printf("Проверка токена с чужим kid:\nРезультат: %v (доступ заблокирован!)\n", badErr)
}
```

## Под капотом

Параметр `n` в JWK представляет собой модуль числа RSA (\(n = p \times q\)), а параметр `e` — публичную экспоненту (обычно 65537, что в Base64URL равно `AQAB`). 
Библиотека на клиенте восстанавливает экземпляр `*rsa.PublicKey`, создавая `big.Int` из байт `n` и `e`. Кэш ключей в памяти исключает сетевые HTTP-запросы при каждом запросе к API, снижая задержку микросервиса до сотен наносекунд.

## Подводные камни

1. **Сетевой запрос на каждый входящий токен:** Если на каждый HTTP-запрос скачивать `jwks.json`, то при 10 000 RPS auth-сервер ляжет от самодельного DoS, а задержка API вырастет до 100 мс. Обязательно кэшируйте JWKS.
2. **Атака истощения кэша (Cache DoS):** Если злоумышленник отправляет миллионы запросов с уникальными случайными `kid`, сервис не должен бесконечно запрашивать JWKS. Ограничивайте частоту фонового обновления (rate limit refresh, например, не чаще раза в 10 секунд).
3. **Отсутствие проверки флага `use: "sig"`:** Публичный ключ с `use: "enc"` предназначен для шифрования, а не для верификации подписи.

## На собеседовании

**Вопрос с собеседования в Авито/VK:** «Как организовать валидацию токенов в архитектуре из 200 Go-микросервисов без создания единой точки отказа (Single Point of Failure) на сервере авторизации?»
**Ответ:** 
1. Использовать асимметричные токены **RS256** или **EdDSA**.
2. Сервер авторизации публикует открытые ключи через эндпоинт **JWKS** (`/.well-known/jwks.json`).
3. Каждый из 200 микросервисов при старте скачивает JWKS и кэширует публичные ключи в локальной оперативной памяти.
4. Микросервисы валидируют входящие токены **автономно и локально в памяти** за микросекунды, не делая сетевых запросов к серверу авторизации.
5. При получении токена с новым `kid` микросервис инициирует фоновое обновление кэша JWKS с защитой от спама через rate limiter. Если сервер авторизации временно недоступен, микросервисы продолжают успешно работать на закэшированных ключах.
