# Обязательная валидация алгоритма в JWT (WithValidMethods)

## Условие

Настройте `jwt.WithValidMethods([]string{"RS256"})`. Без этого ваш код уязвим к algorithm confusion.

### Исходная формулировка

**JWT всегда verificate алгоритм**: Настройте `jwt.WithValidMethods([]string{"RS256"})`. Без этого ваш код уязвим к algorithm confusion.

## Теория

В библиотеке **golang-jwt/jwt/v5** опция **`jwt.WithValidMethods`** является главным системным барьером против атак путаницы алгоритмов и подделки заголовков.

### Что происходит, если `WithValidMethods` НЕ указан?
```go
// ОПАСНЫЙ КОД!
token, err := jwt.Parse(tokenStr, keyFunc)
```
1. Парсер библиотеки считывает заголовок `alg` из токена, переданного недоверенным клиентом.
2. Библиотека находит соответствующий метод в глобальном реестре (где зарегистрированы HS256, HS384, HS512, RS256, RS384, RS512, ES256, EdDSA и даже none).
3. Библиотека вызывает ваш `keyFunc`. Если ваш `keyFunc` не проверяет тип интерфейса метода, токен с подмененным алгоритмом успешно проходит криптографическую валидацию!

### Что делает `jwt.WithValidMethods([]string{"RS256"})`?
Опция выполняет **раннюю проверку (Fail-Fast)** еще до выделения памяти и до запуска криптографических операций:
- Если поле `alg` в заголовке токена не входит в заданный срез строк, разбор токена немедленно прерывается с ошибкой:
  `token is unverifiable: token signature is invalid: signing method ... is invalid`.
- Функция `keyFunc` даже не вызывается, полностью блокируя атаку на корню!

## Решение по шагам

1. Создадим демонстрационный сервер, ожидающий токены с подписью RS256.
2. Сконфигурируем парсер с `jwt.WithValidMethods([]string{"RS256"})`.
3. Попробуем скормить парсеру токен с алгоритмом `HS256`.
4. Убедимся, что парсер мгновенно отвергает токен до вызова `keyFunc`.
5. Подадим корректно подписанный токен `RS256` и подтвердим успешную валидацию.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"fmt"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

func main() {
	// Генерируем серверную пару ключей RSA
	rsaPrivateKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		panic(err)
	}
	rsaPublicKey := &rsaPrivateKey.PublicKey

	// 1. Создаем легитимный токен RS256
	validClaims := jwt.MapClaims{
		"sub":  "alice_engineer",
		"role": "editor",
		"exp":  time.Now().Add(10 * time.Minute).Unix(),
	}
	legitTokenObj := jwt.NewWithClaims(jwt.SigningMethodRS256, validClaims)
	legitTokenStr, _ := legitTokenObj.SignedString(rsaPrivateKey)

	// 2. Создаем вредоносный токен HS256 (симуляция атаки Algorithm Confusion)
	fakeClaims := jwt.MapClaims{
		"sub":  "eve_attacker",
		"role": "admin",
		"exp":  time.Now().Add(10 * time.Minute).Unix(),
	}
	fakeTokenObj := jwt.NewWithClaims(jwt.SigningMethodHS256, fakeClaims)
	fakeTokenStr, _ := fakeTokenObj.SignedString([]byte("some_hmac_secret"))

	// Функция получения ключа
	keyFunc := func(t *jwt.Token) (any, error) {
		// При WithValidMethods сюда попадут ТОЛЬКО токены с RS256!
		fmt.Printf("[KeyFunc] Вызов для алгоритма: %v\n", t.Header["alg"])
		return rsaPublicKey, nil
	}

	fmt.Println("=== 1. Проверка легитимного токена с WithValidMethods(['RS256']) ===")
	validToken, err := jwt.Parse(legitTokenStr, keyFunc, jwt.WithValidMethods([]string{"RS256"}))
	if err != nil {
		panic(err)
	}
	fmt.Printf("Результат проверки: токен валиден = %t (User: %v)\n\n",
		validToken.Valid, validClaims["sub"])

	fmt.Println("=== 2. Попытка скормить вредоносный токен HS256 ===")
	_, attackErr := jwt.Parse(fakeTokenStr, keyFunc, jwt.WithValidMethods([]string{"RS256"}))
	if attackErr != nil {
		fmt.Printf("🛡️ БЛОКИРОВКА СРАБОТАЛА:\n%v\n", attackErr)
		fmt.Println("(Обратите внимание: KeyFunc даже не вызывался!)")
	} else {
		fmt.Println("Ошибка безопасности: поддельный токен был принят!")
	}
}
```

ℹ️ Безопасный разбор JWT с обязательной опцией jwt.WithValidMethods

## Под капотом

Внутри `golang-jwt/jwt/v5` метод `parser.ParseWithClaims` перед обращением к `Keyfunc` выполняет проверку:
```go
if len(p.validMethods) > 0 {
    var hasValidMethod bool
    for _, m := range p.validMethods {
        if m == token.Method.Alg() {
            hasValidMethod = true
            break
        }
    }
    if !hasValidMethod {
        return token, NewValidationError(..., ErrSignatureInvalid)
    }
}
```
Это полностью исключает исполнение любого пользовательского кода валидации при несоответствии алгоритма.

## Подводные камни

1. **Использование глобального `jwt.Parse` без опций:** Забытая опция `WithValidMethods` оставляет токен уязвимым ко всем историческим атакам смены алгоритма.
2. **Передача пустого среза методов:** Вызов `jwt.WithValidMethods([]string{})` отключает фильтрацию.
3. **Разрешение небезопасных методов вместе с безопасными:** Указание `[]string{"RS256", "HS256"}` без строгой изоляции ключей снова возвращает уязвимость Algorithm Confusion.

## На собеседовании

**Вопрос с собеседования в Т-Банк/Ozon:** «Почему в современных версиях golang-jwt/jwt/v5 опция WithValidMethods считается обязательной практикой (Best Practice)?»
**Ответ:** По умолчанию формат JWT позволяет клиенту передавать любой алгоритм в заголовке токена (`alg`). Если сервер доверяет этому полю, атакующий может подменить асимметричный алгоритм RS256 на симметричный HS256 или `none`. Опция `jwt.WithValidMethods` устанавливает жесткий белый список разрешенных алгоритмов на сервере. Любой токен с другим алгоритмом отклоняется парсером немедленно до вызова функции проверки ключа `keyFunc`, что на корню устраняет атаки Algorithm Confusion и `alg: none` без необходимости ручных проверок в каждом микросервисе.
