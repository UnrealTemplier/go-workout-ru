# Уязвимость алгоритма «alg: none» в JWT и защита валидатором

## Условие

Создайте JWT с `"alg":"none"`, удалите signature, покажите, что наивный парсер может принять его как валидный. Напишите защиту: жёсткий whitelist допустимых алгоритмов (`HS256`, `RS256`, `EdDSA`).

### Исходная формулировка

**Атака «alg: none».**: Создайте JWT с `"alg":"none"`, удалите signature, покажите, что наивный парсер может принять его как валидный. Напишите защиту: жёсткий whitelist допустимых алгоритмов (`HS256`, `RS256`, `EdDSA`).

## Теория

Спецификация **RFC 7515 (JSON Web Signature)** содержит специальный алгоритм подписи: **`"alg": "none"`** (Unsecured JWS). Изначально он задумывался для отладки или передачи данных по гарантированно защищенным внутренним каналам (например, внутри TLS без необходимости цифровой подписи).

Однако поддержка `alg: none` привела к одной из самых разрушительных уязвимостей в истории веб-безопасности:
1. Злоумышленник берет легитимный токен обычного пользователя.
2. В расшифрованном JSON-заголовке меняет поле алгоритма на `"alg": "none"` (или `"None"`, `"NONE"`, `"nOnE"`).
3. В полезной нагрузке (payload) меняет `"user_id": 123` на `"user_id": 1, "role": "admin"`.
4. Удаляет криптографическую подпись после второй точки: `header.payload.`.
5. **Наивный парсер:** видит `alg: "none"`, решает, что проверять подпись не требуется, считает токен подлинным и выдает злоумышленнику права суперпользователя!

### Промышленная защита:
В современных библиотеках (например, `github.com/golang-jwt/jwt/v5`) парсер обязан конфигурироваться с **жестким белым списком допустимых алгоритмов** (`jwt.WithValidMethods`), отвергающим любые неразрешенные типы заголовка на этапе разбора.

## Решение по шагам

1. Создадим демонстрационный токен с `"alg": "none"` и правами администратора.
2. Реализуем уязвимый парсер `NaiveJWTParser`, принимающий токен без проверки метода.
3. Покажем, что наивный код пропускает неподписанный токен.
4. Разработаем защищенный парсер `SecureJWTParser` с валидацией белого списка алгоритмов (`HS256`).
5. Убедимся, что защищенный парсер немедленно отклоняет токен с ошибкой неразрешенного алгоритма.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/base64"
	"encoding/json"
	"errors"
	"fmt"
	"strings"

	"github.com/golang-jwt/jwt/v5"
)

// NaiveJWTParser эмулирует исторически уязвимый разбор токена
func NaiveJWTParser(tokenStr string) (map[string]any, error) {
	parts := strings.Split(tokenStr, ".")
	if len(parts) != 3 {
		return nil, errors.New("invalid jwt format")
	}

	headerJSON, err := base64.RawURLEncoding.DecodeString(parts[0])
	if err != nil {
		return nil, err
	}

	var header map[string]any
	if err := json.Unmarshal(headerJSON, &header); err != nil {
		return nil, err
	}

	// ФАТАЛЬНАЯ ОШИБКА: если alg == none, наивный код пропускает проверку подписи!
	if alg, ok := header["alg"].(string); ok && strings.ToLower(alg) == "none" {
		payloadJSON, _ := base64.RawURLEncoding.DecodeString(parts[1])
		var claims map[string]any
		_ = json.Unmarshal(payloadJSON, &claims)
		return claims, nil
	}

	return nil, errors.New("signature verification required")
}

// SecureJWTParser защищен: использует жесткий whitelist методов (только HS256)
func SecureJWTParser(tokenStr string, hmacSecret []byte) (jwt.MapClaims, error) {
	token, err := jwt.Parse(tokenStr, func(token *jwt.Token) (any, error) {
		// Дополнительная валидация интерфейса алгоритма
		if _, ok := token.Method.(*jwt.SigningMethodHMAC); !ok {
			return nil, fmt.Errorf("unexpected signing method: %v", token.Header["alg"])
		}
		return hmacSecret, nil
	},
		// КРИТИЧЕСКАЯ ЗАЩИТА: разрешаем СТРОГО белый список методов
		jwt.WithValidMethods([]string{"HS256"}),
	)

	if err != nil {
		return nil, fmt.Errorf("token validation failed: %w", err)
	}

	if claims, ok := token.Claims.(jwt.MapClaims); ok && token.Valid {
		return claims, nil
	}

	return nil, errors.New("invalid token")
}

func main() {
	secretKey := []byte("ProductionSuperSecretKey2026")

	// 1. Атакующий формирует поддельный токен с "alg": "none"
	maliciousHeader := `{"alg":"none","typ":"JWT"}`
	maliciousPayload := `{"sub":"attacker","role":"superuser","is_admin":true}`

	b64Hdr := base64.RawURLEncoding.EncodeToString([]byte(maliciousHeader))
	b64Pay := base64.RawURLEncoding.EncodeToString([]byte(maliciousPayload))

	// В токене нет подписи (заканчивается точкой):
	attackToken := fmt.Sprintf("%s.%s.", b64Hdr, b64Pay)

	fmt.Println("=== 1. Поддельный неподписанный токен злоумышленника ===")
	fmt.Printf("Attack Token: %s\n\n", attackToken)

	// 2. Тестирование на уязвимом парсере
	claims, err := NaiveJWTParser(attackToken)
	if err == nil {
		fmt.Println("🚨 УЯЗВИМОСТЬ: NaiveJWTParser принял неподписанный токен!")
		fmt.Printf("Авторизован пользователь: %v (is_admin: %v)\n\n", claims["sub"], claims["is_admin"])
	}

	// 3. Тестирование на защищенном парсере с Whitelist методов
	fmt.Println("=== 2. Проверка через SecureJWTParser (Whitelist: [HS256]) ===")
	_, secErr := SecureJWTParser(attackToken, secretKey)
	if secErr != nil {
		fmt.Printf("🛡️ ЗАЩИТА СРАБОТАЛА: %v\n", secErr)
	} else {
		fmt.Println("Ошибка: токен прошел валидацию!")
	}
}
```

## Под капотом

В библиотеке `golang-jwt/jwt/v5` при передаче опции `jwt.WithValidMethods([]string{"HS256"})` парсер на первом шаге считывает заголовок токена и производит строгую проверку строкового равенства поля `"alg"` со списком разрешенных идентификаторов. Если значение не найдено в списке, библиотека немедленно прекращает выполнение до вызова пользовательского колбэка `keyFunc` и не выделяет ресурсы под криптографические операции.

## Подводные камни

1. **Проверка `alg == "none"` с учетом регистра:** Атакующие могут передать `"None"`, `"NONE"` или `"nOnE"`. Защита через проверку строки `header["alg"] != "none"` часто обходится сменой регистра. Белый список разрешенных алгоритмов — единственный надежный способ.
2. **Пустой `Keyfunc`:** Никогда не возвращайте `nil, nil` из функции получения ключа `keyFunc`.
3. **Игнорирование флага `token.Valid`:** Вызов `jwt.Parse` возвращает структуру токена, но проверка `token.Valid` является обязательной для подтверждения статуса валидности.

## На собеседовании

**Вопрос с собеседования в Wildberries/Ozon:** «Как работает атака alg: none в протоколе JWT и почему она стала возможной на уровне архитектуры стандарта?»
**Ответ:** Стандарт RFC 7515 определил открытый заголовок JWS, в котором клиент передает серверу идентификатор алгоритма цифровой подписи, включая служебный алгоритм `none` (отсутствие подписи). В первых реализациях библиотек разработчики наивно проверяли поле `alg` из заголовка клиента: если клиент присылал `"alg": "none"`, парсер пропускал криптографическую проверку и доверял полезной нагрузке. Это позволяло любому пользователю подделать свои привилегии (например, подставить `admin: true`). Решение: никогда не доверять заголовку клиента и явно задавать на сервере строгий белый список алгоритмов (например, `jwt.WithValidMethods([]string{"RS256"})`).
