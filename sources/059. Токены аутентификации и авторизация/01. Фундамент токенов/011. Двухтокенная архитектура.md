# Двухтокенная архитектура: Short-Lived Access + Refresh Token

## Условие

Реализуйте пару: access token (15 мин) + refresh token (30 дней в БД с revocation). Это standard modern pattern.

### Исходная формулировка

**JWT short-lived access + refresh**: Реализуйте пару: access token (15 мин) + refresh token (30 дней в БД с revocation). Это standard modern pattern.

## Теория

Золотым отраслевым стандартом аутентификации в распределенных системах является **двухтокенная модель (Dual-Token Pattern: Access + Refresh Token)**:

### Архитектура компонентов:
1. **Access Token (Короткоживущий):**
   - Время жизни: **10–15 минут**.
   - Формат: Stateless JWT или PASETO.
   - Назначение: Передается в каждом запросе к API в заголовке `Authorization: Bearer <token>`. Проверяется микросервисами локально и автономно без запросов к базе данных.
   - Если токен перехвачен злоумышленником, ущерб ограничен окном в 15 минут.

2. **Refresh Token (Долгоживущий):**
   - Время жизни: **14–30 дней**.
   - Формат: Непрозрачный случайный криптографический токен (Opaque 256-bit token), сгенерированный через `crypto/rand`.
   - Хранение: Хранится в базе данных (в хешированном виде SHA-256) вместе с `user_id`, датой экспирации и флагом `revoked`.
   - Назначение: Используется **только** на специальном эндпоинте `/auth/refresh` для получения новой пары токенов.
   - **Refresh Token Rotation (RTR):** При каждом использовании старый refresh token инвалидируется, и клиенту выдается новый. Если старый токен попытаются использовать повторно, система фиксирует факт кражи и аннулирует всю цепочку сессий пользователя!

## Решение по шагам

1. Создадим структуры моделей `RefreshTokenRecord` для хранения сессий в БД.
2. Реализуем генератор короткоживущего Access Token на 15 минут с помощью `jwt.NewWithClaims`.
3. Реализуем генератор стойкого Refresh Token из 32 случайных байт с сохранением хеша в базе.
4. Разработаем эндпоинт `/auth/refresh` с поддержкой Refresh Token Rotation (RTR).
5. Продемонстрируем штатный сценарий обновления пары токенов и защиту от повторного использования скомпрометированного refresh токена.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

// RefreshTokenRecord представляет запись сессии в базе данных
type RefreshTokenRecord struct {
	TokenHash string
	UserID    string
	ExpiresAt time.Time
	Revoked   bool
}

type AuthManager struct {
	mu           sync.Mutex
	jwtSecret    []byte
	refreshStore map[string]*RefreshTokenRecord // tokenHash -> record
}

func NewAuthManager(jwtSecret []byte) *AuthManager {
	return &AuthManager{
		jwtSecret:    jwtSecret,
		refreshStore: make(map[string]*RefreshTokenRecord),
	}
}

type TokenPair struct {
	AccessToken  string `json:"access_token"`  // 15 минут
	RefreshToken string `json:"refresh_token"` // 30 дней
}

// IssueTokenPair выпускает новую пару токенов
func (m *AuthManager) IssueTokenPair(userID string) (*TokenPair, error) {
	// 1. Создаем короткоживущий Access Token (15 минут)
	accessClaims := jwt.MapClaims{
		"sub": userID,
		"exp": time.Now().Add(15 * time.Minute).Unix(),
		"iat": time.Now().Unix(),
	}
	accessObj := jwt.NewWithClaims(jwt.SigningMethodHS256, accessClaims)
	accessTokenStr, err := accessObj.SignedString(m.jwtSecret)
	if err != nil {
		return nil, err
	}

	// 2. Создаем криптостойкий Refresh Token (32 случайных байта)
	rawBytes := make([]byte, 32)
	if _, err := rand.Read(rawBytes); err != nil {
		return nil, err
	}
	refreshTokenStr := hex.EncodeToString(rawBytes)

	// Сохраняем в БД ТОЛЬКО SHA-256 хэш рефреш-токена!
	tokenHash := sha256.Sum256([]byte(refreshTokenStr))
	hashHex := hex.EncodeToString(tokenHash[:])

	m.mu.Lock()
	m.refreshStore[hashHex] = &RefreshTokenRecord{
		TokenHash: hashHex,
		UserID:    userID,
		ExpiresAt: time.Now().Add(30 * 24 * time.Hour), // 30 дней
		Revoked:   false,
	}
	m.mu.Unlock()

	return &TokenPair{
		AccessToken:  accessTokenStr,
		RefreshToken: refreshTokenStr,
	}, nil
}

// RefreshTokens реализует безопасную ротацию токенов (Refresh Token Rotation)
func (m *AuthManager) RefreshTokens(rawRefreshToken string) (*TokenPair, error) {
	tokenHash := sha256.Sum256([]byte(rawRefreshToken))
	hashHex := hex.EncodeToString(tokenHash[:])

	m.mu.Lock()
	record, exists := m.refreshStore[hashHex]
	if !exists {
		m.mu.Unlock()
		return nil, errors.New("refresh token не найден в базе")
	}

	// Защита от Replay: если токен уже был отозван ранее, возможно, он был украден!
	if record.Revoked {
		m.mu.Unlock()
		return nil, errors.New("SECURITY ALERT: попытка повторного использования отозванного токена!")
	}

	if time.Now().After(record.ExpiresAt) {
		m.mu.Unlock()
		return nil, errors.New("refresh token истек")
	}

	// Инвалидируем старый токен (Rotation)
	record.Revoked = true
	userID := record.UserID
	m.mu.Unlock()

	// Выпускаем совершенно новую пару токенов
	return m.IssueTokenPair(userID)
}

func main() {
	manager := NewAuthManager([]byte("JWT_HMAC_SECRET_KEY_2026"))

	fmt.Println("=== 1. Первичный логин пользователя ===")
	tokens, err := manager.IssueTokenPair("usr_10928")
	if err != nil {
		panic(err)
	}

	fmt.Printf("Access Token (15 мин):  %s...\n", tokens.AccessToken[:32])
	fmt.Printf("Refresh Token (30 дней): %s\n\n", tokens.RefreshToken)

	// 2. Штатное обновление пары токенов через 15 минут
	fmt.Println("=== 2. Ротация токенов на эндпоинте /auth/refresh ===")
	newTokens, err := manager.RefreshTokens(tokens.RefreshToken)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Новый Access Token:       %s...\n", newTokens.AccessToken[:32])
	fmt.Printf("Новый Refresh Token:      %s\n\n", newTokens.RefreshToken)

	// 3. Симуляция атаки перехвата старого refresh-токена
	fmt.Println("=== 3. Попытка повторного использования старого Refresh Token ===")
	_, attackErr := manager.RefreshTokens(tokens.RefreshToken)
	fmt.Printf("Результат: ❌ %v\n", attackErr)
}
```

## Под капотом

В базе данных PostgreSQL хранить сырой `refresh_token` категорически запрещено — при утечке дампа злоумышленник получит сессии всех пользователей. 
Всегда вычисляется `sha256.Sum256([]byte(refreshToken))` и сохраняется только хеш. Поиск в БД выполняется по индексу `CREATE INDEX idx_refresh_hash ON refresh_tokens(token_hash)`. При ротации статус обновляется через `UPDATE refresh_tokens SET revoked = true WHERE token_hash = $1`.

## Подводные камни

1. **Хранение Refresh Token в памяти без персистентности:** Если бэкенд перезапустится, все пользователи разлогинятся. Refresh токены обязаны сохраняться в персистентную СУБД (PostgreSQL / MySQL).
2. **Отсутствие ротации (Static Refresh Token):** Если refresh token не ротируется, то будучи однажды украденным с клиента, он дает злоумышленнику бессрочный доступ.
3. **Хранение Refresh Token в незащищенном виде на клиенте:** В веб-приложениях Refresh токен должен отдаваться в защищенной cookie `HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh`.

## На собеседовании

**Вопрос с собеседования в Авито/Wildberries:** «Что такое Refresh Token Rotation (RTR) и какую конкретную угрозу безопасности она устраняет?»
**Ответ:** Refresh Token Rotation — это механизм, при котором каждый раз, когда клиент обращается к эндпоинту `/auth/refresh` со старым refresh-токеном, сервер однократно инвалидирует его и возвращает совершенно новую пару (новый access + новый refresh token). 
Это решает проблему кражи долгоживущих токенов:
1. Если токен украден, но легитимный пользователь успел обновиться раньше, попытка атакующего использовать старый токен вызовет срабатывание алерта (повторное использование отозванного токена) и немедленную принудительную инвалидацию всей сессии пользователя.
2. Если атакующий использовал токен первым, легитимный пользователь при следующей попытке получит ошибку и сменит пароль, мгновенно выбив злоумышленника.
