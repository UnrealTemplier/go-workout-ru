# Анатомия JWT: создание и верификация с нуля без библиотек

## Условие

Без библиотек! Возьми строку `{"alg":"HS256"}` (заголовок) и `{"user_id":42}` (нагрузка). Закодируй обе части в Base64Url. Соедини через точку. Сгенерируй HMAC-SHA256 подпись от этой строки. Добавь подпись через точку. Напиши верификатор.

### Исходная формулировка

**Анатомия JWT**: Без библиотек! Возьми строку `{"alg":"HS256"}` (заголовок) и `{"user_id":42}` (нагрузка). Закодируй обе части в Base64Url. Соедини через точку. Сгенерируй HMAC-SHA256 подпись от этой строки. Добавь подпись третьей частью. Ты только что руками создал валидный JWT.

## Теория

Для глубокого понимания механики токенов каждый инженер обязан уметь собрать и проверить JWT, используя исключительно стандартную библиотеку языка Go (`crypto/hmac`, `crypto/sha256`, `crypto/subtle`, `encoding/base64`, `encoding/json`, `strings`).

### Алгоритм работы:
1. **Кодирование Header:** Преобразование JSON `{"alg":"HS256"}` в байты, затем кодирование через `base64.RawURLEncoding`.
2. **Кодирование Payload:** Преобразование JSON `{"user_id":42}` в байты, затем кодирование через `base64.RawURLEncoding`.
3. **Объединение:** `signingInput = headerB64 + "." + payloadB64`.
4. **Хеширование подписи:** 
   $$\text{mac} = \text{HMAC-SHA256}(\text{Secret}, \text{signingInput})$$
5. **Финальный токен:** `token = signingInput + "." + base64.RawURLEncoding.EncodeToString(mac)`.

### Алгоритм верификации:
1. Разбить токен по точке на 3 части: `parts = strings.Split(token, ".")`. Если частей не 3 — токен невалиден.
2. Собрать исходный `signingInput = parts[0] + "." + parts[1]`.
3. Вычислить ожидаемый HMAC от `signingInput`.
4. Декодировать подпись `parts[2]` из Base64URL.
5. Сравнить ожидаемую и полученную подписи через `subtle.ConstantTimeCompare`.
6. Распарсить полезную нагрузку из `parts[1]`.

## Решение по шагам

1. Создадим канонические строки заголовка `{"alg":"HS256"}` и полезной нагрузки `{"user_id":42}`.
2. Напишем функцию кодирования `BuildCustomJWT(header, payload, secret)`.
3. Напишем строгий верификатор `VerifyCustomJWT(token, secret) (map[string]any, error)`.
4. Проверим подлинный токен.
5. Продемонстрируем, как попытка изменить `user_id` с 42 на 99 приводит к отказу в валидации.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/base64"
	"encoding/json"
	"errors"
	"fmt"
	"strings"
)

// BuildPureJWT создает токен исключительно средствами стандартной библиотеки
func BuildPureJWT(headerJSON, payloadJSON string, secret []byte) string {
	// Шаг 1: Кодируем заголовок и нагрузку в Base64URL (без паддинга '=')
	hB64 := base64.RawURLEncoding.EncodeToString([]byte(headerJSON))
	pB64 := base64.RawURLEncoding.EncodeToString([]byte(payloadJSON))

	// Шаг 2: Соединяем через точку
	signingInput := hB64 + "." + pB64

	// Шаг 3: Генерируем HMAC-SHA256 подпись
	h := hmac.New(sha256.New, secret)
	h.Write([]byte(signingInput))
	sigBytes := h.Sum(nil)

	// Шаг 4: Кодируем подпись в Base64URL
	sigB64 := base64.RawURLEncoding.EncodeToString(sigBytes)

	// Шаг 5: Итоговый токен
	return signingInput + "." + sigB64
}

// VerifyPureJWT проверяет подлинность и возвращает claims без сторонних пакетов
func VerifyPureJWT(token string, secret []byte) (map[string]any, error) {
	parts := strings.Split(token, ".")
	if len(parts) != 3 {
		return nil, errors.New("неверный формат токена (ожидалось ровно 3 сегмента)")
	}

	signingInput := parts[0] + "." + parts[1]

	// Вычисляем эталонную подпись
	h := hmac.New(sha256.New, secret)
	h.Write([]byte(signingInput))
	expectedSig := h.Sum(nil)

	// Декодируем подпись из токена
	providedSig, err := base64.RawURLEncoding.DecodeString(parts[2])
	if err != nil {
		return nil, fmt.Errorf("ошибка декодирования подписи: %w", err)
	}

	// Сравнение в константное время
	if subtle.ConstantTimeCompare(expectedSig, providedSig) != 1 {
		return nil, errors.New("цифровая подпись не совпадает (токен скомпрометирован)")
	}

	// Декодируем и парсим Payload
	payloadBytes, err := base64.RawURLEncoding.DecodeString(parts[1])
	if err != nil {
		return nil, fmt.Errorf("ошибка декодирования payload: %w", err)
	}

	var claims map[string]any
	if err := json.Unmarshal(payloadBytes, &claims); err != nil {
		return nil, fmt.Errorf("ошибка парсинга payload json: %w", err)
	}

	return claims, nil
}

func main() {
	secret := []byte("MySuperSecretHMACKey_GoWorkout2026")

	headerStr := `{"alg":"HS256"}`
	payloadStr := `{"user_id":42}`

	fmt.Println("=== 1. Сборка JWT без библиотек (чистый Go) ===")
	token := BuildPureJWT(headerStr, payloadStr, secret)
	fmt.Printf("Сгенерированный токен:\n%s\n\n", token)

	// Верификация подлинного токена
	claims, err := VerifyPureJWT(token, secret)
	if err != nil {
		panic(err)
	}
	fmt.Printf("✅ Токен успешно верифицирован!\n")
	fmt.Printf("Извлеченные данные: user_id = %v\n\n", claims["user_id"])

	// 2. Демонстрация попытки подделки (Tampering Attack)
	fmt.Println("=== 2. Попытка подделки: злоумышленник меняет user_id на 99 ===")
	tamperedPayload := `{"user_id":99}`
	tamperedPB64 := base64.RawURLEncoding.EncodeToString([]byte(tamperedPayload))

	parts := strings.Split(token, ".")
	tamperedToken := parts[0] + "." + tamperedPB64 + "." + parts[2]

	_, tamperErr := VerifyPureJWT(tamperedToken, secret)
	fmt.Printf("Результат проверки поддельного токена:\n❌ Ошибка: %v\n", tamperErr)
}
```

## Под капотом

Встроенный пакет `crypto/hmac` реализует конструкцию HMAC по стандарту RFC 2104. При создании нового хэшера `hmac.New(sha256.New, secret)` ключ предварительно сжимается до 64 байт (размер блока SHA-256) или дополняется нулями. 
Затем выполняется внутреннее хеширование \(H(K \oplus \text{ipad} \parallel \text{data})\) и внешнее \(H(K \oplus \text{opad} \parallel \text{inner})\). 
Использование `subtle.ConstantTimeCompare` предотвращает утечку позиции первого несовпадающего байта через процессорный цикл.

## Подводные камни

1. **Использование `strings.Split(token, ".")` без проверки длины:** Если передать пустую строку или строку с одной точкой, обращение к `parts[2]` вызовет панику `index out of range`.
2. **Пропуск валидации `alg`:** Если токен сформирован вручную, верификатор также обязан проверять, что в декодированном заголовке поле `alg` равно в точности `"HS256"`.
3. **Отсутствие проверки срока действия (`exp`):** Подпись доказывает подлинность данных, но проверка актуальности времени жизни токена должна выполняться отдельно.

## На собеседовании

**Вопрос с собеседования в Ozon/Т-Банк:** «Как работает криптографическая проверка подписи HMAC-SHA256 в JWT под капотом, и почему для сравнения подписей обязательно использовать Constant Time?»
**Ответ:** 
1. Сервер берет заголовок и полезную нагрузку токена (`headerB64.payloadB64`) и с помощью своего секретного ключа заново вычисляет значение HMAC-SHA256.
2. Полученный эталонный срез байт сравнивается с байтами подписи из токена.
3. Стандартная операция сравнения `bytes.Equal` или оператор `==` выполняют проверку побайтово слева направо и **немедленно прерывают цикл при первом несовпадающем байте**. 
4. Злоумышленник, замеряя время ответа сервера с микросекундной точностью, может поочередно угадать каждый байт правильной подписи (Timing Attack). 
5. Функция `subtle.ConstantTimeCompare` всегда выполняет сравнение всех байтов массива до конца через операцию побитового `XOR` и `OR`, выполняясь строго за одинаковое процессорное время независимо от содержимого.
