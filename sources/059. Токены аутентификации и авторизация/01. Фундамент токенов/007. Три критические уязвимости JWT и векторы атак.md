# Три критические уязвимости JWT и векторы атак

## Условие

Покажите 3 критических атаки:
* `alg: none` bypass
* Algorithm confusion (RS256 → HS256)
* JKU/X5U header injection

### Исходная формулировка

**JWT алгоритмы и атаки**: Покажите 3 критических атаки:
* `alg: none` bypass
* Algorithm confusion (RS256 → HS256)
* JKU/X5U header injection

## Теория

Протокол JWT проектировался с избыточной гибкостью («Cipher Agility»), что открыло простор для целого семейства атак:

### 1. Атака `alg: none` (Обход подписи)
Атакующий подменяет алгоритм на `none` и удаляет подпись. Уязвимые серверы считают, что проверять подпись не требуется, и безоговорочно доверяют подделанному токену.

### 2. Algorithm Confusion (RS256 \(\rightarrow\) HS256)
Сервер ожидает токены, подписанные асимметричным ключом RS256, и публикует открытый ключ RSA. Атакующий подписывает токен симметричным HMAC-SHA256, используя публичный ключ RSA в качестве секрета. Уязвимый сервер берет открытый ключ и проверяет токен как HMAC, предоставляя права администратора.

### 3. JKU / X5U Header Injection (Подмена источника ключей)
Заголовки JWS поддерживают параметры:
- `jku` (JWK Set URL): URL, с которого сервер должен загрузить набор публичных ключей JWKS.
- `x5u` (X.509 URL): URL сертификата открытого ключа.
- **Вектор атаки:** Атакующий разворачивает собственный вредоносный веб-сервер (`https://attacker.com/jwks.json`), генерирует собственную пару ключей, подписывает токен своим приватным ключом, а в заголовок JWT внедряет `"jku": "https://attacker.com/jwks.json"`. Если сервер без проверки SSRF идет по ссылке `jku`, он скачивает ключ злоумышленника и успешно валидирует токен!

## Решение по шагам

1. Создадим макеты 3 атак:
   - Атака 1: токен с `alg: none`.
   - Атака 2: токен с алгоритмической путаницей RS256 -> HS256.
   - Атака 3: токен с вредоносным заголовком `jku`.
2. Реализуем комплексный защищенный валидатор `HardenedJWTValidator`.
3. Заблокируем `alg: none` белым списком методов.
4. Заблокируем путаницу алгоритмов проверкой конкретного типа интерфейса ключа.
5. Заблокируем JKU-инъекцию полным запретом недоверенных URL или отказом от динамического `jku`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"errors"
	"fmt"
	"net/url"
	"strings"

	"github.com/golang-jwt/jwt/v5"
)

type HardenedJWTValidator struct {
	trustedRSAPublicKey *rsa.PublicKey
	allowedJKUHosts     map[string]bool
}

func NewHardenedJWTValidator(pubKey *rsa.PublicKey) *HardenedJWTValidator {
	return &HardenedJWTValidator{
		trustedRSAPublicKey: pubKey,
		allowedJKUHosts: map[string]bool{
			"auth.company.corp": true, // Строгий белый список доменов для JKU!
		},
	}
}

// ValidateToken проверяет токен с защитой от всех 3 векторов атак
func (v *HardenedJWTValidator) ValidateToken(tokenStr string) (jwt.MapClaims, error) {
	token, err := jwt.Parse(tokenStr, func(t *jwt.Token) (any, error) {
		// --- ЗАЩИТА 1: Отражение атаки 'alg: none' и Algorithm Confusion ---
		if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {
			return nil, fmt.Errorf("ATTACK DETECTED: запрещенный метод подписи '%v'", t.Header["alg"])
		}

		// --- ЗАЩИТА 3: Отражение JKU / X5U Header Injection ---
		if rawJKU, ok := t.Header["jku"].(string); ok {
			parsedURL, err := url.Parse(rawJKU)
			if err != nil || !v.allowedJKUHosts[parsedURL.Hostname()] {
				return nil, fmt.Errorf("ATTACK DETECTED: недоверенный или вредоносный JKU источник '%s'", rawJKU)
			}
		}

		// Возвращаем строго типизированный публичный ключ RSA
		return v.trustedRSAPublicKey, nil
	},
		// Фильтрация разрешенных алгоритмов на этапе парсинга
		jwt.WithValidMethods([]string{"RS256"}),
	)

	if err != nil {
		return nil, err
	}

	if claims, ok := token.Claims.(jwt.MapClaims); ok && token.Valid {
		return claims, nil
	}

	return nil, errors.New("invalid token")
}

func main() {
	rsaKey, _ := rsa.GenerateKey(rand.Reader, 2048)
	validator := NewHardenedJWTValidator(&rsaKey.PublicKey)

	fmt.Println("=== Тестирование защищенного валидатора JWT против 3 атак ===")

	// 1. Атака 'alg: none'
	tokenNone := "eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJhZG1pbiJ9."
	_, err1 := validator.ValidateToken(tokenNone)
	fmt.Printf("1. Атака 'alg: none':\n   Блокировка: %v\n\n", err1 != nil)

	// 2. Атака Algorithm Confusion (RS256 -> HS256)
	tokenConfusionObj := jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{"sub": "hacker"})
	tokenConfusion, _ := tokenConfusionObj.SignedString([]byte("dummy_key"))
	_, err2 := validator.ValidateToken(tokenConfusion)
	fmt.Printf("2. Атака Algorithm Confusion (HS256 вместо RS256):\n   Блокировка: %v\n\n", err2 != nil)

	// 3. Атака JKU Header Injection
	tokenJKUObj := jwt.NewWithClaims(jwt.SigningMethodRS256, jwt.MapClaims{"sub": "intruder"})
	tokenJKUObj.Header["jku"] = "https://evil-attacker.ru/jwks.json" // Инъекция чужого URL
	tokenJKU, _ := tokenJKUObj.SignedString(rsaKey)

	_, err3 := validator.ValidateToken(tokenJKU)
	fmt.Printf("3. Атака JKU Injection (недоверенный jku evil-attacker.ru):\n   Блокировка: %v\n", err3 != nil)
}
```

## Под капотом

Заголовок `jku` (JWK Set URL) опасен тем, что провоцирует уязвимость **Server-Side Request Forgery (SSRF)**. Если бэкенд автоматически скачивает ключи по URL из заголовка токена, злоумышленник может направить сервер на чтение внутренних сервисов инфраструктуры (`http://169.254.169.254/latest/meta-data/` в AWS или внутренний Kubernetes DNS `http://vault.internal`). 
Защита заключается либо в полном игнорировании `jku`/`x5u`, либо в проверке хоста по строгому статическому whitelist.

## Подводные камни

1. **Слепое скачивание `jku` без валидации протокола:** Атакующий может передать схему `file:///etc/passwd` или `gopher://`, что приведет к компрометации файловой системы сервера.
2. **Парсинг URL без проверки Hostname:** Не используйте `strings.Contains(jku, "company.com")` — атакующий зарегистрирует домен `company.com.attacker.net` и обойдет наивную проверку.
3. **Разрешение нескольких методов без разделения ключей:** Не используйте один и тот же секрет для HMAC и RSA.

## На собеседовании

**Вопрос с собеседования в Касперский/VK:** «Что такое атака JKU Header Injection в JWT и к какому классу системных уязвимостей она приводит?»
**Ответ:** Параметр `jku` (JWK Set URL) в заголовке JWT указывает серверу адрес, с которого следует скачать открытый ключ для проверки подписи токена. Если сервер автоматически обращается по переданному URL:
1. **Подделка токенов:** Злоумышленник указывает свой собственный сервер с подконтрольным ключом и подписывает любые токены.
2. **SSRF (Server-Side Request Forgery):** Злоумышленник может указать внутренний IP-адрес облачной инфраструктуры (например, AWS Metadata API `169.254.169.254`) или внутренние микросервисы Kubernetes, заставив бэкенд скачивать данные из защищенного периметра.
Защита: никогда не доверять `jku` от клиента, использовать жестко зашитый в конфигурацию URL собственного JWKS-сервера компании.
