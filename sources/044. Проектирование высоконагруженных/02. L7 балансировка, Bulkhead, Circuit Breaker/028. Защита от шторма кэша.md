# Защита от шторма кэша (Thundering Herd / Cache Stampede) с помощью singleflight.Group

## Условие

**Singleflight (Шторм кэша / Thundering Herd)**: Кэш инвалидировался. Тысяча клиентов одновременно запрашивает один тяжелый SQL-запрос. База данных ложится. Используй пакет `golang.org/x/sync/singleflight`. Оберни вызов к БД. Убедись, что если 1000 горутин обращаются одновременно, реальный SQL-запрос выполнится ровно **один** раз, а результат раздастся всем тысяче ожидающих.

## Теория

Проблема Thundering Herd (Собачья свора / Шторм кэша):
- В 12:00:00 истекает TTL ключа популярного товара `product:iphone-16` в Redis.
- В ту же миллисекунду на сайт поступает 1 000 параллельных запросов от пользователей.
- Все 1 000 горутин видят Cache Miss в Redis.
- Все 1 000 горутин одновременно шлют тяжелый аналитический SQL-запрос в PostgreSQL!
- Процессор СУБД подскакивает до 100%, база встает в дедлок.
- **Решение через `singleflight.Group`:**
  - Метод `sf.Do(key, fn)` подавляет параллельное выполнение одинаковых функций.
  - Первый запрос идет в базу данных.
  - Остальные 999 параллельных горутин блокируются и ждут завершения первого запроса.
  - Когда ответ получен, он **мультиплексируется всем 1000 горутинам**!
  - База данных получает **ровно 1 запрос** вместо 1 000!

## Решение по шагам

1. Создайте группу схлопывания запросов `SingleflightManager`.
2. Запустите 100 параллельных горутин, одновременно запрашивающих один и тот же ключ.
3. Докажите, что счетчик обращений к реальной СУБД равен ровно 1.
4. Верифицируйте идентичность полученных данных у всех участников.

## Код решения

**`singleflight_thundering_herd_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type CallResult struct {
	wg  sync.WaitGroup
	val interface{}
	err error
}

type SafeSingleflightGroup struct {
	mu sync.Mutex
	m  map[string]*CallResult
}

func (g *SafeSingleflightGroup) Do(key string, fn func() (interface{}, error)) (interface{}, error) {
	g.mu.Lock()
	if g.m == nil {
		g.m = make(map[string]*CallResult)
	}
	if c, exists := g.m[key]; exists {
		g.mu.Unlock()
		c.wg.Wait() // Ожидание выполнения первого параллельного запроса
		return c.val, c.err
	}

	c := new(CallResult)
	c.wg.Add(1)
	g.m[key] = c
	g.mu.Unlock()

	c.val, c.err = fn()
	c.wg.Done()

	g.mu.Lock()
	delete(g.m, key)
	g.mu.Unlock()

	return c.val, c.err
}

func TestSingleflightThunderingHerd(t *testing.T) {
	var sf SafeSingleflightGroup
	var actualDatabaseQueries int64

	heavyQuery := func() (interface{}, error) {
		atomic.AddInt64(&actualDatabaseQueries, 1)
		time.Sleep(25 * time.Millisecond) // Имитация тяжелого SQL-запроса
		return "Product: Ноутбук Pro M3 Max (В наличии: 5 шт)", nil
	}

	const concurrentGoroutines = 100
	var wg sync.WaitGroup
	wg.Add(concurrentGoroutines)

	for i := 0; i < concurrentGoroutines; i++ {
		go func() {
			defer wg.Done()
			val, err := sf.Do("product:m3_max", heavyQuery)
			if err != nil || val != "Product: Ноутбук Pro M3 Max (В наличии: 5 шт)" {
				t.Errorf("Некорректный результат: %v", val)
			}
		}()
	}

	wg.Wait()

	if actualDatabaseQueries != 1 {
		t.Fatalf("Сбой Singleflight: в БД ушло %d запросов вместо 1!", actualDatabaseQueries)
	}

	fmt.Println("Подавление шторма кэша (Singleflight Thundering Herd) подтверждено:")
	fmt.Printf("  • Параллельных горутин обратилось: %d\n", concurrentGoroutines)
	fmt.Printf("  • Реальных запросов отправлено в БД: %d (100%% защита от перегрузки)\n", actualDatabaseQueries)
	fmt.Println("  • Все 100 горутин получили готовый результат одного единственного запроса")
}
```

## Под капотом

В `golang.org/x/sync/singleflight` вызов `sf.DoChan()` возвращает канал с каналом завершения `<-chan Result`, что позволяет применять `select` с контекстом запроса: если один из ожидающих клиентов отменил HTTP-запрос по таймауту, остальные клиенты продолжат ожидать ответ СУБД.

## Подводные камни

Мутировать полученный указатель: если `fn` возвращает указатель `*Product`, все 1000 горутин получают ссылку на один и тот же адрес памяти. Изменение полей структуры вызовет Data Race. Возвращаемые объекты должны быть либо иммутабельными, либо глубоко копироваться.

## На собеседовании

**Вопрос с собеседования:** «Защищает ли singleflight от шторма кэша в кластере из 50 подов?»
**Ответ:** singleflight работает строго **внутри одного пода** Go. Если у вас 50 подов, в базу уйдет максимум 50 запросов (по 1 с каждого пода) вместо 50 000, что СУБД легко выдержит. Для абсолютного ограничения до 1 запроса на весь кластер используют распределенный замок Redis (`SET lock_key uuid NX EX 10`).
