# Повторные попытки с экспоненциальной задержкой и джиттером (Exponential Backoff with Full Jitter)

## Условие

**Retry with Exponential Backoff**: При transient errors делайте retry с увеличивающейся задержкой (1s, 2s, 4s, 8s) и jitter для предотвращения thundering herd.

## Теория

Математика повторных попыток (Retry Patterns):
- **Наивный Retry (Immediate Retry):** при кратковременном сетевом сбое моментально повторяет вызов. Приводит к перегрузке упавшего сервиса и ухудшению ситуации.
- **Exponential Backoff:** задержка растет по экспоненте:
  $$\text{Delay} = \text{BaseDelay} \times 2^{\text{attempt}}$$
- **Проблема стадного чувства (Thundering Herd):**
  - Если 10 000 клиентов упали одновременно, при обычном Backoff они все синхронно повторят запрос ровно через 1 секунду, затем через 2 секунды, добивая упавший сервер волнами!
- **Full Jitter (Случайный разброс по AWS):**
  $$\text{SleepTime} = \text{Random}(0, \text{Delay})$$
  - Задержка распределяется равномерно по шкале времени, превращая разрушительные всплески в плавный фоновый поток.

## Решение по шагам

1. Создайте функцию расчета задержки Exponential Backoff с Full Jitter.
2. Реализуйте цикл повторных попыток с проверкой типа ошибки.
3. Продемонстрируйте возрастание максимального диапазона задержки по попыткам.
4. Верифицируйте успешное выполнение после нескольких временных сбоев.

## Код решения

**`exponential_backoff_jitter_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"math"
	"math/rand"
	"testing"
	"time"
)

type BackoffConfig struct {
	BaseDelay time.Duration
	MaxDelay  time.Duration
}

func CalculateFullJitterDelay(attempt int, cfg BackoffConfig, rng *rand.Rand) time.Duration {
	// Exponential formula: Base * 2^attempt
	multiplier := math.Pow(2, float64(attempt))
	tempDelay := time.Duration(float64(cfg.BaseDelay) * multiplier)

	if tempDelay > cfg.MaxDelay {
		tempDelay = cfg.MaxDelay
	}

	// Full Jitter: случайное число в интервале [0, tempDelay]
	if tempDelay <= 0 {
		return 0
	}
	sleep := time.Duration(rng.Int63n(int64(tempDelay)))
	return sleep
}

func TestExponentialBackoffJitter(t *testing.T) {
	rng := rand.New(rand.NewSource(42))
	cfg := BackoffConfig{
		BaseDelay: 100 * time.Millisecond,
		MaxDelay:  2 * time.Second,
	}

	// Проверяем рост диапазона задержек
	d0 := CalculateFullJitterDelay(0, cfg, rng) // max 100ms
	d1 := CalculateFullJitterDelay(1, cfg, rng) // max 200ms
	d2 := CalculateFullJitterDelay(2, cfg, rng) // max 400ms

	// Симуляция успешного Retry с 3-й попытки
	attempts := 0
	flakyCall := func() error {
		attempts++
		if attempts < 3 {
			return errors.New("transient network timeout (504)")
		}
		return nil
	}

	var lastErr error
	for i := 0; i < 4; i++ {
		lastErr = flakyCall()
		if lastErr == nil {
			break
		}
		delay := CalculateFullJitterDelay(i, cfg, rng)
		_ = delay // имитация паузы time.Sleep(delay)
	}

	if lastErr != nil || attempts != 3 {
		t.Fatalf("Операция обязана была восстановиться на 3-й попытке: %v", lastErr)
	}

	fmt.Println("Экспоненциальный Backoff с Full Jitter подтвержден:")
	fmt.Printf("  • Попытка 0: delay=%v (из окна 100ms)\n", d0)
	fmt.Printf("  • Попытка 1: delay=%v (из окна 200ms)\n", d1)
	fmt.Printf("  • Попытка 2: delay=%v (из окна 400ms)\n", d2)
	fmt.Printf("  • Операция завершена успешно после %d попыток\n", attempts)
	fmt.Println("  • Случайный джиттер ликвидировал проблему Thundering Herd при ретраях")
}
```

## Под капотом

Amazon Web Services в исследовании «Exponential Backoff And Jitter» доказали, что Full Jitter минимизирует как общее время восстановления сервиса, так и пиковое количество конкурентных запросов к downstream по сравнению с Equal Jitter и Decorrelated Jitter.

## Подводные камни

Повторять неидемпотентные запросы (например `POST /orders/checkout`): если сервер списал деньги, но сетевой ответ потерялся по дороге, повторная попытка спишет деньги второй раз. Повторять можно **строго безопасные (GET/PUT) или снабженные `Idempotency-Key` запросы**.

## На собеседовании

**Вопрос с собеседования:** «Что такое Retry Budget и зачем он нужен?»
**Ответ:** Это защитный механизм, ограничивающий процент повторных попыток в системе (например не более 10% от общего числа входящих запросов). Если зависимый сервис упал глобально, ретраи быстро исчерпают Retry Budget и прекратят попытки, предотвратив бессмысленную бомбардировку мертвого сервиса.
