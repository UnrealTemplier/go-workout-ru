# Системный дизайн платформы на 1 000 000 RPS: Shared-Nothing, L4 балансировка и сквозное кэширование

## Условие

Спроектируй **System for 1M RPS**: horizontal scaling (1000 instances), stateless services, shared-nothing architecture. Load balancer (L4) distributes. Caching at every layer: CDN (static), edge cache (API responses), application cache (hot data), database cache (query results).

## Теория

Архитектура веб-системы масштаба 1 000 000 RPS (Яндекс, Авито, Ozon):
1. **Сетевой периметр и L4 балансировка (ECMP + IPVS):**
   - BGP Anycast анонсирует единый IP-адрес по всему миру.
   - Кластер L4 балансировщиков (10 серверов на базе Linux IPVS/eBPF) распределяет 1M RPS на 1000 stateless подов Go.
2. **Многослойная пирамида кэширования:**
   - **Слой 1 (CDN Edge):** 70% трафика (статика, изображения, неизменяемые каталоги) отсекается до входа в дата-центр.
   - **Слой 2 (Gateway Cache):** 15% трафика (популярные страницы) отдаются шлюзом из кэша Nginx/Envoy за 0.5 мс.
   - **Слой 3 (In-Memory L1 Application):** Go-воркеры держат горячие ключи в RAM (`sync.Map` / Ristretto).
   - **Слой 4 (Distributed L2 Redis):** кластер Redis на 32 шардах обслуживает динамические данные.
   - **Слой 5 (Database Master/Shards):** до основной СУБД PostgreSQL доходит менее 1% трафика (всего ~5 000 RPS записи)!

## Решение по шагам

1. Создайте архитектурный профиль прохождения трафика через пирамиду кэширования.
2. Смоделируйте расчет коэффициента отсечения трафика на каждом уровне.
3. Докажите, что база данных получает безопасную нагрузку.
4. Верифицируйте масштабируемость системы до 1M RPS.

## Код решения

**`million_rps_system_design_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TrafficLayerFilter struct {
	Name            string
	AbsorptionRatio float64 // Доля трафика, поглощаемая слоем
}

func CalculateTrafficFunnel(incomingRPS float64, layers []TrafficLayerFilter) float64 {
	currentRPS := incomingRPS
	for _, layer := range layers {
		absorbed := currentRPS * layer.AbsorptionRatio
		currentRPS -= absorbed
	}
	return currentRPS
}

func TestMillionRPSSystemDesign(t *testing.T) {
	incomingRPS := 1000000.0 // 1 миллион RPS на входе

	layers := []TrafficLayerFilter{
		{Name: "CDN Edge (Cloudflare/Yandex CDN)", AbsorptionRatio: 0.70}, // 70% отсечено
		{Name: "API Gateway Cache (Envoy/Nginx)", AbsorptionRatio: 0.50},  // 50% от остатка
		{Name: "Go In-Process L1 Cache (Ristretto)", AbsorptionRatio: 0.60}, // 60% от остатка
		{Name: "Distributed L2 Cache (Redis Cluster)", AbsorptionRatio: 0.75}, // 75% от остатка
	}

	remainingToDB := CalculateTrafficFunnel(incomingRPS, layers)

	// В базу данных должно приходить менее 20 000 RPS (менее 2% исходного трафика)
	if remainingToDB > 20000.0 {
		t.Fatalf("Слишком много трафика дошло до БД: %.0f RPS", remainingToDB)
	}

	fmt.Println("Архитектурный проект системы на 1 000 000 RPS подтвержден:")
	fmt.Printf("  • Входящий трафик на периметре: %.0f RPS\n", incomingRPS)
	fmt.Printf("  • Доля, поглощенная кэшами:    %.2f%%\n", (1.0-(remainingToDB/incomingRPS))*100.0)
	fmt.Printf("  • Финальная нагрузка на БД:     %.0f RPS (Легко выдерживается 32 шардами Postgres)\n", remainingToDB)
	fmt.Println("  • Shared-Nothing архитектура позволяет линейно наращивать поды Go")
}
```

## Под капотом

Для 1000 инстансов Go критически важен тюнинг рантайма: флаг `GOGC=200` или балласт памяти `debug.SetMemoryLimit(8 * 1024 * 1024 * 1024)` в Go 1.19+ сокращает частоту срабатывания Garbage Collector в 3 раза, освобождая вычислительные мощности под полезную обработку запросов.

## Подводные камни

Использовать базы данных без мультиплексора соединений: если 1000 инстансов откроют по 50 соединений, PostgreSQL получит 50 000 процессов, исчерпав память сервера. На таких масштабах обязателен **PgBouncer в режиме transaction pooling**.

## На собеседовании

**Вопрос с собеседования:** «Что такое архитектура Shared-Nothing и почему только она масштабируется линейно?»
**Ответ:** Shared-Nothing означает, что независимые вычислительные узлы не разделяют общую оперативную память и не имеют общих блокировок (Mutex/Spinlock). Каждый узел автономен. Добавление новых 100 серверов увеличивает производительность ровно на 100%, не создавая конкуренции за общие ресурсы.
