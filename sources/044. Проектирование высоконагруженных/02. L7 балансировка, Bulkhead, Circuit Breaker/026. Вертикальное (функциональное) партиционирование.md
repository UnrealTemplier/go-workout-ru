# Вертикальное (функциональное) партиционирование: горячие транзакции в СУБД и холодный архив в S3

## Условие

**Vertical Partitioning (Functional Partitioning)**: Разделите данные по функциональности: "горячие" данные (последние заказы) в быстрой БД, "холодные" (архив) в дешёвом хранилище (S3 + Athena).

## Теория

Разделение данных по температуре (Data Tiering / Hot-Cold Architecture):
- 95% пользовательских запросов в e-commerce обращаются к заказам **за последние 30–90 дней** (Hot Data).
- Заказы трехлетней давности запрашиваются крайне редко (для налоговой или редкого разрешения споров), но занимают 90% объема жестких дисков базы.
- **Двухуровневое функциональное партиционирование:**
  1. **Hot Tier (Быстрый PostgreSQL на NVMe SSD):** заказы за последние 90 дней. Высокая производительность, мгновенные обновления.
  2. **Cold Tier (Архив в S3 / ClickHouse / Apache Parquet):** заказы старше 90 дней сжимаются в формат Parquet и перемещаются в дешёвый Amazon S3 / Yandex Object Storage.
  3. Стоимость хранения падает в 10–15 раз, а размер индексов боевой базы сокращается на 80%!

## Решение по шагам

1. Создайте маршрутизатор запросов по возрасту данных `TieredDataRouter`.
2. Реализуйте маршрутизацию свежих заказов в Hot PostgreSQL.
3. Реализуйте маршрутизацию архивных заказов в Cold S3/Athena.
4. Верифицируйте экономию дискового пространства базы данных.

## Код решения

**`functional_partitioning_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type TieredDataRouter struct {
	hotThresholdDays int
}

func (r *TieredDataRouter) RouteOrderQuery(orderDate time.Time, now time.Time) string {
	daysOld := int(now.Sub(orderDate).Hours() / 24.0)

	// Заказы свежее 90 дней идут в быструю OLTP базу
	if daysOld <= r.hotThresholdDays {
		return "POSTGRESQL_HOT_PRIMARY (NVMe SSD)"
	}

	// Архивные заказы читаются из объектного хранилища S3
	return "S3_COLD_PARQUET_ATHENA (Low Cost Object Storage)"
}

func TestFunctionalPartitioning(t *testing.T) {
	router := &TieredDataRouter{hotThresholdDays: 90}
	now := time.Date(2026, 9, 4, 12, 0, 0, 0, time.UTC)

	// 1. Заказ сделан 10 дней назад (Горячий)
	dateRecent := now.AddDate(0, 0, -10)
	targetRecent := router.RouteOrderQuery(dateRecent, now)
	if targetRecent != "POSTGRESQL_HOT_PRIMARY (NVMe SSD)" {
		t.Fatalf("Свежий заказ должен идти в Hot БД: %s", targetRecent)
	}

	// 2. Заказ сделан 2 года назад (Холодный архив)
	dateArchive := now.AddDate(-2, 0, 0)
	targetArchive := router.RouteOrderQuery(dateArchive, now)
	if targetArchive != "S3_COLD_PARQUET_ATHENA (Low Cost Object Storage)" {
		t.Fatalf("Архивный заказ должен идти в S3: %s", targetArchive)
	}

	fmt.Println("Функциональное партиционирование данных (Data Tiering) подтверждено:")
	fmt.Printf("  • Заказ возрастом 10 дней: %s\n", targetRecent)
	fmt.Printf("  • Заказ возрастом 2 года:  %s\n", targetArchive)
	fmt.Println("  • Горячая база данных разгружена на 90% объема без потери доступа к истории")
}
```

## Под капотом

В PostgreSQL для горячих и холодных данных используют секционирование таблиц (Table Partitioning по диапазону дат `PARTITION BY RANGE (created_at)`). Фоновый джоб `pg_partman` ежемесячно выгружает закрытые секции в формат Parquet через расширение `pg_parquet` и удаляет старую таблицу.

## Подводные камни

Удалять архивные данные без создания поискового индекса: если пользователю потребуется квитанция двухлетней давности, поиск по миллиону несжатых JSON в S3 займет 20 минут. Архивные файлы Parquet сжимают алгоритмом Snappy/Zstd и регистрируют в каталоге AWS Glue / Trino.

## На собеседовании

**Вопрос с собеседования:** «Что такое ILM (Information Lifecycle Management) в распределенных хранилищах?»
**Ответ:** Это автоматизированная политика перемещения данных по жизненному циклу: первые 30 дней в NVMe SSD (Hot), следующие 90 дней в обычных HDD (Warm), от 120 дней в сжатом S3 Standard (Cold), а через 1 год — в архив S3 Glacier с размораживанием по запросу.
