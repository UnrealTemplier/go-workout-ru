# Паттерн переборки (Bulkhead Pattern): изоляция пулов ресурсов и защита от каскадных сбоев

## Условие

**Bulkhead Pattern**: Изолируйте ресурсы для разных клиентов/тенантов (separate thread pools, connection pools), чтобы падение одного не уронило всю систему.

## Теория

Морская метафора отсеков корабля (Bulkhead Pattern):
- Корпус подводной лодки или титаника разделен водонепроницаемыми переборками (отсеками). Если один отсек пробит и затоплен, корабль остается на плаву.
- **В программной инженерии:**
  - Если все внешние вызовы используют общий пул горутин или соединений с БД:
  - Зависший вызов платежного шлюза банка «А» исчерпает все 500 коннектов пула.
  - Ни один другой запрос (даже обычный просмотр каталога) не сможет выполниться!
- **Реализация Bulkhead:**
  - Каждый downstream-сервис или тенант получает **изолированный семафор ограниченной емкости**:
    - `BankASemaphore`: макс. 20 одновременных горутин.
    - `BankBSemaphore`: макс. 20 одновременных горутин.
    - `CatalogPool`: 100 горутин.
  - Авария в банке «А» затронет максимум 20 горутин, а остальные 96% мощностей сервиса продолжат работу!

## Решение по шагам

1. Создайте семафор отсека `BulkheadCompartment`.
2. Реализуйте метод `Execute` с быстрым отказом при исчерпании лимита отсека.
3. Смоделируйте перегрузку отсека зависшими операциями.
4. Докажите, что соседний изолированный отсек обслуживается без задержек.

## Код решения

**`bulkhead_isolation_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type BulkheadCompartment struct {
	name    string
	sema    chan struct{}
	maxSize int
}

func NewBulkhead(name string, maxConcurrent int) *BulkheadCompartment {
	return &BulkheadCompartment{
		name:    name,
		sema:    make(chan struct{}, maxConcurrent),
		maxSize: maxConcurrent,
	}
}

func (b *BulkheadCompartment) Execute(task func() error) error {
	// Неблокирующий захват слота в отсеке
	select {
	case b.sema <- struct{}{}:
		defer func() { <-b.sema }()
		return task()
	default:
		return fmt.Errorf("bulkhead [%s] is full: rejected to isolate failure (503)", b.name)
	}
}

func TestBulkheadIsolation(t *testing.T) {
	// Отсек внешнего шлюза банка A (лимит всего 2 слота)
	bulkheadBankA := NewBulkhead("Gateway-Bank-A", 2)
	// Отсек каталога товаров (лимит 10 слотов)
	bulkheadCatalog := NewBulkhead("Internal-Catalog", 10)

	// Заполняем отсек Банка А зависшими задачами
	_ = bulkheadBankA.Execute(func() error {
		// Захватываем слот 1
		return nil
	})

	// Симулируем постоянную занятость двух слотов Банка А
	bulkheadBankA.sema <- struct{}{}
	bulkheadBankA.sema <- struct{}{}

	// 3-й запрос к Банку А должен быть немедленно отсечен переборкой!
	errBankA := bulkheadBankA.Execute(func() error { return nil })
	if errBankA == nil {
		t.Fatal("Переполненный отсек Банка А обязан был отклонить запрос")
	}

	// При этом отсек каталога продолжает мгновенно отвечать!
	errCatalog := bulkheadCatalog.Execute(func() error { return nil })
	if errCatalog != nil {
		t.Fatalf("Каталог не должен страдать от падения Банка А: %v", errCatalog)
	}

	fmt.Println("Паттерн переборки (Bulkhead Pattern) успешно подтвержден:")
	fmt.Printf("  • Отсек Банка А:  %v\n", errBankA)
	fmt.Printf("  • Отсек Каталога: Запрос успешно выполнен (%v)\n", errCatalog == nil)
	fmt.Println("  • Сбой во внешней интеграции изолирован и не привел к падению всей системы")
}
```

ℹ️ Изоляция пулов ресурсов с помощью семафоров Bulkhead для защиты от каскадного коллапса

## Под капотом

В библиотеках устойчивости (Resilience4j, go-resilience) Bulkhead часто комбинируют с ограниченной очередью ожидания (Queue Size). Если семафор занят, запрос может подождать в очереди до 50 мс, но не дольше, предотвращая истощение пулов горутин.

## Подводные камни

Задавать слишком большой размер отсека: если у сервиса 20 зависимостей, и каждой выделить отсек по 100 слотов, суммарно сервер может породить тысячи зависших горутин и упереться в системные лимиты сокетов и дескрипторов файлов.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Bulkhead от Rate Limiter?»
**Ответ:** Rate Limiter контролирует **частоту запросов во времени** (Requests Per Second). Bulkhead контролирует **количество одновременно выполняемых задач в данный момент** (Concurrent In-Flight Requests). Rate Limiter защищает от перегрузки по трафику, а Bulkhead — от исчерпания потоков из-за зависших сетевых ответов.
