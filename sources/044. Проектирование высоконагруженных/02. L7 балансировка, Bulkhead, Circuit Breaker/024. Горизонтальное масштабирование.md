# Горизонтальное масштабирование (Horizontal Scaling): архитектура Stateless-сервисов

## Условие

**Horizontal Scaling**: Спроектируйте сервисы как stateless, чтобы можно было запускать N инстансов за load balancer'ом. State храните в Redis/PostgreSQL/Kafka.

## Теория

Принципы архитектуры Stateless (12-Factor App):
- Главное препятствие для горизонтального масштабирования — **локальное состояние в памяти процесса (In-Memory State)**:
  - Если сессия пользователя хранится в локальной мапе `map[sessionID]User` на Сервере №1:
  - Следующий запрос, направленный балансировщиком на Сервер №2, приведет к ошибке «Пользователь не авторизован».
- **Архитектура Shared-Nothing Stateless:**
  1. Экземпляры сервиса не хранят в памяти никакого клиентского состояния.
  2. Любой запрос от любого пользователя может быть обработан **любым из 100 инстансов**.
  3. Состояние сессий выносится в общий Redis Cluster.
  4. Транзакционные данные хранятся в PostgreSQL.
  5. События — в Apache Kafka.
  6. Добавление новых подов (`kubectl scale --replicas=50`) линейно увеличивает общую пропускную способность системы!

## Решение по шагам

1. Создайте модель сессионного хранилища во внешнем Redis.
2. Создайте три независимых экземпляра сервиса, разделяющих общее состояние.
3. Продемонстрируйте авторизацию на Сервере А и успешное обслуживание на Сервере Б.
4. Верифицируйте независимость экземпляров от локальной памяти.

## Код решения

**`stateless_horizontal_scaling_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SharedRedisSessionStore struct {
	sessions map[string]string // sessionToken -> userID
}

type StatelessAppInstance struct {
	InstanceID string
	store      *SharedRedisSessionStore
}

func (s *StatelessAppInstance) LoginUser(userID, token string) {
	s.store.sessions[token] = userID
}

func (s *StatelessAppInstance) GetCurrentUserID(token string) (string, bool) {
	uid, exists := s.store.sessions[token]
	return uid, exists
}

func TestStatelessHorizontalScaling(t *testing.T) {
	sharedRedis := &SharedRedisSessionStore{sessions: make(map[string]string)}

	// Запускаем 2 независимых пода за балансировщиком
	podA := &StatelessAppInstance{InstanceID: "pod-order-alpha", store: sharedRedis}
	podB := &StatelessAppInstance{InstanceID: "pod-order-bravo", store: sharedRedis}

	// 1. Пользователь логинится через Pod A
	podA.LoginUser("user-777", "token-xyz-secret")

	// 2. Следующий запрос балансировщик направляет на совершенно другой Pod B!
	uidFromB, isAuth := podB.GetCurrentUserID("token-xyz-secret")

	if !isAuth || uidFromB != "user-777" {
		t.Fatalf("Pod B должен был мгновенно распознать сессию: %s, auth=%v", uidFromB, isAuth)
	}

	fmt.Println("Горизонтальное масштабирование (Stateless Architecture) подтверждено:")
	fmt.Printf("  • Пользователь вошел через: %s\n", podA.InstanceID)
	fmt.Printf("  • Запрос успешно принят:   %s (UserID: %s)\n", podB.InstanceID, uidFromB)
	fmt.Println("  • Поды полностью взаимозаменяемы, сервис масштабируется до сотен реплик")
}
```

ℹ️ Вынесение состояния сессий во внешнее хранилище для обеспечения полной взаимозаменяемости подов

## Под капотом

В Stateless архитектуре любой под может быть уничтожен Kubelet (например при Spot Terminate или перебалансировке нод) без малейшего влияния на пользователей, так как следующее TCP-соединение будет обслужено соседней репликой без потери сессии.

## Подводные камни

Сохранять загруженные файлы пользователей (аватарки, сканы) на локальный диск пода (`/tmp/uploads`): при следующем запросе пользователя на просмотр файл не будет найден на соседнем поде, а при перезапуске пода удалится навсегда. Файлы выгружают **строго в объектное хранилище S3/MinIO**.

## На собеседовании

**Вопрос с собеседования:** «Что такое Sticky Sessions (привязка сессий к серверу) и почему в Cloud-Native архитектуре это считается антипаттерном?»
**Ответ:** Sticky Sessions заставляют балансировщик направлять все запросы конкретного пользователя на один и тот же под. Это нарушает равномерность балансировки (один под может быть перегружен 100 активными пользователями, пока другие простаивают) и приводит к сбросу сессий клиентов при плановом перезапуске подов.
