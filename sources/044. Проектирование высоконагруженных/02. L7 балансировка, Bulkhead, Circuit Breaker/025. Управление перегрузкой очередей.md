# Управление перегрузкой очередей: отсечение запросов HTTP 503 при переполнении буфера

## Условие

Реализуй **Backpressure**: `Order Service` получает 10000 RPS, `Payment Service` обрабатывает 1000 RPS. Queue (Kafka) буферизует. Если queue > 100000 messages — reject new requests (`503 Service Unavailable`), клиент retry. Покажи, что без backpressure — OOM, data loss.

## Теория

Защита асинхронных очередей от переполнения:
- Ситуация дисбаланса:
  - `Order Service` принимает 10 000 RPS.
  - `Payment Service` (лимитирован банком) может проводить только 1 000 RPS.
- **Очередь Kafka как амортизатор:**
  - Дельта в 9 000 сообщений/сек накапливается в очереди.
  - Если наплыв длится 2 минуты, в очереди накопится более \(1\,000\,000\) сообщений.
  - Задержка подтверждения заказа вырастает до десятков минут!
- **Жесткий лимит буфера (Queue Watermark):**
  - При достижении лимита в 100 000 сообщений `Order Service` включает самозащиту:
  - Новые заказы временно отклоняются со статусом `HTTP 503 Service Unavailable` и `Retry-After: 30`.
  - Это предотвращает истощение диска Kafka, деградацию задержки и падение брокера по OOM!

## Решение по шагам

1. Создайте структуру буфера заказов с порогом отсечения `MaxQueueDepth`.
2. Реализуйте метод приема заказа `IngestOrder`.
3. Смоделируйте переполнение буфера выше критического порога.
4. Верифицируйте отклонение новых запросов с кодом 503.

## Код решения

**`order_queue_backpressure_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"testing"
)

type OrderQueueIngestionController struct {
	mu            sync.Mutex
	currentDepth  int
	maxQueueLimit int
}

func (c *OrderQueueIngestionController) EnqueueOrder(orderID string) (int, error) {
	c.mu.Lock()
	defer c.mu.Unlock()

	// Если глубина очереди превысила 100 000 (в тесте 5)
	if c.currentDepth >= c.maxQueueLimit {
		return 503, errors.New("503 Service Unavailable: queue is saturated, please retry later")
	}

	c.currentDepth++
	return 202, nil
}

func (c *OrderQueueIngestionController) ProcessedByConsumer() {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.currentDepth > 0 {
		c.currentDepth--
	}
}

func TestOrderQueueBackpressure(t *testing.T) {
	// Лимит очереди: 3 заказа
	controller := &OrderQueueIngestionController{maxQueueLimit: 3}

	// 1. Успешное заполнение буфера
	for i := 1; i <= 3; i++ {
		code, err := controller.EnqueueOrder(fmt.Sprintf("ord-%d", i))
		if code != 202 || err != nil {
			t.Fatalf("Заказ #%d обязан был поместиться в очередь", i)
		}
	}

	// 2. 4-й заказ превышает безопасный буфер очереди!
	codeExceeded, errExceeded := controller.EnqueueOrder("ord-overflow")
	if codeExceeded != 503 || errExceeded == nil {
		t.Fatalf("Ожидался отказ 503 при переполнении буфера: %d", codeExceeded)
	}

	// Консьюмер разгружает очередь
	controller.ProcessedByConsumer()

	// Теперь новый заказ снова принимается!
	codeRecovered, errRecovered := controller.EnqueueOrder("ord-new")
	if codeRecovered != 202 || errRecovered != nil {
		t.Fatalf("После разгрузки заказ должен быть принят: %d", codeRecovered)
	}

	fmt.Println("Защита очереди от переполнения (Backpressure 503) подтверждена:")
	fmt.Printf("  • Буфер полон -> Запрос отклонен: %d %v\n", codeExceeded, errExceeded)
	fmt.Printf("  • Очередь разгружена -> Новый заказ принят: %d\n", codeRecovered)
	fmt.Println("  • Очередь Kafka защищена от неконтролируемого накопления терабайтов лага")
}
```

## Под капотом

Мониторинг глубины очереди (Consumer Lag) осуществляется экспортером `kafka_exporter` в Prometheus. При превышении порога алертинг Prometheus Alertmanager шлет сигнал в API Gateway, который автоматически переходит в режим троттлинга входящего потока заказов.

## Подводные камни

Позволять очереди расти бесконечно: диск сервера Kafka заполнится на 100%, операционная система переведет файловую систему в режим Read-Only, и весь брокер упадет аварийно, остановив работу всех сервисов компании.

## На собеседовании

**Вопрос с собеседования:** «Что лучше для клиента: долгий ответ через 40 секунд или быстрый HTTP 503 через 2 миллисекунды?»
**Ответ:** Быстрый отказ **HTTP 503 через 2 мс с заголовком Retry-After**. Долгий ответ подвешивает поток в браузере или мобильном приложении клиента, блокирует ресурсы шлюза и истощает сокеты, в то время как быстрый отказ позволяет приложению показать понятный экран ожидания или повторить попытку в фоновом режиме.
