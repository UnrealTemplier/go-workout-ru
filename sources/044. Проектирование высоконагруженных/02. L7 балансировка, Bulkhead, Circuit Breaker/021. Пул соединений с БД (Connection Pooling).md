# Пул соединений с БД (Connection Pooling): настройка pgxpool и мониторинг истощения ресурсов

## Условие

Реализуй **Database Connection Pooling**: `pgxpool` с `MaxConns=50`, `MinConns=10`, `MaxConnLifetime=1h`. Мониторинг: `pgxpool.Stat().TotalConns()`, `IdleConns()`, `WaitCount()`. Покажи, что pool exhaustion = cascading failure.

## Теория

Анатомия пула соединений СУБД (PostgreSQL Connection Pooling):
- Открытие нового TCP-соединения с PostgreSQL — крайне дорогая операция:
  - Выделение отдельного процесса на стороне Linux в PostgreSQL (`fork()`).
  - Выделение буферов памяти `work_mem` (~10–20 МБ на процесс).
  - Аутентификация, SSL Handshake. Задержка открытия: **20–80 мс**!
- **Параметры `pgxpool`:**
  - `MaxConns`: максимальный потолок открытых сокетов (например 50).
  - `MinConns`: минимальный подогретый резерв простаивающих соединений (например 10).
  - `MaxConnLifetime`: максимальное время жизни соединения перед ротацией (защита от утечек памяти).
- **Опасность Pool Exhaustion (Истощение пула):**
  - Если все 50 соединений заняты зависшими запросами, новые горутины встают в очередь ожидания (`WaitCount` растет).
  - При превышении таймаута контекста приложение захлебывается, порождая каскадный отказ.

## Решение по шагам

1. Создайте модель пула соединений с лимитом `MaxConns` и очередью ожидания.
2. Реализуйте метрики пула: `TotalConns`, `IdleConns`, `WaitCount`.
3. Смоделируйте исчерпание пула при наплыве тяжелых транзакций.
4. Продемонстрируйте обработку превышения таймаута ожидания свободного коннекта.

## Код решения

**`pgxpool_exhaustion_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
	"time"
)

type MockPGXPool struct {
	mu         sync.Mutex
	maxConns   int
	inUse      int
	waitCount  int
	connTokens chan struct{}
}

func NewMockPGXPool(maxConns int) *MockPGXPool {
	tokens := make(chan struct{}, maxConns)
	for i := 0; i < maxConns; i++ {
		tokens <- struct{}{}
	}
	return &MockPGXPool{
		maxConns:   maxConns,
		connTokens: tokens,
	}
}

func (p *MockPGXPool) Acquire(ctx context.Context) (func(), error) {
	p.mu.Lock()
	p.waitCount++
	p.mu.Unlock()

	select {
	case <-p.connTokens:
		p.mu.Lock()
		p.inUse++
		p.mu.Unlock()

		release := func() {
			p.mu.Lock()
			p.inUse--
			p.mu.Unlock()
			p.connTokens <- struct{}{}
		}
		return release, nil
	case <-ctx.Done():
		return nil, errors.New("db pool exhaustion: acquire connection timed out")
	}
}

func (p *MockPGXPool) Stats() (int, int, int) {
	p.mu.Lock()
	defer p.mu.Unlock()
	return p.maxConns, p.inUse, p.waitCount
}

func TestPGXPoolExhaustion(t *testing.T) {
	// Пул всего на 2 соединения
	pool := NewMockPGXPool(2)

	// Занимаем оба соединения
	ctx := context.Background()
	rel1, err1 := pool.Acquire(ctx)
	rel2, err2 := pool.Acquire(ctx)

	if err1 != nil || err2 != nil {
		t.Fatal("Первые два коннекта обязаны быть успешно получены")
	}

	// 3-я горутина пытается получить коннект с коротким таймаутом
	ctxTimeout, cancel := context.WithTimeout(ctx, 30*time.Millisecond)
	defer cancel()

	_, errExhausted := pool.Acquire(ctxTimeout)
	if errExhausted == nil || errExhausted.Error() != "db pool exhaustion: acquire connection timed out" {
		t.Fatalf("Ожидалась ошибка истощения пула: %v", errExhausted)
	}

	// Освобождаем коннект
	rel1()
	rel2()

	maxC, inUse, waits := pool.Stats()

	fmt.Println("Мониторинг пула соединений БД (Connection Pool Exhaustion) подтвержден:")
	fmt.Printf("  • Метрики: MaxConns=%d, InUse=%d, TotalWaitRequests=%d\n", maxC, inUse, waits)
	fmt.Printf("  • Ошибка при истощении пула: %v\n", errExhausted)
	fmt.Println("  • Контроль таймаутов контекста предотвратил бесконечное зависание горутин")
}
```

## Под капотом

В `pgxpool.Stat()` критически важной метрикой для Prometheus является `WaitDuration`: суммарное время, которое горутины провели в ожидании освобождения коннекта. Рост `rate(pgxpool_wait_duration[1m])` — главный опережающий индикатор надвигающегося падения сервиса.

## Подводные камни

Ставить `MaxConns = 1000` в каждом поде приложения: 50 подов сервиса откроют \(50 \times 1000 = 50\,000\) процессов в PostgreSQL. Ядро Linux на сервере СУБД потратит всю оперативную память на таблицы страниц процессов и упадет от OOM. В HighLoad перед PostgreSQL **всегда ставят PgBouncer**.

## На собеседовании

**Вопрос с собеседования:** «Как рассчитать идеальный размер пула соединений к PostgreSQL для одного сервера?»
**Ответ:** По формуле команды разработки PostgreSQL:
$$\text{PoolSize} = (\text{CPU Cores} \times 2) + \text{Disk Spindle Count}$$
Для сервера с 16 ядрами CPU оптимальный размер пула составляет всего 32–40 соединений! Увеличение пула свыше этого значения приводит к деградации из-за переключения контекста процессора (Context Switching).
