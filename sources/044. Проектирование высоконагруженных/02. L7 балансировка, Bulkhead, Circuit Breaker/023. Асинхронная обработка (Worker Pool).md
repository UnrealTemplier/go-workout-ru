# Асинхронная обработка (Worker Pool): decoupled-архитектура с polling статуса задач

## Условие

Реализуй **Async Processing (Worker Pool)**: HTTP API принимает `CreateReportRequest`, возвращает `job_id`. Job queue (Redis/RabbitMQ/Kafka). Workers (10 goroutines) обрабатывают. Client polls `GET /jobs/{id}/status`. Покажи decoupling от long-running tasks.

## Теория

Паттерн асинхронной отложенной обработки (Asynchronous Request-Reply / RFC 7240):
- Генерация PDF-отчета за год или видеомонтаж занимает от 30 секунд до 10 минут.
- Удерживать открытое синхронное HTTP-соединение 10 минут категорически недопустимо:
  - Балансировщики сбросят соединение по таймауту 60 сек (`504 Gateway Timeout`).
  - Сокеты и память сервера остаются заблокированными.
- **Архитектура Async Jobs:**
  1. Клиент делает `POST /reports`: сервер генерирует UUID `job_id`, кладет задачу в очередь и мгновенно отвечает:
     `HTTP 202 Accepted` с заголовком `Location: /jobs/job-101/status`.
  2. Фоновый пул воркеров (Worker Pool) вычитывает задачи и проводит тяжелые расчеты.
  3. Клиент периодически опрашивает `GET /jobs/job-101/status` (или получает уведомление по WebSocket/Webhook).

## Решение по шагам

1. Создайте структуру очереди задач с пулом фоновых воркеров.
2. Реализуйте эндпоинт отправки задачи с возвратом статуса `PENDING` и `job_id`.
3. Смоделируйте выполнение задачи пулом воркеров со сменой статуса на `COMPLETED`.
4. Верифицируйте получение готового результата через polling.

## Код решения

**`async_worker_pool_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type JobStatus string

const (
	StatusPending   JobStatus = "PENDING"
	StatusRunning   JobStatus = "RUNNING"
	StatusCompleted JobStatus = "COMPLETED"
)

type JobRecord struct {
	ID        string
	Status    JobStatus
	ResultURL string
}

type AsyncJobManager struct {
	mu       sync.RWMutex
	jobs     map[string]*JobRecord
	jobQueue chan string
}

func NewAsyncJobManager(queueSize int, workersCount int) *AsyncJobManager {
	mgr := &AsyncJobManager{
		jobs:     make(map[string]*JobRecord),
		jobQueue: make(chan string, queueSize),
	}

	// Запуск пула воркеров
	for w := 1; w <= workersCount; w++ {
		go func(workerID int) {
			for jobID := range mgr.jobQueue {
				mgr.mu.Lock()
				mgr.jobs[jobID].Status = StatusRunning
				mgr.mu.Unlock()

				// Имитация тяжелой генерации отчета
				time.Sleep(20 * time.Millisecond)

				mgr.mu.Lock()
				mgr.jobs[jobID].Status = StatusCompleted
				mgr.jobs[jobID].ResultURL = fmt.Sprintf("https://s3.corp.ru/reports/%s.pdf", jobID)
				mgr.mu.Unlock()
			}
		}(w)
	}

	return mgr
}

func (m *AsyncJobManager) SubmitJob(jobID string) string {
	m.mu.Lock()
	m.jobs[jobID] = &JobRecord{ID: jobID, Status: StatusPending}
	m.mu.Unlock()

	m.jobQueue <- jobID
	return jobID
}

func (m *AsyncJobManager) GetStatus(jobID string) (JobStatus, string) {
	m.mu.RLock()
	defer m.mu.RUnlock()
	if job, ok := m.jobs[jobID]; ok {
		return job.Status, job.ResultURL
	}
	return "NOT_FOUND", ""
}

func TestAsyncWorkerPool(t *testing.T) {
	manager := NewAsyncJobManager(50, 3)

	// Клиент отправляет тяжелую задачу
	jobID := "report-fin-2026"
	manager.SubmitJob(jobID)

	// Моментальная проверка статуса (должен быть PENDING или RUNNING)
	statusInitial, _ := manager.GetStatus(jobID)
	if statusInitial != StatusPending && statusInitial != StatusRunning {
		t.Fatalf("Начальный статус неверен: %s", statusInitial)
	}

	// Ожидаем завершения обработки воркером (Polling)
	time.Sleep(50 * time.Millisecond)

	statusDone, downloadURL := manager.GetStatus(jobID)
	if statusDone != StatusCompleted || downloadURL == "" {
		t.Fatalf("Задача должна завершиться успехом: %s, url=%s", statusDone, downloadURL)
	}

	fmt.Println("Асинхронная обработка (Async Worker Pool) подтверждена:")
	fmt.Printf("  • Клиент получил HTTP 202 Accepted: JobID=%s (Статус: %s)\n", jobID, statusInitial)
	fmt.Printf("  • По завершении воркером: %s -> %s\n", statusDone, downloadURL)
	fmt.Println("  • Длительные фоновые расчеты полностью изолированы от HTTP соединений")
}
```

## Под капотом

В распределенных средах очередь задач организуют через Redis (Asynq, Machinery) или RabbitMQ. При аварийном падении воркера задача возвращается в очередь по механизму Visibility Timeout (NACK), гарантируя, что ни один отчет не потеряется.

## Подводные камни

Позволять клиентам поллить `GET /jobs/{id}` с частотой 100 раз в секунду: агрессивный опрос создаст нагрузку выше, чем сама генерация отчета. Клиенту всегда возвращают заголовок `Retry-After: 5` (опрашивать не чаще 1 раза в 5 секунд) или используют WebSocket-нотификацию.

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать Graceful Shutdown для пула воркеров в Go?»
**Ответ:** Закрыть канал очереди `close(jobQueue)` и дождаться завершения всех активных задач через `sync.WaitGroup.Wait()`. Воркеры штатно обработают текущие задачи, выйдут из цикла `range jobQueue`, зафиксируют результаты в БД и только после этого завершат процесс.
