# Автомасштабирование (HPA & KEDA): масштабирование по CPU и глубине очереди сообщений в ноль

## Условие

Реализуй **Auto-Scaling (HPA)**: Kubernetes `HorizontalPodAutoscaler` по CPU (target 70%), memory, custom metrics (Kafka lag, request latency). `KEDA` для event-driven scaling: 0 replicas when no messages, scale to 100 when 10000 messages in queue.

## Теория

Принципы масштабирования Kubernetes (HPA vs KEDA):
1. **Kubernetes Horizontal Pod Autoscaler (HPA):**
   - Периодически опрашивает `metrics-server` (каждые 15 секунд).
   - Формула расчета реплик:
     $$\text{DesiredReplicas} = \left\lceil \text{CurrentReplicas} \times \frac{\text{CurrentMetricValue}}{\text{TargetMetricValue}} \right\rceil$$
   - При превышении порога CPU 70% HPA увеличивает число подов.
2. **KEDA (Kubernetes Event-driven Autoscaling):**
   - HPA не умеет масштабировать сервис в **0 реплик**.
   - KEDA опрашивает внешние источники событий (Kafka Lag, RabbitMQ Queue, AWS SQS).
   - Если в очереди 0 сообщений \(\implies\) сервис масштабируется в **0 подов** (нулевые затраты облака!).
   - При появлении 10 000 сообщений KEDA мгновенно разворачивает 100 подов.

## Решение по шагам

1. Создайте модель калькулятора HPA на основе формулы Kubernetes.
2. Реализуйте алгоритм масштабирования KEDA по глубине очереди Kafka.
3. Продемонстрируйте переход в 0 реплик при простое (Scale-to-Zero).
4. Верифицируйте корректность пропорционального масштабирования при пиковом лаге.

## Код решения

**`hpa_keda_autoscaling_test.go`**

```go
package main

import (
	"fmt"
	"math"
	"testing"
)

type HPACalculator struct {
	TargetCPUPercent float64
	MinReplicas      int
	MaxReplicas      int
}

func (h *HPACalculator) CalculateReplicas(currentReplicas int, currentCPUPercent float64) int {
	ratio := currentCPUPercent / h.TargetCPUPercent
	desired := int(math.Ceil(float64(currentReplicas) * ratio))

	if desired < h.MinReplicas {
		return h.MinReplicas
	}
	if desired > h.MaxReplicas {
		return h.MaxReplicas
	}
	return desired
}

type KEDAQueueScaler struct {
	MessagesPerPod int
	MaxReplicas    int
}

func (k *KEDAQueueScaler) CalculateScale(queueLag int) int {
	if queueLag == 0 {
		return 0 // SCALE TO ZERO!
	}
	desired := int(math.Ceil(float64(queueLag) / float64(k.MessagesPerPod)))
	if desired > k.MaxReplicas {
		return k.MaxReplicas
	}
	return desired
}

func TestHPAandKEDAAutoscaling(t *testing.T) {
	// 1. Тест HPA CPU масштабирования
	hpa := &HPACalculator{TargetCPUPercent: 70.0, MinReplicas: 2, MaxReplicas: 20}

	// 5 подов под 90% CPU -> (5 * 90 / 70) = 6.42 -> 7 подов
	scaleUpHPA := hpa.CalculateReplicas(5, 90.0)
	if scaleUpHPA != 7 {
		t.Fatalf("HPA расчет неверен: %d (ожидалось 7)", scaleUpHPA)
	}

	// 2. Тест KEDA Event-driven масштабирования
	keda := &KEDAQueueScaler{MessagesPerPod: 100, MaxReplicas: 100}

	replicasIdle := keda.CalculateScale(0)      // Очередь пуста
	replicasHeavy := keda.CalculateScale(10000) // 10 000 сообщений в очереди

	if replicasIdle != 0 || replicasHeavy != 100 {
		t.Fatalf("KEDA сбой: Idle=%d (ожидалось 0), Heavy=%d (ожидалось 100)",
			replicasIdle, replicasHeavy)
	}

	fmt.Println("Автомасштабирование (HPA & KEDA) успешно подтверждено:")
	fmt.Printf("  • HPA (CPU 90%% при цели 70%%): 5 подов -> %d подов\n", scaleUpHPA)
	fmt.Printf("  • KEDA Scale-to-Zero: Очередь 0 -> %d реплик\n", replicasIdle)
	fmt.Printf("  • KEDA Burst Load:    Очередь 10 000 -> %d реплик\n", replicasHeavy)
	fmt.Println("  • Инфраструктура гибко адаптируется к пикам и экономит бюджет при простое")
}
```

## Под капотом

KEDA регистрирует в Kubernetes собственный Custom Metrics Server. Когда создается объект `ScaledObject`, KEDA транслирует внешние метрики Kafka Lag в стандартный интерфейс Kubernetes Metrics API `custom.metrics.k8s.io`, управляя стандартным HPA контроллером под капотом.

## Подводные камни

Настраивать агрессивный Scale-Down без стабилизационного окна (Cooldown Period): при кратковременном спаде нагрузки поды удалятся, а через 30 секунд прилетит новая пачка сообщений. В HPA задают `behavior.scaleDown.stabilizationWindowSeconds: 300` (5 минут спокойствия перед сжатием).

## На собеседовании

**Вопрос с собеседования:** «Почему масштабирование консьюмеров Kafka по KEDA ограничено количеством партиций топика?»
**Ответ:** По протоколу Kafka каждую партицию внутри группы консьюмеров может вычитывать строго **один** инстанс консьюмера. Если в топике 32 партиции, масштабирование сервиса до 100 подов бессмысленно: 68 подов будут простаивать без назначенных партиций. Максимальное число реплик консьюмеров равно количеству партиций.
