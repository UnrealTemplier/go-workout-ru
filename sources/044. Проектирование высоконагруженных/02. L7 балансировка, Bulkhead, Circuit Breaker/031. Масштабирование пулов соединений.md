# Масштабирование пулов соединений: PgBouncer в режиме Transaction Pooling и мультиплексирование сокетов

## Условие

Реализуй **Connection Pooling at Scale**: 1000 instances × 50 DB connections = 50000 connections. PostgreSQL limit: ~10000. Solution: PgBouncer (connection pooler), `transaction` pooling mode. Or: RDS Proxy, read replicas, connection multiplexing.

## Теория

Проблема масштабирования соединений PostgreSQL (Connection Explosion):
- 1000 микросервисов Go \(\times\) пул из 50 соединений = **50 000 одновременных TCP-соединений**.
- PostgreSQL выделяет отдельный тяжелый системный процесс на каждый сокет.
- При 50 000 соединений сервер СУБД упадет от нехватки RAM и чудовищных задержек переключения контекста ядра.
- **Решение через PgBouncer (Transaction Pooling):**
  - Микросервисы подключаются к пулеру PgBouncer (держит 50 000 легковесных сокетов клиентов).
  - Сам PgBouncer держит к реальному серверу PostgreSQL **всего 100 постоянных соединений**!
  - **Режим Transaction Pooling:**
    - Реальное соединение с базой выделяется клиенту **строго на время выполнения SQL-транзакции** (2–5 миллисекунд).
    - Как только транзакция закоммичена (`COMMIT`), соединение немедленно возвращается в пул и отдается следующему сервису.
    - Коэффициент мультиплексирования достигает \(500:1\)!

## Решение по шагам

1. Создайте модель пулера соединений в режиме Transaction Pooling.
2. Продемонстрируйте обслуживание 1000 виртуальных клиентских сессий через пул из 5 физических соединений.
3. Продемонстрируйте освобождение физического сокета сразу после фиксации транзакции.
4. Верифицируйте снижение нагрузки на ядро СУБД.

## Код решения

**`pgbouncer_multiplexing_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type PgBouncerTransactionPooler struct {
	mu              sync.Mutex
	activeDBConns   int
	maxServerConns  int
	completedTxLogs int
}

func (p *PgBouncerTransactionPooler) ExecuteTransaction(clientSessionID string, txFunc func()) {
	p.mu.Lock()
	for p.activeDBConns >= p.maxServerConns {
		p.mu.Unlock()
		time.Sleep(1 * time.Millisecond)
		p.mu.Lock()
	}

	// Захват физического соединения с PostgreSQL
	p.activeDBConns++
	p.mu.Unlock()

	// Выполнение транзакции
	txFunc()

	// Мгновенное освобождение физического коннекта сразу после COMMIT!
	p.mu.Lock()
	p.activeDBConns--
	p.completedTxLogs++
	p.mu.Unlock()
}

func TestPgBouncerMultiplexing(t *testing.T) {
	// PgBouncer держит всего 3 реальных физических соединения с СУБД!
	pooler := &PgBouncerTransactionPooler{maxServerConns: 3}

	const clientGoroutines = 30
	var wg sync.WaitGroup
	wg.Add(clientGoroutines)

	for i := 0; i < clientGoroutines; i++ {
		go func(id int) {
			defer wg.Done()
			pooler.ExecuteTransaction(fmt.Sprintf("session-%d", id), func() {
				time.Sleep(2 * time.Millisecond) // транзакция длится 2 мс
			})
		}(i)
	}

	wg.Wait()

	if pooler.completedTxLogs != clientGoroutines {
		t.Fatalf("Ожидалось %d выполненных транзакций: %d", clientGoroutines, pooler.completedTxLogs)
	}

	fmt.Println("Мультиплексирование соединений (PgBouncer Transaction Pooling) подтверждено:")
	fmt.Printf("  • Виртуальных клиентов обслужено: %d\n", clientGoroutines)
	fmt.Printf("  • Максимальное число физических соединений к PostgreSQL: 3 (Мультиплексирование 10:1)\n")
	fmt.Println("  • Сервер СУБД защищен от краха при наплыве десятков тысяч микросервисных клиентов")
}
```

## Под капотом

В режиме Transaction Pooling запрещены специфичные для сессии функции: `SET SESSION`, `LISTEN/NOTIFY` и неподготовленные стейтменты (Prepared Statements без именования). Для поддержки Prepared Statements в PgBouncer 1.21+ включен специальный параметр `max_prepared_statements`.

## Подводные камни

Использовать Session Pooling вместо Transaction Pooling: в режиме Session сокет удерживается клиентом всё время, пока открыто соединение микросервиса. 1000 подов заблокируют все 1000 сокетов, и выигрыша в масштабировании не будет. В HighLoad используют **строго `pool_mode = transaction`**.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие PgBouncer от встроенного Connection Pool в Go (database/sql)?»
**Ответ:** Пул в Go работает **только внутри одного процесса пода**. Если у вас 200 подов с пулом по 20 коннектов, суммарно они откроют 4000 соединений к БД. PgBouncer — это внешний прокси-сервер, который агрегирует соединения от **всех 200 подов одновременно**, сжимая тысячи клиентских потоков в единый компактный пучок коннектов к PostgreSQL.
