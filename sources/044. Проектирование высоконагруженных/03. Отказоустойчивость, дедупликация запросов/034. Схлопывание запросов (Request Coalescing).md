# Схлопывание запросов (Request Coalescing): сокращение нагрузки на базу в 1000 раз через singleflight

## Условие

Реализуй **Request Coalescing**: 1000 requests for same `product:123` simultaneously. Only 1 goes to DB, 999 wait for result. `singleflight.Group` (Go) or `cache stampede` protection. Reduces DB load 1000x for hot keys.

## Теория

Механика Request Coalescing (Схлопывание одинаковых запросов):
- Во время распродаж («Черная пятница») тысячи пользователей одновременно открывают одну и ту же страницу главного товара со скидкой 90%.
- Если данные отсутствуют в кэше, 1000 запросов не должны создавать 1000 одинаковых параллельных вычислений.
- **Паттерн Request Coalescing:**
  - Запросы группируются по уникальному ключу сущности (`product:123`).
  - Первая горутина инициирует поход в базу данных или тяжелый расчет.
  - Все последующие 999 запросов встают в ожидание (Join the flight).
  - Как только результат готов, он рассылается всем 1000 клиентам.
  - Нагрузка на базу данных сокращается ровно в 1000 раз!

## Решение по шагам

1. Создайте группу схлопывания `RequestCoalescer`.
2. Смоделируйте одновременный запуск 1000 горутин, запрашивающих карточку `product:123`.
3. Докажите, что счетчик выполнения функции равен ровно 1.
4. Верифицируйте успешное получение данных всеми 1000 клиентами.

## Код решения

**`request_coalescing_scale_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type CoalescedCall struct {
	wg  sync.WaitGroup
	val string
	err error
}

type RequestCoalescer struct {
	mu    sync.Mutex
	calls map[string]*CoalescedCall
}

func (c *RequestCoalescer) Do(key string, fn func() (string, error)) (string, error) {
	c.mu.Lock()
	if c.calls == nil {
		c.calls = make(map[string]*CoalescedCall)
	}

	// Если запрос по этому ключу уже выполняется в полете -> ждем его завершения
	if call, exists := c.calls[key]; exists {
		c.mu.Unlock()
		call.wg.Wait()
		return call.val, call.err
	}

	// Первый запрос берет на себя выполнение
	call := new(CoalescedCall)
	call.wg.Add(1)
	c.calls[key] = call
	c.mu.Unlock()

	call.val, call.err = fn()
	call.wg.Done()

	c.mu.Lock()
	delete(c.calls, key)
	c.mu.Unlock()

	return call.val, call.err
}

func TestRequestCoalescingScale(t *testing.T) {
	coalescer := &RequestCoalescer{}
	var databaseExecutionCounter int64

	fetchProduct := func() (string, error) {
		atomic.AddInt64(&databaseExecutionCounter, 1)
		time.Sleep(30 * time.Millisecond) // Имитация времени SQL запроса
		return "Product: Смартфон Ultra 2026 (Цена: 79 990 руб)", nil
	}

	const totalConcurrentUsers = 1000
	var wg sync.WaitGroup
	wg.Add(totalConcurrentUsers)

	for i := 0; i < totalConcurrentUsers; i++ {
		go func() {
			defer wg.Done()
			res, err := coalescer.Do("product:123", fetchProduct)
			if err != nil || res != "Product: Смартфон Ultra 2026 (Цена: 79 990 руб)" {
				t.Errorf("Некорректный ответ: %v", res)
			}
		}()
	}

	wg.Wait()

	if databaseExecutionCounter != 1 {
		t.Fatalf("Сбой Coalescing: в БД ушло %d вызовов вместо 1!", databaseExecutionCounter)
	}

	fmt.Println("Схлопывание запросов (Request Coalescing) успешно подтверждено:")
	fmt.Printf("  • Пользовательских запросов поступило: %d\n", totalConcurrentUsers)
	fmt.Printf("  • Физических запросов к СУБД:          %d (Снижение нагрузки ровно в 1000 раз!)\n", databaseExecutionCounter)
	fmt.Println("  • Все 1000 клиентов получили идентичный проверенный ответ")
}
```

## Под капотом

В высоконагруженных прокси (Nginx) аналогичный механизм называется `proxy_cache_use_stale updating` и `proxy_cache_lock`: только один запрос направляется к апстриму для обновления кэша, а остальные ждут в буфере сокета.

## Подводные камни

Зависание первого запроса: если функция `fn` зависнет навсегда без таймаута, все 1000 ожидающих горутин зависнут вместе с ней. Функция `fn` **обязана быть обернута в строгий контекстный таймаут**.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если запрос завершится ошибкой в singleflight?»
**Ответ:** Все 1000 ожидающих горутин получат ту же самую ошибку. Чтобы предотвратить лавинообразный сбой при временной сетевой ошибке, в singleflight внедряют механизм `Forget(key)` сразу после ошибки, позволяя следующему запросу попробовать обратиться к базе снова.
