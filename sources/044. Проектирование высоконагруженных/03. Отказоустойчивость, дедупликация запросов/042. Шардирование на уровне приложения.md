# Шардирование на уровне приложения (Application-Level Sharding): прозрачный роутер между узлами PostgreSQL

## Условие

**Application-Level Sharding**: Одна БД больше не справляется. Подними две PostgreSQL (`db_node_0` и `db_node_1`). В Go-коде напиши роутер подключений: при создании юзера бери остаток от деления `userID % 2`. Если 0 — пиши в первую базу, если 1 — во вторую. Реализуй абстракцию, чтобы бизнес-логика не замечала, что баз две.

## Теория

Прозрачное шардирование на уровне кода (Application-Level Sharding Router):
- Вместо тяжелых внешних прокси шардирования (Vitess, Citus) простая и эффективная маршрутизация может быть реализована прямо в коде Go:
  - Бизнес-логика оперирует интерфейсом `UserRepository`.
  - Внутри репозитория скрыт маршрутизатор шардов `ShardConnectionPool`:
    ```go
    shardID := userID % len(shards)
    db := shards[shardID]
    return db.ExecContext(...)
    ```
  - Бизнес-логика даже не знает, что под капотом работают две независимые базы данных!

## Решение по шагам

1. Создайте интерфейс пользователя и абстракцию репозитория.
2. Реализуйте внутренний роутер `TwoNodeShardedUserRepository` с двумя виртуальными СУБД.
3. Продемонстрируйте маршрутизацию четных `userID` на ноду 0, нечетных — на ноду 1.
4. Верифицируйте прозрачность абстракции для вызывающего кода.

## Код решения

**`application_sharding_router_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type UserEntity struct {
	ID    int64
	Name  string
	Email string
}

type DatabaseNodeMock struct {
	NodeName string
	Records  map[int64]UserEntity
}

type TwoNodeShardedUserRepository struct {
	node0 *DatabaseNodeMock
	node1 *DatabaseNodeMock
}

func NewShardedUserRepository() *TwoNodeShardedUserRepository {
	return &TwoNodeShardedUserRepository{
		node0: &DatabaseNodeMock{NodeName: "db_node_0", Records: make(map[int64]UserEntity)},
		node1: &DatabaseNodeMock{NodeName: "db_node_1", Records: make(map[int64]UserEntity)},
	}
}

func (r *TwoNodeShardedUserRepository) SaveUser(ctx context.Context, u UserEntity) (string, error) {
	// Маршрутизация: userID % 2
	if u.ID%2 == 0 {
		r.node0.Records[u.ID] = u
		return r.node0.NodeName, nil
	}
	r.node1.Records[u.ID] = u
	return r.node1.NodeName, nil
}

func (r *TwoNodeShardedUserRepository) GetUserByID(ctx context.Context, id int64) (UserEntity, string, bool) {
	if id%2 == 0 {
		u, exists := r.node0.Records[id]
		return u, r.node0.NodeName, exists
	}
	u, exists := r.node1.Records[id]
	return u, r.node1.NodeName, exists
}

func TestApplicationShardingRouter(t *testing.T) {
	repo := NewShardedUserRepository()

	userEven := UserEntity{ID: 1042, Name: "Четный Пользователь", Email: "even@corp.ru"}
	userOdd := UserEntity{ID: 1043, Name: "Нечетный Пользователь", Email: "odd@corp.ru"}

	// Сохранение пользователей
	targetEven, _ := repo.SaveUser(context.Background(), userEven)
	targetOdd, _ := repo.SaveUser(context.Background(), userOdd)

	if targetEven != "db_node_0" || targetOdd != "db_node_1" {
		t.Fatalf("Сбой маршрутизации: %s, %s", targetEven, targetOdd)
	}

	// Чтение пользователя 1042
	uLoaded, nodeLoaded, found := repo.GetUserByID(context.Background(), 1042)
	if !found || nodeLoaded != "db_node_0" || uLoaded.Name != "Четный Пользователь" {
		t.Fatalf("Сбой чтения из шарда: %s, %v", nodeLoaded, uLoaded)
	}

	fmt.Println("Шардирование на уровне приложения (Application-Level Sharding) подтверждено:")
	fmt.Printf("  • ID 1042 (Четный)  -> Записан в %s\n", targetEven)
	fmt.Printf("  • ID 1043 (Нечетный) -> Записан в %s\n", targetOdd)
	fmt.Println("  • Бизнес-логика вызывает единый репозиторий без знания о разделении баз")
}
```

ℹ️ Прозрачная маршрутизация запросов между несколькими узлами СУБД по остатку от деления userID % 2

## Под капотом

В драйвере базы данных роутер инициализирует два независимых пула `pgxpool.Pool`. Запрос выполняется в пуле соответствующей ноды без накладных расходов на сетевые прокси, обеспечивая минимальную задержку (Zero Overhead).

## Подводные камни

Использовать автоинкремент `SERIAL` в обеих базах: обе базы независимо создадут пользователей с одинаковым ID = 1. Для генерации первичных ключей при шардировании используют **Twitter Snowflake ID или UUIDv7**.

## На собеседовании

**Вопрос с собеседования:** «Как выполнить выборку пользователей по имени `WHERE name = 'Иван'`, если шардирование сделано по `user_id`?»
**Ответ:** Поиск без ключа шардирования (Scatter-Gather) требует параллельного опроса всех шардов через `errgroup` и объединения результатов. В HighLoad для выборок по неключевым полям создают поисковый индекс в Elasticsearch или глобальную таблицу сопоставления (Lookup Table / Secondary Index) в Redis.
