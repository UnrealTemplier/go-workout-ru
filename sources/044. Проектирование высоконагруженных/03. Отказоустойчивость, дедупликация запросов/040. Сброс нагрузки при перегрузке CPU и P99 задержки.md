# Сброс нагрузки при перегрузке CPU и P99 задержки: отсечение второстепенного трафика с Retry-After

## Условие

Реализуй **Load Shedding**: system overloaded (CPU > 90%, latency p99 > 2s). Drop low-priority requests (analytics, non-critical reads). Accept high-priority (payments, critical writes). `503` with `Retry-After` header. Client backs off exponentially.

## Теория

Динамический сброс нагрузки по метрикам здоровья (Dynamic Health-Based Load Shedding):
- В моменты пиковых перегрузок (CPU > 90% или квантиль задержки P99 > 2.0 секунд):
  - Вся система находится в шаге от полного коллапса (Livelock / Cascading Crash).
- **Инженерный механизм Dynamic Load Shedding:**
  1. Шлюз непрерывно считывает скользящую метрику загрузки CPU и P99 Latency.
  2. При пересечении аварийного порога включается фильтрация:
     - Запросы с низким приоритетом (`/analytics`, `/views`, `/recommendations`) немедленно отбрасываются с кодом `HTTP 503 Service Unavailable`.
     - В ответ обязательно инжектируется заголовок `Retry-After: 15` (или случайное значение с джиттером).
     - Критические запросы (`/payments`, `/checkout`) получают 100% оставшихся ядер CPU и выполняются стабильно!

## Решение по шагам

1. Создайте контроллер сброса нагрузки `DynamicLoadShedder`.
2. Реализуйте мониторинг порогов CPU и P99 Latency.
3. Продемонстрируйте блокировку низкоприоритетных запросов при перегрузке.
4. Верифицируйте беспрепятственное проведение критических платежей.

## Код решения

**`dynamic_load_shedding_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type SystemTelemetry struct {
	CPUPercent float64
	P99Latency time.Duration
}

type DynamicLoadShedder struct {
	telemetry SystemTelemetry
}

type RequestMeta struct {
	Path        string
	IsCritical  bool // true для платежей и чекаута
}

func (s *DynamicLoadShedder) EvaluateAdmission(req RequestMeta) (int, string) {
	// Критический порог перегрузки системы: CPU > 90% или P99 > 2s
	isOverloaded := s.telemetry.CPUPercent > 90.0 || s.telemetry.P99Latency > 2*time.Second

	if isOverloaded && !req.IsCritical {
		// Сброс второстепенной нагрузки с заголовком Retry-After
		return 503, "SHED_LOAD_503 (Header Retry-After: 15s)"
	}

	return 200, "ADMITTED_200_OK"
}

func TestDynamicLoadShedding(t *testing.T) {
	// Сервер в огне: CPU на 94%, P99 задержка 2.8 секунды
	shedder := &DynamicLoadShedder{
		telemetry: SystemTelemetry{CPUPercent: 94.0, P99Latency: 2800 * time.Millisecond},
	}

	reqAnalytics := RequestMeta{Path: "/api/v1/analytics/click", IsCritical: false}
	reqPayment := RequestMeta{Path: "/api/v1/payments/charge", IsCritical: true}

	codeAnalytics, resAnalytics := shedder.EvaluateAdmission(reqAnalytics)
	codePayment, resPayment := shedder.EvaluateAdmission(reqPayment)

	if codeAnalytics != 503 || codePayment != 200 {
		t.Fatalf("Сбой Load Shedding: Analytics=%d, Payment=%d", codeAnalytics, codePayment)
	}

	fmt.Println("Динамический сброс нагрузки (Dynamic Load Shedding) подтвержден:")
	fmt.Printf("  • Аналитика (/analytics):  HTTP %d -> %s\n", codeAnalytics, resAnalytics)
	fmt.Printf("  • Оплата    (/payments):   HTTP %d -> %s\n", codePayment, resPayment)
	fmt.Println("  • Критический транзакционный контур защищен от деградации за счет сброса фона")
}
```

ℹ️ Динамический сброс второстепенного трафика с кодом 503 и Retry-After при скачке CPU > 90%

## Под капотом

В gRPC встроен механизм `Overload Protection`: если инфлайт-очередь переполнена, сервер возвращает статус `codes.ResourceExhausted`. Клиентский gRPC перехватывает этот статус и активирует Exponential Backoff на стороне клиента.

## Подводные камни

Возвращать ошибку 500 вместо 503: статус 500 Internal Server Error воспринимается клиентами как баг бэкенда, и многие HTTP-клиенты не считывают заголовок `Retry-After`. Для сброса нагрузки по стандартам RFC используют строго **503 Service Unavailable**.

## На собеседовании

**Вопрос с собеседования:** «Что такое Goodput и как Load Shedding максимизирует его?»
**Ответ:** Throughput — это общее число обработанных запросов. Goodput — это число запросов, завершенных **успешно и уложившихся в SLA по задержке**. При перегрузке Throughput может быть высоким, но 90% ответов опаздывают по таймауту (Goodput падает до нуля). Load Shedding отбрасывает 30% запросов, возвращая Goodput оставшихся 70% клиентов к 100% качеству.
