# Бюджет повторных попыток (Retry Budget): защита от лавины повторных запросов (Retry Storm)

## Условие

**Retry Budget**: Ограничьте общее количество retry в системе (например, не более 10% от общего трафика), чтобы retry storm не усугубил проблему.

## Теория

Опасность лавины повторных попыток (Retry Storm):
- Когда downstream-сервис испытывает 20% деградацию:
  - Если каждый клиент при сбое делает по 3 автоматических повтора:
  - Общий трафик на падающий сервис мгновенно вырастает в 3 раза (\(300\%\))!
  - Сервис добивается лавиной ретраев и падает окончательно.
- **Паттерн Retry Budget (Бюджет ретраев):**
  - Клиент отслеживает долю повторных запросов относительно общего успешного трафика.
  - Правило: повторные запросы не должны составлять более **10% от общего объема вызовов**.
  - Если зависимый сервис лежит глобально, бюджет ретраев исчерпывается за несколько секунд.
  - Клиент прекращает любые дальнейшие повторы и возвращает ошибку немедленно, давая упавшему сервису восстановиться!

## Решение по шагам

1. Создайте структуру счетчика бюджета ретраев `RetryBudgetTracker`.
2. Реализуйте проверку доступности бюджета перед выполнением повторной попытки.
3. Смоделируйте исчерпание 10% лимита при массовом падении downstream.
4. Верифицируйте остановку шторма повторов.

## Код решения

**`retry_budget_protection_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type RetryBudgetTracker struct {
	mu           sync.Mutex
	regularCalls int
	retryCalls   int
	maxRetryRatio float64 // например 0.10 (не более 10%)
}

func NewRetryBudget(maxRatio float64) *RetryBudgetTracker {
	return &RetryBudgetTracker{maxRetryRatio: maxRatio}
}

func (b *RetryBudgetTracker) RecordRegularCall() {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.regularCalls++
}

func (b *RetryBudgetTracker) TryAcquireRetry() bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	// Минимум 10 обычных вызовов для сбора базовой статистики
	if b.regularCalls < 10 {
		return true
	}

	allowedRetries := int(float64(b.regularCalls) * b.maxRetryRatio)
	if b.retryCalls >= allowedRetries {
		return false // Бюджет ретраев исчерпан! Блокируем шторм
	}

	b.retryCalls++
	return true
}

func TestRetryBudgetProtection(t *testing.T) {
	budget := NewRetryBudget(0.10) // максимум 10% ретраев

	// 100 штатных успешных запросов
	for i := 0; i < 100; i++ {
		budget.RecordRegularCall()
	}

	// Лимит: 100 * 0.10 = ровно 10 повторных попыток
	successfulRetries := 0
	for i := 0; i < 15; i++ {
		if budget.TryAcquireRetry() {
			successfulRetries++
		}
	}

	if successfulRetries != 10 {
		t.Fatalf("Бюджет обязан был пропустить ровно 10 ретраев: %d", successfulRetries)
	}

	// 11-й ретрай должен быть отсечен
	if budget.TryAcquireRetry() {
		t.Fatal("Попытка сверх бюджета должна быть заблокирована")
	}

	fmt.Println("Бюджет повторных попыток (Retry Budget) подтвержден:")
	fmt.Printf("  • Всего штатных запросов: 100\n")
	fmt.Printf("  • Разрешено ретраев:      %d (Строго 10%% лимит)\n", successfulRetries)
	fmt.Printf("  • Предотвращено ретраев:  5 (Шторм повторов ликвидирован)\n")
	fmt.Println("  • Downstream-сервис защищен от лавинообразной перегрузки при аварии")
}
```

ℹ️ Жесткое ограничение доли повторных запросов до 10% от общего трафика для предотвращения Retry Storm

## Под капотом

В протоколе Finagle (Twitter) и библиотеке Linkerd Retry Budget реализован на базе скользящего окна токенов: каждый успешный запрос добавляет в пул 0.1 токена ретрая, а каждый повторный вызов забирает 1 целый токен. Если токенов нет — ретраи аппаратно запрещены.

## Подводные камни

Делать ретраи на каждом слое микросервисной цепочки: если Шлюз вызывает Сервис А (3 ретрая), а Сервис А вызывает Сервис Б (3 ретрая), а Сервис Б вызывает БД (3 ретрая), один сбой в базе приведет к \(3 \times 3 \times 3 = 27\) повторным запросам (Экспоненциальный взрыв ретраев). Ретраи настраивают **строго на одном уровне** архитектуры.

## На собеседовании

**Вопрос с собеседования:** «Почему распределенный бюджет ретраев эффективнее обычного фиксированного 'MaxRetries = 3'?»
**Ответ:** Фиксированный `MaxRetries = 3` утраивает нагрузку в момент, когда сервису и так плохо. Retry Budget адаптируется к реальному состоянию системы: при 1% ошибок ретраи работают свободно, но при глобальной аварии бюджет мгновенно обнуляется, предотвращая самозаклинивание системы.
