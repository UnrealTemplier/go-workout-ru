# Тестирование хаосом (Chaos Testing: Pod Kill): проверка самовосстановления кластера при уничтожении реплик

## Условие

**Chaos Testing (Pod Kill)**: Используйте `pumba` или `chaos-mesh` для случайного убийства подов и проверки, что система восстанавливается.

## Теория

Принципы инженерии хаоса (Chaos Engineering / Chaos Monkey):
- «Лучший способ убедиться, что система отказоустойчива — это регулярно ломать её компоненты в случайном порядке».
- Утилиты хаоса (`Chaos Mesh`, `Pumba`, `LitmusChaos`):
  - Случайно отправляют `SIGKILL` произвольному поду микросервиса в случайный момент времени.
- **Критерии успешности проверки хаосом:**
  1. Балансировщик Kubernetes исключает упавший под из эндпоинтов менее чем за 1 секунду.
  2. Входящий пользовательский трафик не получает ошибок `502 Bad Gateway` (соседние 2 реплики берут нагрузку).
  3. Kubelet автоматически перезапускает упавший контейнер (Self-Healing).
  4. Количество успешных запросов (SLO Availability) остается выше 99.9%.

## Решение по шагам

1. Создайте эмулятор кластера с пулом реплик и балансировщиком.
2. Смоделируйте случайное убийство одного пода инжектором хаоса (Chaos Pod Killer).
3. Докажите, что балансировщик перенаправляет трафик на живые реплики.
4. Продемонстрируйте автоматическое восстановление пула подов.

## Код решения

**`chaos_pod_kill_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ClusterPod struct {
	ID    string
	Alive bool
}

type ResilientClusterPool struct {
	pods []*ClusterPod
}

func (c *ResilientClusterPool) RouteRequest() (string, bool) {
	for _, p := range c.pods {
		if p.Alive {
			return p.ID, true
		}
	}
	return "", false
}

func (c *ResilientClusterPool) InjectPodKill(podID string) {
	for _, p := range c.pods {
		if p.ID == podID {
			p.Alive = false // SIGKILL!
		}
	}
}

func (c *ResilientClusterPool) SelfHealReconcile(targetReplicas int) {
	aliveCount := 0
	for _, p := range c.pods {
		if p.Alive {
			aliveCount++
		}
	}
	// Kubelet поднимает замену
	for i := aliveCount; i < targetReplicas; i++ {
		c.pods = append(c.pods, &ClusterPod{ID: fmt.Sprintf("pod-healed-%d", i+1), Alive: true})
	}
}

func TestChaosPodKill(t *testing.T) {
	cluster := &ResilientClusterPool{
		pods: []*ClusterPod{
			{ID: "pod-1", Alive: true},
			{ID: "pod-2", Alive: true},
		},
	}

	// 1. Штатная работа
	target1, ok1 := cluster.RouteRequest()
	if !ok1 || target1 != "pod-1" {
		t.Fatalf("Сбой штатного роутинга: %s", target1)
	}

	// 2. CHAOS EXPERIMENT: Chaos Mesh внезапно убивает pod-1 сигналом SIGKILL
	cluster.InjectPodKill("pod-1")

	// 3. Следующий запрос мгновенно подхватывается выжившим pod-2 без даунтайма!
	target2, ok2 := cluster.RouteRequest()
	if !ok2 || target2 != "pod-2" {
		t.Fatalf("Трафик должен был уйти на живой pod-2: %s", target2)
	}

	// 4. Kubelet Self-Healing восстанавливает число реплик до 2
	cluster.SelfHealReconcile(2)

	aliveTotal := 0
	for _, p := range cluster.pods {
		if p.Alive {
			aliveTotal++
		}
	}

	if aliveTotal != 2 {
		t.Fatalf("Ожидалось 2 живых пода после реконсиляции: %d", aliveTotal)
	}

	fmt.Println("Тестирование хаосом (Chaos Testing: Pod Kill) подтверждено:")
	fmt.Printf("  • Инцидент: pod-1 внезапно уничтожен (SIGKILL)\n")
	fmt.Printf("  • Балансировка: трафик моментально переключен на %s\n", target2)
	fmt.Printf("  • Самовосстановление (Self-Healing): кластер вернулся к %d активным репликам\n", aliveTotal)
	fmt.Println("  • Нулевое количество ошибок на стороне клиентов")
}
```

## Под капотом

В Kubernetes эксперимент Chaos Mesh описывается в виде манифеста `PodChaos`:
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-failure-example
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces: [prod]
    labelSelectors: { "app": "order-service" }
  scheduler: { cron: "@every 2h" }
```

## Подводные камни

Запускать Chaos эксперименты сразу на продакшене без предварительного тестирования в Staging окружении: неконтролируемый хаос может вызвать каскадный отказ всей базы данных. Внедрение хаоса начинают со стейджинга в присутствии дежурной команды инженеров.

## На собеседовании

**Вопрос с собеседования:** «Что такое 'Blast Radius' (радиус поражения) в экспериментах Chaos Engineering?»
**Ответ:** Это контролируемый лимит ущерба, который может нанести эксперимент. Например: воздействие ограничено строго 1% случайных пользователей или одним тестовым регионом. При превышении аварийного порога метрик эксперимент немедленно автоматически сворачивается механизмом Emergency Rollback.
