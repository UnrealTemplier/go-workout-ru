# Управление допуском запросов (Admission Control): многомерные корзины токенов и динамический троттлинг

## Условие

Реализуй **Admission Control**: `token bucket` for incoming requests. If bucket empty — reject immediately. Protects backend from overload. Separate buckets per priority, per tenant, per endpoint. Dynamic: reduce rate if latency grows.

## Теория

Многомерный контроль допуска (Multi-Dimensional Admission Control):
- Простой глобальный Rate Limiting защищает сервер от DDoS, но не защищает от неравномерности трафика внутри системы.
- **Многомерный Admission Control:**
  1. **Per-Endpoint Bucket:** тяжелый эндпоинт `/api/export-pdf` имеет квоту 5 RPS, в то время как `/api/health` имеет 1000 RPS.
  2. **Per-Tenant Bucket:** корпоративный тенант А имеет квоту 500 RPS, стартап Б — 50 RPS.
  3. **Dynamic Throttling (Адаптивный троттлинг):** если задержка P99 начинает расти свыше 500 мс, контроллер автоматически зажимает размер корзины токенов, сбивая наплыв трафика до стабилизации системы.

## Решение по шагам

1. Создайте структуру многомерного контроллера допуска `MultiDimensionalAdmissionController`.
2. Реализуйте раздельные корзины токенов по тенантам и эндпоинтам.
3. Продемонстрируйте динамическое снижение лимита при росте системной задержки.
4. Верифицируйте изоляцию квот тенантов.

## Код решения

**`admission_control_multidim_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type MultiDimensionalAdmissionController struct {
	mu            sync.Mutex
	tenantTokens  map[string]int
	isThrottled   bool
}

func (c *MultiDimensionalAdmissionController) AdmitRequest(tenantID string, isHeavyEndpoint bool) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	tokens := c.tenantTokens[tenantID]

	cost := 1
	if isHeavyEndpoint {
		cost = 5 // Тяжелый эндпоинт стоит 5 токенов!
	}

	// Динамический троттлинг при деградации задержки: удваивает стоимость пропуска
	if c.isThrottled {
		cost *= 2
	}

	if tokens >= cost {
		c.tenantTokens[tenantID] = tokens - cost
		return true
	}

	return false
}

func (c *MultiDimensionalAdmissionController) OnLatencySpike(p99 time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.isThrottled = p99 > 500*time.Millisecond
}

func TestAdmissionControlMultiDim(t *testing.T) {
	controller := &MultiDimensionalAdmissionController{
		tenantTokens: map[string]int{
			"tenant-gold": 20,
			"tenant-free": 5,
		},
	}

	// 1. Обычный запрос бесплатного тенанта -> разрешен
	okFree1 := controller.AdmitRequest("tenant-free", false)
	if !okFree1 {
		t.Fatal("Обычный запрос должен пройти")
	}

	// 2. Скачок задержки системы -> срабатывает динамический троттлинг
	controller.OnLatencySpike(800 * time.Millisecond)

	// Тяжелый запрос бесплатного тенанта при троттлинге требует 10 токенов (у него осталось 4) -> отказ!
	okFreeHeavy := controller.AdmitRequest("tenant-free", true)
	if okFreeHeavy {
		t.Fatal("Тяжелый запрос бесплатного тенанта обязан быть отсечен контроллером допуска")
	}

	// В то же время золотой тенант свободно проходит!
	okGold := controller.AdmitRequest("tenant-gold", true)
	if !okGold {
		t.Fatal("Золотой тенант имеет достаточную квоту токенов")
	}

	fmt.Println("Многомерный контроль допуска (Admission Control) подтвержден:")
	fmt.Printf("  • Бесплатный тенант (тяжелый эндпоинт при троттлинге): Допуск=%v (Отсечен)\n", okFreeHeavy)
	fmt.Printf("  • Золотой тенант: Допуск=%v (Успешно авторизован по квоте)\n", okGold)
	fmt.Println("  • Адаптивное сжатие квот сохранило стабильность бэкенда при всплеске задержки")
}
```

ℹ️ Многомерный контроль допуска с учетом стоимости эндпоинтов, квот тенантов и адаптивного троттлинга

## Под капотом

В Google Site Reliability Engineering для Admission Control применяют алгоритм **Client-Side Throttling**: клиент сам начинает вероятностно отбрасывать запросы, если отношение отклоненных сервером запросов превышает порог:
$$P_{\text{drop}} = \max\left(0, \frac{\text{requests} - K \times \text{accepts}}{\text{requests} + 1}\right)$$

## Подводные камни

Ставить одинаковую стоимость на быстрые и тяжелые запросы: запрос `GET /items/1` выполняется за 0.2 мс, а `POST /reports/export` грузит диск на 15 секунд. Тяжелые эндпоинты обязаны расходовать пропорционально большее количество токенов допуска.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Admission Control от классического Rate Limiting?»
**Ответ:** Rate Limiting защищает систему от внешнего превышения квот клиентов. Admission Control оценивает **внутреннее текущее здоровье сервера** (очередь задач, память, задержку): он может в любой момент динамически ужесточить лимиты, защищая процесс от падения по OOM или CPU Throttling.
