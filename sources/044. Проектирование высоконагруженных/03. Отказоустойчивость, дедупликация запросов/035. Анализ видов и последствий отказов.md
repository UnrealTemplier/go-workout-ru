# Анализ видов и последствий отказов (Failure Mode and Effects Analysis / FMEA) распределенных систем

## Условие

**Failure Mode Analysis**: Для каждого компонента (БД, Redis, Kafka, external API) проанализируйте: что произойдёт при его падении? Как система деградирует?

## Теория

Методология FMEA (Failure Mode and Effects Analysis) в HighLoad архитектуре:
- Архитектор распределенной системы обязан спроектировать поведение каждого компонента при его внезапном отказе:
  1. **Отказ PostgreSQL Primary:**
     - *Последствие:* невозможность создания новых заказов.
     - *Деградация:* автоматический промоут реплики через Patroni (RTO < 30 сек). Чтение каталога продолжается без сбоев из Read Replicas.
  2. **Отказ Redis Cluster:**
     - *Последствие:* промах кэша.
     - *Деградация:* Cache-Aside прозрачно перенаправляет запросы в СУБД с защитой singleflight.
  3. **Отказ Apache Kafka:**
     - *Последствие:* невозможность немедленной отправки асинхронных уведомлений.
     - *Деградация:* паттерн Transactional Outbox сохраняет события в локальную таблицу PostgreSQL до восстановления брокера.
  4. **Отказ внешнего API (Платежи/Служба доставки):**
     - *Деградация:* срабатывание Circuit Breaker, постановка в очередь повторов DLQ.

## Решение по шагам

1. Создайте архитектурную модель оценки матрицы отказов FMEA.
2. Смоделируйте поведение системы при падении каждого компонента.
3. Продемонстрируйте сценарии мягкой деградации.
4. Верифицируйте непрерывность критических функций бизнеса.

```go
package main

import (
	"fmt"
	"testing"
)

type ComponentFailureAnalysis struct {
	Component          string
	FailureMode        string
	ImmediateImpact    string
	DegradationStrategy string
	DataLossRisk       string
}

func GetEnterpriseFMEAMatrix() []ComponentFailureAnalysis {
	return []ComponentFailureAnalysis{
		{
			Component:          "PostgreSQL Primary",
			FailureMode:        "Авария хоста / сбой диска",
			ImmediateImpact:    "Блокировка транзакций записи",
			DegradationStrategy: "Patroni auto-failover на реплику (RTO < 30s), чтение из Read Replicas",
			DataLossRisk:       "Нулевой (Синхронная репликация, RPO = 0)",
		},
		{
			Component:          "Redis Cache Cluster",
			FailureMode:        "Сетевая изоляция / OOM crash",
			ImmediateImpact:    "100% Cache Miss",
			DegradationStrategy: "Cache-Aside fallback в БД + singleflight защита от stampede",
			DataLossRisk:       "Нулевой (Кэш эфемерный)",
		},
		{
			Component:          "Apache Kafka",
			FailureMode:        "Потеря кворума брокеров",
			ImmediateImpact:    "Остановка стриминга событий",
			DegradationStrategy: "Transactional Outbox накапливает события в таблице PostgreSQL",
			DataLossRisk:       "Нулевой (События закоммичены в БД)",
		},
		{
			Component:          "Внешний Payment Gateway",
			FailureMode:        "HTTP 500 / Таймаут 30 секунд",
			ImmediateImpact:    "Зависание чекаута",
			DegradationStrategy: "Circuit Breaker размыкает цепь + сохранение заказа в статус PENDING_PAYMENT",
			DataLossRisk:       "Нулевой",
		},
	}
}

func TestFMEAMatrixAnalysis(t *testing.T) {
	matrix := GetEnterpriseFMEAMatrix()

	if len(matrix) != 4 {
		t.Fatal("Ожидался анализ 4 ключевых компонентов")
	}

	fmt.Println("Матрица анализа видов и последствий отказов (FMEA Analysis):")
	for _, item := range matrix {
		fmt.Printf("  • Компонент: %-22s | Сбой: %s\n", item.Component, item.FailureMode)
		fmt.Printf("    Стратегия деградации: %s\n", item.DegradationStrategy)
		fmt.Printf("    Риск потери данных:   %s\n\n", item.DataLossRisk)
	}
	fmt.Println("  • Все компоненты имеют автономные контуры самовосстановления и безопасной деградации")
}
```

## Под капотом

В теории надежности FMEA оценивает каждый компонент по трем параметрам от 1 до 10: Вероятность сбоя (Occurrence), Критичность (Severity) и Вероятность обнаружения (Detection). Произведение \(RPN = O \times S \times D\) определяет приоритеты инженерных доработок архитектуры.

## Подводные камни

Полагаться на непроверенные теоретические планы восстановления (Runbooks): если процедура переключения базы данных не тестировалась на стейджинге, в момент боевой аварии она завершится ошибкой из-за несовместимости версий или забытых прав доступа. Планы FMEA проверяют практическим **GameDay Chaos Engineering**.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие понятий RPO и RTO при катастрофических отказах инфраструктуры?»
**Ответ:** 
- **RTO (Recovery Time Objective):** допустимое время простоя системы (время от момента падения до восстановления доступности для клиентов).
- **RPO (Recovery Point Objective):** допустимый объем потерянных данных за время инцидента (например: потеря транзакций за последние 5 секунд или строго 0 байт при синхронной репликации).
