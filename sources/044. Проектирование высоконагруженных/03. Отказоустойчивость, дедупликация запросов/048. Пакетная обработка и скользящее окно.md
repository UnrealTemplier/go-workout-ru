# Пакетная обработка и скользящее окно (Batching & Windowing): сокращение 1000 SQL-запросов до 20

## Условие

Реализуй **Batching + Windowing**: 1000 `GetUser` requests/sec. Individual: 1000 DB queries. Batched: accumulate 50ms window, 1 query `SELECT * FROM users WHERE id IN (...)`. 1000 → 20 queries. Trade-off: latency + throughput.

## Теория

Архитектурный паттерн DataLoader (Batching & Windowing):
- При нагрузке 1 000 запросов `GetUser(id)` в секунду:
  - Обычный подход выполняет 1 000 одиночных запросов `SELECT * FROM users WHERE id = ?`.
  - Затраты СУБД: 1 000 сетевых round-trips, 1 000 парсингов SQL, исчерпание пула коннектов.
- **Паттерн Batching с окном 50 мс:**
  1. Входящие запросы накапливаются в буфере в течение короткого временного окна (50 мс) или по достижении батча в 50 элементов.
  2. Горутина объединяет все ID и выполняет **ровно один запрос**:
     `SELECT * FROM users WHERE id IN (1, 2, ..., 50)`.
  3. Результаты раздаются соответствующим ожидающим клиентам.
  4. Число обращений к БД падает с 1 000 до **всего 20 запросов в секунду**!
  5. *Компромисс:* небольшое увеличение задержки (+25 мс) в обмен на 50-кратный рост пропускной способности (Throughput).

## Решение по шагам

1. Создайте структуру сборщика батчей `BatchingWindowLoader`.
2. Реализуйте накопление идентификаторов пользователей в окне 20 мс.
3. Продемонстрируйте выполнение единого группового SQL-запроса `IN (...)`.
4. Верифицируйте раздачу ответов каждому клиенту.

## Код решения

**`batching_dataloader_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type BatchRequestItem struct {
	UserID   string
	resultCh chan string
}

type BatchingWindowLoader struct {
	mu             sync.Mutex
	incomingQueue  []BatchRequestItem
	windowDuration time.Duration
	dbQueriesCount int64
}

func NewBatchingLoader(window time.Duration) *BatchingWindowLoader {
	loader := &BatchingWindowLoader{
		windowDuration: window,
	}
	go loader.runFlusher()
	return loader
}

func (l *BatchingWindowLoader) GetUser(userID string) string {
	resCh := make(chan string, 1)
	l.mu.Lock()
	l.incomingQueue = append(l.incomingQueue, BatchRequestItem{UserID: userID, resultCh: resCh})
	l.mu.Unlock()

	return <-resCh
}

func (l *BatchingWindowLoader) runFlusher() {
	ticker := time.NewTicker(l.windowDuration)
	for range ticker.C {
		l.mu.Lock()
		if len(l.incomingQueue) == 0 {
			l.mu.Unlock()
			continue
		}
		batch := l.incomingQueue
		l.incomingQueue = nil
		l.mu.Unlock()

		// Единый батчевый запрос к БД вместо N одиночных!
		atomic.AddInt64(&l.dbQueriesCount, 1)

		for _, item := range batch {
			item.resultCh <- fmt.Sprintf("UserEntity[%s]", item.UserID)
		}
	}
}

func TestBatchingDataLoader(t *testing.T) {
	loader := NewBatchingLoader(20 * time.Millisecond)

	const concurrentClients = 50
	var wg sync.WaitGroup
	wg.Add(concurrentClients)

	for i := 1; i <= concurrentClients; i++ {
		go func(id int) {
			defer wg.Done()
			user := loader.GetUser(fmt.Sprintf("user-%d", id))
			if user != fmt.Sprintf("UserEntity[user-%d]", id) {
				t.Errorf("Некорректный результат: %s", user)
			}
		}(i)
	}

	wg.Wait()

	queries := atomic.LoadInt64(&loader.dbQueriesCount)

	// 50 запросов должны были схлопнуться в 1 или максимум 2 батча!
	if queries > 3 {
		t.Fatalf("Слишком много обращений к БД: %d (ожидалось <= 3)", queries)
	}

	fmt.Println("Пакетная обработка и скользящее окно (Batching & Windowing) подтверждены:")
	fmt.Printf("  • Пользовательских вызовов обработано: %d\n", concurrentClients)
	fmt.Printf("  • Физических SQL-запросов к СУБД:      %d (Сокращение обращений в 25 раз!)\n", queries)
	fmt.Println("  • Пропускная способность базы данных увеличена на порядок")
}
```

## Под капотом

В GraphQL библиотеках Go (например `graph-gophers/dataloader` или `vikstrous/dataloadgen`) DataLoader решает каноническую проблему **N+1 Queries**: при рендеринге списка из 100 постов с их авторами выполняется 1 запрос за постами и 1 батч-запрос за всеми 100 авторами вместо 101 обращения к БД.

## Подводные камни

Ставить слишком широкое окно накопления батча (например 500 мс): интерактивные пользователи заметят полусекундную задержку интерфейса. Окно батчинга выбирают в диапазоне **10–30 миллисекунд**, что незаметно для глаза человека, но дает колоссальный выигрыш в Throughput.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Batching от Caching?»
**Ответ:** 
- **Caching:** эффективен, когда разные запросы запрашивают **один и тот же ключ** (например один популярный товар).
- **Batching:** эффективен, когда запросы запрашивают **разные ключи** (пользователи запрашивают 50 разных профилей). Батчинг склеивает их в один SQL `WHERE id IN (...)`, снимая накладные расходы на сетевой стек.
