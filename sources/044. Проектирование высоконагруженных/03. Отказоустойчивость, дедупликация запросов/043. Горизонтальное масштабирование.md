# Горизонтальное масштабирование: балансировка трафика между Stateless-сервисами через K8s Service

## Условие

**Горизонтальное масштабирование: stateless-сервисы**. Спроектируйте сервис так, чтобы любой экземпляр мог обработать любой запрос. Вынесите состояние в Redis (сессии) и БД. Покажите балансировку через Nginx или Kubernetes Service.

## Теория

Принципы оркестрации Stateless в Kubernetes (Service & Endpoints):
- **Kubernetes Deployment:** создает \(N\) идентичных реплик пода (`order-service`).
- **Kubernetes Service (ClusterIP):**
  - Предоставляет единый стабильный виртуальный IP-адрес внутри кластера (`order-service.default.svc.cluster.local`).
  - Компонент `kube-proxy` на каждой ноде кластера настраивает правила ядра Linux `iptables` или `IPVS`.
  - Входящие TCP-соединения прозрачно балансируются случайным или циклическим образом между подами.
- Так как поды полностью Stateless, отказ или удаление любого пода происходит на 100% незаметно для балансировщика!

## Решение по шагам

1. Создайте спецификацию Kubernetes Deployment и Service.
2. Продемонстрируйте балансировку запросов между тремя активными подами.
3. Смоделируйте падение одного пода и проверку автоматического вывода из Endpoints.
4. Верифицируйте непрерывность обслуживания клиентских вызовов.

## Код решения

**`k8s_stateless_service_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

func GenerateStatelessK8sBlueprint() string {
	return `apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
      - name: app
        image: cr.yandex/order-service:v2.0
        env:
        - name: REDIS_URL
          value: "redis-cluster.internal:6379"
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  type: ClusterIP
  selector:
    app: order-service
  ports:
  - port: 80
    targetPort: 8080`
}

func TestK8sStatelessService(t *testing.T) {
	manifest := GenerateStatelessK8sBlueprint()

	if !strings.Contains(manifest, "replicas: 3") || !strings.Contains(manifest, "kind: Service") {
		t.Fatal("Манифест обязан описывать Deployment с репликами и Service")
	}

	if !strings.Contains(manifest, "REDIS_URL") {
		t.Fatal("Stateless сервис обязан выносить сессионное состояние во внешний Redis")
	}

	fmt.Println("Архитектура Stateless сервисов в Kubernetes подтверждена:")
	fmt.Println("  • Декларативное описание содержит 3 реплики и балансировщик ClusterIP Service")
	fmt.Println("  • Состояние сессий полностью отделено от контейнеров и вынесено в Redis")
}
```

## Под капотом

В Kubernetes Service трафик балансируется без проксирования на уровне userspace: `kube-proxy` в режиме IPVS использует хэш-таблицы ядра Linux, переписывая IP назначения сетевого пакета (DNAT) с задержкой менее 5 микросекунд.

## Подводные камни

Использовать длинноживущие gRPC соединения через стандартный Kubernetes ClusterIP Service: HTTP/2 мультиплексирует все вызовы в один постоянный TCP-сокет, поэтому весь gRPC трафик пойдет на **один-единственный под**, оставив остальные реплики пустыми. Для gRPC балансировки используют **Client-Side Balancing или Envoy Service Mesh**.

## На собеседовании

**Вопрос с собеседования:** «Как обеспечить Zero-Downtime Deployment в Kubernetes без потери клиентских запросов?»
**Ответ:** 
1. Настроить стратегию обновления `RollingUpdate` с `maxUnavailable: 0` и `maxSurge: 1`.
2. Настроить `readinessProbe` (под не принимает трафик, пока не прогрелся).
3. Обрабатывать сигнал `SIGTERM` в коде Go с 10-секундным Graceful Shutdown, давая балансировщику время удалить IP пода из таблицы маршрутизации.
