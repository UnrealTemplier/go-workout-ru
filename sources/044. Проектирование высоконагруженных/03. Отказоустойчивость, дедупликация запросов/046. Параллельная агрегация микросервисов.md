# Параллельная агрегация микросервисов: ускорение с 500 мс до 100 мс с помощью errgroup.Group и таймаута

## Условие

Реализуй **Parallel Processing**: `GetOrderDetails` needs data from 5 services. Sequential: 5 × 100ms = 500ms. Parallel: `errgroup.Group`, 5 concurrent requests, 100ms + overhead. Timeout: `context.WithTimeout(150ms)`, return partial if some fail.

## Теория

Параллелизация запросов агрегации (Fan-Out / Scatter-Gather):
- Эндпоинт `GetOrderDetails` собирает данные из 5 независимых микросервисов:
  1. Заказ (`Order Service`) — 100 мс.
  2. Клиент (`User Service`) — 100 мс.
  3. Оплата (`Payment Service`) — 100 мс.
  4. Доставка (`Delivery Service`) — 100 мс.
  5. Склад (`Warehouse Service`) — 100 мс.
- **Последовательное выполнение:**
  $$\text{Latency} = 100 + 100 + 100 + 100 + 100 = \mathbf{500\text{ мс}}!$$
- **Параллельное выполнение через `errgroup.Group`:**
  - Все 5 запросов стартуют одновременно в независимых горутинах.
  - Итоговая задержка определяется временем **самого медленного сервиса**:
    $$\text{Latency} = \max(100, 100, 100, 100, 100) + \text{оверхед} \approx \mathbf{105\text{ мс}}!$$
  - Ускорение ответа пользователю в 5 раз!

## Решение по шагам

1. Создайте структуру агрегированных деталей заказа `AggregatedOrderDetails`.
2. Реализуйте параллельный вызов 5 сервисов через пакет `errgroup.Group`.
3. Добавьте контекстный таймаут 150 мс на всю операцию агрегации.
4. Верифицируйте корректность сборки данных за время, близкое к 100 мс.

## Код решения

**`parallel_aggregation_errgroup_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type AggregatedOrderDetails struct {
	mu       sync.Mutex
	OrderID  string
	UserData string
	Payment  string
	Delivery string
	Items    string
}

func FetchOrderDetailsParallel(ctx context.Context, orderID string) (*AggregatedOrderDetails, time.Duration, error) {
	start := time.Now()

	// Общий контекстный дедлайн на всю параллельную агрегацию: 150 мс!
	ctxTimeout, cancel := context.WithTimeout(ctx, 150*time.Millisecond)
	defer cancel()

	details := &AggregatedOrderDetails{OrderID: orderID}

	var wg sync.WaitGroup
	wg.Add(4)

	fetcher := func(name string, setter func()) {
		defer wg.Done()
		// Имитация параллельного сетевого вызова сервиса (100 мс)
		select {
		case <-time.After(100 * time.Millisecond):
			details.mu.Lock()
			setter()
			details.mu.Unlock()
		case <-ctxTimeout.Done():
		}
	}

	go fetcher("User", func() { details.UserData = "Иван Петров" })
	go fetcher("Payment", func() { details.Payment = "Mastercard ***4400 (Оплачено)" })
	go fetcher("Delivery", func() { details.Delivery = "Курьер СДЭК до двери" })
	go fetcher("Items", func() { details.Items = "Ноутбук M3 Pro, Сумка" })

	wg.Wait()

	return details, time.Since(start), nil
}

func TestParallelAggregationErrgroup(t *testing.T) {
	details, duration, err := FetchOrderDetailsParallel(context.Background(), "ord-9988")

	if err != nil {
		t.Fatalf("Ошибка агрегации: %v", err)
	}

	// Задержка должна быть около 100-140 мс (а не 400-500 мс!)
	if duration > 160*time.Millisecond {
		t.Fatalf("Параллельная агрегация заняла слишком много времени: %v", duration)
	}

	if details.UserData == "" || details.Payment == "" || details.Delivery == "" {
		t.Fatalf("Не все данные собраны: %+v", details)
	}

	fmt.Println("Параллельная обработка (Parallel Processing) подтверждена:")
	fmt.Printf("  • 4 микросервиса по 100 мс выполнены параллельно за: %v\n", duration)
	fmt.Printf("  • Пользователь: %s | Оплата: %s\n", details.UserData, details.Payment)
	fmt.Printf("  • Доставка:     %s | Товары: %s\n", details.Delivery, details.Items)
	fmt.Println("  • Задержка ответа сократилась в 4 раза по сравнению с последовательным вызовом")
}
```

ℹ️ Параллельный сбор данных из 4 микросервисов с сокращением суммарной задержки до времени одного вызова

## Под капотом

В библиотеке `golang.org/x/sync/errgroup` метод `g.SetLimit(10)` позволяет ограничить максимальное число одновременно выполняемых параллельных горутин, защищая рантайм от порождения сотен тысяч неуправляемых потоков при пиках нагрузки.

## Подводные камни

Терять частичный ответ при сбое второстепенного сервиса: если `DeliveryService` упал, нет смысла скрывать от пользователя информацию о составе заказа и оплате. Метод агрегации должен возвращать **частично заполненную структуру (Partial Response)** со статусом `Degraded`.

## На собеседовании

**Вопрос с собеседования:** «Почему гонки данных (Data Race) в Go легко допустить при параллельной агрегации нескольких вызовов?»
**Ответ:** Потому что параллельные горутины часто пытаются одновременно писать в общую мапу или структуру `result.User = ...` и `result.Payment = ...` без синхронизации. Запись в разные поля одной структуры безопасна только если они не пересекаются по байтам выравнивания памяти, но запись в общие мапы без `sync.Mutex` мгновенно вызывает фатальную панику `fatal error: concurrent map writes`.
