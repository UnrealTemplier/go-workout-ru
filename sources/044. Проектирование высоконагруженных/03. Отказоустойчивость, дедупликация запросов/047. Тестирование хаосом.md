# Тестирование хаосом (Chaos Testing: Network Latency): инъекция задержек и проверка таймаутов

## Условие

**Chaos Testing (Network Latency)**: Эмулируйте сетевые задержки через `tc` (traffic control) и проверяйте, что таймауты и retry работают корректно.

## Теория

Инженерия сетевого хаоса (Network Chaos Simulation):
- В локальной среде разработки сеть быстрая и идеальная (\(< 0.5\text{ мс}\)).
- В реальном межрегиональном облаке сеть подвержена непредсказуемым аномалиям:
  - Джиттер оптоволокна, перегрузка коммутаторов, потеря пакетов (Packet Loss).
- **Утилита Linux `tc` (Traffic Control & Netem):**
  - Позволяет на уровне ядра Linux инжектировать задержки прямо на сетевой интерфейс:
    `tc qdisc add dev eth0 root netem delay 300ms 50ms`
- **Проверка надежности Go-кода:**
  - Корректно ли срабатывает `context.WithTimeout`?
  - Не блокируются ли пулы соединений?
  - Срабатывает ли Fallback и Circuit Breaker?

## Решение по шагам

1. Создайте эмулятор адаптера сокетов с управляемой сетевой задержкой `ChaosNetworkAdapter`.
2. Смоделируйте инъекцию сетевой задержки 400 мс при клиентском лимите таймаута 100 мс.
3. Докажите, что клиент прерывает ожидание строго по таймауту 100 мс.
4. Верифицируйте срабатывание защитных механизмов системы.

## Код решения

**`chaos_network_latency_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"
)

type ChaosNetworkAdapter struct {
	injectedDelay time.Duration
}

func (a *ChaosNetworkAdapter) CallRemoteService(ctx context.Context) (string, error) {
	select {
	case <-time.After(a.injectedDelay):
		return "HTTP 200 OK from Downstream", nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}

func TestChaosNetworkLatency(t *testing.T) {
	// Эмулируем катастрофическую задержку сети 400 мс через Chaos Netem
	adapter := &ChaosNetworkAdapter{injectedDelay: 400 * time.Millisecond}

	// Клиент имеет жесткий таймаут 100 мс
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	start := time.Now()
	_, err := adapter.CallRemoteService(ctx)
	duration := time.Since(start)

	if !errors.Is(err, context.DeadlineExceeded) {
		t.Fatalf("Ожидался сбой по DeadlineExceeded: %v", err)
	}

	// Запрос должен был прерваться за 100-130 мс, а не ждать 400 мс!
	if duration > 150*time.Millisecond {
		t.Fatalf("Клиент не оборвал соединение вовремя: %v", duration)
	}

	fmt.Println("Тестирование хаосом (Chaos Testing: Network Latency) подтверждено:")
	fmt.Printf("  • Инжектированная задержка сокета (Netem): 400 мс\n")
	fmt.Printf("  • Фактическое время прерывания клиентом:  %v\n", duration)
	fmt.Printf("  • Результат проверки:                   %v\n", err)
	fmt.Println("  • Система доказала устойчивость к деградации качества сетевых каналов")
}
```

## Под капотом

В Chaos Mesh эксперимент с сетью настраивается ресурсом `NetworkChaos` с действием `delay`:
```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: network-delay-example
spec:
  action: delay
  mode: all
  selector:
    namespaces: [prod]
    labelSelectors: { "app": "payment-service" }
  delay:
    latency: "300ms"
    jitter: "50ms"
```

## Подводные камни

Забывать удалять правила `tc` после завершения тестов: забытое правило задержки в Docker-контейнере заставит разработчиков неделями искать причину низкой производительности. В скриптах всегда используют конструкцию очистки `defer cleanup: tc qdisc del dev eth0 root`.

## На собеседовании

**Вопрос с собеседования:** «Как сымитировать сетевое разделение (Network Partition / Split-Brain) в кластере Kubernetes?»
**Ответ:** С помощью сетевых политик Kubernetes NetworkPolicy или команды `iptables -A INPUT -s <node_ip> -j DROP`: пакеты между узлом А и узлом Б полностью отбрасываются, симулируя обрыв оптоволоконной связи между дата-центрами для проверки алгоритма кворума Raft/etcd.
