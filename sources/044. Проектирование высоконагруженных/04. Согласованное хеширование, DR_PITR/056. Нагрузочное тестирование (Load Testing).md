# Нагрузочное тестирование (Load Testing): профилирование точки перегиба (Breaking Point) с k6 и vegeta

## Условие

**Load Testing**: Используйте `k6`, `vegeta` или `wrk` для нагрузочного тестирования. Определите max RPS, P99 latency, breaking point.

## Теория

Методология нагрузочного тестирования (Load & Stress Testing):
- Нельзя запускать систему в продакшен, не зная ее точки разрушения (Breaking Point).
- **Виды нагрузочных тестов:**
  1. **Baseline Test (Дымовой):** проверка отклика при штатной нагрузке (например 1 000 RPS). Замер базовой задержки P50 и P99.
  2. **Stress Test (Стресс-тест):** ступенчатое наращивание нагрузки (\(1k \to 5k \to 10k \to 25k\text{ RPS}\)). Поиск точки, где задержка P99 резко взлетает вверх (Точка перегиба / Knee Point).
  3. **Soak Test (Тест на выносливость):** подача 70% нагрузки непрерывно в течение 24 часов для выявления медленных утечек памяти (Memory Leaks) и дескрипторов сокетов.
  4. **Spike Test (Всплеск):** мгновенный скачок нагрузки в 10 раз за 5 секунд для проверки HPA и кэшей.

## Решение по шагам

1. Создайте спецификацию нагрузочного сценария k6.
2. Смоделируйте генерацию отчета нагрузочного тестирования.
3. Продемонстрируйте определение точки деградации (Breaking Point).
4. Верифицируйте соответствие критериям производительности.

## Код решения

**`load_testing_k6_spec_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
	"time"
)

type LoadTestReport struct {
	TargetRPS       int
	P50Latency      time.Duration
	P99Latency      time.Duration
	ErrorRatePercent float64
	IsBreakingPoint bool
}

func AnalyzeLoadTestResults(reports []LoadTestReport) (int, time.Duration) {
	maxSafeRPS := 0
	safeP99 := time.Duration(0)

	for _, r := range reports {
		if r.ErrorRatePercent < 0.1 && r.P99Latency < 200*time.Millisecond {
			maxSafeRPS = r.TargetRPS
			safeP99 = r.P99Latency
		} else {
			break
		}
	}
	return maxSafeRPS, safeP99
}

func TestLoadTestingK6Spec(t *testing.T) {
	// Ступенчатый стресс-тест
	stressRun := []LoadTestReport{
		{TargetRPS: 1000, P50Latency: 5 * time.Millisecond, P99Latency: 25 * time.Millisecond, ErrorRatePercent: 0.0},
		{TargetRPS: 5000, P50Latency: 12 * time.Millisecond, P99Latency: 45 * time.Millisecond, ErrorRatePercent: 0.0},
		{TargetRPS: 10000, P50Latency: 28 * time.Millisecond, P99Latency: 95 * time.Millisecond, ErrorRatePercent: 0.02},
		// Точка перегиба: на 15 000 RPS P99 превысил лимит SLA 200 мс!
		{TargetRPS: 15000, P50Latency: 180 * time.Millisecond, P99Latency: 850 * time.Millisecond, ErrorRatePercent: 1.5, IsBreakingPoint: true},
	}

	maxSafe, p99 := AnalyzeLoadTestResults(stressRun)

	if maxSafe != 10000 {
		t.Fatalf("Некорректная точка безопасной емкости: %d", maxSafe)
	}

	fmt.Println("Нагрузочное тестирование (Load Testing Analysis) подтверждено:")
	fmt.Printf("  • Максимальная безопасная емкость (Max Safe RPS): %d RPS\n", maxSafe)
	fmt.Printf("  • Задержка P99 на максимальной нагрузке:         %v (В пределах SLA 200ms)\n", p99)
	fmt.Println("  • Точка деградации (Breaking Point) обнаружена на 15 000 RPS (исчерпание пула СУБД)")
}
```

## Под капотом

Генератор нагрузки `vegeta` написан на Go и способен выдавать до 50 000 RPS с одного ноутбука благодаря эффективному переиспользованию пула сокетов и минимальным аллокациям памяти.

## Подводные камни

Запускать нагрузочный генератор с того же сервера, где работает тестируемый сервис: генератор нагрузки сожжет 50% CPU на генерацию запросов, исказив результаты замеров. Нагрузку подают **строго с выделенных независимых инстансов генераторов в той же приватной сети**.

## На собеседовании

**Вопрос с собеседования:** «Что такое 'Coordinated Omission' (Скоординированный пропуск) в нагрузочном тестировании и почему многие утилиты врут про P99?»
**Ответ:** Если сервер завис на 10 секунд, традиционный инструмент ждет ответа и не отправляет новые запросы. В результате за 10 секунд регистрируется только 1 медленный запрос вместо 10 000 зависших. Инструменты вроде `wrk2` и `k6` отправляют запросы по строгому расписанию таймера, объективно учитывая время ожидания в очереди.
