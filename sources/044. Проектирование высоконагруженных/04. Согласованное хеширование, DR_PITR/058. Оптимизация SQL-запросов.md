# Оптимизация SQL-запросов: анализ плана EXPLAIN ANALYZE и устранение Seq Scan

## Условие

**Database Query Optimization**: Используйте `EXPLAIN ANALYZE` для медленных запросов. Добавляйте индексы, оптимизируйте JOIN'ы, используйте materialized views.

## Теория

Анатомия оптимизации запросов PostgreSQL через `EXPLAIN (ANALYZE, BUFFERS)`:
- **Красные флаги плана запроса:**
  1. `Seq Scan (Последовательное сканирование)`: СУБД читает всю таблицу с диска блок за блоком. При миллионе строк это секунды задержки.
  2. `Filter (Rows Removed by Filter)`: миллионы прочитанных строк отбрасываются из-за отсутствия подходящего индекса.
- **Оптимизации:**
  - `Index Scan` / `Bitmap Index Scan`: переход по B-Tree индексу за \(O(\log N)\).
  - `Index Only Scan`: все запрошенные поля (`SELECT id, status`) содержатся в самом индексе (`INCLUDE`), обращение к таблице на диске (Heap Fetch) не требуется вообще!
  - Замена тяжелых коррелированных подзапросов на денормализованные представления.

## Решение по шагам

1. Создайте модель анализатора плана запросов СУБД `QueryPlanAnalyzer`.
2. Реализуйте обнаружение неэффективных `Seq Scan` операций.
3. Продемонстрируйте переход к `Index Only Scan` после добавления B-Tree индекса.
4. Верифицируйте сокращение времени выполнения запроса.

## Код решения

**`query_optimization_explain_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type ExecutionPlan struct {
	QueryText     string
	ScanType      string // "Seq Scan", "Index Scan", "Index Only Scan"
	CostEstimate  float64
	ExecutionTimeMs float64
}

func OptimizeSlowQuery(unindexedPlan ExecutionPlan) ExecutionPlan {
	if unindexedPlan.ScanType == "Seq Scan" {
		// Добавление B-Tree индекса CREATE INDEX idx_orders_user_status ON orders(user_id, status);
		return ExecutionPlan{
			QueryText:       unindexedPlan.QueryText,
			ScanType:        "Index Only Scan using idx_orders_user_status",
			CostEstimate:    12.5,
			ExecutionTimeMs: 0.8, // ускорение в 300 раз!
		}
	}
	return unindexedPlan
}

func TestQueryOptimizationExplain(t *testing.T) {
	slowPlan := ExecutionPlan{
		QueryText:       "SELECT id, status FROM orders WHERE user_id = 42 AND status = 'ACTIVE';",
		ScanType:        "Seq Scan",
		CostEstimate:    45000.0,
		ExecutionTimeMs: 245.0, // 245 миллисекунд!
	}

	optimizedPlan := OptimizeSlowQuery(slowPlan)

	if !strings.Contains(optimizedPlan.ScanType, "Index Only Scan") || optimizedPlan.ExecutionTimeMs > 2.0 {
		t.Fatalf("Оптимизация не устранила Seq Scan: %+v", optimizedPlan)
	}

	fmt.Println("Оптимизация SQL-запросов (EXPLAIN ANALYZE) подтверждена:")
	fmt.Printf("  • До оптимизации:  %s (Время: %.1f мс, Cost: %.0f)\n",
		slowPlan.ScanType, slowPlan.ExecutionTimeMs, slowPlan.CostEstimate)
	fmt.Printf("  • После индексов:   %s (Время: %.1f мс, Cost: %.1f)\n",
		optimizedPlan.ScanType, optimizedPlan.ExecutionTimeMs, optimizedPlan.CostEstimate)
	fmt.Println("  • Устранение последовательного сканирования ликвидировало дисковые очереди в СУБД")
}
```

ℹ️ Анализ плана выполнения EXPLAIN ANALYZE и переход от полного Seq Scan к Index Only Scan

## Под капотом

В PostgreSQL ключевая подсказка скрыта в `BUFFERS`: `shared hit=1240 read=0` означает, что все блоки прочитаны из оперативной памяти кэша страниц (Shared Buffers), а `read=5400` означает реальные физические чтения с SSD-диска.

## Подводные камни

Создавать слишком много индексов на таблицу с высокой частотой записи: каждый `INSERT` требует обновления не только таблицы, но и всех 10 индексов на ней, снижая скорость записи в 5 раз. Индексы должны быть строго выверены.

## На собеседовании

**Вопрос с собеседования:** «Почему составной индекс (a, b) не работает для запроса WHERE b = 10?»
**Ответ:** По правилу крайнего левого префикса (Leftmost Prefix Rule). B-Tree индекс сортируется сначала по первой колонке `a`, а внутри равных значений `a` — по колонке `b`. Без указания фильтра по колонке `a` дерево не может выполнить логарифмический спуск и вынуждено сканировать весь индекс целиком.
