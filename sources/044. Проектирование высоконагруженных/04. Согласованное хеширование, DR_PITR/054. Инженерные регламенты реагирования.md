# Инженерные регламенты реагирования (Incident Response Runbooks): пошаговые сценарии ликвидации аварий

## Условие

**Runbooks**: Документируйте процедуры для incident response: "что делать при high CPU", "что делать при DB connection pool exhaustion".

## Теория

Культура Runbook / Playbook в DevOps и SRE:
- В 03:00 ночи при срабатывании пейджера дежурный инженер находится в состоянии стресса и недосыпа.
- Думать и импровизировать в этот момент опасно: цена ошибки — уничтожение боевой базы.
- **Стандарт Runbook (Интерактивная инструкция):**
  - Каждый Prometheus-алерт обязан содержать прямую ссылку на Runbook:
    `runbook_url: "https://wiki.corp.ru/sre/runbooks/db-pool-exhausted"`
  - Структура регламента:
    1. **Что означает алерт:** симптомы, влияние на пользователей.
    2. **Диагностические команды:** точные CLI-команды для проверки состояния.
    3. **Немедленные шаги локализации (Mitigation):** как быстро вернуть сервис к жизни (перезапуск, сброс кэша, включение Load Shedding).
    4. **Шаги глубокого расследования (Root Cause):** поиск виновного запроса или утечки.

## Решение по шагам

1. Создайте декларативную структуру регламента инцидентов `IncidentRunbook`.
2. Реализуйте регистрацию пошаговых сценариев ликвидации аварий.
3. Продемонстрируйте сценарий реакции на истощение пула соединений БД.
4. Верифицируйте доступность команд локализации.

## Код решения

**`incident_runbooks_spec_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type IncidentRunbook struct {
	AlertName        string
	Severity         string
	ImmediateActions []string
	DiagnosticCLI    []string
	EscalationTeam   string
}

func GetDBPoolExhaustionRunbook() IncidentRunbook {
	return IncidentRunbook{
		AlertName: "PostgresConnectionPoolExhausted",
		Severity:  "P1 - Critical",
		ImmediateActions: []string{
			"1. Включить Load Shedding на API Gateway (отсечь низкоприоритетный трафик)",
			"2. Проверить висящие блокировки: SELECT pid, query, age(clock_timestamp(), query_start) FROM pg_stat_activity WHERE state != 'idle';",
			"3. Принудительно завершить зависший запрос: SELECT pg_terminate_backend(pid);",
			"4. Перезапустить PgBouncer при необходимости: systemctl reload pgbouncer",
		},
		DiagnosticCLI: []string{
			"kubectl logs -n prod -l app=order-service --tail=100 | grep 'pool exhaustion'",
			"pg_top -s 1",
		},
		EscalationTeam: "DBA Team / SRE On-Call",
	}
}

func TestIncidentRunbooksSpec(t *testing.T) {
	rb := GetDBPoolExhaustionRunbook()

	if rb.Severity != "P1 - Critical" || len(rb.ImmediateActions) < 3 {
		t.Fatal("Регламент обязан содержать исчерпывающие инструкции локализации аварии")
	}

	fmt.Println("Инженерный регламент реагирования (Incident Runbook) подтвержден:")
	fmt.Printf("  • Алерт: %s (Уровень: %s)\n", rb.AlertName, rb.Severity)
	fmt.Println("  • Пошаговые действия дежурного:")
	for _, act := range rb.ImmediateActions {
		fmt.Printf("    %s\n", act)
	}
	fmt.Printf("  • Команда эскалации: %s\n", rb.EscalationTeam)
	fmt.Println("  • Четкие стандартизированные инструкции ликвидируют человеческий фактор в момент сбоя")
}
```

## Под капотом

В современных SRE платформах (PagerDuty, Grafana OnCall) внедряют **Executable Runbooks**: дежурный прямо из Slack или веб-интерфейса может нажать кнопку «Restart PgBouncer» или «Drop Slow Queries», и безопасный автоматизированный сценарий выполняется через AWX/Ansible без необходимости ручного входа по SSH на боевые серверы.

## Подводные камни

Устаревание инструкций (Stale Runbooks): сервис переехал в Kubernetes, а в Runbook до сих пор написаны команды `systemctl restart service`. Регламенты хранят в Git рядом с кодом сервиса и актуализируют в рамках Post-Mortem анализа каждого инцидента.

## На собеседовании

**Вопрос с собеседования:** «Что такое Blameless Post-Mortem (Разбор инцидента без поиска виноватых)?»
**Ответ:** Это фундаментальный принцип культуры инженерии BigTech (Google SRE): ошибки людей неизбежны. Цель разбора — не наказать разработчика, допустившего ошибку, а выявить системные изъяны в архитектуре, тестах и мониторинге, и разработать автоматические защитные механизмы (Guardrails), делающие повторение этой ошибки физически невозможным.
