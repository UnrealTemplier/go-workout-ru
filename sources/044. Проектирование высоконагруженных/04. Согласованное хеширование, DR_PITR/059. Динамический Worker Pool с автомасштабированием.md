# Динамический Worker Pool с автомасштабированием: порождение дополнительных горутин при росте очереди

## Условие

**Worker Pool с динамическим масштабированием (Auto-scaling)**: Напиши Worker Pool, который по умолчанию держит 5 горутин. Если длина очереди задач превышает 100, пул должен временно породить еще 20 горутин (до лимита). Когда очередь пустеет — убивать "лишние" горутины для экономии памяти.

## Теория

Принципы эластичного пула воркеров (Elastic Dynamic Worker Pool):
- Статический пул фиксированного размера либо не справляется с пиками, либо впустую расходует память во время ночного простоя.
- **Архитектура Elastic Worker Pool:**
  1. `MinWorkers` (базовый уровень): 5 постоянных горутин.
  2. Если длина очереди задач `len(queue)` превышает пороговое значение (например 100):
     - Пул динамически порождает дополнительные `Burstable Workers` (до `MaxWorkers = 25`).
  3. Если в течение определенного времени (Idle Timeout) очередь пустеет:
     - Дополнительные воркеры выходят из цикла и завершают свою работу.
     - Пул плавно сжимается обратно до базовых 5 горутин!

## Решение по шагам

1. Создайте структуру эластичного пула `DynamicWorkerPool`.
2. Реализуйте логику порождения дополнительных воркеров при заполнении очереди.
3. Смоделируйте автоматическое завершение временных горутин при разгрузке.
4. Верифицируйте сохранение базового числа воркеров.

## Код решения

**`dynamic_worker_pool_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type DynamicWorkerPool struct {
	mu           sync.Mutex
	minWorkers   int
	maxWorkers   int
	activeCount  int32
	taskQueue    chan func()
	scaleThreshold int
}

func NewDynamicWorkerPool(min, max, threshold, queueSize int) *DynamicWorkerPool {
	p := &DynamicWorkerPool{
		minWorkers:     min,
		maxWorkers:     max,
		scaleThreshold: threshold,
		taskQueue:      make(chan func(), queueSize),
	}

	// Запуск базовых 5 воркеров
	for i := 0; i < min; i++ {
		p.startWorker(false)
	}
	return p
}

func (p *DynamicWorkerPool) startWorker(isTemporary bool) {
	atomic.AddInt32(&p.activeCount, 1)
	go func() {
		defer atomic.AddInt32(&p.activeCount, -1)
		for {
			if isTemporary {
				// Временный воркер ждет задачу с таймаутом
				select {
				case task := <-p.taskQueue:
					task()
				case <-time.After(30 * time.Millisecond):
					return // Убиваем лишнюю горутину при простое очереди!
				}
			} else {
				// Базовый воркер ждет вечно
				task := <-p.taskQueue
				task()
			}
		}
	}()
}

func (p *DynamicWorkerPool) Submit(task func()) {
	p.mu.Lock()
	// Если очередь превысила порог и мы еще не достигли maxWorkers -> скейлимся!
	if len(p.taskQueue) >= p.scaleThreshold && int(atomic.LoadInt32(&p.activeCount)) < p.maxWorkers {
		p.startWorker(true)
	}
	p.mu.Unlock()

	p.taskQueue <- task
}

func TestDynamicWorkerPool(t *testing.T) {
	// Базово 2 воркера, макс 6, порог масштабирования: очередь >= 3
	pool := NewDynamicWorkerPool(2, 6, 3, 50)

	initialActive := atomic.LoadInt32(&pool.activeCount)
	if initialActive != 2 {
		t.Fatalf("Начальное число воркеров должно быть 2: %d", initialActive)
	}

	// Отправляем пачку из 15 задач для вызова масштабирования
	var wg sync.WaitGroup
	for i := 0; i < 15; i++ {
		wg.Add(1)
		pool.Submit(func() {
			time.Sleep(10 * time.Millisecond)
			wg.Done()
		})
	}

	time.Sleep(15 * time.Millisecond)
	scaledActive := atomic.LoadInt32(&pool.activeCount)

	if scaledActive <= 2 {
		t.Fatalf("Пул обязан был смасштабироваться выше 2 воркеров: %d", scaledActive)
	}

	wg.Wait()

	// Ждем простоя очереди -> временные воркеры должны завершиться
	time.Sleep(60 * time.Millisecond)
	idleActive := atomic.LoadInt32(&pool.activeCount)

	if idleActive != 2 {
		t.Fatalf("После простоя пул обязан сжаться обратно до 2 воркеров: %d", idleActive)
	}

	fmt.Println("Динамический Worker Pool с автомасштабированием подтвержден:")
	fmt.Printf("  • Базовые воркеры:          %d\n", initialActive)
	fmt.Printf("  • Пик во время наплыва:      %d воркеров (Scale Up)\n", scaledActive)
	fmt.Printf("  • После опустошения очереди: %d воркера (Scale Down)\n", idleActive)
	fmt.Println("  • Эластичное управление памятью и горутинами успешно верифицировано")
}
```

## Подводные камни

Порождать новые горутины на каждый чих без ограничения `maxWorkers`: при залипании базы данных сервер создаст 100 000 горутин, вызвав исчерпание памяти. Потолок `maxWorkers` обязан быть строго фиксированным.

## На собеседовании

**Вопрос с собеседования:** «Сколько памяти занимает одна простаивающая горутина в Go?»
**Ответ:** Начальный размер стека горутины в Go составляет всего **2 КБ** (по сравнению с 1–8 МБ для потока операционной системы в Java/C++). Однако при глубоком стеке вызовов размер может вырастать до 1 ГБ (лимит 64-битных систем). Динамическое завершение простаивающих горутин предотвращает фрагментацию виртуальной памяти процесса.
