# Оптимизация пула соединений PostgreSQL: расчет формулы железа и мультиплексирование PgBouncer

## Условие

**Connection Pooling**: Настройте optimal pool size для PostgreSQL (`max_conns = (core_count * 2) + disk_spindles`). Используйте PgBouncer для connection multiplexing.

## Теория

Формула расчета оптимального пула соединений PostgreSQL:
- Вопреки интуиции, увеличение числа соединений с базой **не увеличивает**, а **замедляет** производительность СУБД.
- 1000 конкурентных транзакций на 16-ядерном сервере приводят к тому, что процессор тратит 80% времени на переключение контекста между процессами.
- **Формула команды PostgreSQL:**
  $$\text{MaxConnections} = (\text{CPU Cores} \times 2) + \text{Effective Spindles}$$
  - Для 16-ядерного сервера с быстрым NVMe SSD (\(\text{Spindles} \approx 1\)):
    $$\text{MaxConns} = (16 \times 2) + 1 = \mathbf{33\text{ соединения}}!$$
- **Связка с PgBouncer:**
  - 1000 подов приложений подключаются к PgBouncer.
  - PgBouncer держит к реальному PostgreSQL ровно 33 соединения, обеспечивая 100% утилизацию ядер CPU без перегрузки!

## Решение по шагам

1. Создайте калькулятор размера пула соединений по параметрам серверного железа.
2. Продемонстрируйте расчет емкости для серверов разной мощности.
3. Опишите параметры конфигурации PgBouncer `pool_mode = transaction`.
4. Верифицируйте оптимальную конфигурацию.

## Код решения

**`optimal_connection_pooling_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ServerHardwareSpec struct {
	CPUCores     int
	DiskSpindles int
}

func CalculateOptimalPostgresPool(spec ServerHardwareSpec) int {
	// Официальная формула: connections = (core_count * 2) + effective_spindles
	return (spec.CPUCores * 2) + spec.DiskSpindles
}

func TestOptimalConnectionPooling(t *testing.T) {
	serverSpec16Core := ServerHardwareSpec{CPUCores: 16, DiskSpindles: 1} // NVMe SSD
	serverSpec64Core := ServerHardwareSpec{CPUCores: 64, DiskSpindles: 1} // HighLoad Enterprise

	pool16 := CalculateOptimalPostgresPool(serverSpec16Core)
	pool64 := CalculateOptimalPostgresPool(serverSpec64Core)

	if pool16 != 33 || pool64 != 129 {
		t.Fatalf("Некорректный расчет пула: 16core=%d, 64core=%d", pool16, pool64)
	}

	fmt.Println("Расчет оптимального пула соединений PostgreSQL подтвержден:")
	fmt.Printf("  • Сервер 16 CPU (NVMe): Оптимальный пул к СУБД = %d соединений\n", pool16)
	fmt.Printf("  • Сервер 64 CPU (NVMe): Оптимальный пул к СУБД = %d соединений\n", pool64)
	fmt.Println("  • PgBouncer мультиплексирует 10 000 клиентских подов в эти 33 соединения с пиковой скоростью")
}
```

## Под капотом

В `pgbouncer.ini` ключевыми настройками являются: `pool_mode = transaction`, `default_pool_size = 33`, `max_client_conn = 10000`. При этом размер памяти PgBouncer составляет всего ~50 МБ, так как он работает на базе ультралегковесного Event Loop на epoll.

## Подводные камни

Выставлять `max_connections = 5000` в `postgresql.conf`: база выделит под каждый процесс буферы памяти и таблицы блокировок, что приведет к деградации производительности на 40% даже при отсутствии реальной нагрузки.

## На собеседовании

**Вопрос с собеседования:** «Почему при использовании PgBouncer в режиме Transaction Pooling перестает работать функция LISTEN/NOTIFY?»
**Ответ:** Потому что `LISTEN/NOTIFY` требует постоянной привязки к конкретному клиентскому бэкенд-процессу PostgreSQL. В режиме Transaction Pooling соединение после коммита транзакции передается другому клиенту, поэтому подписка на уведомления разрывается. Для нотификаций выделяют отдельный пул соединений в режиме `Session Pooling` или используют Redis Pub/Sub.
