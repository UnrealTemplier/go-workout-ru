# Тестирование хаосом (Chaos Testing: Database Failover): автоматическое переключение на реплику

## Условие

**Chaos Testing (Database Failover)**: Остановите primary БД и проверьте, что приложение корректно переключается на replica.

## Теория

Сценарий аварийного переключения СУБД (Database Failover Chaos):
- Внезапная смерть мастера PostgreSQL (падение хоста, отключение питания, сбой гипервизора) — главный кошмар инженера.
- **Оркестратор Patroni + etcd:**
  1. etcd фиксирует потерю Heartbeat лидера (Lease TTL 10 секунд).
  2. Patroni проводит выборы (Raft consensus) среди реплик и назначает реплику с максимальным LSN новым лидером (`PROMOTE`).
  3. Виртуальный IP-адрес или DNS-запись `pg-primary.internal` переключается на новый мастер.
- **Поведение Go-приложения:**
  - Пул `pgxpool` перехватывает ошибку `driver: bad connection` или `read-only transaction`.
  - Закрывает сломанные сокеты и по алгоритму Exponential Backoff переподключается к новому мастеру без перезапуска сервиса!

## Решение по шагам

1. Создайте модель пула соединений с автоматическим переключением мастера `FailoverDBClient`.
2. Смоделируйте внезапную остановку Primary узла инжектором хаоса.
3. Продемонстрируйте автоматическое обнаружение нового промоутированного мастера.
4. Верифицируйте успешное восстановление транзакций записи.

## Код решения

**`chaos_db_failover_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type DatabaseNode struct {
	Name    string
	IsAlive bool
	IsRoleMaster bool
}

type FailoverDBClient struct {
	primaryNode *DatabaseNode
	replicaNode *DatabaseNode
}

func (c *FailoverDBClient) WriteRecord(record string) (string, error) {
	// 1. Попытка записи в текущий Primary
	if c.primaryNode.IsAlive && c.primaryNode.IsRoleMaster {
		return fmt.Sprintf("Written to %s: %s", c.primaryNode.Name, record), nil
	}

	// 2. Если Primary упал, проверяем промоутированную реплику (Failover)
	if c.replicaNode.IsAlive && c.replicaNode.IsRoleMaster {
		return fmt.Sprintf("Written to %s (Promoted New Master): %s", c.replicaNode.Name, record), nil
	}

	return "", errors.New("database cluster unavailable: no active master node")
}

func TestChaosDBFailover(t *testing.T) {
	client := &FailoverDBClient{
		primaryNode: &DatabaseNode{Name: "pg-master-01", IsAlive: true, IsRoleMaster: true},
		replicaNode: &DatabaseNode{Name: "pg-replica-02", IsAlive: true, IsRoleMaster: false},
	}

	// 1. Запись в штатный мастер
	res1, err1 := client.WriteRecord("Tx 101")
	if err1 != nil || res1 != "Written to pg-master-01: Tx 101" {
		t.Fatalf("Ошибка штатной записи: %v, %s", err1, res1)
	}

	// 2. CHAOS EXPERIMENT: Аварийное падение pg-master-01
	client.primaryNode.IsAlive = false

	// Проверяем недоступность до промоута
	_, errBeforePromote := client.WriteRecord("Tx 102")
	if errBeforePromote == nil {
		t.Fatal("Запись должна была вернуть ошибку до промоута реплики")
	}

	// 3. Patroni промоутирует pg-replica-02 в нового мастера!
	client.replicaNode.IsRoleMaster = true

	// 4. Повторная попытка клиента: успешная запись в новый мастер!
	res2, err2 := client.WriteRecord("Tx 102")
	if err2 != nil || res2 != "Written to pg-replica-02 (Promoted New Master): Tx 102" {
		t.Fatalf("Ошибка записи после failover: %v, %s", err2, res2)
	}

	fmt.Println("Тестирование хаосом (Chaos Testing: DB Failover) подтверждено:")
	fmt.Printf("  • Запись до аварии:        %s\n", res1)
	fmt.Printf("  • Авария мастера:          %s упал!\n", client.primaryNode.Name)
	fmt.Printf("  • Запись после Failover:   %s\n", res2)
	fmt.Println("  • Автоматический промоут реплики восстановил доступность кластера без даунтайма")
}
```

ℹ️ Автоматическое переключение клиентского пула на промоутированную реплику при падении Primary СУБД

## Под капотом

В драйвере `jackc/pgx/v5` параметр `target_session_attrs=read-write` заставляет пул автоматически перебирать список адресов `pg-1,pg-2,pg-3` и выполнять проверку `SHOW transaction_read_only`: как только реплика переходит в `off`, драйвер мгновенно направляет транзакции на нее.

## Подводные камни

Проблема Split-Brain (Разделение сознания): если старый мастер оживет и продолжит принимать запись параллельно с новым мастером, данные рассинхронизируются. Для исключения Split-Brain в Patroni используют механизм аппаратного отключения старого узла **STONITH / Fencing** (Shoot The Other Node In The Head).

## На собеседовании

**Вопрос с собеседования:** «Что происходит с транзакциями, которые были в процессе выполнения (In-Flight) в момент падения мастера СУБД?»
**Ответ:** Незавершенные транзакции обрываются с ошибкой сети. Клиентский код перехватывает ошибку и повторяет операцию на новом мастере. При этом для исключения дублирования списания денег операция **обязана использовать ключ идемпотентности (Idempotency-Key)**.
