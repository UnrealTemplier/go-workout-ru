# Резервное копирование и восстановление (Backup & Restore): метрики RPO/RTO и Point-in-Time Recovery

## Условие

**Backup and Restore**: Регулярные backups БД с тестированием restore procedure. RPO (Recovery Point Objective) и RTO (Recovery Time Objective).

## Теория

Золотые стандарты резервного копирования баз данных:
- **Шрёдингеровский бэкап:** *«Состояние любого бэкапа неизвестно до тех пор, пока вы не попытались из него восстановиться»*. Бэкап, восстановление из которого не тестировалось — не существует!
- **Методы бэкапа в PostgreSQL:**
  1. **Логический бэкап (`pg_dump`):** текстовый SQL дамп. Медленный (часы на терабайт), блокирует таблицы, не подходит для Enterprise.
  2. **Физический инкрементальный бэкап (pgBackRest / WAL-G):**
     - Еженедельный полный слепок файлов БД (Full Backup).
     - Ежедневные дифференциальные слепки (Diff Backup).
     - Непрерывная архивация журналов WAL в S3 в реальном времени.
  3. **Point-in-Time Recovery (PITR):** возможность восстановить состояние базы данных **на любую секунду в прошлом** (например: «откатить на 13:42:15, за секунду до случайного `DROP TABLE` стажером»).

## Решение по шагам

1. Создайте модель расчета допустимых потерь данных (RPO) и времени восстановления (RTO).
2. Реализуйте проверку успешности процедуры тестового восстановления.
3. Продемонстрируйте алгоритм расчета точки восстановления PITR.
4. Верифицируйте соответствие SLA резервного копирования.

## Код решения

**`backup_restore_pitr_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type BackupRecoveryPolicy struct {
	MaxAllowedRPO time.Duration // Допустимая потеря данных
	MaxAllowedRTO time.Duration // Допустимое время простоя
}

type RestoreProcedureTestResult struct {
	TargetTimestamp time.Time
	ActualRestoreTime time.Duration
	DataLossGap       time.Duration
	IntegrityVerified bool
}

func ExecuteTestRestore(targetTime time.Time, lastWALArchived time.Time) RestoreProcedureTestResult {
	start := time.Now()
	// Имитация разархивирования WAL и наката транзакций
	time.Sleep(10 * time.Millisecond)

	gap := targetTime.Sub(lastWALArchived)
	if gap < 0 {
		gap = -gap
	}

	return RestoreProcedureTestResult{
		TargetTimestamp:   targetTime,
		ActualRestoreTime: time.Since(start),
		DataLossGap:       gap,
		IntegrityVerified: true,
	}
}

func TestBackupRestorePITR(t *testing.T) {
	policy := BackupRecoveryPolicy{
		MaxAllowedRPO: 1 * time.Minute,  // RPO не более 1 минуты
		MaxAllowedRTO: 15 * time.Minute, // RTO не более 15 минут
	}

	targetIncidentTime := time.Date(2026, 9, 4, 14, 30, 0, 0, time.UTC)
	lastWAL := time.Date(2026, 9, 4, 14, 29, 55, 0, time.UTC) // 5 секунд разницы

	result := ExecuteTestRestore(targetIncidentTime, lastWAL)

	if !result.IntegrityVerified || result.DataLossGap > policy.MaxAllowedRPO {
		t.Fatalf("Нарушение SLA политики RPO: %v > %v", result.DataLossGap, policy.MaxAllowedRPO)
	}

	fmt.Println("Резервное копирование и PITR восстановление подтверждено:")
	fmt.Printf("  • Целевое время отката (PITR): %s\n", result.TargetTimestamp.Format(time.RFC3339))
	fmt.Printf("  • Фактическая потеря данных (RPO): %v (SLA лимит: %v)\n", result.DataLossGap, policy.MaxAllowedRPO)
	fmt.Printf("  • Время восстановления (RTO):      %v (SLA лимит: %v)\n", result.ActualRestoreTime, policy.MaxAllowedRTO)
	fmt.Println("  • Тест целостности таблиц и индексов успешно пройден")
}
```

## Под капотом

В утилите `wal-g` (разработанной в Яндексе) файлы WAL архивируются в объектное хранилище S3 сжатыми алгоритмом lz4 в многопоточном режиме, обеспечивая минимальную задержку RPO (менее 1 секунды) практически без нагрузки на процессор СУБД.

## Подводные камни

Хранить бэкапы в том же облачном аккаунте или регионе, что и боевая база: при компрометации учетной записи или аварии региона будут уничтожены и база, и бэкапы. Бэкапы сохраняют в **изолированный независимый аккаунт с включенной защитой S3 Object Lock (WORM / Write Once Read Many)**.

## На собеседовании

**Вопрос с собеседования:** «Как протестировать бэкап базы данных размером 20 ТБ без развертывания дорогостоящего сервера?»
**Ответ:** С помощью снепшотов хранилища с механизмом Copy-on-Write (AWS EBS Snapshot / ZFS clone): клон диска создается за 2 секунды без физического копирования 20 ТБ. На временном сервере запускается PostgreSQL, проверяется целостность таблиц и контрольных сумм `pg_checksums`, после чего тестовый инстанс удаляется.
