# Пакетная вставка данных (Batch Processing): bulk INSERT против одиночных запросов

## Условие

**Batch Processing**: Объединяйте множество мелких операций в batch (например, bulk INSERT вместо 1000 отдельных INSERT'ов).

## Теория

Сравнение эффективности одиночных и батчевых вставок в БД:
- **1000 одиночных INSERT:**
  - 1000 сетевых вызовов по сокету (Network RTT).
  - 1000 транзакций со сбросом лога WAL на диск (`fsync`).
  - Время выполнения: **5–15 секунд**!
- **1 пакетный Bulk INSERT:**
  - `INSERT INTO telemetry (device_id, temp) VALUES (?, ?), (?, ?), ...`
  - 1 сетевой round-trip.
  - 1 атомарная транзакция и 1 операция `fsync` на диск.
  - Время выполнения: **20 миллисекунд** (ускорение в 250 раз!).

## Решение по шагам

1. Создайте структуру батчевого строителя SQL-запроса `BulkInsertBuilder`.
2. Реализуйте упаковку 1000 элементов в единый составной SQL-запрос.
3. Продемонстрируйте форматирование плейсхолдеров `$1, $2, ...`.
4. Верифицируйте корректность результирующего батча.

## Код решения

**`batch_processing_bulk_insert_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type TelemetryRecord struct {
	DeviceID string
	Temp     float64
}

func BuildBulkInsertQuery(records []TelemetryRecord) (string, []interface{}) {
	if len(records) == 0 {
		return "", nil
	}

	valueStrings := make([]string, 0, len(records))
	valueArgs := make([]interface{}, 0, len(records)*2)

	for i, r := range records {
		p1 := i*2 + 1
		p2 := i*2 + 2
		valueStrings = append(valueStrings, fmt.Sprintf("($%d, $%d)", p1, p2))
		valueArgs = append(valueArgs, r.DeviceID, r.Temp)
	}

	query := fmt.Sprintf("INSERT INTO telemetry (device_id, temp) VALUES %s",
		strings.Join(valueStrings, ", "))

	return query, valueArgs
}

func TestBatchProcessingBulkInsert(t *testing.T) {
	records := []TelemetryRecord{
		{DeviceID: "dev-1", Temp: 22.5},
		{DeviceID: "dev-2", Temp: 23.1},
		{DeviceID: "dev-3", Temp: 21.8},
	}

	query, args := BuildBulkInsertQuery(records)

	if !strings.Contains(query, "($1, $2), ($3, $4), ($5, $6)") || len(args) != 6 {
		t.Fatalf("Некорректная генерация Bulk INSERT: %s, args=%d", query, len(args))
	}

	fmt.Println("Пакетная обработка (Bulk INSERT Batching) подтверждена:")
	fmt.Printf("  • Сгенерированный SQL: %s\n", query)
	fmt.Printf("  • Передано аргументов: %d\n", len(args))
	fmt.Println("  • Единый сетевой round-trip ускоряет вставку тысяч записей в сотни раз")
}
```

## Под капотом

В драйвере `pgx` для максимально быстрой загрузки миллионов строк используют бинарный протокол `pgx.CopyFrom`: данные передаются напрямую в сокет в бинарном потоке PostgreSQL `COPY FROM STDIN`, развивая скорость записи до 200 000 строк в секунду.

## Подводные камни

Вставлять более 65 535 параметров в один SQL-запрос в PostgreSQL: протокол СУБД использует 16-битный счетчик параметров (`int16`), и запрос упадет с ошибкой `too many parameters`. Большие батчи нарезают пачками по 500–1000 строк.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество COPY FROM перед Bulk INSERT при загрузке больших данных?»
**Ответ:** Команда `COPY` минует стадии разбора SQL-дерева, планировщика запросов и оптимизатора PostgreSQL, направляя сырые бинарные строки напрямую в дисковые буферы таблицы, что делает ее в 3–5 раз быстрее любого параметризованного `INSERT`.
