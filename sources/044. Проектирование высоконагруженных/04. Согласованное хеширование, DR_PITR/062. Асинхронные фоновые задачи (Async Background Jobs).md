# Асинхронные фоновые задачи (Async Background Jobs): вынос тяжелых операций в очередь сообщений

## Условие

**Async Processing**: Выносите "тяжёлые" операции (email sending, image processing) в background jobs через Kafka/RabbitMQ.

## Теория

Принцип разгрузки критического пути (Critical Path Offloading):
- Пользователь зарегистрировался в системе.
- **Плохая архитектура:**
  - Хендлер `POST /register`:
    1. Запись в БД (5 мс).
    2. Генерация PDF приветствия (800 мс).
    3. Отправка Email по SMTP (2500 мс).
    4. Синхронизация с CRM (1200 мс).
  - Итоговое время ответа: **4.5 секунды**! При сбое SMTP регистрация падает с ошибкой.
- **Правильная архитектура:**
  1. Запись пользователя в БД и публикация события `UserRegistered` в Kafka/RabbitMQ.
  2. Возврат ответа клиенту за **5 миллисекунд**!
  3. Фоновые независимые воркеры вычитывают событие из очереди и спокойно генерируют PDF, отправляют Email и обновляют CRM.

## Решение по шагам

1. Создайте структуру брокера фоновых событий.
2. Реализуйте регистрацию пользователя с моментальным ответом.
3. Продемонстрируйте асинхронную обработку тяжелых задач независимыми воркерами.
4. Верифицируйте изоляцию критического пути от отказов SMTP.

## Код решения

**`async_background_jobs_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type UserRegisteredEvent struct {
	UserID string
	Email  string
}

type RegistrationSystem struct {
	asyncBus chan UserRegisteredEvent
	processedTasks []string
	mu       sync.Mutex
}

func (s *RegistrationSystem) RegisterUserFastPath(userID, email string) (string, time.Duration) {
	start := time.Now()

	// 1. Быстрая запись в базу (5 мс имитация)
	// 2. Публикация события в асинхронную шину
	s.asyncBus <- UserRegisteredEvent{UserID: userID, Email: email}

	// Моментальный возврат ответа пользователю!
	return "HTTP 201 Created", time.Since(start)
}

func (s *RegistrationSystem) StartBackgroundWorkers() {
	go func() {
		for evt := range s.asyncBus {
			// Фоновая отправка тяжелого Email и синхронизация CRM
			time.Sleep(15 * time.Millisecond)
			s.mu.Lock()
			s.processedTasks = append(s.processedTasks, fmt.Sprintf("Email sent to %s", evt.Email))
			s.mu.Unlock()
		}
	}()
}

func TestAsyncBackgroundJobs(t *testing.T) {
	sys := &RegistrationSystem{
		asyncBus: make(chan UserRegisteredEvent, 100),
	}
	sys.StartBackgroundWorkers()

	// Регистрация пользователя
	status, duration := sys.RegisterUserFastPath("usr-44", "alex@mail.ru")

	if duration > 10*time.Millisecond || status != "HTTP 201 Created" {
		t.Fatalf("Критический путь должен быть мгновенным: %v, status=%s", duration, status)
	}

	// Ждем выполнения фонового воркера
	time.Sleep(30 * time.Millisecond)

	sys.mu.Lock()
	tasksCount := len(sys.processedTasks)
	sys.mu.Unlock()

	if tasksCount != 1 {
		t.Fatalf("Фоновая задача должна быть выполнена: %d", tasksCount)
	}

	fmt.Println("Асинхронные фоновые задачи (Async Background Processing) подтверждены:")
	fmt.Printf("  • Ответ пользователю (Fast Path): %s за %v\n", status, duration)
	fmt.Printf("  • Фоновый воркер:                 %s (Асинхронно в очереди)\n", sys.processedTasks[0])
	fmt.Println("  • Тяжелые интеграции вынесены за пределы HTTP-запроса, задержка минимальна")
}
```

ℹ️ Разгрузка критического пути регистрации пользователя через отправку события в фоновую очередь

## Под капотом

Для исключения потери события при падении сервера прямо перед отправкой в Kafka используют паттерн **Transactional Outbox**: событие сохраняется в таблицу `outbox` в той же SQL-транзакции, что и создание пользователя, а процесс Debezium CDC читает WAL и гарантированно доставляет его в брокер.

## Подводные камни

Порождать горутину `go sendEmail()` прямо внутри HTTP-хендлера без очереди: если под упадет или будет перезапущен K8s, эта горутина оборвется и письмо потеряется навсегда. Фоновые задачи передают **строго через надежный брокер сообщений с персистентностью на диск**.

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать, что фоновый воркер не отправит одно и то же письмо дважды при сбое сети?»
**Ответ:** Идемпотентность на стороне почтового провайдера: каждое письмо помечается уникальным `Message-ID` (хэш от `user_id + email_type + date`). Почтовый шлюз проверяет ID перед отправкой, исключая дубликаты.
