# Прогрев кэша (Cache Warming): предотвращение перегрузки БД при деплое новой версии

## Условие

Реализуй **Cache Warming**: при деплое новой версии — preload hot data into cache. `CacheWarmer` читает `SELECT * FROM products WHERE active = true ORDER BY views DESC LIMIT 10000`, пишет в Redis. Покажи, что cold cache = DB overload.

## Теория

Проблема холодного старта (Cold Cache Problem):
- При перезапуске сервиса или очистке кэша после масштабного релиза:
  - Первый же наплыв трафика в 20 000 RPS обрушивается на абсолютно пустой кэш.
  - 20 000 параллельных запросов одновременно идут в PostgreSQL.
  - Пул соединений СУБД исчерпывается, CPU базы подскакивает до 100%, сайт падает (Cascading Failure).
- **Решение через Cache Warming (Прогрев кэша):**
  - До переключения сетевого трафика (Readiness Probe в K8s):
  - Фоновый воркер `CacheWarmer` выбирает топ-10 000 самых популярных активных товаров (`ORDER BY views DESC LIMIT 10000`).
  - Батчами прогревает их в Redis.
  - Только после 100% готовности кэша сервис открывает порт для пользовательского трафика!

## Решение по шагам

1. Создайте структуру воркера предварительного прогрева `CacheWarmer`.
2. Реализуйте выборку горячих товаров из БД и запись в кэш.
3. Продемонстрируйте прохождение проверки готовности сервиса (Readiness).
4. Верифицируйте защиту базы данных от холодного шторма запросов.

## Код решения

**`cache_warming_readiness_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ProductEntity struct {
	ID    string
	Title string
	Views int
}

type CacheWarmer struct {
	isWarmed bool
	cache    map[string]ProductEntity
}

func (w *CacheWarmer) WarmUpHotProducts(dbProducts []ProductEntity, limit int) int {
	w.cache = make(map[string]ProductEntity)

	// Имитация предзагрузки ТОП-N популярных товаров
	loaded := 0
	for _, p := range dbProducts {
		if loaded >= limit {
			break
		}
		w.cache[p.ID] = p
		loaded++
	}

	w.isWarmed = true
	return loaded
}

func (w *CacheWarmer) IsReadyForTraffic() bool {
	return w.isWarmed && len(w.cache) > 0
}

func TestCacheWarmingReadiness(t *testing.T) {
	warmer := &CacheWarmer{}

	// До прогрева под не должен принимать боевой трафик!
	if warmer.IsReadyForTraffic() {
		t.Fatal("Сервис не имеет права принимать трафик с холодным кэшем")
	}

	hotProducts := []ProductEntity{
		{ID: "prod-1", Title: "Смартфон Флагман 2026", Views: 95000},
		{ID: "prod-2", Title: "Беспроводные наушники", Views: 74000},
		{ID: "prod-3", Title: "Игровая консоль", Views: 62000},
	}

	loadedCount := warmer.WarmUpHotProducts(hotProducts, 10000)

	if !warmer.IsReadyForTraffic() || loadedCount != 3 {
		t.Fatalf("Сбой прогрева: warmed=%v, count=%d", warmer.IsReadyForTraffic(), loadedCount)
	}

	fmt.Println("Прогрев кэша (Cache Warming) успешно подтвержден:")
	fmt.Printf("  • Прогрето горячих позиций в Redis: %d\n", loadedCount)
	fmt.Printf("  • Статус готовности к трафику (K8s Readiness Probe): %v (Готов)\n", warmer.IsReadyForTraffic())
	fmt.Println("  • База данных защищена от шторма запросов при холодном старте подов")
}
```

ℹ️ Предварительный прогрев горячих данных перед открытием K8s Readiness Probe для трафика

## Под капотом

В Kubernetes прогрев кэша настраивают в рамках `startupProbe`: пока скрипт или эндпоинт `/health/warmup` не вернет `200 OK`, Kubelet не направляет трафик с балансировщика Ingress на новый под, обеспечивая 100% прогретый старт.

## Подводные камни

Прогревать весь миллионный каталог товаров: прогрев займет 40 минут, заблокировав CI/CD пайплайн деплоя. Прогревать нужно **строго верхний квантиль (Top 5-10% горячих ключей)** по правилу Парето (80/20).

## На собеседовании

**Вопрос с собеседования:** «Как прогревать кэш без выполнения тяжелого аналитического SQL-запроса `ORDER BY views` на боевом мастере?»
**Ответ:** Выгружать список горячих ключей из аналитической реплики ClickHouse или использовать логирование популярных URL с балансировщика Nginx: скрипт считывает топ-10 000 URL за прошедший час и прогоняет их синтетическими `curl` запросами через сервис до релиза.
