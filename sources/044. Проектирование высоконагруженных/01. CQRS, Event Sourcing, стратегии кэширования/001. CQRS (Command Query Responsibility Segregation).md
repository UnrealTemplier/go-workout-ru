# CQRS (Command Query Responsibility Segregation): разделение моделей записи и чтения

## Условие

**CQRS (Command Query Responsibility Segregation)**: Разделите модели для записи (commands) и чтения (queries). Write model — нормализованная БД, Read model — денормализованные view в Redis/Elasticsearch.

## Теория

Архитектура CQRS (Command Query Responsibility Segregation):
- В высоконагруженных системах (Ozon, Wildberries) соотношение чтений к записям часто превышает \(100:1\) или \(1000:1\).
- Попытка использовать одну и ту же нормализованную реляционную модель (3NF с десятками JOIN) для сложных аналитических запросов приводит к деградации производительности СУБД.
- **Разделение ответственности:**
  1. **Write Model (Команды):** строго нормализованная транзакционная БД (PostgreSQL). Оптимизирована для быстрой записи, целостности данных и ACID-инвариантов.
  2. **Read Model (Запросы):** денормализованные плоские документы в Redis, Elasticsearch или ClickHouse. Запрос чтения возвращает готовый DTO за 1–2 мс без единого JOIN!
  3. **Синхронизация:** асинхронный стриминг событий (Event Bus / Kafka / Debezium CDC).

## Решение по шагам

1. Определите команду создания заказа `CreateOrderCommand` и модель записи в реляционной БД.
2. Реализуйте генерацию плоского денормализованного представления `OrderReadView`.
3. Смоделируйте обновление Read-модели в кэше/поисковике.
4. Продемонстрируйте быстрое чтение готового агрегированного DTO.

## Код решения

**`cqrs_architecture_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

// Write Model (Нормализованная транзакционная сущность)
type OrderWriteModel struct {
	ID         string
	CustomerID string
	ItemIDs    []string
	TotalCents int64
}

// Read Model (Денормализованная плоская проекция для фронтенда)
type OrderReadView struct {
	OrderID      string   `json:"order_id"`
	CustomerName string   `json:"customer_name"`
	ItemTitles   []string `json:"item_titles"`
	TotalRub     float64  `json:"total_rub"`
}

type CQRSOrderRepository struct {
	mu        sync.RWMutex
	writeDB   map[string]OrderWriteModel // PostgreSQL OLTP
	readStore map[string]OrderReadView   // Redis / Elasticsearch Read Store
}

func (r *CQRSOrderRepository) ExecuteCommandCreate(ctx context.Context, cmd OrderWriteModel, customerName string, titles []string) error {
	r.mu.Lock()
	defer r.mu.Unlock()

	// 1. Запись в транзакционную модель
	r.writeDB[cmd.ID] = cmd

	// 2. Асинхронная или синхронная проекция в Read Model
	r.readStore[cmd.ID] = OrderReadView{
		OrderID:      cmd.ID,
		CustomerName: customerName,
		ItemTitles:   titles,
		TotalRub:     float64(cmd.TotalCents) / 100.0,
	}
	return nil
}

func (r *CQRSOrderRepository) ExecuteQueryView(ctx context.Context, orderID string) (OrderReadView, bool) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	view, found := r.readStore[orderID]
	return view, found
}

func TestCQRSArchitecture(t *testing.T) {
	repo := &CQRSOrderRepository{
		writeDB:   make(map[string]OrderWriteModel),
		readStore: make(map[string]OrderReadView),
	}

	cmd := OrderWriteModel{
		ID:         "ord-1001",
		CustomerID: "cust-42",
		ItemIDs:    []string{"item-1", "item-2"},
		TotalCents: 154000,
	}

	err := repo.ExecuteCommandCreate(context.Background(), cmd, "Алексей Смирнов", []string{"MacBook M3 Pro", "Мышь Magic Mouse"})
	if err != nil {
		t.Fatalf("Ошибка выполнения команды: %v", err)
	}

	view, found := repo.ExecuteQueryView(context.Background(), "ord-1001")
	if !found || view.CustomerName != "Алексей Смирнов" || view.TotalRub != 1540.0 {
		t.Fatalf("Некорректная Read-проекция: %+v", view)
	}

	fmt.Println("CQRS Architecture подтверждена:")
	fmt.Printf("  • Write Model сохранена в OLTP (ID=%s, TotalCents=%d)\n", cmd.ID, cmd.TotalCents)
	fmt.Printf("  • Read Model мгновенно доступна без JOIN: %+v\n", view)
}
```

## Под капотом

В микросервисах разделение CQRS позволяет масштабировать поды чтения независимо от подов записи. Поды Queries масштабируются по HPA до 50 реплик с чтением из Read-кластеров Redis/ClickHouse, в то время как поды Commands ограничены пулом соединений к PostgreSQL.

## Подводные камни

Ожидать немедленной строгой согласованности (Strong Consistency) на стороне чтения: при асинхронной репликации в Read-модель возникает задержка Eventual Consistency (обычно 5–100 мс). Если пользователь сразу после нажатия «Оплатить» обновляет страницу, он может на долю секунды увидеть старый статус.

## На собеседовании

**Вопрос с собеседования:** «Как бороться с эффектом 'Read Your Own Writes' в системах с CQRS и Eventual Consistency?»
**Ответ:** 
1. Возвращать обновленное состояние сущности прямо в HTTP-ответе команды `POST /orders` (мутация в UI на клиенте).
2. Читать свежие данные собственного профиля пользователя из Primary БД в течение первых 2 секунд после записи (Read-After-Write window), а для остальных пользователей отдавать реплику.
