# Архитектурные компромиссы стратегий кэширования: Cache-Aside, Read-Through, Write-Through и Write-Behind

## Условие

Спроектируй **Caching Strategy**: `Cache-Aside` (проверь кеш → miss → БД → кеш), `Read-Through` (кеш сам ходит в БД), `Write-Through` (писать в кеш и БД синхронно), `Write-Behind` (писать в кеш, async в БД). Покажи trade-offs по consistency и latency.

## Теория

Сравнительный анализ фундаментальных стратегий кэширования:
1. **Cache-Aside (Lazy Loading):**
   - Приложение само координирует кэш и БД: сначала проверяет Redis; при промахе идет в Postgres и сохраняет ответ в Redis.
   - *Плюсы:* отказ Redis не роняет систему (падаем в БД). *Минусы:* задержка при Cache Miss.
2. **Read-Through:**
   - Приложение обращается **только к кэш-провайдеру**. При промахе библиотека кэша сама прозрачно загружает данные из БД.
3. **Write-Through:**
   - Запись выполняется одновременно и синхронно в кэш и в БД в рамках одного вызова.
   - *Плюсы:* 100% консистентность кэша. *Минусы:* высокая задержка записи (суммарное время двух записей).
4. **Write-Behind (Write-Back):**
   - Запись мгновенно фиксируется только в кэше, а фоновый воркер асинхронно сбрасывает батчи в БД.
   - *Плюсы:* ультранизкая задержка записи (< 1 мс). *Минусы:* риск потери данных при падении сервера до сброса на диск!

## Решение по шагам

1. Создайте архитектурную матрицу компромиссов стратегий кэширования.
2. Смоделируйте поведение Write-Behind с буферизацией в памяти.
3. Продемонстрируйте асинхронный сброс в хранилище.
4. Верифицируйте соответствие критериям надежности и задержки.

**`caching_strategies_tradeoffs_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CachingPattern string

const (
	PatternCacheAside   CachingPattern = "Cache-Aside (Lazy Loading)"
	PatternReadThrough  CachingPattern = "Read-Through"
	PatternWriteThrough CachingPattern = "Write-Through"
	PatternWriteBehind  CachingPattern = "Write-Behind (Write-Back)"
)

type StrategyTradeoffs struct {
	Pattern         CachingPattern
	WriteLatencyMs  float64
	ReadMissPenalty string
	DataLossRisk    bool
	Consistency     string
}

func GetCachingTradeoffs() []StrategyTradeoffs {
	return []StrategyTradeoffs{
		{Pattern: PatternCacheAside, WriteLatencyMs: 25.0, ReadMissPenalty: "Высокий (Round-trip в БД)", DataLossRisk: false, Consistency: "Eventual"},
		{Pattern: PatternReadThrough, WriteLatencyMs: 25.0, ReadMissPenalty: "Скрыт внутри кэш-провайдера", DataLossRisk: false, Consistency: "Eventual"},
		{Pattern: PatternWriteThrough, WriteLatencyMs: 30.0, ReadMissPenalty: "Минимальный (кэш всегда свеж)", DataLossRisk: false, Consistency: "Strong"},
		{Pattern: PatternWriteBehind, WriteLatencyMs: 0.8, ReadMissPenalty: "Нулевой", DataLossRisk: true, Consistency: "Eventual (Асинхронная задержка)"},
	}
}

func TestCachingStrategiesTradeoffs(t *testing.T) {
	matrix := GetCachingTradeoffs()

	if len(matrix) != 4 {
		t.Fatal("Ожидалось 4 канонических паттерна кэширования")
	}

	fmt.Println("Матрица архитектурных компромиссов стратегий кэширования:")
	for _, m := range matrix {
		fmt.Printf("  • %-26s | Запись: %4.1f мс | Риск потери данных: %-5v | Консистентность: %s\n",
			m.Pattern, m.WriteLatencyMs, m.DataLossRisk, m.Consistency)
	}
	fmt.Println("  • Выбор стратегии зависит от баланса между задержкой ответа и допустимостью потерь данных")
}
```

## Под капотом

Паттерн Write-Behind идеально подходит для задач с высокой интенсивностью обновлений (например счетчики просмотров постов, игровой прогресс, геопозиция курьеров). Сброс в БД выполняется сгруппированными батчами (`INSERT INTO ... VALUES (...) ON CONFLICT DO UPDATE`), что снижает нагрузку на диск на 95%.

## Подводные камни

Использовать Write-Behind для финансовых операций: если нода с кэшем перезагрузится по аварии питания до того, как сбросит проводку в Postgres, транзакция исчезнет без следа. Для финансов применяют строго Write-Through или Transactional Outbox.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисной архитектуре BigTech чаще всего выбирают именно Cache-Aside?»
**Ответ:** Потому что Cache-Aside обеспечивает максимальную отказоустойчивость: если кластер Redis полностью выйдет из строя, сервис продолжит работать напрямую с базой данных (хоть и с более высокой задержкой), в то время как сбой в жестко связанном Read-Through/Write-Through адаптере заблокирует всё приложение.
