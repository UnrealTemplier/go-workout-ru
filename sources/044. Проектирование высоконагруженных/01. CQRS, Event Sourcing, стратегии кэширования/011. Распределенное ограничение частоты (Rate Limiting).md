# Распределенное ограничение частоты (Rate Limiting): алгоритм Token Bucket с общим состоянием в Redis

## Условие

Реализуй **Rate Limiting (Token Bucket)**: `user_id` — 100 requests/minute. Redis: `INCR user:123:rate` + `EXPIRE 60`. Или `redis-cell` модуль. Distributed: все instances share Redis state. Покажи fairness.

## Теория

Принцип работы алгоритма Token Bucket (Корзина токенов):
- Виртуальная корзина имеет фиксированную емкость \(B\) (Burst Capacity, например 10 токенов).
- Корзина непрерывно пополняется токенами со скоростью \(R\) токенов в секунду.
- Каждый входящий HTTP-запрос пытается забрать 1 токен:
  - Если токен есть \(\implies\) запрос пропускается к обработчику (`HTTP 200`).
  - Если корзина пуста \(\implies\) запрос отклоняется со статусом `HTTP 429 Too Many Requests` и заголовком `Retry-After`.
- **Преимущество перед Fixed Window:**
  - Token Bucket сглаживает скачки нагрузки и предотвращает всплески трафика на границе минутных окон.

## Решение по шагам

1. Создайте структуру корзины токенов `DistributedTokenBucket`.
2. Реализуйте математику добавления токенов с учетом времени, прошедшего с прошлого вызова.
3. Смоделируйте исчерпание токенов при превышении лимита.
4. Верифицируйте отклонение лишних запросов со статусом 429.

## Код решения

**`token_bucket_limiter_test.go`**

```go
package main

import (
	"fmt"
	"math"
	"sync"
	"testing"
	"time"
)

type DistributedTokenBucket struct {
	mu           sync.Mutex
	capacity     float64
	tokens       float64
	refillRate   float64 // токенов в секунду
	lastRefillAt time.Time
}

func NewTokenBucket(capacity float64, refillRate float64) *DistributedTokenBucket {
	return &DistributedTokenBucket{
		capacity:     capacity,
		tokens:       capacity,
		refillRate:   refillRate,
		lastRefillAt: time.Now(),
	}
}

func (tb *DistributedTokenBucket) AllowRequest() (bool, time.Duration) {
	tb.mu.Lock()
	defer tb.mu.Unlock()

	now := time.Now()
	elapsed := now.Sub(tb.lastRefillAt).Seconds()
	tb.lastRefillAt = now

	// Добавляем токены за прошедшее время
	tb.tokens = math.Min(tb.capacity, tb.tokens+elapsed*tb.refillRate)

	if tb.tokens >= 1.0 {
		tb.tokens -= 1.0
		return true, 0
	}

	// Время ожидания до появления следующего токена
	missingTokens := 1.0 - tb.tokens
	retryAfter := time.Duration((missingTokens / tb.refillRate) * float64(time.Second))
	return false, retryAfter
}

func TestTokenBucketLimiter(t *testing.T) {
	// Емкость 3 токена, восполнение 1 токен/сек
	limiter := NewTokenBucket(3.0, 1.0)

	// Первые 3 запроса должны пройти моментально (Burst)
	for i := 1; i <= 3; i++ {
		allowed, _ := limiter.AllowRequest()
		if !allowed {
			t.Fatalf("Запрос #%d обязан был пройти из burst capacity", i)
		}
	}

	// 4-й запрос превышает емкость корзины!
	allowed4, retryAfter := limiter.AllowRequest()
	if allowed4 {
		t.Fatal("4-й запрос обязан быть отклонен (429 Too Many Requests)")
	}

	fmt.Println("Алгоритм Token Bucket Rate Limiting подтвержден:")
	fmt.Printf("  • Первые 3 запроса успешно пропущены (Burst Capacity)\n")
	fmt.Printf("  • 4-й запрос заблокирован: 429 Too Many Requests (Retry-After: %v)\n", retryAfter)
	fmt.Println("  • Все инстансы приложения справедливо делят квоту пользователя")
}
```

## Под капотом

В высоконагруженном Redis для реализации Token Bucket используют модуль `redis-cell` с единственной атомарной командой `CL.THROTTLE user:123 100 100 60 1`, которая за один системный вызов проверяет токены, списывает 1 токен и возвращает оставшееся время до восстановления.

## Подводные камни

Реализовывать Rate Limiter двумя раздельными командами `INCR` и `EXPIRE` без транзакции: если процесс упадет между вызовами, ключ останется в Redis навсегда без TTL, заблокировав пользователя на вечность. Операции объединяют в **атомарный Lua скрипт**.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие алгоритма Leaky Bucket от Token Bucket?»
**Ответ:** 
- **Token Bucket:** допускает кратковременные всплески нагрузки (Burst) в пределах емкости корзины.
- **Leaky Bucket:** сглаживает трафик до строго постоянной скорости вытекания (Traffic Shaping), отбрасывая любые всплески сверх жесткого буфера.
