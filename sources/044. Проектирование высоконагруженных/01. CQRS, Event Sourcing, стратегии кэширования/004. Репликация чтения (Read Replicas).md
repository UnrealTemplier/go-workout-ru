# Репликация чтения (Read Replicas): разделение пулов соединений Primary и Replica в PostgreSQL

## Условие

**Read Replicas**: Настройте master-slave репликацию в PostgreSQL. Write операции идут в master, read — в slaves (через separate DB connection pool).

## Теория

Архитектура Primary-Replica (Master-Slave) для PostgreSQL:
- База данных Primary принимает весь трафик на запись (`INSERT`, `UPDATE`, `DELETE`).
- Журнал предзаписи (Write-Ahead Log / WAL) непрерывно передается на несколько асинхронных реплик чтения (Read Replicas).
- **Разделение пулов на уровне Go:**
  - В приложении инициализируются два независимых пула соединений (`pgxpool.Pool`):
    1. `PrimaryPool`: направлен на мастер (DNS `pg-primary:5432`).
    2. `ReplicaPool`: направлен на балансировщик реплик (HAProxy / PgBouncer `pg-replicas:5432`).
  - Сервис роутит команды записи в `PrimaryPool`, а запросы каталога и поиска — в `ReplicaPool`.

## Решение по шагам

1. Создайте структуру управления разделенными пулами БД `DBClusterRouter`.
2. Реализуйте метод `ExecWrite` с обращением к Primary.
3. Реализуйте метод `QueryRead` с обращением к Replica.
4. Верифицируйте изоляцию трафика записи и чтения.

## Код решения

**`read_replicas_routing_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type DBClusterRouter struct {
	primaryHits int
	replicaHits int
}

func (r *DBClusterRouter) ExecWrite(ctx context.Context, sqlQuery string) error {
	// Все операции мутации строго на Primary!
	r.primaryHits++
	return nil
}

func (r *DBClusterRouter) QueryRead(ctx context.Context, sqlQuery string) ([]string, error) {
	// Чтение разгружает Primary и уходит на асинхронные реплики
	r.replicaHits++
	return []string{"record_from_replica"}, nil
}

func TestReadReplicasRouting(t *testing.T) {
	router := &DBClusterRouter{}

	// 10 операций записи (создание заказов)
	for i := 0; i < 10; i++ {
		_ = router.ExecWrite(context.Background(), "INSERT INTO orders VALUES (...)")
	}

	// 90 операций чтения (просмотр каталога)
	for i := 0; i < 90; i++ {
		_, _ = router.QueryRead(context.Background(), "SELECT * FROM products WHERE ...")
	}

	if router.primaryHits != 10 || router.replicaHits != 90 {
		t.Fatalf("Сбой распределения нагрузки: Primary=%d, Replica=%d",
			router.primaryHits, router.replicaHits)
	}

	fmt.Println("Архитектура Read Replicas подтверждена:")
	fmt.Printf("  • Запросов записи на Primary: %d (10%% трафика)\n", router.primaryHits)
	fmt.Printf("  • Запросов чтения на Replicas: %d (90%% трафика снято с мастера)\n", router.replicaHits)
	fmt.Println("  • Мастер защищен от перегрузки тяжелыми SELECT-запросами")
}
```

ℹ️ Раздельная маршрутизация операций мутации и чтения между пулами Primary и Replica

## Под капотом

В драйвере `jackc/pgx/v5` строка подключения поддерживает указание нескольких хостов: `postgres://user:pass@host1:5432,host2:5432/db?target_session_attrs=primary` автоматически подключается к мастеру, а `target_session_attrs=read-only` находит активную реплику чтения.

## Подводные камни

Выполнять транзакцию чтения-записи `SELECT ... FOR UPDATE` через Replica: реплики PostgreSQL находятся в режиме `read-only`, и попытка захвата строчной блокировки упадет с ошибкой СУБД `ERROR: cannot execute SELECT FOR UPDATE in a read-only transaction`.

## На собеседовании

**Вопрос с собеседования:** «Что такое Replication Lag (лаг репликации) и как его измерить в PostgreSQL?»
**Ответ:** Это задержка между фиксацией транзакции в WAL на мастере и ее применением на реплике. В PostgreSQL измеряется функцией `pg_wal_lsn_diff(pg_current_wal_lsn(), pg_last_wal_replay_lsn())` в байтах или `EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))` в секундах. Если лаг превышает порог (например 2 сек), балансировщик обязан временно вывести реплику из ротации.
