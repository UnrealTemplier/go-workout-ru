# Материализованные представления (Materialized Views) из потока событий

## Условие

**Materialized Views**: Создавайте read-оптимизированные проекции из event stream (например, `UserOrdersView` обновляется при каждом `OrderCreated` событии).

## Теория

Связь Event Sourcing и проекций Materialized Views:
- Поток доменных событий (Event Stream) содержит полную информацию обо всех операциях в системе.
- Чтобы отдавать личный кабинет пользователя, не нужно опрашивать базу заказов, биллинга и доставки.
- **Проектор (Event Projector):**
  1. Фоновый воркер подписывается на топик `orders.events`.
  2. При получении события `OrderCreated` воркер атомарно обновляет материализованное представление пользователя в Redis / PostgreSQL JSONB:
     `UPDATE user_order_summaries SET total_spent = total_spent + ?, orders_count = orders_count + 1 WHERE user_id = ?`.
  3. API-запрос на профиль пользователя выполняется мгновенно по первичному ключу за 0.5 мс!

## Решение по шагам

1. Создайте модель материализованного представления `UserOrdersSummaryView`.
2. Реализуйте проектор событий `EventStreamProjector`.
3. Смоделируйте поступление потока событий оформления заказов.
4. Верифицируйте корректность агрегированных показателей витрины.

## Код решения

**`materialized_views_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type OrderCreatedEvent struct {
	OrderID   string
	UserID    string
	AmountRub int
}

type UserOrdersSummaryView struct {
	UserID     string
	TotalSpent int
	OrderCount int
}

type EventStreamProjector struct {
	mu    sync.RWMutex
	views map[string]UserOrdersSummaryView
}

func (p *EventStreamProjector) HandleOrderCreated(evt OrderCreatedEvent) {
	p.mu.Lock()
	defer p.mu.Unlock()

	summary := p.views[evt.UserID]
	summary.UserID = evt.UserID
	summary.TotalSpent += evt.AmountRub
	summary.OrderCount++
	p.views[evt.UserID] = summary
}

func (p *EventStreamProjector) GetUserView(userID string) (UserOrdersSummaryView, bool) {
	p.mu.RLock()
	defer p.mu.RUnlock()
	v, ok := p.views[userID]
	return v, ok
}

func TestMaterializedViews(t *testing.T) {
	projector := &EventStreamProjector{views: make(map[string]UserOrdersSummaryView)}

	events := []OrderCreatedEvent{
		{OrderID: "ord-1", UserID: "user-100", AmountRub: 2500},
		{OrderID: "ord-2", UserID: "user-100", AmountRub: 3500},
		{OrderID: "ord-3", UserID: "user-200", AmountRub: 1200},
		{OrderID: "ord-4", UserID: "user-100", AmountRub: 4000},
	}

	for _, e := range events {
		projector.HandleOrderCreated(e)
	}

	viewUser100, found := projector.GetUserView("user-100")
	if !found || viewUser100.TotalSpent != 10000 || viewUser100.OrderCount != 3 {
		t.Fatalf("Некорректная материализованная проекция: %+v", viewUser100)
	}

	fmt.Println("Материализованные представления (Materialized Views) подтверждены:")
	fmt.Printf("  • Пользователь user-100: Заказов=%d, Всего потрачено=%d руб\n",
		viewUser100.OrderCount, viewUser100.TotalSpent)
	fmt.Println("  • Запрос личного кабинета читает готовые агрегаты без выполнения тяжелых SUM/COUNT в БД")
}
```

## Под капотом

В распределенных системах для построения Materialized Views часто применяют специализированные базы стриминговой аналитики, такие как Materialize или Apache Flink, которые выполняют инкрементальные SQL-запросы (Differential Dataflow) прямо по потоку Kafka.

## Подводные камни

Потеря идемпотентности при повторной доставке (At-Least-Once Delivery): если сообщение `OrderCreated` придет консьюмеру дважды, `total_spent` ошибочно увеличится в два раза. Проекции обязаны проверять дедупликацию по `event_id`.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если в бизнес-логике изменился формат витрины и нужно пересчитать проекцию для 100 миллионов пользователей?»
**Ответ:** Паттерн Blue-Green Projection: создается новая таблица `user_order_summaries_v2`. Запускается отдельный фоновый консьюмер, который читает архивный лог событий Kafka с самого начала (`offset = 0`). После завершения синхронизации API-трафик переключается на таблицу `v2`, а старая витрина удаляется.
