# Инвалидация кэша через Redis Pub/Sub при изменении данных в базе

## Условие

**Cache Invalidation**: Реализуйте инвалидацию кэша через pub/sub (Redis Pub/Sub) при изменении данных в БД.

## Теория

Синхронизация распределенных кэшей через шину событий (Pub/Sub Cache Invalidation):
- В микросервисной архитектуре развернуты десятки инстансов приложения, каждый из которых имеет локальный буфер в оперативной памяти.
- Если экземпляр №1 обрабатывает запрос на обновление цены товара:
  1. Экземпляр №1 выполняет `UPDATE products SET price = ? WHERE id = 42` в СУБД.
  2. Экземпляр №1 публикует в Redis канал `cache:invalidation`:
     ```json
     {"action": "INVALIDATE", "key": "product:42"}
     ```
  3. Все остальные 50 инстансов слушают этот канал. Получив событие, они моментально сбрасывают ключ `product:42` из своих локальных кэшей.
  4. Рассинхронизация данных устраняется за доли миллисекунды!

## Решение по шагам

1. Создайте структуру шины сообщений инвалидации `CacheInvalidationBus`.
2. Реализуйте подписку слушателей (инстансов приложения).
3. Смоделируйте публикацию события сброса кэша при обновлении записи в БД.
4. Верифицируйте очистку устаревших значений на всех узлах.

## Код решения

**`cache_invalidation_pubsub_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type CacheInvalidationBus struct {
	mu          sync.Mutex
	subscribers []chan string
}

func (b *CacheInvalidationBus) Subscribe() chan string {
	b.mu.Lock()
	defer b.mu.Unlock()
	ch := make(chan string, 10)
	b.subscribers = append(b.subscribers, ch)
	return ch
}

func (b *CacheInvalidationBus) PublishInvalidate(key string) {
	b.mu.Lock()
	defer b.mu.Unlock()
	for _, sub := range b.subscribers {
		select {
		case sub <- key:
		default:
		}
	}
}

type NodeLocalCache struct {
	data map[string]string
}

func TestCacheInvalidationPubSub(t *testing.T) {
	bus := &CacheInvalidationBus{}

	// Создаем два независимых пода приложения
	nodeA := &NodeLocalCache{data: map[string]string{"item-5": "Старая цена 1000"}}
	nodeB := &NodeLocalCache{data: map[string]string{"item-5": "Старая цена 1000"}}

	subA := bus.Subscribe()
	subB := bus.Subscribe()

	// Нода А обновила товар в БД и публикует инвалидацию
	bus.PublishInvalidate("item-5")

	// Обе ноды вычитывают сигнал инвалидации
	keyA := <-subA
	delete(nodeA.data, keyA)

	keyB := <-subB
	delete(nodeB.data, keyB)

	if len(nodeA.data) != 0 || len(nodeB.data) != 0 {
		t.Fatal("Кэш на обеих нодах должен быть сброшен")
	}

	fmt.Println("Инвалидация кэша через Pub/Sub успешно подтверждена:")
	fmt.Printf("  • Получен сигнал сброса ключа: %s на всех нодах\n", keyA)
	fmt.Println("  • Состояние кэша синхронизировано между распределенными экземплярами сервиса")
}
```

ℹ️ Синхронная инвалидация распределенного кэша через брокер сообщений Pub/Sub

## Под капотом

В Redis 6+ внедрен встроенный протокол **RESP3 Client Tracking**: сервер Redis сам отслеживает, какие клиенты читали определенный ключ, и при его изменении автоматически шлет сокет-пакет `INVALIDATE` в сторону клиента Go без ручного создания Pub/Sub каналов.

## Подводные камни

Использовать Redis Pub/Sub для инвалидации критичных данных без гарантии доставки (At-Most-Once): стандартный Pub/Sub не буферизирует сообщения. Если нода была в кратковременном сетевом флапе, она пропустит событие. Для критичных витрин ключам всегда задают максимальный TTL.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Redis Pub/Sub от Redis Streams в задачах инвалидации кэша?»
**Ответ:** Redis Pub/Sub работает по модели Fire-and-Forget (сообщения не сохраняются в памяти и теряются, если подписчик оффлайн). Redis Streams сохраняет историю событий в Append-Only лог, позволяя отставшему поду дочитать пропущенные инвалидации после восстановления связи.
