# Event Sourcing: сохранение изменений состояния как последовательности событий и Replay

## Условие

**Event Sourcing**: Сохраняйте все изменения состояния как последовательность событий в Kafka/EventStoreDB. Восстанавливайте текущее состояние через replay событий.

## Теория

Принципы архитектуры Event Sourcing:
- **Традиционный подход (CRUD):**
  - Таблица `accounts` хранит только текущий баланс: `UPDATE accounts SET balance = 400 WHERE id = 1`.
  - Вся предыстория того, как баланс стал равен 400 (было 1000, списали 600 или было 0 и начислили 400), безвозвратно утеряна!
- **Event Sourcing:**
  - Состояние сущности **никогда не перезаписывается**.
  - Хранилище событий (Event Store) является Append-Only логом иммутабельных фактов:
    `AccountCreated(id=1, initial=0)`
    `MoneyDeposited(amount=1000)`
    `MoneyWithdrawn(amount=600)`
  - **Восстановление состояния (Replay):** текущий баланс вычисляется последовательным применением (fold/reduce) всех событий агрегата с момента его создания.

## Решение по шагам

1. Создайте интерфейс доменного события `DomainEvent`.
2. Реализуйте структуру агрегата банковского счета `BankAccountAggregate`.
3. Напишите функцию `Apply(event)` для мутации внутреннего состояния агрегата.
4. Продемонстрируйте восстановление состояния через повторное воспроизведение (Replay) лога событий.

## Код решения

**`event_sourcing_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DomainEvent interface {
	EventType() string
}

type AccountOpenedEvent struct {
	AccountID string
	Owner     string
}

func (e AccountOpenedEvent) EventType() string { return "AccountOpened" }

type MoneyDepositedEvent struct {
	AmountRub int
}

func (e MoneyDepositedEvent) EventType() string { return "MoneyDeposited" }

type MoneyWithdrawnEvent struct {
	AmountRub int
}

func (e MoneyWithdrawnEvent) EventType() string { return "MoneyWithdrawn" }

// Агрегат, восстанавливаемый из событий
type BankAccountAggregate struct {
	ID      string
	Owner   string
	Balance int
	Version int
}

func (a *BankAccountAggregate) Apply(evt DomainEvent) {
	switch e := evt.(type) {
	case AccountOpenedEvent:
		a.ID = e.AccountID
		a.Owner = e.Owner
		a.Balance = 0
	case MoneyDepositedEvent:
		a.Balance += e.AmountRub
	case MoneyWithdrawnEvent:
		a.Balance -= e.AmountRub
	}
	a.Version++
}

func ReplayAggregate(history []DomainEvent) *BankAccountAggregate {
	acc := &BankAccountAggregate{}
	for _, evt := range history {
		acc.Apply(evt)
	}
	return acc
}

func TestEventSourcing(t *testing.T) {
	eventStream := []DomainEvent{
		AccountOpenedEvent{AccountID: "acc-99", Owner: "Иван Иванов"},
		MoneyDepositedEvent{AmountRub: 50000},
		MoneyWithdrawnEvent{AmountRub: 12000},
		MoneyDepositedEvent{AmountRub: 5000},
	}

	account := ReplayAggregate(eventStream)

	expectedBalance := 50000 - 12000 + 5000
	if account.Balance != expectedBalance || account.Version != 4 {
		t.Fatalf("Некорректное состояние после Replay: Баланс=%d, Версия=%d",
			account.Balance, account.Version)
	}

	fmt.Println("Паттерн Event Sourcing успешно подтвержден:")
	fmt.Printf("  • Воспроизведено событий: %d\n", len(eventStream))
	fmt.Printf("  • Итоговое состояние счета: Владелец=%s, Баланс=%d руб, Версия=%d\n",
		account.Owner, account.Balance, account.Version)
	fmt.Println("  • 100% аудируемость и возможность путешествия во времени (Time Travel Debugging)")
}
```

## Под капотом

Когда число событий агрегата превышает 1000, Replay всех событий при каждом запросе становится слишком медленным (\(O(N)\)). Для оптимизации используют **снапшоты (Snapshots)**: каждые 100 событий состояние агрегата сохраняется в быстрое хранилище, а при загрузке восстанавливается последний снапшот плюс дельта событий после него.

## Подводные камни

Использовать Kafka в качестве единственного и постоянного источника истины для Event Sourcing: Kafka оптимизирована для стриминга, а не для произвольного чтения событий конкретного агрегата по ID (`SELECT * WHERE aggregate_id = ?`). Для Event Store используют специализированные БД (EventStoreDB, PostgreSQL с версионированием).

## На собеседовании

**Вопрос с собеседования:** «Как изменять схему событий в Event Sourcing при рефакторинге (Schema Evolution)?»
**Ответ:** Паттерн Upcasting: старые события в БД остаются иммутабельными. При вычитке из Event Store специальный Upcaster налету преобразует `v1` события в структуру `v2` (подставляя дефолтные значения новых полей), гарантируя обратную совместимость.
