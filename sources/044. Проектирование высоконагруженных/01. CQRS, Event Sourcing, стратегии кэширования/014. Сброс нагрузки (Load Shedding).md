# Сброс нагрузки (Load Shedding): отсечение второстепенных запросов и отдача кэшированных данных

## Условие

**Load Shedding**: При перегрузке отбрасывайте "дешёвые" запросы (health checks, неважные метрики) или возвращайте cached/stale data.

## Теория

Философия Load Shedding (Управляемый сброс нагрузки):
- Когда сервер перегружен (очередь входящих запросов растет быстрее, чем CPU успевает их обрабатывать), задержка (Latency) стремится к бесконечности.
- Попытка обработать **все** запросы приводит к краху сервера (Server Crash) и 100% отказу для всех пользователей.
- **Load Shedding:**
  1. Приоритезация трафика:
     - `Tier 1 (Critical):` оформление заказа, оплата, авторизация.
     - `Tier 2 (Standard):` добавление в избранное, отзывы.
     - `Tier 3 (Low):` внутренние метрики, фоновые хелсчеки, рекомендации.
  2. При загрузке CPU > 85% шлюз моментально отбрасывает запросы Tier 3 (HTTP 503 Service Unavailable).
  3. Для Tier 2 отдаются устаревшие данные из кэша (Stale Data).
  4. Tier 1 продолжает работать штатно за 5 мс!

## Решение по шагам

1. Создайте модель классификации приоритетов входящих запросов.
2. Реализуйте шлюз сброса нагрузки `LoadSheddingGateway`.
3. Смоделируйте состояние перегрузки сервера (CPU 92%).
4. Верифицируйте пропуск критических транзакций и отсечение второстепенных запросов.

## Код решения

**`load_shedding_gateway_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RequestPriority int

const (
	PriorityCritical RequestPriority = iota // Оплата, Чекаут
	PriorityStandard                        // Карточка товара
	PriorityLow                             // Фоновые метрики, рекомендации
)

type SystemHealthMetrics struct {
	CPUUsagePercent float64
}

type LoadSheddingGateway struct {
	health SystemHealthMetrics
}

func (gw *LoadSheddingGateway) DispatchRequest(priority RequestPriority, payload string) (string, int) {
	// Если система в критической перегрузке (CPU > 85%)
	if gw.health.CPUUsagePercent > 85.0 {
		if priority == PriorityLow {
			return "LOAD_SHED: dropped to protect system health", 503
		}
		if priority == PriorityStandard {
			return "DEGRADED: served from stale fallback cache", 200
		}
	}
	// Критические запросы обслуживаются всегда!
	return fmt.Sprintf("SUCCESS: processed %s", payload), 200
}

func TestLoadSheddingGateway(t *testing.T) {
	// Сервер перегружен: CPU на 92%
	gw := &LoadSheddingGateway{health: SystemHealthMetrics{CPUUsagePercent: 92.0}}

	// 1. Фоновая рекомендация -> должна быть сброшена
	resLow, codeLow := gw.DispatchRequest(PriorityLow, "GetRecommendations")
	if codeLow != 503 {
		t.Fatalf("Низкоприоритетный запрос обязан быть сброшен: %d", codeLow)
	}

	// 2. Просмотр товара -> отдача из кэша
	resStd, codeStd := gw.DispatchRequest(PriorityStandard, "GetProductDetails")
	if codeStd != 200 || resStd != "DEGRADED: served from stale fallback cache" {
		t.Fatalf("Стандартный запрос должен деградировать: %s", resStd)
	}

	// 3. Платеж -> должен быть выполнен в приоритете!
	resCrit, codeCrit := gw.DispatchRequest(PriorityCritical, "ProcessPayment")
	if codeCrit != 200 || resCrit != "SUCCESS: processed ProcessPayment" {
		t.Fatalf("Критический платеж обязан пройти: %s", resCrit)
	}

	fmt.Println("Сброс нагрузки (Load Shedding Gateway) успешно подтвержден:")
	fmt.Printf("  • Low Priority:      %d %s\n", codeLow, resLow)
	fmt.Printf("  • Standard Priority: %d %s\n", codeStd, resStd)
	fmt.Printf("  • Critical Priority: %d %s\n", codeCrit, resCrit)
	fmt.Println("  • Жизнеспособность ядра системы сохранена во время пикового шторма нагрузки")
}
```

ℹ️ Управляемый сброс низкоприоритетных запросов для сохранения критических транзакций при перегрузке

## Под капотом

В Netflix и Uber алгоритм Load Shedding реализуется на основе алгоритма **CoDel (Controlled Delay)**: если время нахождения запроса в очереди ожидания горутин превышает 20 мс, шлюз начинает проактивно сбрасывать входящие запросы до тех пор, пока длина очереди не вернется в норму.

## Подводные камни

Отбрасывать запросы дорого: если для проверки приоритета сервер сначала парсит 10-мегабайтный JSON в куче, сам процесс Load Shedding сожжет процессор. Приоритет запроса проверяют **на уровне заголовков HTTP** (`X-Priority: critical`) за 10 наносекунд.

## На собеседовании

**Вопрос с собеседования:** «Почему возврат HTTP 503 при Load Shedding должен обязательно сопровождаться случайным заголовком Retry-After с джиттером?»
**Ответ:** Без заголовка `Retry-After` все 100 000 клиентов, получив ошибку, синхронно повторят запрос ровно через 1 секунду, вызвав повторный разрушительный шторм (Thundering Herd / Retry Storm). Джиттер (Jitter) распределяет повторные попытки равномерно во времени.
