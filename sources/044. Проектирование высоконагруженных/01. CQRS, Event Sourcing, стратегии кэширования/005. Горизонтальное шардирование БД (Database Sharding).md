# Горизонтальное шардирование БД (Database Sharding): маршрутизация по user_id

## Условие

**Database Sharding**: Горизонтальное шардирование по `user_id` (например, `user_id % 16` определяет шард). Реализуйте routing logic в приложении или через Vitess/Citus.

## Теория

Принципы горизонтального шардирования (Database Sharding):
- Когда размер базы данных превышает 5–10 ТБ или объем записи превышает лимиты IOPS диска одного сервера:
  - Вертикальное масштабирование (увеличение CPU/RAM машины) упирается в потолок возможностей железа.
- **Шардирование по ключу (Hash/Modulo Sharding):**
  - Данные разбиваются на \(N\) независимых физических баз данных (шардов).
  - Ключ шардирования (Shard Key, например `user_id`):
    $$\text{ShardID} = \text{Hash}(\text{user\_id}) \pmod{N}$$
  - Все данные одного пользователя (профиль, заказы, настройки) хранятся на одном и том же шарде, что сохраняет локальные транзакции ACID внутри пользователя!

## Решение по шагам

1. Создайте маршрутизатор шардов `ShardRouter` с пулом виртуальных баз.
2. Реализуйте детерминированное вычисление номера шарда по `user_id`.
3. Смоделируйте запись и чтение данных через соответствующий шард.
4. Верифицируйте равномерное распределение пользователей по шардам.

## Код решения

**`database_sharding_router_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

type ShardDatabaseInstance struct {
	ShardID int
	Storage map[string]string // имитация таблиц конкретного шарда
}

type ApplicationShardRouter struct {
	shardsCount int
	shards      []*ShardDatabaseInstance
}

func NewShardRouter(shardsCount int) *ApplicationShardRouter {
	instances := make([]*ShardDatabaseInstance, shardsCount)
	for i := 0; i < shardsCount; i++ {
		instances[i] = &ShardDatabaseInstance{
			ShardID: i,
			Storage: make(map[string]string),
		}
	}
	return &ApplicationShardRouter{
		shardsCount: shardsCount,
		shards:      instances,
	}
}

func (r *ApplicationShardRouter) GetShardIndex(userID string) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(userID))
	return int(h.Sum32() % uint32(r.shardsCount))
}

func (r *ApplicationShardRouter) SaveUserData(userID, payload string) int {
	shardIdx := r.GetShardIndex(userID)
	r.shards[shardIdx].Storage[userID] = payload
	return shardIdx
}

func TestDatabaseShardingRouter(t *testing.T) {
	router := NewShardRouter(16) // 16 шардов

	users := []string{"user-alice", "user-bob", "user-charlie", "user-diana"}
	seenShards := make(map[int]bool)

	for _, u := range users {
		shardIdx := router.SaveUserData(u, fmt.Sprintf("Profile data of %s", u))
		seenShards[shardIdx] = true
	}

	if len(seenShards) < 2 {
		t.Fatal("Данные должны распределяться по разным шардам")
	}

	// Проверяем идемпотентность выбора шарда для одного и того же пользователя
	aliceShard1 := router.GetShardIndex("user-alice")
	aliceShard2 := router.GetShardIndex("user-alice")
	if aliceShard1 != aliceShard2 {
		t.Fatalf("Маршрутизация шарда обязана быть строго детерминированной: %d != %d", aliceShard1, aliceShard2)
	}

	fmt.Println("Горизонтальное шардирование БД (Database Sharding) подтверждено:")
	for _, u := range users {
		fmt.Printf("  • Пользователь %-12s направлен на Shard #%d\n", u, router.GetShardIndex(u))
	}
	fmt.Printf("  • Всего активных шардов: 16 | Использовано в тесте: %d\n", len(seenShards))
}
```

## Под капотом

При шардировании `user_id % 16` добавление 17-го шарда приведет к перемещению 94% всех данных (Resharding Storm). Чтобы этого избежать, используют **Consistent Hashing (Согласованное хеширование)** с виртуальными нодами или таблицы каталогов (Directory-Based Sharding), где соответствие `user_id -> shard_id` хранится в быстром кэше.

## Подводные камни

Делать Cross-Shard JOIN: запрос вида «Найти всех пользователей, купивших товар X» потребует опроса всех 16 шардов (Scatter-Gather Query) и слияния результатов в памяти бэкенда, что крайне ресурсоемко. Межшардовые выборки выносят в поисковые индексы Elasticsearch или аналитический ClickHouse.

## На собеседовании

**Вопрос с собеседования:** «Как решать проблему суперпопулярных аккаунтов (Hot Partition / Celebrity Problem) при шардировании по автору?»
**Ответ:** Добавлять к ключу шардирования соль (Salt): вместо `sharding_key = author_id` используют составной ключ `sharding_key = hash(author_id + "_" + (post_id % 10))`. Это распределяет посты знаменитости равномерно по 10 разным шардам, ликвидируя перегрузку одного сервера.
