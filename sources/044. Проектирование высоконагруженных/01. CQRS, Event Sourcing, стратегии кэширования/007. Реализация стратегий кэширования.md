# Реализация стратегий кэширования: Cache-Aside, Write-Through и асинхронный Write-Behind

## Условие

**Caching Strategies**: Реализуйте Cache-Aside (lazy loading), Write-Through, Write-Behind (async write). Используйте Redis для hot data, CDN для static assets.

## Теория

Практическая реализация трех стратегий кэширования в Go:
- **Cache-Aside:**
  ```go
  val, err := cache.Get(key)
  if err != nil { val = db.Query(); cache.Set(key, val, ttl) }
  ```
- **Write-Through:**
  ```go
  db.Write(key, val)
  cache.Set(key, val, ttl)
  ```
- **Write-Behind:**
  ```go
  cache.Set(key, val, ttl)
  asyncWriteQueue <- Item{Key: key, Val: val} // фоновый воркер сбрасывает в БД
  ```

## Решение по шагам

1. Создайте интерфейс хранилища кэша и основной базы данных.
2. Реализуйте три метода записи и чтения по соответствующим стратегиям.
3. Продемонстрируйте работу фонового сброса Write-Behind очереди.
4. Верифицируйте корректность сохранения данных.

## Код решения

**`caching_strategies_impl_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type StorageEngine struct {
	mu         sync.Mutex
	cacheStore map[string]string
	dbStore    map[string]string
	writeQueue chan struct{ key, val string }
}

func NewStorageEngine() *StorageEngine {
	engine := &StorageEngine{
		cacheStore: make(map[string]string),
		dbStore:    make(map[string]string),
		writeQueue: make(chan struct{ key, val string }, 100),
	}
	// Фоновый воркер для Write-Behind
	go func() {
		for item := range engine.writeQueue {
			engine.mu.Lock()
			engine.dbStore[item.key] = item.val
			engine.mu.Unlock()
		}
	}()
	return engine
}

// 1. Cache-Aside Read
func (e *StorageEngine) GetCacheAside(key string) (string, string) {
	e.mu.Lock()
	defer e.mu.Unlock()

	if val, ok := e.cacheStore[key]; ok {
		return val, "CACHE_HIT"
	}

	val, ok := e.dbStore[key]
	if !ok {
		return "", "NOT_FOUND"
	}
	e.cacheStore[key] = val // Прогрев кэша
	return val, "CACHE_MISS_LOADED_FROM_DB"
}

// 2. Write-Through
func (e *StorageEngine) WriteThrough(key, val string) {
	e.mu.Lock()
	defer e.mu.Unlock()
	e.dbStore[key] = val
	e.cacheStore[key] = val
}

// 3. Write-Behind (Мгновенный возврат клиенту)
func (e *StorageEngine) WriteBehind(key, val string) {
	e.mu.Lock()
	e.cacheStore[key] = val
	e.mu.Unlock()

	e.writeQueue <- struct{ key, val string }{key, val}
}

func TestCachingStrategiesImpl(t *testing.T) {
	engine := NewStorageEngine()

	// 1. Проверяем Write-Through
	engine.WriteThrough("product:10", "Laptop Pro")
	val1, source1 := engine.GetCacheAside("product:10")
	if source1 != "CACHE_HIT" || val1 != "Laptop Pro" {
		t.Fatalf("Write-Through сбой: %s, %s", source1, val1)
	}

	// 2. Проверяем Write-Behind
	engine.WriteBehind("counter:likes", "1450")
	val2, source2 := engine.GetCacheAside("counter:likes")
	if source2 != "CACHE_HIT" || val2 != "1450" {
		t.Fatalf("Write-Behind сбой: %s, %s", source2, val2)
	}

	fmt.Println("Реализация стратегий кэширования подтверждена:")
	fmt.Printf("  • Write-Through чтение: %s (Источник: %s)\n", val1, source1)
	fmt.Printf("  • Write-Behind чтение:  %s (Источник: %s, Запись в фоне)\n", val2, source2)
}
```

## Под капотом

В распределенных средах статичный контент (изображения, стили, бандлы JS) кэшируется на периферии сети с помощью CDN (Cloudflare, Yandex Cloud CDN). Заголовки `Cache-Control: public, max-age=31536000, immutable` позволяют отсечь до 98% трафика до того, как запрос дойдет до бэкенда Go.

## Подводные камни

Не ограничивать размер очереди `writeQueue` в Write-Behind: при аварии базы данных очередь переполнит оперативную память и приведет к падению контейнера по OOM Killer. Очередь должна иметь фиксированную емкость и стратегию сброса нагрузки.

## На собеседовании

**Вопрос с собеседования:** «Что лучше обновлять в Cache-Aside при изменении данных: перезаписывать значение в кэше (`SET`) или удалять его (`DEL`)?»
**Ответ:** Лучше **удалять ключ (`DEL` / Invalidate)**. Если одновременно два параллельных запроса попытаются обновить кэш (`SET`), из-за гонки сетевых пакетов более старая версия может перезаписать более свежую. Удаление гарантирует, что следующий запрос надежно вычитает актуальные закоммиченные данные из БД.
