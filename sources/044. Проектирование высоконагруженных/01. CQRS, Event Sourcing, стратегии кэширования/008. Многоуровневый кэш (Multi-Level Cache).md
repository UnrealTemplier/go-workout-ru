# Многоуровневый кэш (Multi-Level Cache): L1 в памяти, L2 в Redis и L3 в PostgreSQL с метриками Hit Rate

## Условие

Реализуй **Multi-Level Cache**: L1 (in-process, `sync.Map`, 1ms), L2 (Redis, 5ms), L3 (PostgreSQL, 50ms). `GetUser`: L1 → L2 → L3. `Invalidate`: publish event, все уровни обновляются. Покажи hit rate per level.

## Теория

Иерархия кэширования L1 \(\to\) L2 \(\to\) L3:
- **L1 (In-Process RAM):** локальная память Go (`sync.Map`, Ristretto).
  - Задержка: **< 100 наносекунд** (в 50 000 раз быстрее Redis!).
- **L2 (Distributed In-Memory):** общий сетевой кластер Redis.
  - Задержка: **1–3 миллисекунды**.
- **L3 (Persistent Database):** реляционная СУБД PostgreSQL.
  - Задержка: **10–50 миллисекунд**.
- **Алгоритм поиска:**
  1. Проверяем L1 \(\to\) если HIT, возвращаем результат мгновенно.
  2. Если MISS в L1 \(\to\) проверяем L2 (Redis). При успехе прогреваем L1 и возвращаем.
  3. Если MISS в L2 \(\to\) читаем L3 (PostgreSQL), прогреваем L2 и L1.

## Решение по шагам

1. Создайте структуру трехуровневого кэша с подсчетом счетчиков попаданий.
2. Реализуйте метод `GetUser` с каскадным переходом по уровням.
3. Смоделируйте прогрев и инвалидацию кэша.
4. Рассчитайте метрику Hit Rate для каждого уровня.

## Код решения

**`multilevel_cache_hitrate_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
)

type MultiLevelCacheEngine struct {
	l1Memory sync.Map          // L1: In-process RAM
	l2Redis  map[string]string // L2: Redis cluster
	l3DB     map[string]string // L3: PostgreSQL

	l1Hits int64
	l2Hits int64
	l3Hits int64
}

func (c *MultiLevelCacheEngine) GetUser(userID string) (string, string) {
	// 1. Проверяем L1 (In-process memory)
	if val, ok := c.l1Memory.Load(userID); ok {
		atomic.AddInt64(&c.l1Hits, 1)
		return val.(string), "L1_MEMORY"
	}

	// 2. Проверяем L2 (Redis)
	if val, ok := c.l2Redis[userID]; ok {
		atomic.AddInt64(&c.l2Hits, 1)
		c.l1Memory.Store(userID, val) // Прогрев L1
		return val, "L2_REDIS"
	}

	// 3. Проверяем L3 (PostgreSQL)
	if val, ok := c.l3DB[userID]; ok {
		atomic.AddInt64(&c.l3Hits, 1)
		c.l2Redis[userID] = val        // Прогрев L2
		c.l1Memory.Store(userID, val) // Прогрев L1
		return val, "L3_DATABASE"
	}

	return "", "NOT_FOUND"
}

func (c *MultiLevelCacheEngine) Invalidate(userID string) {
	c.l1Memory.Delete(userID)
	delete(c.l2Redis, userID)
}

func TestMultiLevelCacheHitRate(t *testing.T) {
	engine := &MultiLevelCacheEngine{
		l2Redis: make(map[string]string),
		l3DB:    map[string]string{"user-1": "Анна Каренина"},
	}

	// Запрос 1: L3 (холодный старт)
	_, src1 := engine.GetUser("user-1")
	// Запрос 2: L1 (уже прогрет в памяти)
	_, src2 := engine.GetUser("user-1")
	// Запрос 3: L1
	_, src3 := engine.GetUser("user-1")

	if src1 != "L3_DATABASE" || src2 != "L1_MEMORY" || src3 != "L1_MEMORY" {
		t.Fatalf("Сбой каскада уровней: %s, %s, %s", src1, src2, src3)
	}

	total := float64(engine.l1Hits + engine.l2Hits + engine.l3Hits)
	l1Rate := (float64(engine.l1Hits) / total) * 100.0

	fmt.Println("Многоуровневый кэш (Multi-Level Cache L1/L2/L3) подтвержден:")
	fmt.Printf("  • Попадания L1 (RAM):   %d (%.1f%% Hit Rate)\n", engine.l1Hits, l1Rate)
	fmt.Printf("  • Попадания L2 (Redis): %d\n", engine.l2Hits)
	fmt.Printf("  • Попадания L3 (DB):    %d\n", engine.l3Hits)
	fmt.Println("  • Подавляющее большинство запросов обслуживается из памяти без сетевых накладных расходов")
}
```

ℹ️ Каскадная обработка промахов кэша на уровнях L1 (память), L2 (Redis) и L3 (СУБД)

## Под капотом

В микросервисах с сотнями подов инвалидация локального L1 кэша координируется через Redis Pub/Sub: сервис, изменивший данные, отправляет `PUBLISH invalidate user-1`. Все 100 подов слушают этот канал и моментально вызывают `l1Memory.Delete("user-1")`.

## Подводные камни

Использовать в L1 кэше `sync.Map` без механизма вытеснения (LRU / TinyLFU): при миллионах уникальных пользователей память пода переполнится. Для боевого L1 используют библиотеки с жестким ограничением размера памяти (например `dgraph-io/ristretto`).

## На собеседовании

**Вопрос с собеседования:** «Что делать, если сообщение инвалидации L1 через Redis Pub/Sub потеряется из-за сетевого сбоя?»
**Ответ:** Устанавливать на ключи в L1 жесткий короткий TTL (например 15–30 секунд). Даже при потере широковещательного пакета инвалидации под вернется к согласованному состоянию максимум через 30 секунд.
