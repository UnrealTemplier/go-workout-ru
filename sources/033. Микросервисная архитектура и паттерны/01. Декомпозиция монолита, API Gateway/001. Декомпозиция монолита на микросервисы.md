# Декомпозиция монолита на микросервисы: границы Bounded Context, независимые go.mod и Protobuf-контракты

## Условие

Раздели монолит на 3 сервиса: `user-service`, `order-service`, `notification-service`. Каждый — отдельный Go-модуль с собственным `go.mod`. Определи `.proto` для межсервисного общения.

## Теория

Принципы декомпозиции монолита на микросервисы (Domain-Driven Design):
- **Bounded Context (Ограниченный контекст):** Каждый микросервис владеет своей бизнес-моделью и изолированной базой данных (Database-per-Service).
- **Независимые Go-модули:**
  - `user-service/go.mod` (Управление аккаунтами и аутентификацией)
  - `order-service/go.mod` (Бизнес-логика оформления и оплаты заказов)
  - `notification-service/go.mod` (Отправка Email, SMS, Push через брокер сообщений)
- **API-First подход:** Контракты взаимодействия строго фиксируются в `.proto` файлах в общем репозитории схем или Git-модуле до написания кода.

## Решение по шагам

1. Создайте структуру монорепозитория со схемой proto.
2. Инициализируйте 3 независимых модуля Go (`go.mod`).
3. Опишите контракты сервисов в `api/proto/order.proto`.
4. Продемонстрируйте чистую архитектуру взаимодействия.

## Код решения

**`api/proto/order_service.proto`**

```protobuf
syntax = "proto3";

package order.v1;

option go_package = "github.com/company/order-service/pkg/orderv1;orderv1";

message CreateOrderRequest {
  string user_id = 1;
  repeated string item_ids = 2;
  double total_amount = 3;
}

message OrderResponse {
  string order_id = 1;
  string status = 2; // CREATED, PAID, SHIPPED
}

service OrderService {
  rpc CreateOrder (CreateOrderRequest) returns (OrderResponse);
}
```

**`Терминал`**

```bash
# Инициализация независимых микросервисов:
mkdir -p services/user-service services/order-service services/notification-service

cd services/user-service && go mod init github.com/company/user-service && cd ../..
cd services/order-service && go mod init github.com/company/order-service && cd ../..
cd services/notification-service && go mod init github.com/company/notification-service && cd ../..

# Проверяем независимость модулей:
ls -d services/*/go.mod
# services/notification-service/go.mod
# services/order-service/go.mod
# services/user-service/go.mod
```

**`microservice_architecture_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type OrderDTO struct {
	ID     string
	UserID string
	Amount float64
	Status string
}

type OrderServiceServerMock struct{}

func (s *OrderServiceServerMock) CreateOrder(ctx context.Context, req *OrderDTO) (*OrderDTO, error) {
	if req.UserID == "" {
		return nil, fmt.Errorf("user_id обязателен")
	}
	req.ID = "ord_2026_991"
	req.Status = "CREATED"
	return req, nil
}

func TestMicroserviceDecomposition(t *testing.T) {
	srv := &OrderServiceServerMock{}
	order, err := srv.CreateOrder(context.Background(), &OrderDTO{
		UserID: "usr_42",
		Amount: 4999.00,
	})
	if err != nil {
		t.Fatalf("Ошибка создания заказа: %v", err)
	}

	if order.Status != "CREATED" || order.ID != "ord_2026_991" {
		t.Fatalf("Некорректный результат: %+v", order)
	}

	fmt.Printf("Сервисный контракт успешно выполнен: Заказ #%s для пользователя %s (Статус: %s)\n",
		order.ID, order.UserID, order.Status)
}
```

ℹ️ Юнит-тест сервисного вызова с изолированным контекстом

## Под капотом

Разделение на независимые `go.mod` позволяет каждой команде использовать собственные версии сторонних библиотек, развертывать сервисы в изолированных Docker-контейнерах и масштабировать их по отдельности.

## Подводные камни

Общая база данных (Shared Database Anti-Pattern): предоставление прямого доступа `order-service` к таблицам `user-service` в PostgreSQL. Сервисы связываются намертво, и миграция схемы ломает оба сервиса. Сервисы общаются строго через API!

## На собеседовании

**Вопрос с собеседования:** «Когда НЕ следует делить монолит на микросервисы?»
**Ответ:** 1. На этапе стартапа (MVP), когда границы предметной области размыты и часто меняются. 2. При малой команде разработки (1-3 инженера), так как накладные расходы на CI/CD, Kubernetes, трейсинг и сетевую надежность превысят выгоду. 3. Когда задержка межсервисных сетевых вызовов (Network Latency) критична для бизнеса (Sub-millisecond HFT трейдинг).
