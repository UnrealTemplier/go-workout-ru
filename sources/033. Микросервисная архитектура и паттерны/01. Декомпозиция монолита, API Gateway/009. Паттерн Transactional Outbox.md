# Паттерн Transactional Outbox: надежная доставка событий через PostgreSQL в брокер сообщений

## Условие

Реализуй **Outbox pattern**: сервис пишет событие в PostgreSQL (`outbox` таблица) в одной транзакции с бизнес-данными. Отдельный воркер читает outbox, отправляет в Kafka/NATS, удаляет/помечает как отправленное.

## Теория

Проблема двойной записи (Dual-Write Problem) и её решение:
- Попытка сохранить заказ в БД и отправить сообщение в Kafka:
  ```go
  db.Exec("INSERT INTO orders ...")
  kafka.Produce("OrderCreated") // ЕСЛИ ЗДЕСЬ СБОЙ СЕТИ ИЛИ ПАДЕНИЕ ПОДА — СОБЫТИЕ ПОТЕРЯНО!
  ```
- **Паттерн Transactional Outbox:**
  1. В единой ACID транзакции БД сохраняется заказ и строка в таблице `outbox_messages`:
     `BEGIN; INSERT INTO orders ...; INSERT INTO outbox_messages ...; COMMIT;`
  2. Фоновый процесс (Outbox Relay или Debezium CDC) вычитывает неотправленные строки.
  3. Отправляет их в Kafka/NATS.
  4. Помечает `processed_at = NOW()`.

## Решение по шагам

1. Создайте модель единой ACID транзакции.
2. Реализуйте запись в Outbox.
3. Напишите фоновый воркер-реле отправки сообщений.
4. Протестируйте гарантированную доставку.

## Код решения

**`transactional_outbox_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type OutboxMessage struct {
	ID        int
	Topic     string
	Payload   string
	Processed bool
}

type MockTransactionalDB struct {
	mu       sync.Mutex
	orders   map[string]string
	outbox   []*OutboxMessage
	broker   []string // Имитация топика Kafka
	seqID    int
}

func NewMockDB() *MockTransactionalDB {
	return &MockTransactionalDB{
		orders: make(map[string]string),
	}
}

func (db *MockTransactionalDB) CreateOrderWithOutbox(orderID, item string) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Атомарная запись бизнес-сущности
	db.orders[orderID] = item

	// 2. Атомарная запись события в Outbox в той же транзакции!
	db.seqID++
	db.outbox = append(db.outbox, &OutboxMessage{
		ID:        db.seqID,
		Topic:     "orders-events",
		Payload:   fmt.Sprintf(`{"order_id":%q,"item":%q}`, orderID, item),
		Processed: false,
	})

	return nil
}

func (db *MockTransactionalDB) RunOutboxRelayWorker() int {
	db.mu.Lock()
	defer db.mu.Unlock()

	sentCount := 0
	for _, msg := range db.outbox {
		if !msg.Processed {
			// Отправка в Kafka
			db.broker = append(db.broker, msg.Payload)
			msg.Processed = true
			sentCount++
		}
	}
	return sentCount
}

func TestTransactionalOutbox(t *testing.T) {
	db := NewMockDB()

	// Создаем 2 заказа
	_ = db.CreateOrderWithOutbox("ord_1", "Сервер Dell R740")
	_ = db.CreateOrderWithOutbox("ord_2", "Коммутатор Cisco 9300")

	if len(db.broker) != 0 {
		t.Fatal("Брокер не должен получать сообщения до работы реле")
	}

	// Фоновый реле-воркер вычитывает outbox
	delivered := db.RunOutboxRelayWorker()
	if delivered != 2 || len(db.broker) != 2 {
		t.Fatalf("Ожидалась доставка 2 сообщений, получено: %d", delivered)
	}

	fmt.Printf("Transactional Outbox успешно опубликовал %d событий в брокер:\n", delivered)
	for i, payload := range db.broker {
		fmt.Printf("  [%d] Kafka message: %s\n", i+1, payload)
	}
}
```

## Под капотом

Самым эффективным способом реализации Outbox является Change Data Capture (CDC): Debezium читает WAL (Write-Ahead Log) PostgreSQL напрямую с диска, исключая опрос базы через `SELECT ... FOR UPDATE`.

## Подводные камни

Использовать простой опрос `SELECT * FROM outbox WHERE processed = false` при десятках воркеров без `FOR UPDATE SKIP LOCKED`: воркеры будут блокировать друг друга.

## На собеседовании

**Вопрос с собеседования:** «Какую семантику доставки обеспечивает Transactional Outbox?»
**Ответ:** Семантику **At-Least-Once** (как минимум один раз). В случае сбоя сети во время подтверждения коммита в Kafka сообщение может быть отправлено повторно. Потребители событий ОБЯЗАНЫ быть идемпотентными (Idempotent Consumer).
