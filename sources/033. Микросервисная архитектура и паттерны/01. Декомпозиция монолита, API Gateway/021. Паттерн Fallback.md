# Паттерн Fallback: плавная деградация функционала и выдача устаревших данных из кэша

## Условие

Реализуй **Fallback**: если `GetUserFromService` падает — верни stale-данные из кеша. Если кеша нет — верни default/empty response. Не проваливай весь запрос из-за одного сервиса.

## Теория

Паттерн мягкой деградации (Graceful Degradation / Fallback):
- При падении вторичного сервиса (например, сервиса рекомендаций или персональных настроек) нельзя показывать пользователю белый экран с ошибкой 500.
- Стратегия Fallback:
  1. Попытка вызова сервиса `GetUser(id)`.
  2. При ошибке: попытка прочитать устаревшие данные (Stale Cache) из локального Redis.
  3. Если в кэше пусто: возврат безопасного значения по умолчанию (`Guest User`, пустой список рекомендаций).
- Пользователь продолжает пользоваться приложением, даже не заметив кратковременного сбоя в бэкенде.

## Решение по шагам

1. Создайте функцию получения пользователя с Fallback цепочкой.
2. Смоделируйте ошибку сетевого вызова.
3. Проверьте возврат stale-данных из кэша.
4. Протестируйте дефолтный ответ при пустом кэше.

## Код решения

**`graceful_fallback_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type UserProfile struct {
	Name    string
	IsStale bool
	IsGuest bool
}

type UserClientWithFallback struct {
	staleCache map[string]string
}

func (c *UserClientWithFallback) GetUserWithFallback(ctx context.Context, id string, simulateDown bool) UserProfile {
	// 1. Попытка вызвать реальный сервис
	if !simulateDown {
		return UserProfile{Name: "Иван Иванов", IsStale: false}
	}

	// 2. Сбой сети -> Fallback #1: Устаревший кэш (Stale Cache)
	if cachedName, ok := c.staleCache[id]; ok {
		fmt.Printf("  [Fallback Stale Cache] Сервис недоступен: отдаем кэш для %s\n", id)
		return UserProfile{Name: cachedName, IsStale: true}
	}

	// 3. Кэша нет -> Fallback #2: Значение по умолчанию
	fmt.Printf("  [Fallback Default] Кэш пуст: отдаем профиль Гостя для %s\n", id)
	return UserProfile{Name: "Уважаемый Гость", IsGuest: true}
}

func TestFallbackPipeline(t *testing.T) {
	client := &UserClientWithFallback{
		staleCache: map[string]string{"usr_1": "Иван (из кэша 1 час назад)"},
	}

	// Сценарий 1: Сервер упал, но есть stale-кэш
	p1 := client.GetUserWithFallback(context.Background(), "usr_1", true)
	if !p1.IsStale || p1.Name != "Иван (из кэша 1 час назад)" {
		t.Fatalf("Ожидался stale-профиль: %+v", p1)
	}

	// Сценарий 2: Сервер упал и кэша нет -> возврат Гостя
	p2 := client.GetUserWithFallback(context.Background(), "usr_unknown", true)
	if !p2.IsGuest || p2.Name != "Уважаемый Гость" {
		t.Fatalf("Ожидался гостевой профиль: %+v", p2)
	}

	fmt.Println("Паттерн Fallback успешно обеспечил бесперебойный пользовательский опыт!")
}
```

## Под капотом

В заголовках HTTP ответов при выдаче stale-данных возвращается директива `Warning: 110 - "Response is Stale"`, информирующая клиента о временной деградации источника.

## Подводные камни

Использовать Fallback для финансовых транзакций: нельзя делать fallback на списание денег или создание платежа! Fallback применим strictly для операций чтения контента и вспомогательных сервисов.

## На собеседовании

**Вопрос с собеседования:** «Что такое заголовок Cache-Control: stale-while-revalidate?»
**Ответ:** Это стандарт HTTP кэширования RFC 5861: браузер мгновенно отображает пользователю устаревший кэш (Stale response), а в фоновом режиме отправляет асинхронный запрос на сервер для обновления кэша, обеспечивая нулевое время загрузки страницы.
