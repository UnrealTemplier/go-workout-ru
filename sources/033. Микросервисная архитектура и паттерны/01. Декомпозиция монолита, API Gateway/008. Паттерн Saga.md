# Паттерн Saga: координатор распределенных транзакций и компенсирующие действия

## Условие

Реализуй **Saga pattern** (упрощённый): `CreateOrder` вызывает `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Если шаг падает — компенсируй предыдущие (`ReleaseInventory`, `RefundPayment`). Используй gRPC + координатор.

## Теория

Оркестрация распределенной саги (Saga Orchestration):
- В распределенной архитектуре распределенные транзакции (2PC / XA) запрещены из-за блокировок.
- Шаги саги:
  1. `CreateOrder` (Заказ создан)
  2. `ReserveInventory` (Товар зарезервирован)
  3. `ProcessPayment` (Списание денег)
  4. `ShipOrder` (Передача в доставку)
- При падении на этапе `ShipOrder`:
  - Координатор запускает компенсирующие транзакции в обратном порядке:
    1. `RefundPayment` (Возврат денег клиенту)
    2. `ReleaseInventory` (Снятие брони с товара)
    3. `CancelOrder` (Перевод заказа в статус CANCELED).

## Решение по шагам

1. Создайте структуру шагов саги с функциями прямого хода и компенсации.
2. Реализуйте LIFO порядок отката при ошибке.
3. Сымитируйте сбой платежа.
4. Убедитесь в вызове отката склада.

## Код решения

**`saga_coordinator_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type SagaAction struct {
	Name       string
	Execute    func(ctx context.Context) error
	Compensate func(ctx context.Context) error
}

type SagaManager struct {
	actions []SagaAction
}

func (sm *SagaManager) AddAction(action SagaAction) {
	sm.actions = append(sm.actions, action)
}

func (sm *SagaManager) ExecuteSaga(ctx context.Context) error {
	var completed []SagaAction

	for _, action := range sm.actions {
		fmt.Printf("  [Saga Exec] Шаг: %s\n", action.Name)
		if err := action.Execute(ctx); err != nil {
			fmt.Printf("  [Saga FAIL] Ошибка на шаге %s: %v. Инициируем компенсацию!\n", action.Name, err)
			sm.rollback(ctx, completed)
			return err
		}
		completed = append(completed, action)
	}

	return nil
}

func (sm *SagaManager) rollback(ctx context.Context, completed []SagaAction) {
	for i := len(completed) - 1; i >= 0; i-- {
		action := completed[i]
		if action.Compensate != nil {
			fmt.Printf("  [Saga Compensate] Откат действия: %s\n", action.Name)
			_ = action.Compensate(ctx)
		}
	}
}

func TestSagaFlow(t *testing.T) {
	saga := &SagaManager{}

	warehouseRollback := false
	saga.AddAction(SagaAction{
		Name: "ReserveInventory",
		Execute: func(ctx context.Context) error {
			fmt.Println("    -> Склад: товар зарезервирован")
			return nil
		},
		Compensate: func(ctx context.Context) error {
			warehouseRollback = true
			fmt.Println("    -> Склад: бронь снята (компенсация)")
			return nil
		},
	})

	saga.AddAction(SagaAction{
		Name: "ProcessPayment",
		Execute: func(ctx context.Context) error {
			return fmt.Errorf("банковский шлюз отклонил транзакцию (недостаточно средств)")
		},
		Compensate: func(ctx context.Context) error { return nil },
	})

	err := saga.ExecuteSaga(context.Background())
	if err == nil {
		t.Fatal("Ожидался сбой саги")
	}

	if !warehouseRollback {
		t.Fatal("Компенсация склада не была вызвана!")
	}

	fmt.Println("Паттерн Saga успешно локализовал ошибку и восстановил согласованность данных!")
}
```

## Под капотом

В распределенных системах состояние саги сохраняется в постоянное хранилище (Saga Log), чтобы при аварийном перезапуске координатора он мог продолжить выполнение шагов или компенсаций.

## Подводные камни

Делать компенсирующие транзакции неидемпотентными: если сетевой вызов компенсации вернет таймаут, координатор повторит попытку. Компенсация обязана поддерживать повторные вызовы без двойных списаний/начислений.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если компенсирующая транзакция сама падает с критической ошибкой (Semantic Failure)?»
**Ответ:** Компенсирующие транзакции не могут быть отменены. При сбое компенсации координатор повторяет вызов с экспоненциальной задержкой (Retry Until Success). Если ошибка непреодолима (баг в коде), транзакция переводится в статус `MANUAL_INTERVENTION_REQUIRED` и отправляется алерт дежурным инженерам.
