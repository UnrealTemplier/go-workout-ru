# Интерцептор повторных попыток: интеграция политики Retry с Backoff и Jitter на клиенте

## Условие

Добавьте retry с exponential backoff и jitter: настройте политику повторных попыток через перехватчик клиента.

## Теория

Архитектура клиентского перехватчика повторных попыток (Retry Client Interceptor):
- Перехватчик оборачивает метод `invoker(ctx, method, req, reply, cc, opts...)`.
- При получении временных кодов (`codes.Unavailable`, `codes.ResourceExhausted`):
  1. Вычисляется экспоненциальная задержка со случайным сдвигом (Jitter).
  2. Проверяется, не истек ли родительский дедлайн `ctx.Done()`.
  3. Повторяется вызов инвокера до достижения `maxRetries`.

## Решение по шагам

1. Создайте UnaryClientInterceptor повторов.
2. Настройте список кодов для повтора.
3. Смоделируйте временный сбой и восстановление на 2-й попытке.
4. Протестируйте работу интерцептора.

## Код решения

**`retry_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func UnaryRetryInterceptor(maxRetries int, baseDelay time.Duration) grpc.UnaryClientInterceptor {
	return func(
		ctx context.Context,
		method string,
		req, reply any,
		cc *grpc.ClientConn,
		invoker grpc.UnaryInvoker,
		opts ...grpc.CallOption,
	) error {
		var err error
		for attempt := 0; attempt <= maxRetries; attempt++ {
			err = invoker(ctx, method, req, reply, cc, opts...)
			if err == nil {
				return nil
			}

			// Повторяем только при временной недоступности
			if status.Code(err) != codes.Unavailable {
				return err
			}

			if attempt == maxRetries {
				break
			}

			delay := baseDelay * time.Duration(1<<attempt)
			fmt.Printf("  [Retry Interceptor] Попытка %d провалена (%v). Ожидание %v...\n",
				attempt+1, err, delay)

			select {
			case <-ctx.Done():
				return ctx.Err()
			case <-time.After(delay):
			}
		}
		return err
	}
}

func TestRetryInterceptorFlow(t *testing.T) {
	interceptor := UnaryRetryInterceptor(3, 10*time.Millisecond)

	attempts := 0
	mockInvoker := func(ctx context.Context, method string, req, reply any, cc *grpc.ClientConn, opts ...grpc.CallOption) error {
		attempts++
		if attempts < 3 {
			return status.Error(codes.Unavailable, "сеть моргнула")
		}
		return nil // На 3-й попытке успех
	}

	err := interceptor(context.Background(), "/order.v1/GetStatus", nil, nil, nil, mockInvoker)
	if err != nil {
		t.Fatalf("Интерцептор должен был восстановить вызов: %v", err)
	}

	if attempts != 3 {
		t.Fatalf("Ожидалось 3 попытки, выполнено: %d", attempts)
	}

	fmt.Printf("Интерцептор успешно доставил запрос после %d попыток!\n", attempts)
}
```

## Под капотом

Интерцепторы в gRPC организуются в виде цепочки (Chain). Повторный вызов `invoker` в цикле повторно прогоняет запрос через все нижележащие слои стека.

## Подводные камни

Повторять неидемпотентные мутации (например списание с баланса) без передачи Idempotency Key: если первый запрос на самом деле выполнился, а упал только ответ, повтор приведет к двойному списанию средств.

## На собеседовании

**Вопрос с собеседования:** «Почему декларативный Retry Policy в gRPC Service Config предпочтительнее ручного интерцептора?»
**Ответ:** Декларативная политика в Service Config (`retryPolicy`) управляется централизованно через DNS/Consul/xDS без изменения клиентского кода, поддерживая автоматический парсинг `PushBack` заголовков сервера и `maxAttempts`.
