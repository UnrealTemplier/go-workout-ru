# Балансировка через DNS Resolver: резолвинг нескольких A-записей по схеме dns:///

## Условие

Используйте `dns` резолвер gRPC: зарегистрируйте несколько адресов для имени в `/etc/hosts` (или локальном DNS) и проверьте балансировку с `grpc.Dial("dns:///service:50051")`.

## Теория

Резолвер адресов DNS в gRPC:
- Синтаксис адреса: `dns:///[authority]/host:port`.
  - Префикс `dns:///` сообщает gRPC использовать стандартный DNS-резолвер.
  - DNS-сервер возвращает массив A или AAAA записей.
- Клиент открывает постоянное HTTP/2 соединение **к каждому возвращенному IP-адресу**.
- Политика `round_robin` распределяет RPC-вызовы по всем живым соединениям.

## Решение по шагам

1. Настройте конфигурацию соединения с префиксом `dns:///`.
2. Укажите политику `round_robin`.
3. Смоделируйте резолвинг трех IP адресов сервиса.
4. Продемонстрируйте конфигурацию клиента.

## Код решения

**`dns_resolver_demo.go`**

```go
package main

import (
	"fmt"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

func main() {
	// Декларативная политика циклической балансировки
	serviceConfig := `{"loadBalancingPolicy":"round_robin"}`

	// gRPC клиент с подключением через DNS резолвер
	target := "dns:///order-service.internal:50051"

	conn, err := grpc.NewClient(
		target,
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithDefaultServiceConfig(serviceConfig),
	)
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	fmt.Printf("gRPC клиент успешно сконфигурирован с DNS резолвером:\n")
	fmt.Printf("  Target URI: %s\n", target)
	fmt.Printf("  Балансировка: Round Robin по всем A-записям домена\n")
}
```

## Под капотом

DNS Resolver в Go использует стандартную функцию `net.LookupHost`. Резолвер периодически переопрашивает DNS, динамически добавляя и удаляя адреса подов без перезапуска клиента.

## Подводные камни

Использовать `grpc.Dial` (устаревший) вместо `grpc.NewClient` в Go 1.22+: старый `Dial` блокирует запуск при старте, если DNS-имя временно не резолвится.

## На собеседовании

**Вопрос с собеседования:** «Почему в Kubernetes при использовании схемы dns:/// сервис должен быть Headless (clusterIP: None)?»
**Ответ:** Стандартный ClusterIP сервис k8s возвращает единственный виртуальный IP kube-proxy. DNS резолвер gRPC видит только один адрес и открывает ровно одно соединение к одному поду. Headless-сервис (`clusterIP: None`) возвращает список IP-адресов ВСЕХ подов, позволяя gRPC клиенту подключиться ко всем подам и распределять трафик поровну.
