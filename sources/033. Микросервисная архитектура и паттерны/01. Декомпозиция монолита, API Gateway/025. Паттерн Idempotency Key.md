# Паттерн Idempotency Key: защита от дублирования финансовых транзакций с кэшированием в Redis

## Условие

Реализуй **Idempotency Key**: клиент генерирует `Idempotency-Key: uuid` для mutation-запросов. Сервер хранит обработанные ключи (Redis, TTL=24h). При повторе с тем же ключом — верни кешированный ответ, не выполняй повторно.

## Теория

Принцип идемпотентности мутирующих операций (Idempotency Key Pattern):
- Клиент перед отправкой платежа генерирует случайный UUID v4:
  `Idempotency-Key: 7b31cf46-27a3-41c3-8f0a-115f2081c7e2`.
- Алгоритм работы сервера:
  1. Проверяем наличие ключа в Redis: `GET idempotency:<key>`.
  2. Если найден: возвращаем **сохраненный ранее результат** со статусом `HTTP 200 / OK` без повторного списания с карты!
  3. Если не найден: атомарно захватываем распределенный замок (`SETNX`), выполняем платеж, сохраняем ответ в Redis с TTL=24h и возвращаем клиенту.

## Решение по шагам

1. Создайте модель сервиса платежей с хранилищем ключей.
2. Проверьте обработку первого вызова с ключом.
3. Отправьте повторный вызов с тем же ключом.
4. Убедитесь, что бизнес-логика списания не сработала дважды.

## Код решения

**`idempotency_key_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

type PaymentResult struct {
	TransactionID string
	Amount        float64
	Status        string
}

type IdempotentPaymentService struct {
	mu           sync.Mutex
	redisCache   map[string]PaymentResult
	actualCharges int
}

func NewPaymentService() *IdempotentPaymentService {
	return &IdempotentPaymentService{
		redisCache: make(map[string]PaymentResult),
	}
}

func (s *IdempotentPaymentService) ProcessPayment(ctx context.Context, idempotencyKey string, amount float64) (PaymentResult, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверяем наличие кэшированного результата
	if cached, exists := s.redisCache[idempotencyKey]; exists {
		fmt.Printf("  [Idempotency HIT] Ключ %s уже обработан! Возвращаем кэш.\n", idempotencyKey)
		return cached, true
	}

	// 2. Реальное списание денег
	s.actualCharges++
	txID := fmt.Sprintf("tx_bank_%d", s.actualCharges)
	res := PaymentResult{
		TransactionID: txID,
		Amount:        amount,
		Status:        "CONFIRMED",
	}

	// 3. Сохранение в Redis (TTL=24h)
	s.redisCache[idempotencyKey] = res
	fmt.Printf("  [Idempotency MISS] Первое списание: %s на сумму %.2f ₽\n", txID, amount)
	return res, false
}

func TestIdempotencyProtection(t *testing.T) {
	svc := NewPaymentService()
	key := "uuid-payment-order-42"

	// 1-я попытка (нормальная)
	res1, isCached1 := svc.ProcessPayment(context.Background(), key, 4500.00)
	if isCached1 || res1.TransactionID != "tx_bank_1" {
		t.Fatalf("Некорректная 1-я операция: %+v", res1)
	}

	// 2-я попытка (повтор из-за сбоя сети)
	res2, isCached2 := svc.ProcessPayment(context.Background(), key, 4500.00)
	if !isCached2 || res2.TransactionID != "tx_bank_1" {
		t.Fatalf("Повторный запрос не должен создавать новую транзакцию: %+v", res2)
	}

	if svc.actualCharges != 1 {
		t.Fatalf("Деньги списаны более 1 раза! actualCharges=%d", svc.actualCharges)
	}

	fmt.Printf("Идемпотентность доказана: 2 запроса привели ровно к 1 банковской проводке!\n")
}
```

ℹ️ Гарантия идемпотентности платежей через кэширование результатов

## Под капотом

Для защиты от одновременных параллельных запросов с одним и тем же ключом используется атомарная команда Redis `SET idempotency:<key> "PROCESSING" NX EX 60`. Второй запрос получает отказ о том, что транзакция уже в процессе выполнения.

## Подводные камни

Использовать один и тот же Idempotency-Key для разных параметров запроса (например поменялась сумма или валюта): сервер обязан проверять хеш тела запроса (Payload Hash) и возвращать ошибку `422 Unprocessable Entity` при несовпадении.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать Idempotency Key на уровне базы данных PostgreSQL без Redis?»
**Ответ:** Создать таблицу `processed_requests(idempotency_key UUID PRIMARY KEY, request_hash TEXT, response_body JSONB, created_at TIMESTAMPTZ)`. Запись в эту таблицу выполняется внутри той же ACID транзакции, что и изменение баланса. Уникальный индекс `PRIMARY KEY` блокирует любые попытки параллельной вставки одинаковых ключей.
