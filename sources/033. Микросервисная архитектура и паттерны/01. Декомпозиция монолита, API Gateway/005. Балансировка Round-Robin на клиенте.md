# Балансировка Round-Robin на клиенте: циклический опрос пула адресов

## Условие

Запустите два экземпляра одного gRPC-сервиса на разных портах. Напишите клиент с ручным списком адресов и простым round-robin (выбор следующего адреса).

## Теория

Принцип циклической балансировки нагрузки (Client-Side Round-Robin):
- У клиента есть список адресов бэкендов: `["10.0.1.1:50051", "10.0.1.2:50052"]`.
- Для распределения вызовов используется атомарный счетчик:
  \(\text{index} = \text{counter} \pmod N\)
- Атомарный инкремент `atomic.AddUint64(&counter, 1)` гарантирует потокобезопасность вызова без захвата тяжелых мьютексов.

## Решение по шагам

1. Создайте структуру балансировщика с пулом адресов.
2. Реализуйте метод `Next()` на базе `sync/atomic`.
3. Смоделируйте выполнение 6 запросов к двум серверам.
4. Проверьте равномерное распределение 50/50.

## Код решения

**`client_round_robin_test.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"testing"
)

type SimpleRoundRobin struct {
	endpoints []string
	counter   uint64
}

func NewSimpleRoundRobin(endpoints []string) *SimpleRoundRobin {
	return &SimpleRoundRobin{endpoints: endpoints}
}

func (rr *SimpleRoundRobin) Next() string {
	idx := atomic.AddUint64(&rr.counter, 1) % uint64(len(rr.endpoints))
	return rr.endpoints[idx]
}

func TestRoundRobinDistribution(t *testing.T) {
	nodes := []string{"127.0.0.1:50051", "127.0.0.1:50052"}
	balancer := NewSimpleRoundRobin(nodes)

	stats := make(map[string]int)
	for i := 1; i <= 6; i++ {
		addr := balancer.Next()
		stats[addr]++
		fmt.Printf("Запрос #%d -> отправлен на инстанс: %s\n", i, addr)
	}

	for _, addr := range nodes {
		if stats[addr] != 3 {
			t.Fatalf("Ожидалось ровно 3 вызова на %s, получено: %d", addr, stats[addr])
		}
	}

	fmt.Println("Балансировка Round-Robin идеально распределила трафик 50/50!")
}
```

## Под капотом

Атомарная инструкция `LOCK XADD` на процессорах x86 выполняется за считанные такты ядра без переключения контекста ОС, поддерживая миллионы вычислений адреса в секунду.

## Подводные камни

Использовать обычный счетчик `counter++` без `sync/atomic`: одновременные горутины вызовут гонку данных и перекос балансировки.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях обычный Round-Robin оказывается неэффективным?»
**Ответ:** Когда запросы сильно различаются по ресурсоемкости (один запрос выполняется 2 мс, а соседний — 5 секунд) или сервера имеют разную мощность CPU. В таких случаях используют алгоритм **Least Connection (минимальное число активных запросов)** или **Peak EWMA (с учетом скользящей задержки ответа)**.
