# Распределенная трассировка с OpenTelemetry: сквозные спаны и контекст вызова в Jaeger

## Условие

Настрой **distributed tracing** (OpenTelemetry + Jaeger): инструментируй gRPC client/server interceptors. Каждый RPC — span. Смотри trace в Jaeger UI: timeline, зависимости, latency каждого hop.

## Теория

Сквозная трассировка распределенных вызовов (Distributed Tracing):
- В цепочке `Gateway -> Order Service -> Payment Service -> Bank`:
  - Каждый сервис создает дочерний отрезок времени — **Span**.
  - Все спаны объединяются глобальным 128-битным идентификатором **Trace ID**.
  - Контекст пробрасывается через сетевые метаданные HTTP/2 по стандарту **W3C TraceContext** (`traceparent`).
- Jaeger UI отображает интерактивный таймлайн выполнения (Waterfall View), наглядно демонстрируя, какой именно микросервис вызвал задержку.

## Решение по шагам

1. Создайте модель спана трассировки.
2. Реализуйте генерацию и наследование Trace ID.
3. Смоделируйте сквозной вызов через 3 микросервиса.
4. Проверьте непрерывность цепочки трейса.

## Код решения

**`distributed_tracing_demo_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type Span struct {
	TraceID   string
	SpanID    string
	Service   string
	Operation string
	Duration  time.Duration
}

type MockTracer struct {
	spans []*Span
}

func (t *MockTracer) StartSpan(traceID, spanID, svc, op string, d time.Duration) {
	t.spans = append(t.spans, &Span{
		TraceID:   traceID,
		SpanID:    spanID,
		Service:   svc,
		Operation: op,
		Duration:  d,
	})
}

func TestDistributedTracePropagation(t *testing.T) {
	tracer := &MockTracer{}
	rootTraceID := "4bf92f3577b34da6a3ce929d0e0e4736"

	// Hop 1: API Gateway
	tracer.StartSpan(rootTraceID, "span_gw_01", "api-gateway", "POST /orders", 85*time.Millisecond)

	// Hop 2: Order Service (дочерний вызов)
	tracer.StartSpan(rootTraceID, "span_order_02", "order-service", "CreateOrder", 60*time.Millisecond)

	// Hop 3: Payment Service (вложенный RPC вызов)
	tracer.StartSpan(rootTraceID, "span_pay_03", "payment-service", "ChargeCard", 45*time.Millisecond)

	if len(tracer.spans) != 3 {
		t.Fatalf("Ожидалось 3 спана в трейсе")
	}

	fmt.Println("Сквозная трассировка Jaeger (единый TraceID):")
	for idx, s := range tracer.spans {
		fmt.Printf("  [%d] Service: %-15s | Op: %-12s | TraceID: %s | Latency: %v\n",
			idx+1, s.Service, s.Operation, s.TraceID, s.Duration)
		if s.TraceID != rootTraceID {
			t.Fatalf("Разрыв трассировки на сервисе %s", s.Service)
		}
	}
}
```

## Под капотом

Официальная библиотека `go.opentelemetry.io/contrib/instrumentation/google.golang.org/grpc/otelgrpc` сериализует спаны в фоновом батч-экспортере (BatchSpanProcessor), отправляя их по UDP/gRPC на OTel Collector без блокировки горячего пути обработки запросов.

## Подводные камни

Использовать 100% сэмплирование (Sampling Rate 1.0) под нагрузкой 500 000 RPS: объем трейсов забьет сеть и жесткие диски Jaeger. Используйте Probabilistic Sampler (1–5%) или Tail-Based Sampler (сохранять 100% трейсов с ошибками и медленными ответами).

## На собеседовании

**Вопрос с собеседования:** «Что такое Tail-Based Sampling в OpenTelemetry Collector?»
**Ответ:** При обычном Head-Based сэмплировании решение о записи трейса принимается на входе (случайно 1%). Если запрос упал с ошибкой 500 в глубине стека, трейс может быть потерян. При Tail-Based сэмплировании OTel Collector буферизирует весь граф спанов в памяти до окончания запроса и гарантированно сохраняет трейс, если в нем возникла ошибка или латентность превысила SLA (например > 500 мс).
