# Паттерн Bulkhead (Переборки): изоляция ресурсов и раздельные пулы воркеров

## Условие

Реализуй **Bulkhead** (ограничение ресурсов): сервис A вызывает B и C. Отдельные пулы горутин/каналов для B и C. Если B упал — C продолжает работать. Не исчерпай все ресурсы на одном зависимом сервисе.

## Теория

Морской паттерн отсеков (Bulkhead Pattern):
- Происхождение: на кораблях трюм разделен водонепроницаемыми переборками (bulkheads). При пробоине одного отсека остальные остаются сухими, и корабль не тонет.
- В микросервисах:
  - Если Сервис А выделяет один общий пул на 100 горутин для вызова Сервиса B (Почта) и Сервиса C (Платежи).
  - Если Почтовый сервис зависает, все 100 горутин застревают в ожидании почты.
  - Платежи перестают работать, хотя сервис платежей полностью здоров!
- **Решение Bulkhead:**
  - Пул для сервиса B: максимум 20 горутин (буферизированный канал `make(chan struct{}, 20)`).
  - Пул для сервиса C: максимум 80 горутин.

## Решение по шагам

1. Создайте структуру семафора ограничения емкости отсека.
2. Изолируйте вызовы к разным сервисам в независимые отсеки.
3. Смоделируйте переполнение отсека зависшего сервиса.
4. Проверьте бесперебойную работу второго сервиса.

## Код решения

**`bulkhead_isolation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type BulkheadCompartment struct {
	tokens chan struct{}
}

func NewBulkhead(maxConcurrency int) *BulkheadCompartment {
	ch := make(chan struct{}, maxConcurrency)
	for i := 0; i < maxConcurrency; i++ {
		ch <- struct{}{}
	}
	return &BulkheadCompartment{tokens: ch}
}

func (b *BulkheadCompartment) Execute(ctx context.Context, action func() error) error {
	select {
	case <-b.tokens:
		defer func() { b.tokens <- struct{}{} }()
		return action()
	default:
		return fmt.Errorf("bulkhead exhausted: отсек переполнен (отказ в обслуживании)")
	}
}

func TestBulkheadCompartmentIsolation(t *testing.T) {
	// Отсек почтового сервиса: макс 2 одновременных запроса
	emailBulkhead := NewBulkhead(2)
	// Отсек платежного сервиса: макс 5 одновременных запросов
	paymentBulkhead := NewBulkhead(5)

	// Забиваем оба слота отсека Email зависшими задачами
	for i := 0; i < 2; i++ {
		go func() {
			_ = emailBulkhead.Execute(context.Background(), func() error {
				time.Sleep(100 * time.Millisecond) // Завис
				return nil
			})
		}()
	}
	time.Sleep(10 * time.Millisecond)

	// 3-й запрос к Email немедленно отклоняется переборкой
	errEmail := emailBulkhead.Execute(context.Background(), func() error { return nil })
	if errEmail == nil {
		t.Fatal("Отсек Email должен быть переполнен")
	}
	fmt.Println("Отсек зависшего Email сервиса изолирован:", errEmail)

	// При этом платежный сервис работает стабильно и мгновенно!
	paymentSuccess := false
	errPay := paymentBulkhead.Execute(context.Background(), func() error {
		paymentSuccess = true
		return nil
	})
	if errPay != nil || !paymentSuccess {
		t.Fatalf("Платежный сервис не должен страдать от сбоя почты: %v", errPay)
	}

	fmt.Println("Платежный сервис успешно обработал запрос в изолированном отсеке!")
}
```

## Под капотом

Канал `chan struct{}` емкостью \(N\) работает как эффективный семафор счетчика (Counting Semaphore) без накладных расходов на системные вызовы ядра ОС.

## Подводные камни

Использовать небуферизированный канал `chan struct{}`: емкость будет равна нулю, и ни один запрос не сможет выполниться.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Bulkhead на основе пула горутин (Thread Pool Isolation) от семафорного Bulkhead (Semaphore Isolation)?»
**Ответ:** Семафорный Bulkhead (на каналах) работает в контексте вызывающей горутины и имеет околонулевой оверхед по памяти, но не защищает от зависания внутри блокирующего системного вызова. Пул горутин запускает вызов в отдельной горутине, позволяя принудительно прервать ожидание по таймауту, но расходует память на стек каждой горутины.
