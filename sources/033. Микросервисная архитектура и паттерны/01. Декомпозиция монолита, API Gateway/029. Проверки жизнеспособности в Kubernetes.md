# Проверки жизнеспособности в Kubernetes: разграничение Liveness (/healthz) и Readiness (/ready) проб

## Условие

Настрой **health checks**: Kubernetes liveness probe (`/healthz` — HTTP 200, сервис жив), readiness probe (`/ready` — сервис готов принимать трафик, например БД подключена). Разные endpoint'ы!

## Теория

Принципиальная разница между Liveness и Readiness в Kubernetes:
- **Liveness Probe (`/healthz`):**
  - Вопрос оркестратора: «Процесс сервиса жив (нет дедлока в памяти)?»
  - Если возвращает ошибку \(\to\) Kubernetes **убивает под и перезапускает его (`SIGKILL`)**.
  - Проверка должна быть сверхлегкой (не должна трогать внешнюю БД!).
- **Readiness Probe (`/ready`):**
  - Вопрос оркестратора: «Сервис готов прямо сейчас обрабатывать клиентский трафик?»
  - Проверяет доступность PostgreSQL, прогрев кэша Redis, подключение к Kafka.
  - Если возвращает ошибку \(\to\) Kubernetes **НЕ убивает под**, а временно **исключает его IP из эндпоинтов Service**, предотвращая ошибки у пользователей.

## Решение по шагам

1. Создайте хэндлер `/healthz` для Liveness.
2. Создайте хэндлер `/ready` с проверкой подключения к БД.
3. Проверьте изоляцию логики проб.
4. Протестируйте поведение при временном отключении БД.

## Код решения

**`k8s_probes_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"testing"
)

type ProbeServer struct {
	dbConnected int32 // 1 - подключена, 0 - сбой
}

func (s *ProbeServer) LivenessHandler(w http.ResponseWriter, r *http.Request) {
	// Liveness: только проверка живости рантайма Go (HTTP 200)
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("OK"))
}

func (s *ProbeServer) ReadinessHandler(w http.ResponseWriter, r *http.Request) {
	// Readiness: глубокая проверка зависимостей (PostgreSQL)
	if atomic.LoadInt32(&s.dbConnected) == 1 {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	} else {
		w.WriteHeader(http.StatusServiceUnavailable)
		_, _ = w.Write([]byte("DB_UNAVAILABLE"))
	}
}

func TestK8sProbes(t *testing.T) {
	server := &ProbeServer{}
	atomic.StoreInt32(&server.dbConnected, 0) // БД временно упала

	// 1. Проверяем Liveness: сервис жив, перезапускать под НЕЛЬЗЯ!
	recLive := httptest.NewRecorder()
	server.LivenessHandler(recLive, httptest.NewRequest("GET", "/healthz", nil))
	if recLive.Code != http.StatusOK {
		t.Fatalf("Liveness не должен падать при сбое БД: %d", recLive.Code)
	}

	// 2. Проверяем Readiness: сервис временно не готов к трафику
	recReady := httptest.NewRecorder()
	server.ReadinessHandler(recReady, httptest.NewRequest("GET", "/ready", nil))
	if recReady.Code != http.StatusServiceUnavailable {
		t.Fatalf("Readiness должен вернуть 503 при сбое БД: %d", recReady.Code)
	}

	fmt.Println("Liveness статус: 200 OK (под остается живым)")
	fmt.Println("Readiness статус: 503 Service Unavailable (трафик снят без перезапуска пода)")
}
```

ℹ️ Раздельная архитектура Liveness и Readiness проб для Kubernetes

**`Терминал`**

```bash
go test -v k8s_probes_test.go
# Вывод:
# === RUN   TestK8sProbes
# Liveness статус: 200 OK (под остается живым)
# Readiness статус: 503 Service Unavailable (трафик снят без перезапуска пода)
# --- PASS: TestK8sProbes (0.00s)
# PASS
```

## Под капотом

Если в Liveness пробу поместить `db.Ping()`, то при кратковременном сбое PostgreSQL все 100 подов сервиса одновременно упадут в цикличный перезапуск (`CrashLoopBackOff`), вызвав лавину соединений к базе при старте.

## Подводные камни

Делать Liveness и Readiness одним и тем же эндпоинтом: это грубейшая ошибка эксплуатации Kubernetes в HighLoad.

## На собеседовании

**Вопрос с собеседования:** «Для чего в Kubernetes 1.18+ добавлена Startup Probe?»
**Ответ:** Для медленно стартующих сервисов (тяжелый прогрев ML-модели или загрузка кэша в 60 секунд). Startup Probe отключает Liveness и Readiness до тех пор, пока сервис не подтвердит завершение инициализации, предотвращая преждевременное убийство пода оркестратором по таймауту liveness.
