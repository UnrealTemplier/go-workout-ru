# Архитектура API Gateway: маршрутизация внешнего HTTP-трафика в gRPC бэкенды

## Условие

Реализуй **API Gateway**: HTTP-сервер на `:8080`, маршрутизирует `/users/*` → `user-service:50051`, `/orders/*` → `order-service:50052`. Используй `grpc-gateway` или ручной `httputil.ReverseProxy` + gRPC клиент.

## Теория

Шаблон шлюза API Gateway (Edge Service / North-South Traffic):
- Внешние клиенты (мобильные приложения, Web, сторонние интеграции) не должны знать внутренние адреса и порты подов Kubernetes.
- Функции API Gateway:
  1. Единая входная точка (порт `:8080`).
  2. Маршрутизация по префиксу URL:
     - `/api/v1/users/*` \(\to\) `user-service:50051`
     - `/api/v1/orders/*` \(\to\) `order-service:50052`
  3. Трансляция протоколов: HTTP/1.1 JSON \(\leftrightarrow\) gRPC HTTP/2 Protobuf.
  4. Централизованная аутентификация JWT и Rate Limiting.

## Решение по шагам

1. Создайте маршрутизатор `http.NewServeMux()`.
2. Настройте обработчики префиксов `/users/` и `/orders/`.
3. Реализуйте проксирование запроса в целевой микросервис.
4. Протестируйте разделение маршрутов.

## Код решения

**`api_gateway_core_test.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
)

type APIGateway struct {
	userServiceAddr  string
	orderServiceAddr string
}

func (gw *APIGateway) Routes() http.Handler {
	mux := http.NewServeMux()

	// Роутинг запросов пользователей
	mux.HandleFunc("/users/", func(w http.ResponseWriter, r *http.Request) {
		userID := strings.TrimPrefix(r.URL.Path, "/users/")
		w.Header().Set("Content-Type", "application/json")
		_, _ = fmt.Fprintf(w, `{"service":"user-service","upstream":%q,"user_id":%q}`,
			gw.userServiceAddr, userID)
	})

	// Роутинг запросов заказов
	mux.HandleFunc("/orders/", func(w http.ResponseWriter, r *http.Request) {
		orderID := strings.TrimPrefix(r.URL.Path, "/orders/")
		w.Header().Set("Content-Type", "application/json")
		_, _ = fmt.Fprintf(w, `{"service":"order-service","upstream":%q,"order_id":%q}`,
			gw.orderServiceAddr, orderID)
	})

	return mux
}

func TestAPIGatewayRouting(t *testing.T) {
	gw := &APIGateway{
		userServiceAddr:  "user-service:50051",
		orderServiceAddr: "order-service:50052",
	}

	ts := httptest.NewServer(gw.Routes())
	defer ts.Close()

	// 1. Проверка маршрутизации /users/
	respUser, err := http.Get(ts.URL + "/users/usr_77")
	if err != nil {
		t.Fatalf("Ошибка: %v", err)
	}
	defer respUser.Body.Close()
	bodyUser, _ := io.ReadAll(respUser.Body)
	fmt.Println("Gateway Response User: ", string(bodyUser))

	// 2. Проверка маршрутизации /orders/
	respOrder, err := http.Get(ts.URL + "/orders/ord_99")
	if err != nil {
		t.Fatalf("Ошибка: %v", err)
	}
	defer respOrder.Body.Close()
	bodyOrder, _ := io.ReadAll(respOrder.Body)
	fmt.Println("Gateway Response Order:", string(bodyOrder))

	if !strings.Contains(string(bodyUser), "user-service:50051") ||
		!strings.Contains(string(bodyOrder), "order-service:50052") {
		t.Fatal("Маршрутизация выполнена некорректно")
	}
}
```

## Под капотом

Шлюз держит постоянный пул соединений (Keep-Alive TCP сокетов и HTTP/2 потоков) к внутренним микросервисам, устраняя накладные расходы на повторные TLS-рукопожатия.

## Подводные камни

Помещать сложную бизнес-логику в API Gateway: шлюз превращается в распределенный спагетти-монолит. Шлюз должен заниматься СТРОГО маршрутизацией, авторизацией и агрегацией.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие API Gateway от Ingress Controller в Kubernetes?»
**Ответ:** Ingress Controller (например Ingress NGINX) — это инфраструктурный L7-балансировщик трафика для кластера. API Gateway (BFF на Go или Envoy) реализует прикладные сценарии: валидацию специфических бизнес-токенов, параллельную агрегацию ответов нескольких сервисов (`errgroup`) и трансформацию структур DTO под нужды мобильных клиентов.
