# Паттерн CQRS: разделение моделей чтения и записи (Command Query Responsibility Segregation)

## Условие

Реализуй **CQRS** в микросервисе: `Command` (Write) — gRPC, изменяет состояние. `Query` (Read) — HTTP/GraphQL/gRPC, читает из read model (Redis/Elasticsearch). Синхронизация через events.

## Теория

Принцип CQRS (Command Query Responsibility Segregation):
- В классическом CRUD одна и та же реляционная модель используется для записи и чтения.
- При росте нагрузки сложные SQL JOIN для отображения карточки товара перегружают БД записи.
- **Архитектура CQRS:**
  1. **Write Model (Command):** gRPC сервис принимает команду `UpdateProductPrice`, валидирует бизнес-правила и пишет в нормализованную PostgreSQL.
  2. **Event Sync:** публикуется событие `ProductPriceUpdated`.
  3. **Read Model (Query):** фоновый проектор обновляет денормализованный плоский документ в Redis или Elasticsearch.
  4. Запросы чтения `GetProductDetails` обращаются строго к Redis со скоростью 0.5 мс!

## Решение по шагам

1. Создайте Write-сервис с приемом команд.
2. Создайте Read-модель в виде кэша.
3. Реализуйте проекцию события на Read-модель.
4. Протестируйте разделение операций чтения и записи.

## Код решения

**`cqrs_architecture_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

// Write Model (Нормализованная база данных)
type WriteRepository struct {
	mu       sync.Mutex
	products map[string]float64
}

// Read Model (Денормализованный плоский кэш для мгновенного чтения)
type ReadModelStore struct {
	mu    sync.RWMutex
	views map[string]string
}

type CQRSMicroservice struct {
	writeDB *WriteRepository
	readDB  *ReadModelStore
}

// Command: Изменение цены через gRPC
func (s *CQRSMicroservice) ExecutePriceUpdateCommand(ctx context.Context, id string, newPrice float64) error {
	s.writeDB.mu.Lock()
	s.writeDB.products[id] = newPrice
	s.writeDB.mu.Unlock()

	// Асинхронное обновление Read Model через событие
	s.projectToReadModel(id, newPrice)
	return nil
}

func (s *CQRSMicroservice) projectToReadModel(id string, price float64) {
	s.readDB.mu.Lock()
	defer s.readDB.mu.Unlock()
	s.readDB.views[id] = fmt.Sprintf(`{"product_id":%q,"formatted_price":"%.2f ₽","status":"IN_STOCK"}`, id, price)
}

// Query: Чтение готовой JSON-проекции
func (s *CQRSMicroservice) ExecuteGetProductQuery(ctx context.Context, id string) (string, bool) {
	s.readDB.mu.RUnlock()
	defer s.readDB.RUnlock()
	s.readDB.mu.RLock()
	val, ok := s.readDB.views[id]
	return val, ok
}

func TestCQRSFlow(t *testing.T) {
	svc := &CQRSMicroservice{
		writeDB: &WriteRepository{products: make(map[string]float64)},
		readDB:  &ReadModelStore{views: make(map[string]string)},
	}

	// 1. Выполняем Command (Запись)
	_ = svc.ExecutePriceUpdateCommand(context.Background(), "prod_macbook", 189990.00)

	// 2. Выполняем Query (Чтение из оптимизированной Read-модели)
	view, found := svc.ExecuteGetProductQuery(context.Background(), "prod_macbook")
	if !found {
		t.Fatal("Данные не найдены в Read-модели")
	}

	fmt.Printf("CQRS Query успешно вернул готовую проекцию: %s\n", view)
}
```

ℹ️ Разделение Command (Write) и Query (Read) моделей

## Под капотом

CQRS устраняет необходимость сложных SQL агрегаций на чтение: данные в Read Model хранятся ровно в том виде, в котором их ожидает клиентский интерфейс.

## Подводные камни

Ожидать строгой мгновенной согласованности (Strong Consistency): между записью Command и обновлением Read Model существует задержка репликации (Eventual Consistency lag в 5–50 мс). Фронтенд должен учитывать это при оптимистичном UI.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие CQRS от классического кэширования Cache-Aside?»
**Ответ:** При Cache-Aside кэшируется результат запроса к той же самой базе. В CQRS Read Model имеет **принципиально иную схему данных и другой движок** (например, Elasticsearch для полнотекстового поиска с фасетами, Neo4j для графов друзей или ClickHouse для аналитики), полностью изолированный от реляционной Write-базы.
