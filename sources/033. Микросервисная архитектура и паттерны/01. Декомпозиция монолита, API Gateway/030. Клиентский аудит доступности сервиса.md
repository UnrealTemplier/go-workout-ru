# Клиентский аудит доступности сервиса через grpc_health_v1 перед выполнением запроса

## Условие

Реализуйте health check: добавьте серверу реализацию `grpc_health_v1` и проверяйте его состояние из клиента перед запросами.

## Теория

Превентивная проверка готовности (Pre-flight Health Verification):
- Перед выполнением критического пакетного вызова клиент может быстро запросить статус здоровья целевого сервиса.
- Метод `healthClient.Check(ctx, &HealthCheckRequest{Service: "service_name"})`:
  - Если вернулся статус `SERVING` — выполняем запрос.
  - Если вернулся статус `NOT_SERVING` — перенаправляем запрос на резервный кластер или возвращаем понятную бизнес-ошибку.

## Решение по шагам

1. Создайте клиентский хелпер проверки статуса gRPC.
2. Проверьте реакцию на статус SERVING.
3. Проверьте реакцию на статус NOT_SERVING.
4. Продемонстрируйте безопасное принятие решений.

## Код решения

**`preflight_health_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"

	healthpb "google.golang.org/grpc/health/grpc_health_v1"
)

type MockHealthClient struct {
	status healthpb.HealthCheckResponse_ServingStatus
}

func (m *MockHealthClient) Check(ctx context.Context, in *healthpb.HealthCheckRequest, opts ...any) (*healthpb.HealthCheckResponse, error) {
	return &healthpb.HealthCheckResponse{Status: m.status}, nil
}

func SafeExecuteWithPreflight(ctx context.Context, client *MockHealthClient, action func() error) error {
	resp, err := client.Check(ctx, &healthpb.HealthCheckRequest{Service: "order-service"})
	if err != nil {
		return fmt.Errorf("health check rpc failed: %w", err)
	}

	if resp.Status != healthpb.HealthCheckResponse_SERVING {
		return fmt.Errorf("сервис не готов к обслуживанию (статус: %s)", resp.Status)
	}

	return action()
}

func TestPreflightHealthCheck(t *testing.T) {
	// 1. Сервер готов
	healthyClient := &MockHealthClient{status: healthpb.HealthCheckResponse_SERVING}
	executed := false
	err1 := SafeExecuteWithPreflight(context.Background(), healthyClient, func() error {
		executed = true
		return nil
	})
	if err1 != nil || !executed {
		t.Fatalf("Запрос должен был выполниться: %v", err1)
	}
	fmt.Println("1. Preflight Health Check: статус SERVING -> операция успешно выполнена")

	// 2. Сервер деградировал (NOT_SERVING)
	unhealthyClient := &MockHealthClient{status: healthpb.HealthCheckResponse_NOT_SERVING}
	err2 := SafeExecuteWithPreflight(context.Background(), unhealthyClient, func() error {
		t.Fatal("Операция не должна была запускаться!")
		return nil
	})
	if err2 == nil {
		t.Fatal("Ожидался отказ из-за NOT_SERVING")
	}
	fmt.Printf("2. Preflight Health Check: превентивный отказ -> %v\n", err2)
}
```

ℹ️ Превентивный аудит доступности сервера перед отправкой бизнес-запросов

## Под капотом

Встроенный балансировщик gRPC может автоматически использовать протокол Health Check при включении флага `health_checking_config` в Service Config.

## Подводные камни

Делать preflight проверку перед КАЖДЫМ обычным RPC: это удвоит количество сетевых вызовов (2x RPS) к серверу. Используйте серверный стриминг `Watch` или доверяйте автоматическому балансировщику.

## На собеседовании

**Вопрос с собеседования:** «Чем метод Watch в grpc_health_v1 эффективнее периодического Check?»
**Ответ:** Метод `Watch` открывает один долгоживущий gRPC-стрим. Сервер держит соединение открытым и шлет новый фрейм ТОЛЬКО в момент фактического изменения статуса здоровья (Zero Overhead в нормальном состоянии).
