# Очередь недоставленных сообщений Dead Letter Queue (DLQ): изоляция сбойных событий и ручной ретрай

## Условие

Реализуй **Dead Letter Queue (DLQ)**: воркер обрабатывает события из Kafka/NATS. При 3 неудачных попытках — отправляет в DLQ. Отдельный сервис анализирует DLQ, алертит, позволяет retry вручную.

### Исходная формулировка

Реализуй **Dead Letter Queue (DLQ)**: воркер обрабатывает события из Kafka/NATS. При 3 неудачных попытках — отправляет в DLQ. Отдельный сервис анализирует DLQ, алертит, позволяет retry вручную.

## Теория

Изоляция ядовитых сообщений (Dead Letter Queue / Poison Pill):
- Если сообщение содержит синтаксически битый JSON или вызывает деление на ноль (Poison Pill), воркер будет падать бесконечно, заблокировав партицию Kafka для всех последующих клиентов.
- **Паттерн DLQ:**
  1. Воркер пытается обработать сообщение с локальным повтором (3 попытки).
  2. Если все попытки исчерпаны: сообщение пересылается в специальный топик `orders-dlq`.
  3. Основная очередь продолжает работать без остановки.
  4. Сообщения из `orders-dlq` исследуются инженерами и при исправлении бага возвращаются в работу через скрипт ручного ретрая (Reprocessing).

## Решение по шагам

1. Создайте модель воркера с счетчиком попыток.
2. Реализуйте пересылку в DLQ при 3 сбоях.
3. Смоделируйте ядовитое сообщение.
4. Протестируйте изоляцию и ручной перезапуск.

## Код решения

**`dead_letter_queue_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type EventMessage struct {
	ID       string
	Payload  string
	Attempts int
}

type EventProcessor struct {
	mu           sync.Mutex
	mainQueue    []*EventMessage
	dlqQueue     []*EventMessage
	processed    []string
	maxRetries   int
}

func NewProcessor(maxRetries int) *EventProcessor {
	return &EventProcessor{maxRetries: maxRetries}
}

func (p *EventProcessor) Process(msg *EventMessage, handler func(string) error) {
	p.mu.Lock()
	defer p.mu.Unlock()

	for {
		msg.Attempts++
		err := handler(msg.Payload)
		if err == nil {
			p.processed = append(p.processed, msg.ID)
			fmt.Printf("  [Main Queue] Сообщение %s успешно обработано!\n", msg.ID)
			return
		}

		fmt.Printf("  [Fail Attempt %d] Сообщение %s: %v\n", msg.Attempts, msg.ID, err)
		if msg.Attempts >= p.maxRetries {
			// Перемещение в Dead Letter Queue
			p.dlqQueue = append(p.dlqQueue, msg)
			fmt.Printf("  >>> [DLQ ROUTE] Сообщение %s отправлено в Dead Letter Queue!\n", msg.ID)
			return
		}
	}
}

func TestDeadLetterQueueRouting(t *testing.T) {
	p := NewProcessor(3)

	poisonPill := &EventMessage{ID: "msg_corrupted_13", Payload: "INVALID_JSON_NULL_POINTER"}

	// Обработчик всегда падает на битых данных
	failingHandler := func(payload string) error {
		return fmt.Errorf("критическая ошибка десериализации")
	}

	p.Process(poisonPill, failingHandler)

	if len(p.dlqQueue) != 1 || p.dlqQueue[0].ID != "msg_corrupted_13" {
		t.Fatalf("Сообщение должно было оказаться в DLQ")
	}

	fmt.Printf("Паттерн DLQ успешно защитил пайплайн обработки от зависания!\n")
}
```

## Под капотом

В заголовки Kafka/RabbitMQ сообщений в DLQ добавляются метаданные: `x-death-reason`, `x-original-topic`, `x-death-timestamp`, позволяющие инженеру понять точную причину отправки в морг без дебага исходного кода.

## Подводные камни

Забывать настраивать мониторинг и алерты на размер DLQ: если в DLQ скопится миллион сообщений, они займут всё дисковое пространство брокера.

## На собеседовании

**Вопрос с собеседования:** «Как безопасно переобработать сообщения из DLQ (Reprocessing)?»
**Ответ:** После деплоя фикса бага в коде запускается DLQ Redrive Worker. Он вычитывает сообщения из топика `orders-dlq`, валидирует их исправленным парсером и публикует обратно в исходный топик `orders` с флагом `x-retried-from-dlq=true`.
