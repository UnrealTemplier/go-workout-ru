# Официальный gRPC Health Check: регистрация grpc_health_v1 и опрос клиентом через Check

## Условие

**Стандартный протокол Health Check**: Микросервисы должны уметь сообщать оркестратору (например, Kubernetes) о своем здоровье. Реализуйте в вашем gRPC-сервисе официальный протокол здоровья gRPC, используя стандартный пакет `google.golang.org/grpc/health` и его методы. Напишите клиент, который опрашивает этот сервис.

## Теория

Протокол gRPC Health Checking Protocol (v1):
- Пакет `google.golang.org/grpc/health` реализует интерфейс `grpc_health_v1`:
  - `Check(ctx, &HealthCheckRequest{Service: ""})` \(\to\) возвращает `SERVING` или `NOT_SERVING`.
  - `Watch(req, stream)` \(\to\) серверный стрим мгновенного оповещения о смене статуса.
- Балансировщики нагрузки (Kubernetes kubelet, Envoy) опрашивают этот сервис для определения работоспособности пода.

## Решение по шагам

1. Создайте `healthServer := health.NewServer()`.
2. Зарегистрируйте через `grpc_health_v1.RegisterHealthServer`.
3. Запустите сервер на In-Memory буфере.
4. Напишите gRPC клиента и проверьте ответ метода `Check`.

## Код решения

**`grpc_health_client_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"net"
	"testing"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/health"
	healthpb "google.golang.org/grpc/health/grpc_health_v1"
	"google.golang.org/grpc/test/bufconn"
)

func TestGRPCHealthCheckClient(t *testing.T) {
	lis := bufconn.Listen(1024 * 1024)
	defer lis.Close()

	server := grpc.NewServer()

	// 1. Регистрация официального Health Server
	healthServer := health.NewServer()
	healthpb.RegisterHealthServer(server, healthServer)

	// Устанавливаем статус готовности
	healthServer.SetServingStatus("order.v1.OrderService", healthpb.HealthCheckResponse_SERVING)

	go func() {
		_ = server.Serve(lis)
	}()
	defer server.Stop()

	// 2. Создание gRPC клиента
	conn, err := grpc.NewClient(
		"passthrough://bufnet",
		grpc.WithContextDialer(func(ctx context.Context, s string) (net.Conn, error) {
			return lis.Dial()
		}),
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		t.Fatalf("Ошибка подключения: %v", err)
	}
	defer conn.Close()

	healthClient := healthpb.NewHealthClient(conn)

	// 3. Вызов метода Check
	resp, err := healthClient.Check(context.Background(), &healthpb.HealthCheckRequest{
		Service: "order.v1.OrderService",
	})
	if err != nil {
		t.Fatalf("Ошибка вызова Check: %v", err)
	}

	if resp.Status != healthpb.HealthCheckResponse_SERVING {
		t.Fatalf("Ожидался статус SERVING, получено: %v", resp.Status)
	}

	fmt.Printf("Health Check успешно подтвержден: сервис order.v1.OrderService имеет статус %s!\n", resp.Status)
}
```

## Под капотом

Метод `Check` потокобезопасен: `health.Server` хранит статусы сервисов в `sync.RWMutex`-защищенной карте, отвечая за доли микросекунды.

## Подводные камни

Возвращать ошибку gRPC вместо статуса `NOT_SERVING`: если сервис деградировал (например, отвалилась реплика БД), правильный протокол — вернуть `resp.Status = NOT_SERVING` без ошибки RPC.

## На собеседовании

**Вопрос с собеседования:** «Как в Kubernetes 1.24+ настроить нативную проверку gRPC health check без сторонних бинарников?»
**Ответ:** Использовать нативную директиву `grpc` в спецификации контейнера:
```yaml
livenessProbe:
  grpc:
    port: 50051
    service: "order.v1.OrderService"
  initialDelaySeconds: 5
  periodSeconds: 10
```
Kubelet сам открывает gRPC соединение и вызывает метод `Check` без необходимости установки curl или bash в образ контейнера.
