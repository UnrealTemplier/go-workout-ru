# Динамическая адаптация топологии: фоновый Watcher изменений реестра Consul/etcd

## Условие

Интегрируйте Consul или etcd (можно в Docker) для динамического обнаружения сервисов. Клиент подписывается на изменения и обновляет список адресов.

## Теория

Реактивное обновление топологии сервисов (Dynamic Topology Updates):
- Опрос реестра раз в \(N\) секунд (Polling) создает задержку обнаружения аварий.
- Реактивный подход:
  - Клиент открывает долгоживущий gRPC-стрим или Long Polling к etcd/Consul:
    `watchChan := etcdClient.Watch(ctx, "/services/orders/", clientv3.WithPrefix())`
  - При добавлении (`PUT`) или падении (`DELETE`) пода etcd мгновенно пушит событие в `watchChan`.
  - gRPC балансировщик на лету обновляет адреса без разрыва существующих соединений.

## Решение по шагам

1. Создайте структуру реактивного наблюдателя топологии.
2. Реализуйте канал получения событий изменения адресов.
3. Протестируйте динамическое добавление и удаление подов.
4. Убедитесь в синхронизации локального адресного пула.

## Код решения

**`dynamic_topology_watcher_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type TopologyEvent struct {
	Type    string // "ADD" или "REMOVE"
	Address string
}

type DynamicAddressPool struct {
	mu      sync.RWMutex
	pool    map[string]bool
	updates chan TopologyEvent
}

func NewDynamicPool() *DynamicAddressPool {
	return &DynamicAddressPool{
		pool:    make(map[string]bool),
		updates: make(chan TopologyEvent, 10),
	}
}

func (p *DynamicAddressPool) StartWatcher(ctx context.Context) {
	go func() {
		for {
			select {
			case <-ctx.Done():
				return
			case evt := <-p.updates:
				p.mu.Lock()
				if evt.Type == "ADD" {
					p.pool[evt.Address] = true
					fmt.Printf("  [Topology Event] Добавлен новый под: %s\n", evt.Address)
				} else if evt.Type == "REMOVE" {
					delete(p.pool, evt.Address)
					fmt.Printf("  [Topology Event] Удален сбойный под: %s\n", evt.Address)
				}
				p.mu.Unlock()
			}
		}
	}()
}

func (p *DynamicAddressPool) GetLiveAddresses() []string {
	p.mu.RLock()
	defer p.mu.RUnlock()
	var list []string
	for addr := range p.pool {
		list = append(list, addr)
	}
	return list
}

func TestDynamicWatcher(t *testing.T) {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	pool := NewDynamicPool()
	pool.StartWatcher(ctx)

	// Динамическое добавление двух подов из etcd
	pool.updates <- TopologyEvent{Type: "ADD", Address: "10.0.1.10:50051"}
	pool.updates <- TopologyEvent{Type: "ADD", Address: "10.0.1.11:50051"}
	time.Sleep(20 * time.Millisecond)

	if len(pool.GetLiveAddresses()) != 2 {
		t.Fatalf("Ожидалось 2 адреса")
	}

	// Динамическое удаление упавшего пода
	pool.updates <- TopologyEvent{Type: "REMOVE", Address: "10.0.1.10:50051"}
	time.Sleep(20 * time.Millisecond)

	live := pool.GetLiveAddresses()
	if len(live) != 1 || live[0] != "10.0.1.11:50051" {
		t.Fatalf("Некорректный остаток подов: %v", live)
	}

	fmt.Println("Клиентский пул топологии успешно синхронизирован в реальном времени!")
}
```

## Под капотом

В etcd протокол Watch использует HTTP/2 бинарный стриминг: сервер шлет дельты ревизий (Revisions) без накладных расходов на постоянные TCP-рукопожатия.

## Подводные камни

Игнорировать номер ревизии etcd при обрыве связи: если сокет переподключился, клиент обязан возобновить Watch с последней подтвержденной ревизии (`WithRev`), иначе события за время разрыва связи будут утеряны.

## На собеседовании

**Вопрос с собеседования:** «Как в gRPC реализовать кастомный resolver на базе etcd?»
**Ответ:** Реализовать интерфейсы `resolver.Builder` и `resolver.Resolver` из пакета `google.golang.org/grpc/resolver`. Метод `Build` подписывается на etcd watch, а при получении новых IP вызывает `clientConn.UpdateState(resolver.State{Addresses: newAddrs})`, заставляя gRPC прозрачно обновить пул соединений.
