# Шина событий на gRPC Streaming: реализация распределенного Pub/Sub без внешнего брокера

## Условие

**Event-Driven Architecture**: Используйте gRPC streaming для публикации событий из одного сервиса и подписки в других (Pub/Sub паттерн).

## Теория

Паттерн Pub/Sub на базе gRPC Server Streaming:
- Метод `.proto`:
  `rpc SubscribeEvents (SubscribeRequest) returns (stream EventResponse);`
- Клиент (подписчик) вызывает метод и держит открытым долгоживущий gRPC-стрим.
- Сервер хранит список активных потоков `grpc.ServerStream`.
- При поступлении нового события сервер транслирует его всем подписчикам через `stream.SendMsg()`.
- Идеально подходит для внутренних легковесных шин событий без развертывания тяжелых кластеров Kafka.

## Решение по шагам

1. Создайте структуру Event Bus с реестром стримов.
2. Реализуйте регистрацию подписчиков.
3. Реализуйте метод Broadcast отправки событий.
4. Протестируйте получение событий подписчиками.

## Код решения

**`grpc_streaming_pubsub_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type EventBusHub struct {
	mu          sync.RWMutex
	subscribers map[string]chan string
}

func NewEventHub() *EventBusHub {
	return &EventBusHub{
		subscribers: make(map[string]chan string),
	}
}

func (h *EventBusHub) Subscribe(subID string) <-chan string {
	h.mu.Lock()
	defer h.mu.Unlock()
	ch := make(chan string, 10)
	h.subscribers[subID] = ch
	return ch
}

func (h *EventBusHub) Unsubscribe(subID string) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if ch, ok := h.subscribers[subID]; ok {
		close(ch)
		delete(h.subscribers, subID)
	}
}

func (h *EventBusHub) Broadcast(msg string) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	for _, ch := range h.subscribers {
		select {
		case ch <- msg:
		default:
			// Защита от медленных подписчиков (Slow Consumer Protection)
		}
	}
}

func TestGRPCStreamingPubSub(t *testing.T) {
	hub := NewEventHub()

	// 2 подписчика (сервис уведомлений и сервис аналитики)
	subNotifications := hub.Subscribe("notification-service")
	subAnalytics := hub.Subscribe("analytics-service")
	defer hub.Unsubscribe("notification-service")
	defer hub.Unsubscribe("analytics-service")

	// Публикация события
	hub.Broadcast("EVENT_ORDER_PAID_42")

	msg1 := <-subNotifications
	msg2 := <-subAnalytics

	if msg1 != "EVENT_ORDER_PAID_42" || msg2 != "EVENT_ORDER_PAID_42" {
		t.Fatalf("События не получены: %s, %s", msg1, msg2)
	}

	fmt.Println("gRPC Streaming Event Bus успешно доставил широковещательное событие обоим подписчикам:")
	fmt.Printf("  • Notification Service: %s\n", msg1)
	fmt.Printf("  • Analytics Service:    %s\n", msg2)
}
```

## Под капотом

В gRPC streaming каждый вызов `Send` формирует HTTP/2 DATA фрейм. Мультиплексирование позволяет передавать тысячи сообщений по одному сокету без задержек на повторные рукопожатия.

## Подводные камни

Медленный подписчик (Slow Consumer): если один из клиентов читает медленно, его буфер сокета переполнится, и HTTP/2 Flow Control заблокирует отправку. Всегда используйте неблокирующую отправку через `select default` или буферизацию.

## На собеседовании

**Вопрос с собеседования:** «Когда стриминг на gRPC лучше Kafka, а когда хуже?»
**Ответ:** gRPC Streaming идеален для задач реального времени между несколькими известными сервисами с минимальной задержкой (Sub-millisecond Real-Time), не требуя инфраструктуры Kafka. Однако gRPC не персистит сообщения на диск: если подписчик был оффлайн, он не сможет «перемотать» историю (Offset Replay), для чего и необходима Kafka.
