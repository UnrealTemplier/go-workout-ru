# Канареечный релиз Canary Deployment с Istio и Flagger: автоматический промоут и Rollback по метрикам

## Условие

Реализуй **"Canary Deployment"**:
- Istio/Flagger: 5% трафика на v2, 95% на v1
- Мониторинг error rate, latency на v2
- Автоматическое увеличение до 50%, затем 100% при успехе
- Автоматический rollback при degradation

## Теория

Прогрессивный канареечный релиз (Progressive Delivery / Flagger):
- Манифест Flagger `Canary`:
  - `stepWeight: 5` (увеличение доли трафика на 5% каждые 60 секунд).
  - `maxWeight: 50` (проверка до 50% перед финальным переключением).
  - Метрики проверки качества:
    - **Success Rate:** процент успешных HTTP 200 / gRPC OK \(\ge 99\%\).
    - **Latency P99:** время ответа \(\le 250\) мс.
  - Если на этапе 15% зафиксирован всплеск 500 ошибок, Flagger автоматически откатывает трафик на v1 за 2 секунды (Zero User Impact).

## Решение по шагам

1. Опишите манифест Flagger Canary.
2. Задайте метрики анализа Prometheus.
3. Смоделируйте этапы продвижения трафика (5% -> 20% -> 50% -> 100%).
4. Продемонстрируйте механизм автоматического отката.

## Код решения

**`flagger_canary.yaml`**

```yaml
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: order-service
  namespace: production
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  service:
    port: 50051
    name: order-service
  analysis:
    interval: 1m
    threshold: 3 # Максимум 3 неудачных проверки до отката
    maxWeight: 50
    stepWeight: 5
    metrics:
    - name: request-success-rate
      thresholdRange:
        min: 99 # Минимум 99% успешных вызовов
      interval: 1m
    - name: request-duration
      thresholdRange:
        max: 250 # Максимум 250 мс задержка
      interval: 1m
```

ℹ️ Декларативная спецификация прогрессивного релиза Flagger

**`Терминал`**

```bash
# Мониторинг прогресса канареечного релиза в реальном времени:
kubectl describe canary order-service -n production

# Вывод событий контроллера:
# Normal  Synced  Starting canary analysis for order-service.production
# Normal  Synced  Advance order-service-canary weight 5%
# Normal  Synced  Advance order-service-canary weight 10%
# Warning Synced  Halt advancement: request-success-rate 97.4% < 99%
# Warning Synced  Rolling back order-service: traffic reverted to primary (100% v1)
# Normal  Synced  Canary rollback completed successfully!
```

## Под капотом

Flagger автоматически генерирует и обновляет Istio `VirtualService` манифесты, меняя веса `weight: 95` и `weight: 5` по результатам выполнения PromQL запросов к серверу Prometheus.

## Подводные камни

Проводить канареечный тест при околонулевом трафике (например глубокой ночью): пара тестовых ошибок составит 50% Error Rate и вызовет ложный откат. Flagger требует настройки минимального порога запросов (например > 100 RPS).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Blue-Green Deployment от Canary Deployment?»
**Ответ:** В Blue-Green развертываются 2 полных окружения, и трафик переключается **мгновенно на 100%** с Blue на Green. Если в новой версии есть скрытый баг, с ним столкнутся 100% пользователей. В Canary трафик переводится **плавно по процентам** (1% -> 5% -> 25%), минимизируя радиус поражения (Blast Radius) в случае сбоя.
