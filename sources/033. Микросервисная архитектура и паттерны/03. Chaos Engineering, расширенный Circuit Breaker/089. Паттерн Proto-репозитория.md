# Паттерн Proto-репозитория: единый источник правды контрактов API и версионирование общего Go-модуля

## Условие

**Организация общего репозитория контрактов**: При работе с микросервисами держать файлы `.proto` внутри каждого сервиса неудобно. Реализуйте паттерн "Proto-репозиторий": создайте изолированный Go-модуль, содержащий только файлы `.proto` и сгенерированный Go-код. Опубликуйте его на GitHub или подключите локально в `go.mod` ваших микросервисов `APIGateway` и `UserService` в качестве общей разделяемой зависимости.

## Теория

Паттерн централизованного репозитория схем (Schema Repository / Contracts Module):
- **Проблема разрозненных схем:**
  - Если `order.proto` лежит в `order-service`, а `user.proto` в `user-service`, клиентские сервисы вынуждены копипастить `.proto` файлы вручную. Копии неизбежно рассинхронизируются.
- **Решение: Централизованный репозиторий схем:**
  - Создается отдельный Git-репозиторий: `github.com/company/proto-contracts`.
  - Структура каталогов:
    ```text
    proto-contracts/
    ├── api/
    │   ├── user/v1/user.proto
    │   └── order/v1/order.proto
    ├── gen/go/
    │   ├── user/v1/user.pb.go
    │   └── order/v1/order.pb.go
    └── go.mod
    ```
  - CI пайплайн автоматически компилирует Go-пакеты и тегирует семантические релизы (`v1.2.0`).
  - Микросервисы подключают сгенерированный код через обычный `go get github.com/company/proto-contracts@v1.2.0`.

## Решение по шагам

1. Создайте `go.mod` для общего репозитория контрактов.
2. Настройте директиву `replace` в `go.mod` микросервисов для локальной разработки.
3. Продемонстрируйте импорт сгенерированных пакетов.
4. Проверьте изоляцию версий.

**`contracts_module_import_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ContractMetadata struct {
	ModulePath string
	Version    string
	Services   []string
}

func GetContractsRegistry() ContractMetadata {
	return ContractMetadata{
		ModulePath: "github.com/company/proto-contracts",
		Version:    "v1.2.0",
		Services:   []string{"user.v1.UserService", "order.v1.OrderService"},
	}
}

func TestContractsModule(t *testing.T) {
	meta := GetContractsRegistry()

	if meta.Version != "v1.2.0" || len(meta.Services) != 2 {
		t.Fatalf("Некорректный реестр: %+v", meta)
	}

	fmt.Println("Централизованный модуль контрактов успешно подключен:")
	fmt.Printf("  • Модуль:    %s\n", meta.ModulePath)
	fmt.Printf("  • Версия:    %s (SemVer)\n", meta.Version)
	fmt.Printf("  • Контракты: %v\n", meta.Services)
}
```

## Под капотом

Использование общего репозитория контрактов гарантирует строгую обратную совместимость (Backward Compatibility): компилятор Go не позволит собрать проект, если сигнатура метода или тип поля изменились без ведома зависимых сервисов.

## Подводные камни

Публиковать в репозиторий контрактов тяжелые сторонние зависимости или бизнес-логику: репозиторий контрактов должен содержать СТРОГО `.proto` схемы и сгенерированные файлы `*.pb.go`.

## На собеседовании

**Вопрос с собеседования:** «Что такое Buf Schema Registry (BSR) и как он заменяет Git-репозиторий контрактов?»
**Ответ:** BSR (Buf Schema Registry) — это облачный или on-premise реестр схем Protobuf (аналог npm или Docker Hub). Разработчики пушат только `.proto` файлы (`buf push`), а BSR на лету компилирует и отдает готовые пакеты для Go (`go get buf.build/gen/go/company/apis`), Python, TypeScript и Java без необходимости хранения сгенерированного кода в Git.
