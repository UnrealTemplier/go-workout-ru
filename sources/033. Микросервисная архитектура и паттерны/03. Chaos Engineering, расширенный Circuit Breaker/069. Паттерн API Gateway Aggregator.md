# Паттерн API Gateway Aggregator: параллельная агрегация данных нескольких сервисов через errgroup

## Условие

**API Gateway**: Создайте отдельный сервис-шлюз, который агрегирует данные из нескольких gRPC-сервисов и отдает их клиенту через REST/gRPC.

## Теория

Паттерн шлюза-агрегатора (API Gateway Aggregation / Scatter-Gather):
- Мобильному приложению для экрана «Личный кабинет» нужны:
  1. Данные профиля (`UserService.GetProfile`) — 30 мс.
  2. Список последних заказов (`OrderService.GetOrders`) — 40 мс.
  3. Баланс бонусов (`LoyaltyService.GetBalance`) — 25 мс.
- Последовательный опрос занял бы \(30 + 40 + 25 = 95\) мс.
- Параллельная агрегация через `golang.org/x/sync/errgroup`:
  - Все 3 вызова запускаются в параллельных горутинах.
  - Общее время ответа равно времени самого медленного сервиса: \(\max(30, 40, 25) = 40\) мс!

## Решение по шагам

1. Создайте структуру агрегированного ответа DTO.
2. Используйте `errgroup.WithContext(ctx)` для параллельного сбора.
3. Запустите одновременные вызовы к сервисам.
4. Протестируйте ускорение и корректность сборки данных.

## Код решения

**`gateway_aggregator_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"

	"golang.org/x/sync/errgroup"
)

type DashboardData struct {
	UserName string
	Orders   []string
	Bonuses  int
}

func FetchUserProfile(ctx context.Context) (string, error) {
	time.Sleep(30 * time.Millisecond)
	return "Мария Смирнова", nil
}

func FetchUserOrders(ctx context.Context) ([]string, error) {
	time.Sleep(40 * time.Millisecond)
	return []string{"ord_101", "ord_102"}, nil
}

func FetchUserBonuses(ctx context.Context) (int, error) {
	time.Sleep(25 * time.Millisecond)
	return 1500, nil
}

func AggregateDashboard(ctx context.Context) (*DashboardData, error) {
	g, gCtx := errgroup.WithContext(ctx)

	var (
		mu       sync.Mutex
		dashData DashboardData
	)

	g.Go(func() error {
		name, err := FetchUserProfile(gCtx)
		if err != nil {
			return err
		}
		mu.Lock()
		dashData.UserName = name
		mu.Unlock()
		return nil
	})

	g.Go(func() error {
		orders, err := FetchUserOrders(gCtx)
		if err != nil {
			return err
		}
		mu.Lock()
		dashData.Orders = orders
		mu.Unlock()
		return nil
	})

	g.Go(func() error {
		pts, err := FetchUserBonuses(gCtx)
		if err != nil {
			return err
		}
		mu.Lock()
		dashData.Bonuses = pts
		mu.Unlock()
		return nil
	})

	if err := g.Wait(); err != nil {
		return nil, err
	}

	return &dashData, nil
}

func TestGatewayAggregatorPerformance(t *testing.T) {
	start := time.Now()
	data, err := AggregateDashboard(context.Background())
	elapsed := time.Since(start)

	if err != nil {
		t.Fatalf("Ошибка агрегации: %v", err)
	}

	if data.UserName != "Мария Смирнова" || len(data.Orders) != 2 || data.Bonuses != 1500 {
		t.Fatalf("Некорректно собраны данные: %+v", data)
	}

	fmt.Printf("Агрегация успешно завершена за %v (параллельное ускорение!):\n", elapsed.Round(time.Millisecond))
	fmt.Printf("  • Пользователь: %s\n", data.UserName)
	fmt.Printf("  • Заказы:       %v\n", data.Orders)
	fmt.Printf("  • Бонусы:       %d баллов\n", data.Bonuses)

	if elapsed > 65*time.Millisecond {
		t.Fatalf("Агрегация выполнилась последовательно вместо параллельной: %v", elapsed)
	}
}
```

ℹ️ Параллельная агрегация данных из нескольких микросервисов через errgroup

## Под капотом

`errgroup.WithContext` автоматически отменяет дочерний контекст `gCtx`, если хотя бы одна из горутин возвращает ошибку. Это предотвращает бесполезную работу остальных горутин.

## Подводные камни

Модифицировать общую структуру `DashboardData` из параллельных горутин без мьютекса: это приведет к гонке данных (Data Race), детектируемой флагом `go test -race`.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если второстепенный сервис (например, бонусы) упал при агрегации?»
**Ответ:** Не проваливать весь дашборд! Вызовы второстепенных сервисов оборачивают в мягкий обработчик, игнорирующий ошибку и возвращающий `nil / 0 баллов`. Только критические ошибки (например, профиль пользователя не найден) должны приводить к падению общего запроса.
