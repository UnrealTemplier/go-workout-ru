# CQRS разделение моделей: Write-сервис для команд и оптимизированный Read-сервис для запросов

## Условие

**CQRS (Command Query Responsibility Segregation)**: Разделите сервисы на "write" (gRPC для команд) и "read" (gRPC для запросов) с разными моделями данных.

## Теория

Принцип CQRS на уровне микросервисов:
- **OrderWriteService (Command):**
  - Принимает `CreateOrder`, `CancelOrder`.
  - Валидирует инварианты предметной области.
  - Пишет в нормализованную транзакционную PostgreSQL (3NF).
  - Публикует событие `OrderUpdated` в Kafka.
- **OrderReadService (Query):**
  - Подписан на Kafka и собирает денормализованную проекцию заказа со всеми данными пользователя и товаров в один документ.
  - Сохраняет в Redis / ClickHouse.
  - Принимает `GetOrderSummary` и отдает готовый JSON за 0.8 мс без единого SQL JOIN!

## Решение по шагам

1. Создайте Write-модель сущности.
2. Создайте плоскую Read-модель документа.
3. Реализуйте асинхронную синхронизацию.
4. Протестируйте разделение обязанностей.

## Код решения

**`cqrs_microservice_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

// Write Model (Нормализованная)
type OrderCommandDB struct {
	mu     sync.Mutex
	orders map[string]float64
}

// Read Model (Денормализованная для мгновенного чтения)
type OrderQueryViewStore struct {
	mu    sync.RWMutex
	views map[string]string
}

type OrderWriteService struct {
	db       *OrderCommandDB
	syncChan chan<- string
}

func (s *OrderWriteService) PlaceOrder(id string, amount float64) {
	s.db.mu.Lock()
	s.db.orders[id] = amount
	s.db.mu.Unlock()

	// Асинхронная публикация события обновления
	s.syncChan <- id
}

type OrderReadService struct {
	views *OrderQueryViewStore
}

func (s *OrderReadService) GetOrderView(id string) string {
	s.views.mu.RLock()
	defer s.views.mu.RUnlock()
	return s.views.views[id]
}

func TestCQRSMicroserviceSeparation(t *testing.T) {
	syncCh := make(chan string, 5)
	writeDB := &OrderCommandDB{orders: make(map[string]float64)}
	readViews := &OrderQueryViewStore{views: make(map[string]string)}

	writeSvc := &OrderWriteService{db: writeDB, syncChan: syncCh}
	readSvc := &OrderReadService{views: readViews}

	// Фоновый проектор синхронизации
	go func() {
		for orderID := range syncCh {
			writeDB.mu.Lock()
			amt := writeDB.orders[orderID]
			writeDB.mu.Unlock()

			// Формирование денормализованной проекции
			readViews.mu.Lock()
			readViews.views[orderID] = fmt.Sprintf(`{"order_id":%q,"total":"%.2f ₽","status":"CONFIRMED"}`, orderID, amt)
			readViews.mu.Unlock()
		}
	}()

	// 1. Команда записи
	writeSvc.PlaceOrder("ord_999", 7490.00)

	// Даем 10 мс на проекцию
	var view string
	for i := 0; i < 10; i++ {
		view = readSvc.GetOrderView("ord_999")
		if view != "" {
			break
		}
	}

	if view == "" {
		t.Fatal("Read-модель не получила проекцию")
	}

	fmt.Printf("CQRS: Read-сервис вернул денормализованную карточку:\n  %s\n", view)
}
```

ℹ️ Разделение моделей записи и чтения в микросервисной архитектуре

## Под капотом

Read-сервис можно масштабировать горизонтально до 50 подов независимо от Write-сервиса, так как операции чтения в интернет-магазинах обычно составляют 95–99% всего трафика.

## Подводные камни

Использовать CQRS для простых CRUD систем без сложной предметной области: это неоправданно усложнит архитектуру, добавив задержку Eventual Consistency.

## На собеседовании

**Вопрос с собеседования:** «Как бороться с Eventual Consistency лагом в CQRS на фронтенде?»
**Ответ:** 1. **Optimistic UI:** фронтенд сразу показывает созданный заказ в интерфейсе, не дожидаясь ответа Read-модели. 2. Возвращать ID и базовые поля в ответе на саму команду Write. 3. Использовать WebSocket/SSE подписку на обновления Read-модели.
