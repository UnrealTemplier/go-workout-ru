# Паттерн Saga: многошаговая цепочка вызовов gRPC с компенсирующими транзакциями

## Условие

**Saga Pattern**: Реализуйте распределенную транзакцию через цепочку gRPC-вызовов с компенсирующими действиями при ошибке.

## Теория

Распределенная транзакция заказа (Saga Pattern Chain):
- Цепочка прямых вызовов (Forward Steps):
  1. `InventoryService.ReserveItems()`
  2. `PaymentService.Charge()`
  3. `DeliveryService.CreateShipment()`
- Если `DeliveryService` возвращает ошибку `codes.Unavailable`:
  - Координатор саги последовательно вызывает компенсирующие транзакции (Compensations):
    1. `PaymentService.Refund()`
    2. `InventoryService.ReleaseItems()`
- Согласованность данных восстанавливается (Eventual Consistency).

## Решение по шагам

1. Создайте интерфейс прямого шага и компенсации.
2. Смоделируйте ошибку на 3-м шаге доставки.
3. Проверьте выполнение компенсаций в обратном LIFO порядке.
4. Продемонстрируйте чистоту отката.

## Код решения

**`grpc_saga_chain_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type Step struct {
	Name       string
	Execute    func() error
	Compensate func() error
}

func ExecuteSagaChain(steps []Step) error {
	var executed []Step

	for _, step := range steps {
		fmt.Printf("  [Saga Forward] Выполняем шаг: %s\n", step.Name)
		if err := step.Execute(); err != nil {
			fmt.Printf("  [Saga ERROR] Сбой на шаге %s: %v! Запускаем откат...\n", step.Name, err)
			// LIFO Компенсация
			for i := len(executed) - 1; i >= 0; i-- {
				fmt.Printf("  [Saga Rollback] Компенсируем: %s\n", executed[i].Name)
				_ = executed[i].Compensate()
			}
			return err
		}
		executed = append(executed, step)
	}
	return nil
}

func TestSagaChainRollback(t *testing.T) {
	inventoryRefunded := false
	paymentRefunded := false

	steps := []Step{
		{
			Name: "ReserveInventory",
			Execute: func() error { return nil },
			Compensate: func() error {
				inventoryRefunded = true
				return nil
			},
		},
		{
			Name: "ProcessPayment",
			Execute: func() error { return nil },
			Compensate: func() error {
				paymentRefunded = true
				return nil
			},
		},
		{
			Name: "CreateDelivery",
			Execute: func() error {
				return fmt.Errorf("служба курьерской доставки перегружена (нет свободных курьеров)")
			},
			Compensate: func() error { return nil },
		},
	}

	err := ExecuteSagaChain(steps)
	if err == nil {
		t.Fatal("Сага должна была завершиться ошибкой")
	}

	if !inventoryRefunded || !paymentRefunded {
		t.Fatal("Не все шаги были скомпенсированы!")
	}

	fmt.Println("Сага успешно выполнила компенсирующие транзакции в обратном порядке!")
}
```

## Под капотом

Для надежности в продакшене используется Temporal.io или Cadence: рабочий процесс саги оформляется в виде Workflow, а состояние шагов персистится в Event History, выдерживая перезапуск серверов.

## Подводные камни

Забывать учитывать «грязное чтение» (Pivot Transactions): в сагах транзакции не изолированы (нет уровня Isolation из ACID). Пользователь может увидеть зарезервированный товар до того, как платеж упадет и снимет бронь.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Saga Orchestration от Saga Choreography?»
**Ответ:** При **оркестрации** есть центральный сервис-координатор (Orchestrator), знающий весь граф шагов и явно вызывающий методы участников. При **хореографии** координатора нет: сервисы слушают события друг друга в Kafka (`OrderCreated` \(\to\) Склад \(\to\) `InventoryReserved` \(\to\) Платежи). Оркестрация проще в отладке и аудите для сложных бизнес-процессов.
