# Асинхронная хореография событий: публикация UserCreated в шину событий вместо блокирующего gRPC

## Условие

**Event-Driven Architecture (База)**: Синхронные вызовы gRPC связывают сервисы. Попробуй асинхронный подход (Хореография). Напиши мок-канал (имитирующий брокер вроде Kafka). При создании юзера в `User-Service`, вместо gRPC-вызова `Email-Service`, просто отправляй событие `UserCreated` в канал. А `Email-Service` пусть слушает этот канал и шлет письма.

## Теория

Принцип асинхронной хореографии (Choreography-based Architecture):
- `User-Service` не знает о существовании `Email-Service`, `Analytics-Service` или `CRM-Service`.
- Он выполняет только свою задачу: сохраняет пользователя и публикует факт в топик Kafka:
  `kafka.Publish("users.events", UserCreatedEvent{ID: "usr_42", Email: "alex@yandex.ru"})`
- Любое количество сервисов могут независимо подписаться на этот топик:
  - `Email-Service` отправляет приветственное письмо.
  - `Analytics-Service` обновляет метрики регистраций в ClickHouse.
  - `Fraud-Service` проверяет email по черным спискам.
- Добавление нового потребителя не требует изменения ни единой строчки в `User-Service`!

## Решение по шагам

1. Создайте канал событий Kafka-топика.
2. Реализуйте метод `RegisterUser` с публикацией события.
3. Реализуйте независимого подписчика `EmailService`.
4. Протестируйте слабую связанность (Loose Coupling).

## Код решения

**`event_choreography_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type UserCreatedEvent struct {
	UserID string
	Email  string
}

type EventChannelBroker struct {
	topic chan UserCreatedEvent
}

type UserService struct {
	broker *EventChannelBroker
}

func (s *UserService) RegisterUser(id, email string) {
	fmt.Printf("1. [User-Service] Пользователь %s (%s) успешно сохранен в PostgreSQL!\n", id, email)
	// Асинхронный пуш в топик брокера
	s.broker.topic <- UserCreatedEvent{UserID: id, Email: email}
}

type EmailServiceConsumer struct {
	sentMails []string
	mu        sync.Mutex
}

func (c *EmailServiceConsumer) StartListening(broker *EventChannelBroker, done chan struct{}) {
	go func() {
		for evt := range broker.topic {
			c.mu.Lock()
			msg := fmt.Sprintf("Отправлено приветственное письмо на %s для пользователя %s", evt.Email, evt.UserID)
			c.sentMails = append(c.sentMails, msg)
			c.mu.Unlock()
			fmt.Printf("2. [Email-Service] %s\n", msg)
			close(done)
			return
		}
	}()
}

func TestEventChoreography(t *testing.T) {
	broker := &EventChannelBroker{topic: make(chan UserCreatedEvent, 5)}
	userSvc := &UserService{broker: broker}
	emailSvc := &EmailServiceConsumer{}

	done := make(chan struct{})
	emailSvc.StartListening(broker, done)

	userSvc.RegisterUser("usr_99", "alex@bigtech.ru")

	select {
	case <-done:
		fmt.Println("Асинхронная хореография успешно выполнена!")
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Таймаут ожидания отправки письма")
	}
}
```

## Под капотом

Хореография опирается на принцип OCP (Open-Closed Principle): система открыта для расширения новыми сервисами, но закрыта для модификации существующих продюсеров.

## Подводные камни

Отсутствие единого места понимания сквозного бизнес-процесса: когда 10 сервисов обмениваются 50 событиями, понять, почему заказ отменился, можно только по распределенным трейсам в Jaeger.

## На собеседовании

**Вопрос с собеседования:** «Когда выбирать хореографию, а когда оркестрацию саги?»
**Ответ:** Для простых линейных цепочек уведомлений (Регистрация \(\to\) Email/SMS/Аналитика) идеальна **хореография**. Для сложных финансовых транзакций с жесткими инвариантами и десятком компенсирующих откатов (Заказ \(\to\) Склад \(\to\) Оплата \(\to\) Доставка) выбирают **оркестрацию** на базе Temporal/Cadence.
