# Паттерн BFF (Backend for Frontend): оптимизированные шлюзы для мобильных и веб-клиентов

## Условие

**BFF (Backend for Frontend)**: Создайте отдельные gRPC-сервисы для мобильного и веб-клиентов с разными контрактами.

## Теория

Паттерн BFF (Backend for Frontend Architecture):
- Разные клиентские платформы имеют принципиально разные требования:
  - **Mobile BFF (iOS / Android):**
    - Медленный мобильный интернет 3G/LTE, ограниченный экран смартфона.
    - Нужен компактный JSON, минимальный объем полей (только картинка, название, цена), агрегированный экран в 1 сетевой запрос.
  - **Web Desktop BFF (Браузер):**
    - Широкий экран 4K, быстрый оптоволоконный интернет.
    - Нужны расширенные таблицы, детальные характеристики товара, отзывы, фильтры и аналитические графики.
- Вместо одного универсального перегруженного API создаются 2 независимых сервиса BFF, каждый из которых разрабатывается в связке с соответствующей фронтенд-командой.

## Решение по шагам

1. Создайте контракт мобильного ответа (Compact DTO).
2. Создайте контракт десктопного веб-ответа (Rich DTO).
3. Смоделируйте отдачу данных через специализированные BFF.
4. Проверьте разницу в объемах полезной нагрузки.

## Код решения

**`bff_architecture_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Mobile BFF: компактный легковесный ответ
type MobileProductDTO struct {
	ID    string  `json:"id"`
	Title string  `json:"title"`
	Price float64 `json:"price"`
}

// Web BFF: полная детальная карточка
type WebProductDTO struct {
	ID             string            `json:"id"`
	Title          string            `json:"title"`
	Price          float64           `json:"price"`
	Specs          map[string]string `json:"specs"`
	ReviewsCount   int               `json:"reviews_count"`
	AvailableSizes []string          `json:"sizes"`
}

func ServeMobileBFF(id string) MobileProductDTO {
	return MobileProductDTO{
		ID:    id,
		Title: "Кроссовки Nike Air Max",
		Price: 12990.00,
	}
}

func ServeWebBFF(id string) WebProductDTO {
	return WebProductDTO{
		ID:    id,
		Title: "Кроссовки Nike Air Max",
		Price: 12990.00,
		Specs: map[string]string{
			"Материал": "Текстиль",
			"Цвет":     "Черный",
			"Сезон":    "Демисезон",
		},
		ReviewsCount:   482,
		AvailableSizes: []string{"41", "42", "43", "44"},
	}
}

func TestBFFPayloadSeparation(t *testing.T) {
	mob := ServeMobileBFF("prod_nike_01")
	web := ServeWebBFF("prod_nike_01")

	if mob.Title != web.Title {
		t.Fatal("Базовые данные не совпадают")
	}

	fmt.Printf("1. Mobile BFF Payload: %+v (минимум трафика для смартфона)\n", mob)
	fmt.Printf("2. Web BFF Payload:    %+v (богатый интерфейс для десктопа)\n", web)
}
```

## Под капотом

BFF сервисы не содержат собственной базы данных. Они выступают тонкими оркестраторами (Smart Aggregators), транслирующими запросы во внутренние микросервисы Core Domain.

## Подводные камни

Помещать тяжелую бизнес-логику в BFF: BFF должен заниматься строго форматированием, агрегацией и маппингом данных под экран клиента. Бизнес-правила живут в Core микросервисах.

## На собеседовании

**Вопрос с собеседования:** «Кто должен владеть кодовой базой BFF сервиса — фронтенд или бэкенд команда?»
**Ответ:** По канонической методологии Sam Newman (автора книги Building Microservices), BFF принадлежит **команде конкретного клиента**: Mobile BFF разрабатывают мобильные инженеры, а Web BFF — фронтенд-инженеры. Это устраняет бюрократию согласования API между отдельными отделами.
