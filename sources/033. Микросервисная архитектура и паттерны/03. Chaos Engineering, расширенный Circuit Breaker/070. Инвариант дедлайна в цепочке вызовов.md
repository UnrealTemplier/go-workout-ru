# Инвариант дедлайна в цепочке вызовов: синхронное прерывание при зависании бэкенда

## Условие

**[Deadline Propagation]**: Входящий запрос в `OrderService` имеет `context.Context` с дедлайном (timeout 2s). `OrderService` делает вызов в `InventoryService`, передавая *тот же самый* контекст. Убедись, что если `InventoryService` подвиснет, дедлайн сработает на обоих уровнях одновременно, а не будет удваиваться.

## Теория

Математика дедлайнов (Deadline Invariant):
- Дедлайн — это **абсолютная точка во времени** (`time.Time`), а не относительная продолжительность!
  - Клиент установил: `Deadline = 12:00:02.000` (через 2 секунды).
  - При передаче контекста в `InventoryService` передается то же самое значение `12:00:02.000`.
- Ошибка новичков: создавать на каждом шаге `context.WithTimeout(ctx, 2*time.Second)`. Это удваивает таймаут до 4 секунд, нарушая SLA клиента.
- Правило: контекст с дедлайном пробрасывается как есть, гарантируя одновременное прерывание всех сервисов ровно в `12:00:02.000`.

## Решение по шагам

1. Создайте единый дедлайн на 40 мс.
2. Передайте контекст через 2 микросервиса.
3. Сымитируйте зависание нижнего сервиса на 500 мс.
4. Докажите, что оба сервиса завершаются ровно через 40 мс.

## Код решения

**`deadline_invariant_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

func InventoryServiceHang(ctx context.Context) error {
	select {
	case <-time.After(500 * time.Millisecond):
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func OrderServiceForward(ctx context.Context) error {
	// OrderService передает ТОТ ЖЕ САМЫЙ контекст без создания новых таймаутов!
	return InventoryServiceHang(ctx)
}

func TestDeadlineSimultaneousExpiry(t *testing.T) {
	// Клиент задает жесткий дедлайн 40 мс
	clientCtx, cancel := context.WithTimeout(context.Background(), 40*time.Millisecond)
	defer cancel()

	start := time.Now()
	err := OrderServiceForward(clientCtx)
	elapsed := time.Since(start)

	if err != context.DeadlineExceeded {
		t.Fatalf("Ожидался DeadlineExceeded, получено: %v", err)
	}

	if elapsed > 60*time.Millisecond {
		t.Fatalf("Таймаут не сработал одновременно: %v", elapsed)
	}

	fmt.Printf("Инвариант дедлайна доказан: оба сервиса прерваны одновременно за %v!\n",
		elapsed.Round(time.Millisecond))
}
```

ℹ️ Синхронное срабатывание абсолютного дедлайна на всех уровнях цепочки

**`Терминал`**

```bash

# Вывод:

```

## Под капотом

Если вызвать `context.WithTimeout(parentCtx, 10*time.Second)`, где у `parentCtx` уже есть дедлайн через 2 секунды, Go автоматически выберет **наиболее ранний дедлайн** из двух (2 секунды). Увеличить дедлайн невозможно по архитектуре пакета `context`.

## Подводные камни

Заменять входящий контекст на `context.Background()`: дедлайн сбрасывается в бесконечность, и при зависании склада запрос зависнет навсегда.

## На собеседовании

**Вопрос с собеседования:** «Может ли дочерний контекст иметь таймаут БОЛЬШЕ, чем родительский?»
**Ответ:** Нет. В Go дочерний контекст закрывается в ту же наносекунду, когда закрывается родитель. Если у родителя дедлайн через 1 секунду, а у дочернего вызван `WithTimeout(5s)`, дочерний все равно закроется через 1 секунду по сигналу родителя.
