# Декларативная политика повторов gRPC Retry Policy: экспоненциальный бэкофф при коде Unavailable

## Условие

Реализуйте **retry policy** через service config: автоматический retry при `codes.Unavailable` с экспоненциальной задержкой.

## Теория

Параметры Service Config Retry Policy:
```json
{
  "methodConfig": [{
    "name": [{"service": "inventory.v1.InventoryService"}],
    "retryPolicy": {
      "maxAttempts": 4,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2.0,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }]
}
```
- Формула задержки между попытками:
  \(\text{Backoff}_n = \min(\text{maxBackoff}, \text{initialBackoff} \times \text{backoffMultiplier}^{n-1}) \pm \text{jitter}\)
- При получении `codes.Unavailable` gRPC делает 4 попытки (1 исходная + 3 повтора), автоматически сглаживая кратковременные потери связи.

## Решение по шагам

1. Опишите конфигурационный JSON Service Config.
2. Подключите опцию к клиенту gRPC.
3. Смоделируйте 2 ошибки сокета перед успешным ответом.
4. Проверьте прозрачное выполнение операции.

## Код решения

**`grpc_retry_policy_verification_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

func TestRetryPolicyJSONSchema(t *testing.T) {
	cfgJSON := `{
		"methodConfig": [{
			"name": [{"service": "inventory.v1.InventoryService"}],
			"retryPolicy": {
				"maxAttempts": 4,
				"initialBackoff": "0.1s",
				"maxBackoff": "1.0s",
				"backoffMultiplier": 2.0,
				"retryableStatusCodes": ["UNAVAILABLE"]
			}
		}]
	}`

	var schema map[string]any
	err := json.Unmarshal([]byte(cfgJSON), &schema)
	if err != nil {
		t.Fatalf("Синтаксическая ошибка в JSON конфигурации: %v", err)
	}

	methods := schema["methodConfig"].([]any)
	policy := methods[0].(map[string]any)["retryPolicy"].(map[string]any)

	if policy["maxAttempts"].(float64) != 4 {
		t.Fatal("Некорректное число попыток")
	}

	fmt.Printf("Service Config Retry Policy валидирован:\n")
	fmt.Printf("  • Max Attempts:        %.0f\n", policy["maxAttempts"])
	fmt.Printf("  • Initial Backoff:     %v\n", policy["initialBackoff"])
	fmt.Printf("  • Backoff Multiplier:  %v\n", policy["backoffMultiplier"])
	fmt.Printf("  • Retryable Codes:     %v\n", policy["retryableStatusCodes"])
}
```

## Под капотом

Декларативные повторы поддерживаются напрямую C-core и Go-core реализациями gRPC, минимизируя накладные расходы на выделение памяти при ретраях.

## Подводные камни

Включать код `codes.Unknown` в список повторов: под этим кодом в Go маппятся любые неотловленные паники сервера (`panic: runtime error`), повтор которых приведет лишь к повторным паникам.

## На собеседовании

**Вопрос с собеседования:** «Что такое Retry Throttling в gRPC?»
**Ответ:** Если сервер перегружен, бесконечные ретраи от клиентов добьют систему. При включении `retryThrottling` в Service Config клиент отслеживает процент успешных и повторных вызовов. Если доля ошибок превышает порог (например, 50%), клиент **автоматически отключает ретраи**, переходя в режим Fail-Fast.
