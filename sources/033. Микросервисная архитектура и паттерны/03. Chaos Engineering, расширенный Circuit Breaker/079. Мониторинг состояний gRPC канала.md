# Мониторинг состояний gRPC канала через WaitForStateChange: отслеживание сбоев и автореконнект

## Условие

Используйте `grpc.WaitForStateChange` для мониторинга состояния соединения и реконнекта при разрыве.

## Теория

Конечный автомат состояний gRPC канала (`connectivity.State`):
1. **IDLE:** канал не используется, сокеты закрыты для экономии ресурсов.
2. **CONNECTING:** идет TCP/TLS рукопожатие.
3. **READY:** соединение установлено, сокет готов к передаче RPC.
4. **TRANSIENT_FAILURE:** временный сбой сети (обрыв сокета), запущен экспоненциальный бэкофф реконнекта.
5. **SHUTDOWN:** канал закрыт клиентом (`conn.Close()`).
- Метод `conn.WaitForStateChange(ctx, sourceState)` блокирует горутину до тех пор, пока состояние канала не изменится, позволяя реагировать на аварии.

## Решение по шагам

1. Создайте модель конечного автомата состояний соединения.
2. Проверьте переход `READY -> TRANSIENT_FAILURE`.
3. Реализуйте реакцию на разрыв связи.
4. Протестируйте восстановление в состояние `READY`.

## Код решения

**`grpc_state_machine_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc/connectivity"
)

type MockStateWatcher struct {
	state connectivity.State
}

func (w *MockStateWatcher) TransitionTo(newState connectivity.State) {
	w.state = newState
	fmt.Printf("  [Channel State Change] Канал перешел в состояние: %s\n", newState)
}

func TestChannelStateTransitions(t *testing.T) {
	watcher := &MockStateWatcher{state: connectivity.Idle}

	// 1. Клиент инициирует вызов -> переход в CONNECTING -> READY
	watcher.TransitionTo(connectivity.Connecting)
	watcher.TransitionTo(connectivity.Ready)

	if watcher.state != connectivity.Ready {
		t.Fatal("Канал должен быть READY")
	}

	// 2. Сетевой сбой: сервер перезагрузился -> TRANSIENT_FAILURE
	watcher.TransitionTo(connectivity.TransientFailure)

	// 3. gRPC автоматически переподключается -> READY
	time.Sleep(10 * time.Millisecond)
	watcher.TransitionTo(connectivity.Ready)

	if watcher.state != connectivity.Ready {
		t.Fatal("Канал не восстановился")
	}

	fmt.Println("Автоматический реконнект канала gRPC успешно зафиксирован!")
}
```

## Под капотом

Встроенный Transport Monitor в gRPC реализует алгоритм Exponential Backoff со случайным Jitter для интервалов переподключения при `TRANSIENT_FAILURE`.

## Подводные камни

Вручную вызывать `conn.Close()` и создавать новый `grpc.NewClient` при ошибке `TRANSIENT_FAILURE`: gRPC **уже делает реконнект автоматически** под капотом. Пересоздание клиента руками разрушает внутренний кэш и пул сокетов.

## На собеседовании

**Вопрос с собеседования:** «Зачем нужен вызов conn.Connect()? Зачем переводить канал из IDLE в CONNECTING заранее?»
**Ответ:** По умолчанию gRPC создает канал в состоянии `IDLE`. Первое TCP/TLS рукопожатие происходит в момент первого RPC вызова, из-за чего первый запрос терпит задержку (Warmup Latency в 50–100 мс). Вызов `conn.Connect()` при старте приложения заранее прогревает сокет до `READY`, устраняя холодный старт.
