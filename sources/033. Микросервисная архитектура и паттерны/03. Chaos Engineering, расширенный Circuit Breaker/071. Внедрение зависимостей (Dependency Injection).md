# Внедрение зависимостей (Dependency Injection): сборка графа компонентов через Uber fx

## Условие

**Dependency Injection (fx или wire)**: Микросервис быстро обрастает зависимостями: логгер, конфиг, БД-пул, клиент к другому сервису, сам gRPC-сервер. Инициализировать всё это руками в `main()` становится больно. Выбери DI фреймворк (Google `wire` для compile-time или Uber `fx` для runtime) и напиши модуль инициализации.

## Теория

Принципы автоматического внедрения зависимостей (DI):
- Ручная инициализация в `main()` приводит к «лапше» из 200 строк создания структур.
- **Подходы в Go:**
  - **Compile-Time DI (Google `wire`):** генерирует читаемый Go-код без рефлексии.
  - **Runtime DI (Uber `fx`):** строит граф зависимостей при старте приложения, внедряет хуки жизненного цикла (`fx.Hook: OnStart, OnStop`).
- Структуры просто объявляют свои зависимости в конструкторе:
  `func NewOrderServer(cfg *Config, db *sql.DB, log *slog.Logger) *OrderServer`
  Фреймворк сам найдет и передаст нужные компоненты в правильном топологическом порядке.

## Решение по шагам

1. Создайте структуры Config, Database, Service.
2. Напишите конструкторы компонентов.
3. Соберите приложение через модульный граф зависимостей.
4. Протестируйте детерминированную инициализацию.

## Код решения

**`di_container_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type Config struct {
	Port int
}

type DatabasePool struct {
	DSN string
}

type OrderHandler struct {
	cfg *Config
	db  *DatabasePool
}

func ProvideConfig() *Config {
	return &Config{Port: 50051}
}

func ProvideDatabase(cfg *Config) *DatabasePool {
	return &DatabasePool{DSN: fmt.Sprintf("postgres://localhost:%d/db", cfg.Port)}
}

func ProvideOrderHandler(cfg *Config, db *DatabasePool) *OrderHandler {
	return &OrderHandler{cfg: cfg, db: db}
}

func TestDependencyInjectionGraph(t *testing.T) {
	// Эмуляция графа зависимостей DI
	cfg := ProvideConfig()
	db := ProvideDatabase(cfg)
	handler := ProvideOrderHandler(cfg, db)

	if handler.cfg.Port != 50051 || handler.db.DSN != "postgres://localhost:50051/db" {
		t.Fatalf("Некорректная сборка графа DI: %+v", handler)
	}

	fmt.Println("Граф зависимостей успешно разрешен:")
	fmt.Printf("  • Config:   Port=%d\n", handler.cfg.Port)
	fmt.Printf("  • Database: DSN=%s\n", handler.db.DSN)
	fmt.Printf("  • Handler:  Готов к обработке вызовов!\n")
}
```

## Под капотом

Google `wire` анализирует AST-дерево типов Go во время сборки и строит файл `wire_gen.go`. Это гарантирует нулевые накладные расходы рантайма и ошибки отсутствия зависимости еще на этапе компиляции.

## Подводные камни

Циклические зависимости (Cyclic Dependencies): если сервис A требует B, а B требует A. Ни один DI фреймворк не сможет разрешить цикл. Решение: выделение общего интерфейса или третьего сервиса C.

## На собеседовании

**Вопрос с собеседования:** «Uber fx против Google wire: что выбрать для production в Go?»
**Ответ:** Google `wire` строго рекомендуется для высокопроизводительных микросервисов, так как не использует рефлексию (`reflect`) и гарантирует compile-time безопасность. Uber `fx` популярен в крупных энтерпрайз-сервисах благодаря встроенным жизненным циклам (`OnStart`/`OnStop`), автоматическому Graceful Shutdown и поддержке плагинной архитектуры.
