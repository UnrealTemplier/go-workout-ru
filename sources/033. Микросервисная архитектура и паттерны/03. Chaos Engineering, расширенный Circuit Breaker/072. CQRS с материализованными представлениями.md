# CQRS с материализованными представлениями: проекция событий в ClickHouse и мониторинг лага

## Условие

Реализуй **"CQRS with Materialized Views"**:
- Command side: PostgreSQL, normalized schema
- Event sourcing: все изменения — события
- Read side: Elasticsearch/ClickHouse, denormalized views
- Projection service: читает события, обновляет read model
- Консистентность: eventual, мониторинг lag

## Теория

Архитектура CQRS с материализованными витринами данных:
- **Write Side (PostgreSQL):** транзакционная ACID база.
  - Таблица `orders`, таблица `order_items`, таблица `customers`.
- **Event Stream (Kafka):** события изменений `OrderCreated`, `ItemAdded`.
- **Projection Worker:** читает стрим и формирует денормализованную строку в ClickHouse:
  - `orders_analytics_mv`: плоская широкая строка со 100 колонками для OLAP аналитики.
- **Мониторинг лага репликации (Consumer Lag):**
  - Разница между последним записанным офсетом в Kafka и текущим офсетом воркера:
    \(\text{Lag} = \text{HighwaterMark} - \text{CurrentOffset}\)
  - Если Lag растет — алерт дежурным о задержке аналитики!

## Решение по шагам

1. Создайте модель очереди событий со счетчиком офсетов.
2. Напишите проектор в витрину ClickHouse.
3. Реализуйте метрику вычисления лага консьюмера.
4. Протестируйте работу проекции и контроль лага.

## Код решения

**`cqrs_materialized_views_test.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"testing"
)

type ClickHouseOrderView struct {
	OrderID   string
	UserEmail string
	TotalAmt  float64
}

type EventStreamLagMonitor struct {
	latestEventOffset int64
	consumedOffset    int64
}

func (m *EventStreamLagMonitor) ProduceEvent() int64 {
	return atomic.AddInt64(&m.latestEventOffset, 1)
}

func (m *EventStreamLagMonitor) ConsumeEvent() int64 {
	return atomic.AddInt64(&m.consumedOffset, 1)
}

func (m *EventStreamLagMonitor) GetCurrentLag() int64 {
	latest := atomic.LoadInt64(&m.latestEventOffset)
	consumed := atomic.LoadInt64(&m.consumedOffset)
	return latest - consumed
}

func TestCQRSMaterializedLag(t *testing.T) {
	monitor := &EventStreamLagMonitor{}

	// В PostgreSQL записано 10 заказов
	for i := 0; i < 10; i++ {
		monitor.ProduceEvent()
	}

	// ClickHouse воркер успел обработать только 7
	for i := 0; i < 7; i++ {
		monitor.ConsumeEvent()
	}

	lag := monitor.GetCurrentLag()
	if lag != 3 {
		t.Fatalf("Ожидался лаг 3 сообщения, получено: %d", lag)
	}

	fmt.Printf("Метрика мониторинга Consumer Lag: %d событий в очереди (Eventual Consistency)\n", lag)

	// Дообрабатываем остаток
	for i := 0; i < 3; i++ {
		monitor.ConsumeEvent()
	}

	if monitor.GetCurrentLag() != 0 {
		t.Fatal("Лаг должен быть равен 0 после догонки")
	}

	fmt.Println("Материализованные представления ClickHouse полностью синхронизированы!")
}
```

ℹ️ Контроль лага репликации между источником и материализованной витриной

## Под капотом

ClickHouse Materialized Views обновляются на лету с помощью движка `SummingMergeTree` или `ReplacingMergeTree`, агрегируя терабайты данных в фоновом процессе слияния партиций.

## Подводные камни

Использовать Read-модель для проверки критических бизнес-ограничений (например, проверка баланса перед списанием): из-за лага репликации баланс в ClickHouse/Redis может отставать на пару секунд, что приведет к двойной трате денег (Double Spending). Команды валидируются строго по Write-модели.

## На собеседовании

**Вопрос с собеседования:** «Как вычисляется Kafka Consumer Lag в Prometheus?»
**Ответ:** Через утилиту `kafka-exporter`, собирающую метрики `kafka_consumergroup_lag{topic="...", consumergroup="..."}`. На ее основе настраивается критический алерт: если лаг превышает 50 000 сообщений более 5 минут, инициируется автоскейлинг подов воркеров-консьюмеров (KEDA).
