# Паттерн Sidecar: вынос mTLS, повторов и наблюдаемости в прокси Envoy без модификации кода

## Условие

**Sidecar Pattern**: Разместите Envoy proxy рядом с каждым сервисом для handling mTLS, retries, observability (Service Mesh).

## Теория

Архитектурный шаблон Sidecar (Service Mesh Data Plane):
- Происхождение названия: коляска мотоцикла (Sidecar) едет рядом и делит с мотоциклом дорогу.
- В Kubernetes:
  - Контейнер приложения `app` и контейнер `envoy` находятся в **одном сетевом пространстве (один сетевой неймспейс `localhost`)**.
  - Приложение слушает `:50051` только на `127.0.0.1`.
  - Внешний трафик из сети поступает в Envoy на порт `:15006`.
  - Envoy проверяет mTLS сертификат клиента, собирает метрики Prometheus, генерирует OpenTelemetry спаны и передает расшифрованный запрос в Go-приложение на `localhost:50051`!

## Решение по шагам

1. Опишите структуру пода с двумя контейнерами (App + Sidecar).
2. Смоделируйте передачу запроса через локальный сокет.
3. Проверьте изоляцию инфраструктурной логики.
4. Продемонстрируйте чистый бизнес-код приложения.

## Код решения

**`sidecar_pod_spec.yaml`**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: order-service-pod
  labels:
    app: order-service
spec:
  containers:
  # 1. Основной бизнес-контейнер на Go (Чистая логика!)
  - name: order-app
    image: company/order-service:v1.0.0
    ports:
    - containerPort: 50051 # Слушает только 127.0.0.1
    env:
    - name: LISTEN_ADDR
      value: "127.0.0.1:50051"

  # 2. Sidecar контейнер Envoy (Инфраструктура: mTLS, Tracing, Metrics)
  - name: envoy-proxy
    image: envoyproxy/envoy:v1.30.0
    ports:
    - containerPort: 10000 # Публичный входной порт пода
    volumeMounts:
    - name: envoy-config
      mountPath: /etc/envoy
  volumes:
  - name: envoy-config
    configMap:
      name: envoy-sidecar-config
```

ℹ️ Спецификация Kubernetes Pod с контейнером приложения и Envoy Sidecar

**`Терминал`**

```bash
# Проверка контейнеров внутри одного пода:
kubectl get pod order-service-pod
# NAME                READY   STATUS    RESTARTS   AGE
# order-service-pod   2/2     Running   0          12s

# Логи Envoy sidecar подтверждают mTLS рукопожатие:
kubectl logs order-service-pod -c envoy-proxy | grep tls
# [debug][connection] [source/common/tls/server_ssl_socket.go:63] TLS handshake succeeded: mTLS mutual cert verified
```

## Под капотом

Оба контейнера делят общий виртуальный сетевой интерфейс `lo` (Loopback). Передача трафика между Envoy и Go-приложением выполняется в ОЗУ ядра Linux без выхода в физическую сеть.

## Подводные камни

Порядок старта контейнеров: если приложение `app` стартует раньше, чем поднялся `envoy-proxy`, исходящие запросы приложения к другим сервисам упадут. В Kubernetes 1.29+ добавлена встроенная поддержка `initContainers` с типом `restartPolicy: Always` (Native Sidecars).

## На собеседовании

**Вопрос с собеседования:** «Каковы главные преимущества выноса mTLS в Sidecar вместо реализации на чистом Go?»
**Ответ:** 1. **Единое управление сертификатами:** ротация ключей каждые 12–24 часа выполняется Control Plane (Istio/Vault) централизованно без участия разработчиков. 2. **Полиглотность:** mTLS и метрики работают одинаково для сервисов на Go, Java, Python и Rust. 3. **Разделение ответственности:** разработчики пишут только бизнес-код.
