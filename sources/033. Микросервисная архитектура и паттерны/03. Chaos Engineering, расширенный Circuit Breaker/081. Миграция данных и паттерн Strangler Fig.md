# Миграция данных и паттерн Strangler Fig: плавный перенос из монолита в микросервисы без даунтайма

## Условие

Реализуй **"Data migration between microservices"**:
- Монолит → микросервисы: strangler fig pattern
- Постепенный перенос: read from new service, write to both
- Dual write consistency: saga/compensation
- Verification: сравнение данных в старой и новой системе
- Cutover: переключение трафика, rollback plan

## Теория

Паттерн фигового дерева (Strangler Fig Pattern / Мартин Фаулер):
- Попытка переписать монолит с нуля («Большой взрыв») в 90% случаев заканчивается провалом проекта.
- **Стратегия постепенного вытеснения:**
  1. **Dual Write (Двойная запись):** монолит пишет в старую БД и асинхронно/синхронно дублирует запись в новый микросервис.
  2. **Data Reconciliation (Сверка данных):** фоновый джоб сверяет 100% записей старой и новой БД, выявляя расхождения.
  3. **Dark Launch (Теневое чтение):** шлюз дублирует 10% запросов чтения в новый микросервис и сравнивает ответы, не отдавая их пользователю.
  4. **Cutover (Переключение):** чтение полностью переключается на микросервис.
  5. **Decommission:** старый код монолита удаляется.

## Решение по шагам

1. Создайте модель двойной записи (Dual Write).
2. Реализуйте проверку консистентности данных (Verification Job).
3. Смоделируйте переключение источника чтения (Cutover).
4. Протестируйте план безопасного отката (Rollback).

## Код решения

**`strangler_fig_migration_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type MonolithStore struct {
	mu   sync.RWMutex
	data map[string]string
}

type NewMicroserviceStore struct {
	mu   sync.RWMutex
	data map[string]string
}

type StranglerMigrationRouter struct {
	monolith      *MonolithStore
	microservice  *NewMicroserviceStore
	readFromMicro bool
}

func (r *StranglerMigrationRouter) WriteDual(id, val string) {
	// 1. Запись в старую систему (монолит)
	r.monolith.mu.Lock()
	r.monolith.data[id] = val
	r.monolith.mu.Unlock()

	// 2. Двойная запись в новый микросервис
	r.microservice.mu.Lock()
	r.microservice.data[id] = val
	r.microservice.mu.Unlock()
}

func (r *StranglerMigrationRouter) Read(id string) string {
	if r.readFromMicro {
		r.microservice.mu.RLock()
		defer r.microservice.mu.RUnlock()
		return r.microservice.data[id]
	}

	r.monolith.mu.RLock()
	defer r.monolith.mu.RUnlock()
	return r.monolith.data[id]
}

func (r *StranglerMigrationRouter) ReconcileAndVerify() int {
	r.monolith.mu.RLock()
	r.microservice.mu.RLock()
	defer r.monolith.mu.RUnlock()
	defer r.microservice.mu.RUnlock()

	mismatches := 0
	for k, vOld := range r.monolith.data {
		if vNew, ok := r.microservice.data[k]; !ok || vNew != vOld {
			mismatches++
		}
	}
	return mismatches
}

func TestStranglerFigMigration(t *testing.T) {
	router := &StranglerMigrationRouter{
		monolith:     &MonolithStore{data: make(map[string]string)},
		microservice: &NewMicroserviceStore{data: make(map[string]string)},
	}

	// 1. Фаза Dual Write
	router.WriteDual("user_101", "Алексей (Статус: VIP)")
	router.WriteDual("user_102", "Елена (Статус: Basic)")

	// 2. Фаза сверки (Reconciliation)
	mismatches := router.ReconcileAndVerify()
	if mismatches != 0 {
		t.Fatalf("Обнаружены расхождения данных: %d", mismatches)
	}
	fmt.Printf("Аудит целостности данных: 100%% совпадение (0 расхождений)!\n")

	// 3. Фаза Cutover: переключаем чтение на новый микросервис
	router.readFromMicro = true
	res := router.Read("user_101")
	if res != "Алексей (Статус: VIP)" {
		t.Fatalf("Ошибка чтения из микросервиса: %s", res)
	}

	fmt.Printf("Переключение трафика (Cutover) успешно выполнено! Ответ получен из микросервиса: %s\n", res)
}
```

## Под капотом

Для синхронизации исторических терабайтов данных между базами запускается фоновый CDC-пайплайн (Debezium + Kafka Connect), копирующий исторические снепшоты без блокировки боевой базы.

## Подводные камни

Выполнять Cutover сразу на 100% трафика: всегда переключайте трафик постепенно (Feature Flag / Canaries: 1% -> 5% -> 25% -> 100%), сохраняя возможность мгновенного отката флажком за 1 секунду.

## На собеседовании

**Вопрос с собеседования:** «Как обеспечить идемпотентность при Dual Write, если запись в микросервис упала?»
**Ответ:** Запись в микросервис должна быть асинхронной через Transactional Outbox: монолит в одной транзакции сохраняет данные и событие в outbox-таблицу. Воркер гарантированно доставляет событие в микросервис с семантикой At-Least-Once, а микросервис обрабатывает его идемпотентно по первичному ключу.
