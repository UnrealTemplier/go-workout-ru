# Событийно-ориентированная архитектура (Event-Driven): асинхронное взаимодействие через брокер сообщений

## Условие

**Архитектура событийного обмена (Event-Driven)**: Создайте два независимых gRPC-микросервиса: `OrderService` (создание заказов) и `NotificationService` (отправка писем). Вместо прямого синхронного вызова gRPC между ними, внедрите брокер сообщений (NATS, RabbitMQ или Kafka). При успешном создании заказа `OrderService` должен публиковать событие `OrderCreated` в брокер, а `NotificationService` должен слушать эту очередь и реагировать на событие.

## Теория

Сравнение синхронной и событийно-ориентированной архитектуры:
- **Синхронный вызов (gRPC):** `OrderService` ждет ответа от `NotificationService`. Если почтовый сервер тормозит 5 секунд, клиент интернет-магазина ждет 5 секунд на кнопке «Оплатить».
- **Событийная архитектура (Event-Driven):**
  1. `OrderService` сохраняет заказ и публикует событие `OrderCreated{ID: "42", Email: "user@mail.ru"}` в брокер (NATS/Kafka) за 2 мс.
  2. Клиент немедленно получает ответ «Заказ принят!».
  3. `NotificationService` асинхронно вычитывает событие из очереди и отправляет email.
  4. Даже если сервис уведомлений полностью упал, сообщения копятся в брокере и будут обработаны после его подъема (Decoupling in Time).

## Решение по шагам

1. Создайте модель брокера сообщений на Go-каналах.
2. Реализуйте публикацию события из сервиса заказов.
3. Напишите подписчика в сервисе уведомлений.
4. Проверьте асинхронную доставку.

## Код решения

**`event_driven_broker_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type OrderCreatedEvent struct {
	OrderID   string
	UserEmail string
	Amount    float64
}

type InMemoryMessageBroker struct {
	mu          sync.Mutex
	subscribers []chan OrderCreatedEvent
}

func NewBroker() *InMemoryMessageBroker {
	return &InMemoryMessageBroker{}
}

func (b *InMemoryMessageBroker) Subscribe() <-chan OrderCreatedEvent {
	b.mu.Lock()
	defer b.mu.Unlock()
	ch := make(chan OrderCreatedEvent, 10)
	b.subscribers = append(b.subscribers, ch)
	return ch
}

func (b *InMemoryMessageBroker) Publish(event OrderCreatedEvent) {
	b.mu.Lock()
	defer b.mu.Unlock()
	for _, ch := range b.subscribers {
		ch <- event
	}
}

func TestEventDrivenDecoupling(t *testing.T) {
	broker := NewBroker()

	// NotificationService подписывается на топик
	eventsChan := broker.Subscribe()
	notificationReceived := make(chan string, 1)

	go func() {
		for evt := range eventsChan {
			msg := fmt.Sprintf("Email отправлен на %s: Заказ #%s подтвержден на сумму %.2f ₽",
				evt.UserEmail, evt.OrderID, evt.Amount)
			notificationReceived <- msg
		}
	}()

	// OrderService создает заказ и публикует событие
	orderEvent := OrderCreatedEvent{
		OrderID:   "ord_777",
		UserEmail: "client@bank.ru",
		Amount:    15900.00,
	}

	broker.Publish(orderEvent)

	select {
	case result := <-notificationReceived:
		fmt.Printf("NotificationService успешно обработал событие:\n  %s\n", result)
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Таймаут ожидания асинхронного события")
	}

	fmt.Println("Событийно-ориентированная архитектура полностью изолировала сервисы во времени!")
}
```

ℹ️ Асинхронное взаимодействие через брокер событий (Pub/Sub)

## Под капотом

Асинхронные брокеры (NATS JetStream, Apache Kafka) гарантируют сохранность сообщений на диске (Durable Storage), обеспечивая паттерн Store-and-Forward.

## Подводные камни

Использовать брокер сообщений для синхронных RPC запросов по схеме Request-Reply через временные очереди: это сочетает худшие стороны обоих подходов — сложность очередей и блокирующее ожидание.

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать порядок обработки событий в Kafka при нескольких консьюмерах?»
**Ответ:** Порядок строго гарантируется **только внутри одной партиции**. Чтобы события конкретного заказа обрабатывались строго последовательно (`OrderCreated` -> `OrderPaid` -> `OrderShipped`), в качестве ключа партиционирования (`Record Key`) передается `order_id`. Все события с одинаковым ключом гарантированно попадают в одну и ту же партицию к одному воркеру.
