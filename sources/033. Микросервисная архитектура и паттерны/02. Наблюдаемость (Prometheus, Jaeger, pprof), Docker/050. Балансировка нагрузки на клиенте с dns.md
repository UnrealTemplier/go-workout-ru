# Балансировка нагрузки на клиенте с dns:/// и Headless Service: алгоритм round-robin

## Условие

Настройте **client-side load balancing** в gRPC: используйте `dns:///` схему для резолвинга всех IP сервиса и round-robin балансировки на клиенте.

## Теория

Архитектура Client-Side Load Balancing через DNS:
- Клиент передает адрес вида: `dns:///inventory-headless:50051`.
- DNS-сервер (CoreDNS в Kubernetes) возвращает список IP всех подов: `[10.244.1.10, 10.244.1.11, 10.244.1.12]`.
- Балансировщик `round_robin`:
  1. Поддерживает активный SubConn (TCP сокет) к каждому поду.
  2. На каждый вызов перебирает следующий сокет по кругу.
- Преимущества:
  - Нет промежуточного Proxy-сервера (Zero Hop, минимальная задержка).
  - Равномерная загрузка всех CPU ядер кластера.

## Решение по шагам

1. Задайте конфигурацию `serviceConfig` с политикой `round_robin`.
2. Настройте подключение через `grpc.NewClient`.
3. Смоделируйте распределение 6 вызовов по 3 подам.
4. Проверьте балансировку.

## Код решения

**`client_side_balancer_demo.go`**

```go
package main

import (
	"fmt"

	"google.golang.org/grpc"
	_ "google.golang.org/grpc/balancer/roundrobin"
	"google.golang.org/grpc/credentials/insecure"
)

func main() {
	// JSON-конфигурация клиентской балансировки
	serviceConfig := `{"loadBalancingPolicy":"round_robin"}`

	// Подключение через схему dns:/// к Headless сервису
	target := "dns:///inventory-headless.production.svc.cluster.local:50051"

	conn, err := grpc.NewClient(
		target,
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithDefaultServiceConfig(serviceConfig),
	)
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	fmt.Println("Клиентский балансировщик gRPC успешно инициализирован:")
	fmt.Printf("  • Target URI:     %s\n", target)
	fmt.Printf("  • Алгоритм:       round_robin (по всем A-записям Headless Service)\n")
}
```

## Под капотом

При получении списка адресов gRPC Subchannel Manager открывает независимые пулы сокетов. Если один под перестает отвечать, SubConn переходит в TransientFailure, и балансировщик выводит его из ротации за 0 микросекунд.

## Подводные камни

Использовать обычный ClusterIP сервис без `clusterIP: None`: CoreDNS вернет один виртуальный IP, и вся нагрузка пойдет на один под.

## На собеседовании

**Вопрос с собеседования:** «Каковы недостатки Client-Side балансировки по сравнению с Server-Side (Envoy)?»
**Ответ:** 1. При 1 000 клиентов и 1 000 подов бэкенда суммарно открывается \(1\,000 \times 1\,000 = 1\,000\,000\) постоянных TCP сокетов (Full Mesh Connection Problem), что перегружает память. 2. Сложность реализации логики балансировки на разных языках программирования.
