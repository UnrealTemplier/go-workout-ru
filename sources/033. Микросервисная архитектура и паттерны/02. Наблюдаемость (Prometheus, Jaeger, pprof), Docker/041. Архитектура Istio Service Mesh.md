# Архитектура Istio Service Mesh: прозрачный mTLS, Canary 90/10 и Circuit Breaking без изменения кода

## Условие

Настрой **Istio service mesh**: sidecar proxy для каждого pod. mTLS между сервисами автоматически. Traffic splitting (canary deployment: 90% v1, 10% v2). Circuit breaker на уровне mesh.

## Теория

Принцип работы Istio Service Mesh (Data Plane & Control Plane):
- В каждый под автоматически внедряется sidecar-контейнер **Envoy Proxy** (`istio-proxy`).
- Все входящие и исходящие TCP соединения прозрачно перехватываются правилами `iptables`.
- **Преимущества Mesh-архитектуры:**
  1. **Zero-Code Security:** сквозное mTLS шифрование между всеми подами с автоматической ротацией сертификатов каждые 24 часа.
  2. **Canary Traffic Splitting:** манифест `VirtualService` направляет 90% трафика на версию v1 и 10% на v2.
  3. **Mesh-Level Circuit Breaking:** манифест `DestinationRule` ограничивает число параллельных соединений и отсекает упавшие поды.

## Решение по шагам

1. Опишите манифест Istio VirtualService для разделения трафика 90/10.
2. Опишите манифест DestinationRule для mTLS и Circuit Breaking.
3. Продемонстрируйте структуру управления трафиком.
4. Проверьте параметры конфигурации Canary.

## Код решения

**`istio/order-traffic-routing.yaml`**

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: order-service-routing
  namespace: production
spec:
  hosts:
  - order-service
  http:
  - route:
    - destination:
        host: order-service
        subset: v1
      weight: 90
    - destination:
        host: order-service
        subset: v2 # Canary релиз
      weight: 10
---
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: order-service-destination
  namespace: production
spec:
  host: order-service
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL # Автоматический mTLS между подами
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http1MaxPendingRequests: 10
        maxRequestsPerConnection: 10
    outlierDetection: # Circuit Breaker на уровне Envoy
      consecutive5xxErrors: 3
      interval: 10s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
```

## Под капотом

Envoy sidecar слушает порт 15001. Правила `iptables -t nat -A PREROUTING -p tcp -j REDIRECT --to-ports 15001` заворачивают все сетевые пакеты ядра Linux в пользовательский процесс Envoy.

## Подводные камни

Накладные расходы по задержке: каждый сетевой хоп через Envoy добавляет ~1–2 мс задержки и 50 МБ ОЗУ на каждый контейнер sidecar. Для сверхвысоконагруженных low-latency систем используют Ambient Mesh (без sidecar) или gRPC Proxyless Mesh.

## На собеседовании

**Вопрос с собеседования:** «Что такое gRPC Proxyless Service Mesh?»
**Ответ:** Это решение, при котором gRPC клиент напрямую общается с плоскостью управления Istio (Istiod) по протоколу **xDS**. Балансировка, канареечные веса и mTLS выполняются внутри самого Go-бинарника без промежуточного процесса Envoy, снижая задержку до нуля.
