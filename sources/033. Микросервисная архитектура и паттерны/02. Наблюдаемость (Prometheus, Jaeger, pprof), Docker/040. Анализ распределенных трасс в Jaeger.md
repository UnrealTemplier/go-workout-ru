# Анализ распределенных трасс в Jaeger: выявление узких мест (Bottlenecks) и медленных вызовов

## Условие

Экспортируйте трассы в Jaeger (локально в Docker) и проанализируйте цепочку вызовов между двумя микросервисами.

## Теория

Анализ производительности графа спанов в Jaeger UI:
- На дэшборде Waterfall View отображаются:
  - **Критический путь (Critical Path):** последовательность операций, определяющая суммарное время запроса.
  - **Параллельные ветвления:** одновременные вызовы двух сервисов.
  - **Сетевой оверхед:** разница во времени между отправкой запроса клиентом и получением на сервере.
- Теги спана (`http.status_code`, `error=true`, `db.statement`) позволяют мгновенно найти причину задержки.

## Решение по шагам

1. Создайте модель анализатора графа спанов.
2. Реализуйте алгоритм вычисления критического пути.
3. Найдите самый медленный спан (Bottleneck).
4. Протестируйте диагностику задержки.

## Код решения

**`jaeger_trace_analyzer_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type TraceSpan struct {
	Name     string
	Service  string
	Duration time.Duration
}

func FindTraceBottleneck(spans []TraceSpan) TraceSpan {
	var maxSpan TraceSpan
	for _, s := range spans {
		if s.Duration > maxSpan.Duration {
			maxSpan = s
		}
	}
	return maxSpan
}

func TestTraceBottleneckDetection(t *testing.T) {
	// Граф вызовов одного запроса оформления заказа
	trace := []TraceSpan{
		{Name: "Gateway.Route", Service: "api-gateway", Duration: 5 * time.Millisecond},
		{Name: "OrderService.Validate", Service: "order-service", Duration: 12 * time.Millisecond},
		{Name: "PaymentService.Charge", Service: "payment-service", Duration: 350 * time.Millisecond}, // Узкое место!
		{Name: "NotificationService.SendPush", Service: "notification-service", Duration: 25 * time.Millisecond},
	}

	bottleneck := FindTraceBottleneck(trace)

	if bottleneck.Service != "payment-service" || bottleneck.Duration != 350*time.Millisecond {
		t.Fatalf("Некорректно определено узкое место: %+v", bottleneck)
	}

	fmt.Printf("Анализ трассы Jaeger успешно локализовал узкое место (Bottleneck):\n")
	fmt.Printf("  • Сервис:   %s\n", bottleneck.Service)
	fmt.Printf("  • Операция: %s\n", bottleneck.Name)
	fmt.Printf("  • Задержка: %v (90%% суммарного времени транзакции!)\n", bottleneck.Duration)
}
```

ℹ️ Автоматизированная локализация узких мест в распределенном трейсе

## Под капотом

Jaeger вычисляет критический путь через топологическую сортировку направленного ациклического графа (DAG) спанов, определяя отрезки, где время выполнения нельзя сократить параллелизацией.

## Подводные камни

Создавать слишком много мелких спанов (на каждый вызов локальной Go-функции): это раздует трейс до мегабайт и приведет к задержкам на сериализацию. Спаны создаются только на сетевые и ключевые I/O границы.

## На собеседовании

**Вопрос с собеседования:** «Как Jaeger помогает выявить проблему N+1 сетевых запросов?»
**Ответ:** На таймлайне Jaeger проблема \(N+1\) видна мгновенно в виде характерной «лесенки» (Waterfall Staircase) из сотен последовательных микро-спанов (например 100 запросов `SELECT * FROM items WHERE id = ?`), которые должны быть заменены на один батч-запрос `WHERE id IN (...)`.
