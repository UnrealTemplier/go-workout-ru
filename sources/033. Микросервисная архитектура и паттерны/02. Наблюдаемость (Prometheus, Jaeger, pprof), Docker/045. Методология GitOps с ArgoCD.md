# Методология GitOps с ArgoCD: Git как единственный источник правды и атомарный откат версий

## Условие

Настрой **GitOps** (ArgoCD/Flux): Git-репозиторий с Kubernetes manifests — единственный источник правды. ArgoCD синхронизирует кластер с Git. Rollback через `git revert`.

### Исходная формулировка

Настрой **GitOps** (ArgoCD/Flux): Git-репозиторий с Kubernetes manifests — единственный источник правды. ArgoCD синхронизирует кластер с Git. Rollback через `git revert`.

## Теория

Принципы парадигмы GitOps (ArgoCD / Flux):
- **Declarative Description:** все манифесты инфраструктуры хранятся в Git в виде декларативных YAML файлов (или Helm/Kustomize).
- **Single Source of Truth:** Git-репозиторий является единственным источником правды. Прямые вызовы `kubectl apply` вручную строго запрещены.
- **Continuous Reconciliation:** контроллер ArgoCD в кластере непрерывно сравнивает желаемое состояние в Git с реальным состоянием в Kubernetes.
- **Атомарный откат (Instant Rollback):** для отката неудачного релиза инженер выполняет команду `git revert <commit>`, пушит в Git, и ArgoCD мгновенно восстанавливает предыдущую стабильную версию в кластере.

## Решение по шагам

1. Опишите манифест ArgoCD Application.
2. Задайте параметры автосинхронизации (Automated Sync Policy).
3. Смоделируйте синхронизацию состояния приложения.
4. Проверьте механизм отката через реверт коммита.

## Код решения

**`argocd/application.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: order-service-prod
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: 'https://github.com/company/k8s-gitops-manifests.git'
    targetRevision: main
    path: apps/order-service/production
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: production
  syncPolicy:
    automated:
      prune: true     # Автоматически удалять ресурсы, удаленные из Git
      selfHeal: true  # Автоматически восстанавливать ресурсы при ручном изменении
    syncOptions:
      - CreateNamespace=true
```

ℹ️ Манифест ArgoCD Application с автоматической самосинхронизацией (Self-Heal)

**`Терминал`**

```bash
# Проверка статуса синхронизации через ArgoCD CLI:
argocd app get order-service-prod
# App Name:        order-service-prod
# Sync Status:     Synced to main (commit 9f8a1b2)
# Health Status:   Healthy

# Сценарий мгновенного отката неудачного деплоя через Git:
git revert HEAD --no-edit
git push origin main

# ArgoCD обнаруживает вебхук от GitHub и за 2 секунды синхронизирует предыдущую стабильную версию!
argocd app sync order-service-prod
```

## Под капотом

Опция `selfHeal: true` защищает кластер от дрейфа конфигурации (Configuration Drift): если инженер вручную изменит память пода через `kubectl edit`, ArgoCD за считанные секунды сотрет ручные правки и восстановит состояние из Git.

## Подводные камни

Хранить в одном Git-репозитории исходный код приложения на Go и манифесты развертывания: пуш коммита в код вызовет бесконечный цикл сборки и перезапуска. В BigTech принято разделять репозиторий приложения (`app-repo`) и репозиторий манифестов (`infra-gitops-repo`).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие push-модели CI/CD от pull-модели GitOps?»
**Ответ:** В классической push-модели CI-сервер (GitLab CI / Jenkins) хранит полные root-ключи от боевого кластера и пушит изменения наружу через `kubectl`. В случае взлома CI скомпрометирован весь кластер. В pull-модели GitOps контроллер ArgoCD находится **внутри самого кластера**, не имеет открытых входящих портов наружу и сам забирает безопасные манифесты из Git.
