# Профилирование Go-микросервисов в production: net/http/pprof и безопасность эндпоинтов

## Условие

Настрой **profiling**: `net/http/pprof` endpoint'ы (`/debug/pprof/heap`, `/debug/pprof/goroutine`, `/debug/pprof/cpu`). Собирай профили в production (с осторожностью). Анализируй через `go tool pprof`.

## Теория

Низкоуровневое профилирование в Production (pprof endpoints):
- Пакет `net/http/pprof` автоматически регистрирует обработчики:
  - `/debug/pprof/heap` — снимок распределения памяти и аллокаций.
  - `/debug/pprof/goroutine` — стек-трейсы всех работающих горутин (поиск утечек).
  - `/debug/pprof/profile?seconds=30` — CPU профилирование.
- Правило безопасности: **pprof никогда не экспонируется в публичную сеть!** Он поднимается на отдельном внутреннем порту `:6060` или закрывается mTLS/BasicAuth.

## Решение по шагам

1. Поднимите изолированный HTTP сервер для администрирования.
2. Зарегистрируйте стандартные хэндлеры `net/http/pprof`.
3. Проверьте доступность снимка горутин.
4. Протестируйте сбор профиля без блокировки основного сервиса.

## Код решения

**`pprof_setup_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/http/pprof"
	"testing"
)

func NewInternalAdminMux() *http.ServeMux {
	mux := http.NewServeMux()

	// Регистрация pprof на внутреннем изолированном роутере
	mux.HandleFunc("/debug/pprof/", pprof.Index)
	mux.HandleFunc("/debug/pprof/cmdline", pprof.Cmdline)
	mux.HandleFunc("/debug/pprof/profile", pprof.Profile)
	mux.HandleFunc("/debug/pprof/symbol", pprof.Symbol)
	mux.HandleFunc("/debug/pprof/trace", pprof.Trace)

	return mux
}

func TestPprofEndpoints(t *testing.T) {
	mux := NewInternalAdminMux()

	// Тестируем доступность главной страницы pprof
	rec := httptest.NewRecorder()
	req := httptest.NewRequest("GET", "/debug/pprof/", nil)
	mux.ServeHTTP(rec, req)

	if rec.Code != http.StatusOK {
		t.Fatalf("Ожидался статус 200, получено: %d", rec.Code)
	}

	fmt.Println("pprof внутренний эндпоинт успешно смонтирован и доступен для анализа!")
}
```

ℹ️ Изолированное подключение pprof на внутреннем интерфейсе

**`Терминал`**

```bash
# Команды инженера для снятия профилей с пода Kubernetes:
kubectl port-forward pod/order-service-7f9b8c-x9z 6060:6060

# 1. Анализ утечек памяти в интерактивном веб-интерфейсе:
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap

# 2. Снятие 30-секундного CPU профиля:
curl -sK -v http://localhost:6060/debug/pprof/profile?seconds=30 > cpu.pprof
go tool pprof cpu.pprof
```

## Под капотом

Профилировщик CPU использует системный таймер ядра Linux `setitimer(ITIMER_PROF)`. Ядро шлет сигнал `SIGPROF` процессу каждые 10 мс, записывая текущий счетчик команд (PC) выполняемой горутины.

## Подводные камни

Использовать дефолтный `import _ "net/http/pprof"` вместе с публичным `http.ListenAndServe(":8080", nil)`: злоумышленники получат доступ к коду, дампу памяти и смогут положить сервис DoS-атакой через вызов `/debug/pprof/profile`.

## На собеседовании

**Вопрос с собеседования:** «Каковы накладные расходы (Overhead) от включенного CPU профилирования в production?»
**Ответ:** Накладные расходы CPU профилирования в Go крайне малы и составляют порядка **1–3% CPU**. Его можно безопасно включать на работающем сервисе на 30–60 секунд для локализации аномалий производительности.
