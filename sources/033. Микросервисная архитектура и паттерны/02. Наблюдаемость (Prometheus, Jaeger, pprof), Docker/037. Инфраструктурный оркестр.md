# Инфраструктурный оркестр: docker-compose.yml для 3 микросервисов, PostgreSQL, Redis и Jaeger

## Условие

Создай **docker-compose.yml** для 3 сервисов + PostgreSQL + Redis + Jaeger. Настрой сети, volumes, health checks. Запусти `docker-compose up` и проверь взаимодействие.

## Теория

Проектирование локального окружения микросервисов (Docker Compose):
- Изолированная внутренняя сеть: `networks: backend-net`.
- Постоянные хранилища: `volumes: pgdata, redisdata`.
- Зависимости с проверкой готовности: `depends_on: { condition: service_healthy }`.
- Сервисы не должны стартовать до тех пор, пока PostgreSQL и Redis не пройдут Healthcheck!

## Решение по шагам

1. Опишите сервисы PostgreSQL и Redis с Health Check.
2. Опишите all-in-one Jaeger для трассировки.
3. Настройте запуск микросервисов после готовности БД.
4. Проверьте валидность файла docker-compose.

## Код решения

**`docker-compose.yml`**

```yaml
version: '3.8'

networks:
  backend-net:
    driver: bridge

volumes:
  pgdata:
  redisdata:

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret_password
      POSTGRES_DB: micro_db
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d micro_db"]
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    volumes:
      - redisdata:/data
    networks:
      - backend-net
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  jaeger:
    image: jaegertracing/all-in-one:1.55
    ports:
      - "16686:16686" # Web UI
      - "4317:4317"   # OTLP gRPC receiver
    networks:
      - backend-net

  user-service:
    build:
      context: ./services/user-service
    environment:
      DATABASE_URL: "postgres://app:secret_password@postgres:5432/micro_db?sslmode=disable"
      OTEL_EXPORTER_OTLP_ENDPOINT: "jaeger:4317"
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - backend-net

  order-service:
    build:
      context: ./services/order-service
    environment:
      REDIS_ADDR: "redis:6379"
      OTEL_EXPORTER_OTLP_ENDPOINT: "jaeger:4317"
    depends_on:
      redis:
        condition: service_healthy
    networks:
      - backend-net
```

ℹ️ Спецификация Docker Compose с зависимостями service_healthy

**`Терминал`**

```bash
# Запуск инфраструктуры в фоне:
docker compose up -d

# Проверка статуса контейнеров:
docker compose ps
# NAME                     STATUS                    PORTS
# project-jaeger-1         running                   0.0.0.0:4317->4317/tcp, 0.0.0.0:16686->16686/tcp
# project-postgres-1       running (healthy)         5432/tcp
# project-redis-1          running (healthy)         6379/tcp
# project-user-service-1   running                   50051/tcp
# project-order-service-1  running                   50052/tcp
```

## Под капотом

Директива `condition: service_healthy` гарантирует строгий детерминированный порядок инициализации, исключая падения микросервисов с ошибкой `connection refused` при одновременном старте.

## Подводные камни

Хардкодить пароли в `docker-compose.yml`: для production и стейджинга используйте переменные окружения из `.env` файла.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисах рекомендуется использовать единую сеть bridge в Docker Compose?»
**Ответ:** Единая пользовательская сеть bridge обеспечивает встроенный DNS-резолвинг: сервисы обращаются друг к другу по именам контейнеров (`http://postgres:5432`, `jaeger:4317`) без необходимости ручного проброса портов на хостовую машину.
