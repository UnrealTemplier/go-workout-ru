# Опция waitForReady в gRPC: блокирующее ожидание доступности сервера при холодном старте

## Условие

Настройте `waitForReady: true` в service config, чтобы клиент ждал подключения к серверу, а не падал сразу.

## Теория

Семантика опции WaitForReady (Fail-Fast vs Wait-For-Ready):
- **Дефолтное поведение gRPC (Fail-Fast):**
  - Если при отправке RPC соединение с сервером еще не установлено (`TRANSIENT_FAILURE` / `CONNECTING`), вызов мгновенно падает с кодом `codes.Unavailable`.
- **Режим `waitForReady(true)`:**
  - Клиент приостанавливает вызов и ждет успешного установления TCP/TLS сокета вплоть до истечения таймаута контекста (`ctx.Deadline()`).
  - Критически важно при одновременном старте подов в Kubernetes, когда клиент поднялся на 2 секунды раньше сервера.

## Решение по шагам

1. Создайте опцию `grpc.WaitForReady(true)`.
2. Настройте передачу через `grpc.CallOptions` или Service Config.
3. Продемонстрируйте поведение при холодном старте бэкенда.
4. Проверьте отсечение по общему таймауту контекста.

## Код решения

**`wait_for_ready_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/status"
)

func TestWaitForReadyBehavior(t *testing.T) {
	// Подключаемся к несуществующему порту
	conn, err := grpc.NewClient(
		"passthrough://127.0.0.1:59999",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		t.Fatalf("Ошибка создания: %v", err)
	}
	defer conn.Close()

	// 1. Тест с waitForReady(true) и жестким таймаутом контекста 50 мс
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	start := time.Now()
	// Используем CallOption WaitForReady
	errCall := conn.Invoke(ctx, "/test.Service/Ping", nil, nil, grpc.WaitForReady(true))
	elapsed := time.Since(start)

	if status.Code(errCall) != codes.DeadlineExceeded {
		t.Fatalf("Ожидался DeadlineExceeded из-за ожидания подключения, получено: %v", errCall)
	}

	if elapsed < 40*time.Millisecond {
		t.Fatalf("Клиент не ждал подключения: %v", elapsed)
	}

	fmt.Printf("WaitForReady успешно удерживал вызов %v до истечения дедлайна с кодом [%s]!\n",
		elapsed.Round(time.Millisecond), status.Code(errCall))
}
```

ℹ️ Удержание вызова опцией WaitForReady при недоступности сервера


## Под капотом

При включенном `waitForReady` клиентский пикер блокирует горутину на внутреннем условном сигнале `sync.Cond` до тех пор, пока фоновый транспорт gRPC не перейдет в состояние `READY`.

## Подводные камни

Включать `waitForReady: true` без явного `context.WithTimeout`: если сервер никогда не поднимется, вызывающая горутина зависнет навечно.

## На собеседовании

**Вопрос с собеседования:** «В каких сценариях опция waitForReady является обязательной?»
**Ответ:** При пакетной обработке задач (Batch Jobs / CronJob), при холодном старте микросервисов в тестовом окружении и при обращении к серверу во время Rolling Update, когда старый под уже удален, а новый находится на стадии Readiness проверки.
