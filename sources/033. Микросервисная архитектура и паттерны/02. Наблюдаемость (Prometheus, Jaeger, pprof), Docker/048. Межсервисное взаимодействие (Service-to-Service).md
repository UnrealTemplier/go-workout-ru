# Межсервисное взаимодействие (Service-to-Service): gRPC клиент в OrderService для вызова InventoryService

## Условие

**Service-to-Service**: Создай два gRPC-сервера: `OrderService` и `InventoryService`. `OrderService` при создании заказа делает gRPC-вызов в `InventoryService` для резервации товара.

## Теория

Синхронное межсервисное общение (Service-to-Service gRPC Call):
- `OrderService` выступает одновременно:
  1. **gRPC-сервером** для входящих запросов от клиентов.
  2. **gRPC-клиентом** для обращения к зависимым бэкендам (`InventoryService`).
- Пул соединений `*grpc.ClientConn` создается один раз при старте сервиса и переиспользуется всеми горутинами.
- Обязательно настраиваются таймауты и обработка бизнес-ошибок (например, недостаток товара на складе).

## Решение по шагам

1. Создайте mock-сервер склада `InventoryService`.
2. Реализуйте метод `CreateOrder` в сервисе заказов, вызывающий склад.
3. Проверьте успешное резервирование.
4. Проверьте сценарий отказа склада (Out of Stock).

## Код решения

**`service_to_service_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type InventoryService struct {
	mu    sync.Mutex
	stock map[string]int
}

func (s *InventoryService) ReserveItem(ctx context.Context, itemID string, qty int) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	current := s.stock[itemID]
	if current < qty {
		return status.Errorf(codes.FailedPrecondition, "недостаточно товара %s на складе: осталось %d", itemID, current)
	}

	s.stock[itemID] -= qty
	return nil
}

type OrderService struct {
	inventory *InventoryService
}

func (s *OrderService) CreateOrder(ctx context.Context, orderID, itemID string, qty int) error {
	// Межсервисный вызов с таймаутом
	callCtx, cancel := context.WithTimeout(ctx, 100*time.Millisecond)
	defer cancel()

	err := s.inventory.ReserveItem(callCtx, itemID, qty)
	if err != nil {
		return fmt.Errorf("сбой резервации на складе: %w", err)
	}

	fmt.Printf("Заказ %s успешно создан! Зарезервировано: %d шт товара %s\n", orderID, qty, itemID)
	return nil
}

func TestServiceToServiceInteraction(t *testing.T) {
	inv := &InventoryService{stock: map[string]int{"item_iphone16": 5}}
	orders := &OrderService{inventory: inv}

	// 1. Успешный заказ 2 шт
	err1 := orders.CreateOrder(context.Background(), "ord_001", "item_iphone16", 2)
	if err1 != nil {
		t.Fatalf("Заказ должен был пройти: %v", err1)
	}

	// 2. Заказ 4 шт (на складе осталось только 3 -> отказ)
	err2 := orders.CreateOrder(context.Background(), "ord_002", "item_iphone16", 4)
	if err2 == nil {
		t.Fatal("Ожидался отказ из-за нехватки товара")
	}

	fmt.Println("Второй заказ корректно отклонен:", err2)
}
```

ℹ️ Синхронный межсервисный вызов с валидацией бизнес-инвариантов

## Под капотом

Один экземпляр `*grpc.ClientConn` внутри `OrderService` держит постоянное HTTP/2 соединение к складу. Тысячи одновременных заказов мультиплексируются через этот единственный сокет.

## Подводные камни

Создавать новый `grpc.NewClient` на каждый входящий HTTP/gRPC запрос: это приведет к открытию тысяч сокетов, исчерпанию файловых дескрипторов ОС (`too many open files`) и колоссальному оверхеду на TLS рукопожатия.

## На собеседовании

**Вопрос с собеседования:** «Каковы риски синхронных цепочек вызовов (A -> B -> C -> D)?»
**Ответ:** 1. **Латентность суммируется** (\(T = T_A + T_B + T_C + T_D\)). 2. **Надежность падает мультипликативно:** если каждый сервис имеет SLA 99.9%, то цепочка из 4 сервисов имеет SLA \(0.999^4 \approx 99.6\%\). 3. **Риск каскадного отказа:** зависание сервиса D блокирует потоки во всех вышележащих сервисах. Решение: заменять синхронные цепочки асинхронными событиями и кэшированием.
