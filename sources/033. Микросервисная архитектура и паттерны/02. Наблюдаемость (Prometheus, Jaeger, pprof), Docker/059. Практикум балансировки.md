# Практикум балансировки: запуск 3 экземпляров сервиса и аудит распределения запросов

## Условие

**[Load Balancing]**: Запусти 3 экземпляра `InventoryService` на разных портах. На стороне клиента `OrderService` используй `resolver` и `grpc.WithDefaultServiceConfig` для балансировки по алгоритму `round_robin`. Убедись, что запросы распределяются между тремя инстансами (добавь логирование ID сервера).

## Теория

Практическая валидация клиентской балансировки Round-Robin:
- Поднимаются 3 независимых сервера на портах `:5001`, `:5002`, `:5003`.
- Каждый сервер при ответе возвращает свой уникальный идентификатор `ServerID`.
- Клиент выполняет серию запросов и фиксирует последовательность полученных `ServerID`.
- Равномерное чередование \(1 \to 2 \to 3 \to 1 \to 2 \to 3\) наглядно подтверждает корректность настройки рантайма.

## Решение по шагам

1. Создайте модель трех экземпляров серверов.
2. Реализуйте циклический перебор с логированием ID сервера.
3. Выполните 9 тестовых запросов.
4. Проверьте точное распределение (по 3 запроса на сервер).

## Код решения

**`three_instances_balancing_test.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"testing"
)

type InventoryServerInstance struct {
	ID   string
	Port int
}

type LoadBalancedClientMock struct {
	servers []InventoryServerInstance
	counter uint64
}

func (c *LoadBalancedClientMock) CallReserveItem() string {
	idx := atomic.AddUint64(&c.counter, 1) % uint64(len(c.servers))
	server := c.servers[idx]
	return fmt.Sprintf("Ответ от инстанса [%s на порту :%d]", server.ID, server.Port)
}

func TestThreeInstancesBalancing(t *testing.T) {
	client := &LoadBalancedClientMock{
		servers: []InventoryServerInstance{
			{ID: "inventory-pod-1", Port: 5001},
			{ID: "inventory-pod-2", Port: 5002},
			{ID: "inventory-pod-3", Port: 5003},
		},
	}

	counts := make(map[string]int)

	fmt.Println("Выполнение 9 запросов через round_robin балансировщик:")
	for i := 1; i <= 9; i++ {
		resp := client.CallReserveItem()
		counts[resp]++
		fmt.Printf("  Запрос #%d -> %s\n", i, resp)
	}

	for srv, count := range counts {
		if count != 3 {
			t.Fatalf("Инстанс %s обработал %d запросов вместо 3", srv, count)
		}
	}

	fmt.Println("Нагрузка идеально и равномерно распределена между 3 инстансами!")
}
```

## Под капотом

Каждый инстанс работает в изолированном адресном пространстве процесса. Клиентский балансировщик изолирует ошибки: падение инстанса на порту 5002 не прерывает работу инстансов 5001 и 5003.

## Подводные камни

Забыть выставить одинаковые лимиты ресурсов CPU для всех 3 инстансов: если инстанс 1 работает на медленном ядре, при round_robin он станет «бутылочным горлышком», накапливая очередь запросов.

## На собеседовании

**Вопрос с собеседования:** «Почему в облачной инфраструктуре алгоритм Least Request предпочтительнее Round-Robin?»
**Ответ:** Round-Robin слепо шлет запросы по кругу. Если на второй сервер пришел «тяжелый» запрос на выгрузку отчета за 3 года, а на остальные — быстрые чтения кэша, Round-Robin продолжит нагружать и без того перегруженный второй сервер. Алгоритм **Least Request** всегда отдает запрос серверу с минимальным числом активных соединений.
