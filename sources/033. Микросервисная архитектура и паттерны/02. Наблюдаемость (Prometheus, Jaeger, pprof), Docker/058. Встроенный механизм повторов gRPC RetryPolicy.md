# Встроенный механизм повторов gRPC RetryPolicy: декларативная конфигурация без ручных циклов

## Условие

**Встроенный Retry gRPC**: Тебе не нужно писать цикл `for` для повторных запросов на клиенте. В gRPC есть ServiceConfig. Передай при создании клиента JSON-конфиг (через `grpc.WithDefaultServiceConfig`), в котором укажи политику повторов (RetryPolicy): например, делать 3 попытки при коде `Unavailable` с экспоненциальной задержкой.

## Теория

Спецификация gRPC Retry Policy в Service Config:
- Параметры объекта `retryPolicy`:
  - `maxAttempts`: максимальное число попыток (включая первую).
  - `initialBackoff`: задержка перед первой повторной попыткой (`"0.1s"`).
  - `maxBackoff`: потолок задержки (`"1s"`).
  - `backoffMultiplier`: множитель экспоненты (`2.0`).
  - `retryableStatusCodes`: массив кодов, например `["UNAVAILABLE"]`.
- Ядро gRPC автоматически перехватывает ошибки сокета и выполняет прозрачный повтор без единой строчки прикладного кода!

## Решение по шагам

## Код решения

**`grpc_builtin_retry_config_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type RetryPolicy struct {
	MaxAttempts          int      `json:"maxAttempts"`
	InitialBackoff       string   `json:"initialBackoff"`
	MaxBackoff           string   `json:"maxBackoff"`
	BackoffMultiplier    float64  `json:"backoffMultiplier"`
	RetryableStatusCodes []string `json:"retryableStatusCodes"`
}

type MethodConfig struct {
	Name        []map[string]string `json:"name"`
	RetryPolicy RetryPolicy         `json:"retryPolicy"`
}

type ServiceConfigRoot struct {
	MethodConfig []MethodConfig `json:"methodConfig"`
}

func GenerateServiceConfigJSON(serviceName string) (string, error) {
	cfg := ServiceConfigRoot{
		MethodConfig: []MethodConfig{
			{
				Name: []map[string]string{{"service": serviceName}},
				RetryPolicy: RetryPolicy{
					MaxAttempts:          3,
					InitialBackoff:       "0.1s",
					MaxBackoff:           "1.0s",
					BackoffMultiplier:    2.0,
					RetryableStatusCodes: []string{"UNAVAILABLE"},
				},
			},
		},
	}

	bytes, err := json.MarshalIndent(cfg, "", "  ")
	return string(bytes), err
}

func TestServiceConfigRetryGeneration(t *testing.T) {
	jsonStr, err := GenerateServiceConfigJSON("order.v1.OrderService")
	if err != nil {
		t.Fatalf("Ошибка генерации: %v", err)
	}

	fmt.Printf("Сгенерированный декларативный конфиг gRPC Retry:\n%s\n", jsonStr)
}
```

## Под капотом

Встроенный механизм ретраев gRPC отслеживает HTTP/2 трейлеры `grpc-previous-rpc-attempts`, информируя сервер о том, какая именно попытка запроса сейчас обрабатывается.

## Подводные камни

Повторять стриминговые RPC с отправленными сообщениями: если клиент уже отправил часть данных в `ClientStream`, автоматический ретрай невозможен, так как тело запроса не может быть безопасно перемотано назад.

## На собеседовании

**Вопрос с собеседования:** «Что такое Hedging в gRPC Service Config и чем он отличается от Retry?»
**Ответ:** При обычном Retry повтор отправляется ТОЛЬКО ПОСЛЕ получения ошибки. При **Hedging** (хеджировании) клиент отправляет второй идентичный запрос параллельно, если первый не ответил за заданное время (например за 50 мс), и берет тот ответ, который пришел быстрее, срезая латентность 99-го перцентиля (Tail Latency).
