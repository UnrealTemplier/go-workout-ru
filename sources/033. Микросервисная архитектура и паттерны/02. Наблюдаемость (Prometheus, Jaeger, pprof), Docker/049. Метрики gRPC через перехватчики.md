# Метрики gRPC через перехватчики: автоматический сбор RPS, времени ответа и кодов ошибок

## Условие

Добавьте метрики (Prometheus) для gRPC методов: количество запросов, длительность, ошибки. Используйте перехватчики для сбора.

## Теория

Автоматическая инструментация через gRPC Unary Server Interceptor:
- Перехватчик засекает время перед вызовом хэндлера:
  `start := time.Now()`
- Вызывает `resp, err := handler(ctx, req)`
- Определяет статус-код ответа через `status.Code(err)`.
- Фиксирует метрики:
  - `requests_total.WithLabelValues(method, code).Inc()`
  - `request_duration_seconds.WithLabelValues(method).Observe(duration.Seconds())`

## Решение по шагам

1. Создайте Unary Server Interceptor метрик.
2. Извлеките имя gRPC-метода и статус ответа.
3. Просимулируйте успешный и ошибочный вызовы.
4. Проверьте фиксацию метрик в реестре.

## Код решения

**`grpc_metrics_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type RecordedMetric struct {
	Method   string
	Code     string
	Duration time.Duration
}

type MetricsCollectorMock struct {
	records []RecordedMetric
}

func (m *MetricsCollectorMock) Observe(method, code string, d time.Duration) {
	m.records = append(m.records, RecordedMetric{
		Method:   method,
		Code:     code,
		Duration: d,
	})
}

func UnaryMetricsInterceptor(collector *MetricsCollectorMock) grpc.UnaryServerInterceptor {
	return func(
		ctx context.Context,
		req any,
		info *grpc.UnaryServerInfo,
		handler grpc.UnaryHandler,
	) (any, error) {
		start := time.Now()
		resp, err := handler(ctx, req)
		elapsed := time.Since(start)

		code := status.Code(err).String()
		collector.Observe(info.FullMethod, code, elapsed)

		return resp, err
	}
}

func TestMetricsInterceptor(t *testing.T) {
	collector := &MetricsCollectorMock{}
	interceptor := UnaryMetricsInterceptor(collector)

	// 1. Успешный вызов
	okHandler := func(ctx context.Context, req any) (any, error) {
		time.Sleep(5 * time.Millisecond)
		return "OK", nil
	}
	_, _ = interceptor(context.Background(), nil, &grpc.UnaryServerInfo{FullMethod: "/order.v1/Create"}, okHandler)

	// 2. Сбойный вызов
	errHandler := func(ctx context.Context, req any) (any, error) {
		return nil, status.Error(codes.InvalidArgument, "некорректный ID")
	}
	_, _ = interceptor(context.Background(), nil, &grpc.UnaryServerInfo{FullMethod: "/order.v1/Create"}, errHandler)

	if len(collector.records) != 2 {
		t.Fatalf("Ожидалось 2 записи метрик")
	}

	fmt.Println("Собранные метрики вызовов:")
	for _, r := range collector.records {
		fmt.Printf("  • Метод: %-18s | Code: %-15s | Latency: %v\n", r.Method, r.Code, r.Duration.Round(time.Millisecond))
	}
}
```

## Под капотом

Официальная библиотека `go-grpc-prometheus` предварительно инициализирует лейблы для всех зарегистрированных методов gRPC сервера, предотвращая пропуски метрик на графиках до первого вызова.

## Подводные камни

Включать подробные гистограммы (`EnableHandlingTimeHistogram`) на сервере с 10 000 RPS без ограничения числа бакетов: каждая комбинация лейблов умножается на число бакетов, приводя к перерасходу ОЗУ сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как мониторить стриминговые RPC в Prometheus?»
**Ответ:** Для серверного, клиентского и двунаправленного стриминга используются интерцепторы `StreamServerInterceptor`, считающие отдельные метрики: `grpc_server_msg_received_total` (число сообщений в стриме) и `grpc_server_msg_sent_total`, а также общую продолжительность открытого стрима.
