# Принципы 12-Factor App: многоуровневая конфигурация через YAML и переопределение переменными окружения

## Условие

**12-Factor App (Конфигурация)**: Микросервис не должен содержать захардкоженных портов или паролей от БД. Используй библиотеку `github.com/spf13/viper` или стандартный `os.Getenv`. Напиши парсер конфига, который читает настройки из файла `config.yaml`, но может быть переопределен переменными окружения.

## Теория

Фактор III методологии 12-Factor App (Конфигурация):
- Конфигурация приложения строго отделяется от исполняемого кода.
- Приоритеты загрузки конфигурации (от высшего к низшему):
  1. Флаги командной строки CLI (`--port=8080`).
  2. Переменные окружения ОС (`APP_PORT=8080`).
  3. Конфигурационный файл (`config.yaml`).
  4. Дефолтные значения в коде.
- Переопределение через переменные окружения позволяет запускать **один и тот же Docker-образ** на dev, staging и production окружениях.

## Решение по шагам

1. Создайте структуру конфигурации приложения.
2. Реализуйте чтение дефолтных значений.
3. Реализуйте переопределение из переменных окружения.
4. Протестируйте приоритет переменных ОС.

## Код решения

**`twelve_factor_config_test.go`**

```go
package main

import (
	"fmt"
	"os"
	"strconv"
	"testing"
)

type AppConfig struct {
	Port     int
	DBUrl    string
	LogLevel string
}

func LoadConfig() AppConfig {
	// 1. Дефолтные значения (или прочитанные из config.yaml)
	cfg := AppConfig{
		Port:     50051,
		DBUrl:    "postgres://localhost:5432/dev_db",
		LogLevel: "INFO",
	}

	// 2. Переопределение переменными окружения (12-Factor App)
	if val := os.Getenv("APP_PORT"); val != "" {
		if p, err := strconv.Atoi(val); err == nil {
			cfg.Port = p
		}
	}

	if val := os.Getenv("APP_DATABASE_URL"); val != "" {
		cfg.DBUrl = val
	}

	if val := os.Getenv("APP_LOG_LEVEL"); val != "" {
		cfg.LogLevel = val
	}

	return cfg
}

func Test12FactorConfigOverride(t *testing.T) {
	// Имитируем переменные окружения Kubernetes Pod
	_ = os.Setenv("APP_PORT", "9090")
	_ = os.Setenv("APP_DATABASE_URL", "postgres://prod-cluster.internal:5432/orders_db")
	_ = os.Setenv("APP_LOG_LEVEL", "DEBUG")
	defer func() {
		_ = os.Unsetenv("APP_PORT")
		_ = os.Unsetenv("APP_DATABASE_URL")
		_ = os.Unsetenv("APP_LOG_LEVEL")
	}()

	cfg := LoadConfig()

	if cfg.Port != 9090 || cfg.LogLevel != "DEBUG" || cfg.DBUrl != "postgres://prod-cluster.internal:5432/orders_db" {
		t.Fatalf("Переменные окружения не переопределили конфиг: %+v", cfg)
	}

	fmt.Printf("12-Factor конфигурация успешно загружена:\n")
	fmt.Printf("  • Port:     %d (переопределено из ENV)\n", cfg.Port)
	fmt.Printf("  • DB URL:   %s\n", cfg.DBUrl)
	fmt.Printf("  • LogLevel: %s\n", cfg.LogLevel)
}
```

## Под капотом

В Kubernetes переменные окружения инжектируются в под из ConfigMap и Secret через директиву `envFrom: [configMapRef, secretRef]`.

## Подводные камни

Хранить секреты (токены API, приватные ключи) в файле `config.yaml` в Git-репозитории: секреты попадут в историю коммитов. Используйте HashiCorp Vault или Kubernetes Secrets.

## На собеседовании

**Вопрос с собеседования:** «Почему популярна библиотека spf13/viper для 12-Factor конфигурации?»
**Ответ:** `viper` умеет автоматически связывать JSON/YAML конфиги с переменными окружения через `viper.SetEnvPrefix("APP")` и `viper.AutomaticEnv()`, а также поддерживает динамический Hot Reload из etcd/Consul через `viper.WatchRemoteConfig()`.
