# Каскадная трассировка через 3 микросервиса: граф вызовов API Gateway -> User Service -> Auth Service

## Условие

**Distributed Tracing (OpenTelemetry)**: У тебя 3 микросервиса: `API-Gateway` -> `User-Service` -> `Auth-Service`. Установи OpenTelemetry. Настрой проброс TraceID (через метаданные контекста gRPC) сквозь все три сервиса. (Можно поднять локально Jaeger в Docker и посмотреть на красивые графики "путешествия" запроса).

## Теория

Иерархия распределенного графа спанов (Span Tree Hierarchy):
- Корневой спан: `[API-Gateway: POST /login]` (SpanID: `0001`, Parent: `nil`)
  - Дочерний спан: `[User-Service: VerifyUser]` (SpanID: `0002`, Parent: `0001`)
    - Внучатый спан: `[Auth-Service: CheckPasswordHash]` (SpanID: `0003`, Parent: `0002`)
- Все 3 спана имеют строго **одинаковый глобальный TraceID**.
- Если `Auth-Service` отвечает 250 мс, в Jaeger UI сразу видно, что именно этот спан занимает 90% времени родительских вызовов.

## Решение по шагам

1. Создайте модель связного графа спанов.
2. Смоделируйте сквозную передачу контекста через 3 микросервиса.
3. Проверьте отношение родитель-потомок (Parent-Child).
4. Протестируйте целостность дерева трейсинга.

## Код решения

**`three_service_trace_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TraceHop struct {
	ServiceName string
	SpanID      string
	ParentSpan  string
	TraceID     string
}

func TestCascadeThreeHopTrace(t *testing.T) {
	globalTraceID := "c4f00112233445566778899aabbccdde"

	// Hop 1: Gateway создает корневой спан
	hop1 := TraceHop{
		ServiceName: "api-gateway",
		SpanID:      "span_01_root",
		ParentSpan:  "none",
		TraceID:     globalTraceID,
	}

	// Hop 2: User-Service создает дочерний спан
	hop2 := TraceHop{
		ServiceName: "user-service",
		SpanID:      "span_02_user",
		ParentSpan:  hop1.SpanID,
		TraceID:     globalTraceID,
	}

	// Hop 3: Auth-Service создает дочерний спан к User-Service
	hop3 := TraceHop{
		ServiceName: "auth-service",
		SpanID:      "span_03_auth",
		ParentSpan:  hop2.SpanID,
		TraceID:     globalTraceID,
	}

	tree := []TraceHop{hop1, hop2, hop3}

	fmt.Println("Иерархическое дерево распределенного трейса:")
	for i, h := range tree {
		fmt.Printf("  [%d] Service: %-15s | Span: %-12s | Parent: %-12s | TraceID: %s\n",
			i+1, h.ServiceName, h.SpanID, h.ParentSpan, h.TraceID)
		if h.TraceID != globalTraceID {
			t.Fatalf("TraceID разорван на сервисе %s", h.ServiceName)
		}
	}

	if tree[1].ParentSpan != tree[0].SpanID || tree[2].ParentSpan != tree[1].SpanID {
		t.Fatal("Нарушена иерархия родительских спанов")
	}
}
```

## Под капотом

Внутри OpenTelemetry контекст передается через `context.Context`. Функция `trace.ContextWithSpan(ctx, span)` привязывает спан к контексту, а интерцепторы автоматически сериализуют его при исходящем сетевом вызове.

## Подводные камни

Терять контекст при запуске асинхронных горутин: если вызвать `go doAsyncTask()` без передачи контекста или с новым `context.Background()`, асинхронная задача выпадет из общего графа трейсинга.

## На собеседовании

**Вопрос с собеседования:** «Как связать трассировку синхронного вызова gRPC с асинхронным сообщением в Kafka?»
**Ответ:** При публикации сообщения в Kafka продюсер инжектирует TraceID в бинарные заголовки `kafka.RecordHeader{Key: "traceparent", Value: ...}`. Консьюмер Kafka извлекает заголовок и создает спан с типом связи `trace.Link`, соединяя синхронный HTTP/gRPC трейс с асинхронной обработкой в брокере.
