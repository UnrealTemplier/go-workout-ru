# Проблема Connection Draining при деплое в Kubernetes: безопасное осушение активных сокетов

## Условие

Изучите проблему "connection draining" при деплое: как корректно завершить активные RPC перед остановкой пода?

## Теория

Фазы осушения соединений (Connection Draining Lifecycle) в Kubernetes:
1. **Фаза 1: Удаление из Endpoints.** Kubernetes контроллер удаляет IP удаляемого пода из сервиса `Endpoints`. Это занимает 1–2 секунды на распространение iptables по нодам.
2. **Фаза 2: preStop Hook.** Под запускает команду `sleep 5`. В это время под продолжает нормально отвечать на долетающие запросы!
3. **Фаза 3: Отправка SIGTERM.** Сервис ловит сигнал и запускает `server.GracefulStop()`.
4. **Фаза 4: GOAWAY Frame.** gRPC сервер шлет клиентам фрейм `GOAWAY`, клиенты плавно переключаются на другие поды.
5. **Фаза 5: Завершение.** Активные стримы дорабатывают, и процесс чисто завершается.

## Решение по шагам

1. Опишите конфигурацию preStop hook в манифесте пода.
2. Смоделируйте перехват SIGTERM и вызов GracefulStop.
3. Проверьте отсутствие ошибок у клиентов во время деплоя.
4. Продемонстрируйте этапы жизненного цикла.

## Код решения

**`k8s_prestop_draining.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 30 # Максимальное время на осушение
      containers:
      - name: app
        image: company/order-service:v1.2.0
        lifecycle:
          preStop:
            exec:
              # Даем 5 секунд на удаление IP пода из iptables всех нод кластера
              command: ["/bin/sh", "-c", "sleep 5"]
```

ℹ️ Настройка preStop hook для защиты от сетевых сбоев при Rolling Update

**`connection_draining_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

func SimulateKubernetesPodTermination(drainingDelay, rpcTime time.Duration) error {
	fmt.Println("1. K8s переводит под в Terminating и инициирует preStop sleep...")
	time.Sleep(drainingDelay)

	fmt.Println("2. Запущен server.GracefulStop(): отправлен HTTP/2 GOAWAY...")
	activeRPCCompleted := make(chan bool)
	go func() {
		time.Sleep(rpcTime)
		activeRPCCompleted <- true
	}()

	<-activeRPCCompleted
	fmt.Println("3. Все активные RPC завершены! Под чисто остановлен без единой ошибки 502/503.")
	return nil
}

func TestConnectionDraining(t *testing.T) {
	err := SimulateKubernetesPodTermination(20*time.Millisecond, 15*time.Millisecond)
	if err != nil {
		t.Fatalf("Сбой осушения: %v", err)
	}
}
```

## Под капотом

Если процесс не завершился в течение `terminationGracePeriodSeconds` (дефолт 30 сек), ядро Linux отправляет неотлавливаемый сигнал `SIGKILL` (kill -9), принудительно уничтожая контейнер.

## Подводные камни

Ставить `terminationGracePeriodSeconds: 5` при наличии долгоживущих стримов или тяжелых транзакций в 10 секунд: Kubernetes убьет под посреди выполнения операции, оставив базу в несогласованном состоянии.

## На собеседовании

**Вопрос с собеседования:** «Почему клиенты получают ошибку Connection Refused во время Rolling Update, если GracefulStop настроен идеально?»
**Ответ:** Потому что не был настроен `preStop hook` со `sleep`. Kubelet шлет SIGTERM сервису **одновременно** с удалением IP из Endpoints. Но распространение iptables правил по 100 нодам кластера запаздывает на пару секунд: ноды продолжают слать новые запросы на под, который уже закрыл сокет слушателя.
