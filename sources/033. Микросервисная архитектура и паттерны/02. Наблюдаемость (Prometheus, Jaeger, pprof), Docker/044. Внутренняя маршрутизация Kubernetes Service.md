# Внутренняя маршрутизация Kubernetes Service: резолвинг по FQDN имени и виртуальная балансировка

## Условие

Используйте **Kubernetes Service** (ClusterIP) и подключайтесь по DNS-имени (`user-service.default.svc.cluster.local`). Kubernetes сам балансирует нагрузку.

## Теория

Формат полного доменного имени FQDN (Fully Qualified Domain Name) в Kubernetes:
- Синтаксис: `<service-name>.<namespace>.svc.<cluster-domain>`:
  `user-service.default.svc.cluster.local:50051`
  - `user-service`: имя Service ресурса.
  - `default`: пространство имен (Namespace).
  - `svc`: тип объекта (сервис).
  - `cluster.local`: локальный домен кластера.
- Внутри одного namespace достаточно короткого имени `user-service:50051`.
- При резолвинге FQDN CoreDNS возвращает виртуальный ClusterIP, а сетевой стек ядра выполняет балансировку по живым репликам.

## Решение по шагам

1. Создайте структуру парсера FQDN адреса.
2. Продемонстрируйте извлечение сервиса и namespace.
3. Настройте подключение клиента по FQDN адресу.
4. Проверьте корректность конфигурации.

## Код решения

**`k8s_fqdn_resolver_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type FQDNInfo struct {
	Service   string
	Namespace string
	Domain    string
}

func ParseK8sFQDN(target string) (*FQDNInfo, error) {
	// target: user-service.production.svc.cluster.local:50051
	parts := strings.Split(target, ":")
	host := parts[0]

	tokens := strings.Split(host, ".")
	if len(tokens) < 5 || tokens[2] != "svc" {
		return nil, fmt.Errorf("некорректный K8s FQDN: %s", target)
	}

	return &FQDNInfo{
		Service:   tokens[0],
		Namespace: tokens[1],
		Domain:    strings.Join(tokens[2:], "."),
	}, nil
}

func TestK8sFQDNResolution(t *testing.T) {
	targetURI := "order-service.production.svc.cluster.local:50051"

	info, err := ParseK8sFQDN(targetURI)
	if err != nil {
		t.Fatalf("Ошибка разбора: %v", err)
	}

	if info.Service != "order-service" || info.Namespace != "production" {
		t.Fatalf("Некорректный результат: %+v", info)
	}

	fmt.Printf("FQDN адрес успешно распознан:\n")
	fmt.Printf("  • Сервис:    %s\n", info.Service)
	fmt.Printf("  • Namespace: %s\n", info.Namespace)
	fmt.Printf("  • Зона:      %s\n", info.Domain)
}
```

## Под капотом

В файле `/etc/resolv.conf` каждого пода автоматически прописывается `search default.svc.cluster.local svc.cluster.local cluster.local`. Благодаря этому запрос к `user-service` автоматически дополняется CoreDNS до полного FQDN.

## Подводные камни

Использовать короткое имя `user-service` при межпространственных вызовах (Cross-Namespace): если вызывающий сервис в namespace `frontend`, а целевой в `backend`, короткое имя не найдет сервис! Обязательно указывать namespace: `user-service.backend`.

## На собеседовании

**Вопрос с собеседования:** «Почему при вызове gRPC сервиса через ClusterIP не работает балансировка по подам при обычном DNS запросе?»
**Ответ:** gRPC открывает постоянное HTTP/2 TCP-соединение к полученному IP адресу. Стандартный ClusterIP привязывает это TCP-соединение к **одному поду**. Все последующие 100 000 RPC запросов пойдут в этот же под через то же самое TCP-соединение. Для решения проблемы используют Headless Services (`clusterIP: None`) или балансировку через Envoy/Istio Service Mesh.
