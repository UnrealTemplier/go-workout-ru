# Предохранитель Circuit Breaker при сбое зависимостей: защита от каскадного падения сервисов

## Условие

**Circuit Breaker (Предохранитель)**: `Auth-Service` завис или отвечает медленно. `User-Service` не должен лечь вслед за ним (каскадный сбой). Используй библиотеку `github.com/sony/sonyflake` или `gobreaker`. Настрой предохранитель: если 5 запросов подряд упали с ошибкой, не делай следующие запросы, а сразу отдавай ошибку (или fallback-значение), пока тот сервис не оживет.

## Теория

Предотвращение каскадного коллапса (Cascading Failure Prevention):
- Если `Auth-Service` завис, каждый вызов из `User-Service` блокирует горутину на время таймаута (например, 2 сек).
- При потоке 500 RPS в `User-Service` за 2 секунды образуется 1 000 зависших горутин, переполняя память и сокеты.
- Circuit Breaker размыкает цепь после 5 ошибок подряд:
  - Все последующие запросы мгновенно отклоняются локально за 0.05 мс.
  - `User-Service` продолжает обслуживать запросы других методов без деградации.

## Решение по шагам

1. Настройте `gobreaker.CircuitBreaker`.
2. Задайте правило размыкания после 5 последовательных сбоев.
3. Смоделируйте 5 ошибок авторизации.
4. Убедитесь в мгновенном возврате ошибки предохранителя.

## Код решения

**`cascading_failure_protection_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"

	"github.com/sony/gobreaker"
)

type AuthServiceCaller struct {
	cb *gobreaker.CircuitBreaker
}

func (c *AuthServiceCaller) AuthenticateUser(token string, authDead bool) (string, error) {
	res, err := c.cb.Execute(func() (any, error) {
		if authDead {
			return nil, fmt.Errorf("auth-service 504 Gateway Timeout")
		}
		return "USER_ID_42", nil
	})

	if err != nil {
		return "", err
	}
	return res.(string), nil
}

func TestCascadingFailurePrevention(t *testing.T) {
	st := gobreaker.Settings{
		Name:        "AuthServiceBreaker",
		MaxRequests: 1,
		Timeout:     50 * time.Millisecond,
		ReadyToTrip: func(counts gobreaker.Counts) bool {
			return counts.ConsecutiveFailures >= 5
		},
	}

	caller := &AuthServiceCaller{cb: gobreaker.NewCircuitBreaker(st)}

	// 5 сбоев подряд
	for i := 1; i <= 5; i++ {
		_, _ = caller.AuthenticateUser("invalid_token", true)
	}

	// 6-й вызов мгновенно отклоняется
	start := time.Now()
	_, err := caller.AuthenticateUser("valid_token", true)
	elapsed := time.Since(start)

	if err != gobreaker.ErrOpenState {
		t.Fatalf("Ожидался ErrOpenState, получено: %v", err)
	}

	if elapsed > 2*time.Millisecond {
		t.Fatalf("Отказ должен быть мгновенным: %v", elapsed)
	}

	fmt.Printf("Circuit Breaker успешно спас сервис: 6-й вызов отсечен за %v с ошибкой: %v\n", elapsed, err)
}
```

## Под капотом

Быстрый локальный отказ возвращает заранее аллоцированную ошибку-синглтон `gobreaker.ErrOpenState`, не вызывая дополнительных аллокаций памяти в куче.

## Подводные камни

Использовать одинаковые таймауты и параметры Circuit Breaker для всех сервисов: критические платежные методы требуют более жестких порогов, чем второстепенные сервисы рекомендаций.

## На собеседовании

**Вопрос с собеседования:** «Как совместить Circuit Breaker с Fallback механизмом?»
**Ответ:** В блоке `if err == gobreaker.ErrOpenState` вызывается функция деградации: например, выдача базовых прав доступа гостя, чтение кэшированного профиля из Redis или возврат пустого списка баннеров, предотвращая появление ошибки на экране пользователя.
