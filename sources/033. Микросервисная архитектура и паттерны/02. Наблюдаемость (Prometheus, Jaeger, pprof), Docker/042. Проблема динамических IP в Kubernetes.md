# Проблема динамических IP в Kubernetes: абстракция виртуальных IP ClusterIP и ядро kube-proxy

## Условие

Изучите проблему: в Kubernetes поды имеют динамические IP-адреса. Как клиенту подключиться к сервису, не зная конкретных IP?

## Теория

Архитектура виртуальной адресации в Kubernetes:
- Поды эфемерны: при падении, перезапуске или скейлинге под получает новый случайный IP из подсети ноды (`10.244.x.x`).
- **Решение проблемы (Kubernetes Service & ClusterIP):**
  1. Создается объект `Service` с постоянным виртуальным IP (ClusterIP), например `10.96.0.100`.
  2. Этот IP никогда не меняется на протяжении жизни сервиса.
  3. Внутренний DNS Kubernetes (CoreDNS) сопоставляет доменное имя `order-service` с адресом ClusterIP.
  4. Сетевой агент **kube-proxy** на каждой ноде настраивает правила **IPVS / iptables**, перенаправляя пакеты с виртуального ClusterIP на реальные динамические IP подов.

## Решение по шагам

1. Создайте модель виртуального сервиса ClusterIP.
2. Смоделируйте динамическое изменение IP адресов подов.
3. Проверьте стабильность обращения клиента по единому имени.
4. Протестируйте абстракцию от эфемерных IP.

## Код решения

**`clusterip_abstraction_test.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"testing"
)

type K8sPod struct {
	Name string
	IP   string
}

type ClusterIPService struct {
	mu           sync.RWMutex
	ServiceName  string
	VirtualVIP   string
	activePodIPs []string
}

func (s *ClusterIPService) UpdateEndpoints(pods []K8sPod) {
	s.mu.Lock()
	defer s.mu.Unlock()
	var ips []string
	for _, p := range pods {
		ips = append(ips, p.IP)
	}
	s.activePodIPs = ips
}

func (s *ClusterIPService) RouteCall() (string, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	if len(s.activePodIPs) == 0 {
		return "", fmt.Errorf("нет доступных подов")
	}
	// kube-proxy случайный выбор пода из пула IPVS
	targetIP := s.activePodIPs[rand.Intn(len(s.activePodIPs))]
	return targetIP, nil
}

func TestClusterIPStability(t *testing.T) {
	svc := &ClusterIPService{
		ServiceName: "user-service",
		VirtualVIP:  "10.96.42.100", // Постоянный виртуальный адрес
	}

	// Поколение подов #1
	svc.UpdateEndpoints([]K8sPod{
		{Name: "user-pod-1", IP: "10.244.1.5"},
		{Name: "user-pod-2", IP: "10.244.2.8"},
	})

	// Клиент обращается СТРОГО к постоянному имени user-service
	target1, _ := svc.RouteCall()
	fmt.Printf("1. Запрос к user-service (%s) смаршрутизирован на реальный под: %s\n",
		svc.VirtualVIP, target1)

	// Поды упали и пересоздались с новыми IP (Rolling Update)
	svc.UpdateEndpoints([]K8sPod{
		{Name: "user-pod-3", IP: "10.244.3.99"},
		{Name: "user-pod-4", IP: "10.244.4.101"},
	})

	target2, _ := svc.RouteCall()
	fmt.Printf("2. После перезапуска подов клиент продолжает вызывать %s, попав на новый IP: %s\n",
		svc.ServiceName, target2)

	if target2 != "10.244.3.99" && target2 != "10.244.4.101" {
		t.Fatalf("Некорректная маршрутизация: %s", target2)
	}
}
```

## Под капотом

ClusterIP не существует как физический сетевой интерфейс на хосте. Ядро Linux перехватывает пакеты к этому IP через цепочки `KUBE-SERVICES` в `iptables` и выполняет DNAT подмену на адрес целевого пода.

## Подводные камни

Пытаться пинговать (`ping`) ClusterIP: он не отвечает на ICMP Echo Request пакеты, так как iptables обрабатывает только TCP/UDP порты.

## На собеседовании

**Вопрос с собеседования:** «Почему в крупных кластерах kube-proxy переводят из режима iptables в режим IPVS?»
**Ответ:** Режим iptables имеет сложность поиска правил \(O(N)\) от числа сервисов: при 10 000 подов перестройка правил занимает секунды и грузит CPU. IPVS (IP Virtual Server) использует хэш-таблицы в ядре Linux со сложностью поиска \(O(1)\), масштабируясь до сотен тысяч сервисов без деградации скорости.
