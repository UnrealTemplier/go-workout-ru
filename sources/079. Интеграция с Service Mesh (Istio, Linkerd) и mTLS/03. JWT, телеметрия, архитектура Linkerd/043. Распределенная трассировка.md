# Распределенная трассировка: интеграция Istio с Jaeger и Zipkin

## Условие

Istio автоматически инжектирует trace headers (x-b3-traceid, x-b3-spanid). Настройте Jaeger/Zipkin для сбора traces. Реализуйте в Go-сервисе передачу span context в фоновые задачи.

### Исходная формулировка

**Istio distributed tracing**: Istio автоматически инжектирует trace headers (x-b3-traceid, x-b3-spanid). Настройте Jaeger/Zipkin для сбора traces.

## Теория

В распределенных системах единственный способ найти 'бутылочное горлышко' (bottleneck) — анализ спанов в Jaeger. Envoy Ingress Gateway создает корневой спан (Server Span) и пересылает его в Jaeger Collector по протоколу OTLP/gRPC (порт 4317). Когда Go-приложение принимает запрос, оно должно пробросить контекст трассировки в любые фоновые операции (Worker Pools, очереди сообщений Kafka), чтобы асинхронные задачи не выпадали из общего графа вызовов.

## Решение по шагам

Изучите схему доставки трейсов: Envoy -> Jaeger Collector -> ElasticSearch/ClickHouse.
Напишите Go-сервис, принимающий сетевой вызов и запускающий асинхронный воркер.
Обеспечьте корректное наследование TraceID при создании фоновой горутины.
Проверьте, что родительский контекст не прерывается отменой HTTP-запроса.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
	"time"
)

type asyncTraceKey struct{}

type AsyncTraceContext struct {
	TraceID string
	SpanID  string
}

// DetachedContextWithTrace создает независимый контекст для горутины,
// сохраняя метаданные трассировки, но отвязываясь от таймаута входящего HTTP-запроса.
func DetachedContextWithTrace(r *http.Request) context.Context {
	tc := AsyncTraceContext{
		TraceID: r.Header.Get("x-b3-traceid"),
		SpanID:  r.Header.Get("x-b3-spanid"),
	}
	if tc.TraceID == "" {
		tc.TraceID = "mock-trace-12345"
	}
	return context.WithValue(context.Background(), asyncTraceKey{}, tc)
}

func AsyncWorker(ctx context.Context, taskPayload string) {
	tc, _ := ctx.Value(asyncTraceKey{}).(AsyncTraceContext)
	log.Printf("[Async Worker] Starting background processing under TraceID: %s", tc.TraceID)

	// Имитация длительной фоновой обработки (например, генерация отчета)
	time.Sleep(200 * time.Millisecond)
	log.Printf("[Async Worker] Task '%s' completed successfully for TraceID: %s", taskPayload, tc.TraceID)
}

func OrderHandler(w http.ResponseWriter, r *http.Request) {
	// Создаем безопасный контекст для горутины
	bgCtx := DetachedContextWithTrace(r)
	go AsyncWorker(bgCtx, "order-checkout-77")

	w.WriteHeader(http.StatusAccepted)
	fmt.Fprintf(w, `{"status":"queued"}`)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/order", OrderHandler)

	srv := http.Server{Addr: ":8080", Handler: mux}
	log.Println("Async trace preservation service listening on :8080")
	_ = srv
	fmt.Println("Async trace detachment logic verified")
}
```

ℹ️ Реализация: Распределенная трассировка: интеграция Istio с Jaeger и Zipkin (Упражнение 43)

## Под капотом

Envoy отправляет трейсы батчами (BatchSpanProcessor) по протоколу OTLP gRPC. Семплирование (Sampling Rate) настраивается в `meshConfig.defaultConfig.tracing.sampling`: например, значение 1.0% означает, что только 1 из 100 запросов будет трассироваться, что позволяет экономить терабайты дискового пространства в высоконагруженных системах.

## Подводные камни

Передача оригинального `r.Context()` в фоновую горутину `go AsyncWorker(r.Context())`. Как только HTTP-хендлер завершит работу, рантайм Go вызовет `cancel()` для контекста запроса, и фоновый воркер упадет с ошибкой `context canceled` при первом же обращении к БД или сети.

## На собеседовании

Вопрос на собеседовании в Яндекс: 'Что такое Head-based и Tail-based Sampling в распределенной трассировке?' Ответ: Head-based sampling принимает решение о записи трейса в момент входа запроса на шлюз (на основе процента). Tail-based sampling буферизует все спаны и принимает решение о сохранении только в конце: если в запросе была ошибка 5xx или аномальная задержка > 2с, трейс сохраняется гарантированно.
