# Prometheus Golden Signals: мониторинг Service Mesh в продакшене

## Условие

Настройте сбор метрик Istio в Prometheus: request count, latency, error rate per service. Напишите Go-скрипт расчета основных SLO по формулам Google SRE.

### Исходная формулировка

**Istio metrics**: Istio экспортирует метрики в Prometheus: request count, latency, error rate per service.

## Теория

Методология Google SRE определяет 4 золотых сигнала мониторинга: 1) Latency (задержка выполнения запросов); 2) Traffic (интенсивность нагрузки в RPS); 3) Errors (частота ошибок); 4) Saturation (насыщенность системных ресурсов). В Istio метрики `istio_requests_total` и `istio_request_duration_milliseconds_bucket` позволяют рассчитывать Service Level Indicators (SLI) математически строго, вычисляя доступность сервиса (Availability = (Total - Errors) / Total * 100%).

## Решение по шагам

Изучите формулы расчета SLI доступности и латентности.
Реализуйте в Go калькулятор метрик надежности на базе счетчиков запросов.
Проверьте соблюдение бюджета ошибок (Error Budget) при росте нагрузки.
Смоделируйте срабатывание Prometheus AlertManager при нарушении SLO.

## Код решения

**`server.go`**

```go
package main

import (
	"fmt"
	"log"
)

// SLOMetrics хранит агрегированные счетчики запросов микросервиса.
type SLOMetrics struct {
	TotalRequests uint64
	Errors5xx     uint64
	SlowRequests  uint64 // Latency > 200ms
	SLOTargetPct  float64
}

// CalculateAvailability рассчитывает текущий процент доступности по формуле Google SRE.
func (m *SLOMetrics) CalculateAvailability() float64 {
	if m.TotalRequests == 0 {
		return 100.0
	}
	successful := m.TotalRequests - m.Errors5xx
	return (float64(successful) / float64(m.TotalRequests)) * 100.0
}

// ErrorBudgetRemaining вычисляет остаток бюджета ошибок.
func (m *SLOMetrics) ErrorBudgetRemaining() float64 {
	allowedFailurePct := 100.0 - m.SLOTargetPct
	actualFailurePct := (float64(m.Errors5xx) / float64(m.TotalRequests)) * 100.0
	return allowedFailurePct - actualFailurePct
}

func main() {
	metrics := SLOMetrics{
		TotalRequests: 1_000_000,
		Errors5xx:     450,
		SlowRequests:  1200,
		SLOTargetPct:  99.9, // 99.9% доступности (3 девятки)
	}

	avail := metrics.CalculateAvailability()
	remainingBudget := metrics.ErrorBudgetRemaining()

	fmt.Println("=== Service Mesh SRE Golden Signals Report ===")
	fmt.Printf("Total Requests: %d\n", metrics.TotalRequests)
	fmt.Printf("5xx Errors:     %d\n", metrics.Errors5xx)
	fmt.Printf("Availability:   %.3f%% (Target: %.1f%%)\n", avail, metrics.SLOTargetPct)
	fmt.Printf("Error Budget:   %.3f%%\n", remainingBudget)

	if remainingBudget >= 0 {
		log.Println("✅ SLO is fully satisfied. Error budget is healthy.")
	} else {
		log.Println("🚨 CRITICAL: Error budget exhausted! Freezing production releases.")
	}
}
```

## Под капотом

Метрика `istio_request_duration_milliseconds_bucket` экспортируется в виде гистограммы с фиксированными границами (le). Функция PromQL `histogram_quantile(0.99, sum(rate(istio_request_duration_milliseconds_bucket[5m])) by (le))` вычисляет 99-й перцентиль задержки с линейной интерполяцией внутри корзин.

## Подводные камни

Использование среднего арифметического (avg) вместо квантилей (p95, p99). Среднее время ответа может составлять отличные 50 мс, скрывая тот факт, что 1% пользователей страдает от задержек в 10 секунд.

## На собеседовании

Вопрос на собеседовании в Авито: 'Что такое Error Budget и как инженерные команды используют его при канареечных релизах в Service Mesh?' Ответ: Бюджет ошибок — это допустимый объем сбоев (например, при SLO 99.9% бюджет равен 0.1% запросов). Если канареечный релиз новой версии начинает быстро сжигать бюджет ошибок (burn rate > 14x), автоматика Service Mesh немедленно останавливает раскатку.
