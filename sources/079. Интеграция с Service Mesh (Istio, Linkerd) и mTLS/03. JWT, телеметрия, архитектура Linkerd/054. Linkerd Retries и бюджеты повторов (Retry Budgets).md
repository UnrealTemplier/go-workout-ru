# Linkerd Retries и бюджеты повторов (Retry Budgets) в ServiceProfile

## Условие

Настройте automatic retries через ServiceProfile в Linkerd (маршрут GET /api, isRetryable: true). Реализуйте защиту от перегрузки через Retry Budget.

### Исходная формулировка

**Linkerd retries**: Настройте automatic retries через ServiceProfile:
```yaml
apiVersion: linkerd.io/v1alpha2
kind: ServiceProfile
spec:
  routes:
  - name: GET /api
    condition:
      method: GET
      pathRegex: /api
    isRetryable: true
```

## Теория

Linkerd настраивает поведение HTTP-маршрутов с помощью CRD `ServiceProfile`. Флаг `isRetryable: true` указывает прокси повторять неудачные запросы (HTTP 5xx). Уникальная особенность Linkerd — встроенные бюджеты повторов (`retryBudget`). Бюджет гарантирует, что количество повторных попыток не может превышать заданный процент от общего числа запросов (например, не более 20% поверх регулярного трафика, `retryRatio: 0.2`). Если downstream начинает массово падать, Linkerd автоматически перестает ретраить, предотвращая лавинообразное крушение системы.

## Решение по шагам

Изучите манифест ServiceProfile с маршрутами и флагом isRetryable: true.
Напишите Go-сервис с симуляцией кратковременных 503 ошибок.
Продемонстрируйте ограничение ретраев по бюджету при масштабном сбое.
Сравните семантику retry budget в Linkerd с circuit breaker в Istio.

## Код решения

**`server.go`**

```go
package main

import (
	"fmt"
	"log"
	"sync"
	"time"
)

// RetryBudgetSimulator демонстрирует алгоритм Retry Budget из Linkerd
type RetryBudgetSimulator struct {
	mu           sync.Mutex
	regularCalls int
	retriesMade  int
	maxRetryPct  float64 // 20%
}

func (b *RetryBudgetSimulator) CanRetry() bool {
	b.mu.Lock()
	defer b.mu.Unlock()

	allowedRetries := int(float64(b.regularCalls) * b.maxRetryPct)
	if b.retriesMade < allowedRetries {
		b.retriesMade++
		return true
	}
	return false
}

func (b *RetryBudgetSimulator) RecordSuccess() {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.regularCalls++
}

func main() {
	budget := &RetryBudgetSimulator{maxRetryPct: 0.20} // 20% лимит повторов

	// Симуляция 100 обычных запросов
	for i := 0; i < 100; i++ {
		budget.RecordSuccess()
	}

	// Начинается авария: пробуем сделать 30 ретраев
	approved := 0
	denied := 0
	for i := 0; i < 30; i++ {
		if budget.CanRetry() {
			approved++
		} else {
			denied++
		}
	}

	log.Printf("Retry Budget Results: Approved Retries=%d, Dropped Retries=%d", approved, denied)
	fmt.Printf("Linkerd retry budget strictly prevented retry storm: dropped %d dangerous retries!\n", denied)
}
```

ℹ️ Реализация: Linkerd Retries и бюджеты повторов (Retry Budgets) в ServiceProfile (Упражнение 54)

## Под капотом

Linkerd proxy отслеживает скользящее окно запросов (по умолчанию 10 секунд). Каждый успешный запрос добавляет квоту на повторы. Когда квота исчерпана, прокси немедленно возвращает полученный статус ошибки клиенту, не повторяя запрос.

## Подводные камни

Установка `isRetryable: true` на неидемпотентные маршруты (POST /transfer) может привести к дублированию операций при сетевых таймаутах. В ServiceProfile разрешайте повторы только для GET/HEAD или идемпотентных PUT/DELETE.

## На собеседовании

Вопрос на собеседовании в Авито: 'Почему концепция Retry Budget в Linkerd часто безопаснее стандартных retries: attempts: 3 в Istio?' Ответ: В Istio при падении бэкенда каждый клиент упорно делает 3 попытки, увеличивая нагрузку ровно в 3 раза (300%). Linkerd Retry Budget жестко ограничивает всплеск нагрузки до заданных 10–20%, физически исключая возможность возникновения Retry Storm.
