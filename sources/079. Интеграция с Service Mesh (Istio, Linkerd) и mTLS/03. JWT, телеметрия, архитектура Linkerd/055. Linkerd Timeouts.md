# Linkerd Timeouts: управление временем ожидания через ServiceProfile

## Условие

Настройте timeouts через ServiceProfile в Linkerd. Реализуйте клиентский Go-код с согласованным контекстом.

### Исходная формулировка

**Linkerd timeouts**: Настройте timeouts через ServiceProfile.

## Теория

В Linkerd таймаут настраивается на уровне отдельного маршрута в `ServiceProfile`: параметр `timeout: 500ms`. Если бэкенд не вернул ответ в течение 500 мс, Linkerd-proxy обрывает запрос и возвращает статус `HTTP 504 Gateway Timeout`. Для Go-приложения критически важно иметь таймаут в `context.WithTimeout`, согласованный с ServiceProfile, чтобы избежать рассинхронизации клиентского и прокси таймеров.

## Решение по шагам

Изучите директиву timeout в манифесте Linkerd ServiceProfile.
Напишите Go-клиент с контекстом, настроенным на безопасный интервал.
Продемонстрируйте обработку ответа 504 от Linkerd прокси.
Объясните важность согласования времени ожидания.

## Код решения

**`server.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
	"net/http/httptest"
	"time"
)

// TimeoutProtectedClient выполняет вызовы с учетом таймаута mesh
type TimeoutProtectedClient struct {
	client *http.Client
}

func (c *TimeoutProtectedClient) FetchData(ctx context.Context, url string) (int, error) {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return 0, err
	}

	resp, err := c.client.Do(req)
	if err != nil {
		return 0, err
	}
	defer resp.Body.Close()

	return resp.StatusCode, nil
}

func main() {
	// Имитация бэкенда, отвечающего за 800мс при таймауте прокси 500мс
	mockSlowServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Прокси Linkerd сбросит этот запрос по таймауту 500ms
		http.Error(w, "504 Gateway Timeout by Linkerd", http.StatusGatewayTimeout)
	}))
	defer mockSlowServer.Close()

	client := &TimeoutProtectedClient{client: &http.Client{}}
	ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
	defer cancel()

	status, err := client.FetchData(ctx, mockSlowServer.URL)
	if err != nil {
		log.Fatalf("Client failure: %v", err)
	}

	log.Printf("Received status from mesh proxy: %d", status)
	if status == http.StatusGatewayTimeout {
		fmt.Println("Linkerd ServiceProfile timeout successfully intercepted")
	}
}
```

ℹ️ Реализация: Linkerd Timeouts: управление временем ожидания через ServiceProfile (Упражнение 55)

## Под капотом

Linkerd proxy регистрирует таймер в runtime Tokio (`tokio::time::timeout`). По истечении 500 мс фьюча ожидания ответа прерывается, исходящий сокет закрывается, а клиенту передается синтетический ответ 504.

## Подводные камни

Если таймаут клиента в Go меньше таймаута прокси, клиент разорвет соединение раньше, и в метриках Linkerd появится ошибка Downstream Reset.

## На собеседовании

Вопрос на собеседовании в Ozon: 'Как правильно рассчитать таймаут в распределенной цепочке из 4 сервисов?' Ответ: Использовать убывающие таймауты (Deadline Propagation). Если внешний шлюз установил дедлайн в 2 секунды, каждый последующий сервис должен вычитать время, потраченное на предыдущих шагах, чтобы сервис в конце цепочки не начинал операцию, если времени на ответ уже не осталось.
