# Автоматическая инъекция Sidecar и проверка состава Pod

## Условие

Настройте automatic sidecar injection через istio-injection=enabled label на namespace. Каждый pod получает Envoy proxy. Реализуйте проверку наличия контейнеров через Go Kubernetes Client.

### Исходная формулировка

**Envoy sidecar injection**: Настройте automatic sidecar injection через `istio-injection=enabled` label на namespace. Каждый pod получает Envoy proxy.

## Теория

Механизм Sidecar Injection в Kubernetes работает на базе `MutatingAdmissionWebhook`. Когда контроллер Deployment создает Pod в namespace с меткой `istio-injection=enabled`, Kubernetes API Server отправляет спецификацию Pod'а в вебхук `istiod`. `istiod` модифицирует PodSpec, автоматически добавляя: 1) `initContainers`: образ `istio/proxyv2` для запуска скрипта настройки iptables; 2) `containers`: контейнер `istio-proxy` с бинарником Envoy; 3) `volumes`: монтирование сертификатов `/var/run/secrets/tokens` и Unix-сокетов.

## Решение по шагам

Изучите спецификацию Pod с инжектированным sidecar контейнером.
Напишите Go-утилиту, использующую k8s.io/api/core/v1 для аудита подов.
Реализуйте проверку наличия контейнера istio-proxy и статуса его готовности.
Определите, защищен ли сервис Service Mesh политиками.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
)

// PodContainerInfo имитирует информацию о контейнере из K8s API.
type PodContainerInfo struct {
	Name  string
	Image string
	Ready bool
}

// PodAuditInfo отражает результат аудита пода на наличие Service Mesh.
type PodAuditInfo struct {
	PodName    string
	Namespace  string
	HasSidecar bool
	SidecarVer string
	IsReady    bool
}

// AuditPodSidecar проверяет наличие istio-proxy контейнера.
func AuditPodSidecar(podName, namespace string, containers []PodContainerInfo) PodAuditInfo {
	audit := PodAuditInfo{
		PodName:   podName,
		Namespace: namespace,
	}

	for _, c := range containers {
		if c.Name == "istio-proxy" || c.Name == "linkerd-proxy" {
			audit.HasSidecar = true
			audit.SidecarVer = c.Image
			audit.IsReady = c.Ready
			break
		}
	}
	return audit
}

func main() {
	// Имитация списка контейнеров пода после sidecar injection
	mockContainers := []PodContainerInfo{
		{Name: "order-service", Image: "registry.corp/order-service:v1.2", Ready: true},
		{Name: "istio-proxy", Image: "docker.io/istio/proxyv2:1.20.0", Ready: true},
	}

	result := AuditPodSidecar("order-service-7f8d9b-x92kl", "production", mockContainers)

	log.Printf("[Mesh Audit] Pod %s/%s:", result.Namespace, result.PodName)
	if result.HasSidecar {
		fmt.Printf("✅ Sidecar injected! Image: %s, Ready: %v\n", result.SidecarVer, result.IsReady)
	} else {
		fmt.Println("❌ WARNING: No service mesh sidecar detected! Traffic is NOT protected.")
	}
}
```

ℹ️ Реализация: Автоматическая инъекция Sidecar и проверка состава Pod (Упражнение 36)

## Под капотом

Kube-apiserver выполняет фазу Mutating Webhook до валидации и сохранения объекта в etcd. `istiod` возвращает JSON Patch документ, который вставляет контейнер `istio-proxy` с resource limits (CPU/RAM) и томом `istio-envoy`.

## Подводные камни

Если в поде указана настройка `hostNetwork: true`, автоматическая инъекция sidecar не сработает или сломает сеть хоста, так как iptables перенаправит все порты физической ноды на Envoy.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Почему в Kubernetes 1.28+ появился нативный механизм Native Sidecar Containers и какую проблему Istio он решает?' Ответ: До K8s 1.28 поды не различали порядок запуска и завершения обычных контейнеров. В K8s 1.28 init-контейнер с `restartPolicy: Always` стартует строго до основного контейнера и завершается строго после него. Это устраняет падения Go-приложений при старте и потере логов при завершении.
