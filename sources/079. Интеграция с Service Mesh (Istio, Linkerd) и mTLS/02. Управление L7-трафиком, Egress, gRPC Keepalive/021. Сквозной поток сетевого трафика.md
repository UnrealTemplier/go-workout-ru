# Сквозной поток сетевого трафика (Istio Traffic Flow)

## Условие

Поймите, как трафик течёт: Client → Istio Ingress Gateway → Service A sidecar → Service A, затем Service A → sidecar → Service B sidecar → Service B. Реализуйте диагностический Go-сервис, фиксирующий метаданные каждого сетевого прыжка (hop-by-hop).

### Исходная формулировка

**Istio traffic flow**: Поймите, как трафик течёт:
* Client → Istio Ingress Gateway → Service A sidecar → Service A
* Service A → sidecar → Service B sidecar → Service B

## Теория

Маршрут запроса внутри Service Mesh состоит из серии симметричных сетевых переходов: 1) Клиент отправляет TLS-запрос на Ingress Gateway (периметр кластера); 2) Ingress Gateway терминирует внешний TLS и открывает внутреннюю mTLS-сессию с sidecar-прокси Service A; 3) Sidecar Service A терминирует mTLS и пересылает обычный HTTP по петле (127.0.0.1) в Go-процесс Service A; 4) Service A выполняет бизнес-логику и инициирует вызов `http://service-b`; 5) iptables Service A перехватывает исходящий сокет на локальный Envoy (порт 15001); 6) Envoy Service A открывает mTLS-сессию с Envoy Service B; 7) Envoy Service B валидирует SPIFFE ID Service A и передает запрос локальному Go-процессу Service B.

## Решение по шагам

Создайте микросервис Service A, выполняющий вызов Service B.
Реализуйте сбор и добавление трассировочных заголовков x-forwarded-for и x-envoy-peer-metadata.
Напишите Service B, выводящий полную цепочку участников сетевого пути.
Проверьте передачу контекста и сохранение статусов на каждом этапе.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"io"
	"log"
	"net/http"
	"os"
	"time"
)

type HopTrace struct {
	Service       string              `json:"service"`
	Host          string              `json:"host"`
	RemoteAddr    string              `json:"remote_addr"`
	EnvoyHeaders  map[string]string   `json:"envoy_headers"`
	DownstreamHop *HopTrace           `json:"downstream_hop,omitempty"`
}

// ServiceBHandler принимает вызов от Service A через локальный Envoy B
func ServiceBHandler(w http.ResponseWriter, r *http.Request) {
	trace := HopTrace{
		Service:    "Service-B",
		Host:       os.Getenv("HOSTNAME"),
		RemoteAddr: r.RemoteAddr,
		EnvoyHeaders: map[string]string{
			"x-request-id":             r.Header.Get("x-request-id"),
			"x-forwarded-for":          r.Header.Get("x-forwarded-for"),
			"x-envoy-internal":         r.Header.Get("x-envoy-internal"),
			"x-forwarded-client-cert":  r.Header.Get("x-forwarded-client-cert"),
		},
	}

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(trace)
}

// ServiceAHandler принимает вызов от Ingress и вызывает Service B через локальный Envoy A
func ServiceAHandler(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
	defer cancel()

	// Исходящий вызов на Service B (прозрачно перехватывается Envoy A)
	outReq, _ := http.NewRequestWithContext(ctx, http.MethodGet, "http://service-b:8080/trace", nil)
	// Обязательно пробрасываем request-id и трейсы
	outReq.Header.Set("x-request-id", r.Header.Get("x-request-id"))

	client := &http.Client{Timeout: 2 * time.Second}
	resp, err := client.Do(outReq)
	if err != nil {
		http.Error(w, fmt.Sprintf("Service B call failed: %v", err), http.StatusBadGateway)
		return
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	var bTrace HopTrace
	_ = json.Unmarshal(body, &bTrace)

	currentTrace := HopTrace{
		Service:       "Service-A",
		Host:          os.Getenv("HOSTNAME"),
		RemoteAddr:    r.RemoteAddr,
		DownstreamHop: &bTrace,
		EnvoyHeaders: map[string]string{
			"x-request-id": r.Header.Get("x-request-id"),
		},
	}

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(currentTrace)
}

func main() {
	role := os.Getenv("SERVICE_ROLE")
	mux := http.NewServeMux()

	if role == "B" {
		mux.HandleFunc("/trace", ServiceBHandler)
		log.Println("Starting Service B on :8080")
	} else {
		mux.HandleFunc("/entry", ServiceAHandler)
		log.Println("Starting Service A on :8080")
	}

	_ = http.ListenAndServe(":8080", mux)
}
```

ℹ️ Реализация: Сквозной поток сетевого трафика (Istio Traffic Flow) (Упражнение 21)

## Под капотом

В цепочке вызовов заголовок `x-request-id` (UUID v4) генерируется на Ingress Gateway. Envoy использует его для сквозной корреляции access-логов между Ingress, Service A sidecar и Service B sidecar. Заголовок `x-forwarded-client-cert` инжектируется только при успехе mTLS-рукопожатия между прокси.

## Подводные камни

Забытый проброс `x-request-id` в Go-клиенте приводит к тому, что исходящий Envoy сгенерирует новый UUID, и корреляция сетевых логов между Service A и Service B в Kibana/Grafana Loki будет невозможна.

## На собеседовании

Вопрос на собеседовании в Яндекс: 'Сколько TCP-сокетов открывается при обычном вызове между Service A и Service B внутри Istio Service Mesh?' Ответ: Четыре сокета: 1) Go App A -> Local Envoy A (loopback); 2) Envoy A -> Envoy B (физическая сеть нод, mTLS); 3) Envoy B -> Go App B (loopback); 4) Соединение Envoy с istiod (xDS control plane в фоне).
