# DestinationRule Circuit Breaker и клиентский Rate Limiting на Go

## Условие

Настрой Istio DestinationRule с лимитом: максимум 1 запрос на соединение, остальные ставить в очередь. Напиши Go-клиент, который делает 10 параллельных запросов. Используй golang.org/x/time/rate (Rate Limiter) на стороне клиента, чтобы не получать 503 от Envoy.

### Исходная формулировка

**[Istio DestinationRule (Circuit Breaker)]**: Настрой Istio `DestinationRule` с лимитом: максимум 1 запрос на соединение, остальные ставить в очередь. Напиши Go-клиент, который делает 10 параллельных запросов. Используй `golang.org/x/time/rate` (Rate Limiter) на стороне клиента, чтобы не получать 503 от Envoy.

## Теория

Когда Service Mesh настраивается на жесткий лимит соединений (`maxRequestsPerConnection: 1` или малый `maxConnections`), неконтролируемый всплеск параллельных клиентских запросов приводит к мгновенным ошибкам `503 Service Unavailable (UO)`. Чтобы избежать отказов, на стороне вызывающего Go-клиента внедряется алгоритм Token Bucket (`golang.org/x/time/rate`). Клиентский Rate Limiter сглаживает пики (Traffic Shaping), выстраивая запросы в аккуратную очередь и отправляя их с интенсивностью, согласованной с лимитами пропускной способности Envoy.

## Решение по шагам

Инициализируйте Token Bucket Rate Limiter с разрешенным RPS и Burst емкостью.
Напишите Go-клиент с вызовом limiter.Wait(ctx) перед каждым сетевым обращением.
Смоделируйте 10 параллельных горутин и продемонстрируйте отсутствие ошибок 503.

## Код решения

**`circuit_breaker.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

// SimpleTokenLimiter реализует базовый rate-limiting для сглаживания всплесков.
type SimpleTokenLimiter struct {
	ticker <-chan time.Time
}

func NewSimpleTokenLimiter(rps int) *SimpleTokenLimiter {
	interval := time.Second / time.Duration(rps)
	return &SimpleTokenLimiter{
		ticker: time.Tick(interval),
	}
}

func (l *SimpleTokenLimiter) Wait(ctx context.Context) error {
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-l.ticker:
		return nil
	}
}

func main() {
	// Сервер имитирует строгий Envoy лимит (не более 1 запроса за раз)
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("ok"))
	}))
	defer server.Close()

	limiter := NewSimpleTokenLimiter(5) // 5 запросов в секунду
	var wg sync.WaitGroup

	log.Println("Starting 10 concurrent requests smoothed by Client-side Rate Limiter...")

	for i := 1; i <= 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
			defer cancel()

			// Ожидаем токен перед отправкой в Envoy
			if err := limiter.Wait(ctx); err != nil {
				log.Printf("[Worker %d] Dropped due to timeout: %v", id, err)
				return
			}

			resp, err := http.Get(server.URL)
			if err != nil {
				log.Printf("[Worker %d] Request failed: %v", id, err)
				return
			}
			resp.Body.Close()
			log.Printf("[Worker %d] Success (Status %d)", id, resp.StatusCode)
		}(i)
	}

	wg.Wait()
	fmt.Println("All smoothed requests processed without triggering 503 UO")
}
```

ℹ️ Реализация: DestinationRule Circuit Breaker и клиентский Rate Limiting на Go (Упражнение 28)

## Под капотом

Алгоритм Token Bucket пополняет корзину токенами с постоянной скоростью. Вызов `limiter.Wait()` блокирует горутину через канал таймера до появления доступного токена. Это предотвращает переполнение буфера `http1MaxPendingRequests` в Envoy и сохраняет сокеты от сброса.

## Подводные камни

Если клиенты масштабируются горизонтально (например, 100 реплик подов Go), локальный Rate Limiter на каждом клиенте не спасет upstream от перегрузки (100 подов * 5 RPS = 500 RPS). Для глобального ограничения используется Envoy Global Rate Limiting Service (RLS) на базе Redis.

## На собеседовании

Вопрос на собеседовании в Ozon: 'В чем разница между Rate Limiter на стороне клиента и Rate Limiter на стороне сервера (Envoy)?' Ответ: Серверный Rate Limiter защищает инфраструктуру от перегрузки, сбрасывая избыток запросов с кодом 429/503. Клиентский Rate Limiter защищает сам клиент от получения ошибок 429/503, упорядочивая исходящие запросы в соответствии с установленными квотами SLA.
