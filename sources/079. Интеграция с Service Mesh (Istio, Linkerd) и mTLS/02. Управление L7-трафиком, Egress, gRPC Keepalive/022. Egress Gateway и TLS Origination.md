# Egress Gateway и TLS Origination для контролируемого внешнего трафика

## Условие

Настройте EgressGateway (Istio): весь outbound трафик к внешним API (Stripe, SendGrid) проходит через контролируемый gateway с TLS origination. Покажите, что pod не может напрямую достучаться до внешнего API (firewall + mesh policy). Объясните zero-trust egress.

### Исходная формулировка

**Egress Gateway.**: Настройте `EgressGateway` (Istio): весь outbound трафик к внешним API (Stripe, SendGrid) проходит через контролируемый gateway с TLS origination. Покажите, что pod не может напрямую достучаться до внешнего API (firewall + mesh policy). Объясните zero-trust egress.

## Теория

В корпоративных средах с повышенными требованиями к безопасности (PCI-DSS, ISO 27001) подам запрещен прямой выход в интернет. Все исходящие вызовы направляются на специальный централизованный шлюз — `Istio Egress Gateway`. Паттерн TLS Origination: Go-приложение обращается к внешнему шлюзу по обычному HTTP (`http://api.stripe.com`), трафик в зашифрованном mTLS-виде идет до Egress Gateway, и уже сам Egress Gateway выполняет TLS-рукопожатие с реальным внешним API Stripe. Это централизует аудит, контроль версий TLS, хранение клиентских сертификатов и предотвращает утечки данных мимо корпоративного прокси.

## Решение по шагам

Сконфигурируйте ServiceEntry и Egress Gateway с TLS Origination.
Напишите Go-клиент, выполняющий запрос к внешнему API по простому HTTP через Service Mesh.
Убедитесь, что запрос на стороне приложения не требует загрузки публичных Root CA сертификатов.
Проверьте, что Egress Gateway производит шифрование трафика перед отправкой во внешнюю сеть.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"log"
	"net/http"
	"time"
)

// StripeMeshClient обращается к Stripe API через Istio Egress Gateway.
// Приложение выполняет вызов по обычному HTTP: Envoy перехватывает его,
// пересылает через Egress Gateway, который инициирует TLS 1.3 к Stripe.
type StripeMeshClient struct {
	client *http.Client
}

func NewStripeMeshClient() *StripeMeshClient {
	return &StripeMeshClient{
		client: &http.Client{Timeout: 5 * time.Second},
	}
}

func (s *StripeMeshClient) CreateCustomer(ctx context.Context, email string) ([]byte, error) {
	// Внимание: URL с протоколом http://, так как шифрование делегировано шлюзу!
	reqURL := "http://api.stripe.com/v1/customers"
	req, err := http.NewRequestWithContext(ctx, http.MethodPost, reqURL, nil)
	if err != nil {
		return nil, err
	}

	req.Header.Set("Authorization", "Bearer sk_test_mock_token")
	req.Header.Set("Content-Type", "application/x-www-form-urlencoded")

	log.Printf("[MeshEgress] Sending outbound request to %s via Egress Gateway...", reqURL)
	resp, err := s.client.Do(req)
	if err != nil {
		return nil, fmt.Errorf("egress routing failed: %w", err)
	}
	defer resp.Body.Close()

	log.Printf("[MeshEgress] Received response status: %s", resp.Status)
	return io.ReadAll(resp.Body)
}

func main() {
	client := NewStripeMeshClient()
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	data, err := client.CreateCustomer(ctx, "dev@example.com")
	if err != nil {
		log.Printf("[Egress Info] Request simulated (expected outside K8s cluster): %v", err)
		return
	}
	fmt.Printf("Stripe response: %s\n", string(data))
}
```

ℹ️ Реализация: Egress Gateway и TLS Origination для контролируемого внешнего трафика (Упражнение 22)

## Под капотом

В Istio настраивается `ServiceEntry` с resolution: DNS и `VirtualService`, направляющий трафик с порта 80 на порт 443 Egress Gateway. `DestinationRule` на Egress Gateway содержит `mode: SIMPLE`, предписывая Envoy инициировать стандартный TLS 1.3 с проверкой SNI `api.stripe.com`.

## Подводные камни

Если в Kubernetes сетевой политике (NetworkPolicy) заблокирован egress на порты 80/443, но забыли открыть доступ до порта Egress Gateway, поды не смогут достучаться до шлюза, получая таймаут сокета.

## На собеседовании

Вопрос на собеседовании в Т-Банк: 'Зачем выносить TLS Origination на Egress Gateway вместо прямого выполнения HTTPS вызовов из Go-кода?' Ответ: 1) Безопасность: поды в защищенном контуре не имеют прямого доступа в интернет и не могут 'слить' данные наружу при компрометации кода; 2) Централизованный аудит всех исходящих запросов компании в одном месте; 3) Единая точка управления корпоративными исходящими статическими IP-адресами (NAT Gateway IP).
