## Теория

Сетевые сбои в микросервисах часто носят кратковременный характер (transient failures). Istio `VirtualService` позволяет делегировать логику повторов Envoy: `retries.attempts: 3` и `perTryTimeout: 2s` означают, что Envoy сделает до 3 попыток, ожидая ответа не более 2 секунд на каждую. Однако повторные попытки в распределенных системах смертельно опасны без гарантии идемпотентности: если сервис-получатель уже списал деньги, но ответ задержался в сети, повторный запрос Envoy может привести к повторному списанию! Кроме того, каскадные ретраи вызывают Retry Storms (шторм повторов), способный окончательно обрушить перегруженный downstream-сервис.

## Решение по шагам

Создайте Go HTTP-хендлер с симуляцией задержек time.Sleep и временных 503 ошибок.
Настройте безопасный механизм генерации Idempotency-Key.
Проверьте, что повторные попытки от Envoy обрабатываются идемпотентно с возвратом ранее сохраненного результата.
Реализуйте логирование попыток через заголовок x-envoy-attempt-count.

## Код решения

**`server.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"sync"
	"time"
)

type PaymentStore struct {
	mu    sync.Mutex
	cache map[string]string
}

var store = &PaymentStore{cache: make(map[string]string)}

// IdempotentPaymentHandler безопасно обрабатывает повторы от Envoy.
func IdempotentPaymentHandler(w http.ResponseWriter, r *http.Request) {
	attempt := r.Header.Get("x-envoy-attempt-count")
	idempotencyKey := r.Header.Get("Idempotency-Key")

	log.Printf("[Payment] Attempt #%s for Key: %s", attempt, idempotencyKey)

	if idempotencyKey == "" {
		http.Error(w, "Missing Idempotency-Key", http.StatusBadRequest)
		return
	}

	store.mu.Lock()
	if result, exists := store.cache[idempotencyKey]; exists {
		store.mu.Unlock()
		log.Printf("[Payment] Cache hit for Key %s. Returning previous result.", idempotencyKey)
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusOK)
		w.Write([]byte(result))
		return
	}
	store.mu.Unlock()

	// Имитация сбоя на первой попытке
	if attempt == "1" {
		log.Println("[Payment] Simulating transient network failure on attempt 1")
		http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
		return
	}

	// Успешная обработка на повторной попытке
	result := fmt.Sprintf(`{"status":"success","payment_id":"pay-%d"}`, time.Now().UnixNano())
	store.mu.Lock()
	store.cache[idempotencyKey] = result
	store.mu.Unlock()

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	w.Write([]byte(result))
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/charge", IdempotentPaymentHandler)
	log.Println("Payment service running on :8080")
	_ = http.ListenAndServe(":8080", mux)
}
```

## Под капотом

Envoy инжектирует в исходящий запрос заголовок `x-envoy-attempt-count`, увеличивая его на 1 при каждой попытке. Если сконфигурирован `perTryTimeout: 2s`, Envoy взводит локальный таймер. Если ответ не получен за 2 секунды, Envoy отправляет RST_STREAM (для HTTP/2) или закрывает TCP-сокет к upstream-поду и немедленно инициирует новое соединение к другому поду.

## Подводные камни

Категорически запрещено настраивать ретраи в Istio на методы `POST` или `PUT` без явной фильтрации по retryOn (например, `5xx,connect-failure,refused-stream`). Если бэкенд возвращает 500 из-за валидации базы данных, ретраи Envoy только умножат нагрузку на упавшую базу данных.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Что такое Retry Amplification (коэффициент размножения повторов) и как Service Mesh может его усугубить?' Ответ: Если в цепочке вызовов A -> B -> C каждый сервис настроен на 3 ретрая, то при сбое C сервис B сделает 3 попытки, а сервис A сделает 3 попытки на каждый сбой B. В итоге C получит 3 * 3 = 9 запросов на один пользовательский клик! В Service Mesh ретраи должны настраиваться только на верхнем или строго на одном уровне.
