### Исходная формулировка

## Теория

Flagger — это оператор прогрессивной доставки для Kubernetes, автоматизирующий канареечные релизы через Service Mesh. Flagger управляет генерацией двух Deployment: `app-primary` (стабильная версия) и `app-canary` (новая версия). Каждые N секунд Flagger опрашивает Prometheus, вычисляя метрики успешности запросов (Success Rate > 99%) и задержки (p99 < 500ms). Если SLO соблюдается, Flagger плавно сдвигает веса в `VirtualService` (1% -> 10% -> 50% -> 100%). Если в новой версии возникает всплеск 5xx ошибок, Flagger мгновенно переключает 100% трафика назад на primary и шлет уведомление в Slack.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"math/rand"
	"net/http"
	"os"
	"sync/atomic"
	"time"
)

var (
	totalRequests uint64
	errorRequests uint64
)

// MetricHandler отдает расчетный Success Rate для проверки Flagger.
func MetricHandler(w http.ResponseWriter, r *http.Request) {
	tot := atomic.LoadUint64(&totalRequests)
	errs := atomic.LoadUint64(&errorRequests)

	successRate := 100.0
	if tot > 0 {
		successRate = float64(tot-errs) / float64(tot) * 100.0
	}

	w.Header().Set("Content-Type", "text/plain")
	fmt.Fprintf(w, "# HELP app_success_rate Current success rate percentage\n")
	fmt.Fprintf(w, "app_success_rate %.2f\n", successRate)
}

// WorkloadHandler имитирует полезную нагрузку.
func WorkloadHandler(w http.ResponseWriter, r *http.Request) {
	atomic.AddUint64(&totalRequests, 1)

	// Имитация канареечного дефекта
	isCanaryBroken := os.Getenv("CANARY_BROKEN") == "true"
	if isCanaryBroken && rand.Float32() < 0.15 { // 15% ошибок
		atomic.AddUint64(&errorRequests, 1)
		http.Error(w, "Canary internal regression", http.StatusInternalServerError)
		return
	}

	w.WriteHeader(http.StatusOK)
	w.Write([]byte(`{"status":"success"}`))
}

func main() {
	rand.Seed(time.Now().UnixNano())
	mux := http.NewServeMux()
	mux.HandleFunc("/api/work", WorkloadHandler)
	mux.HandleFunc("/metrics", MetricHandler)

	log.Println("Workload service with Flagger SLO metrics listening on :8080")
	_ = http.ListenAndServe(":8080", mux)
}
```

## Под капотом

Flagger выполняет PromQL-запрос вида: `sum(rate(istio_requests_total{reporter='destination',destination_workload='app-canary',response_code!~'5.*'}[1m])) / sum(rate(istio_requests_total{reporter='destination',destination_workload='app-canary'}[1m])) * 100`. Если результат меньше порога threshold (например, 99%), счетчик итераций ошибок инкрементируется. При достижении `maxWeight` происходит swap подов.

## Подводные камни

Если на канареечную версию направлен 1% трафика, а общий поток запросов мал (например, 1 запрос в минуту), даже 1 случайная ошибка даст падение Success Rate до 0%, что вызовет ложный откат (False Positive Rollback). Для малого трафика необходимо генерировать синтетическую нагрузку (Flagger Webhooks).

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Как Flagger осуществляет финализацию канареечного релиза (promotion) без даунтайма?' Ответ: Flagger обновляет шаблон Pod'а в основном Primary Deployment до новой версии образа, дожидается готовности (Readiness) всех Primary реплик, переключает 100% трафика на Primary через VirtualService, и только затем масштабирует Canary Deployment в 0.
