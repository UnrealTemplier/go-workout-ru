# L7 Traffic Management: Canary Routing через VirtualService и DestinationRule

## Условие

Настройте VirtualService + DestinationRule (Istio) или TrafficSplit (Linkerd): 90% трафика на v1, 10% на v2. Реализуйте Go-сервис с двумя deployment (app=v1, app=v2). Покажите распределение через curl в loop. Объясните, как mesh делает это без изменения клиентского кода.

### Исходная формулировка

**L7 Traffic Management.**: Настройте `VirtualService` + `DestinationRule` (Istio) или `TrafficSplit` (Linkerd): 90% трафика на `v1`, 10% на `v2`. Реализуйте Go-сервис с двумя deployment (`app=v1`, `app=v2`). Покажите распределение через `curl` в loop. Объясните, как mesh делает это без изменения клиентского кода.

## Теория

Управление L7-трафиком в Istio базируется на разделении абстракций: 1) `VirtualService` определяет правила маршрутизации входящих запросов (хосты, пути, заголовки, веса для канареечных релизов); 2) `DestinationRule` определяет политики, применяемые к трафику после маршрутизации (пулы соединений, mTLS режим, алгоритм балансировки, subsets по Kubernetes-меткам). Клиент обращается по стабильному DNS имени `users-svc`. Envoy перехватывает запрос и псевдослучайно согласно весам (90/10) выбирает целевой subset (v1 или v2).

## Решение по шагам

Реализуйте сервис на Go, возвращающий версию приложения из переменной окружения APP_VERSION.
Напишите клиента на Go, посылающего 100 запросов и подсчитывающего процент ответов от v1 и v2.
Сконфигурируйте VirtualService с весами 90 и 10.
Проверьте соблюдение закона больших чисел при канареечном распределении.

## Код решения

**`server.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"io"
	"log"
	"net/http"
	"os"
	"sync"
	"time"
)

type VersionResponse struct {
	Version string `json:"version"`
	Host    string `json:"host"`
}

// ServerSide: сервис возвращает свою версию
func startServer() {
	version := os.Getenv("APP_VERSION")
	if version == "" {
		version = "v1"
	}
	mux := http.NewServeMux()
	mux.HandleFunc("/version", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(VersionResponse{
			Version: version,
			Host:    os.Getenv("HOSTNAME"),
		})
	})
	log.Printf("Starting service version %s on :8080", version)
	_ = http.ListenAndServe(":8080", mux)
}

// ClientSide: генератор трафика для проверки весов 90/10
func runCanaryVerification(targetURL string, totalRequests int) {
	counts := make(map[string]int)
	var mu sync.Mutex
	client := &http.Client{Timeout: 2 * time.Second}

	for i := 0; i < totalRequests; i++ {
		resp, err := client.Get(targetURL)
		if err != nil {
			log.Printf("Request %d failed: %v", i, err)
			continue
		}
		body, _ := io.ReadAll(resp.Body)
		resp.Body.Close()

		var vr VersionResponse
		if err := json.Unmarshal(body, &vr); err == nil {
			mu.Lock()
			counts[vr.Version]++
			mu.Unlock()
		}
	}

	fmt.Printf("Canary traffic results over %d requests:\n", totalRequests)
	for ver, cnt := range counts {
		pct := float64(cnt) / float64(totalRequests) * 100
		fmt.Printf("Version %s: %d requests (%.1f%%)\n", ver, cnt, pct)
	}
}

func main() {
	if len(os.Args) > 1 && os.Args[1] == "client" {
		runCanaryVerification("http://users-service:8080/version", 100)
		return
	}
	startServer()
}
```

## Под капотом

Envoy использует алгоритм Weighted Cluster Selection. В конфигурации Envoy ClusterManager хранит кластеры `outbound|8080|v1|users-svc` и `outbound|8080|v2|users-svc`. При поступлении HTTP-запроса роутер выбирает кластер, используя целочисленный генератор псевдослучайных чисел от 0 до 100. Соединение пересылается через соответствующий upstream connection pool.

## Подводные камни

Если в VirtualService заданы веса (90/10), но забыли создать DestinationRule с подмножествами (subsets v1 и v2), Envoy вернет ошибку HTTP 503 NR (No Route configured). Kubernetes Service сам по себе не умеет делить трафик по меткам версий.

## На собеседовании

Вопрос на собеседовании в Ozon: 'Чем L7 traffic split в Istio отличается от стандартного Kubernetes Deployment с изменением числа реплик (например, 9 реплик v1 и 1 реплика v2)?' Ответ: Деление подами грубое, расходует память и ресурсы CPU на лишние поды и не позволяет маршрутизировать по HTTP-заголовкам (куки, сессии, токены). Istio делает сплит на уровне каждого запроса с нулевым оверхедом по числу подов.
