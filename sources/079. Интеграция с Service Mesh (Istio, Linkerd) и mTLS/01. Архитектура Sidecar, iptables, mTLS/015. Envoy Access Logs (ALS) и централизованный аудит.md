# Envoy Access Logs (ALS) и централизованный аудит трафика

## Условие

Включите Envoy access logs через Telemetry API (Istio) или config.linkerd.io/access-log (Linkerd). Покажите, что каждый HTTP/gRPC запрос логируется sidecar-ом с информацией: upstream, downstream, latency, response code. Объясните, почему это centralizes logging без изменения кода приложения.

### Исходная формулировка

**Access Logs (Envoy ALS).**: Включите Envoy access logs через `Telemetry` API (Istio) или `config.linkerd.io/access-log` (Linkerd). Покажите, что каждый HTTP/gRPC запрос логируется sidecar-ом с информацией: upstream, downstream, latency, response code. Объясните, почему это centralizes logging без изменения кода приложения.

## Теория

Традиционно каждый сервис на Go реализовывал собственное middleware для access-логов. Это приводило к несогласованности форматов (кто-то писал в plaintext, кто-то в JSON с разными именами полей) и создавало нагрузку на Garbage Collector Go при форматировании строк. Включение Envoy Access Logs (через Istio `Telemetry` API или gRPC Access Log Service — ALS) делегирует логирование C++ ядру Envoy. Sidecar генерирует унифицированные JSON-логи с метками времени, IP-адресами подов, временем ожидания upstream, кодами ошибок и флагами протокола.

## Решение по шагам

Изучите структуру JSON-логов, генерируемых Envoy в stdout контейнера istio-proxy.
Напишите симулятор парсинга Envoy Access Log в Go для ELK/OpenSearch агента.
Проанализируйте поля: duration, upstream_service_time, response_flags, upstream_cluster.
Объясните, почему логирование на уровне прокси фиксирует даже аварийные обрывы соединений до приложения.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"log"
	"strings"
	"time"
)

// EnvoyAccessLog представляет структурированную запись Envoy Access Log.
type EnvoyAccessLog struct {
	StartTime            time.Time `json:"start_time"`
	Method               string    `json:"method"`
	Path                 string    `json:"path"`
	Protocol             string    `json:"protocol"`
	ResponseCode         int       `json:"response_code"`
	ResponseFlags        string    `json:"response_flags"`
	BytesReceived        int64     `json:"bytes_received"`
	BytesSent            int64     `json:"bytes_sent"`
	DurationMS           int64     `json:"duration_ms"`
	UpstreamServiceTime  string    `json:"upstream_service_time"`
	XForwardedFor        string    `json:"x_forwarded_for"`
	UserAgent            string    `json:"user_agent"`
	UpstreamCluster      string    `json:"upstream_cluster"`
	UpstreamHost         string    `json:"upstream_host"`
}

func parseEnvoyLogEntry(rawJSON string) (*EnvoyAccessLog, error) {
	var entry EnvoyAccessLog
	err := json.Unmarshal([]byte(rawJSON), &entry)
	if err != nil {
		return nil, err
	}
	return &entry, nil
}

func main() {
	// Пример реальной строки access-лога Envoy sidecar
	rawLog := `{
		"start_time": "2026-09-07T12:00:01.123Z",
		"method": "POST",
		"path": "/api/v1/orders",
		"protocol": "HTTP/1.1",
		"response_code": 503,
		"response_flags": "UH",
		"bytes_received": 512,
		"bytes_sent": 19,
		"duration_ms": 2,
		"upstream_service_time": "-",
		"x_forwarded_for": "10.244.1.15",
		"user_agent": "Go-http-client/1.1",
		"upstream_cluster": "outbound|8080||order-processor.default.svc.cluster.local",
		"upstream_host": "-"
	}`

	logEntry, err := parseEnvoyLogEntry(rawLog)
	if err != nil {
		log.Fatalf("Parse error: %v", err)
	}

	fmt.Println("Successfully parsed Envoy Access Log entry:")
	fmt.Printf("Endpoint: %s %s -> HTTP %d (Flags: %s)\n",
		logEntry.Method, logEntry.Path, logEntry.ResponseCode, logEntry.ResponseFlags)
	fmt.Printf("Cluster: %s, Duration: %d ms\n",
		logEntry.UpstreamCluster, logEntry.DurationMS)

	if strings.Contains(logEntry.ResponseFlags, "UH") {
		fmt.Println("[Alert] Upstream cluster has no healthy endpoints!")
	}
}
```

## Под капотом

Envoy пишет access-логи асинхронно через неблокирующий файловый дескриптор или отправляет их потоком gRPC (Access Log Service) в агрегатор. Даже если Go-приложение зависло в бесконечном цикле или упало с OOMKilled, Envoy запишет лог со статусом 504 Gateway Timeout или 502 Bad Gateway.

## Подводные камни

Включение подробного access logging на высоконагруженных сервисах (десятки тысяч RPS) может вызвать сильную деградацию производительности дисковой подсистемы ноды Kubernetes из-за гигантского объема записи в `/var/log/pods`. В продакшене логируют только ошибки (например, response_code >= 400).

## На собеседовании

Вопрос на собеседовании в Lamoda: 'Если Go-приложение упало в panic, что появится в логах Envoy и что увидит клиент?' Ответ: Go-сервер закроет TCP-соединение (TCP FIN/RST). Envoy зафиксирует `response_flags: 'UC'` (Upstream Connection Termination) или 'UF', запишет access-лог и вернет клиенту ответ `HTTP 502 Bad Gateway`.
