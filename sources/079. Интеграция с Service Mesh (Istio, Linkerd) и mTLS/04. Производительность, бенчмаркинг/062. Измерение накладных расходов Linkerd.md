# Измерение накладных расходов Linkerd: бенчмарк задержки прокси

## Условие

Linkerd proxy имеет ~1ms overhead per request. Измерьте влияние на ваше приложение. Напишите Go-бенчмарк для сравнения времени отклика с прокси и без него.

### Исходная формулировка

**Linkerd performance**: Linkerd proxy имеет ~1ms overhead per request. Измерьте влияние на ваше приложение.

## Теория

Каждый дополнительный уровень абстракции в сетевом стеке вносит задержку (latency overhead). При использовании Service Mesh сетевой пакет проходит через: 1) iptables NAT таблицы ядра; 2) сокет перехвата прокси (inbound); 3) TLS шифрование/дешифрование; 4) локальный loopback-сокет к приложению. Linkerd-proxy оптимизирован для минимизации этой задержки: накладные расходы обычно не превышают 0.5–1.5 мс на 99-м перцентиле (p99).

## Решение по шагам

Создайте высокоточный Go-бенчмарк на базе testing.B или автономного цикла.
Выполните серию замеров времени выполнения HTTP round-trip.
Рассчитайте среднее время, p50, p90 и p99 квантили.
Оцените процентный оверхед сетевого проксирования.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sort"
	"time"
)

// CalculateQuantiles рассчитывает перцентили задержки в миллисекундах
func CalculateQuantiles(latencies []time.Duration) (p50, p90, p99 float64) {
	if len(latencies) == 0 {
		return 0, 0, 0
	}
	sort.Slice(latencies, func(i, j int) bool { return latencies[i] < latencies[j] })

	toMS := func(d time.Duration) float64 { return float64(d.Microseconds()) / 1000.0 }

	n := len(latencies)
	p50 = toMS(latencies[n*50/100])
	p90 = toMS(latencies[n*90/100])
	p99 = toMS(latencies[n*99/100])
	return
}

func main() {
	// Локальный echo-сервер для симуляции
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	}))
	defer server.Close()

	client := &http.Client{
		Transport: &http.Transport{
			MaxIdleConnsPerHost: 50,
		},
	}

	samples := 1000
	latencies := make([]time.Duration, samples)

	// Прогрев соединений
	for i := 0; i < 50; i++ {
		resp, _ := client.Get(server.URL)
		if resp != nil {
			resp.Body.Close()
		}
	}

	// Замер задержек
	for i := 0; i < samples; i++ {
		start := time.Now()
		resp, err := client.Get(server.URL)
		if err == nil {
			resp.Body.Close()
		}
		latencies[i] = time.Since(start)
	}

	p50, p90, p99 := CalculateQuantiles(latencies)
	fmt.Printf("=== Benchmark Latency Profile (%d requests) ===\n", samples)
	fmt.Printf("P50: %.2f ms\n", p50)
	fmt.Printf("P90: %.2f ms\n", p90)
	fmt.Printf("P99: %.2f ms\n", p99)
	fmt.Println("Linkerd typical overhead: +0.5ms to +1.2ms added to baseline")
}
```

ℹ️ Реализация: Измерение накладных расходов Linkerd: бенчмарк задержки прокси (Упражнение 62)

## Под капотом

Linkerd достигает низкой латентности за счет использования epoll в Linux через библиотеку `mio` (Rust), минимального количества аллокаций памяти и передачи сокетов без копирования буферов (zero-copy splice там, где поддерживается).

## Подводные камни

Проведение бенчмарков с использованием `DisableKeepAlives: true` в HTTP-клиенте. В этом случае на каждый запрос будет происходить полное TCP и TLS рукопожатие (3 RTT), что исказит результаты в 10 раз.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Как eBPF (Cilium/Calico) может снизить задержку в Service Mesh?' Ответ: Традиционный iptables пересылает пакет через весь стек сетевого протокола ядра Linux (TCP/IP). eBPF sockmap перехватывает пакет прямо на уровне сокета (socket layer) и копирует его из сокета приложения в сокет прокси напрямую, минуя стек маршрутизации и экономя 20–30% времени задержки.
