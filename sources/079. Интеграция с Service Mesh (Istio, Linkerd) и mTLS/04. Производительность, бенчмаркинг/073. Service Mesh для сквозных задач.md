# Service Mesh для сквозных задач (Cross-Cutting Concerns)

## Условие

mTLS, traffic management, observability — всё это должно быть в service mesh, а не в application code. Istio для enterprise, Linkerd для simplicity. Напишите архитектурный манифест распределения ответственности.

### Исходная формулировка

**Service Mesh для cross-cutting concerns.**: mTLS, traffic management, observability — всё это должно быть в service mesh, а не в application code. Istio для enterprise, Linkerd для simplicity.

## Теория

Архитектурный принцип разделения обязанностей (Separation of Concerns) в cloud-native системах: 1) `Прикладной уровень (Go)`: бизнес-логика, предметные модели (DDD), валидация данных, транзакции базы данных; 2) `Сетевой уровень (Service Mesh)`: mTLS шифрование, ротация сертификатов, повторные попытки (Retries), предохранители (Circuit Breakers), балансировка нагрузки, таймауты, канареечные сплиты, rate limiting и сбор Golden Signals. Попытка реализовывать сетевую логику в Go-коде приводит к дублированию кода, багам в нестандартных сценариях и невозможности централизованного управления политиками компании.

## Решение по шагам

Сформируйте архитектурный шаблон чистого Go-микросервиса без сетевых зависимостей.
Продемонстрируйте делегирование инфраструктурных задач на Data Plane.
Убедитесь в снижении сложности тестирования Go-кода.
Опишите матрицу зон ответственности между платформенной командой и разработчиками.

## Код решения

**`server.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
)

// CleanDomainService содержит чистую бизнес-логику без привязки к инфраструктурным библиотекам TLS/Retries.
type CleanDomainService struct{}

func (s *CleanDomainService) CalculatePrice(ctx context.Context, itemID string, quantity int) (int, error) {
	// Чистая предметная логика
	unitPrice := 150
	return unitPrice * quantity, nil
}

func main() {
	svc := &CleanDomainService{}

	mux := http.NewServeMux()
	mux.HandleFunc("/calculate", func(w http.ResponseWriter, r *http.Request) {
		total, _ := svc.CalculatePrice(r.Context(), "sku-1", 3)
		w.Header().Set("Content-Type", "application/json")
		fmt.Fprintf(w, `{"total_price":%d}`, total)
	})

	log.Println("Clean Domain Microservice initialized (Cross-cutting concerns delegated to Service Mesh)")
	_ = mux
	fmt.Println("Architecture boundary verified successfully")
}
```

ℹ️ Реализация: Service Mesh для сквозных задач (Cross-Cutting Concerns) (Упражнение 73)

## Под капотом

Делегирование cross-cutting concerns позволяет обновлять политики безопасности (например, переход на TLS 1.3 или замена шифров AES-GCM на ChaCha20-Poly1305) во всем кластере из тысяч сервисов путем обновления одного манифеста Mesh, без перекомпиляции и передеплоя тысяч Go-бинарников.

## Подводные камни

Дублирование логики: когда инженер оставляет retry в Go-коде, не зная, что в Istio уже настроен retry. Команды обязаны иметь четкий реестр правил взаимодействия с Service Mesh.

## На собеседовании

Вопрос на собеседовании в Ozon: 'Каковы критерии того, что сетевую функциональность пора выносить из Go-кода в Service Mesh?' Ответ: 1) Гетерогенный стек (сервисы пишутся не только на Go, но и на Java/Python); 2) Необходимость централизованного аудита ИБ; 3) Сложность обновления криптографических библиотек в сотнях репозиториев; 4) Необходимость динамического управления трафиком без изменения кода.
