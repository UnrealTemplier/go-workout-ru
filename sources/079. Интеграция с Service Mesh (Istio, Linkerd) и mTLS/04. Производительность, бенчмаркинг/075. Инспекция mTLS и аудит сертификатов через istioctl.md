# Инспекция mTLS и аудит сертификатов через istioctl authn tls-check

## Условие

Включите PeerAuthentication в режиме STRICT. Убедитесь, что трафик между сервисами шифруется (проверка через istioctl authn tls-check или tcpdump). Напишите Go-утилиту верификации TLS-конфигурации.

### Исходная формулировка

**mTLS в Istio и проверка сертификатов.**: Включите `PeerAuthentication` в режиме `STRICT`. Убедитесь, что трафик между сервисами шифруется (проверка через `istioctl authn tls-check` или tcpdump).

## Теория

Для проверки корректности применения mTLS политик администраторы используют команду: `istioctl authn tls-check <pod-name> <service-name>`. Команда сопоставляет конфигурацию клиентского sidecar с серверной политикой `PeerAuthentication`. Статус `OK` означает, что обе стороны согласованы в режиме STRICT. Статус `CONFLICT` сигнализирует об аварии: например, сервер требует STRICT, а клиент настроен в DISABLE, что приведет к сбросу всех соединений.

## Решение по шагам

Изучите состояния таблицы istioctl tls-check (STATUS: OK, CONFLICT, AUTO).
Напишите Go-утилиту, парсящую отчет соответствия mTLS политик.
Проверьте валидность цепочки сертификатов.
Продемонстрируйте выявление конфигурационных конфликтов.

## Код решения

**`security.go`**

```go
package main

import (
	"fmt"
	"log"
)

type TLSCheckEntry struct {
	Host           string
	Port           int
	ClientStatus   string // STRICT, PERMISSIVE, DISABLE
	ServerPolicy   string // STRICT, PERMISSIVE, DISABLE
	ResolvedStatus string // OK, CONFLICT
}

func AuditMeshTLSAlignment(entries []TLSCheckEntry) []string {
	var conflicts []string
	for _, e := range entries {
		if e.ServerPolicy == "STRICT" && e.ClientStatus == "DISABLE" {
			conflicts = append(conflicts,
				fmt.Sprintf("CONFLICT on %s:%d: Server requires STRICT mTLS, but Client sends plaintext!", e.Host, e.Port))
		}
	}
	return conflicts
}

func main() {
	entries := []TLSCheckEntry{
		{Host: "order-service.default.svc.cluster.local", Port: 8080, ClientStatus: "STRICT", ServerPolicy: "STRICT", ResolvedStatus: "OK"},
		{Host: "legacy-db.default.svc.cluster.local", Port: 5432, ClientStatus: "DISABLE", ServerPolicy: "STRICT", ResolvedStatus: "CONFLICT"},
	}

	conflicts := AuditMeshTLSAlignment(entries)
	if len(conflicts) > 0 {
		for _, c := range conflicts {
			log.Printf("🚨 %s", c)
		}
	} else {
		fmt.Println("✅ All mTLS mesh configurations are in perfect alignment (OK)")
	}
}
```

ℹ️ Реализация: Инспекция mTLS и аудит сертификатов через istioctl authn tls-check (Упражнение 75)

## Под капотом

istioctl опрашивает endpoint istiod `/debug/authenticationz`, где хранится матрица всех пар клиентских кластеров Envoy и целевых слушателей (Listeners).

## Подводные камни

Оставление не-меш сервисов (сервисов без sidecar) в одном неймспейсе с политикой STRICT: трафик от таких сервисов будет мгновенно заблокирован.

## На собеседовании

Вопрос на собеседовании в Lamoda: 'Как проверить факт mTLS шифрования трафика с помощью tcpdump внутри контейнера?' Ответ: Запустить `tcpdump -i any -A 'tcp port 8080'` на интерфейсе eth0 пода. При активном mTLS полезная нагрузка будет представлять собой нечитаемый бинарный мусор (TLS Application Data), а открытый HTTP JSON текст будет виден только на интерфейсе loopback (lo) между Envoy и Go-бинарником.
