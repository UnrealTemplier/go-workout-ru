# Disaster Recovery тестирование: отказоустойчивость Service Mesh и Control Plane

## Условие

Регулярно тестируйте disaster recovery: KMS key compromise response, S3 bucket recovery из backup, Service mesh failover при control plane failure, multi-region failover. Напишите Go-утилиту проверки живучести Data Plane.

### Исходная формулировка

**Test disaster recovery.**: Регулярно тестируйте:
* KMS key compromise response
* S3 bucket recovery из backup
* Service mesh failover при control plane failure
* Multi-region failover

## Теория

План аварийного восстановления (Disaster Recovery Plan) проверяет устойчивость при катастрофических сценариях: 1) Полный отказ Control Plane (`istiod` упал, kube-apiserver недоступен): Data Plane (Envoy) обязан продолжать маршрутизировать трафик без потерь; 2) Падение целого региона: East-West Gateway и DNS должны автоматически перенаправить трафик в живой регион; 3) Компрометация корневого CA: процедура экстренной ротации Root CA без даунтайма.

## Решение по шагам

Смоделируйте аварийную недоступность контроллера управления.
Напишите Go-утилиту, проверяющую сохранение доступности сервисов через существующие соединения.
Проверьте работу Data Plane в автономном режиме.
Сформулируйте чеклист действий дежурного инженера при аварии.

## Код решения

**`server.go`**

```go
package main

import (
	"fmt"
	"log"
	"time"
)

type DRHealthCheck struct {
	ControlPlaneOnline bool
	DataPlaneOnline    bool
	TrafficRoutingOK   bool
}

func EvaluateDRResilience(check DRHealthCheck) {
	fmt.Println("=== Disaster Recovery Verification Scenario ===")
	log.Printf("Control Plane (istiod): Online = %v", check.ControlPlaneOnline)
	log.Printf("Data Plane (Envoy Proxies): Online = %v", check.DataPlaneOnline)

	if !check.ControlPlaneOnline && check.DataPlaneOnline {
		log.Println("✅ DR Resilience Confirmed: Data Plane successfully routes traffic independently!")
	} else if !check.DataPlaneOnline {
		log.Println("🚨 CRITICAL: Data plane failure detected!")
	}
}

func main() {
	// Симуляция падения Control Plane
	simulatedCrash := DRHealthCheck{
		ControlPlaneOnline: false, // istiod упал
		DataPlaneOnline:    true,  // Envoy живы
		TrafficRoutingOK:   true,
	}

	EvaluateDRResilience(simulatedCrash)
	fmt.Println("Disaster recovery simulation completed successfully")
}
```

ℹ️ Реализация: Disaster Recovery тестирование: отказоустойчивость Service Mesh и Control Plane (Упражнение 79)

## Под капотом

Envoy Data Plane полностью декаплирован от istiod. Все активные соединения, TLS-сертификаты и маршруты кэшируются в памяти процесса Envoy. Пока сертификаты действительны, сетевой трафик пользователей не замечает сбоя управляющего слоя.

## Подводные камни

Если в момент падения istiod происходит массовый рестарт подов приложения, новые поды не смогут получить sidecar-конфигурацию от упавшего istiod и зависнут в `Init:0/1`.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Каково максимальное допустимое время простоя istiod до начала деградации Data Plane?' Ответ: Время равно минимальному остаточному сроку действия mTLS сертификатов SVID (обычно от 6 до 12 часов). Если istiod не восстановится до истечения срока действия сертификатов подов, новые TLS сессии перестанут устанавливаться.
