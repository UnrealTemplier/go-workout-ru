# Управление повторами и таймаутами на уровне Service Mesh

## Условие

В VirtualService настройте retry (3 попытки, таймаут 2с) для запросов к downstream-сервису. Симулируйте ошибки и убедитесь, что Istio повторяет запросы. Реализуйте в Go-сервисе проверку идемпотентности.

### Исходная формулировка

**Retry и Timeout на уровне Service Mesh.**: В `VirtualService` настройте retry (3 попытки, таймаут 2с) для запросов к downstream-сервису. Симулируйте ошибки и убедитесь, что Istio повторяет запросы.

## Теория

Сетевые ошибки уровня 'connection reset by peer', 'broken pipe' или временные 503 в облачной динамической среде неизбежны (перемещение подов, рестарты нод). Перенос повторов в Service Mesh гарантирует единый стандарт устойчивости для всех микросервисов. Однако критическим требованием к Go-бэкендам является обеспечение идемпотентности: обработка запроса с одним и тем же уникальным ключом (`X-Request-Id` или `Idempotency-Key`) обязана возвращать один и тот же результат без повторного выполнения транзакций.

## Решение по шагам

Реализуйте потокобезопасное хранилище обработанных транзакций в Go.
Проверьте отсечение повторных списаний средств при повторах Envoy.
Смоделируйте автоматический возврат закешированного ответа.
Убедитесь в корректной обработке заголовка x-envoy-attempt-count.

## Код решения

**`server.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"sync"
)

type TransactionStore struct {
	mu      sync.Mutex
	records map[string]string
}

var txnDB = &TransactionStore{records: make(map[string]string)}

func ChargeHandler(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	attempt := r.Header.Get("X-Envoy-Attempt-Count")

	if key == "" {
		http.Error(w, "Idempotency-Key header is required", http.StatusBadRequest)
		return
	}

	txnDB.mu.Lock()
	defer txnDB.mu.Unlock()

	// Если транзакция уже обработана ранее — возвращаем сохраненный ответ
	if prevResp, exists := txnDB.records[key]; exists {
		log.Printf("[Idempotency HIT] Key=%s, Envoy Attempt=%s -> Returning cached result", key, attempt)
		w.Header().Set("Content-Type", "application/json")
		w.Header().Set("X-Idempotent-Replay", "true")
		w.WriteHeader(http.StatusOK)
		w.Write([]byte(prevResp))
		return
	}

	// Выполняем списание денег первый раз
	log.Printf("[Processing Payment] Key=%s, Envoy Attempt=%s -> Executing charge...", key, attempt)
	newResp := fmt.Sprintf(`{"status":"charged","key":"%s"}`, key)
	txnDB.records[key] = newResp

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	w.Write([]byte(newResp))
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/api/charge", ChargeHandler)

	srv := &http.Server{Addr: ":8080", Handler: mux}
	_ = srv
	fmt.Println("Idempotent payment handler verified successfully")
}
```

ℹ️ Реализация: Управление повторами и таймаутами на уровне Service Mesh (Упражнение 64)

## Под капотом

Envoy выполняет повтор, если статус ответа соответствует правилу `retryOn`. Envoy не очищает и не модифицирует заголовок `Idempotency-Key`, гарантируя, что он в точности дойдет до второй попытки бэкенда.

## Подводные камни

Хранение идемпотентных ключей в локальной памяти инстанса Go (in-memory map): при повторе Envoy может направить запрос на ДРУГОЙ pod сервиса! В продакшене идемпотентные ключи обязаны храниться в распределенном кэше (Redis Cluster).

## На собеседовании

Вопрос на собеседовании в Lamoda: 'Почему в распределенных системах важно использовать распределенную блокировку (SETNX) при проверке Idempotency-Key?' Ответ: Если два параллельных запроса с одинаковым ключом поступят на два разных инстанса одновременно, простая проверка `exists` может вернуть `false` на обоих узлах. Атомарный `SET key val NX EX 60` в Redis гарантирует, что только один поток начнет выполнение операции.
