# Менеджер клиентских подключений (Connection Hub Pattern)

## Условие

Реализуйте Hub: `map[clientID]chan Event`, mutex/RWMutex для безопасности. Каждый клиент — отдельная goroutine, читающая из личного канала и пишущая в `http.ResponseWriter`. При disconnect (ошибка write или `http.CloseNotifier`) — удаление из hub. Объясните, почему `sync.Map` может быть альтернативой при высокой конкуренции.

### Исходная формулировка

**Connection Hub.**: Реализуйте Hub: `map[clientID]chan Event`, mutex/RWMutex для безопасности. Каждый клиент — отдельная goroutine, читающая из личного канала и пишущая в `http.ResponseWriter`. При disconnect (ошибка write или `http.CloseNotifier`) — удаление из hub. Объясните, почему `sync.Map` может быть альтернативой при высокой конкуренции.

## Теория

При обслуживании тысяч параллельных SSE-соединений сервер обязан отслеживать состояние каждого активного подписчика.

### Архитектурный паттерн Connection Hub:
1. **Реестр подписчиков:** Централизованная структура данных, сопоставляющая уникальный `clientID` с персональным каналом доставки задач `chan SSEEvent`.
2. **Изоляция горутин (Thread Confinement):**
   - Главный брокер пишет событие в каналы подписчиков.
   - Каждый клиент обслуживается своей выделенной горутиной (горутина HTTP-обработчика), которая читает из личного канала и пишет в свой `http.ResponseWriter`.
3. **Управление жизненным циклом (Lifecycle Hooks):**
   - `Register`: добавление канала в Hub.
   - `Unregister`: удаление из Hub и закрытие канала при отмене контекста или ошибке записи.
4. **Выбор структуры данных (`sync.RWMutex` vs `sync.Map`):**
   - `sync.RWMutex` эффективен при относительно небольшом количестве изменений (редкие регистрации) и частых чтениях (рассылка).
   - `sync.Map` предпочтителен при огромной конкуренции на множестве процессорных ядер CPU, так как использует lock-free алгоритмы для стабильных множеств ключей, предотвращая контеншн мьютекса.

## Решение по шагам

1. Создайте структуру `ConnectionHub` с защищенной мапой каналов.
2. Реализуйте потокобезопасные методы `Register(id string) chan SSEEvent` и `Unregister(id string)`.
3. Реализуйте метод `Broadcast(evt SSEEvent)` с неблокирующей отправкой.
4. Напишите HTTP-хендлер, регистрирующий клиента в Hub и слушающий его канал до отключения.

## Код решения

**`connection_hub.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type SSEEvent struct {
	Type string
	Data string
}

type ConnectionHub struct {
	mu      sync.RWMutex
	clients map[string]chan SSEEvent
}

func NewConnectionHub() *ConnectionHub {
	return &ConnectionHub{
		clients: make(map[string]chan SSEEvent),
	}
}

func (h *ConnectionHub) Register(clientID string) chan SSEEvent {
	h.mu.Lock()
	defer h.mu.Unlock()

	ch := make(chan SSEEvent, 16) // Буферизированный канал на 16 сообщений
	h.clients[clientID] = ch
	fmt.Printf("[HUB] Зарегистрирован клиент: %s (Всего активно: %d)\n", clientID, len(h.clients))
	return ch
}

func (h *ConnectionHub) Unregister(clientID string) {
	h.mu.Lock()
	defer h.mu.Unlock()

	if ch, exists := h.clients[clientID]; exists {
		delete(h.clients, clientID)
		close(ch)
		fmt.Printf("[HUB] Отключен клиент: %s (Осталось: %d)\n", clientID, len(h.clients))
	}
}

func (h *ConnectionHub) Broadcast(evt SSEEvent) {
	h.mu.RLock()
	defer h.mu.RUnlock()

	for clientID, ch := range h.clients {
		select {
		case ch <- evt:
		default:
			// Защита от медленных клиентов (Slow Consumer Protection)
			fmt.Printf("[HUB WARNING] Буфер клиента %s переполнен, пропуск события!\n", clientID)
		}
	}
}

func (h *ConnectionHub) ClientCount() int {
	h.mu.RLock()
	defer h.mu.RUnlock()
	return len(h.clients)
}

func (h *ConnectionHub) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	clientID := r.URL.Query().Get("client_id")
	if clientID == "" {
		clientID = fmt.Sprintf("client_%d", time.Now().UnixNano())
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	clientChan := h.Register(clientID)
	defer h.Unregister(clientID)

	ctx := r.Context()
	for {
		select {
		case <-ctx.Done():
			return // Сокет разорван клиентом
		case evt, ok := <-clientChan:
			if !ok {
				return // Канал закрыт хабом
			}
			fmt.Fprintf(w, "event: %s\ndata: %s\n\n", evt.Type, evt.Data)
			flusher.Flush()
		}
	}
}

func main() {
	hub := NewConnectionHub()
	ts := httptest.NewServer(hub)
	defer ts.Close()

	fmt.Println("=== Старт тестирования Connection Hub ===")

	// 1. Подключаем клиента А
	clientAURL := ts.URL + "?client_id=client_alice"
	respA, _ := http.Get(clientAURL)
	defer respA.Body.Close()

	// 2. Рассылаем broadcast через Hub
	hub.Broadcast(SSEEvent{Type: "news", Data: "Go 1.24 released!"})

	time.Sleep(50 * time.Millisecond)
	fmt.Printf("Активных клиентов в хабе: %d\n", hub.ClientCount())
}
```

ℹ️ Потокобезопасный Connection Hub для управления пулом активных SSE-подписчиков

## Под капотом

Почему запись в `http.ResponseWriter` нельзя делать напрямую из горутины бродкаста `h.Broadcast()`?
Интерфейс `http.ResponseWriter` в Go **НЕ является потокобезопасным**! Одновременный вызов `w.Write()` из нескольких горутин приведет к гонке данных (Data Race), повреждению памяти буферов и панике рантайма.
Паттерн Hub передает данные через персональный канал `chan SSEEvent`, гарантируя, что в `http.ResponseWriter` каждого клиента пишет строго одна и та же горутина его обработчика.

## Подводные камни

1. **Небуферизированный канал `make(chan SSEEvent)`:** Если у одного клиента подвиснет TCP-соединение, запись `ch <- evt` заблокирует горутину рассылки для ВСЕХ остальных клиентов Hub! Канал обязан быть буферизированным, а отправка — неблокирующей (`select-default`).
2. **Паника отправки в закрытый канал (`send on closed channel`):** Всегда держите мьютекс `h.mu.Lock()` при удалении клиента и закрытии его канала.

## На собеседовании

**Вопрос:** В каких сценариях `sync.Map` производительнее обычной мапы с `sync.RWMutex` в Connection Hub?

**Ответ:** `sync.Map` оптимизирована под два конкретных сценария:
1. Когда ключ записывается один раз, а читается многократно.
2. Когда несколько горутин читают, записывают и перезаписывают непересекающиеся ключи.
В сервере SSE, где 10 000 клиентов непрерывно подключаются и отключаются на 64-ядерном сервере, обычный `RWMutex.RLock()` упрется в кэш-линии процессора (Cache Line Bouncing). `sync.Map` на атомиках исключает взаимные блокировки ядер CPU.
