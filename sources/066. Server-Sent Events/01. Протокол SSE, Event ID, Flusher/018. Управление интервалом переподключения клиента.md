# Управление интервалом переподключения клиента (Retry Interval)

## Условие

**Retry interval**: Отправляйте `retry: 3000\n` событие для указания браузеру интервала reconnect в миллисекундах.

## Теория

По умолчанию большинство браузеров при разрыве SSE-соединения ждут **3 секунды** (3000 мс) перед попыткой переподключения.

### Зачем серверу динамически управлять параметром `retry:`:
1. **Защита от Reconnection Storm при перезагрузке серверов:**
   Если вы деплоите новый релиз и рестартуете сервер с 50 000 клиентов, все 50 000 браузеров ударят в новый инстанс ровно через 3 секунды.
   Перед штатной остановкой (Graceful Shutdown) сервер может разослать:
   ```text
   retry: 15000\n\n
   ```
   заставляя клиентов выждать 15 секунд, давая подам Kubernetes время прогреться.
2. **Адаптивная пауза под нагрузку:**
   При сильной перегрузке платформы сервер может увеличить интервал реконнекта до 30–60 секунд, предотвращая DoS собственной инфраструктуры.
3. **Фиксация в клиенте:**
   Как только браузер видит строку `retry: 5000`, его внутренний таймер переподключения устанавливается в 5000 мс и сохраняется для всех последующих попыток.

## Решение по шагам

1. Реализуйте хендлер, отправляющий директиву `retry: 4000\n\n` сразу при подключении клиента.
2. Напишите эмулятор клиента, считывающий этот параметр и меняющий таймер паузы перед реконнектом.
3. Продемонстрируйте переключение задержки.

## Код решения

**`retry_interval.go`**

```go
package main

import (
	"bufio"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strconv"
	"strings"
	"time"
)

func RetryConfiguredHandler(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")

	// Сервер принудительно задает клиенту интервал реконнекта в 4500 мс
	fmt.Fprintf(w, "retry: 4500\n\n")
	flusher.Flush()

	// Отправляем бизнес-событие
	fmt.Fprintf(w, "id: 1\ndata: Connected with custom retry\n\n")
	flusher.Flush()
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(RetryConfiguredHandler))
	defer ts.Close()

	fmt.Println("=== Клиент подключается к серверу и считывает директиву retry ===")
	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	scanner := bufio.NewScanner(resp.Body)
	var clientRetryInterval time.Duration = 3 * time.Second // Дефолт браузера

	for scanner.Scan() {
		line := scanner.Text()
		if strings.HasPrefix(line, "retry:") {
			msStr := strings.TrimSpace(strings.TrimPrefix(line, "retry:"))
			ms, err := strconv.Atoi(msStr)
			if err == nil {
				clientRetryInterval = time.Duration(ms) * time.Millisecond
				fmt.Printf("[CLIENT UPDATE] Сервер изменил интервал реконнекта на: %v (%d ms)\n",
					clientRetryInterval, ms)
			}
		} else if strings.HasPrefix(line, "data:") {
			fmt.Printf("[CLIENT EVENT]  Получены данные: %s\n", line)
		}
	}

	fmt.Printf("\nИтоговый настроенный интервал реконнекта клиента: %v\n", clientRetryInterval)
}
```

## Под капотом

Внутри спецификации EventSource:
Если значение после `retry:` состоит исключительно из цифр ASCII, браузер парсит его как целое число в миллисекундах и присваивает внутренней переменной `reconnection_time`.
Если значение содержит нечисловые символы, парсер обязан полностью проигнорировать всю строку, оставив предыдущее значение таймера нетронутым.

## Подводные камни

1. **Установка слишком маленького retry (< 100 ms):** Браузер может заблокировать слишком агрессивные реконнекты по соображениям безопасности либо зависнуть в цикле переподключений при падении сервера.
2. **Отсутствие терминатора `\n\n` после `retry:`:** Если написать `retry: 5000\n` без двойного перевода строк, директива останется в буфере парсера и не вступит в силу до следующего события.

## На собеседовании

**Вопрос:** Как применить команду `retry:` во время планового обновления (Rolling Update) кластера веб-серверов в Kubernetes?

**Ответ:** 
В хуке `preStop` жизненного цикла пода (Pod Lifecycle PreStop Hook):
1. Сервер отправляет всем подключенным клиентам фрейм:
   ```text
   retry: 10000
   event: system.reconnect
   data: {"reason": "maintenance"}
   \n\n
   ```
2. Сервер ждет 2 секунды и плавно закрывает соединения со своей стороны.
3. Клиенты получают команду ждать 10 секунд и засыпают.
4. В этот момент старый под удаляется, а новый под успевает подняться и пройти Readiness Probe до того, как клиенты начнут переподключаться!
