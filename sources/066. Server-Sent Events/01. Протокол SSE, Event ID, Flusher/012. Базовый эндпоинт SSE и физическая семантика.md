# Базовый эндпоинт SSE и физическая семантика двойного перевода строк

## Условие

Базовый SSE endpoint: Реализуйте HTTP handler с `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`. Используйте `http.Flusher` для принудительной отправки. Пишите в формате `data: {"msg":"hello"}\n\n`. Объясните, почему два `\n` — разделитель событий.

### Исходная формулировка

## Теория

При реализации SSE-эндпоинта критично понимать сетевую семантику протокола HTTP:

### Почему два `\n` являются разделителем событий:
В сетевых протоколах (HTTP, SMTP, MIME, SIP) двойной перевод строки `\r\n\r\n` (или `\n\n` в Unix) исторически обозначает **конец блока заголовков / метаданных**.
Внутри одного события SSE может идти несколько полей:
- `id: 1\n`
- `event: update\n`
- `data: hello\n`
Каждое поле отделяется **одинарным** `\n`.
Парсер не может знать, закончилось ли событие, пока не увидит **пустую строку** (то есть второй подряд символ `\n`). Встретив `\n\n`, парсер понимает: «Текущее событие полностью собрано, его можно диспатчить в пользовательский код!»

### Обязательные HTTP-заголовки:
- `Content-Type: text/event-stream; charset=utf-8`
- `Cache-Control: no-cache, no-transform` (`no-transform` запрещает CDN сжимать или модифицировать поток)
- `Connection: keep-alive`

## Решение по шагам

1. Напишите HTTP-хендлер `BaseSSEHandler`.
2. Установите все защитные заголовки от кэширования.
3. Отправьте 3 последовательных события в цикле.
4. Продемонстрируйте клиентом пошаговое вычитывание чанков.

## Код решения

**`base_sse_endpoint.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func BaseSSEHandler(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	// 1. Протокольные заголовки
	w.Header().Set("Content-Type", "text/event-stream; charset=utf-8")
	w.Header().Set("Cache-Control", "no-cache, no-transform")
	w.Header().Set("Connection", "keep-alive")
	w.Header().Set("X-Accel-Buffering", "no")

	// 2. Отправка сообщений в потоковом режиме
	for i := 1; i <= 3; i++ {
		// Формат: data: <json>\n\n
		fmt.Fprintf(w, "data: {\"msg\":\"hello\",\"seq\":%d}\n\n", i)
		flusher.Flush()
		time.Sleep(20 * time.Millisecond)
	}
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(BaseSSEHandler))
	defer ts.Close()

	fmt.Println("=== Вызов базового эндпоинта SSE ===")
	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	buf := make([]byte, 512)
	n, _ := resp.Body.Read(buf)
	fmt.Printf("Получено байт: %d\nСодержимое:\n%s\n", n, string(buf[:n]))
}
```

ℹ️ Базовый эндпоинт SSE с правильными заголовками и двойным переносом строк

## Под капотом

В протоколе HTTP/1.1 сервер Go автоматически активирует `Transfer-Encoding: chunked`, если `Content-Length` не задан, а запись идет через `w.Write()`. Каждый вызов `flusher.Flush()` формирует отдельный chunked-фрейм. В протоколе HTTP/2 механизм Chunked отсутствует: вместо него рантайм Go оборачивает байты во фрейм `DATA` (тип 0x0) с флагом потока `stream_id`.

## Подводные камни

1. **Использование пробела в пустой строке (`data: ...\n \n`):** Если в терминаторе вместо чистой пустой строки окажется пробел или табуляция, парсер расценит ее как продолжение поля и фрейм зависнет в буфере!
2. **Отсутствие заголовка `no-transform`:** Некоторые корпоративные прокси-серверы пытаются оптимизировать трафик, пропуская `text/html` и `text/event-stream` через минификаторы, ломая перевод строк.

## На собеседовании

**Вопрос:** Почему в SSE используется текстовый формат с разделителями `\n\n`, а не бинарная длина пакета (как 4-байтный префикс длины в gRPC/Protobuf)?

**Ответ:** Протокол SSE создавался для максимальной простоты отладки и нативной интеграции с веб-платформой. Любой разработчик может открыть URL стрима в браузере или cURL и сразу увидеть форматированный лог сообщений глазами без необходимости использовать специальные парсеры протоколов.
