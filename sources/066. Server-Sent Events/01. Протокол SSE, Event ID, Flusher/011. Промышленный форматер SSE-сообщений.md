# Промышленный форматер SSE-сообщений (Full Specification Formatter)

## Условие

Напишите хелпер, который форматирует данные по строгому текстовому стандарту SSE. Блок сообщения должен выглядеть так:
```text
event: messageAdded
data: {"text": "Привет, мир!"}
id: 42
retry: 5000

```

### Исходная формулировка

**Форматирование SSE-сообщений**: Напишите хелпер, который форматирует данные по строгому текстовому стандарту SSE. Блок сообщения должен выглядеть так (обратите внимание на обязательные двойные символы переноса строки `\n\n` в конце сообщения):
```text
event: messageAdded
data: {"text": "Привет, мир!"}
id: 42
retry: 5000

```

## Теория

Спецификация Server-Sent Events (W3C / WHATWG Living Standard) определяет четыре канонических поля блока сообщения:
1. **`event:`** — тип события (строка).
2. **`data:`** — полезная нагрузка (одна или несколько строк UTF-8).
3. **`id:`** — идентификатор события для возобновления (`Last-Event-ID`).
4. **`retry:`** — указание клиенту, сколько миллисекунд ждать перед повторным подключением при разрыве связи (Reconnection Time).

### Требования к форматированию:
- Порядок полей произвольный, но общепринятый стандарт: `id`, `event`, `retry`, затем `data`.
- Если `data` содержит символы переноса строки (`\n` или `\r\n`), форматер обязан разбить текст на отдельные строки и предварять каждую префиксом `data: `.
- Блок сообщения **ОБЯЗАН** завершаться двумя символами перевода строки `\n\n`.

## Решение по шагам

1. Создайте структуру `SSEMessage` со всеми 4 каноническими полями.
2. Реализуйте метод `Format() []byte` с поддержкой многострочных данных.
3. Добавьте проверку экранирования и валидации целочисленного retry.
4. Протестируйте форматирование одиночных и многострочных сообщений.

## Код решения

**`sse_formatter.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"strings"
)

type SSEMessage struct {
	ID    string
	Event string
	Retry int // В миллисекундах (0 = не отправлять)
	Data  string
}

// Format преобразует структуру в строгий W3C SSE текстовый фрейм
func (m SSEMessage) Format() []byte {
	var buf bytes.Buffer

	// 1. Поле id
	if m.ID != "" {
		buf.WriteString("id: ")
		buf.WriteString(m.ID)
		buf.WriteByte('\n')
	}

	// 2. Поле event
	if m.Event != "" && m.Event != "message" {
		buf.WriteString("event: ")
		buf.WriteString(m.Event)
		buf.WriteByte('\n')
	}

	// 3. Поле retry
	if m.Retry > 0 {
		buf.WriteString(fmt.Sprintf("retry: %d\n", m.Retry))
	}

	// 4. Поле data (поддержка многострочных данных)
	lines := strings.Split(strings.ReplaceAll(m.Data, "\r\n", "\n"), "\n")
	for _, line := range lines {
		buf.WriteString("data: ")
		buf.WriteString(line)
		buf.WriteByte('\n')
	}

	// 5. Обязательный терминатор конца фрейма: пустая строка (\n)
	buf.WriteByte('\n')

	return buf.Bytes()
}

func main() {
	msg := SSEMessage{
		ID:    "42",
		Event: "messageAdded",
		Retry: 5000,
		Data:  "{\"text\": \"Привет, мир!\"}",
	}

	fmt.Println("=== Эталонный фрейм SSE-сообщения ===")
	formatted := msg.Format()
	fmt.Print(string(formatted))

	// Многострочный пример
	multiMsg := SSEMessage{
		ID:    "43",
		Event: "log_stream",
		Data:  "Line 1: Server started\nLine 2: Connected to DB\nLine 3: Ready to serve",
	}
	fmt.Println("=== Многострочный фрейм SSE ===")
	fmt.Print(string(multiMsg.Format()))
}
```

## Под капотом

Почему спецификация SSE требует разбивать многострочные данные на отдельные префиксы `data:`?
В 2004 году, когда Ян Хиксон (Ian Hickson) проектировал спецификацию Server-Sent Events, ключевой целью была простота реализации парсера на любом языке программирования без сложных конечных автоматов. Построчный парсер `while ((line = readLine()) != null)` читает поток построчно: если строка начинается с `data: `, хвост дописывается в буфер аккумулятора, а при пустой строке буфер передается в приложение.

## Подводные камни

1. **Использование `fmt.Sprintf` для каждого фрейма:** При тысячах сообщений в секунду `fmt.Sprintf` создает паразитные аллокации строк. Используйте `bytes.Buffer` или `sync.Pool` для сборки байтовых слайсов.
2. **Нулевой `Retry`:** Если отправить `retry: 0`, браузер начнет бесконечно спамить сервер реконнектами без задержки при первом же сетевом сбое (Busy Reconnect Loop).

## На собеседовании

**Вопрос:** Что произойдет, если в поле `data:` передать сырые бинарные данные (например, JPEG картинку или Protobuf)?

**Ответ:** Протокол SSE спроектирован строго для передачи текстовых данных в кодировке UTF-8. Любые нулевые байты `\0` или случайные комбинации `\n\n` внутри бинарного файла разрушат парсер фреймов. Чтобы передавать бинарные данные по SSE, их необходимо кодировать в Base64 (что добавляет ~33% оверхеда) либо использовать протоколы с бинарным фреймингом (WebSocket / gRPC Web / Connect).
