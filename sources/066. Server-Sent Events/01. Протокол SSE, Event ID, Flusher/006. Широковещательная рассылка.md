# Широковещательная рассылка и защита от медленных клиентов (Broadcast Fan-Out)

## Условие

Реализуйте broadcast: центральный `chan Event` (или `pub/sub` в Redis), все клиенты подписаны. При событии — fan-out в каждый клиентский канал. Объясните, почему неблокирующая отправка (`select` с `default`) предотвращает slow client от блокировки всего hub.

### Исходная формулировка

**Broadcast.**: Реализуйте broadcast: центральный `chan Event` (или `pub/sub` в Redis), все клиенты подписаны. При событии — fan-out в каждый клиентский канал. Объясните, почему неблокирующая отправка (`select` с `default`) предотвращает slow client от блокировки всего hub.

## Теория

В системах реального времени (котировки бирж, спортивные матчи) одно событие рассылается десяткам тысяч активных SSE-клиентов (Fan-Out Broadcast).

### Проблема медленного клиента (The Slow Consumer Problem):
Один из 10 000 клиентов подключился через нестабильный 2G интернет в поезде. Его TCP-буфер приема забит.
Если диспетчер выполняет рассылку в цикле:
```go
for _, clientChan := range clients {
    clientChan <- event // БЛОКИРОВКА!
}
```
Горутина диспетчера намертво заблокируется на этом медленном клиенте. В этот момент доставка событий ВСЕМ остальным 9 999 клиентам с идеальным гигабитным каналом **полностью остановится**!

### Решение: Неблокирующий Fan-Out с селектором `default`:
```go
select {
case clientChan <- event:
    // Успешно помещено в буфер
default:
    // Буфер полон -> Дроп события или фиксация перегрузки
    atomic.AddInt64(&droppedEvents, 1)
}
```
Диспетчер никогда не ждет медленного подписчика, гарантируя нулевую задержку для остальной аудитории.

## Решение по шагам

1. Создайте структуру диспетчера `BroadcastManager`.
2. Реализуйте метод `Publish(evt Event)` с неблокирующей веерной отправкой через `select { case ch <- evt: default: }`.
3. Смоделируйте двух клиентов: быстрый (своевременно читает) и медленный (не читает из канала).
4. Продемонстрируйте, что медленный клиент не замедляет быстрого.

## Код решения

**`fanout_broadcast.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type Event struct {
	ID   int
	Data string
}

type BroadcastHub struct {
	mu            sync.RWMutex
	subscribers   map[string]chan Event
	droppedEvents atomic.Int64
}

func NewBroadcastHub() *BroadcastHub {
	return &BroadcastHub{
		subscribers: make(map[string]chan Event),
	}
}

func (h *BroadcastHub) Subscribe(id string, bufferSize int) chan Event {
	h.mu.Lock()
	defer h.mu.Unlock()

	ch := make(chan Event, bufferSize)
	h.subscribers[id] = ch
	return ch
}

// Broadcast отправляет событие всем подписчикам с защитой от медленных клиентов
func (h *BroadcastHub) Broadcast(evt Event) {
	h.mu.RLock()
	defer h.mu.RUnlock()

	for clientID, ch := range h.subscribers {
		select {
		case ch <- evt:
			// Успешно доставлено в очередь клиента
		default:
			// Клиент медленный: канал полон! Дропаем и увеличиваем счетчик
			h.droppedEvents.Add(1)
			fmt.Printf("[SLOW CONSUMER] Клиент '%s' не успевает читать! Событие #%d сброшено.\n",
				clientID, evt.ID)
		}
	}
}

func main() {
	hub := NewBroadcastHub()

	// 1. Быстрый подписчик (буфер 10)
	fastClient := hub.Subscribe("fast_client", 10)

	// 2. Медленный подписчик (буфер всего 2 сообщения и он их не вычитывает)
	slowClient := hub.Subscribe("slow_client", 2)
	_ = slowClient

	fmt.Println("=== Рассылка 5 событий через Broadcast Hub ===")
	start := time.Now()

	for i := 1; i <= 5; i++ {
		hub.Broadcast(Event{ID: i, Data: fmt.Sprintf("Tick %d", i)})
	}

	elapsed := time.Since(start)
	fmt.Printf("Время всей рассылки: %v (Мгновенно, без блокировок!)\n", elapsed)

	// Быстрый клиент вычитывает все 5 событий
	fmt.Println("\nБыстрый клиент получил:")
	for len(fastClient) > 0 {
		evt := <-fastClient
		fmt.Printf("  -> Событие: #%d (%s)\n", evt.ID, evt.Data)
	}

	fmt.Printf("\nВсего сброшено событий из-за медленных клиентов: %d\n", hub.droppedEvents.Load())
}
```

## Под капотом

Что происходит в рантайме Go при `select { case ch <- x: default: }`?
Инструкция компилируется в функцию рантайма `selectnbsend(c, elem)`.
Функция захватывает lock канала `hchan.lock` и мгновенно проверяет условие: `c.qcount == c.dataqsiz` (буфер полон) и `c.recvq.first == nil` (нет ожидающих читателей). Если условие истинно, функция освобождает мьютекс и мгновенно возвращает `false`, не вызывая планировщик `gopark`. Это гарантирует константное время исполнения \(O(1)\).

## Подводные камни

1. **Блокировка на отправке:** Использование `ch <- evt` без `select-default` превратит любой сетевой лаг одного пользователя в глобальный отказ сервиса для всей компании.
2. **Утечка отписавшихся клиентов:** Если клиент отключился, а его канал не удалили из мапы `subscribers`, память каналов будет утекать бесконечно.

## На собеседовании

**Вопрос:** Если для критичных финансовых данных нельзя сбрасывать сообщения медленных клиентов (`default: drop`), как поступить архитектурно?

**Ответ:** 
1. **Канал управления состоянием сессии:** Вместо потери данных клиент принудительно отключается сервером: `close(clientChan)` с кодом `408 Request Timeout`.
2. Клиент переподключается с заголовком `Last-Event-ID`.
3. Пропущенные финансовые события досылаются из персистентного брокера (Kafka / Redis Stream), не задерживая real-time брокер оперативной памяти.
