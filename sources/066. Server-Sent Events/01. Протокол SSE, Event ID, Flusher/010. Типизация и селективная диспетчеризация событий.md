# Типизация и селективная диспетчеризация событий (Event Types)

## Условие

Используйте `event: message_type\n` перед `data:` для разных типов событий. Клиент на JS может делать `evtSource.addEventListener('user.updated', ...)`. Объясните разделение потоков.

### Исходная формулировка

**Event types**: Используйте `event: message_type\n` перед `data:` для разных типов событий. Клиент на JS может делать `evtSource.addEventListener('user.updated', ...)`.

## Теория

При проектировании интерфейсов реального времени на базе SSE критично не превращать поток данных в «кашу» нетипизированных JSON-объектов.

### Проблема отсутствия типизации:
Если все сообщения отправляются как дефолтные:
```text
data: {"type": "user.updated", "payload": {...}}
\n\n
```
Клиентский JavaScript вынужден слушать общий `onmessage`, парсить JSON для абсолютно каждого события, делать ветвление `switch (msg.type)` и только потом передавать управление в нужный компонент React/Vue. При 500 событиях в секунду это приводит к лагам UI и просадке FPS браузера.

### Стандартное решение: W3C Named Event Types:
1. Сервер явно указывает поле `event:` перед телом:
   ```text
   event: user.updated
   data: {"id": 42, "name": "Анна"}
   \n\n
   ```
2. Браузер на уровне нативного C++ движка WebKit/Blink диспатчит событие **только** зарегистрированным слушателям `addEventListener('user.updated', callback)`.
3. Дефолтный обработчик `onmessage` даже не вызывается, экономя такты CPU клиента.

## Решение по шагам

1. Создайте структуру события с обязательным полем `Type`.
2. Напишите HTTP-обработчик, транслирующий события с префиксом `event: <type>`.
3. Создайте симулятор двух разнородных потоков: системные метрики (`metrics.cpu`) и уведомления пользователя (`user.alert`).
4. Продемонстрируйте корректный вывод фреймов.

## Код решения

**`event_types_demo.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

type EventMessage struct {
	Type string
	Data string
}

func EventTypesHandler(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	events := []EventMessage{
		{Type: "user.created", Data: `{"user_id": 101, "role": "admin"}`},
		{Type: "metrics.cpu", Data: `{"load_percent": 42.8, "cores": 8}`},
		{Type: "user.updated", Data: `{"user_id": 101, "status": "active"}`},
	}

	for _, evt := range events {
		// Стандарт предписывает: event идет строго перед data
		fmt.Fprintf(w, "event: %s\ndata: %s\n\n", evt.Type, evt.Data)
		flusher.Flush()
		time.Sleep(10 * time.Millisecond)
	}
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(EventTypesHandler))
	defer ts.Close()

	fmt.Println("=== Чтение типизированного потока SSE ===")
	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	buf := make([]byte, 512)
	n, _ := resp.Body.Read(buf)
	fmt.Printf("Полученный поток:\n%s\n", string(buf[:n]))
}
```

## Под капотом

Внутри реализации `EventSource` в Chromium (файл `event_source.cc`):
Когда парсер встречает строку `event: foo`, внутреннее строковое поле `event_name_` устанавливается в `"foo"`. При встрече терминатора `\n\n` движок создает объект `MessageEvent` с именем события `event_name_` и вызывает нативный метод `DispatchEvent(event)`. Если обработчик `addEventListener("foo")` не был зарегистрирован, событие просто отбрасывается без создания JS-объектов в V8 heap.

## Подводные камни

1. **Пробел между `event:` и типом:** Согласно RFC, пробел после двоеточия обязателен (`event: my_type`). Без пробела браузер расценит имя события как `:my_type` (включая двоеточие).
2. **Перевод строки внутри имени события:** Имя события не должно содержать `\r` или `\n`, так как это разрушит протокольный фрейминг.

## На собеседовании

**Вопрос:** Может ли одно SSE-сообщение содержать несколько полей `data:` подряд?

**Ответ:** Да! Согласно спецификации W3C SSE, если во фрейме передается несколько строк `data:`:
```text
data: {"part": 1}
data: {"part": 2}
\n\n
```
Клиентский парсер объединяет их через символ переноса строки `\n`. В JavaScript свойство `e.data` получит строку `{"part": 1}\n{"part": 2}`. Это штатный способ передачи многострочных документов или фрагментов кода без предварительного JSON-экранирования.
