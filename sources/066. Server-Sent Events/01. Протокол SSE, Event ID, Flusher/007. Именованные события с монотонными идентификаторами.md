# Именованные события с монотонными идентификаторами (Event Type & Sequence IDs)

## Условие

Расширьте сервер: отправляйте события с полями `event: message`, `id: <порядковый номер>`, `data: ...`. Клиент должен различать типы событий и логировать их.

### Исходная формулировка

**Именованные события и `id`.**: Расширьте сервер: отправляйте события с полями `event: message`, `id: <порядковый номер>`, `data: ...`. Клиент должен различать типы событий и логировать их.

## Теория

В промышленных системах поток SSE состоит из множества разнородных типов бизнес-событий, каждое из которых должно быть строго упорядочено.

### Структура канонического фрейма:
```text
event: order_created
id: 10001
data: {"order_id": 9948, "amount": 1500}

event: order_paid
id: 10002
data: {"order_id": 9948, "transaction_id": "tx_abc"}

event: order_shipped
id: 10003
data: {"order_id": 9948, "courier": "СДЭК"}
```

### Преимущества связки `event` + `id`:
1. **Логический порядок:** Клиентский фронтенд гарантированно видит смену статусов в хронологическом порядке.
2. **Селективная фильтрация:** Модуль аналитики подписывается только на `order_paid`, а модуль логистики — на `order_shipped`.
3. **Атомарность восстановления:** При сбое связи клиент восстановит поток ровно с той точки, на которой прервался.

## Решение по шагам

1. Создайте структуру типизированного события `TypedEvent` с полями `Type`, `SeqID`, `Data`.
2. Реализуйте атомарный генератор последовательности `atomic.Int64`.
3. Напишите HTTP SSE-сервер, генерирующий поток разнородных событий.
4. Создайте тестовый клиент на Go, парсящий входящий поток и маршрутизирующий события по типам.

## Код решения

**`typed_stream.go`**

```go
package main

import (
	"bufio"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync/atomic"
)

type TypedEvent struct {
	Type  string
	SeqID int64
	Data  string
}

type TypedEventPublisher struct {
	sequence atomic.Int64
}

func (p *TypedEventPublisher) NextEvent(eventType, payload string) TypedEvent {
	return TypedEvent{
		Type:  eventType,
		SeqID: p.sequence.Add(1),
		Data:  payload,
	}
}

func TypedSSEHandler(pub *TypedEventPublisher) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		flusher, ok := w.(http.Flusher)
		if !ok {
			http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
			return
		}

		w.Header().Set("Content-Type", "text/event-stream")

		events := []TypedEvent{
			pub.NextEvent("order_created", `{"id":101,"status":"NEW"}`),
			pub.NextEvent("payment_captured", `{"id":101,"amount":3500}`),
			pub.NextEvent("delivery_dispatched", `{"id":101,"tracking":"RU9988"}`),
		}

		for _, evt := range events {
			fmt.Fprintf(w, "event: %s\nid: %d\ndata: %s\n\n", evt.Type, evt.SeqID, evt.Data)
			flusher.Flush()
		}
	}
}

func main() {
	pub := &TypedEventPublisher{}
	ts := httptest.NewServer(TypedSSEHandler(pub))
	defer ts.Close()

	fmt.Println("=== Клиент подключается и парсит типизированный поток ===")
	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	scanner := bufio.NewScanner(resp.Body)
	var curEvent, curID, curData string

	for scanner.Scan() {
		line := scanner.Text()

		if strings.HasPrefix(line, "event: ") {
			curEvent = strings.TrimPrefix(line, "event: ")
		} else if strings.HasPrefix(line, "id: ") {
			curID = strings.TrimPrefix(line, "id: ")
		} else if strings.HasPrefix(line, "data: ") {
			curData = strings.TrimPrefix(line, "data: ")
		} else if line == "" && curData != "" {
			// Пустая строка означает конец фрейма события!
			fmt.Printf("[CLIENT PARSER] Принято событие: тип = %-18s | ID = %s | Data = %s\n",
				curEvent, curID, curData)
			curEvent, curID, curData = "message", "", ""
		}
	}
}
```

## Под капотом

В сетевом стеке HTTP порядок следования чанков (Chunks) внутри одного TCP-соединения гарантируется протоколом TCP (Sequence Number в заголовке TCP).
Байты передаются строго FIFO. Монотонный `SeqID` на уровне приложения позволяет клиенту детектировать потерю целых пакетов при сетевом реконнекте, сверяя `NewID == ExpectedID + 1`.

## Подводные камни

1. **Несброшенные поля парсера при разборе:** Если после пустой строки `\n\n` не очистить переменную `curEvent`, следующее событие без явного `event:` ошибочно унаследует тип предыдущего!
2. **Переполнение целочисленного `id`:** Использование `int32` переполнится при 2 миллиардах событий. Всегда используйте `int64`.

## На собеседовании

**Вопрос:** Как избежать генерации дубликатов `SeqID` при наличии 10 реплик подов SSE-сервера за балансировщиком?

**Ответ:** Порядковый номер `SeqID` генерируется не на уровне отдельного пода, а на уровне централизованной шины событий (Kafka Partition Offset или Redis Stream ID). Поды шлюза лишь транслируют этот глобальный офсет в поле `id: <offset>` фрейма SSE, гарантируя глобальную согласованность последовательности во всем кластере.
