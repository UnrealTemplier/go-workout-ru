# Кольцевой буфер реконнекта на стороне сервера (Server-side Reconnection Ring Buffer)

## Условие

**Server-side reconnection buffer**: Храните последние N событий (или события за M минут) в ring buffer. При reconnect с `Last-Event-ID` отправляйте пропущенные из буфера.

## Теория

При обслуживании сотен тысяч пользователей хранить полную историю всех событий в оперативной памяти каждого процесса невозможно — это приведет к мгновенному переполнению памяти (OOM).

### Алгоритмическое решение: Кольцевой буфер фиксированного размера (Ring Buffer):
1. Выделяется слайс емкостью \(N\) элементов (например, \(N = 1000\)).
2. Указатель записи `head` инкрементируется циклически:
   $$head = (head + 1) \pmod N$$
3. Старые события перезаписываются новыми без дополнительных аллокаций памяти кучи (\(O(1)\) по времени и \(O(1)\) по памяти).
4. **Поиск при реконнекте:**
   - Если переданный `Last-Event-ID` старше самого старого элемента в буфере: отдается ошибка рассинхронизации.
   - Иначе: последовательно вычитываются элементы от `Last-Event-ID + 1` до текущей вершины.

## Решение по шагам

1. Создайте структуру `RingEventBuffer` с фиксированным массивом и указателем `head`.
2. Реализуйте метод `Push(event SSEEvent)` с перезаписью по модулю \(N\).
3. Реализуйте метод `GetEventsSince(lastID int64) ([]SSEEvent, bool)`.
4. Продемонстрируйте корректную работу при переполнении буфера.

## Код решения

**`ring_reconnection_buffer.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type Event struct {
	ID   int64
	Data string
}

type RingReconnectionBuffer struct {
	mu       sync.RWMutex
	capacity int
	events   []Event
	head     int   // Индекс следующей записи
	isFull   bool
	minID    int64 // Минимальный доступный ID в кольце
}

func NewRingReconnectionBuffer(capacity int) *RingReconnectionBuffer {
	return &RingReconnectionBuffer{
		capacity: capacity,
		events:   make([]Event, capacity),
	}
}

func (r *RingReconnectionBuffer) Push(evt Event) {
	r.mu.Lock()
	defer r.mu.Unlock()

	r.events[r.head] = evt
	r.head = (r.head + 1) % r.capacity

	if r.head == 0 {
		r.isFull = true
	}

	// Обновляем минимальный ID
	if !r.isFull {
		r.minID = r.events[0].ID
	} else {
		// Самый старый элемент находится в текущей позиции head
		r.minID = r.events[r.head].ID
	}
}

// GetSince возвращает список пропущенных событий. Если lastID устарел (вытеснен) -> false
func (r *RingReconnectionBuffer) GetSince(lastID int64) ([]Event, bool) {
	r.mu.RLock()
	defer r.mu.RUnlock()

	total := r.head
	if r.isFull {
		total = r.capacity
		// Если клиент отстал сильнее, чем глубина кольца
		if lastID < r.minID {
			return nil, false // Данные безвозвратно утеряны
		}
	}

	var missed []Event
	startIdx := 0
	if r.isFull {
		startIdx = r.head
	}

	for i := 0; i < total; i++ {
		idx := (startIdx + i) % r.capacity
		if r.events[idx].ID > lastID {
			missed = append(missed, r.events[idx])
		}
	}

	return missed, true
}

func main() {
	// Создаем кольцевой буфер на 4 элемента
	rb := NewRingReconnectionBuffer(4)

	fmt.Println("=== Наполнение буфера событиями с 101 по 106 (Емкость = 4) ===")
	for i := 1; i <= 6; i++ {
		rb.Push(Event{ID: int64(100 + i), Data: fmt.Sprintf("Event #%d", i)})
	}
	// Буфер сейчас содержит: 103, 104, 105, 106 (101 и 102 вытеснены!)

	// Тест 1: Реконнект с актуальным Last-Event-ID = 104
	missed, ok := rb.GetSince(104)
	fmt.Printf("Тест 1 (Запрос с ID 104): Найдено = %v, Кол-во = %d\n", ok, len(missed))
	for _, m := range missed {
		fmt.Printf("  -> Дослано: ID=%d (%s)\n", m.ID, m.Data)
	}

	// Тест 2: Реконнект с безнадежно устаревшим ID = 101 (уже удален из памяти)
	missedOld, okOld := rb.GetSince(101)
	fmt.Printf("\nТест 2 (Запрос с ID 101 - вытеснен): Найдено = %v (Требуется полный Resync!)\n", okOld)
	_ = missedOld
}
```

ℹ️ Потокобезопасный кольцевой буфер фиксированной емкости без динамических аллокаций памяти

## Под капотом

Почему Ring Buffer с фиксированным срезом `make([]Event, N)` эффективнее каналов или связных списков?
В Ring Buffer массив памяти аллоцируется один раз при старте сервиса. Все последующие операции `Push` перезаписывают существующие слоты по указателю, не создавая мусора для Garbage Collector (Zero-Allocation Loop). Это гарантирует стабильную латентность p99 без пауз GC.

## Подводные камни

1. **Арифметика отрицательных индексов:** При расчете индекса начала `startIdx` важно следить за модуляцией, иначе возникнет паника `runtime error: index out of range`.
2. **Отсутствие RWMutex:** Конкурентная запись `Push` и чтение `GetSince` без мьютекса приведет к гонке данных (Data Race) и детекции race detector (`-race`).

## На собеседовании

**Вопрос:** Какую структуру данных в Redis вы выберете для организации распределенного Reconnection Buffer между множеством нод?

**Ответ:** **Redis Streams (`XADD` / `XRANGE`)** с аргументом ограничения длины `MAXLEN ~ N`:
```bash
XADD events:doc_42 MAXLEN ~ 1000 * field value
```
Redis Stream аппаратно оптимизирован как сжатое префиксное дерево (Radix Tree), поддерживает монотонные ID вида `<timestamp>-<seq>` и позволяет одной командой `XRANGE events:doc_42 (lastID +` выгрузить точные пропущенные дельты за константное время \(O(\log N + M)\).
