# Обработка заголовка Last-Event-ID и досыл пропущенных данных

## Условие

**Last-Event-ID header**: При reconnect браузер автоматически отправляет `Last-Event-ID` header. Ваш сервер должен прочитать его и отправить пропущенные события.

## Теория

Заголовок `Last-Event-ID` — ключевое звено отказоустойчивости веб-приложений.

### Сценарий автоматического восстановления:
1. Браузер слушал события, последнее успешное событие имело `id: 884`.
2. Ноутбук перешел в спящий режим (закрытие крышки) на 5 минут.
3. При открытии крышки `EventSource` обнаруживает разрыв TCP и немедленно отправляет HTTP GET:
   `GET /api/v1/feed HTTP/1.1`
   `Host: api.company.ru`
   `Last-Event-ID: 884`
4. Сервер читает заголовок через `r.Header.Get("Last-Event-ID")`.
5. Сервер выгружает из буфера события с `885` по `890` и выталкивает их клиенту.
6. Клиентский интерфейс обновляется мгновенно без необходимости перезагрузки страницы пользователем (`F5`).

## Решение по шагам

1. Создайте хранилище истории событий `EventStore`.
2. Реализуйте функцию парсинга заголовка `Last-Event-ID`.
3. Напишите HTTP-обработчик, досылающий дельту из хранилища.
4. Протестируйте сценарий реконнекта с заголовком и проверьте получение пропущенных данных.

## Код решения

**`last_event_id_handler.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strconv"
)

type EventLog struct {
	ID   int64
	Data string
}

// MockEventStore хранит историю последних событий
var globalHistory = []EventLog{
	{ID: 100, Data: "User Alice logged in"},
	{ID: 101, Data: "Order #99 created"},
	{ID: 102, Data: "Payment #99 approved"},
	{ID: 103, Data: "Order #99 shipped"},
}

func ResumingSSEHandler(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	// 1. Извлекаем Last-Event-ID
	lastIDStr := r.Header.Get("Last-Event-ID")
	var lastID int64
	if lastIDStr != "" {
		lastID, _ = strconv.ParseInt(lastIDStr, 10, 64)
		fmt.Printf("[SERVER] Клиент восстанавливает сессию после ID = %d\n", lastID)
	} else {
		fmt.Println("[SERVER] Новое подключение клиента (без Last-Event-ID)")
	}

	// 2. Отправляем пропущенные события из истории
	sentCount := 0
	for _, item := range globalHistory {
		if item.ID > lastID {
			fmt.Fprintf(w, "id: %d\ndata: %s\n\n", item.ID, item.Data)
			flusher.Flush()
			sentCount++
		}
	}

	fmt.Printf("[SERVER] Дослано клиенту: %d событий\n", sentCount)
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(ResumingSSEHandler))
	defer ts.Close()

	// Сценарий 1: Клиент подключается впервые
	fmt.Println("=== Сценарий 1: Первичное подключение ===")
	resp1, _ := http.Get(ts.URL)
	resp1.Body.Close()

	// Сценарий 2: Клиент переподключается с Last-Event-ID = 101
	fmt.Println("\n=== Сценарий 2: Реконнект с Last-Event-ID: 101 ===")
	req, _ := http.NewRequest(http.MethodGet, ts.URL, nil)
	req.Header.Set("Last-Event-ID", "101")
	resp2, _ := http.DefaultClient.Do(req)
	defer resp2.Body.Close()

	buf := make([]byte, 512)
	n, _ := resp2.Body.Read(buf)
	fmt.Printf("Полученные досланные данные (Ожидаются события 102 и 103):\n%s\n", string(buf[:n]))
}
```

## Под капотом

Заголовок `Last-Event-ID` чувствителен к регистру (Case-Insensitive) согласно стандарту HTTP. Метод Go `r.Header.Get("Last-Event-ID")` автоматически канонизирует имя заголовка (`MIMEHeader.CanonicalMIMEHeaderKey`), поэтому вызовы найдут значение независимо от того, прислал ли клиент `Last-Event-ID`, `last-event-id` или `Last-Event-Id`.

## Подводные камни

1. **Браузерные полифилы (Polyfills) и кастомные заголовки:** Если пользователь использует кастомный `fetch`-полифил вместо нативного `EventSource`, заголовок может передаваться в query: `?lastEventId=101`. Сервер должен проверять и заголовок, и query-параметр.
2. **Блокировка базы данных при поиске по истории:** Запрос `SELECT * FROM events WHERE id > last_id` обязан использовать B-Tree индекс по `id`, иначе full-scan по таблице положит базу при массовом реконнекте.

## На собеседовании

**Вопрос:** Что делать, если при реконнекте переданный `Last-Event-ID` слишком старый и уже удален из кэша памяти/Redis?

**Ответ:** 
1. Сервер отправляет специальное событие рассинхронизации:
   ```text
   event: error_out_of_sync
   data: {"action": "full_reload", "reason": "offset_expired"}
   \n\n
   ```
2. Клиентский JavaScript, перехватив событие, сбрасывает локальный стейт (Redux/Pinia) и выполняет полный REST-запрос снэпшота сущности, после чего повторно подписывается на SSE.
