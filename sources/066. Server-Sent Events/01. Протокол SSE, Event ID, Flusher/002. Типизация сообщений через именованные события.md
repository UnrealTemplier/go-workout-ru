# Типизация сообщений через именованные события (Named Events)

## Условие

Используйте `event: user_update\ndata: {...}` для типизации событий. На клиенте (JavaScript) используйте `eventSource.addEventListener('user_update', ...)`. Объясните, почему `event: message` (default) и кастомные имена event помогают разделить потоки данных.

### Исходная формулировка

**Named Events.**: Используйте `event: user_update\ndata: {...}` для типизации событий. На клиенте (JavaScript) используйте `eventSource.addEventListener('user_update', ...)`. Объясните, почему `event: message` (default) и кастомные имена event помогают разделить потоки данных.

## Теория

По умолчанию любой фрейм данных SSE, не содержащий строки `event:`, считается событием типа `message`. В браузере он триггерит стандартный коллбэк `eventSource.onmessage`.

### Преимущества Named Events (Именованных событий):
1. **Мультиплексирование потоков в одном сокете:**
   Вместо открытия трех разных соединений для чата, биржевых котировок и системных алертов сервер шлет их в **один HTTP-стрим**, маркируя заголовками:
   - `event: chat_message`
   - `event: stock_tick`
   - `event: alert`
2. **Декларативная подписка на клиенте:**
   Клиент регистрирует независимые обработчики:
   ```javascript
   const sse = new EventSource('/api/stream');
   sse.addEventListener('chat_message', (e) => renderChat(JSON.parse(e.data)));
   sse.addEventListener('stock_tick', (e) => updatePrice(JSON.parse(e.data)));
   ```
3. **Изоляция парсинга:**
   Обработчик чата не просыпается при получении сотен тиков котировок в секунду, разгружая поток рендеринга браузера.

## Решение по шагам

1. Создайте генератор форматированных фреймов SSE `FormatNamedEvent(eventName, eventID, data)`.
2. Реализуйте эмулятор диспетчера, отправляющего события разных типов.
3. Продемонстрируйте различие обработки дефолтных и именованных событий.

## Код решения

**`named_events.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"net/http/httptest"
)

// FormatSSEFrame формирует валидный по спецификации W3C текстовый фрейм
func FormatSSEFrame(eventType, id, payload string) []byte {
	var buf bytes.Buffer

	if id != "" {
		buf.WriteString(fmt.Sprintf("id: %s\n", id))
	}
	if eventType != "" && eventType != "message" {
		buf.WriteString(fmt.Sprintf("event: %s\n", eventType))
	}
	buf.WriteString(fmt.Sprintf("data: %s\n\n", payload))

	return buf.Bytes()
}

func MultiEventSSEHandler(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	// 1. Дефолтное событие (event: message)
	frame1 := FormatSSEFrame("message", "1", `{"text": "generic broadcast"}`)
	w.Write(frame1)
	flusher.Flush()

	// 2. Именованное событие биржевых котировок (event: ticker)
	frame2 := FormatSSEFrame("ticker", "2", `{"symbol": "SBER", "price": 298.50}`)
	w.Write(frame2)
	flusher.Flush()

	// 3. Именованное событие безопасности (event: security_alert)
	frame3 := FormatSSEFrame("security_alert", "3", `{"level": "CRITICAL", "ip": "10.0.0.1"}`)
	w.Write(frame3)
	flusher.Flush()
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(MultiEventSSEHandler))
	defer ts.Close()

	fmt.Println("=== Чтение потока мультиплексированных именованных событий ===")
	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	buf := make([]byte, 1024)
	n, _ := resp.Body.Read(buf)

	fmt.Printf("Сырой поток байт от сервера:\n--------------------------------\n%s--------------------------------\n",
		string(buf[:n]))
}
```

## Под капотом

В спецификации SSE разделителем полей является символ перевода строки `\n`. Разделителем между соседними событиями является **двойной перевод строки `\n\n`**.
Если полезная нагрузка `data` содержит многострочный JSON или текст:
```text
data: line 1
data: line 2
\n\n
```
Браузерный парсер склеивает такие строки через `\n`, возвращая в `event.data` единый многострочный текст `line 1\nline 2`. Наличие поля `event: my_type` переключает внутренний селектор диспетчера событий браузера на вызов `addEventListener('my_type')`.

## Подводные камни

1. **Забыть финальный двойной перевод строки `\n\n`:** Без второго `\n` браузер считает, что событие еще не завершено, и не передает данные в JS-обработчик!
2. **Пробелы после двоеточия:** По стандарту после `data:` должен идти ровно один пробел `data: {...}`. Если пробел пропущен или их два, парсер может некорректно разобрать первый символ полезной нагрузки.

## На собеседовании

**Вопрос:** Может ли именованное событие содержать дефисы и спецсимволы в имени (например, `event: user.login-failed`)?

**Ответ:** Да, спецификация W3C разрешает любые UTF-8 символы кроме перевода строки и двоеточия в имени `event`. Однако в JavaScript вызов `sse.addEventListener('user.login-failed', ...)` сработает корректно только через явный метод `addEventListener`, так как синтаксис свойств объектов `sse.onuser.login-failed` недопустим в JS.
