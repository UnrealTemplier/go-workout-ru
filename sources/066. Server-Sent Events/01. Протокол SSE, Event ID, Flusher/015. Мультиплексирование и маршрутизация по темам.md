# Мультиплексирование и маршрутизация по темам (Multiplexed Topic SSE)

## Условие

Multiplexed SSE: Один endpoint `/events`, но клиент подписывается на topics через query: `?topics=orders,alerts`. Сервер фильтрует события: отправляет клиенту только те, что совпадают с подпиской. Реализуйте topic-based routing внутри Hub. Объясните, почему фильтрация на сервере лучше, чем отправка всего и фильтрация на клиенте.

## Теория

При разработке комплексных веб-порталов разным виджетам страницы нужны разные данные:
- Виджет биллинга слушает топик `payments`.
- Колокольчик уведомлений слушает топик `alerts`.
- Чат техподдержки слушает топик `support_chat`.

### Почему фильтрация на клиенте (Client-Side Filtering) порочна:
Если сервер шлет клиенту абсолютно ВСЕ события платформы, а клиент фильтрует их в JS:
1. **Колоссальный паразитный трафик:** Браузер мобильного телефона скачивает мегабайты чужих событий, сжигая мобильный трафик и аккумулятор.
2. **Угроза безопасности (Data Leakage):** Чужие конфиденциальные события попадают в DevTools браузера!
3. **Нагрузка на CPU клиента:** Парсинг тысяч ненужных JSON-объектов в JavaScript тормозит рендеринг страницы.

### Архитектура Topic-Based Multiplexed SSE:
- Клиент открывает **одно** соединение: `GET /events?topics=orders,alerts`.
- Сервер парсит список тем и подписывает клиента **только** на указанные топики в Connection Hub.
- В сокет уходят только релевантные события, экономя 90% полосы пропускания.

## Решение по шагам

1. Создайте структуру `TopicRouterHub` с подпиской по множеству тем.
2. Извлеките список топиков из query-параметра `?topics=orders,alerts` через `strings.Split`.
3. Реализуйте метод `PublishToTopic(topic string, data string)`.
4. Продемонстрируйте, что клиент получает события только из тех топиков, на которые подписался.

## Код решения

**`multiplexed_sse.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"time"
)

type TopicHub struct {
	mu          sync.RWMutex
	subscribers map[string]map[chan string]struct{} // Topic -> Набор каналов
}

func NewTopicHub() *TopicHub {
	return &TopicHub{
		subscribers: make(map[string]map[chan string]struct{}),
	}
}

func (h *TopicHub) Subscribe(topics []string, ch chan string) {
	h.mu.Lock()
	defer h.mu.Unlock()

	for _, topic := range topics {
		topic = strings.TrimSpace(topic)
		if topic == "" {
			continue
		}
		if _, exists := h.subscribers[topic]; !exists {
			h.subscribers[topic] = make(map[chan string]struct{})
		}
		h.subscribers[topic][ch] = struct{}{}
		fmt.Printf("[TOPIC HUB] Канал подписан на топик: '%s'\n", topic)
	}
}

func (h *TopicHub) Unsubscribe(topics []string, ch chan string) {
	h.mu.Lock()
	defer h.mu.Unlock()

	for _, topic := range topics {
		topic = strings.TrimSpace(topic)
		if clients, exists := h.subscribers[topic]; exists {
			delete(clients, ch)
		}
	}
}

func (h *TopicHub) Publish(topic, eventType, data string) {
	h.mu.RLock()
	defer h.mu.RUnlock()

	clients, exists := h.subscribers[topic]
	if !exists {
		return
	}

	frame := fmt.Sprintf("event: %s\ndata: %s\n\n", eventType, data)

	for ch := range clients {
		select {
		case ch <- frame:
		default:
			// Защита от переполнения
		}
	}
}

func (h *TopicHub) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
		return
	}

	// 1. Извлекаем topics из query (?topics=orders,alerts)
	rawTopics := r.URL.Query().Get("topics")
	if rawTopics == "" {
		http.Error(w, "Missing 'topics' query param", http.StatusBadRequest)
		return
	}
	topicsList := strings.Split(rawTopics, ",")

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	clientChan := make(chan string, 10)
	h.Subscribe(topicsList, clientChan)
	defer h.Unsubscribe(topicsList, clientChan)

	ctx := r.Context()
	for {
		select {
		case <-ctx.Done():
			return
		case msg := <-clientChan:
			fmt.Fprint(w, msg)
			flusher.Flush()
		}
	}
}

func main() {
	hub := NewTopicHub()
	ts := httptest.NewServer(hub)
	defer ts.Close()

	// Клиент подписывается ТОЛЬКО на orders и alerts (но НЕ на chat)
	targetURL := ts.URL + "?topics=orders,alerts"
	resp, _ := http.Get(targetURL)
	defer resp.Body.Close()

	fmt.Println("=== Рассылка событий в разные топики ===")
	// Это событие клиент ДОЛЖЕН получить
	hub.Publish("orders", "order_update", `{"order_id": 101, "status": "shipped"}`)

	// Это событие клиент НЕ ДОЛЖЕН получить (чужой топик)
	hub.Publish("chat", "chat_message", `{"author": "Support", "text": "Hello"}`)

	// Это событие клиент ДОЛЖЕН получить
	hub.Publish("alerts", "sys_alert", `{"level": "WARNING"}`)

	time.Sleep(50 * time.Millisecond)

	buf := make([]byte, 512)
	n, _ := resp.Body.Read(buf)
	fmt.Printf("Полученные клиентом события (chat строго отфильтрован на сервере):\n%s\n", string(buf[:n]))
}
```

## Под капотом

В распределенной архитектуре (несколько реплик шлюза) TopicHub подключается к брокеру сообщений. Применяется паттерн **Redis Pub/Sub per Topic**:
Каждый серверный процесс подписывается на Redis-каналы `topics:*` только при наличии хотя бы одного локального клиента, слушающего этот топик. Это исключает передачу ненужного трафика между серверами кластера.

## Подводные камни

1. **Неограниченное количество топиков в query:** Злоумышленник может передать `?topics=t1,t2,...t10000`, вызвав исчерпание памяти в мапе подписок. Ограничивайте максимальное число тем на клиента (например, не более 20).
2. **Отсутствие проверки прав доступа (RBAC) к топику:** Не позволяйте обычному пользователю подписаться на `?topics=admin_audit` без валидации JWT-скоупов.

## На собеседовании

**Вопрос:** Как организовать динамическое добавление/удаление топиков (Subscribe/Unsubscribe) в уже открытом SSE-соединении без его переоткрытия?

**Ответ:** По протоколу SSE поток данных идет строго от сервера к клиенту (\(Server \to Client\)). Клиент не может послать команду вверх по тому же сокету.
Решение:
1. Для команд мутации подписок клиент использует стандартный легковесный REST API запрос: `POST /api/v1/sse/subscriptions` с телом `{"add": ["topic3"], "remove": ["topic1"]}` и заголовком `Session-ID`.
2. Серверный Hub находит активный канал сессии по `Session-ID` и динамически перестраивает мапу подписок в памяти без разрыва TCP-сокета!
