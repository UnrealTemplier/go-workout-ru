# Идентификация событий и возобновление потока (Event ID и Last-Event-ID)

## Условие

Генерируйте `id: <uuid>` для каждого события. Клиент при reconnect шлёт заголовок `Last-Event-ID`. Сервер читает его и отправляет только события с `id` больше последнего (храните буфер последних N событий в памяти или Redis). Объясните, как это даёт exactly-once perception для клиента.

### Исходная формулировка

**Event ID и возобновление.**: Генерируйте `id: <uuid>` для каждого события. Клиент при reconnect шлёт заголовок `Last-Event-ID`. Сервер читает его и отправляет только события с `id` больше последнего (храните буфер последних N событий в памяти или Redis). Объясните, как это даёт exactly-once perception для клиента.

## Теория

Протокол **Server-Sent Events (SSE)**, стандартизированный W3C в HTML5, содержит встроенный на уровне браузерного API механизм восстановления сессии при сетевых сбоях.

### Механика возобновления сессии (Reconnection Protocol):
1. **Поле `id: <val>` во фрейме SSE:**
   Каждое событие сопровождается строкой идентификатора. Браузер при получении фрейма сохраняет это значение во внутреннем свойстве `lastEventId`.
   ```text
   id: 1042
   event: order_status
   data: {"status": "paid"}
   \n\n
   ```
2. **Автоматический заголовок `Last-Event-ID`:**
   При обрыве связи (переключение с Wi-Fi на LTE, перезагрузка сервера) браузерный объект `EventSource` автоматически выполняет повторный GET-запрос, добавляя заголовок:
   `Last-Event-ID: 1042`
3. **Воспроизведение пропущенных событий (Replay Buffer):**
   Сервер читает этот заголовок и вместо старта потока с нуля извлекает из кольцевого буфера (Ring Buffer) или Redis Stream события с `ID > 1042`.
4. **Exactly-Once Perception:**
   Для пользователя интерфейс выглядит так, будто соединение никогда не прерывалось и ни одно сообщение не потерялось и не продублировалось.

## Решение по шагам

1. Создайте структуру события `SSEEvent` с целочисленным или UUID идентификатором и полезной нагрузкой.
2. Реализуйте кольцевой буфер истории событий `EventRingBuffer` с защитой мьютексом.
3. В HTTP-обработчике проверьте наличие заголовка `Last-Event-ID`.
4. Если заголовок присутствует, дошлите клиенту пропущенные события из буфера, после чего переключитесь на live-поток.

## Код решения

**`sse_reconnect.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strconv"
	"sync"
	"time"
)

type SSEEvent struct {
	ID   int64
	Type string
	Data string
}

type EventRingBuffer struct {
	mu     sync.RWMutex
	buffer []SSEEvent
	maxCap int
}

func NewEventRingBuffer(maxCap int) *EventRingBuffer {
	return &EventRingBuffer{
		buffer: make([]SSEEvent, 0, maxCap),
		maxCap: maxCap,
	}
}

func (b *EventRingBuffer) Add(evt SSEEvent) {
	b.mu.Lock()
	defer b.mu.Unlock()

	if len(b.buffer) >= b.maxCap {
		// Сдвигаем влево, удаляя самое старое событие (Ring Buffer)
		b.buffer = append(b.buffer[1:], evt)
	} else {
		b.buffer = append(b.buffer, evt)
	}
}

func (b *EventRingBuffer) GetSince(lastID int64) []SSEEvent {
	b.mu.RLock()
	defer b.mu.RUnlock()

	var missed []SSEEvent
	for _, evt := range b.buffer {
		if evt.ID > lastID {
			missed = append(missed, evt)
		}
	}
	return missed
}

type SSEServer struct {
	ringBuffer *EventRingBuffer
}

func (s *SSEServer) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	// 1. Проверяем заголовок Last-Event-ID от клиента
	lastEventIDHeader := r.Header.Get("Last-Event-ID")
	var lastID int64
	if lastEventIDHeader != "" {
		parsed, err := strconv.ParseInt(lastEventIDHeader, 10, 64)
		if err == nil {
			lastID = parsed
			fmt.Printf("[RECONNECT] Клиент переподключился с Last-Event-ID = %d\n", lastID)
		}
	}

	// 2. Досылаем пропущенные события из буфера
	missedEvents := s.ringBuffer.GetSince(lastID)
	for _, evt := range missedEvents {
		fmt.Fprintf(w, "id: %d\nevent: %s\ndata: %s\n\n", evt.ID, evt.Type, evt.Data)
		flusher.Flush()
		fmt.Printf("[REPLAY] Дослано пропущенное событие #%d клиенту\n", evt.ID)
	}

	// 3. Отправляем свежее событие
	newID := int64(1005)
	fmt.Fprintf(w, "id: %d\nevent: tick\ndata: {\"msg\":\"live update\"}\n\n", newID)
	flusher.Flush()
}

func main() {
	buf := NewEventRingBuffer(10)
	// Заполняем буфер событиями с ID 1001..1004
	for i := 1; i <= 4; i++ {
		buf.Add(SSEEvent{
			ID:   int64(1000 + i),
			Type: "notification",
			Data: fmt.Sprintf(`{"seq":%d}`, i),
		})
	}

	server := &SSEServer{ringBuffer: buf}
	ts := httptest.NewServer(server)
	defer ts.Close()

	// Имитируем повторное подключение клиента, который остановился на событии 1002
	req, _ := http.NewRequest(http.MethodGet, ts.URL, nil)
	req.Header.Set("Last-Event-ID", "1002")

	fmt.Println("=== Клиент отправляет запрос с Last-Event-ID: 1002 ===")
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	fmt.Printf("HTTP Статус ответа сервера: %d %s\n", resp.StatusCode, http.StatusText(resp.StatusCode))
}
```

## Под капотом

Спецификация W3C Server-Sent Events гласит: если в потоке SSE встречается пустая строка `id:\n`, браузер сбрасывает свое внутреннее состояние `lastEventId` в пустую строку. Если передано `id: 123\n\n`, браузер атомарно обновляет `lastEventId`. При закрытии сокета браузер делает паузу (по умолчанию 3 секунды, настраивается полем `retry: 5000\n\n`) и посылает новый запрос с заголовком `Last-Event-ID: 123`. Все происходит полностью прозрачно для клиентского JavaScript.

## Подводные камни

1. **Использование случайных UUID в качестве `id` без сохранения порядка:** Если в `id` передавать неупорядоченный UUID v4, сервер не сможет выполнить условие `ID > LastID`. Используйте монотонно растущие счетчики, ULID или Snowflake ID.
2. **Переполнение кольцевого буфера:** Если клиент находился оффлайн дольше, чем глубина буфера, события будут безвозвратно утеряны. В таких случаях сервер обязан отправить кастомное событие `event: resync_required`, заставляющее клиент запросить полный снимок состояния через REST API.

## На собеседовании

**Вопрос:** Как масштабировать Replay Buffer для `Last-Event-ID` в распределенном кластере из 20 серверов в Kubernetes?

**Ответ:** 
1. Локальный буфер в памяти процесса не подходит: при реконнекте клиент может попасть на другой под через балансировщик нагрузки.
2. Используется **Redis Streams (XADD / XRANGE)**: события сохраняются с ключом стрима документа/пользователя (`events:stream:doc_42`).
3. При реконнекте с `Last-Event-ID` любой под кластера вызывает `XRANGE events:stream:doc_42 (lastID +inf`, вычитывая точные пропущенные дельты за микросекунды независимо от того, на какую ноду пришел запрос.
