# Монотонные идентификаторы событий и отслеживание смещений (Event IDs)

## Условие

**Event IDs**: Добавляйте `id: 12345\n` для каждого события. Это позволяет клиенту автоматически resume с последнего полученного ID при reconnect.

## Теория

Идентификатор события `id` в SSE выполняет ту же роль, что и `Offset` в Apache Kafka или `Log Sequence Number (LSN)` в базах данных.

### Ключевые требования к Event IDs:
1. **Строгая монотонность:** Каждое следующее событие обязано иметь ID больший, чем предыдущее (\(ID_{k+1} > ID_k\)).
2. **Уникальность:** В рамках одного потока/сущности два события не могут иметь одинаковый ID.
3. **Автоматическое состояние браузера:** Браузерный движок `EventSource` обновляет внутреннее свойство `lastEventId` **строго атомарно** при успешном приеме события. Если соединение оборвется посредине передачи, браузер запомнит ID последнего полностью доставленного фрейма.

## Решение по шагам

1. Создайте потокобезопасный генератор монотонных идентификаторов `EventIDGenerator`.
2. Реализуйте отправку событий с полем `id: <num>`.
3. Смоделируйте генерацию 5 последовательных событий.
4. Продемонстрируйте валидный порядок идентификаторов.

## Код решения

**`event_ids.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
)

type EventIDGenerator struct {
	counter atomic.Int64
}

func (g *EventIDGenerator) NextID() int64 {
	return g.counter.Add(1)
}

func EventIDStreamHandler(gen *EventIDGenerator) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		flusher, ok := w.(http.Flusher)
		if !ok {
			http.Error(w, "Flusher unsupported", http.StatusInternalServerError)
			return
		}

		w.Header().Set("Content-Type", "text/event-stream")

		for i := 1; i <= 3; i++ {
			id := gen.NextID()
			fmt.Fprintf(w, "id: %d\ndata: {\"order_status\":\"STATUS_%d\"}\n\n", id, i)
			flusher.Flush()
		}
	}
}

func main() {
	gen := &EventIDGenerator{}
	ts := httptest.NewServer(EventIDStreamHandler(gen))
	defer ts.Close()

	fmt.Println("=== Проверка генерации монотонных Event ID ===")
	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	buf := make([]byte, 512)
	n, _ := resp.Body.Read(buf)
	fmt.Printf("Полученный поток с Event ID:\n%s\n", string(buf[:n]))
}
```

## Под капотом

Спецификация WHATWG EventSource: если строка начинается с `id:`, парсер извлекает значение до конца строки.
Если в строке встречается символ `\0` (null-byte), спецификация требует отбросить все поле `id`. Если строка состоит только из `id:` (без значения), сохраненный `lastEventId` очищается. Использование чистых ASCII-чисел в десятичной системе счисления является самым надежным подходом во всех браузерах.

## Подводные камни

1. **Использование строковых меток времени `id: 2026-09-06T15:04:05`:** При высокой частоте событий (1000 msg/sec) временные метки совпадут, лишив сервер возможности определить, на каком именно сообщении из пачки остановился клиент.
2. **Случайные идентификаторы (UUIDv4):** Случайный UUID не позволяет серверу сделать выборку `WHERE id > last_id`.

## На собеседовании

**Вопрос:** Как генерировать монотонные Event ID в распределенной системе без бутылочного горлышка в виде единого счетчика в БД?

**Ответ:** Применяются алгоритмы **Sonyflake / Twitter Snowflake**:
64-битное число состоит из:
- 41 бит: миллисекунды текущего времени (хватит на 69 лет).
- 10 бит: Machine ID / Pod ID (до 1024 независимых нод).
- 12 бит: локальный счетчик последовательности (до 4096 событий в миллисекунду на один под).
Это гарантирует монотонный рост и уникальность без блокировок и сетевых вызовов.
