### Исходная формулировка

Он должен принимать запросы на подписку к определенным топикам, регистрировать каналы клиентов в памяти и при публикации нового сообщения (например, через Redis Pub/Sub) автоматически рассылать его по всем активным клиентским SSE-соединениям, подписанным на этот топик.

---

## Теория

В распределенной системе сервис состоит из множества реплик (подов в K8s), запущенных за балансировщиком нагрузки. Клиент А подключен к Поду 1, а Клиент Б — к Поду 2. Когда событие создается бизнес-сервисом, оно должно быть доставлено всем заинтересованным клиентам независимо от того, на какой конкретно инстанс попало их TCP-соединение.

Архитектура горизонтального масштабирования:
1. **Топики/Каналы:** Клиент подключается к URL `/stream?topic=orders:123`.
2. **Локальный реестр топиков:** Каждый инстанс хранит карту подписчиков: `map[string]map[chan []byte]struct{}`.
3. **Распределенная шина (Redis Pub/Sub / NATS):** При появлении первого подписчика на топик на данном поде, инстанс подписывается на соответствующий канал в Redis (`SUBSCRIBE topic`).
4. При получении сообщения из Redis инстанс транслирует его локальным клиентам через Fan-Out.
5. При отключении последнего подписчика инстанс отписывается от Redis (`UNSUBSCRIBE topic`), экономя трафик.

## Решение по шагам

1. Создайте структуру `TopicManager` с локальной картой топиков и клиентов.
2. Реализуйте подписку клиента на топик `Subscribe(topic string) chan []byte`.
3. Реализуйте имитацию или интеграцию с шиной сообщений `Publish(topic string, payload []byte)`.
4. В HTTP-хэндлере читайте параметр топика из URL и стримьте сообщения подписчикам.
5. Обеспечьте корректную отписку и закрытие каналов при отмене контекста запроса.

## Код решения

**`cluster_sse.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync"
	"time"
)

type TopicManager struct {
	mu     sync.RWMutex
	topics map[string]map[chan []byte]struct{}
}

func NewTopicManager() *TopicManager {
	return &TopicManager{
		topics: make(map[string]map[chan []byte]struct{}),
	}
}

func (tm *TopicManager) Subscribe(topic string) chan []byte {
	tm.mu.Lock()
	defer tm.mu.Unlock()

	ch := make(chan []byte, 32)
	if _, ok := tm.topics[topic]; !ok {
		tm.topics[topic] = make(map[chan []byte]struct{})
		fmt.Printf("[Cluster Hub] First subscriber for topic: %s. Subscribing to bus...\n", topic)
	}
	tm.topics[topic][ch] = struct{}{}
	return ch
}

func (tm *TopicManager) Unsubscribe(topic string, ch chan []byte) {
	tm.mu.Lock()
	defer tm.mu.Unlock()

	if clients, ok := tm.topics[topic]; ok {
		delete(clients, ch)
		close(ch)
		if len(clients) == 0 {
			delete(tm.topics, topic)
			fmt.Printf("[Cluster Hub] No subscribers left for topic: %s. Unsubscribing from bus...\n", topic)
		}
	}
}

// BroadcastLocal вызывается при получении сообщения из Redis Pub/Sub или NATS
func (tm *TopicManager) BroadcastLocal(topic string, payload []byte) {
	tm.mu.RLock()
	defer tm.mu.RUnlock()

	if clients, ok := tm.topics[topic]; ok {
		for ch := range clients {
			select {
			case ch <- payload:
			default:
			}
		}
	}
}

func topicStreamHandler(tm *TopicManager) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		topic := r.URL.Query().Get("topic")
		if topic == "" {
			http.Error(w, "topic parameter is required", http.StatusBadRequest)
			return
		}

		w.Header().Set("Content-Type", "text/event-stream")
		w.Header().Set("Cache-Control", "no-cache")
		w.Header().Set("Connection", "keep-alive")

		rc := http.NewResponseController(w)
		ch := tm.Subscribe(topic)
		defer tm.Unsubscribe(topic, ch)

		for {
			select {
			case <-r.Context().Done():
				return
			case msg, ok := <-ch:
				if !ok {
					return
				}
				if _, err := fmt.Fprintf(w, "event: message\ndata: %s\n\n", msg); err != nil {
					return
				}
				if err := rc.Flush(); err != nil {
					return
				}
			}
		}
	}
}

func main() {
	tm := NewTopicManager()

	// Симуляция внешней шины сообщений
	go func() {
		ticker := time.NewTicker(2 * time.Second)
		defer ticker.Stop()
		i := 0
		for t := range ticker.C {
			i++
			tm.BroadcastLocal("crypto", []byte(fmt.Sprintf("BTC: $65,%03d at %s", i*10, t.Format("15:04:05"))))
			tm.BroadcastLocal("stocks", []byte(fmt.Sprintf("AAPL: $185.%d at %s", i%10, t.Format("15:04:05"))))
		}
	}()

	http.HandleFunc("/topic-stream", topicStreamHandler(tm))
	fmt.Println("Topic SSE Cluster Node listening on :8080/topic-stream?topic=crypto")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Управление топиками и локальная диспетчеризация сообщений внешней шины

## Под капотом

В схеме с Redis Pub/Sub создается единая горутина подписчика на весь процесс Go. Она слушает события от Redis и вызывает `BroadcastLocal(msg.Channel, msg.Payload)`. Это исключает создание N сетевых сокетов к Redis на N клиентов, снижая нагрузку на Redis-сервер на несколько порядков.

## Подводные камни

Подписка на Redis Pub/Sub на уровне каждого отдельного HTTP-запроса клиента. При 50 000 веб-клиентов это породит 50 000 отдельных TCP-сокетов к Redis, что гарантированно приведет к исчерпанию файловых дескрипторов и падению Redis кластера.

## На собеседовании

В Яндекс и Ozon на вопросе по архитектуре стриминга спрашивают: 'Что надежнее для шины SSE: Redis Pub/Sub или Redis Streams / Kafka?' Ответ: классический Pub/Sub в Redis не сохраняет историю и теряет сообщения при обрыве связи между репликами. Для гарантий доставки при реконнектах (Last-Event-ID) следует использовать Redis Streams (`XADD`/`XREAD`) или Kafka, где события персистентны и адресуемы по смещению (offset).
