### Исходная формулировка

## Теория

При проектировании систем реального времени (Real-Time Systems) выбор между Long Polling, SSE и WebSocket определяет нагрузку на сеть, сложность архитектуры и масштабируемость:

1. **Long Polling:**
   - Клиент отправляет HTTP-запрос, сервер держит его до появления события, отвечает и соединение закрывается.
   - Минусы: постоянные повторные HTTP-запросы (TCP handshake, TLS negotiation, отправка заголовков Cookie/Auth на каждый чих), огромный оверхед CPU и трафика, задержка между запросами.
2. **WebSockets:**
   - Полнодуплексный двунаправленный протокол поверх единого TCP-соединения после рукопожатия Upgrade.
   - Плюсы: низкие накладные расходы на заголовки фреймов (от 2 байт), передача бинарных данных, клиент может слать данные серверу с минимальной задержкой.
   - Минусы: не мультиплексируется в HTTP/2, требует отдельных сокетов, сложная балансировка нагрузки (sticky sessions), проблемы с корпоративными файрволами.
3. **Server-Sent Events (SSE):**
   - Однонаправленный потоковый HTTP-ответ.
   - Плюсы: простота реализации (чистый HTTP), работает через любые CDN/прокси, автоматический реконнект с `Last-Event-ID`, мультиплексирование сотен потоков в 1 TCP-соединение через HTTP/2.
   - Минусы: только однонаправленный поток (Server -> Client), только текстовый формат UTF-8.

## Решение по шагам

1. Создайте универсальный сервер, предоставляющий Long-Polling и SSE эндпоинты для одной очереди сообщений.
2. Сравните количество создаваемых TCP-сессий и накладные расходы заголовков.

## Код решения

**`comparison_server.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"sync"
	"time"
)

type Message struct {
	ID   int    `json:"id"`
	Text string `json:"text"`
}

type MessageHub struct {
	mu       sync.Mutex
	notifyCh chan struct{}
	lastMsg  Message
}

var hub = &MessageHub{
	notifyCh: make(chan struct{}),
}

func (h *MessageHub) Publish(text string) {
	h.mu.Lock()
	h.lastMsg.ID++
	h.lastMsg.Text = text
	close(h.notifyCh)
	h.notifyCh = make(chan struct{})
	h.mu.Unlock()
}

// Long-Polling endpoint: держит соединение до появления нового ID, затем завершает запрос
func longPollingHandler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	hub.mu.Lock()
	ch := hub.notifyCh
	hub.mu.Unlock()

	select {
	case <-ctx.Done():
		return
	case <-time.After(10 * time.Second): // Таймаут ожидания
		w.WriteHeader(http.StatusNoContent)
		return
	case <-ch:
		hub.mu.Lock()
		msg := hub.lastMsg
		hub.mu.Unlock()

		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(msg)
	}
}

// SSE endpoint: постоянное потоковое соединение
func sseHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	ctx := r.Context()

	for {
		hub.mu.Lock()
		ch := hub.notifyCh
		hub.mu.Unlock()

		select {
		case <-ctx.Done():
			return
		case <-ch:
			hub.mu.Lock()
			msg := hub.lastMsg
			hub.mu.Unlock()

			payload, _ := json.Marshal(msg)
			if _, err := fmt.Fprintf(w, "id: %d\ndata: %s\n\n", msg.ID, payload); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/poll", longPollingHandler)
	http.HandleFunc("/stream", sseHandler)

	// Периодический генератор сообщений
	go func() {
		ticker := time.NewTicker(3 * time.Second)
		defer ticker.Stop()
		i := 0
		for t := range ticker.C {
			i++
			hub.Publish(fmt.Sprintf("Update #%d at %s", i, t.Format("15:04:05")))
		}
	}()

	fmt.Println("Realtime comparison server listening on :8080 (/poll, /stream)")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

При 10 000 клиентов Long Polling генерирует 10 000 новых HTTP запросов каждые N секунд. Это создает лавинную нагрузку на аллокатор рантайма Go из-за парсинга структур `http.Request`, разбора TLS-записей и создания новых горутин. В SSE соединение устанавливается один раз, и горутина просто блокируется в вызове планировщика GMP (`gopark`), потребляя минимум ресурсов.

## Подводные камни

Использование Long Polling в современных браузерах для высокочастотных обновлений (чаще раза в 2 секунды). Это приводит к исчерпанию пула HTTP-соединений браузера и заметным задержкам рендеринга пользовательского интерфейса.

## На собеседовании

В Авито на системном дизайне любят вопрос: 'У нас есть сервис онлайн-опросов (live voting): 100 000 зрителей и 5 спикеров. Спикеры задают вопросы, зрители голосуют. Какую технологию выбрать?' Ответ: гибридную схему. Зрители отправляют свои голоса через обычный легко масштабируемый HTTP POST, а результаты голосования и новые вопросы получают через SSE-стрим. WebSocket здесь избыточен и создал бы сложности с масштабированием.
