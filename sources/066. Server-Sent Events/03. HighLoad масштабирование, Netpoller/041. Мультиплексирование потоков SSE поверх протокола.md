# Мультиплексирование потоков SSE поверх протокола HTTP/2

## Условие

41. **SSE + HTTP/2 multiplexing**: На HTTP/2 один connection может держать множество SSE streams без overhead. Это эффективно для multi-tenant приложений.

### Исходная формулировка

**SSE + HTTP/2 multiplexing**: На HTTP/2 один connection может держать множество SSE streams без overhead. Это эффективно для multi-tenant приложений.

## Теория

Главное фундаментальное ограничение HTTP/1.1 при работе с SSE — **Connection Limit**:
- Браузеры (Chrome, Safari, Firefox) открывают не более 6 одновременных TCP-соединений к одному доменному имени.
- Если на одной веб-странице открыто несколько SSE-потоков или пользователь открыл 6 вкладок сайта, все последующие сетевые запросы браузера встают в бесконечную очередь (Head-of-Line Blocking на уровне TCP соединений).

Протокол **HTTP/2 (h2)** кардинально решает эту проблему:
1. **Мультиплексирование потоков (Stream Multiplexing):** Все запросы и ответы передаются в виде независимых бинарных фреймов (`DATA`, `HEADERS`) внутри **одного единственного TCP-соединения**.
2. Вкладки и виджеты могут открывать десятки параллельных SSE-соединений к одному серверу, не исчерпывая лимиты браузера.
3. Сервер Go поддерживает HTTP/2 'из коробки' при запуске с TLS (`http.ListenAndServeTLS`).
4. Накладные расходы на поддержание множества стримов в памяти минимальны благодаря единому TCP буферу и эффективному сжатию заголовков HPACK.

## Решение по шагам

1. Сгенерируйте самоподписанный TLS-сертификат для локального тестирования HTTP/2.
2. Запустите сервер через `http.ListenAndServeTLS`.
3. В обработчике проверьте версию протокола `r.Proto` (должно быть `HTTP/2.0`).
4. Убедитесь, что `http.NewResponseController(w).Flush()` корректно отправляет HTTP/2 `DATA` фреймы.

## Код решения

**`h2_server.go`**

```go
package main

import (
	"crypto/tls"
	"fmt"
	"net/http"
	"time"
)

func h2StreamHandler(w http.ResponseWriter, r *http.Request) {
	// Логируем версию протокола: для h2 ожидается HTTP/2.0
	fmt.Printf("[H2] Inbound connection, Proto: %s, Stream: %s\n", r.Proto, r.URL.Path)

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	rc := http.NewResponseController(w)
	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	for i := 1; i <= 5; i++ {
		select {
		case <-r.Context().Done():
			return
		case t := <-ticker.C:
			// В HTTP/2 Flush отправляет кадр DATA с флагом END_STREAM=false
			fmt.Fprintf(w, "event: h2_tick\ndata: {\"proto\":\"%s\",\"step\":%d,\"time\":\"%s\"}\n\n",
				r.Proto, i, t.Format("15:04:05"))
			_ = rc.Flush()
		}
	}
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/h2/stream1", h2StreamHandler)
	mux.HandleFunc("/h2/stream2", h2StreamHandler)

	srv := &http.Server{
		Addr:    ":8443",
		Handler: mux,
		TLSConfig: &tls.Config{
			NextProtos: []string{"h2", "http/1.1"}, // Включение ALPN согласования HTTP/2
		},
	}

	fmt.Println("HTTP/2 TLS SSE server listening on https://localhost:8443")
	// Для тестирования требуются cert.pem и key.pem
	_ = srv
}
```

ℹ️ Поддержка HTTP/2 с мультиплексированием стримов поверх единого TLS-соединения

## Под капотом

В HTTP/2 каждый вызов `Flush()` формирует фрейм типа `DATA` (тип 0x0) с указанием конкретного `Stream Identifier` (31-битное число). Пакеты разных SSE потоков перемежаются в едином потоке TCP, что устраняет необходимость открывать новые сокеты ядра и экономит драгоценную память ядра на TCP-буферы.

## Подводные камни

Использование незашифрованного HTTP/2 (h2c) без TLS. Ни один современный браузер не поддерживает HTTP/2 без TLS шифрования (ALPN `h2`). Попытка открыть SSE по h2c в браузере приведет к откату на HTTP/1.1 с ограничением в 6 одновременных подключений.

## На собеседовании

В Т-Банке и Ozon любят спрашивать: 'В чем опасность мультиплексирования 100 SSE-потоков в одно TCP соединение по HTTP/2 при нестабильной мобильной сети?' Ответ: TCP Head-of-Line Blocking на транспортном уровне! Если теряется хотя бы один TCP-пакет, ядро ОС замораживает доставку данных для ВСЕХ 100 мультиплексированных стримов до тех пор, пока потерянный пакет не будет повторно передан (TCP Retransmission). Решение этой проблемы реализовано в протоколе HTTP/3 (QUIC) на базе UDP.
