# Гарантия строгого порядка доставки событий (In-Order Delivery)

## Условие

42. **SSE event ordering guarantee**: Обеспечьте in-order delivery событий одному клиенту через serialization (один writer per client).

### Исходная формулировка

**SSE event ordering guarantee**: Обеспечьте in-order delivery событий одному клиенту через serialization (один writer per client).

## Теория

В конкурентных системах события могут генерироваться множеством независимых горутин (воркеров фоновых задач, обработчиков Kafka, таймеров). 

Если несколько горутин попытаются одновременно писать в один `http.ResponseWriter`:
1. Нарушится формат протокола SSE: строки `data:` от одного события перемешаются со строками другого события.
2. Возникнет состояние гонки данных (Data Race), приводящее к непредсказуемым паникам внутри рантайма Go.
3. События могут прийти клиенту в нарушенном хронологическом порядке (например, `OrderPaid` придет раньше, чем `OrderCreated`).

Архитектурное решение: **Паттерн 'Single Writer per Connection'**:
- На каждое клиентское соединение создается ровно **одна** горутина-писатель (`Writer Goroutine`).
- Все внешние источники отправляют события в строго последовательную FIFO-очередь (буферизированный канал `chan Event`).
- Горутина-писатель последовательно вычитывает события из канала, инкрементирует монотонный порядковый номер `SeqNumber` и пишет фрейм в сокет.

## Решение по шагам

1. Создайте структуру события с монотонным идентификатором `SequenceNumber uint64`.
2. Реализуйте сессию клиента с выделенным FIFO-каналом.
3. Запретите прямую запись в `ResponseWriter` из параллельных горутин.
4. В горутине обработчика последовательно читайте из канала и вызывайте `Flush()`.
5. Продемонстрируйте корректный порядок при отправке из 10 конкурентных горутин.

## Код решения

**`order_guarantee.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync"
	"sync/atomic"
	"time"
)

type OrderedEvent struct {
	SeqID   uint64
	Payload string
}

type ClientConnection struct {
	queue   chan OrderedEvent
	counter atomic.Uint64
}

func NewClientConnection(bufferSize int) *ClientConnection {
	return &ClientConnection{
		queue: make(chan OrderedEvent, bufferSize),
	}
}

func (c *ClientConnection) Enqueue(payload string) bool {
	seq := c.counter.Add(1)
	ev := OrderedEvent{
		SeqID:   seq,
		Payload: payload,
	}

	select {
	case c.queue <- ev:
		return true
	default:
		return false // Буфер переполнен
	}
}

func orderedStreamHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	client := NewClientConnection(100)

	// Конкурентные генераторы событий
	var wg sync.WaitGroup
	for workerID := 1; workerID <= 3; workerID++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for i := 1; i <= 3; i++ {
				client.Enqueue(fmt.Sprintf("Worker #%d step %d", id, i))
				time.Sleep(10 * time.Millisecond)
			}
		}(workerID)
	}

	go func() {
		wg.Wait()
	}()

	// Single Writer Goroutine: гарантирует строгий порядок фреймов
	for {
		select {
		case <-r.Context().Done():
			return
		case ev := <-client.queue:
			if _, err := fmt.Fprintf(w, "id: %d\ndata: %s\n\n", ev.SeqID, ev.Payload); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/ordered", orderedStreamHandler)
	fmt.Println("Ordered SSE server running on :8080/ordered")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Паттерн Single Writer с монотонным атомарным Sequence ID для гарантии порядка доставки

## Под капотом

Каналы Go (`hchan`) представляют собой потокобезопасные кольцевые FIFO-буферы, защищенные внутренним спин-локом `lock`. Сообщения, записанные в канал, гарантированно вычитываются в том же хронологическом порядке, в котором они были помещены в очередь (First-In, First-Out), исключая перемешивание событий.

## Подводные камни

Попытка записи в один `http.ResponseWriter` из нескольких горутин без мьютекса или канала. `net/http` не является потокобезопасным для параллельной записи, что приводит к порче сетевого буфера и ошибкам `concurrent write to websocket / http connection`.

## На собеседовании

В Касперском и Авито часто спрашивают: 'Как гарантировать последовательность обработки событий на стороне фронтенда, если мобильное приложение переподключилось и запросило данные из реплей-буфера параллельно с приходящими live-событиями?' Ответ: на фронтенде реализовывать буфер упорядочивания (Reordering Buffer / Priority Queue по SeqID). Если получено событие #105, а текущее #103, фронтенд буферизирует #105 до получения #104.
