# Дашборды реального времени без опроса (Real-Time Dashboards)

## Условие

49. **Real-time dashboards**: Обновляйте metrics dashboards через SSE: новые данные приходят как события, frontend обновляет графики без polling.

### Исходная формулировка

**Real-time dashboards**: Обновляйте metrics dashboards через SSE: новые данные приходят как события, frontend обновляет графики без polling.

## Теория

Традиционный подход к обновлению дашбордов через опрос (`setInterval(() => fetch('/api/metrics'), 1000)`) создает паразитную нагрузку:
- Если метрики не изменились, сервер все равно парсит HTTP-запросы, читает БД и сериализует JSON.
- Если произошел аварийный всплеск (spike), пользователь увидит его с задержкой до следующего интервала опроса.

Архитектура Real-Time Dashboards на базе SSE:
1. Клиент устанавливает одно долгоживущее соединение `/api/dashboard/stream`.
2. Сервер отправляет первый фрейм с полным слепком текущего состояния (Initial Snapshot).
3. Далее сервер отправляет обновления только тогда, когда метрика фактически изменилась (Event-Driven Updates), либо с фиксированным тиком агрегатора.
4. Нагрузка на сеть падает в 10-50 раз по сравнению с polling.

## Решение по шагам

1. Создайте структуру метрик дашборда (`CPUUsage`, `MemoryAllocMB`, `ActiveRequests`).
2. При подключении отправьте первоначальный снимок `event: initial_state`.
3. В цикле стриминга отправляйте дельта-обновления `event: metric_tick`.
4. Реализуйте HTML-интерфейс с динамическим графиком.

## Код решения

**`dashboard_server.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"math/rand"
	"net/http"
	"time"
)

type DashboardMetrics struct {
	CPUPercent float64 `json:"cpu_percent"`
	MemAllocMB float64 `json:"mem_alloc_mb"`
	RPS        int     `json:"rps"`
	Timestamp  string  `json:"timestamp"`
}

func dashboardHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)

	// 1. Отправляем первичный снимок состояния
	initial := DashboardMetrics{
		CPUPercent: 12.5,
		MemAllocMB: 256.0,
		RPS:        1450,
		Timestamp:  time.Now().Format("15:04:05"),
	}
	snapBytes, _ := json.Marshal(initial)
	fmt.Fprintf(w, "event: snapshot\ndata: %s\n\n", snapBytes)
	_ = rc.Flush()

	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			return
		case t := <-ticker.C:
			// 2. Периодический поток изменений
			m := DashboardMetrics{
				CPUPercent: 10.0 + rand.Float64()*15.0,
				MemAllocMB: 250.0 + rand.Float64()*20.0,
				RPS:        1400 + rand.Intn(200),
				Timestamp:  t.Format("15:04:05"),
			}
			bytes, _ := json.Marshal(m)
			if _, err := fmt.Fprintf(w, "event: metrics\ndata: %s\n\n", bytes); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/dashboard/stream", dashboardHandler)
	fmt.Println("Dashboard SSE stream running on :8080/dashboard/stream")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Отправка начального снимка snapshot и последующих событий metrics в реальном времени

## Под капотом

Браузер при получении SSE события выполняет минимальную работу: срабатывает колбэк в JavaScript Event Loop, обновляются поля объекта на странице без перезагрузки DOM дерева. Это предотвращает перерисовки (Reflow/Repaint) всего интерфейса, обеспечивая плавную частоту кадров (60 FPS) на дашбордах.

## Подводные камни

Отправка слишком мелких событий с частотой более 100 Гц (100 раз в секунду). Это может перегрузить главный поток (Main Thread) JavaScript в браузере, вызвав зависание вкладки. Высокочастотные метрики на сервере необходимо предварительно батчить или агрегировать до 1-5 Гц.

## На собеседовании

В Wildberries и Tinkoff часто спрашивают: 'Как организовать мониторинг 5 000 подов в реальном времени на одном экране дашборда?' Ответ: серверная агрегация. Сервер объединяет обновления подов в единый массив событий раз в 500 мс и отправляет один агрегированный SSE фрейм, предотвращая перегрузку фронтенда миллионами мелких сообщений.
