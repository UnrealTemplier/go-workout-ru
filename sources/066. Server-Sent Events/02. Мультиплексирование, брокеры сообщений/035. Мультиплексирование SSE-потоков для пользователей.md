# Мультиплексирование SSE-потоков для пользователей (User-Level Multiplexing)

## Условие

35. **Мультиплексирование SSE для разных пользователей.**: Реализуйте брокер событий, который хранит соединения в map `userID -> []chan Event`. При появлении события для пользователя отправляйте его во все активные SSE-соединения.

### Исходная формулировка

**Мультиплексирование SSE для разных пользователей.**: Реализуйте брокер событий, который хранит соединения в map `userID -> []chan Event`. При появлении события для пользователя отправляйте его во все активные SSE-соединения.

## Теория

В распределенных веб-сервисах один авторизованный пользователь может иметь несколько параллельных клиентских сессий:
- Вкладка дашборда на рабочем ноутбуке;
- Вкладка корзины покупок на домашнем ПК;
- Мобильное приложение на смартфоне.

Архитектура мультиплексирующего брокера:
1. Хранилище сессий организовано в виде структуры:
   ```go
   type MultiUserBroker struct {
       mu    sync.RWMutex
       users map[string][]chan Event
   }
   ```
2. При подключении нового соединения канал клиента добавляется в слайс каналов соответствующего `userID`.
3. При публикации события для конкретного `userID` брокер выполняет рассылку (fan-out) по всем зарегистрированным каналам данного пользователя.
4. При разрыве одного соединения из слайса удаляется только отсоединившийся канал, а остальные сессии пользователя продолжают получать обновления без прерывания.

## Решение по шагам

1. Создайте структуру события `Event` с полями `ID`, `Name`, `Payload`.
2. Реализуйте структуру `MultiUserBroker` с методами `Register(userID string) chan Event`, `Unregister(userID string, ch chan Event)` и `SendToUser(userID string, ev Event)`.
3. В методе `Unregister` выполните корректное удаление элемента из слайса по значению указателя на канал.
4. Создайте HTTP-обработчик SSE, использующий мультиплексирующий брокер.
5. Протестируйте отправку события, убедившись, что все вкладки одного пользователя получают обновление.

## Код решения

**`multi_broker.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"sync"
	"time"
)

type Event struct {
	ID      string `json:"id"`
	Type    string `json:"type"`
	Payload string `json:"payload"`
}

type MultiUserBroker struct {
	mu    sync.RWMutex
	users map[string][]chan Event
}

func NewMultiUserBroker() *MultiUserBroker {
	return &MultiUserBroker{
		users: make(map[string][]chan Event),
	}
}

func (b *MultiUserBroker) Register(userID string) chan Event {
	b.mu.Lock()
	defer b.mu.Unlock()

	ch := make(chan Event, 32)
	b.users[userID] = append(b.users[userID], ch)
	fmt.Printf("[+] User %s opened connection (total user tabs: %d)\n", userID, len(b.users[userID]))
	return ch
}

func (b *MultiUserBroker) Unregister(userID string, ch chan Event) {
	b.mu.Lock()
	defer b.mu.Unlock()

	channels := b.users[userID]
	for i, c := range channels {
		if c == ch {
			// Удаляем канал из среза
			b.users[userID] = append(channels[:i], channels[i+1:]...)
			close(ch)
			break
		}
	}

	if len(b.users[userID]) == 0 {
		delete(b.users, userID)
		fmt.Printf("[-] User %s has no active connections left\n", userID)
	} else {
		fmt.Printf("[-] User %s closed one tab (remaining tabs: %d)\n", userID, len(b.users[userID]))
	}
}

func (b *MultiUserBroker) SendToUser(userID string, ev Event) int {
	b.mu.RLock()
	defer b.mu.RUnlock()

	channels, ok := b.users[userID]
	if !ok {
		return 0
	}

	delivered := 0
	for _, ch := range channels {
		select {
		case ch <- ev:
			delivered++
		default:
			// Медленная вкладка — дроп для защиты остальных
		}
	}
	return delivered
}

func (b *MultiUserBroker) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	userID := r.URL.Query().Get("user_id")
	if userID == "" {
		http.Error(w, "user_id query param is required", http.StatusBadRequest)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	ch := b.Register(userID)
	defer b.Unregister(userID, ch)

	for {
		select {
		case <-r.Context().Done():
			return
		case ev, ok := <-ch:
			if !ok {
				return
			}
			payloadBytes, _ := json.Marshal(ev)
			if _, err := fmt.Fprintf(w, "id: %s\nevent: %s\ndata: %s\n\n", ev.ID, ev.Type, payloadBytes); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	broker := NewMultiUserBroker()
	http.Handle("/sse/user", broker)

	// Периодическая рассылка персональных событий
	go func() {
		ticker := time.NewTicker(3 * time.Second)
		defer ticker.Stop()
		i := 0
		for t := range ticker.C {
			i++
			ev := Event{
				ID:      fmt.Sprintf("evt_%d", i),
				Type:    "balance_update",
				Payload: fmt.Sprintf("New balance calculated at %s", t.Format("15:04:05")),
			}
			sent := broker.SendToUser("user_42", ev)
			if sent > 0 {
				fmt.Printf("[Broadcast] Dispatched event #%d to %d tabs of user_42\n", i, sent)
			}
		}
	}()

	fmt.Println("Multi-user broker SSE server running on :8080/sse/user")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Брокер мультиплексирования событий на все открытые вкладки и сессии пользователя

## Под капотом

Использование среза `[]chan Event` внутри мапы эффективно с точки зрения аллокаций памяти при типичном количестве вкладок пользователя (от 1 до 5). Поиск и удаление за \(O(N)\) по короткому слайсу выполняется за единицы наносекунд в L1-кэше процессора, что быстрее, чем накладные расходы на вложенную `map[chan Event]struct{}`.

## Подводные камни

Утечка ссылок на каналы в срезе при удалении без зануления или сдвига. Если при удалении элемента из среза через `append(s[:i], s[i+1:]...)` в конце среза остаются висячие ссылки в базовом массиве, это может препятствовать освобождению памяти сборщиком мусора Go. При интенсивной ротации сессий безопаснее обнулять последний элемент `s[len(s)-1] = nil` перед сжатием длины среза.

## На собеседовании

В Яндекс Такси и Ситимобил часто спрашивают: 'Как организовать доставку геолокации водителя пассажиру, если у пассажира одновременно открыт экран заказа в приложении и виджет на часах?' Ответ: связывать ID поездки или ID пользователя с кластером каналов сессий (`[]chan LocationUpdate`). Все сессии получают обновление в параллельных горутинах, а при закрытии виджета на часах канал отписывается без разрыва сессии приложения.
