# Возобновление связи и Replay-буфер по Last-Event-ID

## Условие

29. **Возобновление связи (Last-Event-ID)**: При кратковременном разрыве соединения браузерный клиент автоматически переподключается и отправляет заголовок `Last-Event-ID`, указывая ID последнего успешно полученного сообщения. Напишите логику на сервере: считайте этот заголовок, найдите пропущенные сообщения в кольцевом буфере или кэше и отправьте их клиенту перед переходом в режим реального времени.

### Исходная формулировка

**Возобновление связи (Last-Event-ID)**: При кратковременном разрыве соединения браузерный клиент автоматически переподключается и отправляет заголовок `Last-Event-ID` [587], указывая ID последнего успешно полученного сообщения. Напишите логику на сервере: считайте этот заголовок, найдите пропущенные сообщения в буфере истории событий вашей программы и отправьте их клиенту сразу после восстановления связи до начала трансляции основного потока [587].

## Теория

Спецификация W3C SSE гарантирует доставку сообщений 'at-least-once' при условии поддержки сервером истории событий:
1. При каждом событии сервер отправляет `id: <monotonic_id>\n`.
2. Браузер сохраняет этот ID в памяти.
3. При потере соединения (обрыв WiFi, таймаут прокси) браузер шлет GET-запрос с заголовком:
   `Last-Event-ID: 1045`
4. Сервер считывает этот заголовок и выполняет процедуру **Replay**:
   - Извлекает из кольцевого буфера (`RingBuffer`) или Redis Stream сообщения с \(ID > 1045\).
   - Отправляет накопившиеся пропущенные сообщения клиенту.
   - Переводит клиента в стандартный режим прослушивания новых событий в реальном времени.
5. Если ID слишком старый и уже вытеснен из буфера, сервер может отправить специальное событие `event: sync_required`, вынуждая клиент запросить полный снимок состояния через REST API.

## Решение по шагам

1. Создайте потокобезопасный кольцевой буфер `EventBuffer` фиксированной емкости (например, 1 000 сообщений).
2. В HTTP-хэндлере прочитайте заголовок `r.Header.Get("Last-Event-ID")`.
3. Если заголовок присутствует, выполните `buffer.GetSince(lastID)` и отправьте найденные события клиенту, вызвав `Flush()`.
4. Подпишите клиента на новые события и продолжите обычный стриминг.

## Код решения

**`replay_server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"strconv"
	"sync"
	"time"
)

type EventMessage struct {
	ID   int64  `json:"id"`
	Data string `json:"data"`
}

type EventRingBuffer struct {
	mu     sync.RWMutex
	events []EventMessage
	cap    int
}

func NewEventRingBuffer(cap int) *EventRingBuffer {
	return &EventRingBuffer{
		events: make([]EventMessage, 0, cap),
		cap:    cap,
	}
}

func (b *EventRingBuffer) Add(ev EventMessage) {
	b.mu.Lock()
	defer b.mu.Unlock()

	if len(b.events) >= b.cap {
		b.events = b.events[1:] // Вытеснение старейшего
	}
	b.events = append(b.events, ev)
}

func (b *EventRingBuffer) GetSince(lastID int64) []EventMessage {
	b.mu.RLock()
	defer b.mu.RUnlock()

	var missed []EventMessage
	for _, ev := range b.events {
		if ev.ID > lastID {
			missed = append(missed, ev)
		}
	}
	return missed
}

func replayHandler(buf *EventRingBuffer) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/event-stream")
		w.Header().Set("Cache-Control", "no-cache")
		w.Header().Set("Connection", "keep-alive")

		rc := http.NewResponseController(w)

		// Читаем Last-Event-ID
		lastIDStr := r.Header.Get("Last-Event-ID")
		if lastIDStr != "" {
			if lastID, err := strconv.ParseInt(lastIDStr, 10, 64); err == nil {
				missed := buf.GetSince(lastID)
				fmt.Printf("[Replay] Sending %d missed events to reconnecting client\n", len(missed))
				for _, ev := range missed {
					fmt.Fprintf(w, "id: %d\ndata: %s\n\n", ev.ID, ev.Data)
				}
				_ = rc.Flush()
			}
		}

		// Симуляция новых сообщений
		ticker := time.NewTicker(2 * time.Second)
		defer ticker.Stop()

		for {
			select {
			case <-r.Context().Done():
				return
			case t := <-ticker.C:
				fmt.Fprintf(w, "data: live tick %s\n\n", t.Format("15:04:05"))
				if err := rc.Flush(); err != nil {
					return
				}
			}
		}
	}
}

func main() {
	buf := NewEventRingBuffer(50)
	// Наполняем буфер тестовыми событиями
	for i := int64(1); i <= 10; i++ {
		buf.Add(EventMessage{
			ID:   i,
			Data: fmt.Sprintf("Historical event #%d", i),
		})
	}

	http.HandleFunc("/events-replay", replayHandler(buf))
	fmt.Println("Replay SSE server running on :8080/events-replay")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Обработка Last-Event-ID с извлечением пропущенных событий из буфера и отправкой перед прямым эфиром

## Под капотом

В спецификации SSE W3C указано: если клиент передает `Last-Event-ID`, этот заголовок должен содержать значение поля `id:` последнего принятого события. Если соединение прервалось посреди передачи события (до получения завершающего `\n\n`), браузер не фиксирует новый `id`, тем самым гарантируя, что недополученное событие будет запрошено повторно.

## Подводные камни

Использование среза `b.events = b.events[1:]` без циклического индекса в срезе фиксированной емкости при миллионах событий приводит к частым перевыделениям базового массива и копированию памяти. В продакшене используйте классический кольцевой буфер на основе фиксированного массива с двумя указателями `head` и `tail` или Redis Streams (`XREAD`).

## На собеседовании

В Авито и Ozon на архитектурной секции спрашивают: 'Как организовать Replay-буфер в кластере из 20 экземпляров Go-сервиса за балансировщиком нагрузки, если клиент при реконнекте попадает на другой Pod?' Ответ: использовать централизованное хранилище событий с последовательными ID (Redis Stream или Kafka). При получении Last-Event-ID любой Pod выполняет `XREAD STREAMS mystream <last_id>` и досылает недостающие данные.
