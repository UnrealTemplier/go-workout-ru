# Ограничение количества одновременных соединений на пользователя

## Условие

32. **Max connections per user**: Ограничьте количество SSE connections на одного пользователя (обычно 1-3). Предотвращает resource exhaustion.

### Исходная формулировка

**Max connections per user**: Ограничьте количество SSE connections на одного пользователя (обычно 1-3). Предотвращает resource exhaustion.

## Теория

Браузерные клиенты при открытии множества вкладок или некорректно написанных фронтенд-скриптах могут порождать десятки параллельных SSE-подключений. 
В спецификации HTTP/1.1 действует жесткое браузерное ограничение: не более 6 одновременных TCP-соединений к одному домену. Если пользователь откроет 6 вкладок с SSE по HTTP/1.1, все остальные HTTP-запросы (загрузка картинок, REST API) в браузере будут полностью заблокированы!

Кроме того, злоумышленник может исчерпать файловые дескрипторы сервера (Resource Exhaustion / DoS).

Для защиты:
1. Сервер ведет счетчик открытых сессий для каждого `userID`.
2. При попытке открыть сессию сверх лимита (например, максимум 3 сессии) сервер возвращает статус `429 Too Many Requests`.
3. Либо сервер закрывает самую старую сессию пользователя (Kick oldest session), освобождая слот для новой вкладки.

## Решение по шагам

1. Создайте структуру `UserConnectionLimiter` с `maxPerUser int` и картой счетчиков `sync.Mutex`.
2. В начале хэндлера вызовите `limiter.Acquire(userID)`.
3. Если лимит превышен, верните `http.StatusTooManyRequests` с сообщением об ошибке.
4. Оберните освобождение слота `defer limiter.Release(userID)`.
5. Установите заголовки SSE и начните передачу.

## Код решения

**`limiter.go`**

```go
package main

import (
	"errors"
	"fmt"
	"net/http"
	"sync"
	"time"
)

var ErrLimitExceeded = errors.New("concurrent connection limit exceeded")

type UserConnectionLimiter struct {
	mu         sync.Mutex
	maxConn    int
	userCounts map[string]int
}

func NewUserConnectionLimiter(maxConn int) *UserConnectionLimiter {
	return &UserConnectionLimiter{
		maxConn:    maxConn,
		userCounts: make(map[string]int),
	}
}

func (l *UserConnectionLimiter) Acquire(userID string) error {
	l.mu.Lock()
	defer l.mu.Unlock()

	current := l.userCounts[userID]
	if current >= l.maxConn {
		return ErrLimitExceeded
	}

	l.userCounts[userID] = current + 1
	return nil
}

func (l *UserConnectionLimiter) Release(userID string) {
	l.mu.Lock()
	defer l.mu.Unlock()

	current := l.userCounts[userID]
	if current <= 1 {
		delete(l.userCounts, userID)
	} else {
		l.userCounts[userID] = current - 1
	}
}

func limitedSSEHandler(limiter *UserConnectionLimiter) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		userID := r.URL.Query().Get("user_id")
		if userID == "" {
			http.Error(w, "user_id is required", http.StatusBadRequest)
			return
		}

		if err := limiter.Acquire(userID); err != nil {
			http.Error(w, "Too many active SSE sessions for this user", http.StatusTooManyRequests)
			return
		}
		defer limiter.Release(userID)

		w.Header().Set("Content-Type", "text/event-stream")
		w.Header().Set("Cache-Control", "no-cache")
		w.Header().Set("Connection", "keep-alive")

		rc := http.NewResponseController(w)
		fmt.Fprintf(w, "event: ready\ndata: Session started for user %s\n\n", userID)
		_ = rc.Flush()

		ticker := time.NewTicker(1 * time.Second)
		defer ticker.Stop()

		for {
			select {
			case <-r.Context().Done():
				return
			case t := <-ticker.C:
				if _, err := fmt.Fprintf(w, "data: ping at %s\n\n", t.Format("15:04:05")); err != nil {
					return
				}
				if err := rc.Flush(); err != nil {
					return
				}
			}
		}
	}
}

func main() {
	limiter := NewUserConnectionLimiter(2) // Максимум 2 соединения на пользователя
	http.HandleFunc("/stream", limitedSSEHandler(limiter))

	fmt.Println("SSE Max connections server running on :8080/stream")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Ограничение количества одновременных SSE соединений на одного пользователя с кодом 429

## Под капотом

Спецификация HTTP/1.1 (RFC 7230) рекомендует клиентам ограничивать количество параллельных TCP-сессий к одному хосту. В современных браузерах (Chrome, Firefox) этот лимит равен 6. В случае HTTP/2 множество SSE-потоков мультиплексируются внутри единого TCP-соединения через виртуальные HTTP/2 Streams, снимая ограничение на 6 сокетов, однако лимитирование на бэкенде по-прежнему необходимо для защиты оперативной памяти от атак Slowloris.

## Подводные камни

Утечка счетчиков сессий при панике внутри хэндлера. Если `limiter.Release(userID)` вызван без ключевого слова `defer`, любая непредвиденная ошибка или вызов `panic()` приведет к тому, что счетчик пользователя навсегда останется увеличенным, и пользователь больше никогда не сможет открыть соединение до перезапуска сервера.

## На собеседовании

В Ozon и Авито на системном интервью часто спрашивают: 'Как ограничить подключения на пользователя в распределенной системе из 50 подов?' Ответ: использовать распределенный счетчик в Redis. При коннекте выполнять атомарный `INCR user:conn:<id>` с проверкой `> MAX_LIMIT`. Если превышен — `DECR` и отказ. Для надежности при сбоях использовать Lua-скрипт с TTL на ключ сессии, продлеваемый периодическим heartbeat.
