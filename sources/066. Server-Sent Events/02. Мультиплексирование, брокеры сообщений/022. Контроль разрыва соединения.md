# Контроль разрыва соединения через req.Context().Done()

## Условие

22. **Контроль разрыва соединения**: Запустите бесконечный цикл отправки событий (например, системных метрик раз в секунду). Напишите обработку отключения клиента: внутри `select` прослушивайте канал закрытия контекста запроса `<-req.Context().Done()`. При получении сигнала мгновенно прерывайте горутину, освобождая ресурсы сервера.

### Исходная формулировка

**Контроль разрыва соединения**: Запустите бесконечный цикл отправки событий (например, системных метрик раз в секунду). Напишите обработку отключения клиента: внутри `select` прослушивайте канал закрытия контекста запроса `<-req.Context().Done()` [586]. При получении сигнала мгновенно прерывайте цикл и завершайте работу горутины, чтобы избежать утечки ресурсов процессора [586].

## Теория

В HTTP/1.1 и HTTP/2 сервер не получает явных пакетов данных от клиента во время чтения однонаправленного SSE-потока. Если пользователь закрывает вкладку браузера или теряет связь:
1. TCP-стек операционной системы отправляет FIN или RST пакет.
2. Внутренний цикл чтения `http.Server` (`conn.serve`) фиксирует EOF или ошибку сокета.
3. Рантайм Go немедленно отменяет контекст текущего запроса `r.Context()`, закрывая сигнальный канал `r.Context().Done()`.
4. Если горутина-обработчик SSE не слушает `<-r.Context().Done()`, а блокируется на внутреннем канале данных или долгом `time.Sleep()`, возникает **утечка горутины (goroutine leak)**. При миллионах клиентов такие зависшие горутины исчерпывают память сервера и вызывают OOM Killer.

## Решение по шагам

1. Получите контекст запроса через `ctx := r.Context()`.
2. В основном цикле генерации/отправки событий используйте конструкцию `select`.
3. Одной из веток `select` обязательно должен быть кейс `case <-ctx.Done():`.
4. При срабатывании кейса логируйте причину отключения через `ctx.Err()` (`context.Canceled`), освобождайте связанные ресурсы и делайте `return`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"runtime"
	"sync/atomic"
	"time"
)

var activeStreams atomic.Int64

func metricsHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	ctx := r.Context()

	clientCount := activeStreams.Add(1)
	defer activeStreams.Add(-1)

	fmt.Printf("[+] Client connected (active: %d)\n", clientCount)

	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	var m runtime.MemStats

	for {
		select {
		case <-ctx.Done():
			// Немедленный выход при закрытии вкладки клиентом
			fmt.Printf("[-] Client disconnected: %v (remaining: %d)\n", ctx.Err(), activeStreams.Load()-1)
			return

		case <-ticker.C:
			runtime.ReadMemStats(&m)
			data := fmt.Sprintf(`{"alloc_mb":%.2f,"goroutines":%d}`, float64(m.Alloc)/(1024*1024), runtime.NumGoroutine())

			if _, err := fmt.Fprintf(w, "data: %s\n\n", data); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/metrics-stream", metricsHandler)
	fmt.Println("Server running on :8080/metrics-stream")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Мгновенное обнаружение отключения клиента через r.Context().Done() с атомарным счетчиком соединений

## Под капотом

В недрах `net/http` для каждого соединения запускается фоновая горутина, выполняющая `conn.serve()`. Когда сокет закрывается, системный вызов `epoll_wait` (в Linux) возвращает событие `EPOLLRDHUP` или `EPOLLHUP`. Сетевой поллер Go (`runtime/netpoll.go`) будит горутину чтения, которая видит `io.EOF`, вызывает `cancelCtx()` для контекста запроса и переводит соединение в состояние `StateClosed`.

## Подводные камни

Использование блокирующих вызовов `time.Sleep()` вместо `time.NewTicker` или таймеров в `select`. Во время выполнения `time.Sleep(5 * time.Second)` горутина не реагирует на `ctx.Done()`, продолжая удерживать память и стек до завершения сна, даже если клиент отключился на первой миллисекунде.

## На собеседовании

На собеседованиях в Wildberries и Касперский любят давать задачу: 'У нас запущен SSE сервер, при 10 000 клиентов нагрузка на CPU 5%, но через час сервер падает по памяти. При этом pprof показывает 200 000 горутин. В чем причина?' Ответ: горутины стриминга заблокированы на операциях записи или каналах и не имеют ветки `case <-r.Context().Done()`, приводя к накоплению зомби-горутин при реконнектах клиентов.
