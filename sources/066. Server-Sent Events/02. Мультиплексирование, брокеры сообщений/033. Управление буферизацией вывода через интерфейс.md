# Управление буферизацией вывода через интерфейс http.Flusher

## Условие

33. **[http.Flusher]**: В цикле пиши данные в `w.Write` в формате `data: {json}\n\n`. Вызывай `w.(http.Flusher).Flush()` после каждой записи, иначе данные останутся в буфере Go/nginx и не уйдут клиенту.

### Исходная формулировка

**[http.Flusher]**: В цикле пиши данные в `w.Write` в формате `data: {json}\n\n`. Вызывай `w.(http.Flusher).Flush()` после каждой записи, иначе данные останутся в буфере Go/nginx и не уйдут клиенту.

## Теория

По умолчанию стандартный HTTP-сервер Go (`net/http`) буферизирует вывод для минимизации количества дорогостоящих системных вызовов `write` в сетевой сокет. Буфер ответа (`bufio.Writer`) накапливает около 4 КБ данных, прежде чем отправить TCP-пакет в сеть.

Для потоковых протоколов (SSE, chunked transfer) такое поведение неприемлемо: клиент должен видеть события мгновенно, не дожидаясь заполнения 4-килобайтного буфера.

Интерфейс `http.Flusher`:
```go
type Flusher interface {
    Flush()
}
```
1. Реализуется внутренним типом `http.response`.
2. Приведение типов `flusher, ok := w.(http.Flusher)` проверяет поддержку потоковой передачи.
3. Метод `Flush()` принудительно сбрасывает накопленные байты из памяти Go в сетевой дескриптор сокета.

## Решение по шагам

1. Внутри HTTP-хэндлера проверьте поддержку `http.Flusher` через type assertion.
2. Если `!ok`, верните `http.StatusInternalServerError` с сообщением о неподдерживаемом потоковом режиме.
3. Запишите сформированное сообщение `data: ...\n\n` в `w`.
4. Немедленно вызовите `flusher.Flush()`.
5. Проверьте отправку событий с помощью утилиты `curl -N` (флаг `-N` отключает буферизацию в curl).

## Код решения

**`flusher.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func legacyFlusherHandler(w http.ResponseWriter, r *http.Request) {
	// Проверяем поддержку интерфейса http.Flusher
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Streaming unsupported by response writer", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	for i := 1; i <= 5; i++ {
		// Формируем событие
		msg := fmt.Sprintf("data: Step %d of 5 completed\n\n", i)
		if _, err := w.Write([]byte(msg)); err != nil {
			return
		}

		// Принудительный сброс сетевого буфера
		flusher.Flush()

		time.Sleep(1 * time.Second)
	}

	_, _ = w.Write([]byte("event: done\ndata: finished\n\n"))
	flusher.Flush()
}

func main() {
	http.HandleFunc("/stream-legacy", legacyFlusherHandler)
	fmt.Println("Legacy Flusher server running on :8080/stream-legacy")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Классический паттерн проверки и вызова w.(http.Flusher).Flush() для потоковой отправки

## Под капотом

При вызове `flusher.Flush()` сервер Go:
1. Если HTTP-заголовки еще не были отправлены, сериализует их в сетевой сокет с заголовком `Transfer-Encoding: chunked` (в HTTP/1.1).
2. Вызывает `w.bufw.Flush()`, что инициирует системный вызов `writev` или `sendto` в ядро ОС.
3. По умолчанию в Linux включен алгоритм Nagle (`TCP_NODELAY = false`), но Go в `net/http` по умолчанию включает сокетную опцию `TCP_NODELAY = 1`, поэтому TCP-пакет не задерживается стеком ядра и уходит в сеть мгновенно.

## Подводные камни

Оборачивание `http.ResponseWriter` сторонними middleware без делегирования интерфейса `http.Flusher`. Если ваше middleware логирования или сжатия декорирует `w` как простую структуру `struct { http.ResponseWriter }`, не реализующую метод `Flush()`, приведение `w.(http.Flusher)` вернет `false` и потоковая передача сломается.

## На собеседовании

В Касперском и Яндекс любят спрашивать: 'Что произойдет, если между Go-бэкендом и браузером стоит обратный прокси Nginx, и как на это влияет Flush()?' Ответ: Go сбросит буфер в сокет к Nginx, но если в Nginx включена директива `proxy_buffering on;`, Nginx задержит байты в своем буфере. Для предотвращения этого сервер Go должен отдавать заголовок `X-Accel-Buffering: no`, который отключает буферизацию в Nginx на лету.
