### Исходная формулировка

**Rate Limit per Connection.**: Реализуйте token bucket для каждого SSE-клиента: максимум 100 событий/сек. При превышении — дроп (`select` с `default`) или буферизация с ограниченным размером (drop oldest). Объясните, как slow consumer может вызвать OOM без backpressure.

## Теория

Проблема медленного потребителя (**Slow Consumer Problem**):
Когда сервер генерирует 1 000 сообщений в секунду, а мобильный клиент подключен через нестабильный 3G со скоростью 10 сообщений в секунду:
1. Выходной буфер сокета заполняется.
2. Канал отправки в памяти Go заполняется.
3. Если канал неограничен (unbounded) или создаются новые горутины на каждое событие, память приложения растет бесконтрольно, вызывая Out-Of-Memory (OOM).

Для защиты применяются:
1. **Token Bucket Rate Limiting:** Ограничение максимальной частоты сообщений на клиента (например, 100 сообщений/сек с запасом burst=20).
2. **Backpressure с политикой вытеснения (Drop Oldest):** Буфер ограниченного размера (кольцевой буфер или канал фиксированной длины). Если буфер полон, самое старое событие отбрасывается, уступая место свежим данным:
   ```go
   select {
   case clientCh <- msg:
   default:
       // Буфер полон: вытесняем старое сообщение
       select {
       case <-clientCh:
       default:
       }
       clientCh <- msg
   }
   ```

## Решение по шагам

1. Создайте структуру клиента с буферизированным каналом `chan []byte` фиксированной емкости (например, 100).
2. Реализуйте алгоритм `TokenBucket` для ограничения пиковой нагрузки.
3. При отправке события проверьте лимит токенов: если токенов нет — отбросьте событие.
4. При записи в канал клиента используйте неблокирующий `select` с политикой вытеснения самого старого элемента.
5. Горутина-писатель читает из канала и отправляет данные в сетевой сокет.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync"
	"time"
)

// TokenBucket ограничивает пропускную способность потока
type TokenBucket struct {
	mu         sync.Mutex
	capacity   float64
	tokens     float64
	refillRate float64 // токенов в секунду
	lastRefill time.Time
}

func NewTokenBucket(rate, capacity float64) *TokenBucket {
	return &TokenBucket{
		capacity:   capacity,
		tokens:     capacity,
		refillRate: rate,
		lastRefill: time.Now(),
	}
}

func (tb *TokenBucket) Allow() bool {
	tb.mu.Lock()
	defer tb.mu.Unlock()

	now := time.Now()
	elapsed := now.Sub(tb.lastRefill).Seconds()
	tb.lastRefill = now

	tb.tokens += elapsed * tb.refillRate
	if tb.tokens > tb.capacity {
		tb.tokens = tb.capacity
	}

	if tb.tokens >= 1.0 {
		tb.tokens -= 1.0
		return true
	}
	return false
}

type SSEClient struct {
	ch      chan string
	limiter *TokenBucket
}

func (c *SSEClient) Send(msg string) bool {
	if !c.limiter.Allow() {
		return false // Дроп по rate limit
	}

	select {
	case c.ch <- msg:
		return true
	default:
		// Буфер полон (медленный клиент): дропаем старейшее
		select {
		case <-c.ch:
		default:
		}
		c.ch <- msg
		return true
	}
}

func rateLimitedStream(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	client := &SSEClient{
		ch:      make(chan string, 10),
		limiter: NewTokenBucket(100, 20), // 100 сообщений/сек, всплеск до 20
	}

	// Имитируем генерацию сообщений
	go func() {
		for i := 0; i < 500; i++ {
			client.Send(fmt.Sprintf("Event payload #%d", i))
			time.Sleep(5 * time.Millisecond) // 200 msg/sec
		}
	}()

	for {
		select {
		case <-r.Context().Done():
			return
		case msg := <-client.ch:
			if _, err := fmt.Fprintf(w, "data: %s\n\n", msg); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/limited-events", rateLimitedStream)
	fmt.Println("Server running on :8080/limited-events")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Token Bucket Rate Limiter в сочетании с drop-oldest политикой для предотвращения переполнения буфера

## Под капотом

В сетевом стеке Linux размер TCP send buffer регулируется параметрами `net.ipv4.tcp_wmem`. Когда буфер сокета заполняется, вызов `w.Write()` блокируется в системном вызове `sendto`/`write`. Если обработчик Go пишет напрямую в сокет без промежуточного канала и таймаута, вся горутина засыпает до освобождения места в буфере сокета медленного клиента. Использование выделенного буфера `chan` с политикой вытеснения изолирует серверный конвейер от сетевых задержек конкретного клиента.

## Подводные камни

Блокировка общего брокера сообщений. Если брокер делает `client.ch <- msg` в одном цикле по всем подписчикам, один медленный или зависший клиент заблокирует рассылку всем остальным 50 000 клиентам! Запись всегда должна производиться через неблокирующий `select` с `default` веткой.

## На собеседовании

В Ozon на секции по надежности систем часто спрашивают: 'Что делать, если брокер рассылает биржевые котировки, а у части пользователей мобильный интернет периодически зависает?' Ответ: применять политику Drop-Oldest (Conflation/Coalescing) — клиенту не нужны устаревшие котировки цен 5-секундной давности; достаточно хранить последнее актуальное состояние по каждому инструменту и передавать только свежий срез при разблокировке канала.
