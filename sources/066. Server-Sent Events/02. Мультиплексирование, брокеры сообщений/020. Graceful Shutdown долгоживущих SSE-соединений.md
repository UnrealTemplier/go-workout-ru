# Graceful Shutdown долгоживущих SSE-соединений при SIGTERM

## Условие

20. **Graceful Shutdown.**: При получении `SIGTERM`: (1) закрыть listener для новых HTTP-соединений, (2) дождаться отправки pending events всем клиентам (context с timeout), (3) закрыть существующие SSE-соединения корректно. Объясните, почему `http.Server.Shutdown` не достаточен для long-lived SSE-клиентов.

### Исходная формулировка

**Graceful Shutdown.**: При получении `SIGTERM`: (1) закрыть listener для новых HTTP-соединений, (2) дождаться отправки pending events всем клиентам (context с timeout), (3) закрыть существующие SSE-соединения корректно. Объясните, почему `http.Server.Shutdown` не достаточен для long-lived SSE-коннекшнов без дополнительной логики.

## Теория

Стандартный метод Go `http.Server.Shutdown(ctx)`:
1. Закрывает все активные слушающие сокеты (`net.Listener`), прекращая прием новых соединений.
2. Закрывает все неактивные соединения в пуле Keep-Alive (`StateIdle`).
3. **НО НЕ ПРЕРЫВАЕТ** активные соединения в состоянии `StateActive`! Так как HTTP-обработчик SSE представляет собой бесконечный цикл `for { select { ... } }`, горутина обработчика не завершается, пока не завершится контекст запроса `r.Context()`. 

Следовательно, `server.Shutdown` зависнет в ожидании завершения горутин SSE вплоть до истечения переданного таймаута `shutdownCtx`, после чего принудительно закроет TCP сокеты через `Close()`. Это приводит к сбросу соединений TCP RST и ошибкам `ERR_CONNECTION_RESET` на стороне клиентов.

Для чистого завершения требуется:
- Централизованный корневой контекст `appCtx` с отменой (`cancelFunc`).
- Регистрация активных SSE-клиентов или ожидание завершения через `sync.WaitGroup`.
- При получении `SIGTERM` отправка прощального события клиентам (`event: shutdown\ndata: reconnect_in_5s\n\n`), закрытие каналов клиентов и дожидание выхода из хэндлеров.

## Решение по шагам

1. Создайте корневой контекст `ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)`.
2. Создайте брокер SSE с поддержкой `sync.WaitGroup` для учета активных потоков.
3. В цикле стриминга ожидайте сигналы либо из канала событий, либо из `r.Context().Done()`, либо из глобального `ctx.Done()`.
4. Перед выходом отправьте клиенту финальное SSE-сообщение о плановой перезагрузке, чтобы браузер знал, что нужно переподключиться.
5. Вызовите `server.Shutdown()` после оповещения всех клиентов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"
)

type SSEManager struct {
	wg sync.WaitGroup
}

func (m *SSEManager) Handler(w http.ResponseWriter, r *http.Request) {
	m.wg.Add(1)
	defer m.wg.Done()

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			// Клиент закрыл вкладку
			return
		case t := <-ticker.C:
			_, err := fmt.Fprintf(w, "data: tick %s\n\n", t.Format(time.RFC3339))
			if err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	mgr := &SSEManager{}
	mux := http.NewServeMux()
	mux.HandleFunc("/events", mgr.Handler)

	srv := &http.Server{
		Addr:    ":8080",
		Handler: mux,
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	go func() {
		fmt.Println("SSE Server listening on :8080")
		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			fmt.Printf("HTTP listen error: %v\n", err)
		}
	}()

	<-ctx.Done()
	fmt.Println("\nShutdown signal received: closing listeners...")

	// Даем 5 секунд на корректное завершение
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	// 1. Закрываем слушающий сокет
	if err := srv.Shutdown(shutdownCtx); err != nil {
		fmt.Printf("Server shutdown error: %v\n", err)
	}

	// 2. Ждем завершения SSE потоков
	waitCh := make(chan struct{})
	go func() {
		mgr.wg.Wait()
		close(waitCh)
	}()

	select {
	case <-waitCh:
		fmt.Println("All SSE clients terminated cleanly.")
	case <-shutdownCtx.Done():
		fmt.Println("Timeout reached: forced exit.")
	}
}
```

ℹ️ Контролируемый graceful shutdown долгоживущих стримов с синхронизацией через sync.WaitGroup

## Под капотом

В `net/http/server.go` при вызове `Shutdown()` сервер устанавливает флаг `inShutdown = true`, закрывает `Listener` и итерируется по связному списку открытых `conn`. Для каждого соединения вызывается `c.rwc.Close()` только если его состояние равно `StateIdle`. Если же соединение `StateActive` (выполняет `ServeHTTP`), `Shutdown` ожидает, пока счетчик активных соединений не обнулится, либо пока не истечет контекст. Так как SSE держит `ServeHTTP` бесконечно, без явного выхода из функции хэндлера `Shutdown` не завершится.

## Подводные камни

Распространенная ошибка в микросервисах Kubernetes: установка слишком короткого `terminationGracePeriodSeconds` (например, 10 сек) при таймауте `Shutdown` в 30 сек. Pod будет уничтожен `SIGKILL` до того, как клиенты успеют штатно переподключиться к новому Pod, что вызовет лавину одновременных ошибок у сотен тысяч подключенных пользователей.

## На собеседовании

В Ozon и Авито на секции System Design часто спрашивают: 'Что произойдет со 100 000 SSE-подключений при деплое новой версии сервиса в K8s?' Ожидаемый ответ: без отправки клиентам команды переподключения с джиттером (случайной задержкой 1-5 сек) сервис при перезапуске получит шторм повторных подключений (Thundering Herd Problem). Нужно слать событие `event: maintenance\ndata: retry_with_jitter` и завершать соединение со стороны сервера.
