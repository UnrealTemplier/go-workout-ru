### Исходная формулировка

**SSE vs WebSocket.**: Реализуйте тот же функционал (broadcast с named events) через WebSocket (`gorilla/websocket`). Сравните: SSE — однонаправленный, текстовый, автоматический reconnect, работает через HTTP/1.1; WebSocket — дуплексный, binary, требует ручного reconnect. Объясните, когда SSE предпочтительнее (live dashboards, notifications), а когда WebSocket (чаты, игры).

## Теория

Выбор между Server-Sent Events (SSE) и WebSockets (WS) — фундаментальное архитектурное решение в распределенных веб-системах.

### Сравнительная матрица:
| Характеристика | Server-Sent Events (SSE) | WebSocket (WS) |
| :--- | :--- | :--- |
| **Направление передачи** | Однонаправленный (Server -> Client) | Полнодуплексный (Server <-> Client) |
| **Протокол** | Чистый HTTP/1.1 или HTTP/2 | Кастомный TCP-протокол (`ws://`, `wss://`) после HTTP Upgrade |
| **Тип данных** | Только UTF-8 текст | Текст (UTF-8) и Бинарные фреймы (Protobuf, MessagePack) |
| **Автоматический реконнект** | Встроен в браузерный `EventSource` | Требует ручной реализации в JS |
| **Прохождение через Proxy/Firewall** | Идеально (стандартный HTTP-трафик) | Часто блокируется строгими корпоративными прокси |
| **Мультиплексирование** | Из коробки при HTTP/2 (1 TCP-соединение) | Каждое соединение требует отдельного TCP-сокета |
| **Поддержка Last-Event-ID** | Встроена в стандарт W3C | Требует собственной прикладной логики |

### Когда выбирать SSE:
1. Однонаправленные потоки: биржевые котировки, дашборды мониторинга, ленты новостей, уведомления, ответы генеративных нейросетей (LLM streaming).
2. Критична простота инфраструктуры: балансировка через стандартный Ingress/Nginx без настройки WebSocket Upgrade.
3. Экономия ресурсов за счет HTTP/2 мультиплексирования.

## Решение по шагам

1. Реализуйте минимальный сервер WebSocket с помощью библиотеки или сырого сетевого рукопожатия.
2. Продемонстрируйте механизм Broadcast с именованными событиями.
3. Проанализируйте ключевые отличия в коде и накладных расходах.

## Код решения

**`comparison.go`**

```go
package main

import (
	"crypto/sha1"
	"encoding/base64"
	"fmt"
	"net"
	"net/http"
	"strings"
	"time"
)

// MinimalWSUpgrader выполняет стандартный RFC 6455 WebSocket handshake без сторонних зависимостей
func MinimalWSUpgrader(w http.ResponseWriter, r *http.Request) (net.Conn, error) {
	if !strings.EqualFold(r.Header.Get("Upgrade"), "websocket") {
		return nil, fmt.Errorf("not a websocket handshake")
	}

	key := r.Header.Get("Sec-WebSocket-Key")
	guid := "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"
	h := sha1.New()
	h.Write([]byte(key + guid))
	acceptKey := base64.StdEncoding.EncodeToString(h.Sum(nil))

	hj, ok := w.(http.Hijacker)
	if !ok {
		return nil, fmt.Errorf("hijack not supported")
	}

	conn, bufrw, err := hj.Hijack()
	if err != nil {
		return nil, err
	}

	res := "HTTP/1.1 101 Switching Protocols\r\n" +
		"Upgrade: websocket\r\n" +
		"Connection: Upgrade\r\n" +
		"Sec-WebSocket-Accept: " + acceptKey + "\r\n\r\n"

	if _, err := bufrw.WriteString(res); err != nil {
		conn.Close()
		return nil, err
	}
	if err := bufrw.Flush(); err != nil {
		conn.Close()
		return nil, err
	}

	return conn, nil
}

// wsSendTextFrame отправляет одиночный текстовый фрейм WebSocket
func wsSendTextFrame(conn net.Conn, text string) error {
	payload := []byte(text)
	length := len(payload)
	frame := []byte{0x81} // FIN=1, Opcode=1 (Text)

	if length <= 125 {
		frame = append(frame, byte(length))
	} else if length <= 65535 {
		frame = append(frame, 126, byte(length>>8), byte(length&0xFF))
	} else {
		return fmt.Errorf("payload too large for demo")
	}
	frame = append(frame, payload...)
	_, err := conn.Write(frame)
	return err
}

func wsHandler(w http.ResponseWriter, r *http.Request) {
	conn, err := MinimalWSUpgrader(w, r)
	if err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}
	defer conn.Close()

	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			return
		case t := <-ticker.C:
			msg := fmt.Sprintf(`{"event":"price_update","data":"BTC: 65000 @ %s"}`, t.Format("15:04:05"))
			if err := wsSendTextFrame(conn, msg); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/ws", wsHandler)
	fmt.Println("Comparison server running on :8080/ws")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Рукопожатие и отправка фреймов WebSocket по RFC 6455 для сравнения сложности протоколов

## Под капотом

WebSocket требует переключения протокола (Switching Protocols 101) и захвата сокета (`Hijack`). После этого сокет переходит в полнодуплексный режим с бинарным кадрированием (фреймы с маскированием со стороны клиента, контрольные фреймы Ping/Pong, Close). SSE работает поверх стандартного HTTP-пайплайна, не требуя выхода из абстракций `http.ResponseWriter` и слоя HTTP middleware.

## Подводные камни

Использование WebSocket для задач, где клиент никогда не шлет данные серверу (например, прогресс экспорта отчета или уведомления об изменениях). WebSocket усложняет балансировку нагрузки, требует кастомного кода переподключения в UI и занимает отдельный TCP-сокет на каждое соединение даже при наличии HTTP/2.

## На собеседовании

В Яндекс и VK часто спрашивают: 'Когда при реализации чата или онлайн-документов стоит предпочесть связку HTTP POST + SSE вместо единого WebSocket?' Ответ: если исходящих сообщений от клиента мало по сравнению со входящими, разделение на POST (для мутаций) и SSE (для получения изменений) упрощает аутентификацию, идемпотентность, кэширование и распределенную трассировку через стандартные HTTP-заголовки.
