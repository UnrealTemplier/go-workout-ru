# Неблокирующая рассылка и дроп медленных клиентов (Drop on Full Buffer)

## Условие

61. **Дроп медленных клиентов**: В брокере из упр. 790 что будет, если у одного клиента завис интернет, и его канал переполнился? Твой цикл `Broadcast` заблокируется! Сделай запись в канал клиента неблокирующей (через `select` + `default`). Если канал переполнен — дропай событие или отключай клиента.

### Исходная формулировка

**Дроп медленных клиентов**: В брокере из упр. 790 что будет, если у одного клиента завис интернет, и его канал переполнился? Твой цикл `Broadcast` заблокируется! Сделай запись в канал клиента неблокирующей (через `select` + `default`). Если канал полон — принудительно отключай клиента (закрывай канал) и освобождай ресурсы.

## Теория

Проблема блокирующей рассылки (Head-of-Line Blocking at Broker):
Если брокер выполняет рассылку в цикле:
```go
for clientCh := range b.clients {
    clientCh <- msg // ОПАСНО: БЛОКИРУЮЩАЯ ЗАПИСЬ!
}
```
Если у **одного** из 10 000 клиентов переполнился локальный канал (мобильная сеть зависла, сокет заблокирован), горутина брокера **заснет на этой операции**. В результате рассылка остановится для ВСЕХ остальных 9 999 клиентов!

Решение: **Неблокирующая запись с вытеснением или дропом**:
- Использование `select` с веткой `default`:
  ```go
  select {
  case clientCh <- msg:
  default:
      // Канал полон: дропаем событие или инициируем отключение
  }
  ```
- Либо отключение медленного клиента (Slow Consumer Eviction): если клиент переполнен, брокер закрывает его канал и удаляет из списка.

## Решение по шагам

1. Создайте брокер с буферизированными каналами клиентов.
2. В цикле рассылки используйте конструкцию `select` с `default`.
3. Реализуйте счетчик отброшенных сообщений (Drop Counter).
4. Протестируйте систему с быстрым и искусственно заблокированным клиентом.

## Код решения

**`nonblocking_broker.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync"
	"sync/atomic"
	"time"
)

type SafeBroker struct {
	mu          sync.RWMutex
	clients     map[chan []byte]struct{}
	droppedMsgs atomic.Uint64
}

func NewSafeBroker() *SafeBroker {
	return &SafeBroker{
		clients: make(map[chan []byte]struct{}),
	}
}

func (b *SafeBroker) Register() chan []byte {
	b.mu.Lock()
	defer b.mu.Unlock()

	ch := make(chan []byte, 4) // Небольшой буфер для демонстрации переполнения
	b.clients[ch] = struct{}{}
	return ch
}

func (b *SafeBroker) Unregister(ch chan []byte) {
	b.mu.Lock()
	defer b.mu.Unlock()

	delete(b.clients, ch)
	close(ch)
}

func (b *SafeBroker) Broadcast(msg []byte) {
	b.mu.RLock()
	defer b.mu.RUnlock()

	for ch := range b.clients {
		select {
		case ch <- msg:
			// Успешно доставлено в буфер клиента
		default:
			// Буфер переполнен: НЕ блокируемся, а отбрасываем событие
			b.droppedMsgs.Add(1)
			fmt.Println("[Broker] Slow client detected! Dropped message to avoid blocking.")
		}
	}
}

func main() {
	broker := NewSafeBroker()

	// 1. Быстрый клиент
	fastClient := broker.Register()
	go func() {
		for msg := range fastClient {
			_ = msg // Читает мгновенно
		}
	}()

	// 2. Медленный зависший клиент (не вычитывает канал)
	_ = broker.Register()

	// Рассылаем 10 сообщений
	for i := 1; i <= 10; i++ {
		broker.Broadcast([]byte(fmt.Sprintf("Event payload #%d", i)))
	}

	fmt.Printf("Total dropped messages for slow clients: %d\n", broker.droppedMsgs.Load())
	fmt.Println("Broker remained fully responsive without deadlocks!")
}
```

ℹ️ Неблокирующая отправка через select с веткой default для изоляции медленных клиентов

## Под капотом

Инструкция `select` в компиляторе Go транслируется в вызов `runtime.selectgo`. Когда присутствует блок `default`, runtime проверяет, свободен ли буфер канала `hchan.qcount < hchan.dataqsiz`. Если место есть, выполняется быстрая вставка. Если канал полон, горутина НЕ переходит в очередь ожидания `sendq`, а мгновенно переходит к выполнению ветки `default` за доли наносекунды.

## Подводные камни

Молчаливый дроп критически важных бизнес-событий (например, списания денег со счета) без уведомления клиента. Если данные критичны, брокер не должен их отбрасывать; вместо этого следует принудительно разорвать соединение с медленным клиентом, чтобы он переподключился и запросил пропущенные данные по `Last-Event-ID`.

## На собеседовании

В Wildberries и Tinkoff часто спрашивают: 'Какую стратегию выбрать при переполнении канала клиента: Drop Newest, Drop Oldest или Disconnect?' Ответ: Зависит от домена. Для котировок цен и метрик — Drop Oldest (клиенту нужна только последняя цена). Для финансовых транзакций и событий заказов — Disconnect (лучше форсировать реконнект, чем потерять часть истории).
