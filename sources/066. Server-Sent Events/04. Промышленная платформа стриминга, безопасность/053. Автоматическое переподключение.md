# Автоматическое переподключение и компенсация пропусков по Last-Event-ID

## Условие

53. **[Автоматическое переподключение]**: Браузерный `EventSource` автоматически переподключается при разрыве. Он отправит заголовок `Last-Event-ID` с последним полученным ID. На сервере прочитай этот заголовок и отправь пропущенные события.

### Исходная формулировка

**[Автоматическое переподключение]**: Браузерный `EventSource` автоматически переподключается при разрыве. Он отправит заголовок `Last-Event-ID` с последним полученным ID. На сервере прочитай этот заголовок и отправь пропущенные события.

## Теория

Автоматическое восстановление соединения (Seamless Reconnect) — одно из ключевых преимуществ SSE перед обычным HTTP и WebSocket:
1. Когда сетевое соединение разрывается, браузерный объект `EventSource` переходит в состояние `CONNECTING` и выжидает интервал (по умолчанию 3 секунды или значение из последней директивы `retry:`).
2. При формировании нового GET-запроса браузер автоматически подставляет HTTP-заголовок `Last-Event-ID: <id>`, содержащий значение поля `id:` последнего успешно разобранного фрейма.
3. Серверная логика должна:
   - Распарсить заголовок `r.Header.Get("Last-Event-ID")`.
   - Если заголовок присутствует, извлечь из хранилища (in-memory buffer, Redis или БД) все сообщения, чей ID строго больше полученного.
   - Незамедлительно отправить их клиенту и вызвать `Flush()`.
   - После этого подключить клиента к прямому эфиру новых событий.

## Решение по шагам

1. Создайте структуру сообщения с инкрементным ID `uint64`.
2. Реализуйте историю событий `EventStore` с методом `GetSince(id uint64) []Event`.
3. В обработчике проверьте `Last-Event-ID` и отправьте клиенту накопившиеся пропущенные данные.
4. Перейдите в цикл ожидания новых событий из канала.

## Код решения

**`reconnect_server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"strconv"
	"sync"
	"time"
)

type Event struct {
	ID   uint64
	Data string
}

type EventLog struct {
	mu     sync.RWMutex
	events []Event
}

func (l *EventLog) Append(data string) Event {
	l.mu.Lock()
	defer l.mu.Unlock()

	id := uint64(len(l.events) + 1)
	ev := Event{ID: id, Data: data}
	l.events = append(l.events, ev)
	return ev
}

func (l *EventLog) GetSince(lastID uint64) []Event {
	l.mu.RLock()
	defer l.mu.RUnlock()

	if lastID >= uint64(len(l.events)) {
		return nil
	}
	return append([]Event(nil), l.events[lastID:]...)
}

func autoReconnectHandler(log *EventLog) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/event-stream")
		w.Header().Set("Cache-Control", "no-cache")
		w.Header().Set("Connection", "keep-alive")

		rc := http.NewResponseController(w)

		// 1. Проверяем заголовок Last-Event-ID
		lastIDHeader := r.Header.Get("Last-Event-ID")
		if lastIDHeader != "" {
			if lastID, err := strconv.ParseUint(lastIDHeader, 10, 64); err == nil {
				missed := log.GetSince(lastID)
				fmt.Printf("[Sync] Client resumed from ID %d. Sending %d missed events\n", lastID, len(missed))
				for _, ev := range missed {
					fmt.Fprintf(w, "id: %d\ndata: %s\n\n", ev.ID, ev.Data)
				}
				_ = rc.Flush()
			}
		}

		ticker := time.NewTicker(2 * time.Second)
		defer ticker.Stop()

		for {
			select {
			case <-r.Context().Done():
				return
			case t := <-ticker.C:
				ev := log.Append(fmt.Sprintf("Live metric at %s", t.Format("15:04:05")))
				if _, err := fmt.Fprintf(w, "id: %d\ndata: %s\n\n", ev.ID, ev.Data); err != nil {
					return
				}
				if err := rc.Flush(); err != nil {
					return
				}
			}
		}
	}
}

func main() {
	eventLog := &EventLog{}
	http.HandleFunc("/events", autoReconnectHandler(eventLog))
	fmt.Println("Auto-reconnect SSE server running on :8080/events")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Обработка заголовка Last-Event-ID и повторная передача пропущенных сообщений из истории

## Под капотом

Спецификация браузерного `EventSource` определяет, что значение `lastEventId` обновляется в памяти только после успешного прочтения завершающей пустой строки `\n\n`. Если пакет с оборванным событием поступил частично, браузер сохранит предыдущий подтвержденный `id`, обеспечивая отсутствие потерянных данных при повторном подключении.

## Подводные камни

Отправка ID событий в произвольном строковом формате (например, случайный UUID) без сохранения индексированного порядка. Без монотонно возрастающих идентификаторов или временных меток сервер не может быстро определить, какие события идут после переданного ID.

## На собеседовании

В Яндекс и Авито часто спрашивают: 'Что делать, если клиент отсутствовал в сети 2 часа, и объем пропущенных событий превышает 50 МБ?' Ответ: Сервер должен проверять возраст переданного Last-Event-ID. Если он выходит за пределы окна хранения (Retention Window), сервер отправляет кастомное событие `event: resync_required` и закрывает стрим, указывая клиенту перезагрузить актуальное состояние через стандартный REST API эндпоинт.
