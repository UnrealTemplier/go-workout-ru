# Координация вкладок браузера через BroadcastChannel API (Multi-tab SSE)

## Условие

56. **SSE multi-tab coordination**: Через `BroadcastChannel` API координируйте SSE connections между вкладками браузера — только одна вкладка держит connection, остальные получают события через BroadcastChannel.

### Исходная формулировка

**SSE multi-tab coordination**: Через `BroadcastChannel` API координируйте SSE connections между вкладками браузера — только одна вкладка держит connection, остальные получают события через BroadcastChannel.

## Теория

Когда пользователь открывает 10 вкладок одного сайта (интернет-магазина, трейдинговой площадки, таск-трекера):
- Каждая вкладка создает отдельное SSE соединение.
- 10 вкладок = 10 открытых TCP-сокетов, 10 горутин на сервере, десятикратный расход трафика.
- В HTTP/1.1 это мгновенно исчерпывает 6-сокетный лимит браузера.

Архитектура Single Leader Multi-Tab:
1. Вкладки общаются между собой локально в браузере с помощью **BroadcastChannel API** или **SharedWorker**.
2. Вкладки выбирают лидера (Leader Election) через `navigator.locks` или таймеры в `localStorage`.
3. Только вкладка-лидер открывает реальное соединение `EventSource` с бэкендом Go.
4. Принимая события, лидер ретранслирует их через `broadcastChannel.postMessage(event)`.
5. Все остальные вкладки-последователи получают события локально с нулевой нагрузкой на Go-сервер!
6. Если вкладка-лидер закрывается, оставшиеся вкладки моментально выбирают нового лидера.

## Решение по шагам

1. Создайте стандартный бэкенд Go, отдающий SSE поток.
2. Напишите клиентский HTML/JavaScript файл с использованием `new BroadcastChannel('sse_channel')`.
3. Реализуйте захват лидерства через Web Locks API `navigator.locks.request('sse_leader')`.
4. Продемонстрируйте, что при открытии 5 вкладок к серверу идет ровно одно подключение.

## Код решения

**`server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync/atomic"
	"time"
)

var openConnections atomic.Int64

func streamHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	connCount := openConnections.Add(1)
	defer openConnections.Add(-1)

	fmt.Printf("[+] Active SSE TCP Connections to Backend: %d\n", connCount)

	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			return
		case t := <-ticker.C:
			fmt.Fprintf(w, "data: Update at %s (Backend active conns: %d)\n\n",
				t.Format("15:04:05"), openConnections.Load())
			_ = rc.Flush()
		}
	}
}

func main() {
	http.HandleFunc("/multitab/events", streamHandler)
	fmt.Println("Multi-tab server running on :8080/multitab/events")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`index.html`**

```html
<!DOCTYPE html>
<html>
<head><title>Multi-Tab SSE Coordination</title></head>
<body>
<h2>Multi-Tab Coordination via Web Locks & BroadcastChannel</h2>
<div id="role" style="font-weight: bold;">Determining role...</div>
<div id="data"></div>

<script>
const channel = new BroadcastChannel('sse_bus');

channel.onmessage = (event) => {
    // Вкладки-последователи получают события локально
    document.getElementById('data').innerText = `[Follower received]: ${event.data}`;
};

if (navigator.locks) {
    // Захват эксклюзивной блокировки лидера
    navigator.locks.request('sse_leader_lock', async (lock) => {
        document.getElementById('role').innerText = "ROLE: LEADER (Holding single SSE connection)";
        console.log("Acquired leadership. Opening EventSource...");

        const es = new EventSource('/multitab/events');
        es.onmessage = (e) => {
            document.getElementById('data').innerText = `[Leader received]: ${e.data}`;
            // Транслируем всем остальным открытым вкладкам браузера
            channel.postMessage(e.data);
        };

        // Держим блокировку до закрытия вкладки
        await new Promise((resolve) => {
            window.addEventListener('unload', () => {
                es.close();
                resolve();
            });
        });
    });
} else {
    document.getElementById('role').innerText = "Web Locks not supported in this browser.";
}
</script>
</body>
</html>
```

## Под капотом

`navigator.locks.request` использует внутренний механизм IPC между процессами браузера Chromium/WebKit/Gecko. Браузер гарантирует, что только один процесс/вкладка удерживает блокировку. При закрытии вкладки-лидера или падении процесса блокировка немедленно освобождается ядром браузера, и следующая вкладка в очереди автоматически становится лидером и открывает `EventSource`.

## Подводные камни

Использование примитивных таймеров в `localStorage` вместо `navigator.locks` или `SharedWorker`. Опрос `localStorage` подвержен гонкам (Race Condition), из-за чего две вкладки могут одновременно посчитать себя лидером и открыть параллельные соединения.

## На собеседовании

В Яндекс и VK на фронтенд/фулстек секциях часто спрашивают: 'Как SharedWorker помогает оптимизировать SSE?' Ответ: SharedWorker работает как фоновый поток уровня всего браузера. Он держит ровно одно SSE соединение с Go-сервером независимо от того, сколько вкладок открыто пользователем, и раздает данные вьюшкам через MessagePort.
