# Сквозная реализация Last-Event-ID для непрерывного восстановления сессий

## Условие

69. **`Last-Event-ID` для seamless reconnect.**: Это встроенная фича браузерного `EventSource` API. Ваш сервер должен уметь resume с указанного ID.

### Исходная формулировка

**`Last-Event-ID` для seamless reconnect.**: Это встроенная фича браузерного `EventSource` API. Ваш сервер должен уметь resume с указанного ID.

## Теория

Завершающий интеграционный паттерн стандарта W3C SSE — гарантированная доставка без дубликатов и пропусков (Exactly-Once / At-Least-Once Delivery):
1. **Каноничный идентификатор:** Каждое событие системы снабжается глобально уникальным монотонным ID (Snowflake, инкрементный счетчик Redis или Sequence ID).
2. **Хранилище истории:** Сервер хранит скользящее окно последних \(N\) событий (или события за последние \(M\) минут).
3. **Обработка рукопожатия:**
   - Клиент передает заголовок `Last-Event-ID`.
   - Если заголовок пустой — клиент новый, ему отправляется текущий snapshot.
   - Если заголовок заполнен — сервер выполняет replay пропущенных событий начиная с \(ID + 1\).
   - После завершения replay сокет без задержек переключается на прямой эфир (Live Stream).

## Решение по шагам

1. Создайте структуру хранилища `HistoryStore` с возможностью извлечения событий по фильтру `ID > lastID`.
2. Реализуйте полный алгоритм обработки `Last-Event-ID` в HTTP-хэндлере.
3. Продемонстрируйте бесшовное возобновление стрима после искусственного разрыва связи.

## Код решения

**`seamless_reconnect.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"strconv"
	"sync"
	"time"
)

type StreamItem struct {
	ID        int64
	EventName string
	Payload   string
}

type ResilientServer struct {
	mu      sync.RWMutex
	history []StreamItem
	current int64
}

func NewResilientServer() *ResilientServer {
	return &ResilientServer{
		history: make([]StreamItem, 0, 1000),
	}
}

func (s *ResilientServer) Publish(eventName, payload string) StreamItem {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.current++
	item := StreamItem{
		ID:        s.current,
		EventName: eventName,
		Payload:   payload,
	}
	s.history = append(s.history, item)
	return item
}

func (s *ResilientServer) GetMissed(lastID int64) []StreamItem {
	s.mu.RLock()
	defer s.mu.RUnlock()

	var missed []StreamItem
	for _, item := range s.history {
		if item.ID > lastID {
			missed = append(missed, item)
		}
	}
	return missed
}

func (s *ResilientServer) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)

	// 1. Проверяем заголовок Last-Event-ID
	lastIDStr := r.Header.Get("Last-Event-ID")
	if lastIDStr != "" {
		if lastID, err := strconv.ParseInt(lastIDStr, 10, 64); err == nil {
			missed := s.GetMissed(lastID)
			fmt.Printf("[Seamless Resume] Replaying %d events starting after ID %d\n", len(missed), lastID)
			for _, item := range missed {
				fmt.Fprintf(w, "id: %d\nevent: %s\ndata: %s\n\n", item.ID, item.EventName, item.Payload)
			}
			_ = rc.Flush()
		}
	}

	ticker := time.NewTicker(2 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			return
		case t := <-ticker.C:
			item := s.Publish("tick", fmt.Sprintf("Time: %s", t.Format("15:04:05")))
			if _, err := fmt.Fprintf(w, "id: %d\nevent: %s\ndata: %s\n\n", item.ID, item.EventName, item.Payload); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	server := NewResilientServer()
	http.Handle("/seamless-stream", server)

	fmt.Println("Seamless Reconnect SSE server running on :8080/seamless-stream")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сквозная реализация протокола возобновления сессий Last-Event-ID

## Под капотом

Алгоритм W3C SSE гарантирует, что браузер никогда не откатывает значение `lastEventId` назад. Если соединение прерывается многократно, браузер всегда передает максимальный подтвержденный ID, исключая повторную отправку дубликатов сообщений.

## Подводные камни

Отсутствие ограничения размера буфера истории в оперативной памяти. При непрерывной работе сервер заполнит всю RAM массивом `history`. В продакшене используйте циклический буфер с фиксацией максимального числа записей либо храните историю в Redis Stream с параметром `MAXLEN ~ 10000`.

## На собеседовании

В Яндекс, Авито и Wildberries на финальных архитектурных собеседованиях любят подводить итог темы: 'Какие 3 главных правила проектирования надежной SSE платформы в продакшене?' Ответ: 1) Обязательный Flush и правильные заголовки (X-Accel-Buffering, no-cache). 2) Контроль жизненного цикла через r.Context().Done() и неблокирующий Fan-Out с дропом медленных клиентов. 3) Поддержка Last-Event-ID и периодический Keep-Alive пинг для защиты от таймаутов сетевых балансировщиков.
