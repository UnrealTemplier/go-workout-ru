# Управление жизненным циклом и предотвращение утечек горутин через Context

## Условие

66. **[Отмена контекста]**: Клент закрыл вкладку. Используй `ctx := r.Context()`. Запусти цикл `select { case <-ctx.Done(): return; case msg := <-ch: ... }`. Убедись, что серверная горутина завершается и не течет.

### Исходная формулировка

**[Отмена контекста]**: Клент закрыл вкладку. Используй `ctx := r.Context()`. Запусти цикл `select { case <-ctx.Done(): return; case msg := <-ch: ... }`. Убедись, что серверная горутина завершается и не течет.

## Теория

Утечка горутин (Goroutine Leak) — критическая уязвимость в сервисах реального времени на Go.
Когда пользователь закрывает вкладку браузера:
1. Браузер отправляет TCP FIN пакет.
2. Сокет переходит в закрытое состояние.
3. Рантайм Go закрывает канал `r.Context().Done()`.

Если обработчик слушает входящий канал данных без проверки контекста:
```go
for msg := range clientCh { // ОПАСНО: зависнет навсегда при отсутствии сообщений!
    fmt.Fprintf(w, "data: %s\n\n", msg)
}
```
Горутина останется висеть в памяти, продолжая удерживать канал, буферы и стек. При миллионе визитов сервер быстро упадет с Out of Memory (OOM).

Идиоматический паттерн Go:
```go
for {
    select {
    case <-ctx.Done():
        return // Чистый выход и вызов всех defer
    case msg := <-clientCh:
        // отправка
    }
}
```

## Решение по шагам

1. Получите контекст запроса `ctx := r.Context()`.
2. Добавьте `defer` блок для логирования и освобождения ресурсов.
3. Используйте `select` с ветками `case <-ctx.Done():` и `case msg := <-ch:`.
4. Проверьте корректное завершение горутины при обрыве клиента через `curl` (Ctrl+C).

## Код решения

**`leak_proof.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"runtime"
	"time"
)

func safeStreamHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)
	ctx := r.Context()

	clientCh := make(chan string, 10)

	// Регистрируем вход и выход горутины
	fmt.Printf("[+] Handler started. Active Goroutines: %d\n", runtime.NumGoroutine())
	defer func() {
		fmt.Printf("[-] Handler exited cleanly. Remaining Goroutines: %d\n", runtime.NumGoroutine())
	}()

	// Фоновый поставщик данных
	go func() {
		for i := 1; i <= 100; i++ {
			select {
			case <-ctx.Done():
				return // Останавливаем фонового поставщика при отключении клиента
			case clientCh <- fmt.Sprintf("Event #%d", i):
				time.Sleep(1 * time.Second)
			}
		}
	}()

	for {
		select {
		case <-ctx.Done():
			// Клиент закрыл вкладку браузера или curl был прерван
			return

		case msg := <-clientCh:
			if _, err := fmt.Fprintf(w, "data: %s\n\n", msg); err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/safe-stream", safeStreamHandler)
	fmt.Println("Leak-proof SSE server running on :8080/safe-stream")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Контроль контекста r.Context().Done() для гарантированного завершения горутины

## Под капотом

В недрах `net/http` горутина чтения сокета вызывает `cancelCtx()` при получении сетевой ошибки или EOF. Это переводит каналы `Done()` всех дочерних контекстов в закрытое состояние, пробуждая все горутины, заблокированные в операциях `select`.

## Подводные камни

Создание дочерних горутин внутри хэндлера без передачи `ctx`. Если дочерняя горутина обращается к ресурсам запроса и не слушает `<-ctx.Done()`, она продолжит работу в фоне как зомби-горутина.

## На собеседовании

В Авито и Т-Банке часто дают практическую задачу на код-ревью с вопросом: 'Найдите утечку памяти в этом SSE-сервисе'. Практически всегда ошибка кроется в бесконечном цикле `range ch` без контроля `ctx.Done()`, либо в `time.Sleep()` без прерывания по контексту.
