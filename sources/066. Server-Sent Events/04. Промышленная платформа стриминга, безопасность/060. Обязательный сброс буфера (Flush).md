# Обязательный сброс буфера (Flush) для предотвращения задержек в reverse proxies

## Условие

60. **http.Flusher**: После каждой записи вызывайте `flusher.Flush()`. Без этого reverse proxies и буферы Go будут задерживать события.

### Исходная формулировка

**http.Flusher**: После каждой записи вызывайте `flusher.Flush()`. Без этого reverse proxies и буферы Go будут задерживать события.

## Теория

Природа сетевой буферизации:
1. `net/http` в Go использует буфер размером 4096 байт перед сокетом.
2. Обратные прокси-серверы (Nginx, Envoy, HAProxy) также имеют входные и выходные буферы (от 4 КБ до 64 КБ).
3. Если сервер Go записал `data: {"status":"ok"}\n\n` (30 байт) и НЕ вызвал `Flush()`:
   - Байты остаются в оперативной памяти Go.
   - Клиент не получит ничего в течение минут или часов, пока суммарный объем данных не достигнет 4096 байт.
   - Пользовательский опыт (UX) реального времени полностью разрушается.

Вызов `http.Flusher.Flush()` гарантирует, что данные немедленно покидают адресное пространство процесса Go и передаются в TCP-стек операционной системы.

## Решение по шагам

1. Получите объект сброса буфера через `http.Flusher` или `http.NewResponseController`.
2. Запишите сформированное событие в `w`.
3. Немедленно вызовите `Flush()`.
4. Проверьте поведение с помощью `curl -N -v`.

## Код решения

**`flusher_demo.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func strictFlushHandler(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")
	w.Header().Set("X-Accel-Buffering", "no") // Отключение буферизации Nginx

	for i := 1; i <= 3; i++ {
		// Записываем короткое сообщение
		fmt.Fprintf(w, "id: %d\ndata: Progress step %d of 3\n\n", i, i)

		// КРИТИЧЕСКИ ВАЖНО: немедленный сброс буфера в сеть
		flusher.Flush()

		time.Sleep(1 * time.Second)
	}
}

func main() {
	http.HandleFunc("/flush-demo", strictFlushHandler)
	fmt.Println("Flush demonstration server running on :8080/flush-demo")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Обязательный вызов flusher.Flush() после каждого сформированного кадра

## Под капотом

Внутри метода `Flush()` стандартного пакета Go `net/http/server.go`:
```go
func (w *response) Flush() {
    w.w.Flush()
    w.conn.bufw.Flush()
}
```
Сначала сбрасывается буфер упаковщика чанков `chunkWriter`, затем сбрасывается нижележащий сетевой буфер `bufio.Writer`, вызывая запись в сокет ядра Linux.

## Подводные камни

Вызов `flusher.Flush()` без проверки успешности предыдущей записи. Если клиент уже отключился, `Flush()` может скрыть ошибку или вызвать ненужные системные вызовы. В Go 1.20+ предпочтительнее использовать `rc := http.NewResponseController(w)` и проверять ошибку `rc.Flush()`.

## На собеседовании

В Ozon на собеседовании по Go любят спрашивать: 'Почему при использовании http.Flusher в связке с gzip middleware события перестают приходить в реальном времени?' Ответ: стандартный `gzip.Writer` накапливает данные блоками для оптимизации алгоритма сжатия Deflate. Для потокового сжатия в SSE необходимо вызывать метод `gzipWriter.Flush()` перед вызовом `http.Flusher.Flush()`!
