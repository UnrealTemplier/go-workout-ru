# Отправка комментариев для поддержания соединения (Keep-Alive Comments)

## Условие

63. **Comments для keep-alive**: Отправляйте `: ping\n\n` (строки с `:` в начале — это комментарии, игнорируются клиентом) каждые 15-30 секунд для поддержания connection через proxies с idle timeout.

### Исходная формулировка

**Comments для keep-alive**: Отправляйте `: ping\n\n` (строки с `:` в начале — это комментарии, игнорируются клиентом) каждые 15-30 секунд для поддержания connection через proxies с idle timeout.

## Теория

Согласно разделу 9.2.6 спецификации W3C SSE, любая строка, первый символ которой является двоеточием `:`, должна игнорироваться парсером клиента как комментарий:
`: ping\n\n`
или
`: keep-alive\n\n`

Преимущества использования комментариев для Keep-Alive:
1. **Нулевой оверхед на фронтенде:** Браузерный движок не создает объектов `MessageEvent`, не расходует память кучи V8 и не нагружает обработчики `onmessage`.
2. **Сброс Idle-таймаутов:** Сетевые файрволы, NAT-роутеры и пограничные прокси видят реальную передачу TCP-пакетов и не закрывают сокет по неактивности.
3. **Обнаружение 'мертвых' клиентов:** Если попытка отправки комментария завершается системной ошибкой `write: broken pipe`, сервер немедленно узнает о разрыве соединения и освобождает горутину.

## Решение по шагам

1. Создайте HTTP-обработчик SSE.
2. Запустите периодический тикер с интервалом 20 секунд.
3. В цикле отправляйте строку `: ping\n\n`.
4. Обязательно вызывайте `Flush()` после записи.
5. Проверяйте ошибку записи для своевременного выхода.

## Код решения

**`comment_ping.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func commentPingHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)

	// Тикер пинга раз в 15 секунд
	pingTicker := time.NewTicker(15 * time.Second)
	defer pingTicker.Stop()

	// Бизнес-события
	dataTicker := time.NewTicker(40 * time.Second)
	defer dataTicker.Stop()

	for {
		select {
		case <-r.Context().Done():
			return

		case <-pingTicker.C:
			// Комментарий стандарта SSE: начинается с двоеточия
			_, err := fmt.Fprintf(w, ": ping %d\n\n", time.Now().Unix())
			if err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}

		case t := <-dataTicker.C:
			_, err := fmt.Fprintf(w, "data: Update at %s\n\n", t.Format("15:04:05"))
			if err != nil {
				return
			}
			if err := rc.Flush(); err != nil {
				return
			}
		}
	}
}

func main() {
	http.HandleFunc("/comments", commentPingHandler)
	fmt.Println("Comment keep-alive server running on :8080/comments")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Отправка комментариев : ping для удержания TCP-сокета без влияния на клиентский код

## Под капотом

В парсере EventSource спецификации WHATWG HTML:
Если первая графема строки равна U+003A COLON (`:`), то строка считается комментарием и шаг сбора полей (event, data, id) пропускается. Данные отбрасываются до следующего перевода строки.

## Подводные камни

Отправка комментария без префикса `:` или с пробелом перед двоеточием (` : ping`). В таком случае парсер посчитает строку поврежденным именем поля, что может привести к непредсказуемому поведению клиента.

## На собеседовании

В Ozon и Авито часто спрашивают: 'Что лучше использовать для проверки живости соединения: TCP Keepalive на уровне сокета или прикладной комментарий SSE?' Ответ: оба механизма дополняют друг друга. TCP Keepalive работает на уровне L4 и не проходит через HTTP прокси (прокси завершает TCP сессию на себе). Прикладной SSE комментарий работает на L7 и прозрачно проходит через всю цепочку прокси вплоть до браузера.
