# Плавная ротация токенов в долгоживущих SSE-сессиях (Token Refresh)

## Условие

55. **SSE token refresh**: SSE connection может жить часами. Реализуйте graceful token refresh: отправьте событие "reconnect with new token" перед expiration.

### Исходная формулировка

**SSE token refresh**: SSE connection может жить часами. Реализуйте graceful token refresh: отправьте событие "reconnect with new token" перед expiration.

## Теория

Короткоживущие JWT токены (обычно со сроком жизни 15-30 минут) создают сложность для постоянных SSE-соединений:
- Если соединение живет 4 часа, исходный токен аутентификации протухает через 15 минут.
- Если сервер разорвет сокет внезапно с ошибкой 401, клиент испытает сетевой сбой.

Паттерн Graceful SSE Token Refresh:
1. Сервер знает точное время истечения токена (`claims.ExpiresAt`).
2. За 60 секунд до истечения токена фоновый таймер соединения отправляет специальное событие:
   ```http
   event: token_expiring
   data: {"expires_in_sec": 60, "action": "refresh_and_reconnect"}
   
   ```
3. Клиент на фронтенде в фоновом режиме делает POST-запрос к эндпоинту `/api/auth/refresh`, получает свежий JWT токен и плавно переподключает SSE-стрим с новым токеном без потери сообщений.

## Решение по шагам

1. Извлеките время жизни токена `exp` при установлении соединения.
2. Рассчитайте момент предупреждения: `time.Until(exp) - 60*time.Second`.
3. Запустите таймер `time.AfterFunc` или ветку в `select`.
4. Отправьте событие `event: token_expiring` с рекомендацией обновить токен.
5. Завершите соединение только при фактическом наступлении срока экспирации.

## Код решения

**`token_refresh_server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func expiringSSEHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	rc := http.NewResponseController(w)

	// Имитация: токен истекает через 10 секунд
	tokenTTL := 10 * time.Second
	warnBefore := 3 * time.Second

	warnTimer := time.NewTimer(tokenTTL - warnBefore)
	defer warnTimer.Stop()

	expireTimer := time.NewTimer(tokenTTL)
	defer expireTimer.Stop()

	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			return

		case <-warnTimer.C:
			// Предупреждение клиенту о скором истечении сессии
			fmt.Println("[Auth] Token expiring soon. Warning client...")
			fmt.Fprintf(w, "event: token_expiring\ndata: {\"expires_in_ms\": %d}\n\n", warnBefore.Milliseconds())
			_ = rc.Flush()

		case <-expireTimer.C:
			// Принудительное закрытие сессии после истечения
			fmt.Println("[Auth] Token expired. Closing connection.")
			fmt.Fprintf(w, "event: token_expired\ndata: {\"status\": \"unauthorized\"}\n\n")
			_ = rc.Flush()
			return

		case t := <-ticker.C:
			fmt.Fprintf(w, "data: normal tick %s\n\n", t.Format("15:04:05"))
			_ = rc.Flush()
		}
	}
}

func main() {
	http.HandleFunc("/expiring-stream", expiringSSEHandler)
	fmt.Println("Expiring token SSE server listening on :8080/expiring-stream")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Предупреждение клиента о скором истечении токена с таймером плавной ротации

## Под капотом

Отправка события `token_expiring` позволяет фронтенду использовать стандартный браузерный механизм Seamless Switch: фронтенд открывает новый экземпляр `EventSource` со свежим токеном, дожидается успешного события `onopen`, и только после этого вызывает `.close()` у старого `EventSource`, обеспечивая непрерывность поступления данных без видимых задержек для пользователя.

## Подводные камни

Жесткий разрыв соединения сервером сразу по истечении токена без предупреждающего события. Браузерный `EventSource` со старым URL попытается повторно подключиться со старым просроченным токеном, получит 401 и полностью остановит реконнекты (`readyState = CLOSED`).

## На собеседовании

В Ozon и Авито часто спрашивают: 'Как обновлять авторизацию в SSE без разрыва текущего TCP-соединения?' Ответ: если на клиенте используется кастомный клиент на базе fetch/ReadableStream, можно послать POST /refresh токена параллельно, а в сокет SSE отправить клиентское управляющее сообщение через другой HTTP-канал, обновляя claims в контексте активной сессии сервера через Redis/ин-мемори состояние.
