# Сравнительный бенчмаркинг накладных расходов: SSE против WebSocket

## Условие

64. **SSE vs WebSocket benchmark**: Сравните overhead: SSE использует стандартный HTTP (работает через corporate proxies, CDN), WebSocket требует отдельного protocol upgrade. SSE идеален для server→client streaming.

### Исходная формулировка

**SSE vs WebSocket benchmark**: Сравните overhead: SSE использует стандартный HTTP (работает через corporate proxies, CDN), WebSocket требует отдельного protocol upgrade. SSE идеален для server→client streaming.

## Теория

При проектировании микросервисов важно понимать точные накладные расходы протоколов:

1. **Установление соединения (Handshake):**
   - **SSE:** Стандартный HTTP/1.1 или HTTP/2 GET-запрос (0 дополнительных сетевых RTT при существующем пуле соединений HTTP/2).
   - **WebSocket:** Требует обязательного HTTP Upgrade (101 Switching Protocols) поверх нового TCP-соединения, что добавляет минимум 1 полный сетевой RTT.
2. **Память на соединение (Memory per Connection):**
   - В Go одна горутина занимает от 2 КБ до 4 КБ стека.
   - SSE требует 1 горутину на клиента (чтение из канала и запись в сокет).
   - WebSocket в классической реализации требует 2 горутины на соединение (одну на чтение `ReadMessage`, другую на запись `WriteMessage`), удваивая потребление оперативной памяти!
3. **Кадрирование (Framing Overhead):**
   - **SSE:** Текстовый заголовок `data: ` (6 байт) + `\n\n` (2 байта). Идеально сжимается в gzip/br.
   - **WebSocket:** Бинарный заголовок от 2 до 10 байт на фрейм (плюс 4 байта маскировки от клиента).

## Решение по шагам

1. Напишите сравнительный тест потребления памяти для 10 000 SSE и WebSocket соединений.
2. Измерьте количество горутин с помощью `runtime.NumGoroutine()`.
3. Зафиксируйте статистику памяти через `runtime.ReadMemStats()`.
4. Сделайте инженерные выводы по выбору архитектуры.

## Код решения

**`benchmark_test.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"testing"
	"time"
)

func BenchmarkConnectionOverhead(b *testing.B) {
	var m1, m2 runtime.MemStats

	runtime.GC()
	runtime.ReadMemStats(&m1)
	initialGoroutines := runtime.NumGoroutine()

	conns := 10000
	channels := make([]chan []byte, conns)

	// Эмулируем 10 000 легких SSE клиентов (1 канал + горутина ожидания)
	for i := 0; i < conns; i++ {
		channels[i] = make(chan []byte, 1)
		go func(ch chan []byte) {
			for range ch {
			}
		}(channels[i])
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("[Benchmark 10k SSE Conns]\n")
	fmt.Printf("Allocated Memory: %.2f MB\n", float64(m2.Alloc-m1.Alloc)/(1024*1024))
	fmt.Printf("Spawned Goroutines: %d\n", runtime.NumGoroutine()-initialGoroutines)

	// Очистка
	for _, ch := range channels {
		close(ch)
	}
	time.Sleep(100 * time.Millisecond)
}
```

ℹ️ Бенчмарк накладных расходов памяти и горутин на 10 000 параллельных сессий

## Под капотом

Стек горутины в Go 1.22+ начинается с 2 КБ. При росте нагрузки стек динамически увеличивается (копируется в новый непрерывный блок памяти кучи). Для 10 000 SSE-клиентов базовый расход памяти составляет около 25-30 МБ, что позволяет легко удерживать миллион соединений на одном стандартном сервере с 32 ГБ RAM.

## Подводные камни

Выбор WebSocket исключительно 'на всякий случай' для чисто однонаправленных потоков (уведомления, котировки). Это влечет необходимость настройки sticky sessions в Ingress, проблемы с кэшированием CDN и усложнение мониторинга.

## На собеседовании

В Wildberries на архитектурной секции часто спрашивают: 'Во сколько раз больше ресурсов требует 1 000 000 соединений WebSocket по сравнению с SSE поверх HTTP/2?' Ответ: В HTTP/2 миллион стримов может быть распределен по значительно меньшему числу TCP-сокетов с мультиплексированием, тогда как WebSocket требует миллион полноценных TCP-сокетов ОС, что упирается в память TCP-буферов ядра Linux (`tcp_rmem`/`tcp_wmem`).
