# Просмотр промежуточного представления SSA и оптимизаций

## Условие

**Просмотр SSA и Оптимизаций компилятора**: Компилятор Go преобразует твой код в SSA (Static Single Assignment) форму, прежде чем сделать машинный код, выполняя десятки проходов (оптимизаций). Напиши функцию с бесполезным кодом (dead code). Запусти компиляцию: `GOSSAFUNC=main go build`. Открой сгенерированный `ssa.html` в браузере. Проследи по вкладкам, на каком этапе компилятор удалил твой мертвый код (Pass: deadcode).

## Теория

Компилятор Go (`cmd/compile`) при преобразовании синтаксического дерева (AST) в машинный код использует SSA (Static Single Assignment) — форму промежуточного представления, где каждая переменная присваивается ровно один раз.

В процессе компиляции выполняется более 40 последовательных оптимизационных проходов (SSA Passes):
- `early deadcode` / `deadcode`: удаление недостижимых инструкций и неиспользуемых вычислений.
- `opt`: свертка констант (constant folding), замена деления на сдвиги.
- `nilcheck`: удаление избыточных проверок указателей на `nil`.
- `prove` / `bce`: удаление проверок выхода за границы срезов (Bounds Check Elimination).
- `regalloc`: распределение физических регистров процессора.

Флаг `GOSSAFUNC=<func_name>` заставляет компилятор сгенерировать интерактивный HTML-файл `ssa.html`, где показан код после каждого прохода.

## Решение по шагам

1. Создайте файл `main.go` с функцией `main`, содержащей очевидный мертвый код (dead code).
2. Запустите сборку с переменной окружения `GOSSAFUNC=main go build`.
3. Убедитесь в создании файла `ssa.html`.
4. Изучите этапы трансформации SSA формы.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func main() {
	x := 10
	y := 20
	sum := x + y

	// Мертвый код (dead code): ветка никогда не выполнится
	if false {
		fmt.Println("Этот код компилятор полностью вырежет на фазе deadcode!")
		deadVar := 999 * x
		_ = deadVar
	}

	fmt.Printf("Результат: %d\n", sum)
}
```

ℹ️ Исходный код с заведомо недостижимой веткой выполнения

**`Терминал`**

```bash
# Запуск компиляции с экспортом проходов SSA для функции main
GOSSAFUNC=main go build -o app main.go
ls -lh ssa.html
```

## Под капотом

В начале SSA генерации строится базовый граф потока управления (Control Flow Graph, CFG).
На проходе `opt` компилятор замечает, что условие `if false` константно. Условный переход превращается в безусловный переход на ветку после блока `if`.
На проходе `deadcode` компилятор находит блоки CFG, у которых нет входящих ребер (unreachable blocks), и вычищает их вместе со всеми содержащимися в них операциями и Phi-узлами, гарантируя нулевой оверхед в итоговом бинарнике.

## Подводные камни

1. Файл `ssa.html` для крупных функций может весить десятки мегабайт и сильно нагружать браузер при рендеринге. Всегда исследуйте компактные функции.
2. Если имя функции содержит пакет (например, `(*MyType).Method`), передавайте имя в точности так, как его ожидает компилятор: `GOSSAFUNC="(*MyType).Method" go build`.

## На собеседовании

**Вопрос с собеседования:** Что такое форма SSA и почему современные компиляторы (Go, LLVM, GCC) оптимизируют код именно в ней, а не в исходном AST?
**Ответ:** В SSA форме каждая переменная определяется ровно один раз, что превращает зависимости по данным в направленный ациклический граф (DAG). Это делает тривиальными и линейными по сложности такие алгоритмы, как свертка констант (constant folding), распространение копий (copy propagation), вынос инвариантов из циклов (LICM) и удаление мертвого кода (DCE), которые в обычном графе переприсваиваемых переменных требовали бы сложнейшего анализа потоков данных.
