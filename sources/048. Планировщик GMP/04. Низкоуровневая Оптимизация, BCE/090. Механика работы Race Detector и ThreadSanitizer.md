# Механика работы Race Detector и ThreadSanitizer

## Условие

**Race detector internals**: Изучите, как `-race` флаг инструментует код для обнаружения data races (через ThreadSanitizer). Оцените overhead (~10x slowdown, 5-10x memory).

## Теория

Флаг `-race` включает в скомпилированный бинарник детектор состояния гонки данных, основанный на библиотеке ThreadSanitizer (TSan) от Google.

Как это работает:
1. Компилятор заменяет каждое обращение к разделяемой памяти на вызовы хуков TSan: `runtime.raceread` и `runtime.racewrite`.
2. Для каждых 8 байт пользовательской памяти TSan выделяет в 4–8 раз больше так называемой «теневой памяти» (Shadow Memory).
3. В теневой памяти сохраняются: ID горутины, векторные часы (Vector Clocks) и тип доступа (чтение/запись).
4. Если два потока обращаются к одной ячейке памяти без отношения «happens-before» и хотя бы одно обращение — запись, TSan мгновенно печатает подробнейший отчет о Data Race с обоими стектрейсами.

## Решение по шагам

1. Напишите код с намеренной гонкой данных между двумя горутинами.
2. Скомпилируйте и запустите программу с флагом `-race`.
3. Проанализируйте отчет детектора гонок и исправьте ошибку атомиком или мьютексом.

## Код решения

**`race_demo.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var counter int
	var wg sync.WaitGroup

	// Две горутины пишут в одну переменную без синхронизации
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 1000; j++ {
				counter++ // Состояние гонки (Data Race)!
			}
		}(i)
	}

	wg.Wait()
	fmt.Printf("Итоговое значение: %d\n", counter)
}
```

ℹ️ Классическое состояние гонки данных (Data Race)

**`Терминал`**

```bash
go run -race race_demo.go
```

## Под капотом

Сборка с `-race` кардинально меняет бинарный код:
- Каждое чтение/запись инструментируется: `CALL runtime.raceread(SB)`.
- Расход оперативной памяти увеличивается в **5–10 раз** из-за отображения теневой памяти (`mmap` гигантских диапазонов виртуальных адресов).
- Время выполнения замедляется в **2–10 раз** из-за непрерывного обновления теневых меток и проверки векторных часов при каждом доступе к памяти.

## Подводные камни

1. Категорически запрещено выкатывать бинарники с флагом `-race` под 100% боевую нагрузку в production из-за падения RPS и риска OOM.
2. Race detector находит гонки данных только на тех путях выполнения, которые **фактически выполнились** во время прогона тестов. Непротестированные ветки кода не проверяются!
3. Для отлова редких гонок тесты запускают с флагами `go test -race -count=100 -cpu=4`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между понятиями «Data Race» (гонка данных) и «Race Condition» (состояние гонки бизнес-логики)? Находит ли `-race` обе проблемы?
**Ответ:** 
- **Data Race:** одновременный доступ двух потоков к одной ячейке памяти без синхронизации, где минимум один пишет. Это баг уровня памяти (Undefined Behavior в C, гарантированный детект в Go). Флаг `-race` ищет **только Data Race**.
- **Race Condition:** логическая ошибка последовательности операций (например, проверка баланса и снятие денег происходят под разными транзакциями). Код может быть идеально защищен мьютексами (Data Race = 0), но бизнес-логика сломается. Race Condition ищется интеграционными тестами.
