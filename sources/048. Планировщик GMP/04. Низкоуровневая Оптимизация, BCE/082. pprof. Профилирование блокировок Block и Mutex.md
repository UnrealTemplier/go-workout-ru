# pprof: Профилирование блокировок Block и Mutex

## Условие

**pprof: Block и Mutex профилирование**: Напиши код с множеством горутин и узким местом (один глобальный `sync.Mutex`, который долго держится залоченным). Собери block и mutex профили. Покажи, как в `go tool pprof` найти строку, на которой горутины ждут дольше всего.

### Исходная формулировка

**pprof: Block и Mutex профилирование**: Напиши код с множеством горутин и узким местом (один глобальный `sync.Mutex`, который долго держится залоченным). Включи `runtime.SetBlockProfileRate(1)` и `runtime.SetMutexProfileFraction(1)`. Открой профили в браузере через `go tool pprof`. Узнай точную строчку кода, где горутины стоят в очереди за мьютексом.

## Теория

Профилирование блокировок — ключевой навык при оптимизации многопоточных Go-сервисов в HighLoad.
- **Mutex profile:** показывает задержки, возникающие из-за конкуренции за `sync.Mutex` и `sync.RWMutex`.
- **Block profile:** показывает задержки, возникающие на каналах (отправка в полный канал, чтение из пустого), ожиданиях в `select`, системных вызовах и сетевых операциях.

Для сбора этих профилей в рантайме включаются:
- `runtime.SetBlockProfileRate(rate)` — замеряет события блокировки длительностью больше `rate` наносекунд (1 = все события).
- `runtime.SetMutexProfileFraction(fraction)` — фиксирует 1 из `fraction` событий contention (1 = 100%).

## Решение по шагам

1. Включите сбор блок- и мьютекс-профилей через соответствующие runtime функции.
2. Смоделируйте конкурентную нагрузку с узким местом (бутылочным горлышком) на глобальном `sync.Mutex`.
3. Сохраните профили в файлы `block.pprof` и `mutex.pprof`.
4. Запустите анализ через `go tool pprof -text` и определите проблемную строку кода.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
	"sync"
	"time"
)

var (
	globalLock sync.Mutex
	sharedData int
)

// Функция с намеренно длительным удержанием мьютекса
func heavyCriticalSection() {
	globalLock.Lock()
	defer globalLock.Unlock()

	sharedData++
	// Имитируем тяжелую операцию под замком
	time.Sleep(2 * time.Millisecond)
}

func main() {
	// Включаем 100% сбор обоих профилей
	runtime.SetBlockProfileRate(1)
	runtime.SetMutexProfileFraction(1)

	const workers = 10
	var wg sync.WaitGroup
	wg.Add(workers)

	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			for j := 0; j < 10; j++ {
				heavyCriticalSection()
			}
		}()
	}

	wg.Wait()

	// Сохраняем mutex profile
	fMut, err := os.Create("mutex.pprof")
	if err != nil {
		panic(err)
	}
	defer fMut.Close()
	_ = pprof.Lookup("mutex").WriteTo(fMut, 0)

	// Сохраняем block profile
	fBlk, err := os.Create("block.pprof")
	if err != nil {
		panic(err)
	}
	defer fBlk.Close()
	_ = pprof.Lookup("block").WriteTo(fBlk, 0)

	fmt.Println("Профили успешно записаны: mutex.pprof и block.pprof")
}
```

ℹ️ Генерация и экспорт block и mutex профилей

**`Терминал`**

```bash
go run main.go
go tool pprof -top -cum mutex.pprof
go tool pprof -top -cum block.pprof
```

## Под капотом

При вызове `pprof.Lookup("mutex").WriteTo(w, 0)` рантайм формирует proto-буфер со списком записей профиля.
Каждая запись содержит:
1. `stack`: массив адресов инструкций PC на момент блокировки.
2. `cycles`: общее количество процессорных тактов или наносекунд, проведенных в ожидании.
3. `count`: количество раз, когда горутина заблокировалась на этой строке кода.
Команда `pprof -top` сопоставляет адреса PC с таблицей символов DWARF в скомпилированном бинарнике и точно указывает имя функции и номер строки файла.

## Подводные камни

1. Включение `SetBlockProfileRate(1)` на production-сервере под 50k RPS приведет к катастрофической деградации производительности из-за накладных расходов на снятие стектрейсов на каждый сетевой пакет. Рекомендуется ставить значение от 10000 (10 микросекунд) или 100000.
2. `pprof.Lookup("block")` агрегирует данные накопительным итогом с момента старта процесса. Для получения картины за последние 30 секунд в HTTP pprof используют эндпоинт `/debug/pprof/block?seconds=30`.

## На собеседовании

**Вопрос с собеседования:** В выводе `go tool pprof` для мьютексов вы видите метрики `contentions` и `delay`. В чем их различие и на какую обращать внимание в первую очередь?
**Ответ:** 
- `contentions`: общее количество фактов конфликтов (сколько раз горутина при вызове `Lock()` обнаружила мьютекс занятым и уснула).
- `delay`: суммарное время ожидания горутин в очереди.
Обращать внимание нужно на обе метрики в комплексе: если `contentions` мало, но `delay` огромный — один мьютекс держится слишком долго (например, в нем делают сетевой запрос). Если `contentions` огромный, а `delay` умеренный — слишком много горутин долбятся в одну критическую секцию (требуется шардирование мьютексов или lock-free).
