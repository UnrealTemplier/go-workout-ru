# Финалайзеры, утечки памяти и runtime.KeepAlive

## Условие

**Финалайзеры (Утечки памяти и Воскрешение)**: В Go нельзя явно удалить объект, но можно повесить хук на момент его уничтожения сборщиком мусора. Напишите пример с `runtime.SetFinalizer`, воскрешением объекта и покажите роль `runtime.KeepAlive`.

### Исходная формулировка

**Финалайзеры (Утечки памяти и Воскрешение)**: В Go нельзя явно удалить объект, но можно повесить хук на момент его уничтожения сборщиком мусора. Напиши объект `type Zombie struct{}`. Повесь на него `runtime.SetFinalizer(z, func(z *Zombie) { fmt.Println("Умираю!") })`. Обязательно убери все ссылки на этот объект и вызови `runtime.GC()`. *Внимание:* в финалайзере ты можешь сохранить указатель на этот объект в глобальную переменную — и GC его не удалит (Объект "воскреснет" из мертвых)!

## Теория

Функция `runtime.SetFinalizer(obj, finalizerFunc)` регистрирует функцию-деструктор, которая будет вызвана сборщиком мусора после того, как `obj` станет недостижим в графе объектов.

Финалайзеры таят в себе колоссальные опасности:
1. **Воскрешение объекта (Object Resurrection):** если финалайзер сохраняет указатель на объект в глобальную переменную, объект снова становится достижимым и «воскресает»!
2. **Преждевременное выполнение:** оптимизатор компилятора может решить, что объект больше не используется в функции до ее завершения, и GC вызовет финалайзер прямо во время работы методов объекта.
Для защиты от преждевременного уничтожения используется `runtime.KeepAlive(x)`.

## Решение по шагам

1. Создайте структуру ресурса (например, файловый дескриптор или сокет).
2. Навесьте финалайзер через `runtime.SetFinalizer`.
3. Продемонстрируйте проблему преждевременного вызова финалайзера.
4. Исправьте ошибку с помощью явного вызова `runtime.KeepAlive`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type Resource struct {
	id     int
	closed bool
}

func newResource(id int) *Resource {
	r := &Resource{id: id}
	// Регистрируем финалайзер
	runtime.SetFinalizer(r, func(res *Resource) {
		fmt.Printf("[Finalizer] Ресурс %d освобожден сборщиком мусора!\n", res.id)
		res.closed = true
	})
	return r
}

func doWork() {
	res := newResource(42)
	fmt.Printf("Используем ресурс %d...\n", res.id)

	// Имитируем долгие вычисления
	// Без runtime.KeepAlive компилятор может считать res недостижимым
	// прямо во время sleep, и GC вызовет финалайзер раньше времени!
	time.Sleep(50 * time.Millisecond)

	// Гарантируем, что res жив до этой точки:
	runtime.KeepAlive(res)
}

func main() {
	doWork()

	// Принудительно вызываем GC для срабатывания финалайзера
	runtime.GC()
	// Даем время горутине runfinq выполнить финалайзер
	time.Sleep(100 * time.Millisecond)

	fmt.Println("Программа завершена.")
}
```

ℹ️ Использование SetFinalizer и защита объекта через runtime.KeepAlive

**`Терминал`**

```bash
go run main.go
```

## Под капотом

Когда объект с финалайзером становится недостижимым во время фазы GC Mark, он не освобождается немедленно!
GC помещает его в специальную очередь финалайзеров. Специальная выделенная горутина рантайма (`runfinq`) поочередно извлекает объекты из очереди и запускает пользовательские колбэки.
Сам объект будет освобожден только на **следующем** цикле сборки мусора (задержка минимум в 1 цикл GC).

Инструкция `runtime.KeepAlive(x)` транслируется компилятором в пустую ассемблерную псевдо-инструкцию, продлевая время жизни переменной (liveness) в графе SSA до точки вызова.

## Подводные камни

1. Если два объекта ссылаются друг на друга по кругу и у обоих есть финалайзеры, GC не сможет определить порядок их вызова и они никогда не освободятся (утечка памяти).
2. Финалайзер не гарантирует выполнение при аварийном или штатном завершении программы (`os.Exit(0)`).
3. Использование `SetFinalizer` категорически не рекомендуется для закрытия сокетов и файлов в production. Используйте явный `defer Close()`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go категорически запрещено использовать `runtime.SetFinalizer` для автоматического освобождения сетевых соединений и файлов в продакшене?
**Ответ:** Потому что вызов финалайзера недетерминирован во времени: GC может сработать через секунды или минуты при нехватке памяти. За это время исчерпается пул доступных дескрипторов файлов ОС (`too many open files`). Кроме того, горутина `runfinq` одна на весь рантайм: если один финалайзер зависнет на сетевой операции, встанут финалайзеры всех остальных объектов в системе.
