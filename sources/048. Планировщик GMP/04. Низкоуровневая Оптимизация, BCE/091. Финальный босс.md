# Финальный босс: Комплексный аудит производительности рантайма

## Условие

**Финальный босс (Runtime Performance Audit):**
    Проведите полный аудит производительности Go-приложения:
    
    **Scheduling Analysis:**
    * Запишите execution trace через `runtime/trace`.
    * Проанализируйте goroutine states, work stealing patterns, scheduler latency.
    * Проверьте на goroutine leaks через `pprof goroutine`.
    * Оптимизируйте GOMAXPROCS для container environment.
    
    **Memory Analysis:**
    * Снимите heap profile (`inuse_space` и `alloc_space`).
    * Найдите top аллокаторов через flame graphs.
    * Проверьте на memory leaks (рост `HeapAlloc` без GC).
    * Оптимизируйте escape analysis (снижение heap аллокаций).
    * Используйте `sync.Pool` для hot objects.
    * Упорядочьте struct fields для снижения padding.
    
    **GC Tuning:**
    * Проанализируйте GC traces (`GODEBUG=gctrace=1`).
    * Измерьте GC pauses через `MemStats.PauseNs`.
    * Настройте `GOGC` для optimal CPU/memory trade-off.
    * Установите `GOMEMLIMIT` для предотвращения OOM.
    * Рассмотрите `runtime.GC()` для critical points.
    
    **Concurrency Profiling:**
    * Включите block profiler для анализа channel/mutex contention.
    * Используйте mutex profiler для выявления hot locks.
    * Оптимизируйте granularity блокировок.
    * Рассмотрите lock-free алгоритмы для hot paths.
    
    **Benchmarking:**
    * Создайте бенчмарки для critical paths.
    * Используйте `benchstat` для статистического сравнения.
    * Профилируйте CPU через `pprof` в бенчмарках.
    * Измерьте allocations через `-benchmem`.
    
    **Production Monitoring:**
    * Экспортируйте runtime метрики в Prometheus.
    * Настройте алерты на аномалии (goroutine leaks, memory growth, high GC CPU).
    * Используйте continuous profiling (Pyroscope/Parca).

## Теория

«Финальный босс» главы 48 объединяет все полученные знания о рантайме Go в комплексную систему аудита производительности Enterprise-уровня.

Архитектура сквозного аудита охватывает 6 фундаментальных слоев:
1. **Планировщик (GMP):** контроль квантов времени, исключение starvation, настройка CFS quota через `uber-go/automaxprocs`.
2. **Память и Аллокации:** профилирование `alloc_space` vs `inuse_space`, выравнивание полей структур (memory padding), минимизация escape analysis.
3. **Сборщик мусора (GC):** связка `GOGC` и `GOMEMLIMIT` (Go 1.19+) для предотвращения деградации задержек при пиковых нагрузках.
4. **Конкурентность:** профилирование contention мьютексов и каналов через block/mutex pprof.
5. **Бенчмаркинг:** статистический анализ гипотез через `benchstat` (расчет p-value и доверительных интервалов).
6. **Production Observability:** экспорт низкоуровневых метрик `runtime/metrics` в Prometheus и непрерывное профилирование в Pyroscope.

## Решение по шагам

1. Создайте сервис с экспортом pprof и встроенным генератором нагрузки.
2. Реализуйте сбор и анализ метрик рантайма (`runtime/metrics` и `runtime.MemStats`).
3. Настройте корректный `GOMEMLIMIT` и автоматическое конфигурирование `GOMAXPROCS`.
4. Сформируйте итоговый отчет аудита производительности.

## Код решения

**`audit_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	_ "net/http/pprof" // Подключение полного набора pprof эндпоинтов
	"os"
	"os/signal"
	"runtime"
	"runtime/debug"
	"runtime/metrics"
	"sync"
	"syscall"
	"time"
)

// Оптимизированная структура с учетом выравнивания (memory alignment)
type EfficientTask struct {
	Timestamp int64  // 8 байт (offset 0)
	Pointer   *byte  // 8 байт (offset 8)
	ID        uint32 // 4 байта (offset 16)
	Flags     uint8  // 1 байт  (offset 20)
	// Padding: 3 байта, итого размер 24 байта (ровно 3 слова)
}

// Пул горячих объектов для снижения нагрузки на GC
var taskPool = sync.Pool{
	New: func() any {
		return new(EfficientTask)
	},
}

func main() {
	// 1. Установка безопасного Soft Memory Limit (GOMEMLIMIT)
	debug.SetMemoryLimit(256 * 1024 * 1024) // 256 MiB

	// 2. Включаем профилирование блокировок и мьютексов
	runtime.SetBlockProfileRate(10000) // сэмплирование от 10 мкс
	runtime.SetMutexProfileFraction(5) // сэмплирование 20% contention

	// 3. Запуск HTTP сервера диагностики pprof
	go func() {
		fmt.Println("Диагностический pprof эндпоинт запущен на :6060")
		if err := http.ListenAndServe("localhost:6060", nil); err != nil && err != http.ErrServerClosed {
			fmt.Printf("Ошибка pprof сервера: %v\n", err)
		}
	}()

	// 4. Запуск фоновой полезной нагрузки с пулом объектов
	ctx, cancel := context.WithCancel(context.Background())
	var wg sync.WaitGroup

	for i := 0; i < runtime.GOMAXPROCS(0); i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				default:
					t := taskPool.Get().(*EfficientTask)
					t.ID = uint32(workerID)
					t.Timestamp = time.Now().UnixNano()
					// Имитируем быструю обработку
					taskPool.Put(t)
					time.Sleep(10 * time.Microsecond)
				}
			}
		}(i)
	}

	// 5. Опрос метрик рантайма через современный runtime/metrics API
	samples := []metrics.Sample{
		{Name: "/sched/goroutines:goroutines"},
		{Name: "/memory/classes/heap/objects:bytes"},
		{Name: "/gc/pauses:seconds"},
	}

	ticker := time.NewTicker(500 * time.Millisecond)
	defer ticker.Stop()

	sigCh := make(chan os.Signal, 1)
	signal.Notify(sigCh, os.Interrupt, syscall.SIGTERM)

	fmt.Println("Сервис аудита активен. Мониторинг ключевых метрик рантайма:")
	for iter := 0; iter < 4; iter++ {
		select {
		case <-ticker.C:
			metrics.Read(samples)
			fmt.Printf("  [Метрики] Горутин: %d | Heap: %d КБ\n",
				samples[0].Value.Uint64(),
				samples[1].Value.Uint64()/1024)
		case <-sigCh:
			goto shutdown
		}
	}

shutdown:
	cancel()
	wg.Wait()
	fmt.Println("Аудит успешно завершен. Все горутины корректно остановлены.")
}
```

## Под капотом

Пакет `runtime/metrics` считывает внутренние счетчики рантайма с нулевыми аллокациями памяти (Zero Allocations).
Вызов `debug.SetMemoryLimit` (или переменная `GOMEMLIMIT`) модифицирует регулятор триггера GC в файле `mgcpacer.go`.
Если объем памяти приближается к лимиту, контроллер агрессивно снижает целевой коэффициент прироста кучи, заставляя GC срабатывать чаще, но предотвращая аварийное завершение процесса ядром Linux по OOM.

## Подводные камни

1. Выставление `GOMEMLIMIT` впритык к лимиту контейнера (например, 512MB limit при cgroup 512MB) приведет к OOM, так как лимит рантайма учитывает память кучи и стеков Go, но не учитывает память бинарника, Cgo и оверхед ядра ОС. Задавайте лимит с запасом 10–20%.
2. Забытый `_ "net/http/pprof"` без авторизации в публичной сети создает критическую уязвимость безопасности (Remote Code & Memory Exposure).

## На собеседовании

**Вопрос с собеседования:** Спроектируйте стратегию управления памятью и CPU для Go-микросервиса, разворачиваемого в Kubernetes с ресурсами `cpu: 2`, `memory: 1Gi`.
**Ответ:** 
1. **CPU:** подключаем библиотеку `go.uber.org/automaxprocs`, которая считывает квоты Linux CFS (`/sys/fs/cgroup/cpu`) и выставляет `GOMAXPROCS=2`, предотвращая деградацию планировщика от троттлинга.
2. **Память:** выставляем `GOMEMLIMIT=850MiB` (около 85% от лимита контейнера), оставляя 150 МБ под память ОС, стеки потоков ядра и дескрипторы.
3. **GC:** оставляем базовый `GOGC=100`. Благодаря soft limit рантайм сам увеличит частоту GC при приближении к 850 МБ и не допустит убийства пода OOMKilled.
4. **Телеметрия:** непрерывный экспорт `/sched/latencies:seconds` в Prometheus для детекта троттлинга CPU.
