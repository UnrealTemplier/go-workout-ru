# Накладные расходы на создание горутины vs поток ОС

## Условие

**Goroutine creation cost**: Измерьте время создания горутины (~200ns) и сравните с OS thread creation (~1μs).

## Теория

Одним из главных преимуществ Go перед Java, C++ и Python является экстремально дешевое создание горутин.
- **Поток ОС (pthread):** требует системного вызова ядра (`clone` в Linux), выделения стека фиксированного размера (обычно 2–8 МБ), страниц Guard Page для защиты от переполнения стека и структур ядра `task_struct`. Время создания составляет ~10–50 микросекунд (10 000 – 50 000 нс).
- **Горутина Go:** не требует системного вызова, создается в userspace. Рантайм переиспользует дескрипторы `g` из пула `p.gFree`, стек стартует всего с 2 КБ в куче. Время создания составляет ~150–300 наносекунд.

## Решение по шагам

1. Напишите бенчмарк для создания и завершения горутины `go func() {}()`.
2. Напишите измерительный код, запускающий 100 000 горутин и замеряющий суммарное время и память.
3. Проанализируйте скорость выделения горутин в пересчете на единицу времени.

## Код решения

**`cost_test.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"testing"
	"time"
)

// Бенчмарк времени создания горутины
func BenchmarkGoroutineCreate(b *testing.B) {
	var wg sync.WaitGroup
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		wg.Add(1)
		go func() {
			wg.Done()
		}()
		wg.Wait()
	}
}

func main() {
	const count = 100_000
	var wg sync.WaitGroup
	wg.Add(count)

	var memBefore runtime.MemStats
	runtime.ReadMemStats(&memBefore)

	start := time.Now()
	for i := 0; i < count; i++ {
		go func() {
			wg.Done()
		}()
	}
	wg.Wait()
	elapsed := time.Since(start)

	var memAfter runtime.MemStats
	runtime.ReadMemStats(&memAfter)

	fmt.Printf("Запуск %d горутин занял: %v\n", count, elapsed)
	fmt.Printf("Среднее время на 1 горутину: %v\n", elapsed/count)
	fmt.Printf("Дельта памяти: %d КБ (%.2f байт/горутину)\n",
		(memAfter.Sys-memBefore.Sys)/1024,
		float64(memAfter.Sys-memBefore.Sys)/count)
}
```

ℹ️ Бенчмарк и замер накладных расходов на создание горутин

**`Терминал`**

```bash
go run cost_test.go
go test -bench=BenchmarkGoroutineCreate cost_test.go
```

## Под капотом

Функция `runtime.newproc` реализует пул свободных горутин:
1. Проверяет `_p_.gFree.stack`. Если там есть завершившаяся горутина с готовым 2 КБ стеком, она извлекается за несколько процессорных тактов без обращения к аллокатору памяти!
2. Если локальный пул пуст, забирается пачка `g` из глобального `sched.gFree`.
3. Только если пулы пусты, вызывается `malg()` для аллокации нового объекта `g` и 2 КБ стека.
Поэтому создание горутины в Go обходится в десятки раз дешевле, чем даже вызов `malloc()` в C.

## Подводные камни

1. Хотя создание горутины дешево, запуск миллионов горутин без ограничения (unbounded concurrency) приводит к исчерпанию оперативной памяти и панике `OOM` (Out of Memory).
2. Сборка мусора и обход стеков: чем больше активных горутин в системе, тем дольше GC выполняет фазу `mark termination` и сканирование корней стеков.

## На собеседовании

**Вопрос с собеседования:** Если создание горутины занимает всего ~200 нс, зачем в Go Highload сервисах вообще используют Worker Pools (пулы горутин вроде `panjf2000/ants`)?
**Ответ:** Worker Pools используют не столько для экономии 200 нс на создании горутины, сколько для **ограничения параллелизма (concurrency limiting)** и защиты системы от перегрузки (backpressure). Если в сервис придет всплеск из 500 000 запросов, неограниченный запуск горутин исчерпает память и положит планировщик; пул же держит стабильное число воркеров и ставит избыточные задачи в очередь.
