# Типичные баги и краевые случаи рантайма Go

## Условие

**Runtime bugs и edge cases**: Изучите известные issues в Go runtime (например, goroutine leaks при неправильном использовании context, GC pauses при больших heap'ах до Go 1.19).

## Теория

Знание краевых случаев и архитектурных ограничений рантайма критически важно для предотвращения скрытых аварий (outages):
1. **Goroutine Leaks (утечки горутин):** забытый `context.WithCancel()` без вызова функции отмены `cancel()`, зависание в чтении из небуферизованного канала без таймаута, блокировка в сетевом вызове без дедлайна.
2. **GC Pause на гигантских кучах (Heap Scan):** до Go 1.19 приложения с миллионами мелких объектов страдали от длительного обхода графа указателей в фазе Mark.
3. **Timer Thundering Herd:** в старых версиях Go (до 1.14) все таймеры сидели на одном глобальном мьютексе, что вызывало жесточайший contention. В Go 1.14 таймеры распределили по \(P\), а в Go 1.23 полностью переписали алгоритм.

## Решение по шагам

1. Смоделируйте классическую утечку горутины при работе с небуферизованным каналом и отменой контекста.
2. Исправьте утечку добавлением буфера или выбором неблокирующей отправки в `select`.
3. Проконтролируйте количество живых горутин с помощью `runtime.NumGoroutine()`.

## Код решения

**`leak.go`**

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

// Ошибочная функция: утечка горутины из-за небуферизованного канала
func leakyOperation(ctx context.Context) error {
	ch := make(chan error) // ОШИБКА: небуферизованный канал!

	go func() {
		time.Sleep(100 * time.Millisecond) // эмулируем работу
		// Если ctx завершился по таймауту раньше, эта строка заблокирует
		// горутину навечно, так как из ch больше некому читать!
		ch <- fmt.Errorf("ошибка операции")
	}()

	select {
	case <-ctx.Done():
		return ctx.Err()
	case err := <-ch:
		return err
	}
}

// Корректная функция: буферизованный канал
func safeOperation(ctx context.Context) error {
	ch := make(chan error, 1) // Решение: буфер 1 позволяет горутине завершиться

	go func() {
		time.Sleep(100 * time.Millisecond)
		ch <- fmt.Errorf("ошибка операции")
	}()

	select {
	case <-ctx.Done():
		return ctx.Err()
	case err := <-ch:
		return err
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel()

	fmt.Printf("Горутин до старта: %d\n", runtime.NumGoroutine())
	_ = leakyOperation(ctx)

	time.Sleep(200 * time.Millisecond)
	fmt.Printf("Горутин после leakyOperation: %d (утекла 1 горутина!)\n", runtime.NumGoroutine())

	ctx2, cancel2 := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel2()
	_ = safeOperation(ctx2)

	time.Sleep(200 * time.Millisecond)
	fmt.Printf("Горутин после safeOperation: %d (без новых утечек)\n", runtime.NumGoroutine())
}
```

## Под капотом

Заблокированная в `ch <- err` горутина переходит в статус `_Gwaiting` и навсегда привязывается к очереди `sendq` канала `ch`.
Поскольку горутина держит ссылку на канал, а канал хранит указатель `sudog` на стек горутины, сборщик мусора GC не имеет права удалить ни стек горутины, ни сам канал, ни замыкания переменных, находящихся в её стеке!
Каждая утекшая горутина потребляет минимум 2 КБ стека + структуры рантайма, вызывая прогрессирующую деградацию RAM.

## Подводные камни

1. Сборщик мусора в Go **не собирает** заблокированные горутины! Горутина считается корневым объектом (GC root) до тех пор, пока не завершится её стартовая функция.
2. Небуферизованные каналы в связке с `select` и таймаутами — причина 90% утечек горутин в микросервисах.

## На собеседовании

**Вопрос с собеседования:** Почему сборщик мусора Go не может автоматически уничтожать горутины, которые больше никогда не разблокируются?
**Ответ:** Полноценный анализ того, «разблокируется ли горутина когда-либо в будущем» математически эквивалентен классической Проблеме остановки Тьюринга (Halting Problem), которая алгоритмически неразрешима в общем виде. Кроме того, заблокированная горутина может ожидать системного события, внешнего сетевого пакета или записи в канал из Cgo-библиотеки, о которых GC ничего не знает.
