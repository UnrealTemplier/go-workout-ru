# Оптимизация BCE: Bounds Check Elimination

## Условие

**BCE (Bounds Check Elimination)**: При доступе к элементу среза `a[i]` Go вставляет скрытую проверку `if i >= len(a) { panic(...) }`. Это замедляет циклы.
    Напиши функцию `func sum(a []int) { for i:=0; i<len(a); i++ { a[i]... } }`. 
    Запусти `go build -gcflags="-d=ssa/check_bce/debug=1"`. Посмотри в логи: компилятор убрал проверку `a[i]`, так как математически доказал, что `i` всегда меньше длины!
    А теперь напиши код, где обращаешься к `a[3]` напрямую внутри функции. Ты увидишь `Found IsInBounds` — проверка вставлена. Добавь строку `_ = a[3]` *до* цикла, и посмотри, как последующие проверки для индексов 0,1,2,3 в этой функции магически исчезнут!

### Исходная формулировка

**BCE (Bounds Check Elimination)**: При доступе к элементу среза `a[i]` Go вставляет скрытую проверку `if i >= len(a) { panic(...) }`. Это замедляет циклы.

## Теория

Безопасность памяти в Go гарантирует, что обращение к срезу за пределами его длины вызывает контролируемую панику `runtime error: index out of range`, а не повреждение памяти, как в C.

Для этого компилятор генерирует машинные инструкции проверки границ (Bounds Checks):
```text
CMPQ AX, CX  ; сравнение индекса i с длиной len(slice)
JAE  panicIndex
```
В высоконагруженных циклах (обработка видео, сетевых пакетов, криптография) эти проверки создают существенный оверхед и мешают векторизации инструкций процессора (SIMD).
Компилятор Go содержит оптимизатор **BCE (Bounds Check Elimination)**, который математически доказывает границы индексов и выбрасывает ненужные проверки.

## Решение по шагам

1. Напишите функцию суммирования среза в цикле `for i := 0; i < len(a); i++`.
2. Напишите функцию прямого чтения нескольких фиксированных индексов.
3. Продемонстрируйте трюк поднятия проверки границы (hoisting bounds check) с помощью `_ = a[3]`.
4. Запустите сборку с флагом `-gcflags="-d=ssa/check_bce/debug=1"` и изучите диагностические логи компилятора.

## Код решения

**`bce.go`**

```go
package main

import "fmt"

// Компилятор автоматически выбрасывает проверку границ для a[i],
// так как условие i < len(a) гарантирует безопасность
func Sum(a []int) int {
	total := 0
	for i := 0; i < len(a); i++ {
		total += a[i] // BCE: проверка границ устранена!
	}
	return total
}

// Наивная функция: компилятор вставит 4 отдельные проверки границ!
func ReadFourNaive(a []int) (int, int, int, int) {
	return a[0], a[1], a[2], a[3] // 4 проверки IsInBounds
}

// Оптимизированная функция с подъемом проверки границы (Bounds Check Hoisting)
func ReadFourOptimized(a []int) (int, int, int, int) {
	// Одна проверка a[3] гарантирует, что срез имеет длину минимум 4 элемента
	_ = a[3]
	// После этого компилятор гарантированно вырезает проверки для 0, 1, 2 и 3!
	return a[0], a[1], a[2], a[3]
}

func main() {
	data := []int{10, 20, 30, 40, 50}
	fmt.Printf("Сумма: %d\n", Sum(data))
	x0, x1, x2, x3 := ReadFourOptimized(data)
	fmt.Printf("Элементы: %d, %d, %d, %d\n", x0, x1, x2, x3)
}
```

ℹ️ Демонстрация устранения проверок выхода за границы среза (BCE)

**`Терминал`**

```bash
# Проверка диагностического лога BCE компилятора Go
go build -gcflags="-d=ssa/check_bce/debug=1" bce.go
```

## Под капотом

Проход `prove` в SSA строит граф фактов и неравенств для всех целочисленных переменных функции.
Когда компилятор встречает операцию `_ = a[3]`, он вставляет проверку `IsInBounds` и добавляет в контекст факт: `len(a) > 3`.
Для последующих обращений к `a[0]`, `a[1]`, `a[2]`, `a[3]` компилятор видит, что константы 0, 1, 2, 3 строго меньше доказанной границы длины, и заменяет проверку на прямую инструкцию чтения из памяти без единого `CMP` и условного перехода `JAE`!

## Подводные камни

1. Написание избыточных хаков с `_ = a[N]` в коде, не являющемся критическим узким местом по CPU, ухудшает читаемость и усложняет рефакторинг. Применяйте BCE только на основе данных профилировщика.
2. Проверка границ в цикле `for i, v := range a` устранена изначально, так как значение `v` берется напрямую из итератора.

## На собеседовании

**Вопрос с собеседования:** Что такое BCE (Bounds Check Elimination) в компиляторе Go и как написать код декодирования бинарного протокола (например, 8-байтного заголовка) максимально быстро?
**Ответ:** BCE — это фаза оптимизации в SSA компилятора, удаляющая рантайм-проверки выхода за границы слайса, если доказано, что индекс валиден. При парсинге 8-байтного пакета `buf []byte` первым делом пишут проверку длины `if len(buf) < 8 { return err }` или инструкцию `_ = buf[7]`. После этого компилятор доказывает, что байты `buf[0]`...`buf[7]` безопасны, и компилирует всю сборку 64-битного числа в одну ассемблерную инструкцию `MOVQ` без единого ветвления.
