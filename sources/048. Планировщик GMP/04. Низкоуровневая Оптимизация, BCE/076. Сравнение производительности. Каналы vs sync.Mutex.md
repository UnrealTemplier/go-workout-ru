# Сравнение производительности: Каналы vs sync.Mutex

## Условие

**Channel vs mutex performance**: Бенчмаркните channel operations vs mutex-protected shared state. Изучите, когда что быстрее.

## Теория

В Go существует популярный афоризм: «Не общайтесь, разделяя память; разделяйте память, общаясь». Однако с точки зрения низкоуровневой производительности и задержки каналы и мьютексы имеют принципиально разные характеристики.

Канал в Go — это сложная структура (`runtime.hchan`), внутри которой уже есть собственный `sync.Mutex`, кольцевой буфер и очереди заблокированных горутин (`waitq`).
Обычный `sync.Mutex` — это легковесная структура из 8 байт, использующая атомарные инструкции процессора `LOCK CMPXCHG` в Fast-Path.

Поэтому для защиты разделяемого состояния (счетчики, кеши, структуры) `sync.Mutex` в десятки раз быстрее каналов. Каналы предназначены для передачи владения данными и оркестрации потоков управления.

## Решение по шагам

1. Создайте бенчмарк для инкремента счетчика с использованием `sync.Mutex`.
2. Создайте бенчмарк для передачи сообщений через буферизованный канал.
3. Создайте бенчмарк с небуферизованным каналом.
4. Сравните время выполнения одной операции (`ns/op`) и аллокации памяти.

## Код решения

**`sync_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

// Инкремент через sync.Mutex
func BenchmarkMutex(b *testing.B) {
	var mu sync.Mutex
	var counter int64

	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			mu.Lock()
			counter++
			mu.Unlock()
		}
	})
}

// Передача через буферизованный канал
func BenchmarkBufferedChannel(b *testing.B) {
	ch := make(chan struct{}, 1)
	ch <- struct{}{}
	var counter int64

	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			<-ch
			counter++
			ch <- struct{}{}
		}
	})
}

// Защита через атомики (для эталона)
func BenchmarkAtomic(b *testing.B) {
	var counter int64
	var mu sync.Mutex // для параллельного теста

	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		mu.Lock()
		counter++
		mu.Unlock()
	}
	_ = counter
}
```

## Под капотом

При захвате свободной блокировки `sync.Mutex.Lock()` выполняется ровно одна ассемблерная инструкция `sync/atomic.CompareAndSwapInt32`, которая занимает ~10-15 наносекунд без обращения к рантайму.

При отправке в канал `ch <- val`:
1. Вызывается функция рантайма `runtime.chansend`.
2. Захватывается внутренний спинлок `lock(&c.lock)` внутри структуры `hchan`.
3. Выполняется проверка закрытия канала, проверка длины буфера.
4. Выполняется копирование данных памяти через `typedmemmove`.
5. Освобождается внутренний спинлок `unlock(&c.lock)`.
Накладные расходы канала в 5–15 раз выше, чем у `sync.Mutex`.

## Подводные камни

1. Использование каналов в качестве мьютекса (`chan struct{}` с буфером 1) создает сильный оверхед в высоконагруженных циклах.
2. Небуферизованный канал требует контекстного переключения горутины, что занимает от 1000 до 3000 нс против 15 нс у мьютекса.
3. Попытка переписать все мьютексы на каналы ради соблюдения догмы «Share memory by communicating» — классическая ошибка новичков, приводящая к падению производительности сервиса.

## На собеседовании

**Вопрос с собеседования:** В каких случаях в production-коде следует предпочесть канал мьютексу, несмотря на проигрыш в скорости?
**Ответ:** Каналы следует выбирать, когда:
1. Передается владение ресурсом (producer-consumer), где после передачи отправитель больше не прикасается к объекту.
2. Требуется координация нескольких независимых потоков событий через мультиплексирование `select` (таймауты, отмена контекста `ctx.Done()`).
3. Реализуются распределители задач (worker pool) и пайплайны обработки данных.
Мьютексы выбираются для защиты разделяемых in-memory структур данных (кеши, таблицы, метрики).
