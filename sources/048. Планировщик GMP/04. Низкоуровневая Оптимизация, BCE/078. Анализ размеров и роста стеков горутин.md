# Анализ размеров и роста стеков горутин с runtime.Stack

## Условие

**Stack size analysis**: Используйте `runtime.Stack()` для анализа размеров стеков горутин. Изучите, как стеки растут при глубоких вызовах.

## Теория

Каждая горутина в Go стартует с минимальным размером непрерывного стека (contiguous stack) размером **2 КБ** (в Go 1.2 до 1.4 использовались сегментированные стеки).
Если функция требует больше стека, чем осталось свободно, рантайм:
1. Аллоцирует новый непрерывный блок памяти в два раза большего размера (4 КБ, 8 КБ, ..., вплоть до 1 ГБ на 64-битных системах).
2. Копирует все стек-фреймы со старого стека в новый.
3. Корректирует все указатели, указывавшие на переменные в старом стеке.
4. Освобождает старый блок памяти.

Функция `runtime.Stack(buf []byte, all bool)` позволяет получить текстовый стектрейс текущей или всех активных горутин.

## Решение по шагам

1. Напишите рекурсивную функцию, которая глубоко погружается по стеку.
2. В контрольных точках вызовите `runtime.Stack()` для сбора текущего состояния стека.
3. Понаблюдайте за поведением адресов локальных переменных, чтобы убедиться в перемещении стека в памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

// Рекурсивная функция с локальным буфером для провокации роста стека
func deepStack(depth int, prevAddr *byte) {
	var localBuf [256]byte
	currAddr := &localBuf[0]

	if prevAddr != nil {
		dist := int64(uintptr(unsafe.Pointer(currAddr)) - uintptr(unsafe.Pointer(prevAddr)))
		if dist < -4096 || dist > 4096 {
			fmt.Printf("-> Стек вырос и перемещен в памяти на глубине %d! Дельта адресов: %d байт\n",
				depth, dist)
		}
	}

	if depth >= 50 {
		buf := make([]byte, 1024)
		n := runtime.Stack(buf, false)
		fmt.Printf("\nСтектрейс текущей горутины (глубина %d):\n%s\n", depth, string(buf[:n]))
		return
	}

	deepStack(depth+1, currAddr)
}

func main() {
	fmt.Println("Демонстрация динамического роста и перемещения стека:")
	deepStack(1, nil)
}
```

ℹ️ Обнаружение переноса стека в памяти при превышении порога 2 КБ

**`Терминал`**

```bash
go run main.go
```

## Под капотом

Компилятор вставляет в пролог каждой функции проверку преамбулы стека: сравнение регистра указателя стека `SP` с `g.stackguard0`.
Если места недостаточно, вызывается `runtime.morestack`.
`morestack` переключается на системный стек `g0` и вызывает `runtime.newstack()`.
`newstack` выделяет новый блок памяти размера `oldsize * 2`, вызывает `copystack()` для перемещения данных и корректировки всех внутренних указателей (pointer adjust pass), после чего возобновляет выполнение функции в новом стеке.

## Подводные камни

1. Из-за перемещения стека в памяти адрес переменной, размещенной на стеке, может измениться! Поэтому небезопасные указатели `unsafe.Pointer`, сохраненные в uintptr, теряют валидность при росте стека.
2. Сжатие стека (stack shrinking): во время работы сборщика мусора GC проверяет неиспользуемые части стека и может ужать его вдвое, если горутина использует менее 1/4 выделенной емкости.

## На собеседовании

**Вопрос с собеседования:** Почему Go перешел от сегментированных стеков (segmented stacks) к непрерывным стекам (contiguous stacks) в версии 1.4?
**Ответ:** Сегментированные стеки вызывали так называемую «проблему горячего разделения» (hot split problem). Если вызов функции происходил прямо на границе сегмента внутри цикла, на каждой итерации происходило выделение нового сегмента и его освобождение, что приводило к колоссальной просадке производительности. Непрерывные стеки удваиваются и сжимаются плавно с амортизированной сложностью \(O(1)\).
