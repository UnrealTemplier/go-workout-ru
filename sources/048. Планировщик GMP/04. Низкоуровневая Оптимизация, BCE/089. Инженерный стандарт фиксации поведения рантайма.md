# Инженерный стандарт фиксации поведения рантайма

## Условие

Для каждого упражнения фиксируйте результат в виде:
- Кода + комментариев
- Скриншота/лога `GODEBUG` или `pprof`
- Вывода в README: «Что ожидал / Что получил / Почему так»

## Теория

В промышленной разработке HighLoad систем недостаточно просто «написать работающий код». Инженер обязан владеть культурой верификации гипотез (hypothesis-driven performance tuning):
1. **Гипотеза (Что ожидал):** формулирование теоретической модели («Ожидаю 0 аллокаций в куче благодаря escape analysis»).
2. **Эксперимент (Что получил):** объективные числовые измерения через бенчмарк (`-benchmem`), execution trace, `pprof` или логи `GODEBUG`.
3. **Анализ расхождений (Почему так):** детальное объяснение низкоуровневой причины расхождения гипотезы с реальностью (интерфейсный боксинг, неинлайненный вызов, рассинхронизация потоков).

## Решение по шагам

1. Напишите тестовый сценарий с проверкой гипотезы о поведении аллокатора.
2. Снимите метрики профилирования аллокаций памяти.
3. Оформите стандартный инженерный отчет по шаблону «Что ожидал / Что получил / Почему так».

## Код решения

**`audit.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

// Функция, в которой мы ожидаем отсутствие аллокаций в куче
//go:noinline
func computeSum(a, b int) int {
	return a + b
}

// Функция, в которой скрыт интерфейсный боксинг (утечка в кучу)
//go:noinline
func formatSum(a, b int) string {
	res := a + b
	// fmt.Sprintf принимает ...any, вызывая escape analysis и аллокации
	return fmt.Sprintf("sum: %d", res)
}

func main() {
	var m1, m2 runtime.MemStats

	// Тест 1: Чистые вычисления
	runtime.ReadMemStats(&m1)
	for i := 0; i < 10000; i++ {
		_ = computeSum(i, i*2)
	}
	runtime.ReadMemStats(&m2)
	allocs1 := m2.Mallocs - m1.Mallocs

	// Тест 2: Форматирование с any
	runtime.ReadMemStats(&m1)
	for i := 0; i < 10000; i++ {
		_ = formatSum(i, i*2)
	}
	runtime.ReadMemStats(&m2)
	allocs2 := m2.Mallocs - m1.Mallocs

	fmt.Printf("Инженерный аудит аллокаций:\n")
	fmt.Printf("  computeSum (10k вызовов): %d аллокаций в куче\n", allocs1)
	fmt.Printf("  formatSum  (10k вызовов): %d аллокаций в куче\n", allocs2)
	fmt.Println("\nВывод аудита: Любая передача примитива в интерфейс interface{} (any) приводит к аллокации памяти.")
}
```

ℹ️ Практический пример протоколирования инженерного аудита рантайма

**`Терминал`**

```bash
go run audit.go
```

## Под капотом

Инструмент `-gcflags="-m"` выполняет анализ побега (escape analysis).
Если тип конкретной переменной приводится к интерфейсному типу `interface{}` / `any`, компилятор не всегда может доказать, что время жизни переменной не превысит вызывающий стек. В результате генерируется вызов `runtime.convT64` или `runtime.newobject`, выделяющий память в `mcache` кучи.

## Подводные камни

1. Замер производительности через микротесты с `fmt.Println` искажает результаты в тысячи раз, так как консольный вывод захватывает глобальный мьютекс стандартного вывода ОС.
2. Не верьте замерам в режиме `debug` без флагов оптимизации компилятора.

## На собеседовании

**Вопрос с собеседования:** Каков стандартный регламент расследования деградации задержки (p99 latency) в Go микросервисе в BigTech компании?
**Ответ:** 
1. Снятие метрик `/sched/latencies:seconds` и `go_gc_duration_seconds` через Prometheus.
2. Если виноват планировщик — снятие 5-секундного `execution trace` (`/debug/pprof/trace`) для поиска блокировок потоков и перегрузки `runq`.
3. Если виноват GC — снятие `heap profile` (`/debug/pprof/heap`) для поиска горячих аллокаторов.
4. Если виноваты мьютексы — снятие `/debug/pprof/mutex` для выявления contention.
