# Инспекция ассемблера Go: Write Barriers и Preemption Checks

## Условие

**Assembly inspection**: Используйте `go build -gcflags="-S"` для просмотра сгенерированного assembly. Изучите, как выглядят write barriers, preemption checks.

## Теория

Компилятор Go транслирует исходный код в машинно-независимый ассемблер стиля Plan 9.
Анализ сгенерированного ассемблера (`go build -gcflags="-S"` или `go tool objdump`) позволяет увидеть скрытую работу рантайма:
1. **Стек-чеки и Preemption Checks:** в начале каждой обычной функции стоит проверка:
   ```text
   MOVQ (TLS), CX
   CMPQ SP, 16(CX)  ; сравнение указателя стека с g.stackguard0
   JLS  morestack   ; переход на расширение стека или вытеснение
   ```
2. **Барьеры записи (Write Barriers):** при записи указателя в кучу компилятор вставляет проверку флага `runtime.writeBarrier.enabled`. Если сборщик мусора активен, вызывается специальная функция рантайма `runtime.gcWriteBarrier` для окраски объектов в серый цвет.

## Решение по шагам

1. Напишите код с записью указателя в кучу.
2. Скомпилируйте код с флагом `-gcflags="-S"`.
3. Найдите в листинге инструкции проверки стека `morestack` и барьера записи `gcWriteBarrier`.

## Код решения

**`demo.go`**

```go
package main

type Node struct {
	Value int
	Next  *Node
}

// Глобальный указатель в куче провоцирует установку write barrier при записи
var GlobalHead *Node

//go:noinline
func insertNode(val int) {
	newNode := &Node{Value: val}
	// Запись указателя в разделяемую память под присмотром GC
	GlobalHead = newNode
}

func main() {
	insertNode(100)
}
```

ℹ️ Код для демонстрации morestack и gcWriteBarrier в ассемблерном выводе

**`Терминал`**

```bash
# Получение ассемблерного листинга для функции insertNode
go build -gcflags="-S" demo.go 2>&1 | grep -A 20 "main.insertNode"
```

## Под капотом

В Plan 9 ассемблере Go:
- `PCDATA` и `FUNCDATA` — директивы генерации метаданных для рантайма и GC (карты указателей на стеке liveness map).
- `CALL runtime.morestack_noctxt(SB)` — переход на аллокацию стека при нехватке памяти или сигнал асинхронного вытеснения.
- `runtime.gcWriteBarrier(SB)` — гибридный барьер записи Юасы (Yuasa) / Дейкстры, гарантирующий, что ни один живой объект не будет пропущен во время конкурентной фазы Mark.

## Подводные камни

1. Псевдорегистры Plan 9 (`FP`, `SP`, `SB`, `PC`) не соответствуют напрямую регистрам процессора x86-64. Например, аппаратный `SP` и виртуальный Plan 9 `SP` отличаются на величину размера фрейма.
2. Проверка барьера записи удваивает количество ассемблерных инструкций при присваивании указателей.

## На собеседовании

**Вопрос с собеседования:** Почему простой вызов функции `foo()` в Go содержит проверку `CMPQ SP, 16(CX)`, а в C/C++ такой инструкции нет?
**Ответ:** В C/C++ потоки имеют гигантский фиксированный стек (8 МБ), завершающийся аппаратной страницей Guard Page (при переполнении ядро ОС генерирует аппаратный `SIGSEGV`). В Go горутины стартуют со стеком всего 2 КБ, поэтому компилятор Go обязан программно проверять границу стека перед каждым фреймом. Эта же проверка используется планировщиком для кооперативного вытеснения горутины (подмена `stackguard0 = stackPreempt`).
