# Диагностические флаги рантайма GODEBUG

## Условие

**GODEBUG flags**: Изучите все полезные `GODEBUG` флаги:
* `schedtrace`, `scheddetail` — scheduler
* `gctrace` — GC
* `allocfreetrace` — аллокации
* `madvdontneed=1` — поведение памяти

## Теория

Переменная окружения `GODEBUG` — мощнейший встроенный инструмент низкоуровневой телеметрии рантайма Go, не требующий модификации исходного кода.

Ключевые флаги:
- `schedtrace=X`: выводит однострочный отчет о состоянии GMP каждые \(X\) миллисекунд (число горутин, \(M\), \(P\), очереди).
- `scheddetail=1`: в сочетании со `schedtrace` выводит детальное состояние каждого потока \(M\), процессора \(P\) и горутины \(G\).
- `gctrace=1`: логирует каждый цикл сборщика мусора (длительность фаз, объем памяти до и после, число воркеров).
- `allocfreetrace=1`: логирует абсолютно каждое выделение и освобождение памяти с выводом стектрейса (используется для поиска утечек в тестовой среде).
- `madvdontneed=1`: принуждает рантайм на Linux использовать `MADV_DONTNEED` вместо `MADV_FREE` при возврате страниц ядру ОС, что приводит к немедленному уменьшению RSS процесса в `top`/`htop`.

## Решение по шагам

1. Напишите программу, создающую нагрузку на планировщик и память (горутины и циклические аллокации).
2. Запустите программу с флагом `GODEBUG=schedtrace=500,gctrace=1`.
3. Разберите вывод консоли и сопоставьте его с поведением рантайма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Println("Запуск программы под управлением GODEBUG...")
	fmt.Printf("GOMAXPROCS: %d\n", runtime.GOMAXPROCS(0))

	// Запускаем фоновые горутины для генерации активности планировщика
	for i := 0; i < 4; i++ {
		go func(id int) {
			for {
				// Выделяем память для провокации GC
				data := make([]byte, 1024*1024)
				_ = data
				time.Sleep(100 * time.Millisecond)
			}
		}(i)
	}

	// Работаем 2 секунды, наблюдая логи GODEBUG
	time.Sleep(2 * time.Second)
	fmt.Println("Работа завершена.")
}
```

ℹ️ Программа для генерации событий планировщика и сборщика мусора

**`Терминал`**

```bash
GODEBUG=schedtrace=500,gctrace=1 go run main.go
```

## Под капотом

При старте программы рантайм в функции `parsedebugvars()` парсит строку `GODEBUG`.
Если включен `schedtrace`, поток `sysmon` рассчитывает интервал времени и при срабатывании таймера вызывает `schedtrace(scheddetail != 0)`.
Если включен `gctrace`, функция `gcSweep()` при финализации сборки мусора форматирует и печатает статистику фаз Mark и Sweep в системный поток ошибок `stderr`.

## Подводные камни

1. Флаг `allocfreetrace=1` замедляет работу программы в сотни раз и генерирует гигабайты логов. Никогда не включайте его в production!
2. Несколько флагов в `GODEBUG` объединяются через запятую без пробелов: `GODEBUG=schedtrace=1000,scheddetail=1`. Пробелы приводят к игнорированию части параметров.

## На собеседовании

**Вопрос с собеседования:** Что означает флаг `madvdontneed=1` в `GODEBUG` и почему в Go 1.16 он стал поведением по умолчанию на Linux?
**Ответ:** Начиная с Go 1.12 рантайм использовал `MADV_FREE` для возврата страниц памяти ядру ОС. При этом ОС фактически освобождала память только при дефиците RAM на хосте, из-за чего RSS процесса в Kubernetes казался раздутым, приводя к ложным срабатываниям мониторинга и OOMKilled по метрикам контейнера. В Go 1.16 рантайм вернулся к `MADV_DONTNEED`, который немедленно обнуляет RSS в таблицах страниц ядра.
