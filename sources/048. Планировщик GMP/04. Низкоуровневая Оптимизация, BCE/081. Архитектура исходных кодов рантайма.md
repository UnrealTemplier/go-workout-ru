# Архитектура исходных кодов рантайма: proc.go, malloc.go, mgc.go

## Условие

    * `proc.go` — планировщик
    * `malloc.go` — аллокатор

    * `chan.go` — каналы
    * `stubs.go` — низкоуровневые заглушки и определения G, M, P.

### Исходная формулировка

## Теория

Рантайм Go — это не отдельная виртуальная машина (как JVM), а библиотека на чистом Go и ассемблере, которая компилируется и линкуется непосредственно в каждый исполняемый файл Go.

Ключевые файлы рантайма в `$GOROOT/src/runtime/`:
- `runtime2.go`: определения фундаментальных структур данных `type g struct`, `type m struct`, `type p struct`, `type hchan struct`.
- `proc.go`: цикл планирования `schedule()`, воровство работы `findrunnable()`, системные вызовы `entersyscall()` / `exitsyscall()`, поток мониторинга `sysmon()`.
- `malloc.go`: трехуровневый аллокатор `mcache`, `mcentral`, `mheap`, классы размеров (size classes), `tiny allocator`.
- `mgc.go`: трехцветный конкурентный маркер `gcStart()`, барьер записи `gcWriteBarrier()`, фазы STW.
- `chan.go`: отправка `chansend()` и прием `chanrecv()` из каналов.

## Решение по шагам

1. Найдите расположение исходных кодов рантайма с помощью команды `go env GOROOT`.
2. Напишите утилиту на Go, которая программно выводит путь к исходникам рантайма и анализирует структуры планировщика.
3. Ознакомьтесь с основными полями структуры `g` и `p` в файле `runtime2.go`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"path/filepath"
	"runtime"
)

func main() {
	goroot := runtime.GOROOT()
	runtimeSrc := filepath.Join(goroot, "src", "runtime")

	fmt.Printf("Директория рантайма Go: %s\n\n", runtimeSrc)

	filesToCheck := []string{
		"runtime2.go", // Описания G, M, P, sudog
		"proc.go",     // Логика планировщика GMP
		"malloc.go",   // Аллокатор памяти
		"mgc.go",      // Garbage Collector
		"chan.go",     // Каналы
	}

	for _, fname := range filesToCheck {
		path := filepath.Join(runtimeSrc, fname)
		info, err := os.Stat(path)
		if err != nil {
			fmt.Printf("[FAIL] Файл %s не найден: %v\n", fname, err)
			continue
		}
		fmt.Printf("  * %-14s : %6d строк/байт (%s)\n",
			fname, info.Size(), info.ModTime().Format("2006-01-02"))
	}

	fmt.Println("\nСовет: Используйте 'go doc runtime' или открывайте эти файлы в IDE для глубокого понимания рантайма.")
}
```

## Под капотом

В `runtime2.go` структура `g` содержит более 80 полей:
- `stack`: границы стека `lo` и `hi`.
- `stackguard0`: граница проверки переполнения стека и прерывания.
- `m`: указатель на текущий поток `*m`.
- `sched`: сохраненный контекст выполнения `gobuf` (регистры `SP`, `PC`, `BP`).
- `atomicstatus`: атомарный статус горутины (`_Gidle`, `_Grunnable`, `_Grunning`, `_Gsyscall`, `_Gwaiting`).

Структура `p` содержит:
- `runqhead`, `runqtail`, `runq [256]guintptr`: локальная кольцевая очередь готовых горутин без локов.
- `runnext`: слот горутины с наивысшим приоритетом выполнения.
- `mcache`: локальный кэш памяти для мелких объектов.

## Подводные камни

1. Исходные коды пакета `runtime` компилируются с особыми флагами: в них запрещены рекурсивные вызовы аллокатора и обычные стек-чеки в некоторых функциях (`//go:nosplit`).
2. Не пытайтесь импортировать приватные сущности рантайма напрямую без `//go:linkname` (использование linkname в Go 1.23+ жестко ограничено компилятором).

## На собеседовании

**Вопрос с собеседования:** Зачем в структуре `p` существует специальное поле `runnext`, если уже есть кольцевая очередь `runq` на 256 элементов?
**Ответ:** Поле `runnext` хранит одну единственную горутину, которая была только что разбужена или создана текущей горутиной. Планировщик отдает `runnext` абсолютный приоритет при следующем вызове `schedule()`. Это критически важно для паттернов вроде producer-consumer или обработки RPC: проснувшийся консьюмер сразу же получает CPU, пока данные еще горячие в L1/L2 кэшах текущего ядра процессора.
