# Архитектура фонового потока sysmon: полная сводка обязанностей

## Условие

**Роль `sysmon` (Системный монитор)**: `sysmon` — это фоновый поток рантайма, который работает без `P`. Его задачи: будить спящие таймеры, опрашивать сеть и... наказывать "жадные" горутины. *Просто запомни это для следующих двух упражнений.*

## Теория

Поток `sysmon` — это «сторожевой пес» (watchdog) всего рантайма Go.
Он выполняет:
1. Вытеснение горутин, работающих >10 мс (`preemptone`);
2. Отсоединение P от блокирующих системных вызовов (`handoffp`);
3. Опрос сетевых сокетов в `netpoll`, если они не опрашивались 10 мс;
4. Запуск принудительного цикла GC раз в 2 минуты (`forcegcperiod`);
5. Возврат физической памяти операционной системе (`scavenger`).

## Решение по шагам

1. Запускаем приложение с длительным временем работы.
2. Логируем поведение через `GODEBUG=schedtrace=1000`.
3. Анализируем стабильность параметров рантайма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Printf("Демонстрация стабильности под контролем sysmon (GOMAXPROCS=%d)...\n", runtime.GOMAXPROCS(0))

	// Запускаем фоновую периодическую нагрузку
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()

	done := time.After(1 * time.Second)
	for {
		select {
		case <-done:
			fmt.Println("Цикл успешно завершен под контролем sysmon.")
			return
		case t := <-ticker.C:
			_ = t
		}
	}
}
```

ℹ️ Фоновый контроль стабильности рантайма

**`Терминал`**

```bash
go run main.go
```

## Под капотом

`sysmon` реализован в файле `src/runtime/proc.go` в виде бесконечного цикла `for {}` с вызовом `usleep(delay)`. Он динамически адаптирует интервал сна: если программа активно работает, интервал равен 20 микросекундам; если программа простаивает, интервал постепенно экспоненциально увеличивается до 10 миллисекунд.

## Подводные камни

`sysmon` не может помочь, если поток M завис внутри ядра ОС в аппаратном сбое (D-state process, ожидание мертвого NFS-диска), так как поток ОС в состоянии uninterruptible sleep не реагирует ни на какие сигналы.

## На собеседовании

**Вопрос с собеседования:** Что произойдет с памятью Go-сервиса, если он выделил 10 ГБ памяти в куче под разовую задачу, освободил ее, но новых запросов больше не поступает?
**Ответ:**
1) Сборщик мусора освободит объекты в куче и пометит спаны памяти как свободные (`mheap`);
2) Однако физическая память ядра ОС (RSS) останется занятой;
3) Фоновый поток `sysmon` (совместно со scavenger-горутиной) обнаружит неиспользуемые страницы памяти и вызовет системный вызов `madvise(addr, len, MADV_DONTNEED)` (или `MADV_FREE` в зависимости от версии Go и ядра Linux);
4) Ядро Linux освободит физические страницы памяти, и RSS процесса снизится обратно до базового уровня.
