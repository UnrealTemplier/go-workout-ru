# Внутреннее устройство каналов: структуры hchan, sudog и функции gopark/goready

## Условие

**Channel operations и planning**: Отправьте/получите данные из канала. Изучите, как `gopark` и `goready` переводят горутину в `_Gwaiting` и обратно в `_Grunnable`.

## Теория

Канал в Go — это структура в куче `runtime.hchan`:
```go
type hchan struct {
    qcount   uint           // Всего элементов в буфере
    dataqsiz uint           // Размер кольцевого буфера
    buf      unsafe.Pointer // Указатель на массив данных
    elemsize uint16
    closed   uint32
    elemtype *_type
    sendx    uint           // Индекс отправки
    recvx    uint           // Индекс приема
    recvq    waitq          // Очередь заблокированных читателей (список sudog)
    sendq    waitq          // Очередь заблокированных писателей (список sudog)
    lock     mutex          // Спинлок канала
}
```

Когда горутина блокируется на канале, она упаковывается в структуру **`sudog`** (pseudo-g), которая связывает `g` с конкретным каналом, и уходит в сон через `gopark()`. При разблокировке парная горутина извлекает `sudog` из `waitq` и вызывает `goready()`.

## Решение по шагам

1. Создаем буферизованный и небуферизованный каналы.
2. Анализируем последовательность вызовов при блокировке и передаче данных.
3. Проверяем поведение очередей ожидания.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	ch := make(chan string) // Небуферизованный канал (dataqsiz = 0)
	var wg sync.WaitGroup
	wg.Add(2)

	// Читатель блокируется первым: попадает в ch.recvq в виде sudog
	go func() {
		defer wg.Done()
		fmt.Println("  [Reader] Ждет данных из канала...")
		val := <-ch // Вызов chansend -> gopark
		fmt.Printf("  [Reader] Получил: %s\n", val)
	}()

	time.Sleep(100 * time.Millisecond)

	// Писатель разблокирует читателя через goready
	go func() {
		defer wg.Done()
		fmt.Println("  [Writer] Отправка данных в канал...")
		ch <- "Hello GMP" // Прямое копирование в стек читателя + goready
		fmt.Println("  [Writer] Отправка завершена.")
	}()

	wg.Wait()
	fmt.Println("Канал успешно отработал цикл gopark/goready.")
}
```

ℹ️ Механизм блокировки и прямой передачи данных через канал

**`Терминал`**

```bash
go run main.go
# Вывод:
#   [Reader] Ждет данных из канала...
#   [Writer] Отправка данных в канал...
#   [Writer] Отправка завершена.
#   [Reader] Получил: Hello GMP
# Канал успешно отработал цикл gopark/goready.
```

## Под капотом

Прямая передача данных из стека в стек (Direct Stack-to-Stack Copy): если читатель уже ждет в `ch.recvq`, отправляющая горутина захватывает `ch.lock`, находит первый `sudog` в очереди, копирует данные напрямую из своего стека по адресу `sudog.elem` в стек читателя и вызывает `goready(sudog.g)`. Это исключает двойное копирование (в буфер канала и из него).

## Подводные камни

Чтение или запись в `nil`-канал навсегда блокирует горутину через `gopark(nil, nil, waitReasonChanReceiveNilChan, ...)`. Так как проснуться она никогда не сможет, это приводит к вечной утечке памяти стека этой горутины.

## На собеседовании

**Вопрос с собеседования:** Что такое структура `sudog` в рантайме Go и почему горутина `g` не может быть помещена напрямую в очередь ожидания канала?
**Ответ:** Горутина может одновременно ожидать на **нескольких** каналах (оператор `select`).
Если бы сама структура `g` содержала поля связного списка `next` и `prev`, она могла бы находиться только в одном списке одновременно.
Структура `sudog` выступает промежуточным связующим звеном: для каждого канала в блоке `select` создается отдельный `sudog`, ссылающийся на одну и ту же горутину `g`. Это позволяет горутине безопасно находиться в очередях десятков каналов одновременно.
