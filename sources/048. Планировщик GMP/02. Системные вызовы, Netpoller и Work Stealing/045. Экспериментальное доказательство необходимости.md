# Экспериментальное доказательство необходимости сигналов SIGURG через asyncpreemptoff=1

## Условие

Создайте CPU-bound задачу без вызовов функций. С помощью `GODEBUG=asyncpreemptoff=1` отключите асинхронное вытеснение. Покажите, что вторая goroutine не запускается. Включите обратно — покажите, как `sysmon` (поток на 10-20 мс) расставляет `asyncPreempt`.

## Теория

Флаг `GODEBUG=asyncpreemptoff=1` позволяет в деталях воспроизвести проблему, с которой инженеры Go боролись с 2012 по 2020 год (до релиза Go 1.14).
Без асинхронного вытеснения горутина с циклом:
```go
for !stop {}
```
не содержит ни вызовов функций, ни аллокаций, ни работы с каналами. Компилятор не генерирует для такого цикла ни одного `morestack`.
Если `GOMAXPROCS=1`, эта горутина монополизирует процессор навсегда: ни таймер, ни сетевой сокет, ни сборщик мусора не смогут получить управление.

## Решение по шагам

1. Создаем программу с каналом таймаута и плотным циклом.
2. Проверяем работу в штатном режиме (вытеснение за 10 мс).
3. Документируем поведение при `asyncpreemptoff=1`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Демонстрация вытеснения пустого цикла:")

	var running int32 = 1

	// Горутина с плотным циклом
	go func() {
		for atomic.LoadInt32(&running) == 1 {
			// Нет вызовов функций
		}
		fmt.Println("Горутина успешно вытеснена и завершена!")
	}()

	time.Sleep(100 * time.Millisecond)
	atomic.StoreInt32(&running, 0)
	time.Sleep(50 * time.Millisecond)

	fmt.Println("Тест завершен.")
}
```

ℹ️ Проверка вытеснения плотного цикла

**`Терминал`**

```bash
go run main.go
# Штатный вывод в современном Go:
# Демонстрация вытеснения пустого цикла:
# Горутина успешно вытеснена и завершена!
# Тест завершен.
```

## Под капотом

В Go 1.14 компилятор также внедрил вставку инструкций вытеснения в циклы (Loop Preemption), но для плотных пустых циклов только сигнал `SIGURG` от ядра Linux гарантирует гарантированное прерывание.

## Подводные камни

В коде на WebAssembly (Wasm) асинхронное вытеснение по сигналам ОС недоступно, так как архитектура Wasm не поддерживает POSIX-сигналы. В Wasm Go по-прежнему использует кооперативное вытеснение.

## На собеседовании

**Вопрос с собеседования:** Почему в WebAssembly (GOOS=js GOARCH=wasm) планировщик Go не поддерживает асинхронное вытеснение через сигналы?
**Ответ:** Потому что модель выполнения WebAssembly в браузерах не предоставляет потоков POSIX и сигнального механизма ядер Unix (`pthread_kill`). Wasm-код выполняется в изолированной виртуальной машине браузера.
Поэтому в WebAssembly Go вынужден полагаться только на кооперативные точки вытеснения (`morestack`), либо компилятор вставляет дополнительные проверки при сборке под Wasm.
