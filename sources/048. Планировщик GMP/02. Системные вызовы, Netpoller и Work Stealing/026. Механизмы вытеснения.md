# Механизмы вытеснения: эволюция от проверки стека до сигналов SIGURG

## Условие

**Кооперативное вытеснение (историческое vs современное).**: Напишите бесконечный цикл без вызовов функций/системных вызовов (Go 1.14+ с асинхронным вытеснением должен прерываться). До 1.14 – проверить поведение (можно на старом Go), показать, что без прерывания горутина блокирует P.

## Теория

Историческая эволюция планировщика Go:
1. **Go 1.0 (2012): Модель GM.** Без абстракции P. Один глобальный лок планировщика.
2. **Go 1.1 (2013): Модель GMP.** Дмитрий Вьюков внедрил логические процессоры `P`, локальные очереди `LRQ` и `Work Stealing`. Вытеснение оставалось кооперативным на проверке стека.
3. **Go 1.2–1.13: Кооперативное вытеснение.** Вставка проверок `morestack` в прологи функций. Плотные циклы `for {}` подвешивали рантайм.
4. **Go 1.14+ (2020): Асинхронное некооперативное вытеснение (Non-cooperative Preemption).** Сигналы ОС `SIGURG` прерывают выполнение потоков независимо от структуры кода.

## Решение по шагам

1. Создаем программу, наглядно демонстрирующую вытеснение горутины без точек вызова функций.
2. Проверяем работу сборщика мусора во время работы бесконечного цикла.
3. Убеждаемся, что STW отрабатывает мгновенно.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Демонстрация вытеснения для сборщика мусора (GC STW)...")

	stop := false
	go func() {
		for !stop {
			// Плотный цикл без вызовов функций
		}
	}()

	time.Sleep(50 * time.Millisecond)

	// В Go < 1.14 вызов runtime.GC() завис бы навсегда, так как GC не мог вытеснить горутину
	start := time.Now()
	runtime.GC()
	fmt.Printf("Сборщик мусора успешно отработал за %v благодаря асинхронному вытеснению!\n", time.Since(start))

	stop = true
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Успешная отработка GC во время плотного цикла

**`Терминал`**

```bash
go run main.go
# Вывод в Go 1.14+:
# Демонстрация вытеснения для сборщика мусора (GC STW)...
# Сборщик мусора успешно отработал за ~1.2ms благодаря асинхронному вытеснению!
```

## Под капотом

Когда запускается GC, рантайму требуется остановить все горутины (`stopTheWorld`). Для этого вызывается `preemptall()`, которая рассылает сигналы `SIGURG` всем потокам `M`, находящимся в состоянии `_Grunning`. Потоки мгновенно паркуются в точках безопасного останова, сборщик мусора выполняет сканирование корней, и вызывается `startTheWorld()`, возобновляющий работу.

## Подводные камни

Если программа использует внешние C/C++ библиотеки через CGO, C-код не знает про сигналы Go. Долгий C-цикл вытеснить сигналом `SIGURG` нельзя, и GC будет ждать завершения вызова CGO.

## На собеседовании

**Вопрос с собеседования:** Почему в Go < 1.14 вызов `runtime.GC()` мог привести к полному зависанию (deadlock) приложения, если в нем работал цикл `for {}`?
**Ответ:** Сборка мусора в Go требует фазы Stop-The-World (остановки всех горутин) для фиксации корневых указателей стеков.
В Go < 1.14 планировщик полагался на кооперативное вытеснение: он выставлял флаг `preempt = true` и ждал, пока каждая горутина сама вызовет функцию и проверит границу стека. Горутина с циклом `for {}` не вызывала функций и игнорировала флаг.
В результате поток GC бесконечно ждал остановки этой горутины, а все остальные горутины уже были остановлены — наступал полный дедлок.
