# Сценарий Half-Half: балансировка двух занятых ядер и двух свободных P

## Условие

Создайте ситуацию «half-half»: 2 CPU-bound goroutine на 2 P, остальные P простаивают. Заставьте «простаивающие» P украсть работу. Объясните, почему steal происходит только при пустой локальной очереди и как работает `findRunnable()`.

## Теория

В распределенных многопроцессорных системах часто возникает ситуация «Half-Half»:
Половина процессоров P полностью загружена долгими CPU-задачами, а вторая половина освободилась.
Планировщик Go использует потоки `Spinning M`:
- Освободившиеся процессоры не выключаются мгновенно, а заходят в цикл `findrunnable()`;
- Они находят занятые P и крадут у них по половине очереди (`runqsteal`);
- Если одна из тяжелых горутин порождает пачку подзадач, они мгновенно растаскиваются свободными ядрами без задержки на пробуждение.

## Решение по шагам

1. Устанавливаем `GOMAXPROCS=4`.
2. Запускаем 2 CPU-bound горутины, занимающие 2 P на 100%.
3. На остальных 2 P запускаем генерацию быстрых задач.
4. Отслеживаем утилизацию ядер.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Println("Сценарий Half-Half на 4 P...")

	var wg sync.WaitGroup
	stopCPU := make(chan struct{})

	// 2 тяжелые CPU-bound горутины на P0 и P1
	for i := 0; i < 2; i++ {
		go func(id int) {
			var acc uint64
			for {
				select {
				case <-stopCPU:
					return
				default:
					acc = (acc*17 + 1) % 1000000007
				}
			}
		}(i)
	}

	// Генерация потока легких задач на оставшихся P
	const tasks = 500
	wg.Add(tasks)
	for i := 0; i < tasks; i++ {
		go func(id int) {
			defer wg.Done()
			time.Sleep(2 * time.Millisecond)
		}(i)
	}

	wg.Wait()
	close(stopCPU)
	time.Sleep(50 * time.Millisecond)
	fmt.Println("Сценарий Half-Half успешно завершен.")
}
```

ℹ️ Сценарий частичной загрузки ядер и свободных P

**`Терминал`**

```bash
go run main.go
```

## Под капотом

В сценарии Half-Half счетчик `sched.idleprocs` равен 2, а `sched.nmspinning` равен 1. Один поток вращения постоянно проверяет очереди занятых P. Это гарантирует, что как только тяжелая горутина уступит процессор или создаст дочернюю горутину, она будет немедленно подхвачена свободным ядром.

## Подводные камни

Если тяжелые задачи выполняют вычисления без аллокаций памяти, кэши L1/L2 занятых ядер не инвалидируются, обеспечивая максимальный IPC (instructions per cycle).

## На собеседовании

**Вопрос с собеседования:** Как рантайм Go балансирует горутины, если в приложении одновременно работают и тяжелые CPU-bound вычисления, и тысячи легковесных сетевых запросов?
**Ответ:**
1) Сетевые горутины уходят в сон в `netpoller`, не занимая CPU;
2) CPU-bound горутины работают на процессорах `P`, но каждые 10 мс вытесняются потоком `sysmon` через `SIGURG`;
3) Проснувшиеся от сетевых событий горутины попадают в очереди `P` и благодаря вытеснению получают процессорное время в течение максимум 10 мс;
4) Work Stealing гарантирует, что сетевые горутины не застрянут на занятом P, а будут украдены свободными процессорами.
