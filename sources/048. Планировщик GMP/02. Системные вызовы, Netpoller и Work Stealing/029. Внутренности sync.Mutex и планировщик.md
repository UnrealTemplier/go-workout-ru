# Внутренности sync.Mutex и планировщик: спиннинг процессора против runtime.gopark

## Условие

**Mutex и planning**: Захватите `sync.Mutex` в одной горутине, попробуйте захватить в другой. Изучите, как semaphore и `gopark` используются для блокировки.

## Теория

`sync.Mutex` в Go — это гибридный адаптивный мьютекс:
1. **Fast Path:** Если мьютекс свободен, захват происходит за одну инструкцию `atomic.CompareAndSwapInt32` (CAS).
2. **Active Spinning:** Если мьютекс занят другим потоком, горутина не засыпает сразу. Она выполняет до 4 циклов активного ожидания (PAUSE-инструкции процессора), надеясь, что критическая секция освободится за микросекунды.
3. **Slow Path:** Если спиннинг исчерпан, горутина вызывает `runtime_SemacquireMutex()`. Рантайм переводит ее в состояние `_Gwaiting` через `gopark()` и вешает на внутренний семафор.
4. **Starvation Mode (Режим голодания):** Если горутина ждет мьютекс дольше 1 мс, мьютекс переключается в режим голодания: новые горутины не спинят, а право захвата передается строго первому в очереди ожидания.

## Решение по шагам

1. Создаем ситуацию жесткой конкуренции за `sync.Mutex`.
2. Анализируем переключение между активным спиннингом и сном.
3. Проверяем поведение режима Starvation.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

type Counter struct {
	mu  sync.Mutex
	val int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	c.val++
	c.mu.Unlock()
}

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Println("Демонстрация конкуренции за sync.Mutex...")

	var c Counter
	var wg sync.WaitGroup
	const routines = 100
	const incs = 10000
	wg.Add(routines)

	start := time.Now()
	for i := 0; i < routines; i++ {
		go func() {
			defer wg.Done()
			for j := 0; j < incs; j++ {
				c.Inc()
			}
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговое значение: %d (ожидалось %d) за %v\n", c.val, routines*incs, time.Since(start))
}
```

**`Терминал`**

## Под капотом

В `src/sync/mutex.go` функция `lockSlow()` проверяет:
- Разрешен ли спиннинг: `runtime_canSpin(iter)`. Спиннинг разрешен только на многоядерных машинах (`GOMAXPROCS > 1`), если локальная очередь `LRQ` пуста и процессор выполнил менее 4 спин-итераций `procyield(30)`.
- Инструкция `procyield(30)` компилируется в 30 инструкций ассемблера `PAUSE`, снимающих нагрузку с конвейера CPU.

## Подводные камни

Удержание `sync.Mutex` во время выполнения сетевого запроса или дисковой операции — грубейший антипаттерн. Горутины, ждущие этот мьютекс, уйдут в режим голодания, а планировщик будет тратить ресурсы на переключения `gopark`/`goready`.

## На собеседовании

**Вопрос с собеседования:** Что такое Starvation Mode (режим голодания) в `sync.Mutex` в Go и для чего он был добавлен в Go 1.9?
**Ответ:** До Go 1.9 мьютексы всегда работали в режиме состязания: новая горутина, уже исполняющаяся на CPU (`_Grunning`), имела преимущество перед горутиной, только что проснувшейся из очереди семафора (`_Gwaiting`), так как ей не нужно было тратить время на пробуждение. Это приводило к **голоданию (tail latency starvation)**: спящая горутина могла не получить лок сотни миллисекунд.
В Go 1.9 внедрен **Starvation Mode**: если горутина ждет мьютекс дольше **1 миллисекунды**, мьютекс переходит в режим голодания. В этом режиме новые горутины вообще не пытаются захватить лок и не спинят, а владение мьютексом передается строго по очереди (FIFO) первому ждущему.
