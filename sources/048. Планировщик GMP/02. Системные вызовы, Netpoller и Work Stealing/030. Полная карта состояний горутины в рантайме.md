# Полная карта состояний горутины в рантайме: Running, Waiting, Runnable, Syscall

## Условие

**Goroutine states**: Используйте `runtime.Stack()` для дампа стека всех горутин. Изучите состояния: `_Grunnable`, `_Grunning`, `_Gsyscall`, `_Gwaiting`, `_Gdead`.

## Теория

Состояния горутины в рантайме Go разделяются на базовые и переходные:
- `_Gidle` (0): горутина только что выделена в памяти, стек не инициализирован.
- `_Grunnable` (1): горутина в очереди (LRQ или GRQ), готова к немедленному запуску.
- `_Grunning` (2): горутина владеет потоком M и процессором P, исполняет машинные инструкции.
- `_Gsyscall` (3): горутина делает системный вызов ядра ОС.
- `_Gwaiting` (4): горутина припаркована рантаймом (на канале, мьютексе, таймере, сетевом сокете).
- `_Gdead` (6): горутина завершилась и помещена в пул `gFree` для повторного использования.
- `_Gcopystack` (8): стек горутины перемещается в куче на новый увеличенный участок памяти.
- `_Gpreempted` (9): горутина вытеснена сигналом `SIGURG` и ждет перевода в `_Grunnable`.

## Решение по шагам

1. Создаем по одной горутине для демонстрации ключевых состояний (`Running`, `Waiting`, `Syscall`).
2. Запускаем срез стека через `runtime.Stack`.
3. Сопоставляем реальные текстовые метки стека с константами рантайма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"syscall"
	"time"
)

func waitingWorker(ch chan struct{}) {
	// Состояние _Gwaiting (chan receive)
	<-ch
}

func syscallWorker() {
	// Состояние _Gsyscall
	var req, rem syscall.Timespec
	req.Sec = 2
	syscall.Nanosleep(&req, &rem)
}

func runningWorker(stop *bool) {
	// Состояние _Grunning
	var x int
	for !*stop {
		x++
	}
	_ = x
}

func main() {
	runtime.GOMAXPROCS(3)

	ch := make(chan struct{})
	stop := false

	go waitingWorker(ch)
	go syscallWorker()
	go runningWorker(&stop)

	time.Sleep(100 * time.Millisecond)

	buf := make([]byte, 16384)
	n := runtime.Stack(buf, true)

	fmt.Println("=== Карта состояний горутин в runtime.Stack ===")
	fmt.Printf("%s\n", buf[:n])

	stop = true
	close(ch)
	time.Sleep(50 * time.Millisecond)
	os.Exit(0)
}
```

ℹ️ Срез состояний горутин: waiting, syscall, running

**`Терминал`**

```bash
go run main.go
# В выводе отчетливо идентифицируются состояния:
# goroutine ... [running]:
# goroutine ... [chan receive]:
# goroutine ... [syscall]:
```

## Под капотом

Переходы между состояниями атомарны и выполняются с помощью `atomic.Cas` или `atomic.Store` над полем `gp.atomicstatus`. Дополнительный бит `_Gscan` устанавливается сборщиком мусора во время параллельного сканирования стека: например `_Gwaiting | _Gscan` сообщает планировщику, что горутину нельзя будить, пока GC не закончит проверку ее указателей.

## Подводные камни

Попытка анализировать стек через парсинг строк `runtime.Stack()` в продакшене несет высокие накладные расходы. Для метрик используйте функцию `runtime.NumGoroutine()` или пакет `runtime/metrics` (Go 1.16+).

## На собеседовании

**Вопрос с собеседования:** Что происходит с горутиной при переходе в состояние `_Gcopystack`?
**Ответ:** Горутина начинает жизнь с маленьким стеком в 2 КБ.
Когда при вызове функции стек исчерпывается, проверка в прологе вызывает `runtime.morestack()`.
Рантайм переводит горутину в состояние `_Gcopystack`:
1) В куче выделяется новый непрерывный блок памяти в 2 раза большего размера (4 КБ, 8 КБ и т.д.);
2) Все фреймы со старого стека побайтово копируются в новый блок;
3) Все указатели, ссылавшиеся внутрь старого стека, автоматически корректируются рантаймом на новые адреса;
4) Старый стек освобождается, статус меняется на `_Grunning`, и выполнение возобновляется.
