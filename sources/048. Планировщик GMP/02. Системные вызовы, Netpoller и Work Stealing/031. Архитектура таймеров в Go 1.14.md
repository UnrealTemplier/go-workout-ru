# Архитектура таймеров в Go 1.14+: интеграция p.timers без глобального timerproc

## Условие

**Timer goroutines**: Создайте множество `time.After()` таймеров. Изучите, как runtime использует timer heap и dedicated goroutine для обработки таймеров.

## Теория

Историческая эволюция таймеров в Go:
- **До Go 1.10:** Был один глобальный поток `timerproc` и один глобальный мьютекс. Огромные блокировки.
- **Go 1.10–1.13:** Таймеры разбили на 64 шардированные кучи. Конкуренция уменьшилась, но сохранялись переключения контекста потоков ОС.
- **Go 1.14+:** Таймеры были полностью **интегрированы в структуру каждого логического процессора P** (`p.timers`).

Каждый `P` управляет собственной 4-арной кучей (4-ary heap) таймеров.
Когда горутина вызывает `time.After()` или `time.Sleep()`:
- Таймер добавляется в кучу текущего `P` без глобальных блокировок;
- Проверка и исполнение сработавших таймеров происходят прямо во время штатного цикла планирования `checkTimers(pp)` и потоком `sysmon`.

## Решение по шагам

1. Создаем тест с генерацией тысяч коротких таймеров `time.After()`.
2. Измеряем задержку и нагрузку на планировщик.
3. Анализируем работу кучи таймеров без утечек.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Printf("GOMAXPROCS = %d. Запуск 10 000 таймеров...\n", runtime.GOMAXPROCS(0))

	const count = 10000
	var wg sync.WaitGroup
	wg.Add(count)

	start := time.Now()
	for i := 0; i < count; i++ {
		go func(id int) {
			defer wg.Done()
			// time.After создает таймер в p.timers текущего P
			<-time.After(10 * time.Millisecond)
		}(i)
	}

	wg.Wait()
	duration := time.Since(start)

	fmt.Printf("Все 10 000 таймеров успешно сработали за %v\n", duration)
	fmt.Printf("Итоговое число горутин: %d\n", runtime.NumGoroutine())
}
```

ℹ️ Массовые таймеры на базе per-P timer heaps

**`Терминал`**

```bash
go run main.go
# Вывод:
# GOMAXPROCS = 4. Запуск 10 000 таймеров...
# Все 10 000 таймеров успешно сработали за ~22.4ms
# Итоговое число горутин: 1
```

## Под капотом

В `src/runtime/time.go` таймеры хранятся в массиве `pp.timers`. Рантайм использует 4-арную кучу (quad-heap), где родитель элемента \(k\) находится по индексу $(k-1)/4$. 4-арная куча обеспечивает лучшую кэш-локальность по сравнению с классической бинарной кучей, требуя меньше перемещений по памяти при операциях просеивания (sift-up / sift-down).

## Подводные камни

Использование `time.After()` внутри циклов `select` без выхода из функции создает скрытую утечку: таймер не будет собран сборщиком мусора до тех пор, пока не истечет его время, даже если сработала другая ветка `select`. Для циклов всегда используйте `time.NewTimer()` с явным `timer.Stop()` и дренажем канала.

## На собеседовании

**Вопрос с собеседования:** Почему в Go 1.14 архитектуру таймеров перенесли внутрь структуры `P`, и какой эффект это дало на latency сетевых серверов?
**Ответ:** В старых версиях сработавший таймер будил специальный отдельный поток `timerproc`, который захватывал мьютекс и будил горутину через `goready()`. Это приводило к постоянным переключениям контекста между потоками ОС и скачкам задержек p99.
Перенос таймеров в `P`:
1) Ликвидировал глобальные мьютексы и отдельный поток;
2) Позволил проверять таймеры прямо в штатном цикле планирования `schedule()` того процессора `P`, на котором и так исполняется код;
3) Улучшил попадание в кэш процессора (L1/L2 Cache Affinity);
4) Сократил накладные расходы на сетевые таймауты в `net/http` и `gRPC` сервисах более чем на 30%.
