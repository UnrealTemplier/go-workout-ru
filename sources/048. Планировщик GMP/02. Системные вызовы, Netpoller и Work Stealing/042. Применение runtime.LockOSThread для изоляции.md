# Применение runtime.LockOSThread для изоляции пространств имен Linux и GUI

## Условие

**[runtime.LockOSThread]**: Напиши программу, где горутина вызывает `runtime.LockOSThread()`. Объясни, почему эта горутина теперь навсегда привязана к конкретному потоку ОС (M), и P не может быть передан другому M, если эта горутина заблокируется. (Где это используется? — В CGO, OpenGL, syscall.Setuid).

## Теория

При разработке системного ПО (систем контейнеризации типа Docker/runC) критически важно управлять сетевыми пространствами имен (Network Namespaces).
Системный вызов `unix.Setns(fd, unix.CLONE_NEWNET)` переключает пространство имен строго для текущего потока ядра Linux.
Если не вызвать `runtime.LockOSThread()`:
- Горутина переключит namespace у потока M1;
- При следующем переключении контекста планировщик перенесет горутину на поток M2, который находится в базовом namespace хоста!
- Произойдет утечка сетевого трафика и нарушение изоляции контейнера.

## Решение по шагам

1. Создаем функцию, изолирующую выполнение внутри заблокированного потока.
2. Применяем `runtime.LockOSThread()`.
3. Гарантируем корректный выход из потока при завершении.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"syscall"
)

// Имитация безопасного выполнения задачи в изолированном контексте потока
func runInDedicatedThread(fn func()) {
	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()
		// 1. Блокируем поток ОС
		runtime.LockOSThread()
		// Внимание: если состояние потока модифицируется необратимо (setns),
		// UnlockOSThread делать НЕЛЬЗЯ — поток должен умереть вместе с горутиной!
		defer runtime.UnlockOSThread()

		fmt.Printf("  [Worker] Запуск в выделенном потоке ОС (TID = %d)\n", syscall.Gettid())
		fn()
	}()

	wg.Wait()
}

func main() {
	fmt.Printf("Главный поток: TID = %d\n", syscall.Gettid())

	runInDedicatedThread(func() {
		fmt.Println("  [Task] Выполнение задачи, требующей привязки к потоку...")
	})

	fmt.Println("Выполнение задачи завершено.")
}
```

ℹ️ Изоляция потока ОС для специфичных системных вызовов

**`Терминал`**

```bash
go run main.go
# Вывод:

#   [Worker] Запуск в выделенном потоке ОС (TID = 1235)
#   [Task] Выполнение задачи, требующей привязки к потоку...
# Выполнение задачи завершено.
```

## Под капотом

Если горутина вызвала `runtime.LockOSThread()`, завершается, но НЕ вызывает `UnlockOSThread()`, рантайм помечает поток `mp.lockedg = nil` и вызывает `pthread_exit()`. Поток ОС не возвращается в общий пул потоков, исключая риск того, что другая горутина случайно выполнит сетевой вызов в чужом namespace.

## Подводные камни

Вызов `LockOSThread()` в массовых горутинах (например внутри HTTP-хендлера) парализует планировщик Go, превращая легковесную модель GMP в классическую тяжелую модель 1:1 с тысячами системных потоков.

## На собеседовании

**Вопрос с собеседования:** Почему в исходном коде утилиты `runc` и библиотеки `libcontainer` переключение Linux Namespaces выполняется в конструкторе на CGO через `__attribute__((constructor))` до старта рантайма Go?
**Ответ:** Потому что рантайм Go стартует многопоточно (`sysmon`, сборщик мусора, потоки M).
В ядре Linux системные вызовы изменения пространств имен (`setns`, `unshare`) имеют жесткие ограничения: поток не может отвязать некоторые namespace, если процесс уже является многопоточным (multithreaded).
Поэтому в `runc` создается конструктор на языке C, который выполняется до того, как Go поднимет свои потоки и инициализирует планировщик.
