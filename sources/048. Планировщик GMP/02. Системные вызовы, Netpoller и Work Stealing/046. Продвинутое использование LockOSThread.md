# Продвинутое использование LockOSThread: привязка горутины для CGO и системных потоков

## Условие

**LockOSThread**: Используйте `runtime.LockOSThread()` для привязки горутины к OS потоку (необходимо для Cgo, GUI-потоков). Изучите последствия для scheduling.

## Теория

При вызове `runtime.LockOSThread()` горутина привязывается к потоку M.
Это критично в следующих сценариях:
1. **Thread-Local Storage (TLS) в CGO:** C-библиотека сохраняет состояние в потоко-локальных переменных (`__thread` или `pthread_key_create`). Если вызвать функцию C из одной горутины, а затем продолжить на другом потоке M, состояние будет потеряно или повреждено.
2. **Системные вызовы ядра, меняющие атрибуты треда:** `prctl()`, `setpriority()`, `sched_setaffinity()`.
3. **Безопасное освобождение:** Если горутина восстанавливает состояние потока, она обязана вызвать парный `runtime.UnlockOSThread()`.

## Решение по шагам

1. Пишем функцию, использующую системный вызов `setpriority` для изменения приоритета (nice) текущего потока.
2. Используем `LockOSThread()` для гарантии, что приоритет изменится именно у нужного потока.
3. Восстанавливаем приоритет перед `UnlockOSThread()`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"syscall"
)

func setThreadNice(priority int) error {
	tid := syscall.Gettid()
	// Изменение приоритета (nice) для текущего потока ядра Linux
	err := syscall.Setpriority(syscall.PRIO_PROCESS, tid, priority)
	return err
}

func main() {
	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()

		// 1. Блокируем горутину на текущем потоке ОС
		runtime.LockOSThread()
		defer runtime.UnlockOSThread()

		tid := syscall.Gettid()
		fmt.Printf("Поток TID %d: установка nice = 10 (пониженный приоритет)\n", tid)

		if err := setThreadNice(10); err != nil {
			fmt.Printf("Ошибка setpriority: %v\n", err)
			return
		}

		prio, err := syscall.Getpriority(syscall.PRIO_PROCESS, tid)
		if err == nil {
			fmt.Printf("Поток TID %d: текущий nice = %d\n", tid, prio)
		}
	}()

	wg.Wait()
	fmt.Println("Операция с потоком ОС завершена успешно.")
}
```

ℹ️ Управление приоритетом потока ОС через LockOSThread

**`Терминал`**

```bash

# Поток TID 12345: текущий nice = 10
```

## Под капотом

`LockOSThread` и `UnlockOSThread` поддерживают счетчик вложенности: если `LockOSThread()` вызван трижды, требуется три вызова `UnlockOSThread()`, чтобы поток M снова стал доступен для других горутин.

## Подводные камни

Если вызвать `LockOSThread()` и передать управление другой горутине через канал, не освободив поток, поток M зависнет в ожидании возврата управления, уменьшая доступное число активных воркеров.

## На собеседовании

**Вопрос с собеседования:** Что произойдет с потоком ОС `M`, если горутина вызвала `runtime.LockOSThread()`, но завершила свое выполнение, забыв вызвать `runtime.UnlockOSThread()`?
**Ответ:** Рантайм Go отслеживает факт гибели горутины с неснятым локом потока.
Так как поток ОС мог быть модифицирован (изменены TLS-переменные, приоритет, маска сигналов, пространство имен), рантайм **не имеет права вернуть этот поток в пул свободных потоков `sched.midle`**, иначе другая горутина унаследует грязное состояние.
Поэтому рантайм принудительно завершает этот поток ОС (`pthread_exit()`), а при необходимости создает новый чистый поток M.
