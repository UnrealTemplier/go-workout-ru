# Эмуляция старого Go: демонстрация кооперативного вытеснения

## Условие

**Кооперативное вытеснение (Эмуляция старого Go)**: До Go 1.14 горутина могла выполняться вечно, если в ней не было вызовов функций (нет точек прерывания). Напиши `for {}` (пустой бесконечный цикл). В Go 1.13 эта горутина захватила бы `P` навсегда.

## Теория

Кооперативное вытеснение полагается на добровольное сотрудничество кода с рантаймом:
- Вызовы функций;
- Каналы;
- Системные вызовы;
- Вызовы `runtime.Gosched()`.

Если код не совершает ни одного из этих действий, в старых версиях Go он полностью блокировал планировщик. Понимание этого исторического контекста необходимо для понимания архитектуры современного планировщика Go 1.22+.

## Решение по шагам

1. Создаем программу, эмулирующую кооперативную передачу через явный `Gosched()`.
2. Показываем разницу в распределении времени между горутинами с уступкой процессора и без нее.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func cooperativeWorker(id int, stop *bool, counter *uint64) {
	for !*stop {
		*counter++
		if *counter%1000000 == 0 {
			runtime.Gosched() // Кооперативная передача управления
		}
	}
}

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Кооперативное распределение на GOMAXPROCS=1...")

	stop := false
	var c1, c2 uint64

	go cooperativeWorker(1, &stop, &c1)
	go cooperativeWorker(2, &stop, &c2)

	time.Sleep(200 * time.Millisecond)
	stop = true
	time.Sleep(50 * time.Millisecond)

	fmt.Printf("Итераций Worker 1: %d\n", c1)
	fmt.Printf("Итераций Worker 2: %d\n", c2)
	fmt.Println("Обе горутины получили справедливое время CPU благодаря точкам уступки.")
}
```

ℹ️ Кооперативное распределение времени выполнения

**`Терминал`**

```bash
go run main.go
# Вывод демонстрирует сопоставимый объем работы у обоих воркеров:
# Кооперативное распределение на GOMAXPROCS=1...
# Итераций Worker 1: 34000000
# Итераций Worker 2: 33000000
# Обе горутины получили справедливое время CPU благодаря точкам уступки.
```

## Под капотом

В функции `goschedImpl()` рантайм сбрасывает текущий тайм-слайс процессора `pp.schedtick++`, предотвращая монополизацию ресурсов.

## Подводные камни

Надежда только на `runtime.Gosched()` в критичных кодовых базах ненадежна: если разработчик забудет вставить вызов в длинный алгоритм, горутина снова начнет вызывать задержки.

## На собеседовании

**Вопрос с собеседования:** Почему вызов `runtime.Gosched()` не гарантирует немедленного запуска конкретной другой горутины?
**Ответ:** Потому что `Gosched()` только помещает текущую горутину в GRQ и запускает стандартный алгоритм планирования `schedule()`.
Планировщик выбирает следующую задачу по стандартным приоритетам:
1) Проверяет `runnext`;
2) Проверяет локальную очередь `LRQ`;
3) Проверяет `GRQ`;
4) Выполняет `netpoll` или `work stealing`.
Какая именно горутина запустится следующей, зависит от текущего состояния очередей всех P.
