# Механизм runtime.Gosched(): добровольная уступка процессора против time.Sleep(0)

## Условие

**Gosched()**: Вызовите `runtime.Gosched()` для явной передачи управления планировщику. Сравните с `time.Sleep(0)`.

## Теория

Функция `runtime.Gosched()` явно передает управление планировщику Go:
- Текущая горутина переводится из статуса `_Grunning` в `_Grunnable`.
- Она помещается в **конец Глобальной Очереди (GRQ)** (`sched.runq`), освобождая текущий процессор P.
- Планировщик немедленно выбирает другую готовую задачу из очереди.

В отличие от `Gosched()`, вызов `time.Sleep(0)` или `time.Sleep(1)` регистрирует таймер в куче `p.timers`, переводит горутину в статус `_Gwaiting` и требует последующего пробуждения по таймеру, что значительно дороже по накладным расходам.

## Решение по шагам

1. Создаем две горутины на `GOMAXPROCS=1`.
2. В цикле вызываем `runtime.Gosched()`.
3. Наблюдаем честное чередование вычислений.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func worker(name string, wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 1; i <= 3; i++ {
		fmt.Printf("Горутина %s: шаг %d\n", name, i)
		runtime.Gosched() // Добровольная уступка кванта времени
	}
}

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("GOMAXPROCS = 1: тестирование runtime.Gosched()...")

	var wg sync.WaitGroup
	wg.Add(2)

	go worker("A", &wg)
	go worker("B", &wg)

	wg.Wait()
	fmt.Println("Работа завершена.")
}
```

ℹ️ Кооперативное чередование горутин через runtime.Gosched

**`Терминал`**

```bash
go run main.go
# Вывод демонстрирует строгое чередование:
# GOMAXPROCS = 1: тестирование runtime.Gosched()...
# Горутина A: шаг 1
# Горутина B: шаг 1
# Горутина A: шаг 2
# Горутина B: шаг 2
# Горутина A: шаг 3
# Горутина B: шаг 3
# Работа завершена.
```

## Под капотом

Внутри `src/runtime/proc.go` функция `gosched_m(gp)` переключает контекст на `g0`, вызывает `casgstatus(gp, _Grunning, _Grunnable)`, помещает `gp` в глобальную очередь через `globrunqput(gp)` и вызывает `schedule()`. То, что горутина помещается именно в GRQ, а не в локальную очередь, гарантирует, что другие горутины на текущем P гарантированно получат процессор.

## Подводные камни

Использование `runtime.Gosched()` в качестве инструмента синхронизации (Spinlock) — антипаттерн, приводящий к 100% утилизации CPU. Для синхронизации всегда используйте каналы, `sync.WaitGroup` или мьютексы.

## На собеседовании

**Вопрос с собеседования:** Куда именно планировщик Go помещает горутину, вызвавшую `runtime.Gosched()` — в LRQ текущего P или в GRQ?
**Ответ:** Строго в **Глобальную Очередь (GRQ)** (`sched.runq`).
Это осознанное архитектурное решение: если бы `Gosched()` возвращал горутину в начало или конец локальной очереди текущего `P`, а других горутин на этом `P` не было, текущая горутина мгновенно запустилась бы снова, сведя уступку процессора к нулю.
Помещение в GRQ позволяет другим процессорам `P` украсть ее или дает текущему `P` возможность сначала разобрать все локальные задачи.
