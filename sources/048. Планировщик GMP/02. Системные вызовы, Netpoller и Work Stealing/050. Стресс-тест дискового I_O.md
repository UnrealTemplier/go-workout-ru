# Стресс-тест дискового I/O: генерация потоков ОС при чтении больших объемов данных

## Условие

Напишите программу, которая делает длинный `syscall` (чтение 1 ГБ с диска). Покажите в `schedtrace`, что M отключается от P (`handoffp`). Объясните механизм `entersyscall` / `exitsyscall` и зачем P передаётся другому M.

## Теория

При параллельном синхронном чтении сотен файлов с диска каждый блокирующийся в ядре поток `M` заставляет рантайм создавать новый `M` для поддержания квоты `GOMAXPROCS`.
Флаг `GODEBUG=schedtrace=200` наглядно показывает рост поля `threads`:
- Изначально: `threads = GOMAXPROCS + 3..4`
- Под нагрузкой: `threads = GOMAXPROCS + N (активных читателей)`
- После завершения: потоки M не уничтожаются мгновенно, а засыпают в пуле `sched.midle`.

## Решение по шагам

1. Создаем тестовые файлы на диске.
2. Запускаем 30 параллельных горутин чтения.
3. Отслеживаем изменение параметра `threads` в выводе `GODEBUG=schedtrace=200`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"os"
	"runtime"
	"sync"
	"time"
)

func makeDummyFile(name string, size int) {
	data := make([]byte, size)
	rand.Read(data)
	os.WriteFile(name, data, 0644)
}

func main() {
	runtime.GOMAXPROCS(2)
	const fileCount = 20
	files := make([]string, fileCount)

	for i := 0; i < fileCount; i++ {
		fn := fmt.Sprintf("tmp_bench_%d.dat", i)
		makeDummyFile(fn, 2*1024*1024)
		files[i] = fn
		defer os.Remove(fn)
	}

	fmt.Println("Запуск 20 параллельных операций чтения с диска...")

	var wg sync.WaitGroup
	wg.Add(fileCount)

	for i := 0; i < fileCount; i++ {
		go func(path string) {
			defer wg.Done()
			b, err := os.ReadFile(path)
			if err == nil {
				_ = len(b)
			}
		}(files[i])
	}

	time.Sleep(100 * time.Millisecond)
	wg.Wait()
	fmt.Println("Все операции чтения завершены.")
}
```

ℹ️ Массовое дисковое чтение и наблюдение за threads

**`Терминал`**

```bash
GODEBUG=schedtrace=100 go run main.go
# Наблюдайте рост счетчика threads в выводе schedtrace
```

## Под капотом

Максимальное количество потоков ОС, которое Go соглашается создать перед аварийным завершением процесса, контролируется функцией `debug.SetMaxThreads(n)`. По умолчанию этот лимит равен 10 000 потоков.

## Подводные камни

Если сервис без ограничений обращается к медленному диску или сетевому хранилищу NFS, рост потоков M исчерпает лимиты ОС (`threads-max`), вызвав фатальную ошибку.

## На собеседовании

**Вопрос с собеседования:** Какой дефолтный лимит потоков ОС (M) установлен в рантайме Go и как защитить сервис от его исчерпания?
**Ответ:** Дефолтный лимит составляет **10 000 системных потоков ОС**.
Для защиты:
1) Ограничивать параллелизм дисковых операций через семафор (`golang.org/x/sync/semaphore`) или пул горутин фиксированного размера (например, 10–20 воркеров);
2) Использовать `debug.SetMaxThreads()` для ранней детекции аномалий на тестовых стендах;
3) Никогда не выполнять блокирующий I/O в неограниченных `go func()` внутри веб-хендлеров.
