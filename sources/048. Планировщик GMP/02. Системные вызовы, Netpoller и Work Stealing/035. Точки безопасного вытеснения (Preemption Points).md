# Точки безопасного вытеснения (Preemption Points): пролог функций и компилятор Go

## Условие

**Preemption points**: Изучите, где runtime вставляет проверки на preemption (function prologue, loop backedges). Напишите код, который избегает этих точек (tight loop без вызовов).

## Теория

Компилятор Go (`cmd/compile`) отвечает за генерацию безопасных точек остановки.
В классической модели компилятор вставляет в пролог каждой функции:
```assembly
CMPQ SP, 16(R14)   // Сравнение указателя стека с g.stackguard0
JLS  morestack      // Если SP <= stackguard0, переход на выделение стека
```
Фокус архитектуры Go в том, что планировщик использует ту же самую проверку для кооперативного вытеснения!
Когда рантайм хочет вытеснить горутину, он присваивает:
`gp.stackguard0 = stackPreempt` (константа `0xfffffffffffffff0`).
При следующем вызове любой функции условие `SP <= stackguard0` гарантированно срабатывает. Вызывается `runtime.morestack()`, которая обнаруживает флаг прерывания, сохраняет контекст горутины и вызывает `runtime.goschedImpl()`.

## Решение по шагам

1. Напишем простую функцию и скомпилируем ее в ассемблер: `go tool compile -S main.go`.
2. Найдем инструкции сравнения со `stackguard0` в начале функции.
3. Разберем логику работы `runtime.morestack`.

## Код решения

**`main.go`**

```go
package main

import "fmt"

//go:noinline
func calculate(a, b int) int {
	return a*a + b*b
}

func main() {
	res := calculate(3, 4)
	fmt.Printf("Результат: %d\n", res)
}
```

ℹ️ Функция для ассемблерной инспекции пролога

**`Терминал`**

```bash
go tool compile -S main.go | grep -A 5 'TEXT.*calculate'
# Пример вывода ассемблера Plan 9:
# main.calculate STEXT ...
#   0x0000 00000 (main.go:6)	CMPQ	SP, 16(R14)
#   0x0004 00004 (main.go:6)	PCDATA	$0, $-2
#   0x0004 00004 (main.go:6)	JLS	28
#   ...
#   0x001c 00028 (main.go:6)	CALL	runtime.morestack_noctxt(SB)
```

## Под капотом

Регистр `R14` в архитектуре amd64 в Go 1.17+ зарезервирован под хранение указателя на текущую горутину `g` (register-based calling convention). Смещение `16(R14)` указывает точно на поле `g.stackguard0`. Проверка занимает всего 2 процессорные инструкции и практически не влияет на скорость вызова функций.

## Подводные камни

Если функция заинлайнена компилятором (`inlined`), ее пролог устраняется, и проверка `morestack` исчезает. Именно поэтому в циклах с инлайнингом кооперативное вытеснение до Go 1.14 не срабатывало.

## На собеседовании

**Вопрос с собеседования:** Каким образом планировщик Go утилизирует проверку переполнения стека (`morestack`) для кооперативного вытеснения горутин?
**Ответ:** Поле `g.stackguard0` хранит границу безопасного использования стека.
Когда планировщик хочет вытеснить горутину (например, при вызове `Gosched()` или по требованию GC), он искусственно завышает эту границу, записывая в `stackguard0` специальное значение `stackPreempt`.
В начале следующей вызываемой функции процессор проверяет `SP <= stackguard0`. Условие неизбежно выполняется, и поток переходит в функцию `morestack()`.
Внутри `morestack()` рантайм проверяет: если `stackguard0 == stackPreempt`, это не настоящее переполнение стека, а запрос на вытеснение. Рантайм паркует горутину и запускает `schedule()`.
