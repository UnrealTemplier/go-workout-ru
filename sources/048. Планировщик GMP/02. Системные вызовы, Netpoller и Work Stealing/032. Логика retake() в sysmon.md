# Логика retake() в sysmon: отзыв процессора P у зависших вычислений

## Условие

**[sysmon: Retaking Bindings]**: Если горутина выполняет CPU-bound работу без вызова функций (например, `for i := 0; i < 1e10; i++ {}`), как `sysmon` понимает, что нужно вытеснить (preempt) эту горутину? Напиши такой цикл и проверь, не блокирует ли он другие горутины (работает ли планировщик).

## Теория

Функция `retake(now)` внутри потока `sysmon` — главный механизм контроля зависших горутин и системных вызовов.
При каждом проходе `sysmon` обходит все P:
1. Если `p.status == _Prunning`: проверяется длительность непрерывного исполнения `pd.schedwhen`. Если она превышает 10 мс, вызывается `preemptone(pp)`, который инициирует асинхронное вытеснение через `SIGURG`.
2. Если `p.status == _Psyscall`: проверяется счетчик `syscalltick`. Если вызов длится дольше 10 мс или в очереди этого P есть готовые горутины, `sysmon` вызывает `handoffp(pp)`, отбирая P у блокирующего потока M.

## Решение по шагам

1. Создаем программу, где одна горутина исполняет непрерывный математический цикл.
2. Вторая горутина фиксирует отметки времени своего пробуждения.
3. Убеждаемся, что интервалы задержек второй горутины не превышают квант вытеснения (~10-20 мс).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("GOMAXPROCS = 1. Тестирование кванта времени вытеснения sysmon...")

	stop := false

	// Горутина 1: непрерывный тяжелый CPU цикл
	go func() {
		var x uint64
		for !stop {
			x = (x + 13) * 7
		}
		_ = x
	}()

	// Горутина 2: замеряет интервалы между квантами
	delays := make([]time.Duration, 0, 5)
	start := time.Now()
	for i := 0; i < 5; i++ {
		time.Sleep(1 * time.Millisecond)
		now := time.Now()
		delays = append(delays, now.Sub(start))
		start = now
	}

	stop = true
	time.Sleep(20 * time.Millisecond)

	fmt.Println("Интервалы между передачами управления:")
	for i, d := range delays {
		fmt.Printf("  Шаг %d: %v\n", i+1, d)
	}
}
```

ℹ️ Фиксация интервалов переключения горутин по таймеру sysmon

**`Терминал`**


## Под капотом

В функции `retake()` в `src/runtime/proc.go` условие вытеснения выглядит так:
`if s == _Prunning { if pd.schedwhen + 10*1000*1000 < now { preemptone(pp) } }`.
Константа \(10 \times 10^6\) наносекунд (10 мс) определяет базовый тайм-слайс планировщика Go.

## Подводные камни

В виртуализированных средах с переподпиской CPU (CPU overcommit) физическое ядро может быть отобрано гипервизором, из-за чего реальный интервал `retake` может растянуться до 50–100 мс.

## На собеседовании

**Вопрос с собеседования:** Какова базовая длительность кванта времени (time-slice) горутины в планировщике Go и почему выбран именно такой интервал?
**Ответ:** Квант времени составляет ровно **10 миллисекунд** (проверяется потоком `sysmon`).
Этот компромисс выбран для баланса:
- Слишком маленький квант (например, 1 мс) создавал бы чрезмерный оверхед на частые сигналы `SIGURG`, переключения контекста и сброс кэшей CPU;
- Слишком большой квант (например, 100 мс) приводил бы к заметным «заиканиям» (jitter) и росту p99/p999 latency при наличии тяжелых вычислительных горутин.
