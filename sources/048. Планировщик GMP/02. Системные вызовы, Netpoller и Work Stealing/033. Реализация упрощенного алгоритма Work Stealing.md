# Реализация упрощенного алгоритма Work Stealing на чистом Go

## Условие

Реализуйте упрощённый алгоритм work stealing на чистом Go (без `runtime`): N «воркеров» с локальными deque (push/pop снизу, steal сверху). Покажите, почему steal сверху уменьшает contention.

## Теория

Для глубокого понимания механики Work Stealing полезно реализовать его модель на прикладном уровне Go.
Модель включает:
1. \(N\) независимых воркеров (эмулирующих потоки \(M\) и процессоры \(P\));
2. Локальную двустороннюю очередь (Deque) у каждого воркера:
   - Владелец кладет и забирает задачи с **хвоста** (LIFO) для максимальной кэш-локальности;
   - Другие воркеры при простое крадут задачи с **головы** (FIFO) чужой очереди для минимизации конфликтов с владельцем.

## Решение по шагам

1. Создаем структуру `Deque` с защитой мьютексом (или атомарным CAS).
2. Реализуем пул из 4 воркеров.
3. Помещаем 100 задач только в очередь воркера 0.
4. Воркеры 1, 2, 3 обнаруживают пустые очереди и успешно воруют задачи у воркера 0.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"sync/atomic"
	"time"
)

type Task func()

type WorkQueue struct {
	mu    sync.Mutex
	tasks []Task
}

func (q *WorkQueue) Push(t Task) {
	q.mu.Lock()
	q.tasks = append(q.tasks, t)
	q.mu.Unlock()
}

func (q *WorkQueue) Pop() (Task, bool) {
	q.mu.Lock()
	defer q.mu.Unlock()
	if len(q.tasks) == 0 {
		return nil, false
	}
	// Владелец берет с хвоста (LIFO)
	last := len(q.tasks) - 1
	t := q.tasks[last]
	q.tasks = q.tasks[:last]
	return t, true
}

func (q *WorkQueue) StealHalf() []Task {
	q.mu.Lock()
	defer q.mu.Unlock()
	n := len(q.tasks)
	if n <= 1 {
		return nil
	}
	// Вор забирает половину с головы (FIFO)
	stealCount := (n + 1) / 2
	stolen := make([]Task, stealCount)
	copy(stolen, q.tasks[:stealCount])
	q.tasks = q.tasks[stealCount:]
	return stolen
}

func main() {
	const numWorkers = 4
	queues := make([]*WorkQueue, numWorkers)
	for i := 0; i < numWorkers; i++ {
		queues[i] = &WorkQueue{}
	}

	var processed [numWorkers]int64
	var wg sync.WaitGroup
	wg.Add(numWorkers)

	const totalTasks = 120
	// Загружаем все задачи только в очередь воркера 0
	for i := 0; i < totalTasks; i++ {
		taskID := i
		queues[0].Push(func() {
			time.Sleep(1 * time.Millisecond)
			_ = taskID
		})
	}

	stop := int32(0)
	for id := 0; id < numWorkers; id++ {
		go func(wid int) {
			defer wg.Done()
			for atomic.LoadInt32(&stop) == 0 {
				// 1. Пытаемся взять свою задачу
				if task, ok := queues[wid].Pop(); ok {
					task()
					atomic.AddInt64(&processed[wid], 1)
					continue
				}

				// 2. Кража работы: выбираем случайную чужую очередь
				victim := rand.Intn(numWorkers)
				if victim != wid {
					stolen := queues[victim].StealHalf()
					if len(stolen) > 0 {
						for _, t := range stolen {
							queues[wid].Push(t)
						}
						continue
					}
				}
				time.Sleep(500 * time.Microsecond)
			}
		}(id)
	}

	time.Sleep(200 * time.Millisecond)
	atomic.StoreInt32(&stop, 1)
	wg.Wait()

	fmt.Println("Результаты распределения работы через Work Stealing:")
	var total int64
	for i := 0; i < numWorkers; i++ {
		cnt := atomic.LoadInt64(&processed[i])
		total += cnt
		fmt.Printf("  Воркер %d обработал: %d задач\n", i, cnt)
	}
	fmt.Printf("Всего обработано: %d / %d\n", total, totalTasks)
}
```

## Под капотом

Классический алгоритм Work Stealing (Chase-Lev deque) оптимизирует параллельный доступ: владелец использует неатомарные операции добавления/извлечения в конец массива, а воры используют CAS-инструкцию для извлечения из начала. Конкуренция возникает только тогда, когда в очереди остается последний элемент.

## Подводные камни

В наивной реализации без рандомизации жертвы воры могут одновременно пытаться красть у одного и того же воркера, вызывая конкуренцию за мьютекс (thundering herd).

## На собеседовании

**Вопрос с собеседования:** Почему владелец очереди в Work Stealing забирает задачи в порядке LIFO (с конца), а воры крадут задачи в порядке FIFO (с начала)?
**Ответ:**
1) **Локальность кэша (Cache Locality):** Самая последняя добавленная задача только что работала с данными, которые еще находятся в быстрых кэшах L1/L2 процессора владельца. Исполнение LIFO минимизирует промахи кэша;
2) **Размер поддерева задач:** Самые старые задачи (в начале очереди FIFO) обычно представляют собой крупные родительские задачи, способные породить много новых подзадач. Украдя старую задачу, ворующий процессор получает большой кусок долгой самостоятельной работы;
3) **Разделение точек доступа:** Владелец работает с хвостом (`tail`), а воры с головой (`head`). Это сводит конкуренцию за доступ к очереди практически к нулю.
