# Work Stealing в действии: перераспределение очередей при неравномерной нагрузке

## Условие

**Work stealing в действии.**: Запустите N горутин с неравномерной нагрузкой (часть считает в цикле, часть сразу завершается). Включите трассировку (`go tool trace`) и визуально найдите моменты, когда P ворует горутины из чужих локальных очередей.

## Теория

При неравномерной нагрузке одни горутины завершаются за миллисекунды, а другие выполняют долгие вычисления.
Без Work Stealing ядра, завершившие быстрые задачи, простаивали бы (Idle CPU), пока перегруженные ядра страдали бы от длинных очередей.
Work Stealing динамически выравнивает длину очередей всех P, стремясь к равновесию.

## Решение по шагам

1. Запускаем тест с неравномерными задачами (от 1 мс до 100 мс).
2. Записываем трассировку `trace.out`.
3. Анализируем сбалансированность использования процессоров P.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"runtime"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Println("Тестирование Work Stealing при неравномерной нагрузке...")

	var wg sync.WaitGroup
	const total = 400
	wg.Add(total)

	for i := 0; i < total; i++ {
		go func(id int) {
			defer wg.Done()
			// Неравномерная длительность нагрузки
			duration := time.Duration(1+rand.Intn(15)) * time.Millisecond
			time.Sleep(duration)
		}(i)
	}

	wg.Wait()
	fmt.Println("Все неравномерные задачи успешно обработаны.")
}
```

ℹ️ Неравномерная нагрузка и автоматическая балансировка

**`Терминал`**

```bash
go run main.go
```

## Под капотом

Каждый раз, когда `P` становится пустым, поток M инкрементирует внутренний счетчик `steal`. В трассировщике `runtime/trace` такие события помечаются как фазы кражи работы, обеспечивая полную прозрачность поведения планировщика.

## Подводные камни

Если задачи микроскопические (<1 микросекунды), стоимость CAS-инструкций при краже работы может превышать выигрыш от параллелизма.

## На собеседовании

**Вопрос с собеседования:** В каком порядке поток M ищет горутину для выполнения, когда его локальная очередь опустела?
**Ответ:** Порядок строго зафиксирован в функции `runtime.findrunnable()`:
1. Проверка слота `runnext` и локальной очереди текущего `P`;
2. Проверка Глобальной Очереди (`sched.runq`) с захватом `sched.lock`;
3. Проверка сетевого поллера `netpoll(0)` на наличие готовых I/O событий;
4. Попытка украсть половину очереди у случайного чужого `P` (`runqsteal`);
5. Повторный опрос сетевого поллера с блокировкой (`netpoll(delay)`);
6. Усыпление потока M и переход в спящий пул `sched.midle`.
