# Обнаружение утечек горутин (Goroutine Leaks) через runtime.NumGoroutine и pprof

## Условие

**Goroutine leaks detection**: Создайте goroutine leak (заблокированная горутина). Используйте `runtime.NumGoroutine()` и `pprof goroutine profile` для обнаружения.

## Теория

Утечка горутин (Goroutine Leak) — одна из наиболее коварных проблем в Go.
Поскольку горутины не уничтожаются сборщиком мусора, пока они заблокированы (даже если на них больше нет внешних ссылок), любая горутина, зависшая на чтении из канала, невозвращенном сетевом запросе или дедлоке мьютекса, удерживает:
1. Стек в куче (от 2 до 8 КБ);
2. Все замыкания и переменные, на которые ссылается ее стек.

При высоком RPS даже 1 зависшая горутина на 100 запросов приведет к утечке сотен тысяч горутин и неминуемому OOM (Out Of Memory) через несколько суток работы сервиса.

## Решение по шагам

1. Создаем функцию с преднамеренной утечкой (запись в небуферизованный канал без читателя).
2. Замеряем `runtime.NumGoroutine()` до и после вызова.
3. Проверяем обнаружение утечки.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// leakingTask порождает горутину, которая навсегда зависает на отправке
func leakingTask() {
	ch := make(chan int) // Небуферизованный канал
	go func() {
		ch <- 42 // Никто никогда не прочитает отсюда
	}()
}

func main() {
	fmt.Printf("До вызовов: Горутин = %d\n", runtime.NumGoroutine())

	for i := 0; i < 50; i++ {
		leakingTask()
	}

	time.Sleep(50 * time.Millisecond)
	leakedCount := runtime.NumGoroutine()
	fmt.Printf("После 50 вызовов leakingTask: Горутин = %d\n", leakedCount)

	if leakedCount >= 50 {
		fmt.Println("⚠️ Зафиксирована утечка 50 горутин в состоянии _Gwaiting [chan send]!")
	}
}
```

ℹ️ Детекция утечки горутин через runtime.NumGoroutine

**`Терминал`**

```bash
go run main.go
# Вывод:
# До вызовов: Горутин = 1
# После 50 вызовов leakingTask: Горутин = 51
# ⚠️ Зафиксирована утечка 50 горутин в состоянии _Gwaiting [chan send]!
```

## Под капотом

Зависшая горутина сохраняет статус `_Gwaiting` в поле `atomicstatus`. Поскольку ее структура `g` закреплена в очереди ожидания `waitq` канала, сборщик мусора рассматривает корень стека этой горутины как активный (Root Object), запрещая сборку мусора для всех привязанных данных.

## Подводные камни

В unit-тестах для предотвращения утечек в продакшене используйте библиотеку `go.uber.org/goleak`. Вызов `defer goleak.VerifyNone(t)` гарантирует, что тестовый кейс завершил все порожденные горутины.

## На собеседовании

**Вопрос с собеседования:** Спасет ли Garbage Collector горутину, которая заблокирована на чтении из закрытой области видимости (например, канал локален для функции и больше никем не используется)?
**Ответ:** **НЕТ, не спасет!** Сборщик мусора Go не умеет определять, что горутина «больше никогда не проснется».
Пока горутина находится в статусе `_Gwaiting`, рантайм Go рассматривает ее дескриптор `g` как постоянный корень (GC Root). Горутина и все объекты, на которые ссылается ее стек, будут жить в оперативной памяти вечно, пока не завершится весь процесс операционной системы.
