# Сглаживание всплесков нагрузки (Burst): Worker Pool против взрывного спавна горутин

## Условие

Напишите программу, которая создаёт «всплеск» goroutine (burst): 10 000 задач кидаются в пул из 4 P. Соберите трассировку (`go tool trace`) и найдите моменты, когда P забирает задачи из глобальной очереди (`globrunq`) vs. из локальной.

## Теория

При внезапном всплеске нагрузки (Burst в 10 000+ запросов) неконтролируемый запуск `go func()` приводит к:
1. Заполнению всех LRQ (по 256 задач) и массовому сбросу тысяч задач в GRQ;
2. Нагрузке на глобальный спинлок `sched.lock`;
3. Взрывному выделению оперативной памяти под новые стеки горутин (10 000 * 2 КБ = 20+ МБ);
4. Нагрузке на GC при их последующей утилизации.

Паттерн **Worker Pool** фиксированного размера (например, кратного `GOMAXPROCS`) держит нагрузку на планировщик стабильной, исключает скачки памяти и аллокаций.

## Решение по шагам

1. Создаем тест с неуправляемым спавном 10 000 горутин.
2. Создаем альтернативный Worker Pool с 8 воркерами.
3. Сравниваем время выполнения и количество аллокаций памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func runBurstUncontrolled(tasks int) time.Duration {
	var wg sync.WaitGroup
	wg.Add(tasks)
	start := time.Now()

	for i := 0; i < tasks; i++ {
		go func(id int) {
			defer wg.Done()
			var acc int
			for j := 0; j < 10000; j++ {
				acc += j
			}
			_ = acc
		}(i)
	}
	wg.Wait()
	return time.Since(start)
}

func runWorkerPool(tasks int, workers int) time.Duration {
	jobs := make(chan int, 1000)
	var wg sync.WaitGroup
	start := time.Now()

	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for range jobs {
				var acc int
				for j := 0; j < 10000; j++ {
					acc += j
				}
				_ = acc
			}
		}()
	}

	for i := 0; i < tasks; i++ {
		jobs <- i
	}
	close(jobs)
	wg.Wait()
	return time.Since(start)
}

func main() {
	runtime.GOMAXPROCS(4)
	const tasks = 20000

	fmt.Printf("Сравнение обработки всплеска из %d задач:\n", tasks)

	d1 := runBurstUncontrolled(tasks)
	fmt.Printf("1. Неуправляемый go func():  %v\n", d1)

	d2 := runWorkerPool(tasks, runtime.GOMAXPROCS(0)*2)
	fmt.Printf("2. Контролируемый WorkerPool: %v\n", d2)
}
```

ℹ️ Сравнение всплеска горутин и Worker Pool

**`Терминал`**

```bash
go run main.go
# Пример вывода:
# Сравнение обработки всплеска из 20000 задач:
# 1. Неуправляемый go func():  14.2ms
# 2. Контролируемый WorkerPool: 6.8ms  (более чем в 2 раза быстрее)
```

## Под капотом

В Worker Pool воркеры постоянно переиспользуют уже прогретые стеки и кэши процессора. При спавне 20 000 новых `go func()` рантайму приходится 20 000 раз вызывать `newproc()`, доставать объекты из `gFree`, очищать стеки и переполнять кольцевые буферы очереди, что создает паразитный CPU overhead.

## Подводные камни

Слишком маленький размер очереди задач в Worker Pool может привести к блокировке продюсеров (Backpressure). Всегда проектируйте размер очереди с учетом максимального пикового всплеска трафика.

## На собеседовании

**Вопрос с собеседования:** Если горутины такие легковесные (~2 КБ), почему в HighLoad системах не рекомендуют спавнить `go func()` на каждый входящий запрос без ограничений?
**Ответ:** Потому что закон сохранения ресурсов непреложен:
1) **Память:** 100 000 внезапных запросов потребуют >200 МБ только под стеки горутин;
2) **Планировщик:** Перегрузка очередей LRQ приводит к борьбе за `sched.lock` при сбросе в GRQ;
3) **GC:** Сборщику мусора приходится сканировать стеки 100 000 горутин, что многократно увеличивает время GC Mark;
4) **CFS Throttling:** Неуправляемый спавн создает конкуренцию за CPU, вызывая спайки задержек p99. Ограничение конкурентности через Worker Pool или семафор гарантирует стабильный SLA.
