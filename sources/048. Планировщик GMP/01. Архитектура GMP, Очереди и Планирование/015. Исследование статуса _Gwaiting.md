# Исследование статуса _Gwaiting и анализ стека спящей горутины

## Условие

Создайте программу с одной goroutine, которая спит 10 секунд (`time.Sleep`). В другой goroutine выведите состояние всех G через `runtime.Stack()` или `GODEBUG=scheddetail=1`. Найдите статус спящей goroutine (`Gwaiting`) и объясните, в какой очереди она находится.

## Теория

Жизненный цикл горутины в Go определяется перечислением состояний в `src/runtime/runtime2.go`:
- `_Gidle` (0): горутина только что выделена;
- `_Grunnable` (1): горутина находится в очереди выполнения и ждет потока M;
- `_Grunning` (2): горутина выполняется прямо сейчас на потоке M;
- `_Gsyscall` (3): горутина выполняет системный вызов;
- `_Gwaiting` (4): горутина заблокирована (на таймере `time.Sleep`, канале, мьютексе или сетевом сокете);
- `_Gdead` (6): горутина завершила выполнение и находится в пуле `gFree`.

Когда горутина вызывает `time.Sleep`, она переводится в `_Gwaiting`, удаляется из всех очередей выполнения (LRQ/GRQ) и привязывается к таймеру рантайма.

## Решение по шагам

1. Запускаем горутину, которая засыпает на 10 секунд через `time.Sleep`.
2. В главной горутине получаем дамп всех горутин с помощью `runtime.Stack()`.
3. Анализируем статус заблокированной горутины и причину ожидания (`sleep`).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"time"
)

func sleepingWorker() {
	// Горутина переходит в состояние _Gwaiting с причиной "sleep"
	time.Sleep(10 * time.Second)
}

func main() {
	go sleepingWorker()

	// Даем горутине время перейти в состояние сна
	time.Sleep(100 * time.Millisecond)

	buf := make([]byte, 16384)
	// runtime.Stack(buf, true) — true означает дамп ВСЕХ горутин программы
	n := runtime.Stack(buf, true)

	fmt.Println("=== Дамп стеков всех горутин рантайма ===")
	fmt.Printf("%s\n", buf[:n])
	fmt.Printf("Всего горутин: %d\n", runtime.NumGoroutine())
	os.Exit(0)
}
```

ℹ️ Снятие полного дампа стеков и статусов через runtime.Stack

**`Терминал`**

```bash
go run main.go
# В дампе отчетливо виден статус спящей горутины:
# goroutine 18 [sleep]:
# time.Sleep(0x2540be400)
#         .../src/runtime/time.go:195
# main.sleepingWorker()
#         .../main.go:11
```

## Под капотом

При вызове `time.Sleep()` горутина вызывает `gopark(resetForSleep, ...)`. Ее контекст регистров сохраняется в `gp.sched`, а статус атомарно меняется с `_Grunning` на `_Gwaiting`. В Go 1.14+ таймеры встроены непосредственно в структуру `P` (массив `p.timers`). Поток M не тратит ресурсы на спящую горутину и сразу берет следующую готовую задачу из LRQ.

## Подводные камни

Спящие горутины не потребляют процессорное время, но удерживают свой стек в памяти (~2-4 КБ). Если приложение в цикле порождает горутины, засыпающие на долгие таймауты, возникнет скрытая утечка памяти (Goroutine Leak).

## На собеседовании

**Вопрос с собеседования:** Где находится горутина, когда она заблокирована в `time.Sleep()`, канале или мьютексе — находится ли она в LRQ или GRQ?
**Ответ:** **Ни в одной из них!** В очередях LRQ и GRQ находятся **только** горутины в статусе `_Grunnable` (готовые к немедленному исполнению на CPU).
Заблокированная горутина находится в статусе `_Gwaiting` и привязана к конкретной структуре ожидания:
- При `time.Sleep` — в таймерной очереди процессора `P` (`p.timers`);
- При блокировке на канале — в очереди ожидания канала (`chan.recvq` или `chan.sendq`);
- При блокировке на мьютексе — в семафорном дереве ожидания `runtime.sudog`;
- При сетевом вводе/выводе — в структурах сетевого поллера ядра ОС (`epoll/kqueue`).
