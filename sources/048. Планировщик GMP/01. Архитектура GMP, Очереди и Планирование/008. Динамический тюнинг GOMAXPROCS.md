# Динамический тюнинг GOMAXPROCS и влияние на CPU-bound параллелизм

## Условие

**GOMAXPROCS**: Изучите `runtime.GOMAXPROCS(0)`. Установите его в 1, 2, 4, `runtime.NumCPU()`. Запустите CPU-bound задачу и измерьте разницу в производительности.

## Теория

Параллельное масштабирование подчиняется **закону Амдала**: ускорение программы ограничено долей последовательного кода.
Для чисто CPU-bound задач увеличение `GOMAXPROCS` от 1 до `runtime.NumCPU()` дает почти линейный прирост производительности, пока число потоков не превысит количество физических ядер.
Превышение `NumCPU()` (например `GOMAXPROCS = NumCPU() * 2`) для CPU-bound задач контрпродуктивно, так как вызывает конкуренцию потоков ОС за одни и те же ядра процессора и частые сбросы кэшей CPU (cache misses).

## Решение по шагам

1. Напишем тестовую CPU-bound функцию (вычисление простых чисел или хеширование).
2. Запустим бенчмарк для `GOMAXPROCS = 1, 2, 4, runtime.NumCPU()`.
3. Замерим время выполнения и вычислим фактор ускорения (Speedup).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func cpuIntensiveTask(iterations int) int {
	count := 0
	for i := 2; i < iterations; i++ {
		isPrime := true
		for j := 2; j*j <= i; j++ {
			if i%j == 0 {
				isPrime = false
				break
			}
		}
		if isPrime {
			count++
		}
	}
	return count
}

func benchmark(p int, tasks int, iterations int) time.Duration {
	runtime.GOMAXPROCS(p)
	var wg sync.WaitGroup
	wg.Add(tasks)

	start := time.Now()
	for i := 0; i < tasks; i++ {
		go func() {
			defer wg.Done()
			cpuIntensiveTask(iterations)
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	numCPU := runtime.NumCPU()
	tasks := numCPU * 2
	iterations := 150000

	fmt.Printf("Бенчмарк CPU-bound нагрузки (%d задач, NumCPU=%d):\n", tasks, numCPU)

	procsToTest := []int{1, 2, 4, numCPU}
	for _, p := range procsToTest {
		if p > numCPU && p != numCPU {
			continue
		}
		duration := benchmark(p, tasks, iterations)
		fmt.Printf("  GOMAXPROCS = %2d: %v\n", p, duration)
	}
}
```

## Под капотом

При увеличении `GOMAXPROCS` операционная система планирует потоки M на разные ядра. Если ядра физические, операции выполняются параллельно. При включенном Hyper-Threading (SMT) два виртуальных ядра делят один физический конвейер инструкций и кэш L1/L2, поэтому рост производительности от дополнительных SMT-потоков обычно составляет ~20-30%, а не 100%.

## Подводные камни

В I/O-bound задачах (сетевые микросервисы, базы данных) установка `GOMAXPROCS(1)` не приводит к пропорциональному замедлению, так как горутины блокируются не на CPU, а на сетевом сокете, обслуживаемом `netpoller`.

## На собеседовании

**Вопрос с собеседования:** Имеет ли смысл устанавливать `GOMAXPROCS` выше, чем количество доступных ядер CPU?
**Ответ:** Для CPU-bound задач — практически никогда. Это приведет только к дополнительным накладным расходам на переключение контекста потоков ОС ядром Linux и деградации L1/L2/L3 кэшей процессора.
Исключение — очень редкие специфичные сценарии с большим количеством блокирующих системных вызовов файлов (не поддерживаемых epoll) или CGO-библиотек, где потоки M блокируются вне контроля планировщика Go, хотя для таких задач правильнее выносить работу в пул горутин или настраивать архитектуру.
