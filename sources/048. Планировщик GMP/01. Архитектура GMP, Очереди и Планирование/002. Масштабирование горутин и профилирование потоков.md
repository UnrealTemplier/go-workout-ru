# Масштабирование горутин и профилирование потоков ОС через GODEBUG=schedtrace

## Условие

Напишите программу, которая создаёт 10 000 goroutine, каждая из которых инкрементирует общий счётчик через `sync/atomic`. Зафиксируйте, сколько ОС-потоков создаёт рантайм (`runtime.NumGoroutine` + `runtime.NumThread` через `GODEBUG=schedtrace`). Объясните разницу.

## Теория

Горутина в Go стоит порядка 2 КБ оперативной памяти (дескриптор `runtime.g` + начальный стек). Создание 10 000 горутин требует всего ~20-30 МБ RAM. Напротив, поток ОС (Linux pthread) требует от 2 до 8 МБ стека и аллокации ресурсов ядра.
Планировщик Go использует мультиплексирование M:N (M горутин на N потоков ОС). Даже при создании 10 000 горутин количество системных потоков ОС `M` остается минимальным — обычно равным числу `P` плюс несколько вспомогательных потоков рантайма (sysmon, template M, GC workers, network poller).

Для наблюдения за внутренним состоянием рантайма используется флаг:
`GODEBUG=schedtrace=1000` (вывод состояния каждые 1000 мс) или `scheddetail=1` (детальный дамп всех G, M, P).

## Решение по шагам

1. Пишем программу, порождающую 10 000 горутин с атомарным счетчиком.
2. Используем `sync.WaitGroup` для ожидания завершения.
3. Проверяем `runtime.NumGoroutine()` до и во время спавна.
4. Запускаем бинарник с `GODEBUG=schedtrace=1000` и анализируем колонки `gomaxprocs`, `threads`, `idleprocs`, `runqueue`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

func main() {
	const total = 10000
	var counter int64
	var wg sync.WaitGroup
	wg.Add(total)

	fmt.Printf("До старта: NumGoroutine = %d, GOMAXPROCS = %d\n", runtime.NumGoroutine(), runtime.GOMAXPROCS(0))

	start := time.Now()
	for i := 0; i < total; i++ {
		go func() {
			defer wg.Done()
			atomic.AddInt64(&counter, 1)
			time.Sleep(100 * time.Millisecond)
		}()
	}

	fmt.Printf("В процессе: NumGoroutine = %d\n", runtime.NumGoroutine())
	wg.Wait()

	fmt.Printf("Готово за %v. Счетчик: %d, Итоговых Goroutines: %d\n",
		time.Since(start), atomic.LoadInt64(&counter), runtime.NumGoroutine())
}
```

## Под капотом

Строка `schedtrace` расшифровывается следующим образом:
- `SCHED Xms`: время с момента старта программы;
- `gomaxprocs=N`: количество доступных процессоров P;
- `threads=M`: общее число созданных потоков операционной системы (M);
- `idleprocs=K`: количество свободных P, у которых нет работы;
- `runqueue=Q`: число горутин в Глобальной Очереди (GRQ);
- `[n1 n2 ... nP]`: количество горутин в Локальной Очереди (LRQ) каждого конкретного P.

## Подводные камни

Если горутины совершают блокирующие CGO-вызовы или системные вызовы файлов без netpoller, рантайм отцепляет M от P (`handoffp`) и создает новый поток M. В таком сценарии `threads` может вырасти до сотен и тысяч, что приведет к исчерпанию лимита потоков ОС (`/proc/sys/kernel/threads-max`) и панике `fatal error: runtime: out of memory` или `failed to create new OS thread`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go горутина создается за микросекунды и занимает всего ~2 КБ, тогда как создание потока ОС требует мегабайтов и значительно медленнее?
**Ответ:** Поток ОС требует участия ядра Linux: выделения структур `task_struct`, страничных таблиц, сигнальных масок и виртуальной памяти под стек (от 2 до 8 МБ). Переключение контекста потоков ОС требует смены привилегий Ring 3 -> Ring 0, сброса кэшей TLB и сохранения всех регистров CPU.
Горутина — это структура пользовательского пространства (`runtime.g`). Она создается без единого системного вызова (через пул `gFree`), ее стек начинается всего с 2 КБ и динамически расширяется в куче (`runtime.morestack`). Переключение между горутинами выполняет планировщик Go в user-space, сохраняя только 14 регистров (PC, SP, callee-save регистры), что занимает всего ~10–20 наносекунд.
