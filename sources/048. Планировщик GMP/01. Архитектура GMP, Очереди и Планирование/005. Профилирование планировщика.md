# Профилирование планировщика: детекция переключения контекста через pprof и trace

## Условие

Сделайте программу с интенсивным вычислением в N goroutine. Поэкспериментируйте с `runtime.GOMAXPROCS(1)`, `GOMAXPROCS(2)`, `GOMAXPROCS(runtime.NumCPU())`. Снимите `perf`/`pprof` и найдите, где в коде рантайма происходит переключение контекста.

## Теория

Переключение контекста между горутинами происходит в функции `runtime.gogo()` (написанной на чистом ассемблере).
Существует два типа переключений:
1. **Добровольное (Cooperative):** Блокировка на канале, мьютексе, системном вызове, таймере или явный вызов `runtime.Gosched()`. Горутина переходит в состояние `_Gwaiting` через `runtime.gopark()`.
2. **Принудительное (Preemptive):** Вытеснение по таймеру `sysmon` через `runtime.asyncPreempt()` или проверку пролога функции `runtime.morestack()`.

Пакет `runtime/trace` фиксирует точные наносекундные события переключения контекста, визуализируя их на таймлайне планировщика.

## Решение по шагам

1. Создаем программу с записью трассировки в файл `trace.out` через `trace.Start()`.
2. Запускаем N горутин с конкурентными вычислениями и `runtime.Gosched()`.
3. Анализируем трассировку командой `go tool trace trace.out`.
4. Находим события переключения контекста на дорожках процессоров P.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/trace"
	"sync"
)

func worker(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < 1000; i++ {
		if i%200 == 0 {
			runtime.Gosched() // Добровольное переключение контекста
		}
	}
}

func main() {
	runtime.GOMAXPROCS(2)
	f, err := os.Create("trace.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	var wg sync.WaitGroup
	const workers = 4
	wg.Add(workers)

	for i := 0; i < workers; i++ {
		go worker(i, &wg)
	}

	wg.Wait()
	fmt.Println("Трассировка успешно записана в trace.out")
}
```

ℹ️ Снятие трассировки планировщика с runtime/trace

**`Терминал`**

```bash
go run main.go
# Анализ трассировки в веб-интерфейсе:
# go tool trace trace.out
```

## Под капотом

Функция `runtime.Gosched()` вызывает `mcall(gosched_m)`. Выполнение переключается с пользовательского стека `g` на системный стек потока `g0`. В контексте `g0` вызывается `goschedImpl(gp)`: текущая горутина переводится из `_Grunning` в `_Grunnable` и кладется в хвост Глобальной Очереди (GRQ). Затем вызывается `schedule()`, которая ищет следующую доступную горутину в локальной очереди `P`, в глобальной очереди или крадет работу у соседей через work-stealing.

## Подводные камни

Чрезмерное количество переключений контекста (например, при спавне сотен тысяч мелких горутин, постоянно дергающих `Gosched()` или небуферизированные каналы) приводит к падению производительности из-за накладных расходов планировщика (scheduler overhead) и деградации кэшей L1/L2 процессора.

## На собеседовании

**Вопрос с собеседования:** Что такое `g0` (g zero) в рантайме Go и почему переключение контекста горутин не может выполняться на их собственном пользовательском стеке?
**Ответ:** `g0` — это специальная горутина, создаваемая для каждого системного потока `M` при его рождении. Ее стек выделяется операционной системой и имеет фиксированный большой размер (~8 МБ в Linux), в отличие от динамического 2 КБ стека обычной горутины.
Все служебные операции рантайма (планирование `schedule()`, аллокация памяти, сборка мусора, расширение стека `morestack`) требуют значительного объема стековой памяти. Если бы планировщик начал работу на пользовательском стеке, в котором осталось 100 байт, произошел бы Stack Overflow. Поэтому перед планированием рантайм всегда выполняет вызов `mcall()`, переключаясь на надежный стек `g0`.
