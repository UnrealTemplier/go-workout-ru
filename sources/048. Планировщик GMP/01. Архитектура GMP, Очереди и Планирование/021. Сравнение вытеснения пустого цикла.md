# Сравнение вытеснения пустого цикла: Go 1.13 (Cooperative) vs Go 1.14+ (Async SIGURG)

## Условие

Реализуйте «busy loop» без вызовов функций рантайма (чистый `for {}`). Запустите параллельную goroutine. Покажите, что при Go ≤1.13 она блокирует планировщик, а при Go ≥1.14 — нет. Объясните роль асинхронного вытеснения (preemption) на safe points vs. loop preemption.

## Теория

До версии Go 1.14 планировщик проверял необходимость вытеснения только в прологе функций (компилятор вставлял `CALL runtime.morestack`).
Если в коде присутствовал плотный цикл без вызовов функций (busy loop):
```go
for !done {}
```
он компилировался в инструкцию безусловного перехода `JMP` на саму себя. Никаких проверок `stackguard0` не происходило.
При `GOMAXPROCS=1` такая горутина навечно захватывала процессор `P`.

Начиная с **Go 1.14**, механизм асинхронного вытеснения по сигналу `SIGURG` прерывает поток на уровне операционной системы, считывает контекст регистров и переключает выполнение даже из пустого цикла `for {}`.

## Решение по шагам

1. Запускаем горутину с пустым циклом `for !done {}`.
2. В параллельной горутине через небольшую паузу меняем флаг `done = true`.
3. Убеждаемся, что при `GOMAXPROCS=1` программа в современном Go штатно завершается за доли секунды.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Тестирование вытеснения плотного цикла for {} при GOMAXPROCS=1")

	var stopFlag int32
	ready := make(chan struct{})

	go func() {
		close(ready)
		// Плотный цикл без единого вызова функций
		for atomic.LoadInt32(&stopFlag) == 0 {
		}
		fmt.Println("Горутина 1 успешно вышла из плотного цикла!")
	}()

	<-ready
	time.Sleep(50 * time.Millisecond)

	// Если бы вытеснения не было, эта строка никогда бы не выполнилась
	atomic.StoreInt32(&stopFlag, 1)
	time.Sleep(50 * time.Millisecond)

	fmt.Println("Тест успешно пройден: поток sysmon прервал плотный цикл.")
}
```

ℹ️ Вытеснение плотного цикла при GOMAXPROCS=1

**`Терминал`**

```bash
go run main.go
# Вывод:
# Тестирование вытеснения плотного цикла for {} при GOMAXPROCS=1
# Горутина 1 успешно вышла из плотного цикла!
# Тест успешно пройден: поток sysmon прервал плотный цикл.
```

## Под капотом

При получении `SIGURG` обработчик рантайма сохраняет в стек структуру `sigctxt`. Он анализирует текущий PC: если PC безопасен для GC, рантайм подменяет PC возврата из сигнала на адрес функции `runtime.asyncPreempt`. Когда ядро ОС завершает обработку сигнала и возвращает поток в user-space, поток автоматически начинает выполнять `asyncPreempt`, которая вызывает `mcall(preemptPark)` и уступает ядро другой горутине.

## Подводные камни

Внутри функций, помеченных прагмой `//go:nosplit`, или в низкоуровневых ассемблерных функциях вытеснение запрещено, так как переключение стека в неподготовленном состоянии сломает инварианты памяти.

## На собеседовании

**Вопрос с собеседования:** Что такое «Safe Point» при асинхронном вытеснении горутин в Go?
**Ответ:** Safe Point (безопасная точка) — это место в машинном коде, где сборщик мусора точно знает расположение всех указателей на стеке (наличие валидной Stack Map).
Если поток прерывается сигналом `SIGURG` в момент, когда в регистрах CPU находятся сырые указатели, не описанные в stack map (например, в середине сложной арифметики с указателями), рантайм **не имеет права** переключать контекст, иначе GC при сканировании стека не поймет, что является живым объектом. В таких точках рантайм просто пропускает сигнал и повторяет попытку чуть позже.
