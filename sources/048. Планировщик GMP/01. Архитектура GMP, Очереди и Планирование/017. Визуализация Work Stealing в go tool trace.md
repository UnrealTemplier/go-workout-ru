# Визуализация Work Stealing в go tool trace: кража горутин между процессорами

## Условие

**Work Stealing (Кража работы)**: Напиши код, где только одна горутина порождает 100 тяжелых под-горутин, а остальные ядра простаивают. Открой `go tool trace`. Изучи на графике, как другие (свободные) `P` заглядывают в локальную очередь загруженного `P` и "крадут" у него половину горутин для балансировки нагрузки.

## Теория

В `go tool trace` каждое перемещение горутины между процессорами протоколируется.
Когда один процессор `P0` генерирует сотни горутин, на таймлайне trace отчетливо видно:
- Дорожка `Proc 0` заполнена непрерывным потоком создания задач;
- На дорожках `Proc 1`, `Proc 2`, `Proc 3` появляются события `Steal` (кража пакетов горутин);
- В блоке статистики отображается количество событий `Work Stealing` и сбалансированность утилизации CPU по всем ядрам.

## Решение по шагам

1. Создаем файл трассировки `trace_steal.out`.
2. Запускаем нагрузку, где исключительно одна горутина спавнит 100 тяжелых вычислительных задач.
3. Открываем `go tool trace trace_steal.out`.
4. Находим на таймлайне визуальные свидетельства перетекания задач с Proc 0 на Proc 1-3.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/trace"
	"sync"
)

func heavyCalculation(n int) int {
	acc := 0
	for i := 0; i < n; i++ {
		acc = (acc*33 + i) % 1000007
	}
	return acc
}

func main() {
	runtime.GOMAXPROCS(4)

	f, err := os.Create("trace_steal.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	var wg sync.WaitGroup
	const tasks = 100
	wg.Add(tasks)

	// Только одна горутина порождает все 100 задач
	go func() {
		for i := 0; i < tasks; i++ {
			go func(id int) {
				defer wg.Done()
				heavyCalculation(2000000)
			}(i)
		}
	}()

	wg.Wait()
	fmt.Println("Трассировка Work Stealing сохранена в trace_steal.out")
}
```

ℹ️ Генерация трассировки для визуализации Work Stealing

**`Терминал`**

```bash
go run main.go
# Просмотр трассировки:
# go tool trace trace_steal.out
```

## Под капотом

Внутри `runtime/trace` события фиксируются локально в кольцевых буферах каждого P без глобальной блокировки. События `traceEvGoStart` на разных P показывают, как горутины, созданные на P0, стартуют на P1..P3, доказывая факт кражи из локальной очереди P0.

## Подводные камни

Если задачи слишком короткие (микросекунды), накладные расходы на саму трассировку `trace.Start` могут исказить профиль выполнения. Для сверхбыстрых задач увеличивайте размер вычислительной нагрузки в теле цикла.

## На собеседовании

**Вопрос с собеседования:** Каким образом планировщик Go предотвращает постоянную конкуренцию между потоками M при попытке украсть работу у одного и того же P?
**Ответ:** Порядок обхода других процессоров при Work Stealing **рандомизирован**:
1) Каждый M генерирует случайную стартовую позицию в массиве `allp` с помощью быстрого генератора случайных чисел `fastrand()`;
2) Шаг обхода является взаимно простым с количеством `GOMAXPROCS`. Это гарантирует, что разные свободные потоки M начинают поиск с разных P и проверяют их в разном порядке, исключая эффект конвоя (Convoy effect) и взаимные блокировки.
