# Управление логическими процессорами P через runtime.GOMAXPROCS

## Условие

**Ограничение `P` (GOMAXPROCS)**: Напиши программу с 10 горутинами, каждая из которых крутит бесконечный математический цикл (CPU-bound). Запусти её с `runtime.GOMAXPROCS(1)`. Открой диспетчер задач ОС и убедись, что программа потребляет ровно 1 ядро (100% одного потока). Измени на `4` и посмотри разницу.

## Теория

Модель планировщика Go основана на абстракции GMP:
- **G (Goroutine):** Легковесный поток выполнения с начальным стеком от 2 КБ. Содержит указатель инструкций (PC), стек и метаданные.
- **M (Machine):** Поток операционной системы (OS Thread, pthread). Выполняет реальный машинный код на физическом ядре CPU.
- **P (Processor):** Логический контекст выполнения или ресурс, необходимый для исполнения Go-кода на M. Количество P определяет максимальный уровень параллелизма (одновременного выполнения вычислений на CPU).

Функция `runtime.GOMAXPROCS(n)` устанавливает количество P. По умолчанию в Go 1.5+ оно равно `runtime.NumCPU()` (числу доступных виртуальных ядер CPU, учитывая cgroups в Go 1.19+). Если передать `GOMAXPROCS(1)`, планировщик сможет одновременно выделять только один P потоку M, и CPU-bound задачи будут исполняться строго конкурентно, но не параллельно, утилизируя ровно 1 ядро процессора (100% одного CPU-треда).

## Решение по шагам

1. Создаем программу, считывающую текущее значение GOMAXPROCS.
2. Устанавливаем `runtime.GOMAXPROCS(1)`.
3. Запускаем 10 горутин с бесконечными CPU-bound циклами (математические операции).
4. Проверяем загрузку процессора в терминале через `top -pid <PID>` или `htop`.
5. Меняем `GOMAXPROCS(4)` и наблюдаем рост потребления до 400% CPU.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"strconv"
	"time"
)

func main() {
	pCount := 1
	if len(os.Args) > 1 {
		if val, err := strconv.Atoi(os.Args[1]); err == nil && val > 0 {
			pCount = val
		}
	}

	prev := runtime.GOMAXPROCS(pCount)
	fmt.Printf("GMP Demo: PID = %d\n", os.Getpid())
	fmt.Printf("NumCPU: %d, Previous GOMAXPROCS: %d, New GOMAXPROCS: %d\n", runtime.NumCPU(), prev, runtime.GOMAXPROCS(0))
	fmt.Printf("Запуск 10 CPU-bound горутин на %d P...\n", pCount)

	for i := 0; i < 10; i++ {
		go func(id int) {
			var x uint64 = 0
			for {
				x = (x * 1664525 + 1013904223) % 4294967296
				if x == 0 {
					runtime.Gosched()
				}
			}
		}(i)
	}

	time.Sleep(3 * time.Second)
	fmt.Println("Демонстрация завершена.")
}
```

ℹ️ Управление числом логических процессоров P

**`Терминал`**

```bash
go run main.go 1
# Вывод:
# GMP Demo: PID = 12345
# NumCPU: 8, Previous GOMAXPROCS: 8, New GOMAXPROCS: 1
# Запуск 10 CPU-bound горутин на 1 P...
# Демонстрация завершена.

# Запуск с 4 P:

```

## Под капотом

Когда вызывается `runtime.GOMAXPROCS(n)`, рантайм выполняет `stopTheWorld("GOMAXPROCS")`. Все горутины приостанавливаются, существующие P реаллоцируются (массив `allp`), неиспользуемые P переводятся в статус `_Pidle`, а затем вызывается `startTheWorld()`. Каждый P имеет локальную очередь выполнения (`runq` размером 256 элементов), структуру `mcache` для быстрой аллокации памяти без блокировок и кэш освобожденных горутин `gFree`.

## Подводные камни

Вызов `runtime.GOMAXPROCS` во время высоконагруженной работы сервиса вызывает полную остановку мира (Stop The World), что приводит к кратковременному спайку задержек (p99 latency). В контейнерах Docker без правильного сопоставления CPU квот `runtime.NumCPU()` до Go 1.19 возвращал число ядер хоста, приводя к CFS throttling. Для контейнеров рекомендуется использовать библиотеку `go.uber.org/automaxprocs`.

## На собеседовании

**Вопрос с собеседования:** Что именно представляет собой `P` в модели GMP и почему планировщик Go не мапит горутины (G) напрямую на потоки ОС (M)?
**Ответ:** `P` (Logical Processor) — это контекст выполнения и владения ресурсами, необходимый для исполнения Go-кода на ОС-потоке `M`. Если бы G мапились напрямую на M (модель GM из Go 1.0), то:
1) Возникала огромная глобальная блокировка (`sched.lock`) при любой операции планирования;
2) Потоки ОС часто блокировались бы на системных вызовах, требуя уничтожения и создания потоков ОС, что крайне дорого;
3) Локальные кэши аллокатора памяти (`mcache`) были бы привязаны к M, вызывая утечки и раздувание памяти при росте числа потоков. Выделение `P` позволило иметь ровно столько локальных очередей и кэшей памяти, сколько ядер выделено рантайму, независимо от числа потоков ОС.
