# Мониторинг очередей LRQ через GODEBUG=scheddetail=1,schedtrace=100

## Условие

**Local Run Queue (LRQ)**: Создайте 10000 горутин. Используйте `GODEBUG=scheddetail=1,schedtrace=100` для наблюдения, как горутины распределяются по P's local queues.

## Теория

Для глубокого анализа поведения планировщика флаг `GODEBUG` поддерживает комбинацию:
`GODEBUG=scheddetail=1,schedtrace=X`

В отличие от компактного `schedtrace`, который выводит одну строку с общими метриками, `scheddetail=1` выполняет полный дамп состояния:
1. Каждого логического процессора **P**: статус (`_Pidle`, `_Prunning`, `_Psyscall`), счетчик переключений (`schedtick`), идентификатор связанного M, содержимое локальной очереди;
2. Каждого потока ОС **M**: стек, статус (`spinning`, `blocked`), связанный P;
3. Каждой активной горутины **G**: статус (`_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gsyscall`), стек вызовов, текущий PC.

## Решение по шагам

1. Создаем программу, распределяющую 10 000 горутин по очередям.
2. Запускаем программу с `GODEBUG=scheddetail=1,schedtrace=100`.
3. Разбираем структуры в выводе терминала.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)
	const count = 5000
	var wg sync.WaitGroup
	wg.Add(count)

	fmt.Println("Запуск 5000 горутин на 2 P для анализа scheddetail...")

	for i := 0; i < count; i++ {
		go func(id int) {
			defer wg.Done()
			time.Sleep(20 * time.Millisecond)
		}(i)
	}

	wg.Wait()
	fmt.Println("Завершено.")
}
```

ℹ️ Генерация нагрузки для детального дампа scheddetail

**`Терминал`**

```bash
go build -o detail_demo main.go
GODEBUG=scheddetail=1,schedtrace=100 ./detail_demo 2>&1 | head -n 35
# Пример вывода:
#   P0: status=1 schedtick=24 syscalltick=0 m=0 runqhead=12 runqtail=140 runqsize=128
#   P1: status=1 schedtick=19 syscalltick=0 m=2 runqhead=4 runqtail=132 runqsize=128
#   M0: p=0 curg=15 mallocing=0 throwing=0 preemptoff= locks=0 dying=0
#   G15: status=2(running) m=0 allocg=0
```

## Под капотом

В дампе `P`:
- `status=1` означает `_Prunning` (процессор исполняет код);
- `schedtick` — счетчик выполненных переключений планировщика на этом P (каждые 61 тик планировщик обязательно проверяет глобальную очередь GRQ для предотвращения голодания);
- `runqhead` и `runqtail` — 32-битные указатели головы и хвоста локального кольцевого буфера очереди LRQ;
- `runqsize` — текущее количество горутин в очереди данного P.

## Подводные камни

Включение `scheddetail=1` в продакшене генерирует гигабайты текстовых логов за считанные секунды и существенно снижает производительность рантайма из-за синхронного вывода в `stderr`. Используйте этот флаг исключительно на стендах разработки и нагрузочного тестирования.

## На собеседовании

**Вопрос с собеседования:** Что означает поле `schedtick` у `P` в выводе `scheddetail` и какое магическое число связано с ним в планировщике Go?
**Ответ:** Поле `schedtick` — это монотонный счетчик квантов планирования, выполненных данным `P`.
Магическое число — **61**. В функции `schedule()` перед тем как проверить локальную очередь `LRQ`, рантайм выполняет проверку:
`if pp.schedtick%61 == 0 && sched.runqsize > 0 { ... забрать горутину из GRQ ... }`
Это сделано для предотвращения **starvation (голодания)**: если бы планировщик всегда брал задачи только из локальной очереди, горутины в Глобальной Очереди (GRQ) могли бы бесконечно ждать выполнения при высокой активности локальных очередей.
