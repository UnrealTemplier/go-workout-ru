# Глубокий анализ очередей LRQ/GRQ с помощью runtime/trace и go tool trace

## Условие

**Локальные и Глобальная очереди (LRQ vs GRQ)**: *Теоретическо-практическое.* Каждому `P` принадлежит своя локальная очередь на 256 горутин (LRQ). Если она переполняется, половина сбрасывается в Глобальную очередь (GRQ). Напиши код, который в цикле спавнит 10 000 горутин. Используй пакет `runtime/trace`, сгенерируй файл трассировки и найди моменты, когда горутины попадают в GRQ.

## Теория

Визуализация работы планировщика через `go tool trace` позволяет детально увидеть:
1. Точные моменты переполнения локальной очереди LRQ и сброса горутин в GRQ;
2. Загрузку каждого виртуального процессора `P` во времени;
3. Всплески задержек планирования (Scheduler Latency) — время от момента, когда горутина стала `_Grunnable`, до момента, когда она реально начала исполняться на `M` (`_Grunning`).

Инструмент `runtime/trace` фиксирует бинарный лог всех событий ядра рантайма с микросекундной точностью.

## Решение по шагам

1. Создаем файл `trace.out` и активируем трассировку через `trace.Start()`.
2. В цикле быстро порождаем 10 000 горутин, провоцируя переполнение LRQ.
3. Останавливаем трассировку `trace.Stop()`.
4. Запускаем веб-интерфейс `go tool trace trace.out`.
5. Переходим в раздел «View trace» и находим события сброса в GRQ.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/trace"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)

	f, err := os.Create("trace_lrq.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	const total = 10000
	var wg sync.WaitGroup
	wg.Add(total)

	fmt.Println("Генерация 10 000 горутин с трассировкой...")

	for i := 0; i < total; i++ {
		go func(id int) {
			defer wg.Done()
			// Короткая работа, вызывающая частые циклы планирования
			sum := 0
			for j := 0; j < 1000; j++ {
				sum += j
			}
			if id%100 == 0 {
				time.Sleep(1 * time.Millisecond)
			}
		}(i)
	}

	wg.Wait()
	fmt.Println("Трассировка успешно сохранена в trace_lrq.out")
}
```

**`Терминал`**


## Под капотом

В бинарном формате `runtime/trace` события планировщика кодируются компактными дельта-таймстемпами. Событие `traceEvGoCreate` фиксирует создание горутины, `traceEvGoStart` — начало исполнения на процессоре P, `traceEvGoBlock` — уход в ожидание. Веб-интерфейс на базе Chromium Perfetto отображает граф потоков, очередей и переключений контекста.

## Подводные камни

Включение `runtime/trace` добавляет накладные расходы (~5-15% CPU и выделение буферов трассировки). На высоконагруженных продакшен-серверах снимайте трейсы короткими окнами (по 3–5 секунд), например через HTTP-эндпоинт `/debug/pprof/trace?seconds=5`.

## На собеседовании

**Вопрос с собеседования:** Как через `go tool trace` диагностировать проблему раздувания задержек (Latency Spikes) из-за перегрузки планировщика?
**Ответ:** В отчете `go tool trace`:
1) Открывают раздел **«Goroutine analysis»** и проверяют колонку **«Execution Time»** против **«Scheduler Wait Time»**. Если время ожидания в очереди (`Scheduler Wait Time`) существенно превышает время непосредственного исполнения (`Execution Time`), приложение страдает от нехватки `P` или переполнения очередей горутинами.
2) На графике **«Goroutines»** смотрят на соотношение горутин в статусе `Runnable` (готовы к исполнению) и `Running` (исполняются). Большой пик `Runnable` сигнализирует о том, что потоки не успевают разбирать задачи из LRQ/GRQ.
