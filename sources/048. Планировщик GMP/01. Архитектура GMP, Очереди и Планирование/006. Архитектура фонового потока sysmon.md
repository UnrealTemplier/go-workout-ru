# Архитектура фонового потока sysmon: мониторинг зависших горутин и вытеснение

## Условие

**Sysmon thread**: Изучите роль sysmon — специального потока, который просыпается каждые 10ms для проверки зависших горутин и принудительного вытеснения. Используйте `GODEBUG=schedtrace=1000` для наблюдения.

## Теория

`sysmon` (System Monitor) — это специализированный фоновый поток операционной системы (M), который работает **без привязки к P** (`m without p`).
Он запускается при старте рантайма в `runtime.main()` отдельным системным вызовом `newm(sysmon, nil, -1)`.

Основные обязанности `sysmon`:
1. **Preemption (Вытеснение):** Обход всех P (`retake()`). Если горутина выполняется непрерывно дольше 10 мс, инициируется ее вытеснение (`preemptone`).
2. **Handoff (Передача P):** Если поток M заблокирован в системном вызове (syscall) дольше 10 мс, `sysmon` отбирает у него `P` и передает другому M для выполнения остальных горутин.
3. **Netpoller:** Пробуждение горутин, готовых к сетевому вводу-выводу, если они не опрашивались дольше 10 мс.
4. **Периодический запуск GC:** Если сборка мусора не запускалась более 2 минут (константа `forcegcperiod`), `sysmon` принудительно инициирует цикл GC.
5. **Scavenger (Очистка памяти):** Возврат неиспользуемых страниц физической памяти ядру ОС (`madvise(MADV_DONTNEED)`).

## Решение по шагам

1. Запускаем приложение с флагом `GODEBUG=schedtrace=1000`.
2. Создаем блокирующие вызовы и долгие CPU-циклы.
3. Наблюдаем логические циклы пробуждения `sysmon` (от 20 мкс в активном режиме до 10 мс в спящем).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Println("sysmon Demo: запуск с GODEBUG=schedtrace=1000")
	fmt.Printf("GOMAXPROCS: %d. Наблюдайте за поведением потоков и очередей...\n", runtime.GOMAXPROCS(0))

	// Запускаем фоновую горутину с периодической нагрузкой
	go func() {
		for {
			t := time.Now()
			for time.Since(t) < 50*time.Millisecond {
				// CPU-интенсивный интервал, превышающий квант 10 мс
			}
			time.Sleep(200 * time.Millisecond)
		}
	}()

	time.Sleep(2500 * time.Millisecond)
	fmt.Println("Демонстрация sysmon завершена.")
}
```

ℹ️ Наблюдение за работой планировщика и sysmon через schedtrace

**`Терминал`**

```bash
GODEBUG=schedtrace=500 go run main.go
# Лог schedtrace демонстрирует фоновые проверки потока sysmon каждые 500 мс
```

## Под капотом

Внутри `src/runtime/proc.go` функция `sysmon()` представляет собой бесконечный цикл. В периоды бездействия он засыпает с помощью `runtime.notesleep()`, увеличивая интервал сна от 20 микросекунд до 10 миллисекунд. Так как `sysmon` не имеет связанного `P`, он не участвует в гонках за очереди горутин и не учитывается в квоте `GOMAXPROCS`.

## Подводные камни

Хотя `sysmon` эффективен, его интервал опроса (~10–20 мс) означает, что мгновенного вытеснения в микросекундном диапазоне в Go нет. Если критичный по latency сервис ждет освобождения ядра от тяжелой CPU-задачи, возможна задержка реакции до 10–20 мс.

## На собеседовании

**Вопрос с собеседования:** Почему поток `sysmon` в Go работает без логического процессора `P` и как он умудряется выполнять код на Go?
**Ответ:** `sysmon` не исполняет пользовательский Go-код: он не создает горутины, не аллоцирует память в куче через `mcache` и не вызывает пользовательские функции. Он выполняет только системные проверки рантайма на своем собственном стеке потока ОС. Если бы `sysmon` требовал `P`, он занимал бы один из слотов параллелизма `GOMAXPROCS`, уменьшая доступные вычислительные ресурсы приложения.
