# Механизм Work Stealing: балансировка нагрузки между логическими процессорами P

## Условие

**[Work Stealing]**: Установи `GOMAXPROCS=4`. Создай 4 горутины, которые做完 (засыпают на 1 сек), и 1 горутину, которая генерирует 1000 задач. Наблюдай через `schedtrace`, как простаивающие P "крадут" горутины из очереди занятого P.

## Теория

Алгоритм **Work Stealing (Кража работы)** — краеугольный камень эффективности распределенного планировщика Go.
Когда у логического процессора `P` заканчиваются горутины в локальной очереди (`runq`), поток `M` не засыпает сразу, а выполняет 4-этапный поиск работы (`findrunnable`):
1. Проверяет приоритетный слот `runnext` и локальную очередь `LRQ`;
2. Проверяет глобальную очередь `GRQ` (каждые 61 тик или если локальная очередь пуста);
3. Проверяет сетевой поллер `netpoll` на наличие готовых сетевых событий;
4. Пытается украсть **половину горутин** из локальной очереди случайно выбранного чужого процессора `P` (`runqsteal`).

## Решение по шагам

1. Устанавливаем `GOMAXPROCS=4`.
2. Создаем сценарий: 1 горутина на P0 быстро порождает 1000 ресурсоемких задач.
3. Процессоры P1, P2, P3 освобождаются и воруют работу у P0.
4. Отслеживаем перераспределение горутин через `GODEBUG=schedtrace=100`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Println("Демонстрация Work Stealing на 4 P...")

	var wg sync.WaitGroup
	const totalTasks = 2000
	wg.Add(totalTasks)

	// Запускаем генерацию пачки задач
	go func() {
		for i := 0; i < totalTasks; i++ {
			go func(id int) {
				defer wg.Done()
				// Имитация вычислений
				var acc uint64
				for j := 0; j < 500000; j++ {
					acc += uint64(j)
				}
				_ = acc
			}(i)
		}
	}()

	wg.Wait()
	fmt.Println("Все задачи успешно обработаны через Work Stealing.")
}
```

ℹ️ Work Stealing при неравномерной генерации нагрузки

## Под капотом

В `src/runtime/proc.go` функция `runqsteal(pp, p2, stealRunNext)` обходит другие процессоры в псевдослучайном порядке (используя генератор `fastrand()`). Чтобы минимизировать задержку, поток забирает ровно `(n + 1) / 2` элементов из чужой очереди атомарными операциями CAS (`atomic.CasRel`). За счет этого чужая очередь разгружается наполовину, а текущий P сразу получает готовый пакет задач без блокировки глобального мьютекса.

## Подводные камни

Work Stealing эффективен, но при огромном числе процессоров (например 128 P) и сверхмелких горутинах (доли микросекунды) время на случайный перебор чужих очередей и промахи кэша памяти может превышать время полезной работы горутины.

## На собеседовании

**Вопрос с собеседования:** Почему при Work Stealing в Go крадется ровно половина очереди чужого P, а не одна горутина?
**Ответ:** Если красть только 1 горутину, то ворующему P придется возвращаться за следующей задачей почти мгновенно, создавая постоянный шквал CAS-операций над чужой очередью и инвалидацию линий кэша процессора.
Кража ровно половины:
1) Гарантирует идеальный баланс: оба процессора теперь имеют равный объем работы;
2) Амортизирует накладные расходы на поиск и CAS-операции;
3) Минимизирует количество повторных краж.
