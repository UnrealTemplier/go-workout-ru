# Сетевой запрос изнутри: состояния горутины и причина ожидания IO wait

## Условие

**Network Poller (Сетевой опросчик)**: Что происходит при сетевом запросе? Запусти горутину, делающую `http.Get`. Горутина заблокируется, но поток ОС (`M`) — нет! Открой трассировку и найди, как горутина паркуется в `netpoller` (под капотом `epoll`/`kqueue`), а `M` берет из очереди другую горутину.

## Теория

При выполнении любого сетевого вызова (`net.Dial`, `conn.Read`, `http.Get`) жизненный цикл горутины проходит через следующие фазы:
1. `_Grunning`: Горутина формирует сетевой буфер и делает системный вызов `read/recv` через рантайм.
2. `_Gwaiting [IO wait]`: Сокет возвращает `EAGAIN`. Горутина паркуется с причиной ожидания `waitReasonIOWait`.
3. `_Grunnable`: `epoll` детектирует событие `EPOLLIN` (данные прибыли на сетевую карту). Netpoller будит горутину.
4. `_Grunning`: Горутина продолжает исполнение на доступном P, считывая данные из сокета в пользовательский буфер.

## Решение по шагам

1. Запускаем горутину, ожидающую данные из медленного сокета.
2. Снимаем срез стека через `runtime.Stack()`.
3. Находим в выводе статус `[IO wait]`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"runtime"
	"time"
)

func main() {
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer ln.Close()

	// Горутина-клиент зависает в ожидании ответа
	go func() {
		conn, err := net.Dial("tcp", ln.Addr().String())
		if err != nil {
			return
		}
		defer conn.Close()

		buf := make([]byte, 1024)
		// Здесь горутина переходит в состояние _Gwaiting [IO wait]
		_, _ = conn.Read(buf)
	}()

	time.Sleep(100 * time.Millisecond)

	buf := make([]byte, 8192)
	n := runtime.Stack(buf, true)
	fmt.Println("=== Поиск горутины в состоянии [IO wait] ===")
	fmt.Printf("%s\n", buf[:n])
}
```

ℹ️ Детекция статуса IO wait через стек вызовов

**`Терминал`**

```bash

```

## Под капотом

В `src/internal/poll/fd_poll_runtime.go` вызов `runtime_pollWait()` обращается напрямую к `netpollblock()`. Внутренняя структура `pollDesc` содержит указатель на горутину `rg` (read goroutine) или `wg` (write goroutine). Когда `netpoll()` возвращает этот дескриптор, рантайм атомарно извлекает `rg`, вызывает `goready(rg, 0)` и очищает указатель.

## Подводные камни

Если сетевой таймаут не задан (`conn.SetDeadline`), горутина в состоянии `[IO wait]` может висеть сутками, удерживая сетевой сокет и память, пока удаленная сторона не разорвет TCP-соединение на уровне ОС.

## На собеседовании

**Вопрос с собеседования:** Что означает статус `[IO wait]` в дампе стека горутины и чем он отличается от `[syscall]`?
**Ответ:**
- `[IO wait]` означает, что горутина ожидает сетевого события в **неблокирующем сетевом сокете**, управляемом `netpoller` (`epoll`/`kqueue`). Поток ОС при этом **не занят** и выполняет другие горутины.
- `[syscall]` означает, что горутина выполняет прямой **блокирующий вызов ядра ОС** (чтение с диска, `cgo`, `futex`). В этом случае системный поток ОС `M` физически спит внутри ядра Linux, а процессор `P` отцепляется через `handoffp`.
