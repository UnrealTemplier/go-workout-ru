# Архитектура Netpoller: асинхронный сетевой ввод-вывод без блокировки потоков ОС

## Условие

**Netpoller**: Создайте множество горутин, блокирующихся на network I/O. Изучите, как netpoller (epoll/kqueue) интегрирован с планировщиком и не блокирует M.

## Теория

Сетевой опросчик (**Netpoller**) — один из ключевых компонентов высочайшей производительности Go в сетевых сервисах.
В традиционных языках (C/Java) синхронный сокет блокирует поток ОС. Если у вас 50 000 клиентов, требуется 50 000 потоков ОС, что разрушает ядро ОС.

В Go сетевые сокеты всегда переводятся в **неблокирующий режим** (`O_NONBLOCK`):
1. Когда горутина вызывает `net.Conn.Read()` и в буфере нет данных, сокет возвращает `EAGAIN`/`EWOULDBLOCK`.
2. Рантайм регистрирует файловый дескриптор в механизме мультиплексирования ОС (`epoll` в Linux, `kqueue` в macOS, `IOCP` в Windows).
3. Горутина переводится в состояние `_Gwaiting` и **отцепляется от потока M**.
4. Поток M не блокируется, а немедленно берет следующую горутину из LRQ!
5. Когда в сокет приходят байты, `epoll_wait` сообщает об этом рантайму, и горутина переводится в `_Grunnable`.

## Решение по шагам

1. Создаем TCP-эхо-сервер.
2. Подключаем 1000 клиентов, отправляющих редкие пинги.
3. Проверяем `GODEBUG=schedtrace=500` и количество потоков ОС `threads`.
4. Убеждаемся, что для обслуживания 1000 соединений требуется всего несколько потоков ОС.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer ln.Close()

	addr := ln.Addr().String()
	fmt.Printf("Netpoller Demo: сервер на %s, GOMAXPROCS=%d\n", addr, runtime.GOMAXPROCS(0))

	var activeClients int64

	// Сервер: слушает подключения
	go func() {
		for {
			conn, err := ln.Accept()
			if err != nil {
				return
			}
			go func(c net.Conn) {
				defer c.Close()
				buf := make([]byte, 64)
				for {
					n, err := c.Read(buf) // Блокировка на уровне горутины, но НЕ потока ОС!
					if err != nil {
						return
					}
					c.Write(buf[:n])
				}
			}(conn)
		}
	}()

	// Клиенты: создаем 500 подключений
	const clients = 500
	for i := 0; i < clients; i++ {
		go func() {
			c, err := net.Dial("tcp", addr)
			if err != nil {
				return
			}
			defer c.Close()
			atomic.AddInt64(&activeClients, 1)

			for j := 0; j < 3; j++ {
				c.Write([]byte("ping"))
				buf := make([]byte, 64)
				c.Read(buf)
				time.Sleep(300 * time.Millisecond)
			}
		}()
	}

	time.Sleep(500 * time.Millisecond)
	fmt.Printf("Активных TCP-клиентов: %d, Горутин: %d\n", atomic.LoadInt64(&activeClients), runtime.NumGoroutine())
	time.Sleep(1 * time.Second)
	fmt.Println("Демонстрация Netpoller успешно завершена.")
}
```

## Под капотом

Внутри `src/runtime/netpoll_epoll.go` рантайм держит глобальный дескриптор `epfd = epoll_create1(EPOLL_CLOEXEC)`. Каждый сокет регистрируется через `epoll_ctl(EPOLL_CTL_ADD, fd, &ev)`. Когда горутина блокируется на чтении, вызывается `netpollblock()`. Она связывает структуру `pollDesc` с текущей `g` и вызывает `gopark()`. Фоновый поток `sysmon` или свободный M в `findrunnable()` опрашивает `netpoll(0)` без задержки и мгновенно переводит проснувшиеся горутины в `_Grunnable`.

## Подводные камни

Файловые дескрипторы обычных файлов на диске (`os.File`) в Linux **не поддерживаются стандартным epoll** (они всегда считаются «готовыми к чтению»). Поэтому дисковый ввод-вывод выполняется через обычные блокирующие системные вызовы с механизмом `handoffp`, создавая новые потоки M.

## На собеседовании

**Вопрос с собеседования:** Почему дисковые операции с файлами (`os.ReadFile`, `os.Open`) в Go могут приводить к росту числа потоков ОС (M), а сетевые операции (`net.Dial`, `http.Get`) — нет?
**Ответ:** Сетевые сокеты в Linux полностью поддерживаются механизмом `epoll`. Go переводит их в `O_NONBLOCK`, и при отсутствии данных горутина паркуется в `netpoller`, освобождая поток M.
Но обычные файлы на диске в ядре Linux **не поддерживают неблокирующий epoll**: системный вызов `read()` из файла на диске всегда синхронно блокирует поток ядра ОС, ожидая ответа контроллера накопителя (SSD/HDD). Из-за этого поток `M` застревает в ядре, и рантайм вынужден делать `handoffp` и создавать новый поток `M` для продолжения работы остальных горутин.
