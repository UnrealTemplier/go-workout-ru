# Локальная очередь (LRQ) против Глобальной очереди (GRQ) в планировщике GMP

## Условие

**[Local Run Queue (LRQ) vs Global Run Queue (GRQ)]**: Напиши программу, которая рекурсивно создает 100 000 горутин. Запусти её с переменной окружения `GODEBUG=schedtrace=1000`. Проанализируй вывод в консоль (колонки `P`, `M`, `G`, `RUNQUEUE`).

## Теория

Планировщик Go использует двухуровневую иерархию очередей выполнения:
1. **LRQ (Local Run Queue):** Локальная очередь каждого процессора `P`. Имеет фиксированную кольцевую структуру без блокировок (Lock-Free ring buffer) емкостью **256 горутин**. Доступ к ней осуществляет только привязанный поток M, что исключает накладные расходы на мьютексы.
2. **GRQ (Global Run Queue):** Глобальная очередь, общая для всех `P`. Защищена глобальным мьютексом `sched.lock`.

**Сброс при переполнении:**
Когда локальная очередь LRQ заполняется (все 256 слотов заняты) и создается новая горутина (`go func()`), рантайм берет **половину (128 штук)** горутин из переполненной LRQ плюс новую горутину и в рамках одной атомарной операции переносит их в Глобальную Очередь GRQ (`runqputslow`).

## Решение по шагам

1. Пишем программу, порождающую 100 000 горутин в цикле.
2. Запускаем с флагом `GODEBUG=schedtrace=1000`.
3. Анализируем поле `runqueue=<N>` в выводе schedtrace — оно отражает количество горутин, вытесненных в Глобальную Очередь GRQ.
4. Сравниваем его со значениями в квадратных скобках `[n1 n2 ... nP]` (локальные очереди LRQ каждого P).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	const count = 100000
	var wg sync.WaitGroup
	wg.Add(count)

	fmt.Printf("Спавн %d горутин на %d P. Наблюдайте runqueue (GRQ) в schedtrace.\n", count, runtime.GOMAXPROCS(0))

	for i := 0; i < count; i++ {
		go func(id int) {
			defer wg.Done()
			// Имитация полезной нагрузки
			time.Sleep(10 * time.Millisecond)
		}(i)
	}

	wg.Wait()
	fmt.Println("Все 100 000 горутин завершены.")
}
```

## Под капотом

В `src/runtime/proc.go` функция `runqput(pp, gp, next)` сначала пытается поместить горутину в специальный слот `runnext` (приоритетный запуск без очереди). Если слот занят, горутина ставится в кольцевой буфер `runq`. Если буфер полон (`runqhead - runqtail == 256`), вызывается `runqputslow(pp, gp, h, t)`. Она захватывает `sched.lock`, забирает половину локального буфера и переносит в связный список `sched.runq` (GRQ).

## Подводные камни

Если приложение постоянно переполняет LRQ, потоки M начинают конкурировать за `sched.lock`, что приводит к падению масштабируемости (Lock Contention) на многоядерных машинах (32–128 ядер). Для высоконагруженных очередей задач эффективнее использовать паттерн Worker Pool фиксированного размера.

## На собеседовании

**Вопрос с собеседования:** Каков размер локальной очереди горутин у `P`, что происходит при ее переполнении и почему именно половина горутин сбрасывается в GRQ?
**Ответ:** Размер LRQ составляет ровно **256 горутин**. При попытке добавить 257-ю горутину рантайм вызывает `runqputslow()`, захватывает глобальный лок `sched.lock` и переносит ровно 128 горутин (половину очереди) плюс новую горутину в GRQ.
Половина очереди (128) выбрана математически для амортизации накладных расходов:
1) Если сбросить только 1 горутину, следующее же создание вызовет повторную блокировку `sched.lock`;
2) Если сбросить все 256, текущий P останется пустым и ему придется сразу же идти воровать работу;
3) Сброс ровно половины освобождает 128 слотов для будущих `go func()` и оставляет 128 горутин для непрерывной работы локального ядра.
