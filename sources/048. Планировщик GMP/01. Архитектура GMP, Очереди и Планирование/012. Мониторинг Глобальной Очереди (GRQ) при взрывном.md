# Мониторинг Глобальной Очереди (GRQ) при взрывном спавне горутин

## Условие

**Global Run Queue (GRQ)**: Запустите программу, которая создаёт горутины быстрее, чем P's могут их обрабатывать. Наблюдайте, как горутины попадают в global queue.

## Теория

Глобальная очередь выполнения (Global Run Queue, GRQ) представляет собой связный список `sched.runq`, защищенный спинлоком `sched.lock`.
Горутины попадают в GRQ в четырех случаях:
1. При переполнении локальной очереди LRQ (сброс 128 горутин);
2. При вызове `runtime.Gosched()` (добровольная уступка процессора);
3. При пробуждении горутин после сетевого поллинга (`netpoll`), если локальная очередь переполнена;
4. При разблокировке горутин во время фазы Stop-The-World.

Если приложение создает новые горутины значительно быстрее, чем логические процессоры P успевают их выполнять, число задач в GRQ (`runqueue` в `schedtrace`) начинает лавинообразно нарастать.

## Решение по шагам

1. Создаем программу, которая в одной горутине непрерывно спавнит короткоживущие задачи в цикле.
2. Рабочие горутины выполняют небольшие задержки.
3. Запускаем с `GODEBUG=schedtrace=200`.
4. Наблюдаем быстрый рост счетчика `runqueue`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)
	fmt.Println("Демонстрация переполнения GRQ. Запустите с GODEBUG=schedtrace=200")

	var active int64
	stop := make(chan struct{})

	// Продюсер: генерирует горутины быстрее, чем 2 P успевают их обработать
	go func() {
		for {
			select {
			case <-stop:
				return
			default:
				atomic.AddInt64(&active, 1)
				go func() {
					time.Sleep(50 * time.Millisecond)
					atomic.AddInt64(&active, -1)
				}()
				time.Sleep(10 * time.Microsecond)
			}
		}
	}()

	time.Sleep(2 * time.Second)
	close(stop)
	time.Sleep(500 * time.Millisecond)
	fmt.Printf("Остановлено. Активных горутин: %d\n", atomic.LoadInt64(&active))
}
```

ℹ️ Быстрый спавн горутин для заполнения GRQ

**`Терминал`**

```bash
go build -o grq_demo main.go
GODEBUG=schedtrace=200 ./grq_demo
# В логах видно, как runqueue растет до тысяч горутин:
# SCHED 402ms: gomaxprocs=2 idleprocs=0 threads=5 spinningthreads=0 runqueue=1420 [256 256]
```

## Под капотом

Когда `runqueue` в GRQ не пуста, любой поток M, освободившись от выполнения локальной очереди, пытается забрать часть горутин из GRQ с помощью функции `globrunqget(pp, max)`. Она рассчитывает порцию по формуле: `n = min(sched.runqsize/gomaxprocs + 1, max)`. Таким образом, глобальная очередь справедливо распределяется между всеми доступными P пропорционально общему объему задач.

## Подводные камни

Всплески размера GRQ приводят к высокому потреблению оперативной памяти и росту задержек выполнения (Scheduler Latency). Каждая горутина в GRQ потребляет минимум 2 КБ памяти под стек, поэтому 500 000 зависших горутин займут более 1 ГБ оперативной памяти только под стеки.

## На собеседовании

**Вопрос с собеседования:** С какой периодичностью планировщик Go заглядывает в Глобальную Очередь (GRQ), даже если в локальной очереди (LRQ) текущего P есть готовые задачи?
**Ответ:** Ровно каждые **61 тик планирования** (`pp.schedtick % 61 == 0`). Это предотвращает голодание (starvation) горутин, попавших в GRQ. Если бы этой проверки не было, высокоактивный P с непрерывным потоком локальных горутин никогда не обратился бы к глобальной очереди, и находящиеся там горутины зависли бы навсегда.
