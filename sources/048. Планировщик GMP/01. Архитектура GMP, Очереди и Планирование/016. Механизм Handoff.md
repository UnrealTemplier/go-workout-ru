# Механизм Handoff: отсоединение P от заблокированного потока M при системных вызовах

## Условие

**Handoff**: Когда M блокируется на syscall, P передаётся другому M. Создайте множество горутин, делающих блокирующие syscall'ы (например, `time.Sleep`), и наблюдайте handoff через `schedtrace`.

## Теория

Когда поток `M` собирается выполнить блокирующий системный вызов (например, чтение файла с диска через `os.Open` или синхронный syscall ОС), он не может использовать неблокирующий сетевой поллер.
Рантайм Go обрабатывает это через механизм **Handoff (передача P)**:
1. Перед вызовом syscall поток вызывает `runtime.entersyscall()`: процессор `P` переходит в статус `_Psyscall`, но пока остается связанным с `M`.
2. Если системный вызов длится дольше кванта времени (~10–20 мкс в активном режиме или 10 мс через `sysmon`), рантайм отцепляет `P` от заблокированного потока `M` (`handoffp(pp)`).
3. Процессор `P` передается другому свободному потоку M (или создается новый поток M), который продолжает выполнять горутины из очереди этого `P`.

## Решение по шагам

1. Создаем программу с множеством горутин, выполняющих блокирующие системные вызовы.
2. Запускаем с флагом `GODEBUG=schedtrace=500`.
3. Наблюдаем, как поле `threads` в выводе растет, превышая `GOMAXPROCS`, подтверждая создание новых M для handoff.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"sync"
	"syscall"
	"time"
)

func blockingSyscallWorker(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	// Прямой блокирующий системный вызов ядра Linux (пауза на 1 секунду)
	var req, rem syscall.Timespec
	req.Sec = 1
	syscall.Nanosleep(&req, &rem)
}

func main() {
	runtime.GOMAXPROCS(2)
	fmt.Printf("GOMAXPROCS = 2. Старт 20 горутин с блокирующими syscalls...\n")

	var wg sync.WaitGroup
	const total = 20
	wg.Add(total)

	for i := 0; i < total; i++ {
		go blockingSyscallWorker(i, &wg)
	}

	time.Sleep(200 * time.Millisecond)
	fmt.Printf("В момент выполнения системных вызовов: Горутин: %d\n", runtime.NumGoroutine())

	wg.Wait()
	fmt.Println("Все системные вызовы завершены.")
}
```

## Под капотом

При возврате из системного вызова (`runtime.exitsyscall()`) поток M пытается снова захватить свой прежний P. Если P уже отобран и занят другим потоком M, текущий M пытается захватить любой свободный P из пула `sched.pidle`. Если свободных P нет, горутина переводится в `_Grunnable` и кладется в Глобальную Очередь (GRQ), а сам поток M засыпает и возвращается в пул свободных потоков `sched.midle`.

## Подводные камни

Массовые блокирующие системные вызовы (например, при обращении к медленным NFS-дискам или плохим CGO-библиотекам) могут вызвать лавинообразное создание тысяч потоков ОС `M`, что приведет к аварийной остановке программы по лимиту `threads-max` ядра Linux.

## На собеседовании

**Вопрос с собеседования:** Что происходит с потоком `M` и контекстом `P`, когда горутина выполняет блокирующий системный вызов (например, `read()` из файла на диске)?
**Ответ:**
1) Перед вызовом горутина сохраняет регистры в `entersyscall()`, и процессор `P` переходит в `_Psyscall`.
2) Поток `M` блокируется в ядре ОС.
3) Поток `sysmon` (или другой M) замечает блокировку и вызывает `handoffp()`, отсоединяя `P` от застрявшего `M`.
4) Контекст `P` передается свободному потоку `M`, который продолжает выполнять другие горутины.
5) Когда системный вызов завершается, поток `M` вызывает `exitsyscall()`. Если свободного `P` нет, горутина сбрасывается в GRQ, а поток `M` паркуется.
