# Взаимодействие Sysmon и Blocking Syscalls: автоматический handoff P при задержках свыше 10 мс

## Условие

**[Sysmon и Blocking Syscalls]**: Напиши программу, которая делает блокирующий системный вызов (например, `syscall.Read` из `/dev/urandom` или `C.sleep(5)` через CGO). Запусти с `GODEBUG=schedtrace=1000`. Убедись, что при блокировке M, P отвязывается от него и передается другому M (потоку ОС), чтобы другие горутины не простаивали.

## Теория

Когда поток `M` выполняет блокирующий вызов операционной системы (например, `time.Sleep` на уровне libc, синхронный `read` из pipe или вызов C-библиотеки через CGO), планировщик переводит контекст `P` в статус `_Psyscall`.
Поток `sysmon`, просыпаясь каждые 10–20 мс, вызывает функцию `retake()`:
- Он проверяет каждый `P` в статусе `_Psyscall`.
- Если с момента входа в системный вызов прошло более 10 мс (или если в очереди этого P есть ожидающие горутины), `sysmon` вызывает `handoffp(pp)`.
- Контекст `P` отбирается и передается новому или свободному потоку M, предотвращая блокировку других горутин.

## Решение по шагам

1. Создаем программу, где горутина делает долгий системный вызов через `syscall.RawSyscall` или CGO-паузу.
2. В очереди того же P оставляем другие горутины.
3. Запускаем с `GODEBUG=schedtrace=200`.
4. Убеждаемся, что остальные горутины продолжают успешно выполняться, несмотря на блокировку первого потока.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"syscall"
	"time"
)

func slowSyscall(wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("  [Syscall] Вход в долгий системный вызов...")
	// Имитация долгого системного вызова nanosleep на 1.5 секунды
	var req, rem syscall.Timespec
	req.Sec = 1
	req.Nsec = 500000000
	syscall.Nanosleep(&req, &rem)
	fmt.Println("  [Syscall] Выход из системного вызова.")
}

func normalWorker(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < 5; i++ {
		time.Sleep(100 * time.Millisecond)
		fmt.Printf("  [Worker %d] Шаг %d успешно выполнен.\n", id, i)
	}
}

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("GOMAXPROCS = 1. Запуск долгого syscall и обычных горутин...")

	var wg sync.WaitGroup
	wg.Add(3)

	go slowSyscall(&wg)
	go normalWorker(1, &wg)
	go normalWorker(2, &wg)

	wg.Wait()
	fmt.Println("Все горутины успешно завершились, handoff сработал!")
}
```

## Под капотом

Когда поток `sysmon` в функции `retake(now)` видит `p.status == _Psyscall`, он сравнивает текущее время с `p.syscalltick`. Если разница больше 10 мс или очередь `runq` не пуста, `sysmon` атомарно переводит `P` из `_Psyscall` в `_Pidle` через `atomic.Cas` и немедленно вызывает `handoffp(pp)`, чтобы поднять новый поток M и спасти оставшиеся горутины.

## Подводные камни

Если программа выполняет тысячи параллельных блокирующих вызовов `syscall`, рантайм Go может создать до 10 000 потоков ОС (дефолтный лимит `debug.SetMaxThreads`). По достижении этого лимита рантайм аварийно завершает процесс с паникой `fatal error: checkdead: no m for timer`.

## На собеседовании

**Вопрос с собеседования:** Что произойдет, если в программе с `GOMAXPROCS=1` одна горутина вызовет блокирующий `syscall.Read()` из именованного канала (FIFO), в который никто ничего не пишет?
**Ответ:** Горутина войдет в ядро ОС и заблокирует свой поток `M`. Процессор `P` перейдет в состояние `_Psyscall`.
Через 10 мс фоновый поток `sysmon` обнаружит, что `P` застрял, отберет `P` у заблокированного `M` (`handoffp`) и запустит новый поток `M2`.
Новый поток `M2` подхватит оставшиеся горутины из очереди `P`, и они продолжат нормально выполняться, несмотря на то, что `GOMAXPROCS=1` и один поток ОС наглухо заблокирован в ядре.
