# Эволюция планировщика: Кооперативное vs Некооперативное вытеснение (Preemption)

## Условие

**Кооперативное вытеснение**: Напишите горутину с бесконечным циклом без syscall'ов и函数 вызовов (`for {}`). Убедитесь, что она блокирует весь P (в Go < 1.14). Изучите, как Go 1.14+ решил это через preemptive scheduling.

## Теория

До Go 1.14 планировщик Go был **кооперативным** (Cooperative Preemption). Горутина могла уступить процессор только в точках вызова функций:
- Компилятор вставлял в пролог каждой функции проверку стека (`morestack`), которая попутно проверяла флаг вытеснения `stackguard0 = stackPreempt`.
- Если горутина содержала плотный бесконечный цикл без вызова функций (`for {}`), флаг вытеснения никогда не проверялся, и горутина навсегда монополизировала поток `M` и процессор `P`. При `GOMAXPROCS=1` вся программа зависала, и даже Garbage Collector не мог остановить мир (STW hang).

В **Go 1.14+** внедрено **асинхронное некооперативное вытеснение** (Non-cooperative Async Preemption) на основе сигналов ОС:
- Поток мониторинга `sysmon` детектирует горутину, работающую дольше 10 мс.
- `sysmon` отправляет потоку `M` сигнал `SIGURG` (на Unix-системах).
- Обработчик сигнала `runtime.sighandler` прерывает поток, проверяет безопасность точки остановки (safe point) и сохраняет контекст регистров, переводя горутину в очередь ожидания.

## Решение по шагам

1. Создаем горутину с плотным циклом без вызовов функций.
2. В Go 1.14+ проверяем, что программа не зависает и вторая горутина успешно получает управление.
3. Демонстрируем точку безопасного останова и логику работы `sysmon`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Демонстрация вытеснения плотного цикла (Go 1.14+ Async Preemption)")

	completed := false

	// Горутина с плотным циклом без вызовов функций и аллокаций
	go func() {
		for !completed {
			// В Go < 1.14 здесь происходило вечное зависание при GOMAXPROCS=1.
			// В Go 1.14+ поток sysmon посылает сигнал SIGURG и вытесняет горутину.
		}
		fmt.Println("Плотный цикл завершен!")
	}()

	time.Sleep(100 * time.Millisecond)
	completed = true
	time.Sleep(50 * time.Millisecond)
	fmt.Println("Главная горутина успешно получила CPU и завершила программу.")
}
```

ℹ️ Вытеснение пустого цикла в Go 1.14+

**`Терминал`**

```bash
go run main.go
# Вывод в Go 1.14+:
# Демонстрация вытеснения плотного цикла (Go 1.14+ Async Preemption)
# Плотный цикл завершен!
# Главная горутина успешно получила CPU и завершила программу.
```

## Под капотом

Когда поток `sysmon` видит, что `_Grunning` горутина исполняется непрерывно > 10 мс, вызывается `preemptone(p)`. Планировщик устанавливает `gp.preempt = true` и `gp.stackguard0 = stackPreempt`. Если горутина не входит в вызовы функций, вызывается `signalM(mp, sigPreempt)` (сигнал `SIGURG`). Ядро ОС прерывает выполнение инструкций и переходит в `runtime.sighandler`. Если текущий PC находится в безопасной точке (не во внутренностях рантайма и не в блоке unsafe без GC-карт), рантайм эмулирует вызов `runtime.asyncPreempt`, сохраняет регистры и вызывает `schedule()`.

## Подводные камни

Вытеснение по сигналам `SIGURG` не может произойти, если код исполняет инструкцию в unsafe-блоках, удерживает внутренние низкоуровневые спинлоки рантайма или непрерывно находится в цикле без safe-points. Также отладчики (`gdb`, старые версии `delve`) могут перехватывать `SIGURG`, требуя добавления флага `handle SIGURG nostop noprint pass`.

## На собеседовании

**Вопрос с собеседования:** Как именно работает асинхронное вытеснение (preemption) в Go, почему выбран именно сигнал `SIGURG` и где вытеснение невозможно?
**Ответ:** Поток `sysmon` раз в 10–20 мс проверяет длительность непрерывной работы горутины. Если она превысила квант (10 мс), `sysmon` отправляет потоку `M` POSIX-сигнал `SIGURG`. Сигнал `SIGURG` выбран потому, что в Linux/Unix он традиционно используется для устаревших срочных данных сокетов (Out-of-band data) и практически не задействован реальными приложениями, что исключает конфликты с `SIGIO`/`SIGUSR1`/`SIGUSR2`.
Вытеснение невозможно:
1) В критических секциях самого рантайма (`systemstack`, обработка паник);
2) В точках, где компилятор не сгенерировал стек-карты для сборщика мусора (GC safe-points);
3) В atomic-инструкциях процессора и атомарных операциях assembly.
