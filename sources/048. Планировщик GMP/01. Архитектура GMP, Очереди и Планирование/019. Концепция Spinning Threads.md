# Концепция Spinning Threads: баланс между энергопотреблением и задержкой запуска

## Условие

**Spinning threads**: Изучите концепцию spinning M's — потоков, которые активно ищут работу перед тем как заснуть. Это снижает latency при появлении новых горутин.

## Теория

Потоки операционной системы (M) в планировщике Go могут находиться в трех состояниях:
1. **Executing M:** Поток привязан к P и активно исполняет Go-код (`_Grunning`).
2. **Spinning M:** Поток не имеет работы в локальной очереди, но **не уходит в сон ядра ОС**. Он активно опрашивает GRQ, netpoller и крадет задачи у других P.
3. **Idle M:** Поток не нашел работы, сбросил статус spinning и заснул на семафоре ядра (`futex`).

Рантайм Go поддерживает строгий инвариант: **всегда поддерживать хотя бы один Spinning M, пока есть незанятые процессоры P**. Это позволяет новой созданной горутине мгновенно найти исполнителя без ожидания пробуждения потока ОС (~10-30 мкс).

## Решение по шагам

1. Создаем программу с неравномерной генерацией задач.
2. Запускаем с флагом `GODEBUG=schedtrace=100`.
3. Анализируем поле `spinningthreads` в выводе терминала.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Println("Наблюдайте spinningthreads в schedtrace...")

	// Генерируем импульсы нагрузки
	for i := 0; i < 5; i++ {
		go func(id int) {
			time.Sleep(50 * time.Millisecond)
		}(i)
		time.Sleep(150 * time.Millisecond)
	}

	time.Sleep(500 * time.Millisecond)
	fmt.Println("Тест завершен.")
}
```

ℹ️ Импульсная нагрузка для наблюдения за spinningthreads

**`Терминал`**

```bash
go build -o spin_demo main.go
GODEBUG=schedtrace=100 ./spin_demo
# Пример лога со spinningthreads:
# SCHED 102ms: gomaxprocs=4 idleprocs=3 threads=6 spinningthreads=1 runqueue=0 [0 0 0 0]
```

## Под капотом

В `src/runtime/proc.go` логика `resetspinning()` гарантирует, что количество spinning-потоков не превышает `gomaxprocs - busy_procs`. Когда создается новая горутина (`wakep()`), планировщик проверяет: если нет ни одного spinning-потока и есть свободный P, он пробуждает один спящий M, который переходит в spinning-режим.

## Подводные камни

В облачных окружениях с оплатой за каждый такт CPU (Serverless, AWS Lambda) чрезмерный спиннинг мог бы тратить лишние такты, но планировщик Go быстро переводит невостребованные потоки в сон при длительном отсутствии задач.

## На собеседовании

**Вопрос с собеседования:** Почему планировщик Go тратит такты CPU на Spinning M вместо того, чтобы сразу усыплять потоки ОС, если работы нет?
**Ответ:** Потому что системный вызов усыпления и последующего пробуждения потока через `futex` в Linux стоит от 5 до 30 микросекунд и сбрасывает кэши процессора. Если поток сразу засыпает, любая новая горутина, созданная через микросекунду, будет ждать пробуждения потока ОС, что создаст неприемлемые скачки задержек (tail latency p99). Spinning M держит одно ядро «наготове», обеспечивая субмикросекундный старт новых задач.
