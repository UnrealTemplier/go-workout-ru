# CPU-bound горутины и верификация загрузки ядер операционной системы

## Условие

Выведи `runtime.GOMAXPROCS(0)` (количество логических процессоров P). Установи `GOMAXPROCS(1)`. Запусти две CPU-bound горутины в бесконечном цикле. Посмотри через `top` или Activity Monitor, что загружен только 1 поток ОС.

## Теория

Конкурентность (Concurrency) — это структура программы, разбитой на независимые процессы выполнения.
Параллелизм (Parallelism) — это одновременное физическое исполнение нескольких инструкций на нескольких физических/логических ядрах CPU.

При вызове `runtime.GOMAXPROCS(0)` рантайм не меняет текущее значение, а возвращает установленное число P.
Если установить `GOMAXPROCS(1)` и запустить 2 бесконечные горутины, планировщик Go будет попеременно переключать их на одном ядре CPU. Монитор процессов операционной системы (`top`, `ps`, `htop`) покажет суммарную утилизацию процесса ровно в 100% (один поток ОС), подтверждая, что параллельное исполнение ограничено одним ядром.

## Решение по шагам

1. Получаем текущее значение `GOMAXPROCS` вызовом `runtime.GOMAXPROCS(0)`.
2. Устанавливаем `GOMAXPROCS(1)`.
3. Запускаем две горутины с математическими расчетами в бесконечных циклах.
4. В главной горутине выводим PID процесса `os.Getpid()`.
5. Через `top -p <PID>` или `ps` проверяем процент загрузки процессора.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"os"
	"runtime"
	"time"
)

func cpuWorker(id int) {
	var val float64 = 1.0001
	for {
		val = math.Sin(val) * math.Cos(val) + 1.0001
		if val > 1e9 {
			val = 1.0001
		}
	}
}

func main() {
	originalP := runtime.GOMAXPROCS(0)
	fmt.Printf("Изначальный GOMAXPROCS: %d (NumCPU: %d)\n", originalP, runtime.NumCPU())

	runtime.GOMAXPROCS(1)
	fmt.Printf("Установлен GOMAXPROCS: %d\n", runtime.GOMAXPROCS(0))
	fmt.Printf("PID процесса: %d. Наблюдайте загрузку CPU ровно ~100%% (1 ядро).\n", os.Getpid())

	go cpuWorker(1)
	go cpuWorker(2)

	time.Sleep(3 * time.Second)
	fmt.Println("Тест завершен.")
}
```

ℹ️ Фиксация GOMAXPROCS=1 для двух CPU-bound горутин

**`Терминал`**

```bash
go run main.go

# Установлен GOMAXPROCS: 1
```

## Под капотом

Планировщик Go гарантирует, что одновременно в состоянии `_Grunning` может находиться не более `P` горутин. Когда `GOMAXPROCS=1`, в системе активен ровно один контекст `P`. Даже если операционная система имеет 64 ядра, рантайм связывает единственный `P` с одним потоком `M`. Если обе горутины вычисляют тригонометрические функции, планировщик использует механизм вытеснения по таймеру `sysmon`, переключая горутины по кванту времени (~10 мс).

## Подводные камни

В микросервисах, запущенных в Kubernetes с квотой CPU (например `resources.limits.cpu: "500m"` или `"1"`), рантайм без `automaxprocs` видит все 32/64 ядра ноды Kubernetes и создает 32/64 `P`. Это приводит к тому, что 64 потока конкурируют за половинку ядра, вызывая катастрофический CFS Throttling и падение пропускной способности в 5-10 раз.

## На собеседовании

**Вопрос с собеседования:** Что произойдет, если в Kubernetes Pod с лимитом `cpu: 2` запустить приложение на Go без использования `automaxprocs` на физической ноде с 64 CPU?
**Ответ:** По умолчанию Go вызовет `sched_getaffinity` или системный вызов количества процессоров хоста и установит `GOMAXPROCS=64`. Планировщик создаст 64 очереди `LRQ` и запустит до 64 потоков `M`. Linux CFS (Completely Fair Scheduler) выделяет квоту 200 мс на 100 мс период (`quota/period = 2`). 64 потока израсходуют эту квоту за 3 мс, после чего ядро Linux заблокирует (throttled) процесс на оставшиеся 97 мс квоты. Возникнут огромные задержки p99/p999. Решение — использовать `go.uber.org/automaxprocs`.
