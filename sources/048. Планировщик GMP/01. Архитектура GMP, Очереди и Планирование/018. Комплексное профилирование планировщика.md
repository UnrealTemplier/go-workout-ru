# Комплексное профилирование планировщика: сопоставление очередей и времени ожидания в runtime/trace

## Условие

**Наблюдение за планировщиком через трассировку.**: Напишите программу с десятком горутин, выполняющих CPU-работу. Запустите с `GODEBUG=schedtrace=1000` и проанализируйте вывод: `SCHED`, `P`, `M`, `G`, очереди.

## Теория

В высоконагруженных системах задержка ответа сервиса (latency) часто вызвана не плохим алгоритмом, а задержками планирования (Scheduling Delay).
Если горутина готова к работе (`_Grunnable`), но ни один поток M не берет ее на выполнение из-за дефицита P или длинных очередей, время ожидания растет.
Инструмент `runtime/trace` предоставляет метрику **Scheduler Latency Profile**, которая показывает распределение времени ожидания горутин в очередях перед запуском.

## Решение по шагам

1. Запускаем трассировку программы с разнородными горутинами (CPU-bound + I/O).
2. Анализируем отчет `go tool trace`.
3. Изучаем профиль Scheduler Latency Profile.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/trace"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)

	f, err := os.Create("trace_sched.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	var wg sync.WaitGroup
	const count = 30
	wg.Add(count)

	for i := 0; i < count; i++ {
		go func(id int) {
			defer wg.Done()
			if id%2 == 0 {
				// CPU-нагрузка
				var sum int
				for j := 0; j < 5000000; j++ {
					sum += j
				}
				_ = sum
			} else {
				// I/O имитация
				time.Sleep(10 * time.Millisecond)
			}
		}(i)
	}

	wg.Wait()
	fmt.Println("Трассировка успешно записана в trace_sched.out")
}
```

ℹ️ Профилирование смешанной нагрузки в runtime/trace

**`Терминал`**

```bash
go run main.go
# Запуск веб-сервера трассировки:
# go tool trace trace_sched.out
```

## Под капотом

В `trace` сохраняется точный момент времени смены статуса с `_Gwaiting` на `_Grunnable`, и затем с `_Grunnable` на `_Grunning`. Разность этих двух отметок дает чистую задержку планирования (Scheduling Delay). В здоровой системе она не превышает 10–50 микросекунд.

## Подводные камни

Если задержка планирования достигает десятков миллисекунд, это верный признак либо нехватки `GOMAXPROCS`, либо наличия горутин, монополизирующих потоки M без возможности прерывания.

## На собеседовании

**Вопрос с собеседования:** В каких случаях в `go tool trace` можно увидеть длительные горизонтальные участки на графике «Goroutines in Runnable state»?
**Ответ:** Участок с высоким числом `Runnable` горутин означает, что горутины уже готовы к выполнению (их канал готов, I/O завершился или кончился таймер), но все процессоры `P` на 100% заняты другими задачами.
Причины:
1) CPU-bound перегрузка сервиса (недостаточно ядер для текущего трафика);
2) Неверно настроенный `GOMAXPROCS` в Docker-контейнере;
3) Дефицит потоков M при длительных блокирующих системных вызовах.
