# Бенчмарк переключения контекста горутин: механизмы goready и gopark

## Условие

Напишите «бенчмарк на количество переключений контекста»: две goroutine обмениваются данными через небуферизованный канал в цикле. Покажите, что при `GOMAXPROCS=1` они всё равно чередуются. Объясните механизм `goready`/`gopark`.

## Теория

Переключение контекста между горутинами при операциях с каналами управляется двумя ключевыми функциями рантайма:
- **`runtime.gopark()`:** Переводит текущую горутину из состояния `_Grunning` в `_Gwaiting`, отцепляет ее от потока M и сохраняет ее контекст. Вызывается, когда горутина пытается прочитать из пустого канала или записать в полный небуферизованный канал.
- **`runtime.goready()`:** Переводит заблокированную горутину из состояния `_Gwaiting` обратно в `_Grunnable` и помещает ее в очередь планировщика (обычно в приоритетный слот `runnext` текущего P). Вызывается парной горутиной, совершившей отправку или прием данных.

Даже при `GOMAXPROCS=1` две горутины, обменивающиеся данными по небуферизованному каналу, гарантированно чередуются в строгом порядке ping-pong, выполняя переключение контекста всего за ~30–50 наносекунд.

## Решение по шагам

1. Создаем пару горутин, обменивающихся целочисленными сообщениями через небуферизованный канал.
2. Реализуем замер времени N итераций пинг-понга.
3. Рассчитываем среднее время одного переключения контекста в наносекундах.
4. Проверяем работу при `GOMAXPROCS=1`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	const iterations = 1000000

	ch1 := make(chan int)
	ch2 := make(chan int)

	go func() {
		for i := 0; i < iterations; i++ {
			val := <-ch1
			ch2 <- val + 1
		}
	}()

	start := time.Now()
	for i := 0; i < iterations; i++ {
		ch1 <- i
		<-ch2
	}
	elapsed := time.Since(start)

	// На каждую итерацию приходится 2 переключения контекста
	totalSwitches := iterations * 2
	nsPerSwitch := float64(elapsed.Nanoseconds()) / float64(totalSwitches)

	fmt.Printf("Итераций: %d, Всего переключений: %d\n", iterations, totalSwitches)
	fmt.Printf("Общее время: %v, Среднее время переключения контекста: %.2f нс\n", elapsed, nsPerSwitch)
}
```

ℹ️ Бенчмарк переключения контекста через небуферизованный канал

**`Терминал`**

```bash
go run main.go
# Пример вывода:
# Итераций: 1000000, Всего переключений: 2000000
# Общее время: 82.35ms, Среднее время переключения контекста: 41.18 нс
```

## Под капотом

В функции `chansend()` в `src/runtime/chan.go`: если на канале уже ожидает получатель (в структуре `waitq`), данные копируются напрямую из стека отправителя в стек получателя через `memmove` (минуя буфер канала!). Затем отправитель вызывает `goready(gp, 3)`: получатель просыпается и помещается в слот `runnext` текущего процессора P. Когда отправитель блокируется на следующем шаге через `gopark()`, планировщик мгновенно берет получателя из `runnext` с нулевой задержкой поиска в очередях.

## Подводные камни

Использование каналов для передачи миллионов сообщений внутри одного потока вычислений несет накладные расходы на `gopark`/`goready` (~40-50 нс). Для экстремально быстрых локальных очередей данных внутри одной горутины обычный слайс или ring buffer работают за ~1 нс.

## На собеседовании

**Вопрос с собеседования:** Что такое слот `runnext` у процессора P и почему он обеспечивает колоссальный выигрыш в задержках при общении через каналы?
**Ответ:** `runnext` — это специальное атомарное поле в структуре `p`, рассчитанное ровно на одну горутину. Когда горутина А разблокирует горутину Б (например, отправкой в канал), рантайм помещает Б не в конец локальной очереди из 256 элементов, а прямо в `runnext`.
Когда горутина А сразу после этого встает в ожидание (`gopark`), планировщик берет горутину из `runnext` первой. Это:
1) Гарантирует максимальную локальность кэша CPU (L1/L2), так как данные только что были записаны в стек горутины Б;
2) Устраняет необходимость захвата очередей или поиска работы;
3) Минимизирует джиттер при межгорутинном взаимодействии.
