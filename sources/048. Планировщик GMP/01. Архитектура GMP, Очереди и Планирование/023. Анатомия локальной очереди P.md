# Анатомия локальной очереди P: кольцевой буфер runqhead, runqtail и runnext

## Условие

Нарисуйте (и реализуйте визуализацию в stdout) схему локальных очередей P (`runqhead`, `runqtail`, `runq` — массив на 256 слотов) и глобальной очереди (`sched.lock`). Симулируйте добавление 1000 goroutine и покажите, как они распределяются.

## Теория

Локальная очередь процессора `P` (`runq`) спроектирована для максимальной скорости без использования мьютексов.
Она состоит из:
1. `runnext` (`guintptr`): приоритетный указатель на следующую горутину. Имеет абсолютный приоритет при вызове `runqget()`.
2. `runq` (`[256]guintptr`): кольцевой массив указателей на горутины.
3. `runqhead` (`uint32`): монотонный счетчик головы очереди (откуда забираются задачи).
4. `runqtail` (`uint32`): монотонный счетчик хвоста очереди (куда добавляются задачи).

Поскольку счетчики 32-битные и инкрементируются монотонно, реальный индекс в массиве вычисляется как `head % 256` и `tail % 256`.
Размер очереди строго равен 256. Разница `tail - head` определяет текущую длину очереди.

## Решение по шагам

1. Реализуем модель локальной очереди процессора P на Go.
2. Демонстрируем добавление задач, вытеснение половины очереди при переполнении и чтение из `runnext`.
3. Визуализируем состояние указателей головы, хвоста и буфера.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

// Модель структуры локальной очереди P из src/runtime/runtime2.go
type LocalQueueModel struct {
	runnext uint32 // 0 означает пусто
	runq    [256]uint32
	head    uint32
	tail    uint32
}

func (q *LocalQueueModel) Put(gid uint32, grq *[]uint32) {
	// Если runnext пуст, помещаем туда
	if q.runnext == 0 {
		q.runnext = gid
		return
	}

	// Вытесняем старый runnext в кольцевой буфер
	toEnqueue := q.runnext
	q.runnext = gid

	// Проверяем переполнение
	if q.tail-q.head < 256 {
		q.runq[q.tail%256] = toEnqueue
		q.tail++
	} else {
		// Сброс половины очереди в GRQ
		fmt.Printf("⚠️ LRQ переполнена! Сброс 128 задач в GRQ (head=%d, tail=%d)\n", q.head, q.tail)
		for i := 0; i < 128; i++ {
			*grq = append(*grq, q.runq[q.head%256])
			q.head++
		}
		q.runq[q.tail%256] = toEnqueue
		q.tail++
	}
}

func (q *LocalQueueModel) Pop() (uint32, bool) {
	if q.runnext != 0 {
		gid := q.runnext
		q.runnext = 0
		return gid, true
	}
	if q.tail == q.head {
		return 0, false
	}
	gid := q.runq[q.head%256]
	q.head++
	return gid, true
}

func main() {
	var q LocalQueueModel
	var grq []uint32

	fmt.Println("Симуляция добавления 300 горутин в локальную очередь P:")
	for gid := uint32(1); gid <= 300; gid++ {
		q.Put(gid, &grq)
	}

	fmt.Printf("\nИтог очереди P:\n")
	fmt.Printf("  runnext: G%d\n", q.runnext)
	fmt.Printf("  head: %d, tail: %d (в очереди LRQ: %d)\n", q.head, q.tail, q.tail-q.head)
	fmt.Printf("  В глобальной очереди GRQ: %d задач\n", len(grq))
}
```

## Под капотом

В реальном рантайме доступ владельца P к `runqtail` не требует атомарных инструкций, так как только владеющий M добавляет элементы. Однако операцию `runqsteal` выполняют другие потоки M, поэтому `runqhead` инкрементируется атомарной операцией `atomic.CasRel`. Это позволяет владельцу и ворам работать конкурентно без использования мьютексов.

## Подводные камни

Если разработчик пытается сделать собственную lock-free очередь без учета барьеров памяти (memory barriers) и ABA-проблемы, неизбежны гонки данных. Планировщик Go использует 32-битные монотонные счетчики без сброса, что исключает ABA-проблему при разнице head/tail.

## На собеседовании

**Вопрос с собеседования:** Почему размер локальной очереди `P` равен ровно 256, а не динамически расширяется как слайс?
**Ответ:** Фиксированный размер 256 выбран по трем причинам:
1) **Предсказуемость памяти:** Каждая структура `P` занимает фиксированный объем памяти, известный на этапе компиляции, и не требует динамических аллокаций в куче;
2) **Кэш-линии процессора:** Буфер из 256 указателей занимает ровно 2 КБ памяти (256 * 8 байт), что идеально укладывается в быстрый L1/L2 кэш ядра CPU;
3) **Предотвращение монополизации:** Если бы очередь была бесконечной, один загруженный P мог бы накопить миллион задач, пока другие ядра CPU простаивали бы в неведении. Лимит в 256 задач форсирует сброс излишков в GRQ и стимулирует work stealing другими ядрами.
