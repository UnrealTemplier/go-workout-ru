# Детектор дедлоков рантайма (Runtime Deadlock Detector): fatal error: all goroutines are asleep

## Условие

Создайте deadlock через `sync.Mutex` в одной goroutine и попытку `Lock()` в другой. Проанализируйте `runtime.Stack()`: покажите, где в стеке виден `gopark` на `semacquire`. Объясните, как `M` освобождается для других задач.

## Теория

Рантайм Go содержит встроенный встроенный сторож взаимных блокировок (Deadlock Detector):
Функция `checkdead()` вызывается планировщиком в `schedule()`, когда:
- Все процессоры P находятся в статусе `_Pidle`;
- Нет ни одного работающего потока M;
- Нет событий в очереди таймеров и netpoller.

Если при этом общее число горутин `sched.ngsys - sched.gFree` больше 0, рантайм понимает: **программа зашла в глухой тупик (Deadlock)**. Ни одна горутина больше никогда не сможет проснуться.
Рантайм выводит фатальную панику:
`fatal error: all goroutines are asleep - deadlock!` с полным дампом стеков всех застрявших горутин.

## Решение по шагам

1. Создаем классический дедлок на двух мьютексах или небуферизованном канале.
2. Запускаем программу.
3. Анализируем фатальную ошибку `checkdead`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	fmt.Println("Демонстрация работы рантайм детектора дедлоков (checkdead)...")

	var mu1, mu2 sync.Mutex
	ready := make(chan struct{})

	// Горутина 1: захватывает mu1, затем mu2
	go func() {
		mu1.Lock()
		defer mu1.Unlock()
		close(ready)
		time.Sleep(20 * time.Millisecond)
		mu2.Lock()
		defer mu2.Unlock()
	}()

	// Горутина 2 (main): захватывает mu2, затем mu1
	<-ready
	mu2.Lock()
	defer mu2.Unlock()

	fmt.Println("Попытка захватить mu1...")
	mu1.Lock()
	defer mu1.Unlock()

	fmt.Println("Этот код никогда не выполнится.")
}
```

## Под капотом

В `src/runtime/proc.go` функция `checkdead()` проверяет:
`if sched.nmspinning == 0 && sched.npidle == gomaxprocs { throw("all goroutines are asleep - deadlock!") }`.
Эта проверка работает **только если заблокированы ВСЕ пользовательские горутины программы**. Если хотя бы одна горутина крутит бесконечный фоновый `time.Sleep` или слушает сетевой сокет, `checkdead` не сработает, и скрытый дедлок останется незамеченным.

## Подводные камни

В сетевых веб-серверах фоновый цикл `http.ListenAndServe()` держит активный дескриптор в `netpoll`. Поэтому `checkdead()` в веб-сервисах **не срабатывает**: при локальном дедлоке двух горутин процесс просто зависнет без паники.

## На собеседовании

**Вопрос с собеседования:** Почему встроенный в Go детектор дедлоков (`fatal error: all goroutines are asleep - deadlock!`) срабатывает в простых тестах, но никогда не спасает реальные production HTTP-серверы?
**Ответ:** Детектор `checkdead()` проверяет глобальное условие: в системе не должно быть **ни одной** горутины, способной продолжить работу.
В реальном веб-сервисе всегда работают:
1) Горутина `sysmon`;
2) Сетевой слушатель `netpoll` (ожидающий входящие HTTP-соединения);
3) Фоновые тикеры метрик.
Поскольку `netpoller` жив, рантайм считает, что из сети в любой момент может прийти пакет, который разблокирует горутины. Поэтому локальные дедлоки на уровне отдельных хендлеров не детектируются рантаймом. Для их обнаружения применяют таймауты (`context.WithTimeout`) и pprof.
