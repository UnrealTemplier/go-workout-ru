# Container-Aware GOMAXPROCS: интеграция go.uber.org/automaxprocs в Kubernetes

## Условие

**Container-aware GOMAXPROCS**: Используйте `go.uber.org/automaxprocs` для автоматической настройки GOMAXPROCS based on container CPU quota (важно для Kubernetes).

## Теория

При развертывании в Kubernetes контейнеру часто назначают квоты процессора:
```yaml
resources:
  limits:
    cpu: "2"
```
Однако стандартный Go рантайм определяет `GOMAXPROCS` через `runtime.NumCPU()`, который считывает количество ядер **физического хоста** (например, 64 ядра).
В результате:
- Go создает 64 процессора P и 64 потока M;
- CFS квота ядра Linux в 2 ядра расходуется за долю кванта;
- Под подвергается жесткому CFS Throttling (задержки возрастают в 10–20 раз).

Библиотека `go.uber.org/automaxprocs` автоматически считывает лимиты из `/sys/fs/cgroup/cpu/cpu.cfs_quota_us` (cgroups v1) или `cpu.max` (cgroups v2) и устанавливает `GOMAXPROCS` равным квоте округленной вниз (или вверх).

## Решение по шагам

1. Демонстрируем подключение `automaxprocs` через blank-import `_ "go.uber.org/automaxprocs"`.
2. Реализуем fallback-алгоритм вычисления CFS-квоты вручную на Go.
3. Проверяем корректность вычисления.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"os"
	"runtime"
	"strconv"
	"strings"
)

// Упрощенный парсер cgroups v1 для демонстрации логики automaxprocs
func getContainerCPULimit() (int, bool) {
	quotaBytes, err := os.ReadFile("/sys/fs/cgroup/cpu/cpu.cfs_quota_us")
	if err != nil {
		return 0, false // Не в контейнере или cgroups v2
	}
	periodBytes, err := os.ReadFile("/sys/fs/cgroup/cpu/cpu.cfs_period_us")
	if err != nil {
		return 0, false
	}

	quota, err1 := strconv.ParseFloat(strings.TrimSpace(string(quotaBytes)), 64)
	period, err2 := strconv.ParseFloat(strings.TrimSpace(string(periodBytes)), 64)

	if err1 != nil || err2 != nil || quota <= 0 || period <= 0 {
		return 0, false // Лимит не задан (-1)
	}

	cores := int(math.Floor(quota / period))
	if cores < 1 {
		cores = 1
	}
	return cores, true
}

func main() {
	hostCPU := runtime.NumCPU()
	currentP := runtime.GOMAXPROCS(0)

	fmt.Printf("Аппаратных ядер хоста: %d\n", hostCPU)
	fmt.Printf("Текущий GOMAXPROCS: %d\n", currentP)

	if limit, ok := getContainerCPULimit(); ok {
		fmt.Printf("Обнаружен лимит контейнера: %d CPU\n", limit)
		runtime.GOMAXPROCS(limit)
		fmt.Printf("GOMAXPROCS автоматически адаптирован к: %d\n", runtime.GOMAXPROCS(0))
	} else {
		fmt.Println("Контейнерные лимиты CFS не обнаружены, используется значение по умолчанию.")
	}
}
```

ℹ️ Логика адаптации GOMAXPROCS под cgroups

**`Терминал`**

```bash

```

## Под капотом

В cgroups v2 параметры квоты объединены в файл `/sys/fs/cgroup/cpu.max` в формате `max 100000` (без лимита) или `200000 100000` (квота 2 ядра). `automaxprocs` поддерживает обе версии cgroups и логирует скорректированное значение в `stdlog` при старте программы.

## Подводные камни

Если лимит задан как дробное число (например `cpu: 500m` или `1.5`), `automaxprocs` по умолчанию округляет вниз до 1, предотвращая троттлинг, но это может снизить пиковую производительность, если требуется дробный оверкоммит.

## На собеседовании

**Вопрос с собеседования:** Что произойдет с сервисом на Go в Kubernetes, если у пода `limits.cpu: 1`, но на ноде 32 ядра, и разработчик не подключил `automaxprocs`?
**Ответ:** Сервис установит `GOMAXPROCS=32`.
При поступлении параллельных запросов рантайм поднимет до 32 потоков ОС, которые параллельно начнут вычисления.
Период квоты Linux CFS по умолчанию составляет 100 мс, а лимит пода — 1 CPU (100 мс процессорного времени за период).
32 потока израсходуют 100 мс квоты суммарно всего за **3.1 миллисекунды** (100 мс / 32 потока).
Оставшиеся **96.9 миллисекунд** каждого периода весь под будет полностью заблокирован ядром Linux (CFS Throttling).
В метриках Prometheus возникнет огромный рост p99 latency и троттлинга (`container_cpu_cfs_throttled_periods_total`).
