# «Отравленная» горутина: влияние непрерывного runtime.Gosched() на планировщик

## Условие

Реализуйте «отравленную» goroutine: бесконечный цикл с вызовом `runtime.Gosched()` каждую итерацию. Сравните с версией без `Gosched()`. Объясните разницу между кооперативной отдачей управления и принудительным вытеснением.

## Теория

Что происходит, если горутина исполняет бесконечный цикл, состоящий исключительно из `runtime.Gosched()`?
```go
for { runtime.Gosched() }
```
Такая горутина называется «отравленной» (poisoned / spinning):
- При каждом вызове она помещается в Глобальную Очередь (GRQ);
- На каждом 61 тике планирования каждый процессор P забирает ее из GRQ;
- Горутина не выполняет никакой полезной работы, но создает непрерывную нагрузку на `sched.lock` и расходует кванты планировщика, конкурируя с полезными задачами.

## Решение по шагам

1. Запускаем «отравленную» горутину.
2. Параллельно запускаем полезную задачу и замеряем время ее исполнения.
3. Сравниваем производительность с нормальным режимом.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)
	fmt.Println("Тестирование влияния отравленной горутины с Gosched()...")

	stopPoison := int32(0)
	var schedCount int64

	// Отравленная горутина: бесконечный цикл Gosched()
	go func() {
		for atomic.LoadInt32(&stopPoison) == 0 {
			atomic.AddInt64(&schedCount, 1)
			runtime.Gosched()
		}
	}()

	// Полезная работа
	var wg sync.WaitGroup
	start := time.Now()
	const workers = 4
	wg.Add(workers)

	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			var acc uint64
			for j := 0; j < 5000000; j++ {
				acc += uint64(j)
			}
			_ = acc
		}()
	}

	wg.Wait()
	duration := time.Since(start)
	atomic.StoreInt32(&stopPoison, 1)

	fmt.Printf("Полезная работа выполнена за: %v\n", duration)
	fmt.Printf("Отравленная горутина успела совершить %d вызовов Gosched()\n", atomic.LoadInt64(&schedCount))
}
```

ℹ️ Исследование нагрузки от паразитных циклов Gosched

**`Терминал`**

```bash
go run main.go
# Вывод:
# Тестирование влияния отравленной горутины с Gosched()...
# Полезная работа выполнена за: ~18.5ms
# Отравленная горутина успела совершить ~450000 вызовов Gosched()
```

## Под капотом

Вызов `Gosched()` требует переключения на стек `g0` через `mcall` и захвата мьютекса `sched.lock` для помещения в GRQ. Сотни тысяч вызовов `Gosched()` в секунду превращают быстрый lock-free планировщик в узкое бутылочное горлышко из-за постоянной борьбы за спинлок глобальной очереди.

## Подводные камни

Никогда не используйте циклы вида `for condition { runtime.Gosched() }` в качестве самодельных каналов или условных переменных. Используйте `sync.Cond` или каналы, которые переводят горутину в честный сон `_Gwaiting` с нулевой нагрузкой на CPU.

## На собеседовании

**Вопрос с собеседования:** Почему активное ожидание через `runtime.Gosched()` в цикле считается грубейшим антипаттерном в Go?
**Ответ:**
1) **Паразитная утилизация CPU:** Процессор загружен на 100%, сжигая электроэнергию и квоты в облаке;
2) **Деградация глобального спинлока:** Каждый вызов `Gosched()` захватывает `sched.lock`, блокируя другие потоки M при доступе к GRQ;
3) **Инвалидация кэшей:** Постоянное переключение горутины между процессорами разрушает кэш-линии L1/L2 процессора;
4) Вместо этого правильный паттерн — `sync.Cond` или чтение из канала, где горутина паркуется через `gopark()` и просыпается по событию с нулевым overhead.
