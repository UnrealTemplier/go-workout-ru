# Различие между NumCPU() и GOMAXPROCS: физические ядра против логических контекстов

## Условие

**NumCPU vs GOMAXPROCS**: Изучите разницу. `NumCPU()` — это hardware cores, `GOMAXPROCS` — это logical processors для Go scheduler. В контейнерах с cgroups они могут отличаться.

## Теория

Фундаментальное отличие:
- **`runtime.NumCPU()`:** Возвращает количество логических ядер процессора, доступных процессу на аппаратном уровне (определяется ОС через `sysconf(_SC_NPROCESSORS_ONLN)` или affinity mask). Это константа аппаратной платформы.
- **`runtime.GOMAXPROCS(n)`:** Задает количество **логических процессоров планировщика P**, управляющих максимальным числом одновременно выполняемых горутин Go.

По умолчанию в Go 1.5+ `GOMAXPROCS == NumCPU()`. Однако в контейнерах, микросервисах и при тюнинге производительности эти величины могут кардинально различаться.

## Решение по шагам

1. Считываем аппаратное число ядер через `runtime.NumCPU()`.
2. Считываем текущий `GOMAXPROCS(0)`.
3. Демонстрируем независимость этих параметров.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	hardwareCores := runtime.NumCPU()
	currentGomaxprocs := runtime.GOMAXPROCS(0)

	fmt.Printf("Аппаратных логических ядер (NumCPU): %d\n", hardwareCores)
	fmt.Printf("Текущее число контекстов P (GOMAXPROCS): %d\n", currentGomaxprocs)

	// Меняем GOMAXPROCS на нестандартное значение
	customP := 3
	runtime.GOMAXPROCS(customP)

	fmt.Printf("\nПосле изменения:\n")
	fmt.Printf("  NumCPU по-прежнему: %d\n", runtime.NumCPU())
	fmt.Printf("  Новый GOMAXPROCS:   %d\n", runtime.GOMAXPROCS(0))
}
```

ℹ️ Сравнение NumCPU и GOMAXPROCS

**`Терминал`**

```bash
go run main.go
# Вывод:
# Аппаратных логических ядер (NumCPU): 8
# Текущее число контекстов P (GOMAXPROCS): 8
# 
# После изменения:
#   NumCPU по-прежнему: 8
#   Новый GOMAXPROCS:   3
```

## Под капотом

`runtime.NumCPU()` запрашивает системную информацию ядра один раз при инициализации рантайма и кэширует результат во внутренней переменной `ncpu`. Изменение `GOMAXPROCS` реаллоцирует внутренний массив `allp` структуры планировщика, не затрагивая `ncpu`.

## Подводные камни

Внутри Docker-контейнеров `NumCPU()` возвращает число ядер физического сервера (например 64), даже если контейнеру выделено всего 2 ядра CPU квоты cgroups.

## На собеседовании

**Вопрос с собеседования:** Почему в Kubernetes-подах использование `runtime.NumCPU()` в качестве размера пула воркеров считается опасной ошибкой?
**Ответ:** Потому что внутри контейнера `runtime.NumCPU()` не знает о лимитах CFS (`cpu.cfs_quota_us`) и возвращает суммарное количество ядер физической ноды Kubernetes (например, 64 или 128 ядер).
Если создать пул из 128 воркеров на поде с лимитом `cpu: 1`, все 128 потоков начнут конкурировать за одно ядро, исчерпают 100-мс квоту за доли миллисекунды и попадут под жесткий троттлинг ядра Linux (CFS Throttling). Задержки сервиса вырастут в десятки раз. Решение — использовать `go.uber.org/automaxprocs`.
