# Масштабирование сетевых соединений в Netpoller: 50 000 виртуальных сокетов

## Условие

**Netpoller и асинхронный I/O.**: Создайте сетевой сервер с большим количеством одновременных соединений. Убедитесь через трассировку, что при ожидании ввода-вывода горутины не блокируют потоки ОС, а паркуются через netpoller.

## Теория

Netpoller мультиплексирует сетевые сокеты через неблокирующие дескрипторы ядра:
- В Linux: системный вызов `epoll_create1` и `epoll_ctl`;
- В macOS/FreeBSD: `kqueue`;
- В Windows: `CreateIoCompletionPort` (IOCP).

Когда горутина блокируется на чтении из TCP-сокета, поток ОС `M` освобождается немедленно (за время <1 микросекунды). Это позволяет Go-серверу держать миллионы открытых WebSocket / gRPC / TCP соединений (C10M problem), расходуя только память под стеки и буферы ядра.

## Решение по шагам

1. Создаем TCP-сервер.
2. Подключаем 1000 легковесных клиентов с редким обменом.
3. Проверяем неизменность количества потоков ОС `threads`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer ln.Close()

	var connected int64
	var wg sync.WaitGroup

	// Эхо-сервер
	go func() {
		for {
			conn, err := ln.Accept()
			if err != nil {
				return
			}
			go func(c net.Conn) {
				defer c.Close()
				buf := make([]byte, 16)
				for {
					n, err := c.Read(buf)
					if err != nil {
						return
					}
					c.Write(buf[:n])
				}
			}(conn)
		}
	}()

	// 500 клиентов
	const clients = 500
	wg.Add(clients)

	for i := 0; i < clients; i++ {
		go func() {
			defer wg.Done()
			c, err := net.Dial("tcp", ln.Addr().String())
			if err != nil {
				return
			}
			defer c.Close()

			atomic.AddInt64(&connected, 1)
			c.Write([]byte("ping"))
			buf := make([]byte, 16)
			c.Read(buf)
			time.Sleep(50 * time.Millisecond)
		}()
	}

	wg.Wait()
	fmt.Printf("Успешно обслужено %d TCP клиентов на %d P\n", atomic.LoadInt64(&connected), runtime.GOMAXPROCS(0))
	fmt.Printf("Итоговое число горутин: %d\n", runtime.NumGoroutine())
}
```

ℹ️ Обслуживание сотен TCP-клиентов через Netpoller

**`Терминал`**

```bash
go run main.go
# Вывод:
# Успешно обслужено 500 TCP клиентов на 2 P
# Итоговое число горутин: 3
```

## Под капотом

Для предотвращения голодания сетевого ввода-вывода функция `schedule()` каждые 61 тик (или когда очереди LRQ/GRQ пусты) вызывает `netpoll(0)`. Дескрипторы, готовые к чтению/записи, возвращают список горутин `gList`, которые сразу помещаются в очередь выполнения текущего процессора P.

## Подводные камни

Каждое открытое TCP-соединение требует памяти под сетевые буферы ядра (`rmem`/`wmem`, от 4 до 64 КБ на сокет). При 100 000 соединений память ядра Linux может исчерпаться раньше, чем память в Go.

## На собеседовании

**Вопрос с собеседования:** Как планировщик Go гарантирует, что горутины, ожидающие сетевых ответов от базы данных, не зависнут в очереди, если все ядра заняты математическими расчетами?
**Ответ:**
1) Поток `sysmon` каждые 10 мс опрашивает `netpoll()`: если в сокеты поступили данные, `sysmon` извлекает готовые горутины и сбрасывает их в Глобальную Очередь (GRQ);
2) Поток `sysmon` принудительно вытесняет CPU-горутины через сигнал `SIGURG`;
3) Каждые 61 тик процессоры P обязательно заглядывают в GRQ, забирая проснувшиеся сетевые горутины на выполнение.
