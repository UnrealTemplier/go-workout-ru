# Справедливость планирования (Fairness): предотвращение голодания горутин

## Условие

**Fairness**: Создайте сценарий, где одна горутина monopolizes CPU. Изучите, как preemption обеспечивает fairness.

## Теория

Справедливость (Fairness) планировщика Go гарантируется тремя механизмами:
1. **Тайм-слайс 10 мс:** Ни одна горутина не может непрерывно удерживать процессор дольше 10 мс при наличии других готовых задач.
2. **Проверка GRQ каждые 61 тик:** Предотвращает зависание горутин в Глобальной Очереди.
3. **Случайный Work Stealing:** Исключает постоянное обделение ресурсами конкретных очередей.

## Решение по шагам

1. Создаем сценарий с 1 монопольной горутиной и 10 легкими горутинами.
2. Запускаем на `GOMAXPROCS=1`.
3. Убеждаемся, что все 10 легких горутин успешно выполнились без голодания.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Тестирование Fairness планировщика на GOMAXPROCS=1...")

	stopHeavy := int32(0)
	var heavyIterations uint64

	// Монопольная тяжелая горутина
	go func() {
		for atomic.LoadInt32(&stopHeavy) == 0 {
			heavyIterations++
		}
	}()

	// 10 легких горутин
	const lightCount = 10
	var wg sync.WaitGroup
	wg.Add(lightCount)
	var completedLight int32

	for i := 0; i < lightCount; i++ {
		go func(id int) {
			defer wg.Done()
			time.Sleep(10 * time.Millisecond)
			atomic.AddInt32(&completedLight, 1)
		}(i)
	}

	wg.Wait()
	atomic.StoreInt32(&stopHeavy, 1)

	fmt.Printf("Все %d легких горутин успешно завершились!\n", completedLight)
	fmt.Printf("Тяжелая горутина выполнила %d итераций и не вызвала голодания.\n", heavyIterations)
}
```

ℹ️ Предотвращение голодания легких горутин при тяжелой нагрузке

**`Терминал`**

```bash
go run main.go
# Вывод:
# Тестирование Fairness планировщика на GOMAXPROCS=1...
# Все 10 легких горутин успешно завершились!
# Тяжелая горутина выполнила 45000000 итераций и не вызвала голодания.
```

## Под капотом

Справедливость обеспечивается тем, что при срабатывании таймера вытесненная тяжелая горутина помещается в **конец** локальной очереди (или в GRQ), давая возможность всем остальным горутинам продвинуться вперед в кольцевом буфере.

## Подводные камни

Хотя планировщик справедлив по времени CPU, в Go **нет механизма приоритетов горутин**: нельзя сделать горутину с «высоким приоритетом» без ручного проектирования очередей сообщений.

## На собеседовании

**Вопрос с собеседования:** Поддерживает ли Go приоритеты горутин на уровне рантайма (как `nice` в Linux или `Thread.setPriority()` в Java), и почему?
**Ответ:** **НЕТ, не поддерживает.**
Авторы Go (Rob Pike, Dmitry Vyukov) осознанно отказались от приоритетов горутин по причинам:
1) **Priority Inversion (Инверсия приоритетов):** Низкоприоритетная горутина может захватить мьютекс, а высокоприоритетная заблокируется на нем, сведя приоритеты на нет;
2) **Сложность планировщика:** Приоритетные очереди уничтожают скорость lock-free очередей и усложняют Work Stealing;
3) В высоконагруженных системах приоритизация реализуется на архитектурном уровне: разделением трафика на разные пулы воркеров и отдельные инстансы микросервисов.
