# Глубокое профилирование памяти (Memory Profiler): inuse_space против inuse_objects

## Условие

**Memory profiler deep dive**: Используйте `go tool pprof -inuse_space` и `-inuse_objects` для анализа memory leaks. Изучите flame graphs.

## Теория

Профилировщик памяти Go (`go tool pprof`) сэмплирует аллокации в куче (по умолчанию 1 аллокация на каждые 512 КБ выделенной памяти, настраивается через `runtime.MemProfileRate`).
Он поддерживает 4 режима анализа:
1. `-inuse_space`: объем **активной живой памяти**, удерживаемой объектами в данный момент (главный инструмент для поиска утечек памяти);
2. `-inuse_objects`: количество **живых объектов** в памяти (поиск утечек миллионов мелких структур);
3. `-alloc_space`: **суммарный объем выделенной памяти** за все время работы (поиск точек создания мусора для снижения нагрузки на GC);
4. `-alloc_objects`: **суммарное число аллоцированных объектов**.

## Решение по шагам

1. Создаем программу, аллоцирующую память в куче.
2. Сохраняем профиль кучи через `pprof.WriteHeapProfile()`.
3. Анализируем отчет в режимах `inuse_space` и `alloc_space`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
)

func allocateGarbage() [][]byte {
	// Создаем временные аллокации, которые будут собраны GC
	data := make([][]byte, 100)
	for i := 0; i < 100; i++ {
		data[i] = make([]byte, 64*1024) // 64 КБ
	}
	return data
}

func allocatePersistent() [][]byte {
	// Создаем долгоживущие объекты, которые останутся в inuse_space
	persistent := make([][]byte, 20)
	for i := 0; i < 20; i++ {
		persistent[i] = make([]byte, 128*1024) // 128 КБ
	}
	return persistent
}

func main() {
	_ = allocateGarbage()
	keepAlive := allocatePersistent()

	// Принудительно запускаем GC для очистки временных объектов
	runtime.GC()

	f, err := os.Create("mem.prof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := pprof.WriteHeapProfile(f); err != nil {
		panic(err)
	}

	fmt.Printf("Профиль памяти записан в mem.prof. Живых блоков удерживается: %d\n", len(keepAlive))
}
```

ℹ️ Генерация профиля кучи для анализа inuse vs alloc

**`Терминал`**

```bash
go run main.go
# Анализ активной живой памяти:
# go tool pprof -inuse_space mem.prof

# Анализ общего объема всех аллокаций:
# go tool pprof -alloc_space mem.prof
```

## Под капотом

В `src/runtime/mprof.go` рантайм использует экспоненциальный сэмплинг. Для каждой аллокации размером `size` вычисляется псевдослучайная граница следующего сэмпла. При превышении счетчика текущий стек вызовов сохраняется в хеш-таблице профилей памяти.

## Подводные камни

Анализ профиля кучи без предварительного вызова `runtime.GC()` может показывать временные объекты, которые еще не успел собрать сборщик мусора. Для чистого анализа утечек всегда смотрите `inuse_space`.

## На собеседовании

**Вопрос с собеседования:** В чем практическая разница при анализе сервиса между режимами `-inuse_space` и `-alloc_space` в pprof?
**Ответ:**
- **`-inuse_space`** показывает, сколько памяти удерживается в куче **прямо сейчас**. Его используют для расследования **OOM (утечек памяти)**: он указывает на структуры, которые забыли освободить или которые висят в глобальных мапах/кешах;
- **`-alloc_space`** показывает совокупный объем памяти, выделенный за все время, **включая уже собранный мусор**. Его используют для оптимизации **нагрузки на Garbage Collector (GC Allocation Rate)**: уменьшение `alloc_space` снижает процент времени, которое CPU тратит на работу сборщика мусора.
