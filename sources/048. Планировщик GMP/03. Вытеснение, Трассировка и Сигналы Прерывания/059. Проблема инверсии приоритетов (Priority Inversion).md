# Проблема инверсии приоритетов (Priority Inversion) и паттерны изоляции очередей

## Условие

**Priority inversion**: Go не поддерживает приоритеты горутин. Изучите, как это влияет на latency-sensitive задачи и какие workarounds существуют (separate P's, goroutine pools).

## Теория

Поскольку в планировщике Go все горутины равноправны, возникает архитектурная проблема:
Если сервер обрабатывает как важные запросы от пользователей (High Priority), так и тяжелые фоновые генерации отчетов (Low Priority), они помещаются в одни и те же очереди LRQ/GRQ.
Тяжелые фоновые задачи могут занять все процессоры P, вызвав деградацию latency критичных пользовательских запросов.

Решение в Go — **архитектурная изоляция на уровне очередей (QoS Buffers)** с принудительным выделением пулов воркеров разной емкости.

## Решение по шагам

1. Создаем диспетчер с разделением на High-Priority и Low-Priority очереди.
2. Обеспечиваем приоритетную обработку срочных задач.
3. Проверяем минимальную задержку критичных запросов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type PriorityDispatcher struct {
	highQueue chan func()
	lowQueue  chan func()
	stop      chan struct{}
	wg        sync.WaitGroup
}

func NewPriorityDispatcher(workers int) *PriorityDispatcher {
	d := &PriorityDispatcher{
		highQueue: make(chan func(), 1000),
		lowQueue:  make(chan func(), 1000),
		stop:      make(chan struct{}),
	}

	for i := 0; i < workers; i++ {
		d.wg.Add(1)
		go func() {
			defer d.wg.Done()
			for {
				select {
				case <-d.stop:
					return
				// Приоритетная проверка: сначала HighQueue
				case task := <-d.highQueue:
					task()
				default:
					select {
					case <-d.stop:
						return
					case task := <-d.highQueue:
						task()
					case task := <-d.lowQueue:
						task()
					}
				}
			}
		}()
	}
	return d
}

func main() {
	d := NewPriorityDispatcher(4)

	var highLatencies []time.Duration
	var mu sync.Mutex

	// Заполняем LowQueue тяжелыми задачами
	for i := 0; i < 50; i++ {
		d.lowQueue <- func() {
			time.Sleep(5 * time.Millisecond)
		}
	}

	// Посылаем High-Priority задачи
	for i := 0; i < 5; i++ {
		created := time.Now()
		d.highQueue <- func() {
			latency := time.Since(created)
			mu.Lock()
			highLatencies = append(highLatencies, latency)
			mu.Unlock()
		}
	}

	time.Sleep(100 * time.Millisecond)
	close(d.stop)
	d.wg.Wait()

	fmt.Println("Задержки High-Priority задач:")
	for i, lat := range highLatencies {
		fmt.Printf("  Запрос %d: %v\n", i+1, lat)
	}
}
```

ℹ️ Реализация прикладного QoS с приоритизацией очередей

**`Терминал`**

```bash

# Вывод:

#   Запрос 2: 150µs
#   Запрос 3: 180µs
#   Запрос 4: 210µs
#   Запрос 5: 240µs
```

## Под капотом

Двойной `select` с веткой `default` реализует неблокирующую приоритетную проверку: если в `highQueue` есть задача, воркер всегда берет ее в обход `lowQueue`, моделируя поведение Strict Priority Queue.

## Подводные камни

Строгая приоритизация может привести к полному голоданию (Starvation) низкоприоритетной очереди. В продакшене используйте взвешенные алгоритмы (Weighted Fair Queuing, WFQ).

## На собеседовании

**Вопрос с собеседования:** Как спроектировать микросервис на Go, чтобы тяжелые фоновые синхронизации не влияли на SLA критичных пользовательских запросов?
**Ответ:**
1) **Разделение очередей:** Выделить отдельные каналы/пулы воркеров под разные типы задач;
2) **Ограничение конкурентности:** Ограничить количество одновременных фоновых горутин семафором (например, не более 2 фоновых задач на 16 ядер);
3) **Изоляция по процессам:** Вынести тяжелые фоновые задачи в отдельный фоновый Worker Pod в Kubernetes, оставив API Pod только для пользовательского трафика.
