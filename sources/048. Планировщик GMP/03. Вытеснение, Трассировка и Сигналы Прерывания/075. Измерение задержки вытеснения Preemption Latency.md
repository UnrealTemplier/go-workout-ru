# Измерение задержки вытеснения Preemption Latency

## Условие

**Preemption latency**: Измерьте, сколько времени проходит от preemption request до фактического вытеснения горутины.

## Теория

Preemption Latency (задержка вытеснения) — это время, которое требуется планировщику Go, чтобы снять вычислительно нагруженную горутину с потока \(M\), когда исчерпан её квант времени (10 мс) или требуется запустить сборщик мусора (STW).

Исторически до Go 1.14 кооперативное вытеснение происходило только на вызовах функций (проверка преамбулы `morestack`). Если горутина крутилась в глухом цикле без вызова функций, latency вытеснения могла составлять бесконечность!
Начиная с Go 1.14 появилось асинхронное вытеснение на сигналах ОС (`SIGURG` на Unix). Поток `sysmon` отправляет `pthread_kill(m.procid, SIGURG)`, обработчик сигнала перехватывает регистры и передает управление в `runtime.asyncPreempt`.

## Решение по шагам

1. Запустите одну горутину с тяжелым бесконечным вычислением.
2. Запустите вторую горутину, которая с заданным интервалом фиксирует ход времени.
3. Ограничьте `runtime.GOMAXPROCS(1)`, чтобы обе горутины делили один единственный процессорный поток.
4. Замерьте задержку между моментом, когда вторая горутина должна была проснуться, и моментом фактического получения управления.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	// Жестко ограничиваем рантайм одним потоком P
	runtime.GOMAXPROCS(1)

	var stop int32

	// Фоновый CPU-bound воркер: чистые вычисления без явных системных вызовов
	go func() {
		counter := 0
		for atomic.LoadInt32(&stop) == 0 {
			counter++
		}
		_ = counter
	}()

	fmt.Println("Замер задержки асинхронного вытеснения (Preemption)...")

	// Главная горутина делает серию коротких пауз
	const iterations = 5
	for i := 1; i <= iterations; i++ {
		expectedDelay := 5 * time.Millisecond
		start := time.Now()
		time.Sleep(expectedDelay)
		actualDelay := time.Since(start)

		jitter := actualDelay - expectedDelay
		fmt.Printf("Итерация %d: задержка Sleep: %v (джиттер/latency вытеснения: %v)\n",
			i, actualDelay, jitter)
	}

	atomic.StoreInt32(&stop, 1)
	time.Sleep(10 * time.Millisecond)
	fmt.Println("Тест успешно завершен.")
}
```

ℹ️ Измерение preemption latency при GOMAXPROCS=1 и тяжелом CPU-bound цикле

**`Терминал`**

```bash
go run main.go
```

## Под капотом

В Go 1.14+ поток `sysmon` каждые 10 мс проверяет горутины в статусе `_Grunning`. Если горутина непрерывно выполняется дольше `forcePreemptNS` (~10 мс):
1. `sysmon` выставляет флаг `preempt = true` и `stackguard0 = stackPreempt`.
2. Вызывает `signalM(mp, sigPreempt)`, где `sigPreempt = SIGURG`.
3. Ядро ОС прерывает выполнение потока \(M\) и запускает обработчик `sighandler`.
4. Если горутина находится в безопасной точке (safe-point, не в рантайме и не в Cgo), регистры обновляются так, чтобы стек вернулся в `runtime.asyncPreempt`.
5. `asyncPreempt` сохраняет все регистры общего назначения и FPU, переводит \(G\) в `_Grunnable` и вызывает `schedule()`.

## Подводные камни

1. На некоторых ОС (например, Windows без поддержки сигналов POSIX или старых ядрах) асинхронное вытеснение работает иначе (через `SuspendThread`).
2. В точках, помеченных компилятором директивой `//go:nosplit` или внутри критических секций рантайма, асинхронный сигнал безопасно игнорируется, и вытеснение откладывается.
3. Очень частые сигналы `SIGURG` создают нагрузку на диспетчер сигналов ядра Linux, поэтому они генерируются с периодичностью ~10 мс, а не микросекунд.

## На собеседовании

**Вопрос с собеседования:** Почему в Go для асинхронного вытеснения был выбран именно сигнал `SIGURG`, а не `SIGUSR1` или `SIGALRM`?
**Ответ:** Сигнал `SIGURG` (Out-of-band data on socket) практически никогда не используется пользовательскими приложениями и сторонними C-библиотеками, в отличие от `SIGUSR1`/`SIGUSR2` или `SIGALRM`. По стандарту POSIX действие по умолчанию для `SIGURG` — игнорирование, поэтому даже если сигнал попадет в неопознанный поток, процесс не упадет.
