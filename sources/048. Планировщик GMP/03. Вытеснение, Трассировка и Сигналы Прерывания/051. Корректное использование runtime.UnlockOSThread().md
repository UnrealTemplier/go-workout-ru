# Корректное использование runtime.UnlockOSThread() и правила парности вызовов

## Условие

**UnlockOSThread**: Вызовите `runtime.UnlockOSThread()` и изучите, когда это безопасно (после завершения Cgo вызовов).

## Теория

Вызов `runtime.UnlockOSThread()` снимает привязку текущей горутины к потоку ОС `M`.
Ключевые правила:
1. **Счетчик вложенности (Nesting Counter):** Если горутина вызвала `LockOSThread()` дважды, она обязана вызвать `UnlockOSThread()` ровно дважды, чтобы поток M освободился.
2. **Безопасность состояния:** Вызывать `UnlockOSThread()` безопасно **только в том случае**, если горутина вернула все параметры потока ОС (приоритет, сигнальные маски, Thread-Local Storage) в исходное состояние.
3. **Уничтожение потока:** Если горутина изменила глобальное состояние потока (например, `setns`), `UnlockOSThread` вызывать **нельзя** — горутина должна завершиться вместе со смертью потока.

## Решение по шагам

1. Демонстрируем парный вызов `LockOSThread` и `UnlockOSThread`.
2. Демонстрируем счетчик вложенности.
3. Проверяем возвращение потока M в общий пул.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"syscall"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()

		// Двойная блокировка (счетчик = 2)
		runtime.LockOSThread()
		runtime.LockOSThread()
		fmt.Printf("Поток заблокирован дважды. TID = %d\n", syscall.Gettid())

		// Первый разблокирующий вызов (счетчик = 1, поток все еще привязан)
		runtime.UnlockOSThread()
		fmt.Println("Первый UnlockOSThread выполнен, поток все еще закреплен.")

		// Второй разблокирующий вызов (счетчик = 0, поток полностью свободен)
		runtime.UnlockOSThread()
		fmt.Println("Второй UnlockOSThread выполнен: поток M возвращен в общий пул планировщика.")
	}()

	wg.Wait()
	fmt.Println("Тест завершен.")
}
```

ℹ️ Вложенные вызовы LockOSThread и UnlockOSThread

**`Терминал`**

```bash
go run main.go
# Вывод:
# Поток заблокирован дважды. TID = 54321
# Первый UnlockOSThread выполнен, поток все еще закреплен.
# Второй UnlockOSThread выполнен: поток M возвращен в общий пул планировщика.
# Тест завершен.
```

## Под капотом

В `src/runtime/proc.go` структура `g` содержит целочисленное поле `lockedm`. Вызов `LockOSThread()` инкрементирует счетчик `gp.m.lockedExt++`. Функция `UnlockOSThread()` декрементирует этот счетчик. Только при достижении 0 обнуляются взаимные ссылки `gp.lockedm = 0` и `mp.lockedg = 0`.

## Подводные камни

Вызов `UnlockOSThread()` без предварительного `LockOSThread()` ни к чему не приводит (счетчик остается 0), но нарушает идиоматичность кода.

## На собеседовании

**Вопрос с собеседования:** Что произойдет, если горутина вызовет `runtime.LockOSThread()` внутри библиотеки, а вызывающий код об этом не знает?
**Ответ:** Поток ОС окажется захваченным до конца жизни этой горутины.
Если горутина долгоживущая (например фоновый воркер), этот поток M будет навсегда изъят из общего пула планировщика.
Поэтому вызовы `LockOSThread` и `UnlockOSThread` обязаны быть строго локализованы в минимальной критической секции и оформляться через `defer runtime.UnlockOSThread()`.
