# Свой планировщик задач: Worker Pool с каналом против рантайма Go

## Условие

Реализуйте «свой планировщик» на чистом Go: N worker-горутин с каналом задач. Сравните latency и throughput с нативным планировщиком при CPU-bound нагрузке. Объясните, почему нативный быстрее (меньше кэш-промахов, локальные очереди, нет каналов).

## Теория

Для сравнения эффективности собственного прикладного пула воркеров и рантайма Go:
- Собственный планировщик: фиксированное число воркеров (\(N\)), общий буферизованный канал задач.
- Рантайм Go: модель GMP с локальными очередями и work stealing.

Прикладной пул задач эффективен для ограничения нагрузки на внешние ресурсы (базу данных, внешнее API), но по чистой скорости диспетчеризации задач рантайм Go обгоняет прикладные каналы за счет lock-free структур.

## Решение по шагам

1. Создаем бенчмарк обработки 500 000 мелких задач через Worker Pool на каналах.
2. Создаем бенчмарк обработки через прямой спавн горутин рантайма.
3. Сравниваем Throughput и Latency.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func benchmarkChannelPool(tasks int, workers int) time.Duration {
	ch := make(chan int, 1000)
	var wg sync.WaitGroup
	start := time.Now()

	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for range ch {
			}
		}()
	}

	for i := 0; i < tasks; i++ {
		ch <- i
	}
	close(ch)
	wg.Wait()
	return time.Since(start)
}

func benchmarkGoScheduler(tasks int) time.Duration {
	var wg sync.WaitGroup
	wg.Add(tasks)
	start := time.Now()

	for i := 0; i < tasks; i++ {
		go func() {
			defer wg.Done()
		}()
	}

	wg.Wait()
	return time.Since(start)
}

func main() {
	runtime.GOMAXPROCS(4)
	const total = 200000

	fmt.Printf("Сравнение производительности диспетчеризации (%d задач):\n", total)

	d1 := benchmarkChannelPool(total, runtime.GOMAXPROCS(0))
	fmt.Printf("1. Worker Pool на канале:   %v (%.2f ops/sec)\n",
		d1, float64(total)/d1.Seconds())

	d2 := benchmarkGoScheduler(total)
	fmt.Printf("2. Нативный Go планировщик: %v (%.2f ops/sec)\n",
		d2, float64(total)/d2.Seconds())
}
```

ℹ️ Сравнение производительности пула на каналах и GMP


## Под капотом

Канал использует спинлок `hchan.lock` и копирование в кольцевой буфер. В нативном спавне `go func()` рантайм выделяет структуры `g`, проверяет стек и помещает в `runnext`. Для тривиальных пустых задач пул на прогретых воркерах обгоняет спавн горутин по аллокациям.

## Подводные камни

Воркер-пулы на каналах эффективны для CPU-bound вычислений, но если воркер в пуле зависнет на сетевом вызове, весь пул начнет деградировать. Горутины Go изолированы от этой проблемы благодаря `handoffp` и `netpoller`.

## На собеседовании

**Вопрос с собеседования:** Когда в Go-сервисе следует использовать Worker Pool, а когда предпочесть нативный спавн горутин `go func()`?
**Ответ:**
- **Worker Pool необходим**, когда требуется **Rate Limiting** и защита внешних ресурсов: пул подключений к БД (PostgreSQL не выдержит 100 000 одновременных коннектов), ограничение одновременных обращений к диску, ограничение RPS во внешние API;
- **Нативный спавн `go func()` предпочтителен** для независимых легковесных сетевых обработчиков (HTTP, WebSocket, gRPC), где горутины большую часть времени ждут I/O в Netpoller, не потребляя системных потоков ОС.
