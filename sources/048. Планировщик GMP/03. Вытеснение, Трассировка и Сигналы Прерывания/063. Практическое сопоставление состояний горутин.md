# Практическое сопоставление состояний горутин: time.Sleep, каналы, LockOSThread

## Условие

**Состояния Горутин**: Напиши программу, где одна горутина спит (`time.Sleep`), другая ждет канал (`<-ch`), третья крутит CPU. Сделай дамп всех стеков программы через `runtime.Stack(buf, true)` (или `SIGQUIT` - `Ctrl+\`). Найди в дампе состояния горутин: `running`, `runnable`, `sleep`, `wait`.

## Теория

При диагностике зависших сервисов инженеру необходимо мгновенно определять причину блокировки по тексту дампа стека:
- `[sleep]`: `time.Sleep()` — горутина в `_Gwaiting`, привязана к таймеру в `p.timers`;
- `[chan receive]`: чтение из пустого канала — горутина в `_Gwaiting` в очереди `hchan.recvq`;
- `[chan send]`: запись в полный канал — горутина в `_Gwaiting` в очереди `hchan.sendq`;
- `[select]`: блокировка на операторе `select` без готовых веток;
- `[locked to thread]`: привязка к системному потоку через `runtime.LockOSThread()`.

## Решение по шагам

1. Создаем 4 горутины, каждая из которых переходит в одно из целевых состояний.
2. Снимаем дамп через `runtime.Stack()`.
3. Анализируем текстовые маркеры состояний.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)

	// 1. Спящая горутина [sleep]
	go func() {
		time.Sleep(5 * time.Second)
	}()

	// 2. Читающая из канала [chan receive]
	emptyCh := make(chan int)
	go func() {
		<-emptyCh
	}()

	// 3. Пишущая в канал [chan send]
	fullCh := make(chan int)
	go func() {
		fullCh <- 1
	}()

	// 4. Привязанная к потоку [locked to thread]
	go func() {
		runtime.LockOSThread()
		time.Sleep(5 * time.Second)
	}()

	time.Sleep(50 * time.Millisecond)

	buf := make([]byte, 16384)
	n := runtime.Stack(buf, true)

	fmt.Println("=== Дамп стеков и статусов ожидания горутин ===")
	fmt.Printf("%s\n", buf[:n])
	os.Exit(0)
}
```

ℹ️ Демонстрация различных статусов ожидания в runtime.Stack

**`Терминал`**

```bash
go run main.go
# В выводе видны: [sleep], [chan receive], [chan send], [locked to thread]
```

## Под капотом

Внутри `src/runtime/traceback.go` функция `goroutinestatus()` мапит целочисленный статус `gp.atomicstatus` и строковое поле `gp.waitreason` в человекочитаемый текст в квадратных скобках.

## Подводные камни

В дампе стека статус `[running]` будет иметь только та горутина, которая вызвала `runtime.Stack()`, плюс еще до `GOMAXPROCS-1` параллельно исполняющихся горутин. Все остальные будут в статусах `[runnable]` или `[waiting]`.

## На собеседовании

**Вопрос с собеседования:** Что означает статус `[chan receive (nil chan)]` в дампе стека и чем он опасен?
**Ответ:** Это признак чтения из неинициализированного (`nil`) канала: `var ch chan int; <-ch`.
В отличие от закрытого канала (который возвращает нулевое значение и `false`), чтение или запись в `nil`-канал блокирует горутину **навсегда**.
Она никогда не проснется, навсегда зависнет в статусе `_Gwaiting` и утечет из памяти вместе со своим стеком.
