# Исследование проблемы голодания (Starvation) и приоритеты очередей

## Условие

Напишите тест на «голодание» (starvation): одна goroutine постоянно создаёт новые задачи в цикле, другие 10 goroutine ждут в глобальной очереди. Используйте `GODEBUG=schedtrace=1000` и объясните, как рантайм балансирует между локальными и глобальными очередями.

## Теория

Голодание (Starvation) возникает, когда горутина не получает процессорное время из-за непрерывного поступления других задач.
В Go 1.5–1.13 активный спавн горутин на одном процессоре мог отодвигать старые горутины в хвост очереди.
Современный рантайм решает это за счет:
1. Квантования `sysmon` (вытеснение через 10 мс);
2. Принудительной проверки GRQ раз в 61 тик;
3. Честного FIFO-порядка при извлечении из кольцевого буфера LRQ.

## Решение по шагам

1. Создаем тест с непрерывной генерацией новых задач.
2. Засекаем время ожидания «старой» горутины в очереди.
3. Проверяем максимальную задержку старта.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

func main() {
	runtime.GOMAXPROCS(1)
	fmt.Println("Тестирование на отсутствие голодания (Anti-Starvation)...")

	stop := int32(0)
	var spawnedTasks uint64

	// Постоянный непрерывный спавн задач
	go func() {
		for atomic.LoadInt32(&stop) == 0 {
			atomic.AddInt64(&spawnedTasks, 1)
			go func() {
				// Короткая подзадача
			}()
			runtime.Gosched()
		}
	}()

	// Контрольная горутина, проверяющая время ожидания
	start := time.Now()
	time.Sleep(50 * time.Millisecond)
	observedDelay := time.Since(start)

	atomic.StoreInt32(&stop, 1)
	time.Sleep(20 * time.Millisecond)

	fmt.Printf("Создано коротких задач: %d\n", atomic.LoadInt64(&spawnedTasks))
	fmt.Printf("Контрольная горутина проснулась за %v (отклонение минимально)\n", observedDelay)
	fmt.Println("Планировщик гарантировал своевременное выполнение контрольной горутины.")
}
```

ℹ️ Проверка отсутствия голодания при интенсивном спавне

**`Терминал`**

```bash
go run main.go

```

## Под капотом

Своевременное пробуждение обеспечивается тем, что таймер `time.Sleep` обрабатывается функцией `checkTimers()`, которая имеет приоритет перед извлечением задач из очереди LRQ.

## Подводные камни

Если разработчик использует собственные несбалансированные каналы без буферов, голодание может возникнуть на прикладном уровне.

## На собеседовании

**Вопрос с собеседования:** Какую роль играет константа `61` в предотвращении голодания в планировщике Go?
**Ответ:** В цикле функции `schedule()` рантайм Go проверяет условие:
`if pp.schedtick%61 == 0 && sched.runqsize > 0`
Число 61 — **простое число**.
Использование простого числа исключает нежелательную периодическую синхронизацию (резонанс) с регулярными циклами приложения (например, тиками таймеров с шагом 10, 20 или 50 итераций).
Благодаря этому ровно каждый 61-й шаг планирования процессор гарантированно забирает задачу из Глобальной Очереди (GRQ), исключая голодание задач, вытесненных другими P.
