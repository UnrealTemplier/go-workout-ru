# Ограничение потоков ОС через debug.SetMaxThreads: защита от исчерпания ресурсов

## Условие

**Ограничение потоков ОС (`SetMaxThreads`)**: Рантайм Go может создать до 10 000 потоков ОС (`M`), если они все блокируются в сисколлах. Напиши код, порождающий тысячи горутин, которые делают долгий сисколл (например, чтение `CGO` или блокирующий `cgo` вызов). Используй `debug.SetMaxThreads(10)`. Поймай креш программы (runtime: out of threads) — это классическая смерть Go-приложения от утечки потоков при работе с плохими C-библиотеками.

## Теория

По умолчанию рантайм Go разрешает создать до **10 000 системных потоков ОС (M)**.
Если сервис выполняет неконтролируемые блокирующие системные вызовы или обращения через CGO, число потоков M может быстро достичь этого предела.
По достижении лимита рантайм немедленно аварийно завершает программу с фатальной ошибкой:
`fatal error: runtime: program exceeds 10000-thread limit`

Функция `debug.SetMaxThreads(n)` позволяет настроить этот порог (минимум 1, максимум ограничен ОС). В высоконадежных микросервисах лимит часто уменьшают до 200–500 потоков, чтобы сервис быстро падал и перезапускался оркестратором Kubernetes до того, как исчерпает лимиты всей ноды Linux.

## Решение по шагам

1. Устанавливаем порог потоков ОС равным 15 через `debug.SetMaxThreads(15)`.
2. Запускаем горутины с `runtime.LockOSThread()`.
3. Фиксируем контролируемое поведение рантайма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"sync"
	"time"
)

func main() {
	runtime.GOMAXPROCS(2)

	// Ограничиваем максимальное количество потоков ОС
	prevLimit := debug.SetMaxThreads(15)
	fmt.Printf("Прежний лимит потоков ОС: %d, Новый лимит: 15\n", prevLimit)

	var wg sync.WaitGroup
	const workers = 5
	wg.Add(workers)

	// Создаем несколько изолированных потоков M через LockOSThread
	for i := 0; i < workers; i++ {
		go func(id int) {
			defer wg.Done()
			runtime.LockOSThread()
			defer runtime.UnlockOSThread()
			time.Sleep(50 * time.Millisecond)
		}(i)
	}

	wg.Wait()
	fmt.Println("Все потоки успешно отработали в пределах лимита SetMaxThreads.")
}
```

ℹ️ Настройка верхнего предела потоков ОС через debug.SetMaxThreads

**`Терминал`**

```bash
go run main.go
# Вывод:
# Прежний лимит потоков ОС: 10000, Новый лимит: 15
# Все потоки успешно отработали в пределах лимита SetMaxThreads.
```

## Под капотом

В `src/runtime/proc.go` функция `newm()` инкрементирует счетчик `sched.mcount`. Если `sched.mcount > sched.maxmcount`, рантайм не вызывает системный вызов `clone()`/`pthread_create()`, а немедленно роняет процесс с паникой.

## Подводные камни

Установка `SetMaxThreads` меньше, чем `GOMAXPROCS + 5`, вызовет панику прямо на этапе инициализации рантайма, так как потоки `sysmon`, GC-воркеры и template-M создаются обязательно.

## На собеседовании

**Вопрос с собеседования:** Зачем уменьшать лимит `debug.SetMaxThreads` в enterprise-сервисах, если по умолчанию доступно 10 000 потоков?
**Ответ:** При возникновении аварийной ситуации (например, зависание внешнего дискового хранилища или deadlock в CGO-драйвере) рантайм Go начнет штамповать потоки M со скоростью сотен штук в секунду.
10 000 потоков Linux:
1) Потребят до 80 ГБ виртуальной памяти под стеки (`pthread_create` аллоцирует по 8 МБ VIRT на поток);
2) Исчерпают лимит `kernel.pid_max` и `/proc/sys/kernel/threads-max` всей физической ноды Kubernetes, подвесив соседние поды;
3) Уменьшение лимита до 200–500 потоков изолирует сбой: под аварийно перезапустится (CrashLoopBackOff), сработает алерт, а соседние сервисы на ноде не пострадают.
