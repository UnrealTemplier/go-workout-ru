---

## Теория

Полная архитектурная схема планировщика Go объединяет 5 сущностей:
1. **G (Goroutine):** Стек, счетчик команд PC, статус (`_Gwaiting`, `_Grunnable` и др.).
2. **M (OS Thread):** Физический поток выполнения ядра ОС.
3. **P (Processor):** Контекст выполнения, владеет `runnext`, `LRQ [256]`, `mcache`, `timers`.
4. **GRQ (Global Run Queue):** Глобальная очередь горутин с защитой `sched.lock`.
5. **Netpoller:** Фоновый опросчик сетевых сокетов на базе `epoll/kqueue`.
6. **sysmon:** Сторожевой поток ядра без P, следящий за вытеснением и памятью.

## Решение по шагам

1. Создаем консольную визуализацию схемы взаимодействия GMP.
2. Выводим текущие параметры запущенного рантайма.
3. Сопоставляем теоретические компоненты с метриками.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

func printGMPSummary() {
	fmt.Println("==================================================================")
	fmt.Println("               АРХИТЕКТУРА ПЛАНИРОВЩИКА GO (GMP)                  ")
	fmt.Println("==================================================================")
	fmt.Println(" [sysmon] --------> (Мониторинг >10ms, SIGURG, Netpoll, GC, Mem) ")
	fmt.Println("     |                                                            ")
	fmt.Println("     v                                                            ")
	fmt.Println(" [GRQ] (Global Run Queue, sched.lock) <--- Сброс при переполнении ")
	fmt.Println("     ^                                                            ")
	fmt.Println("     | (Проверка каждые 61 тик / Work Stealing)                   ")
	fmt.Println("     v                                                            ")
	fmt.Println(" [ P ] (Processor: runnext, LRQ[256], mcache, p.timers)           ")
	fmt.Println("     |                                                            ")
	fmt.Println("     v                                                            ")
	fmt.Println(" [ M ] (OS Thread, pthread) <===> [ G ] (Active Goroutine)        ")
	fmt.Println("     |                                                            ")
	fmt.Println("     +---> Netpoller (epoll/kqueue) при сетевом I/O               ")
	fmt.Println("     +---> HandoffP при блокирующем системном вызове              ")
	fmt.Println("==================================================================")
	fmt.Printf("Текущие параметры рантайма:\n")
	fmt.Printf("  Версия Go:        %s\n", runtime.Version())
	fmt.Printf("  Аппаратных CPU:   %d\n", runtime.NumCPU())
	fmt.Printf("  GOMAXPROCS (P):   %d\n", runtime.GOMAXPROCS(0))
	fmt.Printf("  Живых горутин (G): %d\n", runtime.NumGoroutine())
	fmt.Println("==================================================================")
}

func main() {
	printGMPSummary()
}
```

## Под капотом

В файле `src/runtime/HACKING.md` разработчики рантайма описывают ключевые инварианты: никакой Go-код не может исполняться на M без захваченного P, за исключением специального контекста `g0` и потока `sysmon`.

## Подводные камни

Попытка напрямую манипулировать низкоуровневыми структурами GMP без понимания барьеров памяти приведет к повреждению кучи (Memory Corruption).

## На собеседовании

**Вопрос с собеседования:** Опишите жизненный путь горутины от вызова `go worker()` до завершения.
**Ответ:**
1) **Создание:** Вызов `newproc()`. Берется структура `g` из пула `gFree` (или аллоцируется), выделяется 2 КБ стека;
2) **Постановка в очередь:** Горутина помещается в слот `runnext` текущего P (или в кольцевой буфер LRQ);
3) **Исполнение:** Свободный поток M забирает ее через `runqget()`, переключается на стек горутины через `gogo()` и меняет статус на `_Grunning`;
4) **Ожидание/Вытеснение:** При I/O уходит в `_Gwaiting` (Netpoller), при >10 мс вытесняется сигналом `SIGURG`;
5) **Завершение:** Вызывает `goexit()`, статус меняется на `_Gdead`, дескриптор возвращается в пул `gFree` для повторного использования.
