# Комплексный аудит в Go Trace: визуализация взаимодействия CPU-bound и IO-bound горутин

## Условие

**[Высокая сложность — Go Trace]**: Напиши программу с CPU-bound и IO-bound горутинами. Запусти её, записав трейс в файл: `cat > trace.out` через `runtime/trace`. Открой `go tool trace trace.out`. Найди визуализацию GMP: посмотри, как горутины привязываются к P и M, и когда происходит блокировка.

## Теория

Комплексная трассировка высоконагруженного сервиса объединяет:
1. **CPU Timeline:** Визуализация загрузки каждого процессора `P0..P(N-1)`.
2. **Network Poller:** Время ожидания сетевых ответов.
3. **GC STW Pauses:** Точные границы пауз остановки мира сборщика мусора.
4. **Syscall Handoff:** Фазы отделения потоков M при системных вызовах.

Анализ такого профиля позволяет сразу выявить «узкие горлышки» масштабируемости.

## Решение по шагам

1. Запускаем одновременную нагрузку: CPU-вычисления, сетевые пинги и системные вызовы.
2. Фиксируем трассировку в `complex_trace.out`.
3. Анализируем отчет в `go tool trace`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"os"
	"runtime"
	"runtime/trace"
	"sync"
	"syscall"
	"time"
)

func main() {
	runtime.GOMAXPROCS(4)

	f, err := os.Create("complex_trace.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	var wg sync.WaitGroup
	wg.Add(3)

	// 1. CPU-bound нагрузка
	go func() {
		defer wg.Done()
		var acc uint64
		for i := 0; i < 10000000; i++ {
			acc += uint64(i)
		}
		_ = acc
	}()

	// 2. IO-bound сетевая нагрузка через Netpoller
	ln, _ := net.Listen("tcp", "127.0.0.1:0")
	defer ln.Close()
	go func() {
		defer wg.Done()
		conn, err := net.Dial("tcp", ln.Addr().String())
		if err == nil {
			conn.Close()
		}
	}()

	// 3. Блокирующий системный вызов
	go func() {
		defer wg.Done()
		var req, rem syscall.Timespec
		req.Nsec = 20000000 // 20 мс
		syscall.Nanosleep(&req, &rem)
	}()

	wg.Wait()
	fmt.Println("Комплексная трассировка сохранена в complex_trace.out")
}
```

ℹ️ Комплексная трассировка разнородных нагрузок

**`Терминал`**

```bash
go run main.go
# Открытие отчета:
# go tool trace complex_trace.out
```

## Под капотом

Внутри `go tool trace` формируется интерактивный граф взаимодействия: видно, как поток 1 исполняет CPU, поток 2 паркуется в `netpoll`, а поток 3 уходит в `_Gsyscall`, вызывая `handoffp`.

## Подводные камни

Не открывайте гигантские файлы trace (>500 МБ) в браузере: движок визуализации может исчерпать оперативную память вкладки Chrome. Используйте флаг сэмплинга или профилируйте меньший интервал.

## На собеседовании

**Вопрос с собеседования:** Как с помощью `go tool trace` обнаружить проблему Lock Contention (борьбы за мьютексы)?
**Ответ:**
1) Открыть раздел **«Synchronization blocking profile»** в меню `go tool trace`;
2) Инструмент строит граф задержек, сгруппированный по вызовам `sync.Mutex.Lock` и операциям с каналами;
3) В графе отображаются точные функции и строки кода, на которых горутины суммарно потеряли больше всего времени в состоянии ожидания `_Gwaiting`;
4) Если задержки вызваны мьютексом, решение — шардирование мьютекса (sharded lock) или переход на атомики/RWMutex.
