# Безопасный пуск горутин SafeGo с перехватом паники и логированием стека

## Условие

**Безопасный пуск горутин (`SafeGo`)**: Напишите функцию `SafeGo(fn func())`. Она должна запускать переданную функцию `fn` в горутине, но при этом защищать приложение от падения, если внутри `fn` произойдет паника (panic). Внутри `SafeGo` должен быть перехватчик `recover()`, который логирует панику, но не дает завершиться всему процессу.

## Теория

Архитектурный стандарт отказоустойчивости: утилита `SafeGo` оборачивает запуск горутины в `defer recover()`, извлекая стектрейс через `debug.Stack()` и предотвращая краш сервера.

## Решение по шагам

1. Создадим функцию `SafeGo(fn func())`.
2. В `defer` вызовем `recover()` и залогируем ошибку.
3. Запустим горутину с делением на 0.
4. Проверим, что основной процесс продолжает работать.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func SafeGo(fn func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("[SafeGo Guard] ПЕРЕХВАЧЕНА КРИТИЧЕСКАЯ ПАНИКА: %v! Процесс спасен.\n", r)
			}
		}()
		fn()
	}()
}

func main() {
	var wg sync.WaitGroup
	wg.Add(1)

	// Запуск потенциально опасной горутины
	SafeGo(func() {
		defer wg.Done()
		fmt.Println("[Worker] Старт тяжелой обработки...")
		panic("неожиданный сбой базы данных")
	})

	wg.Wait()
	time.Sleep(10 * time.Millisecond)
	fmt.Println("[Main] Основной сервер продолжает успешно обрабатывать входящие запросы!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Worker] Старт тяжелой обработки...
# [SafeGo Guard] ПЕРЕХВАЧЕНА КРИТИЧЕСКАЯ ПАНИКА: неожиданный сбой базы данных! Процесс спасен.
# [Main] Основной сервер продолжает успешно обрабатывать входящие запросы!
```

## Под капотом

`recover()` останавливает раскрутку стека внутри горутины.

## Подводные камни

Паника, возникшая в горутине без `recover()`, не может быть перехвачена в родительском потоке.

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшн-фреймворках (Gin, Echo, Fiber, Chi) каждый HTTP-хендлер оборачивают в Recovery Middleware?»
**Ответ:** Чтобы ошибка одного некорректного HTTP-запроса (например, nil pointer dereference) не приводила к аварийному завершению всего веб-сервера и разрыву тысяч других активных клиентских соединений.
