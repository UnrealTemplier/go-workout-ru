# Масштабируемый Worker Pool с буферизованной очередью на 100 заданий

## Условие

**Worker Pool (Пул воркеров)**: Создай очередь заданий (канал на 100 элементов). Запусти фиксированное количество воркеров (например, 5), которые читают задания и "обрабатывают" (sleep random time). Дождись выполнения всех заданий через `WaitGroup`.

## Теория

Схема пула воркеров для обработки фоновых пакетов задач с контролем завершения через `sync.WaitGroup`.

## Решение по шагам

1. Создадим буферизованный канал `queue := make(chan int, 100)`.
2. Запустим 5 воркеров.
3. Отправим 15 заданий и вызовем `close(queue)`.
4. Дождемся `wg.Wait()`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func queueWorker(id int, queue <-chan int, wg *sync.WaitGroup) {
	defer wg.Done()
	for taskID := range queue {
		fmt.Printf("[Worker #%d] Старт обработки задачи #%d\n", id, taskID)
		time.Sleep(5 * time.Millisecond)
	}
}

func main() {
	queue := make(chan int, 100)
	var wg sync.WaitGroup

	const numWorkers = 5
	for w := 1; w <= numWorkers; w++ {
		wg.Add(1)
		go queueWorker(w, queue, &wg)
	}

	for i := 1; i <= 10; i++ {
		queue <- i
	}
	close(queue) // Сигнал воркерам о завершении очереди

	wg.Wait()
	fmt.Println("[Main] Все задачи из очереди на 100 элементов успешно выполнены.")
}
```

## Под капотом

5 воркеров конкурируют за получение задач из циклического буфера канала.

## Подводные камни

Закрывайте канал очереди только со стороны отправителя.

## На собеседовании

**Вопрос с собеседования:** «Зачем нужен буфер на 100 элементов в очереди задач?»
**Ответ:** Буфер сглаживает пики входящего трафика (Absorption of Bursts), позволяя отправителям быстро сбросить задачи в память без ожидания освобождения воркеров.
