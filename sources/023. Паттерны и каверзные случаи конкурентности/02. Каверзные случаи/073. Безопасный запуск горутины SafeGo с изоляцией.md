# Безопасный запуск горутины SafeGo с изоляцией паники (Recover Wrapper)

## Условие

Реализуйте функцию, которая "форкает" выполнение (создает горутину), но гарантирует, что при панике внутри горутины программа не упадет молча, а залогирует ошибку (recover внутри горутины).

## Теория

Изоляция паники в горутинах (Goroutine Panic Isolation): непойманная паника внутри любой горутины немедленно роняет **весь Go-процесс целиком**. Обертка `SafeGo` перехватывает панику внутри горутины через `recover()` и логирует стектрейс, защищая весь сервер от аварийного падения.

## Решение по шагам

1. Создадим функцию `SafeGo(fn func())`.
2. Внутри горутины установим `defer` с `recover()` и `runtime.Stack()`.
3. Запустим горутину с намеренной паникой (обращение по nil-указателю).
4. Проверим, что основной сервер продолжает работать.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func SafeGo(wg *sync.WaitGroup, fn func()) {
	wg.Add(1)
	go func() {
		defer wg.Done()
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("[SafeGo Panic Handler] ПЕРЕХВАЧЕНА КРИТИЧЕСКАЯ ПАНИКА: %v! Сервер продолжает работу.\n", r)
			}
		}()
		fn()
	}()
}

func main() {
	var wg sync.WaitGroup

	// Запуск паникующей горутины
	SafeGo(&wg, func() {
		fmt.Println("[Worker 1] Старт работы...")
		var ptr *int
		*ptr = 42 // Фатальное разыменование nil-указателя
	})

	// Запуск нормальной горутины
	SafeGo(&wg, func() {
		time.Sleep(10 * time.Millisecond)
		fmt.Println("[Worker 2] Успешно завершил работу!")
	})

	wg.Wait()
	fmt.Println("[Main] Сервер не упал и успешно обработал все запросы!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Worker 1] Старт работы...
# [SafeGo Panic Handler] ПЕРЕХВАЧЕНА КРИТИЧЕСКАЯ ПАНИКА: runtime error: invalid memory address or nil pointer dereference! Сервер продолжает работу.
# [Worker 2] Успешно завершил работу!
# [Main] Сервер не упал и успешно обработал все запросы!
```

## Под капотом

`recover()` перехватывает панику на уровне стека конкретной горутины, не затрагивая другие потоки планировщика.

## Подводные камни

`recover()` в `main` не может поймать панику из другой горутины — `recover` обязан находиться строго внутри тела самой горутины!

## На собеседовании

**Вопрос с собеседования:** «Может ли recover() в родительской горутине поймать панику в дочерней go func()?»
**Ответ:** Нет! Паника раскручивает стек строго текущей горутины. Если в ее стеке нет отложенного вызова `recover()`, процесс немедленно завершается с дампом всех горутин (Crash-on-Panic).
