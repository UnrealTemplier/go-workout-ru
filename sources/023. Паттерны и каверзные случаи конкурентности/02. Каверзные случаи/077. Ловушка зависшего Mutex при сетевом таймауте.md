# Ловушка зависшего Mutex при сетевом таймауте и паттерн defer Unlock

## Условие

Напишите программу, где горутина удерживает `Mutex` и пытается сделать HTTP-запрос с таймаутом. Что будет, если таймаут сработает, а Mutex останется заблокированным?

## Теория

Опасный антипаттерн «Захват мьютекса вокруг сетевого I/O»: блокировка мьютекса на время HTTP-запроса или запроса к СУБД замораживает все остальные горутины сервиса. Если сетевой вызов упадет по таймауту или выйдет через `return err` без `defer mu.Unlock()`, наступит перманентный Deadlock.

## Решение по шагам

1. Продемонстрируем правильное проектирование: минимизация критической секции.
2. Сетевой вызов выполняется БЕЗ удержания мьютекса.
3. Мьютекс захватывается только на миллисекунду для обновления локального кэша под `defer mu.Unlock()`.
4. Проверим быстродействие.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type SafeAPIState struct {
	mu        sync.Mutex
	lastData  string
	updatedAt time.Time
}

// ПРАВИЛЬНЫЙ ПОДХОД: I/O операция выполняется СНАРУЖИ критической секции!
func (s *SafeAPIState) RefreshDataSafe(ctx context.Context, id int, wg *sync.WaitGroup) {
	defer wg.Done()

	// 1. Сетевой запрос выполняется БЕЗ блокировки мьютекса!
	fmt.Printf("[Client #%d] Старт внешнего сетевого запроса...\n", id)
	time.Sleep(15 * time.Millisecond) // Имитация HTTP I/O
	fetchedResult := fmt.Sprintf("Response-for-#%d", id)

	// 2. Мьютекс захватывается строго на доли микросекунды для записи в память
	s.mu.Lock()
	defer s.mu.Unlock() // Гарантированное освобождение даже при панике!

	s.lastData = fetchedResult
	s.updatedAt = time.Now()
	fmt.Printf(" -> [Client #%d] Кэш успешно обновлен в памяти: %s\n", id, s.lastData)
}

func main() {
	state := &SafeAPIState{}
	var wg sync.WaitGroup

	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go state.RefreshDataSafe(ctx, i, &wg)
	}

	wg.Wait()
	fmt.Println("[Main] Все запросы выполнены параллельно без блокировки мьютексом.")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Client #1] Старт внешнего сетевого запроса...
# [Client #2] Старт внешнего сетевого запроса...
# [Client #3] Старт внешнего сетевого запроса...
#  -> [Client #1] Кэш успешно обновлен в памяти: Response-for-#1
#  -> [Client #2] Кэш успешно обновлен в памяти: Response-for-#2
#  -> [Client #3] Кэш успешно обновлен в памяти: Response-for-#3
# [Main] Все запросы выполнены параллельно без блокировки мьютексом.
```

## Под капотом

Сетевые вызовы выполняются параллельно на 3 ядрах, а время удержания мьютекса сокращается до нескольких наносекунд.

## Подводные камни

Никогда не удерживайте `sync.Mutex` во время выполнения сетевых HTTP/gRPC/SQL запросов.

## На собеседовании

**Вопрос с собеседования:** «Почему удерживать sync.Mutex во время сетевого I/O считается грубейшей архитектурной ошибкой?»
**Ответ:** Сетевой запрос может зависнуть на десятки секунд (таймаут TCP), что заблокирует все остальные горутины, пытающиеся получить доступ к структуре, вызвав полный отказ всего микросервиса (Service Outage).
