# Идиоматичный Broadcast через закрытие сигнального канала (close)

## Условие

«Broadcast» через закрытие канала: несколько горутин ждут сигнала старта, читая из одного канала. Закрытие канала разблокирует всех.

## Теория

Канонический паттерн Go Broadcast: закрытие канала `close(start)` мгновенно переводит его в состояние готовности к чтению Zero Value для **всех** ожидающих горутин одновременно (O(1) время оповещения).

## Решение по шагам

1. Создадим канал `start := make(chan struct{})`.
2. Запустим 4 горутины-атлета, ожидающие `<-start`.
3. В `main` вызовем `close(start)` (выстрел стартового пистолета).
4. Все 4 горутины мгновенно стартуют одновременно.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func runner(id int, start <-chan struct{}, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Printf("[Атлет #%d] На стартовой позиции... ждет выстрела\n", id)

	<-start // Блокировка до закрытия канала start!

	fmt.Printf(" -> [Атлет #%d] ПОБЕЖАЛ!\n", id)
}

func main() {
	start := make(chan struct{})
	var wg sync.WaitGroup

	for i := 1; i <= 4; i++ {
		wg.Add(1)
		go runner(i, start, &wg)
	}

	time.Sleep(20 * time.Millisecond)
	fmt.Println("\n[Судья] ВЫСТРЕЛ СТАРТОВОГО ПИСТОЛЕТА (close(start))!")
	close(start) // Широковещательный сигнал всем 4 горутинам

	wg.Wait()
	fmt.Println("[Main] Все атлеты успешно финишировали.")
}
```

**`Терминал`**

```bash

# Вывод:
```

## Под капотом

Рантайм переносит все горутины из списка ожидания `recvq` канала в глобальную очередь готовности планировщика `_Grunnable`.

## Подводные камни

Отправка значения в канал `start <- struct{}{}` разблокировала бы ровно одну горутину вместо всех.

## На собеседовании

**Вопрос с собеседования:** «Почему close(ch) является самым быстрым способом Broadcast в Go?»
**Ответ:** Потому что отправка \(N\) сообщений требует \(N\) операций с захватом мьютекса канала, а `close(ch)` выполняет один системный сброс очереди `recvq` за \(O(1)\).
