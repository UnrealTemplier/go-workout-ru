# Защита от фатальной паники при закрытии nil-канала (closing nil channel)

## Условие

Напиши программу с **"closing nil channel"**: `var ch chan int; close(ch)`. Получи панику. Напиши защиту: проверяй `if ch != nil` перед закрытием.

## Теория

Вызов `close(ch)` на `nil`-канале немедленно приводит к панике `panic: close of nil channel`. Защитная функция проверяет указатель на неравенство `nil` перед закрытием.

## Решение по шагам

1. Создадим функцию `SafeCloseChannel(ch chan int)`.
2. Добавим явную проверку `if ch != nil`.
3. Протестируем на неинициализированном канале.
4. Убедимся в отсутствии паники.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func SafeCloseChannel[T any](ch chan T) bool {
	if ch == nil {
		fmt.Println("[SafeClose] Предотвращена паника 'close of nil channel': канал равен nil!")
		return false
	}
	close(ch)
	fmt.Println("[SafeClose] Канал успешно закрыт.")
	return true
}

func main() {
	var nilChan chan int // Неинициализированный nil-канал

	success := SafeCloseChannel(nilChan)
	fmt.Printf("Результат закрытия nil-канала: %v\n", success)

	validChan := make(chan int, 1)
	SafeCloseChannel(validChan)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [SafeClose] Предотвращена паника 'close of nil channel': канал равен nil!
# Результат закрытия nil-канала: false
# [SafeClose] Канал успешно закрыт.
```

## Под капотом

Неинициализированная переменная `var ch chan T` имеет значение `nil` (нулевой указатель на `hchan`).

## Подводные камни

Проверка `ch != nil` не защищает от повторного закрытия уже закрытого канала — для этого нужен `sync.Once`.

## На собеседовании

**Вопрос с собеседования:** «Какие 3 операции с каналами вызывают немедленную панику в Go?»
**Ответ:** 1) `close(nil)` — закрытие nil-канала, 2) `close(closed)` — повторное закрытие уже закрытого канала, 3) `closed <- val` — отправка значения в закрытый канал.
