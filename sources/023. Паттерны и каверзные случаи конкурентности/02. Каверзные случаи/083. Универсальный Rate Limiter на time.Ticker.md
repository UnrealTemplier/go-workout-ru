# Универсальный Rate Limiter на time.Ticker и буферизованном канале

## Условие

**Rate Limiter**: Реализуйте ограничитель частоты запросов (например, не более 10 запросов в секунду) с использованием `time.Ticker` и буферизованного канала.

## Теория

Синхронизация RPS: буферизованный канал токенов, наполняемый периодическим тикером `time.NewTicker(20 * time.Millisecond)`.

## Решение по шагам

1. Создадим канал токенов `limiter := make(chan time.Time, 1)`.
2. Запустим тикер пополнения.
3. Пропустим 4 запроса.
4. Зафиксируем равномерность интервалов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	// Лимит: 1 запрос каждые 20 мс
	limiter := make(chan time.Time, 1)

	go func() {
		ticker := time.NewTicker(20 * time.Millisecond)
		defer ticker.Stop()
		for t := range ticker.C {
			limiter <- t
		}
	}()

	requests := []int{1, 2, 3, 4}
	start := time.Now()

	for _, req := range requests {
		<-limiter
		fmt.Printf("[Client] Запрос #%d отправлен в %v\n", 
			req, time.Since(start).Round(time.Millisecond))
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Client] Запрос #1 отправлен в 20ms
# [Client] Запрос #2 отправлен в 40ms
# [Client] Запрос #3 отправлен в 60ms
# [Client] Запрос #4 отправлен в 80ms
```

## Под капотом

`<-limiter` блокирует выполнение до поступления очередного тика.

## Подводные камни

Всегда учитывайте время жизни тикера.

## На собеседовании

**Вопрос с собеседования:** «Какова погрешность time.Ticker в ОС Linux?»
**Ответ:** В зависимости от `hz` ядра и загрузки планировщика погрешность таймеров составляет от 0.1 до 1 мс, что абсолютно достаточно для сетевых микросервисов.
