# Ограничение скорости обработки запросов через периодический тикер

## Условие

**Rate Limiting (Ограничение скорости)**: Используй `time.Tick` (например, каждые 200ms) для ограничения частоты обработки запросов. Запросы поступают быстрее, но обрабатываются только по тику.

## Теория

Фиксированный Rate Limiter: входной поток запросов обрабатывается строго со скоростью тикера `time.NewTicker(20 * time.Millisecond)`.

## Решение по шагам

1. Создадим канал входящих запросов `requests`.
2. Создадим тикер.
3. В цикле считываем `<-ticker.C` перед обработкой каждого запроса.
4. Проверим равномерность таймингов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	requests := make(chan int, 5)
	for i := 1; i <= 4; i++ {
		requests <- i
	}
	close(requests)

	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	start := time.Now()
	for req := range requests {
		<-ticker.C // Ждем тика перед обработкой
		fmt.Printf("[Server] Запрос #%d обработан в %v\n", 
			req, time.Since(start).Round(time.Millisecond))
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Server] Запрос #1 обработан в 20ms
# [Server] Запрос #2 обработан в 40ms
# [Server] Запрос #3 обработан в 60ms
# [Server] Запрос #4 обработан в 80ms
```

## Под капотом

Канал `ticker.C` синхронизирует скорость обработки с таймером ОС.

## Подводные камни

Использование `time.Tick()` в долгоживущих сервисах приводит к утечке памяти, так как его невозможно остановить. Всегда используйте `time.NewTicker` с `defer ticker.Stop()`.

## На собеседовании

**Вопрос с собеседования:** «Почему time.Tick нельзя использовать в функциях, которые вызываются многократно?»
**Ответ:** `time.Tick` не предоставляет способ остановить тикер (`Stop()`), поэтому сборщик мусора не может освободить его горутину и таймер рантайма, вызывая прогрессирующую утечку памяти.
