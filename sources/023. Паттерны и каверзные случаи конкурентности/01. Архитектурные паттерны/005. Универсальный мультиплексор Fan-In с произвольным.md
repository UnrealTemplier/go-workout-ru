# Универсальный мультиплексор Fan-In с произвольным числом каналов

## Условие

**Fan-In**: Напишите функцию, которая принимает множество каналов и сливает их данные в один выходной канал (Multiplexing).

## Теория

Функция `FanIn` с вариативным аргументом `channels ...<-chan T` принимает произвольное количество входных каналов и возвращает единый мультиплексированный канал `<-chan T`.

## Решение по шагам

1. Объявим `FanIn(channels ...<-chan string) <-chan string`.
2. Для каждого канала запустим горутину считывания, инкрементируя `sync.WaitGroup`.
3. Запустим горутину ожидания `wg.Wait()` и закрытия общего канала.
4. Продемонстрируем объединение 3 источников.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func FanIn(channels ...<-chan string) <-chan string {
	out := make(chan string)
	var wg sync.WaitGroup

	for _, ch := range channels {
		wg.Add(1)
		go func(c <-chan string) {
			defer wg.Done()
			for msg := range c {
				out <- msg
			}
		}(ch)
	}

	go func() {
		wg.Wait()
		close(out)
	}()

	return out
}

func sourceStream(prefix string, count int) <-chan string {
	ch := make(chan string)
	go func() {
		defer close(ch)
		for i := 1; i <= count; i++ {
			ch <- fmt.Sprintf("%s-Item#%d", prefix, i)
			time.Sleep(5 * time.Millisecond)
		}
	}()
	return ch
}

func main() {
	s1 := sourceStream("Kafka", 2)
	s2 := sourceStream("RabbitMQ", 2)
	s3 := sourceStream("Redis", 2)

	merged := FanIn(s1, s2, s3)

	for msg := range merged {
		fmt.Printf("Получено событие: %s\n", msg)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Получено событие: Kafka-Item#1
# Получено событие: RabbitMQ-Item#1
# Получено событие: Redis-Item#1
# Получено событие: Kafka-Item#2
# Получено событие: RabbitMQ-Item#2
# Получено событие: Redis-Item#2
```

## Под капотом

`FanIn` использует передачу переменной `c` в аргументы анонимной горутины `go func(c <-chan string)`, предотвращая Data Race замыкания.

## Подводные камни

Захват переменной цикла `ch` по ссылке без передачи параметром в Go < 1.22 приводил к чтению только из последнего канала.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя использовать reflect.Select для объединения произвольного числа каналов в highload-сервисах?»
**Ответ:** `reflect.Select` создает значительные накладные расходы на рефлексию и аллокации `reflect.SelectCase` в куче на каждом шаге. Паттерн Fan-In на горутинах и `sync.WaitGroup` в разы быстрее и эффективнее утилизирует планировщик Go.
