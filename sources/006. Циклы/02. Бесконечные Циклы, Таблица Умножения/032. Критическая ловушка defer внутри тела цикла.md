# Критическая ловушка defer внутри тела цикла и правильный рефакторинг через анонимную функцию

## Условие

**`defer` внутри цикла**: Напишите цикл, который открывает файлы (или эмулирует это) и делает `defer file.Close()` внутри тела цикла. Поймите, почему это приведет к утечке файловых дескрипторов (deffered-функции выполнятся только при выходе из *функции*, а не из *цикла*).

## Теория

**Критический антипаттерн `defer` в цикле:**
1. Инструкции `defer` выполняются **только при возврате из окружающей функции**, а НЕ при завершении итерации цикла!
2. Если в цикле на \(100\,000\) итераций открывать файлы и писать `defer file.Close()`, все \(100\,000\) дескрипторов останутся открытыми до самого конца функции \(\rightarrow\) ОС выдаст ошибку `too many open files` (исчерпание `ulimit -n`);
3. **Идиоматичное решение:** выносить тело итерации в отдельную функцию или замыкание `func() { ... }()`.

## Решение по шагам

1. Демонстрируем проблему накопления `defer`.
2. Исправляем паттерном анонимного замыкания `func(f string) { defer ... }()`.
3. Убеждаемся в своевременном закрытии ресурсов на каждом шаге.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func processResourceSafe(name string) {
	fmt.Printf("1. Открытие ресурса [%s]\n", name)
	// defer выполнится немедленно при выходе из этой функции:
	defer fmt.Printf("2. Закрытие ресурса [%s] ✔\n", name)

	fmt.Printf("   -> Обработка данных [%s]...\n", name)
}

func main() {
	files := []string{"log1.txt", "log2.txt", "log3.txt"}

	fmt.Println("=== Корректная обработка файлов без утечек дескрипторов ===")
	for _, f := range files {
		// Решение: изолированный фрейм функции
		processResourceSafe(f)
	}
	fmt.Println("Все файлы успешно обработаны.")
}
```

ℹ️ Изоляция defer через вызов функции

**`Терминал`**


ℹ️ Своевременное освобождение ресурсов

## Под капотом

`defer` добавляет запись в связный список `_defer` текущей горутины (`g._defer`). Список разматывается только в эпилоге возврата из функции.

## Подводные камни

- Написание `defer resp.Body.Close()` внутри цикла обработки HTTP-запросов: быстро приводит к утечке сокетов операционной системы.

## На собеседовании

**Вопрос с собеседования:** «Почему линтер `gocritic` помечает `deferInLoop` как серьезную проблему?»
**Ответ:** Потому что отложенные вызовы аллоцируют память на каждую итерацию и удерживают системные ресурсы (файлы, мьютексы, сокеты) дольше положенного, провоцируя падение сервиса под нагрузкой.
