# Затенение переменных (Variable Shadowing) в заголовке if

## Условие

**Теневое копирование (Shadowing) в `if`**: Объяви `x := 10` до `if`. Затем напиши `if x := 5; x > 0 { fmt.Println(x) }`. Выведи `x` после `if`. Пойми, почему внутри `if` была 5, а снаружи осталась 10.

## Теория

**Механика Shadowing в `if`:**
- Внешняя переменная `x = 10` находится в Function Scope;
- Заголовок `if x := 5; ...` создает **новую локальную переменную `x`** в Block Scope;
- Внутри блока `if` доступен только внутренний `x` (значение 5);
- После выхода из `if` внешний `x` сохраняет исходное значение 10.

## Решение по шагам

1. Объявляем `x := 10`.
2. Пишем `if x := 5; x > 0 { ... }`.
3. Выводим `x` после блока.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func main() {
	x := 10
	fmt.Println("1. Внешний x до if:     ", x)

	if x := 5; x > 0 {
		fmt.Println("2. Внутренний x внутри if:", x)
	}

	fmt.Println("3. Внешний x после if:    ", x)
}
```

ℹ️ Затенение в if

**`Терминал`**

```bash
go run main.go
# 1. Внешний x до if:      10
# 2. Внутренний x внутри if: 5
# 3. Внешний x после if:     10
```

ℹ️ Результат затенения

## Под капотом

Компилятор резервирует два разных адреса стекового фрейма: один для внешнего `x`, второй для внутреннего `x`.

## Подводные камни

- Случайное затенение глобального контекста `ctx` или `client` в обработчиках HTTP.

## На собеседовании

**Вопрос с собеседования:** «Почему затенение ошибки `if data, err := parse(); err != nil` во вложенном блоке считается одной из самых опасных ошибок?»
**Ответ:** Потому что если внешняя переменная `err` ожидалась для проверки статуса после блока `if`, она останется `nil`, программа продолжит работу со сломанным состоянием и упадет позже с паникой `nil pointer dereference`.
