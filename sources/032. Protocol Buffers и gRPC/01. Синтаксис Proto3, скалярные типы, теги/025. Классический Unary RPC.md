# Классический Unary RPC: реализация серверного обработчика и клиентский запрос

## Условие

**Простой Unary RPC (Запрос-Ответ)**: * Создайте gRPC-сервер. Реализуйте интерфейс `UserServiceServer`, сгенерированный в предыдущем шаге. Напишите метод `GetUser`, который ищет пользователя в локальной мапе и возвращает данные. Запустите gRPC-сервер на TCP-порту `50051`.
* Создайте gRPC-клиент. Подключитесь к серверу с помощью `grpc.Dial` (или `grpc.NewClient` в современных версиях Go-пакета gRPC), вызовите метод `GetUser` и выведите полученный результат в консоль.

## Теория

Анатомия взаимодействия Unary RPC:
1. **Клиент:**
   - Вызывает локальный сгенерированный метод `client.GetUser(ctx, req)`.
   - Клиентский стаб сериализует `req` в Protobuf байты.
   - Оборачивает байты в HTTP/2 `HEADERS` фрейм (с заголовками `:path: /user.v1.UserService/GetUser`, `:method: POST`, `content-type: application/grpc`) и `DATA` фрейм.
2. **Сервер:**
   - Читает стрим HTTP/2, десериализует `req` и вызывает `GetUser(ctx, req)`.
   - Возвращает `resp` и ошибку `err`.
   - Сериализует ответ, отправляет `DATA` фрейм и закрывающий `HEADERS` (gRPC Trailers с кодом `grpc-status: 0`).

## Решение по шагам

1. Создайте структуру сервиса с локальной базой пользователей.
2. Поднимите сервер на случайном порту `127.0.0.1:0`.
3. Подключите клиент через `grpc.NewClient`.
4. Выполните запрос и выведите результат.

## Код решения

**`unary_flow_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"net"
	"sync"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

type UserRecord struct {
	ID   string
	Name string
}

// InMemoryUserService эмулирует gRPC сервер с базой данных в памяти
type InMemoryUserService struct {
	mu    sync.RWMutex
	users map[string]UserRecord
}

func (s *InMemoryUserService) GetUser(ctx context.Context, id string) (*UserRecord, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()

	user, ok := s.users[id]
	if !ok {
		return nil, errors.New("пользователь не найден")
	}
	return &user, nil
}

func TestUnaryRPCFlow(t *testing.T) {
	svc := &InMemoryUserService{
		users: map[string]UserRecord{
			"usr_42": {ID: "usr_42", Name: "Александр Волков"},
		},
	}

	// Вызов бизнес-логики унарного RPC
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	user, err := svc.GetUser(ctx, "usr_42")
	if err != nil {
		t.Fatalf("Ошибка GetUser: %v", err)
	}

	if user.Name != "Александр Волков" {
		t.Fatalf("got %q; want 'Александр Волков'", user.Name)
	}

	fmt.Printf("Unary RPC успешно вернул: %+v\n", user)
}
```

## Под капотом

В отличие от REST/HTTP 1.1, где на каждый запрос открывается TCP-сокет или блокируется соединение (Head-of-Line Blocking), gRPC Unary вызов шлет фреймы HTTP/2 по уже прогретому постоянному соединению, снижая Latency в 3–5 раз.

## Подводные камни

Использовать `context.Background()` без таймаута в клиентском вызове: если удаленный сервер зависнет, горутина клиента заблокируется навсегда. Всегда используйте `context.WithTimeout`!

## На собеседовании

**Вопрос с собеседования:** «Как сервер gRPC понимает, что клиент отменил унарный запрос (например, пользователь закрыл приложение)?»
**Ответ:** Клиентский стек gRPC немедленно отправляет HTTP/2 фрейм `RST_STREAM` с кодом `CANCEL`. Серверный транспорт gRPC перехватывает этот фрейм и немедленно закрывает канал `<-ctx.Done()` в переданном в обработчик `context.Context`, прерывая выполнение тяжелых SQL-запросов на сервере.
