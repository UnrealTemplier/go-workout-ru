# Описание первой схемы Protobuf: спецификация proto3, числовые теги и сервис UserService

## Условие

**Описание первой схемы Protobuf**: Создайте файл `user.proto`. Напишите схему protobuf (версии `syntax = "proto3"`). Объявите сообщение `UserRequest` с полем `user_id` (тип `string`, тег `1`) и сообщение `UserResponse` с полями `id`, `name`, `email` и списком ролей `repeated string roles`. Опишите gRPC-сервис `UserService` с методом `GetUser`, который принимает `UserRequest` и возвращает `UserResponse`.

## Теория

Архитектурные основы Protocol Buffers (proto3):
- Protocol Buffers (Protobuf) — бинарный, компактный, платформо- и языконезависимый протокол сериализации данных, разработанный Google.
- Ключевые концепции спецификации:
  1. `syntax = "proto3";` — обязательное объявление версии синтаксиса в первой строке.
  2. **Числовые теги (Field Numbers):** в бинарном представлении имена полей (`user_id`, `email`) **НЕ передаются по сети**. Вместо них передается тег поля (Field Tag) в связке с типом данных (Wire Type). Теги от 1 до 15 кодируются ровно в 1 байт, поэтому их резервируют для самых частотных полей.
  3. `repeated` — динамический массив произвольной длины (в Go преобразуется в слайс `[]T`).
  4. `service` — декларация удаленного интерфейса вызова процедур (gRPC API).

## Решение по шагам

1. Создайте файл `user.proto`.
2. Укажите версию `proto3` и имя пакета Go через директиву `option go_package`.
3. Опишите сообщения запроса `UserRequest` и ответа `UserResponse`.
4. Объявите сервис `UserService` с унарным методом `GetUser`.

## Код решения

**`proto/user.proto`**

```protobuf
syntax = "proto3";

package user.v1;

option go_package = "github.com/myorg/myapp/gen/user/v1;userv1";

// UserRequest представляет запрос на получение пользователя
message UserRequest {
  string user_id = 1;
}

// UserResponse содержит профиль пользователя и его роли
message UserResponse {
  string id = 1;
  string name = 2;
  string email = 3;
  repeated string roles = 4;
}

// UserService предоставляет операции над пользователями
service UserService {
  rpc GetUser(UserRequest) returns (UserResponse);
}
```

ℹ️ Спецификация схемы user.proto с описанием сервиса и сообщений

**`user_mock.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// UserRequestDTO эмулирует структуру, генерируемую protoc-gen-go
type UserRequestDTO struct {
	UserID string
}

// UserResponseDTO эмулирует сгенерированное сообщение ответа
type UserResponseDTO struct {
	ID    string
	Name  string
	Email string
	Roles []string
}

// UserServerService реализует бизнес-логику gRPC сервиса
type UserServerService struct{}

func (s *UserServerService) GetUser(ctx context.Context, req *UserRequestDTO) (*UserResponseDTO, error) {
	if req.UserID == "" {
		return nil, errors.New("user_id не может быть пустым")
	}

	return &UserResponseDTO{
		ID:    req.UserID,
		Name:  "Алексей Смирнов",
		Email: "alex@example.com",
		Roles: []string{"ADMIN", "DEVELOPER"},
	}, nil
}

func main() {
	svc := &UserServerService{}
	resp, err := svc.GetUser(context.Background(), &UserRequestDTO{UserID: "usr_100500"})
	if err != nil {
		panic(err)
	}
	fmt.Printf("Пользователь: %s (%s), Роли: %v\n", resp.Name, resp.Email, resp.Roles)
}
```

## Под капотом

В бинарном проводе Protobuf заголовок поля кодируется формулой `(field_number << 3) | wire_type`. Для тега `1` и типа `string` (Wire Type 2) получается байт `0x0A` (`00001010` в двоичном виде). Имя поля `user_id` вообще отсутствует в пакете, обеспечивая колоссальную экономию сетевого трафика.

## Подводные камни

Менять числовые теги полей в существующих схемах: если изменить тег `user_id = 1` на `user_id = 2`, старые клиенты перестанут понимать новые серверы, что вызовет тихую потерю данных (десериализатор запишет поле в Unknown Fields).

## На собеседовании

**Вопрос с собеседования:** «Почему в Protobuf номера тегов от 1 до 15 считаются самыми ценными?»
**Ответ:** Заголовок поля `(field_number << 3) | wire_type` для тегов \(1 \dots 15\) помещается ровно в 1 байт (так как \(15 \times 8 + 7 = 127 < 128\)). Начиная с тега 16, под заголовок требуется уже 2 байта Varint. В высоконагруженных системах (Google, Ozon) теги 1–15 резервируют строго для самых частотных полей hot-path сообщений.
