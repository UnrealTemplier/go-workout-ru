# Эволюция контрактов: добавление перечисления Role в сообщение User и обратная совместимость

## Условие

Добавь в `.proto` файл enum `Role` (UNKNOWN, ADMIN, USER). Включи его в сообщение `User`. Перекомпилируй.

## Теория

Золотые правила эволюции Protobuf схем:
1. **Никогда не меняйте номера существующих тегов.**
2. **Никогда не удаляйте поля без резервирования (`reserved`).**
3. **Новое поле всегда получает новый свободный тег.**
4. Если старый клиент отправит запрос без нового поля `Role`, сервер автоматически получит дефолтное значение `ROLE_UNKNOWN = 0`.
5. Если новый клиент пошлет `Role` на старый сервер, старый сервер безопасно сохранит неизвестные байты в `unknownFields`.

## Решение по шагам

1. Создайте схему с новой версией сообщения `User`.
2. Добавьте `Role role = 4;`.
3. Продемонстрируйте корректную обработку старыми и новыми обработчиками в Go.

## Код решения

**`user_v2.proto`**

```protobuf
syntax = "proto3";

package user.v2;

option go_package = "./userv2;userv2";

enum Role {
  ROLE_UNKNOWN = 0;
  ROLE_ADMIN = 1;
  ROLE_USER = 2;
}

message User {
  int64 id = 1;
  string name = 2;
  string email = 3;
  Role role = 4; // Новое поле, добавленное в версию v2
}
```

ℹ️ Обратно-совместимое расширение схемы полем role

**`backward_compat_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type UserV1 struct {
	ID    int64
	Name  string
	Email string
}

type UserV2 struct {
	ID    int64
	Name  string
	Email string
	Role  int32
}

func TestBackwardCompatibility(t *testing.T) {
	// Старый клиент прислал V1 (без поля Role)
	v1ClientData := &UserV1{ID: 10, Name: "Артем", Email: "artem@mail.ru"}

	// Новый сервер парсит в структуру V2:
	v2ServerData := &UserV2{
		ID:    v1ClientData.ID,
		Name:  v1ClientData.Name,
		Email: v1ClientData.Email,
		Role:  0, // Дефолтное значение ROLE_UNKNOWN!
	}

	if v2ServerData.Role != 0 {
		t.Fatalf("Ожидалось дефолтное значение 0")
	}

	fmt.Printf("V1 клиент успешно обработан V2 сервером: Role=%d (UNKNOWN)\n", v2ServerData.Role)
}
```

ℹ️ Тест обратной совместимости при добавлении поля enum

## Под капотом

В proto3 все поля по умолчанию опциональны (Implicit Field Presence). Если десериализатор не обнаружил тег `4` во входном потоке, он просто оставляет поле `Role` инициализированным нулем, не генерируя ошибок.

## Подводные камни

Удалить старое поле и назначить его тег новому полю: старые сообщения распакуются с испорченными данными. Всегда используйте ключевое слово `reserved`.

## На собеседовании

**Вопрос с собеседования:** «Как безопасно удалить устаревшее поле из proto-схемы в продакшене?»
**Ответ:** Пометить номер тега и имя поля как зарезервированные: `reserved 4; reserved "old_field";`. Это защитит других разработчиков от случайного переиспользования этого тега или имени в будущем, гарантируя безопасность старых архивов логов и баз данных.
