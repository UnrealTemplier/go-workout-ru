# Проектирование сообщений запроса и ответа: контракт GetUserRequest и компиляция сервиса

## Условие

Добавь сообщение `GetUserRequest` с полем `id`. Опиши сервис `UserService` с методом `GetUser`, который принимает запрос и возвращает `User`. Скомпилируй.

## Теория

Принцип именования RPC методов и параметров:
- По стандартам проектирования gRPC API (API Design Guide Google):
  1. Имя запроса строится по шаблону: `<MethodName>Request` (например `GetUserRequest`).
  2. Имя ответа строится по шаблону: `<MethodName>Response` или сущность ресурса (например `User`).
  3. Даже если запрос сейчас содержит только одно поле `id`, **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** передавать скалярные типы напрямую в метод:
     `rpc GetUser(int64) returns (User);` — синтаксически недопустимо в Protobuf!

## Решение по шагам

1. Создайте `GetUserRequest` с полем `int64 id = 1;`.
2. Объявите сервис `UserService` с методом `GetUser`.
3. Скомпилируйте контракт.
4. Проверьте сигнатуру сгенерированного метода.

## Код решения

**`user_api.proto`**

```protobuf
syntax = "proto3";

package user.v1;

option go_package = "./userv1;userv1";

message User {
  int64 id = 1;
  string username = 2;
  string email = 3;
}

message GetUserRequest {
  int64 id = 1;
}

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
```

ℹ️ Спецификация метода GetUser с изолированным сообщением запроса

**`service_signature_check.go`**

```go
package main

import (
	"context"
	"fmt"
)

type UserEntity struct {
	Id       int64
	Username string
	Email    string
}

type GetUserReq struct {
	Id int64
}

type UserApiServer interface {
	GetUser(ctx context.Context, req *GetUserReq) (*UserEntity, error)
}

type ConcreteUserService struct{}

func (s *ConcreteUserService) GetUser(ctx context.Context, req *GetUserReq) (*UserEntity, error) {
	return &UserEntity{
		Id:       req.Id,
		Username: "viktor_lead",
		Email:    "viktor@enterprise.com",
	}, nil
}

func main() {
	var api UserApiServer = &ConcreteUserService{}
	user, err := api.GetUser(context.Background(), &GetUserReq{Id: 1001})
	if err != nil {
		panic(err)
	}

	fmt.Printf("Успешный вызов GetUser: ID=%d, User=%s, Email=%s\n",
		user.Id, user.Username, user.Email)
}
```

ℹ️ Проверка соответствия сигнатуры метода интерфейсу

**`Терминал`**

```bash
go run service_signature_check.go
# Вывод:
# Успешный вызов GetUser: ID=1001, User=viktor_lead, Email=viktor@enterprise.com
```

## Под капотом

Оборачивание входных параметров в выделенное сообщение `GetUserRequest` позволяет в будущем добавить поля пагинации, маски полей или флаги кэширования без смены сигнатуры интерфейса метода.

## Подводные камни

Использовать одно и то же сообщение запроса для разных методов (например использовать `GetUserRequest` в `DeleteUser`): при развитии методов требования к полям разойдутся, вызвав запутанность контрактов.

## На собеседовании

**Вопрос с собеседования:** «Почему в Protobuf нельзя передавать примитивные типы (string, int) прямо в сигнатуру rpc Method(string)?»
**Ответ:** Потому что в Protobuf единица сериализации — это сообщение (Message), содержащее числовые теги полей. Примитивный тип не имеет тега. Кроме того, использование структур запроса гарантирует расширяемость API в будущем без ломающих изменений.
