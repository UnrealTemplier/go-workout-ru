# Анатомия сгенерированных файлов: детальный разбор user.pb.go и user_grpc.pb.go

## Условие

Скомпилируй `.proto` файл в Go-код. Изучи сгенерированные файлы `user.pb.go` (структуры) и `user_grpc.pb.go` (интерфейсы клиента и сервера).

## Теория

Разделение ответственности сгенерированных артефактов:
1. **Файл `user.pb.go` (Protobuf Data Model):**
   - Структуры данных (`type User struct`).
   - Приватные поля состояния: `state protoimpl.MessageState`, `sizeCache protoimpl.SizeCache`, `unknownFields protoimpl.UnknownFields`.
   - Метод `ProtoReflect()` — дескриптор метаданных схемы.
   - Метод `Reset()`, `String()`, `ProtoMessage()`.
   - Безопасные геттеры `Get...()`.
2. **Файл `user_grpc.pb.go` (gRPC Networking Layer):**
   - Клиентский интерфейс: `type UserServiceClient interface`.
   - Реализация клиента: `type userClient struct { cc grpc.ClientConnInterface }`.
   - Серверный интерфейс: `type UserServiceServer interface`.
   - Структура совместимости: `UnimplementedUserServiceServer`.
   - Дескриптор сервиса: `UserService_ServiceDesc` с таблицей методов.

## Решение по шагам

1. Сгенерируйте оба файла из схемы.
2. Изучите внутреннее устройство структуры данных в `.pb.go`.
3. Изучите регистрационный дескриптор `ServiceDesc` в `_grpc.pb.go`.

## Код решения

**`generated_anatomy_study.go`**

```go
package main

import (
	"context"
	"fmt"

	"google.golang.org/grpc"
)

// 1. Анатомия структуры из user.pb.go
type GeneratedUserStruct struct {
	Id   int64
	Name string
	// В реальном файле присутствуют:
	// state         protoimpl.MessageState
	// sizeCache     protoimpl.SizeCache
	// unknownFields protoimpl.UnknownFields
}

// 2. Анатомия интерфейса клиента из user_grpc.pb.go
type UserServiceClient interface {
	GetUser(ctx context.Context, in *GeneratedUserStruct, opts ...grpc.CallOption) (*GeneratedUserStruct, error)
}

// 3. Анатомия дескриптора сервиса для grpc.Server
var UserService_ServiceDesc = grpc.ServiceDesc{
	ServiceName: "user.v1.UserService",
	HandlerType: (*any)(nil),
	Methods: []grpc.MethodDesc{
		{
			MethodName: "GetUser",
			Handler: func(srv any, ctx context.Context, dec func(any) error, interceptor grpc.UnaryServerInterceptor) (any, error) {
				// Внутренний диспатчер вызовов gRPC
				return nil, nil
			},
		},
	},
	Streams:  []grpc.StreamDesc{},
	Metadata: "user.proto",
}

func main() {
	fmt.Printf("Зарегистрирован сервис: %s\n", UserService_ServiceDesc.ServiceName)
	fmt.Printf("Количество унарных методов: %d\n", len(UserService_ServiceDesc.Methods))
}
```

ℹ️ Разбор сгенерированных сущностей pb.go и grpc.pb.go

**`Терминал`**

```bash
go run generated_anatomy_study.go
# Вывод:

# Количество унарных методов: 1
```

## Под капотом

Поле `unknownFields` хранит байты полей, которые были присланы новым клиентом, но неизвестны текущей версии сервера. Благодаря этому сервер при повторной отправке не теряет новые данные, сохраняя полную прямую совместимость (Forward Compatibility).

## Подводные камни

Вручную редактировать файлы `*.pb.go`: при следующей команде `buf generate` или `protoc` любые ручные правки будут бесследно перезаписаны.

## На собеседовании

**Вопрос с собеседования:** «Зачем в структуре Protobuf генерируется поле sizeCache int32?»
**Ответ:** Для оптимизации сериализации. Чтобы записать длину вложенного сообщения, Protobuf должен знать его точный размер в байтах. `sizeCache` кэширует вычисленный размер сообщения, исключая повторный рекурсивный обход дерева полей при записи байт в сокет.
