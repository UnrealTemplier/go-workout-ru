# Четыре типа RPC методов в gRPC: Unary, Server Streaming, Client Streaming и Bidirectional Streaming

## Условие

Определите сервис с потоковыми RPC: client streaming, server streaming, bidirectional streaming. Сгенерируйте код и изучите интерфейсы.

## Теория

Четыре архитектурных шаблона RPC в gRPC:
1. **Unary RPC (Один запрос — один ответ):**
   `rpc GetUser(Req) returns (Resp);`
   Классическая семантика REST запроса.
2. **Server Streaming RPC (Один запрос — поток ответов):**
   `rpc SubscribeLogs(Req) returns (stream LogMsg);`
   Сервер шлет поток сообщений клиенту (SSE, котировки акций).
3. **Client Streaming RPC (Поток запросов — один ответ):**
   `rpc UploadChunks(stream Chunk) returns (Summary);`
   Клиент загружает тяжелый файл частями, в конце получает статус.
4. **Bidirectional Streaming RPC (Полнодуплексный поток):**
   `rpc Chat(stream ChatMsg) returns (stream ChatMsg);`
   Клиент и сервер независимо пишут и читают сообщения в реальном времени.

## Решение по шагам

1. Опишите все 4 типа RPC в сервисе `StreamingHub`.
2. Изучите сгенерированные интерфейсы стримов (`Send`, `Recv`).
3. Продемонстрируйте сигнатуры методов сервера в Go.

## Код решения

**`streaming.proto`**

```protobuf
syntax = "proto3";

package streaming.v1;

option go_package = "./streamingv1;streamingv1";

message Request { string query = 1; }
message Response { string data = 1; }

service StreamingHub {
  // 1. Унарный вызов
  rpc SimpleRPC(Request) returns (Response);

  // 2. Потоковая передача от сервера (Server Streaming)
  rpc ServerStream(Request) returns (stream Response);

  // 3. Потоковая передача от клиента (Client Streaming)
  rpc ClientStream(stream Request) returns (Response);

  // 4. Двунаправленный поток (Bidirectional Streaming)
  rpc BidiStream(stream Request) returns (stream Response);
}
```

ℹ️ Спецификация всех 4 шаблонов RPC взаимодействия

**`stream_interfaces_demo.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
)

type RequestMsg struct{ Query string }
type ResponseMsg struct{ Data string }

// Эмуляция сгенерированных интерфейсов стриминга gRPC
type ServerStreamSender interface {
	Send(*ResponseMsg) error
}

type ClientStreamReceiver interface {
	Recv() (*RequestMsg, error)
	SendAndClose(*ResponseMsg) error
}

type BidiStreamChannel interface {
	Send(*ResponseMsg) error
	Recv() (*RequestMsg, error)
}

type StreamingServiceServer interface {
	SimpleRPC(context.Context, *RequestMsg) (*ResponseMsg, error)
	ServerStream(*RequestMsg, ServerStreamSender) error
	ClientStream(ClientStreamReceiver) error
	BidiStream(BidiStreamChannel) error
}

func main() {
	fmt.Println("Все 4 интерфейса стриминга gRPC успешно спроектированы в Go")
	var _ = io.EOF // Сигнал завершения стрима
}
```

ℹ️ Сигнатуры методов четырех типов RPC взаимодействия в Go

**`Терминал`**

```bash
go run stream_interfaces_demo.go
# Вывод:
# Все 4 интерфейса стриминга gRPC успешно спроектированы в Go
```

## Под капотом

Каждый стрим gRPC отображается на отдельный виртуальный HTTP/2 Stream (идентификатор Stream ID). Фреймы данных `DATA` передаются независимыми чанками с флагом `END_STREAM`, сигнализирующим о завершении передачи стороны.

## Подводные камни

Забывать обрабатывать ошибку `io.EOF` при чтении из `Recv()`: в стримах `io.EOF` — это штатный сигнал о том, что клиент или сервер закончил передачу потока, а не авария сети!

## На собеседовании

**Вопрос с собеседования:** «Почему в gRPC Server Streaming надежнее WebSockets в межсервисном взаимодействии?»
**Ответ:** gRPC стриминг мультиплексируется в рамках существующего HTTP/2 TCP-соединения, строго типизирован через схему Protobuf, поддерживает встроенный Backpressure (управление потоком через HTTP/2 Window Update) и стандартизированную отмену через `context.Context`.
