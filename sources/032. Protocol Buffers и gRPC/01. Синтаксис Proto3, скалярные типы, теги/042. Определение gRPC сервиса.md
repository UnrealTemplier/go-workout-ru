# Определение gRPC сервиса: директива service, rpc методы и анализ сгенерированных интерфейсов

## Условие

**Определение сервиса**: В `.proto` файле добавь `service UserService { rpc GetUser (UserRequest) returns (UserResponse); }`. Сгенерируй код с поддержкой gRPC (`--go-grpc_out=.`). Посмотри на сгенерированные интерфейсы сервера и клиента.

## Теория

Генерация клиентских и серверных контрактов плагином protoc-gen-go-grpc:
- Из определения сервиса компилятор генерирует:
  1. **Клиентский интерфейс:**
     ```go
     type UserServiceClient interface {
         GetUser(ctx context.Context, in *UserRequest, opts ...grpc.CallOption) (*UserResponse, error)
     }
     ```
  2. **Серверный интерфейс:**
     ```go
     type UserServiceServer interface {
         GetUser(context.Context, *UserRequest) (*UserResponse, error)
         mustEmbedUnimplementedUserServiceServer()
     }
     ```
  3. **Конструктор клиента:** `NewUserServiceClient(cc grpc.ClientConnInterface)`.

## Решение по шагам

1. Опишите сервис в `.proto` файле.
2. Сгенерируйте код с флагом `--go-grpc_out`.
3. Изучите сгенерированные сигнатуры методов.
4. Проверьте реализацию интерфейса клиентом и сервером.

## Код решения

**`service_contract.proto`**

```protobuf
syntax = "proto3";

package user.v1;

option go_package = "./userv1;userv1";

message UserRequest { string user_id = 1; }
message UserResponse { string user_id = 1; string name = 2; }

service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
}
```

ℹ️ Спецификация сервиса UserService

**`interface_inspector.go`**

```go
package main

import (
	"context"
	"fmt"

	"google.golang.org/grpc"
)

type UserRequest struct{ UserID string }
type UserResponse struct{ UserID, Name string }

// Сгенерированный клиентский интерфейс
type UserServiceClient interface {
	GetUser(ctx context.Context, in *UserRequest, opts ...grpc.CallOption) (*UserResponse, error)
}

// Сгенерированный серверный интерфейс
type UserServiceServer interface {
	GetUser(context.Context, *UserRequest) (*UserResponse, error)
}

func main() {
	fmt.Println("Интерфейсы UserServiceClient и UserServiceServer успешно сгенерированы")
}
```

ℹ️ Анализ структуры сгенерированных интерфейсов

**`Терминал`**

```bash
protoc --go_out=. --go_opt=paths=source_relative \
       --go-grpc_out=. --go-grpc_opt=paths=source_relative \
       service_contract.proto

# Проверяем интерфейсы в сгенерированном файле:
grep -A 5 "type UserServiceClient interface" service_contract_grpc.pb.go
```

## Под капотом

Интерфейс `UserServiceClient` принимает переменное число `opts ...grpc.CallOption`. Это позволяет на уровне отдельного RPC-вызова переопределять интерцепторы, настраивать сжатие (`grpc.UseCompressor("gzip")`) или передавать метаданные заголовков.

## Подводные камни

Забывать передавать `ctx context.Context` первым аргументом: сигнатуры всех gRPC методов в Go строго начинаются с `ctx`.

## На собеседовании

**Вопрос с собеседования:** «Зачем клиенту gRPC передавать интерфейс grpc.ClientConnInterface, а не конкретную структуру *grpc.ClientConn?»
**Ответ:** Это фундаментальный принцип инверсии зависимостей (Dependency Inversion). Благодаря интерфейсу `grpc.ClientConnInterface` клиентский стаб можно легко покрывать unit-тестами с помощью моков, подставляя In-Memory соединения (`bufconn`) без открытия реальных портов операционной системы.
