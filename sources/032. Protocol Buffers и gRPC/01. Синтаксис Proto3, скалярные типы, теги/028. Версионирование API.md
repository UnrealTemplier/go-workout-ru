# Версионирование API: пакеты package user.v1 и package user.v2, импорт с псевдонимами в Go

## Условие

Создай **proto package с версионированием**: `package user.v1;` и `package user.v2;`. Покажи, как импортировать обе версии в одном Go-проекте (разные import paths). Обсуди стратегию обновления API.

### Исходная формулировка

Создай **proto package с версионированием**: `package user.v1;` и `package user.v2;`. Покажи, как импортировать обе версии в одном Go-проекте (разные import paths). Обсуди стратегию обновления API.

## Теория

Стратегия версионирования Protobuf контрактов в BigTech:
- В крупных компаниях (Google, Яндекс, Uber) API версионируется по мажорным версиям в структуре директорий:
  `proto/user/v1/user.proto` \(\to\) `package user.v1;`
  `proto/user/v2/user.proto` \(\to\) `package user.v2;`
- Правила перехода:
  1. Внутри одной мажорной версии (v1) все изменения строго обратно совместимы (только добавление полей).
  2. Если требуется ломающее изменение (удаление методов, смена сигнатур), создается ветка **v2**.
  3. Сервис запускает оба сервера (v1 и v2) на одном порту, поддерживая старых клиентов до окончания срока депрекации.

## Решение по шагам

1. Создайте схемы версий `v1` и `v2`.
2. В Go импортируйте обе версии с псевдонимами `userv1` и `userv2`.
3. Напишите адаптер конвертации между версиями.
4. Проверьте параллельную работу.

## Код решения

**`dual_version_demo.go`**

```go
package main

import (
	"fmt"
)

// Моделируем структуры пакета userv1
type UserV1DTO struct {
	ID   string
	Name string
}

// Моделируем структуры пакета userv2 (с разделением имени на First/Last)
type UserV2DTO struct {
	ID        string
	FirstName string
	LastName  string
}

// Адаптер для плавной миграции клиентов с V1 на V2
func ConvertV1toV2(v1 *UserV1DTO) *UserV2DTO {
	return &UserV2DTO{
		ID:        v1.ID,
		FirstName: v1.Name,
		LastName:  "", // В V1 фамилия не хранилась отдельно
	}
}

func main() {
	v1Client := &UserV1DTO{ID: "usr_10", Name: "Константин"}
	v2Upgraded := ConvertV1toV2(v1Client)

	fmt.Println("V1 сущность:", v1Client)
	fmt.Printf("V2 адаптированная сущность: ID=%s, FirstName=%s, LastName=%q\n",
		v2Upgraded.ID, v2Upgraded.FirstName, v2Upgraded.LastName)
}
```

ℹ️ Импорт двух версий контракта и адаптер миграции

**`Терминал`**

```bash
go run dual_version_demo.go
# Вывод:
# V1 сущность: &{usr_10 Константин}
# V2 адаптированная сущность: ID=usr_10, FirstName=Константин, LastName=
```

## Под капотом

В gRPC полный путь вызова включает имя пакета: `/user.v1.UserService/GetUser` и `/user.v2.UserService/GetUser`. Поскольку URL путей различаются, один gRPC сервер может одновременно регистрировать и обслуживать обе версии API на одном сокете без конфликтов маршрутизации!

## Подводные камни

Удалять поддержку версии v1 сразу после релиза v2: мобильные приложения пользователей обновляются месяцами. В продакшене старую версию поддерживают минимум 6–12 месяцев с метриками мониторинга остаточного трафика.

## На собеседовании

**Вопрос с собеседования:** «Как на одном порту gRPC обслуживать одновременно версию v1 и v2 одного и того же сервиса?»
**Ответ:** Зарегистрировать обе сгенерированные службы в одном `grpc.Server`:
```go
userv1.RegisterUserServiceServer(grpcServer, &UserV1ServerImpl{})
userv2.RegisterUserServiceServer(grpcServer, &UserV2ServerImpl{})
```
HTTP/2 роутер gRPC мультиплексирует запросы по заголовку `:path`, направляя трафик v1 и v2 в соответствующие обработчики.
