# Логгер потоковых вызовов: комплексный перехватчик потока со счетчиком переданных сообщений

## Условие

**Stream Interceptor**: Напиши логгер для стримовых вызовов (это сложнее, так как требуется обернуть интерфейс `grpc.ServerStream` и переопределить методы `SendMsg` и `RecvMsg`).

## Теория

Комплексный аудит потоковых сессий:
- Полный логгер стримов вычисляет:
  1. Время установления стрима.
  2. Общее число принятых сообщений (`recv_total`).
  3. Общее число отправленных сообщений (`sent_total`).
  4. Общее время существования потока.
  5. Код завершения.
- Вся эта информация выводится единой строкой при выходе из `StreamHandler`.

## Решение по шагам

1. Создайте счетчики сообщений внутри структуры обертки.
2. Инкрементируйте счетчики в `SendMsg` и `RecvMsg`.
3. При завершении стрима выведите суммарный отчет.
4. Проверьте правильность подсчета сообщений.

## Код решения

**`stream_traffic_logger_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/status"
)

type DetailedStreamWrapper struct {
	grpc.ServerStream
	methodName string
	msgsIn     int
	msgsOut    int
}

func (w *DetailedStreamWrapper) RecvMsg(m any) error {
	w.msgsIn++
	return nil
}

func (w *DetailedStreamWrapper) SendMsg(m any) error {
	w.msgsOut++
	return nil
}

func LoggingStreamServerInterceptor(
	srv any,
	ss grpc.ServerStream,
	info *grpc.StreamServerInfo,
	handler grpc.StreamHandler,
) error {
	start := time.Now()
	wrapped := &DetailedStreamWrapper{ServerStream: ss, methodName: info.FullMethod}

	err := handler(srv, wrapped)

	duration := time.Since(start)
	code := status.Code(err)

	fmt.Printf("[STREAM SUMMARY] %s | Duration: %v | In: %d msgs | Out: %d msgs | Status: %s\n",
		info.FullMethod, duration.Round(time.Millisecond), wrapped.msgsIn, wrapped.msgsOut, code)

	return err
}

func TestStreamTrafficLogger(t *testing.T) {
	mockHandler := func(srv any, ss grpc.ServerStream) error {
		_ = ss.RecvMsg("chunk 1")
		_ = ss.RecvMsg("chunk 2")
		_ = ss.SendMsg("ack")
		return nil
	}

	info := &grpc.StreamServerInfo{FullMethod: "/upload.v1.FileService/Upload"}
	err := LoggingStreamServerInterceptor(nil, nil, info, mockHandler)
	if err != nil {
		t.Fatalf("Ошибка: %v", err)
	}
}
```

ℹ️ Суммарный аудит переданных и принятых сообщений в стриме

## Под капотом

Такой интерцептор предоставляет ключевые бизнес-метрики: средний размер сессии стриминга и соотношение входящих/исходящих пакетов.

## Подводные камни

Использовать неатомарные счетчики при параллельном вызове `SendMsg` и `RecvMsg` в двунаправленном стриминге: горутины чтения и записи будут конфликтовать, вызывая Data Race (`go test -race`). Счетчики `msgsIn` и `msgsOut` изолированы по направлениям.

## На собеседовании

**Вопрос с собеседования:** «Почему в Bidirectional Streaming счетчики msgsIn и msgsOut не требуют мьютекса?»
**Ответ:** Потому что инкремент `msgsIn` выполняется строго в горутине чтения `RecvMsg`, а инкремент `msgsOut` — строго в горутине отправки `SendMsg`. Это две независимые переменные, читаемые интерцептором только ПОСЛЕ завершения обеих горутин в `handler`.
