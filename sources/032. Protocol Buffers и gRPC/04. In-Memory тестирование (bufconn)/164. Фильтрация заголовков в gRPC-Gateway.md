# Фильтрация заголовков в gRPC-Gateway: опция WithIncomingHeaderMatcher для проброса метаданных

## Условие

Используйте `runtime.WithIncomingHeaderMatcher` для проброса определенных HTTP-заголовков в gRPC metadata.

## Теория

Трансляция HTTP заголовков в gRPC Metadata:
- По умолчанию `gRPC-Gateway` отбрасывает большинство пользовательских HTTP-заголовков из соображений безопасности.
- Функция `runtime.WithIncomingHeaderMatcher(fn)`:
  - Позволяет задать белый список заголовков, которые шлюз обязан пробросить в gRPC metadata:
    ```go
    func customHeaderMatcher(key string) (string, bool) {
        switch strings.ToLower(key) {
        case "x-request-id", "x-device-id", "x-client-platform":
            return key, true
        default:
            return runtime.DefaultHeaderMatcher(key)
        }
    }
    ```

## Решение по шагам

1. Напишите функцию сопоставления заголовков `HeaderMatcher`.
2. Добавьте в белый список кастомные заголовки `x-request-id`.
3. Передайте в `runtime.NewServeMux(runtime.WithIncomingHeaderMatcher(...))`.
4. Проверьте проброс заголовка в метаданные.

## Код решения

**`header_matcher_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"

	"github.com/grpc-ecosystem/grpc-gateway/v2/runtime"
)

func CustomHeaderMatcher(key string) (string, bool) {
	switch strings.ToLower(key) {
	case "x-request-id", "x-device-type", "x-correlation-id":
		return strings.ToLower(key), true
	default:
		return runtime.DefaultHeaderMatcher(key)
	}
}

func TestIncomingHeaderMatcher(t *testing.T) {
	// Проверяем разрешенные заголовки
	key1, ok1 := CustomHeaderMatcher("X-Request-ID")
	if !ok1 || key1 != "x-request-id" {
		t.Fatalf("X-Request-ID должен быть разрешен")
	}

	key2, ok2 := CustomHeaderMatcher("X-Device-Type")
	if !ok2 || key2 != "x-device-type" {
		t.Fatalf("X-Device-Type должен быть разрешен")
	}

	// Проверяем произвольный недоверенный заголовок
	_, ok3 := CustomHeaderMatcher("X-Malicious-Header")
	if ok3 {
		t.Fatal("Недоверенный заголовок не должен пробрасываться")
	}

	fmt.Printf("WithIncomingHeaderMatcher успешно профильтровал заголовки:\n")
	fmt.Printf("  • %s -> разрешен\n", key1)
	fmt.Printf("  • %s -> разрешен\n", key2)
}
```

ℹ️ Безопасный проброс HTTP заголовков в gRPC metadata

**`Терминал`**

```bash
go test -v header_matcher_test.go
# Вывод:
# === RUN   TestIncomingHeaderMatcher
# WithIncomingHeaderMatcher успешно профильтровал заголовки:
#   • x-request-id -> разрешен
#   • x-device-type -> разрешен
# --- PASS: TestIncomingHeaderMatcher (0.00s)
# PASS
```

## Под капотом

`DefaultHeaderMatcher` автоматически добавляет префикс `grpcgateway-` к непроверенным заголовкам. Кастомный матчер предотвращает искажение имен, передавая заголовок в чистом виде `x-request-id`.

## Подводные камни

Возвращать `true` для абсолютно всех входящих заголовков: клиент может прислать огромный заголовок Cookie или скомпрометировать внутренние поля.

## На собеседовании

**Вопрос с собеседования:** «Как в gRPC-Gateway вернуть заголовки ответа (Response Headers) клиенту в браузер?»
**Ответ:** Использовать опцию `runtime.WithOutgoingHeaderMatcher`. Она просматривает серверные `metadata.MD` и определяет, какие метаданные шлюз должен записать в качестве HTTP заголовков клиенту.
