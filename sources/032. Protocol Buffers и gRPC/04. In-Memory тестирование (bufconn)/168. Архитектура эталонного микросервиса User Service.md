# Архитектура эталонного микросервиса User Service: PostgreSQL, Redis кэш, Outbox и Observability

## Условие

Реализуй **полный микросервис "User Service"**:
- gRPC API: `CreateUser`, `GetUser`, `UpdateUser`, `DeleteUser`, `ListUsers` (streaming)
- PostgreSQL для persistence
- Redis для кеша
- Outbox pattern для событий (`UserCreated`, `UserUpdated`)
- gRPC interceptors: logging, auth, metrics, tracing
- Health checks, graceful shutdown
- Dockerfile, docker-compose

## Теория

Промышленный эталон микросервисной архитектуры Go (Clean Architecture / DDD):
- Слои микросервиса:
  1. `transport/grpc`: серверные хэндлеры и интерцепторы (Tracing, Metrics, Logging, Auth, Recovery).
  2. `domain/user`: чистые бизнес-сущности и интерфейсы репозиториев.
  3. `usecase`: прикладные сценарии (создание пользователя, инвалидация кэша, генерация события Outbox).
  4. `infrastructure`: адаптеры PostgreSQL (`pgxpool`), Redis (`go-redis`), Transactional Outbox реле.
- Паттерн **Transactional Outbox**:
  - В одной ACID транзакции с `INSERT INTO users` выполняется `INSERT INTO outbox_events (event_type, payload)`.
  - Фоновый воркер (Debezium или Go-воркер) вычитывает таблицу outbox и отправляет события в Kafka без риска потери данных (Dual-Write Problem).

## Решение по шагам

1. Спроектируйте доменные интерфейсы сервиса.
2. Реализуйте сценарий `CreateUser` с сохранением в БД и Outbox.
3. Добавьте кэширование в Redis (Cache-Aside).
4. Опишите Dockerfile и docker-compose манифест.

## Код решения

**`domain_user_service.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type UserEntity struct {
	ID    string
	Name  string
	Email string
}

type OutboxEvent struct {
	EventType string
	Payload   string
}

// UserUsecase объединяет БД, Redis и Outbox в единый сценарий
type UserUsecase struct {
	mu     sync.Mutex
	db     map[string]*UserEntity
	cache  map[string]*UserEntity
	outbox []*OutboxEvent
}

func NewUserUsecase() *UserUsecase {
	return &UserUsecase{
		db:    make(map[string]*UserEntity),
		cache: make(map[string]*UserEntity),
	}
}

func (uc *UserUsecase) CreateUser(ctx context.Context, u *UserEntity) error {
	uc.mu.Lock()
	defer uc.mu.Unlock()

	// 1. Сохранение в Postgres (ACID транзакция)
	uc.db[u.ID] = u

	// 2. Transactional Outbox: фиксация события в той же транзакции
	uc.outbox = append(uc.outbox, &OutboxEvent{
		EventType: "UserCreated",
		Payload:   fmt.Sprintf(`{"user_id": %q, "email": %q}`, u.ID, u.Email),
	})

	// 3. Запись в Redis кэш
	uc.cache[u.ID] = u

	fmt.Printf("[Usecase] Пользователь %s успешно сохранен в PostgreSQL + Outbox + Redis!\n", u.ID)
	return nil
}

func (uc *UserUsecase) GetUser(ctx context.Context, id string) (*UserEntity, error) {
	uc.mu.Lock()
	defer uc.mu.Unlock()

	// 1. Попытка прочитать из Redis Cache
	if val, found := uc.cache[id]; found {
		fmt.Printf("[Cache HIT] Пользователь %s получен из Redis\n", id)
		return val, nil
	}

	// 2. Cache MISS -> чтение из PostgreSQL
	val, found := uc.db[id]
	if !found {
		return nil, fmt.Errorf("пользователь не найден")
	}

	// Прогрев кэша
	uc.cache[id] = val
	fmt.Printf("[Cache MISS] Пользователь %s прочитан из PostgreSQL и сохранен в кэш\n", id)
	return val, nil
}

func main() {
	uc := NewUserUsecase()
	_ = uc.CreateUser(context.Background(), &UserEntity{ID: "usr_1", Name: "Иван", Email: "ivan@yandex.ru"})
	_, _ = uc.GetUser(context.Background(), "usr_1")
}
```

**`docker-compose.yml`**

```yaml
version: '3.8'

services:
  user-service:
    build: .
    ports:
      - "50051:50051" # gRPC API
      - "8080:8080"   # HTTP Metrics & Health
    environment:
      - POSTGRES_DSN=postgres://user:pass@postgres:5432/users_db?sslmode=disable
      - REDIS_ADDR=redis:6379
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16-alpine
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=users_db
    ports:
      - "5432:5432"

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
```

## Под капотом

Слой транзакционного Outbox предотвращает потерю сообщений при падении брокера Kafka: события хранятся в надежном журнале WAL PostgreSQL и публикуются гарантированно (At-Least-Once Delivery).

## Подводные камни

Писать в Kafka напрямую из HTTP/gRPC хэндлера после коммита в базу: если сервис упадет между коммитом в БД и отправкой в брокер, сообщение будет потеряно навсегда (Dual-Write Anti-pattern).

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить проблему Cache Stampede при инвалидации кэша популярного пользователя?»
**Ответ:** Использовать паттерн **Singleflight** (`golang.org/x/sync/singleflight`). При одновременном запросе одного и того же отсутствующего в кэше ключа тысячами горутин, `singleflight.Group` объединяет их в один единственный запрос к PostgreSQL, защищая базу данных от перегрузки.
