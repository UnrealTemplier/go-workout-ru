# Асинхронная доставка событий в Notification Service: Kafka/NATS, DLQ и gRPC API подписок

## Условие

Реализуй **"Notification Service"**:
- Подписка на events из Kafka/NATS (Outbox от User/Order сервисов)
- Отправка email/SMS/push (заглушки)
- DLQ для необработанных событий
- gRPC API для управления подписками

## Теория

Архитектура Event-Driven потребителя с Dead Letter Queue (DLQ):
- Сервис уведомлений подписывается на топики Kafka/NATS: `user-events`, `order-events`.
- При получении события `OrderCreated`:
  - Выполняется отправка Push-уведомления или SMS.
  - Если шлюз отправки SMS недоступен после 3 попыток:
    - Сообщение НЕ теряется и не блокирует очередь (No Head-of-Line Blocking).
    - Сообщение отправляется в специальный топик **DLQ (Dead Letter Queue)** `notifications-dlq` для последующего анализа инженерами.
- gRPC API сервиса позволяет пользователям настраивать каналы уведомлений (`email: true, push: false`).

## Решение по шагам

1. Создайте структуру обработчика событий.
2. Реализуйте попытки доставки сообщений с ретраями.
3. При превышении попыток перенаправьте в Dead Letter Queue.
4. Протестируйте изоляцию сбойных событий.

## Код решения

**`dlq_consumer_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

type EventMessage struct {
	ID        string
	Recipient string
	Payload   string
	Attempts  int
}

type NotificationConsumer struct {
	mu  sync.Mutex
	dlq []*EventMessage
}

func (c *NotificationConsumer) ProcessMessage(ctx context.Context, msg *EventMessage) error {
	const maxRetries = 3

	// Симулируем постоянный отказ отправки SMS
	for msg.Attempts < maxRetries {
		msg.Attempts++
		fmt.Printf("  [Попытка #%d] Отправка уведомления для %s не удалась (SMS Provider 503)\n",
			msg.Attempts, msg.Recipient)
	}

	// Попытки исчерпаны -> перемещаем в Dead Letter Queue (DLQ)
	c.mu.Lock()
	c.dlq = append(c.dlq, msg)
	c.mu.Unlock()

	fmt.Printf("[DLQ ROUTED] Событие %s направлено в Dead Letter Queue для расследования!\n", msg.ID)
	return nil
}

func TestDeadLetterQueueRouting(t *testing.T) {
	consumer := &NotificationConsumer{}
	msg := &EventMessage{
		ID:        "evt_order_8819",
		Recipient: "+79991234567",
		Payload:   "Ваш заказ собран и передан курьеру",
	}

	_ = consumer.ProcessMessage(context.Background(), msg)

	consumer.mu.Lock()
	dlqCount := len(consumer.dlq)
	consumer.mu.Unlock()

	if dlqCount != 1 {
		t.Fatalf("Ожидалось 1 сообщение в DLQ, получено: %d", dlqCount)
	}

	fmt.Println("Тест подтвердил: сбойное событие не заблокировало очередь и изолировано в DLQ")
}
```

## Под капотом

В Kafka DLQ реализуется как отдельный топик с тем же форматом сообщений плюс метаданные об ошибке в заголовках (`x-original-topic`, `x-exception-message`), что позволяет SRE-инженерам перезапустить обработку после исправления бага.

## Подводные камни

Подавлять ошибки (ack message) без сохранения в DLQ: сообщения будут бесследно утеряны из очереди.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить отправку дубликатов SMS клиенту при ретраях из Kafka (At-Least-Once delivery)?»
**Ответ:** Реализовать **Idempotent Consumer**: перед отправкой SMS сервис атомарно записывает ключ события `eventId` в Redis (`SET event_id "PROCESSING" NX EX 86400`). Если ключ уже существует в Redis, отправка не выполняется, а сообщение сразу подтверждается (ACK), гарантируя доставку ровно одного SMS.
