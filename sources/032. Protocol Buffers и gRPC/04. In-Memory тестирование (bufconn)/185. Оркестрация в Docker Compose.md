# Оркестрация в Docker Compose: взаимодействие микросервисов users, orders, gateway и healthcheck

## Условие

Соберите несколько сервисов в docker-compose: `users`, `orders`, `gateway`. Настройте их взаимодействие по gRPC с healthcheck и зависимостями.

## Теория

Координация зависимостей сервисов в docker-compose:
- Проблема: Сервис `orders` упадет при старте, если сервис `users` еще не поднял gRPC порт.
- Решение: директива `depends_on` с условием `condition: service_healthy`:
  ```yaml
  orders-service:
    depends_on:
      users-service:
        condition: service_healthy
  ```
- Для проверки gRPC сервиса используется официальная утилита `grpc-health-probe`:
  `test: ["CMD", "/bin/grpc-health-probe", "-addr=:50051"]`.

## Решение по шагам

1. Опишите конфигурацию docker-compose с 3 сервисами.
2. Настройте healthcheck через `grpc-health-probe`.
3. Задайте порядок запуска зависимостей.
4. Проверьте валидность файла конфигурации.

## Код решения

**`docker-compose.microservices.yml`**

```yaml
version: '3.8'

services:
  users-service:
    build:
      context: .
      dockerfile: Dockerfile.user
    environment:
      - GRPC_PORT=50051
    healthcheck:
      test: ["CMD", "/bin/grpc-health-probe", "-addr=:50051"]
      interval: 5s
      timeout: 2s
      retries: 3
    networks:
      - backend-net

  orders-service:
    build:
      context: .
      dockerfile: Dockerfile.order
    environment:
      - GRPC_PORT=50052
      - USERS_SERVICE_ADDR=users-service:50051
    depends_on:
      users-service:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "/bin/grpc-health-probe", "-addr=:50052"]
      interval: 5s
      timeout: 2s
      retries: 3
    networks:
      - backend-net

  api-gateway:
    build:
      context: .
      dockerfile: Dockerfile.gateway
    ports:
      - "8080:8080" # Внешний HTTP REST вход
    environment:
      - USERS_ADDR=users-service:50051
      - ORDERS_ADDR=orders-service:50052
    depends_on:
      orders-service:
        condition: service_healthy
    networks:
      - backend-net

networks:
  backend-net:
    driver: bridge
```

## Под капотом

Утилита `grpc-health-probe` вызывает метод `Check` стандартного сервиса `grpc.health.v1.Health` и возвращает код выхода 0 при `SERVING` и код 1 при `NOT_SERVING`, что идеально понимается Docker и Kubernetes.

## Подводные камни

Использовать простой `depends_on` без `condition: service_healthy`: Docker запустит контейнеры одновременно, и `orders` упадет с ошибкой `connection refused`, так как `users` еще не закончил инициализацию.

## На собеседовании

**Вопрос с собеседования:** «Почему в контейнерах вместо curl для healthcheck gRPC используется специальный бинарник grpc-health-probe?»
**Ответ:** Стандартный `curl` в большинстве минимальных Docker образов (Alpine/Distroless) не собран с поддержкой HTTP/2 и не умеет вызывать RPC методы Protobuf. Утилита `grpc-health-probe` — это самодостаточный статический бинарник на Go размером 8 МБ, специально созданный Google для проверки gRPC сокетов.
