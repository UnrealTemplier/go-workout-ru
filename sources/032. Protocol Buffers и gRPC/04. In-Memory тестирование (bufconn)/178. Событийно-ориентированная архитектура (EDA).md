# Событийно-ориентированная архитектура (EDA): Kafka Event Bus и Schema Registry в CI

## Условие

Реализуй **"Event-driven architecture"**:
- Сервисы не вызывают друг друга напрямую
- Все коммуникации через event bus (Kafka/NATS)
- Event schema registry (Avro/protobuf)
- Backward/forward compatibility проверка в CI

## Теория

Event-Driven Architecture (EDA) без прямых синхронных вызовов:
- Прямые gRPC вызовы связывают сервисы (Tight Coupling): если сервис счетов упал, сервис заказов не может работать.
- Решение EDA:
  - Сервис Заказов публикует событие `OrderCreatedEvent` в топик Kafka и немедленно отвечает клиенту.
  - Сервис Складов и Сервис Счетов асинхронно вычитывают событие независимо друг от друга.
- **Protobuf Schema Registry:**
  - Все схемы событий хранятся в Schema Registry (Confluent / Buf Schema Registry).
  - В CI/CD запускается `buf breaking --against .git#branch=main`: если разработчик удалил поле или изменил тег, компиляция блокируется!

## Решение по шагам

1. Опишите событие в Protobuf формате.
2. Продемонстрируйте асинхронную публикацию события.
3. Продемонстрируйте независимое получение события несколькими потребителями.
4. Проверьте валидацию совместимости контрактов.

## Код решения

**`eda_event_bus_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type EventBus struct {
	mu          sync.RWMutex
	subscribers map[string][]chan string
}

func NewEventBus() *EventBus {
	return &EventBus{subscribers: make(map[string][]chan string)}
}

func (b *EventBus) Subscribe(topic string) <-chan string {
	b.mu.Lock()
	defer b.mu.Unlock()
	ch := make(chan string, 10)
	b.subscribers[topic] = append(b.subscribers[topic], ch)
	return ch
}

func (b *EventBus) Publish(topic, payload string) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for _, ch := range b.subscribers[topic] {
		ch <- payload
	}
}

func TestEventDrivenDecoupling(t *testing.T) {
	bus := NewEventBus()

	// 1. Сервис Склада подписывается на заказы
	warehouseCh := bus.Subscribe("orders.v1")
	// 2. Сервис Аналитики подписывается на те же заказы
	analyticsCh := bus.Subscribe("orders.v1")

	// 3. Сервис Заказов публикует событие в брокер (не зная, кто его слушает!)
	bus.Publish("orders.v1", `{"order_id":"ord_100","item":"MacBook Pro"}`)

	msg1 := <-warehouseCh
	msg2 := <-analyticsCh

	fmt.Println("Событие доставлено всем независимым потребителям через Event Bus:")
	fmt.Printf("  • Склад получил:    %s\n", msg1)
	fmt.Printf("  • Аналитика получила: %s\n", msg2)
}
```

ℹ️ Событийно-ориентированная архитектура с независимыми подписчиками

## Под капотом

Шина событий переводит архитектуру из синхронной модели RPC в асинхронный лог коммитов (Distributed Commit Log), гарантируя доступность системы даже при падении 80% потребителей.

## Подводные камни

Использовать события как команды (Event-Carried State Transfer vs Command): событие должно сообщать о свершившемся факте в прошедшем времени (`OrderCreated`), а не приказывать другому сервису (`ReserveInventory`).

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить поломку потребителей при изменении схемы событий в Kafka?»
**Ответ:** Использовать Protobuf с автоматической проверкой `buf breaking` в CI пайплайне: запрещено менять числовые теги, переименовывать enum-константы и менять типы данных полей. Новые поля добавляются только как опциональные, гарантируя обратную и прямую совместимость.
