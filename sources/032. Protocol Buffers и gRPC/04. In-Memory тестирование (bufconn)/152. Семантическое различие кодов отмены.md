# Семантическое различие кодов отмены: codes.Canceled против codes.DeadlineExceeded

## Условие

Изучите разницу между `codes.Canceled` (клиент отменил) и `codes.DeadlineExceeded` (истек таймаут).

## Теория

Различие причин завершения контекста:
| Код gRPC | Причина возникновения | Контекстная ошибка Go | Действие системы |
| :--- | :--- | :--- | :--- |
| `codes.Canceled` (1) | Пользователь нажал «Отмена» в UI, закрыл вкладку браузера или вызвал `cancel()` | `context.Canceled` | Немедленно остановить вычисления; ретраить НЕЛЬЗЯ |
| `codes.DeadlineExceeded` (4) | Истек жесткий лимит времени выполнения операции (`context.WithTimeout`) | `context.DeadlineExceeded` | Операция длилась дольше ожидаемого SLA; можно залогировать алерт |
- Правильная обработка позволяет различать каприз пользователя и деградацию производительности сервиса.

## Решение по шагам

1. Проверьте различие между `context.Canceled` и `context.DeadlineExceeded`.
2. Сопоставьте их со статус-кодами gRPC.
3. Продемонстрируйте корректный возврат ошибки.
4. Проверьте поведение в тестах.

## Код решения

**`canceled_vs_deadline_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

// TranslateContextError преобразует контекстную ошибку в строгий gRPC статус
func TranslateContextError(err error) error {
	if errors.Is(err, context.Canceled) {
		return status.Error(codes.Canceled, "операция отменена инициатором запроса")
	}
	if errors.Is(err, context.DeadlineExceeded) {
		return status.Error(codes.DeadlineExceeded, "превышен лимит времени ожидания (таймаут)")
	}
	return status.Convert(err).Err()
}

func TestContextErrorsDistinction(t *testing.T) {
	// 1. Сценарий: клиент явно отменил запрос
	ctx1, cancel1 := context.WithCancel(context.Background())
	cancel1()
	err1 := TranslateContextError(ctx1.Err())
	if status.Code(err1) != codes.Canceled {
		t.Fatalf("Ожидался Canceled, получено: %v", err1)
	}
	fmt.Printf("1. Явная отмена клиентом: [%s] %s\n", status.Code(err1), status.Convert(err1).Message())

	// 2. Сценарий: истек таймаут операции
	ctx2, cancel2 := context.WithTimeout(context.Background(), 1*time.Nanosecond)
	defer cancel2()
	time.Sleep(1 * time.Millisecond)
	err2 := TranslateContextError(ctx2.Err())
	if status.Code(err2) != codes.DeadlineExceeded {
		t.Fatalf("Ожидался DeadlineExceeded, получено: %v", err2)
	}
	fmt.Printf("2. Истечение таймаута:     [%s] %s\n", status.Code(err2), status.Convert(err2).Message())
}
```

## Под капотом

При отмене клиентом отправляется HTTP/2 фрейм `RST_STREAM` с кодом ошибки `CANCEL` (0x8). При превышении таймаута серверный таймер срабатывает локально, инициируя завершение со статусом `DeadlineExceeded`.

## Подводные камни

Помечать ошибки `codes.Canceled` как 500 Internal Error в метриках: это создает ложные алерты дежурным инженерам, когда пользователи просто закрывают приложение.

## На собеседовании

**Вопрос с собеседования:** «Почему в распределенных транзакциях критично различать Canceled и DeadlineExceeded?»
**Ответ:** При `Canceled` клиент гарантированно сообщил об отказе, транзакцию можно безопасно откатывать. При `DeadlineExceeded` клиент мог не дождаться ответа из-за задержки сети, но бэкенд мог успешно зафиксировать платеж в БД! Потребуется проверка статуса транзакции перед компенсацией.
