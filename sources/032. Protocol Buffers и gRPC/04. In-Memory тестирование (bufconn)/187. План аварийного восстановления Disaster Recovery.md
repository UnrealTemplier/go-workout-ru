# План аварийного восстановления Disaster Recovery: метрики RPO/RTO и регулярные учения

## Условие

Реализуй **"Disaster Recovery"**:
- RPO (Recovery Point Objective): 5 минут потерь данных допустимо
- RTO (Recovery Time Objective): 15 минут на восстановление
- Backup: PostgreSQL WAL archiving, Redis RDB+AOF
- Restore procedure: документирован, автоматизирован, тестируется регулярно
- Multi-AZ, multi-region failover

## Теория

Метрики непрерывности бизнеса (Disaster Recovery / BCP):
- **RPO (Recovery Point Objective):** максимальный объем данных во времени, который допустимо потерять при катастрофе (например 5 минут).
  - Обеспечивается: непрерывной архивацией WAL в S3 (WAL-G / pgBackRest) каждые 60 секунд.
- **RTO (Recovery Time Objective):** максимальное время, за которое система обязана полностью восстановить работоспособность (например 15 минут).
  - Обеспечивается: автоматизированными скриптами подъема базы и подов в резервном регионе (Cold/Warm Standby).
- Регулярные учения GameDays (Chaos Engineering) проверяют готовность команды к реальным авариям.

## Решение по шагам

1. Создайте модель аудита соответствия RPO и RTO.
2. Проверьте замер времени восстановления базы.
3. Проверьте задержку последней точки репликации.
4. Сформируйте отчет соответствия SLA.

## Код решения

**`disaster_recovery_audit_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DRPolicy struct {
	TargetRPOMinutes int
	TargetRTOMinutes int
}

type DRIrrigationDrillResult struct {
	LastBackupAge   time.Duration
	ActualRestoreTime time.Duration
}

func (p *DRPolicy) Audit(drill *DRIrrigationDrillResult) (bool, string) {
	rpoPassed := drill.LastBackupAge <= time.Duration(p.TargetRPOMinutes)*time.Minute
	rtoPassed := drill.ActualRestoreTime <= time.Duration(p.TargetRTOMinutes)*time.Minute

	if !rpoPassed {
		return false, fmt.Sprintf("Нарушение RPO: потеря данных %v превышает лимит %d мин",
			drill.LastBackupAge, p.TargetRPOMinutes)
	}
	if !rtoPassed {
		return false, fmt.Sprintf("Нарушение RTO: время восстановления %v превышает лимит %d мин",
			drill.ActualRestoreTime, p.TargetRTOMinutes)
	}

	return true, "SLA Disaster Recovery полностью соблюден!"
}

func TestDisasterRecoveryVerification(t *testing.T) {
	policy := &DRPolicy{
		TargetRPOMinutes: 5,  // Не более 5 мин потерь
		TargetRTOMinutes: 15, // Не более 15 мин на подъем
	}

	drill := &DRIrrigationDrillResult{
		LastBackupAge:     2 * time.Minute, // Бэкап был 2 минуты назад (RPO OK)
		ActualRestoreTime: 8 * time.Minute, // Восстановление заняло 8 минут (RTO OK)
	}

	passed, msg := policy.Audit(drill)
	if !passed {
		t.Fatalf("Аудит DR провален: %s", msg)
	}

	fmt.Printf("Аудит Disaster Recovery успешно пройден: %s\n", msg)
	fmt.Printf("  • Фактический RPO: %v (Целевой: <= %d мин)\n", drill.LastBackupAge, policy.TargetRPOMinutes)
	fmt.Printf("  • Фактический RTO: %v (Целевой: <= %d мин)\n", drill.ActualRestoreTime, policy.TargetRTOMinutes)
}
```

## Под капотом

WAL-G выполняет потоковую отправку дельта-сегментов журнала транзакций в объектное хранилище S3/Ceph со сжатием LZ4, гарантируя минимальный RPO без снижения производительности дисков БД.

## Подводные камни

Считать бэкап рабочим, если его ни разу не восстанавливали: до 30% неоттестированных резервных копий в IT индустрии оказываются поврежденными при попытке реального восстановления. Восстановление должно тестироваться автоматически по расписанию.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Point-in-Time Recovery (PITR) от обычного ежедневного дампа базы pg_dump?»
**Ответ:** `pg_dump` делает снимок только раз в сутки (потери данных до 24 часов). `PITR` комбинирует базовый бекап (Base Backup) и непрерывный поток WAL-логов, позволяя восстановить состояние базы данных на любую точную секунду в прошлом (например, ровно на 14:32:15, за секунду до случайного `DROP TABLE`).
