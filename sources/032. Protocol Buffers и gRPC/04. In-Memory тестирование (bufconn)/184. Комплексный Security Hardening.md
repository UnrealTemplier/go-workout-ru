# Комплексный Security Hardening: эшелонированная оборона mTLS, OIDC, RBAC и DDoS защита

## Условие

Реализуй **"Security hardening"**:
- mTLS между всеми сервисами
- OAuth2/OIDC для пользовательской аутентификации
- RBAC: роли (admin, user, guest) в JWT, проверка в interceptor
- Input validation: protobuf constraints (`validate.rules`)
- Rate limiting, DDoS protection
- Security headers, CORS policy

## Теория

Архитектура эшелонированной защиты gRPC сервиса (Defense-in-Depth):
1. **L4 Уровень сети:** шифрование mTLS (только проверенные поды кластера).
2. **L7 Уровень Gateway:** защита от DDoS и лимитирование (Rate Limiter).
3. **Аутентификация (AuthN):** валидация криптографической подписи JWT токенов Identity Provider (Keycloak / Okta).
4. **Авторизация (AuthZ):** проверка ролей в RBAC-интерцепторе (`PermissionDenied`).
5. **Валидация данных:** строгие правила Protobuf constraints (отсечение SQL-инъекций и переполнений).

## Решение по шагам

1. Создайте матрицу эшелонированной защиты.
2. Проверьте валидность входящего токена.
3. Проверьте права доступа роли.
4. Протестируйте отражение неавторизованного запроса.

## Код решения

**`security_hardening_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type SecurityChecklist struct {
	MTLSEnabled     bool
	TokenValid      bool
	Role            string
	RateLimitPassed bool
}

func VerifySecurityPipeline(sec *SecurityChecklist, requiredRole string) error {
	if !sec.MTLSEnabled {
		return status.Error(codes.Unavailable, "mTLS: сертификат клиента не предоставлен")
	}
	if !sec.RateLimitPassed {
		return status.Error(codes.ResourceExhausted, "DDoS Protection: превышен лимит RPS")
	}
	if !sec.TokenValid {
		return status.Error(codes.Unauthenticated, "OIDC: недействительный JWT токен")
	}
	if sec.Role != requiredRole && sec.Role != "admin" {
		return status.Error(codes.PermissionDenied, "RBAC: недостаточно привилегий")
	}
	return nil
}

func TestSecurityHardeningPipeline(t *testing.T) {
	// 1. Атака без валидного mTLS
	err1 := VerifySecurityPipeline(&SecurityChecklist{MTLSEnabled: false}, "admin")
	if status.Code(err1) != codes.Unavailable {
		t.Fatalf("Ожидался сбой mTLS")
	}
	fmt.Printf("1. Уровень сети:    %v\n", err1)

	// 2. Атака с превышением лимита запросов
	err2 := VerifySecurityPipeline(&SecurityChecklist{MTLSEnabled: true, RateLimitPassed: false}, "admin")
	if status.Code(err2) != codes.ResourceExhausted {
		t.Fatalf("Ожидался сбой Rate Limit")
	}
	fmt.Printf("2. Уровень DDoS:    %v\n", err2)

	// 3. Доступ с валидным сертификатом и токеном администратора
	errOK := VerifySecurityPipeline(&SecurityChecklist{
		MTLSEnabled:     true,
		RateLimitPassed: true,
		TokenValid:      true,
		Role:            "admin",
	}, "admin")
	if errOK != nil {
		t.Fatalf("Администратор должен получить доступ: %v", errOK)
	}
	fmt.Println("3. Эшелонированная защита: запрос успешно верифицирован на всех 5 уровнях!")
}
```

## Под капотом

Каждый уровень защиты отсекает определенный класс угроз до того, как запрос дойдет до дорогостоящей бизнес-логики, экономя такты процессора при атаках.

## Подводные камни

Полагаться только на один уровень защиты (например только на JWT): при утечке токена злоумышленник получит полный доступ. mTLS и ограничение по IP предотвращают использование украденного токена извне.

## На собеседовании

**Вопрос с собеседования:** «Что такое принцип Zero Trust в контексте gRPC микросервисов?»
**Ответ:** Принцип «Никому не доверяй, всегда проверяй». Внутри периметра корпоративной сети ни один микросервис не считается доверенным по умолчанию. Каждый gRPC вызов между подами шифруется mTLS, проверяется на наличие валидного токена доступа и авторизуется по минимально достаточным правам (Least Privilege).
