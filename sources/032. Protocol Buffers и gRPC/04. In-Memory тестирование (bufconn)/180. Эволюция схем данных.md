# Эволюция схем данных: обратная и прямая совместимость версий Protobuf (v1, v2, v3)

## Условие

Реализуй **"Schema Evolution"**:
- v1: `User { id, name }`
- v2: `User { id, name, email }` (новое обязательное поле?)
- v3: `User { id, name, email, phone }` (optional)
- Покажи backward compatibility: v2 клиент читает v3 сервер (unknown fields ignored)
- Forward compatibility: v3 клиент читает v2 сервер (default values)

## Теория

Законы эволюции контрактов Protocol Buffers:
1. **Никогда не менять числовые теги** существующих полей!
2. **Backward Compatibility (Обратная совместимость):** старый клиент (v1) читает ответ от нового сервера (v3). Новые неизвестные поля (`email`, `phone`) сохраняются в `UnknownFields` и не вызывают ошибку парсинга.
3. **Forward Compatibility (Прямая совместимость):** новый клиент (v3) читает ответ от старого сервера (v1). Отсутствующие поля автоматически получают дефолтные нулевые значения Go (`""` для строк, `0` для чисел).

## Решение по шагам

1. Создайте модель сообщения v1 с тегами 1 и 2.
2. Создайте модель сообщения v2 с тегами 1, 2 и 3.
3. Продемонстрируйте чтение новых данных старым кодом.
4. Продемонстрируйте чтение старых данных новым кодом с дефолтными значениями.

## Код решения

**`schema_evolution_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// UserV1 представляет структуру клиента версии 1
type UserV1 struct {
	ID   string
	Name string
}

// UserV3 представляет структуру сервера версии 3
type UserV3 struct {
	ID    string
	Name  string
	Email string
	Phone string
}

// SimulateV2ClientReadsV3Server демонстрирует обратную совместимость
func SimulateV2ClientReadsV3Server(v3 *UserV3) *UserV1 {
	// Неизвестные поля (Email, Phone) просто игнорируются клиентом v1
	return &UserV1{
		ID:   v3.ID,
		Name: v3.Name,
	}
}

// SimulateV3ClientReadsV1Server демонстрирует прямую совместимость
func SimulateV3ClientReadsV1Server(v1 *UserV1) *UserV3 {
	// Отсутствующие поля автоматически заполняются дефолтными значениями ("")
	return &UserV3{
		ID:    v1.ID,
		Name:  v1.Name,
		Email: "", // default value
		Phone: "", // default value
	}
}

func TestSchemaEvolutionCompatibility(t *testing.T) {
	// 1. Обратная совместимость: V1 клиент читает данные V3 сервера
	serverV3 := &UserV3{ID: "usr_10", Name: "Илья", Email: "ilya@corp.ru", Phone: "+79991112233"}
	clientV1 := SimulateV2ClientReadsV3Server(serverV3)

	if clientV1.ID != "usr_10" || clientV1.Name != "Илья" {
		t.Fatalf("Ошибка обратной совместимости")
	}
	fmt.Printf("1. Обратная совместимость подтверждена: старый клиент прочитал v3 (новые поля пропущены): %+v\n", clientV1)

	// 2. Прямая совместимость: V3 клиент читает данные старого V1 сервера
	serverV1 := &UserV1{ID: "usr_20", Name: "Анна"}
	clientV3 := SimulateV3ClientReadsV1Server(serverV1)

	if clientV3.Email != "" || clientV3.Phone != "" {
		t.Fatalf("Дефолтные значения должны быть пустыми строками")
	}
	fmt.Printf("2. Прямая совместимость подтверждена: новый клиент прочитал v1 (дефолтные поля): %+v\n", clientV3)
}
```

## Под капотом

В бинарном формате Protobuf wire format каждое поле кодируется как `(field_number << 3) | wire_type`. Парсер всегда знает длину поля и может пропустить неизвестный тег байт без падения.

## Подводные камни

Удалить поле и затем создать новое поле с тем же самым номером тега: старые клиенты перепутают типы данных и упадут с ошибкой десериализации. Удаленные теги резервируют через `reserved 3;`!

## На собеседовании

**Вопрос с собеседования:** «Зачем в Protobuf ключевое слово reserved?»
**Ответ:** Ключевое слово `reserved 2, 7, 9 to 11; reserved "foo", "bar";` гарантирует, что ни один разработчик случайно не переиспользует удаленный тег или имя поля в будущих версиях схемы, предотвращая критические ошибки повреждения данных при десериализации.
