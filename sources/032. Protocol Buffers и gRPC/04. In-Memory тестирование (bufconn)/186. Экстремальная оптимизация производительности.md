# Экстремальная оптимизация производительности: Zero-Allocation, sync.Pool и устранение аллокаций памяти

## Условие

Реализуй **"Performance optimization"**:
- Профилирование: CPU profile → найди hotspot
- Memory profile → найди аллокации
- goroutine profile → найди утечки
- Оптимизация: pooling, zero-allocation, batching
- Повтори benchmark, документируй improvement

## Теория

Техники экстремальной оптимизации в HighLoad Go (100 000+ RPS):
1. **sync.Pool для буферов:** повторное использование срезов байт `[]byte` и структур запросов снижает нагрузку на Garbage Collector (GC) практически до 0%.
2. **Zero-Allocation сериализация:** исключение промежуточных конвертаций `string([]byte)` и обратно.
3. **Батчинг вызовов:** объединение 100 одиночных сетевых вызовов в один пакетный RPC `GetUsersBatch(ids []string)` сокращает сетевой оверхед в десятки раз.

## Решение по шагам

1. Создайте пул буферов `sync.Pool`.
2. Напишите функцию с использованием пула.
3. Сравните аллокации памяти с наивной реализацией.
4. Зафиксируйте ускорение в бенчмарке.

## Код решения

**`performance_pool_bench_test.go`**

```go
package main

import (
	"bytes"
	"sync"
	"testing"
)

var bufferPool = sync.Pool{
	New: func() any {
		return new(bytes.Buffer)
	},
}

func NaiveSerialize(data string) []byte {
	// Каждая операция создает новый буфер в куче (аллокация!)
	var buf bytes.Buffer
	buf.WriteString("PREFIX:")
	buf.WriteString(data)
	buf.WriteString(":SUFFIX")
	return buf.Bytes()
}

func PooledSerialize(data string) []byte {
	// Берем буфер из пула без аллокаций памяти
	buf := bufferPool.Get().(*bytes.Buffer)
	buf.Reset()
	defer bufferPool.Put(buf)

	buf.WriteString("PREFIX:")
	buf.WriteString(data)
	buf.WriteString(":SUFFIX")

	out := make([]byte, buf.Len())
	copy(out, buf.Bytes())
	return out
}

func BenchmarkNaive(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = NaiveSerialize("UserDataPayload")
	}
}

func BenchmarkPooled(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_ = PooledSerialize("UserDataPayload")
	}
}
```

ℹ️ Сравнение производительности с использованием sync.Pool

**`Терминал`**

## Под капотом

`sync.Pool` связывается с локальным пулом процессора P в GMP планировщике, позволяя горутинам извлекать буферы lock-free без конкуренции за мьютексы.

## Подводные камни

Помещать в `sync.Pool` слишком большие буферы, раздутые единичным гигантским запросом: буфер останется в памяти навсегда. Сбрасывайте буферы размером больше 64 КБ вместо возврата в пул.

## На собеседовании

**Вопрос с собеседования:** «Когда сборщик мусора Go очищает объекты в sync.Pool?»
**Ответ:** Во время каждой фазы Garbage Collection (GC). Начиная с Go 1.13, очистка пула происходит мягко: объекты живут минимум два полных цикла сборщика мусора перед удалением, предотвращая резкий провал производительности после завершения GC.
