# Управление готовностью сервиса в Kubernetes: gRPC Health Check v1 и переключение SERVING

## Условие

**Health Check**: В микросервисной архитектуре балансировщики нагрузки (Kubernetes, Envoy) должны знать, жив ли сервис. Установи пакет `google.golang.org/grpc/health`, зарегистрируй стандартный сервис `health.v1` и научись менять статус своего сервиса с `SERVING` на `NOT_SERVING`.

## Теория

Стандартный протокол Health Checking Protocol (grpc.health.v1):
- Kubernetes поддерживает нативные gRPC Liveness и Readiness пробы:
  ```yaml
  readinessProbe:
    grpc:
      port: 50051
      service: "order.v1.OrderService"
  ```
- Сервер регистрирует:
  `healthServer := health.NewServer()`
  `healthpb.RegisterHealthServer(grpcServer, healthServer)`
- Управление статусом:
  - При старте и готовности БД: `healthServer.SetServingStatus("", healthpb.HealthCheckResponse_SERVING)`.
  - При перегрузке или потере БД: `healthServer.SetServingStatus("", healthpb.HealthCheckResponse_NOT_SERVING)`.

## Решение по шагам

1. Создайте экземпляр `health.NewServer()`.
2. Зарегистрируйте на gRPC сервере.
3. Переведите сервис в статус `SERVING`.
4. Продемонстрируйте перевод в `NOT_SERVING` при деградации базы данных.

## Код решения

**`health_check_manager_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"

	"google.golang.org/grpc/health"
	healthpb "google.golang.org/grpc/health/grpc_health_v1"
)

func TestHealthCheckTransitions(t *testing.T) {
	healthServer := health.NewServer()
	serviceName := "user.v1.UserService"

	// 1. Инициализация: сервис готов к приему трафика
	healthServer.SetServingStatus(serviceName, healthpb.HealthCheckResponse_SERVING)

	resp1, err := healthServer.Check(context.Background(), &healthpb.HealthCheckRequest{Service: serviceName})
	if err != nil || resp1.Status != healthpb.HealthCheckResponse_SERVING {
		t.Fatalf("Ожидался статус SERVING, получено: %v", resp1)
	}
	fmt.Printf("1. Статус сервиса: %s (Kube-proxy направляет трафик)\n", resp1.Status)

	// 2. Имитация сбоя: отвалился пул соединений PostgreSQL -> уводим под из балансировки
	healthServer.SetServingStatus(serviceName, healthpb.HealthCheckResponse_NOT_SERVING)

	resp2, err := healthServer.Check(context.Background(), &healthpb.HealthCheckRequest{Service: serviceName})
	if err != nil || resp2.Status != healthpb.HealthCheckResponse_NOT_SERVING {
		t.Fatalf("Ожидался статус NOT_SERVING, получено: %v", resp2)
	}
	fmt.Printf("2. Статус сервиса: %s (Kubernetes временно снимает трафик с пода)\n", resp2.Status)
}
```

ℹ️ Управление статусами здоровья пода в протоколе grpc.health.v1

**`Терминал`**

```bash
go test -v health_check_manager_test.go
# Вывод:

# 1. Статус сервиса: SERVING (Kube-proxy направляет трафик)
# 2. Статус сервиса: NOT_SERVING (Kubernetes временно снимает трафик с пода)
# --- PASS: TestHealthCheckTransitions (0.00s)
# PASS
```

## Под капотом

Сервис `healthServer` также реализует потоковый метод `Watch(req, stream)`. Балансировщики Envoy подписываются на стрим и мгновенно реагируют на смену статуса без периодического опрашивания.

## Подводные камни

Указывать имя сервиса `""` (пустая строка) в Check-запросе, если проверяется конкретный сервис: пустая строка проверяет статус всего сервера целиком, игнорируя локальные сбои отдельных подмодулей.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Liveness Probe от Readiness Probe для gRPC в Kubernetes?»
**Ответ:** `Readiness Probe` проверяет, готов ли сервис принимать входящие запросы (подключился ли к БД, прогрелся ли кэш). При статусе `NOT_SERVING` под просто исключается из списка балансировки. `Liveness Probe` проверяет, не завис ли процесс в дедлоке. При сбое Liveness кубернетес принудительно убивает (`SIGKILL`) и перезапускает контейнер.
