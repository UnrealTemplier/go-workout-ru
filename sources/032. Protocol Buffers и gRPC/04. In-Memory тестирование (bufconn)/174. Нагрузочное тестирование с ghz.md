# Нагрузочное тестирование с ghz: профилирование задержек p50/p95/p99 и анализ узких мест pprof

## Условие

Реализуй **"Load Test"**:
- `ghz` или `k6` для gRPC/HTTP нагрузки
- 1000 RPS на User Service
- Измерь latency p50/p95/p99
- Найди bottleneck через pprof
- Оптимизируй и повтори

## Теория

Инженерия нагрузочного тестирования gRPC:
- Инструмент **`ghz`** — промышленный стандарт нагрузочного тестирования gRPC на Go.
- Запуск нагрузки 1000 RPS на 10 000 запросов:
  `ghz --insecure --proto=user.proto --call=user.v1.UserService.GetUser -d '{"id":"usr_1"}' -c 50 -q 1000 -n 10000 localhost:50051`
- Анализ метрик SLA:
  - \(P50\) (медиана): типичное время ответа.
  - \(P95\): граница медленных запросов.
  - \(P99\): критический хвост латентности (Tail Latency).
- Профилирование узких мест: `go tool pprof http://localhost:6060/debug/pprof/profile`.

## Решение по шагам

1. Смоделируйте сбор и вычисление процентилей \(P50\), \(P95\), \(P99\).
2. Отсортируйте задержки вызовов.
3. Продемонстрируйте вычисление показателей латентности.
4. Оцените отчет нагрузочного тестирования.

## Код решения

**`ghz_metrics_parser_test.go`**

```go
package main

import (
	"fmt"
	"sort"
	"testing"
	"time"
)

type LatencyReport struct {
	P50 time.Duration
	P95 time.Duration
	P99 time.Duration
	RPS float64
}

func CalculatePercentiles(samples []time.Duration) LatencyReport {
	sort.Slice(samples, func(i, j int) bool { return samples[i] < samples[j] })
	n := len(samples)

	return LatencyReport{
		P50: samples[int(float64(n)*0.50)],
		P95: samples[int(float64(n)*0.95)],
		P99: samples[int(float64(n)*0.99)],
		RPS: 1000.0,
	}
}

func TestPercentilesReport(t *testing.T) {
	// Имитация 1000 замеров от ghz
	var samples []time.Duration
	for i := 1; i <= 1000; i++ {
		// Большинство запросов 1-3 мс, редкие выбросы до 25 мс
		if i > 980 {
			samples = append(samples, time.Duration(15+i%10)*time.Millisecond)
		} else {
			samples = append(samples, time.Duration(1+i%3)*time.Millisecond)
		}
	}

	report := CalculatePercentiles(samples)

	fmt.Println("Результаты нагрузочного тестирования gRPC сервиса (ghz 1000 RPS):")
	fmt.Printf("  • Latency P50 (Медиана): %v\n", report.P50)
	fmt.Printf("  • Latency P95:          %v\n", report.P95)
	fmt.Printf("  • Latency P99 (Хвост):   %v\n", report.P99)

	if report.P50 > 5*time.Millisecond {
		t.Fatal("Слишком высокая медианная задержка")
	}
}
```

## Под капотом

Высокий \(P99\) чаще всего вызван паузами сборщика мусора Go (GC Stop-The-World STW mark termination) или блокировками пула соединений БД. Профиль `pprof/mutex` выявляет конкуренцию за мьютексы.

## Подводные камни

Запускать нагрузочный генератор `ghz` на той же машине, где крутится сервис: генератор заберет 50% CPU, исказив замеры. Генератор запускают с отдельного тестового сервера.

## На собеседовании

**Вопрос с собеседования:** «Что такое Coordinated Omission в нагрузочном тестировании и как ghz с ним справляется?»
**Ответ:** Это искажение измерений, когда генератор нагрузки ждет ответа на предыдущий запрос перед отправкой следующего. Если сервис замирает на 2 секунды, генератор тоже простаивает и не фиксирует запросы, которые должны были упасть по таймауту. Флаг `--async` или генератор `k6/vegeta` шлют запросы строго по расписанию независимо от задержек сервера.
