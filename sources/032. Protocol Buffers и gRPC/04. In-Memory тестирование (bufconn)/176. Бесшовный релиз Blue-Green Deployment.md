# Бесшовный релиз Blue-Green Deployment: мгновенное переключение трафика 100% Blue в Green

## Условие

Реализуй **"Blue-Green Deployment"**:
- 2 версии сервиса (blue=v1, green=v2)
- Ingress переключает трафик 100% blue → 100% green
- Без downtime, с rollback возможностью
- Проверь через integration tests на green перед переключением

## Теория

Стратегия Blue-Green развертывания без простоя (Zero-Downtime Releases):
- В кластере одновременно развернуты два независимых окружения:
  - **Blue (v1):** текущая стабильная версия, принимающая 100% боевого трафика.
  - **Green (v2):** новая версия, задеплоенная рядом, принимающая 0% пользовательского трафика.
- Этапы:
  1. На Green-окружении прогоняются интеграционные смоук-тесты.
  2. Балансировщик (Ingress / Service selector) переключает селектор подов с `version: blue` на `version: green`.
  3. Новые запросы gRPC мгновенно идут на Green.
  4. При обнаружении аномалий откат (Rollback) на Blue выполняется за 1 секунду переключением селектора.

## Решение по шагам

1. Смоделируйте селектор маршрутизации трафика.
2. Проверьте отправку запросов на Blue.
3. Проведите смоук-тест на версии Green.
4. Переключите селектор на Green и проверьте перенаправление.

## Код решения

**`blue_green_router_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

type ServiceDeployment struct {
	Version string
}

func (s *ServiceDeployment) Handle(ctx context.Context, msg string) string {
	return fmt.Sprintf("[%s] Обработано: %s", s.Version, msg)
}

type IngressTrafficSwitch struct {
	mu            sync.RWMutex
	activeCluster *ServiceDeployment
}

func (sw *IngressTrafficSwitch) Route(ctx context.Context, msg string) string {
	sw.mu.RLock()
	defer sw.mu.RUnlock()
	return sw.activeCluster.Handle(ctx, msg)
}

func (sw *IngressTrafficSwitch) SwitchTraffic(target *ServiceDeployment) {
	sw.mu.Lock()
	defer sw.mu.Unlock()
	sw.activeCluster = target
}

func TestBlueGreenDeploymentFlow(t *testing.T) {
	blueV1 := &ServiceDeployment{Version: "v1.0.0-BLUE"}
	greenV2 := &ServiceDeployment{Version: "v2.0.0-GREEN"}

	router := &IngressTrafficSwitch{activeCluster: blueV1}

	// 1. Текущий боевой трафик идет на Blue
	res1 := router.Route(context.Background(), "Запрос #1")
	fmt.Println("Боевой трафик:", res1)
	if res1 != "[v1.0.0-BLUE] Обработано: Запрос #1" {
		t.Fatalf("Некорректный роутинг на Blue")
	}

	// 2. Дымовое тестирование на Green окружении ДО переключения
	smokeTest := greenV2.Handle(context.Background(), "SmokeTest")
	fmt.Println("Интеграционный тест на Green:", smokeTest)

	// 3. Мгновенное переключение 100% трафика на Green
	router.SwitchTraffic(greenV2)
	fmt.Println(">>> Ingress переключил селектор: 100% трафика направлено на GREEN!")

	// 4. Все новые вызовы идут на Green
	res2 := router.Route(context.Background(), "Запрос #2")
	fmt.Println("Боевой трафик:", res2)
	if res2 != "[v2.0.0-GREEN] Обработано: Запрос #2" {
		t.Fatalf("Некорректный роутинг на Green")
	}
}
```

ℹ️ Мгновенное переключение трафика в Blue-Green стратегии развертывания

## Под капотом

В Kubernetes Blue-Green реализуется изменением селектора в манифесте Service: `kubectl patch service app-service -p '{"spec":{"selector":{"version":"green"}}}'`. Kube-proxy перенаправляет iptables за доли секунды.

## Подводные камни

Вносить обратно-несовместимые изменения в схему БД (например удаление колонки): Blue версия мгновенно упадет при миграции Green. Используйте паттерн Expand and Contract (двухфазные миграции).

## На собеседовании

**Вопрос с собеседования:** «Что делать с долгоживущими gRPC стримами при переключении с Blue на Green?»
**Ответ:** Вызвать на старых Blue подах `GracefulStop()`. Сервер отправит стримам фрейм `GOAWAY`. Клиенты gRPC автоматически откроют новые соединения, которые Ingress направит уже на Green поды, завершая миграцию без потери сообщений.
