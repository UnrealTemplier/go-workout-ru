# Геораспределенная отказоустойчивость: концепция Multi-Region Active-Active и Disaster Failover

## Условие

Реализуй **"Multi-region deployment"** (концептуально):
- Active-Active: 2 региона, каждый обрабатывает свой shard пользователей
- Global load balancer (GeoDNS) маршрутизирует
- Replication PostgreSQL (read replicas), Redis Cluster
- Failover: при падении региона — traffic shift в другой

## Теория

Архитектура Multi-Region Active-Active:
- Развертывание в двух географически удаленных датацентрах (например DC-Москва и DC-СПб).
- Маршрутизация трафика:
  - **GeoDNS / Anycast BGP:** направляет пользователя в ближайший регион (минимальный RTT).
  - Шардирование пользователей: пользователи европейской части обслуживаются в DC-1, восточной — в DC-2.
- Базы данных:
  - PostgreSQL асинхронная потоковая репликация между регионами.
  - Redis активная репликация.
- Сценарий **Disaster Failover:**
  - При отключении питания в DC-1 GeoDNS снимает трафик и перенаправляет 100% запросов в DC-2 за считанные секунды.

## Решение по шагам

1. Создайте модель двух регионов.
2. Реализуйте GeoDNS роутер с проверкой здоровья региона.
3. Смоделируйте аварию в регионе 1.
4. Проверьте автоматическое переключение трафика (Traffic Shift).

## Код решения

**`multi_region_failover_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DataCenter struct {
	Name    string
	IsAlive bool
}

type GeoDNSRouter struct {
	RegionMSK *DataCenter
	RegionSPB *DataCenter
}

func (r *GeoDNSRouter) RouteUser(userHomeRegion string) string {
	// 1. Попытка направить в домашний регион
	if userHomeRegion == "MSK" && r.RegionMSK.IsAlive {
		return r.RegionMSK.Name
	}
	if userHomeRegion == "SPB" && r.RegionSPB.IsAlive {
		return r.RegionSPB.Name
	}

	// 2. Disaster Failover: если домашний регион упал, перенаправляем в резервный
	if r.RegionMSK.IsAlive {
		fmt.Printf("  [ALERT] Failover: пользователь из SPB перенаправлен в %s\n", r.RegionMSK.Name)
		return r.RegionMSK.Name
	}
	if r.RegionSPB.IsAlive {
		fmt.Printf("  [ALERT] Failover: пользователь из MSK перенаправлен в %s\n", r.RegionSPB.Name)
		return r.RegionSPB.Name
	}

	return "OUTAGE: Все датацентры недоступны"
}

func TestMultiRegionFailover(t *testing.T) {
	router := &GeoDNSRouter{
		RegionMSK: &DataCenter{Name: "DC-Moscow-Primary", IsAlive: true},
		RegionSPB: &DataCenter{Name: "DC-SPb-Secondary", IsAlive: true},
	}

	// Нормальная работа: оба региона живы
	dest1 := router.RouteUser("MSK")
	if dest1 != "DC-Moscow-Primary" {
		t.Fatalf("Некорректный роутинг в MSK")
	}
	fmt.Printf("Штатный режим: запрос направлен в %s\n", dest1)

	// АВАРИЯ: Отказ питания датацентра Москва!
	router.RegionMSK.IsAlive = false
	fmt.Println("\n[КАТАСТРОФА] Потеря питания в датацентре DC-Moscow!")

	// Failover переключает московских пользователей в СПБ
	dest2 := router.RouteUser("MSK")
	if dest2 != "DC-SPb-Secondary" {
		t.Fatalf("Failover не сработал!")
	}
	fmt.Printf("Аварийный режим: запрос успешно обработан резервным %s\n", dest2)
}
```

## Под капотом

Сетевые протоколы BGP Anycast анонсируют один и тот же IP-адрес из нескольких географических точек планеты. Маршрутизаторы провайдеров автоматически направляют пакеты по кратчайшему пути.

## Подводные камни

Проблема Split-Brain: при разрыве межрегионального оптического канала оба региона могут посчитать соседа мертвым и начать независимую запись в БД, порождая конфликты версий. Используют кворумный консенсус Raft (CockroachDB, YDB).

## На собеседовании

**Вопрос с собеседования:** «Почему в Multi-Region Active-Active базах данных сложно использовать синхронную репликацию?»
**Ответ:** Скорость света в оптоволокне накладывает физический предел: задержка между Москвой и Владивостоком составляет около 100 мс RTT. Синхронная транзакция 2PC увеличит время каждого `INSERT/UPDATE` до сотен миллисекунд, поэтому используют асинхронную репликацию с согласованностью в конечном счете (Eventual Consistency).
