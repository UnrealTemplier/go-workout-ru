# Ограничения gRPC-Gateway: особенности стриминга и архитектура WebSocket/SSE

## Условие

Изучите ограничения gRPC-Gateway: streaming RPC не поддерживаются (используйте WebSocket или SSE для них).

## Теория

Архитектурные ограничения gRPC-Gateway в потоковых RPC:
- Обычный REST HTTP/1.1 не рассчитан на дуплексный обмен сообщениями:
  - **Server Streaming:** поддерживается через Chunked Transfer-Encoding, но браузерный `fetch()` плохо справляется с частичным парсингом JSON чанков.
  - **Client Streaming / Bidirectional Streaming:** в HTTP/1.1 не поддерживаются в принципе!
- Архитектурные альтернативы для веб-клиентов:
  1. **Server-Sent Events (SSE):** однонаправленный push от сервера в браузер (`EventSource`).
  2. **WebSocket (WS):** полнодуплексный двунаправленный поток (библиотека `grpc-websocket-proxy`).
  3. **gRPC-Web:** официальный протокол Google для работы с gRPC напрямую из браузера через Envoy прокси.

## Решение по шагам

1. Изучите ограничения трансляции стримов.
2. Продемонстрируйте модель SSE (Server-Sent Events).
3. Сравните протоколы gRPC-Web и WebSocket.
4. Выберите подходящую архитектуру для фронтенда.

## Код решения

**`streaming_alternatives_demo.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"testing"
)

// ServerSentEventsHandler демонстрирует отдачу потоковых данных браузеру через SSE
func ServerSentEventsHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")

	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Стриминг не поддерживается", http.StatusInternalServerError)
		return
	}

	messages := []string{"Пакет #1", "Пакет #2", "Пакет #3"}
	for _, msg := range messages {
		_, _ = fmt.Fprintf(w, "data: %s\n\n", msg)
		flusher.Flush() // Немедленная отправка чанка в сеть
	}
}

func TestSSEStreaming(t *testing.T) {
	rec := httptest.NewRecorder()
	req := httptest.NewRequest("GET", "/events", nil)

	ServerSentEventsHandler(rec, req)

	if rec.Header().Get("Content-Type") != "text/event-stream" {
		t.Fatal("Неверный Content-Type для SSE")
	}

	expected := "data: Пакет #1\n\ndata: Пакет #2\n\ndata: Пакет #3\n\n"
	if rec.Body.String() != expected {
		t.Fatalf("got %q; want %q", rec.Body.String(), expected)
	}

	fmt.Println("Server-Sent Events успешно сымитирован как замена Server Streaming для Web!")
}
```

## Под капотом

`http.Flusher` сбрасывает данные в сокет ОС немедленно, не дожидаясь наполнения внутреннего буфера размером 4 КБ.

## Подводные камни

Использовать NGINX перед SSE стримингом без директивы `proxy_buffering off;`: NGINX будет накапливать ответы в буфере, и пользователь увидит все события разом только после закрытия стрима!

## На собеседовании

**Вопрос с собеседования:** «Что такое gRPC-Web и почему браузеры не могут работать с нативным gRPC напрямую?»
**Ответ:** Браузерный JavaScript API (`fetch` и `XMLHttpRequest`) не предоставляет программисту прямого контроля над HTTP/2 фреймами (нельзя прочитать HTTP/2 trailers, в которых передается статус ошибки `grpc-status`). Протокол `gRPC-Web` кодирует trailers в тело ответа со специальным бинарным префиксом, а Envoy прокси транслирует gRPC-Web в нативный gRPC.
