# Распределенные транзакции: паттерн Saga в Order Service и компенсационные действия

## Условие

Реализуй **"Order Service"**, зависящий от User Service:
- gRPC вызов `user.GetUser` при создании заказа
- Circuit breaker + retry + timeout для вызова User Service
- Saga: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`
- Компенсация при ошибке
- Distributed tracing: trace проходит через Order → User → Payment

## Теория

Паттерн Saga в микросервисной архитектуре (Saga Orchestrator):
- В распределенной архитектуре распределенные транзакции (2PC / XA) запрещены из-за блокировок.
- Сага представляет собой последовательность локальных транзакций:
  1. Шаг 1: `CreateOrder` (Order Service)
  2. Шаг 2: `ReserveInventory` (Warehouse Service)
  3. Шаг 3: `ProcessPayment` (Billing Service)
- Если на Шаге 3 списания денег произошел сбой (недостаточно средств):
  - Оркестратор вызывает **компенсирующие транзакции** в обратном порядке:
    - `ReleaseInventory` (Снять бронь склада)
    - `CancelOrder` (Перевести заказ в статус CANCELED).

## Решение по шагам

1. Создайте автомат шагов оркестрации Saga.
2. Реализуйте выполнение прямого шага и регистрацию компенсации.
3. Смоделируйте ошибку платежа на 3 шаге.
4. Убедитесь в автоматическом откате резерва склада (Compensating Transaction).

## Код решения

**`saga_orchestrator_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type SagaStep struct {
	Name       string
	Execute    func(context.Context) error
	Compensate func(context.Context) error
}

type OrderSagaOrchestrator struct {
	steps []SagaStep
}

func (s *OrderSagaOrchestrator) AddStep(step SagaStep) {
	s.steps = append(s.steps, step)
}

func (s *OrderSagaOrchestrator) Run(ctx context.Context) error {
	var executedSteps []SagaStep

	for _, step := range s.steps {
		fmt.Printf("  [Saga Exec] Выполняем шаг: %s\n", step.Name)
		err := step.Execute(ctx)
		if err != nil {
			fmt.Printf("  [Saga ERROR] Сбой на шаге %s: %v. Запуск компенсации...\n", step.Name, err)
			s.rollback(ctx, executedSteps)
			return err
		}
		executedSteps = append(executedSteps, step)
	}

	fmt.Println("  [Saga SUCCESS] Все шаги успешно зафиксированы!")
	return nil
}

func (s *OrderSagaOrchestrator) rollback(ctx context.Context, executed []SagaStep) {
	// Компенсации вызываются в ОБРАТНОМ порядке (LIFO)
	for i := len(executed) - 1; i >= 0; i-- {
		step := executed[i]
		if step.Compensate != nil {
			fmt.Printf("  [Saga Rollback] Компенсируем шаг: %s\n", step.Name)
			_ = step.Compensate(ctx)
		}
	}
}

func TestSagaExecutionWithRollback(t *testing.T) {
	saga := &OrderSagaOrchestrator{}

	saga.AddStep(SagaStep{
		Name: "1. CreateOrder",
		Execute: func(ctx context.Context) error { return nil },
		Compensate: func(ctx context.Context) error {
			fmt.Println("    -> Отмена заказа в базе данных"); return nil
		},
	})

	saga.AddStep(SagaStep{
		Name: "2. ReserveInventory",
		Execute: func(ctx context.Context) error { return nil },
		Compensate: func(ctx context.Context) error {
			fmt.Println("    -> Возврат зарезервированного товара на склад"); return nil
		},
	})

	saga.AddStep(SagaStep{
		Name: "3. ProcessPayment",
		Execute: func(ctx context.Context) error {
			return fmt.Errorf("карта отклонена банком (недостаточно средств)")
		},
		Compensate: func(ctx context.Context) error { return nil },
	})

	err := saga.Run(context.Background())
	if err == nil {
		t.Fatal("Ожидался сбой на шаге платежа")
	}

	fmt.Println("Тест успешно подтвердил: компенсирующие транзакции сняли бронь со склада!")
}
```

## Под капотом

Компенсирующие транзакции ОБЯЗАНЫ быть семантически идемпотентными: если сетевой сбой произойдет во время выполнения компенсации, повторный вызов компенсации должен завершиться успешно.

## Подводные камни

Предполагать, что компенсирующая транзакция может просто удалить строку из базы (`DELETE FROM orders`): в финансовых системах удалять данные запрещено. Компенсация записывает сторнирующую проводку.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Saga Orchestration от Saga Choreography?»
**Ответ:** В хореографии (Choreography) микросервисы слушают события Kafka и сами решают, что делать дальше (нет центрального координатора, но сложно отслеживать граф вызовов). В оркестрации (Orchestration) выделенный Order Service управляет последовательностью вызовов по схеме State Machine, явно вызывая нужные gRPC методы и компенсации.
