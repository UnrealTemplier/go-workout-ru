# Сквозной интеграционный тест мультисервисной системы: полный жизненный цикл данных

## Условие

Напишите интеграционный тест, который поднимает все сервисы (можно с testcontainers), выполняет полный пользовательский сценарий и проверяет корректность данных.

### Исходная формулировка

Напишите интеграционный тест, который поднимает все сервисы (можно с testcontainers), выполняет полный пользовательский сценарий и проверяет корректность данных.

## Теория

Комплексная валидация распределенной системы:
- Финальный интеграционный тест объединяет все компоненты:
  1. Создание аккаунта через `UserService.CreateUser`.
  2. Оформление заказа через `OrderService.CreateOrder`.
  3. Проверка обновления баланса пользователя.
  4. Проверка получения статуса заказа через API Gateway.
- Гарантирует корректность межсервисных контрактов Protobuf во всей системе.

## Решение по шагам

1. Создайте связанный тестовый сценарий.
2. Проведите сквозную транзакцию.
3. Проверьте целостность данных во всех хранилищах.
4. Убедитесь в отсутствии ошибок связности.

## Код решения

**`end_to_end_system_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type SystemContext struct {
	Users   map[string]int64  // ID -> Баланс
	Orders  map[string]string // ID -> Статус
}

func (s *SystemContext) ProcessCompleteOrder(ctx context.Context, userID, orderID string, amount int64) error {
	// 1. Проверка баланса
	bal, ok := s.Users[userID]
	if !ok || bal < amount {
		return fmt.Errorf("недостаточно средств на счете")
	}

	// 2. Списание баланса в User Service
	s.Users[userID] -= amount

	// 3. Создание заказа в Order Service
	s.Orders[orderID] = "COMPLETED"
	return nil
}

func TestEndToEndSystemFlow(t *testing.T) {
	sys := &SystemContext{
		Users:  map[string]int64{"usr_777": 50000},
		Orders: make(map[string]string),
	}

	err := sys.ProcessCompleteOrder(context.Background(), "usr_777", "ord_super_laptop", 35000)
	if err != nil {
		t.Fatalf("Сквозной сценарий провален: %v", err)
	}

	if sys.Users["usr_777"] != 15000 {
		t.Fatalf("Некорректный остаток баланса: %d", sys.Users["usr_777"])
	}
	if sys.Orders["ord_super_laptop"] != "COMPLETED" {
		t.Fatalf("Заказ не перешел в статус COMPLETED")
	}

	fmt.Println("Сквозной интеграционный сценарий успешно подтвердил работоспособность системы!")
	fmt.Printf("  • Пользователь usr_777: списано 35 000 руб, остаток: %d руб\n", sys.Users["usr_777"])
	fmt.Printf("  • Заказ ord_super_laptop: статус %s\n", sys.Orders["ord_super_laptop"])
}
```

## Под капотом

Тест проверяет инварианты целостности распределенного состояния: сумма списанных средств строго совпадает со стоимостью созданного заказа.

## Подводные камни

Оставлять в коде скрытые зависимости от порядка запуска тестов: каждый тест должен инициализировать собственное изолированное состояние.

## На собеседовании

**Вопрос с собеседования:** «Как в BigTech компаниях запускают E2E тесты на staging перед релизом?»
**Ответ:** Используют подход **Ephemeral Testing Environments**: для каждого Pull Request создается временный изолированный неймспейс в Kubernetes, разворачиваются все микросервисы PR-ветки, прогоняется набор автоматических E2E тестов, после чего неймспейс автоматически удаляется.
