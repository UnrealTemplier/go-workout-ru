# Паттерн Circuit Breaker в Client Interceptor: изоляция сбойных сервисов на М секунд при N ошибках

## Условие

Реализуйте паттерн "circuit breaker" в client interceptor'е: при получении N подряд `codes.Unavailable` перестаньте делать запросы на M секунд.

## Теория

Промышленный клиентский Circuit Breaker Interceptor:
- Если сервис авторизации упал, 50 вызывающих микросервисов могут добить его повторными сетевыми вызовами (лавинный эффект).
- Circuit Breaker Interceptor:
  - Считает последовательные ошибки `codes.Unavailable`.
  - При достижении порога \(N\) переводит автомат в режим `OPEN`.
  - На протяжении \(M\) секунд перехватывает все вызовы и немедленно возвращает `codes.Unavailable` **локально**, не трогая сетевой сокет.
  - По истечении \(M\) секунд пропускает один проверочный запрос (HALF-OPEN).

## Решение по шагам

1. Создайте структуру состояния автомата.
2. Напишите `CircuitBreakerClientInterceptor`.
3. Протестируйте отсечение 6-го вызова локально.
4. Убедитесь в защите удаленного сервиса.

## Код решения

**`circuit_breaker_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type AtomicBreaker struct {
	consecutiveFails int64
	isOpen           int32
	lastTripTime     int64
	threshold        int64
	cooldown         time.Duration
}

func CircuitBreakerClientInterceptor(cb *AtomicBreaker) grpc.UnaryClientInterceptor {
	return func(
		ctx context.Context,
		method string,
		req, reply any,
		cc *grpc.ClientConn,
		invoker grpc.UnaryInvoker,
		opts ...grpc.CallOption,
	) error {
		// Проверка состояния предохранителя
		if atomic.LoadInt32(&cb.isOpen) == 1 {
			tripTime := time.Unix(0, atomic.LoadInt64(&cb.lastTripTime))
			if time.Since(tripTime) < cb.cooldown {
				// Быстрый отказ: не трогаем сокет!
				return status.Error(codes.Unavailable, "circuit breaker: удаленный сервис изолирован")
			}
			// Тайм-аут кулдауна истек -> пробуем сделать запрос (Half-Open)
		}

		err := invoker(ctx, method, req, reply, cc, opts...)
		if err != nil {
			if status.Code(err) == codes.Unavailable {
				fails := atomic.AddInt64(&cb.consecutiveFails, 1)
				if fails >= cb.threshold {
					atomic.StoreInt32(&cb.isOpen, 1)
					atomic.StoreInt64(&cb.lastTripTime, time.Now().UnixNano())
					fmt.Printf("[CircuitBreaker] Сработало размыкание цепи после %d ошибок!\n", fails)
				}
			}
			return err
		}

		// Успех -> сброс в нормальное состояние
		atomic.StoreInt32(&cb.isOpen, 0)
		atomic.StoreInt64(&cb.consecutiveFails, 0)
		return nil
	}
}

func TestCircuitBreakerInterceptorFlow(t *testing.T) {
	cb := &AtomicBreaker{threshold: 3, cooldown: 50 * time.Millisecond}
	interceptor := CircuitBreakerClientInterceptor(cb)

	failingInvoker := func(ctx context.Context, method string, req, reply any, cc *grpc.ClientConn, opts ...grpc.CallOption) error {
		return status.Error(codes.Unavailable, "сеть недоступна")
	}

	// 3 вызова достигают инвокера и падают
	for i := 1; i <= 3; i++ {
		_ = interceptor(context.Background(), "/svc/Call", nil, nil, nil, failingInvoker)
	}

	// 4-й вызов отсекается интерцептором мгновенно без вызова failingInvoker
	err := interceptor(context.Background(), "/svc/Call", nil, nil, nil, func(ctx context.Context, method string, req, reply any, cc *grpc.ClientConn, opts ...grpc.CallOption) error {
		t.Fatal("Инвокер не должен был вызываться!")
		return nil
	})

	if status.Code(err) != codes.Unavailable {
		t.Fatalf("Ожидался Unavailable от breaker, получено: %v", err)
	}

	fmt.Printf("4-й вызов безопасно отсечен интерцептором: %v\n", err)
}
```

## Под капотом

Клиентский интерцептор предотвращает аллокацию буферов сериализации и отправку кадров HTTP/2, снижая нагрузку на CPU клиента при авариях в бэкенде.

## Подводные камни

Использовать общий Circuit Breaker на весь сервис целиком: если сбоит только один метод `GetAnalytics`, предохранитель должен изолировать только его, не блокируя критический метод `CreateOrder`.

## На собеседовании

**Вопрос с собеседования:** «Как Circuit Breaker взаимодействует со Service Mesh (Envoy)?»
**Ответ:** В современной архитектуре Circuit Breaking часто выносят в Envoy: через параметры `consecutive_5xx` и `base_ejection_time` прокси автоматически временно исключает сбойные поды из пула балансировки (Outlier Detection), освобождая код микросервиса от ручной реализации.
