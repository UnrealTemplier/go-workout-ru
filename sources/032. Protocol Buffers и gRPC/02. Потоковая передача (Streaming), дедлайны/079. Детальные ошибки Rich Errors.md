# Детальные ошибки Rich Errors: прикрепление errdetails.BadRequest и извлечение на клиенте

## Условие

Добави **rich error** через `google.golang.org/genproto/googleapis/rpc/errdetails`: `st := status.New(codes.InvalidArgument, "invalid email")`, `ds, _ := st.WithDetails(&errdetails.BadRequest{...})`. Верни `ds.Err()`. В клиенте извлеки детали через `status.FromError` + `details := s.Details()`.

## Теория

Модель расширенных ошибок Google Rich Errors:
- Обычное строковое сообщение `desc = "invalid email"` неудобно для фронтенда и мобильных приложений.
- Пакет `google.golang.org/genproto/googleapis/rpc/errdetails` предоставляет стандартизированные Protobuf структуры:
  - `errdetails.BadRequest`: список нарушений полей `FieldViolation { Field: "email", Description: "неверный формат" }`.
  - `errdetails.QuotaFailure`: информация о превышении лимитов.
  - `errdetails.RetryInfo`: через сколько секунд повторить запрос (`retry_delay`).
- Метод `st.WithDetails(...)` упаковывает структуры в `google.protobuf.Any` и прикрепляет к трейлерам gRPC.

## Решение по шагам

1. Создайте `status.New(codes.InvalidArgument, "ошибка валидации")`.
2. Создайте `errdetails.BadRequest` с нарушением поля `email`.
3. Прикрепите детали через `st.WithDetails()`.
4. На клиенте вызовите `s.Details()` и распечатайте нарушенные поля.

## Код решения

**`rich_errors_demo.go`**

```go
package main

import (
	"fmt"

	"google.golang.org/genproto/googleapis/rpc/errdetails"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

// Серверная функция валидации с Rich Error
func ValidateUserForm(email string) error {
	if email == "" || email == "bad_email" {
		st := status.New(codes.InvalidArgument, "ошибка валидации входных данных")

		// Прикрепляем структурированные подробности об ошибке
		br := &errdetails.BadRequest{
			FieldViolations: []*errdetails.BadRequest_FieldViolation{
				{
					Field:       "email",
					Description: "email должен содержать символ @ и валидный домен",
				},
			},
		}

		detailedStatus, err := st.WithDetails(br)
		if err != nil {
			return st.Err()
		}
		return detailedStatus.Err()
	}
	return nil
}

func main() {
	err := ValidateUserForm("bad_email")
	if err != nil {
		st, ok := status.FromError(err)
		if ok {
			fmt.Printf("Код ошибки: %s, Описание: %s\n", st.Code(), st.Message())
			fmt.Println("Детальные нарушения (Field Violations):")
			for _, detail := range st.Details() {
				switch d := detail.(type) {
				case *errdetails.BadRequest:
					for _, violation := range d.GetFieldViolations() {
						fmt.Printf("  -> Поле: %q | Причина: %s\n",
							violation.GetField(), violation.GetDescription())
					}
				}
			}
		}
	}
}
```

## Под капотом

Детали ошибки сериализуются в байты и передаются в HTTP/2 Trailer `grpc-status-details-bin`. Благодаря бинарному кодированию Any в них можно передавать сколь угодно сложные структуры с полной типобезопасностью.

## Подводные камни

Игнорировать ошибку от `st.WithDetails(...)`: если передаваемая структура не является зарегистрированным сообщением Protobuf, метод вернет ошибку, и детали не прикрепятся.

## На собеседовании

**Вопрос с собеседования:** «Как передать информацию клиенту о том, когда безопасно повторить запрос при Rate Limiting (HTTP 429)?»
**Ответ:** Прикрепить к ошибке `codes.ResourceExhausted` структуру `errdetails.RetryInfo{RetryDelay: durationpb.New(5 * time.Second)}`. Клиентские библиотеки gRPC могут автоматически считывать этот заголовок и выполнять повторный запрос ровно через указанный интервал.
