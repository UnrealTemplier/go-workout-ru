# Идиоматичный клиент Server Streaming: вызов метода и корректный цикл чтения до io.EOF

## Условие

Напиши клиент для Server Streaming: вызови метод и читай поток в цикле `for { user, err := stream.Recv(); if err == io.EOF { break } ... }`.

## Теория

Канонический паттерн чтения серверного стрима на клиенте:
- Получение объекта стрима: `stream, err := client.ListUsers(ctx, req)`
- Цикл чтения:
  ```go
  for {
      resp, err := stream.Recv()
      if err == io.EOF {
          // Сервер завершил передачу
          break
      }
      if err != nil {
          // Ошибка сети или бизнес-ошибка сервера
          return fmt.Errorf("ошибка чтения стрима: %w", err)
      }
      // Обработка resp
  }
  ```

## Решение по шагам

1. Создайте клиентский стрим.
2. Организуйте бесконечный цикл.
3. Обработайте условие `err == io.EOF`.
4. Обработайте сетевые ошибки через `status.FromError`.

## Код решения

**`canonical_client_stream_reader.go`**

```go
package main

import (
	"fmt"
	"io"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type EventDTO struct {
	ID   int64
	Type string
}

type MockEventStream struct {
	events []*EventDTO
}

func (s *MockEventStream) Recv() (*EventDTO, error) {
	if len(s.events) == 0 {
		return nil, io.EOF
	}
	evt := s.events[0]
	s.events = s.events[1:]
	return evt, nil
}

func main() {
	stream := &MockEventStream{
		events: []*EventDTO{
			{ID: 1, Type: "ORDER_CREATED"},
			{ID: 2, Type: "PAYMENT_RECEIVED"},
			{ID: 3, Type: "ORDER_SHIPPED"},
		},
	}

	fmt.Println("Клиент начинает вычитку потока событий:")
	for {
		event, err := stream.Recv()
		if err == io.EOF {
			fmt.Println("Поток успешно завершен сервером (io.EOF)")
			break
		}
		if err != nil {
			st, _ := status.FromError(err)
			if st.Code() == codes.Canceled {
				fmt.Println("Стрим отменен клиентом")
				break
			}
			panic(fmt.Sprintf("Критическая ошибка стрима: %v", err))
		}

		fmt.Printf("  Событие #%d: [%s]\n", event.ID, event.Type)
	}
}
```

```bash

```

## Под капотом

Вызов `stream.Recv()` блокирует вызывающую горутину до прихода следующего HTTP/2 фрейма `DATA`. Если новых данных нет, горутина переводится планировщиком Go в состояние ожидания (Waiting), не расходуя процессорное время.

## Подводные камни

Проверять `err != nil` ДО проверки `err == io.EOF`: так как `io.EOF` реализует интерфейс `error`, неправильный порядок условий приведет к ошибочной обработке штатного завершения стрима как аварии.

## На собеседовании

**Вопрос с собеседования:** «Может ли stream.Recv() вернуть не-nil объект и io.EOF одновременно?»
**Ответ:** НЕТ. В gRPC метод `stream.Recv()` строго разделяет состояния: он возвращает либо `(msg, nil)`, либо `(nil, io.EOF)`, либо `(nil, err)`. Если сообщение было последним, оно вернется с ошибкой `nil`, а последующий вызов `Recv()` вернет `io.EOF`.
