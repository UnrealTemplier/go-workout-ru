# Синхронизация двунаправленного стриминга: параллельные Recv() и Send() в разных горутинах

## Условие

Определи **bidirectional streaming**: `rpc Chat(stream ChatMessage) returns (stream ChatMessage);`. Реализуй на сервере: читай `Recv()` в одной горутине, отправляй `Send()` в другой. Обе горутины завершаются при `io.EOF` или ошибке.

## Теория

Координация параллельных горутин в Bidirectional RPC:
- В полнодуплексном стриме чтение и запись не зависят друг от друга:
  - Горутина 1 (Reader): читает входящие сообщения через `stream.Recv()`. При ошибке или `io.EOF` сигнализирует о завершении.
  - Горутина 2 (Writer): вычитывает исходящие сообщения из очереди и шлет через `stream.Send()`.
- Координация завершения:
  - Используется `sync.WaitGroup` или контекст с отменой `context.WithCancel(stream.Context())`.
  - Завершение любой из горутин обязано корректно гасить вторую горутину.

## Решение по шагам

1. Создайте метод `Chat`.
2. Запустите горутину чтения.
3. Запустите горутину записи.
4. Синхронизируйте корректное завершение обеих сторон через канал отмены.

## Код решения

**`bidi_goroutines_sync_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"sync"
	"testing"
	"time"
)

type Msg struct{ Content string }

type MockBidiPipe struct {
	in  chan *Msg
	out chan *Msg
}

func (p *MockBidiPipe) Recv() (*Msg, error) {
	m, ok := <-p.in
	if !ok {
		return nil, io.EOF
	}
	return m, nil
}

func (p *MockBidiPipe) Send(m *Msg) error {
	p.out <- m
	return nil
}

func RunBidiSession(ctx context.Context, pipe *MockBidiPipe) error {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(2)

	// 1. Горутина чтения
	go func() {
		defer wg.Done()
		defer cancel() // Если чтение завершилось, гасим запись
		for {
			msg, err := pipe.Recv()
			if err != nil {
				return
			}
			fmt.Println("  [Сервер прочитал]:", msg.Content)
		}
	}()

	// 2. Горутина записи
	go func() {
		defer wg.Done()
		ticker := time.NewTicker(20 * time.Millisecond)
		defer ticker.Stop()

		for {
			select {
			case <-ctx.Done():
				return
			case <-ticker.C:
				_ = pipe.Send(&Msg{Content: "серверный_пульс"})
			}
		}
	}()

	wg.Wait()
	return nil
}

func TestBidiGoroutinesSync(t *testing.T) {
	pipe := &MockBidiPipe{
		in:  make(chan *Msg, 5),
		out: make(chan *Msg, 5),
	}

	done := make(chan error)
	go func() {
		done <- RunBidiSession(context.Background(), pipe)
	}()

	// Клиент шлет сообщение и закрывает канал
	pipe.in <- &Msg{Content: "Привет сервер!"}
	time.Sleep(30 * time.Millisecond)
	close(pipe.in)

	select {
	case <-done:
		fmt.Println("Обе горутины успешно синхронизированы и остановлены без утечек!")
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Дедлок: горутины не завершились")
	}
}
```

ℹ️ Синхронизация горутин чтения и записи через context.WithCancel

## Под капотом

Вызов `cancel()` в `defer` горутины чтения гарантирует немедленное прерывание `select` во второй горутине записи, исключая утечку горутин (Goroutine Leak) при обрыве стрима.

## Подводные камни

Использовать небуферизированный канал `out` без вычитки: горутина записи заблокируется, `wg.Wait()` зависнет, и память соединения утечет.

## На собеседовании

**Вопрос с собеседования:** «Почему в Bidirectional стримах не рекомендуется запускать Send() прямо внутри цикла Recv()?»
**Ответ:** Потому что если отправка `Send()` заблокируется из-за медленного сетевого окна клиента (Backpressure), цикл `Recv()` также перестанет читать входящие сообщения. Разделение на две параллельные горутины гарантирует, что сервер всегда сможет прочитать входящие сообщения или сигнал отмены от клиента.
