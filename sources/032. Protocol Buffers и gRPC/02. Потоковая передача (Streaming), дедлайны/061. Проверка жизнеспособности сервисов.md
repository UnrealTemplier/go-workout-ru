# Проверка жизнеспособности сервисов: стандартный протокол grpc.health.v1 и статусы SERVING/NOT_SERVING

## Условие

Реализуй **health check**: импортируй `grpc.health.v1`. Реализуй `HealthServer`. Клиент проверяет `healthClient.Check(ctx, &healthpb.HealthCheckRequest{Service: "user.UserService"})`. Верни `SERVING` или `NOT_SERVING`.

### Исходная формулировка

Реализуй **health check**: импортируй `grpc.health.v1`. Реализуй `HealthServer`. Клиент проверяет `healthClient.Check(ctx, &healthpb.HealthCheckRequest{Service: "user.UserService"})`. Верни `SERVING` или `NOT_SERVING`.

## Теория

Официальный стандарт gRPC Health Checking Protocol:
- Спецификация `grpc.health.v1` определяет стандартный сервис проверки здоровья микросервиса.
- Используется Kubernetes для проб `livenessProbe` и `readinessProbe`, а также балансировщиками (Envoy, Consul, NGINX).
- Пакет в Go: `google.golang.org/grpc/health` и `google.golang.org/grpc/health/grpc_health_v1`.
- Статусы:
  - `SERVING`: сервис полностью готов принимать пользовательский трафик.
  - `NOT_SERVING`: сервис испытывает проблемы (например, отвалилась БД) и должен быть временно исключен из балансировки.
  - `SERVICE_UNKNOWN`: переданный сервис не зарегистрирован.

## Решение по шагам

1. Создайте стандартный health-сервер через `health.NewServer()`.
2. Зарегистрируйте его в `grpc.NewServer()`.
3. Установите статус сервиса `SetServingStatus("user.UserService", Serving)`.
4. Проверьте статус со стороны клиента через `Check()`.

## Код решения

**`health_check_demo.go`**

```go
package main

import (
	"context"
	"fmt"

	"google.golang.org/grpc/health"
	healthpb "google.golang.org/grpc/health/grpc_health_v1"
)

func main() {
	// Создаем стандартный сервер проверки здоровья gRPC
	healthServer := health.NewServer()

	// 1. Помечаем сервис как готовый принимать трафик
	serviceName := "user.v1.UserService"
	healthServer.SetServingStatus(serviceName, healthpb.HealthCheckResponse_SERVING)

	// 2. Проверяем статус через клиентский запрос Check
	resp, err := healthServer.Check(context.Background(), &healthpb.HealthCheckRequest{
		Service: serviceName,
	})
	if err != nil {
		panic(err)
	}

	fmt.Printf("Статус сервиса %s: %s\n", serviceName, resp.GetStatus())

	// 3. Имитируем сбой базы данных -> переводим в NOT_SERVING
	healthServer.SetServingStatus(serviceName, healthpb.HealthCheckResponse_NOT_SERVING)

	respDegraded, _ := healthServer.Check(context.Background(), &healthpb.HealthCheckRequest{
		Service: serviceName,
	})
	fmt.Printf("Статус после сбоя БД: %s (Kubernetes снимет трафик!)\n", respDegraded.GetStatus())
}
```

ℹ️ Управление статусами здоровья в grpc.health.v1

**`Терминал`**

```bash
go run health_check_demo.go
# Вывод:
# Статус сервиса user.v1.UserService: SERVING
# Статус после сбоя БД: NOT_SERVING (Kubernetes снимет трафик!)
```

## Под капотом

Помимо унарного метода `Check`, протокол здоровья поддерживает метод `Watch(req, stream)`, позволяющий Kubernetes или балансировщику Envoy мгновенно узнавать об изменении статуса пода через Server Streaming без постоянного спама унарными опросами.

## Подводные камни

Использовать отдельный HTTP/REST порт 8080 только для /healthz в gRPC сервисе: если упадет gRPC порт 50051, HTTP порт может продолжать отвечать 200 OK. Используйте нативный gRPC health check (утилиту `grpc-health-probe`).

## На собеседовании

**Вопрос с собеседования:** «Как настроить gRPC health check в Kubernetes pod manifest без установки дополнительных утилит?»
**Ответ:** Начиная с Kubernetes 1.24+ встроена нативная поддержка gRPC проб:
```yaml
livenessProbe:
  grpc:
    port: 50051
    service: user.v1.UserService
  initialDelaySeconds: 5
```
Kubernetes сам вызывает `grpc.health.v1.Health/Check` без необходимости сторонних bash-скриптов.
