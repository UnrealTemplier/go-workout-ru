# Эмуляция задержек и таймаутов: time.Sleep на сервере и отсечка клиента DeadlineExceeded

## Условие

**Дедлайны (Context)**: На стороне сервера в методе `GetUser` добавь `time.Sleep(2 * time.Second)`. На стороне клиента вызови метод, передав контекст с таймаутом в 1 секунду (`context.WithTimeout`). Убедись, что клиент отваливается с ошибкой `DeadlineExceeded`.

## Теория

Защита от зависающих зависимостей:
- В продакшене база данных или сторонний платежный шлюз могут заблокироваться на 30 секунд.
- Клиентский таймаут:
  `ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)`
- Если сервер спит `time.Sleep(2 * time.Second)`, клиент ровно через 1000 мс прерывает соединение.
- Клиент гарантированно получает статус:
  `codes.DeadlineExceeded` (код 4).

## Решение по шагам

1. Создайте серверный метод с искусственной паузой 2 секунды.
2. Вызовите метод с клиентским таймаутом 1 секунда.
3. Проверьте статус ошибки `codes.DeadlineExceeded`.
4. Зафиксируйте точное время отсечки.

## Код решения

**`timeout_simulation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type SlowUserService struct{}

func (s *SlowUserService) GetUser(ctx context.Context, id int64) (string, error) {
	// Сервер симулирует долгий SQL запрос
	select {
	case <-time.After(2 * time.Second):
		return "Пользователь найден", nil
	case <-ctx.Done():
		return "", status.Error(codes.DeadlineExceeded, "сервер прерван по дедлайну клиента")
	}
}

func TestClientTimeoutCutoff(t *testing.T) {
	svc := &SlowUserService{}

	// Клиент готов ждать только 100 мс (вместо 2 секунд)
	start := time.Now()
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	_, err := svc.GetUser(ctx, 42)
	elapsed := time.Since(start)

	if err == nil {
		t.Fatal("Ожидался сбой по таймауту, но вызов успешно завершился")
	}

	st, ok := status.FromError(err)
	if !ok || st.Code() != codes.DeadlineExceeded {
		t.Fatalf("Ожидался код DeadlineExceeded, получено: %v", err)
	}

	fmt.Printf("Клиент корректно отвалился с ошибкой: [%s]\n", st.Code())
	fmt.Printf("Время ожидания до отсечки составило: %v (ровно по лимиту контекста!)\n", elapsed.Round(time.Millisecond))
}
```

## Под капотом

Таймер контекста в Go реализован внутри рантайма через структуру `time.Timer` в пуле таймеров P (GMP планировщик). При наступлении дедлайна горутина таймера переводит канал `Done` в сигнальное состояние.

## Подводные камни

Использовать в сервере `time.Sleep(2 * time.Second)` без `select` с `<-ctx.Done()`: поток сервера проспит все 2 секунды, даже если клиент уже ушел через 100 мс.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить каскадный отказ сервисов (Cascading Failure), если внешняя зависимость начала отвечать с задержкой 5 секунд вместо 50 мс?»
**Ответ:** 1. Выставить жесткий gRPC дедлайн `context.WithTimeout(ctx, 200*time.Millisecond)`. 2. Включить Circuit Breaker (например gobreaker), чтобы при превышении 50% ошибок сервис сразу переставал слать запросы во внешнюю систему. 3. Настроить Fallback (возврат данных из резервного кэша Redis).
