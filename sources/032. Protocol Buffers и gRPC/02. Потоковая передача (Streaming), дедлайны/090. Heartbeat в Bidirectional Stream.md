# Heartbeat в Bidirectional Stream: периодические пинги по таймеру и отсечка мертвого соединения

## Условие

Реализуй **"heartbeat" в bidirectional stream**: клиент и сервер отправляют пинг каждые 5 секунд. Если пинг не получен за 15 секунд — закройте соединение. Используй `time.Ticker` + `select` с `ctx.Done()`.

### Исходная формулировка

---

## Теория

Обнаружение мертвых соединений (Heartbeat / Dead Peer Detection):
- Проблема Half-Open TCP Connections: при аварии маршрутизатора или обрыве Wi-Fi TCP-сокет может часами висеть открытым, пока не будет сделана попытка записи.
- Механизм Heartbeat:
  - Каждые \(N\) секунд отправляется служебный пакет `PING`.
  - При получении `PING` принимающая сторона сбрасывает таймер неактивности (`heartbeatTimer.Reset(...)`).
  - Если за тайм-аут (например, 15 сек) ни одного сообщения не поступило, соединение принудительно разрывается со статусом `codes.DeadlineExceeded`.

## Решение по шагам

1. Создайте периодический тикер отправки `PING`.
2. Создайте таймер ожидания ответа с таймаутом.
3. Сбрасывайте таймер при каждом входящем пакете.
4. Прерывайте соединение при срабатывании таймера ожидания.

## Код решения

**`heartbeat_stream_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type HeartbeatPacket struct {
	IsPing bool
}

func RunHeartbeatWatcher(
	ctx context.Context,
	in <-chan *HeartbeatPacket,
	out chan<- *HeartbeatPacket,
	pingInterval time.Duration,
	deadTimeout time.Duration,
) error {
	pingTicker := time.NewTicker(pingInterval)
	defer pingTicker.Stop()

	deadTimer := time.NewTimer(deadTimeout)
	defer deadTimer.Stop()

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()

		case <-pingTicker.C:
			// Отправка пинга удаленной стороне
			select {
			case out <- &HeartbeatPacket{IsPing: true}:
			default:
			}

		case pkt, ok := <-in:
			if !ok {
				return nil
			}
			if pkt.IsPing {
				// Пинг получен! Сбрасываем сторожевой таймер
				if !deadTimer.Stop() {
					select {
					case <-deadTimer.C:
					default:
					}
				}
				deadTimer.Reset(deadTimeout)
			}

		case <-deadTimer.C:
			// Тайм-аут: удаленная сторона не присылала heartbeat!
			return status.Error(codes.DeadlineExceeded, "heartbeat timeout: соединение потеряно")
		}
	}
}

func TestHeartbeatTimeoutDetection(t *testing.T) {
	in := make(chan *HeartbeatPacket, 5)
	out := make(chan *HeartbeatPacket, 5)

	// Короткие интервалы для быстрого теста: пинг каждые 20 мс, таймаут 60 мс
	done := make(chan error)
	go func() {
		done <- RunHeartbeatWatcher(context.Background(), in, out, 20*time.Millisecond, 60*time.Millisecond)
	}()

	// Отправляем первый пинг вовремя (через 20 мс)
	time.Sleep(20 * time.Millisecond)
	in <- &HeartbeatPacket{IsPing: true}

	// Затем «зависаем» и ничего не шлем 80 мс -> должен сработать таймаут 60 мс
	err := <-done
	if err == nil {
		t.Fatal("Ожидалась ошибка таймаута heartbeat")
	}

	st, _ := status.FromError(err)
	if st.Code() != codes.DeadlineExceeded {
		t.Fatalf("Ожидался код DeadlineExceeded, получено: %v", err)
	}

	fmt.Printf("Сторожевой таймер корректно разорвал мертвое соединение: [%s] %s\n",
		st.Code(), st.Message())
}
```

## Под капотом

В gRPC встроен транспортный механизм Keepalive: пакет `google.golang.org/grpc/keepalive` позволяет настроить параметры `keepalive.ClientParameters{Time: 10*time.Second, Timeout: 3*time.Second}`, отправляющий HTTP/2 PING фреймы автоматически.

## Подводные камни

Забывать очищать канал `<-deadTimer.C` при сбросе таймера в Go до версии 1.23: это могло приводить к ложным срабатываниям таймера.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие прикладного heartbeat от встроенного gRPC HTTP/2 keepalive?»
**Ответ:** HTTP/2 Keepalive проверяет исключительно жизнеспособность сетевого сокета и ОС. Прикладной Heartbeat в стриме проверяет, что само приложение (горутина, event-loop сервиса) не зависло в дедлоке и способно обрабатывать входящие сообщения.
