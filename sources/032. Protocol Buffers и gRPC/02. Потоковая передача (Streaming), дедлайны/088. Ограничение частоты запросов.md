# Ограничение частоты запросов: Rate Limiting Interceptor на базе Token Bucket и статус ResourceExhausted

## Условие

Создайте interceptor для rate limiting, используя `golang.org/x/time/rate`. Возвращайте `codes.ResourceExhausted` при превышении лимита.

## Теория

Защита от перегрузки (Rate Limiting Middleware):
- Пакет `golang.org/x/time/rate` реализует алгоритм Token Bucket (Корзина токенов):
  - Скорость пополнения: \(R\) токенов в секунду (`rate.Limit`).
  - Вместимость корзины: \(B\) токенов (`burst`).
- При каждом входящем RPC вызове интерцептор вызывает:
  `limiter.Allow()`
- Если токенов в корзине нет:
  - Вызов отклоняется со статусом `codes.ResourceExhausted` (код 8).
  - Клиент получает ошибку, аналогичную HTTP 429 Too Many Requests.

## Решение по шагам

1. Создайте `rate.NewLimiter(rate.Limit(r), burst)`.
2. Напишите `RateLimitUnaryInterceptor`.
3. При отказе возвращайте `status.Error(codes.ResourceExhausted, "превышен лимит запросов")`.
4. Протестируйте отсечку превышающих запросов.

## Код решения

**`rate_limiter_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"

	"golang.org/x/time/rate"
	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func NewRateLimitInterceptor(rps int, burst int) grpc.UnaryServerInterceptor {
	limiter := rate.NewLimiter(rate.Limit(rps), burst)

	return func(
		ctx context.Context,
		req any,
		info *grpc.UnaryServerInfo,
		handler grpc.UnaryHandler,
	) (any, error) {
		if !limiter.Allow() {
			return nil, status.Error(codes.ResourceExhausted, "rate limit exceeded: превышена квота запросов")
		}
		return handler(ctx, req)
	}
}

func TestRateLimiter(t *testing.T) {
	// Лимит: 2 запроса в секунду, burst 2
	interceptor := NewRateLimitInterceptor(2, 2)
	dummyHandler := func(ctx context.Context, req any) (any, error) {
		return "OK", nil
	}

	info := &grpc.UnaryServerInfo{FullMethod: "/api.v1.Service/Method"}

	// Первые 2 запроса должны пройти (израсходуют burst)
	for i := 1; i <= 2; i++ {
		_, err := interceptor(context.Background(), nil, info, dummyHandler)
		if err != nil {
			t.Fatalf("Запрос #%d должен был пройти успешно, ошибка: %v", i, err)
		}
	}

	// 3-й запрос подряд должен быть отклонен
	_, err := interceptor(context.Background(), nil, info, dummyHandler)
	if err == nil {
		t.Fatal("3-й запрос должен был вернуть ошибку ResourceExhausted")
	}

	st, ok := status.FromError(err)
	if !ok || st.Code() != codes.ResourceExhausted {
		t.Fatalf("Ожидался код ResourceExhausted, получено: %v", err)
	}

	fmt.Printf("Rate Limiter успешно защитил сервис: [%s] %s\n", st.Code(), st.Message())
}
```

## Под капотом

`limiter.Allow()` выполняется lock-free или с минимальной синхронизацией мьютекса в наносекундных диапазонах времени, защищая бэкенд от скачков трафика без создания бутылочного горлышка.

## Подводные камни

Использовать один глобальный Rate Limiter на всех пользователей: атакующий клиент может заблокировать доступ всем добросовестным пользователям. Лимитировать нужно по IP или ID клиента (Per-Client Rate Limiting).

## На собеседовании

**Вопрос с собеседования:** «Как реализовать распределенный Rate Limiting для кластера из 50 подов gRPC в Kubernetes?»
**Ответ:** Локального `rate.Limiter` недостаточно, так как поды не знают о трафике друг друга. Используют распределенный кэш **Redis** с алгоритмом Sliding Window или Token Bucket через атомарные Lua-скрипты, либо Envoy Global Rate Limit Service (gRPC RLS).
