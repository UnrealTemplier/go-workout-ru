# Цепочки интерцепторов: паттерн grpc.ChainUnaryInterceptor и строгий порядок выполнения

## Условие

Добави **chain of interceptors**: `grpc.ChainUnaryInterceptor(loggingInterceptor, authInterceptor, recoveryInterceptor)`. Покажи порядок выполнения (внешний → внутренний → handler → обратно).

## Теория

Порядок прохождения цепочки Middleware:
- Функция `grpc.ChainUnaryInterceptor(M1, M2, M3)` объединяет несколько интерцепторов в единую матрешку.
- Порядок исполнения (Паттерн Onion Architecture):
  1. Вход: `M1 (Logging)` \(\to\) `M2 (Auth)` \(\to\) `M3 (Recovery)` \(\to\) **Целевой Handler**.
  2. Выход: **Handler** \(\to\) `M3 (Recovery)` \(\to\) `M2 (Auth)` \(\to\) `M1 (Logging)`.
- Если `M2 (Auth)` обнаруживает невалидный токен и возвращает ошибку, `M3` и `Handler` вообще не вызываются, а `M1 (Logging)` фиксирует ошибку доступа.

## Решение по шагам

1. Создайте три интерцептора: Logging, Auth, Recovery.
2. Соберите их в цепочку через `grpc.ChainUnaryInterceptor`.
3. Запустите тестовый вызов.
4. Убедитесь в соблюдении симметричного порядка входа и выхода.

## Код решения

**`interceptor_chain_demo.go`**

```go
package main

import (
	"context"
	"fmt"

	"google.golang.org/grpc"
)

func StepLogging(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	fmt.Println("1. [ENTER] Logging Interceptor")
	resp, err := handler(ctx, req)
	fmt.Println("1. [EXIT]  Logging Interceptor")
	return resp, err
}

func StepAuth(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	fmt.Println("  2. [ENTER] Auth Interceptor")
	resp, err := handler(ctx, req)
	fmt.Println("  2. [EXIT]  Auth Interceptor")
	return resp, err
}

func StepRecovery(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	fmt.Println("    3. [ENTER] Recovery Interceptor")
	resp, err := handler(ctx, req)
	fmt.Println("    3. [EXIT]  Recovery Interceptor")
	return resp, err
}

func main() {
	chain := grpc.ChainUnaryInterceptor(StepLogging, StepAuth, StepRecovery)

	dummyHandler := func(ctx context.Context, req any) (any, error) {
		fmt.Println("      -> [EXEC] Выполнение бизнес-логики RPC Handler")
		return "OK", nil
	}

	// Эмулируем выполнение цепочки
	server := grpc.NewServer(chain)
	_ = server

	fmt.Println("Порядок выполнения интерцепторов при RPC запросе:")
	// Ручная симуляция прохода цепочки:
	_, _ = StepLogging(context.Background(), "req", &grpc.UnaryServerInfo{}, func(c1 context.Context, r1 any) (any, error) {
		return StepAuth(c1, r1, &grpc.UnaryServerInfo{}, func(c2 context.Context, r2 any) (any, error) {
			return StepRecovery(c2, r2, &grpc.UnaryServerInfo{}, dummyHandler)
		})
	})
}
```

## Под капотом

`grpc.ChainUnaryInterceptor` рекурсивно строит единый функциональный замыкатель `UnaryHandler`, гарантируя нулевые аллокации памяти при обходе цепочки.

## Подводные камни

Ставить Recovery последним или после тяжелых обработчиков: `RecoveryInterceptor` должен быть одним из первых (снаружи), чтобы перехватывать паники даже из других интерцепторов.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие grpc.UnaryInterceptor от grpc.ChainUnaryInterceptor?»
**Ответ:** `grpc.UnaryInterceptor` принимает строго один интерцептор. Если передать его дважды в `grpc.NewServer()`, второй интерцептор молча перезапишет первый. `grpc.ChainUnaryInterceptor` был добавлен в gRPC Go v1.28 специально для безопасного объединения произвольного количества Middleware.
