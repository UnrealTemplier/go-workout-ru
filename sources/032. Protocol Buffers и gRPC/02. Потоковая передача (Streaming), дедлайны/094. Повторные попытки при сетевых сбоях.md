# Повторные попытки при сетевых сбоях: Retry с Exponential Backoff при статусе codes.Unavailable

## Условие

Обработайте `status.Code` на клиенте и реализуйте повторные попытки при `Unavailable` (с exponential backoff).

## Теория

Паттерн надежности Retry с экспоненциальной задержкой:
- В распределенных системах кратковременные сетевые сбои (Transient Network Failures) или перезапуск пода в Kubernetes возвращают ошибку `codes.Unavailable` (код 14).
- Формула Exponential Backoff с джиттером:
  \(T_{\text{wait}} = \text{base\_delay} \times 2^{\text{attempt}} + \text{jitter}\)
- Джиттер (случайная добавка \(\pm 20\%\)) предотвращает проблему Thundering Herd, когда тысячи клиентов одновременно бомбардируют только что поднявшийся сервер повторными запросами.

## Решение по шагам

1. Напишите функцию повтора вызова с проверкой `codes.Unavailable`.
2. Реализуйте увеличение паузы \(2^n\).
3. Добавьте лимит максимального числа попыток.
4. Протестируйте восстановление после временного сбоя.

## Код решения

**`retry_backoff_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type FlakyService struct {
	attempts int
}

func (s *FlakyService) DoWork(ctx context.Context) (string, error) {
	s.attempts++
	// Первые 2 попытки имитируют сбой сети, 3-я попытка успешна
	if s.attempts < 3 {
		return "", status.Error(codes.Unavailable, "сеть временно недоступна (503)")
	}
	return "Успешный результат после повтора", nil
}

func CallWithExponentialBackoff(
	ctx context.Context,
	maxRetries int,
	fn func(context.Context) (string, error),
) (string, error) {
	baseDelay := 10 * time.Millisecond

	for attempt := 0; attempt < maxRetries; attempt++ {
		resp, err := fn(ctx)
		if err == nil {
			return resp, nil
		}

		st, ok := status.FromError(err)
		if !ok || st.Code() != codes.Unavailable {
			// Ошибки вроде InvalidArgument или NotFound ретраить бессмысленно
			return "", err
		}

		backoff := baseDelay * (1 << attempt)
		fmt.Printf("Попытка #%d не удалась (%s). Ожидание %v перед повтором...\n",
			attempt+1, st.Code(), backoff)

		select {
		case <-time.After(backoff):
		case <-ctx.Done():
			return "", ctx.Err()
		}
	}

	return "", status.Error(codes.Unavailable, "исчерпаны все попытки повтора запроса")
}

func TestRetryWithExponentialBackoff(t *testing.T) {
	svc := &FlakyService{}

	result, err := CallWithExponentialBackoff(context.Background(), 4, svc.DoWork)
	if err != nil {
		t.Fatalf("Вызов должен был завершиться успехом, ошибка: %v", err)
	}

	if result != "Успешный результат после повтора" {
		t.Fatalf("Некорректный результат: %s", result)
	}

	fmt.Printf("Итоговый успех: %s (всего попыток: %d)\n", result, svc.attempts)
}
```

## Под капотом

Начиная с gRPC v1.8+, в клиент встроен автоматический механизм ретраев через JSON конфигурацию Service Config (`retryPolicy`), выполняющий повторы прозрачно на уровне транспортного слоя.

## Подводные камни

Ретраить неидемпотентные методы (например, `CreatePayment`): при сбое сети платеж может создаться дважды! Ретраить разрешено строго идемпотентные вызовы (`GET`, `PUT`, `DELETE`) либо методы с ключом идемпотентности (`Idempotency-Key`).

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя повторять запросы со статусом codes.Internal или codes.Unknown?»
**Ответ:** Потому что `Internal` означает программный сбой (баг, панику или нарушение инварианта в коде сервера). Повторный запрос с теми же входными данными гарантированно приведет к тому же самому падению, только увеличивая нагрузку на аварийный сервис.
