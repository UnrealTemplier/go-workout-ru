# Интерцепторы потоковых вызовов: реализация grpc.StreamServerInterceptor

## Условие

Создайте **Stream Server Interceptor** для логирования streaming-вызовов.

## Теория

Интерцепторы потоковых методов (Stream Interceptors):
- В отличие от унарного интерцептора, вызывающегося один раз на запрос, потоковый интерцептор перехватывает создание самого стрима:
  `type StreamServerInterceptor func(srv any, ss ServerStream, info *StreamServerInfo, handler StreamHandler) error`
- Паттерн ServerStream Wrapper:
  - Чтобы логировать каждое отдельное сообщение внутри стрима, интерцептор **оборачивает `grpc.ServerStream`** в собственную структуру:
    ```go
    type wrappedStream struct {
        grpc.ServerStream
    }
    func (w *wrappedStream) RecvMsg(m any) error { ... }
    func (w *wrappedStream) SendMsg(m any) error { ... }
    ```

## Решение по шагам

1. Напишите `LoggingStreamInterceptor`.
2. Создайте обертку структуры `wrappedStream`.
3. Переопределите `RecvMsg` и `SendMsg` для аудита сообщений.
4. Зарегистрируйте интерцептор через `grpc.StreamInterceptor`.

## Код решения

**`stream_interceptor_demo.go`**

```go
package main

import (
	"fmt"

	"google.golang.org/grpc"
)

// WrappedServerStream оборачивает стандартный стрим для перехвата сообщений
type WrappedServerStream struct {
	grpc.ServerStream
	methodName string
}

func (w *WrappedServerStream) RecvMsg(m any) error {
	err := w.ServerStream.RecvMsg(m)
	if err == nil {
		fmt.Printf("[Stream RECV] Метод: %s | Получено сообщение: %+v\n", w.methodName, m)
	}
	return err
}

func (w *WrappedServerStream) SendMsg(m any) error {
	err := w.ServerStream.SendMsg(m)
	if err == nil {
		fmt.Printf("[Stream SEND] Метод: %s | Отправлено сообщение: %+v\n", w.methodName, m)
	}
	return err
}

func LoggingStreamInterceptor(
	srv any,
	ss grpc.ServerStream,
	info *grpc.StreamServerInfo,
	handler grpc.StreamHandler,
) error {
	fmt.Printf("[Stream START] Инициализация стрима для метода: %s\n", info.FullMethod)

	wrapped := &WrappedServerStream{
		ServerStream: ss,
		methodName:   info.FullMethod,
	}

	err := handler(srv, wrapped)
	fmt.Printf("[Stream END] Завершение стрима %s | Ошибка: %v\n", info.FullMethod, err)
	return err
}

func main() {
	server := grpc.NewServer(
		grpc.StreamInterceptor(LoggingStreamInterceptor),
	)
	_ = server
	fmt.Println("Сервер gRPC успешно сконфигурирован со Stream Interceptor")
}
```

ℹ️ Обертка ServerStream для перехвата сообщений в потоке

**`Терминал`**

```bash

# Вывод:
# Сервер gRPC успешно сконфигурирован со Stream Interceptor
```

## Под капотом

Обертка реализует `grpc.ServerStream` через встраивание (Embedding). Методы `RecvMsg` и `SendMsg` являются фундаментальными низкоуровневыми методами gRPC, через которые проходят все сгенерированные вызовы `Recv()` и `Send()`.

## Подводные камни

Забывать передать обернутый `wrapped` стрим в `handler(srv, wrapped)`: если передать исходный `ss`, переопределенные методы `RecvMsg`/`SendMsg` никогда не вызовутся.

## На собеседовании

**Вопрос с собеседования:** «Как во Stream Interceptor подсчитать количество переданных байт в потоке?»
**Ответ:** В переопределенном методе `SendMsg(m any)` сериализовать сообщение во временный размер или проверить длину через интерфейс `proto.Size(m.(proto.Message))`, суммируя переданные байты в атомарном счетчике стрима.
