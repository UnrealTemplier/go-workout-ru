# Пакетная отправка 5 пользователей в Client Streaming и завершение CloseAndRecv

## Условие

Напиши клиент для Client Streaming: отправь 5 пользователей через `stream.Send()` в цикле, затем вызови `stream.CloseAndRecv()` для получения ответа.

## Теория

Циклическая отправка сущностей:
- Клиент формирует коллекцию записей.
- В цикле:
  ```go
  for _, u := range users {
      if err := stream.Send(u); err != nil {
          return err
      }
  }
  ```
- Затем разовый вызов `stream.CloseAndRecv()` получает итоговый агрегированный ответ.

## Решение по шагам

1. Создайте срез из 5 пользователей.
2. В цикле отправьте каждого через `stream.Send()`.
3. Завершите отправку методом `CloseAndRecv()`.
4. Проверьте соответствие счетчика.

## Код решения

**`send_five_users_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type UserPayload struct{ ID int32; Username string }
type ServerReport struct{ ProcessedCount int }

type MockStreamClient struct {
	buffer []*UserPayload
}

func (c *MockStreamClient) Send(u *UserPayload) error {
	c.buffer = append(c.buffer, u)
	return nil
}

func (c *MockStreamClient) CloseAndRecv() (*ServerReport, error) {
	return &ServerReport{ProcessedCount: len(c.buffer)}, nil
}

func TestSendFiveUsers(t *testing.T) {
	clientStream := &MockStreamClient{}

	names := []string{"Анна", "Борис", "Варвара", "Глеб", "Дарья"}
	for idx, name := range names {
		err := clientStream.Send(&UserPayload{ID: int32(idx + 1), Username: name})
		if err != nil {
			t.Fatalf("Ошибка отправки: %v", err)
		}
	}

	report, err := clientStream.CloseAndRecv()
	if err != nil {
		t.Fatalf("Ошибка ответа: %v", err)
	}

	if report.ProcessedCount != 5 {
		t.Fatalf("got %d; want 5", report.ProcessedCount)
	}

	fmt.Printf("Все 5 пользователей успешно отправлены и обработаны сервером!\n")
}
```

ℹ️ Отправка 5 пользователей через Client Streaming

## Под капотом

Каждый вызов `Send` упаковывается в независимый пакет Protobuf. Сериализация выполняется синхронно, а сетевая запись буферизируется для оптимизации TCP-пакетов (Nagle Algorithm отключен через `TCP_NODELAY`).

## Подводные камни

Не проверять ошибку `Send` на каждой итерации: если сервер уже закрыл соединение из-за ошибки валидации, последующие вызовы `Send` вернут ошибку.

## На собеседовании

**Вопрос с собеседования:** «Почему в gRPC по умолчанию включен TCP_NODELAY?»
**Ответ:** Чтобы исключить алгоритм Нейгла (Nagle's algorithm), который задерживает отправку маленьких пакетов до 40 миллисекунд для объединения их в один TCP-сегмент. В микросервисных RPC критически важна минимальная задержка (Sub-millisecond Latency), поэтому данные отсылаются в сокет немедленно.
