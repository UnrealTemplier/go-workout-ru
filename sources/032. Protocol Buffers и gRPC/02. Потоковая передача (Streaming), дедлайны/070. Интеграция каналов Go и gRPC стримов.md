# Интеграция каналов Go и gRPC стримов: паттерн Bridge Channel to gRPC Stream

## Условие

Создайте streaming-метод, который читает из канала Go и отправляет данные клиенту. Это паттерн "bridge channel to gRPC stream".

## Теория

Паттерн Bridge Channel to Stream:
- Микросервисы часто подписываются на внутренние каналы событий (Go channels из брокеров Kafka/NATS/RabbitMQ).
- Серверный метод gRPC перенаправляет события из `<-chan Event` в `stream.Send(event)`.
- Критически важна безопасная обработка двух параллельных событий:
  1. Новое сообщение в канале `case event, ok := <-eventChan:` (отправка клиенту, если `!ok` — завершение стрима).
  2. Отмена клиентом `case <-stream.Context().Done():` (немедленный выход для предотвращения утечки горутины).

## Решение по шагам

1. Создайте канал событий `chan string`.
2. Реализуйте цикл перенаправления с использованием `select`.
3. Обеспечьте корректный выход при закрытии канала или отмене контекста.
4. Протестируйте передачу событий.

## Код решения

**`bridge_channel_demo.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type EventDTO struct{ Text string }

func BridgeChannelToStream(ctx context.Context, in <-chan string, sendFunc func(*EventDTO) error) error {
	for {
		select {
		case <-ctx.Done():
			fmt.Println("Мост: клиент отменил контекст, завершаем отправку")
			return ctx.Err()
		case val, ok := <-in:
			if !ok {
				fmt.Println("Мост: входящий канал закрыт продюсером, закрываем стрим")
				return nil
			}
			if err := sendFunc(&EventDTO{Text: val}); err != nil {
				return fmt.Errorf("ошибка отправки в сокет: %w", err)
			}
		}
	}
}

func main() {
	eventQueue := make(chan string, 5)

	// Имитация продюсера событий (Kafka consumer)
	go func() {
		events := []string{"PAYMENT_INITIATED", "PAYMENT_AUTHORIZED", "ORDER_CONFIRMED"}
		for _, e := range events {
			eventQueue <- e
			time.Sleep(20 * time.Millisecond)
		}
		close(eventQueue)
	}()

	sendMock := func(e *EventDTO) error {
		fmt.Printf("  -> [gRPC Stream Out]: %s\n", e.Text)
		return nil
	}

	ctx := context.Background()
	err := BridgeChannelToStream(ctx, eventQueue, sendMock)
	if err != nil {
		panic(err)
	}
	fmt.Println("Паттерн Bridge успешно передал все события")
}
```

ℹ️ Паттерн безопасного моста между Go-каналом и gRPC стримом

**`Терминал`**

```bash
go run bridge_channel_demo.go
# Вывод:
#   -> [gRPC Stream Out]: PAYMENT_INITIATED
#   -> [gRPC Stream Out]: PAYMENT_AUTHORIZED
#   -> [gRPC Stream Out]: ORDER_CONFIRMED

# Паттерн Bridge успешно передал все события
```

## Под капотом

Такая конструкция гарантирует, что горутина gRPC обработчика не заблокируется навечно на чтении из `<-in`, если продюсер зависнет, так как ветка `case <-ctx.Done()` освободит ресурсы при разрыве TCP соединения.

## Подводные камни

Забывать отписаться от внутренней очереди (unsubscribe) в блоке `defer`: если клиент отключился, брокер продолжит слать сообщения в закрытый канал, вызывая панику.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если горутина продюсера пишет в небуферизированный канал, а клиентский стрим gRPC заблокирован медленной сетью?»
**Ответ:** Возникнет каскадная блокировка продюсера (Head-of-Line Blocking на уровне приложения). Чтобы изолировать продюсер от медленных gRPC клиентов, используют буферизированные каналы с политикой отбрасывания устаревших сообщений (Ring Buffer / Drop Slowest) или очередь в Redis/Kafka.
