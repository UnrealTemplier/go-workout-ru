# Серверные интерцепторы: логирование вызовов через grpc.UnaryServerInterceptor

## Условие

Добави **interceptor (unary)**: `func loggingInterceptor(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error)`. Логируй метод, длительность, ошибку. Зарегистрируй через `grpc.UnaryInterceptor(loggingInterceptor)`.

## Теория

Концепция интерцепторов в gRPC (Middleware):
- Интерцептор оборачивает исполнение каждого RPC вызова (паттерн «Декоратор / Обертка»).
- Сигнатура Unary интерцептора:
  `type UnaryServerInterceptor func(ctx context.Context, req any, info *UnaryServerInfo, handler UnaryHandler) (resp any, err error)`
- Параметры:
  - `info.FullMethod`: полное имя метода (например `/user.v1.UserService/GetUser`).
  - `handler(ctx, req)`: передача управления следующему интерцептору или целевому бизнес-методу.
- Измерение latency: замеряется через `start := time.Now(); resp, err := handler(ctx, req); duration := time.Since(start)`.

## Решение по шагам

1. Напишите функцию `loggingInterceptor`.
2. Замерьте время выполнения вызова.
3. Залогируйте имя метода, статус и задержку.
4. Зарегистрируйте интерцептор через `grpc.UnaryInterceptor`.

## Код решения

**`logging_interceptor.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"google.golang.org/grpc"
)

// LoggingUnaryInterceptor перехватывает все унарные вызовы на сервере
func LoggingUnaryInterceptor(
	ctx context.Context,
	req any,
	info *grpc.UnaryServerInfo,
	handler grpc.UnaryHandler,
) (any, error) {
	start := time.Now()

	// Передача управления бизнес-обработчику
	resp, err := handler(ctx, req)

	duration := time.Since(start)
	statusStr := "OK"
	if err != nil {
		statusStr = fmt.Sprintf("ERROR: %v", err)
	}

	fmt.Printf("[gRPC Access Log] Method=%s | Duration=%v | Status=%s\n",
		info.FullMethod, duration, statusStr)

	return resp, err
}

func main() {
	// Пример создания сервера с интерцептором:
	server := grpc.NewServer(
		grpc.UnaryInterceptor(LoggingUnaryInterceptor),
	)
	_ = server
	fmt.Println("gRPC сервер успешно сконфигурирован с Logging интерцептором")
}
```

ℹ️ Реализация интерцептора логирования времени выполнения

**`Терминал`**

```bash
go run logging_interceptor.go
# Вывод:
# gRPC сервер успешно сконфигурирован с Logging интерцептором
```

## Под капотом

Интерцепторы вызываются в той же горутине, что и сам RPC-хэндлер, что позволяет безопасно оборачивать вызовы в транзакции БД, распределенные трассировки OpenTelemetry и контекстные тайм-ауты.

## Подводные камни

Модифицировать `req` без синхронизации: если запрос читается параллельно, мутация полей в интерцепторе может вызвать состояние гонки (Data Race).

## На собеседовании

**Вопрос с собеседования:** «Как в gRPC интерцепторе перехватить панику (panic recovery)?»
**Ответ:** Обернуть вызов `handler(ctx, req)` в конструкцию с `defer func() { if r := recover(); r != nil { ... } }()`, залогировать стек-трейс с помощью `debug.Stack()` и вернуть клиенту стандартизированную gRPC ошибку `status.Errorf(codes.Internal, "внутренняя ошибка сервера")`.
