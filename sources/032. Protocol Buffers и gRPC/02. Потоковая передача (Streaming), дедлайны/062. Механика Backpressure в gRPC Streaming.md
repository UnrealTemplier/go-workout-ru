# Механика Backpressure в gRPC Streaming: переполнение буферов и HTTP/2 Window Update

## Условие

Изучите проблему "backpressure" в streaming: что будет, если сервер генерирует данные быстрее, чем клиент успевает их читать? (TCP-буферы переполнятся, соединение разорвется).

## Теория

Управление противодавлением (Backpressure) в gRPC:
- Что происходит, если сервер генерирует 100 000 сообщений в секунду, а клиент обрабатывает только 100?
  1. Буфер отправки сокета сервера заполняется.
  2. Буфер приема TCP клиента переполняется.
  3. Протокол HTTP/2 имеет встроенный механизм Flow Control:
     - Окно передачи (Stream/Connection Flow Control Window).
     - Клиент разрешает серверу слать данные только в пределах открытого окна (`WINDOW_UPDATE`).
     - Если окно исчерпано, очередной вызов `stream.Send()` на сервере **блокируется**!
- Сервер автоматически замедляет генерацию до скорости самого медленного клиента, исключая аварии OOM.

## Решение по шагам

1. Смоделируйте быстрый генератор данных.
2. Подключите медленный обработчик с задержкой.
3. Продемонстрируйте блокировку отправки при заполнении буфера канала.
4. Объясните действие Flow Control в HTTP/2.

## Код решения

**`backpressure_simulation.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	// Буфер канала эмулирует размер окна HTTP/2 (Window Size)
	windowSize := 3
	flowControlPipe := make(chan int, windowSize)

	// Быстрый продюсер (сервер)
	go func() {
		for i := 1; i <= 6; i++ {
			fmt.Printf("[Сервер] Попытка отправить пакет #%d...\n", i)
			flowControlPipe <- i // БЛОКИРУЕТСЯ, когда буфер полон!
			fmt.Printf("[Сервер] Пакет #%d успешно отправлен в сокет\n", i)
		}
		close(flowControlPipe)
	}()

	// Даем серверу заполнить окно
	time.Sleep(50 * time.Millisecond)
	fmt.Println("\n--- Окно передачи заполнено, сервер заблокирован противодавлением ---")

	// Медленный консьюмер (клиент)
	for packet := range flowControlPipe {
		fmt.Printf("  [Клиент] Обработка пакета #%d (задержка 40 мс)\n", packet)
		time.Sleep(40 * time.Millisecond) // Освобождение окна
	}

	fmt.Println("Все пакеты безопасно доставлены без переполнения памяти")
}
```

## Под капотом

Размер окна по умолчанию в HTTP/2 составляет 65 535 байт (может увеличиваться до 2 ГБ через фреймы `WINDOW_UPDATE`). Если медленный клиент не вычитывает сокет, TCP Zero Window и HTTP/2 Window Size замораживают отправку на стороне ядра Linux.

## Подводные камни

Копить неотправленные сообщения в неограниченном слайсе в памяти сервера: если клиент завис, сервер упадет по OOM. Всегда полагайтесь на синхронную блокировку `stream.Send()`.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Flow Control на уровне Stream от Flow Control на уровне Connection в gRPC HTTP/2?»
**Ответ:** Flow Control на уровне Stream изолирует конкретный RPC вызов: если один стрим заблокирован медленным клиентом, остальные параллельные стримы в том же TCP-соединении продолжают передавать данные на максимальной скорости. Connection Flow Control защищает общий TCP сокет от переполнения суммарным трафиком всех стримов.
