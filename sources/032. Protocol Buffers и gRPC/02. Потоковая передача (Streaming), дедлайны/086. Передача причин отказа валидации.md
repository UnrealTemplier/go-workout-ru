# Передача причин отказа валидации: интеграция google.rpc.Status и структуры BadRequest

## Условие

Используйте богатые детали ошибки (`google.rpc.Status`): при ошибке валидации прикрепите к статусу `BadRequest` с информацией о поле, вызвавшем ошибку.

## Теория

Проектирование API с информативными ошибками:
- При интеграции со сторонними клиентами (Frontend SPA, iOS/Android) плохой практикой является возврат абстрактного `Invalid parameter`.
- Информативный ответ содержит:
  1. `Field`: точный JSON-путь к невалидному атрибуту (например, `order.items[0].quantity`).
  2. `Description`: локализованное описание причины отказа (`количество товара должно быть больше 0`).
- Это позволяет фронтенду мгновенно подсветить конкретное поле ввода красной рамкой без ручного разбора строк в regex.

## Решение по шагам

1. Создайте структуру ошибки валидации.
2. Задайте путь к вложенному полю `order.delivery_address.zip_code`.
3. Прикрепите деталь `errdetails.BadRequest`.
4. Проверьте разбор на клиенте.

## Код решения

**`nested_field_validation_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"google.golang.org/genproto/googleapis/rpc/errdetails"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func ValidateOrderZipCode(zipCode string) error {
	if len(zipCode) != 6 {
		st := status.New(codes.InvalidArgument, "ошибка валидации заказа")
		br := &errdetails.BadRequest{
			FieldViolations: []*errdetails.BadRequest_FieldViolation{
				{
					Field:       "order.delivery_address.zip_code",
					Description: "почтовый индекс в РФ должен состоять строго из 6 цифр",
				},
			},
		}
		detailedSt, _ := st.WithDetails(br)
		return detailedSt.Err()
	}
	return nil
}

func TestNestedFieldValidation(t *testing.T) {
	err := ValidateOrderZipCode("123")
	if err == nil {
		t.Fatal("Ожидалась ошибка валидации индекса")
	}

	st, ok := status.FromError(err)
	if !ok {
		t.Fatal("Ошибка не является статусом gRPC")
	}

	for _, detail := range st.Details() {
		if br, ok := detail.(*errdetails.BadRequest); ok {
			for _, fv := range br.GetFieldViolations() {
				fmt.Printf("Нарушение валидации во вложенном объекте:\n")
				fmt.Printf("  Путь:     %s\n", fv.GetField())
				fmt.Printf("  Описание: %s\n", fv.GetDescription())
			}
		}
	}
}
```

ℹ️ Валидация глубоко вложенных полей с передачей точного пути

## Под капотом

Использование точных путей `order.delivery_address.zip_code` соответствует спецификации Google AIP-193 (API Improvement Proposals), принятой за основу построения современных REST/gRPC шлюзов.

## Подводные камни

Писать в поле `Field` русскоязычный текст вместо системного пути: поле `Field` должно быть машиночитаемым идентификатором атрибута, а человекочитаемый текст помещается в `Description`.

## На собеседовании

**Вопрос с собеседования:** «Какая стандартная структура из errdetails используется для передачи локализованных сообщений пользователю на его родном языке?»
**Ответ:** Структура `errdetails.LocalizedMessage{Locale: "ru-RU", Message: "Неверный пароль"}`. Она позволяет серверу возвращать уже переведенные строки в зависимости от заголовка `Accept-Language`, избавляя мобильный клиент от необходимости поддерживать локализацию системных ошибок.
