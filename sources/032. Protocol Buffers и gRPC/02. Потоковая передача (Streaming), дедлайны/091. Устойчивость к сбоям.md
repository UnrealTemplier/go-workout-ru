# Устойчивость к сбоям: Recovery Interceptor для перехвата паник и возврат codes.Internal

## Условие

Реализуйте interceptor для recovery (аналог middleware Recovery в HTTP): перехватывайте `panic` в хендлерах и возвращайте `codes.Internal`.

## Теория

Защита gRPC сервера от аварийного падения процесса:
- Необработанная паника (`panic("nil pointer")`) в горутине обработчика gRPC аварийно завершает весь процесс Go (`os.Exit(2)`), роняя весь микросервис.
- Паттерн Recovery Interceptor:
  - Оборачивает вызов `handler(ctx, req)` в функцию с `defer func() { if r := recover(); r != nil { ... } }()`.
  - Логирует стек-трейс паники (`debug.Stack()`).
  - Переводит аварию в контролируемый gRPC статус:
    `status.Errorf(codes.Internal, "внутренняя ошибка сервера")`
  - Процесс сервера продолжает стабильно работать!

## Решение по шагам

1. Напишите `RecoveryUnaryServerInterceptor`.
2. Используйте `recover()` в блоке `defer`.
3. Залогируйте стек вызова.
4. Проверьте перехват паники в unit-тесте.

## Код решения

**`recovery_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"runtime/debug"
	"testing"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func RecoveryUnaryInterceptor(
	ctx context.Context,
	req any,
	info *grpc.UnaryServerInfo,
	handler grpc.UnaryHandler,
) (resp any, err error) {
	defer func() {
		if r := recover(); r != nil {
			stackTrace := string(debug.Stack())
			fmt.Printf("[CRITICAL PANIC RECOVERED] Method: %s | Panic: %v\n", info.FullMethod, r)
			_ = stackTrace // В production отправляется в Sentry / ELK

			// Возвращаем клиенту безопасную ошибку без утечки внутренних деталей
			err = status.Errorf(codes.Internal, "внутренняя ошибка сервера (panic recovered)")
		}
	}()

	return handler(ctx, req)
}

func TestRecoveryInterceptor(t *testing.T) {
	panickingHandler := func(ctx context.Context, req any) (any, error) {
		var ptr *int
		*ptr = 42 // Намеренная паника: nil pointer dereference!
		return nil, nil
	}

	info := &grpc.UnaryServerInfo{FullMethod: "/test.v1.TestService/CrashMethod"}

	resp, err := RecoveryUnaryInterceptor(context.Background(), nil, info, panickingHandler)
	if resp != nil {
		t.Fatalf("Ожидался nil response")
	}

	st, ok := status.FromError(err)
	if !ok || st.Code() != codes.Internal {
		t.Fatalf("Ожидался код ошибки Internal, получено: %v", err)
	}

	fmt.Printf("Паника успешно локализована интерцептором: [%s] %s\n", st.Code(), st.Message())
}
```

ℹ️ Локализация паники в горутине RPC и возврат статуса codes.Internal

## Под капотом

`debug.Stack()` извлекает стек вызовов текущей горутины, позволяя инженеру точно определить номер строки исходного кода, где произошло разыменование nil-указателя.

## Подводные камни

Возвращать клиенту сырой текст паники и стек-трейс: это раскрывает злоумышленникам внутреннее устройство системы (Information Disclosure Vulnerability). Клиенту возвращают только общий статус `Internal`.

## На собеседовании

**Вопрос с собеседования:** «Почему паника в фоновой горутине, запущенной внутри gRPC метода (go func() { panic(...) }()), не перехватывается интерцептором?»
**Ответ:** Потому что ключевое слово `recover()` перехватывает паники **строго в рамках той же самой горутины**, где объявлен `defer`. Если метод порождает отдельную горутину `go worker()`, внутри этой горутины ОБЯЗАН быть собственный независимый `defer func() { recover() }()`, иначе процесс упадет.
