# Клиентский разбор Rich Errors: приведение details[0] к errdetails.BadRequest и печать полей

## Условие

На стороне клиента извлеки детали из ошибки: `st, _ := status.FromError(err); details := st.Details()`. Приведи `details[0]` к типу `*errdetails.BadRequest` и выведи информацию о нарушенных полях.

## Теория

Разбор структурированных ошибок на клиенте:
- Получив ошибку от RPC-вызова:
  1. `st, ok := status.FromError(err)`
  2. `details := st.Details()` — возвращает срез `[]any`.
  3. Проверка типа первого элемента:
     `badRequest, ok := details[0].(*errdetails.BadRequest)`
  4. Обход нарушений:
     `for _, violation := range badRequest.GetFieldViolations() { ... }`
- Позволяет фронтенду и мобильным приложениям отображать точечные подсказки под каждым полем ввода.

## Решение по шагам

1. Создайте структурированную ошибку `BadRequest`.
2. Извлеките детали через `st.Details()`.
3. Выполните приведение типа к `*errdetails.BadRequest`.
4. Распечатайте имена некорректных полей.

## Код решения

**`client_error_details_parser_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"google.golang.org/genproto/googleapis/rpc/errdetails"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func CreateSampleRichError() error {
	st := status.New(codes.InvalidArgument, "ошибка проверки формы профиля")
	br := &errdetails.BadRequest{
		FieldViolations: []*errdetails.BadRequest_FieldViolation{
			{Field: "age", Description: "возраст не может быть отрицательным"},
			{Field: "inn", Description: "ИНН должен содержать 10 или 12 цифр"},
		},
	}
	detailedStatus, _ := st.WithDetails(br)
	return detailedStatus.Err()
}

func TestClientRichErrorExtraction(t *testing.T) {
	err := CreateSampleRichError()

	st, ok := status.FromError(err)
	if !ok {
		t.Fatal("Ошибка не gRPC")
	}

	details := st.Details()
	if len(details) == 0 {
		t.Fatal("Детали ошибки отсутствуют")
	}

	badRequest, ok := details[0].(*errdetails.BadRequest)
	if !ok {
		t.Fatalf("Первая деталь не является *errdetails.BadRequest, тип: %T", details[0])
	}

	fmt.Printf("Код: %s | Статус: %s\n", st.Code(), st.Message())
	fmt.Printf("Количество нарушений: %d\n", len(badRequest.GetFieldViolations()))

	for idx, violation := range badRequest.GetFieldViolations() {
		fmt.Printf("  [%d] Поле: %-5s -> Причина: %s\n",
			idx+1, violation.GetField(), violation.GetDescription())
	}
}
```

ℹ️ Разбор первого элемента деталей ошибки *errdetails.BadRequest

## Под капотом

`st.Details()` десериализует байты из трейлера `grpc-status-details-bin` через функцию `proto.Unmarshal()`. Если структура была упакована через Any, рантайм инстанциирует реальный тип Go.

## Подводные камни

Обращаться к `details[0]` без проверки `if len(details) > 0`: если сервер вернул простую ошибку без деталей, возникнет паника `index out of range [0]`.

## На собеседовании

**Вопрос с собеседования:** «Какие еще типы деталей кроме BadRequest входят в стандарт google.rpc.errdetails?»
**Ответ:** 
- `PreconditionFailure`: нарушение бизнес-состояния (например, аккаунт заблокирован).
- `ResourceInfo`: точный идентификатор отсутствующего ресурса (`resource_type: "User"`, `resource_name: "usr_100"`).
- `QuotaFailure`: квота превышена (`violations: { subject: "client_ip", description: "limit 100 rps" }`).
- `DebugInfo`: стек-трейс для внутренней разработки.
