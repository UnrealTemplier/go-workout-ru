# Декларативная политика повторов: настройка Retry Policy через JSON Service Config

## Условие

Реализуй **retry policy** в клиенте: `grpc.WithDefaultServiceConfig(`{"methodConfig":[{"name":[{"service":"user.UserService"}],"retryPolicy":{"maxAttempts":3,"initialBackoff":"0.1s","maxBackoff":"1s","backoffMultiplier":2,"retryableStatusCodes":["UNAVAILABLE"]}}]}`)`. Покажи автоматический retry.

## Теория

Встроенный механизм автоматических повторов (Native gRPC Retries):
- Вместо написания кастомных интерцепторов gRPC поддерживает спецификацию **Service Config (gRFC A6)**:
  ```json
  {
    "methodConfig": [{
      "name": [{"service": "user.UserService"}],
      "retryPolicy": {
        "maxAttempts": 3,
        "initialBackoff": "0.1s",
        "maxBackoff": "1s",
        "backoffMultiplier": 2,
        "retryableStatusCodes": ["UNAVAILABLE"]
      }
    }]
  }
  ```
- Библиотека gRPC автоматически выполняет повторы со статусом `UNAVAILABLE`, выдерживая экспоненциальную паузу с джиттером.

## Решение по шагам

1. Сформируйте валидный JSON Service Config.
2. Передайте опцию `grpc.WithDefaultServiceConfig(cfg)`.
3. Зарегистрируйте соединение.
4. Продемонстрируйте конфигурацию.

## Код решения

**`service_config_retry_demo.go`**

```go
package main

import (
	"encoding/json"
	"fmt"

	"google.golang.org/grpc"
)

func main() {
	// Декларативная конфигурация повторов gRPC Service Config
	retryPolicyConfig := `{
		"methodConfig": [{
			"name": [{"service": "user.v1.UserService"}],
			"retryPolicy": {
				"maxAttempts": 3,
				"initialBackoff": "0.1s",
				"maxBackoff": "1s",
				"backoffMultiplier": 2.0,
				"retryableStatusCodes": ["UNAVAILABLE"]
			}
		}]
	}`

	// Проверка валидности JSON синтаксиса:
	var parsedConfig map[string]any
	if err := json.Unmarshal([]byte(retryPolicyConfig), &parsedConfig); err != nil {
		panic(err)
	}

	clientOption := grpc.WithDefaultServiceConfig(retryPolicyConfig)
	_ = clientOption

	fmt.Println("gRPC Service Config успешно скомпилирован:")
	fmt.Println("  Целевой сервис: user.v1.UserService")
	fmt.Println("  Максимум попыток: 3 (при статусе UNAVAILABLE)")
	fmt.Println("  Экспоненциальный Backoff: от 100ms до 1s (множитель 2.0)")
}
```

ℹ️ Декларативная настройка нативных повторов gRPC

**`Терминал`**

```bash

```

## Под капотом

Service Config может динамически доставляться с DNS сервера через TXT записи или централизованно из Control Plane (Envoy xDS / Istio), позволяя менять политики ретраев на лету без пересборки бинарников.

## Подводные камни

Указывать `maxAttempts` больше 5: спецификация gRPC запрещает ставить более 5 попыток во избежание перегрузки инфраструктуры.

## На собеседовании

**Вопрос с собеседования:** «Что такое Hedging в gRPC Service Config и чем он отличается от Retries?»
**Ответ:** Retries повторяет вызов ПОСЛЕ получения ошибки. Hedging посылает второй параллельный запрос ДО завершения первого, если первый запрос превысил \(P99\) задержку (`hedgingDelay: 200ms`). Первый вернувшийся успешный ответ отдается клиенту, а второй отменяется, что срезает длинный хвост латентности (Tail Latency).
