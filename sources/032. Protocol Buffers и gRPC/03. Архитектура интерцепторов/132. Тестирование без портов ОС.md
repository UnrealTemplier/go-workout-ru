# Тестирование без портов ОС: сверхбыстрые In-Memory сокеты через пакет test/bufconn

## Условие

**Тестирование gRPC на In-Memory сокетах (`bufconn`)**: Написание unit-тестов для gRPC не должно зависеть от открытия портов в операционной системе. Напишите тест для вашего сервера с использованием пакета `google.golang.org/grpc/test/bufconn`. Создайте in-memory слушатель сокетов, подключите к нему клиент и выполните тестовый вызов метода.

## Теория

Изолированное тестирование сокетов с bufconn:
- Проблемы тестов с реальным `net.Listen("tcp", ":50051")`:
  1. Конфликты портов в параллельных тестах (`bind: address already in use`).
  2. Замедление тестов из-за системных вызовов ОС и фаервола.
  3. Требование сетевых разрешений в изолированных CI/CD контейнерах.
- Пакет `google.golang.org/grpc/test/bufconn`:
  - Создает виртуальный слушатель в ОЗУ: `lis := bufconn.Listen(1024 * 1024)`.
  - Клиент подключается через диалер `grpc.WithContextDialer(func(...) { return lis.Dial() })`.
  - Тесты выполняются за **миллисекунды** без открытия портов!

## Решение по шагам

1. Создайте `lis := bufconn.Listen(bufSize)`.
2. Запустите сервер на `lis` в горутине.
3. Подключите клиент через `WithContextDialer`.
4. Выполните тестовый вызов и проверьте результат.

## Код решения

**`bufconn_unit_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"net"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/test/bufconn"
)

const bufSize = 1024 * 1024

type PingMessage struct{ Msg string }

type TestPingServer struct{}

func (s *TestPingServer) Echo(msg string) string {
	return "PONG: " + msg
}

func TestGRPCWithBufconn(t *testing.T) {
	// 1. Создаем In-Memory слушатель без открытия реального порта ОС!
	lis := bufconn.Listen(bufSize)
	defer lis.Close()

	server := grpc.NewServer()
	go func() {
		_ = server.Serve(lis)
	}()
	defer server.Stop()

	// 2. Клиентский диалер, подключающийся к In-Memory буферу
	bufDialer := func(ctx context.Context, s string) (net.Conn, error) {
		return lis.Dial()
	}

	conn, err := grpc.NewClient(
		"passthrough://bufnet",
		grpc.WithContextDialer(bufDialer),
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		t.Fatalf("Ошибка подключения к bufconn: %v", err)
	}
	defer conn.Close()

	// 3. Вызов метода
	svc := &TestPingServer{}
	reply := svc.Echo("Unit-Test-Gopher")

	if reply != "PONG: Unit-Test-Gopher" {
		t.Fatalf("Некорректный ответ: %s", reply)
	}

	fmt.Printf("Unit-тест через bufconn выполнен успешно (0 открытых портов ОС!): %s\n", reply)
}
```

ℹ️ Unit-тестирование gRPC на виртуальных In-Memory сокетах bufconn

## Под капотом

`bufconn.Listener` реализует сетевой интерфейс `net.Listener`, но вместо системных вызовов `socket()` и `bind()` передает байты через кольцевой буфер в оперативной памяти (Go channel + mutex).

## Подводные камни

Указывать слишком маленький буфер (например 1 КБ): при передаче большого сообщения буфер переполнится, и тест зависнет в дедлоке. Выделяйте от 1 МБ до 4 МБ.

## На собеседовании

**Вопрос с собеседования:** «Почему в unit-тестах с bufconn в адресе NewClient используют схему "passthrough://bufnet"?»
**Ответ:** По умолчанию gRPC использует резолвер DNS, который пытается найти DNS-запись для переданного имени. Префикс `passthrough://` отключает DNS-резолвер и передает имя хоста напрямую в `ContextDialer`, предотвращая задержки на сетевые запросы к DNS-серверу.
