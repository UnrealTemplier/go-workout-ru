# Архитектура Service Mesh: абстракция сетевых адресов через локальный Sidecar Proxy (Envoy)

## Условие

Настрой **service mesh** (упрощённо): клиент коннектится к `localhost:50051` (sidecar proxy, например Envoy). Proxy маршрутизирует на реальные сервисы. Покажи, что клиент не знает о реальных адресах.

## Теория

Принцип работы Service Mesh (Envoy Sidecar Proxy):
- В микросервисной архитектуре клиентскому коду не нужно знать, где физически запущен целевой сервис (на каком хосте или в каком датацентре).
- Клиент всегда обращается к локальному прокси:
  `grpc.NewClient("127.0.0.1:15001")` (Sidecar Envoy).
- Envoy берет на себя:
  1. Service Discovery (Consul / Kubernetes).
  2. TLS шифрование (mTLS).
  3. Маршрутизацию (Canary 90/10, A/B тесты).
  4. Автоматические повторы и Circuit Breaking.
  5. Сбор метрик и трассировку.
- Go-код остается чистым и не содержит сложной инфраструктурной логики.

## Решение по шагам

1. Смоделируйте локальный Sidecar Proxy.
2. Направьте клиентский вызов на `127.0.0.1`.
3. Реализуйте перенаправление прокси на реальный бэкенд.
4. Продемонстрируйте прозрачность для клиента.

## Код решения

**`service_mesh_proxy_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// RealBackend представляет реальный сервис в удаленном датацентре
type RealBackend struct {
	DC string
}

func (b *RealBackend) HandleRequest(query string) string {
	return fmt.Sprintf("Ответ от реального кластера [%s]: %s", b.DC, query)
}

// SidecarProxy симулирует Envoy, запущенный в том же сетевом пространстве (localhost)
type SidecarProxy struct {
	UpstreamDC1 *RealBackend
	UpstreamDC2 *RealBackend
	routeToDC2  bool
}

func (p *SidecarProxy) Forward(ctx context.Context, query string) string {
	// Envoy выполняет умную маршрутизацию (например канареечный релиз в DC-2)
	if p.routeToDC2 {
		return p.UpstreamDC2.HandleRequest(query)
	}
	return p.UpstreamDC1.HandleRequest(query)
}

func TestServiceMeshSidecarPattern(t *testing.T) {
	proxy := &SidecarProxy{
		UpstreamDC1: &RealBackend{DC: "dc-spb-prod-01"},
		UpstreamDC2: &RealBackend{DC: "dc-msk-canary-02"},
	}

	// Клиент обращается СТРОГО к localhost proxy, не зная IP адресов датацентров!
	resp1 := proxy.Forward(context.Background(), "SELECT user_profile")
	fmt.Println("Клиент получил через Sidecar:", resp1)

	// Включаем канареечный релиз в прокси
	proxy.routeToDC2 = true
	resp2 := proxy.Forward(context.Background(), "SELECT user_profile")
	fmt.Println("Клиент получил через Sidecar (Canary):", resp2)
}
```

## Под капотом

В Kubernetes Sidecar запускается в том же Pod через общий `network namespace` (`netns`). Трафик между Go-приложением и Envoy идет через локальный loopback интерфейс `lo` с нулевой задержкой (менее 0.1 мс).

## Подводные камни

Хардкодить прямые IP-адреса удаленных подов в клиенте: при перезапуске подов их IP меняются, что приведет к аварии соединения.

## На собеседовании

**Вопрос с собеседования:** «В чем недостаток архитектуры Sidecar Proxy по сравнению с библиотечным Client-Side Load Balancing?»
**Ответ:** Sidecar Proxy добавляет дополнительный сетевой транзитный шаг (Hop) через сокет `localhost`, потребляет дополнительную память (по 50–100 МБ на каждый под) и требует процессорного времени на повторную обработку HTTP/2 фреймов. Для сверхнизких задержек (< 1 мс) крупные компании (Google, Uber) используют gRPC Proxyless Service Mesh (xDS API прямо в коде Go без Envoy).
