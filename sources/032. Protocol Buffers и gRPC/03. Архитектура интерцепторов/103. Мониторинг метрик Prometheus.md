# Мониторинг метрик Prometheus: счетчики вызовов и распределение статус-кодов в интерцепторе

## Условие

Создайте interceptor для метрик: инкрементируйте счетчики Prometheus для каждого RPC-метода и статуса.

## Теория

Экспорт метрик gRPC в Prometheus (Golden Signals):
- Канонические метрики gRPC:
  1. `grpc_server_handled_total{grpc_method="...", grpc_code="..."}` (Counter): общее количество обработанных запросов.
  2. `grpc_server_handling_seconds{grpc_method="..."}` (Histogram): гистограмма задержек.
  3. `grpc_server_msg_received_total` (Counter): количество входящих потоковых сообщений.
- Интерцептор инкрементирует счетчик при завершении каждого запроса, обеспечивая мониторинг доступности сервиса (Error Rate, Availability SLO).

## Решение по шагам

1. Создайте структуру счетчиков метрик.
2. Напишите `MetricsUnaryInterceptor`.
3. Инкрементируйте счетчик с лейблами метода и кода статуса.
4. Проверьте агрегацию метрик.

## Код решения

**`prometheus_metrics_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type MetricsRegistry struct {
	mu       sync.Mutex
	counters map[string]int64
}

func NewMetricsRegistry() *MetricsRegistry {
	return &MetricsRegistry{counters: make(map[string]int64)}
}

func (r *MetricsRegistry) Inc(method, code string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	key := fmt.Sprintf("grpc_server_handled_total{method=%q,code=%q}", method, code)
	r.counters[key]++
}

func PrometheusUnaryInterceptor(registry *MetricsRegistry) grpc.UnaryServerInterceptor {
	return func(
		ctx context.Context,
		req any,
		info *grpc.UnaryServerInfo,
		handler grpc.UnaryHandler,
	) (any, error) {
		resp, err := handler(ctx, req)

		st := status.Convert(err)
		registry.Inc(info.FullMethod, st.Code().String())

		return resp, err
	}
}

func TestPrometheusInterceptor(t *testing.T) {
	registry := NewMetricsRegistry()
	interceptor := PrometheusUnaryInterceptor(registry)

	okHandler := func(ctx context.Context, req any) (any, error) { return "OK", nil }
	errHandler := func(ctx context.Context, req any) (any, error) {
		return nil, status.Error(codes.NotFound, "not found")
	}

	info := &grpc.UnaryServerInfo{FullMethod: "/catalog.v1.Catalog/GetProduct"}

	// 2 успешных запроса и 1 ошибка
	_, _ = interceptor(context.Background(), nil, info, okHandler)
	_, _ = interceptor(context.Background(), nil, info, okHandler)
	_, _ = interceptor(context.Background(), nil, info, errHandler)

	fmt.Println("Собранные метрики Prometheus:")
	registry.mu.Lock()
	for k, v := range registry.counters {
		fmt.Printf("  %s = %d\n", k, v)
	}
	registry.mu.Unlock()
}
```

## Под капотом

В реальных проектах используется библиотека `github.com/grpc-ecosystem/go-grpc-prometheus`, которая автоматически регистрирует все стандартные гистограммы и счетчики одной строкой.

## Подводные камни

Добавлять User ID или Request ID в лейблы метрик Prometheus: это приводит к катастрофическому росту размерности (High Cardinality Explosion) и падению сервера Prometheus по памяти.

## На собеседовании

**Вопрос с собеседования:** «Почему в метриках Prometheus нельзя использовать произвольные строки ошибок в качестве лейбла?»
**Ответ:** Текст ошибки `err.Error()` содержит уникальные ID (`user_id=12345 не найден`), что создает бесконечное число уникальных временных рядов (Time Series), перегружая индекс Prometheus. Лейблом должен быть СТРОГО фиксированный enum код статуса gRPC (`codes.NotFound`), чье количество ограничено 16 значениями.
