# Клиентский Retry Interceptor: автоматический перезапуск при ошибке codes.Unavailable

## Условие

Напишите interceptor для автоматического retry при определенных ошибках (например, `codes.Unavailable`).

## Теория

Паттерн надежности Client-Side Retry Interceptor:
- Клиентский интерцептор может повторить вызов `invoker(ctx, method, req, reply, cc, opts...)` несколько раз при возникновении переходных сетевых ошибок (`codes.Unavailable`).
- Правила безопасного повтора:
  1. Ограничение количества попыток (например, не более 3).
  2. Проверка контекста: если `ctx.Err() != nil` (таймаут истек), повторы немедленно прекращаются.
  3. Повторяются только идемпотентные вызовы.

## Решение по шагам

1. Создайте `RetryClientInterceptor`.
2. В цикле вызывайте `invoker`.
3. При статусе `codes.Unavailable` сделайте паузу и повторите попытку.
4. Проверьте успешное восстановление.

## Код решения

**`retry_interceptor_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

func RetryUnaryClientInterceptor(maxAttempts int) grpc.UnaryClientInterceptor {
	return func(
		ctx context.Context,
		method string,
		req, reply any,
		cc *grpc.ClientConn,
		invoker grpc.UnaryInvoker,
		opts ...grpc.CallOption,
	) error {
		var lastErr error
		for attempt := 1; attempt <= maxAttempts; attempt++ {
			err := invoker(ctx, method, req, reply, cc, opts...)
			if err == nil {
				return nil
			}

			st, ok := status.FromError(err)
			if ok && st.Code() == codes.Unavailable {
				lastErr = err
				fmt.Printf("[Client Retry] Попытка %d не удалась (Unavailable). Повторяем...\n", attempt)
				time.Sleep(10 * time.Millisecond)
				continue
			}

			// Другие ошибки не ретраим
			return err
		}
		return lastErr
	}
}

func TestRetryInterceptor(t *testing.T) {
	attempts := 0
	fakeInvoker := func(ctx context.Context, method string, req, reply any, cc *grpc.ClientConn, opts ...grpc.CallOption) error {
		attempts++
		if attempts < 3 {
			return status.Error(codes.Unavailable, "сервис временно недоступен")
		}
		return nil
	}

	interceptor := RetryUnaryClientInterceptor(3)
	err := interceptor(context.Background(), "/api.v1/Method", nil, nil, nil, fakeInvoker)
	if err != nil {
		t.Fatalf("Ожидался успех после ретраев, ошибка: %v", err)
	}

	if attempts != 3 {
		t.Fatalf("Ожидалось 3 попытки, выполнено: %d", attempts)
	}

	fmt.Println("Интерцептор успешно выполнил повторные попытки и завершил вызов")
}
```

## Под капотом

Клиентский интерцептор находится выше уровня транспортного пула соединений. Повторный вызов `invoker` может прозрачно использовать другое активное TCP-соединение из пула балансировщика, если первое соединение разорвалось.

## Подводные камни

Мутировать указатель `reply` без очистки перед повторной попыткой: если первый сбойный вызов успел частично заполнить структуру `reply`, перед повторным вызовом необходимо вызывать `proto.Reset(reply.(proto.Message))`.

## На собеседовании

**Вопрос с собеседования:** «Что такое Retry Storm и как его предотвратить?»
**Ответ:** Retry Storm возникает, когда сервис под высокой нагрузкой начинает отвечать медленно, вызывая таймауты. Тысячи клиентов начинают одновременно слать повторные запросы, увеличивая RPS в 3–5 раз и окончательно добивая сервис. Для защиты используют **Retry Budget** (например, библиотека `grpc-ecosystem/go-grpc-middleware` разрешает тратить на повторы не более 10% от общего числа успешных запросов).
