# Многослойная архитектура фильтров: каскадирование интерцепторов через grpc.ChainUnaryInterceptor

## Условие

Используйте `grpc.ChainUnaryInterceptor` для применения нескольких interceptor'ов в цепочке.

## Теория

Композиция сквозной функциональности:
- В реальном микросервисе на каждый вызов накладываются требования:
  1. `Tracing`: инициализация спана трассировки.
  2. `Recovery`: перехват паник.
  3. `Logging`: запись времени и статуса.
  4. `Auth`: валидация JWT токена.
  5. `Validator`: проверка полей Protobuf.
- `grpc.ChainUnaryInterceptor` объединяет их в строгом порядке, обеспечивая модульность и соблюдение принципа Single Responsibility.

## Решение по шагам

1. Создайте функции-интерцепторы.
2. Объедините их через `grpc.ChainUnaryInterceptor`.
3. Подключите к `grpc.NewServer()`.
4. Убедитесь в чистоте архитектуры.

## Код решения

**`layered_interceptors.go`**

```go
package main

import (
	"context"
	"fmt"

	"google.golang.org/grpc"
)

func TracerMiddleware(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	fmt.Println("[1. Tracing] Генерация TraceID: a1b2c3d4")
	return handler(ctx, req)
}

func AuthMiddleware(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	fmt.Println("[2. Security] Токен аутентифицирован успешно")
	return handler(ctx, req)
}

func ValidationMiddleware(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
	fmt.Println("[3. Validation] Входные параметры проверены")
	return handler(ctx, req)
}

func main() {
	server := grpc.NewServer(
		grpc.ChainUnaryInterceptor(
			TracerMiddleware,
			AuthMiddleware,
			ValidationMiddleware,
		),
	)
	_ = server

	fmt.Println("Сконфигурирован gRPC сервер с 3 слоями защиты (Tracing -> Auth -> Validation)")
}
```

ℹ️ Каскадная цепочка интерцепторов на сервере

**`Терминал`**

```bash
go run layered_interceptors.go
# Вывод:
# Сконфигурирован gRPC сервер с 3 слоями защиты (Tracing -> Auth -> Validation)
```

## Под капотом

`ChainUnaryInterceptor` инкапсулирует вызовы в цепочку замыканий (Closure Chain), исключая выделение дополнительных структур данных в куче рантайма при каждом запросе.

## Подводные камни

Помещать `AuthMiddleware` перед `TracerMiddleware`: если запрос отклонен из-за невалидного токена, трассировка не запишется, и инженеры не увидят попытку неавторизованного доступа в Jaeger.

## На собеседовании

**Вопрос с собеседования:** «Каков рекомендованный порядок интерцепторов в продакшн gRPC сервере?»
**Ответ:** 1. `Panic Recovery` (снаружи, чтобы ловить любые паники) \(\to\) 2. `Tracing / OpenTelemetry` \(\to\) 3. `Prometheus Metrics` \(\to\) 4. `Access Logging` \(\to\) 5. `Rate Limiting` \(\to\) 6. `Authentication / Authorization` \(\to\) 7. `Validation` \(\to\) 8. `Business Handler`.
