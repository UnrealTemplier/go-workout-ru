# Канонический Unary Server Interceptor: замер задержки, имя метода и код ответа

## Условие

**Unary Server Interceptor (Логирование)**: Напиши функцию, соответствующую сигнатуре `grpc.UnaryServerInterceptor`. Засеки время старта, вызови `handler(ctx, req)`, логируй имя метода (из `info.FullMethod`), потраченное время и ошибку. Передай интерцептор при создании сервера.

## Теория

Шаблон логирования унарных запросов:
- Сигнатура:
  `func(ctx context.Context, req any, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error)`
- Этапы:
  1. `start := time.Now()`
  2. `resp, err := handler(ctx, req)`
  3. `duration := time.Since(start)`
  4. Форматированный лог с именем метода `info.FullMethod`.
- Подключение:
  `grpc.NewServer(grpc.UnaryInterceptor(MyInterceptor))`.

## Решение по шагам

1. Напишите `AccessLogInterceptor`.
2. Замерьте время исполнения.
3. Проверьте статус ошибки.
4. Продемонстрируйте логирование.

## Код решения

**`canonical_unary_logger_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/status"
)

func AccessLogInterceptor(
	ctx context.Context,
	req any,
	info *grpc.UnaryServerInfo,
	handler grpc.UnaryHandler,
) (any, error) {
	start := time.Now()

	resp, err := handler(ctx, req)

	duration := time.Since(start)
	code := status.Code(err)

	fmt.Printf("[ACCESS] %-30s | %-6s | %v\n",
		info.FullMethod, code.String(), duration.Round(time.Microsecond))

	return resp, err
}

func TestCanonicalLogger(t *testing.T) {
	dummyHandler := func(ctx context.Context, req any) (any, error) {
		time.Sleep(5 * time.Millisecond)
		return "OK", nil
	}

	info := &grpc.UnaryServerInfo{FullMethod: "/user.v1.UserService/GetUser"}
	_, err := AccessLogInterceptor(context.Background(), nil, info, dummyHandler)
	if err != nil {
		t.Fatalf("Ошибка: %v", err)
	}
}
```

## Под капотом

Интерцептор выполняется в контексте входящего HTTP/2 запроса, гарантируя линейность выполнения и корректную передачу стека контекста.

## Подводные камни

Использовать `fmt.Println` в горячем цикле при высоких RPS: стандартный вывод консоли в Linux блокирует дескриптор stdout. Используйте асинхронные логгеры.

## На собеседовании

**Вопрос с собеседования:** «Как интерцептор взаимодействует с контекстом запроса?»
**Ответ:** Интерцептор получает `ctx` от рантайма gRPC и может либо передать его дальше в `handler(ctx, req)`, либо создать дочерний контекст с новыми значениями (`context.WithValue`) или сокращенным таймаутом (`context.WithTimeout`).
