# Потоковая передача тяжелых файлов блоками по 64 КБ: UploadFile и метод SendAndClose

## Условие

**Client Streaming**: Опиши: `rpc UploadFile (stream FileChunk) returns (UploadStatus);`. Напиши клиента, который читает большой файл с диска по 64КБ и отправляет куски серверу. Сервер собирает файл и в конце возвращает финальный статус через `stream.SendAndClose()`.

## Теория

Промышленный шаблон загрузки тяжелых бинарных данных (Chunked File Upload):
- Передача файлов через REST Base64 увеличивает объем на 33% и требует парсинга в ОЗУ.
- gRPC Client Streaming:
  - Чтение файла блоками по 64 КБ (`buffer := make([]byte, 64*1024)`).
  - Отправка в бинарном виде без конвертации в текст: `stream.Send(&FileChunk{Data: buffer[:n]})`.
  - Сервер записывает чанки напрямую в целевой файл на диске или в S3 через Multipart Upload.
  - Потребление памяти как клиента, так и сервера фиксировано на уровне 64 КБ вне зависимости от размера файла (хоть 10 ГБ).

## Решение по шагам

1. Создайте буфер размером 64 КБ.
2. В цикле считывайте куски данных.
3. Отправляйте их в `stream.Send()`.
4. На сервере собирайте данные и финализируйте через `SendAndClose()`.

## Код решения

**`chunked_file_upload_test.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"testing"
)

type FileChunkDTO struct {
	Content []byte
}

type UploadFinalStatus struct {
	BytesSaved int64
	Chunks     int
}

type ChunkedUploadStreamMock struct {
	chunks []*FileChunkDTO
	status *UploadFinalStatus
}

func (s *ChunkedUploadStreamMock) Send(c *FileChunkDTO) error {
	s.chunks = append(s.chunks, c)
	return nil
}

func (s *ChunkedUploadStreamMock) SendAndClose(st *UploadFinalStatus) error {
	s.status = st
	return nil
}

func ServerReceiveFile(stream *ChunkedUploadStreamMock) error {
	var total int64
	for _, chunk := range stream.chunks {
		total += int64(len(chunk.Content))
	}
	return stream.SendAndClose(&UploadFinalStatus{
		BytesSaved: total,
		Chunks:     len(stream.chunks),
	})
}

func TestChunkedFileUpload(t *testing.T) {
	// Имитация файла размером 192 КБ (ровно 3 чанка по 64 КБ)
	filePayload := bytes.Repeat([]byte("X"), 192*1024)
	reader := bytes.NewReader(filePayload)

	stream := &ChunkedUploadStreamMock{}
	chunkBuffer := make([]byte, 64*1024) // 64 KB буфер

	for {
		n, err := reader.Read(chunkBuffer)
		if n > 0 {
			chunkCopy := make([]byte, n)
			copy(chunkCopy, chunkBuffer[:n])
			_ = stream.Send(&FileChunkDTO{Content: chunkCopy})
		}
		if err == io.EOF {
			break
		}
	}

	_ = ServerReceiveFile(stream)

	if stream.status.BytesSaved != 192*1024 {
		t.Fatalf("Ожидалось 192 КБ, сохранено: %d", stream.status.BytesSaved)
	}
	if stream.status.Chunks != 3 {
		t.Fatalf("Ожидалось 3 чанка, получено: %d", stream.status.Chunks)
	}

	fmt.Printf("Файл успешно передан: %d байт в %d чанках по 64 КБ\n",
		stream.status.BytesSaved, stream.status.Chunks)
}
```

## Под капотом

Размер 64 КБ выбран как оптимальный баланс: он кратен размеру страницы памяти ОС (4 КБ), идеально ложится в стандартное окно HTTP/2 Flow Control Window (65 535 байт) и минимизирует системные вызовы ядра Linux.

## Подводные камни

Переиспользовать один и тот же срез байт `chunkBuffer` без создания копии при асинхронной отправке: горутина отправщика может перезаписать данные в буфере до того, как сетевой сокет закончил отправку предыдущего чанка.

## На собеседовании

**Вопрос с собеседования:** «Как в gRPC Client Streaming передать метаданные файла (имя, расширение, автора) вместе с чанками байт?»
**Ответ:** Использовать конструкцию `oneof` в Protobuf сообщении:
```protobuf
message FileUploadRequest {
  oneof data {
    FileMetadata metadata = 1; // Первое сообщение стрима
    bytes chunk = 2;           // Все последующие сообщения
  }
}
```
Клиент первым сообщением шлет структуру `metadata`, а в цикле отправляет сырые байты `chunk`.
