# Клиентский лимит grpc.MaxCallRecvMsgSize: переопределение для приема сообщений более 4 МБ

## Условие

**Ограничение размера сообщения**: По умолчанию gRPC запрещает принимать сообщения больше 4 МБ. Попробуй передать кусок файла на 5 МБ — получишь ошибку. Настрой клиента и сервер, передав опцию `grpc.MaxCallRecvMsgSize()` при инициализации.

### Исходная формулировка

## Теория

Симметрия лимитов размера на клиенте и сервере:
- Ошибка возникает не только на сервере, но и на клиенте:
  `rpc error: code = ResourceExhausted desc = grpc: received message larger than max (5242880 vs. 4194304)`
- Если сервер готов отдать 5 МБ, а клиент использует дефолтные настройки:
  - Клиент упадет с ошибкой при чтении ответа!
- Решение:
  Настроить клиент через `grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(10 * 1024 * 1024))`.

## Решение по шагам

1. Настройте лимит на стороне сервера через `grpc.MaxSendMsgSize(10MB)`.
2. Настройте лимит на стороне клиента через `grpc.MaxCallRecvMsgSize(10MB)`.
3. Убедитесь в отсутствии ошибок `ResourceExhausted`.
4. Протестируйте передачу 5 МБ.

## Код решения

**`symmetric_limits_demo.go`**

```go
package main

import (
	"fmt"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

func main() {
	limit10MB := 10 * 1024 * 1024

	// 1. Конфигурация сервера:
	server := grpc.NewServer(
		grpc.MaxRecvMsgSize(limit10MB),
		grpc.MaxSendMsgSize(limit10MB),
	)
	_ = server

	// 2. Конфигурация клиента:
	conn, err := grpc.NewClient(
		"127.0.0.1:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithDefaultCallOptions(
			grpc.MaxCallRecvMsgSize(limit10MB),
			grpc.MaxCallSendMsgSize(limit10MB),
		),
	)
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	fmt.Println("Симметричные лимиты 10 МБ успешно настроены как на клиенте, так и на сервере!")
}
```

## Под капотом

Лимит `MaxCallRecvMsgSize` проверяется клиентским парсером кадров HTTP/2. Если заголовок фрейма больше лимита, чтение прерывается без аллокации памяти под буфер.

## Подводные камни

Настраивать лимит только для конкретного вызова `client.GetFile(ctx, req, grpc.MaxCallRecvMsgSize(...))` и забыть настроить дефолтные опции `WithDefaultCallOptions`: другие методы продолжат падать с ошибкой.

## На собеседовании

**Вопрос с собеседования:** «Каковы риски установки слишком большого MaxRecvMsgSize (например 256 МБ) на сервере gRPC?»
**Ответ:** Если 100 одновременных клиентов пришлют по 256 МБ, серверу потребуется \(100 \times 256 = 25.6\) ГБ оперативной памяти только на хранение сырых сообщений, что вызовет немедленный Linux OOM Killer и падение процесса.
