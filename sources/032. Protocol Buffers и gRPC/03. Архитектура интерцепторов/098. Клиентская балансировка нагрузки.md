# Клиентская балансировка нагрузки: round_robin в Service Config и DNS Resolver

## Условие

Настрой **load balancing** в клиенте: `grpc.WithDefaultServiceConfig(`{"loadBalancingPolicy":"round_robin"}`)`. Используй **DNS resolver** с несколькими A-записями. Покажи распределение запросов.

## Теория

Балансировка нагрузки на стороне клиента (Client-Side Load Balancing):
- В традиционном REST балансировщик (L4/L7 прокси вроде NGINX) стоит между клиентом и серверами.
- Проблема в gRPC: gRPC держит **одно постоянное TCP соединение**. Обычный L4 балансировщик перенаправит все запросы строго на один и тот же под!
- **Решение gRPC Client-Side Load Balancing:**
  1. Клиент разрешает имя сервиса через DNS (`dns:///my-service:50051`), получая список IP всех реплик.
  2. Клиент открывает постоянное HTTP/2 соединение **к каждому поду**.
  3. Политика `round_robin`: каждый новый RPC-вызов отправляется на следующий под по кругу.

## Решение по шагам

1. Настройте `serviceConfig` с политикой `"round_robin"`.
2. Сконфигурируйте резолвер адресов.
3. Продемонстрируйте циклическое распределение запросов.
4. Проверьте балансировку между тремя репликами.

## Код решения

**`load_balancing_demo.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"

	"google.golang.org/grpc"
)

type BackendNode struct {
	Address string
	Hits    int64
}

type RoundRobinBalancer struct {
	nodes   []*BackendNode
	counter uint64
}

func (b *RoundRobinBalancer) Pick() *BackendNode {
	idx := atomic.AddUint64(&b.counter, 1) % uint64(len(b.nodes))
	node := b.nodes[idx]
	atomic.AddInt64(&node.Hits, 1)
	return node
}

func main() {
	// 1. Декларативная конфигурация для gRPC Client:
	serviceConfig := `{"loadBalancingPolicy":"round_robin"}`
	clientOpt := grpc.WithDefaultServiceConfig(serviceConfig)
	_ = clientOpt

	// 2. Симуляция работы Round-Robin на 3 инстансах сервиса
	balancer := &RoundRobinBalancer{
		nodes: []*BackendNode{
			{Address: "10.0.1.10:50051"},
			{Address: "10.0.1.11:50051"},
			{Address: "10.0.1.12:50051"},
		},
	}

	fmt.Println("Распределение 6 последовательных gRPC вызовов:")
	for i := 1; i <= 6; i++ {
		picked := balancer.Pick()
		fmt.Printf("  Запрос #%d отправлен на реплику: %s\n", i, picked.Address)
	}

	fmt.Println("\nИтоговая статистика попаданий по подам:")
	for _, n := range balancer.nodes {
		fmt.Printf("  %s: %d вызовов\n", n.Address, n.Hits)
	}
}
```

## Под капотом

Схема `dns:///` подключает резолвер, который периодически запрашивает SRV и A-записи DNS сервера (например CoreDNS в Kubernetes). Балансировщик клиента `picker` динамически добавляет новые поды при автоскейлинге (HPA).

## Подводные камни

Подключаться к обычному Kubernetes ClusterIP без Headless Service (`clusterIP: None`): обычный ClusterIP возвращает один виртуальный IP kube-proxy, ломая клиентскую балансировку.

## На собеседовании

**Вопрос с собеседования:** «Почему в Kubernetes для gRPC требуется headless-сервис (ClusterIP: None)?»
**Ответ:** Потому что обычный ClusterIP разрешает DNS-имя сервиса ровно в один виртуальный VIP-адрес, из-за чего gRPC клиент открывает ровно одно HTTP/2 соединение к одному случайному поду, перегружая его на 100%. Headless-сервис возвращает клиенту список IP-адресов ВСЕХ живых подов, позволяя клиенту балансировать вызовы методом `round_robin`.
