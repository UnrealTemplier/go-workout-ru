# Проблема балансировки gRPC за L4-балансировщиком (K8s Service) и ее решение

## Условие

Напишите разбор проблемы залипания gRPC-соединений на L4 (Kubernetes ClusterIP/kube-proxy) и реализуйте клиентскую балансировку с использованием headless service и round_robin политики gRPC.

### Исходная формулировка

**Проблема зависших соединений за L4-балансировщиком**: Напишите архитектурный комментарий, объясняющий проблему балансировки gRPC в K8s [651]. Почему при масштабировании количества реплик gRPC-сервера вверх или вниз стандартный балансировщик L4 (K8s Service ClusterIP) не может перераспределить существующий трафик (так как gRPC удерживает долгоиграющие TCP-соединения, и все запросы от клиента продолжают идти на один и тот же под) [651].

## Теория

Стандартный сервис Kubernetes (`type: ClusterIP`) работает на 4-м уровне модели OSI (Транспортный уровень). kube-proxy настраивает правила iptables/IPVS, которые распределяют запросы при создании TCP-соединения (пакет SYN). Для классического HTTP/1.1 с частым открытием соединений это работает сносно. Однако gRPC использует HTTP/2, где клиент открывает одно постоянное TCP соединение и мультиплексирует миллионы запросов внутри него. В результате gRPC-клиент подключается к одному случайному поду и шлет весь последующий трафик только туда! Масштабирование реплик сервера никак не разгрузит этот под. Решения проблемы: 1) Использование L7 прокси (Envoy, Istio, Linkerd); 2) Клиентская балансировка gRPC через Headless Service (`clusterIP: None`) с резолвером DNS и политикой `round_robin`.

## Решение по шагам

Определите схему Headless Service в K8s без ClusterIP.
Настройте gRPC Dial с использованием схемы dns:///service-name:port.
Установите опцию grpc.WithDefaultServiceConfig с политикой round_robin.
Убедитесь, что клиент резолвит все IP-адреса подов и распределяет запросы поочередно.

## Код решения

**`client_round_robin.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

// DialHeadlessService подключается к Kubernetes Headless сервису с клиентской балансировкой Round Robin
func DialHeadlessService(targetDNS string) (*grpc.ClientConn, error) {
	// JSON конфигурация gRPC для включения round_robin балансировки
	// Вместо отправки всего трафика в один TCP сокет, клиент откроет соединения ко всем A-записям DNS
	serviceConfig := `{
		"loadBalancingConfig": [
			{
				"round_robin": {}
			}
		]
	}`

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	conn, err := grpc.DialContext(
		ctx,
		// Префикс dns:/// заставляет gRPC опрашивать SRV/A записи адреса
		fmt.Sprintf("dns:///%s", targetDNS),
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithDefaultServiceConfig(serviceConfig),
	)
	if err != nil {
		return nil, fmt.Errorf("dial failed: %w", err)
	}

	return conn, nil
}

func main() {
	// В K8s адрес выглядит как: "my-grpc-service.default.svc.cluster.local:50051"
	target := "localhost:50051"
	log.Printf("Connecting to %s with client-side Round Robin...", target)

	conn, err := DialHeadlessService(target)
	if err != nil {
		log.Printf("[Demo] Connection expectedly postponed: %v", err)
		return
	}
	defer conn.Close()

	fmt.Println("Client-side round-robin load balancing configured.")
}
```

ℹ️ Клиентская балансировка gRPC с резолвингом адресов всех реплик

## Под капотом

При указании `round_robin` резолвер gRPC регулярно перечитывает DNS A-записи домена. Для каждого обнаруженного IP адреса gRPC создает отдельный саб-канал (`SubConn`). Пикер (`Picker`) распределяет каждый отдельный вызов RPC по кругу между активными саб-каналами.

## Подводные камни

Использование обычного K8s Service с ClusterIP вместо Headless. Обычный сервис возвращает единый виртуальный ClusterIP, поэтому DNS-резолвер gRPC увидит ровно один адрес и балансировка работать не будет.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Почему в Kubernetes gRPC трафик перегружает один под, игнорируя остальные?' Ответ: 'Потому что kube-proxy работает на уровне L4 (TCP). gRPC устанавливает одно мультиплексированное HTTP/2 соединение. После завершения TCP handshake L4 балансировщик больше не участвует в маршрутизации сообщений. Требуется L7-балансировка (Envoy/Service Mesh) либо клиентский Round Robin через Headless Service'.
