# B3 Headers (Zipkin): конвертация между W3C Trace Context и форматом B3

## Условие

Реализуйте двусторонний транслятор заголовков трассировки между W3C (traceparent) и Zipkin B3 (X-B3-TraceId, X-B3-SpanId, X-B3-Sampled и single b3).

### Исходная формулировка

**B3 headers (Zipkin)**: Изучите B3 headers (используются в Istio):
* `X-B3-TraceId`
* `X-B3-SpanId`
* `X-B3-ParentSpanId`
* `X-B3-Sampled`

## Теория

До принятия стандарта W3C Trace Context де-факто отраслевым стандартом была спецификация Zipkin B3 Propagation. Она до сих пор широко используется в Spring Cloud, Istio, Envoy и старых микросервисах. Формат B3 существует в двух видах: 1) Multiple headers: `X-B3-TraceId` (16 или 32 hex), `X-B3-SpanId` (16 hex), `X-B3-Sampled` ('1' или '0'), `X-B3-ParentSpanId`; 2) Single header: `b3: {TraceId}-{SpanId}-{SamplingState}-{ParentSpanId}`. В гетерогенных архитектурах при переходе на OpenTelemetry шлюз обязан поддерживать бесшовную конвертацию между B3 и W3C, чтобы старые Java/Spring сервисы и новые Go сервисы продолжали видеть единый граф вызовов.

## Решение по шагам

Определите структуру TraceInfo с полями TraceID, SpanID, Sampled.
Реализуйте чтение как W3C traceparent, так и B3 headers из HTTP-запроса.
Реализуйте генерацию заголовков обоих стандартов.
Проверьте трансляцию входящего B3 заголовка в исходящий traceparent.

## Код решения

**`b3_converter.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"strings"
)

type CanonicalTrace struct {
	TraceID string
	SpanID  string
	Sampled bool
}

// ExtractTrace универсально извлекает трейс из W3C traceparent или Zipkin B3
func ExtractTrace(r *http.Request) *CanonicalTrace {
	// 1. Проверяем W3C traceparent
	if tp := r.Header.Get("traceparent"); tp != "" {
		parts := strings.Split(tp, "-")
		if len(parts) == 4 {
			return &CanonicalTrace{
				TraceID: parts[1],
				SpanID:  parts[2],
				Sampled: parts[3] == "01",
			}
		}
	}

	// 2. Проверяем Single header b3
	if b3 := r.Header.Get("b3"); b3 != "" {
		parts := strings.Split(b3, "-")
		if len(parts) >= 2 {
			sampled := false
			if len(parts) >= 3 && parts[2] == "1" {
				sampled = true
			}
			traceID := parts[0]
			// Если TraceID в B3 16 hex, дополняем ведущими нулями до 32 hex стандарта W3C
			if len(traceID) == 16 {
				traceID = "0000000000000000" + traceID
			}
			return &CanonicalTrace{
				TraceID: traceID,
				SpanID:  parts[1],
				Sampled: sampled,
			}
		}
	}

	// 3. Проверяем Multiple B3 headers
	if b3Trace := r.Header.Get("X-B3-TraceId"); b3Trace != "" {
		if len(b3Trace) == 16 {
			b3Trace = "0000000000000000" + b3Trace
		}
		return &CanonicalTrace{
			TraceID: b3Trace,
			SpanID:  r.Header.Get("X-B3-SpanId"),
			Sampled: r.Header.Get("X-B3-Sampled") == "1",
		}
	}

	return nil
}

// InjectW3C проставляет заголовок traceparent
func (t *CanonicalTrace) InjectW3C(req *http.Request) {
	flags := "00"
	if t.Sampled {
		flags = "01"
	}
	req.Header.Set("traceparent", fmt.Sprintf("00-%s-%s-%s", t.TraceID, t.SpanID, flags))
}

// InjectB3Single проставляет единый заголовок b3
func (t *CanonicalTrace) InjectB3Single(req *http.Request) {
	sampleFlag := "0"
	if t.Sampled {
		sampleFlag = "1"
	}
	req.Header.Set("b3", fmt.Sprintf("%s-%s-%s", t.TraceID, t.SpanID, sampleFlag))
}

func main() {
	// Входящий запрос со старым B3 заголовком (от Istio/Spring Cloud)
	inReq, _ := http.NewRequest("GET", "/api/order", nil)
	inReq.Header.Set("X-B3-TraceId", "4bf92f3577b34da6a3ce929d0e0e4736")
	inReq.Header.Set("X-B3-SpanId", "00f067aa0ba902b7")
	inReq.Header.Set("X-B3-Sampled", "1")

	trace := ExtractTrace(inReq)
	fmt.Printf("Extracted trace: ID=%s, Span=%s, Sampled=%v\n", trace.TraceID, trace.SpanID, trace.Sampled)

	// Формируем исходящий вызов в новый микросервис с W3C заголовком
	outReq, _ := http.NewRequest("POST", "/api/payment", nil)
	trace.InjectW3C(outReq)
	fmt.Println("Converted outgoing W3C traceparent:", outReq.Header.Get("traceparent"))
}
```

ℹ️ Универсальный транслятор между Zipkin B3 и W3C Trace Context

## Под капотом

Исторически Zipkin поддерживал 64-битные Trace ID (16 hex символов). W3C строго требует 128 бит (32 hex). При конвертации 64-битный ID выравнивается 16 ведущими нулями слева (`0000000000000000{traceid}`), что сохраняет числовую идентичность при поиске в Jaeger.

## Подводные камни

Отбрасывание старших 16 байт при обратной конвертации 128-битного W3C Trace ID в 64-битный B3. Это вызовет коллизию идентификаторов в старых системах.
