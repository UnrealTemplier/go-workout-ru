# Graceful Connection Draining в gRPC: обработка активных и отклонение новых вызовов

## Условие

Реализуйте в gRPC сервере перехват SIGTERM с вызовом server.GracefulStop(). Убедитесь, что сервер отклоняет новые входящие вызовы, но дает завершиться активным стримам.

### Исходная формулировка

**[Graceful Connection Draining]**: В `main()` перехвати `SIGTERM`. Вызови `server.GracefulStop()`. Убедись, что сервер перестает принимать *новые* соединения, но дорабатывает *текущие* активные стримы.

## Теория

В gRPC вызов `server.GracefulStop()` выполняет строгий протокольный цикл Connection Draining: 1) Сервер немедленно закрывает слушающий TCP порт (net.Listener.Close), делая невозможным открытие новых TCP соединений; 2) Для всех активных клиентских соединений сервер шлет HTTP/2 кадр `GOAWAY` с `ErrCodeNo` (0x0). Этот кадр запрещает клиенту создавать новые HTTP/2 стримы поверх существующего соединения; 3) Сервер продолжает обрабатывать уже начатые унарные запросы и активные стримы; 4) Когда последний активный RPC метод возвращает результат и отправляет TRAILERS кадр, сервер мягко закрывает TCP сокет; 5) Метод `GracefulStop()` разблокируется и возвращает управление в `main()`.

## Решение по шагам

Инициализируйте gRPC сервер с долгим имитационным RPC методом.
Запустите сервер в горутине.
Перехватите сигнал SIGTERM в main.
Вызовите server.GracefulStop() и зафиксируйте успешное завершение долгого запроса.

## Код решения

**`grpc_draining_complete.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"

	"google.golang.org/grpc"
)

type WorkerService struct {
	activeCalls atomic.Int64
}

func (s *WorkerService) ProcessLongTask(ctx context.Context) error {
	s.activeCalls.Add(1)
	defer s.activeCalls.Add(-1)

	log.Println("[RPC] Starting long task (takes 2 seconds)...")
	select {
	case <-time.After(2 * time.Second):
		log.Println("[RPC] Long task completed successfully.")
		return nil
	case <-ctx.Done():
		log.Println("[RPC] Task canceled by client.")
		return ctx.Err()
	}
}

func main() {
	lis, err := net.Listen("tcp", ":50054")
	if err != nil {
		log.Fatalf("Listen error: %v", err)
	}

	server := grpc.NewServer()
	svc := &WorkerService{}

	go func() {
		log.Println("[gRPC] Server running on :50054")
		if err := server.Serve(lis); err != nil {
			log.Printf("[gRPC] Serve ended: %v", err)
		}
	}()

	// Имитируем активный фоновый запрос в процессе работы
	go func() {
		time.Sleep(200 * time.Millisecond)
		_ = svc.ProcessLongTask(context.Background())
	}()

	// Ожидаем сигнала остановки
	sig := make(chan os.Signal, 1)
	signal.Notify(sig, syscall.SIGINT, syscall.SIGTERM)

	// Имитируем получение SIGTERM через 500мс
	go func() {
		time.Sleep(500 * time.Millisecond)
		sig <- syscall.SIGTERM
	}()

	<-sig
	log.Println("[SIGTERM] Initiating server.GracefulStop()...")

	start := time.Now()
	// GracefulStop заблокируется до завершения активного таска
	server.GracefulStop()
	elapsed := time.Since(start)

	log.Printf("[gRPC] GracefulStop finished in %v. Active calls remaining: %d\n", elapsed, svc.activeCalls.Load())
	fmt.Println("gRPC connection draining successfully validated.")
}
```

ℹ️ Практическая демонстрация gRPC GracefulStop с завершением активных задач

## Под капотом

Внутри рантайма gRPC ведется счетчик `serveWG` (sync.WaitGroup). Каждый входящий стрим инкрементирует счетчик при создании и декрементирует при вызове `closeStream`. Метод `GracefulStop` делает `lis.Close()` и ждет `s.serveWG.Wait()`.

## Подводные камни

Вызов `os.Exit(0)` сразу после перехвата сигнала в main. Это немедленно прерывает процесс ядра, убивая все горутины и сокеты без выполнения `defer` и GracefulStop.

## На собеседовании

Вопрос на собеседовании в Kasperskу: 'В чем разница между server.GracefulStop() и server.Stop()?' Ответ: 'GracefulStop() перестает принимать новые запросы, шлет GOAWAY и блокируется до завершения всех активных RPC. Stop() немедленно закрывает все открытые сокеты, сбрасывая активные стримы ошибкой Unavailable'.
