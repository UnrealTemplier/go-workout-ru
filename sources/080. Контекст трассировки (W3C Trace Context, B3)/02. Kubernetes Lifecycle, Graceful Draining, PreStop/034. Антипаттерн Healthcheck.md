# Антипаттерн Healthcheck: Liveness vs Readiness и опасность проверки БД в LivenessProbe

## Условие

Создайте отказоустойчивые эндпоинты /livez и /readyz. Объясните, почему проверка доступности PostgreSQL в livenessProbe является грубейшим антипаттерном, приводящим к каскадному падению всего кластера.

### Исходная формулировка

**Антипаттерн Healthcheck (Liveness vs Readiness)**: Многие новички проверяют подключение к БД в `livenessProbe`. Если БД моргнула, K8s убьет и перезапустит твой Go-под. Это КАТАСТРОФА (поднимется под, БД лежит, он снова упадет — CrashLoopBackOff).
Напиши правильные хендлеры:
* `/live` (Liveness) — возвращает 200 OK всегда, пока сам процесс жив.
* `/ready` (Readiness) — проверяет пинг до БД. Если БД лежит — возвращает 503 (под перестает получать HTTP трафик, но **не перезапускается**!).

## Теория

Один из самых разрушительных антипаттернов в Kubernetes: включение `db.PingContext()` в `livenessProbe`. Что происходит при кратковременной перегрузке или сетевом сбое БД: 1) БД перестает отвечать за таймаут; 2) `livenessProbe` на всех 100 подах микросервиса возвращает 500 Internal Server Error; 3) kubelet делает вывод: 'Приложение зависло!' и одновременно убивает и перезапускает все 100 подов! 4) При старте все 100 подов начинают одновременно инициализироваться, загружать кэши и долбить и без того перегруженную БД сотнями новых TCP-подключений (Thundering Herd / Connection Storm); 5) БД окончательно падает, а поды уходят в бесконечный CrashLoopBackOff! ПРАВИЛО: LivenessProbe проверяет ТОЛЬКО локальный процесс Go (отсутствие дедлока, доступность рантайма). Внешние зависимости (PostgreSQL, Kafka, Redis) проверяются ИСКЛЮЧИТЕЛЬНО в ReadinessProbe!

## Решение по шагам

Реализуйте /livez с минимальной проверкой жизнеспособности локального процесса.
Реализуйте /readyz с асинхронной проверкой внешних ресурсов и коротким таймаутом.
Добавьте Circuit Breaker / кеширование статуса БД, чтобы не перегружать базу частыми проверками готовности.
Проверьте изоляцию сбоев БД от перезапуска подов.

## Код решения

**`resilient_probes.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
	"sync/atomic"
	"time"
)

type ProbeManager struct {
	dbHealthy atomic.Bool
}

func (pm *ProbeManager) SetupEndpoints(mux *http.ServeMux) {
	// LIVENESS: Проверяет ТОЛЬКО рантайм Go. Никаких внешних баз данных!
	// Если процесс отвечает — он жив. Рестарт не требуется.
	mux.HandleFunc("/livez", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ALIVE"))
	})

	// READINESS: Проверяет готовность обслуживать трафик (включая БД).
	// При сбое БД возвращает 503: трафик снимается, но под НЕ УБИВАЕТСЯ!
	mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
		if !pm.dbHealthy.Load() {
			http.Error(w, "Database unavailable, removing from load balancer", http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})
}

// BackgroundDBChecker периодически проверяет БД в фоне без блокировки HTTP зондов
func (pm *ProbeManager) StartBackgroundHealthcheck(ctx context.Context) {
	go func() {
		ticker := time.NewTicker(3 * time.Second)
		defer ticker.Stop()

		for {
			select {
			case <-ctx.Done():
				return
			case <-ticker.C:
				// Имитируем ping к базе данных
				err := mockDatabasePing(ctx)
				pm.dbHealthy.Store(err == nil)
			}
		}
	}()
}

func mockDatabasePing(ctx context.Context) error {
	// Имитация успешного ответа
	return nil
}

func main() {
	pm := &ProbeManager{}
	pm.dbHealthy.Store(true)

	mux := http.NewServeMux()
	pm.SetupEndpoints(mux)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	pm.StartBackgroundHealthcheck(ctx)

	log.Println("Probes listening on :8082: /livez (runtime only) and /readyz (dependencies)")
	fmt.Println("Liveness and Readiness probes configured following cloud-native best practices.")
}
```

ℹ️ Строгое разделение LivenessProbe (рантайм) и ReadinessProbe (зависимости)

## Под капотом

kubelet проверяет Liveness и Readiness с независимой периодичностью. Отказ ReadinessProbe лишь изменяет статус PodReady в False, заставляя контроллер Service Endpoints удалить IP пода из маршрутизации. Память пода, открытые пулы и соединения при этом сохраняются.

## Подводные камни

Вызов синхронного `db.PingContext(ctx)` прямо в HTTP handler'е /readyz. При 10 нодах K8s, опрашивающих под каждые 2 секунды, база получит шквал холостых запросов. Проверку состояния внешних баз лучше выносить в отдельную фоновую горутину с обновлением atomic.Bool.

## На собеседовании

Вопрос на собеседовании в Авито: 'Почему нельзя делать проверку базы данных в livenessProbe?' Ответ: 'Потому что падение БД вызовет массовый перезапуск всех подов кластера. Рестарт не починит базу, но создаст лавинообразную нагрузку новыми подключениями при рестарте (Cascading Failure / Death Spiral). Проверка БД допустима только в ReadinessProbe'.
