# B3 Propagation: поддержка многозаголовочного формата Zipkin

## Условие

Реализуйте аналог для B3: заголовки X-B3-TraceId, X-B3-SpanId, X-B3-ParentSpanId, X-B3-Sampled. Напишите конвертер B3 <-> W3C Trace Context для сохранения непрерывной трассировки при обращении к устаревшим микросервисам.

### Исходная формулировка

**B3 Propagation (Zipkin).**: Реализуйте аналог для B3: заголовки `X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentSpanId`, `X-B3-Sampled`. Покажите, как B3 использует 64-bit IDs (vs 128-bit в W3C). Объясните, когда B3 нужен (legacy Zipkin), а когда W3C (OpenTelemetry, современный стандарт).

## Теория

Исторический стандарт B3 (созданный Zipkin) широко распространен в экосистемах Spring Cloud, Envoy и Istio. В формате B3 параметры передаются раздельными HTTP-заголовками: `X-B3-TraceId`: 16 или 32 hex символа; `X-B3-SpanId`: 16 hex символов; `X-B3-ParentSpanId`: 16 hex символов (опционально); `X-B3-Sampled`: '1' (сохранять) или '0' (игнорировать). При интеграции современного Go-сервиса с B3-сервисами критически важно уметь транслировать 64-битный B3 TraceID в 128-битный W3C TraceID (путем дополнения 16 ведущими нулями) и обратно.

## Решение по шагам

Определите структуру B3TraceContext со всеми полями Zipkin спецификации.
Реализуйте функцию ParseB3Headers для извлечения параметров из входящего запроса.
Напишите конвертер B3ToW3C, выравнивающий длину TraceID до 32 символов.
Напишите метод InjectB3 для простановки заголовков в исходящий HTTP-запрос.

## Код решения

**`b3_propagator.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"strings"
)

// B3TraceContext хранит идентификаторы формата Zipkin B3.
type B3TraceContext struct {
	TraceID      string // 16 или 32 hex символа
	SpanID       string // 16 hex символов
	ParentSpanID string // 16 hex символов
	Sampled      bool
}

// ParseB3Headers считывает семейство заголовков X-B3-*
func ParseB3Headers(h http.Header) (*B3TraceContext, bool) {
	traceID := h.Get("x-b3-traceid")
	spanID := h.Get("x-b3-spanid")
	if traceID == "" || spanID == "" {
		return nil, false
	}

	return &B3TraceContext{
		TraceID:      strings.ToLower(traceID),
		SpanID:       strings.ToLower(spanID),
		ParentSpanID: strings.ToLower(h.Get("x-b3-parentspanid")),
		Sampled:      h.Get("x-b3-sampled") == "1",
	}, true
}

// B3ToW3C преобразует B3 контекст в канонический W3C traceparent.
func (b *B3TraceContext) B3ToW3C() string {
	normalizedTraceID := b.TraceID
	// Если TraceID 64-битный (16 hex символов), дополняем нулями слева до 128 бит (32 hex)
	if len(normalizedTraceID) == 16 {
		normalizedTraceID = "0000000000000000" + normalizedTraceID
	}

	flags := "00"
	if b.Sampled {
		flags = "01"
	}

	return fmt.Sprintf("00-%s-%s-%s", normalizedTraceID, b.SpanID, flags)
}

// InjectB3 внедряет заголовки B3 в исходящий сетевой запрос.
func (b *B3TraceContext) InjectB3(req *http.Request) {
	req.Header.Set("x-b3-traceid", b.TraceID)
	req.Header.Set("x-b3-spanid", b.SpanID)
	if b.ParentSpanID != "" {
		req.Header.Set("x-b3-parentspanid", b.ParentSpanID)
	}
	if b.Sampled {
		req.Header.Set("x-b3-sampled", "1")
	} else {
		req.Header.Set("x-b3-sampled", "0")
	}
}

func main() {
	sampleHeader := http.Header{}
	sampleHeader.Set("x-b3-traceid", "4bf92f3577b34da6") // 64-bit ID
	sampleHeader.Set("x-b3-spanid", "00f067aa0ba902b7")
	sampleHeader.Set("x-b3-sampled", "1")

	b3Ctx, ok := ParseB3Headers(sampleHeader)
	if !ok {
		log.Fatal("Failed to parse B3")
	}

	w3cHeader := b3Ctx.B3ToW3C()
	fmt.Printf("Original B3 TraceID: %s\n", b3Ctx.TraceID)
	fmt.Printf("Converted W3C traceparent: %s\n", w3cHeader)
}
```

ℹ️ Парсинг B3 Multi-header и безопасное расширение 64-битного TraceID до W3C стандарта

## Под капотом

Zipkin исторически поддерживал 64-битные TraceID для экономии памяти в JVM. W3C спецификация требует строго 128 бит. Дополнение ведущими шестнадцатью нулями гарантирует, что при обратной конвертации в Zipkin 64-битное числовое представление TraceID не изменится.

## Подводные камни

Использование одиночного заголовка `b3: <trace>-<span>` без разделителей при обращении к библиотекам, ожидающим исключительно множественные заголовки `X-B3-*`. Рекомендуется дублировать контекст в обоих форматах при межсервисных вызовах.

## На собеседовании

Вопрос на собеседовании в Ozon: 'Почему в Jaeger спаны из сервиса на Go и сервиса на Spring Boot иногда не связываются в одно дерево?' Ответ: Классическая проблема рассинхронизации протоколов: Spring Boot по умолчанию слушал B3, а Go OTel SDK слал W3C `traceparent`. Решение: настройка композитного проброса `propagation.NewCompositeTextMapPropagator(propagation.TraceContext{}, b3.New())`.
