# gRPC Keepalive на стороне клиента: защита от тихого сброса соединений

## Условие

Настройте keepalive.ClientParameters: Time: 10s, Timeout: 3s, PermitWithoutStream: true. Объясните, как PING/PONG кадры предотвращают закрытие соединения NAT-шлюзами, межсетевыми экранами (stateful firewall) и Cloud Load Balancer'ами (AWS NLB, GCP ILB) при отсутствии активных RPC вызовов.

### Исходная формулировка

**gRPC Keepalive на стороне клиента.**: Настройте `keepalive.ClientParameters`: `Time: 10s`, `Timeout: 3s`, `PermitWithoutStream: true`. Проверьте, что при обрыве сети клиент обнаруживает мёртвое соединение и переподключается.

## Теория

Сетевые экраны, NAT-шлюзы и облачные балансировщики (AWS NLB, Google Cloud Network LB) отслеживают состояние TCP-соединений в таблицах conntrack. Если по мультиплексированному HTTP/2 соединению gRPC долгое время не передаются данные (idle), транслятор сбрасывает запись в таблице по таймауту (обычно от 60 до 350 секунд) без отправки TCP FIN или RST. Сокет на стороне клиента переходит в состояние 'black hole' (полуоткрытое соединение): клиент считает сокет живым, но при отправке нового RPC пакеты бесследно теряются, приводя к зависанию на время таймаута ОС. Клиентский gRPC Keepalive решает эту проблему отправкой 8-байтных HTTP/2 фреймов PING с заданным интервалом `Time`. Если за время `Timeout` ответный PING ACK не получен, клиент закрывает мертвый сокет и прозрачно открывает новое соединение.

## Решение по шагам

Импортируйте пакет google.golang.org/grpc/keepalive.
Сконфигурируйте структуру keepalive.ClientParameters с интервалом Time: 10s и ожиданием Timeout: 3s.
Установите флаг PermitWithoutStream: true для пинга во время полного простоя RPC стримов.
Инициализируйте grpc.DialContext с опцией grpc.WithKeepaliveParams.
Проверьте обработку потери PING-ответов и автоматическое переподключение.

## Код решения

**`client.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/keepalive"
)

// InitKeepaliveClient создает отказоустойчивое gRPC соединение с активным зондированием сети.
func InitKeepaliveClient(target string) (*grpc.ClientConn, error) {
	// Параметры keepalive для предотвращения разрыва сессий через NAT/NLB
	kacp := keepalive.ClientParameters{
		Time:                10 * time.Second, // Пинговать сервер каждые 10с при отсутствии трафика
		Timeout:             3 * time.Second,  // Ждать PONG 3с, затем признать сокет мертвым
		PermitWithoutStream: true,             // Разрешить PING даже когда нет активных RPC-вызовов
	}

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	log.Printf("[Keepalive] Connecting to %s with Time=10s, Timeout=3s...", target)
	conn, err := grpc.DialContext(ctx, target,
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithKeepaliveParams(kacp),
		grpc.WithBlock(),
	)
	if err != nil {
		return nil, fmt.Errorf("grpc dial error: %w", err)
	}

	return conn, nil
}

func main() {
	conn, err := InitKeepaliveClient("localhost:50051")
	if err != nil {
		log.Printf("[Demo Note] Dial failed (server not running locally, expected): %v", err)
		return
	}
	defer conn.Close()

	fmt.Println("Persistent keepalive connection successfully configured")
}
```

ℹ️ Настройка gRPC клиента с регулярным зондированием HTTP/2 PING фреймами

## Под капотом

gRPC транспорт запускает фоновую горутину `keepaliveLoop` в структуре `http2Client`. Каждые 10 секунд ожидания таймера горутина вызывает `framer.WritePing(false, [8]byte{...})` и взводит таймер таймаута на 3 секунды. Когда сервер отвечает фреймом PING с установленным флагом ACK (0x1), таймер сбрасывается. Если таймер истекает раньше получения ACK, клиент переводит соединение в состояние `TRANSIENT_FAILURE` и закрывает TCP дескриптор.

## Подводные камни

Если сервер gRPC не настроен с соответствующей `EnforcementPolicy.MinTime`, частые клиентские пинги (меньше 5 минут) будут расценены как DDoS-атака. Сервер отправит HTTP/2 фрейм GOAWAY с ошибкой ENHANCE_YOUR_CALM (too_many_pings) и немедленно разорвет сокет.

## На собеседовании

Вопрос на собеседовании в Яндекс: 'Что происходит на сетевом уровне, когда в AWS NLB срабатывает 350-секундный idle timeout, если клиент не шлет keepalive?' Ответ: NLB просто стирает запись из таблицы маршрутизации conntrack, не отправляя RST ни клиенту, ни серверу. При следующей попытке клиента отправить запрос пакет упрется в дроп на NLB. Клиент будет висеть до TCP retransmission timeout (минуты), если не настроен application-level gRPC keepalive.
