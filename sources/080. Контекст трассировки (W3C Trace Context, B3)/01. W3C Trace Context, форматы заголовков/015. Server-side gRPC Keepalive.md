# Server-side gRPC Keepalive: циклический сброс сессий и защита от зависших стримов

## Условие

Настройте gRPC сервер с keepalive.ServerParameters (MaxConnectionIdle: 5m, MaxConnectionAge: 10m, MaxConnectionAgeGrace: 30s, Time: 2h, Timeout: 20s). Объясните роль MaxConnectionAge в балансировке нагрузки gRPC.

### Исходная формулировка

**[Server-side Keepalive]**: Настрой gRPC сервер с `keepalive.ServerParameters` (`MaxConnectionIdle: 5m`, `MaxConnectionAge: 10m`). Объясни, зачем это нужно (заставить клиентов переподключаться, чтобы балансировщик нагрузки (Envoy/L4 LB) пересчитал веса).

## Теория

gRPC использует HTTP/2 мультиплексирование поверх одного постоянного TCP соединения. При работе за L4 балансировщиком (AWS NLB, Kubernetes ClusterIP) клиенты открывают сокет к существующим подам и держат его часами. Когда вы масштабируете Deployment с 3 до 10 реплик, старые 3 реплики получают 100% трафика, а новые 7 простаивают без соединений! Чтобы решить эту проблему без усложнения балансировщика, сервер gRPC настраивается параметром `MaxConnectionAge`. По истечении `MaxConnectionAge` сервер мягко отправляет клиенту HTTP/2 фрейм `GOAWAY`. Клиент завершает текущие запросы в течение `MaxConnectionAgeGrace`, разрывает TCP сокет и подключается заново. При новом подключении DNS/L4 балансировщик распределяет клиента на новую свободную реплику. Это выравнивает нагрузку по кластеру.

## Решение по шагам

Импортируйте google.golang.org/grpc/keepalive.
Инициализируйте keepalive.ServerParameters с требуемыми параметрами времени жизни соединения.
Сконфигурируйте MaxConnectionAge: 10m и MaxConnectionAgeGrace: 30s.
Передайте параметры в конструктор grpc.NewServer(grpc.KeepaliveParams(kasp)).
Запустите сервер и протестируйте поведение клиента при получении GOAWAY.

## Код решения

**`grpc_server_keepalive.go`**

```go
package main

import (
	"fmt"
	"log"
	"net"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/keepalive"
)

func CreateGRPCServer() *grpc.Server {
	// Параметры keepalive на стороне сервера
	kasp := keepalive.ServerParameters{
		MaxConnectionIdle:     5 * time.Minute, // Время неактивности до закрытия соединения
		MaxConnectionAge:      10 * time.Minute, // Максимальное время жизни одного TCP соединения (ротация)
		MaxConnectionAgeGrace: 30 * time.Second, // Дополнительное время на завершение активных RPC после GOAWAY
		Time:                  2 * time.Hour,    // Периодичность пинга сервера клиенту при отсутствии трафика
		Timeout:               20 * time.Second, // Время ожидания ответа на серверный пинг
	}

	// Политика контроля активности клиентов (защита от частых клиентских пингов)
	kaep := keepalive.EnforcementPolicy{
		MinTime:             5 * time.Second, // Клиент не имеет права слать PING чаще раза в 5 секунд
		PermitWithoutStream: true,            // Разрешить клиенту пинговать даже без активных стримов
	}

	server := grpc.NewServer(
		grpc.KeepaliveParams(kasp),
		grpc.KeepaliveEnforcementPolicy(kaep),
	)

	return server
}

func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		log.Fatalf("Listen failed: %v", err)
	}

	server := CreateGRPCServer()
	log.Println("gRPC Server initialized with MaxConnectionAge=10m for dynamic rebalancing")

	go func() {
		time.Sleep(100 * time.Millisecond)
		lis.Close()
	}()

	_ = server.Serve(lis)
	fmt.Println("Server keepalive demonstration completed.")
}
```

ℹ️ Серверный gRPC keepalive с принудительной ротацией соединений через MaxConnectionAge

## Под капотом

При срабатывании таймера `MaxConnectionAge` сервер вызывает `http2Server.GracefulClose()`. В сокет отправляется первый кадр `GOAWAY` с `LastStreamID = 2^31 - 1`, сообщающий клиенту, что сервер скоро закроется. По истечении `MaxConnectionAgeGrace` сервер отправляет финальный `GOAWAY` с актуальным `LastStreamID` и закрывает TCP сокет.

## Подводные камни

Если клиенты не настроены на автоматический reconnect или не используют retry-политики с экспоненциальным backoff и jitter, одновременное срабатывание MaxConnectionAge на всех серверах может вызвать 'шторм переподключений' (Thundering Herd Problem). Всегда добавляйте случайный jitter к MaxConnectionAge.

## На собеседовании

Вопрос на собеседовании в Авито: 'Зачем в gRPC серверах настраивают MaxConnectionAge, если TCP соединение стабильно и не рвется?' Ответ: 'Чтобы обеспечить равномерную балансировку в динамическом кластере K8s. При добавлении новых реплик gRPC клиенты сами не перейдут на них из-за постоянного HTTP/2 соединения. MaxConnectionAge заставляет клиентов периодически переподключаться и перебалансироваться'.
