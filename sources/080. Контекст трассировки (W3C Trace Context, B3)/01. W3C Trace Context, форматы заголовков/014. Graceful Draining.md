# Graceful Draining: ReadinessProbe 503 при получении SIGTERM

## Условие

Реализуйте переключение ReadinessProbe в статус 503 Service Unavailable при перехвате SIGTERM, сохраняя работоспособность livenessProbe и завершая активные запросы.

### Исходная формулировка

Измени флаг, чтобы `ReadinessProbe` начал отдавать `503 Service Unavailable`.

## Теория

Kubernetes опрашивает два разных зонда: 1) `livenessProbe` — отвечает на вопрос 'Жив ли процесс?'. Если возвращает ошибку, kubelet немедленно убивает контейнер и перезапускает его. При graceful shutdown livenessProbe ДОЛЖЕН отдавать 200 OK! 2) `readinessProbe` — отвечает на вопрос 'Готов ли под принимать трафик клиентов?'. Если возвращает 503, kubelet исключает IP пода из всех Endpoints и балансировщиков (Ingress, Service, Envoy). При перехвате SIGTERM приложение обязано немедленно перевести готовность в `false` (`readinessProbe` -> 503), но продолжать отвечать 200 на `livenessProbe`, чтобы kubelet дал приложению время доработать текущие HTTP/gRPC запросы до истечения terminationGracePeriodSeconds.

## Решение по шагам

Используйте sync/atomic или atomic.Bool для потокобезопасного хранения состояния готовности.
Зарегистрируйте эндпоинт /livez с безусловным возвратом 200 OK.
Зарегистрируйте эндпоинт /readyz с проверкой флага готовности.
При получении SIGTERM выставите флаг готовности в false.
Выдержите задержку и дождитесь завершения активных транзакций.

## Код решения

**`probes_draining.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"
)

type HealthController struct {
	isReady atomic.Bool
	isLive  atomic.Bool
}

func NewHealthController() *HealthController {
	hc := &HealthController{}
	hc.isLive.Store(true)
	hc.isReady.Store(true)
	return hc
}

func (hc *HealthController) SetupRoutes(mux *http.ServeMux) {
	// Liveness: жив ли рантайм Go (всегда 200, если нет дедлока)
	mux.HandleFunc("/livez", func(w http.ResponseWriter, r *http.Request) {
		if !hc.isLive.Load() {
			http.Error(w, "DEAD", http.StatusInternalServerError)
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ALIVE"))
	})

	// Readiness: готов ли принимать клиентский трафик
	mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
		if !hc.isReady.Load() {
			// При 503 K8s удаляет под из балансировки
			http.Error(w, "DRAINING", http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})
}

func main() {
	hc := NewHealthController()
	mux := http.NewServeMux()
	hc.SetupRoutes(mux)

	mux.HandleFunc("/api/data", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"payload":"success"}`))
	})

	server := &http.Server{
		Addr:    ":8080",
		Handler: mux,
	}

	go func() {
		if err := server.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatalf("Server listen failed: %v", err)
		}
	}()
	log.Println("Server running with /livez and /readyz probes")

	// Ловим сигнал остановки
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)
	<-sigChan

	log.Println("[SIGTERM] Draining started: setting readiness to FALSE (503)...")
	// Переводим готовность в false: K8s исключает под из Endpoints
	hc.isReady.Store(false)

	// Liveness остается true! K8s не должен убивать под принудительно
	log.Printf("[SIGTERM] Liveness status is still: %v (200 OK)", hc.isLive.Load())

	// Даем время K8s kube-proxy убрать роуты
	time.Sleep(3 * time.Second)

	// Завершаем сервер
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	if err := server.Shutdown(shutdownCtx); err != nil {
		log.Printf("Graceful shutdown error: %v", err)
	}
	fmt.Println("Clean shutdown finished.")
}
```

ℹ️ Разделение liveness (200) и readiness (503 при drain) во время завершения пода

## Под капотом

kubelet выполняет HTTP GET к readinessProbe с интервалом `periodSeconds` (например, 2с). Как только получен код >= 400, kubelet локально перестает направлять трафик и рапортует apiserver, чтобы IP пода был исключен из EndpointSlice. Если бы мы ошибочно вернули 503 на livenessProbe, kubelet мгновенно отправил бы SIGKILL, оборвав все активные соединения пользователей.

## Подводные камни

Возврат 503 на livenessProbe при выключении. Это частая ошибка начинающих: под не успевает завершить запросы, так как kubelet расценивает отказ livenessProbe как краш приложения и перезапускает его.

## На собеседовании

В чем фундаментальная разница между LivenessProbe и ReadinessProbe при graceful shutdown в K8s? Ответ: 'LivenessProbe сигнализирует о зависании процесса (дедлок, OOM). При ее падении контейнер рестартится. ReadinessProbe управляет маршрутизацией трафика. При graceful shutdown мы выключаем только ReadinessProbe, чтобы отрезать новый трафик, но LivenessProbe держим зеленой, пока дорабатывают старые запросы'.
