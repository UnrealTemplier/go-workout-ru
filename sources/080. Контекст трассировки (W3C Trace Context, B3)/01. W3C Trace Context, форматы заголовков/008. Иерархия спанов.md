# Иерархия спанов: Nested Spans и отношения Parent-Child

## Условие

Реализуйте функцию ProcessOrder, которая создаёт корневой span, внутри последовательно вызывает ValidateCart, ChargePayment и ReserveStock, создавая дочерние спаны (Child Spans). Покажите в коде корректную передачу context.Context между уровнями вызовов.

### Исходная формулировка

**Nested Spans и Parent-Child.**: Реализуйте функцию `ProcessOrder`, которая создаёт span, внутри вызывает `ValidatePayment` (child span) и `ReserveInventory` (child span). Покажите в Jaeger/Zipkin UI иерархию: `ProcessOrder` → `ValidatePayment` + `ReserveInventory`. Объясните, как `context.Context` передаёт parent span.

## Теория

Распределенный трейс представляет собой ориентированный ациклический граф (DAG) спанов. Связь 'родитель-потомок' (Parent-Child) строится автоматически через `context.Context`: когда функция вызывает `tracer.Start(ctx, 'ChildOperation')`, SDK считывает из `ctx` идентификатор родительского спана (`parent.SpanContext().SpanID()`) и записывает его в дочерний спан в качестве поля `ParentSpanID`. Если разработчик случайно передаст `context.Background()` вместо родительского `ctx`, цепочка будет разорвана, и дочерняя операция превратится в отдельный сиротский трейс.

## Решение по шагам

Создайте родительский спан ProcessOrder.
Передайте обновленный ctx в функцию ValidateCart и откройте дочерний спан.
Передайте ctx в ChargePayment и зафиксируйте вложенный таймлайн.
Передайте ctx в ReserveStock и завершите все спаны через defer.
Проверьте единый TraceID у всех участников цепочки.

## Код решения

**`nested_spans.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/attribute"
	"go.opentelemetry.io/otel/trace"
)

func ValidateCart(ctx context.Context) {
	tracer := otel.Tracer("order-service")
	_, span := tracer.Start(ctx, "ValidateCart")
	defer span.End()

	time.Sleep(10 * time.Millisecond)
	span.SetAttributes(attribute.Bool("cart.valid", true))
}

func ChargePayment(ctx context.Context, amount float64) {
	tracer := otel.Tracer("payment-service")
	_, span := tracer.Start(ctx, "ChargePayment",
		trace.WithSpanKind(trace.SpanKindClient),
	)
	defer span.End()

	time.Sleep(30 * time.Millisecond)
	span.SetAttributes(attribute.Float64("payment.amount", amount))
}

func ReserveStock(ctx context.Context, itemID string) {
	tracer := otel.Tracer("warehouse-service")
	_, span := tracer.Start(ctx, "ReserveStock")
	defer span.End()

	time.Sleep(15 * time.Millisecond)
	span.SetAttributes(attribute.String("warehouse.item_id", itemID))
}

// ProcessOrder координирует бизнес-процесс и создает дерево вложенных спанов.
func ProcessOrder(ctx context.Context, orderID string) {
	tracer := otel.Tracer("order-coordinator")
	ctx, rootSpan := tracer.Start(ctx, "ProcessOrder")
	defer rootSpan.End()

	rootSpan.SetAttributes(attribute.String("order.id", orderID))

	log.Printf("[Trace Root] Starting ProcessOrder under TraceID: %s", rootSpan.SpanContext().TraceID())

	// Передаем ctx дальше — дочерние спаны автоматически унаследуют ParentSpanID
	ValidateCart(ctx)
	ChargePayment(ctx, 199.90)
	ReserveStock(ctx, "sku-laptop-x1")

	log.Println("[Trace Root] ProcessOrder successfully completed with all child spans")
}

func main() {
	ProcessOrder(context.Background(), "ord-8831")
	fmt.Println("Nested spans with parent-child relationships verified successfully")
}
```

ℹ️ Иерархическая передача контекста трассировки и генерация дочерних спанов

## Под капотом

При вызове `tracer.Start(ctx, ...)` OpenTelemetry извлекает текущий активный спан через `trace.SpanFromContext(ctx)`. Дочерний спан копирует `TraceID` родителя, генерирует собственный уникальный `SpanID` и сохраняет `parent.SpanID` в поле `parent_span_id`. UI Jaeger рендерит такое дерево в виде каскадной диаграммы Ганта (Gantt Chart).

## Подводные камни

Вызов `tracer.Start(context.TODO(), ...)` внутри вложенной функции. Это распространенная ошибка новичков, которая полностью отвязывает дочерний спан от родителя и ломает сквозную визуализацию.

## На собеседовании

Вопрос на собеседовании в Яндекс: 'В чем разница между отношением спанов ChildOf и FollowsFrom?' Ответ: ChildOf означает синхронную зависимость: родитель ждет завершения дочерней операции (например, HTTP-запрос ждет ответ базы данных). FollowsFrom используется в асинхронных сценариях (очереди Kafka, RabbitMQ): родитель отправил сообщение и пошел дальше, а консьюмер обработал его асинхронно.
