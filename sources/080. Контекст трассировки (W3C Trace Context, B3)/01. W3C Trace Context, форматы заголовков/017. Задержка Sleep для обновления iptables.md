# Задержка Sleep для обновления iptables и kube-proxy роутов при остановке пода

## Условие

Напишите безопасную функцию ожидания деактивации пода в Kubernetes с проверкой сигналов отмены и логами обратного отсчета.

### Исходная формулировка

Сделай `time.Sleep(5 * time.Second)` — дай K8s/Envoy время убрать тебя из роутов.

## Теория

Сетевая подсистема Linux (Netfilter/iptables/IPVS) работает на уровне ядра каждой ноды кластера. Когда Pod переходит в статус `Terminating`, контроллер Kubernetes оповещает kube-proxy на всех нодах. Процесс обновления таблицы правил iptables не происходит мгновенно — это распределенная операция, зависящая от нагрузки на apiserver и размера кластера. Если приложение сразу завершит слушающий сокет, клиенты из других нод продолжат отправлять пакеты на старый IP пода, получая ошибки `ECONNREFUSED`. Выдержка фиксированной паузы (`drain delay`, обычно 5-10 секунд) после перевода ReadinessProbe в 503 позволяет дождаться полного исключения пода из маршрутизации всех нод.

## Решение по шагам

Определите функцию DrainWait с параметром duration и контекстом отмены.
Используйте time.NewTicker для логирования обратного отсчета.
Обеспечьте корректный выход, если родительский контекст завершился раньше времени.
Интегрируйте вызов DrainWait в конвейер остановки сервера.

## Код решения

**`drain_delay.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"
)

// WaitForNetworkDraining ожидает обновления маршрутизации iptables/kube-proxy в кластере
func WaitForNetworkDraining(ctx context.Context, delay time.Duration) error {
	log.Printf("[Draining] Waiting %v for iptables/IPVS routing update across K8s cluster...", delay)

	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	startTime := time.Now()
	deadline := startTime.Add(delay)

	for {
		select {
		case <-ctx.Done():
			return fmt.Errorf("draining interrupted by context deadline: %w", ctx.Err())
		case now := <-ticker.C:
			remaining := deadline.Sub(now).Round(time.Second)
			if remaining <= 0 {
				log.Println("[Draining] Network drain delay completed. Safe to close server socket.")
				return nil
			}
			log.Printf("[Draining] %v remaining until socket close...", remaining)
		}
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// Имитация выдержки паузы в 3 секунды
	if err := WaitForNetworkDraining(ctx, 3*time.Second); err != nil {
		log.Fatalf("Drain error: %v", err)
	}
	fmt.Println("Ready to perform server.Shutdown()")
}
```

ℹ️ Контролируемая пауза с обратным отсчетом для обновления сетевых правил ядра Linux

## Под капотом

kube-proxy синхронизирует iptables батчами (параметр `--iptables-min-sync-interval`, по умолчанию 1с, `--iptables-sync-period`, по умолчанию 30с). Пока этот интервал не истек, ядро хоста направляет сетевые пакеты по старым правилам PREROUTING KUBE-SERVICES. Фиксированная пауза дает гарантию завершения цикла синхронизации.

## Подводные камни

Использование неблокирующего time.Sleep без отслеживания контекста. Если оператор нажмет Ctrl+C повторно или произойдет отмена контекста, 'слепой' time.Sleep заблокирует процесс и проигнорирует команду срочной остановки.

## На собеседовании

Вопрос на собеседовании в Тинькофф: 'Почему в высоконагруженных сервисах нельзя полагаться только на закрытие соединений со стороны балансировщика Ingress?' Ответ: 'Потому что трафик идет не только через внешний Ingress, но и внутри кластера (East-West traffic) от других подов напрямую через kube-proxy / ClusterIP. Если закрыть сокет раньше обновления iptables на нодах-клиентах, внутренние сервисы получат 502/RST ошибки'.
