# Trace Context и Service Mesh: сквозное связывание спанов через Envoy

## Условие

Покажите, как Go-приложение в инфраструктуре Service Mesh (Istio / Envoy sidecar) обязано перекладывать входящие заголовки трассировки (x-request-id, traceparent) в исходящие вызовы, чтобы цепочка спанов не разрывалась.

### Исходная формулировка

**Trace Context + Service Mesh.**: Покажите, что Istio/Linkerd автоматически добавляют `x-request-id` и пропагируют trace headers (если настроен `MeshConfig` с `enableTracing: true`). Объясните, как mesh дополняет application spans своими (Envoy span: ingress/egress, mTLS handshake latency).

## Теория

Распространенное заблуждение: 'Если у нас в Kubernetes развернут Istio Service Mesh, трассировка работает из коробки без изменения Go-кода'. Это правда лишь для входящего и исходящего трафика на уровне одного пода. Envoy перехватывает входящий запрос, генерирует клиентский/серверный спан и передает запрос локальному Go-приложению на 127.0.0.1. Но когда Go-приложение совершает исходящий HTTP/gRPC вызов к другому сервису, Envoy не знает, к какому из 1000 параллельных входящих запросов относится этот вызов! Go-код ОБЯЗАН скопировать заголовки трассировки (`x-request-id`, `traceparent`, `x-b3-traceid`) из входящего контекста в исходящие заголовки. Без этого Envoy создаст абсолютно новый `x-request-id`, и распределенный граф трейса в Jaeger распадется на разрозненные фрагменты.

## Решение по шагам

Определите список обязательных для проброса заголовков Service Mesh (x-request-id, traceparent, x-b3-*).
Реализуйте HTTP middleware, извлекающее эти заголовки и сохраняющее их в контексте.
Создайте http.RoundTripper (или клиентский middleware), инжектирующий сохраненные заголовки в любой исходящий запрос.
Проверьте сохранение единого x-request-id сквозь цепочку микросервисов.

## Код решения

**`mesh_propagation.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
)

type contextKey string

const meshHeadersKey contextKey = "mesh_tracing_headers"

var tracingHeadersToPropagate = []string{
	"x-request-id",
	"traceparent",
	"tracestate",
	"x-b3-traceid",
	"x-b3-spanid",
	"x-b3-sampled",
}

// ServiceMeshTracingMiddleware сохраняет mesh-заголовки входящего запроса в context
func ServiceMeshTracingMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		headers := make(http.Header)
		for _, h := range tracingHeadersToPropagate {
			if val := r.Header.Get(h); val != "" {
				headers.Set(h, val)
			}
		}

		ctx := context.WithValue(r.Context(), meshHeadersKey, headers)
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

// MeshTransport автоматически проставляет mesh-заголовки из контекста в исходящий вызов
type MeshTransport struct {
	Base http.RoundTripper
}

func (m *MeshTransport) RoundTrip(req *http.Request) (*http.Response, error) {
	if headers, ok := req.Context().Value(meshHeadersKey).(http.Header); ok {
		for key, vals := range headers {
			for _, val := range vals {
				req.Header.Add(key, val)
			}
		}
	}
	base := m.Base
	if base == nil {
		base = http.DefaultTransport
	}
	return base.RoundTrip(req)
}

func main() {
	// downstream service
	backend := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		reqID := r.Header.Get("x-request-id")
		tp := r.Header.Get("traceparent")
		fmt.Fprintf(w, "Downstream received x-request-id: %s, traceparent: %s\n", reqID, tp)
	}))
	defer backend.Close()

	// Наш сервис с middleware и MeshTransport
	client := &http.Client{Transport: &MeshTransport{}}

	ourServiceHandler := ServiceMeshTracingMiddleware(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Делаем вызов в downstream сервис, контекст содержит mesh-заголовки
		outReq, _ := http.NewRequestWithContext(r.Context(), "GET", backend.URL, nil)
		resp, err := client.Do(outReq)
		if err != nil {
			http.Error(w, err.Error(), http.StatusInternalServerError)
			return
		}
		defer resp.Body.Close()
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("Mesh propagation completed successfully"))
	}))

	ts := httptest.NewServer(ourServiceHandler)
	defer ts.Close()

	// Имитация входящего запроса от Envoy
	inboundReq, _ := http.NewRequest("GET", ts.URL, nil)
	inboundReq.Header.Set("x-request-id", "envoy-req-abc-987")
	inboundReq.Header.Set("traceparent", "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01")

	res, err := http.DefaultClient.Do(inboundReq)
	if err != nil {
		panic(err)
	}
	defer res.Body.Close()
	fmt.Printf("Gateway response status: %s\n", res.Status)
}
```

ℹ️ Сквозной проброс заголовков трассировки Envoy/Istio через context и RoundTripper

## Под капотом

Envoy генерирует спан Envoy-Inbound, когда запрос попадает на внешний порт пода, и ожидает увидеть тот же самый x-request-id в заголовках, когда Go-приложение обращается к другим внешним сервисам через свой localhost Envoy-Outbound. Если Go-сервис не перекладывает эти заголовки, Envoy считает исходящий запрос новой изолированной транзакцией.

## Подводные камни

Копирование заголовков 'вслепую' без фильтрации. Если скопировать `Host`, `Content-Length` или чувствительные auth-токены в вызовы сторонних API, можно нарушить HTTP/1.1 протокол или допустить утечку секретов.

## На собеседовании

Вопрос на собеседовании в Lamoda: 'Если Istio перехватывает весь трафик через iptables, зачем вообще разработчикам трогать контекст трассировки в Go?' Ответ: 'Istio видит байты на сокете, но внутри Go-процесса выполняются сотни конкурентных горутин. Только рантайм Go знает связь между входящим HTTP-запросом и последующими исходящими RPC-вызовами. Без проброса заголовков сквозь context.Context трассировка фрагментируется'.
