# Проблема SIGTERM в Kubernetes: асинхронность iptables и сокетный сброс

## Условие

Когда K8s гасит под, он шлет SIGTERM и одновременно дает команду iptables/Envoy убрать под из Endpoints. Но распространение iptables занимает 1–3 секунды! Если сервис сразу вызовет GracefulStop(), клиенты получат Connection Refused. Напишите подробный разбор проблемы и Go-архитектуру безопасной задержки (PreStop Sleep).

### Исходная формулировка

**Проблема SIGTERM в K8s**: Когда K8s гасит под, он шлет `SIGTERM` и *одновременно* дает команду iptables/Envoy убрать под из балансировки. Обновление роутинга занимает время (до 1-3 сек). Если твой Go-код сделает `srv.Shutdown()` мгновенно при получении SIGTERM, запросы, которые всё еще летят со стороны Envoy, упадут с 502 Bad Gateway. Осознай эту архитектурную боль!

## Теория

Фундаментальная гонка (Race Condition) при удалении Pod в Kubernetes: 1) Kubelet получает команду на удаление и посылает сигнал `SIGTERM` главному процессу контейнера; 2) Одновременно Endpoint Controller удаляет IP-адрес пода из объекта `Endpoints`; 3) kube-proxy на всех остальных нодах кластера должен получить обновление через watch API и переписать локальные таблицы `iptables` / IPVS. Обновление iptables на всех нодах занимает от 1 до 5 секунд! Если Go-сервис при получении SIGTERM немедленно закроет Listener через `GracefulStop()`, в течение следующих 3 секунд другие поды кластера продолжат слать запросы на этот IP согласно старым таблицам iptables, получая фатальные ошибки `connection refused` (TCP RST). Решение: при получении SIGTERM сервис должен продолжать принимать трафик еще 5–15 секунд!

## Решение по шагам

Изучите схему распространения обновлений Endpoints в Kubernetes.
Реализуйте в Go задержку pre-drain sleep при перехвате SIGTERM.
Переведите ReadinessProbe в состояние 503, чтобы уведомить kube-proxy.
Выдержите паузу 5–10 секунд для очистки очередей сетевых маршрутов.
Только после паузы вызовите srv.Shutdown(ctx).

## Код решения

**`k8s_drain_delay.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"
)

var isDraining int32

// HealthCheckHandler сигнализирует Kubernetes о готовности пода принимать трафик.
func HealthCheckHandler(w http.ResponseWriter, r *http.Request) {
	if atomic.LoadInt32(&isDraining) == 1 {
		// При перехвате SIGTERM возвращаем 503, ускоряя исключение пода из балансировки
		http.Error(w, "Pod is draining", http.StatusServiceUnavailable)
		return
	}
	w.WriteHeader(http.StatusOK)
	w.Write([]byte("ready"))
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/readyz", HealthCheckHandler)
	mux.HandleFunc("/api/work", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte(`{"status":"success"}`))
	})

	srv := &http.Server{
		Addr:    ":8080",
		Handler: mux,
	}

	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGTERM, syscall.SIGINT)

	go func() {
		log.Println("Service running on :8080...")
		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			log.Fatalf("Server listen error: %v", err)
		}
	}()

	<-sigChan
	log.Println("[K8s Shutdown] Received SIGTERM! Phase 1: Marking Readiness as 503...")
	atomic.StoreInt32(&isDraining, 1)

	// КРИТИЧЕСКАЯ ЗАДЕРЖКА: даем kube-proxy и Ingress время обновить iptables роуты
	drainWait := 5 * time.Second
	log.Printf("[K8s Shutdown] Phase 2: Sleeping %v while continuing to serve active traffic...", drainWait)
	time.Sleep(drainWait)

	log.Println("[K8s Shutdown] Phase 3: Now safe to invoke srv.Shutdown()...")
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Fatalf("Shutdown failed: %v", err)
	}
	fmt.Println("Zero-downtime Kubernetes pod termination sequence completed successfully")
}
```

ℹ️ Устранение race condition между SIGTERM и обновлением iptables в Kubernetes

## Под капотом

В Kubernetes жизненный цикл Pod контролируется `terminationGracePeriodSeconds` (дефолт 30с). Если в манифесте Pod не настроен `preStop: exec: command: ['/bin/sleep', '5']`, Go-приложение обязано само реализовать эту задержку в коде при обработке `syscall.SIGTERM`.

## Подводные камни

Вызов `os.Exit(0)` сразу при получении SIGTERM. Это приводит к мгновенному всплеску 502 Bad Gateway / Connection Refused на Ingress шлюзах во время каждого релиза деплоймента.

## На собеседовании

Вопрос на собеседовании в Авито: 'Зачем нужен sleep в preStop хуке Kubernetes контейнера, если в Go уже написан Graceful Shutdown?' Ответ: Graceful Shutdown в Go защищает только те запросы, которые УЖЕ зашли в сервис. Sleep в preStop защищает запросы, которые были отправлены клиентами В МОМЕНТ удаления пода, когда старые правила iptables на других нодах еще направляют трафик на этот IP.
