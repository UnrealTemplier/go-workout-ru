# Кастомный Connection Pooling в gRPC: масштабирование поверх нескольких TCP сокетов

## Условие

Напишите кастомный пул gRPC-соединений (Channel Pool), открывающий N параллельных TCP-сокетов к одному бэкенду и распределяющий RPC между ними для обхода узких мест HTTP/2 Flow Control.

### Исходная формулировка

**[Connection Pooling (Custom)]**: Стандартный gRPC клиент держит 1 TCP-соединение на хост. Напиши кастомный `grpc.Resolver` и `grpc.Balancer`, который открывает N (например, 3) TCP-соединений к одному и тому же поду для увеличения пропускной способности (полезно для очень тяжелых streaming-сервисов).

## Теория

По умолчанию клиент `grpc.DialContext` открывает ровно ОДНО TCP-соединение к указанному адресу и мультиплексирует все вызовы внутри него. В большинстве случаев этого достаточно. Однако при сверхвысокой нагрузке (сотни тысяч RPS или гигабайты видеотрафика) одно TCP-соединение упирается в: 1) Однопоточную обработку фреймов внутри горутины `loopyWriter` в Go; 2) Лимиты HTTP/2 Flow Control окна; 3) TCP head-of-line blocking при потере даже одного пакета в сети. Решение — создание пула из нескольких клиентских каналов (`ClientConn Pool`), где каждый вызов RPC направляется в следующий канал через атомарный Round Robin.

## Решение по шагам

Создайте структуру ClientPool со слайсом []*grpc.ClientConn и атомарным индексом.
Реализуйте конструктор NewClientPool(size int, target string, opts ...grpc.DialOption).
Реализуйте метод Get() *grpc.ClientConn с циклическим выбором через atomic.AddUint64.
Реализуйте метод Close() для корректного закрытия всех сокетов пула.

## Код решения

**`grpc_conn_pool.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync/atomic"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

// GRPCConnectionPool управляет набором параллельных TCP-соединений к одному сервису
type GRPCConnectionPool struct {
	conns []*grpc.ClientConn
	index atomic.Uint64
	size  int
}

func NewGRPCConnectionPool(size int, target string) (*GRPCConnectionPool, error) {
	pool := &GRPCConnectionPool{
		conns: make([]*grpc.ClientConn, size),
		size:  size,
	}

	for i := 0; i < size; i++ {
		ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
		conn, err := grpc.DialContext(ctx, target,
			grpc.WithTransportCredentials(insecure.NewCredentials()),
		)
		cancel()
		if err != nil {
			// В случае ошибки закрываем ранее созданные
			pool.Close()
			return nil, fmt.Errorf("failed to open connection %d: %w", i, err)
		}
		pool.conns[i] = conn
	}

	return pool, nil
}

// GetConn возвращает соединение из пула по алгоритму Round Robin
func (p *GRPCConnectionPool) GetConn() *grpc.ClientConn {
	idx := p.index.Add(1)
	return p.conns[idx%uint64(p.size)]
}

func (p *GRPCConnectionPool) Close() {
	for _, c := range p.conns {
		if c != nil {
			_ = c.Close()
		}
	}
}

func main() {
	log.Println("Initializing gRPC Channel Pool with 4 parallel TCP connections...")
	pool, err := NewGRPCConnectionPool(4, "127.0.0.1:50051")
	if err != nil {
		log.Printf("[Demo note] Expected deferred connection: %v", err)
		return
	}
	defer pool.Close()

	// Получение соединений по очереди
	for i := 1; i <= 8; i++ {
		conn := pool.GetConn()
		_ = conn
		fmt.Printf("Dispatched RPC call %d across multi-socket pool\n", i)
	}
}
```

ℹ️ Клиентский пул постоянных gRPC соединений для снятия лимитов HTTP/2

## Под капотом

Создание 4-8 параллельных соединений позволяет распределить сетевой трафик между разными ядрами CPU и сетевыми очередями NIC (Receive Side Scaling — RSS), увеличивая суммарную пропускную способность микросервиса в несколько раз.

## Подводные камни

Слишком большой размер пула (например 100). Каждое открытое TCP-соединение требует памяти ядра под буферы сокетов (`tcp_rmem`/`tcp_wmem`) и тратит ресурсы на keepalive пинги. Оптимальный размер пула: 2-8 соединений.

## На собеседовании

Вопрос на собеседовании в Ozon: 'Зачем делать пул gRPC соединений, если gRPC и так мультиплексирует запросы?' Ответ: 'Мультиплексирование происходит внутри ОДНОГО TCP соединения. При огромном трафике (сотни тысяч сообщений) узким местом становится сериализация фреймов в одну горутину loopyWriter и лимиты HTTP/2 окон. Пул из 4-8 сокетов снимает эти ограничения'.
