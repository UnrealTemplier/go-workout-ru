# Плавный сброс соединений (Graceful Connection Draining) клиентом с Jitter

## Условие

Реализуйте на клиенте обработку ротации соединений с добавлением случайной задержки (Jitter), чтобы предотвратить одновременный шторм переподключений (Thundering Herd) к новым репликам.

### Исходная формулировка

**Плавный сброс соединений (Graceful Connection Draining)**: Чтобы K8s мог равномерно перераспределять нагрузку между подами gRPC-сервера, заставьте клиентов периодически переподключаться. Настройте на сервере параметры `MaxConnectionAge` и `MaxConnectionAgeGrace` [654]:
```go
keepalive.ServerParameters{
    MaxConnectionAge:      30 * time.Minute, // закрывать TCP-соединение через 30 минут
    MaxConnectionAgeGrace: 15 * time.Second, // дать 15 секунд на завершение активных RPC
}
```
Объясните, как это заставляет клиентов плавно переподключаться к другим подам без обрыва активных пользовательских запросов [654].

## Теория

Когда на gRPC серверах настроен `MaxConnectionAge: 10m`, все соединения, открытые одновременно (например, во время утреннего старта платформы), достигнут предельного возраста в одну и ту же секунду! Серверы отправят клиентам GOAWAY, и тысячи клиентов одновременно кинутся заново резолвить DNS и устанавливать TCP + TLS рукопожатия (Thundering Herd / Reconnect Storm). Это может перегрузить DNS-сервер (CoreDNS в K8s) и CPU бэкендов. Решение: клиентский рандомизированный Jitter. При необходимости переподключения или ротации время жизни соединения варьируется: `actualLifetime = baseTime + rand.Float64() * jitterRange`. Это плавно 'размазывает' переподключения во времени, распределяя нагрузку равномерно.

## Решение по шагам

Импортируйте crypto/rand или math/rand/v2.
Реализуйте функцию CalculateJitterDuration(base, maxJitter time.Duration).
Примените случайную задержку перед переподключением клиента.
Проверьте равномерность распределения попыток подключения.

## Код решения

**`reconnect_jitter.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"log"
	"math/big"
	"time"
)

// AddJitterToDuration добавляет случайный разброс [0, maxJitter] к базовой длительности
func AddJitterToDuration(base time.Duration, maxJitter time.Duration) time.Duration {
	if maxJitter <= 0 {
		return base
	}
	nBig, err := rand.Int(rand.Reader, big.NewInt(int64(maxJitter)))
	if err != nil {
		return base
	}
	return base + time.Duration(nBig.Int64())
}

func main() {
	baseConnectionAge := 10 * time.Minute
	maxJitter := 2 * time.Minute

	log.Printf("Base connection age: %v, Max Jitter: %v", baseConnectionAge, maxJitter)

	// Моделируем расчет времени ротации для 5 клиентов
	for i := 1; i <= 5; i++ {
		staggeredLifetime := AddJitterToDuration(baseConnectionAge, maxJitter)
		fmt.Printf("Client %d scheduled reconnect in: %v\n", i, staggeredLifetime.Round(time.Second))
	}

	fmt.Println("Connection rotation jitter smoothly disperses traffic spikes.")
}
```

ℹ️ Расчет случайного джиттера для предотвращения Reconnect Storm

## Под капотом

Использование криптографического генератора `crypto/rand` или потокобезопасного `math/rand/v2` гарантирует отсутствие корреляции между процессами даже при одинаковом начальном времени запуска подов.

## Подводные камни

Использование фиксированного интервала повтора (например, ровно 5 секунд). Все клиенты, получившие отказ в секунду T, синхронно придут повторно в секунду T+5, повторяя всплеск нагрузки.
