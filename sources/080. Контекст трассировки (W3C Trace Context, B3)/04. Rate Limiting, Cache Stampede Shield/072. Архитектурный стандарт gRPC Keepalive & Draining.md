# Архитектурный стандарт gRPC Keepalive & Draining в распределенных системах

## Условие

Сформулируйте сводный инженерный регламент (Best Practices) по конфигурации Keepalive и Draining для микросервисов HighLoad Enterprise уровня.

### Исходная формулировка

**Блок 35 (gRPC Keepalive/Draining)**: — проходите после Блока 21 (gRPC-Web), так как это продолжение gRPC-инфраструктуры. Знание `context` и `sync` критично для graceful shutdown.

## Теория

Архитектурный стандарт отказоустойчивости gRPC платформы: 1. Клиентская сторона (gRPC Client):    - `Time: 15s`, `Timeout: 5s`, `PermitWithoutStream: true`;    - Балансировка: `round_robin` с DNS резолвером через Headless Service;    - Retry Policy: экспоненциальный backoff с jitter для кодов `UNAVAILABLE`. 2. Серверная сторона (gRPC Server):    - `MaxConnectionAge: 10m` + Jitter (ротация сокетов для балансировки по репликам);    - `MaxConnectionAgeGrace: 30s` (время на завершение запросов после GOAWAY);    - `EnforcementPolicy{MinTime: 5s, PermitWithoutStream: true}`. 3. Оркестрация (Kubernetes):    - `lifecycle.preStop: sleep 10` в PodSpec;    - `readinessProbe` переключается в 503 при получении SIGTERM;    - `terminationGracePeriodSeconds: 45`.

## Решение по шагам

Изучите сводную таблицу параметров.
Проверьте совместимость настроек клиента и сервера.
Сформулируйте чеклист аудита сетевой надежности.
Примените регламент к микросервисам проекта.

## Код решения

**`grpc_standard.md`**

```markdown
# Золотой стандарт gRPC Keepalive & Draining в Production

| Уровень | Параметр | Рекомендуемое значение | Обоснование |
| :--- | :--- | :--- | :--- |
| **Client** | `keepalive.ClientParameters.Time` | `15s` | Зондирование NAT/NLB до сброса таблицы conntrack |
| **Client** | `keepalive.ClientParameters.Timeout` | `5s` | Быстрое обнаружение мертвого сокета |
| **Client** | `PermitWithoutStream` | `true` | Защита от разрыва соединений в часы ночного простоя |
| **Server** | `MaxConnectionAge` | `10m` (+ jitter) | Принудительная перебалансировка клиентов по новым подам |
| **Server** | `MaxConnectionAgeGrace` | `30s` | Бесшовное завершение активных RPC после GOAWAY |
| **Server** | `EnforcementPolicy.MinTime` | `5s` | Защита от DoS-атак частыми пингами клиентов |
| **K8s** | `preStop.exec.command` | `["sleep", "10"]`| Время на обновление iptables во всем кластере |
| **K8s** | `terminationGracePeriodSeconds` | `45s` | Запас времени до принудительного SIGKILL |
```

ℹ️ Сводный инженерный регламент сетевой надежности gRPC

## Под капотом

Соблюдение неравенства `Client.Time > Server.EnforcementPolicy.MinTime` является ключевым правилом, предотвращающим отстрел клиентов сервером с ошибкой too_many_pings.

## Подводные камни

Рассинхронизация конфигураций между разными командами разработки. Рекомендуется выносить единый пресет DialOptions и ServerOptions в общую корпоративную Go-библиотеку (SDK).

## На собеседовании

Вопрос на собеседовании в Яндекс: 'Назовите три главных параметра gRPC сервера для работы в высоконагруженном Kubernetes кластере.' Ответ: '1) MaxConnectionAge для ротации соединений; 2) Keepalive EnforcementPolicy для защиты от флуда; 3) Координированный GracefulStop с дедлайном и preStop хуком'.
