# Локальный singleflight для дедупликации сетевых запросов в микросервисе

## Условие

Реализуйте обертку над сетевым клиентом с использованием golang.org/x/sync/singleflight, гарантирующую, что при 100 одновременных запросах одинаковых данных в сеть уйдет ровно 1 запрос.

### Исходная формулировка

Локальный `singleflight` (чтобы из одного пода в сеть ушел только 1 запрос).

## Теория

Внутри одного пода Go сотни горутин могут одновременно запрашивать один и тот же неизменяемый ресурс: например, профиль популярного пользователя, карточку горячего товара на распродаже или курсы валют. Без дедупликации каждая горутина выполнит отдельный сетевой HTTP или gRPC вызов к удаленному бэкенду. Пакет `golang.org/x/sync/singleflight` объединяет конкурентные вызовы с одинаковым ключом: первая горутина выполняет реальный сетевой запрос, а остальные 99 горутин блокируются и получают копию того же самого результата, как только первый вызов вернет ответ. Это снижает нагрузку на внутреннюю сеть и микросервисы в 10-100 раз.

## Решение по шагам

Импортируйте golang.org/x/sync/singleflight.
Создайте структуру ClientWithSingleflight со встроенной группой sf.Group.
Реализуйте метод FetchData(ctx context.Context, key string) (string, error).
Используйте sf.DoChan для поддержки отмены контекста вызывающей стороны.
Проверьте дедупликацию вызовов на группе конкурентных горутин.

## Код решения

**`singleflight_dedup.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"
	"sync/atomic"
	"time"

	"golang.org/x/sync/singleflight"
)

type NetworkClient struct {
	group        singleflight.Group
	networkCalls atomic.Int64
}

// FetchDataSafe выполняет дедуплицированный сетевой запрос с поддержкой отмены контекста
func (c *NetworkClient) FetchDataSafe(ctx context.Context, resourceID string) (string, error) {
	// DoChan возвращает канал, что позволяет реагировать на отмену ctx конкретного клиента
	resultChan := c.group.DoChan(resourceID, func() (interface{}, error) {
		log.Printf("[Outbound Network] Sending physical request for resource: %s", resourceID)
		c.networkCalls.Add(1)

		// Имитируем сетевой round-trip 100мс
		time.Sleep(100 * time.Millisecond)
		return fmt.Sprintf("PAYLOAD_FOR_%s", resourceID), nil
	})

	select {
	case <-ctx.Done():
		return "", ctx.Err()
	case res := <-resultChan:
		if res.Err != nil {
			return "", res.Err
		}
		return res.Val.(string), nil
	}
}

func main() {
	client := &NetworkClient{}
	var wg sync.WaitGroup

	// Запускаем 10 параллельных горутин за одним и тем же ресурсом
	for i := 1; i <= 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
			defer cancel()

			val, err := client.FetchDataSafe(ctx, "user-profile-1001")
			if err != nil {
				log.Printf("Client %d failed: %v", id, err)
				return
			}
			_ = val
		}(i)
	}

	wg.Wait()
	fmt.Printf("Singleflight complete! Physical network calls made: %d (Expected: 1)\n",
		client.networkCalls.Load())
}
```

ℹ️ Дедупликация конкурентных запросов через singleflight.DoChan с поддержкой ctx

## Под капотом

Использование `DoChan` вместо синхронного `Do` критически важно в продакшене: если одна из горутин отменила свой HTTP-запрос по таймауту клиента, она не должна висеть в блокировке, пока первая горутина доделывает сетевой вызов.

## Подводные камни

Мутация возвращаемого указателя. Если `singleflight.Do` возвращает указатель на срез или структуру `*User`, все 100 горутин получат один и тот же указатель! Если одна из них изменит поле структуры, возникнет состояние гонки (Data Race). Всегда возвращайте неизменяемые данные или делайте глубокую копию.

## На собеседовании

Вопрос на собеседовании в Kasperskу: 'В чем опасность использования singleflight.Do при работе с context.Context?' Ответ: 'Синхронный Do() не принимает context. Если первая горутина зависнет, остальные горутины зависнут вместе с ней, даже если их собственные контексты уже отменены. Необходимо использовать `DoChan` с select по `ctx.Done()`'.
