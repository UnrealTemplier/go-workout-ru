# Тюнинг gRPC Connection: MaxRecvMsgSize, InitialWindowSize и Flow Control

## Условие

Сконфигурируйте gRPC клиент и сервер с расширенными параметрами MaxRecvMsgSize (32MB), MaxSendMsgSize (32MB), InitialWindowSize и InitialConnWindowSize для высокоскоростной передачи больших массивов данных.

### Исходная формулировка

**Connection Pool Tuning.**: Настройте gRPC клиент: `MaxRecvMsgSize`, `MaxSendMsgSize`, `InitialWindowSize`, `InitialConnWindowSize`. Покажите, как маленькое окно (64 KB) ограничивает throughput при высокой latency (RTT 100ms). Объясните BDP (Bandwidth-Delay Product) и зачем увеличивать window для WAN.

## Теория

По умолчанию gRPC имеет консервативные ограничения безопасности: максимальный размер сообщения (`MaxRecvMsgSize`) составляет 4 МБ. При попытке передать файл, крупный отчет или ML-модель клиент упадет с ошибкой `ResourceExhausted: received message larger than max (X vs 4194304)`. Кроме того, механизм управления потоком HTTP/2 (Flow Control) по умолчанию использует небольшие размеры окон приема (64 КБ), что на каналах с высоким RTT (High Bandwidth-Delay Product) приводит к искусственному ограничению пропускной способности (TCP throughput throttling). Тюнинг параметров `InitialWindowSize` и `InitialConnWindowSize` (до 1-4 МБ) позволяет полностью утилизировать 10-гигабитные каналы между датацентрами.

## Решение по шагам

Сконфигурируйте лимиты размеров сообщений grpc.MaxRecvMsgSize и grpc.MaxSendMsgSize.
Настройте HTTP/2 Flow Control окна: InitialWindowSize (1MB) и InitialConnWindowSize (4MB).
Инициализируйте сервер и клиент с расширенными опциями.
Проверьте передачу сообщений размером более 4 МБ.

## Код решения

**`grpc_pool_tuning.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

const (
	maxMsgSize  = 32 * 1024 * 1024 // 32 MB
	streamWinSz = 1 * 1024 * 1024  // 1 MB per stream window
	connWinSz   = 4 * 1024 * 1024  // 4 MB connection window
)

func CreateTunedServer() *grpc.Server {
	return grpc.NewServer(
		grpc.MaxRecvMsgSize(maxMsgSize),
		grpc.MaxSendMsgSize(maxMsgSize),
		grpc.InitialWindowSize(streamWinSz),
		grpc.InitialConnWindowSize(connWinSz),
	)
}

func DialTunedClient(target string) (*grpc.ClientConn, error) {
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	return grpc.DialContext(ctx, target,
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		grpc.WithDefaultCallOptions(
			grpc.MaxCallRecvMsgSize(maxMsgSize),
			grpc.MaxCallSendMsgSize(maxMsgSize),
		),
		grpc.WithInitialWindowSize(streamWinSz),
		grpc.WithInitialConnWindowSize(connWinSz),
	)
}

func main() {
	lis, err := net.Listen("tcp", ":50059")
	if err != nil {
		log.Fatalf("Listen error: %v", err)
	}
	defer lis.Close()

	server := CreateTunedServer()
	go func() {
		_ = server.Serve(lis)
	}()

	conn, err := DialTunedClient("127.0.0.1:50059")
	if err != nil {
		log.Fatalf("Dial failed: %v", err)
	}
	defer conn.Close()

	fmt.Println("High-throughput gRPC connection tuned successfully (32MB payload, 4MB window).")
	server.Stop()
}
```

## Под капотом

HTTP/2 протокол использует фреймы `WINDOW_UPDATE` для уведомления отправителя о свободном буфере в сокете. Увеличение `InitialConnWindowSize` позволяет передавать пакеты непрерывным потоком без ожидания подтверждения получения каждого фрейма.

## Подводные камни

Увеличение лимитов на клиенте, но забытое увеличение на сервере (или наоборот). Лимиты `MaxRecvMsgSize` должны быть согласованы с обеих сторон соединения.
