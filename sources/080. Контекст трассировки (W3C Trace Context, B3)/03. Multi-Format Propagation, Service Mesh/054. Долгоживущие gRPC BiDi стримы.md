# Долгоживущие gRPC BiDi стримы: безопасный Draining и закрытие по EOF

## Условие

Реализуйте двунаправленный потоковый метод (Bidirectional Stream). При получении сигнала SIGTERM сервер должен корректно уведомить клиентов о завершении работы через закрытие стрима (io.EOF), не обрывая соединение аварийно.

### Исходная формулировка

**Long-lived gRPC Streams (BiDi) и Draining.**: Реализуйте BiDi stream. При `GracefulStop` сервер должен отправить `io.EOF` (закрыть stream) клиентам, а не обрывать. Клиент должен обработать `EOF` и реконнектиться. Объясните, почему BiDi streams сложнее drain, чем unary RPC.

## Теория

Обычные унарные вызовы gRPC (Unary RPC) завершаются за миллисекунды. Однако в системах реального времени (чаты, финансовые котировки, телеметрия IoT) соединение держится часами через двунаправленный стрим (`BiDi Streaming`). Если при остановке сервера просто вызвать `GracefulStop()`, он будет ждать завершения стрима бесконечно. Если вызвать жесткий `Stop()`, клиенты получат ошибку `Unavailable: transport is closing`. Правильный паттерн: сервер перехватывает сигнал завершения, рассылает по активным стримам специальное служебное сообщение о закрытии и возвращает `nil` из обработчика метода. На сетевом уровне клиенту отправляется HTTP/2 фрейм с флагом `END_STREAM`, клиент читает `io.EOF` и мягко переподключается к другой ноде.

## Решение по шагам

Определите интерфейс потоковой передачи с контекстом завершения.
Создайте широковещательный канал закрытия drainingChan := make(chan struct{}).
В обработчике стрима используйте select между входящими сообщениями и drainingChan.
При получении сигнала завершите обработку штатным возвратом nil (EOF).
Проверьте отсутствие аварийных ошибок у клиента.

## Код решения

**`bidi_draining.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"log"
	"sync"
	"time"
)

type ChatMessage struct {
	User string
	Text string
}

type BiDiStreamServer struct {
	drainingChan chan struct{}
	mu           sync.Mutex
}

func NewBiDiStreamServer() *BiDiStreamServer {
	return &BiDiStreamServer{
		drainingChan: make(chan struct{}),
	}
}

// StreamHandler имитирует gRPC Bidirectional Stream
func (s *BiDiStreamServer) StreamHandler(ctx context.Context, clientIn <-chan ChatMessage, clientOut chan<- ChatMessage) error {
	log.Println("[Stream] Client connected to BiDi stream.")

	for {
		select {
		case <-s.drainingChan:
			// Сервер выключается: шлем прощальное сообщение и закрываем стрим штатно
			log.Println("[Stream] Server is draining. Notifying client and closing stream gracefully...")
			clientOut <- ChatMessage{User: "SYSTEM", Text: "SERVER_SHUTDOWN_RECONNECT"}
			return nil // Возврат nil шлет HTTP/2 END_STREAM (клиент получает io.EOF)

		case <-ctx.Done():
			return ctx.Err()

		case msg, ok := <-clientIn:
			if !ok {
				return nil
			}
			log.Printf("[Stream] Received from %s: %s", msg.User, msg.Text)
			clientOut <- ChatMessage{User: "ECHO", Text: msg.Text}
		}
	}
}

func (s *BiDiStreamServer) TriggerDrain() {
	s.mu.Lock()
	defer s.mu.Unlock()
	select {
	case <-s.drainingChan:
	default:
		close(s.drainingChan)
	}
}

func main() {
	srv := NewBiDiStreamServer()
	inChan := make(chan ChatMessage, 5)
	outChan := make(chan ChatMessage, 5)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	// Запуск стрима
	streamDone := make(chan error, 1)
	go func() {
		streamDone <- srv.StreamHandler(ctx, inChan, outChan)
	}()

	// Клиент отправляет сообщение
	inChan <- ChatMessage{User: "Alice", Text: "Hello stream"}
	resp := <-outChan
	fmt.Printf("Client received: [%s] %s\n", resp.User, resp.Text)

	// Имитируем SIGTERM и запуск Draining
	log.Println("Simulating SIGTERM draining event...")
	srv.TriggerDrain()

	// Клиент получает уведомление о завершении
	shutdownMsg := <-outChan
	fmt.Printf("Client received shutdown notice: [%s] %s\n", shutdownMsg.User, shutdownMsg.Text)

	err := <-streamDone
	if err == nil || err == io.EOF {
		fmt.Println("Stream cleanly terminated with EOF without transport errors.")
	}
}
```

ℹ️ Корректное завершение gRPC BiDi стримов при Graceful Draining

## Под капотом

Возврат `nil` из стримового метода gRPC заставляет рантайм отправить HTTP/2 DATA кадр с флагом `END_STREAM` (0x1), за которым следует TRAILERS кадр со статусом `codes.OK`. Клиентский метод `stream.Recv()` возвращает ошибку `io.EOF`, что является штатным сигналом закрытия.

## Подводные камни

Вызов `server.GracefulStop()` без уведомления долгоживущих стримов. `GracefulStop()` заблокируется и не завершится, пока клиенты сами не закроют свои стримы.

## На собеседовании

Вопрос на собеседовании в Авито: 'Как корректно остановить gRPC сервер, если на нем висит 50 000 постоянных WebSockets/gRPC стримов?' Ответ: '1) Перестать принимать новые соединения; 2) Закрыть внутренний канал draining; 3) Горутины-обработчики стримов выходят из цикла, отправляя клиентам EOF; 4) Клиенты получают EOF и плавно распределяются на соседние поды с добавлением случайной задержки (jitter)'.
