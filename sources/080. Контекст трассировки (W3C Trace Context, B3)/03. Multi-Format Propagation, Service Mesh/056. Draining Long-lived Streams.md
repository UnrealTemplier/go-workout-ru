# Draining Long-lived Streams: принудительная отмена контекста по дедлайну

## Условие

Реализуйте контроллер стримов, отменяющий контексты всех активных горутин при превышении таймаута Graceful Shutdown, гарантируя выход из GracefulStop().

### Исходная формулировка

**[Draining Long-lived Streams]**: У тебя есть bidirectional stream, который держит соединение часами. `GracefulStop()` будет висеть вечно, дожидаясь его закрытия. Реализуй механизм: при получении `SIGTERM` отправляй всем активным стримам специальное сообщение `ServerShuttingDownError`, заставляя клиентов инициировать разрыв соединения.

## Теория

При реализации серверного стриминга в gRPC горутина обработчика обычно блокируется на `stream.Send()` или чтении канала. Если клиент 'завис' (dead connection) или игнорирует закрытие, метод `GracefulStop()` будет заблокирован навсегда. Чтобы гарантировать завершение работы за отведенный SLA (например, 10 секунд), необходимо связывать контекст каждого активного стрима с родительским `draining context`. При начале процедуры остановки запускается таймер. Если по истечении таймаута стримы не закрылись сами, вызывается функция отмены `cancel()`, что немедленно прерывает блокирующие операции ввода-вывода и освобождает горутины.

## Решение по шагам

Создайте структуру StreamManager с отслеживанием активных контекстов отмены.
Реализуйте регистрацию и дерегистрацию клиентских стримов.
При получении сигнала остановки вызовите мягкое завершение с дедлайном.
Принудительно отмените контексты оставшихся стримов по истечении лимита времени.

## Код решения

**`stream_timeout_drainer.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"
	"time"
)

type StreamSession struct {
	id     string
	cancel context.CancelFunc
}

type StreamManager struct {
	mu       sync.Mutex
	sessions map[string]*StreamSession
}

func NewStreamManager() *StreamManager {
	return &StreamManager{
		sessions: make(map[string]*StreamSession),
	}
}

func (sm *StreamManager) Register(id string, cancel context.CancelFunc) {
	sm.mu.Lock()
	defer sm.mu.Unlock()
	sm.sessions[id] = &StreamSession{id: id, cancel: cancel}
	log.Printf("[Manager] Registered stream %s. Active count: %d", id, len(sm.sessions))
}

func (sm *StreamManager) Unregister(id string) {
	sm.mu.Lock()
	defer sm.mu.Unlock()
	delete(sm.sessions, id)
	log.Printf("[Manager] Unregistered stream %s. Active count: %d", id, len(sm.sessions))
}

// ForceDrainAll принудительно отменяет контексты оставшихся 'зависших' стримов
func (sm *StreamManager) ForceDrainAll() {
	sm.mu.Lock()
	defer sm.mu.Unlock()

	log.Printf("[Manager] Forcibly cancelling %d stubborn active streams...", len(sm.sessions))
	for _, s := range sm.sessions {
		s.cancel()
	}
	sm.sessions = make(map[string]*StreamSession)
}

func main() {
	sm := NewStreamManager()

	// Создаем зависший стрим
	ctx, cancel := context.WithCancel(context.Background())
	sm.Register("client-session-98", cancel)

	streamTerminated := make(chan struct{})
	go func() {
		<-ctx.Done()
		log.Println("[Stream Worker] Context cancelled by drainer. Exiting cleanly.")
		sm.Unregister("client-session-98")
		close(streamTerminated)
	}()

	// Имитируем Graceful Shutdown с жестким лимитом
	log.Println("Shutdown initiated: waiting 1 second before hard cancellation...")
	time.Sleep(1 * time.Second)

	sm.ForceDrainAll()
	<-streamTerminated

	fmt.Println("All streaming goroutines released safely.")
}
```

ℹ️ Управление жизненным циклом долгоживущих стримов с принудительной отменой по таймауту

## Под капотом

Когда контекст стрима отменяется (`ctx.Done()`), внутренний селектор горутины немедленно выходит из ожидания, предотвращая блокировку `serveWG.Wait()` внутри gRPC сервера.

## Подводные камни

Утечка памяти при забытой дерегистрации стримов в блоке `defer sm.Unregister()`. Карта активных сессий будет бесконечно расти, удерживая ссылки на отмененные контексты.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Как избежать дедлока в GracefulStop при наличии подвисших стримов?' Ответ: 'Хранить контексты стримов и отменять их по таймеру дедлайна остановки, либо вызывать жесткий server.Stop() по таймауту'.
