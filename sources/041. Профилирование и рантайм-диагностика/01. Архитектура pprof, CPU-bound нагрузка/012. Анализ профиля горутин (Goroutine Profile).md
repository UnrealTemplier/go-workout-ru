# Анализ профиля горутин (Goroutine Profile): классификация блокировок и выявление Goroutine Leaks

## Условие

Используйте **goroutine profile** для поиска goroutine leaks: какие горутины заблокированы и на чём.

## Теория

Классификация состояний горутин в goroutine profile:
- При снятии дампа горутины группируются по типам ожидания:
  1. `[chan receive]`: ожидание чтения из канала (частая причина утечек — забытый sender).
  2. `[chan send]`: ожидание записи в канал (забытый receiver в небуферизированном канале).
  3. `[select]`: блокировка на конструкции `select` без сработавших веток `case` и без `default`.
  4. `[semacquire]`: ожидание мьютекса `sync.Mutex` или `sync.RWMutex` (борьба за блокировку или дедлок).
  5. `[IO wait]`: ожидание ответа от сетевого сокета в `netpoller` (зависший HTTP/SQL запрос без таймаута).
  6. `[sleep]`: горутина спит в `time.Sleep()`.

## Решение по шагам

1. Смоделируйте структуру сводки профиля горутин.
2. Классифицируйте заблокированные горутины по 5 ключевым состояниям.
3. Рассчитайте долю утекших горутин.
4. Верифицируйте нахождение источника утечки.

## Код решения

**`goroutine_profile_analyzer_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type GoroutineProfileSummary struct {
	TotalGoroutines int
	States          map[string]int
	TopBlockSites   []string
}

func AnalyzeGoroutineDump() GoroutineProfileSummary {
	return GoroutineProfileSummary{
		TotalGoroutines: 1045,
		States: map[string]int{
			"chan receive": 950, // 950 горутин зависли на каналах -> Очевидная УТЕЧКА!
			"IO wait":      70,
			"semacquire":   15,
			"running":      10,
		},
		TopBlockSites: []string{
			"950 @ workerpool.go:42 (workerpool.(*Pool).worker)",
			"70  @ net/http/client.go:180 (net/http.send)",
			"15  @ cache.go:88 (cache.(*RWMutex).RLock)",
		},
	}
}

func TestGoroutineProfileAnalyzer(t *testing.T) {
	summary := AnalyzeGoroutineDump()

	leakPercent := float64(summary.States["chan receive"]) / float64(summary.TotalGoroutines) * 100

	if leakPercent < 90.0 {
		t.Fatalf("Ожидалось выявление критической утечки (>90%%), получено: %.1f%%", leakPercent)
	}

	fmt.Println("Анализ профиля горутин (goroutine profile) успешно подтвержден:")
	fmt.Printf("  • Всего горутин: %d\n", summary.TotalGoroutines)
	fmt.Printf("  • Распределение по состояниям: %v\n", summary.States)
	fmt.Println("  • Топ мест блокировок:")
	for idx, site := range summary.TopBlockSites {
		fmt.Printf("    #%d: %s\n", idx+1, site)
	}
	fmt.Printf("  • Вердикт: 950 горутин заблокированы на workerpool.go:42 (%.1f%% всех горутин сервиса!)\n", leakPercent)
}
```

## Под капотом

Сборщик профиля горутин кратковременно останавливает планировщик Go (STW-фаза на доли миллисекунды), проходит по глобальному массиву всех структур `allgs` (`[]*g`) и считывает текущий счетчик инструкций PC и поле `g.status` каждого объекта.

## Подводные камни

Снимать дамп `goroutine?debug=2` при миллионе запущенных горутин: сериализация текста займет десятки секунд и может забить всю оперативную память. При миллионных пулах горутин снимают `debug=1` (агрегированная сводка).

## На собеседовании

**Вопрос с собеседования:** «Как в продакшене автоматически алертить об утечке горутин до того, как сервис упадет по OOM?»
**Ответ:** Настраивают Prometheus-алерт по метрике `go_goroutines`:
```promql
deriv(go_goroutines[15m]) > 5
```
Если число горутин монотонно растет на протяжении 15 минут без возврата к базовому уровню, дежурный инженер получает уведомление задолго до исчерпания памяти хоста.
