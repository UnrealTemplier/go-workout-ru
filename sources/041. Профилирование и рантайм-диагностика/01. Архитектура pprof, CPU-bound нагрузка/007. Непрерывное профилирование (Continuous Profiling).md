# Непрерывное профилирование (Continuous Profiling): архитектура Pyroscope, Parca и интеграция pyroscope-go

## Условие

Настрой **Continuous Profiling** (Pyroscope/Parca/Cloud Profiler): `github.com/grafana/pyroscope-go`. `pyroscope.Start(pyroscope.Config{ApplicationName: "order-service", ServerAddress: "http://pyroscope:4040"})`. Автоматический профиль 24/7, historical comparison.

## Теория

Эволюция от ad-hoc профилирования к Continuous Profiling:
- **Проблема классического pprof:**
  - Инженер снимает профиль только тогда, когда сервис уже упал или дежурный получил алерт.
  - «Поймать» всплеск нагрузки длительностью 2 секунды вручную невозможно.
- **Continuous Profiling (Непрерывное профилирование 24/7):**
  - Легковесный агент (Pyroscope / Parca) непрерывно собирает профили (CPU, Heap, Goroutines, Mutex) со всех реплик сервиса с микроскопическим оверхедом (< 1% CPU).
  - Сжатые профили сохраняются в специализированную TSDB.
  - Позволяет сравнить профиль сегодня в 14:00 с профилем недельной давности (Diff View) и моментально найти регрессию после недавнего релиза!

## Решение по шагам

1. Создайте модель конфигурации агента `pyroscope.Start`.
2. Задайте имя сервиса `order-service` и адрес сервера `http://pyroscope:4040`.
3. Смоделируйте периодическую отправку профилей.
4. Верифицируйте готовность к непрерывному мониторингу в продакшене.

## Код решения

**`pyroscope_continuous_profiling_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PyroscopeAgentConfig struct {
	ApplicationName string
	ServerAddress   string
	ProfileTypes    []string
	Tags            map[string]string
	Enabled         bool
}

func InitContinuousProfiler(app, server string) PyroscopeAgentConfig {
	return PyroscopeAgentConfig{
		ApplicationName: app,
		ServerAddress:   server,
		ProfileTypes: []string{
			"cpu",
			"inuse_space",
			"inuse_objects",
			"goroutines",
			"mutex_count",
		},
		Tags: map[string]string{
			"region": "ru-central1",
			"env":    "production",
		},
		Enabled: true,
	}
}

func TestPyroscopeContinuousProfiling(t *testing.T) {
	cfg := InitContinuousProfiler("order-service", "http://pyroscope.monitoring:4040")

	if !cfg.Enabled || cfg.ApplicationName != "order-service" || len(cfg.ProfileTypes) != 5 {
		t.Fatalf("Ошибка конфигурации Pyroscope: %+v", cfg)
	}

	fmt.Println("Непрерывный профайлинг (Continuous Profiling Pyroscope) успешно проверен:")
	fmt.Printf("  • Приложение: %s (Env: %s)\n", cfg.ApplicationName, cfg.Tags["env"])
	fmt.Printf("  • Сервер:     %s\n", cfg.ServerAddress)
	fmt.Printf("  • Типы профилей 24/7: %v\n", cfg.ProfileTypes)
	fmt.Println("  • Позволяет находить 5-секундные всплески и регрессии релизов за любой день года!")
}
```

## Под капотом

Pyroscope использует формат деревьев стеков (Trie) и сжатие по колоночному принципу (similar to flamebearer): терабайты профилей за месяц сжимаются в несколько гигабайт дискового пространства.

## Подводные камни

Включать сбор профиля мьютексов с максимальной частотой `runtime.SetMutexProfileFraction(1)` в HighLoad: запись каждого события захвата мьютекса замедлит программу на 30–50%. Для продакшена используют значение от 5 до 100.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Pyroscope от Parca в методах сбора данных?»
**Ответ:** Pyroscope исторически использовал push-модель через SDK приложения (`pyroscope-go`). Parca использует eBPF-агента ядра Linux: она считывает стек-трейсы любых процессов без модификации исходного кода и библиотек Go приложения (Zero-Code Profiling), работая на уровне ядра ОС.
