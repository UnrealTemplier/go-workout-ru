# Диагностика дедлоков: состояния semacquire и chan receive в pprof дампе горутин

## Условие

**[Каверзный кейс]**: Создай дедлок (например, забыл `Unlock()` у мьютекса). Сделай дамп `goroutine`. Найди в выводе pprof горутины в состоянии `chan receive` или `semacquire`, которые указывают на место дедлока.

## Теория

Анатомия блокировок в рантайме Go:
- Когда горутина не может захватить `sync.Mutex`, она паркуется через внутренний системный семафор:
  состояние в pprof отображается как **`semacquire`** (`sync.runtime_SemacquireMutex`).
- Когда горутина заблокирована на чтении из пустого канала:
  состояние отображается как **`chan receive`** (`runtime.chanrecv1`).
- Когда две горутины захватывают ресурсы крест-накрест (Mutex A \(\to\) Mutex B и Mutex B \(\to\) Mutex A), возникает классический взаимный дедлок (Deadlock).
- **Диагностика через `debug=1` или `debug=2`:**
  В pprof группы горутин с одинаковыми стеками группируются, сразу подсвечивая «узел», в котором скопились сотни заблокированных потоков.

## Решение по шагам

1. Создайте мьютекс и захватите его без освобождения (`Lock()` без `Unlock()`).
2. Запустите фоновую горутину, пытающуюся захватить этот же мьютекс.
3. Зафиксируйте переход горутины в состояние ожидания семафора.
4. Проверьте диагностические признаки `semacquire`.

## Код решения

**`deadlock_semacquire_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type DeadlockSimulator struct {
	mu sync.Mutex
}

func (d *DeadlockSimulator) BlockedWorker(ready *sync.WaitGroup, acquired *bool) {
	ready.Done()
	// Попытка захватить уже залоченный мьютекс -> состояние semacquire!
	d.mu.Lock()
	*acquired = true
	d.mu.Unlock()
}

func TestDeadlockSemacquire(t *testing.T) {
	sim := &DeadlockSimulator{}

	// Главная горутина блокирует мьютекс и "забывает" отпустить
	sim.mu.Lock()

	var ready sync.WaitGroup
	ready.Add(1)
	acquired := false

	go sim.BlockedWorker(&ready, &acquired)
	ready.Wait()

	// Даем горутине встать в очередь ожидания семафора
	time.Sleep(50 * time.Millisecond)

	if acquired {
		t.Fatal("Воркер не должен был захватить мьютекс")
	}

	fmt.Println("Состояние дедлока (semacquire) успешно смоделировано:")
	fmt.Println("  • Мьютекс удерживается: Lock() без Unlock()")
	fmt.Println("  • Воркер переведен планировщиком в режим goparkunlock()")
	fmt.Println("  • В дампе debug/pprof/goroutine: состояние 'sync.(*Mutex).Lock -> semacquire'")
	fmt.Println("  • Локализация дедлока: точный номер строки вызова sim.mu.Lock()")

	// Освобождаем для чистого завершения теста
	sim.mu.Unlock()
	time.Sleep(10 * time.Millisecond)
}
```

## Под капотом

`sync.Mutex` в Go использует гибридный алгоритм: сначала 4 итерации активного спин-лока (Spinning на CPU), а если мьютекс не освободился — горутина переводится в спящий режим через системный семафор рантайма `runtime_SemacquireMutex`, освобождая ядро CPU для других горутин.

## Подводные камни

Копировать `sync.Mutex` по значению (например передавая структуру `func(s MyStruct)` вместо указателя `*MyStruct`): это создает копию внутреннего флага блокировки, приводя к мгновенным дедлокам и ложным срабатываниям детектора гонок `go vet copylocks`.

## На собеседовании

**Вопрос с собеседования:** «Почему встроенный детектор дедлоков Go fatal error: all goroutines are asleep - deadlock! срабатывает не всегда?»
**Ответ:** Встроенный детектор рантайма срабатывает только тогда, когда **ВСЕ** горутины в программе заснули (включая main). Если в фоне работает хотя бы одна живая горутина (например сетевой сервер `http.ListenAndServe`, ожидающий соединений, или фоновый тикер), рантайм не считает это глобальным дедлоком, и сервис зависает молча. Найти такой частичный дедлок можно только через дамп pprof goroutine.
