# Диагностика утечки памяти: анализ профиля кучи debug/pprof/heap и поиск аллокаций

## Условие

**[Утечка памяти]**: Напиши программу, которая в бесконечном цикле добавляет элементы в глобальный слайс, не очищая его. Сделай дамп Heap (`debug/pprof/heap`). Найди в pprof строку кода, которая занимает больше всего памяти.

## Теория

Природа утечек памяти в языках со сборщиком мусора:
- В Go нет ручного `free()`, сборщик мусора GC использует триколорный марк-энд-свип (Tri-color Mark & Sweep).
- Объект **не может быть освобожден**, пока до него существует путь по ссылкам от корневых объектов (Root Set: глобальные переменные, стеки активных горутин).
- **Сценарий утечки:**
  - Добавление элементов в срез, привязанный к глобальной переменной или долгоживущему синглтону.
  - Удержание гигантского исходного массива через подстроку или мелкий под-слайс `sub := hugeSlice[:2]`.
- **Профиль кучи `/debug/pprof/heap`:**
  - `inuse_space`: объем памяти, занятый живыми объектами прямо сейчас.
  - `alloc_space`: суммарный объем памяти, выделенный за все время жизни программы (показывает генераторы мусора для GC).

## Решение по шагам

1. Создайте глобальный накопитель данных (срез байтовых блоков).
2. Заполните срез в цикле объектами по 1 МБ без очистки.
3. Продемонстрируйте структуру памяти кучи.
4. Верифицируйте нахождение виновной строки кода через `pprof list`.

## Код решения

**`memory_leak_heap_test.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"testing"
)

// Глобальный накопитель — частая причина утечек в Go
var globalMemoryLeakSink [][]byte

func LeakMemory(chunks int) {
	for i := 0; i < chunks; i++ {
		// Каждая аллокация: 1 МБ
		block := make([]byte, 1024*1024)
		block[0] = 0xFF
		globalMemoryLeakSink = append(globalMemoryLeakSink, block)
	}
}

func TestMemoryLeakHeap(t *testing.T) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// Утечка 10 МБ
	LeakMemory(10)

	runtime.GC() // Принудительный сбор мусора: не сможет удалить globalMemoryLeakSink!
	runtime.ReadMemStats(&m2)

	allocatedMB := float64(m2.HeapAlloc-m1.HeapAlloc) / (1024 * 1024)
	if allocatedMB < 9.0 {
		t.Fatalf("Ожидалось увеличение кучи минимум на 9 МБ, получено: %.2f МБ", allocatedMB)
	}

	fmt.Println("Диагностика утечки памяти в куче успешно подтверждена:")
	fmt.Printf("  • HeapAlloc до утечки:  %.2f МБ\n", float64(m1.HeapAlloc)/(1024*1024))
	fmt.Printf("  • HeapAlloc после утечки: %.2f МБ (Удержано в памяти: %.2f МБ)\n",
		float64(m2.HeapAlloc)/(1024*1024), allocatedMB)
	fmt.Println("  • Команда анализа: go tool pprof http://localhost:6060/debug/pprof/heap")
	fmt.Println("  • В консоли pprof: (pprof) top -inuse_space")
	fmt.Println("  • Строка 'make([]byte, 1024*1024)' занимает 100% живой памяти!")

	// Очистка для изоляции тестов
	globalMemoryLeakSink = nil
	runtime.GC()
}
```

ℹ️ Моделирование классической утечки памяти через глобальный срез и замер HeapAlloc

**`Терминал`**

```bash
# Запуск анализа кучи:
go tool pprof -inuse_space http://localhost:6060/debug/pprof/heap
# (pprof) top
# (pprof) list LeakMemory
# Показана точная строка: block := make([]byte, 1024*1024)
```

## Под капотом

Память в куче Go аллоцируется страницами размером 8 КБ через аллокатор `tcmalloc`-подобной архитектуры (mcache -> mcentral -> mheap). Профиль кучи собирается сэмплированием: по умолчанию `runtime.MemProfileRate = 512 * 1024` (сохраняется срез стека на каждые 512 КБ выделений), что снижает оверхед в продакшене до минимума.

## Подводные камни

Анализировать утечку с флагом `-alloc_space` вместо `-inuse_space`: `-alloc_space` показывает, сколько памяти было выделено суммарно (включая уже удаленный сборщиком мусор). Реальные утечки ищут строго по флагу `-inuse_space`!

## На собеседовании

**Вопрос с собеседования:** «Как под-слайсинг срезов (Sub-slicing) может приводить к скрытым утечкам гигантских объемов памяти?»
**Ответ:** Если функция прочитала из сети массив размером 50 МБ и вернула под-слайс `return buf[:10]`, новый срез указывает на тот же самый базовый массив. Пока жив этот мелкий срез на 10 байт, GC не может освободить весь 50-мегабайтный буфер! Лечение: явно скопировать нужные байты через `copy()` в новый независимый срез.
