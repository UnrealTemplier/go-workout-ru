# Профилирование памяти в бенчмарках: флаги -benchmem, -memprofile и анализ mem.out

## Условие

Напиши бенчмарк, который alloc'ает много памяти. Запусти его с флагами `-benchmem -memprofile=mem.out`. Проанализируй `mem.out` через `go tool pprof`.

## Теория

Связка бенчмаркинга и профайлинга в Go:
- Команда `go test -bench=. -benchmem -memprofile=mem.out`:
  1. Запускает бенчмарки и измеряет параметры аллокаций:
     - `B/op`: количество выделенных байт на операцию.
     - `allocs/op`: количество обращений к аллокатору кучи на операцию.
  2. Генерирует бинарный файл профиля `mem.out`.
- **Анализ профиля `mem.out`:**
  - `go tool pprof -alloc_space mem.out`: показывает, какие функции нагенерировали больше всего мусора за время теста.
  - `go tool pprof -inuse_space mem.out`: показывает, сколько памяти осталось не освобождено на момент окончания бенчмарка.

## Решение по шагам

1. Создайте функцию конкатенации строк через оператор `+` (генерирует много аллокаций).
2. Напишите Benchmark-функцию.
3. Продемонстрируйте замер метрик памяти `B/op` и `allocs/op`.
4. Верифицируйте сбор профиля `mem.out`.

## Код решения

**`string_alloc_bench_test.go`**

```go
package main

import (
	"strings"
	"testing"
)

// Неэффективная функция: конкатенация строк через '+' в цикле
func InefficientConcat(words []string) string {
	var result string
	for _, w := range words {
		result += w + " " // Создает новую аллокацию строки на каждой итерации!
	}
	return result
}

// Оптимизированная функция:strings.Builder с предвыделением
func OptimizedConcat(words []string) string {
	var b strings.Builder
	totalLen := 0
	for _, w := range words {
		totalLen += len(w) + 1
	}
	b.Grow(totalLen)
	for _, w := range words {
		b.WriteString(w)
		b.WriteByte(' ')
	}
	return b.String()
}

func BenchmarkInefficientConcat(b *testing.B) {
	words := []string{"apple", "banana", "cherry", "dragonfruit", "elderberry", "fig", "grape"}
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_ = InefficientConcat(words)
	}
}

func BenchmarkOptimizedConcat(b *testing.B) {
	words := []string{"apple", "banana", "cherry", "dragonfruit", "elderberry", "fig", "grape"}
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_ = OptimizedConcat(words)
	}
}
```

ℹ️ Сравнение неэффективной конкатенации строк и strings.Builder в бенчмарках

**`Терминал`**

```bash
# Запуск бенчмарка со сбором профиля памяти:
go test -bench=. -benchmem -memprofile=mem.out string_alloc_bench_test.go

# Анализ полученного профиля:
go tool pprof -alloc_space mem.out
# (pprof) top
# (pprof) list InefficientConcat
```

## Под капотом

Строки в Go неизменяемы (`immutable`). При вызове `s += w` рантайм выделяет новый блок памяти в куче размером `len(s) + len(w)`, копирует туда старое содержимое и добавляет новое, превращая алгоритм в \(O(N^2)\) по памяти и нагружая сборщик мусора.

## Подводные камни

Забывать вызывать `b.ResetTimer()` перед циклом бенчмарка: если подготовка тестовых данных занимает 100 мс, это время и аллокации попадут в результат первой итерации и исказят профиль.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие флагов pprof -alloc_space и -alloc_objects?»
**Ответ:** 
- `-alloc_space`: показывает суммарный объем в мегабайтах (важно для поиска утечек больших буферов).
- `-alloc_objects`: показывает количество отдельных обращений к аллокатору в штуках. Даже если объекты мелкие (по 16 байт), миллион вызовов аллокатора создаст колоссальное давление на `mcache` и заставит GC работать без остановки.
