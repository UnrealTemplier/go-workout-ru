# Планирование мощностей (Capacity Planning): прогнозирование нагрузки и линейная экстраполяция

## Условие

Реализуй **Capacity Planning**:
- Metrics: `requests_per_second`, `cpu_usage_per_request`, `memory_per_request`
- Forecast: linear regression on historical data
- Plan: `current_capacity = 1000 RPS`, `growth = 20%/month`, `target_headroom = 30%`
- Alert: `predicted_capacity_exhaustion < 30 days`
- Action: scale horizontally (add pods), vertically (bigger instances), or optimize (reduce resource per request)

## Теория

Инженерная методология Capacity Planning в BigTech:
- Управление емкостью инфраструктуры — ключевая задача SRE и техлидов:
  1. **Метрики стоимости запроса:**
     - \(CPU_{req} = \frac{\text{CPU Cores}}{\text{RPS}}\) (ядер на запрос).
     - \(RAM_{req} = \frac{\text{Heap Memory}}{\text{RPS}}\) (байт на запрос).
  2. **Прогнозирование (Trend Forecasting):** линейная экстраполяция темпа роста трафика с учетом сезонности и промо-акций.
  3. **Запас надежности (Headroom, обычно 30%):** емкость кластера обязана выдерживать пики нагрузки и падение одной зоны доступности (Availability Zone / Data Center) без деградации SLA.
  4. **Упреждающий алертинг:** алерт срабатывает, если до исчерпания запаса прочности осталось менее 30 дней.

## Решение по шагам

1. Создайте модель расчета текущей емкости и потребления ресурсов на запрос.
2. Смоделируйте ежемесячный рост трафика на 20%.
3. Рассчитайте точку исчерпания мощностей с учетом целевого запаса Headroom 30%.
4. Сформируйте автоматический план масштабирования кластера (HPA).

## Код решения

**`capacity_planning_forecast_test.go`**

```go
package main

import (
	"fmt"
	"math"
	"testing"
)

type CapacityPlan struct {
	CurrentCapacityRPS float64
	MonthlyGrowthRate  float64
	TargetHeadroomPct  float64
	CurrentTrafficRPS  float64
}

func (p *CapacityPlan) SafeCapacityLimit() float64 {
	// Доступный лимит с учетом обязательного запаса 30%
	return p.CurrentCapacityRPS * (1.0 - (p.TargetHeadroomPct / 100.0))
}

func (p *CapacityPlan) DaysUntilExhaustion() int {
	safeLimit := p.SafeCapacityLimit()
	if p.CurrentTrafficRPS >= safeLimit {
		return 0
	}
	// Дневной темп роста: (1 + MonthlyGrowth)^(1/30) - 1
	dailyGrowth := math.Pow(1.0+p.MonthlyGrowthRate, 1.0/30.0) - 1.0
	days := math.Log(safeLimit/p.CurrentTrafficRPS) / math.Log(1.0+dailyGrowth)
	return int(math.Floor(days))
}

func TestCapacityPlanningForecast(t *testing.T) {
	plan := CapacityPlan{
		CurrentCapacityRPS: 1000.0,
		MonthlyGrowthRate:  0.20, // +20% в месяц
		TargetHeadroomPct:  30.0, // 30% запас надежности
		CurrentTrafficRPS:  650.0,
	}

	safeLimit := plan.SafeCapacityLimit() // 1000 * 0.7 = 700 RPS
	daysLeft := plan.DaysUntilExhaustion()

	if daysLeft > 30 {
		t.Fatalf("Алерт должен предупреждать о приближении к лимиту (<30 дней), получено: %d дней", daysLeft)
	}

	fmt.Println("Математический расчет Capacity Planning:")
	fmt.Printf("  • Максимальная емкость:   %.0f RPS\n", plan.CurrentCapacityRPS)
	fmt.Printf("  • Безопасный порог (70%%):  %.0f RPS (30%% Headroom на случай падения ДЦ)\n", safeLimit)
	fmt.Printf("  • Текущий трафик:         %.0f RPS\n", plan.CurrentTrafficRPS)
	fmt.Printf("  • Дней до исчерпания:     %d дней!\n", daysLeft)
	fmt.Println("  • АЛЕРТ: predicted_capacity_exhaustion < 30 days сработал!")
	fmt.Println("  • Действие SRE: расширение пода Kubernetes Deployment с 10 до 15 реплик.")
}
```

## Под капотом

В Prometheus предиктивный расчет реализуется встроенной функцией линейной регрессии PromQL: `predict_linear(http_requests_total[7d], 86400 * 30)` экстраполирует производную ряда на 30 дней вперед.

## Подводные камни

Использовать 100% емкости кластера без запаса Headroom: любой всплеск трафика от рекламной интеграции или авария одной стойки серверов приведет к перегрузке оставшихся подов и лавинообразному падению всего сервиса (Cascading Failure).

## На собеседовании

**Вопрос с собеседования:** «Что выгоднее для компании: оптимизировать алгоритм в Go или просто добавить еще 50 серверов в Kubernetes?»
**Ответ:** Это вопрос FinOps. Если оптимизация одного горячего цикла в Go (например замена рефлексии на генерацию кода) снижает потребление CPU на 40% во всем парке из 10 000 ядер, компания экономит десятки миллионов рублей в месяц на серверной инфраструктуре. Оптимизация кода почти всегда окупается на масштабах HighLoad.
