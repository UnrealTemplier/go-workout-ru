# Непрерывный профайлинг в Kubernetes: детекция регрессий и интеграция с Pyroscope/Parca

## Условие

Настройте **continuous profiling** через Pyroscope или Parca: автоматический сбор профилей в продакшене для анализа регрессий.

## Теория

Продакшн Continuous Profiling в Kubernetes:
- Классический CI/CD пайплайн проверяет юнит-тесты, но не ловит деградацию производительности (Performance Regression).
- **Схема работы continuous profiling в K8s:**
  1. Каждый под сервиса отправляет профили (CPU, Mem, Goroutines) в кластер Pyroscope/Parca.
  2. В метаданные профиля добавляются теги Git: `service_version=v2.1.0`, `commit_sha=abc123`.
  3. После деплоя новой версии SRE открывает дашборд сравнения версий (Diff View).
  4. Если потребление CPU функцией `json.Unmarshal` выросло на 40%, релиз откатывается автоматически!

## Решение по шагам

1. Создайте модель тегирования профилей релизами сервиса.
2. Смоделируйте сравнение потребления CPU между версиями `v1.0.0` и `v1.1.0`.
3. Рассчитайте процент деградации алгоритма.
4. Верифицируйте принятие решения об откате релиза.

## Код решения

**`continuous_profiling_diff_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type VersionProfile struct {
	Version      string
	CPUPerReqMs  float64
	AllocsPerReq int
}

func DetectPerformanceRegression(oldVer, newVer VersionProfile) (isRegressed bool, cpuDiffPct float64) {
	cpuDiffPct = ((newVer.CPUPerReqMs - oldVer.CPUPerReqMs) / oldVer.CPUPerReqMs) * 100.0
	// Регрессия фиксируется при росте CPU > 15%
	if cpuDiffPct > 15.0 {
		return true, cpuDiffPct
	}
	return false, cpuDiffPct
}

func TestContinuousProfilingDiff(t *testing.T) {
	v1 := VersionProfile{Version: "v1.0.0", CPUPerReqMs: 12.0, AllocsPerReq: 40}
	v2 := VersionProfile{Version: "v1.1.0", CPUPerReqMs: 17.5, AllocsPerReq: 85}

	regressed, diff := DetectPerformanceRegression(v1, v2)

	if !regressed || diff < 40.0 {
		t.Fatalf("Ожидалась фиксация регрессии: regressed=%v, diff=%.1f%%", regressed, diff)
	}

	fmt.Println("Continuous Profiling: Детекция регрессии релизов (Pyroscope/Parca):")
	fmt.Printf("  • Базовая версия %s: %.1f ms CPU/req\n", v1.Version, v1.CPUPerReqMs)
	fmt.Printf("  • Новая версия   %s: %.1f ms CPU/req (Деградация: +%.1f%%)\n", v2.Version, v2.CPUPerReqMs, diff)
	fmt.Println("  • Алертинг: сработал automated canary rollback (откат деплоя в k8s)!")
}
```

ℹ️ Сравнение метрик профилирования между релизами для предотвращения деградации в продакшене

## Под капотом

Системы Continuous Profiling сохраняют профили в виде иерархических графов (Call Trees) с мержем по временным интервалам, позволяя вычислять разность графов \(Graph_{new} - Graph_{old}\) за миллисекунды.

## Подводные камни

Хранить непрерывные профили без Retention-политики: профили сотен микросервисов за год займут десятки терабайт. Настраивают автоматический Downsampling (агрегация старых профилей до 10-минутных средних).

## На собеседовании

**Вопрос с собеседования:** «Чем дифференциальный Flame Graph (Diff Flame Graph) отличается от стандартного?»
**Ответ:** В Diff Flame Graph плашки окрашиваются в красный и синий цвета:
- **Красные плашки:** функции, которые стали потреблять **больше** CPU/памяти по сравнению с базовой версией.
- **Синие плашки:** функции, которые были оптимизированы и стали потреблять **меньше**.
Это позволяет инженеру за 5 секунд понять влияние нового коммита.
