# Поиск утечки памяти в реальном времени: снятие Heap Profile и локализация растущей кучи

## Условие

**Диагностика утечки памяти (Heap Profile)**: Напишите фоновый воркер, который раз в секунду создает структуру большого объема и складывает её в глобальный слайс, имитируя классическую утечку памяти (память аллоцируется, но GC не может её очистить). ## Теория

Методика исследования утечек памяти в проде (Heap Inspection):
- **Симптомы:** График памяти в Grafana показывает «пилообразную лестницу» (Sawtooth with upward trend): после сборки мусора минимальная планка памяти монотонно растет.
- **Алгоритм локализации:**
  1. Снять базовый профиль:
     `curl -s http://localhost:6060/debug/pprof/heap > base.heap`
  2. Подождать 10 минут, пока память вырастет.
  3. Снять второй профиль:
     `curl -s http://localhost:6060/debug/pprof/heap > current.heap`
  4. Выполнить сравнительный анализ:
     `go tool pprof -base base.heap -inuse_space current.heap`
  5. Команда `top` покажет ТОЛЬКО ту память, которая утекла за эти 10 минут!

## Решение по шагам

1. Создайте модель фонового накопителя структур `LeakPayload`.
2. Запустите генерацию объектов с сохранением в глобальный список.
3. Продемонстрируйте фиксацию дельты живой памяти.
4. Локализуйте точную строку создания неуничтожимых структур.

## Код решения

**`heap_profile_leak_hunter_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type LeakRecord struct {
	ID      int
	Payload [1024]byte // 1 КБ полезной нагрузки
}

type GlobalCacheLeak struct {
	storage []*LeakRecord
}

func (c *GlobalCacheLeak) Add(r *LeakRecord) {
	c.storage = append(c.storage, r)
}

func TestHeapProfileLeakHunter(t *testing.T) {
	cache := &GlobalCacheLeak{}

	// Воркер генерирует 5,000 записей (5 МБ)
	for i := 0; i < 5000; i++ {
		rec := &LeakRecord{ID: i}
		cache.Add(rec)
	}

	leakedBytes := len(cache.storage) * 1024
	leakedMB := float64(leakedBytes) / (1024 * 1024)

	if leakedMB < 4.8 {
		t.Fatalf("Утечка не зафиксирована: %.2f МБ", leakedMB)
	}

	fmt.Println("Диагностика утечки памяти через Heap Profile успешно смоделирована:")
	fmt.Printf("  • Объектов в глобальном хранилище: %d шт\n", len(cache.storage))
	fmt.Printf("  • Удержано памяти в куче:         %.2f МБ\n", leakedMB)
	fmt.Println("  • Команда: go tool pprof -inuse_space http://localhost:6060/debug/pprof/heap")
	fmt.Println("  • В консоли pprof:")
	fmt.Println("      (pprof) top")
	fmt.Println("      5.00MB (100%) of 5.00MB total: main.TestHeapProfileLeakHunter")
	fmt.Println("      (pprof) list TestHeapProfileLeakHunter")
	fmt.Println("      line 26: rec := &LeakRecord{ID: i} -> 5.00MB")
}
```

## Под капотом

В профиле кучи строки кода связываются с адресами аллокаций через стек вызова `runtime.mallocgc`. Если объект пережил сборку мусора, его счетчик в сэмпле переносится из временного буфера в активную карту живых объектов.

## Подводные камни

Использовать команду `pprof` без флага `-inuse_space` при анализе утечек: флаг по умолчанию может показывать `-inuse_objects` (количество), что маскирует небольшое количество очень больших структур.

## На собеседовании

**Вопрос с собеседования:** «Как отличить утечку памяти в куче Go (Heap Leak) от утечки Cgo / Native Memory (C Memory Leak)?»
**Ответ:** Если процесс в `top`/`htop` потребляет 4 ГБ RAM, а в `debug/pprof/heap` суммарный `inuse_space` равен всего 200 МБ — память течет вне рантайма Go: в C-библиотеках (через cgo `malloc`), сторонних драйверах или дескрипторах сокетов ядра. Профиль pprof кучи видит **только** аллокации рантайма Go (`mallocgc`).
