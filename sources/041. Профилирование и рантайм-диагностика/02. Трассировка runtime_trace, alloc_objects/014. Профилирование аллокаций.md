# Профилирование аллокаций: выявление генераторов мусора через -alloc_space и -alloc_objects

## Условие

Профилируйте **аллокации**: используйте `pprof` с `-alloc_space` и `-alloc_objects`, чтобы найти функции, создающие больше всего мусора.

## Теория

Разделение аллокаций по объему и количеству:
- Часто сервис страдает не от того, что ему не хватает RAM, а от того, что сборщик мусора GC утилизирует 50% всех ядер процессора.
- **Два режима профилирования аллокаций:**
  1. `pprof -alloc_space`: показывает суммарный объем выделенной памяти в гигабайтах. Позволяет найти функции, аллоцирующие гигантские структуры.
  2. `pprof -alloc_objects`: показывает количество отдельных выделений в штуках (миллионы мелких структур). Позволяет найти места создания миллионов микро-объектов, которые заставляют GC непрерывно сканировать указатели.
- Оптимизация по `-alloc_objects` часто дает куда больший прирост производительности, чем по объему!

## Решение по шагам

1. Создайте сценарий генерации множества мелких объектов (`sync.Pool` кандидат).
2. Смоделируйте отчет профилирования аллокаций.
3. Сопоставьте показатели `alloc_space` и `alloc_objects`.
4. Верифицируйте стратегию оптимизации (переход на пулы объектов).

## Код решения

**`alloc_profile_metrics_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type AllocProfileRecord struct {
	Function     string
	AllocSpaceMB float64
	AllocObjects int
}

func AnalyzeAllocsProfile() []AllocProfileRecord {
	return []AllocProfileRecord{
		{Function: "json.Unmarshal", AllocSpaceMB: 450.0, AllocObjects: 12_500_000},
		{Function: "parser.ParseHeader", AllocSpaceMB: 120.0, AllocObjects: 8_000_000},
		{Function: "logger.FormatLog", AllocSpaceMB: 60.0, AllocObjects: 4_500_000},
	}
}

func TestAllocProfileMetrics(t *testing.T) {
	records := AnalyzeAllocsProfile()

	totalObjects := 0
	for _, r := range records {
		totalObjects += r.AllocObjects
	}

	if totalObjects < 20_000_000 {
		t.Fatalf("Ожидалось выявление миллионов объектов мусора: %d", totalObjects)
	}

	fmt.Println("Профилирование аллокаций кучи (-alloc_space vs -alloc_objects):")
	fmt.Printf("  %-25s %12s %15s\n", "Функция", "Alloc Space", "Alloc Objects")
	for _, r := range records {
		fmt.Printf("  %-25s %10.1f MB %14d шт\n", r.Function, r.AllocSpaceMB, r.AllocObjects)
	}
	fmt.Println("  • json.Unmarshal создал 12.5 МИЛЛИОНОВ объектов! (Главный кандидат на sync.Pool / easyjson)")
}
```

ℹ️ Сравнительный анализ объема памяти и количества объектов в профиле аллокаций

**`Терминал`**

```bash
# Поиск функций, создающих больше всего мусора:
go tool pprof -alloc_objects http://localhost:6060/debug/pprof/allocs
# (pprof) top
# (pprof) list json.Unmarshal

# Поиск функций, выделяющих наибольший объем в мегабайтах:
go tool pprof -alloc_space http://localhost:6060/debug/pprof/allocs
```

## Под капотом

Каждый вызов `new()` или `make()` для объекта, содержащего указатели, регистрируется в mspan-классах аллокатора Go. Сборщик мусора обязан обойти каждый такой объект по графу ссылок. Если заменить структуры без указателей или переиспользовать их через `sync.Pool`, нагрузка на фазу Mark падает до нуля.

## Подводные камни

Оптимизировать `-alloc_space`, не глядя на `-alloc_objects`: сокращение объема с 500 МБ до 400 МБ при сохранении 20 миллионов объектов не снизит утилизацию процессора сборщиком мусора.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go структуры без указателей ([]byte, struct { a, b int }) сканируются сборщиком мусора гораздо быстрее?»
**Ответ:** Если блок памяти в куче не содержит указателей (флаг `noscan` в метаданных класса `mspan`), GC помечает весь блок как «серый/черный» за 1 операцию и вообще не заглядывает внутрь его байтов, экономя такты CPU.
