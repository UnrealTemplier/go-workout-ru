# Реализация непрерывного SSE-канала с контролем отключения клиента

## Условие

Реализуйте Server-Sent Events (SSE): хендлер, который не закрывает соединение, выставляет заголовок `text/event-stream` и периодически отправляет клиенту обновления через `http.Flusher`.

## Теория

SSE с циклом событий обязан слушать `<-r.Context().Done()`:
Если клиент отключается, таймер или канал тиков останавливается, освобождая горутину.

## Решение по шагам

1. Установим `Content-Type: text/event-stream`.
2. Создадим тикер `time.NewTicker`.
3. В `select` будем слушать тикер и `r.Context().Done()`.
4. Проверим корректное завершение при закрытии соединения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func sseStream(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")

	ticker := time.NewTicker(15 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-r.Context().Done():
			fmt.Println("[SSE Server] Клиент отключился, завершаем стрим")
			return
		case t := <-ticker.C:
			fmt.Fprintf(w, "data: ping at %s\n\n", t.Format("15:04:05.000"))
			flusher.Flush()
		}
	}
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(sseStream))
	defer ts.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 40*time.Millisecond)
	defer cancel()

	req, _ := http.NewRequestWithContext(ctx, http.MethodGet, ts.URL, nil)
	resp, _ := http.DefaultClient.Do(req)
	if resp != nil {
		resp.Body.Close()
	}

	time.Sleep(50 * time.Millisecond)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [SSE Server] Клиент отключился, завершаем стрим
```

## Под капотом

Когда соединение закрывается, Netpoller фиксирует событие `HUP/ERR`, и рантайм закрывает канал `Done()` контекста.

## Подводные камни

Если забыть вызвать `flusher.Flush()`, события будут скапливаться во внутреннем буфере и клиент не увидит real-time обновлений.

## На собеседовании

**Вопрос с собеседования:** «Почему SSE потребляет меньше ресурсов, чем WebSocket?»
**Ответ:** SSE работает по обычному однонаправленному HTTP-каналу, не требует сложного фрейминга, маскирования битов и поддержки двустороннего протокола, а также идеально кэшируется и проксируется существующими балансировщиками (Nginx/Envoy).
