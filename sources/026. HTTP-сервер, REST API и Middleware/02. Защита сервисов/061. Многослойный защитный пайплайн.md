# Многослойный защитный пайплайн: Recovery, Auth и Logging Middleware

## Условие

Цепочка middleware: оберните обработчик в middleware логирования, аутентификации и восстановления после паники.

## Теория

Каноническая трехуровневая архитектура защиты HTTP-эндпоинтов в Go:
1. `RecoveryMiddleware` (самый внешний уровень) — перехватывает паники, предотвращая обрыв сокетов.
2. `LoggingMiddleware` — фиксирует метрики каждого запроса (включая перехваченные паники со статусом 500).
3. `AuthMiddleware` — проверяет права доступа до вызова бизнес-логики.
4. `Handler` — целевой обработчик запроса.

## Решение по шагам

1. Реализуем три middleware: `Recovery`, `Logging`, `Auth`.
2. Соберем стек: `Recovery(Logging(Auth(handler)))`.
3. Протестируем успешный запрос.
4. Протестируем паникующий запрос и убедимся, что она залогирована и клиенту отдан код 500.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func RecoveryMW(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				http.Error(w, "Внутренняя ошибка сервера", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}

func LoggingMW(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Printf("[LOG] Запрос %s %s\n", r.Method, r.URL.Path)
		next.ServeHTTP(w, r)
	})
}

func AuthMW(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Header.Get("X-User") == "" {
			http.Error(w, "Требуется авторизация", http.StatusUnauthorized)
			return
		}
		next.ServeHTTP(w, r)
	})
}

func main() {
	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, "Добро пожаловать в защищенную зону")
	})

	pipeline := RecoveryMW(LoggingMW(AuthMW(handler)))
	ts := httptest.NewServer(pipeline)
	defer ts.Close()

	// Запрос с заголовком
	req, _ := http.NewRequest(http.MethodGet, ts.URL, nil)
	req.Header.Set("X-User", "alex")
	res, _ := http.DefaultClient.Do(req)
	res.Body.Close()

	fmt.Println("Статус ответа:", res.StatusCode)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [LOG] Запрос GET /
# Статус ответа: 200
```

## Под капотом

Стек вызовов вложенных функций разворачивается LIFO (Last In, First Out). `RecoveryMW` первым встречает входящий запрос и последним ловит вылетающие паники.

## Подводные камни

Если поместить `RecoveryMW` внутрь `LoggingMW`, то при панике в `AuthMW` или `Handler` внешнее логирование может не зафиксировать статус ответа 500.

## На собеседовании

**Вопрос с собеседования:** «Почему в цепочке Middleware важен строгий порядок регистрации?»
**Ответ:** Неправильный порядок нарушает контракт безопасности: например, если поместить `RateLimiting` после `Auth`, злоумышленник сможет устроить DoS дорогой базой данных паролей до срабатывания ограничений частоты запросов.
