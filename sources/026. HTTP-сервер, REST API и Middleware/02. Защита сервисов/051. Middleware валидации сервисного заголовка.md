# Middleware валидации сервисного заголовка X-API-Key с ранним прерыванием

## Условие

Напиши middleware для проверки заголовка `X-API-Key`. Если ключ неверный или отсутствует, возвращай `http.StatusUnauthorized` (401) и прерывай цепочку (не вызывай `next`).

## Теория

Паттерн API-Key аутентификации широко распространен в B2B и M2M интеграциях. Ключ передается в заголовке `X-API-Key`. Если ключ отсутствует или не проходит валидацию, middleware немедленно прерывает выполнение (Short-Circuiting) без вызова `next.ServeHTTP`.

## Решение по шагам

1. Напишем `APIKeyMiddleware(validKey string, next http.Handler)`.
2. Извлечем заголовок `r.Header.Get("X-API-Key")`.
3. При несовпадении вернем 401 и сделаем `return`.
4. Проверим запросы с ключом и без него.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func APIKeyMiddleware(expectedKey string, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		apiKey := r.Header.Get("X-API-Key")
		if apiKey == "" || apiKey != expectedKey {
			http.Error(w, "Доступ запрещен: отсутствует или невалидный X-API-Key", http.StatusUnauthorized)
			return // Прерываем цепочку!
		}
		next.ServeHTTP(w, r)
	})
}

func main() {
	handler := APIKeyMiddleware("secret-partner-key-99", http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, "Секретные данные шлюза")
	}))

	ts := httptest.NewServer(handler)
	defer ts.Close()

	// 1. Без ключа
	res1, _ := http.Get(ts.URL)
	res1.Body.Close()
	fmt.Println("Без ключа статус:", res1.StatusCode)

	// 2. С валидным ключом
	req, _ := http.NewRequest(http.MethodGet, ts.URL, nil)
	req.Header.Set("X-API-Key", "secret-partner-key-99")
	res2, _ := http.DefaultClient.Do(req)
	res2.Body.Close()
	fmt.Println("С ключом статус: ", res2.StatusCode)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Без ключа статус: 401
# С ключом статус:  200
```

## Под капотом

Проверка заголовка выполняется до любой дорогой бизнес-логики и работы с базой данных, экономя ресурсы CPU.

## Подводные камни

В проде API-ключи проверяются по кэшу Redis или мапе в памяти с хешированием (SHA-256), чтобы исключить утечку открытых ключей из БД.

## На собеседовании

**Вопрос с собеседования:** «Почему для критичных токенов сравнение проводят через crypto/subtle?»
**Ответ:** Для предотвращения атак по сторонним каналам (Side-Channel Timing Attacks). Если злоумышленник может точно замерить время сравнения строк, он способен подобрать ключ посимвольно.
