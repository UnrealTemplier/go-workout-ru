# Стандарты семантики HTTP-методов и обеспечение идемпотентности

## Условие

Используйте правильные HTTP-методы и идемпотентность: `POST` для создания, `PUT` для полного обновления, `PATCH` для частичного, `DELETE` для удаления.

## Теория

Идемпотентность — свойство операции при повторном выполнении приводить к тому же результату, что и при однократном:
- `GET`, `HEAD`, `OPTIONS` — безопасные (Safe) и идемпотентные.
- `PUT`, `DELETE` — идемпотентные (повторный `DELETE` удаляет тот же объект, результат в БД одинаков).
- `POST` — неидемпотентный (повторный запрос создает дубликаты записей).
- `PATCH` — в общем случае неидемпотентный.

## Решение по шагам

1. Реализуем обработчик ресурса документа.
2. Продемонстрируем разницу в поведении POST, PUT, PATCH, DELETE.
3. Проверим идемпотентность повторного вызова DELETE.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type DocStore struct {
	mu   sync.Mutex
	docs map[string]string
}

func main() {
	store := &DocStore{docs: make(map[string]string)}
	mux := http.NewServeMux()

	// POST - создание нового документа (не идемпотентно)
	mux.HandleFunc("POST /docs", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusCreated)
		fmt.Fprint(w, "Doc created")
	})

	// PUT - полная замена (идемпотентно)
	mux.HandleFunc("PUT /docs/{id}", func(w http.ResponseWriter, r *http.Request) {
		id := r.PathValue("id")
		store.mu.Lock()
		store.docs[id] = "full replacement"
		store.mu.Unlock()
		w.WriteHeader(http.StatusOK)
		fmt.Fprint(w, "Doc replaced")
	})

	// DELETE - удаление (идемпотентно)
	mux.HandleFunc("DELETE /docs/{id}", func(w http.ResponseWriter, r *http.Request) {
		id := r.PathValue("id")
		store.mu.Lock()
		delete(store.docs, id)
		store.mu.Unlock()
		w.WriteHeader(http.StatusNoContent)
	})

	ts := httptest.NewServer(mux)
	defer ts.Close()

	// Проверяем идемпотентность DELETE (повторные вызовы возвращают 204)
	req1, _ := http.NewRequest(http.MethodDelete, ts.URL+"/docs/doc1", nil)
	r1, _ := http.DefaultClient.Do(req1)
	r1.Body.Close()

	req2, _ := http.NewRequest(http.MethodDelete, ts.URL+"/docs/doc1", nil)
	r2, _ := http.DefaultClient.Do(req2)
	r2.Body.Close()

	fmt.Printf("DELETE #1 Status: %d\n", r1.StatusCode)
	fmt.Printf("DELETE #2 Status: %d (Идемпотентно!)\n", r2.StatusCode)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# DELETE #1 Status: 204
# DELETE #2 Status: 204 (Идемпотентно!)
```

## Под капотом

Спецификация HTTP/1.1 (RFC 7231) гарантирует клиентам, что идемпотентные методы можно безопасно повторять при сетевых таймаутах.

## Подводные камни

Если в DELETE возвращать 404 при повторном вызове, метод формально теряет статус-код идемпотентности для тупых клиентов, хотя состояние базы данных остается тем же.

## На собеседовании

**Вопрос с собеседования:** «Как сделать POST-запрос платежа идемпотентным?»
**Ответ:** Использовать заголовок `Idempotency-Key` (UUID). Сервер перед списанием средств сохраняет ключ в Redis со статусом `IN_PROGRESS`. При повторном запросе с тем же ключом сервер возвращает сохраненный результат предыдущей транзакции без повторного списания денег.
