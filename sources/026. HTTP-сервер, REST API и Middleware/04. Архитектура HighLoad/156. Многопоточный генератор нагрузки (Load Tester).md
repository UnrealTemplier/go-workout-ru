# Многопоточный генератор нагрузки (Load Tester) со сбором статистики перцентилей

## Условие

Создайте нагрузочный тест: HTTP-клиент, который конкурентно отправляет N запросов на сервер (с горутинами) и собирает статистику (количество успешных, ошибок, среднее время ответа).

### Исходная формулировка

Создайте нагрузочный тест: HTTP-клиент, который конкурентно отправляет N запросов на сервер (с горутинами) и собирает статистику (количество успешных, ошибок, среднее время ответа).

## Теория

Паттерн нагрузочного тестирования (Load Benchmark):
- Запуск \(C\) параллельных горутин-воркеров.
- Отправка суммарно \(N\) запросов.
- Атомарный подсчет успешных и ошибочных ответов.
- Расчет средней задержки (Average Latency) и пропускной способности (RPS).

## Решение по шагам

1. Создадим быстрый целевой сервер.
2. Запустим 5 параллельных горутин.
3. Отправим 20 запросов.
4. Рассчитаем и выведем статистику.

## Код решения

**`load_tester.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"sync/atomic"
	"time"
)

type LoadStats struct {
	success atomic.Uint64
	errors  atomic.Uint64
	totalNs atomic.Int64
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(2 * time.Millisecond)
		w.WriteHeader(http.StatusOK)
	}))
	defer ts.Close()

	totalRequests := 25
	concurrency := 5

	var stats LoadStats
	var wg sync.WaitGroup
	jobs := make(chan struct{}, totalRequests)
	for i := 0; i < totalRequests; i++ {
		jobs <- struct{}{}
	}
	close(jobs)

	startBench := time.Now()

	for w := 0; w < concurrency; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for range jobs {
				t0 := time.Now()
				res, err := http.Get(ts.URL)
				lat := time.Since(t0)

				if err == nil && res.StatusCode == http.StatusOK {
					stats.success.Add(1)
					stats.totalNs.Add(int64(lat))
					res.Body.Close()
				} else {
					stats.errors.Add(1)
				}
			}
		}()
	}

	wg.Wait()
	totalDuration := time.Since(startBench)

	success := stats.success.Load()
	avgLatency := time.Duration(0)
	if success > 0 {
		avgLatency = time.Duration(stats.totalNs.Load() / int64(success))
	}

	fmt.Println("=== РЕЗУЛЬТАТЫ НАГРУЗОЧНОГО ТЕСТА ===")
	fmt.Printf("  • Всего запросов:   %d\n", totalRequests)
	fmt.Printf("  • Успешных (200):   %d\n", success)
	fmt.Printf("  • Ошибок:           %d\n", stats.errors.Load())
	fmt.Printf("  • Средняя латентность: %v\n", avgLatency.Round(time.Microsecond))
	fmt.Printf("  • Общее время теста:   %v\n", totalDuration.Round(time.Millisecond))
}
```

**`Терминал`**

```bash
go run load_tester.go
# Вывод:
# === РЕЗУЛЬТАТЫ НАГРУЗОЧНОГО ТЕСТА ===
#   • Всего запросов:   25
#   • Успешных (200):   25
#   • Ошибок:           0
#   • Средняя латентность: 2ms
#   • Общее время теста:   12ms
```

## Под капотом

Использование общего канала `jobs` реализует пул воркеров (Worker Pool), равномерно распределяя задачи между горутинами по мере их освобождения.

## Подводные камни

Использование `http.DefaultClient` для миллионов запросов в тесте быстро исчерпает сокеты из-за дефолтного `MaxIdleConnsPerHost: 2`. В нагрузочных тестах настраивают кастомный `Transport{MaxIdleConnsPerHost: 1000}`.

## На собеседовании

**Вопрос с собеседования:** «Почему средняя задержка (Average Latency) обманчива при оценке производительности API?»
**Ответ:** Среднее значение скрывает выбросы. Если 99% пользователей получают ответ за 5 мс, а 1% ждет 10 секунд, среднее арифметическое покажет приемлемый результат. В BigTech смотрят строго на перцентили: p95, p99 и p99.9 (хвостовая задержка / Tail Latency).
