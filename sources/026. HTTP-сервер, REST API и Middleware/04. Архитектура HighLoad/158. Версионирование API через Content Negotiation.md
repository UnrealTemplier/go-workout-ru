# Версионирование API через Content Negotiation и заголовки Vendor Accept

## Условие

Напиши **HTTP API с Versioning**: маршрутизация по `Accept: application/vnd.myapp.v1+json` vs `v2`. Или по URL `/v1/users` vs `/v2/users`. Реализуй обе версии с разными структурами ответа.

### Исходная формулировка

Напиши **HTTP API с Versioning**: маршрутизация по `Accept: application/vnd.myapp.v1+json` vs `v2`. Или по URL `/v1/users` vs `/v2/users`. Реализуй обе версии с разными структурами ответа.

## Теория

Стандарт версионирования Vendor Accept Header:
Клиент передает версию в заголовке `Accept: application/vnd.company.v1+json` или `v2+json`.
Преимущества:
- URI ресурса остается чистым и постоянным (`/users`).
- Идеально соответствует принципам RESTful архитектуры.
- Позволяет легко поддерживать обратную совместимость.

## Решение по шагам

1. Опишем структуры пользователя для v1 (string ID) и v2 (int ID + Profile).
2. Проанализируем заголовок `Accept`.
3. Отдадим соответствующую структуру.
4. Проверим работу обеих версий API.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
)

type UserV1 struct {
	ID   string `json:"id"`
	Name string `json:"name"`
}

type UserV2 struct {
	ID        int      `json:"id"`
	FullName  string   `json:"full_name"`
	Roles     []string `json:"roles"`
	IsPremium bool     `json:"is_premium"`
}

func versionedUsersHandler(w http.ResponseWriter, r *http.Request) {
	accept := r.Header.Get("Accept")

	if strings.Contains(accept, "application/vnd.myapp.v2+json") {
		w.Header().Set("Content-Type", "application/vnd.myapp.v2+json")
		_ = json.NewEncoder(w).Encode(UserV2{
			ID:        42,
			FullName:  "Олег Смирнов",
			Roles:     []string{"admin", "editor"},
			IsPremium: true,
		})
		return
	}

	// По умолчанию отдаем v1
	w.Header().Set("Content-Type", "application/vnd.myapp.v1+json")
	_ = json.NewEncoder(w).Encode(UserV1{
		ID:   "usr_42",
		Name: "Олег",
	})
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(versionedUsersHandler))
	defer ts.Close()

	// 1. Клиент запрашивает v1
	reqV1, _ := http.NewRequest(http.MethodGet, ts.URL+"/users", nil)
	reqV1.Header.Set("Accept", "application/vnd.myapp.v1+json")
	res1, _ := http.DefaultClient.Do(reqV1)
	b1, _ := io.ReadAll(res1.Body)
	res1.Body.Close()
	fmt.Printf("[API v1] %s", string(b1))

	// 2. Клиент запрашивает v2
	reqV2, _ := http.NewRequest(http.MethodGet, ts.URL+"/users", nil)
	reqV2.Header.Set("Accept", "application/vnd.myapp.v2+json")
	res2, _ := http.DefaultClient.Do(reqV2)
	b2, _ := io.ReadAll(res2.Body)
	res2.Body.Close()
	fmt.Printf("[API v2] %s", string(b2))
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [API v1] {"id":"usr_42","name":"Олег"}
# [API v2] {"id":42,"full_name":"Олег Смирнов","roles":["admin","editor"],"is_premium":true}
```

## Под капотом

Маршрутизация по заголовку `Accept` позволяет сохранять персистентные ссылки на сущности (Permalinks) неизменными независимо от смены версии API.

## Подводные камни

Браузеры при прямом переходе по URL не умеют кастомизировать заголовок `Accept`. Поэтому для общедоступных публичных API версионирование через URL-префиксы (`/api/v1/`) остается более практичным.

## На собеседовании

**Вопрос с собеседования:** «Как поддерживать заголовок Vary при версионировании через Accept?»
**Ответ:** Сервер обязан отдавать заголовок `Vary: Accept`. Это сообщает промежуточным кэширующим прокси и CDN, что ответ зависит от заголовка `Accept`, предотвращая отдачу закэшированного JSON v1 клиенту, который запросил v2.
