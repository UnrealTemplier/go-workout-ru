# WebSocket-клиент на Go: подключение, отправка фреймов и прием ответов

## Условие

Напишите WebSocket-клиент на Go, который подключается к вашему серверу, отправляет сообщение и читает ответ.

## Теория

WebSocket-клиент в Go реализует:
1. Выполнение запроса рукопожатия `GET` с заголовками `Upgrade: websocket`.
2. Валидацию ответа `101 Switching Protocols`.
3. Отправку текстовых или бинарных фреймов.
4. Чтение потока сообщений до закрытия сокета.

## Решение по шагам

1. Создадим эхо-сервер на базе стандартного Hijacker.
2. Реализуем клиентское подключение с заголовками рукопожатия.
3. Отправим тестовое сообщение.
4. Проверим чтение эхо-ответа.

## Код решения

**`main.go`**

```go
package main

import (
	"bufio"
	"fmt"
	"net/http"
	"net/http/httptest"
)

func echoHijackServer(w http.ResponseWriter, r *http.Request) {
	hijacker, ok := w.(http.Hijacker)
	if !ok {
		return
	}
	conn, bufrw, err := hijacker.Hijack()
	if err != nil {
		return
	}
	defer conn.Close()

	// 101 Ответ рукопожатия
	_, _ = bufrw.WriteString("HTTP/1.1 101 Switching Protocols\r\nUpgrade: websocket\r\nConnection: Upgrade\r\n\r\n")
	_ = bufrw.Flush()

	// Читаем сообщение клиента
	msg, _ := bufrw.ReadString('\n')
	// Отправляем эхо
	_, _ = bufrw.WriteString("ECHO: " + msg)
	_ = bufrw.Flush()
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(echoHijackServer))
	defer ts.Close()

	// Клиентское подключение
	req, _ := http.NewRequest(http.MethodGet, ts.URL, nil)
	req.Header.Set("Upgrade", "websocket")
	req.Header.Set("Connection", "Upgrade")

	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	fmt.Printf("[Client] Подключено со статусом: %d\n", resp.StatusCode)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Client] Подключено со статусом: 101
```

## Под капотом

После подтверждения 101 статус-кода сокет переходит в полнодуплексный режим: клиент и сервер могут слать данные независимо в двух параллельных горутинах.

## Подводные камни

По спецификации RFC 6455 все сообщения, отправляемые клиентом на сервер, обязаны быть маскированы 4-байтовой маской (Client-to-Server Masking).

## На собеседовании

**Вопрос с собеседования:** «Зачем спецификация WebSocket требует обязательного маскирования фреймов от клиента к серверу?»
**Ответ:** Для предотвращения атак Cache Poisoning на устаревшие прозрачные прокси-серверы. Без маскирования вредоносный скрипт в браузере мог бы сымитировать HTTP-запрос внутри полезной нагрузки WebSocket и отравить кэш прокси-сервера.
