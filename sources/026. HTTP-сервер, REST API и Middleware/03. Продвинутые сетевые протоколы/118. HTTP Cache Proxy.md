# HTTP Cache Proxy: кэширование ответов в памяти с проверкой TTL и Cache-Control

## Условие

Напиши **HTTP Cache Proxy**: слушает `:8080`, проверяет кеш (`map[string]cachedResponse` + `sync.RWMutex`) перед проксированием. Если ответ в кеше и не протух — верни из кеша. Иначе — проксируй, сохрани в кеш с TTL. Используй `Cache-Control` заголовки.

## Теория

Кэширующий прокси-сервер (Caching Reverse Proxy):
1. Проверяет наличие ответа в in-memory кэше по ключу `r.URL.Path`.
2. Если кэш валиден (`time.Now().Before(expiresAt)`), возвращает ответ со статусом `X-Cache: HIT`.
3. При промахе (`X-Cache: MISS`) пересылает запрос бэкенду, кэширует тело и отдает клиенту.

## Решение по шагам

1. Создадим структуру `CachedEntry` со сроком экспирации.
2. Реализуем проверку кэша с `sync.RWMutex`.
3. Запросим ресурс дважды и зафиксируем HIT на втором вызове.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type CacheItem struct {
	Body      []byte
	ExpiresAt time.Time
}

type CachingProxy struct {
	mu      sync.RWMutex
	storage map[string]CacheItem
	backend *httptest.Server
}

func (p *CachingProxy) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	key := r.URL.Path

	p.mu.RLock()
	item, found := p.storage[key]
	p.mu.RUnlock()

	if found && time.Now().Before(item.ExpiresAt) {
		w.Header().Set("X-Cache", "HIT")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write(item.Body)
		return
	}

	// Cache MISS -> идем на бэкенд
	resp, err := http.Get(p.backend.URL + key)
	if err != nil {
		http.Error(w, "Gateway Error", http.StatusBadGateway)
		return
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)

	// Сохраняем в кэш с TTL 1 минута
	p.mu.Lock()
	p.storage[key] = CacheItem{
		Body:      body,
		ExpiresAt: time.Now().Add(1 * time.Minute),
	}
	p.mu.Unlock()

	w.Header().Set("X-Cache", "MISS")
	w.WriteHeader(resp.StatusCode)
	_, _ = w.Write(body)
}

func main() {
	backend := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, "Динамический контент бэкенда")
	}))
	defer backend.Close()

	proxy := &CachingProxy{
		storage: make(map[string]CacheItem),
		backend: backend,
	}
	proxyServer := httptest.NewServer(proxy)
	defer proxyServer.Close()

	// 1. Первый запрос (MISS)
	r1, _ := http.Get(proxyServer.URL + "/news")
	fmt.Printf("[Запрос 1] X-Cache: %s\n", r1.Header.Get("X-Cache"))
	r1.Body.Close()

	// 2. Второй запрос (HIT)
	r2, _ := http.Get(proxyServer.URL + "/news")
	fmt.Printf("[Запрос 2] X-Cache: %s\n", r2.Header.Get("X-Cache"))
	r2.Body.Close()
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Запрос 1] X-Cache: MISS
# [Запрос 2] X-Cache: HIT
```

## Под капотом

Чтение из кэша с `RLock` выполняется параллельно сотнями горутин без взаимных блокировок.

## Подводные камни

Кэширование ответов с заголовком `Set-Cookie` или приватными данными пользователей — критическая уязвимость утечки сессий между клиентами.

## На собеседовании

**Вопрос с собеседования:** «Что такое Cache Stampede (Dog-piling) и как от него защититься в Go?»
**Ответ:** Ситуация, когда в момент истечения TTL популярного ключа кэша тысячи параллельных запросов одновременно получают MISS и все вместе бегут в базу данных, роняя её. Решение: использование библиотеки `golang.org/x/sync/singleflight`, которая объединяет параллельные запросы к одному ключу в один единственный запрос к бэкенду.
