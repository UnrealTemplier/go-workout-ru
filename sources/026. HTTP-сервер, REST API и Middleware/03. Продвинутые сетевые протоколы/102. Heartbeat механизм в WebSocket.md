# Heartbeat механизм в WebSocket: периодические фреймы Ping/Pong для выявления мертвых соединений

## Условие

Реализуйте "пинг-понг" фреймы на уровне WebSocket для поддержания соединения активным (Keep-Alive) и обнаружения "мертвых" клиентов (например, если пользователь выдернул сетевой кабель или выключил Wi-Fi).

### Исходная формулировка

Реализуйте "пинг-понг" фреймы на уровне WebSocket для поддержания соединения активным (Keep-Alive) и обнаружения "мертвых" клиентов (например, если пользователь выдернул网线/выключил Wi-Fi).

## Теория

Спецификация WebSocket RFC 6455 включает управляющие фреймы:
- `Ping` (Opcode 0x9) — запрос проверки активности.
- `Pong` (Opcode 0xA) — обязательный немедленный ответ на Ping с теми же данными.
Если клиент внезапно потерял связь без отправки TCP FIN, ОС сервера не узнает об этом часами без регулярных Ping-проверок (Half-Open Socket leak).

## Решение по шагам

1. Создадим структуру мониторинга `HeartbeatTracker`.
2. Запустим периодический таймер отправки `Ping`.
3. Зафиксируем получение `Pong` от клиента.
4. При отсутствии ответа закроем соединение по таймауту.

## Код решения

**`ws_heartbeat.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type HeartbeatMonitor struct {
	lastPong time.Time
}

func (m *HeartbeatMonitor) Start(ctx context.Context, timeout time.Duration) {
	ticker := time.NewTicker(30 * time.Millisecond)
	defer ticker.Stop()

	m.lastPong = time.Now()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			// Проверяем время с последнего Pong
			if time.Since(m.lastPong) > timeout {
				fmt.Printf("[HEARTBEAT TIMEOUT] Клиент не ответил на Pong вовремя (прошло %v). Закрываем сокет!\n",
					time.Since(m.lastPong).Round(time.Millisecond))
				return
			}
			fmt.Println("[WS Server] -> Отправлен Ping-фрейм")
		}
	}
}

func (m *HeartbeatMonitor) HandlePong() {
	m.lastPong = time.Now()
	fmt.Println("[WS Server] <- Получен Pong-фрейм от клиента")
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	monitor := &HeartbeatMonitor{}

	go monitor.Start(ctx, 80*time.Millisecond)

	time.Sleep(35 * time.Millisecond)
	monitor.HandlePong() // Клиент ответил

	// Клиент "умер" (выдернули провод)
	time.Sleep(120 * time.Millisecond)
}
```

**`Терминал`**

```bash
go run ws_heartbeat.go
# Вывод:
# [WS Server] -> Отправлен Ping-фрейм
# [WS Server] <- Получен Pong-фрейм от клиента
# [WS Server] -> Отправлен Ping-фрейм
# [WS Server] -> Отправлен Ping-фрейм
# [HEARTBEAT TIMEOUT] Клиент не ответил на Pong вовремя (прошло 85ms). Закрываем сокет!
```

## Под капотом

WebSocket-фреймы Ping/Pong имеют размер полезной нагрузки не более 125 байт и обрабатываются сетевым стеком на лету без прерывания передачи данных.

## Подводные камни

Промежуточные NAT-роутеры и файрволы сбрасывают неактивные TCP-соединения через 60 секунд. Ping-фреймы с интервалом 30–50 секунд сохраняют сокет активным в таблице трансляций NAT.

## На собеседовании

**Вопрос с собеседования:** «Почему TCP Keep-Alive на уровне ОС не заменяет WebSocket Ping/Pong?»
**Ответ:** Стандартный TCP Keep-Alive в Linux по умолчанию срабатывает только через 2 часа (`tcp_keepalive_time = 7200`). Кроме того, TCP Keep-Alive подтверждает только то, что жив сетевой стек ядра ОС, но не гарантирует, что само пользовательское приложение или вкладка браузера не зависли намертво.
