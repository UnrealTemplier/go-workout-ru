# Server Streaming RPC: непрерывная потоковая передача тикеров времени клиенту

## Условие

Реализуйте **Server Streaming RPC**: клиент отправляет один запрос, а сервер потоком отправляет множество ответов (например, тикеры времени или ленту новостей).

## Теория

Паттерн Server Streaming:
Клиент делает один HTTP-запрос. Сервер оставляет соединение открытым и непрерывно передает поток сообщений (чанки или SSE фреймы) клиенту по мере их генерации.

## Решение по шагам

1. Создадим обработчик потока.
2. Проверим поддержку интерфейса `http.Flusher`.
3. В цикле отправим 4 тика с паузой.
4. Клиент вычитает поток в реальном времени.

## Код решения

**`main.go`**

```go
package main

import (
	"bufio"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func streamTimeTicks(w http.ResponseWriter, r *http.Request) {
	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Streaming not supported", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "text/plain")
	w.Header().Set("Transfer-Encoding", "chunked")

	for i := 1; i <= 3; i++ {
		fmt.Fprintf(w, "Тик #%d: %s\n", i, time.Now().Format("15:04:05.000"))
		flusher.Flush()
		time.Sleep(25 * time.Millisecond)
	}
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(streamTimeTicks))
	defer ts.Close()

	resp, _ := http.Get(ts.URL)
	defer resp.Body.Close()

	scanner := bufio.NewScanner(resp.Body)
	for scanner.Scan() {
		fmt.Printf("[Stream Chunk Received] %s\n", scanner.Text())
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Stream Chunk Received] Тик #1: ...
# [Stream Chunk Received] Тик #2: ...
# [Stream Chunk Received] Тик #3: ...
```

## Под капотом

Заголовок `Transfer-Encoding: chunked` в HTTP/1.1 позволяет передавать данные неопределенной длины частями без указания `Content-Length`.

## Подводные камни

Не буферизуйте вывод на стороне прокси: в Nginx для стриминга необходимо отключать буферизацию `proxy_buffering off;` или выставлять заголовок `X-Accel-Buffering: no`.

## На собеседовании

**Вопрос с собеседования:** «Как Server Streaming реализован в gRPC под капотом?»
**Ответ:** Клиент шлет один HTTP/2 HEADERS фрейм с методом. Сервер отвечает HEADERS фреймом, а затем шлет множество HTTP/2 DATA фреймов с бинарными Protobuf сообщениями. В конце сервер отправляет трейлер HEADERS с `grpc-status: 0` (OK).
