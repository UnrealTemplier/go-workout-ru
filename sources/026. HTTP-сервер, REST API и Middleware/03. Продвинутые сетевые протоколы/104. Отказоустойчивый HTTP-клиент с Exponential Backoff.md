# Отказоустойчивый HTTP-клиент с Exponential Backoff и контекстным контролем

## Условие

Реализуйте HTTP-клиент с таймаутом и повторными попытками: если запрос не удался, повторить до 3 раз с экспоненциальной задержкой.

## Теория

Паттерн Retry with Exponential Backoff:
При временных ошибках сети или 5xx статусах клиент повторяет запрос с экспоненциально возрастающей задержкой:
\(\Delta t = 2^{\text{attempt}} \times \text{base\_delay}\) (например: 10ms, 20ms, 40ms). Это предотвращает перегрузку восстанавливающегося сервера (Thundering Herd Problem).

## Решение по шагам

1. Создадим функцию `ExecuteWithRetry(client, req, maxRetries)`.
2. Проверим ошибки сети и статус-коды `>= 500`.
3. Вычислим задержку и подождем через `select` с `ctx.Done()`.
4. Протестируем успешное восстановление на 3-й попытке.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"time"
)

func DoWithRetry(ctx context.Context, client *http.Client, url string, maxRetries int) (*http.Response, error) {
	baseDelay := 10 * time.Millisecond

	for attempt := 0; attempt < maxRetries; attempt++ {
		req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
		resp, err := client.Do(req)

		// Повторяем при сетевой ошибке или 5xx статусе бэкенда
		if err == nil && resp.StatusCode < 500 {
			return resp, nil
		}

		if resp != nil {
			resp.Body.Close()
		}

		delay := baseDelay * (1 << attempt) // 10ms, 20ms, 40ms...
		fmt.Printf("[Retry Client] Попытка #%d не удалась. Пауза перед ретраем: %v\n", attempt+1, delay)

		select {
		case <-time.After(delay):
		case <-ctx.Done():
			return nil, ctx.Err()
		}
	}
	return nil, fmt.Errorf("все %d попыток исчерпаны", maxRetries)
}

func main() {
	var attempts atomic.Int32

	// Сервер сбоит первые 2 раза, на 3-й отвечает успехом
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		count := attempts.Add(1)
		if count < 3 {
			http.Error(w, "Временный сбой", http.StatusServiceUnavailable) // 503
			return
		}
		fmt.Fprint(w, "Успех после ретраев!")
	}))
	defer ts.Close()

	client := &http.Client{Timeout: 1 * time.Second}
	resp, err := DoWithRetry(context.Background(), client, ts.URL, 4)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("[Client Final] Status: %d, Response: %s\n", resp.StatusCode, string(body))
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Retry Client] Попытка #1 не удалась. Пауза перед ретраем: 10ms
# [Retry Client] Попытка #2 не удалась. Пауза перед ретраем: 20ms
# [Client Final] Status: 200, Response: Успех после ретраев!
```

## Под капотом

Операция сдвига битов `1 << attempt` вычисляет степень двойки \(2^{\text{attempt}}\) за 1 тактовую инструкцию процессора.

## Подводные камни

Никогда не ретрайте неидемпотентные `POST` запросы создания платежей или заказов без заголовка идемпотентности, иначе деньги с клиента спишутся несколько раз!

## На собеседовании

**Вопрос с собеседования:** «Зачем к Exponential Backoff добавляют случайный шум (Full Jitter)?»
**Ответ:** Если упал общий сервис, тысячи клиентов одновременно начнут слать повторные запросы синхронными пачками через одинаковые интервалы времени. Jitter размазывает запросы случайным образом во времени, снимая резонансную пиковую нагрузку с базы данных.
