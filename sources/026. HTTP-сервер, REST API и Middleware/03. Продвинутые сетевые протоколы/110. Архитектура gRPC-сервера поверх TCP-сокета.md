# Архитектура gRPC-сервера поверх TCP-сокета и мультиплексирования HTTP/2

## Условие

Запустите gRPC-сервер, слушающий TCP-порт (gRPC работает поверх HTTP/2).

## Теория

gRPC функционирует поверх протокола HTTP/2:
- Передача бинарных кадров (DATA, HEADERS).
- Мультиплексирование сотен одновременных RPC в рамках одного TCP-соединения.
- Сжатие заголовков через алгоритм HPACK.
- Двусторонний стриминг.

## Решение по шагам

1. Создадим слушающий TCP-сокет `net.Listen("tcp", ":0")`.
2. Продемонстрируем концепцию регистрации обработчика в цикле приема соединений.
3. Проверим запуск и чистое закрытие листенера.

## Код решения

**`grpc_socket_demo.go`**

```go
package main

import (
	"fmt"
	"net"
)

func main() {
	// Открываем слушающий TCP сокет на динамическом порту
	lis, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer lis.Close()

	fmt.Printf("[gRPC Core] Слушающий TCP-сокет открыт на: %s\n", lis.Addr().String())
	fmt.Println("[gRPC Core] Транспортный уровень готов к рукопожатию HTTP/2 фреймов")
}
```

**`Терминал`**

```bash
go run grpc_socket_demo.go
# Вывод:
# [gRPC Core] Слушающий TCP-сокет открыт на: 127.0.0.1:...
# [gRPC Core] Транспортный уровень готов к рукопожатию HTTP/2 фреймов
```

## Под капотом

gRPC-сервер читает заголовок `Content-Type: application/grpc` и мультиплексирует запросы по номерам Stream ID протокола HTTP/2.

## Подводные камни

Обычные L4-балансировщики не умеют балансировать HTTP/2 стримы, отправляя все запросы на один бэкенд, пока открыт сокет. Для gRPC требуется L7-балансировка (Envoy).

## На собеседовании

**Вопрос с собеседования:** «Почему классический круглый робин (Round-Robin) L4-балансировщика не работает с gRPC?»
**Ответ:** gRPC держит одно постоянное TCP-соединение (Keep-Alive) и передает тысячи запросов внутри него в виде HTTP/2 стримов. L4 балансировщик балансирует только TCP-соединения, поэтому все запросы будут бесконечно идти на один и тот же под.
