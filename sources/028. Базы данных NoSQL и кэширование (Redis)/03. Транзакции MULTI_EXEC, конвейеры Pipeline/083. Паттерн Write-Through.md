# Паттерн Write-Through: сквозная синхронизация базы данных и кэша

## Условие

Реализуй **Write-Through cache**: `CreateUser` сначала пишет в БД, затем инвалидирует/обновляет кеш. `UpdateUser` — то же. Покажи консистентность.

## Теория

В паттерне **Write-Through** запись данных всегда проходит через кэширующий слой:
1. Приложение вызывает метод `CreateUser` или `UpdateUser`.
2. Репозиторий атомарно обновляет основную базу данных (PostgreSQL).
3. Затем сразу обновляет (или инвалидирует) запись в Redis.
Это гарантирует, что последующие запросы на чтение не увидят устаревшие данные.

## Решение по шагам

1. Создайте структуру `UserWriteThroughRepository`.
2. Реализуйте методы `CreateUser` и `UpdateUser`.
3. Продемонстрируйте обновление кэша при модификации данных.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type User struct {
	ID    int64  `json:"id"`
	Email string `json:"email"`
}

type UserRepo struct {
	rdb *redis.Client
}

func (r *UserRepo) CreateUser(ctx context.Context, u User) error {
	// 1. Запись в PostgreSQL (INSERT INTO users ...)
	fmt.Printf("[PostgreSQL] INSERT INTO users VALUES (%d, '%s')\n", u.ID, u.Email)

	// 2. Синхронное обновление кэша
	key := fmt.Sprintf("user:%d", u.ID)
	data, _ := json.Marshal(u)
	return r.rdb.Set(ctx, key, data, 10*time.Minute).Err()
}

func (r *UserRepo) UpdateUser(ctx context.Context, u User) error {
	// 1. Обновление в PostgreSQL (UPDATE users ...)
	fmt.Printf("[PostgreSQL] UPDATE users SET email = '%s' WHERE id = %d\n", u.Email, u.ID)

	// 2. Инвалидация/перезапись в Redis
	key := fmt.Sprintf("user:%d", u.ID)
	data, _ := json.Marshal(u)
	return r.rdb.Set(ctx, key, data, 10*time.Minute).Err()
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	repo := &UserRepo{rdb: rdb}
	user := User{ID: 501, Email: "initial@mail.ru"}

	// Создание
	_ = repo.CreateUser(ctx, user)

	// Обновление
	user.Email = "updated@mail.ru"
	_ = repo.UpdateUser(ctx, user)

	// Чтение из кэша
	cached, err := rdb.Get(ctx, "user:501").Result()
	if err != nil {
		log.Fatalf("Get error: %v", err)
	}

	fmt.Printf("[Redis] Актуальное состояние в кэше: %s\n", cached)
}
```

ℹ️ Паттерн Write-Through с поддержанием строгой консистентности

**`Терминал`**

```bash
go run main.go
# Вывод:
# [PostgreSQL] INSERT INTO users VALUES (501, 'initial@mail.ru')
# [PostgreSQL] UPDATE users SET email = 'updated@mail.ru' WHERE id = 501
# [Redis] Актуальное состояние в кэше: {"id":501,"email":"updated@mail.ru"}
```

## Под капотом

Write-Through увеличивает задержку операций записи (поскольку нужно дождаться ответа и от БД, и от Redis), но гарантирует отсутствие промахов (Cache Miss) при последующих чтениях.

## Подводные камни

Конкурентные перезаписи при двух параллельных `UpdateUser`. Если запрос А и запрос Б выполняются одновременно, в Redis может записаться устаревшая версия. Для исключения гонок чаще выбирают инвалидацию (`DEL`).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Write-Through от Write-Behind (Write-Back)?»
**Ответ:** При **Write-Through** запись в БД и кэш происходит синхронно до ответа клиенту. При **Write-Behind** сервис мгновенно сохраняет данные ТОЛЬКО в Redis и сразу отвечает клиенту, а фоновый воркер асинхронно сбрасывает данные в PostgreSQL пачками (batch insert). Write-Behind дает колоссальную скорость записи, но несет риск потери данных при сбое кэша до сброса в БД.
