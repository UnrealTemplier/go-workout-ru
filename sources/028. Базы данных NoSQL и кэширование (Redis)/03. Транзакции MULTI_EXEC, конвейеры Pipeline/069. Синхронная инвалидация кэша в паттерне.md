# Синхронная инвалидация кэша в паттерне Write-Through

## Условие

**Write-Through Cache**: При обновлении данных в Postgres (`UPDATE`) синхронно обновляйте или инвалидируйте соответствующий ключ в Redis в рамках той же бизнес-логики.

## Теория

Для сохранения строгой консистентности (Consistency) между реляционной базой данных и кэшем применяется стратегия **Инвалидации при записи (Cache Invalidation)**:
1. Запускается транзакция в PostgreSQL.
2. Выполняется `UPDATE users SET name = $1 WHERE id = $2`.
3. Транзакция коммитится в PostgreSQL.
4. **Немедленно** выполняется удаление ключа из Redis: `rdb.Del(ctx, cacheKey)`.
Следующий запрос на чтение гарантированно загрузит из базы обновленную запись.

## Решение по шагам

1. Реализуйте метод `UpdateUserWithInvalidation(ctx, id, newName)`.
2. Обновите запись в БД.
3. Удалите ключ из Redis через `rdb.Del`.
4. Убедитесь, что при следующем чтении кэш пуст.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

type AccountRepository struct {
	rdb *redis.Client
}

func (r *AccountRepository) UpdateUserName(ctx context.Context, userID int64, newName string) error {
	cacheKey := fmt.Sprintf("account:%d", userID)

	// 1. Обновление в основной базе данных (Postgres UPDATE)
	fmt.Printf("[PostgreSQL] UPDATE accounts SET name = '%s' WHERE id = %d\n", newName, userID)

	// 2. Инвалидация кэша в Redis
	if err := r.rdb.Del(ctx, cacheKey).Err(); err != nil {
		// Важно: логируем с критическим приоритетом, так как возникает риск грязного чтения!
		return fmt.Errorf("ошибка инвалидации кэша: %w", err)
	}

	fmt.Printf("[Redis] Ключ '%s' успешно удален (кэш инвалидирован)\n", cacheKey)
	return nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	repo := &AccountRepository{rdb: rdb}
	key := "account:15"

	// Запишем старое значение в кэш
	_ = rdb.Set(ctx, key, "Старое имя", 0).Err()

	// Обновляем данные
	if err := repo.UpdateUserName(ctx, 15, "Новое имя"); err != nil {
		log.Fatalf("Update failed: %v", err)
	}

	// Проверяем кэш
	count, _ := rdb.Exists(ctx, key).Result()
	fmt.Printf("Наличие старого ключа в Redis после инвалидации: %d (0 = удален)\n", count)
}
```

ℹ️ Синхронная инвалидация кэша при обновлении данных

**`Терминал`**

```bash

# Вывод:

```

## Под капотом

Инвалидация через `DEL` предпочтительнее обновления через `SET`: если между коммитом в БД и записью в кэш произойдет падение, удаленный ключ просто вызовет штатный Cache Miss при чтении, тогда как неудавшийся `SET` оставил бы вечно рассинхронизированные данные.

## Подводные камни

Удалять ключ из Redis ДО коммита транзакции в PostgreSQL. Конкурентный запрос на чтение успеет промахнуться в кэше, прочитать из БД СТАРОЕ (еще не закоммиченное) значение и снова положить его в кэш! Удалять ключ нужно строго ПОСЛЕ успешного коммита транзакции БД.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если коммит в PostgreSQL прошел, а сетевой запрос на удаление ключа в Redis (`DEL`) упал по таймауту?»
**Ответ:** Применяется паттерн **Transactional Outbox / Change Data Capture (CDC)**: изменения из WAL PostgreSQL вычитываются через Debezium/Kafka и отдельный надежный воркер с ретраями удаляет ключ из Redis. Дополнительно все ключи в Redis всегда должны иметь защитный TTL, гарантирующий удаление устаревших данных со временем.
