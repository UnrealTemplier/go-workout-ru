# Очередь задач: периодический Producer и блокирующий Consumer (BRPOP)

## Условие

**Очередь задач на списках Redis (LPUSH/RPOP)**: Реализуйте простейшую очередь на структурах данных Redis. Напишите одну горутину (Producer), которая раз в секунду добавляет ID задач в конец списка Redis с помощью `LPush`. Напишите вторую горутину (Consumer), которая забирает эти задачи с помощью `RPop` или блокирующего чтения `BRPop`.

## Теория

Использование блокирующего `BRPOP` в воркере устраняет необходимость в пустых циклах `time.Sleep()`. Воркер мгновенно просыпается в момент появления задачи в очереди.

## Решение по шагам

1. Запустите Producer горутину с тикером 500 мс.
2. Запустите Consumer горутину с `BRPop`.
3. Обработайте 3 задачи и завершите работу.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	queueName := "queue:jobs:video_encoding"
	_ = rdb.Del(ctx, queueName).Err()

	var wg sync.WaitGroup
	wg.Add(2)

	// Producer
	go func() {
		defer wg.Done()
		for i := 1; i <= 3; i++ {
			time.Sleep(400 * time.Millisecond)
			jobID := fmt.Sprintf("video_job_%d", i)
			_ = rdb.LPush(ctx, queueName, jobID).Err()
			fmt.Printf("--> [Producer] Задача поставлена в очередь: %s\n", jobID)
		}
	}()

	// Consumer
	go func() {
		defer wg.Done()
		for i := 1; i <= 3; i++ {
			// Ожидаем задачу с таймаутом до 3 секунд
			res, err := rdb.BRPop(ctx, 3*time.Second, queueName).Result()
			if err != nil {
				log.Printf("Consumer error: %v", err)
				return
			}
			fmt.Printf("<-- [Consumer] Задача извлечена и взята в работу: %s\n", res[1])
		}
	}()

	wg.Wait()
	fmt.Println("Все задачи успешно поставлены и обработаны!")
}
```

ℹ️ Асинхронная очередь на LPUSH и BRPOP

## Под капотом

Когда список пуст, `BRPOP` переводит TCP-клиент в блокированное состояние на стороне ядра Redis. Сокет не потребляет процессорное время, пока `LPush` не разбудит его через `signalKeyAsReady()`.

## Подводные камни

Использование бесконечного таймаута `0` в облачных средах с таймаутами простоя TCP-сессий (idle timeout).

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если 100 воркеров одновременно ждут задачу на `BRPOP` в одной очереди?»
**Ответ:** Redis соблюдает принцип FIFO: проснется ровно один воркер — тот, который первым встал в очередь ожидания сокета. Остальные 99 воркеров продолжат спать без гонки за задачу.
