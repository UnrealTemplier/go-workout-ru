# Мгновенное извлечение профиля при Cache Hit

## Условие

Ищем юзера в Redis. Если есть — возвращаем (Cache Hit).

## Теория

Быстрый путь выполнения (Happy Path): проверка наличия ключа и возврат десериализованного объекта без каких-либо обращений к реляционной БД.

## Решение по шагам

1. Заполните профиль пользователя в Redis.
2. Проверьте наличие ключа.
3. Десериализуйте и верните данные за субмиллисекундное время.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

type UserProfile struct {
	ID       int64  `json:"id"`
	Nickname string `json:"nickname"`
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	key := "profile:user:99"
	data, _ := json.Marshal(UserProfile{ID: 99, Nickname: "GoDeveloper"})
	_ = rdb.Set(ctx, key, data, 0).Err()

	// Извлечение
	raw, err := rdb.Get(ctx, key).Bytes()
	if err != nil {
		log.Fatalf("Cache hit failure: %v", err)
	}

	var p UserProfile
	_ = json.Unmarshal(raw, &p)
	fmt.Printf("[CACHE HIT] Профиль пользователя успешно загружен: %+v\n", p)
}
```

ℹ️ Обработка Cache Hit сценария

**`Терминал`**

```bash
go run main.go
# Вывод: [CACHE HIT] Профиль пользователя успешно загружен: {ID:99 Nickname:GoDeveloper}
```

## Под капотом

При попадании в кэш ответ возвращается за 200–500 микросекунд, минуя дисковый стек и планировщик транзакций реляционной СУБД.

## Подводные камни

Аллокация новых буферов на каждый вызов JSON. В высоконагруженных шлюзах используют fastjson или sonic.

## На собеседовании

**Вопрос с собеседования:** «Какое соотношение Cache Hit Ratio считается здоровым для продакшена?»
**Ответ:** Для типичного контентного бэкенда нормальным считается Hit Ratio на уровне 85–98%. Если Hit Ratio падает ниже 70%, это свидетельствует о проблемах: короткий TTL, недостаточный размер RAM, частая инвалидация или Cache Stampede.
