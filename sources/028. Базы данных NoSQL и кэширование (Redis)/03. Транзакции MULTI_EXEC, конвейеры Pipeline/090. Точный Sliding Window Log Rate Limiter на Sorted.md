# Точный Sliding Window Log Rate Limiter на Sorted Set (ZSET)

## Условие

Реализуй **Rate Limiter (sliding window log)**: `ZADD` timestamp'ов, `ZREMRANGEBYSCORE` старых (старше window), `ZCARD` для подсчёта. Более точный, но дороже по памяти.

## Теория

Алгоритм **Sliding Window Log**:
- Элементы ZSET: уникальные метки времени входящих запросов.
- Очистка устаревших: `ZREMRANGEBYSCORE key 0 (now - window)`.
- Подсчет: `ZCARD key`.
- Добавление текущего: `ZADD key now unique_request_id`.
Этот алгоритм абсолютно исключает всплески на границах окон, обеспечивая 100% честное ограничение.

## Решение по шагам

1. Напишите пайплайн очистки и подсчета.
2. Проверьте число запросов в скользящем интервале.
3. Протестируйте поведение.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type SlidingLogLimiter struct {
	rdb    *redis.Client
	limit  int64
	window time.Duration
}

func (s *SlidingLogLimiter) Allow(ctx context.Context, key string) (bool, error) {
	now := time.Now().UnixNano()
	windowStart := now - s.window.Nanoseconds()

	pipe := s.rdb.TxPipeline()
	// 1. Удаляем все запросы, сделанные раньше текущего скользящего окна
	pipe.ZRemRangeByScore(ctx, key, "0", fmt.Sprintf("%d", windowStart))
	// 2. Считаем сколько запросов осталось в окне
	cardCmd := pipe.ZCard(ctx, key)
	// 3. Добавляем текущий запрос
	pipe.ZAdd(ctx, key, redis.Z{Score: float64(now), Member: fmt.Sprintf("%d", now)})
	pipe.Expire(ctx, key, s.window*2)
	_, err := pipe.Exec(ctx)
	if err != nil {
		return false, err
	}

	return cardCmd.Val() < s.limit, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	limiter := &SlidingLogLimiter{
		rdb:    rdb,
		limit:  2,
		window: 1 * time.Second,
	}

	key := "limiter:sliding:user_10"
	_ = rdb.Del(ctx, key).Err()

	// 1. Два запроса подряд
	a1, _ := limiter.Allow(ctx, key)
	a2, _ := limiter.Allow(ctx, key)
	fmt.Printf("Запрос 1: %v, Запрос 2: %v\n", a1, a2)

	// 2. Третий запрос в ту же секунду должен быть заблокирован
	a3, _ := limiter.Allow(ctx, key)
	fmt.Printf("Запрос 3 (в ту же секунду): %v (должен быть false)\n", a3)

	// 3. Ждем 1.1 секунды
	time.Sleep(1100 * time.Millisecond)
	a4, _ := limiter.Allow(ctx, key)
	fmt.Printf("Запрос 4 (после сдвига окна): %v (окно очистилось)\n", a4)
}
```

ℹ️ Высокоточный лимитер на базе ZSET

```bash
# Запрос 3 (в ту же секунду): false (должен быть false)

```

## Под капотом

Использование Unix наносекунд гарантирует уникальность значения `Member` в ZSET даже при конкурентных запросах, пришедших в пределах одной миллисекунды.

## Подводные камни

Расход памяти: при лимите в 10 000 запросов в минуту ZSET будет хранить 10 000 элементов на одного пользователя.

## На собеседовании

**Вопрос с собеседования:** «Как оптимизировать расход памяти Sliding Window без потери точности?»
**Ответ:** Использовать гибридный алгоритм **Sliding Window Counter** (взвешенное среднее двух счетчиков):
$$\text{Requests} = \text{Count}(\text{current\_minute}) + \text{Count}(\text{prev\_minute}) \times (1 - \text{progress})$$
Он требует всего два обычных строковых счетчика в Redis (около 100 байт памяти) и дает точность более 99%.
