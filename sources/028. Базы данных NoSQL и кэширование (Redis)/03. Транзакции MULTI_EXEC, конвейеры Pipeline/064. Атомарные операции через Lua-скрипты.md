# Атомарные операции через Lua-скрипты и метод rdb.Eval

## Условие

**Lua-скрипты**: Напишите Lua-скрипт, который атомарно проверяет наличие ключа и, если его нет, создает его с TTL (идеально для rate-limiting или идемпотентности). Выполните его через `Eval`.

## Теория

Выполнение Lua-скриптов на стороне Redis обеспечивает:
1. **Абсолютную атомарность:** пока выполняется скрипт, ни одна команда других клиентов не может вклиниться в процесс.
2. **Сокращение сетевого трафика (RTT):** вся сложная логика проверок `if ... then ... else` выполняется на сервере.
В Lua аргументы ключей передаются в массив `KEYS`, а значения — в массив `ARGV`.

## Решение по шагам

1. Напишите Lua-скрипт: проверка `EXISTS`, если 0 — вызов `SETEX`.
2. Вызовите скрипт в Go через `rdb.Eval(ctx, script, keys, args...)`.
3. Проверьте результат возврата.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

// Lua-скрипт:
// KEYS[1] - ключ
// ARGV[1] - значение
// ARGV[2] - TTL в секундах
// Возвращает 1, если ключ создан, и 0, если уже существовал
const checkAndSetLua = `
if redis.call("EXISTS", KEYS[1]) == 0 then
    redis.call("SETEX", KEYS[1], ARGV[2], ARGV[1])
    return 1
else
    return 0
end
`

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	key := "idempotency:order:7788"
	_ = rdb.Del(ctx, key).Err()

	// 1. Первый запуск: ключ создается
	res1, err := rdb.Eval(ctx, checkAndSetLua, []string{key}, "created", 60).Result()
	if err != nil {
		log.Fatalf("Eval error: %v", err)
	}
	fmt.Printf("Попытка 1: результат Lua-скрипта = %v (успешно создан)\n", res1)

	// 2. Второй запуск: ключ уже существует
	res2, err := rdb.Eval(ctx, checkAndSetLua, []string{key}, "created", 60).Result()
	if err != nil {
		log.Fatalf("Eval error: %v", err)
	}
	fmt.Printf("Попытка 2: результат Lua-скрипта = %v (дубликат заблокирован!)\n", res2)
}
```

ℹ️ Атомарный скрипт идемпотентности на Lua

**`Терминал`**

```bash
go run main.go
# Вывод:
# Попытка 1: результат Lua-скрипта = 1 (успешно создан)
# Попытка 2: результат Lua-скрипта = 0 (дубликат заблокирован!)
```

## Под капотом

Для оптимизации Redis кэширует скомпилированный байткод Lua-скрипта в SHA1-кэше. При повторных вызовах клиент `go-redis` при использовании структуры `redis.NewScript` сначала пытается выполнить быструю команду `EVALSHA <sha1>`, и только если скрипта нет в кэше сервера (`NOSCRIPT`), шлет полный текст через `EVAL`.

## Подводные камни

Писать в Lua медленные тяжелые циклы: пока выполняется Lua-скрипт, весь Redis полностью заблокирован и не отвечает на запросы других пользователей! Если скрипт выполняется дольше `lua-time-limit` (по умолчанию 5 секунд), Redis начнет отвечать ошибкой `BUSY Redis is busy running a script`.

## На собеседовании

**Вопрос с собеседования:** «Почему в Lua-скрипте Redis все имена ключей ОБЯЗАТЕЛЬНО должны передаваться через массив `KEYS`, а не хардкодиться внутри текста скрипта?»
**Ответ:** Это необходимо для работы в Redis Cluster. Кластерный прокси и клиент парсят массив `KEYS` до отправки на сервер, чтобы определить хэш-слот и направить скрипт на правильный шард. Если ключ захардкожен внутри Lua, кластер не сможет гарантировать, что данные находятся на этом узле, и вернет ошибку.
