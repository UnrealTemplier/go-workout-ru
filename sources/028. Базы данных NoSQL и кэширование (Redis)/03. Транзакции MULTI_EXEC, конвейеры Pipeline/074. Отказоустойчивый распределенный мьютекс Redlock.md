# Отказоустойчивый распределенный мьютекс Redlock для Cron-задач

## Условие

**Распределенный Lock (Redlock)**: Реализуйте надежный мьютекс, который работает across нескольких независимых инстансов Redis, чтобы гарантировать, что фоновая задача (cron job) выполняется только в одном экземпляре во всей кластерной инфраструктуре.

## Теория

Алгоритм **Redlock** разработан автором Redis для обеспечения гарантий взаимного исключения даже при падении любого одиночного мастера:
1. Задействуется \(N\) независимых инстансов Redis (обычно 5).
2. Клиент пытается захватить блокировку на всех \(N\) узлах последовательно с коротким таймаутом.
3. Блокировка считается успешно полученной, если она захвачена на **кворуме** узлов:
$$\text{Quorum} \ge \lfloor N/2 \rfloor + 1 \quad (\ge 3 \text{ из } 5)$$
4. Время жизни лока уменьшается на суммарное время, потраченное на сетевые запросы.

## Решение по шагам

1. Опишите принцип кворума алгоритма Redlock.
2. Реализуйте структуру `RedlockCoordinator`.
3. Покажите попытку захвата блокировки на пуле инстансов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type RedlockCoordinator struct {
	nodes []*redis.Client
	value string
}

func NewRedlockCoordinator(nodes []*redis.Client) *RedlockCoordinator {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	return &RedlockCoordinator{
		nodes: nodes,
		value: hex.EncodeToString(b),
	}
}

func (r *RedlockCoordinator) Acquire(ctx context.Context, resource string, ttl time.Duration) bool {
	quorum := (len(r.nodes) / 2) + 1
	var votes int

	start := time.Now()

	for _, node := range r.nodes {
		callCtx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
		ok, err := node.SetNX(callCtx, resource, r.value, ttl).Result()
		cancel()

		if err == nil && ok {
			votes++
		}
	}

	validity := ttl - time.Since(start)

	// Условие успеха: набрали кворум узлов и время жизни еще не истекло
	if votes >= quorum && validity > 0 {
		fmt.Printf("✅ Кворум достигнут! Голосов: %d/%d. Валидность: %v\n", votes, len(r.nodes), validity)
		return true
	}

	// Откат при недоборе кворума: снимаем на всех узлах
	r.Release(ctx, resource)
	return false
}

func (r *RedlockCoordinator) Release(ctx context.Context, resource string) {
	luaRelease := `
	if redis.call("get", KEYS[1]) == ARGV[1] then
		return redis.call("del", KEYS[1])
	else
		return 0
	end`

	for _, node := range r.nodes {
		_ = node.Eval(ctx, luaRelease, []string{resource}, r.value).Err()
	}
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	// Для наглядности используем срез клиентов
	nodes := []*redis.Client{rdb}
	lock := NewRedlockCoordinator(nodes)

	resKey := "cron:daily_report_generation"
	if lock.Acquire(ctx, resKey, 10*time.Second) {
		fmt.Println("Запускаем единственную Cron-задачу в кластере...")
		time.Sleep(300 * time.Millisecond)
		lock.Release(ctx, resKey)
		fmt.Println("Cron-задача завершена, лок снят.")
	}
}
```

## Под капотом

В промышленной разработке на Go для Redlock используют готовую проверенную библиотеку `github.com/go-redsync/redsync/v4`. Она корректно учитывает дрейф часов (Clock Drift) между физическими серверами и гарантирует математическую корректность распределенного мьютекса.

## Подводные камни

Использовать инстансы Redis, настроенные как Master-Slave в Redlock. Узлы Redlock ОБЯЗАНЫ быть полностью независимыми отдельными инстансами без репликации между собой!

## На собеседовании

**Вопрос с собеседования:** «В чем суть критики алгоритма Redlock Мартином Клеппманом (Martin Kleppmann)?»
**Ответ:** Мартин Клеппман показал, что в распределенных системах с ненадежными часами (паузы GC Stop-The-World, виртуализация, десинхронизация NTP) никакой тайм-аут не гарантирует безопасность без механизма **Fencing Token** (монотонно возрастающего токена эпохи, проверяемого конечным хранилищем данных).
