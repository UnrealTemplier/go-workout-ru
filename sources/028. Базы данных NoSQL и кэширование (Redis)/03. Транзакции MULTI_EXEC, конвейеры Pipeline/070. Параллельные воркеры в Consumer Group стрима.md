# Параллельные воркеры в Consumer Group стрима: StreamReadGroup

## Условие

Напиши функцию `StreamReadGroup(group, consumer, stream string) ([]redis.XMessage, error)` через `rdb.XReadGroup`. Реализуй **consumer group**: несколько воркеров читают из одного stream, каждое сообщение обрабатывается одним воркером.

## Теория

Consumer Group в Redis Streams позволяет масштабировать обработку потока на \(N\) параллельных воркеров (горутин):
- Сообщения распределяются между воркерами без дублирования.
- Каждое сообщение поступает строго одному консьюмеру группы.
- Для чтения новых сообщений используется специальный ID `">"`.

## Решение по шагам

1. Создайте Stream и Consumer Group.
2. Реализуйте метод `StreamReadGroup(ctx, group, consumer, stream, count)`.
3. Запустите двух воркеров и покажите, что они получают разные сообщения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type StreamWorker struct {
	rdb *redis.Client
}

func (w *StreamWorker) StreamReadGroup(ctx context.Context, group, consumer, stream string, count int64) ([]redis.XMessage, error) {
	res, err := w.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
		Group:    group,
		Consumer: consumer,
		Streams:  []string{stream, ">"},
		Count:    count,
		Block:    1 * time.Second,
	}).Result()
	if err != nil {
		return nil, err
	}
	if len(res) > 0 {
		return res[0].Messages, nil
	}
	return nil, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	stream := "stream:payments"
	group := "billing_workers"
	_ = rdb.Del(ctx, stream).Err()

	// Создаем группу
	_ = rdb.XGroupCreateMkStream(ctx, stream, group, "$").Err()

	// Публикуем 2 платежа
	_ = rdb.XAdd(ctx, &redis.XAddArgs{Stream: stream, Values: map[string]interface{}{"payment_id": "P_001"}}).Err()
	_ = rdb.XAdd(ctx, &redis.XAddArgs{Stream: stream, Values: map[string]interface{}{"payment_id": "P_002"}}).Err()

	worker := &StreamWorker{rdb: rdb}

	// Воркер 1 читает 1 сообщение
	msgs1, _ := worker.StreamReadGroup(ctx, group, "worker_alpha", stream, 1)
	if len(msgs1) > 0 {
		fmt.Printf("Воркер Alpha получил: %v\n", msgs1[0].Values)
		_ = rdb.XAck(ctx, stream, group, msgs1[0].ID).Err()
	}

	// Воркер 2 читает следующее сообщение
	msgs2, _ := worker.StreamReadGroup(ctx, group, "worker_beta", stream, 1)
	if len(msgs2) > 0 {
		fmt.Printf("Воркер Beta получил:  %v\n", msgs2[0].Values)
		_ = rdb.XAck(ctx, stream, group, msgs2[0].ID).Err()
	}
}
```

ℹ️ Распределение нагрузки между воркерами в Consumer Group

**`Терминал`**

```bash
go run main.go
# Вывод:
# Воркер Alpha получил: map[payment_id:P_001]
# Воркер Beta получил:  map[payment_id:P_002]
```

## Под капотом

Сервер Redis отслеживает курсор чтения для всей группы. Аргумент `">"` инструктирует Redis отдать сообщения с ID, превышающим максимальный ранее распределенный ID в группе, обеспечивая строгий шардинг нагрузки.

## Подводные камни

Использовать одинаковый `Consumer` name для всех инстансов: в этом случае Redis посчитает их одним консьюмером, и механизм распределения нагрузки сломается. Имя консьюмера должно включать имя пода/хоста (например `hostname + pid`).

## На собеседовании

**Вопрос с собеседования:** «Что вернет `XREADGROUP`, если вместо `">"` передать `"0"`?»
**Ответ:** Redis вернет сообщения из списка PEL (Pending Entries List), которые уже были доставлены этому консьюмеру, но еще НЕ были им подтверждены командой `XACK`. Это механизм восстановления при рестарте упавшего воркера.
