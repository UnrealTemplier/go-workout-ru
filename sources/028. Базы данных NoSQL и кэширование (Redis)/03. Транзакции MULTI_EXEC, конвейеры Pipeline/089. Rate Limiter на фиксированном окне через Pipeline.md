# Rate Limiter на фиксированном окне через Pipeline: атомарный INCR и EXPIRE

## Условие

Реализуй **Rate Limiter** через Redis: `SLIDE_WINDOW`. Ключ = `rate_limit:ip:minute:YYYY-MM-DD-HH-MM`. `INCR` + `EXPIRE 60`. Если счётчик > limit — `429 Too Many Requests`. Используй pipeline для атомарности `INCR` + `EXPIRE`.

## Теория

Паттерн **Fixed Window Rate Limiter** с поминутным ключом:
- Ключ формируется с текущей минутой: `rate:ip:2026-09-03-14-50`.
- В одном пайплайне вызывается `INCR key` и `EXPIRE key 60`.
- Если возвращенный счетчик превышает порог, запрос отклоняется (429).
Благодаря суффиксу минуты старые ключи автоматически отмирают без накопления памяти.

## Решение по шагам

1. Сформируйте ключ с временной меткой текущей минуты.
2. Отправьте `Incr` и `Expire` в пайплайне.
3. Проверьте значение счетчика.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type MinuteRateLimiter struct {
	rdb   *redis.Client
	limit int64
}

func (rl *MinuteRateLimiter) Allow(ctx context.Context, ip string) (bool, int64, error) {
	currentMinute := time.Now().UTC().Format("2006-01-02-15-04")
	key := fmt.Sprintf("rate_limit:%s:%s", ip, currentMinute)

	pipe := rl.rdb.Pipeline()
	incrCmd := pipe.Incr(ctx, key)
	pipe.Expire(ctx, key, 70*time.Second) // 70 сек с запасом на дрейф времени
	_, err := pipe.Exec(ctx)
	if err != nil {
		return false, 0, err
	}

	count := incrCmd.Val()
	return count <= rl.limit, count, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	limiter := &MinuteRateLimiter{rdb: rdb, limit: 3}
	ip := "192.168.1.55"

	for i := 1; i <= 5; i++ {
		allowed, count, err := limiter.Allow(ctx, ip)
		if err != nil {
			log.Fatalf("Error: %v", err)
		}

		if allowed {
			fmt.Printf("Запрос %d (счетчик=%d): 200 OK\n", i, count)
		} else {
			fmt.Printf("Запрос %d (счетчик=%d): 429 Too Many Requests\n", i, count)
		}
	}
}
```

## Под капотом

Использование Pipeline здесь критично: отправка `INCR` и `EXPIRE` двумя независимыми сетевыми запросами создавала бы риск: если после `INCR` сервис упадет, ключ останется без TTL и зависнет в памяти навсегда.

## Подводные камни

Краевой эффект: клиент может отправить 100 запросов в 14:50:59 и еще 100 запросов в 14:51:01, сделав 200 запросов за 2 секунды. Для строгого контроля используйте скользящее окно (Sliding Window Log).

## На собеседовании

**Вопрос с собеседования:** «Почему в `EXPIRE` указано 70 секунд, а не ровно 60?»
**Ответ:** Небольшой запас (buffer time) в 10 секунд гарантирует, что ключ не исчезнет до окончания текущей минуты из-за возможной легкой рассинхронизации системных часов серверов (NTP skew).
