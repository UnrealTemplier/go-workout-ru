# Транзакции MULTI/EXEC через TxPipelined для атомарного перевода

## Условие

Транзакции Redis: атомарно обновите два ключа с помощью `MULTI/EXEC` (или `TxPipelined`).

## Теория

Команды `MULTI` и `EXEC` обрамляют блок команд, гарантируя атомарность исполнения:
- Никакие команды других клиентов не могут вклиниться между командами внутри блока `MULTI/EXEC`.
- В `go-redis` идиоматичный способ работы с транзакцией — метод `rdb.TxPipelined(ctx, fn)`.
Клиент отправляет команду `MULTI`, затем пачку команд и команду `EXEC` за один сетевой round-trip.

## Решение по шагам

1. Подготовьте счета пользователя А (1000) и пользователя Б (500).
2. Вызовите `rdb.TxPipelined` для списания 200 у А и начисления 200 Б.
3. Проверьте новые балансы.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

func transferMoney(ctx context.Context, rdb *redis.Client, from, to string, amount int64) error {
	// TxPipelined оборачивает команды в MULTI / EXEC
	_, err := rdb.TxPipelined(ctx, func(pipe redis.Pipeliner) error {
		pipe.DecrBy(ctx, from, amount)
		pipe.IncrBy(ctx, to, amount)
		return nil
	})
	return err
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	accA := "wallet:user_a:balance"
	accB := "wallet:user_b:balance"

	_ = rdb.Set(ctx, accA, 1000, 0).Err()
	_ = rdb.Set(ctx, accB, 500, 0).Err()

	// Выполняем атомарный перевод 200 единиц
	if err := transferMoney(ctx, rdb, accA, accB, 200); err != nil {
		log.Fatalf("Ошибка транзакции: %v", err)
	}

	balA, _ := rdb.Get(ctx, accA).Int64()
	balB, _ := rdb.Get(ctx, accB).Int64()

	fmt.Println("Транзакция MULTI/EXEC успешно зафиксирована:")
	fmt.Printf("  Баланс А: %d (было 1000)\n", balA)
	fmt.Printf("  Баланс Б: %d (было 500)\n", balB)
}
```

ℹ️ Атомарный перевод средств через TxPipelined

**`Терминал`**

```bash
go run main.go
# Вывод:
# Транзакция MULTI/EXEC успешно зафиксирована:
#   Баланс А: 800 (было 1000)
#   Баланс Б: 700 (было 500)
```

## Под капотом

Сервер Redis при получении `MULTI` переводит клиентское соединение в состояние `CLIENT_MULTI`. Все последующие команды не выполняются немедленно, а складываются в массив команд транзакции `c->mstate.commands`. При получении `EXEC` сервер исполняет весь массив подряд в цикле событий, гарантируя строгую изоляцию (Serializability).

## Подводные камни

Заблуждение о наличии Rollback: в Redis НЕТ отката назад при ошибках исполнения (например, если одна из команд упала из-за неверного типа данных). Все остальные команды всё равно выполнятся! Единственная защита от частичного исполнения — синтаксические ошибки на этапе постановки в очередь.

## На собеседовании

**Вопрос с собеседования:** «Почему создатели Redis не реализовали полноценный откат транзакций (Rollback), как в PostgreSQL?»
**Ответ:** Сальваторе Санфилиппо (antirez) объяснял это философией Redis: ошибки рантайма (вроде попытки вызвать `INCR` на строке текста) возникают только из-за багов в коде разработчика и должны отлавливаться на этапе тестирования. Отсутствие механизма отката позволило сохранить ядро Redis экстремально простым, надежным и быстрым.
