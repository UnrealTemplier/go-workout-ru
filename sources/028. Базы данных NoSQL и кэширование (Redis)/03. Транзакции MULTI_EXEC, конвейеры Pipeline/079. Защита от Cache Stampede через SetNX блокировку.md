# Защита от Cache Stampede через SetNX блокировку загрузки

## Условие

Реализуй **cache stampede protection** через `SetNX`: при cache miss — один запрос ставит lock `"lock:user:123"`, грузит из БД, кладёт в кеш, удаляет lock. Остальные ждут lock'а или берут stale-данные.

## Теория

Распределенный мьютекс на базе `SetNX` — альтернатива Singleflight при масштабировании на десятки независимых подов в Kubernetes:
- При Cache Miss первый под успешно выполняет `SetNX lock:item 1 EX 5`.
- Этот под отправляет SQL-запрос в БД и обновляет кэш.
- Остальные 99 подов получают от `SetNX` значение `false`, засыпают на 50 мс (`time.Sleep`) и затем читают уже готовое значение из кэша, не трогая БД.

## Решение по шагам

1. Реализуйте `GetWithDistributedLock(ctx, id)`.
2. При промахе кэша пробуйте захватить `SetNX`.
3. При неудаче — подождите и повторите чтение из кэша.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"

	"github.com/redis/go-redis/v9"
)

type ProtectedCache struct {
	rdb     *redis.Client
	dbCalls int64
}

func (c *ProtectedCache) fetchFromDB(id int) string {
	atomic.AddInt64(&c.dbCalls, 1)
	time.Sleep(100 * time.Millisecond) // эмуляция долгой генерации отчета
	return fmt.Sprintf("Report_Payload_Data_For_%d", id)
}

func (c *ProtectedCache) GetReport(ctx context.Context, id int) (string, error) {
	cacheKey := fmt.Sprintf("report:%d", id)
	lockKey := fmt.Sprintf("lock:report:%d", id)

	for attempt := 0; attempt < 5; attempt++ {
		// 1. Проверяем кэш
		val, err := c.rdb.Get(ctx, cacheKey).Result()
		if err == nil {
			return val, nil
		}

		if !errors.Is(err, redis.Nil) {
			return "", err
		}

		// 2. Пытаемся взять блокировку на прогрев кэша
		locked, _ := c.rdb.SetNX(ctx, lockKey, "1", 5*time.Second).Result()
		if locked {
			// Только один воркер попадет сюда
			fmt.Printf("[LOCK ACQUIRED] Воркер загружает данные из БД для ID %d\n", id)
			data := c.fetchFromDB(id)

			// Записываем в кэш и снимаем замок
			_ = c.rdb.Set(ctx, cacheKey, data, 1*time.Minute).Err()
			_ = c.rdb.Del(ctx, lockKey).Err()
			return data, nil
		}

		// 3. Другой воркер уже греет кэш: ждем 40 мс и повторяем попытку
		time.Sleep(40 * time.Millisecond)
	}

	return "", fmt.Errorf("timeout waiting for cache warm-up")
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	cache := &ProtectedCache{rdb: rdb}
	_ = rdb.Del(ctx, "report:55", "lock:report:55").Err()

	// Запускаем 20 параллельных горутин
	const routines = 20
	var wg sync.WaitGroup
	wg.Add(routines)

	for i := 0; i < routines; i++ {
		go func() {
			defer wg.Done()
			_, _ = cache.GetReport(ctx, 55)
		}()
	}

	wg.Wait()

	fmt.Printf("Успешно завершено! Обращений к БД: %d (вместо %d)\n",
		atomic.LoadInt64(&cache.dbCalls), routines)
}
```

## Под капотом

TTL на ключ блокировки (`5*time.Second`) критически важен: если воркер, взявший блокировку, упадет по панике в процессе `fetchFromDB`, лок автоматически сбросится, и следующий воркер сможет продолжить работу без постоянного дедлока.

## Подводные камни

Слишком короткая пауза в цикле ожидания (spin wait). Пауза должна составлять от 30 до 100 мс, чтобы не создавать паразитный сетевой трафик к Redis.

## На собеседовании

**Вопрос с собеседования:** «Что такое probabilistic early expiration (алгоритм XFetch)?»
**Ответ:** Это вероятностный алгоритм упреждающего прогрева кэша. Чем ближе время жизни ключа к истечению, тем выше вероятность, что случайный фоновый запрос пересчитает значение и обновит кэш ДО того, как ключ реально протухнет. Формула: \(-\beta \times \delta \times \ln(\text{rand}()) > \text{TTL}\), где \(\delta\) — время вычисления значения. Это полностью исключает Cache Miss для горячих ключей.
