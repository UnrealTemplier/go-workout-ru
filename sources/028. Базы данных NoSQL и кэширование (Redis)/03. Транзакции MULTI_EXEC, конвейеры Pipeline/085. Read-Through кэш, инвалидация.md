# Read-Through кэш, инвалидация и эффект Eventual Consistency

## Условие

Реализуй **Read-Through cache** с TTL: данные в кеше живут 5 минут. При обновлении в БД — `CacheDelete` (invalidate). Покажи **eventual consistency**: между `UPDATE` и `CacheDelete` читатели видят stale-данные.

## Теория

В распределенных системах между моментом коммита `UPDATE` в базе данных и моментом физического удаления ключа в Redis (`DEL`) существует временное окно (race window) длительностью от нескольких микросекунд до десятков миллисекунд.
В этот интервал параллельные читатели видят старое значение (**Stale Read**). Это фундаментальное свойство моделей согласованности в конечном счете (**Eventual Consistency**).

## Решение по шагам

1. Создайте модель данных с кэшем.
2. Продемонстрируйте окно рассинхронизации между UPDATE и инвалидацией.
3. Покажите восстановление консистентности после вызова `CacheDelete`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type CustomerStore struct {
	rdb        *redis.Client
	currentDB  string // эмуляция базы данных
}

func (s *CustomerStore) UpdateDBWithSimulatedLag(ctx context.Context, id int, newValue string) {
	key := fmt.Sprintf("customer:%d", id)

	// 1. Обновляем БД
	s.currentDB = newValue
	fmt.Printf("[DB COMMIT] База данных обновлена: '%s'\n", newValue)

	// Имитация сетевой задержки до инвалидации кэша
	time.Sleep(50 * time.Millisecond)

	// 2. Инвалидируем кэш
	_ = s.rdb.Del(ctx, key).Err()
	fmt.Println("[CACHE INVALIDATE] Ключ удален из Redis")
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	store := &CustomerStore{rdb: rdb, currentDB: "Премиум клиент"}
	key := "customer:10"

	// Заполним кэш старым значением
	_ = rdb.Set(ctx, key, "Базовый клиент", 5*time.Minute).Err()

	// Запускаем обновление в фоне
	go store.UpdateDBWithSimulatedLag(ctx, 10, "VIP клиент")

	// Читатель 1 читает сразу во время лага инвалидации
	time.Sleep(10 * time.Millisecond)
	staleVal, _ := rdb.Get(ctx, key).Result()
	fmt.Printf("⚠️  [Eventual Consistency] Читатель видит stale-данные: '%s'\n", staleVal)

	// Читатель 2 читает после завершения инвалидации
	time.Sleep(80 * time.Millisecond)
	_, err := rdb.Get(ctx, key).Result()
	fmt.Printf("✅  [Consistent Read] Кэш пуст (err=%v), читатель идет в БД за '%s'\n", err, store.currentDB)
}
```

ℹ️ Демонстрация окна Eventual Consistency и stale-чтения

**`Терминал`**

```bash
go run main.go
# Вывод:
# [DB COMMIT] База данных обновлена: 'VIP клиент'
# ⚠️  [Eventual Consistency] Читатель видит stale-данные: 'Базовый клиент'
# [CACHE INVALIDATE] Ключ удален из Redis
# ✅  [Consistent Read] Кэш пуст (err=redis: nil), читатель идет в БД за 'VIP клиент'
```

## Под капотом

Теорема CAP и компромиссы PACELC: использование кэша выбирает Высокую Доступность (Availability) и Низкую Задержку (Latency) ценой слабой согласованности (Eventual Consistency). Для подавляющего большинства бизнес-сценариев (лента новостей, профили, каталог товаров) это абсолютно допустимо.

## Подводные камни

Использовать кэш-слой для балансов счетов или критических финансовых блокировок без строгой транзакционной изоляции.

## На собеседовании

**Вопрос с собеседования:** «Как свести к минимуму окно Stale Read при обновлении данных?»
**Ответ:** 1. Использовать паттерн Double Delete (удалить ключ из кэша до коммита и еще раз асинхронно через 500 мс после коммита). 2. Применять репликацию CDC (Change Data Capture) из бинарных логов СУБД для мгновенного удаления ключей.
