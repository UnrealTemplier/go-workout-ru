# Подтверждение обработки сообщений через XAck и очистка PEL

## Условие

Напиши функцию `StreamAcknowledge(stream, group string, ids ...string) error` через `rdb.XAck`. Покажи, что сообщение удаляется из pending list только после acknowledge.

### Исходная формулировка

Напиши функцию `StreamAcknowledge(stream, group string, ids ...string) error` через `rdb.XAck`. Покажи, что сообщение удаляется из pending list только после acknowledge.

---

## Теория

В Redis Streams каждое вычитанное через `XReadGroup` сообщение попадает в список ожидания подтверждения — **PEL (Pending Entries List)**.
Команда `XACK stream group id [id ...]` подтверждает успешное завершение обработки и удаляет запись из PEL.
До вызова `XACK` сообщение считается находящимся в обработке (In-Flight) и отображается в статистике `XPENDING`.

## Решение по шагам

1. Опубликуйте сообщение и вычитайте через `XReadGroup`.
2. Проверьте `rdb.XPending` — счетчик равен 1.
3. Вызовите `rdb.XAck`.
4. Проверьте `rdb.XPending` снова — счетчик стал 0.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	stream := "stream:emails"
	group := "email_senders"
	_ = rdb.Del(ctx, stream).Err()

	_ = rdb.XGroupCreateMkStream(ctx, stream, group, "$").Err()

	// Публикуем задачу
	msgID, _ := rdb.XAdd(ctx, &redis.XAddArgs{
		Stream: stream,
		Values: map[string]interface{}{"to": "dev@ozon.ru"},
	}).Result()

	// Вычитываем задачу
	_, _ = rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
		Group:    group,
		Consumer: "worker_mail_1",
		Streams:  []string{stream, ">"},
		Count:    1,
	}).Result()

	// 1. Проверяем PEL до ACK
	pendingBefore, err := rdb.XPending(ctx, stream, group).Result()
	if err != nil {
		log.Fatalf("XPending error: %v", err)
	}
	fmt.Printf("1. Задач в PEL (Pending) до вызова XAck: %d\n", pendingBefore.Count)

	// 2. Отправляем XAck
	acked, err := rdb.XAck(ctx, stream, group, msgID).Result()
	if err != nil {
		log.Fatalf("XAck error: %v", err)
	}
	fmt.Printf("2. XAck подтвердил %d сообщений\n", acked)

	// 3. Проверяем PEL после ACK
	pendingAfter, _ := rdb.XPending(ctx, stream, group).Result()
	fmt.Printf("3. Задач в PEL (Pending) после вызова XAck: %d (очищено!)\n", pendingAfter.Count)
}
```

ℹ️ Жизненный цикл подтверждения сообщений через XAck

**`Терминал`**

```bash
go run main.go
# Вывод:
# 1. Задач в PEL (Pending) до вызова XAck: 1
# 2. XAck подтвердил 1 сообщений
# 3. Задач в PEL (Pending) после вызова XAck: 0 (очищено!)
```

## Под капотом

PEL хранится внутри структуры группы потребителей как префиксное дерево `rax`. Запись содержит ID сообщения, имя консьюмера, время последней доставки и счетчик попыток доставки (`delivery count`). При вызове `XACK` узел удаляется из Radix Tree.

## Подводные камни

Забывать вызывать `XACK` после успешной обработки: память PEL будет расти неограниченно, приводя к постепенной утечке RAM инстанса Redis.

## На собеседовании

**Вопрос с собеседования:** «Удаляет ли `XACK` само сообщение из тела стрима?»
**Ответ:** Нет! `XACK` удаляет запись только из списка неподтвержденных задач конкретной Consumer Group. Само сообщение остается в стриме и доступно для других групп потребителей или для повторного чтения через `XRANGE`. Для физического удаления сообщения из стрима используется команда `XDEL stream id`.
