# Ликвидация Cache Stampede (Thundering Herd) через singleflight

## Условие

**Cache Stampede (Thundering Herd)**: Воспроизведите ситуацию, когда TTL популярного ключа истекает, и 1000 горутин одновременно бьют в БД. Решите проблему с помощью пакета `golang.org/x/sync/singleflight`, чтобы в БД пошел только один запрос, а остальные ждали его результата.

## Теория

Проблема **Cache Stampede (Thundering Herd / Dogpiling)**:
Когда протухает TTL ключа с высоким трафиком (например, главная страница или горячая скидка со 100k RPS), в момент истечения сотни параллельных запросов одновременно фиксируют `redis.Nil`. Все они одновременно отправляют тяжелый SQL-запрос в PostgreSQL, что приводит к мгновенной перегрузке CPU базы и падению сервиса.

**Решение на Go:** библиотека `golang.org/x/sync/singleflight`.
Группа `singleflight.Group` гарантирует: сколько бы горутин одновременно ни вызвали `g.Do(key, fn)`, функция `fn` выполнится ровно **ОДИН** раз, а ее результат будет продублирован всем ожидающим горутинам!

## Решение по шагам

1. Подключите `golang.org/x/sync/singleflight`.
2. Создайте группу `sf singleflight.Group`.
3. Запустите 100 конкурентных горутин, запрашивающих протухший ключ.
4. Убедитесь, что в базу данных ушел ровно 1 запрос.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"

	"github.com/redis/go-redis/v9"
	"golang.org/x/sync/singleflight"
)

type WeatherService struct {
	rdb      *redis.Client
	sf       singleflight.Group
	dbCalls  int64 // счетчик реальных обращений в БД
}

func (s *WeatherService) fetchFromSlowDB(city string) (string, error) {
	atomic.AddInt64(&s.dbCalls, 1)
	time.Sleep(100 * time.Millisecond) // имитация тяжелого SQL
	return fmt.Sprintf("Погода в %s: +22°C, Ясно", city), nil
}

func (s *WeatherService) GetWeather(ctx context.Context, city string) (string, error) {
	cacheKey := fmt.Sprintf("weather:%s", city)

	// 1. Пробуем кэш
	val, err := s.rdb.Get(ctx, cacheKey).Result()
	if err == nil {
		return val, nil
	}

	if !errors.Is(err, redis.Nil) {
		return "", err
	}

	// 2. Cache Miss: защищаемся от Thundering Herd через singleflight
	res, err, _ := s.sf.Do(cacheKey, func() (interface{}, error) {
		// Этот блок выполнится РОВНО ОДИН РАЗ даже при 1000 конкурентных вызовах!
		fmt.Printf("--> [ЕДИНСТВЕННЫЙ ЗАПРОС В БД] Загружаем погоду для города: %s\n", city)
		data, err := s.fetchFromSlowDB(city)
		if err != nil {
			return nil, err
		}

		// Сохраняем в кэш с TTL 10 секунд
		_ = s.rdb.Set(ctx, cacheKey, data, 10*time.Second).Err()
		return data, nil
	})

	if err != nil {
		return "", err
	}

	return res.(string), nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	svc := &WeatherService{rdb: rdb}
	_ = rdb.Del(ctx, "weather:Moscow").Err()

	// Имитируем наплыв 50 одновременных запросов в момент протухания кэша
	const concurrentRequests = 50
	var wg sync.WaitGroup
	wg.Add(concurrentRequests)

	for i := 0; i < concurrentRequests; i++ {
		go func() {
			defer wg.Done()
			_, _ = svc.GetWeather(ctx, "Moscow")
		}()
	}

	wg.Wait()

	fmt.Printf("\nПараллельных запросов: %d\n", concurrentRequests)
	fmt.Printf("Реальных обращений в БД: %d (Thundering Herd предотвращен!)\n", atomic.LoadInt64(&svc.dbCalls))
}
```

## Под капотом

Внутри `singleflight.Group` мьютексом защищена мапа `map[string]*call`. Первая пришедшая горутина создает структуру `call`, захватывает исполнение и делает реальный сетевой запрос. Все остальные горутины, пришедшие с тем же ключом, видят существующий `call` и просто встают на чтение из внутреннего канала `c.done`. Когда первый запрос завершается, канал закрывается, и результат возвращается всем 50 горутинам.

## Подводные камни

Зависание функции внутри `singleflight.Do`: если вызов к базе повиснет без таймаута контекста, все конкурентные горутины тоже повиснут на ожидании. Всегда используйте контексты с таймаутом внутри `Do`.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Singleflight от распределенной блокировки Redis Mutex при защите от Thundering Herd?»
**Ответ:** Singleflight работает локально в памяти ОДНОГО экземпляра Go-приложения (защищает инстанс от своих собственных горутин с нулевыми сетевыми накладными расходами). Если у вас 50 реплик сервиса в Kubernetes, Singleflight пропустит в базу 50 запросов (по одному с каждого инстанса), что безопасно для PostgreSQL. Распределенный замок в Redis сложнее и требует дополнительных сетевых RTT.
