# Паттерн Cache-Aside: реализация функции GetProduct с TTL

## Условие

**Cache-Aside (Lazy Loading)**: Напишите функцию `GetProduct(id)`. Сначала ищите в Redis. Если нет (`redis.Nil`) — делайте запрос в Postgres, сохраняйте в Redis с TTL и возвращайте.

## Теория

Cache-Aside позволяет системе работать даже при недоступности кэша. Если Redis вышел из строя, код логирует ошибку и прозрачно идет в базу данных, сохраняя непрерывность бизнес-процессов.

## Решение по шагам

1. Создайте структуру `ProductCatalog`.
2. Реализуйте метод `GetProduct(ctx, id)`.
3. Задайте TTL кэширования 120 секунд.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type ProductCatalog struct {
	rdb *redis.Client
}

func (c *ProductCatalog) queryDB(id int64) (string, error) {
	time.Sleep(80 * time.Millisecond) // эмуляция дискового поиска
	return fmt.Sprintf("Смартфон Флагман Pro (ID: %d)", id), nil
}

func (c *ProductCatalog) GetProduct(ctx context.Context, id int64) (string, error) {
	key := fmt.Sprintf("cache:product:%d", id)

	// 1. Поиск в кэше
	cached, err := c.rdb.Get(ctx, key).Result()
	if err == nil {
		fmt.Printf("[CACHE HIT] Товар %d извлечен из кэша Redis\n", id)
		return cached, nil
	}

	if !errors.Is(err, redis.Nil) {
		log.Printf("Внимание: сетевой сбой Redis: %v", err)
	}

	// 2. Запрос в Postgres
	fmt.Printf("[CACHE MISS] Запрос к базе данных для товара %d...\n", id)
	dbValue, err := c.queryDB(id)
	if err != nil {
		return "", err
	}

	// 3. Сохранение в кэш с TTL 2 минуты
	_ = c.rdb.Set(ctx, key, dbValue, 2*time.Minute).Err()

	return dbValue, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	catalog := &ProductCatalog{rdb: rdb}
	_ = rdb.Del(ctx, "cache:product:42").Err()

	// Первый вызов
	val1, _ := catalog.GetProduct(ctx, 42)
	fmt.Printf("Результат: %s\n\n", val1)

	// Второй вызов
	val2, _ := catalog.GetProduct(ctx, 42)
	fmt.Printf("Результат: %s\n", val2)
}
```

ℹ️ Устойчивый Cache-Aside с обработкой ошибок

**`Терминал`**

```bash
go run main.go
# Вывод:
# [CACHE MISS] Запрос к базе данных для товара 42...
# Результат: Смартфон Флагман Pro (ID: 42)
# 
# [CACHE HIT] Товар 42 извлечен из кэша Redis
# Результат: Смартфон Флагман Pro (ID: 42)
```

## Под капотом

При высокой нагрузке Cache-Aside разгружает реляционную БД на 90–99%, беря чтение на себя. Команда `SET` с TTL использует `PX`, защищая сервер от переполнения памяти устаревшими товарами.

## Подводные камни

Забывать обрабатывать сетевые ошибки Redis. Если при сбое Redis сервис падает, кэш превращается в единую точку отказа (Single Point of Failure).

## На собеседовании

**Вопрос с собеседования:** «Что такое Cache Penetration и как от него защититься в Cache-Aside?»
**Ответ:** Cache Penetration — это атака или ситуация, когда клиенты запрашивают несуществующие ключи (например, ID = -9999). Запрос промахивается мимо кэша, идет в БД, там строки тоже нет, поэтому в кэш ничего не сохраняется. Следующий запрос снова бьет в БД. Защита: кэшировать `nil`-значения (пустую строку) с коротким TTL (30–60 секунд) либо проверять входящие ID через фильтр Блума (Bloom Filter).
