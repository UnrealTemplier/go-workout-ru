# Полный интеграционный алгоритм GetUser с проверкой доступности кэша

## Условие

**Паттерн Cache-Aside (Интеграция)**: Напиши функцию `GetUser(id)`. Алгоритм:
1. Проверяем Redis. Если найден — отдаем.
2. Если Redis недоступен — логируем предупреждение, идем в PostgreSQL.
3. Если ключ отсутствует (redis.Nil) — идем в PostgreSQL, кэшируем в Redis с TTL, возвращаем результат.

## Теория

Промышленный алгоритм кэширования обязан быть отказоустойчивым к сбоям инфраструктуры (Fault-Tolerant). Сервис не должен падать или возвращать 500 ошибку при сетевом разрыве с Redis.

## Решение по шагам

1. Создайте `GetUserRobust(ctx, id)`.
2. Обработайте три ветви: Hit, Miss, Network Error.
3. Продемонстрируйте корректную работу.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type RobustUserStore struct {
	rdb *redis.Client
}

func (s *RobustUserStore) queryPostgreSQL(id int64) (string, error) {
	return fmt.Sprintf("UserRecord{ID: %d, Name: 'Sergey'}", id), nil
}

func (s *RobustUserStore) GetUser(ctx context.Context, id int64) (string, error) {
	key := fmt.Sprintf("user:cache:%d", id)

	// Ветка 1: Проверяем кэш
	val, err := s.rdb.Get(ctx, key).Result()
	if err == nil {
		fmt.Println("[STATUS] Успешное чтение из Redis")
		return val, nil
	}

	// Ветка 2: Анализируем ошибку
	if errors.Is(err, redis.Nil) {
		fmt.Println("[STATUS] Промах кэша (redis.Nil)")
	} else {
		// Сетевой сбой Redis
		log.Printf("[WARN] Сбой подключения к Redis: %v. Деградируем к чтению из БД.", err)
	}

	// Ветка 3: Читаем из PostgreSQL
	data, err := s.queryPostgreSQL(id)
	if err != nil {
		return "", fmt.Errorf("postgres error: %w", err)
	}

	// Пробуем асинхронно или безопасно сохранить в кэш
	_ = s.rdb.Set(ctx, key, data, 10*time.Minute).Err()

	return data, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	store := &RobustUserStore{rdb: rdb}
	_ = rdb.Del(ctx, "user:cache:808").Err()

	// 1. Промах
	u, err := store.GetUser(ctx, 808)
	if err != nil {
		log.Fatalf("Error: %v", err)
	}
	fmt.Printf("Получено: %s\n\n", u)

	// 2. Попадание
	u, _ = store.GetUser(ctx, 808)
	fmt.Printf("Получено: %s\n", u)
}
```

## Под капотом

Такой паттерн проектирования гарантирует, что время жизни (Availability) вашего микросервиса по SLA останется высоким (99.99%) даже при плановых перезагрузках или авариях кэш-слоя.

## Подводные камни

Не ограничивать контекст таймаутом при чтении из Redis. Если сеть повиснет, запрос зависнет надолго. Задавайте `ctx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)` для операций с кэшем.

## На собеседовании

**Вопрос с собеседования:** «Какой максимальный таймаут (SLA) следует выделять на операцию чтения из Redis в высоконагруженных API?»
**Ответ:** В BigTech сервисах таймаут на операцию чтения кэша обычно составляет от 20 до 50 миллисекунд. Если Redis не ответил за 50 мс, контекст отменяется, а запрос немедленно перенаправляется в базу данных, чтобы уложиться в общий пользовательский SLA ответа шлюза.
