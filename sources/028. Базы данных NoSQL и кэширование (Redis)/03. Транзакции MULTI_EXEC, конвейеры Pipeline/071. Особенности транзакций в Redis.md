# Особенности транзакций в Redis: TxPipeline и отсутствие Rollback

## Условие

**Транзакции в Redis**: Redis поддерживает транзакции (они не такие строгие, как в SQL). Используй `client.TxPipeline()`, чтобы выполнить несколько команд. Если хоть одна упадет, остальные не откатятся (особенность Redis), но они гарантированно выполнятся друг за другом, не прерываясь командами других клиентов.

## Теория

Транзакции в Redis (MULTI/EXEC) фундаментально отличаются от ACID-транзакций в SQL:
1. **Изоляция (Isolation):** идеальная. Команды гарантированно выполняются единым неделимым блоком.
2. **Атомарность (Atomicity):** частичная. Если в процессе исполнения одна из команд падает (например, `INCR` по строковому ключу), остальные команды НЕ откатываются назад!

## Решение по шагам

1. Создайте строковый ключ и числовой ключ.
2. Откройте `TxPipeline`.
3. Вызовите корректную команду, затем заведомо ошибочную команду (`Incr` на строке), затем еще одну корректную команду.
4. Убедитесь, что первая и третья команды успешно применились.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	_ = rdb.Set(ctx, "tx:string_val", "not_a_number", 0).Err()
	_ = rdb.Set(ctx, "tx:valid_counter", 10, 0).Err()

	// Открываем транзакционный конвейер MULTI/EXEC
	pipe := rdb.TxPipeline()

	cmd1 := pipe.Incr(ctx, "tx:valid_counter")  // корректно (10 -> 11)
	cmd2 := pipe.Incr(ctx, "tx:string_val")     // ОШИБКА: Incr на нечисловой строке!
	cmd3 := pipe.Set(ctx, "tx:final_key", "ok", 0) // корректно

	// Выполняем транзакцию
	_, err := pipe.Exec(ctx)
	fmt.Printf("Ошибка TxPipeline: %v (ожидалась ошибка от cmd2)\n\n", err)

	// Проверяем результаты отдельных команд
	fmt.Printf("cmd1 (валидный инкремент): Err=%v, Val=%d\n", cmd1.Err(), cmd1.Val())
	fmt.Printf("cmd2 (ошибочный инкремент): Err=%v\n", cmd2.Err())
	fmt.Printf("cmd3 (установка ключа):     Err=%v\n", cmd3.Err())

	// Проверяем состояние ключей в Redis
	cVal, _ := rdb.Get(ctx, "tx:valid_counter").Int64()
	fVal, _ := rdb.Get(ctx, "tx:final_key").Result()
	fmt.Printf("\nИтоговое состояние в Redis:\n  • tx:valid_counter = %d (применилось!)\n  • tx:final_key = %s (применилось!)\n", cVal, fVal)
}
```

ℹ️ Демонстрация отсутствия отката (No Rollback) в транзакциях Redis

**`Терминал`**

```bash
go run main.go
# Вывод:
# Ошибка TxPipeline: ERR value is not an integer or out of range (ожидалась ошибка от cmd2)
# 
# cmd1 (валидный инкремент): Err=<nil>, Val=11
# cmd2 (ошибочный инкремент): Err=ERR value is not an integer or out of range
# cmd3 (установка ключа):     Err=<nil>
# 
# Итоговое состояние в Redis:
#   • tx:valid_counter = 11 (применилось!)
#   • tx:final_key = ok (применилось!)
```

## Под капотом

Этот практический пример наглядно иллюстрирует внутреннее устройство Redis: команды в блоке `MULTI` проверяются на синтаксис при постановке в очередь (`QUEUE`), но ошибки семантики типов возникают только при непосредственном исполнении внутри `EXEC`, не прерывая выполнение последующих команд списка.

## Подводные камни

Полагаться на `TxPipeline` для транзакций, требующих обязательного отката всех действий при любой ошибке. Для строгой атомарности используйте Lua-скрипты.

## На собеседовании

**Вопрос с собеседования:** «В каком единственном случае транзакция `EXEC` отменяется полностью?»
**Ответ:** Транзакция полностью отменяется, если: 1. До вызова `EXEC` сработал триггер `WATCH` (отслеживаемый ключ был изменен извне). 2. При постановке команд в очередь возникла синтаксическая ошибка (например, передано неверное число аргументов команды), в этом случае Redis возвращает ошибку и флаг `CLIENT_DIRTY_EXEC`.
