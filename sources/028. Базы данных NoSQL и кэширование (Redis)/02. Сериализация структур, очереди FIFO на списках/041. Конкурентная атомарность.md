# Конкурентная атомарность: 100 горутин инкрементируют page_views

## Условие

Используй `client.Incr(ctx, "page_views")` для атомарного инкремента счетчика просмотров. Запусти 100 горутин, инкрементирующих счетчик, и убедись, что в итоге будет ровно 100.

## Теория

В распределенных веб-серверах одновременный приход 100 HTTP-запросов на инкремент одного счетчика в Redis не требует локальных мьютексов Go (`sync.Mutex`).
Каждая горутина отправляет сетевой пакет `INCR page_views`. Сервер Redis последовательно обрабатывает каждый запрос в цикле событий, гарантируя результат ровно 100.

## Решение по шагам

1. Сбросьте ключ `"page_views"`.
2. Создайте `sync.WaitGroup` на 100 итераций.
3. В каждой горутине вызовите `client.Incr(ctx, "page_views")`.
4. Дождитесь завершения и распечатайте итоговое значение.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	key := "page_views"
	_ = rdb.Del(ctx, key).Err()

	const goroutines = 100
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := 0; i < goroutines; i++ {
		go func() {
			defer wg.Done()
			if err := rdb.Incr(ctx, key).Err(); err != nil {
				log.Printf("Incr error: %v", err)
			}
		}()
	}

	wg.Wait()

	val, err := rdb.Get(ctx, key).Int64()
	if err != nil {
		log.Fatalf("Get failed: %v", err)
	}

	fmt.Printf("Итоговый счетчик page_views: %d (ожидалось 100)\n", val)
}
```

ℹ️ Конкурентный инкремент из 100 параллельных горутин

**`Терминал`**

```bash
go run main.go
# Вывод: Итоговый счетчик page_views: 100 (ожидалось 100)
```

## Под капотом

Сетевые сокеты в Linux буферизируют входящие TCP-сегменты. Даже если пакеты поступают на сетевую карту в одно мгновение, ядро ОС упорядочивает их в очереди сокета. `epoll_wait` в Redis поочередно считывает дескрипторы и выполняет `incrCommand` без переключения контекста потоков.

## Подводные камни

Забывать вызывать `wg.Add()` до запуска горутины. Вызов `wg.Add()` внутри горутины приводит к гонке данных и преждевременному возврату из `wg.Wait()`.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если при 100k RPS инкремент одного счетчика в Redis упирается в пропускную способность CPU одного ядра?»
**Ответ:** Применяется паттерн **Distributed Sharded Counters**. Создается N независимых ключей: `page_views:0`, `page_views:1`, ..., `page_views:9`. Клиент рандомно инкрементирует `page_views:rand(0, 9)`. Суммарное значение просмотров вычисляется через `MGET` и суммирование в памяти Go. Это распределяет нагрузку по разным ядрам и шардам кластера.
