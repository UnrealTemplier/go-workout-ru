# Конвейеризация команд через Pipeline: оптимизация задержки сети

## Условие

**Pipelines**: Сгруппируйте 1000 команд `GET` в один Pipeline (`pipe := rdb.Pipeline()`), отправьте их одним сетевым запросом и измерьте разницу во времени (latency) по сравнению с последовательными вызовами.

## Теория

При выполнении команд по одной клиент ждет сетевого ответа на каждую команду:
$$\text{Total Time} = N \times (\text{RTT} + \text{Server Time})$$
При \(N = 1000\) и \(\text{RTT} = 1\text{ мс}\) это займет более 1 секунды!

**Redis Pipelining** позволяет клиенту сложить пачку команд в локальный буфер и отправить их на сервер в одном TCP-пакете. Сервер выполняет команды подряд и возвращает ответы одним пакетом:
$$\text{Total Time} = \text{RTT} + N \times \text{Server Time}$$
Время падает с 1000 мс до 3–5 мс!

## Решение по шагам

1. Создайте 100 тестовых ключей.
2. Выполните 100 `Get` последовательно, замерив время.
3. Выполните 100 `Get` через `pipe := rdb.Pipeline()`, замерив время.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	const total = 500

	// Заполним ключи
	initPipe := rdb.Pipeline()
	for i := 0; i < total; i++ {
		initPipe.Set(ctx, fmt.Sprintf("bench:k:%d", i), "val", 10*time.Minute)
	}
	_, _ = initPipe.Exec(ctx)

	// 1. Последовательное чтение
	startSeq := time.Now()
	for i := 0; i < total; i++ {
		_ = rdb.Get(ctx, fmt.Sprintf("bench:k:%d", i)).Err()
	}
	seqDuration := time.Since(startSeq)

	// 2. Чтение через Pipeline
	startPipe := time.Now()
	pipe := rdb.Pipeline()
	cmds := make([]*redis.StringCmd, total)
	for i := 0; i < total; i++ {
		cmds[i] = pipe.Get(ctx, fmt.Sprintf("bench:k:%d", i))
	}
	_, err := pipe.Exec(ctx)
	if err != nil {
		log.Fatalf("Pipeline failed: %v", err)
	}
	pipeDuration := time.Since(startPipe)

	fmt.Printf("Последовательно (500 запросов): %v\n", seqDuration)
	fmt.Printf("Через Pipeline   (500 запросов): %v\n", pipeDuration)
	fmt.Printf("🚀 Ускорение в %.1f раз!\n", float64(seqDuration)/float64(pipeDuration))
}
```

ℹ️ Сравнение производительности Pipeline и обычных запросов

**`Терминал`**

```bash
go run main.go
# Вывод:
# Последовательно (500 запросов): 42.5ms
# Через Pipeline   (500 запросов): 2.1ms
# 🚀 Ускорение в 20.2 раз!
```

## Под капотом

Pipeline не является транзакцией! Команды из пайплайна выполняются быстро, но между ними на сервере могут вклиниваться команды от других клиентов. Если вам нужна строгая атомарность выполнения пачки команд, используйте `rdb.TxPipeline()` (MULTI/EXEC) или Lua-скрипт.

## Подводные камни

Пытаться прочитать результат команды до вызова `pipe.Exec()`. До `Exec()` ни одна команда не отправлена на сервер, поэтому `cmd.Result()` вернет ошибку `redis: pipeline has not been executed`.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между `Pipeline()` и `TxPipeline()`?»
**Ответ:** Обычный `Pipeline()` просто склеивает сетевые запросы для экономии RTT (команды не изолированы). `TxPipeline()` обрамляет пачку команд инструкциями `MULTI` и `EXEC`, гарантируя, что ни одна сторонняя команда не выполнится внутри этой пачки на сервере Redis.
