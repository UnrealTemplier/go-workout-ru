# Оптимистичная блокировка WATCH/MULTI/EXEC для предотвращения Lost Updates

## Условие

**Транзакции (WATCH/MULTI/EXEC)**: Реализуйте оптимистичную блокировку. "Следите" (`WATCH`) за ключом баланса, начинайте транзакцию и выполняйте списание. Если ключ изменился извне до `EXEC`, транзакция прервется, и вы повторите её.

## Теория

Оптимистичная блокировка в Redis реализуется связкой команд `WATCH`, `MULTI` и `EXEC`.
1. Клиент вызывает `WATCH key` — Redis начинает отслеживать любые изменения этого ключа.
2. Клиент считывает текущий баланс и валидирует бизнес-правило (например `balance >= cost`).
3. Клиент открывает транзакцию `MULTI`, добавляет команды и вызывает `EXEC`.
4. Если между шагом 1 и шагом 3 другой клиент успел изменить ключ, Redis прерывает транзакцию и возвращает ошибку `redis.TxFailedErr`. Клиент повторяет попытку (retry loop).

## Решение по шагам

1. Используйте метод `rdb.Watch(ctx, fn, keys...)` библиотеки `go-redis`.
2. Внутри коллбэка считайте баланс, проверьте условие.
3. Откройте транзакционный конвейер через `tx.TxPipelined(ctx, ...)`.
4. Обработайте ошибку `redis.TxFailedErr` и сделайте retry.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"strconv"
	"time"

	"github.com/redis/go-redis/v9"
)

func deductBalanceOptimistic(ctx context.Context, rdb *redis.Client, accountKey string, amount int64) error {
	const maxRetries = 5

	for i := 0; i < maxRetries; i++ {
		err := rdb.Watch(ctx, func(tx *redis.Tx) error {
			// 1. Считываем баланс под защитой WATCH
			balStr, err := tx.Get(ctx, accountKey).Result()
			if err != nil && !errors.Is(err, redis.Nil) {
				return err
			}

			currentBalance, _ := strconv.ParseInt(balStr, 10, 64)
			if currentBalance < amount {
				return fmt.Errorf("недостаточно средств: баланс %d < списание %d", currentBalance, amount)
			}

			// 2. Выполняем транзакцию списания
			_, err = tx.TxPipelined(ctx, func(pipe redis.Pipeliner) error {
				pipe.Set(ctx, accountKey, currentBalance-amount, 0)
				return nil
			})
			return err
		}, accountKey)

		if errors.Is(err, redis.TxFailedErr) {
			fmt.Printf("Конфликт обновления (попытка %d), повторяем retry...\n", i+1)
			time.Sleep(10 * time.Millisecond)
			continue
		}

		return err
	}

	return fmt.Errorf("превышено количество попыток retry")
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	key := "account:wallet:88"
	_ = rdb.Set(ctx, key, 1000, 0).Err()

	err := deductBalanceOptimistic(ctx, rdb, key, 300)
	if err != nil {
		log.Fatalf("Ошибка списания: %v", err)
	}

	newBal, _ := rdb.Get(ctx, key).Int64()
	fmt.Printf("Списание 300 успешно выполнено! Новый баланс: %d\n", newBal)
}
```

## Под капотом

Каждый инстанс Redis хранит словарь `watched_keys`. Если любая команда (`SET`, `INCR`, `DEL`) изменяет отслеживаемый ключ, Redis устанавливает клиенту специальный флаг `CLIENT_DIRTY_CAS`. При последующем вызове `EXEC` Redis проверяет этот флаг и, если он выставлен, отбрасывает транзакцию, возвращая `nil`.

## Подводные камни

Выполнять долгие вызовы (HTTP-запросы или тяжелые вычисления) внутри функции под `WATCH`. Чем дольше открыта транзакция, тем выше вероятность конкурентного изменения ключа и бесконечных повторов `TxFailedErr`.

## На собеседовании

**Вопрос с собеседования:** «Почему вместо сложной связки `WATCH/MULTI/EXEC` сегодня чаще используют Lua-скрипты?»
**Ответ:** Lua-скрипт исполняется атомарно за ОДИН сетевой запрос. В нем нет необходимости организовывать retry-циклы при конфликтах, тратить RTT на отслеживание изменений и переживать за гонки данных. Lua полностью вытеснил `WATCH` в современном HighLoad коде.
