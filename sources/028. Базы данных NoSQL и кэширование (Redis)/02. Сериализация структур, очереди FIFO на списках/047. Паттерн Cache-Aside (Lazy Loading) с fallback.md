# Паттерн Cache-Aside (Lazy Loading) с fallback в базу данных

## Условие

Реализуйте простой кэш с TTL: перед запросом к PostgreSQL проверяйте Redis, если промах — загружайте из БД и сохраняйте в Redis.

## Теория

Паттерн **Cache-Aside (Ленивая загрузка)** — доминирующая стратегия кэширования в распределенных микросервисах:
1. Приложение запрашивает данные из кэша.
2. При наличии (Cache Hit) данные возвращаются мгновенно.
3. При отсутствии (Cache Miss) приложение идет в реляционную БД (PostgreSQL).
4. Загруженные данные сохраняются в Redis с установленным TTL.
5. Данные возвращаются клиенту.

## Решение по шагам

1. Создайте эмулятор вызова к базе данных `fetchProductFromPostgres(id)`.
2. Реализуйте `GetProductWithCache(ctx, id)`.
3. Покажите, что первый вызов обращается к БД, а второй берет данные из Redis.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type ProductService struct {
	rdb *redis.Client
}

func (s *ProductService) queryPostgresSlow(id int64) (string, error) {
	// Имитация тяжелого SQL-запроса с задержкой
	time.Sleep(100 * time.Millisecond)
	return fmt.Sprintf("Товар #%d: Игровой монитор 4K 144Hz", id), nil
}

func (s *ProductService) GetProduct(ctx context.Context, id int64) (string, error) {
	cacheKey := fmt.Sprintf("product:%d", id)

	// 1. Проверяем кэш
	val, err := s.rdb.Get(ctx, cacheKey).Result()
	if err == nil {
		fmt.Printf("[CACHE HIT] Товар %d получен из Redis!\n", id)
		return val, nil
	}

	if !errors.Is(err, redis.Nil) {
		log.Printf("Внимание: ошибка кэша: %v (деградируем в БД)", err)
	}

	// 2. Cache Miss: читаем из базы данных
	fmt.Printf("[CACHE MISS] Товар %d загружается из PostgreSQL...\n", id)
	dbData, err := s.queryPostgresSlow(id)
	if err != nil {
		return "", err
	}

	// 3. Сохраняем в кэш с TTL 60 секунд
	_ = s.rdb.Set(ctx, cacheKey, dbData, 60*time.Second).Err()

	return dbData, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	svc := &ProductService{rdb: rdb}
	_ = rdb.Del(ctx, "product:77").Err()

	// Первый вызов: промах кэша
	start := time.Now()
	val1, _ := svc.GetProduct(ctx, 77)
	fmt.Printf("Вызов 1 занял: %v | Данные: %s\n\n", time.Since(start), val1)

	// Второй вызов: попадание в кэш
	start = time.Now()
	val2, _ := svc.GetProduct(ctx, 77)
	fmt.Printf("Вызов 2 занял: %v | Данные: %s\n", time.Since(start), val2)
}
```

ℹ️ Реализация паттерна Cache-Aside

**`Терминал`**

```bash
go run main.go
# Вывод:

# Вызов 1 занял: 102ms | Данные: Товар #77: Игровой монитор 4K 144Hz
# 
# [CACHE HIT] Товар 77 получен из Redis!
# Вызов 2 занял: 450µs | Данные: Товар #77: Игровой монитор 4K 144Hz
```

## Под капотом

Разница во времени между обращением к БД (100 мс) и попаданием в кэш Redis (450 микросекунд) составляет более чем **200 раз**! Это разгружает дисковую подсистему PostgreSQL и снижает Latency сервиса для конечного пользователя.

## Подводные камни

Проблема устаревания данных (Stale Data): если данные в PostgreSQL обновлены, а кэш еще не истек по TTL, пользователи будут видеть устаревшую информацию. Решение: явная инвалидация кэша (`DEL product:id`) при любом UPDATE/DELETE в базе данных.

## На собеседовании

**Вопрос с собеседования:** «Что лучше делать при обновлении строки в PostgreSQL: обновлять кэш (`SET`) или удалять (`DEL` / инвалидация)?»
**Ответ:** Почти всегда лучше **удалять (`DEL`)**. Если обновлять кэш при каждом UPDATE, мы тратим ресурсы на расчет и сериализацию данных, которые, возможно, никто никогда не запросит. Кроме того, при конкурентных UPDATE двух транзакций можно получить гонку записей в Redis, записав устаревшую версию поверх новой.
