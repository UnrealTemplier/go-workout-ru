# Высоконагруженный счетчик просмотров статьи: Incr без блокировок

## Условие

**Счетчики (Incr / Decr)**: Реализуй счетчик просмотров статьи. Используй `client.Incr(ctx, "article:123:views")`. (В отличие от реляционной БД с транзакциями, в Redis `Incr` атомарен и работает за наносекунды).

## Теория

В HighLoad медиа-порталах (Хабр, VC, новостные порталы) статьи читают десятки тысяч пользователей одновременно. Если при каждом открытии страницы делать `UPDATE articles SET views = views + 1 WHERE id = 123` в PostgreSQL, возникает жесткий lock contention на строке таблицы, раздувание WAL и деградация БД.

Архитектурный стандарт:
1. Быстрый инкремент в Redis: `INCR article:123:views`.
2. Периодический фоновый сброс (Flush) накопленных счетчиков в PostgreSQL раз в 1 минуту (Write-Back pattern).

## Решение по шагам

1. Напишите функцию `RecordArticleView(ctx, articleID)`.
2. Вызовите `rdb.Incr(ctx, fmt.Sprintf("article:%d:views", articleID))`.
3. Запустите 50 конкурентных горутин для имитации трафика.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"

	"github.com/redis/go-redis/v9"
)

type ArticleStatsService struct {
	rdb *redis.Client
}

func (s *ArticleStatsService) RecordView(ctx context.Context, articleID int64) (int64, error) {
	key := fmt.Sprintf("article:%d:views", articleID)
	return s.rdb.Incr(ctx, key).Result()
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	svc := &ArticleStatsService{rdb: rdb}
	articleID := int64(90210)
	key := fmt.Sprintf("article:%d:views", articleID)
	_ = rdb.Del(ctx, key).Err()

	// Имитируем 100 одновременных читателей
	var wg sync.WaitGroup
	const readers = 100
	wg.Add(readers)

	for i := 0; i < readers; i++ {
		go func() {
			defer wg.Done()
			_, err := svc.RecordView(ctx, articleID)
			if err != nil {
				log.Printf("View count error: %v", err)
			}
		}()
	}

	wg.Wait()

	totalViews, err := rdb.Get(ctx, key).Int64()
	if err != nil {
		log.Fatalf("Get error: %v", err)
	}

	fmt.Printf("Итоговое количество просмотров статьи #%d: %d\n", articleID, totalViews)
}
```

ℹ️ Паттерн быстрого сбора просмотров без блокировки реляционной базы

**`Терминал`**

```bash
go run main.go
# Вывод: Итоговое количество просмотров статьи #90210: 100
```

## Под капотом

Благодаря тому, что `INCR` обновляет 8-байтное число по месту в оперативной памяти без дисковых транзакционных логов (при `appendfsync everysec`), один узел Redis способен обрабатывать более 150 000 операций инкремента в секунду на одном процессорном ядре.

## Подводные камни

Хранить просмотры только в Redis без периодического сброса в постоянное хранилище. При аварии или перезагрузке инстанса несохраненные данные могут быть частично утеряны.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать периодическую синхронизацию счетчиков из Redis в PostgreSQL без потери новых поступающих инкрементов?»
**Ответ:** Командой `GETSET key 0` (или `SET key 0 GET` в Redis 6.2+). Мы атомарно считываем накопленную сумму и одновременно обнуляем ключ в Redis. Считанное значение добавляем в PostgreSQL: `UPDATE articles SET views = views + $1 WHERE id = $2`. Новые инкременты от пользователей продолжают накапливаться в Redis с нуля, ничего не теряется.
