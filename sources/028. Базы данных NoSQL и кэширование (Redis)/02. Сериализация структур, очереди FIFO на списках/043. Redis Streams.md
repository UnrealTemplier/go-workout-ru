# Redis Streams: брокер сообщений нового поколения и Consumer Groups

## Условие

**Streams**: Реализуйте современную очередь сообщений (аналог Kafka) с использованием `XADD`, `XREADGROUP` и Consumer Groups для распределенной обработки сообщений несколькими воркерами.

## Теория

Redis Streams (появились в Redis 5.0) — это персистентный append-only лог событий, спроектированный как легковесная альтернатива Apache Kafka:
- `XADD mystream * field value ...`: публикация события с автогенерацией уникального ID (`<timestampMS>-<sequence>`).
- `XGROUP CREATE mystream mygroup $ MKSTREAM`: создание группы потребителей.
- `XREADGROUP GROUP mygroup consumer_1 COUNT 1 BLOCK 2000 STREAMS mystream >`: чтение новых недоставленных сообщений.
- `XACK mystream mygroup id`: подтверждение успешной обработки сообщения.

## Решение по шагам

1. Создайте Stream и добавьте событие заказа через `rdb.XAdd`.
2. Создайте Consumer Group через `rdb.XGroupCreateMkStream`.
3. Прочитайте сообщение воркером через `rdb.XReadGroup`.
4. Подтвердите обработку через `rdb.XAck`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	streamKey := "stream:orders"
	groupName := "order_processors"
	consumerName := "worker_1"

	_ = rdb.Del(ctx, streamKey).Err()

	// 1. Создаем Consumer Group
	err := rdb.XGroupCreateMkStream(ctx, streamKey, groupName, "$").Err()
	if err != nil {
		log.Fatalf("XGroupCreate error: %v", err)
	}
	fmt.Printf("Consumer Group '%s' создана для стрима '%s'\n", groupName, streamKey)

	// 2. Публикуем событие через XADD
	msgID, err := rdb.XAdd(ctx, &redis.XAddArgs{
		Stream: streamKey,
		Values: map[string]interface{}{
			"order_id": 9942,
			"amount":   4500.50,
			"currency": "RUB",
		},
	}).Result()
	if err != nil {
		log.Fatalf("XAdd error: %v", err)
	}
	fmt.Printf("Событие опубликовано с ID: %s\n", msgID)

	// 3. Вычитываем событие воркером через XREADGROUP
	streams, err := rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
		Group:    groupName,
		Consumer: consumerName,
		Streams:  []string{streamKey, ">"}, // ">" означает только новые нераспределенные сообщения
		Count:    1,
		Block:    2 * time.Second,
	}).Result()
	if err != nil {
		log.Fatalf("XReadGroup error: %v", err)
	}

	for _, str := range streams {
		for _, msg := range str.Messages {
			fmt.Printf("Воркер %s получил задачу [ID: %s]: %v\n", consumerName, msg.ID, msg.Values)

			// 4. Подтверждаем обработку (ACK)
			if err := rdb.XAck(ctx, streamKey, groupName, msg.ID).Err(); err != nil {
				log.Printf("Ack error: %v", err)
			}
			fmt.Println("Задача успешно подтверждена (XACK)!")
		}
	}
}
```

ℹ️ Распределенная обработка событий через Redis Streams

```bash

```

## Под капотом

Каждое сообщение в Redis Streams хранится в компактном префиксном дереве (Radix Tree, Rax), узлы которого содержат `listpack`. До отправки `XACK` сообщение числится в структуре PEL (Pending Entries List) данной группы потребителей. Если воркер упадет в процессе обработки, другое приложение может обнаружить зависшее сообщение через `XPENDING` и перехватить его командой `XCLAIM`.

## Подводные камни

Бесконечный рост стрима. В отличие от Kafka с retention policy по времени, в Redis по умолчанию `XADD` добавляет записи навсегда. Чтобы стрим не переполнил оперативную память, используйте ограничение длины: `XADD stream MAXLEN ~ 100000 *`.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Redis Streams от Redis Pub/Sub?»
**Ответ:** Pub/Sub работает по модели "Fire-and-Forget": сообщения нигде не сохраняются, и если подписчик был отключен, сообщение теряется навсегда. Streams — персистентный лог: сообщения сохраняются на диске/в памяти, поддерживают чтение истории, группы потребителей, балансировку нагрузки и подтверждение обработки (`XACK`).
