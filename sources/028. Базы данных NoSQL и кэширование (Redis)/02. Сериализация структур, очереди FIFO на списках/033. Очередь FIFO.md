# Очередь FIFO: QueuePush (RPush) и блокирующий QueuePop (BLPop)

## Условие

Напиши функцию `QueuePush(key string, value string) (int64, error)` и `QueuePop(key string) (string, error)`, использующие `RPush` + `BLPop` (blocking left pop). Реализуй **FIFO очередь** с блокирующим ожиданием.

## Теория

Очередь FIFO строится на симметричных операциях:
- Запись в правый конец списка (хвост): `RPUSH queue value`.
- Блокирующее чтение из левого конца списка (голова): `BLPOP queue timeout`.

Команда `BLPOP` принимает список ключей и таймаут в секундах. Если в очереди есть элементы, она немедленно извлекает первый и возвращает его. Если очередь пуста, соединение блокируется до поступления элемента или истечения времени.

## Решение по шагам

1. Реализуйте `QueuePush(ctx, key, val) (int64, error)`.
2. Реализуйте `QueuePop(ctx, key, timeout) (string, error)`.
3. Продемонстрируйте передачу сообщений между двумя горутинами.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type RedisQueue struct {
	rdb *redis.Client
}

func (q *RedisQueue) QueuePush(ctx context.Context, key, value string) (int64, error) {
	return q.rdb.RPush(ctx, key, value).Result()
}

func (q *RedisQueue) QueuePop(ctx context.Context, key string, timeout time.Duration) (string, error) {
	// BLPop возвращает срез: [имя_очереди, значение]
	res, err := q.rdb.BLPop(ctx, timeout, key).Result()
	if errors.Is(err, redis.Nil) {
		return "", fmt.Errorf("queue timeout: empty")
	}
	if err != nil {
		return "", err
	}
	return res[1], nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	q := &RedisQueue{rdb: rdb}
	queueKey := "orders:processing_queue"
	_ = rdb.Del(ctx, queueKey).Err()

	// 1. Consumer ждет в горутине
	go func() {
		fmt.Println("[Consumer] Ожидаем заказ из очереди...")
		msg, err := q.QueuePop(ctx, queueKey, 5*time.Second)
		if err != nil {
			log.Printf("[Consumer] Ошибка: %v", err)
			return
		}
		fmt.Printf("[Consumer] ✅ Заказ успешно получен и обработан: %s\n", msg)
	}()

	// 2. Producer отправляет через секунду
	time.Sleep(1 * time.Second)
	length, err := q.QueuePush(ctx, queueKey, "order_id_#9841_confirmed")
	if err != nil {
		log.Fatalf("Push failed: %v", err)
	}
	fmt.Printf("[Producer] Заказ отправлен в очередь (длина очереди: %d)\n", length)

	// Ждем завершения обработки
	time.Sleep(500 * time.Millisecond)
}
```

ℹ️ FIFO очередь на базе RPush и BLPop

## Под капотом

В `BLPOP` можно передать сразу несколько ключей очередей: `BLPOP queue:high queue:low 5`. В этом случае Redis реализует приоритетную очередь (Priority Queue): он сначала проверит `queue:high`, и только если она пуста — перейдет к `queue:low`. Это позволяет без дополнительных библиотек строить воркеры с поддержкой приоритетов VIP-задач!

## Подводные камни

Переполненная очередь (Queue Overflow): если продюсеры генерируют 10 000 задач в секунду, а воркеры обрабатывают только 1 000, длина списка (`LLEN`) будет расти до бесконечности, исчерпав память Redis. Всегда мониторьте длину очереди через `rdb.LLen(ctx, queue)`.

## На собеседовании

**Вопрос с собеседования:** «Что лучше для очередей задач: Redis Lists или RabbitMQ/Kafka?»
**Ответ:** Redis Lists превосходны для легковесных простых очередей с низкой задержкой (sub-millisecond) и простыми сценариями. Однако для сложных корпоративных очередей требуются гарантии подтверждения (Manual ACK), очереди недоставленных сообщений (Dead Letter Queue / DLQ), ретраи и строгая персистентность — для этого используют RabbitMQ или Redis Streams.
