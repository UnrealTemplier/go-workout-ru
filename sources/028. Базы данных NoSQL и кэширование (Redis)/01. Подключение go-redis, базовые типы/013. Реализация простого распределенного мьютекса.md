# Реализация простого распределенного мьютекса через SetNX

## Условие

Используйте `SetNX` (Set if Not eXists) для реализации простейшего распределенного лока (mutex).

## Теория

Распределенный мьютекс гарантирует, что критическую секцию в любой момент времени выполняет не более одного экземпляра распределенного приложения.
Базовый алгоритм захвата:
1. Выполнить `SET resource_name my_random_value NX PX 30000`.
2. Если Redis вернул `OK`, блокировка успешно захвачена.
3. Если вернул `nil`, блокировка занята другим процессом — нужно либо подождать с задержкой (backoff), либо вернуть ошибку отказа.

## Решение по шагам

1. Определите структуру `RedisMutex`.
2. Реализуйте метод `Lock(ctx)` с циклом попыток и таймаутом.
3. Реализуйте метод `Unlock(ctx)`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type RedisMutex struct {
	client *redis.Client
	key    string
	value  string
	ttl    time.Duration
}

func NewRedisMutex(client *redis.Client, key, value string, ttl time.Duration) *RedisMutex {
	return &RedisMutex{
		client: client,
		key:    key,
		value:  value,
		ttl:    ttl,
	}
}

func (m *RedisMutex) TryLock(ctx context.Context) (bool, error) {
	return m.client.SetNX(ctx, m.key, m.value, m.ttl).Result()
}

func (m *RedisMutex) Unlock(ctx context.Context) error {
	return m.client.Del(ctx, m.key).Err()
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	mutex := NewRedisMutex(rdb, "mutex:nightly_report", "instance_01", 5*time.Second)

	// Захват блокировки
	ok, err := mutex.TryLock(ctx)
	if err != nil {
		log.Fatalf("Ошибка захвата: %v", err)
	}
	if !ok {
		log.Println("Критическая секция занята другим сервисом, пропускаем запуск")
		return
	}
	defer func() {
		_ = mutex.Unlock(ctx)
		fmt.Println("Блокировка успешно освобождена")
	}()

	fmt.Println("Выполняем тяжелую работу внутри распределенной критической секции...")
	time.Sleep(500 * time.Millisecond)
}
```

ℹ️ Паттерн TryLock на базе SetNX

**`Терминал`**

```bash
go run main.go
# Вывод:
# Выполняем тяжелую работу внутри распределенной критической секции...
# Блокировка успешно освобождена
```

## Под капотом

TTL в `SetNX` критически необходим для защиты от зависаний (Deadlock). Если бы TTL отсутствовал, а сервер с приложением внезапно обесточился (Power Outage), ключ блокировки остался бы навсегда в Redis, парализовав фоновые задачи навсегда. Наличие TTL гарантирует, что даже при физической гибели инстанса блокировка автоматически сбросится через 5-30 секунд.

## Подводные камни

Опасность наивного `Unlock` через `Del`: если критическая секция выполнялась дольше, чем TTL (например, пауза сборщика мусора Stop-The-World или зависание диска), блокировка истечет, ее захватит другой воркер. А первый воркер, очнувшись, вызовет `Unlock` и удалит чужую блокировку!

## На собеседовании

**Вопрос с собеседования:** «Как сделать снятие блокировки `Unlock` абсолютно безопасным?»
**Ответ:** Использовать Lua-скрипт, который атомарно проверяет, совпадает ли значение в ключе с нашим уникальным `UUID`:
`if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`. Это гарантирует, что процесс может удалить только свой собственный замок.
