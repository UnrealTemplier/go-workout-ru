# Полный цикл базовых операций: Set с TTL, Get и Del

## Условие

Реализуйте базовые операции: `Set` (с указанием TTL), `Get`, `Del`. Всегда проверяйте ошибку `redis.Nil`, которая означает, что ключ не найден (это не ошибка сети!).

## Теория

Любое кэширующее решение оперирует триадой CRUD-действий: создание/обновление с экспирацией, выборка и инвалидация. В реальных распределенных системах эти операции должны выполняться строго в рамках SLA (например, таймаут не более 50 мс на операцию с кэшем).

## Решение по шагам

1. Создайте структуру сервиса кэширования `StringCache`.
2. Реализуйте методы `Set(ctx, key, val, ttl)`, `Get(ctx, key)` и `Delete(ctx, key)`.
3. Напишите тест-сценарий, демонстрирующий полный жизненный цикл данных.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type StringCache struct {
	client *redis.Client
}

func (c *StringCache) Set(ctx context.Context, key, value string, ttl time.Duration) error {
	return c.client.Set(ctx, key, value, ttl).Err()
}

func (c *StringCache) Get(ctx context.Context, key string) (string, bool, error) {
	val, err := c.client.Get(ctx, key).Result()
	if errors.Is(err, redis.Nil) {
		return "", false, nil
	}
	if err != nil {
		return "", false, err
	}
	return val, true, nil
}

func (c *StringCache) Del(ctx context.Context, key string) error {
	return c.client.Del(ctx, key).Err()
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	cache := &StringCache{client: rdb}
	key := "auth:token:user_101"

	// 1. Set
	if err := cache.Set(ctx, key, "secret_payload_xyz", 5*time.Second); err != nil {
		log.Fatalf("Set failed: %v", err)
	}
	fmt.Println("1. Ключ успешно записан с TTL 5s")

	// 2. Get
	val, found, err := cache.Get(ctx, key)
	if err != nil {
		log.Fatalf("Get failed: %v", err)
	}
	if found {
		fmt.Printf("2. Ключ прочитан: %s\n", val)
	}

	// 3. Del
	if err := cache.Del(ctx, key); err != nil {
		log.Fatalf("Del failed: %v", err)
	}
	fmt.Println("3. Ключ удален")

	// 4. Проверка отсутствия
	_, found, err = cache.Get(ctx, key)
	if err != nil {
		log.Fatalf("Get after Del failed: %v", err)
	}
	fmt.Printf("4. Повторное чтение: найдено = %v\n", found)
}
```

ℹ️ Полный CRUD цикл над ключами Redis

**`Терминал`**

```bash

# 2. Ключ прочитан: secret_payload_xyz
# 3. Ключ удален

```

## Под капотом

В `go-redis` для строковых значений память аллоцируется в куче Go только при парсинге ответа. Когда вызывается `rdb.Get()`, парсер RESP считывает длину строки `$18\r\n`, делает срез байт `make([]byte, 18)` и преобразует его в `string`. При высоких нагрузках это создает нагрузку на сборщик мусора Go (GC). Для снижения аллокаций в высоконагруженных шлюзах рекомендуется использовать метод `rdb.Get(ctx, key).Bytes()`.

## Подводные камни

Устанавливать ключи без TTL (`ttl = 0`). Если приложение не удалит такой ключ явно, память Redis будет монотонно расти, пока не сработает политика вытеснения или OOM Killer ОС Linux.

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшене запрещено задавать строго одинаковый TTL для всех кэшируемых ключей (например, ровно 3600 секунд для всех товаров)?»
**Ответ:** Это приводит к проблеме `Cache Avalanche` (лавина кэша). Если миллион товаров кэшируются одновременно во время утреннего прогрева с фиксированным TTL 1 час, через ровно 60 минут все миллион ключей одновременно экспирируются. Последующий поток пользовательских запросов мгновенно пробьет кэш и обрушит реляционную СУБД (Postgres). Решение — добавление случайного разброса (TTL Jitter, например `3600s + rand(0, 300s)`).
