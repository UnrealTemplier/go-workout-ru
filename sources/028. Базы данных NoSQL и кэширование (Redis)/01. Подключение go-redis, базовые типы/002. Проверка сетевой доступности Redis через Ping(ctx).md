# Проверка сетевой доступности Redis через Ping(ctx)

## Условие

Подключитесь к Redis с помощью `github.com/redis/go-redis/v9`. Используйте `Ping` для проверки связи.

## Теория

Метод `redis.NewClient(...)` не открывает физическое TCP-соединение немедленно в момент вызова; он лишь создает управляющую структуру и ленивый пул соединений. Реальное рукопожатие TCP происходит только при первом запросе.

Для проверки доступности сервера при старте приложения (например, в рамках Kubernetes Readiness/Liveness Probe) необходимо отправить команду `PING` через метод `rdb.Ping(ctx)`. При успешном ответе Redis возвращает строку `"PONG"`.

## Решение по шагам

1. Создайте клиент с коротким таймаутом на диалог (`DialTimeout: 2 * time.Second`).
2. Сформируйте контекст с ограничением времени выполнения `context.WithTimeout(context.Background(), 1*time.Second)`.
3. Вызовите `rdb.Ping(ctx).Result()` и проверьте результат.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func checkRedisHealth(ctx context.Context, rdb *redis.Client) error {
	pingCtx, cancel := context.WithTimeout(ctx, 1500*time.Millisecond)
	defer cancel()

	pong, err := rdb.Ping(pingCtx).Result()
	if err != nil {
		return fmt.Errorf("redis ping failed: %w", err)
	}

	fmt.Printf("Успешный ответ от Redis: %s\n", pong)
	return nil
}

func main() {
	rdb := redis.NewClient(&redis.Options{
		Addr:        "localhost:6379",
		DialTimeout: 2 * time.Second,
	})
	defer rdb.Close()

	if err := checkRedisHealth(context.Background(), rdb); err != nil {
		log.Fatalf("Healthcheck error: %v", err)
	}
}
```

ℹ️ Проверка доступности инстанса Redis через Ping

**`Терминал`**

```bash
go run main.go
# Вывод: Успешный ответ от Redis: PONG
```

## Под капотом

Команда PING отправляется в формате текстового протокола RESP (REdis Serialization Protocol): `*1\r\n$4\r\nPING\r\n`. Redis парсит входящий буфер, генерирует простой строковый ответ `+PONG\r\n` и немедленно отправляет его обратно в TCP-сокет. В `go-redis` клиент извлекает свободное соединение из внутреннего пула (FIFO queue) или инициирует `net.Dialer.DialContext`, если свободных соединений нет.

## Подводные камни

Считать, что `redis.NewClient` вернет ошибку, если Redis выключен. `redis.NewClient` никогда не возвращает `error`, ошибка сетевого отказа возникнет только на этапе `Ping` или первого запроса.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисах перед стартом HTTP-сервера рекомендуется вызывать `Ping`, а не полагаться на ленивые соединения?»
**Ответ:** Это предотвращает феномен `Cascading Failure` (лавинообразный сбой). Если инстанс поднимется, зарегистрируется в Service Discovery или балансировщике (Kubernetes Endpoint), но Redis недоступен, он сразу начнет отвечать пользователям ошибками 500. Проверка в `main` или Health Probe позволяет задержать маршрутизацию трафика до готовности базы данных.
