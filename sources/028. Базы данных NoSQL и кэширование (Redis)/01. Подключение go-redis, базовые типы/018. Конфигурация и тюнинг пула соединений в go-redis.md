# Конфигурация и тюнинг пула соединений в go-redis

## Условие

Настройте пул соединений в `go-redis` (`PoolSize`, `MinIdleConns`) и изучите, как он влияет на пропускную способность.

## Теория

Пул соединений (Connection Pool) устраняет колоссальные накладные расходы на TCP 3-Way Handshake и TLS-рукопожатие при каждом запросе.
Ключевые параметры пула в `redis.Options`:
- `PoolSize`: максимальное количество TCP-сокетов в пуле (по умолчанию `10 * runtime.GOMAXPROCS`).
- `MinIdleConns`: минимальное количество постоянно открытых «прогретых» соединений, которые клиент держит готовыми к всплескам трафика (Spike Traffic).
- `PoolTimeout`: время ожидания свободного сокета при исчерпании пула перед возвратом ошибки `redis: connection pool timeout`.

## Решение по шагам

1. Настройте `PoolSize: 20`, `MinIdleConns: 5`, `PoolTimeout: 1 * time.Second`.
2. Запросите статистику пула через `rdb.PoolStats()`.
3. Распечатайте количество активных и простаивающих соединений.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	opts := &redis.Options{
		Addr:         "localhost:6379",
		PoolSize:     25,              // макс. 25 соединений
		MinIdleConns: 5,               // держим 5 соединений теплыми
		PoolTimeout:  2 * time.Second, // ждем сокет максимум 2с
		IdleTimeout:  5 * time.Minute, // закрывать сокет при бездействии
	}

	rdb := redis.NewClient(opts)
	defer rdb.Close()

	ctx := context.Background()

	// Выполним проверочный запрос для инициализации
	if err := rdb.Ping(ctx).Err(); err != nil {
		log.Fatalf("Ping failed: %v", err)
	}

	// Считываем статистику пула соединений
	stats := rdb.PoolStats()
	fmt.Printf("--- Статистика пула go-redis ---\n")
	fmt.Printf("Всего соединений (TotalConns): %d\n", stats.TotalConns)
	fmt.Printf("Простаивающих (IdleConns):    %d\n", stats.IdleConns)
	fmt.Printf("Устаревших (StaleConns):       %d\n", stats.StaleConns)
	fmt.Printf("Таймаутов ожидания (Timeouts): %d\n", stats.Timeouts)
}
```

ℹ️ Настройка и мониторинг метрик пула соединений

**`Терминал`**

```bash
go run main.go
# Вывод:
# --- Статистика пула go-redis ---
# Всего соединений (TotalConns): 5
# Простаивающих (IdleConns):    5
# Устаревших (StaleConns):       0
# Таймаутов ожидания (Timeouts): 0
```

## Под капотом

Внутри `go-redis` пул реализован как очередь сокетов. Если горутина запрашивает соединение, а свободных нет и `TotalConns < PoolSize`, создается новое соединение. Если достигнут `PoolSize`, горутина встает в очередь ожидания на канале с таймаутом `PoolTimeout`. Если за отведенное время ни одно соединение не освободилось, возвращается ошибка.

## Подводные камни

Установка чрезмерно большого `PoolSize` (например, 5000 на инстанс). Если у вас 20 реплик сервиса в Kubernetes, суммарно они попытаются открыть 100 000 TCP-соединений к Redis. Это исчерпает лимит файловых дескрипторов `maxclients` сервера Redis и приведет к падению всей инфраструктуры.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если в логах появляется ошибка `redis: connection pool timeout`?»
**Ответ:** 1. Проверить, не зависают ли запросы в Redis (медленные команды, блокирующие Event Loop). 2. Увеличить `PoolSize`, если сервис уперся в лимит при высоком RPS. 3. Проверить утечки: не забывает ли код считывать ответы до конца. 4. Использовать мультиплексирование или шардированный кластер Redis.
