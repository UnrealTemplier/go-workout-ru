# Увеличение счетчика и немедленное получение значения

## Условие

Увеличьте счётчик (`INCR`) и атомарно получите новое значение.

## Теория

В сетевых протоколах критически важно уменьшать количество сетевых обращений (Round Trip Time, RTT). Если разработчик сначала выполняет команду `INCR`, а затем отдельной командой `GET`, он:
1. Тратит удвоенное время на передачу по сети.
2. Теряет гарантию атомарности: между `INCR` и `GET` другой параллельный клиент может успеть еще раз изменить счетчик!

Сервер Redis проектировался с учетом этого: ответ команды `INCR` — это и есть актуальное новое значение счетчика после инкремента.

## Решение по шагам

1. Вызовите `rdb.Incr(ctx, key)`.
2. Сохраните значение возвращаемой переменной `int64`.
3. Убедитесь, что дополнительный вызов `Get` не требуется.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

func trackAction(ctx context.Context, rdb *redis.Client, userID int64) (int64, error) {
	key := fmt.Sprintf("user:%d:action_count", userID)

	// rdb.Incr возвращает IntCmd, у которого метод Result() возвращает (int64, error)
	newCount, err := rdb.Incr(ctx, key).Result()
	if err != nil {
		return 0, fmt.Errorf("failed to increment actions: %w", err)
	}

	return newCount, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	val, err := trackAction(ctx, rdb, 555)
	if err != nil {
		log.Fatalf("Error: %v", err)
	}

	fmt.Printf("Пользователь совершил действие. Текущий счетчик: %d\n", val)
}
```

ℹ️ Атомарное получение результата прямо из Incr

**`Терминал`**

```bash
go run main.go
# Вывод: Пользователь совершил действие. Текущий счетчик: 1
```

## Под капотом

Протокол RESP в ответ на `INCR` шлет целочисленный ответ формата `:1\r\n`. Парсер `go-redis` декодирует префикс `:` сразу в знаковое 64-битное целое `int64`, минуя любые строковые аллокации в памяти Go.

## Подводные камни

Вызов `rdb.Incr(ctx, key)` с последующим `rdb.Get(ctx, key)` — антипаттерн удвоения RTT и источник гонок данных (race condition).

## На собеседовании

**Вопрос с собеседования:** «Каковы гарантии надежности `INCR` при включенном AOF (Append-Only File)?»
**Ответ:** Зависит от настройки `appendfsync`. При `appendfsync always` каждая команда `INCR` сбрасывается на диск через `fsync()` перед возвратом клиенту (максимальная надежность, но производительность падает до нескольких тысяч RPS). При стандартном `appendfsync everysec` сброс буфера ядра на диск происходит раз в секунду, поэтому при аварии ОС может быть утеряна максимум 1 секунда инкрементов.
