# Запись и чтение строк с истечением TTL (SET/GET)

## Условие

**Запись и чтение строк (SET/GET)**: Напишите функцию кэширования текстовых данных. Запишите в Redis ключ `"session_token"` со значением `"user_123_active"`. Установите время жизни ключа (TTL) равным 10 секундам. Прочитайте значение ключа и выведите его на экран. Подождите 11 секунд и попробуйте прочитать ключ снова.

## Теория

Экспирация ключей (TTL) — один из фундаментальных механизмов Redis. Задавая время жизни, мы превращаем базу данных в самоочищающийся кэш, защищенный от переполнения памяти.

При истечении TTL ключ считается несуществующим. Команда `GET` возвращает `redis.Nil`, а команда `TTL key` возвращает `-2` (ключ не существует) либо `-1` (ключ существует, но без TTL).

## Решение по шагам

1. Запишите `"session_token"` со значением `"user_123_active"` и TTL 2 секунды (для быстроты демонстрации в коде).
2. Прочитайте значение сразу после записи.
3. Сделайте `time.Sleep` на время, превышающее TTL.
4. Прочитайте ключ снова и убедитесь в возврате `redis.Nil`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	key := "session_token"
	val := "user_123_active"
	ttl := 2 * time.Second // для наглядности используем 2 сек вместо 10 сек

	// 1. Запись с TTL
	err := rdb.Set(ctx, key, val, ttl).Err()
	if err != nil {
		log.Fatalf("Ошибка Set: %v", err)
	}
	fmt.Printf("1. Записан ключ '%s' со значением '%s' и TTL %v\n", key, val, ttl)

	// 2. Чтение сразу
	res, err := rdb.Get(ctx, key).Result()
	if err != nil {
		log.Fatalf("Ошибка Get: %v", err)
	}
	fmt.Printf("2. Сразу после записи прочитано: '%s'\n", res)

	// 3. Ожидание экспирации
	fmt.Println("3. Ожидаем истечения TTL (спим 3 секунды)...")
	time.Sleep(3 * time.Second)

	// 4. Повторное чтение после истечения TTL
	resAfter, err := rdb.Get(ctx, key).Result()
	if errors.Is(err, redis.Nil) {
		fmt.Println("4. Ключ успешно и автоматически удален Redis по истечении TTL (redis.Nil)")
	} else if err != nil {
		log.Fatalf("Неожиданная ошибка: %v", err)
	} else {
		log.Fatalf("Ключ все еще существует: %s", resAfter)
	}
}
```

## Под капотом

Внутри ядра Redis TTL хранится как абсолютное время Unix Timestamp в миллисекундах (`mstime_t`). Когда мы передаем относительный таймаут 2 секунды, Redis прибавляет его к текущему `server.mstime` (`server.mstime + 2000`). Благодаря этому при репликации на слейвы передается команда `PEXPIREAT key timestamp`, что гарантирует идентичный момент экспирации данных на репликах.

## Подводные камни

Рассинхронизация часов (Clock Drift) между серверами по протоколу NTP. Если часы на реплике отстают или спешат на 10 секунд, ключ может протухнуть раньше времени при переключении мастера.

## На собеседовании

**Вопрос с собеседования:** «Почему освобождение памяти после истечения TTL в Redis не происходит строго мгновенно секунда в секунду?»
**Ответ:** Redis использует ленивое удаление (Lazy Expire при чтении) и фоновый периодический цикл (Periodic Active Expire, проверяющий выборку ключей 10 раз в секунду). Если ключ никто не читает, а в базе миллионы ключей, протухший ключ может физически оставаться в оперативной памяти еще некоторое время, пока до него не дойдет фоновый рандомизированный сборщик мусора.
