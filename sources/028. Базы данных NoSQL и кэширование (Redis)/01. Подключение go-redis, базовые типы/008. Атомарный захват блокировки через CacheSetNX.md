# Атомарный захват блокировки через CacheSetNX

## Условие

Напиши функцию `CacheSetNX(key string, value any, ttl time.Duration) (bool, error)`, использующую `rdb.SetNX(ctx, key, value, ttl)`. Это **distributed lock**: если ключ не существует — устанавливает и возвращает `true`. Иначе — `false`.

## Теория

Команда `SETNX` (Set if Not eXists) исторически была отдельной инструкцией. Сегодня она эквивалентна команде `SET key value NX EX seconds`.
Главное свойство `SetNX` — **строгая атомарность**. Если два или более независимых инстансов микросервисов одновременно пытаются установить один и тот же ключ, Redis благодаря однопоточному Event Loop выполнит только один запрос первым. Первый клиент получит `OK` (в Go `true`), а все остальные — `nil` (в Go `false`). Это простейший строительный блок для распределенных мьютексов.

## Решение по шагам

1. Напишите функцию `CacheSetNX(ctx, key, value, ttl)`.
2. Вызовите `rdb.SetNX(ctx, key, value, ttl).Result()`.
3. Запустите 2 конкурирующие попытки захвата одного и того же ключа.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

type Locker struct {
	rdb *redis.Client
}

func (l *Locker) CacheSetNX(ctx context.Context, key string, value any, ttl time.Duration) (bool, error) {
	// SetNX атомарно проверяет отсутствие ключа и устанавливает его вместе с TTL
	success, err := l.rdb.SetNX(ctx, key, value, ttl).Result()
	if err != nil {
		return false, fmt.Errorf("ошибка SetNX: %w", err)
	}
	return success, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	locker := &Locker{rdb: rdb}
	lockKey := "lock:billing:process:order_999"

	// Первая попытка захвата
	acquired1, err := locker.CacheSetNX(ctx, lockKey, "worker_A", 10*time.Second)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
	fmt.Printf("Воркер А: захват локера = %v (успех)\n", acquired1)

	// Вторая попытка захвата тем же ключом (пока ключ еще жив)
	acquired2, err := locker.CacheSetNX(ctx, lockKey, "worker_B", 10*time.Second)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
	fmt.Printf("Воркер B: захват локера = %v (блокировка занята)\n", acquired2)

	// Очистка
	_ = rdb.Del(ctx, lockKey).Err()
}
```

ℹ️ Реализация распределенного лока через SetNX

**`Терминал`**

```bash
go run main.go
# Вывод:
# Воркер А: захват локера = true (успех)
# Воркер B: захват локера = false (блокировка занята)
```

## Под капотом

В старых версиях Redis разработчики вызывали `SETNX key value`, а затем отдельной командой `EXPIRE key seconds`. Если между этими двумя командами процесс приложения аварийно падал (OOM, SIGKILL) или разрывалась сеть, ключ оставался в Redis навсегда без TTL, приводя к перманентному дедлоку всей системы!
Современный `SetNX` в `go-redis` использует составную команду `SET key value NX PX milliseconds`, которая выполняется атомарно внутри одного тика планировщика Redis.

## Подводные камни

Использовать в качестве значения просто статическую строку (например `"1"` или `"locked"`). Если воркер закончит работу позже истечения TTL и сделает `DEL lockKey`, он случайно удалит блокировку уже другого воркера! Значением всегда должен быть уникальный UUID воркера.

## На собеседовании

**Вопрос с собеседования:** «Почему простейший `SetNX` нельзя использовать в Redis Cluster без дополнительных предосторожностей (алгоритма Redlock)?»
**Ответ:** Репликация в Redis асинхронная. Если клиент успешно захватил блокировку на Master через `SetNX`, но Master упал до того, как реплицировал запись на Slave, произойдет промоушен Slave в новый Master. Новый Master не знает о блокировке и выдаст ее второму клиенту. Произойдет нарушение взаимоисключения (Split Brain). Для отказоустойчивых блокировок применяется Redlock на 5 независимых инстансах.
