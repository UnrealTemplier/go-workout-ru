# Безопасная итерация по ключам: Scan против блокирующего Keys

## Условие

Изучите разницу между `Keys("*")` и `Scan()`. Напишите скрипт, который удаляет ключи по паттерну, используя **только** `Scan`, чтобы не заблокировать продакшен-Redis (команда `KEYS` блокирует поток!).

## Теория

Команда `KEYS pattern` — одна из самых опасных в Redis. Ее сложность составляет O(N), где N — общее число ВСЕХ ключей в БД. На продакшене с десятками миллионов ключей вызов `KEYS *` заблокирует единственный поток сервера на 5–30 секунд! За это время все клиентские соединения отвалятся по таймауту, а сервис ляжет.

Для безопасной итерации используется семейство команд `SCAN`:
`SCAN cursor [MATCH pattern] [COUNT count]`
Команда работает на основе курсора, возвращая за один шаг небольшую порцию ключей (по умолчанию ~10) и новый курсор. Сложность одного шага O(1). Поток сервера не блокируется!

## Решение по шагам

1. Создайте 20 тестовых ключей с префиксом `temp:session:`.
2. Используйте метод `rdb.Scan(ctx, cursor, match, count).Iterator()` библиотеки `go-redis`.
3. В цикле удаляйте найденные ключи.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

func cleanKeysByPattern(ctx context.Context, rdb *redis.Client, matchPattern string) (int, error) {
	var deletedCount int

	// go-redis предоставляет удобный курсорный итератор
	iter := rdb.Scan(ctx, 0, matchPattern, 100).Iterator()

	for iter.Next(ctx) {
		key := iter.Val()
		// Удаляем найденный ключ
		if err := rdb.Del(ctx, key).Err(); err != nil {
			log.Printf("ошибка удаления ключа %s: %v", key, err)
			continue
		}
		deletedCount++
	}

	if err := iter.Err(); err != nil {
		return deletedCount, fmt.Errorf("ошибка scan-итератора: %w", err)
	}

	return deletedCount, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	// Создадим пачку ключей
	for i := 1; i <= 10; i++ {
		key := fmt.Sprintf("temp:cache:item_%d", i)
		_ = rdb.Set(ctx, key, "value", 0).Err()
	}

	fmt.Println("Начинаем безопасную очистку через SCAN...")
	count, err := cleanKeysByPattern(ctx, rdb, "temp:cache:*")
	if err != nil {
		log.Fatalf("Ошибка очистки: %v", err)
	}

	fmt.Printf("Успешно и безопасно удалено %d ключей без блокировки Event Loop!\n", count)
}
```

## Под капотом

Хэш-таблица Redis при `SCAN` обходится по алгоритму обратной реверсивной битовой маски (Reverse Binary Iteration). Это позволяет корректно итерироваться по корзинам таблицы даже в процессе ее динамического масштабирования (Incremental Rehashing), гарантируя, что ключи не будут пропущены при расширении или сжатии хэш-таблицы.

## Подводные камни

1. Ожидать от `SCAN` строго уникального набора ключей: из-за рехэширования во время итерации один и тот же ключ может вернуться дважды. Приложение должно быть готово к дубликатам.
2. Использование `COUNT` как точного лимита: аргумент `COUNT` в Redis — это лишь подсказка серверу (hint), сколько корзин хэш-таблицы просканировать, а не точный размер возвращаемого среза.

## На собеседовании

**Вопрос с собеседования:** «Почему в большинстве компаний команду `KEYS` отключают в конфигурационном файле `redis.conf`?»
**Ответ:** Команду отключают директивой `rename-command KEYS ""` ради стабильности продакшена. Даже опытный разработчик может случайно выполнить `KEYS *` в командной строке `redis-cli`, что мгновенно вызовет отказ обслуживания (DoS) всего сервиса под высокой нагрузкой.
