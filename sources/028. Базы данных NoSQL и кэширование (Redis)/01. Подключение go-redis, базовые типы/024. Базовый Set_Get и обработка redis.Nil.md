# Базовый Set/Get и обработка redis.Nil через errors.Is

## Условие

**Базовый Set/Get и redis.Nil**: Сохрани строковое значение по ключу: `client.Set(ctx, "mykey", "hello", 0)`. Прочитай его. Затем попробуй прочитать несуществующий ключ и обработай ошибку `errors.Is(err, redis.Nil)`.

## Теория

Проверка на `redis.Nil` — важнейший паттерн при работе с кэшем. В отличие от SQL-драйверов, где отсутствие строки возвращает `sql.ErrNoRows`, клиент `go-redis` возвращает `redis.Nil`.

## Решение по шагам

1. Запишите строковый ключ `"mykey" = "hello"`.
2. Прочитайте существующий ключ и выведите его значение.
3. Попробуйте прочитать ключ `"missing_key_example"`.
4. Обработайте ошибку через `errors.Is(err, redis.Nil)`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	// 1. Запись
	if err := rdb.Set(ctx, "mykey", "hello", 0).Err(); err != nil {
		log.Fatalf("Set failed: %v", err)
	}

	// 2. Чтение существующего
	val, err := rdb.Get(ctx, "mykey").Result()
	if err != nil {
		log.Fatalf("Get failed: %v", err)
	}
	fmt.Printf("Значение mykey: %s\n", val)

	// 3. Чтение несуществующего с errors.Is
	_, err = rdb.Get(ctx, "missing_key_example").Result()
	if errors.Is(err, redis.Nil) {
		fmt.Println("Успешно обработан redis.Nil: ключ действительно отсутствует в Redis!")
	} else if err != nil {
		log.Fatalf("Сетевой сбой: %v", err)
	}
}
```

ℹ️ Идиоматичная проверка redis.Nil через errors.Is

**`Терминал`**

```bash
go run main.go
# Вывод:
# Значение mykey: hello
# Успешно обработан redis.Nil: ключ действительно отсутствует в Redis!
```

## Под капотом

`redis.Nil` объявлен в пакете `redis` как переменная `Nil = errors.New("redis: nil")`. Пакет `errors` из стандартной библиотеки Go начиная с Go 1.13 сопоставляет указатели на ошибки при вызове `errors.Is(err, redis.Nil)`.

## Подводные камни

Паниковать или логировать `redis.Nil` как ошибку уровня ERROR. Это заполняет мониторинг и логи ложными тревогами при каждом обычном промахе кэша.

## На собеседовании

**Вопрос с собеседования:** «Каковы три уровня реакции бэкенда на `redis.Nil` в паттерне Cache-Aside?»
**Ответ:** 1. `redis.Nil` зафиксирован: идем в основную СУБД (PostgreSQL). 2. Если запись найдена в PostgreSQL: сериализуем и записываем в Redis с TTL. 3. Если запись отсутствует и в PostgreSQL: кэшируем специальный sentinel-объект (пустоту) с коротким TTL для защиты от Cache Penetration.
