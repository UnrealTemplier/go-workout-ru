# Разграничение ошибок: Cache Miss против сетевого отказа

## Условие

**Обработка отсутствия ключа**: При попытке получить несуществующий ключ клиент `go-redis` возвращает специальную ошибку. Напишите проверку: если возвращаемая ошибка равна `redis.Nil`, выведите сообщение `"Ключ не найден в кэше"`, иначе обработайте сетевую ошибку.

## Теория

Критическая ошибка многих джуниор-разработчиков — писать:
`if err != nil { return err }`
При таком подходе при первом же промахе кэша сервис падает или прекращает обработку запроса! Нужно явно разделять логику:
- `err == nil` -> данные есть в кэше, отдаем клиенту (Cache Hit).
- `errors.Is(err, redis.Nil)` -> данных нет, идем в базу данных (Cache Miss).
- `err != nil` -> сетевой разрыв, Redis недоступен. Логируем WARN, но не роняем сервис: деградируем и пробуем прочитать данные напрямую из БД!

## Решение по шагам

1. Напишите функцию `FetchWithGracefulFallback(ctx, key)`.
2. Если `errors.Is(err, redis.Nil)`, верните сообщение о промахе кэша.
3. Если ошибка сетевая (например, таймаут сокета), верните инфраструктурную ошибку.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

func fetchFromCacheOrDB(ctx context.Context, rdb *redis.Client, key string) (string, error) {
	val, err := rdb.Get(ctx, key).Result()
	if err == nil {
		fmt.Println("[HIT] Данные найдены в кэше Redis!")
		return val, nil
	}

	if errors.Is(err, redis.Nil) {
		fmt.Println("[MISS] Ключ не найден в кэше. Загружаем из базы данных...")
		// Здесь вызов к PostgreSQL...
		dbValue := "данные_из_postgres"
		return dbValue, nil
	}

	// Любая другая ошибка — это реальный сетевой или системный сбой Redis
	return "", fmt.Errorf("инфраструктурный сбой Redis: %w", err)
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	val, err := fetchFromCacheOrDB(ctx, rdb, "product:item_404")
	if err != nil {
		log.Fatalf("Критический сбой: %v", err)
	}

	fmt.Printf("Результат выполнения: %s\n", val)
}
```

ℹ️ Паттерн правильного разграничения Cache Miss и сбоя сети

**`Терминал`**

```bash
go run main.go
# Вывод:
# [MISS] Ключ не найден в кэше. Загружаем из базы данных...
# Результат выполнения: данные_из_postgres
```

## Под капотом

Паттерн Graceful Degradation (плавная деградация) заключается в том, что кэш — это ускоряющая надстройка, а не источник истины. Если инстанс Redis временно перезагружается или потерял сеть, микросервис должен продолжить обслуживать клиентов напрямую из PostgreSQL (возможно, с повышенной задержкой), а не возвращать ошибку 500.

## Подводные камни

Использовать `err == redis.Nil` вместо `errors.Is(err, redis.Nil)`. Если ошибка была обернута через `fmt.Errorf("redis error: %w", err)`, прямое сравнение указателей `==` вернет `false`!

## На собеседовании

**Вопрос с собеседования:** «Что делать, если при падении Redis все микросервисы одновременно пойдут в PostgreSQL и положат её (Thundering Herd)?»
**Ответ:** Применяется паттерн **Circuit Breaker** (предохранитель). Если частота ошибок подключения к Redis превышает порог (например 50%), Circuit Breaker размыкается и временно ограничивает поток запросов к PostgreSQL, либо возвращает пользователям устаревшие данные из локального in-memory кэша инстанса (L1 cache).
