# Первое подключение к Redis и запись с TTL через go-redis

## Условие

Подключитесь к Redis с помощью `go-redis`. Установите ключ `greeting` со значением и TTL 30 секунд.

## Теория

Клиентская библиотека `github.com/redis/go-redis/v9` является де-факто стандартом взаимодействия с Redis в экосистеме Go. Начиная с версии v9, клиент полностью ориентирован на передачу `context.Context` во все исполняемые команды, что гарантирует соблюдение таймаутов и корректную отмену сетевых операций.

Команда `SET key value EX seconds` в протоколе RESP атомарно выполняет запись строкового значения и назначает таймер жизни ключа (Time To Live). В `go-redis` для этого используется метод `rdb.Set(ctx, key, value, expiration)`. Передача ненулевого значения `time.Duration` трансформируется в аргумент `EX` (секунды) или `PX` (миллисекунды).

## Решение по шагам

1. Инициализируйте контекст приложения `ctx := context.Background()`.
2. Создайте клиент Redis через `redis.NewClient` с указанием адреса сервера (`localhost:6379`).
3. Обязательно добавьте отложенное закрытие пула соединений через `defer rdb.Close()`.
4. Вызовите метод `rdb.Set(ctx, "greeting", "Привет из Go!", 30*time.Second).Err()` и проверьте возвращенную ошибку.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()

	// Инициализация клиента
	rdb := redis.NewClient(&redis.Options{
		Addr:     "localhost:6379",
		Password: "", // пароль по умолчанию отсутствует
		DB:       0,  // используем стандартную логическую БД 0
	})
	defer func() {
		if err := rdb.Close(); err != nil {
			log.Printf("ошибка закрытия клиента: %v", err)
		}
	}()

	// Запись ключа greeting со значением и TTL 30 секунд
	err := rdb.Set(ctx, "greeting", "Привет, высоконагруженный Redis!", 30*time.Second).Err()
	if err != nil {
		log.Fatalf("не удалось установить ключ: %v", err)
	}

	fmt.Println("Ключ 'greeting' успешно сохранен с TTL 30s")
}
```

ℹ️ Базовое подключение и запись с TTL в go-redis/v9

**`Терминал`**

```bash
# Запуск локального Redis в Docker для тестов
docker run -d --name redis-local -p 6379:6379 redis:7-alpine

# Запуск Go-программы
go run main.go

# Проверка через redis-cli

# Вывод: (integer) 29
```

## Под капотом

Redis — однопоточный сервер в части обработки команд (Single-Threaded Event Loop на базе `epoll`/`kqueue`), что устраняет необходимость синхронизации структур данных в памяти мьютексами ядра. 
При вызове `SET ... EX 30` Redis сохраняет значение в глобальной хэш-таблице `dict` (как объект `robj` с типом `OBJ_STRING`), а абсолютную временную метку экспирации (Unix timestamp в миллисекундах) помещает во вспомогательный словарь `expires` текущей БД. Механизм удаления протухших ключей гибридный: пассивный (lazy — проверка при обращении к ключу) и активный (фоновый таймер каждые 100 мс случайной выборкой 20 ключей).

## Подводные камни

1. Игнорирование закрытия клиента: `redis.Client` содержит внутри пул сетевых соединений. Не вызывать `rdb.Close()` при завершении сервиса ведет к утечке файловых дескрипторов (FD leak).
2. Использование нулевого контекста: передача `context.TODO()` или неконтролируемого `context.Background()` в продакшене блокирует горутину при сетевом зависании. Всегда используйте `context.WithTimeout`.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если в Redis закончится оперативная память, а мы продолжаем выполнять `SET` с TTL?»
**Ответ:** Поведение зависит от директивы `maxmemory-policy`. По умолчанию при `noeviction` Redis вернет клиенту ошибку `OOM command not allowed when used memory > 'maxmemory'`. При политиках `volatile-lru` или `allkeys-lru` Redis вытеснит наименее востребованные ключи для освобождения места под новый `SET`.
