# Distributed Lock с фоновым автопродлением (Watchdog Heartbeat)

## Условие

Реализуй **distributed lock с автопродлением**: goroutine раз в 5 секунд делает `Expire` на lock, пока основная работа не завершится. При завершении — `Del`. Используй `context` для отмены продления.

## Теория

Классическая дилемма распределенных блокировок:
- Если выставить TTL слишком маленьким (например 3 секунды), тяжелая задача (выгрузка отчета, импорт данных) может не успеть завершиться, лок сбросится, и второй инстанс начнет параллельную работу.
- Если выставить TTL огромным (например 1 час), и инстанс упадет по панике/OOM, ресурс останется заблокированным на целый час.

**Решение: паттерн Watchdog (Heartbeat).** Блокировка берется с коротким TTL (например 6 секунд), а фоновая горутина каждые 2 секунды продлевает жизнь ключа (`EXPIRE lock 6s`). Когда основная задача завершается, контекст отменяется, воркер снимает блокировку через `DEL`.

## Решение по шагам

1. Захватите блокировку с TTL 6 секунд.
2. Создайте отменяемый контекст `watchdogCtx, cancelWatchdog := context.WithCancel(ctx)`.
3. Запустите горутину с тикером `time.NewTicker(2 * time.Second)`, которая шлет `rdb.Expire(ctx, key, 6*time.Second)`.
4. Выполните долгую работу (например, 7 секунд).
5. Остановите Watchdog через `cancelWatchdog()` и удалите ключ.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func runWithLockWatchdog(ctx context.Context, rdb *redis.Client, lockKey string, taskDuration time.Duration) error {
	lockTTL := 4 * time.Second
	refreshInterval := 1500 * time.Millisecond

	// 1. Захват блокировки
	acquired, err := rdb.SetNX(ctx, lockKey, "worker_watchdog", lockTTL).Result()
	if err != nil {
		return fmt.Errorf("setnx failed: %w", err)
	}
	if !acquired {
		return fmt.Errorf("lock already acquired by another worker")
	}
	fmt.Printf("Лок захвачен с базовым TTL %v\n", lockTTL)

	// 2. Инициализируем Watchdog
	watchdogCtx, cancelWatchdog := context.WithCancel(ctx)
	defer func() {
		cancelWatchdog()                // останавливаем горутину продления
		_ = rdb.Del(context.Background(), lockKey).Err() // удаляем лок
		fmt.Println("Watchdog остановлен, лок успешно удален")
	}()

	go func() {
		ticker := time.NewTicker(refreshInterval)
		defer ticker.Stop()

		for {
			select {
			case <-watchdogCtx.Done():
				return
			case <-ticker.C:
				// Продлеваем TTL ключа
				res, err := rdb.Expire(watchdogCtx, lockKey, lockTTL).Result()
				if err != nil || !res {
					log.Printf("Watchdog: не удалось продлить лок: %v", err)
					return
				}
				fmt.Printf("[Watchdog] TTL лока успешно продлен на %v\n", lockTTL)
			}
		}
	}()

	// 3. Выполняем задачу, которая длится дольше, чем начальный TTL
	fmt.Printf("Выполняется долгая операция (длительность %v)...\n", taskDuration)
	time.Sleep(taskDuration)
	fmt.Println("Долгая операция успешно выполнена!")

	return nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	lockKey := "lock:heavy_etl_job"
	_ = rdb.Del(ctx, lockKey).Err()

	// Задача длится 5 секунд при TTL всего 4 секунды
	if err := runWithLockWatchdog(ctx, rdb, lockKey, 5*time.Second); err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

## Под капотом

Если бы процесс с Go-кодом внезапно упал по SIGKILL (OOM Killer ядра Linux), горутина Watchdog мгновенно прекратит свое существование вместе с процессом. Сервер Redis больше не получит команду `EXPIRE`, и ровно через 4 секунды ключ автоматически экспирируется. Это гарантирует отсутствие бесконечного дедлока при внезапных сбоях инфраструктуры.

## Подводные камни

Использовать один и тот же `ctx` для `rdb.Del` в `defer`. Если основной `ctx` был отменен по таймауту запроса, вызов `rdb.Del(ctx, key)` завершится ошибкой `context canceled` и лок не снимется. Для финальной очистки в `defer` следует использовать `context.Background()` или отвязанный контекст.

## На собеседовании

**Вопрос с собеседования:** «Как алгоритм Watchdog реализован в промышленных распределенных локерах, например Redisson (Java) или Redsync (Go)?»
**Ответ:** Полноценный Watchdog не просто шлет `EXPIRE`, а использует Lua-скрипт для проверки, что ключ по-прежнему содержит наш уникальный `token`. Если другой процесс каким-то образом перехватил ключ, продление прерывается. Кроме того, при сбое продления Watchdog оповещает основной рабочий поток об утере блокировки, чтобы рабочий поток немедленно прервал модификацию данных (Fencing / Safety).
