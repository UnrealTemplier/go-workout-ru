# Очередь задач FIFO на списках: LPUSH и блокирующий BRPOP

## Условие

**Lists**: Реализуйте простую FIFO-очередь задач, используя `LPUSH` (для добавления) и `BRPOP` (блокирующее чтение для воркера).

## Теория

Redis Lists представляют собой двусвязные списки строк.
Паттерн FIFO-очереди (First In, First Out):
- Производитель (Producer) добавляет задачи в начало списка командой `LPUSH queue_name task_payload`.
- Потребитель (Consumer) извлекает задачи с конца списка командой `RPOP` или блокирующей версией `BRPOP queue_name timeout`.

Преимущество `BRPOP`: воркер не крутит пустой цикл (busy polling), нагружая процессор и сеть миллионами пустых запросов. TCP-сокет просто блокируется сервером Redis до тех пор, пока в списке не появится элемент, либо пока не истечет таймаут.

## Решение по шагам

1. Создайте Producer горутину, которая раз в 500 мс делает `LPUSH queue task`.
2. Создайте Consumer горутину, которая в цикле вызывает `rdb.BRPop(ctx, 2*time.Second, queue)`.
3. Запустите воркер и обработайте 3 задачи.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	queueKey := "queue:email_tasks"
	_ = rdb.Del(ctx, queueKey).Err()

	// Горутина-Producer: добавляет 3 задачи
	go func() {
		for i := 1; i <= 3; i++ {
			time.Sleep(300 * time.Millisecond)
			task := fmt.Sprintf("send_welcome_email_to_user_%d", i)
			if err := rdb.LPush(ctx, queueKey, task).Err(); err != nil {
				log.Printf("Producer error: %v", err)
			}
			fmt.Printf("--> [Producer] Добавлена задача: %s\n", task)
		}
	}()

	// Consumer: читает через BRPOP
	fmt.Println("Воркер запущен и ожидает задачи через BRPOP...")
	for i := 1; i <= 3; i++ {
		// BRPop возвращает срез [queue_name, element]
		results, err := rdb.BRPop(ctx, 2*time.Second, queueKey).Result()
		if errors.Is(err, redis.Nil) {
			fmt.Println("Таймаут ожидания задачи (очередь пуста)")
			continue
		} else if err != nil {
			log.Fatalf("BRPop error: %v", err)
		}

		queueName := results[0]
		taskPayload := results[1]
		fmt.Printf("<-- [Consumer] Извлечена задача из '%s': %s\n", queueName, taskPayload)
	}
}
```

## Под капотом

Внутри Redis структура `quicklist` объединяет двусвязный список с узлами из упакованных массивов `listpack`. Команда `LPUSH` добавляет элемент в начало, а `BRPOP` удаляет с конца за константное время O(1). Если очередь пуста, Redis регистрирует клиентский сокет в глобальной структуре `server.ready_keys` и не производит опрос сокета, переводя горутину в состояние сна без траты процессорных тактов.

## Подводные камни

Указывать `timeout = 0` при нестабильной сети. При `timeout = 0` соединение блокируется вечно. Промежуточные балансировщики и файрволы (AWS NAT Gateway, Envoy) через несколько минут молчания могут разорвать idle TCP-сессию без уведомления хостов (TCP Silent Drop). Всегда задавайте разумный таймаут (например 5–30 секунд) и перезапускайте цикл ожидания.

## На собеседовании

**Вопрос с собеседования:** «В чем главный недостаток очереди на `LPUSH/BRPOP` при сбое воркера?»
**Ответ:** Потеря сообщений (At-most-once delivery). Если воркер вычитал задачу через `BRPOP`, и в этот момент процесс упал (паника, авария сервера), задача уже удалена из Redis и навсегда утеряна. Для надежных очередей используется паттерн `RPOPLPUSH` / `LMOVE` (перемещение в список обработки `in_flight`) либо Redis Streams с Consumer Groups и подтверждением `XACK`.
