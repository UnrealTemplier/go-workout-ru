# Доказательство строгой атомарности Incr в 1000 горутинах

## Условие

Напиши функцию `CacheIncr(key string) (int64, error)`, использующую `rdb.Incr(ctx, key)`. Покажи атомарность: запусти 1000 горутин, каждая `Incr` — результат будет ровно 1000.

## Теория

Если бы мы увеличивали переменную в памяти Go без мьютекса или атомика (`counter++`), возникло бы состояние гонки (Race Condition), и итоговое значение оказалось бы значительно меньше 1000 из-за потерянных обновлений (Lost Updates).

В Redis все команды выполняются последовательно в едином потоке сервера. Даже если 1000 горутин в Go одновременно выстрелят сетевыми запросами `INCR`, Redis выстроит их в очередь буфера TCP-сокетов и выполнит строго последовательно. Итоговый счетчик гарантированно будет равен 1000.

## Решение по шагам

1. Очистите тестовый ключ.
2. Создайте `sync.WaitGroup` на 1000 элементов.
3. Запустите цикл из 1000 итераций, в каждой порождая горутину с вызовом `rdb.Incr(ctx, key)`.
4. Дождитесь завершения через `wg.Wait()`.
5. Проверьте итоговое значение через `rdb.Get(ctx, key)`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"

	"github.com/redis/go-redis/v9"
)

type CounterService struct {
	rdb *redis.Client
}

func (s *CounterService) CacheIncr(ctx context.Context, key string) (int64, error) {
	return s.rdb.Incr(ctx, key).Result()
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{
		Addr:     "localhost:6379",
		PoolSize: 50, // расширяем пул соединений для параллелизма
	})
	defer rdb.Close()

	svc := &CounterService{rdb: rdb}
	key := "test:atomic:counter"
	_ = rdb.Del(ctx, key).Err()

	const totalGoroutines = 1000
	var wg sync.WaitGroup
	wg.Add(totalGoroutines)

	for i := 0; i < totalGoroutines; i++ {
		go func() {
			defer wg.Done()
			_, err := svc.CacheIncr(ctx, key)
			if err != nil {
				log.Printf("ошибка инкремента: %v", err)
			}
		}()
	}

	wg.Wait()

	finalVal, err := rdb.Get(ctx, key).Int64()
	if err != nil {
		log.Fatalf("ошибка чтения: %v", err)
	}

	fmt.Printf("Ожидалось: %d, Реальное значение в Redis: %d\n", totalGoroutines, finalVal)
	if finalVal == totalGoroutines {
		fmt.Println("✅ Атомарность Redis доказана: 0 потерянных инкрементов!")
	}
}
```

ℹ️ Конкурентный стресс-тест атомарности Incr

**`Терминал`**

```bash
go run main.go
# Вывод:
# Ожидалось: 1000, Реальное значение в Redis: 1000
# ✅ Атомарность Redis доказана: 0 потерянных инкрементов!
```

## Под капотом

Сетевой мультиплексор Redis (на базе системного вызова `epoll_wait` в Linux) принимает сетевые пакеты от сокетов пула Go-клиента. Даже если операционная система считывает байты параллельно с помощью I/O threads (введенных в Redis 6), само выполнение команды `incrCommand` и модификация памяти происходят строго синхронно в центральном потоке Redis. Поэтому взаимная блокировка или гонка данных физически невозможна.

## Подводные камни

Маленький размер пула соединений (`PoolSize`). По умолчанию пул равен `10 * runtime.GOMAXPROCS`. При запуске 1000 горутин они будут конкурировать за взятие сокета из пула, создавая задержки ожидания (`PoolTimeout`).

## На собеседовании

**Вопрос с собеседования:** «Что быстрее при параллельном инкременте счетчика: atomic в памяти одного Go-процесса или Redis Incr?»
**Ответ:** `atomic.AddInt64` в Go работает за ~2-5 наносекунд на процессоре (инструкция `LOCK XADD` на кэш-линиях L1/L2). Запрос `rdb.Incr` в Redis требует сериализации, системных вызовов сокетов и сетевой передачи, занимая от 200 микросекунд до 1 миллисекунды (в 100 000 раз медленнее). Redis выбирают не ради скорости локального инкремента, а ради синхронизации общего состояния между десятками распределенных серверов.
