# Pub/Sub: непрерывный подписчик на канал news и издатель сообщений

## Условие

**[Pub/Sub]**: Напиши две программы (или две горутины). Первая подписывается на канал `client.Subscribe(ctx, "news")` и читает сообщения в бесконечном цикле. Вторая публикует сообщение `client.Publish(ctx, "news", "Hello")`.

## Теория

Паттерн Pub/Sub позволяет реализовать мгновенную шину уведомлений (Event Bus) между различными микросервисами в архитектуре бэкенда.

## Решение по шагам

1. Запустите первую горутину с `Subscribe(ctx, "news")`.
2. Читайте сообщения в цикле `for msg := range pubsub.Channel()`.
3. Запустите вторую горутину с `Publish(ctx, "news", "Hello")`.
4. Зафиксируйте прием сообщения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	topic := "news"
	var wg sync.WaitGroup
	wg.Add(1)

	// 1. Горутина-подписчик
	go func() {
		pubsub := rdb.Subscribe(ctx, topic)
		defer pubsub.Close()

		// Подтверждение подписки
		_, err := pubsub.Receive(ctx)
		if err != nil {
			log.Fatalf("Receive failed: %v", err)
		}
		wg.Done()

		ch := pubsub.Channel()
		for msg := range ch {
			fmt.Printf("📬 [Подписчик] Получена новость: %s\n", msg.Payload)
			if msg.Payload == "stop" {
				break
			}
		}
	}()

	wg.Wait()
	time.Sleep(100 * time.Millisecond)

	// 2. Горутина-издатель
	fmt.Println("🚀 [Издатель] Публикуем 'Hello'...")
	_ = rdb.Publish(ctx, topic, "Hello").Err()
	time.Sleep(100 * time.Millisecond)

	_ = rdb.Publish(ctx, topic, "stop").Err()
	time.Sleep(100 * time.Millisecond)
}
```

ℹ️ Синхронизация горутин через канал Pub/Sub

**`Терминал`**

```bash
go run main.go
# Вывод:
# 🚀 [Издатель] Публикуем 'Hello'...
# 📬 [Подписчик] Получена новость: Hello
# 📬 [Подписчик] Получена новость: stop
```

## Под капотом

Подписчик слушает TCP сокет в режиме блокирующего чтения. Когда издатель отправляет `PUBLISH`, сервер Redis немедленно записывает RESP-фрейм `message\r\nnews\r\nHello\r\n` в сокет каждого подписчика без сохранения в дисковый буфер.

## Подводные камни

Ожидать повторной доставки при разрыве TCP соединения. Если подписчик отключился на 1 секунду, все отправленные в эту секунду новости безвозвратно теряются.

## На собеседовании

**Вопрос с собеседования:** «Какова задержка доставки сообщения в Redis Pub/Sub?»
**Ответ:** Задержка составляет менее 1 миллисекунды (субмиллисекундная доставка в пределах локальной сети ЦОД), так как сообщение передается по уже открытым готовым TCP-сокетам без дискового I/O.
