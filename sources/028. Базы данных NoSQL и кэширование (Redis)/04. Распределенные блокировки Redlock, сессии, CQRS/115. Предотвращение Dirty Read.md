# Предотвращение Dirty Read: атомарное обновление в БД и синхронная инвалидация в Redis

## Условие

**Инвалидация кэша**: Напишите функцию обновления баланса пользователя в PostgreSQL. Чтобы избежать ситуации "грязного чтения" (когда в базе данных баланс уже обновился, а в кэше Redis висит старое значение), добавьте в функцию обязательное удаление соответствующего ключа из Redis (`client.Del`) в рамках одной логической операции обновления данных.

## Теория

Проблема **Грязного чтения (Dirty/Stale Read)**:
Если баланс пользователя обновлен в PostgreSQL, но старое значение осталось в Redis, последующий запрос на снятие средств проверит устаревший кэш и допустит овердрафт!
Эталонная логика:
1. Выполняем `UPDATE users SET balance = balance + $1 WHERE id = $2` в PostgreSQL.
2. В той же функции СИНХРОННО вызываем `rdb.Del(ctx, cacheKey)`.
3. Если удаление из Redis упало, транзакция фиксируется, но ошибка логируется на мониторинг.

## Решение по шагам

1. Создайте структуру `UserBalanceService`.
2. Реализуйте метод `UpdateBalance(ctx, userID, delta)`.
3. Убедитесь в синхронном вызове `rdb.Del`.
4. Проверьте отсутствие старого значения в кэше.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/redis/go-redis/v9"
)

type UserBalanceService struct {
	rdb *redis.Client
}

func (s *UserBalanceService) UpdateBalance(ctx context.Context, userID int64, delta float64) error {
	cacheKey := fmt.Sprintf("user:balance:%d", userID)

	// 1. Обновляем баланс в PostgreSQL (UPDATE accounts SET balance = balance + delta ...)
	fmt.Printf("[PostgreSQL] UPDATE accounts SET balance = balance + %.2f WHERE user_id = %d\n", delta, userID)

	// 2. Инвалидируем ключ в кэше для исключения грязного чтения
	deleted, err := s.rdb.Del(ctx, cacheKey).Result()
	if err != nil {
		// Логируем предупреждение с высоким приоритетом
		return fmt.Errorf("ошибка инвалидации кэша: %w", err)
	}

	fmt.Printf("[Redis] Кэш баланса пользователя %d успешно удален (удалено ключей: %d)\n", userID, deleted)
	return nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	svc := &UserBalanceService{rdb: rdb}
	userID := int64(902)
	key := fmt.Sprintf("user:balance:%d", userID)

	// До обновления в кэше лежит старый баланс 1000 руб.
	_ = rdb.Set(ctx, key, "1000.00", 0).Err()
	oldBal, _ := rdb.Get(ctx, key).Result()
	fmt.Printf("До операции в кэше: %s руб.\n", oldBal)

	// Выполняем пополнение на 500 руб. с инвалидацией
	if err := svc.UpdateBalance(ctx, userID, 500.00); err != nil {
		log.Fatalf("Update failed: %v", err)
	}

	// Проверяем, что кэш гарантированно пуст
	exists, _ := rdb.Exists(ctx, key).Result()
	fmt.Printf("Ключ в кэше после инвалидации: %d (0 = отсутствует, грязное чтение исключено!)\n", exists)
}
```

ℹ️ Синхронная инвалидация кэша для предотвращения грязного чтения

**`Терминал`**

```bash
go run main.go
# Вывод:
# До операции в кэше: 1000.00 руб.
# [PostgreSQL] UPDATE accounts SET balance = balance + 500.00 WHERE user_id = 902
# [Redis] Кэш баланса пользователя 902 успешно удален (удалено ключей: 1)
# Ключ в кэше после инвалидации: 0 (0 = отсутствует, грязное чтение исключено!)
```

## Под капотом

Вызов `DEL` удаляет ключ немедленно, так что любой следующий запрос от микросервисов неизбежно пойдет в PostgreSQL и считает свежее актуальное значение баланса.

## Подводные камни

Делать `SET cacheKey newBalance` вместо `DEL`. Если между UPDATE в БД и записью в кэш пройдет миллисекунда, параллельный поток может перетереть кэш старым значением. Удаление (`DEL`) всегда безопаснее обновления!

## На собеседовании

**Вопрос с собеседования:** «Почему в HighLoad финтехе удаление ключа из кэша предпочтительнее его обновления при изменении данных?»
**Ответ:** 1. **Защита от состояния гонки (Race Condition):** два одновременных `UPDATE` могут записать в кэш данные в обратном порядке. 2. **Экономия ресурсов (Lazy Evaluation):** не тратится время на повторный расчет и сериализацию данных, которые могут больше не понадобиться. 3. **Простота восстановления:** удаленный ключ гарантированно приводит к штатному чтению истины из PostgreSQL.
