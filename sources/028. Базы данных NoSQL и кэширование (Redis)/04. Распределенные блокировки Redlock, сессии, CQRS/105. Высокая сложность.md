# Высокая сложность: конкурентная борьба за распределенный лок SETNX с PX

## Условие

**[Высокая сложность — Распределенная блокировка (Distributed Lock)]**: Реализуй безопасную блокировку с помощью `SET lock_key 1 NX PX 10000` (Set if Not eXists, с истечением 10с). Запусти две горутины, пытающиеся захватить блокировку. Вторая должна ждать или получать ошибку. (Дополнительно: изучи библиотеку Redsync для корректной реализации алгоритма Redlock).

## Теория

Команда `SET key token NX PX milliseconds` выполняет атомарный захват блокировки за один такт процессора Redis:
- `NX`: операция выполнится только если ключ не существует.
- `PX 10000`: таймаут в 10 000 миллисекунд (10 секунд).
Если две горутины одновременно вызывают этот метод, Redis гарантирует, что ровно одна получит ответ `OK`, а вторая вернет ошибку `redis.Nil` (захват не удался).

## Решение по шагам

1. Запустите две параллельные горутины (Воркер 1 и Воркер 2).
2. Обе пытаются захватить ключ `lock_key` через `SetNX`.
3. Победивший воркер выполняет работу и снимает блокировку через Lua.
4. Проигравший воркер корректно обрабатывает отказ.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"

	"github.com/google/uuid"
	"github.com/redis/go-redis/v9"
)

const safeReleaseScript = `
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end`

func tryAcquireAndRun(ctx context.Context, rdb *redis.Client, workerName, lockKey string, wg *sync.WaitGroup) {
	defer wg.Done()

	token := uuid.New().String()
	ttl := 10 * time.Second

	// SET lock_key token NX PX 10000
	ok, err := rdb.SetArgs(ctx, lockKey, token, redis.SetArgs{
		Mode: "NX",
		TTL:  ttl,
	}).Result()

	if err != nil || ok != "OK" {
		fmt.Printf("❌ [%s] Не удалось захватить блокировку: ресурс занят другим воркером!\n", workerName)
		return
	}

	fmt.Printf("🔒 [%s] УСПЕШНО захватил блокировку (токен: %s). Выполняем работу...\n", workerName, token[:8])
	time.Sleep(300 * time.Millisecond)

	// Освобождаем
	_, _ = rdb.Eval(ctx, safeReleaseScript, []string{lockKey}, token).Result()
	fmt.Printf("🔓 [%s] Работа завершена, блокировка освобождена.\n", workerName)
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	lockKey := "lock:critical_export_job"
	_ = rdb.Del(ctx, lockKey).Err()

	var wg sync.WaitGroup
	wg.Add(2)

	// Запускаем две горутины в конкурентную борьбу за один ключ
	go tryAcquireAndRun(ctx, rdb, "Воркер_А", lockKey, &wg)
	go tryAcquireAndRun(ctx, rdb, "Воркер_Б", lockKey, &wg)

	wg.Wait()
}
```

ℹ️ Конкуренция двух горутин за SetNX распределенный замок

**`Терминал`**

```bash
go run main.go
# Вывод:

# ❌ [Воркер_Б] Не удалось захватить блокировку: ресурс занят другим воркером!

```

## Под капотом

Флаг `NX` проверяется в `setGenericCommand()`. Если ключ уже существует, Redis возвращает `NULL` bulk string, который `go-redis` транслирует в ошибку `redis.Nil` или `ok != "OK"`, гарантируя взаимное исключение.

## Подводные камни

Не использовать retry-цикл, если проигравшему воркеру обязательно нужно дождаться освобождения ресурса. Для ожидания используют `time.Sleep` с экспоненциальным бэкоффом или Pub/Sub оповещение об освобождении.

## На собеседовании

**Вопрос с собеседования:** «Как библиотека Redsync реализует продление блокировки во время работы?»
**Ответ:** Redsync запускает фоновую горутину с таймером (watchdog), которая периодически выполняет Lua-скрипт `pexpire` на всех узлах кворума, проверяя валидность UUID токена до тех пор, пока контекст критической секции активен.
