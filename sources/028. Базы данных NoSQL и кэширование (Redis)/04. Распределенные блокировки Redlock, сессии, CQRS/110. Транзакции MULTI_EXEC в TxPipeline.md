# Транзакции MULTI/EXEC в TxPipeline и симуляция отката через Lua

## Условие

**[Транзакции в Redis (MULTI/EXEC)]**: Используй `client.TxPipeline`. В одной транзакции инкрементируй счетчик и добавь элемент в список. Если инкремент пройдет, а добавление в список упадет — откатись.

## Теория

Поскольку нативный `MULTI/EXEC` в Redis не поддерживает откат (No Rollback), для сценариев, требующих строгого отката при несоблюдении условий, в Go-разработке применяют два подхода:
1. **Эмуляция отката на Go:** проверка результатов `cmds` после `Exec()` и выполнение компенсирующих действий (`DECR` при ошибке).
2. **Атомарный Lua-скрипт:** проверка условий на стороне сервера и откат через прерывание скрипта (`error()`).

## Решение по шагам

1. Создайте `TxPipeline` с двумя командами.
2. Проверьте результат выполнения.
3. При ошибке одного из шагов выполните компенсирующую операцию (Rollback).

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/redis/go-redis/v9"
)

func executeWithRollback(ctx context.Context, rdb *redis.Client) {
	counterKey := "tx:demo:counter"
	listKey := "tx:demo:bad_list"

	_ = rdb.Set(ctx, counterKey, 100, 0).Err()
	// Намеренно делаем listKey строкой, чтобы RPush гарантированно упал!
	_ = rdb.Set(ctx, listKey, "i_am_string_not_list", 0).Err()

	// 1. Выполняем TxPipeline
	pipe := rdb.TxPipeline()
	incrCmd := pipe.Incr(ctx, counterKey)
	rpushCmd := pipe.RPush(ctx, listKey, "item1")

	_, execErr := pipe.Exec(ctx)
	fmt.Printf("Ошибка TxPipeline: %v\n", execErr)

	// 2. Анализируем и выполняем компенсирующее действие (Rollback)
	if rpushCmd.Err() != nil {
		fmt.Printf("RPush завершился с ошибкой: %v\n", rpushCmd.Err())
		if incrCmd.Err() == nil {
			fmt.Println("⚠️ Инкремент прошел, но список упал. Выполняем Rollback (DECR)...")
			_ = rdb.Decr(ctx, counterKey).Err()
		}
	}

	// 3. Проверяем итоговый баланс
	finalVal, _ := rdb.Get(ctx, counterKey).Int64()
	fmt.Printf("Итоговое значение счетчика после отката: %d (вернулось к исходным 100!)\n", finalVal)
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	executeWithRollback(ctx, rdb)
}
```

ℹ️ Компенсирующий откат (Saga pattern) при сбое транзакции Redis

**`Терминал`**

```bash
go run main.go
# Вывод:
# Ошибка TxPipeline: WRONGTYPE Operation against a key holding the wrong kind of value
# RPush завершился с ошибкой: WRONGTYPE Operation against a key holding the wrong kind of value
# ⚠️ Инкремент прошел, но список упал. Выполняем Rollback (DECR)...
# Итоговое значение счетчика после отката: 100 (вернулось к исходным 100!)
```

## Под капотом

Этот паттерн компенсирующих транзакций (Compensating Transactions / Saga) широко используется в микросервисах, где распределенные транзакции невозможны.

## Подводные камни

Полагаться на ручной откат при падении самого инстанса Go. Для абсолютной атомарности пишите Lua-скрипт.

## На собеседовании

**Вопрос с собеседования:** «Почему в Redis нет команды `ROLLBACK`?»
**Ответ:** Потому что транзакции в Redis спроектированы для быстрой пакетной изоляции команд в памяти, а не для сложных ACID-гарантий со снимками состояния (Undo Log). Отсутствие Undo Log экономит колоссальный объем оперативной памяти.
