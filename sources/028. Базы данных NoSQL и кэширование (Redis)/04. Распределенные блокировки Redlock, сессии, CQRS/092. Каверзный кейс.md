# Каверзный кейс: анализ задержки RTT при записи 1000 ключей через Pipeline

## Условие

**[Каверзный кейс — Пайплайны]**: Запиши 1000 ключей в Redis. Сначала сделай это в цикле 1000 раз через `client.Set`. Затем сделай то же самое через `client.Pipeline` (одним сетевым запросом). Измерь время выполнения `time.Since()` и оцени разницу.

## Теория

Почему Pipeline ускоряет работу в десятки раз?
В последовательном коде поток Go блокируется на ожидании чтения ответа сокета (`syscall.Read`). Ядро Linux переводит горутину в состояние ожидания, что порождает переключения контекста GMP-планировщика. В Pipeline все 1000 команд формируются в один сетевой буфер и отправляются за один вызов `write`.

## Решение по шагам

1. Замерьте суммарное время 1000 вызовов `client.Set`.
2. Замерьте суммарное время `client.Pipeline`.
3. Рассчитайте метрику Round-Trip Latency.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	const N = 1000

	// Способ А: Последовательно
	t0 := time.Now()
	for i := 0; i < N; i++ {
		_ = rdb.Set(ctx, fmt.Sprintf("bench:seq:%d", i), i, 0).Err()
	}
	seqTime := time.Since(t0)

	// Способ Б: Pipeline
	t1 := time.Now()
	pipe := rdb.Pipeline()
	for i := 0; i < N; i++ {
		pipe.Set(ctx, fmt.Sprintf("bench:pipe:%d", i), i, 0)
	}
	_, _ = pipe.Exec(ctx)
	pipeTime := time.Since(t1)

	fmt.Printf("Последовательно: %v (среднее %.3f ms на операцию)\n",
		seqTime, float64(seqTime.Milliseconds())/float64(N))
	fmt.Printf("Pipeline:        %v (среднее %.3f ms на батч)\n",
		pipeTime, float64(pipeTime.Milliseconds()))
	fmt.Printf("Итоговый прирост производительности: %.1fx\n", float64(seqTime)/float64(pipeTime))
}
```

ℹ️ Сравнение затрат RTT между последовательным выполнением и Pipeline

**`Терминал`**

```bash
go run main.go
# Вывод:
# Последовательно: 71.2ms (среднее 0.071 ms на операцию)
# Pipeline:        3.4ms (среднее 3.000 ms на батч)
# Итоговый прирост производительности: 20.9x
```

## Под капотом

Разница во времени обусловлена не сложностью вычислений на CPU сервера Redis (Redis выполняет `SET` за десятки наносекунд), а физической задержкой сетевого стека операционной системы (TCP ACK, sliding window, context switches).

## Подводные камни

Использовать Pipeline для бесконечно большого числа команд. Если команд больше 10 000, нарезайте их на батчи по 1000 штук.

## На собеседовании

**Вопрос с собеседования:** «Каковы накладные расходы по оперативной памяти у Redis при выполнении огромного Pipeline на 100 000 команд?»
**Ответ:** Redis обязан сформировать и держать в оперативной памяти ответы на все 100 000 команд в клиентском буфере вывода (`client-output-buffer-limit`). Это может вызвать резкий скачок потребления RAM и даже принудительное отключение клиента по превышению лимита буфера.
