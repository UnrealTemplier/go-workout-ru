# Финализация Cache-Aside: корректный возврат результата клиенту

## Условие

Возвращаем результат.

## Теория

Завершающая фаза любого метода получения кэшированных сущностей: возврат десериализованного типизированного объекта клиенту с гарантией, что ошибки записи в кэш не влияют на успешность ответа.

## Решение по шагам

1. Получите результат из источника.
2. Проверьте валидность.
3. Верните результат и `nil` ошибку.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/redis/go-redis/v9"
)

type CatalogItem struct {
	SKU   string
	Price float64
}

func fetchCatalogItem(ctx context.Context, rdb *redis.Client, sku string) (*CatalogItem, error) {
	// Если в кэше пусто — загрузили из источника и безопасно возвращаем клиенту
	item := &CatalogItem{SKU: sku, Price: 1990.00}
	return item, nil
}

func main() {
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	defer rdb.Close()

	item, err := fetchCatalogItem(ctx, rdb, "SKU-909")
	if err != nil {
		fmt.Printf("Ошибка: %v\n", err)
		return
	}

	fmt.Printf("Результат успешно возвращен клиенту: SKU=%s, Цена=%.2f руб.\n", item.SKU, item.Price)
}
```

ℹ️ Корректный возврат результата из сервисного слоя

**`Терминал`**

```bash
go run main.go
# Вывод: Результат успешно возвращен клиенту: SKU=SKU-909, Цена=1990.00 руб.
```

## Под капотом

В языке Go идиоматично возвращать `(*Type, error)`: при успехе возвращается заполненный указатель и `nil`, при ошибке — `nil` и экземпляр ошибки.

## Подводные камни

Возвращать непустой указатель на пустую структуру при ошибке.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go принято возвращать ошибку последним аргументом функции?»
**Ответ:** Это стандарт соглашения об именовании в Go (Go Convention). Это позволяет проверять `if err != nil` единообразно по всему кодовому базису.
