# Мокирование транзакций в sqlmock: цепочка ExpectBegin, ExpectExec и ExpectCommit

## Условие

Напиши тест с **sqlmock для transaction**: `mock.ExpectBegin()`, `mock.ExpectExec(...)`, `mock.ExpectCommit()`. Проверь, что функция начинает и коммитит транзакцию.

## Теория

Атомарные бизнес-операции требуют транзакций (ACID):
Например, перевод денег между счетами: списание со счета А и зачисление на счет Б.
В `sqlmock` транзакция моделируется строгой последовательностью:
1. `mock.ExpectBegin()`
2. `mock.ExpectExec("UPDATE accounts SET balance ...").WithArgs(...)`
3. `mock.ExpectExec("UPDATE accounts SET balance ...").WithArgs(...)`
4. `mock.ExpectCommit()`
Если на шаге 2 или 3 произошла ошибка, вызывается `mock.ExpectRollback()`.

## Решение по шагам

1. Напишите функцию перевода средств `TransferFunds`.
2. Задайте ожидания `ExpectBegin -> ExpectExec -> ExpectExec -> ExpectCommit`.
3. Вызовите функцию.
4. Проверьте `ExpectationsWereMet()`.

## Код решения

**`transfer.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
)

func TransferFunds(ctx context.Context, db *sql.DB, fromID, toID int, amount float64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin tx: %w", err)
	}
	defer tx.Rollback() // Безопасный откат при панике или ошибке

	// Списание
	_, err = tx.ExecContext(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID)
	if err != nil {
		return fmt.Errorf("debit failed: %w", err)
	}

	// Зачисление
	_, err = tx.ExecContext(ctx, "UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID)
	if err != nil {
		return fmt.Errorf("credit failed: %w", err)
	}

	if err := tx.Commit(); err != nil {
		return fmt.Errorf("commit failed: %w", err)
	}
	return nil
}
```

ℹ️ Транзакционный перевод денег

**`transfer_test.go`**

```go
package main

import (
	"context"
	"testing"

	"github.com/DATA-DOG/go-sqlmock"
)

func TestTransferFunds_SuccessTransaction(t *testing.T) {
	db, mock, err := sqlmock.New()
	if err != nil {
		t.Fatalf("sqlmock error: %v", err)
	}
	defer db.Close()

	ctx := context.Background()

	// 1. Ожидаем начало транзакции
	mock.ExpectBegin()

	// 2. Первое списание
	mock.ExpectExec(`UPDATE accounts SET balance = balance - \$1 WHERE id = \$2`).
		WithArgs(500.0, 101).
		WillReturnResult(sqlmock.NewResult(0, 1))

	// 3. Второе зачисление
	mock.ExpectExec(`UPDATE accounts SET balance = balance \+ \$1 WHERE id = \$2`).
		WithArgs(500.0, 102).
		WillReturnResult(sqlmock.NewResult(0, 1))

	// 4. Фиксация транзакции
	mock.ExpectCommit()

	err = TransferFunds(ctx, db, 101, 102, 500.0)
	if err != nil {
		t.Fatalf("TransferFunds failed: %v", err)
	}

	if err := mock.ExpectationsWereMet(); err != nil {
		t.Errorf("Нарушены ожидания sqlmock: %v", err)
	}
}
```

## Под капотом

Вызов `defer tx.Rollback()` после успешного `tx.Commit()` возвращает стандартную безопасную ошибку `sql.ErrTxDone`, которую рантайм `database/sql` молча игнорирует, предотвращая двойной откат.

## Подводные камни

Забывать экранировать знак плюса `\+` в SQL regex-шаблоне: в регулярных выражениях `+` означает квантификатор «1 и более повторений», что вызовет синтаксическую ошибку парсера regex!

## На собеседовании

**Вопрос с собеседования:** «Как протестировать в sqlmock сценарий отката транзакции при сбое на втором шаге?»
**Ответ:** Настроить второе выражение с `WillReturnError(errors.New("db lock error"))` и заменить последующий `ExpectCommit()` на `ExpectRollback()`. Убедиться, что `TransferFunds` вернула ошибку, а транзакция была корректно откачена.
