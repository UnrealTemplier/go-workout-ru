# Архитектурный фундамент тестируемости: сокрытие внешних зависимостей за интерфейсами

## Условие

Спроектируйте код так, чтобы все внешние зависимости (БД, API, файловая система) были скрыты за интерфейсами. Это фундамент тестируемости в Go.

## Теория

Принцип слабой связанности (Loose Coupling) и чистая архитектура в Go:
- Бизнес-логика (Use Case / Domain) должна быть чистой и не содержать прямых импортов драйверов баз данных (`github.com/lib/pq`), SDK облачных хранилищ (`aws-sdk-go`) или HTTP клиентов.
- Все внешние операции объявляются интерфейсами в пакете домена:
  - `UserStorage` — хранилище пользователей.
  - `FileStorage` — файловое хранилище (S3/локальный диск).
  - `Notifier` — транспорт отправки сообщений.
- Это делает систему на 100% тестируемой модульными тестами с нулевым временем выполнения.

## Решение по шагам

1. Объявите интерфейсы `DataStorage` и `FileStorage`.
2. Реализуйте сервис экспорта отчетов, зависящий только от интерфейсов.
3. Протестируйте сервис со стабами в RAM без реального диска и БД.

## Код решения

**`export_service.go`**

```go
package main

import (
	"context"
	"fmt"
)

type DataStorage interface {
	GetSummaryData(ctx context.Context) (string, error)
}

type FileStorage interface {
	SaveFile(ctx context.Context, filename string, data []byte) error
}

type ReportExportService struct {
	db DataStorage
	fs FileStorage
}

func NewReportExportService(db DataStorage, fs FileStorage) *ReportExportService {
	return &ReportExportService{db: db, fs: fs}
}

func (s *ReportExportService) ExportMonthlyReport(ctx context.Context, month string) error {
	summary, err := s.db.GetSummaryData(ctx)
	if err != nil {
		return fmt.Errorf("сбой получения данных: %w", err)
	}

	reportContent := []byte(fmt.Sprintf("Отчет за %s: %s", month, summary))
	filename := fmt.Sprintf("report_%s.txt", month)

	return s.fs.SaveFile(ctx, filename, reportContent)
}
```

ℹ️ Сервис с изоляцией БД и файловой системы через интерфейсы

**`export_service_test.go`**

```go
package main

import (
	"context"
	"testing"
)

type MemoryDataStorage struct{}

func (MemoryDataStorage) GetSummaryData(ctx context.Context) (string, error) {
	return "Выручка 1.5M", nil
}

type MemoryFileStorage struct {
	SavedName string
	SavedBody string
}

func (m *MemoryFileStorage) SaveFile(ctx context.Context, filename string, data []byte) error {
	m.SavedName = filename
	m.SavedBody = string(data)
	return nil
}

func TestReportExportServiceIsolated(t *testing.T) {
	dbMock := MemoryDataStorage{}
	fsMock := &MemoryFileStorage{}
	svc := NewReportExportService(dbMock, fsMock)

	err := svc.ExportMonthlyReport(context.Background(), "September")
	if err != nil {
		t.Fatalf("ExportMonthlyReport failed: %v", err)
	}

	if fsMock.SavedName != "report_September.txt" {
		t.Errorf("SavedName = %q; want report_September.txt", fsMock.SavedName)
	}
	expectedContent := "Отчет за September: Выручка 1.5M"
	if fsMock.SavedBody != expectedContent {
		t.Errorf("SavedBody = %q; want %q", fsMock.SavedBody, expectedContent)
	}
}
```

## Под капотом

Благодаря утиной типизации Go (Duck Typing), сервису безразлично, сохраняется ли файл на локальный SSD, в Amazon S3 или в память тестовой структуры: сигнатура метода `SaveFile` идентична.

## Подводные камни

Создавать гигантские «божественные» интерфейсы с десятками методов (Interface Segregation Principle violation). Делайте интерфейсы узкими (1–3 метода).

## На собеседовании

**Вопрос с собеседования:** «Что гласит поговорка Роба Пайка о размере интерфейсов в Go?»
**Ответ:** «The bigger the interface, the weaker the abstraction» («Чем больше интерфейс, тем слабее абстракция»). Маленькие интерфейсы вроде `io.Reader` (1 метод) обладают максимальной мощью и универсальностью переиспользования.
