# Автоматическая накатка миграций: пакет golang-migrate в SetupSuite

## Условие

Примените миграции к testcontainer-БД через `golang-migrate` в `SetupSuite`.

## Теория

Синхронизация схемы базы данных в тестах через `golang-migrate`:
- В продакшене структура БД версионируется SQL-файлами (`001_init.up.sql`, `002_add_orders.up.sql`).
- Тесты ОБЯЗАНЫ накатывать ровно те же самые файлы миграций, что и в продакшене.
- Библиотека `github.com/golang-migrate/migrate/v4`:
  1. Читает SQL миграции из папки `file://migrations` или через `io/fs` (драйвер `iofs`).
  2. Подключается к тестовой БД: `postgres.WithInstance(db, &postgres.Config{})`.
  3. Вызывает `m.Up()`, гарантируя 100% идентичность схемы продакшену.

## Решение по шагам

1. Создайте экземпляр драйвера базы данных.
2. Создайте объект `migrate.NewWithSourceInstance(...)`.
3. Вызовите `m.Up()` в `SetupSuite`.
4. Проверьте отсутствие ошибок накатки миграций.

## Под капотом

`golang-migrate` создает служебную таблицу `schema_migrations`, где отслеживает текущую версию и флаг `dirty`. Если миграция упала посередине, статус помечается как dirty, блокируя дальнейшие операции.

## Подводные камни

Поддерживать две независимые схемы: одну в файлах миграций для продакшена, а другую хардкодить в `setup.sql` тестов. Рассинхронизация полей неизбежна! Всегда используйте единый источник истины — файлы миграций.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если тест упал и база осталась в состоянии dirty state?»
**Ответ:** Вызывать `m.Force(version)` для сброса флага dirty, либо при использовании временных контейнеров Testcontainers просто уничтожить контейнер целиком (`container.Terminate`) — следующий запуск поднимет свежую чистую базу.
