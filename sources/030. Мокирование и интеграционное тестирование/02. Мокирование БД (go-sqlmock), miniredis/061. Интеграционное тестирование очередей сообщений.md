# Интеграционное тестирование очередей сообщений: таймаут-селекторы и каналы

## Условие

Напиши **интеграционный тест** для **message queue** (Redis Stream или NATS): публикуй сообщение, подписывайся, проверь доставку. Используй таймаут для ожидания сообщения.

### Исходная формулировка

---

## Теория

Тестирование асинхронных брокеров сообщений (Message Brokers):
- Публикация и подписка происходят асинхронно в разных горутинах.
- Если брокер не доставит сообщение из-за бага маршрутизации, горутина теста зависнет навсегда.
- **Золотое правило:** ожидание сообщения из канала брокера ОБЯЗАНО оборачиваться в конструкцию `select` с таймаутом `time.After(5 * time.Second)`.

## Решение по шагам

1. Создайте структуру брокера сообщений на каналах Go (или Redis Streams).
2. Оформите подписку на тему.
3. Опубликуйте сообщение.
4. Проверьте получение сообщения с таймаутом.

## Код решения

**`mq_broker.go`**

```go
package main

import (
	"sync"
)

type EventBus struct {
	mu          sync.RWMutex
	subscribers map[string][]chan string
}

func NewEventBus() *EventBus {
	return &EventBus{subscribers: make(map[string][]chan string)}
}

func (b *EventBus) Subscribe(topic string) <-chan string {
	b.mu.Lock()
	defer b.mu.Unlock()

	ch := make(chan string, 10)
	b.subscribers[topic] = append(b.subscribers[topic], ch)
	return ch
}

func (b *EventBus) Publish(topic, message string) {
	b.mu.RLock()
	defer b.mu.RUnlock()

	for _, ch := range b.subscribers[topic] {
		select {
		case ch <- message:
		default:
		}
	}
}
```

ℹ️ Потокобезопасный брокер сообщений

**`mq_broker_test.go`**

```go
package main

import (
	"testing"
	"time"
)

func TestEventBusPublishSubscribeWithTimeout(t *testing.T) {
	bus := NewEventBus()
	topic := "orders.created"

	// 1. Подписываемся на события
	msgChan := bus.Subscribe(topic)

	// 2. Публикуем событие
	expectedEvent := `{"order_id":888,"status":"NEW"}`
	bus.Publish(topic, expectedEvent)

	// 3. Ожидание с защитой от зависания через time.After
	select {
	case received := <-msgChan:
		if received != expectedEvent {
			t.Errorf("Получено %s; want %s", received, expectedEvent)
		}
	case <-time.After(500 * time.Millisecond):
		t.Fatal("Таймаут! Сообщение не было доставлено брокером за 500 мс")
	}
}
```

## Под капотом

Использование буферизированных каналов в `Subscribe` предотвращает блокировку метода `Publish`, если подписчик не успел встать на чтение до публикации сообщения.

## Подводные камни

Ждать сообщение простым `msg := <-ch` без таймаута: если брокер уронит сообщение, весь прогон тестов в CI зависнет до глобального таймаута джоба (10–30 минут).

## На собеседовании

**Вопрос с собеседования:** «Как протестировать гарантию At-Least-Once доставки сообщений в Kafka consumer?»
**Ответ:** Моделируют падение воркера (Panic) до вызова Commit Offset. Убеждаются, что после перезапуска консьюмер считывает это же сообщение повторно, а идемпотентный обработчик не дублирует записи в базе данных.
