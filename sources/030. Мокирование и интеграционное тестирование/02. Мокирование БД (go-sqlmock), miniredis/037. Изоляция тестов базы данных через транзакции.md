# Изоляция тестов базы данных через транзакции: автоматический откат defer tx.Rollback

## Условие

Используйте транзакции для изоляции тестов: каждый тест запускается в своей транзакции и откатывается, чтобы не влиять на другие.

## Теория

Паттерн Transactional Test Isolation:
- Проблема: если интеграционные тесты сохраняют записи в общую базу данных, тесты загрязняют данные друг друга, а повторный запуск падает из-за конфликта уникальных ключей (Unique Violation).
- **Решение:**
  1. Тест открывает транзакцию `tx, err := db.BeginTx(ctx, nil)`.
  2. В конце теста регистрируется автоматический откат `t.Cleanup(func() { _ = tx.Rollback() })`.
  3. Репозиторий выполняет все операции внутри `tx`.
  4. По завершении теста база данных возвращается в исходное кристально чистое состояние!

## Решение по шагам

1. Создайте интерфейс `DBTX` (абстракция над `*sql.DB` и `*sql.Tx`).
2. Напишите репозиторий, принимающий `DBTX`.
3. В тесте откройте транзакцию и зарегистрируйте `defer tx.Rollback()`.
4. Убедитесь в отсутствии мусора в базе после теста.

## Код решения

**`tx_repo.go`**

```go
package main

import (
	"context"
	"database/sql"
)

// DBTX — общий интерфейс для *sql.DB и *sql.Tx
type DBTX interface {
	ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
	QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
}

type ArticleRepo struct {
	db DBTX
}

func NewArticleRepo(db DBTX) *ArticleRepo {
	return &ArticleRepo{db: db}
}

func (r *ArticleRepo) CreateArticle(ctx context.Context, id int, title string) error {
	_, err := r.db.ExecContext(ctx, "INSERT INTO articles (id, title) VALUES ($1, $2)", id, title)
	return err
}
```

ℹ️ Репозиторий, поддерживающий работу внутри транзакции

**`tx_repo_test.go`**

```go
package main

import (
	"context"
	"testing"

	"github.com/DATA-DOG/go-sqlmock"
)

func TestArticleRepoTransactionalRollback(t *testing.T) {
	db, mock, err := sqlmock.New()
	if err != nil {
		t.Fatalf("sqlmock error: %v", err)
	}
	defer db.Close()

	ctx := context.Background()

	// 1. Ожидаем начало транзакции
	mock.ExpectBegin()

	// 2. Ожидаем операцию вставки
	mock.ExpectExec("INSERT INTO articles").WithArgs(10, "Go 1.22 Concurrency").
		WillReturnResult(sqlmock.NewResult(1, 1))

	// 3. Ожидаем гарантированный откат транзакции
	mock.ExpectRollback()

	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		t.Fatalf("BeginTx failed: %v", err)
	}
	// ИЗОЛЯЦИЯ: транзакция никогда не коммитится в тестах!
	t.Cleanup(func() {
		_ = tx.Rollback()
		t.Log("Транзакция теста успешно откачена, база чиста")
	})

	repo := NewArticleRepo(tx)
	err = repo.CreateArticle(ctx, 10, "Go 1.22 Concurrency")
	if err != nil {
		t.Fatalf("CreateArticle failed: %v", err)
	}

	if err := mock.ExpectationsWereMet(); err != nil {
		t.Errorf("Нарушены ожидания sqlmock: %v", err)
	}
}
```

## Под капотом

Интерфейс `DBTX` — стандартная практика кодогенераторов (sqlc). Он позволяет выполнять методы как напрямую в общем пуле соединений `*sql.DB`, так и внутри конкретной атомарной транзакции `*sql.Tx` без изменения бизнес-кода.

## Подводные камни

Забыть объявить `defer tx.Rollback()` до выполнения операций: если `repo.CreateArticle` запаникует или завершится по `t.Fatal()`, транзакция останется висеть в пуле БД, блокируя таблицы локами (Deadlock).

## На собеседовании

**Вопрос с собеседования:** «В каких случаях паттерн отката транзакции (Rollback Pattern) неприменим для интеграционных тестов?»
**Ответ:** 1. Когда тестируемый метод сам управляет транзакциями (вызывает `tx.Commit()` внутри себя). Вложенные транзакции в большинстве SQL СУБД (PostgreSQL) не поддерживаются без Savepoints. 2. При тестировании асинхронных воркеров, читающих данные из других независимых соединений (Phantom Reads).
