# Тестирование обернутых ошибок: проверка проброса контекста из репозитория

## Условие

Проверьте с помощью мока, что при ошибке репозитория сервис возвращает обёрнутую ошибку.

## Теория

Стандарт надежности сервисного слоя:
- При падении слоя БД сервис не должен возвращать «голую» ошибку драйвера базы.
- Сервис обязан добавить доменный контекст через `fmt.Errorf("user service create failed: %w", err)`.
- Тест мокирует ошибку репозитория и проверяет:
  1. Что сервис вернул ошибку `err != nil`.
  2. Что исходная ошибка присутствует в цепочке через `errors.Is(err, dbErr)`.
  3. Что строка содержит понятный контекст сервиса.

## Решение по шагам

1. Создайте ошибку `var ErrDBUnavailable = errors.New("БД недоступна")`.
2. Настройте мок на возврат этой ошибки.
3. Проверьте результат сервиса через `errors.Is`.

## Код решения

**`err_service.go`**

```go
package main

import (
	"errors"
	"fmt"
)

var ErrDBUnavailable = errors.New("соединение с базой данных разорвано")

type OrderRepo interface {
	GetOrder(id int) (string, error)
}

type OrderService struct {
	repo OrderRepo
}

func (s *OrderService) FetchOrderDetails(id int) (string, error) {
	order, err := s.repo.GetOrder(id)
	if err != nil {
		// Оборачивание ошибки с сохранением корневой причины через %w
		return "", fmt.Errorf("сервис заказов: сбой получения заказа #%d: %w", id, err)
	}
	return order, nil
}
```

ℹ️ Сервисный слой с оборачиванием ошибок

**`err_service_test.go`**

```go
package main

import (
	"errors"
	"strings"
	"testing"
)

type FailingOrderRepoMock struct{}

func (FailingOrderRepoMock) GetOrder(id int) (string, error) {
	return "", ErrDBUnavailable
}

func TestOrderServiceErrorWrapping(t *testing.T) {
	svc := &OrderService{repo: FailingOrderRepoMock{}}

	_, err := svc.FetchOrderDetails(999)
	if err == nil {
		t.Fatal("Ожидалась ошибка сервиса, получен nil")
	}

	// 1. Проверяем, что исходная ошибка доступна через errors.Is
	if !errors.Is(err, ErrDBUnavailable) {
		t.Errorf("errors.Is не нашел исходную ошибку ErrDBUnavailable в цепочке: %v", err)
	}

	// 2. Проверяем наличие контекстного сообщения сервиса
	expectedContext := "сервис заказов: сбой получения заказа #999"
	if !strings.Contains(err.Error(), expectedContext) {
		t.Errorf("текст ошибки %q не содержит контекста %q", err.Error(), expectedContext)
	}
}
```

ℹ️ Валидация обернутой ошибки и контекста

**`Терминал`**

```bash
go test -v err_service_test.go err_service.go
# Вывод:

# --- PASS: TestOrderServiceErrorWrapping (0.00s)
# PASS
```

## Под капотом

`fmt.Errorf` с `%w` создает структуру `wrapError`. Функция `errors.Is` выполняет рекурсивный вызов `Unwrap()` по цепочке до нахождения `ErrDBUnavailable`.

## Подводные камни

Использовать `%s` или `%v` вместо `%w`: связь с оригинальной ошибкой будет потеряна, и `errors.Is` вернет `false`.

## На собеседовании

**Вопрос с собеседования:** «Зачем логировать ошибку только на самом верхнем уровне (в HTTP/gRPC Handler), а не на каждом уровне архитектуры?»
**Ответ:** Если каждый слой логирует ошибку (`repo.go`, `service.go`, `handler.go`), в логах появится 3 дублирующие записи на один инцидент, забивая хранилище логов (Elasticsearch/ClickHouse). Правильный подход: оборачивать контекст через `%w` на каждом слое и логировать полный стек один раз на верхнем уровне.
