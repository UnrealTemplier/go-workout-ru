# Ручной мок с функциональными полями: гибкая подмена методов интерфейса

## Условие

Объяви интерфейс `UserRepository` с методами `GetByID(id int) (*User, error)`, `Save(user *User) error`. Напиши **ручной мок** `MockUserRepository` с полями `GetByIDFunc`, `SaveFunc` (функции). Используй в тесте сервиса.

## Теория

Паттерн «Функция как поле структуры» (Function Field Mock) — идиоматичный и самый гибкий способ ручного мокирования в Go:
1. Структура мока содержит поля-функции, сигнатуры которых в точности совпадают с методами интерфейса:
   `GetByIDFunc func(id int) (*User, error)`
2. В теле метода структуры просто вызывается эта функция:
   `if m.GetByIDFunc != nil { return m.GetByIDFunc(id) }`
3. Преимущество: каждый отдельный тест настраивает ТОЛЬКО те методы, которые вызываются в его сценарии, определяя логику инлайн прямо в теле теста без тяжелых внешних фреймворков.

## Решение по шагам

1. Объявите интерфейс `UserRepository`.
2. Создайте структуру `MockUserRepository` с полями `GetByIDFunc` и `SaveFunc`.
3. Реализуйте методы интерфейса на структуре мока.
4. Напишите тест сервиса `UserService`, переопределив `GetByIDFunc`.

## Код решения

**`user.go`**

```go
package main

import "fmt"

type User struct {
	ID   int
	Name string
}

type UserRepository interface {
	GetByID(id int) (*User, error)
	Save(user *User) error
}

type UserService struct {
	repo UserRepository
}

func NewUserService(repo UserRepository) *UserService {
	return &UserService{repo: repo}
}

func (s *UserService) GetWelcomeMessage(id int) (string, error) {
	u, err := s.repo.GetByID(id)
	if err != nil {
		return "", fmt.Errorf("ошибка получения пользователя: %w", err)
	}
	return fmt.Sprintf("Добро пожаловать, %s!", u.Name), nil
}
```

ℹ️ Сервис и интерфейс репозитория

**`user_mock_test.go`**

```go
package main

import (
	"errors"
	"testing"
)

// MockUserRepository реализует UserRepository через функциональные поля
type MockUserRepository struct {
	GetByIDFunc func(id int) (*User, error)
	SaveFunc    func(user *User) error
}

func (m *MockUserRepository) GetByID(id int) (*User, error) {
	if m.GetByIDFunc != nil {
		return m.GetByIDFunc(id)
	}
	return nil, errors.New("GetByIDFunc не настроена")
}

func (m *MockUserRepository) Save(user *User) error {
	if m.SaveFunc != nil {
		return m.SaveFunc(user)
	}
	return errors.New("SaveFunc не настроена")
}

func TestUserService_GetWelcomeMessage(t *testing.T) {
	// Настраиваем поведение мока инлайн для этого конкретного теста
	mockRepo := &MockUserRepository{
		GetByIDFunc: func(id int) (*User, error) {
			if id == 42 {
				return &User{ID: 42, Name: "Алексей"}, nil
			}
			return nil, errors.New("пользователь не найден")
		},
	}

	service := NewUserService(mockRepo)
	msg, err := service.GetWelcomeMessage(42)

	if err != nil {
		t.Fatalf("неожиданная ошибка: %v", err)
	}
	expected := "Добро пожаловать, Алексей!"
	if msg != expected {
		t.Errorf("got %q; want %q", msg, expected)
	}
}
```

## Под капотом

Функциональные поля позволяют использовать замыкания: мок может захватывать локальные переменные теста, вести счетчики вызовов или эмулировать сетевые ошибки без глобального состояния.

## Подводные камни

Забыть проверить `if m.GetByIDFunc != nil`: если тестируемый код неожиданно вызовет ненастроенный метод, вызов `nil` функции приведет к панике `nil pointer dereference`.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go стандартной практике часто предпочитают ручные функциональные моки вместо генераторов вроде mockgen?»
**Ответ:** Ручные моки не требуют кодогенерации в `go:generate`, моментально компилируются, не ломаются при смене версий инструментов, легко читаются на Code Review и содержат только нужную для теста логику без тысяч строк бойлерплейта.
