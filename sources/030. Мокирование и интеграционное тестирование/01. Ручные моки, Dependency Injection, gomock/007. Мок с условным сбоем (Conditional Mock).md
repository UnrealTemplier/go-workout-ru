# Мок с условным сбоем (Conditional Mock): тестирование Retry-политики

## Условие

Напиши **mock, возвращающий ошибку по условию**: `MockPaymentGateway{FailAfterNCalls: 3}`. Первые 2 вызова — успех, 3-й — ошибка. Используй для тестирования retry-логики.

### Исходная формулировка

Напиши **mock, возвращающий ошибку по условию**: `MockPaymentGateway{FailAfterNCalls: 3}`. Первые 2 вызова — успех, 3-й — ошибка. Используй для тестирования retry-логики.

## Теория

Тестирование механизмов повторных попыток (Retry Policy / Exponential Backoff):
В распределенных системах кратковременные сетевые сбои (Network Blip) решаются повторными запросами.
Для проверки надежности клиента создают мок, который:
1. Симулирует падения первые \(N\) раз.
2. На \(N+1\) попытке возвращает успешный ответ.
3. Либо наоборот: падает после определенного числа обращений.

## Решение по шагам

1. Создайте интерфейс `PaymentGateway`.
2. Реализуйте `MockPaymentGateway` с полями `CallCount` и `FailFirstNCalls`.
3. Напишите функцию `ExecuteWithRetry` с 3 попытками.
4. Проверьте восстановление после двух сбоев.

## Код решения

**`retry_client.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type PaymentGateway interface {
	ProcessPayment(amount int) error
}

func ExecutePaymentWithRetry(gw PaymentGateway, amount int, maxAttempts int) error {
	var lastErr error
	for attempt := 1; attempt <= maxAttempts; attempt++ {
		err := gw.ProcessPayment(amount)
		if err == nil {
			return nil // Успех!
		}
		lastErr = err
	}
	return fmt.Errorf("платеж провален после %d попыток: %w", maxAttempts, lastErr)
}
```

ℹ️ Клиент с поддержкой retry-логики

**`retry_client_test.go`**

```go
package main

import (
	"errors"
	"testing"
)

type MockFailingGateway struct {
	calls            int
	failFirstNCalls  int
}

func (m *MockFailingGateway) ProcessPayment(amount int) error {
	m.calls++
	if m.calls <= m.failFirstNCalls {
		return errors.New("временный сетевой сбой 503 Service Unavailable")
	}
	return nil
}

func TestExecutePaymentWithRetry_RecoversOnThirdAttempt(t *testing.T) {
	// Первые 2 попытки падают, 3-я успешна
	mockGW := &MockFailingGateway{failFirstNCalls: 2}

	err := ExecutePaymentWithRetry(mockGW, 500, 3)
	if err != nil {
		t.Fatalf("платеж должен был завершиться успехом на 3-й попытке, ошибка: %v", err)
	}

	if mockGW.calls != 3 {
		t.Errorf("сделано попыток: %d; want 3", mockGW.calls)
	}
}

func TestExecutePaymentWithRetry_FailsWhenExceedingLimit(t *testing.T) {
	// Падает первые 5 раз, но лимит всего 3 попытки
	mockGW := &MockFailingGateway{failFirstNCalls: 5}

	err := ExecutePaymentWithRetry(mockGW, 500, 3)
	if err == nil {
		t.Fatal("ожидалась ошибка превышения лимита попыток, получен nil")
	}
	if mockGW.calls != 3 {
		t.Errorf("сделано попыток: %d; want 3", mockGW.calls)
	}
}
```

## Под капотом

Условный мок позволяет смоделировать редкие сетевые феномены (дребезг контактов, таймауты TCP handshake, перегрузка очередей), которые невозможно надежно воспроизвести на реальном окружении.

## Подводные камни

Вставлять реальные задержки `time.Sleep` в retry-цикл тестов: это сделает тесты медленными. В тестах задержку (backoff duration) конфигурируют равной 0 или передают виртуальное время.

## На собеседовании

**Вопрос с собеседования:** «Каковы три ключевых правила написания надежного Retry в микросервисах?»
**Ответ:** 1. Идемпотентность операции (нельзя бездумно повторять неидемпотентный `POST /charge`). 2. Экспоненциальная задержка (Exponential Backoff) с добавлением случайного шума (Jitter), чтобы избежать шторма повторных запросов (Thundering Herd). 3. Жесткий лимит максимального числа попыток и общий контекстный таймаут `context.WithTimeout`.
