# Внедрение зависимостей (Dependency Injection) через интерфейсы

## Условие

Создайте интерфейс `UserRepository` с методами `FindByID(id int) (*User, error)` и `Save(user *User) error`. Напишите сервис `UserService`, зависящий от этого интерфейса.

## Теория

Принцип инверсии зависимостей (Dependency Inversion Principle — буква D в SOLID):
- Модули верхнего уровня (бизнес-логика `UserService`) не должны зависеть от модулей нижнего уровня (конкретная реализация `PostgresUserRepository`).
- Оба уровня должны зависеть от абстракций (интерфейс `UserRepository`).
- В Go интерфейс объявляется на стороне **потребителя** (Consumer), а не на стороне реализации. Сервис сам определяет контракт того, что ему требуется для работы.

## Решение по шагам

1. Создайте структуру `User`.
2. Объявите интерфейс `UserRepository`.
3. Реализуйте сервис `UserService` с конструктором `NewUserService(repo UserRepository)`.
4. Напишите метод сервиса `RegisterUser(id int, name string) error`.

## Код решения

**`domain.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type User struct {
	ID   int
	Name string
}

type UserRepository interface {
	FindByID(id int) (*User, error)
	Save(user *User) error
}

type UserService struct {
	repo UserRepository
}

func NewUserService(repo UserRepository) *UserService {
	return &UserService{repo: repo}
}

func (s *UserService) RegisterUser(id int, name string) error {
	if name == "" {
		return errors.New("имя не может быть пустым")
	}

	existing, _ := s.repo.FindByID(id)
	if existing != nil {
		return fmt.Errorf("пользователь с ID %d уже зарегистрирован", id)
	}

	newUser := &User{ID: id, Name: name}
	return s.repo.Save(newUser)
}
```

ℹ️ Архитектура с внедрением зависимостей через конструктор

**`domain_test.go`**

```go
package main

import (
	"testing"
)

type StubRepo struct {
	savedUser *User
}

func (s *StubRepo) FindByID(id int) (*User, error) {
	return nil, nil // пользователя нет
}

func (s *StubRepo) Save(user *User) error {
	s.savedUser = user
	return nil
}

func TestRegisterUser_Success(t *testing.T) {
	stub := &StubRepo{}
	svc := NewUserService(stub)

	err := svc.RegisterUser(100, "Ольга")
	if err != nil {
		t.Fatalf("неожиданная ошибка: %v", err)
	}

	if stub.savedUser == nil || stub.savedUser.Name != "Ольга" {
		t.Errorf("пользователь не был сохранен корректно: %+v", stub.savedUser)
	}
}
```

## Под капотом

В Go интерфейсы удовлетворяются неявно (Implicit Interfaces). Структуре `StubRepo` не нужно писать ключевые слова `implements`: достаточно реализовать методы с совпадающими сигнатурами, и компилятор автоматически признает ее валидной реализацией `UserRepository`.

## Подводные камни

Создавать экземпляр базы данных прямо внутри конструктора сервиса `repo := postgres.New()`. Это намертво связывает сервис с реальной базой и делает юнит-тестирование невозможным.

## На собеседовании

**Вопрос с собеседования:** «Где в архитектуре проекта должен объявляться интерфейс: в пакете репозитория или в пакете сервиса?»
**Ответ:** В Go интерфейсы должны объявляться в пакете **потребителя** (в сервисе). Это соблюдает принцип «Accept interfaces, return structs». Репозиторий возвращает конкретную структуру, а сервис объявляет интерфейс с минимально необходимым набором методов.
