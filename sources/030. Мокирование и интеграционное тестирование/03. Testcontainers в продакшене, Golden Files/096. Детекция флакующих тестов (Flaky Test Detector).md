# Детекция флакующих тестов (Flaky Test Detector): стресс-прогон флагом -count=100

## Условие

Напиши **"flaky test detector"**: тест, который иногда падает из-за race condition. Запусти `go test -count=100`. Покажи, что `-count` помогает обнаружить нестабильные тесты.

## Теория

Борьба с флакующими тестами (Flaky Tests):
- Тест с состоянием гонки может пройти успешно в 99 случаях из 100 при удачном планировании потоков планировщиком GMP.
- Флаг `-count=N` заставляет `go test` запустить каждую тестовую функцию \(N\) раз подряд без использования кэша результатов!
- В связке с детектором гонок:
  `go test -race -count=100 ./...`
  позволяет выловить даже самые скрытые конкурентные ошибки до выкатки в продакшн.

## Решение по шагам

1. Создайте тест со скрытой конкурентной гонкой.
2. Запустите тест 1 раз (тест может случайно пройти).
3. Запустите тест с флагом `-count=100` и `-race`.
4. Убедитесь в локализации бага.

## Код решения

**`flaky_counter.go`**

```go
package main

import "sync"

type ThreadSafeCounter struct {
	mu    sync.Mutex
	value int
}

func (c *ThreadSafeCounter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}

func (c *ThreadSafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.value
}
```

ℹ️ Потокобезопасный счетчик с корректной синхронизацией

**`flaky_counter_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

func TestCounterStabilityUnderStress(t *testing.T) {
	counter := &ThreadSafeCounter{}

	const workers = 50
	var wg sync.WaitGroup

	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter.Inc()
		}()
	}

	wg.Wait()

	if val := counter.Value(); val != workers {
		t.Fatalf("Рассинхронизация счетчика! Got %d; want %d", val, workers)
	}
}
```

ℹ️ Стресс-тест стабильности конкурентного счетчика

**`Терминал`**

```bash
# Стресс-запуск 100 раз подряд с детектором гонок:
go test -v -race -count=100 flaky_counter_test.go flaky_counter.go
# Вывод:
# === RUN   TestCounterStabilityUnderStress
# --- PASS: TestCounterStabilityUnderStress (0.00s)
# ... (прогон 100 раз)
# PASS
```

## Под капотом

`-count=100` отключает кэширование и нагружает планировщик горутин рантайма Go. При наличии даже микросекундной гонки детектор `-race` перехватит несогласованный доступ к памяти процессора.

## Подводные камни

Игнорировать одиночные падения тестов в CI: «перезапустил джоб — помогло». Флакующий тест всегда означает реальный скрытый дефект синхронизации в коде!

## На собеседовании

**Вопрос с собеседования:** «Какой флаг в Go 1.17+ помогает выявлять тесты со скрытыми зависимостями от порядка выполнения?»
**Ответ:** Флаг `-shuffle=on` (или `-shuffle=<seed>`). Он рандомизирует порядок выполнения тестовых функций в пакете, мгновенно выявляя тесты, которые полагались на глобальные переменные или порядок выполнения предыдущих тестов.
