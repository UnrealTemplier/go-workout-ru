# Контрактное тестирование (Contract Testing): единый тестовый набор для разных реализаций

## Условие

Напиши **"contract test"**: интерфейс `Cache` с методами `Get`, `Set`, `Delete`. Напиши тест, параметризованный реализацией (`InMemoryCache`, `RedisCache`). Один и тот же тест проходит для обеих реализаций. Покажи, что контракт соблюдается.

## Теория

Контрактное тестирование интерфейсов (Contract / Compliance Testing):
- Если интерфейс `CacheStore` имеет две реализации (`InMemoryCache` и `RedisCache`), поведение обеих реализаций должно быть абсолютно идентичным (принцип подстановки Барбары Лисков — Liskov Substitution Principle).
- Пишется универсальная функция тестирования контракта:
  `func VerifyCacheContract(t *testing.T, newCache func() CacheStore)`
- Она запускается для каждой реализации, гарантируя, что обе они одинаково обрабатывают отсутствующие ключи, удаление и перезапись.

## Решение по шагам

1. Объявите интерфейс `ContractCache`.
2. Реализуйте две структуры `MapCache` и `SliceCache`.
3. Напишите обобщенную тестовую функцию `testCacheContract`.
4. Запустите субтесты для обеих реализаций.

## Код решения

**`contract_cache.go`**

```go
package main

type ContractCache interface {
	Get(key string) (string, bool)
	Set(key, val string)
	Delete(key string)
}

type MapCacheImpl struct {
	data map[string]string
}

func NewMapCache() *MapCacheImpl {
	return &MapCacheImpl{data: make(map[string]string)}
}

func (m *MapCacheImpl) Get(key string) (string, bool) {
	v, ok := m.data[key]
	return v, ok
}

func (m *MapCacheImpl) Set(key, val string) {
	m.data[key] = val
}

func (m *MapCacheImpl) Delete(key string) {
	delete(m.data, key)
}
```

ℹ️ Интерфейс и первая реализация кэша

**`contract_cache_test.go`**

```go
package main

import (
	"testing"
)

// testCacheContract — единый контрактный тест, параметризованный фабрикой реализаций
func testCacheContract(t *testing.T, factory func() ContractCache) {
	c := factory()

	// 1. Чтение отсутствующего ключа -> (false)
	if _, ok := c.Get("missing"); ok {
		t.Error("Для отсутствующего ключа Get обязан возвращать false")
	}

	// 2. Запись и чтение
	c.Set("alpha", "value_alpha")
	val, ok := c.Get("alpha")
	if !ok || val != "value_alpha" {
		t.Errorf("Get = %q, %v; want value_alpha, true", val, ok)
	}

	// 3. Удаление
	c.Delete("alpha")
	if _, ok := c.Get("alpha"); ok {
		t.Error("После Delete ключ не должен существовать")
	}
}

func TestCacheImplementationsContract(t *testing.T) {
	// Прогон контракта для реализации на мапе
	t.Run("MapCache Implementation", func(t *testing.T) {
		testCacheContract(t, func() ContractCache {
			return NewMapCache()
		})
	})
}
```

ℹ️ Параметризованное тестирование контракта интерфейса

**`Терминал`**

```bash
go test -v contract_cache_test.go contract_cache.go
# Вывод:
# === RUN   TestCacheImplementationsContract
# === RUN   TestCacheImplementationsContract/MapCache_Implementation

```

## Под капотом

Контрактные тесты предотвращают тонкие баги рассинхронизации: например, когда in-memory кэш возвращает `false` на удаленный ключ, а Redis-адаптер возвращает пустую строку `""` и `true`.

## Подводные камни

Писать отдельные дублирующие тесты для каждой новой реализации: при изменении контракта придется править десятки одинаковых файлов тестов.

## На собеседовании

**Вопрос с собеседования:** «Какому принципу SOLID соответствует контрактное тестирование интерфейсов?»
**Ответ:** Принципу подстановки Лисков (Liskov Substitution Principle / LSP): любая реализация интерфейса должна вести себя так, чтобы вызывающий код мог использовать её без каких-либо неожиданных сайд-эффектов или изменения логики.
