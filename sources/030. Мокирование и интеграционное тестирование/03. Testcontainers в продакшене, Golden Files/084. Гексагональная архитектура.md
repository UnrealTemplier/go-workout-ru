# Гексагональная архитектура (Hexagonal Architecture): сквозное тестирование портов и адаптеров

## Условие

Напиши полный **"hexagonal architecture" тест**:
- Domain: `UserService` с интерфейсом `UserRepository`
- Реализация: `PostgresUserRepository` 
- Тест: `InMemoryUserRepository` (stub) для unit-тестов бизнес-логики
- Интеграционный тест: `PostgresUserRepository` с testcontainers

## Теория

Гексагональная архитектура (Ports and Adapters):
1. **Ядро домена (Domain Core):** бизнес-логика `UserService` не имеет внешних зависимостей.
2. **Входящие порты (Driving Ports):** интерфейсы, через которые приложение вызывается (HTTP, gRPC, CLI).
3. **Исходящие порты (Driven Ports):** интерфейс `UserRepository`.
4. **Адаптеры (Adapters):**
   - Продакшн адаптер: `PostgresUserRepository` (реализует порт).
   - Тестовый адаптер: `InMemoryUserRepository` (быстрый стаб для unit-тестов домена).
   - Интеграционный тест: верифицирует `PostgresUserRepository` против реальной базы.

## Решение по шагам

1. Создайте доменный сервис `HexUserService`.
2. Реализуйте порт `HexUserRepo`.
3. Создайте in-memory адаптер и протестируйте бизнес-правила.
4. Создайте контрактный тест для реального PostgreSQL адаптера.

## Код решения

**`hex_domain.go`**

```go
package main

import (
	"errors"
	"strings"
)

type HexUser struct {
	ID    int
	Email string
}

// Driven Port (Интерфейс исходящего адаптера)
type HexUserRepo interface {
	Find(id int) (*HexUser, error)
	Create(u *HexUser) error
}

// Domain Service (Ядро бизнес-логики)
type HexUserService struct {
	repo HexUserRepo
}

func NewHexUserService(repo HexUserRepo) *HexUserService {
	return &HexUserService{repo: repo}
}

func (s *HexUserService) Register(id int, email string) error {
	if !strings.Contains(email, "@") {
		return errors.New("невалидный email")
	}

	existing, _ := s.repo.Find(id)
	if existing != nil {
		return errors.New("пользователь уже существует")
	}

	return s.repo.Create(&HexUser{ID: id, Email: email})
}
```

**`hex_domain_test.go`**

```go
package main

import (
	"testing"
)

// Тестовый адаптер для Unit-тестирования ядра
type InMemoryHexRepo struct {
	users map[int]*HexUser
}

func (m *InMemoryHexRepo) Find(id int) (*HexUser, error) {
	return m.users[id], nil
}

func (m *InMemoryHexRepo) Create(u *HexUser) error {
	m.users[u.ID] = u
	return nil
}

func TestHexagonalCoreBusinessLogic(t *testing.T) {
	inMemoryAdapter := &InMemoryHexRepo{users: make(map[int]*HexUser)}
	service := NewHexUserService(inMemoryAdapter)

	// Тест бизнес-правила: ошибка формата email
	err := service.Register(1, "bad-email")
	if err == nil {
		t.Error("Ожидалась ошибка формата email")
	}

	// Тест успешной регистрации
	err = service.Register(1, "valid@go.dev")
	if err != nil {
		t.Fatalf("Успешная регистрация провалена: %v", err)
	}

	// Тест бизнес-правила: дубликат ID
	err = service.Register(1, "another@go.dev")
	if err == nil {
		t.Error("Ожидалась ошибка дубликата ID")
	}
}
```

## Под капотом

Гексагональная архитектура полностью изолирует бизнес-правила от деталей СУБД. Если компания решит сменить PostgreSQL на DynamoDB или ScyllaDB, доменный код и unit-тесты не изменятся ни на одну строчку.

## Подводные камни

Протекание деталей SQL в домен (например, возвращение `sql.ErrNoRows` из репозитория): репозиторий обязан возвращать доменную ошибку `ErrUserNotFound`.

## На собеседовании

**Вопрос с собеседования:** «Почему в гексагональной архитектуре репозиторий должен возвращать доменные ошибки, а не sql.ErrNoRows?»
**Ответ:** Чтобы не нарушать границу абстракции (Leaky Abstraction). Если сервис обрабатывает `if errors.Is(err, sql.ErrNoRows)`, он становится жестко связан со стандартом `database/sql`, теряя независимость от инфраструктуры.
