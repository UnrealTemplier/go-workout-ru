# Симуляция инфраструктурных падений: ручной мок с настраиваемой ошибкой ReturnError

## Условие

**Симуляция ошибок (Mocking errors)**: В ручном моке из упр. 429 добавь поле `ReturnError error`. Настрой мок так, чтобы он возвращал ошибку (симуляция отвала почтового сервера), и протестируй, как твой `UserService` корректно обрабатывает это падение.

## Теория

Управляемая симуляция аварий (Fault Injection Pattern):
- Надежность сервиса определяется тем, как он ведет себя при отказе зависимостей.
- Ручной мок конфигурируется полем `ReturnError error`:
  `mockMail.ReturnError = errors.New("550 SMTP relay connection refused")`
- Сервис `UserService` при ошибке отправки письма не должен паниковать — он обязан либо вернуть обернутую доменную ошибку, либо залогировать сбой и продолжить работу (в зависимости от требований бизнеса).

## Решение по шагам

1. Создайте структуру `ConfigurableEmailMock` с полем `ReturnError`.
2. Реализуйте сервис регистрации, вызывающий отправку почты.
3. Настройте `ReturnError` на возврат ошибки сети.
4. Убедитесь, что сервис возвращает корректную ошибку регистрации.

## Код решения

**`onboarding.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type MailTransport interface {
	SendEmail(to, text string) error
}

type UserOnboardingService struct {
	mailer MailTransport
}

func NewUserOnboardingService(m MailTransport) *UserOnboardingService {
	return &UserOnboardingService{mailer: m}
}

func (s *UserOnboardingService) Register(email string) error {
	if email == "" {
		return errors.New("email не может быть пустым")
	}

	err := s.mailer.SendEmail(email, "Добро пожаловать в сервис!")
	if err != nil {
		return fmt.Errorf("пользователь зарегистрирован, но письмо подтверждения не отправлено: %w", err)
	}
	return nil
}
```

ℹ️ Сервис регистрации с обработкой ошибок отправки почты

**`onboarding_test.go`**

```go
package main

import (
	"errors"
	"strings"
	"testing"
)

type ConfigurableEmailMock struct {
	ReturnError error
}

func (m *ConfigurableEmailMock) SendEmail(to, text string) error {
	return m.ReturnError
}

func TestUserRegistrationWithMailerFailure(t *testing.T) {
	expectedErr := errors.New("554 SMTP server connection dropped")
	mock := &ConfigurableEmailMock{ReturnError: expectedErr}

	service := NewUserOnboardingService(mock)
	err := service.Register("alex@corporate.ru")

	// Проверяем, что сервис вернул ошибку
	if err == nil {
		t.Fatal("Ожидалась ошибка отвала почтового сервера, получен nil")
	}

	// Проверяем корневую причину через errors.Is
	if !errors.Is(err, expectedErr) {
		t.Errorf("errors.Is не нашел expectedErr: %v", err)
	}

	// Проверяем доменный контекст
	if !strings.Contains(err.Error(), "письмо подтверждения не отправлено") {
		t.Errorf("Ошибка не содержит доменного контекста: %v", err)
	}
}
```

## Под капотом

Поле `ReturnError` позволяет легко тестировать как временные ошибки (Temporary Network Timeout), так и фатальные ошибки валидации (Invalid Recipient Address).

## Подводные камни

Игнорировать ошибку `_ = s.mailer.SendEmail(...)`: если почтовый сервер упал, а код не обработал ошибку, пользователь никогда не получит ссылку на активацию аккаунта.

## На собеседовании

**Вопрос с собеседования:** «Должна ли регистрация пользователя падать, если фоновая отправка приветственного письма завершилась ошибкой?»
**Ответ:** Зависит от бизнес-модели: если email критичен для входа (активация по ссылке), регистрация блокируется. В современных HighLoad архитектурах применяют Transactional Outbox Pattern: профиль сохраняется в БД, а задание на отправку письма пишется в outbox-таблицу в той же SQL-транзакции, гарантируя доставку письма фоновым воркером даже при кратковременном отказе почтового сервиса.
