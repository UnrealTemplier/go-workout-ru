# Хаос-тестирование (Chaos Testing): статистическая верификация Retry-логики на 1000 прогонах

## Условие

Напиши **"chaos test"** (упрощённый): функция `UnreliableDB` с вероятностью ошибки 30%. Напиши тест для retry-логики: при 3 попытках с backoff вероятность общего failure = 0.3³ = 2.7%. Запусти 1000 раз, проверь статистику.

## Теория

Тестирование теории вероятностей в распределенных системах:
- Пусть вероятность единичного сбоя сети или СУБД \(P(\text{fail}) = 0.3\) (30%).
- При независимых повторных попытках вероятность того, что все 3 попытки завершатся неудачей:
  $$P(\text{all fail}) = 0.3^3 = 0.027 \quad (2.7\%)$$
- При запуске \(N = 1000\) итераций число полных отказов по закону больших чисел должно лежать в узком доверительном интервале (около 27 отказов \(\pm 15\)).
- Если Retry-логика реализована с ошибкой (например, не делает повторов), тест мгновенно зафиксирует 300 отказов и упадет!

## Решение по шагам

1. Создайте функцию `UnreliableCall(failureRate float64) error`.
2. Реализуйте функцию `CallWithRetry(attempts int) error`.
3. Запустите 1000 итераций и посчитайте статистику отказов.
4. Проверьте попадание в статистический диапазон.

## Код решения

**`chaos_retry.go`**

```go
package main

import (
	"errors"
	"math/rand"
)

var ErrNetworkGlitch = errors.New("временный сбой сети")

func UnreliableNetworkCall(failureRate float64) error {
	if rand.Float64() < failureRate {
		return ErrNetworkGlitch
	}
	return nil // Успех
}

func RobustExecute(maxAttempts int, failureRate float64) error {
	var lastErr error
	for i := 0; i < maxAttempts; i++ {
		err := UnreliableNetworkCall(failureRate)
		if err == nil {
			return nil // Успешно пробились!
		}
		lastErr = err
	}
	return lastErr
}
```

ℹ️ Ненадежный вызов с retry-механизмом

**`chaos_retry_test.go`**

```go
package main

import (
	"math/rand"
	"testing"
)

func TestChaosRetryStatistics(t *testing.T) {
	// Фиксируем сид для воспроизводимости
	rand.Seed(2026)

	const totalRuns = 1000
	const maxAttempts = 3
	const singleFailureRate = 0.30 // 30%

	failures := 0
	for i := 0; i < totalRuns; i++ {
		if err := RobustExecute(maxAttempts, singleFailureRate); err != nil {
			failures++
		}
	}

	actualFailurePercent := float64(failures) / float64(totalRuns) * 100.0
	t.Logf("Статистика из %d прогонов: полных отказов = %d (%.2f%%)",
		totalRuns, failures, actualFailurePercent)

	// Теоретический отказ: 0.3^3 = 2.7% (около 27 отказов на 1000)
	// Допустимый доверительный диапазон: от 1.5% до 4.5%
	if actualFailurePercent < 1.0 || actualFailurePercent > 5.0 {
		t.Errorf("Аномальная статистика отказов: %.2f%% (ожидалось около 2.7%%)", actualFailurePercent)
	}
}
```

## Под капотом

Тест проверяет математическую модель отказоустойчивости: процент отказов снизился с 30% до 2.4% благодаря 3 попыткам.

## Подводные камни

Использовать слишком маленький порог итераций (\(N = 20\)): из-за дисперсии случайной величины тест будет случайным образом флаковать.

## На собеседовании

**Вопрос с собеседования:** «Что такое Chaos Monkey и как проводятся хаос-тесты в Production Kubernetes?»
**Ответ:** Chaos Monkey (инструменты Chaos Mesh, LitmusChaos) случайно убивают поды, имитируют потерю сетевых пакетов (Packet Loss), вносят сетевые задержки (Latency Injection) и отключают зоны доступности (AZ). Тест проверяет, что система продолжает обслуживать трафик клиентов с соблюдением SLA благодаря авторестартам K8s и Retry-политикам.
