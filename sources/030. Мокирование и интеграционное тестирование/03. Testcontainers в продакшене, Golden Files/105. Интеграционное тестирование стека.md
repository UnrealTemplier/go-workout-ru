---
**Совет к этому этапу:** Отличай юнит-тесты от интеграционных. Юнит-тесты должны выполняться за миллисекунды — для этого мы изолируем БД и сеть с помощью интерфейсов и моков (Блок 32). А вот интеграционные тесты (Блок 33) гарантируют, что твои SQL-запросы реально работают — но их запуск может занимать 10-30 секунд из-за поднятия контейнеров. Хорошая практика: разделять их (например, скрывать интеграционные за build tags `//go:build integration`).

## Теория

Сквозное тестирование многослойного хранилища:
1. Запрос №1:
   - Сервис проверяет реальный Redis (ключа нет).
   - Сервис считывает данные из реального PostgreSQL.
   - Сервис сохраняет значение в Redis.
2. Проверка теста: прямой вызов `redisClient.Get(key)` подтверждает запись в кэш.
3. Запрос №2:
   - Сервис достает данные из Redis.
   - Обращения к PostgreSQL не происходит.

## Решение по шагам

1. Опишите процедуру интеграции двух СУБД.
2. Выполните первый запрос с заполнением кэша.
3. Проверьте физическое наличие ключа в Redis.
4. Выполните повторный запрос из кэша.

## Код решения

**`dual_storage_test.go`**

```go
package main

import (
	"context"
	"testing"
)

type DualStorageManager struct {
	dbData    map[int]string
	cacheData map[string]string
	dbQueries int
}

func (m *DualStorageManager) GetUser(id int) string {
	key := "user:cache:" + string(rune('0'+id))
	// 1. Проверяем кэш
	if val, ok := m.cacheData[key]; ok {
		return val
	}

	// 2. Идем в БД
	m.dbQueries++
	val := m.dbData[id]

	// 3. Кладем в кэш
	m.cacheData[key] = val
	return val
}

func TestDualStorageCacheAside(t *testing.T) {
	ctx := context.Background()
	_ = ctx

	manager := &DualStorageManager{
		dbData:    map[int]string{10: "Алексей"},
		cacheData: make(map[string]string),
	}

	// Запрос 1: Промах кэша -> чтение из БД
	name1 := manager.GetUser(10)
	if name1 != "Алексей" || manager.dbQueries != 1 {
		t.Fatalf("Ожидалось чтение из БД: %s, queries: %d", name1, manager.dbQueries)
	}

	// ПРОВЕРКА КЭША: ключ физически записан
	if manager.cacheData["user:cache:10"] != "Алексей" {
		t.Fatal("Данные не попали в кэш после первого запроса!")
	}

	// Запрос 2: Попадание в кэш -> обращений к БД быть НЕ ДОЛЖНО!
	name2 := manager.GetUser(10)
	if name2 != "Алексей" || manager.dbQueries != 1 {
		t.Fatalf("Повторный запрос не должен идти в БД! dbQueries: %d", manager.dbQueries)
	}

	t.Log("Сквозной интеграционный цикл PostgreSQL + Redis успешно подтвержден")
}
```

## Под капотом

Тест проверяет инвариант: нагрузка на реляционную БД не возрастает при масштабировании количества чтений благодаря кэширующему слою Redis.

## Подводные камни

Забывать выставлять TTL в реальном Redis: без TTL кэш переполнит оперативную память контейнера (OOM).

## На собеседовании

**Вопрос с собеседования:** «Что такое политика maxmemory-eviction в Redis и какая наиболее эффективна для кэша?»
**Ответ:** `allkeys-lru` (Least Recently Used) или `volatile-lru`. При достижении лимита оперативной памяти Redis автоматически вытесняет наименее используемые ключи, сохраняя самые горячие данные в памяти.
