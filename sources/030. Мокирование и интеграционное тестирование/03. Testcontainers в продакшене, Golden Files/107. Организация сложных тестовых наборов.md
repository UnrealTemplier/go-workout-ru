# Организация сложных тестовых наборов: библиотека testify/suite и жизненный цикл xUnit

## Условие

Напиши **"test suite"** через `testify/suite`: `type UserServiceTestSuite struct { suite.Suite; repo UserRepository }`. Методы `SetupTest`, `TearDownTest`. Тесты как методы на suite. Покажи организацию сложных тестов.

### Исходная формулировка

Напиши **"test suite"** через `testify/suite`: `type UserServiceTestSuite struct { suite.Suite; repo UserRepository }`. Методы `SetupTest`, `TearDownTest`. Тесты как методы на suite. Покажи организацию сложных тестов.

## Теория

Пакет `github.com/stretchr/testify/suite`:
- Привносит структуру классических xUnit-тестов в Go.
- Структура сьюта встраивает `suite.Suite`.
- Хуки жизненного цикла:
  - `SetupSuite()` / `TearDownSuite()`: выполняются один раз перед/после всеми тестами сьюта.
  - `SetupTest()` / `TearDownTest()`: выполняются перед/после каждым методом теста.
- Все методы с префиксом `TestXxx()` на структуре сьюта автоматически запускаются через `suite.Run(t, new(MySuite))`.

## Решение по шагам

1. Создайте структуру `OrderTestSuite`, встроив `suite.Suite`.
2. Реализуйте `SetupTest` для инициализации хранилища перед каждым тестом.
3. Напишите тестовые методы с использованием ассертов сьюта `s.Equal()`.
4. Запустите сьют через `suite.Run(t, new(OrderTestSuite))`.

## Код решения

**`order_suite_test.go`**

```go
package main

import (
	"testing"

	"github.com/stretchr/testify/suite"
)

type MemoryOrderRepo struct {
	orders map[int]string
}

// OrderTestSuite объединяет тесты управления заказами
type OrderTestSuite struct {
	suite.Suite
	repo *MemoryOrderRepo
}

// SetupTest выполняется ПЕРЕД каждым тестовым методом
func (s *OrderTestSuite) SetupTest() {
	s.repo = &MemoryOrderRepo{
		orders: make(map[int]string),
	}
	s.repo.orders[1] = "Заказ Оплачен"
}

// TearDownTest выполняется ПОСЛЕ каждого тестового метода
func (s *OrderTestSuite) TearDownTest() {
	// Сброс ресурсов
}

func (s *OrderTestSuite) TestGetExistingOrder() {
	title, ok := s.repo.orders[1]
	s.True(ok, "Заказ должен существовать")
	s.Equal("Заказ Оплачен", title)
}

func (s *OrderTestSuite) TestAddNewOrder() {
	s.repo.orders[2] = "Новый Заказ"
	s.Len(s.repo.orders, 2)
}

// Точка входа для раннера go test
func TestOrderTestSuite(t *testing.T) {
	suite.Run(t, new(OrderTestSuite))
}
```

ℹ️ Организация тестов через testify/suite

**`Терминал`**

```bash
go test -v -run TestOrderTestSuite order_suite_test.go
# Вывод:
# === RUN   TestOrderTestSuite
# === RUN   TestOrderTestSuite/TestAddNewOrder
# === RUN   TestOrderTestSuite/TestGetExistingOrder
# --- PASS: TestOrderTestSuite (0.00s)
#     --- PASS: TestOrderTestSuite/TestAddNewOrder (0.00s)
#     --- PASS: TestOrderTestSuite/TestGetExistingOrder (0.00s)
# PASS
```

## Под капотом

`suite.Run` использует рефлексию `reflect.TypeOf` для поиска всех экспортируемых методов структуры, начинающихся со слова `Test`, и запускает каждый из них как именованный подтест `t.Run`.

## Подводные камни

Забывать объявлять запускающую функцию `func TestXxxSuite(t *testing.T) { suite.Run(...) }`: без неё раннер `go test` не увидит тесты сьюта.

## На собеседовании

**Вопрос с собеседования:** «Когда в Go целесообразно использовать testify/suite вместо стандартных табличных тестов?»
**Ответ:** Когда тестируется сложный жизненный цикл с дорогой инициализацией (поднятие Docker-контейнеров, создание пула соединений, накатка 50 миграций). В `SetupSuite` поднимают инфраструктуру один раз, в `SetupTest` очищают таблицы, а в `TearDownSuite` гасят контейнеры.
