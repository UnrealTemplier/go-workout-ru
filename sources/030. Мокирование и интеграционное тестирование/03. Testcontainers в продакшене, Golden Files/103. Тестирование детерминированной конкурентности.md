# Тестирование детерминированной конкурентности: стресс-верификация sync.Mutex флагом -count=10000

## Условие

Напиши **"test for deterministic concurrency"**: функция с `sync.Mutex` должна давать одинаковый результат при любом порядке планирования. Запусти 10000 раз с `-count=10000`, проверь детерминизм.

## Теория

Детерминизм конкурентных структур данных:
- При конкурентном доступе сотен горутин к общему состоянию порядок выполнения недетерминирован.
- Однако итоговый результат вычислений (например, сумма балансов или размер очереди) ОБЯЗАН быть строго детерминированным.
- Запуск с флагом `-count=10000` прогоняет планировщик GMP через миллионы перестановок контекста (Context Switch), доказывая абсолютную корректность блокировок `sync.Mutex`.

## Решение по шагам

1. Создайте потокобезопасный стек на мьютексе.
2. Запустите параллельные операции Push и Pop.
3. Проверьте баланс элементов.
4. Прогоните тест стрессовым числом итераций.

## Код решения

**`concurrent_stack.go`**

```go
package main

import "sync"

type ConcurrentStack struct {
	mu    sync.Mutex
	items []int
}

func (s *ConcurrentStack) Push(val int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.items = append(s.items, val)
}

func (s *ConcurrentStack) Pop() (int, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if len(s.items) == 0 {
		return 0, false
	}
	n := len(s.items) - 1
	val := s.items[n]
	s.items = s.items[:n]
	return val, true
}

func (s *ConcurrentStack) Len() int {
	s.mu.Lock()
	defer s.mu.Unlock()
	return len(s.items)
}
```

ℹ️ Потокобезопасный стек с мьютексом

**`concurrent_stack_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

func TestConcurrentStackDeterminism(t *testing.T) {
	stack := &ConcurrentStack{}
	const ops = 100

	var wg sync.WaitGroup

	// 100 горутин делают Push
	for i := 0; i < ops; i++ {
		wg.Add(1)
		go func(v int) {
			defer wg.Done()
			stack.Push(v)
		}(i)
	}

	// 100 горутин делают Pop
	for i := 0; i < ops; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			stack.Push(999)
			_, _ = stack.Pop()
		}()
	}

	wg.Wait()

	// ДЕТЕРМИНИРОВАННЫЙ РЕЗУЛЬТАТ: длина обязана быть ровно ops (100)
	if l := stack.Len(); l != ops {
		t.Fatalf("Нарушение детерминизма! Len = %d; want %d", l, ops)
	}
}
```

ℹ️ Стресс-тест детерминизма конкурентного состояния

**`Терминал`**

```bash
# Стресс-запуск 10 000 раз:
go test -v -count=10000 -run TestConcurrentStackDeterminism concurrent_stack_test.go concurrent_stack.go
# Вывод:
# === RUN   TestConcurrentStackDeterminism
# --- PASS: TestConcurrentStackDeterminism (0.00s)
# ... (10000 итераций)
# PASS
```

## Под капотом

Если бы в коде была пропущена блокировка мьютекса, срез `items` повредился бы на первой сотне итераций с паникой `panic: runtime error: slice bounds out of range`.

## Подводные камни

Копировать структуру со встроенным мьютексом по значению: это клонирует его внутреннее битовое состояние, вызывая дедлоки (`go vet copylocks`).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Mutex от RWMutex с точки зрения предотвращения Writer Starvation?»
**Ответ:** В Go `sync.RWMutex` защищен от голодания писателей (Writer Starvation): если горутина ждет `Lock()`, последующие читатели `RLock()` блокируются до тех пор, пока писатель не завершит операцию.
