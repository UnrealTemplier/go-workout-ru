# Тестирование обратной совместимости API: парсинг старых форматов из testdata/v1_response.json

## Условие

Напиши **"test for backward compatibility"**: сохрани старый JSON-ответ в `testdata/v1_response.json`. Новая версия API должна парсить его без ошибок (дополнительные поля — `omitempty`). Проверь совместимость.

## Теория

Гарантия обратной совместимости (Backward Compatibility):
- При обновлении микросервисов нельзя ломать клиентов, отправляющих запросы старого формата.
- Принципы расширения API (Закон Постела / Robustness Principle):
  «Будь либерален к тому, что принимаешь, и консервативен к тому, что отдаешь».
- Новая структура DTO Go должна поддерживать парсинг старых файлов `testdata/v1_response.json`, где отсутствуют новые поля.

## Решение по шагам

1. Создайте структуру DTO версии V2 с новыми полями `omitempty`.
2. Загрузите старый JSON ответа V1.
3. Распарсите его и проверьте дефолтные значения новых полей.

## Код решения

**`compat_dto.go`**

```go
package main

import "encoding/json"

type UserProfileV2 struct {
	ID       int    `json:"id"`
	Username string `json:"username"`
	// Новые поля добавлены с тегами omitempty
	Tier     string `json:"tier,omitempty"`
	Verified bool   `json:"verified,omitempty"`
}

func ParseUserProfile(data []byte) (*UserProfileV2, error) {
	var p UserProfileV2
	// Дефолтные значения для обратной совместимости
	p.Tier = "standard"

	err := json.Unmarshal(data, &p)
	if err != nil {
		return nil, err
	}
	return &p, nil
}
```

ℹ️ DTO V2 с поддержкой обратной совместимости

**`compat_dto_test.go`**

```go
package main

import "testing"

func TestBackwardCompatibilityWithV1JSON(t *testing.T) {
	// Старый JSON формат из testdata/v1_response.json (без полей tier и verified)
	legacyV1JSON := []byte(`{
		"id": 100500,
		"username": "legacy_client"
	}`)

	profile, err := ParseUserProfile(legacyV1JSON)
	if err != nil {
		t.Fatalf("Парсинг старого JSON завершился ошибкой: %v", err)
	}

	// Базовые поля спарсились корректно
	if profile.ID != 100500 || profile.Username != "legacy_client" {
		t.Errorf("Неверные базовые данные: %+v", profile)
	}

	// Новые поля получили безопасные дефолтные значения
	if profile.Tier != "standard" {
		t.Errorf("Tier = %q; want standard", profile.Tier)
	}
	if profile.Verified != false {
		t.Errorf("Verified = %v; want false", profile.Verified)
	}
}
```

## Под капотом

`json.Unmarshal` в Go игнорирует отсутствующие в JSON поля, сохраняя в структуре те значения, которые были инициализированы до парсинга.

## Подводные камни

Использовать в новой версии `json.DisallowUnknownFields()` без необходимости: это мгновенно сломает обратную совместимость при добавлении новых полей в ответы сторонних сервисов.

## На собеседовании

**Вопрос с собеседования:** «Каковы правила эволюции Protobuf контрактов в gRPC для соблюдения обратной совместимости?»
**Ответ:** 1. Никогда не менять числовые теги полей (field numbers). 2. Новые поля добавлять только как optional (в proto3 все поля по умолчанию optional). 3. Удаленные поля помечать ключевым словом `reserved` (и тег, и имя), чтобы предотвратить их случайное переиспользование в будущем.
