# Нагрузочное тестирование через testing.B и перцентили задержки: p50, p95, p99

## Условие

Напиши **"load test"** через `testing.B` + горутины: эмулируй 100 конкурентных пользователей, каждый делает 1000 запросов к `UserService`. Измерь latency (p50, p95, p99) через `github.com/montanaflynn/stats` или ручной расчёт.

## Теория

Оценка производительности и SLA в микросервисах:
- Среднее время (Average / Mean) скрывает проблемы: если 99 запросов выполнились за 1 мс, а один завис на 10 секунд, среднее будет казаться отличным (~100 мс).
- В BigTech производительность оценивают строго по **перцентилям latency**:
  - **p50 (Медиана):** время ответа для 50% пользователей.
  - **p95:** время ответа для 95% пользователей.
  - **p99:** худшие 1% запросов (хвостовая задержка / Tail Latency).

## Решение по шагам

1. Напишите бенчмарк с параллельными горутинами.
2. Сохраните длительности задержек в срез.
3. Отсортируйте срез и вычислите перцентили p50, p95 и p99.

## Код решения

**`latency_bench_test.go`**

```go
package main

import (
	"math/rand"
	"sort"
	"sync"
	"testing"
	"time"
)

func SimulatedServiceCall() time.Duration {
	start := time.Now()
	// Симуляция вариативности ответа от 1 до 10 мс, редкие всплески до 50 мс
	delay := time.Duration(1+rand.Intn(9)) * time.Millisecond
	if rand.Intn(100) == 0 {
		delay = 50 * time.Millisecond // Всплеск (хвост задержки)
	}
	time.Sleep(delay)
	return time.Since(start)
}

func TestCalculateLatencyPercentiles(t *testing.T) {
	const concurrency = 20
	const requestsPerWorker = 50

	var mu sync.Mutex
	latencies := make([]time.Duration, 0, concurrency*requestsPerWorker)

	var wg sync.WaitGroup
	for i := 0; i < concurrency; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			local := make([]time.Duration, 0, requestsPerWorker)
			for j := 0; j < requestsPerWorker; j++ {
				local = append(local, SimulatedServiceCall())
			}
			mu.Lock()
			latencies = append(latencies, local...)
			mu.Unlock()
		}()
	}
	wg.Wait()

	// Сортировка для вычисления перцентилей
	sort.Slice(latencies, func(i, j int) bool {
		return latencies[i] < latencies[j]
	})

	total := len(latencies)
	p50 := latencies[total*50/100]
	p95 := latencies[total*95/100]
	p99 := latencies[total*99/100]

	t.Logf("=== LATENCY SLA REPORT (%d запросов) ===", total)
	t.Logf("p50 (Медиана): %v", p50)
	t.Logf("p95:          %v", p95)
	t.Logf("p99:          %v", p99)

	if p50 > 15*time.Millisecond {
		t.Errorf("p50 превышает SLA (15 мс): %v", p50)
	}
}
```

ℹ️ Расчет перцентилей задержки p50, p95, p99

## Под капотом

Перцентиль p99 выявляет задержки, вызванные паузами сборщика мусора (GC Stop-The-World) и блокировками очередей netpoller под конкурентной нагрузкой.

## Подводные камни

Использовать общий мьютекс внутри замеряемого интервала: время ожидания мьютекса попадет в замер latency.

## На собеседовании

**Вопрос с собеседования:** «Почему в HighLoad системах ориентируются на p99 и p99.9, а не на среднее значение (Mean)?»
**Ответ:** Если страница маркетплейса делает 100 параллельных микросервисных запросов для сборки витрины, вероятность того, что пользователь столкнется с p99 задержкой хотя бы одного сервиса, составляет \(1 - (0.99)^{100} \approx 63.4\%\). То есть 63% пользователей ощутят на себе именно хвостовую задержку!
