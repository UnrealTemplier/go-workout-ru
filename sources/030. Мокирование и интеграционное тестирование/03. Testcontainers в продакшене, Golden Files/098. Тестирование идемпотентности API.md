# Тестирование идемпотентности API: предотвращение дубликатов при повторных вызовах

## Условие

Напиши **"test for idempotency"**: функция `CreateUser` должна быть идемпотентной при повторном вызове с теми же данными. Проверь, что второй вызов не создаёт дубликат (или возвращает тот же ID).

## Теория

Идемпотентность (Idempotency) в HighLoad архитектуре:
- Из-за сетевых сбоев клиенты и брокеры сообщений часто повторяют запросы (At-Least-Once Delivery).
- Метод `CreateUser(id, email)` ОБЯЗАН быть идемпотентным:
  1. При первом вызове: пользователь создается, возвращается `id`.
  2. При повторном идентичном вызове: дубликат НЕ создается, возвращается существующий `id` без ошибки!
- Тест проверяет вызов функции дважды подряд и аудит общего количества записей в хранилище.

## Решение по шагам

1. Реализуйте идемпотентное создание пользователя.
2. Вызовите метод дважды с одинаковым `IdempotencyKey`.
3. Убедитесь, что ID совпадает.
4. Проверьте, что в хранилище осталась ровно одна запись.

## Код решения

**`idempotent_service.go`**

```go
package main

import (
	"sync"
)

type IdempotentUserService struct {
	mu           sync.Mutex
	userByEmail  map[string]int
	nextID       int
	TotalRecords int
}

func NewIdempotentUserService() *IdempotentUserService {
	return &IdempotentUserService{
		userByEmail: make(map[string]int),
		nextID:      1,
	}
}

func (s *IdempotentUserService) CreateUser(email string) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Идемпотентная проверка: если пользователь уже есть, возвращаем существующий ID
	if existingID, found := s.userByEmail[email]; found {
		return existingID
	}

	id := s.nextID
	s.nextID++
	s.userByEmail[email] = id
	s.TotalRecords++
	return id
}
```

ℹ️ Идемпотентный сервис создания пользователей

**`idempotent_service_test.go`**

```go
package main

import "testing"

func TestCreateUserIdempotency(t *testing.T) {
	service := NewIdempotentUserService()

	email := "idempotent@ya.ru"

	// 1. Первый вызов (создание)
	id1 := service.CreateUser(email)
	if id1 <= 0 {
		t.Fatalf("Невалидный id: %d", id1)
	}

	// 2. Повторный вызов с теми же данными (retry)
	id2 := service.CreateUser(email)

	// Идемпотентность: ID обязаны совпадать!
	if id1 != id2 {
		t.Errorf("Нарушение идемпотентности: id1=%d, id2=%d", id1, id2)
	}

	// Сайд-эффект: в базе должна быть ровно 1 запись, а не 2!
	if service.TotalRecords != 1 {
		t.Errorf("TotalRecords = %d; want 1 (создан дубликат!)", service.TotalRecords)
	}
}
```

## Под капотом

В SQL идемпотентность реализуется через конструкцию `INSERT INTO users (email) VALUES ($1) ON CONFLICT (email) DO UPDATE SET updated_at = NOW() RETURNING id`.

## Подводные камни

Возвращать ошибку при повторном вызове: если клиент упал по таймауту, он повторит запрос; возвращение ошибки 409 Conflict вместо 200/201 со старым ID сломает клиентский retry.

## На собеседовании

**Вопрос с собеседования:** «Как реализуется заголовок Idempotency-Key в платежных API (Stripe, Ozon)?»
**Ответ:** Клиент генерирует UUID и передает заголовок `Idempotency-Key: uuid`. Сервис проверяет наличие ключа в Redis. Если ключ найден — возвращает сохраненный кэшированный ответ без повторного списания денег. Если нет — берет блокировку, проводит платеж, сохраняет ответ в Redis на 24 часа и отдает клиенту.
