# Профилирование 1 млн мелких объектов в pprof heap

## Условие

Создайте программу, которая аллоцирует 1 млн маленьких объектов (`struct{ a, b int }`). Снимите `go tool pprof` (heap). Объясните, почему в профиле видны «span» размером 8, 16, 32 байта.

## Теория

Структура `struct{ a, b int }` на 64-битной архитектуре занимает ровно:
$$2 \times 8 = 16 \text{ байт}$$
При создании 1 000 000 таких структур в куче:
1. Аллокатор Go сопоставляет 16 байт с **Size Class 2 (16 байт)**.
2. В куче аллоцируются спаны класса 16 байт. В одном 8 КБ спане помещается ровно:
   $$8192 / 16 = 512 \text{ объектов}$$
3. Суммарно для 1 млн объектов требуется около \(1\,000\,000 / 512 \approx 1953\) спанов.
4. В профиле `pprof heap` отчетливо видно распределение памяти по соответствующим спанам и классам размеров.

## Решение по шагам

1. Создайте 1 миллион структур `struct{ a, b int }` в куче.
2. Сохраните профиль кучи через `pprof.WriteHeapProfile`.
3. Откройте профиль в консольном `pprof` и найдите строку функции создания объектов.

## Код решения

**`million_objects.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
	"time"
	"unsafe"
)

type Pair struct {
	A int
	B int
}

func main() {
	fmt.Printf("Размер структуры Pair: %d байт (Size Class 2 в Go)\n", unsafe.Sizeof(Pair{}))

	const count = 1_000_000
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// Аллоцируем 1 млн маленьких объектов
	slice := make([]*Pair, count)
	for i := 0; i < count; i++ {
		slice[i] = &Pair{A: i, B: i * 2}
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("Выделено памяти: %d МБ\n", (m2.HeapAlloc-m1.HeapAlloc)/(1024*1024))
	fmt.Printf("Всего Mallocs  : %d\n", m2.Mallocs-m1.Mallocs)

	// Сохраняем heap profile
	f, err := os.Create("million.pprof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := pprof.WriteHeapProfile(f); err != nil {
		panic(err)
	}

	fmt.Println("Профиль сохранен в million.pprof")
	runtime.KeepAlive(slice)
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Массовое создание 1 млн объектов и снятие heap profile

**`Терминал`**

```bash
go run million_objects.go
go tool pprof -top -inuse_space million.pprof
```

## Под капотом

В `src/runtime/sizeclasses.go`:
Класс 2:
- `size = 16`
- `npages = 1` (8 КБ)
- `nelems = 512`
- `tail waste = 0 байт` (8192 делится на 16 нацело без остатка!).
Поэтому класс 16 байт является одним из самых эффективных классов в рантайме Go с 0% внутренней фрагментации.

## Подводные камни

1. Хотя сами структуры заняли 16 МБ, срез указателей `[]*Pair` на 1 млн элементов сам по себе весит 8 МБ (`1_000_000 * 8 байт`). Итого память удваивается.
2. 1 млн отдельных объектов создают колоссальную нагрузку на фазу Mark сборщика мусора, так как GC обязан обойти 1 миллион указателей.

## На собеседовании

**Вопрос с собеседования:** Как оптимизировать структуру данных для хранения 1 миллиона пар `(int, int)`, чтобы снизить расход памяти и нагрузку на GC в десятки раз?
**Ответ:** Заменить срез указателей `[]*Pair` на срез структур по значению `[]Pair`:
1. Память выделится одним монолитным куском (16 МБ) вместо 1 млн разрозненных аллокаций.
2. Поскольку в структуре `Pair` нет указателей, весь срез помечается флагом `noscan`.
3. Сборщик мусора пропустит этот срез целиком за 1 шаг, сократив паузы GC с миллисекунд до микросекунд.
