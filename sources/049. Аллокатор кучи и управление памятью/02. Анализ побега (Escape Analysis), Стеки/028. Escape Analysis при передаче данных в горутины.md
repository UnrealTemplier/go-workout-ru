# Escape Analysis при передаче данных в горутины и каналы

## Условие

**Escape analysis**: Напишите код с переменными, которые "убегают" в heap (возвращаются из функции, передаются в горутины). Используйте `go build -gcflags="-m"` для наблюдения escape analysis.

## Теория

Передача указателей между горутинами через аргументы `go func()` или через каналы `chan *T` — один из ключевых триггеров побега в кучу.

Причина побега:
1. Каждая горутина имеет собственный независимый стек (начинается с 2 КБ).
2. Стек родительской горутины может завершиться и быть освобожден (или вырасти и переместиться) в любой произвольный момент времени независимо от дочерней горутины.
3. Компилятор не может гарантировать, что родительская функция не завершится до того, как дочерняя горутина прочитает данные по указателю.
4. Поэтому **любой указатель, переданный в другую горутину, гарантированно вытесняется в кучу**.

## Решение по шагам

1. Напишите функцию, передающую указатель на локальную переменную в фоновую горутину.
2. Напишите функцию, отправляющую указатель в канал.
3. Скомпилируйте с `-gcflags="-m"` и убедитесь в наличии строки `escapes to heap`.

## Код решения

**`goroutine_escape.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type Job struct {
	ID   int
	Data string
}

// 1. Побег через запуск горутины
func spawnWorker() {
	job := Job{ID: 1, Data: "async task"}
	var wg sync.WaitGroup
	wg.Add(1)

	// job утекает в кучу, так как &job передается в независимый стек горутины
	go func(j *Job) {
		defer wg.Done()
		fmt.Printf("Worker processing job: %d\n", j.ID)
	}(&job)

	wg.Wait()
}

// 2. Побег через отправку указателя в канал
func sendThroughChannel(ch chan<- *Job) {
	localJob := Job{ID: 2, Data: "channel task"}
	// localJob утекает в кучу, так как получатель канала находится в неизвестном стеке
	ch <- &localJob
}

func main() {
	spawnWorker()

	ch := make(chan *Job, 1)
	sendThroughChannel(ch)
	received := <-ch
	fmt.Printf("Received job from channel: %d\n", received.ID)
}
```

**`Терминал`**


## Под капотом

В графе SSA компилятора:
Операция `go func(...)` транслируется в `runtime.newproc`.
Параметры горутины копируются в фрейм создания. Если среди параметров есть указатель на локальную переменную текущей функции, ребро графа связывает локальную переменную с глобальным контекстом планировщика (`EscScopeHeap`).
Аналогично операция отправки в канал `runtime.chansend` рассматривается компилятором как потенциальная передача в параллельный поток выполнения.

## Подводные камни

1. Передача структур по значению через канал (`chan Job` вместо `chan *Job`) для небольших объектов позволяет избежать аллокации в куче! Данные просто копируются в кольцевой буфер `hchan`.
2. Передача указателей на переменные цикла в горутину `go func() { ...(&v) }` приводит не только к аллокации в куче, но и к классическому Data Race.

## На собеседовании

**Вопрос с собеседования:** Что эффективнее передавать через канал: `chan T` (по значению) или `chan *T` (по указателю)?
**Ответ:** 
- Если структура небольшая (до 64–128 байт), эффективнее передавать `chan T` по значению: данные копируются напрямую внутри кольцевого буфера канала без единой аллокации в куче и без создания работы для сборщика мусора.
- Если структура крупная (> 512 байт), копирование байтов в буфер канала становится дорогим, и предпочтительнее передавать `chan *T` по указателю (желательно используя `sync.Pool` для переиспользования памяти).
