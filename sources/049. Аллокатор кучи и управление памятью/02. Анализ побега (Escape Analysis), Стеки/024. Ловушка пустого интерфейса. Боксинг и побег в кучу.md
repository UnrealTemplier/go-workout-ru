# Ловушка пустого интерфейса: Боксинг и побег в кучу

## Условие

**Ловушка пустого интерфейса**: Передай простую локальную переменную типа `int` в `fmt.Println(a)`. Запусти Escape Analysis (`-m`). Ты увидишь, что переменная "сбегает" в кучу. Почему? Потому что `Println` принимает `interface{}` (any), а передача значения в интерфейс почти всегда требует аллокации в куче на этапе компиляции.

## Теория

Передача конкретного значения в параметр типа `interface{}` (или `any`) называется **упаковкой (Boxing / Interface Boxing)**.

Интерфейс в рантайме Go представляется структурой `eface`:
```go
type eface struct {
    _type *_type         // указатель на метаданные типа
    data  unsafe.Pointer // указатель на сами данные
}
```
Поскольку поле `data` является **указателем**, компилятор обязан передать туда адрес в памяти.
Если размер переменной больше размера машинного слова (или компилятор не может доказать, что вызываемая функция не сохранит этот указатель на будущее), компилятор вынужден:
1. Выделить память в куче (`runtime.convT64`, `runtime.convTstring` и т.д.).
2. Скопировать значение со стека в эту новую ячейку памяти кучи.
3. Поместить адрес кучи в `eface.data`.

Функция `fmt.Println(a ...any)` принимает срез пустых интерфейсов, поэтому вызов `fmt.Println(x)` гарантированно отправляет `x` в кучу!

## Решение по шагам

1. Напишите функцию, передающую `int` в функцию с параметром `int` (без интерфейса).
2. Напишите функцию, передающую `int` в `fmt.Println`.
3. Скомпилируйте с `go build -gcflags="-m"` и сравните отчеты Escape Analysis.
4. Исследуйте вызовы функций `runtime.convT*` в ассемблере.

## Код решения

**`interface_trap.go`**

```go
package main

import "fmt"

// 1. Быстрая функция без интерфейса: останется на стеке/регистрах
//go:noinline
func fastPrint(x int) {
	_ = x
}

// 2. Функция, принимающая any: провоцирует boxing
//go:noinline
func anyPrint(x any) {
	_ = x
}

func main() {
	num := 42

	// Без боксинга: num на стеке
	fastPrint(num)

	// Ловушка интерфейса: num аллоцируется в куче через runtime.convT64
	anyPrint(num)

	// Стандартный fmt.Println: двойной побег (аргумент + срез ...any)
	fmt.Println(num)
}
```

ℹ️ Сравнение прямой передачи и боксинга в interface{} (any)

**`Терминал`**

```bash
go build -gcflags="-m" interface_trap.go
```

## Под капотом

В ассемблере функции `main`:
При вызове `anyPrint(num)` компилятор генерирует:
```text
MOVQ $42, AX
CALL runtime.convT64(SB)  ; аллоцирует 8 байт в mcache кучи!
MOVQ AX, (SP)             ; передача адреса в eface.data
CALL main.anyPrint(SB)
```
Функция `runtime.convT64` из `src/runtime/iface.go` выделяет 8-байтный слот из `mcache.alloc` (класс 8 байт) и записывает туда число 42. Каждое логирование в горячем цикле порождает мусор в куче!

## Подводные камни

1. Логирование через `log.Printf` или `fmt.Sprintf` внутри циклов с миллионами итераций — классическая причина падения RPS в 5–10 раз из-за интерфейсного боксинга.
2. В Go 1.21+ появились специализированные логгеры (например, `log/slog` с типом `slog.Int`), позволяющие логировать примитивы без выделения памяти в куче.

## На собеседовании

**Вопрос с собеседования:** Почему высокопроизводительные библиотеки логирования (Uber Zap, Zerolog) избегают использования `interface{}` и `fmt.Sprintf`?
**Ответ:** Потому что передача аргументов через `interface{}` приводит к Interface Boxing: на каждое логируемое число, булевый флаг или структуру компилятор Go вызывает `runtime.convT*`, выделяя память в куче. Zap и Zerolog используют типизированные методы (`zap.Int("id", 42)`), которые пишут бинарные данные напрямую в байтовый кольцевой буфер без боксинга и с нулевыми аллокациями в куче (Zero Allocation Logging).
