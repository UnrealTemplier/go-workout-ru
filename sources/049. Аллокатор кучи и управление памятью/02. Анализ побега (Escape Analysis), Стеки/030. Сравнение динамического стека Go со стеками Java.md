# Сравнение динамического стека Go со стеками Java и C++

## Условие

**Stack allocation**: Изучите, как Go аллоцирует стеки горутин (начальный размер 2KB, динамически растёт/сжимается). Сравните с фиксированными стеками в Java/C++.

## Теория

Сравнение моделей работы со стеком:

| Характеристика | Go Goroutines | C++ (pthreads) / Java Threads |
| :--- | :--- | :--- |
| **Начальный размер** | **2 КБ** (2048 байт) | **1 МБ – 8 МБ** (фиксированный) |
| **Модель роста** | Динамический непрерывный стек (x2 при нехватке) | Фиксированный стек с Guard Page |
| **Память на 100k потоков**| \(\approx \mathbf{200 \text{ МБ}}\) | \(\approx \mathbf{100 \text{ ГБ}}\) (невозможно запустить!) |
| **Сжатие стека** | Да (GC ужимает вдвое, если занято \(< 1/4\)) | Нет (память удерживается процессом) |
| **Переполнение стека** | Плавное удвоение (до 1 ГБ) | Падение `SIGSEGV` / `StackOverflowError` |

Благодаря 2 КБ динамическому стеку один Go-процесс может легко удерживать сотни тысяч активных горутин на обычном ноутбуке.

## Решение по шагам

1. Напишите код, запускающий 50 000 легковесных горутин.
2. Замерьте суммарное потребление памяти через `runtime.MemStats`.
3. Рассчитайте фактический расход памяти на один стек горутины.

## Код решения

**`stack_comparison.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func main() {
	const goroutines = 50_000

	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	var wg sync.WaitGroup
	wg.Add(goroutines)
	release := make(chan struct{})

	// Запускаем 50 000 горутин со стартовым 2 КБ стеком
	for i := 0; i < goroutines; i++ {
		go func() {
			wg.Done()
			<-release // удерживаем горутину спящей
		}()
	}

	wg.Wait()
	runtime.ReadMemStats(&m2)

	stackBytes := m2.StackInuse - m1.StackInuse
	fmt.Printf("=== Сравнение стеков памяти ===\n")
	fmt.Printf("Запущено горутин: %d\n", goroutines)
	fmt.Printf("Память под стеки (StackInuse): %d МБ\n", stackBytes/(1024*1024))
	fmt.Printf("Средний размер стека: %.2f КБ на горутину\n", float64(stackBytes)/goroutines/1024)
	fmt.Printf("\nДля сравнения: 50 000 потоков Java/C++ с 2 МБ стеком потребовали бы 100 ГБ RAM!\n")

	close(release)
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Замер потребления памяти 50 000 горутин со стартовыми стеками по 2 КБ

**`Терминал`**

```bash
go run stack_comparison.go
```

## Под капотом

Стек горутины выделяется из пула стеков рантайма (`src/runtime/stack.go`).
Рантайм держит многоуровневый пул кэшей свободных стеков для размеров 2 КБ, 4 КБ, 8 КБ, 16 КБ, 32 КБ.
При завершении горутины её 2 КБ стек не возвращается в ОС, а кладется в локальный список `p.gFree.stack`, готовый к повторному использованию за несколько наносекунд.

## Подводные камни

1. Если горутина временно потребовала большой стек (например, 1 МБ при парсинге XML), а затем вернулась в легкий режим, сборщик мусора сожмет её стек обратно только в следующем цикле GC при условии `used < capacity / 4`.
2. Рекурсивные функции без базового случая переполнят стек до лимита 1 ГБ, после чего процесс упадет.

## На собеседовании

**Вопрос с собеседования:** Как устроен механизм сжатия стека (Stack Shrinking) в Go и почему он необходим?
**Ответ:** Если горутина временно выполнила глубокий вызов (раздув стек, например, до 64 КБ), а затем вернулась в режим ожидания сообщений из канала, удержание 64 КБ на миллион горутин привело бы к исчерпанию десятков гигабайт памяти. Поэтому во время фазы Stop-The-World или конкурентного обхода GC проверяет: если фактическое использование стека горутины меньше 1/4 его емкости, рантайм выделяет новый стек в 2 раза меньше, копирует фреймы через `copystack` и возвращает лишнюю память в пул.
