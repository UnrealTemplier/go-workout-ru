# Аллокация крупных объектов Large Objects (> 32 КБ) в куче

## Условие

**Аллокация крупных объектов (Large Objects)**: Объясните в комментариях, как Go обрабатывает аллокацию крупных объектов (размером более 32 КБ). Почему такие объекты аллоцируются напрямую в глобальной куче `mheap`, полностью минуя локальные уровни кэшей `mcache` и `mcentral`.

### Исходная формулировка

**Аллокация крупных объектов (Large Objects)**: Объясните в комментариях, как Go обрабатывает аллокацию крупных объектов (размером более 32 КБ). Почему такие объекты аллоцируются напрямую в глобальной куче `mheap`, полностью минуя локальные уровни кэшей `mcache` и `mcentral`.

## Теория

В рантайме Go действует строгое разделение логики аллокации по пороговому значению **`maxSmallSize = 32768` байт (32 КБ)**.

Архитектурная причина, почему объекты \(> 32\) КБ минуют `mcache` и `mcentral`:
1. **Экономия памяти:** В Go есть \(P\) логических процессоров (например, 64 ядра). Если бы каждый \(P\) кэшировал крупные объекты (по 100 КБ, 1 МБ, 10 МБ) в своем `mcache`, сотни мегабайт или гигабайты памяти простаивали бы в локальных кэшах без дела.
2. **Низкая частота аллокаций:** Статистически объекты \(> 32\) КБ выделяются в тысячи раз реже, чем мелкие структуры. Поэтому оверхед на захват глобальной блокировки `mheap.lock` на несколько микросекунд не оказывает негативного влияния на общую пропускную способность системы.
3. **Прямое выделение страниц:** Крупный объект представляет собой непрерывный блок из целого числа страниц по 8 КБ (\(N = \lceil \text{size} / 8192 \rceil\)). Аллокатор `pageAlloc` просто находит нужный непрерывный интервал страниц в арене.

## Решение по шагам

1. Напишите программу, сравнивающую выделение мелкого объекта (1 КБ) и крупного (64 КБ).
2. Зафиксируйте в комментариях к коду путь выполнения `mallocgc` для объектов более 32 КБ.
3. Продемонстрируйте вычисление необходимого числа 8 КБ страниц.

## Код решения

**`large_direct.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

// Мелкий объект (пойдет в mcache, класс 1024B)
type SmallBlock struct {
	Data [1024]byte
}

// Крупный объект (64 КБ > 32 КБ, пойдет напрямую в mheap)
type LargeBlock struct {
	Data [64 * 1024]byte
}

func main() {
	fmt.Printf("Порог maxSmallSize в Go: 32768 байт (32 КБ)\n")
	fmt.Printf("Размер SmallBlock: %d байт (Small Object -> mcache)\n", unsafe.Sizeof(SmallBlock{}))
	fmt.Printf("Размер LargeBlock: %d байт (Large Object -> mheap)\n\n", unsafe.Sizeof(LargeBlock{}))

	var m1, m2 runtime.MemStats
	runtime.ReadMemStats(&m1)

	// Выделение LargeBlock: минует mcache и mcentral
	// Вычисляется npages = 65536 / 8192 = 8 страниц
	large := new(LargeBlock)
	large.Data[0] = 1

	runtime.ReadMemStats(&m2)
	fmt.Printf("Выделен Large Object: адрес %p\n", large)
	fmt.Printf("Прирост HeapAlloc: %d КБ\n", (m2.HeapAlloc-m1.HeapAlloc)/1024)
	fmt.Printf("Число задействованных 8 КБ страниц: %d страниц\n", len(large.Data)/8192)

	runtime.KeepAlive(large)
}
```

ℹ️ Прямое выделение LargeBlock в куче mheap минуя mcache

**`Терминал`**

```bash
go run large_direct.go
```

## Под капотом

В `src/runtime/malloc.go`:
```go
if size > maxSmallSize {
    var s *mspan
    systemstack(func() {
        s = largeAlloc(size, needzero, noscan)
    })
    s.freeindex = 1
    s.allocCount = 1
    x = unsafe.Pointer(s.base())
    size = s.elemsize
    // регистрация объекта
    return x
}
```
Вызов выполняется на системном стеке `systemstack`, так как требуется переключение на `g0` для безопасного захвата `mheap_.lock` и манипуляций с Radix Tree страниц.

## Подводные камни

1. Если в цикле с высокой частотой выделять слайсы размером 33 КБ (всего на 1 КБ больше `maxSmallSize`), это приведет к деградации производительности из-за конкуренции за `mheap_.lock`.
2. Если можно уменьшить размер буфера до 32 КБ, он начнет обслуживаться кэшем `mcache` без блокировок.

## На собеседовании

**Вопрос с собеседования:** В высоконагруженном сетевом сервисе буфер чтения пакетов имеет размер 64 КБ. Сервер страдает от задержек аллокатора. Какую оптимизацию размера буфера вы предложите?
**Ответ:** 
1. Если размер пакетов в 90% случаев меньше 32 КБ, уменьшить рабочий буфер до 32 КБ (`maxSmallSize`), чтобы аллокации обслуживались локальным кэшем `mcache` без единой блокировки.
2. Использовать `sync.Pool` для пула 64 КБ буферов, полностью исключив обращения к `mheap` в цикле обработки запросов.
