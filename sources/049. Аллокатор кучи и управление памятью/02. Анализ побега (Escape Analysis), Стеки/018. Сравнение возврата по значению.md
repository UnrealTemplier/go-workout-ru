# Сравнение возврата по значению и по указателю в Escape Analysis

## Условие

**Escape Analysis (Анализ побега)**: Стек быстрый (выделение памяти сводится к сдвигу указателя регистра CPU), куча — медленная. Напиши две функции: одна возвращает `int`, другая `*int`. Скомпилируй с флагом `go build -gcflags="-m"`. Изучи вывод компилятора: найди фразу `escapes to heap`.

## Теория

Размещение данных на стеке и в куче имеет принципиально разные накладные расходы:
- **Стек (Stack Allocation):**
  - Выделение памяти: ровно одна ассемблерная инструкция вычитания из указателя стека `SUBQ $N, SP`. Занимает \(\approx 0\) наносекунд.
  - Очистка: сдвиг `SP` обратно при возврате `ADDQ $N, SP`.
  - Нулевая нагрузка на сборщик мусора GC.
- **Куча (Heap Allocation):**
  - Вызов `runtime.newobject` / `mallocgc`.
  - Поиск слота в `mcache`, обновление битовых карт `allocBits`.
  - Учет в графе объектов, барьеры записи и сканирование в фазе GC Mark.
  - Занимает 10–30 наносекунд на аллокацию + скрытые расходы на сборку мусора.

Когда функция возвращает примитив `int` по значению, значение просто копируется через регистр процессора `AX`. Когда возвращается `*int`, локальная переменная не может умереть вместе со стеком и «убегает» в кучу.

## Решение по шагам

1. Напишите функцию `valFunc() int`, создающую локальную переменную и возвращающую её по значению.
2. Напишите функцию `ptrFunc() *int`, возвращающую указатель `&x`.
3. Скомпилируйте с флагом `go build -gcflags="-m -l"` (флаг `-l` отключает инлайнинг функций для чистоты эксперимента).
4. Проверьте вывод компилятора на наличие строки `escapes to heap`.

## Код решения

**`escape_simple.go`**

```go
package main

import "fmt"

//go:noinline
func valFunc() int {
	x := 42
	return x // x передается по значению через регистр CPU, остается на стеке
}

//go:noinline
func ptrFunc() *int {
	x := 42
	return &x // &x escapes to heap: компилятор переносит x в кучу
}

func main() {
	v := valFunc()
	p := ptrFunc()

	fmt.Printf("Значение со стека: %d\n", v)
	fmt.Printf("Значение из кучи : %d (адрес: %p)\n", *p, p)
}
```

ℹ️ Сравнение передачи по значению и побега указателя в кучу

**`Терминал`**

```bash
go build -gcflags="-m -l" escape_simple.go
```

## Под капотом

В ассемблерном коде (`go build -gcflags="-S -l"`):
- В функции `valFunc`:
  ```text
  MOVL $42, AX  ; помещаем 42 в регистр возврата
  RET           ; мгновенный возврат
  ```
- В функции `ptrFunc`:
  ```text
  LEAQ type:int(SB), AX
  CALL runtime.newobject(SB) ; аллокация в mcache кучи!
  MOVQ $42, (AX)             ; запись значения в кучу
  RET
  ```
Вызов `runtime.newobject` требует сотен процессорных тактов против одной инструкции `MOVL`!

## Подводные камни

1. Преждевременная «оптимизация» передачей указателей на мелкие структуры (`*struct{ a, b int }`) вместо передачи по значению часто ухудшает производительность сервиса, вызывая лишние аллокации в куче и нагружая GC.
2. Передавайте по указателю только если: 1) объект действительно большой (> 64 байт); 2) метод обязан мутировать состояние структуры; 3) структура содержит мьютекс `sync.Mutex`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go правило «передавать по указателю всегда быстрее» является опасным заблуждением?
**Ответ:** Передача по указателю часто заставляет объект «убежать» в кучу (Escape to heap). Выделение в куче требует работы аллокатора, ухудшает кэш-локальность (L1/L2 cache misses) из-за разыменования указателей и многократно увеличивает накладные расходы сборщика мусора на сканирование графа объектов. Передача небольших структур (до 64–128 байт) по значению происходит прямо на регистрах CPU без единой аллокации в памяти.
