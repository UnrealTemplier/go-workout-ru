# Профилирование памяти: inuse_space vs alloc_space в pprof

## Условие

**Memory profiling**: Используйте `pprof heap profile` с флагом `-inuse_space` и `-alloc_space`. Изучите разницу: "что сейчас в памяти" vs "что было аллоцировано за всё время".

## Теория

Профиль кучи `pprof heap` содержит 4 различных представления (Sample Types):
1. **`inuse_space`:** Объем виртуальной памяти в байтах, который занят живыми (достижимыми) объектами **в момент снятия профиля**. Идеален для расследования утечек памяти (Memory Leaks) и поиска причин раздувания RSS.
2. **`alloc_space`:** Суммарный объем памяти в байтах, который был выделен функцией **за всё время работы приложения** (включая уже собранный мусор). Идеален для оптимизации производительности, снижения нагрузки на GC и уменьшения частоты сборок мусора.
3. **`inuse_objects`:** Количество живых объектов на момент снятия профиля.
4. **`alloc_objects`:** Суммарное количество созданных объектов за всё время.

## Решение по шагам

1. Напишите сервис с двумя функциями: одна удерживает долгоживущий буфер (`inuse_space`), другая генерирует временный мусор в цикле (`alloc_space`).
2. Сохраните профиль кучи с помощью `pprof.WriteHeapProfile`.
3. Исследуйте профиль с переключением флагов `-inuse_space` и `-alloc_space`.

## Код решения

**`pprof_spaces.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
	"time"
)

// Долгоживущая память: останется в inuse_space
var persistentData [][]byte

func retainMemory() {
	fmt.Println("Выделяем 20 МБ долгоживущей памяти...")
	for i := 0; i < 20; i++ {
		persistentData = append(persistentData, make([]byte, 1024*1024))
	}
}

// Временный мусор: много alloc_space, но 0 в inuse_space
func generateGarbage() {
	fmt.Println("Генерируем 100 МБ временного мусора...")
	for i := 0; i < 100; i++ {
		tmp := make([]byte, 1024*1024)
		tmp[0] = 1
		_ = tmp
	}
}

func main() {
	retainMemory()
	generateGarbage()

	// Принудительно вызываем GC, чтобы временный мусор ушел из inuse
	runtime.GC()

	f, err := os.Create("spaces.pprof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := pprof.WriteHeapProfile(f); err != nil {
		panic(err)
	}

	fmt.Println("Профиль сохранен в spaces.pprof.")
	fmt.Println("Сравните вывод команд:")
	fmt.Println("  go tool pprof -top -inuse_space spaces.pprof")
	fmt.Println("  go tool pprof -top -alloc_space spaces.pprof")

	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Сравнение долгоживущей памяти и суммарных аллокаций в pprof

**`Терминал`**

```bash
go run pprof_spaces.go
go tool pprof -top -inuse_space spaces.pprof
go tool pprof -top -alloc_space spaces.pprof
```

## Под капотом

Сборщик профиля кучи рантайма (`src/runtime/mprof.go`):
В хеш-таблице `mbuckets` для каждого стектрейса аллокации хранятся 4 счетчика:
- `alloc_bytes`, `alloc_objects`: увеличиваются при каждом вызове `mallocgc`.
- `free_bytes`, `free_objects`: увеличиваются при освобождении объекта в фазе Sweep GC.
- `inuse_bytes = alloc_bytes - free_bytes`.
- `inuse_objects = alloc_objects - free_objects`.
При вызове `WriteHeapProfile` эти счетчики упаковываются в стандартный gzip proto-буфер.

## Подводные камни

1. Оптимизация только по `inuse_space` может скрыть факт того, что функция выделяет 10 ГБ/сек временных объектов, вызывая троттлинг CPU сборщиком мусора.
2. Оптимизация только по `alloc_space` не поможет решить проблему утечки памяти, если утекает всего 10 КБ в минуту.

## На собеседовании

**Вопрос с собеседования:** Если сервис периодически убивается по OOM в Kubernetes, но в профиле `inuse_space` занято всего 200 МБ из лимита в 1 ГБ, куда смотреть в первую очередь?
**Ответ:** 
1. Проверить `alloc_space` и темп аллокаций: при высокой скорости создания объектов GC может отставать (GC Debt), вызывая кратковременный всплеск потребления памяти до следующей сборки.
2. Проверить фрагментацию кучи через `runtime.MemStats`: разницу между `HeapAlloc` (200 МБ) и `HeapInuse`/`HeapSys` (1 ГБ).
3. Проверить утечки памяти вне кучи Go: память Cgo, дескрипторы сокетов или память рантайма (стеки горутин).
