# Моделирование фрагментации памяти Pattern Allocation

## Условие

**Memory fragmentation**: Создайте паттерн аллокаций, вызывающий фрагментацию (множество мелких аллокаций с последующим освобождением через одного). Изучите влияние на memory usage.

## Теория

Фрагментация кучи возникает, когда чередующиеся аллокации и освобождения памяти приводят к тому, что спаны не могут быть освобождены целиком.

Сценарий «дырявой кучи» (Checkerboard pattern):
1. Программа аллоцирует \(N\) мелких объектов (например, 100 000 объектов класса 32 байта).
2. Затем программа обнуляет ссылки на каждый **четный** объект (\(0, 2, 4, 6 \dots\)), оставляя нечетные живыми.
3. В результате:
   - Фактически полезных данных осталось ровно 50%.
   - Однако в каждом `mspan` ровно половина слотов занята.
   - Ни один `mspan` не освобожден целиком, поэтому ни одна страница не может быть возвращена в `mheap` или ОС!
   - Метрика `HeapInuse` остается на уровне 100%, демонстрируя эффект фрагментации.

## Решение по шагам

1. Выделите массив из 100 000 объектов.
2. Замерьте `HeapAlloc` и `HeapInuse`.
3. Освободите ровно 50% объектов через одного и вызовите `runtime.GC()`.
4. Сравните изменение `HeapAlloc` (упал вдвое) и `HeapInuse` (остался прежним из-за фрагментации).

## Код решения

**`fragmentation_demo.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

type Element struct {
	ID   int64
	Data [24]byte // 32 байта суммарно
}

func main() {
	const count = 200_000

	var m1, m2, m3 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// 1. Создаем 200k объектов
	ptrs := make([]*Element, count)
	for i := 0; i < count; i++ {
		ptrs[i] = &Element{ID: int64(i)}
	}

	runtime.ReadMemStats(&m2)
	fmt.Println("=== Фаза 1: 100% объектов создано ===")
	fmt.Printf("HeapAlloc (живые объекты): %d КБ\n", (m2.HeapAlloc-m1.HeapAlloc)/1024)
	fmt.Printf("HeapInuse (занятые спаны): %d КБ\n\n", m2.HeapInuse/1024)

	// 2. Освобождаем каждый четный элемент (50% мусора)
	for i := 0; i < count; i += 2 {
		ptrs[i] = nil
	}

	runtime.GC()
	runtime.ReadMemStats(&m3)

	fmt.Println("=== Фаза 2: 50% объектов освобождено через одного ===")
	fmt.Printf("HeapAlloc (упал вдвое!)   : %d КБ\n", (m3.HeapAlloc-m1.HeapAlloc)/1024)
	fmt.Printf("HeapInuse (спаны удерживаются): %d КБ\n", m3.HeapInuse/1024)

	waste := float64(m3.HeapInuse-(m3.HeapAlloc-m1.HeapAlloc)) / float64(m3.HeapInuse) * 100
	fmt.Printf("Потери памяти из-за фрагментации спанов: %.1f%%\n", waste)

	runtime.KeepAlive(ptrs)
}
```

ℹ️ Экспериментальная демонстрация удержания спанов при фрагментации памяти

**`Терминал`**

```bash
go run fragmentation_demo.go
```

## Под капотом

В структуре `mspan` поле `allocCount` хранит количество занятых слотов.
В фазе Sweep GC пересчитывает:
`s.allocCount = countBits(s.allocBits)`
Если `s.allocCount == 0`, спан возвращается в `mcentral.partial` или `mheap`.
Но если `s.allocCount > 0` (хотя бы 1 живой объект), спан помечается как частично занятый и остается в памяти процесса, не позволяя высвободить 8 КБ физическую страницу ОС.

## Подводные камни

1. Хранение долгоживущих кэшей в виде срезов указателей `[]*Item` с частичным удалением — главная причина фрагментации памяти в микросервисах.
2. Решение: использовать плоские слайсы структур по значению `[]Item`, циклические буферы или арены.

## На собеседовании

**Вопрос с собеседования:** Почему срез указателей `[]*MyStruct` порождает фрагментацию памяти, а срез структур `[]MyStruct` принципиально защищен от нее?
**Ответ:** В срезе указателей каждый элемент аллоцируется независимым вызовом в произвольных спанах кучи. При частичной очистке живые элементы удерживают десятки спанов по всей памяти. В срезе значений `[]MyStruct` все элементы лежат в одном едином непрерывном массиве байт. Память выделяется и освобождается одним куском, что полностью исключает фрагментацию и дает огромный выигрыш по кэш-локальности процессора.
