# Архитектура арен виртуальной памяти heapArena

## Условие

**Arena**: Go резервирует большие регионы виртуальной памяти (arenas, 64MB на 64-bit системах) для эффективного управления памятью.

## Теория

Куча `mheap` в Go не является одним сплошным неразрывным массивом памяти. Она организована как совокупность независимых регионов фиксированного размера — **Arenas (Арены)**:
- На 64-битных системах размер одной арены составляет **64 МБ** (`heapArenaBytes = 64 << 20`).
- На 32-битных системах — **4 МБ**.
- Каждая арена описывается служебной структурой `heapArena`.

Внутри структуры `heapArena` хранятся метаданные для всех 8192 страниц этой арены:
- `spans [pagesPerArena]*mspan`: массив указателей, сопоставляющий каждую страницу арены с её спаном.
- `pageMarks [pagesPerArena / 8]byte`: битовая карта страниц, содержащих живые объекты для GC.
- `pageInUse [pagesPerArena / 8]byte`: битовая карта распределенных страниц.

## Решение по шагам

1. Напишите программу, постепенно аллоцирующую память шагами по 64 МБ.
2. Отследите скачкообразный рост показателя `HeapSys` в `runtime.MemStats`.
3. Рассчитайте количество активных арен рантайма.

## Код решения

**`arena_growth.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

const arenaSize = 64 * 1024 * 1024 // 64 МБ

func main() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	fmt.Println("=== Исследование роста heapArena (шаг 64 МБ) ===")
	initialArenas := m.HeapSys / arenaSize
	fmt.Printf("Стартовый HeapSys: %d МБ (~%d арен по 64 МБ)\n\n",
		m.HeapSys/(1024*1024), initialArenas)

	var storage [][]byte

	// Выделяем память порциями, провоцируя подключение новых 64 МБ арен
	for step := 1; step <= 3; step++ {
		// Аллоцируем 70 МБ (гарантированно требует новую 64 МБ арену)
		chunk := make([]byte, 70*1024*1024)
		for i := 0; i < len(chunk); i += 4096 {
			chunk[i] = byte(step)
		}
		storage = append(storage, chunk)

		runtime.ReadMemStats(&m)
		currentArenas := m.HeapSys / arenaSize
		fmt.Printf("[Шаг %d] Выделено +70 МБ: HeapAlloc=%4d МБ | HeapSys=%4d МБ | Арен=%2d\n",
			step, m.HeapAlloc/(1024*1024), m.HeapSys/(1024*1024), currentArenas)
	}

	fmt.Println("\nВывод: HeapSys прирастает дискретными квантами арен по 64 МБ.")
	runtime.KeepAlive(storage)
}
```

ℹ️ Дискретный рост памяти кучи квантами heapArena по 64 МБ

**`Терминал`**

```bash
go run arena_growth.go
```

## Под капотом

В `src/runtime/mheap.go`:
Двухуровневый массив арен:
`arenas [1 << arenaL1Bits]*[1 << arenaL2Bits]*heapArena`
При вычислении дескриптора арены по адресу `p`:
`arenaIndex := p / heapArenaBytes`
`l1 := arenaIndex >> arenaL1Shift`
`l2 := arenaIndex & arenaL2Mask`
`ha := mheap_.arenas[l1][l2]`
Такая двухуровневая разреженная таблица (Sparse Array) позволяет адресовать гигантские адресные пространства без предварительного выделения памяти под саму таблицу метаданных.

## Подводные камни

1. Если адреса арен в виртуальной памяти фрагментированы сторонними Cgo библиотеками, Go выделяет новые арены по другим свободным адресам, что может приводить к разрывам в адресном пространстве.
2. Рост `HeapSys` происходит скачками, кратными 64 МБ, поэтому график потребления системной памяти выглядит ступенчатым.

## На собеседовании

**Вопрос с собеседования:** Почему Go перешел от единой монолитной арены к разреженным аренам (Sparse Arenas) в версии Go 1.11?
**Ответ:** До Go 1.11 рантайм требовал непрерывного адресного пространства (один гигантский кусок до 512 ГБ). В сложных средах (Cgo, контейнеры Docker с ограничениями адресов, динамические библиотеки) ядро ОС часто не могло выделить такой непрерывный виртуальный кусок из-за конфликтов адресов загрузки библиотек. Sparse Arenas позволяют куче Go собираться из множества независимых 64-мегабайтных кусочков в любых доступных местах виртуальной памяти.
