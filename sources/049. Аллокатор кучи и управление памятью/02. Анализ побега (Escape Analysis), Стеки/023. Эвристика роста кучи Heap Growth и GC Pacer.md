# Эвристика роста кучи Heap Growth и GC Pacer

## Условие

**Heap growth**: Изучите, как runtime решает, когда запрашивать больше памяти у ОС (heuristic based on GC cycles and memory usage).

## Теория

Рост кучи Go (`Heap Growth`) управляется контроллером с обратной связью — **GC Pacer** (файл `src/runtime/mgcpacer.go`).

Принцип работы:
1. В конце каждого цикла GC рантайм фиксирует объем живых данных в куче (`heap_marked`).
2. На основе параметра `GOGC` (по умолчанию 100%) рассчитывается целевой порог следующей сборки мусора (`trigger` и `goal`):
   $$\text{NextGCGoal} = \text{HeapMarked} \times \left(1 + \frac{\text{GOGC}}{100}\right)$$
3. Если приложение аллоцирует память быстрее, чем работают воркеры GC, или целевой порог превышает текущий размер арен, рантайм в функции `mheap.grow()` запрашивает новые 64 МБ арены у операционной системы.
4. Начиная с Go 1.19, в эту формулу вмешивается `GOMEMLIMIT`: при приближении к лимиту памяти Pacer игнорирует `GOGC` и запускает GC раньше, предотвращая рост кучи и спасая процесс от OOM.

## Решение по шагам

1. Напишите программу, которая циклически аллоцирует данные, измеряя динамику `NextGC` и `HeapSys`.
2. Измените целевое поведение с помощью функции `debug.SetGCPercent`.
3. Проанализируйте, как частота сборок мусора влияет на потребность в запросе новых страниц у ОС.

## Код решения

**`heap_growth.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func printHeapState(tag string) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("[%s]\n", tag)
	fmt.Printf("  HeapAlloc: %4d МБ (живые объекты)\n", m.HeapAlloc/(1024*1024))
	fmt.Printf("  NextGC   : %4d МБ (порог триггера следующего GC)\n", m.NextGC/(1024*1024))
	fmt.Printf("  HeapSys  : %4d МБ (память у ОС)\n", m.HeapSys/(1024*1024))
	fmt.Printf("  NumGC    : %4d сборок мусора\n\n", m.NumGC)
}

func main() {
	fmt.Println("=== Эвристика роста кучи (GC Pacer) ===")
	printHeapState("Старт")

	// Устанавливаем GOGC = 100 (цель = x2 от живой памяти)
	debug.SetGCPercent(100)

	// Аллоцируем 50 МБ данных, удерживая ссылки
	data := make([][]byte, 50)
	for i := 0; i < 50; i++ {
		data[i] = make([]byte, 1024*1024)
		data[i][0] = 1
	}

	runtime.GC()
	printHeapState("После аллокации 50 МБ и GC (GOGC=100)")

	// Устанавливаем агрессивный GOGC = 20 (цель = +20% от живой памяти)
	debug.SetGCPercent(20)
	runtime.GC()
	printHeapState("После переключения GOGC=20 (NextGC снизился!)")

	_ = data
}
```

ℹ️ Управление эвристикой порога NextGC и ростом кучи через debug.SetGCPercent

**`Терминал`**

```bash
go run heap_growth.go
```

## Под капотом

В функции `mheap.grow(npages uintptr)`:
1. Проверяется, есть ли свободные страницы в текущих аренах `pageAlloc`.
2. Если свободных непрерывных страниц нужного размера нет, рассчитывается объем расширения (минимум 64 МБ — размер одной арены).
3. Вызывается `sysAlloc` -> системный вызов `mmap(PROT_READ|PROT_WRITE)`.
4. Инициализируется дескриптор `heapArena` и связывается с Radix Tree свободных страниц.
5. Новые страницы помечаются в битовой карте как свободные и объединяются со смежными спанами.

## Подводные камни

1. Высокое значение `GOGC` (например, 400) снижает нагрузку на процессор, но раздувает кучу в 5 раз, что в контейнерах с жесткими лимитами памяти приведет к аварийному OOMKilled.
2. При постоянном создании разнокалиберных объектов рост `HeapSys` может происходить быстрее, чем рост `HeapAlloc`, из-за фрагментации свободных страниц внутри арен.

## На собеседовании

**Вопрос с собеседования:** Как работает механизм GC Pacer в современных версиях Go (1.19+) при одновременной установке `GOGC` и `GOMEMLIMIT`?
**Ответ:** GC Pacer вычисляет два целевых порога запуска GC: один на основе формулы `HeapMarked * (1 + GOGC/100)`, а второй — на основе оставшегося пространства до `GOMEMLIMIT`. Pacer выбирает **минимальный** из двух порогов. В результате, пока памяти много, приложение работает по правилу `GOGC`; но при приближении к `GOMEMLIMIT` частота сборок мусора плавно возрастает, удерживая память внутри лимита без падения процесса по OOM.
