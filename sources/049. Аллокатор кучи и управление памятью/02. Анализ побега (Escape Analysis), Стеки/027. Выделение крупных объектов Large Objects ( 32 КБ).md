# Выделение крупных объектов Large Objects (> 32 КБ) напрямую из mheap

## Условие

**[mheap and Arenas]**: Аллоцируй очень большой слайс (например, 100 MB). Это Large Object (> 32KB). Объясни, как `mheap` выделяет под это непрерывную арену страниц напрямую у ОС (через `mmap`).

## Теория

Объекты размером более **32768 байт (32 КБ)** классифицируются рантаймом Go как **Large Objects (Крупные объекты)**.

Механика работы с Large Objects:
1. Крупные объекты полностью исключены из локальных кэшей `mcache` и `mcentral`.
2. Запрос направляется непосредственно в глобальную кучу `mheap`.
3. Рассчитывается необходимое количество 8 КБ страниц:
   $$N_{\text{pages}} = \lceil \text{size} / 8192 \rceil$$
4. Аллокатор страниц `pageAlloc` находит в Radix Tree диапазон из \(N\) непрерывных страниц.
5. Создается индивидуальный дескриптор `mspan` специального нулевого класса (`spanclass = 0`).
6. Если диапазона страниц в существующих аренах нет, вызывается системный вызов `mmap` для выделения новых 64 МБ арен.

## Решение по шагам

1. Выделите слайс размером 100 МБ.
2. Отследите изменение системных метрик памяти через `runtime.ReadMemStats`.
3. Подтвердите, что аллокация крупного объекта не затронула счетчики `mcache` мелких классов размеров.

## Код решения

**`large_alloc.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	const size100MB = 100 * 1024 * 1024 // 100 МБ > 32 КБ

	fmt.Println("=== Аллокация Large Object (100 МБ) напрямую из mheap ===")
	fmt.Printf("До аллокации   : HeapAlloc=%d МБ | HeapSys=%d МБ\n",
		m1.HeapAlloc/(1024*1024), m1.HeapSys/(1024*1024))

	// Выделяем 100 МБ: mheap аллоцирует 12800 страниц по 8 КБ
	largeSlice := make([]byte, size100MB)
	for i := 0; i < len(largeSlice); i += 1024 * 1024 {
		largeSlice[i] = 1 // физически активируем страницы
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("После аллокации: HeapAlloc=%d МБ | HeapSys=%d МБ\n",
		m2.HeapAlloc/(1024*1024), m2.HeapSys/(1024*1024))
	fmt.Printf("Дельта HeapAlloc: %d МБ\n", (m2.HeapAlloc-m1.HeapAlloc)/(1024*1024))

	// Проверяем количество страниц
	pagesNeeded := size100MB / 8192
	fmt.Printf("Выделено страниц по 8 КБ: %d страниц непрерывного спана\n", pagesNeeded)

	runtime.KeepAlive(largeSlice)
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Прямая аллокация Large Object (100 МБ) через mheap

**`Терминал`**

```bash
go run large_alloc.go
```

## Под капотом

В `src/runtime/malloc.go`:
```go
func largeAlloc(size uintptr, needzero bool, noscan bool) *mspan {
    npages := size >> _PageShift
    if size&_PageMask != 0 {
        npages++
    }
    // Захват глобального лока кучи
    lock(&mheap_.lock)
    s := mheap_.alloc(npages, spanClass(0))
    unlock(&mheap_.lock)
    return s
}
```
Поскольку `spanClass = 0`, спан не привязан ни к одному из 67 классов размеров и существует как единичный монолитный блок памяти.

## Подводные камни

1. Захват `mheap_.lock` блокирует все остальные потоки \(M\), пытающиеся выделить крупные объекты или пополнить `mcache`. Частые аллокации объектов \(> 32\) КБ создают серьезный contention.
2. Для крупных буферов передачи данных (сеть, сжатие, дисковый I/O) обязательно используйте переиспользуемые пулы `sync.Pool`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go крупные объекты (> 32 КБ) не кэшируются в `mcache`, а выделяются каждый раз напрямую из `mheap`?
**Ответ:** Крупные объекты слишком велики, чтобы держать их в локальных кэшах \(P\): кэширование 100-мегабайтных блоков на каждом из 64 процессоров \(P\) мгновенно привело бы к исчерпанию физической памяти сервера. Кроме того, частота аллокаций крупных объектов в нормальных сервисах на порядки ниже, чем мелких, поэтому накладные расходы на обращение к `mheap` остаются пренебрежимо малы.
