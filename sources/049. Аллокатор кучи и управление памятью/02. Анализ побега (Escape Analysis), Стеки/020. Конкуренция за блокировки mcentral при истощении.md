# Конкуренция за блокировки mcentral при истощении mcache

## Условие

**[mcentral and Locks]**: Напиши программу, которая во всех горутинах на всех P аллоцирует объекты одного и того же размера. Заставь `mcache` исчерпаться, чтобы он пошел за памятью в `mcentral` (глобальный для всех P, с мьютексами). Напиши тест с `go test -race`, чтобы увидеть contention (хотя напрямую мьютексы mcentral в race не светятся, можно оценить падение пропускной способности).

## Теория

Хотя Fast-Path аллокации в `mcache` свободен от блокировок, при исчерпании свободных слотов в спане рантайм вынужден идти в Slow-Path — запрашивать новый спан из `mcentral[spc]`.

Каждый `mcentral` защищен внутренним спинлоком `mcentral.lock`.
Если сотни параллельных горутин на всех доступных \(P\) одновременно выполняют миллионы аллокаций **строго одного и того же класса размера**:
1. Их локальные `mcache` для этого класса опустошаются одновременно.
2. Все \(P\) одновременно пытаются захватить блокировку одного и того же `mcentral`.
3. Возникает аппаратный contention процессорных ядер на шине когерентности кэшей (Cache Coherence Bus contention).

## Решение по шагам

1. Напишите тест, запускающий горутины по числу ядер CPU, непрерывно аллоцирующие объекты одинакового размера (например, 128 байт).
2. Замерьте время выполнения при работе с одним общим классом размера.
3. Разбавьте аллокации объектами разных классов и оцените прирост скорости за счет распределения по разным `mcentral`.

## Код решения

**`mcentral_test.go`**

```go
package main

import (
	"runtime"
	"sync"
	"testing"
)

type TargetSize128 struct {
	Data [128]byte
}

type VariedSize1 struct {
	Data [64]byte
}

type VariedSize2 struct {
	Data [256]byte
}

// Тест 1: Все горутины долбятся в один mcentral[128]
func BenchmarkSingleSizeContention(b *testing.B) {
	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			obj := new(TargetSize128)
			runtime.KeepAlive(obj)
		}
	})
}

// Тест 2: Горутины распределяют нагрузку по разным mcentral
func BenchmarkDistributedSizes(b *testing.B) {
	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		i := 0
		for pb.Next() {
			if i%2 == 0 {
				obj := new(VariedSize1)
				runtime.KeepAlive(obj)
			} else {
				obj := new(VariedSize2)
				runtime.KeepAlive(obj)
			}
			i++
		}
	})
}

func main() {
	var wg sync.WaitGroup
	const workers = 8
	wg.Add(workers)

	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			for j := 0; j < 50_000; j++ {
				x := new(TargetSize128)
				runtime.KeepAlive(x)
			}
		}()
	}
	wg.Wait()
}
```

## Под капотом

В `src/runtime/mcentral.go`:
```go
func (c *mcentral) cacheSpan() *mspan {
    lock(&c.lock) // Атомарный спинлок рантайма
    // Поиск спана в c.partial
    unlock(&c.lock)
}
```
Спинлок `lock(&c.lock)` использует инструкцию `LOCK CMPXCHG`. При высокой частоте обращений линии кэша процессора переходят в статус Invalidated в протоколе MESI, замедляя обращения всех ядер к оперативной памяти.

## Подводные камни

1. Мьютексы рантайма (`runtime.mutex`) не видны в стандартном `sync.Mutex` профиле (`pprof mutex`), так как они реализованы на уровне ядра рантайма.
2. Их задержки можно увидеть только через системные события в `go tool trace` (события `proc steal` и паузы планировщика).

## На собеседовании

**Вопрос с собеседования:** Почему в Go сделано 136 отдельных структур `mcentral`, а не один общий глобальный пул?
**Ответ:** Разделение на 136 независимых пулов (по числу подклассов размеров) является классическим паттерном шардирования блокировок (Lock Striping). Запросы на выделение 16 байт, 64 байт и 512 байт конкурируют за совершенно разные мьютексы `mcentral`, что в сотни раз снижает вероятность межъядерной блокировки на многопроцессорных серверах.
