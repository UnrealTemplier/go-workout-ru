# Ложное разделение False Sharing и выравнивание по кэш-линиям

## Условие

**[Каверзный кейс — False Sharing]**: Напиши структуру `Counter` с полем `n int64`. Создай массив из 8 таких счетчиков. Запусти 8 горутин, каждая инкрементирует свой счетчик (`counters[i].n`). Замерь время. Затем добавь padding (отступы), чтобы каждый счетчик занимал ровно 64 байта (размер кэш-линии процессора). Замерь время снова. Оцени колоссальную разницу в скорости.

## Теория

**False Sharing (Ложное разделение кэш-линий)** — один из самых коварных аппаратных эффектов многопоточности.

Механика процессора:
1. Процессор обменивается данными с оперативной памятью не отдельными байтами, а блоками фиксированного размера — **кэш-линиями (Cache Lines)** размером **64 байта** (на архитектурах x86-64 и ARM64).
2. Если две разные переменные лежат рядом в памяти и попадают в одну общую 64-байтную кэш-линию, ядра процессора вынуждены непрерывно синхронизировать её состояние через протокол когерентности кэшей (MESI/MOESI).
3. Когда ядро 1 пишет в переменную \(A\), вся кэш-линия в кэше ядра 2 помечается как `Invalidated`, заставляя ядро 2 перезагружать данные из общей шины, даже если оно работает с совершенно другой независимой переменной \(B\)!

Решение — **Cache Line Padding**: добавление фиктивных байтов отступа, чтобы каждый счетчик гарантированно занимал ровно 64 байта.

## Решение по шагам

1. Создайте структуру `NaiveCounter` (8 байт).
2. Создайте структуру `PaddedCounter` с отступом `_ [56]byte` (ровно 64 байта).
3. Напишите бенчмарк параллельного инкремента 8 независимых счетчиков в 8 горутинах.
4. Сравните скорость выполнения: версия с паддингом в 3–10 раз быстрее!

## Код решения

**`false_sharing_test.go`**

```go
package main

import (
	"sync"
	"testing"
	"unsafe"
)

// 8 байт: 8 счетчиков помещаются в одну общую 64-байтную кэш-линию!
type NaiveCounter struct {
	N int64
}

// 64 байта: каждый счетчик занимает свою собственную кэш-линию CPU
type PaddedCounter struct {
	N   int64
	Pad [56]byte // 8 + 56 = 64 байта
}

func BenchmarkFalseSharing(b *testing.B) {
	var counters [8]NaiveCounter

	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		var wg sync.WaitGroup
		for i := 0; i < 8; i++ {
			wg.Add(1)
			go func(idx int) {
				defer wg.Done()
				for j := 0; j < b.N; j++ {
					counters[idx].N++ // Жесточайший False Sharing!
				}
			}(i)
		}
		wg.Wait()
	})
}

func BenchmarkPaddedNoSharing(b *testing.B) {
	var counters [8]PaddedCounter

	b.ResetTimer()
	b.RunParallel(func(pb *testing.PB) {
		var wg sync.WaitGroup
		for i := 0; i < 8; i++ {
			wg.Add(1)
			go func(idx int) {
				defer wg.Done()
				for j := 0; j < b.N; j++ {
					counters[idx].N++ // Нет False Sharing!
				}
			}(i)
		}
		wg.Wait()
	})
}

func main() {
	println("Размер NaiveCounter :", unsafe.Sizeof(NaiveCounter{}))
	println("Размер PaddedCounter:", unsafe.Sizeof(PaddedCounter{}))
}
```

ℹ️ Бенчмарк устранения эффекта False Sharing через Cache Line Padding

**`Терминал`**

```bash
go test -bench=. -benchtime=2s false_sharing_test.go
```

## Под капотом

В структуре `PaddedCounter`:
Размер равен ровно 64 байтам. В массиве `[8]PaddedCounter` адрес каждого следующего счетчика смещен ровно на 64 байта: `0x00, 0x40, 0x80, 0xC0...`
Каждый счетчик попадает в отдельную аппаратную строку кэша L1/L2 соответствующего процессорного ядра.
Статус строки в протоколе MESI остается `Modified` локально для ядра, исключая трафик по шине межпроцессорной когерентности.

## Подводные камни

1. Паддинг расходует дополнительную оперативную память. Используйте его только в высококонкурентных горячих структурах (метрики, счетчики, кольцевые очереди lock-free).
2. На некоторых архитектурах (например, IBM zSeries или Apple M-серия) размер кэш-линии может составлять 128 байт.

## На собеседовании

**Вопрос с собеседования:** Что такое False Sharing (ложное разделение кэш-линий) и как компилятор или стандартная библиотека Go решают эту проблему?
**Ответ:** False Sharing возникает, когда независимые переменные, модифицируемые параллельными потоками, оказываются в одной 64-байтной кэш-линии процессора, вызывая взаимную инвалидацию кэшей L1/L2. В стандартной библиотеке Go эта проблема решается явным добавлением полей отступа (Padding). Например, в реализации `sync.Pool` структура пула `poolLocal` выравнивается ровно под размер кэш-линии (64 или 128 байт) через поле `pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte`.
