# Структура mspan и внутренняя фрагментация памяти

## Условие

**Понимание спанов (`mspan`) и фрагментации**: Память в Go нарезается на страницы (pages) размером 8 КБ, которые объединяются в структуры `mspan`. Каждый спан нарезается на ячейки фиксированного размера (size classes, всего около 67 классов). Объясните в комментариях концепцию внутренней фрагментации памяти: почему при аллокации структуры размером 33 байта рантайм выделит под неё ячейку из класса 48 байт, и куда деваются "лишние" 15 байт.

## Теория

Основой аллокатора Go является структура `mspan` — непрерывный блок виртуальной памяти, состоящий из одной или нескольких страниц фиксированного размера **8192 байта (8 КБ)**.

Каждый `mspan` привязан к определенному **классу размера (Size Class)**. Например:
- Класс 1: 8 байт
- Класс 2: 16 байт
- Класс 3: 24 байта
- Класс 4: 32 байта
- Класс 5: 48 байт
- ... всего 67 классов вплоть до 32 КБ.

**Внутренняя фрагментация (Internal Fragmentation):**
Когда программа запрашивает объект размером 33 байта, аллокатор не может нарезать память произвольным куском. Он округляет запрос вверх до ближайшего класса размера — 48 байт.
Разница между размером слота (48 байт) и реальным размером объекта (33 байта) составляет 15 байт. Этот остаток остается неиспользованным внутри слота — это плата за устранение внешней фрагментации и скорость аллокации \(O(1)\).

## Решение по шагам

1. Напишите код со структурами пограничных размеров (например, 32 байта и 33 байта).
2. Замерьте аллокацию памяти для 100 000 таких структур.
3. Продемонстрируйте математический расчет потерь памяти на внутреннюю фрагментацию.

## Код решения

**`fragmentation.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

type Exact32 struct {
	Data [32]byte
}

type Size33 struct {
	Data [33]byte
}

func main() {
	fmt.Printf("Размер Exact32: %d байт (попадает в класс 32Б, оверхед = 0 байт)\n",
		unsafe.Sizeof(Exact32{}))
	fmt.Printf("Размер Size33 : %d байт (попадает в класс 48Б, оверхед = 15 байт / 31.2%%)\n\n",
		unsafe.Sizeof(Size33{}))

	const count = 100_000

	// Тест 1: Аллокация 100k объектов по 32 байта
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)
	s32 := make([]*Exact32, count)
	for i := 0; i < count; i++ {
		s32[i] = new(Exact32)
	}
	runtime.ReadMemStats(&m2)
	alloc32 := m2.HeapAlloc - m1.HeapAlloc

	// Тест 2: Аллокация 100k объектов по 33 байта
	runtime.GC()
	runtime.ReadMemStats(&m1)
	s33 := make([]*Size33, count)
	for i := 0; i < count; i++ {
		s33[i] = new(Size33)
	}
	runtime.ReadMemStats(&m2)
	alloc33 := m2.HeapAlloc - m1.HeapAlloc

	fmt.Printf("Память под 100k объектов Exact32 : %d КБ (в среднем %.1f байт/объект)\n",
		alloc32/1024, float64(alloc32)/count)
	fmt.Printf("Память под 100k объектов Size33  : %d КБ (в среднем %.1f байт/объект)\n",
		alloc33/1024, float64(alloc33)/count)

	_ = s32
	_ = s33
}
```

ℹ️ Экспериментальный замер потерь памяти на внутреннюю фрагментацию mspan

**`Терминал`**

```bash
go run fragmentation.go
```

## Под капотом

В структуре `mspan` (файл `runtime2.go`):
- `startAddr uintptr`: начальный виртуальный адрес спана.
- `npages uintptr`: число 8 КБ страниц в спане (от 1 до десятков страниц).
- `spanclass spanClass`: класс размера (младший бит определяет наличие указателей noscan/scan).
- `allocBits *gcBits`: битовая карта свободных/занятых слотов. Аллокация свободного слота выполняется процессорной инструкцией `CTZ` (Count Trailing Zeros) за 1 такт!
- `nelems uintptr`: суммарное количество объектов, умещающихся в спане.

## Подводные камни

1. Увеличение структуры всего на 1 байт (например, с 32 до 33 байт) может привести к скачку потребления памяти приложением на 50% из-за перехода в следующий класс размера.
2. Проектируя структуры, которые создаются миллионами штук, всегда проверяйте попадание `unsafe.Sizeof(T)` точно в границы size classes Go (8, 16, 24, 32, 48, 64, 80, 96...).

## На собеседовании

**Вопрос с собеседования:** В чем фундаментальная разница между внутренней (internal) и внешней (external) фрагментацией памяти? Какую проблему решил Go?
**Ответ:** 
- **Внешняя фрагментация:** память дробится на разношерстные кусочки между занятыми блоками так, что суммарно свободного места много, но непрерывный кусок выделить невозможно. Традиционные аллокаторы `malloc` страдают от этого.
- **Внутренняя фрагментация:** неиспользованное пространство внутри выделенного слота фиксированного размера.
Go нарезает спаны на фиксированные классы размеров (size classes), полностью побеждая внешнюю фрагментацию ценой контролируемой внутренней фрагментации (в среднем не более 12.5%).
