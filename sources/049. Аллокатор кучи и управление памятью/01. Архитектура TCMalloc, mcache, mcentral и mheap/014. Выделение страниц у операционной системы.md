# Выделение страниц у операционной системы: mmap и madvise

## Условие

**Page allocation**: Изучите, как runtime запрашивает страницы у ОС через `mmap`/`VirtualAlloc` и возвращает через `munmap`/`VirtualFree`.

## Теория

Рантайм Go не использует стандартную сишную функцию `malloc()` из `glibc`. Вместо этого Go общается с ядром операционной системы напрямую через быстрые системные вызовы:
- **Linux:**
  - `mmap(addr, length, PROT_READ|PROT_WRITE, MAP_ANON|MAP_PRIVATE, -1, 0)`: выделяет новый диапазон виртуальной памяти.
  - `madvise(addr, length, MADV_DONTNEED)`: сообщает ядру Linux, что страницы не используются. Ядро сбрасывает физические фреймы памяти, обнуляя RSS процесса.
  - `munmap(addr, length)`: освобождает диапазон адресов виртуальной памяти (в Go практически не используется, так как виртуальные арены удерживаются для повторного использования).
- **Windows:**
  - `VirtualAlloc(MEM_RESERVE / MEM_COMMIT)` и `VirtualFree(MEM_DECOMMIT)`.
- **macOS / BSD:**
  - `mmap` и `madvise(MADV_FREE_REUSABLE)`.

## Решение по шагам

1. Напишите код на Go, который с помощью системного вызова `syscall.Mmap` выделяет чистые страницы виртуальной памяти в обход кучи Go.
2. Запишите данные в выделенные страницы.
3. Очистите страницы через `syscall.Madvise` с флагом `MADV_DONTNEED`.
4. Освободите память через `syscall.Munmap`.

## Код решения

**`direct_mmap.go`**

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	const pageSize = 4096
	numPages := 4
	totalBytes := numPages * pageSize

	fmt.Println("=== Прямой системный вызов mmap в Linux/Unix ===")

	// 1. Выделяем анонимную приватную память у ядра ОС (как делает mheap)
	data, err := syscall.Mmap(
		0,
		0,
		totalBytes,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		panic(fmt.Sprintf("Ошибка mmap: %v", err))
	}
	fmt.Printf("Выделено %d байт по адресу %p через mmap\n", len(data), &data[0])

	// 2. Пишем данные (провоцируем page fault и выделение физических страниц ядра)
	data[0] = 42
	data[pageSize] = 43
	fmt.Println("Данные успешно записаны в физические фреймы памяти.")

	// 3. Возвращаем физические страницы ядру ОС через madvise
	// MADV_DONTNEED = 4 в Linux
	const madvDontNeed = 4
	_, _, errno := syscall.Syscall(
		syscall.SYS_MADVISE,
		uintptr(data[0]),
		uintptr(totalBytes),
		uintptr(madvDontNeed),
	)
	if errno != 0 {
		fmt.Printf("Предупреждение madvise: %v\n", errno)
	} else {
		fmt.Println("madvise(MADV_DONTNEED) выполнен: физическая память возвращена ядру!")
	}

	// 4. Освобождаем виртуальный диапазон
	if err := syscall.Munmap(data); err != nil {
		panic(err)
	}
	fmt.Println("munmap выполнен: виртуальный диапазон закрыт.")
}
```

ℹ️ Прямое выделение и возврат страниц ядру ОС через системные вызовы mmap и madvise

**`Терминал`**

```bash
go run direct_mmap.go
```

## Под капотом

При старте Go рантайм резервирует гигантский непрерывный диапазон виртуальных адресов (на 64-битных Linux до нескольких терабайт) флагом `mmap(..., PROT_NONE, MAP_ANON, ...)`.
Это действие потребляет 0 байт физической RAM!
Затем, когда `mheap` запрашивает новую арену 64 МБ, рантайм вызывает `mmap(..., PROT_READ|PROT_WRITE, MAP_FIXED|MAP_ANON, ...)`, активируя этот блок. Физическая RAM выделяется ядром процессора лениво — только при первом обращении к странице (Minor Page Fault).

## Подводные камни

1. Виртуальная память процесса (VIRT) в Go может составлять сотни гигабайт или терабайт. Это нормальное поведение рантайма Go. Никогда не судите о потреблении памяти Go-сервиса по колонке VIRT — смотрите только на RES (Resident Set Size).
2. На 32-битных архитектурах адресное пространство ограничено 4 ГБ, поэтому на них арены и структуры метаданных Go устроены иначе.

## На собеседовании

**Вопрос с собеседования:** Почему в `top` колонка VIRT у Go-процесса сразу после запуска может показывать 500 ГБ, хотя на сервере всего 16 ГБ RAM?
**Ответ:** Потому что Go резервирует виртуальное адресное пространство (Virtual Address Space) на будущее с помощью `mmap` без выделения физических страниц (lazy paging). Это позволяет размещать арены памяти кучи по фиксированным виртуальным смещениям и исключить конфликт адресов, не расходуя ни одного мегабайта физической оперативной памяти.
