# Устройство структуры mspan и битовые карты занятости

## Условие

**mspan**: Непрерывный блок памяти, состоящий из нескольких страниц (8KB каждая). Содержит объекты одного size class.

## Теория

`mspan` (Memory Span) — базовый кирпич управления памятью в Go.

Ключевые поля структуры `mspan` (определена в `src/runtime/mspan.go`):
- `startAddr uintptr`: начальный виртуальный адрес спана.
- `npages uintptr`: число страниц (по 8192 байта), выделенных под данный спан.
- `elemsize uintptr`: размер слота под объект в байтах (например, 24 байта).
- `nelems uintptr`: общее количество объектов, помещающихся в спане (`(npages * 8192) / elemsize`).
- `allocBits *gcBits`: битовая карта, где 1 означает занятый слот, 0 — свободный.
- `gcmarkBits *gcBits`: битовая карта, в которой сборщик мусора выставляет 1 для каждого достижимого (живого) объекта.
- `freeindex uintptr`: индекс первого потенциально свободного слота (ускоряет поиск до \(O(1)\)).

## Решение по шагам

1. Напишите код, эмулирующий расчет параметров `mspan` для разных классов размеров.
2. Рассчитайте число страниц, емкость объектов и внутреннюю фрагментацию для классов 16Б, 48Б, 512Б и 4КБ.
3. Продемонстрируйте работу побитовой маски `allocBits`.

## Код решения

**`mspan_calc.go`**

```go
package main

import "fmt"

const pageSize = 8192 // 8 КБ

type SpanSpec struct {
	ClassID  int
	ElemSize int
	Pages    int
}

func main() {
	specs := []SpanSpec{
		{ClassID: 2, ElemSize: 16, Pages: 1},
		{ClassID: 5, ElemSize: 48, Pages: 1},
		{ClassID: 15, ElemSize: 512, Pages: 1},
		{ClassID: 35, ElemSize: 4096, Pages: 2},
	}

	fmt.Printf("%-8s %-10s %-8s %-10s %-12s %-10s\n",
		"Класс", "Объект (Б)", "Страниц", "Всего (Б)", "Вместимость", "Потери (Б)")
	fmt.Println("----------------------------------------------------------------")

	for _, s := range specs {
		totalSpanBytes := s.Pages * pageSize
		capacity := totalSpanBytes / s.ElemSize
		usedBytes := capacity * s.ElemSize
		wasteBytes := totalSpanBytes - usedBytes

		fmt.Printf("Class %-2d %-10d %-8d %-10d %-12d %-10d\n",
			s.ClassID, s.ElemSize, s.Pages, totalSpanBytes, capacity, wasteBytes)
	}

	// Эмуляция битовой карты allocBits (64 бита на uint64)
	var allocBits uint64 = 0b0000_1111 // первые 4 слота заняты
	freeIndex := 4                     // следующий свободный слот
	fmt.Printf("\nЭмуляция allocBits: 0x%016x (следующий свободный слот: %d)\n",
		allocBits, freeIndex)
}
```

ℹ️ Математическая модель параметров и емкости mspan

**`Терминал`**

```bash
go run mspan_calc.go
```

## Под капотом

Во время фазы Sweep (очистка мусора):
Рантайм не очищает память байт за байтом!
Он просто меняет местами указатели на битовые карты:
`s.allocBits = s.gcmarkBits`
`s.gcmarkBits = newMarkBits(s.nelems)`
Все немаркированные объекты мгновенно становятся «свободными» для будущих аллокаций за **1 такт процессора**! Это гениальная оптимизация алгоритма триколор GC в Go.

## Подводные камни

1. Потери памяти в хвосте спана (`totalBytes - nelems * elemsize`) возникают, когда размер страницы (8192) не делится нацело на размер объекта. Чтобы минимизировать этот остаток, крупные классы объединяют несколько 8 КБ страниц в один спан.
2. Не путайте `allocBits` со стековыми фреймами: спаны используются исключительно в куче.

## На собеседовании

**Вопрос с собеседования:** Как рантайм Go выполняет освобождение памяти целого `mspan` в фазе Sweep за константное время \(O(1)\)?
**Ответ:** Благодаря битовым картам `allocBits` и `gcmarkBits`. В ходе маркировки живые объекты помечаются битами в `gcmarkBits`. В фазе Sweep рантайм просто делает указатель `allocBits` равным старому `gcmarkBits`, а под новый `gcmarkBits` аллоцирует чистый нулевой массив. Если все биты в `gcmarkBits` оказались нулями (ни один объект не выжил), весь `mspan` целиком возвращается в `mcentral/mheap`.
