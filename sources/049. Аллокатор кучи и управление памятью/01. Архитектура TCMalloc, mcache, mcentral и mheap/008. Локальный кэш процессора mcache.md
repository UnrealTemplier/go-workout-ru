# Локальный кэш процессора mcache и Lock-free аллокации

## Условие

**mcache**: Каждый P имеет свой `mcache` — локальный кэш `mspan`'ов для разных size classes. Это позволяет аллоцировать без блокировок.

## Теория

`mcache` — это фундаментальная структура аллокатора, отвечающая за высочайшую скорость выделения памяти в Go.

Каждый логический процессор \(P\) в рантайме владеет собственной структурой `mcache`:
- Массив `alloc [numSpanClasses]*mspan`: указатели на активные спаны каждого из 136 подклассов (67 классов скан/носкан + пустые).
- В `mcache` также расположен буфер `tiny` и смещение `tinyoffset` для Tiny-аллокатора.

Поскольку поток ОС \(M\) монопольно владеет ассоциированным с ним \(P\) во время исполнения Go-кода, горутины, работающие на данном \(P\), аллоцируют память **абсолютно без мьютексов, без spinlock'ов и без атомарных CAS инструкций**. Выделение памяти занимает всего ~5-15 наносекунд.

## Решение по шагам

1. Смоделируйте конкурентную аллокацию памяти в нескольких горутинах при `GOMAXPROCS=1` и `GOMAXPROCS=4`.
2. Замерьте пропускную способность аллокаций.
3. Продемонстрируйте масштабируемость независимых кэшей `mcache` при росте числа доступных ядер CPU.

## Код решения

**`mcache_bench_test.go`**

```go
package main

import (
	"runtime"
	"sync"
	"testing"
)

type DataPoint struct {
	ID    int64
	Score float64
}

// Бенчмарк параллельной аллокации памяти
func BenchmarkParallelAlloc(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			// Выделение памяти из локального mcache текущего P
			d := &DataPoint{ID: 100, Score: 99.5}
			runtime.KeepAlive(d)
		}
	})
}

func main() {
	var wg sync.WaitGroup
	const workers = 4
	wg.Add(workers)

	// Проверяем работу на всех P
	for i := 0; i < workers; i++ {
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 100_000; j++ {
				_ = &DataPoint{ID: int64(j), Score: float64(j) * 1.5}
			}
		}(i)
	}

	wg.Wait()
}
```

ℹ️ Бенчмарк параллельного выделения памяти из изолированных кэшей mcache

**`Терминал`**

```bash
go test -bench=BenchmarkParallelAlloc -cpu=1,2,4,8 mcache_bench_test.go
```

## Под капотом

В `src/runtime/mcache.go` метод `mcache.allocLarge` или `nextFreeFast`:
```go
func (c *mcache) nextFree(spc spanClass) (gclinkptr, uintptr, bool) {
    s := c.alloc[spc]
    freeIndex := s.nextFreeIndex()
    if freeIndex == s.nelems {
        // Спан полон — вызываем пополнение mcache из mcentral
        c.refill(spc)
    }
    // Быстрое извлечение адреса
}
```
Метод `nextFreeFast` инлайнится компилятором. При наличии свободных слотов он выполняется всего за 3 процессорные инструкции: битовый сдвиг, чтение и инкремент индекса.

## Подводные камни

1. Если горутина мигрирует между разными \(P\) (например, после системного вызова или yield), она начинает использовать `mcache` нового \(P\). Это нормальное поведение рантайма и не приводит к утечкам.
2. `mcache` очищается и сбрасывается обратно в `mcentral` во время фазы Stop-The-World (STW) сборщика мусора перед фазой разметки.

## На собеседовании

**Вопрос с собеседования:** Что происходит с объектами в `mcache`, когда сборщик мусора GC начинает цикл сборки?
**Ответ:** Перед началом фазы разметки (Mark Phase) рантайм выполняет сброс (flush) кэшей `mcache` всех процессоров \(P\) в функции `mcache.releaseAll()`. Все спаны возвращаются в `mcentral`, чтобы сборщик мусора видел единое целостное состояние всех объектов в куче и мог корректно отслеживать неиспользуемую память.
