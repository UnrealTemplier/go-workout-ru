# Слияние спанов Span Coalescing и устранение внешней фрагментации

## Условие

**Span coalescing**: Когда смежные `mspan`'ы освобождаются, runtime объединяет их для снижения фрагментации.

## Теория

Одной из главных угроз для долгоживущих процессов является **внешняя фрагментация памяти** — ситуация, когда в памяти образуется множество свободных мелких блоков, разделенных занятыми, из-за чего невозможно выделить один крупный непрерывный сегмент.

Для решения этой проблемы рантайм Go реализует алгоритм **Span Coalescing (слияние смежных спанов)**:
1. Когда спан полностью освобождается в фазе Sweep (все объекты в нем стали мусором), он возвращается из `mcentral` в глобальный `pageAlloc` кучи `mheap`.
2. Аллокатор проверяет соседние страницы слева и справа в Radix Tree.
3. Если смежные страницы также свободны, они объединяются в один большой непрерывный диапазон страниц (Chunk/Span).
4. Полученный крупный блок в будущем может быть нарезан под любой другой класс размера или отдан под крупный срез.

## Решение по шагам

1. Напишите код, моделирующий паттерн создания и освобождения мелких смежных спанов.
2. Продемонстрируйте объединение страниц памяти в более крупные свободные блоки.
3. Исследуйте показатели `HeapIdle` и структуру свободных чанков в `pageAlloc`.

## Код решения

**`coalescing.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Println("=== Демонстрация Span Coalescing в mheap ===")

	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// 1. Выделяем 1000 разнородных блоков, которые займут смежные страницы в арене
	chunks := make([][]byte, 1000)
	for i := 0; i < len(chunks); i++ {
		chunks[i] = make([]byte, 16*1024) // по 16 КБ (по 2 страницы на блок)
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("Выделено памяти под чанки: %d КБ\n", (m2.HeapAlloc-m1.HeapAlloc)/1024)

	// 2. Освобождаем все чанки одновременно
	for i := 0; i < len(chunks); i++ {
		chunks[i] = nil
	}

	// 3. Запускаем GC: спаны очищаются и сливаются в mheap
	runtime.GC()

	var m3 runtime.MemStats
	runtime.ReadMemStats(&m3)

	fmt.Printf("Память после GC (HeapAlloc): %d КБ (очищена!)\n", m3.HeapAlloc/1024)
	fmt.Printf("Память в пуле mheap (HeapIdle): %d КБ (слита в непрерывные блоки)\n", m3.HeapIdle/1024)

	// 4. Проверяем, что теперь можно выделить один крупный сплошной блок
	// из тех же самых слившихся страниц!
	hugeChunk := make([]byte, 14*1024*1024) // 14 МБ сплошной блок
	hugeChunk[0] = 1

	var m4 runtime.MemStats
	runtime.ReadMemStats(&m4)
	fmt.Printf("HeapSys не вырос при аллокации 14 МБ: переиспользованы слитые страницы! (%d МБ)\n",
		m4.HeapSys/(1024*1024))

	_ = hugeChunk
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Слияние свободных страниц и выделение крупного блока из пула HeapIdle

**`Терминал`**

```bash
go run coalescing.go
```

## Под капотом

В `src/runtime/mpagealloc.go` метод `pageAlloc.free(base, npages)`:
1. Вычисляет битовые индексы освобождаемых страниц в битовой карте `chunks`.
2. Сбрасывает биты занятости в 0.
3. Проверяет префиксные и суффиксные нули в соседних 64-страничных чанках.
4. Обновляет сводные поля в промежуточных узлах Radix Tree (`pallocSum`), объединяя свободные интервалы в один максимальный диапазон.
Благодаря битовым операциям слияние спанов в Go не требует перестроения сложных связанных списков.

## Подводные камни

1. Если хотя бы один маленький объект в спане удерживается живой ссылкой, весь спан не может быть освобожден и слит с соседями (проблема Pinning).
2. Чрезмерное дробление на разношерстные размеры в долгоживущих коллекциях может препятствовать эффективному слиянию спанов.

## На собеседовании

**Вопрос с собеседования:** Что такое проблема «Pinning» памяти в спанах и как она мешает работе алгоритма Span Coalescing?
**Ответ:** Если в спане размером 8 КБ размещено 100 объектов по 80 байт, и 99 из них стали мусором, но 1 объект удерживается глобальной переменной, весь 8 КБ спан считается активным (`HeapInuse`). Его страницы нельзя вернуть в `mheap`, нельзя слить с соседями (coalesce) и нельзя вернуть операционной системе. Решение — избегать хранения одиночных долгоживущих мелких объектов внутри кратковременных коллекций.
