# Категории аллокаций: Tiny, Small и Large Allocations

## Условие

**Tiny, Small, Large allocations:**
* Tiny: < 16 bytes (special handling, может объединять несколько аллокаций)
* Small: 16 bytes - 32 KB (через mspan)
* Large: > 32 KB (напрямую из mheap)

## Теория

Аллокатор Go делит все запросы памяти на 3 принципиально разные категории в зависимости от размера:

1. **Tiny Allocations (< 16 байт без указателей):**
   - Мелкие структуры, строки, числовые переменные.
   - Обслуживаются специальным **Tiny Allocator** внутри `mcache`.
   - Несколько независимых мелких объектов объединяются (упаковываются) в один 16-байтный блок, что экономит память и снижает фрагментацию.
2. **Small Allocations (16 байт – 32 КБ):**
   - Округляются до ближайшего из 67 классов размеров.
   - Выделяются из соответствующего `mspan` в `mcache` за 1-2 процессорных такта без локов.
3. **Large Allocations (> 32 КБ):**
   - Большие срезы, буферы и крупные структуры.
   - Полностью минуют `mcache` и `mcentral`.
   - Выделяются напрямую из глобальной кучи `mheap` страницами по 8 КБ под глобальной блокировкой `mheap.lock`.

## Решение по шагам

1. Напишите код, выполняющий аллокации всех трех типов: Tiny (4 байта), Small (512 байт) и Large (128 КБ).
2. Зафиксируйте адреса памяти и убедитесь в упаковке крошечных объектов.
3. Исследуйте накладные расходы времени выполнения на каждый тип аллокации.

## Код решения

**`alloc_types.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

type TinyObj struct {
	X uint16 // 2 байта
	Y uint16 // 2 байта (итого 4 байта < 16B, без указателей)
}

type SmallObj struct {
	Buffer [512]byte // 512 байт (16B <= size <= 32KB)
}

func main() {
	fmt.Println("=== Демонстрация категорий аллокаций в Go ===")

	// 1. Tiny Allocation (< 16B)
	t1 := new(TinyObj)
	t2 := new(TinyObj)
	t1.X, t2.X = 1, 2
	addr1 := uintptr(unsafe.Pointer(t1))
	addr2 := uintptr(unsafe.Pointer(t2))

	fmt.Printf("Tiny 1: адрес 0x%x (размер %d байт)\n", addr1, unsafe.Sizeof(*t1))
	fmt.Printf("Tiny 2: адрес 0x%x (размер %d байт)\n", addr2, unsafe.Sizeof(*t2))
	fmt.Printf("Дельта адресов Tiny объектов: %d байт (упакованы в один блок!)\n\n", addr2-addr1)

	// 2. Small Allocation (16B - 32KB)
	s := new(SmallObj)
	fmt.Printf("Small: адрес %p (размер %d байт, класс 512B в mcache)\n\n",
		s, unsafe.Sizeof(*s))

	// 3. Large Allocation (> 32KB)
	const largeSize = 64 * 1024 // 64 КБ > 32 КБ
	largeSlice := make([]byte, largeSize)
	fmt.Printf("Large: адрес %p (размер %d КБ, выделен напрямую из mheap)\n",
		&largeSlice[0], len(largeSlice)/1024)

	runtime.KeepAlive(t1)
	runtime.KeepAlive(t2)
	runtime.KeepAlive(s)
	runtime.KeepAlive(largeSlice)
}
```

ℹ️ Практическая демонстрация Tiny, Small и Large аллокаций памяти

**`Терминал`**

```bash
go run alloc_types.go
```

## Под капотом

В `mallocgc` ветвление выглядит следующим образом:
```go
if size <= maxSmallSize {
    if noscan && size < maxTinySize {
        // Tiny Allocator: упаковка в mcache.tiny
    } else {
        // Small Allocator: mcache.alloc[spanclass]
    }
} else {
    // Large Allocator: largeAlloc(size, needzero, noscan) -> mheap_.alloc
}
```
Флаг `noscan` критически важен: Tiny Allocator объединяет объекты **только если в них нет указателей**, иначе сборщику мусора пришлось бы сканировать весь 16-байтный блок целиком даже при освобождении одного из объектов.

## Подводные камни

1. Если в крошечной структуре (даже размером 4 байта) есть указатель `*int`, она **не попадает** в Tiny Allocator и идет в общий Small Allocator (класс 16 байт).
2. Частые аллокации Large объектов (> 32 КБ) нагружают глобальный спинлок `mheap.lock`, вызывая деградацию параллелизма на многоядерных серверах.

## На собеседовании

**Вопрос с собеседования:** Почему Tiny Allocator упаковывает только объекты без указателей (`noscan`) и никогда не упаковывает структуры, содержащие указатели?
**Ответ:** Если упаковать в один 16-байтный блок несколько объектов, содержащих указатели, сборщик мусора не сможет понять, к какому именно логическому объекту относится каждый указатель. Более того, пока хотя бы один из упакованных объектов жив, весь 16-байтный блок удерживается в памяти, что при наличии указателей могло бы вызвать задержку освобождения целого поддерева объектов в куче.
