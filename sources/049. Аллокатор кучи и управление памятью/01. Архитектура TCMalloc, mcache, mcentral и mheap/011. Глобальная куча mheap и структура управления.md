# Глобальная куча mheap и структура управления страницами

## Условие

**mheap**: Глобальный heap, управляющий всей памятью процесса. Содержит все `mspan`'ы, организованные в radix tree для быстрого поиска.

## Теория

`mheap` — это вершина иерархии памяти Go (L3 глобальная куча). В рантайме существует ровно один глобальный экземпляр `mheap_`.

Архитектурные обязанности `mheap`:
1. **Управление виртуальной памятью (Arenas):** Go резервирует виртуальную память гигантскими сегментами — аренами размером **64 МБ** (на 64-битных ОС). Арены отображаются на физическую память по мере необходимости.
2. **Аллокатор страниц (Page Allocator):** Память внутри арен нарезается на страницы по **8192 байта (8 КБ)**. Для поиска свободных непрерывных диапазонов страниц используется битовая карта и структура Radix Tree (`pageAlloc`).
3. **Хранилище `mcentral`:** Внутри `mheap` находится массив из 136 структур `mcentral`.
4. **Связка адресов со спанами:** Через трехуровневый массив `arenas[L1][L2]` рантайм мгновенно по адресу любого байта находит дескриптор его `*mspan`.

## Решение по шагам

1. Напишите код, аллоцирующий память крупными порциями (> 32 КБ), заставляя задействовать страницы `mheap`.
2. Измерьте изменения `HeapSys` и `HeapIdle` через `runtime.ReadMemStats`.
3. Изучите карту арен виртуальной памяти процесса.

## Код решения

**`mheap_demo.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	var m1, m2 runtime.MemStats
	runtime.ReadMemStats(&m1)

	fmt.Println("=== Исследование глобальной кучи mheap ===")
	fmt.Printf("Базовый HeapSys  : %d МБ (виртуальная память у ОС)\n", m1.HeapSys/(1024*1024))
	fmt.Printf("Базовый HeapAlloc: %d МБ (живые объекты)\n\n", m1.HeapAlloc/(1024*1024))

	// Выделяем крупный объект (50 МБ), который минует mcache и запрашивается напрямую у mheap
	fmt.Println("Аллоцируем крупный массив 50 МБ напрямую из mheap...")
	largeBuffer := make([]byte, 50*1024*1024)
	for i := range largeBuffer {
		largeBuffer[i] = 1 // физически трогаем страницы памяти
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("HeapSys после аллокации  : %d МБ\n", m2.HeapSys/(1024*1024))
	fmt.Printf("HeapAlloc после аллокации: %d МБ\n", m2.HeapAlloc/(1024*1024))
	fmt.Printf("HeapInuse (занятые спаны): %d МБ\n", m2.HeapInuse/(1024*1024))

	// Освобождаем ссылку
	largeBuffer = nil
	runtime.GC()

	var m3 runtime.MemStats
	runtime.ReadMemStats(&m3)
	fmt.Printf("\nПосле GC:\n")
	fmt.Printf("HeapAlloc (живая память): %d МБ (память очищена!)\n", m3.HeapAlloc/(1024*1024))
	fmt.Printf("HeapIdle  (в пуле mheap): %d МБ (удерживается в аренах)\n", m3.HeapIdle/(1024*1024))
	fmt.Printf("HeapReleased (отдано ОС): %d МБ\n", m3.HeapReleased/(1024*1024))

	time.Sleep(100 * time.Millisecond)
}
```

ℹ️ Прямая аллокация крупных блоков страниц в mheap и поведение HeapSys/HeapIdle

**`Терминал`**

```bash
go run mheap_demo.go
```

## Под капотом

В `src/runtime/mpagealloc.go` аллокатор страниц `pageAlloc` использует компактное побитовое Radix Tree:
- Каждый лист дерева представляет 64 страницы (512 КБ).
- Промежуточные узлы хранят сводную информацию: максимальное непрерывное количество свободных страниц в поддереве.
- Поиск диапазона из \(K\) свободных страниц выполняется за \(O(\log N)\) процессорными инструкциями поиска битов `BSR`/`BSF` без линейного сканирования памяти!
Если страниц в текущих аренах не хватает, вызывается `sysAlloc` -> `mmap(PROT_READ|PROT_WRITE)`.

## Подводные камни

1. Рост метрики `HeapSys` означает, что процесс запросил виртуальную память у ядра Linux. Даже после сборки мусора `HeapSys` не уменьшается автоматически — страницы переходят в статус `HeapIdle` и возвращаются ядру только фоновым потоком `scavenger`.
2. Прямые аллокации в `mheap` блокируют глобальный мьютекс `mheap_.lock`, поэтому множественные параллельные аллокации объектов > 32 КБ создают бутылочное горлышко.

## На собеседовании

**Вопрос с собеседования:** Что такое `HeapIdle` и почему после вызова `runtime.GC()` объем памяти процесса в выводе команды `top` (колонка RES) часто вообще не уменьшается?
**Ответ:** `HeapIdle` — это объем памяти страниц, которые принадлежат аренам Go, но в данный момент не содержат живых объектов. Go намеренно не возвращает эту память ядру ОС немедленно, так как системные вызовы `munmap`/`madvise` дороги по CPU, а сервису вскоре снова может понадобиться память. Память возвращается ядру фоновым сборщиком (Scavenger) постепенно через `madvise(MADV_DONTNEED)`.
