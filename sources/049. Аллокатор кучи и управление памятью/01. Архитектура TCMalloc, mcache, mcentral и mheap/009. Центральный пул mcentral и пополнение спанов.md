# Центральный пул mcentral и пополнение спанов

## Условие

**mcentral**: Когда `mcache` истощается, он запрашивает новые `mspan`'ы из `mcentral` (глобальный для каждого size class, с блокировкой).

## Теория

`mcentral` — это второй уровень иерархии аллокатора памяти Go (L2 пул).

Характеристики `mcentral`:
- В рантайме существует ровно **136 экземпляров `mcentral`** (по два на каждый из 68 классов: один для объектов без указателей `noscan`, другой для объектов с указателями `scan`).
- Каждый `mcentral` управляет двумя списками спанов:
  1. `partial`: спаны, в которых есть как минимум один свободный слот для аллокации.
  2. `full`: спаны, в которых все слоты заняты.
- Поскольку к одному `mcentral` обращаются все процессоры \(P\) при исчерпании своих `mcache`, доступ к нему защищен спинлоком `mcentral.lock`.

## Решение по шагам

1. Напишите код с массовой аллокацией объектов одного размера большим числом параллельных горутин.
2. Смоделируйте опустошение локальных кэшей `mcache`.
3. Объясните логику перехода из `partial` в `full` списки `mcentral`.

## Код решения

**`mcentral_demo.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

// Структура размером ровно 64 байта (Size Class 6)
type Block64 struct {
	Data [8]int64
}

func main() {
	fmt.Printf("Число доступных P: %d\n", runtime.GOMAXPROCS(0))

	const goroutines = 16
	const allocsPerG = 20_000

	var wg sync.WaitGroup
	wg.Add(goroutines)

	start := time.Now()

	// Запускаем 16 горутин, одновременно требующих сотни тысяч объектов класса 64B
	// Это многократно опустошит mcache каждого P и заставит их синхронизироваться на mcentral[6]
	for i := 0; i < goroutines; i++ {
		go func(workerID int) {
			defer wg.Done()
			storage := make([]*Block64, allocsPerG)
			for j := 0; j < allocsPerG; j++ {
				storage[j] = &Block64{Data: [8]int64{int64(workerID), int64(j)}}
			}
			_ = storage
		}(i)
	}

	wg.Wait()
	elapsed := time.Since(start)

	var mem runtime.MemStats
	runtime.ReadMemStats(&mem)

	fmt.Printf("Время параллельной аллокации: %v\n", elapsed)
	fmt.Printf("Всего аллокаций в куче: %d\n", mem.Mallocs)
	fmt.Println("Все P успешно пополнили спаны через mcentral.")
}
```

ℹ️ Массовая параллельная аллокация для провокации обращений к mcentral

**`Терминал`**

```bash
go run mcentral_demo.go
```

## Под капотом

Когда `mcache.refill(spc)` вызывает `mcentral.cacheSpan()`:
1. Захватывается `mcentral.lock`.
2. Проверяется список `partial swept`: спаны, уже очищенные от мусора (swept), имеющие свободные ячейки. Если найден, он отдается в `mcache`.
3. Если там пусто, проверяется список `partial unswept`: вызывается `mspan.sweep()` для немедленной очистки спана прямо на месте!
4. Если свободных спанов нет ни в swept, ни в unswept, вызывается `mcentral.grow()`, который идет на L3 уровень — в глобальный `mheap.alloc()` за новыми страницами памяти.
5. Лок освобождается.

## Подводные камни

1. Блокировка `mcentral.lock` является спинлоком рантайма, а не пользовательским мьютексом. При высокой конкуренции (тысячи горутин, аллоцирующих один класс размера) процессорные ядра могут кратковременно прогреваться на спин-циклах.
2. Использование объектов разных классов снижает contention на `mcentral`, так как разные классы используют разные структуры `mcentral` со своими независимыми спинлоками.

## На собеседовании

**Вопрос с собеседования:** Почему списки спанов в `mcentral` разделены на `swept` (очищенные) и `unswept` (неочищенные)?
**Ответ:** Go использует алгоритм ленивой очистки мусора (Lazy Sweeping). После фазы разметки Mark GC не очищает сразу все гигабайты кучи (это вызвало бы долгую паузу). Вместо этого спаны помечаются как `unswept`. Когда конкретному \(P\) требуется новый спан из `mcentral`, он сам доочищает один `unswept` спан (On-demand sweeping), распределяя нагрузку по времени и ядрам процессора.
