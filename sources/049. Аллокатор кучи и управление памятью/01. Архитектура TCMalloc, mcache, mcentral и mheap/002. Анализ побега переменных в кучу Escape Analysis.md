# Анализ побега переменных в кучу Escape Analysis

## Условие

**Анализ ухода переменных в кучу (Escape Analysis)**: Напишите три примера кода:
* Где переменная гарантированно остается на стеке горутины.
* Где переменная "утекает" (escapes) в кучу (например, возврат указателя на локальную переменную из функции).
* Где переменная утекает в кучу из-за динамического выделения памяти (слайс с переменной длиной `make([]int, n)`).
Запустите компиляцию с подробным выводом анализа escape-анализа: `go build -gcflags="-m"` и проверьте правильность ваших гипотез по отчету компилятора.

## Теория

Escape Analysis (анализ побега) — это фаза компилятора Go, которая на этапе сборки статически определяет, может ли время жизни переменной превысить время жизни фрейма стека функции, в которой она создана.

Правила анализа побега:
1. **Стек (Stack):** Если компилятор может доказать, что переменная не используется после возврата из функции, и её размер известен на этапе компиляции, память выделяется на стеке горутины. Выделение сводится к вычитанию из регистра `SP` (0 накладных расходов, не требует работы GC).
2. **Куча (Heap):** Если указатель на переменную возвращается наружу, сохраняется в глобальную переменную, передается в замыкание или размер среза неизвестен на этапе компиляции (`make([]T, n)`), память выделяется в куче (`runtime.newobject`).

## Решение по шагам

1. Напишите функцию `stackAlloc`, где локальная структура не выходит за пределы функции.
2. Напишите функцию `escapePointer`, возвращающую указатель на локальную структуру.
3. Напишите функцию `escapeDynamicSlice`, аллоцирующую срез переменной длины `n`.
4. Скомпилируйте код с флагом `-gcflags="-m"` и найдите диагностические сообщения компилятора.

## Код решения

**`escape.go`**

```go
package main

type Item struct {
	ID   int
	Val  int64
}

// 1. Гарантированно остается на стеке: передача по значению, размер фиксирован
//go:noinline
func stackAlloc() int64 {
	it := Item{ID: 1, Val: 100}
	return it.Val * 2
}

// 2. Утекает в кучу: возврат указателя наружу из стекового фрейма
//go:noinline
func escapePointer() *Item {
	it := Item{ID: 2, Val: 200}
	return &it // &it escapes to heap
}

// 3. Утекает в кучу: размер n динамический, неизвестен на этапе компиляции
//go:noinline
func escapeDynamicSlice(n int) []int {
	slice := make([]int, n) // make([]int, n) escapes to heap
	for i := 0; i < n; i++ {
		slice[i] = i
	}
	return slice
}

func main() {
	v := stackAlloc()
	ptr := escapePointer()
	sl := escapeDynamicSlice(5)

	_ = v
	_ = ptr
	_ = sl
}
```

ℹ️ Три классических сценария Escape Analysis в компиляторе Go

**`Терминал`**

```bash
# Запуск компилятора с флагом escape analysis
go build -gcflags="-m" escape.go
```

## Под капотом

Компилятор строит граф потока данных (Directed Data Flow Graph).
Узлами графа являются переменные и выражения, ребрами — операции присваивания и взятия адреса `&`.
Компилятор выполняет поиск связей с корнями (внешними указателями).
Если от переменной существует путь до возвращаемого значения, глобальной переменной или интерфейса `any`, вес узла становится бесконечным (`EscHeap`), и генератор SSA вставляет вызов `runtime.newobject`.

## Подводные камни

1. Передача примитивных переменных в `fmt.Println(x)` заставляет `x` утекать в кучу, так как `Println` принимает аргументы типа `...any`.
2. Слишком большие структуры (больше 64 КБ) даже при локальном использовании в функции могут вытесняться в кучу, чтобы не переполнять стартовый 2 КБ стек горутины.

## На собеседовании

**Вопрос с собеседования:** Почему возврат указателя на локальную переменную в C приводит к Segmentation Fault (висячий указатель), а в Go является абсолютно безопасной и идиоматичной операцией?
**Ответ:** В C компилятор всегда размещает локальные переменные на стеке вызываемой функции, который уничтожается при возврате инструкции `RET`. В Go компилятор проводит Escape Analysis: обнаружив возврат указателя, он гарантированно аллоцирует переменную не на стеке, а в управляемой куче (heap), где за её временем жизни следит Garbage Collector.
