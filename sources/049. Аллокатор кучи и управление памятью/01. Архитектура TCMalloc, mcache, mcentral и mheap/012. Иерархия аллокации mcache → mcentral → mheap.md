# Иерархия аллокации mcache → mcentral → mheap и pprof

## Условие

**Иерархия: mcache → mcentral → mheap.**: Напишите программу, интенсивно выделяющую объекты разного размера (маленькие <32KB, большие). Соберите профиль памяти (`pprof`), определите, из каких классов размеров (size classes) выделялась память, и в каких компонентах аллокатора.

## Теория

Иерархия памяти Go работает по принципу каскадного кэширования:
1. **L1: `mcache`:** Объекты \(\le 32\) КБ выделяются локально на текущем \(P\). Это Fast-Path без локов.
2. **L2: `mcentral`:** Когда в спане `mcache` заканчиваются свободные ячейки, спан возвращается в `mcentral`, а взамен забирается спан со свободными слотами. Это Slow-Path с блокировкой `mcentral.lock`.
3. **L3: `mheap`:** Если в `mcentral` нет свободных спанов (или объект \(> 32\) КБ), запрос идет в `mheap`. Выделяются 8 КБ страницы под глобальной блокировкой `mheap.lock`.

С помощью `pprof.WriteHeapProfile` можно зафиксировать как текущее распределение объектов (`inuse_space`), так и суммарный объем выделенной памяти за время работы (`alloc_space`).

## Решение по шагам

1. Напишите код, аллоцирующий мелкие объекты (128 байт), средние (4 КБ) и крупные (> 64 КБ).
2. Сохраните профиль кучи в файл `heap.pprof` с помощью пакета `runtime/pprof`.
3. Запустите анализ профиля через `go tool pprof -sample_index=alloc_space heap.pprof`.

## Код решения

**`hierarchy.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
	"sync"
)

// Мелкий объект (128B) -> mcache
type SmallItem struct {
	Data [128]byte
}

// Средний объект (4KB) -> mcache/mcentral
type MediumItem struct {
	Data [4096]byte
}

// Крупный объект (128KB > 32KB) -> напрямую mheap
type LargeItem struct {
	Data [128 * 1024]byte
}

func main() {
	var wg sync.WaitGroup
	const iterations = 1000

	// 1. Аллокация мелких объектов
	wg.Add(1)
	go func() {
		defer wg.Done()
		var items []*SmallItem
		for i := 0; i < iterations*10; i++ {
			items = append(items, new(SmallItem))
		}
		runtime.KeepAlive(items)
	}()

	// 2. Аллокация средних объектов
	wg.Add(1)
	go func() {
		defer wg.Done()
		var items []*MediumItem
		for i := 0; i < iterations; i++ {
			items = append(items, new(MediumItem))
		}
		runtime.KeepAlive(items)
	}()

	// 3. Аллокация крупных объектов
	wg.Add(1)
	go func() {
		defer wg.Done()
		var items []*LargeItem
		for i := 0; i < 50; i++ {
			items = append(items, new(LargeItem))
		}
		runtime.KeepAlive(items)
	}()

	wg.Wait()

	// Сохраняем heap profile
	f, err := os.Create("heap.pprof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	runtime.GC() // принудительно для фиксации актуального состояния
	if err := pprof.WriteHeapProfile(f); err != nil {
		panic(err)
	}

	fmt.Println("Профиль кучи сохранен в heap.pprof")
}
```

ℹ️ Сбор профиля кучи при разнокалиберных аллокациях памяти

**`Терминал`**

```bash
go run hierarchy.go
go tool pprof -top -alloc_space heap.pprof
```

## Под капотом

В `src/runtime/malloc.go` функция `mallocgc`:
- Для `SmallItem`: `spc = makeSpanClass(size_to_class8[128], false)` -> обращение к `c.alloc[spc]`.
- Если `c.alloc[spc]` пуст -> `c.refill(spc)` -> `mcentral[spc].cacheSpan()`.
- Для `LargeItem`: размер 131072 байт > `maxSmallSize` (32768) -> вызов `largeAlloc(131072, needzero, noscan)`.
`largeAlloc` вычисляет число страниц `npages = 131072 / 8192 = 16` и вызывает `mheap_.alloc(16, spanClass(0))`.

## Подводные камни

1. По умолчанию pprof heap сэмплирует одну аллокацию на каждые 512 КБ выделенной памяти (`runtime.MemProfileRate = 512 * 1024`). Мелкие аллокации отображаются со статистической погрешностью.
2. Для точного анализа в тестах можно установить `runtime.MemProfileRate = 1`, но в production это сильно просадит RPS.

## На собеседовании

**Вопрос с собеседования:** В профиле `pprof heap` есть 4 режима: `inuse_space`, `inuse_objects`, `alloc_space`, `alloc_objects`. Для поиска каких проблем предназначен каждый из них?
**Ответ:** 
- `inuse_space`: объем памяти, занятый прямо сейчас. Используется для поиска утечек памяти (Memory Leaks).
- `inuse_objects`: количество живых объектов. Позволяет выявить раздувание графа объектов, замедляющее фазу Mark GC.
- `alloc_space`: суммарный объем выделенной памяти за всё время. Используется для оптимизации темпа генерации мусора (GC pressure).
- `alloc_objects`: суммарное число созданных объектов. Показывает узкие места частых аллокаций, требующих внедрения `sync.Pool`.
