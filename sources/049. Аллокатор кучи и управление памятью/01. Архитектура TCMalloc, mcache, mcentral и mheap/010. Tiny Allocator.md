# Tiny Allocator: Упаковка мелких объектов до 16 байт

## Условие

**[Tiny Allocator (< 16 bytes)]**: Напиши структуру из двух полей `bool` и `int8` (занимает 2 байта). Создай миллион таких структур. Объясни, как Tiny Allocator объединяет маленькие объекты (< 16B) в один блок 16B, чтобы уменьшить фрагментацию памяти.

## Теория

Tiny Allocator в Go — это специализированный субаллокатор внутри `mcache`, разработанный специально для упаковки крошечных объектов размером **менее 16 байт без указателей** (`noscan`).

Механика работы:
1. В `mcache` хранятся два поля: `tiny uintptr` (адрес текущего 16-байтного блока) и `tinyoffset uintptr` (текущее смещение внутри этого блока).
2. При запросе объекта размера \(N\) байт (например, 2 байта):
   - Проверяется выравнивание (alignment).
   - Если в текущем 16-байтном блоке есть место (`tinyoffset + N <= 16`), объект размещается прямо в этом блоке, а `tinyoffset` сдвигается на \(N\).
   - Если места нет, выделяется новый 16-байтный блок из `mcache.alloc[tinySpanClass]`.
3. Благодаря этому несколько независимых мелких переменных делят один общий 16-байтный слот спана, снижая расход памяти в 4–8 раз!

## Решение по шагам

1. Создайте структуру размером 2 байта: `struct { a bool; b int8 }`.
2. Создайте массив указателей на миллион таких структур.
3. Проанализируйте адреса соседних элементов и подтвердите, что они упакованы в общие 16-байтные слоты.

## Код решения

**`tiny_allocator.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

type MiniNode struct {
	Flag bool // 1 байт
	Code int8 // 1 байт (итого 2 байта)
}

func main() {
	fmt.Printf("Размер структуры MiniNode: %d байт\n\n", unsafe.Sizeof(MiniNode{}))

	// Демонстрация упаковки нескольких объектов в один 16-байтный блок
	nodes := make([]*MiniNode, 8)
	for i := 0; i < len(nodes); i++ {
		nodes[i] = &MiniNode{Flag: true, Code: int8(i)}
	}

	fmt.Println("Адреса последовательно созданных MiniNode:")
	for i, n := range nodes {
		addr := uintptr(unsafe.Pointer(n))
		if i > 0 {
			prev := uintptr(unsafe.Pointer(nodes[i-1]))
			fmt.Printf("  [%d] 0x%x (дельта с предыдущим: %d байт)\n", i, addr, addr-prev)
		} else {
			fmt.Printf("  [%d] 0x%x\n", i, addr)
		}
	}

	// Замер памяти на миллион структур
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	const count = 1_000_000
	millionNodes := make([]*MiniNode, count)
	for i := 0; i < count; i++ {
		millionNodes[i] = &MiniNode{Flag: true, Code: int8(i % 128)}
	}

	runtime.ReadMemStats(&m2)
	allocated := m2.HeapAlloc - m1.HeapAlloc

	fmt.Printf("\nПамять под %d MiniNode: %d КБ (в среднем %.2f байт на узел)\n",
		count, allocated/1024, float64(allocated)/count)
	fmt.Println("Без Tiny Allocator каждый объект занимал бы минимум 8-16 байт в спане!")

	runtime.KeepAlive(nodes)
	runtime.KeepAlive(millionNodes)
}
```

**`Терминал`**

```bash
go run tiny_allocator.go
```

## Под капотом

В функции `mallocgc`:
```go
off := c.tinyoffset
// Выравнивание смещения
off = alignUp(off, size)
if off+size <= maxTinySize && c.tiny != 0 {
    // Успех! Объект помещается в текущий tiny блок
    x = unsafe.Pointer(c.tiny + off)
    c.tinyoffset = off + size
    c.tinyAllocs++
    return x
}
// Иначе аллоцируем новый 16-байтный слот из spanclass tiny
```
Поскольку весь 16-байтный блок не содержит указателей (`noscan`), GC маркирует его целиком одним битом в `gcmarkBits`.

## Подводные камни

1. Если хотя бы один из крошечных объектов внутри 16-байтного блока остается достижимым (живым), сборщик мусора не может освободить весь 16-байтный блок. Это может вызывать небольшое удержание неиспользуемой памяти.
2. Не пытайтесь складывать в Tiny Allocator структуры с указателями или интерфейсами — они автоматически дисквалифицируются и идут в Small Allocator.

## На собеседовании

**Вопрос с собеседования:** Какой выигрыш дает Tiny Allocator в реальных сценариях (например, сетевые сервисы, парсеры JSON/Protobuf)?
**Ответ:** В сетевых сервисах создаются миллиарды короткоживущих строк, слайсов чисел, булевых флагов и мелких структур размером 1–4 байта. Без Tiny Allocator минимальный слот аллокатора составлял бы 8 байт (а на 64-битных ОС часто 16 байт), что приводило бы к потере 75–87% памяти на внутреннюю фрагментацию. Tiny Allocator пакует их в один блок, снижая расход RAM в 3–5 раз и ускоряя аллокацию до пары процессорных инструкций.
