# Архитектура аллокатора памяти Go (TCMalloc)

## Условие

**Архитектура аллокатора (TCMalloc)**: Опишите трехуровневую иерархию аллокатора кучи Go в комментариях к коду [483]:
* `mcache` — персональный локальный кэш каждого процессора `P` для сверхбыстрой аллокации мелких объектов без блокировок [483].
* `mcentral` — центральный пул свободных спанов, сгруппированных по классам размеров (size classes), защищенный мьютексом [483].
* `mheap` — глобальная куча, запрашивающая страницы памяти напрямую у операционной системы [483].

## Теория

Аллокатор кучи Go основан на архитектуре TCMalloc (Thread-Caching Malloc), адаптированной для работы в рантайме Go поверх абстракции планировщика GMP.

Вместо привязки к потокам ОС (Threads), как в классическом C++ TCMalloc, локальный кэш в Go привязан к логическим процессорам \(P\) (Processor). Это обеспечивает трехуровневую иерархию:
1. **`mcache` (L1 кэш):** У каждого \(P\) есть собственный дескриптор `mcache`. Поскольку горутина выполняется на конкретном \(P\) в однопоточном режиме, выделение памяти из `mcache` происходит **без единой атомарной блокировки** (Lock-Free Fast Path).
2. **`mcentral` (L2 пул):** Центральное хранилище спанов (`mspan`), сгруппированное по классам размеров (всего 67 классов). Доступ к `mcentral` защищен мьютексом. Сюда \(P\) обращается, только когда в его `mcache` закончились свободные ячейки заданного размера.
3. **`mheap` (L3 глобальная куча):** Управляет всей виртуальной памятью процесса, разбитой на страницы по 8 КБ. Выделяет спаны для `mcentral` и запрашивает арены памяти у ядра ОС через системные вызовы `mmap` (Linux) или `VirtualAlloc` (Windows).

## Решение по шагам

1. Напишите демонстрационную программу с подробным документированием трехуровневой архитектуры в комментариях.
2. Продемонстрируйте выделение объектов различных размеров в куче.
3. С помощью `runtime.ReadMemStats` снимите показания системных счетчиков кучи `HeapAlloc`, `HeapSys` и `HeapInuse`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

// Демонстрация трехуровневой модели аллокатора TCMalloc в Go:
//
// 1. mcache:  Per-P кэш (Lock-free). Запрос до 32 КБ обслуживается за единицы наносекунд.
// 2. mcentral: Central pool по классам размеров (с блокировкой спинлока).
// 3. mheap:    Глобальная куча (8 КБ страницы, arenas, обращение к ОС через mmap).

type SmallObject struct {
	ID   int64
	Data [24]byte
}

func main() {
	var m1, m2 runtime.MemStats
	runtime.ReadMemStats(&m1)

	// Аллоцируем 1000 небольших объектов (размер 32 байта, обслуживаются mcache)
	holders := make([]*SmallObject, 1000)
	for i := 0; i < len(holders); i++ {
		holders[i] = &SmallObject{ID: int64(i)}
	}

	runtime.ReadMemStats(&m2)

	fmt.Println("=== Архитектура TCMalloc в Go ===")
	fmt.Printf("Логических P (mcache пулов): %d\n", runtime.GOMAXPROCS(0))
	fmt.Printf("HeapAlloc (живые объекты)  : %d байт\n", m2.HeapAlloc-m1.HeapAlloc)
	fmt.Printf("HeapInuse (занятые спаны)  : %d байт\n", m2.HeapInuse)
	fmt.Printf("HeapSys   (память от ОС)   : %d байт\n", m2.HeapSys)
	fmt.Printf("Всего mallocs              : %d\n", m2.Mallocs-m1.Mallocs)

	_ = holders
}
```

**`Терминал`**

```bash
go run main.go
```

## Под капотом

В исходниках Go (`src/runtime/malloc.go`) функция `mallocgc(size uintptr, typ *_type, needzero bool) unsafe.Pointer` координирует все три уровня:
- Если `size <= maxSmallSize` (32 КБ), запрашивается span нужного класса из `getg().m.p.ptr().mcache.alloc[spc]`.
- Если спан в `mcache` пуст, вызывается `mcache.refill(spc)`, обращающийся к `mcentral[spc]` с захватом блокировки `mcentral.lock`.
- Если и в `mcentral` нет свободных спанов, вызывается `mheap_.alloc(npages, spc)`, которая выделяет страницы из bitmap-аллокатора `pageAlloc`.

## Подводные камни

1. Ошибочно полагать, что `mcache` привязан к потокам ОС \(M\). В Go `mcache` привязан к логическим процессорам \(P\). При переключении горутины на другой \(M\) горутина использует `mcache` того \(P\), на котором она сейчас исполняется.
2. Объекты размером более 32 КБ считаются Large Objects и никогда не попадают в `mcache` или `mcentral` — они сразу выделяются из `mheap` под глобальным локом.

## На собеседовании

**Вопрос с собеседования:** Почему в Go аллокатор памяти привязан к абстракции \(P\) (Processor), а не к \(M\) (OS Thread) или \(G\) (Goroutine)?
**Ответ:** 
- Если бы кэш был у \(G\), миллионы горутин расходовали бы гигабайты памяти на структуры аллокатора.
- Если бы кэш был у \(M\), то при блокировке потока на системном вызове память в его кэше простаивала бы впустую.
- Число \(P\) строго ограничено значением `GOMAXPROCS` (обычно равно числу ядер CPU). Привязка к \(P\) гарантирует, что число локальных кэшей минимально, конкуренция между ядрами отсутствует, а память расходуется предельно эффективно.
