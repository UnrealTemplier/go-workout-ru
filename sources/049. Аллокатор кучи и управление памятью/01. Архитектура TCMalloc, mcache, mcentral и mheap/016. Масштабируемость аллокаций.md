# Масштабируемость аллокаций: mcache при GOMAXPROCS=1 vs 8

## Условие

**[mcache (Per-P Cache)]**: Напиши бенчмарк, который аллоцирует много мелких объектов. Установи `GOMAXPROCS=1` и `GOMAXPROCS=8`. Объясни, почему при большем числе P аллокация быстрее (у каждого P свой локальный кэш `mcache`, не нужны блокировки).

## Теория

Главная причина масштабируемости Go на многоядерных архитектурах (NUMA, 64-128 ядер) — архитектура **Per-P Cache (`mcache`)**.

В классических аллокаторах с глобальной блокировкой кучи (Global Heap Lock) увеличение числа потоков приводит к лавинообразному росту contention (соперничества за мьютекс), и производительность деградирует.
В Go:
- У каждого \(P\) свой персональный массив спанов `mcache`.
- Когда 8 горутин работают на 8 \(P\), они выделяют память **в 8 независимых регионах кэша одновременно**, не обращаясь к шине памяти и не вызывая инвалидации кэш-линий (False Sharing).
- Время на одну аллокацию остается константным, а суммарная пропускная способность растет линейно.

## Решение по шагам

1. Создайте параллельный бенчмарк `BenchmarkAllocScale`.
2. Запустите его с флагами `-cpu=1` и `-cpu=8`.
3. Сравните суммарную пропускную способность (`ns/op`) и убедитесь в отсутствии блокировок.

## Код решения

**`scale_test.go`**

```go
package main

import (
	"runtime"
	"testing"
)

type WorkItem struct {
	A, B, C, D int64
}

// Параллельный бенчмарк аллокации
func BenchmarkAllocScale(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			// Выделение памяти из локального mcache текущего P
			item := &WorkItem{A: 1, B: 2, C: 3, D: 4}
			runtime.KeepAlive(item)
		}
	})
}
```

ℹ️ Бенчмарк масштабируемости аллокатора при разном числе P

**`Терминал`**

```bash
go test -bench=BenchmarkAllocScale -cpu=1,2,4,8 scale_test.go
```

## Под капотом

В `src/runtime/proc.go` при инициализации или изменении `GOMAXPROCS` вызывается `procresize(nprocs int32)`.
Для каждого нового \(P\) рантайм вызывает `allocmcache()`:
`pp.mcache = allocmcache()`
Дескриптор `mcache` аллоцируется в специальной области памяти рантайма (`mheap_.cachealloc`), не подверженной сборке мусора.
Благодаря этому доступ к полям `p.mcache` гарантированно локален для текущего процессорного ядра.

## Подводные камни

1. Линейный рост скорости аллокаций возможен только до тех пор, пока хватает пропускной способности аппаратной шины памяти процессора (Memory Bandwidth). При сотнях ядер шина памяти DRAM становится физическим ограничителем.
2. Частые аллокации создают работу для GC, который периодически отбирает 25% CPU на разметку (GC CPU fraction).

## На собеседовании

**Вопрос с собеседования:** Что произойдет с `mcache`, если в рантайме на лету динамически уменьшить `runtime.GOMAXPROCS(2)` с прежних 8?
**Ответ:** Лишние процессоры \(P\) (с индексами от 2 до 7) будут переведены в статус `_Pidle` и отвязаны. Для каждого деактивированного \(P\) рантайм вызовет `freemcache(p.mcache)`. Все удерживаемые спаны из их `mcache` будут аккуратно сброшены обратно в соответствующие `mcentral`, предотвращая утечку свободных слотов памяти.
