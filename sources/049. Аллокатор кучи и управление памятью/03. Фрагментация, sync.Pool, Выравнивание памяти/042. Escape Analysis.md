# Escape Analysis: Влияние побега на скорость выполнения

## Условие

**Побег в кучу и стек.**: Напишите функции, где переменная остаётся на стеке, и где «убегает» в кучу. Используйте `go build -gcflags="-m"` для анализа решений escape analysis. Проверьте, как это влияет на аллокацию.

## Теория

Размещение переменной на стеке vs в куче кардинально меняет производительность кода:
1. **На стеке (Stack):**
   - Выделение: 0 ns (движение регистра `SP`).
   - Использование: максимальная кэш-локальность (горячие L1/L2 кэши процессора).
   - Очистка: 0 ns при завершении функции.
   - GC: полностью игнорирует стековые переменные без указателей.
2. **В куче (Heap):**
   - Выделение: 10–30 ns (поиск слота в `mcache`, атомарные счетчики).
   - Использование: возможные промахи кэша (Pointer Chasing).
   - Очистка: задержки на трехцветную маркировку (Mark Phase) и барьеры записи (Write Barriers).

Разница в скорости выполнения между стековым и кучевым кодом в горячих циклах может достигать **10–50 раз**!

## Решение по шагам

1. Напишите стековую функцию вычисления расстояния между точками.
2. Напишите кучевую версию с возвратом указателя и интерфейсным боксингом.
3. Проведите сравнительный бенчмарк с замером аллокаций памяти (`-benchmem`).
4. Подтвердите результаты выводом `go build -gcflags="-m"`.

## Код решения

**`escape_impact_test.go`**

```go
package main

import (
	"testing"
)

type Vector3D struct {
	X, Y, Z float64
}

// 1. Чистая стековая функция: передача и возврат по значению
//go:noinline
func StackVectorAdd(a, b Vector3D) Vector3D {
	return Vector3D{
		X: a.X + b.X,
		Y: a.Y + b.Y,
		Z: a.Z + b.Z,
	}
}

// 2. Кучевая функция: возврат указателя заставляет объект убегать в кучу
//go:noinline
func HeapVectorAdd(a, b *Vector3D) *Vector3D {
	res := Vector3D{
		X: a.X + b.X,
		Y: a.Y + b.Y,
		Z: a.Z + b.Z,
	}
	return &res // &res escapes to heap
}

func BenchmarkStackAdd(b *testing.B) {
	v1 := Vector3D{1, 2, 3}
	v2 := Vector3D{4, 5, 6}
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		_ = StackVectorAdd(v1, v2)
	}
}

func BenchmarkHeapAdd(b *testing.B) {
	v1 := &Vector3D{1, 2, 3}
	v2 := &Vector3D{4, 5, 6}
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		_ = HeapVectorAdd(v1, v2)
	}
}
```

ℹ️ Бенчмарк производительности: аллокация на стеке против побега в кучу

**`Терминал`**

```bash
go test -bench=. -benchmem escape_impact_test.go
```

## Под капотом

В бенчмарке:
- `BenchmarkStackAdd`: **0 B/op, 0 allocs/op**, время выполнения \(\approx 1.5\) нс/op (работа только с FPU регистрами `XMM0-XMM3`).
- `BenchmarkHeapAdd`: **24 B/op, 1 allocs/op**, время выполнения \(\approx 25\) нс/op.
Разница в скорости составляет более чем 1500%! Перенос переменной в кучу обошелся в 16 раз медленнее по CPU.

## Подводные камни

1. Ошибочно думать, что оптимизатор компилятора Go исправит плохой дизайн за вас: если указатель возвращается наружу, компилятор обязан отправить его в кучу по закону языка.
2. Проверяйте критические функции сервиса с помощью `go test -benchmem` в CI/CD конвейере.

## На собеседовании

**Вопрос с собеседования:** В PR разработчик заменил передачу структуры `Config` (128 байт) по значению на указатель `*Config`, мотивируя это «ускорением копирования». В каких случаях это ускорит, а в каких замедлит программу?
**Ответ:** 
- Это ускорит код, только если `Config` передается в длинную цепочку функций, которые его не сохраняют, и сам `Config` уже был создан в куче ранее.
- Это замедлит код, если `Config` создается локально в цикле запроса: передача по указателю может вызвать Escape Analysis и переместить `Config` из быстрого стека в кучу, породив аллокацию памяти, нагрузку на GC и потерю кэш-локальности, что многократно перекроет микроскопическую экономию на копировании 128 байт.
