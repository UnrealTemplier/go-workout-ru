# Возврат страниц операционной системе через madvise MADV_DONTNEED

## Условие

**[MADV_DONTNEED]**: Изучи, как Go возвращает память ОС. Если `HeapIdle` сильно больше `HeapInuse`, рантайм отправляет `madvise(MADV_DONTNEED)` страницам. Напиши программу, которая аллоцирует 1GB, освобождает его, и подожди. Проследи через `top`, как RSS процесса падает не сразу, а спустя десятки секунд.

## Теория

Когда сборщик мусора GC завершает цикл, освобожденная память не возвращается ядру Linux немедленно.

Почему так устроено:
1. Системный вызов `madvise(addr, len, MADV_DONTNEED)` является относительно дорогой операцией: он блокирует структуры виртуальной памяти процесса в ядре Linux (`mmap_lock`) и инициирует сброс физических Page Frames.
2. Если бы Go вызывал `madvise` немедленно после каждого GC, то при следующей пачке входящих запросов рантайму пришлось бы заново вызывать Page Faults у процессора, приводя к падению RPS.
3. Фоновый процесс **Scavenger** выполняет ленивый возврат: он отслеживает соотношение `HeapIdle` к `HeapInuse` и порциями отправляет неиспользуемые 8 КБ страницы ядру Linux с лимитом не более 1% CPU.
4. В результате Resident Set Size (RSS) процесса в выводе `top` падает плавно в течение десятков секунд.

## Решение по шагам

1. Напишите код, выделяющий 500 МБ данных в куче и физически заполняющий страницы.
2. Сбросьте ссылку и запустите `runtime.GC()`.
3. Отследите рост `HeapIdle` и постепенное увеличение `HeapReleased`.
4. Наблюдайте за падением RSS процесса через чтение `/proc/self/statm`.

## Код решения

**`madvise_scavenge.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"strconv"
	"strings"
	"time"
)

// Чтение Resident Set Size (RSS) процесса из /proc/self/statm на Linux
func getRSS() int {
	data, err := os.ReadFile("/proc/self/statm")
	if err != nil {
		return 0
	}
	fields := strings.Fields(string(data))
	if len(fields) >= 2 {
		pages, _ := strconv.Atoi(fields[1])
		return pages * 4 / 1024 // 4 КБ страницы Linux -> МБ
	}
	return 0
}

func main() {
	fmt.Println("=== Исследование задержки madvise (MADV_DONTNEED) ===")
	fmt.Printf("Начальный RSS процесса: %d МБ\n\n", getRSS())

	// 1. Выделяем 500 МБ памяти
	fmt.Println("Аллоцируем 500 МБ памяти в куче...")
	buf := make([]byte, 500*1024*1024)
	for i := 0; i < len(buf); i += 4096 {
		buf[i] = 1
	}
	fmt.Printf("RSS после аллокации: %d МБ\n", getRSS())

	// 2. Сбрасываем ссылку и запускаем сборку мусора
	fmt.Println("\nОбнуляем указатель и вызываем runtime.GC()...")
	buf = nil
	runtime.GC()

	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("HeapAlloc сразу после GC: %d МБ (объекты удалены)\n", m.HeapAlloc/(1024*1024))
	fmt.Printf("HeapIdle  сразу после GC: %d МБ (удерживается в пуле)\n", m.HeapIdle/(1024*1024))
	fmt.Printf("RSS сразу после GC      : %d МБ (ОС еще не вернула память!)\n\n", getRSS())

	// 3. Ждем работы фонового Scavenger
	fmt.Println("Ожидание фонового Scavenger (наблюдаем за RSS):")
	for i := 1; i <= 4; i++ {
		time.Sleep(1 * time.Second)
		runtime.ReadMemStats(&m)
		fmt.Printf("  [Секунда %d] RSS: %3d МБ | HeapReleased: %3d МБ\n",
			i, getRSS(), m.HeapReleased/(1024*1024))
	}
}
```

ℹ️ Прямое отслеживание изменения RSS процесса и метрики HeapReleased

**`Терминал`**

```bash
go run madvise_scavenge.go
```

## Под капотом

В `src/runtime/mgcscavenge.go` поток Scavenger:
1. Вызывает `pageAlloc.scavenge(maxPages)`.
2. Сканирует битовую карту свободных страниц и находит блоки, не тронутые дольше определенного времени.
3. Вызывает `sysUnused(addr, size)` -> `madvise(addr, size, MADV_DONTNEED)`.
4. Ядро Linux сбрасывает аппаратные таблицы страниц (PTE), уменьшая счетчик `RSS` в `task_struct` процесса.
5. При этом виртуальный диапазон `HeapSys` остается зарезервированным.

## Подводные камни

1. На старых ядрах Linux без поддержки `MADV_DONTNEED` или в эмуляторах поведение может отличаться.
2. Если в контейнере K8s память подошла к пределу `limits.memory`, полагаться на пассивный Scavenger рискованно — используйте `GOMEMLIMIT` для автоматической активации скейвенджера.

## На собеседовании

**Вопрос с собеседования:** Почему после вызова `runtime.GC()` метрика `HeapAlloc` мгновенно падает до 10 МБ, а метрика `container_memory_working_set_bytes` в Prometheus остается на уровне 500 МБ еще минуту?
**Ответ:** Потому что `HeapAlloc` отражает логическое состояние кучи Go (живые объекты), а метрика контейнера в Prometheus считывает фактический Resident Set Size (RSS) ядра Linux из контрольной группы cgroups. Память физически освобождается только тогда, когда фоновый Scavenger рантайма выполнит системный вызов `madvise(MADV_DONTNEED)` для неиспользуемых страниц `HeapIdle`, что происходит постепенно с задержкой в десятки секунд для экономии CPU.
