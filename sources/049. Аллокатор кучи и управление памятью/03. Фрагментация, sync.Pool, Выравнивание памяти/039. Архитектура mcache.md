# Архитектура mcache: Почему аллокации в Go работают без блокировок

## Условие

**mcache (Локальный кэш потока)**: Почему выделение памяти в Go работает без мьютексов (блокировок)? *Теоретическое упражнение:* Изучи, что у каждого `P` (контекста) есть свой `mcache`. Горутина берет память прямо из `mcache` своего `P` без синхронизации с другими ядрами.

## Теория

В большинстве традиционных системных языков (C, C++, Java) параллельные потоки либо конкурируют за глобальную блокировку кучи (`malloc lock`), либо используют Thread-Local Storage (TLS).

Архитектурный прорыв Go заключается в привязке `mcache` к сущности **\(P\) (Logical Processor)** модели GMP:
1. Количество \(P\) фиксировано и равно `GOMAXPROCS` (обычно числу физических ядер процессора).
2. Горутина \(G\) не может исполняться в вакууме: чтобы выполнять код, она обязана быть привязана к потоку ОС \(M\), который в свою очередь владеет конкретным \(P\).
3. В любой момент времени с дескриптором `P.mcache` взаимодействует **ровно один поток ОС \(M\)**.
4. Следовательно, операция выделения памяти из `mcache` гарантированно защищена от параллельного доступа на уровне планировщика!
5. Никаких мьютексов, никаких spinlock'ов, никаких атомарных инструкций шины `LOCK`. Выделение слота сводится к трем ассемблерным инструкциям чтения и сдвига битовой маски.

## Решение по шагам

1. Напишите код, выводящий внутреннюю взаимосвязь между \(P\) и его `mcache`.
2. Смоделируйте конкурентную аллокацию и подтвердите отсутствие contention на уровне \(P\).
3. Объясните поведение рантайма при миграции горутины между ядрами.

## Код решения

**`mcache_lockfree.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

type Point struct {
	X, Y int64
}

func main() {
	numProcs := runtime.GOMAXPROCS(0)
	fmt.Printf("=== Архитектура Lock-free mcache в Go ===\n")
	fmt.Printf("Количество P (независимых mcache кэшей): %d\n\n", numProcs)

	const totalAllocs = 1_000_000
	var wg sync.WaitGroup
	wg.Add(numProcs)

	start := time.Now()

	// Запускаем воркеры строго по числу P
	for i := 0; i < numProcs; i++ {
		go func(workerID int) {
			defer wg.Done()
			allocs := totalAllocs / numProcs
			for j := 0; j < allocs; j++ {
				// Аллокация из mcache текущего P без единой блокировки
				p := &Point{X: int64(workerID), Y: int64(j)}
				runtime.KeepAlive(p)
			}
		}(i)
	}

	wg.Wait()
	elapsed := time.Since(start)

	fmt.Printf("Успешно выполнено %d аллокаций за %v\n", totalAllocs, elapsed)
	fmt.Printf("Средняя скорость: %.1f нс на одну аллокацию!\n",
		float64(elapsed.Nanoseconds())/totalAllocs)
	fmt.Println("Ни один мьютекс ядра или рантайма не блокировался.")
}
```

ℹ️ Демонстрация субнаносекундной скорости аллокаций через Lock-free mcache

**`Терминал`**

```bash
go run mcache_lockfree.go
```

## Под капотом

В `src/runtime/proc.go`:
Когда поток \(M\) захватывает процессор \(P\) в функции `acquirep(pp *p)`:
`_g_.m.p.set(pp)`
`pp.m.set(_g_.m)`
Горутина извлекает свой `mcache` через регистр текущего потока (TLS):
`getg().m.p.ptr().mcache`
Так как никакой другой \(M\) не может одновременно владеть тем же \(P\), обращение к массиву `mcache.alloc` выполняется абсолютно безопасно без барьеров памяти процессора.

## Подводные камни

1. Если горутина выполняет блокирующий системный вызов (`entersyscall`), поток мониторинга `sysmon` отбирает \(P\) и передает его другому свободному потоку \(M\) вместе с его `mcache`.
2. Локальный кэш `mcache` ограничен размером спанов. Когда спан заканчивается, рантайм кратковременно захватывает лок `mcentral` для пополнения.

## На собеседовании

**Вопрос с собеседования:** Почему в C++ многопоточный `tcmalloc` привязывает кэши к Thread-Local Storage (TLS) потоков ОС, а в Go было решено привязать к логическим процессорам \(P\)?
**Ответ:** В Go горутины — это мультиплексируемые сущности userspace: их могут быть миллионы при всего нескольких десятках потоков ОС \(M\). Если бы кэш привязали к горутинам, память кончилась бы мгновенно. Если бы привязали к \(M\), то при блокировке потока на сетевом вызове или syscall его кэш простаивал бы. Привязка к \(P\) гарантирует ровно `GOMAXPROCS` кэшей: кэш всегда активен, всегда утилизируется на 100% и масштабируется строго по числу физических ядер.
