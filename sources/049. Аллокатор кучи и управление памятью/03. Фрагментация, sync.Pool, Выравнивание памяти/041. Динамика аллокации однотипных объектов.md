# Динамика аллокации однотипных объектов: HeapSys vs HeapAlloc

## Условие

Напишите программу, которая аллоцирует объекты одного размера (например, 96 байт) в цикле. Через `runtime.ReadMemStats` покажите рост `HeapSys` vs `HeapAlloc`. Объясните разницу: `HeapSys` — память у ОС, `HeapAlloc` — реально занятая.

## Теория

При аллокации множества объектов фиксированного класса размера (например, 96 байт — Size Class 8) наблюдается интересная динамика:
- `HeapAlloc` растет плавно и линейно: каждый новый объект прибавляет ровно 96 байт к счетчику живых данных.
- `HeapSys` растет дискретными скачками: рантайм запрашивает у ОС страницы аренами по 64 МБ только тогда, когда в ранее выделенных спанах закончились физические страницы.

Разница между ними:
- `HeapAlloc`: суммарный вес фактически созданных структур данных программы.
- `HeapSys`: общий объем виртуальной памяти, которую рантайм зарезервировал у ядра Linux для поддержания кучи, метаданных и стеков.

## Решение по шагам

1. Создайте структуру размером ровно 96 байт.
2. В цикле аллоцируйте 500 000 таких объектов, периодически выводя показания `HeapAlloc` и `HeapSys`.
3. Проанализируйте ступени роста `HeapSys` по сравнению с плавным ростом `HeapAlloc`.

## Код решения

**`alloc96.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

// Структура ровно 96 байт (Size Class 8 в Go)
type Object96 struct {
	Data [12]int64 // 12 * 8 = 96 байт
}

func main() {
	fmt.Printf("Размер Object96: %d байт (Size Class 8)\n\n", unsafe.Sizeof(Object96{}))

	const total = 500_000
	storage := make([]*Object96, total)

	var m runtime.MemStats

	fmt.Printf("%-10s %-15s %-15s %-15s\n", "Объектов", "HeapAlloc (МБ)", "HeapSys (МБ)", "Разница (МБ)")
	fmt.Println("------------------------------------------------------------")

	for i := 0; i < total; i++ {
		storage[i] = &Object96{}

		if (i+1)%100_000 == 0 {
			runtime.ReadMemStats(&m)
			allocMB := m.HeapAlloc / (1024 * 1024)
			sysMB := m.HeapSys / (1024 * 1024)
			diffMB := sysMB - allocMB
			fmt.Printf("%-10d %-15d %-15d %-15d\n", i+1, allocMB, sysMB, diffMB)
		}
	}

	runtime.KeepAlive(storage)
}
```

ℹ️ Сравнение плавного роста HeapAlloc и ступенчатого роста HeapSys

**`Терминал`**

```bash
go run alloc96.go
```

## Под капотом

В `src/runtime/sizeclasses.go`:
Класс 8:
- `size = 96` байт
- `npages = 3` страницы (\(3 \times 8192 = 24576\) байт)
- `nelems = 256` объектов в одном спане.
- `tail waste = 0` байт (\(256 \times 96 = 24576\)).
Каждый новый спан вмещает ровно 256 объектов. Пока эти 256 слотов заполняются, память выделяется без обращения к операционной системе.
Только когда заполняются все страницы текущей арены, происходит системный вызов расширения `HeapSys`.

## Подводные камни

1. Не путайте `HeapSys` с общим `Sys` в `MemStats`: показатель `Sys` включает в себя память стеков горутин, метаданные типов, кэши профайлера и структуры планировщика.
2. В высоконагруженных микросервисах полезно следить за отношением `HeapAlloc / HeapSys`: если оно падает ниже 0.3, куча сильно фрагментирована.

## На собеседовании

**Вопрос с собеседования:** Если метрика `HeapAlloc` показывает 200 МБ, а контейнер в Kubernetes падает по лимиту памяти 500 МБ, какие компоненты рантайма Go могут потреблять оставшиеся 300 МБ?
**Ответ:** 
1. `HeapIdle` (свободные страницы в аренах кучи, еще не сброшенные скейвенджером).
2. `StackInuse` (память стеков активных горутин, не входящая в `HeapAlloc`).
3. Метаданные рантайма: `MSpanSys`, `MCacheSys`, `GCSys`.
4. Память, выделенная вне кучи Go через Cgo / `libc malloc` или системные вызовы `mmap`.
5. Фрагментация страниц в аллокаторе ядра ОС.
