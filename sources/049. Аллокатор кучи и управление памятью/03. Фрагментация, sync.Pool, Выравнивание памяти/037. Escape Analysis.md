# Escape Analysis: Сравнение Heap vs Stack на практике

## Условие

**[Escape Analysis (Heap vs Stack)]**: Напиши функцию, которая возвращает указатель на локальную переменную. Запусти `go build -gcflags="-m"`. Убедись, что переменная "утекла" в кучу (escapes to heap). Напиши другую функцию, которая не возвращает указатель, и убедись, что аллокация произошла на стеке (не требует работы GC).

## Теория

Escape Analysis компилятора Go является гарантией безопасности памяти:
- В C++ возврат указателя на стековую переменную приводит к Undefined Behavior и уязвимостям безопасности (Dangling Pointer / Stack Smashing).
- В Go компилятор анализирует граф потока данных: если указатель на переменную возвращается из функции наружу, компилятор переписывает генерацию кода, аллоцируя эту переменную в куче через `runtime.newobject`.
- Если же переменная возвращается по значению (копированием) или используется только локально, она размещается на стеке текущей горутины.

## Решение по шагам

1. Напишите функцию `createOnStack() int`.
2. Напишите функцию `createOnHeap() *int`.
3. Скомпилируйте файл с ключами `-gcflags="-m"`.
4. Сопоставьте вывод компилятора с поведением памяти в ассемблере.

## Код решения

**`heap_vs_stack.go`**

```go
package main

import "fmt"

// 1. Аллокация на стеке: переменная не выходит за пределы стекового фрейма
//go:noinline
func createOnStack() int {
	x := 100
	return x // x копируется в регистр процессора AX
}

// 2. Аллокация в куче: указатель возвращается наружу
//go:noinline
func createOnHeap() *int {
	x := 200
	return &x // &x escapes to heap
}

func main() {
	stackVal := createOnStack()
	heapPtr := createOnHeap()

	fmt.Printf("Stack value: %d\n", stackVal)
	fmt.Printf("Heap value : %d (адрес: %p)\n", *heapPtr, heapPtr)
}
```

ℹ️ Практическая проверка решений Escape Analysis компилятора Go

**`Терминал`**

```bash
go build -gcflags="-m" heap_vs_stack.go
```

## Под капотом

В выводе `go build -gcflags="-m"`:
```text
./heap_vs_stack.go:14:9: &x escapes to heap
./heap_vs_stack.go:13:2: moved to heap: x
```
Фраза `moved to heap: x` означает, что компилятор удалил переменную `x` из стекового фрейма функции `createOnHeap` и полностью перенес её аллокацию в кучу через внутренний вызов `runtime.newobject(type:int)`.

## Подводные камни

1. Чрезмерное использование указателей там, где достаточно обычных значений (например, `*int`, `*bool`), создает бессмысленную нагрузку на аллокатор кучи.
2. Не забывайте директиву `//go:noinline`: без неё компилятор может заинлайнить обе функции в `main()`, и переменная `x` из `createOnHeap` может остаться на стеке `main`!

## На собеседовании

**Вопрос с собеседования:** Если функция возвращает указатель `&x`, может ли компилятор Go при определенных условиях ВСЕ-ТАКИ оставить `x` на стеке?
**Ответ:** Да! Если функция `foo()` возвращает `&x`, но компилятор выполняет **инлайнинг (Inlining)** этой функции в точку вызова (например, в функцию `bar()`), и в функции `bar()` указатель никуда дальше не утекает, компилятор оставляет переменную `x` на стеке `bar()`. Инлайнинг нейтрализует побег в кучу.
