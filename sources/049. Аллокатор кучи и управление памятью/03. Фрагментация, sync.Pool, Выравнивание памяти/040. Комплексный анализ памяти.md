# Комплексный анализ памяти: HeapAlloc, HeapSys и HeapIdle

## Условие

**[Высокая сложность — memstats]**: Напиши программу, которая в цикле аллоцирует и отбрасывает объекты. Раз в секунду выводи `runtime.ReadMemStats()`. Проанализируй `HeapAlloc` (сколько сейчас занято), `HeapSys` (сколько запрошено у ОС), `HeapIdle` (пустые страницы). Убедись, что `HeapSys` не падает до нуля сразу после очистки (Go не сразу возвращает память ОС).

## Теория

Понимание метрик структуры `runtime.MemStats` критически важно для диагностики памяти в HighLoad:
- **`HeapAlloc`:** Объем памяти в байтах, занятый живыми объектами кучи. При сборке мусора резко падает.
- **`HeapInuse`:** Объем памяти во всех активных спанах (включая занятые слоты и свободные слоты внутри частично заполненных спанов).
- **`HeapIdle`:** Объем памяти спанов, которые удерживаются рантаймом Go, но в данный момент не содержат живых объектов.
- **`HeapReleased`:** Часть `HeapIdle`, которая уже физически возвращена ядру ОС через `madvise(MADV_DONTNEED)`.
- **`HeapSys`:** Общий объем виртуальной памяти, запрошенный рантаймом у ОС (`HeapInuse + HeapIdle`).

`HeapSys` практически никогда не падает до нуля, так как Go сохраняет виртуальные страницы для будущих нагрузок процесса.

## Решение по шагам

1. Напишите программу, которая циклически выделяет 100 МБ памяти, затем сбрасывает ссылку и запускает `runtime.GC()`.
2. Выводите подробные метрики `HeapAlloc`, `HeapSys`, `HeapIdle`, `HeapReleased` в каждой итерации.
3. Проанализируйте, почему `HeapSys` остается стабильным, а память курсирует между `HeapAlloc` и `HeapIdle`.

## Код решения

**`memstats_deep.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func logMemory(iteration int, phase string) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	fmt.Printf("[Итерация %d | %-12s] HeapAlloc=%4d МБ | HeapInuse=%4d МБ | HeapIdle=%4d МБ | HeapSys=%4d МБ | GC=%d\n",
		iteration, phase,
		m.HeapAlloc/(1024*1024),
		m.HeapInuse/(1024*1024),
		m.HeapIdle/(1024*1024),
		m.HeapSys/(1024*1024),
		m.NumGC,
	)
}

func main() {
	fmt.Println("=== Анализ динамики памяти runtime.MemStats ===")

	for iter := 1; iter <= 3; iter++ {
		// 1. Выделяем 100 МБ
		data := make([][]byte, 100)
		for i := 0; i < 100; i++ {
			data[i] = make([]byte, 1024*1024)
			data[i][0] = 1
		}
		logMemory(iter, "Allocated 100M")

		// 2. Сбрасываем ссылки и вызываем GC
		data = nil
		runtime.GC()
		logMemory(iter, "After GC")

		time.Sleep(500 * time.Millisecond)
	}

	fmt.Println("\nВывод: HeapAlloc падает после GC, но HeapSys удерживается в HeapIdle.")
}
```

ℹ️ Глубокий анализ перехода памяти между HeapAlloc, HeapInuse, HeapIdle и HeapSys

**`Терминал`**

```bash
go run memstats_deep.go
```

## Под капотом

Связь компонентов кучи выражается строгим инвариантом:
$$\text{HeapSys} = \text{HeapInuse} + \text{HeapIdle}$$
$$\text{HeapIdle} = \text{HeapReleased} + \text{HeapUnreleased}$$
Когда GC очищает неиспользуемые объекты:
1. Спаны без живых объектов переходят из `HeapInuse` в `HeapIdle`.
2. Они не удаляются системным вызовом `munmap`, а остаются в битовой карте `pageAlloc`.
3. При следующей аллокации аллокатор мгновенно берет готовые страницы из `HeapIdle` за 0 микросекунд, не беспокоя ядро ОС!

## Подводные камни

1. Ошибочно паниковать, увидев, что `HeapSys` не уменьшается после завершения обработки крупной пачки данных. Это штатное поведение эффективного пулинга памяти рантайма.
2. Реальную физическую память процесса в Linux определяет `RSS` (Resident Set Size), который снижается, когда `HeapIdle` переходит в `HeapReleased`.

## На собеседовании

**Вопрос с собеседования:** В мониторинге микросервиса `HeapAlloc = 50 MB`, а `HeapSys = 1 GB`. Является ли это утечкой памяти (Memory Leak)?
**Ответ:** Нет, это не обязательно утечка памяти. Такая ситуация означает, что ранее сервис пережил пиковый всплеск нагрузки (Spike), потребовавший 1 ГБ памяти, после чего сборщик мусора успешно очистил память, и 950 МБ перешли в состояние `HeapIdle` (готовы к повторному использованию). Утечкой памяти является только непрерывный монотонный рост метрики `HeapAlloc` после регулярных сборок GC.
