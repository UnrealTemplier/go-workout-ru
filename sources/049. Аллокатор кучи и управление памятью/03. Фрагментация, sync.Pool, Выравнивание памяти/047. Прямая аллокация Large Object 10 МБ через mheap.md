# Прямая аллокация Large Object 10 МБ через mheap

## Условие

**Large Allocations (Большие объекты)**: Выдели сразу большой срез `make([]byte, 10 * 1024 * 1024)` (10 МБ). Посмотри через трассировку или документацию, что объекты больше 32 КБ (Large Objects) обходят `mcache` и `mcentral` и выделяются напрямую из `mheap`.

## Теория

Выделение крупных массивов данных (например, 10 МБ буфера) принципиально отличается от создания мелких структур:
- Размер \(10 \times 1024 \times 1024 = 10\,485\,760\) байт.
- Это ровно **1280 страниц по 8192 байта**.
- Аллокатор `mallocgc` мгновенно определяет, что \(10 \text{ МБ} > 32 \text{ КБ}\) (`maxSmallSize`), и переключается на `largeAlloc()`.
- Функция `largeAlloc` напрямую захватывает `mheap_.lock` и запрашивает непрерывный блок из 1280 страниц в Radix Tree аллокатора страниц.
- Никаких поисков по классам размеров, никаких списков `mcentral`.

## Решение по шагам

1. Напишите код, аллоцирующий массив 10 МБ.
2. Продемонстрируйте расчет страниц и фиксацию изменений в `runtime.MemStats`.
3. Зафиксируйте в логах прямое обращение к глобальной куче.

## Код решения

**`large10m.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	const size10MB = 10 * 1024 * 1024
	const pageSize = 8192

	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	fmt.Printf("=== Выделение Large Object 10 МБ напрямую из mheap ===\n")
	fmt.Printf("Размер объекта: %d байт (10 МБ > 32 КБ)\n", size10MB)
	fmt.Printf("Требуется страниц по 8 КБ: %d страниц\n\n", size10MB/pageSize)

	// Аллоцируем 10 МБ
	start := time.Now()
	bigData := make([]byte, size10MB)
	// Активируем страницы физической памяти
	for i := 0; i < len(bigData); i += 4096 {
		bigData[i] = 1
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	fmt.Printf("Время аллокации: %v\n", elapsed)
	fmt.Printf("Прирост HeapAlloc: %d МБ\n", (m2.HeapAlloc-m1.HeapAlloc)/(1024*1024))
	fmt.Printf("Статус mcache: обойден на 100%%\n")

	runtime.KeepAlive(bigData)
}
```

ℹ️ Прямая аллокация Large Object 10 МБ в глобальной куче mheap

**`Терминал`**

```bash
go run large10m.go
```

## Под капотом

В `src/runtime/mheap.go`:
Метод `mheap.alloc(npages uintptr, spanclass spanClass)`:
1. Захватывает спинлок `mheap_.lock`.
2. Вызывает `pageAlloc.alloc(npages)`: Radix Tree находит диапазон из 1280 последовательных свободных бит.
3. Если непрерывный кусок из 1280 страниц не найден в существующих аренах, куча растет через `mheap.grow()`.
4. Создается новый дескриптор `mspan` с полями `npages = 1280`, `elemsize = 10485760`, `spanclass = 0`.
5. Лок освобождается.

## Подводные камни

1. Выделение огромных непрерывных блоков памяти подвержено внешней фрагментации: если суммарно свободно 100 МБ, но они разбиты на мелкие кусочки по 1 МБ, выделить 10 МБ непрерывный срез без расширения кучи невозможно.
2. Для потоковых данных разбивайте большие массивы на чанки по 32 КБ.

## На собеседовании

**Вопрос с собеседования:** Почему при частых аллокациях крупных срезов (например, 10 МБ) сервис начинает испытывать задержки даже при наличии свободного CPU?
**Ответ:** Потому что аллокация объектов \(> 32\) КБ требует захвата глобальной блокировки `mheap_.lock`. Если несколько потоков или горутин параллельно обрабатывают большие файлы или медиа-буферы, они выстраиваются в очередь к одному мьютексу кучи. Решение — использовать переиспользуемые пулы буферов (`sync.Pool`) или потоковую обработку (`io.Reader`/`io.Writer`) чанками фиксированного размера.
