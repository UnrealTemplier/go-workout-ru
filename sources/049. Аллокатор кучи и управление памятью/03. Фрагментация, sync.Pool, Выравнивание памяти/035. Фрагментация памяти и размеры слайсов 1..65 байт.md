# Фрагментация памяти и размеры слайсов 1..65 байт

## Условие

**Фрагментация и размер классов.**: Создайте слайсы байт разной ёмкости (1, 2, 3... 65 байт). Измерьте через `runtime.ReadMemStats` реальное потребление (`HeapInuse`, `HeapAlloc`). Сопоставьте с классами размеров (class_to_size в `runtime/sizeclasses.go`).

## Теория

При аллокации среза `make([]byte, N)` аллокатор выделяет под базовый массив память из ближайшего класса размера:
- \(N \in [1..8]\) байт \(\to\) класс 8 байт (при \(N=1\) потеря 7 байт / 87.5% внутренняя фрагментация).
- \(N \in [9..16]\) байт \(\to\) класс 16 байт.
- \(N \in [17..24]\) байт \(\to\) класс 24 байта.
- \(N \in [25..32]\) байт \(\to\) класс 32 байта.
- \(N \in [33..48]\) байт \(\to\) класс 48 байт (при \(N=33\) потеря 15 байт / 31.2%).
- \(N \in [49..64]\) байт \(\to\) класс 64 байта.
- \(N = 65\) байт \(\to\) класс 80 байт (потеря 15 байт / 18.7%).

Знание этой таблицы позволяет точно подбирать емкость слайсов для исключения паразитного расхода памяти.

## Решение по шагам

1. Напишите программу, которая для размеров от 1 до 65 байт рассчитывает фактический класс размера и процент потерь.
2. Проверьте реальное потребление памяти для срезов пограничных размеров (32, 33, 64, 65 байт).
3. Сопоставьте результаты с таблицей `class_to_size` рантайма Go.

## Код решения

**`slice_classes.go`**

```go
package main

import "fmt"

// Каноничные классы размеров Go до 80 байт из runtime/sizeclasses.go
var sizeClasses = []int{8, 16, 24, 32, 48, 64, 80}

func findClass(size int) int {
	for _, sc := range sizeClasses {
		if sc >= size {
			return sc
		}
	}
	return 96
}

func main() {
	testSizes := []int{1, 8, 9, 16, 17, 24, 25, 32, 33, 48, 49, 64, 65}

	fmt.Printf("%-10s %-12s %-12s %-10s\n",
		"Запрос (Б)", "Класс (Б)", "Потери (Б)", "Фрагментация")
	fmt.Println("--------------------------------------------------")

	for _, req := range testSizes {
		allocated := findClass(req)
		waste := allocated - req
		percent := float64(waste) / float64(allocated) * 100

		fmt.Printf("%-10d %-12d %-12d %5.1f%%\n",
			req, allocated, waste, percent)
	}

	fmt.Println("\nВывод: Запрос 33 байт выделяет 48 байт (+45% к запросу), а 65 байт выделяет 80 байт (+23%).")
}
```

ℹ️ Расчет внутренней фрагментации и попадания в size classes для слайсов 1..65 байт

**`Терминал`**

```bash
go run slice_classes.go
```

## Под капотом

Компилятор Go оптимизирует создание срезов:
Если размер среза константен и мал, компилятор на этапе сборки заменяет вызов `makeslice` на `new([ClassSize]byte)`.
Встроенная функция `append` при росте среза выбирает новую емкость `cap` не просто умножением на 2 или 1.25, а с округлением вверх до точного размера ближайшего `size class` (`roundupsize`), гарантируя нулевые потери в хвосте выделенного слота памяти!

## Подводные камни

1. Вызов `make([]byte, 0, 33)` выделяет ровно столько же памяти, сколько `make([]byte, 0, 48)`. Задавая `cap = 48`, вы получаете 15 дополнительных байт абсолютно бесплатно без единого лишнего байта в куче.
2. Мелкие строки и срезы размером 1 байт вызывают самую высокую относительную фрагментацию (87.5%).

## На собеседовании

**Вопрос с собеседования:** Как функция `append` в Go выбирает новую емкость слайса при переполнении, начиная с Go 1.18?
**Ответ:** 
1. Для срезов емкостью \(< 256\) элементов `cap` удваивается (\(2x\)).
2. Для срезов \(\ge 256\) элементов емкость плавно растет по формуле:
   $$\text{newcap} = \text{oldcap} + (\text{oldcap} + 3 \times 256) / 4$$
3. Полученное число байт передается в функцию `roundupsize(newcap * elemsize)`, которая **округляет размер до границы ближайшего Size Class** в аллокаторе Go. Это гарантирует, что выделенная память используется на 100% без остатка.
