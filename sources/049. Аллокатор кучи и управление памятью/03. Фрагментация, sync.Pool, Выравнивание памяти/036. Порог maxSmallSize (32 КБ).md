# Порог maxSmallSize (32 КБ) и архитектурные константы malloc

## Условие

Напишите программу с большим объектом (>32 KB по умолчанию). Покажите, что он идёт напрямую в `mheap` (large allocation). Найдите в исходниках порог (`maxSmallSize`, `pageSize`) и объясните, почему именно так.

## Теория

Константы аллокатора памяти Go зафиксированы в пакете `runtime`:
- `_PageShift = 13` \(\implies\) `pageSize = 8192` (8 КБ, размер страницы аллокатора Go).
- `_MaxSmallSize = 32768` (32 КБ, граница между Small и Large объектами).
- `_NumSizeClasses = 68` (число классов размеров).

Почему именно 32 КБ:
- Страница кучи Go равна 8 КБ. 32 КБ — это ровно 4 страницы.
- Объекты до 32 КБ эффективно группируются в спанах от 1 до 4 страниц (8 КБ – 32 КБ).
- Если бы порог был, например, 512 КБ, размер спана пришлось бы увеличивать до десятков страниц, что привело бы к раздуванию локального кэша `mcache` каждого потока \(P\) и неэффективному использованию памяти.

## Решение по шагам

1. Напишите код с объектом размером ровно 32768 байт (Small) и 32769 байт (Large).
2. Зафиксируйте в логах разницу в обработке этих двух объектов рантаймом.
3. Проанализируйте исходные константы `runtime/malloc.go`.

## Код решения

**`threshold.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

const (
	MaxSmallSize = 32768 // 32 КБ
	PageSize     = 8192  // 8 КБ
)

func main() {
	fmt.Printf("Архитектурные константы Go Runtime:\n")
	fmt.Printf("  PageSize     = %d байт (8 КБ)\n", PageSize)
	fmt.Printf("  MaxSmallSize = %d байт (32 КБ)\n\n", MaxSmallSize)

	// Объект 1: Ровно 32 КБ -> последний класс Small Objects (Класс 67)
	objSmall := make([]byte, MaxSmallSize)
	// Объект 2: 32 КБ + 1 байт -> первый Large Object (напрямую mheap)
	objLarge := make([]byte, MaxSmallSize+1)

	fmt.Printf("Объект 32768 Б (Small): адрес %p -> выделен через mcache (класс 67, 4 страницы)\n",
		&objSmall[0])
	fmt.Printf("Объект 32769 Б (Large): адрес %p -> выделен напрямую через mheap (5 страниц по 8КБ)\n",
		&objLarge[0])

	pagesSmall := (len(objSmall) + PageSize - 1) / PageSize
	pagesLarge := (len(objLarge) + PageSize - 1) / PageSize

	fmt.Printf("\nСтраниц под Small (32768B): %d страниц\n", pagesSmall)
	fmt.Printf("Страниц под Large (32769B): %d страниц (из-за 1 байта выделена 5-я страница!)\n", pagesLarge)

	runtime.KeepAlive(objSmall)
	runtime.KeepAlive(objLarge)
}
```

ℹ️ Исследование пограничного порога 32 КБ между mcache и mheap

**`Терминал`**

```bash
go run threshold.go
```

## Под капотом

В `src/runtime/sizeclasses.go`:
Класс 67 (последний):
- `size = 32768`
- `npages = 4` (\(4 \times 8192 = 32768\))
- `nelems = 1`
Спан класса 67 содержит ровно один объект и занимает 4 страницы.
При запросе 32769 байт рантайм вычисляет:
`npages = (32769 + 8191) / 8192 = 5 страниц (40960 байт)`.
Потеря на округление до страниц составляет \(40960 - 32769 = 8191\) байт!

## На собеседовании

**Вопрос с собеседования:** Почему размер страницы в аллокаторе Go выбран равным 8 КБ (`PageSize = 8192`), тогда как аппаратная страница x86-64 равна 4 КБ?
**Ответ:** Использование 8 КБ страниц вместо 4 КБ:
1. Вдвое уменьшает размер таблиц метаданных (`pageAlloc` Radix Tree, массивы `spans`), экономя оперативную память процесса.
2. Увеличивает средний размер непрерывного спана, снижая накладные расходы на поиск и слияние смежных страниц (Span Coalescing).
3. 8 КБ является оптимальным компромиссом между гранулярностью аллокаций и оверхедом системных структур ядра ОС.
