# Поведение HeapSys при отключенном сборщике мусора GOGC=off

## Условие

Напишите программу с `GOGC=off`, которая аллоцирует память до OOM. Зафиксируйте, как ведёт себя `HeapSys` — достигает ли она физического лимита плавно или скачками (по 64 MB/1 GB — arena chunks).

## Теория

Переменная окружения `GOGC=off` полностью отключает автоматический сборщик мусора Go.

В таком режиме:
1. Ни один объект, созданный в куче, никогда не освобождается.
2. Локальные `mcache` и центральные `mcentral` непрерывно опустошаются.
3. Глобальная куча `mheap` вынуждена непрерывно запрашивать новые арены у операционной системы.
4. Метрика `HeapSys` растет дискретными скачками, кратными **64 МБ** (размер `heapArenaBytes`).
5. Процесс потребляет всю доступную оперативную память вплоть до срабатывания механизма OOM Killer ядра Linux (Out-Of-Memory Killer).

## Решение по шагам

1. Напишите код, выделяющий память порциями в бесконечном цикле без сохранения ссылок.
2. Установите программно `debug.SetGCPercent(-1)` (эквивалент `GOGC=off`).
3. Логируйте рост `HeapAlloc` и ступенчатый рост `HeapSys`.
4. Ограничьте цикл безопасным порогом для предотвращения зависания хоста.

## Код решения

**`gogc_off.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	// Отключаем сборщик мусора полностью (эквивалент GOGC=off)
	oldGC := debug.SetGCPercent(-1)
	defer debug.SetGCPercent(oldGC)

	fmt.Println("=== Поведение аллокатора при GOGC=off (GC отключен) ===")

	var m runtime.MemStats
	const limitMB = 300 // Безопасный предел для теста
	prevSys := uint64(0)

	for step := 1; ; step++ {
		// Создаем временный мусор 10 МБ (но GC отключен, поэтому память не чистится!)
		trash := make([]byte, 10*1024*1024)
		trash[0] = byte(step)

		runtime.ReadMemStats(&m)
		allocMB := m.HeapAlloc / (1024 * 1024)
		sysMB := m.HeapSys / (1024 * 1024)

		if m.HeapSys != prevSys {
			deltaSys := (m.HeapSys - prevSys) / (1024 * 1024)
			prevSys = m.HeapSys
			fmt.Printf("[Шаг %2d] Скачок HeapSys: +%d МБ (Арена) -> Итого HeapSys: %d МБ (HeapAlloc: %d МБ)\n",
				step, deltaSys, sysMB, allocMB)
		}

		if allocMB >= limitMB {
			fmt.Printf("\nДостигнут безопасный порог теста %d МБ. Остановка.\n", limitMB)
			break
		}
	}
}
```

ℹ️ Демонстрация дискретного скачкообразного роста кучи при выключенном GC

**`Терминал`**

```bash
go run gogc_off.go
```

## Под капотом

В `src/runtime/mheap.go`:
Когда свободных страниц нет:
```go
func (h *mheap) grow(npage uintptr) bool {
    ask := alignUp(npage, pallocChunkPages) * pageSize
    if ask < heapArenaBytes {
        ask = heapArenaBytes // Минимум 64 МБ!
    }
    // mmap(PROT_READ|PROT_WRITE, MAP_ANONYMOUS)
}
```
Куча Go физически не может запросить у ядра Linux меньше 64 МБ за один раз на 64-битных ОС, поэтому рост `HeapSys` строго ступенчатый.

## Подводные камни

1. Никогда не ставьте `GOGC=off` в production, если только вы не пишете одноразовую CLI-утилиту, которая отрабатывает за 200 мс и завершается (`os.Exit(0)`).
2. Для ограничения памяти вместо `GOGC=off` всегда используйте `GOMEMLIMIT`.

## На собеседовании

**Вопрос с собеседования:** В каких редких сценариях в реальной практике оправдано отключение GC (`GOGC=off`)?
**Ответ:** 
1. **Короткоживущие CLI-утилиты (Short-lived CLI):** утилита считывает JSON/YAML, выполняет расчет за 100 мс и завершается. Отключение GC экономит такты процессора на сборку мусора, а всю память ядро ОС мгновенно освободит при закрытии процесса.
2. **Пакетные воркеры с перезапуском (Batch workers):** воркер обрабатывает фиксированный батч данных в изолированном контейнере и перезапускается.
В остальных HighLoad сервисах `GOGC=off` приведет к неминуемому OOM.
