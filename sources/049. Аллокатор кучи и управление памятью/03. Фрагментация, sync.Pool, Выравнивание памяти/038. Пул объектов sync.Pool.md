# Пул объектов sync.Pool: Архитектура, GC очистка и бенчмарк

## Условие

Реализуйте «пул объектов» через `sync.Pool` и сравните с прямым `make([]*T, 1000)`. Объясните, как `sync.Pool` взаимодействует с GC (очистка каждый цикл) и почему это быстрее, чем общая куча.

## Теория

`sync.Pool` — это высокопроизводительный потокобезопасный пул переиспользуемых временных объектов.

Внутреннее устройство `sync.Pool`:
1. **Привязка к \(P\) (`poolLocal`):** Пул шардирован по числу процессоров \(P\). У каждого \(P\) есть:
   - Приватный слот `private`: для мгновенного захвата текущей горутиной без единой блокировки.
   - Двусторонняя lock-free очередь `shared`: другие \(P\) могут воровать из неё объекты при опустошении своего пула (Work Stealing).
2. **Victim Cache (Кэш жертв, Go 1.13+):**
   - До Go 1.13 пул полностью очищался при каждом запуске GC, вызывая просадку RPS (GC thrashing).
   - В Go 1.13+ очистка двухфазная: при наступлении GC объекты перемещаются в кэш `victim`.
   - Если объект запрашивается из пула в течение следующего цикла GC, он возвращается обратно в `primary`.
   - Если за целый цикл GC к объекту никто не обратился, он окончательно утилизируется.

## Решение по шагам

1. Создайте структуру буфера `Buffer` размером 4 КБ.
2. Напишите бенчмарк с прямой аллокацией через `make([]byte, 4096)`.
3. Напишите бенчмарк с переиспользованием буферов через `sync.Pool`.
4. Сравните скорость и количество аллокаций памяти (`0 B/op`).

## Код решения

**`pool_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

type Buffer struct {
	Data [4096]byte
}

var bufPool = sync.Pool{
	New: func() any {
		return new(Buffer)
	},
}

// 1. Прямая аллокация: нагружает аллокатор и GC
func BenchmarkDirectAlloc(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			buf := new(Buffer)
			buf.Data[0] = 1
			_ = buf
		}
	})
}

// 2. Переиспользование через sync.Pool: 0 аллокаций
func BenchmarkSyncPool(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			buf := bufPool.Get().(*Buffer)
			buf.Data[0] = 1
			bufPool.Put(buf)
		}
	})
}

func main() {
	println("Запустите тест: go test -bench=. -benchmem pool_test.go")
}
```

## Под капотом

В `src/sync/pool.go`:
Метод `Get()`:
1. Вызывает `pin()`, который отключает прерывание горутины (`runtime.acquireLock` на \(P\)) и получает указатель на локальный `poolLocal` текущего \(P\).
2. Проверяет `l.private`. Если объект есть, он забирается за 1 такт!
3. Если пуст, извлекается элемент из локальной двухсторонней очереди `l.shared.popHead()`.
4. Если пуст, воруется элемент из `shared` очереди случайного соседнего \(P\) (`getSlow`).
5. Если все очереди пусты, проверяется `victim` кэш прошлого цикла GC.
6. Только если все уровни пусты, вызывается конструктор `New()`.

## Подводные камни

1. Перед возвратом объекта в пул через `Put()` обязательно очищайте его состояние (например, `buf.Reset()`), иначе следующий потребитель прочитает чужие данные (Data Leak / Security bug).
2. Никогда не сохраняйте ссылки на объекты после того, как вернули их в `Put()`. Это приведет к неконтролируемым гонкам данных (Data Race).

## На собеседовании

**Вопрос с собеседования:** Как работает механизм Victim Cache в `sync.Pool` и почему он сделал `sync.Pool` пригодным для HighLoad в Go 1.13+?
**Ответ:** До Go 1.13 сборщик мусора очищал `sync.Pool` целиком при каждой сборке (STW). В сервисах с частым GC это приводило к тому, что сразу после GC все пулы оказывались пустыми, и тысячи входящих запросов одновременно шли в аллокатор кучи, вызывая скачки задержки (Latency Spikes). В Go 1.13+ при наступлении GC старые объекты перемещаются в кэш `victim`, а освобождаются только те объекты, которые пролежали в `victim` два полных цикла GC без единого обращения. Это сгладило всплески аллокаций до нуля.
