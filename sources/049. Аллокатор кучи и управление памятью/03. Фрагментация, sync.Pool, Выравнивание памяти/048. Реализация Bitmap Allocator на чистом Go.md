# Реализация Bitmap Allocator на чистом Go: allocBits и gcmarkBits

## Условие

Реализуйте bitmap allocator на чистом Go: массив страниц, каждая страница 8 KB, объекты фиксированного размера 32 байта. Покажите, как `allocBits` и `gcmarkBits` работают в паре (один для аллокации, другой для GC).

## Теория

Основой управления памятью внутри `mspan` является пара побитовых карт:
1. **`allocBits` (битовая карта аллокатора):**
   - Каждый бит представляет один слот объекта (например, 32 байта).
   - \(1\) = слот занят живым объектом.
   - \(0\) = слот свободен для аллокации.
2. **`gcmarkBits` (битовая карта сборщика мусора):**
   - На старте цикла GC все биты сброшены в \(0\).
   - В ходе фазы Mark сборщик мусора помечает бит в \(1\) для каждого объекта, до которого удалось добраться по указателям.
3. **Фаза Sweep (Очистка):**
   - Рантайм делает: `allocBits = gcmarkBits`.
   - Объекты, которые не были помечены сборщиком (были нулями в `gcmarkBits`), автоматически становятся нулями в `allocBits` — то есть свободными ячейками!
   - Это исключает необходимость физической очистки памяти каждого удаленного объекта.

## Решение по шагам

1. Создайте структуру `BitmapSpan` со страницей 8 КБ и 256 слотами по 32 байта.
2. Реализуйте метод `Alloc()` с поиском свободного бита в `allocBits`.
3. Реализуйте метод `Mark(index)` для эмуляции сборщика мусора.
4. Реализуйте метод `Sweep()`, меняющий битовые карты местами.

## Код решения

**`bitmap_allocator.go`**

```go
package main

import (
	"fmt"
	"math/bits"
)

const (
	PageSize = 8192
	SlotSize = 32
	NumSlots = PageSize / SlotSize // 256 слотов
)

type BitmapSpan struct {
	data       [PageSize]byte
	allocBits  [4]uint64 // 4 * 64 = 256 бит
	gcmarkBits [4]uint64 // 4 * 64 = 256 бит
}

// Поиск свободного слота (allocBits == 0)
func (s *BitmapSpan) Alloc() (int, error) {
	for wordIdx := 0; wordIdx < 4; wordIdx++ {
		freeMask := ^s.allocBits[wordIdx]
		if freeMask != 0 {
			bitIdx := bits.TrailingZeros64(freeMask)
			slot := wordIdx*64 + bitIdx
			if slot < NumSlots {
				s.allocBits[wordIdx] |= (1 << bitIdx)
				return slot, nil
			}
		}
	}
	return -1, fmt.Errorf("спан заполнен")
}

// Эмуляция GC: пометка живого объекта
func (s *BitmapSpan) Mark(slot int) {
	wordIdx := slot / 64
	bitIdx := slot % 64
	s.gcmarkBits[wordIdx] |= (1 << bitIdx)
}

// Эмуляция фазы Sweep: мгновенное освобождение мусора
func (s *BitmapSpan) Sweep() {
	// Старые метки GC становятся новой маской аллокации
	s.allocBits = s.gcmarkBits
	// Очищаем gcmarkBits для следующего цикла GC
	s.gcmarkBits = [4]uint64{}
}

func main() {
	span := &BitmapSpan{}
	fmt.Printf("=== Bitmap Allocator (Страница %d Б, Слотов %d по %d Б) ===\n",
		PageSize, NumSlots, SlotSize)

	// 1. Выделяем 4 объекта
	s0, _ := span.Alloc()
	s1, _ := span.Alloc()
	s2, _ := span.Alloc()
	s3, _ := span.Alloc()
	fmt.Printf("Выделены слоты: %d, %d, %d, %d\n", s0, s1, s2, s3)
	fmt.Printf("allocBits[0]: 0b%08b (первые 4 слота заняты)\n\n", span.allocBits[0]&0xFF)

	// 2. Эмулируем GC: объекты 0 и 2 выжили, а 1 и 3 стали мусором
	fmt.Println("GC Mark: объекты 0 и 2 достижимы (живы):")
	span.Mark(s0)
	span.Mark(s2)
	fmt.Printf("gcmarkBits[0]: 0b%08b\n\n", span.gcmarkBits[0]&0xFF)

	// 3. Фаза Sweep
	fmt.Println("GC Sweep: замена allocBits = gcmarkBits:")
	span.Sweep()
	fmt.Printf("Новый allocBits[0]: 0b%08b\n", span.allocBits[0]&0xFF)

	// 4. Следующая аллокация переиспользует освобожденный слот 1!
	reusedSlot, _ := span.Alloc()
	fmt.Printf("Следующая аллокация взяла освободившийся слот: %d (переиспользован!)\n", reusedSlot)
}
```

```bash

```

## Под капотом

В рантайме Go структуры `gcBits` аллоцируются специальным пулом `gcBitsArenas`.
При замене указателей:
`s.allocBits = s.gcmarkBits`
Старый массив `allocBits` возвращается в пул свободных битовых карт без вызова `free()`.
Такой подход делает операцию освобождения памяти в спане практически бесплатной для CPU.

## Подводные камни

1. Если в ходе разметки GC случайно потеряет указатель на объект, соответствующий бит в `gcmarkBits` останется нулем, и объект будет освобожден в фазе Sweep (Use-after-free).
2. Барьеры записи (Write Barriers) защищают от потери указателей во время конкурентной разметки.

## На собеседовании

**Вопрос с собеседования:** Почему в `mspan` используются две отдельные битовые карты (`allocBits` и `gcmarkBits`), а не одно общее поле статуса для каждого объекта?
**Ответ:** Потому что в Go сборщик мусора работает **конкурентно** с выполняющейся программой (мутатором). Пока программа продолжает аллоцировать новые объекты (модифицируя `allocBits`), фоновые воркеры GC параллельно размечают живые объекты в независимой карте `gcmarkBits`. Разделение битовых карт исключает гонки данных и взаимные блокировки между аллокатором и сборщиком мусора.
