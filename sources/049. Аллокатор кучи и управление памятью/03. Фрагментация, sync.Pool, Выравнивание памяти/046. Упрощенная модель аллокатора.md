# Упрощенная модель аллокатора: mspan, mcache, mcentral, mheap

## Условие

Напишите «визуализатор» span: создайте структуры `mspan`, `mcache`, `mcentral`, `mheap` на чистом Go (упрощённые) и покажите, как запрос на 64 байта проходит от P → `mcache` → `mcentral` → `mheap` → ОС.

## Теория

Для кристального понимания пути аллокации построим работающую модель аллокатора на чистом Go:
1. `Span`: непрерывный блок ячеек фиксированного размера (например, 64 байта) со счетчиком свободных слотов.
2. `MCache`: локальный кэш, хранящий текущий активный спан для быстрого взятия слота.
3. `MCentral`: центральный пул свободных спанов с блокировкой.
4. `MHeap`: глобальная куча, запрашивающая блоки памяти у операционной системы.

Маршрут запроса:
\(P \to \text{mcache.Alloc()}\) (Fast Path) \(\xrightarrow{\text{пусто}}\) \(\text{mcentral.GetSpan()}\) (Slow Path) \(\xrightarrow{\text{пусто}}\) \(\text{mheap.AllocPages()}\) \(\xrightarrow{\text{пусто}}\) ОС `mmap`.

## Решение по шагам

1. Создайте структуры `MockSpan`, `MockMCache`, `MockMCentral`, `MockMHeap`.
2. Реализуйте каскадный вызов пополнения кэша при исчерпании слотов.
3. Выведите пошаговый лог маршрута аллокации 64-байтного объекта.

## Код решения

**`allocator_model.go`**

```go
package main

import (
	"fmt"
	"sync"
)

// 1. Уровень mspan: спан на 4 слота по 64 байта
type MockSpan struct {
	ID        int
	ElemSize  int
	FreeSlots int
}

// 4. Уровень mheap: глобальная куча (эмуляция ОС)
type MockMHeap struct {
	mu          sync.Mutex
	spansAlloc  int
}

func (h *MockMHeap) AllocPages() *MockSpan {
	h.mu.Lock()
	defer h.mu.Unlock()
	h.spansAlloc++
	fmt.Printf("    -> [L3: MHeap] Запрос страниц у ОС (mmap). Создан новый Span #%d\n", h.spansAlloc)
	return &MockSpan{ID: h.spansAlloc, ElemSize: 64, FreeSlots: 4}
}

// 3. Уровень mcentral: пул спанов класса 64B
type MockMCentral struct {
	mu    sync.Mutex
	heap  *MockMHeap
	spans []*MockSpan
}

func (c *MockMCentral) GetSpan() *MockSpan {
	c.mu.Lock()
	defer c.mu.Unlock()

	if len(c.spans) > 0 {
		s := c.spans[len(c.spans)-1]
		c.spans = c.spans[:len(c.spans)-1]
		fmt.Printf("  -> [L2: MCentral] Взят готовый свободный Span #%d из центрального пула\n", s.ID)
		return s
	}

	fmt.Println("  -> [L2: MCentral] Центральный пул пуст! Обращение к MHeap...")
	return c.heap.AllocPages()
}

// 2. Уровень mcache: локальный per-P кэш (Lock-free)
type MockMCache struct {
	central *MockMCentral
	current *MockSpan
}

func (c *MockMCache) Alloc64(reqID int) {
	if c.current != nil && c.current.FreeSlots > 0 {
		c.current.FreeSlots--
		fmt.Printf("[Req #%02d] [L1: MCache] FAST PATH: Слот взят из Span #%d (осталось слотов: %d)\n",
			reqID, c.current.ID, c.current.FreeSlots)
		return
	}

	fmt.Printf("[Req #%02d] [L1: MCache] SLOW PATH: Текущий спан полон! Запрос в MCentral...\n", reqID)
	c.current = c.central.GetSpan()
	c.current.FreeSlots--
	fmt.Printf("         [L1: MCache] Слот успешно получен из нового Span #%d\n", c.current.ID)
}

func main() {
	heap := &MockMHeap{}
	central := &MockMCentral{heap: heap}
	mcache := &MockMCache{central: central}

	fmt.Println("=== Моделирование 3-уровневой иерархии TCMalloc в Go ===")
	// Делаем 10 последовательных аллокаций по 64 байта
	for i := 1; i <= 10; i++ {
		mcache.Alloc64(i)
	}
}
```

**`Терминал`**

```bash
go run allocator_model.go
```

## Под капотом

В реальном рантайме Go:
- Fast Path (`mcache.nextFreeFast`) инлайнится компилятором прямо в тело вызывающей функции, избегая даже накладных расходов на вызов функции `CALL`!
- Slow Path (`mcache.refill`) вызывается только один раз на каждые 128–512 аллокаций (в зависимости от емкости спана).
- Slower Path (`mheap_.alloc`) вызывается только раз на десятки пополнений `mcentral`.
Благодаря этому 99.8% всех аллокаций в Go завершаются на L1 уровне за 5 наносекунд.

## Подводные камни

1. Не путайте локальный `mcache` потока \(P\) с процессорным кэшем L1 процессора Intel/AMD. `mcache` — это программная структура в оперативной памяти, но благодаря компактности она идеально ложится в аппаратный кэш L1/L2 CPU.
2. Ошибка в расчете `freeindex` в реальном спане может привести к перезаписи чужих данных.

## На собеседовании

**Вопрос с собеседования:** Каково среднее амортизированное время аллокации мелкого объекта в Go и почему оно близко к времени аллокации на стеке?
**Ответ:** Амортизированное время аллокации составляет **5–15 наносекунд**. Благодаря трехуровневой архитектуре TCMalloc подавляющее большинство запросов (< 32 КБ) удовлетворяется локальным кэшем `mcache` без единого системного вызова и без единого мьютекса. Операция сводится к поиску бита в 64-битном регистре `allocCache` и инкременту указателя.
