# Профилирование накладных расходов runtime.mallocgc в pprof

## Условие

**mcentral и mheap**: Если в `mcache` закончились слоты нужного размера, он идет в `mcentral` (глобальный кэш определенного размера, здесь уже нужны мьютексы). Если и там пусто — память запрашивается у `mheap` (операционной системы). Напиши бенчмарк, выделяющий миллионы объектов. Посмотри в профиле (`pprof`), сколько времени тратится на `runtime.mallocgc`.

## Теория

Функция `runtime.mallocgc` — центральное сердце подсистемы памяти Go. В высоконагруженных сервисах, страдающих от избыточных аллокаций, `mallocgc` может потреблять до **20–40% всего процессорного времени (CPU)**!

Время работы `mallocgc` складывается из:
1. Fast-Path: извлечение слота из `mcache.alloc` (2–5 ns).
2. Slow-Path: пополнение из `mcentral.cacheSpan` под спинлоком (20–100 ns).
3. Slower-Path: аллокация страниц из `mheap.alloc` под глобальным локом (500–2000 ns).
4. Очистка памяти нулями (`memclrNoHeapPointers`).
5. Учет в системе GC Assist (`gcAssistAlloc`).

Профилирование CPU через `pprof` позволяет точно измерить долю времени, съедаемую аллокатором.

## Решение по шагам

1. Создайте бенчмарк с массовой аллокацией миллионов структур в куче.
2. Запустите бенчмарк со снятием CPU профиля: `go test -bench=. -cpuprofile=cpu.pprof`.
3. Откройте `go tool pprof -top cpu.pprof` и найдите долю функции `runtime.mallocgc`.

## Код решения

**`malloc_bench_test.go`**

```go
package main

import (
	"runtime"
	"testing"
)

type EventLog struct {
	Timestamp int64
	UserID    int64
	Payload   [32]byte
}

func BenchmarkMallocGCPressure(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		// Каждая итерация вызывает mallocgc
		ev := &EventLog{
			Timestamp: int64(i),
			UserID:    12345,
		}
		runtime.KeepAlive(ev)
	}
}

func main() {
	println("Запустите: go test -bench=. -cpuprofile=cpu.pprof malloc_bench_test.go")
}
```

ℹ️ Бенчмарк для профилирования доли CPU, потребляемой runtime.mallocgc

**`Терминал`**

```bash
go test -bench=BenchmarkMallocGCPressure -cpuprofile=cpu.pprof malloc_bench_test.go
go tool pprof -top cpu.pprof
```

## Под капотом

В выводе `pprof -top`:
```text
(pprof) top
Showing nodes accounting for 1.82s, 85.45% of 2.13s total
      flat  flat%   sum%        cum   cum%
     0.98s 46.01% 46.01%      1.45s 68.08%  runtime.mallocgc
     0.28s 13.15% 59.15%      0.28s 13.15%  runtime.memclrNoHeapPointers
     0.19s  8.92% 68.08%      0.19s  8.92%  runtime.nextFreeFast
```
Видно, что `runtime.mallocgc` занимает львиную долю времени! Оптимизация такого кода через `sync.Pool` или устранение побега в кучу мгновенно высвобождает до 50% вычислительных мощностей процессора.

## Подводные камни

1. Оптимизировать микросекунды в бизнес-логике бессмысленно, если в топ-1 профиля CPU висит `runtime.mallocgc`. Всегда начинайте оптимизацию с устранения аллокаций.
2. Обнуление памяти (`runtime.memclrNoHeapPointers`) внутри `mallocgc` обязательно по стандарту безопасности Go: все новые объекты гарантированно инициализируются нулями.

## На собеседовании

**Вопрос с собеседования:** В выводе `pprof cpu` вашего микросервиса функция `runtime.mallocgc` занимает 35% CPU, а `runtime.gcDrain` — еще 20%. Что это означает и каков план действий?
**Ответ:** Это классический симптом «Memory Allocation Thrashing» (приложение генерирует слишком много мусора в куче). План действий:
1. Снять `pprof heap` с флагом `-alloc_space` для поиска функций, создающих максимальный темп аллокаций.
2. Проверить Escape Analysis (`-gcflags="-m"`): заменить передачу по указателю на структуры по значению.
3. Использовать `sync.Pool` для частых временных буферов и объектов.
4. Проверить предвыделение емкости срезов и мап (`make([]T, 0, expectedSize)`).
Устранение аллокаций автоматически снизит как время `mallocgc`, так и время `gcDrain` (сборки мусора).
