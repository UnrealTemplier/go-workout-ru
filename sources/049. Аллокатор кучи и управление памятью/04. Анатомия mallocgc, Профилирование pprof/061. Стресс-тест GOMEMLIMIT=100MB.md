# Стресс-тест GOMEMLIMIT=100MB и адаптивное поведение аллокатора

## Условие

Напишите «allocator stress test» с `GOMEMLIMIT=100MB` и `GOGC=100`. Покажите, как при приближении к лимиту GC начинает работать чаще, а аллокатор агрессивнее возвращает память ОС.

## Теория

Переменная окружения `GOMEMLIMIT` (введена в Go 1.19) является главным инструментом предотвращения падений по OOM в облачной инфраструктуре (Kubernetes / Docker).

Механизм взаимного регулирования `GOMEMLIMIT` и `GOGC`:
1. **Зона комфорта:** Пока память далека от `GOMEMLIMIT`, GC запускается строго по формуле `GOGC` (например, при удвоении кучи).
2. **Зона сжатия:** Когда общий объем памяти процесса (`HeapAlloc + Stack + Metadata`) приближается к `GOMEMLIMIT`, контроллер GC Pacer начинает принудительно снижать целевой коэффициент роста кучи.
3. **Агрессивный Scavenger:** Аллокатор мгновенно переводит неиспользуемые страницы в `HeapReleased`, защищая процесс от пересечения жесткого лимита cgroups.
4. **Защита от GC Thrashing:** Если память не освобождается, рантайм ограничивает время работы GC пределом в **50% всего CPU**, не позволяя процессу окончательно зависнуть в бесконечной сборке мусора.

## Решение по шагам

1. Задайте программно лимит памяти `debug.SetMemoryLimit(100 * 1024 * 1024)`.
2. Запустите генератор нагрузки с выделением временной памяти.
3. Отследите увеличение частоты сборок мусора при приближении к 100 МБ порогу.

## Код решения

**`memlimit_stress.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func main() {
	// Устанавливаем Soft Memory Limit = 100 МБ
	const limitBytes = 100 * 1024 * 1024
	oldLimit := debug.SetMemoryLimit(limitBytes)
	defer debug.SetMemoryLimit(oldLimit)

	fmt.Println("=== Стресс-тест аллокатора под GOMEMLIMIT=100MB ===")
	fmt.Printf("Целевой лимит памяти: %d МБ\n\n", limitBytes/(1024*1024))

	var m runtime.MemStats
	startTime := time.Now()

	// Генерируем 1 ГБ суммарного временного мусора
	for step := 1; step <= 20; step++ {
		// Каждая итерация создает 50 МБ временных данных
		trash := make([][]byte, 50)
		for i := 0; i < 50; i++ {
			trash[i] = make([]byte, 1024*1024)
			trash[i][0] = 1
		}

		runtime.ReadMemStats(&m)
		fmt.Printf("[Шаг %2d] HeapAlloc: %2d МБ | NextGC: %2d МБ | Сборок GC: %2d\n",
			step,
			m.HeapAlloc/(1024*1024),
			m.NextGC/(1024*1024),
			m.NumGC,
		)

		_ = trash
		time.Sleep(100 * time.Millisecond)
	}

	fmt.Printf("\nТест завершен за %v. Процесс удержан строго в пределах 100 МБ!\n",
		time.Since(startTime))
}
```

**`Терминал`**


## Под капотом

В `src/runtime/mgcpacer.go`:
Контроллер вычисляет пространство до границы:
```go
memoryLimit := gcController.memoryLimit.Load()
runway := memoryLimit - currentTotalMemory
```
Если `runway` сокращается, Pacer пересчитывает триггер:
`trigger = min(triggerFromGOGC, memoryLimit - headroom)`
В результате целевой порог `NextGC` сжимается, заставляя GC собирать мусор заблаговременно до исчерпания доступной оперативной памяти.

## Подводные камни

1. Установка `GOMEMLIMIT` впритык к объему долгоживущих данных сервиса (например, 90 МБ данных при лимите 100 МБ) вызовет постоянную 50% загрузку CPU сборщиком мусора.
2. Оставляйте запас минимум в 25–30% между рабочим объемом живых данных и `GOMEMLIMIT`.

## На собеседовании

**Вопрос с собеседования:** Как устроен механизм защиты от GC Thrashing (пробуксовки сборщика мусора) в Go 1.19+ при выставленном `GOMEMLIMIT`?
**Ответ:** Если живые данные сервиса превышают `GOMEMLIMIT`, наивный алгоритм запускал бы GC непрерывно, отбирая 100% CPU и блокируя работу бизнес-логики. Go 1.19+ ввел жесткое ограничение: сборщик мусора не имеет права потреблять суммарно более **50% времени CPU** в скользящем окне. Если лимит памяти всё равно превышен, рантайм позволяет куче временно превысить `GOMEMLIMIT`, отдавая приоритет выполнению кода программы.
