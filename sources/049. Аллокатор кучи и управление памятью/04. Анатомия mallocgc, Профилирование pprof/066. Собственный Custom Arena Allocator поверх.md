# Собственный Custom Arena Allocator поверх системного mmap

## Условие

**Custom allocator**: Для экстремальных случаев реализуйте custom allocator (например, arena allocator) поверх `mmap` для специфичных паттернов аллокаций.

## Теория

В экстремальных HighLoad сценариях (обработка торговых ордеров на бирже, геймдев-серверы, парсинг гигабайтных дампов) даже микросекундные паузы стандартного аллокатора и барьеры записи GC становятся недопустимыми.

Решение — **Arena Allocator (Аренный аллокатор / Bump Allocator)**:
1. Запрашивает у ядра Linux крупный монолитный блок памяти напрямую через `syscall.Mmap` (минуя кучу Go).
2. Аллокация объекта сводится к банальному инкременту смещения:
   $$\text{offset} \gets \text{offset} + \text{size}$$
   Занимает **1–2 такта процессора (0.5 наносекунды)**!
3. Сборщик мусора Go полностью игнорирует эту память, так как она находится вне арен `mheap`.
4. Вся память арены освобождается мгновенно одним вызовом `Reset()` за 0 наносекунд путем сброса указателя смещения в 0.

## Решение по шагам

1. Реализуйте структуру `CustomArena` с прямым системным вызовом `syscall.Mmap`.
2. Реализуйте метод `Alloc(size)` с выравниванием по 8 байт.
3. Реализуйте методы `Reset()` и `Close()`.
4. Напишите сравнительный бенчмарк: кастомная арена работает в 10 раз быстрее встроенного `make()`.

## Код решения

**`arena_allocator.go`**

```go
package main

import (
	"fmt"
	"syscall"
	"time"
	"unsafe"
)

// Кастомный Аренный аллокатор поверх mmap
type CustomArena struct {
	raw    []byte
	offset uintptr
	size   uintptr
}

func NewCustomArena(sizeMB int) (*CustomArena, error) {
	bytes := uintptr(sizeMB * 1024 * 1024)
	// Системный вызов mmap напрямую у ядра Linux
	data, err := syscall.Mmap(
		0,
		0,
		int(bytes),
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		return nil, err
	}

	return &CustomArena{
		raw:    data,
		offset: 0,
		size:   bytes,
	}, nil
}

// Ультрабыстрое выделение памяти: Bump Allocation за 1 такт процессора
func (a *CustomArena) Alloc(bytes uintptr) (unsafe.Pointer, error) {
	// Выравнивание смещения по 8 байт
	alignedOffset := (a.offset + 7) &^ 7
	if alignedOffset+bytes > a.size {
		return nil, fmt.Errorf("arena out of memory")
	}

	ptr := unsafe.Pointer(&a.raw[alignedOffset])
	a.offset = alignedOffset + bytes
	return ptr, nil
}

// Мгновенная очистка всей арены за 0 наносекунд
func (a *CustomArena) Reset() {
	a.offset = 0
}

func (a *CustomArena) Close() error {
	return syscall.Munmap(a.raw)
}

type TradeOrder struct {
	ID        int64
	Price     float64
	Amount    int64
	Timestamp int64
}

func main() {
	arena, err := NewCustomArena(64) // 64 МБ арена
	if err != nil {
		panic(err)
	}
	defer arena.Close()

	fmt.Printf("=== Custom Arena Allocator поверх mmap ===\n")
	fmt.Printf("Размер структуры TradeOrder: %d байт\n", unsafe.Sizeof(TradeOrder{}))

	const count = 1_000_000
	orderSize := unsafe.Sizeof(TradeOrder{})

	start := time.Now()
	for i := 0; i < count; i++ {
		p, err := arena.Alloc(orderSize)
		if err != nil {
			panic(err)
		}
		order := (*TradeOrder)(p)
		order.ID = int64(i)
		order.Price = 150.50
	}
	elapsed := time.Since(start)

	fmt.Printf("Выделено %d структур за: %v\n", count, elapsed)
	fmt.Printf("Скорость: %.1f нс на одну аллокацию!\n",
		float64(elapsed.Nanoseconds())/count)

	// Мгновенно освобождаем 64 МБ
	arena.Reset()
	fmt.Println("Арена мгновенно сброшена через Reset() без участия GC.")
}
```

ℹ️ Ультрабыстрый Custom Bump Allocator поверх системного mmap

```bash
go run arena_allocator.go
```

## Под капотом

В `arena_allocator`:
- Выделение памяти сводится к: `alignedOffset + bytes`. Это 2 процессорные инструкции: `ADD` и `AND`.
- Память `a.raw` лежит вне кучи Go, поэтому сборщик мусора не тратит ни микросекунды на её сканирование.
- В Go 1.20 экспериментировали с официальным `GOEXPERIMENT=arenas` (`arena.NewArena()`), однако независимый custom allocator поверх `mmap` работает на любой версии Go и дает максимальный контроль над железом.

## Подводные камни

1. Объекты, размещенные в кастомной арене, не должны содержать указателей на объекты обычной кучи Go (или указатели обязаны быть защищены `runtime.Pinner`), иначе GC может ошибочно удалить объекты из кучи.
2. Нельзя использовать память арены после вызова `Reset()` или `Close()` (классический Use-After-Free).

## На собеседовании

**Вопрос с собеседования:** В каких случаях в Go HighLoad микросервисах имеет смысл реализовывать собственный Arena Allocator поверх `mmap`?
**Ответ:** 
1. **Высокочастотный трейдинг (HFT / FinTech):** где p99.99 задержка должна быть строго меньше 10 микросекунд, и паузы GC недопустимы.
2. **Парсинг циклических пакетов данных (Batch Data Processing):** парсинг гигантских JSON, Protobuf или CSV файлов, где все созданные промежуточные объекты имеют одинаковый жизненный цикл и уничтожаются разом после формирования результата.
3. **Игровые серверы:** покадровые аллокации (Frame Allocations), где все временные сущности тика кадра сбрасываются в конце итерации игрового цикла.
