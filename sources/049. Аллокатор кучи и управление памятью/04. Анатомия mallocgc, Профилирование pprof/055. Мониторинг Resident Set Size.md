# Мониторинг Resident Set Size и работа фонового Scavenger

## Условие

**Захват памяти у ОС (Memory Scavenger)**: Создай слайс на 1 Гигабайт. ОС выделит память (посмотри в `top` на метрику RES). Обнули указатель на слайс. Вызови `runtime.GC()`. Посмотри в `top` снова. Память не сразу вернется в ОС! Go запускает фоновый процесс "scavenger", который постепенно (чтобы не грузить CPU) возвращает свободные страницы (`mspan`) операционной системе.

## Теория

Жизненный цикл страниц памяти между Go и ядром ОС:
1. **Выделение (Allocation):**
   - Программа запрашивает 1 ГБ памяти.
   - Рантайм расширяет арены через `mmap`. Физические страницы выделяются ядром (RSS растет до 1 ГБ).
2. **Сборка мусора (GC):**
   - Указатель обнулен, вызывается `runtime.GC()`.
   - GC переводит спаны в состояние `HeapIdle`.
   - **Физический RSS процесса в ОС не изменяется!** Страницы остаются привязанными к процессу.
3. **Очистка (Scavenging):**
   - Фоновый Scavenger просыпается и дозированно вызывает `madvise(MADV_DONTNEED)`.
   - Ядро Linux сбрасывает страницы. RSS плавно снижается до базового уровня.
   - Это гарантирует, что освобождение памяти не создает внезапных спайков CPU.

## Решение по шагам

1. Напишите программу, выделяющую 800 МБ памяти.
2. Считайте системный статус RSS из `/proc/self/status`.
3. Запустите GC и отследите задержку возврата физических страниц операционной системе.

## Код решения

**`scavenger_monitor.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"strings"
	"time"
)

func printRSS(stage string) {
	data, err := os.ReadFile("/proc/self/status")
	if err != nil {
		fmt.Printf("[%s] Ошибка чтения /proc/self/status\n", stage)
		return
	}
	lines := strings.Split(string(data), "\n")
	for _, l := range lines {
		if strings.HasPrefix(l, "VmRSS:") || strings.HasPrefix(l, "VmSize:") {
			fmt.Printf("  [%s] %s\n", stage, l)
		}
	}
}

func main() {
	fmt.Println("=== Мониторинг VmRSS и работы Scavenger ===")
	printRSS("Старт")

	// 1. Выделяем 800 МБ памяти
	fmt.Println("\nВыделяем 800 МБ памяти...")
	data := make([]byte, 800*1024*1024)
	for i := 0; i < len(data); i += 4096 {
		data[i] = 1 // активируем фреймы памяти ядра
	}
	printRSS("После выделения 800 МБ")

	// 2. Освобождаем ссылку и вызываем GC
	fmt.Println("\nОбнуляем ссылку и вызываем GC...")
	data = nil
	runtime.GC()
	printRSS("Сразу после runtime.GC() (память все еще в RES!)")

	// 3. Наблюдаем за фоновым Scavenger
	fmt.Println("\nОжидание работы фонового Scavenger:")
	for sec := 1; sec <= 3; sec++ {
		time.Sleep(1 * time.Second)
		printRSS(fmt.Sprintf("Секунда %d", sec))
	}

	fmt.Println("\nВывод: Go возвращает память ядру ОС лениво через фоновый Scavenger.")
}
```

## Подводные камни

1. Не путайте `VmSize` (виртуальная память) и `VmRSS` (физическая память). `VmSize` никогда не уменьшается, пока жив процесс Go — это абсолютно нормально.
2. В Windows вместо `madvise` рантайм использует системный вызов `VirtualFree(MEM_DECOMMIT)`.

## На собеседовании

**Вопрос с собеседования:** Как настроить рантайм Go, чтобы в моменты простоя он максимально быстро возвращал неиспользуемую память операционной системе?
**Ответ:** 
1. Установить переменную `GODEBUG=madvdontneed=1` (в Go 1.16+ включена по умолчанию), гарантирующую немедленное обнуление RSS при освобождении страниц.
2. Выставить параметр `GOMEMLIMIT` с запасом 15–20% от квоты контейнера: рантайм будет заблаговременно инициировать скейвенджинг при приближении к границе.
3. В редких сценариях после тяжелой пакетной обработки вызывать `debug.FreeOSMemory()` для принудительного синхронного сброса неиспользуемых страниц ядру ОС.
