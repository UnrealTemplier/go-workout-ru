# Профилирование метаданных спанов: MSpanInuse и MSpanSys

## Условие

Напишите «span profiler»: через `runtime.ReadMemStats` и рефлексию (или cgo) попытайтесь оценить, сколько span занято vs. свободно. Объясните, почему Go не экспонирует эту статистику напрямую.

## Теория

В структуре `runtime.MemStats` подсистема управления спанами представлена специализированными системными метриками:
- `MSpanInuse`: объем памяти в байтах, занятый самими служебными структурами `mspan` (дескрипторами), которые сейчас обслуживают активную память.
- `MSpanSys`: общий объем памяти, выделенный рантаймом под хранение структур `mspan` у операционной системы.
- `MCacheInuse`: память структур `mcache` для всех процессоров \(P\).
- `MCacheSys`: зарезервированная память под кэши `mcache`.

Почему Go не экспонирует список всех спанов наружу:
1. Безопасность и целостность: внутренний граф спанов непрерывно мутирует в реальном времени параллельными потоками и сборщиком мусора. Экспорт наружу потребовал бы долгой STW-паузы.
2. Изоляция абстракций: рантайм гарантирует стабильность публичного API Go 1 Compatibility Promise, сохраняя за собой право оптимизировать алгоритмы аллокатора между релизами.

## Решение по шагам

1. Напишите код, считывающий метрики спанов и кэшей через `runtime.ReadMemStats`.
2. Выделите серию объектов для роста числа активных спанов.
3. Рассчитайте средний оверхед структур метаданных `mspan` на один мегабайт кучи.

## Код решения

**`span_profiler.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func printSpanMetrics(tag string) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	fmt.Printf("[%s]\n", tag)
	fmt.Printf("  MSpanInuse : %6d КБ (память активных дескрипторов mspan)\n", m.MSpanInuse/1024)
	fmt.Printf("  MSpanSys   : %6d КБ (память под дескрипторы mspan от ОС)\n", m.MSpanSys/1024)
	fmt.Printf("  MCacheInuse: %6d КБ (память активных кэшей mcache)\n", m.MCacheInuse/1024)
	fmt.Printf("  MCacheSys  : %6d КБ (память под кэши mcache от ОС)\n", m.MCacheSys/1024)
	fmt.Printf("  HeapInuse  : %6d МБ (объем памяти в спанах кучи)\n\n", m.HeapInuse/(1024*1024))
}

func main() {
	fmt.Println("=== Исследование метаданных mspan и mcache ===")
	printSpanMetrics("Старт программы")

	// Аллоцируем 100 000 разнокалиберных объектов для создания сотен спанов
	data := make([]any, 100_000)
	for i := 0; i < len(data); i++ {
		if i%2 == 0 {
			data[i] = make([]byte, 48)
		} else {
			data[i] = make([]byte, 128)
		}
	}

	printSpanMetrics("После создания 100 000 объектов (спаны развернуты)")

	runtime.KeepAlive(data)
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Снятие метрик структур mspan и mcache через runtime.MemStats

**`Терминал`**

```bash
go run span_profiler.go
```

## Под капотом

Служебные структуры `mspan` не аллоцируются в обычной куче Go (чтобы избежать рекурсивной зависимости аллокатора от самого себя!).
Они выделяются из фиксированного аллокатора рантайма — `mheap_.spanalloc` (тип `fixalloc`).
Аллокатор `fixalloc` запрашивает у ОС чистую память кусками по 64 КБ без барьеров записи и без участия сборщика мусора.

## Подводные камни

1. Метрика `MSpanInuse` показывает размер служебных метаданных, а не самих страниц кучи. Отношение `MSpanInuse / HeapInuse` обычно составляет менее 1%.
2. Рост `MSpanSys` при стабильном `HeapAlloc` сигнализирует о сильном дроблении кучи на мелкие спаны.

## На собеседовании

**Вопрос с собеседования:** Почему внутренние структуры рантайма Go (`mspan`, `mcache`, `g`, `p`) не выделяются в обычной куче через `new()` или `make()`?
**Ответ:** Если бы рантайм выделял собственные метаданные в куче, возникла бы фатальная взаимная рекурсия: для создания спана потребовалось бы выделить память в спане. Кроме того, сборщик мусора GC сам опирается на целостность этих структур при сканировании памяти: если бы структуры рантайма находились в куче, GC мог бы случайно пометить дескриптор спана как мусор или сломаться на барьере записи во время фазы Stop-The-World.
