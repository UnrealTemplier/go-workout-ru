## Теория

Файл `src/runtime/sizeclasses.go` генерируется автоматически алгоритмом из `src/runtime/mksizeclasses.go`.

Математические принципы выбора классов размеров:
1. **Максимальная внутренняя фрагментация:** строго ограничена значением **12.5%** (1/8).
   - Это означает, что шаг между соседними классами составляет около \(12.5\%\):
     $$\text{Size}_{i+1} \approx \text{Size}_i \times 1.125$$
2. **Выравнивание по страницам и словам:**
   - Размеры до 128 байт кратны 8 или 16 байтам для идеального выравнивания по регистрам процессора.
   - Емкость спана подбирается так, чтобы суммарный остаток на границе страниц 8 КБ (`tail waste`) был минимален.
3. Всего классов размеров: ровно **67 классов** для объектов от 8 байт до 32768 байт.

## Решение по шагам

1. Напишите функцию, эмулирующую быстрый перевод запрошенного размера байт в индекс класса размера.
2. Проверьте точность для размеров 7, 8, 9, 32, 33, 1024 и 32768 байт.
3. Рассчитайте теоретическую максимальную фрагментацию таблицы.

## Код решения

**`size_math.go`**

```go
package main

import (
	"fmt"
)

// Выдержка базовых классов размеров Go из sizeclasses.go
var classToSize = []int{
	0, 8, 16, 24, 32, 48, 64, 80, 96, 112, 128,
	144, 160, 176, 192, 208, 224, 240, 256,
	320, 384, 448, 512, 1024, 2048, 4096, 8192, 16384, 32768,
}

// Формула округления размера в класс размера
func roundToSizeClass(req int) (int, int) {
	if req > 32768 {
		return 0, req // Large object
	}
	for idx, sz := range classToSize {
		if sz >= req {
			return idx, sz
		}
	}
	return len(classToSize) - 1, 32768
}

func main() {
	testRequests := []int{1, 8, 9, 25, 32, 33, 65, 100, 500, 1025, 32768, 40000}

	fmt.Printf("%-12s %-12s %-12s %-10s\n",
		"Запрос (Б)", "Класс ID", "Выделено (Б)", "Оверхед")
	fmt.Println("--------------------------------------------------")

	for _, req := range testRequests {
		classID, allocated := roundToSizeClass(req)
		diff := allocated - req
		percent := float64(diff) / float64(allocated) * 100
		if allocated == req {
			percent = 0
		}

		fmt.Printf("%-12d %-12d %-12d %5.1f%%\n",
			req, classID, allocated, percent)
	}

	fmt.Println("\nВывод: Классы размеров гарантируют средние потери памяти не более 12.5%.")
}
```

## Под капотом

В `src/runtime/sizeclasses.go`:
Количество классов \(67\) выбрано не случайно:
Оно идеально укладывается в 8-битный байт (`uint8`), что позволяет хранить номер класса в дескрипторе `spanClass` всего одним байтом!
Таблицы поиска `size_to_class8` (129 байт) и `size_to_class128` (249 байт) суммарно весят менее 500 байт и целиком умещаются в одну аппаратную кэш-линию L1 кэша процессора.

## Подводные камни

1. Попытка создания объектов с нестандартными размерами (например, 32769 байт) выбивает объект из эффективной таблицы классов в медленный Large Allocator.
2. Для минимизации потерь держите размеры критических структур кратными 8 или 16 байтам.

## На собеседовании

**Вопрос с собеседования:** Почему в Go шаг между классами размеров составляет именно 12.5%, а не 50% (степени двойки: 8, 16, 32, 64, 128...) как в аллокаторах Buddy Allocator?
**Ответ:** В Buddy Allocator (шаг \(2\times\)) средняя внутренняя фрагментация составляет 25%, а максимальная — до 50% (запрос 33 байт выделит 64 байта). Для микросервисов с миллиардами объектов потеря 30–50% оперативной памяти недопустима. Шаг 12.5% в Go обеспечивает золотой баланс: максимальная фрагментация не превышает 12.5%, а общее число классов остается компактным (всего 67), позволяя держать все метаданные в кэше L1 процессора.
