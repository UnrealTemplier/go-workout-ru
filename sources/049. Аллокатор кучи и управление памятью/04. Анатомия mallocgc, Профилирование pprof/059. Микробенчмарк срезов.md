# Микробенчмарк срезов: make(0, 100) vs make(100) vs append

## Условие

Напишите микробенчмарк: сравните `make([]int, 0, 100)` vs `make([]int, 100)` vs `append` в цикле. Объясните через escape analysis и аллокатор, почему `make` с капасити иногда уходит в кучу, а иногда нет.

## Теория

Сравнение трех популярных паттернов работы со срезами:
1. `make([]int, 0, 100)`:
   - Создает срез с `len = 0` и предварительно выделенной емкостью `cap = 100`.
   - Последующие вызовы `append` происходят без единого перевыделения памяти.
2. `make([]int, 100)`:
   - Создает срез с `len = 100`, заполненный нулями.
   - Запись выполняется по прямому индексу `s[i] = v`.
3. `var s []int` + `append` в цикле (наивный подход):
   - Срез стартует с `cap = 0`.
   - На итерациях 1, 2, 4, 8, 16, 32, 64, 128 происходят повторные аллокации кучи (`runtime.growslice`), копирование старых данных и выброс старых массивов в мусор.

Почему `make` с капасити иногда остается на стеке:
Если емкость константна (`cap = 100`) и срез не утекает наружу, компилятор размещает весь массив прямо на стеке горутины (`0 B/op`). Но если емкость переменная (`cap = n`), срез гарантированно отправляется в кучу.

## Решение по шагам

1. Напишите бенчмарк для `make([]int, 0, 100)` с `append`.
2. Напишите бенчмарк для `make([]int, 100)` с прямой записью по индексу.
3. Напишите бенчмарк для наивного `append` с нуля.
4. Сравните время выполнения и количество аллокаций памяти.

## Код решения

**`slice_bench_test.go`**

```go
package main

import "testing"

const sliceSize = 100

// 1. Предвыделение cap: make([]int, 0, 100) + append
func BenchmarkPreallocAppend(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		s := make([]int, 0, sliceSize)
		for j := 0; j < sliceSize; j++ {
			s = append(s, j)
		}
		_ = s
	}
}

// 2. Предвыделение len: make([]int, 100) + прямая запись по индексу
func BenchmarkPreallocIndex(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		s := make([]int, sliceSize)
		for j := 0; j < sliceSize; j++ {
			s[j] = j
		}
		_ = s
	}
}

// 3. Наивный append без предвыделения: многократный growslice
func BenchmarkNaiveAppend(b *testing.B) {
	b.ReportAllocs()
	b.ResetTimer()

	for i := 0; i < b.N; i++ {
		var s []int
		for j := 0; j < sliceSize; j++ {
			s = append(s, j)
		}
		_ = s
	}
}

func main() {
	println("Запустите: go test -bench=. -benchmem slice_bench_test.go")
}
```

ℹ️ Сравнение производительности и аллокаций паттернов создания срезов

**`Терминал`**

```bash
go test -bench=. -benchmem slice_bench_test.go
```

## Под капотом

В наивном `BenchmarkNaiveAppend`:
Происходит 7 последовательных аллокаций памяти и 7 вызовов `runtime.growslice`.
Каждый вызов выделяет новый массив, копирует элементы через `typedmemmove` и оставляет старый массив в качестве мусора в куче.
В версиях с предвыделением (`PreallocAppend` и `PreallocIndex`) аллокация происходит ровно 1 раз (или 0 раз, если срез остается на стеке). Прямая запись по индексу быстрее еще и за счет устранения проверок длины `append`.

## Подводные камни

1. Создание среза через `make([]int, 100)` с последующим ошибочным вызовом `append` удвоит размер до 200 элементов, где первые 100 будут нулями! Для `append` используйте `make([]int, 0, 100)`.
2. Если точный размер среза известен заранее, всегда используйте прямую запись по индексу `s[i] = v`.

## На собеседовании

**Вопрос с собеседования:** Почему в микробенчмарках локальный срез `make([]int, 100)` показывает `0 B/op, 0 allocs/op`, а если размер передать как переменную `make([]int, n)`, результат становится `800 B/op, 1 allocs/op`?
**Ответ:** Компилятор Go может разместить срез на стеке только если его размер статически известен на этапе компиляции (константа) и укладывается в стек-лимит (64 КБ). Если размер задан динамической переменной `n`, компилятор не может знать размер фрейма при генерации машинного кода и обязан вызвать `runtime.makeslice`, выделив память в куче через `mallocgc`.
