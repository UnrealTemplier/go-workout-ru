# Анатомия функции mallocgc: Fast Path, Slow Path и Slower Path

## Условие

Прочитайте `src/runtime/mheap.go` и `src/runtime/malloc.go`. Найдите функцию `mallocgc()` и проследите путь: fast path (`mcache`) → slow path (`mcentral`) → slower path (`mheap.alloc`). Напишите пошаговый разбор с номерами строк.

## Теория

Функция `mallocgc` в файле `src/runtime/malloc.go` — фундаментальный диспетчер памяти рантайма Go.

Пошаговый конвейер аллокации:
1. **Fast Path (Lock-free, L1):**
   - Проверка размера: `size <= maxSmallSize` (32 КБ).
   - Определение подкласса размера `spanClass`.
   - Извлечение спана из локального кэша `c := getg().m.p.ptr().mcache; s := c.alloc[spc]`.
   - Поиск свободного слота за 1 такт: `v := nextFreeFast(s)`.
   - Если успешно — немедленный возврат адреса!
2. **Slow Path (Spinlock, L2):**
   - Если в текущем спане кончились ячейки (`s.empty()`), вызывается `c.refill(spc)`.
   - `refill` вызывает `mcentral.cacheSpan()`:
   - Захватывается `lock(&c.lock)` центрального пула.
   - Извлекается свободный спан из списка `partial`.
   - Спан устанавливается в `c.alloc[spc]`.
3. **Slower Path (Global Lock / OS, L3):**
   - Если в `mcentral` нет свободных спанов, вызывается `mcentral.grow()`.
   - Захватывается глобальный `lock(&mheap_.lock)`.
   - Вызывается `mheap_.alloc(npages, spc)`: поиск свободных 8 КБ страниц в `pageAlloc`.
   - Если страниц нет — `mheap_.grow()` \(\to\) системный вызов `mmap` у ОС.

## Решение по шагам

1. Напишите код, документирующий все три ветви исполнения `mallocgc`.
2. Смоделируйте условия перехода между Fast, Slow и Slower Path.
3. Продемонстрируйте проверку баланса квот GC Assist.

	fmt.Println("3. Fast Path: p.mcache.alloc[spc].nextFreeFast().")
	fmt.Println("4. Slow Path: mcentral[spc].cacheSpan().")

## Под капотом

В начале `mallocgc` всегда проверяется флаг ассистирования:
```go
if gcBlackenEnabled != 0 {
    assistG = getg()
    if assistG.gcAssistBytes < 0 {
        gcAssistAlloc(assistG)
    }
}
```
Если в системе идет конкурентная фаза сборщика мусора, рантайм Go не позволяет горутине выделить память до тех пор, пока она не «отработает долг» по маркировке памяти, защищая процесс от исчерпания RAM.

## Подводные камни

1. Внутри критических секций самого рантайма вызов `mallocgc` категорически запрещен: для внутренних нужд рантайм использует специальные аллокаторы `fixalloc` и `sysAlloc`.
2. Нарушение инвариантов `mallocgc` при использовании `//go:linkname` приводит к трудноуловимым падениям планировщика.

## На собеседовании

**Вопрос с собеседования:** Что происходит внутри `mallocgc`, если программа аллоцирует память быстрее, чем воркеры GC успевают маркировать живые объекты?
**Ответ:** Включается механизм **GC Assist (мутатор-ассистент)**. Аллокатор вычисляет баланс `gcAssistBytes`. Если баланс отрицательный, аллокатор приостанавливает выполнение бизнес-логики текущей горутины и заставляет её выполнять работу сборщика мусора — сканировать указатели и маркировать серые объекты пропорционально объему запрашиваемой памяти. Это автоматически притормаживает агрессивных аллокаторов и предотвращает падение по OOM.
