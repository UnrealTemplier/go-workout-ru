# Утечка памяти в map и ноды bmap как отдельный Size Class

## Условие

Создайте программу с «утечкой» через глобальный map (`map[int][]byte`). Используйте `go tool pprof -inuse_space` и найдите, в каких `mspan` (size class) живут объекты. Объясните, почему map-ноды — отдельный size class.

## Теория

Мапа в Go (`runtime.hmap`) организована как массив корзин — **бакетов (`bmap`)**:
- Каждый бакет `bmap` вмещает ровно **8 пар ключ-значение** + переполняющий указатель `overflow`.
- Размер структуры `bmap` фиксирован для каждого конкретного типа мапы и рассчитывается компилятором.
- Бакеты мапы выделяются аллокатором как самостоятельные объекты кучи и попадают в ближайший `Size Class`.

Опасность утечки памяти в map:
В Go мапа **никогда не уменьшает количество бакетов при удалении элементов (`delete`)**!
Если положить в мапу 1 000 000 ключей, а затем удалить все 1 000 000 ключей, мапа сохранит все выделенные бакеты в памяти.
Память освобождается только при пересоздании мапы: `m = make(map[K]V)`.

## Решение по шагам

1. Создайте глобальную мапу и наполните её 100 000 записей крупными байтовыми массивами.
2. Сохраните профиль памяти кучи `heap_leak.pprof`.
3. Удалите все элементы через `delete()`.
4. Покажите, что память бакетов мапы осталась заблокированной в `HeapInuse`.

## Код решения

**`map_leak.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
	"time"
)

var globalMap = make(map[int][]byte)

func main() {
	var m1, m2, m3 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	const count = 200_000

	// 1. Заполняем мапу: создаются десятки тысяч бакетов bmap
	fmt.Printf("Заполняем мапу %d элементами...\n", count)
	for i := 0; i < count; i++ {
		globalMap[i] = make([]byte, 128)
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("HeapAlloc после заполнения: %d МБ\n", (m2.HeapAlloc-m1.HeapAlloc)/(1024*1024))
	fmt.Printf("HeapInuse после заполнения: %d МБ\n\n", m2.HeapInuse/(1024*1024))

	// 2. Удаляем ВСЕ элементы из мапы через delete()
	fmt.Println("Удаляем все элементы через delete()...")
	for i := 0; i < count; i++ {
		delete(globalMap, i)
	}

	runtime.GC()
	runtime.ReadMemStats(&m3)

	fmt.Printf("После delete() и runtime.GC():\n")
	fmt.Printf("  Длина мапы len(globalMap): %d (мапа пуста!)\n", len(globalMap))
	fmt.Printf("  HeapAlloc: %d МБ (значения освобождены)\n", m3.HeapAlloc/(1024*1024))
	fmt.Printf("  HeapInuse: %d МБ (бакеты bmap удерживаются в памяти!)\n\n", m3.HeapInuse/(1024*1024))

	// Сохраняем профиль
	f, _ := os.Create("map_leak.pprof")
	defer f.Close()
	_ = pprof.WriteHeapProfile(f)

	fmt.Println("Профиль сохранен в map_leak.pprof")
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Демонстрация сохранения памяти бакетов bmap после полного delete

**`Терминал`**

```bash
go run map_leak.go
go tool pprof -top -inuse_space map_leak.pprof
```

## Под капотом

В `src/runtime/map.go`:
Структура `hmap.buckets` указывает на непрерывный массив `bmap`.
При удалении элемента `delete(m, k)` рантайм лишь очищает ячейку `tophash` внутри бакета. Массив бакетов никогда не сжимается и не перемещается, чтобы не нарушать адресацию и не тратить время на реструктуризацию хэш-таблицы.
Единственный способ освободить память пустой мапы — присвоить ей новую ссылку: `globalMap = make(map[int][]byte)`.

## Подводные камни

1. Использование глобальной мапы в качестве долгоживущего in-memory кэша без периодического пересоздания приводит к скрытой утечке оперативной памяти на миллионы бакетов.
2. Для кэшей используйте структуры с TTL (например, `ccache` или шардированные кэши).

## На собеседовании

**Вопрос с собеседования:** Если из `map[int]string` удалить все 10 миллионов элементов с помощью `delete()`, почему потребление оперативной памяти процессом в Prometheus не снизится?
**Ответ:** По спецификации рантайма Go хэш-таблица `hmap` не уменьшает количество бакетов при удалении элементов. Значения удаляются и могут быть собраны GC, но сами структуры бакетов `bmap` (вместимостью по 8 слотов) остаются выделенными в куче навсегда. Чтобы освободить память, необходимо явно создать новую мапу `m = make(...)` или скопировать оставшиеся живые данные в новую мапу.
