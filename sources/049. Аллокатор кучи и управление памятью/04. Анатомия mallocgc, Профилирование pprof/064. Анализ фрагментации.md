# Анализ фрагментации: Расчет коэффициента фрагментации кучи

## Условие

**Fragmentation analysis**: Создайте workload с высокой фрагментацией и измерьте разницу между `HeapAlloc` и `HeapSys`.

## Теория

Коэффициент фрагментации памяти кучи (Heap Fragmentation Ratio) — ключевой показатель здоровья рантайма в долгоживущих Enterprise-сервисах:
$$\text{Fragmentation Ratio} = 1 - \frac{\text{HeapAlloc}}{\text{HeapSys}}$$
- **Нормальный диапазон:** 0.15 – 0.35 (15–35% оверхеда на спаны, кэши и технологические запасы).
- **Критическая фрагментация:** \(> 0.60\) (более 60% памяти процесса удерживается впустую).

Причины высокой фрагментации:
1. Частичное освобождение коллекций (Checkerboard pattern).
2. Застревание мелких долгоживущих объектов в больших спанах (Pinning).
3. Разношерстные размеры объектов, препятствующие объединению смежных страниц.

## Решение по шагам

1. Создайте нагрузочный сценарий, аллоцирующий 50 000 разнокалиберных объектов.
2. Освободите 70% случайных объектов.
3. Рассчитайте метрику фрагментации кучи на основе `HeapAlloc` и `HeapSys`.
4. Продемонстрируйте методы снижения коэффициента фрагментации.

## Код решения

**`fragmentation_analysis.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"runtime"
	"time"
)

func main() {
	fmt.Println("=== Анализ коэффициента фрагментации памяти (Fragmentation Ratio) ===")

	const total = 100_000
	objects := make([][]byte, total)

	// 1. Аллоцируем 100 000 объектов случайных классов (16Б - 2КБ)
	r := rand.New(rand.NewSource(12345))
	for i := 0; i < total; i++ {
		sz := 16 + r.Intn(2000)
		objects[i] = make([]byte, sz)
		objects[i][0] = 1
	}

	// 2. Освобождаем 75% объектов, оставляя каждый 4-й (дырявая память)
	for i := 0; i < total; i++ {
		if i%4 != 0 {
			objects[i] = nil
		}
	}

	runtime.GC()

	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	heapAllocMB := float64(m.HeapAlloc) / (1024 * 1024)
	heapInuseMB := float64(m.HeapInuse) / (1024 * 1024)
	heapSysMB := float64(m.HeapSys) / (1024 * 1024)

	fragRatio := (1.0 - (heapAllocMB / heapSysMB)) * 100
	spanWasteRatio := (1.0 - (heapAllocMB / heapInuseMB)) * 100

	fmt.Printf("Показатели памяти после фрагментации:\n")
	fmt.Printf("  HeapAlloc (полезные данные) : %.2f МБ\n", heapAllocMB)
	fmt.Printf("  HeapInuse (занятые спаны)   : %.2f МБ\n", heapInuseMB)
	fmt.Printf("  HeapSys   (память от ОС)    : %.2f МБ\n\n", heapSysMB)

	fmt.Printf("Фрагментация внутри спанов : %.1f%%\n", spanWasteRatio)
	fmt.Printf("Общий коэффициент фрагментации: %.1f%%\n", fragRatio)

	runtime.KeepAlive(objects)
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Расчет коэффициента фрагментации кучи на основе HeapAlloc и HeapSys

**`Терминал`**

```bash
go run fragmentation_analysis.go
```

## Под капотом

Разница между `HeapInuse` и `HeapAlloc` показывает **внутреннюю фрагментацию спанов**: сколько памяти заблокировано в частично заполненных спанах.
Разница между `HeapSys` и `HeapInuse` показывает **внешнюю фрагментацию и технологический резерв кучи** (`HeapIdle`).
Если `spanWasteRatio` превышает 50%, это означает, что миллионы мелких объектов разбросаны по чужим спанам, и сборщик мусора не может освободить ни одну 8 КБ страницу целиком.

## Подводные камни

1. Высокая фрагментация не всегда означает баг: в приложениях с всплесками нагрузки память вернется в норму через работу Scavenger.
2. Для минимизации фрагментации используйте компактные массивы примитивов вместо деревьев указателей.

## На собеседовании

**Вопрос с собеседования:** Как в production мониторинге настроить алерт на аномальную фрагментацию памяти Go сервиса?
**Ответ:** В Prometheus настраивается вычисляемое правило:
`1 - (go_memstats_heap_alloc_bytes / go_memstats_heap_sys_bytes) > 0.65`
Если в течение 15 минут коэффициент фрагментации держится выше 65% при стабильном RPS, это означает, что сервис страдает от утечки спанов (Span Pinning) или неоптимальных кэшей. Срабатывает алерт на необходимость оптимизации структур данных.
