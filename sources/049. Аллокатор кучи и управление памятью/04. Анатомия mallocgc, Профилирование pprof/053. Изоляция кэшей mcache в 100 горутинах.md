# Изоляция кэшей mcache в 100 горутинах и влияние GOMAXPROCS=1

## Условие

Создайте программу с интенсивной аллокацией в 100 goroutine. Покажите, что `mcache` у каждой P изолирован (нет contention). Затем сделайте `GOMAXPROCS=1` — покажите рост contention на единственном `mcache`.

## Теория

Масштабируемость аллокатора при росте числа параллельных горутин:
- При нормальном `GOMAXPROCS = NumCPU` (например, 8):
  - 100 горутин распределяются по 8 очередям планировщика \(P\).
  - Каждое ядро CPU работает со своим независимым `mcache`.
  - Аллокации происходят параллельно и без блокировок.
- При `GOMAXPROCS = 1`:
  - В системе существует **ровно один \(P\) и ровно один `mcache`**.
  - Все 100 горутин делят один единственный спан для каждого класса размера.
  - Спан опустошается в 8 раз быстрее, вызывая постоянные вытеснения, частые походы в `mcentral` и замедление работы планировщика.

## Решение по шагам

1. Напишите функцию, запускающую 100 горутин с интенсивной аллокацией мелких структур.
2. Измерьте время выполнения при дефолтном `GOMAXPROCS`.
3. Измерьте время при `GOMAXPROCS=1`.
4. Сравните задержки планировщика и накладные расходы.

## Код решения

**`mcache_contention.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

type Payload struct {
	ID   int64
	Data [48]byte
}

func runWorkload(procs int) time.Duration {
	runtime.GOMAXPROCS(procs)
	runtime.GC()

	const goroutines = 100
	const allocsPerG = 20_000

	var wg sync.WaitGroup
	wg.Add(goroutines)

	start := time.Now()
	for i := 0; i < goroutines; i++ {
		go func(id int) {
			defer wg.Done()
			for j := 0; j < allocsPerG; j++ {
				p := &Payload{ID: int64(id)}
				runtime.KeepAlive(p)
			}
		}(i)
	}

	wg.Wait()
	return time.Since(start)
}

func main() {
	numCPU := runtime.NumCPU()
	fmt.Printf("=== Изоляция mcache: Multi-Core vs GOMAXPROCS=1 ===\n")
	fmt.Printf("Доступно физических CPU: %d\n\n", numCPU)

	dMulti := runWorkload(numCPU)
	fmt.Printf("Время работы при GOMAXPROCS=%d : %v\n", numCPU, dMulti)

	dSingle := runWorkload(1)
	fmt.Printf("Время работы при GOMAXPROCS=1  : %v\n", dSingle)

	fmt.Printf("\nУскорение за счет параллельных изолированных mcache: %.2fx\n",
		float64(dSingle)/float64(dMulti))
}
```

ℹ️ Сравнение времени аллокаций при изоляции mcache на всех ядрах против одного P

**`Терминал`**

```bash
go run mcache_contention.go
```

## Под капотом

При `GOMAXPROCS=1` все 100 горутин конкурируют за кванты времени одного ядра.
Хотя contention за мьютексы отсутствует (ядро одно), локальный спан в `mcache` исчерпывается лавинообразно, и рантайм постоянно выполняет проверку `refill`.
При `GOMAXPROCS=8` 8 ядер аппаратно параллельно извлекают слоты из кэшей L1/L2 процессора, удваивая и учетверяя пропускную способность шины памяти.

## Подводные камни

1. Ограничение `GOMAXPROCS=1` в контейнерах Docker при квотах CPU `cpu: 1` часто используется намеренно, но требует осознания, что кэш аллокатора будет один.
2. При падении производительности сервиса всегда проверяйте реальное значение `runtime.GOMAXPROCS(0)`.

## На собеседовании

**Вопрос с собеседования:** Почему Go-сервис в контейнере Kubernetes с лимитом `cpu: 0.5` может испытывать высокий троттлинг CFS, если не настроить `GOMAXPROCS`?
**Ответ:** Если не настроить `GOMAXPROCS` (например, через библиотеку `uber-go/automaxprocs`), рантайм Go выставит `GOMAXPROCS` равным количеству ядер физической ноды (например, 64 ядра). Рантайм создаст 64 \(P\) и попытается запустить десятки горутин параллельно, исчерпав квоту в 0.5 ядра за доли миллисекунды, после чего ядро Linux заблокирует процесс троттлингом до конца 100-миллисекундного окна CFS.
