# Локализация утечек памяти в pprof heap inuse_space

## Условие

**pprof: Heap (Поиск утечек памяти)**: Напиши HTTP-сервер, который при каждом запросе `GET /leak` добавляет срез данных в глобальную мапу, не удаляя старые. Запусти `pprof` heap профиль (`go tool pprof http://localhost:8080/debug/pprof/heap`). Переключи режим отображения на `inuse_space`. Увидь строку, которая удерживает мегабайты памяти (глобальная мапа).

## Теория

Профиль памяти `inuse_space` — золотой стандарт расследования утечек памяти (Memory Leaks) в production:
- В отличие от `alloc_space` (который показывает суммарный оборот), `inuse_space` показывает **только те объекты, которые живы прямо сейчас и удерживаются ссылками**.
- Если при повторных запросах определенная строка кода монотонно увеличивает свое значение в `inuse_space`, это 100% доказательство утечки памяти.
- Типичные причины: глобальные срезы/мапы, незакрытые горутины, удерживающие контексты, забытые слушатели событий.

## Решение по шагам

1. Напишите HTTP-сервер с подключенным пакетом `net/http/pprof`.
2. Реализуйте эндпоинт `/leak`, добавляющий данные в глобальный срез без очистки.
3. Сохраните heap profile и проанализируйте его через `go tool pprof -top -inuse_space`.

## Код решения

**`leak_server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	_ "net/http/pprof" // регистрация /debug/pprof/*
	"os"
	"runtime/pprof"
	"sync"
)

var (
	leakMu      sync.Mutex
	leakedStore [][]byte
)

// Обработчик с намеренной утечкой памяти
func leakHandler(w http.ResponseWriter, r *http.Request) {
	leakMu.Lock()
	defer leakMu.Unlock()

	// Утечка: добавляем 2 МБ при каждом вызове
	chunk := make([]byte, 2*1024*1024)
	chunk[0] = 42
	leakedStore = append(leakedStore, chunk)

	fmt.Fprintf(w, "Утекло 2 МБ! Всего блоков: %d\n", len(leakedStore))
}

func main() {
	http.HandleFunc("/leak", leakHandler)

	// Имитируем 5 вызовов утечки локально
	for i := 0; i < 5; i++ {
		req, _ := http.NewRequest("GET", "/leak", nil)
		leakHandler(nil, req)
	}

	// Сбрасываем heap profile
	f, err := os.Create("leak_audit.pprof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := pprof.WriteHeapProfile(f); err != nil {
		panic(err)
	}

	fmt.Println("Сгенерирован профиль утечки: leak_audit.pprof")
	fmt.Println("Для инспекции запустите:")
	fmt.Println("  go tool pprof -top -inuse_space leak_audit.pprof")
}
```

ℹ️ Моделирование утечки памяти и экспорт inuse_space профиля

**`Терминал`**

```bash
go run leak_server.go
go tool pprof -top -inuse_space leak_audit.pprof
```

## Под капотом

При открытии `pprof -inuse_space leak_audit.pprof`:
Команда `top` выводит:
```text
(pprof) top
Showing nodes accounting for 10MB, 100% of 10MB total
      flat  flat%   sum%        cum   cum%
      10MB   100%   100%       10MB   100%  main.leakHandler
```
Команда `list leakHandler` точно указывает на строку:
`chunk := make([]byte, 2*1024*1024)`
и показывает, что 10 МБ активны и удерживаются глобальным массивом `leakedStore`.

## Подводные камни

1. Анализ утечки по `alloc_space` покажет много мусора в парсерах JSON или сетевых буферах, сбив с толку инженера. Для поиска утечек всегда используйте **только `-inuse_space`**.
2. Чтобы исключить временный мусор, перед снятием профиля полезно вызывать принудительный GC (`/debug/pprof/heap?gc=1`).

## На собеседовании

**Вопрос с собеседования:** Как с помощью `go tool pprof` найти дифференциал утечки (разницу памяти) между двумя точками во времени?
**Ответ:** Используется флаг базового профиля `-base`:
1. В момент времени \(T_1\) снимается первый профиль: `curl -s http://localhost:6060/debug/pprof/heap > base.pprof`.
2. В момент времени \(T_2\) (после нагрузки) снимается второй: `curl -s http://localhost:6060/debug/pprof/heap > current.pprof`.
3. Запускается сравнительный анализ:
   `go tool pprof -inuse_space -base base.pprof current.pprof`
pprof покажет дельту (`+X MB`): будут отображены **только те строки кода, которые увеличили объем удерживаемой памяти за прошедший интервал**.
