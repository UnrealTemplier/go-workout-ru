# Оркестрация Саги (Saga Orchestrator): централизованная стейт-машина, команды и компенсации

## Условие

Реализуй **Saga Orchestrator с RabbitMQ**:
- Orchestrator service: state machine (pending → reserved → paid → shipped)
- Commands: `ReserveInventory`, `ProcessPayment`, `CreateShipment`
- Events: `InventoryReserved`, `PaymentProcessed`, `ShipmentCreated`
- Compensation: `ReleaseInventory`, `RefundPayment`, `CancelShipment`
- State в PostgreSQL, outbox pattern для commands

## Теория

Паттерн Saga Orchestrator:
- В отличие от хореографии, логика бизнес-процесса сосредоточена в едином сервисе `OrderSagaOrchestrator`.
- Стейт-машина заказа в PostgreSQL:
  `PENDING` \(\to\) `INVENTORY_RESERVED` \(\to\) `PAYMENT_COMPLETED` \(\to\) `SHIPPED`.
- Оркестратор отправляет команды в брокер сообщений:
  - `ReserveInventoryCommand` \(\to\) ждет событие `InventoryReservedEvent`.
  - `ProcessPaymentCommand` \(\to\) при сбое отправляет компенсирующую команду `ReleaseInventoryCommand`.
- Прозрачный контроль статуса, легкий мониторинг и простое добавление новых шагов.

## Решение по шагам

1. Создайте стейт-машину оркестратора с перечислением состояний.
2. Смоделируйте выполнение команд бронирования и оплаты.
3. Проверьте сценарий компенсации при сбое платежа.
4. Убедитесь в возврате системы в безопасное состояние `CANCELLED`.

## Код решения

**`saga_orchestrator_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SagaState string

const (
	StatePending           SagaState = "PENDING"
	StateInventoryReserved SagaState = "INVENTORY_RESERVED"
	StatePaymentFailed     SagaState = "PAYMENT_FAILED"
	StateCompensated       SagaState = "COMPENSATED_CANCELLED"
)

type OrderSagaOrchestrator struct {
	State           SagaState
	CommandsEmitted []string
}

func (s *OrderSagaOrchestrator) StepInventoryReserved() {
	s.State = StateInventoryReserved
	s.CommandsEmitted = append(s.CommandsEmitted, "ProcessPaymentCommand")
}

func (s *OrderSagaOrchestrator) StepPaymentFailed() {
	s.State = StatePaymentFailed
	// Компенсирующая команда
	s.CommandsEmitted = append(s.CommandsEmitted, "ReleaseInventoryCommand")
	s.State = StateCompensated
}

func TestSagaOrchestrator(t *testing.T) {
	orchestrator := &OrderSagaOrchestrator{State: StatePending}

	// 1. Склад успешно зарезервирован -> отправляем команду на списание денег
	orchestrator.StepInventoryReserved()
	if orchestrator.State != StateInventoryReserved {
		t.Fatalf("Некорректное состояние: %s", orchestrator.State)
	}

	// 2. Оплата не прошла -> запускаем компенсацию
	orchestrator.StepPaymentFailed()
	if orchestrator.State != StateCompensated {
		t.Fatalf("Состояние должно быть COMPENSATED: %s", orchestrator.State)
	}

	lastCommand := orchestrator.CommandsEmitted[len(orchestrator.CommandsEmitted)-1]
	if lastCommand != "ReleaseInventoryCommand" {
		t.Fatalf("Ожидалась компенсирующая команда ReleaseInventory: %s", lastCommand)
	}

	fmt.Println("Saga Orchestrator успешно выполнил координацию и компенсацию:")
	fmt.Printf("  • Итоговое состояние Саги: %s\n", orchestrator.State)
	fmt.Printf("  • Выпущенные команды: %v\n", orchestrator.CommandsEmitted)
}
```

ℹ️ Централизованная координация Саги со стейт-машиной и компенсацией

## Под капотом

Оркестратор сохраняет текущее состояние в БД после каждого шага. Если сервис оркестратора упадет, после рестарта он восстановит стейт-машину из PostgreSQL и продолжит выполнение Саги с точки останова.

## Подводные камни

Забывать делать компенсирующие команды идемпотентными: если команда `ReleaseInventory` придет на склад дважды, склад не должен разблокировать двойное количество товара.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Pivot Step в Саге от обычных шагов?»
**Ответ:** Pivot Step (Поворотный шаг) — это операция, после успешного выполнения которой Сага больше никогда не компенсируется (откатывается назад), а обязана идти строго вперед до победного конца (Retry until success). Например, фактическая авторизация списания средств в платежном шлюзе часто является поворотным шагом.
