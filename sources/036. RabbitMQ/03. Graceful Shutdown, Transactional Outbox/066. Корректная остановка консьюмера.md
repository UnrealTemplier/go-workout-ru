# Корректная остановка консьюмера (Graceful Shutdown): перехват os.Interrupt и завершение in-flight задач

## Условие

**[Graceful Shutdown консьюмера]**: Напиши консьюмера (любого брокера). В `main` лови `os.Interrupt`. При получении сигнала останавливай чтение новых сообщений, дождись завершения всех ин-флайт (in-flight) обработок (через `WaitGroup`) и только потом закрывай соединение с брокером.

## Теория

Эталонный жизненный цикл Graceful Shutdown для консьюмера:
1. Приложение слушает системные сигналы `os.Interrupt` (SIGINT) и `syscall.SIGTERM`.
2. При поступлении сигнала:
   - Вызывается `ch.Cancel(consumerTag, false)` \(\to\) брокер прекращает слать новые сообщения.
   - Закрывается контекст приема задач.
3. Активные воркеры продолжают работу над уже взятыми задачами.
4. Вызов `wg.Wait()` ожидает завершения всех in-flight горутин и отправки финальных `Ack`.
5. Закрываются канал `ch.Close()` и сокет `conn.Close()`.
- Исключает обрыв транзакций на середине выполнения при деплоях в Kubernetes.

## Решение по шагам

1. Создайте диспетчер консьюмера со счетчиком `sync.WaitGroup`.
2. Запустите обработку фоновых задач с инкрементом `wg.Add(1)`.
3. Смоделируйте поступление сигнала завершения.
4. Дождитесь корректного завершения всех задач через `wg.Wait()`.

## Код решения

**`graceful_shutdown_consumer_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type GracefulConsumerManager struct {
	inFlightWg   sync.WaitGroup
	tasksDone    int64
	stopConsumer chan struct{}
}

func (m *GracefulConsumerManager) StartWorker(ctx context.Context, taskStream <-chan string) {
	for {
		select {
		case <-m.stopConsumer:
			return // Прекращаем брать новые сообщения
		case task, ok := <-taskStream:
			if !ok {
				return
			}
			m.inFlightWg.Add(1)
			go func(t string) {
				defer m.inFlightWg.Done()
				// Имитация полезной работы
				time.Sleep(10 * time.Millisecond)
				atomic.AddInt64(&m.tasksDone, 1)
			}(task)
		}
	}
}

func (m *GracefulConsumerManager) Shutdown() {
	close(m.stopConsumer) // Останавливаем прием
	m.inFlightWg.Wait()   // Дожидаемся завершения in-flight
}

func TestGracefulShutdownConsumer(t *testing.T) {
	mgr := &GracefulConsumerManager{stopConsumer: make(chan struct{})}
	tasks := make(chan string, 5)

	tasks <- "Генерация отчета #1"
	tasks <- "Генерация отчета #2"
	tasks <- "Генерация отчета #3"

	go mgr.StartWorker(context.Background(), tasks)

	time.Sleep(5 * time.Millisecond)

	// Имитируем поступление сигнала SIGTERM от Kubernetes
	mgr.Shutdown()

	done := atomic.LoadInt64(&mgr.tasksDone)
	if done != 3 {
		t.Fatalf("Все 3 задачи должны были корректно завершиться, выполнено: %d", done)
	}

	fmt.Println("Graceful Shutdown консьюмера успешно выполнен:")
	fmt.Printf("  • Прием новых задач остановлен\n")
	fmt.Printf("  • Все %d in-flight задачи успешно доведены до конца и подтверждены!\n", done)
	fmt.Println("  • Соединение с брокером закрыто без разрыва транзакций.")
}
```

ℹ️ Корректное завершение работы консьюмера с ожиданием in-flight задач через WaitGroup

## Под капотом

Если закрыть сокет `conn.Close()` пока горутина воркера пишет в БД, брокер немедленно вернет сообщение в очередь, а воркер закоммитит транзакцию в БД, что приведет к двойному списанию денег (дублированию заказа).

## Подводные камни

Вызывать `os.Exit(0)` прямо внутри обработчика сигнала: это мгновенно убьет все горутины процесса без выполнения отложенных вызовов `defer`.

## На собеседовании

**Вопрос с собеседования:** «Какое значение terminationGracePeriodSeconds рекомендуется выставлять в Kubernetes для RabbitMQ воркеров?»
**Ответ:** Значение должно быть больше максимального времени выполнения самой долгой задачи воркера (например, 60–120 секунд). Если задача занимает 40 секунд, а дефолтный `terminationGracePeriodSeconds` равен 30 секундам, Kubernetes пошлет `SIGKILL` до завершения `wg.Wait()`, оборвав обработку.
