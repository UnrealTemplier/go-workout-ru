# Детальная реализация схемы Transactional Outbox: блокировка FOR UPDATE SKIP LOCKED и очистка

## Условие

**Transactional Outbox Pattern**: Реализуйте паттерн, где бизнес-операция и публикация сообщения происходят в одной транзакции БД. Отдельный процесс читает outbox table и публикует в queue.

## Теория

Промышленный шаблон Outbox Worker с блокировкой `SKIP LOCKED`:
```sql
SELECT id, payload FROM outbox 
WHERE status = 'PENDING' 
ORDER BY id ASC 
LIMIT 50 
FOR UPDATE SKIP LOCKED;
```
- Преимущества:
  - Несколько реплик поллера могут работать параллельно: каждая берет свои 50 строк без взаимного ожидания (No Lock Wait).
  - Исключает повторную отправку одних и тех же записей параллельными воркерами.

## Решение по шагам

1. Создайте структуру транзакционного хранилища Outbox.
2. Реализуйте захват пачки задач с эмуляцией `SKIP LOCKED`.
3. Опубликуйте задачи в очередь.
4. Проверьте фиксацию статуса обработки.

## Код решения

**`outbox_skip_locked_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OutboxRow struct {
	ID     int
	Locked bool
	Sent   bool
}

func FetchBatchSkipLocked(rows []*OutboxRow, limit int) []*OutboxRow {
	var batch []*OutboxRow
	for _, r := range rows {
		if !r.Locked && !r.Sent {
			r.Locked = true
			batch = append(batch, r)
			if len(batch) >= limit {
				break
			}
		}
	}
	return batch
}

func TestOutboxSkipLocked(t *testing.T) {
	rows := []*OutboxRow{
		{ID: 1}, {ID: 2}, {ID: 3}, {ID: 4},
	}

	// Воркер 1 берет 2 записи
	batch1 := FetchBatchSkipLocked(rows, 2)
	// Воркер 2 берет следующие 2 записи без ожидания разблокировки!
	batch2 := FetchBatchSkipLocked(rows, 2)

	if len(batch1) != 2 || batch1[0].ID != 1 || batch1[1].ID != 2 {
		t.Fatalf("Некорректный batch1: %+v", batch1)
	}

	if len(batch2) != 2 || batch2[0].ID != 3 || batch2[1].ID != 4 {
		t.Fatalf("Некорректный batch2: %+v", batch2)
	}

	fmt.Println("Transactional Outbox (FOR UPDATE SKIP LOCKED) успешно отработал:")
	fmt.Printf("  • Воркер 1 захватил ID: %d, %d\n", batch1[0].ID, batch1[1].ID)
	fmt.Printf("  • Воркер 2 захватил ID: %d, %d (без взаимных блокировок!)\n", batch2[0].ID, batch2[1].ID)
}
```

ℹ️ Параллельная неблокирующая выборка пачек Outbox через FOR UPDATE SKIP LOCKED

## Под капотом

Конструкция `SKIP LOCKED` появилась в PostgreSQL 9.5 и MySQL 8.0 специально для реализации надежных очередей на таблицах реляционных баз данных.

## Подводные камни

Забывать указывать `ORDER BY id`: без сортировки порядок выдачи строк недетерминирован, что может приводить к нарушению хронологии событий.

## На собеседовании

**Вопрос с собеседования:** «Почему классический SELECT ... FOR UPDATE без SKIP LOCKED не подходит для пула воркеров?»
**Ответ:** Без `SKIP LOCKED` второй воркер зависнет в ожидании снятия блокировки первой транзакции (Lock Contention), что полностью парализует параллелизм и приведет к резкому росту времени ответа.
