# Паттерн Event Sourcing: сохранение дельты событий и восстановление состояния через Event Replay

## Условие

**Event Sourcing**: Сохраняйте все изменения состояния как последовательность событий в Kafka/NATS JetStream. Восстанавливайте состояние через replay событий.

## Теория

Парадигма Event Sourcing:
- **Традиционный подход (CRUD):** база данных хранит только текущее состояние сущности (`balance = 1500`), а история затирается `UPDATE`.
- **Event Sourcing:**
  - База данных (или брокер) хранит неизменяемый лог всех событий (Append-Only Event Stream):
    1. `AccountOpened { initial: 1000 }`
    2. `MoneyDeposited { amount: 500 }`
    3. `MoneyWithdrawn { amount: 200 }`
  - Текущее состояние сущности вычисляется в любой момент времени путем воспроизведения (Event Replay) всех событий от начала до конца:
    $$1000 + 500 - 200 = 1300.$$
  - Дает 100% аудируемость, возможность отката во времени (Time Travel Debugging) и построение любых аналитических проекций.

## Решение по шагам

1. Создайте структуру доменных событий счета.
2. Реализуйте метод `ReplayEvents`, сворачивающий срез событий в текущий баланс.
3. Смоделируйте историю из 3 событий.
4. Убедитесь в точнейшем расчете текущего состояния.

## Код решения

**`event_sourcing_replay_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BankEvent struct {
	Type   string
	Amount int
}

type BankAccountState struct {
	Balance int
}

func ReplayBankEvents(events []BankEvent) BankAccountState {
	state := BankAccountState{}
	for _, ev := range events {
		switch ev.Type {
		case "ACCOUNT_OPENED":
			state.Balance = ev.Amount
		case "MONEY_DEPOSITED":
			state.Balance += ev.Amount
		case "MONEY_WITHDRAWN":
			state.Balance -= ev.Amount
		}
	}
	return state
}

func TestEventSourcingReplay(t *testing.T) {
	history := []BankEvent{
		{Type: "ACCOUNT_OPENED", Amount: 1000},
		{Type: "MONEY_DEPOSITED", Amount: 500},
		{Type: "MONEY_WITHDRAWN", Amount: 200},
	}

	state := ReplayBankEvents(history)

	if state.Balance != 1300 {
		t.Fatalf("Баланс после Replay должен быть 1300: got %d", state.Balance)
	}

	fmt.Println("Event Sourcing (восстановление через Replay) успешно протестирован:")
	fmt.Printf("  • Всего событий в потоке: %d\n", len(history))
	fmt.Printf("  • Восстановленный текущий баланс счета: %d руб!\n", state.Balance)
}
```

## Под капотом

Когда число событий превышает тысячи, восстановление с нуля замедляется. Для оптимизации используют снимки состояния (Snapshots): раз в 1000 событий сохраняется слепок `balance = 100000`, и replay выполняется только для событий после последнего снапшота.

## Подводные камни

Изменять формат структуры старых событий: события в Event Sourcing неизменяемы (Immutable). При эволюции схемы данных пишут upcasters (адаптеры версий событий).

## На собеседовании

**Вопрос с собеседования:** «Почему RabbitMQ плохо подходит в качестве основного Event Store для Event Sourcing?»
**Ответ:** RabbitMQ спроектирован так, чтобы удалять сообщения сразу после подтверждения (Ack). Он не сохраняет историю за дни и месяцы. Для Event Store используют Apache Kafka (с бесконечным retention), NATS JetStream или специализированную базу данных EventStoreDB.
