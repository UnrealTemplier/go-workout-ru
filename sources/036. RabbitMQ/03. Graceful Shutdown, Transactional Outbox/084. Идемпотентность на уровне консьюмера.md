# Идемпотентность на уровне консьюмера: уникальный message_id и фильтрация повторов

## Условие

**Idempotency**: Добавьте уникальный `message_id` в каждое сообщение. Consumer проверяет, обрабатывалось ли это сообщение раньше (через Redis или БД).

## Теория

Принцип дедупликации через уникальный Message ID:
- Каждое событие при рождении получает `message_id = uuid.NewString()`.
- Воркер:
  1. Выполняет проверку наличия `message_id` в хранилище (БД/Redis).
  2. Если запись есть \(\to\) пропускает операцию и делает `Ack`.
  3. Если записи нет \(\to\) выполняет операцию и сохраняет `message_id` в рамках той же транзакции.
- Гарантирует безопасность при любых повторных доставках.

## Решение по шагам

1. Создайте хранилище обработанных ID.
2. Проверьте успешное выполнение первичного сообщения.
3. Смоделируйте поступление дубликата и проверьте его отсечение.
4. Протестируйте неизменность состояния базы данных.

## Код решения

**`message_id_dedup_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type AccountBalance struct {
	processed map[string]bool
	balance   int
}

func (a *AccountBalance) Deposit(msgID string, amount int) bool {
	if a.processed[msgID] {
		return false // Дубликат: баланс не меняем!
	}
	a.processed[msgID] = true
	a.balance += amount
	return true
}

func TestMessageIDDeduplication(t *testing.T) {
	acc := &AccountBalance{processed: make(map[string]bool), balance: 1000}

	msgID := "tx-uuid-7711"

	// 1. Пополнение счета на 500 руб
	ok1 := acc.Deposit(msgID, 500)
	if !ok1 || acc.balance != 1500 {
		t.Fatalf("Баланс должен стать 1500: %d", acc.balance)
	}

	// 2. Сеть мигнула, продюсер прислал дубликат с тем же msgID
	ok2 := acc.Deposit(msgID, 500)
	if ok2 || acc.balance != 1500 {
		t.Fatalf("Баланс не должен меняться при дубликате: %d", acc.balance)
	}

	fmt.Println("Идемпотентность по message_id успешно подтверждена:")
	fmt.Printf("  • Первое пополнение: успешно (Баланс: %d)\n", acc.balance)
	fmt.Printf("  • Дубликат отброшен:  баланс остался неизменным (%d)!\n", acc.balance)
}
```

## Под капотом

В AMQP 0-9-1 свойство `MessageId` зафиксировано в структуре `amqp.Publishing.MessageId`. Брокер не проверяет его уникальность сам, перекладывая проверку на приложение консьюмера.

## Подводные камни

Генерировать `message_id` внутри цикла ретрая отправки: каждое повторное сообщение получит новый ID, и консьюмер не сможет распознать дубликат! ID должен генерироваться один раз при создании задачи.

## На собеседовании

**Вопрос с собеседования:** «Как долго нужно хранить message_id в кэше дедупликации?»
**Ответ:** Срок хранения (TTL) должен превышать максимальное время жизни ретраев в системе (например, 24–72 часа). Если система повторяет отправку с задержкой до 6 часов, TTL в 24 часа дает 100% гарантию защиты от дублей, предотвращая переполнение памяти.
