# Circuit Breaker на консьюмере через gobreaker: пауза 30 секунд при сбоях внешней базы данных

## Условие

**[Circuit Breaker для консьюмера]**: Если БД упала, консьюмер не должен бесконечно накручивать ретраи (засоряя логи и нагружая брокер). Оберни логику обработки в `gobreaker`. Если БД недоступна, консьюмер должен остановить чтение (или накапливать в памяти до лимита) на 30 секунд, а не спамить `nack`.

## Теория

Защита инфраструктуры с помощью gobreaker:
- Библиотека `github.com/sony/gobreaker` — промышленный стандарт реализации шаблона Предохранителя в Go.
- Если внешний ресурс (PostgreSQL / Redis) падает:
  - Каждая неудачная операция фиксируется в `gobreaker.Settings.ReadyToTrip`.
  - При превышении порога сбоев Circuit Breaker размыкается (`StateOpen`).
  - Метод `cb.Execute()` мгновенно возвращает ошибку `gobreaker.ErrOpenState` без реального обращения к упавшей БД.
  - Консьюмер прекращает вычитку очереди на время таймаута (например 30 секунд), предотвращая лавинообразный спам логами.

## Решение по шагам

1. Создайте структуру настроек Circuit Breaker.
2. Оберните операцию записи в метод `Execute`.
3. Смоделируйте серию сбоев и переход в состояние `Open`.
4. Убедитесь в блокировке вызовов во время таймаута отдыха.

## Код решения

**`gobreaker_consumer_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type CircuitBreakerSimulation struct {
	consecutiveErrors int
	isOpen            bool
}

func (cb *CircuitBreakerSimulation) Execute(fn func() error) error {
	if cb.isOpen {
		return errors.New("circuit breaker is OPEN: fast failing requests")
	}

	err := fn()
	if err != nil {
		cb.consecutiveErrors++
		if cb.consecutiveErrors >= 3 {
			cb.isOpen = true
		}
		return err
	}

	cb.consecutiveErrors = 0
	return nil
}

func TestConsumerGoBreaker(t *testing.T) {
	cb := &CircuitBreakerSimulation{}

	failingDB := func() error {
		return errors.New("connection refused (PostgreSQL 5432)")
	}

	// 1. Три сбоя подряд приводят к размыканию предохранителя
	for i := 1; i <= 3; i++ {
		_ = cb.Execute(failingDB)
	}

	if !cb.isOpen {
		t.Fatal("Circuit Breaker должен был разомкнуться после 3 ошибок")
	}

	// 2. Следующий вызов отсекается мгновенно без нагрузки на БД!
	fastFailErr := cb.Execute(failingDB)
	if fastFailErr.Error() != "circuit breaker is OPEN: fast failing requests" {
		t.Fatalf("Ожидался быстрый отказ: %v", fastFailErr)
	}

	fmt.Println("Circuit Breaker на консьюмере успешно предотвратил спам:")
	fmt.Printf("  • Статус предохранителя: isOpen=%v\n", cb.isOpen)
	fmt.Printf("  • Быстрый отказ: %v\n", fastFailErr)
}
```

## Под капотом

Предохранитель отслеживает время нахождения в состоянии `StateOpen` через встроенный таймер. По истечении таймаута (30с) он переходит в `StateHalfOpen` и пропускает ровно один пробный запрос (Canary Request).

## Подводные камни

Продолжать вычитывать сообщения из RabbitMQ и делать им `Nack(requeue=true)` при открытом Circuit Breaker: сообщения будут крутиться со скоростью 100 000 в секунду, раскаляя процессор. При открытии CB необходимо вызывать `ch.Cancel()`.

## На собеседовании

**Вопрос с собеседования:** «Как сочетать Circuit Breaker и Kubernetes Liveness Probes?»
**Ответ:** Размыкание Circuit Breaker НЕ должно ронять Liveness Probe (`/healthz`). Если Liveness начнет возвращать 500 при открытом CB, Kubernetes перезапустит контейнер, убив in-flight транзакции и создав бесконечный рестарт-луп. Сервис должен оставаться Alive, но временно остановить вычитку очередей.
