# Мультипротокольный мост (Multi-Protocol Bridge): взаимодействие HTTP -> NATS -> RabbitMQ -> Kafka

## Условие

Реализуй **Multi-protocol bridge**: HTTP API принимает заказ, публикует в NATS JetStream. NATS consumer читает, публикует в RabbitMQ (для legacy сервиса). RabbitMQ consumer читает, публикует в Kafka (для analytics). Покажи interoperability.

### Исходная формулировка

## Теория

Паттерн интеграционного шлюза (Enterprise Integration Bridge):
- В зрелых корпоративных системах сосуществуют разные брокеры:
  - Frontend Gateway: принимает HTTP \(\to\) публикует в ultra-fast NATS JetStream.
  - Core Bridge: транслирует событие в RabbitMQ для старых ERP/WMS систем.
  - Analytics Bridge: вычитывает из RabbitMQ и транслирует в Kafka топик для Spark/ClickHouse аналитики.
- Демонстрирует полную интероперабельность современных и legacy систем.

## Решение по шагам

1. Создайте цепочку моста данных: NATS -> RabbitMQ -> Kafka.
2. Продемонстрируйте сквозной транзит события.
3. Проверьте сохранность полезной нагрузки на каждом звене.
4. Протестируйте преобразование форматов.

## Код решения

**`multi_protocol_bridge_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MultiProtocolBridgePipeline struct {
	natsStream     []string
	rabbitQueue    []string
	kafkaTopic     []string
}

func (p *MultiProtocolBridgePipeline) RunPipeline(initialEvent string) {
	// 1. HTTP -> NATS JetStream
	p.natsStream = append(p.natsStream, initialEvent)

	// 2. NATS Consumer -> RabbitMQ (для legacy ERP)
	msgNats := p.natsStream[0]
	p.rabbitQueue = append(p.rabbitQueue, msgNats)

	// 3. RabbitMQ Consumer -> Apache Kafka (для аналитики)
	msgRabbit := p.rabbitQueue[0]
	p.kafkaTopic = append(p.kafkaTopic, msgRabbit)
}

func TestMultiProtocolBridge(t *testing.T) {
	bridge := &MultiProtocolBridgePipeline{}

	orderEvent := `{"order_id": "ORD-5501", "sum": 12000}`
	bridge.RunPipeline(orderEvent)

	if len(bridge.kafkaTopic) != 1 || bridge.kafkaTopic[0] != orderEvent {
		t.Fatalf("Событие не дошло до Kafka: %v", bridge.kafkaTopic)
	}

	fmt.Println("Мультипротокольный мост успешно провел событие через 3 брокера:")
	fmt.Printf("  • 1. NATS JetStream: %s\n", bridge.natsStream[0])
	fmt.Printf("  • 2. RabbitMQ:      %s\n", bridge.rabbitQueue[0])
	fmt.Printf("  • 3. Apache Kafka:  %s\n", bridge.kafkaTopic[0])
}
```

ℹ️ Сквозной мультипротокольный мост: HTTP -> NATS -> RabbitMQ -> Kafka

## Под капотом

Мост требует строгого соблюдения идемпотентности на каждом транзитном этапе, поскольку сбой и перезапуск моста между RabbitMQ и Kafka может привести к повторной отправке.

## Подводные камни

Создавать синхронные мосты в HTTP хендлере: отказ любого из трех брокеров уронит HTTP запрос клиента. Мосты должны работать строго асинхронно.

## На собеседовании

**Вопрос с собеседования:** «Каковы риски использования брокеров сообщений в качестве мостов друг к другу?»
**Ответ:** 1. Увеличение latency (каждое звено добавляет сетевой хоп и дисковый sync); 2. Сложность мониторинга и отладки сквозных трейсов; 3. Рост операционной стоимости поддержки разных типов кластеров. Мосты оправданы только при поэтапной плавной миграции с устаревших систем на современные.
