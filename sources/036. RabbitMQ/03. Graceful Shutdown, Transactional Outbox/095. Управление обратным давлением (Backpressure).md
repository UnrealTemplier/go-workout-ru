# Управление обратным давлением (Backpressure): prefetch limits, динамические батчи и троттлинг

## Условие

**Backpressure**: Если consumer не успевает, используйте prefetch limits, уменьшайте batch size или временно приостанавливайте producer.

## Теория

Стратегии управления Backpressure в распределенных системах:
1. **Pull-модель вместо Push:** клиент запрашивает сообщения только тогда, когда у него есть свободные ресурсы процессора и памяти.
2. **Prefetch Limits (`channel.Qos`):** жесткое ограничение количества задач «в полете» на одного воркера.
3. **Adaptive Batch Sizing:** при росте задержки обработки размер пачки автоматически уменьшается.
4. **Producer Throttling (TCP Flow Control):** когда брокер видит забитые очереди, он перестает считывать данные из TCP сокета продюсера, естественным образом замедляя его генерацию.

## Решение по шагам

1. Создайте динамический регулятор размера пачки (Adaptive Backpressure).
2. Смоделируйте рост времени обработки задачи.
3. Проверьте автоматическое уменьшение размера следующей пачки.
4. Убедитесь в стабилизации потребления ресурсов.

## Код решения

**`backpressure_adaptive_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type AdaptiveBackpressureManager struct {
	currentBatchSize int
	maxBatchSize     int
	minBatchSize     int
}

func (m *AdaptiveBackpressureManager) Adjust(latency time.Duration) {
	// Если обработка заняла больше 50мс -> уменьшаем батч (Backpressure)
	if latency > 50*time.Millisecond {
		m.currentBatchSize /= 2
		if m.currentBatchSize < m.minBatchSize {
			m.currentBatchSize = m.minBatchSize
		}
	} else {
		// Система справляется -> увеличиваем размер
		m.currentBatchSize += 5
		if m.currentBatchSize > m.maxBatchSize {
			m.currentBatchSize = m.maxBatchSize
		}
	}
}

func TestAdaptiveBackpressure(t *testing.T) {
	mgr := &AdaptiveBackpressureManager{
		currentBatchSize: 50,
		maxBatchSize:     100,
		minBatchSize:     10,
	}

	// Задержка взлетела до 120мс (сервер перегружен)
	mgr.Adjust(120 * time.Millisecond)

	if mgr.currentBatchSize != 25 {
		t.Fatalf("Размер батча должен был уменьшиться до 25: %d", mgr.currentBatchSize)
	}

	fmt.Println("Адаптивный контроль нагрузки (Backpressure) успешно отработал:")
	fmt.Printf("  • Обнаружена перегрузка -> размер батча снижен до: %d сообщений\n", mgr.currentBatchSize)
	fmt.Println("  • Потребление памяти стабилизировано!")
}
```

## Под капотом

В ядре RabbitMQ при превышении порога памяти Erlang посылает сигнал `alarm: set` и блокирует вызовы `socket:recv` для всех продюсерских соединений, распространяя Backpressure по цепочке upstream сервисов.

## Подводные камни

Пытаться накапливать бесконечные локальные буферы в каналах Go (`make(chan Message, 1000000)`): это просто переносит OOM из брокера в оперативную память приложения.

## На собеседовании

**Вопрос с собеседования:** «Что происходит на сетевом уровне TCP, когда RabbitMQ включает Backpressure на продюсера?»
**Ответ:** RabbitMQ перестает вычитывать входящие байты из TCP сокета. Буфер сокета операционной системы заполняется, и стек TCP отправляет клиенту TCP Window Update со значением `Window Size = 0` (Zero Window). Сетевой стек продюсера аппаратно блокирует системный вызов `write()`, физически останавливая отправку сообщений без падений.
