# Сага на событиях (Saga Choreography): сквозная цепочка событий OrderCreated -> PaymentFailed -> OrderCancelled

## Условие

**Saga Pattern через events**: Реализуйте распределенную транзакцию через цепочку событий с компенсирующими действиями (например, `OrderCreated` -> `PaymentFailed` -> `OrderCancelled`).

## Теория

Децентрализованная Сага на событиях (Event-Driven Saga):
- Никакого центрального сервера-оркестратора.
- Событийный поток:
  1. `OrderService`: публикует `OrderCreated`.
  2. `PaymentService`: реагирует на `OrderCreated`, фиксирует нехватку денег на счете \(\to\) публикует `PaymentFailed`.
  3. `OrderService`: слушает `PaymentFailed`, переводит статус заказа в `CANCELLED` \(\to\) публикует `OrderCancelled`.
  4. `AnalyticsService`: слушает `OrderCancelled`, обновляет конверсию.
- Максимальная децентрализация и независимость сервисов.

## Решение по шагам

1. Создайте цепочку обработчиков событий децентрализованной Саги.
2. Проверьте реакцию сервиса платежей на `OrderCreated`.
3. Проверьте реакцию сервиса заказов на `PaymentFailed`.
4. Убедитесь в корректной отмене заказа.

## Код решения

**`event_saga_choreography_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type EventDrivenSagaSystem struct {
	orderStatus string
	eventsLog   []string
}

func (s *EventDrivenSagaSystem) HandleEvent(event string) {
	s.eventsLog = append(s.eventsLog, event)
	switch event {
	case "OrderCreated":
		// Платежный сервис пробует списать средства -> Сбой -> Публикует PaymentFailed
		s.HandleEvent("PaymentFailed")
	case "PaymentFailed":
		// Сервис заказов отменяет заказ
		s.orderStatus = "CANCELLED"
		s.eventsLog = append(s.eventsLog, "OrderCancelled")
	}
}

func TestEventDrivenSaga(t *testing.T) {
	sys := &EventDrivenSagaSystem{orderStatus: "NEW"}

	sys.HandleEvent("OrderCreated")

	if sys.orderStatus != "CANCELLED" {
		t.Fatalf("Заказ должен быть отменен: %s", sys.orderStatus)
	}

	fmt.Println("Event-Driven Saga Choreography успешно завершена:")
	fmt.Printf("  • Цепочка событий: %v\n", sys.eventsLog)
	fmt.Printf("  • Итоговый статус заказа: %s\n", sys.orderStatus)
}
```

ℹ️ Децентрализованная реакция сервисов на события и выполнение компенсаций

## Под капотом

В хореографии сервисы обмениваются сообщениями исключительно через абстрактные Exchange брокера, не зная физических адресов друг друга.

## Подводные камни

Отсутствие глобального `correlation_id`: при отладке в логах будет невозможно связать `PaymentFailed` с конкретным `OrderCreated`.

**Вопрос с собеседования:** «Каковы главные недостатки Saga Choreography по сравнению с Orchestration?»
**Ответ:** 1. Сложность визуализации бизнес-процесса; 2. Риск циклических зависимостей; 3. Трудность тестирования всей интеграционной цепочки; 4. Сложность контроля таймаутов, когда один из шагов завис и не отвечает.
