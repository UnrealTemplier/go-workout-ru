# Локальный повтор с экспоненциальным отпором и джиттером: обработка в памяти до отправки в DLQ

## Условие

Реализуйте retry с exponential backoff и jitter на стороне консюмера без повторной публикации: используйте внутренний таймер и повторную обработку в памяти, пока не будет успеха или не исчерпаются попытки, после чего отправляйте в DLQ.

## Теория

Паттерн локального повтора (In-Memory Retry with Jitter):
- Вместо того чтобы сразу возвращать сообщение в брокер через `nack(requeue=true)`:
  - Консьюмер повторяет операцию локально в памяти горутины.
  - Интервал между попытками:
    $$\text{Delay} = \min(\text{MaxDelay}, \text{Base} \times 2^{\text{attempt}}) + \text{rand}(0, \text{Jitter}).$$
  - Если за 3–5 попыток успех не достигнут \(\to\) сообщение один раз отправляется в DLQ через `reject(false)`.
  - Снижает холостой сетевой трафик и нагрузку на брокер в десятки раз.

## Решение по шагам

1. Создайте функцию расчета задержки с джиттером.
2. Смоделируйте локальный цикл из 3 попыток.
3. Проверьте успешное выполнение на 3-й попытке без отправки в DLQ.
4. Протестируйте уход в DLQ при исчерпании лимита попыток.

## Код решения

**`in_memory_retry_jitter_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"math/rand"
	"testing"
	"time"
)

func CalculateBackoffWithJitter(attempt int, base time.Duration) time.Duration {
	multiplier := 1 << attempt
	delay := base * time.Duration(multiplier)
	jitter := time.Duration(rand.Int63n(int64(base)))
	return delay + jitter
}

func TestInMemoryRetryWithJitter(t *testing.T) {
	attempts := 0
	flakyOperation := func() error {
		attempts++
		if attempts < 3 {
			return errors.New("temporary resource lock")
		}
		return nil
	}

	maxRetries := 4
	var err error
	for a := 0; a < maxRetries; a++ {
		err = flakyOperation()
		if err == nil {
			break
		}
		backoff := CalculateBackoffWithJitter(a, 2*time.Millisecond)
		time.Sleep(backoff)
	}

	if err != nil || attempts != 3 {
		t.Fatalf("Операция должна была завершиться успехом на 3-й попытке: attempts=%d, err=%v", attempts, err)
	}

	fmt.Println("Локальный повтор с Exponential Backoff и Jitter успешен:")
	fmt.Printf("  • Потребовалось попыток: %d\n", attempts)
	fmt.Println("  • Задача успешно решена локально в памяти без лишней пересылки в брокер!")
}
```

## Под капотом

Джиттер (случайный сдвиг) размывает пик обращений: если 100 воркеров одновременно упали на обращении к базе, они повторят запросы не строго через 2000 мс, а в случайном окне 2000–2500 мс, предотвращая повторный коллапс БД.

## Подводные камни

Делать локальный `time.Sleep` дольше дедлайна брокера: если консьюмер спит в памяти 5 минут без подтверждения, брокер сочтет его мертвым по таймауту и отдаст сообщение другому воркеру.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между Full Jitter и Equal Jitter алгоритмами?»
**Ответ:** Full Jitter выбирает случайное число от 0 до расчетного экспоненциального бэкоффа: `rand(0, backoff)`. Equal Jitter оставляет половину времени фиксированной, а вторую половину рандомизирует: `backoff/2 + rand(0, backoff/2)`. Исследования AWS показали, что Full Jitter дает наименьшее время устранения заторов.
