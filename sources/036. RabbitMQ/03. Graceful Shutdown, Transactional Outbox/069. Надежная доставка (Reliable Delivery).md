# Надежная доставка (Reliable Delivery): Transactional Outbox + Publisher Confirms

## Условие

Реализуйте **reliable delivery**: сохраняйте сообщения в локальной БД перед отправкой, помечайте как sent после confirm (transactional outbox pattern).

## Теория

Сквозная надежность доставки бизнес-событий:
- Связка Transactional Outbox + Publisher Confirms:
  1. В транзакции БД сохраняется заказ и создается запись в таблице `outbox` со статусом `NEW`.
  2. Фоновый воркер считывает записи со статусом `NEW`.
  3. Публикует сообщение в RabbitMQ в режиме `Confirm(false)`.
  4. При получении `Ack` от брокера статус записи обновляется на `SENT`.
  5. Если произошел сбой сети или брокер вернул `Nack`, запись остается в `NEW` и будет отправлена повторно при следующем цикле.

## Решение по шагам

1. Создайте структуру записи таблицы Outbox с полем статуса.
2. Реализуйте метод отправки с обновлением статуса по подтверждению.
3. Смоделируйте временный отказ брокера и повторный цикл.
4. Проверьте гарантированную доставку.

## Код решения

**`reliable_outbox_confirms_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OutboxMessageStatus string

const (
	StatusNew  OutboxMessageStatus = "NEW"
	StatusSent OutboxMessageStatus = "SENT"
)

type ReliableOutboxEntry struct {
	ID      int
	Payload string
	Status  OutboxMessageStatus
}

type ReliableOutboxRepository struct {
	entries []*ReliableOutboxEntry
}

func (r *ReliableOutboxRepository) ProcessPending(publishFn func(payload string) bool) int {
	sentCount := 0
	for _, e := range r.entries {
		if e.Status == StatusNew {
			// Отправка с ожиданием Publisher Confirm
			if publishFn(e.Payload) {
				e.Status = StatusSent
				sentCount++
			}
		}
	}
	return sentCount
}

func TestReliableDeliveryPattern(t *testing.T) {
	repo := &ReliableOutboxRepository{
		entries: []*ReliableOutboxEntry{
			{ID: 1, Payload: "Платеж #101", Status: StatusNew},
			{ID: 2, Payload: "Платеж #102", Status: StatusNew},
		},
	}

	sent := repo.ProcessPending(func(payload string) bool {
		// Брокер успешно подтвердил запись на диск (Publisher Confirm Ack)
		return true
	})

	if sent != 2 || repo.entries[0].Status != StatusSent || repo.entries[1].Status != StatusSent {
		t.Fatalf("Все записи должны перейти в статус SENT, отправлено: %d", sent)
	}

	fmt.Println("Reliable Delivery (Transactional Outbox + Confirms) успешно протестирован:")
	fmt.Printf("  • Успешно отправлено и подтверждено записей: %d\n", sent)
	fmt.Printf("  • Статус записи в БД: %s\n", repo.entries[0].Status)
}
```

## Под капотом

Связка Outbox + Confirms полностью защищает систему от рассинхронизации состояния базы данных и брокера сообщений, гарантируя семантику At-Least-Once Delivery.

## Подводные камни

Помечать статус `SENT` до получения ответа `Publisher Confirm`: при сетевом сбое сообщение будет считаться отправленным, но брокер его так и не получит.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить конкурентную вычитку одних и тех же записей таблицы outbox несколькими репликами сервиса?»
**Ответ:** Использовать конструкцию `SELECT * FROM outbox WHERE status = 'NEW' ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`. Конструкция `SKIP LOCKED` блокирует 100 выбранных строк для текущей транзакции, позволяя другим параллельным подам одновременно захватывать следующие свободные пачки без взаимных блокировок.
