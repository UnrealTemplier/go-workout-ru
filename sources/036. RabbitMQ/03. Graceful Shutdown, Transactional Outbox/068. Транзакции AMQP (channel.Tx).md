# Транзакции AMQP (channel.Tx): атомарность пачки сообщений и сравнение скорости с Confirms

## Условие

Настройте **transactions** (`channel.Tx()`) для атомарной публикации нескольких сообщений (но это медленно, используйте confirms).

## Теория

Атомарные транзакции протокола AMQP:
- Методы:
  - `ch.Tx()`: переводит канал в транзакционный режим (`tx.select`).
  - `ch.TxCommit()`: коммитит все сообщения, отправленные в канал с момента начала транзакции.
  - `ch.TxRollback()`: отменяет все отправленные сообщения.
- **Инженерное сравнение с Publisher Confirms:**
  - `TxCommit` является **синхронным блокирующим** вызовом: клиент ждет сетевой round-trip и дисковый sync брокера.
  - Скорость транзакций: ~200 сообщений/сек.
  - Скорость Publisher Confirms: ~50 000 сообщений/сек (быстрее в 250 раз!).
  - В современных HighLoad системах транзакции AMQP практически не применяются в пользу Confirms.

## Решение по шагам

1. Создайте модель транзакционного канала `AMQPTransactionSession`.
2. Опубликуйте пачку сообщений в транзакции.
3. Продемонстрируйте сценарий отката `TxRollback` при ошибке.
4. Продемонстрируйте сценарий успешного коммита `TxCommit`.

## Код решения

**`amqp_transactions_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type AMQPTransactionSession struct {
	inTx       bool
	buffer     []string
	committed  []string
}

func (s *AMQPTransactionSession) TxSelect() {
	s.inTx = true
}

func (s *AMQPTransactionSession) Publish(msg string) {
	if s.inTx {
		s.buffer = append(s.buffer, msg)
	} else {
		s.committed = append(s.committed, msg)
	}
}

func (s *AMQPTransactionSession) TxRollback() {
	s.buffer = nil // Очищаем буфер
}

func (s *AMQPTransactionSession) TxCommit() {
	s.committed = append(s.committed, s.buffer...)
	s.buffer = nil
}

func TestAMQPTransactions(t *testing.T) {
	tx := &AMQPTransactionSession{}
	tx.TxSelect()

	// 1. Сценарий отката: публикуем 2 сообщения, затем сбой
	tx.Publish("Сообщение 1 (откат)")
	tx.Publish("Сообщение 2 (откат)")
	tx.TxRollback()

	if len(tx.committed) != 0 {
		t.Fatal("После Rollback committed должен быть пуст")
	}

	// 2. Сценарий успешного коммита
	tx.Publish("Атомарный перевод: списание со счета А")
	tx.Publish("Атомарный перевод: зачисление на счет Б")
	tx.TxCommit()

	if len(tx.committed) != 2 {
		t.Fatalf("Ожидалось 2 закоммиченных сообщения, получено: %d", len(tx.committed))
	}

	fmt.Println("Атомарные транзакции AMQP (channel.Tx) успешно протестированы:")
	fmt.Printf("  • Сценарий Rollback: отменено 2 сообщения\n")
	fmt.Printf("  • Сценарий Commit: успешно зафиксировано 2 сообщения атомарно!\n")
}
```

## Под капотом

Режим `Tx` и режим `Confirm` взаимоисключающие в AMQP 0-9-1: канал может находиться либо в режиме транзакций, либо в режиме подтверждений, одновременный вызов вызовет ошибку `channel exception (406): PRECONDITION_FAILED`.

## Подводные камни

Использовать `TxCommit` в высоконагруженных продюсерах: пропускная способность сервера мгновенно просядет на 2 порядка.

## На собеседовании

**Вопрос с собеседования:** «Почему в RabbitMQ отказались от AMQP Transactions в пользу Publisher Confirms?»
**Ответ:** Транзакции AMQP блокируют поток выполнения и требуют синхронного ожидания дискового ввода-вывода брокера на каждый коммит. Publisher Confirms полностью асинхронны: продюсер продолжает слать сообщения непрерывным потоком, а брокер присылает подтверждения по мере готовности, обеспечивая скорость на 2–3 порядка выше.
