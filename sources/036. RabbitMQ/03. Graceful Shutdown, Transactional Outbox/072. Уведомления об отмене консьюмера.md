# Уведомления об отмене консьюмера: перехват channel.NotifyCancel при удалении очереди

## Условие

Используйте **consumer cancellation notification**: если queue удаляется, consumer получает уведомление и может переподключиться.

## Теория

Механизм Consumer Cancellation Notification:
- Если администратор или автоматический скрипт удаляет очередь на брокере:
  - По стандарту AMQP брокер отправляет консьюмеру кадр `basic.cancel`.
  - Канал `ch.NotifyCancel(make(chan string, 1))` получает строковый идентификатор `consumerTag`.
  - Цикл чтения `range msgs` штатно закрывается.
  - Консьюмер может перехватить это событие, залогировать предупреждение, заново объявить очередь и возобновить работу.

## Решение по шагам

1. Создайте канал перехвата отмены `NotifyCancel`.
2. Смоделируйте событие удаления очереди со стороны брокера.
3. Перехватите `consumerTag`.
4. Протестируйте реакцию восстановления.

## Код решения

**`consumer_cancel_notification_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CancellationListener struct {
	notifyCancel chan string
}

func (l *CancellationListener) OnQueueDeletedByAdmin(tag string) {
	l.notifyCancel <- tag
}

func TestConsumerCancelNotification(t *testing.T) {
	listener := &CancellationListener{
		notifyCancel: make(chan string, 1),
	}

	consumerTag := "ctag-order-worker-104"

	// Имитация удаления очереди брокером
	listener.OnQueueDeletedByAdmin(consumerTag)

	receivedTag := <-listener.notifyCancel
	if receivedTag != consumerTag {
		t.Fatalf("Ожидался consumerTag %s, получено: %s", consumerTag, receivedTag)
	}

	fmt.Println("Consumer Cancellation Notification успешно перехвачен:")
	fmt.Printf("  • Отмененный ConsumerTag: %s\n", receivedTag)
	fmt.Println("  • Консьюмер готов к переобъявлению топологии!")
}
```

## Под капотом

Уведомление об отмене консьюмера позволяет приложению избежать зависания на блокирующем чтении из пустого сетевого сокета после того, как очередь на брокере прекратила существование.

## Подводные камни

Не слушать канал `NotifyCancel`: в этом случае при удалении очереди консьюмер продолжит висеть в памяти без входящих сообщений, внешне казаясь живым.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях RabbitMQ отправляет basic.cancel консьюмеру?»
**Ответ:** 
1. Очередь была удалена администратором через CLI или Management UI.
2. Нода кластера, на которой физически находилась очередь, упала (для незеркалированных очередей).
3. Очередь была удалена по таймауту неактивности (`x-expires`).
