# Шардирование очередей: Consistent Hash Exchange (x-consistent-hash) и балансировка по ключу

## Условие

Создайте **sharded queue** через `x-consistent-hash` exchange для распределения нагрузки.

## Теория

Горизонтальное шардирование очередей (Consistent Hash Exchange):
- В RabbitMQ одна очередь обслуживается одним ядром CPU процессора (Erlang Process).
- Если поток событий превышает 50 000 RPS, одна очередь становится бутылочным горлышком.
- **Плагин `rabbitmq_consistent_hash_exchange`:**
  - Обменник объявляется с типом `"x-consistent-hash"`.
  - К нему привязываются \(N\) очередей шардов: `orders_shard_1`, `orders_shard_2`, `orders_shard_3`.
  - Брокер вычисляет хэш от routing key (например, `user_id`) и направляет сообщение в соответствующий шард.
  - Сообщения одного пользователя всегда попадают строго в один шард (сохранение порядка), а нагрузка равномерно делится между ядрами CPU.

## Решение по шагам

1. Создайте хеш-функцию консистентного распределения по шардам.
2. Смоделируйте привязку 3 очередей шардов с весами.
3. Проверьте, что один и тот же `user_id` всегда попадает в один и тот же шард.
4. Убедитесь в равномерном распределении разных пользователей.

## Код решения

**`consistent_hash_sharding_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

type ConsistentHashRouter struct {
	shards []string
}

func (r *ConsistentHashRouter) GetShard(routingKey string) string {
	h := fnv.New32a()
	_, _ = h.Write([]byte(routingKey))
	index := int(h.Sum32()) % len(r.shards)
	return r.shards[index]
}

func TestConsistentHashSharding(t *testing.T) {
	router := &ConsistentHashRouter{
		shards: []string{"orders_shard_0", "orders_shard_1", "orders_shard_2"},
	}

	// 1. Детерминированность: один пользователь всегда попадает в один шард
	shardA1 := router.GetShard("user_1001")
	shardA2 := router.GetShard("user_1001")
	if shardA1 != shardA2 {
		t.Fatalf("Нарушена детерминированность хэширования: %s vs %s", shardA1, shardA2)
	}

	// 2. Другой пользователь может попасть в другой шард
	shardB := router.GetShard("user_9942")

	fmt.Println("Consistent Hash Exchange успешно распределил нагрузку по шардам:")
	fmt.Printf("  • user_1001 -> %s (повтор: %s)\n", shardA1, shardA2)
	fmt.Printf("  • user_9942 -> %s\n", shardB)
}
```

ℹ️ Детерминированное распределение сообщений по очередям-шардам через Consistent Hash

**`Терминал`**

```bash

go test -v consistent_hash_sharding_test.go

```

## Под капотом

Плагин использует алгоритм хэш-кольца (Hash Ring) с весами привязок. Если привязать очередь с весом `"10"`, она получит в 10 раз больше виртуальных слотов на кольце, чем очередь с весом `"1"`.

## Подводные камни

Использовать случайный routing key (например, `uuid.NewString()`): в этом случае сообщения одного пользователя раскидаются по разным шардам, и строгий порядок обработки нарушится.

## На собеседовании

**Вопрос с собеседования:** «Как Consistent Hash Exchange позволяет объединить преимущества RabbitMQ и Kafka?»
**Ответ:** В Kafka сообщения распределяются по партициям по хэшу ключа (Partition Key). В RabbitMQ с плагином `x-consistent-hash` достигается аналогичный эффект: шардирование очередей по ключу обеспечивает параллелизм нескольких очередей и сохранение строгого порядка сообщений в рамках сущности.
