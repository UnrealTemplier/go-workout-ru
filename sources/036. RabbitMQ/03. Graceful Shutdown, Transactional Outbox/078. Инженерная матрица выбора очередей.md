# Инженерная матрица выбора очередей (Decision Matrix): когда NATS, RabbitMQ или Apache Kafka

## Условие

Напиши **decision matrix**: когда какой MQ. NATS Core — simple pub/sub, low latency, no persistence. NATS JetStream — persistence, streams, KV, simple ops. RabbitMQ — complex routing, AMQP, enterprise. Kafka — high throughput, log compaction, stream processing, big data.

## Теория

Архитектурная матрица выбора брокера сообщений:
| Критерий | NATS Core | NATS JetStream | RabbitMQ | Apache Kafka |
| :--- | :--- | :--- | :--- | :--- |
| **Главная цель** | Ultra Low Latency Pub/Sub | Легковесный персистентный стриминг | Сложная маршрутизация бизнес-задач | High Throughput распределенный лог |
| **Задержка (Latency)** | Микросекунды (< 10 µs) | Суб-миллисекунды (< 1 ms) | Миллисекунды (1–3 ms) | Десятки миллисекунд (5–20 ms) |
| **Throughput** | 10M+ msg/s | 500k+ msg/s | 50k–100k msg/s | 1M–5M msg/s |
| **Фичи** | Fire-and-Forget | Streams, KV, ObjectStore | AMQP, DLX, TTL, Priority, Headers | Partitions, Log Compaction, Retention |
| **Где использовать** | Торговые роботы, IoT телеметрия | Cloud-native микросервисы | E-commerce заказы, платежные шлюзы | Кликстрим, CDC, BigData, аналитика |

## Решение по шагам

1. Создайте структуру критериев выбора брокера.
2. Реализуйте функцию рекомендации по бизнес-требованиям.
3. Протестируйте сценарий сложной маршрутизации заказов (RabbitMQ).
4. Протестируйте сценарий Big Data аналитики (Kafka).

## Код решения

**`mq_decision_matrix_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BusinessRequirements struct {
	NeedsComplexRouting bool
	NeedsUltraLowLatency bool
	NeedsBigDataStreams bool
}

func RecommendBroker(req BusinessRequirements) string {
	if req.NeedsUltraLowLatency {
		return "NATS Core (микросекундная задержка)"
	}
	if req.NeedsBigDataStreams {
		return "Apache Kafka (миллионный throughput, партиции, log compaction)"
	}
	if req.NeedsComplexRouting {
		return "RabbitMQ (гибкая AMQP топология, DLX, приоритеты, подтверждения)"
	}
	return "NATS JetStream (легковесный cloud-native стриминг)"
}

func TestMQDecisionMatrix(t *testing.T) {
	b1 := RecommendBroker(BusinessRequirements{NeedsComplexRouting: true})
	b2 := RecommendBroker(BusinessRequirements{NeedsBigDataStreams: true})
	b3 := RecommendBroker(BusinessRequirements{NeedsUltraLowLatency: true})

	if b1 != "RabbitMQ (гибкая AMQP топология, DLX, приоритеты, подтверждения)" {
		t.Fatalf("Ожидался RabbitMQ: %s", b1)
	}

	fmt.Println("Инженерная матрица выбора брокеров (Decision Matrix) успешно подтверждена:")
	fmt.Printf("  • Сложные заказы / платежи: %s\n", b1)
	fmt.Printf("  • Поток кликов / аналитика:  %s\n", b2)
	fmt.Printf("  • Торговые роботы / HFT:    %s\n", b3)
}
```

## Под капотом

В крупных BigTech компаниях (Яндекс, Ozon, Авито) эксплуатируют гибридный стек: Kafka для шины событий и аналитики, а RabbitMQ для очередей задач транзакционных бэкенд-сервисов.

## Подводные камни

Использовать Kafka в качестве классической Work Queue: из-за привязки воркеров к партициям невозможно добавить воркеров больше, чем число партиций.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя использовать RabbitMQ для хранения истории событий за 2 года?»
**Ответ:** RabbitMQ — это брокер очередей, его цель — доставить сообщение и немедленно стереть его. При накоплении миллионов сообщений производительность очередей деградирует (сообщения сбрасываются на диск, замедляя оперативную память). Для долговременного хранения истории (Event Sourcing) предназначена Kafka с настраиваемым retention period.
