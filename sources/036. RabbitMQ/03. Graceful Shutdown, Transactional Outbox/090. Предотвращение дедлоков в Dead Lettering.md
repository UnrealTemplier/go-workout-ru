# Предотвращение дедлоков в Dead Lettering: чтение из dlx_q, сохранение в failed_events и удаление

## Условие

**[Дедлоки при DLX]**: Разберись с коварным багом RabbitMQ: сообщение летит в DLX, но DLX очередь тоже переполнена или брокер не может ее записать на диск. Реализуй логику: если сообщение попало в `dlx_q`, консьюмер читает его и пишет в БД как "failed event", навсегда удаляя из брокера.

## Теория

Проблема циклического переполнения Dead Lettering (DLX Deadlock):
- Если очередь `dlx_q` переполнилась (`x-max-length`), брокер не может записать в нее новые мертвые сообщения.
- При вызове `msg.Nack(false, false)` основная очередь зависает, так как сообщение некуда сбросить!
- **Промышленное решение:**
  1. Выделенный сервис-консьюмер слушает `dlx_q`.
  2. Считывает отравленное сообщение.
  3. Сохраняет его в постоянную таблицу БД `failed_events (id, payload, reason, error_trace, created_at)`.
  4. Отправляет `Ack` брокеру, окончательно удаляя сообщение из очередей RabbitMQ.
- Очереди брокера всегда остаются чистыми и разблокированными.

## Решение по шагам

1. Создайте структуру обработчика очереди DLQ.
2. Сохраните упавшее сообщение в таблицу аудита базы данных `failed_events`.
3. Отправьте `Ack` брокеру для удаления сообщения из памяти.
4. Проверьте полную очистку очереди брокера.

## Код решения

**`dlx_deadlock_prevention_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FailedEventRecord struct {
	MessageID string
	Body      string
	Reason    string
}

type DLXDrainWorker struct {
	databaseTable []*FailedEventRecord
	dlqCleared    bool
}

func (w *DLXDrainWorker) HandleDLQMessage(msgID, body, reason string) {
	// 1. Записываем в персистентную базу данных
	w.databaseTable = append(w.databaseTable, &FailedEventRecord{
		MessageID: msgID,
		Body:      body,
		Reason:    reason,
	})

	// 2. Делаем Ack брокеру -> сообщение навсегда удалено из RabbitMQ!
	w.dlqCleared = true
}

func TestDLXDeadlockPrevention(t *testing.T) {
	worker := &DLXDrainWorker{}

	badMsgID := "msg-corrupted-991"
	badBody := `{"broken_json": true`
	reason := "JSON_SYNTAX_ERROR"

	worker.HandleDLQMessage(badMsgID, badBody, reason)

	if len(worker.databaseTable) != 1 || !worker.dlqCleared {
		t.Fatal("Сообщение должно быть сохранено в БД и удалено из брокера")
	}

	fmt.Println("Защита от дедлока Dead Letter Queue успешно подтверждена:")
	fmt.Printf("  • Сбойное сообщение надежно сохранено в БД: ID=%s\n", worker.databaseTable[0].MessageID)
	fmt.Printf("  • Очередь dlx_q очищена брокером через Ack (dlqCleared=%v)!\n", worker.dlqCleared)
}
```

ℹ️ Разгрузка очереди DLQ со сбросом сообщений в БД для предотвращения дедлока брокера

## Под капотом

После того как консьюмер подтвердил сообщение из `dlx_q`, RabbitMQ освобождает дисковый слот и память, исключая любые циклические дедлоки и переполнение брокера.

## Подводные камни

Оставлять очередь DLQ без консьюмеров: через несколько месяцев накопленный миллион упавших сообщений забьет диск брокера и парализует всю компанию.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если и база данных failed_events временно недоступна при разгрузке DLQ?»
**Ответ:** При падении базы данных консьюмер DLQ делает `Nack(requeue=true)` и засыпает на 30 секунд по Circuit Breaker. Сообщения остаются ждать в `dlx_q`, пока инженер не восстановит БД, но не теряются.
