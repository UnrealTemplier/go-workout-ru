# Мультитенантная очередь сообщений (Multi-Tenant MQ): изоляция субъектов и лимиты квот

## Условие

Реализуй **Multi-tenant Message Queue** (NATS):
- Account per tenant, JWT-based auth
- Subject isolation: `tenant-a.orders.>`, `tenant-b.orders.>`
- Shared stream `ORDERS` с subject mapping: `orders.>` captures all, `orders.{tenant}.>` per tenant
- Resource quotas: max messages/sec, max storage per tenant

## Теория

Изоляция арендаторов в Multi-Tenant архитектуре:
- Предотвращение проблемы шумного соседа (Noisy Neighbor Problem):
  - Каждый клиент (Tenant A, Tenant B) изолирован на уровне пространств имен.
  - Топики: `tenant-a.orders.*` и `tenant-b.orders.*`.
  - Квоты ресурсов: тенант не может слать более 500 сообщений в секунду и занимать более 10 ГБ диска.
  - Утечка данных исключена: токен авторизации Tenant A не имеет прав чтения очередей Tenant B.

## Решение по шагам

1. Создайте модель изоляции пространства имен по `tenant_id`.
2. Реализуйте проверку прав доступа к топикам арендатора.
3. Смоделируйте квоту скорости публикаций на тенанта.
4. Проверьте блокировку попыток межтенантного доступа.

## Код решения

**`multitenant_isolation_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"strings"
	"testing"
)

type TenantSecurityContext struct {
	TenantID   string
	RateLimit  int
	msgCount   int
}

func (ctx *TenantSecurityContext) AuthorizeSubject(subject string) error {
	expectedPrefix := ctx.TenantID + "."
	if !strings.HasPrefix(subject, expectedPrefix) {
		return fmt.Errorf("доступ запрещен: тенант %s не может публиковать в %s", ctx.TenantID, subject)
	}
	if ctx.msgCount >= ctx.RateLimit {
		return errors.New("квота превышена: rate limit exceeded")
	}
	ctx.msgCount++
	return nil
}

func TestMultiTenantIsolation(t *testing.T) {
	tenantA := &TenantSecurityContext{TenantID: "tenant-a", RateLimit: 2}

	// 1. Валидный топик
	err1 := tenantA.AuthorizeSubject("tenant-a.orders.created")
	if err1 != nil {
		t.Fatalf("Ошибка валидного топика: %v", err1)
	}

	// 2. Попытка взлома/доступа к чужому тенанту B
	err2 := tenantA.AuthorizeSubject("tenant-b.orders.created")
	if err2 == nil {
		t.Fatal("Должна быть ошибка нарушения изоляции тенантов")
	}

	fmt.Println("Multi-Tenant Message Queue изоляция успешно подтверждена:")
	fmt.Printf("  • Свой субъект: разрешено\n")
	fmt.Printf("  • Чужой субъект: заблокировано security политикой (%v)\n", err2)
}
```

## Под капотом

В RabbitMQ мультитенантность строится на независимых виртуальных хостах (vhosts) с отдельными лимитами соединений и очередей (`rabbitmqctl set_vhost_limits`). В NATS для этого используются NATS Accounts с криптографическими JWT токенами.

## Подводные камни

Использовать единую общую очередь для всех тенантов с фильтрацией внутри кода воркера: один тенант с багом в генераторе сообщений забьет очередь и парализует всех остальных клиентов платформы.

## На собеседовании

**Вопрос с собеседования:** «Как в RabbitMQ изолировать ресурсы между тенантами без создания отдельных кластеров?»
**Ответ:** Создать отдельные виртуальные хосты `vhost` для каждого тенанта. Назначить каждому тенанту изолированного AMQP пользователя с регулярными выражениями прав (permissions) только на его собственный `vhost`. Настроить квоту соединений и очередей на `vhost` через RabbitMQ Limits API.
