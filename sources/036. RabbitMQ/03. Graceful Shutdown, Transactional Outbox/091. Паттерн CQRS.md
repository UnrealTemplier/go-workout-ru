# Паттерн CQRS: разделение потоков команд на запись через RabbitMQ и Read Model

## Условие

**CQRS (Command Query Responsibility Segregation)**: Используйте queue для команд (write operations) и отдельную read model (например, Elasticsearch) для запросов.

## Теория

Принцип CQRS (Command Query Responsibility Segregation):
- Разделение модели записи (Write Model) и модели чтения (Read Model):
  - **Команды (Write):** клиент отправляет команду `CreateOrderCommand` \(\to\) попадает в очередь RabbitMQ \(\to\) воркер валидирует и сохраняет в реляционную БД (PostgreSQL).
  - **События синхронизации:** после сохранения воркер публикует `OrderUpdatedEvent`.
  - **Проекция на чтение (Read Model):** специальный проектор слушает события и обновляет денормализованный индекс Elasticsearch/Redis.
  - **Запросы (Read):** HTTP GET запросы пользователей читают данные напрямую из сверхбыстрого Read Model без джойнов в PostgreSQL.

## Решение по шагам

1. Создайте структуры Command (запись) и ReadProjection (чтение).
2. Реализуйте асинхронную обработку команды через очередь.
3. Обновите проекцию чтения на основе события.
4. Проверьте мгновенный ответ на чтение из Read Model.

## Код решения

**`cqrs_queue_projection_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type UserReadProjection struct {
	ID    int
	Name  string
	Email string
}

type CQRSSystem struct {
	mu           sync.RWMutex
	commandQueue []string
	readModel    map[int]*UserReadProjection
}

func (s *CQRSSystem) SendCommand(cmd string) {
	s.commandQueue = append(s.commandQueue, cmd)
}

func (s *CQRSSystem) ProcessCommandsAndProject() {
	for _, cmd := range s.commandQueue {
		// Имитация обновления Read Model (например, Elasticsearch)
		if cmd == "UpdateEmail(id=42, email=alex@yandex.ru)" {
			s.mu.Lock()
			s.readModel[42] = &UserReadProjection{ID: 42, Name: "Алексей", Email: "alex@yandex.ru"}
			s.mu.Unlock()
		}
	}
	s.commandQueue = nil
}

func (s *CQRSSystem) QueryUser(id int) (*UserReadProjection, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	u, ok := s.readModel[id]
	return u, ok
}

func TestCQRSQueueAndReadModel(t *testing.T) {
	sys := &CQRSSystem{readModel: make(map[int]*UserReadProjection)}

	// 1. Отправка команды в очередь записи
	sys.SendCommand("UpdateEmail(id=42, email=alex@yandex.ru)")

	// 2. Воркер обрабатывает очередь и обновляет поисковую модель
	sys.ProcessCommandsAndProject()

	// 3. Быстрый запрос на чтение из денормализованной Read Model
	user, found := sys.QueryUser(42)
	if !found || user.Email != "alex@yandex.ru" {
		t.Fatalf("Пользователь не найден в Read Model: %+v", user)
	}

	fmt.Println("Паттерн CQRS успешно протестирован:")
	fmt.Printf("  • Команда записи обработана через очередь\n")
	fmt.Printf("  • Запрос на чтение мгновенно обслужен из Read Model: Email=%s\n", user.Email)
}
```

ℹ️ Разделение операций записи через очередь и прямого чтения из денормализованной Read Model

**`Терминал`**

```bash

# Паттерн CQRS успешно протестирован:

#   • Запрос на чтение мгновенно обслужен из Read Model: Email=alex@yandex.ru

# PASS
```

## Под капотом

В архитектуре CQRS модель чтения обладает свойством Eventual Consistency: в течение нескольких миллисекунд после отправки команды Read Model может возвращать старые данные, пока воркер не применит событие проекции.

## Подводные камни

Делать синхронный запрос к Read Model сразу же в теле того же HTTP запроса, который отправил команду: из-за асинхронности очереди Read Model еще не успеет обновиться.

## На собеседовании

**Вопрос с собеседования:** «Как решить проблему Eventual Consistency в UI, если пользователь ожидает увидеть результат своей команды сразу?»
**Ответ:** Использовать паттерн Optimistic UI Updates: фронтенд сразу локально отображает новое состояние на экране пользователя, не дожидаясь завершения фонового воркера проекции, либо возвращает `202 Accepted` со ссылкой на статус выполнения задачи.
