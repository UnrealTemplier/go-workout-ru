# Многоуровневый повтор с задержкой: каскад очередей delay.1s, delay.2s, delay.4s, delay.8s

## Условие

**Retry с exponential backoff**: При ошибке обработки отправляйте сообщение в delay queue с увеличивающейся задержкой (1s, 2s, 4s, 8s...).

## Теория

Каскадный паттерн отложенных ретраев (Retry Delay Queues):
- Создается цепочка очередей ожидания:
  - `retry.1s` (TTL = 1000 мс) \(\to\) DLX в основную очередь.
  - `retry.2s` (TTL = 2000 мс).
  - `retry.4s` (TTL = 4000 мс).
  - `retry.8s` (TTL = 8000 мс).
- Маршрутизация:
  - При первой ошибке консьюмер публикует сообщение в `retry.1s`.
  - При второй ошибке — в `retry.2s` и так далее.
  - При превышении 4 попыток — сообщение уходит в финальный `events.dlq`.
- Исключает Head-of-Line blocking и дает внешним сервисам время восстановиться.

## Решение по шагам

1. Создайте калькулятор целевой очереди ретрая по номеру попытки.
2. Проверьте выбор очереди `retry.1s` для попытки 0.
3. Проверьте выбор очереди `retry.8s` для попытки 3.
4. Проверьте отправку в `events.dlq` при исчерпании лимита.

## Код решения

**`retry_delay_cascade_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

func ResolveRetryQueue(attempt int) string {
	switch attempt {
	case 0:
		return "retry.1s"
	case 1:
		return "retry.2s"
	case 2:
		return "retry.4s"
	case 3:
		return "retry.8s"
	default:
		return "events.dlq" // Финальный сброс в DLQ
	}
}

func TestRetryDelayCascade(t *testing.T) {
	q0 := ResolveRetryQueue(0)
	q1 := ResolveRetryQueue(1)
	q2 := ResolveRetryQueue(2)
	q3 := ResolveRetryQueue(3)
	qFinal := ResolveRetryQueue(4)

	if q0 != "retry.1s" || q3 != "retry.8s" || qFinal != "events.dlq" {
		t.Fatalf("Некорректная маршрутизация ретраев: %s, %s, %s", q0, q3, qFinal)
	}

	fmt.Println("Каскад очередей повторной обработки успешно проверен:")
	fmt.Printf("  • Попытка 1: -> %s (задержка 1 секунда)\n", q0)
	fmt.Printf("  • Попытка 2: -> %s (задержка 2 секунды)\n", q1)
	fmt.Printf("  • Попытка 3: -> %s (задержка 4 секунды)\n", q2)
	fmt.Printf("  • Попытка 4: -> %s (задержка 8 секунд)\n", q3)
	fmt.Printf("  • Превышение: -> %s (Dead Lettering)\n", qFinal)
}
```

ℹ️ Каскадная маршрутизация сообщений по очередям задержек экспоненциального повтора

## Под капотом

Каждая очередь `retry.Xs` не имеет консьюмеров. По истечении TTL сообщения автоматически сбрасываются брокером через свой `x-dead-letter-exchange` обратно в основную очередь обработки.

## Подводные камни

Забыть увеличивать счетчик `retry_count` в заголовке сообщения при каждой пересылке: без инкремента сообщение войдет в вечный цикл ретраев.

## На собеседовании

**Вопрос с собеседования:** «Почему каскад очередей delay.Xs надежнее локального sleep в горутине консьюмера?»
**Ответ:** Если во время `time.Sleep(8 * time.Second)` под воркера упадет или перезагрузится по деплою, сообщение не потеряется: оно физически лежит в очереди на надежном брокере и вернется на обработку точно в назначенный срок.
