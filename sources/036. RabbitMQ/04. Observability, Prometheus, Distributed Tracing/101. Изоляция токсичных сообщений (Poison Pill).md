# Изоляция токсичных сообщений (Poison Pill): перехват паники через recover и уход в DLQ

## Условие

**Poison pill handling**: Если сообщение вызывает crash consumer, отправляйте его в dead letter queue после N попыток, чтобы не блокировать всю queue.

## Теория

Защита от токсичных сообщений (Poison Pill Protection):
- Сообщение «отравленная пилюля» (Poison Pill):
  - Вызывает панику в рантайме Go (например, разыменование nil указателя при парсинге).
  - Без перехвата: процесс падает, перезапускается, берет то же сообщение и снова падает (CrashLoopBackOff).
- **Паттерн Safe Handler:**
  1. Блок `defer func() { if r := recover(); r != nil { ... } }`.
  2. Перехват паники и стектрейса.
  3. Немедленный вызов `msg.Nack(false, false)` \(\to\) уход в DLQ.
  4. Основная очередь мгновенно разблокирована, следующие задачи выполняются в штатном режиме.

## Решение по шагам

1. Создайте безопасный обработчик с блоком `recover()`.
2. Смоделируйте поступление отравленного сообщения (паника в коде).
3. Перехватите панику без падения процесса.
4. Убедитесь в фиксации отправки в DLQ.

## Код решения

**`poison_pill_recovery_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

func SafeMessageExecution(payload string, sendToDLQ func(reason string)) {
	defer func() {
		if r := recover(); r != nil {
			errReason := fmt.Sprintf("PANIC_RECOVERED: %v", r)
			sendToDLQ(errReason)
		}
	}()

	// Имитация отравленного сообщения, вызывающего панику в бизнес-логике
	if payload == "poison_pill" {
		var ptr *int
		_ = *ptr // nil pointer dereference!
	}
}

func TestPoisonPillHandling(t *testing.T) {
	dlqSent := false
	dlqReason := ""

	sendToDLQ := func(reason string) {
		dlqSent = true
		dlqReason = reason
	}

	// Обрабатываем токсичное сообщение
	SafeMessageExecution("poison_pill", sendToDLQ)

	if !dlqSent || dlqReason == "" {
		t.Fatal("Токсичное сообщение должно быть перехвачено и отправлено в DLQ")
	}

	fmt.Println("Защита от Poison Pill успешно сработала:")
	fmt.Printf("  • Паника перехвачена рантаймом Go\n")
	fmt.Printf("  • Сообщение изолировано в DLQ: %s\n", dlqReason)
	fmt.Println("  • Консьюмер продолжил работу без краша процесса!")
}
```

## Под капотом

Вызов `recover()` восстанавливает нормальный ход выполнения горутины, позволяя коду отправить брокеру `basic.reject(requeue=false)` и освободить очередь.

## Подводные камни

Оставлять в теле `recover()` пустой блок: паника проглотится, `Ack/Nack` не будет вызван, и сообщение зависнет в статусе `Unacked` до перезагрузки сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как отличить временную ошибку базы данных от Poison Pill?»
**Ответ:** По типу ошибки и ее детерминированности: синтаксическая ошибка JSON или `nil pointer` происходят на 100% попыток при одинаковых входных данных (перманентная ошибка / Poison Pill). Сетевой таймаут или `deadlock detected` в БД носят случайный характер и успешно проходят на 2-й или 3-й попытке повтора.
