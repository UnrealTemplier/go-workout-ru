# Резервный контур при отказе брокера (Queue Fallback): аварийное сохранение в локальную БД

## Условие

**Circuit Breaker для queue**: Если queue недоступна, временно переключитесь на fallback (например, сохраняйте в локальную БД).

## Теория

Паттерн аварийного переключения на локальное хранилище (Queue Fallback):
- Если весь кластер RabbitMQ недоступен (сетевая изоляция, авария нод):
  - Продюсер не должен отвечать пользователям ошибкой 500!
  - Срабатывает аварийный Fallback:
    - Сообщение сохраняется в аварийную локальную таблицу SQLite/PostgreSQL `fallback_messages`.
    - Пользователю возвращается успешный статус `202 Accepted`.
  - Когда брокер возвращается в строй:
    - Фоновый демон-репликатор переносит накопленные данные из локальной БД в RabbitMQ.

## Решение по шагам

1. Создайте отказоустойчивый продюсер с Fallback логикой.
2. Смоделируйте недоступность брокера сообщений.
3. Проверьте автоматическое сохранение в аварийное хранилище.
4. Протестируйте восстановление штатной публикации.

## Код решения

**`queue_fallback_storage_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FallbackMessageProducer struct {
	brokerOnline   bool
	brokerMessages []string
	localDBStorage []string
}

func (p *FallbackMessageProducer) Publish(msg string) string {
	if p.brokerOnline {
		p.brokerMessages = append(p.brokerMessages, msg)
		return "PUBLISHED_TO_BROKER"
	}
	// Аварийный Fallback в локальную БД!
	p.localDBStorage = append(p.localDBStorage, msg)
	return "SAVED_TO_FALLBACK_DB"
}

func TestQueueFallbackStorage(t *testing.T) {
	prod := &FallbackMessageProducer{brokerOnline: false}

	status := prod.Publish("Платеж во время сбоя сети #9912")

	if status != "SAVED_TO_FALLBACK_DB" || len(prod.localDBStorage) != 1 {
		t.Fatalf("Сообщение должно было сохраниться в fallback хранилище: %s", status)
	}

	fmt.Println("Резервный контур (Queue Fallback) успешно защитил данные от потери:")
	fmt.Printf("  • Статус публикации: %s\n", status)
	fmt.Printf("  • Сообщение безопасно сохранено в локальной БД: «%s»\n", prod.localDBStorage[0])
}
```

## Под капотом

Такой подход реализует принцип Graceful Degradation: бизнес продолжает принимать заказы клиентов даже во время полной недоступности сетевой шины сообщений.

## Подводные камни

Хранить fallback данные в неперсистентной оперативной памяти: при рестарте контейнера все накопленные платежи будут безвозвратно утеряны. Хранилище обязано быть дисковым (SQLite, PostgreSQL, RocksDB).

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить переполнение локального диска при длительной аварии брокера?»
**Ответ:** Настроить локальную дисковую квоту и лимит сообщений. При приближении к 90% заполнения локального диска сервис обязан перейти в режим жесткого Fast Fail (`503 Service Unavailable`), уведомить дежурных инженеров и включить защиту от каскадного падения сервера.
