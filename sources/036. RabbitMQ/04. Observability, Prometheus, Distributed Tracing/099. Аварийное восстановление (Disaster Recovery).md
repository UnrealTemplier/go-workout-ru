# Аварийное восстановление (Disaster Recovery): RPO, RTO и стратегии репликации очередей

## Условие

Реализуй **Disaster Recovery для MQ**:
- Kafka: MirrorMaker 2, replication factor 3, min.insync.replicas 2
- NATS: Stream replication (clustered JetStream), snapshot + restore
- RabbitMQ: federation, shovel, mirrored queues (quorum queues)
- RPO: 0 (synchronous replication) vs 5 min (asynchronous)
- RTO: automatic failover vs manual switchover

## Теория

Метрики Disaster Recovery (RPO и RTO) для Message Brokers:
- **RPO (Recovery Point Objective):** допустимый объем потерянных данных во времени:
  - \(\text{RPO} = 0\): синхронная репликация (Quorum Queues с кворумом нод, Kafka `acks=all`). Ни одно подтвержденное сообщение не теряется!
  - \(\text{RPO} \le 5 \text{ мин}\): асинхронная репликация между удаленными дата-центрами через Shovel/MirrorMaker.
- **RTO (Recovery Time Objective):** время восстановления сервиса до рабочего состояния:
  - \(\text{RTO} \approx 0\) (Automatic Failover): автоматический выбор нового лидера за 1–3 секунды.
  - \(\text{RTO} \approx 15 \text{ мин}\) (Manual Switchover): ручное переключение DNS записей инженером на резервный ЦОД.

## Решение по шагам

1. Создайте структуру параметров плана Disaster Recovery.
2. Проверьте соответствие настроек строгому требованию RPO = 0.
3. Продемонстрируйте автоматическое переключение при сбое ноды (RTO).
4. Протестируйте устойчивость данных.

## Код решения

**`disaster_recovery_metrics_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DRPlan struct {
	BrokerType   string
	SyncReplicas int
	TargetRPO    time.Duration
	TargetRTO    time.Duration
}

func (p DRPlan) IsStrictLossless() bool {
	return p.TargetRPO == 0 && p.SyncReplicas >= 2
}

func TestDisasterRecoveryMQ(t *testing.T) {
	plan := DRPlan{
		BrokerType:   "RabbitMQ Quorum Queues",
		SyncReplicas: 3,
		TargetRPO:    0,                    // RPO = 0: нулевая потеря сообщений!
		TargetRTO:    3 * time.Second,      // RTO = 3s: автовыбор лидера по Raft
	}

	if !plan.IsStrictLossless() {
		t.Fatal("План должен гарантировать отсутствие потерь (Lossless)")
	}

	fmt.Println("Disaster Recovery конфигурация для брокера успешно подтверждена:")
	fmt.Printf("  • Архитектура: %s\n", plan.BrokerType)
	fmt.Printf("  • RPO (Потери данных): %v (Zero Data Loss)\n", plan.TargetRPO)
	fmt.Printf("  • RTO (Время простоя): %v (Автоматический failover)\n", plan.TargetRTO)
}
```

## Под капотом

Синхронная репликация с \(\text{RPO} = 0\) требует обязательного кворума записей на диск на нескольких физических серверах до отправки Publisher Confirm продюсеру.

## Подводные камни

Утверждать, что асинхронный Shovel обеспечивает \(\text{RPO} = 0\): при внезапном обесточивании дата-центра все сообщения, находящиеся в сетевом буфере Shovel, будут потеряны.

## На собеседовании

**Вопрос с собеседования:** «Каковы компромиссы между RPO=0 и задержкой публикации (Latency)?»
**Ответ:** Достижение \(\text{RPO} = 0\) требует синхронного ожидания дискового ввода-вывода (`fsync`) на большинстве нод кластера (Raft кворум). Это увеличивает latency с микросекунд до нескольких миллисекунд (2–5 мс) и снижает максимальный Throughput. Для некритичных данных (логи) выбирают асинхронный сброс, а для финансов — строгий \(\text{RPO} = 0\).
