# Бесшовная миграция с RabbitMQ на Kafka: стратегия двойной записи (Dual-Write) и Cutover

## Условие

Реализуй **Migration from RabbitMQ to Kafka**:
- Dual-write: пиши в обе системы (RabbitMQ для legacy, Kafka для new)
- Change data capture: RabbitMQ → Kafka Connect source
- Gradual cutover: consumers мигрируют с RabbitMQ на Kafka
- Verification: сравни сообщения в обеих системах
- Rollback plan: если Kafka fail → вернуться на RabbitMQ

## Теория

Четырехэтапная стратегия Zero-Downtime миграции между брокерами:
1. **Dual-Write (Двойная запись):** продюсер пишет одновременно и в RabbitMQ, и в Apache Kafka.
2. **Shadow Consumption & Verification:** новые консьюмеры читают Kafka в теневом режиме и сверяют результаты с RabbitMQ.
3. **Gradual Cutover (Плавное переключение):** продакшен-трафик консьюмеров по процентам (10%, 50%, 100%) переключается на чтение из Kafka.
4. **Decommission:** отключение записи в старый RabbitMQ после стабильной работы Kafka в течение недели.

## Решение по шагам

1. Создайте модуль Dual-Write продюсера.
2. Смоделируйте синхронную запись в оба брокера.
3. Проверьте сохранность данных в обеих системах.
4. Протестируйте сценарий безопасного отката (Rollback).

## Код решения

**`dual_write_migration_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DualWriteMigrator struct {
	rabbitStorage []string
	kafkaStorage  []string
	activeTarget  string // "RABBITMQ" или "KAFKA"
}

func (m *DualWriteMigrator) PublishDual(msg string) {
	// Этап 1: Dual-Write в обе системы
	m.rabbitStorage = append(m.rabbitStorage, msg)
	m.kafkaStorage = append(m.kafkaStorage, msg)
}

func (m *DualWriteMigrator) ConsumeActive() string {
	if m.activeTarget == "KAFKA" {
		msg := m.kafkaStorage[0]
		m.kafkaStorage = m.kafkaStorage[1:]
		return msg
	}
	msg := m.rabbitStorage[0]
	m.rabbitStorage = m.rabbitStorage[1:]
	return msg
}

func TestDualWriteMigration(t *testing.T) {
	migrator := &DualWriteMigrator{activeTarget: "RABBITMQ"}

	payload := "Перевод средств #1005"
	migrator.PublishDual(payload)

	// Проверяем, что сообщение продублировано в обе системы
	if len(migrator.rabbitStorage) != 1 || len(migrator.kafkaStorage) != 1 {
		t.Fatal("Dual-Write должен записать данные в обе системы")
	}

	// Этап 2: Переключаем консьюмеров на Kafka (Cutover)
	migrator.activeTarget = "KAFKA"
	consumed := migrator.ConsumeActive()

	if consumed != payload {
		t.Fatalf("Некорректное сообщение из Kafka: %s", consumed)
	}

	fmt.Println("Миграция RabbitMQ -> Kafka через Dual-Write успешно проведена:")
	fmt.Printf("  • Данные синхронизированы в обоих брокерах\n")
	fmt.Printf("  • Консьюмеры переключены на Kafka: получено «%s»\n", consumed)
	fmt.Println("  • Zero Downtime обеспечен!")
}
```

ℹ️ Стратегия плавной миграции брокеров очередей с использованием паттерна Dual-Write

## Под капотом

Двойная запись позволяет в любой момент повернуть флаг `activeTarget` назад (Rollback), если новый кластер Kafka не выдержит пиковой нагрузки в Черную Пятницу.

## Подводные камни

Удалять старый брокер сразу после 100% переключения: необходимо выждать гарантийный период (Cool-down Period) не менее 7–14 дней.

## На собеседовании

**Вопрос с собеседования:** «Каковы главные подводные камни паттерна Dual-Write?»
**Ответ:** Проблема частичного сбоя (Partial Failure): если запись в RabbitMQ прошла успешно, а запись в Kafka упала по таймауту, возникнет рассинхронизация брокеров. Решение: использовать Transactional Outbox в единой БД, откуда два независимых воркера асинхронно доставляют события в RabbitMQ и Kafka с индивидуальными ретраями.
