# Сервис биллинга (Billing Consumer): обработка заказов, OrderConfirmed и OrderRejected

## Условие

**Billing Consumer**: Слушает `orders`. При получении списывает деньги. Если баланс < 0 — пушит событие `OrderRejected` в другой топик. Если успех — `OrderConfirmed`.

## Теория

Ветвление бизнес-логики в консьюмере биллинга:
- Консьюмер слушает очередь `orders`:
  - Получает запрос на списание суммы заказа.
  - Проверяет доступный остаток баланса пользователя в базе данных.
  - Если средств достаточно:
    - Списывает деньги.
    - Публикует `OrderConfirmed` в топик подтвержденных заказов.
  - Если средств недостаточно (баланс < 0):
    - Публикует `OrderRejected` с причиной `"INSUFFICIENT_FUNDS"`.
- Обеспечивает автономность платежного шлюза.

## Решение по шагам

1. Создайте модель пользователя с балансом.
2. Смоделируйте успешное списание и выпуск `OrderConfirmed`.
3. Смоделируйте нехватку средств и выпуск `OrderRejected`.
4. Проверьте корректность публикации событий в соответствующие топики.

## Код решения

**`billing_consumer_branching_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BillingAccount struct {
	Balance float64
}

type BillingOutcomeEvent struct {
	Topic   string
	OrderID string
	Reason  string
}

func ProcessBilling(acc *BillingAccount, orderID string, amount float64) BillingOutcomeEvent {
	if acc.Balance < amount {
		return BillingOutcomeEvent{
			Topic:   "orders.rejected",
			OrderID: orderID,
			Reason:  "INSUFFICIENT_FUNDS",
		}
	}
	acc.Balance -= amount
	return BillingOutcomeEvent{
		Topic:   "orders.confirmed",
		OrderID: orderID,
		Reason:  "PAYMENT_SUCCESS",
	}
}

func TestBillingConsumerBranching(t *testing.T) {
	acc := &BillingAccount{Balance: 1000.0}

	// 1. Успешный платеж
	ev1 := ProcessBilling(acc, "ORD-OK-1", 400.0)
	if ev1.Topic != "orders.confirmed" || acc.Balance != 600.0 {
		t.Fatalf("Ожидалось подтверждение: %+v, баланс=%f", ev1, acc.Balance)
	}

	// 2. Нехватка средств
	ev2 := ProcessBilling(acc, "ORD-FAIL-2", 800.0)
	if ev2.Topic != "orders.rejected" || ev2.Reason != "INSUFFICIENT_FUNDS" {
		t.Fatalf("Ожидался отказ: %+v", ev2)
	}

	fmt.Println("Billing Consumer успешно выполнил ветвление бизнес-событий:")
	fmt.Printf("  • Успешная оплата: -> Топик %s (Остаток: %.2f руб)\n", ev1.Topic, acc.Balance)
	fmt.Printf("  • Отказ по балансу: -> Топик %s (Причина: %s)\n", ev2.Topic, ev2.Reason)
}
```

## Под капотом

Списание средств и сохранение исходящего события в outbox выполняются в единой транзакции БД с уровнем изоляции `SERIALIZABLE` или `READ COMMITTED` с пессимистической блокировкой счета `FOR UPDATE`.

## Подводные камни

Забывать делать `msg.Ack(false)` при отклонении заказа: отклоненный заказ — это штатный бизнес-исход, брокер должен получить подтверждение об успешной обработке задачи.

## На собеседовании

**Вопрос с собеседования:** «Как защититься от состояния гонки (Race Condition), если клиент отправил два платежа одновременно с разных устройств?»
**Ответ:** Использовать блокировку строки счета в базе данных: `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE`. Второй запрос будет ждать завершения транзакции первого, что исключит уход баланса в минус.
