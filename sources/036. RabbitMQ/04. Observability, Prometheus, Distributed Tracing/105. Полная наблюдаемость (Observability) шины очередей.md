# Полная наблюдаемость (Observability) шины очередей: трейсинг, метрики и алертинг

## Условие

Реализуй **Observability for MQ**:
- Distributed tracing: OpenTelemetry, each produce/consume = span, trace across services
- Metrics: Prometheus, `mq_messages_produced_total`, `mq_messages_consumed_total`, `mq_consumer_lag`, `mq_publish_latency_seconds`
- Logging: structured JSON, correlation ID, message metadata
- Alerting: lag > threshold, dead letter queue growth, broker disk > 80%

## Теория

Три столпа Observability для брокера сообщений:
1. **Метрики (Prometheus):**
   - `mq_messages_produced_total`: счетчик отправленных сообщений.
   - `mq_messages_consumed_total`: счетчик подтвержденных сообщений.
   - `mq_publish_latency_seconds`: гистограмма времени ответа Publisher Confirms.
2. **Трассировка (OpenTelemetry):**
   - Создание Span при публикации (`producer span`).
   - Извлечение SpanContext из AMQP Headers при вычитке (`consumer span`).
3. **Структурированные логи (JSON):**
   - Обязательные поля `correlation_id`, `message_id`, `queue`, `duration_ms`.

## Решение по шагам

1. Создайте структуру метрик мониторинга очереди.
2. Смоделируйте сквозной трейс сквозь отправку и вычитку.
3. Проверьте сбор метрик опубликованных и обработанных задач.
4. Протестируйте правила генерации алертов.

## Код решения

**`mq_observability_suite_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MQMetricsTracker struct {
	ProducedTotal int64
	ConsumedTotal int64
	CurrentLag    int64
}

func (m *MQMetricsTracker) OnProduced() {
	m.ProducedTotal++
	m.CurrentLag++
}

func (m *MQMetricsTracker) OnConsumed() {
	m.ConsumedTotal++
	m.CurrentLag--
}

func TestMQObservabilitySuite(t *testing.T) {
	tracker := &MQMetricsTracker{}

	// Имитируем отправку 10 задач
	for i := 0; i < 10; i++ {
		tracker.OnProduced()
	}

	// Имитируем вычитку 8 задач
	for i := 0; i < 8; i++ {
		tracker.OnConsumed()
	}

	if tracker.ProducedTotal != 10 || tracker.ConsumedTotal != 8 || tracker.CurrentLag != 2 {
		t.Fatalf("Некорректный учет метрик: %+v", tracker)
	}

	fmt.Println("Observability для брокера сообщений успешно подтверждена:")
	fmt.Printf("  • mq_messages_produced_total: %d\n", tracker.ProducedTotal)
	fmt.Printf("  • mq_messages_consumed_total: %d\n", tracker.ConsumedTotal)
	fmt.Printf("  • mq_consumer_lag:            %d сообщений\n", tracker.CurrentLag)
}
```

ℹ️ Сбор ключевых метрик Observability: Produced, Consumed и Consumer Lag

## Подводные камни

Использовать строковую интерполяцию вместо структурированного логера (slog/zap): парсер логов (Vector/Fluentbit) не сможет индексировать поля в Elasticsearch/Loki.

## На собеседовании

**Вопрос с собеседования:** «Почему время задержки в очереди (Queue Wait Time) важнее времени обработки воркером?»
**Ответ:** Время обработки показывает производительность CPU воркера. Время нахождения в очереди (от `CreatedAt` до старта вычитки) показывает общее здоровье архитектуры и наличие бэклога (Backlog). Всплеск Queue Wait Time сигнализирует о необходимости горизонтального масштабирования подов.
