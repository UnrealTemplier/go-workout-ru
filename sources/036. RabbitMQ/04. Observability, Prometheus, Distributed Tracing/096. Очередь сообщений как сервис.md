# Очередь сообщений как сервис (Message Queue as a Service): HTTP API, WebSocket и аудит

## Условие

Реализуй **Message Queue as a Service** (внутренний):
- HTTP API: `POST /queues/{name}/messages` — publish
- `GET /queues/{name}/messages` — consume (long-polling)
- WebSocket: real-time subscribe
- Backend: NATS JetStream (persistence), Redis (caching), PostgreSQL (audit)
- Multi-protocol: HTTP, gRPC, WebSocket, AMQP

## Теория

Архитектура универсального брокер-шлюза (Queue as a Service Gateway):
- Позволяет любым клиентам (браузеры, мобильные приложения, скрипты на Python/PHP) работать с очередями без AMQP-драйверов:
  - `POST /queues/orders/messages`: публикация JSON задачи через REST API.
  - `GET /queues/orders/messages`: чтение через Long-Polling.
  - `WebSocket /ws/subscribe`: подписка в реальном времени.
- Внутренний бэкенд транслирует запросы в RabbitMQ или NATS JetStream, сохраняя журнал аудита в PostgreSQL.

## Решение по шагам

1. Создайте маршруты REST API шлюза очередей.
2. Смоделируйте публикацию сообщения через HTTP POST.
3. Смоделируйте вычитку через Long-Polling GET.
4. Проверьте аудит и сквозную доставку.

## Код решения

**`queue_as_a_service_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MQServiceGateway struct {
	queues map[string][]string
	audit  []string
}

func (gw *MQServiceGateway) PublishHTTP(queueName, body string) {
	gw.queues[queueName] = append(gw.queues[queueName], body)
	gw.audit = append(gw.audit, fmt.Sprintf("AUDIT: POST /queues/%s/messages", queueName))
}

func (gw *MQServiceGateway) ConsumeHTTP(queueName string) (string, bool) {
	q := gw.queues[queueName]
	if len(q) == 0 {
		return "", false
	}
	msg := q[0]
	gw.queues[queueName] = q[1:]
	gw.audit = append(gw.audit, fmt.Sprintf("AUDIT: GET /queues/%s/messages", queueName))
	return msg, true
}

func TestQueueAsAService(t *testing.T) {
	gw := &MQServiceGateway{queues: make(map[string][]string)}

	// 1. Клиент публикует через HTTP API
	gw.PublishHTTP("tasks", `{"task": "send_welcome_email"}`)

	// 2. Воркер вычитывает через HTTP Long-Polling
	msg, ok := gw.ConsumeHTTP("tasks")
	if !ok || msg != `{"task": "send_welcome_email"}` {
		t.Fatalf("Сбой получения: %s, %v", msg, ok)
	}

	if len(gw.audit) != 2 {
		t.Fatalf("Аудит должен содержать 2 записи: %v", gw.audit)
	}

	fmt.Println("Message Queue as a Service шлюз успешно протестирован:")
	fmt.Printf("  • Сообщение получено: %s\n", msg)
	fmt.Printf("  • Журнал аудита: %v\n", gw.audit)
}
```

## Под капотом

Подобные шлюзы (аналоги AWS SQS / Azure Service Bus) инкапсулируют сложность AMQP протокола, позволяя фронтенду взаимодействовать с очередями через стандартные веб-протоколы.

## Подводные камни

Использовать HTTP Long-Polling для сверхвысокочастотных очередей: создание сотен TCP/TLS соединений на каждый запрос создает заметный overhead по сравнению с постоянным AMQP каналом.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать механизм Long-Polling при чтении из очереди по HTTP?»
**Ответ:** Консьюмер отправляет запрос `GET /queues/{name}?timeout=20s`. Сервер проверяет наличие сообщений в брокере. Если очередь пуста, сервер удерживает HTTP соединение открытым через `select { case msg := <-notifyChan: ... case <-time.After(20*time.Second): return 204 No Content }`, отвечая клиенту сразу по приходу нового сообщения.
