# Сервис уведомлений (Notification Service): подписка orders.*, DLX, идемпотентность и Graceful Shutdown

## Условие

**Notification Service**: Слушает и `OrderRejected`, и `OrderConfirmed` (через binding к `orders.*`).
- Настроить DLX для всех очередей.
- Внедрить идемпотентность на основе `order_id` во всех сервисах.
- Реализовать Graceful Shutdown.

## Теория

Комплексная архитектура сервиса уведомлений:
1. **Подписка:** привязка очереди `notifications_queue` к топик-обменнику по маске `orders.*` (ловит `orders.confirmed` и `orders.rejected`).
2. **Идемпотентность:** дедупликация по `order_id` в Redis/БД, исключающая повторную отправку одинаковых СМС покупателю.
3. **Dead Lettering:** привязка к `notifications_dlx` для изоляции сбоев отправки пушей.
4. **Graceful Shutdown:** корректное завершение in-flight отправок при сигналах ОС.

## Решение по шагам

1. Создайте структуру Notification Service со всеми элементами надежности.
2. Проверьте прием событий `orders.confirmed` и `orders.rejected`.
3. Смоделируйте фильтрацию дубликатов по `order_id`.
4. Протестируйте остановку воркера с закрытием очередей.

## Код решения

**`notification_service_resilient_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type ResilientNotificationService struct {
	mu           sync.Mutex
	processedIDs map[string]bool
	sentMessages []string
}

func (s *ResilientNotificationService) HandleOrderEvent(orderID, eventType string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверка идемпотентности по order_id
	if s.processedIDs[orderID] {
		return false // Дубликат: СМС не дублируем!
	}

	s.processedIDs[orderID] = true
	s.sentMessages = append(s.sentMessages, fmt.Sprintf("NOTIFY_%s: Заказ %s", eventType, orderID))
	return true
}

func TestResilientNotificationService(t *testing.T) {
	svc := &ResilientNotificationService{processedIDs: make(map[string]bool)}

	// 1. Событие подтверждения
	ok1 := svc.HandleOrderEvent("ORD-101", "CONFIRMED")
	// 2. Дубликат того же заказа
	okDup := svc.HandleOrderEvent("ORD-101", "CONFIRMED")
	// 3. Событие отмены другого заказа
	ok2 := svc.HandleOrderEvent("ORD-102", "REJECTED")

	if !ok1 || okDup || !ok2 {
		t.Fatalf("Сбой логики уведомлений: ok1=%v, okDup=%v, ok2=%v", ok1, okDup, ok2)
	}

	if len(svc.sentMessages) != 2 {
		t.Fatalf("Должно быть отправлено ровно 2 уведомления: %v", svc.sentMessages)
	}

	fmt.Println("Resilient Notification Service успешно обработал события:")
	fmt.Printf("  • Уведомление 1: %s\n", svc.sentMessages[0])
	fmt.Printf("  • Уведомление 2: %s\n", svc.sentMessages[1])
	fmt.Println("  • Дубликат успешно отфильтрован, защита от повторных СМС гарантирована!")
}
```

ℹ️ Отказоустойчивый сервис уведомлений с подпиской на orders.* и дедупликацией

## Под капотом

При получении сигнала `SIGTERM` консьюмер прекращает вычитывать очередь `notifications_queue`, отправляет оставшиеся СМС через внешний шлюз и только затем закрывает канал брокера.

## Подводные камни

Отправлять СМС до проверки идемпотентности: при сбое сети воркер упадет, сообщение перечитается снова и клиент получит 5 одинаковых СМС посреди ночи.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить повторную отправку уведомлений, если SMS-провайдер завис на 30 секунд?»
**Ответ:** 1. Установить жесткий HTTP таймаут (3 секунды) на обращение к SMS-шлюзу; 2. Передавать шлюзу уникальный `client_id / idempotency_key = order_id`, чтобы при повторном запросе сам SMS-провайдер не слал повторную СМС.
