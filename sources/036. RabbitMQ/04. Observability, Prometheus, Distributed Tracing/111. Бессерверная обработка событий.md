# Бессерверная обработка событий (Serverless Event Processing): Lambda / Cloud Functions, идемпотентность и DLQ

## Условие

Реализуй **Serverless Event Processing**:
- AWS Lambda / Google Cloud Functions triggered by Kafka/NATS events
- Function: `func HandleEvent(ctx context.Context, event kafka.Message) error`
- Cold start optimization: keep-alive, provisioned concurrency
- Idempotency: deduplication by event ID, store processed IDs in DynamoDB/Redis
- Error handling: DLQ for failed invocations, retry with exponential backoff

## Теория

Архитектура Serverless обработки очередей:
- Триггеры событий (Event Source Mapping):
  - Облачный провайдер автоматически считывает пачки сообщений из брокера и вызывает функцию `HandleEvent(ctx, msg)`.
  - При масштабировании от 0 до 1000 инстансов:
    - **Оптимизация холодного старта:** переиспользование соединений к БД/Redis вне тела хендлера (Global Init Scope).
    - **Дедупликация:** проверка уникального `event_id` в распределенной таблице DynamoDB/Redis.
    - **Error Handling:** при сбое функции облачная платформа делает 3 попытки, после чего сбрасывает событие в Dead Letter Queue (DLQ SQS/SNS).

## Решение по шагам

1. Создайте сигнатуру бессерверного хендлера `HandleEvent`.
2. Реализуйте проверку идемпотентности события в глобальном скоупе.
3. Протестируйте успешную обработку и отсечение дубликата.
4. Смоделируйте уход в DLQ при ошибке.

## Код решения

**`serverless_event_processing_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
)

type ServerlessEvent struct {
	ID      string
	Payload string
}

type ServerlessProcessor struct {
	mu           sync.Mutex
	processedIDs map[string]bool
	dlqSink      []string
}

func (p *ServerlessProcessor) HandleEvent(ctx context.Context, ev ServerlessEvent) error {
	p.mu.Lock()
	defer p.mu.Unlock()

	// 1. Проверка идемпотентности
	if p.processedIDs[ev.ID] {
		return nil // Дубликат: завершаем без ошибки
	}

	// 2. Обработка полезной нагрузки
	if ev.Payload == "fatal_error" {
		p.dlqSink = append(p.dlqSink, ev.ID)
		return errors.New("unrecoverable execution error")
	}

	p.processedIDs[ev.ID] = true
	return nil
}

func TestServerlessEventProcessing(t *testing.T) {
	proc := &ServerlessProcessor{processedIDs: make(map[string]bool)}
	ctx := context.Background()

	evValid := ServerlessEvent{ID: "evt-001", Payload: "Заказ оформлен"}
	evBad := ServerlessEvent{ID: "evt-002", Payload: "fatal_error"}

	_ = proc.HandleEvent(ctx, evValid)
	_ = proc.HandleEvent(ctx, evValid) // дубликат
	_ = proc.HandleEvent(ctx, evBad)   // ошибка

	if len(proc.processedIDs) != 1 || len(proc.dlqSink) != 1 {
		t.Fatalf("Некорректная обработка: processed=%d, dlq=%d", len(proc.processedIDs), len(proc.dlqSink))
	}

	fmt.Println("Serverless Event Processing успешно протестирован:")
	fmt.Printf("  • Обработано валидных событий: %d (дубликат отсеян)\n", len(proc.processedIDs))
	fmt.Printf("  • Сбойное событие направлено в DLQ: %s\n", proc.dlqSink[0])
}
```

## Под капотом

В Serverless средах соединения с базами данных инициализируются вне обработчика (в функции `init()` или глобальных переменных). Это позволяет теплому контейнеру переиспользовать пул соединений между миллионами вызовов.

## Подводные камни

Открывать новое соединение к RabbitMQ внутри функции `HandleEvent`: это создаст тысячи TCP сокетов в секунду и немедленно положит брокер.

## На собеседовании

**Вопрос с собеседования:** «Как бороться с проблемой холодного старта (Cold Start) в Go Lambda функциях при обработке очередей?»
**Ответ:** 1. Использовать легковесный рантайм `provided.al2023` со скомпилированным бинарником Go; 2. Включать Provisioned Concurrency для удержания пула прогретых инстансов; 3. Минимизировать размер зависимостей и собирать бинарник с флагами `-ldflags="-s -w"`.
