# Игровая шина событий (Gaming Event Pipeline): сверхнизкая задержка движений и аналитика матча

## Условие

Реализуй **Gaming Event Pipeline** (NATS):
- Game server publishes: `player.move`, `player.shoot`, `match.end`
- Real-time: matchmaking service subscribes to `player.online`, updates Redis
- Analytics: daily active users, retention, monetization (Kafka → ClickHouse)
- Replay: spectator mode, replay match from events

## Теория

Архитектура высоконагруженного игрового бэкенда:
- Миллионы событий в секунду:
  - `player.move`: передается через ultra-low latency брокер (NATS Core) за микросекунды для синхронизации координат между игроками.
  - `match.end`: передается в Kafka для сохранения в ClickHouse (аналитика K/D ratio, расчет рейтинга ELO).
  - Стриминг событий матча позволяет реализовать режим наблюдателя (Spectator Mode) и воспроизведение реплеев киберспортивных турниров.

## Решение по шагам

1. Создайте структуру игрового события.
2. Смоделируйте маршрутизацию событий движения игрока.
3. Смоделируйте агрегацию финального события матча.
4. Проверьте задержку доставки координат.

## Код решения

**`gaming_event_pipeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type GamePlayerEvent struct {
	Subject  string
	PlayerID string
	Payload  string
}

type GamingEventBus struct {
	realtimeCoordSink []string
	analyticsSink     []string
}

func (b *GamingEventBus) RouteEvent(ev GamePlayerEvent) {
	if ev.Subject == "player.move" {
		b.realtimeCoordSink = append(b.realtimeCoordSink, ev.Payload)
	} else if ev.Subject == "match.end" {
		b.analyticsSink = append(b.analyticsSink, ev.Payload)
	}
}

func TestGamingEventPipeline(t *testing.T) {
	bus := &GamingEventBus{}

	bus.RouteEvent(GamePlayerEvent{Subject: "player.move", PlayerID: "p1", Payload: "X:124,Y:89,Z:10"})
	bus.RouteEvent(GamePlayerEvent{Subject: "match.end", PlayerID: "p1", Payload: "Winner: p1, Kills: 14"})

	if len(bus.realtimeCoordSink) != 1 || len(bus.analyticsSink) != 1 {
		t.Fatal("События должны быть разведены по разным шинам")
	}

	fmt.Println("Gaming Event Pipeline успешно обработал игровые события:")
	fmt.Printf("  • Real-time NATS (Координаты): %s\n", bus.realtimeCoordSink[0])
	fmt.Printf("  • Analytics Kafka (Статистика): %s\n", bus.analyticsSink[0])
}
```

## Под капотом

Для синхронизации координат часто используют ненадежный UDP протокол или NATS Core без подтверждений (at-most-once), поскольку потеря одной координаты игрока несущественна (следующая координата придет через 16 мс).

## Подводные камни

Использовать RabbitMQ с записью на диск для передачи каждого тика мыши или шага игрока: это вызовет лаги и сделает шутер неиграбельным.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать Spectator Mode с задержкой в 2 минуты (для защиты от стримснайпинга)?»
**Ответ:** Записывать поток игровых событий в топик брокера. Спектатор-сервис вычитывает топик с фиксированным временным лагом в 2 минуты (`consumer offset = timestamp - 120s`), воспроизводя матч для зрителей с точной двухминутной задержкой.
