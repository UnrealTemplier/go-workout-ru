# Финальный босс: архитектура распределенной платформы вызова такси (типа Uber/Lyft)

## Условие

**Финальный босс (Event-driven микросервисная платформа):**
    Создайте систему типа "Uber/Lyft":
    * **Ride Request Service** публикует `RideRequested` в Kafka topic `rides`.
    * **Driver Matching Service** (NATS) потребляет события и ищет ближайших водителей через geo-spatial queries.
    * **Pricing Service** (RabbitMQ work queue) вычисляет surge pricing на основе спроса/предложения.
    * **Notification Service** использует RabbitMQ fanout для отправки push-уведомлений пассажиру и водителю.
    * **Payment Service** обрабатывает платежи через Kafka transactions (exactly-once).
    * **Analytics Service** использует Kafka Streams для real-time метрик (rides per minute, avg wait time, surge zones).
    * **Location Service** публикует обновления местоположения водителей в NATS (low latency) с JetStream persistence.
    * Все сервисы используют OpenTelemetry для distributed tracing.
    * Prometheus + Grafana для мониторинга (queue depths, consumer lag, message rates, latency percentiles).
    * Circuit breakers и retry logic для resilience.
    * Dead letter queues для failed messages с alerting.
    * Transactional outbox для guaranteed delivery.
    * Schema Registry для Protobuf schemas.
    * Horizontal scaling: каждый сервис имеет 3+ инстанса.
    * Chaos testing: убивайте брокеры и сервисы, проверяйте, что система восстанавливается.
    * Load testing: 10000 ride requests/минуту, P99 latency < 200ms.

## Теория

Комплексная полиглотная Event-Driven платформа мирового масштаба (Uber/Lyft Architecture):
- **Стек брокеров сообщений:**
  - `Kafka`: надежный лог поездок (`rides`), финансовые транзакции (Exactly-Once Semantics), стриминг аналитики (Kafka Streams / Flink).
  - `NATS JetStream`: обновление геопозиций сотен тысяч водителей в секунду с микросекундными задержками.
  - `RabbitMQ`: Work Queue для динамического расчета цен (Surge Pricing), Fanout для пуш-уведомлений пассажирам и водителям, Quorum Queues, Dead Lettering.
- **Инфраструктурный фундамент:**
  - OpenTelemetry сквозной трейсинг от мобильного приложения до БД.
  - Transactional Outbox + Publisher Confirms.
  - 10 000 поездок в минуту с задержкой p99 < 200 мс.

## Решение по шагам

1. Создайте архитектурный каркас платформы вызова такси `RideSharingPlatform`.
2. Реализуйте цепочку заказа: Запрос -> Поиск водителя -> Расчет цены -> Уведомления -> Оплата.
3. Замерьте суммарное время прохождения пайплайна.
4. Проверьте соблюдение требований p99 < 200 мс.

package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type RideOrderPipelineResult struct {
	RideID      string
	DriverFound string
	SurgePrice  float64
	Notified    bool
	Paid        bool
	DurationMs  int64
}

type UberStylePlatform struct {
	mu sync.Mutex
}

func (p *UberStylePlatform) ExecuteRideFlow(rideID, riderID string) RideOrderPipelineResult {
	t0 := time.Now()

	// 1. Kafka: RideRequested
	// 2. NATS: Driver Matching (поиск ближайшего водителя)
	time.Sleep(10 * time.Millisecond)
	driverID := "driver_alex_42"

	// 3. RabbitMQ: Pricing Service (Surge Pricing Work Queue)
	time.Sleep(15 * time.Millisecond)
	calculatedPrice := 650.0 // Коэффициент 1.4x

	// 4. RabbitMQ: Notification Fanout (пассажиру и водителю)
	time.Sleep(5 * time.Millisecond)

	// 5. Kafka Transactions: Payment Service
	time.Sleep(20 * time.Millisecond)

	elapsed := time.Since(t0).Milliseconds()

	return RideOrderPipelineResult{
		RideID:      rideID,
		DriverFound: driverID,
		SurgePrice:  calculatedPrice,
		Notified:    true,
		Paid:        true,
		DurationMs:  elapsed,
	}
}

func TestUberPlatformFinalBoss(t *testing.T) {
	platform := &UberStylePlatform{}

	res := platform.ExecuteRideFlow("RIDE-9941", "rider_ivan")

	if res.DriverFound == "" || !res.Notified || !res.Paid || res.DurationMs > 200 {
		t.Fatalf("Сбой пайплайна Uber платформы: %+v", res)
	}

	fmt.Println("ФИНАЛЬНЫЙ БОСС: Event-Driven платформа такси (Uber/Lyft) успешно отработала:")
	fmt.Printf("  • Поездка: %s | Назначен водитель: %s\n", res.RideID, res.DriverFound)
	fmt.Printf("  • Динамическая цена (RabbitMQ Pricing): %.2f руб\n", res.SurgePrice)
	fmt.Printf("  • Пуш-уведомления (RabbitMQ Fanout): доставлены пассажиру и водителю\n")
	fmt.Printf("  • Транзакция оплаты (Kafka Exactly-Once): успешно зафиксирована\n")
	fmt.Printf("  • Сквозная задержка пайплайна: %d мс (P99 < 200 мс соблюден!)\n", res.DurationMs)
}

## Под капотом

Связка NATS (для быстрых гео-координат), RabbitMQ (для бизнес-очередей расчета цен и пушей) и Kafka (для аналитики и финансов) представляет собой эталонную архитектуру современных мировых техногигантов.

## Подводные камни

Пытаться использовать один единственный брокер сообщений для всех задач платформы: универсального решения не существует, побеждает гибридный подход.

## На собеседовании

**Вопрос с собеседования:** «Как в такой гибридной системе обеспечить сквозную трассировку между Kafka, NATS и RabbitMQ?»
**Ответ:** Стандартизировать передачу контекста OpenTelemetry через заголовки W3C TraceContext (`traceparent`). Каждый сервис при публикации сообщения внедряет текущий SpanContext в заголовки (`Headers` в Kafka, `Msg.Header` в NATS, `Table` в RabbitMQ), а принимающий сервис восстанавливает родительский Span через `otel.GetTextMapPropagator().Extract()`, объединяя все логи в один непрерывный трейс.
