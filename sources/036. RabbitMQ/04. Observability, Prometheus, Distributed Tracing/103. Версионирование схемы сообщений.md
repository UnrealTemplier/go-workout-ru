# Версионирование схемы сообщений (Message Versioning): заголовок schema-version и эволюция API

## Условие

**Message versioning**: Добавляйте версию схемы в заголовок сообщения (`schema-version: v2`). Consumer выбирает нужный парсер в зависимости от версии.

## Теория

Эволюция схемы данных без простоя (Schema Versioning Pattern):
- При обновлении структуры доменных событий:
  - Версия 1: `{"full_name": "Иван Иванов"}`.
  - Версия 2: `{"first_name": "Иван", "last_name": "Иванов"}`.
- Заголовок сообщения:
  `headers["schema-version"] = "v2"`.
- Консьюмер:
  - Читает заголовок `schema-version`.
  - Выбирает соответствующий парсер `ParserV1` или `ParserV2`.
  - Приводит данные к единой внутренней канонической модели сервиса.
- Гарантирует бесшовный переход и параллельную работу старых и новых продюсеров.

## Решение по шагам

1. Создайте структуры сообщений версий V1 и V2.
2. Реализуйте диспетчер парсеров по заголовку `schema-version`.
3. Проверьте корректное преобразование версии V1 в каноническую модель.
4. Проверьте парсинг версии V2.

## Код решения

**`message_schema_versioning_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type CanonicalUserEvent struct {
	FirstName string
	LastName  string
}

type EventV1 struct {
	FullName string `json:"full_name"`
}

type EventV2 struct {
	FirstName string `json:"first_name"`
	LastName  string `json:"last_name"`
}

func ParseVersionedEvent(version string, raw []byte) (*CanonicalUserEvent, error) {
	switch version {
	case "v1":
		var v1 EventV1
		if err := json.Unmarshal(raw, &v1); err != nil {
			return nil, err
		}
		return &CanonicalUserEvent{FirstName: v1.FullName, LastName: ""}, nil
	case "v2":
		var v2 EventV2
		if err := json.Unmarshal(raw, &v2); err != nil {
			return nil, err
		}
		return &CanonicalUserEvent{FirstName: v2.FirstName, LastName: v2.LastName}, nil
	default:
		return nil, fmt.Errorf("неподдерживаемая версия схемы: %s", version)
	}
}

func TestMessageSchemaVersioning(t *testing.T) {
	rawV1 := []byte(`{"full_name": "Алексей Смирнов"}`)
	rawV2 := []byte(`{"first_name": "Елена", "last_name": "Орлова"}`)

	c1, err1 := ParseVersionedEvent("v1", rawV1)
	c2, err2 := ParseVersionedEvent("v2", rawV2)

	if err1 != nil || err2 != nil {
		t.Fatalf("Ошибка парсинга версий: %v, %v", err1, err2)
	}

	if c1.FirstName != "Алексей Смирнов" || c2.LastName != "Орлова" {
		t.Fatalf("Некорректная нормализация: %+v, %+v", c1, c2)
	}

	fmt.Println("Версионирование сообщений (schema-version) успешно подтверждено:")
	fmt.Printf("  • Версия V1 -> Каноническая модель: FirstName=«%s»\n", c1.FirstName)
	fmt.Printf("  • Версия V2 -> Каноническая модель: FirstName=«%s», LastName=«%s»\n", c2.FirstName, c2.LastName)
}
```

ℹ️ Поддержка обратной совместимости схем сообщений по заголовку schema-version

```bash

#   • Версия V1 -> Каноническая модель: FirstName=«Алексей Смирнов»
#   • Версия V2 -> Каноническая модель: FirstName=«Елена», LastName=«Орлова»

```

## Под капотом

В микросервисной архитектуре это соответствует правилу толерантного читателя (Tolerant Reader Pattern): сервис должен уметь читать форматы предыдущих версий без падений.

## Подводные камни

Удалять поддержку старой версии V1 сразу в день релиза V2: в брокере в очереди еще могут лежать миллионы сообщений формата V1, которые упадут при вычитке.

## На собеседовании

**Вопрос с собеседования:** «Как централизованно валидировать обратную совместимость схем в BigTech?»
**Ответ:** Использовать Schema Registry (например, Confluent Schema Registry или Apicurio). Продюсер регистрирует схему Protobuf/Avro перед публикацией. Schema Registry гарантирует правило совместимости (Full/Backward/Forward Compatibility) и отвергает несовместимые схемы еще на этапе сборки CI/CD.
