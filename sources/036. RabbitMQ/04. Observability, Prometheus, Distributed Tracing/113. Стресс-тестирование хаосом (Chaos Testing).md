# Стресс-тестирование хаосом (Chaos Testing): эмуляция сетевых задержек, потерь пакетов и отказа нод

## Условие

**Chaos testing**: Используйте `tc` (traffic control) или `pumba` для эмуляции сетевых задержек, потерь пакетов и падения брокеров.

## Теория

Инженерия хаоса для шин очередей (Chaos Engineering):
- Проверка отказоустойчивости в реальных боевых условиях:
  1. `tc qdisc add dev eth0 root netem delay 200ms 50ms loss 10%`: эмуляция дропа 10% пакетов и задержки 200 мс.
  2. `pumba kill --signal SIGKILL rabbitmq-node-2`: внезапное принудительное убийство ноды кластера.
- Цель тестирования:
  - Убедиться, что Publisher Confirms корректно переподключаются.
  - Quorum Queues выбирают нового лидера без потери сообщений.
  - Консьюмеры не зависают намертво.

## Решение по шагам

1. Создайте модель сети с внедрением случайных сетевых задержек и сбоев.
2. Протестируйте отправку сообщения через нестабильную сеть.
3. Убедитесь в успешной доставке благодаря повторным попыткам клиента.
4. Зафиксируйте сохранение целостности данных.

## Код решения

**`chaos_network_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type UnreliableNetworkChannel struct {
	dropNext bool
}

func (c *UnreliableNetworkChannel) Send(payload string) error {
	if c.dropNext {
		c.dropNext = false
		return errors.New("simulated network packet drop (Chaos Netem)")
	}
	return nil
}

func TestChaosNetworkResilience(t *testing.T) {
	ch := &UnreliableNetworkChannel{dropNext: true}

	payload := "Критический заказ в условиях хаоса"

	// Клиент с ретраем преодолевает потерю пакета
	var err error
	for attempt := 1; attempt <= 3; attempt++ {
		err = ch.Send(payload)
		if err == nil {
			fmt.Printf("  • Попытка #%d: успешно доставлено через нестабильную сеть!\n", attempt)
			break
		}
		fmt.Printf("  • Попытка #%d: зафиксирован сбой сети (%v), выполняем ретрай...\n", attempt, err)
	}

	if err != nil {
		t.Fatalf("Сообщение должно было пройти после ретрая: %v", err)
	}

	fmt.Println("Chaos Testing: клиент успешно выдержал сетевые потери без потери данных!")
}
```

ℹ️ Устойчивость клиента очередей к искусственным сетевым потерям пакетов

## Под капотом

В Kubernetes для проведения Chaos-тестов используют оператор Chaos Mesh. Он внедряет задержки на уровне iptables и cgroups ядра Linux без изменения кода сервисов.

## Подводные камни

Проводить Chaos-тесты в продакшене без предварительного тестирования в Staging среде: неверно настроенный скрипт может убить весь кластер баз данных.

## На собеседовании

**Вопрос с собеседования:** «Каковы главные метрики при проведении Chaos GameDay для очередей сообщений?»
**Ответ:** 1. Message Loss Rate (должен быть строго 0%); 2. Time to Recover (время перевыбора лидера в секундах); 3. Spike in 5xx HTTP Errors на клиентских шлюзах; 4. Рост памяти и процессорного времени во время реконнектов.
