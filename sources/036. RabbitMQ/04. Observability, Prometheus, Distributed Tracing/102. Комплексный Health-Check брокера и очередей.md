# Комплексный Health-Check брокера и очередей: проверка сокета и мониторинг Consumer Lag

## Условие

Напишите health-check для очереди: периодически проверяйте соединение с брокером, состояние consumer lag (для Kafka). Если lag превышает порог — логируйте алерт.

## Теория

Промышленный эндпоинт `/healthz` и `/readyz` с проверкой очередей:
- Проверка разделяется на два уровня:
  1. **Liveness Probe (`/healthz`):** проверяет, что процесс жив и внутренний канал брокера не закрыт (`conn.IsClosed() == false`).
  2. **Readiness Probe (`/readyz`):** проверяет способность принимать трафик:
     - Очередь не переполнена.
     - Отставание консьюмеров (Consumer Lag) не превышает критический порог (например, 5000 сообщений).
- Если Consumer Lag зашкаливает \(\to\) сервис сигнализирует о деградации для автомасштабирования пода через HPA/KEDA.

## Решение по шагам

1. Создайте структуру проверки здоровья очереди `QueueHealthChecker`.
2. Реализуйте проверку открытости соединения.
3. Реализуйте проверку допустимого Consumer Lag.
4. Протестируйте генерацию алерта при превышении лимита lag.

## Код решения

**`queue_health_check_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type QueueHealthStatus struct {
	Connected   bool
	ConsumerLag int
	IsHealthy   bool
	AlertMsg    string
}

func EvaluateQueueHealth(connected bool, lag int, maxLag int) QueueHealthStatus {
	if !connected {
		return QueueHealthStatus{Connected: false, ConsumerLag: lag, IsHealthy: false, AlertMsg: "CRITICAL: брокер недоступен"}
	}
	if lag > maxLag {
		return QueueHealthStatus{Connected: true, ConsumerLag: lag, IsHealthy: false, AlertMsg: fmt.Sprintf("WARNING: высокий lag %d > %d", lag, maxLag)}
	}
	return QueueHealthStatus{Connected: true, ConsumerLag: lag, IsHealthy: true, AlertMsg: "OK"}
}

func TestQueueHealthCheck(t *testing.T) {
	// 1. Нормальное состояние
	h1 := EvaluateQueueHealth(true, 45, 1000)
	if !h1.IsHealthy {
		t.Fatal("Очередь должна быть здоровой")
	}

	// 2. Отставание консьюмеров превысило порог
	h2 := EvaluateQueueHealth(true, 5400, 1000)
	if h2.IsHealthy || h2.AlertMsg != "WARNING: высокий lag 5400 > 1000" {
		t.Fatalf("Должен сработать алерт отставания: %+v", h2)
	}

	fmt.Println("Health-Check очередей успешно протестирован:")
	fmt.Printf("  • Норма:    %s (Lag=%d)\n", h1.AlertMsg, h1.ConsumerLag)
	fmt.Printf("  • Деградация: %s (Lag=%d)\n", h2.AlertMsg, h2.ConsumerLag)
}
```

ℹ️ Проверка доступности соединения и мониторинг порога отставания Consumer Lag

## Под капотом

Для RabbitMQ показатель Consumer Lag рассчитывается как количество сообщений в статусе `Ready` в очереди (`messages_ready`). Для Kafka lag — это разница между High Watermark смещением в партиции и текущим Offset консьюмера.

## Подводные камни

Делать тяжелый сетевой запрос к брокеру на каждый вызов `/healthz` Kubernetes (каждые 2 секунды): опрос должен выполняться в фоновой горутине раз в 10–15 секунд, кэшируя статус в `atomic.Value`.

## На собеседовании

**Вопрос с собеседования:** «Почему опасно ронять Readiness Probe сервиса при высоком Consumer Lag?»
**Ответ:** Если сервис выключить из балансировщика Kubernetes при высоком лаге, он перестанет получать входящие HTTP запросы, но продолжит вычитывать очередь сообщений (что хорошо). Однако, если этот же сервис обслуживает запросы пользователей, отключение Readiness Probe приведет к отказу пользовательского API.
