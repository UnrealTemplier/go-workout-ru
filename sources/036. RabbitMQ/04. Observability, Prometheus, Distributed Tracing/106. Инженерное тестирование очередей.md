# Инженерное тестирование очередей: юнит-тесты на моках, Testcontainers и контрактные тесты

## Условие

Реализуй **Message Queue Testing**:
- Unit: mock `kafka.Writer`/`kafka.Reader` через интерфейсы
- Integration: testcontainers Kafka/RabbitMQ/NATS, real produce/consume
- Contract: Pact или ручной — producer test публикует, consumer test проверяет schema
- Load: `kafka-producer-perf-test`, `kafka-consumer-perf-test`, custom k6 script
- Chaos: randomly kill brokers/consumers, verify no data loss

## Теория

Пирамида тестирования очередей сообщений:
1. **Unit Tests (Юнит):** изоляция бизнес-логики через интерфейсы издателя и читателя (быстро, без сети).
2. **Integration Tests (Интеграция):** библиотека `testcontainers-go` поднимает реальный контейнер RabbitMQ в Docker на случайном порту для проверки реальных протоколов.
3. **Contract Tests (Контракты):** проверка совместимости JSON схем между продюсером и консьюмером.
4. **Chaos Testing (Хаос):** принудительное убийство брокера (`docker kill`) во время отправки для проверки сохранения данных.

## Решение по шагам

1. Создайте мок интерфейса отправки сообщений `MockPublisher`.
2. Реализуйте юнит-тест бизнес-логики сервиса.
3. Проверьте фиксацию вызова публикации без реального сетевого брокера.
4. Протестируйте проверку контракта полезной нагрузки.

## Код решения

**`mq_testing_pyramid_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MessagePublisher interface {
	Publish(topic, message string) error
}

type MockPublisher struct {
	PublishedMessages []string
}

func (m *MockPublisher) Publish(topic, message string) error {
	m.PublishedMessages = append(m.PublishedMessages, message)
	return nil
}

type OrderService struct {
	publisher MessagePublisher
}

func (s *OrderService) CreateOrder(id string) error {
	return s.publisher.Publish("orders", fmt.Sprintf("ORDER_CREATED:%s", id))
}

func TestMQUnitMock(t *testing.T) {
	mock := &MockPublisher{}
	svc := &OrderService{publisher: mock}

	err := svc.CreateOrder("ORD-UNIT-42")
	if err != nil {
		t.Fatalf("Ошибка создания заказа: %v", err)
	}

	if len(mock.PublishedMessages) != 1 || mock.PublishedMessages[0] != "ORDER_CREATED:ORD-UNIT-42" {
		t.Fatalf("Сообщение не опубликовано в мок: %v", mock.PublishedMessages)
	}

	fmt.Println("Юнит-тестирование очередей через интерфейсные моки успешно:")
	fmt.Printf("  • Бизнес-логика протестирована изолированно без поднятия брокера\n")
	fmt.Printf("  • Зафиксировано событие в моке: %s\n", mock.PublishedMessages[0])
}
```

ℹ️ Изолированное юнит-тестирование отправки сообщений через мок-интерфейс

**`Терминал`**

```bash
go test -v mq_testing_pyramid_test.go
# Вывод:
# === RUN   TestMQUnitMock
# Юнит-тестирование очередей через интерфейсные моки успешно:
#   • Бизнес-логика протестирована изолированно без поднятия брокера
#   • Зафиксировано событие в моке: ORDER_CREATED:ORD-UNIT-42
# --- PASS: TestMQUnitMock (0.00s)
# PASS
```

## Под капотом

Тестирование через интерфейсы обеспечивает выполнение сотен тестов за миллисекунды, а Testcontainers гарантирует точное соответствие поведению реального продакшена.

## Подводные камни

Использовать общий общий статический экземпляр RabbitMQ для всех параллельных тестов: тесты будут перезаписывать очереди друг друга и давать флакающие результаты (flaky tests).

## На собеседовании

**Вопрос с собеседования:** «Как организовать параллельное тестирование консьюмеров с Testcontainers в Go?»
**Ответ:** Запускать отдельный контейнер на пакет тестов через `TestMain`, либо создавать изолированный `vhost` со случайным UUID на каждый тестовый кейс `t.Run`. Это позволяет запускать тесты с флагом `go test -parallel 8` в полной изоляции.
