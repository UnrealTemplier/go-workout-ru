# Утилита переотправки сообщений (DLQ Redrive Tool): чтение из DLQ и повторная отправка в прод

## Условие

**Dead Letter Queue (DLQ)**: Настрой RabbitMQ (или вручную в Kafka). Если сообщение не удалось обработать 3 раза (например, кривой JSON или сторонняя апишка лежит), не выкидывай его. Консьюмер должен переложить его в отдельную очередь/топик `events.dlq`. Напиши тулзу, которая позволяет админу прочитать DLQ и попробовать переотправить сообщения.

## Теория

Паттерн ручного расследования и повторной отправки (DLQ Redrive Tool):
- Когда баг в продакшене исправлен и задеплоен:
  - 500 упавших сообщений лежат в `events.dlq`.
  - Администратор или SRE инженер запускает CLI утилиту `dlq-redrive`:
    1. Читает сообщения из `events.dlq`.
    2. Выводит превью полезной нагрузки.
    3. При подтверждении публикует сообщения обратно в основную очередь `events.primary`.
    4. Отправляет `Ack` брокеру для удаления из DLQ.
  - Полное восстановление бизнес-данных без ручной правки таблиц БД.

## Решение по шагам

1. Создайте модель очереди DLQ и основной очереди.
2. Реализуйте функцию `RedriveDLQMessages`.
3. Смоделируйте перенос сообщений из DLQ в рабочую очередь.
4. Проверьте очистку DLQ и готовность к повторной обработке.

## Код решения

**`dlq_redrive_tool_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RedriveSystem struct {
	dlqQueue     []string
	primaryQueue []string
}

func (s *RedriveSystem) RunRedrive() int {
	moved := 0
	for len(s.dlqQueue) > 0 {
		msg := s.dlqQueue[0]
		s.dlqQueue = s.dlqQueue[1:]
		// Перекладываем в основную очередь для повторной обработки
		s.primaryQueue = append(s.primaryQueue, msg)
		moved++
	}
	return moved
}

func TestDLQRedriveTool(t *testing.T) {
	sys := &RedriveSystem{
		dlqQueue: []string{
			`{"tx_id": "failed-1", "user": "ivan"}`,
			`{"tx_id": "failed-2", "user": "olga"}`,
		},
	}

	count := sys.RunRedrive()

	if count != 2 || len(sys.dlqQueue) != 0 || len(sys.primaryQueue) != 2 {
		t.Fatalf("Сбой redrive: перенесено %d, dlq=%d, primary=%d", count, len(sys.dlqQueue), len(sys.primaryQueue))
	}

	fmt.Println("DLQ Redrive Tool успешно восстановил задачи в продакшен:")
	fmt.Printf("  • Успешно перенесено сообщений: %d\n", count)
	fmt.Printf("  • Очередь DLQ очищена: %d сообщений\n", len(sys.dlqQueue))
	fmt.Printf("  • Основная очередь готова к работе: %d сообщений!\n", len(sys.primaryQueue))
}
```

## Под капотом

В промышленном RabbitMQ функцию DLQ Redrive выполняет официальный плагин `rabbitmq_shovel`: динамическая shovel-конфигурация перемещает все сообщения из DLQ в исходную очередь в фоновом режиме.

## Подводные камни

Запускать redrive до того, как баг в коде консьюмера был исправлен: сообщения мгновенно упадут повторно и снова вернутся в DLQ, породив бесполезную нагрузку.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать фильтрацию сообщений в DLQ Redrive Tool (переотправлять только определенный тип ошибок)?»
**Ответ:** При чтении из DLQ анализировать заголовки `x-death` или `x-exception-message`. Если причина — `timeout connecting to third-party API`, отправлять в основную очередь. Если причина — `permanent validation error` (битые данные), пропускать сообщение и оставлять в архивной таблице БД.
