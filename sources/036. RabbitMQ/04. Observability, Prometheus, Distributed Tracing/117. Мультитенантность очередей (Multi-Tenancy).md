# Мультитенантность очередей (Multi-Tenancy): изоляция очередей клиентов и маршрутизация по токенам

## Условие

**Multi-tenancy**: Изолируйте данные разных клиентов через отдельные topics/queues или через partition key + ACL.

## Теория

Стратегии изоляции клиентов (Multi-Tenancy Isolation Patterns):
1. **Queue-per-Tenant:** каждому клиенту создается персональная очередь `tenant_{id}_orders`.
   - Плюсы: 100% изоляция, простота мониторинга квот.
   - Минусы: расход ресурсов при десятках тысяч клиентов.
2. **Partition-Key Filtering:** единая очередь, сообщения содержат `tenant_id`.
   - Плюсы: масштабируемость.
   - Минусы: риск утечки при ошибке в коде воркера.
- Для B2B финтеха и медицины стандартом является строгая изоляция на уровне очередей/vhost.

## Решение по шагам

1. Создайте маршрутизатор мультитенантных очередей.
2. Смоделируйте создание изолированных очередей для Тенанта 1 и Тенанта 2.
3. Проверьте доставку сообщения строго в очередь целевого клиента.
4. Убедитесь в отсутствии смешивания данных.

## Код решения

**`multi_tenant_queues_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MultiTenantQueueHub struct {
	tenantQueues map[string][]string
}

func NewMultiTenantQueueHub() *MultiTenantQueueHub {
	return &MultiTenantQueueHub{tenantQueues: make(map[string][]string)}
}

func (h *MultiTenantQueueHub) Dispatch(tenantID, payload string) {
	queueName := fmt.Sprintf("tenant_%s_queue", tenantID)
	h.tenantQueues[queueName] = append(h.tenantQueues[queueName], payload)
}

func TestMultiTenantQueues(t *testing.T) {
	hub := NewMultiTenantQueueHub()

	hub.Dispatch("sber", "Платеж Сбера #501")
	hub.Dispatch("tinkoff", "Платеж Т-Банка #902")

	qSber := hub.tenantQueues["tenant_sber_queue"]
	qTinkoff := hub.tenantQueues["tenant_tinkoff_queue"]

	if len(qSber) != 1 || qSber[0] != "Платеж Сбера #501" {
		t.Fatalf("Данные Сбера скомпрометированы: %v", qSber)
	}

	if len(qTinkoff) != 1 || qTinkoff[0] != "Платеж Т-Банка #902" {
		t.Fatalf("Данные Т-Банка скомпрометированы: %v", qTinkoff)
	}

	fmt.Println("Multi-Tenant изоляция очередей успешно подтверждена:")
	fmt.Printf("  • Очередь tenant_sber_queue:    «%s»\n", qSber[0])
	fmt.Printf("  • Очередь tenant_tinkoff_queue: «%s»\n", qTinkoff[0])
	fmt.Println("  • Полная изоляция финансовых потоков клиентов обеспечена!")
}
```

## Под капотом

Изолированные очереди позволяют настраивать разные политики SLA: VIP клиенту можно выделить 10 выделенных воркеров с гарантией обработки за 5 мс, а бесплатному клиенту — 1 воркер со строгим лимитом.

## Подводные камни

Позволять клиенту передавать произвольное имя очереди в HTTP запросе: это приведет к созданию миллионов мусорных очередей (Queue Injection Attack). Имя очереди должно генерироваться строго сервером.

## На собеседовании

**Вопрос с собеседования:** «Каковы ограничения на количество очередей в кластере RabbitMQ?»
**Ответ:** Классический кластер RabbitMQ может стабильно обслуживать от 10 000 до 50 000 очередей. Дальнейший рост до 100k+ очередей перегружает Erlang Mnesia и расходует оперативную память на поддержание метаданных. Для миллионов очередей используют партиционирование или внешние брокеры.
