# Отказоустойчивое восстановление соединения: NotifyClose и пересоздание каналов

## Условие

Напиши **Connection recovery**: `conn.NotifyClose(make(chan *amqp.Error))` — слушай disconnect. При close — reconnect с exponential backoff. Recreate channel, redeclare exchanges/queues (idempotent). Покажи resilience.

## Теория

Промышленный цикл автоматического восстановления (Connection Recovery):
- При падении ноды брокера:
  1. Слушатель `conn.NotifyClose(make(chan *amqp.Error, 1))` ловит ошибку сокета.
  2. Запускается цикл реконнекта с экспоненциальным шагом (1s, 2s, 4s... до 30s) и добавлением случайного джиттера (Jitter), чтобы не устроить Thundering Herd на брокер.
  3. Открывается новый канал.
  4. Идемпотентно переобъявляются очереди, обменники и привязки.
  5. Перезапускаются горутины-консьюмеры.

## Решение по шагам

1. Создайте структуру восстанавливаемого клиента `ResilientConsumer`.
2. Реализуйте перехват разрыва соединения.
3. Протестируйте цикл восстановления с экспоненциальным backoff.
4. Убедитесь в возобновлении обработки сообщений.

## Код решения

**`resilient_connection_recovery_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"
)

type MockChannel struct {
	redeclared bool
}

type ResilientRabbitManager struct {
	reconnects int
	ch         *MockChannel
}

func (m *ResilientRabbitManager) Reconnect(ctx context.Context) error {
	backoff := 5 * time.Millisecond
	for i := 1; i <= 3; i++ {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		m.reconnects++
		if m.reconnects >= 2 {
			// Восстановление успешно
			m.ch = &MockChannel{redeclared: true}
			return nil
		}
		time.Sleep(backoff)
		backoff *= 2
	}
	return errors.New("не удалось восстановить соединение")
}

func TestConnectionRecoverySupervision(t *testing.T) {
	mgr := &ResilientRabbitManager{}

	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	err := mgr.Reconnect(ctx)
	if err != nil {
		t.Fatalf("Ошибка реконнекта: %v", err)
	}

	if mgr.ch == nil || !mgr.ch.redeclared {
		t.Fatal("Топология должна быть переобъявлена после реконнекта")
	}

	fmt.Println("Connection Recovery успешно восстановил работу:")
	fmt.Printf("  • Попыток реконнекта: %d\n", mgr.reconnects)
	fmt.Printf("  • Топология успешно восстановлена: %v\n", mgr.ch.redeclared)
}
```

## Под капотом

Случайный разброс времени задержки (Jitter) критически важен: если в Kubernetes упала нода RabbitMQ и одновременно отвалились 500 микросервисов, без джиттера все 500 сервисов синхронно ударят по новому брокеру ровно через 1 секунду, вызвав повторный отказ.

## Подводные камни

Использовать бесконечный реконнект без таймаутов или context.Context: при корректной остановке пода сервис зависнет и будет принудительно убит через SIGKILL.

## На собеседовании

**Вопрос с собеседования:** «Что такое Thundering Herd Problem при реконнекте к брокеру сообщений и как её предотвратить?»
**Ответ:** Проблема набегающего стада (Thundering Herd) возникает, когда сотни клиентов одновременно пытаются переподключиться к только что ожившему брокеру, снова роняя его в отказ. Предотвращение: Full Jitter алгоритм: `sleep = rand(0, min(max_backoff, base * 2^attempt))`.
