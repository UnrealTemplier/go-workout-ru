# Паттерн Saga Choreography: распределенная транзакция и компенсирующие действия при сбое оплаты

## Условие

Реализуй **Saga Choreography через RabbitMQ**: каждый сервис слушает события, выполняет шаг, публикует следующее событие. `OrderCreated` → `InventoryService` резервирует → `InventoryReserved` → `PaymentService` списывает → `PaymentProcessed` → `ShippingService` отправляет. Compensation: `PaymentFailed` → `InventoryService` освобождает.

## Теория

Архитектура Saga Choreography (Хореография Саги):
- Распределенная транзакция разбивается на цепочку локальных транзакций:
  1. `OrderService`: создает заказ в статусе `PENDING` \(\to\) публикует `OrderCreated`.
  2. `InventoryService`: слушает `OrderCreated`, резервирует товар на складе \(\to\) публикует `InventoryReserved`.
  3. `PaymentService`: слушает `InventoryReserved`, пытается списать средства.
- **Сбой и Компенсация (Compensating Transaction):**
  - Если на балансе клиента недостаточно средств:
    - `PaymentService` публикует `PaymentFailed`.
    - `InventoryService` ловит `PaymentFailed` и выполняет компенсацию: **разблокирует зарезервированный товар**.
    - `OrderService` переводит заказ в статус `CANCELLED`.
- Гарантирует целостность системы без тяжелых распределенных блокировок (2PC).

## Решение по шагам

1. Создайте цепочку сервисов Саги.
2. Реализуйте успешный шаг резервирования склада.
3. Смоделируйте сбой оплаты и публикацию `PaymentFailed`.
4. Проверьте выполнение компенсирующей транзакции освобождения товара на складе.

## Код решения

**`saga_choreography_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SagaInventoryState struct {
	ReservedItems int
}

func (s *SagaInventoryState) OnOrderCreated(qty int) {
	s.ReservedItems += qty
	fmt.Printf("1. Склад: зарезервировано %d шт товара -> событие InventoryReserved\n", qty)
}

func (s *SagaInventoryState) OnPaymentFailed(qty int) {
	s.ReservedItems -= qty
	fmt.Printf("2. Склад: компенсация! Освобождено %d шт товара из-за PaymentFailed\n", qty)
}

func TestSagaChoreographyCompensation(t *testing.T) {
	inventory := &SagaInventoryState{}

	// Шаг 1: OrderCreated -> Резерв на складе
	inventory.OnOrderCreated(3)
	if inventory.ReservedItems != 3 {
		t.Fatalf("Должно быть зарезервировано 3 шт: %d", inventory.ReservedItems)
	}

	// Шаг 2: PaymentService не смог списать деньги -> публикует PaymentFailed
	// Шаг 3: InventoryService выполняет компенсирующее действие
	inventory.OnPaymentFailed(3)
	if inventory.ReservedItems != 0 {
		t.Fatalf("После компенсации резерв должен быть 0: %d", inventory.ReservedItems)
	}

	fmt.Println("Saga Choreography с компенсирующей транзакцией отработала успешно:")
	fmt.Printf("  • Резерв возвращен в исходное состояние: %d шт\n", inventory.ReservedItems)
	fmt.Println("  • Согласованность данных (Eventual Consistency) гарантирована!")
}
```

## Под капотом

В отличие от ACID, Сага обеспечивает модель BASE (Eventual Consistency). В течение нескольких миллисекунд или секунд система находится в промежуточном состоянии, но гарантированно сходится к корректному результату.

## Подводные камни

Создать циклические зависимости событий между сервисами: Сага может войти в бесконечный цикл компенсаций. Цепочка событий должна быть направленным ациклическим графом (DAG).

## На собеседовании

**Вопрос с собеседования:** «Когда следует предпочесть Saga Orchestration вместо Saga Choreography?»
**Ответ:** Когда бизнес-процесс насчитывает более 4–5 шагов или имеет сложную условную логику ветвления. В хореографии при 10 сервисах становится невозможно понять общий ход процесса по логам брокера. В оркестрации выделенный оркестратор (например, Temporal или Cadence) централизованно хранит стейт-машину каждого заказа.
