# Паттерн Work Queue: один продюсер и конкурирующие воркеры с балансировкой

## Условие

Реализуйте **work queue pattern**: один producer, несколько consumers, каждое сообщение обрабатывается одним consumer (round-robin).

## Теория

Каноническая модель распределения работы:
- Продюсер непрерывно генерирует задачи в очередь `tasks`.
- Пул воркеров забирает задачи.
- Гарантия: каждое конкретное сообщение обрабатывается **строго одним** воркером.
- Достигается параллелизм вычислений без состояния гонки за ресурсы.

## Решение по шагам

1. Создайте пул конкурирующих потребителей.
2. Отправьте пакет из 12 задач.
3. Проверьте распределение между воркерами.
4. Убедитесь, что ни одна задача не выполнилась дважды.

## Код решения

**`canonical_work_queue_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

func TestCanonicalWorkQueue(t *testing.T) {
	workerCount := 3
	tasksCount := 12

	workerTasks := make([][]int, workerCount)

	for taskID := 1; taskID <= tasksCount; taskID++ {
		wID := (taskID - 1) % workerCount
		workerTasks[wID] = append(workerTasks[wID], taskID)
	}

	for i, tasks := range workerTasks {
		if len(tasks) != 4 {
			t.Fatalf("Воркер %d должен был получить 4 задачи: %v", i+1, tasks)
		}
		fmt.Printf("  • Воркер #%d обработал задачи: %v\n", i+1, tasks)
	}

	fmt.Println("Work Queue pattern успешно распределил 12 задач без дублирования!")
}
```

ℹ️ Каноническое распределение задач пула Work Queue

## Под капотом

RabbitMQ блокирует доставленное сообщение для других консьюмеров на время обработки, пока первый консьюмер не подтвердит его через `Ack` или не упадет.

## Подводные камни

Запускать воркеры с разными версиями кода на одной Work Queue: половина задач будет обработана по старой логике, а половина — по новой (рекомендуются сине-зеленые деплои).

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать порядок обработки сообщений (Strict Ordering) в Work Queue с 10 параллельными воркерами?»
**Ответ:** Никак! Если на одной очереди работают 10 воркеров, порядок завершения задач недетерминирован из-за разной скорости CPU и сети. Для строгого упорядочивания используют: 1) Single Active Consumer (`x-single-active-consumer: true`), где в каждый момент времени читает строго один воркер; 2) Либо шардирование по ключу (Consistent Hash Exchange / Kafka партиции).
