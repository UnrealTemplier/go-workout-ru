# Срок жизни сообщений (Message TTL): уровень очереди x-message-ttl и per-message Expiration

## Условие

Напиши **Message TTL**: Queue args `{"x-message-ttl": 60000}` — сообщение удаляется через 60s если не обработано. Или per-message: `amqp.Publishing{Expiration: "60000"}`. Покажи timeout для time-sensitive задач.

## Теория

Два уровня настройки Message TTL:
1. **Queue-level TTL (`x-message-ttl: 60000`):**
   - Единый срок жизни (в миллисекундах) для ВСЕХ сообщений очереди.
   - Брокер гарантирует удаление строго по истечении 60 секунд.
2. **Per-message TTL (`amqp.Publishing{Expiration: "10000"}`):**
   - Индивидуальный срок жизни для конкретного сообщения в миллисекундах (в строковом представлении).
   - Если заданы оба параметра, применяется **меньшее** значение!

## Решение по шагам

1. Создайте структуру с параметрами Message TTL.
2. Проверьте логику выбора минимального таймаута.
3. Протестируйте сценарий отсечения просроченных одноразовых СМС кодов.
4. Проверьте корректность значений в миллисекундах.

## Код решения

**`message_ttl_modes_test.go`**

```go
package main

import (
	"fmt"
	"strconv"
	"testing"
)

func ResolveEffectiveTTL(queueTTL int64, msgExpiration string) int64 {
	effective := queueTTL
	if msgExpiration != "" {
		if perMsg, err := strconv.ParseInt(msgExpiration, 10, 64); err == nil {
			if effective == 0 || perMsg < effective {
				effective = perMsg
			}
		}
	}
	return effective
}

func TestMessageTTLModes(t *testing.T) {
	// Очередь с TTL 60 секунд (60000 мс)
	queueTTL := int64(60000)

	// Сообщение с индивидуальным сроком 10 секунд (10000 мс)
	msgExp := "10000"

	effective := ResolveEffectiveTTL(queueTTL, msgExp)
	if effective != 10000 {
		t.Fatalf("Эффективный TTL должен быть минимальным (10000): got %d", effective)
	}

	fmt.Printf("Message TTL успешно рассчитан:\n")
	fmt.Printf("  • Queue TTL:     %d мс\n", queueTTL)
	fmt.Printf("  • Per-Message:   %s мс\n", msgExp)
	fmt.Printf("  • Итоговый TTL:  %d мс (выбран наименьший таймаут!)\n", effective)
}
```

## Под капотом

Значение `Expiration` в `amqp.Publishing` передается как строка в миллисекундах согласно спецификации AMQP 0-9-1. Нечисловое значение приведет к игнорированию параметра.

## Подводные камни

Полагаться на per-message TTL для очистки памяти: брокер проверяет срок жизни индивидуального сообщения только в момент, когда оно доходит до головы очереди (Head of Queue).

## На собеседовании

**Вопрос с собеседования:** «Почему per-message TTL может вызвать задержку отправки просроченного сообщения в DLQ?»
**Ответ:** RabbitMQ классических очередей не ставит индивидуальный таймер на каждое сообщение. Он проверяет протухание только у сообщения во главе очереди. Если первое сообщение имеет TTL 1 час, а за ним лежит сообщение с TTL 10 секунд, второе сообщение не перейдет в DLQ, пока не выйдет 1 час у первого.
