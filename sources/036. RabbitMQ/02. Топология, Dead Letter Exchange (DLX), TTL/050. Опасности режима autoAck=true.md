# Опасности режима autoAck=true: потеря критических данных при аварийном падении воркера

## Условие

Реализуйте **consumer**, который читает из queue `orders` с auto-ack (`autoAck: true`). Изучите, почему это опасно (потеря сообщений при crash).

## Теория

Почему режим `autoAck: true` смертельно опасен для ценных данных:
- Как только сообщение покидает сетевой буфер брокера:
  - Брокер **мгновенно стирает его с диска и из памяти**.
  - Сообщение существует только в буфере сетевой карты воркера.
- Если воркер аварийно падает (паника в коде, нехватка памяти OOM, убийство пода Kubernetes):
  - Сообщение пропадает навсегда! Никакого Redelivery не произойдет.
- Режим `autoAck: true` допустим только для некритичных логов и метрик, потеря которых безразлична.

## Решение по шагам

1. Создайте модель очереди в режиме `autoAck: true`.
2. Смоделируйте выдачу сообщения клиенту.
3. Продемонстрируйте, что в брокере сообщений не осталось.
4. Сымитируйте падение процесса и зафиксируйте безвозвратную потерю данных.

## Код решения

**`autoack_danger_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FragileBroker struct {
	queue []string
}

func (b *FragileBroker) ConsumeAutoAck() (string, bool) {
	if len(b.queue) == 0 {
		return "", false
	}
	// Сообщение немедленно удаляется из брокера!
	msg := b.queue[0]
	b.queue = b.queue[1:]
	return msg, true
}

func TestAutoAckDanger(t *testing.T) {
	broker := &FragileBroker{
		queue: []string{"Оплата заказа #99401 на сумму 1 000 000 руб"},
	}

	// 1. Консьюмер забирает сообщение в режиме autoAck=true
	msg, ok := broker.ConsumeAutoAck()
	if !ok {
		t.Fatal("Ожидалось сообщение")
	}

	// 2. В брокере уже ничего нет!
	if len(broker.queue) != 0 {
		t.Fatal("В брокере не должно оставаться сообщений в режиме autoAck")
	}

	// 3. Воркер падает (паника/OOM) до записи в базу данных!
	workerCrashed := true
	if workerCrashed {
		fmt.Printf("⚠️ АВАРИЯ: Воркер упал до записи в БД! Сообщение «%s» БЕЗВОЗВРАТНО УТЕРЯНО!\n", msg)
	}

	fmt.Println("Демонстрация рисков autoAck=true успешно выполнена.")
}
```

ℹ️ Демонстрация безвозвратной потери данных при аварии воркера в режиме autoAck

## Под капотом

В спецификации AMQP 0-9-1 режим `autoAck` называется `no_ack`. Имя говорит само за себя: брокер работает в предположении, что клиент никогда не подтверждает сообщения, уничтожая данные сразу при отправке.

## Подводные камни

Включать `autoAck: true` ради ускорения бенчмарков: приложение на синтетических тестах покажет высокий RPS, но в проде при первом же сбое потеряет заказы клиентов.

## На собеседовании

**Вопрос с собеседования:** «Есть ли случаи, когда autoAck: true оправдан в продакшене?»
**Ответ:** Да, только в системах сбора высокочастотной телеметрии (метрики CPU/RAM агентов, кликстрим пользователей), где пропуск нескольких точек данных несущественен, а производительность и минимальные накладные расходы критичны.
