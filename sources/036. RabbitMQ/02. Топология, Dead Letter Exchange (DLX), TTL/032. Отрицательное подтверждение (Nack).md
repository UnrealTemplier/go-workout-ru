# Отрицательное подтверждение (Nack): различие requeue=true (повтор) и requeue=false (отброс в DLX)

## Условие

Напиши **Negative acknowledgment + requeue**: `d.Nack(false, true)` — requeue this message (возвращает в очередь). `d.Nack(false, false)` — discard (или в DLX). Покажи retry logic: `Nack` + requeue → повторная обработка.

## Теория

Развилка обработки сбоев:
- `d.Nack(multiple: false, requeue: true)`:
  - Используется при **транзиентных** сбоях (сеть мигнула, таймаут сервиса).
  - Сообщение возвращается в голову/хвост очереди.
- `d.Nack(multiple: false, requeue: false)`:
  - Используется при **перманентных** сбоях (битый формат данных, схема невалидна, бизнес-ошибка).
  - Сообщение отбрасывается брокером (Discard) либо, если настроен DLX, пересылается в Dead Letter Queue.

## Решение по шагам

1. Создайте обработчик с разделением типов ошибок.
2. При временной ошибке верните решение `Nack(requeue=true)`.
3. При критической ошибке верните решение `Nack(requeue=false)`.
4. Протестируйте оба сценария.

## Код решения

**`nack_requeue_strategy_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

var (
	ErrTemporaryNetwork = errors.New("timeout connecting to payment gateway")
	ErrPermanentCorrupt = errors.New("invalid JSON payload: syntax error")
)

func DecideNackAction(err error) (requeue bool, action string) {
	if errors.Is(err, ErrTemporaryNetwork) {
		return true, "REQUEUE (Повторная попытка обработки)"
	}
	return false, "DISCARD_TO_DLX (Отброс в Dead Letter Queue)"
}

func TestNackRequeueStrategy(t *testing.T) {
	// Сценарий 1: Временный сетевой сбой
	req1, act1 := DecideNackAction(ErrTemporaryNetwork)
	if !req1 {
		t.Fatal("Временная ошибка должна возвращать requeue=true")
	}

	// Сценарий 2: Битые данные
	req2, act2 := DecideNackAction(ErrPermanentCorrupt)
	if req2 {
		t.Fatal("Поврежденные данные должны возвращать requeue=false")
	}

	fmt.Println("Стратегия Nack успешно протестирована:")
	fmt.Printf("  • Временная ошибка: %s\n", act1)
	fmt.Printf("  • Фатальная ошибка: %s\n", act2)
}
```

ℹ️ Разделение логики requeue=true и requeue=false в зависимости от типа ошибки

## Под капотом

Если у очереди нет `x-dead-letter-exchange`, вызов `Nack(false, false)` приводит к физическому удалению байтов сообщения из памяти и журнала брокера.

## Подводные камни

Вызывать `Nack(false, true)` при наличии всего одного консьюмера: этот же консьюмер мгновенно получит это же сообщение обратно, сформировав 100% busy-loop зависание.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисах предпочитают паттерн Dead Lettering вместо прямого Nack requeue=true?»
**Ответ:** Потому что прямой `requeue=true` забивает очередь и создает эффект Head-of-Line Blocking (следующие валидные сообщения ждут разблокировки). DLX изолирует сбойные задачи в отдельный топик, позволяя основной очереди продолжать обработку на полной скорости.
