# Паттерн Fanout в маркетинговых рассылках: обменник marketing_events и временные очереди

## Условие

**Паттерн Fanout (Publish-Subscribe)**: Реализуйте систему уведомлений. Объявите Exchange типа `fanout` с именем `marketing_events`. Создайте двух независимых консьюмеров (например, сервис отправки Email и сервис отправки Push-уведомлений). Каждый при старте должен объявлять временную анонимную очередь (`channel.QueueDeclare("", false, true, true...)`) и связывать её с exchange. Убедитесь, что одно отправленное продюсером событие дублируется в обе очереди и обрабатывается обоими сервисами параллельно.

## Теория

Архитектура маркетинговой платформы рассылок:
- Продюсер:
  - Публикует событие `marketing_events`: промокод на скидку 20%.
- Подписчики:
  - `EmailService`: при старте объявляет анонимную очередь `QueueDeclare("", false, true, true)`.
  - `PushService`: аналогично объявляет свою независимую анонимную очередь.
- Fanout дублирует событие в обе очереди:
  - Пользователь получает и пуш на смартфон, и письмо на почту одновременно.

## Решение по шагам

1. Создайте структуру Fanout обменника маркетинговых событий.
2. Подключите Email и Push сервисы с временными очередями.
3. Опубликуйте маркетинговое событие.
4. Убедитесь в параллельной доставке обоим сервисам.

## Код решения

**`marketing_fanout_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type MarketingServiceSubscriber struct {
	ServiceName string
	Inbox       chan string
}

func TestMarketingFanoutPattern(t *testing.T) {
	subEmail := &MarketingServiceSubscriber{ServiceName: "EmailSender", Inbox: make(chan string, 1)}
	subPush := &MarketingServiceSubscriber{ServiceName: "PushNotifier", Inbox: make(chan string, 1)}

	subscribers := []*MarketingServiceSubscriber{subEmail, subPush}

	promoEvent := `{"promo": "SPRING2026", "discount_pct": 20}`

	// Публикация в marketing_events fanout exchange
	for _, sub := range subscribers {
		sub.Inbox <- promoEvent
	}

	var wg sync.WaitGroup
	results := make(map[string]string)
	var mu sync.Mutex

	for _, sub := range subscribers {
		wg.Add(1)
		go func(s *MarketingServiceSubscriber) {
			defer wg.Done()
			msg := <-s.Inbox
			mu.Lock()
			results[s.ServiceName] = msg
			mu.Unlock()
		}(sub)
	}

	wg.Wait()

	if len(results) != 2 || results["EmailSender"] != promoEvent || results["PushNotifier"] != promoEvent {
		t.Fatalf("Сбой доставки: %+v", results)
	}

	fmt.Println("Маркетинговый Fanout Exchange успешно выполнил параллельную рассылку:")
	fmt.Printf("  • EmailSender  получил: %s\n", results["EmailSender"])
	fmt.Printf("  • PushNotifier получил: %s\n", results["PushNotifier"])
}
```

ℹ️ Параллельная доставка маркетингового события в независимые временные очереди

## Под капотом

Анонимная очередь со случайным именем удаляется сервером автоматически, как только сервис завершает работу (`autoDelete: true`), предотвращая утечки ресурсов в кластере.

## Подводные камни

Использовать анонимную временную очередь для критичных заказов: при падении сервиса все недообработанные заказы испарятся вместе с очередью.

## На собеседовании

**Вопрос с собеседования:** «Как обеспечить масштабирование одного из подписчиков Fanout Exchange (например, поднять 5 реплик PushService)?»
**Ответ:** Все 5 реплик `PushService` должны подключаться к **одной и той же именованной очереди** `marketing_push_queue`, привязанной к Fanout Exchange. Тогда Fanout отдаст одно сообщение в `marketing_push_queue`, а 5 реплик разберут задачи между собой по Round-Robin.
