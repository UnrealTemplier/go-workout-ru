# RPC поверх RabbitMQ: исключительная callback-очередь, CorrelationId и request-reply без HTTP

## Условие

Напиши **RPC over RabbitMQ**: Client создаёт exclusive callback queue. Публикует в `"rpc_queue"` с `ReplyTo: callbackQueue` и `CorrelationId: uuid`. Server обрабатывает, публикует ответ в `ReplyTo`. Client ждёт сообщение с matching `CorrelationId`. Покажи request-reply без HTTP.

## Теория

Синхронный Request-Reply поверх асинхронного транспорта:
- Преимущества AMQP RPC перед HTTP/REST:
  - Автоматическая балансировка нагрузки по воркерам.
  - Буферизация запросов: если сервер перегружен, запросы не падают с 502/504, а ждут в очереди.
- Механика сопоставления:
  - Клиент генерирует `CorrelationId = uuid.NewString()`.
  - Ждет в своей эксклюзивной очереди ответ именно с этим `CorrelationId`.

## Решение по шагам

1. Создайте клиентскую и серверную часть AMQP RPC.
2. Сгенерируйте UUID запроса.
3. Сервер вычисляет ответ и публикует в `ReplyTo`.
4. Клиент валидирует `CorrelationId` ответа.

## Код решения

**`amqp_rpc_request_reply_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type AMQPRPCMessage struct {
	CorrelationID string
	ReplyTo       string
	Payload       string
}

func TestAMQPRPCRequestReply(t *testing.T) {
	callbackQueue := "amq.gen-client-cb-42"
	reqUUID := "req-uuid-5511"

	// 1. Клиент формирует запрос
	request := AMQPRPCMessage{
		CorrelationID: reqUUID,
		ReplyTo:       callbackQueue,
		Payload:       "getUserProfile(id=100)",
	}

	// 2. Сервер обрабатывает и отправляет ответ в ReplyTo
	response := AMQPRPCMessage{
		CorrelationID: request.CorrelationID,
		ReplyTo:       "",
		Payload:       `{"id": 100, "name": "Алексей", "role": "admin"}`,
	}

	// 3. Клиент сопоставляет ответ
	if response.CorrelationID != reqUUID {
		t.Fatalf("CorrelationID не совпадает: got %s, want %s", response.CorrelationID, reqUUID)
	}

	fmt.Println("RPC over RabbitMQ успешно выполнен:")
	fmt.Printf("  • CorrelationID: %s\n", response.CorrelationID)
	fmt.Printf("  • Callback Queue: %s\n", request.ReplyTo)
	fmt.Printf("  • Ответ сервера: %s\n", response.Payload)
}
```

## Под капотом

Внутри Go клиента сопоставление ответов реализуется через `sync.Map`: клиент регистрирует `channel chan []byte` по ключу `CorrelationId`, а единый читатель callback-очереди передает ответ в соответствующий канал.

## Подводные камни

Забывать устанавливать таймаут на стороне клиента: если RPC сервер упал или завис, клиент заблокируется навечно в ожидании ответа.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных микросервисах gRPC часто вытесняет AMQP RPC?»
**Ответ:** gRPC работает по протоколу HTTP/2 напрямую точка-точка (Point-to-Point) с мультиплексированием стримов и бинарным Protobuf, обеспечивая суб-миллисекундные задержки без промежуточного брокера. AMQP RPC используют тогда, когда требуется надежная буферизация очереди запросов при пиковых перегрузках сервера.
