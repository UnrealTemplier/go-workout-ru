# Сквозная изоляция сбоев: аргументы x-dead-letter-exchange и x-dead-letter-routing-key

## Условие

Реализуй **Dead Letter Exchange (DLX)**: Queue args: `amqp.Table{"x-dead-letter-exchange": "orders.dlx", "x-dead-letter-routing-key": "failed"}`. При `Nack(false, false)` или message TTL expired — сообщение идёт в DLX. Consumer DLX обрабатывает/логирует/alert'ит.

## Теория

Точная маршрутизация мертвых писем:
- Аргументы очереди:
  - `x-dead-letter-exchange: "orders.dlx"`
  - `x-dead-letter-routing-key: "failed"`
- Когда сообщение отбрасывается:
  - RabbitMQ подменяет оригинальный `routing_key` на указанный `x-dead-letter-routing-key` (`"failed"`).
  - Направляет сообщение в обменник `orders.dlx`.
  - Отдельный консьюмер DLQ сохраняет полезную нагрузку в PostgreSQL для ручного аудита и отсылает алерт в Telegram/Slack.

## Решение по шагам

1. Создайте структуру аргументов DLX очереди.
2. Проверьте обязательные ключи `x-dead-letter-exchange` и `x-dead-letter-routing-key`.
3. Смоделируйте перенаправление упавшего сообщения в DLQ.
4. Проверьте получение сообщения консьюмером DLQ.

## Код решения

**`dlx_routed_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DLQConfig struct {
	DLXName       string
	DLQRoutingKey string
}

func (c DLQConfig) ToTable() map[string]any {
	return map[string]any{
		"x-dead-letter-exchange":    c.DLXName,
		"x-dead-letter-routing-key": c.DLQRoutingKey,
	}
}

func TestDLXRoutedQueue(t *testing.T) {
	cfg := DLQConfig{
		DLXName:       "orders.dlx",
		DLQRoutingKey: "failed",
	}

	table := cfg.ToTable()

	if table["x-dead-letter-exchange"] != "orders.dlx" || table["x-dead-letter-routing-key"] != "failed" {
		t.Fatalf("Некорректная таблица аргументов: %+v", table)
	}

	fmt.Println("Конфигурация DLX очереди успешно сформирована:")
	fmt.Printf("  • x-dead-letter-exchange:    %v\n", table["x-dead-letter-exchange"])
	fmt.Printf("  • x-dead-letter-routing-key: %v\n", table["x-dead-letter-routing-key"])
}
```

## Под капотом

Если параметр `x-dead-letter-routing-key` опущен, брокер сохраняет исходный routing key, с которым сообщение было изначально опубликовано в систему.

## Подводные камни

Забыть объявить сам обменник `orders.dlx` и привязать к нему очередь `orders.dlq`: если целевого обменника или очереди нет, dead-lettered сообщение будет окончательно уничтожено.

## На собеседовании

**Вопрос с собеседования:** «Какую метаинформацию RabbitMQ записывает в заголовок x-death?»
**Ответ:** Заголовок `x-death` содержит массив структур: `queue` (имя исходной очереди), `reason` (`rejected`, `expired`, `maxlen`), `time` (таймстамп сбоя), `exchange` (исходный обменник), `routing-keys` и `count` (сколько раз сообщение проходило через DLX).
