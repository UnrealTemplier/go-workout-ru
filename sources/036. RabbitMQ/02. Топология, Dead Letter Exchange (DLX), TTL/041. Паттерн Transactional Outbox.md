# Паттерн Transactional Outbox: атомарность транзакции в БД и фоновая публикация в RabbitMQ

## Условие

Реализуй **Transaction Outbox с RabbitMQ**: PostgreSQL транзакция: `INSERT INTO outbox ...`. Poller: `SELECT * FROM outbox`, `ch.Publish`, `DELETE FROM outbox`. Покажи, что outbox гарантирует at-least-once (если publish fail — retry, если publish success + delete fail — duplicate, consumer идемпотентен).

## Теория

Решение проблемы двойной записи (Dual Write Problem):
- Нельзя в одном HTTP-хендлере делать `db.Exec(INSERT)` и `ch.Publish()`: если БД закоммитилась, а RabbitMQ упал (или наоборот), возникнет рассинхронизация данных.
- **Паттерн Transactional Outbox:**
  1. В единой локальной ACID транзакции БД:
     - Сохраняются бизнес-данные (`orders`).
     - Записывается событие в таблицу `outbox_events` со статусом `PENDING`.
  2. Фоновый процесс (Outbox Poller / Debezium CDC):
     - Читает события из `outbox_events`.
     - Публикует в RabbitMQ с Publisher Confirms.
     - После подтверждения удаляет или помечает запись как `SENT`.
- Гарантирует At-Least-Once публикацию без потери данных.

## Решение по шагам

1. Создайте структуры таблицы `outbox_events`.
2. Реализуйте атомарное сохранение бизнес-сущности и outbox-записи.
3. Смоделируйте фоновый воркер опроса и публикации.
4. Проверьте гарантированную доставку при сбое сети.

## Код решения

**`transactional_outbox_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type OutboxRecord struct {
	ID        int
	Aggregate string
	Payload   string
	Sent      bool
}

type SimulatedDB struct {
	mu     sync.Mutex
	outbox []*OutboxRecord
}

func (db *SimulatedDB) CreateOrderWithOutbox(orderID int, payload string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	// В одной ACID транзакции!
	rec := &OutboxRecord{
		ID:        len(db.outbox) + 1,
		Aggregate: fmt.Sprintf("order-%d", orderID),
		Payload:   payload,
		Sent:      false,
	}
	db.outbox = append(db.outbox, rec)
}

func (db *SimulatedDB) PollAndPublish(publishFn func(rec *OutboxRecord) bool) int {
	db.mu.Lock()
	defer db.mu.Unlock()

	sentCount := 0
	for _, rec := range db.outbox {
		if !rec.Sent {
			if publishFn(rec) {
				rec.Sent = true
				sentCount++
			}
		}
	}
	return sentCount
}

func TestTransactionalOutboxPattern(t *testing.T) {
	db := &SimulatedDB{}

	// 1. Создаем заказ в базе данных
	db.CreateOrderWithOutbox(101, `{"status": "CREATED", "total": 2500}`)

	// 2. Фоновый воркер публикует запись в брокер
	published := db.PollAndPublish(func(rec *OutboxRecord) bool {
		// Публикация в RabbitMQ с подтверждением
		return true
	})

	if published != 1 {
		t.Fatalf("Ожидалась публикация 1 записи, опубликовано: %d", published)
	}

	fmt.Println("Transactional Outbox успешно гарантировал атомарность:")
	fmt.Printf("  • Событие сохранено в БД в одной транзакции с заказом\n")
	fmt.Printf("  • Фоновый поллер успешно опубликовал событие в RabbitMQ (Sent=%v)!\n", db.outbox[0].Sent)
}
```

## Под капотом

В современных HighLoad сервисах вместо `SELECT FOR UPDATE SKIP LOCKED` таблицы outbox используют Change Data Capture (CDC): Debezium читает журнал WAL (Write-Ahead Log) PostgreSQL и транслирует изменения в брокер с околонулевой задержкой.

## Подводные камни

Удалять строки из таблицы outbox синхронно по одной: это вызывает фрагментацию и разрастание (Bloat) таблиц в PostgreSQL. Рекомендуется пачковое удаление `DELETE ... WHERE id IN (...)` или партиционирование.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если Outbox Poller опубликовал сообщение в RabbitMQ, но упал до фиксации DELETE в базе данных?»
**Ответ:** При перезапуске поллер вычитает ту же запись снова и повторно опубликует сообщение в RabbitMQ (дубликат). Именно поэтому консьюмер сообщений обязан быть идемпотентным (дедупликация по ключу `message_id`).
