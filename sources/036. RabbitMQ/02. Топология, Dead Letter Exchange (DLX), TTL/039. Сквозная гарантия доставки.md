# Сквозная гарантия доставки: Publisher Confirms в связке с идемпотентным консьюмером

## Условие

Реализуй **Publisher Confirms**: `ch.Confirm(false)`, `confirms := ch.NotifyPublish(make(chan amqp.Confirmation, 1))`. После `Publish` жди `<-confirms`, проверь `ack.DeliveryTag`. Покажи exactly-once publishing (с idempotent consumer).

## Теория

Достижение Exactly-Once обработки через At-Least-Once транспорт + Идемпотентность:
- 100% гарантия доставки (At-Least-Once):
  - Продюсер шлет сообщение с уникальным UUID `message_id`.
  - Ждет подтверждения брокера через Publisher Confirms.
  - При сбое сети продюсер повторяет отправку (возможен дубликат).
- Идемпотентный консьюмер (Deduplication):
  - Перед обработкой проверяет `SETNX processed_messages:<uuid>` в Redis или уникальный индекс в PostgreSQL.
  - Если ключ уже существует \(\to\) сразу отправляет `Ack` без повторного выполнения бизнес-логики!

## Решение по шагам

1. Создайте продюсера с Publisher Confirms.
2. Создайте идемпотентного консьюмера с дедупликацией по UUID.
3. Отправьте исходное сообщение и его дубликат.
4. Проверьте, что бизнес-действие выполнилось строго один раз.

## Код решения

**`publisher_confirms_idempotency_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type IdempotentConsumer struct {
	mu           sync.Mutex
	processedIDs map[string]bool
	ordersCount  int
}

func (c *IdempotentConsumer) HandleMessage(msgID string) (isDuplicate bool) {
	c.mu.Lock()
	defer c.mu.Unlock()

	if c.processedIDs[msgID] {
		// Дубликат: игнорируем бизнес-логику, но подтверждаем брокеру!
		return true
	}

	c.processedIDs[msgID] = true
	c.ordersCount++
	return false
}

func TestPublisherConfirmsAndIdempotency(t *testing.T) {
	consumer := &IdempotentConsumer{processedIDs: make(map[string]bool)}

	msgUUID := "msg-uuid-9901"

	// 1. Первая доставка
	dup1 := consumer.HandleMessage(msgUUID)
	if dup1 {
		t.Fatal("Первая доставка не должна считаться дубликатом")
	}

	// 2. Повторная доставка из-за ретрая продюсера
	dup2 := consumer.HandleMessage(msgUUID)
	if !dup2 {
		t.Fatal("Вторая доставка должна быть распознана как дубликат")
	}

	if consumer.ordersCount != 1 {
		t.Fatalf("Бизнес-логика должна была выполниться ровно 1 раз, выполнено: %d", consumer.ordersCount)
	}

	fmt.Println("Связка Publisher Confirms + Идемпотентный консьюмер успешна:")
	fmt.Printf("  • Первая доставка: успешно обработана\n")
	fmt.Printf("  • Вторая доставка: распознана как дубликат и отфильтрована!\n")
	fmt.Printf("  • Итоговый счетчик бизнес-операций: %d (Exactly-Once семантика!)\n", consumer.ordersCount)
}
```

## Под капотом

В распределенных системах математически невозможно реализовать чистый Exactly-Once на физическом сетевом уровне (Two Generals Problem). Семантика Exactly-Once всегда достигается комбинацией At-Least-Once доставки и идемпотентного хранилища.

## Подводные камни

Хранить список обработанных ID в памяти процесса: при перезапуске пода кэш очистится, и дубликаты повторно применятся к базе данных. Реестр должен храниться в Redis или БД с TTL.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать идемпотентность в реляционной базе данных PostgreSQL?»
**Ответ:** 1. Использовать `INSERT INTO orders (...) ON CONFLICT (message_id) DO NOTHING`. 2. Либо сохранять `message_id` в отдельную таблицу `processed_messages (message_id PRIMARY KEY, processed_at)` в рамках единой ACID транзакции с бизнес-данными.
