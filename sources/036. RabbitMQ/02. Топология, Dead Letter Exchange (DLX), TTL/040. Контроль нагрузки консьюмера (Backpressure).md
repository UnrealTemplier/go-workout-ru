# Контроль нагрузки консьюмера (Backpressure): prefetchCount=10 и защита от Out Of Memory

## Условие

**Контроль нагрузки консьюмера (Prefetch Limit / Backpressure)**: По умолчанию RabbitMQ пытается вывалить в память консьюмера все сообщения из очереди сразу, что может привести к OOM (Out Of Memory) падению процесса. Настройте ограничение `channel.Qos(prefetchCount=10, prefetchSize=0, global=false)`. Объясните в комментариях, как этот лимит (ограничивающий количество одновременно обрабатываемых, но еще не подтвержденных воркером сообщений) реализует паттерн Backpressure в продакшене.

## Теория

Паттерн Backpressure через Prefetch Limit:
- Проблема без Backpressure:
  - В очереди накопилось 500 000 сообщений.
  - Запускается под воркера. RabbitMQ пытается залить все 500 000 сообщений в TCP-сокет клиента за несколько секунд.
  - Потребление RAM взлетает с 20 МБ до 4 ГБ. Linux OOM-killer убивает процесс.
- Решение: `ch.Qos(10, 0, false)`:
  - Воркер единовременно держит в памяти не более 10 сообщений.
  - Новые сообщения выдаются только по мере освобождения слотов после вызова `Ack`.
  - Потребление памяти строго фиксировано и предсказуемо.

## Решение по шагам

1. Создайте модель ограничителя обратного давления (Backpressure Limiter).
2. Задайте лимит `prefetchCount = 10`.
3. Смоделируйте поступление 50 задач.
4. Убедитесь, что в памяти находится строго не более 10 задач одновременно.

## Код решения

**`backpressure_prefetch_limit_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BackpressureLimiter struct {
	limit       int
	inFlightMsg int
}

func (l *BackpressureLimiter) OnMessageDelivered() bool {
	if l.inFlightMsg >= l.limit {
		return false // Брокер останавливает подачу сообщений (Backpressure!)
	}
	l.inFlightMsg++
	return true
}

func (l *BackpressureLimiter) OnMessageAcked() {
	if l.inFlightMsg > 0 {
		l.inFlightMsg--
	}
}

func TestBackpressurePrefetchLimit(t *testing.T) {
	limiter := &BackpressureLimiter{limit: 10}

	// 1. Подаем 10 сообщений -> все приняты
	for i := 1; i <= 10; i++ {
		ok := limiter.OnMessageDelivered()
		if !ok {
			t.Fatalf("Сообщение #%d должно было пройти в лимит", i)
		}
	}

	// 2. Попытка 11-го сообщения -> срабатывает Backpressure
	if limiter.OnMessageDelivered() {
		t.Fatal("11-е сообщение должно быть заблокировано лимитом QoS")
	}

	// 3. Подтверждаем одно сообщение (Ack)
	limiter.OnMessageAcked()

	// 4. Теперь можно принять следующее сообщение
	if !limiter.OnMessageDelivered() {
		t.Fatal("После Ack лимит должен освободить слот")
	}

	fmt.Println("Контроль нагрузки (Backpressure / QoS=10) успешно защитил память:")
	fmt.Printf("  • Максимум сообщений в памяти: %d\n", limiter.limit)
	fmt.Println("  • Поток данных регулируется скоростью воркера (Zero OOM)!")
}
```

ℹ️ Реализация паттерна Backpressure через лимит неподтвержденных сообщений

## Под капотом

AMQP 0-9-1 кредит-система: при `Qos(10)` брокер выделяет консьюмеру 10 кредитов. Каждый `basic.deliver` уменьшает кредит на 1, а каждый `basic.ack` возвращает 1 кредит. При нулевом балансе отправка блокируется.

## Подводные камни

Вызывать `ch.Consume()` до настройки `ch.Qos()`: первые сотни сообщений успеют пролететь в сокет до применения ограничения.

## На собеседовании

**Вопрос с собеседования:** «Как Backpressure в RabbitMQ влияет на здоровье других микросервисов в кластере?»
**Ответ:** Если воркер обрабатывает задачи медленно, сообщения остаются в очереди брокера, а не перегружают оперативную память воркера. При достижении пределов брокер RabbitMQ начинает притормаживать продюсеров (TCP Socket Throttling / Flow Control), распространяя обратное давление по всей цепочке системы.
