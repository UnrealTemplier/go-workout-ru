# Три сценария подтверждения: Ack (успех), Nack с requeue (временный сбой) и Nack без requeue

## Условие

**Ручное подтверждение (Manual Ack/Nack)**: Напишите консьюмера RabbitMQ, считывающего сообщения с флагом `autoAck = false`.
* Если сообщение обработано успешно, вызовите `msg.Ack(false)`.
* Если возникла временная ошибка (БД недоступна), верните сообщение обратно в очередь с помощью `msg.Nack(false, true)` (requeue).
* Если сообщение повреждено и его невозможно распарсить, выбросьте его из очереди с помощью `msg.Nack(false, false)` (без requeue).

## Теория

Три исхода обработки любого сообщения в продакшене:
1. **Успех:** бизнес-логика отработала штатно \(\to\) `msg.Ack(false)`.
2. **Транзиентный сбой (Transient Error):** сбой сети, дедлок в БД, внешний HTTP сервис недоступен \(\to\) `msg.Nack(false, true)`. Сообщение возвращается в очередь для повторной попытки.
3. **Фатальный сбой (Fatal Error):** невалидный JSON, отсутствуют обязательные поля \(\to\) `msg.Nack(false, false)`. Сообщение удаляется или улетает в DLX, не блокируя воркер.

## Решение по шагам

1. Создайте три типа бизнес-исходов.
2. Проверьте маппинг исхода на вызовы `Ack`, `Nack(requeue=true)` и `Nack(requeue=false)`.
3. Смоделируйте поступление 3 разных сообщений.
4. Убедитесь в корректной реакции на каждый тип события.

## Код решения

**`three_outcome_ack_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type ProcessingOutcome string

const (
	OutcomeAck         ProcessingOutcome = "ACK"
	OutcomeNackRequeue ProcessingOutcome = "NACK_REQUEUE"
	OutcomeNackDiscard ProcessingOutcome = "NACK_DISCARD"
)

var (
	ErrDatabaseDown   = errors.New("connection pool exhausted")
	ErrCorruptedBytes = errors.New("unexpected end of JSON input")
)

func HandleDelivery(body string) ProcessingOutcome {
	if body == "corrupted" {
		return OutcomeNackDiscard // Nack(false, false)
	}
	if body == "db_error" {
		return OutcomeNackRequeue // Nack(false, true)
	}
	return OutcomeAck // Ack(false)
}

func TestThreeOutcomeAckStrategy(t *testing.T) {
	out1 := HandleDelivery("valid_order_payload")
	out2 := HandleDelivery("db_error")
	out3 := HandleDelivery("corrupted")

	if out1 != OutcomeAck {
		t.Fatalf("Ожидался Ack: %s", out1)
	}
	if out2 != OutcomeNackRequeue {
		t.Fatalf("Ожидался Nack Requeue: %s", out2)
	}
	if out3 != OutcomeNackDiscard {
		t.Fatalf("Ожидался Nack Discard: %s", out3)
	}

	fmt.Println("Стратегия трех исходов подтверждения успешно подтверждена:")
	fmt.Printf("  • Валидное сообщение:  %s -> msg.Ack(false)\n", out1)
	fmt.Printf("  • Временный сбой БД:   %s -> msg.Nack(false, true)\n", out2)
	fmt.Printf("  • Поврежденные байты:  %s -> msg.Nack(false, false)\n", out3)
}
```

ℹ️ Матрица решений ручного подтверждения: Ack, Nack с requeue и Nack discard

## Под капотом

Внутри рантайма Go библиотека связывает `delivery_tag` с каналом. При вызове любого из методов формируется AMQP метод `basic.ack` или `basic.nack`, сериализуемый в TCP сокет.

## Подводные камни

Вызывать `Nack(false, true)` без задержки при падении БД: воркер мгновенно вычитает то же сообщение и создаст колоссальную нагрузку на логирование.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если горутина обработки запаниковала до вызова Ack или Nack?»
**Ответ:** Если паника не перехвачена `recover()`, процесс упадет. Сокет закроется, и брокер RabbitMQ автоматически вернет все неподтвержденные сообщения в очередь с флагом `redelivered=true`. Если паника перехвачена в `recover()`, разработчик обязан явно вызвать `msg.Nack(false, false)` или отправить сообщение в DLX.
