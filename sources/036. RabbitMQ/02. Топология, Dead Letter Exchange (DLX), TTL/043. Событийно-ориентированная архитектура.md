# Событийно-ориентированная архитектура (Event-Driven Microservices): слабая связанность через Fanout

## Условие

Напиши **Event-driven microservices с RabbitMQ**: `UserService` публикует `UserCreated` в `"events.user.created"`. `NotificationService` и `AnalyticsService` — отдельные queues, bound to fanout exchange `"events"`. Покажи decoupling: добавь `AuditService` без изменения `UserService`.

## Теория

Принцип открытости/закрытости (Open/Closed Principle) в архитектуре микросервисов:
- `UserService` не знает, кто слушает событие `UserCreated`.
- Добавление нового потребителя `AuditService`:
  1. Создается новая очередь `audit_service_queue`.
  2. Привязывается к существующему обменнику `events`.
  3. `UserService` не требует ни единой строчки правок кода и не перезагружается!
- Полная автономность и независимость релизных циклов команд.

## Решение по шагам

1. Создайте обменник `events`.
2. Подключите исходные сервисы `NotificationService` и `AnalyticsService`.
3. Опубликуйте событие создания пользователя.
4. Динамически подключите `AuditService` и убедитесь в получении события всеми тремя сервисами.

## Код решения

**`event_driven_decoupling_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type EventDrivenBus struct {
	subscribers map[string]chan string
}

func NewEventDrivenBus() *EventDrivenBus {
	return &EventDrivenBus{subscribers: make(map[string]chan string)}
}

func (b *EventDrivenBus) RegisterService(serviceName string) <-chan string {
	ch := make(chan string, 5)
	b.subscribers[serviceName] = ch
	return ch
}

func (b *EventDrivenBus) PublishUserCreated(event string) {
	for _, ch := range b.subscribers {
		ch <- event
	}
}

func TestEventDrivenDecoupling(t *testing.T) {
	bus := NewEventDrivenBus()

	// 1. Исходные сервисы
	notifCh := bus.RegisterService("NotificationService")
	analyticsCh := bus.RegisterService("AnalyticsService")

	// 2. Новый сервис подключается без изменения издателя!
	auditCh := bus.RegisterService("AuditService")

	eventPayload := `{"user_id": 404, "email": "dev@yandex.ru", "event": "UserCreated"}`
	bus.PublishUserCreated(eventPayload)

	m1 := <-notifCh
	m2 := <-analyticsCh
	m3 := <-auditCh

	if m1 != eventPayload || m2 != eventPayload || m3 != eventPayload {
		t.Fatal("Все сервисы должны получить одинаковое событие")
	}

	fmt.Println("Event-Driven слабая связанность успешно продемонстрирована:")
	fmt.Printf("  • NotificationService получил: %s\n", m1)
	fmt.Printf("  • AnalyticsService    получил: %s\n", m2)
	fmt.Printf("  • Новый AuditService  получил: %s (без правок UserService!)\n", m3)
}
```

ℹ️ Слабая связанность микросервисов: добавление нового подписчика без изменения издателя

## Под капотом

Такая схема реализует паттерн Smart Endpoints and Dumb Pipes (Умные эндпоинты, глупая труба): брокер не знает о бизнес-логике микросервисов, а просто реплицирует байты по подпискам.

## Подводные камни

Использовать один routing key для абсолютно разных доменных событий: разделяйте события по типам для удобства селективной фильтрации.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие хореографии событий (Choreography) от оркестрации (Orchestration)?»
**Ответ:** При оркестрации есть единый сервис-координатор (Orchestrator), который напрямую командует сервисам, что делать (Request-Reply). При хореографии сервисы реагируют на события брокера автономно (Event-Driven), не зная о существовании друг друга, что обеспечивает максимальную масштабируемость.
