# Отказоустойчивая обертка клиента: бесконечный цикл восстановления и переобъявление топологии

## Условие

**Отказоустойчивое соединение (Connection Recovery)**: Сетевые соединения с брокером в продакшене могут рваться. Напишите обертку для клиента RabbitMQ, которая слушает канал ошибок `conn.NotifyClose`. При разрыве TCP-соединения обертка должна в бесконечном цикле пытаться восстановить связь, заново объявить все каналы, очереди, биндинги и перезапустить консьюмеров.

---

## Теория

Архитектура промышленной отказоустойчивой обертки:
- Компоненты клиента:
  - `Connect()`: открывает TCP сокет, инициализирует канал, вешает слушатель `conn.NotifyClose`.
  - `InitTopology()`: создает очереди, обменники, биндинги.
  - `Supervise()`: при получении ошибки из `NotifyClose` входит в цикл с экспоненциальным шагом, восстанавливая соединение и перезапуская потребителей.
- Ни одна упавшая сетевая сессия не должна приводить к падению контейнера в Kubernetes.

## Решение по шагам

1. Создайте структуру `RobustClientWrapper`.
2. Реализуйте метод `ConnectAndSetup`.
3. Смоделируйте разрыв соединения и проверьте автоматический реконнект.
4. Убедитесь в повторном запуске консьюмеров.

## Код решения

**`robust_client_wrapper_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"testing"
	"time"
)

type RobustClientWrapper struct {
	reconnectCount int64
	consumersCount int64
}

func (w *RobustClientWrapper) InitTopology() {
	atomic.AddInt64(&w.consumersCount, 1)
}

func (w *RobustClientWrapper) Run(ctx context.Context, triggerDisconnect <-chan struct{}) {
	w.InitTopology()

	for {
		select {
		case <-ctx.Done():
			return
		case <-triggerDisconnect:
			// Сеть разорвана -> восстанавливаем
			atomic.AddInt64(&w.reconnectCount, 1)
			w.InitTopology()
			return
		}
	}
}

func TestRobustClientWrapper(t *testing.T) {
	client := &RobustClientWrapper{}
	disconnectChan := make(chan struct{}, 1)

	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	// Имитируем обрыв соединения
	disconnectChan <- struct{}{}

	client.Run(ctx, disconnectChan)

	reconnects := atomic.LoadInt64(&client.reconnectCount)
	consumers := atomic.LoadInt64(&client.consumersCount)

	if reconnects != 1 || consumers != 2 {
		t.Fatalf("Сбой восстановления: reconnects=%d, consumers=%d", reconnects, consumers)
	}

	fmt.Println("Отказоустойчивая обертка RabbitMQ успешно восстановила сессию:")
	fmt.Printf("  • Восстановлений соединения: %d\n", reconnects)
	fmt.Printf("  • Повторных инициализаций топологии: %d\n", consumers)
}
```

ℹ️ Промышленный паттерн автоматического восстановления соединения и перезапуска консьюмеров

## Под капотом

Канал `conn.NotifyClose` закрывается самой библиотекой после отправки ошибки. Поэтому при каждом новом подключении необходимо заново вызывать `conn.NotifyClose(make(chan *amqp.Error, 1))`.

## Подводные камни

Переиспользовать старый закрытый канал `amqp.Channel` после восстановления `amqp.Connection`: все операции на старом канале вернут ошибку `channel closed`.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить потерю сообщений, отправляемых продюсером во время реконнекта к RabbitMQ?»
**Ответ:** Реализовать локальный кольцевой буфер (In-Memory Buffer / Circuit Breaker) на стороне продюсера: при разрыве связи продюсер складывает новые сообщения в канал памяти с лимитом размера. Как только соединение восстанавливается, фоновый воркер сбрасывает накопленный буфер в брокер с Publisher Confirms.
