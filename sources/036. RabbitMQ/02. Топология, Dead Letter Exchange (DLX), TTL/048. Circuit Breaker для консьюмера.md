# Circuit Breaker для консьюмера: остановка вычитки ch.Cancel при 5 ошибках подряд и прогрев

## Условие

Напиши **Circuit Breaker для RabbitMQ consumer'а**: если обработка 5 сообщений подряд падает — пауза 30 секунд (не consume). Потом пробный consume. Если успех — resume. Используй `ch.Cancel` + `time.Timer` + `ch.Consume`.

### Исходная формулировка

Напиши **Circuit Breaker для RabbitMQ consumer'а**: если обработка 5 сообщений подряд падает — пауза 30 секунд (не consume). Потом пробный consume. Если успех — resume. Используй `ch.Cancel` + `time.Timer` + `ch.Consume`.

## Теория

Паттерн Consumer Circuit Breaker:
- Если внешняя платежная система или база данных полностью легла:
  - Бесполезно продолжать вычитывать по 10 000 сообщений в секунду и забивать диск миллионами логов ошибок.
- **Состояния Circuit Breaker:**
  1. `CLOSED` (Норма): консьюмер активно вычитывает очередь.
  2. `OPEN` (Защита): при 5 ошибках подряд вызывается `ch.Cancel(consumerTag, false)` \(\to\) вычитка очереди прекращается. Запускается таймер паузы на 30 секунд.
  3. `HALF_OPEN` (Проверка): таймер истек \(\to\) запускается пробная вычитка. Если задача выполнена успешно \(\to\) переход в `CLOSED`.

## Решение по шагам

1. Создайте стейт-машину Circuit Breaker (`Closed`, `Open`, `HalfOpen`).
2. Настройте счетчик последовательных ошибок (порог = 5).
3. Смоделируйте срабатывание аварийной остановки при сбоях.
4. Протестируйте автоматическое восстановление после пробного запуска.

## Код решения

**`consumer_circuit_breaker_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CircuitState string

const (
	StateClosed   CircuitState = "CLOSED"
	StateOpen     CircuitState = "OPEN"
	StateHalfOpen CircuitState = "HALF_OPEN"
)

type ConsumerCircuitBreaker struct {
	State        CircuitState
	failureCount int
	threshold    int
}

func NewConsumerCircuitBreaker(threshold int) *ConsumerCircuitBreaker {
	return &ConsumerCircuitBreaker{
		State:     StateClosed,
		threshold: threshold,
	}
}

func (cb *ConsumerCircuitBreaker) OnFailure() {
	cb.failureCount++
	if cb.failureCount >= cb.threshold {
		cb.State = StateOpen
		fmt.Printf("  • Порог %d ошибок превышен! Circuit Breaker -> OPEN (вызов ch.Cancel)\n", cb.threshold)
	}
}

func (cb *ConsumerCircuitBreaker) OnSuccess() {
	cb.failureCount = 0
	cb.State = StateClosed
	fmt.Println("  • Пробное сообщение успешно обработано! Circuit Breaker -> CLOSED (вычитка возобновлена)")
}

func TestConsumerCircuitBreaker(t *testing.T) {
	cb := NewConsumerCircuitBreaker(5)

	// Имитируем 5 сбоев подряд
	for i := 1; i <= 5; i++ {
		cb.OnFailure()
	}

	if cb.State != StateOpen {
		t.Fatalf("Circuit Breaker должен перейти в OPEN: %s", cb.State)
	}

	// Имитируем переход таймера в Half-Open
	cb.State = StateHalfOpen

	// Пробное сообщение завершилось успехом
	cb.OnSuccess()

	if cb.State != StateClosed {
		t.Fatalf("Circuit Breaker должен вернуться в CLOSED: %s", cb.State)
	}

	fmt.Println("Consumer Circuit Breaker успешно защитил систему от каскадного сбоя!")
}
```

## Под капотом

Вызов `ch.Cancel(consumerTag, false)` корректно останавливает доставку новых сообщений от брокера, позволяя воркеру спокойно дообработать текущие ин-флайт сообщения и дать внешней системе время восстановиться.

## Подводные камни

Убивать весь процесс воркера при сбое внешнего сервиса: Kubernetes начнет циклически перезапускать контейнер (CrashLoopBackOff), создавая ложные алерты.

## На собеседовании

**Вопрос с собеседования:** «Почему паттерн Circuit Breaker на консьюмере брокера очередей отличается от Circuit Breaker на HTTP клиенте?»
**Ответ:** На HTTP клиенте Circuit Breaker сразу возвращает ошибку (Fast Fail) пользователю. На консьюмере брокера Circuit Breaker приостанавливает вычитку сообщений из очереди (`ch.Cancel`), позволяя сообщениям безопасно накапливаться в RabbitMQ до восстановления базы данных, исключая потерю данных.
