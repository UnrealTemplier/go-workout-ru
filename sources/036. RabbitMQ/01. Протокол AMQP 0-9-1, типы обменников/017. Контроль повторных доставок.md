# Контроль повторных доставок: заголовок redelivery count и изоляция в DLX через reject(false)

## Условие

Обработайте повторную доставку: консюмер проверяет заголовок `x-redelivered-count`, и если превышен порог, отправляет сообщение в Dead Letter Queue (DLX) с помощью `reject(false)`.

## Теория

Защита от бесконечного цикла повторов:
- При повторной доставке RabbitMQ устанавливает флаг `msg.Redelivered = true`.
- В кворум-очередях (Quorum Queues) брокер также проставляет заголовок `x-delivery-count` (число попыток).
- Логика консьюмера:
  - Если `deliveryCount > maxAttempts`:
    - Логируем критический алерт.
    - Вызываем `channel.Reject(deliveryTag, false)` (`requeue: false`).
    - Сообщение уходит в DLQ для разбора инженерами.

## Решение по шагам

1. Создайте валидатор счетчика доставок `DeliveryCounter`.
2. Задайте максимальный порог попыток (например, 3).
3. Смоделируйте поступление сообщения с превышенным порогом.
4. Убедитесь в вызове `reject(false)` и отправке в DLX.

## Код решения

**`redelivered_count_guard_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type GuardedMessage struct {
	ID            string
	DeliveryCount int
}

func ProcessGuardedMessage(msg GuardedMessage, maxRetries int) (isRejectedToDLQ bool) {
	if msg.DeliveryCount > maxRetries {
		// Превышен порог -> reject(false) -> отправка в DLX
		return true
	}
	return false
}

func TestRedeliveredCountGuard(t *testing.T) {
	const maxRetries = 3

	msgNormal := GuardedMessage{ID: "ord-1", DeliveryCount: 2}
	msgPoison := GuardedMessage{ID: "ord-2", DeliveryCount: 4}

	if ProcessGuardedMessage(msgNormal, maxRetries) {
		t.Fatal("Сообщение с 2 попытками не должно быть отклонено в DLQ")
	}

	if !ProcessGuardedMessage(msgPoison, maxRetries) {
		t.Fatal("Сообщение с 4 попытками должно быть отправлено в DLQ через reject(false)")
	}

	fmt.Println("Контроль повторных доставок (x-delivery-count) успешно защитил очередь:")
	fmt.Printf("  • Доставка #2: штатная обработка\n")
	fmt.Printf("  • Доставка #4: порог %d превышен -> вызов channel.Reject(false) -> DLX!\n", maxRetries)
}
```

## Под капотом

Заголовок `x-delivery-count` поддерживается современными Quorum Queues на основе алгоритма Raft, исключая потерю счетчика даже при аварийном рестарте нод кластера.

## Подводные камни

Полагаться на хранение счетчика в памяти самого консьюмера: если контейнер консьюмера упадет по OOM, локальный счетчик обнулится, и цикл повторов начнется заново.

## На собеседовании

**Вопрос с собеседования:** «Почему в классических очередях (Classic Queues) нет заголовка x-delivery-count, а есть только булев флаг Redelivered?»
**Ответ:** В классических очередях сохранение точного счетчика на каждую попытку доставки требовало бы синхронной записи на диск (fsync) при каждом сбое, что обрушило бы пропускную способность брокера. В Quorum Queues это решено благодаря консенсусу Raft и оптимизированному журналу WAL.
