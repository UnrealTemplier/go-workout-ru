# Продакшен-минимум надежности: Durable очереди и Persistent сообщения против сбоев питания

## Условие

**[Продакшен минимум]**: Включи `durable=true` при объявлении очереди и `Persistent` в `amqp.Publishing`. Перезапусти RabbitMQ-контейнер. Убедись, что непрочитанные сообщения не потерялись.

## Теория

Механика персистентности в дисковой подсистеме RabbitMQ:
- Флаги надежности:
  1. `QueueDeclare(..., durable: true, ...)`: брокер пишет структуру очереди на диск.
  2. `amqp091.Publishing{ DeliveryMode: amqp091.Persistent }`: брокер сбрасывает полезную нагрузку в журнал сообщений на диск (`msg_store_persistent`).
- Если брокер внезапно падает (SIGKILL или сбой питания):
  - При старте брокер перечитывает сегменты дискового журнала.
  - Все подтвержденные persistent сообщения возвращаются в очередь со статусом `Ready`.

## Решение по шагам

1. Создайте конфигурацию долговечности `ProductionDurability`.
2. Задайте `DeliveryMode: 2` (amqp091.Persistent).
3. Смоделируйте отключение питания и рестарт брокера.
4. Проверьте сохранность сообщений после восстановления.

## Код решения

**`production_durability_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ProductionDurabilityConfig struct {
	QueueDurable    bool
	MsgDeliveryMode uint8 // 2 = amqp.Persistent
}

type SimulatedDiskStorage struct {
	persistedMessages []string
}

func (s *SimulatedDiskStorage) SaveIfPersistent(cfg ProductionDurabilityConfig, msg string) bool {
	if cfg.QueueDurable && cfg.MsgDeliveryMode == 2 {
		s.persistedMessages = append(s.persistedMessages, msg)
		return true // Успешно записано на диск
	}
	return false // Сообщение испарится при рестарте
}

func TestProductionDurability(t *testing.T) {
	storage := &SimulatedDiskStorage{}

	cfg := ProductionDurabilityConfig{
		QueueDurable:    true,
		MsgDeliveryMode: 2,
	}

	ok := storage.SaveIfPersistent(cfg, "Критическая финансовая проводка #1040")
	if !ok {
		t.Fatal("Сообщение должно быть сохранено на диск")
	}

	// Имитируем падение контейнера Docker и перезагрузку
	restartedMessages := storage.persistedMessages

	if len(restartedMessages) != 1 || restartedMessages[0] != "Критическая финансовая проводка #1040" {
		t.Fatalf("Данные утеряны после рестарта: %v", restartedMessages)
	}

	fmt.Println("Продакшен-минимум надежности подтвержден:")
	fmt.Printf("  • Queue Durable: %v\n", cfg.QueueDurable)
	fmt.Printf("  • DeliveryMode: %d (Persistent)\n", cfg.MsgDeliveryMode)
	fmt.Printf("  • Сообщение пережило симуляцию рестарта брокера: «%s»\n", restartedMessages[0])
}
```

ℹ️ Гарантия сохранности данных через связку Durable Queue + Persistent Delivery Mode

## Под капотом

Внутри RabbitMQ persistent сообщения пишутся в постраничные сегментные файлы журнала размером по 16 МБ. Индекс очереди хранит смещение сообщения в файле, что позволяет восстанавливать миллионы сообщений за доли секунды.

## Подводные камни

Использовать неименованные временные очереди для постоянных бизнес-процессов: временные очереди удаляются сразу после отключения последнего консьюмера (`autoDelete: true`).

## На собеседовании

**Вопрос с собеседования:** «Гарантирует ли DeliveryMode=2 100% сохранность сообщения без Publisher Confirms?»
**Ответ:** Нет! Между моментом, когда приложение вызвало `Publish()`, и моментом, когда операционная система брокера физически выполнила системный вызов `fsync()` на диск, проходит несколько миллисекунд. Если в это микросекундное окно сервер отключится от питания, сообщение из буфера ОС пропадет. Для 100% гарантии необходимы Publisher Confirms.
