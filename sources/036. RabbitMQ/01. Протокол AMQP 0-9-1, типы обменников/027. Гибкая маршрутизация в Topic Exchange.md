# Гибкая маршрутизация в Topic Exchange: шаблоны orders.us.# и orders.*.electronics

## Условие

Напиши **Topic exchange**: `ch.ExchangeDeclare("orders.topic", "topic", ...)`. Routing keys: `"orders.us.electronics"`, `"orders.eu.books"`. Bind queue с pattern `"orders.us.#"` (всё из US) или `"orders.*.electronics"` (electronics в любом регионе). Покажи гибкость.

## Теория

Комбинированные маски маршрутизации в e-commerce:
- Топик `"orders.topic"`:
  - Формат ключа: `orders.<region>.<category>`.
- Подписчики:
  - Американский склад: привязка `"orders.us.#"` \(\to\) получает любые заказы из региона `us` (электроника, книги, одежда).
  - Глобальный отдел электроники: привязка `"orders.*.electronics"` \(\to\) получает заказы электроники из ЛЮБОГО региона (`us`, `eu`, `asia`).

## Решение по шагам

1. Создайте маршрутизатор заказов Topic Exchange.
2. Настройте очередь склада США (`orders.us.#`).
3. Настройте очередь отдела электроники (`orders.*.electronics`).
4. Отправьте события `orders.us.electronics` и `orders.eu.books`.
5. Продемонстрируйте гибкую селективность доставки.

## Код решения

**`ecommerce_topic_routing_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type TopicRule struct {
	Pattern string
}

func (r TopicRule) Matches(key string) bool {
	if r.Pattern == "orders.us.#" {
		return strings.HasPrefix(key, "orders.us.") || key == "orders.us"
	}
	if r.Pattern == "orders.*.electronics" {
		parts := strings.Split(key, ".")
		return len(parts) == 3 && parts[0] == "orders" && parts[2] == "electronics"
	}
	return false
}

func TestEcommerceTopicRouting(t *testing.T) {
	ruleUS := TopicRule{Pattern: "orders.us.#"}
	ruleElectronics := TopicRule{Pattern: "orders.*.electronics"}

	k1 := "orders.us.electronics"
	k2 := "orders.eu.books"
	k3 := "orders.eu.electronics"

	// k1: orders.us.electronics -> подходит ОБОИМ
	if !ruleUS.Matches(k1) || !ruleElectronics.Matches(k1) {
		t.Fatalf("k1 должен подойти обоим правилам")
	}

	// k2: orders.eu.books -> не подходит ни одному
	if ruleUS.Matches(k2) || ruleElectronics.Matches(k2) {
		t.Fatalf("k2 не должен подойти ни одному правилу")
	}

	// k3: orders.eu.electronics -> только отделу электроники
	if ruleUS.Matches(k3) || !ruleElectronics.Matches(k3) {
		t.Fatalf("k3 должен подойти только ruleElectronics")
	}

	fmt.Println("Topic маршрутизация заказов успешно проверена:")
	fmt.Printf("  • %s: US=%v, Electronics=%v\n", k1, ruleUS.Matches(k1), ruleElectronics.Matches(k1))
	fmt.Printf("  • %s: US=%v, Electronics=%v\n", k2, ruleUS.Matches(k2), ruleElectronics.Matches(k2))
	fmt.Printf("  • %s: US=%v, Electronics=%v\n", k3, ruleUS.Matches(k3), ruleElectronics.Matches(k3))
}
```

ℹ️ Гибкая региональная и категориальная фильтрация заказов в Topic Exchange

## Под капотом

Такая схема позволяет добавлять новые микросервисы (например, сервис аналитики заказов в Азии `orders.asia.#`) без внесения малейших изменений в код издателя заказов.

## Подводные камни

Использовать символ `*` там, где глубина иерархии может меняться: `orders.*.electronics` не поймает `orders.us.california.electronics` (требуется `#`).

## На собеседовании

**Вопрос с собеседования:** «Как спроектировать схему топиков для распределенной микросервисной платформы?»
**Ответ:** Стандартная схема: `<домен>.<сущность>.<действие>.<версия>`. Например: `billing.invoice.created.v1`, `auth.user.logged_in.v2`. Это позволяет подписчикам легко фильтровать как весь домен (`billing.#`), так и конкретные действия (`*.invoice.*.v1`).
