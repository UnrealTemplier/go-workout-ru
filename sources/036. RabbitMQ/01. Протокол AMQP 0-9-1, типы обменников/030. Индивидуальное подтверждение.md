# Индивидуальное подтверждение: флаг autoAck=false и метод Delivery.Ack(multiple=false)

## Условие

Напиши **Message acknowledgment**: `autoAck := false` в `ch.Consume`. Обработай сообщение, затем `d.Ack(false)` (ack только это сообщение). Если consumer упал до `Ack` — сообщение redeliver'ится другому consumer'у. Покажи reliability.

## Теория

Анатомия метода `Delivery.Ack(multiple)`:
- Поле `d.DeliveryTag uint64`: уникальный порядковый номер сообщения на текущем канале.
- Вызов `d.Ack(false)`:
  - Отправляет брокеру AMQP кадр `basic.ack(delivery_tag=d.DeliveryTag, multiple=false)`.
  - Подтверждает строго это единичное сообщение.
  - Брокер удаляет его из списка `unacknowledged`.
- Если консьюмер завершится до этого вызова, брокер инициирует Redelivery.

## Решение по шагам

1. Создайте структуру сообщения Delivery с методом `Ack`.
2. Смоделируйте выполнение бизнес-логики.
3. Вызовите `Ack(false)` после успешного сохранения в БД.
4. Проверьте фиксацию статуса обработки.

## Код решения

**`individual_ack_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type Delivery struct {
	DeliveryTag uint64
	Body        string
	isAcked     bool
}

func (d *Delivery) Ack(multiple bool) {
	d.isAcked = true
}

func TestIndividualMessageAck(t *testing.T) {
	delivery := &Delivery{
		DeliveryTag: 1042,
		Body:        "Обновление баланса пользователя #12",
	}

	// 1. Выполнение транзакции
	if len(delivery.Body) == 0 {
		t.Fatal("Пустое тело")
	}

	// 2. Явный единичный Ack
	delivery.Ack(false)

	if !delivery.isAcked {
		t.Fatal("Сообщение должно быть подтверждено")
	}

	fmt.Printf("Индивидуальный Ack успешно выполнен: Tag=%d, Acked=%v\n",
		delivery.DeliveryTag, delivery.isAcked)
}
```

ℹ️ Явное индивидуальное подтверждение сообщения через Delivery.Ack(false)

## Под капотом

После получения `basic.ack` RabbitMQ помечает слот в оперативной памяти как освобожденный. Если сообщение было persistent на диске, брокер удаляет запись из транзакционного журнала в фоне.

## Подводные камни

Вызывать `d.Ack()` в фоновой горутине после того, как основной поток хендлера уже закрыл канал: это приведет к ошибке закрытого канала.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если воркер вызвал Ack(false) дважды для одного и того же DeliveryTag?»
**Ответ:** Брокер зафиксирует ошибку протокола `channel exception (406): PRECONDITION_FAILED - unknown delivery tag` и немедленно принудительно закроет канал. Все остальные сообщения на этом канале перестанут обрабатываться.
