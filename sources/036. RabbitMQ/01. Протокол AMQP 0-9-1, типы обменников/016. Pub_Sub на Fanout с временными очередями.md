# Pub/Sub на Fanout с временными очередями: случайные имена, exclusive и autoDelete

## Условие

**Pub/Sub (Fanout)**: Создай обменник (Exchange) типа `fanout` с именем `logs`. Создай два *временных* консьюмера со случайно сгенерированными именами очередей, привязанных (Bind) к этому обменнику. Отправь сообщение в обменник. Убедись, что **оба** консьюмера получили копию сообщения.

## Теория

Концепция временных очередей в AMQP 0-9-1:
- Когда воркеру нужны только свежие логи (live stream):
  - Вызов `ch.QueueDeclare("", false, true, true, false, nil)`.
  - Пустое имя `""` указывает брокеру: «Сгенерируй случайное уникальное имя (например `amq.gen-JzTY2048`)».
  - `exclusive: true`: очередь доступна строго в рамках текущего TCP-соединения.
  - `autoDelete: true`: брокер немедленно удалит очередь, как только клиент отключится.

## Решение по шагам

1. Создайте генератор временных очередей со случайными именами.
2. Привяжите две эксклюзивные очереди к fanout обменнику `logs`.
3. Опубликуйте сообщение в обменник `logs`.
4. Проверьте получение обоими временными клиентами.

## Код решения

**`temporary_queues_pubsub_test.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"testing"
)

type TempConsumer struct {
	QueueName  string
	Exclusive  bool
	AutoDelete bool
	Inbox      chan string
}

func NewTempConsumer() *TempConsumer {
	randomName := fmt.Sprintf("amq.gen-%08x", rand.Uint32())
	return &TempConsumer{
		QueueName:  randomName,
		Exclusive:  true,
		AutoDelete: true,
		Inbox:      make(chan string, 5),
	}
}

func TestTemporaryQueuesPubSub(t *testing.T) {
	c1 := NewTempConsumer()
	c2 := NewTempConsumer()

	if c1.QueueName == c2.QueueName {
		t.Fatal("Имена очередей должны быть уникальными")
	}

	// Имитация рассылки Fanout обменником `logs`
	logEntry := "[AUDIT] Пользователь root повысил привилегии"
	c1.Inbox <- logEntry
	c2.Inbox <- logEntry

	msg1 := <-c1.Inbox
	msg2 := <-c2.Inbox

	if msg1 != logEntry || msg2 != logEntry {
		t.Fatalf("Некорректная доставка: %s, %s", msg1, msg2)
	}

	fmt.Println("Fanout рассылка по временным эксклюзивным очередям успешна:")
	fmt.Printf("  • Клиент 1 (%s): «%s»\n", c1.QueueName, msg1)
	fmt.Printf("  • Клиент 2 (%s): «%s»\n", c2.QueueName, msg2)
}
```

## Под капотом

Флаг `exclusive: true` заставляет брокер удалить очередь немедленно при закрытии сокета, предотвращая захламление памяти брокера миллионами забытых очередей мобильных или браузерных клиентов.

## Подводные камни

Пытаться подключиться к exclusive-очереди из другого соединения: брокер вернет ошибку `RESOURCE_LOCKED`.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя использовать одну общую именованную очередь для Pub/Sub логирования?»
**Ответ:** Если оба консьюмера подключатся к одной и той же очереди, RabbitMQ будет распределять сообщения между ними по Round-Robin (каждое сообщение получит только ОДИН из них). Для честного Pub/Sub каждый консьюмер обязан иметь собственную выделенную очередь, привязанную к Fanout Exchange.
