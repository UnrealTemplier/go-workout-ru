# Ручное подтверждение (Manual Ack) и повторная доставка (Redelivery) при падении воркера

## Условие

Добавьте подтверждение обработки (manual ack). Консюмер получает сообщение, выполняет работу и подтверждает. Если консюмер падает без ack, сообщение переотправляется другому (redelivery).

## Теория

Семантика At-Least-Once через ручные подтверждения:
- При вызове `Consume(..., autoAck: false, ...)` брокер требует явного подтверждения.
- Состояние сообщения:
  - `Ready` \(\to\) передано клиенту \(\to\) `Unacknowledged`.
  - Если воркер завершил работу: вызывает `msg.Ack(false)` \(\to\) брокер окончательно удаляет сообщение.
  - Если воркер аварийно завершился (TCP сокет закрылся без `Ack`): брокер возвращает сообщение в очередь с флагом `Redelivered: true` и отдает другому воркеру.

## Решение по шагам

1. Создайте структуру очереди с реестром Unacknowledged сообщений.
2. Сымитируйте получение сообщения Воркером 1.
3. Смоделируйте падение Воркера 1 без отправки `Ack`.
4. Убедитесь в повторной доставке (Redelivery) Воркеру 2 с флагом `Redelivered: true`.

## Код решения

**`manual_ack_redelivery_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TrackedMessage struct {
	ID          string
	Body        string
	Redelivered bool
}

type ResilientQueue struct {
	ready      []*TrackedMessage
	unacked    map[string]*TrackedMessage
}

func NewResilientQueue() *ResilientQueue {
	return &ResilientQueue{unacked: make(map[string]*TrackedMessage)}
}

func (q *ResilientQueue) DeliverToWorker() *TrackedMessage {
	if len(q.ready) == 0 {
		return nil
	}
	msg := q.ready[0]
	q.ready = q.ready[1:]
	q.unacked[msg.ID] = msg
	return msg
}

func (q *ResilientQueue) Ack(msgID string) {
	delete(q.unacked, msgID) // Успешно удалено из брокера
}

// Воркер упал: сокет разорван без Ack!
func (q *ResilientQueue) OnWorkerCrashed(msgID string) {
	if msg, ok := q.unacked[msgID]; ok {
		delete(q.unacked, msgID)
		msg.Redelivered = true // Помечаем как повторно доставленное
		q.ready = append(q.ready, msg) // Возвращаем в очередь
	}
}

func TestManualAckAndRedelivery(t *testing.T) {
	q := NewResilientQueue()
	q.ready = append(q.ready, &TrackedMessage{ID: "tx-501", Body: "Списание средств 5000 руб"})

	// 1. Воркер 1 забирает сообщение
	msgW1 := q.DeliverToWorker()
	if msgW1 == nil || msgW1.Redelivered {
		t.Fatal("Первая доставка не должна иметь флаг Redelivered")
	}

	// 2. Воркер 1 аварийно падает (SIGKILL/паника) без Ack
	q.OnWorkerCrashed(msgW1.ID)

	// 3. Сообщение возвращается в очередь и достается Воркеру 2
	msgW2 := q.DeliverToWorker()
	if msgW2 == nil || !msgW2.Redelivered {
		t.Fatalf("Ожидалась повторная доставка с Redelivered=true: %+v", msgW2)
	}

	// 4. Воркер 2 успешно выполняет работу и вызывает Ack
	q.Ack(msgW2.ID)

	if len(q.ready) != 0 || len(q.unacked) != 0 {
		t.Fatal("Очередь должна быть пуста после успешного Ack")
	}

	fmt.Println("Ручное подтверждение (Manual Ack) и Redelivery успешно проверены:")
	fmt.Printf("  • Первая попытка: Воркер 1 упал без Ack\n")
	fmt.Printf("  • Вторая попытка: Воркер 2 получил Redelivered=%v\n", msgW2.Redelivered)
	fmt.Println("  • Сообщение успешно подтверждено и удалено из брокера!")
}
```

ℹ️ Повторная доставка сообщения другому воркеру при аварийном падении без Ack

## Под капотом

В RabbitMQ нет таймаута на ожидание Ack по умолчанию: пока TCP-соединение с воркером открыто, сообщение остается в `unacked`. Ределивери происходит только тогда, когда канал или TCP-соединение закрывается.

## Подводные камни

Забывать вызывать `msg.Ack(false)` при успешной обработке: память брокера будет расти бесконечно, так как RabbitMQ не имеет права удалить неподтвержденные сообщения.

## На собеседовании

**Вопрос с собеседования:** «Что означает флаг multiple в методах msg.Ack(multiple) и msg.Nack(multiple)?»
**Ответ:** Если `multiple: true`, брокер подтверждает не только текущее сообщение, но и ВСЕ предыдущие неподтвержденные сообщения на данном канале с меньшим или равным `delivery_tag` (пакетный Ack). Если `multiple: false`, подтверждается строго одно конкретное сообщение.
