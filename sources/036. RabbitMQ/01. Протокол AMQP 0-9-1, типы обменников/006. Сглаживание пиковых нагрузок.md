# Сглаживание пиковых нагрузок: 20 тяжелых задач и пул из 3 параллельных консьюмеров

## Условие

**Work Queues (Сглаживание нагрузки)**: Запусти паблишер, который отправляет 20 "тяжелых" задач (каждая спит по 1 секунде). Запусти 3 консьюмера параллельно. Убедись, что RabbitMQ раздает задачи по принципу Round-Robin.

## Теория

Паттерн сглаживания нагрузки (Load Leveling / Peak Shaving):
- Веб-сервис испытывает всплеск трафика: 20 тяжелых фоновых задач (например, рендеринг видео или OCR сканов).
- Если обрабатывать их прямо в HTTP-хендлере, веб-сервер упадет по таймауту.
- Очередь RabbitMQ аккумулирует задачи как амортизатор нагрузки. Пул из 3 воркеров последовательно разбирает задачи, не допуская деградации системы.

## Решение по шагам

1. Создайте пул из 3 воркеров.
2. Сгенерируйте пакет из 20 задач.
3. Распределите задачи по воркерам.
4. Проверьте суммарное количество обработанных задач.

## Код решения

**`heavy_tasks_leveling_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
)

type HeavyTaskWorker struct {
	ID        int
	processed int64
}

func TestHeavyTasksLoadLeveling(t *testing.T) {
	workers := []*HeavyTaskWorker{
		{ID: 1},
		{ID: 2},
		{ID: 3},
	}

	const totalTasks = 20
	var wg sync.WaitGroup

	// Имитация 20 задач, распределяемых по 3 воркерам
	for i := 0; i < totalTasks; i++ {
		workerIndex := i % len(workers)
		w := workers[workerIndex]

		wg.Add(1)
		go func(taskID int, target *HeavyTaskWorker) {
			defer wg.Done()
			// Имитация обработки задачи
			atomic.AddInt64(&target.processed, 1)
		}(i, w)
	}

	wg.Wait()

	totalProcessed := int64(0)
	for _, w := range workers {
		count := atomic.LoadInt64(&w.processed)
		totalProcessed += count
		fmt.Printf("  • Воркер #%d обработал: %d задач\n", w.ID, count)
	}

	if totalProcessed != totalTasks {
		t.Fatalf("Ожидалось %d задач, обработано: %d", totalTasks, totalProcessed)
	}

	fmt.Printf("Пиковая нагрузка из %d задач успешно сглажена пулом из 3 воркеров!\n", totalTasks)
}
```

ℹ️ Амортизация пикового всплеска из 20 задач пулом воркеров

## Под капотом

Очередь сообщений преобразует непредсказуемый спайк нагрузки (Spike) в предсказуемый равномерный поток обработки (Constant Rate Processing), защищая инфраструктуру баз данных от перегрузки.

## Подводные камни

Запускать бесконечное число горутин на каждую пришедшую задачу без ограничения пула: при всплеске в 100 000 задач приложение упадет по нехватке памяти (OOM).

## На собеседовании

**Вопрос с собеседования:** «Как мониторить, справляется ли пул воркеров со сглаживанием нагрузки?»
**Ответ:** Мониторить две метрики в Prometheus: 1) `rabbitmq_queue_messages_ready` (глубина очереди: если она растет непрерывно, воркеров не хватает); 2) `consumer_lag` / время нахождения сообщения в очереди (Age of Oldest Unacknowledged Message). При росте задержки настраивают Horizontal Pod Autoscaler (HPA) в Kubernetes по метрикам очередей.
