# Управление качеством обслуживания (Prefetch / QoS): prefetchCount=1 и справедливое распределение

## Условие

**[Prefetch / QoS]**: Установи `channel.Qos(prefetchCount=1)`. Запусти двух консьюмеров. Убедись, что сообщения распределяются по Round-Robin, но новый консьюмер не получает сообщение, пока не подтвердил (ack) предыдущее.

## Теория

Принцип Fair Dispatch через `channel.Qos(1, 0, false)`:
- По умолчанию брокер отправляет консьюмеру всё, что есть в очереди (жадный push).
- Параметр `prefetchCount = 1`:
  - Сообщает брокеру: «Не присылай этому воркеру следующее сообщение, пока он не подтвердит (Ack) предыдущее».
  - Если воркер занят тяжелой задачей, брокер отдает поступающие сообщения свободным воркерам.
  - Устраняет эффект «голодания» (Worker Starvation) и обеспечивает оптимальную утилизацию CPU кластера.

## Решение по шагам

1. Создайте модель воркера с флагом `busy`.
2. Реализуйте проверку Prefetch: брокер передает задачу только воркеру с `busy == false`.
3. Отправьте тяжелую задачу Воркеру 1.
4. Убедитесь, что вторая задача ушла свободному Воркеру 2, не ожидая завершения Воркера 1.

## Код решения

**`prefetch_qos_fair_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type FairWorker struct {
	ID        int
	isBusy    bool
	completed int
}

type FairDispatcher struct {
	mu      sync.Mutex
	workers []*FairWorker
}

func (d *FairDispatcher) DispatchFair(taskName string) (*FairWorker, error) {
	d.mu.Lock()
	defer d.mu.Unlock()

	for _, w := range d.workers {
		if !w.isBusy {
			w.isBusy = true // Занял квоту prefetchCount=1
			return w, nil
		}
	}
	return nil, fmt.Errorf("все воркеры заняты (QoS лимит)")
}

func (d *FairDispatcher) Ack(w *FairWorker) {
	d.mu.Lock()
	defer d.mu.Unlock()
	w.isBusy = false
	w.completed++
}

func TestPrefetchQoS(t *testing.T) {
	d := &FairDispatcher{
		workers: []*FairWorker{
			{ID: 1},
			{ID: 2},
		},
	}

	// 1. Первая задача уходит Воркеру 1
	wA, err := d.DispatchFair("Тяжелая задача #1")
	if err != nil || wA.ID != 1 {
		t.Fatalf("Ожидался воркер 1: %v", err)
	}

	// 2. Воркер 1 занят. Вторая задача уходит свободному Воркеру 2!
	wB, err := d.DispatchFair("Задача #2")
	if err != nil || wB.ID != 2 {
		t.Fatalf("Ожидался воркер 2: %v", err)
	}

	// 3. Оба воркера заняты -> QoS блокирует отправку
	_, errBlocked := d.DispatchFair("Задача #3")
	if errBlocked == nil {
		t.Fatal("Ожидалась блокировка QoS лимитом")
	}

	// 4. Воркер 1 подтверждает выполнение
	d.Ack(wA)

	// 5. Теперь задача #3 успешно отправляется освободившемуся Воркеру 1
	wC, err := d.DispatchFair("Задача #3")
	if err != nil || wC.ID != 1 {
		t.Fatalf("Ожидался освободившийся воркер 1: %v", err)
	}

	fmt.Println("Prefetch Count (QoS) успешно протестирован:")
	fmt.Printf("  • Задача #1: Воркер #%d (занят)\n", wA.ID)
	fmt.Printf("  • Задача #2: Воркер #%d (свободен)\n", wB.ID)
	fmt.Printf("  • Блокировка перегрузки: %v\n", errBlocked)
	fmt.Printf("  • После Ack задача #3 ушла воркеру #%d\n", wC.ID)
}
```

## Под капотом

AMQP метод `basic.qos` устанавливает верхний порог счетчика неподтвержденных сообщений (Unacknowledged Messages) на канале. Брокер отслеживает этот счетчик в памяти и приостанавливает отправку новых кадров `basic.deliver`.

## Подводные камни

Вызывать `channel.Qos` ПОСЛЕ вызова `channel.Consume`: это состояние гонки. Настройку QoS обязаны выполнять строго ДО подписки на получение сообщений.

## На собеседовании

**Вопрос с собеседования:** «Почему prefetchCount=1 может быть плохим выбором для сверхбыстрых микрозадач?»
**Ответ:** Если обработка задачи занимает 0.5 мс, а сетевой пинг до RabbitMQ составляет 2 мс, при `prefetchCount=1` воркер 80% времени будет простаивать в ожидании доставки следующего сообщения. Для быстрых задач выставляют `prefetchCount = 50..200`, чтобы держать сетевой буфер заполненным (Pipelining).
