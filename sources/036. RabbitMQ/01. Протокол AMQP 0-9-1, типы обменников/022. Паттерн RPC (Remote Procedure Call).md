# Паттерн RPC (Remote Procedure Call): параметры ReplyTo, CorrelationId и callback-очередь

## Условие

Реализуйте RPC-паттерн: клиент отправляет запрос в очередь с `reply_to` и `correlation_id`, сервер обрабатывает и отвечает в указанную очередь. Клиент дожидается ответа с таймаутом.

## Теория

Двустороннее взаимодействие через очереди (AMQP RPC):
- Клиент:
  1. Создает временную эксклюзивную callback-очередь `reply_to`.
  2. Генерирует уникальный `correlation_id = uuid.New()`.
  3. Отправляет запрос в `rpc_queue` с полями `ReplyTo` и `CorrelationId`.
  4. Ждет ответное сообщение в своей callback-очереди с тем же `CorrelationId`.
- Сервер:
  1. Читает запрос из `rpc_queue`.
  2. Вычисляет результат.
  3. Отправляет ответ в очередь `msg.ReplyTo` с сохранением исходного `msg.CorrelationId`.

## Решение по шагам

1. Создайте структуру RPC запроса и ответа.
2. Реализуйте серверную обработку вычисления факториала.
3. Клиент отправляет запрос с `CorrelationId` и слушает callback-очередь.
4. Проверьте сопоставление ответа по `CorrelationId` с таймаутом.

## Код решения

**`amqp_rpc_pattern_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type RPCRequest struct {
	CorrelationID string
	ReplyTo       chan RPCResponse
	Arg           int
}

type RPCResponse struct {
	CorrelationID string
	Result        int
}

func RPCServerWorker(requests <-chan RPCRequest) {
	for req := range requests {
		// Сервер вычисляет факториал
		res := 1
		for i := 1; i <= req.Arg; i++ {
			res *= i
		}
		// Отвечает строго в reply_to с тем же CorrelationID
		req.ReplyTo <- RPCResponse{
			CorrelationID: req.CorrelationID,
			Result:        res,
		}
	}
}

func TestAMQPRPCPattern(t *testing.T) {
	reqQueue := make(chan RPCRequest, 5)
	defer close(reqQueue)

	// Запуск сервера в фоне
	go RPCServerWorker(reqQueue)

	// Клиент формирует вызов
	callbackQueue := make(chan RPCResponse, 1)
	corrID := "corr-id-9941"

	reqQueue <- RPCRequest{
		CorrelationID: corrID,
		ReplyTo:       callbackQueue,
		Arg:           5, // 5! = 120
	}

	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	select {
	case resp := <-callbackQueue:
		if resp.CorrelationID != corrID || resp.Result != 120 {
			t.Fatalf("Некорректный RPC ответ: %+v", resp)
		}
		fmt.Printf("AMQP RPC вызов успешно завершен:\n")
		fmt.Printf("  • CorrelationID: %s\n", resp.CorrelationID)
		fmt.Printf("  • Вычисленный результат (5!): %d\n", resp.Result)
	case <-ctx.Done():
		t.Fatal("Таймаут ожидания RPC ответа")
	}
}
```

## Под капотом

Использование одной постоянной callback-очереди на клиента с маршрутизацией по `CorrelationId` (Direct Reply-to) в разы эффективнее, чем создание новой временной очереди на каждый RPC-запрос.

## Подводные камни

Создавать новую очередь на каждый RPC-вызов: создание и удаление очередей в кластере RabbitMQ нагружает Mnesia и снижает RPS системы до нескольких сотен вызовов.

## На собеседовании

**Вопрос с собеседования:** «Что такое RabbitMQ Direct Reply-to (amq.rabbitmq.reply-to) и почему он лучше обычных callback-очередей?»
**Ответ:** `amq.rabbitmq.reply-to` — это псевдоочередь, встроенная в RabbitMQ. Клиент подписывается на нее в режиме `no-ack`, а брокер передает ответ напрямую в сетевой сокет клиента без фактического создания дисковой очереди в Mnesia. Это снижает latency до уровня чистого сокета и устраняет накладные расходы на менеджмент очередей.
