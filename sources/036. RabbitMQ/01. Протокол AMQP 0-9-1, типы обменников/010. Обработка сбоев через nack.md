# Обработка сбоев через nack: возврат в очередь (requeue=true) и повторная обработка

## Условие

**[Manual Acknowledgement]**: Сымитируй ошибку обработки в консьюмере (паника или возврат ошибки). Вместо `ack` вызови `nack(delivery_tag, multiple=false, requeue=true)`. Посмотри, как сообщение возвращается в очередь.

## Теория

Отказ от сообщения с возвратом в очередь (`nack` с `requeue=true`):
- Если при обработке произошел временный сбой (например, внешняя база данных кратковременно недоступна):
  - Воркер вызывает `msg.Nack(false, true)`.
  - Брокер возвращает сообщение обратно в очередь.
  - Сообщение станет доступно для повторной обработки этим же или другим воркером.
- **Опасность:** если ошибка перманентна (битый JSON или логическая ошибка в коде), сообщение будет бесконечно крутиться в цикле (Poison Pill).

## Решение по шагам

1. Создайте обработчик с возвратом ошибки.
2. Перехватите ошибку и вызовите `Nack(false, true)`.
3. Убедитесь, что сообщение вернулось в очередь.
4. Протестируйте успешную обработку со второй попытки.

## Код решения

**`nack_requeue_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type RetryableConsumer struct {
	attemptCount int
}

func (c *RetryableConsumer) Process(data string) error {
	c.attemptCount++
	if c.attemptCount == 1 {
		// Первая попытка падает из-за временного сбоя БД
		return errors.New("БД временно недоступна (503)")
	}
	return nil // Вторая попытка успешна
}

func TestNackRequeue(t *testing.T) {
	consumer := &RetryableConsumer{}
	msg := "Перевод средств клиенту #9001"

	// 1. Первая попытка
	err1 := consumer.Process(msg)
	if err1 == nil {
		t.Fatal("Ожидался сбой на 1-й попытке")
	}

	// Имитация msg.Nack(false, true): сообщение возвращается в очередь
	fmt.Printf("Попытка 1 провалена: %v -> Вызываем msg.Nack(multiple=false, requeue=true)\n", err1)

	// 2. Вторая попытка (повторное извлечение из очереди)
	err2 := consumer.Process(msg)
	if err2 != nil {
		t.Fatalf("Вторая попытка должна быть успешной: %v", err2)
	}

	fmt.Println("Попытка 2 успешна -> Вызываем msg.Ack(false)")
}
```

## Под капотом

При вызове `Nack(false, true)` RabbitMQ возвращает сообщение в его исходную позицию очереди, если это возможно, либо в конец очереди, если позиция была занята другими сообщениями.

## Подводные камни

Вызывать `Nack(false, true)` при фатальных ошибках валидации (битый JSON, отсутствует обязательное поле): сообщение войдет в бесконечный цикл 100% утилизации CPU и забьет очередь.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие между channel.Reject и channel.Nack в AMQP?»
**Ответ:** `basic.reject` — это старый базовый метод AMQP, который может отклонять строго одно сообщение. `basic.nack` — это расширение RabbitMQ, поддерживающее флаг `multiple: true` для пакетного отклонения пачки сообщений.
