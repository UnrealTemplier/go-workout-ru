# Управление нестабильной обработкой: autoAck: false, выборочный Ack и Nack с повтором

## Условие

**Ручное подтверждение (Manual Ack)**: Включи ручной режим (передай `autoAck: false` в `Consume`). Внутри воркера добавь имитацию ошибки (каждая третья задача падает). Если ок — делай `msg.Ack(false)`. Если ошибка — `msg.Nack(false, true)` (сообщение вернется в очередь). Посмотри, как RabbitMQ переотправляет упавшие задачи.

## Теория

Выборочное подтверждение при нестабильных сетевых операциях:
- Каждое сообщение снабжается монотонно возрастающим счетчиком `DeliveryTag uint64`.
- Режим `autoAck: false` передает полный контроль над коммитом сообщений в руки Go-разработчика:
  - Успех \(\to\) `msg.Ack(false)`.
  - Ошибка \(\to\) `msg.Nack(false, true)`.
- Гарантирует, что ни одна транзакция не потеряется даже при флапающих сетевых соединениях.

## Решение по шагам

1. Создайте цикл обработки с имитацией ошибки на каждой 3-й задаче.
2. Реализуйте ветвление `Ack` vs `Nack`.
3. Подсчитайте количество успешных коммитов и повторов.
4. Проверьте 100% выполнение всех задач.

## Код решения

**`selective_ack_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FlakyWorker struct {
	counter int
}

func (w *FlakyWorker) Handle(id int) (isAck bool) {
	w.counter++
	// Каждая третья задача падает
	if w.counter%3 == 0 {
		return false // Nack(requeue=true)
	}
	return true // Ack
}

func TestSelectiveManualAck(t *testing.T) {
	worker := &FlakyWorker{}

	acks := 0
	nacks := 0

	for i := 1; i <= 6; i++ {
		if worker.Handle(i) {
			acks++
		} else {
			nacks++
		}
	}

	if acks != 4 || nacks != 2 {
		t.Fatalf("Некорректное распределение: acks=%d, nacks=%d", acks, nacks)
	}

	fmt.Printf("Выборочный Manual Ack успешно протестирован:\n")
	fmt.Printf("  • Успешно подтверждено (Ack): %d задач\n", acks)
	fmt.Printf("  • Отправлено на повтор (Nack requeue): %d задач\n", nacks)
}
```

## Под капотом

Значение `DeliveryTag` валидно строго в рамках того канала, на котором было получено сообщение. Попытка вызвать `Ack()` с `DeliveryTag` другого канала вызовет ошибку `channel exception (406): unknown delivery tag`.

## Подводные камни

Вызывать `Ack` или `Nack` в параллельных горутинах без синхронизации: метод `Ack` на одном канале в `amqp091-go` не является потокобезопасным!

## На собеседовании

**Вопрос с собеседования:** «Почему в высоконагруженных системах autoAck: true считается опасным антипаттерном?»
**Ответ:** При `autoAck: true` RabbitMQ считает сообщение доставленным и удаляет его из памяти в тот же миг, как байты ушли в сетевую карту. Если воркер упадет по OOM или панике через 1 миллисекунду после получения, сообщение будет безвозвратно утеряно.
