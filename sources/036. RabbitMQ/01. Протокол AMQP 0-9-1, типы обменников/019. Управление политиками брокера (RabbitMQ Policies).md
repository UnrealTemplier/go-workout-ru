# Управление политиками брокера (RabbitMQ Policies): автоматический TTL и Dead Lettering без правок кода

## Условие

Настройте TTL на сообщениях и автоматическое перемещение просроченных сообщений в DLQ через политики RabbitMQ.

## Теория

Декларативное управление через RabbitMQ Policies:
- **Антипаттерн:** хардкодить параметры `x-message-ttl` и `x-dead-letter-exchange` в Go-коде каждого сервиса (изменение требует передеплоя и пересоздания очередей).
- **Best Practice (RabbitMQ Policies):**
  - Администратор или DevOps применяет политику через CLI или HTTP API:
    `rabbitmqctl set_policy TTL-DLQ-Policy "^orders\." '{"message-ttl": 60000, "dead-letter-exchange": "dlx"}' --apply-to queues`.
  - Политика динамически на лету применяется ко всем очередям, чьи имена подходят под регулярное выражение, без перезагрузки приложений!

## Решение по шагам

1. Создайте структуру политики `BrokerPolicy`.
2. Реализуйте сопоставление очередей по regex шаблону.
3. Проверьте применение параметров TTL и DLX к подходящим очередям.
4. Убедитесь в изоляции очередей, не подпадающих под политику.

## Код решения

**`rabbitmq_policies_test.go`**

```go
package main

import (
	"fmt"
	"regexp"
	"testing"
)

type BrokerPolicy struct {
	Name       string
	Pattern    *regexp.Regexp
	MessageTTL int // ms
	DLX        string
}

func (p *BrokerPolicy) Apply(queueName string) (ttl int, dlx string, matched bool) {
	if p.Pattern.MatchString(queueName) {
		return p.MessageTTL, p.DLX, true
	}
	return 0, "", false
}

func TestRabbitMQPolicies(t *testing.T) {
	policy := BrokerPolicy{
		Name:       "Orders-TTL-DLQ-Policy",
		Pattern:    regexp.MustCompile(`^orders\.`),
		MessageTTL: 60000, // 60 секунд
		DLX:        "orders_dlx",
	}

	ttl1, dlx1, match1 := policy.Apply("orders.payments")
	_, _, match2 := policy.Apply("analytics.events")

	if !match1 || ttl1 != 60000 || dlx1 != "orders_dlx" {
		t.Fatalf("Политика должна была примениться к orders.payments")
	}

	if match2 {
		t.Fatal("Политика не должна была примениться к analytics.events")
	}

	fmt.Println("Декларативная политика RabbitMQ успешно протестирована:")
	fmt.Printf("  • Очередь orders.payments: TTL=%d ms, DLX=%s (Matched=%v)\n", ttl1, dlx1, match1)
	fmt.Printf("  • Очередь analytics.events: Matched=%v\n", match2)
}
```

ℹ️ Декларативное назначение параметров TTL и DLQ через механизм политик брокера

**`Терминал`**

```bash
# Команда установки политики в реальном кластере:
rabbitmqctl set_policy OrdersPolicy "^orders\." \
  '{"message-ttl":60000, "dead-letter-exchange":"orders_dlx"}' \
  --apply-to queues

go test -v rabbitmq_policies_test.go
# Вывод:
# === RUN   TestRabbitMQPolicies
# Декларативная политика RabbitMQ успешно протестирована:
#   • Очередь orders.payments: TTL=60000 ms, DLX=orders_dlx (Matched=true)
#   • Очередь analytics.events: Matched=false
# --- PASS: TestRabbitMQPolicies (0.00s)
# PASS
```

## Под капотом

Политики в RabbitMQ обновляются на лету во всей Erlang Mnesia кластере без прерывания активных консьюмеров. Если очередь уже существовала, она мгновенно подхватывает новые параметры TTL.

## Подводные камни

Задать конфликт аргументов очереди: если в коде объявлен аргумент `x-message-ttl: 30000`, а политика выставляет `60000`, значение политики имеет более высокий приоритет.

## На собеседовании

**Вопрос с собеседования:** «Почему в Enterprise-инфраструктуре запрещают задавать TTL и DLX в коде через QueueDeclare arguments?»
**Ответ:** Аргументы очереди в коде являются неизменяемыми (Immutable). Если нужно изменить TTL с 5 до 10 минут, придется удалять очередь (с потерей сообщений!) и передеплоить все сервисы. Политики позволяют DevOps-инженерам менять TTL, DLX и лимиты длины очередей динамически через GitOps без трогания кода.
