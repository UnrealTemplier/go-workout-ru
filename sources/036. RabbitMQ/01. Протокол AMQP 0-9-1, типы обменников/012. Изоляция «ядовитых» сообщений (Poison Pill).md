# Изоляция «ядовитых» сообщений (Poison Pill): Dead Letter Exchange (DLX) и маршрутизация сбоев

## Условие

**[Каверзный кейс — Poison Pill]**: Сообщение вызывает панику при каждой обработке. С `requeue=true` оно будет крутиться бесконечно, блокируя очередь. Реализуй паттерн DLX (Dead Letter Exchange): создай exchange `main_ex` и привяжи к нему очередь `main_q` с аргументом `x-dead-letter-exchange: dlx_ex`. При `nack(requeue=false)` сообщение улетит в `dlx_q`.

## Теория

Паттерн Dead Letter Exchange (DLX / Очередь мертвых писем):
- **Проблема «Ядовитого сообщения» (Poison Pill):** некорректный байт-код или баг в парсере вызывает панику воркера при каждой попытке обработки.
- **Решение через DLX:**
  1. Очередь объявляется с аргументами:
     `amqp.Table{"x-dead-letter-exchange": "dlx_exchange"}`.
  2. При возникновении неисправимой ошибки воркер вызывает `msg.Nack(false, false)` (`requeue: false`).
  3. Брокер автоматически перенаправляет сообщение в `dlx_exchange`, откуда оно попадает в `dlx_queue`.
  4. Основная очередь разблокирована, а упавшее сообщение сохранено для ручного анализа инженерами.

## Решение по шагам

1. Сконфигурируйте основную очередь с аргументом `x-dead-letter-exchange`.
2. Смоделируйте падение на Poison Pill сообщении.
3. Вызовите `Nack(requeue: false)`.
4. Убедитесь, что сообщение автоматически переместилось в DLQ.

## Код решения

**`poison_pill_dlx_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PoisonPillRouter struct {
	mainQueue []string
	dlqQueue  []string
	dlxName   string
}

func (r *PoisonPillRouter) Process(msg string) bool {
	// Имитируем Poison Pill: паника или фатальная ошибка
	if msg == "POISON_PILL_CORRUPTED_BYTES" {
		// Отклоняем без возврата в основную очередь (requeue=false) -> уходит в DLQ
		r.dlqQueue = append(r.dlqQueue, msg)
		return false
	}
	return true
}

func TestDeadLetterExchangePoisonPill(t *testing.T) {
	router := &PoisonPillRouter{
		dlxName: "dlx_service_exchange",
	}

	poisonMessage := "POISON_PILL_CORRUPTED_BYTES"
	ok := router.Process(poisonMessage)

	if ok {
		t.Fatal("Ядовитое сообщение не должно быть успешно обработано")
	}

	if len(router.dlqQueue) != 1 || router.dlqQueue[0] != poisonMessage {
		t.Fatalf("Сообщение должно было попасть в DLQ: %v", router.dlqQueue)
	}

	fmt.Println("Паттерн Dead Letter Exchange (DLX) успешно изолировал Poison Pill:")
	fmt.Printf("  • Основная очередь разблокирована (0 зависаний)\n")
	fmt.Printf("  • Неисправимое сообщение сохранено в DLQ: «%s»\n", router.dlqQueue[0])
}
```

ℹ️ Изоляция ядовитых сообщений в Dead Letter Queue через nack(requeue=false)

## Под капотом

При перемещении сообщения в DLX брокер автоматически добавляет в заголовок `headers["x-death"]` детальную диагностическую информацию: имя исходной очереди, причину отклонения (`rejected`, `expired`, `maxlen`), время и количество попыток.

## Подводные камни

Настроить циклическую маршрутизацию между основной очередью и DLQ без задержки: сообщения войдут в бесконечный бесконечный штопор, перегрузив CPU брокера.

## На собеседовании

**Вопрос с собеседования:** «При каких трех условиях сообщение попадает в Dead Letter Exchange в RabbitMQ?»
**Ответ:** 
1. Сообщение отклонено консьюмером с флагом `requeue=false` (`basic.reject` или `basic.nack`).
2. Истек срок жизни сообщения (Message TTL).
3. Очередь переполнена и достигнут лимит максимальной длины (`x-max-length`).
