# Отказоустойчивость CDC-воркера: Персистентность LSN в Redis и автовосстановление

## Условие

**[High Availability]**: Если твой CDC-воркер упал, поднялся заново — он должен продолжить чтение с того места, где остановился. Сохраняй последний подтвержденный LSN (Log Sequence Number) в Redis или локальный файл перед стартом репликации (`StartReplication` с `lsn`).

## Теория

При падении пода в Kubernetes или перезапуске ноды CDC-сервис должен подняться, переподключиться к слоту и продолжить чтение с гарантией отсутствия пропусков.

Архитектура High Availability (HA) для CDC:
1. **Чекпоинтинг (Checkpointing):** Воркер накапливает подтвержденные downstream-системой смещения LSN.
2. **Внешнее состояние (External Store):** LSN сохраняется в высоконадежное распределенное хранилище (Redis / etcd / отдельная контрольная таблица в БД) по завершении обработки каждой транзакции.
3. **Восстановление при старте:** При запуске сервис делает `GetLSN`, проверяет валидность и передает полученный LSN в `StartReplication`.
4. **Защита от сбоя слота:** Если сохраненный LSN меньше `restart_lsn` слота (сегменты уже удалены), сервис сообщает об аварии и запрашивает переинициализацию снимка.

## Решение по шагам

1. Реализуйте структуру `RedisLSNTracker` с методами `SaveCheckpoint(slot, lsn)` и `LoadCheckpoint(slot)`.
2. Смоделируйте сценарий падения воркера посреди обработки потока.
3. Покажите чтение сохраненного LSN при рестарте.
4. Продемонстрируйте проверку валидности LSN перед передачей в `StartReplication`.

## Код решения

**`ha_cdc_worker.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"

	"github.com/jackc/pglogrepl"
)

type HAStateStore struct {
	mu   sync.Mutex
	data map[string]string
}

func NewHAStateStore() *HAStateStore {
	return &HAStateStore{data: make(map[string]string)}
}

func (s *HAStateStore) Save(key string, val string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.data[key] = val
}

func (s *HAStateStore) Load(key string) (string, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	v, ok := s.data[key]
	return v, ok
}

type CDCSupervisor struct {
	slotName string
	store    *HAStateStore
}

func (s *CDCSupervisor) ResumeReplication(ctx context.Context) (pglogrepl.LSN, error) {
	checkpointKey := fmt.Sprintf("cdc:checkpoint:%s", s.slotName)
	rawLSN, found := s.store.Load(checkpointKey)

	if !found {
		fmt.Printf("Чекпоинт для слота '%s' не найден. Старт с LSN 0 (позиция слота).\n", s.slotName)
		return pglogrepl.LSN(0), nil
	}

	lsn, err := pglogrepl.ParseLSN(rawLSN)
	if err != nil {
		return 0, fmt.Errorf("поврежденный LSN в хранилище: %w", err)
	}

	fmt.Printf("Найден сохраненный чекпоинт: %s. Возобновление репликации!\n", lsn)
	return lsn, nil
}

func (s *CDCSupervisor) CommitCheckpoint(ctx context.Context, lsn pglogrepl.LSN) {
	checkpointKey := fmt.Sprintf("cdc:checkpoint:%s", s.slotName)
	s.store.Save(checkpointKey, lsn.String())
	fmt.Printf("💾 [CHECKPOINT SAVED] Сохранен LSN %s в Redis/KV\n", lsn)
}

func main() {
	ctx := context.Background()
	store := NewHAStateStore()
	supervisor := &CDCSupervisor{slotName: "orders_cdc_slot", store: store}

	// 1. Первый старт сервиса (нет чекпоинта)
	lsn1, _ := supervisor.ResumeReplication(ctx)
	fmt.Printf("Стартовая позиция #1: %s\n\n", lsn1)

	// 2. Обработка транзакций и сохранение чекпоинта
	processedLSN, _ := pglogrepl.ParseLSN("0/16B6200")
	supervisor.CommitCheckpoint(ctx, processedLSN)

	// 3. Сымитируем падение и перезапуск сервиса
	fmt.Println("\n💥 Имитация сбоя / перезапуска контейнера в Kubernetes...")
	lsn2, _ := supervisor.ResumeReplication(ctx)
	fmt.Printf("Стартовая позиция #2 после восстановления: %s\n", lsn2)
}
```

## Под капотом

При рестарте передача точного LSN в `StartReplication` исключает зависимость от задержки отправки сетевых статусов `StandbyStatusUpdate`.
Даже если соединение оборвалось в середине 10-секундного интервала между keepalive-сообщениями, консьюмер продолжит стриминг строго с момента последней успешно зафиксированной бизнес-транзакции.

## Подводные камни

1. Хранение LSN в локальном файле контейнера без Persistent Volume: при пересоздании пода Kubernetes в другом узле локальный файл сотрется, и сервис потеряет позицию.
2. Сохранение LSN до подтверждения транзакции в Kafka: приводит к потере данных.

## На собеседовании

В: Что делать, если сохраненный в Redis LSN меньше, чем restart_lsn слота в PostgreSQL (сегменты уже удалены)?
О: Это аварийная ситуация рассинхронизации (Replication Slot Loss). Сервер вернет ошибку:
`ERROR: requested WAL segment has already been removed`.
Автоматически восстановить непрерывный поток невозможно без потери промежуточных данных.
Алгоритм действий:
1) Зафиксировать критический инцидент в мониторинге.
2) Инициировать процедуру переинициализации: пересоздать слот репликации.
3) Запустить фоновую процедуру согласованного снимка (Initial Snapshot / Full Resync) для полной актуализации данных в downstream-системе.
