# Фоновый heartbeat-тикер и регулярный SendStandbyStatusUpdate

## Условие

**SendStandbyStatusUpdate**: Регулярно отправляйте `StandbyStatusUpdate` для подтверждения получения WAL. Иначе slot разрастётся и заполнит диск.

## Теория

Даже если в базе данных нет активных пишущих транзакций (например, ночью или в выходные), поток репликации не должен засыпать.

Почему критичен фоновый heartbeat:
1. PostgreSQL отслеживает активность клиента по таймеру `wal_sender_timeout`. Если за 60 секунд не было подтверждений, сервер разрывает соединение.
2. В активной БД без подтверждений слот репликации замораживает удаление файлов WAL, что быстро приводит к исчерпанию свободного места на диске.

Решение: запуск отдельной горутины с тикером `time.NewTicker(10 * time.Second)`, которая регулярно отправляет `SendStandbyStatusUpdate` с текущим максимальным зафиксированным LSN.

## Решение по шагам

1. Создайте потокобезопасную структуру для хранения последнего зафиксированного LSN с использованием `sync/atomic`.
2. Запустите горутину с таймером на 10 секунд.
3. По тику таймера вызывайте `pglogrepl.SendStandbyStatusUpdate`.
4. Корректно останавливайте тикер при завершении контекста сервиса.

## Код решения

**`heartbeat_ticker.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"sync/atomic"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

type ReplicationFeedbackManager struct {
	conn       *pgconn.PgConn
	flushedLSN uint64
}

func NewFeedbackManager(conn *pgconn.PgConn) *ReplicationFeedbackManager {
	return &ReplicationFeedbackManager{conn: conn}
}

func (m *ReplicationFeedbackManager) UpdateFlushedLSN(lsn pglogrepl.LSN) {
	atomic.StoreUint64(&m.flushedLSN, uint64(lsn))
}

func (m *ReplicationFeedbackManager) GetFlushedLSN() pglogrepl.LSN {
	return pglogrepl.LSN(atomic.LoadUint64(&m.flushedLSN))
}

func (m *ReplicationFeedbackManager) StartHeartbeat(ctx context.Context, interval time.Duration) {
	go func() {
		ticker := time.NewTicker(interval)
		defer ticker.Stop()

		for {
			select {
			case <-ctx.Done():
				fmt.Println("Heartbeat горутина остановлена.")
				return
			case <-ticker.C:
				current := m.GetFlushedLSN()
				if current == 0 {
					continue
				}

				err := pglogrepl.SendStandbyStatusUpdate(ctx, m.conn, pglogrepl.StandbyStatusUpdate{
					WALWritePosition: current,
					WALFlushPosition: current,
					WALApplyPosition: current,
					ClientTime:       time.Now(),
					ReplyRequested:   false,
				})
				if err != nil {
					log.Printf("Ошибка отправки планового StandbyStatusUpdate: %v", err)
				} else {
					fmt.Printf("💓 [HEARTBEAT] Подтвержден LSN %s в PostgreSQL\n", current)
				}
			}
		}
	}()
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
	defer cancel()

	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"
	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка соединения: %v", err)
	}
	defer conn.Close(context.Background())

	mgr := NewFeedbackManager(conn)
	// Имитация движения прогресса
	startLSN, _ := pglogrepl.ParseLSN("0/16B3950")
	mgr.UpdateFlushedLSN(startLSN)

	// Запускаем фоновый тикер каждые 5 секунд
	mgr.StartHeartbeat(ctx, 5*time.Second)

	fmt.Println("Heartbeat менеджер запущен. Ожидание тиков...")
	<-ctx.Done()
	fmt.Println("Тест завершен.")
}
```

## Под капотом

Сетевое соединение `pgconn.PgConn` безопасно использовать для отправки служебных сообщений статуса параллельно с ожиданием в `ReceiveMessage`, так как запись в сокет буферизуется.
При получении статуса сервер PostgreSQL обновляет поля `pg_stat_replication.flush_lsn`, благодаря чему администратор СУБД видит актуальный лаг в дашбордах мониторинга Grafana.

## Подводные камни

1. Слишком частый тикер (например, каждые 10 мс): вызовет постоянный флуд управляющими пакетами по сети и повышенную нагрузку на мастер-ноду. Оптимальный интервал — от 5 до 15 секунд.
2. Обновление `WALFlushPosition` до фактической фиксации: приводит к фатальной потере данных при рестарте консьюмера.
3. Утечка горутины тикера: горутина обязана слушать `ctx.Done()`, иначе она останется висеть в памяти после закрытия соединения.

## На собеседовании

В: Почему отправка StandbyStatusUpdate критически важна даже тогда, когда консьюмер не получает никаких новых данных из базы?
О: Если в базе нет пишущей нагрузки, `walsender` все равно периодически инкрементирует системное время и проверяет живость соединения.
Если консьюмер молчит дольше `wal_sender_timeout`, сервер закрывает TCP сокет по таймауту.
Кроме того, если транзакции идут в других таблицах базы, не включенных в публикацию данного клиента, WAL на мастере растет. Регулярный `StandbyStatusUpdate` сообщает серверу, что клиент уже пропустил эти нерелевантные сегменты и их можно безопасно удалить с диска.
