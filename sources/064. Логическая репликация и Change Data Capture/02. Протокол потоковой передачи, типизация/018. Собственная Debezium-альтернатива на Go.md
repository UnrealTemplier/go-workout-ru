# Собственная Debezium-альтернатива на Go: Архитектура и преимущества

## Условие

**Debezium альтернатива**: Напишите собственный Debezium-подобный коннектор для вашего use case.

## Теория

Debezium — популярное стандартное решение для CDC, работающее поверх Apache Kafka Connect на базе JVM.

Однако в BigTech (Ozon, Авито, Яндекс) для критических highload-нагрузок часто пишут собственные CDC-коннекторы на **Go**:
1. **Потребление ресурсов:** JVM + Kafka Connect требует от 2 до 8 ГБ RAM на процесс, страдает от пауз Garbage Collection (Stop-the-World) и долго стартует (cold start). Go-демон на базе `pglogrepl` потребляет всего 30–70 МБ оперативной памяти.
2. **Задержка (Latency):** Минимальный путь данных — от сокета PostgreSQL прямо в брокер без промежуточных JNI и абстракций Kafka Connect. End-to-end p99 задержка составляет единицы миллисекунд.
3. **Гибкость маршрутизации:** Возможность фильтрации, маскирования персональных данных (PII) и динамического шардирования прямо в коде демона до отправки в очередь.
4. **Снижение операционной сложности:** Единый статически скомпилированный бинарник без Java-зависимостей, легко упаковываемый в scratch/alpine Docker контейнер.

## Решение по шагам

1. Спроектируйте канонический формат события CDC: `CDCEvent` (`Source`, `Table`, `Op`, `Timestamp`, `Before`, `After`, `LSN`).
2. Напишите конвейер, связывающий `pglogrepl` со слотом репликации и сериализатор в JSON.
3. Реализуйте интерфейс `Sink` (приемник данных).
4. Продемонстрируйте сквозную обработку событий в едином демоне.

## Код решения

**`go_debezium.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"time"

	"github.com/jackc/pglogrepl"
)

// CDCEvent — универсальный конверт события изменения данных
type CDCEvent struct {
	Source    string            `json:"source"`
	Table     string            `json:"table"`
	Op        string            `json:"op"` // 'c' = create, 'u' = update, 'd' = delete
	Timestamp int64             `json:"ts_ms"`
	LSN       string            `json:"lsn"`
	Before    map[string]any    `json:"before,omitempty"`
	After     map[string]any    `json:"after,omitempty"`
}

type Sink interface {
	Publish(ctx context.Context, event *CDCEvent) error
}

type ConsoleSink struct{}

func (s *ConsoleSink) Publish(ctx context.Context, event *CDCEvent) error {
	data, _ := json.MarshalIndent(event, "", "  ")
	fmt.Printf("🚀 [SINK EMIT] Отправлено событие:\n%s\n\n", string(data))
	return nil
}

func main() {
	sink := &ConsoleSink{}
	ctx := context.Background()

	// Имитация формирования CDC события внутри Go-демона
	event := &CDCEvent{
		Source:    "postgresql-production",
		Table:     "public.orders",
		Op:        "c",
		Timestamp: time.Now().UnixMilli(),
		LSN:       "0/16B4120",
		After: map[string]any{
			"id":          1052,
			"customer_id": 99,
			"amount":      2999.00,
			"status":      "created",
		},
	}

	_ = sink.Publish(ctx, event)
	fmt.Println("Демон готов для интеграции с Kafka, NATS JetStream или ClickHouse!")
}
```

## Под капотом

Go CDC-демон подключается к сокету PostgreSQL как единственный клиент репликации и читает сырой TCP-поток напрямую в стек горутин.
Отсутствие промежуточных преобразований в Java-объекты и JNI-мосты сокращает аллокации памяти на 95%, обеспечивая стабильный latency profile без скачков GC.

## Подводные камни

1. Нехватка функционала Debezium «из коробки»: написание собственного коннектора требует ручной реализации механизма Initial Snapshot (начальной выгрузки), обработки сбоев сети и трансформаций.
2. Сложность поддержки большого парка разнородных баз (MySQL, MongoDB, Oracle, SQL Server): если Debezium поддерживает все СУБД единым интерфейсом, то на Go придется писать отдельные адаптеры для каждой базы.

## На собеседовании

В: В каких сценариях разработка собственного CDC-коннектора на Go оправдана, а когда лучше использовать Debezium?
О: 1) **Собственный коннектор на Go:** оправдан при ультра-низких требованиях к задержкам (<10 мс), экстремальном HighLoad (миллионы RPS), жестких лимитах по памяти (Kubernetes pod с лимитом 128 МБ) и необходимости сложной бизнес-фильтрации на лету.
2) **Debezium:** оправдан в крупных Enterprise-системах, где требуется поддержка десятков различных типов СУБД, готовый механизм согласованного Initial Snapshot, Schema Registry интеграции и поддержка со стороны экосистемы Apache Kafka.
