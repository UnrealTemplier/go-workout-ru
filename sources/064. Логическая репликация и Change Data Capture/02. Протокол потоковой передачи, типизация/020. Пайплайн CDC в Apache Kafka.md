# Пайплайн CDC в Apache Kafka: Формат событий и сериализация

## Условие

**CDC → Kafka pipeline**: Настройте CDC reader, который публикует изменения в Kafka topic в формате `{"op": "c/u/d", "before": {...}, "after": {...}}`.

## Теория

Change Data Capture (CDC) в связке с распределенной шиной сообщений Apache Kafka — фундамент архитектуры современных распределенных систем (Event-Driven Architecture).

Стандартный канонический формат сообщения (по стандарту Debezium / Kafka Connect):
- `op`: код операции (`'c'` — create/insert, `'u'` — update, `'d'` — delete, `'r'` — read/snapshot).
- `ts_ms`: эпоха времени фиксации транзакции в миллисекундах.
- `source`: метаданные (версия, БД, схема, таблица, LSN, txId).
- `before`: снимок строки до изменения (для update/delete при `REPLICA IDENTITY FULL`).
- `after`: снимок строки после изменения (для insert/update).

Критически важно: сообщение публикуется в топик с **ключом (Kafka Key)**, равным первичному ключу строки (например, `id = "1052"`). Это гарантирует, что все операции по одной сущности обрабатываются строго последовательно одной партицией.

## Решение по шагам

1. Спроектируйте Go-структуры `DebeziumPayload` и `SourceMeta`.
2. Напишите функцию-трансформер, преобразующую `InsertMessage` и `UpdateMessage` в канонический JSON.
3. Реализуйте публикацию в Kafka с выставлением ключа партиционирования по первичному ключу.
4. Продемонстрируйте сериализацию и валидацию структуры JSON-события.

## Код решения

**`cdc_kafka_pipeline.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

type SourceMeta struct {
	Version   string `json:"version"`
	Connector string `json:"connector"`
	DB        string `json:"db"`
	Schema    string `json:"schema"`
	Table     string `json:"table"`
	TxID      uint32 `json:"txId"`
	LSN       string `json:"lsn"`
	TsMS      int64  `json:"ts_ms"`
}

type DebeziumPayload struct {
	Before map[string]any `json:"before"`
	After  map[string]any `json:"after"`
	Source SourceMeta     `json:"source"`
	Op     string         `json:"op"`
	TsMS   int64          `json:"ts_ms"`
}

func BuildKafkaCDCMessage(table string, op string, lsn string, txID uint32, before, after map[string]any) ([]byte, string, error) {
	now := time.Now().UnixMilli()

	payload := DebeziumPayload{
		Before: before,
		After:  after,
		Source: SourceMeta{
			Version:   "2.0",
			Connector: "go-pglogrepl-cdc",
			DB:        "workout_db",
			Schema:    "public",
			Table:     table,
			TxID:      txID,
			LSN:       lsn,
			TsMS:      now,
		},
		Op:   op,
		TsMS: now,
	}

	data, err := json.Marshal(payload)
	if err != nil {
		return nil, "", err
	}

	// Ключ партиционирования Kafka — первичный ключ строки
	var key string
	if after != nil && after["id"] != nil {
		key = fmt.Sprintf("%v", after["id"])
	} else if before != nil && before["id"] != nil {
		key = fmt.Sprintf("%v", before["id"])
	}

	return data, key, nil
}

func main() {
	afterRow := map[string]any{
		"id":         4201,
		"user_email": "engineer@yandex-team.ru",
		"tier":       "platinum",
		"balance":    150000.00,
	}

	msgBytes, kafkaKey, err := BuildKafkaCDCMessage("users", "c", "0/16B4500", 1089, nil, afterRow)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Kafka Partition Key: '%s'\n", kafkaKey)
	fmt.Printf("Kafka Value (Debezium JSON):\n%s\n", string(msgBytes))
}
```

## Под капотом

Использование первичного ключа в качестве ключа партиции Kafka гарантирует, что стандартный партиционер (MurmurHash2 / DefaultPartitioner) направляет все события для строки с `id = 4201` в один и тот же partition топика.
Это исключает race conditions между конкурентными консьюмерами в consumer group, гарантируя строгую причинно-следственную последовательность изменений (Causal Ordering).

## Подводные камни

1. Отправка сообщений без ключа (key = nil): Kafka распределит сообщения round-robin по всем партициям. В результате события Update могут быть прочитаны и обработаны раньше Insert!
2. Включение метаданных в ключ: ключ должен содержать строго первичный ключ сущности, иначе хеш изменится при изменении LSN.

## На собеседовании

В: Что такое Tombstone Message в контексте CDC-пайплайна в Kafka, и зачем оно нужно при удалении строки (DELETE)?
О: Когда строка удаляется в базе данных (`op: "d"`), CDC-продюсер отправляет два события с ключом удаленной строки:
1) Событие удаления (`op: "d"`) с `before: {...}` и `after: null`.
2) Сразу следом — **Tombstone Message**: сообщение с тем же самым ключом (`key = "4201"`), но с пустым телом полезной нагрузки (`value = null`).
Если топик Kafka настроен с политикой сжатия `cleanup.policy=compact` (Log Compaction), Kafka оставляет в топике только последнее состояние каждого ключа. Получив Tombstone, Kafka брокер физически удаляет всю историю этого ключа при следующей очистке сегмента.
