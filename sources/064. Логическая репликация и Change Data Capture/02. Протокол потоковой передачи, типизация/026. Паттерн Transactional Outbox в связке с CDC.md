# Паттерн Transactional Outbox в связке с CDC: Zero-Overhead события

## Условие

**Outbox pattern**: Реализуйте transactional outbox в приложении: бизнес-операция + запись в outbox table в одной транзакции. Отдельный процесс читает outbox через CDC.

## Теория

Паттерн **Transactional Outbox** решает фундаментальную проблему Dual Write:
«Как атомарно обновить базу данных и отправить событие в Kafka без распределенных двухфазных транзакций (2PC)?»

Традиционный опрос Outbox (Polling Publisher через `SELECT ... FOR UPDATE SKIP LOCKED`):
- Создает постоянную нагрузку на диск и CPU СУБД.
- Вызывает конкурентные блокировки и раздувание индексов (index bloat).
- Имеет лаг опроса (polling latency, обычно от 500 мс до 5 секунд).

**CDC-Powered Outbox (Современный BigTech подход):**
- Приложение пишет бизнес-данные и строку в таблицу `outbox` в рамках **одной локальной ACID транзакции**.
- Воркер на Go слушает таблицу `outbox` через логическую репликацию (`pgoutput`).
- При коммите транзакции воркер мгновенно (за доли миллисекунды) получает событие из WAL и публикует в Kafka.
- В таблице `outbox` не требуется статус `is_processed`, и она может очищаться по TTL/партициям без блокировок!

## Решение по шагам

1. Создайте таблицу `outbox` с полями `id`, `aggregate_type`, `aggregate_id`, `payload`, `created_at`.
2. Напишите функцию бизнес-транзакции: создание заказа в `orders` + вставка в `outbox`.
3. Настройте публикацию CDC только для таблицы `outbox`: `CREATE PUBLICATION outbox_pub FOR TABLE outbox;`.
4. Реализуйте Go CDC воркер, который вычитывает строки из `outbox` и пушит полезную нагрузку в целевой топик.

## Код решения

**`transactional_outbox_cdc.go`**

```go
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type OrderCreatedEvent struct {
	OrderID    int64   `json:"order_id"`
	CustomerID int64   `json:"customer_id"`
	Total      float64 `json:"total"`
}

func CreateOrderWithOutbox(ctx context.Context, db *sql.DB, customerID int64, total float64) (int64, error) {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return 0, err
	}
	defer tx.Rollback()

	// 1. Создаем заказ
	var orderID int64
	err = tx.QueryRowContext(ctx, `
		INSERT INTO orders (customer_id, amount) 
		VALUES ($1, $2) 
		RETURNING id;
	`, customerID, total).Scan(&orderID)
	if err != nil {
		return 0, fmt.Errorf("ошибка создания заказа: %w", err)
	}

	// 2. В этой же транзакции формируем Outbox событие
	eventData, _ := json.Marshal(OrderCreatedEvent{
		OrderID:    orderID,
		CustomerID: customerID,
		Total:      total,
	})

	_, err = tx.ExecContext(ctx, `
		INSERT INTO outbox (aggregate_type, aggregate_id, event_type, payload)
		VALUES ($1, $2, $3, $4);
	`, "Order", fmt.Sprintf("%d", orderID), "OrderCreated", eventData)
	if err != nil {
		return 0, fmt.Errorf("ошибка записи в outbox: %w", err)
	}

	// 3. Фиксация единой ACID транзакции
	if err := tx.Commit(); err != nil {
		return 0, fmt.Errorf("ошибка коммита транзакции: %w", err)
	}

	return orderID, nil
}

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка БД: %v", err)
	}
	defer db.Close()

	ctx := context.Background()

	// Создаем таблицу outbox
	initSQL := `
		CREATE TABLE IF NOT EXISTS outbox (
			id BIGSERIAL PRIMARY KEY,
			aggregate_type VARCHAR(100) NOT NULL,
			aggregate_id VARCHAR(100) NOT NULL,
			event_type VARCHAR(100) NOT NULL,
			payload JSONB NOT NULL,
			created_at TIMESTAMPTZ DEFAULT NOW()
		);
	`
	_, _ = db.ExecContext(ctx, initSQL)

	orderID, err := CreateOrderWithOutbox(ctx, db, 108, 8990.00)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	fmt.Printf("✅ Заказ №%d успешно сохранен вместе с Outbox событием в единой ACID транзакции!\n", orderID)
	fmt.Println("CDC-воркер мгновенно вычитает событие из WAL без единого polling SELECT запроса.")
}
```

## Под капотом

В связке Outbox + CDC база данных никогда не испытывает блокировок чтения.
Воркер CDC подключен к потоку репликации `outbox_pub`, получая строки таблицы `outbox` напрямую из кольцевого буфера WAL в разделяемой памяти (shared buffers).
Поскольку поллинг (`SELECT`) отсутствует, накладные расходы на СУБД равны нулю, а таблица `outbox` может быть секционирована по дням (`PARTITION BY RANGE (created_at)`) и старые секции удаляются мгновенным `DROP TABLE`.

## Подводные камни

1. Хранение статуса `processed_at` в таблице outbox: при CDC обновлять строку в outbox категорически не нужно! Обновление строки породит второе событие `UPDATE` в WAL, вызвав повторную отправку события.
2. Слишком длинные полезные нагрузки (payload): хранение огромных JSON в outbox раздувает WAL. Рекомендуется сохранять только идентификаторы и минимальный контекст события.

## На собеседовании

В: Почему связка Outbox Pattern + CDC считается золотым стандартом для микросервисной архитектуры в HighLoad?
О: 1) **Гарантия атомарности:** Бизнес-изменение и событие фиксируются в единой локальной транзакции (гарантия 100% отсутствия рассинхронизации).
2) **Минимальная задержка:** Событие отправляется в Kafka за доли миллисекунды после `COMMIT` (без таймеров polling).
3) **Нулевая деградация базы:** Исключается постоянный polling (`SELECT ... FOR UPDATE`), не раздуваются B-Tree индексы, отсутствуют взаимоблокировки (Deadlocks).
