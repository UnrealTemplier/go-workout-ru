# Обработка гигантских транзакций: Потоковая передача и Backpressure

## Условие

**Handling large transactions**: Большие транзакции могут исчерпать память. Реализуйте streaming processing и backpressure.

## Теория

При массовых операциях в БД (например, ночной перерасчет цен или миграция `UPDATE products SET price = price * 1.05;` на 10 млн строк) размер одной транзакции в WAL может достигать нескольких гигабайт.

Опасности больших транзакций для CDC:
1. **OOM (Out Of Memory):** Если консьюмер накапливает все строки между `Begin` и `Commit` в оперативной памяти Go, процесс будет убит ядром ОС по Out Of Memory.
2. **Перегрузка брокера сообщений:** Попытка отправить миллионы сообщений за одну секунду вызовет скачок очередей (Buffer Overflow).
3. **Разрыв соединения:** Долгая отправка в Kafka без чтения сокета репликации приведет к закрытию сокета сервером PostgreSQL по таймауту `wal_sender_timeout`.

Решение: потоковая обработка (Streaming Processing) с буферизацией и механизмом обратного давления (**Backpressure**).

## Решение по шагам

1. Создайте ограниченный буферизованный канал событий `chan *CDCEvent` (например, ёмкостью 1000 элементов).
2. Читайте сообщения из сокета в отдельной горутине-ридере.
3. Отправляйте события в пул воркеров.
4. При заполнении буфера ридер автоматически замедляет чтение из TCP-сокета (Backpressure на уровне сокета ОС).
5. Параллельно отправляйте плановые подтверждения Keepalive, чтобы сервер не закрыл сессию.

## Код решения

**`large_tx_streaming.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type StreamedChange struct {
	XID    uint32
	RowID  int
	Action string
}

func RunStreamingConsumer(ctx context.Context, inputQueue <-chan StreamedChange, numWorkers int) {
	var wg sync.WaitGroup

	for i := 1; i <= numWorkers; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			processed := 0
			for {
				select {
				case <-ctx.Done():
					fmt.Printf("Воркер #%d завершен (обработано %d строк)\n", workerID, processed)
					return
				case item, ok := <-inputQueue:
					if !ok {
						return
					}
					processed++
					// Имитация записи в downstream с троттлингом
					time.Sleep(10 * time.Millisecond)
					if processed%20 == 0 {
						fmt.Printf("  [Worker %d] Обработано %d строк транзакции XID=%d...\n",
							workerID, processed, item.XID)
					}
				}
			}
		}(i)
	}

	wg.Wait()
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// Ограниченный канал с backpressure
	eventChan := make(chan StreamedChange, 50)

	// Продюсер (имитация непрерывного поступления строк гигантской транзакции)
	go func() {
		defer close(eventChan)
		for i := 1; i <= 100; i++ {
			select {
			case <-ctx.Done():
				return
			case eventChan <- StreamedChange{XID: 9910, RowID: i, Action: "UPDATE"}:
			}
		}
	}()

	fmt.Println("Запуск потоковой обработки крупной транзакции с backpressure...")
	RunStreamingConsumer(ctx, eventChan, 2)
	fmt.Println("Потоковая обработка успешно завершена без переполнения памяти!")
}
```

## Под капотом

Когда внутренний Go-канал заполняется, горутина-ридер блокируется на операции записи `channel <- item`.
Это останавливает чтение из сетевого буфера `net.Conn`.
Буфер сокета TCP Receive Window (SO_RCVBUF) заполняется, и стек TCP ядра Linux отправляет обратно серверу PostgreSQL TCP Window Update со значением `Win=0`.
Сервер PostgreSQL мгновенно останавливает отправку WAL пакетов по протоколу TCP Flow Control, естественным образом распределяя нагрузку по всей цепочке.

## Подводные камни

1. Накопление всей транзакции в `[]*InsertMessage` до прихода `CommitMessage`: при транзакции в 10 миллионов строк процесс гарантированно получит OOM.
2. Блокировка чтения сокета без отправки KeepAlive: если воркеры тормозят дольше `wal_sender_timeout` (60с), сервер аварийно разорвет соединение. Необходимо отправлять `StandbyStatusUpdate` из независимой горутины.

## На собеседовании

В: Как в PostgreSQL 14+ включить потоковую передачу незафиксированных транзакций на уровне плагина pgoutput?
О: При вызове `StartReplication` передается опция `streaming 'on'` (или `'parallel'`).
В этом режиме PostgreSQL не держит гигантскую транзакцию в оперативной памяти сервера (ReorderBuffer) до коммита, а передает ее кусками по мере генерации изменений в WAL, оборачивая блоки в `StreamStartMessage` и `StreamStopMessage`.
Это защищает память как сервера PostgreSQL, так и консьюмера.
