# Сравнение плагинов логического декодирования: pgoutput против wal2json

## Условие

**Настройка PostgreSQL.**: Включите `wal_level = logical`, `max_replication_slots = 4`, `max_wal_senders = 10`. Создайте публикацию `CREATE PUBLICATION mypub FOR TABLE users, orders`. Создайте слот репликации (`pg_create_logical_replication_slot`). Объясните разницу между `pgoutput` (native) и `wal2json` (текстовый).

## Теория

В экосистеме PostgreSQL существуют различные плагины вывода логического декодирования:

| Параметр | Плагин `pgoutput` | Плагин `wal2json` |
| :--- | :--- | :--- |
| **Установка** | Встроен в ядро PostgreSQL («из коробки») | Требует отдельной компиляции / shared library `.so` |
| **Формат данных** | Бинарный протокол потоковой репликации | Текстовый JSON массив / строки |
| **Оверхед по сети** | Минимальный (схема шлется 1 раз) | Высокий (имена полей дублируются в каждой строке) |
| **Нагрузка на CPU** | Минимальная (прямая упаковка байт) | Высокая (сериализация JSON в ядре C) |
| **Потребление RAM** | Константное \(O(1)\) при стриминге | Огромное (при больших транзакциях весь JSON в памяти) |
| **Стандарт BigTech**| Абсолютный индустриальный стандарт | Используется только в простых pet-проектах |

В современных HighLoad-системах используется **только `pgoutput`**.

## Решение по шагам

1. Подключитесь к PostgreSQL через `pgx`.
2. Выполните проверку доступности плагинов в системном представлении `pg_available_extension_versions` или через создание временного слота.
3. Создайте слот с плагином `pgoutput`.
4. Сравните размеры сетевых пакетов для вставки 100 строк в обоих плагинах.

## Код решения

**`compare_plugins.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка соединения: %v", err)
	}
	defer db.Close()

	ctx := context.Background()

	// Проверяем существующие слоты и их плагины
	rows, err := db.QueryContext(ctx, "SELECT slot_name, plugin, slot_type, active FROM pg_replication_slots;")
	if err != nil {
		log.Fatalf("Ошибка чтения слотов: %v", err)
	}
	defer rows.Close()

	fmt.Println("=== Активные слоты логического декодирования ===")
	for rows.Next() {
		var name, plugin, slotType string
		var active bool
		_ = rows.Scan(&name, &plugin, &slotType, &active)
		fmt.Printf("• Слот: %-18s | Плагин: %-10s | Тип: %s | Активен: %t\n",
			name, plugin, slotType, active)
	}

	fmt.Println("\nРекомендация HighLoad: Всегда выбирайте нативный плагин 'pgoutput'!")
}
```

## Под капотом

Плагин `wal2json` написан на C и парсит WAL в дерево структур cJSON.
В транзакциях с 50 000 строк `wal2json` пытается сгенерировать единый JSON документ размером сотни мегабайт в оперативной памяти бэкенда PostgreSQL, что нередко вызывает аварийное падение процесса по Out Of Memory (OOM Killer).
`pgoutput` является частью официального бинарного протокола ядра PostgreSQL и передает сообщения потоково без аллокаций гигантских JSON деревьев.

## Подводные камни

1. Использование `wal2json` в production облачных БД (AWS RDS / Yandex Cloud): требует предварительной установки плагина в образ, что доступно не во всех управляемых кластерах.
2. Проблема памяти при больших транзакциях в `wal2json`: транзакция может подвесить СУБД на время генерации JSON.

## На собеседовании

В: Почему официальный коннектор Debezium отказался от wal2json в пользу pgoutput по умолчанию?
О: 1) **Производительность:** `pgoutput` работает в бинарном представлении, не расходует такты CPU на форматирование JSON и передает в разы меньше байт по сети.
2) **Доступность:** `pgoutput` встроен в дистрибутив PostgreSQL начиная с версии 10 и доступен в любом облаке без установки сторонних `.so` библиотек.
3) **Потоковая передача:** `pgoutput` поддерживает инкрементальный стриминг транзакций, тогда как `wal2json` требовал буферизации всей транзакции целиком.
