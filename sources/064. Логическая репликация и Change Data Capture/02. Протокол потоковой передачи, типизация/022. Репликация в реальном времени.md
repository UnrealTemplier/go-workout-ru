# Репликация в реальном времени: PostgreSQL CDC → Elasticsearch

## Условие

**CDC → Elasticsearch**: Синхронизируйте PostgreSQL таблицу с Elasticsearch индексом в real-time через CDC.

## Теория

Классическая архитектурная задача: PostgreSQL выступает в качестве надежной транзакционной системы (OLTP), а Elasticsearch обеспечивает мгновенный полнотекстовый поиск с опечатками и фасетную навигацию.

Паттерн near-real-time синхронизации:
1. Таблица `products` в PostgreSQL включена в публикацию CDC.
2. Go-воркер вычитывает `InsertMessage`, `UpdateMessage` и `DeleteMessage`.
3. Сообщения трансформируются в поисковые документы:
   - `Insert` / `Update` \(\to\) `IndexRequest` (или `UpdateRequest` с `doc_as_upsert: true`).
   - `Delete` \(\to\) `DeleteRequest` по идентификатору документа.
4. Документы отправляются в Elasticsearch через пакетный `esutil.NewBulkIndexer`.

## Решение по шагам

1. Спроектируйте структуру документа `ESProduct`.
2. Реализуйте функцию маппинга строки PostgreSQL в документ Elasticsearch.
3. Обработайте операцию `Insert`: отправка документа на индексацию.
4. Обработайте операцию `Delete`: удаление документа из индекса по ID.
5. Продемонстрируйте синхронизацию изменений.

## Код решения

**`pg_to_es_cdc.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
)

type ESProduct struct {
	ID          int64    `json:"id"`
	Title       string   `json:"title"`
	Description string   `json:"description"`
	Price       float64  `json:"price"`
	Categories  []string `json:"categories"`
	InStock     bool     `json:"in_stock"`
}

type ElasticSearchSink struct{}

func (s *ElasticSearchSink) Upsert(ctx context.Context, doc *ESProduct) error {
	data, _ := json.Marshal(doc)
	fmt.Printf("🔍 [ES UPSERT] Индекс 'products', DocID: %d, Data: %s\n", doc.ID, string(data))
	return nil
}

func (s *ElasticSearchSink) Delete(ctx context.Context, id int64) error {
	fmt.Printf("🗑️ [ES DELETE] Индекс 'products', Удален DocID: %d\n", id)
	return nil
}

func HandleCDCEvent(ctx context.Context, es *ElasticSearchSink, op string, row map[string]any) error {
	id := int64(row["id"].(int))

	switch op {
	case "c", "u":
		product := &ESProduct{
			ID:          id,
			Title:       row["title"].(string),
			Description: row["description"].(string),
			Price:       row["price"].(float64),
			InStock:     row["in_stock"].(bool),
		}
		return es.Upsert(ctx, product)
	case "d":
		return es.Delete(ctx, id)
	default:
		return fmt.Errorf("неизвестная операция: %s", op)
	}
}

func main() {
	es := &ElasticSearchSink{}
	ctx := context.Background()

	// 1. Пришло событие создания товара
	insertRow := map[string]any{
		"id":          501,
		"title":       "Умная колонка Яндекс Станция",
		"description": "Голосовой помощник Алиса с мощным звуком",
		"price":       14990.00,
		"in_stock":    true,
	}
	if err := HandleCDCEvent(ctx, es, "c", insertRow); err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	// 2. Пришло событие удаления товара
	deleteRow := map[string]any{"id": 501}
	if err := HandleCDCEvent(ctx, es, "d", deleteRow); err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

## Под капотом

Использование `doc_as_upsert: true` в Elasticsearch гарантирует идемпотентность: если документ с таким ID уже существовал, он обновится; если не существовал — создастся заново.
При репликации через CDC задержка между выполнением `COMMIT` в PostgreSQL и появлением документа в поисковом индексе Elasticsearch (near real-time) составляет обычно от 50 до 200 миллисекунд (зависит от `refresh_interval` в ES).

## Подводные камни

1. Поштучная отправка в Elasticsearch: одиночный HTTP-запрос на каждое CDC-событие приведет к исчерпанию HTTP пула соединений ES. Всегда группируйте события в микро-батчи через `BulkIndexer`.
2. Удаление без первичного ключа: если таблица в PG не имеет `REPLICA IDENTITY FULL`, при DELETE консьюмер получит только ключ. Этого достаточно для удаления документа из ES по его `_id`.

## На собеседовании

В: Как решить проблему Out-of-Order событий при репликации в Elasticsearch, когда старое обновление перезаписывает более свежее?
О: В Elasticsearch используется механизм **External Versioning (`version_type: "external"`)**.
В качестве версии документа передается либо номер версии транзакции (`txId`), либо `LSN` (преобразованный в uint64), либо микросекундная метка времени `updated_at`.
Если в Elasticsearch приходит событие со значением версии \(\le\) текущей версии документа в индексе, Elasticsearch автоматически отбрасывает его с ошибкой 409 Conflict, предотвращая перезапись свежих данных старыми.
