# Синхронизация с аналитической СУБД: PostgreSQL CDC → ClickHouse

## Условие

**CDC → ClickHouse**: Синхронизируйте transactional данные в аналитическую БД через CDC + Kafka.

## Теория

ClickHouse — колоночная аналитическая СУБД, оптимизированная для агрегаций над миллиардами строк, но крайне неэффективная для точечных `UPDATE` и `DELETE` (мутации требуют тяжелого фонового слияния партов).

Архитектура CDC в ClickHouse:
1. Прием данных в ClickHouse выполняется строго крупными батчами (пакетами от 10 000 до 100 000 строк).
2. Таблицы в ClickHouse создаются на специализированном движке **`ReplacingMergeTree`** или **`VersionedCollapsingMergeTree`**.
3. В каждое событие добавляются технические поля: `sign` (1 для insert/update, -1 для delete) и `version` (LSN или timestamp).
4. При фоновом слиянии (Merge) ClickHouse автоматически дедуплицирует строки, оставляя только финальное состояние каждой записи по первичному ключу.

## Решение по шагам

1. Создайте DDL целевой таблицы в ClickHouse: `orders_ch` на движке `ReplacingMergeTree(version)`.
2. Реализуйте Go-буфер для накопления CDC-событий.
3. По таймеру (каждые 2 секунды) или по объему (5 000 строк) сбрасывайте пакет в ClickHouse через Columnar Batch API.
4. Продемонстрируйте вставку нескольких версий одной строки и ее корректное схлопывание.

## Код решения

**`pg_to_ch_cdc.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type ClickHouseOrderRow struct {
	ID        int64
	Amount    float64
	Status    string
	Version   uint64 // LSN транзакции
	UpdatedAt time.Time
}

type ClickHouseBatchBuffer struct {
	mu      sync.Mutex
	buffer  []ClickHouseOrderRow
	maxSize int
}

func NewBatchBuffer(maxSize int) *ClickHouseBatchBuffer {
	return &ClickHouseBatchBuffer{
		buffer:  make([]ClickHouseOrderRow, 0, maxSize),
		maxSize: maxSize,
	}
}

func (b *ClickHouseBatchBuffer) Add(row ClickHouseOrderRow) []ClickHouseOrderRow {
	b.mu.Lock()
	defer b.mu.Unlock()

	b.buffer = append(b.buffer, row)
	if len(b.buffer) >= b.maxSize {
		flush := b.buffer
		b.buffer = make([]ClickHouseOrderRow, 0, b.maxSize)
		return flush
	}
	return nil
}

func FlushToClickHouse(ctx context.Context, batch []ClickHouseOrderRow) {
	if len(batch) == 0 {
		return
	}
	fmt.Printf("🚀 [CLICKHOUSE BATCH FLUSH] Отправлено %d строк в ReplacingMergeTree\n", len(batch))
	for i, r := range batch {
		fmt.Printf("   [%d] ID: %d | Status: %-10s | Version(LSN): %d\n",
			i+1, r.ID, r.Status, r.Version)
	}
}

func main() {
	buf := NewBatchBuffer(3)
	ctx := context.Background()

	// Имитация потока обновлений одного заказа ID=1001 через CDC
	events := []ClickHouseOrderRow{
		{ID: 1001, Amount: 500.0, Status: "created", Version: 23801000, UpdatedAt: time.Now()},
		{ID: 1001, Amount: 500.0, Status: "paid", Version: 23802000, UpdatedAt: time.Now()},
		{ID: 1001, Amount: 500.0, Status: "shipped", Version: 23803000, UpdatedAt: time.Now()},
	}

	for _, ev := range events {
		if flush := buf.Add(ev); flush != nil {
			FlushToClickHouse(ctx, flush)
		}
	}
}
```

## Под капотом

В ClickHouse движок `ReplacingMergeTree(version)` выполняет схлопывание дубликатов по ключу `ORDER BY (id)` во время слияния партов.
Строка с максимальным значением `Version` (наибольшим LSN) замещает все предыдущие промежуточные состояния.
Для аналитических запросов без ожидания слияния используется модификатор `SELECT * FROM orders_ch FINAL` или функция `argMax(status, version)`.

## Подводные камни

1. Попытка отправлять строки в ClickHouse поштучно: моментально вызовет ошибку `Too many parts in all data in table` и заблокирует вставку.
2. Неверное поле версии: использование системного времени сервера приложения `time.Now()` может привести к ошибкам при рассинхронизации часов NTP. Версией ВСЕГДА должен служить монотонно возрастающий LSN из PostgreSQL.

## На собеседовании

В: Как в ClickHouse через CDC реализовать физическое удаление данных при получении DELETE из PostgreSQL?
О: 1) **VersionedCollapsingMergeTree:** В таблицу добавляется колонка `Sign Int8`. При DELETE вставляется строка со старыми данными, тем же `Version` и `Sign = -1`. При слиянии партов строки со знаками +1 и -1 взаимно аннигилируют.
2) **Флаг `is_deleted` в ReplacingMergeTree:** При DELETE вставляется строка с `is_deleted = 1`. В аналитических представлениях добавляется фильтр `WHERE is_deleted = 0`.
