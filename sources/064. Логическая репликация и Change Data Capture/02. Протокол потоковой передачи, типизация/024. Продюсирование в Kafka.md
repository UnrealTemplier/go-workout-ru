# Продюсирование в Kafka: Партиционирование по первичному ключу и порядок

## Условие

**PostgreSQL → Kafka.**: Реализуйте producer: читаете WAL, сериализуете в Avro/JSON, публикуете в Kafka topic `db.users`, `db.orders` с key = `primary_key`. Обеспечьте ordering (same partition for same key). Объясните, как Kafka Connect Debezium делает то же самое.

## Теория

Главная гарантия, которую обязан обеспечивать любой CDC-коннектор — **сохранение строгой хронологии изменений сущности (Per-Entity Ordering)**.

Если пользователь сменил статус заказа:
`CREATED` \(\to\) `PAID` \(\to\) `CANCELLED`.
Если эти три события попадут в разные партиции Kafka, консьюмеры прочитают их параллельно, и статус `PAID` может примениться поверх `CANCELLED`, вызвав рассинхронизацию баз данных.

Архитектура надежного продюсера:
1. Вычисление первичного ключа таблицы (из метаданных `RelationMessage`).
2. Сериализация ключа в бинарный или строковый Kafka Message Key.
3. Использование `segment.bytes` и `cleanup.policy=compact` на стороне брокера Kafka для автоматического сжатия истории.

## Решение по шагам

1. Создайте структуру `KafkaMessage` с полями `Topic`, `Key []byte`, `Value []byte`, `Timestamp`.
2. Реализуйте функцию хэширования Murmur2 / FNV-1a для демонстрации детерминированного выбора партиции по ключу.
3. Продемонстрируйте, что при любых повторах ключ `orders:9901` гарантированно попадает в одну и ту же партицию из 8 доступных.
4. Выведите таблицу маршрутизации событий.

## Код решения

**`kafka_order_producer.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
)

func calculatePartition(key string, numPartitions int) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	// Гарантируем неотрицательный индекс партиции
	return int(h.Sum32()) % numPartitions
}

func main() {
	numPartitions := 8

	keys := []string{
		"users:101",
		"users:102",
		"orders:9901",
		"orders:9901", // Повторное обновление того же заказа
		"orders:9902",
	}

	fmt.Println("=== Проверка детерминированного партиционирования по ключу ===")
	for i, k := range keys {
		part := calculatePartition(k, numPartitions)
		fmt.Printf("[%d] Key: %-15s -> Target Partition: %d (из %d)\n",
			i+1, k, part, numPartitions)
	}

	fmt.Println("\nВывод: События с одинаковым ключом всегда попадают в строго одну партицию!")
}
```

ℹ️ Детерминированное партиционирование сообщений по первичному ключу строки

## Под капотом

В Apache Kafka брокер гарантирует строгий порядок сообщений (FIFO) исключительно внутри одной партиции.
Привязка `Partition = Hash(Key) % PartitionsCount` гарантирует, что ни при каких обстоятельствах два события одного заказа не попадут в разные очереди.
Даже при сбоях сети и ретраях продюсера флаг `enable.idempotence=true` в Kafka Producer предотвратит дублирование и перестарение записей на брокере.

## Подводные камни

1. Изменение количества партиций в Kafka топике на лету: при увеличении числа партиций (\(8 \to 16\)) значение `Hash(Key) % Partitions` изменится, и новые события пойдут в другую партицию, нарушив порядок с еще не вычитанными старыми событиями.
2. Использование случайного ключа при DELETE: приведет к тому, что удаление попадет в другую партицию и применится раньше вставки.

## На собеседовании

В: Что произойдет с очередностью событий CDC, если продюсер Kafka выполнит повторную отправку (retry) при сетевой ошибке, если max.in.flight.requests.per.connection > 1?
О: Без идемпотентного продюсера может возникнуть перестановка сообщений:
Пакет 1 падает по таймауту, Пакет 2 отправляется следом и успешно записывается, а затем ретрай Пакета 1 завершается успехом.
В результате Update применится раньше Insert!
Для предотвращения этого в конфигурации продюсера **обязательно** выставляют:
`enable.idempotence = true` (начиная с Kafka 3.0 включено по умолчанию) и `acks = all`.
