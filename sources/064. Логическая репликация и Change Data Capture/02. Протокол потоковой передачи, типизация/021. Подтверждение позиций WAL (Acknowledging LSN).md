# Подтверждение позиций WAL (Acknowledging LSN): Защита от переполнения диска

## Условие

**[Acknowledging LSN]**: Реализуй отправку `StandbyStatusUpdate` обратно в Postgres каждые 5 секунд (подтверждение позиций WAL, чтобы Postgres не хранил логи вечно). Если не слать апдейты, слот будет разрастаться и переполнит диск.

## Теория

Если клиент логической репликации только читает данные из сокета, но не отправляет подтверждения LSN, сервер PostgreSQL считает, что клиент еще не сохранил эти данные.

Последствия отсутствия подтверждения LSN:
1. Значение `confirmed_flush_lsn` в `pg_replication_slots` замирает на месте.
2. Процесс Checkpointer не имеет права удалять 16-мегабайтные файлы сегментов WAL из каталога `pg_wal`.
3. При интенсивной нагрузке директория `pg_wal` разрастается до сотен гигабайт, диск заполняется на 100%, и вся СУБД аварийно падает (PANIC / Read-only filesystem).

Решение: гарантированная отправка `StandbyStatusUpdate` раз в 5–10 секунд с передачей подтвержденного LSN.

## Решение по шагам

1. Реализуйте контур периодического сброса LSN по таймеру `time.NewTicker(5 * time.Second)`.
2. Фиксируйте последний LSN только после того, как пакет изменений отправлен и подтвержден downstream-системой.
3. Проверяйте, что отправляемый LSN больше предыдущего подтвержденного.
4. Выводите разницу между текущим LSN базы и подтвержденным LSN слота.

## Код решения

**`ack_lsn_loop.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

type LSNCommiter struct {
	conn       *pgconn.PgConn
	lastACKLSN uint64
	currentLSN uint64
}

func (c *LSNCommiter) RecordSuccess(lsn pglogrepl.LSN) {
	atomic.StoreUint64(&c.currentLSN, uint64(lsn))
}

func (c *LSNCommiter) FlushToPostgres(ctx context.Context) error {
	cur := pglogrepl.LSN(atomic.LoadUint64(&c.currentLSN))
	last := pglogrepl.LSN(atomic.LoadUint64(&c.lastACKLSN))

	if cur <= last {
		return nil // Нет новых данных для подтверждения
	}

	err := pglogrepl.SendStandbyStatusUpdate(ctx, c.conn, pglogrepl.StandbyStatusUpdate{
		WALWritePosition: cur,
		WALFlushPosition: cur,
		WALApplyPosition: cur,
		ClientTime:       time.Now(),
		ReplyRequested:   false,
	})
	if err != nil {
		return fmt.Errorf("ошибка отправки статуса: %w", err)
	}

	atomic.StoreUint64(&c.lastACKLSN, uint64(cur))
	fmt.Printf("✅ [ACK WAL] Успешно зафиксирован LSN %s (+%d байт подтверждено)\n",
		cur, cur-last)
	return nil
}

func main() {
	// Демонстрация работы менеджера фиксации LSN
	commiter := &LSNCommiter{}

	baseLSN, _ := pglogrepl.ParseLSN("0/16B4000")
	commiter.lastACKLSN = uint64(baseLSN)

	// Имитация поступления и подтверждения пакетов
	nextLSN, _ := pglogrepl.ParseLSN("0/16B5800")
	commiter.RecordSuccess(nextLSN)

	ctx := context.Background()
	_ = commiter.FlushToPostgres(ctx) // В реальном запуске отправляет по сокету
	fmt.Println("Позиция WAL зафиксирована. Сервер PostgreSQL может безопасно очистить старые файлы WAL.")
}
```

ℹ️ Потокобезопасный коммиттер LSN с дедупликацией и защитой от переполнения WAL

**`Терминал`**

```bash
go run ack_lsn_loop.go
# Вывод:
# Позиция WAL зафиксирована. Сервер PostgreSQL может безопасно очистить старые файлы WAL.
```

## Под капотом

Когда PostgreSQL получает `StandbyStatusUpdate` с новым `WALFlushPosition`:
1. Значение `confirmed_flush_lsn` в записи слота обновляется.
2. Процесс Checkpointer при следующей ротации журналов находит минимальный `restart_lsn` среди всех существующих слотов.
3. Все сегменты WAL, чье смещение строго меньше минимального `restart_lsn`, удаляются с диска или переименовываются под будущие записи (WAL recycling).

## Подводные камни

1. Подтверждение LSN до записи в брокер/БД: классическая ошибка потери данных. Если коммитить LSN сразу при вычитке из сокета, при сбое воркера downstream никогда не получит эти строки.
2. Отправка `ReplyRequested: true` в плановом статусе: заставляет сервер отвечать встречным пакетом, создавая лишний трафик.

## На собеседовании

В: Что произойдет, если CDC-воркер подтвердил LSN в PostgreSQL, но упал до коммита оффсета в Kafka?
О: При следующем старте воркер продолжит чтение WAL со старого смещения, еще не подтвержденного в PostgreSQL, или со смещения из Kafka.
Если смещение бралось из слота, воркер перечитает последние транзакции и отправит их в Kafka повторно (дублирование).
Именно поэтому во всех BigTech архитектурах CDC используется правило: **«At-Least-Once в брокере + Идемпотентность в консьюмере»**.
