# Динамическая маршрутизация CDC-событий по Kafka топикам

## Условие

**[Маршрутизация событий]**: Изменения таблицы `users` отправляй в Kafka topic `users_cdc`, а изменения `orders` — в `orders_cdc`.

## Теория

В реальных архитектурах база данных содержит десятки таблиц, но смешивать изменения всех таблиц в один общий топик Kafka — антипаттерн:
1. Разные таблицы читаются разными микросервисами (сервис биллинга слушает только `orders`, сервис профилей — только `users`).
2. Разные требования к Log Compaction и Retention (транзакции заказов хранятся годами, аудит сессий — 7 дней).

Паттерн динамической маршрутизации (Dynamic Topic Routing):
Консьюмер анализирует `RelationMessage.RelationName` и направляет событие в топик по шаблону `<prefix>.<schema>.<table>` (например, `cdc.public.users` и `cdc.public.orders`).

## Решение по шагам

1. Создайте роутер топиков с префиксом `cdc`.
2. Реализуйте функцию `RouteTopic(schema, table string) string`.
3. Напишите диспетчер сообщений, распределяющий события по соответствующим виртуальным продюсерам.
4. Продемонстрируйте маршрутизацию событий разных таблиц.

## Код решения

**`topic_router.go`**

```go
package main

import (
	"fmt"
)

type CDCRouter struct {
	topicPrefix string
}

func NewCDCRouter(prefix string) *CDCRouter {
	return &CDCRouter{topicPrefix: prefix}
}

func (r *CDCRouter) GetTopicName(schema, table string) string {
	return fmt.Sprintf("%s.%s.%s", r.topicPrefix, schema, table)
}

func main() {
	router := NewCDCRouter("cdc_events")

	incomingChanges := []struct {
		schema string
		table  string
		rowID  int
	}{
		{"public", "users", 101},
		{"public", "orders", 9502},
		{"public", "users", 102},
		{"public", "payments", 881},
		{"public", "orders", 9503},
	}

	fmt.Println("=== Динамическая маршрутизация CDC-событий по топикам Kafka ===")
	for i, ch := range incomingChanges {
		targetTopic := router.GetTopicName(ch.schema, ch.table)
		fmt.Printf("[%d] Изменение в %s.%-10s (ID: %d) -> Отправка в Kafka Topic: '%s'\n",
			i+1, ch.schema, ch.table, ch.rowID, targetTopic)
	}
}
```

## Под капотом

Изоляция таблиц по отдельным топикам позволяет независимо настраивать параметры партиционирования.
Например, таблица `orders` с огромным потоком данных может иметь 32 партиции и обслуживаться пулом из 32 микросервисов-воркеров, в то время как справочник `cities` может иметь всего 1 партицию с бесконечным сроком хранения compact-лога.

## Подводные камни

1. Автоматическое создание топиков брокером (auto.create.topics.enable = true): если в БД случайно создадут временную таблицу, в Kafka появится неконтролируемый топик с дефолтными неоптимальными настройками.
2. Потеря транзакционной связности: изменения разных таблиц в рамках одной транзакции разойдутся по разным топикам, и downstream-системы не смогут восстановить атомарность без специального координатора.

## На собеседовании

В: Как сохранить транзакционную консистентность, если одна бизнес-транзакция затронула таблицы users и orders, а события ушли в разные топики Kafka?
О: Для сохранения сквозной транзакционной целостности применяются два подхода:
1) **Transactional Metadata Topic:** CDC-продюсер публикует в специальный служебный топик `transaction_markers` события `Begin` и `Commit` со списком `txId` и затронутых партиций. Консьюмеры используют алгоритм слияния потоков (Stream Join) по общему `txId`.
2) **Паттерн Transactional Outbox:** Все связанные изменения упаковываются в единый агрегированный JSON документ в таблице `outbox`, откуда событие публикуется в один целевой топик агрегата.
