# Синхронизация CDC с ClickHouse: ReplacingMergeTree, _version и _sign

## Условие

**CDC → ClickHouse (Upsert).**: Реализуйте consumer: CDC-события вставляются в `ReplacingMergeTree` с дополнительными колонками `_version` (LSN) и `_sign` (1 для insert/update, -1 для delete). Покажите, как `FINAL` и `OPTIMIZE` дают актуальное состояние. Объясните, почему ClickHouse не любит deletes и как `_sign` решает это.

## Теория

Колоночная архитектура ClickHouse физически хранит данные сжатыми блоками в партовских директориях. Из-за этого классические точечные операции `DELETE` и `UPDATE` в ClickHouse требуют перезаписи сотен мегабайт данных (тяжелые мутации `ALTER TABLE UPDATE/DELETE`).

Индустриальный паттерн решения через CDC:
1. Использование движка **`ReplacingMergeTree(_version)`** или **`VersionedCollapsingMergeTree(_sign, _version)`**.
2. В каждое событие добавляются технические метаколонки:
   - `_version UInt64`: монотонно возрастающая версия (LSN из PostgreSQL).
   - `_sign Int8`: флаг состояния (`1` для Insert/Update, `-1` для Delete).
3. При вставке новых версий строки они просто дописываются в конец (Append-only).
4. Во время фонового слияния партов ClickHouse удаляет старые версии.
5. Для мгновенного чтения актуального состояния без ожидания фонового слияния используется модификатор `FINAL` или агрегатные функции `argMax`.

## Решение по шагам

1. Создайте структуру данных `CHRecord` с техническими полями `Version uint64` и `Sign int8`.
2. Реализуйте трансляцию операций:
   - `INSERT` \(\to\) `Sign: 1`, `Version: LSN`.
   - `UPDATE` \(\to\) `Sign: 1`, `Version: new_LSN`.
   - `DELETE` \(\to\) `Sign: -1`, `Version: del_LSN`.
3. Сформируйте батч для пакетной вставки.
4. Продемонстрируйте SQL-запрос `SELECT ... FINAL` для выборки актуального состояния без дубликатов.

## Код решения

**`clickhouse_cdc_upsert.go`**

```go
package main

import (
	"fmt"
	"time"
)

type CHRecord struct {
	ID        int64
	UserEmail string
	Amount    float64
	Version   uint64 // LSN
	Sign      int8   // 1 = active, -1 = deleted
	UpdatedAt time.Time
}

func TranslateCDCToClickHouse(op string, lsn uint64, row map[string]any) CHRecord {
	sign := int8(1)
	if op == "d" {
		sign = -1
	}

	amount := 0.0
	if val, ok := row["amount"].(float64); ok {
		amount = val
	}
	email := ""
	if val, ok := row["email"].(string); ok {
		email = val
	}

	return CHRecord{
		ID:        int64(row["id"].(int)),
		UserEmail: email,
		Amount:    amount,
		Version:   lsn,
		Sign:      sign,
		UpdatedAt: time.Now(),
	}
}

func main() {
	// Демонстрация жизненного цикла одной строки через CDC
	records := []CHRecord{
		TranslateCDCToClickHouse("c", 23801000, map[string]any{"id": 42, "email": "user@mail.ru", "amount": 100.0}),
		TranslateCDCToClickHouse("u", 23802500, map[string]any{"id": 42, "email": "user@mail.ru", "amount": 250.0}),
		TranslateCDCToClickHouse("d", 23804000, map[string]any{"id": 42, "email": "user@mail.ru", "amount": 250.0}),
	}

	fmt.Println("=== Поток событий для ClickHouse Replacing/CollapsingMergeTree ===")
	for i, r := range records {
		opName := "INSERT"
		if r.Sign == -1 {
			opName = "DELETE"
		} else if i > 0 {
			opName = "UPDATE"
		}
		fmt.Printf("[%s] ID=%d | Amount=%.2f | Version(LSN)=%d | Sign=%d\n",
			opName, r.ID, r.Amount, r.Version, r.Sign)
	}

	fmt.Println("\nЗапрос для выборки актуального состояния без ожидания merge:")
	fmt.Println("SELECT id, argMax(user_email, version), argMax(amount, version)")
	fmt.Println("FROM users_cdc")
	fmt.Println("GROUP BY id")
	fmt.Println("HAVING argMax(sign, version) > 0;")
}
```

## Под капотом

Связка `argMax(column, version)` с фильтром `HAVING argMax(sign, version) > 0` является наиболее производительным способом чтения дедуплицированных данных в ClickHouse.
В отличие от `SELECT ... FINAL`, который блокирует параллельную обработку стримов на уровне партов, комбинатор `argMax` компилируется в векторизованные инструкции SIMD (AVX2), обрабатывая десятки миллионов строк в секунду.

## Подводные камни

1. Злоупотребление командой `OPTIMIZE TABLE ... FINAL`: принудительное слияние партов в проде перегружает CPU и дисковую подсистему ClickHouse, замедляя выполнение аналитических запросов пользователей.
2. Неконсистентный LSN: если в качестве `_version` использовать неуникальное поле (например, секунды `time.Now().Unix()`), события внутри одной секунды могут схлопнуться в произвольном порядке.

## На собеседовании

В: Почему в ClickHouse нельзя использовать стандартный UPDATE для синхронизации CDC-потоков из PostgreSQL?
О: `UPDATE` в ClickHouse — это асинхронная тяжелая мутация (`ALTER TABLE ... UPDATE`), которая не является транзакционной.
При выполнении мутации ClickHouse переписывает физические файлы всех затронутых партов на диске.
Если в секунду поступает 10 000 обновлений строк, ClickHouse мгновенно перегрузится очередью мутаций (Mutation Queue Exhaustion) и остановит прием данных.
Единственный масштабируемый подход — потоковая вставка версий через Append-only и их последующее схлопывание через ReplacingMergeTree/CollapsingMergeTree.
