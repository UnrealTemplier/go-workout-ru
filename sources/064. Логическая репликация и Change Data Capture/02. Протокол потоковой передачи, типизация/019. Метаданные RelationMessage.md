# Метаданные RelationMessage: Идентичность реплики и флаги колонок

## Условие

**Relation messages**: Обрабатывайте Relation messages для получения схемы таблиц (column names, types). Кэшируйте их.

## Теория

Сообщение `RelationMessage` содержит исчерпывающее описание не только типов данных, но и правил репликации таблицы:
1. `RelationID` (uint32): идентификатор таблицы в СУБД.
2. `Namespace` (string): имя схемы (например, `"public"`).
3. `RelationName` (string): имя таблицы (например, `"users"`).
4. `ReplicaIdentity` (uint8): режим идентичности реплики:
   - `'d'` (`DEFAULT`): первичный ключ (Primary Key).
   - `'n'` (`NOTHING`): обновления не содержат старого ключа.
   - `'f'` (`FULL`): старое значение всей строки целиком.
   - `'i'` (`INDEX`): уникальный индекс, отличный от PK.
5. Массив `Columns`: каждый элемент содержит имя, OID типа, модификатор типа `TypeModifier` и байтовый флаг:
   - Флаг `0x01`: колонка является частью ключа идентичности реплики (`Part of Replica Identity Key`).

## Решение по шагам

1. Создайте структуру для парсинга колонок `RelationMessage`.
2. Проверьте флаг `Flags & 0x01` у каждой колонки для автоматического определения первичного ключа таблицы.
3. Проверьте значение `ReplicaIdentity`.
4. Распечатайте детальный аудит метаданных таблицы.

## Код решения

**`inspect_relation.go`**

```go
package main

import (
	"fmt"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgtype"
)

func inspectRelation(rel *pglogrepl.RelationMessage) {
	fmt.Printf("=== Метаданные таблицы %s.%s (ID: %d) ===\n",
		rel.Namespace, rel.RelationName, rel.RelationID)

	var identityMode string
	switch rel.ReplicaIdentity {
	case 'd':
		identityMode = "DEFAULT (Primary Key)"
	case 'f':
		identityMode = "FULL (Вся строка целиком)"
	case 'i':
		identityMode = "INDEX (Кастомный индекс)"
	case 'n':
		identityMode = "NOTHING (Без идентификатора)"
	default:
		identityMode = fmt.Sprintf("Unknown ('%c')", rel.ReplicaIdentity)
	}
	fmt.Printf("Режим Replica Identity: %s\n", identityMode)
	fmt.Printf("Колонки таблицы (%d шт.):\n", len(rel.Columns))

	for i, col := range rel.Columns {
		isKey := (col.Flags & 0x01) != 0
		keyMarker := " "
		if isKey {
			keyMarker = "🔑 [KEY]"
		}
		fmt.Printf("  [%d] %-15s | OID: %-5d | %s\n",
			i+1, col.Name, col.DataType, keyMarker)
	}
}

func main() {
	// Имитация RelationMessage таблицы с составным ключом
	rel := &pglogrepl.RelationMessage{
		RelationID:      99120,
		Namespace:       "public",
		RelationName:    "order_items",
		ReplicaIdentity: 'd',
		Columns: []*pglogrepl.RelationMessageColumn{
			{Name: "order_id", DataType: pgtype.Int8OID, Flags: 0x01},
			{Name: "item_id", DataType: pgtype.Int4OID, Flags: 0x01},
			{Name: "quantity", DataType: pgtype.Int4OID, Flags: 0x00},
			{Name: "price", DataType: pgtype.NumericOID, Flags: 0x00},
		},
	}

	inspectRelation(rel)
}
```

## Под капотом

Флаг `Flags & 0x01` выставляется ядром PostgreSQL на основе системного каталога `pg_index.indisreplident`.
Это позволяет CDC консьюмеру безошибочно вычислять ключ партиционирования для брокера Kafka: сообщения для строк с одинаковым первичным ключом обязаны попадать в один и тот же partition Kafka, гарантируя строгую последовательность обработки.

## Подводные камни

1. Попытка десериализовать старое значение строки при `ReplicaIdentity == 'd'`: в `UpdateMessage.OldTuple` будет `nil`, если ни одна колонка первичного ключа не изменялась в ходе апдейта.
2. Использование `REPLICA IDENTITY FULL` на таблицах с миллионами строк: генерирует колоссальный объем WAL, так как при изменении одного поля СУБД пишет в лог полное старое состояние всей строки.

## На собеседовании

В: Зачем в Kafka топиках CDC событий первичный ключ строки из PostgreSQL используют в качестве Kafka Message Key?
О: В Apache Kafka строгий порядок сообщений гарантируется только **внутри одной партиции (partition)**.
Если первичный ключ строки (например, `order_id = 42`) передается как Kafka Message Key, алгоритм хэширования гарантирует, что все события по этому заказу (Insert -> Update -> Update -> Delete) попадут в одну и ту же партицию.
Это предотвращает состояние гонки, когда Update обгоняет Insert при конкурентном чтении из разных партиций.
