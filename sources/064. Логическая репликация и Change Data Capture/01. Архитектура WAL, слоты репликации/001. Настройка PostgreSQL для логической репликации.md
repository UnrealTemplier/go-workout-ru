# Настройка PostgreSQL для логической репликации в Docker

## Условие

Настрой PostgreSQL в Docker: включи `wal_level=logical` и `max_replication_slots=10`.

## Теория

Логическая репликация (Logical Replication) в PostgreSQL базируется на декодировании журнала упреждающей записи (Write-Ahead Log, WAL) в поток логических событий изменений данных (Insert, Update, Delete).

По умолчанию PostgreSQL работает с `wal_level = replica`, что позволяет организовать только физическую потоковую репликацию (копирование байтов страниц памяти один-в-один). Для логической репликации и систем Change Data Capture (CDC) требуются специальные настройки сервера:
1. `wal_level = logical`: заставляет СУБД записывать в WAL дополнительную контекстную информацию, необходимую для восстановления логических строк кортежей (tuples) из физических страниц.
2. `max_replication_slots = 10`: максимальное количество активных слотов репликации. Слот удерживает сегменты WAL на диске до тех пор, пока их не вычитает подписчик.
3. `max_wal_senders = 10`: лимит выделенных процессов `walsender`, обслуживающих стриминг WAL клиентам.
4. Права пользователя: клиент CDC обязан обладать атрибутом `REPLICATION` или ролью `SUPERUSER`.

## Решение по шагам

1. Создайте файл конфигурации `docker-compose.yml` или команду запуска контейнера PostgreSQL 16+.
2. Передайте флаги конфигурации через параметры запуска `postgres -c wal_level=logical -c max_replication_slots=10 -c max_wal_senders=10`.
3. Напишите Go-программу, которая подключается к БД и выполняет проверку значений `wal_level` и `max_replication_slots` через SQL-запросы `SHOW <parameter>`.
4. Проверьте права текущего пользователя на запуск логической репликации (`SELECT rolreplication FROM pg_roles WHERE rolname = CURRENT_USER`).

## Код решения

**`docker-compose.yml`**

```yaml
version: '3.8'
services:
  postgres:
    image: postgres:16-alpine
    container_name: cdc_postgres
    environment:
      POSTGRES_USER: cdc_user
      POSTGRES_PASSWORD: cdc_password
      POSTGRES_DB: workout_db
    command:
      - "postgres"
      - "-c"
      - "wal_level=logical"
      - "-c"
      - "max_replication_slots=10"
      - "-c"
      - "max_wal_senders=10"
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

**`check_config.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Не удалось открыть подключение: %v", err)
	}
	defer db.Close()

	if err := db.PingContext(ctx); err != nil {
		log.Fatalf("Ошибка пинга PostgreSQL: %v", err)
	}

	var walLevel string
	var maxSlots int
	var maxSenders int

	if err := db.QueryRowContext(ctx, "SHOW wal_level;").Scan(&walLevel); err != nil {
		log.Fatalf("Ошибка проверки wal_level: %v", err)
	}
	if err := db.QueryRowContext(ctx, "SHOW max_replication_slots;").Scan(&maxSlots); err != nil {
		log.Fatalf("Ошибка проверки max_replication_slots: %v", err)
	}
	if err := db.QueryRowContext(ctx, "SHOW max_wal_senders;").Scan(&maxSenders); err != nil {
		log.Fatalf("Ошибка проверки max_wal_senders: %v", err)
	}

	var isReplicationRole bool
	err = db.QueryRowContext(ctx, `
		SELECT rolreplication OR rolsuper 
		FROM pg_roles 
		WHERE rolname = CURRENT_USER;
	`).Scan(&isReplicationRole)
	if err != nil {
		log.Fatalf("Ошибка проверки прав: %v", err)
	}

	fmt.Printf("Конфигурация PostgreSQL CDC:\n")
	fmt.Printf("• wal_level: %s (требуется 'logical')\n", walLevel)
	fmt.Printf("• max_replication_slots: %d\n", maxSlots)
	fmt.Printf("• max_wal_senders: %d\n", maxSenders)
	fmt.Printf("• Права REPLICATION у пользователя: %t\n", isReplicationRole)

	if walLevel != "logical" {
		log.Fatalf("КРИТИЧЕСКАЯ ОШИБКА: wal_level должен быть 'logical'!")
	}
	fmt.Println("✅ Сервер PostgreSQL полностью готов к логической репликации.")
}
```

## Под капотом

Параметр `wal_level=logical` изменяет формат внутренних записей в файлах WAL (`pg_wal/`).
При уровнях `minimal` и `replica` в WAL пишутся только бинарные дельты физических дисковых страниц (FPI — Full Page Images и дельты смещений). Для логического декодера этих данных недостаточно, чтобы понять, какая именно строка таблицы изменилась, какие колонки обновились и чему равнялся первичный ключ.
Уровень `logical` инструктирует ядро PostgreSQL включать идентификаторы кортежей, значения первичных ключей и метаданные транзакций в заголовки WAL-записей, увеличивая оверхед записи на диск примерно на 5-10%.

## Подводные камни

1. Попытка изменить `wal_level` через `ALTER SYSTEM SET wal_level = 'logical'`: изменение не вступит в силу без полного перезапуска сервера базы данных (параметр static, требует restart).
2. Забытый флаг `max_replication_slots`: если слотов создано больше, чем значение параметра, создание нового слота завершится ошибкой `all replication slots are in use`.
3. Отсутствие флага `REPLICATION` у пользователя приложения: попытка подключения в режиме репликации вернет ошибку `FATAL: must be superuser or replication role to start walsender`.

## На собеседовании

В: Почему изменение wal_level на 'logical' требует перезапуска PostgreSQL, и как это влияет на производительность дисковой подсистемы в HighLoad?
О: `wal_level` определяет внутреннюю архитектуру генератора записей XLOG в разделяемой памяти (`shared_buffers` и WAL buffers). Поскольку формат записей изменяется глобально, ядро СУБД не может переключить структуру на лету.
В HighLoad с миллионами транзакций `wal_level=logical` увеличивает объем генерируемого WAL трафика, так как логируются не только бинарные блоки, но и кортежи данных для логического декодирования. Это повышает утилизацию полосы пропускания диска и ускоряет ротацию 16-мегабайтных сегментов WAL.
