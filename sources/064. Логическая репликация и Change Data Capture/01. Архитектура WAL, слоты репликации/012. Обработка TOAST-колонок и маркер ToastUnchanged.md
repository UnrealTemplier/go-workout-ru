# Обработка TOAST-колонок и маркер ToastUnchanged

## Условие

**Обработка TOAST.**: Создайте таблицу с колонкой `TEXT` (>2 KB). При обновлении другой колонки покажите, что TOAST-поле передаётся как `ToastUnchanged` (не передаётся в WAL). Объясните, как обработать: либо хранить полную копию в consumer, либо делать `SELECT` из таблицы по ключу.

## Теория

Механизм TOAST (The Oversized-Attribute Storage Technique) в PostgreSQL выносит значения колонок размером более 2 КБ в отдельную системную таблицу для экономии места на страницах данных.

В логической репликации `pgoutput` оптимизирует передачу TOAST-колонок:
- При `INSERT`: значение TOAST передается целиком в `TupleData`.
- При `UPDATE`: если колонка TOAST **не была изменена**, PostgreSQL не тратит трафик на ее повторную отправку!
- В кортеже `NewTuple` тип данных такого поля равен `'u'` (`pglogrepl.TupleDataTypeToastUnchanged`), а тело байтов пустое (`len == 0`).

Стратегии обработки `ToastUnchanged` в CDC:
1. **Downstream Patch:** если в целевой системе (Elasticsearch/ClickHouse/Redis) уже хранится документ, выполняется частичное обновление (`PATCH`), не затирая старое значение.
2. **Local State Store (RocksDB):** консьюмер кэширует последнюю полную версию строки по первичному ключу.
3. **Fallback SELECT:** при получении `'u'` консьюмер делает точечный `SELECT column FROM table WHERE id = ?` в исходную БД.

## Решение по шагам

1. Создайте таблицу `articles` с колонкой `content TEXT`.
2. Вставьте статью размером > 5 КБ.
3. Выполните `UPDATE articles SET title = 'New Title' WHERE id = 1` (колонка `content` не меняется).
4. Продемонстрируйте в Go-коде, что значение `content` получено с маркером `col.DataType == 'u'`.
5. Реализуйте логику обработки через fallback SELECT по первичному ключу.

## Код решения

**`toast_handler.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	"github.com/jackc/pglogrepl"
	_ "github.com/jackc/pgx/v5/stdlib"
)

type ArticleConsumer struct {
	db *sql.DB
}

func (c *ArticleConsumer) HandleUpdate(colName string, col *pglogrepl.TupleDataColumn, articleID int) (string, error) {
	if col.DataType == 'u' { // ToastUnchanged
		fmt.Printf("Поле '%s' не изменилось (маркер 'u'). Выполняем точечный SELECT из БД...\n", colName)
		var fullContent string
		err := c.db.QueryRow("SELECT content FROM articles WHERE id = $1", articleID).Scan(&fullContent)
		if err != nil {
			return "", fmt.Errorf("ошибка fallback SELECT: %w", err)
		}
		return fullContent, nil
	}

	return string(col.Data), nil
}

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка БД: %v", err)
	}
	defer db.Close()

	consumer := &ArticleConsumer{db: db}

	// Имитация полученной колонки с маркером ToastUnchanged ('u')
	mockColumn := &pglogrepl.TupleDataColumn{
		DataType: 'u',
		Data:     nil,
	}

	articleID := 1
	val, err := consumer.HandleUpdate("content", mockColumn, articleID)
	if err != nil {
		log.Printf("Демонстрация fallback: %v", err)
	} else {
		fmt.Printf("Итоговое восстановленное значение: %s\n", val[:min(50, len(val))])
	}
}

func min(a, b int) int {
	if a < b {
		return a
	}
	return b
}
```

## Под капотом

TOAST таблицы хранят чанки данных по 2 КБ в сжатом виде (алгоритмы PGLZ или LZ4).
При обновлении строки, если TOAST-указатель (`va_pointer`) не изменился, PostgreSQL копирует старый pointer в новый кортеж без чтения чанков с диска.
В поток логической репликации `pgoutput` выдает маркер `'u'`, что экономит десятки мегабайт трафика сети и предотвращает раздувание ReorderBuffer в оперативной памяти сервера.

## Подводные камни

1. Запись пустого значения при `'u'`: если консьюмер запишет пустую строку `""` или `NULL` в downstream базу (Elasticsearch), данные большого поля будут стерты при первом же апдейте любого другого поля.
2. Массовые fallback SELECT в продакшене: если при каждом апдейте делать SELECT обратно в мастер-базу, это создаст колоссальную нагрузку на пул соединений. Рекомендуется использовать `REPLICA IDENTITY FULL` или локальное состояние (Stateful CDC).

## На собеседовании

В: Как избежать необходимости делать fallback SELECT при обработке ToastUnchanged полей в CDC?
О: 1) **REPLICA IDENTITY FULL:** Не решает проблему TOAST для неизмененных полей (они все равно шлются как 'u').
2) **Stateful Stream Processing:** Хранение последнего состояния объекта в локальном KV-хранилище воркера (RocksDB или BadgerDB). При получении 'u' воркер берет старое значение поля из RocksDB и мерджит его с новыми колонками.
3) **Частичное обновление (Partial Update):** Отправлять в downstream-систему (например, Kafka/Elasticsearch) только измененные поля, не требуя полной реконструкции всей строки.
