# Пакет jackc/pglogrepl: Бинарный протокол потоковой репликации

## Условие

**pgoutput protocol**: Используйте `pglogrepl` пакет (`github.com/jackc/pglogrepl`) для чтения изменений через pgoutput protocol.

## Теория

Библиотека `github.com/jackc/pglogrepl` — это официальная реализация протокола логической и физической репликации PostgreSQL для экосистемы Go (созданная автором `pgx`).

В отличие от ORM и `database/sql`, `pglogrepl` работает непосредственно с бинарными фреймами:
- Управление соединением через `pgconn.PgConn`.
- Команды протокола репликации: `IDENTIFY_SYSTEM`, `CREATE_REPLICATION_SLOT`, `START_REPLICATION`, `DROP_REPLICATION_SLOT`.
- Парсинг системных параметров: получение системного идентификатора кластера (`SystemID`), текущей эпохи таймлайна (`Timeline`) и начального LSN (`XLogPos`).

## Решение по шагам

1. Подключитесь к PostgreSQL с параметром `replication=database`.
2. Вызовите функцию `pglogrepl.IdentifySystem(ctx, conn)`.
3. Распарсите и выведите поля: `SystemID`, `Timeline`, `XLogPos`, `DBName`.
4. Проверьте соответствие имени базы данных.

## Код решения

**`identify_system.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

func main() {
	ctx := context.Background()
	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"

	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка подключения к сокету репликации: %v", err)
	}
	defer conn.Close(ctx)

	// Выполняем базовую команду протокола репликации IDENTIFY_SYSTEM
	sysInfo, err := pglogrepl.IdentifySystem(ctx, conn)
	if err != nil {
		log.Fatalf("Ошибка IdentifySystem: %v", err)
	}

	fmt.Println("=== Системная информация PostgreSQL Replication ===")
	fmt.Printf("• System ID:  %s\n", sysInfo.SystemID)
	fmt.Printf("• Timeline:   %d\n", sysInfo.Timeline)
	fmt.Printf("• Current LSN: %s\n", sysInfo.XLogPos)
	fmt.Printf("• DB Name:    %s\n", sysInfo.DBName)
}
```

ℹ️ Выполнение низкоуровневой команды протокола репликации IdentifySystem

**`Терминал`**


## Под капотом

Команда `IDENTIFY_SYSTEM` отправляется на бэкенд PostgreSQL в виде строковой команды протокола репликации (аналог SQL запроса, но исполняемый напрямую процессом `walsender` до входа в парсер SQL).
Сервер возвращает системный идентификатор кластера (64-битное случайное число, генерируемое при `initdb`), номер текущей временной шкалы (TimelineID) и позицию текущего хвоста WAL. Это гарантирует, что клиент подключается именно к тому кластеру СУБД, от которого ожидает получать изменения.

## Подводные камни

1. Подключение к реплике (Standby) без каскадной репликации: создание слотов логической репликации на standby-нодах поддерживается только начиная с PostgreSQL 16+. В старых версиях логический слот можно создавать строго на Primary.
2. Несоответствие `TimelineID`: при переключении мастера (failover / switchover) таймлайн инкрементируется (\(1 \to 2\)). CDC-консьюмер обязан уметь продолжать репликацию через границу смены таймлайна.

## На собеседовании

В: Зачем в протоколе репликации используется TimelineID, и что происходит при продвижении реплики в новый Primary (failover)?
О: `TimelineID` предотвращает коллизии и раздвоение истории WAL после аварийных сбоев.
Когда старый Primary падает, а Standby продвигается в новый Primary, таймлайн увеличивается на 1 (\(TL_1 \to TL_2\)), и нумерация LSN продолжается в новой ветке истории.
Благодаря проверке `TimelineID` клиенты репликации и реплики никогда не спутают сегменты WAL старого изолированного мастера с новыми сегментами нового лидера кластера.
