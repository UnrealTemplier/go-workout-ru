# Управление публикациями: FOR ALL TABLES vs целевые таблицы

## Условие

**Logical replication в PostgreSQL**: Включите `wal_level = logical` в `postgresql.conf`. Создайте publication для таблиц.

## Теория

Публикация (`PUBLICATION`) — это фильтр на уровне ядра PostgreSQL, определяющий, какие именно таблицы и операции логируются для репликации.

Ключевые режимы создания публикаций:
1. `CREATE PUBLICATION pub FOR ALL TABLES;`
   - Логирует изменения абсолютно всех таблиц базы данных (включая создаваемые в будущем).
   - Требует прав суперпользователя (`SUPERUSER`).
2. `CREATE PUBLICATION pub FOR TABLE users, accounts;`
   - Логирует только явно перечисленные таблицы.
3. Фильтрация по операциям (`WITH (publish = 'insert, update')`):
   - Позволяет исключить удаление (`delete`) или усечение (`truncate`).
4. Построчная фильтрация (Row Filter, появилось в PG 15+):
   - `CREATE PUBLICATION active_users FOR TABLE users WHERE (status = 'active');` — реплицируются только строки, удовлетворяющие предикату.

## Решение по шагам

1. Создайте через Go таблицы `users` и `audit_logs`.
2. Создайте публикацию `app_pub`, включающую только таблицу `users` с операциями `INSERT` и `UPDATE`.
3. Запросите метаданные публикации из системного представления `pg_publication_tables`.
4. Продемонстрируйте динамическое добавление таблицы в публикацию через `ALTER PUBLICATION app_pub ADD TABLE audit_logs;`.

## Код решения

**`manage_publication.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка открытия БД: %v", err)
	}
	defer db.Close()

	ctx := context.Background()

	// 1. Создаем схемы таблиц
	initSQL := `
		CREATE TABLE IF NOT EXISTS users (
			id SERIAL PRIMARY KEY,
			email VARCHAR(255) NOT NULL,
			status VARCHAR(50) NOT NULL
		);
		CREATE TABLE IF NOT EXISTS audit_logs (
			id SERIAL PRIMARY KEY,
			action VARCHAR(100) NOT NULL
		);
		DROP PUBLICATION IF EXISTS selective_pub;
		CREATE PUBLICATION selective_pub FOR TABLE users WITH (publish = 'insert, update');
	`
	if _, err := db.ExecContext(ctx, initSQL); err != nil {
		log.Fatalf("Ошибка создания публикации: %v", err)
	}
	fmt.Println("Публикация 'selective_pub' создана для таблицы 'users' (только INSERT, UPDATE).")

	// 2. Проверяем состав публикации
	queryTables := func() {
		rows, err := db.QueryContext(ctx, "SELECT tablename FROM pg_publication_tables WHERE pubname = 'selective_pub';")
		if err != nil {
			log.Fatalf("Ошибка чтения pg_publication_tables: %v", err)
		}
		defer rows.Close()

		fmt.Print("Таблицы в публикации: ")
		var tables []string
		for rows.Next() {
			var t string
			_ = rows.Scan(&t)
			tables = append(tables, t)
		}
		fmt.Printf("%v\n", tables)
	}

	queryTables()

	// 3. Динамически добавляем таблицу audit_logs
	fmt.Println("Добавляем таблицу 'audit_logs' в публикацию...")
	if _, err := db.ExecContext(ctx, "ALTER PUBLICATION selective_pub ADD TABLE audit_logs;"); err != nil {
		log.Fatalf("Ошибка ALTER PUBLICATION: %v", err)
	}

	queryTables()
}
```

ℹ️ Декларативное управление публикациями и динамическое изменение состава таблиц

## Под капотом

Метаданные публикаций хранятся в системных каталогах `pg_publication` и `pg_publication_rel`.
Когда транзакция выполняет изменения строк, движок PostgreSQL проверяет, входит ли изменяемая таблица хотя бы в одну активную публикацию.
Если да, декодер `pgoutput` транслирует изменения в сокет логической репликации. Если таблица не включена в публикацию, изменения полностью игнорируются плагином логического декодирования, не создавая лишнего оверхеда на сеть и сериализацию.

## Подводные камни

1. Использование `FOR ALL TABLES` в продакшене без разбора: в публикацию попадут технические таблицы очередей, временные таблицы сессий и таблицы логов, генерируя гигантский мусорный CDC-трафик.
2. Пропуск `ALTER PUBLICATION ADD TABLE` при создании новой бизнес-таблицы: изменения новой таблицы тихо не будут попадать в CDC-пайплайн.
3. Добавление таблицы без Primary Key или `REPLICA IDENTITY`: операции `UPDATE` и `DELETE` будут завершаться ошибкой транзакции в СУБД.

## На собеседовании

В: Что произойдет при выполнении UPDATE в таблице, входящей в публикацию, если у таблицы нет первичного ключа (Primary Key)?
О: Если у таблицы нет первичного ключа и `REPLICA IDENTITY` установлена по умолчанию (`DEFAULT`), PostgreSQL выбросит ошибку при попытке выполнить `UPDATE` или `DELETE`:
`ERROR: cannot update table "t" because it does not have a replica identity and publishes updates`.
Для решения проблемы необходимо либо добавить `PRIMARY KEY`, либо изменить идентичность реплики на `ALTER TABLE t REPLICA IDENTITY FULL` (что заставит СУБД писать в WAL старые значения абсолютно всех колонок строки).
