# Создание публикации и слота репликации через jackc/pglogrepl

## Условие

Создай публикацию (`CREATE PUBLICATION my_pub FOR ALL TABLES;`) и слот логической репликации через Go-код (`pglogrepl.CreateReplicationSlot`).

## Теория

Архитектура логической репликации PostgreSQL состоит из двух ключевых компонентов:
1. **Publication (Публикация):** декларативный список таблиц, изменения которых транслируются подписчикам. Создается через SQL-команду `CREATE PUBLICATION name FOR ALL TABLES` или `FOR TABLE t1, t2`.
2. **Replication Slot (Слот репликации):** механизм на стороне сервера, гарантирующий, что PostgreSQL не удалит сегменты WAL с диска до тех пор, пока их не подтвердит конкретный клиент.

Для управления слотами из Go используется низкоуровневая библиотека `github.com/jackc/pglogrepl`, работающая поверх бинарного протокола потоковой репликации PostgreSQL. Слот привязывается к логическому плагину декодирования — стандартом для Go является встроенный плагин `pgoutput`.

## Решение по шагам

1. Подключитесь к PostgreSQL с параметром `replication=database` в строке подключения.
2. Создайте тестовую таблицу `orders` и публикацию `orders_pub`.
3. С помощью функции `pglogrepl.CreateReplicationSlot` создайте слот логической репликации с плагином `pgoutput`.
4. Получите и выведите начальный `ConsistentPoint` (LSN создания слота) и имя снимка данных `SnapshotName`.
5. Проверьте наличие слота в системном каталоге `pg_replication_slots`.

## Код решения

**`create_slot.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// 1. Обычное соединение для создания схемы и публикации
	normalConn, err := pgconn.Connect(ctx, "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable")
	if err != nil {
		log.Fatalf("Ошибка подключения к БД: %v", err)
	}
	defer normalConn.Close(ctx)

	// Создаем тестовую таблицу и публикацию
	setupSQL := `
		CREATE TABLE IF NOT EXISTS orders (
			id SERIAL PRIMARY KEY,
			customer_id INT NOT NULL,
			amount NUMERIC(10,2) NOT NULL,
			created_at TIMESTAMPTZ DEFAULT NOW()
		);
		DROP PUBLICATION IF EXISTS orders_pub;
		CREATE PUBLICATION orders_pub FOR TABLE orders;
	`
	if err := normalConn.Exec(ctx, setupSQL).Close(); err != nil {
		log.Fatalf("Ошибка инициализации публикации: %v", err)
	}
	fmt.Println("Таблица 'orders' и публикация 'orders_pub' успешно подготовлены.")

	// 2. Специальное соединение в режиме репликации (replication=database)
	replConnStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"
	replConn, err := pgconn.Connect(ctx, replConnStr)
	if err != nil {
		log.Fatalf("Ошибка подключения в режиме репликации: %v", err)
	}
	defer replConn.Close(ctx)

	slotName := "orders_cdc_slot"

	// 3. Создаем слот логической репликации с плагином pgoutput
	res, err := pglogrepl.CreateReplicationSlot(
		ctx,
		replConn,
		slotName,
		"pgoutput",
		pglogrepl.CreateReplicationSlotOptions{
			Temporary:      false,
			SnapshotAction: "EXPORT_SNAPSHOT",
		},
	)
	if err != nil {
		log.Fatalf("Ошибка создания слота репликации: %v", err)
	}

	fmt.Printf("Слот репликации успешно создан!\n")
	fmt.Printf("• Имя слота: %s\n", res.SlotName)
	fmt.Printf("• Consistent Point (LSN): %s\n", res.ConsistentPoint)
	fmt.Printf("• Snapshot Name: %s\n", res.SnapshotName)
	fmt.Printf("• Плагин: %s\n", res.OutputPlugin)
}
```

## Под капотом

Когда клиент вызывает `CreateReplicationSlot`, PostgreSQL выполняет:
1. Выделение записи в системной таблице слотов в `shared_memory`.
2. Фиксацию текущей позиции WAL — `ConsistentPoint` (LSN). Начиная с этого LSN, ни один сегмент WAL не будет удален чеклистом `pg_wal`.
3. Создание снимка состояния транзакций (`SnapshotAction: EXPORT_SNAPSHOT`), который можно использовать в отдельной транзакции (`SET TRANSACTION SNAPSHOT`) для начальной выгрузки данных (Initial Snapshot / Backfill) без риска пропустить или сдублировать строки.

## Подводные камни

1. Создание слота репликации и последующее игнорирование чтения: если слот создан, но приложение упало или не читает поток, PostgreSQL будет накапливать WAL на диске до 100% заполнения файловой системы.
2. Подключение без query-параметра `replication=database`: PostgreSQL воспримет подключение как обычную SQL сессию и вернет ошибку при вызове команд репликации.
3. Повторный вызов `CreateReplicationSlot` с существующим именем без проверки: вернет ошибку `replication slot "orders_cdc_slot" already exists`.

## На собеседовании

В: Зачем функция CreateReplicationSlot возвращает SnapshotName, и как его используют в промышленных CDC-пайплайнах (например, в Debezium)?
О: `SnapshotName` позволяет решить проблему согласованного начального чтения (Initial Snapshot).
Если таблица уже содержит миллионы строк на момент создания слота:
1) Создается слот репликации с экспортом снимка (`EXPORT_SNAPSHOT`).
2) В отдельном пуле воркеров запускаются параллельные `SELECT *` в транзакции с `SET TRANSACTION SNAPSHOT '<SnapshotName>'`, читая консистентный срез данных на момент времени \(T_0\).
3) По завершении выгрузки включается потоковое чтение слота репликации ровно с точки `ConsistentPoint` (\(T_0\)), что обеспечивает переход от батч-выгрузки к потоку без пропусков и дубликатов.
