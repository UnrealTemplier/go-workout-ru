# Сквозной парсинг XLogData: Begin, Commit, DML и TypeMessage

## Условие

**Parse WAL messages**: Парсите `XLogData` сообщения: `Begin`, `Commit`, `Insert`, `Update`, `Delete`, `Relation`, `Type`.

## Теория

Содержимое пакета `XLogData` плагина `pgoutput` может содержать не только стандартные операции над строками (Insert, Update, Delete), но и метаинформацию о типах данных:
1. `TypeMessage ('Y')`: передает описание пользовательских типов данных (типы ENUM, Composite Types, Domains). Содержит `DataTypeID`, имя схемы и имя типа.
2. `BeginMessage ('B')`: открывает логическую границу транзакции.
3. `RelationMessage ('R')`: объявляет структуру таблицы.
4. `CommitMessage ('C')`: закрывает транзакцию и фиксирует LSN на диске.

Потоковый парсер `pglogrepl.Parse` возвращает полиморфный интерфейс `pglogrepl.Message`, позволяя в одном цикле диспетчеризировать события всех типов.

## Решение по шагам

1. Создайте в PostgreSQL пользовательский ENUM-тип `order_status` ('pending', 'paid', 'shipped').
2. Запустите репликацию через `pglogrepl.StartReplication`.
3. При чтении `XLogData` вызовите `pglogrepl.Parse`.
4. Реализуйте обработчики для всех типов сообщений: `*pglogrepl.TypeMessage`, `*pglogrepl.BeginMessage`, `*pglogrepl.RelationMessage`, `*pglogrepl.InsertMessage`, `*pglogrepl.CommitMessage`.
5. Выведите детальную статистику разобранных сообщений.

## Код решения

**`full_parser.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgproto3"
)

func main() {
	ctx := context.Background()
	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"

	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer conn.Close(ctx)

	slotName := "orders_cdc_slot"
	_ = pglogrepl.StartReplication(ctx, conn, slotName, pglogrepl.LSN(0), pglogrepl.StartReplicationOptions{
		PluginArgs: []string{"proto_version '1'", "publication_names 'orders_pub'"},
	})

	fmt.Println("Слушаем поток WAL. Ожидание событий...")

	customTypes := make(map[uint32]string)

	for {
		rawMsg, err := conn.ReceiveMessage(ctx)
		if err != nil {
			log.Fatalf("Ошибка чтения: %v", err)
		}

		copyData, ok := rawMsg.(*pgproto3.CopyData)
		if !ok || copyData.Data[0] != pglogrepl.XLogDataByteID {
			continue
		}

		xld, err := pglogrepl.ParseXLogData(copyData.Data[1:])
		if err != nil {
			continue
		}

		logicalMsg, err := pglogrepl.Parse(xld.WALData)
		if err != nil {
			continue
		}

		switch m := logicalMsg.(type) {
		case *pglogrepl.TypeMessage:
			customTypes[m.DataType] = fmt.Sprintf("%s.%s", m.Namespace, m.Name)
			fmt.Printf("📦 [TYPE] OID=%d, CustomType: %s.%s\n",
				m.DataType, m.Namespace, m.Name)

		case *pglogrepl.BeginMessage:
			fmt.Printf("▶ [BEGIN] XID=%d, FinalLSN=%s\n", m.Xid, m.FinalLSN)

		case *pglogrepl.RelationMessage:
			fmt.Printf("📋 [RELATION] ID=%d (%s.%s)\n", m.RelationID, m.Namespace, m.RelationName)

		case *pglogrepl.InsertMessage:
			fmt.Printf("➕ [INSERT] RelID=%d\n", m.RelationID)

		case *pglogrepl.UpdateMessage:
			fmt.Printf("✏️ [UPDATE] RelID=%d\n", m.RelationID)

		case *pglogrepl.DeleteMessage:
			fmt.Printf("❌ [DELETE] RelID=%d\n", m.RelationID)

		case *pglogrepl.CommitMessage:
			fmt.Printf("✔ [COMMIT] CommitLSN=%s\n", m.CommitLSN)
		}
	}
}
```

ℹ️ Обработка всех типов сообщений логической репликации включая TypeMessage

## Под капотом

`TypeMessage` отправляется сервером перед `RelationMessage`, если в таблице используются составные типы или enum, определенные пользователем (`CREATE TYPE`).
Это позволяет консьюмеру зарегистрировать кодеки десериализации в локальном пуле типов до того, как начнется обработка кортежей строк, содержащих эти OID.

## Подводные камни

1. Игнорирование `TypeMessage`: при наличии кастомных enum или доменов декодер кортежей не сможет определить строковое значение и упадет с ошибкой десериализации.
2. Неполный type switch: появление новых типов сообщений в будущих версиях PostgreSQL (например, `StreamStartMessage` при `streaming = on`) вызовет пропуск сообщений, если нет ветки `default`.

## На собеседовании

В: Что такое StreamStartMessage и StreamStopMessage в протоколе pgoutput (PostgreSQL 14+), и зачем они нужны?
О: При включенном параметре `streaming = on` в `StartReplication`, PostgreSQL не ждет коммита для гигантских транзакций (например, вставка 50 млн строк в `COPY`), а начинает передавать изменения порциями (chunks) между сообщениями `StreamStart` и `StreamStop`.
Это предотвращает переполнение дискового кэша ReorderBuffer на стороне СУБД, но требует от CDC консьюмера способности сохранять промежуточные куски транзакций во временное хранилище (RocksDB/RAM) до получения финального `StreamCommit`.
