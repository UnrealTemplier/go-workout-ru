# StartReplication: Параметры плагина pgoutput и Log Sequence Number (LSN)

## Условие

**StartReplication**: Вызовите `StartReplication` с `StartReplicationOptions{PluginArgs: ...}`. Поймите LSN (Log Sequence Number).

## Теория

Команда `START_REPLICATION` запускает фактическую потоковую передачу данных из указанного слота.

Формат LSN (Log Sequence Number):
- LSN представляет собой 64-битное целое число (`uint64`), определяющее байтовое смещение в истории WAL с момента инициализации кластера.
- В текстовом виде LSN представляется шестнадцатеричной парой через слэш: `F/16B3420`, где левая часть — идентификатор сегментного лог-файла, а правая — смещение байта внутри сегмента.

Параметры плагина `pgoutput` (`PluginArgs`):
- `proto_version '1'`: версия бинарного протокола сообщений `pgoutput`.
- `publication_names 'pub1,pub2'`: список публикаций, из которых нужно стримить изменения.
- `binary 'true'`: передача бинарных значений вместо текстового формата (ускоряет парсинг целых чисел, float и дат).
- `messages 'true'`: включение логических сообщений (`pg_logical_emit_message`).

## Решение по шагам

1. Преобразуйте текстовую строку LSN (например, `"0/16B3000"`) в тип `pglogrepl.LSN` через функцию `pglogrepl.ParseLSN`.
2. Сформируйте массив строковых параметров плагина `PluginArgs`.
3. Запустите репликацию методом `pglogrepl.StartReplication`.
4. Продемонстрируйте арифметические операции над LSN (сравнение, разница в байтах).

## Код решения

**`start_replication_options.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

func main() {
	ctx := context.Background()

	// Демонстрация работы с Log Sequence Number (LSN)
	lsn1, err := pglogrepl.ParseLSN("0/16B3000")
	if err != nil {
		log.Fatalf("Ошибка парсинга LSN: %v", err)
	}
	lsn2, _ := pglogrepl.ParseLSN("0/16B4000")

	fmt.Printf("LSN 1: %s (uint64: %d)\n", lsn1, uint64(lsn1))
	fmt.Printf("LSN 2: %s (uint64: %d)\n", lsn2, uint64(lsn2))
	fmt.Printf("Разница между LSN: %d байт (%.2f КБ WAL)\n\n",
		lsn2-lsn1, float64(lsn2-lsn1)/1024)

	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"
	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer conn.Close(ctx)

	// Конфигурация плагина pgoutput
	options := pglogrepl.StartReplicationOptions{
		Timeline: 0, // 0 = текущий активный таймлайн
		Mode:     pglogrepl.LogicalReplication,
		PluginArgs: []string{
			"proto_version '1'",
			"publication_names 'orders_pub'",
			"messages 'true'",
		},
	}

	slotName := "orders_cdc_slot"
	startLSN := pglogrepl.LSN(0) // 0 означает старт с последнего подтвержденного restart_lsn

	err = pglogrepl.StartReplication(ctx, conn, slotName, startLSN, options)
	if err != nil {
		log.Fatalf("Ошибка вызова StartReplication: %v", err)
	}

	fmt.Printf("Потоковая логическая репликация успешно запущена со слота '%s' с позиции LSN %s!\n",
		slotName, startLSN)
}
```

ℹ️ Парсинг LSN, расчет смещений и вызов StartReplication с расширенными опциями плагина

## Под капотом

Тип `pglogrepl.LSN` в Go объявлен как `type LSN uint64`.
Старшие 32 бита содержат номер файла сегмента WAL (`000000010000000000000001`), а младшие 32 бита — смещение байта внутри этого файла (от 0 до 16 МБ).
Благодаря представлению в виде 64-битного целого числа, сравнение хронологии событий выполняется обычной операцией `lsn1 < lsn2` без десериализации строк.

## Подводные камни

1. Передача некорректной версии `proto_version`: плагин `pgoutput` в версиях PostgreSQL 10–13 поддерживает только версию `'1'`. Передача `'2'` без проверки версии СУБД приведет к ошибке старта.
2. Передача несуществующего имени публикации: репликация запустится, но клиент не получит ни одного события изменения таблиц.
3. Попытка стартовать с LSN больше текущего конца WAL (`pg_current_wal_lsn()`): вызовет ошибку `requested starting point is in the future`.

## На собеседовании

В: Что означает передача LSN=0 в функцию StartReplication?
О: Если передать `startLSN = 0`, PostgreSQL начинает репликацию не с начала истории базы, а с позиции `restart_lsn`, зафиксированной в самом слоте репликации на сервере.
Это избавляет приложение от необходимости хардкодить LSN при первом старте: сервер сам отдаст минимальный LSN, необходимый для сохранения согласованности данных.
