# Чтение WAL потока и протокол подтверждений (KeepAlive и Feedback)

## Условие

**Чтение WAL через Go.**: Используйте `jackc/pglogrepl` для подключения к слоту: `StartReplication`, цикл `WaitForReplicationMessage`. Обрабатывайте `PrimaryKeepaliveMessage` (отправляйте `StandbyStatusMessage` с `replyRequested`). Объясните, почему PostgreSQL может отключить клиента, если он не шлёт feedback.

## Теория

Протокол потоковой логической репликации PostgreSQL работает поверх сокета в асинхронном режиме. Сервер отправляет сообщения клиенту непрерывно.

Критически важный механизм протокола — **Standby Status Updates (Feedback)**:
1. Сервер `walsender` периодически отправляет клиенту сообщение `PrimaryKeepaliveMessage`.
2. Если в сообщении выставлен флаг `ReplyRequested == 1`, клиент **обязан немедленно** отправить серверу ответное сообщение `StandbyStatusUpdate`.
3. В сообщении подтверждения клиент сообщает три смещения LSN:
   - `WALWritePosition`: позиция, записанная клиентом на диск/в буфер.
   - `WALFlushPosition`: позиция, гарантированно сброшенная (fsync / ack от Kafka).
   - `WALApplyPosition`: позиция, примененная downstream-системой.
4. Если клиент не отвечает дольше тайм-аута `wal_sender_timeout` (по умолчанию 60 секунд), сервер принудительно разрывает TCP-соединение!

## Решение по шагам

1. Подключитесь к слоту репликации через `pglogrepl.StartReplication`.
2. Задайте параметры плагина `proto_version '1'` и `publication_names 'orders_pub'`.
3. В цикле вызывайте `pglogrepl.WaitForReplicationMessage` с контекстом и тайм-аутом.
4. При получении `*pglogrepl.PrimaryKeepaliveMessage` обновите локальный LSN и отправьте `pglogrepl.SendStandbyStatusUpdate`.
5. Логируйте полученные LSN и время ответа сервера.

## Код решения

**`stream_keepalive.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgproto3"
)

func main() {
	ctx := context.Background()
	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"

	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer conn.Close(ctx)

	slotName := "orders_cdc_slot"
	pluginArguments := []string{
		"proto_version '1'",
		"publication_names 'orders_pub'",
	}

	// Запуск потоковой репликации с LSN 0
	err = pglogrepl.StartReplication(
		ctx,
		conn,
		slotName,
		pglogrepl.LSN(0),
		pglogrepl.StartReplicationOptions{
			PluginArgs: pluginArguments,
		},
	)
	if err != nil {
		log.Fatalf("Ошибка StartReplication: %v", err)
	}

	fmt.Printf("Потоковая репликация запущена для слота '%s'...\n", slotName)

	var lastReceivedLSN pglogrepl.LSN

	for {
		// Ожидаем сообщение из сокета
		msgCtx, msgCancel := context.WithTimeout(ctx, 10*time.Second)
		rawMsg, err := conn.ReceiveMessage(msgCtx)
		msgCancel()

		if err != nil {
			if pgconn.Timeout(err) {
				// Периодический feedback для предотвращения разрыва соединения
				sendFeedback(ctx, conn, lastReceivedLSN)
				continue
			}
			log.Fatalf("Ошибка получения сообщения: %v", err)
		}

		switch msg := rawMsg.(type) {
		case *pgproto3.CopyData:
			switch msg.Data[0] {
			case pglogrepl.PrimaryKeepaliveMessageByteID:
				pkm, err := pglogrepl.ParsePrimaryKeepaliveMessage(msg.Data[1:])
				if err != nil {
					log.Printf("Ошибка парсинга Keepalive: %v", err)
					continue
				}

				if pkm.ServerWALEnd > lastReceivedLSN {
					lastReceivedLSN = pkm.ServerWALEnd
				}

				fmt.Printf("[KEEPALIVE] ServerWALEnd: %s, ReplyRequested: %v\n",
					pkm.ServerWALEnd, pkm.ReplyRequested)

				if pkm.ReplyRequested {
					sendFeedback(ctx, conn, lastReceivedLSN)
				}
			}
		}
	}
}

func sendFeedback(ctx context.Context, conn *pgconn.PgConn, lsn pglogrepl.LSN) {
	err := pglogrepl.SendStandbyStatusUpdate(
		ctx,
		conn,
		pglogrepl.StandbyStatusUpdate{
			WALWritePosition: lsn,
			WALFlushPosition: lsn,
			WALApplyPosition: lsn,
			ClientTime:       time.Now(),
			ReplyRequested:   false,
		},
	)
	if err != nil {
		log.Printf("Ошибка отправки StandbyStatusUpdate: %v", err)
		return
	}
	fmt.Printf("-> Отправлен StandbyStatusUpdate: LSN %s\n", lsn)
}
```


## Под капотом

Процесс `walsender` на стороне PostgreSQL содержит таймер `wal_sender_timeout` (по умолчанию 60с).
Каждые `wal_sender_timeout / 2` (обычно 30с) сервер отправляет сообщение `PrimaryKeepaliveMessage` со смещением текущего конца WAL `ServerWALEnd`.
Если клиент шлет ответное сообщение `StandbyStatusUpdate`, сервер сбрасывает сторожевой таймер и обновляет поля `confirmed_flush_lsn` и `restart_lsn` в представлении `pg_replication_slots`. Если ответ не приходит за 60 секунд, сервер считает сокет зависшим (half-open TCP) и убивает форк-процесс.

## Подводные камни

1. Игнорирование отправки `StandbyStatusUpdate`: сервер принудительно закроет соединение по таймауту ровно через 60 секунд.
2. Подтверждение LSN до гарантированной обработки: если подтвердить `WALFlushPosition` до отправки сообщения в Kafka или персистентный диск, при внезапном сбое приложения данные будут безвозвратно утеряны.
3. Отправка `ReplyRequested: true` в ответ на keepalive: спровоцирует бесконечный пинг-понг сообщений между клиентом и сервером, нагружая CPU.

## На собеседовании

В: В чем разница между WALWritePosition, WALFlushPosition и WALApplyPosition в структуре StandbyStatusUpdate?
О: 1) **WALWritePosition:** LSN, который клиент прочитал из сокета и сохранил в оперативную память (буфер приложения).
2) **WALFlushPosition:** LSN, который гарантированно сброшен на персистентное хранилище (выполнен `fsync` на диск или получен Ack от брокера сообщений Kafka/RabbitMQ). Именно этот LSN использует PostgreSQL для очистки старых WAL сегментов с диска!
3) **WALApplyPosition:** LSN, который применен в целевой базе данных (актуально для физических реплик standby, когда WAL применен к файлам данных таблицы).
