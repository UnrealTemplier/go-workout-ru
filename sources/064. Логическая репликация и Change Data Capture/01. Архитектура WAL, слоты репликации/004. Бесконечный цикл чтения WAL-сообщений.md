# Бесконечный цикл чтения WAL-сообщений и обработка сигналов

## Условие

Запусти репликацию (`pglogrepl.StartReplication`). Напиши бесконечный цикл, который читает WAL (Write-Ahead Log) сообщения.

## Теория

Сервис Change Data Capture (CDC) — это непрерывный фоновый демон (daemon/worker), который должен надежно функционировать месяцами.

Требования к надежному циклу чтения WAL:
1. **Graceful Shutdown:** перехват системных сигналов ОС (`SIGINT`, `SIGTERM`), корректное завершение текущей транзакции WAL, отправка финального подтверждения LSN и закрытие соединения.
2. **Backoff при отсутствии данных:** протокол репликации не блокирует поток навечно — при тайм-ауте `ReceiveMessage` воркер шлет keepalive и проверяет контекст.
3. **Разделение типов сообщений:** чтение обернуто в транспортный конверт `CopyData` протокола PostgreSQL v3, внутри которого лежат байты плагина `pgoutput` или служебные keepalive.

## Решение по шагам

1. Создайте канал для перехвата сигналов ОС (`os.Interrupt`, `syscall.SIGTERM`).
2. Запустите репликацию с помощью `pglogrepl.StartReplication`.
3. В цикле `for` читайте сообщения через `conn.ReceiveMessage(ctx)`.
4. Обрабатывайте тип сообщения `pgproto3.CopyData`.
5. При получении сигнала остановки прервите цикл, отправьте последний LSN и закройте соединение с СУБД.

## Код решения

**`wal_loop.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgproto3"
)

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"
	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка соединения: %v", err)
	}
	defer conn.Close(context.Background())

	slotName := "orders_cdc_slot"
	err = pglogrepl.StartReplication(
		ctx,
		conn,
		slotName,
		pglogrepl.LSN(0),
		pglogrepl.StartReplicationOptions{
			PluginArgs: []string{"proto_version '1'", "publication_names 'orders_pub'"},
		},
	)
	if err != nil {
		log.Fatalf("Ошибка запуска репликации: %v", err)
	}

	fmt.Println("CDC Worker успешно запущен. Нажмите Ctrl+C для Graceful Shutdown.")

	var currentLSN pglogrepl.LSN
	msgCount := 0

	for {
		select {
		case <-ctx.Done():
			fmt.Println("\nПолучен сигнал завершения работы...")
			// Отправляем финальный статус перед отключением
			_ = pglogrepl.SendStandbyStatusUpdate(context.Background(), conn, pglogrepl.StandbyStatusUpdate{
				WALWritePosition: currentLSN,
				WALFlushPosition: currentLSN,
				WALApplyPosition: currentLSN,
				ClientTime:       time.Now(),
			})
			fmt.Printf("Финальный LSN %s зафиксирован. Завершение работы.\n", currentLSN)
			return
		default:
		}

		receiveCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
		rawMsg, err := conn.ReceiveMessage(receiveCtx)
		cancel()

		if err != nil {
			if pgconn.Timeout(err) {
				continue
			}
			if ctx.Err() != nil {
				return
			}
			log.Printf("Ошибка получения сообщения: %v", err)
			time.Sleep(500 * time.Millisecond)
			continue
		}

		if copyData, ok := rawMsg.(*pgproto3.CopyData); ok {
			switch copyData.Data[0] {
			case pglogrepl.PrimaryKeepaliveMessageByteID:
				pkm, err := pglogrepl.ParsePrimaryKeepaliveMessage(copyData.Data[1:])
				if err == nil {
					currentLSN = pkm.ServerWALEnd
					if pkm.ReplyRequested {
						_ = pglogrepl.SendStandbyStatusUpdate(ctx, conn, pglogrepl.StandbyStatusUpdate{
							WALWritePosition: currentLSN,
							WALFlushPosition: currentLSN,
							WALApplyPosition: currentLSN,
							ClientTime:       time.Now(),
						})
					}
				}
			case pglogrepl.XLogDataByteID:
				xld, err := pglogrepl.ParseXLogData(copyData.Data[1:])
				if err == nil {
					currentLSN = xld.WALStart + pglogrepl.LSN(len(xld.WALData))
					msgCount++
					fmt.Printf("[WAL] Пакет #%d: LSN Start=%s, DataLen=%d байт\n",
						msgCount, xld.WALStart, len(xld.WALData))
				}
			}
		}
	}
}
```

## Под капотом

Сетевой обмен при потоковой репликации в протоколе PostgreSQL v3 ведется через подпротокол Copy-both mode.
Сервер переходит в состояние `CopyOut`, в котором все изменения WAL оборачиваются в сообщения `CopyData` (байт `'d'`).
Первый байт внутри полезной нагрузки `CopyData` идентифицирует тип сообщения:
- `'k'` (`PrimaryKeepaliveMessageByteID` = 107): служебный keepalive.
- `'w'` (`XLogDataByteID` = 119): полезная нагрузка WAL записи, закодированная выбранным плагином (`pgoutput`).

## Подводные камни

1. Жесткое завершение процесса по `os.Exit(1)`: не дает отправить `StandbyStatusUpdate`, из-за чего сервер при следующем старте начнет стриминг с более раннего LSN, вызывая повторную обработку уже прочитанных событий.
2. Блокирующий вызов без таймаута: если сервер зависнет или связь оборвется без FIN пакета, процесс зависнет навечно. Всегда используйте `context.WithTimeout`.
3. Отсутствие буферизации или разделения потоков: обработка сложной бизнес-логики прямо в цикле чтения может замедлить вычитывание сокета, вызвав переполнение сетевого буфера TCP.

## На собеседовании

В: Что происходит на стороне PostgreSQL, когда CDC-клиент разрывает TCP-соединение без закрытия слота?
О: Слот логической репликации остается активным в состоянии `active = false` (поле в `pg_replication_slots`).
PostgreSQL продолжает накапливать все изменения в WAL файлах на диске, ожидая повторного подключения клиента.
Как только клиент снова подключается и вызывает `StartReplication`, стриминг возобновляется ровно с сохраненного `restart_lsn`. Если клиент не подключится длительное время, размер директории `pg_wal` превысит доступный объем диска.
