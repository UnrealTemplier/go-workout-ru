# Персистентное отслеживание LSN (LSN Tracking) и Resume

## Условие

**LSN tracking**: Сохраняйте последний обработанный LSN в БД или Redis. При рестарте resume с этого LSN.

## Теория

Позиция LSN — это указатель прогресса в потоке изменений (аналог Kafka Offset).

При перезапуске CDC сервиса:
1. Если стартовать с `LSN(0)`, PostgreSQL начнет стриминг с позиции `restart_lsn` слота на сервере.
2. Однако слот репликации обновляется не на каждое событие, а периодически. Если сервис подтвердил пакет в Kafka, но упал до отправки статуса в PostgreSQL, после рестарта возможен повтор событий.
3. Промышленный подход: сохранять последний успешно зафиксированный LSN в надежном внешнем хранилище (Redis, PostgreSQL или метаданные Kafka топика) и при старте передавать его в `pglogrepl.StartReplication`.

## Решение по шагам

1. Создайте интерфейс `LSNStore` с методами `SaveLSN(slot string, lsn pglogrepl.LSN)` и `GetLSN(slot string)`.
2. Реализуйте хранилище с эмуляцией персистентности (или записью в Redis/БД).
3. При старте воркера прочитайте сохраненный LSN.
4. Вызовите `pglogrepl.StartReplication` с прочитанным `startLSN`.
5. Обновляйте позицию в хранилище после каждой успешно обработанной транзакции (`CommitMessage`).

## Код решения

**`lsn_tracker.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"

	"github.com/jackc/pglogrepl"
)

// LSNStore описывает контракт персистентного хранения позиции репликации
type LSNStore interface {
	SaveLSN(ctx context.Context, slot string, lsn pglogrepl.LSN) error
	GetLSN(ctx context.Context, slot string) (pglogrepl.LSN, error)
}

// MemoryLSNStore — реализация потокобезопасного хранилища (в проде заменяется на Redis / PostgreSQL)
type MemoryLSNStore struct {
	mu    sync.RWMutex
	store map[string]pglogrepl.LSN
}

func NewMemoryLSNStore() *MemoryLSNStore {
	return &MemoryLSNStore{store: make(map[string]pglogrepl.LSN)}
}

func (s *MemoryLSNStore) SaveLSN(ctx context.Context, slot string, lsn pglogrepl.LSN) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.store[slot] = lsn
	return nil
}

func (s *MemoryLSNStore) GetLSN(ctx context.Context, slot string) (pglogrepl.LSN, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return s.store[slot], nil
}

func main() {
	ctx := context.Background()
	store := NewMemoryLSNStore()
	slotName := "orders_cdc_slot"

	// 1. Имитация предыдущей сессии: сохранение LSN 0/16B3800
	previousLSN, _ := pglogrepl.ParseLSN("0/16B3800")
	_ = store.SaveLSN(ctx, slotName, previousLSN)
	fmt.Printf("Сессия #1 завершена. Сохраненный чекпоинт: %s\n\n", previousLSN)

	// 2. Старт Сессии #2: чтение последнего LSN для Resume
	resumeLSN, err := store.GetLSN(ctx, slotName)
	if err != nil {
		fmt.Printf("Чекпоинт не найден, старт с LSN 0\n")
		resumeLSN = pglogrepl.LSN(0)
	}

	fmt.Printf("Сессия #2 запускается. Возобновление чтения со смещения: %s (uint64: %d)\n",
		resumeLSN, uint64(resumeLSN))

	// В реальном коде: pglogrepl.StartReplication(ctx, conn, slotName, resumeLSN, options)
	fmt.Println("StartReplication вызван с точной сохраненной позиции. Дубликаты исключены!")
}
```

## Под капотом

Когда клиент передает `startLSN > 0` в команду `START_REPLICATION`, PostgreSQL находит ближайший рубеж транзакции перед этим LSN.
Если переданный LSN находится внутри транзакции, PostgreSQL начнет чтение с `Begin` этой транзакции, чтобы клиент получил полный контекст строк.
Поэтому downstream системы обязаны реализовывать идемпотентность (Idempotent Consumer) по первичному ключу и версии строки.

## Подводные камни

1. Сохранение LSN для каждого `InsertMessage`: LSN транзакции фиксируется только на `CommitMessage`. Сохранение промежуточных LSN приведет к сбоям при перезапуске посреди транзакции.
2. Попытка стартовать с LSN, который уже очищен чеклистом (`WAL segment has already been removed`): если слот был удален или пересоздан, восстановиться по старому LSN невозможно — потребуется полный перезапуск с Initial Snapshot.

## На собеседовании

В: Почему даже при надежном персистентном сохранении LSN невозможно гарантировать семантику Exactly-Once без идемпотентности на стороне приемника?
О: При сбое между фиксацией данных в целевом хранилище (например, запись в Kafka) и коммитом LSN в хранилище чекпоинтов, воркер после перезапуска перечитает часть WAL повторно (семантика At-Least-Once).
Для достижения сквозного Exactly-Once приемник данных обязан быть идемпотентным (дедупликация по XID + Primary Key или Upsert по естественному ключу).
