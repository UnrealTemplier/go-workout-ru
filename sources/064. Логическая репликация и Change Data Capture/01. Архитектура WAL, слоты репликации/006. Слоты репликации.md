# Слоты репликации: pg_create_logical_replication_slot и мониторинг лага

## Условие

**Replication slots**: Создайте replication slot через `pg_create_logical_replication_slot('slot_name', 'pgoutput')`. Поймите, что slot предотвращает удаление WAL до прочтения.

## Теория

Слот логической репликации (Logical Replication Slot) — это центральный управляющий примитив PostgreSQL CDC.

Главная функция слота — **гарантия доставки (at-least-once)**:
- Слот сохраняет в памяти и на диске позицию `restart_lsn` (минимальный LSN, необходимый клиенту при перезапуске) и `confirmed_flush_lsn` (последний подтвержденный клиентом LSN).
- Движок контрольных точек (`checkpoint`) и фоновый процесс очистки WAL сегментов гарантируют, что ни один WAL файл, содержащий данные после `restart_lsn`, **не будет удален или перезаписан**.

Если CDC-приложение остановлено на 2 часа, PostgreSQL бережно сохранит все 2 часа изменений в файлах WAL на диске.

## Решение по шагам

1. Создайте слот логической репликации через SQL функцию `pg_create_logical_replication_slot('demo_slot', 'pgoutput')`.
2. Запросите состояние слота из `pg_replication_slots`.
3. Рассчитайте отставание слота (replication lag) в байтах с помощью встроенной функции `pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)`.
4. Удалите слот после демонстрации через `pg_drop_replication_slot('demo_slot')`.

## Код решения

**`monitor_slot.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type SlotInfo struct {
	SlotName          string
	Plugin            string
	Active            bool
	RestartLSN        sql.NullString
	ConfirmedFlushLSN sql.NullString
	LagBytes          int64
}

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer db.Close()

	ctx := context.Background()

	// 1. Создаем слот через чистый SQL (если не существует)
	createSlotSQL := `
		DO $$
		BEGIN
			IF NOT EXISTS (SELECT 1 FROM pg_replication_slots WHERE slot_name = 'analytics_slot') THEN
				PERFORM pg_create_logical_replication_slot('analytics_slot', 'pgoutput');
			END IF;
		END $$;
	`
	if _, err := db.ExecContext(ctx, createSlotSQL); err != nil {
		log.Fatalf("Ошибка создания слота: %v", err)
	}
	fmt.Println("Слот 'analytics_slot' успешно проверен/создан.")

	// 2. Мониторинг параметров и лага слота
	query := `
		SELECT 
			slot_name, 
			plugin, 
			active, 
			restart_lsn::text, 
			confirmed_flush_lsn::text,
			COALESCE(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn), 0) AS lag_bytes
		FROM pg_replication_slots
		WHERE slot_name = 'analytics_slot';
	`

	var info SlotInfo
	err = db.QueryRowContext(ctx, query).Scan(
		&info.SlotName,
		&info.Plugin,
		&info.Active,
		&info.RestartLSN,
		&info.ConfirmedFlushLSN,
		&info.LagBytes,
	)
	if err != nil {
		log.Fatalf("Ошибка выборки состояния слота: %v", err)
	}

	fmt.Printf("Состояние слота репликации:\n")
	fmt.Printf("• Имя слота: %s\n", info.SlotName)
	fmt.Printf("• Плагин: %s\n", info.Plugin)
	fmt.Printf("• Активен (подключен клиент): %t\n", info.Active)
	fmt.Printf("• Restart LSN: %s\n", info.RestartLSN.String)
	fmt.Printf("• Confirmed Flush LSN: %s\n", info.ConfirmedFlushLSN.String)
	fmt.Printf("• Отставание от текущего конца WAL: %d байт (%.2f КБ)\n",
		info.LagBytes, float64(info.LagBytes)/1024)
}
```

## Под капотом

Слоты репликации сохраняются в файлах на диске в директории `pg_replslot/<slot_name>/state`.
При выполнении каждого Checkpoint PostgreSQL сбрасывает состояние слота на диск.
Функция `pg_wal_lsn_diff(lsn1, lsn2)` производит 64-битное вычитание двух позиций в журнале WAL.
Разница показывает точный объем байт изменений, которые уже зафиксированы на мастере, но еще не подтверждены подписчиком слота.

## Подводные камни

1. Забытый тестовый слот в продакшене: «мертвый» неактивный слот будет удерживать все генерируемые WAL файлы, пока диск сервера не заполнится на 100%, что приведет к аварийной остановке СУБД (PANIC / Read-only mode).
2. Отсутствие алерта на `pg_wal_lsn_diff`: в системах мониторинга (Prometheus) критически необходимо настраивать алертинг на отставание слота (например, лаг > 1 ГБ или > 30 минут).
3. Использование параметра `max_slot_wal_keep_size`: если его настроить, PostgreSQL удалит WAL при превышении лимита, но слот перейдет в статус `invalidated` (сломан навсегда, репликацию придется пересоздавать с нуля).

## На собеседовании

В: Что такое параметр max_slot_wal_keep_size в PostgreSQL, и к каким компромиссам приводит его настройка?
О: Параметр `max_slot_wal_keep_size` задает максимальный объем WAL (например, 20 ГБ), который разрешено удерживать неактивным слотам репликации.
- **Без лимита (-1):** При падении CDC воркера СУБД хранит WAL бесконечно. Приоритет — целостность репликации ценой риска падения основной БД при переполнении диска.
- **С лимитом (20GB):** При накоплении 20 ГБ невычитанного WAL сервер принудительно инвалидирует слот (`wal_status = lost`) и удаляет старые сегменты. Приоритет — доступность основной БД ценой поломки CDC пайплайна.
