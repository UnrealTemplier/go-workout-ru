# Декодирование сообщений pgoutput: Begin, Relation, Insert, Update, Delete, Commit

## Условие

**Декодирование pgoutput.**: Распарсите поток WAL: `BeginMessage` (транзакция началась), `RelationMessage` (схема таблицы), `InsertMessage` (новая строка), `UpdateMessage` (старая + новая), `DeleteMessage`, `CommitMessage`. Выведите человекочитаемый лог изменений.

## Теория

Плагин `pgoutput` преобразует физический WAL в структурированный поток логических сообщений протокола репликации:
1. `BeginMessage ('B')`: маркер начала транзакции. Содержит `FinalLSN`, `CommitTime` и `XID` (идентификатор транзакции).
2. `RelationMessage ('R')`: описание схемы таблицы. Содержит `RelationID`, имя схемы, имя таблицы и массив колонок с типами (OID). Присылается перед первым изменением строки в таблице.
3. `InsertMessage ('I')`: вставка новой строки. Содержит `RelationID` и кортеж значений `NewTuple`.
4. `UpdateMessage ('U')`: обновление строки. Содержит `NewTuple`, а также `OldTuple` (если включен `REPLICA IDENTITY FULL`).
5. `DeleteMessage ('D')`: удаление строки. Содержит `OldTuple` или кортеж первичного ключа `KeyTuple`.
6. `CommitMessage ('C')`: успешная фиксация транзакции. Содержит `CommitLSN` и время коммита. Только после Commit данные становятся консистентными!

## Решение по шагам

1. Подключитесь к слоту репликации через `pglogrepl`.
2. При получении `XLogData` передайте полезную нагрузку в функцию `pglogrepl.Parse(data)`.
3. Организуйте `type switch` по возвращенным структурам `pglogrepl.Message`.
4. Обрабатывайте события жизненного цикла транзакции: `BeginMessage`, `RelationMessage`, `InsertMessage`, `CommitMessage`.
5. Логируйте человекочитаемые события в консоль.

## Код решения

**`decode_pgoutput.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgproto3"
)

func main() {
	ctx := context.Background()
	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"

	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer conn.Close(ctx)

	slotName := "orders_cdc_slot"
	err = pglogrepl.StartReplication(ctx, conn, slotName, pglogrepl.LSN(0), pglogrepl.StartReplicationOptions{
		PluginArgs: []string{"proto_version '1'", "publication_names 'orders_pub'"},
	})
	if err != nil {
		log.Fatalf("Ошибка старта: %v", err)
	}

	fmt.Println("Слушаем поток изменений pgoutput...")

	relations := make(map[uint32]*pglogrepl.RelationMessage)

	for {
		rawMsg, err := conn.ReceiveMessage(ctx)
		if err != nil {
			log.Fatalf("Ошибка сокета: %v", err)
		}

		copyData, ok := rawMsg.(*pgproto3.CopyData)
		if !ok || copyData.Data[0] != pglogrepl.XLogDataByteID {
			continue
		}

		xld, err := pglogrepl.ParseXLogData(copyData.Data[1:])
		if err != nil {
			continue
		}

		// Декодируем логическое сообщение плагина pgoutput
		logicalMsg, err := pglogrepl.Parse(xld.WALData)
		if err != nil {
			log.Printf("Ошибка парсинга pgoutput: %v", err)
			continue
		}

		switch m := logicalMsg.(type) {
		case *pglogrepl.BeginMessage:
			fmt.Printf("\n▶ [BEGIN] XID: %d, CommitTime: %s, FinalLSN: %s\n",
				m.Xid, m.CommitTime.Format(time.RFC3339), m.FinalLSN)

		case *pglogrepl.RelationMessage:
			relations[m.RelationID] = m
			fmt.Printf("📋 [RELATION] ID=%d: %s.%s (колонок: %d)\n",
				m.RelationID, m.Namespace, m.RelationName, len(m.Columns))

		case *pglogrepl.InsertMessage:
			rel := relations[m.RelationID]
			fmt.Printf("➕ [INSERT] Таблица: %s, Значений в кортеже: %d\n",
				rel.RelationName, len(m.Tuple.Columns))

		case *pglogrepl.UpdateMessage:
			rel := relations[m.RelationID]
			fmt.Printf("✏️ [UPDATE] Таблица: %s (NewTuple: %d колонок)\n",
				rel.RelationName, len(m.NewTuple.Columns))

		case *pglogrepl.DeleteMessage:
			rel := relations[m.RelationID]
			fmt.Printf("❌ [DELETE] Таблица: %s\n", rel.RelationName)

		case *pglogrepl.CommitMessage:
			fmt.Printf("✔ [COMMIT] CommitLSN: %s, TransactionEndLSN: %s\n",
				m.CommitLSN, m.TransactionEndLSN)
		}
	}
}
```

## Под капотом

Сообщения логического декодирования `pgoutput` упорядочены строго хронологически по моменту фиксации транзакций (`commit order`).
Даже если транзакция выполнялась 10 минут и выполнила миллион операций, `pgoutput` не отправит ни одного байта клиенту до тех пор, пока транзакция не сделает успешный `COMMIT` (если не включен стриминг незавершенных транзакций `streaming = on`).
Если транзакция выполнит `ROLLBACK`, она вообще не появится в логическом потоке репликации!

## Подводные камни

1. Обработка изменений без кэширования `RelationMessage`: `RelationMessage` приходит один раз при первом изменении таблицы. Если приложение перезапустится или пропустит маппинг, оно не сможет связать `RelationID` из `InsertMessage` с именами колонок.
2. Игнорирование порядка транзакций: логическая репликация гарантирует порядок коммитов, но не порядок выполнения отдельных `INSERT` в конкурентных сессиях.
3. Большие транзакции: транзакция с 10 млн строк приведет к гигантскому потоку данных между `Begin` и `Commit`, забивая память консьюмера.

## На собеседовании

В: Почему в поток логической репликации попадают только успешно зафиксированные (committed) транзакции, и как это влияет на откат изменений?
О: Физический WAL содержит все операции, включая откаченные (aborted/rolled back).
Однако плагин логического декодирования (`pgoutput`) читает WAL на сервере и удерживает изменения транзакции в буфере (ReorderBuffer).
Если транзакция фиксируется (`COMMIT`), ReorderBuffer выплескивает логические события клиенту между тегами `Begin` и `Commit`.
Если происходит `ROLLBACK`, ReorderBuffer просто уничтожает накопленные операции.
Благодаря этому CDC-клиенты никогда не получают «грязных» данных (dirty reads) и избавлены от необходимости обрабатывать откаты транзакций.
