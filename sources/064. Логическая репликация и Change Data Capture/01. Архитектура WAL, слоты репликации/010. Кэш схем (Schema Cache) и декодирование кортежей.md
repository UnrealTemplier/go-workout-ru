# Кэш схем (Schema Cache) и декодирование кортежей TupleData

## Условие

Обрабатывай сообщения типа `*pglogrepl.RelationMessage` (сохраняй структуру таблиц в памяти) и `*pglogrepl.InsertMessage` (декодируй кортеж данных в Go-структуру).

## Теория

В отличие от JSON-ориентированных плагинов (вроде `wal2json`), стандартный плагин `pgoutput` оптимизирован для экстремальной производительности и не включает имена колонок в каждую строку изменений.

Архитектура декодирования `pgoutput`:
1. При изменении таблицы сервер шлет `RelationMessage`: в нем передается соответствие `RelationID -> [ColumnName, TypeOID]`.
2. При вставке/обновлении строки сервер шлет `InsertMessage`: в нем содержатся только `RelationID` и массив анонимных байтовых срезов `TupleData.Columns`.
3. Консьюмер ОБЯЗАН вести локальный кэш схем (`map[uint32]*RelationMessage`).
4. При декодировании кортежа консьюмер сопоставляет \(i\)-й элемент массива данных с \(i\)-й колонкой из кэша схемы.

## Решение по шагам

1. Создайте структуру `SchemaCache` на базе `map[uint32]*pglogrepl.RelationMessage`.
2. При получении `RelationMessage` сохраняйте метаданные таблицы в кэш.
3. При получении `InsertMessage` найдите схему по `RelationID`.
4. Для каждого значения в `m.Tuple.Columns` проверьте тип данных: текстовый (`'t'`), NULL (`'n'`) или TOAST (`'u'`).
5. Преобразуйте массив колонок в структуру `map[string]any` и распечатайте результат.

## Код решения

**`schema_cache.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgproto3"
)

type SchemaCache struct {
	relations map[uint32]*pglogrepl.RelationMessage
}

func NewSchemaCache() *SchemaCache {
	return &SchemaCache{relations: make(map[uint32]*pglogrepl.RelationMessage)}
}

func (s *SchemaCache) Put(rel *pglogrepl.RelationMessage) {
	s.relations[rel.RelationID] = rel
}

func (s *SchemaCache) DecodeTuple(relID uint32, tuple *pglogrepl.TupleData) (string, map[string]any, error) {
	rel, ok := s.relations[relID]
	if !ok {
		return "", nil, fmt.Errorf("неизвестный relation_id: %d (схема не найдена в кэше)", relID)
	}

	result := make(map[string]any)
	for i, col := range tuple.Columns {
		colName := rel.Columns[i].Name
		switch col.DataType {
		case 'n': // NULL значение
			result[colName] = nil
		case 'u': // Неизмененное TOAST значение
			result[colName] = "[TOAST Unchanged]"
		case 't': // Текстовое представление
			result[colName] = string(col.Data)
		case 'b': // Бинарное представление
			result[colName] = col.Data
		}
	}
	tableName := fmt.Sprintf("%s.%s", rel.Namespace, rel.RelationName)
	return tableName, result, nil
}

func main() {
	ctx := context.Background()
	connStr := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"

	conn, err := pgconn.Connect(ctx, connStr)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer conn.Close(ctx)

	slotName := "orders_cdc_slot"
	_ = pglogrepl.StartReplication(ctx, conn, slotName, pglogrepl.LSN(0), pglogrepl.StartReplicationOptions{
		PluginArgs: []string{"proto_version '1'", "publication_names 'orders_pub'"},
	})

	cache := NewSchemaCache()
	fmt.Println("Кэш схем инициализирован. Ожидание транзакций...")

	for {
		rawMsg, err := conn.ReceiveMessage(ctx)
		if err != nil {
			log.Fatalf("Ошибка сокета: %v", err)
		}

		copyData, ok := rawMsg.(*pgproto3.CopyData)
		if !ok || copyData.Data[0] != pglogrepl.XLogDataByteID {
			continue
		}

		xld, err := pglogrepl.ParseXLogData(copyData.Data[1:])
		if err != nil {
			continue
		}

		logicalMsg, err := pglogrepl.Parse(xld.WALData)
		if err != nil {
			continue
		}

		switch m := logicalMsg.(type) {
		case *pglogrepl.RelationMessage:
			cache.Put(m)
			fmt.Printf("Обновлена схема таблицы: %s.%s (колонок: %d)\n",
				m.Namespace, m.RelationName, len(m.Columns))

		case *pglogrepl.InsertMessage:
			tableName, rowData, err := cache.DecodeTuple(m.RelationID, m.Tuple)
			if err != nil {
				log.Printf("Ошибка декодирования строки: %v", err)
				continue
			}
			fmt.Printf("Успешно декодирована строка в '%s':\n", tableName)
			for col, val := range rowData {
				fmt.Printf("   %-12s = %v\n", col, val)
			}
		}
	}
}
```

## Под капотом

Разделение метаданных схемы и данных кортежей — ключевое архитектурное преимущество `pgoutput`.
В таблице с 50 колонками передача имен колонок в каждой строке приводила бы к тому, что 80% сетевого трафика занимали бы имена ключей JSON.
`pgoutput` передает схему таблицы только один раз в `RelationMessage`, а затем в `InsertMessage` и `UpdateMessage` шлет только компактный массив байтов `TupleData`.
Это уменьшает объем сетевого трафика репликации в 5–10 раз по сравнению с JSON-декодерами.

## Подводные камни

1. Непонимание маркера `'u'` (TOAST Unchanged): если колонка большого размера (> 2 КБ) не изменялась в ходе `UPDATE`, PostgreSQL шлет байт `'u'`, а тело поля оставляет пустым. Попытка прочитать его как пустое значение приведет к порче данных downstream.
2. Проблема DDL-миграций: если в таблицу добавили колонку (`ALTER TABLE ADD COLUMN`), PostgreSQL пришлет новый `RelationMessage` с обновленной структурой. Кэш обязан атомарно перезаписать старую схему.
3. Кодировка строк: данные в `col.Data` закодированы в кодировке базы данных (обычно UTF-8). Необходимо учитывать локаль сервера.

## На собеседовании

В: Почему в pgoutput типы данных колонок передаются в виде числовых OID (например, 23 для int4, 25 для text), и как их эффективно типизировать в Go?
О: OID (Object Identifier) — это внутренний 32-битный целочисленный идентификатор типа данных в системном каталоге `pg_type`.
Передача OID вместо строк экономит память и процессорное время.
В Go для маппинга OID в нативные типы используется регистр типов библиотеки `pgtype.Map` (из пакета `github.com/jackc/pgx/v5/pgtype`).
Зная OID, `pgtype.Map` мгновенно выбирает зарегистрированный кодек и преобразует байты в `int32`, `time.Time`, `uuid.UUID` или `numeric` без тяжелой рефлексии.
