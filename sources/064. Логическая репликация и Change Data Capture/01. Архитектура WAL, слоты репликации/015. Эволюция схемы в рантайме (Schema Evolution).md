# Эволюция схемы в рантайме (Schema Evolution) и инвалидация кэша

## Условие

**[Каверзный кейс — Schema Changes]**: Что будет, если во время репликации в Postgres добавят новую колонку? Реализуй обновление локального кэша схем при получении нового `RelationMessage`.

## Теория

В динамично развивающихся приложениях структура таблиц постоянно изменяется: выполняются миграции `ALTER TABLE ADD COLUMN`, `ALTER TABLE DROP COLUMN` или переименование типов.

Как `pgoutput` ведет себя при изменениях схемы:
1. При выполнении DDL-миграции ядро PostgreSQL инкрементирует внутренний счетчик версии схемы таблицы.
2. Перед отправкой следующей DML операции (`Insert`/`Update`) с обновленной структурой сервер автоматически отправляет **новый `RelationMessage`** с тем же `RelationID`, но с обновленным списком колонок.
3. Консьюмер не должен падать или использовать устаревшие индексы колонок — он обязан атомарно обновить схему в памяти.

## Решение по шагам

1. Реализуйте потокобезопасный `DynamicSchemaCache` с мьютексом `sync.RWMutex`.
2. Реализуйте метод `UpdateSchema(rel *pglogrepl.RelationMessage)`, отслеживающий появление новых или удаление старых полей.
3. Продемонстрируйте сценарий: таблица `users` изначально имеет 2 колонки (`id`, `name`), а затем миграция добавляет колонку `phone`.
4. Покажите, как декодер адаптируется к новой структуре без перезапуска сервиса.

## Код решения

**`dynamic_schema.go`**

```go
package main

import (
	"fmt"
	"sync"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgtype"
)

type DynamicSchemaCache struct {
	mu     sync.RWMutex
	tables map[uint32]*pglogrepl.RelationMessage
}

func NewDynamicSchemaCache() *DynamicSchemaCache {
	return &DynamicSchemaCache{tables: make(map[uint32]*pglogrepl.RelationMessage)}
}

func (c *DynamicSchemaCache) UpdateSchema(rel *pglogrepl.RelationMessage) {
	c.mu.Lock()
	defer c.mu.Unlock()

	old, exists := c.tables[rel.RelationID]
	if !exists {
		fmt.Printf("🆕 Зарегистрирована новая схема: %s.%s (колонок: %d)\n",
			rel.Namespace, rel.RelationName, len(rel.Columns))
	} else if len(old.Columns) != len(rel.Columns) {
		fmt.Printf("⚡ [SCHEMA EVOLUTION] Изменение структуры %s.%s: было колонок %d -> стало %d!\n",
			rel.Namespace, rel.RelationName, len(old.Columns), len(rel.Columns))
	}

	c.tables[rel.RelationID] = rel
}

func (c *DynamicSchemaCache) Decode(relID uint32, tuple *pglogrepl.TupleData) map[string]string {
	c.mu.RLock()
	defer c.mu.RUnlock()

	rel := c.tables[relID]
	res := make(map[string]string)
	for i, col := range tuple.Columns {
		colName := rel.Columns[i].Name
		if col.DataType == 't' {
			res[colName] = string(col.Data)
		}
	}
	return res
}

func main() {
	cache := NewDynamicSchemaCache()
	relID := uint32(24501)

	// 1. Исходная схема: id, name
	v1 := &pglogrepl.RelationMessage{
		RelationID:   relID,
		Namespace:    "public",
		RelationName: "users",
		Columns: []*pglogrepl.RelationMessageColumn{
			{Name: "id", DataType: pgtype.Int4OID},
			{Name: "name", DataType: pgtype.TextOID},
		},
	}
	cache.UpdateSchema(v1)

	row1 := &pglogrepl.TupleData{
		Columns: []*pglogrepl.TupleDataColumn{
			{DataType: 't', Data: []byte("1")},
			{DataType: 't', Data: []byte("Иван")},
		},
	}
	fmt.Printf("Декодирована строка v1: %v\n\n", cache.Decode(relID, row1))

	// 2. Миграция схемы в PostgreSQL: добавлен столбец phone
	v2 := &pglogrepl.RelationMessage{
		RelationID:   relID,
		Namespace:    "public",
		RelationName: "users",
		Columns: []*pglogrepl.RelationMessageColumn{
			{Name: "id", DataType: pgtype.Int4OID},
			{Name: "name", DataType: pgtype.TextOID},
			{Name: "phone", DataType: pgtype.TextOID},
		},
	}
	cache.UpdateSchema(v2)

	row2 := &pglogrepl.TupleData{
		Columns: []*pglogrepl.TupleDataColumn{
			{DataType: 't', Data: []byte("2")},
			{DataType: 't', Data: []byte("Мария")},
			{DataType: 't', Data: []byte("+79991234567")},
		},
	}
	fmt.Printf("Декодирована строка v2: %v\n", cache.Decode(relID, row2))
}
```

ℹ️ Динамическая адаптация к эволюции схемы БД на лету без перезапуска

## Под капотом

В ядре PostgreSQL таблица идентифицируется 32-битным идентификатором `relfilenode` и `oid`.
При выполнении некоторых DDL операций (`ALTER TABLE ADD COLUMN` с дефолтными константами в PG 11+) физическая перестройка таблицы не требуется, но схема получает новый хэш.
`pgoutput` гарантирует сериализуемость: новый `RelationMessage` всегда предшествует в потоке первой операции DML, затронувшей обновленную структуру.

## Подводные камни

1. Кэширование схемы по имени таблицы вместо `RelationID`: при удалении и повторном создании таблицы с тем же именем `RelationID` изменится, и консьюмер начнет декодировать поля некорректно.
2. Downstream неготовность: если схема в CDC обновилась, но таблица в ClickHouse или Elasticsearch еще не имеет новой колонки, запись батча завершится ошибкой. Необходим механизм Schema Registry или отложенной очереди (DLQ).

## На собеседовании

В: Как организовать безопасное применение DDL миграций в production при наличии активных CDC-пайплайнов?
О: Применяется паттерн **Expand / Contract (Расширение / Сужение)**:
1) **Expand:** Новые колонки добавляются строго как `NULLABLE` (или с константным DEFAULT). CDC-консьюмер мгновенно подхватывает новое поле, downstream-системы начинают его сохранять.
2) **Миграция кода:** Приложения начинают писать в новую колонку.
3) **Contract:** Удаление старых колонок происходит только после того, как все downstream-сервисы перестали полагаться на удаляемое поле. Удаление выполняется через `DROP COLUMN`.
