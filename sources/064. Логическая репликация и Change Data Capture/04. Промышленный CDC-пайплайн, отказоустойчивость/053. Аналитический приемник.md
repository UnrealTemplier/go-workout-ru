# Аналитический приемник: Пакетное вычитывание из NATS/Kafka в ClickHouse

## Условие

**Аналитический приемник**: Второй Go-воркер читает батчами из NATS и пушит через Native Protocol прямо в ClickHouse.

## Теория

Аналитический воркер-консьюмер (OLAP Ingestion Worker) — это второй компонент архитектуры реального времени:
1. Вычитывает сообщения пачками (батчами) из промежуточного брокера (NATS JetStream или Kafka).
2. Накапливает пакет: условие сброса — 10 000 строк или 1 секунда по таймеру (Flush Interval).
3. Использует нативный бинарный интерфейс драйвера ClickHouse (`batch.Column(i).Append`).
4. Подтверждает смещения (Commit Offset / JetStream Ack) строго **после** успешной записи пакета в ClickHouse.

## Решение по шагам

1. Создайте структуру пакетного процессора с настраиваемым размером батча.
2. Реализуйте функцию сброса (Flush) с замером времени.
3. Покажите обработку таймера ожидания сброса.
4. Продемонстрируйте подтверждение смещений только после фиксации партов.

## Код решения

**`olap_ingestion_worker.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type ClickHouseIngestBatcher struct {
	batchSize int
	items     []int64
}

func (b *ClickHouseIngestBatcher) Ingest(ctx context.Context, itemID int64) bool {
	b.items = append(b.items, itemID)
	if len(b.items) >= b.batchSize {
		b.Flush(ctx)
		return true
	}
	return false
}

func (b *ClickHouseIngestBatcher) Flush(ctx context.Context) {
	if len(b.items) == 0 {
		return
	}
	fmt.Printf("🚀 [CLICKHOUSE NATIVE API] Записан парт из %d строк в ReplacingMergeTree\n", len(b.items))
	// Имитация успешной вставки
	b.items = b.items[:0]
	fmt.Println("✔ Сообщения подтверждены (Ack) в NATS/Kafka.")
}

func main() {
	ctx := context.Background()
	batcher := &ClickHouseIngestBatcher{batchSize: 3}

	fmt.Println("=== Вычитывание потока изменений из шины в ClickHouse ===")
	events := []int64{101, 102, 103, 104}

	for _, id := range events {
		batcher.Ingest(ctx, id)
	}

	// Сброс остатка по таймеру
	batcher.Flush(ctx)
	fmt.Println("Все данные согласованы между шиной сообщений и аналитической базой.")
}
```

## Под капотом

ClickHouse оптимизирован под редкие, но объемные вставки блоков.
Каждый пакет формирует на диске один новый парт (Part).
Фоновый пул потоков `BackgroundMergePool` объединяет парты в более крупные директории в фоновом режиме без блокировки входящих записей.

## Подводные камни

1. Отправка подтверждения (Ack) до вызова `batch.Send()`: при падении воркера в момент сетевой вставки в ClickHouse пачка сообщений будет потеряна.
2. Бесконечное накопление батча при низком трафике: обязателен тикер принудительного сброса по времени.

## На собеседовании

В: Что произойдет, если в ClickHouse настроить слишком частый сброс микро-батчей (например, каждые 10 мс)?
О: Возникнет ошибка **Too many parts in all data in table**.
Каждая вставка создает директорию парта на диске. Фоновый процесс слияния (Merge) не успевает объединять сотни мелких партов в секунду.
Когда количество неслитых партов превышает лимит (по умолчанию 300 партов на партицию), ClickHouse принудительно отклоняет все входящие запросы на вставку с HTTP 500 / TCP ошибкой до завершения слияний.
