# Паттерн Transactional Outbox против прямого Direct Publish

## Условие

**Outbox pattern для reliable events.**: Если нужна гарантия доставки вместе с бизнес-транзакцией — используйте outbox, а не direct publish.

## Теория

Проблема «Двойной записи» (Dual Write Problem) — фундаментальная ошибка распределенных систем:
```go
db.Exec("INSERT INTO orders ...") // Шаг 1: запись в БД
kafka.Produce("order_created")    // Шаг 2: отправка в очередь
```
Если процесс упадет между Шагом 1 и Шагом 2, заказ появится в базе данных, но сообщение в Kafka никогда не уйдет.
Если поменять шаги местами — сообщение уйдет, а транзакция базы данных откатится по ошибке ограничения (Constraint Error).

Сравнение подходов:
- **Direct Publish:** не гарантирует согласованность (нарушение атомарности).
- **2PC / XA:** распределенные двухфазные коммиты медленные и ненадежные.
- **Transactional Outbox + CDC:** запись в таблицу `outbox` в рамках той же транзакции базы данных. CDC гарантирует, что сообщение будет отправлено в Kafka строго после коммита.

## Решение по шагам

1. Смоделируйте сценарий сбоя прямого вызова (Dual Write Failure).
2. Реализуйте транзакционную вставку в таблицу `outbox` в едином блоке `tx.Commit()`.
3. Продемонстрируйте, как CDC считывает зафиксированное Outbox-событие.
4. Докажите математическую невозможность рассинхронизации.

## Код решения

**`dual_write_vs_outbox.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

// Демонстрация Transactional Outbox
func CreateOrderReliable(ctx context.Context, db *sql.DB, customerID int, amount float64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	// 1. Бизнес-сущность
	var orderID int
	err = tx.QueryRowContext(ctx, `
		INSERT INTO orders (customer_id, amount) VALUES ($1, $2) RETURNING id;
	`, customerID, amount).Scan(&orderID)
	if err != nil {
		return err
	}

	// 2. Outbox-событие В ТОЙ ЖЕ САМОЙ ТРАНЗАКЦИИ
	outboxPayload := fmt.Sprintf(`{"order_id": %d, "amount": %.2f, "status": "CREATED"}`, orderID, amount)
	_, err = tx.ExecContext(ctx, `
		INSERT INTO outbox (aggregate_type, aggregate_id, event_type, payload)
		VALUES ('Order', $1, 'OrderCreated', $2::jsonb);
	`, fmt.Sprintf("%d", orderID), outboxPayload)
	if err != nil {
		return err
	}

	// 3. Атомарный коммит обоих изменений
	return tx.Commit()
}

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка БД: %v", err)
	}
	defer db.Close()

	ctx := context.Background()
	if err := CreateOrderReliable(ctx, db, 55, 3490.00); err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	fmt.Println("=== Гарантия надежности Transactional Outbox ===")
	fmt.Println("1. Заказ и событие зафиксированы единым блоком ACID в PostgreSQL.")
	fmt.Println("2. Даже при немедленном выключении питания сервера событие уже находится в WAL.")
	fmt.Println("3. CDC-демон вычитает событие сразу после перезагрузки.")
	fmt.Println("Результат: 100% устранение проблемы Dual Write!")
}
```

## Под капотом

Таблица `outbox` находится в том же пространстве таблиц (Tablespace), что и бизнес-таблицы.
Обе записи попадают в один и тот же буфер транзакции XLOG.
Когда вызывается `tx.Commit()`, ядро PostgreSQL записывает единую запись `XLOG_XACT_COMMIT`.
Это гарантирует, что появление заказа и события Outbox абсолютно неразделимы.

## Подводные камни

1. Очистка таблицы outbox частыми DELETE: порождает раздувание таблицы (table bloat) и лишний мусорный WAL. Очищайте outbox секционированием (`DROP TABLE partition_2026_09_05`).
2. Забытая публикация для таблицы outbox: если публикация настроена только на orders, события из outbox не попадут в репликацию.

## На собеседовании

В: Почему Transactional Outbox в связке с CDC превосходит Transactional Outbox с фоновым Polling воркером?
О: При Polling воркере:
1) База постоянно нагружена тяжелыми `SELECT ... FOR UPDATE SKIP LOCKED`, что разрушает производительность в HighLoad.
2) Минимальная задержка ограничена интервалом опроса (например, 1-2 секунды).
3) Растет фрагментация таблиц и индексов.
При CDC:
Накладные расходы равны нулю (данные читаются из потока WAL), а задержка доставки в Kafka падает до нескольких миллисекунд.
