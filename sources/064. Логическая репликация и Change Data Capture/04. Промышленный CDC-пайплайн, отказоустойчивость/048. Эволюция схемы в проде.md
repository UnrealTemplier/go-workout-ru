# Эволюция схемы в проде: RelationMessage как единственный источник правды

## Условие

**Schema evolution — это боль.**: Готовьтесь к ALTER TABLE в source БД. Relation messages в pgoutput — ваш друг.

## Теория

При выполнении DDL-миграций в базе данных разработчики часто сталкиваются с рассинхронизацией:
- В приложении изменился код Go-структуры, но миграция в БД еще не доехала.
- Или наоборот: DBA накатил `ALTER TABLE` в БД, а сервис еще не обновили.

В архитектуре `pgoutput` **единственным источником правды** является сервер PostgreSQL:
1. `RelationMessage` приходит в поток репликации строго синхронно с изменением данных.
2. Консьюмер не должен жестко полагаться на скомпилированные структуры Go, а обязан использовать динамический парсинг на основе полей `RelationMessageColumn`.
3. Это исключает падения сервиса при добавлении, удалении или переименовании колонок.

## Решение по шагам

1. Создайте обобщенную модель `GenericRow` на основе `map[string]any`.
2. Напишите функцию динамического маппинга без использования предопределенных структур.
3. Продемонстрируйте корректную обработку строки с произвольным набором колонок, пришедшим из `RelationMessage`.
4. Покажите, как новые колонки прозрачно попадают в JSON payload.

## Код решения

**`schema_source_of_truth.go`**

```go
package main

import (
	"encoding/json"
	"fmt"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgtype"
)

type GenericRow map[string]any

func DecodeWithRelationMeta(rel *pglogrepl.RelationMessage, tuple *pglogrepl.TupleData) GenericRow {
	row := make(GenericRow, len(rel.Columns))

	for i, col := range tuple.Columns {
		meta := rel.Columns[i]
		if col.DataType == 't' {
			row[meta.Name] = string(col.Data)
		} else if col.DataType == 'n' {
			row[meta.Name] = nil
		}
	}
	return row
}

func main() {
	// Имитация RelationMessage с динамически добавленными колонками
	rel := &pglogrepl.RelationMessage{
		RelationName: "dynamic_orders",
		Columns: []*pglogrepl.RelationMessageColumn{
			{Name: "id", DataType: pgtype.Int8OID},
			{Name: "amount", DataType: pgtype.NumericOID},
			{Name: "promocode", DataType: pgtype.TextOID}, // Поле добавлено DBA в рантайме!
		},
	}

	tuple := &pglogrepl.TupleData{
		Columns: []*pglogrepl.TupleDataColumn{
			{DataType: 't', Data: []byte("5001")},
			{DataType: 't', Data: []byte("7490.00")},
			{DataType: 't', Data: []byte("AUTUMN2026")},
		},
	}

	row := DecodeWithRelationMeta(rel, tuple)
	data, _ := json.MarshalIndent(row, "", "  ")

	fmt.Printf("Динамически декодированная строка по метаданным RelationMessage:\n%s\n", string(data))
	fmt.Println("Ни одна колонка не потеряна, жесткие DTO не потребовались!")
}
```

ℹ️ Динамическое декодирование кортежей по метаданным RelationMessage как единственного источника правды

**`Терминал`**

```bash

# Вывод:
# Динамически декодированная строка по метаданным RelationMessage:
# {

```

## Под капотом

Использование схемы из `RelationMessage` вместо скомпилированных Go-структур изолирует CDC-коннектор от бизнес-логики.
Коннектор превращается в универсальный инфраструктурный компонент (Generic Ingestion Engine), способный реплицировать любые таблицы базы данных без перекомпиляции бинарника.

## Подводные камни

1. Попытка десериализовать динамические поля в жесткую структуру `struct`: новые поля будут тихо проигнорированы `json.Unmarshal`.
2. Изменение регистра имен: PostgreSQL приводит имена к нижнему регистру, если они не были взяты в кавычки.

## На собеседовании

В: Как реализовать универсальный CDC-коннектор для 500 таблиц без написания 500 отдельных Go структур?
О: Применяется подход **Schema-Free Ingestion / Generic Payload**:
1) Воркер не содержит структур моделей таблиц.
2) Вся информация о полях извлекается динамически из `RelationMessage`.
3) Данные сериализуются в обобщенный формат JSON или Apache Avro с динамической регистрацией схемы в Confluent Schema Registry.
4) Downstream-системы (например, ClickHouse) применяют функцию `JSONExtract` или нативный тип `JSON` для извлечения полей.
