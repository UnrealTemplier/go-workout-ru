# Тестирование аварийных сценариев: Сбой консьюмера, отказ Kafka и DDL

## Условие

**Тестируйте failure scenarios.**: Что будет, если consumer упадёт на час? Если Kafka недоступен? Если schema изменится?

## Теория

Промышленный CDC конвейер обязан быть протестирован в условиях трех критических аварийных сценариев (Chaos Engineering):
1. **Consumer Down (Консьюмер оффлайн 1 час):**
   - Слот в PostgreSQL удерживает WAL.
   - Проверяется: хватает ли диска, возобновляется ли стриминг после рестарта без потери данных.
2. **Broker Outage (Kafka недоступна 10 минут):**
   - CDC-демон не может опубликовать события.
   - Проверяется: остановка подтверждений LSN в PostgreSQL (Backpressure), отсутствие пропуска транзакций, экспоненциальный retry.
3. **DDL Schema Drift (Изменение схемы на мастере):**
   - Добавление колонок в разгар нагрузки.
   - Проверяется: отсутствие падений, динамическая адаптация к новому `RelationMessage`.

## Решение по шагам

1. Реализуйте контур симуляции сбоев с переключаемыми флагами аварий.
2. Смоделируйте сценарий недоступности брокера: переход в состояние ретраев и блокировка коммита LSN.
3. Смоделируйте восстановление связи и успешную досылку сообщений.
4. Проверьте сохранение консистентности позиций LSN.

## Код решения

**`chaos_scenarios.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"github.com/jackc/pglogrepl"
)

type ChaosSimulator struct {
	brokerOnline bool
	currentLSN   pglogrepl.LSN
}

func (s *ChaosSimulator) SendWithRetry(ctx context.Context, lsn pglogrepl.LSN, msg string) error {
	attempts := 0
	backoff := 50 * time.Millisecond

	for {
		attempts++
		if !s.brokerOnline {
			fmt.Printf("⚠️ [CHAOS SIM] Попытка #%d: Kafka брокер недоступен (ConnectionRefused)! Ожидание %v...\n",
				attempts, backoff)
			time.Sleep(backoff)
			backoff *= 2
			if attempts >= 3 {
				// Связь восстановилась
				s.brokerOnline = true
				fmt.Println("📶 [CHAOS SIM] Связь с брокером восстановлена!")
			}
			continue
		}

		fmt.Printf("✅ [CHAOS SIM] Пакет LSN %s успешно доставлен в брокер на попытке #%d!\n", lsn, attempts)
		s.currentLSN = lsn
		return nil
	}
}

func main() {
	ctx := context.Background()
	sim := &ChaosSimulator{brokerOnline: false}

	lsn, _ := pglogrepl.ParseLSN("0/16B9800")
	fmt.Println("=== Тестирование сценария отказа брокера сообщений ===")
	err := sim.SendWithRetry(ctx, lsn, "test_payload")
	if err == nil {
		fmt.Printf("Фиксация LSN в PostgreSQL разрешена: %s\n", sim.currentLSN)
	}

	fmt.Println("Вывод: Система успешно перенесла сетевой сбой без потери транзакций!")
}
```

## Под капотом

При временной недоступности брокера CDC-воркер останавливает продвижение подтвержденного LSN.
Поскольку `StandbyStatusUpdate` отправляется со старым LSN (или не отправляется вовсе), сервер PostgreSQL не удаляет сегменты WAL.
Когда связь восстанавливается, воркер передает накопившиеся данные и подтверждает итоговый LSN, обеспечивая Zero Data Loss.

## Подводные камни

1. Игнорирование ошибок отправки в брокер («fire and forget»): приведет к тому, что при сбое брокера сообщения будут потеряны навсегда, а LSN в PostgreSQL подтвержден.
2. Бесконечный backoff без ограничения максимального интервала: интервал должен ограничиваться `max_backoff = 5 * time.Second`.

## На собеседовании

В: Что произойдет, если CDC-воркер упадет ровно на 1 час в системе с генерацией 50 ГБ WAL в час?
О: 1) Слот репликации перейдет в состояние `active = false`.
2) PostgreSQL зафиксирует `restart_lsn` и сохранит все 50 ГБ WAL-файлов в директории `pg_wal`.
3) Если свободного места на диске достаточно, СУБД продолжит нормальную работу.
4) При перезапуске воркер вычитает накопившиеся 50 ГБ со скоростью диска и сети (Catch-up Mode), догонит хвост WAL и подтвердит актуальный LSN.
5) Checkpointer немедленно удалит 50 ГБ освободившихся файлов WAL с диска.
