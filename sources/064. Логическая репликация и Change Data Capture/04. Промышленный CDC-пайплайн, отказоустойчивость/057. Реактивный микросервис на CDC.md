# Реактивный микросервис на CDC: Welcome Email и синхронизация кэша Redis

## Условие

**Построение микросервиса, реагирующего на изменения.**: Реализуйте микросервис, который слушает слот репликации, при появлении новой записи в `users` отправляет приветственное письмо (заглушка) и обновляет кэш Redis. Учтите обработку ошибок и перезапуск слота с сохранением LSN.

### Исходная формулировка

**Построение микросервиса, реагирующего на изменения.**: Реализуйте микросервис, который слушает слот репликации, при появлении новой записи в `users` отправляет приветственное письмо (заглушка) и обновляет кэш Redis. Учтите обработку ошибок и перезапуск слота с сохранением LSN.

## Теория

Change Data Capture позволяет выстраивать реактивную микросервисную архитектуру без прямого связывания сервисов (Zero-Coupling Architecture).

Сценарий:
1. Основной сервис регистрации просто делает `INSERT INTO users ...` в PostgreSQL.
2. Независимый микросервис `Notification & Cache Service` слушает слот логической репликации:
   - При обнаружении нового пользователя мгновенно отправляет Welcome Email.
   - Записывает профиль пользователя в оперативный кэш Redis (`SET user:<id> <json> EX 3600`).
   - Сохраняет LSN чекпоинт.
3. Если сервис отправки писем упадет, он перезапустится и дошлет неотправленные письма благодаря надежному слоту репликации.

## Решение по шагам

1. Спроектируйте микросервис `UserReactionService`.
2. Реализуйте заглушку отправки email `SendWelcomeEmail(email)`.
3. Реализуйте функцию обновления кэша `UpdateRedisCache(userID, data)`.
4. Продемонстрируйте реакцию на событие создания пользователя с обработкой ошибок.

## Код решения

**`reactive_user_service.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"
)

type ReactiveUserService struct{}

func (s *ReactiveUserService) SendWelcomeEmail(email string) error {
	fmt.Printf("📧 [EMAIL SERVICE] Отправлено приветственное письмо на адрес: %s\n", email)
	return nil
}

func (s *ReactiveUserService) UpdateRedisCache(userID string, userData map[string]string) error {
	fmt.Printf("⚡ [REDIS CACHE] Ключ 'user:%s' обновлен в кэше (TTL: 3600s)\n", userID)
	return nil
}

func (s *ReactiveUserService) HandleCDCEvent(ctx context.Context, op string, row map[string]string) error {
	if op != "c" { // Нас интересует только регистрация (Create)
		return nil
	}

	userID := row["id"]
	email := row["email"]

	// 1. Отправляем email
	if err := s.SendWelcomeEmail(email); err != nil {
		return fmt.Errorf("ошибка отправки email: %w", err)
	}

	// 2. Инвалидируем / прогреваем кэш Redis
	if err := s.UpdateRedisCache(userID, row); err != nil {
		return fmt.Errorf("ошибка обновления Redis: %w", err)
	}

	return nil
}

func main() {
	service := &ReactiveUserService{}
	ctx := context.Background()

	// Имитация перехвата создания нового пользователя из слота репликации
	newUser := map[string]string{
		"id":         "9012",
		"email":      "newbie@golang-workout.dev",
		"created_at": time.Now().Format(time.RFC3339),
	}

	fmt.Println("=== Реактивный микросервис: Реакция на события CDC ===")
	if err := service.HandleCDCEvent(ctx, "c", newUser); err != nil {
		log.Fatalf("Ошибка обработки: %v", err)
	}

	fmt.Println("\n🎉 Реактивная логика успешно отработала без изменения кода основного сервиса!")
}
```

ℹ️ Полноценный реактивный микросервис, реагирующий на CDC события базы данных

## Под капотом

Такая архитектура устраняет связанность систем (Decoupled Microservices).
Основной сервис авторизации не знает о существовании почтового сервиса или кэша Redis, не зависит от их доступности и не тратит время на сетевые вызовы в рамках регистрации пользователя.

## Подводные камни

1. Отправка повторных писем при рестарте консьюмера: поскольку доставка At-Least-Once, сервис отправки писем обязан проверять флаг `email_sent` в БД/Redis для обеспечения идемпотентности.
2. Блокирующий вызов SMTP-сервера: долгая отправка письма замедлит вычитку WAL слота. Отправку необходимо выносить в асинхронную очередь задач.

## На собеседовании

В: Как в реактивном микросервисе на базе CDC предотвратить повторную отправку Welcome Email пользователю при рестарте сервиса после сбоя?
О: Применяется паттерн **Идемпотентный потребитель (Idempotent Consumer)**:
1) Перед вызовом почтового шлюза сервис выполняет атомарную команду в Redis:
   `SET cdc:email_sent:<user_id> 1 NX EX 86400`.
2) Если Redis вернул `OK`, письмо отправляется.
3) Если ключ уже существует (возвращен `nil`), сервис понимает, что это повтор события после рестарта, и пропускает вызов SMTP.
Это гарантирует строго однократную отправку письма пользователю (Exactly-Once Side-Effect).
