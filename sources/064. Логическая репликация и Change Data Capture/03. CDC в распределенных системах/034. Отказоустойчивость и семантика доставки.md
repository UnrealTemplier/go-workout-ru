# Отказоустойчивость и семантика доставки: At-Least-Once против Exactly-Once

## Условие

**Fault tolerance и LSN tracking.**: Реализуйте механизм: consumer обрабатывает батч, коммитит offset (LSN) в PostgreSQL через `SendStandbyStatus` только после успешной записи в downstream. При рестарте читайте с `restart_lsn`. Объясните at-least-once vs exactly-once semantics.

## Теория

В распределенных системах передачи данных Change Data Capture обеспечение семантики доставки подчиняется теореме FLP и ограничениям двухфазной фиксации (2PC).

Сравнение моделей доставки:
1. **At-Least-Once (Хотя бы один раз):**
   - Событие гарантированно доставляется, но возможны дубликаты при сбоях сети или перезапусках.
   - Стандарт для всех промышленных CDC-пайплайнов (включая Debezium).
   - Требует идемпотентности на стороне приемника данных (Idempotent Consumer / Upsert).
2. **Exactly-Once (Ровно один раз):**
   - Возможно только в рамках единой транзакционной экосистемы (например, Kafka Streams с транзакционным продюсером и двухфазным коммитом).
   - Сквозной Exactly-Once между двумя разными гетерогенными системами (PostgreSQL \(\to\) ClickHouse) невозможен без распределенного консенсуса.

Паттерн надежности:
LSN коммитится в PostgreSQL **строго после** получения подтверждения записи (Ack) от downstream-хранилища.

## Решение по шагам

1. Спроектируйте интерфейс целевого хранилища `AckSink` с подтверждением записи.
2. Реализуйте контур обработки: `Receive` \(\to\) `Publish to Sink` \(\to\) `Wait Ack` \(\to\) `SendStandbyStatus`.
3. Смоделируйте ошибку брокера: пока брокер не вернет Ack, LSN в PostgreSQL не продвигается.
4. Продемонстрируйте гарантию отсутствия потери данных.

## Код решения

**`delivery_semantics.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"github.com/jackc/pglogrepl"
)

type EventSink interface {
	WriteWithAck(ctx context.Context, lsn pglogrepl.LSN, data string) error
}

type ReliableKafkaSink struct {
	failNext bool
}

func (s *ReliableKafkaSink) WriteWithAck(ctx context.Context, lsn pglogrepl.LSN, data string) error {
	if s.failNext {
		s.failNext = false
		return errors.New("сетевой тайм-аут брокера Kafka (BrokerNotAvailable)")
	}
	fmt.Printf("📥 [KAFKA ACK] Сообщение для LSN %s успешно сохранено на репликах!\n", lsn)
	return nil
}

func ProcessCDCBatch(ctx context.Context, sink EventSink, lsn pglogrepl.LSN, payload string) (pglogrepl.LSN, error) {
	// 1. Сначала пишем в downstream хранилище
	err := sink.WriteWithAck(ctx, lsn, payload)
	if err != nil {
		fmt.Printf("⚠️ Ошибка доставки LSN %s: %v. LSN НЕ подтверждается в Postgres!\n", lsn, err)
		return 0, err
	}

	// 2. И только ПОСЛЕ успешного подтверждения возвращаем LSN для коммита в PostgreSQL
	fmt.Printf("🔒 [POSTGRES COMMIT] Разрешено зафиксировать LSN %s в слоте репликации.\n", lsn)
	return lsn, nil
}

func main() {
	ctx := context.Background()
	sink := &ReliableKafkaSink{failNext: true}

	lsn1, _ := pglogrepl.ParseLSN("0/16B7000")

	// Попытка #1: Сбой брокера
	fmt.Println("--- Попытка обработки пакета #1 ---")
	_, err := ProcessCDCBatch(ctx, sink, lsn1, "order_created_payload")
	if err != nil {
		fmt.Println("Повторная попытка (Retry) после сбоя...")
	}

	// Попытка #2: Успех
	fmt.Println("\n--- Попытка обработки пакета #2 (Retry) ---")
	confirmedLSN, err := ProcessCDCBatch(ctx, sink, lsn1, "order_created_payload")
	if err == nil {
		fmt.Printf("Успешно зафиксирован LSN: %s\n", confirmedLSN)
	}
}
```

## Под капотом

Если в момент ошибки отправки в Kafka процесс упадет, слот в PostgreSQL останется на предыдущей позиции.
После рестарта воркер перечитает ту же самую транзакцию из WAL заново.
Это гарантирует невозможность потери данных (Zero Data Loss), перенося ответственность за фильтрацию возможных повторов на идемпотентный слой консьюмера.

## Подводные камни

1. Коммит LSN до получения Ack от реплик Kafka (`acks=0` или `acks=1`): если брокер упадет до сброса на диск, сообщение исчезнет, а PostgreSQL уже удалит сегмент WAL.
2. Бесконечный цикл ретраев без таймаутов (Poison Pill): «битое» сообщение может заблокировать весь конвейер репликации, вызвав неконтролируемый рост WAL на мастере. Необходим Dead Letter Queue (DLQ).

## На собеседовании

В: Почему в CDC-системах промышленным стандартом является семантика At-Least-Once, а не Exactly-Once?
О: Достижение сквозного Exactly-Once между разнородными распределенными системами требует протокола двухфазной фиксации (Two-Phase Commit, 2PC) с распределенными блокировками.
2PC вносит колоссальную деградацию пропускной способности (latency вырастает в 10–50 раз) и подвержен блокировкам при сетевых сбоях.
Индустрия BigTech выбирает высокую производительность и простоту: надежная доставка **At-Least-Once** со стороны CDC-пайплайна в сочетании с **идемпотентным применением** (Upsert / Дедупликация) на стороне приемника данных.
