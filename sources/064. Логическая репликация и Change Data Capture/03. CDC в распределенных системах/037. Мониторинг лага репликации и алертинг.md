# Мониторинг лага репликации и алертинг: Экспорт метрик в Prometheus

## Условие

**Мониторинг и lag.**: Напишите метрики: `pg_stat_replication` → `pg_current_wal_lsn() - confirmed_flush_lsn` (lag в байтах). Выведите в Prometheus. Настройте алерт при lag > 100 MB. Объясните, почему рост lag приводит к bloat WAL и потенциальному OOM.

## Теория

Главная эксплуатационная метрика любого CDC-пайплайна — **Replication Lag (Отставание репликации)**:
$$\text{Replication Lag (Bytes)} = \text{pg\_current\_wal\_lsn}() - \text{confirmed\_flush\_lsn}$$

Почему критичен мониторинг лага:
1. Если лаг растет, значит консьюмер не успевает вычитывать изменения (Downstream Bottleneck) или завис.
2. Растущий лаг означает удержание сегментов WAL в директории `pg_wal/`.
3. При лаге более 50–100 ГБ возникает угроза аварийного отказа СУБД.

Промышленный стандарт: экспорт метрик `pg_stat_replication` в Prometheus и алерт в Telegram/PagerDuty при превышении порога в 100 МБ или 15 минут отставания.

## Решение по шагам

1. Напишите SQL-запрос для извлечения метрик из `pg_stat_replication` и `pg_replication_slots`.
2. Рассчитайте метрики `replication_lag_bytes` и статус активности `is_active`.
3. Реализуйте функцию эмуляции Prometheus Exporter.
4. Продемонстрируйте проверку критического порога лага (> 100 МБ) с генерацией алерта.

## Код решения

**`cdc_metrics_exporter.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type CDCSlotMetrics struct {
	SlotName string
	Active   bool
	LagBytes int64
}

func CollectCDCMetrics(ctx context.Context, db *sql.DB) ([]CDCSlotMetrics, error) {
	query := `
		SELECT 
			slot_name,
			active,
			COALESCE(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn), 0)::bigint AS lag_bytes
		FROM pg_replication_slots
		WHERE slot_type = 'logical';
	`
	rows, err := db.QueryContext(ctx, query)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var metrics []CDCSlotMetrics
	for rows.Next() {
		var m CDCSlotMetrics
		if err := rows.Scan(&m.SlotName, &m.Active, &m.LagBytes); err != nil {
			return nil, err
		}
		metrics = append(metrics, m)
	}
	return metrics, nil
}

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer db.Close()

	ctx := context.Background()
	metrics, err := CollectCDCMetrics(ctx, db)
	if err != nil {
		log.Fatalf("Ошибка сбора метрик: %v", err)
	}

	fmt.Println("=== Метрики Prometheus: PostgreSQL CDC Replication ===")
	thresholdBytes := int64(100 * 1024 * 1024) // 100 MB

	for _, m := range metrics {
		fmt.Printf("# HELP pg_replication_slot_lag_bytes Лаг репликации слота в байтах\n")
		fmt.Printf("# TYPE pg_replication_slot_lag_bytes gauge\n")
		fmt.Printf("pg_replication_slot_lag_bytes{slot=\"%s\"} %d\n", m.SlotName, m.LagBytes)

		fmt.Printf("# HELP pg_replication_slot_active Статус активности слота (1=активен, 0=отключен)\n")
		fmt.Printf("# TYPE pg_replication_slot_active gauge\n")
		activeVal := 0
		if m.Active {
			activeVal = 1
		}
		fmt.Printf("pg_replication_slot_active{slot=\"%s\"} %d\n\n", m.SlotName, activeVal)

		if m.LagBytes > thresholdBytes {
			fmt.Printf("🚨 [CRITICAL ALERT] Слот '%s' отстает на %.2f МБ! Риск переполнения диска pg_wal!\n",
				m.SlotName, float64(m.LagBytes)/(1024*1024))
		} else {
			fmt.Printf("✅ Слот '%s' в норме (лаг: %.2f КБ)\n",
				m.SlotName, float64(m.LagBytes)/1024)
		}
	}
}
```

## Под капотом

Функция `pg_current_wal_lsn()` возвращает позицию последней байтовой записи, сброшенной на диск сервером.
Функция `pg_wal_lsn_diff` производит 64-битное вычитание без накладных расходов.
Сбор этой метрики каждые 15 секунд дает непрерывный график в Grafana, позволяющий мгновенно обнаружить деградацию консьюмера задолго до исчерпания дискового пространства.

## Подводные камни

1. Мониторинг только `pg_stat_replication`: если консьюмер отключился, запись в `pg_stat_replication` исчезает! Слот становится неактивным, но продолжает удерживать WAL. Мониторить необходимо таблицу `pg_replication_slots`.
2. Игнорирование неактивных слотов: если `active = 0`, лаг будет линейно расти со временем.

## На собеседовании

В: Чем отличается мониторинг pg_stat_replication от pg_replication_slots?
О: 1) `pg_stat_replication`: динамическое представление, отображающее только **активно подключенные в данный момент** сессии `walsender`. Если консьюмер упал, строки в `pg_stat_replication` больше нет.
2) `pg_replication_slots`: постоянное состояние всех зарегистрированных слотов (как активных, так и оффлайн).
Для алертинга переполнения диска критически важно мониторить именно `pg_replication_slots`, так как именно неактивные слоты накапливают терабайты мертвого WAL!
