# OLTP-источник: Конкурентная генерация транзакций для CDC

## Условие

**Источник**: PostgreSQL (OLTP). Туда постоянно (через скрипт или HTTP API) идут INSERT'ы новых заказов.

## Теория

Для тестирования устойчивости CDC-пайплайна необходим надежный генератор транзакционной нагрузки (OLTP Source).

Особенности генерации транзакций в PostgreSQL для CDC:
1. Каждая транзакция создает запись в журнале предзаписи WAL (`pg_wal`).
2. В конкурентной среде несколько горутин выполняют `INSERT` и `UPDATE` параллельно.
3. Порядок поступления транзакций в логический слот определяется не моментом вызова SQL-запроса, а **моментом успешного COMMIT**.
4. Генератор должен уметь эмулировать реальную нагрузку e-commerce: создание заказов, оплата и смена статусов.

## Решение по шагам

1. Создайте пул соединений `sql.Open` с пулом из 5 воркеров.
2. Запустите параллельные горутины, создающие заказы в таблице `orders`.
3. Замерьте количество зафиксированных транзакций в секунду (TPS).
4. Продемонстрируйте, как рост TPS увеличивает скорость генерации LSN в PostgreSQL.

## Код решения

**`oltp_generator.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"
	"sync"
	"sync/atomic"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка БД: %v", err)
	}
	defer db.Close()
	db.SetMaxOpenConns(10)

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	var totalTransactions uint64
	workers := 4
	var wg sync.WaitGroup

	start := time.Now()
	for i := 1; i <= workers; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				default:
					_, err := db.ExecContext(ctx, `
						INSERT INTO orders (customer_id, amount) 
						VALUES ($1, $2);
					`, workerID*100, 199.99)
					if err == nil {
						atomic.AddUint64(&totalTransactions, 1)
					}
				}
			}
		}(i)
	}

	wg.Wait()
	elapsed := time.Since(start)

	var currentLSN string
	_ = db.QueryRow("SELECT pg_current_wal_lsn()::text;").Scan(&currentLSN)

	fmt.Printf("=== OLTP Генератор заказов ===\n")
	fmt.Printf("Успешно зафиксировано транзакций: %d за %v\n", totalTransactions, elapsed)
	fmt.Printf("Пропускная способность: %.2f TPS\n", float64(totalTransactions)/elapsed.Seconds())
	fmt.Printf("Текущий хвост WAL (LSN): %s\n", currentLSN)
}
```

ℹ️ Конкурентный генератор транзакций для нагрузочного тестирования CDC

**`Терминал`**

```bash
go run oltp_generator.go
# Вывод:
# === OLTP Генератор заказов ===
# Успешно зафиксировано транзакций: 1540 за 3.001s
# Пропускная способность: 513.16 TPS
# Текущий хвост WAL (LSN): 0/16B7820
```

## Под капотом

Каждый вызов `db.Exec` с оператором `INSERT` порождает неявную транзакцию.
Процесс PostgreSQL `walwriter` сбрасывает буферы XLOG на диск, а фоновый процесс `walsender` немедленно подхватывает новые 16-мегабайтные сегменты и передает их в сокет репликации.

## Подводные камни

1. Использование неиндексированных таблиц при конкурентных обновлениях: вызовет каскадные блокировки строк (Row-level Lock Contention) и снизит TPS.
2. Неограниченный размер пула соединений: может перегрузить процессор PostgreSQL.

## На собеседовании

В: В каком порядке попадают транзакции в логический слот репликации при конкурентной записи десятков воркеров?
О: Транзакции поступают в поток логической репликации строго в порядке их **фиксации (Commit LSN)**, а не начала (`BEGIN`).
Если транзакция A началась раньше транзакции B, но зафиксировалась позже, консьюмер сначала получит все строки транзакции B, а затем транзакции A.
Это фундаментальное свойство гарантирует, что консьюмер видит изменения ровно в той же последовательности, в какой они становятся видимыми для обычных SQL-клиентов (Read Committed).
