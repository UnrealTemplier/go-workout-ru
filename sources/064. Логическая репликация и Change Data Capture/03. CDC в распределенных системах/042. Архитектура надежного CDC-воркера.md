# Архитектура надежного CDC-воркера на jackc/pglogrepl

## Условие

**CDC Worker**: Go-сервис с `pglogrepl` читает инсерты, декодирует их.

## Теория

Промышленный CDC-воркер состоит из трех слабосвязанных компонентов:
1. **WAL Reader:** горутина, читающая байты из сокета PostgreSQL через `conn.ReceiveMessage` и парсящая `XLogData`.
2. **Decoder Engine:** компонент, сопоставляющий `RelationID` с кэшем схемы и преобразующий `TupleData` в типизированные сущности.
3. **Commit Manager:** компонент, координирующий фиксацию LSN в СУБД строго после успешной отправки данных в целевую шину.

## Решение по шагам

1. Создайте структуру `CDCWorker` с каналами очередей.
2. Реализуйте метод `Run(ctx)` с разделением потоков чтения и обработки.
3. Добавьте счетчик успешно обработанных вставок `InsertMessage`.
4. Продемонстрируйте запуск и обработку событий.

## Код решения

**`modular_cdc_worker.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"

	"github.com/jackc/pglogrepl"
)

type DecodedInsertEvent struct {
	TableName string
	LSN       pglogrepl.LSN
	Values    map[string]string
}

type CDCWorker struct {
	processedInserts uint64
}

func (w *CDCWorker) HandleInsert(event DecodedInsertEvent) {
	atomic.AddUint64(&w.processedInserts, 1)
	fmt.Printf("⚡ [WORKER DISPATCH] Таблица: %s | LSN: %s | Данные: %v\n",
		event.TableName, event.LSN, event.Values)
}

func main() {
	worker := &CDCWorker{}

	// Имитация поступления событий из потока логической репликации
	events := []DecodedInsertEvent{
		{TableName: "orders", LSN: 23805100, Values: map[string]string{"id": "1", "amount": "990.00"}},
		{TableName: "orders", LSN: 23805200, Values: map[string]string{"id": "2", "amount": "1450.00"}},
	}

	for _, ev := range events {
		worker.HandleInsert(ev)
	}

	fmt.Printf("\nИтого обработано вставок: %d\n", atomic.LoadUint64(&worker.processedInserts))
	fmt.Println("Архитектура воркера обеспечивает независимость логики от сетевого сокета.")
}
```

## Под капотом

Разделение на горутину чтения сокета и воркеры обработки через ограниченный канал Go (`chan DecodedInsertEvent`) устраняет блокировки сетевого сокета.
Чтение сокета всегда идет на максимальной скорости, а бизнес-логика выполняется параллельно на всех ядрах процессора.

## Подводные камни

1. Потеря очередности при распараллеливании воркеров: если запустить 10 воркеров, читающих из одного канала, порядок событий по одному `order_id` нарушится! Для сохранения порядка шардируйте события по внутренним каналам: `channels[Hash(Key) % N]`.
2. Неограниченный размер очереди событий в памяти: при торможении downstream приведет к росту аллокаций памяти.

## На собеседовании

В: Как распараллелить обработку CDC-событий в Go на несколько горутин, не нарушая строгую последовательность изменений по каждой сущности?
О: Применяется паттерн **Actor / Key-Based Partitioning**:
1) Главная горутина читает WAL и декодирует события.
2) Создается массив из \(N\) рабочих каналов (`[]chan *CDCEvent`).
3) По первичному ключу вычисляется хэш: `workerID = MurmurHash(entityID) % N`.
4) Событие направляется строго в канал `channels[workerID]`.
Каждый воркер обрабатывает события последовательно, что гарантирует идеальный порядок по каждому объекту при \(N\)-кратном масштабировании CPU.
