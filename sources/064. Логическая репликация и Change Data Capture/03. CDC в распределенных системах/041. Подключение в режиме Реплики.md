# Подключение в режиме Реплики: handshake и параметры сессии

## Условие

**Подключение как Реплика**: Используй библиотеку `github.com/jackc/pglogrepl` (от создателей `pgx`). Напиши Go-код, который подключается к Postgres не как обычный клиент, а притворяется **сервером-репликой** (передавая спец. параметры при соединении).

## Теория

Когда Go-приложение подключается к PostgreSQL с параметром `replication=database`, процесс соединения кардинально отличается от обычного SQL-клиента:
1. В стартовом пакете (Startup Message) передается специальный флаг `replication: "database"`.
2. PostgreSQL вместо обычного бэкенд-процесса запускает выделенный процесс `walsender`.
3. Сессия не поддерживает транзакции SQL (`BEGIN`/`COMMIT`), а принимает команды Streaming Replication Protocol: `IDENTIFY_SYSTEM`, `START_REPLICATION`, `TIMELINE_HISTORY`.
4. Сессия удерживает одно из подключений лимита `max_wal_senders`.

## Решение по шагам

1. Подключитесь к PostgreSQL через `pgconn.Connect` с параметром `replication=database`.
2. Проверьте параметры текущей сессии через системные переменные.
3. Продемонстрируйте выполнение команды `IDENTIFY_SYSTEM`.
4. Закройте соединение корректно.

## Код решения

**`replica_handshake.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

func main() {
	ctx := context.Background()

	// Параметр replication=database активирует walsender бэкенд
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable&replication=database"

	conn, err := pgconn.Connect(ctx, dsn)
	if err != nil {
		log.Fatalf("Ошибка подключения в режиме сервера-реплики: %v", err)
	}
	defer conn.Close(ctx)

	// Выполняем команду handshake протокола репликации
	sys, err := pglogrepl.IdentifySystem(ctx, conn)
	if err != nil {
		log.Fatalf("Ошибка IDENTIFY_SYSTEM: %v", err)
	}

	fmt.Println("=== Успешный Handshake сервера-реплики ===")
	fmt.Printf("• Статус соединения:  АКТИВНО (WALSENDER)\n")
	fmt.Printf("• System Identifier:  %s\n", sys.SystemID)
	fmt.Printf("• Timeline ID:        %d\n", sys.Timeline)
	fmt.Printf("• Current XLOG LSN:   %s\n", sys.XLogPos)
	fmt.Printf("• Целевая база:       %s\n", sys.DBName)
}
```

## Под капотом

На стороне ядра PostgreSQL при получении флага `replication` вызывается внутренняя функция `InitProcess`, которая переводит процесс в режим `AmWalSenderProcess = true`.
Процесс освобождается от блокировок таблиц и переходит на чтение кольцевого буфера WAL через вызовы `XLogRead`.

## Подводные камни

1. Превышение лимита `max_wal_senders`: если все слоты заняты другими репликами или зависшими процессами, подключение вернет ошибку `FATAL: number of requested standby connections exceeds max_wal_senders`.
2. Попытка открыть пул `pgxpool.Pool` с параметром `replication=database`: пулы соединений не умеют управлять репликационными сокетами. Используйте строго одиночные `pgconn.PgConn`.

## На собеседовании

В: Почему для CDC нельзя использовать стандартный пул соединений database/sql или pgxpool?
О: Стандартный пул соединений рассчитан на разделение сокетов между множеством кратковременных SQL-запросов (запрос завершился — сокет вернулся в пул).
Репликационное соединение `walsender` является монопольным и долгоживущим: оно монополизирует TCP сокет на недели и месяцы, непрерывно считывая поток WAL через Copy-Both режим.
Попытка вернуть репликационный сокет в обычный пул приведет к зависанию пула и поломке SQL-запросов приложения.
