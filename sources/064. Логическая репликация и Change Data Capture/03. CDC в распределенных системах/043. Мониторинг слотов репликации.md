# Мониторинг слотов репликации и диагностика заброшенных слотов

## Условие

**Replication slots требуют мониторинга.**: Неухоженный slot заполнит диск primary БД. Мониторьте `pg_replication_slots`.

## Теория

Заброшенный или неактивный слот репликации — главная причина аварий баз данных PostgreSQL под нагрузкой.

Ключевые поля системного каталога `pg_replication_slots`:
- `active`: подключен ли клиент к слоту в данный момент (`true/false`).
- `restart_lsn`: позиция самого старого WAL, который требуется для рестарта.
- `confirmed_flush_lsn`: позиция, подтвержденная клиентом.
- `wal_status`: состояние удержания WAL (`normal`, `reserved`, `extended`, `lost`).

Если слот находится в состоянии `active = false`, а `pg_current_wal_lsn() - restart_lsn` растет более 10 ГБ — слот считается «заброшенным» и подлежит принудительному удалению через `pg_drop_replication_slot`.

## Решение по шагам

1. Напишите SQL-запрос для выявления неактивных слотов репликации.
2. Рассчитайте объем удерживаемого WAL для каждого слота.
3. Реализуйте логику автоматического предупреждения (warning) при простое неактивного слота.
4. Продемонстрируйте диагностику кластера.

## Код решения

**`slot_healthcheck.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type ReplicationSlotAudit struct {
	SlotName   string
	Plugin     string
	Active     bool
	WALStatus  string
	RetainedMB float64
}

func AuditReplicationSlots(ctx context.Context, db *sql.DB) ([]ReplicationSlotAudit, error) {
	query := `
		SELECT 
			slot_name,
			plugin,
			active,
			COALESCE(wal_status, 'normal') AS wal_status,
			ROUND(COALESCE(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn), 0) / (1024*1024)::numeric, 2)::float8 AS retained_mb
		FROM pg_replication_slots;
	`
	rows, err := db.QueryContext(ctx, query)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var audits []ReplicationSlotAudit
	for rows.Next() {
		var a ReplicationSlotAudit
		if err := rows.Scan(&a.SlotName, &a.Plugin, &a.Active, &a.WALStatus, &a.RetainedMB); err != nil {
			return nil, err
		}
		audits = append(audits, a)
	}
	return audits, nil
}

func main() {
	dsn := "postgres://cdc_user:cdc_password@localhost:5432/workout_db?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		log.Fatalf("Ошибка подключения: %v", err)
	}
	defer db.Close()

	ctx := context.Background()
	slots, err := AuditReplicationSlots(ctx, db)
	if err != nil {
		log.Fatalf("Ошибка аудита: %v", err)
	}

	fmt.Println("=== Аудит состояния слотов репликации ===")
	for _, s := range slots {
		status := "🟢 РАБОТАЕТ"
		if !s.Active {
			status = "🔴 ОТКЛЮЧЕН"
		}

		fmt.Printf("• Слот: %-18s | Плагин: %-10s | %s | Удерживает WAL: %.2f МБ | Статус: %s\n",
			s.SlotName, s.Plugin, status, s.RetainedMB, s.WALStatus)

		if !s.Active && s.RetainedMB > 500 {
			fmt.Printf("   ⚠️ ВНИМАНИЕ: Слот '%s' неактивен и накопил более 500 МБ WAL! Проверьте воркер!\n", s.SlotName)
		}
	}
}
```

## Под капотом

Поле `wal_status` появилось в PostgreSQL 13+.
Значение `lost` означает, что объем невычитанного WAL превысил параметр `max_slot_wal_keep_size`, и сервер принудительно удалил сегменты.
Такой слот навсегда потерял целостность и должен быть немедленно пересоздан.

## Подводные камни

1. Удаление активного слота (`active = true`): PostgreSQL вернет ошибку `ERROR: replication slot is active for PID ...`. Сначала необходимо остановить клиентский процесс, и только затем удалять слот.
2. Отсутствие автоматического очистителя (Auto-reaper) в staging/dev окружениях: разработчики создают тестовые слоты и забывают их, что приводит к падению общих баз данных.

## На собеседовании

В: Что произойдет, если значение wal_status слота перешло в 'lost'?
О: Слот переходит в состояние `invalidated`.
При попытке клиента вызвать `StartReplication` сервер вернет фатальную ошибку:
`ERROR: can no longer get changes from replication slot`.
Это означает необратимую потерю сегментов WAL.
Единственный способ восстановления — удалить поврежденный слот через `SELECT pg_drop_replication_slot('name')`, создать его заново и запустить процедуру полного Initial Snapshot.
