# Обязательность отслеживания LSN: Предотвращение потери данных при рестартах

## Условие

**LSN tracking обязателен.**: Без сохранения LSN вы потеряете события при рестарте.

## Теория

При проектировании промышленных CDC-систем потеря даже одного события изменения баланса пользователя или статуса заказа недопустима.

Без внешнего отслеживания LSN:
1. При перезапуске воркера он обращается к слоту, который хранит только периодически сбрасываемый `confirmed_flush_lsn`.
2. Если воркер сохранил данные в Kafka, но упал до отправки сетевого подтверждения в PostgreSQL, сервер начнет передачу с более старой позиции.
3. Возникает всплеск дубликатов сообщений (Duplicate Storm).
4. Если же сервис ошибется и передаст LSN «из будущего», он навсегда пропустит часть транзакций!

Правило: LSN должен персистентно фиксироваться вместе с контрольной меткой транзакции.

## Решение по шагам

1. Спроектируйте структуру журнала прогресса `ReplicationProgress`.
2. Реализуйте атомарное обновление прогресса при получении каждого `CommitMessage`.
3. Реализуйте проверку монотонности LSN: LSN не может уменьшаться в рамках одного таймлайна.
4. Продемонстрируйте валидацию последовательности.

## Код решения

**`lsn_progress_validator.go`**

```go
package main

import (
	"fmt"

	"github.com/jackc/pglogrepl"
)

type ReplicationProgressTracker struct {
	lastCommittedLSN pglogrepl.LSN
}

func (t *ReplicationProgressTracker) Commit(lsn pglogrepl.LSN) error {
	if lsn <= t.lastCommittedLSN {
		return fmt.Errorf("нарушение монотонности: входящий LSN %s <= последнего зафиксированного %s",
			lsn, t.lastCommittedLSN)
	}

	fmt.Printf("Продвижение прогресса: %s -> %s (+%d байт)\n",
		t.lastCommittedLSN, lsn, lsn-t.lastCommittedLSN)
	t.lastCommittedLSN = lsn
	return nil
}

func main() {
	tracker := &ReplicationProgressTracker{}

	lsn1, _ := pglogrepl.ParseLSN("0/16B8000")
	lsn2, _ := pglogrepl.ParseLSN("0/16B8500")
	lsnStale, _ := pglogrepl.ParseLSN("0/16B8200") // Устаревший LSN

	_ = tracker.Commit(lsn1)
	_ = tracker.Commit(lsn2)

	// Попытка применить старый LSN
	err := tracker.Commit(lsnStale)
	if err != nil {
		fmt.Printf("⚠️ Ошибка отклонена: %v\n", err)
	}
}
```

ℹ️ Валидация монотонности LSN для защиты от повторов и рассинхронизации

**`Терминал`**

```bash
go run lsn_progress_validator.go
# Вывод:

# Продвижение прогресса: 0/16B8000 -> 0/16B8500 (+1280 байт)
# ⚠️ Ошибка отклонена: нарушение монотонности: входящий LSN 0/16B8200 <= последнего зафиксированного 0/16B8500
```

## Под капотом

Внутри одного TimelineID значение LSN является строго монотонно возрастающим 64-битным счетчиком.
Проверка монотонности исключает фатальные ошибки человеческого фактора или рассинхронизации кэша при чтении сохраненного чекпоинта.

## Подводные камни

1. Перезапись LSN меньшим значением: заставит консьюмер бесконечно перечитывать один и тот же участок WAL.
2. Смена TimelineID: при переключении на реплику (failover) LSN может начаться с другого диапазона. В трекере необходимо учитывать пару `(TimelineID, LSN)`.

## На собеседовании

В: Как восстановить репликацию, если при переключении мастера на реплику (Failover) номер таймлайна изменился?
О: При промоуте реплики в новый мастер в PostgreSQL создается файл `.history` и инкрементируется `TimelineID`.
В `StartReplicationOptions` параметр `Timeline: 0` инструктирует сервер использовать текущий активный таймлайн.
Если в слоте сохранен LSN от старого мастера, клиент может продолжить чтение с нового мастера, если старый мастер успел передать все сегменты до точки развилки (Fork Point).
