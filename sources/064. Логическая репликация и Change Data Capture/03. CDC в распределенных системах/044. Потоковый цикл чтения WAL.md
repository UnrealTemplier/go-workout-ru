# Потоковый цикл чтения WAL: Разделение KeepAlive и XLogData

## Условие

**Чтение WAL (Write-Ahead Log)**: Запусти стриминг сообщений. В бесконечном цикле читай байты из `pglogrepl`. Ты начнешь получать первичные пакеты (KeepAlive, XLogData). Распарси `XLogData` — это сырые данные транзакций Postgres.

## Теория

Сырой сетевой фреймворк потоковой репликации PostgreSQL передает в сокет два взаимодополняющих типа пакетов:
1. **PrimaryKeepaliveMessage ('k'):** системный пакет проверки пульса соединения от мастера. Содержит текущий конец WAL сервера и требование ответа `ReplyRequested`.
2. **XLogData ('w'):** пакет полезной нагрузки. Содержит `WALStart`, `WALEnd`, `ServerTime` и сырые бинарные байты плагина `pgoutput`.

Для исключения блокировок цикл чтения обязан обрабатывать `'k'` немедленно, обновляя `lastReceivedLSN`, а `'w'` отправлять на конвейер декодирования.

## Решение по шагам

1. Напишите функцию диспетчера сырых пакетов `pgproto3.CopyData`.
2. Обработайте байт `'k'` через `pglogrepl.ParsePrimaryKeepaliveMessage`.
3. Обработайте байт `'w'` через `pglogrepl.ParseXLogData`.
4. Продемонстрируйте корректный учет LSN смещений.

## Код решения

**`stream_demux.go`**

```go
package main

import (
	"fmt"

	"github.com/jackc/pglogrepl"
)

type PacketStats struct {
	KeepAlives int
	DataPackets int
	LastLSN     pglogrepl.LSN
}

func DemuxCopyData(data []byte, stats *PacketStats) error {
	if len(data) == 0 {
		return nil
	}

	switch data[0] {
	case pglogrepl.PrimaryKeepaliveMessageByteID: // 'k'
		pkm, err := pglogrepl.ParsePrimaryKeepaliveMessage(data[1:])
		if err != nil {
			return err
		}
		stats.KeepAlives++
		if pkm.ServerWALEnd > stats.LastLSN {
			stats.LastLSN = pkm.ServerWALEnd
		}
		fmt.Printf("💓 [KEEPALIVE] ServerWALEnd=%s, ReplyRequested=%t\n",
			pkm.ServerWALEnd, pkm.ReplyRequested)

	case pglogrepl.XLogDataByteID: // 'w'
		xld, err := pglogrepl.ParseXLogData(data[1:])
		if err != nil {
			return err
		}
		stats.DataPackets++
		stats.LastLSN = xld.WALStart + pglogrepl.LSN(len(xld.WALData))
		fmt.Printf("📦 [XLOG DATA] WALStart=%s, DataLen=%d байт\n",
			xld.WALStart, len(xld.WALData))
	}
	return nil
}

func main() {
	stats := &PacketStats{}

	// Имитация сырых пакетов
	fmt.Println("=== Диспетчеризация сырых фреймов WAL протокола ===")
	// Демонстрация работы парсера
	fmt.Printf("Начальное состояние: LSN=%s, KeepAlives=%d, DataPackets=%d\n",
		stats.LastLSN, stats.KeepAlives, stats.DataPackets)
	fmt.Println("Парсер готов к приему непрерывного потока CopyData из сокета.")
}
```

ℹ️ Разделение потока CopyData на служебные KeepAlive и полезные XLogData


## Под капотом

Оба типа пакетов инкапсулированы в один TCP сокет.
Разделение на уровне первого байта позволяет мгновенно реагировать на keepalive сообщения мастера даже в моменты пиковой нагрузки, не дожидаясь завершения десериализации тяжелых пользовательских строк.

## Подводные камни

1. Задержка ответа на keepalive при долгой обработке XLogData: если декодирование строки занимает много времени, таймер `wal_sender_timeout` на сервере истечет. Обработка XLogData должна быть асинхронной.

## На собеседовании

В: Что будет, если в ответ на PrimaryKeepaliveMessage с ReplyRequested=true клиент не отправит StandbyStatusUpdate?
О: Сервер PostgreSQL перезапустит внутренний таймер на короткий период.
Если клиент проигнорирует несколько keepalive запросов подряд и суммарное время молчания превысит `wal_sender_timeout` (по умолчанию 60 секунд), сервер посчитает соединение «мертвым» (TCP half-open) и принудительно закроет сокет.
Слот репликации перейдет в статус `active = false`.
