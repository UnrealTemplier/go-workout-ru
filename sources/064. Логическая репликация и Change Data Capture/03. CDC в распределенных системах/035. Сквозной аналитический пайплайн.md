# Сквозной аналитический пайплайн: PostgreSQL CDC → Kafka → ClickHouse

## Условие

**[Финальное испытание — Real-time Analytics Pipeline]**
Построй сквозную систему аналитики в реальном времени:

## Теория

Сквозной конвейер реального времени объединяет все изученные компоненты:
1. **OLTP (PostgreSQL):** обработка транзакций заказов и платежей пользователей.
2. **CDC Демон (Go + pglogrepl):** неблокирующее чтение изменений из WAL без нагрузки на базу данных.
3. **Шина событий (Apache Kafka):** буферизация, изоляция продюсеров и консьюмеров, гарантированное хранение и масштабирование по партициям.
4. **OLAP Воркер (Go Consumer):** вычитывание пачек сообщений из Kafka и пакетная вставка в ClickHouse через нативный бинарный протокол.
5. **Аналитическая СУБД (ClickHouse):** мгновенное выполнение агрегаций над миллиардами записей для дашбордов Grafana/BI.

## Решение по шагам

1. Спроектируйте сквозной тип `OrderAnalyticsEvent`.
2. Реализуйте канал эмуляции шины Kafka между CDC-генератором и аналитическим батчером.
3. Реализуйте аналитический воркер с пакетным сбросом в ClickHouse.
4. Продемонстрируйте прохождение события от имитации WAL до аналитической вставки.

## Код решения

**`e2e_pipeline.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OrderAnalyticsEvent struct {
	ID        int64     `json:"id"`
	Amount    float64   `json:"amount"`
	Status    string    `json:"status"`
	LSN       uint64    `json:"lsn"`
	CreatedAt time.Time `json:"created_at"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// Эмуляция шины Kafka через буферизованный канал Go
	kafkaTopic := make(chan OrderAnalyticsEvent, 100)
	var wg sync.WaitGroup

	// 1. CDC Producer (читает WAL и пушит в шину)
	wg.Add(1)
	go func() {
		defer wg.Done()
		defer close(kafkaTopic)

		events := []OrderAnalyticsEvent{
			{ID: 101, Amount: 1200.50, Status: "PAID", LSN: 23801000, CreatedAt: time.Now()},
			{ID: 102, Amount: 450.00, Status: "PAID", LSN: 23801200, CreatedAt: time.Now()},
			{ID: 103, Amount: 9900.00, Status: "PENDING", LSN: 23801400, CreatedAt: time.Now()},
		}

		for _, ev := range events {
			select {
			case <-ctx.Done():
				return
			case kafkaTopic <- ev:
				fmt.Printf("📤 [CDC -> KAFKA] Опубликован заказ ID=%d (LSN: %d)\n", ev.ID, ev.LSN)
				time.Sleep(50 * time.Millisecond)
			}
		}
	}()

	// 2. ClickHouse Batch Consumer (читает пачками из Kafka и сохраняет в OLAP)
	wg.Add(1)
	go func() {
		defer wg.Done()
		batch := make([]OrderAnalyticsEvent, 0, 10)
		ticker := time.NewTicker(200 * time.Millisecond)
		defer ticker.Stop()

		flush := func() {
			if len(batch) == 0 {
				return
			}
			fmt.Printf("🚀 [KAFKA -> CLICKHOUSE] Пакетный сброс %d записей в таблицу orders_report!\n", len(batch))
			totalRevenue := 0.0
			for _, item := range batch {
				totalRevenue += item.Amount
			}
			fmt.Printf("   📊 Суммарная выручка в батче: %.2f руб\n", totalRevenue)
			batch = batch[:0]
		}

		for {
			select {
			case <-ctx.Done():
				flush()
				return
			case item, ok := <-kafkaTopic:
				if !ok {
					flush()
					return
				}
				batch = append(batch, item)
				if len(batch) >= 2 {
					flush()
				}
			case <-ticker.C:
				flush()
			}
		}
	}()

	wg.Wait()
	fmt.Println("\n✅ Сквозной Real-time пайплайн CDC -> Kafka -> ClickHouse успешно отработал!")
}
```

## Под капотом

В производственных масштабах такой конвейер изолирует OLTP базу от аналитической нагрузки.
Сложные агрегации `GROUP BY` и `COUNT(DISTINCT user_id)` исполняются на стороне ClickHouse, не расходуя ни одного процента CPU на основном мастере PostgreSQL.

## Подводные камни

1. Отсутствие буфера Kafka между CDC и ClickHouse: прямая запись из CDC в ClickHouse приведет к падению репликации при любой кратковременной недоступности ClickHouse. Kafka выступает амортизатором нагрузки (Shock Absorber).
2. Слишком мелкие батчи в ClickHouse: размер батча должен составлять от 1 000 до 50 000 записей.

## На собеседовании

В: Зачем между CDC-демоном и ClickHouse обязательно ставят Kafka, вместо прямой записи?
О: Причины три:
1) **Амортизация всплесков (Decoupling & Buffering):** При пиковых распродажах (Black Friday) база генерирует миллионы изменений. Kafka надежно буферизует этот поток на диске, позволяя ClickHouse консьюмеру вычитывать данные с комфортной скоростью батчинга.
2) **Отказоустойчивость:** Если ClickHouse перезагружается или накатывает обновление, CDC-воркер продолжает работу без остановок.
3) **Fan-out:** Одно и то же событие из Kafka могут независимо читать разные потребители: ClickHouse (аналитика), Elasticsearch (поиск) и сервис уведомлений.
