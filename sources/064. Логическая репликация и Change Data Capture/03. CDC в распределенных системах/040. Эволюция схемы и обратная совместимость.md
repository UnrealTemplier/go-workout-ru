# Эволюция схемы и обратная совместимость: Nullable поля и Soft Delete

## Условие

## Теория

Синхронизация схемы между источником (PostgreSQL) и приемниками (downstream Kafka / ClickHouse / Elasticsearch) требует соблюдения правил **обратной совместимости (Backward Compatibility)**:

Правила эволюции схем в CDC:
1. **Добавление колонки (`ALTER TABLE ADD COLUMN`):**
   - Новое поле ОБЯЗАНО быть либо `NULLABLE`, либо иметь константный `DEFAULT`.
   - В downstream-хранилищах поле создается как nullable до или одновременно с миграцией.
2. **Удаление колонки (`DROP COLUMN`):**
   - Прямое удаление колонки ломает старых консьюмеров, которые ожидают это поле.
   - Стандарт BigTech: сначала в коде выполняется отказ от использования колонки, затем миграция на Soft Delete (пометка поля как deprecated), и только потом физический `DROP`.
3. `RelationMessage` от PostgreSQL автоматически содержит обновленный список полей.

## Решение по шагам

1. Смоделируйте выполнение миграции `ALTER TABLE users ADD COLUMN phone VARCHAR;`.
2. Реализуйте консьюмер, который валидирует входящие кортежи на наличие опциональных полей.
3. Продемонстрируйте корректную обработку событий как со старой схемой (без `phone`), так и с новой схемой (с `phone`).
4. Выведите результат сериализации в JSON с сохранением обратной совместимости.

## Код решения

**`schema_compatibility.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
)

type UserDownstreamDTO struct {
	ID        int64   `json:"id"`
	Email     string  `json:"email"`
	Phone     *string `json:"phone,omitempty"` // Nullable колонка для обратной совместимости
	IsDeleted bool    `json:"is_deleted"`
}

func ProcessCDCRecord(schemaVersion int, rawData map[string]any) ([]byte, error) {
	dto := UserDownstreamDTO{
		ID:    int64(rawData["id"].(int)),
		Email: rawData["email"].(string),
	}

	// Если в новой схеме появилось поле phone — заполняем его
	if val, ok := rawData["phone"]; ok && val != nil {
		phoneStr := val.(string)
		dto.Phone = &phoneStr
	}

	return json.Marshal(dto)
}

func main() {
	// 1. Событие до миграции (версия 1: id, email)
	rowV1 := map[string]any{"id": 101, "email": "user1@yandex.ru"}
	jsonV1, _ := ProcessCDCRecord(1, rowV1)
	fmt.Printf("Версия схемы 1 (до ALTER TABLE):\n%s\n\n", string(jsonV1))

	// 2. Событие после миграции (версия 2: id, email, phone)
	rowV2 := map[string]any{"id": 102, "email": "user2@yandex.ru", "phone": "+7-999-000-11-22"}
	jsonV2, _ := ProcessCDCRecord(2, rowV2)
	fmt.Printf("Версия схемы 2 (после ALTER TABLE ADD COLUMN phone):\n%s\n", string(jsonV2))

	fmt.Println("\n✅ Обратная совместимость downstream-систем полностью сохранена!")
}
```

## Под капотом

В PostgreSQL 11+ добавление колонки с константным значением по умолчанию (`ALTER TABLE ... ADD COLUMN col INT DEFAULT 0`) выполняется за \(O(1)\) без блокировки и перезаписи строк таблицы (значение по умолчанию пишется только в системный каталог `pg_attribute`).
При логическом декодировании `pgoutput` подставляет это дефолтное значение в кортеж строки для старых записей на лету.

## Подводные камни

1. Добавление колонки `NOT NULL` без значения `DEFAULT`: заблокирует таблицу эксклюзивным замком `ACCESS EXCLUSIVE LOCK`, что приведет к остановке всей OLTP базы данных.
2. Изменение типа существующей колонки (например, `INT` в `VARCHAR`): может привести к аварийному падению CDC-консьюмера из-за несовместимости OID кодеков.

## На собеседовании

В: Что произойдет с CDC-пайплайном, если в PostgreSQL выполнить ALTER TABLE DROP COLUMN?
О: При удалении колонки в PostgreSQL:
1) Следующее сообщение `RelationMessage` от `pgoutput` больше не будет содержать эту колонку в массиве `Columns`.
2) Если консьюмер маппит поля по жестким индексам массива без проверки имени колонки, значения колонок «съедут» на одну позицию, что вызовет порчу данных!
3) Для предотвращения инцидентов downstream поля должны маппиться **исключительно по именам колонок**, а удаленные поля должны сохраняться со значением `nil` (soft delete поля).
