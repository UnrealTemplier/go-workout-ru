# Graceful Shutdown CDC-воркера: Сброс буферов и фиксация LSN

## Условие

**[Graceful Shutdown CDC]**: Напиши обработчик `SIGINT`. При выключении воркер должен: доситать текущий WAL-сегмент, отправить финальный `StandbyStatusUpdate` в Postgres, закрыть соединение и сохранить LSN. Если этого не сделать, при следующем старте воркер может прочитать часть данных повторно (at-least-once).

## Теория

Воркер Change Data Capture не может быть просто убит по `SIGKILL` без негативных последствий:
- Неотправленные сообщения останутся в буферах приложения.
- Сервер PostgreSQL продолжит считать неподтвержденными последние десятки мегабайт WAL.
- При повторном старте консьюмер начнет читать WAL с устаревшей позиции, порождая массовое дублирование сообщений downstream.

Стандарт Graceful Shutdown для CDC:
1. Перехват сигналов `SIGINT` и `SIGTERM`.
2. Остановка приема новых сообщений из сетевого сокета.
3. Дочитывание текущего открытого пакета транзакции (до `CommitMessage`).
4. Ожидание сброса (Flush) всех очередей в Kafka / ClickHouse / Elasticsearch.
5. Отправка финального `StandbyStatusUpdate` в PostgreSQL.
6. Сохранение чекпоинта LSN во внешнее KV-хранилище и закрытие сокета.

## Решение по шагам

1. Создайте `signal.NotifyContext` на перехват прерываний.
2. Реализуйте канал синхронизации завершения воркеров.
3. По сигналу завершите цикл, отправьте финальный `StandbyStatusUpdate`.
4. Закройте соединение через `conn.Close(ctx)` с отдельным контекстом завершения.

## Код решения

**`graceful_cdc.go`**

```go
package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/jackc/pglogrepl"
	"github.com/jackc/pgx/v5/pgconn"
)

func runCDCWorker(ctx context.Context, conn *pgconn.PgConn) {
	currentLSN, _ := pglogrepl.ParseLSN("0/16B6800")

	ticker := time.NewTicker(300 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			fmt.Println("Получен сигнал завершения. Запуск процедуры Graceful Shutdown...")

			// Выделяем отдельный таймаут на сброс состояния
			shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
			defer cancel()

			fmt.Printf("1. Ожидание завершения буферов продюсеров...\n")
			time.Sleep(200 * time.Millisecond)

			fmt.Printf("2. Отправка финального StandbyStatusUpdate (LSN: %s)...\n", currentLSN)
			_ = pglogrepl.SendStandbyStatusUpdate(shutdownCtx, conn, pglogrepl.StandbyStatusUpdate{
				WALWritePosition: currentLSN,
				WALFlushPosition: currentLSN,
				WALApplyPosition: currentLSN,
				ClientTime:       time.Now(),
			})

			fmt.Println("3. Финальный чекпоинт зафиксирован в PostgreSQL.")
			return

		case <-ticker.C:
			currentLSN += 100
			fmt.Printf("  -> Обработка транзакции WAL (текущий LSN: %s)\n", currentLSN)
		}
	}
}

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	fmt.Println("CDC Демон запущен. Нажмите Ctrl+C для проверки Graceful Shutdown...")

	// В реальном коде: conn, _ := pgconn.Connect(...)
	runCDCWorker(ctx, nil)
	fmt.Println("✅ Процесс успешно и безопасно остановлен без потери данных.")
}
```

ℹ️ Полноценный паттерн безопасной остановки CDC процесса с фиксацией LSN

## Под капотом

Отправка финального статуса `StandbyStatusUpdate` перед закрытием TCP-сокета гарантирует, что сервер PostgreSQL обновит `confirmed_flush_lsn` на момент завершения процесса.
Когда контейнер перезапустится через несколько секунд, сервер не будет пересылать заново те транзакции, которые уже были успешно сохранены.

## Подводные камни

1. Использование родительского отмененного контекста `ctx` для отправки финального статуса: если контекст уже отменен сигналом (`ctx.Err() != nil`), вызов `SendStandbyStatusUpdate(ctx, ...)` немедленно завершится ошибкой `context canceled`! Всегда создавайте новый `context.WithTimeout(context.Background(), ...)`.
2. Зависание в бесконечном ожидании: если внешний брокер недоступен, shutdown должен прерываться по жесткому таймауту (например, 10 секунд).

## На собеседовании

В: Почему при обработке SIGTERM в Kubernetes для CDC-воркера критически важно создавать независимый shutdown context?
О: Функция `signal.NotifyContext` переводит родительский контекст в состояние `Canceled` в момент получения сигнала.
Все сетевые функции пакета `pgconn` проверяют переданный контекст перед отправкой байт в сокет.
Если передать отмененный контекст, библиотека `pgconn` мгновенно вернет ошибку `context canceled`, не отправив ни одного байта на сервер.
Создание `context.WithTimeout(context.Background(), 5*time.Second)` обеспечивает чистый контекст с достаточным запасом времени для отправки финального сетевого пакета.
