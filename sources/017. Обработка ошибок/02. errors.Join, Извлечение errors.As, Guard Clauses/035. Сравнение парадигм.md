# Сравнение парадигм: возврат ошибок в Go против исключений try/catch

## Условие

Сравните подход "возвращать ошибки" (как в Go) и "бросать исключения" (как в Java/Python). Попробуйте написать функцию без `if err != nil` и осознайте, почему в Go это считается плохой практикой.

## Теория

В языках с исключениями (`try/catch`) ошибки невидимы в сигнатуре метода и приводят к скрытым аварийным завершениям. В Go ошибки являются явной частью контракта функции.

## Решение по шагам

1. Создадим функцию `ParseUser(raw string) (*User, error)`.
2. Покажем явную обработку ошибок.
3. В комментариях проанализируем архитектурные преимущества подхода Go.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type User struct {
	Name string
}

func ParseUser(raw string) (*User, error) {
	if raw == "" {
		return nil, errors.New("raw string is empty")
	}
	return &User{Name: raw}, nil
}

func main() {
	user, err := ParseUser("")
	if err != nil {
		fmt.Println("Явная обработка ошибки на месте вызова:", err)
		return
	}
	fmt.Println("Пользователь:", user.Name)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Явная обработка ошибки на месте вызова: raw string is empty
```

## Под капотом

Отсутствие исключений исключает сбор стектрейсов и накладные расходы на раскрутку стека при штатных бизнес-ошибках.

## Подводные камни

Игнорирование ошибок через пустой идентификатор `_` лишает код гарантий надежности.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go нет исключений (exceptions)?»
**Ответ:** 1) Исключения стимулируют разработчиков относиться к штатным ситуациям (файл не найден, сеть недоступна) как к авариям. 2) Исключения запутывают поток управления (нелокальные переходы goto по стеку). 3) Ошибки как значения заставляют продумывать обработку каждого сбоя.
