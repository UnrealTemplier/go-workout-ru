# Кастомный тип NotFoundError с деталями ресурса и ID

## Условие

Создай **кастомный тип ошибки** `type NotFoundError struct { Resource string; ID int }`. Реализуй `Error() string`. Используй `errors.As` для извлечения конкретного типа из цепочки ошибок.

## Теория

Структурированная ошибка `NotFoundError` точно указывает, какой именно ресурс (`User`, `Order`, `Invoice`) и с каким идентификатором отсутствует.

## Решение по шагам

1. Объявим `type NotFoundError struct { Resource string; ID int }`.
2. Реализуем `Error() string`.
3. Создадим функцию `FindUser(id int) error`.
4. В `main` извлечем `NotFoundError` и выведем форматированное сообщение.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type NotFoundError struct {
	Resource string
	ID       int
}

func (e *NotFoundError) Error() string {
	return fmt.Sprintf("ресурс %s с ID=%d не найден", e.Resource, e.ID)
}

func FindUser(id int) error {
	return fmt.Errorf("user repository: %w", &NotFoundError{Resource: "User", ID: id})
}

func main() {
	err := FindUser(777)
	if err != nil {
		var notFound *NotFoundError
		if errors.As(err, &notFound) {
			fmt.Printf("Сущность: %s | Идентификатор: %d\n", notFound.Resource, notFound.ID)
		}
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Сущность: User | Идентификатор: 777
```

## Под капотом

`NotFoundError` передается по указателю `*NotFoundError`, реализуя контракт `error`.

## Подводные камни

Не забывайте, что `NotFoundError` реализует `error` только для указателя `*NotFoundError`.

## На собеседовании

**Вопрос с собеседования:** «Почему структурированные ошибки лучше конкатенации строк fmt.Errorf?»
**Ответ:** Структурированные ошибки позволяют тестировать логику через проверку полей структуры `err.ID == 777` вместо ненадежного сравнения строковых сообщений.
