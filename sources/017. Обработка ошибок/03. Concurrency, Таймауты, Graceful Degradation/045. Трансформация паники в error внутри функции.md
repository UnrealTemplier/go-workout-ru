# Трансформация паники в error внутри функции

## Условие

Используй `defer` и `recover()` внутри функции для перехвата паники. Верни перехваченную панику как обычную `error` из функции.

## Теория

Преобразование паники в ошибку позволяет изолировать опасный код внутри функции, защищая вызывающий код от аварийного завершения.

## Решение по шагам

1. Объявим `func ExecutePlugin(name string) (err error)`.
2. В `defer` перехватим панику и сформируем `err = fmt.Errorf("plugin panic: %v", r)`.
3. В `main` вызовем функцию и распечатаем возвращенный `err`.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func riskyPlugin() {
	var ptr *int
	*ptr = 42 // Nil pointer dereference panic
}

func ExecutePlugin() (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("plugin execution crashed: %v", r)
		}
	}()

	riskyPlugin()
	return nil
}

func main() {
	err := ExecutePlugin()
	if err != nil {
		fmt.Println("Штатно обработана внутренняя авария плагина:")
		fmt.Println("->", err)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Штатно обработана внутренняя авария плагина:
# -> plugin execution crashed: runtime error: invalid memory address or nil pointer dereference
```

## Под капотом

Присваивание именованному возвращаемому значению `err` в `defer` перезаписывает результат функции до возврата в стек вызова.

## Подводные камни

Не скрывайте паники вслепую без логирования или возврата ошибки — это затруднит поиск багов.

## На собеседовании

**Вопрос с собеседования:** «Когда паттерн Panic-to-Error оправдан в архитектуре?»
**Ответ:** При интеграции с динамическими плагинами, парсерами недоверенных форматов или выполнении пользовательского кода/скриптов, чтобы ошибка в одном модуле не обрушила весь микросервис.
