# Упорядочивание памяти (Memory Ordering) и семантика Acquire-Release

## Условие

Исследуйте модель памяти Go (Go Memory Model) и аппаратное переупорядочивание инструкций (Memory Reordering). Покажите, как отсутствие атомарных операций в SPSC буфере приводит к чтению устаревших или полузаписанных данных, и объясните семантику Acquire-Release.

### Исходная формулировка

**Memory Ordering.**: Добавьте `runtime.Gosched()` в SPSC и покажите, что без `atomic` (plain reads/writes) может произойти reordering. Объясните acquire/release семантику: consumer делает `atomic.LoadUint64(&tail)` (acquire) перед чтением данных, producer — `atomic.StoreUint64` (release) после записи данных.

## Теория

Современные процессоры (Out-of-Order Execution) и оптимизирующие компиляторы имеют право **переупорядочивать независимые операции чтения и записи** в памяти для ускорения работы конвейера.

Если в алгоритме SPSC продюсер напишет обычный код:
```go
data[head] = value // Запись данных (Write 1)
head = head + 1    // Запись индекса (Write 2)
```
Процессор может задержать сброс `Write 1` в Store Buffer и первым сбросить в шину `Write 2`! Консьюмер увидит обновленный `head`, прочитает слот `data[head]` и получит **мусор или полузаписанные байты** (Data Corruption).

**Семантика Acquire-Release**:
* **Release (Публикация)**: операция `atomic.StoreUint64(&head, next)` создает барьер памяти. Процессор и компилятор гарантируют, что **все предыдущие записи памяти будут зафиксированы ДО операции Release**.
* **Acquire (Получение)**: операция `atomic.LoadUint64(&head)` гарантирует, что **все последующие чтения памяти произойдут ПОСЛЕ операции Acquire**.
* В Go модель памяти строго гарантирует, что операция `Load` видит эффекты всех записей, предшествовавших парному `Store`.

## Решение по шагам

1. Напишите код, демонстрирующий потенциальное состояние гонки при обычных операциях чтения-записи без синхронизации.
2. Продемонстрируйте запуск детектора гонок `go run -race`.
3. Замените обычные переменные на `atomic.Uint64` и объясните соблюдение барьера памяти.
4. Продемонстрируйте вызов `runtime.Gosched()` для предотвращения голодания потоков.
5. Сформулируйте правила Go Memory Model для многопоточного взаимодействия.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type Payload struct {
	A int64
	B int64
}

type SafeChannel struct {
	ready atomic.Bool
	data  Payload
}

func (c *SafeChannel) Send(val Payload) {
	// 1. Записываем полезные данные в память
	c.data = val
	// 2. Release: гарантируем, что запись data завершена до установки ready!
	c.ready.Store(true)
}

func (c *SafeChannel) Receive() (Payload, bool) {
	// 1. Acquire: читаем флаг готовности
	if !c.ready.Load() {
		return Payload{}, false
	}
	// 2. Гарантированно читаем корректные опубликованные данные
	return c.data, true
}

func main() {
	ch := &SafeChannel{}
	var wg sync.WaitGroup
	wg.Add(2)

	// Продюсер
	go func() {
		defer wg.Done()
		time.Sleep(10 * time.Millisecond)
		ch.Send(Payload{A: 100, B: 200})
	}()

	// Консьюмер
	go func() {
		defer wg.Done()
		for {
			data, ok := ch.Receive()
			if ok {
				if data.A != 100 || data.B != 200 {
					panic(fmt.Sprintf("MEMORY REORDERING BUG: data=%+v", data))
				}
				fmt.Printf("Получены корректные данные: A=%d, B=%d\n", data.A, data.B)
				return
			}
			runtime.Gosched()
		}
	}()

	wg.Wait()
	fmt.Println("Тест корректности Memory Ordering успешно пройден!")
}
```

ℹ️ Пакет sync/atomic в Go гарантирует строгую семантику публикации данных (Acquire-Release).

## Под капотом

Архитектура памяти x86 (TSO — Total Store Order) аппаратным образом гарантирует порядок Store-Store и Load-Load, но разрешает переупорядочивание Store-Load (чтения могут обогнать запись через Store Buffer). Архитектуры ARM64 и POWER имеют слабую модель памяти (Weak Memory Ordering), где переупорядочиваться могут любые независимые обращения. В Go все операции пакета `sync/atomic` компилируются в барьеры `DMB ISH` (на ARM64) или с префиксом `LOCK` (на x86), навязывая строгий порядок памяти независимо от процессора.

## Подводные камни

1. Использование неатомарных флагов `var ready bool`: компилятор Go имеет право заинлайнить проверку `for !ready` в бесконечный цикл `if !ready { for {} }`, вынеся чтение за пределы цикла!
2. Игнорирование Go Memory Model: предположение, что «на моем процессоре Intel x86 это работает и без атомиков» приводит к неуловимым сбоям при деплое на серверы ARM (AWS Graviton, Ampere Altra).

## На собеседовании

Вопрос на Senior/Staff: «Какова модель памяти Go в отношении sync/atomic? Предоставляет ли Go Relaxed или Consume атомики, как C++20?». Ответ: дизайнеры Go сознательно отказались от сложных моделей упорядочивания памяти (Relaxed / Acquire / Release / Sequentially Consistent). В Go все атомарные операции гарантируют строгую последовательную консистентность (Sequential Consistency) либо строгий Acquire-Release, чтобы защитить разработчиков от фатальных ошибок микроархитектуры.
