# Неблокирующий стек Трайбера (Treiber Stack) на CAS

## Условие

Спроектируйте каноничный неблокирующий стек Трайбера (Treiber Stack) на основе односвязного списка и атомарного CAS. Реализуйте конкурентные операции Push и Pop и проверьте корректность работы детектора гонок (go test -race).

### Исходная формулировка

**Lock-Free стек (Treiber stack).**: Реализуйте неблокирующий стек на основе односвязного списка с `atomic.Pointer` или `atomic.Value` (используя unsafe.Pointer). Поддержите операции `Push` и `Pop`. Проверьте корректность в конкурентном тесте с `-race`.

## Теория

**Стек Трайбера (Treiber Stack)**, предложенный Р. Кентом Трайбером в 1986 году — классический пример Lock-Free структуры данных с семантикой LIFO:
* Узлы стека представляют собой односвязный список: `type Node struct { val T; next *Node }`.
* Единственной точкой синхронизации является указатель на вершину стека `head`.

**Алгоритм Push(val)**:
1. Создается новый узел `newNode := &Node{val: val}`.
2. В цикле читается текущая вершина: `oldHead := atomic.LoadPointer(&head)`.
3. Ссылка нового узла направляется на текущую вершину: `newNode.next = (*Node)(oldHead)`.
4. Выполняется атомарный CAS: `CompareAndSwapPointer(&head, oldHead, unsafe.Pointer(newNode))`.
5. Если CAS успешен — операция завершена. Если вершина изменилась конкурентным потоком — шаг 2 повторяется.

**Алгоритм Pop()**:
1. В цикле читается `oldHead`. Если `oldHead == nil`, стек пуст.
2. Читается следующий узел `next := oldHead.next`.
3. Выполняется `CompareAndSwapPointer(&head, oldHead, unsafe.Pointer(next))`.
4. При успехе возвращается `oldHead.val`, иначе цикл повторяется.

## Решение по шагам

1. Создайте структуру `Node` со значением и ссылкой `next *Node`.
2. Создайте структуру `TreiberStack` с полем `head unsafe.Pointer`.
3. Реализуйте метод `Push(val int)` с CAS-циклом.
4. Реализуйте метод `Pop() (int, bool)` с проверкой пустоты и CAS-циклом.
5. Запустите параллельный стресс-тест из 100 горутин, одновременно выполняющих Push и Pop.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

type Node struct {
	value int
	next  *Node
}

type TreiberStack struct {
	head unsafe.Pointer
}

func (s *TreiberStack) Push(val int) {
	newNode := &Node{value: val}
	for {
		oldHead := atomic.LoadPointer(&s.head)
		newNode.next = (*Node)(oldHead)
		if atomic.CompareAndSwapPointer(&s.head, oldHead, unsafe.Pointer(newNode)) {
			return
		}
	}
}

func (s *TreiberStack) Pop() (int, bool) {
	for {
		oldHead := atomic.LoadPointer(&s.head)
		if oldHead == nil {
			return 0, false // Стек пуст
		}
		node := (*Node)(oldHead)
		next := unsafe.Pointer(node.next)
		if atomic.CompareAndSwapPointer(&s.head, oldHead, next) {
			return node.value, true
		}
	}
}

func main() {
	stack := &TreiberStack{}
	const workers = 50
	const itemsPerWorker = 20_000

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	// Параллельное наполнение стека
	for i := 0; i < workers; i++ {
		workerID := i
		go func() {
			defer wg.Done()
			for j := 0; j < itemsPerWorker; j++ {
				stack.Push(workerID*itemsPerWorker + j)
			}
		}()
	}
	wg.Wait()

	// Параллельное извлечение
	var popCount atomic.Int64
	wg.Add(workers)
	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			for {
				_, ok := stack.Pop()
				if !ok {
					// Повторяем проверку при конкурентном опустошении
					if popCount.Load() >= int64(workers*itemsPerWorker) {
						break
					}
					continue
				}
				popCount.Add(1)
			}
		}()
	}
	wg.Wait()

	cost := time.Since(start)
	fmt.Printf("Успешно обработано %d операций Push/Pop за %v\n", popCount.Load(), cost)
}
```

ℹ️ Классический Lock-Free стек Трайбера на базе CAS-указателя вершины head.

## Под капотом

В стеке Трайбера прогресс системы гарантирован (Lock-Free свойство): даже если 99 горутин потерпели неудачу в CAS и ушли на повторный круг, ровно одна горутина обязательно завершила свой `Push` или `Pop`. Однако под экстремальной нагрузкой возникает контеншн вершины `head`, вызывающий частые перезапуски циклов (CAS Contention).

## Подводные камни

1. Проблема ABA: в C++ освобождение узла через `delete` может вернуть тот же адрес новому узлу, разрушая связность. В Go автоматический GC спасает от классического ABA, так как память узла не переиспользуется, пока на нее есть живые ссылки.
2. Нагрузка на аллокатор: операция `Push` на каждый вызов аллоцирует `&Node{}` в куче.

## На собеседовании

Вопрос: «В чем разница между свойствами Lock-Free и Wait-Free?». Ответ: Lock-Free гарантирует, что хотя бы один поток в системе делает прогресс за конечное число шагов (остальные могут крутиться в CAS-циклах). Wait-Free дает более строгую гарантию: каждый поток завершает операцию за фиксированное число шагов независимо от действий других потоков.
