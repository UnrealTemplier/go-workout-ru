# Сравнение атомарного сложения и ручного CAS-инкремента под нагрузкой

## Условие

Реализуйте инкремент счетчика двумя способами: через прямой atomic.AddInt64 и через ручной цикл atomic.CompareAndSwapInt64. Сравните их производительность под высокой конкурентной нагрузкой и с sync.Mutex.

### Исходная формулировка

**Атомарный счётчик и CAS (Compare-And-Swap).**: Реализуйте потокобезопасный инкремент счётчика с использованием `atomic.AddInt64`. Сравните производительность с `sync.Mutex` под высокой конкурентной нагрузкой.

## Теория

Существует два принципиально разных способа атомарного изменения переменной:

1. **Прямой атомик (`atomic.AddInt64`)**:
   * Компилируется в единую инструкцию процессора `LOCK XADDQ`.
   * Аппаратно неделима: сложение выполняется контроллером кэша за 1 обращение.
   * **Wait-Free**: никогда не перезапускается и всегда завершается за фиксированное время.

2. **Ручной CAS-цикл (`CompareAndSwapInt64`)**:
   * Выполняет чтение, сложение в регистре и `LOCK CMPXCHGQ`.
   * Если между чтением и записью другое ядро изменило переменную, операция **откатывается**, и цикл повторяется.
   * Под высокой нагрузкой (32 параллельных потока) процент неудачных CAS может превышать 90%, вызывая резкую деградацию скорости по сравнению с `atomic.Add`!

## Решение по шагам

1. Реализуйте функцию инкремента через `atomic.AddInt64`.
2. Реализуйте функцию инкремента через CAS-цикл.
3. Реализуйте инкремент через `sync.Mutex`.
4. Запустите 16 горутин, выполняющих по 1 000 000 инкрементов каждым способом.
5. Сравните пропускную способность и задержку (ns/op).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

func benchmarkAdd(workers, iters int) time.Duration {
	var val int64
	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				atomic.AddInt64(&val, 1)
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func benchmarkCAS(workers, iters int) time.Duration {
	var val int64
	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				for {
					old := atomic.LoadInt64(&val)
					if atomic.CompareAndSwapInt64(&val, old, old+1) {
						break
					}
				}
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func benchmarkMutex(workers, iters int) time.Duration {
	var val int64
	var mu sync.Mutex
	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				mu.Lock()
				val++
				mu.Unlock()
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	const workers = 16
	const iters = 1_000_000
	totalOps := float64(workers * iters)

	fmt.Println("=== Бенчмарк: atomic.Add vs CAS Loop vs sync.Mutex ===")

	tAdd := benchmarkAdd(workers, iters)
	tCAS := benchmarkCAS(workers, iters)
	tMutex := benchmarkMutex(workers, iters)

	fmt.Printf("1. atomic.Add (Hardware XADD): %v (%.2f ns/op)\n",
		tAdd, float64(tAdd.Nanoseconds())/totalOps)
	fmt.Printf("2. CAS Loop   (Optimistic):    %v (%.2f ns/op)\n",
		tCAS, float64(tCAS.Nanoseconds())/totalOps)
	fmt.Printf("3. sync.Mutex (Pessimistic):   %v (%.2f ns/op)\n",
		tMutex, float64(tMutex.Nanoseconds())/totalOps)

	if tAdd < tCAS {
		fmt.Printf("\nВывод: Аппаратный atomic.Add быстрее CAS-цикла в %.2fx раз из-за отсутствия повторных попыток!\n",
			float64(tCAS)/float64(tAdd))
	}
}
```

ℹ️ Аппаратная инструкция XADD выполняет сложение гарантированно без коллизий и перезапусков.

## Под капотом

Инструкция `LOCK XADD` на аппаратном уровне заменяет значение и возвращает старое за один неделимый такт шины кэш-когерентности. При CAS-цикле ядро сначала читает строку, вычисляет сумму, и только затем пытается выполнить `CMPXCHG`. Если за эти 10 тактов другое ядро успело сбросить свой `XADD`, операция проваливается, вызывая холостой перезапуск.

## Подводные камни

1. Использование CAS-цикла для простых арифметических операций: `atomic.Add` всегда быстрее и не подвержен коллизиям.
2. CAS-цикл незаменим только тогда, когда новое значение вычисляется по нелинейной логике (умножение, битовые маски, максимумы, условия границ).

## На собеседовании

Вопрос: «Почему CAS-цикл деградирует быстрее, чем atomic.Add при увеличении числа параллельных потоков?». Ответ: из-за вероятности конфликта. При \(N\) потоках вероятность успешного первого завершения CAS падает как \(1/N\), приводя к лавине повторных итераций (CAS Contention), тогда как `LOCK XADD` выстраивается контроллером шины в строгую аппаратную очередь FIFO.
