# Блокировка последовательностей (Sequence Lock / SeqLock)

## Условие

Реализуйте структуру SeqLock (Sequence Lock) с монотонным версионным счетчиком sequence uint64. Обеспечьте сверхбыстрое чтение разделяемой конфигурации без блокировок и проверку консистентности по четности/нечетности версии.

### Исходная формулировка

**Sequence Lock (SeqLock).**: Реализуйте структуру с `sequence uint64` (чётная = чтение без изменений, нечётная = write in progress). Reader: `seq = atomic.LoadUint64(&seq); if seq%2==1 retry; read data; if seq != atomic.LoadUint64(&seq) retry`. Writer: `atomic.AddUint64(&seq, 1); write data; atomic.AddUint64(&seq, 1)`. Объясните, почему это эффективно для read-heavy данных (например, конфигурация).

## Теория

В системах с преобладанием чтения (Read-Heavy, отношение чтений к записям 10 000 к 1) стандартный `sync.RWMutex` создает заметный оверхед:
* Каждый читатель при вызове `RLock()` модифицирует общий атомарный счетчик `readerCount`.
* На 32 ядрах тысячи читателей блокируют друг друга по шине кэша (Cache Contention на мьютексе), даже не выполняя никаких записей!

**Sequence Lock (SeqLock)** — решение из ядра Linux:
* Содержит целочисленный счетчик `seq uint64`:
  * **Четное число** (0, 2, 4...) — данные консистентны, активных писателей нет.
  * **Нечетное число** (1, 3, 5...) — писатель прямо сейчас модифицирует данные.

**Протокол чтения (Zero Lock / Lock-Free Readers)**:
1. Читатель считывает `seq1`. Если он нечетный — ждет.
2. Копирует полезные данные.
3. Считывает `seq2`. Если `seq1 != seq2` (писатель изменил данные во время чтения) — отбрасывает прочитанное и повторяет попытку.
Читатели **вообще ничего не пишут в память**, не создают contention и читают со скоростью L1-кэша!

## Решение по шагам

1. Создайте структуру `SeqLock` с полем `seq atomic.Uint64` и мьютексом для координации писателей.
2. Создайте защищаемую структуру `Config { TimeoutMs int64; MaxConns int64; Host string }`.
3. Реализуйте метод `Write(cfg Config)`: инкремент `seq` до нечетного, запись, инкремент `seq` до четного.
4. Реализуйте метод `Read() Config` с циклом проверки версий.
5. Замерьте задержку чтения при 16 параллельных читателях.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type ConfigData struct {
	TimeoutMs int64
	MaxConns  int64
	RateLimit int64
}

type SeqLock struct {
	seq atomic.Uint64
	mu  sync.Mutex // Сериализует редких писателей
}

type SafeConfig struct {
	lock SeqLock
	data ConfigData
}

func (sc *SafeConfig) Read() ConfigData {
	for {
		seq1 := sc.lock.seq.Load()
		if seq1%2 != 0 {
			// Писатель в процессе обновления: уступаем квант времени
			runtime.Gosched()
			continue
		}

		// Копируем данные локально
		val := sc.data

		seq2 := sc.lock.seq.Load()
		if seq1 == seq2 {
			// Данные не были изменены во время чтения: они 100% консистентны!
			return val
		}
		// Коллизия: повторяем чтение
		runtime.Gosched()
	}
}

func (sc *SafeConfig) Write(update ConfigData) {
	sc.lock.mu.Lock()
	defer sc.lock.mu.Unlock()

	// 1. Делаем seq нечетным (маркер: идет запись)
	sc.lock.seq.Add(1)

	// 2. Модифицируем данные
	sc.lock.data = update

	// 3. Делаем seq четным (маркер: запись завершена)
	sc.lock.seq.Add(1)
}

func main() {
	cfg := &SafeConfig{
		data: ConfigData{TimeoutMs: 100, MaxConns: 500, RateLimit: 1000},
	}

	const readers = 16
	const readsPerWorker = 200_000

	var wg sync.WaitGroup
	wg.Add(readers + 1)
	start := time.Now()

	// 1 писатель периодически обновляет конфиг
	go func() {
		defer wg.Done()
		for i := int64(1); i <= 100; i++ {
			time.Sleep(200 * time.Microsecond)
			cfg.Write(ConfigData{
				TimeoutMs: 100 + i,
				MaxConns:  500 + i*10,
				RateLimit: 1000 + i*50,
			})
		}
	}()

	// 16 читателей непрерывно читают конфиг без блокировок
	for r := 0; r < readers; r++ {
		go func() {
			defer wg.Done()
			for i := 0; i < readsPerWorker; i++ {
				c := cfg.Read()
				_ = c
			}
		}()
	}

	wg.Wait()
	cost := time.Since(start)
	totalReads := readers * readsPerWorker

	finalCfg := cfg.Read()
	fmt.Printf("SeqLock: выполнено %d чтений за %v (%.2f млн чтений/sec)\n",
		totalReads, cost, float64(totalReads)/cost.Seconds()/1e6)
	fmt.Printf("Итоговый конфиг: %+v\n", finalCfg)
}
```

ℹ️ SeqLock позволяет тысячам горутин читать составные данные без блокировок и конкуренции за память.

## Под капотом

В SeqLock читатели выполняют только `atomic.LoadUint64`. Это инструкция `MOVQ`, которая читает строку кэша в состоянии Shared. Никакие инвалидации кэша между читателями не происходят! Читатели масштабируются со 100% линейной эффективностью на любое число ядер процессора.

## Подводные камни

1. SeqLock нельзя использовать для данных, содержащих указатели (`*T`, строки, срезы): если читатель прочитает полузаписанный указатель и перейдет по нему до проверки `seq2`, произойдет `SIGSEGV` (паника разыменования). SeqLock применяется только для примитивных структур чисел и флагов.
2. Риск голодания читателей (Starvation) при непрерывном потоке записей.

## На собеседовании

Вопрос: «Как в ядре Linux реализован доступ к системным часам (jiffies/xtime) без блокировок?». Ответ: через SeqLock (seqlock_t). Таймерный прерывающий поток инкрементирует счетчик и обновляет время, а системные вызовы gettimeofday читают время в цикле проверки четности последовательности.
