# Типизированный atomic.Pointer[T] в Go 1.19+ и защита от проблемы ABA

## Условие

Реализуйте обобщенный lock-free стек Трайбера с использованием atomic.Pointer[Node[T]]. Разберите природу проблемы ABA в lock-free алгоритмах и объясните, почему сборщик мусора Go (Garbage Collector) естественным образом предотвращает классическую проблему ABA.

### Исходная формулировка

**Atomic.Pointer (Go 1.19+).**: Реализуйте lock-free стек (Treiber Stack): `Push` через `atomic.CompareAndSwapPointer` на `head`, `Pop` — аналогично. Покажите, что это работает без mutex. Объясните ABA problem в общем случае и почему в вашем тесте его нет (GC не освобождает память немедленно).

## Теория

До Go 1.19 реализация lock-free структур требовала приведения типов через `unsafe.Pointer`:
```go
atomic.CompareAndSwapPointer((*unsafe.Pointer)(&head), oldPtr, newPtr)
```
Тип **atomic.Pointer[T]** (Go 1.19+) обеспечивает полную типобезопасность без использования пакета `unsafe`.

**Что такое проблема ABA?**
1. Поток 1 читает вершину стека `A` и собирается заменить ее на `A.next` (узел `B`).
2. Поток 1 вытесняется планировщиком.
3. Поток 2 извлекает `A`, затем извлекает `B`. Память узла `A` освобождается.
4. Поток 2 создает НОВЫЙ узел, и аллокатор памяти (malloc) выделяет ему **тот же самый адрес памяти**, что был у `A`! Новый узел помещается на вершину стека.
5. Поток 1 просыпается и выполняет `CAS(&head, A, B)`.
6. Адрес вершины совпадает с `A`! CAS успешно завершается, но стек оказывается сломан, так как узел `B` уже был удален или переиспользован!

**Почему в Go классическая проблема ABA отсутствует для памяти?**
В Go работает автоматический сборщик мусора с отслеживанием ссылок. Пока Поток 1 держит локальную ссылку на узел `A`, этот узел **никогда не будет освобожден и переаллоцирован** под другой объект!

## Решение по шагам

1. Объявите обобщенную структуру `Node[T] { value T; next *Node[T] }`.
2. Создайте структуру `GenericStack[T]` с полем `head atomic.Pointer[Node[T]]`.
3. Реализуйте метод `Push(val T)` с использованием `head.CompareAndSwap`.
4. Реализуйте метод `Pop() (T, bool)`.
5. Продемонстрируйте работу со строковыми и структурными типами.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type Node[T any] struct {
	value T
	next  *Node[T]
}

type GenericTreiberStack[T any] struct {
	head atomic.Pointer[Node[T]]
}

func (s *GenericTreiberStack[T]) Push(val T) {
	newNode := &Node[T]{value: val}
	for {
		oldHead := s.head.Load()
		newNode.next = oldHead
		if s.head.CompareAndSwap(oldHead, newNode) {
			return
		}
	}
}

func (s *GenericTreiberStack[T]) Pop() (T, bool) {
	for {
		oldHead := s.head.Load()
		if oldHead == nil {
			var zero T
			return zero, false
		}
		next := oldHead.next
		if s.head.CompareAndSwap(oldHead, next) {
			return oldHead.value, true
		}
	}
}

func main() {
	stack := &GenericTreiberStack[string]{}
	const workers = 20
	const msgsPerWorker = 1000

	var wg sync.WaitGroup
	wg.Add(workers)

	for i := 0; i < workers; i++ {
		workerID := i
		go func() {
			defer wg.Done()
			for j := 0; j < msgsPerWorker; j++ {
				stack.Push(fmt.Sprintf("msg_%d_%d", workerID, j))
			}
		}()
	}
	wg.Wait()

	// Извлечение
	extracted := 0
	for {
		_, ok := stack.Pop()
		if !ok {
			break
		}
		extracted++
	}

	fmt.Printf("Успешно извлечено %d сообщений из обобщенного GenericTreiberStack!\n", extracted)
}
```

ℹ️ atomic.Pointer[T] гарантирует типобезопасность обобщенных lock-free коллекций без unsafe.Pointer.

## Под капотом

Компилятор Go генерирует для `atomic.Pointer[T].CompareAndSwap` ассемблерный вызов `runtime/internal/atomic.CasPointer`, который на платформах x86 транслируется в `LOCK CMPXCHGQ`. При этом благодаря Tri-color Mark GC любой узел, адрес которого сохранен в локальной переменной горутины, остается достижимым объектом (Marked Black/Grey), полностью предотвращая повторное выделение того же адреса аллокатором кучи.

## Подводные камни

1. Семантический ABA (Logical ABA): если структура хранит логическое состояние или индекс, значение может измениться с 1 на 2, а затем снова на 1. В таких случаях требуется дополнительный монотонный счетчик версий (Tagged Pointer).
2. Забытая очистка указателей при Pop.

## На собеседовании

Вопрос на интервью: «Существует ли проблема ABA в Go?». Ответ: в классическом понимании C/C++ (переиспользование адреса освобожденной памяти под новый узел) проблема ABA в Go невозможна благодаря Garbage Collector. Однако логическая проблема ABA (когда переменная меняет состояние \(A \to B \to A\)) по-прежнему актуальна для примитивных чисел или индексов кольцевых буферов.
