# Горячий кэш конфигурации с atomic.Value (Copy-On-Write)

## Условие

Спроектируйте архитектуру динамической конфигурации приложения на основе atomic.Value с паттерном Copy-On-Write (COW). Продемонстрируйте, как этот подход обеспечивает миллионы чтений конфигурации в секунду с нулевыми блокировками и безопасное атомарное обновление структуры в фоне.

### Исходная формулировка

**Atomic.Value для горячего кэша.**: Используйте `atomic.Value` для хранения конфигурации, которая обновляется раз в минуту, но читается миллионы раз в секунду. Измерьте overhead по сравнению с мьютексом.

## Теория

В высоконагруженных сервисах конфигурация (Feature Flags, Rate Limits, параметры подключения) читается при обработке **каждого входящего HTTP/gRPC запроса** (миллионы раз в секунду). При этом обновляется она крайне редко (например, раз в минуту из etcd или consul).

Использование `sync.RWMutex`:
* Читатели конкурируют за строку кэша мьютекса при `RLock()`.
* Обновление конфигурации через `Lock()` блокирует ВСЕ входящие запросы.

**Паттерн Copy-On-Write (COW) на atomic.Value**:
1. Конфигурация представлена иммутабельной структурой `type Config struct { ... }`.
2. Текущая активная конфигурация хранится в `atomic.Value`:
   ```go
   var currentConfig atomic.Value
   currentConfig.Store(&Config{...})
   ```
3. **Чтение (Millions RPS)**:
   ```go
   cfg := currentConfig.Load().(*Config)
   // Прямой доступ к полям cfg.Timeout без мьютексов!
   ```
4. **Обновление**: фоновая горутина создает **новую копию** структуры, наполняет ее свежими данными и атомарно подменяет указатель через `currentConfig.Store(newCfg)`.
Старые читатели спокойно дочитывают предыдущую версию структуры, после чего она безопасно утилизируется сборщиком мусора.

## Решение по шагам

1. Объявите структуру `AppConfig` с полями параметров сервиса.
2. Инициализируйте `atomic.Value` начальной конфигурацией.
3. Реализуйте функцию чтения `GetConfig() *AppConfig`.
4. Реализуйте функцию обновления `UpdateConfig(newCfg *AppConfig)`.
5. Запустите 16 читателей и фонового писателя, измерьте RPS и задержку.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type AppConfig struct {
	ServiceName string
	RateLimit   int
	FeatureX    bool
	Endpoints   []string
}

type ConfigManager struct {
	val atomic.Value
}

func NewConfigManager(initial AppConfig) *ConfigManager {
	cm := &ConfigManager{}
	cm.val.Store(&initial)
	return cm
}

func (cm *ConfigManager) Get() *AppConfig {
	return cm.val.Load().(*AppConfig)
}

func (cm *ConfigManager) Update(newCfg AppConfig) {
	// Атомарная замена указателя на новую неизменяемую структуру
	cm.val.Store(&newCfg)
}

func main() {
	cm := NewConfigManager(AppConfig{
		ServiceName: "checkout_service",
		RateLimit:   1000,
		FeatureX:    false,
		Endpoints:   []string{"http://node1:8080"},
	})

	const readers = 16
	const itersPerReader = 500_000

	var wg sync.WaitGroup
	wg.Add(readers + 1)
	start := time.Now()

	// Фоновый писатель обновляет конфигурацию на лету
	go func() {
		defer wg.Done()
		for i := 0; i < 5; i++ {
			time.Sleep(10 * time.Millisecond)
			cm.Update(AppConfig{
				ServiceName: "checkout_service",
				RateLimit:   2000 + i*100,
				FeatureX:    i%2 == 0,
				Endpoints:   []string{fmt.Sprintf("http://node%d:8080", i+1)},
			})
		}
	}()

	// Параллельные читатели читают конфигурацию с 0 блокировок
	for r := 0; r < readers; r++ {
		go func() {
			defer wg.Done()
			for i := 0; i < itersPerReader; i++ {
				cfg := cm.Get()
				_ = cfg.RateLimit
				_ = cfg.FeatureX
			}
		}()
	}

	wg.Wait()
	cost := time.Since(start)
	totalReads := readers * itersPerReader

	fmt.Printf("Обработано %d чтений конфигурации за %v (%.2f млн чтений/sec)\n",
		totalReads, cost, float64(totalReads)/cost.Seconds()/1e6)
	fmt.Printf("Финальная конфигурация: %+v\n", cm.Get())
}
```

ℹ️ atomic.Value обеспечивает Zero-Lock доступ к динамической конфигурации через Copy-On-Write.

## Под капотом

Внутри `atomic.Value` хранятся два указателя: `typ unsafe.Pointer` (информация о динамическом типе) и `data unsafe.Pointer`. При вызове `Load()` процессор выполняет ассемблерные инструкции `MOVQ` для чтения типа и данных. Если тип совпадает, чтение завершается за пару тактов. Так как структура неизменяема (Immutable), чтение ее полей абсолютно потокобезопасно.

## Подводные камни

1. Мутация данных после вызова Store: если после `cm.Update(cfg)` другой код изменит поля исходной структуры (например, `cfg.Endpoints[0] = ...`), возникнет Data Race. Структуры в COW обязаны быть строго неизменяемыми.
2. Сохранение разных типов данных: вызов `atomic.Value.Store` со значением другого типа приведет к панике `panic: sync/atomic: store of inconsistently typed value into Value`.

## На собеседовании

Вопрос: «Как реализовать Zero-Downtime перезагрузку конфигурации или правил маршрутизации в Ingress-контроллере (Envoy/Traefik на Go)?». Ответ: паттерн Copy-On-Write с хранением корневой таблицы маршрутов в `atomic.Value` (или `atomic.Pointer`). Запросы читают текущий снапшот без блокировок, а фоновый воркер формирует новое дерево и выполняет атомарный swap.
