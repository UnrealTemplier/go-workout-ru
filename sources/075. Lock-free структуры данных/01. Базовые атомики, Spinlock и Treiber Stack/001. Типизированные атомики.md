# Типизированные атомики: использование atomic.Int64 в Go 1.19+

## Условие

Используйте типизированную структуру atomic.Int64, представленную в Go 1.19+. Спроектируйте высоконагруженный счетчик метрик, безопасно инкрементируемый 1000 параллельными горутинами без мьютексов. Покажите преимущества типизированных оберток над сырыми функциями atomic.AddInt64.

### Исходная формулировка

**[atomic.Int64]**: Используй новые типы-обертки (Go 1.19+) `atomic.Int64`. Создайте счетчик, инкрементируемый 1000 горутинами без мьютексов.

## Теория

До версии Go 1.19 работа с атомиками требовала вызова низкоуровневых функций пакета `sync/atomic`:
```go
var counter int64
atomic.AddInt64(&counter, 1)
val := atomic.LoadInt64(&counter)
```
Этот подход имел три фундаментальных недостатка:
1. **Отсутствие инкапсуляции**: программист мог случайно обратиться к `counter` напрямую (`counter++` или `val = counter`), что порождало Data Race, не отслеживаемый компилятором.
2. **Паника невыравнивания на 32-битных системах**: на архитектурах ARM32/x86-32 сырой `int64` по 4-байтному смещению вызывал фатальную ошибку `panic: unaligned 64-bit atomic operation`.
3. **Засорение сигнатур**: передача `*int64` по указателю размывала семантику владения.

Начиная с Go 1.19, стандартная библиотека предоставляет типизированные типы-обертки: `atomic.Int64`, `atomic.Uint64`, `atomic.Bool`, `atomic.Pointer[T]`.
Внутреннее устройство:
```go
type Int64 struct {
    _ noCopy
    _ align64
    v int64
}
```
Поле `_ align64` гарантирует 8-байтное выравнивание структуры даже на 32-битных платформах, а `_ noCopy` предотвращает ошибочное копирование объекта по значению через предупреждение линтера `go vet`.

## Решение по шагам

1. Объявите структуру `MetricsRegistry` с полем `requests atomic.Int64`.
2. Запустите 1000 параллельных горутин с помощью `sync.WaitGroup`.
3. В каждой горутине выполните по 10 000 атомарных инкрементов методом `requests.Add(1)`.
4. Дождитесь завершения всех воркеров и прочитайте значение методом `requests.Load()`.
5. Убедитесь в полном совпадении результата с ожидаемым числом (\(1000 \times 10\,000 = 10\,000\,000\)).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type ServiceMetrics struct {
	totalRequests atomic.Int64
	activeWorkers atomic.Int64
}

func (m *ServiceMetrics) RecordRequest() {
	m.totalRequests.Add(1)
}

func (m *ServiceMetrics) Snapshot() (int64, int64) {
	return m.totalRequests.Load(), m.activeWorkers.Load()
}

func main() {
	metrics := &ServiceMetrics{}
	const goroutines = 1000
	const requestsPerWorker = 10_000

	var wg sync.WaitGroup
	wg.Add(goroutines)

	start := time.Now()
	for i := 0; i < goroutines; i++ {
		go func() {
			defer wg.Done()
			metrics.activeWorkers.Add(1)
			defer metrics.activeWorkers.Add(-1)

			for j := 0; j < requestsPerWorker; j++ {
				metrics.RecordRequest()
			}
		}()
	}

	wg.Wait()
	duration := time.Since(start)

	total, active := metrics.Snapshot()
	expected := int64(goroutines * requestsPerWorker)

	fmt.Printf("Всего запросов:  %d (ожидалось %d)\n", total, expected)
	fmt.Printf("Активных воркеров: %d\n", active)
	fmt.Printf("Время обработки: %v (%.2f млн ops/sec)\n",
		duration, float64(total)/duration.Seconds()/1e6)
}
```

ℹ️ atomic.Int64 гарантирует строгую инкапсуляцию и автоматическое 8-байтное выравнивание.

## Под капотом

На уровне ассемблера вызов `metrics.totalRequests.Add(1)` компилируется на архитектуре x86_64 в инструкцию `LOCK XADDQ %rax, (%rbx)`. Префикс `LOCK` заставляет процессор активировать протокол когерентности кэша (Cache Locking): строка кэша, содержащая `v`, переводится в эксклюзивное состояние (Exclusive/Modified), гарантируя неделимость чтения, модификации и записи значения на аппаратном уровне.

## Подводные камни

1. Ошибочное копирование структуры: передача структуры, содержащей `atomic.Int64`, по значению скопирует текущее числовое значение, разорвав атомарную связь (`go vet` выдает ошибку `passes lock by value`).
2. Составные условия: проверка `if metrics.Load() > 0 { metrics.Add(-1) }` не является атомарной. Для составных операций необходимо использовать CAS-цикл `CompareAndSwap`.

## На собеседовании

Вопрос: «Почему в Go 1.19 добавили типы atomic.Int64/atomic.Pointer, если уже были функции atomic.AddInt64/StorePointer?». Ответ: для защиты от Alignment Faults на 32-битных ARM/MIPS платформах, статического запрета копирования через `noCopy` линтер и избавления от небезопасного приведения типов через `unsafe.Pointer` при работе с указателями.
