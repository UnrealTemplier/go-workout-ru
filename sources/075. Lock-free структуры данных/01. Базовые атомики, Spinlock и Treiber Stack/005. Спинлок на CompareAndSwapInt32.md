# Спинлок на CompareAndSwapInt32: uncontended vs contended бенчмарк

## Условие

Реализуйте Spinlock на CompareAndSwapInt32. Проведите профилирование в сценариях без конкуренции (1 поток) и с экстремальной конкуренцией (32 параллельных потока) в сравнении с sync.Mutex.

### Исходная формулировка

**[Spinlock]**: Реализуй свой `Spinlock` на основе `atomic.CompareAndSwapInt32`. Напиши бенчмарк, сравнивающий твой Spinlock с `sync.Mutex` в сценарии без конкуренции (uncontended) и с высокой конкуренцией.

## Теория

Производительность механизмов синхронизации кардинально меняется в зависимости от уровня конкуренции (Contention Level):

1. **Сценарий Uncontended (1 горутина, нет конкуренции)**:
   * `Spinlock`: выполняет ровно одну инструкцию `LOCK CMPXCHGL`. Это занимает ~5–8 нс.
   * `sync.Mutex`: проверяет состояние и устанавливает флаг захвата. Занимает ~8–10 нс.
   * На одном ядре спинлок показывает сопоставимую или чуть лучшую скорость.

2. **Сценарий High Contention (32 горутины на 8 ядрах)**:
   * `sync.Mutex`: после короткого спина переводит конкурирующие горутины в спящий режим (`gopark`), освобождая ядра процессора для выполнения полезной работы.
   * `Spinlock`: все 32 горутины непрерывно долбят память инструкциями CAS, вызывая шторм когерентных сообщений по шине процессора. Производительность спинлока падает в 10–50 раз по сравнению с `sync.Mutex`!

## Решение по шагам

1. Реализуйте спинлок `Int32Spinlock` на основе `int32`.
2. Напишите тестовые функции для одного потока (uncontended) и 32 потоков (contended).
3. Сравните `Int32Spinlock` и `sync.Mutex` в обоих режимах.
4. Выведите задержку операций в наносекундах.
5. Проанализируйте график падения производительности спинлока.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type Int32Spinlock struct {
	state int32
}

func (s *Int32Spinlock) Lock() {
	for !atomic.CompareAndSwapInt32(&s.state, 0, 1) {
		runtime.Gosched()
	}
}

func (s *Int32Spinlock) Unlock() {
	atomic.StoreInt32(&s.state, 0)
}

func runBenchmark(name string, workers int, iters int, useMutex bool) time.Duration {
	var mu sync.Mutex
	var spin Int32Spinlock
	var counter int

	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				if useMutex {
					mu.Lock()
					counter++
					mu.Unlock()
				} else {
					spin.Lock()
					counter++
					spin.Unlock()
				}
			}
		}()
	}
	wg.Wait()
	cost := time.Since(start)
	_ = counter
	return cost
}

func main() {
	fmt.Println("=== Исследование Spinlock vs sync.Mutex ===")

	// 1. Uncontended (1 воркер)
	const itersSingle = 5_000_000
	tSpinSingle := runBenchmark("Spin Uncontended", 1, itersSingle, false)
	tMutexSingle := runBenchmark("Mutex Uncontended", 1, itersSingle, true)

	fmt.Printf("Uncontended (1 воркер):\n")
	fmt.Printf("  Spinlock:   %v (%.2f ns/op)\n", tSpinSingle, float64(tSpinSingle.Nanoseconds())/itersSingle)
	fmt.Printf("  sync.Mutex: %v (%.2f ns/op)\n", tMutexSingle, float64(tMutexSingle.Nanoseconds())/itersSingle)

	// 2. High Contention (16 воркеров)
	const itersContended = 500_000
	const workers = 16
	totalOps := float64(workers * itersContended)

	tSpinContended := runBenchmark("Spin Contended", workers, itersContended, false)
	tMutexContended := runBenchmark("Mutex Contended", workers, itersContended, true)

	fmt.Printf("\nHigh Contention (16 воркеров):\n")
	fmt.Printf("  Spinlock:   %v (%.2f ns/op)\n", tSpinContended, float64(tSpinContended.Nanoseconds())/totalOps)
	fmt.Printf("  sync.Mutex: %v (%.2f ns/op)\n", tMutexContended, float64(tMutexContended.Nanoseconds())/totalOps)

	if tMutexContended < tSpinContended {
		fmt.Printf("\nВывод: При конкуренции sync.Mutex быстрее Spinlock в %.2fx раз за счет парковки горутин!\n",
			float64(tSpinContended)/float64(tMutexContended))
	}
}
```

ℹ️ Сравнение спинлока и мьютекса при отсутствии конкуренции и при ее пиковых значениях.

## Под капотом

В режиме высокой конкуренции спинлок удерживает ядра процессора загруженными на 100%, сжигая энергопотребление и блокируя шину памяти непрерывными инвалидациями строк кэша. `sync.Mutex` в рантайме Go после небольшого числа неудачных попыток спина переводит горутину в спящий режим (`runtime.goparkunlock`), снимая нагрузку с процессорных ядер.

## Подводные камни

1. Ошибочный вывод на основе одиночных бенчмарков: тестирование спинлока в 1 поток вводит разработчиков в заблуждение, скрывая катастрофическое падение при 16+ потоках.
2. Отсутствие Backoff-паузы при конкуренции.

## На собеседовании

Вопрос: «Когда в пользовательском коде допустимо использовать спинлок вместо sync.Mutex?». Ответ: практически никогда в userspace бизнес-логике. Единственное редкое исключение — специфические сетевые драйверы реального времени (DPDK / io_uring polling) с изолированными pinned-ядрами процессора, где задержка переключения контекста ядра ОС (1-2 мкс) абсолютно неприемлема.
