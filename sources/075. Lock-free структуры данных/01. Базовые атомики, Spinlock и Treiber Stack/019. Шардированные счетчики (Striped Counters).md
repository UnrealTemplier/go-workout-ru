# Шардированные счетчики (Striped Counters) для снятия Cache Contention

## Условие

Реализуйте шардированный счетчик высокой пропускной способности (Striped Counter / LongAdder). Разнесите инкременты по независимым полосам (stripes) с выравниванием по кэш-линиям, обеспечив линейное масштабирование до десятков процессорных ядер. Объясните компромисс: мгновенная скорость записи против eventual-консистентности чтения суммы.

### Исходная формулировка

**Striped Counters.**: Реализуйте `type StripedCounter [64]PaddedCounter` (по числу CPU). `Add` — `stripe[cpuID].Add`, `Sum` — сумма всех stripes. Покажите, что это масштабируется линейно до числа ядер, в отличие от глобального `atomic.Uint64`. Объясните компромисс: точность `Sum` (eventual) vs скорость.

## Теория

Когда 64 ядра процессора одновременно выполняют `atomic.AddUint64(&counter, 1)`, все они пытаются модифицировать одну 64-байтную кэш-линию. Протокол когерентности MESI перегружает шину процессора запросами инвалидации (Cache Bouncing), и производительность резко падает.

Паттерн **Striped Counters (Шардированный счетчик / Java LongAdder)**:
* Вместо одного счетчика создается массив из \(N\) независимых счетчиков (полос / страйпов), где \(N\) кратно числу ядер (`GOMAXPROCS`):
```go
type PaddedStripedCell struct {
    val atomic.Uint64
    _   [56]byte // 64-байтный отступ для исключения False Sharing!
}
type StripedCounter struct {
    stripes [64]PaddedStripedCell
}
```
* **Запись (Write)**: каждый воркер инкрементирует свою полосу по формуле \(StripeIndex = Hash(WorkerID) \pmod N\). Ядра процессора работают в абсолютно изолированных кэш-линиях без взаимных инвалидаций! Скорость масштабируется линейно.
* **Чтение (Read/Sum)**: функция `Sum()` суммирует значения всех 64 полос. Это компромисс: операция чтения суммы становится \(O(N)\) и не является строго атомарным моментальным снимком (Eventual Consistency), но операции записи ускоряются в 10–50 раз.

## Решение по шагам

1. Создайте структуру `PaddedCell` с `atomic.Uint64` и 56 байтами padding.
2. Создайте структуру `StripedCounter` с массивом из 16 или 32 полос.
3. Реализуйте метод `Add(workerID int, delta uint64)`.
4. Реализуйте метод `Sum() uint64`.
5. Сравните пропускную способность записи со стандартным единым `atomic.Uint64` при 16 параллельных горутинах.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

const NumStripes = 16
const StripeMask = NumStripes - 1

type PaddedStripe struct {
	val atomic.Uint64
	_   [56]byte // Защита от False Sharing
}

type StripedCounter struct {
	stripes [NumStripes]PaddedStripe
}

func (c *StripedCounter) Add(workerID int, delta uint64) {
	idx := workerID & StripeMask
	c.stripes[idx].val.Add(delta)
}

func (c *StripedCounter) Sum() uint64 {
	var total uint64
	for i := 0; i < NumStripes; i++ {
		total += c.stripes[i].val.Load()
	}
	return total
}

func main() {
	var stripe PaddedStripe
	fmt.Printf("Размер PaddedStripe: %d байт (ровно 1 кэш-линия)\n\n", unsafe.Sizeof(stripe))

	const workers = 16
	const iters = 5_000_000
	totalOps := float64(workers * iters)

	// 1. Единый глобальный атомик (Cache Contention)
	var globalAtomic atomic.Uint64
	var wg1 sync.WaitGroup
	wg1.Add(workers)
	start1 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg1.Done()
			for i := 0; i < iters; i++ {
				globalAtomic.Add(1)
			}
		}()
	}
	wg1.Wait()
	dGlobal := time.Since(start1)

	// 2. Striped Counter (Изолированные кэш-линии)
	var striped StripedCounter
	var wg2 sync.WaitGroup
	wg2.Add(workers)
	start2 := time.Now()
	for w := 0; w < workers; w++ {
		workerID := w
		go func() {
			defer wg2.Done()
			for i := 0; i < iters; i++ {
				striped.Add(workerID, 1)
			}
		}()
	}
	wg2.Wait()
	dStriped := time.Since(start2)

	fmt.Printf("1. Единый atomic.Uint64: %v (%.2f ns/op)\n",
		dGlobal, float64(dGlobal.Nanoseconds())/totalOps)
	fmt.Printf("2. StripedCounter (16):   %v (%.2f ns/op)\n",
		dStriped, float64(dStriped.Nanoseconds())/totalOps)

	if dStriped < dGlobal {
		fmt.Printf("\nУскорение шардированного счетчика: %.2fx раз!\n",
			float64(dGlobal)/float64(dStriped))
	}
	fmt.Printf("Итоговая сумма: %d\n", striped.Sum())
}
```

ℹ️ Striped Counter устраняет конкуренцию за кэш-линию, распределяя инкременты по независимым полосам.

## Под капотом

Каждая полоса `PaddedStripe` занимает ровно 64 байта и гарантированно изолирована в памяти. Ядро процессора, выполняющее горутину `w`, удерживает строку `stripes[w]` в состоянии Exclusive в своем локальном L1 кэше. Контроллер шины межсоединений не получает никаких запросов инвалидации, обеспечивая максимальную вычислительную плотность процессора.

## Подводные камни

1. Забытый padding: если массив объявлен как `[16]atomic.Uint64`, все 16 счетчиков поместятся всего в две кэш-линии, и шардирование потеряет всякий смысл из-за False Sharing.
2. Неатомарность моментального снимка: во время выполнения `Sum()` параллельные горутины могут успеть изменить некоторые полосы, поэтому результат суммы является eventual-consistent.

## На собеседовании

Вопрос: «Как устроен класс LongAdder в Java 8 и как реализовать его аналог в Go?». Ответ: массив выровненных ячеек `Cell` с padding до размера кэш-линии, привязанных к хешу потока. В Go шардирование реализуется через массив `[GOMAXPROCS]PaddedStripe`, где чтение агрегирует полосы, а запись масштабируется без блокировок шины памяти.
