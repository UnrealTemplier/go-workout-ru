# Спинлоки на CAS (Compare-And-Swap) и опасность в Userspace

## Условие

Реализуйте примитив синхронизации Spinlock на основе CAS-цикла с вызовом runtime.Gosched(). Сравните его с sync.Mutex при сверхкороткой критической секции. Объясните фундаментальные опасности спинлоков в пространстве пользователя (инверсия приоритетов, сжигание CPU, голодание планировщика).

### Исходная формулировка

**Spinlock на CAS.**: Реализуйте `type Spinlock uint32` с методами `Lock()` (`for !atomic.CompareAndSwapUint32(&l, 0, 1) { runtime.Gosched() }`) и `Unlock()`. Сравните с `sync.Mutex` при очень короткой критической секции (1 инкремент). Объясните, почему spinlock опасен в userspace (приоритет inversion, wasted CPU).

## Теория

**Спинлок (Spinlock)** — это механизм взаимного исключения, при котором поток ожидает освобождения ресурса в активном цикле (Busy Waiting / Polling), непрерывно выполняя атомарную операцию CAS (Compare-And-Swap):
```go
type Spinlock uint32

func (sl *Spinlock) Lock() {
    for !atomic.CompareAndSwapUint32((*uint32)(sl), 0, 1) {
        runtime.Gosched() // уступаем квант времени
    }
}
```

Спинлоки идеальны в ядре ОС (Linux Kernel Spinlocks), где они удерживаются на время в несколько тактов ЦПУ с отключенными прерываниями.

**Почему спинлоки опасны в Userspace и Go?**
1. **Сжигание ресурсов CPU**: крутящаяся горутина тратит 100% ядра процессора впустую.
2. **Инверсия приоритетов (Priority Inversion)**: если горутина A захватила спинлок, а планировщик Go вытеснил ее ради горутины B, горутина B будет бесконечно крутиться в цикле, сжигая квант времени процессора, который необходим горутине A для завершения работы!
3. В стандартной библиотеке `sync.Mutex` использует гибридный спинлок: всего несколько циклов `procyield`, после чего принудительно паркует горутину.

## Решение по шагам

1. Создайте тип `Spinlock uint32`.
2. Реализуйте метод `Lock()` с циклом CAS и вызовом `runtime.Gosched()`.
3. Реализуйте метод `Unlock()` через `atomic.StoreUint32`.
4. Напишите тест со сверхкороткой критической секцией (1 инкремент).
5. Продемонстрируйте корректность работы под нагрузкой и с флагом `-race`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type Spinlock uint32

func (sl *Spinlock) Lock() {
	for !atomic.CompareAndSwapUint32((*uint32)(sl), 0, 1) {
		// Уступаем управление шедулеру GMP во избежание дедлока
		runtime.Gosched()
	}
}

func (sl *Spinlock) Unlock() {
	atomic.StoreUint32((*uint32)(sl), 0)
}

func main() {
	var lock Spinlock
	var sharedCounter int
	const workers = 16
	const itersPerWorker = 50_000

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			for j := 0; j < itersPerWorker; j++ {
				lock.Lock()
				sharedCounter++ // сверхкороткая критическая секция
				lock.Unlock()
			}
		}()
	}

	wg.Wait()
	cost := time.Since(start)

	expected := workers * itersPerWorker
	fmt.Printf("Итоговое значение: %d (ожидалось %d)\n", sharedCounter, expected)
	fmt.Printf("Время работы со спинлоком: %v\n", cost)
	fmt.Println("Внимание: Userspace спинлоки опасны инверсией приоритетов и голоданием CPU!")
}
```

ℹ️ Пользовательский спинлок на CAS требует аккуратного вызова runtime.Gosched().

## Под капотом

Инструкция `atomic.CompareAndSwapUint32` компилируется в `LOCK CMPXCHGL`. Если 16 горутин крутятся в цикле, шина когерентности перегружается постоянными RFO-запросами. Для оптимизации таких циклов процессор предоставляет ассемблерную инструкцию `PAUSE` (в Go runtime вызывается через `runtime.procyield(30)`), которая снижает энергопотребление ядра и предотвращает сброс спекулятивного конвейера процессора при выходе из цикла.

## Подводные камни

1. Забытый `runtime.Gosched()`: при кооперативном планировании Go горутина в плотном цикле `for !CAS` может заблокировать системный поток M навсегда, вызвав зависание программы.
2. Использование спинлока для длительных операций (I/O, сетевые запросы): приводит к 100% утилизации CPU и деградации соседних сервисов.

## На собеседовании

Вопрос: «Почему в Go нет официального sync.Spinlock?». Ответ: в многозадачной среде с GMP-планировщиком спинлоки в userspace приводят к тяжелым патологиям шедулинга. Реализация `sync.Mutex` в Go уже включает оптимизированный спин-цикл с ограниченным числом попыток и инструкцией PAUSE, после чего адаптивно переходит в ожидание на системных семафорах.
