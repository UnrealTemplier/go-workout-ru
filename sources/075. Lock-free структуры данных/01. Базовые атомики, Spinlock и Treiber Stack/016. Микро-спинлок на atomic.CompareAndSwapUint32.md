# Микро-спинлок на atomic.CompareAndSwapUint32: оптимизация критической секции

## Условие

Напишите простейший Spinlock на atomic.CompareAndSwapUint32 для защиты сверхкороткой критической секции. Продемонстрируйте технику yield-пауз при активном ожидании для снижения нагрузки на процессор.

### Исходная формулировка

**Спин-блокировка (Spinlock) на атомиках**: Напишите простейший механизм взаимного исключения — Spinlock. Используйте переменную `uint32` в качестве флага блокировки и функции пакета `sync/atomic` (в частности, метод Compare-And-Swap: `atomic.CompareAndSwapUint32`). Воркер должен крутиться в активном цикле (busy wait) до тех пор, пока не захватит блокировку. Сравните производительность Spinlock с обычным `sync.Mutex` в сценариях с экстремально короткими критическими секциями.

## Теория

При проектировании критических секций длиной в 1–2 инструкции процессора (например, инкремент счетчика или сдвиг указателя) вызов `sync.Mutex` несет оверхед на вызов функций и потенциальный переход в рантайм.

Простейший **микро-спинлок**:
```go
type SimpleSpinlock struct {
    flag atomic.Uint32
}
```
Алгоритм захвата:
1. Быстрый путь (**Fast Path**): первая попытка `flag.CompareAndSwap(0, 1)` выполняется сразу. Если лок был свободен — секция захвачена за 5 нс без циклов!
2. Медленный путь (**Slow Path**): если лок занят, выполняется цикл ожидания. Чтобы не пережигать конвейер процессора и не блокировать другие горутины на том же системном потоке M, в цикле вызывается `runtime.Gosched()` или адаптивный счетчик спинов.

## Решение по шагам

1. Создайте структуру `SimpleSpinlock` с полем `flag atomic.Uint32`.
2. Реализуйте метод `Lock()` с разделением на Fast Path и Slow Path.
3. Реализуйте метод `Unlock()` через `flag.Store(0)`.
4. Запустите параллельный тест на 8 воркеров со сверхкороткой секцией.
5. Замерьте задержку одной операции.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type SimpleSpinlock struct {
	flag atomic.Uint32
}

func (s *SimpleSpinlock) Lock() {
	// Fast Path: попытка мгновенного захвата
	if s.flag.CompareAndSwap(0, 1) {
		return
	}
	// Slow Path: активное ожидание
	for {
		// Оптимизация: сначала проверяем чтением без тяжелого CAS (Test-and-Test-and-Set)
		for s.flag.Load() != 0 {
			runtime.Gosched()
		}
		if s.flag.CompareAndSwap(0, 1) {
			return
		}
	}
}

func (s *SimpleSpinlock) Unlock() {
	s.flag.Store(0)
}

func main() {
	var spin SimpleSpinlock
	var sharedVal int64
	const workers = 8
	const iters = 100_000

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				spin.Lock()
				sharedVal++
				spin.Unlock()
			}
		}()
	}
	wg.Wait()
	cost := time.Since(start)

	expected := int64(workers * iters)
	fmt.Printf("SimpleSpinlock: результат = %d (ожидалось %d), время = %v\n",
		sharedVal, expected, cost)
}
```

ℹ️ Паттерн Test-and-Test-and-Set (TTAS) снижает трафик шины памяти в спинлоках.

## Под капотом

В коде используется классический паттерн **TTAS (Test-and-Test-and-Set)**: внутренний цикл `for s.flag.Load() != 0` выполняет только операцию чтения. Чтение удерживает строку кэша в состоянии Shared между всеми ядрами. Если бы поток непрерывно выполнял `CAS`, ядро на каждой итерации требовало бы эксклюзивного владения строкой, полностью парализуя работу процессора.

## Подводные камни

1. Забытый Fast Path: проверка в цикле без предварительного вызова CAS замедляет одиночные обращения.
2. Невозможность обнаружения дедлоков: спинлок не имеет встроенного детектора дедлоков.

## На собеседовании

Вопрос: «Что такое паттерн TTAS (Test-and-Test-and-Set) в lock-free синхронизации?». Ответ: это оптимизация спинлока, при которой поток сначала проверяет доступность блокировки обычной операцией чтения из локального кэша L1, и только когда видит освобождение (flag == 0), пытается выполнить дорогую инструкцию CAS по шине межсоединений.
