# Атомики против Мьютексов: аппаратная механика Lock Prefix

## Условие

Реализуйте сравнительный микро-бенчмарк счетчика на atomic.AddUint64 и sync.Mutex при 1, 2, 4, 8 параллельных горутинах. Докажите превосходство атомиков и объясните, почему атомик — это не полное отсутствие блокировок, а аппаратная блокировка на уровне шины и кэша процессора.

### Исходная формулировка

**Atomic vs Mutex.**: Реализуйте счётчик: `atomic.AddUint64` vs `sync.Mutex` + `counter++`. Бенчмарк с 1, 2, 4, 8 goroutine. Покажите, что atomic масштабируется лучше (нет contention на cache line, только hardware lock prefix). Объясните, почему `atomic` — это не «без блокировок», а «блокировка на уровне шины/кэша».

## Теория

Среди разработчиков распространено заблуждение, что атомарные операции (Lock-Free) выполняются «магически без блокировок».

В реальности:
* **sync.Mutex (Программная блокировка в Userspace + OS)**: если мьютекс занят, горутина сначала крутится в адаптивном спинлоке (до 30 итераций `procyield`), а затем переводит себя в состояние ожидания (`gopark`), передавая управление планировщику GMP. При освобождении вызывается `goready` и системный вызов футекса (`futex` в Linux). Это сопровождается переключением контекста (задержка 1–5 микросекунд).
* **atomic.AddUint64 (Аппаратная блокировка шины/кэша процессора)**: компилируется в инструкцию с префиксом `LOCK` (например, `lock xaddq`). Процессор блокирует не поток ОС, а **строку кэша (Cache Line Lock)** в L1 контроллере ядра. На время исполнения инструкции (10–30 тактов) никакое другое ядро не может изменить эту строку.

Таким образом, атомик — это **микросекундная аппаратная блокировка на уровне транзисторов кремния**, которая в сотни раз быстрее программного планирования потоков.

## Решение по шагам

1. Создайте счетчик на `atomic.Uint64`.
2. Создайте счетчик на `sync.Mutex` с обычным полем `uint64`.
3. Реализуйте функцию замера для \(N\) горутин (\(N \in [1, 2, 4, 8]\)).
4. Замерьте среднее время на операцию инкремента (ns/op) для обоих подходов.
5. Сравните масштабируемость и деградацию при росте конкуренции.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type MutexCounter struct {
	mu  sync.Mutex
	val uint64
}

func (c *MutexCounter) Inc() {
	c.mu.Lock()
	c.val++
	c.mu.Unlock()
}

type AtomicCounter struct {
	val atomic.Uint64
}

func (c *AtomicCounter) Inc() {
	c.val.Add(1)
}

func benchmarkWorkers(workers int, iters int) (time.Duration, time.Duration) {
	// 1. Mutex
	mc := &MutexCounter{}
	var wg1 sync.WaitGroup
	wg1.Add(workers)
	start1 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg1.Done()
			for i := 0; i < iters; i++ {
				mc.Inc()
			}
		}()
	}
	wg1.Wait()
	dMutex := time.Since(start1)

	// 2. Atomic
	ac := &AtomicCounter{}
	var wg2 sync.WaitGroup
	wg2.Add(workers)
	start2 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg2.Done()
			for i := 0; i < iters; i++ {
				ac.Inc()
			}
		}()
	}
	wg2.Wait()
	dAtomic := time.Since(start2)

	return dMutex, dAtomic
}

func main() {
	const itersPerWorker = 2_000_000
	fmt.Println("=== Бенчмарк: Atomic vs sync.Mutex ===")
	fmt.Printf("%-8s | %-15s | %-15s | %-10s\n", "Воркеры", "Mutex (ns/op)", "Atomic (ns/op)", "Ускорение")
	fmt.Println("---------------------------------------------------------")

	for _, w := range []int{1, 2, 4, 8} {
		dM, dA := benchmarkWorkers(w, itersPerWorker)
		totalOps := int64(w * itersPerWorker)
		nsM := float64(dM.Nanoseconds()) / float64(totalOps)
		nsA := float64(dA.Nanoseconds()) / float64(totalOps)
		ratio := nsM / nsA

		fmt.Printf("%-8d | %-15.2f | %-15.2f | %-10.2fx\n", w, nsM, nsA, ratio)
	}
}
```

ℹ️ Атомики превосходят мьютексы за счет аппаратной блокировки кэш-линии без участия планировщика ОС.

## Под капотом

В `sync.Mutex` при отсутствии конкуренции (1 горутина) вызов `Lock()` выполняет ровно один `atomic.CompareAndSwapInt32`. Однако как только появляется вторая горутина, конкуренция заставляет рантайм вызывать `runtime.sync_runtime_SemacquireMutex`, выделять узел ожидания в семафоре и переключать контекст планировщика. `atomic.Add` никогда не паркует горутину: ядро процессора либо выполняет операцию сразу, либо процессорный арбитр шины задерживает конвейер на несколько тактов.

## Подводные камни

1. Иллюзия бесконечной масштабируемости атомиков: при 64+ ядрах, пишущих в один атомарный счетчик, производительность резко падает из-за Cache Line Bouncing (контеншн на шине MESI).
2. Замена сложных критических секций цепочками атомиков: если нужно атомарно обновить два поля, разрозненные атомики приведут к состоянию гонки.

## На собеседовании

Вопрос на Senior собеседовании: «Что физически происходит в процессоре при выполнении инструкции atomic.Add?». Ответ: ядро процессора отправляет запрос RFO (Request For Ownership) в кэш-когерентную сеть, блокирует соответствующую строку кэша в состоянии Modified, запрещая доступ другим ядрам на время чтения-модификации-записи (Lock Prefix), и сбрасывает локальные буферы записи (Store Buffers).
