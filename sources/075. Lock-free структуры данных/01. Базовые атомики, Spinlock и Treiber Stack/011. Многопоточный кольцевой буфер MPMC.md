# Многопоточный кольцевой буфер MPMC (Multi-Producer Multi-Consumer)

## Условие

Реализуйте высокопроизводительный lock-free кольцевой буфер MPMC (Multi-Producer Multi-Consumer) по алгоритму Дмитрия Вьюкова (bounded MPMC queue). Используйте слоты с версионными последовательностями (sequence numbers) и побитовую маску для степени двойки. Объясните, почему MPMC сложнее SPSC из-за конкуренции за head/tail и Cache Line Bouncing.

### Исходная формулировка

**MPMC Ring Buffer.**: Расширьте до Multi-Producer–Multi-Consumer: используйте `CAS` на `head`/`tail`, power-of-2 размер для маски `(tail+1) & mask`. Реализуйте `Enqueue` и `Dequeue` с возвратом `bool` (full/empty). Объясните, почему MPMC сложнее (contention на одном head/tail, cache line bouncing).

## Теория

В отличие от SPSC, где пишущий и читающий потоки никогда не конкурируют за одни и те же переменные, в **MPMC (Multi-Producer Multi-Consumer)**:
* Множество горутин одновременно пытаются захватить позицию добавления (`head`).
* Множество горутин одновременно пытаются захватить позицию извлечения (`tail`).

Наивный подход «просто делать `CAS(&head, cur, cur+1)`» не работает, так как между резервированием индекса и фактической записью данных в ячейку проходит время. Читатель может прочитать слот раньше, чем писатель успеет положить туда данные!

**Алгоритм Вьюкова (Dmitry Vyukov Bounded MPMC Queue)**:
Каждый слот кольцевого буфера снабжается собственным версионным счетчиком `sequence atomic.Uint64`:
```go
type Cell[T any] struct {
    sequence atomic.Uint64
    data     T
}
```
1. Начальное состояние слота \(i\): `sequence = i`.
2. **Enqueue**: продюсер ищет слот, у которого `sequence == pos`. Если условие выполнено, он атомарно продвигает `head` на `pos + 1`. Затем записывает данные и выставляет `sequence = pos + 1` (сигнал готовности для консьюмера).
3. **Dequeue**: консьюмер ищет слот, у которого `sequence == pos + 1`. Забирает данные и выставляет `sequence = pos + Capacity` (сигнал продюсеру на следующий круг).

## Решение по шагам

1. Объявите структуру `MPMCCell[T]` с полем `sequence atomic.Uint64` и полезной нагрузкой `data T`.
2. Объявите структуру `MPMCQueue[T]` с буфером размером \(N = 2^k\), маской и счетчиками `head` и `tail`.
3. Добавьте padding для изоляции `head` и `tail`.
4. Реализуйте метод `Enqueue(val T) bool` и `Dequeue() (T, bool)`.
5. Протестируйте очередь с 16 параллельными продюсерами и 16 консьюмерами.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

const MPMCCapacity = 1024
const MPMCMask = MPMCCapacity - 1

type MPMCCell[T any] struct {
	sequence atomic.Uint64
	data     T
}

type MPMCQueue[T any] struct {
	head   atomic.Uint64
	_      [56]byte
	tail   atomic.Uint64
	_      [56]byte
	buffer [MPMCCapacity]MPMCCell[T]
}

func NewMPMCQueue[T any]() *MPMCQueue[T] {
	q := &MPMCQueue[T]{}
	for i := 0; i < MPMCCapacity; i++ {
		q.buffer[i].sequence.Store(uint64(i))
	}
	return q
}

func (q *MPMCQueue[T]) Enqueue(val T) bool {
	var cell *MPMCCell[T]
	pos := q.head.Load()

	for {
		cell = &q.buffer[pos&MPMCMask]
		seq := cell.sequence.Load()
		diff := int64(seq) - int64(pos)

		if diff == 0 {
			// Слот готов для записи: пытаемся зарезервировать позицию
			if q.head.CompareAndSwap(pos, pos+1) {
				break
			}
			// Другой продюсер опередил: перечитываем pos
			pos = q.head.Load()
		} else if diff < 0 {
			// Буфер полон
			return false
		} else {
			pos = q.head.Load()
		}
	}

	cell.data = val
	// Сигнализируем консьюмерам: данные записаны!
	cell.sequence.Store(pos + 1)
	return true
}

func (q *MPMCQueue[T]) Dequeue() (T, bool) {
	var cell *MPMCCell[T]
	pos := q.tail.Load()

	for {
		cell = &q.buffer[pos&MPMCMask]
		seq := cell.sequence.Load()
		diff := int64(seq) - int64(pos+1)

		if diff == 0 {
			// Данные готовы для чтения: пытаемся зарезервировать
			if q.tail.CompareAndSwap(pos, pos+1) {
				break
			}
			pos = q.tail.Load()
		} else if diff < 0 {
			// Буфер пуст
			var zero T
			return zero, false
		} else {
			pos = q.tail.Load()
		}
	}

	val := cell.data
	// Освобождаем слот для следующего оборота буфера
	cell.sequence.Store(pos + MPMCCapacity)
	return val, true
}

func main() {
	q := NewMPMCQueue[int64]()
	const producers = 8
	const consumers = 8
	const itemsPerProducer = 100_000
	const totalExpected = int64(producers * itemsPerProducer)

	var wg sync.WaitGroup
	wg.Add(producers)
	start := time.Now()

	// Продюсеры
	for p := 0; p < producers; p++ {
		pID := int64(p)
		go func() {
			defer wg.Done()
			for i := int64(1); i <= itemsPerProducer; i++ {
				for !q.Enqueue(pID*1_000_000 + i) {
					runtime.Gosched()
				}
			}
		}()
	}

	// Консьюмеры
	var consumedCount atomic.Int64
	var wgConsumers sync.WaitGroup
	wgConsumers.Add(consumers)
	for c := 0; c < consumers; c++ {
		go func() {
			defer wgConsumers.Done()
			for {
				_, ok := q.Dequeue()
				if ok {
					if consumedCount.Add(1) == totalExpected {
						return
					}
				} else {
					if consumedCount.Load() >= totalExpected {
						return
					}
					runtime.Gosched()
				}
			}
		}()
	}

	wg.Wait()
	wgConsumers.Wait()
	cost := time.Since(start)

	fmt.Printf("MPMC Queue: успешно передано %d сообщений за %v (%.2f млн msg/sec)\n",
		consumedCount.Load(), cost, float64(totalExpected)/cost.Seconds()/1e6)
}
```

ℹ️ Lock-Free MPMC очередь Вьюкова координирует множество продюсеров и консьюмеров через версионные последовательности.

## Под капотом

В алгоритме Вьюкова каждая ячейка хранит состояние в `sequence`. Проверка `diff == 0` гарантирует, что ячейка свободна для записи на текущем витке ($pos = sequence$). После успешного `CAS` на `head` продюсер владеет ячейкой монопольно. Никакой другой поток не может залезть в эту ячейку, пока не завершится `cell.sequence.Store(pos + 1)`, что обеспечивает идеальную консистентность памяти без глобальных блокировок.

## Подводные камни

1. Высокий contention на `head` и `tail`: при 64+ ядрах постоянные CAS-попытки вызывают Cache Line Bouncing.
2. Фиксированный размер буфера: переполнение требует либо отката операции, либо вызова `runtime.Gosched()`.

## На собеседовании

Классический вопрос: «Как устроен алгоритм Vyukov MPMC Queue и почему он быстрее очереди Майкла-Скотта?». Ответ: очередь Вьюкова использует плоский предварительно выделенный кольцевой массив без аллокаций в куче, а синхронизация слотов через версионные счетчики предотвращает конфликт чтения и записи.
