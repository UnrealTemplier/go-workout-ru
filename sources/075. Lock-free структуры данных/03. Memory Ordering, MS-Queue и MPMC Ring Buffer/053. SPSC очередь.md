# SPSC очередь: архитектура без CAS на atomic load/store

## Условие

Изучите архитектуру Single-Producer Single-Consumer (SPSC) кольцевого буфера. Объясните, почему для одного производителя и одного потребителя не требуется инструкция Compare-And-Swap (CAS), а достаточно атомарных операций Load и Store с семантикой Acquire/Release.

### Исходная формулировка

**Single-producer single-consumer (SPSC)**: Простейший case: один producer, один consumer. Не нужен CAS, достаточно atomic load/store.

## Теория

Очередь **SPSC (Single-Producer Single-Consumer)** — это фундаментальный примитив высокопроизводительных систем передачи сообщений с ультранизкой задержкой (Low-Latency Trading, сетевые драйверы DPDK, аудио-движки).

**Почему CAS не нужен в SPSC?**
1. **Только один писатель для каждого индекса**:
   - Поле `head` (указатель записи) модифицирует **исключительно** Producer. Никакой другой поток в системе никогда не записывает в `head`.
   - Поле `tail` (указатель чтения) модифицирует **исключительно** Consumer.
2. **Отсутствие гонки за слот**:
   - Поскольку за право модификации `head` никто не борется, у Producer нет необходимости атомарно проверять «не изменил ли кто-то `head` пока я вычислял слот».
3. **Требуется только публикация (Visibility)**:
   - Producer должен быть уверен, что Consumer видит актуальное значение `head` после того, как данные физически записаны в слот буфера.
   - Consumer должен быть уверен, что видит актуальное значение `tail` после освобождения слота.
   - Это решается обычными операциями `atomic.StoreUint64` и `atomic.LoadUint64`.

## Решение по шагам

1. Опишите структуру `SPSCQueue` с фиксированным размером (степень двойки).
2. Реализуйте метод `Enqueue(item T) bool`, в котором Producer читает `tail`, проверяет `head - tail < capacity`, пишет в массив и обновляет `head`.
3. Реализуйте метод `Dequeue() (T, bool)`, в котором Consumer читает `head`, проверяет `tail < head`, читает элемент и обновляет `tail`.
4. Продемонстрируйте передачу 1 000 000 сообщений между двумя горутинами.
5. Измерьте время работы и убедитесь в отсутствии блокировок и CAS-циклов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// SPSCQueue представляет кольцевой буфер для одного производителя и одного потребителя.
type SPSCQueue struct {
	buffer   []int64
	capacity uint64
	mask     uint64
	head     uint64 // Индекс записи (пишет только Producer)
	tail     uint64 // Индекс чтения (пишет только Consumer)
}

func NewSPSCQueue(size uint64) *SPSCQueue {
	// Размер обязан быть степенью двойки
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be a power of 2")
	}
	return &SPSCQueue{
		buffer:   make([]int64, size),
		capacity: size,
		mask:     size - 1,
	}
}

// Enqueue вызывается строго из одной горутины-производителя.
func (q *SPSCQueue) Enqueue(val int64) bool {
	head := atomic.LoadUint64(&q.head)
	tail := atomic.LoadUint64(&q.tail)

	// Проверка на переполнение буфера
	if head-tail >= q.capacity {
		return false // Очередь заполнена
	}

	// 1. Запись элемента в буфер
	q.buffer[head&q.mask] = val

	// 2. Публикация нового head с барьером памяти Store-Release
	atomic.StoreUint64(&q.head, head+1)
	return true
}

// Dequeue вызывается строго из одной горутины-потребителя.
func (q *SPSCQueue) Dequeue() (int64, bool) {
	tail := atomic.LoadUint64(&q.tail)
	head := atomic.LoadUint64(&q.head)

	// Проверка на пустоту буфера
	if tail >= head {
		return 0, false // Очередь пуста
	}

	// 1. Чтение элемента из буфера
	val := q.buffer[tail&q.mask]

	// 2. Публикация нового tail с барьером памяти
	atomic.StoreUint64(&q.tail, tail+1)
	return val, true
}

func main() {
	const count = 500000
	q := NewSPSCQueue(1024)

	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	// Producer
	go func() {
		defer wg.Done()
		for i := int64(1); i <= count; i++ {
			for !q.Enqueue(i) {
				// Очередь полна: активное ожидание
			}
		}
	}()

	// Consumer
	var sum int64
	go func() {
		defer wg.Done()
		for i := int64(1); i <= count; i++ {
			for {
				if val, ok := q.Dequeue(); ok {
					sum += val
					break
				}
				// Очередь пуста: активное ожидание
			}
		}
	}()

	wg.Wait()
	elapsed := time.Since(start)

	expectedSum := int64(count) * int64(count+1) / 2
	fmt.Printf("Processed %d items in %v (sum: %d, valid: %t)\n", count, elapsed, sum, sum == expectedSum)
	fmt.Printf("Throughput: %.2f million msgs/sec\n", float64(count)/elapsed.Seconds()/1000000)
}
```

ℹ️ Базовый SPSC кольцевой буфер без CAS на чистых atomic Load/Store.

## Под капотом

Инструкция `atomic.StoreUint64` гарантирует порядок записи: процессор и компилятор не имеют права поместить запись в `q.buffer` ПОСЛЕ инкремента `head`. На аппаратном уровне x86 любая обычная запись уже обладает семантикой Release, поэтому `atomic.Store` обходится почти бесплатно без дорогостоящего префикса `LOCK`.

## Подводные камни

1. Нарушение инварианта одиночного вызова: если `Enqueue` вызовут одновременно две горутины, они прочитают одинаковый `head`, одновременно запишут в один слот `q.buffer[head & mask]` и перезапишут данные друг друга. SPSC гарантирует корректность ТОЛЬКО при одном производителе и одном потребителе.
2. Активное ожидание (Spin-wait): пустой цикл `for !q.Enqueue(i) {}` загружает ядро CPU на 100%. В production-коде применяют экспоненциальный backoff (`runtime.Gosched()` или паузы).

## На собеседовании

Вопрос на собеседовании в HighLoad отдел Яндекса: «Почему операция деления по модулю `head % capacity` заменяется на `head & mask`?». Ответ: операция целочисленного деления `DIV` на CPU занимает 20–40 тактов. Если размер буфера равен степени двойки \(2^k\), то остаток от деления равен побитовому И с маской \(2^k - 1\) (`head & (capacity - 1)`), что выполняется за 1 такт процессора.
