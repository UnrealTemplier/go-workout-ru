# Периодические состояния покоя (Quiescent States) в Epoch-Based Reclamation

## Условие

Спроектируйте архитектуру Epoch-Based Reclamation с явным отслеживанием состояний покоя (Quiescent State Tracking). Продемонстрируйте, как продвижение глобальной эпохи привязано к прохождению всеми воркерами контрольных точек покоя.

### Исходная формулировка

**Epoch-based reclamation**: Альтернатива hazard pointers — epoch-based reclamation. Проще в реализации, но требует periodic quiescent state.

## Теория

В алгоритмах **Epoch-Based Reclamation (EBR)** ключевое понятие — **Состояние покоя (Quiescent State)**:
* Состояние покоя — это момент времени в жизненном цикле потока, когда он **гарантированно не удерживает ссылок** ни на одну lock-free структуру данных (например, пауза между обработкой двух HTTP-запросов, итерация сетевого цикла epoll или возврат в пул воркеров).

**Инвариант продвижения эпох**:
1. Если поток \(i\) зафиксировал прохождение Quiescent State в эпохе \(E\), он не может удерживать узлы, удаленные в эпохе \(E-1\).
2. Когда **все зарегистрированные потоки** прошли хотя бы одно состояние покоя в эпохе \(E\), глобальная эпоха увеличивается: \(E \to E + 1\).
3. Все объекты, помещенные в очередь отложенного удаления в эпохе \(E-1\), могут быть безопасно освобождены!

## Решение по шагам

1. Создайте класс `QuiescentTracker` с глобальной эпохой и массивом эпох потоков.
2. Реализуйте метод `Checkpoint(threadID int)`.
3. Реализуйте логику проверки завершения эпохи всеми воркерами.
4. Смоделируйте цикл обработки задач воркерами с контрольными точками.
5. Продемонстрируйте очистку пакетов памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

const ThreadsCount = 4

type QuiescentTracker struct {
	globalEpoch atomic.Uint64
	threadEpoch [ThreadsCount]atomic.Uint64
}

func NewQuiescentTracker() *QuiescentTracker {
	return &QuiescentTracker{}
}

// Checkpoint вызывается потоком между задачами (Quiescent State)
func (t *QuiescentTracker) Checkpoint(threadID int) {
	currentGlobal := t.globalEpoch.Load()
	t.threadEpoch[threadID].Store(currentGlobal)
}

func (t *QuiescentTracker) TryAdvanceEpoch() bool {
	cur := t.globalEpoch.Load()
	for i := 0; i < ThreadsCount; i++ {
		// Если поток еще не догнал текущую эпоху, продвигать нельзя
		if t.threadEpoch[i].Load() < cur {
			return false
		}
	}
	// Все потоки подтвердили состояние покоя в текущей эпохе!
	t.globalEpoch.Add(1)
	return true
}

func main() {
	tracker := NewQuiescentTracker()

	fmt.Println("=== Отслеживание состояний покоя (Quiescent States) ===")
	fmt.Printf("Начальная эпоха: %d\n", tracker.globalEpoch.Load())

	var wg sync.WaitGroup
	wg.Add(ThreadsCount)

	for id := 0; id < ThreadsCount; id++ {
		tID := id
		go func() {
			defer wg.Done()
			for task := 0; task < 5; task++ {
				// Имитация обработки запроса
				time.Sleep(10 * time.Millisecond)

				// Контрольная точка покоя (Quiescent State)
				tracker.Checkpoint(tID)
			}
		}()
	}

	// Координатор проверяет продвижение эпохи
	go func() {
		for i := 0; i < 3; i++ {
			time.Sleep(15 * time.Millisecond)
			if tracker.TryAdvanceEpoch() {
				fmt.Printf("[Координатор] Все потоки прошли состояние покоя! Новая эпоха: %d (старая память освобождена)\n",
					tracker.globalEpoch.Load())
			}
		}
	}()

	wg.Wait()
	fmt.Println("Все воркеры успешно завершили работу с верификацией эпох.")
}
```

ℹ️ Контрольные точки Quiescent State позволяют точно координировать циклы безопасной очистки памяти.

## Под капотом

В рантайме Go функции `runtime.Gosched()`, вызовы системных вызовов и аллокации памяти являются точками безопасной остановки (Safe Points). Сборщик мусора использует их как естественные Quiescent States для координации фаз сканирования кучи без необходимости явных вызовов со стороны программиста.

## Подводные камни

1. «Застрявший воркер» (Stalled Worker): длительный блокирующий вызов в одном потоке без Checkpoint замораживает продвижение эпохи для всей системы.
2. Чрезмерно частый Checkpoint создает оверхед атомарных записей.

## На собеседовании

Вопрос: «Что такое Safe Points в JVM и Go runtime и как они связаны с Quiescent States?». Ответ: Safe Points — это точки в сгенерированном машинном коде, где состояние регистров и стека потока полностью известно компилятору и предсказуемо. В этих точках среда исполнения может безопасно приостановить поток для сборки мусора (GC STW) или проверки продвижения эпох.
