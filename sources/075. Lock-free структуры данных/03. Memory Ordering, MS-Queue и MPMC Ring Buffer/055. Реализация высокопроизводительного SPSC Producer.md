# Реализация высокопроизводительного SPSC Producer с кэшированием индекса

## Условие

Реализуйте оптимизированный SPSC Producer с локальным кэшированием указателя чтения (Cached Tail). Объясните, как кэширование устраняет необходимость межъядерного чтения `tail` на каждой итерации записи.

### Исходная формулировка

**SPSC producer**: Producer проверяет, что buffer не full (`head - tail < size`), пишет в `buffer[head & mask]`, атомарно инкрементирует `head`.

## Теория

В стандартном алгоритме SPSC Producer при каждой записи выполняет:
```go
tail := atomic.LoadUint64(&q.tail)
if head - tail >= capacity { return false }
```
Хотя Producer не модифицирует `tail`, вызов `atomic.LoadUint64(&q.tail)` требует чтения из кэша другого ядра (Consumer). Это порождает паразитный трафик шины когерентности памяти при каждом пуше.

**Оптимизация «Cached Tail» (Локальный кэш указателя чтения)**:
1. Producer сохраняет у себя локальное поле `cachedTail uint64`. Это поле приватное для потока Producer и не требует синхронизации.
2. При вызове `Enqueue` Producer сначала проверяет буфер относительно `cachedTail`:
   `if head - q.cachedTail < capacity { /* есть гарантированное свободное место! */ }`
3. Если место есть, Producer пишет в буфер и делает инкремент `head`, вообще **не читая** настоящий `q.tail`!
4. Только если буфер оказался «полным» по мнению `cachedTail`, Producer обращается к настоящему атомарному `q.tail` (`q.cachedTail = atomic.LoadUint64(&q.tail)`).
5. Если Consumer к этому моменту уже продвинулся, `cachedTail` обновится, и Producer продолжит работу еще на целую серию записей без единого межъядерного чтения!

## Решение по шагам

1. Добавьте в структуру очереди приватное поле `cachedTail uint64` в кэш-линию производителя.
2. Модифицируйте метод `Enqueue`: сначала сравнивайте `head - cachedTail`, и только при заполнении делайте `atomic.LoadUint64(&q.tail)`.
3. Аналогично в Consumer добавьте `cachedHead uint64` для отложенного чтения `head`.
4. Напишите тест с передачей пакетов данных и замером времени.
5. Продемонстрируйте снижение нагрузки на память.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type OptimizedSPSCQueue struct {
	buffer   []uint64
	capacity uint64
	mask     uint64
	_pad0    [40]byte

	// Producer Cache Line
	head       uint64
	cachedTail uint64 // Локальная копия tail, доступная ТОЛЬКО Producer
	_pad1      [48]byte

	// Consumer Cache Line
	tail       uint64
	cachedHead uint64 // Локальная копия head, доступная ТОЛЬКО Consumer
	_pad2      [48]byte
}

func NewOptimizedSPSCQueue(size uint64) *OptimizedSPSCQueue {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be power of 2")
	}
	return &OptimizedSPSCQueue{
		buffer:   make([]uint64, size),
		capacity: size,
		mask:     size - 1,
	}
}

// Enqueue с оптимизацией cachedTail
func (q *OptimizedSPSCQueue) Enqueue(val uint64) bool {
	head := q.head // Локальное чтение без атомика, так как пишет только эта горутина

	// Проверяем по локальной копии
	if head-q.cachedTail >= q.capacity {
		// Локальный буфер полон, обновляем знание о реальном tail
		q.cachedTail = atomic.LoadUint64(&q.tail)
		if head-q.cachedTail >= q.capacity {
			return false // Действительно переполнен
		}
	}

	q.buffer[head&q.mask] = val
	// Публикуем head атомарно
	atomic.StoreUint64(&q.head, head+1)
	q.head = head + 1
	return true
}

// Dequeue с оптимизацией cachedHead
func (q *OptimizedSPSCQueue) Dequeue() (uint64, bool) {
	tail := q.tail // Локальное чтение

	if tail >= q.cachedHead {
		// Локальный буфер пуст, читаем реальный head
		q.cachedHead = atomic.LoadUint64(&q.head)
		if tail >= q.cachedHead {
			return 0, false // Действительно пуст
		}
	}

	val := q.buffer[tail&q.mask]
	atomic.StoreUint64(&q.tail, tail+1)
	q.tail = tail + 1
	return val, true
}

func main() {
	const total = 2000000
	q := NewOptimizedSPSCQueue(4096)

	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	go func() {
		defer wg.Done()
		for i := uint64(1); i <= total; i++ {
			for !q.Enqueue(i) {
			}
		}
	}()

	var receivedCount uint64
	go func() {
		defer wg.Done()
		for receivedCount < total {
			if _, ok := q.Dequeue(); ok {
				receivedCount++
			}
		}
	}()

	wg.Wait()
	elapsed := time.Since(start)

	fmt.Printf("Sent & Received %d messages in %v\n", total, elapsed)
	fmt.Printf("Speed: %.2f M msgs/sec\n", float64(total)/elapsed.Seconds()/1e6)
}
```

ℹ️ SPSC кольцевой буфер с локальным кэшированием указателей чтения и записи.

## Под капотом

При емкости буфера в 4096 слотов Producer обращается к удаленной кэш-линии Consumer всего 1 раз на каждые 4096 успешных вставок (при условии, что потребитель успевает разгребать очередь). Это сокращает нагрузку на шину памяти на 99.97%, позволяя достигать скоростей свыше 50–100 миллионов операций в секунду на одном процессорном ядре.

## Подводные камни

1. Забыть обновить `cachedTail`: если не обновлять `q.cachedTail = atomic.LoadUint64(&q.tail)`, Producer навсегда решит, что очередь переполнена, и зависнет в вечном цикле ожидания.
2. Гонка за локальное поле: `cachedTail` и `cachedHead` ни в коем случае нельзя делать публичными или вызывать методы из разных горутин.

## На собеседовании

В LMAX Disruptor и высокочастотных торговых шлюзах (HFT) на C++ и Go этот паттерн известен как Batch Head/Tail Peeking. На собеседованиях в финансовый сектор это ключевой вопрос проверки понимания микроархитектуры CPU.
