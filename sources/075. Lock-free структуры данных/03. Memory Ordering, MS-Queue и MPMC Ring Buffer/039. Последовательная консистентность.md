# Последовательная консистентность (Sequential Consistency) в модели памяти Go

## Условие

Исследуйте модель последовательной консистентности (Sequential Consistency, SC) в рантайме Go. Объясните, почему все операции пакета sync/atomic гарантируют глобальный порядок выполнения для всех процессоров, и какие компромиссы между простотой модели и предельной аппаратной скоростью были приняты разработчиками языка.

### Исходная формулировка

**Sequential consistency**: В Go все atomic operations имеют sequential consistency semantics. Это проще для понимания, но может быть медленнее.

## Теория

Модель **последовательной консистентности (Sequential Consistency)** была впервые сформулирована Лесли Лэмпортом в 1979 году:
> «Результат любого параллельного выполнения эквивалентен тому, как если бы операции всех процессоров выполнялись в некотором последовательном порядке, и операции каждого отдельного процессора появлялись в этой последовательности в порядке, заданном его программой».

В стандарте C++20 разработчикам доступны сложные модели: `relaxed`, `consume`, `acquire`, `release`, `acq_rel`, `seq_cst`. На слабых процессорах (ARM64) `relaxed` атомики не ставят барьеры памяти и работают быстрее.

**Почему в Go выбран строгий Sequential Consistency?**
1. **Предотвращение критических ошибок**: 95% разработчиков допускают ошибки при использовании relaxed/acquire-release моделей, получая гонки данных, которые проявляются только под нагрузкой на серверах ARM.
2. **Простота верификации**: для Go-кода математически проще доказать корректность алгоритмов.
3. **Плата за простоту**: на архитектурах ARM64 и POWER все операции `sync/atomic` генерируют барьеры памяти (инструкции `DMB ISH`), что несет небольшие накладные расходы (~5–10%), но гарантирует абсолютную переносимость.

## Решение по шагам

1. Создайте симулятор двух параллельных горутин, выполняющих перекрестную запись и чтение флагов.
2. Запустите 100 000 итераций и зафиксируйте невозможность состояния нарушения SC в Go.
3. Объясните, как барьер памяти запрещает Store-Load переупорядочивание.
4. Продемонстрируйте ассемблерный код для x86_64 и ARM64.
5. Сформулируйте правила Go Memory Model для атомиков.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type SCVerification struct {
	a atomic.Int32
	b atomic.Int32
}

func main() {
	const trials = 100_000
	reorderedCount := 0

	fmt.Printf("Проверка Sequential Consistency в Go на %d итераций...\n", trials)

	for i := 0; i < trials; i++ {
		test := &SCVerification{}
		var readA, readB int32
		var wg sync.WaitGroup
		wg.Add(2)

		// Горутина 1: пишет в A, читает B
		go func() {
			defer wg.Done()
			test.a.Store(1)
			readB = test.b.Load()
		}()

		// Горутина 2: пишет в B, читает A
		go func() {
			defer wg.Done()
			test.b.Store(1)
			readA = test.a.Load()
		}()

		wg.Wait()

		// Если нарушена последовательная консистентность, оба потока могут прочитать 0
		if readA == 0 && readB == 0 {
			reorderedCount++
		}
	}

	fmt.Printf("Нарушений последовательного порядка (readA=0 && readB=0): %d\n", reorderedCount)
	fmt.Println("В Go атомики гарантируют глобальный неделимый порядок (Sequential Consistency)!")
}
```

ℹ️ Go sync/atomic гарантирует модель Sequential Consistency на всех поддерживаемых архитектурах.

## Под капотом

На архитектуре x86_64 инструкции с префиксом `LOCK` или вызов `atomic.StoreInt32` используют инструкцию `XCHGL`, которая принудительно очищает Store Buffer ядра. На архитектуре ARM64 компилятор генерирует пару `STLR` (Store-Release) и `LDAR` (Load-Acquire), создавая полный двусторонний барьер памяти, гарантирующий последовательную консистентность.

## Подводные камни

1. Обычные неатомарные переменные не имеют гарантий SC: для них процессор и компилятор имеют право переупорядочивать чтения и записи.
2. Неучет накладных расходов: на серверах с сотнями ядер частые SC-атомики создают нагрузку на шину когерентности.

## На собеседовании

Вопрос: «Что такое Sequential Consistency и почему в Go нет memory_order_relaxed?». Ответ: SC гарантирует существование единого глобального порядка всех атомарных операций, разделяемого всеми ядрами. В Go нет relaxed-атомиков из-за философии надежности: сложность отладки слабых моделей памяти перевешивает незначительный выигрыш в микросекундах.
