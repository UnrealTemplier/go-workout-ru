# Cache Line Padding для SPSC кольцевого буфера

## Условие

Оптимизируйте структуру SPSC кольцевого буфера с помощью выравнивания и добавления отступов кэш-линий (Cache Line Padding), полностью устранив эффект False Sharing между указателями head и tail.

### Исходная формулировка

**Cache line padding для SPSC**: Разделите `head` и `tail` в разные cache lines для избежания false sharing:
```go
type SPSCRingBuffer struct {
    _      [40]byte       // padding
    head   atomic.Uint64
    _      [56]byte       // padding
    tail   atomic.Uint64
    _      [56]byte       // padding
    buffer []int64
    mask   uint64
}
```

## Теория

В базовой реализации SPSC буфера:
```go
type SPSCQueue struct {
    buffer   []int64
    capacity uint64
    mask     uint64
    head     uint64 // Ядро 1 постоянно пишет сюда
    tail     uint64 // Ядро 2 постоянно пишет сюда
}
```
Поля `head` и `tail` расположены в памяти рядом. Размер кэш-линии на подавляющем большинстве современных процессоров x86-64 и ARM64 составляет **64 байта**.

Поскольку оба 8-байтных поля попадают в одну и ту же 64-байтную кэш-линию:
1. Когда Ядро 1 (Producer) записывает в `head`, оно переводит кэш-линию в состояние Modified (M) по протоколу MESI.
2. Кэш L1 Ядра 2 (Consumer) мгновенно инвалидируется.
3. Когда Ядро 2 (Consumer) записывает в `tail`, оно запрашивает эксклюзивное владение той же кэш-линией, инвалидируя кэш Ядра 1.
4. Возникает эффект **Cache Line Bouncing (False Sharing)**: кэш-линия непрерывно пересылается между ядрами по межъядерной шине, снижая производительность в 5–10 раз!

**Решение**: разнести `head` и `tail` в разные кэш-линии, окружив каждое поле отступами размером не менее 64 байт (или `[56]byte` / `[64]byte`).

## Решение по шагам

1. Создайте структуру `PaddedSPSCQueue` с явными полями заполнения `_ [56]byte` до и после `head` и `tail`.
2. Убедитесь, что смещения `unsafe.Offsetof` полей `head` и `tail` кратны 64 байтам.
3. Реализуйте методы `Enqueue` и `Dequeue`.
4. Сравните время передачи сообщений с padding и без него.
5. Продемонстрируйте прирост пропускной способности.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

// PaddedSPSCQueue гарантирует, что head и tail находятся в разных cache lines (64 байта).
type PaddedSPSCQueue struct {
	// Cache line 1: Метаданные буфера
	buffer   []int64
	capacity uint64
	mask     uint64
	_pad0    [40]byte // Дополняем до 64 байт: slice (24) + cap (8) + mask (8) = 40 байт -> pad 24/40

	// Cache line 2: Head (пишет только Producer)
	head uint64
	_pad1 [56]byte // 8 байт head + 56 байт pad = 64 байта

	// Cache line 3: Tail (пишет только Consumer)
	tail uint64
	_pad2 [56]byte // 8 байт tail + 56 байт pad = 64 байта
}

func NewPaddedSPSCQueue(size uint64) *PaddedSPSCQueue {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be a power of 2")
	}
	return &PaddedSPSCQueue{
		buffer:   make([]int64, size),
		capacity: size,
		mask:     size - 1,
	}
}

func (q *PaddedSPSCQueue) Enqueue(val int64) bool {
	head := atomic.LoadUint64(&q.head)
	tail := atomic.LoadUint64(&q.tail)

	if head-tail >= q.capacity {
		return false
	}

	q.buffer[head&q.mask] = val
	atomic.StoreUint64(&q.head, head+1)
	return true
}

func (q *PaddedSPSCQueue) Dequeue() (int64, bool) {
	tail := atomic.LoadUint64(&q.tail)
	head := atomic.LoadUint64(&q.head)

	if tail >= head {
		return 0, false
	}

	val := q.buffer[tail&q.mask]
	atomic.StoreUint64(&q.tail, tail+1)
	return val, true
}

func main() {
	q := NewPaddedSPSCQueue(2048)

	fmt.Println("=== Memory Layout Analysis ===")
	fmt.Printf("Struct Total Size: %d bytes\n", unsafe.Sizeof(*q))
	fmt.Printf("Offset of head:   %d bytes (mod 64 = %d)\n", unsafe.Offsetof(q.head), unsafe.Offsetof(q.head)%64)
	fmt.Printf("Offset of tail:   %d bytes (mod 64 = %d)\n", unsafe.Offsetof(q.tail), unsafe.Offsetof(q.tail)%64)

	const count = 1000000
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	go func() {
		defer wg.Done()
		for i := int64(1); i <= count; i++ {
			for !q.Enqueue(i) {
			}
		}
	}()

	var sum int64
	go func() {
		defer wg.Done()
		for i := int64(1); i <= count; i++ {
			for {
				if v, ok := q.Dequeue(); ok {
					sum += v
					break
				}
			}
		}
	}()

	wg.Wait()
	elapsed := time.Since(start)

	fmt.Printf("\nTransferred %d items in %v\n", count, elapsed)
	fmt.Printf("Throughput: %.2f M ops/sec\n", float64(count)/elapsed.Seconds()/1e6)
}
```

ℹ️ Cache line padding для разнесения head и tail в разные 64-байтные блоки памяти.

## Под капотом

Размер кэш-линий определяется аппаратно. Добавление `_pad [56]byte` гарантирует, что между переменными `head` и `tail` находится дистанция минимум в одну линию кэша. Даже если объект структуры в куче начнется не с идеального выравнивания по 64 байта, расстояние между адресами `&q.head` и `&q.tail` гарантированно превышает 64 байта, поэтому они физически никогда не смогут оказаться в одной строке L1-кэша.

## Подводные камни

1. Оптимизации компилятора: поля с именем `_` компилятор не имеет права вырезать, так как они участвуют в расчете размера структуры в памяти.
2. Увеличение расхода оперативной памяти: структура растет со стандартных 40 байт до 200+ байт. Для очередей, существующих в единичных экземплярах, этот расход пренебрежимо мал по сравнению с полученным выигрышем.

## На собеседовании

В Lamoda и Авито на позициях Highload Go разработчика часто предлагают решить задачу: «Как программно узнать размер кэш-линии хоста в Go?». Ответ: в Go стандартного API в пакете runtime нет, но можно читать sysfs на Linux `/sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size` или использовать внутренний пакет `internal/cpu.CacheLinePad`.
