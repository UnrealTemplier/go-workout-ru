## Теория

Современные компиляторы и суперскалярные процессоры (x86, ARM64) не выполняют инструкции строго в порядке их написания в исходном коде:
1. **Оптимизации компилятора**: компилятор может переставлять независимые инструкции для оптимизации использования регистров, устранения общих подвыражений или векторизации.
2. **Процессорный конвейер (Out-of-Order Execution)**: процессор переупорядочивает инструкции, если данные для следующей инструкции уже готовы в кэше, а текущая инструкция ожидает загрузки из оперативной памяти.
3. **Store Buffers**: запись в память не происходит мгновенно в кэш L1/L2. Процессор помещает запись в буфер записи (Store Buffer) и немедленно переходит к выполнению следующих чтений (Store-Load reordering).

**Классический пример Dekkers/Peterson Race:**
```go
// Горутина 1        // Горутина 2
x = 1                y = 1
r1 = y               r2 = x
```
В однопоточном мире невозможно получить `r1 == 0 && r2 == 0`. Но на x86 из-за буферов записи оба процессора могут прочитать старые значения из кэша до того, как их собственные буферы сбросятся в кэш! В результате `r1 == 0 && r2 == 0`.

**Барьеры памяти (Memory Barriers / Fences):**
- **StoreStore**: гарантирует, что все предыдущие записи станут видимы другим ядрам до последующих записей.
- **LoadLoad**: гарантирует порядок последовательных чтений.
- **StoreLoad (Full Fence)**: самый тяжелый барьер (`MFENCE` на x86, `DMB ISH` на ARM). Гарантирует сброс Store Buffer.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
)

// ReorderDetector симулирует проверку сохранения порядка операций
type ReorderDetector struct {
	x int32
	y int32
	r1 int32
	r2 int32
}

func main() {
	// Фиксируем количество потоков ОС
	runtime.GOMAXPROCS(2)

	const iterations = 50000
	var reorderCount int

	for i := 0; i < iterations; i++ {
		var x, y int32
		var r1, r2 int32

		var start sync.WaitGroup
		var done sync.WaitGroup
		start.Add(1)
		done.Add(2)

		// Горутина 1
		go func() {
			start.Wait()
			atomic.StoreInt32(&x, 1) // Store x
			// Барьер обеспечивается атомиком в Go Memory Model
			r1 = atomic.LoadInt32(&y) // Load y
			done.Done()
		}()

		// Горутина 2
		go func() {
			start.Wait()
			atomic.StoreInt32(&y, 1) // Store y
			r2 = atomic.LoadInt32(&x) // Load x
			done.Done()
		}()

		start.Done()
		done.Wait()

		if r1 == 0 && r2 == 0 {
			reorderCount++
		}
	}

	fmt.Printf("Total iterations: %d\n", iterations)
	fmt.Printf("Reordering anomalies detected: %d\n", reorderCount)
	if reorderCount == 0 {
		fmt.Println("Sequential consistency maintained by sync/atomic!")
	}
}
```

ℹ️ Демонстрация соблюдения Sequential Consistency атомиками Go.

## Под капотом

В Go `sync/atomic.Store` на архитектуре x86_64 компилируется либо в `XCHGQ` (которая имеет неявный префикс `LOCK` и сбрасывает Store Buffer), либо обычный `MOVQ` с последующим барьером памяти, если требуется `StoreLoad`. На ARM64 компилятор генерирует пару инструкций `STLR` (Store-Release) и `LDAR` (Load-Acquire) или `DMB ISH`, что исключает любое спекулятивное переупорядочивание за пределы границы барьера.

## Подводные камни

1. Обычные неатомарные переменные: если в коде выше заменить `atomic.Store/Load` на прямое чтение и запись `x = 1; r1 = y`, Go-компилятор и процессор имеют полное право переставить эти инструкции местами, так как они независимы в рамках одной горутины.
2. Гонка данных (Data Race): при отсутствии барьеров детектор гонок `go test -race` немедленно зарегистрирует concurrent read/write data race.

## На собеседовании

В Т-Банке и Ozon на позиции Senior часто спрашивают: «Чем модель памяти Go отличается от C++11?». Ответ: в C++ программист вручную выбирает `std::memory_order_relaxed`, `memory_order_acquire/release` или `memory_order_seq_cst`. В Go намеренно оставлена только строгая модель Sequential Consistency (`seq_cst`), чтобы сделать код надежным и безопасным от изощренных низкоуровневых багов синхронизации.
