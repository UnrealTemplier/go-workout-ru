# Проблема ABA в lock-free структурах: анатомия, риски и методы решения

## Условие

Изучите феномен проблемы ABA (ABA Problem) в lock-free структурах данных. Создайте наглядный сценарий, объясняющий, почему наивная проверка равенства указателя в CAS не гарантирует неизменности структуры, и продемонстрируйте решение с помощью версионированных дескрипторов (Tagged Pointers).

### Исходная формулировка

**ABA problem**: Изучите ABA problem: CAS видит, что значение = A, но не знает, что оно было A → B → A. Решение: version counter или hazard pointers.

## Теория

**Проблема ABA** — классическая уязвимость lock-free алгоритмов, основанных на операции Compare-And-Swap (CAS).

**Сценарий возникновения в Lock-Free Stack (Treiber Stack):**
1. Стек содержит элементы: `Top -> A -> B -> C`.
2. Поток 1 хочет извлечь верхний элемент (`Pop`):
   - Читает `currTop = A`.
   - Читает следующий элемент `next = A.next` (это `B`).
   - Перед тем как вызвать `CAS(&Top, A, B)`, Поток 1 вытесняется планировщиком ОС!
3. Поток 2 просыпается и делает два действия:
   - Извлекает `A` (`Pop` -> `Top` становится `B`).
   - Извлекает `B` (`Pop` -> `Top` становится `C`).
   - Помещает `A` обратно в стек (`Push(A)` с новым полем `A.next = C`).
   - Теперь стек выглядит как: `Top -> A -> C`, а узел `B` освобожден или переиспользован!
4. Поток 1 возобновляет работу и выполняет свой отложенный CAS:
   - `CAS(&Top, A, B)` проверяет: равно ли текущее значение `Top` сохраненному `A`?
   - Да! `Top` действительно указывает на `A`!
   - CAS успешно срабатывает и переставляет `Top = B`!
5. **Катастрофа**: `Top` теперь указывает на уже удаленный/невалидный узел `B`, стек поврежден, данные потеряны, память разрушена.

**Решения проблемы ABA:**
1. **Сборщик мусора (GC)**: в языках с GC (Go, Java) память узла `B` не освобождается, пока на него есть ссылки. Однако в структурах с логическим переиспользованием узлов (Free-list / `sync.Pool`) ABA остается актуальной!
2. **Tagged Pointers (Версионирование)**: вместе с адресом хранится счетчик изменений `version`. Значение обновляется с `(A, v1)` на `(B, v2)`. Даже если вернулся узел `A`, его метка станет `(A, v3)`, и CAS `(A, v1)` завершится ошибкой.

## Решение по шагам

1. Создайте структуру `TaggedNode`, инкапсулирующую указатель на узел и 64-битный счетчик версий (`stamp` или `tag`).
2. Объедините указатель и версию в упакованную структуру или используйте двойной CAS / атомарный дескриптор.
3. Смоделируйте стек, использующий версионированные ссылки.
4. Продемонстрируйте, как версионная метка блокирует ложное срабатывание CAS при возвращении узла A.
5. Запустите проверку и выведите детальный лог работы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"unsafe"
)

type Node struct {
	value int
	next  *Node
}

// TaggedPointer упаковывает указатель и номер версии.
type TaggedPointer struct {
	ptr     *Node
	version uint64
}

type TaggedStack struct {
	// Храним указатель на TaggedPointer атомарно
	head unsafe.Pointer
}

func NewTaggedStack() *TaggedStack {
	initial := &TaggedPointer{ptr: nil, version: 0}
	return &TaggedStack{
		head: unsafe.Pointer(initial),
	}
}

func (s *TaggedStack) Push(val int) {
	newNode := &Node{value: val}
	for {
		curHeadPtr := atomic.LoadPointer(&s.head)
		curHead := (*TaggedPointer)(curHeadPtr)

		newNode.next = curHead.ptr
		newHead := &TaggedPointer{
			ptr:     newNode,
			version: curHead.version + 1, // Инкремент версии исключает ABA
		}

		if atomic.CompareAndSwapPointer(&s.head, curHeadPtr, unsafe.Pointer(newHead)) {
			return
		}
	}
}

func (s *TaggedStack) Pop() (int, bool) {
	for {
		curHeadPtr := atomic.LoadPointer(&s.head)
		curHead := (*TaggedPointer)(curHeadPtr)

		if curHead.ptr == nil {
			return 0, false // Стек пуст
		}

		newHead := &TaggedPointer{
			ptr:     curHead.ptr.next,
			version: curHead.version + 1, // Каждая модификация версионируется
		}

		if atomic.CompareAndSwapPointer(&s.head, curHeadPtr, unsafe.Pointer(newHead)) {
			return curHead.ptr.value, true
		}
	}
}

func main() {
	stack := NewTaggedStack()

	stack.Push(10)
	stack.Push(20)
	stack.Push(30)

	fmt.Println("Pushed 10, 20, 30 with ABA protection via tagged versions.")

	for {
		val, ok := stack.Pop()
		if !ok {
			break
		}
		curHead := (*TaggedPointer)(atomic.LoadPointer(&stack.head))
		fmt.Printf("Popped: %d | Current Version Stamp: %d\n", val, curHead.version)
	}
}
```

ℹ️ Устранение проблемы ABA с помощью версионирования TaggedPointer.

## Под капотом

В C++ для tagged pointers используют упаковку версии в неиспользуемые старшие 16 бит 64-битного виртуального адреса (так как архитектуры x86-64 используют 48 бит адресации) или 128-битную атомарную инструкцию `CMPXCHG16B`. В Go рантайм использует сборку мусора, поэтому многие ABA-сценарии с разрушением памяти сглаживаются, однако при использовании пулов объектов (`sync.Pool`) защита счетчиком версий абсолютно необходима.

## Подводные камни

1. Переполнение счетчика версий: 32-битный счетчик может переполниться за несколько секунд при 100M ops/s. 64-битный счетчик версий не переполнится за столетия непрерывной работы.
2. Дополнительные аллокации `TaggedPointer`: выделение дескриптора в куче создает нагрузку на GC. Для предотвращения аллокаций используют упаковку `uintptr(ptr) | (version << 48)` с помощью пакета `unsafe`.

## На собеседовании

«Защищает ли Garbage Collector в Go от проблемы ABA?». Ответ: GC защищает от use-after-free (память узла B не будет отдана операционной системе или перезаписана другим объектом). Но GC НЕ защищает от нарушения логической целостности структуры данных (например, если узлы возвращаются в локальный free-list и переиспользуются, топология графа нарушится точно так же, как в C++).
