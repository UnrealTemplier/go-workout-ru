# Паттерн RCU (Read-Copy-Update) для сценариев с преобладанием чтения

## Условие

Реализуйте высокопроизводительный паттерн RCU (Read-Copy-Update) для шардированного справочника метаданных. Обеспечьте нулевые блокировки для читателей и атомарную замену таблицы писателем с ожиданием выхода читателей (Grace Period).

### Исходная формулировка

**RCU (Read-Copy-Update)**: Для read-heavy workloads используйте RCU: readers не блокируются, writers создают copy и атомарно swap.

## Теория

Паттерн **RCU (Read-Copy-Update)**, созданный Полом Маккенни (Paul McKenney) для ядра Linux — один из самых мощных инструментов для Read-Heavy архитектур:
* **Читатели (Readers)**: не используют никаких блокировок, семафоров или счетчиков! Они просто получают текущий указатель на структуру и читают ее на полной скорости L1-кэша.
* **Писатели (Writers)**:
  1. **Read & Copy**: создают полную копию структуры данных в куче.
  2. **Update**: модифицируют копию.
  3. **Publish**: атомарно подменяют корневой указатель (`atomic.Pointer.Store`).
  4. **Grace Period (Период отсрочки)**: ожидают, пока все читатели, начавшие чтение до момента публикации, завершат свою работу.
  5. **Reclaim**: безопасно освобождают старую структуру.

## Решение по шагам

1. Создайте справочник `RoutingTable` в виде неизменяемой карты.
2. Создайте класс `RCUManager` с корневым `atomic.Pointer[RoutingTable]`.
3. Реализуйте метод `Read() *RoutingTable` с нулевыми блокировками.
4. Реализуйте метод `Update(fn func(map[string]string))` с атомарной подменой.
5. Продемонстрируйте параллельную работу 20 читателей и фонового писателя.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type RoutingTable struct {
	routes map[string]string
}

type RCUManager struct {
	current atomic.Pointer[RoutingTable]
	writeMu sync.Mutex
}

func NewRCUManager(initial map[string]string) *RCUManager {
	mgr := &RCUManager{}
	mgr.current.Store(&RoutingTable{routes: initial})
	return mgr
}

// Read: Zero Locks, Zero Wait, 100% L1 Cache Hit
func (m *RCUManager) Read() *RoutingTable {
	return m.current.Load()
}

// Update: Copy-On-Write + Graceful Publish
func (m *RCUManager) Update(modifier func(copyMap map[string]string)) {
	m.writeMu.Lock()
	defer m.writeMu.Unlock()

	// 1. Копируем данные
	oldTable := m.current.Load()
	newMap := make(map[string]string, len(oldTable.routes)+1)
	for k, v := range oldTable.routes {
		newMap[k] = v
	}

	// 2. Модифицируем копию
	modifier(newMap)

	// 3. Атомарно публикуем новую версию
	m.current.Store(&RoutingTable{routes: newMap})

	// В Go сборщик мусора автоматически дожидается окончания работы
	// всех горутин, читающих oldTable, устраняя необходимость сложного Grace Period!
}

func main() {
	rcu := NewRCUManager(map[string]string{
		"/api/v1/user":  "srv_user:8080",
		"/api/v1/order": "srv_order:8080",
	})

	const readers = 16
	const readsPerWorker = 200_000

	var wg sync.WaitGroup
	wg.Add(readers + 1)
	start := time.Now()

	// Писатель обновляет таблицу маршрутов
	go func() {
		defer wg.Done()
		for i := 1; i <= 3; i++ {
			time.Sleep(10 * time.Millisecond)
			rcu.Update(func(m map[string]string) {
				m[fmt.Sprintf("/api/v1/service_%d", i)] = fmt.Sprintf("srv_%d:9000", i)
			})
		}
	}()

	// Читатели непрерывно читают таблицу
	for r := 0; r < readers; r++ {
		go func() {
			defer wg.Done()
			for i := 0; i < readsPerWorker; i++ {
				tbl := rcu.Read()
				_ = tbl.routes["/api/v1/user"]
			}
		}()
	}

	wg.Wait()
	cost := time.Since(start)
	totalReads := readers * readsPerWorker

	fmt.Printf("RCU: обработано %d чтений за %v (%.2f млн чтений/sec)\n",
		totalReads, cost, float64(totalReads)/cost.Seconds()/1e6)
	fmt.Printf("Финальное число маршрутов: %d\n", len(rcu.Read().routes))
}
```

ℹ️ Паттерн RCU гарантирует полное отсутствие блокировок для читателей при обновлении данных.

## Под капотом

В RCU читатели не совершают ни одной операции записи в разделяемую память. Строка кэша, содержащая указатель `current`, удерживается ядрами в состоянии Shared. Когда писатель вызывает `current.Store`, кэш-линия указателя обновляется, и читатели при следующем запросе мгновенно переключаются на новую таблицу маршрутов.

## Подводные камни

1. Мутация данных старой таблицы: если писатель напрямую изменит `oldTable.routes`, произойдет фатальный Data Race с читателями. Копирование структуры перед изменением обязательно.
2. Неэффективно при частых записях: стоимость копирования больших структур съедает выигрыш.

## На собеседовании

Вопрос: «Что такое Grace Period в алгоритме RCU?». Ответ: это интервал времени после публикации новой версии объекта, в течение которого гарантированно завершаются все операции чтения, начатые со старой версией. Только после окончания Grace Period память старого объекта может быть безопасно освобождена.
