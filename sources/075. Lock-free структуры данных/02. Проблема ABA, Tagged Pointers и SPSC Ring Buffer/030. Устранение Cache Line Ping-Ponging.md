# Устранение Cache Line Ping-Ponging через адаптивный Backoff в CAS-циклах

## Условие

Реализуйте оптимистичный алгоритм обновления разделяемого состояния с экспоненциальным Backoff при неудачном CAS. Покажите, как добавление пауз между повторными попытками снижает конкуренцию за кэш-линию (Cache Line Ping-Ponging) и увеличивает суммарную пропускную способность под нагрузкой из 32 горутин.

### Исходная формулировка

**[Backoff в CAS]**: Если много горутин борются за один CAS, они будут тратить CPU впустую (Cache Line Ping-Ponging). Реализуй экспоненциальный backoff (через `runtime.Gosched()` или `time.Sleep`) внутри цикла CAS при неудаче. Оцени прирост пропускной способности.

## Теория

Когда десятки параллельных ядер процессора одновременно пытаются выполнить CAS над одной переменной, возникает явление **CAS Contention (или Cache Line Ping-Ponging)**:
* Ядро 0 считывает значение \(V\), начинает вычислять новое состояние.
* В этот момент Ядро 1 успевает выполнить CAS, инвалидируя строку кэша у всех остальных ядер.
* Ядро 0 получает промах, перезапускает цикл, генерирует новый запрос RFO (Request For Ownership).
* 32 ядра непрерывно пересылают одну 64-байтную кэш-линию по кольцевой шине процессора. Время на одну операцию возрастает с 5 нс до сотен наносекунд!

**Решение: Randomized Exponential Backoff (Экспоненциальный бэкофф с рандомизацией)**:
Если CAS провалился, горутина не пытается повторить операцию немедленно, а выдерживает паузу:
$$\text{Delay} = \text{Random}(0, \min(2^{\text{retries}}, \text{MaxDelay}))$$
Пауза разносит попытки разных ядер во времени, давая выигравшему ядру возможность завершить операцию без постоянных помех.

## Решение по шагам

1. Создайте структуру `OptimisticAccumulator` с полем `value atomic.Uint64`.
2. Реализуйте метод `AddNaive(delta uint64)` с немедленным повторением CAS.
3. Реализуйте метод `AddBackoff(delta uint64)` с экспоненциальным бэкоффом.
4. Запустите 32 параллельные горутины и замерьте время выполнения 1 000 000 операций каждым методом.
5. Сравните throughput и стабильность латентности.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type BackoffAccumulator struct {
	value atomic.Uint64
}

func (a *BackoffAccumulator) AddNaive(delta uint64) {
	for {
		cur := a.value.Load()
		if a.value.CompareAndSwap(cur, cur+delta) {
			return
		}
	}
}

func (a *BackoffAccumulator) AddBackoff(delta uint64) {
	retries := 0
	const maxBackoff = 64

	for {
		cur := a.value.Load()
		if a.value.CompareAndSwap(cur, cur+delta) {
			return
		}

		retries++
		// Адаптивная пауза: снижаем давление на шину кэша
		backoff := 1 << retries
		if backoff > maxBackoff {
			backoff = maxBackoff
		}
		// Рандомизация предотвращает синхронные повторы (thundering herd)
		spin := rand.Intn(backoff) + 1
		for s := 0; s < spin; s++ {
			_ = s
		}
		if retries > 10 {
			runtime.Gosched()
		}
	}
}

func main() {
	const workers = 32
	const opsPerWorker = 50_000

	// 1. Наивный CAS
	accNaive := &BackoffAccumulator{}
	var wg1 sync.WaitGroup
	wg1.Add(workers)
	start1 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg1.Done()
			for i := 0; i < opsPerWorker; i++ {
				accNaive.AddNaive(1)
			}
		}()
	}
	wg1.Wait()
	dNaive := time.Since(start1)

	// 2. CAS с Backoff
	accBackoff := &BackoffAccumulator{}
	var wg2 sync.WaitGroup
	wg2.Add(workers)
	start2 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg2.Done()
			for i := 0; i < opsPerWorker; i++ {
				accBackoff.AddBackoff(1)
			}
		}()
	}
	wg2.Wait()
	dBackoff := time.Since(start2)

	totalOps := float64(workers * opsPerWorker)
	fmt.Println("=== Исследование влияния Backoff при CAS Contention ===")
	fmt.Printf("Наивный CAS (шторм на шине памяти): %v (%.2f ns/op)\n",
		dNaive, float64(dNaive.Nanoseconds())/totalOps)
	fmt.Printf("CAS с адаптивным Backoff:           %v (%.2f ns/op)\n",
		dBackoff, float64(dBackoff.Nanoseconds())/totalOps)

	if dBackoff <= dNaive {
		fmt.Printf("Backoff уменьшает контеншн и стабилизирует конвейер ЦПУ!\n")
	}
}
```

ℹ️ Рандомизированный экспоненциальный бэкофф разряжает плотность CAS-запросов к шине памяти.

## Под капотом

Без бэкоффа все 32 ядра отправляют запросы `LOCK CMPXCHG` одновременно. Процессорный арбитр вынужден непрерывно блокировать и освобождать строки L3 кэша. С бэкоффом неудачные ядра засыпают на случайное число тактов, позволяя одному ядру совершить несколько успешных операций подряд без вытеснения своей кэш-линии.

## Подводные камни

1. Слишком большой начальный бэкофф: приводит к деградации при низкой конкуренции (Uncontended latency).
2. Вызов `time.Sleep`: системные таймеры ОС имеют дискретность в миллисекунды, что неприемлемо для микросекундных lock-free циклов.

## На собеседовании

Вопрос: «Как защитить lock-free структуры данных от деградации при лавинообразном росте параллелизма?». Ответ: использование рандомизированного экспоненциального бэкоффа (Jittered Backoff), шардирование (Striping), либо элиминация встречных запросов (Elimination Array).
