# Иерархия моделей упорядочивания памяти (Memory Ordering Models)

## Условие

Изучите различные уровни строгой и слабой согласованности памяти: Relaxed, Acquire-Release и Sequential Consistency (SC). Объясните, как барьеры памяти предотвращают переупорядочивание инструкций процессором и компилятором, и продемонстрируйте модель памяти Go.

### Исходная формулировка

**Memory ordering**: Изучите memory ordering:
* `atomic.Load` — relaxed (может reorder)
* `atomic.LoadAcquire` — acquire (не reorder после)
* `atomic.StoreRelease` — release (не reorder до)
* `atomic.CompareAndSwap` — sequential consistency

## Теория

В стандартах языков C++20 и Rust существует детальная шкала упорядочивания памяти (`std::memory_order`):

1. **memory_order_relaxed**:
   * Гарантирует только атомарность самой переменной.
   * **Разрешает любое переупорядочивание** окружающих операций чтения и записи! Подходит только для изолированных счетчиков метрик.
2. **memory_order_acquire / release**:
   * **Release (Store)**: никакие записи памяти ДО барьера не могут переместиться ПОСЛЕ него.
   * **Acquire (Load)**: никакие чтения памяти ПОСЛЕ барьера не могут переместиться ДО него.
   * Обеспечивает синхронизацию двух потоков (Producer-Consumer) с минимальными накладными расходами.
3. **memory_order_seq_cst (Последовательная консистентность)**:
   * Самый строгий уровень: существует единый глобальный порядок всех операций для всех ядер процессора.
   * Требует сброса Store Buffer и генерации тяжелых барьеров памяти (на x86: `MFENCE` или префикс `LOCK`).

**Модель памяти в Go**:
В языке Go сознательно **нет флагов relaxed/acquire/release** в публичном API пакета `sync/atomic`! Все атомарные операции в Go по умолчанию гарантируют **строгую последовательную согласованность (Sequential Consistency)** или строгий Acquire-Release, защищая разработчиков от микроархитектурных аномалий.

## Решение по шагам

1. Создайте программу с демонстрацией взаимной публикации двух переменных (Dekker/Peterson style).
2. Продемонстрируйте, как атомарные операции `Store` и `Load` предотвращают аномалию переупорядочивания.
3. Объясните поведение Store Buffer процессора.
4. Проверьте поведение с помощью детектора гонок `go test -race`.
5. Сформулируйте правила написания переносимого многопоточного кода на Go.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

// Демонстрация безопасного обмена флагами (Store-Load barrier)
type MemoryOrderingExperiment struct {
	x atomic.Int32
	y atomic.Int32
}

func main() {
	const iters = 100_000
	anomalies := 0

	fmt.Printf("Запуск эксперимента Memory Ordering на %d итераций...\n", iters)

	for i := 0; i < iters; i++ {
		exp := &MemoryOrderingExperiment{}
		var r1, r2 int32
		var wg sync.WaitGroup
		wg.Add(2)

		// Поток 1: пишет x, читает y
		go func() {
			defer wg.Done()
			exp.x.Store(1)
			r1 = exp.y.Load()
		}()

		// Поток 2: пишет y, читает x
		go func() {
			defer wg.Done()
			exp.y.Store(1)
			r2 = exp.x.Load()
		}()

		wg.Wait()

		// Если произошло переупорядочивание Store-Load (оба чтения опередили записи),
		// то оба потока прочитали 0 (r1 == 0 && r2 == 0).
		// В Go благодаря seq_cst атомикам это аппаратно невозможно!
		if r1 == 0 && r2 == 0 {
			anomalies++
		}
	}

	fmt.Printf("Аномалий переупорядочивания (r1=0, r2=0): %d\n", anomalies)
	fmt.Println("В Go все операции sync/atomic навязывают строгий барьер памяти (Sequential Consistency)!")
}
```

ℹ️ Операции sync/atomic в Go гарантируют строгую последовательную консистентность без аномалий переупорядочивания.

## Под капотом

В процессорах x86 без барьеров памяти Store Buffer может задержать сброс записи `exp.x.Store(1)`, позволив последующему чтению `exp.y.Load()` выполниться раньше. Инструкция `LOCK CMPXCHG` или `XCHG` в `sync/atomic` принудительно сбрасывает Store Buffer, гарантируя, что ни один процессор не увидит аномалию `r1=0 && r2=0`.

## Подводные камни

1. Предположение о наличии Relaxed атомиков в Go: некоторые разработчики думают, что `atomic.Load` бесплатнее `sync.Mutex`, но на слабых архитектурах (ARM) он все равно генерирует барьер памяти.
2. Неатомарные доступы к соседним переменным.

## На собеседовании

Вопрос: «Почему в C++ есть std::memory_order_relaxed, а в Go все атомики строгие?». Ответ: язык Go ставит во главу угла простоту, надежность и отсутствие скрытых багов многопоточности. Relaxed атомики в C++ требуют глубоких знаний микроархитектуры и часто приводят к трудноуловимым гонкам, тогда как строгая модель Go гарантирует корректность на любых процессорах.
