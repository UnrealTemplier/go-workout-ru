# Теория проблемы ABA в алгоритмах Compare-And-Swap

## Условие

Исследуйте фундаментальную теоретическую уязвимость алгоритмов на базе Compare-And-Swap — проблему ABA (The ABA Problem). Смоделируйте сценарий, при котором состояние переменной проходит путь A -> B -> A, заставляя поток ошибочно считать, что изменений в системе не происходило, и разберите различия между языками с ручным управлением памятью (C/C++) и Go с автоматическим Garbage Collector.

### Исходная формулировка

**Проблема ABA (Теория)**: Узнай, почему наивный CAS уязвим к ABA. Процесс 1 прочитал `A`, собирается записать `C`. Процесс 2 успел изменить `A` на `B`, а процесс 3 вернул обратно на `A`. Процесс 1 делает CAS, видит `A` (думает, что ничего не менялось) и пишет `C`. Состояние памяти сломано! (В Go с GC проблема ABA стоит не так остро, как в C/C++, но о ней нужно знать).

## Теория

Инструкция **Compare-And-Swap (CAS)** проверяет исключительно **равенство значений (или адресов указателей)**, а не историю их изменений:
$$\text{CAS}(V, A, C) \implies \text{true if } V == A$$

**Анатомия катастрофы ABA**:
1. Поток 1 считывает из переменной \(V\) значение \(A\) и начинает вычислять новое состояние \(C\) на основе прочитанного контекста \(A\).
2. Поток 1 вытесняется операционной системой.
3. Поток 2 изменяет значение \(V\) с \(A\) на \(B\).
4. Поток 3 изменяет значение \(V\) обратно с \(B\) на \(A\).
5. Поток 1 просыпается и выполняет \(\text{CAS}(V, A, C)\).
6. Процессор видит, что \(V == A\), и успешно записывает \(C\)!
7. **Катастрофа**: Поток 1 ошибочно предположил, что мир не менялся, тогда как все связанные с \(A\) внутренние структуры данных уже были модифицированы или уничтожены!

**Почему в C/C++ ABA фатальна, а в Go смягчена?**
* В C/C++ узлы освобождаются вручную через `free()`. Когда Поток 2 удаляет узел \(A\), аллокатор `glibc malloc` помещает адрес узла \(A\) в свой `free list`. При следующем вызове `malloc()` узел \(A\) перевыделяется под новый объект и возвращается в стек по **тому же самому адресу**! Поток 1 выполняет CAS по старому указателю, что приводит к разрыву связных списков и порче памяти (`use-after-free`).
* В Go работает **Tracing Garbage Collector**: пока Поток 1 удерживает указатель на узел \(A\) в стеке горутины, объект \(A\) не может быть уничтожен и его адрес памяти не может быть переиспользован для другого объекта!

## Решение по шагам

1. Создайте модель учетной записи `AccountState` с балансом и версией.
2. Продемонстрируйте сценарий, когда баланс временно менялся с \(100 \to 200 \to 100\).
3. Покажите, почему наивный CAS по балансу пропустил транзакции.
4. Продемонстрируйте защиту через монотонный счетчик транзакций.
5. Сформулируйте правила устойчивости к логическому ABA в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
)

// Моделирование логической ABA проблемы
type BankAccount struct {
	balance atomic.Int64
}

// Защищенный счетчик версий: баланс + монотонный счетчик транзакций
type VersionedAccount struct {
	state atomic.Uint64 // [32 бита: версия] | [32 бита: баланс]
}

func pack(balance int32, version uint32) uint64 {
	return (uint64(version) << 32) | uint64(uint32(balance))
}

func unpack(v uint64) (balance int32, version uint32) {
	return int32(v & 0xFFFFFFFF), uint32(v >> 32)
}

func main() {
	fmt.Println("=== Моделирование уязвимости ABA ===")

	// 1. Наивный баланс: подвержен логическому ABA
	account := &BankAccount{}
	account.balance.Store(100) // Состояние A

	// Поток 1 прочитал 100 и заснул
	observed := account.balance.Load()

	// Параллельные транзакции изменяют состояние: 100 -> 500 (B) -> 100 (A)
	account.balance.Store(500)
	account.balance.Store(100)

	// Поток 1 проснулся и делает CAS(100 -> 50)
	// CAS проходит успешно, хотя контекст промежуточных транзакций потерян!
	success := account.balance.CompareAndSwap(observed, 50)
	fmt.Printf("Наивный CAS(100 -> 50) успешен: %v (Баланс: %d, ABA не замечен!)\n",
		success, account.balance.Load())

	// 2. Версионированный баланс: иммунитет к ABA
	vAcc := &VersionedAccount{}
	vAcc.state.Store(pack(100, 1)) // Баланс 100, Версия 1

	vObserved := vAcc.state.Load()
	bal1, ver1 := unpack(vObserved)

	// Промежуточные транзакции инкрементируют версию
	vAcc.state.Store(pack(500, ver1+1))
	vAcc.state.Store(pack(100, ver1+2))

	// Поток 1 пытается применить CAS
	vSuccess := vAcc.state.CompareAndSwap(vObserved, pack(50, ver1+3))
	fmt.Printf("Версионированный CAS успешен: %v (ABA обнаружен, транзакция отклонена!)\n",
		vSuccess)

	curBal, curVer := unpack(vAcc.state.Load())
	fmt.Printf("Текущий баланс: %d, Версия: %d (поток защищен от скрытых изменений!)\n",
		curBal, curVer)
	_ = bal1
}
```

ℹ️ Упаковка счетчика версий в 64-битное число полностью предотвращает проблему ABA.

## Под капотом

В 64-битном числе `uint64` старшие 32 бита отводятся под монотонно возрастающий счетчик версий (Sequence / Tag). Даже если младшие 32 бита (баланс) вернулись в исходное состояние \(100 \to 500 \to 100\), старшие биты версии увеличились с 1 до 3. Инструкция `CMPXCHGQ` проверяет все 64 бита одновременно, благодаря чему несовпадение версии предотвращает ложное срабатывание CAS.

## Подводные камни

1. Переполнение счетчика версий: при 16-битном счетчике переполнение может произойти через 65536 операций. 32 или 64-битные версии практически бесконечны.
2. Неполная упаковка данных: если данные превышают 32 бита, упаковка в один `uint64` невозможна (требуется Double-Word CAS или структуры с указателями).

## На собеседовании

Вопрос на собеседовании: «Почему в lock-free очередях и стеках на C++ используют Hazard Pointers или Tagged Pointers, а в Go разработчики часто обходятся обычным CAS?». Ответ: в C++ освобожденная память немедленно переиспользуется аллокатором (ABA на указателях). В Go Tracing Garbage Collector удерживает узел в живых, пока на него ссылается хотя бы одна локальная переменная горутины, устраняя аппаратную проблему переиспользования указателей.
