# Спинлок с экспоненциальным Backoff (Exponential Backoff Spinlock)

## Условие

Реализуйте высокоэффективный Spinlock на atomic.Bool с адаптивной экспоненциальной задержкой (Exponential Backoff). Покажите, как увеличение паузы между неудачными попытками CAS снижает температуру шины памяти и предотвращает троттлинг процессора.

### Исходная формулировка

**Spin-Lock с Backoff**: Напиши свой мьютекс поверх `atomic.Bool`. В методе `Lock()` крути бесконечный цикл `CompareAndSwap(false, true)`. Чтобы не сжечь процессор в 100% при конкуренции, добавь `runtime.Gosched()` (отдать контекст) или адаптивный бэкофф (пустой цикл `for i:=0; i<10; i++`).

## Теория

Примитивный спинлок выполняет CAS непрерывно:
```go
for !atomic.CompareAndSwap(target, 0, 1) {}
```
Если 16 ядер одновременно крутятся в таком цикле, каждое ядро генерирует до 50 000 000 обращений к шине памяти в секунду. Протокол MESI захлебывается, энергопотребление процессора подскакивает до максимума, и включается аппаратный троттлинг частоты (CPU Throttling).

**Алгоритм экспоненциального Backoff (Exponential Backoff)**:
1. При первой неудаче поток делает короткую паузу (например, 1 пустая итерация).
2. При каждой следующей неудаче время паузы **удваивается**:
   $$\text{Backoff}_{k+1} = \min(\text{Backoff}_k \times 2, \text{MaxBackoff})$$
3. Внутри короткой паузы используется холостой спин-цикл с процессорной инструкцией `PAUSE` (или пустой цикл).
4. Если число попыток превышает порог (например, 32 итерации), поток вызывает `runtime.Gosched()`, отдавая квант времени планировщику Go.

Это разряжает очередь обращений к шине памяти и ускоряет завершение критической секции потоком-владельцем.

## Решение по шагам

1. Создайте структуру `BackoffSpinlock` с `flag atomic.Bool`.
2. Реализуйте метод `Lock()` с переменной `backoff := 1`.
3. Внутри цикла ожидания выполняйте пустой цикл от 0 до `backoff` и удваивайте `backoff`.
4. При превышении лимита вызывайте `runtime.Gosched()`.
5. Сравните с «наивным» спинлоком под нагрузкой из 16 горутин.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type BackoffSpinlock struct {
	locked atomic.Bool
}

func (s *BackoffSpinlock) Lock() {
	backoff := 1
	const maxBackoff = 64

	for {
		// Fast Path: попытка мгновенного захвата
		if s.locked.CompareAndSwap(false, true) {
			return
		}

		// Адаптивный Backoff: разгружаем шину памяти
		for i := 0; i < backoff; i++ {
			// В ассемблере здесь PAUSE; в Go имитируем короткий холостой спин
			_ = i
		}

		if backoff < maxBackoff {
			backoff <<= 1 // экспоненциальный рост
		} else {
			// При сильном контеншне отдаем контекст горутине-владельцу
			runtime.Gosched()
		}
	}
}

func (s *BackoffSpinlock) Unlock() {
	s.locked.Store(false)
}

func main() {
	var spin BackoffSpinlock
	var sharedCounter int
	const workers = 16
	const iters = 100_000

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				spin.Lock()
				sharedCounter++
				spin.Unlock()
			}
		}()
	}
	wg.Wait()
	cost := time.Since(start)

	expected := workers * iters
	fmt.Printf("BackoffSpinlock: результат = %d (ожидалось %d)\n", sharedCounter, expected)
	fmt.Printf("Время работы с адаптивным бэкоффом: %v\n", cost)
}
```

ℹ️ Экспоненциальный бэкофф защищает кэш-шину процессора от перегрузки во время ожидания замка.

## Под капотом

В архитектуре x86 холостой спин с задержкой дает процессору возможность применить технику Store-Forwarding и освободить буферы RFO. В планировщике Go `sync.Mutex` использует функцию `runtime.procyield(cycles)`, которая напрямую вызывает инструкцию `PAUSE`. Инструкция `PAUSE` снижает энергопотребление ядра и предотвращает сброс спекулятивного конвейера конвейера (Pipeline Flush) при выходе из цикла.

## Подводные камни

1. Слишком большой `MaxBackoff`: приводит к неоправданным паузам, если блокировка освобождается быстро.
2. Отсутствие `runtime.Gosched()` на однопроцессорных машинах: приводит к полному зависанию (Live-lock).

## На собеседовании

Вопрос: «Что такое инструкция PAUSE в ассемблере x86 и почему она критична для спинлоков?». Ответ: `PAUSE` введена в Pentium 4. Она задерживает выполнение следующей итерации спин-цикла на фиксированное число тактов (~10–40 тактов в зависимости от поколения CPU), снимая нагрузку с шины когерентности памяти и защищая процессор от ложных срабатываний предсказателя переходов.
