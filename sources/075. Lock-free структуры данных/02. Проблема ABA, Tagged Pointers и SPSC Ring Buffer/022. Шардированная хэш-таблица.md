# Шардированная хэш-таблица и сравнение с lock-free мапами

## Условие

Реализуйте шардированную хэш-таблицу (Sharded Concurrent Map) на 256 шардов с независимыми sync.RWMutex. Докажите, почему шардирование радикально снижает contention, и объясните, почему полностью lock-free хэш-таблицы (как в Java ConcurrentHashMap) редки в Go из-за отсутствия аппаратной транзакционной памяти (HTM).

### Исходная формулировка

**Lock-free Hash Table (sharded).**: Реализуйте массив из 256 `sync.RWMutex` или `atomic.Pointer` на bucket. Покажите, что sharding уменьшает contention. Объясните, почему полностью lock-free hash table (например, Java `ConcurrentHashMap`) в Go сложна из-за отсутствия transactional memory.

## Теория

Создание полностью **Lock-Free Hash Table** (без мьютексов вообще) — одна из сложнейших задач компьютерных наук:
* Вставка нового ключа требует создания бакета.
* Изменение существующего бакета требует перелинковки связного списка или открытой адресации.
* При превышении Load Factor требуется **рехеширование (Resizing/Rehash)**: создание массива в 2 раза большего размера и миграция миллионов ключей. Сделать рехеширование Lock-Free без блокировки читателей требует сложных алгоритмов (Split-Ordered Lists Клиффа Клика / Cliff Click Lock-Free Hash Map).

В языке Go стандартным промышленным решением является **Шардирование (Striped / Sharded Map)**:
* Таблица делится на \(256\) независимых шардов.
* Каждый шард содержит обычную карту `map[K]V` и свой локальный `sync.RWMutex`.
* Хэш ключа определяет номер шарда: \(ShardID = Hash(Key) \pmod{256}\).
* Вероятность коллизии двух параллельных потоков на одном шарде составляет всего \(\frac{1}{256} \approx 0.39\%\), что практически полностью ликвидирует Lock Contention!

## Решение по шагам

1. Создайте структуру `ConcurrentShardedMap` с массивом из 256 шардов.
2. Реализуйте хэш-функцию FNV-1a для быстрого распределения строковых ключей.
3. Реализуйте методы `Get(key string)` и `Set(key string, val any)`.
4. Запустите 32 параллельные горутины, выполняющие чтение и запись.
5. Сравните пропускную способность с монолитной мапой, защищенной единым мьютексом.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sync"
	"time"
)

const ShardsCount = 256
const ShardMask = ShardsCount - 1

type MapShard struct {
	mu   sync.RWMutex
	data map[string]int
}

type ShardedMap struct {
	shards [ShardsCount]MapShard
}

func NewShardedMap() *ShardedMap {
	m := &ShardedMap{}
	for i := 0; i < ShardsCount; i++ {
		m.shards[i].data = make(map[string]int)
	}
	return m
}

func (m *ShardedMap) getShard(key string) *MapShard {
	h := fnv.New32a()
	h.Write([]byte(key))
	idx := h.Sum32() & ShardMask
	return &m.shards[idx]
}

func (m *ShardedMap) Get(key string) (int, bool) {
	shard := m.getShard(key)
	shard.mu.RLock()
	val, ok := shard.data[key]
	shard.mu.RUnlock()
	return val, ok
}

func (m *ShardedMap) Set(key string, val int) {
	shard := m.getShard(key)
	shard.mu.Lock()
	shard.data[key] = val
	shard.mu.Unlock()
}

func main() {
	sm := NewShardedMap()
	const workers = 32
	const opsPerWorker = 50_000

	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		wID := w
		go func() {
			defer wg.Done()
			for i := 0; i < opsPerWorker; i++ {
				key := fmt.Sprintf("user_session_%d_%d", wID, i%100)
				if i%10 == 0 {
					sm.Set(key, i)
				} else {
					_, _ = sm.Get(key)
				}
			}
		}()
	}
	wg.Wait()
	cost := time.Since(start)

	totalOps := workers * opsPerWorker
	fmt.Printf("ShardedMap: выполнено %d смешанных операций за %v (%.2f млн ops/sec)\n",
		totalOps, cost, float64(totalOps)/cost.Seconds()/1e6)
}
```

ℹ️ Шардирование на 256 корзин устраняет Lock Contention на 99.6%.

## Под капотом

В `ShardedMap` операция блокировки затрагивает только 1 из 256 мьютексов. Если 32 ядра обращаются к случайным ключам, среднее число потоков на один шард составляет \(32 / 256 = 0.125\). Это означает, что почти всегда мьютекс свободен, и `shard.mu.Lock()` захватывается мгновенно за 1 такт ЦПУ без переключения контекста.

## Подводные камни

1. Операция подсчета общего размера `Len()`: требует захвата `RLock()` на ВСЕ 256 шардов одновременно, что на время блокирует запись во всю таблицу.
2. Неравномерное распределение ключей (Hot Shard): если ключи хэшируются неудачно, один шард может стать узким местом.

## На собеседовании

Вопрос: «Почему в Go не реализовали полностью Lock-Free ConcurrentHashMap, как в Java?». Ответ: Java ConcurrentHashMap использует сложный массив бакетов с CAS на узлы и синхронизацию сегментов. В Go стандартная `sync.Map` оптимизирована под конкретный сценарий (append-only или стабильный набор ключей с частым чтением), а для произвольных нагрузок шардированная мапа с RWMutex на практике работает быстрее и проще в сопровождении.
