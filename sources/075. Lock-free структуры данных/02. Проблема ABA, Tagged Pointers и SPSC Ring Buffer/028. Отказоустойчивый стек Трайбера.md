# Отказоустойчивый стек Трайбера на atomic.Pointer[Node[T]]

## Условие

Реализуйте потокобезопасный LIFO-стек Трайбера без мьютексов с использованием обобщенного типа atomic.Pointer[Node[T]]. Продемонстрируйте корректность параллельной работы при экстремальном количестве горутин (1000 воркеров) под стресс-нагрузкой.

### Исходная формулировка

**Lock-Free Treiber Stack**: Реализуй потокобезопасный LIFO-стек без мьютексов. Используй `atomic.Pointer[Node]` (появился в Go 1.19). В методе `Push` создай новую ноду, сделай `new.next = head`, а затем попытайся атомарно подменить `head` через CAS. Если не вышло — повторяй в цикле.

## Теория

Стек Трайбера на базе `atomic.Pointer[Node[T]]` (Go 1.19+) — один из самых надежных и идиоматичных примеров lock-free структур данных:
* Не требует небезопасного пакета `unsafe`.
* Обеспечивает полную типобезопасность времени компиляции.
* Не содержит блокировок и не вызывает системных вызовов ОС.

**Математическое свойство Lock-Freedom**:
В любой момент времени среди \(N\) горутин, выполняющих `Push` или `Pop`:
* Хотя бы одна горутина успешно завершает операцию за \(O(1)\) шагов.
* Система в целом никогда не может войти в дедлок (Deadlock-Free).
* Никакая горутина не может быть заблокирована аварийно завершившимся соседним потоком.

## Решение по шагам

1. Объявите узел `StackNode[T] { val T; next *StackNode[T] }`.
2. Объявите `TreiberStack[T]` с `head atomic.Pointer[StackNode[T]]`.
3. Реализуйте метод `Push(v T)`.
4. Реализуйте метод `Pop() (T, bool)`.
5. Запустите 1000 горутин, одновременно выполняющих по 5000 операций Push и Pop.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type StackNode[T any] struct {
	val  T
	next *StackNode[T]
}

type TreiberStack[T any] struct {
	head atomic.Pointer[StackNode[T]]
}

func (s *TreiberStack[T]) Push(v T) {
	newNode := &StackNode[T]{val: v}
	for {
		head := s.head.Load()
		newNode.next = head
		if s.head.CompareAndSwap(head, newNode) {
			return
		}
	}
}

func (s *TreiberStack[T]) Pop() (T, bool) {
	for {
		head := s.head.Load()
		if head == nil {
			var zero T
			return zero, false
		}
		if s.head.CompareAndSwap(head, head.next) {
			return head.val, true
		}
	}
}

func main() {
	stack := &TreiberStack[int]{}
	const workers = 500
	const iters = 2000

	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	// Параллельное наполнение
	for w := 0; w < workers; w++ {
		go func(id int) {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				stack.Push(id*iters + i)
			}
		}(w)
	}
	wg.Wait()

	// Параллельное извлечение
	var popSuccess atomic.Int64
	wg.Add(workers)
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for {
				_, ok := stack.Pop()
				if ok {
					popSuccess.Add(1)
				} else {
					if popSuccess.Load() >= int64(workers*iters) {
						break
					}
				}
			}
		}()
	}
	wg.Wait()

	cost := time.Since(start)
	total := workers * iters
	fmt.Printf("TreiberStack: успешно обработано %d Push/Pop операций за %v (%.2f млн ops/sec)\n",
		total, cost, float64(total*2)/cost.Seconds()/1e6)
}
```

ℹ️ Идиоматичная реализация стека Трайбера на atomic.Pointer[Node[T]].

## Под капотом

В цикле `Push` операция `newNode.next = head` выполняется до атомарного `CompareAndSwap`. Это гарантирует, что к моменту публикации `head` новый узел уже полностью инициализирован в памяти. Даже если поток прервется между инициализацией и CAS, структура данных останется нетронутой.

## Подводные камни

1. Высокая нагрузка на Garbage Collector: частые аллокации узлов в куче при миллионах Push/Pop операций в секунду.
2. Нарушение LIFO при конкурентном опустошении.

## На собеседовании

Вопрос: «Почему Treiber Stack не масштабируется на 64+ ядрах?». Ответ: из-за единой точки синхронизации — указателя `head`. Все ядра процессора непрерывно соревнуются за одну кэш-линию вершины стека, что приводит к лавинообразным повторным попыткам CAS (CAS Contention). Для масштабирования на сотни ядер применяют алгоритм Elimination Backoff Stack (где встречные Push и Pop обмениваются данными напрямую через массив элиминации).
