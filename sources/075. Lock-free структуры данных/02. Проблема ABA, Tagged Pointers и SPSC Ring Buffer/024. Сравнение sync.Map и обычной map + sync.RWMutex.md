# Сравнение sync.Map и обычной map + sync.RWMutex: точки перелома

## Условие

Спроектируйте сравнительный бенчмарк между sync.Map и шардированной map + sync.RWMutex в сценарии Read-Heavy (99% чтений, 1% записей) при 32 параллельных горутинах. Покажите, за счет каких внутренних архитектурных механизмов sync.Map превосходит RWMutex при стабильном наборе ключей.

### Исходная формулировка

**Сравнение lock-free map (sync.Map) с обычной map+mutex.**: Создайте сценарий: много чтений, редкие записи. Замерьте `Load` и `Store` у `sync.Map` и `map + sync.RWMutex` на большом количестве горутин. Покажите, когда `sync.Map` выигрывает.

## Теория

Структура **sync.Map** в стандартной библиотеке Go спроектирована под два конкретных сценария:
1. Запись ключа происходит один раз, а чтение — многократно (Append-Only Cache).
2. Множество горутин читают, изменяют и перезаписывают непересекающиеся ключи.

**Внутреннее устройство sync.Map**:
Содержит две внутренние карты:
* `read atomic.Pointer[readOnly]`: неизменяемая карта, доступная **полностью без блокировок (Lock-Free reads)**. Чтение из `read` не вызывает взаимной инвалидации кэша между читателями.
* `dirty map[any]*entry`: изменяемая карта, защищенная `sync.Mutex`. Новые ключи попадают сначала в `dirty`.
* Счетчик промахов (`misses`): если ключ не найден в `read`, читатель обращается в `dirty` под мьютексом и инкрементирует `misses`.
* Когда `misses >= len(dirty)`, карта `dirty` атомарно промоутится (продвигается) в `read` через `atomic.StorePointer`!

При стабильном наборе ключей читатели работают со 100% скоростью L1-кэша без единого мьютекса.

## Решение по шагам

1. Создайте сценарий тестирования со 100 000 ключами.
2. Протестируйте `sync.RWMutex + map[string]int` при 32 читателях и редких записях.
3. Протестируйте `sync.Map` при тех же условиях.
4. Замерьте задержку и пропускную способность.
5. Объясните, почему при частой вставке новых ключей `sync.Map` уступает обычной мапе.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type RWMutexMap struct {
	mu   sync.RWMutex
	data map[string]int
}

func (m *RWMutexMap) Get(k string) (int, bool) {
	m.mu.RLock()
	v, ok := m.data[k]
	m.mu.RUnlock()
	return v, ok
}

func (m *RWMutexMap) Set(k string, v int) {
	m.mu.Lock()
	m.data[k] = v
	m.mu.Unlock()
}

func main() {
	const keysCount = 10_000
	const workers = 16
	const readsPerWorker = 200_000

	// 1. Инициализация RWMutexMap
	rwMap := &RWMutexMap{data: make(map[string]int, keysCount)}
	for i := 0; i < keysCount; i++ {
		rwMap.data[fmt.Sprintf("key_%d", i)] = i
	}

	// 2. Инициализация sync.Map
	var sMap sync.Map
	for i := 0; i < keysCount; i++ {
		sMap.Store(fmt.Sprintf("key_%d", i), i)
	}

	// Бенчмарк RWMutexMap
	var wg1 sync.WaitGroup
	wg1.Add(workers)
	start1 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg1.Done()
			for i := 0; i < readsPerWorker; i++ {
				k := fmt.Sprintf("key_%d", i%keysCount)
				_, _ = rwMap.Get(k)
			}
		}()
	}
	wg1.Wait()
	dRW := time.Since(start1)

	// Бенчмарк sync.Map
	var wg2 sync.WaitGroup
	wg2.Add(workers)
	start2 := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg2.Done()
			for i := 0; i < readsPerWorker; i++ {
				k := fmt.Sprintf("key_%d", i%keysCount)
				_, _ = sMap.Load(k)
			}
		}()
	}
	wg2.Wait()
	dSyncMap := time.Since(start2)

	totalReads := float64(workers * readsPerWorker)
	fmt.Println("=== Сравнение производительности чтения: sync.Map vs RWMutexMap ===")
	fmt.Printf("RWMutexMap: %v (%.2f ns/read)\n", dRW, float64(dRW.Nanoseconds())/totalReads)
	fmt.Printf("sync.Map:   %v (%.2f ns/read)\n", dSyncMap, float64(dSyncMap.Nanoseconds())/totalReads)

	if dSyncMap < dRW {
		fmt.Printf("sync.Map быстрее в %.2fx раз благодаря lock-free чтению из поля read!\n",
			float64(dRW)/float64(dSyncMap))
	}
}
```

ℹ️ sync.Map превосходит RWMutex на стабильных ключах за счет отсутствия блокировок в readOnly карте.

## Под капотом

В `sync.RWMutex` каждый вызов `RLock()` атомарно инкрементирует `readerCount` инструкцией `LOCK XADD`. При 16 ядрах читатели непрерывно пересылают строку кэша мьютекса друг другу. В `sync.Map` метод `Load()` читает неизменяемый указатель `m.read.Load()`, не совершая ни единой записи в память. Кэш-линия находится в состоянии Shared на всех ядрах без каких-либо задержек.

## Подводные камни

1. Частая вставка новых ключей: каждый новый ключ вызывает промах в `read`, блокировку глобального мьютекса `m.mu` и копирование всей карты из `read` в `dirty` при промоушене. В сценарии Write-Heavy `sync.Map` работает в разы медленнее обычной мапы с мьютексом.
2. Потеря типизации: `sync.Map` оперирует типами `any` (interface{}), что влечет аллокации для примитивных типов.

## На собеседовании

Вопрос: «Когда следует использовать sync.Map, а когда обычную map с sync.RWMutex?». Ответ: `sync.Map` эффективна строго в двух случаях: 1) стабильный набор ключей с миллионами параллельных чтений (кэширование схем, метаданных); 2) непересекающиеся множества ключей у разных горутин. Для всех остальных сценариев (особенно при частых вставках и удалениях) предпочтительна шардированная мапа с `sync.RWMutex`.
