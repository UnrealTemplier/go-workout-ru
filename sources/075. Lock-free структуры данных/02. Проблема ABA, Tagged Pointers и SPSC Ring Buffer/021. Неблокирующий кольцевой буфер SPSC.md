# Неблокирующий кольцевой буфер SPSC: строгий порядок памяти

## Условие

Реализуйте кольцевой буфер SPSC (Single-Producer Single-Consumer) фиксированного размера с соблюдением строгого порядка памяти (Memory Ordering). Продемонстрируйте инвариант: продюсер обязан записать полезные данные ДО инкремента tail, а консьюмер обязан проверить tail ДО чтения ячейки данных.

### Исходная формулировка

**[Ring Buffer (SPSC)]**: Реализуй неблокирующий Ring Buffer (Fixed-size queue) для Single Producer, Single Consumer. Используй `atomic.LoadUint64` для `head` и `tail`. *Ключевой момент:* продюсер пишет данные *до* инкремента `tail`, а консьюмер проверяет `tail` *до* чтения данных (Memory Ordering).

## Теория

При проектировании Lock-Free структур данных без использования мьютексов ключевое значение имеет **инвариант публикации данных (Data Publication Invariant)**.

В алгоритме SPSC кольцевого буфера:
1. **Продюсер**:
   * Сначала вычисляет свободное место: \(\text{Free} = N - (Head - Tail)\).
   * Записывает полезные данные в ячейку: `buffer[head & Mask] = data`.
   * **Только после этого** публикует новый индекс: `head.Store(head + 1)`.
   * Если бы процессор переупорядочил эти действия (Store-Store Reordering), консьюмер прочитал бы полузаписанный слот.
2. **Консьюмер**:
   * Сначала проверяет индекс публикации: `h := head.Load()`.
   * Если \(Tail < h\), читает данные из слота: `val := buffer[tail & Mask]`.
   * **Только после этого** освобождает слот: `tail.Store(tail + 1)`.
   * Если бы консьюмер сначала обновил `tail`, продюсер мог бы перезаписать еще не прочитанный слот на следующем обороте кольца!

## Решение по шагам

1. Создайте структуру `StrictSPSC[T]` с емкостью 1024 элемента.
2. Реализуйте метод `Push(val T) bool` со строгим порядком: запись данных -> Release store `head`.
3. Реализуйте метод `Pop() (T, bool)` со строгим порядком: Acquire load `head` -> чтение данных -> Release store `tail`.
4. Запустите 5 000 000 параллельных итераций передачи между двумя горутинами.
5. Проверьте строгую сохранность порядка элементов (FIFO).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

const RingCap = 512
const RingMask = RingCap - 1

type StrictSPSC struct {
	head atomic.Uint64
	_    [56]byte
	tail atomic.Uint64
	_    [56]byte
	data [RingCap]int64
}

func (r *StrictSPSC) Push(val int64) bool {
	h := r.head.Load()
	t := r.tail.Load()

	if h-t >= RingCap {
		return false // Буфер полон
	}

	// 1. Запись данных в массив
	r.data[h&RingMask] = val

	// 2. Публикация нового head (Release Barrier)
	// Гарантирует, что r.data[h] физически видна до обновления head
	r.head.Store(h + 1)
	return true
}

func (r *StrictSPSC) Pop() (int64, bool) {
	t := r.tail.Load()
	h := r.head.Load()

	if t == h {
		return 0, false // Буфер пуст
	}

	// 1. Чтение данных из слота (Acquire Barrier от Load head)
	val := r.data[t&RingMask]

	// 2. Освобождение слота для продюсера (Release Barrier)
	r.tail.Store(t + 1)
	return val, true
}

func main() {
	rb := &StrictSPSC{}
	const total = 5_000_000

	var wg sync.WaitGroup
	wg.Add(2)
	start := time.Now()

	// Producer
	go func() {
		defer wg.Done()
		for i := int64(1); i <= total; i++ {
			for !rb.Push(i) {
				runtime.Gosched()
			}
		}
	}()

	// Consumer с валидацией непрерывной последовательности
	go func() {
		defer wg.Done()
		expected := int64(1)
		for expected <= total {
			val, ok := rb.Pop()
			if ok {
				if val != expected {
					panic(fmt.Sprintf("CORRUPTED FIFO ORDER: got %d, expected %d", val, expected))
				}
				expected++
			} else {
				runtime.Gosched()
			}
		}
	}()

	wg.Wait()
	duration := time.Since(start)

	fmt.Printf("StrictSPSC: передано %d сообщений за %v (%.2f млн msg/sec)\n",
		total, duration, float64(total)/duration.Seconds()/1e6)
	fmt.Println("Инвариант строгой последовательности и Memory Ordering соблюден на 100%!")
}
```

ℹ️ Соблюдение инварианта порядка записи и чтения предотвращает гонки данных в SPSC буфере.

## Под капотом

В Go рантайме вызовы `atomic.Store` и `atomic.Load` создают аппаратно-зависимые барьеры памяти (Memory Fences). На x86 инструкции `MOV` достаточны благодаря модели TSO. На ARM64 компилятор генерирует инструкции `LDAR` (Load-Acquire) и `STLR` (Store-Release), заставляя процессор синхронизировать кэши ядер строго в заданном порядке.

## Подводные камни

1. Забытый барьер при оптимизации: попытка убрать `atomic.Store` в пользу обычного присваивания приведет к чтению устаревших данных на многоядерных машинах.
2. Недостаточный размер кольцевого буфера: буфер должен вмещать пиковые всплески трафика во избежание простоя продюсера.

## На собеседовании

Вопрос: «Что произойдет, если в SPSC кольцевом буфере продюсер сначала обновит head, а затем запишет данные в массив?». Ответ: состояние гонки (Data Race) — консьюмер на другом ядре увидит новый `head`, немедленно прочитает ячейку массива и получит неинициализированное значение или мусор из предыдущего цикла буфера.
