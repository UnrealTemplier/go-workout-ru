# Управление памятью в Lock-Free структурах: упрощенный Epoch-Based Reclamation

## Условие

Изучите проблему безопасного освобождения памяти в неблокирующих структурах данных (Memory Reclamation Problem). Реализуйте упрощенный механизм Epoch-Based Reclamation (EBR) со списком отложенного удаления (Retired List) и эпохальными счетчиками. Объясните, почему автоматический GC в Go решает эту задачу из коробки, тогда как в C++/Rust требуются Hazard Pointers или EBR.

### Исходная формулировка

**Epoch-Based Reclamation (упрощённый).**: Для lock-free stack добавьте механизм: при `Pop` не удаляйте узел, а помещайте в локальный «retired list». Периодически (каждые N операций) освобождайте узлы, которые гарантированно не видны другими goroutine (через глобальный epoch counter). Объясните, почему Go GC делает это за вас, но в C/C++ без EBRM/HP — утечка или use-after-free.

## Теория

В языках с ручным управлением памятью (C/C++, Rust без GC) самая сложная проблема lock-free алгоритмов — **Memory Reclamation (Безопасное освобождение памяти)**:
* Если поток 1 извлекает узел \(X\) из очереди через `Pop()`, он не может сразу вызвать `free(X)`.
* В этот же момент параллельный поток 2 мог успеть прочитать указатель `curr = X` и собирается обратиться к его полям `X.val` или `X.next`!
* Мгновенное освобождение вызовет крах программы (`Use-After-Free` / `Segmentation Fault`).

**Механизм Epoch-Based Reclamation (EBR / RCU-style)**:
1. Поддерживается глобальный счетчик эпох `GlobalEpoch` (0, 1, 2).
2. Каждый поток при входе в критическую секцию регистрирует свою локальную эпоху: `LocalEpoch[threadID] = GlobalEpoch`.
3. Узлы, удаленные из структуры, помещаются в локальный список «отставных» узлов (**Retired List**) с пометкой текущей эпохи.
4. Глобальная эпоха продвигается (\(E \to E+1\)), когда все активные потоки покинули предыдущую эпоху.
5. Физическое освобождение (`free`) узлов эпохи \(E-2\) выполняется только тогда, когда в системе гарантированно нет ни одного потока, способного удерживать ссылку на эти узлы!

В языке Go сборщик мусора выполняет эту работу аппаратно и прозрачно для программиста.

## Решение по шагам

1. Создайте структуру `RetiredNode` со значением и эпохой удаления.
2. Создайте класс `EpochManager` с глобальной эпохой и срезом активных потоков.
3. Реализуйте метод `EnterEpoch(threadID int)` и `LeaveEpoch(threadID int)`.
4. Реализуйте метод `Retire(node *RetiredNode)` и `TryReclaim()`.
5. Смоделируйте безопасную очистку узлов после завершения работы всех читателей.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type RetiredNode struct {
	Value int
	Epoch uint64
}

type SimpleEBR struct {
	globalEpoch atomic.Uint64
	activeEpoch [8]atomic.Uint64 // по числу потоков
	retired     []*RetiredNode
	mu          sync.Mutex
}

func NewSimpleEBR() *SimpleEBR {
	return &SimpleEBR{}
}

func (e *SimpleEBR) Enter(threadID int) {
	// Поток объявляет, что находится в текущей глобальной эпохе
	current := e.globalEpoch.Load()
	e.activeEpoch[threadID].Store(current)
}

func (e *SimpleEBR) Leave(threadID int) {
	// Поток покинул критическую секцию (0 = неактивен)
	e.activeEpoch[threadID].Store(0)
}

func (e *SimpleEBR) Retire(val int) {
	e.mu.Lock()
	defer e.mu.Unlock()
	current := e.globalEpoch.Load()
	e.retired = append(e.retired, &RetiredNode{Value: val, Epoch: current})
}

func (e *SimpleEBR) AdvanceAndReclaim() int {
	e.mu.Lock()
	defer e.mu.Unlock()

	cur := e.globalEpoch.Load()
	// Проверяем, есть ли потоки в старых эпохах
	for i := 0; i < len(e.activeEpoch); i++ {
		tEpoch := e.activeEpoch[i].Load()
		if tEpoch != 0 && tEpoch < cur {
			// Есть отстающие потоки: удалять нельзя!
			return 0
		}
	}

	// Продвигаем эпоху
	e.globalEpoch.Add(1)

	// Безопасное освобождение узлов, удаленных до текущей эпохи
	reclaimed := 0
	var remaining []*RetiredNode
	for _, node := range e.retired {
		if node.Epoch < cur {
			// Узел физически безопасен для уничтожения
			reclaimed++
		} else {
			remaining = append(remaining, node)
		}
	}
	e.retired = remaining
	return reclaimed
}

func main() {
	ebr := NewSimpleEBR()

	fmt.Println("=== Демонстрация Epoch-Based Reclamation (EBR) ===")
	// Поток 0 читает структуру в эпохе 0
	ebr.Enter(0)
	fmt.Printf("Поток 0 вошел в эпоху %d\n", ebr.globalEpoch.Load())

	// Поток 1 удаляет элементы
	ebr.Retire(42)
	ebr.Retire(99)
	fmt.Printf("Удалено 2 элемента в список Retired\n")

	// Попытка очистки: поток 0 все еще держит эпоху!
	freed1 := ebr.AdvanceAndReclaim()
	fmt.Printf("Очищено при активном потоке 0: %d узлов (защита от Use-After-Free)\n", freed1)

	// Поток 0 завершил чтение и вышел
	ebr.Leave(0)
	fmt.Println("Поток 0 покинул критическую секцию")

	// Повторная очистка: теперь безопасно!
	freed2 := ebr.AdvanceAndReclaim()
	fmt.Printf("Очищено после выхода потока: %d узлов\n", freed2)
	fmt.Println("Вывод: Go Garbage Collector избавляет от необходимости вручную писать EBR/Hazard Pointers!")
}
```

ℹ️ Упрощенная модель EBR демонстрирует правила безопасной отложенной утилизации памяти.

## Под капотом

EBR является основой таких технологий ядра Linux, как RCU (Read-Copy Update), и библиотек Crossbeam в Rust. Проблема классического EBR — застрявший поток (Stalled Thread): если один поток уснул на секунду внутри эпохи, освобождение памяти блокируется для всей системы, вызывая утечку памяти (Memory Bloat). Для решения этой проблемы в C++ применяют более сложные Hazard Pointers.

## Подводные камни

1. Ручная реализация EBR в Go является избыточной: встроенный рантайм Go и алгоритм Tri-color GC делают отслеживание доступности объектов эффективнее и безопаснее.
2. Необходимость вызова `Leave()`: забытый выход приводит к утечке памяти.

## На собеседовании

Вопрос: «Что такое проблема ABA и почему она тесно связана с задачей Memory Reclamation в lock-free структурах данных?». Ответ: если поток освобождает память узла сразу после удаления, системный аллокатор может вернуть тот же адрес новому узлу, порождая ABA. Техники безопасного освобождения (EBR, Hazard Pointers, Tracing GC) гарантируют, что адрес узла не будет переиспользован, пока на него есть хотя бы один живой читатель.
