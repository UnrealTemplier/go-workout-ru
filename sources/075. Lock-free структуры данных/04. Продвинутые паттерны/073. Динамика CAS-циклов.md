# Динамика CAS-циклов: вероятность коллизий и стратегии экспоненциального Backoff

## Условие

Изучите поведение циклов Compare-And-Swap при экстремальной конкуренции. Реализуйте алгоритм адаптивного экспоненциального отката (Exponential Backoff with Jitter), объяснив, как он предотвращает деградацию пропускной способности при CAS retry storms.

### Исходная формулировка

**CAS retry loops — это нормально.**: В lock-free алгоритмах CAS может fail из-за contention, и вы retry. Это expected behavior. Но убедитесь, что retry probability низкая.

## Теория

При проектировании lock-free структур разработчики ожидают, что цикл `for !atomic.CompareAndSwap(...)` выполнится за 1–2 итерации.

**Проблема лавины повторов (CAS Retry Storm):**
Если 64 горутины одновременно пытаются обновить один атомарный указатель:
- 1 горутина побеждает и обновляет значение.
- 63 горутины проигрывают, синхронно читают новое значение и снова одновременно делают CAS!
- Шанс победы для каждой отдельной горутины падает до \(1/N\).
- На шине межъядерной когерентности памяти возникает лавина сообщений инвалидации (Bus Contention), процессорные ядра тратят 95% времени на ожидание ответов от кэшей соседних ядер.

**Решение — Exponential Backoff с шумом (Jitter):**
При каждой неудачной попытке CAS горутина приостанавливает выполнение на случайно возрастающее время:
$$\text{delay} = \text{min}(\text{maxDelay}, \text{baseDelay} \cdot 2^{\text{attempts}}) + \text{randJitter}$$
В Go короткая пауза реализуется вызовом `procyield` (на ассемблере x86 `PAUSE`, на ARM `YIELD`) или `runtime.Gosched()` при затянувшемся конфликте.

## Решение по шагам

1. Создайте структуру `Backoff` с параметрами минимальной и максимальной задержки.
2. Реализуйте метод `Pause()`, выполняющий прогрессивную паузу.
3. Реализуйте счетчик со сбором статистики числа попыток CAS.
4. Протестируйте инкремент 128 параллельными горутинами с Backoff и без него.
5. Продемонстрируйте снижение общего числа коллизий шины памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type Backoff struct {
	attempts int
	minSpin  int
	maxSpin  int
}

func NewBackoff(minSpin, maxSpin int) Backoff {
	return Backoff{
		minSpin: minSpin,
		maxSpin: maxSpin,
	}
}

// Spin выполняет адаптивную паузу
func (b *Backoff) Spin() {
	b.attempts++
	if b.attempts <= 4 {
		// Короткая пауза через уступку тактов CPU
		for i := 0; i < (b.minSpin << b.attempts); i++ {
			// Симуляция инструкции CPU PAUSE
		}
	} else if b.attempts <= 8 {
		// Средняя конкуренция: уступаем квант времени планировщику Go
		runtime.Gosched()
	} else {
		// Жесткая конкуренция: засыпаем на микросекунды со случайным джиттером
		jitter := time.Duration(rand.Intn(50)) * time.Microsecond
		time.Sleep(100*time.Microsecond + jitter)
	}
}

func (b *Backoff) Reset() {
	b.attempts = 0
}

type BackoffCounter struct {
	val         int64
	totalRetries int64
}

func (c *BackoffCounter) IncWithBackoff() {
	bo := NewBackoff(4, 32)
	for {
		cur := atomic.LoadInt64(&c.val)
		if atomic.CompareAndSwapInt64(&c.val, cur, cur+1) {
			return
		}
		atomic.AddInt64(&c.totalRetries, 1)
		bo.Spin()
	}
}

func main() {
	const workers = 64
	const incrementsPerWorker = 20000

	counter := &BackoffCounter{}
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()

	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < incrementsPerWorker; i++ {
				counter.IncWithBackoff()
			}
		}()
	}

	wg.Wait()
	dur := time.Since(start)

	expected := int64(workers * incrementsPerWorker)
	actual := atomic.LoadInt64(&counter.val)
	retries := atomic.LoadInt64(&counter.totalRetries)

	fmt.Printf("Workers: %d, Total Incs: %d (Valid: %t)\n", workers, actual, actual == expected)
	fmt.Printf("Total CAS Retries: %d (Ratio: %.2f retries/op)\n", retries, float64(retries)/float64(expected))
	fmt.Printf("Time taken: %v\n", dur)
}
```

ℹ️ Экспоненциальный откат (Backoff) для сглаживания пиков конкуренции в CAS-циклах.

## Под капотом

Инструкция процессора `PAUSE` на x86 (в ассемблере Go доступна во внутреннем рантайме как `runtime.procyield`) сообщает конвейеру ядра, что процессор находится в цикле ожидания блокировки. Это отключает спекулятивную предвыборку инструкций, предотвращая сброс конвейера ядра при выходе из цикла и снижая энергопотребление процессора.

## Подводные камни

1. Слишком длинный сон: использование `time.Sleep(1 * time.Millisecond)` на первых же попытках катастрофически обрушит пропускную способность. Миллисекунда для процессора с тактовой частотой 3 ГГц — это 3 миллиона упущенных тактов.
2. Отсутствие Jitter (случайного шума): если все проигравшие потоки сделают паузу ровно на 10 микросекунд, они проснутся одновременно и снова устроят идентичную коллизию.

## На собеседовании

«Что такое Thundering Herd Problem и как экспоненциальный Backoff решает эту проблему?». Ответ: Thundering Herd (проблема стада) возникает, когда множество потоков одновременно просыпаются по одному событию и пытаются захватить единственный ресурс. Backoff со случайным шумом (Full Jitter) распределяет моменты повторных попыток во времени, сглаживая пиковую нагрузку.
