# Стратегии Backpressure в кольцевом буфере: Block, Drop Oldest, Drop Newest

## Условие

Реализуйте кольцевой буфер с поддержкой трех различных стратегий противодавления (Backpressure Strategies) при переполнении: блокировка с ожиданием (Block), вытеснение самых старых данных (Drop Oldest / Overwrite) и отказ с ошибкой (Drop Newest). Сравните их применимость в HighLoad-системах.

### Исходная формулировка

**Backpressure в ring buffer**: Если buffer full, producer может:
* Block (wait for space)
* Drop oldest (overwrite)
* Return error
Выберите стратегию based on use case.

## Теория

В реальных распределенных системах скорость поступления данных часто превышает скорость их обработки потребителем (всплески трафика, сетевые лаги, сбои баз данных). Без продуманного механизма **Backpressure** система неминуемо упадет с ошибкой Out Of Memory (OOM).

**Три ключевые стратегии обработки переполнения:**
1. **Block (Ожидание)**: производитель приостанавливает работу, пока в буфере не освободится место.
   - *Плюсы*: нулевая потеря данных (Zero Data Loss).
   - *Минусы*: замедление всей цепочки сервисов (Head-of-Line Blocking), риск каскадных сбоев.
   - *Применение*: финансовые транзакции, биллинг, надежные брокеры сообщений.
2. **Drop Oldest (Вытеснение старых данных / Кольцевая перезапись)**: производитель принудительно сдвигает указатель `tail`, удаляя самые старые невычитанные данные.
   - *Плюсы*: всегда сохраняются самые свежие (актуальные) данные; продюсер никогда не блокируется.
   - *Минусы*: потеря исторических сообщений.
   - *Применение*: видеостриминг, телеметрия IoT, котировки акций в реальном времени.
3. **Drop Newest / Return Error (Отказ)**: продюсер немедленно возвращает ошибку `ErrBufferFull` и отбрасывает новое входящее сообщение.
   - *Плюсы*: защита очереди от перегрузки; клиент получает явный сигнал о перегрузке (HTTP 429 / 503).
   - *Применение*: логирование, метрики, системы с Circuit Breaker.

## Решение по шагам

1. Определите перечисление стратегий `BackpressureStrategy`: `StrategyBlock`, `StrategyDropOldest`, `StrategyDropNewest`.
2. Создайте структуру буфера `ConfigurableRingBuffer`.
3. Реализуйте метод `Push(val int64) error` с ветвлением логики согласно выбранной стратегии.
4. Протестируйте каждую стратегию с медленным консьюмером.
5. Зафиксируйте поведение системы при переполнении.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

var ErrBufferFull = errors.New("buffer is full: message dropped")

type BackpressureStrategy int

const (
	StrategyBlock BackpressureStrategy = iota
	StrategyDropOldest
	StrategyDropNewest
)

type BackpressureBuffer struct {
	buffer   []int64
	capacity uint64
	mask     uint64
	strategy BackpressureStrategy

	head uint64
	_pad [56]byte
	tail uint64
}

func NewBackpressureBuffer(size uint64, strategy BackpressureStrategy) *BackpressureBuffer {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be power of 2")
	}
	return &BackpressureBuffer{
		buffer:   make([]int64, size),
		capacity: size,
		mask:     size - 1,
		strategy: strategy,
	}
}

func (b *BackpressureBuffer) Push(val int64) error {
	for {
		head := atomic.LoadUint64(&b.head)
		tail := atomic.LoadUint64(&b.tail)

		if head-tail >= b.capacity {
			switch b.strategy {
			case StrategyDropNewest:
				return ErrBufferFull

			case StrategyDropOldest:
				// Атомарно продвигаем tail вперед, отбрасывая старый элемент
				atomic.CompareAndSwapUint64(&b.tail, tail, tail+1)
				// Повторяем цикл записи
				continue

			case StrategyBlock:
				runtime.Gosched()
				continue
			}
		}

		b.buffer[head&b.mask] = val
		atomic.StoreUint64(&b.head, head+1)
		return nil
	}
}

func (b *BackpressureBuffer) Pop() (int64, bool) {
	for {
		tail := atomic.LoadUint64(&b.tail)
		head := atomic.LoadUint64(&b.head)

		if tail >= head {
			return 0, false
		}

		val := b.buffer[tail&b.mask]
		if atomic.CompareAndSwapUint64(&b.tail, tail, tail+1) {
			return val, true
		}
	}
}

func main() {
	// Демонстрация StrategyDropOldest
	fmt.Println("=== Testing StrategyDropOldest ===")
	buf := NewBackpressureBuffer(4, StrategyDropOldest)

	// Пишем 6 элементов в буфер емкостью 4
	for i := int64(1); i <= 6; i++ {
		_ = buf.Push(i)
	}

	// Читаем оставшиеся данные: ожидаем элементы 3, 4, 5, 6 (1 и 2 были вытеснены)
	fmt.Print("Retrieved items: ")
	for {
		val, ok := buf.Pop()
		if !ok {
			break
		}
		fmt.Printf("%d ", val)
	}
	fmt.Println()

	// Демонстрация StrategyDropNewest
	fmt.Println("\n=== Testing StrategyDropNewest ===")
	bufErr := NewBackpressureBuffer(4, StrategyDropNewest)
	for i := int64(1); i <= 6; i++ {
		err := bufErr.Push(i)
		if err != nil {
			fmt.Printf("Push %d failed: %v\n", i, err)
		} else {
			fmt.Printf("Push %d succeeded\n", i)
		}
	}
}
```

ℹ️ Реализация стратегий Backpressure: блокировка, вытеснение и отказ.

## Под капотом

В стратегии `StrategyDropOldest` при сдвиге `tail` через CAS может возникнуть ситуация, когда консьюмер в этот самый момент читает вытесняемый слот. Чтобы предотвратить чтение поврежденных данных, для многопоточного буфера используют генерационные маркеры или версионирование слотов.

## Подводные камни

1. Бесконечная блокировка в `StrategyBlock`: если потребитель упал с паникой или закрылся, производитель навсегда зависнет в цикле ожидания. В production-коде необходимо поддерживать таймауты через `context.Context`.
2. Неучтенные потери при `DropOldest`: если в метриках не фиксировать факт вытеснения, инженеры поддержки не узнают о потере части сообщений.

## На собеседовании

«Какую стратегию Backpressure использует брокер Apache Kafka, а какую — UDP сокеты ОС Linux?». Ответ: Kafka использует `StrategyBlock` (производитель ждет освобождения буфера или возвращает таймаут), в то время как UDP сокеты ядра Linux используют `StrategyDropNewest` (при переполнении ring buffer сетевой карты или сокета входящие пакеты молча отбрасываются — `rx_dropped`).
