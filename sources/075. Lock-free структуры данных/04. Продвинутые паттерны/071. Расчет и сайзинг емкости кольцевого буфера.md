# Расчет и сайзинг емкости кольцевого буфера: Закон Литтла и утилизация памяти

## Условие

Разработайте инженерную методику расчета емкости кольцевого буфера (Capacity Sizing) для гарантированного поглощения всплесков трафика (Burst Traffic) на основе Закона Литтла (Little's Law) с контролем утилизации оперативной памяти.

### Исходная формулировка

**Ring buffer sizing**: Размер ring buffer должен быть достаточным для absorbtion burst traffic, но не слишком большим (waste memory).

## Теория

Выбор размера кольцевого буфера — критическое архитектурное решение:
- **Слишком маленький буфер**: при малейшем всплеске трафика (Spike) буфер переполняется, вызывая отбрасывание сообщений или каскадные задержки.
- **Слишком большой буфер**: нерациональный расход оперативной памяти, вымывание L1/L2/L3 кэшей процессора и скрытый буферблоат (Bufferbloat — недопустимый рост задержки доставки).

**Закон Литтла (Little's Law):**
$$L = \lambda \cdot W$$
где:
- \(L\) — среднее число элементов в очереди (Queue Depth);
- \(\lambda\) — средняя интенсивность входящего потока (RPS);
- \(W\) — среднее время пребывания элемента в очереди (Latency).

**Инженерная формула сайзинга емкости с учетом всплесков (Burst Capacity):**
$$C = \text{NextPowerOf2}((\lambda \cdot W) + (\text{BurstRPS} \cdot T_{\text{burst}}))$$
Если сервис обрабатывает 100 000 RPS со средним временем обработки 10 мс (\(W = 0.01\) с), базовая очередь требует \(100000 \cdot 0.01 = 1000\) слотов.
При возможном всплеске трафика в 300 000 RPS длительностью 200 мс дополнительный запас составит \(300000 \cdot 0.2 = 60000\) слотов.
Итоговая емкость: \(\text{NextPowerOf2}(1000 + 60000) = \text{NextPowerOf2}(61000) = 65536\) слотов.

## Решение по шагам

1. Реализуйте калькулятор параметров сайзинга `CalculateRingBufferSize`.
2. Создайте структуру для профилирования использования емкости и отслеживания пиковой глубины очереди (High Watermark).
3. Смоделируйте ступенчатый всплеск нагрузки.
4. Проверьте, поглотил ли рассчитанный буфер всплеск без потерь элементов.
5. Выведите детальный расчет занимаемой памяти в мегабайтах.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/bits"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

type SizingParams struct {
	NormalRPS     float64
	AvgLatency    time.Duration
	BurstRPS      float64
	BurstDuration time.Duration
	ItemSizeBytes int
}

type SizingResult struct {
	Capacity          uint64
	MemorySizeBytes   uint64
	MaxBufferedTimeMs float64
}

func CalculateBufferSize(p SizingParams) SizingResult {
	// Базовое число по закону Литтла: L = lambda * W
	baseItems := p.NormalRPS * p.AvgLatency.Seconds()

	// Всплеск нагрузки: Burst = BurstRPS * BurstDuration
	burstItems := p.BurstRPS * p.BurstDuration.Seconds()

	totalRequired := uint64(baseItems + burstItems)

	// Округление вверх до степени 2
	var capacity uint64 = 1
	if totalRequired > 1 {
		capacity = 1 << (64 - bits.LeadingZeros64(totalRequired-1))
	}

	memBytes := capacity * uint64(p.ItemSizeBytes)
	maxTimeMs := (float64(capacity) / p.NormalRPS) * 1000.0

	return SizingResult{
		Capacity:          capacity,
		MemorySizeBytes:   memBytes,
		MaxBufferedTimeMs: maxTimeMs,
	}
}

type MonitoredBuffer struct {
	buffer        []int64
	mask          uint64
	capacity      uint64
	head          uint64
	tail          uint64
	highWatermark uint64
}

func NewMonitoredBuffer(cap uint64) *MonitoredBuffer {
	return &MonitoredBuffer{
		buffer:   make([]int64, cap),
		mask:     cap - 1,
		capacity: cap,
	}
}

func (b *MonitoredBuffer) Push(val int64) bool {
	h := atomic.LoadUint64(&b.head)
	t := atomic.LoadUint64(&b.tail)

	depth := h - t
	if depth >= b.capacity {
		return false
	}

	// Отслеживаем High Watermark
	for {
		hw := atomic.LoadUint64(&b.highWatermark)
		if depth <= hw || atomic.CompareAndSwapUint64(&b.highWatermark, hw, depth) {
			break
		}
	}

	b.buffer[h&b.mask] = val
	atomic.StoreUint64(&b.head, h+1)
	return true
}

func (b *MonitoredBuffer) Pop() (int64, bool) {
	t := atomic.LoadUint64(&b.tail)
	h := atomic.LoadUint64(&b.head)
	if t >= h {
		return 0, false
	}
	v := b.buffer[t&b.mask]
	atomic.StoreUint64(&b.tail, t+1)
	return v, true
}

func main() {
	params := SizingParams{
		NormalRPS:     50000,
		AvgLatency:    5 * time.Millisecond,
		BurstRPS:      150000,
		BurstDuration: 100 * time.Millisecond,
		ItemSizeBytes: int(unsafe.Sizeof(int64(0))),
	}

	res := CalculateBufferSize(params)
	fmt.Println("=== Ring Buffer Sizing Calculation ===")
	fmt.Printf("Optimal Capacity:    %d slots\n", res.Capacity)
	fmt.Printf("Memory Footprint:    %.2f KB\n", float64(res.MemorySizeBytes)/1024)
	fmt.Printf("Max Bufferbloat:     %.2f ms at normal load\n\n", res.MaxBufferedTimeMs)

	// Симуляция всплеска трафика
	buf := NewMonitoredBuffer(res.Capacity)
	var wg sync.WaitGroup
	wg.Add(2)

	// Producer со всплеском
	go func() {
		defer wg.Done()
		for i := int64(1); i <= 20000; i++ {
			for !buf.Push(i) {
				time.Sleep(10 * time.Microsecond)
			}
		}
	}()

	// Consumer
	go func() {
		defer wg.Done()
		var count int
		for count < 20000 {
			if _, ok := buf.Pop(); ok {
				count++
			}
		}
	}()

	wg.Wait()
	fmt.Printf("Simulation Finished. Peak Queue Depth (High Watermark): %d / %d (%.1f%% utilization)\n",
		buf.highWatermark, buf.capacity, float64(buf.highWatermark)/float64(buf.capacity)*100)
}
```

ℹ️ Математический расчет емкости буфера по закону Литтла и отслеживание High Watermark.

## Под капотом

Закон Литтла примерен независимо от распределения вероятностей входящего потока (пуассоновский, равномерный или с тяжелыми хвостами). Важно контролировать метрику High Watermark в системах мониторинга: если очередь стабильно заполнена более чем на 75%, емкость буфера выбрана неправильно либо пропускная способность потребителя недостаточна.

## Подводные камни

1. Буферблоат (Bufferbloat): если сделать буфер избыточно огромным (например, на 10 000 000 слотов), при зависании консьюмера в очереди накопится сообщений на несколько минут работы. Клиенты отвалятся по HTTP-таймаутам, но система продолжит бессмысленно обрабатывать уже протухшие данные.
2. Всплески памяти: аллокация крупных непрерывных слайсов создает фрагментацию виртуальной памяти.

## На собеседовании

«Что такое Bufferbloat и как его предотвратить в высоконагруженных очередях?». Ответ: Bufferbloat — это эффект чрезмерной задержки пакетов из-за гигантских очередей в маршрутизаторах или сервисах. Для борьбы с ним применяют ограничение максимального времени нахождения сообщения в буфере (TTL per message) и алгоритмы CoDel (Controlled Delay) / RED (Random Early Detection).
