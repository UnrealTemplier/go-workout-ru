# Границы применимости: Lock-free против Mutex в зависимости от Contention

## Условие

Проведите практическое исследование пределов применимости lock-free структур по сравнению с `sync.Mutex`. Докажите на бенчмарках, почему при низкой конкуренции (Low Contention) мьютекс превосходит lock-free, а lock-free выигрывает только при высокой борьбе за ресурсы (High Contention).

### Исходная формулировка

**Lock-free только при high contention.**: При low contention mutex быстрее (проще, нет CAS retry loops). Lock-free имеет смысл, когда 100+ threads конкурируют за один resource.

## Теория

Распространенное заблуждение начинающих инженеров: *«Lock-free всегда быстрее, чем мьютекс»*. В реальности это не так.

**Поведение `sync.Mutex` в Go:**
- При отсутствии конкуренции (Uncontended case) захват `sync.Mutex` сводится к одной быстрой атомарной инструкции `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)`. Если мьютекс свободен, горутина захватывает его за ~3–5 нс без обращения к планировщику.
- При высокой конкуренции горутины переводятся в режим ожидания (паркуются через `runtime.gopark`), освобождая процессор для полезной работы.

**Поведение Lock-Free (CAS loop):**
- При отсутствии конкуренции CAS выполняется за ~3–5 нс (так же, как мьютекс).
- При экстремальной конкуренции (100+ ядер): десятки горутин одновременно пытаются сделать `CAS`. Только одна побеждает, остальные 99 терпят неудачу и начинают заново.
- Возникает **CAS Retry Storm (шторм повторов)**: ядра CPU непрерывно бомбардируют шину памяти запросами инвалидации кэш-линий, сжигая 100% мощности процессора впустую.

**Золотое правило инженерии**: Lock-free алгоритмы требуют тщательного профилирования. Если поток находится в критической секции доли микросекунды, а число параллельных потоков невелико, `sync.Mutex` часто проще, надежнее и быстрее.

## Решение по шагам

1. Создайте два счетчика: `MutexCounter` и `CASCounter`.
2. Напишите сравнительный тест при низкой конкуренции (1–2 горутины).
3. Напишите тест при высокой конкуренции (64–128 горутин).
4. Замерьте время выполнения и число выполненных повторов (retries).
5. Сформулируйте матрицу решений выбора между Mutex и Lock-free.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type MutexCounter struct {
	mu  sync.Mutex
	val int64
}

func (c *MutexCounter) Inc() {
	c.mu.Lock()
	c.val++
	c.mu.Unlock()
}

type CASCounter struct {
	val     int64
	retries int64
}

func (c *CASCounter) Inc() {
	for {
		cur := atomic.LoadInt64(&c.val)
		if atomic.CompareAndSwapInt64(&c.val, cur, cur+1) {
			return
		}
		atomic.AddInt64(&c.retries, 1)
	}
}

func runBenchmark(name string, workers int, opsPerWorker int) {
	fmt.Printf("--- %s (Workers: %d, Ops/worker: %d) ---\n", name, workers, opsPerWorker)

	// 1. Mutex Test
	{
		mc := &MutexCounter{}
		var wg sync.WaitGroup
		wg.Add(workers)
		start := time.Now()

		for w := 0; w < workers; w++ {
			go func() {
				defer wg.Done()
				for i := 0; i < opsPerWorker; i++ {
					mc.Inc()
				}
			}()
		}
		wg.Wait()
		dur := time.Since(start)
		fmt.Printf("Mutex Time: %v | Total: %d\n", dur, mc.val)
	}

	// 2. CAS Test
	{
		cc := &CASCounter{}
		var wg sync.WaitGroup
		wg.Add(workers)
		start := time.Now()

		for w := 0; w < workers; w++ {
			go func() {
				defer wg.Done()
				for i := 0; i < opsPerWorker; i++ {
					cc.Inc()
				}
			}()
		}
		wg.Wait()
		dur := time.Since(start)
		fmt.Printf("CAS   Time: %v | Total: %d | Retries: %d\n\n", dur, cc.val, cc.retries)
	}
}

func main() {
	// Сценарий 1: Низкая конкуренция (Low Contention)
	runBenchmark("Low Contention", 2, 500000)

	// Сценарий 2: Высокая конкуренция (High Contention)
	runBenchmark("High Contention", 64, 50000)
}
```

ℹ️ Сравнение Mutex и CAS в режимах Low Contention и High Contention.

## Под капотом

В Go реализация `sync.Mutex` является адаптивной (Adaptive Spin-Lock). Если мьютекс занят на многоядерной машине, горутина сначала делает до 30 циклов активного ожидания (`procyield`), надеясь быстро захватить блокировку без ухода в ядро ОС. Если блокировка не освободилась, она переходит в режим ожидания семафора рантайма (`runtime_SemacquireMutex`).

## Подводные камни

1. Голодание (Starvation) в CAS: при десятках конкурирующих потоков неудачливая горутина может выполнить миллионы холостых итераций CAS loop, так и не завершив операцию.
2. Усложнение кода: lock-free код требует на порядок больше усилий при написании, отладке и аудите, а риск незаметных багов конкурентности многократно возрастает.

## На собеседовании

«В каком случае вы выберете `sync.Mutex`, а в каком — Lock-free CAS структуру данных?». Ответ: если логика внутри критической секции включает больше одного поля, ветвления или внешние вызовы (IO, аллокации) — всегда `sync.Mutex`. Lock-free оправдан только для простейших атомарных примитивов (счетчики, флаги) или специализированных структур очередей в критических по задержке путях системы.
