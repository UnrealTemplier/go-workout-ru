# Пакетные операции (Batch Operations) в Lock-free очередях

## Условие

Реализуйте поддержку пакетной записи (`EnqueueBatch`) и пакетного чтения (`DequeueBatch`) для кольцевого буфера. Докажите, что амортизация атомарных инструкций повышает пропускную способность очереди в разы.

### Исходная формулировка

**Batch operations**: Для throughput producer может batch write multiple items. Consumer может batch read.

## Теория

Главный лимитирующий фактор производительности lock-free структур — **атомарные инструкции с барьерами памяти** (`LOCK CMPXCHG`, `DMB ISH`) и связанный с ними трафик когерентности кэшей (MESI invalidation storm).

Когда поток отправляет 100 сообщений по одному:
- Он выполняет 100 атомарных операций CAS.
- 100 раз инвалидирует кэш-линию счетчика `head` у всех остальных процессорных ядер.

**Пакетные операции (Batching)**:
1. Поток резервирует сразу \(N\) слотов одной атомарной инструкцией:
   `batchHead := atomic.AddUint64(&q.head, N) - N`
2. Поток копирует \(N\) элементов в буфер обычными быстрыми инструкциями памяти (`runtime.memmove` или простой цикл).
3. Потребитель аналогично атомарно резервирует до \(M\) доступных сообщений за один `atomic.AddUint64(&q.tail, M)`.
4. В результате накладные расходы на синхронизацию сокращаются в \(N\) раз!

## Решение по шагам

1. Создайте структуру `BatchSPSCQueue`.
2. Реализуйте метод `EnqueueBatch(items []int64) int`, записывающий сразу срез элементов.
3. Реализуйте метод `DequeueBatch(buf []int64) int`, считывающий пачку элементов за одно обновление указателя.
4. Сравните throughput одиночной и пакетной передачи данных на объеме 2 000 000 элементов.
5. Проанализируйте график ускорения.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type BatchQueue struct {
	buffer   []int64
	capacity uint64
	mask     uint64
	_pad0    [40]byte

	head uint64
	_pad1 [56]byte

	tail uint64
	_pad2 [56]byte
}

func NewBatchQueue(size uint64) *BatchQueue {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be power of 2")
	}
	return &BatchQueue{
		buffer:   make([]int64, size),
		capacity: size,
		mask:     size - 1,
	}
}

// EnqueueBatch вставляет срез элементов, возвращая фактически записанное количество
func (q *BatchQueue) EnqueueBatch(items []int64) int {
	count := uint64(len(items))
	if count == 0 {
		return 0
	}

	head := atomic.LoadUint64(&q.head)
	tail := atomic.LoadUint64(&q.tail)

	available := q.capacity - (head - tail)
	if available == 0 {
		return 0
	}

	toWrite := count
	if toWrite > available {
		toWrite = available
	}

	// Записываем пачку
	for i := uint64(0); i < toWrite; i++ {
		q.buffer[(head+i)&q.mask] = items[i]
	}

	// Одно атомарное обновление на всю пачку!
	atomic.StoreUint64(&q.head, head+toWrite)
	return int(toWrite)
}

// DequeueBatch вычитывает до len(dst) элементов в переданный буфер
func (q *BatchQueue) DequeueBatch(dst []int64) int {
	maxToRead := uint64(len(dst))
	if maxToRead == 0 {
		return 0
	}

	tail := atomic.LoadUint64(&q.tail)
	head := atomic.LoadUint64(&q.head)

	available := head - tail
	if available == 0 {
		return 0
	}

	toRead := maxToRead
	if toRead > available {
		toRead = available
	}

	for i := uint64(0); i < toRead; i++ {
		dst[i] = q.buffer[(tail+i)&q.mask]
	}

	// Одно атомарное обновление на всю пачку!
	atomic.StoreUint64(&q.tail, tail+toRead)
	return int(toRead)
}

func main() {
	const total = 2000000
	const batchSize = 64

	q := NewBatchQueue(8192)

	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	// Batch Producer
	go func() {
		defer wg.Done()
		batch := make([]int64, batchSize)
		for i := 0; i < batchSize; i++ {
			batch[i] = int64(i + 1)
		}

		var sent int
		for sent < total {
			remaining := total - sent
			curBatch := batch
			if remaining < batchSize {
				curBatch = batch[:remaining]
			}
			n := q.EnqueueBatch(curBatch)
			sent += n
		}
	}()

	// Batch Consumer
	go func() {
		defer wg.Done()
		readBuf := make([]int64, batchSize)
		var received int
		for received < total {
			n := q.DequeueBatch(readBuf)
			received += n
		}
	}()

	wg.Wait()
	dur := time.Since(start)

	fmt.Printf("Batch transfer of %d items completed in %v\n", total, dur)
	fmt.Printf("Throughput: %.2f M items/sec\n", float64(total)/dur.Seconds()/1e6)
}
```

ℹ️ Пакетные операции записи и чтения в кольцевом буфере с амортизацией атомиков.

## Под капотом

При пакетной записи один барьер `atomic.StoreUint64` покрывает сразу 64 или 128 записей в память. Процессор может эффективно задействовать векторные инструкции `AVX-512 / NEON` и конвейерную предвыборку данных (Hardware Prefetcher), кратно снижая удельные наносекунды на элемент.

## Подводные камни

1. Задержка (Latency) при малых объемах: пакетная буферизация улучшает Throughput (пропускную способность), но ухудшает задержку (Latency), если поток ожидает накопления полной пачки. В системах реального времени используют механизм Flush по таймауту.
2. Кольцевой перегиб: если пачка пересекает границу конца буфера (`head + count > capacity`), запись распадается на два фрагмента (конец слайса и начало). В коде выше операция `(head+i) & mask` корректно обрабатывает это поэлементно.

## На собеседовании

«Почему Kafka и ClickHouse показывают огромную скорость записи по сравнению со стандартными SQL СУБД?». Ответ: за счет повсеместного применения пакетной обработки (Batching). На всех уровнях — от TCP-сокетов до дискового ввода-вывода `fsync` — данные накапливаются пачками, снижая накладные расходы системных вызовов и блокировок на 2–3 порядка.
