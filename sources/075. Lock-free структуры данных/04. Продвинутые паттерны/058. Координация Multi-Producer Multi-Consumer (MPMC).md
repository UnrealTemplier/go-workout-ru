# Координация Multi-Producer Multi-Consumer (MPMC) на базе CAS

## Условие

Изучите архитектурные принципы координации множества параллельных производителей (Producers) и потребителей (Consumers) в очереди MPMC. Объясните, почему для MPMC недостаточно атомарных Load/Store и требуется двухфазная фиксация слота с помощью CAS.

### Исходная формулировка

**Multi-producer multi-consumer (MPMC)**: Сложнее: multiple producers и multiple consumers. Нужен CAS для coordination.

## Теория

В отличие от SPSC очереди, где индекс записи монопольно принадлежит одному потоку, в архитектуре **Multi-Producer Multi-Consumer (MPMC)**:
1. **Множество производителей** конкурируют за следующий свободный слот для записи. Если два производителя одновременно инкрементируют указатель `head` без атомарной синхронизации, они попытаются записать данные в один и тот же индекс массива.
2. **Множество потребителей** конкурируют за извлечение элементов. Два потребителя могут одновременно попытаться вычитать один и тот же слот.
3. **Рассинхронизация записи и чтения**: производитель может успешно инкрементировать `head`, но еще не успеть скопировать данные в память слота. Если потребитель сразу попытается прочитать этот слот, он получит мусор или неинициализированные данные.

**Принцип двухфазной координации**:
Чтобы избежать чтения неготовых данных, каждый слот кольцевого буфера снабжается собственным атомарным маркером состояния (флагом готовности или монотонным счетчиком последовательности `sequence`).
- Фаза 1 (Резервирование): поток атомарно через CAS резервирует индекс слота.
- Фаза 2 (Публикация): после записи данных поток переводит маркер слота в состояние «Готово к чтению».

## Решение по шагам

1. Создайте структуру `MPMCSlot` с полезной нагрузкой и атомарным флагом `ready uint32`.
2. Реализуйте структуру `BasicMPMCQueue` с атомарными индексами `head` и `tail`.
3. Реализуйте метод `Enqueue`: резервирование индекса через `atomic.AddUint64(&head, 1)`, запись данных в слот, выставление флага готовности `atomic.StoreUint32(&slot.ready, 1)`.
4. Реализуйте метод `Dequeue`: чтение индекса, ожидание флага готовности, чтение данных и сброс флага.
5. Протестируйте работу с 10 производителями и 10 потребителями.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type MPMCSlot struct {
	value int64
	ready uint32 // 0 - пусто/свободно, 1 - заполнено данными
}

type BasicMPMCQueue struct {
	slots    []MPMCSlot
	capacity uint64
	mask     uint64
	head     uint64 // Индекс резервирования продюсерами
	tail     uint64 // Индекс резервирования консьюмерами
}

func NewBasicMPMCQueue(size uint64) *BasicMPMCQueue {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be a power of 2")
	}
	return &BasicMPMCQueue{
		slots:    make([]MPMCSlot, size),
		capacity: size,
		mask:     size - 1,
	}
}

func (q *BasicMPMCQueue) Enqueue(val int64) bool {
	for {
		head := atomic.LoadUint64(&q.head)
		tail := atomic.LoadUint64(&q.tail)

		if head-tail >= q.capacity {
			return false // Буфер переполнен
		}

		// Пытаемся зарезервировать слот
		if atomic.CompareAndSwapUint64(&q.head, head, head+1) {
			slot := &q.slots[head&q.mask]

			// Ждем пока предыдущий консьюмер освободит слот (если очередь сделала оборот)
			for atomic.LoadUint32(&slot.ready) != 0 {
				runtime.Gosched()
			}

			// Записываем данные
			slot.value = val

			// Публикуем готовность элемента
			atomic.StoreUint32(&slot.ready, 1)
			return true
		}
	}
}

func (q *BasicMPMCQueue) Dequeue() (int64, bool) {
	for {
		tail := atomic.LoadUint64(&q.tail)
		head := atomic.LoadUint64(&q.head)

		if tail >= head {
			return 0, false // Очередь пуста
		}

		// Пытаемся зарезервировать слот для чтения
		if atomic.CompareAndSwapUint64(&q.tail, tail, tail+1) {
			slot := &q.slots[tail&q.mask]

			// Ожидаем завершения записи продюсером
			for atomic.LoadUint32(&slot.ready) != 1 {
				runtime.Gosched()
			}

			val := slot.value

			// Помечаем слот как освобожденный
			atomic.StoreUint32(&slot.ready, 0)
			return val, true
		}
	}
}

func main() {
	q := NewBasicMPMCQueue(512)
	const producers = 8
	const consumers = 8
	const itemsPerProducer = 10000

	var wg sync.WaitGroup
	wg.Add(producers + consumers)

	// Producers
	for p := 0; p < producers; p++ {
		go func(id int) {
			defer wg.Done()
			for i := 1; i <= itemsPerProducer; i++ {
				val := int64(id*itemsPerProducer + i)
				for !q.Enqueue(val) {
					runtime.Gosched()
				}
			}
		}(p)
	}

	// Consumers
	var totalConsumed int64
	var sumConsumed int64
	for c := 0; c < consumers; c++ {
		go func() {
			defer wg.Done()
			for {
				val, ok := q.Dequeue()
				if ok {
					atomic.AddInt64(&totalConsumed, 1)
					atomic.AddInt64(&sumConsumed, val)
				} else {
					if atomic.LoadInt64(&totalConsumed) >= int64(producers*itemsPerProducer) {
						break
					}
					runtime.Gosched()
				}
			}
		}()
	}

	wg.Wait()
	fmt.Printf("MPMC Finished: Consumed %d items, Sum: %d\n", totalConsumed, sumConsumed)
}
```

ℹ️ Базовая MPMC очередь на CAS с проверкой готовности слотов.

## Под капотом

Слабое место данного алгоритма — возможность зависания (Livelock/Starvation), если горутина-продюсер зарезервировала `head`, но была вытеснена планировщиком операционной системы до вызова `StoreUint32(&slot.ready, 1)`. При обороте кольца другой продюсер упрется в цикл `for slot.ready != 0`, ожидая вытесненный поток. Для устранения этого дефекта используют алгоритм Дмитрия Вьюкова на монотонных счетчиках версий.

## Подводные камни

1. Зависание при конкуренции за слот: активный спин `for slot.ready != 1` без пауз сжигает 100% CPU. Обязательно использовать `runtime.Gosched()` или экспоненциальный backoff.
2. Проблема false sharing: если слоты расположены вплотную в массиве, флаги `ready` соседних слотов могут оказаться в одной кэш-линии.

## На собеседовании

«Почему наивный MPMC буфер может работать медленнее, чем очередь с обычным `sync.Mutex`?». Ответ: из-за жесткой борьбы за атомарные счетчики `head` и `tail` при большом числе ядер (CAS retry storm). Мьютекс усыпляет ожидающие потоки в очередь планировщика ОС/рантайма, не перегружая кэш-шину, в то время как десятки горутин в CAS-цикле непрерывно генерируют запросы инвалидации кэшей.
