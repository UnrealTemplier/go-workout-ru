# Событийно-ориентированная обработка на базе кольцевых буферов (Event Processing)

## Условие

Спроектируйте архитектуру событийно-ориентированной обработки (EDA) на базе кольцевых буферов с маршрутизацией событий по типам между независимыми пулами воркеров.

### Исходная формулировка

**Ring buffer для event processing**: Используйте ring buffer для event-driven architecture. Producers publish events, consumers process events.

## Теория

В событийно-ориентированных архитектурах (Event-Driven Architecture) микросервисов прием входящего потока событий и их обработка должны быть строго изолированы:
1. **Event Ingestion Ring Buffer**: первичный кольцевой буфер принимает все сырые события от внешних протоколов (Kafka, Webhook, HTTP) с минимальной задержкой.
2. **Event Router / Dispatcher**: один высокоскоростной диспетчер вычитывает события из входного кольца и направляет их в специализированные кольцевые буферы соответствующих обработчиков (Billing, Analytics, Notifications).
3. **Изоляция сбоев (Failure Isolation)**: если обработчик уведомлений завис или работает медленно, его локальный буфер переполняется, но обработка биллинга продолжается на максимальной скорости.

## Решение по шагам

1. Определите тип события `DomainEvent` с кодом типа и полезной нагрузкой.
2. Реализуйте кольцевой буфер событий `EventRingBuffer`.
3. Создайте структуру диспетчера `EventDispatcher`, маршрутизирующего события по дочерним очередям.
4. Смоделируйте параллельную обработку заказов, оплат и уведомлений.
5. Продемонстрируйте изоляцию очередей и корректный shutdown.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type EventType int

const (
	EventOrderCreated EventType = iota
	EventPaymentReceived
	EventNotification
)

type DomainEvent struct {
	ID        int64
	Type      EventType
	Data      string
	Timestamp int64
}

type EventRingBuffer struct {
	buffer   []DomainEvent
	mask     uint64
	capacity uint64
	head     uint64
	tail     uint64
}

func NewEventRingBuffer(size uint64) *EventRingBuffer {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be power of 2")
	}
	return &EventRingBuffer{
		buffer:   make([]DomainEvent, size),
		mask:     size - 1,
		capacity: size,
	}
}

func (b *EventRingBuffer) Push(ev DomainEvent) bool {
	h := atomic.LoadUint64(&b.head)
	t := atomic.LoadUint64(&b.tail)
	if h-t >= b.capacity {
		return false
	}
	b.buffer[h&b.mask] = ev
	atomic.StoreUint64(&b.head, h+1)
	return true
}

func (b *EventRingBuffer) Pop() (DomainEvent, bool) {
	t := atomic.LoadUint64(&b.tail)
	h := atomic.LoadUint64(&b.head)
	if t >= h {
		return DomainEvent{}, false
	}
	ev := b.buffer[t&b.mask]
	atomic.StoreUint64(&b.tail, t+1)
	return ev, true
}

func main() {
	inboundRing := NewEventRingBuffer(1024)
	billingRing := NewEventRingBuffer(512)
	notifyRing := NewEventRingBuffer(512)

	var wg sync.WaitGroup
	stop := make(chan struct{})

	// 1. Dispatcher
	wg.Add(1)
	go func() {
		defer wg.Done()
		for {
			ev, ok := inboundRing.Pop()
			if ok {
				switch ev.Type {
				case EventOrderCreated, EventPaymentReceived:
					for !billingRing.Push(ev) {
						runtime.Gosched()
					}
				case EventNotification:
					for !notifyRing.Push(ev) {
						runtime.Gosched()
					}
				}
			} else {
				select {
				case <-stop:
					return
				default:
					runtime.Gosched()
				}
			}
		}
	}()

	// 2. Billing Worker
	var billingProcessed int64
	wg.Add(1)
	go func() {
		defer wg.Done()
		for {
			ev, ok := billingRing.Pop()
			if ok {
				atomic.AddInt64(&billingProcessed, 1)
				_ = ev
			} else {
				select {
				case <-stop:
					return
				default:
					runtime.Gosched()
				}
			}
		}
	}()

	// 3. Producer: генерируем события
	const totalEvents = 50000
	start := time.Now()
	for i := int64(1); i <= totalEvents; i++ {
		evType := EventNotification
		if i%2 == 0 {
			evType = EventPaymentReceived
		}
		ev := DomainEvent{
			ID:        i,
			Type:      evType,
			Data:      "payload",
			Timestamp: time.Now().UnixNano(),
		}
		for !inboundRing.Push(ev) {
			runtime.Gosched()
		}
	}

	time.Sleep(50 * time.Millisecond)
	close(stop)
	wg.Wait()

	fmt.Printf("Processed %d events in %v\n", totalEvents, time.Since(start))
	fmt.Printf("Billing Worker handled: %d events\n", atomic.LoadInt64(&billingProcessed))
}
```

ℹ️ Маршрутизация доменных событий через каскад кольцевых буферов.

## Под капотом

Схема «Один входной буфер -> Диспетчер -> Несколько специализированных очередей» минимизирует конкуренцию за кэш-линии. Диспетчер является единственным потребителем входного буфера и единственным производителем выходных буферов, благодаря чему все звенья работают по ультрабыстрому SPSC-протоколу без CAS-циклов.

## Подводные камни

1. Узкое горлышко в диспетчере: если логика маршрутизации сложная (парсинг JSON, обращение к БД), диспетчер станет узким местом. Диспетчер должен оперировать только легковесными числовыми тегами событий.
2. Потеря событий при переполнении входного кольца: продюсеры должны иметь политику реакции на переполнение (backpressure).

## На собеседовании

«Как паттерн Reactor / Proactor соотносится с кольцевыми буферами?». Ответ: движки на базе `io_uring` в Linux (а также сетевые серверы gnet) используют два кольцевых буфера ядра: Submission Queue (SQ) для передачи системных вызовов ядру и Completion Queue (CQ) для получения результатов без блокировок и системных прерываний.
