# Архитектурное сравнение: Ring Buffer против стандартных каналов Go

## Условие

Изучите внутреннее устройство каналов Go (`runtime.hchan`) и сравните их с кастомным lock-free Ring Buffer. Объясните на уровне исходников рантайма, почему кастомный кольцевой буфер обходит каналы по производительности при межгорутинной коммуникации.

### Исходная формулировка

**Ring buffer vs channel**: Go channels — это тоже ring buffers internally. Но custom ring buffer может быть быстрее (нет goroutine scheduling overhead).

## Теория

Стандартный канал Go (`chan T`) — один из самых мощных и удобных примитивов синхронизации, однако за его универсальность приходится платить производительностью.

**Анатомия канала в рантайме Go (`src/runtime/chan.go`):**
```go
type hchan struct {
    qcount   uint           // Количество элементов в буфере
    dataqsiz uint           // Емкость буфера
    buf      unsafe.Pointer // Указатель на массив элементов
    elemsize uint16
    closed   uint32
    elemtype *_type
    sendx    uint           // Индекс отправки
    recvx    uint           // Индекс приема
    recvq    waitq          // Список спящих горутин-получателей (sudog)
    sendq    waitq          // Список спящих горутин-отправителей (sudog)
    lock     mutex          // Внутренний spin-мьютекс рантайма!
}
```

**Почему кастомный SPSC/MPMC Ring Buffer быстрее канала?**
1. **Отсутствие мьютекса**: в `hchan` КАЖДАЯ операция `ch <- x` или `<-ch` захватывает `lock mutex`. В ring buffer блокировок нет вообще.
2. **Нулевые накладные расходы планировщика**: при блокировке канала рантайм создает структуру `sudog`, снимает горутину с потока \(M\) и ставит в очередь ожидания. В ring buffer используются атомики и локальное ожидание без смены контекста.
3. **Cache Locality и Padding**: в ring buffer указатели выравниваются по границам кэш-линий (64 байта), исключая False Sharing, тогда как в `hchan` поля сгруппированы вместе.

## Решение по шагам

1. Создайте сценарий профилирования отправки сообщений через `chan int64` и через lock-free кольцевой буфер.
2. Замерьте время на операцию в наносекундах (`ns/op`).
3. Исследуйте структуры `hchan` и `sudog` через вывод размеров типов `unsafe.Sizeof`.
4. Проанализируйте профиль задержек (Latency Distribution).
5. Сделайте вывод об архитектурных компромиссах.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type SPSC struct {
	buf  []int64
	mask uint64
	cap  uint64
	_pad0 [40]byte
	head uint64
	_pad1 [56]byte
	tail uint64
	_pad2 [56]byte
}

func NewSPSC(size uint64) *SPSC {
	return &SPSC{
		buf:  make([]int64, size),
		mask: size - 1,
		cap:  size,
	}
}

func (q *SPSC) Push(v int64) bool {
	h := atomic.LoadUint64(&q.head)
	t := atomic.LoadUint64(&q.tail)
	if h-t >= q.cap {
		return false
	}
	q.buf[h&q.mask] = v
	atomic.StoreUint64(&q.head, h+1)
	return true
}

func (q *SPSC) Pop() (int64, bool) {
	t := atomic.LoadUint64(&q.tail)
	h := atomic.LoadUint64(&q.head)
	if t >= h {
		return 0, false
	}
	v := q.buf[t&q.mask]
	atomic.StoreUint64(&q.tail, t+1)
	return v, true
}

func main() {
	const count = 1000000

	fmt.Println("=== Go Channel vs Lock-Free Ring Buffer ===")

	// 1. Benchmark SPSC
	{
		q := NewSPSC(4096)
		var wg sync.WaitGroup
		wg.Add(2)

		start := time.Now()
		go func() {
			defer wg.Done()
			for i := int64(0); i < count; i++ {
				for !q.Push(i) {
				}
			}
		}()

		go func() {
			defer wg.Done()
			for i := int64(0); i < count; i++ {
				for {
					if _, ok := q.Pop(); ok {
						break
					}
				}
			}
		}()

		wg.Wait()
		dur := time.Since(start)
		fmt.Printf("SPSC Ring Buffer: %v (%.2f ns/op)\n", dur, float64(dur.Nanoseconds())/count)
	}

	// 2. Benchmark Channel
	{
		ch := make(chan int64, 4096)
		var wg sync.WaitGroup
		wg.Add(2)

		start := time.Now()
		go func() {
			defer wg.Done()
			for i := int64(0); i < count; i++ {
				ch <- i
			}
		}()

		go func() {
			defer wg.Done()
			for i := int64(0); i < count; i++ {
				<-ch
			}
		}()

		wg.Wait()
		dur := time.Since(start)
		fmt.Printf("Go Channel:       %v (%.2f ns/op)\n", dur, float64(dur.Nanoseconds())/count)
	}
}
```

ℹ️ Сравнение накладных расходов Go Channel и SPSC кольцевого буфера.

## Под капотом

Канал Go спроектирован как универсальный координационный примитив для CSP (Communicating Sequential Processes). Он поддерживает `select` с несколькими каналами, неблокирующие проверки, закрытие `close(ch)` с уведомлением сотен горутин. Кастомный ring buffer оптимизирован исключительно под передачу данных между выделенными горутинами, поэтому в узком сценарии работает в 5–10 раз быстрее.

## Подводные камни

1. Преждевременная оптимизация: замена каналов на кастомные кольцевые буферы лишает код идиоматичности Go, усложняет чтение и отладку.
2. Невозможность интеграции с `select`: кастомный буфер нельзя использовать в стандартной конструкции `select { case ... }`.

## На собеседовании

«Что находится внутри переменной `var ch chan int`?». Ответ: переменная канала — это просто указатель на структуру `runtime.hchan` в куче (`*hchan`). Именно поэтому каналы в Go можно безопасно передавать по значению в функции и горутины без явного взятия адреса `&ch`.
