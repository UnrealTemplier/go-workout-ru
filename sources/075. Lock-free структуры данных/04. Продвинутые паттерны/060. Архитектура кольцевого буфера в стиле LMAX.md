# Архитектура кольцевого буфера в стиле LMAX Disruptor

## Условие

Изучите архитектурный паттерн LMAX Disruptor. Реализуйте упрощенную версию кольцевого буфера с разделением этапов публикации и подтверждения курсоров (Sequence Barrier / Cursor).

### Исходная формулировка

**MPMC implementation (Disruptor-style)**: Изучите LMAX Disruptor — high-performance MPMC ring buffer. Реализуйте упрощённую версию.

## Теория

Паттерн **LMAX Disruptor** был разработан для британской финансовой биржи LMAX Group с целью обработки 6+ миллионов финансовых ордеров в секунду с задержкой менее 1 микросекунды.

**Ключевые принципы Disruptor:**
1. **Pre-allocated Ring Buffer**: кольцевой массив предварительно аллоцированных объектов. Память выделяется один раз при старте программы, в рантайме нет никаких аллокаций в куче и работы для Garbage Collector.
2. **Курсоры последовательностей (Sequences)**: производители и потребители оперируют монотонно возрастающими 64-битными счетчиками (`int64`).
3. **Разделение Claim и Publish**:
   - `Claim(n)`: продюсер атомарно резервирует диапазон слотов.
   - Запись полезной нагрузки прямо в предварительно созданную структуру без копирования.
   - `Publish(sequence)`: публикация курсора, делающая элемент видимым для потребителей.
4. **Sequence Barrier (Барьер последовательностей)**: потребители отслеживают курсор продюсеров. Потребитель может вычитать пачкой все сообщения от текущего `consumedSeq` до `availableSeq` за одно чтение без лишних атомиков.

## Решение по шагам

1. Создайте структуру `OrderEvent` для финансовых транзакций.
2. Создайте `DisruptorRingBuffer` с фиксированным массивом событий и курсором `cursor int64`.
3. Реализуйте метод `Next() int64` для атомарного резервирования следующего слота.
4. Реализуйте метод `Publish(seq int64)` для публикации слота.
5. Напишите обработчик потребителя, читающий пачки событий до текущего курсора.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type OrderEvent struct {
	ID        int64
	Price     float64
	Quantity  int32
	Timestamp int64
}

type DisruptorRingBuffer struct {
	ring     []OrderEvent
	mask     int64
	capacity int64
	_pad0    [40]byte

	cursor    int64 // Максимальный зарезервированный номер
	_pad1     [56]byte

	published int64 // Максимальный опубликованный номер
	_pad2     [56]byte
}

func NewDisruptor(capacity int64) *DisruptorRingBuffer {
	if capacity <= 0 || (capacity&(capacity-1)) != 0 {
		panic("capacity must be a power of 2")
	}
	return &DisruptorRingBuffer{
		ring:      make([]OrderEvent, capacity),
		mask:      capacity - 1,
		capacity:  capacity,
		cursor:    -1,
		published: -1,
	}
}

// Next резервирует слот для записи
func (d *DisruptorRingBuffer) Next() int64 {
	return atomic.AddInt64(&d.cursor, 1)
}

// Get возвращает указатель на предварительно аллоцированный слот
func (d *DisruptorRingBuffer) Get(seq int64) *OrderEvent {
	return &d.ring[seq&d.mask]
}

// Publish публикует слот, делая его доступным консьюмерам
func (d *DisruptorRingBuffer) Publish(seq int64) {
	// В многопоточном режиме публикуем строго по порядку
	for {
		curPub := atomic.LoadInt64(&d.published)
		if curPub == seq-1 {
			atomic.StoreInt64(&d.published, seq)
			return
		}
		runtime.Gosched()
	}
}

// GetPublished возвращает максимальный доступный для чтения sequence
func (d *DisruptorRingBuffer) GetPublished() int64 {
	return atomic.LoadInt64(&d.published)
}

func main() {
	const count = 1000000
	disruptor := NewDisruptor(4096)

	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	// Producer
	go func() {
		defer wg.Done()
		for i := int64(0); i < count; i++ {
			seq := disruptor.Next()
			// Прямая запись в память без аллокаций
			slot := disruptor.Get(seq)
			slot.ID = i
			slot.Price = 100.50 + float64(i%100)
			slot.Quantity = int32(i % 10)
			slot.Timestamp = time.Now().UnixNano()

			disruptor.Publish(seq)
		}
	}()

	// Batching Consumer
	go func() {
		defer wg.Done()
		nextReadSeq := int64(0)
		for nextReadSeq < count {
			available := disruptor.GetPublished()
			if available >= nextReadSeq {
				// Пакетная обработка всех готовых сообщений
				for seq := nextReadSeq; seq <= available; seq++ {
					_ = disruptor.Get(seq)
				}
				nextReadSeq = available + 1
			} else {
				runtime.Gosched()
			}
		}
	}()

	wg.Wait()
	dur := time.Since(start)

	fmt.Printf("Disruptor processed %d orders in %v\n", count, dur)
	fmt.Printf("Throughput: %.2f M events/sec\n", float64(count)/dur.Seconds()/1e6)
}
```

ℹ️ Упрощенный LMAX Disruptor с разделением резервирования и пакетного чтения.

## Под капотом

В LMAX Disruptor чтение выполняется пачками (Batch Processing). Когда потребитель видит, что `availableSeq` ушел вперед на 500 элементов, он обрабатывает все 500 элементов в плотном линейном цикле. Это обеспечивает максимальную локальность ссылок в кэше процессора (L1 Instruction & Data Cache hit rate > 99%) и полное отсутствие переключений контекста.

## Подводные камни

1. Нарушение порядка при Publish: если поток 2 закончил подготовку раньше потока 1, он не может сразу обновить `published`, иначе консьюмер прочитает неинициализированный слот потока 1. Поэтому `Publish` ждет `seq - 1`.
2. Медленный потребитель: если производители обгонят потребителя на размер кольца, произойдет перезапись невычитанных данных. В production Disruptor требует отслеживания курсора самого медленного потребителя.

## На собеседовании

«В чем преимущество LMAX Disruptor над традиционными очередями на базе связанных списков?». Ответ: в связных списках каждый узел выделяется в куче (heap allocation), создавая фрагментацию памяти, нагрузку на GC и промахи кэша (Cache Misses). В Disruptor весь массив выделен в непрерывном блоке памяти один раз, работа с данными идет по указателям на постоянные слоты с нулевыми аллокациями.
