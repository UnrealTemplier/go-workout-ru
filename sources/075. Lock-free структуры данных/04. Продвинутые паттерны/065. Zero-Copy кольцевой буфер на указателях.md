# Zero-Copy кольцевой буфер на указателях для тяжелых сообщений

## Условие

Реализуйте высокопроизводительный Zero-Copy кольцевой буфер для крупных структур данных (например, сетевых пакетов размером 1500–9000 байт), устраняющий дорогостоящее копирование памяти при передаче между горутинами.

### Исходная формулировка

**Zero-copy ring buffer**: Для large items используйте ring buffer of pointers вместо ring buffer of values. Это избегает expensive copy.

## Теория

При передаче структур данных размером более 64–128 байт операция копирования памяти по значению (`val := buffer[idx]`) начинает доминировать над всеми остальными накладными расходами. Копирование 1 КБ данных занимает 50–100 наносекунд и сбрасывает кэш L1.

**Паттерн Zero-Copy Ring Buffer:**
1. Кольцевой буфер хранит не значения, а **указатели** на объекты: `[]*Packet` или `[]unsafe.Pointer`.
2. Пул объектов (Object Pool): чтобы избежать постоянного выделения памяти в куче через `new()`, используется пул предварительно аллоцированных буферов (`sync.Pool` или кастомный Free-list).
3. Производитель берет готовый свободный буфер из пула, наполняет его данными прямо из сети или диска и отправляет в кольцевой буфер **только указатель** (8 байт).
4. Потребитель забирает 8-байтный указатель, обрабатывает данные на месте и возвращает указатель обратно в пул свободных буферов.
5. Результат: ноль аллокаций, ноль копирований тяжелых массивов, максимальная скорость.

## Решение по шагам

1. Создайте структуру `NetworkPacket` с полезной нагрузкой `Payload [2048]byte`.
2. Создайте кольцевой буфер `ZeroCopyQueue` для указателей `*NetworkPacket`.
3. Создайте lock-free пул свободных пакетов.
4. Продемонстрируйте передачу 100 000 пакетов без копирования полезных данных.
5. Замерьте количество аллокаций памяти (`0 allocs/op`).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

const PacketSize = 2048

type NetworkPacket struct {
	ID      int64
	Length  int
	Payload [PacketSize]byte
}

type ZeroCopyQueue struct {
	buffer   []*NetworkPacket
	capacity uint64
	mask     uint64
	_pad0    [40]byte

	head uint64
	_pad1 [56]byte

	tail uint64
	_pad2 [56]byte
}

func NewZeroCopyQueue(size uint64) *ZeroCopyQueue {
	if size == 0 || (size&(size-1)) != 0 {
		panic("size must be power of 2")
	}
	return &ZeroCopyQueue{
		buffer:   make([]*NetworkPacket, size),
		capacity: size,
		mask:     size - 1,
	}
}

func (q *ZeroCopyQueue) Push(pkt *NetworkPacket) bool {
	h := atomic.LoadUint64(&q.head)
	t := atomic.LoadUint64(&q.tail)

	if h-t >= q.capacity {
		return false
	}

	q.buffer[h&q.mask] = pkt
	atomic.StoreUint64(&q.head, h+1)
	return true
}

func (q *ZeroCopyQueue) Pop() (*NetworkPacket, bool) {
	t := atomic.LoadUint64(&q.tail)
	h := atomic.LoadUint64(&q.head)

	if t >= h {
		return nil, false
	}

	pkt := q.buffer[t&q.mask]
	// Очищаем ссылку для помощи GC
	q.buffer[t&q.mask] = nil
	atomic.StoreUint64(&q.tail, t+1)
	return pkt, true
}

func main() {
	const totalPackets = 100000
	q := NewZeroCopyQueue(1024)

	// Пул пакетов для исключения постоянных аллокаций
	pool := &sync.Pool{
		New: func() interface{} {
			return &NetworkPacket{}
		},
	}

	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	// Producer
	go func() {
		defer wg.Done()
		for i := int64(1); i <= totalPackets; i++ {
			pkt := pool.Get().(*NetworkPacket)
			pkt.ID = i
			pkt.Length = PacketSize
			pkt.Payload[0] = byte(i % 255)

			for !q.Push(pkt) {
			}
		}
	}()

	// Consumer
	go func() {
		defer wg.Done()
		var count int
		for count < totalPackets {
			pkt, ok := q.Pop()
			if ok {
				count++
				// Обработка пакета на месте (In-place processing)
				_ = pkt.Payload[0]
				// Возврат в пул
				pool.Put(pkt)
			}
		}
	}()

	wg.Wait()
	dur := time.Since(start)

	totalMB := float64(totalPackets*PacketSize) / (1024 * 1024)
	fmt.Printf("Zero-Copy transferred %d packets (%.1f MB) in %v\n", totalPackets, totalMB, dur)
	fmt.Printf("Throughput: %.2f M pkts/sec (%.2f GB/sec)\n",
		float64(totalPackets)/dur.Seconds()/1e6, (totalMB/1024)/dur.Seconds())
}
```

ℹ️ Zero-Copy кольцевой буфер на указателях с повторным использованием памяти через sync.Pool.

## Под капотом

Обратите внимание на строку `q.buffer[t & q.mask] = nil` при извлечении указателя. Это критически важное действие для Go: если не занулять указатель в слоте кольцевого буфера, ссылка на объект будет удерживаться в памяти массива до следующего оборота кольца, что может препятствовать сборке мусора и приводить к скрытым утечкам памяти (Memory Leak / Retained Memory).

## Подводные камни

1. Гонка Use-After-Free при возврате в пул: если горутина вернула `pkt` в `sync.Pool`, но продолжила читать или писать в его поля, возникнет повреждение данных.
2. Неочищенные указатели в буфере: удержание старых указателей может заблокировать освобождение мегабайт памяти.

## На собеседовании

«Как zero-copy концепция реализована в сетевом стеке ядра Linux (например, `sendfile`, `splice` и `AF_XDP`)?». Ответ: традиционный сетевой ввод-вывод требует копирования данных из буфера сетевой карты (NIC ring) в пространство ядра (sk_buff), затем в память процесса (user space), затем обратно. `AF_XDP` и `sendfile` исключают промежуточные копирования: ядро передает сокету прямые дескрипторы DMA-памяти ring buffer сетевого адаптера.
