# Предельная производительность SPSC: почему архитектура без CAS доминирует в Low-Latency

## Условие

Проведите углубленный микроархитектурный анализ кольцевого буфера Single-Producer Single-Consumer (SPSC). Объясните, почему отсутствие инструкции CAS и блокировок делает SPSC самым быстрым алгоритмом межпоточного взаимодействия в компьютерных системах.

### Исходная формулировка

**SPSC ring buffer — fastest.**: Single-producer single-consumer ring buffer не требует CAS, только atomic load/store. Это в 10-100x быстрее, чем MPMC или Go channels.

## Теория

В мире ультранизких задержек (Ultra Low-Latency) каждый такт процессора имеет решающее значение.

**Сравнение микроархитектурных затрат:**
1. **MPMC на CAS (`LOCK CMPXCHG`)**:
   - Требует блокировки шины когерентности процессора (MESI протокол переходит в режим Exclusive/Modified).
   - Аппаратная задержка инструкции: **15–40 тактов процессора** даже при отсутствии конкуренции.
   - Сброс Store Buffer процессора.
2. **Очередь на мьютексах (`sync.Mutex`)**:
   - В лучшем случае: 1 атомарная операция CAS на захват + 1 атомарная операция Store на освобождение (~30 тактов).
   - В худшем случае: переключение контекста ОС / горутины (~1000–3000 тактов).
3. **SPSC Ring Buffer на чистых Load/Store**:
   - Чтение: обычная инструкция `MOV` из L1 кэша. Время: **1 такт (0.3 нс)**!
   - Запись данных: обычная инструкция `MOV` в память буфера.
   - Публикация указателя: `Store` с семантикой Release. На x86 это обычный `MOVQ`, так как модель Total Store Order (TSO) аппаратно гарантирует порядок записей!
   - Время операции: **менее 3–5 наносекунд**!

Именно поэтому ядро Linux, DPDK, Solarflare OpenOnload и биржевые движки строятся исключительно на цепочках SPSC очередей.

## Решение по шагам

1. Создайте структуру `UltraFastSPSC` с жестким cache-line выравниванием.
2. Реализуйте передачу данных между горутинами с замером задержки одного сообщения (Round-Trip Time).
3. Сравните RTT с Go channel.
4. Продемонстрируйте достижение производительности 50+ миллионов сообщений в секунду на одном ядре.
5. Зафиксируйте архитектурные выводы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type UltraFastSPSC struct {
	buffer   []uint64
	mask     uint64
	capacity uint64
	_pad0    [40]byte

	head uint64
	_pad1 [56]byte

	tail uint64
	_pad2 [56]byte
}

func NewUltraFastSPSC(size uint64) *UltraFastSPSC {
	return &UltraFastSPSC{
		buffer:   make([]uint64, size),
		mask:     size - 1,
		capacity: size,
	}
}

func (q *UltraFastSPSC) Push(val uint64) bool {
	h := atomic.LoadUint64(&q.head)
	t := atomic.LoadUint64(&q.tail)

	if h-t >= q.capacity {
		return false
	}

	q.buffer[h&q.mask] = val
	atomic.StoreUint64(&q.head, h+1)
	return true
}

func (q *UltraFastSPSC) Pop() (uint64, bool) {
	t := atomic.LoadUint64(&q.tail)
	h := atomic.LoadUint64(&q.head)

	if t >= h {
		return 0, false
	}

	val := q.buffer[t&q.mask]
	atomic.StoreUint64(&q.tail, t+1)
	return val, true
}

func main() {
	const count = 2000000
	q := NewUltraFastSPSC(4096)

	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()

	// Producer
	go func() {
		defer wg.Done()
		for i := uint64(1); i <= count; i++ {
			for !q.Push(i) {
			}
		}
	}()

	// Consumer
	go func() {
		defer wg.Done()
		var received uint64
		for received < count {
			if _, ok := q.Pop(); ok {
				received++
			}
		}
	}()

	wg.Wait()
	dur := time.Since(start)

	fmt.Println("=== SPSC Ultra Low-Latency Evaluation ===")
	fmt.Printf("Transferred %d messages in %v\n", count, dur)
	fmt.Printf("Average Latency: %.2f ns per message\n", float64(dur.Nanoseconds())/count)
	fmt.Printf("Throughput:      %.2f Million msgs/sec\n", float64(count)/dur.Seconds()/1e6)
}
```

ℹ️ Демонстрация предельной скорости SPSC кольцевого буфера без CAS.

## Под капотом

В архитектуре x86 память обладает сильной моделью памяти (Total Store Order). Это означает, что процессору x86 не требуются дорогостоящие барьеры памяти для операций Load и Store, в то время как операция CAS обязана использовать префикс `LOCK`, который принудительно захватывает шину когерентности кэшей. Поэтому SPSC работает со скоростью чистого чтения и записи в L1-кэш.

## Подводные камни

1. Ошибочное использование несколькими потоками: достаточно вызвать `Push` из двух параллельных горутин, и буфер мгновенно повредит данные без каких-либо паник или ошибок компиляции.
2. Процессорный троттлинг: при непрерывном 100% spin-wait ядро нагревается и процессор может снизить турбо-частоту.

## На собеседовании

«Если SPSC работает так быстро, почему в бэкенд-сервисах повсеместно используют каналы и MPMC очереди?». Ответ: потому что в реальных веб-сервисах архитектура редко сводится к строго одной горутине-писателю и одной горутине-читателю. Реальный микросервис обрабатывает сотни параллельных HTTP/gRPC запросов от пула клиентов, где естественным образом требуется модель Multi-Producer (MPMC).
