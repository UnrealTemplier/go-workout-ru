# Предотвращение утечки ресурсов в Keep-Alive соединениях через IdleTimeout

## Условие

Сконфигурируйте параметр IdleTimeout: 30 * time.Second в http.Server и объясните механизм очистки соединений, удерживаемых неактивными клиентами.

### Исходная формулировка

**IdleTimeout (Утечка Keep-Alive)**: Клиенты открывают соединения и "молчат". Установи `IdleTimeout: 30 * time.Second` (время жизни пустых Keep-Alive соединений). Если не установить, Go будет использовать значение `ReadTimeout`, что может быть неоптимально.

## Теория

HTTP Keep-Alive позволяет переиспользовать одно TCP-соединение для отправки множества HTTP-запросов. Однако клиенты (браузеры, пулы микросервисов) часто оставляют соединение открытым после завершения серии запросов. Если `IdleTimeout` не задан, Go использует значение `ReadTimeout`. Если же и `ReadTimeout` не задан, неактивные Keep-Alive соединения будут висеть часами, удерживая память и системные сокеты. `IdleTimeout` строго лимитирует время ожидания СЛЕДУЮЩЕГО запроса в уже открытом канале.

## Решение по шагам

Инициализируйте сервер с `IdleTimeout: 30 * time.Second`.
Установите `ReadTimeout: 60 * time.Second` для длинных запросов.
Выполните первый запрос с заголовком `Connection: keep-alive`.
Не отправляйте новые данные в течение 30 секунд.
Убедитесь, что сервер закрывает сокет через 30 секунд простоя, не дожидаясь 60 секунд ReadTimeout.

## Код решения

**`idle_timeout_server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/api/ping", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "pong")
	})

	srv := &http.Server{
		Addr:        ":8080",
		Handler:     mux,
		IdleTimeout: 30 * time.Second, // Сброс соединения при простое между запросами
		ReadTimeout: 60 * time.Second, // Длинный таймаут для передачи полезной нагрузки
	}

	fmt.Println("[SERVER] IdleTimeout 30s успешно настроен для Keep-Alive пула")
	_ = srv
}
```

ℹ️ Разделение таймаута простоя Keep-Alive и времени чтения запроса

## Под капотом

После успешной отправки ответа на предыдущий запрос сервер переводит сокет в состояние `http.StateIdle` и взводит дедлайн чтения на величину `IdleTimeout`. При получении первого байта следующего запроса дедлайн переключается на `ReadTimeout`.

## Подводные камни

Слишком короткий `IdleTimeout` (например, 1-2 секунды) приведет к постоянному разрыву соединений между легитимными микросервисами и росту затрат на повторные TLS-рукопожатия.

## На собеседовании

Вопрос на собеседовании: 'Клиент выполнил GET-запрос и держит TCP сокет открытым. Какой именно таймаут Go сервера сработает при бездействии клиента?' Ответ: Сработает IdleTimeout, а если он не задан — ReadTimeout.
