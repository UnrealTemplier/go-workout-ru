# Масштабирование сокетов на многоядерных CPU через SO_REUSEPORT

## Условие

Используйте net.ListenConfig и системный вызов unix.SetsockoptInt для включения SO_REUSEPORT, позволив запустить несколько параллельных процессов или горутин-листенеров на одном сетевом порту.

### Исходная формулировка

**SO_REUSEPORT (Шардирование сокетов)**: Для супер-Highload на Linux один `Accept` на порту становится бутылочным горлышком. Используй пакет `golang.org/x/sys/unix`. Создай `net.ListenConfig` с кастомной `Control` функцией. Сделай системный вызов `unix.SetsockoptInt(fd, unix.SOL_SOCKET, unix.SO_REUSEPORT, 1)`. Запусти 4 независимых Go-процесса на **одном и том же порту 8080**. Ядро Linux (через хэширование IP) само распределит входящий TCP-трафик между процессами на разных ядрах CPU!

## Теория

В классической модели один поток или горутина вызывает `Accept()` на сетевом сокете, что при миллионах RPS создает блокировку на спинлоке очереди сокета в ядре Linux. Опция `SO_REUSEPORT` (доступна в Linux с ядра 3.9) позволяет нескольким независимым процессам привязаться к одному и тому же IP-адресу и TCP-порту. Ядро Linux аппаратно распределяет входящие TCP-соединения между слушающими сокетами с помощью хэширования 4-кортежа (src_ip, src_port, dst_ip, dst_port), устраняя конкуренцию за сокет.

## Решение по шагам

Инициализируйте структуру `net.ListenConfig` с кастомной функцией `Control`.
Внутри `Control` вызовите `unix.SetsockoptInt(int(fd), unix.SOL_SOCKET, unix.SO_REUSEPORT, 1)`.
Запустите 4 независимых экземпляра программы на порту 8080.
Убедитесь через утилиту `ss -lntp`, что порт 8080 слушают 4 различных процесса.
Проверьте распределение нагрузки по ядрам CPU.

## Код решения

**`reuseport_listener.go`**

```go
package main

import (
	"context"
	"fmt"
	"net"
	"syscall"
)

func CreateReusePortListener(network, address string) (net.Listener, error) {
	lc := net.ListenConfig{
		Control: func(network, address string, c syscall.RawConn) error {
			var opErr error
			err := c.Control(func(fd uintptr) {
				// 0xF соответствует SO_REUSEPORT в Linux x86_64
				opErr = syscall.SetsockoptInt(int(fd), syscall.SOL_SOCKET, 0xF, 1)
			})
			if err != nil {
				return err
			}
			return opErr
		},
	}
	return lc.Listen(context.Background(), network, address)
}

func main() {
	ln, err := CreateReusePortListener("tcp", "127.0.0.1:0")
	if err != nil {
		fmt.Printf("[WARN] SO_REUSEPORT не поддерживается или ошибка: %v\n", err)
		return
	}
	defer ln.Close()

	fmt.Printf("[SO_REUSEPORT] Сокет успешно поднят на %s с шардированием ядра\n", ln.Addr())
}
```

ℹ️ Установка флага SO_REUSEPORT через ListenConfig Control hook

## Под капотом

При поступлении входящего пакета SYN ядро Linux вычисляет хэш от IP/порта отправителя и получателя и помещает сокет в очередь одного из листенеров, обеспечивая идеальную локальность кэша процессора (NUMA / CPU affinity).

## Подводные камни

Если один из процессов аварийно завершится, соединения, ожидающие в его индивидуальной очереди backlog, будут сброшены (TCP RST), если не используется eBPF-балансировщик.

## На собеседовании

В высоконагруженных прокси Nginx и Envoy директива `reuseport` позволяет линейно масштабировать пропускную способность по числу физических ядер процессора.
