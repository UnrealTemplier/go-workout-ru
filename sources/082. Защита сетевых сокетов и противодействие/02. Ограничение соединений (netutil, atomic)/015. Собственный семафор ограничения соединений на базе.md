# Собственный семафор ограничения соединений на базе атомарных счетчиков

## Условие

Реализуйте кастомную обертку net.Listener с атомарным счетчиком (sync/atomic) и лимитом maxConns = 100, немедленно сбрасывающую избыточные соединения через TCP RST или быстрый ответ 503.

### Исходная формулировка

**Connection Limits.**: Реализуйте `netutil.LimitListener` (или свой atomic-счётчик) с `maxConns = 100`. При превышении — новые соединения немедленно закрываются (`TCP RST` или `503` + `Connection: close`). Покажите, что это защищает от ресурс-исчерпания, но не от DDoS на уровне ядра (SYN flood).

## Теория

Стандартный `netutil.LimitListener` блокирует вызов `Accept()`, заставляя новые соединения ожидать в очереди ядра ОС. При интенсивном наплыве клиентов очередь переполняется, вызывая неконтролируемые задержки. Альтернативный подход — активный сброс (Active Rejection): сервис принимает соединение, но если лимит `maxConns` превышен, немедленно отправляет `HTTP/1.1 503 Service Unavailable\r\nConnection: close\r\n\r\n` и закрывает сокет, сигнализируя балансировщику о перегрузке ноды.

## Решение по шагам

Определите структуру `AtomicLimitListener` со счетчиком активных соединений.
В методе `Accept()` проверяйте счетчик через `atomic.AddInt64`.
Если лимит превышен — сбросьте счетчик, отправьте быстрый ответ 503 и вызовите `conn.Close()`.
При завершении легитимного соединения уменьшайте счетчик на единицу.
Протестируйте поведение под параллельной нагрузкой.

## Код решения

**`atomic_limit_listener.go`**

```go
package main

import (
	"fmt"
	"net"
	"sync/atomic"
)

type FastRejectListener struct {
	net.Listener
	maxConns    int64
	activeConns int64
}

func (l *FastRejectListener) Accept() (net.Conn, error) {
	conn, err := l.Listener.Accept()
	if err != nil {
		return nil, err
	}

	current := atomic.AddInt64(&l.activeConns, 1)
	if current > l.maxConns {
		atomic.AddInt64(&l.activeConns, -1)
		// Быстрый сброс с кодом 503
		_, _ = conn.Write([]byte("HTTP/1.1 503 Service Unavailable\r\nConnection: close\r\n\r\n"))
		_ = conn.Close()
		return nil, fmt.Errorf("превышен лимит одновременных соединений (%d)")
	}

	return &trackedConn{Conn: conn, listener: l}, nil
}

type trackedConn struct {
	net.Conn
	listener *FastRejectListener
	closed   int32
}

func (c *trackedConn) Close() error {
	if atomic.CompareAndSwapInt32(&c.closed, 0, 1) {
		atomic.AddInt64(&c.listener.activeConns, -1)
	}
	return c.Conn.Close()
}

func main() {
	fmt.Println("[LISTENER] FastRejectListener инициализирован (Active Rejection с 503).")
}
```

ℹ️ Активный сброс соединений при превышении лимита на уровне Accept

## Под капотом

Атомарные операции `atomic.CompareAndSwapInt32` гарантируют, что декремент счетчика выполнится строго один раз даже при многократном вызове `Close()` из разных горутин.

## Подводные камни

Возврат ошибки из метода `Accept()` заставляет серверный цикл Go сделать небольшую паузу (sleep 5ms), поэтому в ряде случаев выгоднее возвращать специальную фиктивную сессию, закрываемую сервером.

## На собеседовании

В чем разница между стратегиями Backpressure: блокирующий LimitListener vs Fast Reject? Блокирующий подходит для краткосрочных всплесков, а Fast Reject идеален для микросервисов за Service Mesh/Envoy для быстрого ретрая на другие поды.
