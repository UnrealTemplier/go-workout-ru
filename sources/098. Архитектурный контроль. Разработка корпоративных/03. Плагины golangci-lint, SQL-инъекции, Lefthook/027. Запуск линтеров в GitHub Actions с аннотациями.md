# Запуск линтеров в GitHub Actions с аннотациями в PR

## Условие

Настройте рабочий процесс CI/CD в GitHub Actions для проверки архитектурных правил: использование официального флага --out-format=github-actions, генерация встроенных аннотаций прямо в коде Pull Request (Inline Annotations) и блокировка слияния невалидного кода через branch protection rules.

### Исходная формулировка

**Запуск линтеров в GitHub Actions с аннотациями в PR**: Настройте CI-пайплайн: запуск golangci-lint run --out-format=github-actions. Продемонстрируйте, как сообщения об ошибках вашего кастомного линтера автоматически подсвечиваются прямо в интерфейсе GitHub Pull Request на строках коммита.

## Теория

В современных процессах разработки отчет линтера в виде сырого консольного лога на 5000 строк текста никто не читает.

Флаг `--out-format=github-actions` заставляет `golangci-lint` выводить ошибки в специальном синтаксисе метакоманд GitHub Runner Workflow:
`::error file={name},line={line},col={col}::{message}`

Когда GitHub Actions видит такой вывод в stdout:
1) В интерфейсе Pull Request на вкладке **Files Changed** на соответствующей строке автоматически появляется красная плашка с точным текстом ошибки;
2) Разработчик видит замечание линтера точно так же, как если бы его оставил живой сеньор-разработчик на ревью;
3) Пайплайн падает с кодом 1, предотвращая автоматический мерж.

## Решение по шагам

Создать файл workflow `.github/workflows/lint.yml`.
Настроить шаг кэширования модулей `actions/setup-go` с параметром `cache: true`.
Запустить команду проверки с флагом `--out-format=github-actions`.
Продемонстрировать отображение inline-аннотации на строке коммита.

## Код решения

**`github_actions_workflow.go`**

```go
package main

import (
	"fmt"
)

// GenerateGitHubActionsWorkflow генерирует YAML пайплайна CI/CD
func GenerateGitHubActionsWorkflow() string {
	return `
name: "Architectural Lint & Code Quality"

on:
  pull_request:
    branches: [ main, master ]
  push:
    branches: [ main, master ]

jobs:
  golangci:
    name: "Run Corporate Linters"
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true

      # Запуск с официальным форматом вывода GitHub Actions
      - name: "Run Custom golangci-lint"
        run: |
          golangci-lint run \
            --out-format=github-actions \
            --timeout=5m \
            --issues-exit-code=1
`
}

func main() {
	fmt.Println("=== GitHub Actions: Запуск линтеров с Inline Annotations ===")
	fmt.Println(GenerateGitHubActionsWorkflow())
	fmt.Println("При флаге '--out-format=github-actions' линтер выводит специальные команды:")
	fmt.Println("::error file=main.go,line=42,col=5::Запрещен context.Background() в бизнес-логике")
	fmt.Println("GitHub автоматически подсвечивает эту строку красным прямо в диффе Pull Request!")
}
```

## Под капотом

GitHub Runner парсит stdout каждого шага регулярным выражением на префикс `::error` и `::warning`. Обнаружив совпадение, runner через внутренний REST API GitHub регистрирует объект Check Run Annotation, привязанный к SHA коммита.

## Подводные камни

Неправильный путь к файлу в монорепозитории (если линтер запускается из подкаталога, аннотации не смогут привязаться к корню репозитория).
Превышение лимита GitHub на количество аннотаций (максимум 50 аннотаций на один Check Run).
Забытый флаг `--issues-exit-code=1`, из-за чего шаг линтера завершается с успехом даже при наличии ошибок.

## На собеседовании

Как не допустить замедления CI при запуске линтера на тысячах пакетов? Ответ: Использовать кэширование каталога `~/.cache/golangci-lint` и `~/.cache/go-build` в GitHub Actions через `actions/cache`. При повторных запусках линтер переиспользует результаты проверки неизмененных пакетов, сокращая время выполнения с 3 минут до 15 секунд.
