# Интеграция через Module Plugins в golangci-lint

## Условие

Динамические плагины .so хрупки и не работают на Windows. Освойте официальный механизм Module Plugins в golangci-lint: декларативный файл конфигурации .custom-gcl.yml, утилиту golangci-lint custom и статическую компиляцию монолитного корпоративного бинарника линтера со встроенными анализаторами компании.

### Исходная формулировка

**Интеграция через Module Plugins в golangci-lint**: Начиная с современных версий golangci-lint, плагины можно компилировать напрямую без CGO с помощью утилиты сборки кастомного бинарника. Настройте конфигурацию сборки кастомного golangci-lint со встроенными корпоративными анализаторами компании.

## Теория

Для решения проблем с динамическими плагинами создатели `golangci-lint` разработали команду `golangci-lint custom` (Module Plugins).

Принцип работы:
1) Создается манифест `.custom-gcl.yml`:
```yaml
version: v1.60.0
plugins:
  - module: 'github.com/mycompany/governance-linters'
    import: 'github.com/mycompany/governance-linters/pkg/rules'
    version: v1.2.0
```
2) Запускается команда `golangci-lint custom`;
3) Утилита скачивает Go-модули ваших линтеров, генерирует обертку `main.go` и статически компилирует единый самодостаточный бинарный файл `custom-gcl`;
4) Полученный бинарник распространяется среди разработчиков и в Docker-образах CI/CD. Он на 100% стабилен, работает без CGO на любой ОС (Linux, macOS, Windows) и запускается мгновенно.

## Решение по шагам

Спроектировать манифест `.custom-gcl.yml` с указанием версии базового линтера и модулей плагинов.
Реализовать экспорт структуры анализатора из корпоративного Go-модуля.
Выполнить сборку через `golangci-lint custom`.
Проверить работу собственного бинарника командой `./custom-gcl linters`.

## Код решения

**`custom_gcl_builder.go`**

```go
package main

import (
	"fmt"
)

// ExplainModulePlugins демонстрирует статическую сборку golangci-lint с линтерами
func ExplainModulePlugins() {
	fmt.Println("=== Статическая интеграция через Module Plugins в golangci-lint ===")
	fmt.Println()
	fmt.Println("Современный стандарт без CGO и без проблем с версиями (golangci-lint custom):")
	fmt.Println("1. Создание манифеста сборщика .custom-gcl.yml:")
	fmt.Println("   version: v1.60.0")
	fmt.Println("   plugins:")
	fmt.Println("     - module: 'github.com/mycompany/linters'")
	fmt.Println("       import: 'github.com/mycompany/linters/cleanarch'")
	fmt.Println("       version: v1.0.0")
	fmt.Println()
	fmt.Println("2. Команда сборки корпоративного бинарника:")
	fmt.Println("   golangci-lint custom")
	fmt.Println()
	fmt.Println("3. Результат: Единый монолитный бинарник ./custom-gcl со всеми встроенными")
	fmt.Println("   корпоративными анализаторами, работающий на любой ОС без CGO и .so файлов!")
}

func main() {
	ExplainModulePlugins()
}
```

## Под капотом

Команда `custom` под капотом разворачивает временный модуль Go в каталоге кэша, генерирует код вызова конструкторов линтеров, запускает стандартный компилятор `go build -o custom-gcl` и очищает временные артефакты.

## Подводные камни

Конфликт версий транзитивных зависимостей между `golangci-lint` и вашим линтером (требуется выравнивание go.mod).
Отсутствие тэга версии в Git-репозитории кастомного линтера при сборке через модуль.
Забытое обновление версии базового golangci-lint в манифесте.

## На собеседовании

Как распространять кастомный корпоративный `golangci-lint` среди 500 разработчиков компании? Ответ: Собирать бинарник `custom-gcl` в базовый Docker-образ CI/CD и выкладывать мультиплатформенные бинарники (linux/amd64, darwin/arm64, windows/amd64) во внутренний реестр Nexus/Artifactory с автоматическим обновлением через корпоративный менеджер пакетов (brew tap или asdf plugin).
