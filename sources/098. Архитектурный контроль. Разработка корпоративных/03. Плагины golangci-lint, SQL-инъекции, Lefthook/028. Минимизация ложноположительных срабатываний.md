# Минимизация ложноположительных срабатываний (False Positives)

## Условие

Линтер, генерирующий ложные срабатывания (False Positives), вызывает раздражение разработчиков и быстро отключается командой. Разработайте механизм подавления предупреждений через директивы комментариев //nolint:mylinter с обязательным указанием причины, а также учет интерфейсных методов и сгенерированного кода (code generated).

### Исходная формулировка

**Минимизация ложноположительных срабатываний (False Positives)**: Протестируйте анализатор на популярных open-source проектах (например, gin, prometheus). Найдите ложные срабатывания, добавьте учет директив подавления //nolint:myanalyzer и специальных интерфейсных исключений.

## Теория

Качество статического анализатора измеряется не тем, сколько предупреждений он нашел, а отношением полезного сигнала к шуму (Signal-to-Noise Ratio).

Если анализатор выдает ложную ошибку в легитимном краевом случае (например, в автогенерированном protobuf-коде или в разовой миграционной утилите), у разработчика должен быть цивилизованный способ подавить проверку.

Стандарты чистоты линтеров:
1) **Игнорирование сгенерированных файлов**: Первая строка файла проверяется на маркер `^// Code generated .* DO NOT EDIT\.$`;
2) **Директивы подавления**: Анализатор парсит `file.Comments` на наличие `//nolint:analyzer_name`;
3) **Запрет слепого `//nolint`**: Требовать обязательного указания конкретного имени правила и комментария с обоснованием (`//nolint:nobackground // legacy code, ticket JIRA-1234`).

## Решение по шагам

Использовать флаг `parser.ParseComments` для сохранения комментариев в AST.
Реализовать проверку заголовка файла на сгенерированный код `astutil.IsGenerated`.
Написать функцию сопоставления номеров строк комментариев с диагностиками.
Проверить работу точечного подавления ошибки директивой `//nolint`.

## Код решения

**`nolint_suppression.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"strings"
)

// NolintDetector проверяет наличие директив подавления //nolint
type NolintDetector struct{}

func (d *NolintDetector) IsSuppressed(comments []*ast.CommentGroup, targetPos token.Pos, fset *token.FileSet, linterName string) bool {
	targetLine := fset.Position(targetPos).Line

	for _, cg := range comments {
		for _, c := range cg.List {
			commentLine := fset.Position(c.Pos()).Line
			// Если комментарий находится на той же строке или прямо над ней
			if commentLine == targetLine || commentLine == targetLine-1 {
				text := c.Text
				if strings.Contains(text, "//nolint") {
					// Если указан конкретный линтер (например, //nolint:nobackground) или глобальный //nolint
					if strings.Contains(text, linterName) || text == "//nolint" {
						return true
					}
				}
			}
		}
	}
	return false
}

func main() {
	fmt.Println("=== Минимизация False Positives и поддержка //nolint ===")
	src := `package main

import "context"

func LegacyMigration() {
	//nolint:nobackground // Осознанное исключение для разовой миграции
	ctx := context.Background()
	_ = ctx
}
`
	fset := token.NewFileSet()
	file, _ := parser.ParseFile(fset, "migration.go", src, parser.ParseComments)

	detector := &NolintDetector{}
	// Проверяем строку с вызовом
	suppressed := detector.IsSuppressed(file.Comments, token.Pos(65), fset, "nobackground")
	fmt.Printf("Подавление директивой //nolint:nobackground активно: %v\n", suppressed)
	fmt.Println("Результат: Анализатор не выдает ошибку, сохраняя гибкость для легитимных исключений.")
}
```

## Под капотом

В `golangci-lint` встроен специальный процессор `nolintlint`. Он следит за культурой подавлений: запрещает глобальные `//nolint` без имени линтера и предупреждает, если директива `//nolint` висит на строке, где линтер на самом деле не находит никаких ошибок (Unused nolint directive).

## Подводные камни

Игнорирование комментариев внутри многострочных блоков `/* ... */`.
Подавление всех последующих строк файла вместо одной целевой строки.
Пропуск сгенерированных файлов из-за опечатки в регулярке `Code generated`.

## На собеседовании

Почему в Google запрещено ставить `//nolint` без ссылки на задачу в трекере? Ответ: Потому что подавление проверки без обоснования превращается в способ замаскировать технический долг. Требование формата `//nolint:rule // TODO(username): JIRA-123 reason` гарантирует, что у каждого исключения есть ответственный автор и запланированный срок устранения.
