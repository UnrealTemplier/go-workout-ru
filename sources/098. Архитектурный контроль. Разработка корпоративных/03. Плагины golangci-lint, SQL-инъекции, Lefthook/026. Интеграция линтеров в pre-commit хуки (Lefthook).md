# Интеграция линтеров в pre-commit хуки (Lefthook)

## Условие

Если проверки линтера работают только в CI, разработчик тратит десятки минут на цикл 'коммит -> пуш -> ожидание пайплайна -> ошибка'. Настройте скоростной запуск линтеров на этапе Git Pre-Commit с помощью инструмента Lefthook на Go: фильтрация только измененных файлов ({staged_files}), параллельный запуск и время отклика менее 1 секунды.

### Исходная формулировка

**Интеграция линтеров в pre-commit хуки (Lefthook)**: Настройте быстрый запуск анализаторов перед коммитом с помощью lefthook или pre-commit: запуск проверок только для измененных файлов (git diff --staged) для мгновенной обратной связи разработчику (менее 1 секунды).

## Теория

Инженерная обратная связь (Feedback Loop) тем эффективнее, чем ближе она к моменту написания кода.

Проблема стандартных pre-commit хуков на Python/Bash — медлительность: запуск проверки всего проекта занимает 30 секунд, из-за чего разработчики начинают коммитить с флагом `--no-verify`.

**Lefthook** — сверхбыстрый менеджер Git-хуков, написанный на Go:
1) **Параллелизм (`parallel: true`)**: запускает несколько линтеров одновременно на всех ядрах CPU;
2) **Селективность (`{staged_files}`)**: передает линтеру не весь проект из миллиона строк, а только те 3 файла, которые разработчик добавил в индекс `git add`;
3) **Фокус на новом коде**: аргумент `--new-from-rev=HEAD~1` заставляет линтер анализировать только измененные строки.
В результате проверка выполняется за 300–600 миллисекунд прямо в момент нажатия Enter в терминале или IDE.

## Решение по шагам

Установить Lefthook в проект через `go install github.com/evilmartians/lefthook@latest`.
Спроектировать файл конфигурации `lefthook.yml`.
Настроить фильтрацию файлов по маске `*.go` и подстановку плейсхолдера `{staged_files}`.
Проверить запуск хука при попытке коммита с нарушением архитектурного правила.

## Код решения

**`lefthook_integration.go`**

```go
package main

import (
	"fmt"
)

// GenerateLefthookConfig генерирует конфигурацию ультрабыстрых pre-commit хуков
func GenerateLefthookConfig() string {
	return `
# lefthook.yml — скоростные pre-commit проверки перед коммитом
pre-commit:
  parallel: true
  commands:
    # Проверка только проиндексированных файлов (staged files)
    golangci-lint:
      tags: backend style
      glob: "*.go"
      run: golangci-lint run --new-from-rev=HEAD~1 {staged_files}
    
    # Быстрая проверка форматирования
    gofmt:
      tags: backend style
      glob: "*.go"
      run: gofumpt -l {staged_files}

    # Проверка архитектурных линтеров компании
    corporate-linters:
      tags: architecture
      glob: "*.go"
      run: custom-gcl run {staged_files}
`
}

func main() {
	fmt.Println("=== Интеграция линтеров в pre-commit хуки (Lefthook) ===")
	fmt.Println(GenerateLefthookConfig())
	fmt.Println("Преимущество Lefthook: Параллельный запуск на Go, фильтрация staged_files")
	fmt.Println("и мгновенная обратная связь разработчику менее чем за 500 миллисекунд!")
}
```

## Под капотом

Lefthook выполняет команду `git diff --name-only --cached --diff-filter=ACMR` для мгновенного получения списка файлов в оперативной памяти и запускает процессы линтеров в параллельных горутинах через `os/exec`.

## Подводные камни

Передача полного пути к файлам, ломающая относительные пути импортов модулей Go.
Использование медленных bash-скриптов с циклом for по файлам вместо пакетной передачи списка аргументов.
Отсутствие автоматической установки хуков при вызове `go mod download` или `make init`.

## На собеседовании

Почему фильтрация staged_files в pre-commit хуках критична для монорепозиториев? Ответ: В монорепозитории размером в 5 миллионов строк запуск полного линтинга занимает 2–3 минуты. Проверка только 2–3 файлов из staged_files занимает 0.4 секунды, не раздражая разработчика и гарантируя, что некачественный код никогда не попадет в Git.
