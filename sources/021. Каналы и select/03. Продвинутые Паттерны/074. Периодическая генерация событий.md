# Периодическая генерация событий: time.Tick и завершение по таймауту

## Условие

Тикер: каждые 500 мс отправлять в канал `time.Tick`, основная горутина читает и выводит «tick», пока не истечёт таймаут.

## Теория

`time.Tick(d)` возвращает канал, в который рантайм периодически отправляет метки времени `time.Time`.

## Решение по шагам

1. Создадим канал тиков `ticker := time.Tick(15 * time.Millisecond)`.
2. Создадим канал завершения `timeout := time.After(50 * time.Millisecond)`.
3. В цикле `select` считываем тики.
4. По истечении таймаута штатно выходим.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	tickChan := time.Tick(15 * time.Millisecond)
	timeoutChan := time.After(50 * time.Millisecond)

	fmt.Println("Старт периодического опроса:")
	count := 0

	for {
		select {
		case t := <-tickChan:
			count++
			fmt.Printf(" [Tick #%d] Сработал тик в %s\n", count, t.Format("15:04:05.000"))
		case <-timeoutChan:
			fmt.Println("Общий таймаут истек! Завершение цикла тиков.")
			return
		}
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Старт периодического опроса:
#  [Tick #1] Сработал тик в 15:04:05.015
#  [Tick #2] Сработал тик в 15:04:05.030
#  [Tick #3] Сработал тик в 15:04:05.045
# Общий таймаут истек! Завершение цикла тиков.
```

## Под капотом

`time.Tick` оборачивает `time.NewTicker`, но не экспортирует метод `Stop()`.

## Подводные камни

Никогда не используйте `time.Tick` внутри долгоживущих методов и хендлеров, так как лежащий в его основе тикер невозможно остановить (утечка памяти). Используйте `time.NewTicker`.

## На собеседовании

**Вопрос с собеседования:** «Почему официальная документация Go не рекомендует использовать time.Tick в большинстве случаев?»
**Ответ:** Потому что `time.Tick` не возвращает объект тикера и не предоставляет метод `Stop()`. Созданный тикер и его горутина никогда не удаляются сборщиком мусора, вызывая постоянную утечку памяти при многократных вызовах.
