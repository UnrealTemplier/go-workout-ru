# Ловушка утечки памяти с time.After в цикле select и рефакторинг на time.NewTimer

## Условие

**Каверзный `time.After` в цикле**: Напиши `for` с `select`, внутри которого есть `case <-time.After(...)`. Изучи (в теории или профилировщиком), почему это вызывает **утечку памяти** (на каждой итерации создается новый таймер, который висит в памяти до срабатывания). Вынеси `time.NewTimer` перед циклом.

### Исходная формулировка

**Каверзный `time.After` в цикле**: Напиши `for` с `select`, внутри которого есть `case <-time.After(...)`. Изучи (в теории или профилировщиком), почему это вызывает **утечку памяти** (на каждой итерации создается новый таймер, который висит в памяти до срабатывания). Вынеси `time.NewTimer` перед циклом.

## Теория

Критическая архитектурная ловушка: вызов `time.After(5 * time.Minute)` внутри частого цикла `for select` создает новый объект `runtime.timer` на каждой итерации. Если сообщения поступают каждые 10 мс, за 5 минут создается \(30\,000\) таймеров, которые не могут быть удалены сборщиком мусора до их срабатывания! Решение — создание единого `time.NewTimer` перед циклом со сбросом `timer.Reset()`.

## Решение по шагам

1. Создадим поток частых сообщений `stream := make(chan int)`.
2. Создадим один таймер перед циклом: `timer := time.NewTimer(timeout)`.
3. На каждой итерации сбрасываем таймер через `timer.Reset()`.
4. Убедимся в отсутствии утечки таймеров.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	stream := make(chan int)

	// Продюсер шлет 4 быстрых сообщения
	go func() {
		for i := 1; i <= 4; i++ {
			time.Sleep(10 * time.Millisecond)
			stream <- i
		}
		close(stream)
	}()

	const idleTimeout = 50 * time.Millisecond

	// ПРАВИЛЬНОЕ РЕШЕНИЕ: один таймер перед циклом
	timer := time.NewTimer(idleTimeout)
	defer timer.Stop()

	fmt.Println("Обработка потока с защитой от утечек таймеров:")

	for {
		// Сбрасываем существующий таймер перед каждой итерацией
		if !timer.Stop() {
			select {
			case <-timer.C:
			default:
			}
		}
		timer.Reset(idleTimeout)

		select {
		case val, ok := <-stream:
			if !ok {
				fmt.Println("Поток успешно завершен!")
				return
			}
			fmt.Printf(" -> Обработан элемент: %d (таймер сброшен)\n", val)

		case <-timer.C:
			fmt.Println("ТАЙМАУТ: Превышен лимит простоя потока!")
			return
		}
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Обработка потока с защитой от утечек таймеров:
#  -> Обработан элемент: 1 (таймер сброшен)
#  -> Обработан элемент: 2 (таймер сброшен)
#  -> Обработан элемент: 3 (таймер сброшен)
#  -> Обработан элемент: 4 (таймер сброшен)
# Поток успешно завершен!
```

## Под капотом

Сброс `timer.Reset()` переиспользует существующую структуру таймера в куче.

## Подводные камни

В Go 1.23+ поведение `time.Timer` улучшено (таймеры удаляются GC сразу после потери ссылок), но паттерн с `NewTimer` и `Reset` остается стандартом для HighLoad систем.

## На собеседовании

**Вопрос с собеседования:** «Почему перед вызовом timer.Reset(d) необходимо вызвать timer.Stop() и очистить timer.C?»
**Ответ:** Чтобы исключить ложное мгновенное срабатывание таймера, если старый таймер уже успел отправить событие в буферизованный канал `timer.C` до вызова `Reset`.
