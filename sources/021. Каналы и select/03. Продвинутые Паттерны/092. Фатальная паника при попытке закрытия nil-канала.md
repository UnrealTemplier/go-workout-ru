# Фатальная паника при попытке закрытия nil-канала (panic: close of nil channel)

## Условие

**Каверзный случай**: Что произойдет, если попытаться закрыть `nil`-канал? (Паника).

## Теория

Попытка вызова `close(ch)` на неинициализированном канале `nil` немедленно вызывает фатальную панику `panic: close of nil channel`.

## Решение по шагам

1. Создадим переменную `var nilChan chan int`.
2. Вызовем `close(nilChan)` внутри защищенной функции `defer recover()`.
3. Перехватим и проанализируем текст паники.
4. Проверим корректность.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func safeCloseNilChannel() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("Перехвачена критическая паника: %v\n", r)
		}
	}()

	var nilChan chan int
	fmt.Println("Попытка закрытия nil-канала: close(nilChan)...")
	close(nilChan) // ВЫЗЫВАЕТ ПАНИКУ: close of nil channel
}

func main() {
	safeCloseNilChannel()
	fmt.Println("Программа штатно продолжила работу после обработки паники.")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Попытка закрытия nil-канала: close(nilChan)...
# Перехвачена критическая паника: close of nil channel
# Программа штатно продолжила работу после обработки паники.
```

## Под капотом

В функции `closechan` первой строкой выполняется проверка: `if c == nil { panic(plainError("close of nil channel")) }`.

## Подводные камни

Всегда проверяйте `if ch != nil { close(ch) }`, если канал может быть не инициализирован.

## На собеседовании

**Вопрос с собеседования:** «Почему close(nil) паникует, а чтение/запись на nil-канале блокируются?»
**Ответ:** Блокировка чтения/записи на nil-канале необходима для работы динамического отключения веток в `select`. Закрытие же nil-канала не имеет никакого практического смысла и указывает на грубую ошибку инициализации структуры.
