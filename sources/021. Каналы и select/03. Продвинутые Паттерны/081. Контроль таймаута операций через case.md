# Контроль таймаута операций через case <-time.After() в select

## Условие

**Таймаут через `select`**: Добавь в `select` case: `case <-time.After(2 * time.Second):`. Убедись, что если данные не приходят 2 секунды, срабатывает этот таймаут.

## Теория

Шаблон таймаута на `time.After()` гарантирует верхнюю границу ожидания для любой синхронной операции.

## Решение по шагам

1. Создадим канал `data := make(chan int)`.
2. Запустим `select` с ожиданием данных или таймаута 30 мс.
3. Продемонстрируем безопасный выход.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	data := make(chan int)

	fmt.Println("[Client] Ожидание поступления данных с таймаутом 30мс...")

	select {
	case val := <-data:
		fmt.Printf("[Client] Успешно получены данные: %d\n", val)
	case <-time.After(30 * time.Millisecond):
		fmt.Println("[Client] ТАЙМАУТ: Данные не поступили в течение 30мс -> безопасный выход!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Client] Ожидание поступления данных с таймаутом 30мс...
# [Client] ТАЙМАУТ: Данные не поступили в течение 30мс -> безопасный выход!
```

## Под капотом

`time.After` запускает таймер в фоновом рантайме таймеров Go.

## Подводные камни

Не забывайте, что таймер создается заново при каждом вызове `time.After()`.

## На собеседовании

**Вопрос с собеседования:** «Что происходит с каналом time.After, если данные из рабочего канала пришли раньше таймаута?»
**Ответ:** Рабочая ветка успешно отрабатывает, но канал таймера и его внутренний объект `runtime.timer` остаются в памяти до фактического истечения времени таймаута, после чего собираются GC.
