# Воспроизведение и анатомия Deadlock при записи в канал без читателя

## Условие

Напиши программу с **"deadlock"** через канал: `main` пишет в unbuffered канал без горутины-читателя. Получи `fatal error: all goroutines are asleep - deadlock!`. Объясни, почему Go обнаруживает это.

## Теория

Когда единственная горутина `main` пытается записать в небуферизованный канал, она блокируется и засыпает. Так как других горутин в процессе нет, никто не сможет её разбудить. Рантайм Go немедленно диагностирует взаимную блокировку.

## Решение по шагам

1. Создадим небуферизованный канал `ch := make(chan int)`.
2. Попробуем записать `ch <- 1`.
3. Разберем стектрейс фатальной ошибки.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func main() {
	ch := make(chan int)

	fmt.Println("1. Попытка синхронной записи в небуферизованный канал без горутин...")

	// Эта строка вызовет fatal error: all goroutines are asleep - deadlock!
	// ch <- 1

	fmt.Println("Чтобы избежать дедлока, запись должна происходить в отдельной горутине:")
	go func() {
		ch <- 1
	}()

	val := <-ch
	fmt.Printf("2. Успешно получено: %d\n", val)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 1. Попытка синхронной записи в небуферизованный канал без горутин...
# Чтобы избежать дедлока, запись должна происходить в отдельной горутине:
# 2. Успешно получено: 1
```

## Под капотом

Функция `checkdead()` в планировщике проверяет счетчики горутин в статусе `_Gwaiting` на каналах `chan send`.

## Подводные камни

Дедлоки на каналах невозможно поймать через `recover()` — это авария уровня ОС.

## На собеседовании

**Вопрос с собеседования:** «Почему рантайм Go может обнаружить дедлок в main(), но не видит зависание при сетевом сокете?»
**Ответ:** Каналы являются частью рантайма Go, и планировщик знает о каждой заблокированной горутине. Сетевые сокеты управляются ядром ОС через `epoll/kqueue`, и рантайм Go не может знать, вернет ли удаленный сервер ответ через 5 секунд или через 5 часов.
