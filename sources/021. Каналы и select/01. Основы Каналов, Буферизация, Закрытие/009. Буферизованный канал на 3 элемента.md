# Буферизованный канал на 3 элемента: отправка 5 сообщений и Backpressure

## Условие

Буферизированный канал ёмкостью 3: отправьте 5 значений в горутине, читайте в main с задержкой. Проверьте блокировку отправителя при заполнении.

## Теория

Буферизованный канал выступает амортизатором всплесков нагрузки (Burst Absorber). Если продюсер производит быстрее, чем консумер потребляет, первые 3 элемента помещаются в буфер без задержек, а на 4-м элементе продюсер приостанавливается (Backpressure).

## Решение по шагам

1. Создадим `ch := make(chan int, 3)`.
2. В горутине запишем 5 чисел с логированием.
3. В `main` читаем с задержкой `time.Sleep(30 * time.Millisecond)`.
4. Проследим блокировку отправителя.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan int, 3)

	// Продюсер
	go func() {
		for i := 1; i <= 5; i++ {
			fmt.Printf("[Producer] Попытка отправки #%d (текущий len=%d)...\n", i, len(ch))
			ch <- i
			fmt.Printf(" -> [Producer] Элемент #%d успешно помещен в буфер!\n", i)
		}
		close(ch)
	}()

	// Медленный читатель
	time.Sleep(20 * time.Millisecond)
	fmt.Println("\n[Consumer] Начинаю медленное вычитывание:")

	for val := range ch {
		fmt.Printf("   <- [Consumer] Прочитан элемент: %d\n", val)
		time.Sleep(30 * time.Millisecond)
	}
}
```

## Под капотом

Когда `qcount == dataqsiz`, отправитель паркуется в списке `sendq` структуры `hchan` до первого чтения.

## Подводные камни

Чрезмерно большой буфер маскирует проблемы производительности потребителя, приводя к скрытым скачкам потребления памяти (Bufferbloat).

## На собеседовании

**Вопрос с собеседования:** «Как подобрать оптимальный размер буфера канала?»
**Ответ:** По умолчанию выбирают небуферизованный канал (0) для строгой синхронизации. Буфер задают, когда известен точный размер пачки (например, число воркеров) или для сглаживания коротких пиков I/O.
