# Синхронная блокировка в unbuffered канале и механизм Rendezvous

## Условие

**Небуферизированный канал**: Создай канал `ch := make(chan int)`. В `main` отправь в него число: `ch <- 42`. Запусти и поймай `fatal error: all goroutines are asleep - deadlock!`. (Запись в такой канал блокирует выполнение, пока кто-то не прочитает из него).

## Теория

Запись в небуферизованный канал не может завершиться изолированно: она требует одновременного присутствия горутины-получателя на другом конце канала.

## Решение по шагам

1. Создадим `ch := make(chan int)`.
2. Запустим горутину для приема данных.
3. Отправим число 42.
4. Продемонстрируем устранение дедлока.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func main() {
	ch := make(chan int)

	// Запуск читателя в отдельной горутине предотвращает дедлок
	go func() {
		received := <-ch
		fmt.Printf("[Горутина-Читатель] Успешно прочитано: %d\n", received)
	}()

	fmt.Println("[Main] Отправка числа 42...")
	ch <- 42
	fmt.Println("[Main] Отправка завершена!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Main] Отправка числа 42...
# [Горутина-Читатель] Успешно прочитано: 42
# [Main] Отправка завершена!
```

## Под капотом

`ch <- 42` и `<-ch` синхронизируются через внутренний мьютекс `hchan.lock`.

## Подводные камни

Никогда не выполняйте запись в небуферизованный канал до запуска горутины-читателя.

## На собеседовании

**Вопрос с собеседования:** «Может ли горутина-отправитель быть разбужена до того, как читатель скопирует данные?»
**Ответ:** Нет! При небуферизованной передаче отправитель пробуждается планировщиком только **после** того, как данные гарантированно скопированы на стек читателя.
