# Переполнение емкости буфера канала: дедлок при превышении capacity

## Условие

**Переполнение буфера**: Добавь в упр. 266 отправку третьего числа (при буфере 2). Поймай дедлок.

## Теория

Буферизованный канал емкостью \(N\) превращается в блокирующий при попытке записать \((N+1)\)-й элемент, если ни один из предыдущих элементов еще не был вычитан.

## Решение по шагам

1. Создадим канал `ch := make(chan int, 2)`.
2. Заполним буфер первыми двумя элементами.
3. Продемонстрируем, как вызов `ch <- 30` в горутине блокируется до вычитывания.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan int, 2)

	// Заполняем буфер полностью
	ch <- 10
	ch <- 20
	fmt.Printf("[Main] Буфер заполнен: len=%d, cap=%d\n", len(ch), cap(ch))

	// Запускаем фоновую отправку 3-го элемента
	go func() {
		fmt.Println("[Worker] Попытка записи 3-го элемента ch <- 30 (буфер полон, ожидание освобождения)...")
		ch <- 30
		fmt.Println("[Worker] УРА! 3-й элемент успешно записан в освобожденный слот!")
	}()

	time.Sleep(20 * time.Millisecond)

	// Читаем 1 элемент, освобождая место в буфере
	fmt.Printf("[Main] Вычитан первый элемент: %d\n", <-ch)

	time.Sleep(10 * time.Millisecond)
	fmt.Printf("[Main] Вычитан второй элемент: %d\n", <-ch)
	fmt.Printf("[Main] Вычитан третий элемент: %d\n", <-ch)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Main] Буфер заполнен: len=2, cap=2
# [Worker] Попытка записи 3-го элемента ch <- 30 (буфер полон, ожидание освобождения)...
# [Main] Вычитан первый элемент: 10
# [Worker] УРА! 3-й элемент успешно записан в освобожденный слот!
# [Main] Вычитан второй элемент: 20
# [Main] Вычитан третий элемент: 30
```

## Под капотом

Отправитель 3-го элемента засыпает в очереди `sendq`. Как только читатель выполняет `<-ch`, рантайм переносит ожидающее значение в буфер и пробуждает отправителя.

## Подводные камни

Запись \((N+1)\)-го элемента в главном потоке без фонового читателя приведет к панике `deadlock!`.

## На собеседовании

**Вопрос с собеседования:** «Что происходит с порядком сообщений в буферизованном канале при конкурентной записи?»
**Ответ:** Буферизованный канал строго гарантирует порядок FIFO (First-In, First-Out): элементы извлекаются точно в том порядке, в котором они были зафиксированы в кольцевом буфере под мьютексом `hchan.lock`.
