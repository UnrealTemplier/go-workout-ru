# Блокировка на 4-м элементе в буфере емкостью 3

## Условие

Попробуй отправить 4-е число в канал из предыдущего задания (без читателя). Дождись дедлока.

## Теория

Заполнение буфера до предела (`len == cap`) переводит канал в заблокированное состояние для последующих записей.

## Решение по шагам

1. Создадим `ch := make(chan int, 3)`.
2. Запишем 3 числа.
3. Запустим фоновую горутину, ожидающую чтения перед записью 4-го числа.
4. Продемонстрируем безопасное разрешение блокировки.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan int, 3)

	// Заполняем буфер ровно на 3 элемента
	ch <- 1
	ch <- 2
	ch <- 3
	fmt.Println("[Main] Буфер заполнен (3/3)")

	// 4-я запись в фоне
	go func() {
		fmt.Println("[Worker] Ожидание слота для отправки 4-го числа...")
		ch <- 4
		fmt.Println("[Worker] 4-е число успешно записано в буфер!")
	}()

	time.Sleep(15 * time.Millisecond)

	// Вычитываем одно значение
	fmt.Printf("[Main] Прочитано: %d (освобожден 1 слот)\n", <-ch)

	time.Sleep(10 * time.Millisecond)
	fmt.Printf("[Main] Прочитано: %d\n", <-ch)
	fmt.Printf("[Main] Прочитано: %d\n", <-ch)
	fmt.Printf("[Main] Прочитано: %d\n", <-ch)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Main] Буфер заполнен (3/3)
# [Worker] Ожидание слота для отправки 4-го числа...
# [Main] Прочитано: 1 (освобожден 1 слот)
# [Worker] 4-е число успешно записано в буфер!
# [Main] Прочитано: 2
# [Main] Прочитано: 3
# [Main] Прочитано: 4
```

## Под капотом

Освобождение слота переносит горутину из `sendq` в очередь выполнения.

## Подводные камни

Не полагайтесь на неограниченное увеличение буфера для исправления дедлоков.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если горутина отправляет данные в буферизованный канал, когда в recvq уже спит читатель?»
**Ответ:** Рантайм Go оптимизирует этот случай: данные передаются напрямую спящему читателю со стека на стек, минуя кольцевой буфер `hchan.buf`.
