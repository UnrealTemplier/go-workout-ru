# Глубокий анализ nil-канала: вечный сон в gopark()

## Условие

**[Каверзный кейс]**: Попробуй прочитать данные из `nil`-канала (`var ch chan int; <-ch`). Поймай дедлок. Затем попробуй записать в `nil`-канал. Изучи это поведение.

## Теория

В исходном коде Go (`src/runtime/chan.go`) функции `chansend` и `chanrecv` при получении `c == nil` сразу вызывают `gopark(nil, nil, waitReasonChanSendNilChan, traceBlockChanSend, 2)`. Горутина переводится в спящее состояние без дескриптора ожидания.

## Решение по шагам

1. Создадим переменную `var nilChan chan string`.
2. Запустим горутину с попыткой чтения из `nilChan`.
3. В `main` убедимся с помощью таймаута, что горутина так и не проснулась.
4. Зафиксируем поведение.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	var nilChan chan string

	done := make(chan struct{})

	go func() {
		fmt.Println("[Worker] Попытка чтения из nil-канала: <-nilChan (усыпление навечно)...")
		_ = <-nilChan
		// Эта строка никогда не выполнится
		close(done)
	}()

	select {
	case <-done:
		fmt.Println("Ошибка: чтение разблокировалось")
	case <-time.After(30 * time.Millisecond):
		fmt.Println("[Main] Подтверждено: горутина заблокирована на nil-канале навечно!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Worker] Попытка чтения из nil-канала: <-nilChan (усыпление навечно)...
# [Main] Подтверждено: горутина заблокирована на nil-канале навечно!
```

## Под капотом

Горутина, спящая на nil-канале, не регистрируется ни в одном списке `hchan.recvq`, поэтому её невозможно разбудить закрытием или записью.

## Подводные камни

Забытая инициализация канала через `make()` приводит к тихим зависаниям функций.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go не сделали панику при записи в nil-канал, как при разыменовании nil-указателя?»
**Ответ:** Для поддержки динамического отключения веток в конструкции `select`: присваивание `ch = nil` позволяет «выключить» ветку `case <-ch:` в рантайме без реструктуризации кода.
