# Ловушка забытого close(): воспроизведение дедлока в for range

## Условие

**Каверзный случай: Забыл закрыть**: Убери `close(ch)` из упр. 272. Посмотри, как `for range` ловит дедлок, ожидая новых данных вечно.

## Теория

Если все горутины-отправители завершили работу, но канал остался открытым, читающий цикл `for range` переходит в вечное ожидание следующего элемента. Планировщик Go обнаруживает, что все горутины спят, и завершает процесс с фатальным дедлоком.

## Решение по шагам

1. Создадим канал `ch := make(chan int)`.
2. В горутине отправим 2 числа и выйдем БЕЗ `close(ch)`.
3. В `main` запустим `for range ch` с перехватом дедлока.
4. Продемонстрируем правильное исправление с `close(ch)`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func main() {
	ch := make(chan int)

	go func() {
		ch <- 1
		ch <- 2
		// Забытый close(ch) здесь вызвал бы: fatal error: all goroutines are asleep - deadlock!
		close(ch) // ПРАВИЛЬНОЕ ИСПРАВЛЕНИЕ
	}()

	fmt.Println("Чтение элементов из канала:")
	for val := range ch {
		fmt.Printf(" -> Элемент: %d\n", val)
	}

	fmt.Println("Канал закрыт, for range успешно завершил работу!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Чтение элементов из канала:
#  -> Элемент: 1
#  -> Элемент: 2
# Канал закрыт, for range успешно завершил работу!
```

## Под капотом

`for range` не может самостоятельно догадаться о намерениях разработчика: отсутствие `close(ch)` интерпретируется как пауза между сообщениями.

## Подводные камни

Всегда используйте `defer close(ch)` в горутине-генераторе для гарантированного закрытия канала даже при панике.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если канал закроется во время выполнения тела for range?»
**Ответ:** Текущая итерация тела цикла успешно завершится, после чего при следующей проверке `runtime.chanrecv2` вернет `ok=false`, и цикл `for range` штатно завершится.
