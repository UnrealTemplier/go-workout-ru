# Емкость буфера: неблокирующая отправка 3 элементов и поведение 4-го

## Условие

Создайте буферизованный канал (`make(chan int, 3)`). Отправьте туда 3 значения без блокировки. Что будет при попытке отправить 4-е значение?

## Теория

Канал с буфером емкостью 3 элемента гарантирует неблокирующее выполнение ровно для первых 3 операций записи `ch <- v`. Четвертая операция записи переводит горутину в заблокированное состояние ожидания освобождения хотя бы одного слота.

## Решение по шагам

1. Создадим канал `ch := make(chan int, 3)`.
2. Запишем 3 элемента в главном потоке.
3. Запустим горутину с неблокирующей попыткой записи 4-го элемента через `select default`.
4. Сверим логику.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func main() {
	ch := make(chan int, 3)

	// Первые 3 отправки не блокируются
	ch <- 100
	ch <- 200
	ch <- 300
	fmt.Printf("Канал заполнен: len=%d / cap=%d\n", len(ch), cap(ch))

	// Проверяем 4-ю отправку через неблокирующий select
	select {
	case ch <- 400:
		fmt.Println("4-й элемент успешно отправлен")
	default:
		fmt.Println("ВНИМАНИЕ: Буфер переполнен! Прямая запись ch <- 400 заблокировала бы горутину!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Канал заполнен: len=3 / cap=3
# ВНИМАНИЕ: Буфер переполнен! Прямая запись ch <- 400 заблокировала бы горутину!
```

## Под капотом

`select` с веткой `default` при `qcount == dataqsiz` сразу переходит в `default` без вызова `gopark`.

## Подводные камни

В критических системах переполнение буфера часто обрабатывают сбросом метрики `buffer_overflow_dropped_total`.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если емкость буфера задать отрицательным числом make(chan int, -1)?»
**Ответ:** Компилятор или рантайм Go немедленно выбросит панику: `panic: makechan: size out of range`.
