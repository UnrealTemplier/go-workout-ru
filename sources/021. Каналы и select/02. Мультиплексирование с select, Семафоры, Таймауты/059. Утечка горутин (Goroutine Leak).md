# Утечка горутин (Goroutine Leak) на небуферизованном канале и способы устранения

## Условие

Утечка горутин: горутина блокируется на отправке в канал, который никто не читает. Исправьте с помощью `select` с таймаутом или буфера.

## Теория

Goroutine Leak на каналах: если вызывающий код выходит до того, как фоновый воркер успел отправить результат в небуферизованный канал, воркер зависает на строке `ch <- result` в памяти навсегда вместе со своим стеком.

## Решение по шагам

1. Создадим функцию с утечкой на небуферизованном канале.
2. Продемонстрируем исправление через буферизованный канал `make(chan string, 1)` (Capacity = 1).
3. Убедимся, что воркер завершает работу без читателя.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// ПРАВИЛЬНОЕ ИСПРАВЛЕНИЕ: буфер на 1 элемент позволяет воркеру положить ответ и выйти,
// даже если вызывающий код завершился по таймауту!
func fetchFastestResult() string {
	resChan := make(chan string, 1) // БУФЕР = 1 ИСКЛЮЧАЕТ УТЕЧКУ ГОРУТИНЫ!

	go func() {
		time.Sleep(50 * time.Millisecond)
		resChan <- "Данные от сервера" // Не заблокируется даже при отсутствии читателя
		fmt.Println("[Background Worker] Воркер успешно положил данные в буфер и завершил работу!")
	}()

	select {
	case res := <-resChan:
		return res
	case <-time.After(10 * time.Millisecond):
		return "Default Timeout Fallback"
	}
}

func main() {
	fmt.Printf("Активно горутин до вызова: %d\n", runtime.NumGoroutine())

	res := fetchFastestResult()
	fmt.Printf("Результат функции: %s\n", res)

	time.Sleep(80 * time.Millisecond)
	fmt.Printf("Активно горутин после завершения: %d (утечка отсутствует!)\n", runtime.NumGoroutine())
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Активно горутин до вызова: 1
# Результат функции: Default Timeout Fallback
# [Background Worker] Воркер успешно положил данные в буфер и завершил работу!
# Активно горутин после завершения: 1 (утечка отсутствует!)
```

## Под капотом

Буфер емкостью 1 поглощает результат, позволяя фоновой горутине завершиться и освободить стек (2 КБ) для GC.

## Подводные камни

В паттернах конкурентного запроса к репликам (First-Response / Hedged Requests) емкость буфера всегда должна быть равна количеству запускаемых реплик (\(N\)).

## На собеседовании

**Вопрос с собеседования:** «Почему буфер make(chan T, 1) является лучшей защитой от Goroutine Leak при таймаутах?»
**Ответ:** Потому что горутина-поставщик может гарантированно записать результат в буфер без ожидания вызывающего потока и штатно завершить выполнение, не оставаясь в состоянии `_Gwaiting` в памяти.
