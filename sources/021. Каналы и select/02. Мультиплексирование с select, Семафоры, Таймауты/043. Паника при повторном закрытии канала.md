# Паника при повторном закрытии канала (panic: close of closed channel)

## Условие

**Двойное закрытие**: Попробуй закрыть уже закрытый канал. Снова паника.

## Теория

Рантайм Go отслеживает битовое поле `closed` в `runtime.hchan`. Если при вызове `close(c)` поле `closed != 0`, рантайм мгновенно генерирует неперехватываемое исключение (если нет `recover`).

## Решение по шагам

1. Создадим канал `ch := make(chan int)`.
2. Вызовем первый `close(ch)` — успешно.
3. Вызовем второй `close(ch)` внутри защищенной `defer recover()` функции.
4. Зафиксируем сообщение паники.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func main() {
	ch := make(chan int)

	// 1. Первое закрытие
	close(ch)
	fmt.Println("1. Первое закрытие close(ch) прошло успешно.")

	// 2. Второе закрытие с перехватом паники
	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("2. Перехвачена паника при повторном close: %v\n", r)
			}
		}()

		close(ch) // Вызывает panic: close of closed channel
	}()

	fmt.Println("Программа безопасно продолжила выполнение.")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 1. Первое закрытие close(ch) прошло успешно.
# 2. Перехвачена паника при повторном close: close of closed channel
# Программа безопасно продолжила выполнение.
```

## Под капотом

В функции `closechan` рантайма: `if c.closed != 0 { unlock(&c.lock); panic(plainError("close of closed channel")) }`.

## Подводные камни

Никогда не передавайте ответственность за закрытие канала нескольким горутинам без `sync.Once`.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go не сделали close(ch) идемпотентным (без паники)?»
**Ответ:** Потому что повторное закрытие канала свидетельствует о серьезной архитектурной ошибке в проектировании многопоточного протокола (гонке за владение ресурсом). Явная паника позволяет сразу выявить баг.
