# Моментальный Deadlock при синхронной отправке в канал без читателя

## Условие

Попробуйте отправить значение в канал в `main` без запуска горутины для чтения. Убедитесь, что это вызывает моментальный Deadlock.

## Теория

Запись в небуферизованный канал блокирует горутину в ожидании читателя. Если в рантайме нет ни одной другой активной горутины, программа падает с фатальной ошибкой рантайма.

## Решение по шагам

1. Создадим небуферизованный канал `ch := make(chan string)`.
2. Запустим читателя в отдельной горутине.
3. Отправим сообщение без дедлока.
4. Разберем механику рантайма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func main() {
	ch := make(chan string)

	// Без этой горутины строка ch <- "data" вызвала бы fatal error: all goroutines are asleep - deadlock!
	go func() {
		msg := <-ch
		fmt.Printf("[Reader] Получено: %s\n", msg)
	}()

	fmt.Println("[Main] Отправка данных в небуферизованный канал...")
	ch <- "Safe Message Transfer"
	fmt.Println("[Main] Передача успешно завершена!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Main] Отправка данных в небуферизованный канал...
# [Reader] Получено: Safe Message Transfer
# [Main] Передача успешно завершена!
```

## Под капотом

Рантайм отслеживает счетчик спящих горутин `sched.ngsys` и завершает процесс с кодом ошибки 2 при отсутствии живых горутин.

## Подводные камни

Не блокируйте `main()` до старта фоновых горутин.

## На собеседовании

**Вопрос с собеседования:** «Почему дедлок на каналах не вызывает 100% загрузки процессора?»
**Ответ:** Потому что заблокированная горутина снимается с потока ОС и переводится в состояние сна `_Gwaiting` (`gopark`), не потребляя ни одного такта CPU.
