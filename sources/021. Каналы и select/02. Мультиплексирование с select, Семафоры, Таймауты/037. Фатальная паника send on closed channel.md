# Фатальная паника send on closed channel при попытке записи в закрытый канал

## Условие

Закройте канал с помощью `close(ch)`. Попытайтесь отправить данные в закрытый канал (поймайте `panic: send on closed channel`).

## Теория

Запись в закрытый канал категорически запрещена спецификацией Go и приводит к фатальной панике `panic: send on closed channel`. Для предотвращения таких аварий в конкурентных средах используют паттерны владения каналом.

## Решение по шагам

1. Создадим канал `ch := make(chan int)`.
2. Закроем канал `close(ch)`.
3. Перехватим панику через `recover()` в защитной функции.
4. Проверим сообщение об ошибке.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

func safeSend(ch chan int, val int) (panicked bool) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("[SafeSend] Перехвачена паника: %v\n", r)
			panicked = true
		}
	}()

	ch <- val // Вызывает панику, если канал закрыт
	return false
}

func main() {
	ch := make(chan int, 2)
	close(ch) // Канал закрыт

	fmt.Println("Попытка отправки числа 99 в закрытый канал...")
	wasPanic := safeSend(ch, 99)

	fmt.Printf("Результат отправки: произошла паника = %v\n", wasPanic)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Попытка отправки числа 99 в закрытый канал...
# [SafeSend] Перехвачена паника: send on closed channel
# Результат отправки: произошла паника = true
```

## Под капотом

Внутри `runtime.chansend` при обнаружении `c.closed != 0` вызывается системная паника `panic("send on closed channel")`.

## Подводные камни

Не используйте `recover` как регулярный способ проверки открытости канала — канал должен закрываться строго по завершении всех отправок.

## На собеседовании

**Вопрос с собеседования:** «Как безопасно закрыть канал при \(N\) параллельных писателях?»
**Ответ:** 1) Использовать `sync.WaitGroup` для ожидания завершения всех \(N\) писателей, после чего отдельная горутина закрывает канал. 2) Либо использовать `sync.Once` для закрытия.
