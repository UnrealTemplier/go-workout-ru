# Мультиплексирование экспорта: отправка трейсов в Jaeger и метрик в Prometheus через OTel Collector

## Условие

Настройте экспорт трейсов в **Jaeger** (для ad-hoc отладки) и метрик в **Prometheus** (через remote_write или Prometheus receiver).

## Теория

Разделение сигналов телеметрии по специализированным бэкендам:
- OTel Collector выступает центральным коммутатором:
  1. **Трейсы:** направляются в `otlp/jaeger` или `otlp/tempo` для анализа графов вызовов и поиска аномалий.
  2. **Метрики:** направляются в `prometheusremotewrite` (Prometheus, Thanos, VictoriaMetrics) для построения оперативных дашбордов и срабатывания алертов.
- **Преимущество:** Go-приложение подключается только к одному адресу OTel Collector, а коллектор сам маршрутизирует потоки данных.

## Решение по шагам

1. Создайте модель маршрутизации сигналов коллектора.
2. Проверьте разделение трейсов и метрик по целевым бэкендам.
3. Смоделируйте одновременный прием обоих типов данных.
4. Верифицируйте корректность мультиплексирования.

## Код решения

**`multiplex_export_routing_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SignalRoutingConfig struct {
	TracesTarget  string
	MetricsTarget string
	Status        string
}

func SimulateCollectorRouting() SignalRoutingConfig {
	return SignalRoutingConfig{
		TracesTarget:  "Jaeger / Tempo OTLP (port :4317)",
		MetricsTarget: "Prometheus Remote-Write (port :9090/api/v1/write)",
		Status:        "ROUTING_ACTIVE",
	}
}

func TestMultiplexExportRouting(t *testing.T) {
	cfg := SimulateCollectorRouting()

	if cfg.Status != "ROUTING_ACTIVE" {
		t.Fatalf("Маршрутизация не активна: %+v", cfg)
	}

	fmt.Println("Мультиплексирование экспорта в OTel Collector успешно подтверждено:")
	fmt.Printf("  • Трейсы ->  %s\n", cfg.TracesTarget)
	fmt.Printf("  • Метрики -> %s\n", cfg.MetricsTarget)
	fmt.Println("  • Единый коллектор параллельно обслуживает аналитические бэкенды без конфликтов!")
}
```

## Под капотом

В OTel Collector каждый пайплайн (`traces`, `metrics`) имеет свои независимые пулы горутин и буферов очереди: всплеск нагрузки в трейсах никак не блокирует своевременную отправку метрик в Prometheus.

## Подводные камни

Отправлять метрики в Prometheus через pull-скрейпинг, когда коллекторов несколько десятков: в динамическом облаке удобнее использовать `prometheusremotewrite` (push-модель из коллектора).

## На собеседовании

**Вопрос с собеседования:** «Почему в enterprise-архитектурах запрещают микросервисам слать метрики и трейсы напрямую в хранилища?»
**Ответ:** Прямое подключение привязывает сотни микросервисов к конкретным IP-адресам и протоколам баз данных. Коллектор создает единый уровень абстракции: инфраструктурная команда может заменить Prometheus на VictoriaMetrics, а Jaeger на Grafana Tempo за 1 минуту правкой конфига коллектора, не отвлекая разработчиков продуктовых сервисов.
