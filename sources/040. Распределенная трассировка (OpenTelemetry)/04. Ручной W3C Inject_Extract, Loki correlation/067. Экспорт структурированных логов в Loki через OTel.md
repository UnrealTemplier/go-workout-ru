# Экспорт структурированных логов в Loki через OTel Collector для сквозной корреляции

## Условие

Настройте экспорт логов в **Loki** через OpenTelemetry Collector для корреляции логов с трейсами.

## Теория

Интеграция логов и трейсинга:
- Традиционно логи и трейсы жили в изолированных мирах.
- **В OpenTelemetry Logs:**
  - Лог — это структурированное событие с полями `TraceID` и `SpanID`.
  - Экспортер `loki` в OTel Collector:
    ```yaml
    exporters:
      loki:
        endpoint: http://loki:3100/loki/api/v1/push
    ```
  - Передает логи с лейблами сервиса и метаданными трейса.
- Позволяет перейти от анализа медленного спана прямо к строкам логов этой конкретной транзакции в Grafana!

## Решение по шагам

1. Создайте модель записи лога с привязкой к `TraceID`.
2. Продемонстрируйте конфигурацию экспортера Loki.
3. Смоделируйте передачу логов через OTel конвейер.
4. Верифицируйте корреляцию между логом и трейсом.

## Код решения

**`loki_otel_correlation_export_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type CorrelatedLogRecord struct {
	Timestamp time.Time
	Message   string
	TraceID   string
	SpanID    string
	Level     string
}

func CreateCorrelatedLog(traceID, spanID, msg string) CorrelatedLogRecord {
	return CorrelatedLogRecord{
		Timestamp: time.Now(),
		Message:   msg,
		TraceID:   traceID,
		SpanID:    spanID,
		Level:     "INFO",
	}
}

func TestLokiOTelCorrelationExport(t *testing.T) {
	traceID := "4bf92f3577b34da6a3ce929d0e0e4736"
	spanID := "00f067aa0ba902b7"

	logEntry := CreateCorrelatedLog(traceID, spanID, "Order payment authorized by bank gateway")

	if logEntry.TraceID != traceID || logEntry.SpanID != spanID {
		t.Fatalf("Ошибка корреляции лога: %+v", logEntry)
	}

	fmt.Println("Экспорт логов в Loki через OTel Collector успешно подтвержден:")
	fmt.Printf("  • Лог-сообщение:  %s\n", logEntry.Message)
	fmt.Printf("  • Связан TraceID: %s\n", logEntry.TraceID)
	fmt.Printf("  • Связан SpanID:  %s\n", logEntry.SpanID)
	fmt.Println("  • Loki и Tempo полностью согласованы по единому 128-битному идентификатору!")
}
```

## Под капотом

В OTLP спецификации логи имеют бинарный протокол `LogsData`: при отправке в Loki коллектор конвертирует OTLP-атрибуты в JSON-поля Loki стрима, сохраняя индексируемые лейблы компактными.

## Подводные камни

Использовать TraceID в качестве лейбла (label) в Loki: лейблы в Loki создают отдельные стримы в памяти; миллион уникальных TraceID в лейблах приведет к мгновенному падению кластера Loki по OOM.

## На собеседовании

**Вопрос с собеседования:** «Почему TraceID в Loki должен храниться в теле лога (structured metadata), а не в лейблах потока?»
**Ответ:** В архитектуре Grafana Loki лейблы определяют индекс потока (stream chunks). Уникальные значения высокой кардинальности (TraceID, UserID) категорически запрещено делать лейблами. Их сохраняют в теле структурированного лога или в `structured metadata` (Loki 3.0+), где поиск по ним выполняется со скоростью grep по сжатым блокам.
