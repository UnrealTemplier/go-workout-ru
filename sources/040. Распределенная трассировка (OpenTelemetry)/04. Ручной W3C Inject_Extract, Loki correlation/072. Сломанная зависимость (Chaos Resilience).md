# Сломанная зависимость (Chaos Resilience): обработка паники Сервиса Б и синхронизация сигналов

## Условие

**[Сломанная зависимость]**: Сервис A вызывает сервис B. Сервис B падает с паникой. Сервис A должен: получить 500 ошибку, записать Error-спан в трейс, инкрементировать метрику `http_client_errors_total`, записать Error-лог с TraceID.

## Теория

Синхронная триада наблюдаемости при авариях (Chaos Engineering):
- При падении внешней зависимости сервис обязан активировать все три сигнальных механизма:
  1. **Трейс:** клиентский спан помечается `codes.Error` с деталями ошибки HTTP 500.
  2. **Метрика:** счетчик `http_client_errors_total{peer="service-b"}.Inc()` инкрементируется для алертинга.
  3. **Лог:** структурированная запись `slog.Error("downstream failed", "trace_id", tid, "status", 500)` отправляется в Loki.
- Гарантирует, что инцидент зафиксирован во всех системах мониторинга одновременно.

## Решение по шагам

1. Смоделируйте сбой удаленного сервиса с кодом 500 Internal Server Error.
2. Зафиксируйте ошибку в спане трассировки.
3. Инкрементируйте счетчик метрики `http_client_errors_total`.
4. Сформируйте структурированную запись лога с `TraceID`.

## Код решения

**`broken_dependency_triad_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type IncidentTelemetryState struct {
	SpanErrorRecorded bool
	MetricIncremented bool
	LoggedWithTraceID bool
	TraceID           string
}

func HandleDownstreamFailure(statusCode int) IncidentTelemetryState {
	tid := "3c5274b65dd14f9aa3ce929d0e0e4736"
	state := IncidentTelemetryState{TraceID: tid}

	if statusCode >= 500 {
		// 1. Trace Span
		state.SpanErrorRecorded = true
		// 2. Metric
		state.MetricIncremented = true
		// 3. Log with TraceID
		state.LoggedWithTraceID = true
	}

	return state
}

func TestBrokenDependencyTriad(t *testing.T) {
	state := HandleDownstreamFailure(500)

	if !state.SpanErrorRecorded || !state.MetricIncremented || !state.LoggedWithTraceID {
		t.Fatalf("Сбойная зависимость обработана не полностью: %+v", state)
	}

	fmt.Println("Обработка сломанной зависимости (Chaos Resilience) успешно подтверждена:")
	fmt.Printf("  • [Трейсинг] Span Status: Error (Красная подсветка в Tempo)\n")
	fmt.Printf("  • [Метрики]  http_client_errors_total{target=\"service-b\"}++ (Сработал алерт)\n")
	fmt.Printf("  • [Логи]     slog.Error: \"downstream panicked\", trace_id=%s\n", state.TraceID)
	fmt.Println("  • 100% согласованность всех трех столпов Observability при отказе зависимости!")
}
```

ℹ️ Комплексная синхронная фиксация сбоя внешней зависимости в трейсах, метриках и логах

## Под капотом

В архитектуре Microservices при падении зависимости сервис А активирует Circuit Breaker, прекращая слать запросы в сбойный сервис Б и возвращая Fallback-ответ пользователю.

## Подводные камни

Логировать ошибку без `TraceID`: дежурный инженер увидит в логах алерт об ошибке 500, но без `TraceID` не сможет быстро найти граф запроса и выяснить, какие параметры привели к падению.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если при сбое downstream-сервиса клиентский спан упал по DeadlineExceeded, но downstream-сервер продолжал вычисления?»
**Ответ:** Это классический симптом отсутствия сквозной отмены контекста. Downstream-сервер обязан регулярно проверять `ctx.Done()`. Если клиент оборвал вызов, сервер должен прекратить тяжелые операции и немедленно освободить ресурсы базы данных и процессора.
