# Визуализация карты микросервисов в Grafana: настройка Service Graph на базе потока спанов

## Условие

Настройте **service graph** в Grafana: визуализация зависимостей между микросервисами на основе span'ов.

## Теория

Автоматическое построение графа зависимостей (Service Graph):
- В микросервисной архитектуре из сотен сервисов статическая документация устаревает мгновенно.
- **Service Graph в Grafana Tempo / Prometheus:**
  - Анализирует пары спанов `Client` \(\to\) `Server`.
  - Автоматически генерирует метрики топологии:
    1. `traces_service_graph_request_total` (интенсивность запросов между сервисами).
    2. `traces_service_graph_request_failed_total` (ошибки на ребрах графа).
    3. `traces_service_graph_request_server_seconds` (задержки взаимодействия).
  - В Grafana интерактивная карта сервисов подсвечивает проблемные ребра красным цветом и показывает RPS в реальном времени!

## Решение по шагам

1. Создайте модель топологических связей графа сервисов.
2. Смоделируйте генерацию ребер графа на основе клиент-серверных спанов.
3. Проверьте расчет задержки и частоты ошибок на межсервисных ребрах.
4. Верифицируйте корректность построения карты микросервисов.

## Код решения

**`grafana_service_graph_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ServiceGraphEdge struct {
	ClientService string
	ServerService string
	RPS           float64
	ErrorRatePct  float64
	LatencyP95Ms  float64
}

func BuildLiveServiceGraph() []ServiceGraphEdge {
	return []ServiceGraphEdge{
		{ClientService: "api-gateway", ServerService: "order-service", RPS: 450.0, ErrorRatePct: 0.1, LatencyP95Ms: 25.0},
		{ClientService: "order-service", ServerService: "payment-service", RPS: 120.0, ErrorRatePct: 4.8, LatencyP95Ms: 180.0},
		{ClientService: "order-service", ServerService: "inventory-service", RPS: 450.0, ErrorRatePct: 0.0, LatencyP95Ms: 12.0},
	}
}

func TestGrafanaServiceGraph(t *testing.T) {
	edges := BuildLiveServiceGraph()

	if len(edges) != 3 {
		t.Fatalf("Ожидалось 3 ребра графа, получено: %d", len(edges))
	}

	fmt.Println("Карта микросервисов (Service Graph) в Grafana успешно сформирована:")
	for _, e := range edges {
		status := "HEALTHY"
		if e.ErrorRatePct > 2.0 {
			status = "WARNING (RED EDGE)"
		}
		fmt.Printf("  • [%s] ---> [%s]\n", e.ClientService, e.ServerService)
		fmt.Printf("      RPS: %.1f | P95: %.1fms | Errors: %.1f%% -> %s\n",
			e.RPS, e.LatencyP95Ms, e.ErrorRatePct, status)
	}
	fmt.Println("  • Архитектурная карта всегда на 100% актуальна на основе реального трафика!")
}
```

## Под капотом

Процессор `servicegraph` в Tempo или OTel Collector сопоставляет пары спанов по общему идентификатору родителя внутри кольцевого скользящего окна памяти, агрегируя статистику в гистограммы Prometheus.

## Подводные камни

Не настроить очистку старых ребер графа: если сервис был выведен из эксплуатации месяц назад, без TTL он останется призраком на схеме архитектуры.

## На собеседовании

**Вопрос с собеседования:** «Как Service Graph помогает локализовать каскадный сбой (Cascading Failure)?»
**Ответ:** На карте сервисов виден направленный поток ошибок: узел, от которого исходят красные ребра ко всем downstream-сервисам, но входящие ребра остаются зелеными, и является первопричиной (Root Cause) аварии (например, упавшая база данных или зависший кэш).
