# Распределенный анализ трейсов (Distributed Trace Analysis): локализация блокировок в POST /orders

## Условие

Реализуй **Distributed Trace Analysis**:
- Trace: `POST /orders` → `OrderService.CreateOrder` → `ValidateInventory` (50ms) → `ReserveInventory` (200ms, DB lock contention!) → `ProcessPayment` (300ms, external API) → `SendNotification` (100ms, async)
- Identify bottleneck: `ReserveInventory` — optimize DB query, add index
- Identify optimization: `SendNotification` — make async, don't block response
- Measure improvement: before/after trace comparison

## Теория

Методология инженерного аудита распределенных трейсов:
- Анализ диаграммы водопада (Gantt Chart Analysis):
  1. **Критический путь (Critical Path):** непрерывная последовательность самых длинных блокирующих операций.
  2. **Поиск блокировок СУБД (Lock Contention):** спан длится аномально долго при простом запросе -> нехватка индексов или конфликт блокировок строк `SELECT FOR UPDATE`.
  3. **Вынос неблокирующих операций:** отправка email/push уведомлений не должна блокировать синхронный HTTP ответ покупателю!

## Решение по шагам

1. Создайте модель временных спанов до оптимизации (суммарно 650 мс).
2. Оптимизируйте спан `ReserveInventory` (устранение lock contention: с 200 мс до 15 мс).
3. Вынесите спан `SendNotification` (100 мс) в асинхронную фоновую горутину с сохранением трейса.
4. Продемонстрируйте сокращение времени отклика клиенту с 650 мс до 365 мс (ускорение в 1.8 раза).

## Код решения

**`distributed_trace_analysis_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TracePerformanceComparison struct {
	Stage              string
	ValidateMs         int
	ReserveInventoryMs int
	ProcessPaymentMs   int
	SendNotificationMs int
	TotalClientWaitMs  int
}

func CalculatePipeline(reserve, notifyBlock bool) TracePerformanceComparison {
	validate := 50
	reserveTime := 200
	if !reserve {
		reserveTime = 15 // Оптимизировали SQL запрос, добавили индекс
	}
	payment := 300
	notify := 100

	totalWait := validate + reserveTime + payment
	if notifyBlock {
		totalWait += notify // Блокирующая отправка
	}

	stage := "BEFORE Optimization"
	if !reserve && !notifyBlock {
		stage = "AFTER Optimization (DB Index + Async Notification)"
	}

	return TracePerformanceComparison{
		Stage:              stage,
		ValidateMs:         validate,
		ReserveInventoryMs: reserveTime,
		ProcessPaymentMs:   payment,
		SendNotificationMs: notify,
		TotalClientWaitMs:  totalWait,
	}
}

func TestDistributedTraceAnalysis(t *testing.T) {
	before := CalculatePipeline(true, true)
	after := CalculatePipeline(false, false)

	if before.TotalClientWaitMs != 650 || after.TotalClientWaitMs != 365 {
		t.Fatalf("Некорректный расчет задержек: before=%d, after=%d", before.TotalClientWaitMs, after.TotalClientWaitMs)
	}

	speedup := float64(before.TotalClientWaitMs) / float64(after.TotalClientWaitMs)

	fmt.Println("Анализ и оптимизация распределенного трейса POST /orders:")
	fmt.Printf("  • [ДО]   Задержка клиента: %dms (ReserveInventory: 200ms DB lock, Notification: 100ms sync)\n", before.TotalClientWaitMs)
	fmt.Printf("  • [ПОСЛЕ] Задержка клиента: %dms (ReserveInventory: 15ms index, Notification: async)\n", after.TotalClientWaitMs)
	fmt.Printf("  • Итоговое ускорение критического пути: %.2fx (Задержка снижена почти в 2 раза!)\n", speedup)
}
```

## Под капотом

При выносе `SendNotification` в фон спан уведомления оформляется через `trace.Link` или запускается в горутине с `context.WithoutCancel(ctx)`, позволяя клиенту получить ответ за 365 мс, пока фоновый воркер завершает отправку письма.

## Подводные камни

Оптимизировать операции вне критического пути: ускорение `ValidateInventory` с 50 до 40 мс даст мизерный эффект, пока в `ReserveInventory` висит блокировка на 200 мс.

## На собеседовании

**Вопрос с собеседования:** «Как с помощью трассировки выявить эффект "DB Lock Contention" (борьбу за блокировки строк)?»
**Ответ:** Если простой запрос `UPDATE products SET stock = stock - 1 WHERE id = 1` обычно выполняется за 0.5 мс, но под нагрузкой на графике трейса время спана вырастает до 500 мс при нулевой утилизации CPU СУБД — транзакция заблокирована другой горутиной, удерживающей эксклюзивную блокировку этой же строки.
