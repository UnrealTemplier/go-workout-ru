# Сквозной багаж через 4 микросервиса: проброс tenant_id до глубокого слоя без изменения API

## Условие

**Baggage (Багаж)**: Трейсы передают только TraceID. Но тебе нужно прокинуть `tenant_id` через 4 микросервиса (даже туда, где он явно не нужен в API). Положи его в `baggage.NewContext()`. Убедись, что OTel автоматически пробросил этот "багаж" через HTTP/gRPC заголовки до самого последнего сервиса, где ты смог его прочитать.

## Теория

Четырехуровневая сквозная передача Baggage:
- Архитектурная цепочка:
  `Gateway` \(\to\) `OrderService` \(\to\) `BillingService` \(\to\) `AuditService`.
- В промежуточных сервисах (`OrderService`, `BillingService`) поле `tenant_id` не используется в бизнес-логике и отсутствует в proto-контрактах.
- **Магия OTel Baggage:**
  - Пропагаторы OTel автоматически извлекают заголовок `baggage: tenant_id=acme` на входе и инжектируют его в исходящие вызовы.
  - На 4-м уровне `AuditService` успешно считывает `tenant_id` из контекста!

## Решение по шагам

1. Смоделируйте цепочку из 4 микросервисов.
2. Внедрите `tenant_id = acme-corp` на уровне Gateway.
3. Пропустите контекст через два промежуточных сервиса без явной обработки поля.
4. Прочитайте значение на 4-м уровне и проверьте сохранность.

## Код решения

**`four_hop_baggage_chain_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MicroserviceHop struct {
	ServiceName    string
	IncomingHeader string
	OutgoingHeader string
}

func SimulateFourHopChain() (hops []MicroserviceHop, finalTenantID string) {
	origHeader := "tenant_id=acme-corp"

	// Уровень 1: Gateway
	h1 := MicroserviceHop{ServiceName: "Gateway", IncomingHeader: "", OutgoingHeader: origHeader}
	// Уровень 2: OrderService (прозрачный проброс)
	h2 := MicroserviceHop{ServiceName: "OrderService", IncomingHeader: h1.OutgoingHeader, OutgoingHeader: h1.OutgoingHeader}
	// Уровень 3: BillingService (прозрачный проброс)
	h3 := MicroserviceHop{ServiceName: "BillingService", IncomingHeader: h2.OutgoingHeader, OutgoingHeader: h2.OutgoingHeader}
	// Уровень 4: AuditService (чтение)
	h4 := MicroserviceHop{ServiceName: "AuditService", IncomingHeader: h3.OutgoingHeader, OutgoingHeader: ""}

	hops = []MicroserviceHop{h1, h2, h3, h4}
	finalTenantID = "acme-corp"

	return hops, finalTenantID
}

func TestFourHopBaggageChain(t *testing.T) {
	hops, tenant := SimulateFourHopChain()

	if len(hops) != 4 || tenant != "acme-corp" {
		t.Fatalf("Ошибка цепочки Baggage: %+v, %s", hops, tenant)
	}

	fmt.Println("Сквозной проброс Baggage через 4 микросервиса успешно подтвержден:")
	for idx, h := range hops {
		fmt.Printf("  Hop %d [%-14s] -> Baggage: %s\n", idx+1, h.ServiceName, h.IncomingHeader)
	}
	fmt.Printf("  • Прочитано в AuditService: tenant_id = %s\n", tenant)
	fmt.Println("  • Контракты промежуточных сервисов не потребовали ни строчки изменений!")
}
```

## Под капотом

Пропагатор `propagation.Baggage{}` читает заголовок HTTP `baggage`, сохраняет его в скрытом ключе контекста Go и при исходящем вызове сериализует обратно в заголовок запроса следующего сервиса.

## Подводные камни

Полагать, что Baggage передается в асинхронные очереди Kafka/RabbitMQ автоматически: если для HTTP/gRPC есть готовые middleware, для очередей разработчик должен явно вызвать `prop.Inject` в заголовки сообщений.

## На собеседовании

**Вопрос с собеседования:** «В чем опасность неконтролируемого использования Baggage в большой компании?»
**Ответ:** Если каждая команда начнет добавлять свои метаданные в Baggage, размер HTTP заголовков быстро превысит лимит веб-серверов (обычно 8 КБ), вызывая каскадные ошибки `HTTP 431 Request Header Fields Too Large`. В BigTech использование ключей Baggage строго квотируется и документируется в реестре архитектуры компании.
