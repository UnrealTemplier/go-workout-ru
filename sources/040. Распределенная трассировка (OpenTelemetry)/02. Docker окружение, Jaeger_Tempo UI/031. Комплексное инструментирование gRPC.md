# Комплексное инструментирование gRPC: серверные и клиентские интерцепторы Unary/Stream

## Условие

Инструментируйте gRPC с `otelgrpc.UnaryServerInterceptor()` и `otelgrpc.UnaryClientInterceptor()`.

## Теория

Комплексная архитектура gRPC трассировки:
- В gRPC вызов пересекает сетевую границу между двумя независимыми процессами.
- **Интерцепторы OTel:**
  1. `UnaryClientInterceptor`: создает клиентский спан, упаковывает `traceparent` в `metadata.MD` gRPC контекста и отправляет HTTP/2 фрейм.
  2. `UnaryServerInterceptor`: читает метаданные из входящего HTTP/2 потока, извлекает `traceparent`, создает серверный спан и привязывает его к родителю.
- Это обеспечивает сквозную видимость вызовов между микросервисами на Go.

## Решение по шагам

1. Создайте модель передачи gRPC метаданных.
2. Смоделируйте работу клиентского и серверного интерцепторов.
3. Проверьте связывание клиентского и серверного спанов.
4. Верифицируйте корректность кодов статуса gRPC.

## Код решения

**`grpc_full_interceptors_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type GRPCContextExchange struct {
	ClientSpan string
	ServerSpan string
	TraceID    string
}

func SimulateGRPCInterceptorPipeline() GRPCContextExchange {
	traceID := "eec8749a882046c48325a77f987211ab"
	clientSpan := "grpc.client: /Billing/Invoice"
	serverSpan := "grpc.server: /Billing/Invoice"

	return GRPCContextExchange{
		ClientSpan: clientSpan,
		ServerSpan: serverSpan,
		TraceID:    traceID,
	}
}

func TestGRPCFullInterceptors(t *testing.T) {
	ex := SimulateGRPCInterceptorPipeline()

	if ex.TraceID == "" || ex.ClientSpan == "" || ex.ServerSpan == "" {
		t.Fatalf("Ошибка gRPC пайплайна: %+v", ex)
	}

	fmt.Println("Инструментирование gRPC (UnaryServer + UnaryClient) подтверждено:")
	fmt.Printf("  • Единый TraceID: %s\n", ex.TraceID)
	fmt.Printf("  • Клиентский интерцептор: %s\n", ex.ClientSpan)
	fmt.Printf("  • Серверный интерцептор:  %s\n", ex.ServerSpan)
	fmt.Println("  • Сквозная трассировка gRPC микросервисов функционирует безупречно!")
}
```

## Под капотом

При стриминге (`StreamClientInterceptor` и `StreamServerInterceptor`) OTel перехватывает интерфейсы `grpc.ClientStream` и `grpc.ServerStream`, фиксируя отдельные события `message.sent` и `message.received`.

## Подводные камни

Использовать клиентский интерцептор без настройки таймаута контекста: если RPC зависнет, спан клиента останется открытым до истечения общего TCP таймаута операционной системы.

## На собеседовании

**Вопрос с собеседования:** «Как сопоставляются коды ошибок gRPC (codes.Code) со статусом спана OTel?»
**Ответ:** Код `codes.OK (0)` соответствует статусу `codes.Unset`. Коды ошибок `codes.Canceled (1)`, `codes.Unknown (2)`, `codes.InvalidArgument (3)`, `codes.DeadlineExceeded (4)`, `codes.Internal (13)` приводят к установке статуса спана `codes.Error` и записи события ошибки.
