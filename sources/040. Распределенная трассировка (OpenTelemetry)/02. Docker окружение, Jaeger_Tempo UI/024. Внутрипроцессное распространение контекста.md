# Внутрипроцессное распространение контекста: передача ctx и автоматическая привязка дочерних спанов

## Условие

Используйте **context propagation**: передавайте `ctx` через все функции, чтобы дочерние span'ы автоматически привязывались к родительским.

## Теория

Принцип единства контекста в Go:
- В Go нет механизма Thread-Local Storage (TLS), как в Java или Python.
- Единственный канонический способ передать спан вглубь стека вызовов — **первый параметр `ctx context.Context`**.
- Механика связывания:
  1. Вызывающая функция: `ctx, parent := tracer.Start(ctx, "Parent")`.
  2. Передача: `childFunc(ctx)`.
  3. Внутри: `_, child := tracer.Start(ctx, "Child")`.
  4. OTel автоматически читает `parent.SpanID` из входящего `ctx` и связывает их!

## Решение по шагам

1. Создайте функции верхнего и нижнего уровней с аргументом `ctx`.
2. Смоделируйте передачу `ctx` от контроллера к сервису и репозиторию.
3. Проверьте автоматическое формирование связей `ParentSpanID`.
4. Верифицируйте непрерывность трейса.

## Код решения

**`in_process_context_propagation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type traceContextKey struct{}

type TraceNodeCtx struct {
	Name     string
	SpanID   string
	ParentID string
}

func WithSpan(ctx context.Context, name, id string) (context.Context, TraceNodeCtx) {
	parentID := ""
	if parent, ok := ctx.Value(traceContextKey{}).(TraceNodeCtx); ok {
		parentID = parent.SpanID
	}

	node := TraceNodeCtx{Name: name, SpanID: id, ParentID: parentID}
	return context.WithValue(ctx, traceContextKey{}, node), node
}

func ServiceLayer(ctx context.Context) TraceNodeCtx {
	_, span := WithSpan(ctx, "Service.ExecuteBusinessLogic", "span-srv-2")
	return span
}

func RepositoryLayer(ctx context.Context) TraceNodeCtx {
	_, span := WithSpan(ctx, "Repo.QueryDB", "span-repo-3")
	return span
}

func TestInProcessContextPropagation(t *testing.T) {
	ctx := context.Background()

	// 1. Controller
	ctx, root := WithSpan(ctx, "HTTP.Handler", "span-ctrl-1")

	// 2. Service
	srvSpan := ServiceLayer(ctx)

	// 3. Repo (передаем контекст сервиса!)
	srvCtx := context.WithValue(ctx, traceContextKey{}, srvSpan)
	repoSpan := RepositoryLayer(srvCtx)

	if srvSpan.ParentID != root.SpanID {
		t.Fatalf("Service span должен ссылаться на Controller: %s != %s", srvSpan.ParentID, root.SpanID)
	}
	if repoSpan.ParentID != srvSpan.SpanID {
		t.Fatalf("Repo span должен ссылаться на Service: %s != %s", repoSpan.ParentID, srvSpan.SpanID)
	}

	fmt.Println("Внутрипроцессное распространение контекста подтверждено:")
	fmt.Printf("  • Controller: %s (ID: %s)\n", root.Name, root.SpanID)
	fmt.Printf("    └── Service: %s (ParentID: %s)\n", srvSpan.Name, srvSpan.ParentID)
	fmt.Printf("        └── Repo: %s (ParentID: %s)\n", repoSpan.Name, repoSpan.ParentID)
}
```

ℹ️ Сквозная передача context.Context через слои Controller -> Service -> Repository

## Под капотом

В Go `context.Context` представляет собой связный список (Linked List) неизменяемых узлов: каждый вызов `WithValue` создает тонкую обертку над родительским контекстом, не мутируя исходный объект.

## Подводные камни

Передавать `context.TODO()` или `context.Background()` в дочерние методы: это полностью ломает распространение трейсинга, создавая изолированные корневые спаны вместо связного дерева.

## На собеседовании

**Вопрос с собеседования:** «Почему в стандартной библиотеке Go контекст всегда передается первым аргументом функции func(ctx context.Context, ...)?»
**Ответ:** Это фундаментальное архитектурное соглашение Go (Go Code Review Comments). Оно обеспечивает единообразие сигнатур, гарантирует, что разработчик сразу видит контекст отмены/таймаута, и позволяет линтерам (`revive`, `golangci-lint`) автоматически проверять корректность передачи трейсинга.
