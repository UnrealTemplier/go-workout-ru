# Управление спаном HTTP-обработчика: tracer.Start(ctx, handleRequest) и гарантированный defer span.End()

## Условие

Создай span для HTTP-обработчика: `tracer.Start(ctx, "handleRequest")`. Обязательно вызови `span.End()` через `defer`.

## Теория

Строгая идиома defer span.End():
- Главное правило OpenTelemetry: **каждый созданный спан ОБЯЗАН быть закрыт вызовом `span.End()`**.
- Конструкция `defer span.End()` гарантирует:
  1. Корректное закрытие спана при любом пути возврата (`return nil`, `return err`).
  2. Фиксацию времени даже при возникновении паники внутри функции.
  3. Предотвращение утечек памяти в буфере процессора спанов.

## Решение по шагам

1. Создайте HTTP обработчик с ручным созданием спана.
2. Примените идиому `defer span.End()`.
3. Смоделируйте выполнение запроса с ранним выходом.
4. Проверьте обязательную фиксацию закрытия спана.

## Код решения

**`handler_defer_span_end_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type TrackedHandlerSpan struct {
	Name   string
	Closed bool
}

func HandleUserRequest(ctx context.Context, failEarly bool) (span *TrackedHandlerSpan, err error) {
	span = &TrackedHandlerSpan{Name: "handleRequest"}
	defer func() {
		span.Closed = true
	}()

	if failEarly {
		return span, fmt.Errorf("bad request payload")
	}

	return span, nil
}

func TestHandlerDeferSpanEnd(t *testing.T) {
	// 1. Тест с ранней ошибкой
	span1, err := HandleUserRequest(context.Background(), true)
	if err == nil || !span1.Closed {
		t.Fatalf("Спан обязан быть закрыт даже при раннем выходе: %+v", span1)
	}

	// 2. Тест с успешным выполнением
	span2, err := HandleUserRequest(context.Background(), false)
	if err != nil || !span2.Closed {
		t.Fatalf("Спан обязан быть закрыт при успехе: %+v", span2)
	}

	fmt.Println("Идиома defer span.End() успешно подтверждена:")
	fmt.Printf("  • Сценарий 1 (Ранняя ошибка): Closed = %v\n", span1.Closed)
	fmt.Printf("  • Сценарий 2 (Успех):         Closed = %v\n", span2.Closed)
	fmt.Println("  • Утечки незакрытых спанов в рантайме полностью исключены!")
}
```

ℹ️ Гарантия закрытия спана через defer при любых вариантах завершения функции

## Под капотом

Незакрытый спан навсегда зависает в памяти: `BatchSpanProcessor` не может отправить спан экспортеру до тех пор, пока не выставлена конечная временная метка `EndTime`.

## Подводные камни

Вызывать `span.End()` вручную в конце функции без `defer`: при возникновении паники или возврате по `if err != nil` спан останется незакрытым и никогда не появится в UI Jaeger.

## На собеседовании

**Вопрос с собеседования:** «Можно ли вызывать span.End() несколько раз для одного спана?»
**Ответ:** Первый вызов `span.End()` фиксирует конечное время и передает спан процессору. Все последующие вызовы `span.End()` по спецификации OTel игнорируются (no-op), однако повторный вызов считается плохим стилем кода.
