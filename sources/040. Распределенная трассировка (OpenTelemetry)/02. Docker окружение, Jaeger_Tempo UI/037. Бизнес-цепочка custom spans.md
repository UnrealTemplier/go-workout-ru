# Бизнес-цепочка custom spans: иерархия createOrder -> validateOrder, reserveInventory, processPayment

## Условие

Создайте **custom span** для бизнес-логики: `validateOrder`, `reserveInventory`, `processPayment` — каждый как отдельный span внутри `createOrder`.

## Теория

Шаблон бизнес-оркестрации в трассировке:
- Корневой спан `createOrder` агрегирует общее время выполнения транзакции оформления заказа.
- Вложенные бизнес-спаны:
  1. `validateOrder` (проверка цен, наличия и адреса доставки).
  2. `reserveInventory` (резервирование ячеек на складе).
  3. `processPayment` (взаимодействие с платежным шлюзом).
- В случае ошибки одного из этапов UI четко подсветит проблемный узел, не требуя копания в логах.

## Решение по шагам

1. Создайте метод оркестрации бизнес-заказа.
2. Инициируйте родительский спан `createOrder`.
3. Последовательно выполните шаги `validateOrder`, `reserveInventory` и `processPayment`.
4. Проверьте связность дерева спанов.

## Код решения

**`business_pipeline_hierarchy_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type ExecutionStep struct {
	Name     string
	Parent   string
	Duration time.Duration
}

func ExecuteOrderBusinessFlow() []ExecutionStep {
	var steps []ExecutionStep
	parent := "createOrder"

	// 1. Валидация
	steps = append(steps, ExecutionStep{Name: "validateOrder", Parent: parent, Duration: 4 * time.Millisecond})
	// 2. Резервирование
	steps = append(steps, ExecutionStep{Name: "reserveInventory", Parent: parent, Duration: 15 * time.Millisecond})
	// 3. Платеж
	steps = append(steps, ExecutionStep{Name: "processPayment", Parent: parent, Duration: 45 * time.Millisecond})

	return steps
}

func TestBusinessPipelineHierarchy(t *testing.T) {
	steps := ExecuteOrderBusinessFlow()

	if len(steps) != 3 {
		t.Fatalf("Ожидалось 3 шага, получено: %d", len(steps))
	}

	fmt.Println("Иерархия бизнес-спанов createOrder успешно подтверждена:")
	fmt.Printf("└── [ROOT] createOrder\n")
	for _, s := range steps {
		fmt.Printf("    ├── %-20s (Parent: %s, Задержка: %v)\n", s.Name, s.Parent, s.Duration)
	}
	fmt.Println("  • Любая задержка платежного шлюза мгновенно видна на диаграмме водопада!")
}
```

## Под капотом

Дочерние спаны автоматически наследуют родительские семантические флаги сэмплирования: если корневой спан `createOrder` был отобран для сохранения, все его дочерние спаны гарантированно сохранятся.

## Подводные камни

Создавать дочерние спаны параллельно в горутинах без правильной синхронизации: если родительский спан закроется раньше, чем завершатся дочерние горутины, граф вызова покажется сломанным (дочерние спаны вылезут за пределы родителя).

## На собеседовании

**Вопрос с собеседования:** «Как корректно завершать родительский спан, если дочерние этапы выполняются параллельно в sync.WaitGroup?»
**Ответ:** Родительский спан должен закрываться только **после** вызова `wg.Wait()`. В главной горутине пишут:
```go
ctx, parentSpan := tracer.Start(ctx, "ParallelJob")
defer parentSpan.End()

var wg sync.WaitGroup
// запуск дочерних горутин
wg.Wait()
```
Это гарантирует, что время родительского спана полностью покроет самую медленную из параллельных веток.
