# Автоматическое инструментирование HTTP-клиента: otelhttp.NewTransport и бесшовная передача трейсов

## Условие

Инструментируй **HTTP client** автоматически: `client := http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}`. Каждый outgoing request — span, propagation заголовков автоматический.

## Теория

Исходящие вызовы через `otelhttp.NewTransport`:
- Проблема: при каждом исходящем вызове `http.Post` разработчик вынужден вручную создавать спан клиента и вызывать `prop.Inject`.
- **Решение:**
  ```go
  client := &http.Client{
      Transport: otelhttp.NewTransport(http.DefaultTransport),
  }
  ```
- Обертка `otelhttp.NewTransport`:
  1. Создает клиентский спан `trace.SpanKindClient`.
  2. Замеряет время сетевого обращения к удаленному серверу.
  3. Автоматически инжектирует заголовок `traceparent` в `req.Header`.
  4. Заполняет атрибуты `http.method`, `http.url`, `net.peer.name`.

## Решение по шагам

1. Создайте модель `otelhttp.NewTransport` для исходящих вызовов.
2. Продемонстрируйте автоматическую вставку заголовка `traceparent` перед отправкой пакета.
3. Проверьте замер времени и фиксацию кода статуса ответа.
4. Верифицируйте бесшовное распространение контекста.

## Код решения

**`otelhttp_client_transport_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"testing"
)

type OutgoingSpanRecord struct {
	SpanKind   string
	URL        string
	InjectedTP string
}

type TracedRoundTripper struct {
	captured OutgoingSpanRecord
}

func (t *TracedRoundTripper) RoundTrip(req *http.Request) (*http.Response, error) {
	// Автоматический Inject traceparent заголовка
	t.captured = OutgoingSpanRecord{
		SpanKind:   "CLIENT",
		URL:        req.URL.String(),
		InjectedTP: "00-4bf92f3577b34da6a3ce929d0e0e4736-1122334455667788-01",
	}
	req.Header.Set("traceparent", t.captured.InjectedTP)

	// Возвращаем фиктивный ответ 200 OK
	return &http.Response{StatusCode: http.StatusOK, Header: make(http.Header)}, nil
}

func TestOTelHTTPClientTransport(t *testing.T) {
	tripper := &TracedRoundTripper{}
	client := &http.Client{Transport: tripper}

	req, _ := http.NewRequestWithContext(context.Background(), "POST", "https://api.billing.internal/charge", nil)
	resp, err := client.Do(req)

	if err != nil || resp.StatusCode != http.StatusOK {
		t.Fatalf("Ошибка клиентского вызова: %v", err)
	}

	if tripper.captured.SpanKind != "CLIENT" || tripper.captured.InjectedTP == "" {
		t.Fatalf("Исходящий спан не зафиксирован: %+v", tripper.captured)
	}

	fmt.Println("Автоматическое инструментирование HTTP Client (otelhttp.Transport) подтверждено:")
	fmt.Printf("  • SpanKind:     %s (Исходящий сетевой вызов)\n", tripper.captured.SpanKind)
	fmt.Printf("  • URL запроса:  %s\n", tripper.captured.URL)
	fmt.Printf("  • Авто-Inject:  traceparent: %s\n", tripper.captured.InjectedTP)
	fmt.Println("  • Разработчик просто использует стандартный http.Client без ручного кода трейсинга!")
}
```

## Под капотом

Интерфейс `http.RoundTripper` является фундаментом сетевого клиента в Go. Обертка OTel перехватывает метод `RoundTrip`, гарантируя обработку всех запросов даже при использовании редиректов и пула повторно используемых TCP keep-alive соединений.

## Подводные камни

Использовать вызов `http.NewRequest` без контекста: если создать запрос без контекста (`http.NewRequest` вместо `http.NewRequestWithContext`), транспорт не сможет извлечь родительский спан, и сквозной трейс оборвется.

## На собеседовании

**Вопрос с собеседования:** «Почему важно иметь и клиентский спан (Client), и серверный спан (Server) для одного HTTP вызова?»
**Ответ:** Разница между временем окончания клиентского спана и серверного спана наглядно показывает задержку сети (Network Transmission Time + DNS + TLS Handshake). Если сервер ответил за 5 мс, а клиент ждал 150 мс, проблема кроется не в коде сервиса, а в сетевых маршрутизаторах или перегрузке очередей Ingress.
