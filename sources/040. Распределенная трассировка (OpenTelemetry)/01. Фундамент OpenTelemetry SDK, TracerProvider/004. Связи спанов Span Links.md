# Связи спанов Span Links: моделирование пакетной обработки в очередях Kafka и асинхронные графы

## Условие

Создай **span links**: при обработке batch сообщения из Kafka — создай span для каждого сообщения, но link'ай к span'у producer'а через `span.AddLink(trace.Link{SpanContext: producerSpanCtx})`. Покажи, что link — не parent-child, а causal connection.

## Теория

Причинно-следственные связи Span Links против Parent-Child:
- В классическом синхронном HTTP родительский спан длится дольше дочернего (`Parent.Start < Child.Start < Child.End < Parent.End`).
- **Специфика пакетных очередей сообщений (Kafka / RabbitMQ):**
  - Продюсер опубликовал 500 сообщений в разное время и завершил свои спаны.
  - Консьюмер вычитал батч из 500 сообщений в одном общем цикле.
  - Какое сообщение считать родителем? Никакое!
- **Span Link (`trace.WithLinks`):**
  - Отражает причинно-следственную связь (Causal Connection) между независимыми трейсами.
  - Позволяет спану консьюмера ссылаться на спан продюсера без искусственного продления жизни родительского контекста.

## Решение по шагам

1. Создайте модель спан-контекста продюсера.
2. Смоделируйте пакетную вычитку сообщений консьюмером.
3. Добавьте `SpanLink` к каждому обрабатываемому сообщению.
4. Проверьте сохранение независимости TraceID при наличии причинной связи.

## Код решения

**`span_links_kafka_batch_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ProducerContext struct {
	TraceID string
	SpanID  string
}

type ConsumerSpan struct {
	Name    string
	TraceID string
	SpanID  string
	Links   []ProducerContext
}

func ProcessKafkaBatchItem(itemData string, producerCtx ProducerContext) ConsumerSpan {
	// Консьюмер создает собственный независимый трейс
	consumerTraceID := "consumer-trace-5566"
	consumerSpanID := "span-consumer-001"

	// Но связывает его причинно-следственной ссылкой (Link) с продюсером!
	span := ConsumerSpan{
		Name:    "ConsumeMessage: " + itemData,
		TraceID: consumerTraceID,
		SpanID:  consumerSpanID,
		Links:   []ProducerContext{producerCtx},
	}
	return span
}

func TestSpanLinksKafkaBatch(t *testing.T) {
	// Продюсер создал сообщение в своем трейсе
	producerCtx := ProducerContext{
		TraceID: "producer-trace-1122",
		SpanID:  "producer-span-77",
	}

	consumerSpan := ProcessKafkaBatchItem("OrderCreatedPayload", producerCtx)

	if len(consumerSpan.Links) != 1 {
		t.Fatalf("Ожидалась ровно 1 ссылка SpanLink, получено: %d", len(consumerSpan.Links))
	}

	link := consumerSpan.Links[0]
	if link.TraceID != producerCtx.TraceID || link.SpanID != producerCtx.SpanID {
		t.Fatalf("Некорректный SpanLink: %+v", link)
	}

	fmt.Println("Механизм Span Links успешно подтвержден:")
	fmt.Printf("  • Consumer TraceID: %s (Собственный независимый трейс)\n", consumerSpan.TraceID)
	fmt.Printf("  • Linked Producer:  TraceID=%s, SpanID=%s (Причинная связь)\n", link.TraceID, link.SpanID)
	fmt.Println("  • UI Jaeger/Tempo отображает кликабельную ссылку на продюсера без деформации графа!")
}
```

ℹ️ Использование Span Links для связывания пакетных сообщений очередей без Parent-Child отношений

## Под капотом

В спецификации OTel спан-ссылки могут содержать собственные атрибуты: `trace.Link{SpanContext: sc, Attributes: []attribute.KeyValue{attribute.Int("messaging.batch_index", 4)}}`, что позволяет фиксировать позицию сообщения в батче.

## Подводные камни

Пытаться назначить продюсера родителем (Parent) для пакетной обработки: в UI один гигантский родительский спан продюсера покажется длящимся часами, искажая расчет реальной сетевой задержки.

## На собеседовании

**Вопрос с собеседования:** «В каких трех архитектурных сценариях обязательны Span Links вместо обычного Parent-Child?»
**Ответ:** 
1. **Пакетная обработка (Batching):** один консьюмер обрабатывает сообщения от 100 разных продюсеров.
2. **Fan-out / Fan-in агрегация:** объединение результатов нескольких независимых параллельных вычислений в один отчет.
3. **Асинхронные крон-джобы / фоновые пайплайны:** фоновая задача берет данные, созданные пользователем 2 дня назад, и ссылается на исходную транзакцию.
