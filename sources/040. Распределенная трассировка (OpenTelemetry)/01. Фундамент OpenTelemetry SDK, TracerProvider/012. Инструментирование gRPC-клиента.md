# Инструментирование gRPC-клиента: цепочка client span -> server span -> database span

## Условие

Инструментируй **gRPC client**: `grpc.Dial(..., grpc.WithUnaryInterceptor(otelgrpc.UnaryClientInterceptor()))`. Покажи distributed trace: client span → server span → database span.

## Теория

Сквозная распределенная цепочка трассировки (End-to-End Distributed Trace):
- Архитектурная цепочка вызова:
  1. `Frontend Gateway`: клиентский спан `grpc.Client` (`otelgrpc.UnaryClientInterceptor`).
  2. `Order Microservice`: серверный спан `grpc.Server` (`otelgrpc.UnaryServerInterceptor`).
  3. `PostgreSQL Database`: спан базы данных `db.Query` (`otelsql`).
- Все три операции имеют строго одинаковый `TraceID`, демонстрируя непрерывный путь данных от API шлюза до диска СУБД.

## Решение по шагам

1. Создайте модель сквозной трассировки из трех звеньев.
2. Продемонстрируйте вызов gRPC клиента с сохранением TraceID.
3. Продемонстрируйте переход на сервер gRPC и далее к SQL запросу.
4. Проверьте целостность сквозного графа.

## Код решения

**`grpc_client_distributed_trace_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TraceNode struct {
	Role    string
	Name    string
	TraceID string
	SpanID  string
	Parent  string
}

func TestGRPCClientDistributedTrace(t *testing.T) {
	commonTraceID := "distributed-trace-uuid-7711"

	// 1. Client Span (Gateway)
	clientSpan := TraceNode{
		Role:    "gRPC Client",
		Name:    "Invoke /OrderService/CreateOrder",
		TraceID: commonTraceID,
		SpanID:  "span-client-01",
		Parent:  "",
	}

	// 2. Server Span (Order Service)
	serverSpan := TraceNode{
		Role:    "gRPC Server",
		Name:    "Exec /OrderService/CreateOrder",
		TraceID: commonTraceID,
		SpanID:  "span-server-02",
		Parent:  clientSpan.SpanID,
	}

	// 3. Database Span (SQL Query)
	dbSpan := TraceNode{
		Role:    "Database",
		Name:    "SQL: INSERT INTO orders VALUES ($1)",
		TraceID: commonTraceID,
		SpanID:  "span-db-03",
		Parent:  serverSpan.SpanID,
	}

	nodes := []TraceNode{clientSpan, serverSpan, dbSpan}

	for _, n := range nodes {
		if n.TraceID != commonTraceID {
			t.Fatalf("Разрыв TraceID в узле: %+v", n)
		}
	}

	fmt.Println("Сквозной распределенный трейс (Distributed Trace) успешно подтвержден:")
	fmt.Printf("1. [%-11s] %s (SpanID: %s)\n", clientSpan.Role, clientSpan.Name, clientSpan.SpanID)
	fmt.Printf("   └── 2. [%-11s] %s (Parent: %s, SpanID: %s)\n", serverSpan.Role, serverSpan.Name, serverSpan.Parent, serverSpan.SpanID)
	fmt.Printf("          └── 3. [%-11s] %s (Parent: %s, SpanID: %s)\n", dbSpan.Role, dbSpan.Name, dbSpan.Parent, dbSpan.SpanID)
	fmt.Printf("  • Единый сквозной TraceID: %s\n", commonTraceID)
}
```

ℹ️ Сквозная трехуровневая трассировка вызова gRPC Client -> gRPC Server -> Database

**`Терминал`**


## Под капотом

В распределенном графе спан `dbSpan` наследует `SpanID` серверного спана как `ParentSpanID`, формируя каноническую структуру дерева водопада в UI Grafana/Tempo.

## Подводные камни

Создавать новый экземпляр `grpc.ClientConn` на каждый запрос: создание gRPC соединения включает TLS-рукопожатие и занимает до 100 мс. Клиентский пул gRPC соединений создается один раз при старте сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как в распределенном трейсинге определить, на каком звене произошел сетевой таймаут (DeadlineExceeded)?»
**Ответ:** По сопоставлению временных меток спанов: клиентский спан завершится со статусом `codes.DeadlineExceeded`, а спан сервера либо вообще не появится (если запрос не дошел по сети), либо завершится с событием отмены контекста `context.Canceled`, указывая, что клиент оборвал соединение до завершения работы базы.
