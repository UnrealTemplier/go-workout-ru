# Инструментирование клиента Redis: хуки redisotel для замера команд и семантика db.system

## Условие

Инструментируй **Redis/go-redis**: `github.com/redis/go-redis/extra/redisotel/v9`. `rdb.AddHook(redisotel.NewTracingHook())`. Каждая команда — span с `db.system = redis`, `db.statement = GET user:123`.

## Теория

Инструментирование кэширующего слоя `go-redis`:
- Пакет `github.com/redis/go-redis/extra/redisotel/v9`:
  - Использует встроенную систему перехвата вызовов `rdb.AddHook(...)`.
  - Перед отправкой команды (`ProcessHook`):
    - Создает дочерний спан с именем команды (`redis.GET`).
    - Заполняет `db.system = "redis"`, `db.statement = "GET user:123"`.
    - Измеряет время сетевого RTT до инстанса Redis.
  - Обрабатывает ошибки типа `redis.Nil` (ключ отсутствует в кэше — не считается ошибкой сервиса!).

## Решение по шагам

1. Создайте модель перехватчика хуков клиента Redis.
2. Продемонстрируйте выполнение команды `GET user:123`.
3. Заполните семантические атрибуты `db.system` и `db.statement`.
4. Проверьте корректное измерение задержки кэша.

## Код решения

**`redisotel_client_hook_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type RedisSpanRecord struct {
	SpanName    string
	DBSystem    string
	DBStatement string
	Duration    time.Duration
}

type MockRedisClientWithTracing struct {
	recordedSpans []RedisSpanRecord
}

func (c *MockRedisClientWithTracing) Get(ctx context.Context, key string) (string, error) {
	start := time.Now()
	// Имитируем быстрый ответ Redis за 1 мс
	time.Sleep(1 * time.Millisecond)

	c.recordedSpans = append(c.recordedSpans, RedisSpanRecord{
		SpanName:    "GET",
		DBSystem:    "redis",
		DBStatement: fmt.Sprintf("GET %s", key),
		Duration:    time.Since(start),
	})
	return "cached_user_data", nil
}

func TestRedisOTelClientHook(t *testing.T) {
	client := &MockRedisClientWithTracing{}

	val, err := client.Get(context.Background(), "user:profile:1020")
	if err != nil || val != "cached_user_data" {
		t.Fatalf("Ошибка вызова Redis: %v", err)
	}

	if len(client.recordedSpans) != 1 {
		t.Fatalf("Ожидался 1 спан Redis, получено: %d", len(client.recordedSpans))
	}

	span := client.recordedSpans[0]
	if span.DBSystem != "redis" || span.DBStatement != "GET user:profile:1020" {
		t.Fatalf("Некорректный спан Redis: %+v", span)
	}

	fmt.Println("Инструментирование go-redis (redisotel) успешно подтверждено:")
	fmt.Printf("  • Имя спана:    %s\n", span.SpanName)
	fmt.Printf("  • db.system:    %s\n", span.DBSystem)
	fmt.Printf("  • db.statement: %s\n", span.DBStatement)
	fmt.Printf("  • Длительность: %v (Субмиллисекундный кэш)\n", span.Duration)
}
```

## Под капотом

В `redisotel` ошибка `redis.Nil` специально исключена из пометок `codes.Error`: отсутствие ключа в кэше является нормальным ходом выполнения программы (Cache Miss), требующим похода в базу, а не красной аварии.

## Подводные камни

Включать в `db.statement` гигантские бинарные значения команды `SET key <blob>`: в `redisotel` передается только имя команды и ключ, а само тело полезной нагрузки отсекается для экономии памяти.

## На собеседовании

**Вопрос с собеседования:** «Как с помощью трассировки Redis выявить паттерн "N+1 Queries" при обращении к кэшу?»
**Ответ:** На диаграмме водопада в Jaeger/Tempo видна цепочка из 50 последовательных спанов `GET user:1`, `GET user:2` ... `GET user:50`, каждый по 1 мс, суммарно съедающих 50 мс. Оптимизация заключается в объединении вызовов в один пакетный спан `MGET` или pipeline.
