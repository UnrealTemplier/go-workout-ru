# Пользовательское инструментирование бизнес-логики: метод ProcessOrder, атрибуты и sub-spans этапов

## Условие

Создай **custom instrumentation** для бизнес-логики: `func ProcessOrder(ctx context.Context, orderID string) error { ctx, span := tracer.Start(ctx, "ProcessOrder", trace.WithAttributes(attribute.String("order.id", orderID))); defer span.End(); ... }`. Добави sub-spans для каждого шага.

## Теория

Кастомная трассировка бизнес-процессов (Domain Tracing):
- Автоматические библиотеки (HTTP, SQL) видят только технический транспорт.
- **Инженерная ценность кастомной трассировки:**
  - Отражает шаги предметной области (DDD Domain Steps):
    1. `ValidateCart` (проверка цен и промокодов).
    2. `ReserveWarehouseStock` (резервирование остатков).
    3. `ExecuteCardBilling` (обращение к эквайрингу).
  - Позволяет продакт-менеджерам и техлидам видеть время каждого бизнес-этапа на графике без погружения в стек SQL-таблиц.

## Решение по шагам

1. Создайте функцию `ProcessOrder` с корневым бизнес-спаном.
2. Реализуйте дочерние спаны для шагов валидации, резервирования и списания.
3. Обогатите спаны бизнес-атрибутами `order.id` и `items.count`.
4. Проверьте целостность иерархии бизнес-транзакции.

## Код решения

**`custom_business_instrumentation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type BusinessSpan struct {
	Name     string
	OrderID  string
	Step     string
	Duration time.Duration
}

type OrderPipelineTracker struct {
	steps []BusinessSpan
}

func (p *OrderPipelineTracker) RunStep(orderID, stepName string, work time.Duration) {
	start := time.Now()
	time.Sleep(work)
	p.steps = append(p.steps, BusinessSpan{
		Name:     "ProcessOrderStep",
		OrderID:  orderID,
		Step:     stepName,
		Duration: time.Since(start),
	})
}

func ExecuteOrderPipeline(orderID string) []BusinessSpan {
	tracker := &OrderPipelineTracker{}

	// Шаг 1: Валидация корзины
	tracker.RunStep(orderID, "ValidateCart", 5*time.Millisecond)

	// Шаг 2: Резервирование остатков на складе
	tracker.RunStep(orderID, "ReserveWarehouseStock", 12*time.Millisecond)

	// Шаг 3: Списание средств
	tracker.RunStep(orderID, "ExecuteCardBilling", 20*time.Millisecond)

	return tracker.steps
}

func TestCustomBusinessInstrumentation(t *testing.T) {
	steps := ExecuteOrderPipeline("ord-778899")

	if len(steps) != 3 {
		t.Fatalf("Ожидалось 3 бизнес-шага, получено: %d", len(steps))
	}

	fmt.Println("Пользовательская бизнес-трассировка успешно выполнена:")
	for idx, s := range steps {
		fmt.Printf("  #%d [%s] Step: %-22s -> %v\n", idx+1, s.OrderID, s.Step, s.Duration)
	}
	fmt.Println("  • Полная прозрачность бизнес-процесса для инженеров и продуктовых аналитиков!")
}
```

## Под капотом

Каждый бизнес-спан получает свои временные рамки и может независимо устанавливать статус ошибки, позволяя локализовать точный шаг, на котором споткнулся бизнес-процесс.

## Подводные камни

Создавать спан на каждую строчку кода (микро-спаны по 100 наносекунд): создание спана в памяти требует около 1–2 микросекунд. Трассируют только значимые логические блоки и вызовы ввода-вывода.

## На собеседовании

**Вопрос с собеседования:** «Как именовать спаны в соответствии со стандартами OpenTelemetry Semantic Conventions?»
**Ответ:** Имя спана должно быть кратким и не содержать динамических данных: глагол + существительное низкой кардинальности (например `ValidateCart`, `ProcessOrder`, `FetchUser`). Динамические данные (`order.id = "123"`, `user.id = "456"`) передаются строго через **атрибуты**, а не через имя спана.
