# Фиксация ошибок в трейсах: семантический статус codes.Error против детального события span.RecordError

## Условие

Добави **status и error recording**: при ошибке `span.SetStatus(codes.Error, "database connection failed")`, `span.RecordError(err, trace.WithAttributes(attribute.String("db.instance", "postgres-primary")))`. Покажи разницу между status (semantic) и error event (detailed).

## Теория

Разница между Status и Error Event в OpenTelemetry:
1. **Span Status (`codes.Error`):**
   - Семантический флаг результата операции: `Unset` (по умолчанию), `Ok` или `Error`.
   - В UI (Jaeger/Tempo) окрашивает полоску спана в красный цвет.
   - Используется системами мониторинга для подсчета процента сбоев (Error Rate).
2. **Error Event (`span.RecordError`):**
   - Создает детальное структурированное событие (Event) спана с временной меткой.
   - Содержит точный тип ошибки (`exception.type`), текст сообщения (`exception.message`), стектрейс (`exception.stacktrace`) и кастомные атрибуты (`db.instance`).
- В BigTech при любой ошибке вызывают **ОБА** метода: `SetStatus` для подсветки и алертинга, и `RecordError` для глубокого разбора инцидента.

## Решение по шагам

1. Создайте спан с поддержкой статуса и коллекции событий.
2. Смоделируйте возникновение ошибки базы данных.
3. Вызовите `RecordError` с атрибутом экземпляра БД.
4. Вызовите `SetStatus(codes.Error, ...)`.
5. Проверьте различие между статусом спана и записью события.

## Код решения

**`status_vs_error_event_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
	"time"
)

type StatusCode string

const (
	StatusUnset StatusCode = "UNSET"
	StatusOK    StatusCode = "OK"
	StatusError StatusCode = "ERROR"
)

type Event struct {
	Name       string
	Timestamp  time.Time
	Attributes map[string]string
}

type DetailedSpan struct {
	Status      StatusCode
	Description string
	Events      []Event
}

func (s *DetailedSpan) SetStatus(code StatusCode, desc string) {
	s.Status = code
	s.Description = desc
}

func (s *DetailedSpan) RecordError(err error, attrs map[string]string) {
	if attrs == nil {
		attrs = make(map[string]string)
	}
	attrs["exception.message"] = err.Error()
	attrs["exception.type"] = fmt.Sprintf("%T", err)

	s.Events = append(s.Events, Event{
		Name:       "exception",
		Timestamp:  time.Now(),
		Attributes: attrs,
	})
}

func TestStatusVsErrorEvent(t *testing.T) {
	span := &DetailedSpan{Status: StatusUnset}

	dbErr := errors.New("pq: connection refused on port 5432")

	// 1. Детальная запись события ошибки
	span.RecordError(dbErr, map[string]string{"db.instance": "postgres-primary"})

	// 2. Семантическая установка статуса ошибки
	span.SetStatus(StatusError, "database connection failed")

	if span.Status != StatusError {
		t.Fatalf("Ожидался статус ERROR, получено: %s", span.Status)
	}
	if len(span.Events) != 1 || span.Events[0].Attributes["db.instance"] != "postgres-primary" {
		t.Fatalf("Событие ошибки записано некорректно: %+v", span.Events)
	}

	fmt.Println("Разделение Status и Error Event успешно верифицировано:")
	fmt.Printf("  • Span Status: %s (%s) -> Красная подсветка в Grafana/Tempo\n", span.Status, span.Description)
	fmt.Printf("  • Error Event: %s -> %s (Тип: %s, Instance: %s)\n",
		span.Events[0].Name,
		span.Events[0].Attributes["exception.message"],
		span.Events[0].Attributes["exception.type"],
		span.Events[0].Attributes["db.instance"],
	)
}
```

## Под капотом

Спецификация OpenTelemetry запрещает перезаписывать статус спана на `codes.Ok`, если он уже был установлен в `codes.Error`: статус ошибки является терминальным и имеет наивысший приоритет в анализе надежности.

## Подводные камни

Вызывать `RecordError`, забывая вызвать `SetStatus(codes.Error)`: в таком случае спан останется с нейтральным статусом `Unset`, и в интерфейсе Jaeger/Tempo запрос покажется успешным, несмотря на наличие события ошибки внутри.

## На собеседовании

**Вопрос с собеседования:** «Когда в OpenTelemetry следует явно выставлять статус codes.Ok?»
**Ответ:** Практически никогда. По спецификации OTel спан по умолчанию имеет статус `Unset`, что означает успешное завершение операции без явных отклонений. Статус `codes.Ok` выставляют только тогда, когда нужно явно перекрыть возможные ошибочные предположения родительского спана (например, при успешном выполнении Fallback-логики после первичного сбоя).
