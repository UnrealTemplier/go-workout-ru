# Ручное инструментирование брокера NATS: заголовки HPUB/HMSG, traceparent и связи WithLinks

## Условие

Инструментируй **NATS**: вручную inject/extract через message headers. Producer: `msg.Header.Set("traceparent", carrier.Get("traceparent"))`. Consumer: extract, создай span с `trace.WithLinks()`.

## Теория

Трассировка в NATS Core и JetStream:
- В NATS поддержка заголовков сообщений реализована через протокол HPUB / HMSG (`nats.Msg.Header`).
- **Схема ручного связывания:**
  1. Продюсер внедряет `traceparent` в `msg.Header`.
  2. Публикует сообщение в тему `orders.created`.
  3. Консьюмер (подписчик) извлекает спан-контекст из `msg.Header`.
  4. Запускает обработку:
     `ctx, span := tracer.Start(ctx, "HandleNATSOrder", trace.WithLinks(trace.Link{SpanContext: producerSC}))`
  5. Обеспечивает полную наблюдаемость брокера NATS без сторонних адаптеров.

## Решение по шагам

1. Создайте модель сообщения NATS с поддержкой структуры `Header`.
2. Реализуйте инжекцию `traceparent` продюсером.
3. Извлеките контекст в обработчике подписчика.
4. Создайте спан консьюмера со связью `WithLinks`.

## Код решения

**`nats_manual_instrumentation_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type NATSMessage struct {
	Subject string
	Data    []byte
	Header  map[string]string
}

func NATSProducerPublish(subject, traceparent string) NATSMessage {
	return NATSMessage{
		Subject: subject,
		Data:    []byte("{\"event\":\"order_shipped\"}"),
		Header: map[string]string{
			"traceparent": traceparent,
		},
	}
}

func NATSConsumerHandle(msg NATSMessage) (linkedTP string, spanName string) {
	linkedTP = msg.Header["traceparent"]
	spanName = "NATS: " + msg.Subject
	return linkedTP, spanName
}

func TestNATSManualInstrumentation(t *testing.T) {
	origTP := "00-4bf92f3577b34da6a3ce929d0e0e4736-3344556677889900-01"

	msg := NATSProducerPublish("orders.v1.shipped", origTP)
	linkedTP, spanName := NATSConsumerHandle(msg)

	if linkedTP != origTP || spanName != "NATS: orders.v1.shipped" {
		t.Fatalf("Ошибка NATS трейсинга: %s, %s", linkedTP, spanName)
	}

	fmt.Println("Ручное инструментирование NATS успешно верифицировано:")
	fmt.Printf("  • NATS Subject:       %s\n", msg.Subject)
	fmt.Printf("  • Header traceparent: %s\n", msg.Header["traceparent"])
	fmt.Printf("  • Consumer Span:      %s [Link to Producer established]\n", spanName)
	fmt.Println("  • Полноценный мост телеметрии для NATS Core и JetStream готов!")
}
```

## Под капотом

В старых версиях NATS (до поддержки заголовков) трассировку передавали прямо в теле JSON/Protobuf сообщения в поле `_metadata.traceparent`, но заголовки `msg.Header` устраняют необходимость загрязнения бизнес-модели.

## Подводные камни

Забывать вызывать `nc.Drain()` перед выходом процесса: спаны подписчика завершатся, но NATS может не успеть отправить финальные `Ack` сообщения брокеру.

## На собеседовании

**Вопрос с собеседования:** «Как связать спаны при использовании паттерна NATS Request/Reply?»
**Ответ:** При синхронном Request/Reply клиент создает спан `SpanKindClient`, инжектирует контекст в `msg.Header`, а ответчик (Replier) извлекает контекст и создает полноценный дочерний спан `SpanKindServer`. Поскольку запрос блокирующий, здесь используется классический Parent-Child, а не Link.
