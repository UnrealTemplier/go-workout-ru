# Пакетный процессор batch в OpenTelemetry Collector: буферизация, сжатие и снижение нагрузки на бэкенд

## Условие

Используйте **batch processor** для агрегации данных перед отправкой (снижение нагрузки на backend).

## Теория

Оптимизация сетевого ввода-вывода процессором batch:
- Отправка каждого спана отдельным HTTP/gRPC запросом создает колоссальный оверхед: на каждый спан приходится полный стек TCP/TLS заголовков.
- **Процессор `batch` в OTel Collector:**
  ```yaml
  processors:
    batch:
      timeout: 1s
      send_batch_size: 1024
      send_batch_max_size: 2048
  ```
- **Механика работы:**
  - Накапливает спаны в кольцевом буфере.
  - Сбрасывает батч при накоплении `send_batch_size` элементов ИЛИ по истечении `timeout`.
  - Применяет сжатие Snappy/Gzip к готовому батчу, снижая нагрузку на сеть и бэкенд (Tempo) на 85%.

## Решение по шагам

1. Создайте модель кольцевого буфера процессора `batch`.
2. Смоделируйте поступление спанов с триггером по размеру батча.
3. Смоделируйте срабатывание тайм-аута сброса неполного пакета.
4. Верифицируйте снижение количества исходящих сетевых пакетов.

## Код решения

**`batch_processor_buffering_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BatchProcessorSim struct {
	BatchSizeLimit int
	currentBatch   []string
	FlushedBatches int
}

func (b *BatchProcessorSim) Ingest(spanID string) {
	b.currentBatch = append(b.currentBatch, spanID)
	if len(b.currentBatch) >= b.BatchSizeLimit {
		b.Flush()
	}
}

func (b *BatchProcessorSim) Flush() {
	if len(b.currentBatch) > 0 {
		b.FlushedBatches++
		b.currentBatch = nil
	}
}

func TestBatchProcessorBuffering(t *testing.T) {
	proc := &BatchProcessorSim{BatchSizeLimit: 100}

	// Посылаем 250 спанов
	for i := 1; i <= 250; i++ {
		proc.Ingest(fmt.Sprintf("span-%03d", i))
	}

	// Оставшиеся 50 сбрасываются по таймеру
	proc.Flush()

	if proc.FlushedBatches != 3 {
		t.Fatalf("Ожидалось 3 сброшенных батча (100+100+50), получено: %d", proc.FlushedBatches)
	}

	fmt.Println("Процессор batch в OTel Collector успешно подтвержден:")
	fmt.Printf("  • Обработано спанов: 250\n")
	fmt.Printf("  • Сетевых пакетов:   %d (Вместо 250 одиночных сетевых вызовов!)\n", proc.FlushedBatches)
	fmt.Println("  • Оверхед на TCP/TLS рукопожатия и заголовки снижен на 98.8%!")
}
```

## Под капотом

`batch` процессор в OTel Collector написан с использованием пула объектов `sync.Pool`, переиспользующего байтовые срезы Protobuf сериализации и минимизирующего давление на рантайм-сборщик мусора Go.

## Подводные камни

Выставлять слишком большой таймаут (`timeout: 60s`): спаны будут доходить до Jaeger с минутной задержкой, что недопустимо во время расследования оперативных инцидентов.

## На собеседовании

**Вопрос с собеседования:** «Почему процессор batch должен стоять в конце списка processors, а не в начале?»
**Ответ:** Потому что процессоры фильтрации (`filter`) и сэмплирования (`tail_sampling`) отбрасывают значительную часть данных. Если поставить `batch` в начале, коллектор будет формировать пакеты из спанов, которые через шаг будут уничтожены, впустую расходуя процессорное время.
