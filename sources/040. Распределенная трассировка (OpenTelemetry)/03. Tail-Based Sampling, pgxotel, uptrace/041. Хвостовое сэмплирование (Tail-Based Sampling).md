# Хвостовое сэмплирование (Tail-Based Sampling) в OTel Collector: 100% ошибок и 1% успешных

## Условие

Реализуйте **tail-based sampling** через OpenTelemetry Collector: сохраняйте 100% трейсов с ошибками и только 1% успешных.

## Теория

Хвостовое сэмплирование (Tail-Based Sampling):
- При классическом (Head-Based) сэмплировании решение принимается до начала запроса: система не знает, завершится ли вызов ошибкой или падением.
- **Процессор `tail_sampling` в OpenTelemetry Collector:**
  - Буферизует все спаны трейса в оперативной памяти коллектора в течение окна ожидания (например, `decision_wait: 10s`).
  - После завершения последнего спана оценивает весь трейс целиком:
    1. Если статус любого спана в графе равен `ERROR` -> сохранить **100%**!
    2. Если длительность трейса превысила 2 секунды (медленный запрос) -> сохранить **100%**!
    3. Если все операции успешны и быстры -> сохранить лишь **1%** случайной выборки (проба).
- Это кардинально экономит дисковое пространство хранилища Tempo/Jaeger без потери редких багов.

## Решение по шагам

1. Создайте модель конфигурации процессора `tail_sampling`.
2. Смоделируйте входящий поток успешных и ошибочных трейсов.
3. Примените правило 100% сохранения при ошибке (`status_code: ERROR`).
4. Примените 1% вероятностный фильтр к успешным вызовам.

## Код решения

**`tail_based_sampling_collector_test.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"testing"
)

type CompleteTrace struct {
	TraceID  string
	HasError bool
	DurationMs int
}

type TailSamplerEngine struct {
	SampledTraces []string
	DroppedTraces []string
}

func (s *TailSamplerEngine) EvaluateTrace(t CompleteTrace, seed int) {
	// 1. Правило: 100% трейсов с ошибками сохраняются безусловно!
	if t.HasError {
		s.SampledTraces = append(s.SampledTraces, t.TraceID)
		return
	}

	// 2. Правило: 1% успешных сохраняются для базовой статистики
	if seed%100 == 0 {
		s.SampledTraces = append(s.SampledTraces, t.TraceID)
	} else {
		s.DroppedTraces = append(s.DroppedTraces, t.TraceID)
	}
}

func TestTailBasedSamplingCollector(t *testing.T) {
	engine := &TailSamplerEngine{}
	r := rand.New(rand.NewSource(100))

	// Имитируем 200 успешных запросов и 5 аварийных
	for i := 1; i <= 200; i++ {
		engine.EvaluateTrace(CompleteTrace{
			TraceID:    fmt.Sprintf("trace-ok-%d", i),
			HasError:   false,
			DurationMs: 15,
		}, r.Intn(1000))
	}

	for i := 1; i <= 5; i++ {
		engine.EvaluateTrace(CompleteTrace{
			TraceID:    fmt.Sprintf("trace-err-%d", i),
			HasError:   true,
			DurationMs: 350,
		}, 999)
	}

	// Проверяем, что ВСЕ 5 ошибок сохранены!
	errCount := 0
	for _, id := range engine.SampledTraces {
		if id[:9] == "trace-err" {
			errCount++
		}
	}

	if errCount != 5 {
		t.Fatalf("Tail sampler обязан сохранить ровно 5 ошибок, сохранено: %d", errCount)
	}

	fmt.Println("Tail-Based Sampling процессор в OTel Collector успешно подтвержден:")
	fmt.Printf("  • Всего трейсов с ошибками: 5  -> Сохранено: %d (100%%)\n", errCount)
	fmt.Printf("  • Успешных трейсов:        200 -> Отброшено: %d (Экономия диска)\n", len(engine.DroppedTraces))
	fmt.Println("  • Ни один критический инцидент не потерян из-за слепого сэмплирования!")
}
```

## Под капотом

Для корректной работы `tail_sampling` все спаны одного трейса от разных микросервисов должны приходить на один и тот же инстанс OTel Collector. Для этого перед коллекторами ставят OTel Load-Balancing Exporter, маршрутизирующий спаны по хэшу `TraceID`.

## Подводные камни

Выделять слишком мало оперативной памяти инстансу OTel Collector при Tail-Based Sampling: буферизация миллионов спанов за окно `decision_wait: 30s` может привести к Out-Of-Memory kill.

## На собеседовании

**Вопрос с собеседования:** «Почему Head-Based сэмплирование непригодно для расследования редких дефектов (Heisenbugs) в HighLoad?»
**Ответ:** При 100 000 RPS и Head-Based сэмплировании 1% вероятность того, что редкая ошибка (возникающая 1 раз в 10 000 запросов) попадет в сохраненный 1% трейсов, составляет сотые доли процента. Инженеры никогда не увидят трейс аварии. Tail-Based сэмплирование гарантирует сохранение 100% сбойных запросов независимо от общего потока.
