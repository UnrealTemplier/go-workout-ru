# Защита OTel Collector от OOM: процессор memory_limiter, check_interval и процентные лимиты

## Условие

Используйте **memory_limiter processor** для защиты Collector от OOM при пиковых нагрузках.

## Теория

Защита от Out-Of-Memory через memory_limiter:
- При пиковой нагрузке (DDOS или шквал ошибок) OTel Collector может исчерпать оперативную память контейнера и быть убит ядром Linux (`OOMKilled exit code 137`).
- **Процессор `memory_limiter`:**
  ```yaml
  processors:
    memory_limiter:
      check_interval: 1s
      limit_percentage: 75
      spike_limit_percentage: 20
  ```
- **Принцип работы:**
  1. Регулярно опрашивает рантайм Go (`runtime.ReadMemStats`).
  2. Если память приближается к порогу отсечения, коллектор начинает временно отбрасывать входящие данные и возвращать клиентам ошибку `429 Too Many Requests`.
  3. Процесс коллектора остается живым, сохраняя базовую работоспособность сервиса.

## Решение по шагам

1. Создайте модель ограничителя памяти `memory_limiter`.
2. Задайте жесткий лимит 75% и порог скачка 20%.
3. Смоделируйте скачок потребления памяти до 80%.
4. Проверьте активацию защитного сброса нагрузки (Drop/Backpressure).

## Код решения

**`memory_limiter_oom_protection_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MemoryLimiterConfig struct {
	LimitPercentage      int
	SpikeLimitPercentage int
}

func ShouldDropPayload(currentUsagePercent int, cfg MemoryLimiterConfig) (drop bool, reason string) {
	threshold := cfg.LimitPercentage - cfg.SpikeLimitPercentage
	if currentUsagePercent >= cfg.LimitPercentage {
		return true, "HARD_LIMIT_EXCEEDED"
	}
	if currentUsagePercent >= threshold {
		return true, "SPIKE_PROTECTION_TRIGGERED"
	}
	return false, "NORMAL"
}

func TestMemoryLimiterOOMProtection(t *testing.T) {
	cfg := MemoryLimiterConfig{
		LimitPercentage:      75,
		SpikeLimitPercentage: 20, // Порог ранней защиты: 75 - 20 = 55%
	}

	// 1. Нормальная нагрузка (40% RAM)
	drop1, _ := ShouldDropPayload(40, cfg)
	if drop1 {
		t.Fatal("40% RAM не должно вызывать сброс данных")
	}

	// 2. Всплеск нагрузки (65% RAM)
	drop2, reason2 := ShouldDropPayload(65, cfg)
	if !drop2 || reason2 != "SPIKE_PROTECTION_TRIGGERED" {
		t.Fatalf("Защита от скачка памяти должна сработать: %v, %s", drop2, reason2)
	}

	fmt.Println("Процессор memory_limiter в OTel Collector успешно подтвержден:")
	fmt.Printf("  • Жесткий лимит:  %d%% RAM\n", cfg.LimitPercentage)
	fmt.Printf("  • Порог скачка:   %d%% RAM (Ранний сброс при %d%%)\n", cfg.SpikeLimitPercentage, cfg.LimitPercentage-cfg.SpikeLimitPercentage)
	fmt.Printf("  • Тест на 65%% RAM: Drop=%v (%s)\n", drop2, reason2)
	fmt.Println("  • Коллектор гарантированно защищен от аварийного OOMKilled в Kubernetes!")
}
```

## Под капотом

В Go 1.19+ `memory_limiter` опирается на переменную окружения `GOMEMLIMIT`, заставляя рантайм Go агрессивнее запускать Garbage Collector до достижения лимита контейнера cgroups.

## Подводные камни

Ставить `memory_limiter` после других процессоров: процессор обязан стоять самым первым в секции `processors: [memory_limiter, ...]`, чтобы отсекать избыточный трафик до того, как на него будет выделена память в очередях.

## На собеседовании

**Вопрос с собеседования:** «Почему в memory_limiter рекомендуется использовать limit_percentage, а не фиксированный limit_mib?»
**Ответ:** Потому что при изменении `resources.limits.memory` в манифесте Kubernetes Deployment процентная конфигурация (`limit_percentage: 80%`) автоматически подстроится под новый лимит памяти контейнера без необходимости ручной правки ConfigMap коллектора.
