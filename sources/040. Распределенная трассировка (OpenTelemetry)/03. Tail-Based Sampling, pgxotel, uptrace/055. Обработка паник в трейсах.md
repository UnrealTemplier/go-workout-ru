# Обработка паник в трейсах: связка recover(), span.RecordError и codes.Error перед повторным паникованием

## Условие

**Обработка паник и ошибок в трейсах**: Если внутри спана происходит ошибка или паника, трейс должен визуализировать это красным цветом. ## Теория

Паттерн перехвата паник в критических спанах:
- Паника в Go обрывает стек выполнения и может уронить процесс.
- **Безопасная обертка спана:**
  ```go
  defer func() {
      if r := recover(); r != nil {
          err := fmt.Errorf("panic: %v", r)
          span.RecordError(err)
          span.SetStatus(codes.Error, "panic recovered")
          span.End()
          panic(r) // Повторный выброс паники для вышестоящего middleware!
      }
  }()
  ```
- Гарантирует, что даже при панике спан успеет зафиксировать факт сбоя и отправиться в Jaeger до того, как процесс завершится.

## Решение по шагам

1. Создайте функцию с защитным блоком `defer recover()`.
2. Смоделируйте возникновение паники деления на ноль.
3. Зафиксируйте панику в `RecordError` и выставьте `codes.Error`.
4. Верифицируйте корректность фиксации аварии.

## Код решения

**`panic_recovery_trace_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PanicTrackedSpan struct {
	Status      string
	Description string
	PanicMsg    string
	Closed      bool
}

func ExecuteWithPanicTracking(causePanic bool) (span *PanicTrackedSpan) {
	span = &PanicTrackedSpan{}
	defer func() {
		span.Closed = true
		if r := recover(); r != nil {
			span.Status = "ERROR"
			span.Description = "critical panic trapped"
			span.PanicMsg = fmt.Sprintf("%v", r)
		}
	}()

	if causePanic {
		panic("runtime error: integer divide by zero")
	}

	span.Status = "OK"
	return span
}

func TestPanicRecoveryTrace(t *testing.T) {
	span := ExecuteWithPanicTracking(true)

	if !span.Closed || span.Status != "ERROR" || span.PanicMsg != "runtime error: integer divide by zero" {
		t.Fatalf("Ошибка перехвата паники: %+v", span)
	}

	fmt.Println("Обработка паник в трейсах успешно подтверждена:")
	fmt.Printf("  • Статус спана:     %s\n", span.Status)
	fmt.Printf("  • Описание сбоя:    %s\n", span.Description)
	fmt.Printf("  • Сообщение паники: %s\n", span.PanicMsg)
	fmt.Printf("  • Спан закрыт:      %v (Данные гарантированно ушли в бэкенд)\n", span.Closed)
}
```

## Под капотом

Для сохранения стектрейса паники вызывают `debug.Stack()` и передают его в атрибуты события ошибки `trace.WithAttributes(attribute.String("exception.stacktrace", string(debug.Stack())))`.

## Подводные камни

Подавлять панику («глотать ошибку») без повторного вызова `panic(r)` в фоновых процессах: программа продолжит работу в поврежденном (inconsistent) состоянии памяти.

## На собеседовании

**Вопрос с собеседования:** «Почему defer span.End() необходимо объявлять ДО или ПОСЛЕ defer с recover()?»
**Ответ:** Порядок вызова `defer` работает по принципу LIFO (стек). Блок `recover()` должен стоять **позже** создания спана, чтобы сначала перехватить панику, вызвать `span.RecordError`, и только затем вызовется `span.End()`, завершающий спан со статусом ошибки.
