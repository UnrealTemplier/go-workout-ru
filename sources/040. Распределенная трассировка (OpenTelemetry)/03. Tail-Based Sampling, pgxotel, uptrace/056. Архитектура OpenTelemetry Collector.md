# Архитектура OpenTelemetry Collector: топология агента (Sidecar / DaemonSet) против централизованного Gateway

## Условие

Настройте **OpenTelemetry Collector** как агент (sidecar) и как gateway (centralized). Изучите разницу.

## Теория

Топология развертывания OpenTelemetry Collector в BigTech:
1. **Режим агента (Agent / Sidecar / DaemonSet):**
   - Развертывается локально на том же поде (Sidecar) или на каждой ноде Kubernetes (DaemonSet).
   - Принимает трафик по локалхосту (`localhost:4317` / `localhost:4318`).
   - Сверхнизкая задержка, разгрузка микросервиса (быстрый сброс в локальный сокет).
2. **Режим шлюза (Centralized Gateway):**
   - Кластер мощных инстансов коллектора за балансировщиком (HPA по CPU/RAM).
   - Выполняет тяжелые операции: Tail-Based Sampling, сжатие, маршрутизацию по нескольким ЦОД, обогащение k8s-метаданными.
- **Индустриальный стандарт:** Микросервис \(\to\) Локальный Агент \(\to\) Централизованный Gateway \(\to\) Хранилище (Tempo/Jaeger).

## Решение по шагам

1. Создайте модель топологии с двумя уровнями коллекторов.
2. Проверьте роли локального агента и централизованного шлюза.
3. Смоделируйте передачу спанов от сервиса к хранилищу.
4. Верифицируйте преимущества двухуровневой архитектуры.

## Код решения

**`otel_collector_topologies_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TopologyNode struct {
	Name     string
	Role     string
	Target   string
	Features []string
}

func BuildOTelPipelineTopology() []TopologyNode {
	return []TopologyNode{
		{
			Name:   "Service Pod",
			Role:   "Source Application (Go)",
			Target: "localhost:4317 (Local Sidecar)",
			Features: []string{"Zero TLS Overhead", "Fast In-Memory Push"},
		},
		{
			Name:   "OTel Agent (DaemonSet)",
			Role:   "Node-Level Collector",
			Target: "otel-gateway.monitoring:4317",
			Features: []string{"Local Batching", "Host Metrics Collection", "Memory Limiter"},
		},
		{
			Name:   "OTel Gateway (Cluster HPA)",
			Role:   "Centralized Aggregator",
			Target: "Grafana Tempo / Jaeger S3",
			Features: []string{"Tail-Based Sampling", "PII Data Masking", "Multi-Tenant Routing"},
		},
	}
}

func TestOTelCollectorTopologies(t *testing.T) {
	topology := BuildOTelPipelineTopology()

	if len(topology) != 3 {
		t.Fatalf("Ожидалось 3 уровня топологии: %+v", topology)
	}

	fmt.Println("Архитектура OpenTelemetry Collector (Agent vs Gateway) подтверждена:")
	for idx, n := range topology {
		fmt.Printf("  [%d] %-25s -> %s\n", idx+1, n.Name, n.Target)
		fmt.Printf("      Роль:  %s\n", n.Role)
		fmt.Printf("      Задачи: %v\n", n.Features)
	}
	fmt.Println("  • Двухуровневая топология масштабируется до сотен тысяч подов без единой точки отказа!")
}
```

ℹ️ Двухуровневая архитектура телеметрии: локальный Sidecar/DaemonSet и центральный Gateway

## Под капотом

В режиме DaemonSet коллектор монтирует сокет хоста `/var/run/docker.sock` или сокет containerd, автоматически обогащая спаны атрибутами пода (Pod UID, Namespace, Node Name) через `k8sattributes` процессор.

## Подводные камни

Использовать Sidecar на каждом поде при микросервисной базе из 10 000 подов: суммарное потребление RAM сайдкарами съест терабайты памяти кластера. В таких масштабах используют DaemonSet (один коллектор на ноду).

## На собеседовании

**Вопрос с собеседования:** «В чем ключевая разница в масштабировании OTel Collector в режиме Agent и в режиме Gateway?»
**Ответ:** Агенты (DaemonSet) масштабируются автоматически вместе с ростом числа физических нод кластера. Шлюзы (Gateway) масштабируются горизонтально через Kubernetes HPA на основе потребления CPU и глубины очередей процессоров экспорта (`otelcol_exporter_queue_size`).
