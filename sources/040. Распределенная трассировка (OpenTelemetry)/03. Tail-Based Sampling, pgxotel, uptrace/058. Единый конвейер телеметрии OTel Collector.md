# Единый конвейер телеметрии OTel Collector: архитектура receivers -> processors -> exporters

## Условие

Настройте pipeline: `receivers → processors → exporters` для traces, metrics и logs (единый пайплайн для всех сигналов).

## Теория

Унифицированная архитектура сигналов (Traces, Metrics, Logs):
- Конфигурационный файл `otel-collector-config.yaml` объединяет все три столпа наблюдаемости (Three Pillars of Observability):
  ```yaml
  service:
    pipelines:
      traces:
        receivers: [otlp]
        processors: [memory_limiter, batch]
        exporters: [otlp/tempo]
      metrics:
        receivers: [otlp, prometheus]
        processors: [memory_limiter, batch]
        exporters: [prometheusremotewrite]
      logs:
        receivers: [otlp, filelog]
        processors: [memory_limiter, batch]
        exporters: [loki]
  ```
- Единый агент заменяет три разнородных демона (Fluentbit, Promtail, Jaeger-Agent).

## Решение по шагам

1. Создайте модель конвейера `Pipeline` из трех звеньев.
2. Продемонстрируйте прохождение данных через Receiver, Processor и Exporter.
3. Проверьте согласованность обработки всех трех типов сигналов.
4. Верифицируйте корректность архитектуры.

## Код решения

**`unified_telemetry_pipeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SignalPipeline struct {
	Signal     string
	Receivers  []string
	Processors []string
	Exporters  []string
}

func VerifyCollectorPipelines() []SignalPipeline {
	return []SignalPipeline{
		{
			Signal:     "Traces",
			Receivers:  []string{"otlp (grpc:4317, http:4318)"},
			Processors: []string{"memory_limiter", "batch"},
			Exporters:  []string{"tempo / jaeger"},
		},
		{
			Signal:     "Metrics",
			Receivers:  []string{"otlp", "prometheus"},
			Processors: []string{"memory_limiter", "batch"},
			Exporters:  []string{"prometheusremotewrite (Mimir/Victoria)"},
		},
		{
			Signal:     "Logs",
			Receivers:  []string{"otlp", "filelog"},
			Processors: []string{"memory_limiter", "batch"},
			Exporters:  []string{"loki / elasticsearch"},
		},
	}
}

func TestUnifiedTelemetryPipeline(t *testing.T) {
	pipes := VerifyCollectorPipelines()

	if len(pipes) != 3 {
		t.Fatalf("Ожидалось 3 конвейера сигналов, получено: %d", len(pipes))
	}

	fmt.Println("Единый пайплайн телеметрии OpenTelemetry Collector успешно проверен:")
	for _, p := range pipes {
		fmt.Printf("  • Пайплайн [%-7s]: Receivers(%v) -> Processors(%v) -> Exporters(%v)\n",
			p.Signal, p.Receivers, p.Processors, p.Exporters)
	}
	fmt.Println("  • Все сигналы обрабатываются через единый унифицированный процессинг!")
}
```

ℹ️ Структурная валидация унифицированного пайплайна OTel Collector для трейсов, метрик и логов

## Под капотом

Внутри рантайма OTel Collector данные передаются между компонентами через внутренний бинарный формат `pdata` (Pluggable Data Representation), исключающий повторные JSON-маршалинги на промежуточных этапах конвейера.

## Подводные камни

Забыть объявить пайплайн внутри секции `service.pipelines`: даже если ресивер и экспортер описаны в yaml, они не запустятся, пока явно не связаны в блоке `service.pipelines`.

## На собеседовании

**Вопрос с собеседования:** «В каком строгом порядке должны располагаться процессоры в pipelines OpenTelemetry Collector?»
**Ответ:** 
1. Первым **ВСЕГДА** идет `memory_limiter` (для защиты от OOM).
2. Далее процессоры модификации данных (`k8sattributes`, `filter`, `transform`).
3. Далее `tail_sampling` (для трейсов).
4. Последним перед экспортом идет `batch` (для пакетирования и сжатия).
