# Обработка конкурентных дублей: ответ HTTP 409 Conflict при статусе STARTED

## Условие

2. **Обработка конкурентных дублей (Race Condition)**: Что если второй запрос пришел, пока первый еще выполняется (статус `STARTED`)? Твой сервер не должен выполнять бизнес-логику во второй раз, но и ответа у него еще нет. В этом случае возвращай клиенту HTTP 409 Conflict с сообщением "Запрос уже обрабатывается, повторите позже".

### Исходная формулировка

**Обработка конкурентных дублей (Race Condition)**: Что если второй запрос пришел, пока первый еще выполняется (статус `STARTED`)? Твой сервер не должен выполнять бизнес-логику во второй раз, но и ответа у него еще нет. В этом случае возвращай клиенту HTTP 409 Conflict с сообщением "Запрос уже обрабатывается, повторите позже".

## Теория

В условиях сетевых задержек мобильный клиент или браузер может отправить повторный запрос до того, как сервер закончил обработку первого запроса (например, когда обращение к банку занимает 3 секунды).

В этот момент в хранилище идемпотентности находится статус `STARTED`:
1. Запрос 1: получил замок `SETNX` -> статус `STARTED` -> ушел в медленный вызов платежного шлюза.
2. Запрос 2: пришел с тем же ключом -> увидел статус `STARTED` -> **бизнес-логику выполнять нельзя** (иначе произойдет двойное списание), но и кэшированного ответа еще нет.
3. Корректный ответ по стандарту REST: **HTTP 409 Conflict** (или HTTP 425 Too Early) с телом `{"error": "Request is currently being processed. Please retry later."}` и заголовком `Retry-After: 2`.

## Решение по шагам

1. Реализуйте метод проверки статуса ключа `CheckStatus(ctx, key)`.
2. Если статус равен `STARTED`, формируйте ответ HTTP 409 Conflict.
3. Добавьте заголовок `Retry-After: 2` для указания клиенту времени ожидания.
4. Продемонстрируйте возврат 409 при параллельном вызове.

## Код решения

**`concurrent_race_409.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type RequestStatus string

const (
	StatusStarted   RequestStatus = "STARTED"
	StatusCompleted RequestStatus = "COMPLETED"
)

type IdempotencyStore struct {
	mu   sync.Mutex
	data map[string]RequestStatus
}

func (s *IdempotencyStore) TryStart(key string) (isNew bool, currentStatus RequestStatus) {
	s.mu.Lock()
	defer s.mu.Unlock()

	status, exists := s.data[key]
	if !exists {
		s.data[key] = StatusStarted
		return true, StatusStarted
	}
	return false, status
}

func (s *IdempotencyStore) Complete(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.data[key] = StatusCompleted
}

func HandlePayment(w http.ResponseWriter, r *http.Request, store *IdempotencyStore) {
	idempKey := r.Header.Get("Idempotency-Key")
	if idempKey == "" {
		http.Error(w, "Missing Idempotency-Key", http.StatusBadRequest)
		return
	}

	isNew, status := store.TryStart(idempKey)
	if !isNew {
		if status == StatusStarted {
			// Конкурентный дубликат: первичный запрос еще выполняется
			w.Header().Set("Retry-After", "2")
			w.WriteHeader(http.StatusConflict) // 409 Conflict
			_, _ = w.Write([]byte(`{"error": "Request is currently being processed, please retry later"}`))
			return
		}
		// Если статус уже COMPLETED, отдается сохраненный ответ
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status": "ALREADY_COMPLETED"}`))
		return
	}

	// Имитация долгой бизнес-логики (например, обращение к эквайрингу)
	time.Sleep(50 * time.Millisecond)
	store.Complete(idempKey)

	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"status": "SUCCESS", "payment_id": "pay-777"}`))
}

func main() {
	store := &IdempotencyStore{data: make(map[string]RequestStatus)}
	key := "uuid-concurrent-100"

	// Запрос 1: начинает выполнение
	req1 := httptest.NewRequest(http.MethodPost, "/payments", nil)
	req1.Header.Set("Idempotency-Key", key)
	rr1 := httptest.NewRecorder()

	// Запрос 2: приходит пока Запрос 1 еще работает
	req2 := httptest.NewRequest(http.MethodPost, "/payments", nil)
	req2.Header.Set("Idempotency-Key", key)
	rr2 := httptest.NewRecorder()

	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		HandlePayment(rr1, req1, store)
	}()

	// Даем первому запросу захватить лок
	time.Sleep(10 * time.Millisecond)

	go func() {
		defer wg.Done()
		HandlePayment(rr2, req2, store)
	}()

	wg.Wait()

	fmt.Printf("Request 1 Response Code: %d, Body: %s\n", rr1.Code, rr1.Body.String())
	fmt.Printf("Request 2 Response Code: %d, Body: %s (Retry-After: %s)\n",
		rr2.Code, rr2.Body.String(), rr2.Header().Get("Retry-After"))
}
```

ℹ️ При параллельном обращении второй запрос получает 409 Conflict с заголовком Retry-After

## Под капотом

HTTP статус 409 Conflict по спецификации RFC 9110 указывает, что запрос не может быть обработан из-за конфликта с текущим состоянием целевого ресурса. Клиент обязан подождать время из `Retry-After` и повторить вызов, когда первый запрос перейдет в статус `COMPLETED`.

## Подводные камни

1. Возврат ошибки 500 при статусе STARTED: клиент решит, что на сервере упала база, и начнет агрессивный шторм повторов (Retry Storm).
2. Ожидание завершения первого запроса во втором через бесконечный цикл `time.Sleep`: это заблокирует все горутины HTTP-сервера и исчерпает пул потоков.

## На собеседовании

Вопрос: Что лучше возвращать на конкурентный дубликат: HTTP 409 Conflict или подвешивать запрос в ожидании ответа первого?
Ответ: В распределенных веб-системах предпочтительнее возвращать HTTP 409 Conflict с заголовком `Retry-After`. Подвешивание входящих HTTP-соединений приводит к исчерпанию файловых дескрипторов и памяти сервера (Connection Pool Starvation). Пусть клиент сам повторит запрос через 1–2 секунды.
