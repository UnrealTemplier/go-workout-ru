# Redis Idempotency Store: атомарная инициализация ключа через SETNX со статусом STARTED

## Условие

1. **Redis Idempotency Store**: Напиши структуру `IdempotencyManager`, использующую Redis. При получении запроса делай `SETNX` (Set if Not Exists) с ключом `idemp:{user_id}:{idempotency_key}` и значением `STARTED`. Если Redis вернул `false` — запрос с таким ключом уже существует!

### Исходная формулировка

**Redis Idempotency Store**: Напиши структуру `IdempotencyManager`, использующую Redis. При получении запроса делай `SETNX` (Set if Not Exists) с ключом `idemp:{user_id}:{idempotency_key}` и значением `STARTED`. Если Redis вернул `false` — запрос с таким ключом уже существует!

## Теория

Идемпотентность в REST API — это свойство операции производить тот же результат при многократном повторении, что и при однократном вызове (\(f(f(x)) = f(x)\)). Если клиент отправляет платеж на 1000 рублей, но из-за разрыва сети не получает подтверждения и делает повтор (HTTP retry), списание должно произойти строго один раз.

Первым рубежом защиты является распределенный замок идемпотентности в памяти Redis:
1. Клиент генерирует уникальный заголовок `Idempotency-Key: <uuid>`.
2. Сервер формирует ключ `idemp:{user_id}:{idempotency_key}`.
3. Сервер выполняет команду `SETNX key STARTED`.
4. Если команда вернула `1` (true) — ключ свободен, текущий запрос стал первичным владельцем блокировки.
5. Если команда вернула `0` (false) — ключ уже занят предыдущим или параллельным запросом.

## Решение по шагам

1. Спроектируйте структуру `IdempotencyManager` с клиентом Redis.
2. Реализуйте метод `Lock(ctx, userID, idempotencyKey)` с вызовом `SetNX`.
3. При успешной установке возвращайте статус первичного запроса.
4. При получении `false` сигнализируйте о повторной доставке.
5. Продемонстрируйте блокировку параллельного дубликата.

## Код решения

**`redis_idempotency_store.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type MockRedis struct {
	mu   sync.Mutex
	data map[string]string
}

func NewMockRedis() *MockRedis {
	return &MockRedis{data: make(map[string]string)}
}

func (r *MockRedis) SetNX(ctx context.Context, key string, val string, ttl time.Duration) (bool, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	if _, exists := r.data[key]; exists {
		return false, nil // Ключ уже существует
	}
	r.data[key] = val
	return true, nil
}

type IdempotencyManager struct {
	redis *MockRedis
	ttl   time.Duration
}

func NewIdempotencyManager(redis *MockRedis, ttl time.Duration) *IdempotencyManager {
	return &IdempotencyManager{
		redis: redis,
		ttl:   ttl,
	}
}

func (m *IdempotencyManager) AcquireLock(ctx context.Context, userID, idempKey string) (bool, error) {
	redisKey := fmt.Sprintf("idemp:%s:%s", userID, idempKey)
	return m.redis.SetNX(ctx, redisKey, "STARTED", m.ttl)
}

func main() {
	redis := NewMockRedis()
	mgr := NewIdempotencyManager(redis, 24*time.Hour)
	ctx := context.Background()

	userID := "user-42"
	idempKey := "req-uuid-999-aaa"

	fmt.Println("=== 1. First HTTP Request arrival ===")
	acquired, err := mgr.AcquireLock(ctx, userID, idempKey)
	if err != nil {
		panic(err)
	}
	if acquired {
		fmt.Printf("[Idempotency Manager] Lock ACQUIRED for %s! Set status=STARTED. Executing handler...\n", idempKey)
	}

	fmt.Println("\n=== 2. Duplicate HTTP Request arrival (Client retry or race) ===")
	acquired, err = mgr.AcquireLock(ctx, userID, idempKey)
	if err != nil {
		panic(err)
	}
	if !acquired {
		fmt.Printf("[Idempotency Manager] Lock REJECTED (false) for %s! Key already exists in Redis.\n", idempKey)
	}
}
```

ℹ️ Атомарный SETNX в Redis гарантирует, что только один поток станет владельцем ключа

**`output.txt`**

```bash
=== 1. First HTTP Request arrival ===
[Idempotency Manager] Lock ACQUIRED for req-uuid-999-aaa! Set status=STARTED. Executing handler...

=== 2. Duplicate HTTP Request arrival (Client retry or race) ===
[Idempotency Manager] Lock REJECTED (false) for req-uuid-999-aaa! Key already exists in Redis.
```

ℹ️ Первый запрос получил эксклюзивный статус STARTED, повторный мгновенно отклонен

## Под капотом

Внутри Redis операция `SET key val NX EX ttl` выполняется в однопоточном цикле ядра без блокировок. Ключ привязывается к пользователю `idemp:{user_id}:{idempotency_key}`, чтобы исключить атаку угадывания чужих ключей (IDOR): ключ пользователя \(A\) никак не пересекается с пользователем \(B\).

## Подводные камни

1. Отсутствие `user_id` в префиксе ключа: злоумышленник может подобрать чужой UUID ключа и прочитать чужой ответ.
2. Вызов `GET` перед `SET`: классическое состояние гонки (Race Condition). Только атомарный `SETNX` безопасен.

## На собеседовании

Вопрос: Почему в качестве ключа Redis используется составной ключ `idemp:{user_id}:{idempotency_key}`, а не просто `idempotency_key`?
Ответ: Изоляция арендаторов (Tenant Isolation). Если два разных пользователя случайно или злонамеренно сгенерируют одинаковый ключ (например, `order-1`), без `user_id` второй клиент либо получит ошибку 409, либо увидит чужие персональные данные и реквизиты платежа из кэшированного ответа.
