# Проверка наличия ключа: быстрый Look-Up в хранилище с обработкой состояния выполнения

## Условие

14. **Проверяет, есть ли key в таблице**: Проверяет, есть ли key в таблице.

### Исходная формулировка

Проверяет, есть ли key в таблице

## Теория

Проверка наличия ключа в хранилище (Cache Look-up) — второй шаг конвейера. При выборке строки из БД или ключа из Redis возвращаются метаданные:
1. Статус записи: `STARTED` (в процессе) или `COMPLETED` (завершен).
2. Время создания: `created_at` (для проверки таймаута).
3. Хэш запроса: `request_hash` (для проверки мутации payload).

Если ключ отсутствует (`NOT_FOUND`), конвейер начинает первичное выполнение. Если ключ найден, сервер переходит к валидации отпечатка и отдаче сохраненного ответа.

## Решение по шагам

1. Реализуйте метод хранилища `LookupKey(ctx, key) (*KeyInfo, error)`.
2. Обработайте сценарий `KeyNotFound`.
3. Обработайте сценарий `KeyFound` с возвратом структуры метаданных.
4. Продемонстрируйте ветвление логики в зависимости от результата поиска.

## Код решения

**`lookup_key.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type KeyMetadata struct {
	Key       string
	Status    string
	CreatedAt time.Time
	Payload   string
}

type IdempotencyLookupStore struct {
	mu    sync.Mutex
	table map[string]KeyMetadata
}

func (s *IdempotencyLookupStore) Lookup(key string) (*KeyMetadata, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()

	meta, found := s.table[key]
	if !found {
		return nil, false
	}
	return &meta, true
}

func HandleLookupStep(key string, store *IdempotencyLookupStore) {
	fmt.Printf("[Pipeline] Checking existence of Idempotency Key '%s'...\n", key)

	meta, found := store.Lookup(key)
	if !found {
		fmt.Printf(" -> Result: NOT FOUND. Proceeding to create new transaction lock.\n\n")
		return
	}

	fmt.Printf(" -> Result: FOUND! Status='%s', CreatedAt=%v. Branching to replay/conflict handler.\n\n",
		meta.Status, meta.CreatedAt.Format("15:04:05"))
}

func main() {
	store := &IdempotencyLookupStore{
		table: map[string]KeyMetadata{
			"uuid-existing-888": {
				Key:       "uuid-existing-888",
				Status:    "COMPLETED",
				CreatedAt: time.Now().Add(-10 * time.Minute),
				Payload:   `{"status": "OK"}`,
			},
		},
	}

	_ = context.Background()

	// 1. Поиск нового ключа
	HandleLookupStep("uuid-new-111", store)

	// 2. Поиск существующего ключа
	HandleLookupStep("uuid-existing-888", store)
}
```

ℹ️ Этап Look-Up определяет дальнейшую маршрутизацию запроса: исполнение или повтор

**`output.txt`**

```bash

 -> Result: NOT FOUND. Proceeding to create new transaction lock.

[Pipeline] Checking existence of Idempotency Key 'uuid-existing-888'...
 -> Result: FOUND! Status='COMPLETED', CreatedAt=10:45:00. Branching to replay/conflict handler.
```

## Под капотом

В PostgreSQL для ускорения этапа Look-Up индекс по `idempotency_key` должен быть `UNIQUE INDEX` B-Tree. Поиск по первичному ключу (`SELECT status, response FROM idempotency_keys WHERE key = $1`) выполняется через `Index Scan` за доли миллисекунды.

## Подводные камни

1. Выполнение тяжелых `SELECT *` без необходимости: если ответ содержит 100 КБ JSON, сначала достаточно запросить только `status` и `hash`, а полное тело дочитывать только при совпадении.
2. Игнорирование таймаута контекста: при зависании Redis запрос в Look-Up может заблокировать HTTP поток.

## На собеседовании

Вопрос: Что делать, если при Look-Up Redis вернул ошибку таймаута сети?
Ответ: Это ситуация Fail-Open vs Fail-Closed. В финансовых сервисах действует политика **Fail-Closed**: при недоступности кэша идемпотентности запрос отклоняется с кодом HTTP 503 Service Unavailable, так как выполнение вслепую может привести к двойному списанию денег.
