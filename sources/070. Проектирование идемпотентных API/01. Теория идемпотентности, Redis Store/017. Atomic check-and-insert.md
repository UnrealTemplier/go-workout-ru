# Atomic check-and-insert: конкурентная проверка через INSERT ON CONFLICT DO NOTHING

## Условие

17. **Atomic check-and-insert**: Используйте `INSERT ... ON CONFLICT DO NOTHING` для конкурентной проверки:
```go
result := tx.Exec("INSERT INTO idempotency_keys (key) VALUES ($1) ON CONFLICT DO NOTHING", key)
if result.RowsAffected() == 0 {
    // Key already exists, return cached response
    return cachedResponse
}
// Execute request
```

### Исходная формулировка

**Atomic check-and-insert**: Используйте `INSERT ... ON CONFLICT DO NOTHING` для конкурентной проверки:
```go
result := tx.Exec("INSERT INTO idempotency_keys (key) VALUES ($1) ON CONFLICT DO NOTHING", key)
if result.RowsAffected() == 0 {
    // Key already exists, return cached response
    return cachedResponse
}
// Execute request
```

## Теория

Классический антипаттерн `Check-Then-Act`:
```go
// ОШИБКА: состояние гонки!
exists := db.QueryRow('SELECT 1 FROM keys WHERE key = $1', key)
if !exists {
    db.Exec('INSERT INTO keys ...')
}
```
Если два запроса с одинаковым ключом придут одновременно на два разных пода, оба выполнят `SELECT`, оба увидят, что ключа нет, и оба выполнят списание денег.

**Эталонное решение:** атомарный SQL запрос **Atomic Check-and-Insert**:
`INSERT INTO idempotency_keys (key, created_at) VALUES ($1, NOW()) ON CONFLICT (key) DO NOTHING;`
Драйвер базы данных возвращает объект `sql.Result`. Метод `result.RowsAffected()`:
- Возвращает `1` — строка успешно вставлена (первичный запрос, выполняем бизнес-код).
- Возвращает `0` — сработал конфликт уникальности (дубликат, отдаем кэшированный ответ).

## Решение по шагам

1. Смоделируйте выполнение `tx.Exec` с возвратом `sql.Result`.
2. Проверьте `RowsAffected()`: при 0 выполните чтение кэшированного ответа.
3. При `RowsAffected() == 1` выполните мутирующую бизнес-логику.
4. Продемонстрируйте параллельную конкурентную гонку двух запросов.

## Код решения

**`atomic_check_insert.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type MockResult struct {
	affected int64
}

func (r MockResult) RowsAffected() (int64, error) {
	return r.affected, nil
}

type SQLDatabaseMock struct {
	mu     sync.Mutex
	keys   map[string]string // key -> cachedResponse
	orders int
}

func (db *SQLDatabaseMock) ExecInsertOnConflict(key string) MockResult {
	db.mu.Lock()
	defer db.mu.Unlock()

	if _, exists := db.keys[key]; exists {
		return MockResult{affected: 0} // ON CONFLICT DO NOTHING
	}

	db.keys[key] = "" // Резервируем ключ
	return MockResult{affected: 1} // Успешная вставка
}

func (db *SQLDatabaseMock) UpdateCachedResponse(key, response string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.keys[key] = response
	db.orders++
}

func (db *SQLDatabaseMock) GetCached(key string) string {
	db.mu.Lock()
	defer db.mu.Unlock()
	return db.keys[key]
}

func HandleOrderRequest(db *SQLDatabaseMock, key string) string {
	// Атомарная проверка и вставка за один запрос к БД
	res := db.ExecInsertOnConflict(key)
	affected, _ := res.RowsAffected()

	if affected == 0 {
		// Ключ уже существует -> возвращаем кэшированный ответ
		cached := db.GetCached(key)
		fmt.Printf(" -> [Atomic Dedup] RowsAffected=0: Key '%s' already exists! Returning cached response.\n", key)
		return cached
	}

	// Первый вызов -> выполняем создание заказа
	fmt.Printf(" -> [Business Execution] RowsAffected=1: First time key '%s'! Creating Order in DB...\n", key)
	response := fmt.Sprintf(`{"status": "SUCCESS", "order_id": "ORD-%s"}`, key)
	db.UpdateCachedResponse(key, response)
	return response
}

func main() {
	db := &SQLDatabaseMock{keys: make(map[string]string)}
	key := "uuid-idemp-atom-777"
	_ = context.Background()

	var wg sync.WaitGroup
	results := make([]string, 2)

	fmt.Println("=== Racing 2 Concurrent Requests with the SAME Key ===")
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func(idx int) {
			defer wg.Done()
			results[idx] = HandleOrderRequest(db, key)
		}(i)
	}
	wg.Wait()

	fmt.Println("\n=== Final Verification ===")
	fmt.Printf("Total Orders created in DB: %d (Expected: 1)\n", db.orders)
	fmt.Printf("Worker 1 got: %s\n", results[0])
	fmt.Printf("Worker 2 got: %s\n", results[1])
}
```

ℹ️ Паттерн Atomic Check-and-Insert гарантирует исключение гонок при проверке ключа

## Под капотом

В реляционных СУБД с изоляцией Read Committed или Repeatable Read, конструкция `ON CONFLICT DO NOTHING` выполняет атомарную фиксацию на уровне уникального B-Tree индекса. Это исключает необходимость распределенных локов типа Redlock или ZooKeeper.

## Подводные камни

1. Использование MySQL 5.7 без проверки `RowsAffected`: в MySQL `INSERT ... ON DUPLICATE KEY UPDATE` возвращает 2 при обновлении строки, что требует адаптации проверки.
2. Ожидание записи в блоке `affected == 0`: если первый запрос еще не сохранил ответ, чтение вернет пустую строку (нужно обрабатывать статус STARTED).

## На собеседовании

Вопрос: Почему `INSERT ... ON CONFLICT DO NOTHING` лучше, чем транзакционный `SELECT FOR UPDATE`?
Ответ: При `SELECT FOR UPDATE` строки еще физически не существует в базе, поэтому заблокировать ее нельзя (придется блокировать весь диапазон через Gap Lock или предикатную блокировку таблицы, что уничтожает производительность). `INSERT ON CONFLICT` атомарно пытается занять слот на уровне индекса без предикатных дедлоков.
