# Возврат сохраненного ответа: гидратация заголовков, статус-кода и тела ответа

## Условие

15. **Если есть — возвращает cached response**: Если есть — возвращает cached response.

### Исходная формулировка

Если есть — возвращает cached response

## Теория

При обнаружении завершенного ключа (`status == COMPLETED`) сервер выполняет процедуру **гидратации ответа (Response Replay)**:

1. **Восстановление заголовков:** сервер переносит сохраненные заголовки (`Content-Type`, `X-Custom-Header`).
2. **Добавление трассировочных заголовков:**
   - `X-Cache-Lookup: HIT`
   - `Idempotent-Replayed: true` (стандарт IETF)
3. **Установка статус-кода:** `w.WriteHeader(cached.Code)` (критично вызвать до записи тела!).
4. **Передача тела ответа:** `w.Write(cached.Body)`.
Бизнес-логика при этом не вызывается, а клиент получает точную копию оригинального ответа.

## Решение по шагам

1. Реализуйте функцию `WriteCachedResponse(w http.ResponseWriter, resp CachedResponse)`.
2. Скопируйте заголовки из сохраненной структуры в `w.Header()`.
3. Добавьте заголовок `Idempotent-Replayed: true`.
4. Вызовите `w.WriteHeader(resp.StatusCode)`.
5. Запишите тело и проверьте результат через `httptest.ResponseRecorder`.

## Код решения

**`write_cached_response.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

type StoredResponse struct {
	StatusCode int
	Headers    map[string]string
	Body       []byte
}

func ReplayResponse(w http.ResponseWriter, cached StoredResponse) {
	// 1. Восстанавливаем оригинальные заголовки
	for k, v := range cached.Headers {
		w.Header().Set(k, v)
	}

	// 2. Добавляем сервисный заголовок повторного воспроизведения
	w.Header().Set("Idempotent-Replayed", "true")

	// 3. Отправляем сохраненный HTTP статус
	w.WriteHeader(cached.StatusCode)

	// 4. Записываем тело ответа
	_, _ = w.Write(cached.Body)
}

func main() {
	cached := StoredResponse{
		StatusCode: http.StatusCreated,
		Headers: map[string]string{
			"Content-Type": "application/json; charset=utf-8",
			"Location":     "/orders/ord-9988",
		},
		Body: []byte(`{"order_id": "ord-9988", "status": "CONFIRMED", "paid": true}`),
	}

	rr := httptest.NewRecorder()
	ReplayResponse(rr, cached)

	fmt.Println("=== Replayed HTTP Response Verification ===")
	fmt.Printf("HTTP Status Code:    %d %s\n", rr.Code, http.StatusText(rr.Code))
	fmt.Printf("Content-Type:        %s\n", rr.Header().Get("Content-Type"))
	fmt.Printf("Location Header:     %s\n", rr.Header().Get("Location"))
	fmt.Printf("Idempotent-Replayed: %s\n", rr.Header().Get("Idempotent-Replayed"))
	fmt.Printf("Response Body:       %s\n", rr.Body.String())
}
```

ℹ️ Восстановление статус-кода, доменных заголовков и служебного маркера Idempotent-Replayed

**`output.txt`**

```bash
=== Replayed HTTP Response Verification ===
HTTP Status Code:    201 Created
Content-Type:        application/json; charset=utf-8
Location Header:     /orders/ord-9988
Idempotent-Replayed: true
Response Body:       {"order_id": "ord-9988", "status": "CONFIRMED", "paid": true}
```

ℹ️ Клиент получил сохраненный статус 201 и заголовки Location и Content-Type

## Под капотом

В Go порядок вызовов в `http.ResponseWriter` имеет строгое значение: любая модификация `w.Header()` должна производиться **до** вызова `w.WriteHeader()`. Первый же вызов `w.Write()` неявно вызывает `WriteHeader(200)`, если статус не был задан явно.

## Подводные камни

1. Вызов `w.WriteHeader()` после `w.Write()`: код статуса будет проигнорирован Go рантаймом, и клиенту уйдет 200 OK вместо 201 Created.
2. Перезапись уникальных заголовков прокси (например, `CF-Ray` или `X-Request-ID`): кэшировать нужно только доменные заголовки ответа бэкенда.

## На собеседовании

Вопрос: Почему важно возвращать заголовок `Idempotent-Replayed: true`?
Ответ: Этот заголовок позволяет клиентским библиотекам (SDK) и аналитике понимать, был ли запрос обработан сервером в данный момент или был отдан из кэша идемпотентности. Это критично для отладки сетевых сбоев и расследования инцидентов.
