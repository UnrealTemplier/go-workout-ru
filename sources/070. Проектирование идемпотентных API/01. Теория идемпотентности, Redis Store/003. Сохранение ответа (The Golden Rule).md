# Сохранение ответа (The Golden Rule): кэширование HTTP-статуса и тела ответа в Redis

## Условие

3. **Сохранение ответа (The Golden Rule)**: Истинная идемпотентность означает, что на дублирующийся запрос клиент должен получить **ровно тот же ответ**, что и в первый раз. В конце успешного `POST /payments` сохрани в Redis HTTP-статус (200) и JSON-тело ответа. При повторном запросе с тем же ключом доставай ответ из Redis и отдавай клиенту без похода в БД.

### Исходная формулировка

**Сохранение ответа (The Golden Rule)**: Истинная идемпотентность означает, что на дублирующийся запрос клиент должен получить **ровно тот же ответ**, что и в первый раз. В конце успешного `POST /payments` сохрани в Redis HTTP-статус (200) и JSON-тело ответа. При повторном запросе с тем же ключом доставай ответ из Redis и отдавай клиенту без похода в БД.

## Теория

Золотое правило идемпотентности: повторный запрос с тем же `Idempotency-Key` должен возвращать **байт-в-байт идентичный ответ** (тот же HTTP статус-код, заголовки и JSON-тело), который получил бы клиент, если бы сеть не оборвалась.

Жизненный цикл ключа идемпотентности:
1. Фаза 1 (Lock): `SETNX idemp:key STARTED`.
2. Фаза 2 (Execute): выполнение бизнес-транзакции в СУБД (создание заказа #777).
3. Фаза 3 (Commit & Cache): обновление ключа в Redis значением:
   ```json
   {
     "status": 201,
     "headers": {"Content-Type": "application/json"},
     "body": "{\"order_id\": \"777\", \"status\": \"PAID\"}"
   }
   ```
4. Повторные запросы: мгновенный возврат сохраненного JSON без единого обращения к бизнес-базе данных.

## Решение по шагам

1. Спроектируйте структуру `CachedResponse` с полями `StatusCode`, `Headers`, `Body`.
2. Реализуйте метод `SaveResponse(key, cachedResp)`.
3. Реализуйте метод `GetCachedResponse(key)`.
4. Продемонстрируйте возврат точной копии ответа при повторном обращении.

## Код решения

**`cached_response_golden_rule.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type CachedResponse struct {
	StatusCode int               `json:"status_code"`
	Headers    map[string]string `json:"headers"`
	Body       string            `json:"body"`
}

type IdempotencyService struct {
	mu    sync.Mutex
	cache map[string]string // key -> JSON(CachedResponse)
}

func NewIdempotencyService() *IdempotencyService {
	return &IdempotencyService{cache: make(map[string]string)}
}

func (s *IdempotencyService) Save(key string, resp CachedResponse) {
	s.mu.Lock()
	defer s.mu.Unlock()
	bytes, _ := json.Marshal(resp)
	s.cache[key] = string(bytes)
}

func (s *IdempotencyService) Get(key string) (*CachedResponse, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	raw, exists := s.cache[key]
	if !exists {
		return nil, false
	}
	var resp CachedResponse
	_ = json.Unmarshal([]byte(raw), &resp)
	return &resp, true
}

func ProcessOrderAPI(w http.ResponseWriter, r *http.Request, idempSvc *IdempotencyService, dbHits *int) {
	idempKey := r.Header.Get("Idempotency-Key")

	// 1. Проверяем наличие кэшированного ответа
	if cached, found := idempSvc.Get(idempKey); found {
		fmt.Println(" -> [Cache HIT] Serving cached response directly from Redis! DB NOT TOUCHED.")
		for k, v := range cached.Headers {
			w.Header().Set(k, v)
		}
		w.Header().Set("X-Cache-Lookup", "HIT")
		w.WriteHeader(cached.StatusCode)
		_, _ = w.Write([]byte(cached.Body))
		return
	}

	// 2. Первичный запрос: идем в БД
	*dbHits++
	fmt.Println(" -> [Cache MISS] Executing DB transaction (Insert Order #888)...")

	responseBody := `{"order_id": "ord-888", "status": "APPROVED", "amount": 2500}`
	cachedResp := CachedResponse{
		StatusCode: http.StatusCreated,
		Headers: map[string]string{
			"Content-Type": "application/json",
		},
		Body: responseBody,
	}

	// 3. Сохраняем результат в кэш
	idempSvc.Save(idempKey, cachedResp)

	w.Header().Set("Content-Type", "application/json")
	w.Header().Set("X-Cache-Lookup", "MISS")
	w.WriteHeader(http.StatusCreated)
	_, _ = w.Write([]byte(responseBody))
}

func main() {
	idempSvc := NewIdempotencyService()
	dbHits := 0
	idempKey := "order-uuid-golden-555"

	fmt.Println("=== 1. First HTTP POST request ===")
	req1 := httptest.NewRequest(http.MethodPost, "/orders", nil)
	req1.Header.Set("Idempotency-Key", idempKey)
	w1 := httptest.NewRecorder()
	ProcessOrderAPI(w1, req1, idempSvc, &dbHits)
	fmt.Printf("HTTP Status: %d, Cache: %s, Body: %s\n",
		w1.Code, w1.Header().Get("X-Cache-Lookup"), w1.Body.String())

	fmt.Println("\n=== 2. Duplicate HTTP POST request (Network retry) ===")
	req2 := httptest.NewRequest(http.MethodPost, "/orders", nil)
	req2.Header.Set("Idempotency-Key", idempKey)
	w2 := httptest.NewRecorder()
	ProcessOrderAPI(w2, req2, idempSvc, &dbHits)
	fmt.Printf("HTTP Status: %d, Cache: %s, Body: %s\n",
		w2.Code, w2.Header().Get("X-Cache-Lookup"), w2.Body.String())

	fmt.Printf("\nVerification: Total Database Hits = %d (Expected: 1)\n", dbHits)
}
```

ℹ️ The Golden Rule: на повторный запрос отдается байт-в-байт идентичный кэшированный ответ

## Под капотом

Кэширование ответа позволяет сервису выдерживать 100-кратные спайки повторных запросов (Thundering Herd) при сбоях у клиента без деградации базы данных. Время ответа для повторного запроса падает с 50–200 мс (время SQL-транзакции) до 1–2 мс.

## Подводные камни

1. Кэширование динамических заголовков типа `Date` или `Set-Cookie`: повторный запрос может перезаписать новую сессию клиента старыми куками.
2. Кэширование слишком больших ответов: если эндпоинт отдает мегабайтный PDF, хранить его в Redis нерационально.

## На собеседовании

Вопрос: Должен ли заголовок `Date` или `X-Request-ID` в повторном ответе обновляться или браться из кэша?
Ответ: Заголовок `X-Request-ID` текущего HTTP-запроса должен быть новым (соответствующим новому сетевому обращению), а доменные заголовки и тело ответа — из кэша. Также в ответ принято добавлять специальный маркерный заголовок, например `Idempotent-Replayed: true` (по стандарту Stripe API), чтобы клиент знал, что получил сохраненный результат.
