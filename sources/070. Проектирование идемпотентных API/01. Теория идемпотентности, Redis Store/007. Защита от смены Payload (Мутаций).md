# Защита от смены Payload (Мутаций): хэширование SHA-256 и возврат HTTP 422

## Условие

7. **Защита от смены Payload (Мутаций)**: Клиент послал `POST /payments` с ключом `Key-1` и телом `{"amount": 100}`. А через секунду послал запрос с тем же `Key-1`, но телом `{"amount": 5000}`. Это может быть баг или попытка взлома. На стороне сервера хэшируй (SHA-256) тело первого запроса и сохраняй в Redis. Сравнивай хэш тела повторного запроса. Если они отличаются — возвращай HTTP 422 Unprocessable Entity.

### Исходная формулировка

Если они отличаются — возвращай HTTP 422 Unprocessable Entity.

## Теория

Опасный вектор атаки или баг интеграции: переиспользование одного и того же ключа идемпотентности для совершенно разных бизнес-операций (Idempotency Key Collision / Payload Mismatch).

Пример инцидента:
- Клиент переводит 100 руб другу с ключом `key-abc` -> Успех 200 OK.
- Через 5 минут тот же клиент переводит 50 000 руб за аренду квартиры с тем же багованным ключом `key-abc`.
- Если сервер просто вернет кэшированный ответ, клиент подумает, что перевел 50 000 руб, хотя деньги не списались!

**Защита по стандарту IETF / Stripe API:**
При первом запросе вычисляется `request_hash = SHA256(method + path + body)` и сохраняется в кэше. При повторном запросе хэш вычисляется заново. Если хэши не совпадают — сервер немедленно возвращает **HTTP 422 Unprocessable Entity** с сообщением: `"Idempotency key already used with different payload"`.

## Решение по шагам

1. Реализуйте функцию хэширования `CalculateRequestHash(method, path, body)` через `crypto/sha256`.
2. Сохраняйте хэш в структуру состояния ключа.
3. При повторном запросе сравнивайте хэш входящего запроса с сохраненным.
4. При несовпадении возвращайте HTTP 422.
5. Продемонстрируйте защиту от подмены суммы платежа.

## Код решения

**`payload_hash_protection.go`**

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
)

func HashRequest(method, path string, body []byte) string {
	h := sha256.New()
	h.Write([]byte(method + ":" + path + ":"))
	h.Write(body)
	return hex.EncodeToString(h.Sum(nil))
}

type IdempRecord struct {
	RequestHash  string
	ResponseCode int
	ResponseBody string
}

type SecurityIdempotencyStore struct {
	mu      sync.Mutex
	records map[string]IdempRecord
}

func HandlePaymentSecure(w http.ResponseWriter, r *http.Request, bodyStr string, store *SecurityIdempotencyStore) {
	key := r.Header.Get("Idempotency-Key")
	currentHash := HashRequest(r.Method, r.URL.Path, []byte(bodyStr))

	store.mu.Lock()
	record, exists := store.records[key]
	if exists {
		store.mu.Unlock()
		// Проверка совпадения Payload
		if record.RequestHash != currentHash {
			w.WriteHeader(http.StatusUnprocessableEntity) // 422
			_, _ = w.Write([]byte(`{"error": "Idempotency key was previously used with a different request payload"}`))
			return
		}

		// Payload совпал -> отдаем кэшированный ответ
		w.WriteHeader(record.ResponseCode)
		_, _ = w.Write([]byte(record.ResponseBody))
		return
	}

	// Первичный запрос -> сохраняем хэш
	respBody := `{"status": "SUCCESS", "message": "Payment accepted"}`
	store.records[key] = IdempRecord{
		RequestHash:  currentHash,
		ResponseCode: http.StatusOK,
		ResponseBody: respBody,
	}
	store.mu.Unlock()

	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(respBody))
}

func main() {
	store := &SecurityIdempotencyStore{records: make(map[string]IdempRecord)}
	key := "shared-user-key-001"

	fmt.Println("=== 1. Request 1: Pay 100 Rubles ===")
	body1 := `{"amount": 100, "recipient": "Alice"}`
	req1 := httptest.NewRequest(http.MethodPost, "/api/pay", strings.NewReader(body1))
	req1.Header.Set("Idempotency-Key", key)
	rr1 := httptest.NewRecorder()
	HandlePaymentSecure(rr1, req1, body1, store)
	fmt.Printf("Response 1 Code: %d, Body: %s\n", rr1.Code, rr1.Body.String())

	fmt.Println("\n=== 2. Request 2: RETRY Pay 100 Rubles (Exact same payload) ===")
	rr2 := httptest.NewRecorder()
	HandlePaymentSecure(rr2, req1, body1, store)
	fmt.Printf("Response 2 Code: %d, Body: %s (Idempotent Replay OK)\n", rr2.Code, rr2.Body.String())

	fmt.Println("\n=== 3. Request 3: TAMPERED PAYLOAD! Pay 5000 Rubles with SAME Key ===")
	body3 := `{"amount": 5000, "recipient": "Bob"}`
	req3 := httptest.NewRequest(http.MethodPost, "/api/pay", strings.NewReader(body3))
	req3.Header.Set("Idempotency-Key", key)
	rr3 := httptest.NewRecorder()
	HandlePaymentSecure(rr3, req3, body3, store)
	fmt.Printf("Response 3 Code: %d, Body: %s (ATTACK BLOCKED!)\n", rr3.Code, rr3.Body.String())
}
```

ℹ️ Хэширование тела запроса предотвращает использование старого ключа с измененными параметрами

## Под капотом

Спецификация IETF draft-ietf-httpapi-idempotency-key-header явно требует валидации `Request Payload Fingerprint`. Если сервер замечает расхождение между отпечатком первого запроса и повторного, статус 422 защищает финансовую систему от искажения смысла транзакции.

## Подводные камни

1. Неодинаковый порядок ключей в JSON: `{"a":1,"b":2}` и `{"b":2,"a":1}` дадут разные SHA-256. Перед хэшированием рекомендуется проводить каноническую нормализацию JSON.
2. Вычитывание `r.Body` без восстановления: после `io.ReadAll(r.Body)` тело запроса опустошается, и последующий хэндлер не сможет прочитать JSON. Нужно делать `r.Body = io.NopCloser(bytes.NewReader(buf))`.

## На собеседовании

Вопрос: Почему для валидации мутаций payload используется HTTP 422, а не 400 Bad Request?
Ответ: Код 400 означает синтаксическую невалидность запроса (битый JSON). Код 422 Unprocessable Entity означает, что запрос синтаксически корректен, но семантически недопустим, так как нарушает бизнес-инвариант неизменности параметров ранее зарегистрированного ключа идемпотентности.
