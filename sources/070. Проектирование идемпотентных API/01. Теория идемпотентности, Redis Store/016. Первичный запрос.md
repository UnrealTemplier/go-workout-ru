# Первичный запрос: сквозное выполнение хэндлера и сохранение ответа в таблицу

## Условие

16. **Если нет — выполняет запрос, сохраняет response в таблицу**: Если нет — выполняет запрос, сохраняет response в таблицу.

### Исходная формулировка

Если нет — выполняет запрос, сохраняет response в таблицу

## Теория

Ветка `MISS` (ключ не найден в хранилище) выполняет полный цикл обработки:
1. Захват блокировки (Locking): регистрация ключа со статусом `STARTED`.
2. Исполнение целевого бизнес-хэндлера через обертку Response Recorder.
3. Постобработка ответа:
   - Если статус ответа `2xx` или `4xx` (клиентская ошибка) -> фиксируем ответ в хранилище со статусом `COMPLETED`.
   - Если статус ответа `5xx` (серверный сбой) -> удаляем ключ, освобождая слот для повторных попыток клиента.
4. Завершение HTTP-вызова с передачей данных в клиентский сокет.

## Решение по шагам

1. Реализуйте полный блок первичного выполнения в хэндлере.
2. Используйте `httptest.ResponseRecorder` для захвата байтов.
3. Выполните бизнес-операцию (например, создание бронирования билета).
4. Сохраните успешный результат в структуру хранилища.
5. Проверьте переход ключа в состояние `COMPLETED`.

## Код решения

**`execute_and_store.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type ExecutionRecord struct {
	Key        string
	Status     string
	StatusCode int
	Body       string
}

type IdempotencyStorage struct {
	mu      sync.Mutex
	records map[string]ExecutionRecord
}

func ExecuteAndStore(w http.ResponseWriter, r *http.Request, store *IdempotencyStorage, key string, businessFn http.HandlerFunc) {
	// 1. Фиксируем статус STARTED
	store.mu.Lock()
	store.records[key] = ExecutionRecord{Key: key, Status: "STARTED"}
	store.mu.Unlock()
	fmt.Printf("[Idempotency] Key '%s' locked as STARTED.\n", key)

	// 2. Выполняем бизнес-логику в рекордер
	rec := httptest.NewRecorder()
	businessFn(rec, r)

	// 3. Анализируем статус-код
	store.mu.Lock()
	if rec.Code < 500 {
		// Успех или 4xx ошибка -> сохраняем как COMPLETED
		store.records[key] = ExecutionRecord{
			Key:        key,
			Status:     "COMPLETED",
			StatusCode: rec.Code,
			Body:       rec.Body.String(),
		}
		fmt.Printf("[Idempotency] Request succeeded (Status %d). Saved to storage as COMPLETED.\n", rec.Code)
	} else {
		// Серверный сбой 5xx -> удаляем ключ
		delete(store.records, key)
		fmt.Printf("[Idempotency] Request failed with %d. Lock removed for retry.\n", rec.Code)
	}
	store.mu.Unlock()

	// 4. Отдаем оригинальный ответ клиенту
	for k, v := range rec.Header() {
		w.Header()[k] = v
	}
	w.WriteHeader(rec.Code)
	_, _ = w.Write(rec.Body.Bytes())
}

func main() {
	store := &IdempotencyStorage{records: make(map[string]ExecutionRecord)}
	key := "uuid-ticket-book-101"

	ticketHandler := func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"ticket_id": "TCK-777", "seat": "12A", "price": 4500}`))
	}

	req := httptest.NewRequest(http.MethodPost, "/tickets/book", nil)
	rr := httptest.NewRecorder()

	fmt.Println("=== Executing First Time Request ===")
	ExecuteAndStore(rr, req, store, key, ticketHandler)

	fmt.Printf("\nClient Received: Status %d, Body: %s\n", rr.Code, rr.Body.String())

	// Проверяем состояние в хранилище
	stored := store.records[key]
	fmt.Printf("Storage State: Key=%s, Status=%s, SavedStatusCode=%d\n",
		stored.Key, stored.Status, stored.StatusCode)
}
```

ℹ️ Первичный запрос выполняет бизнес-код и атомарно переводит ключ в статус COMPLETED

## Под капотом

Запись ответа в базу данных выполняется в режиме `UPSERT` (`UPDATE ... WHERE key = $1` или `INSERT ... ON CONFLICT (key) DO UPDATE SET status = 'COMPLETED', response_body = $2`). Это исключает ошибку дублирования ключа при обновлении состояния.

## Подводные камни

1. Забытая передача заголовков: если скопировать только `Body` и `Code`, клиент потеряет `Content-Type: application/json` и получит `text/plain`.
2. Память рекордера: при отдаче файлов гигабайтного размера буферизация всего тела в памяти вызовет OOM.

## На собеседовании

Вопрос: Что делать, если бизнес-операция возвращает потоковый ответ (streaming / chunked transfer)?
Ответ: Идемпотентность не применяется к бесконечным потокам (SSE/WebSockets). Для больших файлов ответ сохраняется в объектное хранилище (S3), а в таблице идемпотентности кэшируется ссылка на S3 URL и метаданные файла.
