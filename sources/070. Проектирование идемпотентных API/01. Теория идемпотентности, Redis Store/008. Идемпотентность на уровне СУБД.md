# Идемпотентность на уровне СУБД: DDL-схема и семантика INSERT ON CONFLICT DO NOTHING

## Условие

### Исходная формулировка

**Идемпотентность на уровне БД (Альтернатива Redis)**: Redis может потерять данные при рестарте. Создай таблицу `idempotency_keys (key, user_id, response_status, response_body, created_at)`. Делай `INSERT ... ON CONFLICT DO NOTHING`. Это медленнее Redis, но дает 100% гарантию на уровне PostgreSQL.

## Теория

Redis работает в оперативной памяти и по умолчанию использует асинхронную репликацию. В случае внезапного отключения питания сервера Redis ключ идемпотентности может быть потерян. Для банковских и финансовых транзакций высшего уровня критичности хранилище идемпотентности размещается непосредственно в реляционной СУБД (PostgreSQL):

```sql
CREATE TABLE idempotency_keys (
    key VARCHAR(128) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    request_hash CHAR(64) NOT NULL,
    response_status INT NULL,
    response_body JSONB NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, key)
);
```
Атомарная проверка выполняется через `INSERT INTO idempotency_keys (...) ON CONFLICT (user_id, key) DO NOTHING`. Если строка вставлена (`RowsAffected == 1`) — запрос первичный. Если `RowsAffected == 0` — запрос повторный, выполняется `SELECT response_body`.

## Решение по шагам

1. Спроектируйте структуру базы данных с первичным ключом `(user_id, key)`.
2. Напишите функцию `TryAcquireDBKey(ctx, userID, key, hash)`.
3. При успехе вставки выполните бизнес-логику и обновите `response_status`.
4. При конфликте ключа верните сохраненный результат из БД.

## Код решения

**`db_idempotency_store.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type DBIdempRow struct {
	Key            string
	UserID         string
	RequestHash    string
	ResponseStatus int
	ResponseBody   string
	CreatedAt      time.Time
}

type PostgresMock struct {
	mu   sync.Mutex
	rows map[string]DBIdempRow // key: userID + ":" + key
}

func NewPostgresMock() *PostgresMock {
	return &PostgresMock{rows: make(map[string]DBIdempRow)}
}

// Эмуляция INSERT INTO idempotency_keys (...) ON CONFLICT DO NOTHING
func (db *PostgresMock) TryInsertKey(userID, key, hash string) bool {
	db.mu.Lock()
	defer db.mu.Unlock()

	compositeKey := userID + ":" + key
	if _, exists := db.rows[compositeKey]; exists {
		return false // ON CONFLICT DO NOTHING -> RowsAffected = 0
	}

	db.rows[compositeKey] = DBIdempRow{
		Key:         key,
		UserID:      userID,
		RequestHash: hash,
		CreatedAt:   time.Now().UTC(),
	}
	return true // Inserted -> RowsAffected = 1
}

func (db *PostgresMock) UpdateResponse(userID, key string, status int, body string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	compositeKey := userID + ":" + key
	row := db.rows[compositeKey]
	row.ResponseStatus = status
	row.ResponseBody = body
	db.rows[compositeKey] = row
}

func (db *PostgresMock) GetRow(userID, key string) (DBIdempRow, bool) {
	db.mu.Lock()
	defer db.mu.Unlock()
	compositeKey := userID + ":" + key
	row, ok := db.rows[compositeKey]
	return row, ok
}

func ProcessBankingTransfer(db *PostgresMock, userID, key, hash string, amount int) (int, string) {
	// Шаг 1: Атомарная вставка в PostgreSQL
	inserted := db.TryInsertKey(userID, key, hash)
	if !inserted {
		// Ключ уже был -> читаем сохраненный ответ
		row, _ := db.GetRow(userID, key)
		fmt.Printf(" -> [Postgres] Key conflict! Returning cached result: %s\n", row.ResponseBody)
		return row.ResponseStatus, row.ResponseBody
	}

	// Шаг 2: Выполнение бизнес-транзакции
	fmt.Printf(" -> [Postgres] Fresh transaction! Debiting %d rubles from account...\n", amount)
	respBody := fmt.Sprintf(`{"tx_status": "COMMITTED", "amount": %d}`, amount)
	statusCode := 200

	// Шаг 3: Сохранение результата в таблице
	db.UpdateResponse(userID, key, statusCode, respBody)
	return statusCode, respBody
}

func main() {
	db := NewPostgresMock()
	_ = context.Background()

	userID := "usr-enterprise-101"
	key := "key-tx-uuid-888"
	hash := "sha256-hash-of-body"

	fmt.Println("=== Transaction 1: First attempt ===")
	status1, body1 := ProcessBankingTransfer(db, userID, key, hash, 15000)
	fmt.Printf("Result 1: Status=%d, Body=%s\n\n", status1, body1)

	fmt.Println("=== Transaction 2: Duplicate delivery (PostgreSQL ON CONFLICT) ===")
	status2, body2 := ProcessBankingTransfer(db, userID, key, hash, 15000)
	fmt.Printf("Result 2: Status=%d, Body=%s\n", status2, body2)
}
```

ℹ️ Хранение ключей в реляционной СУБД дает 100% гарантию ACID и защиту от потери данных

## Под капотом

Операция `INSERT ... ON CONFLICT DO NOTHING` в PostgreSQL опирается на уникальный индекс B-Tree. Даже если два пода приложения попытаются вставить одинаковый ключ в одну и ту же миллисекунду, PostgreSQL заблокирует страницу индекса и пропустит строго одну транзакцию.

## Подводные камни

1. Высокая нагрузка на диск PostgreSQL: в отличие от Redis, вставка в БД порождает запись в WAL лог. Для некритичных систем это может стать узким местом по I/O.
2. Раздувание таблицы: требуется регулярный партиционированный Pruning Daemon для очистки записей старше 30 дней.

## На собеседовании

Вопрос: Можно ли вставить запись в таблицу `idempotency_keys` и обновить баланс в одной транзакции СУБД?
Ответ: Да! В этом заключается главное преимущество СУБД над Redis: `BEGIN; INSERT INTO idempotency_keys ...; UPDATE accounts SET balance = balance - 100; COMMIT;`. Если баланс не удалось списать (недостаточно средств), вся транзакция откатится вместе с ключом идемпотентности, что исключает любые рассинхронизации.
