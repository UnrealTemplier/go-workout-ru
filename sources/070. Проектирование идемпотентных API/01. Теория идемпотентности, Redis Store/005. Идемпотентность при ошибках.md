# Идемпотентность при ошибках: очистка ключа или статус FAILED при сбоях 5xx для ретраев

## Условие

5. **Идемпотентность при ошибках**: Если бизнес-логика упала (HTTP 500, БД недоступна), ключ идемпотентности **нужно удалить** (или пометить как `FAILED`). Клиент *должен* иметь право безопасно повторить (retry) упавший запрос с тем же ключом. Реализуй эту логику в Middleware.

### Исходная формулировка

**Идемпотентность при ошибках**: Если бизнес-логика упала (HTTP 500, БД недоступна), ключ идемпотентности **нужно удалить** (или пометить как `FAILED`). Клиент *должен* иметь право безопасно повторить (retry) упавший запрос с тем же ключом. Реализуй эту логику в Middleware.

## Теория

Критическая ошибка многих наивных реализаций: если запрос упал с ошибкой сервера (HTTP 500 Internal Server Error, Database Connection Refused), сервер кэширует ошибку 500 как результат выполнения. В результате все последующие попытки клиента повторить запрос с тем же ключом получают навсегда заблокированную ошибку 500!

Инженерное правило обработки сбоев:
1. Если хэндлер завершился ошибкой сервера (`statusCode >= 500`) или произошла паника (`panic`):
   - Бизнес-действие **не выполнено**.
   - Ключ в Redis должен быть немедленно **удален** (`DEL key`) либо переведен в статус `FAILED` с коротким TTL (5 сек).
2. Это позволяет клиенту через секунду повторить упавший запрос с тем же `Idempotency-Key` и успешно выполнить операцию, когда БД восстановится.

## Решение по шагам

1. В Middleware добавьте блок анализа статус-кода после вызова `next.ServeHTTP`.
2. Если `statusCode >= 500` — выполните команду `redis.Del(key)`.
3. Обработайте восстановление после паники (`defer recover()`) с удалением ключа.
4. Продемонстрируйте возможность успешного повтора после сбоя 500.

## Код решения

**`error_idempotency_cleanup.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type Store struct {
	mu   sync.Mutex
	data map[string]string
}

func (s *Store) Set(key, val string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.data[key] = val
}

func (s *Store) Delete(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.data, key)
	fmt.Printf(" -> [Middleware Cleanup] Deleted key '%s' from Redis (Allowed retry)\n", key)
}

func (s *Store) Get(key string) (string, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	val, exists := s.data[key]
	return val, exists
}

type statusRecorder struct {
	http.ResponseWriter
	code int
	body *bytes.Buffer
}

func (r *statusRecorder) WriteHeader(code int) {
	r.code = code
	r.ResponseWriter.WriteHeader(code)
}

func (r *statusRecorder) Write(b []byte) (int, error) {
	r.body.Write(b)
	return r.ResponseWriter.Write(b)
}

func ResilientIdempotencyMiddleware(store *Store) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" {
				next.ServeHTTP(w, r)
				return
			}

			if cached, ok := store.Get(key); ok && cached != "STARTED" {
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(cached))
				return
			}

			// Бронируем ключ
			store.Set(key, "STARTED")

			rec := &statusRecorder{ResponseWriter: w, code: 200, body: &bytes.Buffer{}}

			// Защита от паники
			defer func() {
				if err := recover(); err != nil {
					store.Delete(key) // Удаляем ключ при панике
					http.Error(w, "Internal Server Error", http.StatusInternalServerError)
				}
			}()

			next.ServeHTTP(rec, r)

			// Если сервер вернул 5xx, удаляем ключ!
			if rec.code >= 500 {
				store.Delete(key)
			} else {
				// Успех -> сохраняем
				store.Set(key, rec.body.String())
			}
		})
	}
}

func main() {
	store := &Store{data: make(map[string]string)}
	attempts := 0

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		attempts++
		if attempts == 1 {
			fmt.Println(" [Handler] Database connection timeout! Returning 500...")
			w.WriteHeader(http.StatusInternalServerError)
			_, _ = w.Write([]byte(`{"error": "db down"}`))
			return
		}
		fmt.Println(" [Handler] Database restored! Payment processed successfully.")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status": "SUCCESS"}`))
	})

	app := ResilientIdempotencyMiddleware(store)(handler)
	key := "uuid-err-retry-777"

	fmt.Println("=== Attempt 1: Server fails with 500 ===")
	req1 := httptest.NewRequest(http.MethodPost, "/pay", nil)
	req1.Header.Set("Idempotency-Key", key)
	rr1 := httptest.NewRecorder()
	app.ServeHTTP(rr1, req1)
	fmt.Printf("Attempt 1 Status: %d\n", rr1.Code)

	fmt.Println("\n=== Attempt 2: Client retries with the EXACT SAME key ===")
	req2 := httptest.NewRequest(http.MethodPost, "/pay", nil)
	req2.Header.Set("Idempotency-Key", key)
	rr2 := httptest.NewRecorder()
	app.ServeHTTP(rr2, req2)
	fmt.Printf("Attempt 2 Status: %d, Body: %s\n", rr2.Code, rr2.Body.String())
}
```

ℹ️ Удаление ключа при ошибке 500 позволяет клиенту успешно повторить запрос с тем же ключом

## Под капотом

С точки зрения конечного автомата (FSM), переход в состояние ошибки сервера является терминальным только для конкретного сетевого запроса, но не для всей транзакции. Удаление ключа переводит систему в исходное состояние (Init), позволяя клиентскому retry механизму отработать штатно.

## Подводные камни

1. Удаление ключа при ошибках валидации клиента (400 Bad Request): ошибки 4xx детерминированы. Их можно кэшировать, так как при повторении того же запроса валидация снова упадет.
2. Утечка ключа при панике горутины: без `recover()` ключ останется в статусе `STARTED` навсегда.

## На собеседовании

Вопрос: Следует ли кэшировать ошибки 4xx (например, 422 Unprocessable Entity или 404)?
Ответ: Да! Ошибки клиента 4xx идемпотентны и детерминированы: если клиент отправил невалидный JSON, повтор точно такого же запроса вернет ту же ошибку. Кэширование 4xx предотвращает лишнюю нагрузку на сервер. Удалять ключ нужно строго при временных серверных ошибках 5xx.
