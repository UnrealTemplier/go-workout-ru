# Response caching: персистентное сохранение HTTP-статуса и тела ответа в таблицу

## Условие

18. **Response caching**: Сохраняйте response code и body в idempotency table для повторных запросов.

### Исходная формулировка

**Response caching**: Сохраняйте response code и body в idempotency table для повторных запросов.

## Теория

Структура сохранения ответа в таблице идемпотентности должна сохранять не только тело, но и полный контекст выполнения:
1. `response_code INT`: код статуса HTTP (200, 201, 204, 400, 422).
2. `response_headers JSONB`: заголовки (`Content-Type`, `Location`, `ETag`).
3. `response_body TEXT / JSONB`: тело ответа.
4. `locked_until TIMESTAMPTZ`: время освобождения аварийного замка.

Когда хэндлер завершает работу, в рамках той же или отдельной транзакции выполняется:
```sql
UPDATE idempotency_keys
SET response_code = $1,
    response_headers = $2,
    response_body = $3,
    status = 'COMPLETED'
WHERE key = $4 AND user_id = $5;
```
Теперь любой повторный запрос клиента получает полноценный кэшированный ответ.

## Решение по шагам

1. Спроектируйте полную структуру записи `IdempotencyEntity`.
2. Реализуйте метод `SaveResponse(ctx, key, code, headers, body)`.
3. Реализуйте метод `GetResponse(ctx, key)`.
4. Продемонстрируйте сохранение статуса 201 и восстановление тела ответа.

## Код решения

**`response_caching_table.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type IdempotencyEntity struct {
	Key             string            `json:"key"`
	Status          string            `json:"status"` // STARTED, COMPLETED
	ResponseCode    int               `json:"response_code"`
	ResponseHeaders map[string]string `json:"response_headers"`
	ResponseBody    string            `json:"response_body"`
	UpdatedAt       time.Time         `json:"updated_at"`
}

type PersistentIdempotencyTable struct {
	mu   sync.Mutex
	rows map[string]IdempotencyEntity
}

func NewPersistentIdempotencyTable() *PersistentIdempotencyTable {
	return &PersistentIdempotencyTable{rows: make(map[string]IdempotencyEntity)}
}

func (t *PersistentIdempotencyTable) SaveResponse(key string, code int, headers map[string]string, body string) {
	t.mu.Lock()
	defer t.mu.Unlock()

	t.rows[key] = IdempotencyEntity{
		Key:             key,
		Status:          "COMPLETED",
		ResponseCode:    code,
		ResponseHeaders: headers,
		ResponseBody:    body,
		UpdatedAt:       time.Now().UTC(),
	}
	fmt.Printf("[Idempotency Table] Successfully persisted response for Key '%s' (Status: %d)\n", key, code)
}

func (t *PersistentIdempotencyTable) Get(key string) (*IdempotencyEntity, bool) {
	t.mu.Lock()
	defer t.mu.Unlock()
	row, ok := t.rows[key]
	if !ok || row.Status != "COMPLETED" {
		return nil, false
	}
	return &row, true
}

func main() {
	table := NewPersistentIdempotencyTable()
	_ = context.Background()

	key := "req-transfer-uuid-9900"
	headers := map[string]string{
		"Content-Type": "application/json",
		"X-Trace-ID":   "trace-7788-9900",
	}
	body := `{"transfer_id": "tr-555", "amount": 10000, "currency": "RUB", "state": "SUCCESS"}`

	fmt.Println("=== 1. Saving Response into Idempotency Table ===")
	table.SaveResponse(key, 201, headers, body)

	fmt.Println("\n=== 2. Re-fetching Saved Response on Subsequent Request ===")
	entity, found := table.Get(key)
	if !found {
		panic("Not found")
	}

	marshaled, _ := json.MarshalIndent(entity, "", "  ")
	fmt.Printf("Persisted Record State in Database:\n%s\n", string(marshaled))
}
```

ℹ️ Кэширование полного HTTP ответа (код, заголовки, тело) обеспечивает прозрачный replay

## Под капотом

Поле `response_body` в PostgreSQL рекомендуется хранить в виде типа `JSONB` или `TEXT` со сжатием TOAST. Если тело ответа превышает 2 КБ, PostgreSQL автоматически сжимает его алгоритмом pglz или lz4, экономя дисковое пространство.

## Подводные камни

1. Несжатые огромные ответы в памяти: кэширование мегабайтных ответов без лимита приведет к деградации производительности БД.
2. Несохранение заголовка `Content-Type`: браузерный клиент попытается интерпретировать ответ как plain text.

## На собеседовании

Вопрос: Сколько времени следует хранить записи в таблице `idempotency_keys` в базе данных?
Ответ: В соответствии со стандартами финансовых платформ (Stripe, PayPal), срок хранения составляет от 24 до 72 часов. После этого фоновый партиционированный процесс удаляет устаревшие партиции, так как клиенты не повторяют сетевые запросы трехдневной давности.
