# Идемпотентность в бизнес-логике через уникальные ограничения БД

## Условие

64. **[Идемпотентность в бизнес-логике]**: Реализуй идемпотентность без отдельной таблицы. В таблице `payments` создай уникальное поле `idempotency_key`. При `INSERT` лови ошибку `unique constraint violation` и возвращай существующий платеж.

### Исходная формулировка

**[Идемпотентность в бизнес-логике]**: Реализуй идемпотентность без отдельной таблицы. В таблице `payments` создай уникальное поле `idempotency_key`. При `INSERT` лови ошибку `unique constraint violation` и возвращай существующий платеж.

## Теория

Хотя выделенная таблица идемпотентности или Redis являются универсальными решениями, в простых монолитах или сервисах с единственной таблицей сущности можно реализовать идемпотентность **без создания отдельной таблицы**.

### Архитектура через колонку в бизнес-таблице:
1. В основную бизнес-таблицу добавляется колонка с уникальным ограничением:
   ```sql
   ALTER TABLE payments ADD COLUMN idempotency_key VARCHAR(128) NOT NULL;
   CREATE UNIQUE INDEX uq_payments_idempotency_key ON payments (idempotency_key);
   ```
2. При поступлении запроса сервис пытается вставить запись:
   `INSERT INTO payments (id, amount, idempotency_key, status) VALUES ($1, $2, $3, 'COMPLETED');`
3. Если СУБД возвращает ошибку нарушения уникальности:
   - В PostgreSQL: код ошибки `23505` (`unique_violation`).
   - Сервис перехватывает ошибку и выполняет:
     `SELECT id, amount, status FROM payments WHERE idempotency_key = $1;`
   - Возвращает найденный существующий платеж клиенту с кодом `200 OK` (или `201 Created`).

## Решение по шагам

1. Создадим модель `Payment` с полем `IdempotencyKey`.
2. Реализуем репозиторий `PaymentRepository` с эмуляцией уникального индекса БД.
3. Реализуем обработчик: при ошибке дубликата ключа запрашиваем существующую запись.
4. Продемонстрируем сохранение ровно одной строки в базе данных при многократных вызовах.

## Код решения

**`business_idempotency.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

var ErrUniqueConstraintViolation = errors.New("pq: duplicate key value violates unique constraint \"uq_payments_idemp_key\" (SQLSTATE 23505)")

type Payment struct {
	ID             string
	Amount         int
	IdempotencyKey string
	Status         string
}

type PaymentRepository struct {
	mu          sync.Mutex
	payments    map[string]*Payment // ID -> Payment
	keyIndex    map[string]string   // IdempotencyKey -> ID (Unique Index)
	idGenerator int
}

func NewPaymentRepository() *PaymentRepository {
	return &PaymentRepository{
		payments: make(map[string]*Payment),
		keyIndex: make(map[string]string),
	}
}

func (r *PaymentRepository) CreatePayment(ctx context.Context, key string, amount int) (*Payment, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	// Проверка уникального индекса (эмуляция СУБД)
	if existingID, exists := r.keyIndex[key]; exists {
		return nil, ErrUniqueConstraintViolation
	}

	r.idGenerator++
	id := fmt.Sprintf("pay_%04d", r.idGenerator)
	p := &Payment{
		ID:             id,
		Amount:         amount,
		IdempotencyKey: key,
		Status:         "CONFIRMED",
	}

	r.payments[id] = p
	r.keyIndex[key] = id
	return p, nil
}

func (r *PaymentRepository) GetByIdempotencyKey(ctx context.Context, key string) (*Payment, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	if id, exists := r.keyIndex[key]; exists {
		return r.payments[id], nil
	}
	return nil, errors.New("not found")
}

type PaymentBusinessService struct {
	repo *PaymentRepository
}

func (s *PaymentBusinessService) ProcessCharge(ctx context.Context, key string, amount int) (*Payment, bool, error) {
	// 1. Попытка создания платежа
	payment, err := s.repo.CreatePayment(ctx, key, amount)
	if err == nil {
		return payment, false, nil // Успешно создан новый платеж
	}

	// 2. Если поймали ошибку уникального индекса (23505) — достаем существующий!
	if errors.Is(err, ErrUniqueConstraintViolation) {
		existing, getErr := s.repo.GetByIdempotencyKey(ctx, key)
		if getErr != nil {
			return nil, false, getErr
		}
		return existing, true, nil // Возвращаем существующий платеж (Idempotent Replay)
	}

	return nil, false, err
}

func main() {
	repo := NewPaymentRepository()
	service := &PaymentBusinessService{repo: repo}
	ctx := context.Background()

	clientKey := "order-checkout-uuid-888"

	// 1. Первая попытка списания $150
	p1, isReplay1, err1 := service.ProcessCharge(ctx, clientKey, 150)
	if err1 != nil {
		panic(err1)
	}
	fmt.Printf("Попытка 1: ID=%s, Amount=$%d, Replay=%v\n", p1.ID, p1.Amount, isReplay1)

	// 2. Повторная попытка списания $150 с тем же ключом
	p2, isReplay2, err2 := service.ProcessCharge(ctx, clientKey, 150)
	if err2 != nil {
		panic(err2)
	}
	fmt.Printf("Попытка 2: ID=%s, Amount=$%d, Replay=%v (тот же ID!)\n", p2.ID, p2.Amount, isReplay2)

	// 3. Проверяем общее количество записей в базе данных
	fmt.Printf("\nИтого записей в таблице payments: %d (должна быть строго 1!)\n", len(repo.payments))
}
```

ℹ️ Идемпотентность через UNIQUE INDEX в бизнес-таблице с перехватом ошибки 23505

## Под капотом

В PostgreSQL код ошибки нарушения уникального индекса определяется константой:
```go
import "github.com/lib/pq"

if pqErr, ok := err.(*pq.Error); ok && pqErr.Code == "23505" {
    // Unique violation: извлекаем существующую запись
}
```
Также можно использовать конструкцию `INSERT INTO payments ... ON CONFLICT (idempotency_key) DO UPDATE SET updated_at = NOW() RETURNING id, amount, status;`, позволяющую выполнить операцию и вернуть существующий платеж за один сетевой round-trip к базе данных.

## Подводные камни

1. **Невозможность кэшировать HTTP-заголовки:** В отличие от отдельной таблицы идемпотентности, этот подход сохраняет только бизнес-сущность. Если клиенту важны точные заголовки ответа (`X-Trace-ID`, `ETag`), их придется генерировать заново.
2. **Проблема при отмене или ошибке валидации:** Если создание платежа завершилось ошибкой бизнес-валидации, запись в таблицу не попадет, и повторный запрос попытается создаться снова (что в данном случае допустимо).
3. **Разрастание размера бизнес-таблицы:** Добавление индекса `VARCHAR(128)` увеличивает размер страниц индекса в PostgreSQL. Рекомендуется использовать частичный уникальный индекс `WHERE idempotency_key IS NOT NULL`.

## На собеседовании

**Вопрос:** В каких случаях предпочтительнее использовать отдельную таблицу `idempotency_keys`, а в каких — уникальную колонку в бизнес-таблице `payments`?
**Ответ:**
- **Колонка в бизнес-таблице:** Идеальна для простых REST API, где операция сводится к вставке одной сущности (`INSERT INTO payments`). Это исключает лишние JOIN-ы и необходимость поддержки двух таблиц.
- **Отдельная таблица идемпотентности:** Необходима, когда операция затрагивает множество таблиц (например, списание бонусов, бронирование на складе, отправка письма), требует кэширования HTTP-кодов, заголовков и сохранения ответа при ошибках валидации.
