# Сквозной интеграционный тест распределенной идемпотентной системы

### Исходная формулировка

**Сквозной тест идемпотентной распределённой транзакции.**: Объедините паттерны: клиент → API Gateway (проверка idempotency) → Оркестратор саги (с хранением статуса) → Outbox → Брокер → Inbox сервисов. Проверьте, что повторный запрос с тем же ключом не приводит к дублированию заказа.

## Теория

Завершающий шаг построения распределенных систем — **сквозной интеграционный аудит (End-to-End Distributed Audit)**.

В полной архитектуре задействованы все уровни защиты:
1. **L7 Edge / API Gateway:** Проверяет `Idempotency-Key`, кэширует готовый ответ, предотвращает повторный вход в инфраструктуру.
2. **Saga Orchestrator:** Отвечает за координацию шагов транзакции и детерминированную нумерацию задач (`saga_id + step_index`).
3. **Transactional Outbox:** Гарантирует надежную публикацию событий в брокер без потери сообщений (At-Least-Once).
4. **Message Broker (Kafka/RabbitMQ):** Передает события между микросервисами.
5. **Idempotent Inbox Consumers:** Фильтруют дубликаты на стороне downstream-сервисов (дебет склада, биллинг, нотификации).

### Цель сквозного теста:
Смоделировать жесткие сетевые аварии: обрыв связи между клиентом и шлюзом, повторную отправку сообщений брокером и повторный запуск шагов саги, доказав, что **все бизнес-инварианты сохраняются на 100%**.

## Решение по шагам

1. Создадим компоненты всей цепочки: `ApiGateway`, `SagaOrchestrator`, `OutboxRelay`, `WarehouseInboxService`.
2. Настроим передачу детерминированных идентификаторов через всю цепочку.
3. Симулируем 3 последовательных запроса клиента с одинаковым `Idempotency-Key` при искусственных сетевых сбоях.
4. Проверим, что:
   - Клиент получил корректный ответ `201 Created` и два `Replay` ответа.
   - Склад забронировал товар ровно один раз.
   - Баланс пользователя списан ровно один раз.

## Код решения

**`e2e_distributed_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
)

// 1. Warehouse Service (Inbox)
type WarehouseService struct {
	mu           sync.Mutex
	inbox        map[string]bool
	reserveCount int64
}

func (w *WarehouseService) ReserveItem(msgID string) {
	w.mu.Lock()
	defer w.mu.Unlock()

	if w.inbox[msgID] {
		return // Дубликат от брокера проигнорирован
	}

	w.inbox[msgID] = true
	atomic.AddInt64(&w.reserveCount, 1)
}

// 2. Outbox Broker Relay
type MockBroker struct {
	warehouse *WarehouseService
}

func (b *MockBroker) DeliverWithPossibleDuplicates(msgID string) {
	// Имитация At-Least-Once доставки (брокер доставил сообщение дважды!)
	b.warehouse.ReserveItem(msgID)
	b.warehouse.ReserveItem(msgID)
}

// 3. Saga Orchestrator
type OrderOrchestrator struct {
	broker *MockBroker
	mu     sync.Mutex
	sagas  map[string]string // idempKey -> sagaID
}

func (o *OrderOrchestrator) StartOrderSaga(clientKey string) string {
	o.mu.Lock()
	defer o.mu.Unlock()

	if sagaID, exists := o.sagas[clientKey]; exists {
		return sagaID // Возвращаем существующую сагу
	}

	sagaID := "saga_" + clientKey
	o.sagas[clientKey] = sagaID

	// Отправка шага в Outbox
	stepMsgID := fmt.Sprintf("%s:reserve_inventory", sagaID)
	o.broker.DeliverWithPossibleDuplicates(stepMsgID)

	return sagaID
}

// 4. API Gateway
type E2EGateway struct {
	orchestrator *OrderOrchestrator
	mu           sync.Mutex
	cachedResp   map[string]string
}

func (gw *E2EGateway) HandleClientRequest(key string) (string, bool) {
	gw.mu.Lock()
	defer gw.mu.Unlock()

	if resp, ok := gw.cachedResp[key]; ok {
		return resp, true // Cache Hit (Replay)
	}

	sagaID := gw.orchestrator.StartOrderSaga(key)
	resp := fmt.Sprintf(`{"status":"created","saga_id":"%s"}`, sagaID)
	gw.cachedResp[key] = resp

	return resp, false
}

func main() {
	warehouse := &WarehouseService{inbox: make(map[string]bool)}
	broker := &MockBroker{warehouse: warehouse}
	orchestrator := &OrderOrchestrator{broker: broker, sagas: make(map[string]string)}
	gateway := &E2EGateway{orchestrator: orchestrator, cachedResp: make(map[string]string)}

	clientKey := "e2e-order-tx-777"

	fmt.Println("=== Сквозной тест распределенной транзакции ===")

	// 1. Первый клиентский запрос
	resp1, isReplay1 := gateway.HandleClientRequest(clientKey)
	fmt.Printf("Запрос 1: Replay=%v, Body=%s\n", isReplay1, resp1)

	// 2. Сетевой повтор клиента №1
	resp2, isReplay2 := gateway.HandleClientRequest(clientKey)
	fmt.Printf("Запрос 2: Replay=%v, Body=%s\n", isReplay2, resp2)

	// 3. Сетевой повтор клиента №2
	resp3, isReplay3 := gateway.HandleClientRequest(clientKey)
	fmt.Printf("Запрос 3: Replay=%v, Body=%s\n", isReplay3, resp3)

	fmt.Println("\n=== Итоговый аудит инвариантов системы ===")
	actualReservations := atomic.LoadInt64(&warehouse.reserveCount)
	fmt.Printf("Количество физических броней на складе: %d (Строго должно быть: 1)\n", actualReservations)

	if actualReservations == 1 && isReplay2 && isReplay3 {
		fmt.Println("ТЕСТ УСПЕШНО ПРОЙДЕН: 100% согласованность на всех уровнях распределенной архитектуры!")
	} else {
		panic("ОШИБКА: Обнаружено дублирование действий в распределенной системе!")
	}
}
```

ℹ️ Сквозной интеграционный тест: Client -> Gateway -> Saga -> Outbox -> Broker -> Inbox

## Под капотом

Сквозная трассировка (Distributed Tracing OpenTelemetry):
Для сквозного аудита распределенной идемпотентности сквозь все микросервисы передается контекст `traceparent` (W3C Trace Context) и `X-Correlation-ID`. В спанах Jaeger/Grafana Tempo видно:
- Первый вызов порождает дерево спанов: `Gateway -> Orchestrator -> Outbox -> Kafka -> Inbox`.
- Второй вызов с тем же ключом завершается на спане `Gateway.IdempotencyCheck` с атрибутом `cache.hit = true`, вообще не порождая downstream сетевого трафика.

## Подводные камни

1. **Тестирование компонентов изолированно:** Изолированные тесты часто не выявляют проблемы расхождения форматов ключей между Gateway и Inbox.
2. **Игнорирование асинхронности брокеров в тестах:** В реальных интеграционных тестах (Testcontainers с настоящей Kafka и PostgreSQL) консьюмеры работают асинхронно, поэтому требуются утверждения с ожиданием `assert.Eventually`.

## На собеседовании

**Вопрос:** Как доказать корректность распределенной идемпотентности под непрерывной нагрузкой перед выкаткой в Production?
**Ответ:**
1. **Chaos Engineering & Jepsen Testing:** Запуск стресс-тестов с хаотическим внесением сбоев: инжекция сетевых задержек (`tc qdisc`), принудительный kill подов Kafka и рестарты базы данных.
2. **Shadow Traffic / Replay Traffic:** Дублирование реального продакшн-трафика на теневой стенд с проверкой идентичности ответов.
3. **Invariants Verification Worker:** Фоновый скрипт, непрерывно сверяющий сумму списаний в биллинге с количеством оформленных заказов в БД.
