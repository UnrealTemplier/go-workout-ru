# Комбинированная стратегия: Idempotency Key + ETag (Условные запросы)

## Условие

63. **Комбинированная стратегия: Idempotency Key + ETag.**: Добавьте условные запросы: клиент отправляет `If-Match` с ETag ресурса. Сервер выполняет операцию только если ресурс не изменился. Реализуйте middleware, проверяющий ETag.

### Исходная формулировка

**Комбинированная стратегия: Idempotency Key + ETag.**: Добавьте условные запросы: клиент отправляет `If-Match` с ETag ресурса. Сервер выполняет операцию только если ресурс не изменился. Реализуйте middleware, проверяющий ETag.

## Теория

В распределенных веб-архитектурах часто требуется совместить защиту от повторов запроса (Idempotency) с защитой от параллельных конфликтующих правок (Optimistic Concurrency Control / Lost Update Problem).

### Роли двух механизмов:
1. **`Idempotency-Key` (Защита от сетевых сбоев и ретраев):**
   Гарантирует, что *один и тот же запрос* одного клиента не исполнится дважды при сетевом сбое.
2. **`ETag` + `If-Match` (Оптимистическая блокировка версии):**
   Гарантирует, что клиент модифицирует *актуальную версию ресурса*, и никто другой не изменил ресурс между чтением и записью.

### Алгоритм комбинированной проверки:
1. Клиент делает `GET /articles/42`, получая ресурс с заголовком `ETag: "v1.0"`.
2. Клиент шлет `PUT /articles/42` с заголовками:
   - `If-Match: "v1.0"` (проверка версии ресурса).
   - `Idempotency-Key: upd-art-999` (защита от сетевого повтора).
3. Сервер:
   - Если `Idempotency-Key` найден в кэше завершенных: возвращает сохраненный ответ.
   - Если ресурс в базе изменился (текущий ETag `"v2.0"` != `"v1.0"`): сервер отвергает запрос со статусом `412 Precondition Failed`.
   - Если версии совпадают: применяет обновление, генерирует новый ETag `"v2.0"` и кэширует ответ по ключу идемпотентности.

## Решение по шагам

1. Создадим сущность `Document` с полями `ID`, `Content`, `Version`, `ETag`.
2. Напишем middleware, проверяющее совпадение заголовка `If-Match` с текущим ETag ресурса.
3. Интегрируем проверку `Idempotency-Key`.
4. Продемонстрируем защиту от Lost Update (`412 Precondition Failed`) и безопасный повтор успешного обновления (`Replay`).

## Код решения

**`etag_idempotency.go`**

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
)

type Document struct {
	ID      string `json:"id"`
	Content string `json:"content"`
	Version int    `json:"version"`
	ETag    string `json:"etag"`
}

func computeETag(id, content string, version int) string {
	sum := sha256.Sum256([]byte(fmt.Sprintf("%s:%s:%d", id, content, version)))
	return `"` + hex.EncodeToString(sum[:8]) + `"`
}

type DocumentService struct {
	mu    sync.Mutex
	doc   *Document
	store map[string]string // idempKey -> response body
}

func (s *DocumentService) UpdateDocument(w http.ResponseWriter, r *http.Request) {
	s.mu.Lock()
	defer s.mu.Unlock()

	idempKey := r.Header.Get("Idempotency-Key")
	if idempKey != "" {
		if cached, exists := s.store[idempKey]; exists {
			w.Header().Set("Content-Type", "application/json")
			w.Header().Set("ETag", s.doc.ETag)
			w.Header().Set("X-Idempotent-Replay", "true")
			w.WriteHeader(http.StatusOK)
			_, _ = w.Write([]byte(cached))
			return
		}
	}

	// 1. Проверка ETag через заголовок If-Match
	ifMatch := r.Header.Get("If-Match")
	if ifMatch != "" && ifMatch != s.doc.ETag {
		w.Header().Set("ETag", s.doc.ETag)
		http.Error(w, "Precondition Failed: Resource was modified by another client", http.StatusPreconditionFailed)
		return
	}

	// 2. Применение изменений
	var updateReq struct {
		Content string `json:"content"`
	}
	_ = json.NewDecoder(r.Body).Decode(&updateReq)

	s.doc.Content = updateReq.Content
	s.doc.Version++
	s.doc.ETag = computeETag(s.doc.ID, s.doc.Content, s.doc.Version)

	respBytes, _ := json.Marshal(s.doc)
	if idempKey != "" {
		s.store[idempKey] = string(respBytes)
	}

	w.Header().Set("Content-Type", "application/json")
	w.Header().Set("ETag", s.doc.ETag)
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write(respBytes)
}

func main() {
	initialETag := computeETag("doc-1", "Initial Draft", 1)
	svc := &DocumentService{
		doc: &Document{
			ID:      "doc-1",
			Content: "Initial Draft",
			Version: 1,
			ETag:    initialETag,
		},
		store: make(map[string]string),
	}

	fmt.Printf("Исходный документ: Version=%d, ETag=%s\n\n", svc.doc.Version, svc.doc.ETag)

	// Сценарий 1: Успешное обновление клиентом Alice
	req1 := httptest.NewRequest(http.MethodPut, "/docs/doc-1", strings.NewReader(`{"content":"Edited by Alice"}`))
	req1.Header.Set("If-Match", initialETag)
	req1.Header.Set("Idempotency-Key", "alice-edit-01")
	rec1 := httptest.NewRecorder()
	svc.UpdateDocument(rec1, req1)
	fmt.Printf("1. Alice Update: HTTP %d, New ETag: %s\n", rec1.Code, rec1.Header().Get("ETag"))

	// Сценарий 2: Клиент Bob пытается обновить документ со старым ETag -> 412 Precondition Failed
	req2 := httptest.NewRequest(http.MethodPut, "/docs/doc-1", strings.NewReader(`{"content":"Edited by Bob"}`))
	req2.Header.Set("If-Match", initialETag) // Старый ETag!
	req2.Header.Set("Idempotency-Key", "bob-edit-01")
	rec2 := httptest.NewRecorder()
	svc.UpdateDocument(rec2, req2)
	fmt.Printf("2. Bob Update (Lost Update Conflict): HTTP %d (Ожидается 412)\n", rec2.Code)

	// Сценарий 3: Alice повторяет свой запрос из-за таймаута сети -> Replay кэша!
	req3 := httptest.NewRequest(http.MethodPut, "/docs/doc-1", strings.NewReader(`{"content":"Edited by Alice"}`))
	req3.Header.Set("If-Match", initialETag)
	req3.Header.Set("Idempotency-Key", "alice-edit-01")
	rec3 := httptest.NewRecorder()
	svc.UpdateDocument(rec3, req3)
	fmt.Printf("3. Alice Retry: HTTP %d, Replay: %s\n", rec3.Code, rec3.Header().Get("X-Idempotent-Replay"))
}
```

ℹ️ Комбинация Idempotency Key (защита от сетевых ретраев) и ETag (защита от Lost Update)

## Под капотом

RFC 7232 (Conditional Requests):
Заголовок `If-Match: "<etag_value>"` указывает серверу применить метод изменения только в случае, если текущее представление ресурса строго совпадает с предоставленным значением ETag. Если значения не совпадают, сервер обязан вернуть статус `412 Precondition Failed`, предотвращая случайное затирание параллельных правок.

## Подводные камни

1. **Проверка If-Match после применения изменений:** Проверка версии обязана выполняться строго до выполнения записи в базу данных.
2. **Использование слабого ETag (`W/"..."`):** Для предотвращения коллизий параллельных модификаций в `If-Match` спецификация требует использования строгого (Strong) ETag.
3. **Неизменность ETag при модификации полей:** Любое изменение любого поля сущности обязано приводить к генерации нового ETag.

## На собеседовании

**Вопрос:** В чем различие между решением конфликтов с помощью `Idempotency-Key` и заголовка `If-Match: <ETag>`?
**Ответ:**
- `Idempotency-Key` идентифицирует **намерение одного конкретного клиента** повторить ту же самую операцию в случае сетевых проблем.
- `If-Match` идентифицирует **состояние и ревизию самого ресурса на сервере**, защищая от одновременной правки одного документа двумя разными пользователями (Lost Update Problem). Они идеально дополняют друг друга.
