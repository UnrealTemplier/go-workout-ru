# Универсальный принцип проектирования: Idempotency Keys как закон API

## Условие

65. **Idempotency Keys — это закон.**: Каждый POST/PUT/PATCH endpoint должен поддерживать idempotency keys. Это защита от network retries, user double-clicks, client bugs.

### Исходная формулировка

**Idempotency Keys — это закон.**: Каждый POST/PUT/PATCH endpoint должен поддерживать idempotency keys. Это защита от network retries, user double-clicks, client bugs.

## Теория

В распределенной сети ненадежно всё: мобильный интернет в метро, Wi-Fi в кафе, маршрутизаторы операторов, балансировщики AWS/Yandex Cloud и сокетные соединения ОС.

### Закон ненадежности сети (Fallacies of Distributed Computing):
1. Сеть **всегда** ненадежна.
2. Задержка **никогда** не равна нулю.
3. Доставка HTTP-ответа **не гарантирована**, даже если запрос успешно выполнился на сервере!

Когда мобильный клиент отправляет `POST /checkout` и через 3 секунды соединение обрывается (`ECONNRESET`), клиент не знает:
- Дошел ли запрос до сервера?
- Списались ли деньги?
- Упала сеть по дороге туда или обратно?

Единственный способ обеспечить безопасные ретраи — **обязательная поддержка заголовка `Idempotency-Key` на всех мутирующих эндпоинтах (`POST`, `PUT`, `PATCH`, `DELETE`)**.

### Корпоративный стандарт BigTech:
Любой вызов создания, модификации или удаления сущности в открытом API обязан принимать `Idempotency-Key`. Если клиент не прислал ключ, API Gateway в строгом режиме может либо отклонить запрос (`400 Bad Request: Idempotency-Key header is required`), либо сгенерировать временный ключ на основе криптографического отпечатка тела запроса.

## Решение по шагам

1. Создадим универсальный каркас `StrictIdempotencyEnforcer`.
2. Реализуем проверку обязательности заголовка `Idempotency-Key` для мутирующих методов (POST, PUT, PATCH, DELETE).
3. Добавим пропуск безопасных методов (GET, HEAD, OPTIONS).
4. Продемонстрируем защиту от дабл-клика и сетевого ретрая на примере создания заказа.

## Код решения

**`universal_law.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
)

type StrictIdempotencyPolicy struct {
	mu      sync.Mutex
	storage map[string]string // key -> cached body
}

func NewStrictIdempotencyPolicy() *StrictIdempotencyPolicy {
	return &StrictIdempotencyPolicy{storage: make(map[string]string)}
}

func (p *StrictIdempotencyPolicy) EnforceMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Безопасные методы (Safe Methods) по RFC 7231 не требуют Idempotency-Key
		if r.Method == http.MethodGet || r.Method == http.MethodHead || r.Method == http.MethodOptions {
			next.ServeHTTP(w, r)
			return
		}

		key := r.Header.Get("Idempotency-Key")
		if strings.TrimSpace(key) == "" {
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusBadRequest)
			_ = json.NewEncoder(w).Encode(map[string]string{
				"error":   "missing_idempotency_key",
				"message": "Mutating endpoints (POST/PUT/PATCH/DELETE) require a valid 'Idempotency-Key' header.",
			})
			return
		}

		p.mu.Lock()
		if cached, ok := p.storage[key]; ok {
			p.mu.Unlock()
			w.Header().Set("Content-Type", "application/json")
			w.Header().Set("X-Idempotent-Replay", "true")
			w.WriteHeader(http.StatusOK)
			_, _ = w.Write([]byte(cached))
			return
		}
		p.mu.Unlock()

		rec := httptest.NewRecorder()
		next.ServeHTTP(rec, r)

		if rec.Code < 500 {
			p.mu.Lock()
			p.storage[key] = rec.Body.String()
			p.mu.Unlock()
		}

		for k, v := range rec.Header() {
			w.Header()[k] = v
		}
		w.WriteHeader(rec.Code)
		_, _ = w.Write(rec.Body.Bytes())
	})
}

func main() {
	policy := NewStrictIdempotencyPolicy()
	orderHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"order_id":"ord_1001","status":"created"}`))
	})

	app := policy.EnforceMiddleware(orderHandler)

	// 1. Попытка запроса БЕЗ заголовка Idempotency-Key -> 400 Bad Request
	reqWithoutKey := httptest.NewRequest(http.MethodPost, "/v1/orders", nil)
	recWithoutKey := httptest.NewRecorder()
	app.ServeHTTP(recWithoutKey, reqWithoutKey)
	fmt.Printf("1. Запрос без ключа: HTTP %d, Body: %s\n", recWithoutKey.Code, recWithoutKey.Body.String())

	// 2. Первый запрос С ключом -> 201 Created
	reqWithKey := httptest.NewRequest(http.MethodPost, "/v1/orders", nil)
	reqWithKey.Header.Set("Idempotency-Key", "idemp-client-law-001")
	recWithKey := httptest.NewRecorder()
	app.ServeHTTP(recWithKey, reqWithKey)
	fmt.Printf("2. Запрос с ключом: HTTP %d, Body: %s\n", recWithKey.Code, recWithKey.Body.String())

	// 3. Запрос GET /v1/orders/1001 без ключа -> Разрешен без ключа!
	reqGet := httptest.NewRequest(http.MethodGet, "/v1/orders/1001", nil)
	recGet := httptest.NewRecorder()
	app.ServeHTTP(recGet, reqGet)
	fmt.Printf("3. GET запрос без ключа: HTTP %d (Safe method allowed)\n", recGet.Code)
}
```

## Под капотом

Спецификация IETF Draft (The Idempotency-Key HTTP Header Field):
Заголовок `Idempotency-Key` стандартизируется IETF HTTPbis working group. Согласно черновику, если сервер поддерживает идемпотентность для ресурса, но клиент не предоставил ключ, сервер может вернуть заголовок `Preference-Applied: idempotency-key=required` или статус 400. Ключи регистрируются в формате ASCII видимых символов длиной от 1 до 256 символов.

## Подводные камни

1. **Применение требования Idempotency-Key к GET запросам:** Метод GET обязан быть идемпотентным и безопасным по определению HTTP. Требовать заголовок на чтение — грубое нарушение спецификации REST.
2. **Кэширование ответов с авторизационными куками:** Если сохранить ответ вместе с `Set-Cookie`, повторный запрос вернет чужую сессию. Очищайте заголовок `Set-Cookie` перед записью в кэш ответов.
3. **Недостаточная длина ключа:** Разрешение односимвольных ключей типа "1" приведет к мгновенным коллизиям между пользователями.

## На собеседовании

**Вопрос:** Почему метод DELETE считается идемпотентным в HTTP, но первый вызов возвращает `200/204`, а второй `404 Not Found`?
**Ответ:** Идемпотентность в HTTP означает неизменность **состояния сервера**, а не идентичность возвращаемого кода ответа. После первого `DELETE /item/1` ресурс удален. После второго `DELETE /item/1` ресурс по-прежнему удален — состояние сервера не изменилось. Однако для полного воспроизведения ответов в API с `Idempotency-Key` второй вызов вернет оригинальный код (`200 OK` / `204 No Content`).
