# Снятие блокировки при транзитных ошибках (5xx) и панике

## Условие

60. **Игнорирование транзитных ошибок (5xx)**: Если во время обработки первого запроса произошел внутренний сбой (например, база данных вернула `500 Internal Server Error` или таймаут), мы не имеем права кэшировать этот ответ, так как операция фактически не завершилась успешно. Реализуй снятие блокировки в Redis при ошибках 5xx.

### Исходная формулировка

**Игнорирование транзитных ошибок (5xx)**: Если во время обработки первого запроса произошел внутренний сбой (например, база данных вернула `500 Internal Server Error` или таймаут), мы не имеем права кэшировать этот ответ, так как операция фактически не завершилась успехом. Настройте логику вашего middleware: если обработчик вернул статус-код `>= 500`, middleware должно мгновенно удалить блокировку из Redis, позволив клиенту совершить повторный запрос. Кэшируйте только успешные коды ответов (`2xx`) и некоторые ошибки бизнес-логики (`4xx`).

## Теория

В архитектуре высокой доступности (High Availability) крайне важно разделять типы сбоев:
- **Бизнес-ошибки клиента (Client Errors 4xx):**
  Запрос семантически некорректен (`400 Bad Request`, `404 Not Found`, `422 Unprocessable Entity`). Данные ошибки детерминированы. Повторный вызов вернет то же самое. Их можно и нужно сохранять в кэш идемпотентности.
- **Транзитные сбои инфраструктуры (Server Errors 5xx, Network Drops, Panic):**
  Временная недоступность СУБД, крах пода Kubernetes, сетевой тайм-аут, дедлок. Операция фактически **не завершилась**.

### Протокол работы с Redis:
1. Захват блокировки: `SET lock:{key} token NX EX 60`.
2. Вызов обработчика.
3. Если код ответа `>= 500` или возникла паника:
   - Вызываем `DEL lock:{key}`.
   - Никаких записей в кэш ответов НЕ делается.
   - Клиент получает 500/503 и имеет полную возможность повторить запрос с тем же `Idempotency-Key` после восстановления инфраструктуры.

## Решение по шагам

1. Создадим структуру `RedisLockStore` с методами `Acquire`, `Commit` и `Delete`.
2. Реализуем middleware с отслеживанием паники через `defer recover()` и проверкой статус-кода.
3. Продемонстрируем: при ошибке 500 ключ мгновенно удаляется, и второй вызов с тем же ключом успешно выполняет операцию.

## Код решения

**`transit_error_handler.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"sync/atomic"
)

type RedisLockStore struct {
	mu    sync.Mutex
	locks map[string]string // key -> owner
	cache map[string]string // key -> final response
}

func NewRedisLockStore() *RedisLockStore {
	return &RedisLockStore{
		locks: make(map[string]string),
		cache: make(map[string]string),
	}
}

func (s *RedisLockStore) TryLock(key, owner string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if _, locked := s.locks[key]; locked {
		return false
	}
	s.locks[key] = owner
	return true
}

func (s *RedisLockStore) Unlock(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.locks, key)
}

func (s *RedisLockStore) SaveResponse(key, resp string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.locks, key) // Снимаем временный лок
	s.cache[key] = resp  // Сохраняем финальный результат
}

func TransitErrorMiddleware(store *RedisLockStore) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" {
				next.ServeHTTP(w, r)
				return
			}

			// Проверка кэша
			store.mu.Lock()
			if cached, ok := store.cache[key]; ok {
				store.mu.Unlock()
				w.Header().Set("X-Cache", "HIT")
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(cached))
				return
			}
			store.mu.Unlock()

			if !store.TryLock(key, "worker-1") {
				http.Error(w, "concurrent conflict", http.StatusConflict)
				return
			}

			rec := httptest.NewRecorder()
			var isPanic = true
			defer func() {
				if r := recover(); r != nil || isPanic {
					store.Unlock(key) // Гарантированное снятие блокировки при панике!
					http.Error(w, "internal crash", http.StatusInternalServerError)
				}
			}()

			next.ServeHTTP(rec, r)
			isPanic = false

			if rec.Code >= 500 {
				// Ошибка 5xx: Снимаем блокировку, НЕ сохраняем в кэш!
				store.Unlock(key)
				fmt.Printf("[Idempotency] Статус %d >= 500: ключ %s разблокирован для retry!\n", rec.Code, key)
			} else {
				// Успех (2xx, 4xx): Фиксируем результат
				store.SaveResponse(key, rec.Body.String())
				fmt.Printf("[Idempotency] Успешный статус %d: результат для ключа %s сохранен!\n", rec.Code, key)
			}

			for k, v := range rec.Header() {
				w.Header()[k] = v
			}
			w.WriteHeader(rec.Code)
			_, _ = w.Write(rec.Body.Bytes())
		})
	}
}

func main() {
	store := NewRedisLockStore()
	var invocationCount int64

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		count := atomic.AddInt64(&invocationCount, 1)
		if count == 1 {
			// Первая попытка: сбой соединения с базой данных
			w.WriteHeader(http.StatusServiceUnavailable)
			_, _ = w.Write([]byte(`{"error":"db_down"}`))
			return
		}
		// Вторая попытка: успешная фиксация заказа
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"order_id":"ord_final_101"}`))
	})

	app := TransitErrorMiddleware(store)(handler)
	sameKey := "client-key-transient-fail-42"

	// 1. Попытка №1: Сервис падает с HTTP 503
	req1 := httptest.NewRequest(http.MethodPost, "/order", nil)
	req1.Header.Set("Idempotency-Key", sameKey)
	rec1 := httptest.NewRecorder()
	app.ServeHTTP(rec1, req1)
	fmt.Printf("Попытка #1: Code = %d\n", rec1.Code)

	// 2. Попытка №2: Клиент повторяет с тем же ключом -> ключ свободен и запрос проходит!
	req2 := httptest.NewRequest(http.MethodPost, "/order", nil)
	req2.Header.Set("Idempotency-Key", sameKey)
	rec2 := httptest.NewRecorder()
	app.ServeHTTP(rec2, req2)
	fmt.Printf("Попытка #2: Code = %d, Body = %s\n", rec2.Code, rec2.Body.String())

	// 3. Попытка №3: Проверка попадания в кэш после успеха
	req3 := httptest.NewRequest(http.MethodPost, "/order", nil)
	req3.Header.Set("Idempotency-Key", sameKey)
	rec3 := httptest.NewRecorder()
	app.ServeHTTP(rec3, req3)
	fmt.Printf("Попытка #3: Code = %d, Cache = %s\n", rec3.Code, rec3.Header().Get("X-Cache"))
}
```

ℹ️ Снятие блокировки в Redis при 5xx позволяет клиенту безопасно повторить запрос

## Под капотом

В Redis при обработке 5xx выполняется вызов:
`redisClient.Del(ctx, "lock:idem:" + key)`
Если удаление завершилось сетевым сбоем, сработает защитный короткий TTL (например, 30 секунд), по истечении которого Redis автоматически уничтожит замок, гарантируя отсутствие перманентных тупиков.

## Подводные камни

1. **Кэширование ошибки 500 из-за отсутствия проверки статуса:** Если сохранить `{status: 500, body: "db timeout"}`, клиент будет вечно получать эту ошибку на все попытки повтора.
2. **Неснятие лока при panic:** Необработанная паника в сторонней библиотеке уронит горутину, а ключ останется заблокированным до истечения TTL.
3. **Удаление ключа без проверки владельца:** При медленных запросах TTL может истечь, ключ займет другой запрос, а обработчик первого вызовет `Unlock()` и снимет чужой замок.

## На собеседовании

**Вопрос:** Почему ошибки клиента 4xx (например, `422 Unprocessable Entity`) можно кэшировать, а ошибки сервера 5xx (`500/503`) кэшировать категорически запрещено?
**Ответ:**
- Ошибки 4xx детерминированы и вызваны нарушением инвариантов бизнес-логики (например, «недостаточно средств на счете» или «невалидный email»). При повторе с тем же телом исход гарантированно будет тем же самым.
- Ошибки 5xx отражают деградацию окружения или инфраструктуры (сеть, диск, перезагрузка базы данных). Они транзитны по своей природе и успешно разрешаются при повторной попытке после восстановления сервисов.
