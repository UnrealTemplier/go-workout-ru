# Упорядочивание событий через Partition Key (Kafka / Redis Streams)

## Условие

71. **Event ordering через partition key.**: Для одной сущности (order_id, user_id) события должны быть ordered. Используйте Kafka partition key или Redis stream.

### Исходная формулировка

**Event ordering через partition key.**: Для одной сущности (order_id, user_id) события должны быть ordered. Используйте Kafka partition key или Redis stream.

## Теория

Идемпотентность защищает от дубликатов, но не спасает от **нарушения порядка событий (Out-of-Order Execution)**, если сообщения попадают в разные партиции очереди.

### Проблема переупорядочивания:
1. Заказ создан: `OrderCreated` отправлен в Partition 0.
2. Заказ отменен: `OrderCancelled` отправлен в Partition 1.
3. Из-за сетевых задержек воркер партиции 1 отстал. Воркер партиции 0 обработал `OrderCreated`.
4. А если бы `OrderCancelled` обработался раньше, чем `OrderCreated`? Заказ был бы сначала отменен, а затем создан заново, навсегда зависнув в статусе `CREATED`!

### Решение: Partition Key по Entity ID:
В Apache Kafka и Redis Streams действует строгое правило:
$$\text{Partition} = \text{MurmurHash2}(\text{PartitionKey}) \pmod{\text{NumPartitions}}$$
Все события одной бизнес-сущности (`order_id`, `user_id`, `account_id`) **обязаны отправляться с одинаковым Partition Key**.
Это гарантирует, что события одного заказа всегда обрабатываются **последовательно одним воркером в порядке отправки**.

## Решение по шагам

1. Создадим эмулятор кластера брокера `PartitionedBroker` с несколькими партициями.
2. Реализуем функцию детерминированного хеширования ключа партиции (`Hash(key) % N`).
3. Продемонстрируем, что события одного `order_id` строго упорядочиваются в одной партиции.

## Код решения

**`partition_ordering.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sync"
)

type EventMessage struct {
	PartitionKey string
	Sequence     int
	Action       string
}

type PartitionQueue struct {
	mu       sync.Mutex
	messages []EventMessage
}

type KafkaTopicSimulator struct {
	numPartitions int
	partitions    []*PartitionQueue
}

func NewKafkaTopic(partitions int) *KafkaTopicSimulator {
	topic := &KafkaTopicSimulator{
		numPartitions: partitions,
		partitions:    make([]*PartitionQueue, partitions),
	}
	for i := 0; i < partitions; i++ {
		topic.partitions[i] = &PartitionQueue{}
	}
	return topic
}

func (t *KafkaTopicSimulator) getPartitionIndex(key string) int {
	hasher := fnv.New32a()
	_, _ = hasher.Write([]byte(key))
	return int(hasher.Sum32()) % t.numPartitions
}

func (t *KafkaTopicSimulator) Publish(key string, seq int, action string) {
	partIdx := t.getPartitionIndex(key)
	pq := t.partitions[partIdx]

	pq.mu.Lock()
	defer pq.mu.Unlock()

	msg := EventMessage{PartitionKey: key, Sequence: seq, Action: action}
	pq.messages = append(pq.messages, msg)
	fmt.Printf("[Kafka] Событие '%s' (Seq: %d) для ключа '%s' -> Партиция #%d\n",
		action, seq, key, partIdx)
}

func main() {
	topic := NewKafkaTopic(4) // 4 партиции в топике orders.events

	// Серия событий для Заказа 101
	order1 := "ord_101"
	topic.Publish(order1, 1, "ORDER_CREATED")
	topic.Publish(order1, 2, "PAYMENT_CONFIRMED")
	topic.Publish(order1, 3, "ORDER_SHIPPED")

	// События для Заказа 202
	order2 := "ord_202"
	topic.Publish(order2, 1, "ORDER_CREATED")
	topic.Publish(order2, 2, "ORDER_CANCELLED")

	fmt.Println("\nПроверка порядка сообщений в партициях:")
	for idx, pq := range topic.partitions {
		if len(pq.messages) > 0 {
			fmt.Printf("--- Партиция #%d (сообщений: %d) ---\n", idx, len(pq.messages))
			for _, m := range pq.messages {
				fmt.Printf("  [Seq: %d] Ключ: %s, Действие: %s\n", m.Sequence, m.PartitionKey, m.Action)
			}
		}
	}
}
```

ℹ️ Упорядочивание событий сущности через Partition Key гарантирует последовательную обработку

## Под капотом

В Apache Kafka:
Если `ProducerRecord` содержит ключ (key != nil), Kafka использует дефолтный партиционер `org.apache.kafka.clients.producer.internals.DefaultPartitioner` на базе 32-битного хеша Murmur2. Сообщения с одинаковым ключом гарантированно направляются в одну и ту же партицию. Внутри одной партиции порядок сообщений абсолютно строгий и неизменный.

## Подводные камни

1. **Изменение количества партиций в Kafka на лету:** Если топик имел 10 партиций, а затем администратор добавил еще 5, формула `hash(key) % N` изменится! Новые события одного заказа начнут попадать в другие партиции, нарушая глобальный порядок.
2. **Пустой ключ партиции (`key == ""`):** При отсутствии ключа Kafka использует Round-Robin, разбрасывая события одного заказа по всем партициям.
3. **Параллельная обработка внутри консьюмера без деления по ключу:** Если горутины консьюмера читают одну партицию пачкой и обрабатывают сообщения асинхронно без шардирования, порядок снова нарушится.

## На собеседовании

**Вопрос:** Что делать, если из-за сетевого сбоя событие `OrderCancelled` все-таки обогнало `OrderCreated` и пришло раньше?
**Ответ:** Применяется концепция **State-Based Deduplication & Version Vectors**:
1. Каждое событие содержит монотонно возрастающий номер версии (`version: 2`).
2. Если консьюмер видит событие версии 2 раньше версии 1, он либо помещает его во временный буфер отложенных событий (Out-of-order Buffer), либо статус сущности переводится в терминальный `CANCELLED`, блокируя запоздавшее создание версии 1.
