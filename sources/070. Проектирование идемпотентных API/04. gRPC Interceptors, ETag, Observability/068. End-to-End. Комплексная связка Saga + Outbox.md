## Теория

В распределенной корпоративной архитектуре ни один паттерн не существует изолированно. Надежность банковского уровня достигается только согласованной работой квартета паттернов:

$$\mathbf{API\ Gateway\ Idempotency} \longleftrightarrow \mathbf{Saga\ Orchestrator} \longleftrightarrow \mathbf{Transactional\ Outbox} \longleftrightarrow \mathbf{Idempotent\ Inbox}$$

### Сквозной поток бронирования (Booking Pipeline):
1. **Клиент** шлет `POST /orders` с `Idempotency-Key: ord-req-777`.
2. **OrderService (Orchestrator):**
   - Открывает локальную транзакцию в PostgreSQL.
   - Записывает состояние Саги `ORDER_CREATED`.
   - Записывает события в таблицу `outbox_events` (Transactional Outbox).
   - Коммитит транзакцию и отдает клиенту `201 Created`.
3. **Outbox Relay:**
   - Вычитывает события и шлет их в очередь брокера (Kafka / RabbitMQ).
   - Из-за сбоя сети брокер может получить и доставить сообщение **дважды**!
4. **PaymentService & InventoryService (Inbox Consumers):**
   - Принимают сообщение, извлекают `EventID` / `StepKey`.
   - Проверяют таблицу `inbox_processed_events`.
   - Если событие дублируется: мгновенно подтверждают ACK без повторного дебета склада или карты!
   - Если событие новое: исполняют логику и атомарно коммитят Inbox.

## Решение по шагам

1. Создадим модель распределенного события `OrderSagaEvent`.
2. Реализуем `OrderService` с генерацией Outbox-задач.
3. Реализуем `PaymentService` и `InventoryService` с паттерном Inbox.
4. Симулируем доставку дубликатов на каждом шаге и покажем 100% согласованность системы.

## Код решения

**`end_to_end_saga.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
)

type SagaEvent struct {
	SagaID    string
	Step      string
	Payload   string
	MessageID string
}

// PaymentService реализует Inbox и идемпотентность списаний
type PaymentService struct {
	mu           sync.Mutex
	inbox        map[string]bool
	debitCounter int64
}

func (s *PaymentService) ProcessPaymentEvent(evt SagaEvent) {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Inbox дедупликация
	if s.inbox[evt.MessageID] {
		fmt.Printf("[PaymentService] Inbox HIT: дубликат сообщения %s проигнорирован.\n", evt.MessageID)
		return
	}

	// Бизнес-логика списания
	atomic.AddInt64(&s.debitCounter, 1)
	s.inbox[evt.MessageID] = true
	fmt.Printf("[PaymentService] Успешное списание для саги %s (MsgID: %s)\n", evt.SagaID, evt.MessageID)
}

// InventoryService реализует Inbox и идемпотентность бронирования товаров
type InventoryService struct {
	mu            sync.Mutex
	inbox         map[string]bool
	reservations  int64
}

func (s *InventoryService) ProcessInventoryEvent(evt SagaEvent) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if s.inbox[evt.MessageID] {
		fmt.Printf("[InventoryService] Inbox HIT: дубликат сообщения %s проигнорирован.\n", evt.MessageID)
		return
	}

	atomic.AddInt64(&s.reservations, 1)
	s.inbox[evt.MessageID] = true
	fmt.Printf("[InventoryService] Успешная бронь товара для саги %s (MsgID: %s)\n", evt.SagaID, evt.MessageID)
}

func main() {
	paymentSvc := &PaymentService{inbox: make(map[string]bool)}
	inventorySvc := &InventoryService{inbox: make(map[string]bool)}

	sagaID := "saga-order-e2e-1001"

	// 1. Событие оплаты с детерминированным MessageID
	payEvent := SagaEvent{
		SagaID:    sagaID,
		Step:      "STEP_1_PAYMENT",
		MessageID: fmt.Sprintf("%s:pay", sagaID),
		Payload:   "amount=4500",
	}

	// 2. Событие склада
	invEvent := SagaEvent{
		SagaID:    sagaID,
		Step:      "STEP_2_INVENTORY",
		MessageID: fmt.Sprintf("%s:inv", sagaID),
		Payload:   "sku=macbook-m3-pro",
	}

	fmt.Println("=== Эмуляция работы брокера сообщений с повторными доставками (At-Least-Once) ===")

	// Сеть доставила платежное событие ДВАЖДЫ
	paymentSvc.ProcessPaymentEvent(payEvent)
	paymentSvc.ProcessPaymentEvent(payEvent) // Дубликат!

	// Сеть доставила событие склада ТРИЖДЫ
	inventorySvc.ProcessInventoryEvent(invEvent)
	inventorySvc.ProcessInventoryEvent(invEvent) // Дубликат!
	inventorySvc.ProcessInventoryEvent(invEvent) // Дубликат!

	fmt.Println("\n=== Проверка целостности сквозного инварианта ===")
	fmt.Printf("Фактических списаний со счета: %d (Ожидается: 1)\n", atomic.LoadInt64(&paymentSvc.debitCounter))
	fmt.Printf("Фактических броней на складе: %d (Ожидается: 1)\n", atomic.LoadInt64(&inventorySvc.reservations))
}
```

ℹ️ Сквозная архитектура: интеграция Saga, Outbox, Inbox и Idempotency под дубликатами сети

## Под капотом

В полномасштабных системах на базе Apache Kafka и Debezium:
1. `OrderService` пишет заказ и событие в `outbox_table` внутри одной транзакции PostgreSQL.
2. `Debezium CDC` читает WAL PostgreSQL и без задержек транслирует запись в Kafka Topic `orders.events` с partition key `saga_id`.
3. Консьюмеры (`PaymentService`, `InventoryService`) считывают партицию и выполняют вставку в свою локальную таблицу `inbox_events (message_id PRIMARY KEY)`.
Это дает математически строгую гарантию **Exactly-Once Processing** на прикладном уровне.

## Подводные камни

1. **Асинхронный коммит Offset в Kafka до завершения транзакции:** Если консьюмер сохранил offset в Kafka, но упал до коммита в БД, сообщение будет потеряно безвозвратно.
2. **Случайный MessageID при ретраях Outbox Relay:** Если воркер Outbox пересоздает MessageID при повторной публикации, Inbox не сможет распознать дубль.
3. **Разные ключи партиционирования в Kafka:** Если события одной саги попадают в разные партиции, нарушится строгий порядок их обработки.

## На собеседовании

**Вопрос:** Почему ни один брокер сообщений (Kafka, RabbitMQ, SQS) не может гарантировать «Exactly-Once Delivery» по сети без поддержки идемпотентности на стороне консьюмера?
**Ответ:** По фундаментальной **теореме двух генералов**: в ненадежной среде отправитель не может различить аварию консьюмера от потери подтверждения (ACK) в сети. Поэтому любая надежная очередь вынуждена переотправлять сообщение при отсутствии ACK, обеспечивая лишь семантику **At-Least-Once**. Превращение At-Least-Once в Exactly-Once возможно исключительно на стороне получателя через паттерн **Idempotent Inbox**.
