# Интеграция идемпотентности с паттерном Saga

## Условие

58. **Idempotency + Saga Integration.**: Каждый шаг Saga передаёт `Idempotency-Key: saga_id + step_index`. Покажите, что при retry orchestrator сервис-участник распознаёт дубль и возвращает уже выполненный результат, позволяя Saga продолжить. Объясните, почему saga orchestrator не может работать без idempotency участников.

### Исходная формулировка

**Idempotency + Saga Integration.**: Каждый шаг Saga передаёт `Idempotency-Key: saga_id + step_index`. Покажите, что при retry orchestrator сервис-участник распознаёт дубль и возвращает уже выполненный результат, позволяя Saga продолжить. Объясните, почему без этого Saga зациклится или создаст дубли.

## Теория

Оркестратор распределенной саги (Saga Orchestrator) координирует транзакцию между несколькими независимыми сервисами (OrderService, PaymentService, InventoryService, DeliveryService).

В распределенных сетях сбои неизбежны: оркестратор может потерять соединение с сервисом платежей сразу после того, как платеж был списан. Оркестратор обязан выполнить повторную попытку (Retry Step).

### Фундаментальная теорема Саг:
**Сага не может гарантировать согласованность (Eventual Consistency) без 100% идемпотентности всех шагов (Forward Actions) и всех компенсаций (Compensating Actions).**

### Схема детерминированных ключей шага:
Оркестратор вычисляет ключ для каждого шага детерминированно:
$$\text{StepKey} = \text{saga\_id} + ":" + \text{step\_name} + ":" + \text{step\_index}$$
Если шаг повторяется из-за сбоя сети, участник видит знакомый `StepKey`, возвращает сохраненный статус успешного выполнения, и оркестратор спокойно переходит к следующему шагу саги.

## Решение по шагам

1. Создадим структуру `SagaStep` с детерминированным формированием ключа.
2. Реализуем сервис-участник `PaymentParticipant` с поддержкой идемпотентности по `saga_id + step_index`.
3. Симулируем сетевой сбой оркестратора после первого вызова.
4. Покажем, что повторный шаг оркестратора распознается как дубль, возвращает результат и продвигает сагу вперед.

## Код решения

**`saga_idempotency.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type PaymentParticipant struct {
	mu           sync.Mutex
	charges      map[string]string // stepKey -> result
	actualDebits int64
}

func NewPaymentParticipant() *PaymentParticipant {
	return &PaymentParticipant{charges: make(map[string]string)}
}

func (p *PaymentParticipant) ExecuteStep(stepKey string, amount int) (string, error) {
	p.mu.Lock()
	defer p.mu.Unlock()

	// Если шаг уже выполнен ранее — возвращаем кэшированный результат!
	if res, exists := p.charges[stepKey]; exists {
		fmt.Printf("[PaymentService] Обнаружен дубль шага саги! Ключ: %s. Возвращаем кэш.\n", stepKey)
		return res, nil
	}

	// Реальное списание
	atomic.AddInt64(&p.actualDebits, 1)
	result := fmt.Sprintf("tx_success_amt_%d", amount)
	p.charges[stepKey] = result
	fmt.Printf("[PaymentService] Выполнено списание средств для шага: %s\n", stepKey)
	return result, nil
}

type SagaOrchestrator struct {
	sagaID  string
	payment *PaymentParticipant
}

func (s *SagaOrchestrator) RunStepWithRetry(stepIndex int, stepName string, amount int) string {
	// Детерминированный ключ шага саги!
	stepKey := fmt.Sprintf("%s:%s:%d", s.sagaID, stepName, stepIndex)

	// Попытка 1: Успешно выполнилось, но сеть оборвалась на возврате ответа
	_, _ = s.payment.ExecuteStep(stepKey, amount)

	// Имитация сетевого сбоя и повторной попытки оркестратора
	fmt.Println("[Orchestrator] Сетевой таймаут! Оркестратор повторяет шаг саги...")
	finalRes, err := s.payment.ExecuteStep(stepKey, amount)
	if err != nil {
		panic(err)
	}

	return finalRes
}

func main() {
	paymentService := NewPaymentParticipant()
	orchestrator := &SagaOrchestrator{
		sagaID:  "saga-uuid-999-order-42",
		payment: paymentService,
	}

	result := orchestrator.RunStepWithRetry(1, "DEBIT_WALLET", 500)

	fmt.Printf("\nИтог шага саги: %s\n", result)
	fmt.Printf("Количество реальных списаний в БД банка: %d (должно быть ровно 1!)\n",
		atomic.LoadInt64(&paymentService.actualDebits))
}
```

ℹ️ Детерминированные ключи шагов Saga (saga_id + step_index) исключают дублирование списаний

## Под капотом

В распределенных оркестраторах (Temporal.io, Zeebe/Camunda, Cadence) детерминизм — это закон:
Каждая активность (Activity Execution) идентифицируется тройкой:
`(WorkflowID, RunID, ActivityType, SequenceNumber)`.
При рестартах оркестратора движок воспроизводит журнал истории (Event Sourcing Replay) и пропускает повторный вызов активностей, если в журнале уже зафиксировано событие `ActivityTaskCompleted`.

## Подводные камни

1. **Недетерминированный ключ шага:** Если оркестратор при ретрае генерирует новый `uuid.New()`, шаг выполнится повторно, баланс спишется дважды, и сага нарушит инвариант.
2. **Неидемпотентная компенсация:** Если компенсирующая транзакция (`RefundStep`) упадет по таймауту и выполнится повторно, клиент получит двойной возврат средств. Компенсации обязаны быть идемпотентными!
3. **Отсутствие таймаута на шаге саги:** Зависший шаг без таймаута может парализовать оркестратор навсегда.

## На собеседовании

**Вопрос:** Что произойдет, если в оркестраторе саги запрос на компенсацию шага придет РУЧЬЕМ РАНЬШЕ, чем сам запрос на выполнение шага (состояние гонки из-за переупорядочивания сообщений в сети)?
**Ответ:** Это классический феномен **Out-of-order execution**.
Сервис-участник обязан записать ключ в таблицу с флагом `COMPENSATED_BEFORE_EXECUTION`. Когда отставший запрос на выполнение шага наконец прибудет, сервис увидит признак предварительной отмены и немедленно отклонит выполнение без списания средств.
