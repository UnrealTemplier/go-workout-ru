# Мониторинг аномалий: Stale Key Ratio и падение Hit Rate

## Условие

### Исходная формулировка

**Мониторинг Idempotency.**: Реализуйте метрики: `idempotency_cache_hit_rate`, `idempotency_inflight_conflicts`, `idempotency_stale_key_ratio` (keys, повторно использованные после TTL). Настройте алерт: если `hit_rate` падает — возможно, клиенты не шлют keys или TTL слишком короткий.

## Теория

Мониторинг идемпотентности позволяет обнаруживать скрытые баги в клиентских SDK и сетевой инфраструктуре еще до того, как о них сообщат пользователи.

### Ключевые диагностические метрики:
1. **`idempotency_stale_key_ratio`:**
   Доля запросов, пришедших с ключом, который был записан в постоянную историю (аудит-лог), но чей срок жизни в быстром кэше (24h) уже истек. Высокий `stale_key_ratio` сигнализирует, что клиентские приложения «застряли» в бесконечном цикле ретраев старых операций.
2. **Аномальное падение Cache Hit Rate (`hit_rate < 0.001`):**
   Если при высокой нагрузке (например, 10 000 RPS) `hit_rate` падает почти до нуля, это верный признак бага: разработчики мобильного приложения при каждом сетевом ретрае ошибочно вызывают `uuid.New()`, генерируя новый ключ на каждый повтор! Это лишает сервер защиты от дублирования.
3. **`idempotency_inflight_conflicts`:**
   Индикатор параллельных гонок и агрессивных нетерпеливых клиентов.

## Решение по шагам

1. Создадим структуру мониторинга `AdvancedIdempotencyMetrics`.
2. Реализуем метод проверки метрик и детекции аномалий (Alert Evaluator).
3. Смоделируем нормальный трафик и аномальное поведение клиентов.
4. Продемонстрируем срабатывание предупреждений о падении Hit Rate и устаревании ключей.

## Код решения

**`idempotency_alerts.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"time"
)

type ProductionMetrics struct {
	RequestsTotal    uint64
	CacheHits        uint64
	InFlightConflicts uint64
	StaleKeyReuses   uint64
}

type AnomalyDetector struct {
	metrics *ProductionMetrics
}

func (d *AnomalyDetector) EvaluateHealth() []string {
	var alerts []string
	total := atomic.LoadUint64(&d.metrics.RequestsTotal)
	hits := atomic.LoadUint64(&d.metrics.CacheHits)
	conflicts := atomic.LoadUint64(&d.metrics.InFlightConflicts)
	stale := atomic.LoadUint64(&d.metrics.StaleKeyReuses)

	if total < 100 {
		return alerts // Недостаточно данных для статистики
	}

	hitRate := float64(hits) / float64(total)
	conflictRate := float64(conflicts) / float64(total)
	staleRate := float64(stale) / float64(total)

	// Правило 1: Подозрительно низкий Hit Rate при наличии ретраев
	if hitRate < 0.005 {
		alerts = append(alerts, fmt.Sprintf(
			"ALERT: Low Idempotency Hit Rate (%.4f%%). Clients might be regenerating UUID on every retry attempt!",
			hitRate*100,
		))
	}

	// Правило 2: Высокая частота in-flight конфликтов
	if conflictRate > 0.05 {
		alerts = append(alerts, fmt.Sprintf(
			"WARNING: High In-Flight Conflict Rate (%.2f%%). Check client retry backoff/jitter settings.",
			conflictRate*100,
		))
	}

	// Правило 3: Использование просроченных ключей
	if staleRate > 0.01 {
		alerts = append(alerts, fmt.Sprintf(
			"CRITICAL: Stale Keys Reused (%.2f%%). Clients are retrying requests older than TTL window (24h)!",
			staleRate*100,
		))
	}

	return alerts
}

func main() {
	metrics := &ProductionMetrics{}
	detector := &AnomalyDetector{metrics: metrics}

	// Симулируем 1000 запросов от сломанного клиента, который при каждом ретрае генерирует новый ключ
	atomic.StoreUint64(&metrics.RequestsTotal, 1000)
	atomic.StoreUint64(&metrics.CacheHits, 1) // всего 1 хит на 1000 запросов!
	atomic.StoreUint64(&metrics.InFlightConflicts, 65)
	atomic.StoreUint64(&metrics.StaleKeyReuses, 15)

	alerts := detector.EvaluateHealth()

	fmt.Println("Результаты автоматической диагностики слоя идемпотентности:")
	for i, alert := range alerts {
		fmt.Printf("[%d] %s\n", i+1, alert)
	}
}
```

ℹ️ Автоматическая детекция аномалий: выявление багов клиентских SDK по метрикам идемпотентности

## Под капотом

В системах APM (Prometheus + Alertmanager) правила оформляются в виде файлов алертов:
```yaml
groups:
  - name: idempotency_alerts
    rules:
      - alert: IdempotencyHitRateTooLow
        expr: (sum(rate(idempotency_requests_total{status="hit"}[10m])) / sum(rate(idempotency_requests_total[10m]))) < 0.005
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Клиенты не используют Idempotency-Key повторно при ретраях"
```
Такой алерт предотвращает катастрофические списания еще на этапе бета-тестирования новой версии мобильного приложения.

## Подводные камни

1. **Алерты на малом объеме трафика:** В ночные часы или на тестовом стенде при 5 запросах в минуту Hit Rate может быть нулевым. Всегда добавляйте проверку минимального порога запросов (`RequestsTotal > 1000`).
2. **Отсутствие метрик времени ожидания (Latency):** Запросы в статусе In-Flight могут ожидать освобождения блокировки, занижая общую производительность сервиса.
3. **Хранение бесконечной истории ключей для проверки Stale:** Для подсчета Stale Keys достаточно хранить легковесный фильтр Блума (Bloom Filter) или лог транзакций в ClickHouse.

## На собеседовании

**Вопрос:** Как по метрикам Grafana быстро определить, что на стороне клиентов возник баг «Thundering Herd» (лавина одновременных ретраев)?
**Ответ:** На дашборде будет виден одновременный скачок двух метрик:
1. `idempotency_inflight_conflicts` (HTTP 409) взлетает вертикально вверх.
2. `http_request_duration_seconds` (p99) резко возрастает.
Это указывает на то, что клиенты не используют экспоненциальный бэкофф с джиттером (Jitter) и одновременно шлют сотни запросов с одним и тем же ключом при малейшем колебании сети.
