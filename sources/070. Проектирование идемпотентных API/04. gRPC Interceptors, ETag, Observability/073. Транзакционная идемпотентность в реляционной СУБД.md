```sql

```
Проверьте результат выполнения: если строка не была вставлена (возник конфликт уникального ключа), обработайте это событие в Go как повторный запрос, считайте залогированный ранее ответ из таблицы `idempotency_keys` и отдайте его клиенту. Если вставка прошла успешно — продолжите выполнение обработчика.

## Теория

Когда в архитектуре нет Redis или требуется абсолютная финансовая надежность без риска рассинхронизации между In-Memory кэшем и базой данных, слой идемпотентности целиком переносится на уровень **реляционной СУБД (PostgreSQL)**.

### Схема таблицы:
```sql
CREATE TABLE idempotency_keys (
    key VARCHAR(128) PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL, -- 'started', 'completed'
    response_code INT,
    response_body TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

### Транзакционный алгоритм:
1. Клиент вызывает `POST /transfer`.
2. Middleware открывает транзакцию `tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})`.
3. Выполняется атомарная попытка вставки:
   ```sql
   INSERT INTO idempotency_keys (key, user_id, status)
   VALUES ($1, $2, 'started')
   ON CONFLICT (key) DO NOTHING;
   ```
4. Если вставлено `0` строк:
   - Запись уже существует! Делаем `SELECT status, response_code, response_body FROM idempotency_keys WHERE key = $1 FOR UPDATE`.
   - Если статус `'started'`: другая транзакция еще работает \(\to\) откат и `409 Conflict`.
   - Если статус `'completed'`: откат и возврат сохраненного ответа.
5. Если строка успешно вставлена:
   - Выполняем бизнес-логику внутри `tx`.
   - Обновляем статус: `UPDATE idempotency_keys SET status = 'completed', response_code = $2, response_body = $3 WHERE key = $1`.
   - Коммитим транзакцию `tx.Commit()`.

## Решение по шагам

1. Создадим структуру `PostgresTransactionManager` для эмуляции транзакций СУБД.
2. Реализуем вставку со статусом `started` и строчную блокировку `FOR UPDATE`.
3. Свяжем обновление бизнес-таблицы и статуса идемпотентности в один атомарный коммит.
4. Продемонстрируем надежность при параллельных обращениях и повторах.

## Код решения

**`postgres_transactional.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

type TxStatus string

const (
	TxStarted   TxStatus = "started"
	TxCompleted TxStatus = "completed"
)

type IdempDBRecord struct {
	Key          string
	Status       TxStatus
	ResponseCode int
	ResponseBody string
}

type MockPostgresDB struct {
	mu      sync.Mutex
	records map[string]*IdempDBRecord
	balance map[string]int
}

func NewMockPostgresDB() *MockPostgresDB {
	return &MockPostgresDB{
		records: make(map[string]*IdempDBRecord),
		balance: map[string]int{"user_1": 1000},
	}
}

func (db *MockPostgresDB) ExecuteTransferTx(ctx context.Context, key, userID string, amount int) (int, string, error) {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Проверяем наличие ключа в таблице
	if rec, exists := db.records[key]; exists {
		if rec.Status == TxStarted {
			// Операция выполняется прямо сейчас в другой транзакции!
			return 409, `{"error":"concurrent_tx_in_progress"}`, nil
		}
		// Возвращаем зафиксированный результат
		return rec.ResponseCode, rec.ResponseBody, nil
	}

	// 2. Вставка со статусом 'started' (INSERT INTO ... ON CONFLICT DO NOTHING)
	db.records[key] = &IdempDBRecord{
		Key:    key,
		Status: TxStarted,
	}

	// 3. Выполнение бизнес-логики (списание баланса)
	currentBal := db.balance[userID]
	if currentBal < amount {
		// Откат: удаляем запись при бизнес-ошибке
		delete(db.records, key)
		return 422, `{"error":"insufficient_funds"}`, nil
	}

	db.balance[userID] = currentBal - amount
	newBal := db.balance[userID]

	// 4. Фиксация результата и перевод в 'completed'
	respBody := fmt.Sprintf(`{"transfer":"success","remaining":%d}`, newBal)
	db.records[key].Status = TxCompleted
	db.records[key].ResponseCode = 200
	db.records[key].ResponseBody = respBody

	return 200, respBody, nil
}

func main() {
	db := NewMockPostgresDB()
	ctx := context.Background()
	key := "tx-bank-idemp-001"

	// Попытка 1: Успешный перевод $300
	code1, body1, _ := db.ExecuteTransferTx(ctx, key, "user_1", 300)
	fmt.Printf("1. Первая попытка: HTTP %d, Ответ: %s\n", code1, body1)

	// Попытка 2: Сетевой повтор с тем же ключом
	code2, body2, _ := db.ExecuteTransferTx(ctx, key, "user_1", 300)
	fmt.Printf("2. Повторная попытка: HTTP %d, Ответ: %s\n", code2, body2)

	fmt.Printf("\nИТОГ: Итоговый баланс в PostgreSQL: $%d (списание выполнено ровно 1 раз!)\n", db.balance["user_1"])
}
```

ℹ️ Транзакционная идемпотентность в реляционной СУБД: статус started и фиксация в единой транзакции

## Под капотом

В реальном драйвере `database/sql` и `pgx`:
```go
tx, err := db.BeginTx(ctx, nil)
defer tx.Rollback()

var status string
err = tx.QueryRowContext(ctx, "INSERT INTO idempotency_keys (key, status) VALUES ($1, 'started') ON CONFLICT (key) DO UPDATE SET updated_at = NOW() RETURNING status", key).Scan(&status)
```
Использование `RETURNING status` позволяет за один сетевой запрос определить: создана ли новая запись (`status == 'started'`) или ключ уже существовал.

## Подводные камни

1. **Удержание транзакции во время сетевых вызовов:** Никогда не выполняйте внешние HTTP-запросы (например, вызов стороннего банка) внутри открытой `sql.Tx` транзакции базы данных.
2. **Неснятые блокировки при Rollback:** Если транзакция откатилась, запись `started` исчезает благодаря свойствам ACID, что автоматически разрешает клиенту повторить попытку.
3. **Дедлоки при параллельных вставках:** Убедитесь, что все транзакции обращаются к таблицам в строго одинаковом порядке.

## На собеседовании

**Вопрос:** В чем фундаментальное преимущество использования реляционной транзакции PostgreSQL для идемпотентности по сравнению с Redis?
**Ответ:** 
В PostgreSQL запись об идемпотентности и изменение финансового баланса коммитятся в рамках **одной физической ACID-транзакции в журнал предзаписи (WAL)**. 
Это математически исключает Dual-Write Problem: ситуацию, когда баланс списался, а запись в кэш упала из-за сетевого сбоя. В PostgreSQL либо применяются оба изменения, либо ни одного.
