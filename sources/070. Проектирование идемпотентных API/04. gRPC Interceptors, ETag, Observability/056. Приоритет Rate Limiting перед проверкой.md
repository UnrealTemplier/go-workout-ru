# Приоритет Rate Limiting перед проверкой идемпотентности

## Условие

56. **Idempotency + rate limiting**: Rate limiting применяется до idempotency check. Иначе атакующий может bypass rate limit через повторные requests с тем же key.

### Исходная формулировка

**Idempotency + rate limiting**: Rate limiting применяется до idempotency check. Иначе атакующий может bypass rate limit через повторные requests с тем же key.

## Теория

Порядок следования middleware в HTTP-пайплайне критичен для безопасности. Распространенная уязвимость архитектуры — размещение слоя идемпотентности **перед** слоем ограничения частоты запросов (Rate Limiter).

### Анализ вектора атаки (Bypass / DoS Exploit):
Если `IdempotencyMiddleware` стоит перед `RateLimiter`:
1. Злоумышленник перехватывает один легитимный `Idempotency-Key` или генерирует свой.
2. Сервер выполняет запрос и сохраняет ответ в кэш.
3. Атакующий генерирует лавину из 200 000 RPS с этим же ключом.
4. Поскольку `IdempotencyMiddleware` перехватывает запрос первым, оно мгновенно возвращает кэшированный ответ, минуя счетчики `RateLimiter`.
5. Итог: сервер тратит ресурсы CPU, сокетов и сетевой полосы на обслуживание DoS-атаки, а квоты клиента не списываются!

### Канонический порядок фильтров:
$$\text{Request} \longrightarrow \mathbf{RateLimiter} \longrightarrow \mathbf{Authentication} \longrightarrow \mathbf{IdempotencyMiddleware} \longrightarrow \mathbf{BusinessHandler}$$
Сначала отсекается превышение квот (Token Bucket / Leaky Bucket), затем проверяются права доступа, и только потом происходит поиск в хранилище идемпотентности.

## Решение по шагам

1. Создадим `TokenBucketRateLimiter` с лимитом N запросов в секунду.
2. Создадим `IdempotencyStore` с кэшированными ответами.
3. Сконструируем цепочку middleware: сначала Rate Limiter, затем Idempotency.
4. Продемонстрируем, что спам повторными запросами с одинаковым ключом блокируется статусом `429 Too Many Requests` при превышении лимита.

## Код решения

**`ratelimit_order.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type RateLimiter struct {
	mu       sync.Mutex
	tokens   int
	capacity int
}

func NewRateLimiter(capacity int) *RateLimiter {
	return &RateLimiter{tokens: capacity, capacity: capacity}
}

func (rl *RateLimiter) Allow() bool {
	rl.mu.Lock()
	defer rl.mu.Unlock()
	if rl.tokens > 0 {
		rl.tokens--
		return true
	}
	return false
}

func RateLimitMiddleware(rl *RateLimiter) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			if !rl.Allow() {
				w.Header().Set("Retry-After", "1")
				http.Error(w, `{"error":"rate_limit_exceeded"}`, http.StatusTooManyRequests)
				return
			}
			next.ServeHTTP(w, r)
		})
	}
}

func main() {
	rl := NewRateLimiter(2) // Разрешено максимум 2 запроса
	store := NewSafeIdempotencyStore()

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"data":"success"}`))
	})

	// ПРАВИЛЬНЫЙ ПОРЯДОК: Rate Limiter оборачивает Idempotency Middleware!
	pipeline := RateLimitMiddleware(rl)(PartialFailureMiddleware(store)(handler))

	sameKey := "attack-key-duplicate-999"

	for i := 1; i <= 4; i++ {
		req := httptest.NewRequest(http.MethodPost, "/resource", nil)
		req.Header.Set("Idempotency-Key", sameKey)
		rec := httptest.NewRecorder()

		pipeline.ServeHTTP(rec, req)
		fmt.Printf("Запрос #%d: HTTP %d (Body: %s)\n", i, rec.Code, rec.Body.String())
	}
}
```

ℹ️ Rate Limiting перед Idempotency Check защищает сервер от исчерпания сетевых ресурсов

## Под капотом

В распределенных шлюзах (Envoy, Kong, Nginx) модуль Rate Limiting работает на уровне L7 Envoy filter chain:
```yaml
http_filters:
  - name: envoy.filters.http.ratelimit
  - name: envoy.filters.http.jwt_authn
  - name: envoy.filters.http.idempotency
```
При таком порядке запросы, превышающие квоту (DDoS), сбрасываются ядром Envoy без расходования ресурсов памяти Redis на поиск ключей идемпотентности.

## Подводные камни

1. **Неправильный порядок middleware в Go (`r.Use`):** В фреймворках типа Gin/Chi вызов `r.Use(Idempotency, RateLimit)` приведет к уязвимости обхода лимитов.
2. **Лимитирование без разделения по IP/API-Key:** Глобальный лимит заблокирует всех добросовестных пользователей, если один из клиентов попал в шторм ретраев.
3. **Отсутствие дифференциации для повторов:** В некоторых системах для повторных запросов с `Idempotency-Key` выделяют отдельный, более мягкий лимит, но они никогда не пропускаются безлимитно.

## На собеседовании

**Вопрос:** Почему даже кэшированный ответ из Redis нельзя отдавать в обход Rate Limiter?
**Ответ:** Отдача кэшированного ответа требует сетевого I/O, аллокации буферов в рантайме Go, десериализации JSON и сериализации HTTP-пакетов. Атакующий с ботнетом может сгенерировать 500 000 RPS повторов с одним ключом, исчерпав дескрипторы сокетов сервера (file descriptors) и вызвав отказ в обслуживании (Denial of Service).
