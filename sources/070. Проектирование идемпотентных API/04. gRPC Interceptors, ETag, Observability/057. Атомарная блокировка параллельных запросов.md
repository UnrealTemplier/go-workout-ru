# Атомарная блокировка параллельных запросов (Distributed Lock / Redlock)

## Условие

57. **[Каверзный кейс — Concurrent Requests (Гонка)]**: Злоумышленник (или баг в клиенте) отправляет два абсолютно одинаковых запроса с одним `Idempotency-Key` одновременно. Оба запроса могут пройти проверку в Redis до того, как первый успеет сохранить результат. Реализуй атомарную блокировку (Distributed Lock / Redlock / SET NX) с коротким TTL (например, 30 сек) на момент выполнения запроса.

### Исходная формулировка

**[Каверзный кейс — Concurrent Requests (Гонка)]**: Злоумышленник (или баг в клиенте) отправляет два абсолютно одинаковых запроса с одним `Idempotencyency-Key` одновременно. Оба запроса могут пройти проверку в Redis до того, как первый успеет сохранить результат. Реализуй блокировку: используй `SETNX` (Set if Not eXists) в Redis. Второй запрос получает ошибку или ждет (или получает `409 Conflict` / `425 Too Early`).

## Теория

Сценарий критической уязвимости:
1. Запрос \(R_1\) и запрос \(R_2\) с одинаковым `Idempotency-Key: pay-123` поступают на два разных инстанса API Gateway с разницей в 2 миллисекунды.
2. Инстанс 1 проверяет Redis: ключ не найден.
3. Инстанс 2 проверяет Redis: ключ все еще не найден!
4. Оба инстанса одновременно запускают списание средств с банковского счета.

### Решение через Distributed Lock (SET NX EX):
Вместо чтения перед записью выполняется **атомарная заявка на исполнение**:
```text
SET lock:idem:{key} {worker_uuid} NX EX 30
```
- Если результат `OK`: данный воркер получил монопольное право на выполнение операции.
- Если результат `nil`: ключ уже удерживается другим параллельным запросом.
  Сервер возвращает `409 Conflict` с заголовком `Retry-After: 2` или переходит в режим ожидания (Polling/PubSub) готовности ответа с коротким таймаутом.

## Решение по шагам

1. Создадим распределенный менеджер блокировок `DistributedLockStore` с имитацией Redis SETNX.
2. Настроим атомарный захват блокировки с TTL 30 секунд.
3. Симулируем две одновременные горутины, пытающиеся обработать один и тот же ключ.
4. Убедимся, что ровно одна горутина получает лок и выполняет задачу, а вторая получает статус конфликта.

## Код решения

**`distributed_lock.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type DistLockManager struct {
	mu    sync.Mutex
	locks map[string]time.Time // key -> expiration
}

func NewDistLockManager() *DistLockManager {
	return &DistLockManager{locks: make(map[string]time.Time)}
}

// TryAcquireLock реализует Redis SET key val NX EX ttl
func (m *DistLockManager) TryAcquireLock(key string, ttl time.Duration) bool {
	m.mu.Lock()
	defer m.mu.Unlock()

	now := time.Now()
	if exp, exists := m.locks[key]; exists {
		if exp.After(now) {
			return false // Ключ уже заблокирован!
		}
	}

	m.locks[key] = now.Add(ttl)
	return true
}

func (m *DistLockManager) ReleaseLock(key string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	delete(m.locks, key)
}

func main() {
	lockMgr := NewDistLockManager()
	idempKey := "order-lock-concurrent-999"

	var wg sync.WaitGroup
	results := make([]string, 2)

	// Запуск двух параллельных горутин (одновременный клик)
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			acquired := lockMgr.TryAcquireLock(idempKey, 30*time.Second)
			if !acquired {
				results[workerID] = fmt.Sprintf("Воркер #%d: 409 Conflict (Lock busy)", workerID+1)
				return
			}

			// Имитация полезной работы
			time.Sleep(50 * time.Millisecond)
			results[workerID] = fmt.Sprintf("Воркер #%d: 201 Created (Success)", workerID+1)
		}(i)
	}

	wg.Wait()

	fmt.Println("Результат конкурентной гонки:")
	for _, res := range results {
		fmt.Println(" ", res)
	}
}
```

ℹ️ Атомарный захват блокировки SET NX EX 30 устраняет Race Condition при параллельных запросах

## Под капотом

В распределенных кластерах Redis (Redis Cluster с мультимастером) для предотвращения гонок при сплит-брейнах применяется алгоритм **Redlock**:
Клиент пытается захватить блокировку с одинаковым случайным значением во всех \(N\) независимых инстансах Redis (обычно 5 нод). Блокировка считается успешной, только если клиент захватил большинство (\(\frac{N}{2} + 1 = 3\)) нод за время, меньшее чем таймаут валидности ключа.

## Подводные камни

1. **Снятие чужой блокировки при задержках GC:** Если горутина заснула в Stop-the-World GC паузе на 31 секунду, TTL истек, другой воркер захватил лок, а первая горутина проснулась и вызвала `DEL key`. Она удалит чужой лок! Используйте UUID владельца и удаление через Lua-скрипт (`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`).
2. **Отсутствие TTL у блокировки:** Если процесс упадет до снятия лока, ключ заблокирует операцию навсегда. TTL обязателен всегда!
3. **Слишком длинный TTL на блокировку:** Установка 10 минут приведет к тому, что при реальном падении инстанса клиент не сможет повторить операцию 10 минут.

## На собеседовании

**Вопрос:** Как безопасно освободить распределенный лок в Redis, чтобы исключить удаление блокировки другого процесса при истечении собственного таймаута?
**Ответ:** При захвате генерируется уникальный криптографический маркер (`ownerToken = uuid.New()`). Освобождение выполняется исключительно атомарным Lua-скриптом:
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```
Это гарантирует, что если наш TTL истек и ключ занят другим процессом, мы не снимем чужую блокировку.
