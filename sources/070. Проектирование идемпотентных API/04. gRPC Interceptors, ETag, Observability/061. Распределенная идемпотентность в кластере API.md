# Распределенная идемпотентность в кластере API Gateway (PostgreSQL SKIP LOCKED / Redlock)

## Условие

61. **Distributed Idempotency.**: API Gateway состоит из 3 инстансов. In-memory map не работает. Реализуйте хранилище на PostgreSQL с `UNIQUE(idempotency_key, user_id)` и `SKIP LOCKED` для in-flight detection. Альтернатива: Redis Cluster с `Redlock`.

### Исходная формулировка

**Distributed Idempotency.**: API Gateway состоит из 3 инстансов. In-memory map не работает. Реализуйте хранилище на PostgreSQL с `UNIQUE(idempotency_key, user_id)` и `SKIP LOCKED` для in-flight detection. Альтернатива: Redis Cluster с `Redlock`. Сравните latency и надёжность.

## Теория

Когда API Gateway горизонтально масштабируется (например, 10 инстансов в Kubernetes Pods), локальная память (`sync.Map`) становится бесполезной: запрос 1 приходит на Pod A, а повтор через балансировщик попадает на Pod B.

### Реляционная реализация на PostgreSQL:
Создается централизованная таблица:
```sql
CREATE TABLE idempotency_keys (
    user_id VARCHAR(64) NOT NULL,
    idempotency_key VARCHAR(128) NOT NULL,
    status VARCHAR(32) NOT NULL, -- 'IN_PROGRESS', 'COMPLETED'
    response_code INT,
    response_body JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, idempotency_key)
);
```

### In-Flight Detection через транзакционную семантику:
1. Запрос пытается вставить запись:
   `INSERT INTO idempotency_keys (user_id, idempotency_key, status) VALUES ($1, $2, 'IN_PROGRESS') ON CONFLICT DO NOTHING;`
2. Если вставка удалась: Pod захватил право выполнения.
3. Если строка уже существует, Pod выполняет:
   `SELECT status, response_code, response_body FROM idempotency_keys WHERE user_id = $1 AND idempotency_key = $2 FOR UPDATE NOWAIT;`
   - Если строка заблокирована (`NOWAIT` вернул ошибку `55P03 lock_not_available`): операция выполняется прямо сейчас на другом поде! Возвращаем `409 Conflict`.
   - Если статус `COMPLETED`: возвращаем кэшированный ответ.

## Решение по шагам

1. Создадим модель кластерного хранилища `ClusterIdempotencyStorage`.
2. Реализуем строчные транзакционные блокировки и обработку параллельных конфликтов.
3. Смоделируем 3 независимых пода шлюза, конкурирующих за один ключ.
4. Продемонстрируем согласованность кластера при перенаправлении ретраев между подами.

## Код решения

**`cluster_gateway.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrLockConflict = errors.New("55P03: lock_not_available (in-flight on another instance)")
)

type DBRow struct {
	UserID       string
	Key          string
	Status       string // IN_PROGRESS, COMPLETED
	StatusCode   int
	ResponseBody string
	Locked       bool
}

type PostgresEmulator struct {
	mu   sync.Mutex
	rows map[string]*DBRow // user:key -> row
}

func NewPostgresEmulator() *PostgresEmulator {
	return &PostgresEmulator{rows: make(map[string]*DBRow)}
}

func (db *PostgresEmulator) TryInsertOrLock(userID, key string) (*DBRow, error) {
	db.mu.Lock()
	defer db.mu.Unlock()

	compositeKey := userID + ":" + key
	row, exists := db.rows[compositeKey]

	if !exists {
		// INSERT INTO ... ON CONFLICT DO NOTHING (успешная вставка)
		newRow := &DBRow{
			UserID: userID,
			Key:    key,
			Status: "IN_PROGRESS",
			Locked: true,
		}
		db.rows[compositeKey] = newRow
		return newRow, nil
	}

	// Строка уже есть. Проверяем FOR UPDATE NOWAIT
	if row.Locked || row.Status == "IN_PROGRESS" {
		return nil, ErrLockConflict
	}

	return row, nil
}

func (db *PostgresEmulator) CommitResult(userID, key string, code int, body string) {
	db.mu.Lock()
	defer db.mu.Unlock()

	compositeKey := userID + ":" + key
	if row, exists := db.rows[compositeKey]; exists {
		row.Status = "COMPLETED"
		row.StatusCode = code
		row.ResponseBody = body
		row.Locked = false
	}
}

type GatewayInstance struct {
	Name string
	db   *PostgresEmulator
}

func (gw *GatewayInstance) HandleRequest(userID, key string) (int, string) {
	row, err := gw.db.TryInsertOrLock(userID, key)
	if errors.Is(err, ErrLockConflict) {
		return 409, fmt.Sprintf(`{"error":"concurrent_operation_processing_on_other_node"}`)
	}

	if row.Status == "COMPLETED" {
		return row.StatusCode, row.ResponseBody
	}

	// Имитируем выполнение тяжелой логики
	time.Sleep(50 * time.Millisecond)
	respBody := `{"order_id":"ord_cluster_777","status":"created"}`
	gw.db.CommitResult(userID, key, 201, respBody)

	return 201, respBody
}

func main() {
	sharedDB := NewPostgresEmulator()

	// 3 независимых инстанса API Gateway за Round-Robin балансировщиком
	pod1 := &GatewayInstance{Name: "Gateway-Pod-1", db: sharedDB}
	pod2 := &GatewayInstance{Name: "Gateway-Pod-2", db: sharedDB}
	pod3 := &GatewayInstance{Name: "Gateway-Pod-3", db: sharedDB}

	userID := "user_enterprise_99"
	idempKey := "order_tx_uuid_555"

	var wg sync.WaitGroup
	wg.Add(2)

	// Запрос 1 поступает на Pod 1
	go func() {
		defer wg.Done()
		code, body := pod1.HandleRequest(userID, idempKey)
		fmt.Printf("[%s] Запрос 1 завершен: HTTP %d, Body: %s\n", pod1.Name, code, body)
	}()

	// Запрос 2 (параллельный дубль) через 5 мс попадает на Pod 2
	go func() {
		defer wg.Done()
		time.Sleep(5 * time.Millisecond)
		code, body := pod2.HandleRequest(userID, idempKey)
		fmt.Printf("[%s] Запрос 2 завершен: HTTP %d, Body: %s\n", pod2.Name, code, body)
	}()

	wg.Wait()

	// Запрос 3 (повтор после завершения) попадает на Pod 3
	code, body := pod3.HandleRequest(userID, idempKey)
	fmt.Printf("[%s] Запрос 3 (Replay) завершен: HTTP %d, Body: %s\n", pod3.Name, code, body)
}
```

## Под капотом

Использование предложения `FOR UPDATE SKIP LOCKED`:
В сценариях фоновой пакетной обработки очередей опция `SKIP LOCKED` позволяет воркерам не вставать в блокировку и не получать ошибку, а мгновенно пропускать строки, захваченные другими транзакциями. Это ключевой механизм реализации высокопроизводительных очередей задач прямо в PostgreSQL без Redis/RabbitMQ.

## Подводные камни

1. **Блокировки без таймаутов (Statement Timeout):** Если сетевой сбой разорвал соединение с подом, транзакция может удерживать строку в PostgreSQL. Обязательно настраивайте `SET idle_in_transaction_session_timeout = '10s'`.
2. **Слишком большая таблица без секционирования:** В кластере под высокой нагрузкой таблица `idempotency_keys` генерирует интенсивные обновления. Регулярно настраивайте автоочистку или партиционирование.
3. **Dual Master коллизии:** При использовании мультимастер репликации асинхронный конфликт ключей может привести к split-brain. Используйте строго одну Master-ноду для записи ключей.

## На собеседовании

**Вопрос:** Чем отличается использование PostgreSQL с `FOR UPDATE NOWAIT` от распределенного лока в Redis через Redlock?
**Ответ:**
1. **Транзакционность:** В PostgreSQL ключ идемпотентности блокируется и фиксируется в рамках единой ACID-транзакции вместе с бизнес-сущностями, исключая рассинхронизацию.
2. **Задержка:** Redis Redlock работает быстрее (микросекунды против миллисекунд), но подвержен рискам задержек сборщика мусора (GC pause risk) и рассинхронизации системных часов нод (Clock Drift). Для биллинга выбирают PostgreSQL, для стриминга и нотификаций — Redis Cluster.
