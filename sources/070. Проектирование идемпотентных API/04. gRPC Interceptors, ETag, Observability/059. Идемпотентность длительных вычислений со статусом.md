# Идемпотентность длительных вычислений со статусом Processing

## Условие

59. **Идемпотентность для асинхронных операций.**: Реализуйте обработку, где операция длительная (статус `processing`), а клиент повторяет запрос с тем же ключом. Сервер должен вернуть статус выполнения, не запуская повторно. При завершении — вернуть результат.

### Исходная формулировка

**Идемпотентность для асинхронных операций.**: Реализуйте обработку, где операция длительная (статус `processing`), а клиент повторяет запрос с тем же ключом. Сервер должен вернуть статус выполнения, не запуская повторно. При завершении — вернуть результат.

## Теория

Когда запрос требует сложной обработки (генерация PDF-выписки за 5 лет, сверка транзакций, импорт каталога), клиент может повторно нажать кнопку «Сформировать отчет».

### Протокол взаимодействия при длительных операциях:
1. **Первый запрос:**
   - Сервер регистрирует операцию со статусом `PROCESSING` и сохраняет метаданные.
   - Запускается фоновая горутина или задача в очереди.
   - Сервер возвращает статус `202 Accepted` или `200 OK` с телом `{"status":"processing","progress":0}`.
2. **Повторные запросы во время обработки:**
   - Middleware находит ключ со статусом `PROCESSING`.
   - **Новая задача НЕ создается.**
   - Сервер возвращает текущий статус обработки: `{"status":"processing","progress":45,"eta_seconds":15}`.
3. **Повторный запрос после завершения:**
   - Middleware видит статус `COMPLETED`.
   - Сервер мгновенно отдает финальный сформированный результат (например, ссылку на скачивание файла).

## Решение по шагам

1. Создадим менеджер задач `JobManager` с состояниями `StateProcessing` и `StateCompleted`.
2. Реализуем обработчик, отслеживающий прогресс выполнения задачи.
3. Покажем, что параллельные или повторные запросы во время вычислений получают статус `processing`, а после завершения — итоговый отчет.

## Код решения

**`processing_idempotency.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type JobState string

const (
	JobStateProcessing JobState = "PROCESSING"
	JobStateCompleted  JobState = "COMPLETED"
)

type JobRecord struct {
	ID        string    `json:"job_id"`
	State     JobState  `json:"state"`
	Progress  int       `json:"progress_percent"`
	ResultURL string    `json:"result_url,omitempty"`
	CreatedAt time.Time `json:"created_at"`
}

type HeavyJobService struct {
	mu   sync.Mutex
	jobs map[string]*JobRecord // idempKey -> job
}

func NewHeavyJobService() *HeavyJobService {
	return &HeavyJobService{jobs: make(map[string]*JobRecord)}
}

func (s *HeavyJobService) HandleReportGeneration(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "Idempotency-Key required", http.StatusBadRequest)
		return
	}

	s.mu.Lock()
	existing, found := s.jobs[key]
	if found {
		s.mu.Unlock()
		// Возвращаем текущее состояние работы (PROCESSING или COMPLETED)
		w.Header().Set("Content-Type", "application/json")
		w.Header().Set("X-Idempotent-State", string(existing.State))
		w.WriteHeader(http.StatusOK)
		_ = json.NewEncoder(w).Encode(existing)
		return
	}

	// Создаем новую операцию
	job := &JobRecord{
		ID:        fmt.Sprintf("job_%d", time.Now().UnixNano()),
		State:     JobStateProcessing,
		Progress:  10,
		CreatedAt: time.Now(),
	}
	s.jobs[key] = job
	s.mu.Unlock()

	// Запуск фоновой генерации
	go func(j *JobRecord) {
		time.Sleep(100 * time.Millisecond) // Имитация расчета
		s.mu.Lock()
		j.Progress = 100
		j.State = JobStateCompleted
		j.ResultURL = fmt.Sprintf("https://storage.yandexcloud.net/reports/%s.pdf", j.ID)
		s.mu.Unlock()
	}(job)

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusAccepted)
	_ = json.NewEncoder(w).Encode(job)
}

func main() {
	svc := NewHeavyJobService()
	key := "user-report-q4-2026"

	// 1. Первый запуск задачи
	req1 := httptest.NewRequest(http.MethodPost, "/reports", nil)
	req1.Header.Set("Idempotency-Key", key)
	rec1 := httptest.NewRecorder()
	svc.HandleReportGeneration(rec1, req1)
	fmt.Printf("Запрос 1 (Старт): HTTP %d, Body: %s", rec1.Code, rec1.Body.String())

	// 2. Повтор через 20мс: задача еще выполняется!
	time.Sleep(20 * time.Millisecond)
	req2 := httptest.NewRequest(http.MethodPost, "/reports", nil)
	req2.Header.Set("Idempotency-Key", key)
	rec2 := httptest.NewRecorder()
	svc.HandleReportGeneration(rec2, req2)
	fmt.Printf("Запрос 2 (В процессе): HTTP %d, State: %s, Body: %s",
		rec2.Code, rec2.Header().Get("X-Idempotent-State"), rec2.Body.String())

	// 3. Повтор через 150мс: задача завершена!
	time.Sleep(150 * time.Millisecond)
	req3 := httptest.NewRequest(http.MethodPost, "/reports", nil)
	req3.Header.Set("Idempotency-Key", key)
	rec3 := httptest.NewRecorder()
	svc.HandleReportGeneration(rec3, req3)
	fmt.Printf("Запрос 3 (Финал): HTTP %d, State: %s, Body: %s",
		rec3.Code, rec3.Header().Get("X-Idempotent-State"), rec3.Body.String())
}
```

## Под капотом

В распределенной архитектуре состояние задачи хранится в PostgreSQL или Redis Hash:
`HSET job:{id} state "PROCESSING" progress 45`
При получении запроса с тем же ключом сервер считывает `HGETALL` и формирует ответ. Когда фоновый воркер (Celery/Asynq) завершает генерацию файла в S3, он атомарно меняет `state` на `COMPLETED` и публикует событие в Redis PubSub для нотификации клиентов.

## Подводные камни

1. **Падение фонового воркера (Zombified Job):** Если воркер убит по OOM Killer, задача навсегда останется со статусом `PROCESSING`. Реализуйте Dead Man's Snitch или Heartbeat: если задача в статусе `PROCESSING` без обновлений более 5 минут, статус переводится в `FAILED`.
2. **Игнорирование отмены клиентом:** Если клиент разорвал соединение, фоновая задача может продолжать пожирать CPU. Передавайте `context.Context` с отменой.
3. **Хранение готовых бинарных файлов в теле ответа:** Никогда не сохраняйте PDF/ZIP в поле ответа таблицы идемпотентности! Сохраняйте только Pre-signed URL на S3/MinIO.

## На собеседовании

**Вопрос:** Как организовать защиту от «зависших задач» со статусом `PROCESSING`, если сервер аварийно перезагрузился во время расчета?
**Ответ:** Используется паттерн **Heartbeat / Lease Time**:
1. Воркер каждые \(N\) секунд обновляет поле `last_heartbeat_at = NOW()`.
2. Если при входящем запросе обнаруживается запись `PROCESSING`, но `NOW() - last_heartbeat_at > 2 * lease_time`, сервер считает предыдущий воркер погибшим.
3. Предыдущая задача аннулируется, а вычисление безопасно перезапускается с тем же `Idempotency-Key`.
