# Идемпотентная обработка входящих вебхуков (Webhook Callbacks)

## Условие

### Исходная формулировка

**Idempotency в Webhook Callbacks.**: Интегрируйте с Блоком 18: webhook receiver извлекает `Idempotency-Key` из payload (или header `X-Idempotency-Key`) и защищает от дублирования доставки. Покажите, что даже если провайдер шлёт дубль, downstream система обработает ровно один раз.

## Теория

Поставщики вебхуков (Stripe, GitHub, ЮKassa, Telegram Bot API) функционируют по модели доставки **At-least-once (как минимум один раз)**. Если наш сервер не ответил статусом `200 OK` за 5 секунд, провайдер повторяет отправку вебхука через 1 минуту, 5 минут, 1 час.

### Проблема уязвимости дублирования вебхуков:
Если вебхук об успешной оплате `payment.succeeded` обработан дважды, интернет-магазин может отгрузить товар дважды или начислить баланс повторно.

### Стандарт безопасного Webhook Receiver:
1. **Извлечение уникального ID события:**
   Внешние провайдеры всегда включают уникальный идентификатор события (например, `id: "evt_1NxABC123"` в теле JSON или заголовок `X-Event-ID`).
2. **Атомарная дедупликация (Inbox Pattern):**
   Перед выполнением логики сервис пытается зафиксировать `evt_id` в таблице `processed_webhooks`.
3. **Быстрый ACK (HTTP 200):**
   Если событие уже обработано ранее, сервер **немедленно возвращает `200 OK`**, подтверждая прием провайдеру, но полностью подавляет повторный вызов downstream-логики.

## Решение по шагам

1. Создадим модель вебхука `WebhookEvent` с полями `EventID`, `Type`, `Data`.
2. Реализуем хранилище обработанных событий `WebhookInbox`.
3. Напишем обработчик вебхуков, проверяющий наличие `EventID`.
4. Продемонстрируем, что троекратная отправка одного вебхука приводит к ровно одному вызову бизнес-логики и трем успешным ответам 200 OK.

## Код решения

**`webhook_idempotency.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"sync/atomic"
)

type WebhookEvent struct {
	ID        string `json:"id"`
	EventType string `json:"type"`
	Amount    int    `json:"amount"`
}

type WebhookReceiver struct {
	mu           sync.Mutex
	processedIDs map[string]bool
	ordersFilled int64
}

func NewWebhookReceiver() *WebhookReceiver {
	return &WebhookReceiver{processedIDs: make(map[string]bool)}
}

func (recv *WebhookReceiver) HandleWebhook(w http.ResponseWriter, r *http.Request) {
	var event WebhookEvent
	if err := json.NewDecoder(r.Body).Decode(&event); err != nil {
		http.Error(w, "bad json", http.StatusBadRequest)
		return
	}

	// Идентификатор извлекается из заголовка или тела события
	eventID := event.ID
	if eventID == "" {
		eventID = r.Header.Get("X-Event-ID")
	}

	if eventID == "" {
		http.Error(w, "missing event id", http.StatusBadRequest)
		return
	}

	recv.mu.Lock()
	if recv.processedIDs[eventID] {
		recv.mu.Unlock()
		// КРИТИЧЕСКИ ВАЖНО: Возвращаем 200 OK, чтобы провайдер прекратил ретраи!
		w.Header().Set("X-Webhook-Duplicate", "true")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"already_processed"}`))
		fmt.Printf("[Webhook] Дублирующее событие %s проигнорировано.\n", eventID)
		return
	}

	// Фиксируем обработку
	recv.processedIDs[eventID] = true
	recv.mu.Unlock()

	// Вызов downstream бизнес-логики (отгрузка товара, отправка письма)
	atomic.AddInt64(&recv.ordersFilled, 1)
	fmt.Printf("[Webhook] Успешно обработано новое событие %s: отгрузка заказа на $%d!\n", eventID, event.Amount)

	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"status":"accepted"}`))
}

func main() {
	receiver := NewWebhookReceiver()

	webhookPayload := `{
		"id": "evt_stripe_payment_success_9988",
		"type": "charge.succeeded",
		"amount": 250
	}`

	// Симуляция 3 доставок одного вебхука от платежного шлюза
	for i := 1; i <= 3; i++ {
		req := httptest.NewRequest(http.MethodPost, "/webhooks/stripe", strings.NewReader(webhookPayload))
		rec := httptest.NewRecorder()

		receiver.HandleWebhook(rec, req)
		fmt.Printf("Попытка доставки #%d: HTTP %d (Duplicate Header: %s)\n",
			i, rec.Code, rec.Header().Get("X-Webhook-Duplicate"))
	}

	fmt.Printf("\nИТОГ: Количество отгрузок товаров клиенту: %d (должна быть ровно 1!)\n",
		atomic.LoadInt64(&receiver.ordersFilled))
}
```

ℹ️ Дедупликация входящих вебхуков: ответ 200 OK на дубли без повторного вызова логики

## Под капотом

Согласно документации Stripe Webhooks:
Если обработчик возвращает `500` или сетевой таймаут, Stripe повторяет отправку вебхука в течение 3 дней по экспоненциальному расписанию. При возврате `200` или `202` попытки немедленно прекращаются. Поэтому дублирующиеся вебхуки **всегда обязаны возвращать 200 OK**.

## Подводные камни

1. **Возврат ошибки 409 Conflict на повторный вебхук:** Провайдер вебхуков посчитает `409` ошибкой доставки и продолжит слать дублирующие запросы в течение трех суток.
2. **Асинхронная обработка без фиксации ID:** Запуск `go process(event)` до сохранения `event_id` в БД приведет к тому, что пришедший через 100 мс дубль не увидит записи и запустит вторую параллельную горутину.
3. **Отсутствие проверки криптографической подписи:** Проверяйте HMAC-SHA256 подпись (`Stripe-Signature`), иначе злоумышленник сможет отправить поддельный вебхук.

## На собеседовании

**Вопрос:** Как организовать прием вебхуков под нагрузкой 20 000 RPS, если downstream-обработка занимает 1.5 секунды?
**Ответ:** Применяется паттерн **Fast Ingest + Buffer Queue**:
1. Webhook Handler мгновенно проверяет HMAC-подпись.
2. Событие атомарно сохраняется в буферную очередь (Kafka / Redis Stream) с ключом партиционирования по `event_id`.
3. Сервер немедленно возвращает провайдеру `200 OK`.
4. Downstream-воркеры вычитывают сообщения из Kafka и выполняют дедупликацию через `INSERT INTO processed_events ... ON CONFLICT DO NOTHING` в фоновом режиме.
