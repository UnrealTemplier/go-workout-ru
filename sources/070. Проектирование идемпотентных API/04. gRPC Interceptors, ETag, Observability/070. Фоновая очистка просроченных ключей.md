# Фоновая очистка просроченных ключей идемпотентности (GC Job)

## Условие

70. **Очистка старых ключей идемпотентности.**: Реализуйте фоновую задачу, которая удаляет просроченные idempotency-ключи из БД/Redis, предотвращая бесконечный рост хранилища.

### Исходная формулировка

**Очистка старых ключей идемпотентности.**: Реализуйте фоновую задачу, которая удаляет просроченные idempotency-ключи из БД/Redis, предотвращая бесконечный рост хранилища.

## Теория

Без регулярной утилизации устаревших ключей идемпотентности любая СУБД со временем исчерпает ресурсы диска и оперативной памяти.

### Проблемы наивного удаления в PostgreSQL:
Запрос `DELETE FROM idempotency_keys WHERE created_at < NOW() - INTERVAL '24 HOURS';`
- На большой таблице сканирует миллионы строк.
- Блокирует страницы таблицы.
- Генерирует огромный объем WAL, перегружая репликацию.
- Оставляет «дыры» в страницах (Table Bloat), замедляя последующие запросы.

### Архитектура промышленного фонового GC:
1. **Итерация батчами (Batched Iteration):**
   Удаление выполняется небольшими порциями (по 1000–5000 строк) в цикле с паузой (sleep 100ms) между транзакциями.
2. **Контроль предельного времени выполнения:**
   Воркер запускается раз в час через Cron / Kubernetes CronJob.
3. **Партиционирование по суткам:**
   Для сверхнагруженных баз данных удаление целой партиции за день выполняется командой `DROP TABLE ...`, что мгновенно освобождает терабайты диска.

## Решение по шагам

1. Создадим потокобезопасный репозиторий с записями и метками `ExpiresAt`.
2. Реализуем фоновый воркер `IdempotencyGarbageCollector`.
3. Реализуем батчевое удаление устаревших данных с контролем контекста отмены (`context.Context`).
4. Продемонстрируем эффективную очистку просроченных записей без влияния на актуальные ключи.

## Код решения

**`gc_cleaner.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type ExpiringKeyRecord struct {
	Key       string
	ExpiresAt time.Time
}

type KeyStorage struct {
	mu   sync.Mutex
	data map[string]*ExpiringKeyRecord
}

func (s *KeyStorage) DeleteExpiredBatch(batchLimit int) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	var toDelete []string

	for k, rec := range s.data {
		if now.After(rec.ExpiresAt) {
			toDelete = append(toDelete, k)
			if len(toDelete) >= batchLimit {
				break
			}
		}
	}

	for _, k := range toDelete {
		delete(s.data, k)
	}

	return len(toDelete)
}

type IdempotencyGC struct {
	storage   *KeyStorage
	batchSize int
	interval  time.Duration
}

func NewIdempotencyGC(storage *KeyStorage, batchSize int, interval time.Duration) *IdempotencyGC {
	return &IdempotencyGC{
		storage:   storage,
		batchSize: batchSize,
		interval:  interval,
	}
}

func (gc *IdempotencyGC) Run(ctx context.Context) {
	ticker := time.NewTicker(gc.interval)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			fmt.Println("[GC] Остановка фонового сборщика мусора...")
			return
		case <-ticker.C:
			totalDeleted := 0
			for {
				deleted := gc.storage.DeleteExpiredBatch(gc.batchSize)
				totalDeleted += deleted
				if deleted < gc.batchSize {
					break // Все просроченные записи удалены
				}
				time.Sleep(10 * time.Millisecond) // Пауза для снятия нагрузки на CPU
			}
			if totalDeleted > 0 {
				fmt.Printf("[GC] Успешно очищено просроченных ключей: %d\n", totalDeleted)
			}
		}
	}
}

func main() {
	storage := &KeyStorage{data: make(map[string]*ExpiringKeyRecord)}

	// Заполняем хранилище: 3 просроченных ключа и 1 актуальный
	now := time.Now()
	storage.data["old_key_1"] = &ExpiringKeyRecord{Key: "old_key_1", ExpiresAt: now.Add(-2 * time.Hour)}
	storage.data["old_key_2"] = &ExpiringKeyRecord{Key: "old_key_2", ExpiresAt: now.Add(-1 * time.Hour)}
	storage.data["old_key_3"] = &ExpiringKeyRecord{Key: "old_key_3", ExpiresAt: now.Add(-10 * time.Minute)}
	storage.data["fresh_key_4"] = &ExpiringKeyRecord{Key: "fresh_key_4", ExpiresAt: now.Add(24 * time.Hour)}

	fmt.Printf("Ключей в хранилище до GC: %d\n", len(storage.data))

	gc := NewIdempotencyGC(storage, 2, 50*time.Millisecond)
	ctx, cancel := context.WithTimeout(context.Background(), 120*time.Millisecond)
	defer cancel()

	gc.Run(ctx)

	fmt.Printf("Ключей в хранилище после GC: %d (должен остаться только 'fresh_key_4')\n", len(storage.data))
}
```

ℹ️ Фоновый GC воркер с батчевым удалением устаревших ключей идемпотентности

## Под капотом

В PostgreSQL батчевое удаление оформляется в процедуру:
```sql
CREATE OR REPLACE PROCEDURE purge_expired_idempotency_keys(batch_size INT)
LANGUAGE plpgsql AS $$
DECLARE
    rows_deleted INT;
BEGIN
    LOOP
        DELETE FROM idempotency_keys
        WHERE ctid IN (
            SELECT ctid FROM idempotency_keys
            WHERE created_at < NOW() - INTERVAL '24 hours'
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        );
        GET DIAGNOSTICS rows_deleted = ROW_COUNT;
        COMMIT; -- Освобождаем блокировку и ресурсы WAL
        EXIT WHEN rows_deleted < batch_size;
        PERFORM pg_sleep(0.05);
    END LOOP;
END;
$$;
```
Фиксация `COMMIT` внутри цикла исключает удержание блокировок и рост WAL.

## Подводные камни

1. **Удаление в одной огромной транзакции:** Запрос `DELETE` без LIMIT приведет к блокировке всей таблицы и аварийной остановке сервиса.
2. **Отсутствие паузы (Sleep) между батчами:** Без пауз непрерывный цикл удаления утилизирует 100% дискового I/O, замедляя пользовательские запросы.
3. **Забытый индекс по полю даты истечения:** Без индекса `CREATE INDEX idx_idemp_expires ON idempotency_keys (expires_at)` каждый цикл очистки выполняет полное сканирование таблицы.

## На собеседовании

**Вопрос:** Как избежать деградации базы данных при удалении миллиардов устаревших записей идемпотентности?
**Ответ:** При нагрузках масштаба BigTech строчное удаление `DELETE` заменяют на **партиционирование по датам (Date Partitioning)**:
Таблица делится на суточные секции. Удаление данных за позавчерашний день выполняется мгновенной DDL-командой `DROP TABLE idempotency_keys_2026_09_04`. Это не генерирует строк в WAL, не требует `VACUUM` и занимает менее 10 миллисекунд.
