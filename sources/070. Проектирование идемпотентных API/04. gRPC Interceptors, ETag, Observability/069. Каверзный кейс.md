# Каверзный кейс: Несоответствие полезной нагрузки (Payload Mismatch -> 422)

## Условие

69. **[Каверзный кейс — Payload Mismatch]**: Клиент прислал запрос с ключом `KEY-1` и телом `{"amount": 100}`. Сервер обработал. Затем клиент присылает запрос с тем же ключом `KEY-1`, но телом `{"amount": 500}`. middleware не должна вернуть старый ответ на 100! Она должна вернуть ошибку `422 Unprocessable Entity` (или 400 Bad Request) с сообщением "Idempotency key was reused with different payload".

### Исходная формулировка

**[Каверзный кейс — Payload Mismatch]**: Клиент прислал запрос с ключом `KEY-1` и телом `{"amount": 100}`. Сервер обработал. Затем клиент присылает запрос с тем же ключом `KEY-1`, но телом `{"amount": 500}`. middleware не должна вернуть старый ответ! Она должна проверить хэш (SHA256) тела запроса. Если хэш не совпадает — возвращать `422 Unprocessable Entity` (Idempotency Key Reuse).

## Теория

Одной из грубейших брешей в защите API является слепое возвращение закэшированного ответа, если тело запроса было изменено.

### Сценарий эксплуатации или бага:
1. Запрос 1:
   - `Idempotency-Key: key-secret-99`
   - Payload: `{"recipient": "Ivan", "amount": 100}`
   - Сервер перевел Ивану $100 и закэшировал результат.
2. Запрос 2:
   - `Idempotency-Key: key-secret-99` (случайно переиспользован мобильным клиентом)
   - Payload: `{"recipient": "Petr", "amount": 500}`
3. Если сервер не проверяет хэш тела:
   - Он вернет: `{"status": "transferred", "recipient": "Ivan", "amount": 100}`.
   - Клиентское приложение покажет пользователю: «Успешно переведено Петру $500», хотя Петр не получил ни копейки!

### Поведение правильного шлюза:
Сравнение хэшей выявляет коллизию намерений:
`SavedHash != IncomingHash` \(\implies\) Немедленный ответ **`422 Unprocessable Entity`**.

## Решение по шагам

1. Реализуем компонент `StrictPayloadValidator`.
2. Сохраним первый запрос с SHA-256 хэшем полезной нагрузки.
3. Отправим второй запрос с тем же ключом, но измененной суммой.
4. Проверим, что сервер вернул статус 422 и детальное сообщение об ошибке.

## Код решения

**`payload_mismatch.go`**

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
)

type StoredTx struct {
	BodyHash     string
	ResponseCode int
	ResponseBody string
}

type PayloadMismatchGuard struct {
	mu      sync.Mutex
	history map[string]*StoredTx
}

func NewPayloadMismatchGuard() *PayloadMismatchGuard {
	return &PayloadMismatchGuard{history: make(map[string]*StoredTx)}
}

func hashBody(b []byte) string {
	sum := sha256.Sum256(b)
	return hex.EncodeToString(sum[:])
}

func (g *PayloadMismatchGuard) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "missing key", http.StatusBadRequest)
		return
	}

	body, _ := io.ReadAll(r.Body)
	reqHash := hashBody(body)

	g.mu.Lock()
	existing, exists := g.history[key]
	if exists {
		g.mu.Unlock()
		// Проверка соответствия тела запроса
		if existing.BodyHash != reqHash {
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusUnprocessableEntity)
			_ = json.NewEncoder(w).Encode(map[string]string{
				"error":   "idempotency_key_reuse_error",
				"message": "Idempotency key was reused with different payload",
			})
			return
		}

		// Тело совпадает — отдаем кэш
		w.Header().Set("Content-Type", "application/json")
		w.Header().Set("X-Idempotent-Replay", "true")
		w.WriteHeader(existing.ResponseCode)
		_, _ = w.Write([]byte(existing.ResponseBody))
		return
	}

	// Первое выполнение
	respBody := fmt.Sprintf(`{"payment":"success","payload":%s}`, string(body))
	g.history[key] = &StoredTx{
		BodyHash:     reqHash,
		ResponseCode: http.StatusCreated,
		ResponseBody: respBody,
	}
	g.mu.Unlock()

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
	_, _ = w.Write([]byte(respBody))
}

func main() {
	guard := NewPayloadMismatchGuard()
	key := "KEY-1"

	// 1. Первый запрос: amount = 100
	req1 := httptest.NewRequest(http.MethodPost, "/pay", strings.NewReader(`{"amount": 100}`))
	req1.Header.Set("Idempotency-Key", key)
	rec1 := httptest.NewRecorder()
	guard.ServeHTTP(rec1, req1)
	fmt.Printf("1. Запрос (amount: 100): Code = %d, Body = %s\n", rec1.Code, rec1.Body.String())

	// 2. Второй запрос: тот же ключ KEY-1, но amount = 500!
	req2 := httptest.NewRequest(http.MethodPost, "/pay", strings.NewReader(`{"amount": 500}`))
	req2.Header.Set("Idempotency-Key", key)
	rec2 := httptest.NewRecorder()
	guard.ServeHTTP(rec2, req2)
	fmt.Printf("2. Запрос (amount: 500): Code = %d (Ожидается 422), Body = %s\n", rec2.Code, rec2.Body.String())
}
```

ℹ️ Детекция Payload Mismatch: немедленный возврат HTTP 422 при изменении тела запроса

## Под капотом

Спецификация Stripe API:
Если запрос шлется с тем же ключом, но другими параметрами, Stripe возвращает ошибку 400 Bad Request:
```json
{
  "error": {
    "type": "idempotency_error",
    "message": "Keys for idempotent requests can only be used with the same parameters they were first used with."
  }
}
```
IETF Draft также рекомендует статус 422 Unprocessable Entity или 400 Bad Request.

## Подводные камни

1. **Сравнение JSON строк без нормализации пробелов:** Если клиент при первом запросе прислал `{"a":1}`, а при повторе `{"a": 1}`, посимвольный хэш не совпадет, вызвав ложный 422! Нормализуйте JSON перед хешированием.
2. **Игнорирование URL параметров (Query String):** Хэш обязан включать и Query параметры: `POST /transfer?urgent=true` vs `POST /transfer?urgent=false`.
3. **Отсутствие логирования инцидентов 422:** Частые ошибки 422 указывают на рассинхронизацию между фронтендом и бэкендом.

## На собеседовании

**Вопрос:** Как избежать ложных срабатываний детектора Payload Mismatch, если клиент переставляет поля в JSON-структуре местами?
**Ответ:** Используется **каноническая нормализация JSON (Canonical JSON / RFC 8785)**:
Перед расчетом SHA-256 JSON парсится в универсальное дерево объектов `map[string]any`, ключи всех объектов рекурсивно сортируются по алфавиту в лексикографическом порядке, удаляются незначимые пробелы и переносы строк, и лишь затем вычисляется криптографический хэш.
