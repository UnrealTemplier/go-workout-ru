# Идемпотентность длительных асинхронных операций (202 Accepted + Polling)

## Условие

49. **Idempotency + long-running operations**: Для async operations (например, video processing) возвращайте `202 Accepted` с `operation_id`. Client polls `GET /operations/{id}`. Idempotency key для initial POST.

### Исходная формулировка

**Idempotency + long-running operations**: Для async operations (например, video processing) возвращайте `202 Accepted` с `operation_id`. Client polls `GET /operations/{id}`. Idempotency key для initial POST.

## Теория

Далеко не все операции могут быть выполнены в рамках одного синхронного HTTP-запроса (например: рендеринг видео, пакетная генерация отчетов за год, обучение модели ML или импорт реестра на 1 млн строк).

### Архитектурный паттерн:
1. **Инициализация через POST с `Idempotency-Key`:**
   Клиент отправляет команду на запуск длительной операции:
   `POST /videos/transcode` с заголовком `Idempotency-Key: vid-task-123`.
2. **Немедленный ответ `202 Accepted`:**
   Сервер не держит соединение открытым, а регистрирует задачу в очереди (Kafka, RabbitMQ, Celery/Asynq) и возвращает:
   - Статус `202 Accepted`.
   - Заголовок `Location: /operations/op_998877`.
   - Заголовок `Retry-After: 10`.
3. **Повторный вызов POST с тем же ключом:**
   Если клиент повторит POST (например, из-за сетевого сбоя при приеме ответа), middleware не запускает второй фоновый процесс! Оно мгновенно возвращает тот же сохраненный `202 Accepted` со ссылкой на уже работающий `operation_id`.
4. **Опрос статуса клиентом (Polling):**
   Клиент опрашивает `GET /operations/op_998877` до перехода статуса из `PENDING` / `PROCESSING` в `COMPLETED`.

## Решение по шагам

1. Создадим модель фоновой задачи `AsyncOperation` со статусами `PROCESSING`, `SUCCESS`, `FAILED`.
2. Реализуем обработчик POST, проверяющий наличие задачи по ключу идемпотентности.
3. Если задача существует — возвращаем `202 Accepted` с уже созданным `operation_id`.
4. Реализуем обработчик GET для проверки готовности результата.

## Код решения

**`async_idempotency.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type OperationStatus string

const (
	StatusProcessing OperationStatus = "PROCESSING"
	StatusDone       OperationStatus = "DONE"
)

type AsyncOperation struct {
	ID        string          `json:"operation_id"`
	Status    OperationStatus `json:"status"`
	ResultURL string          `json:"result_url,omitempty"`
}

type AsyncManager struct {
	mu           sync.Mutex
	keysToOp     map[string]string          // idempotency_key -> operation_id
	operations   map[string]*AsyncOperation // operation_id -> data
	counter      int
}

func NewAsyncManager() *AsyncManager {
	return &AsyncManager{
		keysToOp:   make(map[string]string),
		operations: make(map[string]*AsyncOperation),
	}
}

func (m *AsyncManager) HandleCreate(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "Idempotency-Key header is required", http.StatusBadRequest)
		return
	}

	m.mu.Lock()
	defer m.mu.Unlock()

	// 1. Проверяем, создана ли уже операция для этого ключа
	if opID, exists := m.keysToOp[key]; exists {
		op := m.operations[opID]
		w.Header().Set("Location", "/operations/"+op.ID)
		w.Header().Set("X-Idempotent-Replay", "true")
		w.WriteHeader(http.StatusAccepted)
		_ = json.NewEncoder(w).Encode(op)
		return
	}

	// 2. Создаем новую асинхронную задачу
	m.counter++
	newOpID := fmt.Sprintf("op_%04d", m.counter)
	op := &AsyncOperation{
		ID:     newOpID,
		Status: StatusProcessing,
	}

	m.keysToOp[key] = newOpID
	m.operations[newOpID] = op

	// Имитируем запуск фонового воркера
	go func(id string) {
		time.Sleep(100 * time.Millisecond)
		m.mu.Lock()
		defer m.mu.Unlock()
		if target, ok := m.operations[id]; ok {
			target.Status = StatusDone
			target.ResultURL = fmt.Sprintf("https://cdn.example.com/videos/%s.mp4", id)
		}
	}(newOpID)

	w.Header().Set("Location", "/operations/"+newOpID)
	w.WriteHeader(http.StatusAccepted)
	_ = json.NewEncoder(w).Encode(op)
}

func main() {
	manager := NewAsyncManager()

	// Первый POST-запрос с ключом
	req1 := httptest.NewRequest(http.MethodPost, "/transcode", nil)
	req1.Header.Set("Idempotency-Key", "client-job-video-001")
	rec1 := httptest.NewRecorder()
	manager.HandleCreate(rec1, req1)
	fmt.Printf("POST 1: Status=%d, Body=%s", rec1.Code, rec1.Body.String())

	// Дублирующий POST-запрос с тем же ключом во время работы задачи
	req2 := httptest.NewRequest(http.MethodPost, "/transcode", nil)
	req2.Header.Set("Idempotency-Key", "client-job-video-001")
	rec2 := httptest.NewRecorder()
	manager.HandleCreate(rec2, req2)
	fmt.Printf("POST 2 (Retry): Status=%d, Replay=%s, Body=%s",
		rec2.Code, rec2.Header().Get("X-Idempotent-Replay"), rec2.Body.String())
}
```

## Под капотом

Согласно RFC 7231 (HTTP/1.1 Semantics):
Статус `202 Accepted` означает, что запрос принят в обработку, но обработка еще не завершена. Включение заголовка `Location` со ссылкой на ресурс состояния задачи регламентируется стандартом REST Asynchronous Processing Pattern. При повторе запроса семантика `202` остается идемпотентной: идентификатор задачи неизменен.

## Подводные камни

1. **Создание новой фоновой задачи при ретрае POST:** Если не сохранять маппинг `idempotency_key -> operation_id`, ретрай клиента запустит второй тяжелый процесс видео-кодирования, удвоив затраты на CPU GPU.
2. **Отсутствие срока хранения результатов задач:** Объекты завершенных операций должны иметь TTL, иначе память процесса или таблица задач переполнится.
3. **Бесконечный поллинг без backoff:** Клиенты должны увеличивать интервал между вызовами GET (например, 1s, 2s, 5s), иначе сервер опроса упадет от нагрузки.

## На собеседовании

**Вопрос:** Как избежать лавины GET-запросов (Polling Storm) при мониторинге состояния длительной операции тысячами клиентов?
**Ответ:**
1. Возвращать заголовок `Retry-After: 15`, регламентирующий минимальную паузу до следующего запроса.
2. Использовать **WebSocket** или **Server-Sent Events (SSE)** для пуш-уведомления клиента о завершении задачи вместо активного поллинга.
3. Кэшировать промежуточные ответы GET в CDN или Redis с коротким TTL (1–2 сек).
