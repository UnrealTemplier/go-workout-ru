# Частичная идемпотентность (Partial Idempotency) и семантика PATCH

## Условие

54. **Partial Idempotency.**: Реализуйте `PATCH /profile`. Первый запрос меняет `display_name`. Дубль с тем же key не должен откатить изменения (не replay, а ignore). Объясните разницу между «safe to retry» (операция идемпотентна по сути) и «replay exact response».

### Исходная формулировка

**Partial Idempotency.**: Реализуйте `PATCH /profile`. Первый запрос меняет `display_name`. Дубль с тем же key не должен откатить изменения (не replay, а ignore). Объясните разницу между «safe to retry» (операция идемпотентна по сути) и «replay exactly» (неприменимо к PATCH).

## Теория

Существует принципиальная разница между двумя концепциями:
1. **Идемпотентность по спецификации протокола (Idempotent by Design):**
   Методы HTTP `GET`, `PUT`, `DELETE` идемпотентны по определению RFC 7231.
   Например, вызов `PUT /users/1 { "email": "a@b.com" }` 10 раз подряд оставляет состояние ресурса неизменным. Повторный вызов безопасен (Safe to retry).
2. **Точное воспроизведение ответа (Exact Replay Idempotency):**
   Фиксация и возврат точной копии оригинального ответа (включая метки времени `updated_at`, ревизии и токены).

### Проблема Partial Idempotency в `PATCH /profile`:
Представьте сценарий:
- Время \(T_1\): Запрос 1 (`PATCH /profile { "name": "Alice" }`, `Key: 111`) → успешно меняет имя на `Alice`.
- Время \(T_2\): Другой запрос 2 (`PATCH /profile { "role": "Admin" }`) → меняет роль.
- Время \(T_3\): Ретрай Запроса 1 (`Key: 111`).

Если сервер при ретрае слепо накатит старые изменения или перезапишет весь объект из кэша, он затрет изменения, сделанные в момент \(T_2\)!
Правильное поведение:
- Middleware видит завершенный ключ `Key: 111`.
- Оно **не накатывает повторно изменения в базу**, а просто отдает клиенту сохраненный ответ момента \(T_1\) (или актуальное состояние ресурса), гарантируя невмешательство в параллельные поля.

## Решение по шагам

1. Создадим модель `UserProfile` с независимыми полями `DisplayName`, `Role`, `UpdatedAt`.
2. Реализуем обработчик `PATCH`, обновляющий только переданные поля.
3. Добавим уровень идемпотентности, который при повторном ключе игнорирует повторную модификацию базы и возвращает кэшированный ответ.
4. Продемонстрируем, что сторонние изменения профиля не портятся при ретрае старого PATCH-запроса.

## Код решения

**`partial_idempotency.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"time"
)

type UserProfile struct {
	DisplayName string    `json:"display_name"`
	Role        string    `json:"role"`
	UpdatedAt   time.Time `json:"updated_at"`
}

type ProfileService struct {
	mu      sync.Mutex
	profile UserProfile
	store   map[string]string // key -> cached json response
}

func (s *ProfileService) PatchProfile(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")

	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверяем ключ идемпотентности: Replay exact response, NOT re-applying mutation!
	if cachedResp, exists := s.store[key]; exists {
		w.Header().Set("Content-Type", "application/json")
		w.Header().Set("X-Idempotent-Action", "IGNORED_REPLAY")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(cachedResp))
		return
	}

	// 2. Применяем частичные изменения (Partial Update)
	var patchData map[string]string
	_ = json.NewDecoder(r.Body).Decode(&patchData)

	if name, ok := patchData["display_name"]; ok {
		s.profile.DisplayName = name
	}
	if role, ok := patchData["role"]; ok {
		s.profile.Role = role
	}
	s.profile.UpdatedAt = time.Now()

	respBytes, _ := json.Marshal(s.profile)
	if key != "" {
		s.store[key] = string(respBytes)
	}

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write(respBytes)
}

func main() {
	svc := &ProfileService{
		profile: UserProfile{DisplayName: "OldName", Role: "User", UpdatedAt: time.Now()},
		store:   make(map[string]string),
	}

	// Шаг 1: Клиент отправляет PATCH display_name = "Bob" с Idempotency-Key: patch-key-1
	req1 := httptest.NewRequest(http.MethodPatch, "/profile", strings.NewReader(`{"display_name":"Bob"}`))
	req1.Header.Set("Idempotency-Key", "patch-key-1")
	rec1 := httptest.NewRecorder()
	svc.PatchProfile(rec1, req1)
	fmt.Printf("Шаг 1 (PATCH Bob): %s\n", rec1.Body.String())

	// Шаг 2: Другой запрос меняет Role на "SuperAdmin"
	req2 := httptest.NewRequest(http.MethodPatch, "/profile", strings.NewReader(`{"role":"SuperAdmin"}`))
	rec2 := httptest.NewRecorder()
	svc.PatchProfile(rec2, req2)
	fmt.Printf("Шаг 2 (PATCH SuperAdmin): %s\n", rec2.Body.String())

	// Шаг 3: Клиент повторяет Запрос 1 из-за таймаута (Idempotency-Key: patch-key-1)
	req3 := httptest.NewRequest(http.MethodPatch, "/profile", strings.NewReader(`{"display_name":"Bob"}`))
	req3.Header.Set("Idempotency-Key", "patch-key-1")
	rec3 := httptest.NewRecorder()
	svc.PatchProfile(rec3, req3)
	fmt.Printf("Шаг 3 (Retry Bob): Action=%s\n", rec3.Header().Get("X-Idempotent-Action"))

	// Шаг 4: Проверяем актуальный профиль: роль SuperAdmin сохранена!
	fmt.Printf("\nИТОГОВЫЙ ПРОФИЛЬ: Name='%s', Role='%s'\n", svc.profile.DisplayName, svc.profile.Role)
}
```

ℹ️ Partial Idempotency: повторный PATCH игнорирует модификацию и не затирает параллельные поля

## Под капотом

Различие между семантикой PUT и PATCH в контексте идемпотентности:
- `PUT` заменяет ресурс целиком (`Full Replacement`). Если ресурс заменен дважды одним и тем же телом, итог эквивалентен.
- `PATCH` применяет дельту изменений (`Partial Modification`). Применение дельты \(A \to A'\) дважды может быть как безопасным (установить поле), так и опасным (например, инкремент поля `views = views + 1`).
Поэтому для неидемпотентных PATCH-операций `Idempotency-Key` обязателен!

## Подводные камни

1. **Откат к старому состоянию (State Regression):** Если middleware кэширует полный снимок базы данных и при ретрае восстанавливает его в БД, оно сотрет все последующие коммиты других пользователей.
2. **Инкрементные операции в PATCH:** Запрос `PATCH /account {"increment_balance": 50}` не идемпотентен без строгой блокировки по ключу.
3. **Игнорирование конфликтов версий:** Рекомендуется комбинировать PATCH с заголовком `If-Match: "<ETag>"`, отвергая устаревшие патчи кодом `412 Precondition Failed`.

## На собеседовании

**Вопрос:** В чем разница между свойствами «Safe», «Idempotent» и «Deterministic» в распределенных REST API?
**Ответ:**
1. **Safe (Безопасный):** Не изменяет состояние сервера (только чтение: `GET`, `HEAD`, `OPTIONS`).
2. **Idempotent (Идемпотентный):** Десятикратное повторение запроса приводит к тому же конечному состоянию системы, что и однократный вызов (`PUT`, `DELETE`, либо любой метод с `Idempotency-Key`).
3. **Deterministic (Детерминированный):** При одинаковых входных данных операция всегда возвращает идентичный результат. Запрос может быть идемпотентным, но недетерминированным (например, возвращать обновленный timestamp текущего времени сервера при каждом вызове).
