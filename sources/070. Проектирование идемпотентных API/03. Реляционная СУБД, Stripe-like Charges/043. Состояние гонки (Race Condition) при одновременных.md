# Состояние гонки (Race Condition) при одновременных запросах

## Условие

43. **Race Condition при одновременных запросах.**: Запустите 10 goroutine с одинаковым `Idempotency-Key`, обращающихся к endpoint. Покажите, что только один проходит, остальные получают cached response или `409`. Реализуйте через `SELECT FOR UPDATE` или `SETNX`.

### Исходная формулировка

**Race Condition при одновременных запросах.**: Запустите 10 goroutine с одинаковым `Idempotency-Key`, обращающихся к endpoint. Покажите, что только один проходит, остальные получают cached response или `409`. Реализуйте через `SELECT FOR UPDATE` или Redis Redlock (для distributed gateway).

## Теория

Классическая проблема наивной реализации идемпотентности заключается в проверке существования ключа перед записью («Check-Then-Act»):
```go
// АНТИПАТТЕРН! Состояние гонки!
if !store.Exists(key) {
    store.Save(key, "processing")
    processOrder()
}
```
Если 10 горутин одновременно выполнят условие `!store.Exists(key)`, все 10 потоков увидят, что ключа нет, и параллельно запустят `processOrder()`.

### Правильные механизмы устранения гонки:
1. **Redis `SET key value NX EX 30`:**
   Атомарная примитивная операция на стороне движка Redis. Возвращает `OK` только первому клиенту, остальным — `nil`.
2. **PostgreSQL Row-Level Locking (`SELECT FOR UPDATE` / `ON CONFLICT`):**
   Вставка строки `INSERT INTO idempotency_keys (key) VALUES ($1) ON CONFLICT (key) DO NOTHING;`
   База данных гарантирует, что только одна транзакция вставит запись благодаря уникальному индексу `B-Tree`.

## Решение по шагам

1. Напишем реализацию `SafeIdempotencyBarrier` с использованием мьютекса или атомарного Compare-And-Swap (CAS).
2. Создадим симуляцию тяжелой бизнес-операции с задержкой 50 мс.
3. Запустим 10 параллельных горутин с одинаковым ключом через `sync.WaitGroup`.
4. Зафиксируем распределение ответов: ровно 1 успешный исполнитель, остальные получают статус `409 Conflict` (или кэшированный ответ).

## Код решения

**`race_condition.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"sync/atomic"
	"time"
)

type AtomicBarrierStore struct {
	mu    sync.Mutex
	locks map[string]string // key -> status ("IN_PROGRESS", "DONE")
	resps map[string]string // key -> cached response
}

func NewAtomicBarrierStore() *AtomicBarrierStore {
	return &AtomicBarrierStore{
		locks: make(map[string]string),
		resps: make(map[string]string),
	}
}

// TryAcquire атомарно проверяет и занимает ключ (аналог SETNX в Redis)
func (s *AtomicBarrierStore) TryAcquire(key string) (acquired bool, cachedResp string) {
	s.mu.Lock()
	defer s.mu.Unlock()

	status, exists := s.locks[key]
	if !exists {
		s.locks[key] = "IN_PROGRESS"
		return true, ""
	}

	if status == "DONE" {
		return false, s.resps[key]
	}

	// Ключ в процессе выполнения другим потоком
	return false, ""
}

func (s *AtomicBarrierStore) Complete(key, response string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.locks[key] = "DONE"
	s.resps[key] = response
}

func main() {
	store := NewAtomicBarrierStore()
	var executionCounter int64

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := r.Header.Get("Idempotency-Key")
		acquired, cached := store.TryAcquire(key)

		if !acquired {
			if cached != "" {
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(cached))
				return
			}
			// Запрос в процессе выполнения
			w.Header().Set("Retry-After", "1")
			w.WriteHeader(http.StatusConflict)
			_, _ = w.Write([]byte(`{"error":"concurrent_conflict"}`))
			return
		}

		// Выполнение тяжелой бизнес-логики
		atomic.AddInt64(&executionCounter, 1)
		time.Sleep(50 * time.Millisecond) // Имитация работы с БД/внешним шлюзом

		resp := fmt.Sprintf(`{"payment_id":"pay_%d","status":"confirmed"}`, time.Now().UnixNano())
		store.Complete(key, resp)

		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(resp))
	})

	const concurrentWorkers = 10
	var wg sync.WaitGroup
	results := make([]int, concurrentWorkers)

	for i := 0; i < concurrentWorkers; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			req := httptest.NewRequest(http.MethodPost, "/pay", nil)
			req.Header.Set("Idempotency-Key", "global-tx-order-555")
			rec := httptest.NewRecorder()

			handler.ServeHTTP(rec, req)
			results[workerID] = rec.Code
		}(i)
	}

	wg.Wait()

	fmt.Println("Результаты конкурентного стресс-теста (10 параллельных запросов):")
	var count201, count409, count200 int
	for i, code := range results {
		fmt.Printf("  Горутина #%d: HTTP %d\n", i+1, code)
		switch code {
		case http.StatusCreated:
			count201++
		case http.StatusConflict:
			count409++
		case http.StatusOK:
			count200++
		}
	}

	fmt.Printf("\nИтог: Создано (201): %d | Конфликт (409): %d | Кэш (200): %d\n", count201, count409, count200)
	fmt.Printf("Реальных исполнений бизнес-логики: %d\n", atomic.LoadInt64(&executionCounter))
}
```

ℹ️ Стресс-тестирование 10 параллельных горутин с отсечением гонки через атомарный барьер

## Под капотом

На уровне ядра Linux и Redis:
Команда `SET key val NX` внутри Redis выполняется в однопоточном цикле обработки событий (`epoll/event loop`). Благодаря этому между операцией проверки отсутствия ключа и операцией записи нет временного зазора — они абсолютно неделимы.

В PostgreSQL при конкурентном выполнении:
`INSERT INTO idempotency_keys (key) VALUES ('k1') ON CONFLICT (key) DO NOTHING;`
движок захватывает эксклюзивную блокировку на бакет индекса (Index Tuple Lock), гарантируя строгую сериализацию вставок.

## Подводные камни

1. **Проверка ключа через GET перед SET:** Если код вызывает `redis.Get()` и затем `redis.Set()`, между ними успевают проскочить десятки горутин. Используйте только атомарные `SET NX` или Lua-скрипты.
2. **Deadlock при блокировке связанных таблиц:** Если один поток блокирует `idempotency_keys` затем `orders`, а второй наоборот — возникнет классический взаимный тупик (Deadlock). Порядок захвата ресурсов всегда должен быть детерминированным.
3. **Слишком длинный таймаут блокировки:** Если первая горутина зависла на 30 секунд, все остальные будут получать 409 или стоять в очереди. Устанавливайте контекстные таймауты (`context.WithTimeout`).

## На собеседовании

**Вопрос:** Как реализовать блокировку на уровне PostgreSQL без создания постоянной строки в таблице при каждом запросе?
**Ответ:** С помощью **PostgreSQL Advisory Locks**:
`SELECT pg_try_advisory_xact_lock(hashtext('idemp:' || key));`
Функция возвращает `true`, если блокировка на 64-битный хэш успешно захвачена текущей транзакцией, и `false`, если ключ уже удерживается параллельным запросом. Блокировка автоматически освобождается при завершении транзакции (`COMMIT` или `ROLLBACK`), не засоряя диск временными записями.
