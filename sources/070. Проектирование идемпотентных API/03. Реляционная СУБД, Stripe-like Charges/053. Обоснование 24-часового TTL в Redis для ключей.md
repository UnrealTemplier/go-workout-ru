# Обоснование 24-часового TTL в Redis для ключей идемпотентности

## Условие

53. **[TTL]**: Установи TTL для ключей идемпотентности в Redis на 24 часа. Объясни, почему хранить их вечно бессмысленно (клиенты редко ретраят запросы недельной давности).

### Исходная формулировка

**[TTL]**: Установи TTL для ключей идемпотентности в Redis на 24 часа. Объясни, почему хранить их вечно бессмысленно (клиенты редко ретраят запросы недельной давности).

## Теория

Установка 24-часового TTL (Time-To-Live) в Redis (`SET key val EX 86400`) является признанным стандартом в архитектуре распределенных систем.

### Почему вечное хранение бессмысленно и вредно:
1. **Распределение сетевых повторов (Retry Decay Curve):**
   Более 99.9% клиентских повторов происходят в первые 5 секунд после сбоя.
   Оставшиеся 0.09% (клиент был оффлайн в метро, перезапуск мобильного приложения) разрешаются в течение 1–4 часов.
   Вероятность повтора запроса через неделю практически равна нулю: за это время пользователь либо вручную пересоздал заказ, либо сессия авторизации истекла.
2. **Экспоненциальный рост оперативной памяти (RAM Cost):**
   При нагрузке 5 000 RPS хранение ключей в течение года потребует:
   $$5\,000 \times 86\,400 \times 365 \approx 157.6 \text{ миллиардов ключей}$$
   Даже при 200 байтах на запись это более **30 Терабайт дорогостоящей оперативной памяти Redis**!
3. **24 часа покрывают все регламентные окна обслуживания:**
   Суточный интервал гарантирует, что даже если дата-центр упал на несколько часов или очередь сообщений задержалась, все ретраи будут безопасно дедуплицированы.

## Решение по шагам

1. Создадим константу `DefaultIdempotencyTTL = 24 * time.Hour`.
2. Реализуем обертку над Redis-клиентом, принудительно выставляющую TTL при сохранении ключа.
3. Продемонстрируем автоматическое удаление ключей по истечении времени жизни.

## Код решения

**`ttl_twenty_four.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

const (
	// IdempotencyKeyTTL фиксирует 24-часовой горизонт безопасных повторов
	IdempotencyKeyTTL = 24 * time.Hour
)

type RedisIdempotencyService struct {
	ttl time.Duration
}

func NewRedisIdempotencyService() *RedisIdempotencyService {
	return &RedisIdempotencyService{ttl: IdempotencyKeyTTL}
}

func (s *RedisIdempotencyService) BuildRedisCommand(key, value string) string {
	// В реальном redis-go: client.Set(ctx, key, value, s.ttl)
	return fmt.Sprintf("SET %s %s EX %d", key, value, int(s.ttl.Seconds()))
}

func main() {
	svc := NewRedisIdempotencyService()
	cmd := svc.BuildRedisCommand("idem:usr_55:req_9988", `{"status":"paid"}`)

	fmt.Println("Команда записи в Redis с 24-часовым TTL:")
	fmt.Println(cmd)
	fmt.Printf("Время жизни ключа: %v (%d секунд)\n", svc.ttl, int(svc.ttl.Seconds()))
}
```

ℹ️ Установка 24-часового TTL (86400 сек) для безопасной и экономичной работы Redis

## Под капотом

Внутри ядра Redis механизм TTL работает гибридно:
1. **Пассивное удаление (Lazy Expire):** Когда клиент пытается прочитать ключ командой `GET`, Redis проверяет метку времени. Если время истекло — ключ немедленно удаляется и возвращается `nil`.
2. **Активное удаление (Active Periodic Expire):** 10 раз в секунду (`hz 10`) Redis сканирует случайную выборку из 20 ключей с установленным TTL. Если более 25% из них просрочены — цикл повторяется, предотвращая накопление мертвых ключей в RAM.

## Подводные камни

1. **Использование команды SET без указания EX:** Команда `redis.Set(key, val, 0)` создает вечный ключ. При тысячах запросов память кончится за считанные дни.
2. **Слишком маленький TTL (например, 30 секунд):** Если обработка заказа в распределенной саге занимает 40 секунд, ключ удалится раньше, чем закончится первый запрос, открывая окно для дублирования.
3. **Отсутствие Jitter на TTL при пакетных записях:** Если 1 миллион ключей записан в один момент с одинаковым TTL 86400, через 24 часа активный цикл очистки Redis вызовет скачок задержки (Latency Spike). Всегда добавляйте небольшой рандом к TTL (`ttl + rand(600)`).

## На собеседовании

**Вопрос:** Что произойдет, если клиент отправит запрос с тем же `Idempotency-Key` ровно через 24 часа и 1 минуту?
**Ответ:** Поскольку ключ в Redis уже удален сборщиком мусора, сервер воспримет этот запрос как абсолютно новый и выполнит бизнес-логику повторно. Поэтому на уровне продуктовой аналитики клиентам запрещено ретраить запросы старше 24 часов: при превышении этого порога клиентское приложение должно показать пользователю ошибку «Время сессии операции истекло, обновите страницу».
