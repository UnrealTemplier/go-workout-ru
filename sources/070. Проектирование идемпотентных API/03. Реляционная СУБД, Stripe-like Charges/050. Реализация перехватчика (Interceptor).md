# Реализация перехватчика (Interceptor) идемпотентности в gRPC

## Условие

50. **[Idempotency в gRPC]**: Реализуй перехватчик (Interceptor) для gRPC-сервера, который достает `Idempotency-Key` из метаданных запроса (`metadata.FromIncomingContext`) и применяет логику кэширования/дедупликации.

### Исходная формулировка

**[Idempotency в gRPC]**: Реализуй перехватчик (Interceptor) для gRPC-сервера, который достает `Idempotency-Key` из метаданных запроса (`metadata.FromIncomingContext`) и применяет логику кэширования/дедупликации.

## Теория

В микросервисных архитектурах на базе gRPC/Protobuf заголовок идемпотентности передается не через HTTP-заголовки напрямую, а через метаданные контекста gRPC (`google.golang.org/grpc/metadata`).

### Механика работы UnaryServerInterceptor:
1. **Извлечение метаданных:** Вызов `metadata.FromIncomingContext(ctx)` возвращает маппинг метаданных incoming RPC.
2. **Поиск ключа:** Ключ извлекается по имени `idempotency-key` (в gRPC metadata ключи всегда приводятся к нижнему регистру!).
3. **Проверка кэша:**
   - Если ключ найден и операция уже завершена: интерцептор сериализует сохраненный protobuf-ответ и возвращает его без вызова `handler(ctx, req)`.
   - Если ключ отсутствует: интерцептор регистрирует ключ, вызывает `handler(ctx, req)`, перехватывает результат и кэширует его.
4. **Коды ошибок gRPC:**
   При конфликте параллельного выполнения возвращается статус `codes.AlreadyExists` или `codes.Aborted`.

## Решение по шагам

1. Создадим эмулятор `grpc.UnaryServerInterceptor`.
2. Реализуем извлечение метаданных из контекста.
3. Реализуем кэширование произвольных сообщений `proto.Message` (или interface{}).
4. Продемонстрируем защиту от повторного вызова gRPC RPC-метода.

## Код решения

**`grpc_interceptor.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/metadata"
	"google.golang.org/grpc/status"
)

type GrpcCacheStore struct {
	mu      sync.Mutex
	records map[string]interface{}
}

func NewGrpcCacheStore() *GrpcCacheStore {
	return &GrpcCacheStore{records: make(map[string]interface{})}
}

// MockUnaryServerInterceptor реализует сигнатуру перехватчика gRPC
func IdempotencyUnaryInterceptor(store *GrpcCacheStore) func(
	ctx context.Context,
	req interface{},
	info string,
	handler func(ctx context.Context, req interface{}) (interface{}, error),
) (interface{}, error) {
	return func(
		ctx context.Context,
		req interface{},
		info string,
		handler func(ctx context.Context, req interface{}) (interface{}, error),
	) (interface{}, error) {
		md, ok := metadata.FromIncomingContext(ctx)
		if !ok {
			return handler(ctx, req)
		}

		// Метаданные в gRPC всегда в нижнем регистре!
		keys := md.Get("idempotency-key")
		if len(keys) == 0 || keys[0] == "" {
			return handler(ctx, req)
		}

		idempKey := keys[0]

		store.mu.Lock()
		if cachedResp, exists := store.records[idempKey]; exists {
			store.mu.Unlock()
			fmt.Printf("[gRPC Interceptor] Cache HIT для ключа %s! Пропускаем вызов сервиса.\n", idempKey)
			return cachedResp, nil
		}
		store.mu.Unlock()

		// Вызываем целевой RPC хэндлер
		resp, err := handler(ctx, req)
		if err != nil {
			return nil, err
		}

		// Сохраняем успешный RPC-ответ
		store.mu.Lock()
		store.records[idempKey] = resp
		store.mu.Unlock()

		return resp, nil
	}
}

type OrderResponse struct {
	OrderID string
	Status  string
}

func main() {
	store := NewGrpcCacheStore()
	interceptor := IdempotencyUnaryInterceptor(store)

	var rpcExecutionCount int64
	mockHandler := func(ctx context.Context, req interface{}) (interface{}, error) {
		atomic.AddInt64(&rpcExecutionCount, 1)
		return &OrderResponse{OrderID: "grpc_ord_777", Status: "APPROVED"}, nil
	}

	// 1. Первый gRPC RPC-вызов
	md1 := metadata.Pairs("idempotency-key", "grpc-client-key-01")
	ctx1 := metadata.NewIncomingContext(context.Background(), md1)
	resp1, err := interceptor(ctx1, "req_data", "/OrderService/CreateOrder", mockHandler)
	if err != nil {
		panic(err)
	}
	fmt.Printf("RPC Ответ 1: %+v\n", resp1)

	// 2. Повторный gRPC RPC-вызов с тем же ключом метаданных
	md2 := metadata.Pairs("idempotency-key", "grpc-client-key-01")
	ctx2 := metadata.NewIncomingContext(context.Background(), md2)
	resp2, err := interceptor(ctx2, "req_data", "/OrderService/CreateOrder", mockHandler)
	if err != nil {
		panic(err)
	}
	fmt.Printf("RPC Ответ 2: %+v\n", resp2)

	fmt.Printf("Итого вызовов целевого RPC метода: %d (должен быть 1)\n", atomic.LoadInt64(&rpcExecutionCount))
}
```

ℹ️ Перехватчик gRPC с извлечением Idempotency-Key из context metadata и кэшированием ответа

## Под капотом

В gRPC передача метаданных осуществляется через HTTP/2 заголовки. Метаданные сериализуются в HPACK-фреймы заголовков. 
Входящие метаданные (`metadata.IncomingContext`) нормализуются в gRPC рантайме: ключи преобразуются к lower-case (`strings.ToLower`). Поэтому поиск по `"Idempotency-Key"` завершится неудачей, правильный ключ — `"idempotency-key"`.

## Подводные камни

1. **Регистрозависимый поиск в gRPC Metadata:** Обращение `md["Idempotency-Key"]` вернет `nil`. gRPC строго нормализует заголовки HTTP/2 к нижнему регистру.
2. **Кэширование gRPC ошибок со статусом Unavailable:** Если нижележащий микросервис вернул ошибку `codes.Unavailable`, кэширование заблокирует работу клиента.
3. **Клонирование сообщений Proto:** Если возвращать указатель на закэшированный `proto.Message`, параллельные горутины могут случайно мутировать поля структуры в памяти. Используйте `proto.Clone(msg)` перед возвратом.

## На собеседовании

**Вопрос:** Какой статус gRPC следует вернуть клиенту, если в момент вызова уже идет обработка запроса с таким же `idempotency-key`?
**Ответ:** Рекомендуется вернуть `codes.Aborted` или `codes.AlreadyExists` с добавлением деталей ошибки через `status.WithDetails`:
```go
st := status.New(codes.Aborted, "concurrent request in progress")
stWithDetails, _ := st.WithDetails(&errdetails.RetryInfo{
    RetryDelay: durationpb.New(2 * time.Second),
})
return nil, stWithDetails.Err()
```
Это стандартный подход в gRPC для указания времени ожидания перед повторной попыткой.
