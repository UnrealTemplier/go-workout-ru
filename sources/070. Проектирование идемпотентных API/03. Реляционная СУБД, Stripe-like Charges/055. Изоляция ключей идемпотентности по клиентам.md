# Изоляция ключей идемпотентности по клиентам и тенантам (Key Scoping)

## Условие

55. **Idempotency key scope**: Key должен быть scoped к user/tenant. User A и User B могут использовать одинаковые keys без collision.

### Исходная формулировка

**Idempotency key scope**: Key должен быть scoped к user/tenant. User A и User B могут использовать одинаковые keys без collision.

## Теория

Глобальная уникальность строкового ключа `Idempotency-Key` — опасная иллюзия. Если ключ хранится в глобальном пространстве имен `idemp:{key}`:
1. **Уязвимость захвата ключей (Key Hijacking / Denial of Service):** Злоумышленник может сгенерировать простые ключи (`key-1`, `payment-01`) и заблокировать создание платежей для других пользователей.
2. **Утечка конфиденциальных данных:** Если User B случайно укажет тот же ключ, что User A, он получит кэшированный ответ User A с его персональными данными (PII)!
3. **Коллизии UUID v4:** Хотя вероятность коллизии случайна, в мультитенантных системах клиенты часто используют локальные счетчики (`order_1`, `order_2`).

### Правило композитного ключа (Scoped Key):
Ключ идемпотентности в обязательном порядке должен быть **составным**:
$$\text{StorageKey} = \text{TenantID} + ":" + \text{UserID} + ":" + \text{ClientID} + ":" + \text{IdempotencyKey}$$
В базе данных накладывается уникальный композитный индекс:
`UNIQUE (tenant_id, user_id, idempotency_key)`.

## Решение по шагам

1. Создадим структуру `RequestContext` с полями `TenantID`, `UserID`, `ClientKey`.
2. Реализуем функцию генерации изолированного ключа хранилища `FormatScopedKey(tenant, user, key string)`.
3. Создадим middleware, извлекающее контекст аутентификации (JWT / API-Key) перед формированием ключа.
4. Продемонстрируем, что два разных пользователя могут использовать абсолютно одинаковый `Idempotency-Key: pay-001` без коллизий и конфликтов.

## Код решения

**`scoped_keys.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type ScopedStore struct {
	mu      sync.Mutex
	records map[string]string // scopedKey -> response
}

func NewScopedStore() *ScopedStore {
	return &ScopedStore{records: make(map[string]string)}
}

// BuildScopeKey гарантирует полную изоляцию пространств имен разных тенантов и пользователей
func BuildScopeKey(tenantID, userID, clientKey string) string {
	return fmt.Sprintf("tenant:%s:user:%s:idemp:%s", tenantID, userID, clientKey)
}

func (s *ScopedStore) Save(scopedKey, response string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.records[scopedKey] = response
}

func (s *ScopedStore) Get(scopedKey string) (string, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	val, ok := s.records[scopedKey]
	return val, ok
}

func ScopedMiddleware(store *ScopedStore) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			tenantID := r.Header.Get("X-Tenant-ID")
			userID := r.Header.Get("X-User-ID")
			idempKey := r.Header.Get("Idempotency-Key")

			if tenantID == "" || userID == "" {
				http.Error(w, "missing authentication context", http.StatusUnauthorized)
				return
			}

			if idempKey == "" {
				next.ServeHTTP(w, r)
				return
			}

			scopedKey := BuildScopeKey(tenantID, userID, idempKey)

			// Проверяем изолированное хранилище
			if cached, ok := store.Get(scopedKey); ok {
				w.Header().Set("X-Scoped-Key", scopedKey)
				w.Header().Set("X-Cache", "HIT")
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(cached))
				return
			}

			rec := httptest.NewRecorder()
			next.ServeHTTP(rec, r)

			if rec.Code < 500 {
				store.Save(scopedKey, rec.Body.String())
			}

			w.Header().Set("X-Scoped-Key", scopedKey)
			w.Header().Set("X-Cache", "MISS")
			w.WriteHeader(rec.Code)
			_, _ = w.Write(rec.Body.Bytes())
		})
	}
}

func main() {
	store := NewScopedStore()

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		user := r.Header.Get("X-User-ID")
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(fmt.Sprintf(`{"owner":"%s","data":"success"}`, user)))
	})

	app := ScopedMiddleware(store)(handler)

	sharedKey := "duplicate-key-same-name-100"

	// 1. Запрос от User A
	reqA := httptest.NewRequest(http.MethodPost, "/items", nil)
	reqA.Header.Set("X-Tenant-ID", "company_alpha")
	reqA.Header.Set("X-User-ID", "alice")
	reqA.Header.Set("Idempotency-Key", sharedKey)
	recA := httptest.NewRecorder()
	app.ServeHTTP(recA, reqA)
	fmt.Printf("User Alice: Code=%d, Cache=%s, Scope=%s\nBody=%s\n\n",
		recA.Code, recA.Header().Get("X-Cache"), recA.Header().Get("X-Scoped-Key"), recA.Body.String())

	// 2. Запрос от User B с ТОЧНО ТАКИМ ЖЕ ключом "duplicate-key-same-name-100"
	reqB := httptest.NewRequest(http.MethodPost, "/items", nil)
	reqB.Header.Set("X-Tenant-ID", "company_alpha")
	reqB.Header.Set("X-User-ID", "bob")
	reqB.Header.Set("Idempotency-Key", sharedKey)
	recB := httptest.NewRecorder()
	app.ServeHTTP(recB, reqB)
	fmt.Printf("User Bob (тот же ключ!): Code=%d, Cache=%s, Scope=%s\nBody=%s\n\n",
		recB.Code, recB.Header().Get("X-Cache"), recB.Header().Get("X-Scoped-Key"), recB.Body.String())

	// 3. Повторный запрос от User Alice: попадает в кэш Алисы!
	reqA2 := httptest.NewRequest(http.MethodPost, "/items", nil)
	reqA2.Header.Set("X-Tenant-ID", "company_alpha")
	reqA2.Header.Set("X-User-ID", "alice")
	reqA2.Header.Set("Idempotency-Key", sharedKey)
	recA2 := httptest.NewRecorder()
	app.ServeHTTP(recA2, reqA2)
	fmt.Printf("User Alice Повтор: Code=%d, Cache=%s, Scope=%s\nBody=%s\n",
		recA2.Code, recA2.Header().Get("X-Cache"), recA2.Header().Get("X-Scoped-Key"), recA2.Body.String())
}
```

## Под капотом

В реляционных СУБД (PostgreSQL) композитный ключ поддерживается индексом:
```sql
CREATE TABLE idempotency_records (
    tenant_id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    idempotency_key VARCHAR(128) NOT NULL,
    response_payload JSONB NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    CONSTRAINT pk_idemp PRIMARY KEY (tenant_id, user_id, idempotency_key)
);
```
Благодаря композитному первичному ключу поиск `WHERE tenant_id = $1 AND user_id = $2 AND idempotency_key = $3` выполняется за константное время \(O(\log N)\) с гарантией физической изоляции данных.

## Подводные камни

1. **Доверие заголовкам от клиента:** Никогда не берите `X-User-ID` напрямую из недоверенного HTTP-запроса клиента! Идентификатор пользователя и тенанта должен извлекаться из проверенного криптографического JWT-токена или mTLS-сертификата.
2. **Отсутствие валидации длины ключа:** Клиент может прислать ключ длиной 10 мегабайт, переполнив буфер. Ограничивайте длину `idempotency_key` (например, не более 128 байт).
3. **Разделители в компонентах ключа:** Если идентификатор пользователя содержит символ двоеточия (`user:123`), используйте безопасное экранирование или хеширование составных частей.

## На собеседовании

**Вопрос:** Что может произойти, если сервис выполняет дедупликацию запросов ДО этапа аутентификации пользователя?
**Ответ:** Возникнет критическая уязвимость безопасности:
1. Неавторизованный атакующий может подобрать чужой `Idempotency-Key` и получить в ответе конфиденциальные данные чужой транзакции без прохождения авторизации.
2. Атакующий может «застолбить» ключ легитимного пользователя фиктивным запросом, заблокировав ему проведение реального платежа.
Проверка аутентификации и авторизации обязана предшествовать проверке идемпотентности.
