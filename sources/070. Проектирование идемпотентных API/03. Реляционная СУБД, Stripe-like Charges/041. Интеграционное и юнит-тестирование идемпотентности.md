# Интеграционное и юнит-тестирование идемпотентности API

## Условие

41. **Idempotency testing**: Напишите тесты, которые отправляют duplicate requests с тем же key и проверяют, что бизнес-логика выполняется только один раз.

### Исходная формулировка

**Idempotency testing**: Напишите тесты, которые отправляют duplicate requests с тем же key и проверяют, что бизнес-логика выполняется только один раз.

## Теория

Тестирование идемпотентности должно доказывать два обязательных постулата:
1. **Single Execution Invariant:** Бизнес-логика (списание денег, отправка нотификации, запись в хранилище) выполняется ровно один раз, сколько бы повторных запросов ни пришло.
2. **Identical Response Invariant:** Все последующие повторные запросы получают в точности тот же статус, заголовки и тело ответа, что и оригинальный запрос.

Для надежного тестирования в Go применяют:
- Табличные тесты (`table-driven tests`) для проверки позитивных и негативных сценариев.
- Запуск параллельных запросов через `sync.WaitGroup` для выявления состояния гонки (Race Condition).
- Проверку счетчика вызова реального бизнес-сервиса (через мок или `atomic.Int32`).

## Решение по шагам

1. Создадим обработчик `PaymentHandler`, инкрементирующий атомарный счетчик реальных списаний.
2. Обернем его в `IdempotencyMiddleware`.
3. Напишем Go-тест, отправляющий серию последовательных запросов с одинаковым ключом.
4. Проверим, что счетчик списаний равен ровно `1`.
5. Проверим, что коды ответа и ID транзакции во всех ответах строго совпадают.

## Код решения

**`idempotency_test.go`**

```go
package main

import (
	"encoding/json"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"sync/atomic"
	"testing"
)

type PaymentServiceMock struct {
	chargeCount int64
}

func (s *PaymentServiceMock) Charge(amount int) string {
	atomic.AddInt64(&s.chargeCount, 1)
	return "ch_success_999"
}

func TestIdempotentApi_DuplicateRequests(t *testing.T) {
	service := &PaymentServiceMock{}
	memStore := NewInFlightStore()

	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		chargeID := service.Charge(100)
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusCreated)
		_ = json.NewEncoder(w).Encode(map[string]string{
			"charge_id": chargeID,
			"status":    "paid",
		})
	})

	app := InFlightMiddleware(memStore, 5)(handler)

	idempotencyKey := "client-generated-uuid-v4-abc"
	var firstResponseBody string

	// 1. Первый запрос (создание ресурса)
	{
		req := httptest.NewRequest(http.MethodPost, "/charges", strings.NewReader(`{"amount":100}`))
		req.Header.Set("Idempotency-Key", idempotencyKey)
		rec := httptest.NewRecorder()

		app.ServeHTTP(rec, req)

		if rec.Code != http.StatusCreated {
			t.Fatalf("expected status 201, got %d", rec.Code)
		}
		firstResponseBody = rec.Body.String()
	}

	// 2. Серия повторных запросов (дубликаты)
	for i := 2; i <= 5; i++ {
		req := httptest.NewRequest(http.MethodPost, "/charges", strings.NewReader(`{"amount":100}`))
		req.Header.Set("Idempotency-Key", idempotencyKey)
		rec := httptest.NewRecorder()

		app.ServeHTTP(rec, req)

		if rec.Code != http.StatusCreated {
			t.Errorf("iteration %d: expected cached status 201, got %d", i, rec.Code)
		}
		if rec.Body.String() != firstResponseBody {
			t.Errorf("iteration %d: body mismatch! Expected %s, got %s", i, firstResponseBody, rec.Body.String())
		}
		if rec.Header().Get("X-Idempotent-Replay") != "true" {
			t.Errorf("iteration %d: expected header X-Idempotent-Replay: true", i)
		}
	}

	// 3. Проверка инварианта: бизнес-логика выполнилась ровно один раз!
	actualCharges := atomic.LoadInt64(&service.chargeCount)
	if actualCharges != 1 {
		t.Fatalf("CRITICAL INVARIANT BROKEN: Expected 1 charge, but executed %d times!", actualCharges)
	}
}

func main() {
	// Демонстрационный запуск тестовой логики в main
	t := &testing.T{}
	TestIdempotentApi_DuplicateRequests(t)
	if !t.Failed() {
		fmt.Println("Тест успешно пройден: ровно 1 списание при 5 запросах с одинаковым Idempotency-Key!")
	}
}
```

ℹ️ Автоматизированная проверка инварианта идемпотентности с использованием httptest

## Под капотом

При тестировании идемпотентности под нагрузкой критически важно запускать тесты с флагом `-race`:
`go test -race -v -count=10 ./...`
Детектор гонок компилятора Go вставляет специальные хуки на чтение и запись в память, выявляя конкурентные обращения к кэшу или БД без должной синхронизации (Mutex / CAS / Transactions).

## Подводные камни

1. **Несброшенное состояние между тестами:** Использование глобального хранилища без очистки приводит к эффекту ложного прохождения последующих тестов («тестовое загрязнение»).
2. **Тестирование только последовательных вызовов:** Последовательные тесты никогда не поймают гонку двух одновременных запросов. Обязательно тестируйте параллельный вызов через goroutines.
3. **Игнорирование проверки заголовков ответа:** Проверка только статус-кода не гарантирует, что клиент получит корректный `Content-Type`, `ETag` или специфичные кастомные заголовки.

## На собеседовании

**Вопрос:** Как протестировать граничный случай, когда клиент делает retry ровно в момент, пока первый запрос еще выполняется в базе данных?
**Ответ:** В тесте используется синхронизация через каналы или блокировки:
1. В мок бизнес-логики внедряется задержка через `blockChan := make(chan struct{})`.
2. Первая горутина запускает запрос и зависает в обработчике, удерживая ключ в статусе `IN_PROGRESS`.
3. Вторая горутина делает запрос с тем же ключом и утверждает получение статуса `409 Conflict` с заголовком `Retry-After`.
4. Тест закрывает `close(blockChan)`, позволяя первому запросу завершиться, после чего третий запрос подтверждает получение сохраненного ответа с флагом `X-Idempotent-Replay: true`.
