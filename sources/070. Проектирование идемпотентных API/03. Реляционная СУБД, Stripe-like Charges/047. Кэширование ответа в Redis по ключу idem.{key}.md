# Кэширование ответа в Redis по ключу idem:{key}

## Условие

47. **[Кэширование ответа]**: middleware сохраняет тело запроса и ответ (Status Code + Body) в Redis по ключу `idem:{key}`. При повторном запросе с тем же ключом middleware мгновенно возвращает закэшированный ответ, не пропуская запрос к обработчику.

### Исходная формулировка

**[Кэширование ответа]**: middleware сохраняет тело запроса и ответ (Status Code + Body) в Redis по ключу `idem:{key}`. При повторном запросе с тем же ключом middleware мгновенно возвращает закэшированный ответ, не пропуская запрос к обработчику.

## Теория

Для обеспечения полной прозрачности идемпотентного API повторный запрос клиента не просто должен игнорироваться сервером, а обязан вернуть в точности тот же результат, который вернул оригинальный вызов: статус-код (например, `201 Created`), ключевые заголовки (`Content-Type`, `ETag`) и тело (JSON payload).

В архитектурах с кэшированием в Redis:
1. Ключ формируется по конвенции: `idem:{tenant_id}:{idempotency_key}`.
2. Значением выступает сериализованная структура:
   ```json
   {
     "status_code": 201,
     "headers": {"Content-Type": "application/json"},
     "body": "{\"id\":\"ord_123\",\"status\":\"created\"}"
   }
   ```
3. При поступлении запроса middleware проверяет наличие ключа:
   - При наличии (Cache HIT): десериализует ответ, проставляет HTTP-заголовки, статус, тело и немедленно завершает вызов с добавлением служебного заголовка `X-Cache-Lookup: HIT`.
   - При отсутствии (Cache MISS): запрос пропускается к основному хэндлеру с перехватом через wrapper над `http.ResponseWriter`.

## Решение по шагам

1. Создадим структуру `CachedHTTPResponse` для сериализации кода, заголовков и полезной нагрузки.
2. Реализуем интерфейс хранилища `RedisClientMock` с операциями `Get` и `SetEx`.
3. Напишем HTTP Middleware, перехватывающее ответ обработчика.
4. Продемонстрируем мгновенную отдачу кэшированного ответа на повторный запрос без вызова целевого обработчика.

## Код решения

**`redis_cache.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"sync/atomic"
	"time"
)

type CachedPayload struct {
	StatusCode int               `json:"status_code"`
	Headers    map[string]string `json:"headers"`
	Body       string            `json:"body"`
}

type MockRedisClient struct {
	mu   sync.RWMutex
	data map[string]string
}

func NewMockRedisClient() *MockRedisClient {
	return &MockRedisClient{data: make(map[string]string)}
}

func (c *MockRedisClient) Get(key string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	val, ok := c.data[key]
	return val, ok
}

func (c *MockRedisClient) SetEX(key, value string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[key] = value
}

func RedisCacheMiddleware(redis *MockRedisClient, ttl time.Duration) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			idempKey := r.Header.Get("Idempotency-Key")
			if idempKey == "" {
				next.ServeHTTP(w, r)
				return
			}

			redisKey := fmt.Sprintf("idem:%s", idempKey)

			// 1. Проверка наличия кэшированного ответа
			if rawVal, found := redis.Get(redisKey); found {
				var cached CachedPayload
				if err := json.Unmarshal([]byte(rawVal), &cached); err == nil {
					for k, v := range cached.Headers {
						w.Header().Set(k, v)
					}
					w.Header().Set("X-Cache-Lookup", "HIT")
					w.WriteHeader(cached.StatusCode)
					_, _ = w.Write([]byte(cached.Body))
					return
				}
			}

			// 2. Перехват оригинального ответа
			rec := httptest.NewRecorder()
			next.ServeHTTP(rec, r)

			// 3. Сохранение успешных ответов в Redis
			if rec.Code >= 200 && rec.Code < 500 {
				headersMap := make(map[string]string)
				for k := range rec.Header() {
					headersMap[k] = rec.Header().Get(k)
				}
				payload := CachedPayload{
					StatusCode: rec.Code,
					Headers:    headersMap,
					Body:       rec.Body.String(),
				}
				data, _ := json.Marshal(payload)
				redis.SetEX(redisKey, string(data), ttl)
			}

			// 4. Отправка клиенту
			for k, v := range rec.Header() {
				w.Header()[k] = v
			}
			w.Header().Set("X-Cache-Lookup", "MISS")
			w.WriteHeader(rec.Code)
			_, _ = w.Write(rec.Body.Bytes())
		})
	}
}

func main() {
	redis := NewMockRedisClient()
	var handlerExecutions int64

	businessHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		atomic.AddInt64(&handlerExecutions, 1)
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"account_id":"acc_99","status":"activated"}`))
	})

	app := RedisCacheMiddleware(redis, 24*time.Hour)(businessHandler)

	// Запрос 1: Промах кэша, вызов обработчика
	req1 := httptest.NewRequest(http.MethodPost, "/accounts", nil)
	req1.Header.Set("Idempotency-Key", "key-uuid-101")
	rec1 := httptest.NewRecorder()
	app.ServeHTTP(rec1, req1)
	fmt.Printf("Запрос 1: Code = %d, Lookup = %s\n", rec1.Code, rec1.Header().Get("X-Cache-Lookup"))

	// Запрос 2: Попадание в кэш Redis, мгновенный ответ
	req2 := httptest.NewRequest(http.MethodPost, "/accounts", nil)
	req2.Header.Set("Idempotency-Key", "key-uuid-101")
	rec2 := httptest.NewRecorder()
	app.ServeHTTP(rec2, req2)
	fmt.Printf("Запрос 2: Code = %d, Lookup = %s\n", rec2.Code, rec2.Header().Get("X-Cache-Lookup"))

	fmt.Printf("Итого вызовов бизнес-хэндлера: %d (ожидается: 1)\n", atomic.LoadInt64(&handlerExecutions))
}
```

## Под капотом

В Redis для оптимизации объема памяти часто используют HSET или сжатие Snappy/Gzip перед сохранением:
`HSET idem:{key} code 201 body <compressed_bytes> ct "application/json"`
`EXPIRE idem:{key} 86400`
Использование Redis Hashes снижает оверхед по аллокациям строк и позволяет обновлять статус ключа атомарно без полной перезаписи структуры.

## Подводные камни

1. **Неэкранированные спецсимволы в ключе:** Ключи, содержащие пробелы или управляющие символы, могут ломать протокол RESP в Redis. Всегда валидируйте входящий заголовок регулярным выражением `^[a-zA-Z0-9_\-\.]{1,128}$`.
2. **Сериализация больших тел ответов:** Кэширование ответов размером в десятки мегабайт быстро исчерпает оперативную память Redis (`maxmemory`). Ограничивайте размер кэшируемого тела (например, до 128 Кб).
3. **Отсутствие проверки заголовка Content-Type:** Если клиент ожидает JSON, а кэш отдал `text/plain`, клиентский парсер упадет с синтаксической ошибкой.

## На собеседовании

**Вопрос:** Как защитить Redis от нехватки оперативной памяти при агрессивных DDoS-атаках случайными уникальными ключами идемпотентности?
**Ответ:**
1. Настроить политику вытеснения ключей `maxmemory-policy volatile-lru` или `volatile-lfu`.
2. Перед записью ключа в Redis пропускать запрос через **Rate Limiter** (Token Bucket) по IP/API-key.
3. Валидировать формат ключа (UUID v4) до обращения к хранилищу.
4. Использовать фильтр Блума (Bloom Filter) на шлюзе для быстрого отсечения мусорных ключей.
