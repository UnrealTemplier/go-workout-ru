# Redis vs Реляционная СУБД для хранения ключей идемпотентности

## Условие

    * DB: slower (ms), но reliable
    Используйте Redis для high-volume, DB для critical operations.

### Исходная формулировка

**Redis vs DB для idempotency:**
* Redis: faster (μs), но может потерять данные (если не persistence)
* DB: slower (ms), но reliable
Используйте Redis для high-volume, DB для critical operations.

## Теория

Выбор между In-Memory хранилищем (Redis) и реляционной СУБД (PostgreSQL, MySQL) для слоя идемпотентности определяет баланс между производительностью (Latency, Throughput) и финансовой надежностью (ACID, Durability).

### Сравнительный анализ характеристик:

| Критерий | Redis (In-Memory Key-Value) | PostgreSQL (RDBMS) |
| :--- | :--- | :--- |
| **Задержка (Latency)** | 0.2 – 1.0 мс (субмиллисекунды) | 5 – 25 мс (дисковый I/O, WAL, блокировки) |
| **Пропускная способность** | До 100 000+ RPS на узел | 2 000 – 10 000 RPS на узел |
| **Гарантия сохранности** | Асинхронный AOF/RDB (риск потери секунд данных при крахе) | Полный ACID, синхронный fsync в WAL |
| **Атомарность с бизнес-данными**| Нет двухфазного коммита (возможен рассинхрон с БД) | **100% атомарность в одной транзакции** |
| **Управление временем жизни** | Нативный `EXPIRE` / TTL с автоматической сборкой | Требуются партиции (`pg_partman`) или cron-очистка |

### Архитектурное правило BigTech:
1. **Critical Financial / Order Operations:** Ключ идемпотентности сохраняется **в той же транзакции БД**, что и заказ/платеж (`INSERT INTO payments ...`, `INSERT INTO idempotency_keys ...`). Это исключает Dual-Write Problem.
2. **High-Volume / Non-Financial Operations:** (отправка пуш-уведомлений, постановка задач в очередь, аналитика) — используется Redis с нативным TTL.

## Решение по шагам

1. Создадим абстракцию `IdempotencyBackend` для переключения между стратегиями.
2. Реализуем `PostgresIdempotentStore`, сохраняющий ключ и payload в рамках единой транзакции базы данных.
3. Реализуем `RedisIdempotentStore` для легковесной высокопроизводительной дедупликации с автоматическим TTL.
4. Продемонстрируем гибридный подход: Redis для быстрой защиты от in-flight гонок на входе, PostgreSQL для постоянного аудиторского хранения.

## Код решения

**`storage_strategies.go`**

```go
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"time"
)

type StorageStrategy string

const (
	StrategyRDBMS StorageStrategy = "POSTGRESQL_TRANSACTIONAL"
	StrategyRedis StorageStrategy = "REDIS_IN_MEMORY"
)

type IdempotencyRecord struct {
	Key          string
	UserID       string
	ResponseCode int
	ResponseBody string
	CreatedAt    time.Time
}

// PaymentTxService демонстрирует ACID-идемпотентность в реляционной БД
type PaymentTxService struct {
	db *sql.DB
}

func (s *PaymentTxService) ProcessPayment(ctx context.Context, key, userID string, amount int) (string, error) {
	// В реальном коде открывается sql.Tx
	// 1. BEGIN TX
	// 2. INSERT INTO idempotency_keys (key, user_id, status) VALUES (...) ON CONFLICT (key, user_id) DO NOTHING;
	// 3. Если уже есть завершенная запись: ROLLBACK и вернуть сохраненный ответ
	// 4. Выполнить списание: UPDATE accounts SET balance = balance - amount WHERE user_id = ...
	// 5. Обновить статус idempotency_keys на 'COMPLETED'
	// 6. COMMIT TX
	return fmt.Sprintf("txn_pg_%d", time.Now().UnixNano()), nil
}

// HybridIdempotencyGateway объединяет Redis для быстрого in-flight замка и Postgres для хранения
type HybridIdempotencyGateway struct {
	redisConnected bool
	dbConnected    bool
}

func (g *HybridIdempotencyGateway) RouteStrategy(isFinancial bool) StorageStrategy {
	if isFinancial {
		// Финансовые транзакции требуют строгого ACID и хранения в БД
		return StrategyRDBMS
	}
	// Пуши, аналитика, генерация отчетов — идут через быстрый Redis
	return StrategyRedis
}

func main() {
	gateway := &HybridIdempotencyGateway{redisConnected: true, dbConnected: true}

	fmt.Println("Маршрутизация стратегий идемпотентности:")
	fmt.Printf("1. Списание баланса $500: %s\n", gateway.RouteStrategy(true))
	fmt.Printf("2. Отправка SMS-кода авторизации: %s\n", gateway.RouteStrategy(false))
	fmt.Printf("3. Создание билета техподдержки: %s\n", gateway.RouteStrategy(false))
	fmt.Printf("4. Оформление кредита: %s\n", gateway.RouteStrategy(true))
}
```

ℹ️ Разделение стратегий: реляционный ACID для критических операций и In-Memory для High-Volume

## Под капотом

Проблема Dual-Write при раздельном использовании Redis и SQL:
Если сервис обновляет баланс в PostgreSQL, а затем планирует сохранить результат в Redis:
1. База закоммитила списание.
2. Инстанс сервиса внезапно завершился по SIGKILL до вызова `redis.Set(...)`.
3. Клиент не получил ответ и делает повторный запрос.
4. Redis пуст! Запрос повторно проходит в БД и списывает средства второй раз.

Именно поэтому финансовые транзакции используют **Transactional Outbox / Idempotency Table** в одной локальной транзакции с бизнес-таблицами через `sql.Tx`.

## Подводные камни

1. **Использование Redis без Fallback для биллинга:** Сбой репликации Redis Sentinel или перезапуск пода без RDB/AOF приведет к повторным неконтролируемым списаниям средств клиентов.
2. **Разрастание таблицы в PostgreSQL:** Без регулярного партиционирования по дням таблица `idempotency_keys` вырастает до сотен миллионов строк, замедляя индексы `B-Tree` и вытесняя горячие страницы из `shared_buffers`.
3. **Отсутствие таймаутов на advisory locks:** Зависшая транзакция в PostgreSQL может заблокировать advisory lock и вызвать дефицит пула соединений (`max_connections`).

## На собеседовании

**Вопрос:** Как организовать безопасное хранение ключей идемпотентности при нагрузке 50 000 RPS, если финансовая транзакция требует ACID?
**Ответ:** Используется гибридная двухфазная архитектура:
1. На Edge / API Gateway уровне Redis используется только как быстрый in-flight распределенный лок (`SET key NX EX 30`) для отсечения дублей в пределах микросекунд.
2. В основном биллинговом сервисе проверка и сохранение ключа осуществляются в единой транзакции PostgreSQL с уникальным ограничением `CONSTRAINT uq_idemp UNIQUE (user_id, idempotency_key)`.
3. После успешного коммита транзакции итоговый ответ дублируется в Redis с TTL 24 часа для кэширования ответов на последующие ретраи без нагрузки на БД.
