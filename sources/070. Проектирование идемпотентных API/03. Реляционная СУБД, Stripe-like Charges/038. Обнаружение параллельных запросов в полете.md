# Обнаружение параллельных запросов в полете (In-Flight Detection)

### Исходная формулировка

**In-flight Detection.**: Если запрос с тем же key выполняется прямо сейчас, верните `409 Conflict` или `429` с `Retry-After`. Реализуйте через Redis `SET key "in-flight" NX EX 60` или PostgreSQL advisory lock. Объясните, почему важно не дублировать операцию, пока предыдущая не завершена.

## Теория

При проектировании идемпотентных API критически важно обрабатывать сценарий, когда повторный запрос с тем же `Idempotency-Key` поступает на сервер **до** того, как завершилась обработка первого запроса (in-flight request). Такая ситуация возникает при сетевых таймаутах на стороне клиента, агрессивных повторных отправках (retries) или случайном дабл-клике пользователя.

Если сервер не отслеживает состояние «в процессе обработки», оба запроса одновременно пройдут к бизнес-логике, что вызовет классическое состояние гонки (Race Condition), двойное списание средств или повреждение инвариантов БД.

Стандартный протокол обработки in-flight запросов:
1. **Атомарный захват блокировки (Lock Acquisition):**
   При входе в middleware выполняется атомарная операция фиксации состояния `in-progress` (например, Redis `SET key "in-progress" NX EX 60` или PostgreSQL `pg_try_advisory_xact_lock`).
2. **Обработка конфликта (Conflict Handling):**
   Если ключ уже существует со статусом `in-progress`, сервер немедленно прерывает обработку и возвращает статус:
   - `409 Conflict` с заголовком `Retry-After: 2` (рекомендовано Stripe/IETF draft), сообщая клиенту, что операция уже выполняется и повтор следует отложить.
   - Либо `429 Too Many Requests` с указанием времени ожидания.
3. **Сохранение финала или снятие блокировки:**
   По завершении успешной обработки статус меняется на `completed` с сохранением кода ответа и тела. В случае паники или фатального сбоя временный ключ удаляется, чтобы дать клиенту возможность повторить операцию.

## Решение по шагам

1. Создадим интерфейс `IdempotencyStore` с методами `TryLock(ctx, key string, ttl time.Duration) (bool, error)`, `SaveResponse(ctx, key string, resp CachedResponse) error` и `Unlock(ctx, key string) error`.
2. Реализуем In-Memory хранилище с `sync.Mutex` для демонстрации атомарных переходов состояний (`StatusInProgress`, `StatusCompleted`).
3. Напишем HTTP Middleware, проверяющее наличие заголовка `Idempotency-Key`.
4. Если запись уже завершена (`StatusCompleted`), возвращаем сохраненный ответ с заголовком `X-Cache-Lookup: HIT`.
5. Если ключ занят (`StatusInProgress`), выставляем заголовок `Retry-After: 2` и отдаем HTTP-код `409 Conflict`.
6. Если ключ свободен, переводим в `StatusInProgress`, выполняем целевой обработчик через `httptest.ResponseRecorder` и сохраняем ответ.

## Код решения

**`inflight.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type ExecutionStatus string

const (
	StatusInProgress ExecutionStatus = "IN_PROGRESS"
	StatusCompleted  ExecutionStatus = "COMPLETED"
)

type SavedResponse struct {
	StatusCode int               `json:"status_code"`
	Headers    map[string]string `json:"headers"`
	Body       []byte            `json:"body"`
}

type Record struct {
	Status    ExecutionStatus
	Response  SavedResponse
	ExpiresAt time.Time
}

type InFlightStore struct {
	mu      sync.Mutex
	records map[string]*Record
}

func NewInFlightStore() *InFlightStore {
	return &InFlightStore{
		records: make(map[string]*Record),
	}
}

var ErrInFlight = errors.New("request already in flight")

func (s *InFlightStore) AcquireOrGet(key string, ttl time.Duration) (*Record, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	rec, exists := s.records[key]
	now := time.Now()

	if exists && rec.ExpiresAt.After(now) {
		if rec.Status == StatusInProgress {
			return nil, ErrInFlight
		}
		return rec, nil
	}

	// Захватываем блокировку in-flight
	s.records[key] = &Record{
		Status:    StatusInProgress,
		ExpiresAt: now.Add(ttl),
	}
	return nil, nil
}

func (s *InFlightStore) Complete(key string, resp SavedResponse, ttl time.Duration) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.records[key] = &Record{
		Status:    StatusCompleted,
		Response:  resp,
		ExpiresAt: time.Now().Add(ttl),
	}
}

func (s *InFlightStore) Release(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.records, key)
}

func InFlightMiddleware(store *InFlightStore, ttl time.Duration) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" {
				next.ServeHTTP(w, r)
				return
			}

			rec, err := store.AcquireOrGet(key, ttl)
			if errors.Is(err, ErrInFlight) {
				w.Header().Set("Retry-After", "2")
				w.Header().Set("Content-Type", "application/json")
				w.WriteHeader(http.StatusConflict)
				_ = json.NewEncoder(w).Encode(map[string]string{
					"error":   "concurrent_request",
					"message": "Another request with this idempotency key is currently processing. Please retry shortly.",
				})
				return
			}

			if rec != nil && rec.Status == StatusCompleted {
				for k, v := range rec.Response.Headers {
					w.Header().Set(k, v)
				}
				w.Header().Set("X-Idempotent-Replay", "true")
				w.WriteHeader(rec.Response.StatusCode)
				_, _ = w.Write(rec.Response.Body)
				return
			}

			recWriter := httptest.NewRecorder()
			var succeeded bool
			defer func() {
				if !succeeded {
					store.Release(key)
				}
			}()

			next.ServeHTTP(recWriter, r)

			if recWriter.Code < 500 {
				headers := make(map[string]string)
				for k := range recWriter.Header() {
					headers[k] = recWriter.Header().Get(k)
				}
				saved := SavedResponse{
					StatusCode: recWriter.Code,
					Headers:    headers,
					Body:       recWriter.Body.Bytes(),
				}
				store.Complete(key, saved, 24*time.Hour)
				succeeded = true
			}

			for k, vals := range recWriter.Header() {
				for _, val := range vals {
					w.Header().Add(k, val)
				}
			}
			w.WriteHeader(recWriter.Code)
			_, _ = w.Write(recWriter.Body.Bytes())
		})
	}
}

func main() {
	store := NewInFlightStore()
	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(100 * time.Millisecond) // Имитация долгой работы
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"order_id":"ord_1001","status":"created"}`))
	})

	mw := InFlightMiddleware(store, 10*time.Second)(handler)

	var wg sync.WaitGroup
	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			req := httptest.NewRequest(http.MethodPost, "/orders", nil)
			req.Header.Set("Idempotency-Key", "idemp-req-777")
			rec := httptest.NewRecorder()

			mw.ServeHTTP(rec, req)
			fmt.Printf("Worker #%d: Status = %d, Body = %s\n", id, rec.Code, rec.Body.String())
		}(i)
	}
	wg.Wait()
}
```

ℹ️ Обработка in-flight запросов: один получает 201 Created, параллельные — 409 Conflict с Retry-After

## Под капотом

В распределенной среде для in-flight detection используют Redis команду:
`SET idempotency:{tenant}:{key} "{\"status\":\"IN_PROGRESS\"}" NX EX 120`
Опция `NX` гарантирует атомарность: ключ установится только если его еще нет. Если ключ уже существует, команда возвратит `nil`, что на уровне приложения означает конфликт.

В PostgreSQL для этого применяется строчный замок:
`INSERT INTO idempotency_keys (key, status, created_at) VALUES ($1, 'IN_PROGRESS', NOW()) ON CONFLICT (key) DO NOTHING;`
Если количество вставленных строк равно 0, приложение выполняет:
`SELECT status, response_body FROM idempotency_keys WHERE key = $1 FOR UPDATE;`
Если статус равен `IN_PROGRESS`, транзакция завершается с возвратом HTTP 409, исключая гонки на уровне изоляции Read Committed.

## Подводные камни

1. **Зависание ключа при аварии (Lock Leak):** Если приложение упало по OOM или panic до вызова `Complete` или `Release`, ключ может остаться в состоянии `IN_PROGRESS` навсегда. Всегда используйте короткий TTL (например, 60–120 секунд) на фазу `IN_PROGRESS`.
2. **Отсутствие заголовка `Retry-After`:** Клиенты без четкого указания задержки могут начать отправлять запросы в цикле (busy waiting), перегружая шлюз.
3. **Неверный HTTP-статус:** Возврат `200 OK` или `500 Internal Server Error` вместо `409 Conflict` путает клиентские библиотеки и нарушает семантику HTTP.

## На собеседовании

**Вопрос:** Почему при получении второго идентичного запроса во время выполнения первого лучше вернуть `409 Conflict` с заголовком `Retry-After`, а не заблокировать поток до завершения первого запроса?
**Ответ:** Блокировка клиентского соединения (holding the connection) в ожидании первого запроса быстро исчерпывает пул горутин и сокетов сервера (head-of-line blocking), повышая риск каскадного отказа всего API Gateway. Возврат `409 Conflict` с `Retry-After` освобождает ресурсы сервера и перекладывает оркестрацию повтора на клиента с экспоненциальной задержкой (backoff).
