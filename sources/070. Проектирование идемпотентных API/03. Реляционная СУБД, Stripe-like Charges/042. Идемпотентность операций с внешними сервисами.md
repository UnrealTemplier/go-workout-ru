# Идемпотентность операций с внешними сервисами и допосылка

## Условие

42. **Идемпотентность операций с внешними сервисами.**: Доработайте middleware: если запрос уже обработан, но внешний сервис (например, платёжный шлюз) недополучил вызов в первой попытке (сбой после ответа клиенту), реализуйте механизм «допосылки» через Outbox.

### Исходная формулировка

**Идемпотентность операций с внешними сервисами.**: Доработайте middleware: если запрос уже обработан, но внешний сервис (например, платёжный шлюз) недополучил вызов в первой попытке (сбой после ответа клиенту), реализуйте механизм «допосылки» через фоновую задачу, не дублируя основную операцию.

## Теория

Сложнейший сценарий распределенных систем возникает при вызове сторонних внешних API (Payment Provider, SMS Gateway, Bank Processing), которые не участвуют в распределенной транзакции.

### Проблема «сбоя на границе»:
1. Наш сервис успешно списал внутренний баланс пользователя в PostgreSQL.
2. Наш сервис упал (или оборвалась сеть) ровно в момент вызова внешнего шлюза.
3. Клиент получил ошибку таймаута и делает повторный запрос с тем же `Idempotency-Key`.

Если мы просто отдадим клиенту «успешный кэшированный ответ», внешний платеж так и не будет отправлен (состояние рассинхрона).

### Решение через Transactional Outbox + Forward Recovery:
- Все внешние вызовы фиксируются в таблице `outbox_calls` **в той же транзакции БД**.
- При повторном запросе middleware видит: «Бизнес-операция зарегистрирована, но статус внешнего шлюза — `PENDING`».
- Фоновый воркер (или сам middleware) выполняет гарантированную допосылку внешнему сервису, передавая детерминированный `Idempotency-Key` (например, `idemp_outbox_{internal_id}`).

## Решение по шагам

1. Спроектируем модель `OutboxTask` со статусами `PENDING`, `DISPATCHED`, `FAILED`.
2. Реализуем атомарное создание платежа и задачи Outbox в одной транзакции.
3. Разработаем компонент `ForwardRecoveryWorker`, отвечающий за повторные попытки внешнего вызова с экспоненциальной задержкой.
4. Продемонстрируем передачу производного ключа идемпотентности во внешний шлюз.

## Код решения

**`external_idempotency.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxStatus string

const (
	OutboxPending    OutboxStatus = "PENDING"
	OutboxDispatched OutboxStatus = "DISPATCHED"
	OutboxFailed     OutboxStatus = "FAILED"
)

type OutboxTask struct {
	ID             string
	IdempotencyKey string
	ExternalURL    string
	Payload        string
	Status         OutboxStatus
	Attempts       int
}

type ExternalPaymentGateway interface {
	SendPayment(ctx context.Context, idempotencyKey, payload string) (string, error)
}

type MockStripeGateway struct {
	mu           sync.Mutex
	receivedKeys map[string]int
}

func (m *MockStripeGateway) SendPayment(ctx context.Context, key, payload string) (string, error) {
	m.mu.Lock()
	defer m.mu.Unlock()
	if m.receivedKeys == nil {
		m.receivedKeys = make(map[string]int)
	}
	m.receivedKeys[key]++
	return fmt.Sprintf("ext_tx_%s_attempt_%d", key, m.receivedKeys[key]), nil
}

type OutboxRelay struct {
	mu      sync.Mutex
	tasks   map[string]*OutboxTask
	gateway ExternalPaymentGateway
}

func NewOutboxRelay(gw ExternalPaymentGateway) *OutboxRelay {
	return &OutboxRelay{
		tasks:   make(map[string]*OutboxTask),
		gateway: gw,
	}
}

func (r *OutboxRelay) Enqueue(task *OutboxTask) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.tasks[task.ID] = task
}

func (r *OutboxRelay) ProcessPending(ctx context.Context) {
	r.mu.Lock()
	defer r.mu.Unlock()

	for _, task := range r.tasks {
		if task.Status == OutboxPending {
			// Передаем исходный или детерминированный ключ во внешний сервис!
			extID, err := r.gateway.SendPayment(ctx, task.IdempotencyKey, task.Payload)
			if err != nil {
				task.Attempts++
				if task.Attempts > 3 {
					task.Status = OutboxFailed
				}
				continue
			}
			task.Status = OutboxDispatched
			fmt.Printf("Успешная допосылка во внешний шлюз! Task: %s, ExtID: %s\n", task.ID, extID)
		}
	}
}

func main() {
	gateway := &MockStripeGateway{}
	relay := NewOutboxRelay(gateway)

	// Клиентский запрос сгенерировал задачу в локальной БД
	clientKey := "usr_req_9988_pay"
	task := &OutboxTask{
		ID:             "outbox_1",
		IdempotencyKey: fmt.Sprintf("stripe_%s", clientKey),
		ExternalURL:    "https://api.stripe.com/v1/charges",
		Payload:        `{"amount": 5000, "currency": "rub"}`,
		Status:         OutboxPending,
	}
	relay.Enqueue(task)

	// Воркер фоновой допосылки гарантирует доставку даже при сетевых сбоях
	relay.ProcessPending(context.Background())
}
```

ℹ️ Связка Outbox и детерминированного Idempotency Key для надежной интеграции с внешними API

## Под капотом

Детерминированная генерация ключа для внешнего сервиса:
Если внешний сервис требует `Idempotency-Key`, никогда не генерируйте случайный `uuid.New()` при повторной отправке!
Ключ для внешнего API должен строго вычисляться из первичного идентификатора операции:
`extKey = sha256.Sum256([]byte(localTransactionID + ":stripe_charge"))`
Это гарантирует, что даже если воркер Outbox перезапустится и отправит задачу повторно, внешний шлюз распознает дубль и не выполнит повторное списание.

## Подводные камни

1. **Генерация нового UUID при ретрае во внешний сервис:** Классический баг новичков — при сетевой ошибке генерировать новый ключ. Внешний сервис выполнит двойное списание!
2. **Синхронный вызов внешнего сервиса внутри транзакции БД:** Удержание транзакции PostgreSQL на время HTTP-запроса во внешний мир (который может длиться 10–30 секунд) быстро исчерпает все соединения к базе данных.
3. **Отсутствие DLQ (Dead Letter Queue):** Если внешний сервис постоянно возвращает `400 Bad Request` (невалидные данные), задача не должна блокировать воркер бесконечными ретраями.

## На собеседовании

**Вопрос:** Как избежать ситуации, когда наш сервис списал деньги у себя, но внешний банк не ответил вовремя, а затем сервис аварийно перезагрузился?
**Ответ:** Применяется паттерн **Transactional Outbox с двухфазным согласованием**:
1. Списание внутреннего счета и запись в таблицу `outbox` со статусом `PENDING` фиксируются в единой транзакции БД.
2. Внешний вызов выполняется строго асинхронно отдельным процессом (Outbox Processor) с передачей детерминированного ключа `external_idempotency_key = hash(transaction_id)`.
3. При отсутствии ответа воркер повторяет запрос с тем же ключом. Внешний шлюз вернет либо результат первой попытки, либо выполнит операцию ровно один раз.
