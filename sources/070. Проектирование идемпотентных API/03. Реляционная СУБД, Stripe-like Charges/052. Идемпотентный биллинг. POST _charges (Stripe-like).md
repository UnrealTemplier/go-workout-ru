# Идемпотентный биллинг: POST /charges (Stripe-like)

## Условие

52. **Idempotency для POST /charges (Stripe-like).**: Реализуйте endpoint создания платежа. Первый запрос с `Idempotency-Key: abc` создаёт charge и возвращает 201. Повторный запрос с тем же key возвращает уже созданный charge (201 или 200). Покажите, что баланс списывается только один раз.

### Исходная формулировка

**Idempotency для POST /charges (Stripe-like).**: Реализуйте endpoint создания платежа. Первый запрос с `Idempotency-Key: abc` создаёт charge и возвращает 201. Повторный запрос с тем же key возвращает уже созданный charge (201 или 200). Покажите, что деньги списаны ровно один раз. Объясните, почему `409` не подходит (клиент должен получить результат, а не ошибку).

## Теория

Создание платежа `POST /charges` — канонический пример, где идемпотентность является вопросом финансовой и юридической ответственности бизнеса.

### Жизненный цикл платежа:
1. Клиент инициирует списание $100 с заголовком `Idempotency-Key: ch_req_uuid_99`.
2. Сервер:
   - Проверяет баланс пользователя (например, $500).
   - Списывает $100 (остаток $400).
   - Создает транзакцию с ID `ch_12345`.
   - Сохраняет связку `(Idempotency-Key, ch_12345, HTTP 201)`.
   - Возвращает `201 Created` с деталями платежа.
3. Внезапный обрыв связи: клиент не получил ответ `201` из-за таймаута сети.
4. Клиентская библиотека выполняет автоматический retry с тем же `Idempotency-Key: ch_req_uuid_99`.
5. Сервер видит существующий ключ, достает готовый объект `ch_12345` и возвращает его без списания баланса! Баланс остается $400, а не $300.

## Решение по шагам

1. Создадим структуру счета пользователя `Account` со строгим балансом.
2. Реализуем обработчик `POST /charges`, выполняющий списание средств.
3. Интегрируем идемпотентный барьер.
4. Продемонстрируем серию из 3 вызовов: баланс уменьшается ровно один раз, все ответы возвращают одинаковый `ChargeID`.

## Код решения

**`charges_api.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type Account struct {
	mu      sync.Mutex
	Balance int
}

type ChargeRequest struct {
	Amount int `json:"amount"`
}

type ChargeResponse struct {
	ID        string `json:"id"`
	Amount    int    `json:"amount"`
	Remaining int    `json:"remaining_balance"`
	Status    string `json:"status"`
}

type BillingService struct {
	account *Account
	store   *SafeIdempotencyStore
	txCount int
}

func NewBillingService(initialBalance int) *BillingService {
	return &BillingService{
		account: &Account{Balance: initialBalance},
		store:   NewSafeIdempotencyStore(),
	}
}

func (b *BillingService) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "Idempotency-Key header is required", http.StatusBadRequest)
		return
	}

	// 1. Проверяем кэш выполненных платежей
	if cached, ok := b.store.Get(key); ok {
		w.Header().Set("Content-Type", "application/json")
		w.Header().Set("X-Idempotent-Replay", "true")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(cached))
		return
	}

	// 2. Атомарно занимаем ключ
	if !b.store.TryLock(key) {
		http.Error(w, `{"error":"in_progress"}`, http.StatusConflict)
		return
	}

	// 3. Выполняем финансовую операцию
	b.account.mu.Lock()
	defer b.account.mu.Unlock()

	var req ChargeRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		b.store.Unlock(key)
		http.Error(w, "invalid body", http.StatusBadRequest)
		return
	}

	if b.account.Balance < req.Amount {
		b.store.Unlock(key)
		http.Error(w, "insufficient funds", http.StatusUnprocessableEntity)
		return
	}

	// Списание средств
	b.account.Balance -= req.Amount
	b.txCount++
	chargeID := fmt.Sprintf("ch_tx_%05d", b.txCount)

	resp := ChargeResponse{
		ID:        chargeID,
		Amount:    req.Amount,
		Remaining: b.account.Balance,
		Status:    "succeeded",
	}

	data, _ := json.Marshal(resp)
	b.store.Commit(key, string(data))

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
	_, _ = w.Write(data)
}

func main() {
	billing := NewBillingService(1000) // Начальный баланс: $1000

	idempKey := "stripe_charge_key_abc_123"

	// Попытка 1: Списание $300
	req1 := httptest.NewRequest(http.MethodPost, "/v1/charges", bytes.NewReader([]byte(`{"amount":300}`)))
	req1.Header.Set("Idempotency-Key", idempKey)
	rec1 := httptest.NewRecorder()
	billing.ServeHTTP(rec1, req1)
	fmt.Printf("Попытка 1: Code=%d, Body=%s\n", rec1.Code, rec1.Body.String())

	// Попытка 2: Сетевой повтор с тем же ключом
	req2 := httptest.NewRequest(http.MethodPost, "/v1/charges", bytes.NewReader([]byte(`{"amount":300}`)))
	req2.Header.Set("Idempotency-Key", idempKey)
	rec2 := httptest.NewRecorder()
	billing.ServeHTTP(rec2, req2)
	fmt.Printf("Попытка 2 (Retry): Code=%d, Replay=%s, Body=%s\n",
		rec2.Code, rec2.Header().Get("X-Idempotent-Replay"), rec2.Body.String())

	// Попытка 3: Еще один повтор
	req3 := httptest.NewRequest(http.MethodPost, "/v1/charges", bytes.NewReader([]byte(`{"amount":300}`)))
	req3.Header.Set("Idempotency-Key", idempKey)
	rec3 := httptest.NewRecorder()
	billing.ServeHTTP(rec3, req3)
	fmt.Printf("Попытка 3 (Retry): Code=%d, Replay=%s, Body=%s\n",
		rec3.Code, rec3.Header().Get("X-Idempotent-Replay"), rec3.Body.String())

	fmt.Printf("\nИТОГ: Итоговый баланс счета: $%d (списание произошло ровно 1 раз!)\n", billing.account.Balance)
}
```

ℹ️ Идемпотентный эндпоинт POST /charges: ровно одно списание при серии повторных запросов

## Под капотом

В Stripe при создании платежа создается объект `Charge`. Запрос связывается с аккаунтом продавца. 
База данных использует транзакционную изоляцию `Serializable` или строчные блокировки `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE`. Запись в `idempotency_keys` и дебет счета фиксируются одним атомарным коммитом в WAL.

## Подводные камни

1. **Возврат обновленного баланса при повторе:** Обратите внимание: при повторе запроса возвращается сохраненный снимок ответа! Если между первой попыткой и повтором баланс изменился из-за других операций, повторный ответ должен вернуть исходное состояние или актуальный статус транзакции.
2. **Невозможность провести возврат (Refund):** Возврат средств — это отдельная новая операция с новым `Idempotency-Key`.
3. **Отсутствие проверки суммы:** Если в ретрае изменена сумма с $300 на $500, запрос должен быть отклонен статусом 400 Mismatch.

## На собеседовании

**Вопрос:** Если клиент шлет повторный запрос на создание платежа, должен ли сервер возвращать HTTP `201 Created` или `200 OK`?
**Ответ:** Согласно спецификации Stripe и IETF Idempotency Draft, допустимо возвращать как `201 Created` (оригинальный код ответа ресурса), так и `200 OK`. Однако критически важно добавить HTTP-заголовок `Idempotent-Replay: true`, чтобы клиентский SDK понимал, что запрос не создал новый ресурс, а вернул ранее зафиксированный результат.
