# Настройка TTL и стратегии очистки (Cleanup Job, pg_partman)

## Условие

48. **TTL и Cleanup.**: Настройте TTL для idempotency records: 24 часа для финансовых операций, 5 минут для idempotent-by-design операций (GET). Реализуйте cleanup job (cron или `pg_partman`). Объясните компромисс: короткий TTL позволяет дублирование, длинный — нагрузка на память.

### Исходная формулировка

**TTL и Cleanup.**: Настройте TTL для idempotency records: 24 часа для финансовых операций, 5 минут для idempotent-by-design операций (GET). Реализуйте cleanup job (cron или `pg_partman`). Объясните компромисс: короткий TTL позволяет дублирование, длинный — раздувает БД.

## Теория

Выбор времени жизни (TTL) записей идемпотентности — это фундаментальный архитектурный компромисс:
- **Слишком короткий TTL (например, 1 минута):** Риск повторного исполнения! Если клиент столкнулся с сетевым сбоем, завис в GC паузе или делал повтор с экспоненциальным бэкоффом через 70 секунд, сервер посчитает его запрос новым и выполнит двойное списание.
- **Слишком длинный TTL (например, 1 год / вечно):** Деградация хранилища! Таблица или кэш разрастаются до сотен гигабайт, B-Tree индексы перестают помещаться в RAM, наступает деградация I/O.

### Стандарты BigTech для TTL:
1. **Финансовые списания и транзакции (Charges, Refunds):** `TTL = 24..72 часа`.
2. **Асинхронные задачи (Long-running jobs):** `TTL = 7 дней`.
3. **Безопасные / идемпотентные по дизайну методы:** `TTL = 5..15 минут`.

### Стратегии очистки в БД:
- **Cron / Background Worker (`DELETE WHERE created_at < NOW() - INTERVAL '24h'`):** Вызывает деградацию из-за `VACUUM` и блокировок строк (Table Bloat).
- **Партиционирование по диапазону времени (`pg_partman`):** Таблица делится по суткам (`RANGE (created_at)`). Очистка старых данных происходит мгновенно через `DROP TABLE idempotency_keys_p2026_09_01`, что не создает никакой нагрузки на транзакционный журнал (WAL).

## Решение по шагам

1. Создадим менеджер политик TTL `TTLPolicyManager` с дифференцированными сроками жизни.
2. Реализуем фоновую задачу сборки мусора (Cleanup Job), удаляющую устаревшие записи пачками (Batched Deletion).
3. Продемонстрируем очистку записей без блокировки читателей.

## Код решения

**`cleanup_job.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OperationCategory string

const (
	CategoryFinancial    OperationCategory = "FINANCIAL"     // 24 часа
	CategoryAsyncJob     OperationCategory = "ASYNC_JOB"     // 72 часа
	CategorySafeByDesign OperationCategory = "SAFE_BY_DESIGN" // 5 минут
)

type TTLConfig struct {
	Durations map[OperationCategory]time.Duration
}

func DefaultTTLConfig() *TTLConfig {
	return &TTLConfig{
		Durations: map[OperationCategory]time.Duration{
			CategoryFinancial:    24 * time.Hour,
			CategoryAsyncJob:     72 * time.Hour,
			CategorySafeByDesign: 5 * time.Minute,
		},
	}
}

type IdempRecord struct {
	Key       string
	Category  OperationCategory
	ExpiresAt time.Time
}

type PersistentStoreWithCleanup struct {
	mu      sync.Mutex
	records map[string]*IdempRecord
}

func NewPersistentStore() *PersistentStoreWithCleanup {
	return &PersistentStoreWithCleanup{
		records: make(map[string]*IdempRecord),
	}
}

func (s *PersistentStoreWithCleanup) Insert(key string, cat OperationCategory, ttl time.Duration) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.records[key] = &IdempRecord{
		Key:       key,
		Category:  cat,
		ExpiresAt: time.Now().Add(ttl),
	}
}

// CleanupExpiredBatch удаляет просроченные ключи батчами для снижения нагрузки на CPU/Lock
func (s *PersistentStoreWithCleanup) CleanupExpiredBatch(batchSize int) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	var deletedKeys []string

	for k, rec := range s.records {
		if now.After(rec.ExpiresAt) {
			deletedKeys = append(deletedKeys, k)
			if len(deletedKeys) >= batchSize {
				break
			}
		}
	}

	for _, k := range deletedKeys {
		delete(s.records, k)
	}
	return len(deletedKeys)
}

func main() {
	cfg := DefaultTTLConfig()
	store := NewPersistentStore()

	// Добавляем тестовые ключи с разным сроком жизни
	store.Insert("tx-fin-01", CategoryFinancial, cfg.Durations[CategoryFinancial])
	store.Insert("job-sync-02", CategorySafeByDesign, -1*time.Minute) // Уже просрочен
	store.Insert("job-sync-03", CategorySafeByDesign, -2*time.Minute) // Уже просрочен

	fmt.Printf("Ключей до очистки: %d\n", len(store.records))

	// Запуск сборщика мусора
	deleted := store.CleanupExpiredBatch(100)
	fmt.Printf("Фоновый Cleanup Job удалил устаревших записей: %d\n", deleted)
	fmt.Printf("Ключей после очистки: %d\n", len(store.records))
}
```

## Под капотом

Скрипт создания партиционированной таблицы в PostgreSQL (`pg_partman`):
```sql
CREATE TABLE idempotency_keys (
    idempotency_key VARCHAR(128) NOT NULL,
    account_id VARCHAR(64) NOT NULL,
    response_code INT NOT NULL,
    response_body JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (created_at, account_id, idempotency_key)
) PARTITION BY RANGE (created_at);

-- Настройка pg_partman на автоматическое создание суточных секций и удаление партиций старше 3 дней
SELECT create_parent('public.idempotency_keys', 'created_at', 'native', 'daily');
UPDATE part_config SET retention = '3 days', retention_keep_table = false WHERE parent_table = 'public.idempotency_keys';
```
При такой схеме очистка `DROP TABLE` не сканирует строки и не генерирует `dead tuples` в PostgreSQL.

## Подводные камни

1. **Использование `DELETE FROM idempotency_keys WHERE expires_at < NOW()` без LIMIT:** На таблице в 50 млн строк один такой запрос заблокирует таблицы, вызовет спайк CPU и переполнит диск логами WAL.
2. **Хранение бесконечного TTL в Redis:** Redis по умолчанию настроен на `maxmemory-policy noeviction`. При заполнении памяти сервер начнет возвращать ошибку `OOM command not allowed`, парализуя все сервисы.
3. **Отсутствие индекса по `expires_at`:** При выполнении фонового удаления без индекса СУБД делает последовательное сканирование (`Seq Scan`) всей огромной таблицы.

## На собеседовании

**Вопрос:** Почему удаление старых записей через `DROP TABLE` в партициях значительно эффективнее классического SQL-запроса `DELETE`?
**Ответ:** 
1. В PostgreSQL операция `DELETE` не освобождает место на диске, а лишь помечает кортежи как «мертвые» (`dead tuples`), требуя последующего агрессивного `VACUUM`.
2. `DELETE` миллионов строк записывает гигабайты изменений в WAL, перегружая репликацию и дисковую подсистему.
3. `DROP TABLE` атомарно отвязывает файл сегмента на файловой системе ядра Linux через `unlink()`, освобождая дисковое пространство за миллисекунды без генерации WAL для каждой строки.
