# Клиентские повторы (Retries) с экспоненциальным бэкоффом и Jitter

## Условие

45. **Idempotency + retries**: Client retries с тем же key. Server возвращает cached response. Это safe retry.

### Исходная формулировка

**Idempotency + retries**: Client retries с тем же key. Server возвращает cached response. Это safe retry.

## Теория

Идемпотентность на стороне сервера теряет смысл, если клиент не умеет правильно выполнять повторные попытки (Safe Retries). 

### Золотое правило безопасного клиента:
- При любых сетевых сбоях (DNS error, connection reset, HTTP 500/502/503/504, timeout) клиент **обязан сохранять один и тот же `Idempotency-Key`** для всех попыток в рамках одной логической операции.
- Генерация нового ключа при ретрае превращает повтор в новую операцию, вызывая множественные списания.

### Алгоритм Full Jitter Exponential Backoff:
Повторные запросы без пауз вызывают эффект «громоподобного стада» (Thundering Herd Problem), окончательно добивая восстанавливающийся сервер.
Формула паузы перед следующей попыткой:
$$T_{\text{sleep}} = \text{random}(0, \min(T_{\text{max}}, T_{\text{base}} \times 2^{\text{attempt}}))$$
Случайный разброс (Jitter) размазывает всплеск повторных запросов во времени.

## Решение по шагам

1. Создадим кастомный HTTP-клиент `SafeRetryClient` с поддержкой идемпотентности.
2. Сгенерируем стабильный `Idempotency-Key` (UUID v4) перед первой попыткой.
3. Реализуем цикл повторов с экспоненциальной задержкой и полнодиапазонным джиттером.
4. Продемонстрируем, как клиент успешно получает кэшированный ответ сервера после серии сетевых сбоев.

## Код решения

**`retry_client.go`**

```go
package main

import (
	"context"
	"fmt"
	"math/rand"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"time"
)

type RetryPolicy struct {
	MaxRetries int
	BaseDelay  time.Duration
	MaxDelay   time.Duration
}

func calculateBackoffWithJitter(attempt int, policy RetryPolicy) time.Duration {
	multiplier := 1 << attempt
	temp := float64(policy.BaseDelay) * float64(multiplier)
	if temp > float64(policy.MaxDelay) {
		temp = float64(policy.MaxDelay)
	}
	// Full Jitter
	sleepDuration := time.Duration(rand.Float64() * temp)
	return sleepDuration
}

type IdempotentHttpClient struct {
	client *http.Client
	policy RetryPolicy
}

func (c *IdempotentHttpClient) ExecuteWithRetry(ctx context.Context, reqFactory func() (*http.Request, error), idempotencyKey string) (*http.Response, error) {
	var lastErr error

	for attempt := 0; attempt < c.policy.MaxRetries; attempt++ {
		req, err := reqFactory()
		if err != nil {
			return nil, err
		}

		// Заголовок идемпотентности НЕ меняется между попытками!
		req.Header.Set("Idempotency-Key", idempotencyKey)

		resp, err := c.client.Do(req.WithContext(ctx))
		if err == nil && resp.StatusCode < 500 && resp.StatusCode != http.StatusConflict {
			// Успех или постоянная клиентская ошибка — ретраить не нужно
			return resp, nil
		}

		lastErr = err
		backoff := calculateBackoffWithJitter(attempt, c.policy)
		fmt.Printf("Попытка #%d не удалась. Пауза перед ретраем (Jitter): %v\n", attempt+1, backoff)

		select {
		case <-time.After(backoff):
		case <-ctx.Done():
			return nil, ctx.Err()
		}
	}

	return nil, fmt.Errorf("exceeded max retries: %w", lastErr)
}

func main() {
	var serverAttempts int64

	// Тестовый сервер, падающий на первых 2 запросах
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		attempt := atomic.AddInt64(&serverAttempts, 1)
		key := r.Header.Get("Idempotency-Key")

		if attempt < 3 {
			// Имитируем падение инфраструктуры
			http.Error(w, "503 Service Unavailable", http.StatusServiceUnavailable)
			return
		}

		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(fmt.Sprintf(`{"status":"success","key":"%s"}`, key)))
	}))
	defer ts.Close()

	retryClient := &IdempotentHttpClient{
		client: ts.Client(),
		policy: RetryPolicy{
			MaxRetries: 4,
			BaseDelay:  20 * time.Millisecond,
			MaxDelay:   200 * time.Millisecond,
		},
	}

	stableKey := "stable-client-uuid-777"
	resp, err := retryClient.ExecuteWithRetry(context.Background(), func() (*http.Request, error) {
		return http.NewRequest(http.MethodPost, ts.URL+"/process", nil)
	}, stableKey)

	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	fmt.Printf("Запрос успешно завершен со статусом: %d! Всего попыток сервера: %d\n", resp.StatusCode, serverAttempts)
}
```

ℹ️ Клиент с гарантией сохранения Idempotency-Key и экспоненциальным бэкоффом с джиттером

## Под капотом

Почему Full Jitter превосходит обычный экспоненциальный бэкофф:
При возникновении аварии у сотен клиентов без Jitter все они просыпаются строго через \(2^k\) секунд (например, ровно через 1.0 с, затем 2.0 с, 4.0 с). Это порождает синхронные пиковые волны трафика. Full Jitter распределяет моменты повторов равномерно по интервалу \([0, 2^k]\), снижая пиковую нагрузку на CPU сервера в десятки раз.

## Подводные камни

1. **Чтение тела запроса без буферизации:** В Go `req.Body` является `io.ReadCloser`. После первой отправки тело вычитано и закрыто. Повторная отправка того же `req` отправит пустое тело! Используйте функцию-фабрику запроса `reqFactory()` или `io.NopCloser(bytes.NewReader(bodyBytes))`.
2. **Ретраи без тайм-аута контекста:** Бесконечные ретраи могут заблокировать клиентский процесс на часы. Всегда передавайте `context.WithTimeout`.
3. **Ретраи при статусах 4xx:** Повторять запросы с кодами `400 Bad Request`, `401 Unauthorized` или `422 Unprocessable Entity` бессмысленно — они требуют исправления тела запроса.

## На собеседовании

**Вопрос:** Как избежать проблемы утечки ресурсов в Go при повторной отправке `*http.Request` с телом `io.Reader`?
**Ответ:** Перед выполнением `client.Do(req)` тело запроса необходимо вычитать в срез байт `bodyBytes` и перед каждой попыткой заново оборачивать через `req.Body = io.NopCloser(bytes.NewReader(bodyBytes))` с установкой `req.GetBody = func() (io.ReadCloser, error) { return io.NopCloser(bytes.NewReader(bodyBytes)), nil }`. Также критически важно закрывать `resp.Body.Close()` при каждой неудачной попытке.
