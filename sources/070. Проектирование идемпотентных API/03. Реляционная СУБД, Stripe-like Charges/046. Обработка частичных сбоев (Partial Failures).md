# Обработка частичных сбоев (Partial Failures) и транзитных ошибок (5xx)

## Условие

46. **Idempotency + partial failures**: Если запрос failed (500), не сохраняйте response в idempotency table. Retry с тем же key попытается снова.

### Исходная формулировка

**Idempotency + partial failures**: Если запрос failed (500), не сохраняйте response в idempotency table. Retry с тем же key попытается снова.

## Теория

Одной из самых фатальных ошибок при реализации слоя идемпотентности является слепое кэширование **всех** ответов, включая `500 Internal Server Error`, `502 Bad Gateway` или аварийные завершения горутины (`panic`).

### Фундаментальный принцип надежности:
- **Кэшируются только финальные, детерминированные исходы:**
  - `2xx Success` (успешно выполнено).
  - `4xx Client Errors` (ошибки валидации входных данных, бизнес-отказы типа «недостаточно средств» `422`). Повтор с теми же данными детерминированно даст ту же ошибку.
- **Транзитные сбои инфраструктуры (5xx, Deadlock, Timeout, Panic) кэшировать ЗАПРЕЩЕНО!**
  Если при первой попытке упало сетевое соединение с базой данных (500), сохранение ошибки в кэш идемпотентности «замурует» операцию: все последующие законные попытки клиента будут моментально получать закешированную ошибку 500, хотя база данных уже восстановилась!

При возникновении 5xx временный замок (`IN_PROGRESS`) должен быть **немедленно удален** (`store.Delete(key)`), давая клиенту возможность повторить операцию.

## Решение по шагам

1. Создадим middleware с перехватом паники (`recover()`) и проверкой статус-кода ответа.
2. Если обработчик вернул статус `>= 500` или запаниковал:
   - Снимаем временную блокировку ключа (`ReleaseLock(key)`).
   - Не сохраняем ответ в таблицу истории.
3. Если ответ `< 500`:
   - Сохраняем статус и тело ответа с установкой TTL 24 часа.
4. Протестируем поведение: сбойный запрос освобождает ключ, а повторный запрос успешно проходит.

## Код решения

**`partial_failures.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"sync/atomic"
)

type SafeIdempotencyStore struct {
	mu      sync.Mutex
	records map[string]string // key -> response body
	locks   map[string]bool   // key -> in_flight
}

func NewSafeIdempotencyStore() *SafeIdempotencyStore {
	return &SafeIdempotencyStore{
		records: make(map[string]string),
		locks:   make(map[string]bool),
	}
}

func (s *SafeIdempotencyStore) TryLock(key string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.locks[key] || s.records[key] != "" {
		return false
	}
	s.locks[key] = true
	return true
}

func (s *SafeIdempotencyStore) Unlock(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.locks, key)
}

func (s *SafeIdempotencyStore) Commit(key, response string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.locks, key)
	s.records[key] = response
}

func (s *SafeIdempotencyStore) Get(key string) (string, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	resp, ok := s.records[key]
	return resp, ok
}

func PartialFailureMiddleware(store *SafeIdempotencyStore) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" {
				next.ServeHTTP(w, r)
				return
			}

			// 1. Проверяем кэш успешных ответов
			if cached, found := store.Get(key); found {
				w.Header().Set("X-Cache", "HIT")
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(cached))
				return
			}

			// 2. Пытаемся захватить замок
			if !store.TryLock(key) {
				http.Error(w, `{"error":"conflict"}`, http.StatusConflict)
				return
			}

			rec := httptest.NewRecorder()
			var panicOccurred = true

			defer func() {
				if r := recover(); r != nil {
					store.Unlock(key) // Снимаем замок при панике!
					http.Error(w, `{"error":"internal_panic"}`, http.StatusInternalServerError)
				} else if panicOccurred {
					store.Unlock(key)
				}
			}()

			next.ServeHTTP(rec, r)
			panicOccurred = false

			// 3. Анализируем статус: 5xx НЕ КЭШИРУЕМ!
			if rec.Code >= 500 {
				store.Unlock(key) // Освобождаем ключ для возможности повтора
				fmt.Printf("[Idempotency] Транзитный сбой (HTTP %d). Ключ %s освобожден!\n", rec.Code, key)
			} else {
				// Кэшируем только 2xx, 3xx, 4xx
				store.Commit(key, rec.Body.String())
				fmt.Printf("[Idempotency] Финальный ответ (HTTP %d). Ключ %s сохранен!\n", rec.Code, key)
			}

			for k, v := range rec.Header() {
				w.Header()[k] = v
			}
			w.WriteHeader(rec.Code)
			_, _ = w.Write(rec.Body.Bytes())
		})
	}
}

func main() {
	store := NewSafeIdempotencyStore()
	var attempts int64

	// Обработчик, который падает на первой попытке (500) и успешен на второй (200)
	flakyHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		att := atomic.AddInt64(&attempts, 1)
		if att == 1 {
			w.WriteHeader(http.StatusInternalServerError)
			_, _ = w.Write([]byte(`{"error":"db_connection_timeout"}`))
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"order_completed_successfully"}`))
	})

	app := PartialFailureMiddleware(store)(flakyHandler)
	testKey := "order-retry-key-888"

	// Попытка 1: Сбой в БД -> HTTP 500
	req1 := httptest.NewRequest(http.MethodPost, "/checkout", nil)
	req1.Header.Set("Idempotency-Key", testKey)
	rec1 := httptest.NewRecorder()
	app.ServeHTTP(rec1, req1)
	fmt.Printf("Попытка 1: Код ответа = %d\n", rec1.Code)

	// Попытка 2: Клиент повторяет с тем же ключом -> ключ НЕ заблокирован и запрос успешен!
	req2 := httptest.NewRequest(http.MethodPost, "/checkout", nil)
	req2.Header.Set("Idempotency-Key", testKey)
	rec2 := httptest.NewRecorder()
	app.ServeHTTP(rec2, req2)
	fmt.Printf("Попытка 2: Код ответа = %d, Body = %s\n", rec2.Code, rec2.Body.String())

	// Попытка 3: Проверка кэширования успешного ответа
	req3 := httptest.NewRequest(http.MethodPost, "/checkout", nil)
	req3.Header.Set("Idempotency-Key", testKey)
	rec3 := httptest.NewRecorder()
	app.ServeHTTP(rec3, req3)
	fmt.Printf("Попытка 3: Код ответа = %d, Header X-Cache = %s\n", rec3.Code, rec3.Header().Get("X-Cache"))
}
```

ℹ️ Корректная обработка 5xx: освобождение ключа без сохранения для возможности успешного повтора

## Под капотом

Механизм отката транзакции в PostgreSQL:
Если внутри обработчика произошла ошибка 500, выполняется оператор `ROLLBACK`. Транзакция не фиксирует изменения, а строка в таблице `idempotency_keys` либо удаляется, либо ее статус переводится в `FAILED`. Это позволяет клиенту повторить транзакцию с тем же ключом через механизм изоляции Read Committed.

## Подводные камни

1. **Кэширование ошибки 502/504:** Сетевой сбой балансировщика Nginx/Envoy не является бизнес-результатом операции. Если middleware закэширует 502, ресурс никогда не будет создан.
2. **Забытый `defer store.Unlock()` при panic:** Если горутина упадет по nil pointer dereference, а замок не снят, ключ зависнет навсегда. Всегда страхуйте обработку через `recover()`.
3. **Неверная классификация 4xx vs 5xx:** 400/404/422 отражают детерминированный бизнес-результат и могут кэшироваться, тогда как 500/503 требуют повтора.

## На собеседовании

**Вопрос:** Что делать, если при обработке запроса внешний сервис вернул таймаут (Unknown State), и мы не знаем, выполнилась ли операция на его стороне? Имеем ли мы право отдавать клиенту 500 и разрешать retry?
**Ответ:** Это классическая проблема византийских генералов. В финансовом секторе при получении таймаута от внешнего шлюза статус операции переводится в `PENDING_RECONCILIATION` (на согласовании). Повторные запросы клиента получают `202 Accepted` или `409 Conflict` со статусом ожидания. Параллельно фоновый процесс отправляет запрос сверки (Status Inquiry) во внешний шлюз с тем же ключом идемпотентности для выяснения реального исхода.
