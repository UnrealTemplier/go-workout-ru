# Очистка устаревших ключей: периодический фоновый процесс удаления просроченных записей

## Условие

20. **Cleanup expired keys**: Периодически удаляйте expired keys для предотвращения роста таблицы.

### Исходная формулировка

**Cleanup expired keys**: Периодически удаляйте expired keys для предотвращения роста таблицы.

## Теория

Если база данных хранит ключи идемпотентности, ленивого удаления (Lazy Eviction) недостаточно: ключи, к которым клиент никогда больше не обратится, останутся мертвым грузом в СУБД. Необходим активный сборщик мусора (Periodic Cleaner):

1. Фоновая горутина просыпается по тикеру раз в \(N\) минут (или раз в сутки).
2. Выполняет удаление пачками:
   ```sql
   DELETE FROM idempotency_keys
   WHERE ctid IN (
       SELECT ctid FROM idempotency_keys
       WHERE expires_at < NOW()
       LIMIT 1000
   );
   ```
3. Повторяет цикл до тех пор, пока `RowsAffected == 1000`.
Это предотвращает раздувание индексов и стабилизирует потребление диска.

## Решение по шагам

1. Создайте структуру `ExpiredKeysCleaner` с каналом остановки `stopChan`.
2. Настройте запуск метода удаления по тикеру `time.NewTicker`.
3. Удаляйте устаревшие записи пачками с ограничением (Chunk Limit).
4. Реализуйте Graceful Shutdown фоновой горутины.

## Код решения

**`cleanup_expired_keys.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type KeyItem struct {
	Key       string
	ExpiresAt time.Time
}

type TableStorage struct {
	mu    sync.Mutex
	items map[string]KeyItem
}

func (s *TableStorage) DeleteExpiredChunk(limit int) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	deleted := 0

	for k, item := range s.items {
		if item.ExpiresAt.Before(now) {
			delete(s.items, k)
			deleted++
			if deleted >= limit {
				break
			}
		}
	}
	return deleted
}

type CleanerJob struct {
	store    *TableStorage
	ticker   *time.Ticker
	stopChan chan struct{}
}

func NewCleanerJob(store *TableStorage, interval time.Duration) *CleanerJob {
	return &CleanerJob{
		store:    store,
		ticker:   time.NewTicker(interval),
		stopChan: make(chan struct{}),
	}
}

func (j *CleanerJob) Start(ctx context.Context) {
	go func() {
		fmt.Println("[Cleaner Daemon] Started periodic cleanup...")
		for {
			select {
			case <-ctx.Done():
				return
			case <-j.stopChan:
				return
			case <-j.ticker.C:
				total := 0
				for {
					n := j.store.DeleteExpiredChunk(2) // Пачками по 2
					total += n
					if n < 2 {
						break
					}
				}
				if total > 0 {
					fmt.Printf("[Cleaner Daemon] Purged %d expired idempotency keys.\n", total)
				}
			}
		}
	}()
}

func (j *CleanerJob) Stop() {
	j.ticker.Stop()
	close(j.stopChan)
}

func main() {
	store := &TableStorage{items: make(map[string]KeyItem)}
	now := time.Now()

	// 3 просроченных ключа
	for i := 1; i <= 3; i++ {
		k := fmt.Sprintf("expired-key-%d", i)
		store.items[k] = KeyItem{Key: k, ExpiresAt: now.Add(-1 * time.Hour)}
	}

	// 2 активных ключа
	for i := 1; i <= 2; i++ {
		k := fmt.Sprintf("active-key-%d", i)
		store.items[k] = KeyItem{Key: k, ExpiresAt: now.Add(2 * time.Hour)}
	}

	fmt.Printf("Initial table size: %d keys\n", len(store.items))

	cleaner := NewCleanerJob(store, 20*time.Millisecond)
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	cleaner.Start(ctx)

	time.Sleep(50 * time.Millisecond)
	cleaner.Stop()

	fmt.Printf("Final table size: %d keys (Only active keys preserved!)\n", len(store.items))
}
```

ℹ️ Фоновый сборщик мусора очищает просроченные ключи пачками по таймеру

**`output.txt`**

```bash

[Cleaner Daemon] Started periodic cleanup...
[Cleaner Daemon] Purged 3 expired idempotency keys.
Final table size: 2 keys (Only active keys preserved!)
```

## Под капотом

Удаление через `ctid` (физический адрес кортежа в PostgreSQL) работает быстрее, чем удаление по `key`, так как СУБД не тратит время на повторный поиск строки в индексе. После массовой очистки СУБД запускает `VACUUM` для возврата страниц в пул свободного места.

## Подводные камни

1. Запуск очистки в часы пик: если запустить тяжелый `DELETE` в 12:00 дня, транзакции создания заказов встанут в очередь блокировок.
2. Слишком длинная транзакция очистки: держите размер батча в диапазоне 1 000–5 000 строк.

## На собеседовании

Вопрос: Как очищать миллиарды ключей идемпотентности в HighLoad без блокировки таблиц?
Ответ: Партиционированием таблицы по дням: `PARTITION BY RANGE (created_at)`. Вместо выполнения `DELETE`, который нагружает автовакуум и процессор, раз в сутки запускается `DROP TABLE idempotency_keys_2026_09_01`, что мгновенно и без блокировок удаляет всю партицию.
