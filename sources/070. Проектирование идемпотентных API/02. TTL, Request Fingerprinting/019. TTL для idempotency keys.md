# TTL для idempotency keys: вычисление expires_at и автоматическое удаление просроченных записей

## Условие

19. **TTL для idempotency keys**: Установите `expires_at` (например, 24 часа). После expiration удаляйте key.

### Исходная формулировка

**TTL для idempotency keys**: Установите `expires_at` (например, 24 часа). После expiration удаляйте key.

## Теория

В реляционных базах данных, в отличие от Redis, нет встроенной команды `EXPIRE`. Поэтому в DDL схему таблицы идемпотентности добавляется колонка:
`expires_at TIMESTAMPTZ NOT NULL DEFAULT (NOW() + INTERVAL '24 hours')`.

При выборке ключа проверяется условие актуальности:
`SELECT response_body FROM idempotency_keys WHERE key = $1 AND expires_at > NOW();`
Если запись найдена, но `expires_at <= NOW()`, СУБД считает ключ просроченным (Expired). Такая запись немедленно удаляется или перезаписывается новым запросом клиента, что исключает вечную блокировку ключа.

## Решение по шагам

1. Спроектируйте структуру `IdempotencyRecord` с полем `ExpiresAt time.Time`.
2. При создании ключа вычислите `expires_at = time.Now().Add(ttl)`.
3. В методе выборки проверяйте условие `time.Now().Before(rec.ExpiresAt)`.
4. Если запись просрочена, удаляйте ее из памяти/БД.
5. Продемонстрируйте корректную фильтрацию просроченного ключа.

## Код решения

**`expires_at_ttl.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type ExpiringKeyRecord struct {
	Key          string
	ExpiresAt    time.Time
	ResponseJSON string
}

type DatabaseWithTTL struct {
	mu    sync.Mutex
	table map[string]ExpiringKeyRecord
}

func NewDatabaseWithTTL() *DatabaseWithTTL {
	return &DatabaseWithTTL{table: make(map[string]ExpiringKeyRecord)}
}

func (db *DatabaseWithTTL) Save(key string, responseJSON string, ttl time.Duration) {
	db.mu.Lock()
	defer db.mu.Unlock()

	db.table[key] = ExpiringKeyRecord{
		Key:          key,
		ExpiresAt:    time.Now().Add(ttl),
		ResponseJSON: responseJSON,
	}
}

func (db *DatabaseWithTTL) GetActive(key string) (string, bool) {
	db.mu.Lock()
	defer db.mu.Unlock()

	rec, exists := db.table[key]
	if !exists {
		return "", false
	}

	// Проверка срока жизни
	if time.Now().After(rec.ExpiresAt) {
		// Ключ просрочен -> удаляем (Lazy Eviction)
		delete(db.table, key)
		fmt.Printf(" -> [Database Lazy GC] Key '%s' has expired (ExpiresAt=%v)! Evicted.\n",
			key, rec.ExpiresAt.Format("15:04:05"))
		return "", false
	}

	return rec.ResponseJSON, true
}

func main() {
	db := NewDatabaseWithTTL()
	_ = context.Background()

	key := "uuid-payment-exp-001"
	resp := `{"status": "PAID", "amount": 5000}`

	// Сохраняем ключ с коротким TTL 40ms для теста
	fmt.Println("=== 1. Saving key with 40ms TTL ===")
	db.Save(key, resp, 40*time.Millisecond)

	// Немедленная выборка
	val, ok := db.GetActive(key)
	fmt.Printf("Immediate Lookup -> Found: %t, Body: %s\n\n", ok, val)

	// Ожидание истечения TTL
	fmt.Println("=== 2. Sleeping 60ms to let key expire ===")
	time.Sleep(60 * time.Millisecond)

	valAfter, okAfter := db.GetActive(key)
	fmt.Printf("Lookup After Expiration -> Found: %t (Key successfully expired!)\n", okAfter)
}
```

ℹ️ Поле expires_at и ленивая проверка позволяют отсекать просроченные ключи

**`output.txt`**

```bash
=== 1. Saving key with 40ms TTL ===
Immediate Lookup -> Found: true, Body: {"status": "PAID", "amount": 5000}

=== 2. Sleeping 60ms to let key expire ===
 -> [Database Lazy GC] Key 'uuid-payment-exp-001' has expired (ExpiresAt=10:45:00)! Evicted.
Lookup After Expiration -> Found: false (Key successfully expired!)
```

ℹ️ Просроченный ключ безопасно удален при попытке чтения

## Под капотом

Индекс в PostgreSQL по полю `expires_at` (`CREATE INDEX idx_idemp_expires ON idempotency_keys (expires_at)`) позволяет запросу `SELECT ... WHERE key = $1 AND expires_at > NOW()` использовать быстрый комбинированный Index Scan.

## Подводные камни

1. Сравнение времени без учета часовых поясов (UTC vs Local): всегда используйте `NOW() AT TIME ZONE 'UTC'` и `time.Now().UTC()`.
2. Отсутствие удаления: если полагаться только на проверку `WHERE expires_at > NOW()`, просроченные строки останутся лежать на диске вечно.

## На собеседовании

Вопрос: Почему срок хранения ключей идемпотентности в Stripe равен строго 24 часам?
Ответ: 24 часа покрывают любые мыслимые сетевые сбои, ретраи клиентов и повторные попытки мобильных приложений при выходе из авиарежима или туннеля метро. Хранить ключи дольше экономически невыгодно из-за раздувания хранилища, а через сутки транзакция считается закрытой.
