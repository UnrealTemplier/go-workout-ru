# Idempotency в Saga Orchestrator: предотвращение повторного резервирования ресурсов

## Условие

25. **Idempotency + Saga**: В Saga orchestrator используйте idempotency keys для каждого шага. Повторный вызов `ReserveInventory` с тем же key не резервирует inventory дважды.

### Исходная формулировка

**Idempotency + Saga**: В Saga orchestrator используйте idempotency keys для каждого шага. Повторный вызов `ReserveInventory` с тем же key не резервирует inventory дважды.

## Теория

В распределенных сагах (Saga Pattern) координатор выполняет шаги через ненадежную сеть. Если оркестратор вызвал сервис склада `ReserveInventory`, но сетевой ответ отвалился по таймауту, оркестратор обязан выполнить повтор (Retry) шага Саги.

Без идемпотентности на каждом шаге:
- Попытка 1: Склад зарезервировал 2 ноутбука -> Таймаут сети.
- Попытка 2 (Ретрай Саги): Склад зарезервировал еще 2 ноутбука -> Итого списано 4 ноутбука!

**Правило проектирования Саги:**
Оркестратор генерирует детерминированный ключ для каждого шага:
`step_key = fmt.Sprintf("saga:%s:step:%s", sagaID, stepName)`.
При повторном вызове склад видит знакомый `step_key`, не списывает остатки и возвращает уже созданную ранее бронь.

## Решение по шагам

1. Сформируйте составной ключ шага Саги `sagaID + ":" + stepName`.
2. Реализуйте сервис склада `WarehouseService` с дедупликацией по ключу шага.
3. Смоделируйте падение сети после первого резервирования.
4. Вызовите шаг повторно и убедитесь, что остаток на складе списан строго 1 раз.

## Код решения

**`saga_step_idempotency.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type ReservationResult struct {
	ReservationID string
	ReservedItems int
}

type WarehouseService struct {
	mu           sync.Mutex
	stock        int
	reservations map[string]ReservationResult // key: sagaStepKey -> result
}

func NewWarehouseService(stock int) *WarehouseService {
	return &WarehouseService{
		stock:        stock,
		reservations: make(map[string]ReservationResult),
	}
}

func (w *WarehouseService) ReserveInventory(stepKey string, items int) ReservationResult {
	w.mu.Lock()
	defer w.mu.Unlock()

	// Проверка идемпотентности шага Саги
	if res, exists := w.reservations[stepKey]; exists {
		fmt.Printf(" -> [Warehouse] StepKey '%s' already executed! Returning existing reservation %s without deducting stock.\n",
			stepKey, res.ReservationID)
		return res
	}

	// Первичное списание
	w.stock -= items
	result := ReservationResult{
		ReservationID: fmt.Sprintf("RES-%s", stepKey),
		ReservedItems: items,
	}
	w.reservations[stepKey] = result
	fmt.Printf(" -> [Warehouse] Fresh execution! Reserved %d items. Remaining stock: %d\n", items, w.stock)
	return result
}

func main() {
	warehouse := NewWarehouseService(100)
	_ = context.Background()

	sagaID := "saga-order-uuid-999"
	stepName := "reserve_inventory"

	// Детерминированный ключ шага Саги
	stepKey := fmt.Sprintf("%s:%s", sagaID, stepName)

	fmt.Println("=== Saga Step 1: Initial call from Orchestrator ===")
	res1 := warehouse.ReserveInventory(stepKey, 2)
	fmt.Printf("Orchestrator received: Reservation %s\n\n", res1.ReservationID)

	fmt.Println("=== Saga Step 1 RETRY: Network dropped response, Orchestrator retries ===")
	res2 := warehouse.ReserveInventory(stepKey, 2)
	fmt.Printf("Orchestrator received: Reservation %s\n\n", res2.ReservationID)

	fmt.Println("=== Verification ===")
	fmt.Printf("Warehouse Stock: %d (Expected: 98, NOT 96!)\n", warehouse.stock)
}
```

ℹ️ Детерминированный ключ шага Саги защищает от повторного резервирования при сетевых повторах

**`output.txt`**

```bash
=== Saga Step 1: Initial call from Orchestrator ===
 -> [Warehouse] Fresh execution! Reserved 2 items. Remaining stock: 98
Orchestrator received: Reservation RES-saga-order-uuid-999:reserve_inventory

=== Saga Step 1 RETRY: Network dropped response, Orchestrator retries ===
 -> [Warehouse] StepKey 'saga-order-uuid-999:reserve_inventory' already executed! Returning existing reservation RES-saga-order-uuid-999:reserve_inventory without deducting stock.
Orchestrator received: Reservation RES-saga-order-uuid-999:reserve_inventory

=== Verification ===
Warehouse Stock: 98 (Expected: 98, NOT 96!)
```

ℹ️ Остаток уменьшился ровно на 2 единицы, повторный вызов Саги вернул существующую бронь

## Под капотом

В промышленных движках оркестрации Саг (Temporal, Cadence, AWS Step Functions) детерминированный идентификатор `Activity Task Token` или `WorkflowID + ActivityID` автоматически прокидывается в качестве ключа идемпотентности во все внешние вызовы.

## Подводные камни

1. Генерация случайного UUID на каждую попытку retry внутри шага Саги: склад спишет товар повторно.
2. Неидемпотентная компенсация: метод компенсации `CancelReservation` тоже обязан быть идемпотентным, иначе при повторном откате склад вернет лишний товар.

## На собеседовании

Вопрос: Должны ли компенсационные транзакции (Compensations) в Saga быть идемпотентными?
Ответ: Да, обязательно! При сбое Саги оркестратор повторяет компенсацию до победного конца (Backward Recovery). Если компенсация `RefundPayment` не идемпотентна, повторный запуск вернет покупателю деньги дважды.
