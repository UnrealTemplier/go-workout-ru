# Idempotency в GraphQL: передача Idempotency-Key в Variables и защита мутаций

## Условие

26. **Idempotency в GraphQL**: Для mutations используйте idempotency keys. Client отправляет key в variables.

### Исходная формулировка

**Idempotency в GraphQL**: Для mutations используйте idempotency keys. Client отправляет key в variables.

## Теория

В GraphQL все запросы отправляются методом `POST /graphql` на единый эндпоинт, а тип операции (`query` или `mutation`) определяется внутри тела запроса. Поэтому проверять метод HTTP запроса недостаточно — Idempotency Middleware в GraphQL должен анализировать GraphQL AST или извлекать ключ из секции `variables`:

```graphql
mutation CreatePayment($input: PaymentInput!, $idempotencyKey: String!) {
  createPayment(input: $input, idempotencyKey: $idempotencyKey) {
    id
    status
  }
}
```
Сервер GraphQL (gqlgen / graphql-go) через плагин (Field Middleware / Directive) перехватывает вызов резолвера мутации, проверяет `variables["idempotencyKey"]` в Redis и отдает кэшированный результат мутации при повторе.

## Решение по шагам

1. Спроектируйте структуру входящего GraphQL запроса с полями `Query`, `Variables`.
2. Извлеките `idempotencyKey` из карты переменных `variables`.
3. Проверьте наличие ключа в кэше до вызова мутационного резолвера.
4. Сохраните результат резолвера и отдайте клиенту.
5. Продемонстрируйте защиту GraphQL мутации от повторного исполнения.

## Код решения

**`graphql_idempotency.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"sync"
)

type GraphQLRequest struct {
	Query     string                 `json:"query"`
	Variables map[string]interface{} `json:"variables"`
}

type GraphQLResponse struct {
	Data   interface{} `json:"data"`
	Errors []string    `json:"errors,omitempty"`
}

type GraphQLIdempEngine struct {
	mu            sync.Mutex
	cache         map[string]string // key -> JSON GraphQLResponse
	mutationCount int
}

func (e *GraphQLIdempEngine) ExecuteMutation(ctx context.Context, req GraphQLRequest) string {
	e.mu.Lock()
	defer e.mu.Unlock()

	// 1. Извлечение idempotencyKey из GraphQL Variables
	keyRaw, exists := req.Variables["idempotencyKey"]
	if !exists {
		return `{"errors": ["Missing idempotencyKey in variables"]}`
	}
	idempKey := fmt.Sprintf("%v", keyRaw)

	// 2. Проверка кэша
	if cached, found := e.cache[idempKey]; found {
		fmt.Printf(" -> [GraphQL Plugin] Cache HIT for key '%s'! Returning cached mutation result.\n", idempKey)
		return cached
	}

	// 3. Вызов резолвера мутации
	e.mutationCount++
	fmt.Printf(" -> [GraphQL Resolver] Executing createOrder mutation (Total mutations: %d)...\n", e.mutationCount)
	resp := fmt.Sprintf(`{"data": {"createOrder": {"id": "GQL-ORD-88", "key": "%s", "status": "CONFIRMED"}}}`, idempKey)

	e.cache[idempKey] = resp
	return resp
}

func main() {
	engine := &GraphQLIdempEngine{cache: make(map[string]string)}
	ctx := context.Background()

	idempUUID := "uuid-gql-mutation-555"

	gqlQuery := `mutation ProcessOrder($idempotencyKey: String!) {
		createOrder(idempotencyKey: $idempotencyKey) { id status }
	}`

	req := GraphQLRequest{
		Query: gqlQuery,
		Variables: map[string]interface{}{
			"idempotencyKey": idempUUID,
		},
	}

	fmt.Println("=== 1. First GraphQL Mutation Execution ===")
	out1 := engine.ExecuteMutation(ctx, req)
	fmt.Printf("Client 1: %s\n\n", out1)

	fmt.Println("=== 2. Duplicate GraphQL Mutation Execution (Retry) ===")
	out2 := engine.ExecuteMutation(ctx, req)
	fmt.Printf("Client 2: %s\n\n", out2)

	fmt.Printf("Verification: Total GraphQL Resolver Executions = %d (Expected: 1)\n", engine.mutationCount)
}
```

ℹ️ Передача ключа в GraphQL Variables позволяет резолверам мутаций работать идемпотентно

## Под капотом

В библиотеке `gqlgen` для Go идемпотентность реализуется через директиву схемы: `directive @idempotent on FIELD_DEFINITION`. Плагин директивы перехватывает аргументы поля до вызова резолвера, проверяет ключ в хранилище и при наличии отдает кэшированное значение.

## Подводные камни

1. Попытка проверять `Idempotency-Key` в HTTP-заголовке для GraphQL Query: клиенты шлют batch-запросы (Query + Mutation в одном POST), что делает HTTP заголовок двусмысленным.
2. Кэширование GraphQL ошибок `errors`: если мутация упала из-за временного сбоя СУБД, ошибку нельзя сохранять в постоянный кэш.

## На собеседовании

Вопрос: Как правильно организовать идемпотентность в GraphQL при Batching запросах (несколько операций в одном POST)?
Ответ: При пакетных запросах HTTP заголовок использовать нельзя, так как батч содержит множество независимых операций. Каждая мутация внутри массива должна иметь свой собственный `idempotencyKey` в `variables`, а проверка должна выполняться на уровне Field Middleware для каждой мутации индивидуально.
