# In-Progress Lock: распределенная блокировка SET key IN_PROGRESS NX PX 10s и HTTP 409 Conflict

## Условие

37. **Idempotency Middleware: обработка параллельных запросов (In-Progress Lock)**: Если клиент отправляет два идентичных запроса с одним ключом идемпотентности практически одновременно (до того, как первый запрос успел завершиться), обычная проверка кэша не сработает. Напишите HTTP-middleware в Go, реализующее распределенную блокировку в Redis:
* При получении запроса выполните команду `SET key "IN_PROGRESS" NX PX 10s`.
* Если Redis возвращает ошибку (ключ уже занят), а значение равно `"IN_PROGRESS"`, middleware должно приостановить выполнение второго запроса (например, опрашивать Redis раз в 100 миллисекунд или слушать Pub/Sub канал) или мгновенно вернуть статус `409 Conflict`, сообщив, что запрос уже обрабатывается.

### Исходная формулировка

**Idempotency Middleware: обработка параллельных запросов (In-Progress Lock)**: Если клиент отправляет два идентичных запроса с одним ключом идемпотентности практически одновременно (до того, как первый запрос успел завершиться), обычная проверка кэша не сработает. * Если Redis возвращает ошибку (ключ уже занят), а значение равно `"IN_PROGRESS"`, middleware должно приостановить выполнение второго запроса (например, опрашивать Redis раз в 100 миллисекунд или слушать Pub/Sub канал) или мгновенно вернуть статус `409 Conflict`, сообщив, что запрос уже обрабатывается.

## Теория

В распределенной среде два параллельных запроса с одинаковым ключом могут прийти на два разных инстанса бэкенда в одну и ту же миллисекунду (Race Condition). Если оба проверят кэш и увидят `MISS`, оба выполнят мутирующую операцию.

Паттерн **In-Progress Lock** в Redis решает эту проблему:
1. При получении запроса выполняется команда: `SET key IN_PROGRESS NX PX 10000` (блокировка на 10 сек).
2. Если команда вернула `false` (замок уже кем-то занят):
   - Сервер читает текущее значение ключа `GET key`.
   - Если значение равно `IN_PROGRESS` -> операция прямо сейчас выполняется другим потоком. Сервер немедленно возвращает **HTTP 409 Conflict** с заголовком `Retry-After: 1`.
   - Если значение содержит готовый ответ -> сервер отдает кэш `HTTP 200 OK`.
3. Первый поток по завершении работы перезаписывает замок готовым ответом с TTL 24 часа.

## Решение по шагам

1. Реализуйте метод `LockOrGet(key)` с вызовом `SET NX PX`.
2. В Middleware обработайте параллельный вызов со статусом `IN_PROGRESS`.
3. Верните статус HTTP 409 Conflict и заголовок `Retry-After`.
4. Продемонстрируйте параллельную гонку двух одновременных горутин.

## Код решения

**`in_progress_lock_middleware.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type LockState struct {
	Value     string
	ExpiresAt time.Time
}

type RedisLockManager struct {
	mu    sync.Mutex
	locks map[string]LockState
}

func (r *RedisLockManager) TryAcquireInProgress(key string, ttl time.Duration) (acquired bool, currentValue string) {
	r.mu.Lock()
	defer r.mu.Unlock()

	now := time.Now()
	state, exists := r.locks[key]
	if exists && now.Before(state.ExpiresAt) {
		return false, state.Value // Замок уже занят кем-то
	}

	// Захватываем блокировку IN_PROGRESS
	r.locks[key] = LockState{
		Value:     "IN_PROGRESS",
		ExpiresAt: now.Add(ttl),
	}
	return true, "IN_PROGRESS"
}

func (r *RedisLockManager) ReleaseWithResult(key, result string, ttl time.Duration) {
	r.mu.Lock()
	defer r.mu.Unlock()

	r.locks[key] = LockState{
		Value:     result,
		ExpiresAt: time.Now().Add(ttl),
	}
}

func InProgressIdempotencyMiddleware(redis *RedisLockManager) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" {
				next.ServeHTTP(w, r)
				return
			}

			acquired, currentVal := redis.TryAcquireInProgress(key, 10*time.Second)
			if !acquired {
				if currentVal == "IN_PROGRESS" {
					// Параллельный запрос перехвачен!
					w.Header().Set("Retry-After", "1")
					w.WriteHeader(http.StatusConflict) // 409 Conflict
					_, _ = w.Write([]byte(`{"error": "Concurrent request in progress. Please retry later"}`))
					return
				}

				// Запрос уже завершен -> отдаем кэш
				w.Header().Set("X-Idempotency", "REPLAY")
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(currentVal))
				return
			}

			// Выполнение хэндлера
			rec := httptest.NewRecorder()
			next.ServeHTTP(rec, r)

			// Фиксация результата
			redis.ReleaseWithResult(key, rec.Body.String(), 24*time.Hour)

			w.WriteHeader(rec.Code)
			_, _ = w.Write(rec.Body.Bytes())
		})
	}
}

func main() {
	redis := &RedisLockManager{locks: make(map[string]LockState)}

	heavyHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(50 * time.Millisecond) // Долгая операция
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"order_id": "ORD-777", "status": "CONFIRMED"}`))
	})

	app := InProgressIdempotencyMiddleware(redis)(heavyHandler)
	key := "uuid-in-progress-test-1"

	var wg sync.WaitGroup
	wg.Add(2)

	// Запрос 1
	req1 := httptest.NewRequest(http.MethodPost, "/orders", nil)
	req1.Header.Set("Idempotency-Key", key)
	rr1 := httptest.NewRecorder()

	// Запрос 2 (приходит одновременно)
	req2 := httptest.NewRequest(http.MethodPost, "/orders", nil)
	req2.Header.Set("Idempotency-Key", key)
	rr2 := httptest.NewRecorder()

	fmt.Println("=== Racing 2 Concurrent Requests with In-Progress Lock ===")
	go func() {
		defer wg.Done()
		app.ServeHTTP(rr1, req1)
	}()

	time.Sleep(10 * time.Millisecond) // Небольшой сдвиг, чтобы первый успел занять замок

	go func() {
		defer wg.Done()
		app.ServeHTTP(rr2, req2)
	}()

	wg.Wait()

	fmt.Printf("Request 1 Status: %d, Body: %s\n", rr1.Code, rr1.Body.String())
	fmt.Printf("Request 2 Status: %d, Body: %s (Retry-After: %s)\n",
		rr2.Code, rr2.Body.String(), rr2.Header().Get("Retry-After"))
}
```

ℹ️ Блокировка IN_PROGRESS мгновенно перехватывает параллельный дубликат статусом 409 Conflict

## Под капотом

Опция `PX 10000` выставляет TTL замка в миллисекундах (10 000 мс = 10 сек). Это предотвращает постоянный дедлок: если воркер упадет по OOM во время выполнения бизнес-кода, замок автоматически испарится через 10 секунд, позволив клиенту повторить запрос.

## Подводные камни

1. Слишком короткий PX TTL (например, 500 мс): если база данных замедлилась и ответ занял 800 мс, замок спадет раньше времени и параллельный запрос начнет выполняться.
2. Отсутствие заголовка `Retry-After`: клиент начнет мгновенно спамить запросами с интервалом в 1 мс.

## На собеседовании

Вопрос: Что эффективнее при конкурентных дубликатах: опрашивать Redis в цикле или сразу вернуть HTTP 409?
Ответ: В распределенных веб-системах HighLoad индустриальный стандарт — немедленный возврат HTTP 409 Conflict. Поллинг Redis внутри HTTP горутины сервера держит открытым сокет клиента, занимает память стека горутины и создает паразитную нагрузку на сеть Redis. Возврат 409 переносит ожидание на сторону клиента.
