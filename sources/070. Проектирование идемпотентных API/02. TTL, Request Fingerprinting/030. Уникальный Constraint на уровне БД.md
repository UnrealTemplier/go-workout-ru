# Уникальный Constraint на уровне БД: обработка нарушения уникальности и возврат сохраненного ответа

## Условие

30. **Уникальный constraint на уровне БД для идемпотентности.**: Вместо Redis, сохраняйте `idempotency_key` в таблицу БД с уникальным индексом. В middleware выполните вставку ключа в начале обработки. При нарушении уникальности верните ранее сохранённый ответ (или 409 Conflict).

### Исходная формулировка

**Уникальный constraint на уровне БД для идемпотентности.**: Вместо Redis, сохраняйте `idempotency_key` в таблицу БД с уникальным индексом. В middleware выполните вставку ключа в начале обработки. При нарушении уникальности верните ранее сохранённый ответ (или 409 Conflict).

## Теория

Хранение ключей идемпотентности в таблице базы данных с уникальным ограничением (`UNIQUE CONSTRAINT`) — наиболее надежный способ защиты в условиях распределенного кластера бэкендов.

Алгоритм работы в Middleware:
1. При получении запроса выполняется предварительная вставка замка:
   `INSERT INTO idempotency_keys (key, status, created_at) VALUES ($1, 'STARTED', NOW());`
2. Если СУБД возвращает ошибку нарушения уникальности (`23505 unique_violation` в PostgreSQL):
   - Выполняется `SELECT status, response_body FROM idempotency_keys WHERE key = $1`.
   - Если статус `STARTED` -> возвращаем **HTTP 409 Conflict**.
   - Если статус `COMPLETED` -> возвращаем сохраненный `response_body` с оригинальным статус-кодом.
3. Если вставка успешна — передаем управление в хэндлер, а затем обновляем статус на `COMPLETED`.

## Решение по шагам

1. Реализуйте структуру записи таблицы `DBIdempEntry`.
2. В Middleware сымитируйте вставку с проверкой уникальности первичного ключа.
3. При конфликте ключа проверьте статус и верните 409 или кэш.
4. Продемонстрируйте работу Middleware.

## Код решения

**`db_constraint_middleware.go`**

```go
package main

import (
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

var ErrUniqueConstraintViolation = errors.New("pq: duplicate key value violates unique constraint 'idx_idemp_key'")

type DBRecord struct {
	Key          string
	Status       string // STARTED, COMPLETED
	ResponseCode int
	ResponseBody string
}

type DatabaseManager struct {
	mu   sync.Mutex
	rows map[string]DBRecord
}

func (db *DatabaseManager) TryInsertStarted(key string) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	if _, exists := db.rows[key]; exists {
		return ErrUniqueConstraintViolation
	}

	db.rows[key] = DBRecord{Key: key, Status: "STARTED"}
	return nil
}

func (db *DatabaseManager) Get(key string) (DBRecord, bool) {
	db.mu.Lock()
	defer db.mu.Unlock()
	r, ok := db.rows[key]
	return r, ok
}

func (db *DatabaseManager) MarkCompleted(key string, code int, body string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.rows[key] = DBRecord{
		Key:          key,
		Status:       "COMPLETED",
		ResponseCode: code,
		ResponseBody: body,
	}
}

func DBIdempotencyMiddleware(db *DatabaseManager) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			key := r.Header.Get("Idempotency-Key")
			if key == "" {
				next.ServeHTTP(w, r)
				return
			}

			// Шаг 1: Атомарная попытка вставить статус STARTED
			err := db.TryInsertStarted(key)
			if err != nil {
				if errors.Is(err, ErrUniqueConstraintViolation) {
					// Ключ уже есть в базе -> анализируем статус
					record, _ := db.Get(key)
					if record.Status == "STARTED" {
						w.Header().Set("Retry-After", "1")
						w.WriteHeader(http.StatusConflict) // 409 Conflict
						_, _ = w.Write([]byte(`{"error": "Operation is currently in progress"}`))
						return
					}
					// COMPLETED -> отдаем кэш
					w.Header().Set("X-Idempotency-Source", "PostgreSQL-Cache")
					w.WriteHeader(record.ResponseCode)
					_, _ = w.Write([]byte(record.ResponseBody))
					return
				}
				http.Error(w, "Database error", http.StatusInternalServerError)
				return
			}

			// Шаг 2: Первичное исполнение
			rec := httptest.NewRecorder()
			next.ServeHTTP(rec, r)

			// Шаг 3: Сохранение ответа
			db.MarkCompleted(key, rec.Code, rec.Body.String())

			w.WriteHeader(rec.Code)
			_, _ = w.Write(rec.Body.Bytes())
		})
	}
}

func main() {
	db := &DatabaseManager{rows: make(map[string]DBRecord)}

	businessHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"transfer_status": "SUCCESS"}`))
	})

	app := DBIdempotencyMiddleware(db)(businessHandler)
	key := "uuid-db-constraint-999"

	fmt.Println("=== 1. First execution ===")
	req1 := httptest.NewRequest(http.MethodPost, "/transfer", nil)
	req1.Header.Set("Idempotency-Key", key)
	rr1 := httptest.NewRecorder()
	app.ServeHTTP(rr1, req1)
	fmt.Printf("Response 1: Status %d, Body: %s\n", rr1.Code, rr1.Body.String())

	fmt.Println("\n=== 2. Replay execution with same key (Unique violation in DB) ===")
	req2 := httptest.NewRequest(http.MethodPost, "/transfer", nil)
	req2.Header.Set("Idempotency-Key", key)
	rr2 := httptest.NewRecorder()
	app.ServeHTTP(rr2, req2)
	fmt.Printf("Response 2: Status %d, Source: %s, Body: %s\n",
		rr2.Code, rr2.Header().Get("X-Idempotency-Source"), rr2.Body.String())
}
```

ℹ️ Уникальный индекс в БД перехватывает дубликат и возвращает сохраненный ответ

## Под капотом

Ограничение `UNIQUE` в PostgreSQL реализуется через B-Tree индекс. При попытке параллельной вставки одинакового ключа СУБД использует блокировку `Speculative Execution Lock`. Как только первая транзакция делает `COMMIT`, вторая мгновенно отбрасывается с ошибкой `SQLSTATE 23505`.

## Подводные камни

1. Забытый статус `STARTED`: если вставлять запись только после выполнения хэндлера, конкурентные запросы во время долгой работы хэндлера не обнаружат дубликат.
2. Падение процесса на этапе `STARTED`: запись останется висеть, поэтому требуется поле `locked_until` для автоматического перехвата зависших замков.

## На собеседовании

Вопрос: Что произойдет, если воркер упал после вставки записи со статусом STARTED?
Ответ: Запись останется со статусом STARTED, и последующие запросы будут получать 409 Conflict. Для решения этой проблемы в схему добавляется колонка `locked_until TIMESTAMPTZ DEFAULT (NOW() + INTERVAL '30 seconds')`. Если повторный запрос видит статус `STARTED`, но `NOW() > locked_until`, он считает предыдущий воркер погибшим и перехватывает блокировку через `UPDATE ... WHERE key = $1 AND locked_until < NOW()`.
