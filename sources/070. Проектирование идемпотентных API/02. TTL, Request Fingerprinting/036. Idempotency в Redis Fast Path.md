# Idempotency в Redis Fast Path: высокопроизводительный путь через SET key response NX EX 86400

## Условие

36. **Idempotency в Redis (fast path)**: Для high-performance используйте Redis для idempotency:
```
SET key "response" NX EX 86400
```
Если SET successful (NX = not exists) — выполняйте запрос. Иначе — return cached.

### Исходная формулировка

**Idempotency в Redis (fast path)**: Для high-performance используйте Redis для idempotency:
```
SET key "response" NX EX 86400
```
Если SET successful (NX = not exists) — выполняйте запрос. Иначе — return cached.

## Теория

В архитектуре Fast Path (быстрый путь) для сверхвысоких нагрузок (100 000+ RPS) применяется оптимизированная одношаговая команда Redis `SET key val NX EX 86400`:

1. Клиент отправляет запрос.
2. Если ответ уже заранее известен или запрос является синхронной трансляцией: сервер пытается выполнить `SET key response NX EX 86400`.
3. Если команда вернула `OK` (в Go `redis.Nil == false`): ключ был свободен и мгновенно занят.
4. Если команда вернула nil: ключ уже существовал, и Redis вернул отказ, после чего сервер командой `GET key` забирает готовый кэшированный ответ.
Задержка проверки составляет всего 0.2 миллисекунды.

## Решение по шагам

1. Реализуйте функцию Fast Path с использованием команды `SET NX EX`.
2. Обработайте успешную установку ключа.
3. При конфликте выполните `GET` и верните кэшированный ответ.
4. Продемонстрируйте пропускную способность алгоритма.

## Код решения

**`redis_fast_path.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type MockRedisFastPath struct {
	mu    sync.Mutex
	store map[string]string
}

func (r *MockRedisFastPath) SetNXEX(key, val string, ttl time.Duration) bool {
	r.mu.Lock()
	defer r.mu.Unlock()

	if _, exists := r.store[key]; exists {
		return false // Key already exists (NX condition failed)
	}
	r.store[key] = val
	return true
}

func (r *MockRedisFastPath) Get(key string) string {
	r.mu.Lock()
	defer r.mu.Unlock()
	return r.store[key]
}

func HandleFastPath(redis *MockRedisFastPath, key string, businessFn func() string) string {
	// В Fast-Path пробуем выполнить предварительное бронирование
	booked := redis.SetNXEX(key, "IN_FLIGHT", 86400*time.Second)
	if !booked {
		// Ключ уже есть -> отдаем кэшированный результат
		cached := redis.Get(key)
		fmt.Printf(" -> [Fast Path HIT] Key '%s' found in Redis! Returning cached response.\n", key)
		return cached
	}

	// Первый запуск -> исполнение
	fmt.Printf(" -> [Fast Path MISS] Key '%s' acquired lock! Executing payload...\n", key)
	resp := businessFn()

	// Обновляем значение ответа
	redis.mu.Lock()
	redis.store[key] = resp
	redis.mu.Unlock()
	return resp
}

func main() {
	redis := &MockRedisFastPath{store: make(map[string]string)}
	_ = context.Background()

	key := "fast-path-uuid-8899"

	businessLogic := func() string {
		return `{"result": "fast_processed", "timestamp": 1725619200}`
	}

	fmt.Println("=== 1. First Execution via Redis Fast Path ===")
	out1 := HandleFastPath(redis, key, businessLogic)
	fmt.Printf("Result 1: %s\n\n", out1)

	fmt.Println("=== 2. Replay Execution via Redis Fast Path ===")
	out2 := HandleFastPath(redis, key, businessLogic)
	fmt.Printf("Result 2: %s\n", out2)
}
```

ℹ️ Команда SET NX EX обеспечивает минимальную задержку и атомарность в оперативной памяти

**`output.txt`**

```bash

 -> [Fast Path MISS] Key 'fast-path-uuid-8899' acquired lock! Executing payload...
Result 1: {"result": "fast_processed", "timestamp": 1725619200}

=== 2. Replay Execution via Redis Fast Path ===

```

## Под капотом

Команда `SET key val NX EX 86400` объединила функционал старых устаревших команд `SETNX` и `EXPIRE` в единую неделимую операцию. В старых версиях Redis между `SETNX` и `EXPIRE` сервер мог упасть, оставляя ключ вечным (Zombie Key без TTL).

## Подводные камни

1. Запись ответа до его получения: если сохранить плейсхолдер и упасть, клиент навсегда закэширует статус `IN_FLIGHT`.
2. Переполнение памяти при 86400 секундах: при 100 000 RPS память должна быть точно рассчитана по формуле \(\text{RAM} = 100\,000 \times 86\,400 \times 500\text{ байт} \approx 4.3\text{ ГБ}\).

## На собеседовании

Вопрос: В чем преимущество `SET key val NX EX` перед связкой `SETNX` + `EXPIRE` в коде Go?
Ответ: Атомарность! Связка двух команд требует двух сетевых раунд-трипов к Redis (2 RTT) и уязвима к сбоям: если приложение упало между `SETNX` и `EXPIRE`, ключ останется в памяти без TTL навсегда. `SET NX EX` атомарно выполняется на сервере Redis за 1 RTT.
