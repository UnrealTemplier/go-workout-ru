# Идемпотентность в Webhooks: передача Idempotency-Key и дедупликация на стороне подписчика

## Условие

28. **Idempotency в webhooks**: При отправке webhook добавляйте `Idempotency-Key` header. Client использует его для deduplication.

### Исходная формулировка

**Idempotency в webhooks**: При отправке webhook добавляйте `Idempotency-Key` header. Client использует его для deduplication.

## Теория

Платформы отправки вебхуков (Stripe, GitHub, Shopify) используют семантику At-Least-Once: если сервер подписчика ответил с задержкой или вернул HTTP 500, диспетчер вебхуков повторяет отправку через 1 минуту, 5 минут, 1 час. Это гарантирует, что вебхуки обязательно придут дублирующимися.

Стандарт надежного вебхука:
1. Провайдер вебхука (Sender) отправляет запрос с заголовками:
   - `Idempotency-Key: evt_uuid_12345` (уникальный ID события)
   - `X-Webhook-Event-ID: evt_uuid_12345`
   - `X-Webhook-Signature: t=123,v1=sha256...`
2. Подписчик вебхука (Receiver) извлекает `Idempotency-Key`, проверяет его в своей локальной таблице дедупликации и при повторном получении мгновенно возвращает `HTTP 200 OK` без повторного выполнения логики.

## Решение по шагам

1. Реализуйте структуру отправки вебхука `WebhookDispatcher` с добавлением `Idempotency-Key`.
2. Реализуйте вебхук-хэндлер на стороне получателя с таблицей дедупликации.
3. Сымитируйте отправку одного и того же вебхука дважды (ретрай провайдера).
4. Убедитесь, что получатель обработал событие строго 1 раз и заакал оба запроса кодом 200.

## Код решения

**`webhook_idempotency.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

// Приемник вебхука (Client Webhook Receiver)
type WebhookReceiver struct {
	mu            sync.Mutex
	processedKeys map[string]bool
	businessCalls int
}

func (rec *WebhookReceiver) HandleWebhook(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "Missing Idempotency-Key", http.StatusBadRequest)
		return
	}

	rec.mu.Lock()
	defer rec.mu.Unlock()

	// Проверка дедупликации
	if rec.processedKeys[key] {
		fmt.Printf(" -> [Webhook Receiver] Event '%s' was already processed! Immediate 200 OK (No-Op).\n", key)
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status": "DUPLICATE_ACK"}`))
		return
	}

	// Первичная обработка
	rec.processedKeys[key] = true
	rec.businessCalls++
	fmt.Printf(" -> [Webhook Receiver] Fresh Event '%s' processed! Triggering business workflow (Calls: %d)...\n",
		key, rec.businessCalls)

	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"status": "PROCESSED"}`))
}

func main() {
	receiver := &WebhookReceiver{processedKeys: make(map[string]bool)}
	eventID := "evt-charge-succeeded-uuid-999"
	payload := `{"event": "charge.succeeded", "amount": 15000, "customer": "cust-42"}`

	// 1. Первая доставка вебхука от платежной системы
	fmt.Println("=== 1. Webhook Provider sends first delivery ===")
	req1 := httptest.NewRequest(http.MethodPost, "/webhooks/payments", bytes.NewBufferString(payload))
	req1.Header.Set("Idempotency-Key", eventID)
	rr1 := httptest.NewRecorder()
	receiver.HandleWebhook(rr1, req1)
	fmt.Printf("Provider got HTTP %d: %s\n\n", rr1.Code, rr1.Body.String())

	// 2. Повторная доставка того же вебхука (провайдер не дождался ack из-за сетевого сбоя)
	fmt.Println("=== 2. Webhook Provider retries delivery of the exact same event ===")
	req2 := httptest.NewRequest(http.MethodPost, "/webhooks/payments", bytes.NewBufferString(payload))
	req2.Header.Set("Idempotency-Key", eventID)
	rr2 := httptest.NewRecorder()
	receiver.HandleWebhook(rr2, req2)
	fmt.Printf("Provider got HTTP %d: %s\n\n", rr2.Code, rr2.Body.String())

	fmt.Printf("Verification: Total Business Handler Executions = %d (Expected: 1)\n", receiver.businessCalls)
}
```

ℹ️ Заголовок Idempotency-Key в вебхуках позволяет приемнику безопасно акцептовать повторы

## Под капотом

Вебхуки часто обрабатываются асинхронно: при получении HTTP 200 тело вебхука сразу складывается в локальную очередь консьюмера (Transactional Inbox). Идентификатор `Idempotency-Key` используется в качестве уникального ключа задачи в очереди.

## Подводные камни

1. Возврат ошибки 400 или 409 при дубликате вебхука: провайдер вебхуков воспримет это как сбой доставки и начнет спамить повторами по экспоненциальному расписанию.
2. Обработка вебхука без проверки подписи HMAC: злоумышленник может слать поддельные вебхуки с чужими ключами.

## На собеседовании

Вопрос: Что должен возвращать эндпоинт вебхука при получении повторного (дублирующегося) события?
Ответ: Строго HTTP 200 OK (или 204 No Content)! Для провайдера вебхуков статус 200 означает: 'событие успешно доставлено, прекрати повторы'. Если вернуть 4xx или 5xx, провайдер продолжит слать ретраи.
