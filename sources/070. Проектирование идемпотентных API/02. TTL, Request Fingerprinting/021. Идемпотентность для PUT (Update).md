# Идемпотентность для PUT (Update): исключение повторных мутаций и паразитных записей в Audit Log

## Условие

21. **Idempotency для PUT (update)**: При повторном PUT с тем же key возвращайте результат обновления (не обновляйте дважды).

### Исходная формулировка

**Idempotency для PUT (update)**: При повторном PUT с тем же key возвращайте результат обновления (не обновляйте дважды).

## Теория

Хотя по спецификации HTTP метод `PUT` считается идемпотентным (замена сущности ее полным представлением), в реальной микросервисной архитектуре это не так:
1. При каждом вызове `PUT /users/profile` генерируется событие `UserProfileUpdatedEvent` в Outbox/Kafka.
2. В таблице аудита создается запись `audit_logs (user_id, updated_at, changed_fields)`.
3. Срабатывают триггеры пересчета кэшей и уведомления мобильных устройств.

Если мобильное приложение при плохой сети отправит один и тот же `PUT` 5 раз подряд, без `Idempotency-Key` система сгенерирует 5 событий в Kafka и 5 записей аудита! Idempotency Middleware на `PUT` перехватывает дубликат и возвращает результат первого обновления без повторных побочных эффектов.

## Решение по шагам

1. Смоделируйте бизнес-операцию `UpdateUserProfile` с ведением счетчика событий аудита.
2. Оберните операцию в проверку `Idempotency-Key`.
3. Выполните первый `PUT` — убедитесь, что профиль обновился и записался аудит.
4. Выполните повторный `PUT` с тем же ключом — убедитесь, что ответ вернулся, а аудит не продублировался.

## Код решения

**`put_idempotency.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type UserProfile struct {
	Email string
	Name  string
}

type SystemAudit struct {
	mu           sync.Mutex
	auditEvents  []string
	profile      UserProfile
	idempStorage map[string]string // key -> cachedResponse
}

func (s *SystemAudit) HandlePutProfile(idempKey, newEmail, newName string) string {
	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверка идемпотентности
	if cached, ok := s.idempStorage[idempKey]; ok {
		fmt.Printf(" -> [PUT Idempotent Replay] Key '%s' recognized! Returning cached response without side effects.\n", idempKey)
		return cached
	}

	// 2. Первичное обновление
	s.profile.Email = newEmail
	s.profile.Name = newName

	// 3. Побочные эффекты (генерация событий аудита)
	auditMsg := fmt.Sprintf("AUDIT: Profile updated to %s (%s)", newName, newEmail)
	s.auditEvents = append(s.auditEvents, auditMsg)
	fmt.Printf(" -> [PUT Mutation Executed] %s\n", auditMsg)

	resp := fmt.Sprintf(`{"status": "UPDATED", "email": "%s", "name": "%s"}`, newEmail, newName)
	s.idempStorage[idempKey] = resp
	return resp
}

func main() {
	sys := &SystemAudit{
		profile:      UserProfile{Email: "old@example.com", Name: "Old Name"},
		idempStorage: make(map[string]string),
	}

	key := "uuid-put-key-444"

	fmt.Println("=== 1. First PUT Request ===")
	resp1 := sys.HandlePutProfile(key, "new@example.com", "Ivan Ivanov")
	fmt.Printf("Client 1 got: %s\n\n", resp1)

	fmt.Println("=== 2. Duplicate PUT Request (Network Retry with same key) ===")
	resp2 := sys.HandlePutProfile(key, "new@example.com", "Ivan Ivanov")
	fmt.Printf("Client 2 got: %s\n\n", resp2)

	fmt.Println("=== Final Audit Log Verification ===")
	fmt.Printf("Total Audit Events in DB: %d (Expected: 1)\n", len(sys.auditEvents))
	for _, ev := range sys.auditEvents {
		fmt.Println(" - " + ev)
	}
}
```

ℹ️ Повторный PUT возвращает результат без повторной генерации аудит-логов и событий

## Под капотом

Разница между математической идемпотентностью состояния (State Idempotency) и сайд-эффект идемпотентностью (Side-Effect Idempotency): повторный `PUT` оставляет состояние записи тем же, но плодит каскадные события в брокерах. Паттерн `Idempotency-Key` глушит именно каскадные побочные эффекты.

## Подводные камни

1. Предположение, что `PUT` идемпотентен 'из коробки' и не требует ключа: каскадные вебхуки и триггеры создадут дублирующие уведомления пользователю (5 пуш-уведомлений на одно действие).
2. Перезапись ключа: при смене данных в `PUT` с тем же ключом необходимо возвращать 422 (защита от мутаций).

## На собеседовании

Вопрос: Является ли HTTP метод PUT идемпотентным сам по себе?
Ответ: По стандарту HTTP — да, так как повторное присвоение \(x = 5\) не меняет \(x\). Но в реальных распределенных архитектурах мутация порождает сайд-эффекты (Outbox events, аудит, триггеры). Поэтому для предотвращения шторма побочных событий в BigTech метод PUT защищается ключом идемпотентности так же, как и POST.
