# Проблема сетевых ретраев: почему HTTP POST по умолчанию не идемпотентен

## Условие

31. **[Проблема ретраев]**: Напиши HTTP-клиент, который делает POST `/payments`. Сымитируй таймаут сети. Клиент повторяет запрос. Сервер успел списать деньги дважды. Объясни, почему HTTP POST по умолчанию не идемпотентен.

### Исходная формулировка

**[Проблема ретраев]**: Напиши HTTP-клиент, который делает POST `/payments`. Сымитируй таймаут сети. Клиент повторяет запрос. Сервер успел списать деньги дважды. Объясни, почему HTTP POST по умолчанию не идемпотентен.

## Теория

По спецификации RFC 9110 метод `POST` является неидемпотентным (Non-Idempotent by default):
каждый вызов `POST /payments` сообщает серверу о необходимости создания **нового независимого ресурса**.

Анатомия сетевого сбоя при отсутствии `Idempotency-Key`:
1. Клиент отправляет `POST /payments` (списать 10 000 руб).
2. Сервер получил запрос, успешно списал 10 000 руб и отправил клиенту ответ `200 OK`.
3. По дороге к клиенту сетевой пакет потерялся (Wi-Fi роутер разорвал соединение).
4. Клиент по таймауту (`Client.Timeout = 2s`) получает ошибку `context deadline exceeded`.
5. Наивная логика ретрая клиента думает, что платеж не прошел, и отправляет `POST /payments` снова.
6. Сервер создает **второй платеж** и списывает еще 10 000 руб!
Результат: потеря 10 000 рублей клиентом.

## Решение по шагам

1. Реализуйте наивный сервер списания без проверки ключей.
2. Реализуйте клиента с автоматическим циклом повторов при сетевых таймаутах.
3. Сымитируйте потерю ответа первого запроса.
4. Продемонстрируйте катастрофическое двойное списание средств.
5. Сформулируйте вывод о необходимости Idempotency-Key.

## Код решения

**`post_retry_disaster.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type NaiveServer struct {
	mu           sync.Mutex
	userBalance  int
	chargeLog    []int
	dropResponse bool
}

func (s *NaiveServer) ChargeMoney(amount int) (bool, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Списание средств в БД сервера
	s.userBalance -= amount
	s.chargeLog = append(s.chargeLog, amount)
	fmt.Printf(" [Server DB] Deducted %d rubles. Current user balance: %d\n", amount, s.userBalance)

	if s.dropResponse {
		// Симуляция обрыва связи: сервер списал, но пакет ответа потерян в сети!
		s.dropResponse = false // Сбрасываем для следующей попытки
		fmt.Printf(" -> [Network Glitch] TCP Connection dropped before HTTP 200 response reached client!\n")
		return false, fmt.Errorf("network timeout: client did not receive response")
	}

	return true, nil
}

func main() {
	server := &NaiveServer{
		userBalance:  10000,
		dropResponse: true, // Первый ответ потеряется
	}
	_ = context.Background()

	chargeAmount := 2000
	fmt.Printf("Initial Client Balance: %d rubles\n\n", server.userBalance)

	// НАИВНЫЙ КЛИЕНТ С ПОВТОРАМИ:
	maxRetries := 2
	for attempt := 1; attempt <= maxRetries; attempt++ {
		fmt.Printf("=== Client Attempt #%d: Sending POST /payments (Amount: %d) ===\n", attempt, chargeAmount)

		success, err := server.ChargeMoney(chargeAmount)
		if err != nil {
			fmt.Printf(" -> Client received error: %v. Retrying request...\n\n", err)
			continue
		}

		if success {
			fmt.Printf(" -> Client received SUCCESS confirmation!\n")
			break
		}
	}

	fmt.Println("\n=== Disaster Analysis: POST without Idempotency ===")
	fmt.Printf("Expected Final Balance: 8000 rubles (1 charge of %d)\n", chargeAmount)
	fmt.Printf("Actual Final Balance:   %d rubles (DOUBLE CHARGE!)\n", server.userBalance)
	fmt.Printf("Total Charges Logged:   %d\n", len(server.chargeLog))
	fmt.Println("Conclusion: HTTP POST is non-idempotent by default. Idempotency-Key is MANDATORY.")
}
```

ℹ️ Симуляция катастрофы двойного списания при наивных ретраях HTTP POST

## Под капотом

Проблема носит фундаментальный характер: сетевой сокет полудуплексный, и клиент не может различить ошибку 'сервер упал ДО обработки' от ошибки 'сервер упал ПОСЛЕ обработки'. Единственный способ устранить эту неопределенность — передача сервером детерминированного маркера.

## Подводные камни

1. Автоматические ретраи на уровне HTTP Reverse Proxy (Nginx / Envoy / Traefik): по умолчанию прокси ретраят только GET, но неправильная конфигурация `proxy_next_upstream non_idempotent` заставит прокси дублировать POST запросы клиентов.
2. Повторы браузеров при нажатии F5 (Form Resubmission).

## На собеседовании

Вопрос: Почему HTTP клиентские библиотеки (например, Go `http.Client`) никогда автоматически не ретраят POST запросы?
Ответ: По спецификации HTTP RFC 9110 клиент не имеет права повторять небезопасные (non-safe) и неидемпотентные методы без явного согласия пользователя, так как это чревато финансовым или физическим дублированием операций. Автоматический retry допустим только при наличии заголовка `Idempotency-Key`.
