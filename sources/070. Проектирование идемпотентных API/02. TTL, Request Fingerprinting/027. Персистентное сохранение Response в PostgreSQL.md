# Персистентное сохранение Response в PostgreSQL: почему Redis-only опасен для финансов

### Исходная формулировка

Объясните, почему Redis-only — рискованно для финансовых операций (eviction, persistence), и как PostgreSQL даёт durability.

## Теория

Архитектурный анализ рисков подхода **Redis-Only** для биллинга и платежей:

1. **Риск потери данных при Failover (Асинхронная репликация):**
   - Redis по умолчанию использует асинхронную репликацию на реплики.
   - Если Master подтвердил `SETNX` клиенту и мгновенно упал по питанию до репликации, Sentinel переключит Master на реплику, где ключа нет! Клиент сделает ретрай и спишет деньги повторно.
2. **Риск вытеснения по памяти (Memory Eviction):**
   - При исчерпании RAM политика `maxmemory-policy` (например, `volatile-lru` или `allkeys-lru`) удалит старые ключи идемпотентности в пользу новых запросов.
3. **Невозможность атомарной транзакции с бизнес-таблицей:**
   - Нельзя сделать `ROLLBACK` в Redis при падении коммита в PostgreSQL.

**Преимущества PostgreSQL:**
Свойство Durability (буква D в ACID): синхронная запись в WAL и fsync гарантируют, что факт обработки платежа никогда не пропадет даже при отключении электричества во всем дата-центре.

## Код решения

**`postgres_durability_store.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

// SQL DDL Schema:
// CREATE TABLE idempotency_records (
//     idempotency_key VARCHAR(128) PRIMARY KEY,
//     request_method  VARCHAR(10) NOT NULL,
//     request_path    VARCHAR(255) NOT NULL,
//     request_hash    CHAR(64) NOT NULL,
//     response_status INT NOT NULL,
//     response_body   JSONB NOT NULL,
//     response_headers JSONB NOT NULL,
//     created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
// );

type FullAuditRecord struct {
	IdempotencyKey  string            `json:"idempotency_key"`
	RequestMethod   string            `json:"request_method"`
	RequestPath     string            `json:"request_path"`
	RequestHash     string            `json:"request_hash"`
	ResponseStatus  int               `json:"response_status"`
	ResponseBody    json.RawMessage   `json:"response_body"`
	ResponseHeaders map[string]string `json:"response_headers"`
	CreatedAt       time.Time         `json:"created_at"`
}

func main() {
	record := FullAuditRecord{
		IdempotencyKey: "8f4b2386-35f9-4eb5-8e7c-ec870e8a7199",
		RequestMethod:  "POST",
		RequestPath:    "/v1/charges",
		RequestHash:    "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
		ResponseStatus: 201,
		ResponseBody:   json.RawMessage(`{"charge_id": "ch_9988", "amount": 10000, "status": "succeeded"}`),
		ResponseHeaders: map[string]string{
			"Content-Type": "application/json",
			"Location":     "/v1/charges/ch_9988",
		},
		CreatedAt: time.Now().UTC(),
	}

	marshaled, _ := json.MarshalIndent(record, "", "  ")
	fmt.Println("=== PostgreSQL Durability Record Sample ===")
	fmt.Println(string(marshaled))

	fmt.Println("\n=== Durability Comparison: PostgreSQL vs Redis ===")
	fmt.Println("| Параметр              | Redis (In-Memory)           | PostgreSQL (ACID RDBMS)     |")
	fmt.Println("|-----------------------|-----------------------------|-----------------------------|")
	fmt.Println("| Сохранность (Durability)| Слаб (AOF fsync=everysec)  | 100% (fsync on COMMIT)      |")
	fmt.Println("| Риск Eviction         | Да (при нехватке RAM)       | Нет (хранение на SSD)       |")
	fmt.Println("| Атомарность с БД      | Нет (Dual write)            | Да (единая локальная Tx)    |")
	fmt.Println("| Latency               | 0.2 - 0.5 ms                | 5 - 15 ms                   |")
	fmt.Println("| Вердикт               | High-volume телеметрия      | Финансы, биллинг, платежи   |")
}
```

ℹ️ PostgreSQL гарантирует 100% сохранность состояния идемпотентности при любых сбоях

## Под капотом

Свойство Durability в PostgreSQL обеспечивается механизмом Write-Ahead Logging (WAL). Даже если сервер потеряет питание в момент коммита, при перезапуске процедура Crash Recovery накатит изменения из WAL на страницы данных, гарантируя целостность записи идемпотентности.

## Подводные камни

1. Использование `fsync = off` в настройках PostgreSQL: уничтожает гарантии надежности ради скорости.
2. Хранение незашифрованных персональных данных в `response_body`: если в ответе есть номер банковской карты или паспортные данные, поле должно маскироваться.

## На собеседовании

Вопрос: Почему ведущие платежные платформы (Stripe, Adyen) используют реляционную БД для идемпотентности, а не Redis?
Ответ: Потому что стоимость ошибки двойного списания в финансах несопоставимо выше стоимости дополнительных 5 мс задержки. PostgreSQL позволяет зафиксировать факт списания баланса и запись ключа идемпотентности в одной неделимой транзакции ACID, что исключает любые состояния рассинхронизации данных.
