# HMAC-SHA256 для вебхуков: иммунитет к Length Extension и ConstantTimeCompare

## Условие

**HMAC-SHA256.**: Реализуйте подпись webhook-запросов или API-ответов через `crypto/hmac` + `sha256`. Покажите, почему `HMAC(key, data)` безопаснее, чем `SHA256(key || data)` (length extension attacks). Реализуйте verify с `subtle.ConstantTimeCompare`.

## Теория

При проектировании систем доставки вебхуков (Webhook Delivery: Stripe, GitHub, ЮKassa, Telegram) сервер отправляет HTTP POST-запрос стороннему сервису и обязан подтвердить подлинность полезной нагрузки с помощью заголовка `X-Signature: sha256=...`.

**Почему наивная подпись `SHA256(secret + payload)` катастрофически уязвима:**
Хэш-функции семейств MD5, SHA-1, SHA-256 используют итеративную конструкцию Меркла-Дамгора:
- Исходный массив дополняется паддингом и нарезается на блоки.
- Выходной хэш — это просто конечное состояние внутренних регистров \(A, B, C, D, E, F, G, H\).
- **Атака на расширение длины (Length Extension Attack):**
  Злоумышленник перехватывает `payload` и подпись `hash = SHA256(secret + payload)`.
  Не зная секрета `secret`, атакующий инициализирует хэшер значением `hash`, дописывает вредоносные данные `&admin=true` и получает **абсолютно валидный хэш** для сообщения `payload + padding + &admin=true`!

**Стандарт HMAC (RFC 2104):**
Вложенная конструкция:
$$\text{HMAC}(K, M) = H((K \oplus opad) \parallel H((K \oplus ipad) \parallel M))$$
Внешний проход хэширования скрывает внутреннее состояние регистров, математически исключая атаки расширения длины.

## Решение по шагам

1. Создайте секретный ключ подписи вебхуков (32 байта).
2. Напишите функцию `SignWebhookPayload(secret []byte, body []byte) string`.
3. Напишите функцию `VerifyWebhookSignature(secret []byte, body []byte, signatureHex string) bool`.
4. Используйте `subtle.ConstantTimeCompare` для безопасной верификации.
5. Продемонстрируйте защиту: попытка модификации хотя бы одного байта в JSON приводит к мгновенному отклонению.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
)

// SignWebhookPayload вычисляет безопасную цифровую подпись HMAC-SHA256
func SignWebhookPayload(secret []byte, body []byte) string {
	mac := hmac.New(sha256.New, secret)
	mac.Write(body)
	return hex.EncodeToString(mac.Sum(nil))
}

// VerifyWebhookSignature валидирует подпись вебхука в постоянном времени
func VerifyWebhookSignature(secret []byte, body []byte, signatureHex string) bool {
	expectedSigHex := SignWebhookPayload(secret, body)

	sigBytes, err := hex.DecodeString(signatureHex)
	if err != nil {
		return false
	}
	expectedBytes, err := hex.DecodeString(expectedSigHex)
	if err != nil {
		return false
	}

	// Защита от тайминг-атак
	return subtle.ConstantTimeCompare(sigBytes, expectedBytes) == 1
}

func main() {
	webhookSecret := []byte("whsec_99182_fintech_production_secret_key")

	// Тело вебхука платежного шлюза
	payload := []byte(`{"event":"payment.succeeded","order_id":8841,"amount":50000}`)

	// 1. Отправитель (Платежный шлюз): генерация подписи
	signature := SignWebhookPayload(webhookSecret, payload)

	fmt.Println("=== Промышленная валидация Webhook через HMAC-SHA256 ===")
	fmt.Printf("JSON пейлоад: %s\n", string(payload))
	fmt.Printf("Подпись в заголовке X-Signature-256: %s\n\n", signature)

	// 2. Получатель (Наш бэкенд): успешная проверка
	isValid := VerifyWebhookSignature(webhookSecret, payload, signature)
	fmt.Printf("Проверка легитимного вебхука: %v (УСПЕХ)\n", isValid)

	// 3. Атака: перехватчик подменил order_id или сумму
	tamperedPayload := []byte(`{"event":"payment.succeeded","order_id":8841,"amount":99999}`)
	isTamperedValid := VerifyWebhookSignature(webhookSecret, tamperedPayload, signature)
	fmt.Printf("Проверка поддельного вебхука: %v (АТАКА ПРЕДОТВРАЩЕНА!)\n", isTamperedValid)
}
```

## Под капотом

Почему HMAC-SHA256 защищен от Length Extension Attack:
1. В конструкции Меркла-Дамгора: \(\text{Hash}(M) = \text{State}_{\text{final}}\).
2. В наивной схеме \(\text{Hash}(K \parallel M)\) состояние регистров после обработки \(M\) раскрывается вызывающей стороне в виде значения самого хэша.
3. В HMAC:
   - Внутренний хэш вычисляет \(H_{in} = H((K \oplus ipad) \parallel M)\).
   - Внешний хэш вычисляет \(H_{out} = H((K \oplus opad) \parallel H_{in})\).
   Даже зная значение \(H_{out}\), злоумышленник не знает значения \(H_{in}\), и тем более не знает ключа \(K \oplus opad\). Попытка дописать данные в конец вызовет сбой внешнего хэша, делая атаку математически неосуществимой.

## Подводные камни

1. **Проверка подписи после парсинга JSON:** Если разработчик сначала парсит JSON в `map[string]any`, а затем сериализует его обратно `json.Marshal(obj)` для проверки подписи — порядок ключей в JSON изменится, и подпись не совпадет! Подпись должна проверяться **строго по сырым байтам** тела запроса (`io.ReadAll(r.Body)`).
2. **Replay-атаки (Повторное воспроизведение):** Подпись подтверждает целостность, но не уникальность. Злоумышленник может перехватить валидный вебхук и отправить его 100 раз подряд. Защита: передавать временную метку `t=1710000000` в заголовке и включать её в подписываемые данные.

## На собеседовании

**Вопрос с собеседования:** Как устроен механизм защиты от Replay-атак в вебхуках Stripe и GitHub?
**Ответ:** В заголовок запроса передается временная метка и подпись: `Stripe-Signature: t=1614000000,v1=5257a...`.
1. Подпись вычисляется поверх строки: `t + "." + request_body`.
2. Сервер-получатель сначала парсит `t` и проверяет, что `time.Now() - t <= 5 * time.Minute` (защита от устаревших повторных пакетов).
3. Затем сервер вычисляет HMAC от `t + "." + rawBody` и сверяет с `v1` через `subtle.ConstantTimeCompare`. Это одновременно защищает от изменения данных, от подделки времени и от повторной отправки старых вебхуков.
