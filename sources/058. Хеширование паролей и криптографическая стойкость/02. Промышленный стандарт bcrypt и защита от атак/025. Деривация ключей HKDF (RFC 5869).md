# Деривация ключей HKDF (RFC 5869): безопасное формирование 32-байтных ключей AES

## Условие

**Деривация ключей (HKDF)**: У пользователя есть пароль, но для AES-шифрования тебе нужен ключ ровно в 32 байта. Используй `golang.org/x/crypto/hkdf`, чтобы безопасно "растянуть" пароль пользователя (с добавлением соли) до 32-байтного криптографического ключа.

### Исходная формулировка

**Деривация ключей (HKDF)**: У пользователя есть пароль, но для AES-шифрования тебе нужен ключ ровно в 32 байта. Используй `golang.org/x/crypto/hkdf`, чтобы безопасно "растянуть" пароль пользователя (с добавлением соли) до 32-байтного криптографического ключа.

## Теория

В криптографических протоколах исходный материал ключа (Input Keying Material, IKM) часто имеет неравномерное распределение энтропии или не совпадает по длине с требованиями шифра (например, общий секрет Диффи-Хеллмана ECDH имеет длину 32 байта, но требует разделения на ключ шифрования, ключ аутентификации и IV).

Стандарт **HKDF (HMAC-based Extract-and-Expand Key Derivation Function, RFC 5869)**:
Состоит из двух независимых фаз:
1. **HKDF-Extract(salt, IKM) \(\to\) PRK:**
   - Извлекает псевдослучайный мастер-ключ фиксированной длины (PRK, 32 байта для SHA-256) из сырого источника энтропии с добавлением соли:
     $$\text{PRK} = \text{HMAC-Hash}(\text{salt}, \text{IKM})$$
2. **HKDF-Expand(PRK, info, L) \(\to\) OKM:**
   - Безопасно «растягивает» PRK до запрошенной длины \(L\) байт (Output Keying Material).
   - Примешивает контекстную строку `info` (контекст домена, например `"aes-encryption-key"`, `"hmac-auth-key"`), гарантируя, что ключи для разных подсистем будут криптографически ортогональны и независимы.

В Go официальная библиотека `golang.org/x/crypto/hkdf` предоставляет удобный интерфейс `io.Reader`.

## Решение по шагам

1. Создайте исходный секрет `ikm` (например, общий секрет сессии или мастер-токен).
2. Сгенерируйте случайную соль `salt` (16 байт).
3. Настройте контекстную метку `info` (например, `"handshake-aes-256-gcm-key"`).
4. Инициализируйте HKDF ридер с помощью `hkdf.New(sha256.New, ikm, salt, info)`.
5. С помощью `io.ReadFull` прочитайте ровно 32 байта целевого ключа AES.
6. Продемонстрируйте: при изменении строки `info` формируется совершенно другой независимый ключ.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"log"

	"golang.org/x/crypto/hkdf"
)

// DeriveKeyHKDF формирует криптографический ключ заданной длины из мастер-секрета
func DeriveKeyHKDF(masterSecret, salt, info []byte, keyLen int) ([]byte, error) {
	// Инициализируем генератор HKDF на базе SHA-256
	hkdfReader := hkdf.New(sha256.New, masterSecret, salt, info)

	derivedKey := make([]byte, keyLen)
	// Читаем запрошенное число байт
	if _, err := io.ReadFull(hkdfReader, derivedKey); err != nil {
		return nil, fmt.Errorf("ошибка деривации HKDF: %w", err)
	}

	return derivedKey, nil
}

func main() {
	// Исходный мастер-секрет (IKM)
	masterSecret := []byte("diffie-hellman-shared-secret-or-passphrase-2026")

	// Случайная соль (рекомендовано 16-32 байта)
	salt := make([]byte, 16)
	io.ReadFull(rand.Reader, salt)

	// 1. Деривация ключа шифрования AES-256 (32 байта)
	encInfo := []byte("tls-v1.3:aes-256-gcm:data-encryption-key")
	aesKey, err := DeriveKeyHKDF(masterSecret, salt, encInfo, 32)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	// 2. Деривация ключа аутентификации HMAC (32 байта) с ДРУГОЙ строкой info
	authInfo := []byte("tls-v1.3:hmac-sha256:integrity-auth-key")
	hmacKey, err := DeriveKeyHKDF(masterSecret, salt, authInfo, 32)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	fmt.Println("=== Формирование ключей через HKDF (RFC 5869) ===")
	fmt.Printf("Исходный мастер-секрет: %s\n", string(masterSecret))
	fmt.Printf("Случайная соль (hex):   %s\n\n", hex.EncodeToString(salt))

	fmt.Printf("Ключ AES-256 (32 байта):  %s\n", hex.EncodeToString(aesKey))
	fmt.Printf("Ключ HMAC (32 байта):     %s\n\n", hex.EncodeToString(hmacKey))

	// 3. Тест: использование сгенерированного ключа в AES-GCM
	block, err := aes.NewCipher(aesKey)
	if err != nil {
		log.Fatalf("Ошибка создания AES: %v", err)
	}
	gcm, _ := cipher.NewGCM(block)
	nonce := make([]byte, gcm.NonceSize())
	io.ReadFull(rand.Reader, nonce)

	ciphertext := gcm.Seal(nil, nonce, []byte("Конфиденциальный пейлоад микросервиса"), nil)
	fmt.Printf("Шифрование AES-GCM на деривированном ключе успешно: %d байт шифротекста\n", len(ciphertext))
}
```

## Под капотом

Математическая формула HKDF-Expand:
Пусть запрошена длина \(L\) байт. Число блоков \(N = \lceil L / \text{HashLen} \rceil\).
Блоки вычисляются рекурсивно:
$$T(0) = \text{empty}$$
$$T(1) = \text{HMAC-Hash}(\text{PRK}, T(0) \parallel \text{info} \parallel 0x01)$$
$$T(2) = \text{HMAC-Hash}(\text{PRK}, T(1) \parallel \text{info} \parallel 0x02)$$
$$\dots$$
$$T(N) = \text{HMAC-Hash}(\text{PRK}, T(N-1) \parallel \text{info} \parallel N)$$
$$\text{OKM} = \text{first } L \text{ bytes of } (T(1) \parallel T(2) \parallel \dots \parallel T(N))$$
Каждый блок связывается с предыдущим и включает однобайтный счетчик раунда, гарантируя псевдослучайность и предотвращая зацикливание потока.

## Подводные камни

1. **Использование HKDF для паролей человека:** HKDF — быстрый алгоритм, он **НЕ является memory-hard** и не содержит тысяч итераций замедления. Он предназначен для деривации ключей из данных с высокой энтропией (ECDH shared secret). Для паролей людей (низкая энтропия) обязателен Password-Based KDF: Argon2id или scrypt!
2. **Одинаковая строка info для разных ключей:** Если для ключа шифрования и ключа подписи передать одинаковый `info = "my-key"`, вы получите абсолютно одинаковые ключи (Key Reuse), что нарушает безопасность криптосистемы.

## На собеседовании

**Вопрос с собеседования:** В чем ключевое отличие между HKDF (RFC 5869) и PBKDF2 (RFC 2898), и в каких сценариях каждый из них применяется?
**Ответ:** 1) **HKDF (HMAC-based KDF):** Применяется, когда входные данные **уже обладают высокой криптографической энтропией** (например, 256-битный общий секрет Диффи-Хеллмана в TLS 1.3 / Signal). HKDF выполняется за 1–2 быстрых вызова HMAC (~1 микросекунда) и предназначен для разделения секрета на независимые ключи шифрования, аутентификации и векторы инициализации. 2) **PBKDF2 / Argon2id:** Применяются, когда входные данные — это **низкоэнтропийный пароль человека** (8–12 символов). Они намеренно тратят сотни миллисекунд CPU и мегабайты памяти, замедляя перебор на GPU.
