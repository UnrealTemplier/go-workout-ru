# Сетевые тайминг-атаки: бенчмарк сравнения префиксов и аудит через testing.B

## Условие

**Timing attacks и constant-time сравнение.**: Напишите наивную проверку API-ключа (`if token == storedToken`) и измерьте время выполнения через `testing.B` с разными префиксами. Затем используйте `crypto/subtle.ConstantTimeCompare`. Объясните, почему `==` на строках уязвим для timing-атак.

## Теория

Сравнение строк оператором `==` в Go оптимизировано для обычной бизнес-логики: компилятор использует ранний выход из цикла при первом несовпадающем байте.

В криптографических приложениях эта оптимизация превращается в уязвимость:
- Время выполнения \(T = c_0 + c_1 \cdot K\), где \(K\) — количество совпавших байт с начала строки.
- Если злоумышленник подбирает 32-байтный токен:
  - При 0 совпавших байт процессор выполняет \(\sim 3\) такта.
  - При 16 совпавших байтах процессор выполняет \(\sim 20\) тактов.
  - При полном совпадении процессор проходит все 32 байта.

Хотя в наносекундном масштабе разница мала, современные алгоритмы сетевого статистического фильтра (Box-Cox transformation, Welch's t-test) позволяют атакующему надежно различать задержки в 10–20 наносекунд даже через 5 сетевых маршрутизаторов.

## Решение по шагам

1. Создайте функции `InsecureCheck(a, b string) bool` и `SecureCheck(a, b string) bool`.
2. Подготовьте эталонный токен длиной 64 байта.
3. Подготовьте тестовые токены с 0, 16, 32 и 64 совпадающими префиксными байтами.
4. Проведите бенчмарк времени вычисления для каждого сценария на 5 000 000 итераций.
5. Продемонстрируйте: в `InsecureCheck` время линейно растет по мере совпадения префикса, а в `SecureCheck` время строго неизменно.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/subtle"
	"fmt"
	"strings"
	"time"
)

func InsecureCheck(candidate, secret string) bool {
	return candidate == secret
}

func SecureCheck(candidate, secret string) bool {
	return subtle.ConstantTimeCompare([]byte(candidate), []byte(secret)) == 1
}

func benchOperation(fn func(string, string) bool, candidate, secret string, iters int) time.Duration {
	t0 := time.Now()
	for i := 0; i < iters; i++ {
		_ = fn(candidate, secret)
	}
	return time.Since(t0)
}

func main() {
	// Секретный токен длиной 64 символа
	secret := strings.Repeat("K", 64)

	// Кандидаты с разной степенью совпадения префикса:
	cand0 := strings.Repeat("0", 64)                         // 0 совпадений
	cand16 := strings.Repeat("K", 16) + strings.Repeat("0", 48) // 16 совпадений
	cand32 := strings.Repeat("K", 32) + strings.Repeat("0", 32) // 32 совпадения
	cand64 := strings.Repeat("K", 64)                         // 64 совпадения (100%)

	iters := 5_000_000

	fmt.Println("=== Исследование тайминг-атаки на оператор '==' ===")
	d0 := benchOperation(InsecureCheck, cand0, secret, iters)
	d16 := benchOperation(InsecureCheck, cand16, secret, iters)
	d32 := benchOperation(InsecureCheck, cand32, secret, iters)
	d64 := benchOperation(InsecureCheck, cand64, secret, iters)

	fmt.Printf("0  совпадений: %v (Базовое время отказа)\n", d0)
	fmt.Printf("16 совпадений: %v\n", d16)
	fmt.Printf("32 совпадения: %v\n", d32)
	fmt.Printf("64 совпадения: %v (Максимальное время, все байты проверены)\n\n", d64)

	fmt.Println("=== Защищенное сравнение crypto/subtle.ConstantTimeCompare ===")
	sd0 := benchOperation(SecureCheck, cand0, secret, iters)
	sd16 := benchOperation(SecureCheck, cand16, secret, iters)
	sd32 := benchOperation(SecureCheck, cand32, secret, iters)
	sd64 := benchOperation(SecureCheck, cand64, secret, iters)

	fmt.Printf("0  совпадений: %v\n", sd0)
	fmt.Printf("16 совпадений: %v\n", sd16)
	fmt.Printf("32 совпадения: %v\n", sd32)
	fmt.Printf("64 совпадения: %v\n", sd64)

	maxDelta := float64(sd64-sd0) / float64(sd0) * 100.0
	fmt.Printf("\nМаксимальный разброс в crypto/subtle: %.2f%% (Время константно!)\n", maxDelta)
}
```

ℹ️ Бенчмарк времени проверки префиксов токена: утечка в операторе == против crypto/subtle

## Под капотом

Почему тайминг-атаки работают на современных процессорах с Out-of-Order исполнением:
1. Процессор использует блок предсказания ветвлений (Branch Predictor).
2. При выполнении обычного цикла сравнения `for i := 0; i < len; i++ { if a[i] != b[i] { return false } }` процессор спекулятивно предполагает, что условие выхода не сработает.
3. Когда происходит несовпадение, процессор сбрасывает конвейер инструкций (Pipeline Flush / Branch Misprediction Penalty), что занимает от 15 до 20 тактов.
4. В `subtle.ConstantTimeCompare` ветвления отсутствуют вовсе — команды выполняются строго линейно через инструкции `OR` и `XOR`, не вызывая сбросов конвейера и флуктуаций времени.

## Подводные камни

1. **Проведение замеров на одном ядре без учета Turbo Boost:** Динамическое изменение частоты процессора (Intel Turbo Boost / AMD Precision Boost) может вносить шум в бенчмарки. В продакшене тесты таймингов проводят с фиксированной частотой CPU.
2. **Игнорирование сборщика мусора:** Если во время проверки токена сработает GC, задержка ответа подскочит на миллисекунды. Поэтому криптографические проверки не должны аллоцировать память в куче (`0 B/op`).

## На собеседовании

**Вопрос с собеседования:** Как уязвимость тайминга в функции `memcmp` позволила взломать систему авторизации игровой консоли Xbox 360?
**Ответ:** Прошивка консоли проверяла цифровую подпись загрузчика (HMAC) с помощью стандартной функции `memcmp`, завершавшейся на первом несовпавшем байте. Хакеры подключили высокоточный осциллограф к шине процессора и замеряли задержку до перезагрузки консоли. Перебирая первый байт от 0x00 до 0xFF, они нашли байт, вызывавший задержку на 1 такт дольше. Зафиксировав его, они аналогично подобрали второй и все последующие байты. За несколько часов подпись была полностью сфальсифицирована, что позволило запускать неподписанный кастомный код.
