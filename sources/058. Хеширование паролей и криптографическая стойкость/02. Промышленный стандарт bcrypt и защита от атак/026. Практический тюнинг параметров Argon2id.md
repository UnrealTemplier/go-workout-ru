# Практический тюнинг параметров Argon2id под профиль серверной нагрузки

## Условие

**argon2id: современный стандарт.**: Реализуйте хеширование через `golang.org/x/crypto/argon2`. Используйте параметры: time=1, memory=64 MB, threads=4, salt=16 байт (из `crypto/rand`), key length=32. Объясните, как подбирать параметры под ваш CPU/память.

## Теория

Настройка параметров Argon2id в реальном продакшене — это инженерная задача оптимизации с ограничениями:
1. **Защита от взлома:** Чем выше `memory` и `time`, тем сложнее и дороже хакеру подбирать пароли.
2. **Доступность сервиса (SLA / DoS Resilience):** Чем выше параметры, тем больше CPU и RAM потребляет каждый запрос `/api/login`.

Алгоритм калибровки параметров Argon2id под конкретный сервер (RFC 9106 Tuning Guide):
1. **Фиксация потоков (`threads`):** Устанавливается равным количеству процессорных ядер, доступных контейнеру (обычно \(p = 2\) или \(p = 4\)).
2. **Выделение максимальной памяти (`memory`):** Выбирается максимально возможный объем ОЗУ на одну операцию, который сервер может позволить без риска OOM при пиковой нагрузке (золотой стандарт — **64 МБ** = 65 536 КиБ).
3. **Калибровка времени (`time`):** Подбирается минимальное число итераций \(t \ge 1\) так, чтобы время одного вычисления на сервере укладывалось в интервал **от 150 до 300 миллисекунд**.

## Решение по шагам

1. Создайте утилиту автокалибровки `BenchmarkArgon2Settings(memoryMB, iterations, threads int)`.
2. Замерьте среднее время хэширования на локальной машине при 16 МБ, 32 МБ и 64 МБ памяти.
3. Рассчитайте максимальный допустимый RPS сервера авторизации без риска исчерпания RAM.
4. Продемонстрируйте генерацию хэша с выверенными параметрами.
5. Сформулируйте правила мониторинга метрик памяти в Prometheus.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"io"
	"time"

	"golang.org/x/crypto/argon2"
)

// BenchmarkArgon2 замеряет производительность связки параметров
func BenchmarkArgon2(memMB uint32, timeRounds uint32, threads uint8) time.Duration {
	password := []byte("CalibrationPasswordTest#2026")
	salt := make([]byte, 16)
	io.ReadFull(rand.Reader, salt)

	t0 := time.Now()
	_ = argon2.IDKey(password, salt, timeRounds, memMB*1024, threads, 32)
	return time.Since(t0)
}

func main() {
	fmt.Println("=== Автокалибровка параметров Argon2id под сервер ===")
	fmt.Println("Память (RAM) | Итерации | Потоки | Время расчёта | Оценка защиты")
	fmt.Println("-------------+-----------+--------+---------------+-------------------")

	testProfiles := []struct {
		memMB   uint32
		rounds  uint32
		threads uint8
		label   string
	}{
		{16, 2, 2, "IoT / Мобильный профиль"},
		{32, 1, 4, "Легкий микросервис (Low RAM)"},
		{64, 1, 4, "OWASP Enterprise Recommended"},
		{64, 2, 4, "High-Security Banking Profile"},
	}

	for _, p := range testProfiles {
		duration := BenchmarkArgon2(p.memMB, p.rounds, p.threads)
		fmt.Printf("    %2d МБ    |     %d     |    %d   | %13v | %s\n",
			p.memMB, p.rounds, p.threads, duration, p.label)
	}

	fmt.Println("\n=== Инженерные рекомендации по сайзингу памяти ===")
	fmt.Println("При m=64MB, t=1, p=4: вычисление занимает ~50-100 мс.")
	fmt.Println("Лимит памяти пода Kubernetes должен рассчитываться как:")
	fmt.Println("MemoryLimit = (BaselineRAM + ConcurrentLogins * 64Mi) * 1.5 SafetyBuffer")
}
```

## Под капотом

Как подбирать параметры Argon2id под ограничения контейнеров (Kubernetes cgroups):
1. В Kubernetes лимит памяти жестко контролируется подсистемой ядра Linux `memory.max` (cgroups v2).
2. Если в поде с `limits.memory = 512Mi` одновременно запустятся 8 запросов логина с \(m = 64\) МБ, суммарный объем выделенной памяти составит \(8 \times 64 = 512\) МБ. Девятый запрос приведет к немедленному сигналу `SIGKILL` от OOM-киллера ядра!
3. Для предотвращения падения пода внедряется **семафор ограниченного параллелизма**:
   ```go
   var authSemaphore = make(chan struct{}, 4) // не более 4 одновременных Argon2
   ```
   Лишние запросы ожидают в очереди либо отклоняются HTTP 429 Too Many Requests.

## Подводные камни

1. **Увеличение итераций вместо памяти:** Попытка компенсировать малый объем памяти (\(m=4\) МБ) увеличением числа итераций (\(t=20\)) уязвима к GPU-атакам: видеокарта все равно параллельно разместит миллионы потоков в VRAM. Память — первичный фактор защиты Argon2!
2. **Параллелизм выше числа CPU:** Установка \(p=16\) на 2-ядерном контейнере приводит к просадке производительности из-за конкуренции горутин за CPU.

## На собеседовании

**Вопрос с собеседования:** Почему при использовании Argon2id в микросервисах необходимо ограничивать количество одновременных операций хэширования через семафор (`chan struct{}`)?
**Ответ:** Поскольку каждая операция Argon2id с рекомендациями OWASP гарантированно аллоцирует ровно 64 МБ оперативной памяти, всплеск из 100 одновременных запросов аутентификации (например, атака Credential Stuffing) потребует мгновенного выделения 6.4 ГБ RAM. Контейнер будет аварийно уничтожен Linux OOM Killer. Семафор с буфером (например, на 4–8 слотов) гарантирует жесткий потолок потребления памяти (не более \(8 \times 64 = 512\) МБ), сохраняя стабильность сервиса даже при DoS-атаках.
