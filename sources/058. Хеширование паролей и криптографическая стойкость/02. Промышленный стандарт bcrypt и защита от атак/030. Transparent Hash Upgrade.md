# Transparent Hash Upgrade: бесшовная миграция с bcrypt на Argon2id при логине

## Условие

**Transparent hash upgrade.**: Реализуйте middleware: при успешном логине проверяете пароль против старого bcrypt-хеша, если совпало — перехешируете в argon2id и обновляете в БД. Объясните стратегию миграции без сброса паролей всех пользователей.

## Теория

При модернизации устаревших монолитов (где пароли хранились в MD5, SHA-256 или старом bcrypt) компания сталкивается с дилеммой: открытые пароли пользователей неизвестны, поэтому перехэшировать всю базу данных разом в новый алгоритм (Argon2id) невозможно.

Принудительный сброс паролей всех 10 миллионов пользователей («пожалуйста, перейдите по ссылке и задайте новый пароль») вызывает гигантский отток клиентов (Churn Rate) и парализует службу поддержки.

**Паттерн Transparent Hash Upgrade (Прозрачный апгрейд хэшей «на лету»):**
1. При авторизации сервер считывает хэш из базы данных и анализирует его префикс:
   - Если хэш начинается на `$2a$` или `$2b$` — это старый **bcrypt**.
   - Если хэш начинается на `$argon2id$` — это современный **Argon2id**.
2. Сервер валидирует введенный пароль через соответствующий алгоритм (для bcrypt — `bcrypt.CompareHashAndPassword`).
3. Если пароль верен, но алгоритм устаревший:
   - Сервер прямо в памяти берет открытый пароль `plainPassword`, пока он доступен в текущем запросе.
   - Вычисляет новый хэш **Argon2id**.
   - Асинхронно обновляет строку пользователя в БД.
4. За 3–6 месяцев до 90% активных пользователей автоматически и незаметно переходят на Argon2id без единого письма и сброса!

## Решение по шагам

1. Создайте модель `User` со старым bcrypt-хэшем в памяти.
2. Реализуйте метод `LoginAndUpgrade(username, password string) (bool, error)`.
3. Определите тип хэша по префиксу строки (`$2a$` vs `$argon2id$`).
4. Проверьте пароль через старый bcrypt.
5. При успешной проверке сгенерируйте хэш Argon2id и обновите запись в базе.
6. Продемонстрируйте: при следующем логине проверка проходит уже напрямую через быстрый и безопасный Argon2id.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/base64"
	"fmt"
	"io"
	"log"
	"strings"

	"golang.org/x/crypto/argon2"
	"golang.org/x/crypto/bcrypt"
)

// UserAccount хранит состояние пользователя в БД
type UserAccount struct {
	Username     string
	PasswordHash string // может быть как $2a$ (bcrypt), так и $argon2id$
}

// hashArgon2id создает строку PHC Argon2id
func hashArgon2id(password string) (string, error) {
	salt := make([]byte, 16)
	io.ReadFull(rand.Reader, salt)
	hash := argon2.IDKey([]byte(password), salt, 1, 64*1024, 4, 32)

	b64Salt := base64.RawStdEncoding.EncodeToString(salt)
	b64Hash := base64.RawStdEncoding.EncodeToString(hash)
	return fmt.Sprintf("$argon2id$v=%d$m=65536,t=1,p=4$%s$%s", argon2.Version, b64Salt, b64Hash), nil
}

// verifyArgon2id проверяет хэш Argon2id
func verifyArgon2id(password, storedHash string) bool {
	parts := strings.Split(storedHash, "$")
	if len(parts) != 6 {
		return false
	}
	salt, _ := base64.RawStdEncoding.DecodeString(parts[4])
	expected, _ := base64.RawStdEncoding.DecodeString(parts[5])

	computed := argon2.IDKey([]byte(password), salt, 1, 64*1024, 4, 32)
	return subtle.ConstantTimeCompare(computed, expected) == 1
}

// LoginWithTransparentUpgrade проверяет пароль и бесшовно обновляет устаревший хэш
func LoginWithTransparentUpgrade(user *UserAccount, inputPassword string) (bool, bool, error) {
	hash := user.PasswordHash
	var isCorrect bool
	var neededUpgrade bool

	// 1. Проверяем старый bcrypt ($2a$ или $2b$)
	if strings.HasPrefix(hash, "$2a$") || strings.HasPrefix(hash, "$2b$") {
		err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(inputPassword))
		if err == nil {
			isCorrect = true
			neededUpgrade = true // Пароль верен, но алгоритм устарел -> апгрейдим!
		}
	} else if strings.HasPrefix(hash, "$argon2id$") {
		// 2. Современный Argon2id
		if verifyArgon2id(inputPassword, hash) {
			isCorrect = true
			neededUpgrade = false
		}
	}

	if !isCorrect {
		return false, false, nil
	}

	// 3. Выполняем бесшовный апгрейд на лету
	if neededUpgrade {
		newHash, err := hashArgon2id(inputPassword)
		if err != nil {
			return true, false, fmt.Errorf("ошибка генерации нового хэша: %w", err)
		}
		// Обновляем в БД:
		user.PasswordHash = newHash
		return true, true, nil
	}

	return true, false, nil
}

func main() {
	userPass := "CorporateSuperMaster2026!"

	// Создаем пользователя со старым bcrypt-хэшем в БД
	oldBcryptHash, _ := bcrypt.GenerateFromPassword([]byte(userPass), 10)
	user := &UserAccount{
		Username:     "alex",
		PasswordHash: string(oldBcryptHash),
	}

	fmt.Println("=== До миграции: состояние БД ===")
	fmt.Printf("Текущий хэш пользователя: %s (Формат: bcrypt)\n\n", user.PasswordHash[:25]+"...")

	// 1. Первый логин: срабатывает прозрачный апгрейд
	fmt.Println("=== Попытка 1: Первый вход пользователя ===")
	authOk, upgraded, err := LoginWithTransparentUpgrade(user, userPass)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	fmt.Printf("Авторизация успешна?   %v\n", authOk)
	fmt.Printf("Выполнен апгрейд хэша? %v (Хэш бесшовно переписан на Argon2id!)\n", upgraded)
	fmt.Printf("Новый хэш в БД:         %s\n\n", user.PasswordHash[:35]+"...")

	// 2. Второй логин: апгрейд уже не требуется, проверка идет через Argon2id
	fmt.Println("=== Попытка 2: Повторный вход пользователя ===")
	authOk2, upgraded2, _ := LoginWithTransparentUpgrade(user, userPass)
	fmt.Printf("Авторизация успешна?   %v\n", authOk2)
	fmt.Printf("Выполнен апгрейд хэша? %v (Уже актуальный Argon2id)\n", upgraded2)
}
```

## Под капотом

Как устроена стратегия миграции неактивных пользователей:
1. За несколько месяцев активная аудитория (70–90%) обновляется естественным путем при входе.
2. Для оставшихся «мертвых» или редких аккаунтов, которые не логинились более 6–12 месяцев:
   - Сервер сохраняет старый хэш bcrypt.
   - Когда пользователь однажды возвращается, он всё равно успешно проходит авторизацию через блок `if bcrypt` и тут же мигрирует.
   - Через 1–2 года для оставшихся неактивных аккаунтов можно принудительно включить флаг `requires_password_reset = true`.

## Подводные камни

1. **Синхронная блокировка ответа клиенту:** Перехэширование в Argon2id (64 МБ, ~60 мс) добавляется к времени проверки старого bcrypt (~60 мс), увеличивая задержку ответа до 120 мс. В большинстве случаев это допустимо, но обновление в БД можно вынести в отдельную горутину `go db.UpdateHash(user.ID, newHash)` при наличии контекста.
2. **Откат транзакции при ошибке перехэширования:** Если новый хэш не удалось сохранить в БД (например, сбой сети), вход пользователя **не должен блокироваться**. Пользователь успешно входит, а апгрейд повторится при следующем логине.

## На собеседовании

**Вопрос с собеседования:** Как архитектурно защитить базу данных, если компания приобрела стартап, где пароли 5 миллионов пользователей хранились в открытом виде или в небезопасном MD5?
**Ответ:** Применяется стратегия **Double-Hashing Migration (Двойное оборачивание)**:
1. В день закрытия сделки запускается пакетная оффлайн-миграция всей базы данных без участия пользователей: каждый существующий MD5-хэш оборачивается современным KDF:
   $$\text{NewHash} = \text{Argon2id}(\text{OldMD5Hash}, \text{salt})$$
   База мгновенно становится защищенной от утечек.
2. В коде аутентификации логика проверки обновляется:
   `Argon2id.Verify(MD5(inputPassword), user.PasswordHash)`
3. Когда пользователь вводит пароль при входе, сервис проверяет двойной хэш, извлекает чистый открытый пароль и выполняет Transparent Upgrade, сохраняя чистый `Argon2id(inputPassword)`. База полностью очищается от следов MD5.
