# HMAC (Keyed-Hash Message Authentication Code): подпись и валидация через hmac.Equal

## Условие

**HMAC (Аутентификация сообщений)**: Тебе нужно передать данные клиенту и убедиться, что он их не подделал. Используй `crypto/hmac` с SHA-256 и секретным ключом сервера, чтобы сгенерировать подпись для строки. Напиши функцию валидации этой подписи.

## Теория

Симметричная аутентификация сообщений (Message Authentication Code, MAC) необходима, когда сервер передает клиенту состояние (Cookie, URL-параметры перенаправления, корзину товаров) и должен быть абсолютно уверен, что при возврате данных клиент не изменил ни единого байта.

Стандарт **HMAC (RFC 2104 / FIPS 198-1)**:
$$\text{HMAC}(K, M) = H((K \oplus opad) \parallel H((K \oplus ipad) \parallel M))$$
где:
- \(K\) — секретный ключ сервера.
- \(ipad\) (inner pad) — байт `0x36`, повторенный \(B\) раз (\(B = 64\) байта для SHA-256).
- \(opad\) (outer pad) — байт `0x5C`, повторенный \(B\) раз.
- \(M\) — передаваемое сообщение.

Ключевые свойства HMAC:
1. **Невозможность подделки (Unforgeability):** Без знания секрета \(K\) клиент не может рассчитать валидный HMAC для измененных данных.
2. **Иммунитет к Length Extension:** Двухпроходная структура полностью устраняет уязвимость удлинения сообщения.
3. **Безопасная валидация:** Функция `hmac.Equal(macA, macB)` выполняет сравнение строго в constant-time.

## Решение по шагам

1. Определите секретный ключ сервера (минимум 32 байта).
2. Реализуйте функцию подписания `SignMessage(secretKey []byte, message string) string`.
3. Закодируйте HMAC-подпись в hex-строку.
4. Реализуйте функцию проверки `VerifyMessage(secretKey []byte, message, signatureHex string) bool`.
5. Продемонстрируйте защиту: при попытке изменить хотя бы один символ в сообщении функция `VerifyMessage` возвращает `false`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

// SignMessage подписывает произвольную строку секретным ключом через HMAC-SHA256
func SignMessage(secretKey []byte, message string) string {
	mac := hmac.New(sha256.New, secretKey)
	mac.Write([]byte(message))
	signature := mac.Sum(nil)
	return hex.EncodeToString(signature)
}

// VerifyMessage проверяет подлинность сообщения с защитой от тайминг-атак
func VerifyMessage(secretKey []byte, message, signatureHex string) bool {
	expectedSigHex := SignMessage(secretKey, message)

	sigBytes, err := hex.DecodeString(signatureHex)
	if err != nil {
		return false
	}
	expectedBytes, err := hex.DecodeString(expectedSigHex)
	if err != nil {
		return false
	}

	// hmac.Equal выполняет сравнение строго за постоянное время (crypto/subtle)
	return hmac.Equal(sigBytes, expectedBytes)
}

func main() {
	serverSecret := []byte("master_secret_hmac_key_2026_fintech_auth")

	// 1. Формируем состояние сессии пользователя для передачи в Cookie
	userSessionPayload := "user_id=4091&role=billing_viewer&balance=10000"
	signature := SignMessage(serverSecret, userSessionPayload)

	fmt.Println("=== Симметричная аутентификация сообщений (HMAC-SHA256) ===")
	fmt.Printf("Исходные данные: %s\n", userSessionPayload)
	fmt.Printf("HMAC подпись:    %s\n\n", signature)

	// 2. Клиент возвращает исходные данные и подпись без изменений
	isValid := VerifyMessage(serverSecret, userSessionPayload, signature)
	fmt.Printf("Проверка легитимных данных клиента: %v (ПОДТВЕРЖДЕНО)\n", isValid)

	// 3. Атака: клиент пытается повысить баланс или сменить роль на admin
	tamperedPayload := "user_id=4091&role=super_admin&balance=999999"
	isTamperedValid := VerifyMessage(serverSecret, tamperedPayload, signature)
	fmt.Printf("Проверка модифицированных данных:    %v (ОТКЛОНЕНО СЕРВЕРОМ!)\n", isTamperedValid)

	// 4. Атака: попытка изменить хотя бы одну цифру баланса
	subtleTamper := "user_id=4091&role=billing_viewer&balance=10001"
	isSubtleValid := VerifyMessage(serverSecret, subtleTamper, signature)
	fmt.Printf("Проверка изменения 1 цифры:          %v (ОТКЛОНЕНО СЕРВЕРОМ!)\n", isSubtleValid)
}
```

## Под капотом

Реализация `hmac.Equal` в стандартной библиотеке Go:
```go
func Equal(mac1, mac2 []byte) bool {
    return subtle.ConstantTimeCompare(mac1, mac2) == 1
}
```
Почему HMAC безопаснее простого `Hash(Key + Message)`:
1. Конструкция `H(Key || Message)` уязвима к Length Extension Attack (атака удлинения сообщения).
2. Конструкция `H(Message || Key)` уязвима к коллизиям в хэш-функции: если атакующий находит коллизию \(M_1\) и \(M_2\) (\(H(M_1) = H(M_2)\)), то \(\text{MAC}(M_1) = \text{MAC}(M_2)\) для любого ключа!
3. HMAC математически доказывает псевдослучайность функции (PRF), пока базовая функция \(H\) устойчива к коллизиям в раундах сжатия.

## Подводные камни

1. **Использование короткого ключа HMAC (меньше размера блока):** Ключ HMAC для SHA-256 должен иметь длину не менее 32 байт (рекомендовано 32–64 байта). Ключ из 4 символов (`"1234"`) легко перебирается по словарю в офлайн-режиме.
2. **Использование `bytes.Equal` вместо `hmac.Equal`:** Использование `bytes.Equal` открывает сервис для побайтовых тайминг-атак на подпись.

## На собеседовании

**Вопрос с собеседования:** В чем разница между шифрованием (Encryption) и HMAC-аутентификацией, и почему HMAC не обеспечивает конфиденциальность?
**Ответ:** Шифрование обеспечивает **конфиденциальность (Confidentiality)**: скрывает смысл данных от третьих лиц. HMAC обеспечивает **целостность (Integrity)** и **аутентификацию источника (Authenticity)**: гарантирует, что данные были созданы доверенным сервером и не были модифицированы в пути. При этом данные в HMAC передаются **открытым текстом** (любой наблюдатель может прочитать `user_id=4091`). Если требуется одновременно и конфиденциальность, и аутентификация, применяется режим AEAD (AES-GCM) или схема Encrypt-then-MAC.
