# Bcrypt Cost Tuning: калибровка оптимальной стоимости под целевое время 250 мс

## Условие

**bcrypt cost tuning**: Определите оптимальный cost для вашего сервера: должен занимать ~250ms на хэш. Это даёт 4 пароля/сек на ядро — атакующему очень больно.

## Теория

Закон Мура и развитие серверных процессоров (AMD EPYC, Intel Xeon, ARM Neoverse) приводят к тому, что старый параметр `cost=10`, настроенный в 2010 году, сегодня вычисляется на современном процессоре за 30–50 миллисекунд.

Целевой отраслевой норматив OWASP:
- Вычисление одного bcrypt-хэша на целевом сервере должно занимать **от 200 до 300 миллисекунд** (в среднем **~250 мс**).
- При 250 мс на операцию:
  - Легитимный пользователь не замечает задержки в четверть секунды при отправке формы входа.
  - Одно процессорное ядро сервера способно обработать 4 авторизации в секунду.
  - Для атакующего скорость перебора ограничивается всего 4 попытками в секунду на ядро, что делает подбор бессмысленным.

Утилита тюнинга должна автоматически протестировать значения cost от 8 до 15 и выбрать то, которое ближе всего к 250 мс.

## Решение по шагам

1. Напишите функцию `BenchmarkBcryptCost(cost int, iters int) time.Duration`.
2. Реализуйте функцию автоподбора `FindOptimalBcryptCost(targetDuration time.Duration) (int, time.Duration)`.
3. Запустите замеры для cost от 8 до 14 на текущем процессоре.
4. Выберите значение, наиболее близкое к 250 миллисекундам.
5. Выведите готовый фрагмент конфигурации для вставки в `config.yaml` или `.env`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"time"

	"golang.org/x/crypto/bcrypt"
)

// BenchmarkCost замеряет среднее время одного вычисления bcrypt для заданного cost
func BenchmarkCost(cost int) time.Duration {
	password := []byte("CalibrationTargetSecretPassword2026")
	t0 := time.Now()
	_, _ = bcrypt.GenerateFromPassword(password, cost)
	return time.Since(t0)
}

// FindOptimalBcryptCost находит cost, наиболее близкий к target
func FindOptimalBcryptCost(target time.Duration) (int, time.Duration) {
	bestCost := bcrypt.DefaultCost
	bestDiff := time.Duration(math.MaxInt64)
	var bestDuration time.Duration

	// Перебираем диапазон допустимых рабочих стоимостей: 8..15
	for cost := 8; cost <= 14; cost++ {
		duration := BenchmarkCost(cost)
		diff := duration - target
		if diff < 0 {
			diff = -diff
		}

		fmt.Printf("Тест Cost %2d: Время = %10v (Отклонение от 250ms: %v)\n",
			cost, duration, diff)

		if diff < bestDiff {
			bestDiff = diff
			bestCost = cost
			bestDuration = duration
		}

		// Если время уже превысило 1 секунду, дальше подниматься опасно
		if duration > 1*time.Second {
			break
		}
	}

	return bestCost, bestDuration
}

func main() {
	targetDuration := 250 * time.Millisecond

	fmt.Println("=== Автоподбор оптимального bcrypt cost (Цель: ~250 мс) ===")
	optimalCost, actualDuration := FindOptimalBcryptCost(targetDuration)

	fmt.Println("\n=== Результат калибровки под текущее железо ===")
	fmt.Printf("Рекомендованный Cost:    %d\n", optimalCost)
	fmt.Printf("Фактическое время хэша:  %v\n", actualDuration)
	fmt.Printf("Пропускная способность:  %.1f операций/сек на 1 CPU ядро\n\n",
		1.0/actualDuration.Seconds())

	fmt.Println("Рекомендуемая конфигурация для config.yaml:")
	fmt.Printf("security:\n  auth:\n    bcrypt_cost: %d\n", optimalCost)
}
```

## Под капотом

Закон Мура и пересчет cost раз в два года:
1. Согласно закону Мура, производительность процессоров удваивается примерно каждые 18–24 месяца.
2. Поскольку каждый шаг `cost + 1` удваивает число раундов Eksblowfish (\(2^{\text{cost}}\)), **каждые 2 года параметр cost в продакшене должен увеличиваться ровно на +1**:
   - 2020 год: cost = 10 (~250 мс на сервере того поколения)
   - 2022 год: cost = 11
   - 2024–2026 год: cost = 12
3. Благодаря паттерну Transparent Hash Upgrade увеличение cost в конфигурационном файле не ломает авторизацию старых пользователей.

## Подводные камни

1. **Калибровка на мощном ноутбуке разработчика вместо сервера:** Процессор MacBook Pro M3 Max считает bcrypt значительно быстрее, чем виртуальное ядро vCPU в облаке (AWS t3.medium). Калибровку необходимо запускать непосредственно на целевом серверном инстансе в staging/production!
2. **Игнорирование всплесков нагрузки:** Если при cost=12 сервер тратит 250 мс, то при атаке 100 одновременных логинов сервер займет 25 секунд процессорного времени. Внедрение Rate Limiter (ограничение частоты запросов) строго обязательно.

## На собеседовании

**Вопрос с собеседования:** Почему при запуске бенчмарков bcrypt на локальной машине разработчика и в облачном контейнере Kubernetes результаты времени могут различаться в 3–5 раз?
**Ответ:** 1) **vCPU Throttling и CFS Quota:** В Kubernetes лимит CPU задается через Linux Completely Fair Scheduler (CFS). Если контейнеру выделен лимит `cpu: "500m"` (половина ядра), ядро Linux будет принудительно останавливать выполнение процесса на миллисекунды (CPU Throttling), увеличивая общее время bcrypt в разы. 2) **Архитектура процессора:** На ноутбуках часто стоят ядра с высокой частотой (до 4.5–5.0 ГГц), тогда как в облачных серверах частота vCPU обычно зафиксирована на уровне 2.4–2.8 ГГц. Калибровку параметров безопасности всегда нужно проводить в реальной среде выполнения Kubernetes.
