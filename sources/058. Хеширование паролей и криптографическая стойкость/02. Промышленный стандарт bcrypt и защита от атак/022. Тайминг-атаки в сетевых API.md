# Тайминг-атаки в сетевых API: защита проверки API-ключей через crypto/subtle

## Условие

**Тайминг-атаки (`crypto/subtle`)**: Тебе прислали API-ключ. Если ты проверишь его как `if input == secretKey`, злоумышленник сможет попиксельно угадать ключ, замеряя наносекунды ответа сервера (сравнение `==` прерывается на первом несовпадающем символе). Замени `==` на `subtle.ConstantTimeCompare()`, которое всегда выполняется за одинаковое время.

## Теория

При проектировании защищенных API Gateway и эндпоинтов авторизации вебхуков проверка входящего API-ключа (`Authorization: Bearer <token>`) или заголовка `X-API-Key` часто реализуется наивно:
```go
if requestKey == serverSecretKey { ... } // КРИТИЧЕСКАЯ УЯЗВИМОСТЬ
```

Анатомия тайминг-атаки на сравнение строк:
1. В Go оператор `string == string` компилируется в функцию `runtime.memequal`.
2. Она сначала сравнивает длины строк, а затем выполняет побайтовое сравнение в цикле, завершаясь при **первом же несовпадении байтов**.
3. Если секретный ключ — `"secret_token_12345"`, то:
   - При попытке `"a..."` процессор проверит 1-й байт и вернет `false` за 2 такта.
   - При попытке `"s..."` процессор проверит 1-й байт (совпал!), перейдет ко 2-му байту и вернет `false` за 5 тактов.
4. Отправляя тысячи запросов с каждого символа ASCII, злоумышленник по статистическому выбросу задержки находит верный первый символ, затем переходит ко второму, угадывая ключ за \(O(N \cdot |\Sigma|)\) запросов вместо экспоненциального \(O(|\Sigma|^N)\).

Решение: функция `subtle.ConstantTimeCompare([]byte(a), []byte(b)) == 1` гарантирует выполнение строго константного числа машинных циклов.

## Решение по шагам

1. Создайте HTTP-middleware для валидации API-ключа `X-API-Key`.
2. Продемонстрируйте уязвимый вариант проверки через `==`.
3. Замените проверку на криптостойкий вызов `subtle.ConstantTimeCompare`.
4. Реализуйте предварительное хэширование ключей перед сравнением для сокрытия информации о длине.
5. Напишите HTTP-хэндлер и подтвердите корректность авторизации.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/sha256"
	"crypto/subtle"
	"fmt"
	"net/http"
	"net/http/httptest"
)

// SecureAuthMiddleware защищает эндпоинт от тайминг-атак на API-ключ
func SecureAuthMiddleware(expectedKey string, next http.HandlerFunc) http.HandlerFunc {
	// Предварительно хэшируем эталонный ключ в SHA-256 (32 байта)
	// Это защищает от утечки длины ключа!
	expectedKeyHash := sha256.Sum256([]byte(expectedKey))

	return func(w http.ResponseWriter, r *http.Request) {
		clientKey := r.Header.Get("X-API-Key")
		if clientKey == "" {
			http.Error(w, "Отсутствует заголовок X-API-Key", http.StatusUnauthorized)
			return
		}

		// Хэшируем полученный ключ клиента
		clientKeyHash := sha256.Sum256([]byte(clientKey))

		// Сравнение хэшей фиксированной длины (32 байта) в константном времени
		if subtle.ConstantTimeCompare(clientKeyHash[:], expectedKeyHash[:]) != 1 {
			http.Error(w, "Недействительный API-ключ", http.StatusUnauthorized)
			return
		}

		next(w, r)
	}
}

func main() {
	secretAPIKey := "api_live_99481_enterprise_secret_token_alpha"

	// Защищенный обработчик
	protectedHandler := SecureAuthMiddleware(secretAPIKey, func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		w.Write([]byte(`{"status": "success", "data": "Доступ к секретному API разрешен"}`))
	})

	// 1. Тест: Запрос с корректным ключом
	reqValid := httptest.NewRequest("GET", "/api/v1/orders", nil)
	reqValid.Header.Set("X-API-Key", secretAPIKey)
	wValid := httptest.NewRecorder()
	protectedHandler(wValid, reqValid)

	fmt.Println("=== Тестирование защиты API-ключа через crypto/subtle ===")
	fmt.Printf("Запрос с легитимным ключом: Код %d, Тело: %s\n\n",
		wValid.Code, wValid.Body.String())

	// 2. Тест: Запрос с неверным ключом
	reqBad := httptest.NewRequest("GET", "/api/v1/orders", nil)
	reqBad.Header.Set("X-API-Key", "api_live_00000_wrong_token")
	wBad := httptest.NewRecorder()
	protectedHandler(wBad, reqBad)

	fmt.Printf("Запрос с мошенническим ключом: Код %d, Ошибка: %s\n",
		wBad.Code, wBad.Body.String())
	fmt.Println("Защита подтверждена: время ответа не зависит от позиции расхождения байт!")
}
```

## Под капотом

Зачем перед вызовом `subtle.ConstantTimeCompare` хэшировать ключ в SHA-256:
1. Сигнатура `subtle.ConstantTimeCompare(x, y []byte) int` содержит ранний выход:
   ```go
   if len(x) != len(y) {
       return 0
   }
   ```
2. Если злоумышленник передает ключи разной длины (10 символов, 11 символов, 12 символов...), вызов завершается мгновенно, раскрывая точную длину настоящего секретного ключа по времени ответа.
3. Если предварительно вычислить `sha256.Sum256` от обоих ключей, на вход `ConstantTimeCompare` **всегда подаются два массива ровно по 32 байта**, что полностью исключает утечку информации о длине секрета.

## Подводные камни

1. **Прямое сравнение строк после проверки длины:** Написание `if len(a) == len(b) && a == b` полностью возвращает уязвимость тайминг-атаки, так как `a == b` опять вызовет `memequal` с ранним выходом.
2. **Логирование сырых API-ключей при ошибке авторизации:** Вызов `log.Printf("Failed key: %s", clientKey)` при утечке логов в Elasticsearch/Loki скомпрометирует учетные данные пользователей.

## На собеседовании

**Вопрос с собеседования:** Почему в `subtle.ConstantTimeCompare` передают не сами токены, а их SHA-256 хэши?
**Ответ:** По двум причинам: 1) **Устранение утечки длины секрета:** Функция `subtle.ConstantTimeCompare` сразу возвращает 0, если длины срезов не совпадают. Зная время ответа, атакующий может точно определить длину API-ключа. Хэширование приводит любые входные строки к строго одинаковой длине в 32 байта. 2) **Фиксированное время вычисления:** Время сравнения 32 байт всегда константно и не зависит от того, передал клиент токен длиной 10 символов или вредоносный пейлоад размером 10 мегабайт, предотвращая DoS на функцию сравнения.
