# Password-Based KDF: фундаментальная разница между Password Hashing и деривацией ключей AES

## Условие

**Password-Based KDF.**: Используйте `argon2id` или `bcrypt` для получения ключа из пароля, затем используйте этот ключ в AES-GCM. Объясните разницу между *password hashing* (для проверки) и *key derivation* (для шифрования), и почему `bcrypt` не подходит как KDF для ключей AES.

## Теория

В прикладной криптографии существует критически важное концептуальное различие между двумя операциями над паролями:

1. **Password Hashing (Хэширование для аутентификации):**
   - Цель: проверить, знает ли пользователь секрет.
   - Требования: односторонность, медлительность, компактный строковый хэш.
   - Вывод: непрозрачная строка с солью и метаданными (например, `$2a$12$...` в bcrypt).
   - Обратимость: не требуется (пароль никогда не восстанавливается).

2. **Password-Based Key Derivation (PBKDF — Формирование криптографических ключей):**
   - Цель: превратить низкоэнтропийный пароль человека в полноценный, математически строгий симметричный ключ шифрования (например, ровно 32 байта псевдослучайных бит для AES-256-GCM).
   - Требования: настраиваемая длина вывода (`keyLen`), равномерное распределение энтропии всех битов.

**Почему bcrypt НЕЛЬЗЯ использовать как KDF для AES:**
1. **Фиксированный и неподходящий размер вывода:** bcrypt возвращает строго 184 бита (23 байта) зашифрованного текста `"OrpheanBeholderScryDoubt"`. Для AES-256 требуется ровно 256 бит (32 байта). Не хватает 9 байт!
2. **Лимит входа в 72 байта:** bcrypt отбрасывает всё после 72 байт.
3. **Отсутствие API деривации:** bcrypt проектировался исключительно как алгоритм проверки, а не KDF.

Для генерации ключей AES из паролей стандартом является **Argon2id** (`argon2.IDKey(..., keyLength=32)`) или **scrypt**.

## Решение по шагам

1. Сформируйте мастер-пароль пользователя и криптографическую соль (16 байт).
2. Используйте `argon2.IDKey` с параметром `keyLength = 32` для генерации полноценного ключа AES-256.
3. Инициализируйте блочный шифр `aes.NewCipher(derivedKey)` и режим `cipher.NewGCM`.
4. Зашифруйте конфиденциальный файл (симметричное шифрование хранилища).
5. Продемонстрируйте расшифрование файла с тем же паролем и солью.
6. Покажите, почему bcrypt непригоден для этой задачи.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
	"log"

	"golang.org/x/crypto/argon2"
)

// DeriveAESKeyFromPassword использует Argon2id как Password-Based KDF
func DeriveAESKeyFromPassword(password string, salt []byte) []byte {
	// keyLength = 32 байта (строго 256 бит для AES-256)
	return argon2.IDKey([]byte(password), salt, 1, 64*1024, 4, 32)
}

// EncryptVault шифрует данные ключом, полученным из мастер-пароля
func EncryptVault(password string, plaintext []byte) ([]byte, []byte, []byte, error) {
	// 1. Генерируем соль для KDF
	salt := make([]byte, 16)
	io.ReadFull(rand.Reader, salt)

	// 2. Деривируем ключ AES-256
	key := DeriveAESKeyFromPassword(password, salt)

	// 3. Шифруем через AES-GCM
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, nil, nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, nil, nil, err
	}

	nonce := make([]byte, gcm.NonceSize())
	io.ReadFull(rand.Reader, nonce)

	ciphertext := gcm.Seal(nil, nonce, plaintext, nil)
	return ciphertext, nonce, salt, nil
}

// DecryptVault расшифровывает хранилище по мастер-паролю
func DecryptVault(password string, ciphertext, nonce, salt []byte) ([]byte, error) {
	key := DeriveAESKeyFromPassword(password, salt)

	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}

	return gcm.Open(nil, nonce, ciphertext, nil)
}

func main() {
	userPassword := "Master-Passphrase-Encrypt-Secrets-2026!"
	secretData := []byte("КОНФИДЕНЦИАЛЬНО: приватные SSH-ключи инфраструктуры дата-центра")

	// 1. Шифрование
	ciphertext, nonce, salt, err := EncryptVault(userPassword, secretData)
	if err != nil {
		log.Fatalf("Ошибка шифрования: %v", err)
	}

	fmt.Println("=== Password-Based Key Derivation (Argon2id -> AES-256-GCM) ===")
	fmt.Printf("Соль KDF (16 байт): %s\n", hex.EncodeToString(salt))
	fmt.Printf("Nonce (12 байт):    %s\n", hex.EncodeToString(nonce))
	fmt.Printf("Шифротекст:         %s\n\n", hex.EncodeToString(ciphertext))

	// 2. Успешное расшифрование с тем же паролем
	decrypted, err := DecryptVault(userPassword, ciphertext, nonce, salt)
	if err != nil {
		log.Fatalf("Ошибка расшифрования: %v", err)
	}

	fmt.Printf("Успешно расшифровано:\n%s\n\n", string(decrypted))
	fmt.Printf("Целостность подтверждена: %v\n", bytes.Equal(decrypted, secretData))

	// 3. Почему bcrypt непригоден:
	fmt.Println("\n=== Почему bcrypt НЕЛЬЗЯ использовать как KDF ===")
	fmt.Println("1. Вывод bcrypt содержит всего 184 бита энтропии (для AES-256 нужно строго 256 бит).")
	fmt.Println("2. bcrypt молча обрезает пароль на 72-м байте.")
	fmt.Println("3. bcrypt не имеет интерфейса генерации произвольной длины байт (keyLen).")
	fmt.Println("ВЫВОД: Для деривации ключей шифрования используйте строго Argon2id или scrypt!")
}
```

## Под капотом

Стандарты NIST SP 800-132 (Recommendation for Password-Based Key Derivation):
1. Пароль человека содержит избыточность языка и низкую энтропию (\(< 40\) бит).
2. PBKDF решает задачу **растяжения энтропии (Entropy Stretching)**: за счет десятков тысяч вычислений и распределения по памяти эффективная стоимость перебора каждого бита ключа многократно возрастает.
3. Argon2id на выходе гарантирует, что каждый из 256 бит сгенерированного ключа псевдослучаен и некоррелирован с остальными битами, что является фундаментальным требованием безопасности для ключа шифра AES.

## Подводные камни

1. **Использование быстрого SHA-256(password) в качестве ключа AES:** Это грубейшая ошибка. Если взять `key := sha256.Sum256([]byte(pass))`, злоумышленник переберет пароль по словарю за пару секунд, расшифрует AES и получит доступ к данным. Для паролей обязателен ресурсоемкий PBKDF (Argon2id).
2. **Несохранение соли рядом с шифротекстом:** Если соль не сохранена в файле хранилища, расшифровать данные будет невозможно даже при знании верного пароля.

## На собеседовании

**Вопрос с собеседования:** В чем разница между KDF на основе пароля (Password-Based KDF: Argon2id, PBKDF2) и KDF на основе случайного ключа (HKDF)?
**Ответ:** Разница в исходной энтропии входных данных:
1. **HKDF:** Рассчитан на входные данные, которые **уже криптографически случайны** (например, 256-битный секрет эллиптического обмена ECDH). Он работает мгновенно (микросекунды) и лишь форматирует/разделяет секрет на субключи нужной длины.
2. **Password-Based KDF (Argon2id):** Рассчитан на входные данные с **крайне низкой энтропией** (пароли людей вроде `"Password123!"`). Его задача — искусственно замедлить вычисления и занять 64 МБ оперативной памяти, чтобы исключить возможность перебора по словарю на видеокартах.
