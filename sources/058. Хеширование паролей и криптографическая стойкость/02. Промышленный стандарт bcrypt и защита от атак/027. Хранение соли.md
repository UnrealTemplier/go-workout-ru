# Хранение соли: упаковка base64(salt + hash) и недопустимость глобальной соли

## Условие

**Соль: уникальность и хранение.**: Напишите функцию, которая генерирует случайную соль (16 байт) для каждого пользователя. Объясните, почему глобальная соль — уязвимость (rainbow tables), и как хранить соль вместе с хешем (например, `base64(salt+hash)`).

## Теория

Вопрос хранения соли часто вызывает путаницу: начинающие разработчики считают, что соль должна храниться в секрете или в отдельной таблице.

Фундаментальные правила криптографической соли:
1. **Соль обязана быть уникальной (Per-User Salt):**
   - Если используется одна глобальная соль для всех пользователей (`const GlobalSalt = "salt123"`), то два пользователя с одинаковым паролем получат одинаковый хэш.
   - Злоумышленник может рассчитать радужную таблицу под эту одну глобальную соль и мгновенно взломать всех пользователей базы разом.
2. **Соль не требует шифрования и скрытия:**
   - Соль является открытым параметром (Public Nonce).
   - Задача соли — разрушить возможность параллельного и предварительного вычисления.
3. **Упаковка соли с хэшем:**
   - В современных архитектурах соль объединяют с хэшем в единое бинарное или строковое поле:
     `Combined = Salt (16 байт) || Hash (32 байта)`.
   - Результирующие 48 байт кодируются в Base64 (`base64.RawStdEncoding`).
   - Это гарантирует атомарность: соль невозможно случайно потерять, отвязать от хэша или повредить при миграциях схемы БД.

## Решение по шагам

1. Напишите функцию `CreateUserPasswordHash(password string) (string, error)`.
2. Сгенерируйте 16 байт случайной соли через `crypto/rand`.
3. Вычислите хэш Argon2id / KDF.
4. Объедините соль и хэш в один срез байт: `append(salt, hash...)`.
5. Закодируйте объединенный срез в Base64 строку.
6. Напишите функцию проверки `VerifyUserPasswordHash(password, packedBase64 string) (bool, error)`, извлекающую первые 16 байт как соль, а оставшиеся 32 байта — как эталонный хэш.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/base64"
	"errors"
	"fmt"
	"io"
	"log"

	"golang.org/x/crypto/argon2"
)

const (
	SaltSizeBytes = 16
	HashSizeBytes = 32
)

// CreateUserPasswordHash упаковывает соль и хэш в единую Base64 строку (48 байт)
func CreateUserPasswordHash(password string) (string, error) {
	// 1. Генерация уникальной соли для конкретного пользователя
	salt := make([]byte, SaltSizeBytes)
	if _, err := io.ReadFull(rand.Reader, salt); err != nil {
		return "", err
	}

	// 2. Хэширование через Argon2id (быстрый тестовый профиль)
	hash := argon2.IDKey([]byte(password), salt, 1, 32*1024, 2, HashSizeBytes)

	// 3. Упаковка: [16 байт соли][32 байта хэша] = 48 байт
	combined := make([]byte, 0, SaltSizeBytes+HashSizeBytes)
	combined = append(combined, salt...)
	combined = append(combined, hash...)

	// 4. Кодирование в компактную Base64 строку
	return base64.RawStdEncoding.EncodeToString(combined), nil
}

// VerifyUserPasswordHash распаковывает соль и проверяет пароль
func VerifyUserPasswordHash(password, packedBase64 string) (bool, error) {
	combined, err := base64.RawStdEncoding.DecodeString(packedBase64)
	if err != nil {
		return false, fmt.Errorf("ошибка декодирования base64: %w", err)
	}

	if len(combined) != SaltSizeBytes+HashSizeBytes {
		return false, errors.New("некорректная длина упакованного хэша")
	}

	// Извлекаем соль и ожидаемый хэш по фиксированным смещениям
	salt := combined[:SaltSizeBytes]
	expectedHash := combined[SaltSizeBytes:]

	// Вычисляем хэш заново с извлеченной солью
	computedHash := argon2.IDKey([]byte(password), salt, 1, 32*1024, 2, HashSizeBytes)

	// Constant-time сравнение
	return subtle.ConstantTimeCompare(computedHash, expectedHash) == 1, nil
}

func main() {
	pass := "SafePasswordStoragePattern#2026"

	// 1. Регистрация: создание упакованного хэша
	storedString, err := CreateUserPasswordHash(pass)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	fmt.Println("=== Паттерн хранения соли: Base64(salt + hash) ===")
	fmt.Printf("Упакованная строка для БД (users.password_hash):\n%s\n", storedString)
	fmt.Printf("Длина строки в БД: %d символов (ровно 48 байт в base64)\n\n", len(storedString))

	// 2. Проверка верного пароля
	isValid, err := VerifyUserPasswordHash(pass, storedString)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
	fmt.Printf("Проверка корректного пароля: %v (УСПЕХ)\n", isValid)

	// 3. Проверка неверного пароля
	isBadValid, _ := VerifyUserPasswordHash("WrongPassword!", storedString)
	fmt.Printf("Проверка ошибочного пароля:   %v (ОТКЛОНЕНО)\n", isBadValid)
}
```

## Под капотом

Преимущества бинарной упаковки перед отдельными SQL-колонками:
1. **Атомарность транзакций:** Невозможно случайно обновить `password_hash` без обновления `salt`.
2. **Экономия дискового пространства и индексов:** Единая колонка `VARCHAR(64)` или бинарный `BYTEA(48)` в PostgreSQL занимает меньше места в строке таблицы, чем две отдельные колонки со своими заголовками null-масок и выравнивания.
3. **Совместимость с микросервисами:** Любой сервис на Go, Python или Java, зная соглашение о первых 16 байтах, легко верифицирует хэш без знания схемы базы данных.

## Подводные камни

1. **Использование переменной длины соли без указания длины:** Если длина соли варьируется, невозможно однозначно понять, где кончается соль и начинается хэш. Длина соли должна быть строго зафиксирована (например, ровно 16 байт).
2. **Использование стандартного fmt.Sprintf("%s:%s", salt, hash):** Текстовые разделители (например `:`) могут случайно встретиться внутри бинарных данных, если они предварительно не закодированы в hex/base64.

## На собеседовании

**Вопрос с собеседования:** Почему в схеме базы данных крупных сервисов для паролей часто используют единую текстовую колонку `password_hash VARCHAR(255)` вместо раздельных колонок `hash`, `salt`, `algorithm`, `iterations`?
**Ответ:** Единая колонка позволяет использовать стандартные самодостаточные форматы сериализации (Modular Crypt Format в bcrypt или PHC String Format в Argon2). Это позволяет хранить в одной таблице пароли разных поколений: старые пользователи могут иметь хэши `$2a$10$...`, а новые — `$argon2id$v=19$m=65536...`. Приложение при логине по префиксу строки мгновенно определяет нужный алгоритм и параметры проверки, что делает миграцию между алгоритмами полностью прозрачной и не требующей изменений схемы БД (DDL migrations).
