# bcrypt полный цикл: регистрация, аутентификация и защита Constant-Time

## Условие

**bcrypt: полный цикл.**: Реализуйте регистрацию и аутентификацию через `golang.org/x/crypto/bcrypt`. Сгенерируйте хеш с `cost=10` и `cost=14`. Замерьте время хеширования. Объясните, почему `bcrypt.CompareHashAndPassword` использует constant-time сравнение.

## Теория

Полный жизненный цикл работы с паролями в веб-приложениях состоит из двух изолированных фаз:

1. **Фаза регистрации (Хэширование, Register):**
   - Пользователь отправляет открытый пароль по защищенному каналу TLS 1.3.
   - Сервер валидирует сложность пароля (длина, отсутствие в базах утекших паролей HIBP).
   - Вызывается `bcrypt.GenerateFromPassword([]byte(pass), cost)`. Внутри генерируется 128-битная криптографическая соль из CSPRNG ядра ОС.
   - Результирующая 60-символьная строка сохраняется в колонку `users.password_hash`. Открытый пароль немедленно стирается из памяти.

2. **Фаза аутентификации (Верификация, Login):**
   - Пользователь присылает пару `(login, password)`.
   - Сервер находит пользователя в базе данных.
   - Вызывается `bcrypt.CompareHashAndPassword([]byte(storedHash), []byte(inputPassword))`.
   - Соль и cost извлекаются из самого хэша, вычисляется Eksblowfish, и результат сверяется с эталоном.

**Зачем bcrypt.CompareHashAndPassword использует constant-time:**
Даже внутри функции проверки сравнение вычисленного шифротекста с сохраненным в хэше обязано производиться через `subtle.ConstantTimeCompare`. Если бы сравнение прерывалось на первом несовпавшем байте, злоумышленник по сетевым задержкам мог бы восстановить контрольный шифротекст bcrypt.

## Решение по шагам

1. Создайте структуру сервиса `UserService` с хранилищем в памяти `map[string]string`.
2. Реализуйте метод `Register(username, password string, cost int) error`.
3. Реализуйте метод `Authenticate(username, password string) error`.
4. Сравните время выполнения регистрации при `cost = 10` и `cost = 14`.
5. Продемонстрируйте успешную аутентификацию и отклонение неверного пароля с возвратом `ErrMismatchedHashAndPassword`.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
	"sync"
	"time"

	"golang.org/x/crypto/bcrypt"
)

// UserService управляет учетными записями пользователей
type UserService struct {
	mu    sync.RWMutex
	users map[string]string // login -> bcrypt_hash
}

func NewUserService() *UserService {
	return &UserService{users: make(map[string]string)}
}

// Register выполняет хэширование пароля и сохранение пользователя
func (s *UserService) Register(username, password string, cost int) (time.Duration, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if _, exists := s.users[username]; exists {
		return 0, errors.New("пользователь уже зарегистрирован")
	}

	t0 := time.Now()
	hash, err := bcrypt.GenerateFromPassword([]byte(password), cost)
	duration := time.Since(t0)

	if err != nil {
		return 0, fmt.Errorf("сбой bcrypt: %w", err)
	}

	s.users[username] = string(hash)
	return duration, nil
}

// Authenticate проверяет учетные данные пользователя
func (s *UserService) Authenticate(username, password string) error {
	s.mu.RLock()
	hash, exists := s.users[username]
	s.mu.RUnlock()

	if !exists {
		return errors.New("неверный логин или пароль")
	}

	// CompareHashAndPassword выполняет constant-time сравнение
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	if err != nil {
		if errors.Is(err, bcrypt.ErrMismatchedHashAndPassword) {
			return errors.New("неверный логин или пароль")
		}
		return fmt.Errorf("ошибка валидации: %w", err)
	}

	return nil
}

func main() {
	svc := NewUserService()

	// 1. Регистрация пользователя с cost=10
	dCost10, err := svc.Register("alice", "AliceSecurePass#2026", 10)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	// 2. Регистрация пользователя с cost=14
	dCost14, err := svc.Register("bob", "BobMasterKey!9900", 14)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	fmt.Println("=== Полный цикл bcrypt: Регистрация и аутентификация ===")
	fmt.Printf("Время регистрации Alice (cost=10): %v (Быстро, стандарт)\n", dCost10)
	fmt.Printf("Время регистрации Bob   (cost=14): %v (В 16 раз медленнее, высокая нагрузка)\n\n", dCost14)

	// 3. Аутентификация: успешный вход
	err = svc.Authenticate("alice", "AliceSecurePass#2026")
	fmt.Printf("Вход Alice с верным паролем:   %v (УСПЕХ)\n", err == nil)

	// 4. Аутентификация: неверный пароль
	err = svc.Authenticate("alice", "WrongPassword123")
	fmt.Printf("Вход Alice с неверным паролем: %v (ОТКЛОНЕНО: %v)\n", err == nil, err)
}
```

ℹ️ Полный цикл сервиса пользователей с регистрацией, замером стоимости bcrypt и верификацией

## Под капотом

Почему в `bcrypt.CompareHashAndPassword` используется constant-time:
В исходном коде `bcrypt`:
```go
func CompareHashAndPassword(hashedPassword, password []byte) error {
    h, err := newFromHash(hashedPassword)
    if err != nil { return err }
    otherHash, err := bcrypt(password, h.cost, h.salt)
    if err != nil { return err }
    if subtle.ConstantTimeCompare(h.hash, otherHash) != 1 {
        return ErrMismatchedHashAndPassword
    }
    return nil
}
```
Хотя время вычисления самого bcrypt огромно (~100 мс) по сравнению с микросекундным сравнением, отсутствие constant-time позволило бы локальному атакующему на том же физическом хосте (через сожительство виртуальных машин в облаке) анализировать прерывания кэша и восстанавливать биты хэша из памяти.

## Подводные камни

1. **Разные ошибки для несуществующего логина и неверного пароля:** Если сервер возвращает `404 Пользователь не найден` и `401 Неверный пароль`, злоумышленники используют это для составления базы зарегистрированных клиентов (User Enumeration Attack). Ошибка всегда должна быть обезличенной: `401 Неверный логин или пароль`.
2. **Блокировка базы данных при долгом bcrypt:** Не выполняйте `bcrypt.GenerateFromPassword` внутри открытой транзакции базы данных (`db.Begin()`), иначе транзакция удержит блокировку строки на сотни миллисекунд.

## На собеседовании

**Вопрос с собеседования:** Почему вычисление bcrypt категорически запрещено выполнять внутри транзакции SQL (`BEGIN ... COMMIT`)?
**Ответ:** Операция `bcrypt` является CPU-bound и длится от 100 до 300 миллисекунд. Если открыть транзакцию `tx, _ := db.Begin()`, заблокировать строку `SELECT FOR UPDATE` или удерживать открытое соединение из ограниченного пула базы данных (Connection Pool) во время вычисления bcrypt, пул соединений СУБД будет исчерпан за секунды при минимальной нагрузке. Сначала необходимо полностью завершить вычисление хэша в оперативной памяти Go, и только затем открывать быструю микросекундную транзакцию в БД для вставки или обновления записи.
