# Лимит длины пароля в bcrypt и pre-hashing

## Условие

Покажите, что bcrypt обрезает пароли до 72 байт. Длинный passphrase теряет энтропию! Используйте pre-hashing через SHA-256 для длинных паролей.

### Исходная формулировка

**bcrypt length limit**: Покажите, что bcrypt обрезает пароли до 72 байт. Длинный passphrase теряет энтропию! Используйте pre-hashing через SHA-256 для длинных паролей.

## Теория

Исторический алгоритм **bcrypt** построен на основе блочного шифра **Eksblowfish** (Expensive Key Schedule Blowfish). В оригинальной спецификации ключевое расписание Blowfish принимает ключ длиной от 32 до 448 бит (4–56 байт), однако реализация bcrypt расширила этот лимит ровно до **72 байт** (576 бит).

Любые символы пароля, находящиеся после 72-го байта, **полностью отбрасываются** функцией `bcrypt.GenerateFromPassword`. Это создает критическую уязвимость логики аутентификации:
1. Если пользователь задает длинный passphrase (например, из 100 символов), атакующий, угадавший первые 72 символа, успешно авторизуется под любой комбинацией хвоста.
2. Пароли в кодировке UTF-8 с кириллицей или эмодзи занимают 2–4 байта на символ. Фраза из 25 русских букв уже достигает 50–100 байт и незаметно обрезается!

Решением промышленного стандарта является **Pre-hashing**:
Перед передачей пароля в bcrypt строка хешируется быстрым криптографическим дайджестом — **SHA-256** (или HMAC-SHA256). Результат SHA-256 всегда имеет фиксированную длину ровно **32 байта** (256 бит), что гарантированно укладывается в 72-байтовый лимит bcrypt, сохраняет полную криптографическую энтропию исходной фразы любой длины и исключает коллизии усечения. При этом важно избегать проблемы нулевых байтов (NULL-byte truncation в C-библиотеках), поэтому сырой дайджест часто передают в Base64 или Hex.

## Решение по шагам

1. Создадим демонстрацию усечения bcrypt: возьмем пароль длиной более 72 байт и изменим его окончание.
2. Проверим с помощью `bcrypt.CompareHashAndPassword`, что оба разных пароля дают положительный результат проверки хеша.
3. Разработаем функцию `HashPasswordPreHashed(password string, cost int) ([]byte, error)`, вычисляющую `sha256.Sum256([]byte(password))` перед передачей в `bcrypt.GenerateFromPassword`.
4. Реализуем безопасную функцию верификации `VerifyPasswordPreHashed(password string, hashedPassword []byte) bool`.
5. Протестируем сценарии с длинными UTF-8 строками и убедимся, что изменение хотя бы одного символа в хвосте приводит к отказу в доступе.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/sha256"
	"encoding/base64"
	"fmt"
	"strings"

	"golang.org/x/crypto/bcrypt"
)

// HashPasswordPreHashed хэширует длинный пароль, исключая лимит 72 байт bcrypt
func HashPasswordPreHashed(password string, cost int) (string, error) {
	// Шаг 1: Сжимаем пароль произвольной длины до 32 байт через SHA-256
	digest := sha256.Sum256([]byte(password))

	// Шаг 2: Кодируем в Base64 (длина 44 символа, гарантированно < 72 байт)
	b64Digest := base64.StdEncoding.EncodeToString(digest[:])

	// Шаг 3: Вычисляем bcrypt от безопасного Base64 дайджеста
	hashBytes, err := bcrypt.GenerateFromPassword([]byte(b64Digest), cost)
	if err != nil {
		return "", fmt.Errorf("bcrypt generation failed: %w", err)
	}

	return string(hashBytes), nil
}

// VerifyPasswordPreHashed верифицирует пароль с предварительным SHA-256
func VerifyPasswordPreHashed(password, storedHash string) bool {
	digest := sha256.Sum256([]byte(password))
	b64Digest := base64.StdEncoding.EncodeToString(digest[:])

	err := bcrypt.CompareHashAndPassword([]byte(storedHash), []byte(b64Digest))
	return err == nil
}

func main() {
	fmt.Println("=== 1. Демонстрация уязвимости усечения 72 байт в стандартном bcrypt ===")

	// Создаем префикс ровно 72 байта 'A'
	prefix72 := strings.Repeat("A", 72)
	pass1 := prefix72 + "СЕКРЕТ_ХВОСТ_1"
	pass2 := prefix72 + "СОВЕРШЕННО_ДРУГОЙ_ХВОСТ_2"

	// Хэшируем pass1 стандартным bcrypt
	rawHash, err := bcrypt.GenerateFromPassword([]byte(pass1), bcrypt.DefaultCost)
	if err != nil {
		panic(err)
	}

	// Проверяем pass2 против хэша pass1!
	matchErr := bcrypt.CompareHashAndPassword(rawHash, []byte(pass2))
	if matchErr == nil {
		fmt.Println("[ВНИМАНИЕ] Стандартный bcrypt пропустил pass2! Хвост после 72 байт был отброшен!")
	}

	fmt.Println("\n=== 2. Безопасное решение через Pre-hashing (SHA-256 + bcrypt) ===")
	secureHash, err := HashPasswordPreHashed(pass1, bcrypt.DefaultCost)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Pre-hashed bcrypt hash: %s\n", secureHash)

	// Проверка корректного пароля pass1
	ok1 := VerifyPasswordPreHashed(pass1, secureHash)
	fmt.Printf("Проверка оригинального pass1: %t (ожидается true)\n", ok1)

	// Проверка некорректного pass2
	ok2 := VerifyPasswordPreHashed(pass2, secureHash)
	fmt.Printf("Проверка поддельного pass2:    %t (ожидается false)\n", ok2)
}
```

## Под капотом

Внутри пакета `golang.org/x/crypto/bcrypt` исходная функция `bcrypt` инициализирует внутренний массив `key [72]byte`. Алгоритм `ExpandKey` циклически считывает ровно до 72 байт пользовательского ключа для инициализации P-массива и S-боксов Blowfish:
```go
for i := 0; i < len(key) && i < 72; i++ { ... }
```
Если `len(key) > 72`, компилятор даже не выбрасывает ошибку, а молча обрезает срез до `key[:72]`.
Если в системе используется pre-hashing через `sha256.Sum256`, 32-байтный результат Base64-кодируется в 44 байта ASCII. Поскольку 44 < 72, никакой обрезки не происходит, а энтропия длинных паролей (passphrases) сохраняется полностью.

## Подводные камни

1. **Проблема нулевого байта (NULL byte truncation):** В некоторых библиотеках C (например, старых версиях OpenBSD/PHP) сырые байты SHA-256 могут содержать `0x00`, из-за чего строка `char*` обрывалась еще раньше. В Go `[]byte` содержит явную длину, но при межъязыковой совместимости всегда рекомендуется кодировать SHA-256 в Base64 или Hex перед подачей в bcrypt.
2. **Pre-hashing без соли:** Нельзя путать pre-hashing со «сквозным хэшированием». SHA-256 выполняется на сервере исключительно для ограничения длины, а bcrypt уже самостоятельно генерирует 128-битную криптографическую соль.
3. **DoS длинными строками:** Если злоумышленник отправит строку размером 500 МБ в эндпоинт логина, вычисление SHA-256 может перегрузить CPU/память. Всегда ограничивайте размер тела HTTP-запроса (`http.MaxBytesReader`) и максимальную длину поля пароля (например, до 1024 байт).

## На собеседовании

**Вопрос с собеседования в Яндекс/Ozon:** «Почему bcrypt не подходит в чистом виде для систем с требованиями к длине пароля более 72 символов, и как это решить в архитектуре HighLoad-сервиса?»
**Ответ:** Bcrypt жестко ограничен 72 байтами из-за спецификации ключевого расписания шифра Eksblowfish. Символы после 72-го байта игнорируются, что делает уязвимыми длинные пароли и пароли на кириллице (где 1 символ = 2 байта). В архитектуре HighLoad применяется pre-hashing: пароль предварительно хешируется быстрым SHA-256 (или HMAC-SHA256 с серверным секретом pepper) и кодируется в Base64 (44 байта), после чего отправляется в bcrypt. Это гарантирует детерминированную длину входа, защиту от усечения и возможность параллельного горизонтального масштабирования auth-сервисов.
