# Тюнинг и калибровка параметров Argon2id

## Условие

**Argon2 параметры tuning:**
* memory: 64 MB minimum (для 1 потока)
* iterations: 3-5
* parallelism: число ядер
* salt: 16 байт
* key length: 32 байт

## Теория

Эффективность защиты паролей зависит от правильного подбора параметров (tuning) под аппаратные ресурсы конкретного production-кластера. Стандарт **RFC 9106** и рекомендации **OWASP Password Storage Cheat Sheet** предлагают два основных профиля для Argon2id:

1. **Первый профиль (High-Memory):**
   - Memory: **64 МБ** (\(65536\) КиБ)
   - Iterations (\(t\)): **3**
   - Parallelism (\(p\)): **4** (или \(N\) ядер CPU)
   - Salt: **16 байт** (128 бит энтропии)
   - Key length: **32 байта** (256 бит)
   Оптимален для стандартных бэкендов, балансирует задержку (~100–300 мс) и колоссальную стойкость против перебора на GPU.

2. **Второй профиль (Low-Memory / Constrained Systems):**
   - Memory: **19 МБ** (\(19456\) КиБ)
   - Iterations (\(t\)): **2**
   - Parallelism (\(p\)): **1**
   Применяется в средах с жесткими лимитами по памяти (например, небольшие контейнеры или мобильные клиенты).

### Принцип подбора параметров:
- **Память (\(m\)):** Увеличивайте до максимального значения, которое бэкенд может выделить при пиковой нагрузке (с учетом пула соединений), не рискуя вызвать OOM Killer.
- **Время (\(t\)):** Подбирается так, чтобы суммарное время вычисления одного хэша на продакшн-сервере укладывалось в **200–500 мс**.
- **Параллелизм (\(p\)):** Устанавливается равным числу потоков, которые сервер может выделить на задачу (обычно `runtime.NumCPU()` или 2–4).

## Решение по шагам

1. Создадим конфигурируемую структуру `TuningConfig` с валидацией входных значений.
2. Реализуем функцию динамического определения параллелизма на основе доступных процессорных ядер `runtime.NumCPU()`.
3. Напишем функцию хеширования, принимающую калиброванную конфигурацию.
4. Продемонстрируем автоматическую валидацию границ параметров (проверка минимальной памяти 64 МБ, длины соли и т.д.).
5. Выведем детальный отчет о ресурсах, задействованных при вычислении.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"errors"
	"fmt"
	"io"
	"runtime"
	"time"

	"golang.org/x/crypto/argon2"
)

// TuningConfig инкапсулирует калиброванные параметры Argon2id
type TuningConfig struct {
	MemoryKiB   uint32
	Iterations  uint32
	Parallelism uint8
	SaltLen     uint32
	KeyLen      uint32
}

// Validate проверяет соблюдение стандартов безопасности RFC 9106 / OWASP
func (c *TuningConfig) Validate() error {
	if c.MemoryKiB < 19*1024 {
		return errors.New("memory must be at least 19 MB (19456 KiB)")
	}
	if c.Iterations < 1 {
		return errors.New("iterations must be at least 1")
	}
	if c.Parallelism < 1 {
		return errors.New("parallelism must be >= 1")
	}
	if c.SaltLen < 16 {
		return errors.New("salt length must be at least 16 bytes")
	}
	if c.KeyLen < 16 {
		return errors.New("key length must be at least 16 bytes")
	}
	return nil
}

// AutoTunedConfig создает конфигурацию, адаптированную под текущее число CPU
func AutoTunedConfig() TuningConfig {
	cpus := runtime.NumCPU()
	parallelism := uint8(cpus)
	if cpus > 8 {
		parallelism = 8 // Ограничиваем сверху, чтобы не исчерпать планировщик
	}
	if parallelism < 1 {
		parallelism = 1
	}

	return TuningConfig{
		MemoryKiB:   64 * 1024, // 64 MB minimum
		Iterations:  3,         // 3 прохода
		Parallelism: parallelism,
		SaltLen:     16, // 16 байт криптосоли
		KeyLen:      32, // 32 байта дайджеста
	}
}

func main() {
	cfg := AutoTunedConfig()
	if err := cfg.Validate(); err != nil {
		panic(err)
	}

	fmt.Printf("Калибровка Argon2id:\n")
	fmt.Printf("- Память:       %d MB (%d KiB)\n", cfg.MemoryKiB/1024, cfg.MemoryKiB)
	fmt.Printf("- Итерации:     %d\n", cfg.Iterations)
	fmt.Printf("- Параллелизм:  %d потоков (доступно CPU: %d)\n", cfg.Parallelism, runtime.NumCPU())
	fmt.Printf("- Размер соли:  %d байт\n", cfg.SaltLen)
	fmt.Printf("- Длина ключа:  %d байт\n", cfg.KeyLen)

	salt := make([]byte, cfg.SaltLen)
	if _, err := io.ReadFull(rand.Reader, salt); err != nil {
		panic(err)
	}

	password := "EngineerSecretPassPhrase2026!"

	start := time.Now()
	hash := argon2.IDKey([]byte(password), salt, cfg.Iterations, cfg.MemoryKiB, cfg.Parallelism, cfg.KeyLen)
	duration := time.Since(start)

	fmt.Printf("\nРезультат:\n")
	fmt.Printf("Время генерации: %s\n", duration)
	fmt.Printf("Размер хэша:     %d байт\n", len(hash))
	fmt.Printf("Хэш (первые 8B): %x...\n", hash[:8])
}
```

## Под капотом

Параметр `parallelism` (\(p\)) разбивает выделенную матрицу памяти на \(p\) независимых полос (lanes). Внутренний планировщик Go запускает \(p\) горутин, каждая из которых вычисляет блоки своей полосы. В конце каждого прохода (pass) горутины синхронизируются через барьер, так как блоки следующего сегмента могут ссылаться на блоки соседних полос. 
Поэтому выставление \(p\) больше, чем реальное число физических ядер контейнера (vCPU), не ускоряет расчет, а лишь создает накладные расходы на переключение контекста горутин.

## Подводные камни

1. **Игнорирование ограничений vCPU в контейнерах (CFS Quota):** В Kubernetes контейнеру может быть выделен лимит `cpu: "1"`, в то время как `runtime.NumCPU()` вернет 64 (число ядер хост-машины). Установка `parallelism = 64` в 1-ядерном контейнере вызовет жесточайший throttling планировщика Linux CFS и замедлит хэширование в 10–20 раз! Используйте библиотеки типа `uber-go/automaxprocs` или читайте cgroups quota.
2. **Слишком большая длина результирующего ключа (\(keyLen\)):** Некоторые разработчики указывают \(keyLen = 64\) или \(128\). Это избыточно: 32 байта (256 бит) обеспечивают максимальный криптографический уровень безопасности.
3. **Недостаточная длина соли:** Соль менее 16 байт снижает пространство состояний и повышает риск коллизий в масштабах базы данных с миллионами пользователей.

## На собеседовании

**Вопрос с собеседования в VK/Яндекс:** «Как правильно выбрать параметры Argon2id для сервиса авторизации в Kubernetes-кластере с 500 RPS на регистрацию и вход?»
**Ответ:** Никакой одиночный сервер не сможет обрабатывать 500 RPS надежного Argon2id (при 100 мс на хэш для 500 RPS потребуется 50 ядер CPU и десятки гигабайт памяти в секунду). Решение:
1. Выбрать параметры Argon2id под целевую задержку (например, \(m=64\text{MB}, t=3, p=2 \rightarrow \sim 150\text{ мс}\)).
2. Изолировать вычисление хэшей паролей в специализированные stateless Auth-воркеры с горизонтальным масштабированием (HPA по CPU).
3. Применить строгий rate limiting по IP и учетным записям (например, Redis Token Bucket), чтобы исключить DoS-атаки.
4. Ограничить конкурентность на каждом инстансе через bounded worker pool (семафор), чтобы не допустить OOM из-за одновременных аллокаций памяти по 64 МБ.
