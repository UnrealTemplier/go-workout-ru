# Бенчмаркинг Argon2id под целевую серверную задержку

## Условие

Определите параметры Argon2 так, чтобы хэширование занимало 300-500ms на ваш типичный сервер.

### Исходная формулировка

**Argon2 benchmark под вашу нагрузку**: Определите параметры Argon2 так, чтобы хэширование занимало 300-500ms на ваш типичный сервер.

## Теория

Основополагающий принцип безопасности паролей гласит: **хэширование должно быть настолько медленным, насколько это приемлемо для бизнес-логики сервиса, но не быстрее**.
Для интерактивных веб-сервисов целевое время верификации пароля при логине обычно составляет **300–500 мс**. 
- Для пользователя задержка в 300–500 мс при вводе пароля воспринимается как мгновенный отклик.
- Для злоумышленника задержка в 500 мс означает, что перебор даже небольшого словаря на одном сервере займет десятилетия.

Подбор параметров осуществляется методом динамического тестирования (benchmarking):
1. Фиксируем \(p\) (параллелизм) равным числу выделенных ядер CPU для задачи (например, 2 или 4).
2. Фиксируем \(m\) (память) на максимальном разумном уровне (например, 64 МБ).
3. Варьируем \(t\) (итерации) и \(m\) до тех пор, пока медианное время выполнения не попадет в диапазон \([300, 500]\) мс.

В Go бенчмарки можно реализовать как в стандартном пакете `testing.B`, так и с помощью микро-бенчмаркера в `main.go`, автоматически находящего оптимальную конфигурацию.

## Решение по шагам

1. Создадим тестовый прогон с несколькими комбинациями параметров (память от 32 МБ до 128 МБ, итерации от 1 до 5).
2. Напишем функцию замера времени `benchmarkRun(cfg, salt, password)` с отсечением шума первого холодного запуска.
3. Просканируем кандидатов и выберем конфигурацию, время которой ближе всего к 300–500 мс.
4. Выведем подробную таблицу замеров с расчетом пропускной способности (хэшей в секунду на ядро).
5. Продемонстрируем сохранение итоговой конфигурации в виде констант для бэкенда.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"runtime"
	"time"

	"golang.org/x/crypto/argon2"
)

type BenchConfig struct {
	Name        string
	MemoryKiB   uint32
	Iterations  uint32
	Parallelism uint8
}

func benchmarkRun(cfg BenchConfig, salt []byte, password []byte) time.Duration {
	// Делаем прогрев (warm-up)
	_ = argon2.IDKey(password, salt, 1, 16*1024, cfg.Parallelism, 32)

	// Замеряем среднее время по нескольким прогонам
	runs := 3
	var total time.Duration
	for i := 0; i < runs; i++ {
		start := time.Now()
		_ = argon2.IDKey(password, salt, cfg.Iterations, cfg.MemoryKiB, cfg.Parallelism, 32)
		total += time.Since(start)
	}
	return total / time.Duration(runs)
}

func main() {
	salt := make([]byte, 16)
	_, _ = rand.Read(salt)
	password := []byte("TargetLatencyPassphrase2026")

	parallelism := uint8(runtime.NumCPU())
	if parallelism > 4 {
		parallelism = 4
	}

	candidates := []BenchConfig{
		{"Легкий профиль (32MB, t=2)", 32 * 1024, 2, parallelism},
		{"OWASP профиль (64MB, t=3)", 64 * 1024, 3, parallelism},
		{"Усиленный OWASP (64MB, t=5)", 64 * 1024, 5, parallelism},
		{"HighLoad Heavy (128MB, t=3)", 128 * 1024, 3, parallelism},
		{"HighLoad Heavy (128MB, t=5)", 128 * 1024, 5, parallelism},
	}

	fmt.Printf("=== Бенчмаркинг Argon2id под целевую задержку 300-500ms ===\n")
	fmt.Printf("Платформа: %s/%s, CPU cores: %d (потоков: %d)\n\n",
		runtime.GOOS, runtime.GOARCH, runtime.NumCPU(), parallelism)

	var optimal *BenchConfig
	var optimalDur time.Duration

	for _, c := range candidates {
		dur := benchmarkRun(c, salt, password)
		status := "Слишком быстро (<300ms)"
		if dur >= 300*time.Millisecond && dur <= 500*time.Millisecond {
			status = "★ ИДЕАЛЬНО (300-500ms)"
			if optimal == nil {
				cfgCopy := c
				optimal = &cfgCopy
				optimalDur = dur
			}
		} else if dur > 500*time.Millisecond {
			status = "Слишком медленно (>500ms)"
		}

		fmt.Printf("%-30s | RAM: %4d MB | t=%d | Время: %7.1f ms | %s\n",
			c.Name, c.MemoryKiB/1024, c.Iterations, float64(dur.Microseconds())/1000.0, status)
	}

	fmt.Println("\n--- Итог калибровки ---")
	if optimal != nil {
		fmt.Printf("Рекомендуемая конфигурация: %s (Задержка: %s)\n", optimal.Name, optimalDur)
	} else {
		fmt.Println("Ни один профиль не попал точно в 300-500ms. Выберите конфигурацию, ближайшую к 300ms с учетом SLA.")
	}
}
```

## Под капотом

Во время бенчмарка ключевое влияние оказывает пропускная способность контроллера памяти (Memory Bus Bandwidth). Если несколько ядер одновременно запускают Argon2id, они начинают конкурировать за кэш L3 и шину памяти. 
Поэтому замер одиночного хэша всегда дает чуть меньшее время, чем замер в условиях реального продакшна с несколькими параллельными запросами. Рекомендуется закладывать 20–30% запаса по задержке.

## Подводные камни

1. **Проведение бенчмарка на ноутбуке разработчика:** CPU десктопа (например, Apple M3 или Intel i9) обычно работает на более высокой частоте одиночного ядра, чем облачные серверные процессоры (Intel Xeon / AMD EPYC c частотой 2.2–2.8 ГГц). Всегда запускайте калибровочный бенчмарк непосредственно в staging/prod среде Kubernetes.
2. **Игнорирование сборщика мусора (GC) Go:** Постоянное выделение 64–128 МБ памяти на каждый запрос создает нагрузку на аллокатор Go (`mheap`). Убедитесь, что выделяемые срезы не ускользают надолго в кучу и своевременно освобождаются.
3. **DoS от неаутентифицированных пользователей:** 500 мс на хэш означает, что злоумышленник может положить сервер простыми запросами логина с несуществующими логинами. Обязательно используйте кэш и CAPTCHA.

## На собеседовании

**Вопрос с собеседования в Ozon/Т-Банк:** «Почему время хэширования пароля калибруют именно в районе 300-500 мс, а не 5 секунд для максимальной безопасности?»
**Ответ:** Время 300–500 мс является эмпирическим компромиссом между User Experience (UX), устойчивостью к Denial of Service (DoS) и криптографической защитой:
1. **UX:** Задержка до 0.5 с воспринимается человеком как нормальный отклик интерфейса. Задержка в 5 секунд вызовет раздражение пользователей, повторные клики и таймауты мобильных приложений.
2. **DoS и Capacity:** Если хэширование длится 5 секунд, то даже 10 одновременных запросов логина займут все ядра 10-ядерного сервера на 5 секунд, полностью заблокировав сервис.
3. **Безопасность:** Задержка в 500 мс при объеме памяти 64 МБ делает перебор на GPU/ASIC катастрофически медленным (всего 2 попытки в секунду на ядро), сводя к нулю шансы на подбор даже за сотни лет.
