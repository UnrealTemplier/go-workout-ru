# Использование криптографического перца (Password Pepper)

## Условие

Добавьте server-wide secret (pepper) к паролю перед хэшированием. Pepper не в БД — утечка БД не даёт атакующему ничего без pepper.

### Исходная формулировка

**Password pepper**: Добавьте server-wide secret (pepper) к паролю перед хэшированием. Pepper не в БД — утечка БД не даёт атакующему ничего без pepper.

## Теория

Даже при использовании стойких алгоритмов (Argon2id, bcrypt) и уникальных солей, в случае полной компрометации базы данных (SQL-инъекция, украденный бэкап, утечка через дамп) злоумышленник получает доступ ко всем хэшам и солям пользователей и может запустить автономный оффлайн-брутфорс.

Для защиты от утечек базы данных применяется **перец (Password Pepper)**:
- **Соль (Salt):** Публична, уникальна для каждого пользователя, хранится прямо в базе данных рядом с хэшем. Защищает от радужных таблиц (Rainbow Tables).
- **Перец (Pepper):** Строго секретен, один на все приложение (или набор версионированных секретов), хранится **вне базы данных** — в переменных окружения, HashiCorp Vault, AWS Secrets Manager или аппаратном модуле безопасности (HSM).

### Как правильно комбинировать пароль и pepper?
Наивная конкатенация строк `password + pepper` уязвима к атакам удлинения и коллизиям.
Рекомендованный криптографический стандарт: **HMAC-SHA256(pepper, password)**.
1. Вычисляется HMAC от пароля с использованием перца в качестве секретного ключа:
   $$\text{PreHashed} = \text{HMAC-SHA256}(\text{Pepper}, \text{Password})$$
2. Полученный 32-байтный дайджест передается в Argon2id или bcrypt.

Если база данных украдена, но злоумышленник не скомпрометировал сервер приложений с перцем, **все оффлайн-атаки полностью блокируются**, так как атакующий не знает ключ HMAC!

## Решение по шагам

1. Получим секретный перец из безопасного источника (конфиг/окружение).
2. Реализуем предварительное хэширование пароля через `hmac.New(sha256.New, pepper)`.
3. Передадим результат HMAC в Argon2id (или bcrypt).
4. Проверим, что при изменении даже одного бита в перце проверка пароля завершается отказом.
5. Продемонстрируем паттерн ротации перца с поддержкой версионирования ключей.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	"io"

	"golang.org/x/crypto/argon2"
)

// PepperedAuthService управляет хэшированием паролей с серверным перцем
type PepperedAuthService struct {
	pepperSecret []byte // Хранится в Vault / AWS KMS, а НЕ в базе данных!
}

func NewPepperedAuthService(pepperKey []byte) *PepperedAuthService {
	return &PepperedAuthService{pepperSecret: pepperKey}
}

// computeHMAC вычисляет детерминированный 32-байтный псевдопароль
func (s *PepperedAuthService) computeHMAC(password string) []byte {
	mac := hmac.New(sha256.New, s.pepperSecret)
	mac.Write([]byte(password))
	return mac.Sum(nil)
}

// HashPassword хеширует пароль: HMAC-SHA256(pepper, pass) -> Argon2id
func (s *PepperedAuthService) HashPassword(password string) (salt, hash []byte, err error) {
	pepperedPass := s.computeHMAC(password)

	salt = make([]byte, 16)
	if _, err = io.ReadFull(rand.Reader, salt); err != nil {
		return nil, nil, err
	}

	// Хэшируем подготовленный HMAC дайджест
	hash = argon2.IDKey(pepperedPass, salt, 3, 64*1024, 4, 32)
	return salt, hash, nil
}

// VerifyPassword проверяет пароль с использованием перца
func (s *PepperedAuthService) VerifyPassword(password string, salt, expectedHash []byte) bool {
	pepperedPass := s.computeHMAC(password)
	candidateHash := argon2.IDKey(pepperedPass, salt, 3, 64*1024, 4, 32)

	return subtle.ConstantTimeCompare(candidateHash, expectedHash) == 1
}

func main() {
	// Секретный перец приложения из защищенного хранилища ключей
	serverPepper := []byte("SuperSecretProductionPepperKMSKey#2026!")

	authService := NewPepperedAuthService(serverPepper)
	rawPassword := "UserSuperSecretPassword"

	// 1. Успешная регистрация и сохранение в БД
	salt, hash, err := authService.HashPassword(rawPassword)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Данные в БД (скомпрометированы при утечке):\n")
	fmt.Printf("Salt: %s\n", hex.EncodeToString(salt))
	fmt.Printf("Hash: %s\n", hex.EncodeToString(hash))

	// 2. Штатная аутентификация на легитимном сервере
	ok := authService.VerifyPassword(rawPassword, salt, hash)
	fmt.Printf("\nШтатная верификация с верным pepper: %t\n", ok)

	// 3. Симуляция оффлайн-атаки злоумышленника, завладевшего дампом БД, но без pepper!
	attackerFakePepper := []byte("AttackerGuessedPepper")
	attackerService := NewPepperedAuthService(attackerFakePepper)

	attackerAttempt := attackerService.VerifyPassword(rawPassword, salt, hash)
	fmt.Printf("Попытка оффлайн-перебора атакующего без pepper: %t (Взлом невозможен!)\n", attackerAttempt)
}
```

## Под капотом

Конструкция `HMAC-SHA256(pepper, password)` обеспечивает стойкое криптографическое псевдослучайное отображение. Даже если злоумышленник точно знает пароль жертвы (например, распространенный пароль «123456»), он не сможет сгенерировать входной дайджест для проверки совпадения с украденным хэшем, не зная значения `pepperSecret`.
Кроме того, HMAC нивелирует проблему ограничения длины (как 72 байта в bcrypt) и устраняет любые риски атак расширением длины (Length Extension Attacks).

## Подводные камни

1. **Хранение pepper в таблице базы данных рядом с хэшами:** Если сохранить pepper в конфигурационной таблице БД (`app_settings`), то при дампах базы данных перец утечет вместе с хэшами, обесценив всю защиту. Pepper обязан внедряться через переменные окружения или защищенные API (Vault, KMS).
2. **Потеря перца:** Если файл секретов или ключ в KMS утерян без бэкапа, **ни один пользователь системы больше никогда не сможет войти**, и восстановить пароли будет математически невозможно. Необходима процедура Disaster Recovery для ключей KMS.
3. **Ротация перца без версионирования:** При смене скомпрометированного перца нельзя просто заменить ключ — иначе старые пользователи не смогут войти. Рекомендуется хранить идентификатор версии перца (например, `$pepper_v1$...`) в строке хэша.

## На собеседовании

**Вопрос с собеседования в Авито/Ozon:** «В чем принципиальная разница между Salt и Pepper при защите учетных данных, и где каждый из них должен храниться?»
**Ответ:** 
- **Соль (Salt)** генерируется случайно для каждого пользователя, хранится открыто в базе данных и предотвращает использование предварительно рассчитанных радужных таблиц (Rainbow Tables) и атак по схожим паролям разных пользователей.
- **Перец (Pepper)** является секретным ключом приложения (один на всех или пул версионированных ключей), хранится строго изолированно от базы данных (в Vault, KMS или HSM). Он защищает учетные записи от оффлайн-брутфорса при полной утечке дампа базы данных: без секретного ключа перебор невозможен даже на суперкомпьютере.
