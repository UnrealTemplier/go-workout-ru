# [MD5/SHA-256] Почему быстрое прямое хэширование паролей — катастрофа

## Условие

**[MD5/SHA256 — Почему так нельзя]**: Напиши функцию хэширования пароля через `sha256.Sum256`. Объясни, почему хранение паролей в виде обычного SHA-хэша смертельно опасно (уязвимость к радужным таблицам и быстрому перебору на GPU).

## Теория

Исторически начинающие разработчики совершают грубейшую ошибку: вычисляют хэш пароля функцией `sha256.Sum256([]byte(password))` или `md5.Sum` и сохраняют полученную hex-строку в базу данных.

Почему прямое хэширование быстрым криптографическим хэшем смертельно опасно:
1. **Чудовищная скорость современных GPU и ASIC:**
   - Алгоритмы семейств MD5, SHA-1, SHA-256 проектировались как **быстрые потоковые хэш-функции** для проверки целостности гигабайтных файлов и сетевых пакетов.
   - Одна потребительская видеокарта NVIDIA GeForce RTX 4090 вычисляет **более 25 миллиардов SHA-256 в секунду** (25 GH/s).
   - Кластер из 8 видеокарт перебирает все 8-значные пароли из букв и цифр (\(62^8 \approx 2.18 \times 10^{14}\)) менее чем за **15 минут**!
2. **Уязвимость к радужным таблицам (Rainbow Tables):**
   - Если хэшировать пароль без соли, одинаковые пароли разных пользователей (`"123456"`, `"password"`) дадут абсолютно идентичный хэш `e3b0c44298fc...`.
   - Злоумышленники заранее сгенерировали терабайтные базы данных (Rainbow Tables), где для каждого популярного MD5/SHA хэша предвычислен исходный пароль. Взлом происходит за одну операцию поиска по индексу (0.001 секунды).

## Решение по шагам

1. Напишите наивную функцию хэширования `insecureFastHash(password string) string`.
2. Продемонстрируйте проблему одинаковых хэшей: хэшируйте одинаковый пароль двух разных пользователей.
3. Проведите микро-бенчмарк: замерьте время вычисления 100 000 итераций `sha256.Sum256`.
4. Рассчитайте теоретическое время перебора 8-символьного пароля на современном GPU-кластере.
5. Сделайте инженерный вывод о необходимости специализированных медленных функций (bcrypt, Argon2).

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/sha256"
	"fmt"
	"time"
)

// insecureFastHash иллюстрирует КАТАСТРОФИЧЕСКИ НЕБЕЗОПАСНЫЙ антипаттерн
func insecureFastHash(password string) string {
	hash := sha256.Sum256([]byte(password))
	return fmt.Sprintf("%x", hash)
}

func main() {
	fmt.Println("=== ДЕМОНСТРАЦИЯ АНТИПАТТЕРНА: Хэширование через SHA-256 ===")

	// 1. Проблема идентичных хэшей
	user1Pass := "SecretPassword123"
	user2Pass := "SecretPassword123"

	hash1 := insecureFastHash(user1Pass)
	hash2 := insecureFastHash(user2Pass)

	fmt.Printf("User 1 Hash: %s\n", hash1)
	fmt.Printf("User 2 Hash: %s\n", hash2)
	fmt.Printf("Хэши идентичны? %v (Утечка: злоумышленник сразу видит совпадение паролей!)\n\n", hash1 == hash2)

	// 2. Замер скорости вычисления (почему GPU перебирает миллиарды хэшей)
	iterations := 200_000
	t0 := time.Now()
	for i := 0; i < iterations; i++ {
		_ = sha256.Sum256([]byte(user1Pass))
	}
	duration := time.Since(t0)

	hashesPerSec := float64(iterations) / duration.Seconds()
	fmt.Printf("=== Скорость на ОДНОМ ядре CPU ===\n")
	fmt.Printf("Вычислено %d хэшей за %v\n", iterations, duration)
	fmt.Printf("Скорость CPU: %.0f хэшей/сек\n", hashesPerSec)

	// Экстраполяция на GPU
	rtx4090Speed := 25_000_000_000.0 // 25 млрд/сек
	combinations8Chars := 218_340_105_584_896.0 // 62^8

	secondsToCrack := combinations8Chars / rtx4090Speed
	fmt.Printf("\n=== Оценка времени взлома на 1x RTX 4090 ===\n")
	fmt.Printf("Пространство 8-значных паролей (A-Z, a-z, 0-9): ~2.18e14\n")
	fmt.Printf("Время полного перебора: %.1f секунд (~%.1f минут)\n", secondsToCrack, secondsToCrack/60)
	fmt.Println("ВЫВОД: Быстрые хэши категорически непригодны для паролей!")
}
```

## Под капотом

В чем архитектурная разница между криптографическими хэшами данных и функциями хэширования паролей:
1. **Хэш данных (SHA-256, BLAKE3):** Требует минимальной задержки, чтобы проверять гигабайтные файлы со скоростью работы шины NVMe/PCIe (до 5–10 ГБ/с). Каждая операция занимает десятки наносекунд.
2. **Хэш паролей (Password KDF: bcrypt, Argon2id):**
   - Пароль проверяется человеком при авторизации (человек не заметит задержку в 100–300 мс).
   - Алгоритм **обязан быть вычислительно дорогим** (Time-cost) и требовать много оперативной памяти (Memory-cost).
   - Если проверка одного пароля на сервере занимает 250 мс, сервер легко обрабатывает 4 RPS на ядро. Но для злоумышленника скорость перебора падает с 25 млрд попыток в секунду до 4 попыток в секунду, делая брутфорс физически невозможным.

## Подводные камни

1. **Иллюзия безопасности через множественный SHA-256:** Некоторые разработчики пишут цикл: `for i := 0; i < 1000; i++ { pass = sha256(pass) }`. Это не спасает от специализированных FPGA/ASIC, так как алгоритм не требует памяти (memory-hardness = 0) и аппаратно конвейеризуется в микросхемах.
2. **Добавление статического префикса вместо случайной соли:** Префикс `sha256("my_secret_prefix" + pass)` легко нивелируется после первой же утечки исходного кода.

## На собеседовании

**Вопрос с собеседования:** Почему нельзя использовать SHA-256 или SHA-512 даже с добавлением уникальной соли для хэширования паролей в продакшене?
**Ответ:** Соль защищает исключительно от предварительно рассчитанных радужных таблиц (Rainbow Tables), но **совершенно не защищает от прямого перебора на GPU/ASIC**. SHA-256 аппаратно прост и требует менее 100 байт оперативной памяти. На современных видеокартах или майнинговых ASIC-чипах можно параллельно запускать миллионы потоков перебора SHA-256. Пароль длиной 8-10 символов со случайной солью будет взломан на ферме GPU за считанные часы. Для паролей обязательны memory-hard алгоритмы (Argon2id, scrypt) или CPU-hard с настраиваемой стоимостью (bcrypt).
