# Параметр Cost в bcrypt: экспоненциальный рост времени и защита от DoS сервера

## Условие

**Cost (Стоимость bcrypt)**: Запусти бенчмарк для `bcrypt` с `cost = 10` и `cost = 14`. Убедись, что увеличение стоимости делает хэширование экспоненциально медленнее (что защищает от брутфорса), но сильно грузит CPU сервера.

## Теория

Параметр `cost` в bcrypt (от `bcrypt.MinCost = 4` до `bcrypt.MaxCost = 31`) представляет собой **двоичный показатель степени**:
$$\text{Iterations} = 2^{\text{cost}}$$

Экспоненциальная шкала:
- `cost = 10`: \(2^{10} = 1024\) раундов (\(\sim 40 - 80\) мс на современном CPU). Значение по умолчанию (`bcrypt.DefaultCost`).
- `cost = 11`: \(2^{11} = 2048\) раундов (\(\sim 80 - 160\) мс, в 2 раза медленнее).
- `cost = 12`: \(2^{12} = 4096\) раундов (\(\sim 160 - 320\) мс, в 4 раза медленнее). Рекомендация OWASP.
- `cost = 14`: \(2^{14} = 16384\) раундов (\(\sim 800 - 1500\) мс, в 16 раз медленнее!).

Инженерный компромисс безопасности:
- Если `cost` слишком низкий (например, 6): GPU-ферма атакующего перебирает миллионы паролей в секунду.
- Если `cost` слишком высокий (например, 15): проверка одного пароля блокирует поток на 2 секунды. При атаке 100 одновременных запросов сервер исчерпает пул горутин и упадет с DoS.

## Решение по шагам

1. Создайте бенчмарк-функцию, замеряющую точное время выполнения `bcrypt.GenerateFromPassword` для заданного cost.
2. Протестируйте значения cost: 10, 11, 12, 13, 14.
3. Вычислите коэффициент замедления между соседними шагами (должен быть строго \(\approx 2.0\)).
4. Проанализируйте максимальную пропускную способность одного CPU-ядра при различных cost.
5. Сформулируйте рекомендации по выбору cost под конкретное серверное железо.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"

	"golang.org/x/crypto/bcrypt"
)

func main() {
	password := []byte("StandardCorporatePassword#2026")

	fmt.Println("=== Исследование экспоненциального роста стоимости bcrypt ===")
	fmt.Println("Cost | Раундов | Время вычисления | Коэффициент | Макс. RPS на 1 ядро")
	fmt.Println("-----+---------+------------------+-------------+-------------------")

	costs := []int{10, 11, 12, 13, 14}
	var prevDuration time.Duration

	for _, cost := range costs {
		rounds := 1 << cost // 2^cost

		t0 := time.Now()
		_, _ = bcrypt.GenerateFromPassword(password, cost)
		duration := time.Since(t0)

		var ratioStr string
		if prevDuration > 0 {
			ratio := float64(duration) / float64(prevDuration)
			ratioStr = fmt.Sprintf("x%.2f", ratio)
		} else {
			ratioStr = "база"
		}

		maxRPS := 1.0 / duration.Seconds()

		fmt.Printf(" %2d  | %7d | %16v | %11s | %10.1f rps\n",
			cost, rounds, duration, ratioStr, maxRPS)

		prevDuration = duration
	}

	fmt.Println("\nВЫВОД: Каждый шаг (+1 cost) строго удваивает время вычислений (2^N).")
	fmt.Println("Рекомендация: выбирать cost так, чтобы хэширование занимало ~150-250 мс.")
}
```

## Под капотом

Почему bcrypt так эффективен против GPU перебора:
1. В алгоритме Eksblowfish ключевое расписание интенсивно модифицирует S-блоки размером 4 КБ в цикле \(2^{\text{cost}}\) раз.
2. Доступ к S-блокам происходит по псевдослучайным адресам, зависящим от данных.
3. Процессоры x86-64 имеют быстрый кэш L1d (32–48 КБ на ядро с латентностью 4 такта), где эти 4 КБ помещаются идеально.
4. На видеокартах GPU тысячи потоков делят крошечный общий кэш, из-за чего при независимом случайном обращении к памяти происходит катастрофическая деградация (Memory Divergence и Bank Conflicts), снижая эффективность GPU-майнеров в сотни раз по сравнению с простым SHA-256.

## Подводные камни

1. **Установка cost=15+ в синхронном HTTP-хэндлере:** Приводит к быстрому исчерпанию соединений пула обратного прокси (Nginx/Envoy gateway timeout 504) при малейшем всплеске трафика авторизации.
2. **Использование cost=4 (bcrypt.MinCost) в продакшене:** Некоторые разработчики ставят минимальную стоимость, «чтобы API летало». При cost=4 хэш вычисляется за 0.5 миллисекунды, и стойкость системы падает до уровня SHA-256.

## На собеседовании

**Вопрос с собеседования:** Как в BigTech-сервисе с миллионами пользователей плавно повысить стоимость bcrypt с устаревшего cost=10 до cost=12 без сброса паролей пользователей?
**Ответ:** Используется паттерн **Transparent Hash Upgrade (Прозрачный апгрейд хэша)**:
1. При авторизации сервер считывает хэш из базы данных и вызывает `cost, _ := bcrypt.Cost([]byte(user.PasswordHash))`.
2. Сервер валидирует введенный пароль через `bcrypt.CompareHashAndPassword`.
3. Если пароль верный, но `cost < TargetCost` (например, \(10 < 12\)), сервер тут же в этой же горутине генерирует новый хэш с `cost = 12` из уже находящегося в памяти открытого пароля и асинхронно обновляет запись в БД (`UPDATE users SET password_hash = $1 WHERE id = $2`).
4. За 3–6 месяцев все активные пользователи незаметно и бесшовно мигрируют на новый уровень безопасности без сброса паролей.
