# Углубленный анализ crypto/rand vs math/rand: безопасность против атак на сид

## Условие

**crypto/rand vs math/rand**: Напишите код, который использует оба пакета для генерации чисел. Покажите, почему `math/rand` **никогда** нельзя использовать для security-задач (предсказуемость seed, state-based атаки).

## Теория

Безопасность любой криптографической системы базируется на невозможности для атакующего предсказать случайные значения.

Почему `math/rand` фундаментально непригоден для безопасности:
1. **Ограниченное пространство состояний:** В Go `math/rand` исторически использовал 607-битный генератор с обратной связью (LFSR) или 64-битный сид. Если сид инициализируется как `time.Now().UnixNano()`, злоумышленнику, знающему примерное время генерации токена с точностью до 1 секунды, достаточно перебрать всего \(10^9\) вариантов (1 секунда на CPU).
2. **State Reconstruction (Атака восстановления состояния):** Если злоумышленник перехватил несколько подряд идущих случайных чисел `math/rand`, он может решить систему линейных уравнений над полем \(\mathbb{F}_2\) и полностью вычислить текущий внутренний регистр сдвига генератора. После этого злоумышленник знает все будущие значения токенов до перезапуска процесса.
3. **Отсутствие энтропийного перемешивания:** `math/rand` не собирает новую энтропию во время работы. `crypto/rand`, напротив, постоянно черпает аппаратную энтропию из пула ядра операционной системы.

## Решение по шагам

1. Создайте генератор `math/rand` с сидом на основе миллисекунд текущего времени.
2. Сгенерируйте и выведите 5 псевдослучайных чисел.
3. Напишите код атакующего, который зная диапазон времени в пределах 50 миллисекунд, восстанавливает точный сид за миллисекунды.
4. Сгенерируйте аналогичные 5 чисел через `crypto/rand` с помощью `rand.Int`.
5. Докажите, что вывод `crypto/rand` не содержит математической корреляции и не поддается обратной редукции.

## Код решения

**`main.go`**

```go
package main

import (
	crand "crypto/rand"
	"fmt"
	"math/big"
	mrand "math/rand"
	"time"
)

func main() {
	// 1. Имитация уязвимого сервера
	serverTime := time.Now().UnixMilli()
	insecurePRNG := mrand.New(mrand.NewSource(serverTime))

	// Сервер генерирует 3 последовательных сессионных ID
	victimToken1 := insecurePRNG.Int63()
	victimToken2 := insecurePRNG.Int63()
	victimToken3 := insecurePRNG.Int63()

	fmt.Println("=== Уязвимый сервер на базе math/rand ===")
	fmt.Printf("Выпущен токен 1: %d\n", victimToken1)
	fmt.Printf("Выпущен токен 2: %d\n\n", victimToken2)

	// 2. Атакующий перехватывает token1 и token2
	fmt.Println("=== Атака реконструкции сида ===")
	approximateTime := time.Now().UnixMilli()
	searchRadiusMs := int64(100) // перебираем окно +/- 100 мс

	var foundSeed int64 = -1
	for candidate := approximateTime - searchRadiusMs; candidate <= approximateTime+searchRadiusMs; candidate++ {
		tester := mrand.New(mrand.NewSource(candidate))
		if tester.Int63() == victimToken1 && tester.Int63() == victimToken2 {
			foundSeed = candidate
			break
		}
	}

	if foundSeed != -1 {
		fmt.Printf("УСПЕХ! Сид взломан: %d (задержка поиска < 1 мс)\n", foundSeed)
		// Предсказываем токен 3:
		cracker := mrand.New(mrand.NewSource(foundSeed))
		cracker.Int63()
		cracker.Int63()
		predicted := cracker.Int63()

		fmt.Printf("Предсказанный токен 3 жертвы: %d\n", predicted)
		fmt.Printf("Реальный токен 3 на сервере:    %d\n", victimToken3)
		fmt.Printf("Атака успешна? %v\n\n", predicted == victimToken3)
	}

	// 3. Защищенная генерация через crypto/rand
	fmt.Println("=== Защищенный генератор crypto/rand ===")
	maxLimit := big.NewInt(1_000_000_000)
	secureNum1, _ := crand.Int(crand.Reader, maxLimit)
	secureNum2, _ := crand.Int(crand.Reader, maxLimit)

	fmt.Printf("Безопасное случайное число 1: %s\n", secureNum1.String())
	fmt.Printf("Безопасное случайное число 2: %s\n", secureNum2.String())
	fmt.Println("Сид отсутствует в памяти процесса, состояние защищено ядром ОС.")
}
```

## Под капотом

Разница в безопасности на уровне операционной системы:
- `math/rand`: Вся структура генератора (`rngSource` со срезом `vec [607]int64`) аллоцирована в куче Go-процесса. Она абсолютно изолирована от системной энтропии и живет по детерминированным правилам линейной рекурренты \(X_n = (X_{n-24} + X_{n-55}) \pmod{2^{31}-1}\).
- `crypto/rand`: Вызывает системный вызов ядра `getrandom(2)` или `sysctl(KERN_ARND)`. Ядро Linux непрерывно подмешивает энтропию физических устройств (дисковый контроллер, сетевые карты, микросекундные флуктуации тактов CPU). Даже имея полный снимок оперативной памяти процесса Go в момент времени \(T\), невозможно предсказать, какие байты вернет следующий вызов `crypto/rand` в момент \(T+1\).

## Подводные камни

1. **Создание одного глобального math/rand с мьютексом:** Помимо уязвимости безопасности, стандартный `math/rand` использует глобальный `sync.Mutex` под капотом, создавая колоссальные блокировки и просадку RPS в высоконагруженных микросервисах.
2. **Использование crypto/rand для тасования слайсов в тестах:** В тестах или бенчмарках `crypto/rand` избыточен и замедляет выполнение из-за системных вызовов в ядро. Там как раз уместен быстрый `math/rand/v2`.

## На собеседовании

**Вопрос с собеседования:** В каких случаях в Go допустимо использовать `math/rand`, а в каких строго обязателен `crypto/rand`?
**Ответ:** `math/rand` (или `math/rand/v2`) допустим **исключительно для некасающихся безопасности задач**: симуляции Монте-Карло, тасование тестовых данных в unit-тестах, расчет случайного джиттера для сетевых повторов (exponential backoff with jitter) и балансировка нагрузки (randomized load balancing). Во всех задачах, связанных с безопасностью (генерация паролей, солей, session ID, CSRF-токенов, API-ключей, симметричных ключей AES и Nonce/IV), использование `math/rand` является критической уязвимостью первого уровня (CVE High/Critical) и строго требует `crypto/rand`.
