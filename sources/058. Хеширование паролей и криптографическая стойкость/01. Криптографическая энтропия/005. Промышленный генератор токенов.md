# Промышленный генератор токенов: GenerateToken(n int) с обработкой ошибок энтропии

## Условие

**Генерация криптографически стойкого токена**: Напишите функцию `GenerateToken(n int) (string, error)`, которая возвращает base64url-закодированные `n` случайных байт через `crypto/rand.Read`.

## Теория

Написание надежных вспомогательных утилит генерации токенов в промышленных библиотеках требует строгого соблюдения принципов defensiveness (защитного программирования).

Ключевые инженерные правила:
1. **Валидация входных аргументов:** Защита от передачи отрицательных или недопустимо малых длин энтропии (например, токен длиной 2 байта тривиально подбирается за 65536 запросов).
2. **Использование `io.ReadFull`:** Обычный `rand.Read(buf)` теоретически может вернуть частичное чтение при прерывании системного вызова сигналом ОС (`EINTR`). Обертка `io.ReadFull(rand.Reader, buf)` гарантирует чтение строго запрошенного количества байт.
3. **Строгое кодирование `base64.RawURLEncoding`:** Гарантирует отсутствие символов `+`, `/` и `=` без необходимости дополнительного URL-экранирования.
4. **Константный размер вывода:** Для \(N\) байт длина результирующей строки в `RawURLEncoding` строго детерминирована и равна \(\lceil \frac{8N}{6} \rceil\) символов.

## Решение по шагам

1. Создайте функцию `GenerateToken(n int) (string, error)`.
2. Проверьте граничное условие \(n \ge 16\).
3. Выделите срез байт `make([]byte, n)`.
4. Заполните срез через `io.ReadFull(rand.Reader, buf)`.
5. Верните результат `base64.RawURLEncoding.EncodeToString(buf)`.
6. Напишите тесты для проверки уникальности 10 000 сгенерированных подряд токенов.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/base64"
	"errors"
	"fmt"
	"io"
	"log"
)

var (
	ErrInvalidTokenLength = errors.New("длина токена должна быть не менее 16 байт")
	ErrEntropyFailure     = errors.New("сбой системного генератора случайных чисел")
)

// GenerateToken возвращает криптографически стойкий URL-safe токен из n случайных байт
func GenerateToken(n int) (string, error) {
	if n < 16 {
		return "", fmt.Errorf("%w: запрошено %d", ErrInvalidTokenLength, n)
	}

	buf := make([]byte, n)
	if _, err := io.ReadFull(rand.Reader, buf); err != nil {
		return "", fmt.Errorf("%w: %w", ErrEntropyFailure, err)
	}

	return base64.RawURLEncoding.EncodeToString(buf), nil
}

func main() {
	// 1. Генерация стандартного API-ключа (32 байта)
	apiKey, err := GenerateToken(32)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
	fmt.Printf("API-токен (32 байта -> %d символов):\n%s\n\n", len(apiKey), apiKey)

	// 2. Генерация компактного CSRF-токена (16 байт)
	csrfToken, err := GenerateToken(16)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
	fmt.Printf("CSRF-токен (16 байт -> %d символов):\n%s\n\n", len(csrfToken), csrfToken)

	// 3. Проверка валидации на малый размер
	_, err = GenerateToken(8)
	if errors.Is(err, ErrInvalidTokenLength) {
		fmt.Printf("Ожидаемый отказ при небезопасном размере: %v\n\n", err)
	}

	// 4. Тест уникальности: генерируем 10 000 токенов в map
	seen := make(map[string]struct{}, 10000)
	for i := 0; i < 10000; i++ {
		t, _ := GenerateToken(16)
		if _, exists := seen[t]; exists {
			log.Fatalf("Коллизия токенов обнаружена на шаге %d!", i)
		}
		seen[t] = struct{}{}
	}
	fmt.Println("Тест на коллизии пройден: 10 000 токенов абсолютно уникальны.")
}
```

## Под капотом

Почему `io.ReadFull` предпочтительнее простого `rand.Read`:
В стандартной библиотеке Go метод `rand.Read` реализован так:
```go
func Read(b []byte) (n int, err error) {
    return io.ReadFull(Reader, b)
}
```
Однако прямой вызов `io.ReadFull(rand.Reader, buf)` в собственном коде считается лучшей практикой по двум причинам:
1. Он явно декларирует контракт полного чтения на уровне статического анализатора и линтера.
2. В случае работы с пользовательскими реализациями `io.Reader` (например, аппаратный HSM-модуль через unix socket) гарантирует, что если ридер вернет меньше байт до EOF, вызов вернет ошибку `io.ErrUnexpectedEOF`, а не вернет частично заполненный массив нулей.

## Подводные камни

1. **Аллокация лишней памяти при форматировании:** Использование `fmt.Sprintf("%x", buf)` вместо `hex.EncodeToString` или `base64.RawURLEncoding.EncodeToString` создает лишние аллокации интерфейсов `any` и замедляет высоконагруженные аутентификационные middleware.
2. **Использование стандартного Base64 вместо URLEncoding:** Стандартный Base64 генерирует символы `+` и `/`. При передаче в GET-запросе веб-сервер распарсит `+` как пробел, и валидация токена завершится ошибкой 401 Unauthorized.

## На собеседовании

**Вопрос с собеседования:** Почему длина 16 байт (128 бит) считается абсолютным минимальным порогом для генерации криптографических идентификаторов сессий и токенов?
**Ответ:** Согласно парадоксу дней рождения (Birthday Paradox), вероятность возникновения коллизии достигает 50% при генерации \(N \approx \sqrt{2^B} = 2^{B/2}\) случайных элементов. Для 128 бит энтропии порог коллизии составляет \(2^{64} \approx 1.84 \times 10^{19}\) токенов. Даже если в распределенной системе генерируется 1 миллиард токенов в секунду, вероятность случайной коллизии между двумя пользователями за 100 лет пренебрежимо мала (\(< 10^{-6}\)). Использование 64-битных токенов (8 байт) снижает порог коллизий до \(2^{32} \approx 4\) миллиардов, что в BigTech масштабах достигается за несколько недель.
