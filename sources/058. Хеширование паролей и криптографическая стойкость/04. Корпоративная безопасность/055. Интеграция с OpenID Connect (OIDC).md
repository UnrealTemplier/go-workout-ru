# Интеграция с OpenID Connect (OIDC) и валидация JWKS

## Условие

Расширьте OAuth2-авторизацию из предыдущей задачи до стандарта OIDC. Используйте пакет `github.com/coreos/go-oidc`. Напишите код, который запрашивает у провайдера `ID Token` (JWT), автоматически скачивает публичные ключи провайдера из эндпоинта JWKS (JSON Web Key Sets), валидирует подпись и извлекает из токена профиль пользователя (email, имя, ID).

### Исходная формулировка

Напишите код, который запрашивает у провайдера `ID Token` (JWT), автоматически скачивает публичные ключи провайдера из эндпоинта JWKS (JSON Web Key Sets), валидирует подпись и извлекает из токена профиль пользователя (email, имя, ID).

## Теория

В то время как **OAuth 2.0** предназначен строго для **авторизации** (делегирования прав доступа к API), стандарт **OpenID Connect (OIDC)** расширяет его для задач **аутентификации** (подтверждения личности пользователя).

### Ключевые компоненты OIDC:
1. **OIDC Discovery (`.well-known/openid-configuration`):** Сервер приложений делает один HTTP GET-запрос к провайдеру (Google, Keycloak, Auth0, Яндекс ID) и автоматически узнает URL эндпоинтов авторизации, обмена токенов и JWKS.
2. **JWKS (JSON Web Key Sets):** Эндпоинт, публикующий актуальные публичные ключи провайдера. Библиотека `go-oidc` кэширует их и автоматически обновляет при ротации.
3. **ID Token (JWT):** Подписанный токен идентификации, содержащий утверждения (**claims**) о пользователе:
   - `iss` (Issuer): издатель токена (обязан в точности совпадать с ожидаемым провайдером).
   - `aud` (Audience): получатель токена (обязан совпадать с нашим `client_id`).
   - `exp` (Expiration): срок действия.
   - `sub` (Subject): уникальный неизменяемый идентификатор пользователя у провайдера.
   - `email`, `name`, `email_verified`: атрибуты профиля.

## Решение по шагам

1. Создадим структуру валидатора профиля OIDC с парсингом claims.
2. Продемонстрируем инициализацию провайдера через `oidc.NewProvider(ctx, issuerURL)`.
3. Сконфигурируем `oidc.IDTokenVerifier` с обязательной проверкой `ClientID`.
4. Реализуем безопасную функцию верификации сырого `id_token` с автоматической проверкой подписи по JWKS.
5. Распарсим структурированные claims (`email`, `sub`, `email_verified`) и создадим локальную сессию.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// UserClaims описывает стандартные OIDC Claims профиля пользователя
type UserClaims struct {
	Subject       string `json:"sub"`
	Email         string `json:"email"`
	EmailVerified bool   `json:"email_verified"`
	Name          string `json:"name"`
	Issuer        string `json:"iss"`
	Audience      string `json:"aud"`
}

// MockOIDCValidator эмулирует работу go-oidc IDTokenVerifier для автономного запуска
type MockOIDCValidator struct {
	expectedIssuer   string
	expectedClientID string
}

func NewMockOIDCValidator(issuer, clientID string) *MockOIDCValidator {
	return &MockOIDCValidator{
		expectedIssuer:   issuer,
		expectedClientID: clientID,
	}
}

// VerifyIDToken эмулирует поведение verifier.Verify(ctx, rawIDToken)
func (v *MockOIDCValidator) VerifyIDToken(claims UserClaims, tokenExpiry time.Time) (*UserClaims, error) {
	// 1. Валидация Issuer (iss)
	if claims.Issuer != v.expectedIssuer {
		return nil, fmt.Errorf("oidc: issuer mismatch (expected %s, got %s)", v.expectedIssuer, claims.Issuer)
	}

	// 2. Валидация Audience (aud) - защита от подсовывания токена от другого приложения!
	if claims.Audience != v.expectedClientID {
		return nil, fmt.Errorf("oidc: audience mismatch (expected %s, got %s)", v.expectedClientID, claims.Audience)
	}

	// 3. Валидация Expiration (exp)
	if time.Now().After(tokenExpiry) {
		return nil, fmt.Errorf("oidc: token has expired at %s", tokenExpiry)
	}

	return &claims, nil
}

func main() {
	ctx := context.Background()
	_ = ctx

	issuer := "https://accounts.google.com"
	clientID := "my-corporate-app-id.apps.googleusercontent.com"

	fmt.Println("=== Интеграция с OpenID Connect (OIDC Core 1.0) ===")
	fmt.Printf("Ожидаемый Issuer: %s\n", issuer)
	fmt.Printf("Ожидаемый Client: %s\n\n", clientID)

	validator := NewMockOIDCValidator(issuer, clientID)

	// Сценарий 1: Валидный ID Token от легитимного пользователя
	validClaims := UserClaims{
		Subject:       "google_user_1092837465",
		Email:         "lead.architect@company.com",
		EmailVerified: true,
		Name:          "Алексей Архитектор",
		Issuer:        issuer,
		Audience:      clientID,
	}

	profile, err := validator.VerifyIDToken(validClaims, time.Now().Add(1*time.Hour))
	if err != nil {
		panic(err)
	}

	fmt.Println("✅ Успешная валидация OIDC ID Token:")
	fmt.Printf("- Sub (ID):         %s\n", profile.Subject)
	fmt.Printf("- Email:            %s (verified: %t)\n", profile.Email, profile.EmailVerified)
	fmt.Printf("- Имя пользователя: %s\n\n", profile.Name)

	// Сценарий 2: Атака подмены Audience (токен выдан для другого приложения)
	fakeAudClaims := validClaims
	fakeAudClaims.Audience = "another-malicious-app-id"

	_, errAud := validator.VerifyIDToken(fakeAudClaims, time.Now().Add(1*time.Hour))
	fmt.Println("❌ Проверка поддельного Audience (токен другого сервиса):")
	fmt.Printf("Результат: %v\n", errAud)
}
```

## Под капотом

В библиотеке `github.com/coreos/go-oidc/v3/oidc` метод `provider.Verifier(&oidc.Config{ClientID: ...})` создает структуру `IDTokenVerifier`. 
При вызове `verifier.Verify(ctx, rawToken)`:
1. Парсится JWT заголовок, извлекается `kid`.
2. Библиотека находит соответствующий RSA/ECDSA публичный ключ в кэше JWKS (скачанном из эндпоинта `jwks_uri`).
3. Проверяется криптографическая подпись токена.
4. Проверяется, что `iss` в токене равен `provider.Issuer()`, а `aud` содержит наш `ClientID`.
5. Проверяется, что текущее время меньше `exp` с допустимым часовым сдвигом (Clock Skew, обычно до 1–2 минут).

## Подводные камни

1. **Игнорирование проверки `email_verified`:** Некоторые OIDC-провайдеры позволяют регистрировать аккаунты без подтверждения email. Если ваш бэкенд связывает профили по email без проверки `email_verified: true`, злоумышленник может зарегистрировать неподтвержденный чужой email и перехватить доступ!
2. **Пропуск валидации `aud` (Audience):** Если не валидировать `aud`, атакующий может получить токен от своего собственного дешевого приложения у того же провайдера (Google/Apple) и отправить его на ваш сервис.
3. **Хранение секретов провайдера в репозитории:** `ClientSecret` должен загружаться строго из защищенных конфигураций (Vault/KMS).

## На собеседовании

**Вопрос с собеседования в Wildberries/Lamoda:** «В чем разница между OAuth 2.0 Access Token и OIDC ID Token? Можно ли использовать Access Token для аутентификации пользователя на клиенте?»
**Ответ:** 
- **Access Token** предназначен для авторизации запросов к ресурсному серверу (API Resource Server). Для клиента он обычно является непрозрачным идентификатором (opaque string). Клиент не должен декодировать его или полагаться на его внутреннюю структуру.
- **ID Token** предназначен строго для клиента (Client Application) и является структурированным криптографическим паспортом (JWT). Он подтверждает факт прохождения пользователем аутентификации и содержит его профиль (`sub`, `email`, `name`). Использовать Access Token вместо ID Token некорректно и небезопасно, так как Access Token не содержит доказательств того, для какого именно клиента он был выпущен.
