## Теория

Формат **JSON Web Tokens (JWT / RFC 7519)** на протяжении десятилетия доминировал в веб-разработке, однако накопил фундаментальные архитектурные изъяны (Design Flaws):

### Главные уязвимости JWT:
1. **Атака `"alg": "none"`:** Заголовок JWT передается клиентом в открытом виде. Злоумышленник может изменить алгоритм на `none` и стереть подпись. Уязвимые библиотеки доверяли заголовку и считали токен валидным!
2. **Algorithm Confusion (RS256 vs HS256):** Злоумышленник меняет в заголовке `RS256` на `HS256`. Сервер берет публичный ключ RSA и проверяет токен как HMAC-SHA256, используя публичный ключ (который известен всем!) в качестве секрета HMAC.
3. **Открытость полезной нагрузки (Payload Leaks):** По умолчанию JWT в формате JWS только подписан, но не зашифрован. Любые данные (User ID, роли, email) видны клиенту через обычный Base64.

### Почему PASETO (Platform-Agnostic Security Tokens) безопаснее?
**PASETO** исключает выбор алгоритмов разработчиком («Cipher Agility Trap»). Формат токена строго версионирован:
- **`v4.local`:** Симметричное сквозное шифрование. Полезная нагрузка полностью зашифрована шифром **XChaCha20-Poly1305** с аутентификацией открытого текста. Клиент не видит содержимое токена, а подделка математически невозможна.
- **`v4.public`:** Асимметричная цифровая подпись на эллиптической кривой **Ed25519**.
- В PASETO **нет заголовка `alg`**, поэтому подмена алгоритма невозможна в принципе.

## Решение по шагам

1. Подключим стандартный генератор PASETO v2/v4 (`aidarkhanov/nanopaseto` или `o1egl/paseto`).
2. Создадим структуру полезной нагрузки `CustomClaims` с ролями пользователя и временем экспирации.
3. Сгенерируем 32-байтный симметричный ключ шифрования.
4. Зашифруем токен с помощью метода `Encrypt` (v2/v4.local), получив защищенную строку вида `v4.local....`.
5. Расшифруем токен, проверим срок действия и извлечем данные пользователя.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"time"

	"github.com/o1egl/paseto"
)

// AppSessionClaims содержит пользовательские сессионные данные
type AppSessionClaims struct {
	UserID    string    `json:"user_id"`
	Role      string    `json:"role"`
	Email     string    `json:"email"`
	IssuedAt  time.Time `json:"iat"`
	ExpiresAt time.Time `json:"exp"`
}

// TokenManager управляет безопасными токенами PASETO
type TokenManager struct {
	pasetoV2     *paseto.V2
	symmetricKey []byte // 32 байта для симметричного шифрования AEAD
}

func NewTokenManager(key []byte) (*TokenManager, error) {
	if len(key) != 32 {
		return nil, fmt.Errorf("symmetric key must be exactly 32 bytes")
	}
	return &TokenManager{
		pasetoV2:     paseto.NewV2(),
		symmetricKey: key,
	}, nil
}

// GenerateToken шифрует claims в симметричный токен (v2/v4.local)
func (m *TokenManager) GenerateToken(userID, role, email string, duration time.Duration) (string, error) {
	now := time.Now()
	claims := AppSessionClaims{
		UserID:    userID,
		Role:      role,
		Email:     email,
		IssuedAt:  now,
		ExpiresAt: now.Add(duration),
	}

	// Encrypt производит шифрование (AEAD ChaCha20-Poly1305)
	// Содержимое токена полностью зашифровано и недоступно для чтения клиентом!
	token, err := m.pasetoV2.Encrypt(m.symmetricKey, claims, nil)
	if err != nil {
		return "", fmt.Errorf("failed to encrypt paseto token: %w", err)
	}

	return token, nil
}

// VerifyAndDecrypt расшифровывает и валидирует claims
func (m *TokenManager) VerifyAndDecrypt(tokenString string) (*AppSessionClaims, error) {
	var claims AppSessionClaims
	var footer string

	// Decrypt расшифровывает данные и проверяет целостность полинома Poly1305
	err := m.pasetoV2.Decrypt(tokenString, m.symmetricKey, &claims, &footer)
	if err != nil {
		return nil, fmt.Errorf("invalid or tampered paseto token: %w", err)
	}

	// Проверяем срок действия токена (Expiration check)
	if time.Now().After(claims.ExpiresAt) {
		return nil, fmt.Errorf("token expired at %s", claims.ExpiresAt)
	}

	return &claims, nil
}

func main() {
	// Генерируем 256-битный секретный ключ шифрования (32 байта)
	secretKey := make([]byte, 32)
	if _, err := rand.Read(secretKey); err != nil {
		panic(err)
	}

	manager, err := NewTokenManager(secretKey)
	if err != nil {
		panic(err)
	}

	fmt.Println("=== Генерация токена PASETO (v2/v4.local) ===")
	token, err := manager.GenerateToken("usr_9981", "senior_dev", "lead@company.tech", 15*time.Minute)
	if err != nil {
		panic(err)
	}

	fmt.Printf("PASETO Token:\n%s\n\n", token)
	fmt.Printf("Префикс версии и назначения: %s...\n", token[:8])
	fmt.Println("(Обратите внимание: в отличие от JWT, полезная нагрузка ПОЛНОСТЬЮ зашифрована!)")

	// Проверка и расшифровка
	claims, err := manager.VerifyAndDecrypt(token)
	if err != nil {
		panic(err)
	}

	fmt.Printf("\nУспешная авторизация по токену:\n")
	fmt.Printf("User ID: %s\nRole:    %s\nEmail:   %s\nExp:     %s\n",
		claims.UserID, claims.Role, claims.Email, claims.ExpiresAt.Format(time.RFC3339))
}
```

## Под капотом

Формат токена PASETO строго стандартизирован: `version.purpose.payload(.footer)`.
Для `local` токенов:
1. Версия 2 использует: ChaCha20-Poly1305 + HKDF-HMAC-SHA384.
2. Версия 4 использует: XChaCha20-Poly1305 (24-байтный nonce, исключающий коллизии) + BLAKE2b.
В начале полезной нагрузки упакован случайный криптографический Nonce. Затем выполняется аутентифицированное шифрование (AEAD). Пакет проверяет подлинность заголовка `version.purpose` как дополнительных аутентифицированных данных (AAD), исключая любую возможность подмены контекста.

## Подводные камни

1. **Использование одного ключа для `local` и `public`:** Для `v4.local` требуется 32-байтный симметричный секрет, а для `v4.public` — пара асимметричных ключей Ed25519 (Private/Public). Их смешивание приведет к ошибкам валидации.
2. **Хранение токенов в LocalStorage браузера:** Как и JWT, токены PASETO нельзя сохранять в `window.localStorage` из-за угрозы кражи через XSS. Рекомендуется использовать защищенные cookies с флагами `HttpOnly; Secure; SameSite=Strict`.
3. **Игнорирование проверки Expiration:** Библиотека проверяет криптографическую целостность, но проверка `time.Now().After(exp)` должна выполняться явно в обработчике claims.

## На собеседовании

**Вопрос с собеседования в Яндекс/Касперский:** «Почему архитекторы безопасности рекомендуют переходить с JWT на PASETO в современных распределенных микросервисах?»
**Ответ:** JWT содержит критические архитектурные изъяны спецификации JOSE: он позволяет клиенту диктовать серверу используемый алгоритм шифрования/подписи в открытом заголовке `alg`, что привело к историческим уязвимостям `"none"`, Algorithm Confusion (HMAC vs RSA) и некорректным реализациям парсеров. PASETO спроектирован по принципу «No Cipher Agility»: в нем нет выбора алгоритма. Версия жестко определяет безопасные современные примитивы (XChaCha20-Poly1305 / Ed25519). Кроме того, `v4.local` шифрует payload, предотвращая утечку внутренних данных архитектуры (ID, email, roles) третьим лицам.
