# Стратегия безопасной миграции паролей (Transparent Re-hashing)

## Условие

Реализуйте transparent rehashing: при успешном логине, если хэш в слабом формате (MD5/sha256/bcrypt cost<10), пересоздайте его в Argon2id.

### Исходная формулировка

**Password migration strategy**: Реализуйте transparent rehashing: при успешном логине, если хэш в слабом формате (MD5/sha256/bcrypt cost<10), пересоздайте его в Argon2id.

## Теория

В процессе эволюции корпоративных бэкенд-систем неизбежно возникает необходимость обновления криптографических стандартов: переход от старых быстрых хэшей (MD5, SHA-1, SHA-256) или слабых настроек (bcrypt cost < 10) к современному стойкому стандарту **Argon2id**.

Массово перехешировать пароли в базе данных невозможно, поскольку хэш-функции необратимы, а открытые пароли пользователей бэкенд не знает и не хранит. Принудительный сброс паролей (Password Reset) вызывает отток клиентов и перегрузку службы поддержки.

### Архитектурный паттерн: Transparent Re-hashing (Прозрачная миграция)
1. **Идентификация формата хэша:** При запросе логина система определяет алгоритм сохраненного хэша по префиксу или сигнатуре (например, префикс `$argon2id$` — современный, `$2a$` или `$2b$` — bcrypt, `$sha256$` — SHA-256 с солью, 32-символьный hex — старый MD5).
2. **Проверка подлинности:** Пароль верифицируется с использованием старого (legacy) алгоритма. Если пароль неверен — возвращается ошибка аутентификации.
3. **Бесшовное обновление (Re-hash):** Если пароль верен, бэкенд прямо в памяти берет открытый пароль из текущего запроса, вычисляет новый стойкий хэш **Argon2id** и сохраняет его в БД вместо устаревшего.
4. По мере регулярных входов пользователей база данных органически и без простоев мигрирует на Argon2id.

## Решение по шагам

1. Создадим интерфейс хранилища пользователей с эмуляцией базы данных.
2. Поддержим несколько типов хэшей: Legacy MD5, Legacy Bcrypt (cost=8) и современный Argon2id PHC.
3. Реализуем функцию `AuthenticateAndMigrate(username, password) (bool, error)`.
4. Внутри функции определим тип хэша: если тип устарел, проверим старым алгоритмом, затем вычислим Argon2id и обновим запись в БД.
5. Продемонстрируем, как после первого входа пользователя его устаревший хэш автоматически заменяется на Argon2id.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/md5"
	"crypto/rand"
	"crypto/subtle"
	"encoding/base64"
	"encoding/hex"
	"fmt"
	"io"
	"strings"

	"golang.org/x/crypto/argon2"
	"golang.org/x/crypto/bcrypt"
)

type UserRecord struct {
	Username     string
	PasswordHash string
}

// UserStore эмулирует таблицу базы данных
type UserStore struct {
	users map[string]*UserRecord
}

// HashArgon2id хэширует пароль в формат PHC
func HashArgon2id(password string) (string, error) {
	salt := make([]byte, 16)
	if _, err := io.ReadFull(rand.Reader, salt); err != nil {
		return "", err
	}
	hash := argon2.IDKey([]byte(password), salt, 3, 64*1024, 4, 32)
	b64Salt := base64.RawStdEncoding.EncodeToString(salt)
	b64Hash := base64.RawStdEncoding.EncodeToString(hash)
	return fmt.Sprintf("$argon2id$v=%d$m=%d,t=%d,p=%d$%s$%s", argon2.Version, 64*1024, 3, 4, b64Salt, b64Hash), nil
}

// VerifyArgon2id верифицирует хэш формата PHC
func VerifyArgon2id(password, phcHash string) bool {
	parts := strings.Split(phcHash, "$")
	if len(parts) != 6 || parts[1] != "argon2id" {
		return false
	}
	var m, t uint32
	var p uint8
	_, _ = fmt.Sscanf(parts[3], "m=%d,t=%d,p=%d", &m, &t, &p)
	salt, _ := base64.RawStdEncoding.DecodeString(parts[4])
	expectedHash, _ := base64.RawStdEncoding.DecodeString(parts[5])

	computed := argon2.IDKey([]byte(password), salt, t, m, p, uint32(len(expectedHash)))
	return subtle.ConstantTimeCompare(computed, expectedHash) == 1
}

// AuthenticateAndMigrate выполняет прозрачную миграцию на Argon2id при успешном логине
func (s *UserStore) AuthenticateAndMigrate(username, password string) (bool, error) {
	user, exists := s.users[username]
	if !exists {
		return false, fmt.Errorf("user not found")
	}

	currentHash := user.PasswordHash
	isAuthenticated := false
	needsUpgrade := false

	switch {
	case strings.HasPrefix(currentHash, "$argon2id$"):
		// Уже актуальный Argon2id
		isAuthenticated = VerifyArgon2id(password, currentHash)
		needsUpgrade = false

	case strings.HasPrefix(currentHash, "$2a$") || strings.HasPrefix(currentHash, "$2b$"):
		// bcrypt: проверяем, если cost < 12 — помечаем для апгрейда
		err := bcrypt.CompareHashAndPassword([]byte(currentHash), []byte(password))
		isAuthenticated = (err == nil)
		cost, _ := bcrypt.Cost([]byte(currentHash))
		if cost < 12 {
			needsUpgrade = true
		}

	case strings.HasPrefix(currentHash, "md5:"):
		// Устаревший MD5
		legacyHash := strings.TrimPrefix(currentHash, "md5:")
		md5Sum := md5.Sum([]byte(password))
		md5Hex := hex.EncodeToString(md5Sum[:])
		isAuthenticated = (subtle.ConstantTimeCompare([]byte(md5Hex), []byte(legacyHash)) == 1)
		needsUpgrade = true

	default:
		return false, fmt.Errorf("unsupported hash scheme")
	}

	if !isAuthenticated {
		return false, nil // Неверный пароль
	}

	// Если аутентификация успешна и хэш устарел — прозрачно перехешируем!
	if needsUpgrade {
		newHash, err := HashArgon2id(password)
		if err != nil {
			return true, fmt.Errorf("auth success, but failed to upgrade hash: %w", err)
		}
		user.PasswordHash = newHash
		fmt.Printf("[MIGRATION] Пароль пользователя '%s' успешно мигрирован на Argon2id!\n", username)
	}

	return true, nil
}

func main() {
	// Инициализируем БД со старыми и новыми учетными записями
	legacyMD5 := md5.Sum([]byte("Secret123!"))
	weakBcrypt, _ := bcrypt.GenerateFromPassword([]byte("Secret123!"), 6) // слабый cost 6

	store := &UserStore{
		users: map[string]*UserRecord{
			"alice_legacy_md5":    {Username: "alice", PasswordHash: "md5:" + hex.EncodeToString(legacyMD5[:])},
			"bob_weak_bcrypt":     {Username: "bob", PasswordHash: string(weakBcrypt)},
			"charlie_modern_user": {Username: "charlie"},
		},
	}
	modernHash, _ := HashArgon2id("Secret123!")
	store.users["charlie_modern_user"].PasswordHash = modernHash

	fmt.Println("=== 1. Первый логин Alice (MD5 -> Argon2id) ===")
	fmt.Printf("Хэш до логина: %s\n", store.users["alice_legacy_md5"].PasswordHash)
	ok, _ := store.AuthenticateAndMigrate("alice_legacy_md5", "Secret123!")
	fmt.Printf("Логин успешен: %t\n", ok)
	fmt.Printf("Хэш после логина: %s\n\n", store.users["alice_legacy_md5"].PasswordHash)

	fmt.Println("=== 2. Первый логин Bob (bcrypt cost 6 -> Argon2id) ===")
	fmt.Printf("Хэш до логина: %s\n", store.users["bob_weak_bcrypt"].PasswordHash)
	ok, _ = store.AuthenticateAndMigrate("bob_weak_bcrypt", "Secret123!")
	fmt.Printf("Логин успешен: %t\n", ok)
	fmt.Printf("Хэш после логина: %s\n\n", store.users["bob_weak_bcrypt"].PasswordHash)

	fmt.Println("=== 3. Повторный логин Alice (уже работает по нативному Argon2id) ===")
	ok, _ = store.AuthenticateAndMigrate("alice_legacy_md5", "Secret123!")
	fmt.Printf("Повторный логин Alice: %t\n", ok)
}
```

## Под капотом

С точки зрения базы данных операция обновления хэша должна выполняться атомарно. Если обновление упадет по таймауту базы данных, транзакция откатится, но сам логин пользователя не должен прерываться (пользователь успешно авторизован, а миграция повторится при следующем входе). 
Рекомендуется выполнять сохранение нового хэша либо в той же транзакции сессии, либо через фоновую горутину с контекстом `context.WithoutCancel(ctx)`.

## Подводные камни

1. **Блокировка ответа пользователю при сбое БД:** Если операция `UPDATE users SET password_hash = ...` упадет, нельзя возвращать пользователю статус `401 Unauthorized` или `500 Internal Server Error`, если его введенный пароль был верным! Залогиньте ошибку в Sentry/ELK и впустите пользователя.
2. **Множественные параллельные логины:** Если пользователь залогинился одновременно с двух вкладок браузера, две горутины могут попытаться обновить хэш параллельно. База данных должна корректно разруливать UPDATE через оптимистичную блокировку или стандартные row-level locks.
3. **«Мертвые души»:** Пользователи, которые не заходили годами, никогда не мигрируют сами. Для них спустя дедлайн (например, 1 год) на уровне компании объявляется обязательная процедура Password Reset по email.

## На собеседовании

**Вопрос с собеседования в Wildberries/Ozon:** «Как без даунтайма и сброса паролей перевести 50 миллионов пользователей со старого SHA-1/MD5 на Argon2id?»
**Ответ:** Применяется паттерн **Transparent Re-hashing**:
1. В микросервисе аутентификации реализуется распознавание формата сохраненного хэша.
2. При входе пользователя проверяется старый хэш (SHA-1/MD5). В случае успеха из памяти берется пароль в чистом виде, хэшируется новым алгоритмом Argon2id и асинхронно обновляется в БД.
3. В течение 6–12 месяцев 80–90% активной аудитории перейдет на Argon2id без малейшего влияния на пользовательский опыт.
4. Для оставшихся неактивных аккаунтов по истечении срока внедряется флаг `must_reset_password = true`, требующий подтверждения через почту или СМС.
