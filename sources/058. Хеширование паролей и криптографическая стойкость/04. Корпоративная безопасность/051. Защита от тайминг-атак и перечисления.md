# Защита от тайминг-атак и перечисления пользователей в bcrypt

## Условие

Используйте постоянную стоимость сравнения. Покажите, как разница во времени успешного/неуспешного логина может раскрыть информацию.

### Исходная формулировка

**Bcrypt timing attack protection**: Используйте постоянную стоимость сравнения. Покажите, как разница во времени успешного/неуспешного логина может раскрыть информацию.

## Теория

Одна из самых распространенных уязвимостей в API аутентификации — **утечка факта существования пользователя через замеры времени (Timing Attack / User Enumeration)**:

### Механика уязвимости в наивном коде:
```go
user, err := db.FindUser(email)
if err != nil {
    // Пользователя нет: возвращаем 401 Unauthorized МГНОВЕННО (за 0.5 мс)
    return ErrUnauthorized
}
// Пользователь существует: вычисляем тяжелый bcrypt (занимает ~150 мс)
if err := bcrypt.CompareHashAndPassword(user.Hash, password); err != nil {
    return ErrUnauthorized
}
```
Атакующий отправляет 1000 запросов со списком email-адресов сотрудников компании:
- Если ответ приходит за **0.5 мс**, пользователя с таким email **нет в системе**.
- Если ответ приходит за **150 мс**, пользователь **существует**, но пароль неверен!
Таким образом, злоумышленник с легкостью составляет список валидных корпоративных аккаунтов для целенаправленного фишинга и подбора (Password Spraying).

### Архитектурное решение: Dummy Hash Evaluation
Если пользователь не найден в базе данных, сервер **не должен немедленно возвращать ошибку**. Вместо этого сервер обязан выполнить фиктивное вычисление `bcrypt.CompareHashAndPassword` с заранее сгенерированным фейковым хэшем той же сложности (dummy hash). Время ответа для существующего и несуществующего пользователя становится **строго одинаковым**.

## Решение по шагам

1. Сгенерируем при старте сервиса константный `dummyHash` с рабочим фактором `bcrypt.DefaultCost`.
2. Реализуем наивный метод входа `NaiveLogin` и замерим разницу времени между существующим и несуществующим пользователем.
3. Разработаем защищенный метод `SecureLogin`: если пользователь не найден, выполняем сравнение с `dummyHash`.
4. Замерим время ответа в защищенном методе и убедимся, что задержка одинакова (~100–150 мс) в обоих сценариях.
5. Выведем сравнительную таблицу дельты времени.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"

	"golang.org/x/crypto/bcrypt"
)

type AuthService struct {
	users     map[string]string // email -> bcrypt hash
	dummyHash []byte            // Фейковый хэш для выравнивания тайминга
}

func NewAuthService() *AuthService {
	// Предварительно генерируем dummy-хэш с той же сложностью
	dummy, err := bcrypt.GenerateFromPassword([]byte("dummy_fallback_password"), bcrypt.DefaultCost)
	if err != nil {
		panic(err)
	}

	validHash, _ := bcrypt.GenerateFromPassword([]byte("RealUserSecretPass!"), bcrypt.DefaultCost)

	return &AuthService{
		users: map[string]string{
			"victim@company.ru": string(validHash),
		},
		dummyHash: dummy,
	}
}

// NaiveLogin уязвим к User Enumeration через замер времени
func (s *AuthService) NaiveLogin(email, password string) (bool, time.Duration) {
	start := time.Now()
	hash, exists := s.users[email]
	if !exists {
		// Ранний возврат: занимает доли миллисекунды!
		return false, time.Since(start)
	}

	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil, time.Since(start)
}

// SecureLogin защищен: время одинаково независимо от существования пользователя
func (s *AuthService) SecureLogin(email, password string) (bool, time.Duration) {
	start := time.Now()
	hash, exists := s.users[email]

	targetHash := s.dummyHash
	if exists {
		targetHash = []byte(hash)
	}

	// Bcrypt вычисляется ВСЕГДА: и для существующего, и для несуществующего юзера!
	err := bcrypt.CompareHashAndPassword(targetHash, []byte(password))

	// Возвращаем true только если юзер реально существовал и пароль совпал
	authenticated := exists && (err == nil)

	return authenticated, time.Since(start)
}

func main() {
	svc := NewAuthService()

	fmt.Println("=== 1. Уязвимый вход (NaiveLogin): утечка через тайминг ===")
	_, durNaiveNonExisting := svc.NaiveLogin("nobody@company.ru", "guess123")
	_, durNaiveExisting := svc.NaiveLogin("victim@company.ru", "wrongpass")

	fmt.Printf("Несуществующий email: %10s (БД вернула miss)\n", durNaiveNonExisting)
	fmt.Printf("Существующий email:    %10s (bcrypt работал)\n", durNaiveExisting)
	fmt.Printf("Разница во времени:   %10.2f раз! Атакующий вычислил жертву!\n\n",
		float64(durNaiveExisting)/float64(durNaiveNonExisting))

	fmt.Println("=== 2. Защищенный вход (SecureLogin): Dummy Hash выравнивание ===")
	_, durSecureNonExisting := svc.SecureLogin("nobody@company.ru", "guess123")
	_, durSecureExisting := svc.SecureLogin("victim@company.ru", "wrongpass")

	fmt.Printf("Несуществующий email: %10s (dummy bcrypt работал)\n", durSecureNonExisting)
	fmt.Printf("Существующий email:    %10s (real bcrypt работал)\n", durSecureExisting)

	diff := durSecureExisting - durSecureNonExisting
	if diff < 0 {
		diff = -diff
	}
	fmt.Printf("Абсолютная разница:   %10s (Тайминг неотличим от сетевого шума)\n", diff)
}
```

## Под капотом

В микросекундном диапазоне разница между 40 микросекундами и 70 миллисекундами составляет более трех порядков величины (\(>1500\times\)). Даже при наличии сетевого джиттера в Интернете статистический анализ медианного времени по 5–10 запросам позволяет атакующему с вероятностью 99.9% определить наличие пользователя в базе данных.
Вызов `bcrypt.CompareHashAndPassword` с `dummyHash` принудительно тратит ровно \(2^{\text{cost}}\) итераций шифра Blowfish, нивелируя дельту до статистической погрешности.

## Подводные камни

1. **Генерация нового Dummy-хэша на лету:** Если вызывать `bcrypt.GenerateFromPassword` внутри каждого запроса отсутствующего юзера, время удвоится (генерация + сравнение займут 300 мс вместо 150 мс), что снова выдаст сервер! Dummy-хэш обязан генерироваться один раз при инициализации сервиса.
2. **Утечка через текст ошибки:** Если сервер возвращает "Пользователь не найден" вместо общего "Неверный логин или пароль", выравнивание тайминга бесполезно. Сообщение об ошибке обязано быть единым.
3. **Разница в статусах HTTP:** Не возвращайте `404 Not Found` для отсутствующего юзера и `401 Unauthorized` для неверного пароля. Всегда возвращайте единый HTTP-код `401 Unauthorized`.

## На собеседовании

**Вопрос с собеседования в Касперский/Яндекс:** «Как злоумышленник может определить список зарегистрированных пользователей сервиса, если форма логина возвращает одинаковую ошибку "Invalid credentials"? Как предотвратить эту атаку в Go?»
**Ответ:** Через **Side-Channel Timing Attack (атаку по времени отклика)**:
Если пользователь не зарегистрирован, наивный код завершает обработку сразу после чтения из БД (за доли миллисекунды). Если пользователь есть, вызывается ресурсоемкая функция `bcrypt` или `Argon2id` (занимает ~100–300 мс). Злоумышленник замеряет латентность HTTP-ответов и вычисляет существующие аккаунты.
Для предотвращения применяется фиктивное вычисление: при промахе в БД запускается проверка пароля против предварительно рассчитанного эталонного `dummyHash` с тем же фактором сложности. Это делает латентность одинаковой для всех запросов.
