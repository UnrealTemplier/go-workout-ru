# Механизм ротации ключей подписи (Key Rotation)

## Условие

Реализуйте в вашей системе авторизации на базе PASETO/JWT механизм ротации ключей. Сервер должен хранить список активных ключей подписи. Новые токены должны подписываться самым свежим (актуальным) ключом, однако при проверке входящих токенов система должна успешно принимать токены, подписанные старыми ключами, если их время жизни (TTL) еще не истекло.

### Исходная формулировка

Новые токены должны подписываться самым свежим (актуальным) ключом, однако при проверке входящих токенов система должна успешно принимать токены, подписанные старыми ключами, если их время жизни (TTL) еще не истекло.

## Теория

Периодическая смена криптографических ключей (**Key Rotation**) — фундаментальное требование информационной безопасности (NIST SP 800-57, ISO 27001, PCI-DSS).

Если сервер использует один постоянный статический ключ подписи токенов:
1. Компрометация ключа позволяет злоумышленнику бессрочно подделывать токены любых пользователей до ручной перенастройки всей инфраструктуры.
2. Внезапная смена ключа мгновенно разлогинивает миллионы активных пользователей, вызывая шквал повторных запросов аутентификации.

### Архитектура Graceful Key Rotation (Кольцо ключей):
- Каждому ключу присваивается уникальный идентификатор: **Key ID (`kid`)**.
- Сервер хранит **Key Ring (набор ключей)**:
  1. **Primary Key (Актуальный):** Используется для создания всех **новых** токенов.
  2. **Retired Keys (Устаревающие / Grace Period):** Старые ключи, которые больше **не используются для выпуска**, но продолжают приниматься при проверке входящих токенов до тех пор, пока не истечет максимальный TTL ранее выданных токенов (например, 24 часа).
  3. **Revoked Keys (Отозванные):** Ключи, удаленные из кольца при компрометации.

## Решение по шагам

1. Создадим структуру `KeyRecord` с полями ID, SecretKey, CreatedAt, IsActive.
2. Разработаем менеджер ключей `KeyRing`, поддерживающий регистрацию новых ключей и назначение первичного (Primary).
3. При генерации токена упакуем `kid` в футер PASETO или заголовок токена.
4. При верификации токена извлечем `kid`, найдем соответствующий ключ в кольце и выполним проверку.
5. Продемонстрируем успешную проверку старого токена после ротации ключа на новый.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/json"
	"fmt"
	"sync"
	"time"

	"github.com/o1egl/paseto"
)

type TokenFooter struct {
	KeyID string `json:"kid"`
}

type KeyRecord struct {
	ID        string
	Key       []byte
	CreatedAt time.Time
}

// RotatableKeyRing управляет пулом версионированных ключей
type RotatableKeyRing struct {
	mu         sync.RWMutex
	primaryKID string
	keys       map[string]*KeyRecord
	pasetoV2   *paseto.V2
}

func NewRotatableKeyRing() *RotatableKeyRing {
	return &RotatableKeyRing{
		keys:     make(map[string]*KeyRecord),
		pasetoV2: paseto.NewV2(),
	}
}

// RotateToNewKey добавляет новый свежий ключ и делает его основным для выпуска токенов
func (r *RotatableKeyRing) RotateToNewKey(kid string) error {
	newSecret := make([]byte, 32)
	if _, err := rand.Read(newSecret); err != nil {
		return err
	}

	r.mu.Lock()
	defer r.mu.Unlock()

	r.keys[kid] = &KeyRecord{
		ID:        kid,
		Key:       newSecret,
		CreatedAt: time.Now(),
	}
	r.primaryKID = kid
	fmt.Printf("[KEY-ROTATION] Успешная ротация! Новый Primary Key ID: %s\n", kid)
	return nil
}

// IssueToken подписывает токен самым свежим Primary-ключом
func (r *RotatableKeyRing) IssueToken(payload map[string]string) (string, error) {
	r.mu.RLock()
	primaryID := r.primaryKID
	record, exists := r.keys[primaryID]
	r.mu.RUnlock()

	if !exists {
		return "", fmt.Errorf("no primary key configured")
	}

	footer := TokenFooter{KeyID: primaryID}
	footerBytes, _ := json.Marshal(footer)

	// Шифруем токен, сохраняя kid в открытом, но защищенном футере
	token, err := r.pasetoV2.Encrypt(record.Key, payload, string(footerBytes))
	if err != nil {
		return "", err
	}

	return token, nil
}

// VerifyToken находит правильный ключ по kid из футера и валидирует токен
func (r *RotatableKeyRing) VerifyToken(tokenString string) (map[string]string, error) {
	var footerRaw string
	// В PASETO v2 footer можно извлечь и прочитать до дешифрования
	var footer TokenFooter
	var payload map[string]string

	// Быстро считываем footer без проверки для поиска kid
	footerJSON, err := paseto.NewV2().GetFooter(tokenString)
	if err != nil {
		return nil, fmt.Errorf("failed to read token footer: %w", err)
	}

	if err := json.Unmarshal([]byte(footerJSON), &footer); err != nil {
		return nil, fmt.Errorf("invalid footer json: %w", err)
	}

	r.mu.RLock()
	keyRecord, exists := r.keys[footer.KeyID]
	r.mu.RUnlock()

	if !exists {
		return nil, fmt.Errorf("unknown or expired key ID: %s", footer.KeyID)
	}

	// Расшифровываем ключом, соответствующим указанному kid
	err = r.pasetoV2.Decrypt(tokenString, keyRecord.Key, &payload, &footerRaw)
	if err != nil {
		return nil, fmt.Errorf("signature/decryption failed for kid %s: %w", footer.KeyID, err)
	}

	return payload, nil
}

func main() {
	ring := NewRotatableKeyRing()

	// 1. Начальная эпоха ключей: активен ключ 'key-2026-v1'
	_ = ring.RotateToNewKey("key-2026-v1")

	oldToken, err := ring.IssueToken(map[string]string{"user": "alice", "sub": "1001"})
	if err != nil {
		panic(err)
	}
	fmt.Printf("Токен Alice (выпущен на key-2026-v1):\n%s\n\n", oldToken)

	// 2. Наступает плановая ротация ключей (Graceful Rotation)
	// Сервер переключается на 'key-2026-v2'
	_ = ring.RotateToNewKey("key-2026-v2")

	newToken, err := ring.IssueToken(map[string]string{"user": "bob", "sub": "1002"})
	if err != nil {
		panic(err)
	}
	fmt.Printf("Токен Bob (выпущен на НОВОМ key-2026-v2):\n%s\n\n", newToken)

	// 3. Проверка: система должна бесшовно валидировать ОБА токена!
	claimsOld, err := ring.VerifyToken(oldToken)
	fmt.Printf("Валидация старого токена Alice: %v (User: %s, Ошибка: %v)\n",
		err == nil, claimsOld["user"], err)

	claimsNew, err := ring.VerifyToken(newToken)
	fmt.Printf("Валидация нового токена Bob:    %v (User: %s, Ошибка: %v)\n",
		err == nil, claimsNew["user"], err)
}
```

## Под капотом

В распределенных микросервисах набор публичных ключей публикуется через эндпоинт JWKS (`/.well-known/jwks.json`). 
Менеджер ключей обновляет кэш JWKS в памяти по расписанию или по требованию, если получен неизвестный `kid`. Использование мьютекса `sync.RWMutex` предотвращает гонки данных при фоновом добавлении новых ключей ротации.

## Подводные камни

1. **Немедленное удаление старого ключа:** Если при ротации сразу удалить предыдущий ключ, все выданные ранее токены пользователей мгновенно перестанут работать. Старый ключ обязан жить в пуле не менее `MaxTokenTTL` (например, 24–48 часов).
2. **Незащищенный `kid` (SQL-инъекция в хранилище ключей):** Если `kid` используется для динамического поиска ключа в базе данных, злоумышленник может внедрить SQL-инъекцию в `kid`. Всегда валидируйте формат `kid` (только алфавитно-цифровые символы и дефисы).
3. **Отсутствие лимита на размер KeyRing:** Не храните ключи пятилетней давности. Автоматический сборщик (cleaner) должен удалять ключи старше `MaxTokenTTL + gracePeriod`.

## На собеседовании

**Вопрос с собеседования в Авито/VK:** «Как организовать бессбойную ротацию секретных ключей подписи токенов в кластере из 100 микросервисов?»
**Ответ:** 
1. Использовать идентификатор ключа `kid` в заголовке токена.
2. Применять схему с асимметричной криптографией (Ed25519 или RSA): Auth-сервис подписывает приватным ключом, а все 100 сервисов скачивают публичные ключи через эндпоинт JWKS (`/.well-known/jwks.json`) и кэшируют их в памяти.
3. При плановой ротации создается новая пара ключей `kid_2`, которая заранее добавляется в JWKS.
4. Спустя время распространения кэша Auth-сервис начинает подписывать новые токены ключом `kid_2`. Старый ключ `kid_1` остается в JWKS на время жизни токена (TTL), гарантируя отсутствие разлогинов.
