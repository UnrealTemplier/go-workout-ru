# Затирание секретов в оперативной памяти (Zeroing Memory)

## Условие

Переменные типа string в Go неизменяемы, поэтому при обработке пароля или секретного ключа они могут надолго зависнуть в оперативной памяти (в куче) до запуска GC, что позволит злоумышленнику считать их из дампа памяти (heap dump) [554]. Напишите код: принимайте пароли в виде среза байт []byte. После того как пароль проверен, принудительно затрите этот срез байт нулями во всей выделенной под него памяти с помощью функции copy или ручного обнуления элементов в цикле [554].

### Исходная формулировка

**Затирание секретов в оперативной памяти**: Переменные типа `string` в Go неизменяемы, поэтому при обработке пароля или секретного ключа они могут надолго зависнуть в оперативной памяти (в куче) до запуска GC, что позволит злоумышленнику считать их из дампа памяти (heap dump) [554]. Напишите код: принимайте пароли в виде среза байт `[]byte`. После того как пароль проверен, принудительно затрите этот срез байт нулями во всей выделенной под него памяти с помощью функции `copy` или ручного обнуления элементов в цикле [554].

## Теория

В языке Go тип данных `string` является **неизменяемым (immutable)**. Любая операция конкатенации или создания строки аллоцирует массив байт в памяти кучи (heap). Поскольку изменить строку нельзя:
- Открытый пароль или приватный ключ остается в оперативной памяти до тех пор, пока сборщик мусора (GC) не освободит страницу, а операционная система не перевыделит её под другие нужды.
- При аварийном завершении сервиса (panic / SIGSEGV) ядро Linux может сбросить дамп памяти (**Core Dump / Heap Dump**) на диск.
- При атаках через соседние процессы (например, уязвимости Spectre/Meltdown, чтение `/proc/$PID/mem`) злоумышленник с повышенными правами может извлечь открытые секреты из памяти.

### Отраслевой стандарт DevSecOps: Zeroing Memory
1. Все чувствительные данные (пароли, seed-фразы, мастер-ключи шифрования) обязаны приниматься и обрабатываться исключительно в виде **изменяемого среза байт `[]byte`**, а не `string`!
2. Сразу после использования срез **принудительно затирается нулями**:
   ```go
   for i := range secretBytes { secretBytes[i] = 0 }
   ```
3. **Защита от оптимизатора компилятора (DCE — Dead Code Elimination):**
   Компилятор Go при агрессивной оптимизации (`-O2` / SSA pass) может заметить, что массив `secretBytes` больше нигде не читается после цикла зануления, и **полностью удалить цикл затирания из ассемблерного кода**!
   Чтобы гарантировать затирание, применяют `runtime.KeepAlive(secretBytes)` или барьеры памяти.

## Решение по шагам

1. Создадим защищенную структуру `SecureBuffer`, оборачивающую `[]byte`.
2. Реализуем метод `Destroy()`, зануляющий байты буфера.
3. Добавим защиту от удаления кода компилятором с помощью `runtime.KeepAlive`.
4. Продемонстрируем безопасную обработку пароля: чтение `[]byte`, вычисление хэша, немедленное зануление.
5. Убедимся, что после вызова `Destroy()` в памяти буфера не остается ни одного исходного символа.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/sha256"
	"fmt"
	"runtime"
)

// SecureBuffer инкапсулирует чувствительные данные в оперативной памяти
type SecureBuffer struct {
	data []byte
}

func NewSecureBuffer(secret []byte) *SecureBuffer {
	// Создаем изолированную копию среза
	buf := make([]byte, len(secret))
	copy(buf, secret)
	return &SecureBuffer{data: buf}
}

// Bytes возвращает срез данных
func (b *SecureBuffer) Bytes() []byte {
	return b.data
}

// Destroy принудительно затирает память нулями
func (b *SecureBuffer) Destroy() {
	if b.data == nil {
		return
	}

	// 1. Ручное обнуление всех байт среза
	for i := 0; i < len(b.data); i++ {
		b.data[i] = 0
	}

	// 2. Гарантия предотвращения Dead Code Elimination (DCE):
	// runtime.KeepAlive заставляет компилятор считать, что объект data
	// активно используется вплоть до этой точки, блокируя оптимизацию затирания.
	runtime.KeepAlive(b.data)

	b.data = nil
}

// ProcessPasswordSecurely демонстрирует безопасный цикл жизни пароля
func ProcessPasswordSecurely(rawSecret []byte) [32]byte {
	// Оборачиваем в защищенный буфер
	secBuf := NewSecureBuffer(rawSecret)
	// Немедленно затираем исходный входной буфер
	for i := range rawSecret {
		rawSecret[i] = 0
	}

	// defer гарантирует очистку памяти даже при возникновении паники!
	defer secBuf.Destroy()

	// Выполняем криптографическую операцию (например, хеширование)
	digest := sha256.Sum256(secBuf.Bytes())

	return digest
}

func main() {
	fmt.Println("=== Безопасная работа с секретами и затирание памяти (Zeroing) ===")

	// Пароль выделяется как []byte (НИ В КОЕМ СЛУЧАЕ НЕ string!)
	passwordBytes := []byte("SuperConfidentialMasterPassword#2026")

	fmt.Printf("Пароль в памяти ДО обработки:    '%s'\n", string(passwordBytes))

	// Запуск безопасной обработки
	digest := ProcessPasswordSecurely(passwordBytes)

	fmt.Printf("Пароль в памяти ПОСЛЕ затирания: '%s' (длина: %d, байты: %v)\n",
		string(passwordBytes), len(passwordBytes), passwordBytes[:8])
	fmt.Printf("Вычисленный дайджест:            %x\n", digest)

	// Дополнительный тест SecureBuffer
	standaloneBuf := NewSecureBuffer([]byte("PrivateKeyBytes12345"))
	fmt.Printf("\nStandalone буфер до Destroy:     '%s'\n", string(standaloneBuf.Bytes()))
	standaloneBuf.Destroy()
	fmt.Printf("Standalone буфер после Destroy:  nil (память очищена)\n")
}
```

## Под капотом

Компилятор Go (бэкенд SSA) выполняет оптимизацию удаления мертвого кода (Dead Code Elimination). Если переменная перезаписывается нулями непосредственно перед выходом из области видимости, оптимизатор может счесть эту запись избыточной и исключить процессорные инструкции `MOV` или `memset`.
Вызов `runtime.KeepAlive(b.data)` создает псевдо-использование ссылки, гарантируя, что все операции записи в массив `b.data` будут реально исполнены микропроцессором до точки вызова.

## Подводные камни

1. **Преобразование `string([]byte)`:** Вызов `s := string(passwordBytes)` создает в куче неизменяемую копию строки, которую невозможно затереть! Никогда не приводите секретные байты к `string`.
2. **Игнорирование системного вызова `mlock`:** В Linux страницы памяти могут быть сброшены на диск в раздел подкачки (`swap`). Для банковских и криптографических систем критические страницы блокируют в физической RAM через системный вызов `unix.Mlock`.
3. **Логирование структур с секретами:** Передача структуры с секретным срезом в `log.Printf("%+v", creds)` приведет к утечке секрета в ELK/stdout. Реализуйте интерфейс `fmt.Stringer` для сокрытия полей.

## На собеседовании

**Вопрос с собеседования в Касперский/Т-Банк:** «Почему для паролей и криптографических ключей в Go нельзя использовать тип `string`, и как компилятор может сломать функцию очистки памяти?»
**Ответ:** 
1. Строки в Go неизменяемы (`immutable`). При выделении строки данные попадают в кучу и не могут быть затерты разработчиком, оставаясь доступными в дампах памяти до непредсказуемого момента сборки мусора (GC). Секреты необходимо хранить в срезах `[]byte`.
2. При вызове цикла зануления `for i := range b { b[i] = 0 }` оптимизатор компилятора Go (pass Dead Code Elimination) может заметить, что срез `b` дальше не читается, и полностью вырезать цикл очистки из результирующего бинарника. Для предотвращения этого обязателен вызов `runtime.KeepAlive(b)` в конце процедуры очистки.
