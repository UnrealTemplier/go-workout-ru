# Концепция Fencing Token: защита от GC-пауз и задержек сети

### Исходная формулировка

**[Fencing Token — Концепция]**: Изучи проблему предыдущего задания. Решением являются Fencing Tokens. Каждый раз, когда блокировка берется, она возвращает монотонно возрастающий токен (Token 1, Token 2, ...).

## Теория

Фундаментальная статья Мартина Клеппмана (Martin Kleppmann) «How to do distributed locking» показала неустранимую уязвимость простых распределенных блокировок с временным сроком действия (Lease / TTL):

Представьте последовательность событий:
1. **Клиент 1** получает эксклюзивную блокировку на файл `storage.dat` в Redis с TTL 10 секунд.
2. Сразу после получения блокировки в рантайме Go Клиента 1 начинается длительная **STW GC-пауза** (или задержка paging памяти, гипервизора, vCPU steal time) длительностью 15 секунд.
3. Через 10 секунд координатор блокировок снимает ключ по TTL.
4. **Клиент 2** запрашивает блокировку на `storage.dat`, успешно ее получает и начинает модификацию данных.
5. Через 15 секунд Клиент 1 «просыпается». Локально его код не знает о прошедшем времени (или проверил таймер за миллисекунду до окончания паузы) и отправляет запрос на запись.
6. **Катастрофа Split-Brain:** Клиент 1 перезаписывает свежие изменения Клиента 2.

**Решение: Fencing Tokens (Ограждающие токены).**
Координатор блокировок при каждой успешной выдаче мьютекса выдает строго возрастающий числовой токен:
- Клиент 1 получает блокировку с токеном `33`.
- Клиент 2 получает блокировку с токеном `34`.
Целевое хранилище данных (Storage / Database) сохраняет максимальный увиденный токен (`max_token`). Когда зомби-Клиент 1 шлет операцию с токеном `33`, хранилище видит `33 < 34` и отклоняет операцию с ошибкой `StaleFencingTokenError`.

## Решение по шагам

1. Создайте структуру `LockServer` с потокобезопасным счетчиком `tokenCounter atomic.Uint64`.
2. Метод `AcquireLock(clientID)` инкрементирует счетчик и возвращает новый `FencingToken`.
3. Создайте структуру `StorageServer` с полем `highestToken uint64`.
4. Реализуйте метод хранилища `WriteData(key, value string, token uint64) error`.
5. Внутри `WriteData` проверьте: если `token < s.highestToken`, верните фатальную ошибку `ErrStaleToken`.
6. Если `token >= s.highestToken`, обновите `highestToken = token` и запишите данные.
7. Продемонстрируйте корректную защиту от устаревшей записи.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

var ErrStaleFencingToken = errors.New("storage: fencing token is stale, write rejected")

type LockServer struct {
	counter atomic.Uint64
}

func (ls *LockServer) AcquireLock(resource, clientID string) (uint64, error) {
	// Каждый захват блокировки возвращает монотонно возрастающее число
	token := ls.counter.Add(1)
	return token, nil
}

type StorageServer struct {
	mu           sync.Mutex
	data         map[string]string
	highestToken map[string]uint64
}

func NewStorageServer() *StorageServer {
	return &StorageServer{
		data:         make(map[string]string),
		highestToken: make(map[string]uint64),
	}
}

func (s *StorageServer) Write(key, value string, token uint64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	lastToken := s.highestToken[key]
	if token < lastToken {
		return fmt.Errorf("%w: token %d < highest %d", ErrStaleFencingToken, token, lastToken)
	}

	s.highestToken[key] = token
	s.data[key] = value
	return nil
}

func main() {
	lockServer := &LockServer{}
	storage := NewStorageServer()

	// 1. Клиент 1 получает блокировку
	tokenClient1, _ := lockServer.AcquireLock("doc-42", "client-1")
	fmt.Printf("[Client 1] Acquired lock with Fencing Token: %d\n", tokenClient1)

	// Симуляция: Клиент 1 засыпает в STW GC паузе
	fmt.Println("[Client 1] Frozen in GC pause...")

	// 2. Блокировка перехватывается Клиентом 2
	tokenClient2, _ := lockServer.AcquireLock("doc-42", "client-2")
	fmt.Printf("[Client 2] Acquired lock with Fencing Token: %d\n", tokenClient2)

	// Клиент 2 успешно записывает данные
	err := storage.Write("doc-42", "Version 2 by Client 2", tokenClient2)
	fmt.Printf("[Client 2] Write result: %v\n", err)

	// 3. Клиент 1 очнулся от паузы и пытается записать свои устаревшие данные
	fmt.Printf("[Client 1] Woke up! Attempting write with Token %d...\n", tokenClient1)
	err = storage.Write("doc-42", "Version 1 by Client 1 (Stale)", tokenClient1)
	if errors.Is(err, ErrStaleFencingToken) {
		fmt.Printf("[Client 1] SUCCESS: Storage safely blocked zombie write: %v\n", err)
	} else {
		fmt.Printf("[Client 1] FAILURE: Inconsistent state: %v\n", err)
	}

	time.Sleep(10 * time.Millisecond)
}
```

ℹ️ Симуляция отсечения зомби-записей через монотонный Fencing Token в хранилище

## Под капотом

Fencing Token переносит финальную точку синхронизации на уровень самого хранилища. Невозможно построить абсолютно безопасную распределенную блокировку только на стороне клиентов и сервера блокировок, если само конечное хранилище (БД, S3, файловая система) слепо принимает запись от любого клиента. Единственный способ математически защититься от асинхронных задержек в распределенной системе с моделью сбоев Crash-Recovery — обязать хранилище проверять номер версии (фенсинг-токен).

## Подводные камни

1. Использование timestamp вместо монотонного счетчика: NTP-синхронизация может давать скачки времени назад (clock leap), из-за чего токен окажется меньше предыдущего.
2. Неатомарная проверка токена в хранилище: проверка `token >= highest` и запись данных должны выполняться в единой транзакции.

## На собеседовании

«Почему Redlock в Redis критикуется за отсутствие встроенных Fencing Tokens?»
Ответ: Redis при команде `SET key val NX PX ttl` не генерирует автоматически монотонно возрастающий Sequence Number в ответе. Если клиент зависнет в GC-паузе, а затем пошлет команду в PostgreSQL или Redis без проверки версии, Redlock не спасет от повреждения данных. etcd и ZooKeeper решают это аппаратно: etcd возвращает `Header.Revision`, а ZooKeeper — `zxid` / `cversion`, которые естественным образом служат fencing-токенами.
