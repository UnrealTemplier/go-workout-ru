### Исходная формулировка

Покажите fair vs unfair: fair — FIFO очередь ожидания, unfair — первый кто успел. Объясните, почему Redis Redlock не подходит для fair semaphore.

## Теория

В отличие от мьютекса (Mutex), который предоставляет доступ строго одному процессу (N=1), **распределенный семафор (Distributed Semaphore)** ограничивает параллельный доступ к ресурсу фиксированным числом клиентов \(N > 1\) (например, не более 5 параллельных вызовов к внешнему банковскому API или тяжелой аналитической СУБД).

**Реализация в Redis через Sorted Set (ZSET):**
Ключ семафора — это ZSET, где элементами являются уникальные идентификаторы запросов клиентов, а оценкой (`score`) — Unix timestamp захвата в миллисекундах.
Алгоритм атомарного захвата через Lua:
1. **Очистка протухших слотов:** `redis.call('zremrangebyscore', key, '-inf', now - ttl)` удаляет клиентов, которые упали и не освободили слот.
2. **Проверка емкости:** `if redis.call('zcard', key) < limit then`.
3. **Захват слота:** `redis.call('zadd', key, now, request_id)`.

**Fair vs Unfair семафоры:**
- **Unfair (Несправедливый):** Клиенты просто конкурируют за освободившийся слот в цикле polling. Первый, кто послал запрос в момент освобождения слота, забирает его. Возможен эффект «голодания» (Starvation) клиентов с медленным сетевым каналом.
- **Fair (Справедливый):** Клиенты встают в очередь FIFO по времени прихода (например, через Redis List или упорядоченный ZSET с монотонным номером запроса). Доступ предоставляется строго в порядке очереди.

**Почему Redlock не подходит для Fair Semaphore?**
Алгоритм Redlock разработан исключительно для бинарного мьютекса на нескольких независимых несогласованных инстансах Redis (N Master). Redlock полагается на несинхронизированные локальные таймеры физических машин. Обеспечить строгую упорядоченность FIFO (Fair ordering) между несколькими независимыми серверами Redis без протокола распределенного консенсуса (Raft/Paxos) невозможно из-за асинхронных сдвигов часов (Clock Skew) и недетерминированного сетевого порядка сообщений.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// Имитация Redis ZSET и Lua-движка в памяти
type MockRedisZSet struct {
	mu     sync.Mutex
	scores map[string]int64 // member -> timestamp
}

func NewMockRedisZSet() *MockRedisZSet {
	return &MockRedisZSet{scores: make(map[string]int64)}
}

// Атомарная имитация Lua-скрипта захвата слота семафора
func (r *MockRedisZSet) EvalAcquire(nowMs int64, ttlMs int64, limit int, member string) bool {
	r.mu.Lock()
	defer r.mu.Unlock()

	// 1. Очистка старых слотов: ZREMRANGEBYSCORE key -inf (now - ttl)
	expireBoundary := nowMs - ttlMs
	for m, score := range r.scores {
		if score < expireBoundary {
			delete(r.scores, m)
		}
	}

	// 2. Проверка ZCARD
	if len(r.scores) < limit {
		// 3. Захват: ZADD key now member
		r.scores[member] = nowMs
		return true
	}
	return false
}

func (r *MockRedisZSet) EvalRelease(member string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	delete(r.scores, member)
}

type DistributedSemaphore struct {
	redis    *MockRedisZSet
	limit    int
	ttl      time.Duration
	activeCt atomic.Int32
}

func NewDistributedSemaphore(redis *MockRedisZSet, limit int, ttl time.Duration) *DistributedSemaphore {
	return &DistributedSemaphore{
		redis: redis,
		limit: limit,
		ttl:   ttl,
	}
}

func (s *DistributedSemaphore) Acquire(ctx context.Context) (string, error) {
	b := make([]byte, 8)
	rand.Read(b)
	memberID := hex.EncodeToString(b)

	ttlMs := s.ttl.Milliseconds()

	for {
		select {
		case <-ctx.Done():
			return "", ctx.Err()
		default:
		}

		nowMs := time.Now().UnixMilli()
		if s.redis.EvalAcquire(nowMs, ttlMs, s.limit, memberID) {
			s.activeCt.Add(1)
			return memberID, nil
		}

		// Backoff перед следующей попыткой
		time.Sleep(20 * time.Millisecond)
	}
}

func (s *DistributedSemaphore) Release(memberID string) {
	s.redis.EvalRelease(memberID)
	s.activeCt.Add(-1)
}

func main() {
	redisMock := NewMockRedisZSet()
	// Семафор разрешает не более 3 одновременных исполнителей
	sem := NewDistributedSemaphore(redisMock, 3, 2*time.Second)

	var maxConcurrent atomic.Int32
	var wg sync.WaitGroup
	numWorkers := 8

	wg.Add(numWorkers)
	for i := 1; i <= numWorkers; i++ {
		workerID := fmt.Sprintf("worker-%d", i)
		go func(id string) {
			defer wg.Done()
			ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
			defer cancel()

			member, err := sem.Acquire(ctx)
			if err != nil {
				fmt.Printf("[%s] Failed to acquire: %v\n", id, err)
				return
			}
			defer sem.Release(member)

			// Фиксация пика параллельности
			cur := sem.activeCt.Load()
			for {
				oldMax := maxConcurrent.Load()
				if cur <= oldMax || maxConcurrent.CompareAndSwap(oldMax, cur) {
					break
				}
			}

			fmt.Printf("[%s] Entered critical section (Active: %d)\n", id, cur)
			time.Sleep(100 * time.Millisecond) // полезная работа
			fmt.Printf("[%s] Leaving critical section\n", id)
		}(workerID)
	}

	wg.Wait()
	fmt.Printf("\nMax concurrent workers recorded in critical section: %d (Limit: 3)\n", maxConcurrent.Load())
	if maxConcurrent.Load() > 3 {
		panic("Semaphore limit exceeded!")
	}
	_ = errors.New("")
}
```

## Под капотом

Семафор на ZSET чувствителен к системному времени (System Time) клиентов Redis. Если часы на клиенте спешат, его `score` будет больше, и он будет удерживать слот дольше положенного TTL. Поэтому в продакшене в Redis Lua-скрипте рекомендуется вызывать команду `redis.call('TIME')`, используя время самого сервера Redis, а не клиента.

## Подводные камни

1. Отсутствие TTL очистки в ZSET: если упавший клиент занял слот и не вызвал Release, этот слот навсегда потерян (Semaphore Leaking).
2. Thundering Herd при освобождении: если 100 клиентов в цикле опрашивают Redis на предмет свободного слота, это создает шторм запросов. Рекомендуется использовать Redis Pub/Sub для оповещения об освобождении слота.

## На собеседовании

«Почему справедливый (Fair) семафор сложнее реализовать, чем обычный мьютекс?»
Ответ: В Fair семафоре недостаточно просто проверить счетчик `count < limit`. Требуется поддерживать строгую очередь ожидания (FIFO Queue). Если освободился 1 слот, его должен занять строго первый в очереди. Если клиенты просто пробуют захватить слот вперегонки (Unfair), клиент, пришедший последним, может перехватить слот у клиента, ожидавшего 10 минут.
