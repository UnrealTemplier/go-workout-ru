# Усиление Redlock монотонными токенами: генерация версий через Redis INCR

## Условие

39. **Проблема Redlock и Fencing Token.**: Продемонстрируйте сценарий, где долгая GC-пауза приводит к истечению блокировки, но клиент продолжает работу. Усилите безопасность, добавив монотонно возрастающий fencing token (версию) из Redis, который проверяется при записи в БД.

### Исходная формулировка

**Проблема Redlock и Fencing Token.**: Продемонстрируйте сценарий, где долгая GC-пауза приводит к истечению блокировки, но клиент продолжает работу. Усилите безопасность, добавив монотонно возрастающий fencing token (версию) из Redis, который проверяется на целевом сервисе перед модификацией данных.

## Теория

Гибридная архитектура: Redlock + Monotonic Redis Counter.

Чтобы компенсировать главный недостаток Redlock (уязвимость к паузам процессов и дрейфу часов), алгоритм дополняют **централизованным генератором монотонных версий**:
1. Клиент захватывает кворум Redlock на \(3/5\) узлов.
2. Внутри критической секции клиент атомарно запрашивает монотонный токен:
   ```text
   INCR fencing:counter:<resource>
   ```
3. Клиент передает полученный `token` в целевую базу данных:
   ```sql
   UPDATE documents
   SET body = :body, version = :token
   WHERE id = :id AND version < :token;
   ```
4. Если клиент засыпает на время, превышающее TTL, и второй клиент захватывает лок, второй клиент вызывает `INCR`, получая `token + 1`.
5. Запоздалая запись первого клиента гарантированно отклоняется базой данных.

Таким образом, Redlock обеспечивает **эффективность и мажоритарную доступность**, а Monotonic Token в связке с SQL Guard обеспечивает **абсолютную безопасность данных**.

## Решение по шагам

1. Создайте структуру `EnhancedRedlockService` с генератором монотонных версий.
2. Реализуйте метод `AcquireWithFencing(key, ttl)` возвращающий токен владения и монотонную версию.
3. Реализуйте базу данных с проверкой версии.
4. Смоделируйте случай, когда заснувший Воркер 1 пытается применить запись после того, как Воркер 2 применил более высокую версию.
5. Зафиксируйте успешную защиту целостности данных.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type EnhancedRedlock struct {
	mu           sync.Mutex
	activeHolder string
	exp          time.Time
	tokenCounter uint64
}

func NewEnhancedRedlock() *EnhancedRedlock {
	return &EnhancedRedlock{tokenCounter: 50}
}

func (r *EnhancedRedlock) AcquireWithFencing(worker string, ttl time.Duration) (uint64, bool) {
	r.mu.Lock()
	defer r.mu.Unlock()

	now := time.Now()
	if now.Before(r.exp) {
		return 0, false
	}

	// Redlock quorum acquired -> atomically increment monotonic fencing token!
	fencingToken := atomic.AddUint64(&r.tokenCounter, 1)
	r.activeHolder = worker
	r.exp = now.Add(ttl)

	fmt.Printf("[Enhanced Redlock] Worker '%s' acquired lock. Generated Fencing Version: %d\n",
		worker, fencingToken)
	return fencingToken, true
}

type ProtectedDocumentStore struct {
	mu          sync.Mutex
	content     string
	lastVersion uint64
}

func (s *ProtectedDocumentStore) SaveDocument(author, content string, version uint64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Strict Guard Condition
	if version <= s.lastVersion {
		return fmt.Errorf("stale write rejected for '%s': version %d <= last seen %d",
			author, version, s.lastVersion)
	}

	s.content = content
	s.lastVersion = version
	fmt.Printf("✅ Document saved by '%s'! Content: '%s' (Version: %d)\n", author, content, version)
	return nil
}

func main() {
	lockService := NewEnhancedRedlock()
	docStore := &ProtectedDocumentStore{content: "Initial v0", lastVersion: 50}
	var wg sync.WaitGroup

	// 1. Worker 1 acquires lock with short 100ms TTL
	token1, ok1 := lockService.AcquireWithFencing("Worker-1", 100*time.Millisecond)
	if !ok1 {
		panic("failed acquire")
	}

	// Worker 1 freezes...
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("[Worker-1] ⏸️ Frozen in long network/GC lag for 200ms...")
		time.Sleep(200 * time.Millisecond) // Exceeds 100ms TTL!

		fmt.Printf("[Worker-1] Resumed! Attempting write with Version %d...\n", token1)
		err := docStore.SaveDocument("Worker-1", "Data from Worker-1", token1)
		if err != nil {
			fmt.Printf("🛡️ Shielded against zombie write: %v\n", err)
		}
	}()

	// 2. Worker 2 steps in after 120ms (TTL expired)
	time.Sleep(120 * time.Millisecond)
	token2, ok2 := lockService.AcquireWithFencing("Worker-2", 100*time.Millisecond)
	if ok2 {
		_ = docStore.SaveDocument("Worker-2", "Data from Worker-2 (Fresh)", token2)
	}

	wg.Wait()

	fmt.Printf("\nFinal Document Content: '%s' (Protected by Version %d)\n",
		docStore.content, docStore.lastVersion)
}
```

ℹ️ Усиление Redlock атомарными инкрементными токенами для защиты целевой БД

## Под капотом

Где хранить счетчик `fencing:counter`:
Счетчик токенов в Redis хранится в персистентном ключе и никогда не удаляется при снятии блокировки. Команда `INCR` атомарна и гарантирует строго возрастающую последовательность \(1, 2, 3 \dots 2^{64}-1\). Даже если сам лок удаляется по TTL, счетчик версий продолжает расти, обеспечивая монотонность сквозь любые сбои и перезагрузки клиентов.

## Подводные камни

- **Сброс счетчика версий при рестарте**: Если Redis сбросит счетчик в 0 после перезагрузки, база данных начнет отклонять все запросы. Счетчик обязан персистироваться на диск (AOF) или храниться в PostgreSQL Sequence.
- **Пропуск валидации версий на чтении**: При оптимистичных блокировках версия должна сверяться и при чтении.

## На собеседовании

В Wildberries и Касперском на архитектурном собеседовании спрашивают: *«Является ли Redlock с добавлением генератора токенов полноценной заменой etcd/Raft?»*
**Ответ**: По надежности для сохранения данных в БД (Safety) — **да**, так как Fencing Token на стороне БД математически исключает порчу данных. Однако по сложности инфраструктуры Redlock требует поддержки 5 независимых инстансов Redis, пулов соединений и ручного управления токенами. etcd предоставляет все это из коробки (Raft + MVCC CreateRevision) в рамках единого готового продукта, поэтому в современной enterprise-архитектуре почти всегда выбирают **etcd**.
