# Защита от устаревших лидеров и воркеров: архитектура Fencing Tokens и предотвращение гонок

## Условие

35. **Fencing tokens защищают от stale leaders/workers.**: При получении leadership/lock генерируйте монотонно возрастающий token. Используйте его для защиты от race conditions.

### Исходная формулировка

**Fencing tokens защищают от stale leaders/workers.**: При получении leadership/lock генерируйте монотонно возрастающий token. Используйте его для защиты от race conditions.

## Теория

В распределенных системах узел, потерявший лидерство или право на блокировку, не узнает об этом мгновенно (проблема зомби-лидера / Stale Worker).

Почему локальные проверки не спасают:
Если узел проверяет `if isLeader { writeToStorage() }`, между проверкой `isLeader` и реальной отправкой пакета в хранилище может произойти сетевой разрыв, пауза GC или вытеснение потока ОС. За это время кластер выберет нового лидера, и старый лидер перезапишет данные.

Архитектура Fencing Tokens:
1. Каждая смена лидера или захват блокировки генерирует строго монотонное число: \(\text{Token}_{k+1} > \text{Token}_k\).
2. Целевое хранилище (PostgreSQL, Ceph, S3) ведет учет максимального примененного токена: `max_applied_token`.
3. Любая операция записи сопровождается токеном. Хранилище атомарно выполняет:
   ```sql
   UPDATE state SET val = :val, max_applied_token = :token
   WHERE id = :id AND max_applied_token < :token;
   ```
4. Если запрос пришел от смещенного старого лидера с \(\text{Token}_{old} \le \text{max_applied_token}\), хранилище отвергает запись, предотвращая повреждение данных.

## Решение по шагам

1. Создайте структуру координатора лидерства `LeaderCoordinator` с генератором монотонных эпох.
2. Реализуйте структуру защищенного хранилища `GuardedResource`, валидирующего входящую эпоху.
3. Смоделируйте захват лидерства Лидером 1 с Эпохой 1.
4. Сымитируйте перевыборы: Лидер 2 получает Эпоху 2 и успешно применяет изменение.
5. Продемонстрируйте, как запоздалый пакет от Лидера 1 с Эпохой 1 отклоняется хранилищем.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
)

var (
	ErrStaleLeaderRejected = errors.New("guard rejection: fencing epoch is stale")
)

type LeadershipElectionCoordinator struct {
	epoch uint64
}

func (c *LeadershipElectionCoordinator) ElectLeader(nodeID string) (string, uint64) {
	newEpoch := atomic.AddUint64(&c.epoch, 1)
	fmt.Printf("[Coordinator] Node '%s' elected Leader for Epoch %d\n", nodeID, newEpoch)
	return nodeID, newEpoch
}

type GuardedStorage struct {
	mu            sync.Mutex
	configData    string
	highestEpoch  uint64
	activeLeader  string
}

func (s *GuardedStorage) CommitConfig(data, leaderID string, epoch uint64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Strict Monotonic Fencing Check
	if epoch <= s.highestEpoch {
		return fmt.Errorf("%w: leader '%s' (epoch %d) tried to overwrite current epoch %d",
			ErrStaleLeaderRejected, leaderID, epoch, s.highestEpoch)
	}

	s.configData = data
	s.highestEpoch = epoch
	s.activeLeader = leaderID
	fmt.Printf("✅ Storage accepted config '%s' from Leader '%s' (Epoch: %d)\n",
		data, leaderID, epoch)
	return nil
}

func main() {
	coord := &LeadershipElectionCoordinator{epoch: 10}
	storage := &GuardedStorage{highestEpoch: 10}

	// 1. Leader 1 elected with Epoch 11
	leader1, epoch1 := coord.ElectLeader("node-srv-1")

	// Leader 1 freezes due to network partition...

	// 2. Majority cluster elects Leader 2 with Epoch 12
	leader2, epoch2 := coord.ElectLeader("node-srv-2")

	// 3. Leader 2 commits new configuration first
	if err := storage.CommitConfig("Config v2.0 (Port 8443)", leader2, epoch2); err != nil {
		panic(err)
	}

	// 4. Stale Leader 1 unfreezes and attempts to commit old config with Epoch 11
	fmt.Println("\n[Stale Leader 1] Attempting to push outdated configuration...")
	err := storage.CommitConfig("Config v1.0 (Port 8080)", leader1, epoch1)
	if err != nil {
		fmt.Printf("🛡️ Fencing protected storage: %v\n", err)
	}

	fmt.Printf("\nFinal Storage State: '%s' (Committed by %s at Epoch %d)\n",
		storage.configData, storage.activeLeader, storage.highestEpoch)
}
```

ℹ️ Защита хранилища от устаревших лидеров через монотонные Fencing Epochs

## Под капотом

Связь с протоколом Raft:
В алгоритме Raft концепция токена ограждения заложена в самое ядро через параметр **`Term`**.
Каждый RPC-запрос `AppendEntries` или `RequestVote` содержит `term`.
Если узел получает сообщение с `msg.Term < currentTerm`, он немедленно отвергает его.
Аналогично, когда Raft-лидер координирует запись во внешнюю систему, он передает свой `currentTerm` как Fencing Token.

## Подводные камни

- **Генерация токенов через случайные числа**: Случайные UUID не обладают свойством частичного или тотального порядка (\(A > B\)) и не могут служить токенами ограждения. Токен обязан быть монотонным числом.
- **Отсутствие поддержки токенов на стороне ресурса**: Если само хранилище не проверяет `token > last_token`, алгоритм не работает.

## На собеседовании

В Яндекс Облаке и Ozon часто спрашивают: *«В чем разница между UUID токеном блокировки в Redis и Fencing Token?»*
**Ответ**:
- **UUID в Redis** защищает только **сам Redis**: он нужен для фазы `Unlock`, чтобы процесс \(A\) случайно не удалил блокировку, которую перехватил процесс \(B\). Но UUID никак не защищает саму базу данных!
- **Fencing Token** защищает **целевое хранилище данных (PostgreSQL, S3)**: это монотонное число, которое база данных валидирует при каждой записи (`WHERE token > max_token`), отсекая запросы от процессов, чья блокировка уже истекла.
