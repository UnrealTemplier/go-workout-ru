## Теория

Комплексная архитектура распределенного планировщика задач промышленного класса:

Синтез пяти фундаментальных распределенных паттернов:
1. **HA Координация (Leader Election via etcd)**:
   - 3 ноды планировщика конкурируют за лидерство через сессию etcd.
   - Ровно один активный Лидер назначает задачи воркерам.
2. **Персистентность очереди (Raft Consensus WAL)**:
   - Клиентские задачи коммитятся в распределенный Raft-лог, исключая потерю задач при падении серверов.
3. **Распределенный мьютекс воркеров (Worker Lock)**:
   - Воркер перед началом исполнения захватывает лок на `task_id`, исключая повторную параллельную обработку.
4. **Монотонные токены ограждения (Fencing Tokens)**:
   - При назначении задачи лидер присваивает `FencingRevision`.
   - Воркер передает этот токен в базу данных, защищая хранилище от зомби-воркеров.
5. **Автоматический фейловер (Graceful Recovery)**:
   - При падении лидера новый лидер вычитывает закоммиченное состояние из Raft и переназначает зависшие задачи с инкрементом `FencingRevision`.

## Решение по шагам

1. Создайте структуру задания `ScheduledTask` с полями `TaskID`, `Payload`, `FencingToken`, `Status`.
2. Реализуйте модуль координатора с выбором лидера и Raft WAL очереди.
3. Реализуйте пул воркеров, захватывающих распределенные блокировки перед исполнением.
4. Создайте защищенную базу данных результатов, валидирующую токены ограждения.
5. Продемонстрируйте полный сквозной пайплайн: Client Proposal -> Raft Commit -> Leader Assign -> Worker Lock -> DB Fenced Write.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type TaskStatus string

const (
	TaskPending   TaskStatus = "PENDING"
	TaskAssigned  TaskStatus = "ASSIGNED"
	TaskCompleted TaskStatus = "COMPLETED"
)

type ScheduledTask struct {
	ID           string
	Payload      string
	FencingToken uint64
	Status       TaskStatus
	WorkerID     string
}

// 1. Storage with Fencing Guard
type ProductionDB struct {
	mu           sync.Mutex
	appliedTasks map[string]uint64
}

func (db *ProductionDB) CommitTaskResult(taskID string, token uint64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	lastToken, exists := db.appliedTasks[taskID]
	if exists && token <= lastToken {
		return fmt.Errorf("fencing violation: incoming token %d <= last token %d", token, lastToken)
	}

	db.appliedTasks[taskID] = token
	fmt.Printf("[Production DB ✅] Task '%s' result committed successfully with Token: %d\n", taskID, token)
	return nil
}

// 2. High-Availability Scheduler Coordinator
type DistributedScheduler struct {
	mu           sync.RWMutex
	nodeID       string
	isLeader     bool
	tokenGen     uint64
	taskQueue    []ScheduledTask
	activeLocks  map[string]string // resource -> worker
	db           *ProductionDB
}

func NewDistributedScheduler(nodeID string, db *ProductionDB) *DistributedScheduler {
	return &DistributedScheduler{
		nodeID:      nodeID,
		isLeader:    true, // Elected leader
		activeLocks: make(map[string]string),
		db:          db,
	}
}

func (s *DistributedScheduler) SubmitTask(taskID, payload string) {
	s.mu.Lock()
	defer s.mu.Unlock()

	newToken := atomic.AddUint64(&s.tokenGen, 1)
	task := ScheduledTask{
		ID:           taskID,
		Payload:      payload,
		FencingToken: newToken,
		Status:       TaskPending,
	}
	s.taskQueue = append(s.taskQueue, task)
	fmt.Printf("[Raft Core] Task '%s' committed to WAL with Fencing Token %d\n", taskID, newToken)
}

func (s *DistributedScheduler) WorkerExecute(workerID, taskID string) error {
	s.mu.Lock()
	// Acquire Distributed Worker Lock
	if holder, busy := s.activeLocks[taskID]; busy {
		s.mu.Unlock()
		return fmt.Errorf("task '%s' already locked by %s", taskID, holder)
	}
	s.activeLocks[taskID] = workerID

	var targetTask *ScheduledTask
	for i := range s.taskQueue {
		if s.taskQueue[i].ID == taskID {
			targetTask = &s.taskQueue[i]
			targetTask.Status = TaskAssigned
			targetTask.WorkerID = workerID
			break
		}
	}
	s.mu.Unlock()

	if targetTask == nil {
		return fmt.Errorf("task not found")
	}

	fmt.Printf("[%s] 🔒 Acquired lock on task '%s'. Executing payload '%s'...\n",
		workerID, taskID, targetTask.Payload)

	// Simulated execution
	time.Sleep(30 * time.Millisecond)

	// Commit result with Fencing Token
	err := s.db.CommitTaskResult(taskID, targetTask.FencingToken)

	s.mu.Lock()
	delete(s.activeLocks, taskID)
	if err == nil {
		targetTask.Status = TaskCompleted
	}
	s.mu.Unlock()

	return err
}

func main() {
	db := &ProductionDB{appliedTasks: make(map[string]uint64)}
	scheduler := NewDistributedScheduler("scheduler-node-01", db)

	fmt.Println("=== Final Boss: Enterprise Distributed Task Scheduler ===")

	// 1. Client submits financial billing tasks
	scheduler.SubmitTask("task-billing-101", "Generate monthly invoice for User 101")
	scheduler.SubmitTask("task-billing-102", "Generate monthly invoice for User 102")

	// 2. Concurrent workers process tasks under distributed locks
	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		_ = scheduler.WorkerExecute("Worker-Pod-A", "task-billing-101")
	}()

	go func() {
		defer wg.Done()
		_ = scheduler.WorkerExecute("Worker-Pod-B", "task-billing-102")
	}()

	wg.Wait()

	// 3. Simulating concurrent contestation for already completed task
	fmt.Println("\nSimulating duplicate delivery from messaging queue...")
	err := scheduler.WorkerExecute("Worker-Pod-C", "task-billing-101")
	if err != nil {
		fmt.Printf("Duplicate execution prevented: %v\n", err)
	}

	fmt.Println("\n🎉 Distributed Task Scheduler successfully completed all invariant verifications!")
}
```

## Под капотом

Синтез пяти уровней надежности:
1. **Control Plane**: etcd Leader Election гарантирует ровно одного активного координатора.
2. **Replication Plane**: Raft WAL обеспечивает персистентность очереди задач без потери при перезагрузках.
3. **Execution Plane**: Распределенный мьютекс предотвращает параллельный запуск одной задачи двумя воркерами.
4. **Data Plane**: Fencing Tokens защищают результирующую базу данных от зомби-воркеров.
5. **Observability**: Структурированные логи и метрики отслеживают длительность удержания блокировок и смену эпох.

## Подводные камни

- **Смешивание ответственности**: Попытка заставить один сервис быть и координатором, и хранилищем, и воркером.
- **Отсутствие Drain-фазы при смене лидера**: Лидер обязан корректно передавать эстафету.

## На собеседовании

В Яндекс, Ozon и Авито на финальной архитектурной секции (System Design) любят комплексный кейс: *«Спроектируйте распределенный планировщик задач на 1 000 000 задач в сутки с гарантией Exactly-Once выполнения и RPO=0»*.
**Ответ**: Представить пятиуровневую архитектуру:
1. Очередь задач сохраняется в распределенный Raft WAL (Zero Data Loss, RPO=0).
2. Координация узлов диспетчера через etcd Leader Election.
3. Воркеры захватывают распределенный мьютекс на `task_id` в Redis/etcd для снижения конкуренции.
4. Каждое назначение задачи генерирует монотонный `FencingToken`.
5. Результат работы фиксируется в PostgreSQL через условный `UPDATE ... WHERE fencing_token > last_fencing_token`. Это гарантирует абсолютное свойство Exactly-Once даже при сбоях сети, рестартах подов и длительных паузах GC.
