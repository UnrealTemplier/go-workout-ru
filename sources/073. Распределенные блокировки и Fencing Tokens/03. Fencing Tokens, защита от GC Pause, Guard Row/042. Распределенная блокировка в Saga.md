# Распределенная блокировка в Saga: предотвращение двойного выполнения шагов при Split-Brain

## Условие

42. **Distributed Lock в Saga.**: Свяжите с Блоком 22: Saga Orchestrator перед выполнением шага захватывает lock на `saga_id` + `step_index`. Это предотвращает dual execution при split-brain (два orchestrator-а думают, что они primary). Покажите интеграцию.

### Исходная формулировка

**Distributed Lock в Saga.**: Свяжите с Блоком 22: Saga Orchestrator перед выполнением шага захватывает lock на `saga_id` + `step_index`. Это предотвращает dual execution при split-brain (два orchestrator-а думают, что они primary). Покажите интеграцию: `Lock` → `Execute Step` → `Store Result` → `Unlock`.

## Теория

Интеграция распределенных блокировок с паттерном распределенных транзакций Saga (Saga Pattern):

Проблема Dual Execution при оркестрации Saga:
В высокодоступных кластерах (Active-Passive или Active-Active) развертывается несколько инстансов Saga Orchestrator:
1. При сетевом сбое (Split-Brain) два оркестратора \(O_1\) и \(O_2\) могут одновременно решить, что они назначены ведущими для выполнения шага распределенной транзакции.
2. Оркестратор \(O_1\) отправляет команду «Списать деньги со счета».
3. Оркестратор \(O_2\) параллельно отправляет команду «Списать деньги со счета».
4. Происходит двойное списание!

Решение:
Перед вызовом компенсационного или прямого действия оркестратор обязан атомарно захватить распределенный мьютекс на составной ключ:
$$\text{LockKey} = \text{fmt.Sprintf}("saga:lock:%s:step:%d", \text{sagaID}, \text{stepIndex})$$
Ровно один оркестратор выполняет шаг; второй видит занятость ресурса и уступает выполнение.

## Решение по шагам

1. Создайте структуру шага Saga `SagaStepExecution` с идентификаторами `SagaID` и `StepIndex`.
2. Реализуйте метод `ExecuteStepSafely(step, orchestratorID)`.
3. Смоделируйте одновременную попытку запуска шага 2 (Резервирование билета) двумя оркестраторами.
4. Продемонстрируйте, как первый оркестратор выполняет шаг, а второй отсекается блокировкой.
5. Зафиксируйте исключение двойного выполнения в истории саги.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type SagaStep struct {
	SagaID    string
	StepIndex int
	Action    string
}

type DistributedSagaLockCoordinator struct {
	mu    sync.Mutex
	locks map[string]string // "saga:id:step:idx" -> orchestratorID
}

func (c *DistributedSagaLockCoordinator) TryAcquireStepLock(sagaID string, stepIdx int, orchestrator string) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	key := fmt.Sprintf("saga:%s:step:%d", sagaID, stepIdx)
	if _, busy := c.locks[key]; busy {
		return false
	}
	c.locks[key] = orchestrator
	return true
}

func (c *DistributedSagaLockCoordinator) ReleaseStepLock(sagaID string, stepIdx int, orchestrator string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	key := fmt.Sprintf("saga:%s:step:%d", sagaID, stepIdx)
	if c.locks[key] == orchestrator {
		delete(c.locks, key)
	}
}

func OrchestratorExecuteStep(
	ctx context.Context,
	coord *DistributedSagaLockCoordinator,
	orchestratorID string,
	step SagaStep,
	stepFn func() error,
) error {
	// 1. Acquire step lock
	if !coord.TryAcquireStepLock(step.SagaID, step.StepIndex, orchestratorID) {
		return fmt.Errorf("[%s] Step %d of Saga %s already locked by competing orchestrator (Dual Execution Blocked!)",
			orchestratorID, step.StepIndex, step.SagaID)
	}
	defer coord.ReleaseStepLock(step.SagaID, step.StepIndex, orchestratorID)

	fmt.Printf("[%s] 🔒 Locked Step %d. Executing action: '%s'...\n",
		orchestratorID, step.StepIndex, step.Action)

	return stepFn()
}

func main() {
	coord := &DistributedSagaLockCoordinator{locks: make(map[string]string)}
	ctx := context.Background()

	stepBookFlight := SagaStep{
		SagaID:    "saga-vacation-9901",
		StepIndex: 2,
		Action:    "Reserve Airline Seat (Flight SU-100)",
	}

	var wg sync.WaitGroup
	wg.Add(2)

	// Orchestrator A attempts execution
	go func() {
		defer wg.Done()
		err := OrchestratorExecuteStep(ctx, coord, "Orchestrator-Instance-A", stepBookFlight, func() error {
			time.Sleep(50 * time.Millisecond)
			fmt.Println("✅ [Orchestrator-Instance-A] Flight seat booked successfully!")
			return nil
		})
		if err != nil {
			fmt.Println(err)
		}
	}()

	// Competing Orchestrator B attempts simultaneous execution (Split-Brain)
	go func() {
		defer wg.Done()
		time.Sleep(10 * time.Millisecond) // slightly later
		err := OrchestratorExecuteStep(ctx, coord, "Orchestrator-Instance-B", stepBookFlight, func() error {
			time.Sleep(50 * time.Millisecond)
			fmt.Println("💥 DUAL BOOKING DISASTER!")
			return nil
		})
		if err != nil {
			fmt.Printf("🛡️ %v\n", err)
		}
	}()

	wg.Wait()
	fmt.Println("\nSaga step orchestration verified: Mutual exclusion maintained across orchestrators.")
}
```

## Под капотом

Связка Saga и Outbox с блокировками:
В надежной архитектуре оркестратор фиксирует статус шага в локальной таблице саги (`saga_state`) внутри транзакции базы данных.
Распределенный мьютекс на составной ключ `saga:step` отсекает параллельные сетевые прерывания от резервных реплик до того, как они начнут отправлять внешние команды в брокер RabbitMQ/Kafka.

## Подводные камни

- **Лок на всю Saga целиком**: Если заблокировать всю сагу на 10 минут, нельзя будет параллельно запустить независимые компенсации или шаги. Блокироваться обязан конкретный шаг `step_index`.
- **Отсутствие проверки статуса шага перед взятием лока**: Если шаг уже был завершен ранее, лок брать бессмысленно.

## На собеседовании

В Wildberries и Lamoda часто спрашивают: *«Как предотвратить дублирование списания денег в распределенной саге при одновременном перезапуске пода-оркестратора в Kubernetes?»*
**Ответ**: Использовать двухконтурную защиту:
1. **Распределенный мьютекс** на составной ключ `saga_id + step_index` при входе в обработчик шага (отсекает 99.9% параллельных попыток оркестраторов).
2. **Идемпотентный ключ** `Idempotency-Key: <saga_id>-<step_index>`, передаваемый в заголовке вызова платежного шлюза. Если даже оба запроса дойдут до банка, платежная система отклонит дубликат на своей стороне.
