# Каверзный кейс: Stop-The-World пауза сборщика мусора и кража блокировки во время работы

## Условие

38. **[Каверзный кейс — The GC Pause Problem]**: Напиши симуляцию: Горутина A берет Redlock на 2 секунды. Локально она начинает выполнять работу. Но тут происходит Stop-The-World (GC) на 3 секунды (сэмулируй через `runtime.GC()` в цикле или `debug.SetGCPercent(-1)` + Sleep). Пока A висит, лок протухает, горутина B берет лок и успевает сделать работу. Горутина A отвисает и пытается доделать работу. Покажи гонку и защити через Fencing Token.

### Исходная формулировка

**[Каверзный кейс — The GC Pause Problem]**: Напиши симуляцию: Горутина A берет Redlock на 2 секунды. Локально она начинает выполнять работу. Но тут происходит Stop-The-World (GC) на 3 секунды (сэмулируй через `runtime.GC()` в цикле или `debug.SetGCPercent(-1)`). Lock в Redis истекает. Горутина B берет блокировку и начинает писать в файл/БД. Горутина A просыпается после GC и *продолжает* писать, думая, что держит лок. Происходит повреждение данных.

## Теория

Сценарий Stop-The-World (STW) GC Pause:

Детальная хронология катастрофы:
1. Горутина \(A\) берет Redlock с \(TTL = 200\text{ мс}\).
2. Горутина \(A\) запускает ресурсоемкую операцию (обработка платежа).
3. В рантайме Go запускается сборщик мусора или происходит вытеснение виртуальной машины на \(300\text{ мс}\).
4. Все горутины заморожены в фазе Stop-The-World.
5. Время \(TTL = 200\text{ мс}\) в Redis истекает.
6. Горутина \(B\) просыпается на другом сервере, запрашивает лок на тот же ресурс, успешно получает его с новым Fencing Token и изменяет баланс в БД.
7. Горутина \(A\) оттаивает. Если она просто отправит свой SQL `UPDATE`, она затрет правки Горутины \(B\).

Спасение через Fencing Token:
Горутина \(A\) получила \(\text{Token} = 101\).
Горутина \(B\) получила \(\text{Token} = 102\).
База данных выполняет `UPDATE ... WHERE token > last_token`.
Правка Горутины \(B\) проходит (\(102 > 100\)). Запоздалая правка Горутины \(A\) отвергается базой (\(101 < 102\)).

## Решение по шагам

1. Создайте имитатор STW-паузы через контролируемый сон горутины.
2. Настройте координатор блокировок с монотонными токенами.
3. Горутина \(A\) берет лок с токеном 101 и засыпает на 300 мс (STW freeze).
4. Горутина \(B\) берет лок с токеном 102 после истечения 200 мс TTL и применяет транзакцию.
5. Горутина \(A\) просыпается, пытается записать данные в БД и получает отказ по Fencing Token.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type FencedDBRecord struct {
	Value            string
	LastFencingToken uint64
}

type SecureDatabase struct {
	mu     sync.Mutex
	record FencedDBRecord
}

func (db *SecureDatabase) ApplyUpdate(author, val string, token uint64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// FENCING SHIELD: Reject any token less than or equal to current highest
	if token <= db.record.LastFencingToken {
		return fmt.Errorf("FENCING VIOLATION: rejected stale write from '%s' (token %d <= current %d)",
			author, token, db.record.LastFencingToken)
	}

	db.record.Value = val
	db.record.LastFencingToken = token
	fmt.Printf("[DB Commit] Accepted write from '%s': '%s' (Token: %d)\n", author, val, token)
	return nil
}

type CentralLockManager struct {
	tokenSeq uint64
	mu       sync.Mutex
	holder   string
	exp      time.Time
}

func (m *CentralLockManager) Acquire(worker string, ttl time.Duration) (uint64, bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	if time.Now().Before(m.exp) {
		return 0, false
	}

	token := atomic.AddUint64(&m.tokenSeq, 1)
	m.holder = worker
	m.exp = time.Now().Add(ttl)
	return token, true
}

func main() {
	db := &SecureDatabase{record: FencedDBRecord{Value: "Initial State", LastFencingToken: 100}}
	lockMgr := &CentralLockManager{tokenSeq: 100}
	var wg sync.WaitGroup

	fmt.Println("=== Tricky Case: Stop-The-World GC Pause vs Fencing Token ===")

	// 1. Goroutine A acquires lock with 200ms TTL
	tokenA, okA := lockMgr.Acquire("Goroutine-A", 200*time.Millisecond)
	if !okA {
		panic("expected A to acquire")
	}
	fmt.Printf("Goroutine-A acquired lock! Token = %d (TTL = 200ms)\n", tokenA)

	// Goroutine A enters simulated Stop-The-World pause
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("[Goroutine-A] ❄️ Stop-The-World GC Pause initiated (Freezing for 350ms)...")
		time.Sleep(350 * time.Millisecond) // STW pause exceeds 200ms TTL!

		fmt.Printf("[Goroutine-A] ☀️ Woke up after GC. Attempting write with Token %d...\n", tokenA)
		err := db.ApplyUpdate("Goroutine-A", "Data from Goroutine A", tokenA)
		if err != nil {
			fmt.Printf("🛡️ SHIELD ACTIVATED: %v\n", err)
		}
	}()

	// 2. While A is frozen, TTL expires. Goroutine B steps in at 220ms
	time.Sleep(220 * time.Millisecond)
	fmt.Println("\n[Lock Manager] TTL expired! Goroutine-B acquiring lock...")
	tokenB, okB := lockMgr.Acquire("Goroutine-B", 200*time.Millisecond)
	if okB {
		fmt.Printf("Goroutine-B acquired lock! Token = %d\n", tokenB)
		_ = db.ApplyUpdate("Goroutine-B", "Legitimate Data from Goroutine B", tokenB)
	}

	wg.Wait()

	fmt.Println("\n=== FINAL AUDIT ===")
	fmt.Printf("Final Database Content: '%s' (Protected by Token %d)\n",
		db.record.Value, db.record.LastFencingToken)
}
```

## Под капотом

Почему Go рантайм может сделать долгую паузу:
Хотя с Go 1.5 сборщик мусора является конкурентным (concurrent tri-color mark & sweep), фазы `STW 1` (включение write barrier) и `STW 2` (выключение write barrier) требуют остановки всех горутин на точках безопасной остановки (Safe Points).
Если одна горутина исполняет плотный цикл без вызовов функций (до Go 1.14), или если ОС испытывает жесткий свопинг страниц (swap thrashing), время достижения safe point может достигать сотен миллисекунд и секунд.

## Подводные камни

- **Попытка использовать time.Now() для самопроверки**: Как уже доказано, проверка `time.Now().Before(exp)` может пройти успешно, а пауза GC случится ровно между этой строкой и сетевым вызовом в БД.
- **Хранилище без строгой монотонной проверки**: Если база просто перезаписывает поле без `WHERE token > last_token`.

## На собеседовании

В Яндекс Облаке и Авито часто спрашивают: *«Как математически доказать, что в асинхронной распределенной системе невозможно построить корректную распределенную блокировку без участия целевого ресурса?»*
**Ответ**: Согласно теореме FLP (Fischer-Lynch-Paterson) и анализу асинхронных сетей, задержки передачи сообщений и задержки исполнения процессов не ограничены сверху константой. Любой клиент после получения подтверждения о захвате блокировки может быть задержан средой выполнения на время \(\Delta t > \text{TTL}\). Следовательно, координатор блокировок не может гарантировать безопасность (Safety) постфактум. Единственным компонентом, способным сериализовать доступ, является сам **целевой ресурс хранения**, валидирующий монотонный порядок входящих операций.
