# Fencing с использованием etcd CreateRevision: интеграция с транзакциями clientv3.Txn

## Условие

36. **Fencing с etcd Revision.**: Используйте `CreateRevision` из etcd как fencing token. При захвате lock через `clientv3.Txn` получите `CreateRevision`. Все последующие writes в БД включают `WHERE revision >= $createRevision`. Объясните, почему etcd — идеальный источник fencing tokens.

### Исходная формулировка

**Fencing с etcd Revision.**: Используйте `CreateRevision` из etcd как fencing token. При захвате lock через `clientv3.Txn` получите `CreateRevision`. Все последующие writes в БД включают `WHERE revision >= $createRevision`. Объясните, почему etcd revision — идеальный fencing token (strictly monotonic, persistent, replicated).

## Теория

Почему etcd является идеальным источником токенов ограждения:

1. **Глобальный монотонный счетчик**: Любая мутация в etcd коммитится через Raft и инкрементирует 64-битное глобальное число `Header.Revision`.
2. **Иммутабельность `CreateRevision`**:
   - При захвате блокировки создается эфемерный ключ `/locks/my-resource/<lease_id>`.
   - Поле `CreateRevision` фиксирует точную глобальную ревизию момента создания этого ключа.
   - Это значение **абсолютно неизменно (Immutable)** на все время удержания блокировки и строго превышает ревизии всех предыдущих владельцев.
3. **Транзакционная интеграция с БД**:
   - Клиент считывает `token := response.Header.Revision`.
   - В SQL-запросах используется предикат:
     ```sql
     UPDATE orders
     SET status = 'PROCESSED',
         last_fencing_revision = :rev
     WHERE order_id = :id
       AND last_fencing_revision < :rev;
     ```

## Решение по шагам

1. Создайте модель `EtcdTxnLock` с возвратом метаданных транзакции etcd.
2. Реализуйте метод `AcquireWithRevision(key)`, возвращающий `CreateRevision`.
3. Смоделируйте целевой сервис заказов `OrderServiceDB` с проверкой ревизии.
4. Продемонстрируйте захват лока с ревизией 450 и успешную обработку заказа.
5. Сымитируйте попытку записи со старой ревизией 440 и зафиксируйте отклонение.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

type EtcdTxnResult struct {
	Key            string
	CreateRevision int64
	Success        bool
}

type MockEtcdTxnEngine struct {
	mu          sync.Mutex
	globalRev   int64
	activeLocks map[string]int64
}

func NewMockEtcdTxnEngine(startRev int64) *MockEtcdTxnEngine {
	return &MockEtcdTxnEngine{
		globalRev:   startRev,
		activeLocks: make(map[string]int64),
	}
}

// Emulates: clientv3.Txn If(CreateRevision(key) == 0).Then(Put(key, lease)).Commit()
func (e *MockEtcdTxnEngine) AcquireLock(key string) EtcdTxnResult {
	e.mu.Lock()
	defer e.mu.Unlock()

	e.globalRev++
	if _, exists := e.activeLocks[key]; exists {
		return EtcdTxnResult{Key: key, Success: false}
	}

	createRev := e.globalRev
	e.activeLocks[key] = createRev
	return EtcdTxnResult{
		Key:            key,
		CreateRevision: createRev,
		Success:        true,
	}
}

type OrderRecord struct {
	ID                  string
	Status              string
	LastFencingRevision int64
}

type OrderDatabase struct {
	mu     sync.Mutex
	orders map[string]OrderRecord
}

func (db *OrderDatabase) UpdateOrderStatus(orderID, newStatus string, rev int64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	ord, exists := db.orders[orderID]
	if !exists {
		return errors.New("order not found")
	}

	// Guard condition: WHERE last_fencing_revision < :rev
	if ord.LastFencingRevision >= rev {
		return fmt.Errorf("stale write rejected: order revision %d >= request revision %d",
			ord.LastFencingRevision, rev)
	}

	ord.Status = newStatus
	ord.LastFencingRevision = rev
	db.orders[orderID] = ord
	fmt.Printf("[PostgreSQL] Order '%s' updated to '%s' with Fencing Revision: %d\n",
		orderID, newStatus, rev)
	return nil
}

func main() {
	etcd := NewMockEtcdTxnEngine(440)
	db := &OrderDatabase{
		orders: map[string]OrderRecord{
			"ord-707": {ID: "ord-707", Status: "NEW", LastFencingRevision: 440},
		},
	}

	// 1. Worker 1 acquires lock via etcd Txn
	res1 := etcd.AcquireLock("/locks/orders/707")
	fmt.Printf("Worker 1 acquired lock via etcd! CreateRevision: %d\n", res1.CreateRevision)

	// Worker 1 writes to DB
	if err := db.UpdateOrderStatus("ord-707", "PROCESSING", res1.CreateRevision); err != nil {
		panic(err)
	}

	// 2. Simulate subsequent lock acquisition (Worker 2 gets higher revision)
	etcd.activeLocks["/locks/orders/707"] = 0 // unlocked
	res2 := etcd.AcquireLock("/locks/orders/707")
	fmt.Printf("\nWorker 2 acquired lock via etcd! CreateRevision: %d\n", res2.CreateRevision)

	_ = db.UpdateOrderStatus("ord-707", "COMPLETED", res2.CreateRevision)

	// 3. Stale Worker 1 attempts delayed write with Revision 441
	fmt.Printf("\n[Zombie Worker 1] Attempting delayed write with Stale Revision %d...\n", res1.CreateRevision)
	err := db.UpdateOrderStatus("ord-707", "PROCESSING_FAILED", res1.CreateRevision)
	if err != nil {
		fmt.Printf("🛡️ Database guard successfully blocked stale write: %v\n", err)
	}
}
```

## Под капотом

Гарантия монотонности в etcd:
Глобальная ревизия etcd инкрементируется **строго по одной единице на каждую успешную запись в Raft-лог**.
Она персистируется в bbolt MVCC хранилище под ключом метаданных. При рестарте кластера etcd читает последнюю ревизию с диска и продолжает счет с нее. Никакие перезагрузки, смены лидеров или сбои сети не могут заставить `CreateRevision` уменьшиться.

## Подводные камни

- **Использование `ModRevision` вместо `CreateRevision`**: Если ключ обновляется внутри сессии, `ModRevision` будет расти, но `CreateRevision` остается постоянным маркером момента захвата блокировки. Для токена ограждения сессии используют именно `CreateRevision`.
- **Забытый WHERE в SQL**: Если выполнить `UPDATE ... WHERE id = :id` без проверки ревизии, данные будут перезаписаны.

## На собеседовании

В Wildberries и Авито часто спрашивают: *«Почему `CreateRevision` в etcd превосходит генерацию токена через Redis `INCR`?»*
**Ответ**:
1. **Атомарность связки**: В etcd захват блокировки и генерация токена происходят в **одной транзакции консенсуса**. Не требуется отдельного сетевого вызова.
2. **Отказоустойчивость**: `CreateRevision` закоммичена большинством узлов Raft на диск (fsync). При падении любой ноды токен не потеряется. В Redis при аварии мастера значение `INCR` может потеряться из-за асинхронной репликации.
