# Обязательность TTL для блокировок: предотвращение Deadlock и фоновый Heartbeat

## Условие

41. **TTL обязателен для locks.**: Без TTL hung process будет держать lock вечно. Всегда устанавливайте expiry и heartbeating для long-running operations. Смоделируйте случай зависания без TTL и с TTL.

### Исходная формулировка

**TTL обязателен для locks.**: Без TTL hung process будет держать lock вечно. Всегда устанавливайте expiry и heartbeating для long-running operations.

## Теория

Аксиома распределенных систем:
**Распределенная блокировка БЕЗ времени жизни (TTL = \(\infty\)) — это гарантированный распределенный Deadlock в будущем.**

Почему блокировка без TTL недопустима:
- Любой процесс операционной системы смертен: `SIGKILL`, Kernel Panic, отказ оперативной памяти, аппаратный сбой стойки ЦОД, завершение пода Kubernetes по `OOMKilled`.
- Если процесс захватил блокировку без TTL (`SET lock:res token`) и умер, ключ останется в памяти навсегда.
- Ни один другой сервер в мире больше никогда не сможет получить доступ к этому ресурсу без ручного вмешательства инженера дежурной смены (On-call PagerDuty alert).

Единственный правильный паттерн:
1. Любой захват **обязан иметь конечный TTL** (Lease Expiry).
2. Для операций с неопределенным временем выполнения запускается фоновый **Heartbeat / Watchdog**, продлевающий TTL до тех пор, пока процесс жив.

## Решение по шагам

1. Создайте модель координатора с двумя режимами захвата: `AcquireWithoutTTL` (опасный) и `AcquireWithTTL` (безопасный).
2. Смоделируйте крах воркера, державшего лок без TTL: покажите вечный Deadlock для последующих запросов.
3. Смоделируйте крах воркера, державшего лок с TTL 100 мс: покажите автоматическое восстановление доступности через 100 мс.
4. Сформулируйте правила настройки времени жизни блокировок.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type TTLComparisonStore struct {
	mu     sync.Mutex
	holder string
	hasTTL bool
	exp    time.Time
}

func (s *TTLComparisonStore) AcquireUnsafeNoTTL(worker string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.holder != "" {
		return false
	}
	s.holder = worker
	s.hasTTL = false
	fmt.Printf("[Unsafe Lock] %s acquired lock WITHOUT TTL (Infinite lock)!\n", worker)
	return true
}

func (s *TTLComparisonStore) AcquireSafeWithTTL(worker string, ttl time.Duration) bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	if s.holder != "" {
		if s.hasTTL && now.After(s.exp) {
			// Auto-evict expired holder
			fmt.Printf("[Auto-Evict ⏰] Expired lock previously held by '%s' cleared!\n", s.holder)
			s.holder = ""
		} else {
			return false
		}
	}

	s.holder = worker
	s.hasTTL = true
	s.exp = now.Add(ttl)
	fmt.Printf("[Safe Lock] %s acquired lock with TTL = %v\n", worker, ttl)
	return true
}

func main() {
	// Scenario A: Disaster without TTL
	fmt.Println("=== SCENARIO A: Lock WITHOUT TTL (Permanent Deadlock) ===")
	storeA := &TTLComparisonStore{}
	storeA.AcquireUnsafeNoTTL("Zombie-Process-1")
	fmt.Println("💥 Zombie-Process-1 crashed (SIGKILL)! Key left without TTL.")

	// Attempt from another worker
	time.Sleep(50 * time.Millisecond)
	if !storeA.AcquireUnsafeNoTTL("Worker-2") {
		fmt.Println("🚨 PERMANENT DEADLOCK: Worker-2 blocked forever because lock has no TTL!")
	}

	// Scenario B: Graceful recovery with TTL
	fmt.Println("\n=== SCENARIO B: Lock WITH TTL (Self-Healing System) ===")
	storeB := &TTLComparisonStore{}
	storeB.AcquireSafeWithTTL("Worker-3", 100*time.Millisecond)
	fmt.Println("💥 Worker-3 crashed (SIGKILL)! But lock has 100ms TTL.")

	fmt.Println("Worker-4 waiting for lease expiry...")
	time.Sleep(120 * time.Millisecond) // Wait for TTL

	if storeB.AcquireSafeWithTTL("Worker-4", 100*time.Millisecond) {
		fmt.Println("✅ SELF-HEALED: Worker-4 successfully acquired lock after TTL expired!")
	}
}
```

## Под капотом

Механизм Active Expiration в Redis:
Redis удаляет ключи с TTL двумя способами:
1. **Passive (Lazy Expiration)**: При попытке доступа к ключу (`GET/SET`) Redis сверяет текущее время с TTL. Если ключ просрочен, он удаляется прямо в момент чтения и возвращается `nil`.
2. **Active Periodic Expiration**: Каждые 100 мс фоновый таймер Redis берет 20 случайных ключей с TTL из базы. Если более 25% из них просрочены, цикл повторяется. Это гарантирует очистку даже тех ключей, к которым больше никто не обращается.

## Подводные камни

- **Попытка сделать лок «пока не завершится задача» без TTL**: Если задача упадет, система остановится. Всегда ставьте разумный TTL (например, удвоенное максимальное время задачи) + KeepAlive.
- **TTL меньше времени сетевого RTT**: Приведет к мгновенному сбросу ключа.

## На собеседовании

В Ozon и Авито часто спрашивают: *«Как подобрать значение TTL для распределенной блокировки в продакшене?»*
**Ответ**: Использовать эмпирическое правило:
$$\text{TTL} = 3 \times \text{P99.9 Latency of Operation} + \text{Clock Drift}$$
Если 99.9% операций завершаются за 500 мс, базовый TTL выставляют в 1.5–2 секунды с интервалом фонового продления (KeepAlive) каждые 500 мс. Это гарантирует, что штатная операция не потеряет лок, а при сбое ресурс освободится менее чем за 2 секунды.
