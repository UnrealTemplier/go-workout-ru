# Иерархия блокировок (Lock Ordering) для предотвращения распределенных дедлоков

## Условие

47. **Lock hierarchy**: Для multiple locks всегда захватывайте в одинаковом порядке для предотвращения deadlocks.

### Исходная формулировка

**Lock hierarchy**: Для multiple locks всегда захватывайте в одинаковом порядке для предотвращения deadlocks.

## Теория

Когда распределенная бизнес-транзакция требует одновременной монопольной блокировки двух или более независимых ресурсов (например, перевод денежных средств со счета A на счет B, перемещение товара со склада 1 на склад 2), возникает риск возникновения **распределенного взаимного блокирования (Distributed Deadlock)**.

Классический сценарий дедлока:
- Воркер 1 выполняет перевод A -> B: сначала блокирует ресурс `A`, затем пытается заблокировать ресурс `B`.
- Воркер 2 одновременно выполняет перевод B -> A: сначала блокирует ресурс `B`, затем пытается заблокировать ресурс `A`.
- В результате Воркер 1 ждет `B`, удерживая `A`, а Воркер 2 ждет `A`, удерживая `B`. Ни один из них не может продолжить работу, ресурсы заблокированы до истечения TTL (Deadlock).

Для предотвращения дедлоков применяется принцип **Lock Hierarchy (Lock Ordering)** — четвертое условие Коффмана (Circular Wait) разрушается принудительным глобальным порядком захвата. Все ресурсы упорядочиваются по каноническому признаку (например, лексикографическая сортировка строковых ID). Воркер обязан захватывать блокировки строго в порядке возрастания ключей: сначала `min(A, B)`, затем `max(A, B)`.

## Решение по шагам

1. Создайте структуру менеджера распределенных блокировок.
2. Реализуйте метод `AcquireMultiLock(ctx, resourceIDs []string, ttl time.Duration)`.
3. Отсортируйте полученный срез ключей лексикографически с помощью `sort.Strings()` или `slices.Sort()`.
4. Удалите дубликаты ключей во избежание повторного захвата одного и того же ресурса.
5. Последовательно захватывайте блокировки по возрастанию ключей.
6. В случае ошибки на любом этапе немедленно освободите все ранее захваченные блокировки в обратном порядке (LIFO rollback) и верните ошибку.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sort"
	"sync"
	"time"
)

type MultiLockManager struct {
	mu     sync.Mutex
	locked map[string]string // resource -> owner
}

func NewMultiLockManager() *MultiLockManager {
	return &MultiLockManager{
		locked: make(map[string]string),
	}
}

func (m *MultiLockManager) tryLock(resource, owner string) bool {
	m.mu.Lock()
	defer m.mu.Unlock()
	if _, held := m.locked[resource]; held {
		return false
	}
	m.locked[resource] = owner
	return true
}

func (m *MultiLockManager) unlock(resource, owner string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	if m.locked[resource] == owner {
		delete(m.locked, resource)
	}
}

// AcquireMultiLock захватывает несколько ресурсов строго в лексикографическом порядке
func (m *MultiLockManager) AcquireMultiLock(ctx context.Context, owner string, resources []string, timeout time.Duration) ([]string, error) {
	// 1. Копируем и сортируем ресурсы канонически
	sorted := make([]string, len(resources))
	copy(sorted, resources)
	sort.Strings(sorted)

	// 2. Дедупликация
	unique := make([]string, 0, len(sorted))
	for i, r := range sorted {
		if i == 0 || r != sorted[i-1] {
			unique = append(unique, r)
		}
	}

	acquired := make([]string, 0, len(unique))
	deadline := time.Now().Add(timeout)

	for _, res := range unique {
		for {
			if time.Now().After(deadline) {
				// Таймаут! Откатываем все ранее взятые блокировки
				m.rollback(owner, acquired)
				return nil, fmt.Errorf("timeout acquiring lock on %s", res)
			}

			if m.tryLock(res, owner) {
				acquired = append(acquired, res)
				break
			}

			// Backoff перед повторной попыткой
			select {
			case <-ctx.Done():
				m.rollback(owner, acquired)
				return nil, ctx.Err()
			case <-time.After(10 * time.Millisecond):
			}
		}
	}

	return acquired, nil
}

func (m *MultiLockManager) rollback(owner string, resources []string) {
	// Освобождаем в обратном порядке
	for i := len(resources) - 1; i >= 0; i-- {
		m.unlock(resources[i], owner)
	}
}

func (m *MultiLockManager) ReleaseMultiLock(owner string, resources []string) {
	m.rollback(owner, resources)
}

func main() {
	manager := NewMultiLockManager()
	var wg sync.WaitGroup
	wg.Add(2)

	// Воркер 1 переводит средства с ACC_200 на ACC_100
	go func() {
		defer wg.Done()
		req := []string{"ACC_200", "ACC_100"}
		held, err := manager.AcquireMultiLock(context.Background(), "worker-1", req, 2*time.Second)
		if err != nil {
			fmt.Println("[Worker 1] Error:", err)
			return
		}
		defer manager.ReleaseMultiLock("worker-1", held)

		fmt.Printf("[Worker 1] Acquired %v in sorted order\n", held)
		time.Sleep(100 * time.Millisecond) // работа
	}()

	// Воркер 2 параллельно переводит средства с ACC_100 на ACC_200
	go func() {
		defer wg.Done()
		req := []string{"ACC_100", "ACC_200"}
		held, err := manager.AcquireMultiLock(context.Background(), "worker-2", req, 2*time.Second)
		if err != nil {
			fmt.Println("[Worker 2] Error:", err)
			return
		}
		defer manager.ReleaseMultiLock("worker-2", held)

		fmt.Printf("[Worker 2] Acquired %v in sorted order\n", held)
		time.Sleep(100 * time.Millisecond) // работа
	}()

	wg.Wait()
	fmt.Println("All multi-lock transfers completed without deadlock!")
}
```

ℹ️ Упорядочивание ресурсов по алфавиту для предотвращения взаимных блокировок (Lock Ordering)

## Под капотом

Математически условия Коффмана требуют одновременного выполнения четырех факторов: 1) Взаимное исключение, 2) Удержание и ожидание (Hold and Wait), 3) Отсутствие принудительного снятия (No Preemption), 4) Циклическое ожидание (Circular Wait). Применение глобального линейного порядка (\(R_1 < R_2 < \dots < R_n\)) делает граф распределенных ожиданий направленным ациклическим графом (DAG). В DAG циклы невозможны по определению, что математически исключает возможность дедлока.

## Подводные камни

1. Забывание дедупликации: если в срез передан один и тот же ключ дважды `["res_a", "res_a"]`, попытка повторного взятия без реентерабельности приведет к самоблокировке (Self-Deadlock).
2. Неполный откат при таймауте: если взяли 2 из 3 блокировок и на третьей вылетел таймаут, не освобожденные первые две останутся заблокированными.

## На собеседовании

«Как разрешать конфликты блокировок в распределенной БД, если порядок доступа к таблицам невозможно отсортировать заранее (динамический запрос)?»
Ответ: В таких системах применяются алгоритмы обнаружения и разрешения дедлоков (Deadlock Detection): 1) Построение графа ожидания транзакций (Wait-For Graph) и поиск циклов (Tarjan's algorithm); 2) Алгоритмы на основе меток времени (Wait-Die и Wound-Wait), где более старая транзакция либо прерывает молодую, либо умирает сама; 3) Агрессивный Lock Timeout с последующим экспоненциальным случайным откатом (Exponential Backoff with Full Jitter).
