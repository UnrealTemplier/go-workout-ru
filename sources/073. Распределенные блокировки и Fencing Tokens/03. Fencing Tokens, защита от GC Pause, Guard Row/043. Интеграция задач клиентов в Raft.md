# Интеграция задач клиентов в Raft: прием запроса и фиксация в распределенном состоянии

## Условие

43. **Client submits task → leader adds to Raft state**: Клиент отправляет задачу на выполнение. Лидер принимает запрос, реплицирует через Raft-лог и переводит задачу в статус PENDING в общем состоянии FSM.

### Исходная формулировка

Client submits task → leader adds to Raft state

## Теория

Паттерн надежного приема задач в распределенных планировщиках:
**Ни одна задача клиента не считается принятой до тех пор, пока она не сохранена в отказоустойчивом консенсус-логе Raft.**

Последовательность операций:
1. Клиент отправляет HTTP/gRPC запрос: `POST /tasks {"id": "task-1", "action": "send_email"}`.
2. Запрос попадает к Лидеру кластера. Если запрос пришел на фолловер, он перенаправляется лидеру.
3. Лидер упаковывает команду в лог Raft: `CMD_TASK_SUBMIT(task_id, payload)`.
4. Лидер вызывает `raft.Apply(payload, timeout)`.
5. Запись реплицируется кворумом нод и персистируется на диски в WAL.
6. Конечный автомат (`FSM.Apply`) фиксирует задачу в памяти со статусом `TaskPending`.
7. Только после этого клиент получает HTTP 201 Created с подтверждением приема задачи.

## Решение по шагам

1. Создайте структуру команды `SubmitTaskCommand` с полями задачи.
2. Реализуйте конечный автомат задач `TaskSchedulerFSM` с методами `Apply` и чтения состояния.
3. Реализуйте эндпоинт отправки задач лидером через консенсус.
4. Продемонстрируйте подтверждение клиенту только после фиксации в FSM.
5. Убедитесь в сохранении задачи в состоянии очереди.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"sync"
	"time"
)

type TaskRecord struct {
	ID        string    `json:"id"`
	Payload   string    `json:"payload"`
	Status    string    `json:"status"` // "PENDING", "RUNNING", "COMPLETED"
	CreatedAt time.Time `json:"created_at"`
}

type TaskFSM struct {
	mu    sync.RWMutex
	tasks map[string]TaskRecord
}

func NewTaskFSM() *TaskFSM {
	return &TaskFSM{tasks: make(map[string]TaskRecord)}
}

func (f *TaskFSM) Apply(cmdBytes []byte) any {
	var task TaskRecord
	if err := json.Unmarshal(cmdBytes, &task); err != nil {
		return err
	}

	f.mu.Lock()
	defer f.mu.Unlock()

	task.Status = "PENDING"
	task.CreatedAt = time.Now()
	f.tasks[task.ID] = task
	fmt.Printf("[FSM Apply 📝] Task '%s' registered in state machine with status PENDING\n", task.ID)
	return task
}

func (f *TaskFSM) GetTask(id string) (TaskRecord, bool) {
	f.mu.RLock()
	defer f.mu.RUnlock()
	t, ok := f.tasks[id]
	return t, ok
}

type LeaderRaftNode struct {
	isLeader bool
	fsm      *TaskFSM
	mu       sync.Mutex
}

func (n *LeaderRaftNode) SubmitTask(id, payload string) (TaskRecord, error) {
	n.mu.Lock()
	if !n.isLeader {
		n.mu.Unlock()
		return TaskRecord{}, errors.New("node is not leader: cannot accept client proposals")
	}
	n.mu.Unlock()

	task := TaskRecord{ID: id, Payload: payload}
	data, _ := json.Marshal(task)

	// Simulate Raft Quorum Replication Delay
	time.Sleep(20 * time.Millisecond)

	// Committed to WAL -> Apply to FSM
	res := n.fsm.Apply(data)
	if err, isErr := res.(error); isErr {
		return TaskRecord{}, err
	}
	return res.(TaskRecord), nil
}

func main() {
	fsm := NewTaskFSM()
	leader := &LeaderRaftNode{isLeader: true, fsm: fsm}

	fmt.Println("=== Client Submits Task to Raft Leader ===")
	task, err := leader.SubmitTask("task-invoice-441", "Generate monthly PDF invoice for client 441")
	if err != nil {
		panic(err)
	}

	fmt.Printf("✅ Client received ACK! TaskID: %s, Status: %s, Created: %v\n",
		task.ID, task.Status, task.CreatedAt.Format("15:04:05.000"))

	// Verify in FSM
	saved, ok := fsm.GetTask("task-invoice-441")
	fmt.Printf("State machine verification: Found = %t, Payload = '%s'\n", ok, saved.Payload)
}
```

ℹ️ Прием клиентской задачи и ее фиксация через консенсус Raft в состоянии FSM

## Под капотом

Почему нельзя слать задачи напрямую в базу данных без Raft:
Если 100 воркеров одновременно пишут в обычную очередь RabbitMQ или Postgres, при сбое брокера или разделении сети задачи могут продублироваться или потеряться.
Фиксация через Raft WAL гарантирует **тотальный порядок (Total Order)** и персистентность на дисках кворума нод. Никакой сбой одного или двух серверов не приведет к потере зарегистрированной задачи.

## Подводные камни

- **Отправка подтверждения клиенту до коммита кворумом**: Если ответить клиенту «OK», а кворум не соберется из-за обрыва сети, клиент решит, что задача в работе, а кластер ее потеряет.
- **Хранение огромных бинарных payloads в Raft**: В Raft-лог шлют только метаданные задачи, а само тело сохраняют в S3.

## На собеседовании

В Яндекс Маркете и Ozon часто спрашивают: *«Как в распределенном планировщике задач обеспечить нулевую потерю задач при отказе серверов (RPO = 0)?»*
**Ответ**: Использовать распределенный консенсус Raft (или etcd). Клиентский запрос парсится лидером и записывается в лог Raft. Подтверждение клиенту (HTTP 201 Created) отправляется **только после того**, как запись лога закоммичена кворумом серверов и сброшена на диск с `fsync`. При падении лидера новый лидер поднимает точное состояние из лога, гарантируя RPO = 0.
