# Фиксация завершения задачи воркером в реплицированном Raft State

## Условие

44. Worker reports completion → leader updates Raft state

### Исходная формулировка

Worker reports completion → leader updates Raft state

## Теория

В распределенном отказоустойчивом диспетчере задач завершение задачи воркером не может быть просто локальным изменением в оперативной памяти лидера. Если лидер примет отчет о завершении от воркера, но упадет до репликации этого события в кворум, новый лидер переназначит задачу другому исполнильтелю, что приведет к повторному исполнению (дублированию эффекта).

Для обеспечения семантики Exactly-Once (или Effectively-Once при наличии идемпотентности) процесс репорта о завершении выглядит следующим образом:
1. Воркер отправляет RPC-запрос завершения `CompleteTaskRequest` с указанием `TaskID`, `WorkerID`, `FencingToken` и `ExecutionResult`.
2. Лидер валидирует запрос: задача должна находиться в статусе `Running`, назначенный воркер должен совпадать, а переданный `FencingToken` обязан быть равен текущему выданному токену.
3. Лидер создает команду перехода стейт-машины `OpTaskCompleted` и передает ее в консенсусный лог Raft через `raft.Apply()`.
4. Raft реплицирует запись на фолловеров. Как только кворум узлов подтвердил запись, стейт-машина обновляет статус задачи на `Completed` и персистирует результат.
5. Только после коммита в Raft лидер отправляет воркеру успешный ACK. Если до коммита лидер падает, клиент/воркер повторяет попытку к новому лидеру, который корректно обработает или отклонит отчет.

## Решение по шагам

1. Определите структуры данных `TaskCompletionReport` и команды стейт-машины `TaskOp`.
2. Реализуйте метод лидера `ReportCompletion(report TaskCompletionReport) error`.
3. Выполните предварительную валидацию: проверка наличия задачи, соответствия назначенного воркера и равенства Fencing Token.
4. Выполните сериализацию команды и вызовите имитацию `Raft.Apply(payload)`.
5. В стейт-машине обновите статус задачи на `TaskStatusCompleted` и сохраните результат выполнения.
6. Верните подтверждение воркеру.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type TaskStatus string

const (
	TaskPending   TaskStatus = "PENDING"
	TaskRunning   TaskStatus = "RUNNING"
	TaskCompleted TaskStatus = "COMPLETED"
	TaskFailed    TaskStatus = "FAILED"
)

type Task struct {
	ID           string
	Status       TaskStatus
	WorkerID     string
	FencingToken uint64
	Result       string
	UpdatedAt    time.Time
}

type TaskCompletionReport struct {
	TaskID       string
	WorkerID     string
	FencingToken uint64
	Result       string
}

type RaftNode struct {
	mu          sync.Mutex
	state       map[string]*Task
	appliedLogs []string
}

func NewRaftNode() *RaftNode {
	return &RaftNode{
		state: make(map[string]*Task),
	}
}

func (rn *RaftNode) Apply(ctx context.Context, cmd string) error {
	rn.mu.Lock()
	defer rn.mu.Unlock()
	// Симуляция репликации в Raft кворум
	rn.appliedLogs = append(rn.appliedLogs, cmd)
	return nil
}

type TaskCoordinator struct {
	mu   sync.RWMutex
	raft *RaftNode
}

func NewTaskCoordinator(raft *RaftNode) *TaskCoordinator {
	return &TaskCoordinator{raft: raft}
}

func (tc *TaskCoordinator) ReportCompletion(ctx context.Context, report TaskCompletionReport) error {
	tc.mu.Lock()
	task, exists := tc.raft.state[report.TaskID]
	if !exists {
		tc.mu.Unlock()
		return errors.New("task not found")
	}

	if task.Status != TaskRunning {
		tc.mu.Unlock()
		return fmt.Errorf("task %s is not running (current status: %s)", report.TaskID, task.Status)
	}

	if task.WorkerID != report.WorkerID {
		tc.mu.Unlock()
		return fmt.Errorf("worker mismatch: expected %s, got %s", task.WorkerID, report.WorkerID)
	}

	if task.FencingToken != report.FencingToken {
		tc.mu.Unlock()
		return fmt.Errorf("stale fencing token: expected %d, got %d", task.FencingToken, report.FencingToken)
	}
	tc.mu.Unlock()

	// Формируем команду для Raft Log
	cmd := fmt.Sprintf("COMPLETE_TASK:%s:%s:%d", report.TaskID, report.Result, report.FencingToken)
	if err := tc.raft.Apply(ctx, cmd); err != nil {
		return fmt.Errorf("raft replication failed: %w", err)
	}

	// Обновляем состояние после подтверждения Raft
	tc.mu.Lock()
	task.Status = TaskCompleted
	task.Result = report.Result
	task.UpdatedAt = time.Now()
	tc.mu.Unlock()

	return nil
}

func main() {
	raft := NewRaftNode()
	coord := NewTaskCoordinator(raft)

	raft.state["task-101"] = &Task{
		ID:           "task-101",
		Status:       TaskRunning,
		WorkerID:     "worker-A",
		FencingToken: 42,
		UpdatedAt:    time.Now(),
	}

	ctx := context.Background()

	// 1. Попытка с устаревшим токеном
	err := coord.ReportCompletion(ctx, TaskCompletionReport{
		TaskID:       "task-101",
		WorkerID:     "worker-A",
		FencingToken: 41,
		Result:       "success data",
	})
	fmt.Println("Stale report error:", err)

	// 2. Валидный отчет
	err = coord.ReportCompletion(ctx, TaskCompletionReport{
		TaskID:       "task-101",
		WorkerID:     "worker-A",
		FencingToken: 42,
		Result:       "processed 1000 items successfully",
	})
	fmt.Println("Valid report error:", err)
	fmt.Printf("Final task state: %+v\n", raft.state["task-101"])
}
```

## Под капотом

При репликации отчета о завершении в Raft критически важно понимать порядок фиксации. Если лидер применит изменение в локальный стейт до того, как запись закомичена в Raft, в случае аварии лидера возникнет рассинхронизация: старый лидер будет считать задачу завершенной, а новый лидер (избранный кворумом) увидит задачу зависшей в статусе `Running` и переназначит ее. Поэтому двухфазный процесс: 1) Репликация команды в Raft, 2) Применение к стейт-машине после коммита — фундаментальное правило распределенных диспетчеров.

## Подводные камни

1. Забывание проверки `WorkerID` и `FencingToken`: если упавший воркер воскреснет и отправит запоздалый отчет, он затрет результат работы нового воркера.
2. Неидемпотентная обработка: при сбоях сети воркер отправляет повтор `CompleteTaskRequest`. Если задача уже `Completed` с тем же токеном, лидер должен возвращать успех, а не падать с ошибкой 'task not running'.

## На собеседовании

«Как в распределенном шедулере (например, Kubernetes Kube-Scheduler или Temporal) защититься от ситуации, когда два воркера считают себя исполнителями одной задачи и одновременно отправляют результаты?»
Ответ: Назначение задачи сопровождается монотонным Fencing Token (или Generation ID / Term). Лидер координирует назначение через консенсусный лог (Raft/etcd). Воркер обязан прикладывать токен ко всем RPC. При получении первого отчета состояние атомарно переводится в `Completed` через консенсус. Второй воркер получает ошибку невалидного токена или статуса задачи.
