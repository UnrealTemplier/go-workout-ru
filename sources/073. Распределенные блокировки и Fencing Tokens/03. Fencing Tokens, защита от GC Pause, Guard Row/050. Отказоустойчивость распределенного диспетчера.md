# Отказоустойчивость распределенного диспетчера задач с Fencing Tokens и переназначением

## Условие

50. If worker fails → leader reassigns task (with fencing token) ... Reliability, Scaling, Observability, Testing, Production features

### Исходная формулировка

If worker fails → leader reassigns task (with fencing token)

    **Reliability:**
    * **Raft replication** для task queue persistence
    * **Leader failover** при crash (automatic через etcd)
    * **Worker failover** при crash (task reassigned)
    * **Fencing tokens** для защиты от stale workers
    * **Idempotency** для task execution (task ID как idempotency key)

    **Scaling:**
    * **Horizontal scaling:** add more scheduler nodes
    * **Worker pool:** dynamic worker scaling
    * **Task prioritization:** high-priority tasks first
    * **Rate limiting:** per-client task submission limits

    **Observability:**
    * **Metrics:** task queue depth, task latency, worker utilization, leader election frequency
    * **Traces:** каждый task как distributed trace
    * **Logs:** task lifecycle events, lock acquisition, leader changes
    * **Alerts:** high task queue depth, worker failures, leader instability

    **Testing:**
    * **Unit tests:** task scheduling logic, lock acquisition
    * **Integration tests:** Raft replication, leader election
    * **Chaos tests:** kill leader, kill workers, network partitions
    * **Load tests:** 10k tasks/minute, 100 concurrent workers

    **Production features:**
    * **Task retries** с exponential backoff
    * **Dead letter queue** для failed tasks
    * **Task cancellation** через distributed signal
    * **Task dependencies** (DAG execution)
    * **Multi-tenancy** с per-tenant quotas
    * **Webhook notifications** для task completion

## Теория

Комплексная архитектура распределенного планировщика задач (Task Scheduler / Distributed Workflow Engine в духе Temporal, Cadence, Airflow) требует сквозной интеграции пяти ключевых инженерных слоев:

1. **Reliability (Надежность):**
   - **Raft Replication:** Очередь задач реплицируется в консенсусный журнал. Смерть лидера не приводит к потере задач.
   - **Automatic Failover:** При падении воркера (отсутствие heartbeat за `HeartbeatTimeout`) лидер переводит задачу из `Running` в `Pending`.
   - **Fencing Tokens:** При переназначении задачи инкрементируется `FencingToken`. Если старый воркер очнется («зомби»), его результат будет отвергнут.
   - **Idempotency:** Каждая задача имеет неизменяемый `TaskID` в качестве ключа идемпотентности.

2. **Scaling (Масштабируемость):**
   - Горизонтальный пул воркеров с динамическим расширением.
   - Приоритизация очередей задач (High / Normal / Low).

3. **Observability (Наблюдаемость):**
   - Метрики: глубина очереди, утилизация воркеров, частота сбоев heartbeat.
   - Трассировка: `TraceID` пробрасывается от создания задачи через планировщик до воркера.

4. **Testing (Тестирование):**
   - Chaos Engineering: симуляция внезапной смерти лидера и воркеров во время выполнения.

## Решение по шагам

1. Создайте структуру `Task` с полями `ID`, `Status`, `WorkerID`, `FencingToken`, `LastHeartbeat`, `MaxRetries`.
2. Реализуйте планировщик `SchedulerCoordinator` с фоновым циклом проверки здоровья воркеров (`ReapDeadWorkers`).
3. При обнаружении сбоя воркера инкрементируйте `task.FencingToken++`, переведите статус в `Pending` и сбросьте `WorkerID`.
4. Реализуйте метод `AssignTask(workerID)` выдающий задачу с актуальным токеном.
5. Реализуйте метод `SubmitCompletion(taskID, workerID, token, result)` с проверкой токена.
6. Продемонстрируйте сценарий отказа первого воркера, успешного переназначения второму воркеру и отсечения зомби.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type TaskState string

const (
	StatePending   TaskState = "PENDING"
	StateRunning   TaskState = "RUNNING"
	StateCompleted TaskState = "COMPLETED"
	StateFailed    TaskState = "FAILED"
)

type ScheduledTask struct {
	ID            string
	Status        TaskState
	AssignedTo    string
	FencingToken  uint64
	LastHeartbeat time.Time
	Retries       int
	MaxRetries    int
	Result        string
}

type DistributedScheduler struct {
	mu               sync.Mutex
	tasks            map[string]*ScheduledTask
	heartbeatTimeout time.Duration
}

func NewDistributedScheduler(timeout time.Duration) *DistributedScheduler {
	return &DistributedScheduler{
		tasks:            make(map[string]*ScheduledTask),
		heartbeatTimeout: timeout,
	}
}

func (s *DistributedScheduler) SubmitTask(id string, maxRetries int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.tasks[id] = &ScheduledTask{
		ID:           id,
		Status:       StatePending,
		FencingToken: 1,
		MaxRetries:   maxRetries,
	}
}

// AssignTask назначает свободную задачу воркеру
func (s *DistributedScheduler) AssignTask(workerID string) (*ScheduledTask, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	for _, t := range s.tasks {
		if t.Status == StatePending {
			t.Status = StateRunning
			t.AssignedTo = workerID
			t.LastHeartbeat = time.Now()
			// Возвращаем копию
			taskCopy := *t
			return &taskCopy, nil
		}
	}
	return nil, errors.New("no pending tasks")
}

func (s *DistributedScheduler) Heartbeat(taskID, workerID string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	t, ok := s.tasks[taskID]
	if !ok {
		return errors.New("task not found")
	}
	if t.AssignedTo != workerID || t.Status != StateRunning {
		return errors.New("worker is not the current active executor")
	}
	t.LastHeartbeat = time.Now()
	return nil
}

// ReapDeadWorkers находит застрявшие задачи и переназначает их с новым Fencing Token
func (s *DistributedScheduler) ReapDeadWorkers() {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	for _, t := range s.tasks {
		if t.Status == StateRunning && now.Sub(t.LastHeartbeat) > s.heartbeatTimeout {
			fmt.Printf("[Leader] Worker %s timed out on task %s!\n", t.AssignedTo, t.ID)
			t.Retries++
			if t.Retries > t.MaxRetries {
				t.Status = StateFailed
				fmt.Printf("[Leader] Task %s exceeded max retries, marked FAILED\n", t.ID)
				continue
			}

			// Увеличиваем Fencing Token и возвращаем в очередь
			t.FencingToken++
			t.Status = StatePending
			t.AssignedTo = ""
			fmt.Printf("[Leader] Reassigned task %s with new Fencing Token %d\n", t.ID, t.FencingToken)
		}
	}
}

func (s *DistributedScheduler) CompleteTask(taskID, workerID string, token uint64, result string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	t, ok := s.tasks[taskID]
	if !ok {
		return errors.New("task not found")
	}

	if t.FencingToken != token {
		return fmt.Errorf("FENCING VIOLATION: Stale token %d (current active token: %d)", token, t.FencingToken)
	}

	if t.Status != StateRunning || t.AssignedTo != workerID {
		return fmt.Errorf("task not running by worker %s", workerID)
	}

	t.Status = StateCompleted
	t.Result = result
	return nil
}

func main() {
	scheduler := NewDistributedScheduler(150 * time.Millisecond)
	scheduler.SubmitTask("task-A1", 3)

	// 1. Воркер-1 берет задачу
	taskW1, err := scheduler.AssignTask("worker-1")
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Worker-1] Acquired task %s with Token %d\n", taskW1.ID, taskW1.FencingToken)

	// 2. Воркер-1 уходит в симуляцию сбоя сети (не шлет heartbeat 250мс)
	time.Sleep(250 * time.Millisecond)

	// 3. Лидер детектирует сбой
	scheduler.ReapDeadWorkers()

	// 4. Воркер-2 забирает переназначенную задачу
	taskW2, err := scheduler.AssignTask("worker-2")
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Worker-2] Acquired task %s with Token %d\n", taskW2.ID, taskW2.FencingToken)

	// Воркер-2 успешно завершает
	err = scheduler.CompleteTask(taskW2.ID, "worker-2", taskW2.FencingToken, "SUCCESS_PAYLOAD")
	fmt.Printf("[Worker-2] Completed task: err=%v\n", err)

	// 5. Оживший воркер-1 пытается прислать результат со старым токеном
	err = scheduler.CompleteTask(taskW1.ID, "worker-1", taskW1.FencingToken, "STALE_RESULT")
	fmt.Printf("[Worker-1] Submission result: %v\n", err)

	_ = context.Background()
}
```

## Под капотом

В производственных планировщиках (например, Kubernetes Kubelet -> Control Plane) статус ноды обновляется через Lease объекты в пространстве `kube-node-lease`. Каждые 10 секунд Kubelet обновляет свой Lease. Если за 40 секунд аренда не обновилась, NodeLifecycleController помечает ноду как `NotReady` и инициирует процедуру выселения подов (Pod Eviction), переназначая поды на здоровые ноды.

## Подводные камни

1. Слишком агрессивный таймаут heartbeat: временная нагрузка на сеть может спровоцировать ложное переназначение («шторм переназначений»).
2. Отсутствие ограничения максимального числа повторов (`MaxRetries`): упавшая задача-«отравитель» (poison pill) может уложить весь пул воркеров по цепочке.

## На собеседовании

«Как предотвратить дублирование платежа, если воркер упал в момент, когда платежный шлюз уже списал деньги, но до отправки отчета в планировщик?»
Ответ: Задача обязана использовать глобальный ключ идемпотентности (Idempotency Key = `TaskID`). Новый воркер, получив переназначенную задачу, отправляет запрос в шлюз с тем же ключом идемпотентности. Шлюз возвращает статус уже проведенной транзакции без повторного списания.
