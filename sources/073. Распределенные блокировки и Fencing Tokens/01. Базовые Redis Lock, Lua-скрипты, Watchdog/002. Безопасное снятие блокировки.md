# Безопасное снятие блокировки: Lua-скрипт и защита от удаления чужого ключа

## Условие

2. **Безопасное снятие блокировки (Lua-скрипт)**: Клиент должен удалять *только свою* блокировку. Если просто сделать `GET` и `DEL`, то между ними другой процесс может перехватить ключ (Race Condition). ### Исходная формулировка

**Безопасное снятие блокировки (Lua-скрипт)**: Клиент должен удалять *только свою* блокировку. Если просто сделать `GET` и `DEL`, то между ними другой процесс может перехватить ключ (Race Condition). Напиши Lua-скрипт `if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`. Выполни его через `client.Eval()`.

## Теория

Проблема наивного снятия блокировки через `DEL key`:
1. Клиент \(A\) захватил блокировку с \(TTL = 5\text{ с}\).
2. Клиент \(A\) выполняет бизнес-логику дольше 5 секунд (например, из-за медленного SQL-запроса).
3. TTL истекает, Redis автоматически удаляет ключ.
4. Клиент \(B\) успешно захватывает блокировку с тем же именем.
5. Клиент \(A\) просыпается и наивно вызывает `DEL key`.
6. **Катастрофа**: Клиент \(A\) удаляет блокировку, принадлежащую клиенту \(B\)! Теперь третий клиент \(C\) может захватить лок, и \(B\) и \(C\) окажутся в критической секции одновременно!

Решение — атомарный CAS (Compare-And-Delete) через Lua-скрипт:
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```
Redis исполняет Lua-скрипты строго атомарно в основном потоке событий (Event Loop), исключая любые гонки между `GET` и `DEL`.

## Решение по шагам

1. Опишите каноничный Lua-скрипт безопасного освобождения блокировки.
2. Создайте структуру `RedisClient` с поддержкой метода `Eval` для исполнения Lua.
3. Смоделируйте случай истечения срока аренды и попытки снятия чужой блокировки.
4. Убедитесь, что скрипт возвращает `0` (отказ) при несовпадении токена и не удаляет чужой ключ.
5. Покажите успешное удаление (`return 1`), если токен совпал.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

const UnlockLuaScript = `
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
`

var (
	ErrLockReleaseFailed = errors.New("lock release failed: token mismatch or lock expired")
)

type MemoryRedis struct {
	mu   sync.Mutex
	data map[string]string
}

func NewMemoryRedis() *MemoryRedis {
	return &MemoryRedis{data: make(map[string]string)}
}

// Simulates Redis Lua engine execution
func (m *MemoryRedis) EvalUnlock(key, token string) (int, error) {
	m.mu.Lock()
	defer m.mu.Unlock()

	currentVal, exists := m.data[key]
	if !exists {
		return 0, nil // Key does not exist
	}

	// Compare-and-delete
	if currentVal == token {
		delete(m.data, key)
		return 1, nil // Successfully deleted
	}

	return 0, nil // Token mismatch
}

type LockHandle struct {
	redis *MemoryRedis
	key   string
	token string
}

func (l *LockHandle) Release() error {
	res, err := l.redis.EvalUnlock(l.key, l.token)
	if err != nil {
		return err
	}
	if res == 0 {
		return ErrLockReleaseFailed
	}
	return nil
}

func main() {
	redis := NewMemoryRedis()
	lockKey := "lock:billing:user:123"

	// Step 1: Worker A acquires lock with token "token-A"
	redis.data[lockKey] = "token-A"
	handleA := &LockHandle{redis: redis, key: lockKey, token: "token-A"}

	// Step 2: Simulate timeout: Worker B acquires lock with "token-B"
	fmt.Println("--- Simulating Lock Theft / Expiration ---")
	redis.data[lockKey] = "token-B" // Worker B now owns the lock!

	// Step 3: Worker A wakes up and attempts to release
	fmt.Println("Worker A attempting to unlock (with token-A)...")
	errA := handleA.Release()
	if errors.Is(errA, ErrLockReleaseFailed) {
		fmt.Printf("🛡️ Worker A unlock REJECTED: %v\n", errA)
	}

	// Verify Worker B's lock was NOT touched!
	fmt.Printf("Current lock owner in Redis: '%s' (Worker B is safe!)\n", redis.data[lockKey])

	// Step 4: Worker B releases with valid token
	handleB := &LockHandle{redis: redis, key: lockKey, token: "token-B"}
	if err := handleB.Release(); err == nil {
		fmt.Println("✅ Worker B successfully unlocked with token-B!")
	}
}
```

ℹ️ Безопасное снятие блокировки через атомарный Compare-And-Delete скрипт

## Под капотом

Почему Lua-скрипты в Redis атомарны:
Redis исполняет команды в однопоточном ядре (Single-Threaded Reactor). Когда вызывается `EVAL` или `EVALSHA`, скрипт монопольно блокирует обработку всех входящих сетевых команд до полного завершения своего выполнения. Никакая другая команда `GET`, `SET` или `DEL` не может вклиниться между строками скрипта, что математически исключает гонку данных.

## Подводные камни

- **Тяжелые циклы в Lua-скриптах**: Выполнение длительных вычислений в Lua заморозит Redis на время работы скрипта, приведя к таймаутам всех остальных запросов. Скрипт разблокировки обязан содержать ровно один `if` и завершаться за микросекунды.
- **Отсутствие кеширования через `SCRIPT LOAD`**: Посылка полного текста скрипта на каждый `Unlock` тратит сетевую полосу. В продакшене используют `EVALSHA`.

## На собеседовании

В Wildberries и Авито на системном интервью часто спрашивают: *«Что произойдет, если в Go при освобождении Redis-блокировки сделать `v := client.Get(ctx, key); if v == token { client.Del(ctx, key) }` без Lua?»*
**Ответ**: Возникнет классическое состояние гонки Time-of-Check to Time-of-Use (TOCTOU). Если сразу после вызова `Get` поток задержится на сетевом раундтрипе или сборке мусора, а TTL ключа истечет, другой микросервис успеет захватить блокировку. Затем запоздавший вызов `Del` удалит уже чужой ключ! Из-за этого третий микросервис войдет в критическую секцию параллельно со вторым, разрушив инвариант взаимного исключения. Поэтому снятие обязано быть строго атомарным через Lua-скрипт.
