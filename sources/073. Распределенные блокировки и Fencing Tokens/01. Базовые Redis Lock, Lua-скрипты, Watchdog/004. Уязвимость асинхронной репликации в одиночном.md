# Уязвимость асинхронной репликации в одиночном Redis и введение в алгоритм Redlock

## Условие

4. **Уязвимость одиночного Redis (Redlock)**: Redis кластер асинхронен. Ты взял лок на мастере, мастер упал, данные не успели реплицироваться на слейв, слейв стал мастером. Другой сервис берет лок на те же данные! Изучи алгоритм **Redlock**. Установи библиотеку `github.com/go-redsync/redsync/v4`.

### Исходная формулировка

**Уязвимость одиночного Redis (Redlock)**: Redis кластер асинхронен. Ты взял лок на мастере, мастер упал, данные не успели реплицироваться на слейв, слейв стал мастером. Другой сервис берет лок на те же данные! Изучи алгоритм **Redlock**. Установи библиотеку `github.com/go-redsync/redsync`. Подними 3 независимых Redis-сервера и настрой блокировку, требующую кворума (минимум 2 из 3 серверов должны подтвердить лок).

## Теория

Архитектурный изъян связки Redis Master-Replica для распределенных блокировок:
Репликация в Redis **асинхронная (Asynchronous Replication)**.

Хронология катастрофы при аварийном переключении (Failover):
1. Клиент \(A\) захватывает блокировку `lock:order:100` на Мастере Redis.
2. Мастер отвечает клиенту `OK`.
3. Мастер аварийно падает (Kernel Panic, сбой питания) **до того**, как успел переслать реплику команды `SET` на Slave.
4. Sentinel или Redis Cluster повышает Slave до статуса нового Master.
5. В новом Мастере ключ `lock:order:100` **отсутствует**!
6. Клиент \(B\) запрашивает блокировку `lock:order:100` и успешно получает ее на новом Мастере.
7. **Взаимное исключение полностью разрушено**: Клиенты \(A\) и \(B\) одновременно владеют одной и той же блокировкой!

Решение Сальваторе Санфилиппо (Antirez) — алгоритм **Redlock**:
Вместо связки Master-Replica разворачиваются **\(N\) абсолютно независимых инстансов Redis** (обычно \(N=5\), без репликации и без общего состояния).
Клиент считается захватившим блокировку, если он смог успешно получить ее на **большинстве узлов** (\(\lfloor N/2 \rfloor + 1 = 3\) из 5) за время, существенно меньшее, чем общий TTL.

## Решение по шагам

1. Создайте симулятор кластера из 5 независимых инстансов Redis.
2. Реализуйте алгоритм сбора кворума Redlock: последовательный опрос независимых инстансов с жестким сетевым таймаутом.
3. Рассчитайте общее затраченное время (Elapsed Time) и проверьте, превышает ли оставшийся срок аренды допустимый порог.
4. Продемонстрируйте сценарий компенсационного отката (Rollback Unlock) всех узлов при недоборе кворума.
5. Проанализируйте устойчивость к падению 2 узлов из 5.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"time"
)

type SingleRedisInstance struct {
	ID    int
	Alive bool
	store map[string]string
	mu    sync.Mutex
}

func (inst *SingleRedisInstance) SetNX(key, token string) bool {
	inst.mu.Lock()
	defer inst.mu.Unlock()
	if !inst.Alive {
		return false
	}
	if _, ok := inst.store[key]; ok {
		return false
	}
	inst.store[key] = token
	return true
}

func (inst *SingleRedisInstance) Del(key, token string) {
	inst.mu.Lock()
	defer inst.mu.Unlock()
	if inst.Alive && inst.store[key] == token {
		delete(inst.store, key)
	}
}

type RedlockCoordinator struct {
	instances []*SingleRedisInstance
	quorum    int
}

func NewRedlockCoordinator(n int) *RedlockCoordinator {
	instances := make([]*SingleRedisInstance, n)
	for i := 0; i < n; i++ {
		instances[i] = &SingleRedisInstance{
			ID:    i + 1,
			Alive: true,
			store: make(map[string]string),
		}
	}
	return &RedlockCoordinator{
		instances: instances,
		quorum:    n/2 + 1,
	}
}

func (r *RedlockCoordinator) Acquire(key string, ttl time.Duration) (string, error) {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	token := hex.EncodeToString(b)

	startTime := time.Now()
	successCount := 0

	for _, inst := range r.instances {
		if inst.SetNX(key, token) {
			successCount++
		}
	}

	elapsed := time.Since(startTime)
	validityTime := ttl - elapsed

	// Quorum check and validity check
	if successCount >= r.quorum && validityTime > 0 {
		fmt.Printf("✅ Redlock Acquired! Nodes agreed: %d/%d (Elapsed: %v, Validity: %v)\n",
			successCount, len(r.instances), elapsed, validityTime)
		return token, nil
	}

	// Compensation: Unlock all acquired nodes on failure
	fmt.Printf("❌ Redlock Failed (only %d/%d acks). Rolling back...\n", successCount, len(r.instances))
	for _, inst := range r.instances {
		inst.Del(key, token)
	}
	return "", errors.New("failed to acquire redlock quorum")
}

func main() {
	coordinator := NewRedlockCoordinator(5) // 5 independent nodes, quorum = 3

	fmt.Println("--- 1. Normal Quorum Acquisition (All 5 Alive) ---")
	token, err := coordinator.Acquire("lock:payment:777", 2*time.Second)
	if err != nil {
		panic(err)
	}

	fmt.Println("\n--- 2. Simulating Failure of 2 Nodes (Quorum 3/5 still works) ---")
	coordinator.instances[0].Alive = false
	coordinator.instances[1].Alive = false

	_, err = coordinator.Acquire("lock:payment:888", 2*time.Second)
	if err != nil {
		fmt.Println("Error:", err)
	}

	fmt.Println("\n--- 3. Simulating Failure of 3 Nodes (Quorum 2/5 FAILS) ---")
	coordinator.instances[2].Alive = false // 3 dead, only 2 alive

	_, err = coordinator.Acquire("lock:payment:999", 2*time.Second)
	if err != nil {
		fmt.Printf("Correctly failed: %v\n", err)
	}
}
```

ℹ️ Кворумная модель алгоритма Redlock на 5 независимых инстансах Redis

## Под капотом

Математика Redlock:
- Время валидности блокировки: \(\text{Validity} = \text{TTL} - \Delta t - \text{ClockDrift}\), где \(\Delta t\) — время опроса всех инстансов, а \(\text{ClockDrift}\) — допустимая погрешность дрейфа системных часов узлов (обычно \(1-2\%\) от TTL).
- Если клиент потратил на опрос узлов больше времени, чем \(\text{TTL}\), блокировка считается недействительной, и инициируется откат.

## Подводные камни

- **Запуск Redlock на нодах одного физического сервера**: Если все 5 инстансов крутятся на одной виртуальной машине, падение гипервизора положит все 5 нод одновременно. Ноды обязаны жить на изолированном железе в разных зонах доступности.
- **Быстрый рестарт узла без персистентности**: Если нода сбросила лог из памяти при перезагрузке, она мгновенно выдаст повторную блокировку.

## На собеседовании

В Яндексе и Авито на позицию Principal/Staff Engineer часто задают вопрос: *«В чем суть знаменитых дебатов Мартина Клеппмана и Сальваторе Санфилиппо о надежности Redlock?»*
**Ответ**: Мартин Клеппман (автор «Designing Data-Intensive Applications») доказал, что Redlock **не может гарантировать взаимное исключение для безопасности данных**:
1. **Clock Drift**: Алгоритм опирается на синхронность часов. Скачок времени NTP может досрочно сбросить ключ на одной ноде.
2. **Паузы процессов (GC Pause)**: Клиент \(A\) получил лок, завис на 10 сек, лок истек, клиент \(B\) взял лок. Клиент \(A\) отвис и пишет в БД одновременно с \(B\).
Клеппман резюмировал: если блокировка нужна только для эффективности (избежать лишней работы), Redlock избыточен (хватит 1 Redis). А если блокировка нужна для корректности (чтобы не испортить балансы в БД), Redlock недостаточен — требуются **Fencing Tokens**.
