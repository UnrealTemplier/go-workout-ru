# Ужас Split-Brain при паузах сборщика мусора (GC-pause) и задержках гипервизора

## Условие

5. **Ужас Split-Brain (Пауза сборщика мусора)**: *Мысленный и практический тест.* Воркер А взял лок на 5 секунд. Внезапно Go ловит тяжелую GC-паузу (или гипервизор ОС фризит виртуалку) на 6 секунд. Лок в Redis истек. Воркер Б берет лок и пишет в БД. Воркер А просыпается и тоже пишет в БД! Данные повреждены. Смоделируй этот сценарий.

### Исходная формулировка

**Ужас Split-Brain (Пауза сборщика мусора)**: *Мысленный и практический тест.* Воркер А взял лок на 5 секунд. Внезапно Go ловит тяжелую GC-паузу (или гипервизор ОС фризит виртуалку) на 6 секунд. Лок в Redis истек. Воркер Б берет лок и пишет в БД. Тут Воркер А "отвисает" и ТОЖЕ пишет в БД (он же уверен, что лок его!). Осознай, почему *любые* TTL-локи уязвимы к рассинхронизации времени.

## Теория

Фундаментальная иллюзия распределенных блокировок:
*«Если я успешно захватил блокировку, я защищен от одновременной записи в базу данных на все время выполнения критической секции».*

Почему это утверждение ложно:
В асинхронных распределенных системах время относительно, а процессы подвержены недетерминированным задержкам:
- **Длительные паузы Stop-The-World GC** (в Go, Java, Python).
- **Свопинг памяти на диск (Page Fault / OOM thrashing)**.
- **Заморозка процесса гипервизором** при миграции виртуальной машины (VM live migration).
- **Сетевой лаг (TCP retransmissions)** при отправке запроса в БД.

Сценарий катастрофы (Ghost Write / Zombie Worker):
1. Воркер \(A\) получает лок на \(5\text{ с}\).
2. Воркер \(A\) зависает на \(6\text{ с}\) (GC Pause).
3. Время \(TTL = 5\text{ с}\) истекает в Redis.
4. Воркер \(B\) захватывает лок на \(5\text{ с}\) и записывает файл `data.v2` в хранилище.
5. Воркер \(A\) наконец «отвисает». Он не знает, что спал! Он считает, что лок еще у него.
6. Воркер \(A\) перезаписывает файл устаревшими данными `data.v1`.
7. **Результат**: Повреждение данных (Silent Data Corruption).

## Решение по шагам

1. Создайте симулятор разделяемого хранилища `SharedStorage` (например, целевую базу данных).
2. Запустите Воркера \(A\), который берет блокировку с TTL 100 мс.
3. Сымитируйте GC-паузу Воркера \(A\) длительностью 250 мс через `time.Sleep`.
4. В этот промежуток времени запустите Воркера \(B\), который видит, что лок свободен, захватывает его и сохраняет запись со статусом «Approved».
5. Продемонстрируйте, как проснувшийся Воркер \(A\) затирает изменения Воркера \(B\), возвращая состояние «Declined».

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type DatabaseRecord struct {
	OrderID   string
	Status    string
	UpdatedBy string
}

type TargetDatabase struct {
	mu     sync.Mutex
	record DatabaseRecord
}

func (db *TargetDatabase) Write(status, author string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.record.Status = status
	db.record.UpdatedBy = author
	fmt.Printf("[DB Write] Status='%s', Author='%s'\n", status, author)
}

type FlakyLockStore struct {
	mu     sync.Mutex
	holder string
	exp    time.Time
}

func (l *FlakyLockStore) Acquire(worker string, ttl time.Duration) bool {
	l.mu.Lock()
	defer l.mu.Unlock()

	if time.Now().Before(l.exp) {
		return false
	}
	l.holder = worker
	l.exp = time.Now().Add(ttl)
	return true
}

func main() {
	db := &TargetDatabase{record: DatabaseRecord{OrderID: "ord-42", Status: "Created"}}
	lockStore := &FlakyLockStore{}
	var wg sync.WaitGroup

	fmt.Println("=== Simulating Distributed Split-Brain via GC Pause ===")

	// 1. Worker A acquires lock with short TTL (100ms)
	lockStore.Acquire("Worker-A", 100*time.Millisecond)
	fmt.Println("[Lock Manager] Worker-A acquired lock with TTL = 100ms")

	// Worker A enters critical section, but immediately freezes (Heavy GC STW pause)
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("[Worker-A] ⏸️ FREEZING: Simulating 300ms Stop-The-World GC pause...")
		time.Sleep(300 * time.Millisecond) // GC freeze exceeds 100ms TTL!

		// Worker A wakes up and blindly writes to DB, assuming it still owns the lock!
		fmt.Println("[Worker-A] ☀️ Woke up! Blindly writing to DB without knowing TTL expired...")
		db.Write("Declined (Old Decision)", "Worker-A")
	}()

	// 2. While Worker-A is sleeping, TTL expires (after 100ms). Worker B acquires lock!
	time.Sleep(150 * time.Millisecond)
	fmt.Println("\n[Lock Manager] TTL expired in Redis! Lock is now free.")
	if lockStore.Acquire("Worker-B", 200*time.Millisecond) {
		fmt.Println("[Lock Manager] Worker-B acquired lock legitimately!")
		// Worker B performs critical update
		db.Write("Approved & Paid", "Worker-B")
	}

	wg.Wait()

	fmt.Println("\n--- FINAL DATABASE STATE ---")
	fmt.Printf("Final Status: '%s', Last Author: '%s'\n", db.record.Status, db.record.UpdatedBy)
	if db.record.UpdatedBy == "Worker-A" {
		fmt.Println("💥 DATA CORRUPTION DETECTED: Zombie Worker-A overwrote legitimate update from Worker-B!")
	}
}
```

## Под капотом

Почему таймеры внутри процесса не спасают:
Разработчики часто пытаются проверить `if time.Now().Before(deadline)` перед записью в БД.
Но в многозадачной ОС пауза может произойти **между этой проверкой и реальной отправкой TCP-пакета в сокет базы данных**:
```go
if time.Now().Before(deadline) {
    // <-- ИМЕННО ЗДЕСЬ СЛУЧАЕТСЯ ПАУЗА GC НА 10 СЕКУНД!
    db.Exec("UPDATE ...")
}
```
Клиент в принципе не может полагаться на локальные часы для синхронизации с удаленной БД.

## Подводные камни

- **Попытка решить проблему увеличением TTL**: Увеличение TTL до 10 минут просто увеличивает задержку восстановления при аварии процесса, но не устраняет проблему принципиально (гипервизор может заморозить VM на любое время).
- **Слепое доверие коду `Unlock()`**: Ошибочно полагать, что если в коде есть `defer Unlock()`, параллельной записи быть не может.

## На собеседовании

В Ozon и Wildberries на вопрос: *«Может ли распределенный мьютекс в Redis гарантировать 100% защиту от двойного списания денег?»*
**Ответ**: **Категорически нет!** Из-за пауз сборщика мусора, сетевого джиттера или зависаний ОС процесс неизбежно может превратиться в «зомби» и отправить запись в базу данных после истечения TTL аренды. Распределенный лок в Redis — это лишь оптимизация, снижающая нагрузку. Единственной истинной защитой от повреждения данных является валидация монотонных токенов ограждения (**Fencing Tokens**) на стороне самой базы данных.
