# Продление времени аренды (Watchdog Pattern): фоновая горутина поддержания блокировки

## Условие

3. **Продление TTL (Watchdog Pattern)**: Бизнес-логика занимает больше 10 секунд, но ставить TTL = 1 час опасно (вдруг воркер упал). Напиши фоновую горутину ("сторожевой пес"). Пока основная горутина работает, "пес" каждые 3 секунды отправляет в Redis команду `EXPIRE resource_name 10`.

### Исходная формулировка

**Продление TTL (Watchdog Pattern)**: Бизнес-логика занимает больше 10 секунд, но ставить TTL = 1 час опасно (вдруг воркер упал). Напиши фоновую горутину ("сторожевой пес"). Пока основная горутина работает, "пес" каждые 3 секунды отправляет в Redis команду на продление TTL (`PEXPIRE`) текущего лока. При выходе из функции убивай "пса" через `context`.

## Теория

Проблема выбора оптимального TTL блокировки:
- **Маленький TTL (например, 5–10 секунд)**: риск того, что тяжелая операция (транскодирование видео, пакетная генерация счетов) не уложится в интервал, ключ удалится, и возникнет параллельное выполнение.
- **Большой TTL (например, 1 час)**: если процесс упадет по `SIGKILL`, ресурс останется заблокированным на целый час, останавливая пайплайн.

Паттерн Watchdog («Сторожевой пёс»):
1. Блокировка берется с коротким TTL (например, \(10\text{ с}\)).
2. Запускается фоновая горутина-хранитель (Watchdog).
3. С интервалом \(\text{TTL}/3\) (каждые 3 секунды) Watchdog атомарно продлевает аренду ключа через Redis `PEXPIRE` только в том случае, если токен все еще принадлежит текущему владельцу:
   ```lua
   if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("pexpire", KEYS[1], ARGV[2])
   else
       return 0
   end
   ```
4. Если воркер завершает работу или аварийно падает, горутина Watchdog останавливается, и ключ безопасно удаляется через несколько секунд.

## Решение по шагам

1. Создайте структуру `AutoRenewLock` с каналами управления жизненным циклом `stopCh`.
2. Реализуйте метод `startWatchdog`, запускающий периодический `time.Ticker` с интервалом обновления \(\text{TTL}/3\).
3. Реализуйте безопасное продление срока аренды только для своего токена.
4. Продемонстрируйте выполнение бизнес-логики, длящейся дольше базового TTL, с непрерывным автопродлением.
5. Убедитесь в корректной остановке сторожевого таймера при вызове `Unlock()`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type HeartbeatStore struct {
	mu   sync.Mutex
	data map[string]string
	exp  map[string]time.Time
}

func NewHeartbeatStore() *HeartbeatStore {
	return &HeartbeatStore{
		data: make(map[string]string),
		exp:  make(map[string]time.Time),
	}
}

func (s *HeartbeatStore) RefreshTTL(key, token string, ttl time.Duration) bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	if val, ok := s.data[key]; ok && val == token {
		s.exp[key] = time.Now().Add(ttl)
		return true
	}
	return false
}

type WatchdogLock struct {
	store   *HeartbeatStore
	key     string
	token   string
	ttl     time.Duration
	stopCh  chan struct{}
	stopped chan struct{}
}

func NewWatchdogLock(store *HeartbeatStore, key, token string, ttl time.Duration) *WatchdogLock {
	l := &WatchdogLock{
		store:   store,
		key:     key,
		token:   token,
		ttl:     ttl,
		stopCh:  make(chan struct{}),
		stopped: make(chan struct{}),
	}
	go l.runWatchdog()
	return l
}

func (l *WatchdogLock) runWatchdog() {
	defer close(l.stopped)
	// Refresh interval is TTL / 3
	ticker := time.NewTicker(l.ttl / 3)
	defer ticker.Stop()

	for {
		select {
		case <-l.stopCh:
			fmt.Println("[Watchdog] Work finished. Stopping heartbeat loop.")
			return
		case <-ticker.C:
			ok := l.store.RefreshTTL(l.key, l.token, l.ttl)
			if ok {
				fmt.Printf("[Watchdog 🐶] Heartbeat sent: TTL refreshed for key '%s'\n", l.key)
			} else {
				fmt.Printf("[Watchdog ⚠️] Refresh failed: lock lost or token changed!\n")
				return
			}
		}
	}
}

func (l *WatchdogLock) Unlock() {
	close(l.stopCh)
	<-l.stopped // Wait for watchdog to terminate cleanly
	l.store.mu.Lock()
	delete(l.store.data, l.key)
	delete(l.store.exp, l.key)
	l.store.mu.Unlock()
	fmt.Println("Lock successfully released from Redis.")
}

func main() {
	store := NewHeartbeatStore()
	key := "lock:video:export"
	token := "worker-uuid-42"

	store.mu.Lock()
	store.data[key] = token
	store.exp[key] = time.Now().Add(300 * time.Millisecond) // Short 300ms initial TTL
	store.mu.Unlock()

	// Initial lock has only 300ms TTL
	lock := NewWatchdogLock(store, key, token, 300*time.Millisecond)

	fmt.Println("--- Starting long business job (takes 400ms) ---")
	// Business job takes 400ms (longer than initial 300ms TTL!)
	time.Sleep(400 * time.Millisecond)

	// Verify key is STILL alive because of Watchdog!
	store.mu.Lock()
	stillAlive := time.Now().Before(store.exp[key])
	store.mu.Unlock()
	fmt.Printf("Is lock still valid after 400ms? %t (Saved by Watchdog!)\n\n", stillAlive)

	lock.Unlock()
}
```

ℹ️ Реализация паттерна Watchdog для автопродления срока распределенной аренды

## Под капотом

Как работает Watchdog в Java Redisson и Go redsync:
- В Redisson Watchdog по умолчанию устанавливает `lockWatchdogTimeout = 30000` (30 сек) и делает попытку продления каждые 10 секунд.
- При получении сигнала отмены контекста (`ctx.Done()`) или вызове `Unlock()` сторожевой таймер немедленно останавливается, избегая утечки сетевых запросов.

## Подводные камни

- **Утечка горутин Watchdog**: Если при возникновении ошибки в бизнес-логике (например, паника или `return err`) забыть вызвать `Unlock()` или закрыть `stopCh`, горутина сторожевого пса будет жить вечно и бесконечно продлевать лок в Redis. Всегда используйте `defer lock.Unlock()`!
- **Продление чужого ключа**: Продление TTL ОБЯЗАНО проверять соответствие токена через Lua-скрипт, иначе можно случайно продлить лок, уже перехваченный другим воркером.

## На собеседовании

В Касперском и Т-Банке часто спрашивают: *«Что произойдет со сторожевым псом (Watchdog), если в Go рантайме произойдет задержка Stop-The-World GC или гипервизор заморозит виртуальную машину?»*
**Ответ**: Горутина Watchdog будет заморожена вместе со всем процессом Go. Пока процесс спит, таймер не сработает, сетевой запрос `EXPIRE` не отправится, и TTL ключа в Redis истечет. Другой воркер перехватит блокировку. Когда замороженный воркер очнется, он ошибочно продолжит считать себя владельцем ресурса! Это ключевая уязвимость Redis-локов, доказывающая необходимость использования **Fencing Tokens**.
