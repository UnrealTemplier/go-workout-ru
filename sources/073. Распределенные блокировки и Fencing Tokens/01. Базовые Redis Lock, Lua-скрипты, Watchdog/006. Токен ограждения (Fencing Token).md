# Токен ограждения (Fencing Token): архитектурное решение проблемы зомби-воркеров

## Условие

6. **Fencing Token (Защита от Split-Brain)**: Решение проблемы 835. Токен ограждения (Fencing) — это монотонно возрастающее число. В Redis/etcd при взятии блокировки получай инкрементный токен (например, `Token: 42`). Воркер передает этот токен в БД при записи. Если база видела токен больше, запрос отклоняется.

### Исходная формулировка

**Fencing Token (Защита от Split-Brain)**: Решение проблемы 835. Токен ограждения (Fencing) — это монотонно возрастающее число. В Redis/etcd при взятии блокировки получай инкрементный токен (например, `Token: 42`). Воркер передает этот токен в БД вместе с запросом на изменение данных.

## Теория

Концепция токена ограждения (Fencing Token), предложенная Мартином Клеппманом:

Принцип работы:
1. Координатор блокировок (Redis, etcd, Consul) при каждом успешном захвате ресурса генерирует **строго монотонно возрастающее число (Monotonic Sequence Number)**:
   - Воркер \(A\) получает лок и `FencingToken = 42`.
   - Воркер \(B\) при следующем захвате получает `FencingToken = 43`.
2. Целевое хранилище (PostgreSQL, S3, файловая система) хранит текущее максимальное значение примененного токена: `last_fencing_token`.
3. Каждый пишущий запрос обязан передавать токен: `UPDATE target SET val = ?, token = 42 WHERE token < 42`.
4. Если Воркер \(A\) завис из-за GC-паузы, а Воркер \(B\) уже применил `Token = 43`, то запоздалый запрос от Воркера \(A\) с `Token = 42` будет **отклонен базой данных**, так как \(42 < 43\).

Таким образом, безопасность (Safety) гарантируется целевым ресурсом независимо от сетевых задержек и пауз воркеров.

## Решение по шагам

1. Создайте сервис генерации монотонных токенов `FencingLockService` с использованием атомарного инкремента (`INCR`).
2. Опишите структуру хранилища `FencedStorage`, требующего передачу токена при каждой записи.
3. Реализуйте проверку инварианта: `newToken > currentToken`.
4. Смоделируйте захват токенов: Воркер 1 получает токен 101, Воркер 2 получает токен 102.
5. Продемонстрируйте, как запись Воркера 2 принимается, а запоздалая запись Воркера 1 с токеном 101 отклоняется.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
)

var (
	ErrStaleFencingToken = errors.New("write rejected: fencing token is stale or outdated")
)

type FencedLockService struct {
	tokenCounter uint64
}

func (s *FencedLockService) AcquireLock() uint64 {
	// Monotonically increasing token counter
	return atomic.AddUint64(&s.tokenCounter, 1)
}

type FencedStorage struct {
	mu               sync.Mutex
	data             string
	lastFencingToken uint64
}

func (s *FencedStorage) Write(payload string, token uint64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// CRITICAL INVARIANT: Token must be strictly greater than last seen token
	if token <= s.lastFencingToken {
		return fmt.Errorf("%w (incoming token: %d, current highest token: %d)",
			ErrStaleFencingToken, token, s.lastFencingToken)
	}

	s.data = payload
	s.lastFencingToken = token
	fmt.Printf("✅ Storage accepted write '%s' with Fencing Token %d\n", payload, token)
	return nil
}

func main() {
	lockService := &FencedLockService{tokenCounter: 100}
	storage := &FencedStorage{}

	// 1. Worker A acquires lock and receives Token 101
	tokenA := lockService.AcquireLock()
	fmt.Printf("[Lock Service] Worker A acquired lock with Token: %d\n", tokenA)

	// Worker A freezes due to GC/network lag...

	// 2. Worker B acquires lock and receives Token 102
	tokenB := lockService.AcquireLock()
	fmt.Printf("[Lock Service] Worker B acquired lock with Token: %d\n", tokenB)

	// 3. Worker B writes to storage first
	if err := storage.Write("State V2: Confirmed by Worker B", tokenB); err != nil {
		fmt.Println("Worker B error:", err)
	}

	// 4. Zombie Worker A wakes up and attempts to write with outdated Token 101
	fmt.Println("\n[Zombie Worker A] Woke up. Attempting write with Token 101...")
	errA := storage.Write("State V1: Old Data from Worker A", tokenA)
	if errA != nil {
		fmt.Printf("🛡️ Rejected stale write: %v\n", errA)
	}

	// 5. Verify final storage state
	fmt.Printf("\nFinal Storage Content: '%s' (Highest Token: %d)\n",
		storage.data, storage.lastFencingToken)
}
```

## Под капотом

Где брать монотонный Fencing Token:
- В **etcd**: это встроенное свойство движка MVCC — ревизия создания ключа (`CreateRevision`) или глобальная ревизия `Header.Revision`. При каждом изменении etcd увеличивает 64-битный счетчик, гарантируя строгую монотонность.
- В **ZooKeeper**: это `zxid` транзакции или монотонный счетчик `cversion`.
- В **Redis**: генерация через команду `INCR lock:counter:resource`.

## Подводные камни

- **Использование Unix Timestamp вместо монотонного счетчика**: Системные часы могут идти назад при корректировке NTP (Time Step / Slew), что приведет к коллизиям токенов. Fencing Token обязан быть монотонным числом, а не временем.
- **Генерация токена клиентом**: Клиенты не могут сами генерировать токен, так как их часы не синхронизированы.

## На собеседовании

В Яндекс Облаке и Авито часто спрашивают: *«Как быть, если целевая система (например, сторонний API или S3 бакет) не поддерживает валидацию Fencing Tokens?»*
**Ответ**: Если целевой сервис не может валидировать токены (dumb storage), распределенная блокировка не способна на 100% гарантировать безопасность данных при сбоях сети или GC-паузах. В таких случаях перед сторонним API ставят промежуточный слой (BFF / Proxy / State Service), поддерживающий условные транзакции (Conditional Writes / ETag / CAS), либо используют распределенные транзакции на базе двухфазного коммита (2PC) / Raft.
