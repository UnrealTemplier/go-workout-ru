# Проблема гонки без распределенных блокировок: двойное списание средств и Race Condition

## Условие

12. **Проблема без distributed locks**: Два инстанса одновременно обрабатывают один order. Результат: double payment, data corruption. Смоделируйте эту проблему на практике.

### Исходная формулировка

**Проблема без distributed locks**: Два инстанса одновременно обрабатывают один order. Результат: double payment, data corruption.

## Теория

Классическая проблема несогласованного чтения-модификации-записи (Read-Modify-Write Race Condition):

Хронология инцидента двойного списания (Double Spending / Double Payment):
1. Баланс пользователя в хранилище: \(1000\text{ руб}\).
2. Клиент нажимает кнопку «Оплатить заказ на 800 руб» дважды или вебхук платежной системы дублируется в две очереди RabbitMQ.
3. **Инстанс 1** вычитывает баланс: `balance = 1000`. Проверяет `1000 >= 800` (OK).
4. **Инстанс 2** параллельно вычитывает баланс: `balance = 1000`. Проверяет `1000 >= 800` (OK).
5. **Инстанс 1** списывает средства: `1000 - 800 = 200`. Записывает `balance = 200`. Отправляет товар.
6. **Инстанс 2** списывает средства: `1000 - 800 = 200`. Записывает `balance = 200`. Отправляет второй товар!
7. **Финансовый ущерб**: Списано \(800\text{ руб}\), а отправлено товаров на \(1600\text{ руб}\)! Баланс должен был стать отрицательным или вторая операция должна была быть заблокирована.

Без распределенной сериализации параллельные микросервисы разрушают инварианты финансовой целостности.

## Решение по шагам

1. Создайте модель счета `BankAccount` с балансом и счетчиком списаний.
2. Запустите два параллельных инстанса воркеров, обрабатывающих один и тот же заказ без использования блокировок.
3. Добавьте искусственную задержку между операциями чтения баланса и записи нового значения.
4. Зафиксируйте двойное списание средств и потерю консистентности.
5. Продемонстрируйте, как внедрение распределенного мьютекса полностью предотвращает финансовую коллизию.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type BankAccount struct {
	mu            sync.Mutex
	Balance       float64
	ItemsShipped  int
	TotalCharged  float64
}

func (b *BankAccount) ReadBalance() float64 {
	b.mu.Lock()
	defer b.mu.Unlock()
	return b.Balance
}

func (b *BankAccount) SaveBalance(newBalance, chargeAmount float64) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.Balance = newBalance
	b.TotalCharged += chargeAmount
	b.ItemsShipped++
}

func ProcessPaymentWithoutLock(acc *BankAccount, orderAmount float64, workerID string, wg *sync.WaitGroup) {
	defer wg.Done()

	// 1. Read phase
	curr := acc.ReadBalance()
	fmt.Printf("[%s] Read balance: %.2f руб (Order: %.2f руб)\n", workerID, curr, orderAmount)

	if curr < orderAmount {
		fmt.Printf("[%s] ❌ Insufficient funds!\n", workerID)
		return
	}

	// 2. Heavy verification / external API call latency
	time.Sleep(50 * time.Millisecond)

	// 3. Write phase (VULNERABILITY: Blind overwrite based on stale read!)
	newBalance := curr - orderAmount
	acc.SaveBalance(newBalance, orderAmount)
	fmt.Printf("[%s] ✅ Deducted %.2f руб! New balance written: %.2f руб\n",
		workerID, orderAmount, newBalance)
}

func main() {
	account := &BankAccount{Balance: 1000.0}
	var wg sync.WaitGroup

	fmt.Println("=== Initial State ===")
	fmt.Printf("Account Balance: %.2f руб | Shipped Items: %d\n\n", account.Balance, account.ItemsShipped)

	fmt.Println("=== Processing 2 Concurrent Payment Requests of 800 руб WITHOUT Lock ===")
	wg.Add(2)
	go ProcessPaymentWithoutLock(account, 800.0, "Worker-Instance-1", &wg)
	go ProcessPaymentWithoutLock(account, 800.0, "Worker-Instance-2", &wg)
	wg.Wait()

	fmt.Println("\n=== DISASTER POST-MORTEM ===")
	fmt.Printf("Final Account Balance: %.2f руб\n", account.Balance)
	fmt.Printf("Total Charged from User: %.2f руб\n", account.TotalCharged)
	fmt.Printf("Total Items Shipped: %d (Worth: 1600.00 руб)\n", account.ItemsShipped)

	if account.ItemsShipped == 2 && account.Balance == 200.0 {
		fmt.Println("🚨 CRITICAL BUG: Double Spending! User bought 1600 руб worth of goods for only 800 руб!")
	}
}
```

ℹ️ Практическое воспроизведение финансовой гонки данных без блокировок

## Под капотом

Уровни изоляции транзакций в SQL против Distributed Lock:
В реляционных базах данных эту проблему можно решить через `SELECT balance FROM accounts WHERE id = 1 FOR UPDATE` (Pessimistic Locking) или `UPDATE accounts SET balance = balance - 800 WHERE id = 1 AND balance >= 800`.
Однако если критическая секция включает в себя обращение к **внешним сторонним сервисам** (списание миль авиакомпании, холдирование денег в Stripe API, резервирование на складе 1С), транзакция базы данных бессильна, так как внешний вызов нельзя обернуть в SQL-транзакцию. Здесь распределенная блокировка незаменима.

## Подводные камни

- **Надежда на локальный `sync.Mutex`**: Обычный Go-мьютекс защищает только горутины внутри одного процесса ОС. При масштабировании до двух реплик в Kubernetes локальный мьютекс бесполезен.
- **Отсутствие идемпотентности**: Даже с локом повторные сетевые вызовы обязаны проверять `Idempotency-Key`.

## На собеседовании

В Авито и Т-Банке на системном дизайне часто задают вопрос: *«Почему для предотвращения двойной оплаты заказа в HighLoad системе недостаточно просто распределенной блокировки в Redis?»*
**Ответ**:
1. **Сетевые сбои**: Если Redis-сервер упадет в момент подтверждения, блокировка может быть снята преждевременно.
2. **Паузы GC**: Инстанс может зависнуть на время, превышающее TTL блокировки, и продолжить выполнение после его истечения.
3. **Пакетные повторы**: Клиент может послать запрос дважды с разницей в 1 минуту (когда первый лок уже снят).
Поэтому надежная финансовая архитектура строится на трех эшелонах:
- Эшелон 1: **Распределенный лок** (снижает конкуренцию и отсекает 99% гонок).
- Эшелон 2: **Idempotency Key** в базе данных (уникальный индекс `order_id` в таблице платежей).
- Эшелон 3: **Атомарный SQL-запрос** со списанием `WHERE balance >= amount`.
