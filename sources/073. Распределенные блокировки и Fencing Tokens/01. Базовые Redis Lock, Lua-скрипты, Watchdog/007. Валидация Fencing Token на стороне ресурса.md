# Валидация Fencing Token на стороне ресурса: условные транзакции в PostgreSQL

## Условие

7. **Валидация Fencing Token на ресурсе**: Модифицируй таблицу в PostgreSQL, добавив `last_token_id INT`. Когда Воркер А (отвисший) присылает запрос с `Token=42`, а БД уже обработала запрос от Воркера Б с `Token=43`, база должна отклонить запрос А (42 < 43). Напиши SQL и Go-код.

### Исходная формулировка

**Валидация Fencing Token на ресурсе**: Модифицируй таблицу в PostgreSQL, добавив `last_token_id INT`. Когда Воркер А (отвисший) присылает запрос с `Token=42`, а БД уже обработала запрос от Воркера Б с `Token=43`, база должна отклонить запрос А (42 < 43). Напиши логику, где ресурс сам защищается от устаревших локов!

## Теория

Реализация механизма токенов ограждения на уровне реляционной СУБД (PostgreSQL / MySQL):

Схема таблицы:
```sql
CREATE TABLE account_balances (
    account_id BIGINT PRIMARY KEY,
    balance NUMERIC(18, 2) NOT NULL,
    last_fencing_token BIGINT NOT NULL DEFAULT 0
);
```

Условный SQL-запрос обновления (Conditional Update / Optimistic Guard):
```sql
UPDATE account_balances
SET balance = balance + :amount,
    last_fencing_token = :fencing_token
WHERE account_id = :account_id
  AND last_fencing_token < :fencing_token;
```

Анализ выполнения:
- Если база данных уже обработала транзакцию с токеном 43, а отставший «зомби»-воркер присылает токен 42, условие `last_fencing_token < 42` вернет `FALSE`.
- Метод Go `sql.Result.RowsAffected()` вернет `0`!
- Приложение фиксирует ошибку `ErrStaleFencingToken`, откатывает локальное состояние и не производит двойного списания.

## Решение по шагам

1. Создайте структуру транзакционного репозитория с проверкой `last_fencing_token`.
2. Реализуйте метод `ApplyBalanceChange(accountID, delta, token)`.
3. Смоделируйте выполнение условного SQL `UPDATE ... WHERE last_fencing_token < $token`.
4. Проверьте `RowsAffected()`: если обновлено 0 строк, верните ошибку конкурентного изменения.
5. Продемонстрируйте защиту от запоздалого обновления баланса.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

var (
	ErrConcurrentModification = errors.New("stale fencing token: transaction rejected by database")
)

type AccountRecord struct {
	AccountID        int64
	Balance          float64
	LastFencingToken uint64
}

type MockPostgresDB struct {
	mu       sync.Mutex
	accounts map[int64]AccountRecord
}

func NewMockPostgresDB() *MockPostgresDB {
	return &MockPostgresDB{
		accounts: map[int64]AccountRecord{
			1001: {AccountID: 1001, Balance: 5000.0, LastFencingToken: 40},
		},
	}
}

// Emulates: UPDATE account_balances SET balance = balance + delta, last_fencing_token = token
//           WHERE account_id = id AND last_fencing_token < token
func (db *MockPostgresDB) UpdateBalanceWithFencing(accountID int64, delta float64, token uint64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	rec, exists := db.accounts[accountID]
	if !exists {
		return errors.New("account not found")
	}

	// SQL WHERE clause condition: last_fencing_token < token
	if rec.LastFencingToken >= token {
		// 0 rows affected!
		return fmt.Errorf("%w (db token=%d >= request token=%d)",
			ErrConcurrentModification, rec.LastFencingToken, token)
	}

	// Apply update
	rec.Balance += delta
	rec.LastFencingToken = token
	db.accounts[accountID] = rec

	fmt.Printf("[PostgreSQL SQL UPDATE] Balance updated to %.2f (New Token: %d)\n",
		rec.Balance, rec.LastFencingToken)
	return nil
}

func main() {
	db := NewMockPostgresDB()

	fmt.Println("--- 1. Worker B executes update with Token 43 ---")
	errB := db.UpdateBalanceWithFencing(1001, -500.0, 43)
	if errB != nil {
		panic(errB)
	}

	fmt.Println("\n--- 2. Lagging Worker A attempts update with outdated Token 42 ---")
	errA := db.UpdateBalanceWithFencing(1001, -1000.0, 42)
	if errA != nil {
		fmt.Printf("🛡️ Database successfully protected balance: %v\n", errA)
	}

	// Final verification
	db.mu.Lock()
	finalRec := db.accounts[1001]
	db.mu.Unlock()
	fmt.Printf("\nFinal Account Balance: %.2f руб (Token: %d)\n",
		finalRec.Balance, finalRec.LastFencingToken)
}
```

ℹ️ Условное обновление баланса в БД с проверкой монотонного Fencing Token

## Под капотом

Атомарность на уровне PostgreSQL:
Запрос `UPDATE ... WHERE last_fencing_token < $token` исполняется внутри неявной транзакции PostgreSQL с блокировкой строки на запись (`FOR UPDATE`). Если параллельно придут два запроса, один из них заблокируется на уровне строки. Второй запрос перечитает свежее значение `last_fencing_token`, условие `WHERE` не совпадет, и операция завершится с `RowsAffected() == 0` без взаимоблокировок.

## Подводные камни

- **Забытая проверка `rowsAffected == 0`**: В Go вызов `db.Exec()` не возвращает ошибку, если условие `WHERE` не нашло подходящих строк. Разработчик обязан вызвать `res.RowsAffected()` и явно вернуть ошибку, если затронуто 0 строк.
- **Откат счетчика при сбоях**: Fencing токен никогда не должен уменьшаться обратно.

## На собеседовании

В Т-Банке и Wildberries часто спрашивают: *«Как в распределенной транзакции между несколькими микросервисами гарантировать идемпотентность и защиту от запоздалых пакетов сети?»*
**Ответ**: Сочетанием **Idempotency Key** и **Fencing Token**. Ключ идемпотентности предотвращает повторную обработку дубликатов запроса от одного и того же клиента. Токен ограждения, валидируемый в SQL-запросе через `WHERE fencing_token > last_seen_token`, защищает от перезаписи данных запоздалыми пакетами от старых реплик или бывших лидеров (Zombie Writers).
