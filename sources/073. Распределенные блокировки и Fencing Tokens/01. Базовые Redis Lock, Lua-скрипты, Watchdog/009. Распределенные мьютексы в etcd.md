### Исходная формулировка

**etcd Distributed Lock**: etcd решает проблемы Redis-локов за счет строгого консенсуса. Используй встроенный пакет `go.etcd.io/etcd/client/v3/concurrency`. Создай сессию `concurrency.NewSession()` и мьютекс `concurrency.NewMutex()`. Вызови `Lock()` и `Unlock()`.

## Теория

Пакет `go.etcd.io/etcd/client/v3/concurrency` предоставляет эталонную реализацию распределенного мьютекса:

Архитектурная схема:
1. **`concurrency.Session`**:
   - Связывает клиентский процесс с арендой (`Lease`) в etcd.
   - Запускает фоновый KeepAlive поток, который непрерывно продлевает аренду, пока жив процесс и есть сеть.
2. **`concurrency.Mutex`**:
   - При вызове `mutex.Lock(ctx)` клиент создает эфемерный ключ с префиксом: `/my-lock/<lease_id>`.
   - Ключ привязывается к аренде сессии.
   - etcd упорядочивает созданные ключи по их `CreateRevision`.
3. **Честная очередь (Fair FIFO Queue)**:
   - Клиент проверяет, является ли его ключ первым (с минимальной `CreateRevision`).
   - Если да — блокировка захвачена!
   - Если нет — клиент не спамит запросами, а подписывается через `Watch` **только на предыдущий перед ним ключ в очереди**, засыпая до его удаления.
4. **Crash-Safety**:
   - Если процесс падает, etcd закрывает сессию по истечении TTL аренды, удаляет эфемерный ключ, и следующий узел в очереди мгновенно просыпается.

## Решение по шагам

1. Создайте модель сессии `EtcdSession` с арендой и фоновым поддержанием жизни (Heartbeat).
2. Реализуйте алгоритм `EtcdMutex` на основе ревизий создания ключей.
3. Продемонстрируйте захват мьютекса первым процессом.
4. Покажите, как второй процесс ожидает освобождения ресурса через канал ожидания.
5. Вызовите `Unlock()` и зафиксируйте мгновенную передачу прав второму процессу.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type MockSession struct {
	LeaseID int64
	TTLSec  int
	alive   bool
	mu      sync.Mutex
}

func (s *MockSession) Close() {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.alive = false
}

type QueueEntry struct {
	ClientName string
	Revision   int64
	WakeCh     chan struct{}
}

type EtcdLockCoordinator struct {
	mu           sync.Mutex
	currentRev   int64
	waitingQueue []*QueueEntry
}

func NewEtcdLockCoordinator() *EtcdLockCoordinator {
	return &EtcdLockCoordinator{
		currentRev:   100,
		waitingQueue: make([]*QueueEntry, 0),
	}
}

func (c *EtcdLockCoordinator) Lock(ctx context.Context, clientName string) (*QueueEntry, error) {
	c.mu.Lock()
	c.currentRev++
	entry := &QueueEntry{
		ClientName: clientName,
		Revision:   c.currentRev,
		WakeCh:     make(chan struct{}, 1),
	}
	c.waitingQueue = append(c.waitingQueue, entry)
	isFirst := len(c.waitingQueue) == 1
	c.mu.Unlock()

	if isFirst {
		fmt.Printf("[etcd Mutex] %s is at the head of the queue (Rev: %d). Lock acquired immediately!\n",
			clientName, entry.Revision)
		return entry, nil
	}

	fmt.Printf("[etcd Mutex] %s queued at Rev: %d. Watching predecessor...\n", clientName, entry.Revision)

	select {
	case <-ctx.Done():
		return nil, ctx.Err()
	case <-entry.WakeCh:
		fmt.Printf("[etcd Mutex] %s woke up! Lock acquired!\n", clientName)
		return entry, nil
	}
}

func (c *EtcdLockCoordinator) Unlock(entry *QueueEntry) {
	c.mu.Lock()
	defer c.mu.Unlock()

	if len(c.waitingQueue) == 0 || c.waitingQueue[0].Revision != entry.Revision {
		return
	}

	// Pop head
	c.waitingQueue = c.waitingQueue[1:]
	fmt.Printf("[etcd Mutex] %s released lock.\n", entry.ClientName)

	// Wake up next in FIFO line
	if len(c.waitingQueue) > 0 {
		next := c.waitingQueue[0]
		close(next.WakeCh)
	}
}

func main() {
	coordinator := NewEtcdLockCoordinator()
	ctx := context.Background()

	var wg sync.WaitGroup
	wg.Add(2)

	// Worker 1
	go func() {
		defer wg.Done()
		entry, err := coordinator.Lock(ctx, "Worker-1")
		if err != nil {
			panic(err)
		}
		// Critical Section
		time.Sleep(150 * time.Millisecond)
		coordinator.Unlock(entry)
	}()

	// Worker 2 starts slightly later
	time.Sleep(20 * time.Millisecond)
	go func() {
		defer wg.Done()
		entry, err := coordinator.Lock(ctx, "Worker-2")
		if err != nil {
			panic(err)
		}
		// Critical Section
		time.Sleep(50 * time.Millisecond)
		coordinator.Unlock(entry)
	}()

	wg.Wait()
	fmt.Println("All workers finished executing critical section with fair FIFO ordering!")
}
```

## Под капотом

Почему etcd Mutex не создает Thundering Herd («набег толпы»):
В наивных мьютексах при освобождении блокировки просыпаются все 500 ожидающих процессов и одновременно ломятся захватить ключ, создавая колоссальный всплеск нагрузки на CPU и сеть.
В алгоритме `concurrency.Mutex` каждый процесс подписывается через `Watch` **только на один конкретный ключ**, который находится непосредственно перед ним в отсортированном списке ревизий. При вызове `Unlock` сетевой пакет от etcd получает **ровно один процесс** — следующий в очереди.

## Подводные камни

- **Забытый `session.Close()`**: Если не закрыть сессию, аренда в etcd продолжит удерживаться до истечения таймаута TTL, задерживая другие сервисы.
- **Утечка сессий при повторном создании**: Создание новой сессии `concurrency.NewSession` на каждый вызов `Lock` приводит к расходу ресурсов etcd. Сессия должна переиспользоваться.

## На собеседовании

В Wildberries и Авито на системном проектировании часто спрашивают: *«Сравните распределенную блокировку на Redis и на etcd. Что вы выберете для блокировки баланса кошелька пользователя?»*
**Ответ**:
- **Redis (SET NX)**: Сверхбыстрый (микросекунды), масштабируемый, но ненадежный в граничных случаях (асинхронная репликация грозит потерей лока при падении мастера; подвержен Split-Brain при GC-паузах). Подходит для дедупликации фоновых задач или Rate Limiting.
- **etcd (Raft-консенсус)**: Строгая математическая гарантия консенсуса (Safety), синхронная персистентность на диск, честная очередь FIFO через MVCC-ревизии, отсутствие Thundering Herd. Для финансовых балансов и критических ресурсов безоговорочно выбирают **etcd** (или Consul).
