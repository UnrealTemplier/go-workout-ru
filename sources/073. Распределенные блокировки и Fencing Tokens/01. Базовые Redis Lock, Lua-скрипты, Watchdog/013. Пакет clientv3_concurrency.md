# Пакет clientv3/concurrency: etcd Mutex против Redis Lock и гарантии Crash-Safety

### Исходная формулировка

## Теория

Сравнение фундаментов надежности etcd и Redis:

| Критерий | Redis Lock | etcd concurrency.Mutex |
| :--- | :--- | :--- |
| **Алгоритм согласованности** | Асинхронная репликация (AP/деградированная) | Строгий Raft-консенсус (CP) |
| **Поведение при падении мастера** | Возможна потеря блокировки (Replication Lag) | Гарантия сохранности: лог закоммичен кворумом |
| **Очередь ожидания** | Активный опрос (Spin-lock / polling) | Честная очередь FIFO по `CreateRevision` |
| **Оповещение о снятии** | Polling или Pub/Sub (ненадежный) | Высоконадежный gRPC `Watch` на предшественника |
| **Нагрузка на сеть при ожидании**| Высокая (Thundering Herd при Pub/Sub) | Минимальная (\(O(1)\) пакетов, только один узел) |

Гарантия Crash-Safety в etcd:
При аварийном завершении держателя блокировки (`kill -9`):
1. Разрывается TCP-соединение gRPC.
2. etcd ждет истечения TTL аренды (например, 5 секунд).
3. Аренда отзывается (Revoked), эфемерный ключ удаляется.
4. etcd по протоколу `Watch` шлет событие `DELETE` ровно следующему в очереди процессу, обеспечивая безопасный автоматический фейловер.

## Решение по шагам

1. Создайте кластер etcd с поддержкой сессий и Raft-кворума.
2. Реализуйте захват мьютекса процессом 1 с привязкой к сессии.
3. Процесс 2 запрашивает лок и встает в очередь ожидания по `Watch`.
4. Сымитируйте крах Процесса 1 (`Crash()`) с обрывом сессии.
5. Продемонстрируйте, как etcd отзывает аренду и мгновенно пробуждает Процесс 2.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type EtcdRaftMutex struct {
	mu         sync.Mutex
	holder     string
	leaseExp   time.Time
	waitQueue  chan string
	holderDown bool
}

func NewEtcdRaftMutex() *EtcdRaftMutex {
	return &EtcdRaftMutex{
		waitQueue: make(chan string, 1),
	}
}

func (m *EtcdRaftMutex) Lock(ctx context.Context, clientID string, leaseTTL time.Duration) error {
	m.mu.Lock()
	if m.holder == "" {
		m.holder = clientID
		m.leaseExp = time.Now().Add(leaseTTL)
		m.holderDown = false
		m.mu.Unlock()
		fmt.Printf("[etcd Raft] %s successfully acquired lock via Quorum. Lease TTL: %v\n", clientID, leaseTTL)
		return nil
	}
	m.mu.Unlock()

	fmt.Printf("[etcd Raft] %s waiting in FIFO queue (Watching active lease)...\n", clientID)

	select {
	case <-ctx.Done():
		return ctx.Err()
	case next := <-m.waitQueue:
		if next == clientID {
			m.mu.Lock()
			m.holder = clientID
			m.leaseExp = time.Now().Add(leaseTTL)
			m.mu.Unlock()
			fmt.Printf("[etcd Raft] %s woke up by Watch event! Lock acquired.\n", clientID)
			return nil
		}
	}
	return nil
}

func (m *EtcdRaftMutex) CrashHolder(clientID string) {
	m.mu.Lock()
	defer m.mu.Unlock()

	if m.holder == clientID {
		m.holderDown = true
		fmt.Printf("💥 [OS Alert] %s CRASHED (SIGKILL)! KeepAlive stream broken.\n", clientID)

		// Start asynchronous lease expiration timer on etcd cluster
		go func() {
			time.Sleep(200 * time.Millisecond) // Wait for lease timeout
			m.mu.Lock()
			fmt.Printf("[etcd Raft ⏳] Lease expired for crashed %s. Auto-releasing lock...\n", clientID)
			m.holder = ""
			m.mu.Unlock()
			m.waitQueue <- "Client-2" // Notify next watcher
		}()
	}
}

func main() {
	mutex := NewEtcdRaftMutex()
	ctx := context.Background()
	var wg sync.WaitGroup

	// Client 1 acquires lock
	wg.Add(1)
	go func() {
		defer wg.Done()
		_ = mutex.Lock(ctx, "Client-1", 200*time.Millisecond)
		time.Sleep(50 * time.Millisecond)
		// Simulating sudden crash
		mutex.CrashHolder("Client-1")
	}()

	// Client 2 attempts to acquire same lock
	time.Sleep(20 * time.Millisecond)
	wg.Add(1)
	go func() {
		defer wg.Done()
		_ = mutex.Lock(ctx, "Client-2", 500*time.Millisecond)
		fmt.Println("[Client-2] Executing critical section safely!")
	}()

	wg.Wait()
	fmt.Println("Verification complete: etcd Raft lease successfully ensured crash-safety without deadlock!")
}
```

## Под капотом

Как устроен префикс ключа в `concurrency.Mutex`:
При вызове `mutex := concurrency.NewMutex(session, "/my-lock/")` etcd создает ключ вида:
`/my-lock/7595a82e0e2348a1` (где суффикс — шестнадцатеричный `LeaseID`).
Затем клиент делает `client.Get(ctx, "/my-lock/", clientv3.WithPrefix(), clientv3.WithSort(clientv3.SortByCreateRevision, clientv3.SortAscend))`.
Если ключ клиента стоит первым в списке, он владеет локом. Если нет — он выбирает ключ с ревизией, предшествующей его собственной, и запускает `client.Watch(ctx, predecessorKey)`.

## Подводные камни

- **Потеря сети между клиентом и etcd**: Если клиент потерял связь с etcd, но продолжает работать локально, etcd отзовет аренду через TTL секунд. Клиент ОБЯЗАН слушать канал `session.Done()`. Если `session.Done()` закрылся — клиент обязан немедленно прекратить работу!
- **Слишком агрессивный TTL аренды**: Установка TTL в 1 секунду может привести к отзыву блокировки при малейшем сетевом спайке.

## На собеседовании

В Wildberries и Касперском часто спрашивают: *«Почему для распределенной блокировки etcd принципиально надежнее одиночного Redis или Redis Sentinel?»*
**Ответ**:
1. **Синхронный консенсус Raft**: В etcd запись о создании блокировки считается успешной только после того, как сохранена в WAL и зафиксирована большинством узлов (\(N/2 + 1\)). Ни при каких сбоях отдельных серверов закоммиченный лок не может исчезнуть. В Redis Master-Replica репликация асинхронна — при аварии мастера данные блокировки теряются до репликации на реплику, что ведет к Split-Brain.
2. **Линеаризуемость**: etcd математически гарантирует строгий глобальный порядок событий (Total Order).
