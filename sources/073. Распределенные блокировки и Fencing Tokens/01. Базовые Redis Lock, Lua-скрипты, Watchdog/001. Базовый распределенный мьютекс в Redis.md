# Базовый распределенный мьютекс в Redis: атомарная семантика SET resource_name token NX PX

## Условие

1. **Базовый Redis Lock**: Реализуй блокировку. Используй `SET resource_name my_random_value NX PX 10000`. `NX` (только если ключа нет) гарантирует эксклюзивность, `PX 10000` (TTL 10 сек) спасает от дедлока, если сервер умрет с блокировкой.

### Исходная формулировка

**Базовый Redis Lock**: Реализуй блокировку. Используй `SET resource_name my_random_value NX PX 10000`. `NX` (только если ключа нет) гарантирует эксклюзивность, `PX 10000` (TTL 10 сек) спасает от дедлока, если сервер умрет с блокировкой.

## Теория

Распределенная блокировка (Distributed Lock) необходима в микросервисной архитектуре, когда несколько независимых процессов или подов конкурируют за доступ к разделяемому не-сериализуемому ресурсу (списание баланса, обработка заказа, отправка SMS).

Команда Redis `SET key value [NX|XX] [GET] [EX seconds|PX milliseconds]`:
- **Флаг `NX` (Not eXists)**: Записывает ключ только в том случае, если он еще не существует в пространстве ключей. Гарантирует **взаимное исключение (Mutual Exclusion)** — ровно один клиент получит статус `OK`.
- **Флаг `PX <ms>`**: Устанавливает атомарный Time-To-Live (время жизни) в миллисекундах. Это спасает систему от вечной взаимной блокировки (Deadlock), если держатель блокировки аварийно упадет (`SIGKILL`, OOM, kernel panic).
- **Уникальный токен (Random Value / UUIDv4)**: Значение обязано быть уникальным для каждого инстанса и каждого захвата блокировки, чтобы избежать снятия чужой блокировки при задержках выполнения.

## Решение по шагам

1. Создайте структуру `RedisLocker`, инкапсулирующую работу с ассоциативным хранилищем.
2. Сформируйте криптографически стойкий случайный токен владельца блокировки (UUID).
3. Реализуйте атомарную команду `AcquireLock(key, token, ttl)` с проверкой флага `NX` и установкой `PX`.
4. Протестируйте конкурентный захват одного и того же ресурса двумя параллельными воркерами.
5. Убедитесь, что первый воркер успешно захватывает ресурс, а второй получает отказ `ErrLockNotAcquired`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrLockNotAcquired = errors.New("lock already acquired by another client")
)

type MockRedisStore struct {
	mu    sync.Mutex
	store map[string]string
	exp   map[string]time.Time
}

func NewMockRedisStore() *MockRedisStore {
	return &MockRedisStore{
		store: make(map[string]string),
		exp:   make(map[string]time.Time),
	}
}

// Emulates: SET key value NX PX ttlMs
func (r *MockRedisStore) SetNXPX(key, value string, ttl time.Duration) bool {
	r.mu.Lock()
	defer r.mu.Unlock()

	now := time.Now()
	// Clean expired keys
	if expireAt, exists := r.exp[key]; exists && now.After(expireAt) {
		delete(r.store, key)
		delete(r.exp, key)
	}

	if _, exists := r.store[key]; exists {
		return false // NX failed: key exists
	}

	r.store[key] = value
	r.exp[key] = now.Add(ttl)
	return true
}

type DistributedLock struct {
	client *MockRedisStore
	key    string
	token  string
	ttl    time.Duration
}

func GenerateRandomToken() string {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	return hex.EncodeToString(b)
}

func TryAcquire(client *MockRedisStore, key string, ttl time.Duration) (*DistributedLock, error) {
	token := GenerateRandomToken()
	success := client.SetNXPX(key, token, ttl)
	if !success {
		return nil, ErrLockNotAcquired
	}
	return &DistributedLock{
		client: client,
		key:    key,
		token:  token,
		ttl:    ttl,
	}, nil
}

func main() {
	redisClient := NewMockRedisStore()
	resourceKey := "lock:order:89421"

	fmt.Println("=== 1. Worker A attempts to acquire lock ===")
	lockA, err := TryAcquire(redisClient, resourceKey, 10*time.Second)
	if err != nil {
		fmt.Printf("Worker A failed: %v\n", err)
	} else {
		fmt.Printf("✅ Worker A acquired lock! Token: %s\n", lockA.token)
	}

	fmt.Println("\n=== 2. Worker B attempts to acquire SAME lock concurrently ===")
	lockB, err := TryAcquire(redisClient, resourceKey, 10*time.Second)
	if err != nil {
		fmt.Printf("❌ Worker B rejected as expected: %v\n", err)
	} else {
		fmt.Printf("Worker B acquired lock! Token: %s\n", lockB.token)
	}
}
```

## Под капотом

В старых версиях Redis разработчики вызывали две команды: `SETNX lock 1` и затем `EXPIRE lock 10`.
Если между этими вызовами процесс падал или соединение разрывалось, ключ оставался в Redis **навечно без TTL**. Все сервисы в продакшене уходили в Deadlock до ручного вмешательства администратора.
Начиная с Redis 2.6.12 команда `SET` объединила `NX` и `PX/EX` в **единый атомарный синтаксический опкод**, гарантируя установку TTL за один сетевой пакет.

## Подводные камни

- **Использование константного токена (`value = "1"`)**: Если все клиенты пишут `1`, процесс \(A\) не сможет проверить, принадлежит ли блокировка ему или другому воркеру.
- **Слишком короткий TTL**: Если фоновая операция длится 12 секунд, а TTL равен 10 секунд, ключ удалится посреди выполнения, и другой процесс войдет в критическую секцию.

## На собеседовании

В Яндекс Маркете и Ozon любят вопрос: *«Почему в Redis нельзя разделять проверку занятости и установку времени жизни на две команды `SETNX` и `EXPIRE`?»*
**Ответ**: Любая неатомарная операция в распределенной среде уязвима к сбоям сети и падениям узлов. Если процесс успел выполнить `SETNX` и аварийно завершился (OOM-killer ОС, физический обрыв питания или потеря сети) до отправки `EXPIRE`, ключ навсегда зависнет в Redis без времени жизни. Вся бизнес-система встанет в вечный дедлок. Использование единой атомарной команды `SET key val NX PX ms` исключает это окно уязвимости.
