# Каноничная реализация Redis Lock: SET lock:res UUID NX EX 30 и безопасный Compare-and-Delete

## Условие

11. **Redis SET NX EX.**: Реализуйте lock: `SET lock:resource <random_value> NX EX 30`. Unlock через Lua-скрипт: удалить только если `value` совпадает. Объясните, почему нужен уникальный `random_value` (UUID) и почему `DEL` без проверки — опасен (может снять чужой lock).

### Исходная формулировка

**Redis SET NX EX.**: Реализуйте lock: `SET lock:resource <random_value> NX EX 30`. Unlock через Lua-скрипт: удалить только если `value` совпадает. Объясните, почему нужен уникальный `random_value` (UUID) и почему `DEL` без проверки — опасен (можно удалить чужой lock).

## Теория

Каноничный распределенный мьютекс в Redis базируется на строгом соблюдении двух фаз:

1. **Фаза захвата (Acquire)**:
   ```text
   SET lock:<resource> <uuid> NX EX 30
   ```
   - `NX`: Взаимное исключение (Mutual Exclusion). Только первый получает `OK`.
   - `EX 30`: Автоматическое освобождение через 30 секунд при падении держателя (Deadlock Prevention).
   - `<uuid>`: Уникальный маркер владения (Cryptographic Randomness).

2. **Фаза освобождения (Release)**:
   - Вызов `DEL lock:<resource>` без проверки значения — **грубейшая архитектурная ошибка**.
   - Если воркер задержался на 31 секунду, его лок истек, а соседний воркер взял лок с новым UUID. Наивный `DEL` удалит лок соседа!
   - Поэтому снятие производится исключительно через атомарный CAS Lua-скрипт:
   ```lua
   if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1])
   else
       return 0
   end
   ```

## Решение по шагам

1. Создайте структуру `RedisMutex` с полями `resource`, `token`, `ttl`.
2. Реализуйте метод `Lock(ctx)` с экспоненциальным backoff при повторных попытках.
3. Реализуйте метод `Unlock(ctx)` через атомарную проверку токена.
4. Продемонстрируйте защиту от снятия чужого лока при искусственном изменении токена в базе.
5. Проверьте корректное освобождение ресурса при штатной работе.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"time"
)

type RedisEngine struct {
	mu   sync.Mutex
	data map[string]string
	exp  map[string]time.Time
}

func NewRedisEngine() *RedisEngine {
	return &RedisEngine{
		data: make(map[string]string),
		exp:  make(map[string]time.Time),
	}
}

func (r *RedisEngine) SetNXEX(key, val string, seconds int) bool {
	r.mu.Lock()
	defer r.mu.Unlock()

	now := time.Now()
	if expireAt, exists := r.exp[key]; exists && now.After(expireAt) {
		delete(r.data, key)
		delete(r.exp, key)
	}

	if _, exists := r.data[key]; exists {
		return false
	}

	r.data[key] = val
	r.exp[key] = now.Add(time.Duration(seconds) * time.Second)
	return true
}

func (r *RedisEngine) EvalCompareAndDelete(key, token string) bool {
	r.mu.Lock()
	defer r.mu.Unlock()

	current, exists := r.data[key]
	if !exists {
		return false
	}
	if current == token {
		delete(r.data, key)
		delete(r.exp, key)
		return true
	}
	return false // Token mismatch: cannot unlock someone else's lock!
}

type RedisMutex struct {
	engine   *RedisEngine
	resource string
	token    string
	ttlSec   int
}

func NewRedisMutex(engine *RedisEngine, resource string, ttlSec int) *RedisMutex {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	return &RedisMutex{
		engine:   engine,
		resource: "lock:" + resource,
		token:    hex.EncodeToString(b),
		ttlSec:   ttlSec,
	}
}

func (m *RedisMutex) Lock(ctx context.Context, retryDelay time.Duration) error {
	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		if m.engine.SetNXEX(m.resource, m.token, m.ttlSec) {
			fmt.Printf("[Redis Mutex] Successfully locked '%s' with Token: %s\n", m.resource, m.token)
			return nil
		}

		time.Sleep(retryDelay)
	}
}

func (m *RedisMutex) Unlock() error {
	ok := m.engine.EvalCompareAndDelete(m.resource, m.token)
	if !ok {
		return errors.New("failed to unlock: token mismatch or lock expired")
	}
	fmt.Printf("[Redis Mutex] Successfully unlocked '%s'\n", m.resource)
	return nil
}

func main() {
	engine := NewRedisEngine()
	ctx := context.Background()

	mutex1 := NewRedisMutex(engine, "invoice:901", 30)
	if err := mutex1.Lock(ctx, 10*time.Millisecond); err != nil {
		panic(err)
	}

	// Tamper simulation: another client overwrites the key with their token
	fmt.Println("\n--- Simulating TTL Expiry and Lock Hijack by Client 2 ---")
	engine.mu.Lock()
	engine.data["lock:invoice:901"] = "alien-token-999"
	engine.mu.Unlock()

	// Mutex 1 tries to unlock
	err := mutex1.Unlock()
	fmt.Printf("Mutex 1 Unlock Result: '%v' (Alien lock protected from accidental deletion!)\n", err)
}
```

## Под капотом

Сравнение энтропии: почему именно криптографический UUID:
Если использовать `PID` процесса или инкрементный счетчик, то в распределенной системе с контейнерами Docker разные поды на разных нодах могут иметь **абсолютно одинаковый PID** (например, `PID = 1` внутри контейнера).
Генерация 128-битного криптографически стойкого случайного числа (`crypto/rand`) дает вероятность коллизии менее \(10^{-36}\), гарантируя абсолютную уникальность токена владения.

## Подводные камни

- **Использование `math/rand` без сидирования**: Псевдослучайные генераторы без криптографического сида могут выдать одинаковые токены на двух разных подах после старта контейнера из одного Docker-образа.
- **Отсутствие ограничения количества попыток (Max Retries)**: Бесконечный цикл попыток может создать шторм запросов к Redis. Всегда используйте jitter backoff и `ctx` с дедлайном.

## На собеседовании

В Ozon и Wildberries часто спрашивают: *«Что делать, если при вызове Lua-скрипта разблокировки произошел сетевой таймаут (Read Timeout)? Освобожден ли лог в Redis или нет?»*
**Ответ**: Это классическая проблема неопределенности состояния (Two Generals' Problem). Запрос мог дойти до Redis и успешно удалить ключ, но ответ застрял в сети; либо запрос вообще не дошел. При получении таймаута клиент **не должен паниковать**: благодаря механизму TTL ключ в любом случае гарантированно исчезнет из Redis через оставшиеся секунды. Однако для безопасности данных бизнес-логика обязана опираться на Fencing Tokens в базе данных.
