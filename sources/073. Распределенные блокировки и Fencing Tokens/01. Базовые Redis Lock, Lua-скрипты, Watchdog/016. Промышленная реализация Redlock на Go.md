## Теория

Библиотека `github.com/go-redsync/redsync/v4` является де-факто стандартом реализации алгоритма Redlock в экосистеме Go.

Ключевые конфигурационные опции `redsync`:
1. **`redsync.WithExpiry(d)`**: Задает максимальное время жизни блокировки (TTL). По умолчанию 8 секунд.
2. **`redsync.WithTries(n)`**: Максимальное количество попыток захвата блокировки перед возвратом ошибки `ErrFailed`.
3. **`redsync.WithRetryDelay(d)`**: Базовый интервал между попытками.
4. **`redsync.WithRetryDelayFunc(fn)`**: Функция расчета задержки с поддержкой Full Jitter, предотвращающая коллизии между параллельными воркерами.
5. **`redsync.WithDriftFactor(f)`**: Доля времени, закладываемая на дрейф часов (по умолчанию \(0.01\), то есть \(1\%\)).

Архитектура пулов:
`redsync.New(pools...)` принимает срез `redis.Pool` (например, адаптеры к `go-redis/v9` или `gomodule/redigo`). Каждый пул обязан указывать на **отдельный независимый экземпляр Redis**.

## Решение по шагам

1. Создайте структуру-обертку `DistributedSyncManager` над пулами соединений.
2. Настройте параметры мьютекса: время жизни (`Expiry = 5s`), количество повторов (`Tries = 3`) и интервал с рандомизацией.
3. Реализуйте безопасный захват и освобождение блокировки в паттерне `defer mutex.Unlock()`.
4. Смоделируйте конкурентный конфликт между двумя воркерами с проверкой отката.
5. Убедитесь в корректной обработке ошибки `ErrFailed` при недоступности кворума.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"math/rand"
	"sync"
	"time"
)

// Emulation of go-redsync Mutex API
type RedsyncMutex struct {
	name        string
	expiry      time.Duration
	tries       int
	retryDelay  time.Duration
	driftFactor float64
	holderToken string
	mu          sync.Mutex
	isLocked    bool
}

type RedsyncOption func(*RedsyncMutex)

func WithExpiry(d time.Duration) RedsyncOption {
	return func(m *RedsyncMutex) { m.expiry = d }
}

func WithTries(n int) RedsyncOption {
	return func(m *RedsyncMutex) { m.tries = n }
}

func WithRetryDelay(d time.Duration) RedsyncOption {
	return func(m *RedsyncMutex) { m.retryDelay = d }
}

type RedsyncPool struct {
	mu     sync.Mutex
	states map[string]string
}

type Redsync struct {
	pool *RedsyncPool
}

func NewRedsync() *Redsync {
	return &Redsync{
		pool: &RedsyncPool{states: make(map[string]string)},
	}
}

func (r *Redsync) NewMutex(name string, opts ...RedsyncOption) *RedsyncMutex {
	m := &RedsyncMutex{
		name:        name,
		expiry:      8 * time.Second,
		tries:       32,
		retryDelay:  500 * time.Millisecond,
		driftFactor: 0.01,
	}
	for _, opt := range opts {
		opt(m)
	}
	return m
}

func (m *RedsyncMutex) LockContext(ctx context.Context, r *Redsync) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	rGen := rand.New(rand.NewSource(time.Now().UnixNano()))

	for attempt := 1; attempt <= m.tries; attempt++ {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		r.pool.mu.Lock()
		if _, busy := r.pool.states[m.name]; !busy {
			token := fmt.Sprintf("token-%d-%d", time.Now().UnixNano(), rGen.Intn(1000))
			r.pool.states[m.name] = token
			m.holderToken = token
			m.isLocked = true
			r.pool.mu.Unlock()
			fmt.Printf("[redsync] ✅ Lock '%s' acquired on attempt %d (Token: %s)\n", m.name, attempt, token[:16])
			return nil
		}
		r.pool.mu.Unlock()

		// Jitter backoff
		jitter := time.Duration(rGen.Int63n(int64(m.retryDelay / 2)))
		time.Sleep(m.retryDelay/2 + jitter)
	}

	return errors.New("redsync: failed to acquire lock after max retries")
}

func (m *RedsyncMutex) Unlock(r *Redsync) (bool, error) {
	m.mu.Lock()
	defer m.mu.Unlock()

	if !m.isLocked {
		return false, errors.New("redsync: lock not held")
	}

	r.pool.mu.Lock()
	defer r.pool.mu.Unlock()

	if r.pool.states[m.name] == m.holderToken {
		delete(r.pool.states, m.name)
		m.isLocked = false
		m.holderToken = ""
		fmt.Printf("[redsync] 🔓 Lock '%s' released cleanly.\n", m.name)
		return true, nil
	}
	return false, errors.New("redsync: token mismatch or lock stolen")
}

func main() {
	rs := NewRedsync()
	ctx := context.Background()

	// Configure industrial Redsync Mutex
	mutexA := rs.NewMutex("order:checkout:555",
		WithExpiry(10*time.Second),
		WithTries(3),
		WithRetryDelay(50*time.Millisecond),
	)

	// Worker 1 acquires lock
	if err := mutexA.LockContext(ctx, rs); err != nil {
		panic(err)
	}

	// Worker 2 attempts to acquire same lock (should fail after 3 tries)
	mutexB := rs.NewMutex("order:checkout:555",
		WithExpiry(10*time.Second),
		WithTries(3),
		WithRetryDelay(20*time.Millisecond),
	)

	fmt.Println("\nWorker 2 attempting to contest the lock...")
	errB := mutexB.LockContext(ctx, rs)
	if errB != nil {
		fmt.Printf("Worker 2 rejected as expected: %v\n", errB)
	}

	// Worker 1 finishes and unlocks
	fmt.Println("\nWorker 1 releasing lock...")
	_, _ = mutexA.Unlock(rs)
}
```

ℹ️ Промышленная архитектура Redlock с поддержкой Full Jitter и конфигурации пулов

## Под капотом

Внутренний механизм продления в `go-redsync`:
Метод `mutex.Extend()` или `mutex.ExtendContext(ctx)`:
Позволяет вручную или через фоновую горутину продлить срок жизни захваченного Redlock.
Внутри он исполняет специальный Lua-скрипт продления на всех \(N\) узлах:
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("pexpire", KEYS[1], ARGV[2])
else
    return 0
end
```
Продление считается успешным, только если большинство узлов ответили подтверждением до истечения дедлайна.

## Подводные камни

- **Использование Redsync поверх Redis Cluster**: Частая ошибка новичков — передать в `redsync.New` 5 узлов из одного Redis Cluster! В кластере Redis хэш-слот ключа `order:1` всегда отображается ровно на один мастер. В итоге все 5 запросов пойдут в одну и ту же ноду, полностью разрушив идею Redlock. Redlock требует 5 **изолированных, не знающих друг о друге инстансов Redis**.
- **Слишком жесткий `WithTries(1)`**: При малейшей конкуренции запрос будет отваливаться.

## На собеседовании

В Lamoda и Авито часто спрашивают: *«Как в `go-redsync` защититься от Thundering Herd при одновременной попытке захвата блокировки 1000 горутинами?»*
**Ответ**: Настроить стратегию **Exponential Backoff с Full Jitter** через опцию `WithRetryDelayFunc`. Если все горутины будут повторять попытки через фиксированные 100 мс, они будут циклически сталкиваться и забивать Redis запросами. Jitter добавляет случайный разброс времени ожидания `delay = rand(0, base_delay * 2^attempt)`, равномерно размазывая запросы во времени и обеспечивая быструю сходимость.
