### Исходная формулировка

**Redis single-node lock**: Простейший distributed lock:
```
SET lock_key "owner" NX EX 30
```
Проблема: если Redis упадёт, lock потерян.

## Теория

Использование одиночного инстанса Redis (Single-Node Redis) для распределенных блокировок — самый популярный и одновременно самый рискованный паттерн в индустрии.

Архитектурная дилемма Single-Node Redis:
1. **Случай А: Одиночный Redis без репликации**:
   - Является абсолютной единой точкой отказа (Single Point of Failure — SPOF).
   - Если сервер падает по OOM или перезагружается по требованию ОС, все активные блокировки **мгновенно исчезают из оперативной памяти**.
   - Вся распределенная система теряет координацию и начинает параллельную несинхронизированную обработку ресурсов.
2. **Случай Б: Одиночный Redis с включенным AOF (Append-Only File) `fsync everysec`**:
   - При аварии процесса теряются данные за последнюю секунду. Если блокировка была взята за 200 мс до краха, после рестарта Redis о ней не узнает.
3. **Случай В: Redis с `fsync always`**:
   - Гарантирует персистентность, но пропускная способность падает с 100 000 RPS до 1 000 RPS из-за синхронного ввода-вывода SSD. Теряется главное преимущество Redis — скорость.

Вывод: Одиночный Redis допустим исключительно для **Best-Effort задач** (Rate Limiting, кеширование, предотвращение дубликатов фоновых отчетов), где редкий сбой не ведет к финансовым потерям.

## Решение по шагам

1. Создайте модель одиночного инстанса Redis `SingleNodeRedis`.
2. Реализуйте захват блокировки несколькими воркерами.
3. Смоделируйте внезапный крах процесса Redis с потерей оперативной памяти.
4. Перезапустите Redis и покажите, как ранее заблокированный ресурс оказывается доступен новому процессу, пока старый все еще работает.
5. Сформулируйте матрицу применимости Single-Node Redis.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type SingleNodeRedisInstance struct {
	mu      sync.Mutex
	storage map[string]string
	isDown  bool
}

func NewSingleNodeRedis() *SingleNodeRedisInstance {
	return &SingleNodeRedisInstance{
		storage: make(map[string]string),
	}
}

func (r *SingleNodeRedisInstance) SetNX(key, val string) bool {
	r.mu.Lock()
	defer r.mu.Unlock()
	if r.isDown {
		return false
	}
	if _, ok := r.storage[key]; ok {
		return false
	}
	r.storage[key] = val
	return true
}

func (r *SingleNodeRedisInstance) CrashAndReboot() {
	r.mu.Lock()
	defer r.mu.Unlock()
	fmt.Println("\n💥 [Hardware Crash] Redis Server rebooted! In-memory state LOST!")
	// Volatile memory reset: all active locks vanish!
	r.storage = make(map[string]string)
}

func main() {
	redis := NewSingleNodeRedis()
	resourceKey := "lock:batch:payroll"

	// 1. Worker 1 acquires lock on Single-Node Redis
	if redis.SetNX(resourceKey, "Worker-1-Token") {
		fmt.Println("Worker-1 acquired lock. Starting 1-hour payroll calculation...")
	}

	// 2. Worker 2 tries to acquire -> rejected
	if !redis.SetNX(resourceKey, "Worker-2-Token") {
		fmt.Println("Worker-2 rejected as expected: lock is busy.")
	}

	// 3. DISASTER: Single Redis crashes and restarts empty!
	redis.CrashAndReboot()

	// 4. Worker 3 arrives while Worker 1 is still computing!
	fmt.Println("\nWorker-3 attempts to acquire payroll lock...")
	if redis.SetNX(resourceKey, "Worker-3-Token") {
		fmt.Println("🚨 CATASTROPHE: Worker-3 acquired the lock because Redis rebooted empty!")
		fmt.Println("Worker-1 and Worker-3 are now executing payroll concurrently! Double payroll dispatched!")
	}
}
```

## Под капотом

Почему Redis не проектировался как распределенная блокировка:
Сальваторе Санфилиппо изначально создавал Redis как **сверхбыстрый in-memory кэш и брокер структур данных**.
Вся внутренняя архитектура подчинена минимизации задержек (sub-millisecond latency): однопоточный цикл, асинхронный сброс AOF/RDB, асинхронная репликация репликам без подтверждения кворума.
Попытка требовать от него свойств CP-системы (как etcd или Raft) противоречит заложенным архитектурным компромиссам.

## Подводные камни

- **Использование Single Redis для списания денег**: Ведет к гарантированным финансовым инцидентам при регламентных перезагрузках серверов или миграциях подов в Kubernetes.
- **Включение AOF `fsync always` без понимания последствий**: Приведет к падению производительности и преждевременному износу SSD-накопителей.

## На собеседовании

В Авито и Ozon на архитектурной секции часто спрашивают: *«Когда в продакшене оправдано использование распределенного лока на одиночном Redis вместо etcd?»*
**Ответ**: Использование одиночного Redis оправдано в сценариях, где приоритетом является **скорость и простота (Efficiency)**, а цена ошибки при сбое минимальна:
1. Дедупликация тяжелых фоновых задач по расписанию (если задача выполнится дважды раз в год — ничего страшного не произойдет).
2. Защита от Stampede / Thundering Herd при обновлении горячего кеша (если два потока одновременно прогреют кеш, база выдержит).
Если же цена сбоя — деньги, искажение инвентаря или нарушение юридических SLA, использование Single Redis категорически запрещено — требуется etcd или Consul с Fencing Tokens.
