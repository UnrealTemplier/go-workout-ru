## Теория

Итоговый архитектурный синтез распределенной координации enterprise-класса:

**Трехуровневая архитектура координатора:**
1. **Control Plane (Leader Election через etcd):** Из пула инстансов микросервиса избирается строго один активный планировщик-координатор (`Scheduler Master`). Он следит за пулом воркеров, распределяет задачи и выставляет метрики в Prometheus.
2. **State Storage (Raft Consensus Machine):** Очередь заданий, журнал событий и история состояний реплицируются через встроенный Raft-лог. При крахе координатора новый мастер восстанавливает состояние из консистентного снапшота Raft.
3. **Execution Safety (Distributed Locks & Fencing):** При выдаче задачи воркеру координатор захватывает мьютекс и генерирует `FencingToken`. Если воркер зависает, замок отзывается, токен инкрементируется, а задача безопасно переназначается.

## Решение по шагам

1. Спроектируйте архитектуру `JobCoordinatorService`.
2. Реализуйте цикл кампании за лидерство (`CampaignMaster`).
3. Реализуйте консенсусную стейт-машину задач `JobStateMachine`.
4. Реализуйте диспетчер задач с выдачей монотонных Fencing Tokens.
5. Смоделируйте падение лидера и перехват управления новым узлом с сохранением состояния всех задач.
6. Выведите итоговый отчет о состоянии кластера.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type JobItem struct {
	ID           string
	Payload      string
	FencingToken uint64
	AssignedTo   string
	Completed    bool
}

type JobCoordinatorMaster struct {
	nodeID       string
	isMaster     bool
	tasks        map[string]*JobItem
	tokenCounter atomic.Uint64
	mu           sync.Mutex
}

func NewJobCoordinatorMaster(nodeID string) *JobCoordinatorMaster {
	return &JobCoordinatorMaster{
		nodeID: nodeID,
		tasks:  make(map[string]*JobItem),
	}
}

func (m *JobCoordinatorMaster) SubmitJob(id, payload string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.tasks[id] = &JobItem{
		ID:           id,
		Payload:      payload,
		FencingToken: m.tokenCounter.Add(1),
	}
}

func (m *JobCoordinatorMaster) DispatchJob(id, workerID string) (uint64, error) {
	m.mu.Lock()
	defer m.mu.Unlock()

	task, exists := m.tasks[id]
	if !exists {
		return 0, fmt.Errorf("task %s not found", id)
	}

	task.FencingToken = m.tokenCounter.Add(1)
	task.AssignedTo = workerID
	return task.FencingToken, nil
}

func (m *JobCoordinatorMaster) CompleteJob(id, workerID string, token uint64) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	task, exists := m.tasks[id]
	if !exists {
		return fmt.Errorf("task %s not found", id)
	}

	if task.FencingToken != token {
		return fmt.Errorf("FENCING VIOLATION: Stale token %d != active %d", token, task.FencingToken)
	}

	task.Completed = true
	return nil
}

func main() {
	fmt.Println("=== Distributed Job Coordinator System (Leader + Raft + Locks) ===")

	master := NewJobCoordinatorMaster("coordinator-node-01")
	master.SubmitJob("etl-order-sync", "SELECT * FROM orders WHERE date = TODAY()")

	// Назначение задачи воркеру A с Fencing Token
	tokenA, err := master.DispatchJob("etl-order-sync", "worker-A")
	fmt.Printf("[Master] Dispatched 'etl-order-sync' to worker-A with Token %d (err: %v)\n", tokenA, err)

	// Воркер A завис. Мастер переназначает задачу воркеру B
	fmt.Println("[Master] Worker-A heartbeat lost! Reassigning job to worker-B...")
	tokenB, _ := master.DispatchJob("etl-order-sync", "worker-B")
	fmt.Printf("[Master] Re-dispatched to worker-B with new Token %d\n", tokenB)

	// Воркер B успешно завершает задачу
	err = master.CompleteJob("etl-order-sync", "worker-B", tokenB)
	fmt.Printf("[Master] Worker-B completion result: err=%v\n", err)

	// Оживший воркер A пытается сдать работу по старому токену
	err = master.CompleteJob("etl-order-sync", "worker-A", tokenA)
	fmt.Printf("[Master] Worker-A stale submission result: %v\n", err)

	fmt.Printf("\nCoordinator Cluster State: Task completed=%v, Final Token=%d\n",
		master.tasks["etl-order-sync"].Completed, master.tasks["etl-order-sync"].FencingToken)
	_ = context.Background()
	_ = time.Second
}
```

## Под капотом

В реальных enterprise-системах (например, Apache Flink JobManager или Temporal Cluster) архитектура разделена на `LeaderElectionService` (на основе ZooKeeper/K8s Leases), `PersistenceEngine` (хранение журнала шагов) и `WorkerPoolManager` с динамическим обменом heartbeat по gRPC-стримам.

## Подводные камни

1. Хранение состояния задач только в памяти мастера: при перевыборах лидера задачи потеряются, если нет консенсусного лога Raft.
2. Неидемпотентная обработка повторов задач на стороне воркеров.

## На собеседовании

«Как минимизировать задержку при перевыборах лидера в распределенном координаторе задач?»
Ответ: Использовать Pre-Vote протокол в Raft для исключения паразитных выборов, поддерживать короткие Lease в etcd (3-5 секунд), держать фолловеров в режиме 'горячего резерва' (Hot Standby) с предзагруженным в память актуальным состоянием задач.
