## Теория

Классическая задача распределенных вычислений — безопасный параллельный доступ к разделяемому ресурсу без поддержки транзакций (например, текстовый файл на сетевом диске NFS, шаре CephFS или локальный файл, разделяемый несколькими контейнерами).

Если несколько независимых процессов операционной системы одновременно открывают файл с флагом `os.O_APPEND | os.O_WRONLY` и выполняют составную запись (например, форматированный многострочный JSON или несколько вызовов `Write`), без взаимного исключения строки перемешаются (Interleaving), разрушая целостность файла.

**Решение на базе `go.etcd.io/etcd/client/v3/concurrency`:**
1. Каждый процесс создает сессию: `session, err := concurrency.NewSession(client, concurrency.WithTTL(5))`.
2. Создается распределенный мьютекс: `mutex := concurrency.NewMutex(session, "/locks/shared_file")`.
3. Перед открытием и записью вызывается `mutex.Lock(ctx)`.
4. Процесс безопасно дописывает данные в файл.
5. Вызывается `mutex.Unlock(ctx)`, передавая право записи следующему процессу из очереди ожидания etcd.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"strings"
	"sync"
	"time"
)

type SharedNetworkFile struct {
	mu      sync.Mutex
	content []string
}

func (f *SharedNetworkFile) AppendChunk(lines []string) {
	f.mu.Lock()
	defer f.mu.Unlock()
	for _, l := range lines {
		f.content = append(f.content, l)
		time.Sleep(5 * time.Millisecond) // симуляция медленного сетевого I/O
	}
}

type EtcdConcurrencyMutex struct {
	mu    sync.Mutex
	queue chan struct{}
}

func NewEtcdConcurrencyMutex() *EtcdConcurrencyMutex {
	ch := make(chan struct{}, 1)
	ch <- struct{}{} // 1 доступный слот
	return &EtcdConcurrencyMutex{queue: ch}
}

func (m *EtcdConcurrencyMutex) Lock(ctx context.Context) error {
	select {
	case <-m.queue:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func (m *EtcdConcurrencyMutex) Unlock(ctx context.Context) error {
	m.queue <- struct{}{}
	return nil
}

func RunFileWorker(id int, file *SharedNetworkFile, mutex *EtcdConcurrencyMutex, wg *sync.WaitGroup) {
	defer wg.Done()
	ctx := context.Background()

	for iter := 1; iter <= 2; iter++ {
		// 1. Захват распределенной блокировки etcd
		if err := mutex.Lock(ctx); err != nil {
			fmt.Printf("[Proc %d] Lock error: %v\n", id, err)
			return
		}

		// 2. Критическая секция: атомарная запись блока строк
		chunk := []string{
			fmt.Sprintf("=== START Process %d Block %d ===", id, iter),
			fmt.Sprintf("Process %d: writing payload record 1", id),
			fmt.Sprintf("Process %d: writing payload record 2", id),
			fmt.Sprintf("=== END Process %d Block %d ===", id, iter),
		}
		file.AppendChunk(chunk)

		// 3. Освобождение блокировки
		_ = mutex.Unlock(ctx)
		time.Sleep(10 * time.Millisecond)
	}
}

func main() {
	file := &SharedNetworkFile{}
	mutex := NewEtcdConcurrencyMutex()

	var wg sync.WaitGroup
	numProcs := 3

	fmt.Printf("Starting %d parallel processes coordinating file writes via etcd Mutex...\n\n", numProcs)
	wg.Add(numProcs)
	for i := 1; i <= numProcs; i++ {
		go RunFileWorker(i, file, mutex, &wg)
	}

	wg.Wait()

	fmt.Println("=== Final Shared File Content (Clean blocks without corruption) ===")
	for _, line := range file.content {
		if strings.HasPrefix(line, "===") {
			fmt.Println(line)
		} else {
			fmt.Println("  " + line)
		}
	}

	expectedLines := numProcs * 2 * 4
	if len(file.content) == expectedLines {
		fmt.Printf("\nSUCCESS: All %d lines written atomically without corruption!\n", expectedLines)
	}
}
```

ℹ️ Координированная запись в разделяемый файл тремя процессами через распределенный мьютекс

## Под капотом

При использовании `concurrency.NewMutex` в etcd под капотом создается префиксный ключ `/locks/shared_file/<lease_id>`. etcd назначает ревизию создания. Процессы ранжируются в строгую очередь. Каждый процесс через `etcd.Watch` ждет удаления ключа предыдущего процесса в очереди, устраняя проблему 'громоподобного стада' (Thundering Herd) и обеспечивая справедливую (Fair FIFO) сериализацию.

## Подводные камни

1. Забывание закрытия сессии `session.Close()`: аренда останется активной в etcd на полный TTL, блокируя доступ к файлу другим процессам.
2. Неучет разрыва сети с etcd: если сессия потеряна, мьютекс недействителен, и процесс обязан прекратить запись в файл.

## На собеседовании

«Как в Linux гарантировать неделимость дозаписи в файл на локальном диске без распределенного мьютекса?»
Ответ: В стандарте POSIX операции записи с флагом `O_APPEND` гарантируют атомарность на уровне ядра ОС, если размер записываемого буфера не превышает `PIPE_BUF` (обычно 4096 байт). Однако если данные превышают 4 КБ или запись идет через NFS/SMB по сети, POSIX не гарантирует неделимость, и распределенный мьютекс обязателен.
