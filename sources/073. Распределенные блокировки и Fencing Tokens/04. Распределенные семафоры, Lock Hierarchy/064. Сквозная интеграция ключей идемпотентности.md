# Сквозная интеграция ключей идемпотентности и распределенных блокировок

## Условие

64. **Idempotency + distributed locks.**: Даже с distributed locks используйте idempotency keys. Lock может быть lost (TTL expiry), task может быть executed twice.

### Исходная формулировка

**Idempotency + distributed locks.**: Даже с distributed locks используйте idempotency keys. Lock может быть lost (TTL expiry), task может быть executed twice.

## Теория

Частая иллюзия разработчиков: «Если у нас есть распределенная блокировка, наша система автоматически защищена от повторных списаний и дубликатов».

**Это опасное заблуждение.**
Блокировка может быть потеряна в любой момент по трем естественным причинам:
1. **Истечение TTL:** Обработка длилась дольше ожидаемого, блокировка снялась автоматически.
2. **Watchdog Network Failure:** Сбой сети разорвал KeepAlive, и координатор посчитал клиента умершим.
3. **Краш процесса после выполнения работы, но до отправки ACK:** Воркер списал средства со счета клиента, но упал до отправки ответа. Планировщик повторно отправит задачу другому воркеру.

Единственный способ гарантировать надежность уровня финансовых транзакций (Banking-Grade Reliability) — **сочетать распределенные блокировки с ключами идемпотентности (Idempotency Keys)**:
- **Lock:** Защищает от одновременного параллельного выполнения задачи несколькими нодами (Mutual Exclusion / Concurrency Control).
- **Idempotency Key:** Защищает от повторного последовательного выполнения той же задачи при ретраях и сбоях.

## Решение по шагам

1. Создайте структуру `PaymentService` с таблицей идемпотентных записей `idempotency_store`.
2. Реализуйте метод `ProcessPayment(ctx, idempotencyKey, amount)`.
3. Захватите блокировку по ключу `lock:payment:{idempotencyKey}`.
4. Проверьте статус операции в `idempotency_store`: если `COMPLETED`, немедленно верните сохраненный результат без повторного списания.
5. Если статус `NEW` — выполните списание, сохраните результат в `idempotency_store` со статусом `COMPLETED`.
6. Освободите блокировку.
7. Продемонстрируйте корректную обработку ретраев.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type PaymentResult struct {
	TransactionID string
	Amount        int64
	Status        string
}

type PaymentService struct {
	mu           sync.Mutex
	idempotency  map[string]PaymentResult // IdempotencyKey -> Result
	locks        map[string]bool          // LockKey -> IsHeld
	totalBalance int64
}

func NewPaymentService(initialBalance int64) *PaymentService {
	return &PaymentService{
		idempotency:  make(map[string]PaymentResult),
		locks:        make(map[string]bool),
		totalBalance: initialBalance,
	}
}

func (s *PaymentService) tryLock(key string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.locks[key] {
		return false
	}
	s.locks[key] = true
	return true
}

func (s *PaymentService) unlock(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.locks, key)
}

func (s *PaymentService) ExecutePayment(ctx context.Context, idemKey string, amount int64) (PaymentResult, error) {
	lockKey := fmt.Sprintf("lock:payment:%s", idemKey)

	// 1. Захват распределенной блокировки для исключения параллельных гонок
	if !s.tryLock(lockKey) {
		return PaymentResult{}, errors.New("concurrent payment processing in flight, retry later")
	}
	defer s.unlock(lockKey)

	s.mu.Lock()
	// 2. Проверка ключа идемпотентности внутри защищенной секции
	if existing, found := s.idempotency[idemKey]; found {
		s.mu.Unlock()
		fmt.Printf("[IDEMPOTENCY HIT] Returning cached result for key %s without debiting again\n", idemKey)
		return existing, nil
	}

	// 3. Выполнение бизнес-логики (списание средств)
	s.totalBalance -= amount
	res := PaymentResult{
		TransactionID: fmt.Sprintf("tx-%d", time.Now().UnixNano()),
		Amount:        amount,
		Status:        "SUCCESS",
	}
	s.idempotency[idemKey] = res
	s.mu.Unlock()

	fmt.Printf("[PAYMENT PROCESSED] Debited %d. Remaining balance: %d\n", amount, s.totalBalance)
	return res, nil
}

func main() {
	service := NewPaymentService(1000)
	ctx := context.Background()
	clientKey := "order-request-uuid-888"

	// Первая попытка списания
	res1, err := service.ExecutePayment(ctx, clientKey, 200)
	fmt.Printf("Attempt 1: TxID=%s, Err=%v\n", res1.TransactionID, err)

	// Повторная попытка (например, сетевой ретрай клиента из-за сбоя связи)
	res2, err := service.ExecutePayment(ctx, clientKey, 200)
	fmt.Printf("Attempt 2 (Retry): TxID=%s, Err=%v\n", res2.TransactionID, err)

	if res1.TransactionID == res2.TransactionID && service.totalBalance == 800 {
		fmt.Println("\nSUCCESS: Idempotency Key guaranteed exactly-once balance debit!")
	} else {
		panic("CRITICAL ERROR: Duplicate charge occurred!")
	}
}
```

## Под капотом

В архитектурах уровня Stripe и Adyen запись о ключе идемпотентности и финансовая проводка выполняются в единой ACID-транзакции реляционной СУБД с изоляцией Serializable. Распределенная блокировка на входе (API Gateway) отсекает дублирующие параллельные HTTP-запросы на раннем этапе, защищая базу данных от шторма транзакций.

## Подводные камни

1. Хранение ключей идемпотентности только в памяти: при перезагрузке пода кэш сотрется, и повторный запрос выполнит списание заново.
2. Отсутствие TTL у записей идемпотентности: база ключей идемпотентности разрастается до сотен миллионов строк; обычно их хранят от 24 часов до 7 дней.

## На собеседовании

«Что произойдет, если запрос упадет ровно в момент между списанием в БД и освобождением блокировки в Redis?»
Ответ: Блокировка автоматически истечет по TTL в Redis. При повторном запросе клиента с тем же `IdempotencyKey` новая блокировка будет успешно захвачена, код обратится к таблице идемпотентности в БД, увидит уже сохраненный статус `COMPLETED` и вернет сохраненный ответ клиенту без повторного списания.
