# Мониторинг, метрики и алертинг распределенных блокировок (Lock Alerting)

## Условие

52. **Lock alerting**: Алерт при:
    * High lock contention (>50% timeout rate)
    * Long lock hold times (>1 min)
    * Lock acquisition failures

### Исходная формулировка

**Lock alerting**: Алерт при:
* High lock contention (>50% timeout rate)
* Long lock hold times (>1 min)
* Lock acquisition failures

## Теория

Распределенные блокировки являются критической точкой отказа (Single Point of Failure / Bottleneck) в архитектуре микросервисов. Неправильная настройка или деградация бэкенда блокировок способна парализовать весь кластер.

Для надежной эксплуатации в Production необходим непрерывный мониторинг трех ключевых индикаторов (SLI):
1. **Lock Contention (Конкуренция за блокировку):** Доля попыток захвата, завершившихся по таймауту. Если более 50% попыток захвата `TryLock` или `Acquire` завершаются неудачей из-за занятости ресурса, это свидетельствует о чрезмерной длительности критической секции или недостаточной гранулярности блокировок (необходим шардинг ресурсов).
2. **Lock Hold Time (Время удержания):** Гистограмма и P99 времени между `Acquire` и `Release`. Удержание блокировки дольше 1 минуты — критическая аномалия, указывающая на зависшие сетевые вызовы внутри критической секции или утечку блокировки без вызова `Release`.
3. **Acquisition Failure Rate (Ошибки захвата):** Ошибки сетевого взаимодействия с координатором (etcd timeout, redis unreachable, consul session loss). Рост этой метрики требует немедленного пейджинг-алерта дежурному SRE.

## Решение по шагам

1. Создайте структуру метрик `LockMetrics` (счетчики попыток, отказов по таймауту, системных ошибок и гистограмму длительности).
2. Оберните распределенный мьютекс в декоратор `InstrumentedLock`.
3. В методе `Acquire` замеряйте длительность ожидания и инкрементируйте счетчики сбоев.
4. В методе `Release` вычисляйте фактическое время удержания блокировки (`holdDuration`).
5. Реализуйте функцию оценки алертов `CheckAlertRules`, проверяющую пороги: contention > 50%, hold time > 1 мин, failure rate > 5%.
6. Продемонстрируйте срабатывание алертов в демонстрационном коде.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type LockMetrics struct {
	TotalAttempts atomic.Uint64
	Timeouts      atomic.Uint64
	SystemErrors  atomic.Uint64
	Successes     atomic.Uint64
	MaxHoldNano   atomic.Int64
}

type InstrumentedLock struct {
	mu         sync.Mutex
	isHeld     bool
	owner      string
	acquiredAt time.Time
	metrics    *LockMetrics
}

func NewInstrumentedLock(metrics *LockMetrics) *InstrumentedLock {
	return &InstrumentedLock{metrics: metrics}
}

func (l *InstrumentedLock) TryAcquire(ctx context.Context, owner string, timeout time.Duration) (func(), error) {
	l.metrics.TotalAttempts.Add(1)
	start := time.Now()

	deadline := time.Now().Add(timeout)
	for {
		l.mu.Lock()
		if !l.isHeld {
			l.isHeld = true
			l.owner = owner
			l.acquiredAt = time.Now()
			l.mu.Unlock()
			l.metrics.Successes.Add(1)

			// Возвращаем функцию освобождения
			releaseFunc := func() {
				l.mu.Lock()
				defer l.mu.Unlock()
				if l.isHeld && l.owner == owner {
					l.isHeld = false
					holdDuration := time.Since(l.acquiredAt)
					// Обновляем максимальное время удержания
					for {
						oldMax := l.metrics.MaxHoldNano.Load()
						if int64(holdDuration) <= oldMax || l.metrics.MaxHoldNano.CompareAndSwap(oldMax, int64(holdDuration)) {
							break
						}
					}
				}
			}
			return releaseFunc, nil
		}
		l.mu.Unlock()

		if time.Now().After(deadline) {
			l.metrics.Timeouts.Add(1)
			return nil, errors.New("lock contention: timeout waiting for lock")
		}

		select {
		case <-ctx.Done():
			l.metrics.SystemErrors.Add(1)
			return nil, ctx.Err()
		case <-time.After(10 * time.Millisecond):
		}
	}
}

func (l *InstrumentedLock) CheckAlerts() []string {
	var alerts []string
	total := l.metrics.TotalAttempts.Load()
	if total == 0 {
		return alerts
	}

	timeouts := l.metrics.Timeouts.Load()
	contentionRate := float64(timeouts) / float64(total)
	if contentionRate > 0.50 {
		alerts = append(alerts, fmt.Sprintf("CRITICAL ALERT: High Lock Contention (%.1f%% timeouts)", contentionRate*100))
	}

	maxHold := time.Duration(l.metrics.MaxHoldNano.Load())
	if maxHold > 100*time.Millisecond { // в продакшене > 1 min, в тесте порог 100ms
		alerts = append(alerts, fmt.Sprintf("WARNING ALERT: Long Lock Hold Time detected: %v", maxHold))
	}

	return alerts
}

func main() {
	metrics := &LockMetrics{}
	lock := NewInstrumentedLock(metrics)

	// Симуляция: Клиент 1 удерживает лок долго (150ms)
	release1, err := lock.TryAcquire(context.Background(), "worker-1", 50*time.Millisecond)
	if err != nil {
		panic(err)
	}

	var wg sync.WaitGroup
	// 5 клиентов параллельно пытаются захватить лок с коротким таймаутом (будет contention)
	for i := 2; i <= 6; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			_, err := lock.TryAcquire(context.Background(), fmt.Sprintf("worker-%d", id), 20*time.Millisecond)
			if err != nil {
				// Ожидаемый таймаут
			}
		}(i)
	}

	time.Sleep(150 * time.Millisecond)
	release1()
	wg.Wait()

	fmt.Printf("Metrics Summary: Total=%d, Success=%d, Timeouts=%d\n",
		metrics.TotalAttempts.Load(), metrics.Successes.Load(), metrics.Timeouts.Load())

	alerts := lock.CheckAlerts()
	for _, alert := range alerts {
		fmt.Println("[ALERT ENGINE]", alert)
	}
}
```

## Под капотом

В мониторинге Prometheus распределенные блокировки экспортируют метрики: `distributed_lock_acquire_duration_seconds` (гистограмма ожидания очереди), `distributed_lock_held_duration_seconds` (гистограмма владения), и счетчики `distributed_lock_errors_total{reason="contention|network|lease_expired"}`. Настройка алертов основана на формуле PromQL: `rate(distributed_lock_errors_total[5m]) / rate(distributed_lock_acquire_total[5m]) > 0.5`.

## Подводные камни

1. Использование неатомарных операций при сборе метрик в высоконагруженных циклах: используйте `sync/atomic` или официальный Prometheus SDK.
2. Алерт по единичному сбою: кратковременный всплеск нагрузки не должен вызывать ложный звонок дежурному, применяйте `for: 5m` в правилах Prometheus Alertmanager.

## На собеседовании

«Как расследовать инцидент, когда в распределенной системе внезапно подскакивает Lock Contention до 90%?»
Ответ: 1) Анализируем метрику `held_duration`: если время удержания выросло, ищем застрявшие внешние вызовы (БД, сетевые запросы) внутри критической секции по OpenTelemetry спанам. 2) Анализируем распределение ключей: если все клиенты стучатся в один ключ, переходим на партиционирование (Sharded Locking). 3) Проверяем наличие GC-пауз или зависания фоновых воркеров.
