# TryLock с Deadline через etcd Watch вместо Busy-Polling

## Условие

53. **TryLock с Deadline.**: Реализуйте `TryLock(ctx, timeout)` через etcd Watch: если ключ занят, ждём `DELETE` event с `ctx.Done()` таймаутом. Сравните с busy-polling. Объясните, почему Watch эффективнее (нет нагрузки на etcd), но сложнее в реализации.

### Исходная формулировка

**TryLock с Deadline.**: Реализуйте `TryLock(ctx, timeout)` через etcd Watch: если ключ занят, ждём `DELETE` event с `ctx.Done()` таймаутом. Сравните с busy-polling. Объясните, почему Watch эффективнее (нет нагрузки на etcd), но сложнее в реализации.

## Теория

При попытке захвата распределенной блокировки наивный подход использует **Busy-Polling (активный опрос в цикле)**: клиент каждые 50 миллисекунд отправляет сетевой запрос к серверу координации, проверяя, не освободился ли ключ.

Недостатки Busy-Polling:
- **Колоссальная нагрузка на CPU и сеть:** 1000 ожидающих воркеров генерируют 20 000 запросов в секунду на etcd/Redis, вызывая деградацию всего кластера.
- **Низкая реактивность:** Блокировка может освободиться в момент \(T\), а клиент узнает об этом только в \(T + \Delta\), когда сработает таймер опроса.

**Подход на основе Reactive Watch (etcd Watch API):**
1. Клиент пытается создать ключ через транзакцию `Txn`.
2. Если ключ уже существует, клиент выставляет подписку `client.Watch(ctx, lockKey)`.
3. Горутина блокируется на чтении канала событий etcd, ожидая события `mvccpb.DELETE`.
4. etcd отправляет push-уведомление по постоянному gRPC-соединению ровно в момент удаления ключа.
5. При получении `DELETE` клиент повторяет попытку захвата. При истечении дедлайна контекста `ctx.Done()` подписка автоматически аннулируется.

**Сравнение:** Watch снижает число сетевых пакетов до \(O(1)\), исключает лишнюю нагрузку, но требует корректной обработки сетевых переподключений и потери стрима.

## Решение по шагам

1. Создайте структуру симуляции `MockWatchEtcd` с поддержкой каналов уведомлений об удалении ключей.
2. Реализуйте метод `TryLock(ctx, key, timeout)`.
3. Попробуйте захватить ключ атомарно.
4. Если занято, создайте канал подписки на удаление ключа.
5. Запустите `select` по трем каналам: `eventChan` (удаление ключа), `deadlineCtx.Done()` (таймаут) и `parentCtx.Done()`.
6. При получении события удаления повторите попытку атомарного захвата.
7. Продемонстрируйте мгновенную передачу замка без цикла постоянного опроса.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type MockWatchStore struct {
	mu       sync.Mutex
	holders  map[string]string         // key -> owner
	watchers map[string][]chan struct{} // key -> list of notify channels
}

func NewMockWatchStore() *MockWatchStore {
	return &MockWatchStore{
		holders:  make(map[string]string),
		watchers: make(map[string][]chan struct{}),
	}
}

func (s *MockWatchStore) TryAcquire(key, owner string) (bool, <-chan struct{}) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if _, exists := s.holders[key]; !exists {
		s.holders[key] = owner
		return true, nil
	}

	// Ключ занят: регистрируем канал уведомления
	ch := make(chan struct{}, 1)
	s.watchers[key] = append(s.watchers[key], ch)
	return false, ch
}

func (s *MockWatchStore) Release(key, owner string) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if s.holders[key] == owner {
		delete(s.holders, key)
		// Оповещаем всех наблюдателей о событии DELETE
		for _, ch := range s.watchers[key] {
			select {
			case ch <- struct{}{}:
			default:
			}
		}
		delete(s.watchers, key)
	}
}

type EtcdWatchMutex struct {
	store *MockWatchStore
	key   string
	owner string
}

func NewEtcdWatchMutex(store *MockWatchStore, key, owner string) *EtcdWatchMutex {
	return &EtcdWatchMutex{store: store, key: key, owner: owner}
}

func (m *EtcdWatchMutex) TryLock(ctx context.Context, timeout time.Duration) error {
	deadlineCtx, cancel := context.WithTimeout(ctx, timeout)
	defer cancel()

	for {
		acquired, deleteChan := m.store.TryAcquire(m.key, m.owner)
		if acquired {
			return nil
		}

		// Реактивное ожидание события DELETE вместо busy-polling
		select {
		case <-deadlineCtx.Done():
			return errors.New("trylock: timeout exceeded while waiting for lock release")
		case <-ctx.Done():
			return ctx.Err()
		case <-deleteChan:
			// Ключ освободился, немедленно повторяем попытку
		}
	}
}

func (m *EtcdWatchMutex) Unlock() {
	m.store.Release(m.key, m.owner)
}

func main() {
	store := NewMockWatchStore()

	m1 := NewEtcdWatchMutex(store, "/resource/db_sync", "client-1")
	m2 := NewEtcdWatchMutex(store, "/resource/db_sync", "client-2")

	// Клиент 1 успешно захватывает лок
	if err := m1.TryLock(context.Background(), time.Second); err != nil {
		panic(err)
	}
	fmt.Println("[Client 1] Acquired lock via Watch store")

	// Клиент 2 запускает TryLock с таймаутом 500мс
	start := time.Now()
	go func() {
		time.Sleep(100 * time.Millisecond)
		fmt.Println("[Client 1] Releasing lock...")
		m1.Unlock()
	}()

	err := m2.TryLock(context.Background(), 500*time.Millisecond)
	elapsed := time.Since(start)
	if err != nil {
		fmt.Println("[Client 2] Failed:", err)
	} else {
		fmt.Printf("[Client 2] Successfully acquired lock via Watch notification after %v!\n", elapsed)
		m2.Unlock()
	}
}
```

## Под капотом

Под капотом etcd Watcher мультиплексирует подписки через один HTTP/2 gRPC стрим `Watch.Watch`. Сервер etcd поддерживает b-tree индексы ревизий в памяти. Когда транзакция удаляет ключ (`DeleteRange`), etcd в цикле обхода фильтрует активных наблюдателей по префиксу и пушит сообщение `WatchResponse` в сетевой сокет, мгновенно пробуждая горутину клиента на стороне Go.

## Подводные камни

1. Утечка каналов Watch при выходе по таймауту: если контекст отменился, подписка на Watch обязана быть отменена, иначе сервер продолжит слать события.
2. Пропуск события между `TryAcquire` и `Watch`: если ключ удалился до того, как выставлен Watch, клиент может зависнуть. Код должен повторно проверять наличие ключа после регистрации подписки.

## На собеседовании

«Что такое Thundering Herd при использовании Watch на одиночный ключ и как etcd Concurrency решает эту проблему?»
Ответ: Если 1000 клиентов слушают один и тот же ключ `/lock`, в момент `DELETE` все 1000 клиентов одновременно просыпаются и посылают запросы `PUT` (Thundering Herd). Решение etcd: каждый клиент создает ключ со своим lease id `/lock/1`, `/lock/2` (sequential keys) и выставляет Watch строго на предыдущую ревизию (`prev revision`). При освобождении замка просыпается строго один следующий клиент.
