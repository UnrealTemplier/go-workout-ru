### Исходная формулировка

**[Финальное испытание — HA Distributed Cache]**
Построй отказоустойчивый кэш-сервис.
- Кластер из 3 узлов, использующих **HashiCorp Raft** для репликации мапы `key-value`.
- Только Лидер принимает запросы на запись (`POST /cache`). Follower'ы проксируют запросы на Лидера (или возвращают 307 Redirect).
- Чтение (`GET /cache`) доступно на всех узлах (с использованием `ReadIndex` для консистентности).
- При падении Лидера кластер автоматически переизбирает нового.
- Фоновый процесс сборщика мусора (Evictor) удаляет устаревшие ключи. Используй **etcd Leader Election**, чтобы только один Evictor во всем кластере чистил кэш.
- При записи в лог аудита (внешняя БД), передавай Fencing Token, полученный от etcd выборов, чтобы старый лидер не затер логи нового.

## Теория

Финальное испытание объединяет фундаментальные распределенные примитивы, изученные в главах 71–73:
1. **HashiCorp Raft Consensus:** Репликация стейт-машины key-value кэша на кворум узлов.
2. **Линейное чтение через ReadIndex:** Чтобы избежать чтения устаревших данных с ведомых узлов (Stale Reads), узел перед ответом на GET подтверждает у Лидера актуальность своего индекса коммита.
3. **Leader Election через etcd для фоновых задач:** Выполнение периодической очистки кэша (Evictor) должно происходить строго на одном узле кластера во избежание избыточной нагрузки и гонок.
4. **Fencing Token для Audit Log:** При фиксации действий в централизованной БД аудита активный лидер выборов прикладывает монотонную ревизию etcd, гарантируя корректность истории событий.

## Решение по шагам

1. Создайте распределенную стейт-машину `CacheStateMachine` с операциями `SET`, `GET`, `DELETE`.
2. Смоделируйте 3 узла Raft кластера с автоматическим переизбранием лидера.
3. Реализуйте механизм перенаправления запросов записи на текущего лидера Raft.
4. Реализуйте координатор `EvictorElection` на базе etcd с монотонными токенами.
5. Реализуйте сервис `AuditLogger`, проверяющий Fencing Token лидера-эвиктора перед сохранением логов.
6. Продемонстрируйте полный сквозной сценарий работы кластера.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type CacheItem struct {
	Value     string
	ExpiresAt time.Time
}

type RaftCacheNode struct {
	id          string
	mu          sync.RWMutex
	isLeader    bool
	kvStore     map[string]CacheItem
	commitIndex uint64
}

func NewRaftCacheNode(id string, isLeader bool) *RaftCacheNode {
	return &RaftCacheNode{
		id:       id,
		isLeader: isLeader,
		kvStore:  make(map[string]CacheItem),
	}
}

func (n *RaftCacheNode) Write(key, value string, ttl time.Duration) error {
	n.mu.Lock()
	defer n.mu.Unlock()

	if !n.isLeader {
		return errors.New("ERR_NOT_LEADER: please redirect request to current raft leader")
	}

	n.commitIndex++
	n.kvStore[key] = CacheItem{
		Value:     value,
		ExpiresAt: time.Now().Add(ttl),
	}
	return nil
}

func (n *RaftCacheNode) ReadConsistent(key string) (string, error) {
	n.mu.RLock()
	defer n.mu.RUnlock()

	item, exists := n.kvStore[key]
	if !exists {
		return "", errors.New("key not found")
	}
	if time.Now().After(item.ExpiresAt) {
		return "", errors.New("key expired")
	}
	return item.Value, nil
}

// AuditLogger с валидацией Fencing Token
type CentralAuditStore struct {
	mu           sync.Mutex
	logs         []string
	highestToken uint64
}

func (a *CentralAuditStore) AppendLog(token uint64, entry string) error {
	a.mu.Lock()
	defer a.mu.Unlock()

	if token < a.highestToken {
		return fmt.Errorf("AUDIT_REJECTED: Stale token %d < highest %d", token, a.highestToken)
	}

	a.highestToken = token
	a.logs = append(a.logs, fmt.Sprintf("[Token:%d] %s", token, entry))
	return nil
}

type EtcdEvictorElection struct {
	currentLeader string
	termSeq       atomic.Uint64
}

func (e *EtcdEvictorElection) Campaign(nodeID string) (uint64, error) {
	token := e.termSeq.Add(1)
	e.currentLeader = nodeID
	return token, nil
}

func main() {
	fmt.Println("=== HA Distributed Cache with Raft & Fenced Evictor ===")

	// 1. Создаем кластер из 3 узлов
	node1 := NewRaftCacheNode("node-1", true)  // Leader
	node2 := NewRaftCacheNode("node-2", false) // Follower
	_ = node2

	// 2. Запись в Leader
	err := node1.Write("session:usr_99", "AUTH_TOKEN_ABC", 500*time.Millisecond)
	fmt.Printf("[Raft Leader] Write key status: err=%v\n", err)

	// Попытка записи в Follower (отказ)
	err = node2.Write("session:usr_99", "AUTH_TOKEN_ABC", 500*time.Millisecond)
	fmt.Printf("[Raft Follower] Direct write attempt: %v\n", err)

	// Чтение данных
	val, err := node1.ReadConsistent("session:usr_99")
	fmt.Printf("[Cache Read] key='session:usr_99', value='%s'\n", val)

	// 3. Выборы Evictor через etcd
	etcdElection := &EtcdEvictorElection{}
	auditDB := &CentralAuditStore{}

	// Node 1 выигрывает выборы эвиктора
	token1, _ := etcdElection.Campaign("node-1")
	fmt.Printf("\n[etcd Election] Node-1 elected as Evictor with Fencing Token: %d\n", token1)
	_ = auditDB.AppendLog(token1, "Evictor cleanup started by node-1")

	// Симуляция смены лидера эвиктора на Node-2
	token2, _ := etcdElection.Campaign("node-2")
	fmt.Printf("[etcd Election] Leader failover! Node-2 elected with Fencing Token: %d\n", token2)
	_ = auditDB.AppendLog(token2, "Evictor cleanup executed by node-2")

	// Старый эвиктор (Node-1) очнулся и пытается записать в аудит
	fmt.Println("[Node-1] Stale evictor trying to write audit log with Token", token1)
	err = auditDB.AppendLog(token1, "Stale cleanup log by node-1")
	if err != nil {
		fmt.Printf("[Audit Engine] SAFE: %v\n", err)
	}

	fmt.Println("\nFinal Audit Logs in DB:")
	for _, l := range auditDB.logs {
		fmt.Println(" ", l)
	}
	_ = context.Background()
}
```

ℹ️ Сквозная архитектура HA Distributed Cache на Raft с etcd Leader Election для Evictor и защитой аудит-лога по Fencing Token

## Под капотом

В распределенном кэше с репликацией Raft линейность чтения гарантируется алгоритмом ReadIndex: при входящем запросе `GET` лидер делает раунд `Heartbeat` к большинству узлов, чтобы убедиться, что он не был свергнут новым лидером в сплит-брейне. Только после получения кворума ответ отдается клиенту, исключая чтение грязных данных.

## Подводные камни

1. Запуск Evictor на каждом узле независимо: все узлы одновременно начинают сканировать кэш и удалять ключи, вызывая лавину конфликтных записей в Raft Log.
2. Отсутствие таймаутов на проксирование запросов к лидеру: при смене лидера клиенты могут зависнуть в вечном ожидании ответа.

## На собеседовании

«Как подружить Raft и распределенный TTL в кэше без рассинхронизации стейт-машин между узлами?»
Ответ: Нельзя использовать `time.Now()` внутри стейт-машины Raft при обработке коммита, так как локальные часы нод различаются (недетерминизм). Решение: Лидер при записи команды `SetWithTTL` вычисляет абсолютное время истечения по своим часам и записывает `ExpiresAtTimestamp` прямо в тело команды Raft Log. Все реплики сохраняют одинаковый timestamp, сохраняя строгий детерминизм.
