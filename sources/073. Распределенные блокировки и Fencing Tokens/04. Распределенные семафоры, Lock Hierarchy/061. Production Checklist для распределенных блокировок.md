## Теория

В распределенных системах термин «Distributed Mutex» обманчив. Классический мьютекс в многопоточном программировании (например, `sync.Mutex` в Go) опирается на общую память и атомарные процессорные инструкции `CMPXCHG`, гарантируя 100% взаимное исключение на уровне аппаратуры ядра.

**Распределенная блокировка — это вероятностный механизм координации (Best-Effort Coordination)**. Из-за асинхронной природы сетей, GC-пауз и сбоев оборудования любая аренда (Lease) может истечь, пока клиент продолжает считать себя владельцем. Без монотонного Fencing Token распределенная блокировка фундаментально **production-небезопасна**.

**Обязательный Production Checklist защиты блокировок:**
1. **`max_lock_hold_time`:** Жесткий лимит общего времени удержания (например, не более 60 секунд). Если операция превышает этот порог, генерируется критический алерт, а локальный контекст выполнения отменяется.
2. **`lease_renew_limit`:** Ограничение числа автоматических продлений аренды (например, максимум 10 продлений по 5 секунд). Это спасает систему от вечной блокировки зависшего процесса, чей watchdog продолжает механически обновлять ключ.
3. **`lock_staleness_check`:** Внутри критической секции код обязан периодически проверять валидность блокировки перед каждым вызовом внешнего I/O.

## Решение по шагам

1. Создайте структуру `SafeDistributedLockGuard` с полями `MaxHoldTime`, `MaxRenewCount`, `RenewInterval`.
2. Реализуйте метод `ExecuteGuarded(ctx, taskFn)` с запуском контролируемого продления.
3. Ограничьте количество продлений счетчиком `renewCount`. По достижении лимита прекратите продление и отмените `taskCtx`.
4. Внутри `taskFn` организуйте проверку `ctx.Err()`.
5. Продемонстрируйте корректный аварийный останов зависшей задачи.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type ProductionLockConfig struct {
	ResourceName    string
	MaxHoldTime     time.Duration
	RenewInterval   time.Duration
	MaxRenewCount   int
	AlertCallback   func(msg string)
}

type SafeLockController struct {
	cfg ProductionLockConfig
	mu  sync.Mutex
}

func NewSafeLockController(cfg ProductionLockConfig) *SafeLockController {
	return &SafeLockController{cfg: cfg}
}

func (c *SafeLockController) RunWithGuard(parentCtx context.Context, workerID string, taskFn func(ctx context.Context) error) error {
	// Создаем контекст с предельным таймаутом удержания
	guardCtx, cancel := context.WithTimeout(parentCtx, c.cfg.MaxHoldTime)
	defer cancel()

	acquiredAt := time.Now()
	renewCount := 0
	renewTicker := time.NewTicker(c.cfg.RenewInterval)
	defer renewTicker.Stop()

	stopRenew := make(chan struct{})
	defer close(stopRenew)

	// Фоновый Watchdog с ограничением числа продлений
	go func() {
		for {
			select {
			case <-stopRenew:
				return
			case <-guardCtx.Done():
				return
			case <-renewTicker.C:
				renewCount++
				if renewCount > c.cfg.MaxRenewCount {
					msg := fmt.Sprintf("ALERT: Lock %s exceeded max renew limit (%d). Terminating task!",
						c.cfg.ResourceName, c.cfg.MaxRenewCount)
					c.cfg.AlertCallback(msg)
					cancel() // принудительно отменяем зависшую задачу
					return
				}
				fmt.Printf("[Watchdog] Renewed lock %s (count: %d/%d)\n",
					c.cfg.ResourceName, renewCount, c.cfg.MaxRenewCount)
			}
		}
	}()

	// Выполнение бизнес-логики
	err := taskFn(guardCtx)

	holdDuration := time.Since(acquiredAt)
	if holdDuration > c.cfg.MaxHoldTime/2 {
		c.cfg.AlertCallback(fmt.Sprintf("WARNING: Lock held duration %v approached max threshold", holdDuration))
	}

	return err
}

func main() {
	cfg := ProductionLockConfig{
		ResourceName:  "order_export_job",
		MaxHoldTime:   500 * time.Millisecond,
		RenewInterval: 100 * time.Millisecond,
		MaxRenewCount: 3, // разрешено максимум 3 продления (300мс)
		AlertCallback: func(msg string) {
			fmt.Printf(">>> [SRE_ALERT_BUS] %s\n", msg)
		},
	}

	controller := NewSafeLockController(cfg)

	// Симуляция зависшей задачи
	err := controller.RunWithGuard(context.Background(), "worker-99", func(ctx context.Context) error {
		fmt.Println("[Task] Started heavy processing loop...")
		for step := 1; step <= 10; step++ {
			select {
			case <-ctx.Done():
				fmt.Println("[Task] Received abort signal, performing graceful rollback!")
				return ctx.Err()
			case <-time.After(80 * time.Millisecond):
				fmt.Printf("[Task] Completed step %d\n", step)
			}
		}
		return nil
	})

	if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
		fmt.Printf("Task aborted safely by production lock guard: %v\n", err)
	}
}
```

## Под капотом

В реальных сбоях процесс может зависнуть в бесконечном цикле или блокирующем системном вызове `futex` / `epoll_wait`, при этом фоновая горутина watchdog (KeepAlive) на основе сетевых таймеров продолжает крутиться в рантайме Go и бесконечно продлевать lease. Ограничение `MaxRenewCount` и `MaxHoldTime` аппаратно разрывает эту петлю, освобождая ресурс для живых нод кластера.

## Подводные камни

1. Отсутствие обработки `ctx.Done()` в коде задачи: если код не проверяет отмену контекста, отмена таймера не остановит CPU-нагрузку.
2. Слишком короткий `RenewInterval`: создает паразитный флуд сетевыми запросами к etcd/Redis.

## На собеседовании

«Почему распределенная блокировка без Fencing Token считается antipattern в mission-critical системах?»
Ответ: Ни один распределенный протокол не способен гарантировать, что процесс не испытает задержку после проверки лока и до записи в хранилище. Процесс может быть остановлен гипервизором (vCPU steal time), уйти в своп или длинную паузу GC. В этот момент замок перехватывается другим воркером. Без Fencing Token на стороне хранилища оба воркера запишут данные, вызвав повреждение базы данных (Split-Brain).
