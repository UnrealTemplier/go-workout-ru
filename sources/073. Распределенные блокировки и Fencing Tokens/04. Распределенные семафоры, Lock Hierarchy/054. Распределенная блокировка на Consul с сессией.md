# Распределенная блокировка на Consul с сессией и fencing

## Условие

54. **Распределенная блокировка на Consul с сессией и fencing.**: Используйте Consul сессию с монотонным ID (`Session.Create` возвращает ID). Этот ID можно использовать как fencing token. Передавайте его в запросы к сервису, сервис проверяет, что ID не меньше предыдущего использованного.

### Исходная формулировка

**Распределенная блокировка на Consul с сессией и fencing.**: Используйте Consul сессию с монотонным ID (`Session.Create` возвращает ID). Этот ID можно использовать как fencing token. Передавайте его в запросы к сервису, сервис проверяет, что ID не меньше предыдущего использованного.

## Теория

HashiCorp Consul предоставляет первоклассный механизм распределенных блокировок на основе KV-хранилища и **Consul Sessions**.

Механизм работы Consul Lock:
1. **Создание сессии:** Клиент создает сессию с помощью `session.Create(&SessionEntry{TTL: "15s", Behavior: SessionBehaviorDelete})`. Consul генерирует уникальный строковый или числовой `SessionID`.
2. **Захват ключа через `acquire`:** Клиент выполняет запрос записи ключа с параметром `?acquire=<SessionID>`. Consul атомарно проверяет, не удерживается ли ключ другой активной сессией. Если свободен — ключ переходит во владение сессии, а значение поля `ModifyIndex` инкрементируется.
3. **Session ID как Fencing Token:** `ModifyIndex` или порядковый номер сессии служит монотонным Fencing Token. Клиент отправляет этот токен целевому сервису. Сервис отвергает операции с токеном ниже текущего.
4. **Health Check и TTL:** Consul агент регулярно обновляет TTL сессии (`session.Renew`). Если агент или узел падают, Consul аннулирует сессию и автоматически освобождает ключ.

## Решение по шагам

1. Смоделируйте Consul Session API: методы `CreateSession`, `RenewSession`, `AcquireLockKey`.
2. Сгенерируйте монотонный `SessionID` и свяжите его с `ModifyIndex`.
3. Создайте бизнес-сервис `AccountService`, хранящий `lastKnownSessionIndex`.
4. Реализуйте метод `TransferMoney(sessionIndex, amount)`.
5. Продемонстрируйте защиту от зомби-воркера со старой Consul-сессией.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type ConsulSession struct {
	ID        string
	TTL       time.Duration
	CreatedAt time.Time
	ExpiresAt time.Time
}

type MockConsulKV struct {
	mu           sync.Mutex
	sessions     map[string]*ConsulSession
	sessionSeq   uint64
	lockHolders  map[string]string // key -> sessionID
	modifyIndex  map[string]uint64 // key -> monotonic index
}

func NewMockConsulKV() *MockConsulKV {
	return &MockConsulKV{
		sessions:    make(map[string]*ConsulSession),
		lockHolders: make(map[string]string),
		modifyIndex: make(map[string]uint64),
	}
}

func (c *MockConsulKV) CreateSession(ttl time.Duration) (string, uint64) {
	c.mu.Lock()
	defer c.mu.Unlock()

	c.sessionSeq++
	id := fmt.Sprintf("session-%d", c.sessionSeq)
	c.sessions[id] = &ConsulSession{
		ID:        id,
		TTL:       ttl,
		CreatedAt: time.Now(),
		ExpiresAt: time.Now().Add(ttl),
	}
	return id, c.sessionSeq
}

func (c *MockConsulKV) Acquire(key, sessionID string) (bool, uint64) {
	c.mu.Lock()
	defer c.mu.Unlock()

	sess, ok := c.sessions[sessionID]
	if !ok || time.Now().After(sess.ExpiresAt) {
		return false, 0
	}

	curHolder, held := c.lockHolders[key]
	if !held || curHolder == sessionID {
		c.lockHolders[key] = sessionID
		c.modifyIndex[key]++
		return true, c.modifyIndex[key]
	}

	return false, 0
}

func (c *MockConsulKV) Release(key, sessionID string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.lockHolders[key] == sessionID {
		delete(c.lockHolders, key)
	}
}

type BankService struct {
	mu              sync.Mutex
	balance         int64
	lastFencingIdx  uint64
}

func (b *BankService) ProcessWithdraw(amount int64, fencingIdx uint64) error {
	b.mu.Lock()
	defer b.mu.Unlock()

	if fencingIdx <= b.lastFencingIdx {
		return fmt.Errorf("CONSUL FENCING REJECT: provided index %d <= last seen %d",
			fencingIdx, b.lastFencingIdx)
	}

	b.lastFencingIdx = fencingIdx
	b.balance -= amount
	return nil
}

func main() {
	consul := NewMockConsulKV()
	bank := &BankService{balance: 1000}

	// 1. Клиент А создает сессию и захватывает ключ
	sessA, idxA := consul.CreateSession(5 * time.Second)
	ok, lockIdxA := consul.Acquire("service/bank/lock", sessA)
	fmt.Printf("[Client A] Session=%s, Acquired=%v, ModifyIndex (Fencing Token)=%d\n", sessA, ok, lockIdxA)

	// Клиент А уходит в паузу... В это время сессия А удаляется
	consul.Release("service/bank/lock", sessA)

	// 2. Клиент B создает новую сессию и берет ключ
	sessB, idxB := consul.CreateSession(5 * time.Second)
	okB, lockIdxB := consul.Acquire("service/bank/lock", sessB)
	fmt.Printf("[Client B] Session=%s, Acquired=%v, ModifyIndex (Fencing Token)=%d\n", sessB, okB, lockIdxB)

	// Клиент B выполняет операцию в банке с токеном lockIdxB
	err := bank.ProcessWithdraw(100, lockIdxB)
	fmt.Printf("[Client B] Withdraw status: err=%v, NewBalance=%d\n", err, bank.balance)

	// 3. Клиент A оживает и пытается выполнить списание со своим старым lockIdxA
	fmt.Printf("[Client A] Attempting withdraw with stale ModifyIndex %d...\n", lockIdxA)
	err = bank.ProcessWithdraw(50, lockIdxA)
	if err != nil {
		fmt.Printf("[Client A] BLOCKED: %v\n", err)
	}

	_ = idxA
	_ = idxB
	_ = errors.New("")
}
```

ℹ️ Распределенная блокировка через Consul Session с использованием ModifyIndex в качестве Fencing Token

## Под капотом

В Consul под капотом используется протокол консенсуса Raft. Каждая модификация KV-хранилища инкрементирует глобальный счетчик Raft Index (`ModifyIndex`). Когда клиент вызывает `PUT /v1/kv/my-key?acquire=<session>`, Consul применяет команду к Raft-логу. При успехе `ModifyIndex` ключа строго возрастает, что делает его идеальным аппаратным Fencing Token.

## Подводные камни

1. Неправильный выбор `SessionBehavior`: по умолчанию `release` просто снимает флаг владения, оставляя ключ в KV. Если требуется автоматическое удаление ключа, используйте `SessionBehaviorDelete`.
2. Забывание фонового продления сессии (`session.RenewPeriodic`): если сессия не обновляется, Consul снимет блокировку через TTL.

## На собеседовании

«В чем разница между сессиями Consul и арендой (Lease) в etcd?»
Ответ: Сессия Consul может быть привязана к Service Health Checks (Node Check, HTTP Check). Если сервис на машине начал отвечать кодом 500, Consul автоматически признает сессию невалидной и снимет лок. В etcd Lease привязана исключительно к соединению gRPC (KeepAlive) клиента и не знает о состоянии бизнес-чеков приложения.
