# Отказоустойчивая очередь задач с Redlock и удалением по Fencing Token

## Условие

62. **[Высокая сложность — Distributed Job Queue with Locks]**: Реализуй систему воркеров, обрабатывающих задачи из БД. Когда воркер берет задачу, он ставит Redlock по `task_id`, чтобы другой воркер не взял её параллельно. В конце работы воркер удаляет задачу. Реализуй передачу Fencing Token в БД при удалении, чтобы "зомби"-воркер не удалил уже переработанную задачу.

### Исходная формулировка

**[Высокая сложность — Distributed Job Queue with Locks]**: Реализуй систему воркеров, обрабатывающих задачи из БД. Когда воркер берет задачу, он ставит Redlock по `task_id`, чтобы другой воркер не взял её параллельно. В конце работы воркер удаляет задачу. Реализуй передачу Fencing Token в БД при удалении, чтобы "зомби"-воркер не удалил уже переработанную задачу.

## Теория

В распределенных системах очередей (Distributed Job Queue) воркеры извлекают задачи из общей базы данных. Если две ноды одновременно попытаются обработать одну задачу, возникнет дублирование побочных эффектов.

**Архитектура решения высокой надежности:**
1. **Дедупликация через распределенную блокировку:** Воркер перед началом работы захватывает распределенный мьютекс по ключу `task_lock:{task_id}` и получает монотонный `FencingToken`.
2. **Фиксация назначения в БД:** В таблице `tasks` поле `fencing_token` обновляется до полученного значения.
3. **Обработка задачи:** Воркер выполняет тяжелую бизнес-логику.
4. **Безопасное удаление / завершение:** По окончании работы воркер отправляет запрос:
   ```sql
   DELETE FROM tasks WHERE id = :task_id AND fencing_token = :token;
   ```
5. **Защита от зомби:** Если воркер завис, его блокировка истекла, а задачу перехватил другой воркер с токеном `token+1` и уже переработал ее, старый воркер при попытке удаления затронет 0 строк (`RowsAffected == 0`), что исключит ложное удаление новой версии задачи.

## Решение по шагам

1. Создайте модель `JobTask` с полями `ID`, `Payload`, `FencingToken`, `Status`.
2. Реализуйте менеджер блокировок `DistributedJobLocker`, генерирующий инкрементные токены.
3. Реализуйте БД задач `JobDatabase` с методами `AssignJob`, `DeleteWithFencing`.
4. Смоделируйте Воркер 1, берущий задачу с токеном 100 и засыпающий в паузе.
5. Смоделируйте Воркер 2, перехватывающий задачу с токеном 101 и успешно завершающий ее.
6. Воркер 1 просыпается и пытается удалить задачу с токеном 100.
7. Продемонстрируйте отторжение операции удаление от зомби-воркера.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type JobTask struct {
	ID           string
	Payload      string
	FencingToken uint64
	Status       string
}

type JobDatabase struct {
	mu    sync.Mutex
	tasks map[string]*JobTask
}

func NewJobDatabase() *JobDatabase {
	return &JobDatabase{tasks: make(map[string]*JobTask)}
}

func (db *JobDatabase) UpdateToken(id string, token uint64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	task, exists := db.tasks[id]
	if !exists {
		return errors.New("task not found")
	}
	task.FencingToken = token
	task.Status = "PROCESSING"
	return nil
}

// DeleteWithFencing симулирует DELETE FROM tasks WHERE id = $1 AND fencing_token = $2
func (db *JobDatabase) DeleteWithFencing(id string, token uint64) (bool, error) {
	db.mu.Lock()
	defer db.mu.Unlock()

	task, exists := db.tasks[id]
	if !exists {
		return false, nil // задача уже удалена
	}

	if task.FencingToken != token {
		// Токен не совпал: задачу уже перехватил другой воркер с более новым токеном!
		return false, fmt.Errorf("fencing mismatch: task has token %d, worker sent stale %d",
			task.FencingToken, token)
	}

	delete(db.tasks, id)
	return true, nil
}

type RedlockCoordinator struct {
	tokenSeq atomic.Uint64
}

func (r *RedlockCoordinator) Acquire(taskID string) (uint64, error) {
	// Возвращаем монотонный Fencing Token
	return r.tokenSeq.Add(1), nil
}

func main() {
	db := NewJobDatabase()
	coord := &RedlockCoordinator{}
	coord.tokenSeq.Store(100)

	// Инициализация задачи в БД
	taskID := "task-payment-404"
	db.tasks[taskID] = &JobTask{ID: taskID, Payload: "Charge $50", FencingToken: 100, Status: "PENDING"}

	// 1. Воркер 1 берет задачу с токеном 101
	tokenW1, _ := coord.Acquire(taskID)
	_ = db.UpdateToken(taskID, tokenW1)
	fmt.Printf("[Worker 1] Acquired job %s with Fencing Token: %d\n", taskID, tokenW1)

	// Воркер 1 засыпает в тяжелой сетевой паузе
	fmt.Println("[Worker 1] Freezes in network partition...")

	// 2. Блокировка истекает по TTL. Воркер 2 перехватывает задачу с токеном 102
	tokenW2, _ := coord.Acquire(taskID)
	_ = db.UpdateToken(taskID, tokenW2)
	fmt.Printf("[Worker 2] Re-acquired job %s with Fencing Token: %d\n", taskID, tokenW2)

	// Воркер 2 успешно завершает работу и удаляет задачу
	deletedW2, err := db.DeleteWithFencing(taskID, tokenW2)
	fmt.Printf("[Worker 2] Deleted job: %v, err: %v\n", deletedW2, err)

	// 3. Воркер 1 просыпается и пытается удалить задачу по своему старому токену 101
	fmt.Printf("[Worker 1] Woke up! Trying to delete job with stale token %d...\n", tokenW1)
	deletedW1, err := db.DeleteWithFencing(taskID, tokenW1)
	if err != nil || !deletedW1 {
		fmt.Printf("[Worker 1] DELETE BLOCKED BY STORAGE: %v\n", err)
	} else {
		fmt.Println("[Worker 1] BUG: Stale deletion succeeded!")
	}

	fmt.Printf("Final tasks in DB: %d\n", len(db.tasks))
	_ = context.Background()
	_ = time.Second
}
```

ℹ️ Распределенная очередь задач с блокировкой и безопасным удалением по Fencing Token

## Под капотом

В продакшене при удалении выполненной задачи из реляционной СУБД используется `DELETE ... WHERE id = $1 AND fencing_token = $2`. Если возвращается `RowsAffected == 0`, воркер немедленно логирует предупреждение о потере владения задачей и сбрасывает локальные метрики, предотвращая отправку ложных подтверждений (ACK) во внешние брокеры сообщений.

## Подводные камни

1. Удаление по ID без проверки Fencing Token: если задача успела упасть, быть переназначенной и создана заново, безусловный `DELETE WHERE id = $1` уничтожит чужую активную задачу.
2. Неосвобождение Redis-ключа при успехе: всегда вызывайте unlock в блоке `defer`.

## На собеседовании

«Как в распределенной очереди задач организовать Dead Letter Queue (DLQ) при постоянных сбоях воркеров по таймауту?»
Ответ: В схеме задачи хранится счетчик попыток `retry_count`. При каждом переназначении по таймауту координатор инкрементирует `retry_count++`. Если счетчик превышает порог (например, 5 попыток), задача не возвращается в очередь, а перемещается в таблицу DLQ с сохранением истории ошибок и генерирует алерт инженерам поддержки.
