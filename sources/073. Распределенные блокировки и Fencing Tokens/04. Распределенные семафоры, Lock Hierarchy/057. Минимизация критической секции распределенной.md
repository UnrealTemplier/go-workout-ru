# Минимизация критической секции распределенной блокировки

## Условие

57. **Minimize critical section.**: Держите lock только для essential operations. Не делайте I/O, network calls под lock если возможно.

### Исходная формулировка

**Minimize critical section.**: Держите lock только для essential operations. Не делайте I/O, network calls под lock если возможно.

## Теория

Главное правило высокопроизводительных распределенных систем — **минимизация критической секции (Lock Minimization)**.

Распределенная блокировка — это крайне дорогой глобальный ресурс. Захват блокировки требует нескольких сетевых RTT (Round Trip Time) до Redis/etcd. Если клиент внутри критической секции выполняет:
- Длительные HTTP-запросы к внешним API;
- Тяжелое чтение больших объемов данных с диска или S3;
- Сложную сериализацию или парсинг JSON/XML,
то все остальные воркеры в кластере выстраиваются в очередь ожидания, пропускная способность системы падает до единиц операций в секунду, а вероятность истечения TTL замка подскакивает экспоненциально.

**Паттерн оптимизации:**
1. **Подготовка данных ДО захвата блокировки:** Выполните парсинг, валидацию, подготовку payload и чтение предварительных данных БЕЗ блокировки.
2. **Захват блокировки на минимально необходимое время:** Только для атомарного чтения версии, применения изменения в БД и получения нового токена.
3. **Освобождение блокировки НЕМЕДЛЕННО после записи:** Освободите мьютекс до отправки нотификаций, вебхуков или метрик.
4. **Пост-обработка ПОСЛЕ освобождения блокировки:** Логирование, отправка писем, асинхронные уведомления клиентов.

## Решение по шагам

1. Создайте сценарий с плохой практикой: сетевой вызов (100мс) внутри блокировки.
2. Создайте оптимизированный сценарий: сетевой вызов вынесен ДО и ПОСЛЕ критической секции.
3. Сравните время удержания распределенной блокировки в обоих случаях.
4. Продемонстрируйте десятикратный выигрыш в доступности ресурса для параллельных воркеров.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type FakeDistributedLock struct {
	mu       sync.Mutex
	heldBy   string
	heldFrom time.Time
}

func (l *FakeDistributedLock) Lock(owner string) {
	l.mu.Lock()
	l.heldBy = owner
	l.heldFrom = time.Now()
}

func (l *FakeDistributedLock) Unlock() time.Duration {
	duration := time.Since(l.heldFrom)
	l.heldBy = ""
	l.mu.Unlock()
	return duration
}

// АНТИПАТТЕРН: Вся работа внутри блокировки
func BadProcessPayment(lock *FakeDistributedLock, clientID string) time.Duration {
	lock.Lock(clientID)
	defer lock.Unlock()

	// 1. Медленный внешний I/O под замком (ПЛОХО!)
	time.Sleep(100 * time.Millisecond)

	// 2. Атомарное обновление в БД (1мс)
	time.Sleep(2 * time.Millisecond)

	// 3. Отправка вебхука и email под замком (ПЛОХО!)
	time.Sleep(50 * time.Millisecond)

	return time.Since(lock.heldFrom)
}

// ПАТТЕРН: Минимальная критическая секция
func GoodProcessPayment(lock *FakeDistributedLock, clientID string) time.Duration {
	// 1. Вся тяжелая подготовка ДО блокировки
	time.Sleep(100 * time.Millisecond) // подготовка параметров платежа

	// 2. Блокировка ТОЛЬКО на время атомарной фиксации
	lock.Lock(clientID)
	time.Sleep(2 * time.Millisecond) // строго обновление баланса в БД
	heldDuration := lock.Unlock()

	// 3. Уведомления и вебхуки ПОСЛЕ снятия блокировки
	time.Sleep(50 * time.Millisecond)

	return heldDuration
}

func main() {
	lock := &FakeDistributedLock{}

	badDuration := BadProcessPayment(lock, "client-bad")
	fmt.Printf("[ANTI-PATTERN] Lock held duration: %v (Throughput: ~%.1f ops/sec)\n",
		badDuration, float64(time.Second)/float64(badDuration))

	goodDuration := GoodProcessPayment(lock, "client-good")
	fmt.Printf("[BEST PRACTICE] Lock held duration: %v (Throughput: ~%.1f ops/sec)\n",
		goodDuration, float64(time.Second)/float64(goodDuration))

	speedup := float64(badDuration) / float64(goodDuration)
	fmt.Printf("Critical section minimized by %.1fx!\n", speedup)
	_ = context.Background()
}
```

ℹ️ Вынос сетевых вызовов и I/O за пределы критической секции для многократного снижения времени удержания лока

## Под капотом

Пропускная способность распределенного мьютекса ограничена формулой Литтла: \(\text{Throughput} \le \frac{1}{\text{LockHoldDuration} + \text{AcquireRTT}}\). Если блокировка удерживается 150мс, система физически не может обрабатывать более 6.6 операций в секунду на данный ключ. Сокращение удержания до 2мс поднимает теоретический предел до 200–500 операций в секунду на том же железе.

## Подводные камни

1. Отправка сообщений в Kafka/RabbitMQ под блокировкой: если брокер временно подтормаживает, блокировка зависнет и истечет по TTL.
2. Вложенные распределенные блокировки: попытка захватить lock B, удерживая lock A, многократно увеличивает риск дедлока.

## На собеседовании

«Что делать, если внешнее API обязательно требует подтверждения под распределенной блокировкой?»
Ответ: Используйте двухфазный подход: 1) Резервирование ресурса под замком с переводом в статус `Pending`; 2) Снятие лока; 3) Асинхронный вызов внешнего API; 4) Повторный короткий захват лока для перевода в статус `Confirmed` или отката по Fencing Token.
