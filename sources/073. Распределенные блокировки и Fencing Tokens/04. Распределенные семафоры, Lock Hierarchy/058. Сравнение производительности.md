## Теория

Выбор технологии распределенной блокировки — фундаментальный архитектурный компромисс между **Latency / Throughput (Производительностью)** и **Safety / Consistency (Корректностью и надежностью)**:

| Технология | Модель консенсуса | Задержка (Latency) | Пропускная способность | Устойчивость к сбоям (Safety) |
| :--- | :--- | :--- | :--- | :--- |
| **Redis (Single Node)** | Нет (In-memory single thread) | Сверхнизкая (~0.5-1 ms) | Экстремальная (>50k ops/sec) | ⚠️ Низкая (потеря лока при падении мастера) |
| **Redis Redlock (5 nodes)** | Кворум independent nodes | Средняя (~5-15 ms) | Умеренная (~2-5k ops/sec) | ⚠️ Уязвима к сдвигам часов и GC-паузам |
| **etcd** | Raft (Linearizable State) | Средняя (~3-8 ms) | Высокая (~5-10k ops/sec) | ✅ Абсолютная (CP по теореме CAP) |
| **ZooKeeper** | Zab (Atomic Broadcast) | Средняя (~2-6 ms) | Высокая (~10k ops/sec) | ✅ Абсолютная (Ephemeral Sequential nodes) |
| **PostgreSQL Advisory Lock** | RDBMS WAL / MVCC | Низкая/Средняя (~2-5 ms)| Ограничена пулом соединений | ✅ Высокая (ACID в рамках одного инстанса БД) |

**Критерии выбора:**
- **Redis Single / Cluster:** Используется для некритичных задач (дедупликация задач кэширования, rate-limiting, cron-джокеры), где случайное дублирование не ведет к потере денег.
- **etcd / ZooKeeper / Consul:** Корпоративный стандарт для критических координаций (Leader Election, назначение шард в БД, распределенные транзакции).
- **PostgreSQL Advisory Locks:** Идеален, когда стек не включает etcd, а база данных уже является центральным ядром системы.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type LockBackend interface {
	Name() string
	Lock(ctx context.Context) error
	Unlock()
}

type SimulatedBackend struct {
	name        string
	mu          sync.Mutex
	networkCost time.Duration
}

func (b *SimulatedBackend) Name() string { return b.name }

func (b *SimulatedBackend) Lock(ctx context.Context) error {
	b.mu.Lock()
	// Симуляция RTT и протокола консенсуса
	time.Sleep(b.networkCost)
	return nil
}

func (b *SimulatedBackend) Unlock() {
	time.Sleep(b.networkCost / 2)
	b.mu.Unlock()
}

func RunLockBenchmark(b LockBackend, totalOps int, concurrency int) (time.Duration, float64) {
	var wg sync.WaitGroup
	opsPerWorker := totalOps / concurrency
	counter := 0

	start := time.Now()
	for w := 0; w < concurrency; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < opsPerWorker; i++ {
				if err := b.Lock(context.Background()); err != nil {
					continue
				}
				counter++
				b.Unlock()
			}
		}()
	}

	wg.Wait()
	duration := time.Since(start)
	throughput := float64(totalOps) / duration.Seconds()
	return duration, throughput
}

func main() {
	backends := []LockBackend{
		&SimulatedBackend{name: "Redis (Single Node)", networkCost: 50 * time.Microsecond},
		&SimulatedBackend{name: "PostgreSQL Advisory Lock", networkCost: 150 * time.Microsecond},
		&SimulatedBackend{name: "etcd (Raft Consensus)", networkCost: 300 * time.Microsecond},
		&SimulatedBackend{name: "Redis Redlock (5 nodes)", networkCost: 500 * time.Microsecond},
	}

	totalOps := 200
	concurrency := 10

	fmt.Printf("=== Distributed Lock Performance Comparison (%d ops, %d workers) ===\n\n", totalOps, concurrency)
	fmt.Printf("%-28s | %-12s | %-16s\n", "Backend", "Duration", "Throughput")
	fmt.Println("---------------------------------------------------------------")

	for _, b := range backends {
		dur, tps := RunLockBenchmark(b, totalOps, concurrency)
		fmt.Printf("%-28s | %-12v | %8.1f ops/sec\n", b.Name(), dur.Round(time.Millisecond), tps)
	}

	fmt.Println("\nArchitectural Recommendation:")
	fmt.Println("- For absolute safety & CP consensus: Use etcd (Kubernetes standard)")
	fmt.Println("- For maximum speed & soft-locks: Use Redis single/cluster")
	fmt.Println("- For RDBMS-centric workloads without new infra: Use PG Advisory Locks")
}
```

## Под капотом

В Redis операция `SET NX PX` выполняется строго в основном однопоточном цикле `aeProcessEvents` в оперативной памяти без сброса на диск (fsync). В etcd транзакция обязана пройти раунд сетевого RPC Raft AppendEntries к кворуму узлов и сброситься на диск через WAL `fsync` в bbolt, что физически ограничивает максимальный TPS скоростью дискового ввода-вывода (IOPS).

## Подводные камни

1. Использование Redis для финансовых транзакций без Fencing Token: асинхронная репликация при падении мастера неизбежно приведет к потере замка и двойному списанию.
2. Перегрузка PostgreSQL Advisory Locks: если тысячи соединений держат advisory locks, пул соединений СУБД исчерпывается (Connection Starvation), блокируя обычные бизнес-запросы.

## На собеседовании

«Почему в BigTech (Яндекс, Авито, Ozon) не используют Redlock для критичных сервисов?»
Ответ: Redlock требует развертывания 5 независимых инстансов Redis, не гарантирует монотонных Fencing Tokens, уязвим к рассинхронизации часов (Clock Skew) и подвергся жесткой критике экспертов по распределенным системам (Martin Kleppmann). Для критичных сценариев используют проверенные системы на консенсусе Raft/Paxos (etcd, ZooKeeper, YDB, CockroachDB).
