# Защита целостности на стороне хранилища (Storage Fencing)

## Условие

59. **[Защита на стороне хранилища]**: Клиент A (токен 1) берет лок, получает GC паузу. Клиент B (токен 2) берет лок. Когда B пишет в хранилище (например, PostgreSQL), он передает токен 2. Хранилище запоминает `last_token = 2`. Когда просыпается A и пытается записать с токеном 1, PostgreSQL отклоняет операцию (через триггер или middleware), так как `1 < 2`.

### Исходная формулировка

**[Защита на стороне хранилища]**: Клиент A (токен 1) берет лок, получает GC паузу. Клиент B (токен 2) берет лок. Когда B пишет в хранилище (например, PostgreSQL), он передает токен 2. Хранилище запоминает `last_token = 2`. Когда просыпается A и пытается записать с токеном 1, PostgreSQL отклоняет операцию (через триггер или middleware), так как `1 < 2`.

## Теория

Классическая аксиома распределенных систем: **«Никогда не доверяй клиенту распределенной блокировки»**.

Любой клиент распределенного мьютекса может:
- Зависнуть в GC-паузе;
- Испытать сетевую задержку;
- Потерять соединение с координатором блокировок;
- Перезагрузиться и восстановить старый контекст.

Поэтому распределенная блокировка становится надежной только тогда, когда само **целевое хранилище (Storage System)** реализует валидацию монотонности токена (**Storage Fencing**).

**Реализация в PostgreSQL через триггер:**
В базе создается триггер `BEFORE UPDATE OR INSERT`, который проверяет:
```sql
CREATE OR REPLACE FUNCTION verify_fencing_token() RETURNS trigger AS $$
BEGIN
    IF NEW.fencing_token <= OLD.fencing_token THEN
        RAISE EXCEPTION 'Fencing violation: token % is not greater than %', 
            NEW.fencing_token, OLD.fencing_token;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```
Если зомби-клиент присылает запрос с токеном \(T \le T_{\text{current}}\), транзакция мгновенно падает на уровне ядра БД с исключением, исключая порчу данных.

## Решение по шагам

1. Смоделируйте движок базы данных с механизмом триггеров на Go.
2. Зарегистрируйте триггер `verify_fencing_token`, отклоняющий обновления с `token <= old_token`.
3. Клиент A захватывает блокировку с токеном 1.
4. Клиент A уходит в длительную паузу.
5. Клиент B захватывает блокировку с токеном 2 и обновляет запись в хранилище.
6. Клиент A просыпается и пытается выполнить обновление с токеном 1.
7. Продемонстрируйте срабатывание триггера хранилища и успешную защиту данных.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

var ErrTriggerFencingViolation = errors.New("DB_TRIGGER_ERROR: fencing_token must be strictly greater than current")

type DocumentRecord struct {
	ID           string
	Content      string
	FencingToken uint64
	UpdatedAt    time.Time
}

type DatabaseWithTrigger struct {
	mu    sync.Mutex
	table map[string]DocumentRecord
}

func NewDatabaseWithTrigger() *DatabaseWithTrigger {
	return &DatabaseWithTrigger{
		table: make(map[string]DocumentRecord),
	}
}

// UpdateDocument симулирует UPDATE с выполнением триггера verify_fencing_token
func (db *DatabaseWithTrigger) UpdateDocument(id, newContent string, token uint64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	old, exists := db.table[id]
	if exists {
		// Срабатывание BEFORE UPDATE триггера в PostgreSQL
		if token <= old.FencingToken {
			return fmt.Errorf("%w (attempted: %d, current in DB: %d)",
				ErrTriggerFencingViolation, token, old.FencingToken)
		}
	}

	db.table[id] = DocumentRecord{
		ID:           id,
		Content:      newContent,
		FencingToken: token,
		UpdatedAt:    time.Now(),
	}
	return nil
}

func main() {
	db := NewDatabaseWithTrigger()

	// Инициализация документа
	_ = db.UpdateDocument("doc-1", "Initial Content", 0)
	fmt.Println("[DB Init] Document doc-1 initialized with FencingToken = 0")

	// Клиент А получил блокировку с токеном 1
	tokenA := uint64(1)
	fmt.Printf("[Client A] Lock acquired with Token %d\n", tokenA)

	// Клиент А уходит в STW GC паузу...
	fmt.Println("[Client A] Frozen in STW GC pause...")

	// Клиент B получил блокировку с токеном 2
	tokenB := uint64(2)
	fmt.Printf("[Client B] Lock acquired with Token %d\n", tokenB)

	// Клиент B успешно сохраняет новую версию
	err := db.UpdateDocument("doc-1", "Updated by Client B", tokenB)
	fmt.Printf("[Client B] Write result: err=%v\n", err)

	// Клиент А просыпается и шлет свои устаревшие данные
	fmt.Printf("[Client A] Woke up! Sending write with Token %d...\n", tokenA)
	err = db.UpdateDocument("doc-1", "Stale write by Client A", tokenA)
	if errors.Is(err, ErrTriggerFencingViolation) {
		fmt.Printf("[Client A] REJECTED BY DATABASE TRIGGER: %v\n", err)
	} else {
		fmt.Println("[Client A] CRITICAL ERROR: Stale data overwritten!")
	}

	finalDoc := db.table["doc-1"]
	fmt.Printf("\nFinal State in Database: Content=%q, Token=%d\n", finalDoc.Content, finalDoc.FencingToken)
}
```

ℹ️ Симуляция триггера PostgreSQL verify_fencing_token, гарантирующего строгое возрастание токена на уровне ядра БД

## Под капотом

В реляционных СУБД триггер `BEFORE UPDATE` выполняется в том же транзакционном контексте, что и сам запрос `UPDATE`. Если триггер выбрасывает исключение `RAISE EXCEPTION`, транзакция PostgreSQL мгновенно переходит в статус `ABORTED`, все изменения кортежей откатываются, а вызывающему Go-клиенту возвращается сетевая ошибка `pq: Fencing violation`.

## Подводные камни

1. Проверка `>=` вместо `>`: если повторный запрос с тем же токеном (идемпотентный retry) не поддерживается триггером, клиент получит ошибку. Для идемпотентности разрешают `token == old.token` только при совпадении хэша payload.
2. Отключение триггеров при миграциях БД: случайный `DISABLE TRIGGER ALL` снимает всю защиту системы от зомби-воркеров.

## На собеседовании

«Как реализовать Storage Fencing при записи файлов в объектное хранилище S3, где нет SQL-триггеров?»
Ответ: В S3 Storage Fencing реализуется через: 1) Механизм S3 Object Versioning и условную запись `PutObject` с заголовком `If-Match: <ETag>`; 2) Conditional Writes (появились в Amazon S3 в 2024 году): заголовок `If-None-Match: *` для предотвращения перезаписи уже существующего файла; 3) Запись каждого изменения в новый ключ с монотонным префиксом `/events/token_00123.json`.
