# Тестирование состояния гонки (Race Condition) с потерей распределенной блокировки

## Условие

60. **Тестирование гонок с потерей блокировки.**: Напишите тест, в котором два конкурента пытаются одновременно захватить блокировку и увеличить общий счётчик. Без блокировки – гонка. С блокировкой – строгая последовательность.

### Исходная формулировка

**Тестирование гонок с потерей блокировки.**: Напишите тест, в котором два конкурента пытаются одновременно захватить блокировку и увеличить общий счётчик. Без блокировки – гонка. С блокировкой – строгая последовательность.

## Теория

Состояние гонки (Race Condition) в распределенных системах возникает, когда два процесса параллельно считывают общее состояние, модифицируют его локально и записывают обратно. Без взаимного исключения одно из обновлений неизбежно теряется (Lost Update).

Методология верификации:
1. **Эксперимент БЕЗ блокировки:** 2 параллельных воркера выполняют неатомарный инкремент счетчика: `val := counter; time.Sleep(1ms); counter = val + 1`. В результате вместо 200 инкрементов итоговый счетчик будет существенно меньше (например, 110-130) из-за потерянных обновлений.
2. **Эксперимент С распределенной блокировкой:** Каждый воркер перед чтением и записью захватывает распределенный мьютекс. Критическая секция строго сериализуется. Итоговый счетчик обязан быть строго равен 200.
3. **Детектор гонок Go (`go test -race`):** Позволяет выявлять несинхронизированный доступ к разделяемым ресурсам памяти на уровне рантайма.

## Решение по шагам

1. Создайте структуру `SharedCounter` с неатомарным методом `Increment()`.
2. Запустите тест без использования блокировки и покажите расхождение результатов.
3. Реализуйте распределенный мьютекс `SpinLockMutex`.
4. Запустите аналогичный тест с защитой критической секции через мьютекс.
5. Проверьте строгое равенство счетчика ожидаемому значению.
6. Выведите отчет о тестировании.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type SharedCounter struct {
	val int
}

func (c *SharedCounter) UnsafeIncrement() {
	// Неатомарное чтение-модификация-запись (RMW)
	current := c.val
	time.Sleep(10 * time.Microsecond) // симуляция задержки вычисления
	c.val = current + 1
}

type SimpleDistMutex struct {
	mu     sync.Mutex
	isHeld bool
}

func (m *SimpleDistMutex) Lock() {
	for {
		m.mu.Lock()
		if !m.isHeld {
			m.isHeld = true
			m.mu.Unlock()
			return
		}
		m.mu.Unlock()
		time.Sleep(50 * time.Microsecond)
	}
}

func (m *SimpleDistMutex) Unlock() {
	m.mu.Lock()
	m.isHeld = false
	m.mu.Unlock()
}

func RunWithoutLock(totalInc int) int {
	counter := &SharedCounter{}
	var wg sync.WaitGroup
	wg.Add(2)

	worker := func() {
		defer wg.Done()
		for i := 0; i < totalInc/2; i++ {
			counter.UnsafeIncrement()
		}
	}

	go worker()
	go worker()
	wg.Wait()

	return counter.val
}

func RunWithLock(totalInc int) int {
	counter := &SharedCounter{}
	lock := &SimpleDistMutex{}
	var wg sync.WaitGroup
	wg.Add(2)

	worker := func() {
		defer wg.Done()
		for i := 0; i < totalInc/2; i++ {
			lock.Lock()
			counter.UnsafeIncrement()
			lock.Unlock()
		}
	}

	go worker()
	go worker()
	wg.Wait()

	return counter.val
}

func main() {
	totalOps := 100

	fmt.Println("=== Distributed Race Condition Verification Test ===")

	// 1. Тест БЕЗ блокировки (Lost Updates)
	resultWithoutLock := RunWithoutLock(totalOps)
	fmt.Printf("[TEST 1 - NO LOCK] Expected: %d, Actual: %d (Lost %d updates!)\n",
		totalOps, resultWithoutLock, totalOps-resultWithoutLock)

	// 2. Тест С распределенной блокировкой (Strict Serialization)
	resultWithLock := RunWithLock(totalOps)
	fmt.Printf("[TEST 2 - WITH LOCK] Expected: %d, Actual: %d (100%% consistency!)\n",
		totalOps, resultWithLock)

	if resultWithLock == totalOps {
		fmt.Println("\nCONCLUSION: Distributed Lock strictly eliminated race conditions!")
	} else {
		panic("Test failed: inconsistency detected despite locking!")
	}
	_ = context.Background()
}
```

ℹ️ Сравнительный тест гонки обновлений (Lost Update) с демонстрацией строгой сериализации через распределенную блокировку

## Под капотом

На многоядерном процессоре при отсутствии барьеров памяти и взаимного исключения кэши L1/L2 ядер процессора содержат устаревшие копии переменной (CPU Cache Invalidation Delay). В распределенной же системе масштаб проблемы вырастает на порядки: задержки синхронизации между физическими машинами составляют миллисекунды, гарантируя 100% потерю данных при параллельных RMW без мьютекса.

## Подводные камни

1. Тестирование только на localhost: на одной локальной машине задержки минимальны, и гонки могут не проявиться. Необходимы искусственные задержки или стресс-тесты под нагрузкой.
2. Ложное ощущение безопасности: мьютекс защищает от параллельных инкрементов, но если один воркер упал посреди инкремента, требуется механизм восстановления транзакции.

## На собеседовании

«Как в Go написать модульный тест, гарантирующий отсутствие состояния гонки при обращении к распределенному ресурсу?»
Ответ: Используем флаг `go test -race` в сочетании с пакетом `sync/atomic` или мок-координатором с искусственным внедрением задержек (Chaos Delay Injection). Запускаем \(N\) горутин, выполняющих конкурентные операции, и проверяем инвариант системы (например, сумму балансов всех аккаунтов) с помощью `assert.Equal`.
