# Use Case сценарий Fencing Token: предотвращение Split-Brain при падении воркера

## Условие

65. **Fencing token use case**: Worker A получает lock с token=100, начинает task. Worker A crashes. Lock expires. Worker B получает lock с token=101, начинает task. Worker A восстанавливается, пытается завершить task с token=100. Storage system rejects write с stale token=100. Это защита от split-brain.

### Исходная формулировка

**Fencing token use case**: Worker A получает lock с token=100, начинает task. Worker A crashes. Lock expires. Worker B получает lock с token=101, начинает task. Worker A восстанавливается, пытается завершить task с token=100. Storage system rejects write с stale token=100. Это защита от split-brain.

## Теория

Рассмотрим детальный пошаговый сценарий предотвращения катастрофы **Split-Brain** в распределенном кластере с использованием Fencing Token:

**Хронология событий:**
1. **Шаг 1 (\(T_0\)):** Воркер A получает задачу и захватывает распределенную блокировку на файл `report.csv`. Сервер блокировок выдает `Token = 100`.
2. **Шаг 2 (\(T_1\)):** Воркер A начинает генерацию отчета. Неожиданно в операционной системе Воркера A происходит сбой сети или остановка гипервизора (Freeze). Воркер A временно «умирает».
3. **Шаг 3 (\(T_2\)):** Проходит 10 секунд. Сервер блокировок констатирует отсутствие heartbeat и снимает ключ по таймауту.
4. **Шаг 4 (\(T_3\)):** Воркер B обнаруживает зависшую задачу, захватывает блокировку и получает строго больший `Token = 101`.
5. **Шаг 5 (\(T_4\)):** Воркер B быстро генерирует актуальный отчет и сохраняет его в хранилище (БД / S3). Хранилище фиксирует: `current_token = 101`.
6. **Шаг 6 (\(T_5\)):** Воркер A «оттаивает». Будучи уверенным, что он все еще держит замок, Воркер A шлет свой устаревший отчет в хранилище с `Token = 100`.
7. **Спасение:** Хранилище сравнивает токен запроса: \(100 < 101\) и **отвергает запись Воркера A**. Split-Brain предотвращен!

## Решение по шагам

1. Смоделируйте хранилище `FencedStorage` с полем `lastCommittedToken uint64`.
2. Реализуйте метод `CommitData(token uint64, payload string) error`.
3. Создайте генератор токенов `LockServer` с начальным значением 100.
4. Воркер A получает токен 100.
5. Имитируйте сбой воркера A.
6. Воркер B получает токен 101 и успешно сохраняет данные.
7. Воркер A оживает и пробует применить запись с токеном 100.
8. Убедитесь, что хранилище возвращает ошибку `ErrStaleFencingToken`.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

var ErrSplitBrainPrevented = errors.New("storage: fencing token is stale, potential split-brain detected")

type FencedStorage struct {
	mu                 sync.Mutex
	committedData      string
	lastCommittedToken uint64
}

func (s *FencedStorage) CommitData(token uint64, data string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	if token < s.lastCommittedToken {
		return fmt.Errorf("%w (attempted token: %d, storage current token: %d)",
			ErrSplitBrainPrevented, token, s.lastCommittedToken)
	}

	s.lastCommittedToken = token
	s.committedData = data
	return nil
}

type CentralLockServer struct {
	mu      sync.Mutex
	counter uint64
}

func (l *CentralLockServer) GrantLock() uint64 {
	l.mu.Lock()
	defer l.mu.Unlock()
	l.counter++
	return l.counter
}

func main() {
	lockServer := &CentralLockServer{counter: 99}
	storage := &FencedStorage{lastCommittedToken: 0}

	// 1. Worker A получает блокировку
	tokenA := lockServer.GrantLock()
	fmt.Printf("[T0] Worker A acquired lock with Token: %d\n", tokenA)

	// 2. Worker A «замерзает» (freeze/pause)
	fmt.Println("[T1] Worker A crashes / experiences massive freeze...")

	// 3. Таймаут блокировки. Worker B получает лок
	tokenB := lockServer.GrantLock()
	fmt.Printf("[T2] Lock expired. Worker B acquired lock with Token: %d\n", tokenB)

	// 4. Worker B успешно сохраняет отчет
	err := storage.CommitData(tokenB, "FINAL_REPORT_V2_BY_WORKER_B")
	fmt.Printf("[T3] Worker B write result: err=%v (Storage token now: %d)\n", err, storage.lastCommittedToken)

	// 5. Worker A просыпается и пытается сохранить устаревший отчет
	fmt.Printf("[T4] Worker A recovers! Attempting commit with stale Token: %d...\n", tokenA)
	err = storage.CommitData(tokenA, "STALE_REPORT_V1_BY_WORKER_A")
	if errors.Is(err, ErrSplitBrainPrevented) {
		fmt.Printf("[T5] SUCCESS! Storage safely blocked Worker A: %v\n", err)
	} else {
		panic("Catastrophic failure: Stale write was accepted!")
	}

	fmt.Printf("\nFinal Preserved Storage Data: %q\n", storage.committedData)
	_ = time.Second
}
```

## Под капотом

С точки зрения теории распределенных систем (Lamport Clocks, Vector Clocks) Fencing Token выполняет роль монотонного логического времени (Logical Timestamp). Любое хранилище с правилом Last-Write-Wins (LWW) по логическому токену гарантирует упорядоченность причинно-следственных связей (Causal Ordering) независимо от физических задержек передачи пакетов.

## Подводные камни

1. Генерация токенов через `time.Now().UnixNano()`: физические часы на разных серверах могут идти назад при NTP-синхронизации (Slewing / Step adjustment). Токен обязан генерироваться консенсусом (etcd revision, ZooKeeper zxid).
2. Хранение Fencing Token в оперативной памяти воркера, а не хранилища: хранилище обязано проверять токен атомарно при каждой операции записи.

## На собеседовании

«Что делать, если целевое хранилище — это legacy сервис без поддержки Fencing Tokens (не умеет проверять токены)?»
Ответ: Между воркерами и legacy-сервисом внедряется тонкий прокси-шлюз (Fencing Gateway Middleware). Все запросы от воркеров идут через шлюз, который хранит максимальный увиденный токен в Redis/PostgreSQL и отсекает запросы с устаревшими токенами до их попадания в legacy-систему.
