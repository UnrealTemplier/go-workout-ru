# Fencing через транзакции etcd с возвратом Revision ключа

## Условие

55. **[Fencing через etcd]**: Реализуй распределенную блокировку в etcd с использованием транзакций. Вместо обычной записи, используй `etcd.Txn`. Возвращай `revision` ключа — это и будет твой Fencing Token.

### Исходная формулировка

**[Fencing через etcd]**: Реализуй распределенную блокировку в etcd с использованием транзакций. Вместо обычной записи, используй `etcd.Txn`. Возвращай `revision` ключа — это и будет твой Fencing Token.

## Теория

В etcd каждое изменение любого ключа в кластере инкрементирует глобальный 64-битный счетчик — **Revision (Ревизия хранилища)**. Ревизия в etcd строго монотонна, глобально упорядочена и никогда не уменьшается даже после перезагрузки кластера или смены лидера Raft.

Благодаря этому etcd предоставляет идеальный фундамент для Fencing Tokens:
1. Клиент выполняет транзакцию `clientv3.Txn`:
   ```go
   txn.If(clientv3.Compare(clientv3.CreateRevision(key), "=", 0)).
       Then(clientv3.OpPut(key, clientID, clientv3.WithLease(leaseID)))
   ```
2. Если ключ не существовал, etcd атомарно записывает ключ и возвращает `TxnResponse`.
3. В ответе поле `resp.Header.Revision` отражает текущую ревизию хранилища на момент выполнения транзакции.
4. Клиент берет `resp.Header.Revision` и использует его как свой уникальный **Fencing Token**.
5. Целевые сервисы (БД, S3, очереди) проверяют, чтобы ревизия запроса была строго больше всех ранее обработанных.

## Решение по шагам

1. Создайте структуру `EtcdFencingLock` с имитацией `clientv3.Txn`.
2. Реализуйте метод `LockWithFencing(ctx, key, clientID, leaseID) (fencingToken int64, err error)`.
3. Сформируйте транзакцию с условием `CreateRevision == 0`.
4. В ветке успеха извлеките `resp.Header.Revision` и верните его в качестве токена.
5. Продемонстрируйте сценарий получения возрастающих токенов разными клиентами.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

type TxnHeader struct {
	Revision int64
}

type TxnResponse struct {
	Succeeded bool
	Header    TxnHeader
}

type MockEtcdTxnStore struct {
	mu          sync.Mutex
	globalRev   int64
	kvStore     map[string]string
	createRevs  map[string]int64
}

func NewMockEtcdTxnStore() *MockEtcdTxnStore {
	return &MockEtcdTxnStore{
		globalRev:  1000,
		kvStore:    make(map[string]string),
		createRevs: make(map[string]int64),
	}
}

// TxnPutIfAbsent имитирует Txn.If(CreateRevision == 0).Then(OpPut)
func (s *MockEtcdTxnStore) TxnPutIfAbsent(key, val string) TxnResponse {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.globalRev++

	if _, exists := s.kvStore[key]; exists {
		return TxnResponse{
			Succeeded: false,
			Header:    TxnHeader{Revision: s.globalRev},
		}
	}

	s.kvStore[key] = val
	s.createRevs[key] = s.globalRev

	return TxnResponse{
		Succeeded: true,
		Header:    TxnHeader{Revision: s.globalRev},
	}
}

func (s *MockEtcdTxnStore) DeleteKey(key string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.globalRev++
	delete(s.kvStore, key)
	delete(s.createRevs, key)
}

type EtcdFencingLocker struct {
	store *MockEtcdTxnStore
}

func NewEtcdFencingLocker(store *MockEtcdTxnStore) *EtcdFencingLocker {
	return &EtcdFencingLocker{store: store}
}

func (l *EtcdFencingLocker) Acquire(ctx context.Context, lockKey, clientID string) (int64, error) {
	resp := l.store.TxnPutIfAbsent(lockKey, clientID)
	if !resp.Succeeded {
		return 0, errors.New("lock already held by another client")
	}

	// resp.Header.Revision является эталонным монотонным Fencing Token
	fencingToken := resp.Header.Revision
	return fencingToken, nil
}

func (l *EtcdFencingLocker) Release(lockKey string) {
	l.store.DeleteKey(lockKey)
}

func main() {
	store := NewMockEtcdTxnStore()
	locker := NewEtcdFencingLocker(store)

	ctx := context.Background()
	lockKey := "/locks/billing_export"

	// Клиент 1 берет лок
	token1, err := locker.Acquire(ctx, lockKey, "billing-service-1")
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Client 1] Acquired lock. Fencing Token (etcd Revision): %d\n", token1)

	// Клиент 2 пытается взять лок -> отказ
	_, err = locker.Acquire(ctx, lockKey, "billing-service-2")
	fmt.Println("[Client 2] Acquire attempt result:", err)

	// Клиент 1 освобождает лок
	locker.Release(lockKey)
	fmt.Println("[Client 1] Released lock")

	// Клиент 2 берет лок -> получает строго больший Fencing Token!
	token2, err := locker.Acquire(ctx, lockKey, "billing-service-2")
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Client 2] Acquired lock. Fencing Token (etcd Revision): %d\n", token2)

	if token2 <= token1 {
		panic("Revision must be strictly monotonic!")
	}
	fmt.Println("Fencing monotonicity verified: token2 > token1")
}
```

ℹ️ Использование транзакций etcd Txn с получением Header.Revision в качестве Fencing Token

## Под капотом

В etcd ревизия хранится в памяти как `uint64` внутри `lease/lessor` и bbolt хранилища. Каждая транзакция `Apply` увеличивает ревизию ровно на единицу (или число модификаций). Поскольку Raft сериализует все записи в единый линейный журнал, совпадение ревизий для двух разных операций изменения невозможно в силу свойств консенсуса.

## Подводные камни

1. Использование `ModRevision` вместо `Header.Revision` или `CreateRevision`: `ModRevision` отражает только ревизию последнего изменения конкретного ключа, в то время как `Header.Revision` глобален для всего кластера.
2. Использование обычной операции `Put` без `Txn.If(CreateRevision == 0)`: обычный `Put` перезапишет ключ другого владельца.

## На собеседовании

«Почему etcd Revision превосходит Redis Redlock при построении безопасного распределенного мьютекса?»
Ответ: Redis при захвате блокировки возвращает лишь статус `OK` без гарантии монотонного упорядочивания между клиентами. etcd гарантирует глобальную линейную ревизию `Header.Revision` на уровне протокола Raft. Это дает клиенту бесплатный Fencing Token без необходимости поднимать отдельный сервис генерации Snowflake или последовательностей.
