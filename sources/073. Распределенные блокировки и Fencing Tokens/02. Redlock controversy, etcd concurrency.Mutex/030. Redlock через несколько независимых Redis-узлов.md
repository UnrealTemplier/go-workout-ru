# Redlock через несколько независимых Redis-узлов: обработка частичных сбоев и сетевой изоляции

## Условие

30. **Redlock: блокировка через несколько Redis-узлов.**: Реализуйте алгоритм Redlock: попытайтесь захватить блокировку на N независимых Redis-серверах (минимум 3), используя одинаковый ключ и случайный токен. Блокировка считается успешной, если захвачено большинство узлов.

### Исходная формулировка

**Redlock: блокировка через несколько Redis-узлов.**: Реализуйте алгоритм Redlock: попытайтесь захватить блокировку на N независимых Redis-серверах (минимум 3), используя одинаковый ключ и случайный токен. Блокировка считается успешной, если захвачено большинство за время таймаута.

## Теория

Глубокий анализ граничных состояний при исполнении Redlock:

Сценарий частичного отказа и сетевой изоляции (Network Partition):
- У нас есть 5 узлов Redis: \(R_1, R_2, R_3, R_4, R_5\).
- Клиент \(A\) успешно записывает токен в \(R_1, R_2, R_3\). Кворум \(3/5\) собран. Клиент \(A\) владеет локом.
- Внезапно сеть между клиентом \(A\) и узлами \(R_1, R_2\) обрывается.
- Клиент \(B\) пытается захватить лок:
  - \(R_1, R_2\): Клиент \(B\) видит занятый ключ клиента \(A\).
  - \(R_3\): Клиент \(B\) видит занятый ключ клиента \(A\).
  - \(R_4, R_5\): Свободны, клиент \(B\) записывает свой токен.
  - Итог для Клиента \(B\): Получено только 2 голоса из 5. Кворум \(2 < 3\) **не набран**!
  - Клиент \(B\) фиксирует неудачу и откатывает свои записи на \(R_4, R_5\).

Инвариант безопасности:
Пока Клиент \(A\) держит кворум (\(3/5\)), ни один другой клиент не может набрать пересекающееся большинство (\(3/5\)), так как любые два большинства в нечетном кластере обязаны иметь хотя бы один общий узел (\(3 + 3 = 6 > 5\)).

## Решение по шагам

1. Создайте кластер из 5 узлов с поддержкой симуляции сетевой изоляции отдельных нод.
2. Продемонстрируйте успешный захват кворума Клиентом 1 на нодах 1, 2, 3.
3. Запустите конкурентный запрос Клиента 2 на оставшихся нодах.
4. Покажите, как пересечение кворумов препятствует одновременному захвату.
5. Продемонстрируйте автоматический откат частичных записей Клиента 2.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"sync"
	"time"
)

type MultiRedisNode struct {
	ID        int
	mu        sync.Mutex
	keys      map[string]string
	isolated  bool
}

func (n *MultiRedisNode) SetNX(key, token string) bool {
	n.mu.Lock()
	defer n.mu.Unlock()
	if n.isolated {
		return false
	}
	if _, exists := n.keys[key]; exists {
		return false
	}
	n.keys[key] = token
	return true
}

func (n *MultiRedisNode) DelIfToken(key, token string) {
	n.mu.Lock()
	defer n.mu.Unlock()
	if n.keys[key] == token {
		delete(n.keys, key)
	}
}

type MultiRedlockManager struct {
	nodes  []*MultiRedisNode
	quorum int
}

func NewMultiRedlockManager(n int) *MultiRedlockManager {
	nodes := make([]*MultiRedisNode, n)
	for i := 0; i < n; i++ {
		nodes[i] = &MultiRedisNode{ID: i + 1, keys: make(map[string]string)}
	}
	return &MultiRedlockManager{
		nodes:  nodes,
		quorum: n/2 + 1,
	}
}

func (m *MultiRedlockManager) Acquire(clientName, key string) (string, bool) {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	token := clientName + ":" + hex.EncodeToString(b)[:8]

	acks := 0
	for _, node := range m.nodes {
		if node.SetNX(key, token) {
			acks++
		}
	}

	if acks >= m.quorum {
		fmt.Printf("[%s] ✅ Redlock acquired! Quorum satisfied: %d/%d votes\n",
			clientName, acks, len(m.nodes))
		return token, true
	}

	// Compensation
	fmt.Printf("[%s] ❌ Quorum failed (%d/%d). Reverting partial locks...\n",
		clientName, acks, len(m.nodes))
	for _, node := range m.nodes {
		node.DelIfToken(key, token)
	}
	return "", false
}

func main() {
	manager := NewMultiRedlockManager(5) // Quorum is 3/5
	lockKey := "lock:ticket:seat-12B"

	// 1. Client 1 acquires lock on 5 healthy nodes
	token1, ok1 := manager.Acquire("Client-1", lockKey)
	if !ok1 {
		panic("expected client 1 to acquire")
	}

	// 2. Client 2 tries to acquire same key concurrently
	fmt.Println("\nClient 2 attempting concurrent acquisition...")
	_, ok2 := manager.Acquire("Client-2", lockKey)
	if !ok2 {
		fmt.Println("Client 2 successfully blocked: Quorum intersection prevented split-brain!")
	}

	// 3. Client 1 releases
	fmt.Println("\nClient 1 releasing lock...")
	for _, n := range manager.nodes {
		n.DelIfToken(lockKey, token1)
	}

	// 4. Client 2 retries after release
	fmt.Println("Client 2 retrying after release...")
	_, ok3 := manager.Acquire("Client-2", lockKey)
	if ok3 {
		fmt.Println("Client 2 successfully acquired released lock!")
	}
}
```

## Под капотом

Теорема пересечения кворумов (Quorum Intersection):
Пусть общее число узлов \(N = 2F + 1\).
Любое подмножество \(Q_1\) размера \(F + 1\) и любое подмножество \(Q_2\) размера \(F + 1\) имеют размер суммы:
\(|Q_1| + |Q_2| = 2F + 2 = N + 1 > N\).
По принципу Дирихле (Pigeonhole Principle), подмножества \(Q_1\) и \(Q_2\) обязаны иметь как минимум **один общий узел** (\(Q_1 \cap Q_2 \neq \emptyset\)). Этот общий узел отклонит второй запрос флагом `NX`, гарантируя невозможность одновременного кворума.

## Подводные камни

- **Использование четного числа узлов (\(N=4\))**: При 4 узлах кворум равен 3. Падение двух узлов оставляет 2 узла — кворум потерян. Четное число узлов не увеличивает отказоустойчивость.
- **Откат чужих ключей**: Вызов `DEL` без проверки токена сотрет лок конкурента.

## На собеседовании

В Касперском и Ozon на архитектурном собеседовании спрашивают: *«Что произойдет в Redlock, если 2 клиента одновременно отправят запросы к 5 узлам, и каждый успеет захватить по 2 узла, а пятый узел упадет?»*
**Ответ**: Ни один из клиентов не сможет набрать кворум (для кворума требуется 3 узла, а каждый набрал только 2). Оба клиента зафиксируют ошибку нехватки голосов, выполнят компенсационный откат (удалят свои токены на захваченных узлах) и уснут на случайный интервал с Full Jitter. Тот клиент, у которого таймер джиттера истечет раньше, захватит освободившиеся узлы в следующем раунде.
