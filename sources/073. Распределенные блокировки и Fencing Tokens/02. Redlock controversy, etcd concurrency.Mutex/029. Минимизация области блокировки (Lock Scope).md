# Минимизация области блокировки (Lock Scope): вынос I/O операций за пределы критической секции

## Условие

29. **Lock scope**: Минимизируйте critical section под lock. Не держите lock дольше необходимого. Вынесите валидацию, парсинг и подготовку данных наружу.

### Исходная формулировка

**Lock scope**: Минимизируйте critical section под lock. Не держите lock дольше необходимого.

## Теория

Золотое правило высокопроизводительных распределенных систем:
**Область действия блокировки (Lock Scope) обязана быть минимально возможной (Microsecond-level Critical Section).**

Антипаттерн «Широкая блокировка» (Fat Lock Scope):
```go
lock.Lock()
defer lock.Unlock()
// 1. Чтение данных из сети (HTTP запрос к стороннему API) -> 500 мс!
// 2. Валидация JSON схемы -> 20 мс!
// 3. Генерация PDF-отчета -> 1200 мс!
// 4. Атомарный инкремент счетчика -> 1 мс!
```
Последствия: ресурс удерживается почти 2 секунды. Максимальный теоретический Throughput системы ограничен значением \(1 / 2\text{ с} = 0.5\text{ RPS}\)! Все остальные воркеры стоят в очереди.

Паттерн «Узкая блокировка» (Slim Lock Scope):
1. Вся подготовка, валидация данных, парсинг JSON и внешние вызовы выполняются **ДО захвата блокировки**.
2. Блокировка захватывается **только на время финальной атомарной модификации** (например, запись в БД за 5 мс).
3. Throughput вырастает с \(0.5\text{ RPS}\) до \(200+\text{ RPS}\).

## Решение по шагам

1. Создайте класс симулятора тяжелой задачи с фазами: подготовка (Pre-processing), критическая запись (Commit) и постобработка (Post-processing).
2. Реализуйте неоптимальный вариант: вся задача обернута в `Lock/Unlock`.
3. Реализуйте оптимизированный вариант: лок берется строго на время фазы коммита.
4. Сравните время удержания блокировки (Lock Contention Time).
5. Продемонстрируйте многократный рост пропускной способности системы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type MetricsTracker struct {
	mu           sync.Mutex
	holdDuration time.Duration
}

type HeavyOrderTask struct {
	OrderID   string
	RawJSON   string
	ParsedDoc string
}

// 1. Preparation outside lock (CPU-intensive or network I/O)
func PrepareData(orderID string) *HeavyOrderTask {
	// Simulating external network call & complex parsing (150ms)
	time.Sleep(150 * time.Millisecond)
	return &HeavyOrderTask{
		OrderID:   orderID,
		ParsedDoc: "Validated & Prepared Document for " + orderID,
	}
}

// 2. Slim Critical Section (In-Memory / Atomic DB Write)
func CommitOrderSlim(gate *sync.Mutex, task *HeavyOrderTask, tracker *MetricsTracker) {
	start := time.Now()

	gate.Lock()
	// CRITICAL SECTION: strictly minimal (only state change)
	time.Sleep(5 * time.Millisecond) // Fast atomic update
	gate.Unlock()

	duration := time.Since(start)
	tracker.mu.Lock()
	tracker.holdDuration += duration
	tracker.mu.Unlock()
}

// 3. Bad Practice: Fat Lock Scope wrapping entire pipeline
func CommitOrderFat(gate *sync.Mutex, orderID string, tracker *MetricsTracker) {
	start := time.Now()

	gate.Lock()
	// Holding lock during 150ms I/O preparation! (ANTI-PATTERN)
	time.Sleep(150 * time.Millisecond)
	time.Sleep(5 * time.Millisecond)
	gate.Unlock()

	duration := time.Since(start)
	tracker.mu.Lock()
	tracker.holdDuration += duration
	tracker.mu.Unlock()
}

func main() {
	var gate sync.Mutex
	slimTracker := &MetricsTracker{}
	fatTracker := &MetricsTracker{}

	fmt.Println("=== Comparing Lock Scope Performance ===")

	// Simulating 5 sequential orders with Slim Scope
	for i := 1; i <= 5; i++ {
		task := PrepareData(fmt.Sprintf("order-%d", i))
		CommitOrderSlim(&gate, task, slimTracker)
	}

	// Simulating 5 sequential orders with Fat Scope
	for i := 1; i <= 5; i++ {
		CommitOrderFat(&gate, fmt.Sprintf("order-%d", i), fatTracker)
	}

	fmt.Printf("Total Lock Held Time (Slim Scope): %v (Max Throughput: ~200 ops/sec)\n", slimTracker.holdDuration)
	fmt.Printf("Total Lock Held Time (Fat Scope):  %v (Max Throughput: ~6 ops/sec)\n", fatTracker.holdDuration)
	fmt.Println("🚀 Slim Scope reduced lock contention by over 95%!")
}
```

## Под капотом

Закон Амдала (Amdahl's Law) в распределенных системах:
Максимально возможное ускорение системы при параллелизации ограничено долей последовательного кода:
$$S = \frac{1}{(1 - P) + \frac{P}{N}}$$
Где \(P\) — доля параллельного кода, а \((1 - P)\) — время нахождения под распределенной блокировкой.
Если блокировка удерживается 150 мс из 200 мс работы функции (\(75\%\)), добавление хоть 1000 подов в Kubernetes не сможет поднять производительность системы более чем в 1.33 раза!
Сужение области блокировки до 5 мс (\(2.5\%\)) открывает возможность 40-кратного линейного масштабирования.

## Подводные камни

- **Вызов сторонних HTTP API под распределенным мьютексом**: Сторонний платежный шлюз задерживает ответ на 5 секунд — вся очередь входящих запросов встает в ступор.
- **Транзакционный лог в цикле**: Накопление данных в память под локом вместо пакетной обработки.

## На собеседовании

В Wildberries и Авито часто спрашивают: *«Как провести аудит микросервиса, в котором распределенные блокировки стали боттлнеком производительности?»*
**Ответ**:
1. Замерить гистограмму метрики `lock_held_duration_seconds`.
2. Найти код внутри критической секции и вынести наружу все операции валидации, маршалинга JSON, обращений к кэшу и внешним HTTP/gRPC сервисам.
3. Оставить под блокировкой только атомарное изменение состояния в БД.
4. Проверить возможность замены эксклюзивного мьютекса на шардированные блокировки (Sharded Locks / Key-based Striping) по `hash(user_id)`.
