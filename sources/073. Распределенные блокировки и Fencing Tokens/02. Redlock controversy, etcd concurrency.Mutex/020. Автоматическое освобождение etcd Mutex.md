# Автоматическое освобождение etcd Mutex при истечении Lease: защита от аварий процессов

## Условие

20. **etcd lock + lease**: etcd lock автоматически освобождается при session expiry (lease TTL). Смоделируйте случай аварийного закрытия сессии и проверьте передачу лока второму процессу.

### Исходная формулировка

**etcd lock + lease**: etcd lock автоматически освобождается при session expiry (lease TTL).

## Теория

Связка `concurrency.Mutex` и `concurrency.Session` в etcd:

Ключевые инварианты:
1. **Эфемерность ключей**:
   - Ключ мьютекса создается с опцией `clientv3.WithLease(session.Lease())`.
   - Это означает: «Если аренда исчезает, база etcd **обязана физически удалить этот ключ**».
2. **Сеть и фоновые процессы**:
   - Пока приложение живет, фоновый gRPC-поток шлет `LeaseKeepAlive` каждые $TTL/3$ секунд.
3. **Краш процесса**:
   - При внезапном завершении процесса (`kill -9`, segmentation fault, out-of-memory) поток KeepAlive мгновенно прекращается.
   - etcd отсчитывает оставшиеся секунды Lease TTL.
   - По истечении TTL кластер etcd выполняет операцию `LeaseRevoke`.
   - Ключ удаляется из B-Tree.
   - Следующий ожидающий процесс в очереди мгновенно получает событие `DELETE` через свой `Watch` и становится полноправным владельцем блокировки.

## Решение по шагам

1. Создайте модель etcd кластера с механизмом отслеживания аренды.
2. Процесс 1 захватывает блокировку с привязкой к Lease TTL = 200 мс.
3. Процесс 2 ожидает освобождения ресурса.
4. Сымитируйте аварию Процесса 1 с обрывом потока KeepAlive.
5. Зафиксируйте момент истечения аренды и автоматический переход прав к Процессу 2.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type LeaseEngine struct {
	mu        sync.Mutex
	owner     string
	leaseExp  time.Time
	transfer  chan string
	isDead    bool
}

func NewLeaseEngine() *LeaseEngine {
	return &LeaseEngine{
		transfer: make(chan string, 1),
	}
}

func (e *LeaseEngine) Acquire(worker string, ttl time.Duration) {
	e.mu.Lock()
	defer e.mu.Unlock()

	e.owner = worker
	e.leaseExp = time.Now().Add(ttl)
	e.isDead = false
	fmt.Printf("[etcd Engine] Granted lock to %s with Lease TTL = %v\n", worker, ttl)
}

func (e *LeaseEngine) SimulateCrash(worker string) {
	e.mu.Lock()
	if e.owner == worker {
		e.isDead = true
		fmt.Printf("💥 %s process KILLED (SIGKILL)! KeepAlive stream abruptly disconnected.\n", worker)
	}
	e.mu.Unlock()
}

func (e *LeaseEngine) StartReaperLoop() {
	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	for range ticker.C {
		e.mu.Lock()
		if e.owner != "" && e.isDead && time.Now().After(e.leaseExp) {
			fmt.Printf("[etcd Reaper] Lease expired for dead worker '%s'! Revoking lease and deleting lock key.\n", e.owner)
			e.owner = ""
			e.mu.Unlock()
			e.transfer <- "Worker-2"
			return
		}
		e.mu.Unlock()
	}
}

func main() {
	engine := NewLeaseEngine()
	go engine.StartReaperLoop()

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// 1. Worker 1 acquires lock with 150ms lease
	engine.Acquire("Worker-1", 150*time.Millisecond)

	// 2. Worker 1 crashes after 50ms
	time.Sleep(50 * time.Millisecond)
	engine.SimulateCrash("Worker-1")

	// 3. Worker 2 waits for lock transfer via etcd watch
	fmt.Println("[Worker-2] Waiting on etcd Watch stream for lock key...")
	select {
	case <-ctx.Done():
		panic("timeout waiting for lock")
	case nextWorker := <-engine.transfer:
		fmt.Printf("🎉 %s woke up! Lock ownership successfully transferred via Lease Revocation!\n", nextWorker)
	}
}
```

ℹ️ Моделирование отзыва etcd Lease и пробуждения следующего процесса в очереди

## Под капотом

Как etcd очищает аренды под капотом:
- Сервер etcd хранит структуру `lessor`, управляющую всеми активными `Lease`.
- Аренды сгруппированы в min-heap по времени экспирации.
- Фоновый цикл `lessor.RevokeExpiredLeases` извлекает просроченные аренды, ищет все привязанные ключи и отправляет команду `Txn` в Raft WAL.
- Это гарантирует, что удаление ключей является закоммиченным событием консенсуса, реплицируемым на все узлы кластера.

## Подводные камни

- **Слишком длинный TTL сессии**: Если выставить `concurrency.NewSession(client, concurrency.WithTTL(300))` (5 минут), то при крахе пода следующий инстанс будет ждать 5 минут до захвата блокировки! Для быстрого фейловера TTL выставляют в 5–10 секунд.
- **Слишком короткий TTL при нагрузке**: TTL \(< 2\text{ с}\) может привести к ложному отзыву при сетевых задержках.

## На собеседовании

В Wildberries и Т-Банке часто спрашивают: *«Какой параметр TTL сессии вы порекомендуете настроить для etcd Mutex в распределенном сервисе с жестким SLA доступности?»*
**Ответ**: Рекомендуемый баланс в продакшене — **5–10 секунд**.
- Если процесс упадет, система восстановит обработку максимум через 5–10 секунд (MTTR).
- При этом клиент шлет KeepAlive каждые \(1.5-3\text{ с}\), что дает запас прочности на 2–3 потерянных пакета или кратковременную паузу GC без риска ложной потери блокировки.
