# Распределенные блокировки чтения-записи (Distributed Read-Write Locks): параллельное чтение и эксклюзивная запись

## Условие

32. **Read-write locks**: Для read-heavy workloads используйте read-write locks (multiple readers, single writer). Реализуйте распределенный RWMutex на Redis или etcd.

### Исходная формулировка

**Read-write locks**: Для read-heavy workloads используйте read-write locks (multiple readers, single writer).

## Теория

В сценариях с преобладанием операций чтения (Read-Heavy Workloads, 95% чтений и 5% записей) эксклюзивный мьютекс превращается в колоссальный боттлнек, заставляя читателей вставать в одну очередь.

Контракт распределенного **RWMutex (Shared Reader / Exclusive Writer Lock)**:
1. **`RLock()` (Shared Lock)**:
   - Множество читателей могут одновременно удерживать блокировку на чтение.
   - Запись инкрементирует счетчик активных читателей: `INCR lock:<res>:readers`.
   - Разрешено только при отсутствии активного писателя.
2. **`RUnlock()`**:
   - Читатель декрементирует счетчик: `DECR lock:<res>:readers`.
3. **`Lock()` (Exclusive Writer Lock)**:
   - Писатель требует монопольного доступа: ни одного активного читателя (`readers == 0`) и ни одного активного писателя.
   - Устанавливает эксклюзивный флаг `SET lock:<res>:writer token NX PX ttl`.
4. **`Unlock()`**:
   - Писатель атомарно удаляет ключ писателя.

## Решение по шагам

1. Создайте структуру `DistributedRWMutex` с раздельными ключами для писателей и счетчика читателей.
2. Реализуйте метод `RLock` с проверкой отсутствия активного писателя.
3. Реализуйте метод `Lock` с ожиданием завершения всех активных читателей.
4. Продемонстрируйте параллельную работу 3 читателей без блокировки друг друга.
5. Покажите, как писатель блокирует всех новых читателей до завершения своей транзакции.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type DistributedRWMutexStore struct {
	mu           sync.Mutex
	writerHolder string
	readerCount  int
}

type DistributedRWMutex struct {
	store *DistributedRWMutexStore
	name  string
}

func NewDistributedRWMutex(store *DistributedRWMutexStore, name string) *DistributedRWMutex {
	return &DistributedRWMutex{store: store, name: name}
}

// RLock: shared read access
func (m *DistributedRWMutex) RLock(readerID string) error {
	m.store.mu.Lock()
	defer m.store.mu.Unlock()

	if m.store.writerHolder != "" {
		return fmt.Errorf("read rejected: exclusive writer '%s' is active", m.store.writerHolder)
	}

	m.store.readerCount++
	fmt.Printf("[RWMutex] 📖 Reader '%s' acquired shared lock. Active readers: %d\n",
		readerID, m.store.readerCount)
	return nil
}

func (m *DistributedRWMutex) RUnlock(readerID string) {
	m.store.mu.Lock()
	defer m.store.mu.Unlock()

	if m.store.readerCount > 0 {
		m.store.readerCount--
		fmt.Printf("[RWMutex] 📖 Reader '%s' released shared lock. Active readers: %d\n",
			readerID, m.store.readerCount)
	}
}

// Lock: exclusive write access
func (m *DistributedRWMutex) Lock(writerID string) error {
	m.store.mu.Lock()
	defer m.store.mu.Unlock()

	if m.store.writerHolder != "" {
		return errors.New("writer lock busy")
	}
	if m.store.readerCount > 0 {
		return fmt.Errorf("writer rejected: %d active readers still reading", m.store.readerCount)
	}

	m.store.writerHolder = writerID
	fmt.Printf("[RWMutex] ✍️ WRITER '%s' acquired EXCLUSIVE lock!\n", writerID)
	return nil
}

func (m *DistributedRWMutex) Unlock(writerID string) {
	m.store.mu.Lock()
	defer m.store.mu.Unlock()

	if m.store.writerHolder == writerID {
		m.store.writerHolder = ""
		fmt.Printf("[RWMutex] ✍️ WRITER '%s' released exclusive lock.\n", writerID)
	}
}

func main() {
	store := &DistributedRWMutexStore{}
	rw := NewDistributedRWMutex(store, "catalog:products")

	fmt.Println("=== 1. Multiple Concurrent Readers (Shared Access) ===")
	_ = rw.RLock("reader-pod-1")
	_ = rw.RLock("reader-pod-2")
	_ = rw.RLock("reader-pod-3")

	fmt.Println("\n=== 2. Writer attempts to acquire exclusive lock while readers active ===")
	err := rw.Lock("writer-pod-A")
	if err != nil {
		fmt.Printf("🛡️ Writer blocked as expected: %v\n", err)
	}

	fmt.Println("\n=== 3. Readers finish and release shared locks ===")
	rw.RUnlock("reader-pod-1")
	rw.RUnlock("reader-pod-2")
	rw.RUnlock("reader-pod-3")

	fmt.Println("\n=== 4. Writer retries acquisition (All readers gone) ===")
	if err := rw.Lock("writer-pod-A"); err == nil {
		fmt.Println("Writer modifying catalog data exclusively...")
		rw.Unlock("writer-pod-A")
	}
}
```

## Под капотом

Проблема голодания писателя (Writer Starvation):
Если поток читателей непрерывен (новые читатели приходят быстрее, чем уходят старые), счетчик `readerCount` никогда не опустится до нуля! Писатель будет ждать бесконечно (Starvation).
В продвинутых реализациях (например, Redisson RWMutex):
Когда писатель объявляет о намерении захватить лок, он выставляет флаг `write_intent = true`. Все новые читатели перестают допускаться к чтению и ждут завершения писателя, предотвращая голодание.

## Подводные камни

- **Забытый `RUnlock()` у одного из 50 читателей**: Если один читатель упадет без снятия лока, счетчик `readerCount` навсегда останется \(>0\), заблокировав всех писателей в системе! Читательские локи обязаны иметь жесткий TTL.
- **Двойное снятие читательского лока**: Декремент ниже нуля разрушает логику.

## На собеседовании

В Авито и Яндекс Маркете часто спрашивают: *«Как в распределенном RWMutex на Redis предотвратить утечку счетчика читателей при падении одного из подов-читателей?»*
**Ответ**: Вместо простого числового счетчика `readerCount` использовать структуру **Redis Hash** со списком активных читателей: `HSET lock:readers <token> <expire_at>`. Фоновый Lua-скрипт при каждой проверке валидирует временные метки читателей и автоматически удаляет протухшие токены упавших подов, предотвращая вечную блокировку писателя.
