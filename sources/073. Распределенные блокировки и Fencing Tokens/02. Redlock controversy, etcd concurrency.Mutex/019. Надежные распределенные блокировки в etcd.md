# Надежные распределенные блокировки в etcd: concurrency.NewSession и concurrency.NewMutex

### Исходная формулировка

**etcd distributed lock**: Используйте etcd для reliable distributed locks:
```go
session, _ := concurrency.NewSession(client)
mutex := concurrency.NewMutex(session, "/locks/my-lock")
mutex.Lock(ctx)
defer mutex.Unlock(ctx)
```

## Теория

Библиотека `go.etcd.io/etcd/client/v3/concurrency` предоставляет эталонный примитив распределенной синхронизации на базе протокола Raft:

Компоненты:
1. **`concurrency.NewSession(client, opts...)`**:
   - Автоматически создает Lease в etcd (по умолчанию TTL 60 сек).
   - Запускает фоновый двунаправленный gRPC KeepAlive стрим.
   - Экспортирует канал `session.Done()`, который закрывается, если аренда потеряна (обрыв сети или падение etcd).
2. **`concurrency.NewMutex(session, prefix)`**:
   - Реализует блокировку на основе упорядоченных префиксов MVCC.
   - Метод `mutex.Lock(ctx)`:
     - Создает ключ `/locks/my-lock/<lease_id>`.
     - Находит всех владельцев префикса и определяет свой порядковый номер.
     - Если ключ не первый, подписывается через `Watch` на своего предшественника.
   - Метод `mutex.Unlock(ctx)`: удаляет ключ и передает эстафету следующему пиру.
   - Метод `mutex.Header().Revision`: возвращает монотонную ревизию etcd, готовую к использованию в качестве **Fencing Token**!

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// Emulation of etcd clientv3/concurrency
type EtcdSessionMock struct {
	LeaseID int64
	doneCh  chan struct{}
	mu      sync.Mutex
	closed  bool
}

func (s *EtcdSessionMock) Done() <-chan struct{} {
	return s.doneCh
}

func (s *EtcdSessionMock) Close() {
	s.mu.Lock()
	defer s.mu.Unlock()
	if !s.closed {
		s.closed = true
		close(s.doneCh)
	}
}

type EtcdMutexMock struct {
	session    *EtcdSessionMock
	prefix     string
	revision   int64
	holderID   int64
	mu         sync.Mutex
	globalLock sync.Mutex
}

func NewEtcdMutexMock(s *EtcdSessionMock, prefix string) *EtcdMutexMock {
	return &EtcdMutexMock{
		session: s,
		prefix:  prefix,
	}
}

func (m *EtcdMutexMock) Lock(ctx context.Context) error {
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-m.session.Done():
		return fmt.Errorf("session already expired")
	default:
	}

	m.globalLock.Lock()
	m.holderID = m.session.LeaseID
	m.revision = time.Now().UnixNano()
	fmt.Printf("[etcd concurrency.Mutex] Lock acquired on '%s' (Lease: %d, Fencing Revision: %d)\n",
		m.prefix, m.holderID, m.revision)
	return nil
}

func (m *EtcdMutexMock) Unlock(ctx context.Context) error {
	m.holderID = 0
	m.globalLock.Unlock()
	fmt.Printf("[etcd concurrency.Mutex] Lock '%s' released successfully.\n", m.prefix)
	return nil
}

func (m *EtcdMutexMock) Revision() int64 {
	return m.revision
}

func main() {
	session := &EtcdSessionMock{LeaseID: 778899, doneCh: make(chan struct{})}
	defer session.Close()

	mutex := NewEtcdMutexMock(session, "/locks/order/1001")
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	fmt.Println("--- 1. Acquiring etcd Distributed Mutex ---")
	if err := mutex.Lock(ctx); err != nil {
		panic(err)
	}
	defer mutex.Unlock(ctx)

	// Obtain Fencing Token from etcd revision!
	fencingToken := mutex.Revision()
	fmt.Printf("Generated Fencing Token for DB: %d\n", fencingToken)

	// Critical section with session liveness check
	fmt.Println("Executing business critical section...")
	select {
	case <-session.Done():
		fmt.Println("🚨 ABORT: Session expired unexpectedly during critical section!")
		return
	case <-time.After(100 * time.Millisecond):
		fmt.Println("✅ Critical section finished safely!")
	}
}
```

ℹ️ Каноничная интеграция etcd concurrency.Mutex с мониторингом сессии и Fencing Revision

## Под капотом

Как etcd гарантирует честность FIFO:
Каждый вызов `Lock` создает эфемерный ключ с монотонной ревизией etcd:
- Клиент 1: `/locks/p/0000000000000010` (Rev 10)
- Клиент 2: `/locks/p/0000000000000015` (Rev 15)
- Клиент 3: `/locks/p/0000000000000018` (Rev 18)
Клиент 3 видит, что перед ним есть Rev 15, и подписывается только на нее. Клиент 2 подписывается на Rev 10.
Когда Клиент 1 удаляет Rev 10, сервер etcd отправляет событие ровно Клиенту 2. Клиент 3 спит и не тратит CPU.

## Подводные камни

- **Игнорирование закрытия `session.Done()`**: Если сеть между подом и etcd оборвется, etcd отзовет аренду через 60 секунд. Если pod продолжает молотить в критической секции без проверки `session.Done()`, он превращается в зомби.
- **Утечка контекста в `mutex.Lock(context.Background())`**: При сетевой изоляции горутина зависнет навечно.

## На собеседовании

В Касперском и Ozon на системном дизайне часто спрашивают: *«Как извлечь Fencing Token из `concurrency.Mutex` библиотеки etcd?»*
**Ответ**: Вызвать метод `mutex.Header().Revision`. etcd возвращает 64-битную глобальную ревизию кластера, зафиксированную в момент атомарной транзакции создания ключа мьютекса. Это число строго монотонно возрастает при каждом изменении кластера и идеально подходит на роль `fencing_token` для валидации на стороне PostgreSQL или внешнего API.
