# Нагрузочное тестирование распределенных мьютексов: проверка инварианта взаимного исключения

## Условие

34. **Lock testing**: Напишите тесты, которые:
    * Запускают N concurrent goroutines
    * Каждая пытается захватить lock
    * Проверяют, что только одна goroutine в critical section одновременно (active_holders <= 1).

### Исходная формулировка

**Lock testing**: Напишите тесты, которые:
* Запускают N concurrent goroutines
* Каждая пытается захватить lock
* Проверяют, что только одна goroutine в critical section одновременно

## Теория

Методология верификации распределенных мьютексов:

Ключевой инвариант безопасности (Safety Invariant):
В любой момент времени \(t\) количество горутин, одновременно исполняющих код внутри критической секции, обязано строго удовлетворять условию:
$$\text{ActiveHolders}(t) \le 1$$

Как тестировать:
1. Запускается \(N\) параллельных горутин (\(N \ge 50\)).
2. Каждая горутина пытается захватить распределенный мьютекс.
3. Внутри критической секции:
   - Атомарно инкрементируется счетчик `atomic.AddInt32(&activeHolders, 1)`.
   - Проверяется условие: `if activeHolders > 1 { panic("MUTEX BROKEN: Race detected!") }`.
   - Выполняется случайная задержка (1–5 мс), провоцирующая состояние гонки при ошибках реализации.
   - Атомарно декрементируется счетчик `atomic.AddInt32(&activeHolders, -1)`.
4. Тест считается пройденным, если все \(N\) горутин завершили выполнение и ни разу не было зафиксировано \(\text{activeHolders} > 1\).

## Решение по шагам

1. Создайте структуру счетчика нарушений `ConcurrencyAuditGuard`.
2. Реализуйте стресс-тест с 30 параллельными горутинами.
3. Внедрите счетчик одновременных держателей `atomic.Int32`.
4. Проверьте инвариант `active <= 1` на протяжении 100 циклов захвата.
5. Убедитесь в отсутствии состояний гонки и корректной работе мьютекса под нагрузкой.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"sync/atomic"
	"time"
)

type TestedDistributedMutex struct {
	mu     sync.Mutex
	holder int
	busy   bool
}

func (m *TestedDistributedMutex) Lock(id int) {
	for {
		m.mu.Lock()
		if !m.busy {
			m.busy = true
			m.holder = id
			m.mu.Unlock()
			return
		}
		m.mu.Unlock()
		time.Sleep(time.Duration(rand.Intn(5)) * time.Millisecond)
	}
}

func (m *TestedDistributedMutex) Unlock(id int) {
	m.mu.Lock()
	defer m.mu.Unlock()
	if m.busy && m.holder == id {
		m.busy = false
		m.holder = 0
	}
}

func main() {
	mutex := &TestedDistributedMutex{}
	const numGoroutines = 30
	const iterationsPerGoroutine = 5

	var activeHolders int32
	var violationsCount int32
	var totalOperations int64

	var wg sync.WaitGroup
	fmt.Printf("=== Running Stress Concurrency Test (%d Goroutines, %d Ops Each) ===\n",
		numGoroutines, iterationsPerGoroutine)

	for i := 1; i <= numGoroutines; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()

			for iter := 0; iter < iterationsPerGoroutine; iter++ {
				mutex.Lock(workerID)

				// INVARIANT CHECK: exactly one worker allowed inside critical section
				current := atomic.AddInt32(&activeHolders, 1)
				if current > 1 {
					atomic.AddInt32(&violationsCount, 1)
					fmt.Printf("🚨 RACE CONDITION! Active holders = %d (Worker: %d)\n", current, workerID)
				}

				// Simulate unpredictable workload inside critical section
				time.Sleep(time.Duration(rand.Intn(4)+1) * time.Millisecond)

				atomic.AddInt32(&activeHolders, -1)
				atomic.AddInt64(&totalOperations, 1)

				mutex.Unlock(workerID)
				time.Sleep(time.Duration(rand.Intn(3)) * time.Millisecond)
			}
		}(i)
	}

	wg.Wait()

	fmt.Println("\n=== STRESS TEST RESULTS ===")
	fmt.Printf("Total Critical Section Executions: %d\n", totalOperations)
	fmt.Printf("Concurrency Invariant Violations: %d\n", violationsCount)

	if violationsCount == 0 {
		fmt.Println("✅ PASSED: 100% Mutual Exclusion verified! Active holders never exceeded 1.")
	} else {
		fmt.Println("❌ FAILED: Mutex implementation has race conditions!")
	}
}
```

ℹ️ Стресс-тестирование взаимного исключения в распределенном мьютексе

## Под капотом

Тестирование распределенных систем с `go test -race`:
Флаг `-race` компилятора Go встраивает инструмент ThreadSanitizer.
Однако ThreadSanitizer анализирует **только локальную память одного процесса ОС**.
Он не способен обнаружить распределенные гонки между двумя процессами через сокеты Redis или etcd!
Поэтому для верификации распределенного мьютекса используют интеграционные стресс-тесты с валидацией внешних счетчиков (`atomic.Int32`) или проверку линейности через верификаторы Porcupine / Jepsen.

## Подводные камни

- **Тестирование без искусственных задержек**: Если критическая секция выполняется за 5 наносекунд, вероятность совпадения горутин во времени мала. Случайный `time.Sleep(1..5ms)` провоцирует максимальное перекрытие интервалов.
- **Deadlock в тестах без таймаута**: Всегда оборачивайте тесты в `t.Deadline()`.

## На собеседовании

В Lamoda и Авито на секции лайвкодинга часто просят: *«Напишите юнит-тест, доказывающий, что ваша реализация мьютекса не допускает параллельного входа двух горутин в критическую секцию»*.
**Ответ**: Использовать `atomic.AddInt32(&counter, 1)` при входе и `atomic.AddInt32(&counter, -1)` при выходе. Если `counter > 1`, зафиксировать ошибку `t.Fatalf("Mutual exclusion violated: %d holders", val)`. Запустить 50+ конкурентных горутин с использованием `sync.WaitGroup` и случайной задержкой внутри секции, доказав строгое соблюдение инварианта взаимного исключения.
