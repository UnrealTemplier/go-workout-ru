# Стратегия повторов при блокировках: экспоненциальный откат (Exponential Backoff) и Full Jitter

## Условие

27. **Lock retry with backoff**: Если lock не получен, retry с exponential backoff + jitter. Реализуйте алгоритм повторных попыток для устранения коллизий конкурентов.

### Исходная формулировка

**Lock retry with backoff**: Если lock не получен, retry с exponential backoff + jitter.

## Теория

Когда ресурс занят, наивный опрос (Spin-lock с фиксированным `time.Sleep(100ms)`) приводит к эффекту **самосинхронизации (Self-Synchronization)**:
Сотни воркеров одновременно засыпают на 100 мс, одновременно просыпаются и одновременно шлют запросы к координатору (Redis/etcd), вызывая спайки нагрузки и взаимные отказы.

Математическая модель Full Jitter (AWS Architecture Best Practice):
1. **Базовый интервал**: \(B\) (например, \(20\text{ мс}\)).
2. **Максимальный потолок**: \(M\) (например, \(1000\text{ мс}\)).
3. **Экспоненциальная граница**: \(E_i = \min(M, B \times 2^i)\), где \(i\) — номер попытки.
4. **Full Jitter**:
   $$\text{SleepTime} = \text{random}(0, E_i)$$

Случайный разброс времени от нуля до экспоненциального предела равномерно распределяет запросы во времени, сводя вероятность повторного одновременного столкновения практически к нулю.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"math/rand"
	"sync"
	"time"
)

type BackoffConfig struct {
	BaseDelay   time.Duration
	MaxDelay    time.Duration
	MaxAttempts int
}

type BackoffRetrier struct {
	cfg BackoffConfig
	rng *rand.Rand
	mu  sync.Mutex
}

func NewBackoffRetrier(cfg BackoffConfig) *BackoffRetrier {
	return &BackoffRetrier{
		cfg: cfg,
		rng: rand.New(rand.NewSource(time.Now().UnixNano())),
	}
}

// Full Jitter: Sleep = rand(0, min(MaxDelay, BaseDelay * 2^attempt))
func (b *BackoffRetrier) NextDelay(attempt int) time.Duration {
	b.mu.Lock()
	defer b.mu.Unlock()

	multiplier := 1 << attempt // 2^attempt
	temp := b.cfg.BaseDelay * time.Duration(multiplier)
	if temp > b.cfg.MaxDelay || temp < 0 { // overflow guard
		temp = b.cfg.MaxDelay
	}

	sleepNs := b.rng.Int63n(int64(temp))
	return time.Duration(sleepNs)
}

type SimpleSharedGate struct {
	mu     sync.Mutex
	holder string
}

func (g *SimpleSharedGate) TryAcquire(worker string) bool {
	g.mu.Lock()
	defer g.mu.Unlock()
	if g.holder == "" {
		g.holder = worker
		return true
	}
	return false
}

func (g *SimpleSharedGate) Release(worker string) {
	g.mu.Lock()
	defer g.mu.Unlock()
	if g.holder == worker {
		g.holder = ""
	}
}

func main() {
	gate := &SimpleSharedGate{}
	cfg := BackoffConfig{
		BaseDelay:   20 * time.Millisecond,
		MaxDelay:    300 * time.Millisecond,
		MaxAttempts: 8,
	}

	var wg sync.WaitGroup
	workers := []string{"Client-Alfa", "Client-Bravo", "Client-Charlie"}

	for _, w := range workers {
		wg.Add(1)
		go func(workerID string) {
			defer wg.Done()
			retrier := NewBackoffRetrier(cfg)
			ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
			defer cancel()

			for attempt := 0; attempt < cfg.MaxAttempts; attempt++ {
				if gate.TryAcquire(workerID) {
					fmt.Printf("🎉 [%s] Acquired lock on attempt %d!\n", workerID, attempt+1)
					time.Sleep(60 * time.Millisecond) // critical section
					gate.Release(workerID)
					return
				}

				delay := retrier.NextDelay(attempt)
				select {
				case <-ctx.Done():
					fmt.Printf("[%s] Aborted by context deadline.\n", workerID)
					return
				case <-time.After(delay):
					// Retry after jittered delay
				}
			}
			fmt.Printf("[%s] Exhausted max retries.\n", workerID)
		}(w)
	}

	wg.Wait()
	fmt.Println("All competing clients resolved conflicts smoothly via Exponential Backoff with Full Jitter!")
}
```

ℹ️ Реализация алгоритма Exponential Backoff с Full Jitter для распределенных повторов

## Под капотом

Сравнение стратегий Backoff (исследование Amazon AWS):
1. **Без Jitter (`delay = Base * 2^i`)**: Коллизии сохраняются, волны запросов двигаются строем синхронно.
2. **Equal Jitter (`delay = (limit/2) + rand(0, limit/2)`)**: Снижает коллизии, но оставляет половину интервала жестко детерминированной.
3. **Full Jitter (`delay = rand(0, limit)`)**: Математически доказано обеспечивает **минимальное суммарное время ожидания клиентов** и минимальную пиковую нагрузку на сервер координации.

## Подводные камни

- **Целочисленное переполнение `2^attempt`**: В Go при `attempt > 62` выражение `1 << attempt` переполняется в отрицательное число! Всегда проверяйте границы и ограничивайте экспоненту сверху.
- **Общий генератор `rand.Rand` без мьютекса**: Вызов `rand.Int63n()` не является потокобезопасным и вызовет Data Race.

## На собеседовании

В Яндекс Такси и Авито часто спрашивают: *«Почему Full Jitter превосходит обычный экспоненциальный откат при конкуренции за распределенный мьютекс?»*
**Ответ**: При обычном экспоненциальном откате конкурирующие процессы получают строго одинаковые задержки (\(20\text{ мс}, 40\text{ мс}, 80\text{ мс}\)). Они просыпаются одновременно и повторно атакуют сервер (Thundering Herd). Full Jitter рандомизирует интервал в диапазоне \([0, 2^i \times B]\), полностью разрушая периодичность и распределяя запросы по непрерывной временной оси, что снижает процент коллизий в десятки раз.
