## Теория

Знаменитая научная дискуссия между Мартином Клеппманом (Martin Kleppmann, Кембриджский университет) и Сальваторе Санфилиппо (Salvatore Sanfilippo, автор Redis):

Клеппман разделил цели использования блокировок на две фундаментальные категории:
1. **Блокировки для Эффективности (Locking for Efficiency)**:
   - Цель: предотвратить дублирование дорогостоящих вычислений (например, рендеринг картинки, парсинг отчета, прогрев кэша).
   - Сценарий сбоя: если блокировка нарушится (два процесса выполнят работу одновременно), система потратит чуть больше CPU/RAM, но данные **не будут повреждены**.
   - Вердикт: Для эффективности Redlock **избыточно сложен и дорог**. Достаточно одного инстанса Redis с `SET NX EX`. Разворачивать 5 отдельных инстансов ради кеша бессмысленно.
2. **Блокировки для Корректности (Locking for Correctness)**:
   - Цель: предотвратить потерю данных, порчу инвентаря, двойное списание денег со счетов.
   - Сценарий сбоя: если два процесса одновременно зайдут в критическую секцию, данные будут необратимо искажены.
   - Вердикт: Для корректности Redlock **недостаточно надежен (unsafe)**, так как:
     - Опирается на синхронность физических часов (Clock Skew / NTP jumps).
     - Не защищает от пауз процессов (GC Pause, гипервизор, сетевой лаг).
     - Не предоставляет монотонных токенов ограждения (**Fencing Tokens**).

Итог: Либо Redlock избыточен (для efficiency), либо недостаточен (для correctness). Для строгой корректности необходим Raft/etcd + Fencing Token.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

type UseCaseCategory string

const (
	CategoryEfficiency  UseCaseCategory = "Efficiency (Optimization)"
	CategoryCorrectness UseCaseCategory = "Correctness (Data Integrity)"
)

type LockingDecision struct {
	Category       UseCaseCategory
	System         string
	RequiresTokens bool
	Rationale      string
}

func EvaluateLockingStrategy(cat UseCaseCategory) LockingDecision {
	switch cat {
	case CategoryEfficiency:
		return LockingDecision{
			Category:       cat,
			System:         "Single Redis (SET NX EX)",
			RequiresTokens: false,
			Rationale:      "Failures only waste CPU; fast and simple. Redlock is wasteful overkill here.",
		}
	case CategoryCorrectness:
		return LockingDecision{
			Category:       cat,
			System:         "etcd / Consul with Fencing Tokens",
			RequiresTokens: true,
			Rationale:      "Failures corrupt data. Redlock cannot guarantee mutual exclusion under GC pauses and clock jumps.",
		}
	default:
		panic("unknown category")
	}
}

// Simulates Kleppmann's NTP Jump scenario on Redlock
type NodeWithNTP struct {
	ID        int
	ClockSkew time.Duration
	Expiry    time.Time
	Key       string
}

func main() {
	fmt.Println("=== 1. Martin Kleppmann's Taxonomy of Distributed Locks ===")
	d1 := EvaluateLockingStrategy(CategoryEfficiency)
	fmt.Printf("[%s]\nRecommended: %s\nRationale: %s\n\n", d1.Category, d1.System, d1.Rationale)

	d2 := EvaluateLockingStrategy(CategoryCorrectness)
	fmt.Printf("[%s]\nRecommended: %s\nRequires Fencing: %t\nRationale: %s\n\n",
		d2.Category, d2.System, d2.RequiresTokens, d2.Rationale)

	fmt.Println("=== 2. Kleppmann's NTP Jump Counter-Example Simulation ===")
	// Node 1 had key expiring at +10s
	node := &NodeWithNTP{ID: 1, Expiry: time.Now().Add(10 * time.Second), Key: "lock:critical"}

	fmt.Println("Client A holds lock on Node 1 (Expires in 10s).")
	// System clock jumps forward by 11 seconds (bad NTP sync)
	fmt.Println("⚠️ NTP administrator adjusts clock: +11 seconds jump forward!")
	node.ClockSkew = 11 * time.Second
	currentTimeOnNode := time.Now().Add(node.ClockSkew)

	if currentTimeOnNode.After(node.Expiry) {
		fmt.Println("💥 Node 1 prematurely evicts lock due to NTP time step!")
		fmt.Println("Client B now acquires the same lock while Client A is still running!")
		fmt.Println("Safety is broken. Redlock cannot prevent this without physical synchronized clocks (TrueTime).")
	}
}
```

## Под капотом

Сравнение моделей времени:
- **Синхронная модель (Synchronous)**: задержки сообщений и дрейф часов строго ограничены известной константой. В ней Redlock был бы корректен.
- **Асинхронная модель (Asynchronous)**: реальный интернет и облака (AWS, GCP, Bare-metal). Пакеты могут задерживаться на минуты, потоки ОС могут замораживаться на любое время. В асинхронной модели распределенный консенсус не может опираться на физические часы (теорема FLP).
Google решает эту проблему в Spanner с помощью TrueTime API (атомные часы + GPS в каждом ЦОД), гарантируя границы погрешности \(\epsilon \le 7\text{ мс}\). В обычных серверах таких гарантий нет.

## Подводные камни

- **Заблуждение, что Redlock заменяет транзакции**: Redlock не дает сериализуемости на уровне хранилища данных.
- **Использование Redlock в критическом финтехе без проверки токенов**: Прямой путь к финансовым потерям при сетевых аномалиях.

## На собеседовании

В Яндекс и Авито часто задают классический вопрос: *«Почему для обеспечения строгой корректности распределенной блокировки недостаточно одного лишь кворума из 5 нод Redis (Redlock)?»*
**Ответ**: Потому что кворум узлов Redis подтверждает лишь то, что в момент времени \(T\) большинство узлов согласились записать ключ. Но Redis не контролирует то, что происходит с клиентом дальше! Если клиент после получения кворума завис на 15 секунд (пауза GC, swap, задержка гипервизора), срок аренды на узлах истечет, и другой клиент получит новый лок. Когда первый клиент очнется, он отправит запись в базу данных одновременно со вторым. Кворум Redis никак не защищает саму базу данных от коллизии без механизма Fencing Tokens.
