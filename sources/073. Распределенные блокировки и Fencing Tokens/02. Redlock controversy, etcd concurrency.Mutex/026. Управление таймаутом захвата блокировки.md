# Управление таймаутом захвата блокировки: предотвращение Deadlock при зависших процессах

## Условие

26. **Lock timeout**: Всегда устанавливайте timeout на lock acquisition. Иначе deadlock при hung process. Напишите функцию захвата с контекстом и дедлайном.

### Исходная формулировка

**Lock timeout**: Всегда устанавливайте timeout на lock acquisition. Иначе deadlock при hung process.

## Теория

Правило устойчивости распределенных систем:
**Ни один сетевой вызов (включая попытку захвата блокировки) не имеет права выполняться без явного таймаута (Deadline)!**

Что происходит при попытке захвата блокировки без таймаута (`Lock(context.Background())`):
1. Сервис \(A\) держит ресурс и завис (или выполняет долгую операцию).
2. Сервисы \(B, C, D \dots\) вызывают `Lock` в бесконечном цикле ожидания.
3. В каждом входящем HTTP-запросе создается новая горутина, которая блокируется на мьютексе.
4. За 2 минуты в Go-процессе накапливается 50 000 заблокированных горутин.
5. Память исчерпывается (Goroutine Leak), планировщик Go деградирует, срабатывает OOM Killer.
6. **Каскадный сбой (Cascading Failure)** по всему кластеру.

Использование `context.WithTimeout` гарантирует быстрое завершение с ошибкой `context.DeadlineExceeded`, возврат HTTP 503 / 429 клиенту и сохранение стабильности системы.

## Решение по шагам

1. Создайте клиент мьютекса с поддержкой `LockWithTimeout(ctx, timeout)`.
2. Смоделируйте случай, когда ресурс занят другим процессом.
3. Установите таймаут ожидания 100 мс.
4. Продемонстрируйте корректный выход по дедлайну с возвратом `ErrAcquisitionTimeout`.
5. Убедитесь, что горутины ожидания не утекают в память.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrAcquisitionTimeout = errors.New("lock acquisition timeout: resource is busy")
)

type ResourceGate struct {
	mu     sync.Mutex
	holder string
}

func (g *ResourceGate) TryAcquire(worker string) bool {
	g.mu.Lock()
	defer g.mu.Unlock()
	if g.holder != "" {
		return false
	}
	g.holder = worker
	return true
}

func (g *ResourceGate) Release(worker string) {
	g.mu.Lock()
	defer g.mu.Unlock()
	if g.holder == worker {
		g.holder = ""
	}
}

func LockWithTimeout(parentCtx context.Context, gate *ResourceGate, worker string, timeout time.Duration) error {
	ctx, cancel := context.WithTimeout(parentCtx, timeout)
	defer cancel()

	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	for {
		if gate.TryAcquire(worker) {
			fmt.Printf("✅ [%s] Lock acquired successfully!\n", worker)
			return nil
		}

		select {
		case <-ctx.Done():
			return fmt.Errorf("%w after %v for worker '%s'", ErrAcquisitionTimeout, timeout, worker)
		case <-ticker.C:
			// Retry after backoff interval
		}
	}
}

func main() {
	gate := &ResourceGate{}

	// 1. Worker A acquires and holds lock for 500ms
	gate.TryAcquire("Worker-A")
	fmt.Println("[Init] Worker-A holds the lock for 500ms.")

	// 2. Worker B attempts to acquire with short 100ms timeout
	fmt.Println("\nWorker-B attempting to acquire lock with 100ms timeout...")
	start := time.Now()
	err := LockWithTimeout(context.Background(), gate, "Worker-B", 100*time.Millisecond)
	elapsed := time.Since(start)

	if errors.Is(err, ErrAcquisitionTimeout) {
		fmt.Printf("🛡️ Worker-B safely timed out after %v: %v\n", elapsed, err)
		fmt.Println("No goroutine leaks, service remains responsive and fast-fails!")
	}
}
```

ℹ️ Безопасный захват блокировки с ограничением времени ожидания через context.WithTimeout

## Под капотом

Паттерн Fast-Fail в микросервисах:
В микросервисной архитектуре быстрый отказ (`Fail-Fast`) всегда предпочтительнее бесконечного ожидания. Если сервис вернет ошибку за 100 мс, клиентский шлюз (API Gateway) сможет перенаправить запрос на другую реплику, вернуть кешированный ответ или показать пользователю понятное сообщение «Сервис перегружен, повторите попытку» вместо бесконечно висящего спиннера в приложении.

## Подводные камни

- **Использование `time.After` внутри цикла ожидания**: Написание `select { case <-time.After(timeout): }` внутри цикла `for` создает новый таймер на каждой итерации! Они не очищаются сборщиком мусора до истечения своего срока, вызывая утечку памяти. В цикле всегда используйте `context.Done()` и единственный внешний таймер/дедлайн.
- **Слишком короткий таймаут при холодном старте**: Задание таймаута в 5 мс при задержке сети в 10 мс приведет к 100% сбоев.

## На собеседовании

В Т-Банке и Lamoda часто спрашивают: *«Какую ошибку чаще всего совершают разработчики при организации цикла ожидания блокировки с таймаутом в Go?»*
**Ответ**: Использование вызова `time.After(delay)` внутри тела цикла `for`. На каждой неудачной попытке аллоцируется объект `time.Timer` и канал. Если попыток сотни в секунду, эти таймеры висят в памяти рантайма до истечения своего срока, создавая колоссальный мусор в куче. Корректный паттерн: объявлять `time.NewTicker` до входа в цикл с обязательным `defer ticker.Stop()`, либо использовать контекст `ctx.Done()`.
