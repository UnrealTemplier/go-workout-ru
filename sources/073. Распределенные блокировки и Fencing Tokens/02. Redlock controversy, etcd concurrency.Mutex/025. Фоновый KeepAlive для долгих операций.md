# Фоновый KeepAlive для долгих операций: безопасное продление аренды через Ticker и context

## Условие

25. **Keepalive при длинной операции.**: Операция занимает 60 сек, lock TTL = 30 сек. Реализуйте горутину, которая каждые 10 сек продлевает lease (Redis `PEXPIRE` или etcd `KeepAlive`). При завершении операции — stop renew, release lock. Объясните, почему нельзя ставить TTL = 10 минут сразу.

### Исходная формулировка

**Keepalive при длинной операции.**: Операция занимает 60 сек, lock TTL = 30 сек. Реализуйте горутину, которая каждые 10 сек продлевает lease (Redis `PEXPIRE` или etcd `KeepAlive`). При завершении операции — stop renew, release lock. Объясните, почему `max_extension_count` защищает от infinite loop при hung process.

## Теория

Архитектурный шаблон продления аренды для тяжелых фоновых задач:

Почему нельзя сразу поставить большой TTL (например, \(TTL = 10\text{ минут}\)):
Если процесс упадет на 5-й секунде выполнения из-за Out-Of-Memory (OOM) или Kernel Panic:
- Ресурс останется заблокированным в координаторе на оставшиеся **9 минут и 55 секунд**!
- Все остальные сервисы и пользователи будут получать отказ в обслуживании на протяжении 10 минут (катастрофический MTTR).

Корректное решение — **короткий TTL + частый динамический KeepAlive**:
- Базовый \(TTL = 30\text{ с}\).
- Фоновая горутина с `time.NewTicker(10 * time.Second)` продлевает аренду каждые 10 секунд.
- При штатной работе задача выполняется сколь угодно долго (хоть 2 часа).
- При аварийном падении процесса горутина погибает вместе с процессом, и блокировка автоматически сбрасывается максимум через 30 секунд.

## Решение по шагам

1. Создайте класс менеджера долгоживущих задач `LongTaskLockRunner`.
2. Реализуйте запуск фонового воркера продления с частотой \(\text{TTL}/3\).
3. Организуйте передачу `context.WithCancel` для детерминированной остановки продления.
4. Смоделируйте выполнение задачи длительностью 600 мс при базовом TTL 300 мс с 3 успешными продлениями.
5. Проверьте мгновенную остановку таймера и корректное снятие блокировки по завершении функции.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type LeaseCoordinator struct {
	mu     sync.Mutex
	key    string
	holder string
	exp    time.Time
}

func (c *LeaseCoordinator) Acquire(key, holder string, ttl time.Duration) bool {
	c.mu.Lock()
	defer c.mu.Unlock()
	if time.Now().Before(c.exp) {
		return false
	}
	c.key = key
	c.holder = holder
	c.exp = time.Now().Add(ttl)
	return true
}

func (c *LeaseCoordinator) Extend(key, holder string, ttl time.Duration) bool {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.key == key && c.holder == holder {
		c.exp = time.Now().Add(ttl)
		return true
	}
	return false
}

func (c *LeaseCoordinator) Release(key, holder string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.key == key && c.holder == holder {
		c.exp = time.Time{}
		c.holder = ""
	}
}

func RunWithDynamicKeepAlive(
	ctx context.Context,
	coord *LeaseCoordinator,
	resource, workerID string,
	ttl time.Duration,
	taskFn func() error,
) error {
	// 1. Initial Acquire
	if !coord.Acquire(resource, workerID, ttl) {
		return fmt.Errorf("failed to acquire lock '%s'", resource)
	}

	keepAliveCtx, stopKeepAlive := context.WithCancel(ctx)
	var wg sync.WaitGroup
	wg.Add(1)

	// 2. Background Heartbeat Goroutine
	go func() {
		defer wg.Done()
		renewInterval := ttl / 3
		ticker := time.NewTicker(renewInterval)
		defer ticker.Stop()

		for {
			select {
			case <-keepAliveCtx.Done():
				return
			case <-ticker.C:
				ok := coord.Extend(resource, workerID, ttl)
				if ok {
					fmt.Printf("[KeepAlive 💓] Extended lease for '%s' by %v\n", resource, ttl)
				} else {
					fmt.Printf("[KeepAlive ⚠️] Failed to extend lease for '%s'!\n", resource)
					return
				}
			}
		}
	}()

	// 3. Execute business logic
	taskErr := taskFn()

	// 4. Stop KeepAlive and Release Lock cleanly
	stopKeepAlive()
	wg.Wait()
	coord.Release(resource, workerID)
	fmt.Printf("[Runner] Task finished. Lock '%s' released cleanly.\n", resource)

	return taskErr
}

func main() {
	coord := &LeaseCoordinator{}
	ctx := context.Background()

	// Task takes 500ms, while lock TTL is only 200ms!
	err := RunWithDynamicKeepAlive(ctx, coord, "job:video:render", "worker-1", 200*time.Millisecond, func() error {
		fmt.Println("--- Long-running video render started (500ms) ---")
		time.Sleep(500 * time.Millisecond) // Exceeds 200ms TTL, kept alive dynamically!
		fmt.Println("--- Video render completed successfully! ---")
		return nil
	})

	if err != nil {
		panic(err)
	}
}
```

ℹ️ Паттерн безопасного исполнения долгих задач с динамическим продлением аренды

## Под капотом

Синхронизация горутин при завершении задачи:
В коде используется `wg.Wait()` после `stopKeepAlive()`.
Это гарантирует, что горутина продления **полностью остановила свои таймеры и сетевые запросы ДО того**, как вызывается метод `Release()`. Иначе возможна редкая гонка: поток освобождения отправляет `DEL`, а параллельно летящий запоздалый запрос `EXPIRE` от горутины KeepAlive пересоздает ключ в Redis!

## Подводные камни

- **Забытый `defer ticker.Stop()`**: Утечка системных таймеров в Go рантайме.
- **Отсутствие проверки результата `Extend()`**: Если продление вернуло `false` (лок перехвачен), задача обязана немедленно отменить свой контекст и прекратить запись.

## На собеседовании

В Ozon и Авито часто спрашивают: *«Как быть, если операция в `taskFn()` зависла в бесконечном цикле или дедлоке? Будет ли KeepAlive продлевать лок вечно?»*
**Ответ**: Да, наивный KeepAlive будет продлевать аренду бесконечно. Чтобы исключить «вечные зависания», на задачу накладывают **глобальный максимальный дедлайн (Hard Deadline)** через `context.WithTimeout(ctx, 10*time.Minute)`. Если задача превысила максимальный лимит, контекст отменяется, KeepAlive прекращается, и сервис аварийно завершает обработчик.
