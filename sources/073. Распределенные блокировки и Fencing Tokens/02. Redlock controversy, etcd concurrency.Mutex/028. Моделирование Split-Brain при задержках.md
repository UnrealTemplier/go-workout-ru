### Исходная формулировка

**Проблема Delay (GC Pause, Network Lag).**: Реализуйте симуляцию: узел захватил lock (TTL=5с), затем GC pause 10 сек (или `time.Sleep`). Lease истекает, другой узел захватывает lock. Первый узел просыпается и продолжает работу в критической секции. Покажите, что **два узла одновременно владеют lock**.

## Теория

Практическая лабораторная работа по проверке феномена асинхронного Split-Brain:

Анатомия уязвимости:
1. Система опирается на распределенный мьютекс с таймаутом \(TTL = 100\text{ мс}\).
2. Инстанс \(A\) захватывает лок и начинает операцию обновления профиля клиента.
3. Инстанс \(A\) «зависает» на \(250\text{ мс}\) (симулируя GC Pause, Stop-The-World, дисковый свопинг или сетевой lag).
4. Тайм-аут аренды \(100\text{ мс}\) истекает в координаторе.
5. Инстанс \(B\) видит, что лок свободен, захватывает его и выполняет операцию «Блокировка аккаунта мошенника» со статусом `BLOCKED`.
6. Инстанс \(A\) «отвисает». Процесс не имеет встроенного чувства прошедшего времени!
7. Инстанс \(A\) отправляет свой запоздалый SQL-запрос `UPDATE users SET status = 'ACTIVE'`.
8. **Катастрофа**: Заблокированный мошенник снова стал активным!

## Решение по шагам

1. Создайте модель базы данных учетных записей `UserAccountStorage`.
2. Запустите Воркера \(A\), устанавливающего статус `ACTIVE`.
3. Внедрите задержку 200 мс в критическую секцию Воркера \(A\).
4. Запустите Воркера \(B\), выставляющего статус `FRAUD_BLOCKED` после истечения 100 мс TTL.
5. Зафиксируйте перезапись критического статуса зомби-воркером \(A\) и покажите необходимость Fencing Tokens.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type UserProfile struct {
	UserID    string
	Status    string
	UpdatedAt time.Time
	UpdatedBy string
}

type UserDatabase struct {
	mu      sync.Mutex
	profile UserProfile
}

func (db *UserDatabase) UpdateStatus(status, author string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.profile.Status = status
	db.profile.UpdatedAt = time.Now()
	db.profile.UpdatedBy = author
	fmt.Printf("[DB COMMIT] User %s status set to '%s' by %s at %v\n",
		db.profile.UserID, status, author, db.profile.UpdatedAt.Format("15:04:05.000"))
}

type ExpiringLockServer struct {
	mu     sync.Mutex
	holder string
	exp    time.Time
}

func (s *ExpiringLockServer) Acquire(worker string, ttl time.Duration) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	now := time.Now()
	if now.Before(s.exp) {
		return false
	}
	s.holder = worker
	s.exp = now.Add(ttl)
	return true
}

func main() {
	db := &UserDatabase{profile: UserProfile{UserID: "user-404", Status: "PENDING"}}
	lockServer := &ExpiringLockServer{}
	var wg sync.WaitGroup

	fmt.Println("=== Lab: Simulating GC Freeze & Data Inconsistency ===")

	// 1. Worker A acquires lock with 100ms TTL
	lockServer.Acquire("Worker-A", 100*time.Millisecond)
	fmt.Println("[Lock Server] Worker-A granted lock for 100ms.")

	// Worker A enters critical section and freezes
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("[Worker-A] ❄️ Freezing: Simulating 250ms GC Pause...")
		time.Sleep(250 * time.Millisecond) // Freeze exceeds 100ms TTL!

		// Wakes up and blindly executes DB write
		fmt.Println("[Worker-A] ☀️ Woke up! Blindly writing: Status = 'ACTIVE'...")
		db.UpdateStatus("ACTIVE", "Worker-A")
	}()

	// 2. While Worker-A sleeps, TTL expires at 100ms. Worker B steps in at 120ms
	time.Sleep(120 * time.Millisecond)
	fmt.Println("\n[Lock Server] Lock TTL expired! Resource is free.")
	if lockServer.Acquire("Security-Worker-B", 200*time.Millisecond) {
		fmt.Println("[Security-Worker-B] Legitimate lock acquired. Flagging fraud!")
		db.UpdateStatus("FRAUD_BLOCKED", "Security-Worker-B")
	}

	wg.Wait()

	fmt.Println("\n=== FINAL DATABASE STATE AUDIT ===")
	fmt.Printf("Current User Status: '%s' (Last Updated By: %s)\n",
		db.profile.Status, db.profile.UpdatedBy)

	if db.profile.Status == "ACTIVE" && db.profile.UpdatedBy == "Worker-A" {
		fmt.Println("🚨 CATASTROPHIC FAILURE: Zombie Worker-A overwrote critical security decision 'FRAUD_BLOCKED'!")
		fmt.Println("Proof: Distributed Locks WITHOUT Fencing Tokens CANNOT guarantee data safety!")
	}
}
```

## Под капотом

Почему ОС не предупреждает процесс:
Операционная система управляет виртуальной памятью и потоками ядра. Когда поток вытесняется планировщиком ОС или рантайм Go выполняет сканирование стека для GC, процесс полностью пассивен. Никаких прерываний или уведомлений «вы спали 15 секунд» процессу не посылается. Локальный вызов `time.Now()` покажет новое время, но если код не сверяет время перед каждым низкоуровневым системным вызовом сокета, предотвратить запись невозможно.

## Подводные камни

- **Иллюзия, что Go не подвержен GC-паузам**: Хотя современный Go GC выполняет фазу разметки конкурентно с паузами STW \(< 1\text{ мс}\), при нехватке памяти (Memory Pressure) или вытеснении гипервизором облака задержки могут составлять секунды.
- **Отсутствие транзакционной изоляции в БД**: Полагаться только на лок без защиты хранилища.

## На собеседовании

В Яндекс Облаке и Авито часто спрашивают: *«Как физически доказать руководству или заказчику, что проект с распределенными мьютексами в Redis уязвим к порче данных?»*
**Ответ**: Написать интеграционный тест с инъекцией искусственной задержки (`SIGSTOP` и `SIGCONT` через Linux сигналы или Chaos Mesh). Процесс-1 берет лок, получает `SIGSTOP`, спит время больше TTL. Процесс-2 берет лок и пишет версию V2. Процесс-1 получает `SIGCONT`, просыпается и перезаписывает версию V1. Это наглядно демонстрирует неизбежность Split-Brain в асинхронных сетях без Fencing Tokens.
