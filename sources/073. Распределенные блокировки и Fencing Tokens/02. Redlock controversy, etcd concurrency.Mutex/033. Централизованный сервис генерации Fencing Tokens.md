# Централизованный сервис генерации Fencing Tokens: Sequence в PostgreSQL и MVCC ревизии в etcd

## Условие

33. **Fencing Token: Monotonic Counter.**: Реализуйте центральный сервис (etcd или PostgreSQL sequence), который выдаёт monotonic token при каждом захвате lock. Процесс получает token=42, выполняет `UPDATE accounts SET balance = 100, token = 42 WHERE token < 42`.

### Исходная формулировка

**Fencing Token: Monotonic Counter.**: Реализуйте центральный сервис (etcd или PostgreSQL sequence), который выдаёт monotonic token при каждом захвате lock. Процесс получает token=42, выполняет `UPDATE accounts SET balance = 100, token = 42 WHERE token < 42`. Объясните, как storage отклоняет stale операции (token < current).

## Теория

Централизованная генерация монотонных токенов ограждения:

Источники строгой монотонности в распределенных системах:
1. **PostgreSQL Sequence (`nextval('fencing_seq')`)**:
   - Быстрый атомарный генератор 64-битных чисел.
   - Гарантирует уникальность и строгое возрастание даже при откатах транзакций (`nextval` не откатывается обратно).
2. **etcd MVCC Revision (`Header.Revision`)**:
   - Каждая транзакция `clientv3.Txn` в etcd инкрементирует глобальную ревизию кластера.
   - Ревизия привязывается к коммиту в Raft-лог и является абсолютно надежным токеном.

Применение в целевой базе данных:
```sql
UPDATE account_balances
SET balance = balance - 100.0,
    last_fencing_token = 42
WHERE account_id = 'acc-1'
  AND last_fencing_token < 42;
```
Если база возвращает `RowsAffected == 0`, транзакция отклоняется как устаревшая (Stale Write Guard).

## Решение по шагам

1. Создайте класс `CentralTokenAuthority`, эмулирующий генератор монотонных последовательностей PostgreSQL Sequence.
2. Создайте класс целевой базы данных с защитой по `last_fencing_token`.
3. Смоделируйте получение токена 42 Воркером 1 и токена 43 Воркером 2.
4. Продемонстрируйте применение транзакции с токеном 43.
5. Продемонстрируйте отклонение запоздалой транзакции с токеном 42.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
)

var (
	ErrStaleWriteRejected = errors.New("optimistic lock failure: fencing token is stale")
)

// Central Monotonic Sequence Generator (Emulating Postgres nextval('seq'))
type CentralTokenAuthority struct {
	seq uint64
}

func (a *CentralTokenAuthority) NextToken() uint64 {
	return atomic.AddUint64(&a.seq, 1)
}

type AccountState struct {
	ID               string
	Balance          float64
	LastFencingToken uint64
}

type BankingDatabase struct {
	mu       sync.Mutex
	accounts map[string]AccountState
}

func (db *BankingDatabase) ExecuteFencedTransfer(accountID string, amount float64, token uint64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	acc, ok := db.accounts[accountID]
	if !ok {
		return errors.New("account not found")
	}

	// SQL check: WHERE last_fencing_token < token
	if token <= acc.LastFencingToken {
		return fmt.Errorf("%w: incoming token %d <= db token %d",
			ErrStaleWriteRejected, token, acc.LastFencingToken)
	}

	acc.Balance += amount
	acc.LastFencingToken = token
	db.accounts[accountID] = acc

	fmt.Printf("[DB Success] Account '%s' balance adjusted by %.2f (New Token: %d, Balance: %.2f)\n",
		accountID, amount, token, acc.Balance)
	return nil
}

func main() {
	authority := &CentralTokenAuthority{seq: 41} // starting from 41
	db := &BankingDatabase{
		accounts: map[string]AccountState{
			"acc-100": {ID: "acc-100", Balance: 1000.0, LastFencingToken: 41},
		},
	}

	// 1. Worker A acquires lock and fetches Token 42
	tokenA := authority.NextToken()
	fmt.Printf("[Worker A] Acquired lock. Fencing Token = %d\n", tokenA)

	// Worker A freezes...

	// 2. Worker B acquires lock and fetches Token 43
	tokenB := authority.NextToken()
	fmt.Printf("[Worker B] Acquired lock. Fencing Token = %d\n", tokenB)

	// 3. Worker B writes to DB first with Token 43
	if err := db.ExecuteFencedTransfer("acc-100", -200.0, tokenB); err != nil {
		panic(err)
	}

	// 4. Stale Worker A wakes up and attempts to apply write with Token 42
	fmt.Printf("\n[Worker A] Woke up. Attempting write with Stale Token %d...\n", tokenA)
	errA := db.ExecuteFencedTransfer("acc-100", -150.0, tokenA)
	if errA != nil {
		fmt.Printf("🛡️ Database guard protected state: %v\n", errA)
	}

	fmt.Printf("\nFinal Account Balance: %.2f руб (Highest Token: %d)\n",
		db.accounts["acc-100"].Balance, db.accounts["acc-100"].LastFencingToken)
}
```

ℹ️ Генерация монотонных токенов ограждения и их валидация на уровне SQL UPDATE

## Под капотом

Почему Sequence в PostgreSQL не создает узкого места:
В PostgreSQL вызов `nextval('seq')` использует неблокирующие атомарные инструкции процессора (`lock xadd`) и выделяет диапазоны номеров в буфере сессии (`CACHE`). Это позволяет генерировать более 500 000 монотонных токенов в секунду на одном ядре процессора, исключая задержки.

## Подводные камни

- **Попытка отката Sequence при ошибке транзакции**: Номера Sequence в SQL никогда не откатываются при `ROLLBACK`. Дырки в нумерации (например, 42, 45, 46) абсолютно нормальны — главное свойство Fencing Tokens — **строгая монотонность (\(T_{new} > T_{old}\))**, а не непрерывность.
- **Переполнение 32-битного счетчика**: Всегда используйте 64-битный `BIGINT` (`uint64`), чтобы исключить переполнение через 4 миллиарда операций.

## На собеседовании

В Яндекс Облаке и Т-Банке часто спрашивают: *«Обязаны ли Fencing Tokens следовать строго подряд (1, 2, 3...) или допускаются пропуски (1, 5, 10)?»*
**Ответ**: Пропуски абсолютно допустимы и никак не нарушают корректность! Единственное математическое требование токена ограждения — это **строго монотонный порядок (Strict Monotonicity)**: каждая новая блокировка обязана получать число, строго большее любого ранее выданного числа. Проверка в базе данных `WHERE last_fencing_token < incoming_token` корректно отсекает любые запоздалые операции независимо от размера шага инкремента.
