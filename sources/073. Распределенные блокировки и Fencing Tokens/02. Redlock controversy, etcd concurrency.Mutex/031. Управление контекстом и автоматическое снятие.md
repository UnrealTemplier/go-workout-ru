# Управление контекстом и автоматическое снятие: redsync.LockContext и graceful cancel

## Условие

31. **[Lock with Context]**: Используй `redsync.LockContext`. Если контекст отменяется (таймаут), блокировка должна автоматически сниматься или отменять попытку захвата. Реализуйте graceful cancellation.

### Исходная формулировка

**[Lock with Context]**: Используй `redsunc.LockContext`. Если контекст отменяется (таймаут), блокировка должна автоматически сниматься.

## Теория

Интеграция распределенных мьютексов со стандартным механизмом отмены Go (`context.Context`):

Два аспекта работы `LockContext(ctx)`:
1. **Отмена во время ожидания захвата (Acquisition Cancellation)**:
   - Если мьютекс занят, а клиент находится в цикле повторных попыток (Retry Loop), отмена `ctx.Done()` (например, HTTP-клиент закрыл вкладку браузера) обязана **мгновенно прервать цикл**, не совершая лишних сетевых запросов к Redis.
2. **Отмена во время удержания блокировки (Execution Cancellation)**:
   - Если контекст отменился в процессе исполнения критической секции (сработал таймаут операции), сервис обязан:
     1. Прервать выполнение бизнес-логики.
     2. Гарантированно освободить распределенный мьютекс через `Unlock()` в чистом контексте.
     3. Не оставлять зависших ключей в Redis до истечения TTL.

## Решение по шагам

1. Создайте класс `ContextAwareMutex` с поддержкой метода `LockContext(ctx)`.
2. Реализуйте немедленное прерывание ожидания при закрытии `ctx.Done()`.
3. Смоделируйте отмену родительского HTTP-запроса через `context.WithTimeout`.
4. Убедитесь, что отмененный запрос корректно возвращает `context.DeadlineExceeded`.
5. Продемонстрируйте чистое освобождение ресурсов через независимый `unlockCtx` в блоке `defer`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type ContextMutex struct {
	mu       sync.Mutex
	isLocked bool
	holder   string
}

func (m *ContextMutex) LockContext(ctx context.Context, clientID string, retryInterval time.Duration) error {
	ticker := time.NewTicker(retryInterval)
	defer ticker.Stop()

	for {
		m.mu.Lock()
		if !m.isLocked {
			m.isLocked = true
			m.holder = clientID
			m.mu.Unlock()
			fmt.Printf("[%s] Lock acquired successfully via context!\n", clientID)
			return nil
		}
		m.mu.Unlock()

		select {
		case <-ctx.Done():
			fmt.Printf("[%s] Lock acquisition aborted by context: %v\n", clientID, ctx.Err())
			return ctx.Err()
		case <-ticker.C:
			// Continue retrying
		}
	}
}

func (m *ContextMutex) Unlock(ctx context.Context, clientID string) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	if !m.isLocked || m.holder != clientID {
		return errors.New("cannot unlock: not holder or lock not held")
	}

	m.isLocked = false
	m.holder = ""
	fmt.Printf("[%s] Lock released cleanly via cleanup context.\n", clientID)
	return nil
}

func main() {
	mutex := &ContextMutex{}

	// 1. Initial lock taken by Background Worker
	_ = mutex.LockContext(context.Background(), "Worker-Legacy", 10*time.Millisecond)

	// 2. HTTP Request arrives with strict 150ms timeout
	httpCtx, httpCancel := context.WithTimeout(context.Background(), 150*time.Millisecond)
	defer httpCancel()

	fmt.Println("\nIncoming HTTP handler attempting to acquire busy lock...")
	err := mutex.LockContext(httpCtx, "HTTP-Handler-Pod-3", 30*time.Millisecond)
	if errors.Is(err, context.DeadlineExceeded) {
		fmt.Println("🛡️ Handler exited gracefully on deadline! Returning HTTP 504 Gateway Timeout.")
	}

	// 3. Worker-Legacy finishes and releases with fresh context
	cleanupCtx, cleanupCancel := context.WithTimeout(context.Background(), 1*time.Second)
	defer cleanupCancel()
	_ = mutex.Unlock(cleanupCtx, "Worker-Legacy")
}
```

ℹ️ Паттерн работы с распределенной блокировкой через context.Context с дедлайнами

## Под капотом

Скрытая ловушка отмены контекста в defer:
Если написать:
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
mutex.LockContext(ctx)
defer mutex.Unlock(ctx) // <-- ОШИБКА!
```
Если `ctx` отменится по таймауту 5 секунд, вызов `mutex.Unlock(ctx)` внутри `defer` **не сможет отправить сетевой запрос в Redis**, так как сетевой драйвер сразу проверит `ctx.Err() != nil` и упадет с ошибкой!
Поэтому операция `Unlock` в `defer` всегда должна принимать `context.Background()` или выделенный `cleanupCtx`.

## Подводные камни

- **Передача `nil` вместо контекста**: Вызывает панику рантайма `panic: nil Context`.
- **Игнорирование ошибок в `LockContext`**: Попытка выполнить критическую секцию после того, как `LockContext` вернул ошибку отмены.

## На собеседовании

В Т-Банке и Wildberries часто спрашивают: *«Почему в методе `Unlock` нельзя переиспользовать тот же `ctx`, что был передан в `LockContext`?»*
**Ответ**: Потому что контекст бизнес-операции может быть отменен по дедлайну прямо в середине выполнения критической секции. Если передать этот же протухший контекст в `Unlock`, сетевой клиент Redis или etcd откажется выполнять gRPC/TCP запрос и вернет `context deadline exceeded`. В результате блокировка останется «висеть» на сервере до естественного истечения TTL, блокируя другие процессы. Для `Unlock` в блоке `defer` всегда создается свежий контекст с коротким таймаутом (1–2 сек).
