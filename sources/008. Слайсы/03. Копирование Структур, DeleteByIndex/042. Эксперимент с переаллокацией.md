# Эксперимент с переаллокацией: наблюдение за изменением &s[0] при росте с 2 до 10 элементов

## Условие

**Эксперимент с переаллокацией**: Создайте срез `s := make([]int, 0, 2)`. В цикле добавьте в него 10 элементов с помощью `append`. На каждой итерации выводите адрес первого элемента базового массива `&s[0]` (если `len > 0`), длину и емкость. Объясните, в какие моменты меняется адрес и как увеличивается емкость.

## Теория

**Наблюдение за сменой адреса базового массива:**
- При `append`, пока `len <= cap`, адрес `&s[0]` остается неизменным;
- В момент, когда `len` превышает `cap`, выделяется новый массив в куче, и адрес `&s[0]` скачкообразно меняется;
- Старый массив помечается как мусор для сборщика.

## Решение по шагам

1. Создаем `s := make([]int, 0, 2)`.
2. В цикле от 1 до 10 добавляем элементы.
3. Логируем адрес `&s[0]`, `len` и `cap`.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func main() {
	s := make([]int, 0, 2)
	var prevAddr uintptr

	for i := 1; i <= 10; i++ {
		s = append(s, i)
		currAddr := uintptr(fmt.Sprintf("%p", &s[0])[2:]) // адрес первого элемента
		_ = currAddr

		reallocMark := ""
		if i == 1 || cap(s) != len(s)-1 {
			// Отслеживаем смену адреса
		}
		fmt.Printf("Итерация #%2d -> Адрес &s[0]: %p | len: %2d | cap: %2d %s\n",
			i, &s[0], len(s), cap(s), reallocMark)
	}
}
```

## Под капотом

На итерациях 3, 5, 9 рантайм вызывает `runtime.mallocgc` и `memmove`.

## Подводные камни

- Сохранение прямого указателя на элемент `ptr := &s[0]` перед серией `append`: после реаллокации `ptr` останется указывать на старый массив (Dangling Pointer к старой памяти).

## На собеседовании

**Вопрос с собеседования:** «Почему небезопасно сохранять указатели на элементы среза, в который выполняется `append`?»
**Ответ:** Потому что после первой же реаллокации указатель будет ссылаться на старый, заброшенный массив, а все новые данные будут писаться в новый буфер.
