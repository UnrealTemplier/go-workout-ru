# Нагрузочное тестирование HTTP API: замер перцентилей Latency p50/p95/p99 через hey и vegeta

## Условие

Используйте `vegeta` или `hey` для нагрузочного тестирования вашего HTTP API.

## Теория

Метрики нагрузочного тестирования HighLoad систем:
- Среднее время ответа (Average Latency) обманчиво: 99 запросов могут выполниться за 1 мс, а 1 запрос зависнуть на 10 секунд (среднее будет красивым ~100 мс).
- В Production SLA оценивается по перцентилям:
  - **P50 (Медиана):** 50% пользователей получили ответ быстрее этого времени.
  - **P95:** отсекает медленные запросы.
  - **P99:** время ответа для 1% самых медленных запросов (всплески GC, сетевые ретраи, блокировки диска).
- Утилиты `hey` и `vegeta` генерируют постоянный профиль нагрузки (Constant Rate RPS).

## Решение по шагам

1. Соберите и запустите HTTP-сервер.
2. Подайте нагрузку 1000 RPS утилитой `vegeta` на 10 секунд.
3. Сгенерируйте отчет распределения перцентилей.
4. Проанализируйте задержки P99.

## Под капотом

`vegeta` использует модель Closed-Loop / Open-Loop генерирования трафика с защитой от скоординированного пропуска (Coordinated Omission), выдавая истинные значения Latency даже при зависании сервера.

## Подводные камни

Запускать генератор нагрузки на той же машине, где работает сервер: `vegeta` займет 8 ядер процессора, исказив метрики сервера из-за конкуренции за ресурсы CPU.

## На собеседовании

**Вопрос с собеседования:** «Что такое проблема Coordinated Omission при нагрузочном тестировании?»
**Ответ:** Если тестирующий инструмент отправляет следующий запрос только после получения ответа на предыдущий, то во время секундного зависания сервера генератор тоже замирает и не посылает запросы. В итоге в отчет не попадают тысячи запросов, которые должны были получить таймаут, и статистика задержек оказывается заниженной в разы.
