# Тестирование Retry-политики с экспоненциальным backoff: проверка попыток без реального ожидания

## Условие

Напиши тест для **"retry with exponential backoff"**: функция пытается 3 раза с задержками. Используй mock clock, чтобы "промотать" время без реального `Sleep`. Проверь количество попыток.

## Теория

Тестирование повторных попыток (Exponential Backoff Testing):
- При сбоях сети сервис повторяет запрос с возрастающими задержками:
  - Попытка 1: задержка 100 мс.
  - Попытка 2: задержка 200 мс.
  - Попытка 3: задержка 400 мс.
- Суммарное время ожидания составило бы 700 мс.
- Замена функции задержки на мок `sleepFunc func(time.Duration)` позволяет выполнить тест за **0 миллисекунд**, проверив корректность расчета интервалов backoff.

## Решение по шагам

1. Напишите `ExecuteWithBackoff` с внедрением функции сна.
2. В тесте запишите переданные задержки в срез.
3. Проверьте число попыток ровно 3.
4. Проверьте формулу экспоненциального роста задержек.

## Код решения

**`retry_backoff.go`**

```go
package main

import (
	"errors"
	"time"
)

type SleeperFunc func(d time.Duration)

func ExecuteWithExponentialBackoff(attempts int, initialBackoff time.Duration, sleep SleeperFunc, op func() error) error {
	backoff := initialBackoff
	var lastErr error

	for i := 0; i < attempts; i++ {
		err := op()
		if err == nil {
			return nil // Успех
		}
		lastErr = err

		if i < attempts-1 {
			sleep(backoff)
			backoff *= 2 // Экспоненциальное удваивание
		}
	}
	return lastErr
}
```

ℹ️ Retry с экспоненциальным backoff и DI функции сна

**`retry_backoff_test.go`**

```go
package main

import (
	"errors"
	"testing"
	"time"
)

func TestExponentialBackoffRetryMocked(t *testing.T) {
	recordedSleeps := []time.Duration{}
	mockSleep := func(d time.Duration) {
		recordedSleeps = append(recordedSleeps, d) // Мгновенная фиксация без реального time.Sleep!
	}

	callCount := 0
	failingOp := func() error {
		callCount++
		return errors.New("temporary 503 gateway error")
	}

	start := time.Now()
	err := ExecuteWithExponentialBackoff(3, 100*time.Millisecond, mockSleep, failingOp)
	elapsed := time.Since(start)

	// Тест обязан завершиться за доли миллисекунды
	if elapsed > 20*time.Millisecond {
		t.Fatalf("Тест слишком медленный: %v", elapsed)
	}

	if err == nil {
		t.Fatal("Ожидалась ошибка после исчерпания попыток")
	}

	if callCount != 3 {
		t.Fatalf("callCount = %d; want 3", callCount)
	}

	// Проверяем точный экспоненциальный ряд задержек: 100 мс, затем 200 мс
	if len(recordedSleeps) != 2 {
		t.Fatalf("Число пауз = %d; want 2", len(recordedSleeps))
	}
	if recordedSleeps[0] != 100*time.Millisecond || recordedSleeps[1] != 200*time.Millisecond {
		t.Fatalf("Неверный ряд backoff: %v", recordedSleeps)
	}
}
```

## Под капотом

Тест проверяет математическую модель удваивания интервала (`100ms -> 200ms`) и количество вызовов `callCount = 3` за 0.00 секунд.

## Подводные камни

Делать retry без добавления случайного джиттера (Full Jitter): в продакшене одновременный retry тысяч клиентов по одинаковым интервалам приведет к шторму запросов (Thundering Herd Problem).

## На собеседовании

**Вопрос с собеседования:** «Что такое Full Jitter в алгоритмах Exponential Backoff (AWS/Google)?»
**Ответ:** Вместо фиксированной паузы \(T = 2^i \times \text{base}\) клиент выбирает случайную задержку из диапазона \([0, T]\). Это размазывает одновременные повторные запросы клиентов по времени, спасая упавшую базу данных от пиковых всплесков нагрузки.
