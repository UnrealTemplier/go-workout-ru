# Стресс-тестирование Worker Pool: гарантия однократной обработки Exactly-Once для N задач

## Условие

Протестируйте Worker Pool, отправив туда N задач и проверив, что все они были обработаны ровно один раз.

## Теория

Семантика Exactly-Once Processing в пуле воркеров:
- В распределенных системах и конкурентных пулах критично гарантировать, что:
  1. Ни одна задача не была потеряна (No Data Loss).
  2. Ни одна задача не была обработана дважды (No Duplicates).
- Тест проверяет инвариант через потокобезопасную карту или массив счетчиков вызовов.

## Решение по шагам

1. Создайте пул воркеров.
2. Отправьте \(N = 200\) уникальных ID задач.
3. Зафиксируйте обработку каждого ID в массиве счетчиков с мьютексом.
4. Убедитесь, что счетчик каждого задания строго равен 1.

## Код решения

**`exactly_once_pool_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

func TestWorkerPoolExactlyOnceExecution(t *testing.T) {
	const totalTasks = 200
	const numWorkers = 8

	tasks := make(chan int, totalTasks)

	var mu sync.Mutex
	executionCounts := make(map[int]int, totalTasks)

	var wg sync.WaitGroup
	wg.Add(numWorkers)

	// Запуск пула воркеров
	for w := 0; w < numWorkers; w++ {
		go func() {
			defer wg.Done()
			for taskID := range tasks {
				mu.Lock()
				executionCounts[taskID]++
				mu.Unlock()
			}
		}()
	}

	// Отправляем все 200 задач
	for i := 1; i <= totalTasks; i++ {
		tasks <- i
	}
	close(tasks)

	wg.Wait()

	// ВЕРИФИКАЦИЯ EXACTLY-ONCE:
	if len(executionCounts) != totalTasks {
		t.Fatalf("Обработано только %d уникальных задач из %d",
			len(executionCounts), totalTasks)
	}

	for id := 1; id <= totalTasks; id++ {
		count := executionCounts[id]
		if count != 1 {
			t.Fatalf("Задача ID %d обработана %d раз (ожидалось строго ровно 1 раз!)", id, count)
		}
	}

	t.Logf("Все %d задач успешно и ровно 1 раз обработаны пулом из %d воркеров",
		totalTasks, numWorkers)
}
```

## Под капотом

Канал в Go выступает в роли потокобезопасного распределителя задач: рантайм гарантирует, что каждое сообщение из очереди `hchan` будет выдано ровно одному получателю из очереди ожидания `hchan.recvq`.

## Подводные камни

Повторно открывать закрытый канал: канал закрывается отправителем один раз навсегда.

## На собеседовании

**Вопрос с собеседования:** «Почему в распределенных очередях (Kafka, RabbitMQ) тяжело гарантировать Exactly-Once?»
**Ответ:** Из-за сбоев сети подтверждение (ACK) может потеряться. Брокер решит, что воркер упал, и переотправит сообщение другому воркеру (At-Least-Once). Для достижения Exactly-Once в бизнес-логику встраивают проверку ключа идемпотентности (Idempotency Key) в БД.
