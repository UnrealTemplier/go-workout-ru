# Тестирование кэша с временем жизни (TTL): проверка Hit и Expiration через Mock Clock

## Условие

Напиши тест для **"cache with TTL"**: используй mock clock. Установи время T, положи значение в кеш с TTL=5 мин. "Промотай" время на 4 минуты — значение должно быть валидно. На 6 минутах — протухло.

### Исходная формулировка

---

## Теория

Тестирование инвалидации кэша по TTL (Time-To-Live):
- Кэш сохраняет объект со сроком действия: `expiresAt = now + ttl`.
- Проверка через Mock Clock:
  1. Время \(T\): сохранение ключа с `TTL = 5m`.
  2. Перемотка времени на \(+4m\): ключ обязан быть доступен (`ok == true`, Cache Hit).
  3. Перемотка времени еще на \(+2m\) (суммарно \(+6m\)): ключ обязан считаться протухшим (`ok == false`, Cache Miss).
- Тест выполняется за 0 наносекунд без зависаний на `time.Sleep(5 * time.Minute)`.

## Решение по шагам

1. Напишите `TTLCache` с зависимостью от часов.
2. Сохраните ключ с TTL 5 минут.
3. Проверьте валидность через 4 минуты.
4. Проверьте протухание через 6 минут.

## Код решения

**`ttl_cache.go`**

```go
package main

import (
	"sync"
	"time"
)

type CacheItem struct {
	value     string
	expiresAt time.Time
}

type TTLCache struct {
	mu      sync.Mutex
	nowFunc func() time.Time
	data    map[string]CacheItem
}

func NewTTLCache(nowFunc func() time.Time) *TTLCache {
	return &TTLCache{
		nowFunc: nowFunc,
		data:    make(map[string]CacheItem),
	}
}

func (c *TTLCache) Set(key, value string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[key] = CacheItem{
		value:     value,
		expiresAt: c.nowFunc().Add(ttl),
	}
}

func (c *TTLCache) Get(key string) (string, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()

	item, found := c.data[key]
	if !found {
		return "", false
	}

	// Проверка срока жизни
	if c.nowFunc().After(item.expiresAt) {
		delete(c.data, key) // Ленивое удаление
		return "", false
	}

	return item.value, true
}
```

ℹ️ Кэш с ленивой инвалидацией по TTL

**`ttl_cache_test.go`**

```go
package main

import (
	"testing"
	"time"
)

func TestTTLCacheExpirationWithMockClock(t *testing.T) {
	currentTime := time.Date(2026, time.September, 1, 12, 0, 0, 0, time.UTC)
	mockNow := func() time.Time {
		return currentTime
	}

	cache := NewTTLCache(mockNow)

	// Кладем ключ с TTL 5 минут
	cache.Set("session_token", "secret123", 5*time.Minute)

	// 1. Прокручиваем время на 4 минуты вперед -> ключ ДОЛЖЕН жить!
	currentTime = currentTime.Add(4 * time.Minute)
	val, ok := cache.Get("session_token")
	if !ok || val != "secret123" {
		t.Fatalf("Через 4 минуты ключ обязан быть валиден! got %q, %v", val, ok)
	}

	// 2. Прокручиваем время еще на 2 минуты вперед (суммарно 6 минут) -> ПРОТУХ!
	currentTime = currentTime.Add(2 * time.Minute)
	val, ok = cache.Get("session_token")
	if ok {
		t.Fatalf("Через 6 минут ключ обязан протухнуть! Получено: %q", val)
	}

	t.Log("Инвалидация TTL успешно протестирована за 0 миллисекунд")
}
```

## Под капотом

Ленивая инвалидация (Lazy Eviction) удаляет протухший ключ `delete(c.data, key)` в момент вызова `Get`, что экономит процессорное время на фоновых таймерах очистки.

## Подводные камни

Использовать только ленивую инвалидацию без фоновой очистки: если ключ записали и больше никогда не читали, он останется в памяти навсегда, вызвав утечку памяти. В продакшене добавляют периодический фоновый сборщик протухших ключей.

## На собеседовании

**Вопрос с собеседования:** «Как устроен алгоритм очистки ключей по TTL в Redis?»
**Ответ:** Redis сочетает два механизма: 1. **Пассивный (Lazy):** ключ проверяется и удаляется при попытке чтения `GET`. 2. **Активный (Active):** 10 раз в секунду фоновый процесс случайным образом выбирает 20 ключей с установленным TTL и удаляет протухшие, удерживая процент протухших ключей в памяти ниже 25%.
