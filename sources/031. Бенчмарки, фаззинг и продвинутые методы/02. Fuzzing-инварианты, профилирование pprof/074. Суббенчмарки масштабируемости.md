# Суббенчмарки масштабируемости: сопоставление режимов small и large в b.Run

## Условие

**[Суб-бенчмарки]**: Напиши бенчмарк, который использует `b.Run("small", func(b *testing.B){...})` и `b.Run("large", ...)` для тестирования функции на слайсах разной длины.

## Теория

Тестирование крайних диапазонов масштабируемости:
- Режимы `small` (10 элементов) и `large` (100 000 элементов) отражают два разных типа нагрузки:
  - `small`: алгоритм полностью помещается в быстрый кэш L1/Регистры процессора.
  - `large`: срез превышает размеры L3 кэша процессора, вызывая сброс кэш-линий и чтение из оперативной памяти RAM.
- Суббенчмарки `b.Run("small", ...)` и `b.Run("large", ...)` наглядно выявляют границу деградации кэш-локальности.

## Решение по шагам

1. Напишите функцию подсчета четных чисел.
2. Создайте бенчмарк с субтестами `"small"` и `"large"`.
3. Запустите замер с флагом `-benchmem`.
4. Сопоставьте пропускную способность.

## Код решения

**`small_large_bench_test.go`**

```go
package main

import "testing"

func CountEvens(nums []int) int {
	c := 0
	for _, v := range nums {
		if v%2 == 0 {
			c++
		}
	}
	return c
}

var sinkCountEvens int

func BenchmarkCountEvensScalability(b *testing.B) {
	b.Run("small", func(b *testing.B) {
		data := make([]int, 10)
		for i := range data {
			data[i] = i
		}
		b.ResetTimer()
		b.ReportAllocs()

		var res int
		for i := 0; i < b.N; i++ {
			res = CountEvens(data)
		}
		sinkCountEvens = res
	})

	b.Run("large", func(b *testing.B) {
		data := make([]int, 100000)
		for i := range data {
			data[i] = i
		}
		b.ResetTimer()
		b.ReportAllocs()

		var res int
		for i := 0; i < b.N; i++ {
			res = CountEvens(data)
		}
		sinkCountEvens = res
	})
}
```

ℹ️ Суббенчмарки для режимов small и large

**`Терминал`**

```bash
go test -bench=BenchmarkCountEvensScalability -run=^$
# Вывод:
# BenchmarkCountEvensScalability/small-16     284102910      4.12 ns/op     0 B/op   0 allocs/op
# BenchmarkCountEvensScalability/large-16         28410  42150.0 ns/op     0 B/op   0 allocs/op
# PASS
# ok      mymodule    2.412s
```

## Под капотом

В режиме `small` операция выполняется за 4.12 наносекунды (L1 Cache Hit), а в режиме `large` время растет строго линейно до 42 микросекунд без единой аллокации в куче.

## Подводные камни

Аллоцировать срез внутри цикла `for i := 0; i < b.N; i++`: в режиме `large` это вызовет выделение 800 КБ на каждой итерации, полностью забив память тестом.

## На собеседовании

**Вопрос с собеседования:** «Что такое Cache-Conscious Data Structures в Go и почему срез эффективнее связного списка?»
**Ответ:** Срез в Go расположен в непрерывном блоке оперативной памяти. При чтении элемента процессор автоматически загружает в кэш L1/L2 всю кэш-линию целиком (64 байта — сразу 8 элементов `int64`), задействуя аппаратный Hardware Prefetcher. Связный список распределен по куче хаотично, порождая постоянные промахи кэша (Cache Misses).
