# Разделение тестов по тегам сборки: директива //go:build integration и флаг -tags

## Условие

**Разделение тестов по тегам (Build Tags)**: Напишите медленный интеграционный тест, который не должен запускаться при обычном вызове `go test` (чтобы не замедлять CI). Добавьте в самое начало файла теста тег сборки (например, `//go:build integration` [346]). Проверьте, что обычный вызов `go test` игнорирует этот файл. Запустите только интеграционные тесты с помощью `go test -tags=integration` [346].

## Теория

Сегрегация Unit и Integration тестов через Build Tags:
- Юнит-тесты обязаны выполняться за миллисекунды (Fast Feedback Loop).
- Интеграционные тесты поднимают Docker-контейнеры, ходят в реальные базы данных и выполняются 30–60 секунд.
- Директива сборки Go 1.17+: `//go:build integration` в первой строке файла.
- Поведение компилятора:
  - `go test ./...`: полностью пропускает все файлы с тегом `integration`.
  - `go test -tags=integration ./...`: компилирует и запускает интеграционные тесты.

## Решение по шагам

1. Создайте файл с тегом `//go:build integration`.
2. Напишите тяжелый интеграционный тест с имитацией паузы 50 мс.
3. Запустите `go test`: убедитесь в пропуске файла.
4. Запустите `go test -tags=integration`: убедитесь в исполнении теста.

## Код решения

**`heavy_integration_test.go`**

```go
//go:build integration

package main

import (
	"testing"
	"time"
)

func TestPostgresClusterIntegration(t *testing.T) {
	t.Log("Запуск тяжелого интеграционного теста с подключением к внешнему сервису...")
	time.Sleep(50 * time.Millisecond) // Имитация обращения к БД
	t.Log("Интеграционный тест успешно завершен")
}
```

ℹ️ Интеграционный тест с тегом сборки //go:build integration

**`Терминал`**

```bash
# 1. Обычный запуск (игнорирует интеграционный тест):
go test -v heavy_integration_test.go
# Вывод:
# ?   	command-line-arguments	[no test files]

# 2. Запуск с явным указанием тега:
go test -v -tags=integration heavy_integration_test.go
# Вывод:
# === RUN   TestPostgresClusterIntegration
#     heavy_integration_test.go:11: Запуск тяжелого интеграционного теста...
#     heavy_integration_test.go:13: Интеграционный тест успешно завершен
# --- PASS: TestPostgresClusterIntegration (0.05s)
# PASS
```

## Под капотом

Компилятор Go парсит комментарий `//go:build` на стадии лексического анализа AST. Если тег не указан в `-tags`, компилятор даже не парсит синтаксис файла, исключая его из сборки целиком.

## Подводные камни

Использовать устаревший синтаксис `// +build integration` без `//go:build`: компилятор Go 1.17+ требует современного стандарта `//go:build`.

## На собеседовании

**Вопрос с собеседования:** «Как с помощью build tags запускать тесты только на определенной операционной системе (например, только на Linux)?»
**Ответ:** Использовать встроенные теги платформы: `//go:build linux`. Также поддерживаются логические операторы: `//go:build linux && integration` (тест запускается только на Linux и только при передаче флага `-tags=integration`).
