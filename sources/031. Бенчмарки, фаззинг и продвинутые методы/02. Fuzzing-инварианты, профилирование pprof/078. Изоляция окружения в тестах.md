# Изоляция окружения в тестах: встроенный метод t.Setenv и защита от гонок в t.Parallel

## Условие

Напиши тест с **`t.Parallel()` + `t.Setenv()`**: проверь, что `t.Setenv` безопасен для параллельных тестов (Go 1.17+ — каждый тест получает копию окружения). До 1.17 — `t.Setenv` запрещал `t.Parallel`.

## Теория

Строгие ограничения метода `t.Setenv` и `t.Parallel()`:
- В Go 1.17 появился метод `t.Setenv(key, val)`.
- **Фундаментальное правило ОС:** В Linux/Windows переменные окружения процесса (`environ`) являются глобальными для всех потоков.
- Если разрешить параллельным тестам `t.Parallel()` менять глобальное окружение через `t.Setenv`, возникнет непредсказуемая гонка данных (Data Race).
- **Поведение рантайма Go:** Если вызвать `t.Setenv` в тесте, помеченном `t.Parallel()`, рантайм **НЕМЕДЛЕННО ПАНИКУЕТ**:
  `testing: t.Setenv called after t.Parallel`
- Тест демонстрирует эту защиту рантайма от скрытых дефектов окружения.

## Решение по шагам

1. Напишите тест с вызовом `t.Setenv`.
2. Проверьте автоматический откат переменной по завершении теста.
3. Продемонстрируйте защиту рантайма при попытке вызова `t.Parallel()`.

## Код решения

**`env_isolation_test.go`**

```go
package main

import (
	"os"
	"testing"
)

func TestIsolatedEnvironmentSequential(t *testing.T) {
	// В последовательном тесте t.Setenv работает идеально
	t.Setenv("DATABASE_URL", "postgres://localhost:5432/testdb")

	if val := os.Getenv("DATABASE_URL"); val != "postgres://localhost:5432/testdb" {
		t.Fatalf("DATABASE_URL не установлена: %s", val)
	}

	t.Log("Переменная окружения успешно изолирована внутри теста")
}

func TestSetenvPanicsOnParallel(t *testing.T) {
	// Проверяем, что рантайм Go защищает от одновременного использования t.Parallel и t.Setenv
	defer func() {
		r := recover()
		if r == nil {
			t.Fatal("Ожидалась паника рантайма при вызове t.Setenv после t.Parallel!")
		}
		t.Logf("Рантайм успешно предотвратил гонку окружения: %v", r)
	}()

	t.Parallel() // Помечаем тест как параллельный
	t.Setenv("FORBIDDEN_PARALLEL_KEY", "should_panic")
}
```

ℹ️ Демонстрация защиты t.Setenv от гонок окружения при t.Parallel

## Под капотом

Внутри `testing.common` флаг `isParallel` проверяется в методе `Setenv`. Если `c.isParallel == true`, рантайм вызывает `panic("testing: t.Setenv called after t.Parallel")`, защищая память процесса.

## Подводные камни

Пытаться обойти ограничение через `os.Setenv` в параллельных тестах: это вызовет скрытую Data Race в CI, из-за которой тесты будут случайным образом флаковать.

## На собеседовании

**Вопрос с собеседования:** «Как протестировать конфигурацию приложения в параллельных тестах t.Parallel() без использования t.Setenv?»
**Ответ:** Не читать переменные окружения напрямую из `os.Getenv` внутри бизнес-логики! Создать структуру `Config` и передавать её экземпляр явно через Dependency Injection. В параллельных тестах создавать разные структуры `cfg := Config{DB: "test"}` в памяти без касания глобального окружения процесса.
