# Ограничение времени фаззинга: флаги -fuzztime=30s и -fuzztime=10000x

## Условие

Запустите fuzz-тест с ограничением по времени: `go test -fuzz=FuzzParseJSON -fuzztime=30s`.

## Теория

Управление длительностью фаззинг-сессий (`-fuzztime`):
- По умолчанию в Go запуск `go test -fuzz=...` запускается в бесконечном режиме (Infinite Fuzzing).
- Для автоматизации в CI/CD пайплайнах фаззинг обязан быть ограничен:
  1. **По времени:** `-fuzztime=30s` (30 секунд), `-fuzztime=5m` (5 минут), `-fuzztime=1h` (1 час).
  2. **По количеству итераций:** `-fuzztime=100000x` (ровно 100 000 прогонов мутатора).
- По завершении времени или числа итераций фаззер выводит итоговую статистику и завершает тест с кодом 0 (PASS).

## Решение по шагам

1. Напишите фазз-тест парсинга числа.
2. Запустите фаззер с ограничением по времени `-fuzztime=3s`.
3. Запустите фаззер с ограничением по итерациям `-fuzztime=50000x`.
4. Сравните вывод отчетов.

## Код решения

**`fuzz_time_test.go`**

```go
package main

import (
	"strconv"
	"testing"
)

func FuzzParseSmallInt(f *testing.F) {
	f.Add("100")
	f.Add("-200")
	f.Add("0")

	f.Fuzz(func(t *testing.T, s string) {
		_, _ = strconv.Atoi(s)
	})
}
```

ℹ️ Фазз-тест для демонстрации флага -fuzztime

**`Терминал`**

```bash
# 1. Запуск строго на 3 секунды:
go test -fuzz=FuzzParseSmallInt -fuzztime=3s
# Вывод:
# fuzz: elapsed: 3s, execs: 712040 (237346/sec), new interesting: 8 (total: 11)
# PASS

# 2. Запуск ровно на 50 000 итераций:
go test -fuzz=FuzzParseSmallInt -fuzztime=50000x
# Вывод:
# fuzz: elapsed: 0s, execs: 50000 (245100/sec), new interesting: 4 (total: 7)
# PASS
```

## Под капотом

Суффикс `x` в значении флага указывает парсеру рантайма тестирования интерпретировать число как счетчик итераций (Execution Count Threshold).

## Подводные камни

Запустить фаззинг в CI без флага `-fuzztime`: джоб зависнет до общего таймаута раннера GitHub Actions (6 часов), заблокировав очередь пайплайна.

## На собеседовании

**Вопрос с собеседования:** «Какова рекомендуемая стратегия запуска фаззинга в современной CI/CD архитектуре?»
**Ответ:** 1. В PR/MR запускать быстрый регрессионный фаззинг на 10–30 секунд (`-fuzztime=30s`). 2. В ночном CI (Nightly Build) запускать фаззинг на несколько часов (`-fuzztime=4h`) на выделенных серверах для глубокого исследования кодовой базы.
