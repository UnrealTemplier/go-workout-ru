# Тестирование пула воркеров (Worker Pool): гарантия обработки всех N задач без потерь

## Условие

Протестируйте Worker Pool: убедитесь, что все задания обработаны и результаты собраны в правильном количестве.

## Теория

Тестирование паттерна Worker Pool:
- Пул из \(M\) горутин-воркеров читает задачи из канала `jobs <-chan Task`.
- Записывает обработанные результаты в канал `results chan<- Result`.
- **Инварианты теста:**
  1. Ни одно задание не потеряно: число полученных результатов строго равно числу отправленных задач.
  2. Отсутствие состояния гонки: одновременная запись результатов не повреждает срез.
  3. Отсутствие дедлоков: каналы корректно закрываются, горутины воркеров завершаются через `sync.WaitGroup`.

## Решение по шагам

1. Напишите функцию `WorkerPool(workers, jobsCount int) []int`.
2. Запустите \(M\) воркеров с чтением из `jobs`.
3. Отправьте \(N\) задач и закройте `jobs`.
4. Соберите результаты и проверьте сумму.

## Код решения

**`worker_pool.go`**

```go
package main

import "sync"

// RunWorkerPool запускает пул горутин и возвращает удвоенные значения
func RunWorkerPool(numWorkers, numJobs int) []int {
	jobs := make(chan int, numJobs)
	results := make(chan int, numJobs)

	var wg sync.WaitGroup

	// Запуск пула воркеров
	for w := 0; w < numWorkers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobs {
				results <- j * 2 // Обработка задачи
			}
		}()
	}

	// Отправка задач
	for j := 1; j <= numJobs; j++ {
		jobs <- j
	}
	close(jobs) // Сигнал воркерам: задач больше нет

	// Ожидаем завершения воркеров в отдельной горутине
	go func() {
		wg.Wait()
		close(results) // Закрываем результаты после завершения всех воркеров
	}()

	var output []int
	for res := range results {
		output = append(output, res)
	}

	return output
}
```

ℹ️ Паттерн Worker Pool с корректным закрытием каналов

**`worker_pool_test.go`**

```go
package main

import (
	"slices"
	"testing"
)

func TestWorkerPoolExecution(t *testing.T) {
	const numWorkers = 5
	const numJobs = 100

	results := RunWorkerPool(numWorkers, numJobs)

	// Проверка 1: получено ровно 100 результатов
	if len(results) != numJobs {
		t.Fatalf("Потеряны задачи! Получено %d результатов из %d", len(results), numJobs)
	}

	// Проверка 2: сортируем и проверяем каждый элемент
	slices.Sort(results)
	for i, val := range results {
		expected := (i + 1) * 2
		if val != expected {
			t.Errorf("Неверный результат на позиции %d: got %d, want %d", i, val, expected)
		}
	}
}
```

## Под капотом

Паттерн с отдельной горутиной ожидания `go func() { wg.Wait(); close(results) }()` предотвращает дедлок, позволяя главной горутине читать результаты из `results` параллельно с работой воркеров.

## Подводные камни

Вызывать `wg.Wait()` в той же горутине ДО цикла чтения `for res := range results` при небуферизированном канале: воркеры заблокируются на записи, а главная горутина зависнет на `Wait()` (дедлок).

## На собеседовании

**Вопрос с собеседования:** «Как в Worker Pool корректно обработать отмену по context.Context?»
**Ответ:** Внутри цикла воркера использовать оператор `select`:
```go
select {
case <-ctx.Done():
    return
case job, ok := <-jobs:
    if !ok { return }
    process(job)
}
```
Это гарантирует немедленное прекращение обработки задач при отмене клиентского запроса или graceful shutdown сервера.
