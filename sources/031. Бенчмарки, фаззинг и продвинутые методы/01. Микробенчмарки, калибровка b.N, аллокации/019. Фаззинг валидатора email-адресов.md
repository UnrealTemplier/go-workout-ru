# Фаззинг валидатора email-адресов: поиск граничных паник и скрытых регулярных зависаний (ReDoS)

## Условие

Напишите fuzz-тест для функции валидации email-адреса. Попробуйте найти входные данные, которые вызовут панику или бесконечный цикл.

## Теория

Тестирование надежности парсеров строк фаззингом:
- Валидаторы email-адресов часто содержат уязвимости:
  1. Паника при взятии среза по байтовому индексу внутри мультибайтового UTF-8 символа.
  2. Паника при обращении к индексу `s[0]` на пустой строке.
  3. ReDoS (Regular Expression Denial of Service): катастрофический бэктрекинг в регулярных выражениях, вешающий ядро CPU на 100%.
- Фаззер генерирует миллионы аномальных строк (`@`, `..@..`, null-байты, эмодзи) для проверки стабильности.

## Решение по шагам

1. Напишите функцию валидации `ValidateEmail(email string) bool`.
2. Задайте начальные валидные семена в `f.Add`.
3. Запустите фаззинг на проверку отсутствия паник.
4. Убедитесь в стабильности парсера.

## Код решения

**`email_validator.go`**

```go
package main

import (
	"strings"
)

// ValidateEmail проверяет базовые правила email адреса
func ValidateEmail(email string) bool {
	if len(email) < 3 || len(email) > 254 {
		return false
	}

	parts := strings.Split(email, "@")
	if len(parts) != 2 {
		return false
	}

	user, domain := parts[0], parts[1]
	if len(user) == 0 || len(domain) == 0 {
		return false
	}

	if !strings.Contains(domain, ".") {
		return false
	}

	// Защита от точек в начале или конце домена
	if strings.HasPrefix(domain, ".") || strings.HasSuffix(domain, ".") {
		return false
	}

	return true
}
```

ℹ️ Безопасный валидатор email

**`email_validator_fuzz_test.go`**

```go
package main

import "testing"

func FuzzValidateEmail(f *testing.F) {
	// Добавляем типичные примеры
	f.Add("alex@ya.ru")
	f.Add("admin@company.com")
	f.Add("@emptyuser.com")
	f.Add("bad-email-without-at")
	f.Add("user@.dotstart.com")

	f.Fuzz(func(t *testing.T, email string) {
		// Функция НИКОГДА не должна паниковать ни на каких строках!
		_ = ValidateEmail(email)
	})
}
```

## Под капотом

Движок фаззинга автоматически генерирует строки с невалидными UTF-8 байтовыми последовательностями, проверяя, что функции срезов Go не вызывают панику `panic: slice bounds out of range`.

## Подводные камни

Использовать сложные регулярные выражения с вложенными квантификаторами `(a+)+$` в `ValidateEmail`: это прямой путь к уязвимости ReDoS.

## На собеседовании

**Вопрос с собеседования:** «Почему движок регулярных выражений regexp в Go защищен от катастрофического бэктрекинга ReDoS?»
**Ответ:** В Go пакет `regexp` основан на алгоритме RE2 (конечные автоматы Томпсона / DFA), гарантирующем линейное время выполнения \(O(N)\) от длины строки. Он в принципе не использует экспоненциальный бэктрекинг, делая атаки ReDoS невозможными.
