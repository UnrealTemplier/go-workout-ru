# Автоматизированная проверка аллокаций: функция testing.AllocsPerRun

## Условие

Используйте `testing.AllocsPerRun` для проверки, что функция делает ровно ожидаемое количество аллокаций.

## Теория

Утверждение аллокаций в Unit-тестах (`testing.AllocsPerRun`):
- Бенчмарки показывают аллокации визуально, но не валят unit-тест при возникновении регрессии памяти.
- Если разработчик случайно превратил значение в интерфейс `any` или допустил побег переменной в кучу (Escape Analysis), тест должен упасть!
- `testing.AllocsPerRun(runs int, f func()) float64`:
  1. Вызывает функцию \(N\) раз для прогрева (warm-up).
  2. Замеряет суммарное количество аллокаций памяти.
  3. Возвращает среднее число аллокаций за 1 вызов (например `0.0` или `1.0`).

## Решение по шагам

1. Напишите функцию без аллокаций памяти (Stack-Only).
2. В unit-тесте вызовите `testing.AllocsPerRun(100, ...)`.
3. Сравните возвращенное значение с нулем.
4. Убедитесь в отсутствии аллокаций в куче.

## Код решения

**`zero_alloc.go`**

```go
package main

// FastSum вычисляет сумму без побега переменных в кучу
func FastSum(a, b int) int {
	return a + b
}
```

ℹ️ Функция со 100% аллокацией на стеке

**`zero_alloc_test.go`**

```go
package main

import "testing"

func TestFastSumZeroAllocations(t *testing.T) {
	// Запускаем функцию 500 раз и замеряем среднее число аллокаций
	allocs := testing.AllocsPerRun(500, func() {
		res := FastSum(10, 20)
		if res != 30 {
			t.Fatalf("unexpected res: %d", res)
		}
	})

	t.Logf("Среднее число аллокаций: %.2f", allocs)

	// СТРОГИЙ АССЕРТ: функция ОБЯЗАНА делать 0 аллокаций в куче!
	if allocs > 0 {
		t.Errorf("Регрессия производительности! Ожидалось 0 аллокаций, получено %.2f", allocs)
	}
}
```

ℹ️ Тест регрессии аллокаций памяти через AllocsPerRun

**`Терминал`**

```bash
go test -v zero_alloc_test.go zero_alloc.go
# Вывод:
# === RUN   TestFastSumZeroAllocations
#     zero_alloc_test.go:15: Среднее число аллокаций: 0.00
# --- PASS: TestFastSumZeroAllocations (0.00s)
# PASS
```

## Под капотом

Перед основным замером `testing.AllocsPerRun` делает разогревочный прогон (Warm-up Run), чтобы отсечь разовую статическую инициализацию глобальных пакетов и структур рантайма.

## Подводные камни

Передавать в функцию `fmt.Println` внутри `AllocsPerRun`: форматированный вывод в консоль сам по себе аллоцирует память, что приведет к ложному падению ассерта.

## На собеседовании

**Вопрос с собеседования:** «Почему testing.AllocsPerRun возвращает float64, а не целое число int?»
**Ответ:** Потому что алгоритм делит суммарное число аллокаций на количество запусков. Если функция аллоцирует объект в куче один раз каждые 10 вызовов (например, при расширении кэша), метод вернет `0.1`, что невозможно представить в виде `int`.
