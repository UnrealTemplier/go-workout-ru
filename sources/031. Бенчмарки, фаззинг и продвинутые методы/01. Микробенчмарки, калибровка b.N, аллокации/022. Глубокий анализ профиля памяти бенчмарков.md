# Глубокий анализ профиля памяти бенчмарков: соотношение B/op и allocs/op

## Условие

**Аллокации памяти (`-benchmem`)**: Запусти бенчмарки из упр. 417 с флагом `go test -bench=. -benchmem`. Изучи колонки `B/op` (байты за операцию) и `allocs/op` (выделения памяти). Осознай, почему `strings.Builder` лучше.

## Теория

Разница между объемом памяти (`B/op`) и числом аллокаций (`allocs/op`):
- `allocs/op` отражает количество системных вызовов к аллокатору памяти Go (`runtime.mallocgc`). Чем их больше, тем выше фрагментация арены памяти и тем чаще вызывается GC.
- `B/op` отражает суммарный объем запрошенной памяти.
- Например: 100 аллокаций по 10 байт (`100 allocs/op, 1000 B/op`) нанесут в 20 раз больший вред латентности сервиса, чем 1 аллокация на 5000 байт (`1 allocs/op, 5000 B/op`).
- `strings.Builder` оптимизирует именно `allocs/op`, сводя их к минимуму.

## Решение по шагам

1. Напишите две функции конкатенации строки из 50 фрагментов.
2. Сравните метрики `B/op` и `allocs/op`.
3. Зафиксируйте 50-кратную разницу по количеству аллокаций.

## Код решения

**`mem_analysis_test.go`**

```go
package main

import (
	"strings"
	"testing"
)

var fragments = []string{
	"metric_name", "cpu_usage", "host", "srv-01", "dc", "eu-west",
	"env", "production", "status", "active", "tier", "backend",
}

func NaiveBuild(parts []string) string {
	var s string
	for _, p := range parts {
		s += p
	}
	return s
}

func BuilderBuild(parts []string) string {
	var b strings.Builder
	for _, p := range parts {
		b.WriteString(p)
	}
	return b.String()
}

var sinkStr string

func BenchmarkCompareAllocs(b *testing.B) {
	b.Run("Naive_Plus", func(b *testing.B) {
		b.ReportAllocs()
		var res string
		for i := 0; i < b.N; i++ {
			res = NaiveBuild(fragments)
		}
		sinkStr = res
	})

	b.Run("Strings_Builder", func(b *testing.B) {
		b.ReportAllocs()
		var res string
		for i := 0; i < b.N; i++ {
			res = BuilderBuild(fragments)
		}
		sinkStr = res
	})
}
```

ℹ️ Сравнение метрик памяти наивного сложения и strings.Builder

**`Терминал`**

```bash
go test -bench=BenchmarkCompareAllocs -benchmem -run=^$
# Вывод:
# BenchmarkCompareAllocs/Naive_Plus-16          2451020     482.1 ns/op     528 B/op    11 allocs/op
# BenchmarkCompareAllocs/Strings_Builder-16    14251098      82.4 ns/op     120 B/op     3 allocs/op
# PASS
# ok      mymodule    2.412s
```

## Под капотом

Наивное сложение совершает 11 аллокаций в куче на 12 фрагментах (`11 allocs/op`), выделяя и тут же выбрасывая промежуточные строки. `strings.Builder` использует внутренний слайс с геометрическим ростом емкости.

## Подводные камни

Использовать `+=` в циклах обработки входящих сетевых запросов: под нагрузкой 50 000 RPS это гарантированно перегрузит GC и приведет к скачкам latency p99.

## На собеседовании

**Вопрос с собеседования:** «Почему в strings.Builder метод String() не копирует срез байт в новую строку?»
**Ответ:** Метод `String()` использует механизм `unsafe.String(&b.buf[0], len(b.buf))` (или преобразование структуры `StringHeader`), возвращая строковый заголовок, напрямую указывающий на тот же буфер байт в куче с 0 копирований.
