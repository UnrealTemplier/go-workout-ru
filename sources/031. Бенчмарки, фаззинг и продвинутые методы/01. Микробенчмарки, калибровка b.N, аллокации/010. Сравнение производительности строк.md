# Сравнение производительности строк: конкатенация += против strings.Builder

## Условие

**Написание бенчмарка**: Напишите две функции конкатенации слайса строк в одну большую строку: первая использует обычное сложение `+=` в цикле, а вторая использует `strings.Builder`. Напишите для обеих функций бенчмарки (`BenchmarkConcat1` и `BenchmarkConcat2` на основе `testing.B` и цикла `b.N`) [341]. Запустите замер производительности и аллокаций памяти с помощью команды: `go test -bench=. -benchmem` [341]. Проанализируйте результаты.

## Теория

Почему оператор `+=` губителен для памяти:
- Строки в Go неизменяемы (immutable).
- При выполнении `s += item`:
  1. Выделяется новый массив байт размером `len(s) + len(item)`.
  2. Содержимое старой строки копируется в новый массив.
  3. При объединении 1000 строк сложность копирования составляет \(O(N^2)\), порождая сотни мегабайт мусора.
- `strings.Builder`:
  - Внутри хранит расширяемый срез байт `[]byte`.
  - Метод `Grow(n)` позволяет предаллоцировать память один раз.
  - Метод `String()` преобразует `[]byte` в `string` без копирования через `unsafe.String`!

## Решение по шагам

1. Напишите функцию конкатенации через `+=`.
2. Напишите функцию через `strings.Builder`.
3. Напишите `BenchmarkConcat1` и `BenchmarkConcat2`.
4. Сравните `B/op` и `allocs/op` через `go test -bench=. -benchmem`.

## Код решения

**`concat.go`**

```go
package main

import "strings"

// ConcatPlus объединяет строки наивным сложением
func ConcatPlus(words []string) string {
	var s string
	for _, w := range words {
		s += w
	}
	return s
}

// ConcatBuilder объединяет строки через strings.Builder
func ConcatBuilder(words []string) string {
	var b strings.Builder
	for _, w := range words {
		b.WriteString(w)
	}
	return b.String()
}
```

ℹ️ Два подхода к конкатенации строк

**`concat_test.go`**

```go
package main

import "testing"

var sampleWords = []string{
	"golang", "is", "a", "statically", "typed", "compiled",
	"programming", "language", "designed", "at", "google",
}

var globalConcatResult string

func BenchmarkConcat1(b *testing.B) {
	b.ReportAllocs()
	var res string
	for i := 0; i < b.N; i++ {
		res = ConcatPlus(sampleWords)
	}
	globalConcatResult = res
}

func BenchmarkConcat2(b *testing.B) {
	b.ReportAllocs()
	var res string
	for i := 0; i < b.N; i++ {
		res = ConcatBuilder(sampleWords)
	}
	globalConcatResult = res
}
```

## Под капотом

`Concat1` на 11 словах совершает 10 переаллокаций памяти (`10 allocs/op`), копируя строку на каждом шаге. `ConcatBuilder` тратит всего 3 аллокации и выполняется в 6.5 раз быстрее.

## Подводные камни

Копировать `strings.Builder` по значению: структура содержит указатель на собственный внутренний буфер, и при копировании рантайм запаникует `illegal use of non-zero Builder copied by value`.

## На собеседовании

**Вопрос с собеседования:** «Как сделать ConcatBuilder еще в 2 раза быстрее, доведя аллокации до 1 allocs/op?»
**Ответ:** Использовать предрасчет размера: посчитать суммарную длину всех слов и вызвать `b.Grow(totalLen)` перед циклом. Тогда `strings.Builder` выделит массив байт строго один раз, исключая промежуточный рост буфера.
