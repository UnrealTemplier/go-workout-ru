# Оптимизация срезов: замер уменьшения allocs/op при переходе от append к make

## Условие

Напиши бенчмарк для **аллокаций**: функция, которая `append`ит в слайс в цикле. Запусти с `-benchmem`. Покажи `allocs/op`. Оптимизируй: предвыдели слайс через `make([]int, 0, len)`. Сравни `allocs/op` до и после.

## Теория

Фиксация эффекта предаллокации в метриках бенчмарка:
- При добавлении 1000 элементов через `append` без указания емкости:
  - Слайс растет поэтапно: \(0 \to 1 \to 2 \to 4 \to 8 \to 16 \to 32 \dots\)
  - Каждое расширение — это вызов `runtime.growslice`, порождающий **12 аллокаций** на одну операцию (`12 allocs/op`).
- С `make([]int, 0, 1000)`:
  - Выделяется ровно один блок памяти нужного размера.
  - Показатель снижается до **1 allocs/op** (падение нагрузки на аллокатор в 12 раз!).

## Решение по шагам

1. Напишите `UnoptimizedAppend(n int)`.
2. Напишите `OptimizedMake(n int)`.
3. Запустите сравнительный бенчмарк с `-benchmem`.
4. Зафиксируйте падение `allocs/op` с 12 до 1.

## Код решения

**`alloc_opt_bench_test.go`**

```go
package main

import "testing"

const itemsCount = 1000

func UnoptimizedAppend(n int) []int {
	var s []int
	for i := 0; i < n; i++ {
		s = append(s, i)
	}
	return s
}

func OptimizedMake(n int) []int {
	s := make([]int, 0, n) // Точная предаллокация емкости
	for i := 0; i < n; i++ {
		s = append(s, i)
	}
	return s
}

var sinkSlice []int

func BenchmarkSliceAllocationOptimization(b *testing.B) {
	b.Run("Unoptimized_Append", func(b *testing.B) {
		b.ReportAllocs()
		var res []int
		for i := 0; i < b.N; i++ {
			res = UnoptimizedAppend(itemsCount)
		}
		sinkSlice = res
	})

	b.Run("Optimized_Make", func(b *testing.B) {
		b.ReportAllocs()
		var res []int
		for i := 0; i < b.N; i++ {
			res = OptimizedMake(itemsCount)
		}
		sinkSlice = res
	})
}
```

ℹ️ Сравнение аллокаций памяти до и после оптимизации

**`Терминал`**

```bash
go test -bench=BenchmarkSliceAllocationOptimization -benchmem -run=^$
# Вывод:
# BenchmarkSliceAllocationOptimization/Unoptimized_Append-16      384102      3120 ns/op     25208 B/op     12 allocs/op
# BenchmarkSliceAllocationOptimization/Optimized_Make-16        1841029       650 ns/op      8192 B/op      1 allocs/op
# PASS
# ok      mymodule    2.105s
```

## Под капотом

В оптимизированной версии потребление памяти снизилось с 25 КБ до 8 КБ (ровно \(1000 \times 8\) байт с округлением до размера сайз-класса mcache), а скорость выросла почти в 5 раз.

## Подводные камни

Предаллоцировать избыточную емкость `make([]int, 0, 1000000)`, если реально потребуется только 10 элементов: это приведет к напрасной трате оперативной памяти.

## На собеседовании

**Вопрос с собеседования:** «Как размер структуры влияет на выбор сайз-класса в mcache аллокатора Go?»
**Ответ:** Рантайм Go делит объекты кучи на 67 фиксированных размерных классов (от 8 байт до 32 КБ). Запрос на 8000 байт округляется аллокатором вверх до ближайшего класса (8192 байта), чтобы избежать внешней фрагментации страниц памяти.
