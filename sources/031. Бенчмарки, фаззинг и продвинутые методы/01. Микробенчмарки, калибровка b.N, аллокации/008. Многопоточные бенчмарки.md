# Многопоточные бенчмарки: метод b.RunParallel и пул рабочих горутин pb.Next()

## Условие

Создайте бенчмарк с `b.RunParallel(func(pb *testing.PB) { ... })` для измерения производительности в многопоточном режиме.

## Теория

Зачем нужен метод `b.RunParallel`:
- Обычный цикл `for i := 0; i < b.N` выполняется строго в одной горутине на одном ядре.
- Он не выявляет узкие места конкурентности: конкуренцию за мьютексы (Lock Contention), инвалидацию L1/L2 кэша процессора (False Sharing) и масштабируемость.
- `b.RunParallel`:
  1. Создает пул горутин, количество которых равно `GOMAXPROCS` (или настраивается через `b.SetParallelism(multiplier)`).
  2. Распределяет `b.N` итераций между горутинами.
  3. Цикл `for pb.Next()` атомарно выбирает следующую порцию работы.

## Решение по шагам

1. Создайте структуру с `sync.RWMutex`.
2. Напишите бенчмарк с `b.RunParallel`.
3. Внутри функции запустите цикл `for pb.Next()`.
4. Запустите бенчмарк и оцените пропускную способность.

## Код решения

**`parallel_cache.go`**

```go
package main

import "sync"

type ThreadSafeStore struct {
	mu   sync.RWMutex
	data map[string]int
}

func NewStore() *ThreadSafeStore {
	return &ThreadSafeStore{data: map[string]int{"status": 200}}
}

func (s *ThreadSafeStore) Read(key string) int {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return s.data[key]
}
```

ℹ️ Потокобезопасное хранилище на RWMutex

**`parallel_cache_test.go`**

```go
package main

import "testing"

func BenchmarkStoreParallelReads(b *testing.B) {
	store := NewStore()

	b.ResetTimer()
	b.ReportAllocs()

	// Запуск параллельного бенчмарка на всех доступных ядрах CPU
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			_ = store.Read("status")
		}
	})
}
```

ℹ️ Конкурентный бенчмарк с b.RunParallel

**`Терминал`**


## Под капотом

`pb.Next()` использует атомарный декремент счетчика `atomic.AddUint64` для раздачи пачек итераций горутинам пула без блокировок мьютексами.

## Подводные камни

Использовать общие переменные без синхронизации внутри тела `b.RunParallel`: это приведет к моментальной гонке данных (Data Race). Локальное состояние горутины объявляется до цикла `for pb.Next()`.

## На собеседовании

**Вопрос с собеседования:** «Почему при увеличении числа ядер CPU в b.RunParallel с sync.Mutex (обычным мьютексом) производительность может не расти, а падать?»
**Ответ:** Из-за конкуренции за блокировку (Lock Contention) и эффекта Cache Line Bouncing: ядра процессора непрерывно сбрасывают L1/L3 кэш-линии мьютекса по протоколу когерентности кэша (MESI/MOESI), расходуя шину памяти на межъядерную синхронизацию.
