# Аудит аллокаций памяти в бенчмарках: флаг -benchmem, метрики B/op и allocs/op

## Условие

Запустите бенчмарк с флагом `-benchmem`, чтобы увидеть количество аллокаций памяти и выделенных байт.

## Теория

Метрики флага `-benchmem`:
- В HighLoad Go-сервисах процессорное время (CPU) часто тратится не на бизнес-вычисления, а на сборку мусора (GC) и выделение памяти в куче (heap allocations).
- Флаг `-benchmem` добавляет в отчет две критически важные колонки:
  1. `B/op`: сколько байт памяти выделила операция в куче за 1 вызов.
  2. `allocs/op`: сколько раз рантайм Go обратился к аллокатору (`runtime.newobject` / `mallocgc`) за 1 вызов.
- Идеальный результат оптимизации: `0 B/op, 0 allocs/op` (объект живет на стеке или переиспользуется через `sync.Pool`).

## Решение по шагам

1. Напишите функцию, выделяющую память в куче.
2. Напишите бенчмарк.
3. Запустите `go test -bench=. -benchmem`.
4. Проанализируйте вывод `B/op` и `allocs/op`.

## Код решения

**`alloc_demo_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// HeapAllocatingFunc заставляет рантайм выделять память в куче
func HeapAllocatingFunc(id int) string {
	return fmt.Sprintf("order-id-%d", id)
}

var globalStr string

func BenchmarkHeapAllocating(b *testing.B) {
	var s string
	for i := 0; i < b.N; i++ {
		s = HeapAllocatingFunc(i)
	}
	globalStr = s
}
```

ℹ️ Бенчмарк функции с аллокациями в куче

**`Терминал`**

```bash
go test -bench=BenchmarkHeapAllocating -benchmem -run=^$
# Вывод:
# BenchmarkHeapAllocating-16    18543210    64.2 ns/op    32 B/op    2 allocs/op
# PASS
# ok      mymodule    1.256s
```

## Под капотом

Рантайм Go считывает статистику аллокаций через `runtime.ReadMemStats(&ms)`. Разница между `ms.Mallocs` до и после цикла делится на `b.N`.

## Подводные камни

Ориентироваться только на `ns/op`: код может быть быстрым на 1 ядре, но при 100 000 RPS частые аллокации вызовут частые паузы сборщика мусора (GC Stop-The-World) и деградацию латентности.

## На собеседовании

**Вопрос с собеседования:** «Почему уменьшение allocs/op важнее, чем микрооптимизация ассемблерных инструкций CPU в Go-бэкенде?»
**Ответ:** Каждая аллокация в куче создает нагрузку на сборщик мусора (триколорный маркер GC должен просканировать объект). Уменьшение аллокаций до 0 снижает паузы GC, стабилизирует Tail Latency (p99) и позволяет сервису масштабироваться линейно под миллионами RPS.
