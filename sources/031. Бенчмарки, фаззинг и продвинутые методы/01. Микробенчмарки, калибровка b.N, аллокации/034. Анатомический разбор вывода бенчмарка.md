# Анатомический разбор вывода бенчмарка: расшифровка колонок и суффикса GOMAXPROCS

## Условие

Проанализируй вывод бенчмарка: `BenchmarkSumSlice-8    10000000    105 ns/op    0 B/op    0 allocs/op`. Объясни каждое число. Покажи, что `-8` — GOMAXPROCS.

## Теория

Расшифровка стандартного формата вывода бенчмарков Go:
Строка отчета:
`BenchmarkSumSlice-8    10000000    105 ns/op    0 B/op    0 allocs/op`
1. **`BenchmarkSumSlice`**: имя тестовой функции.
2. **`-8`**: значение `GOMAXPROCS` (число доступных логических ядер CPU во время замера).
3. **`10000000`**: итоговое значение `b.N` (сколько итераций выполнил раннер за время калибровки).
4. **`105 ns/op`**: среднее время выполнения одной итерации (наносекунды на операцию).
5. **`0 B/op`**: сколько байт в куче выделила одна операция.
6. **`0 allocs/op`**: сколько обращений к аллокатору совершила одна операция.

## Решение по шагам

1. Напишите функцию бенчмарка.
2. Запустите замер с флагом `-cpu=1,4,8`.
3. Сопоставьте суффикс `-N` с параметром `-cpu`.
4. Проанализируйте масштаб изменений метрик.

## Код решения

**`cpu_bench_test.go`**

```go
package main

import (
	"runtime"
	"testing"
)

var sink int

func BenchmarkCPUDemo(b *testing.B) {
	b.ReportAllocs()

	// Логируем текущий GOMAXPROCS для проверки
	if b.N == 1 {
		b.Logf("Текущий GOMAXPROCS: %d", runtime.GOMAXPROCS(0))
	}

	var s int
	for i := 0; i < b.N; i++ {
		s += i
	}
	sink = s
}
```

ℹ️ Демонстрация работы суффикса GOMAXPROCS

**`Терминал`**

```bash
# Запуск с принудительным перебором разных конфигураций CPU:
go test -bench=BenchmarkCPUDemo -cpu=1,4,8 -run=^$
# Вывод:
# BenchmarkCPUDemo-1      1000000000         0.28 ns/op        0 B/op          0 allocs/op
# BenchmarkCPUDemo-4      1000000000         0.28 ns/op        0 B/op          0 allocs/op
# BenchmarkCPUDemo-8      1000000000         0.28 ns/op        0 B/op          0 allocs/op
# PASS
# ok      mymodule    1.120s
```

## Под капотом

Суффикс `-cpu` указывает рантайму вызвать `runtime.GOMAXPROCS(n)` перед началом бенчмарка. Для однопоточных бенчмарков `ns/op` остается постоянным, а для `b.RunParallel` масштабируется пропорционально ядрам.

## Подводные камни

Сравнивать бенчмарки с разными суффиксами `-4` и `-16`: результаты получены при разных лимитах параллелизма, сопоставлять их напрямую некорректно.

## На собеседовании

**Вопрос с собеседования:** «Почему в контейнерах Docker/Kubernetes GOMAXPROCS по умолчанию может быть равен числу физических ядер хоста (например 64), даже если поду выделен лимит CPU 2?»
**Ответ:** Потому что Go считывает количество ядер через `sysconf(_SC_NPROCESSORS_ONLN)`, игнорируя cgroups квоты Linux. Это приводит к созданию сотен лишних потоков ОС и деградации из-за троттлинга CPU CFS Quota. Для исправления подключают библиотеку `go.uber.org/automaxprocs`.
