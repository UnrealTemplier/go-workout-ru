# Модель памяти Go (Memory Model): отношение happens-before и несинхронизированный доступ

## Условие

Напиши тест для **"happens-before"**: `var x, y int`. Горутина 1: `x = 1; y = 2`. Горутина 2: читает `y`, затем `x`. Покажи, что без синхронизации порядок не гарантирован. Запусти много раз — иногда `y` прочитается раньше `x`.

## Теория

Спецификация модели памяти Go (Go Memory Model):
- Внутри одной горутины чтение и запись гарантированно упорядочены так, как написано в коде.
- **Но между разными горутинами:** если нет явной синхронизации (канал, мьютекс, atomic), компилятор и процессор имеют право переупорядочивать инструкции (Instruction Reordering) и кэшировать переменные в регистрах/Store Buffer процессора.
- В результате Горутина 2 может увидеть запись `y = 2`, но при этом всё еще видеть старое значение `x = 0`!
- Отношение **happens-before** гарантирует строгую видимость изменений только через механизмы синхронизации.

## Решение по шагам

1. Создайте переменные `x` и `y`.
2. Запустите две горутины без синхронизации.
3. Продемонстрируйте риск переупорядочивания.
4. Исправьте код с использованием `sync.Mutex` или каналов.

## Код решения

**`happens_before_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

type MemoryOrderDemo struct {
	mu   sync.Mutex
	x, y int
}

func (m *MemoryOrderDemo) Write() {
	m.mu.Lock()
	m.x = 1
	m.y = 2
	m.mu.Unlock()
}

func (m *MemoryOrderDemo) Read() (int, int) {
	m.mu.Lock()
	defer m.mu.Unlock()
	return m.x, m.y
}

func TestHappensBeforeGuarantee(t *testing.T) {
	demo := &MemoryOrderDemo{}
	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		demo.Write()
	}()

	var readX, readY int
	go func() {
		defer wg.Done()
		readX, readY = demo.Read()
	}()

	wg.Wait()

	// При синхронизации мьютексом гарантируется строгое состояние:
	// Либо оба 0 (прочитали до записи), либо x=1, y=2 (прочитали после записи).
	// Промежуточное состояние x=0, y=2 НЕВОЗМОЖНО!
	if readX == 0 && readY == 2 {
		t.Fatal("Нарушение happens-before! Прочитано y=2 при x=0!")
	}
}
```

ℹ️ Синхронизация через мьютекс гарантирует отношение happens-before

**`Терминал`**

```bash
go test -v -race happens_before_test.go
# Вывод:
# === RUN   TestHappensBeforeGuarantee
# --- PASS: TestHappensBeforeGuarantee (0.00s)
# PASS
```

## Под капотом

Мьютекс `sync.Mutex` устанавливает барьеры памяти (Memory Barriers / MFENCE). Захват `Lock()` гарантирует, что все предыдущие записи в других горутинах, освободивших этот мьютекс, сброшены в оперативную память и видны текущему ядру.

## Подводные камни

Полагаться на «интуитивный» порядок в многопоточном коде без примитивов синхронизации: процессор с Out-of-Order Execution выполнит инструкции в обратном порядке ради оптимизации конвейера.

## На собеседовании

**Вопрос с собеседования:** «Что такое Write Barrier и когда он применяется в Go?»
**Ответ:** 1. Аппаратный барьер памяти процессора (Instruction Reordering). 2. Внутренний Write Barrier рантайма Go в GC: при включенной фазе маркировки GC сборщик перехватывает каждую запись указателя в память, чтобы не пропустить живой объект в триколорном алгоритме.
