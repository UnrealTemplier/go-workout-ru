# Сравнительные бенчмарки входных объемов: подтесты b.Run для 10, 1000 и 100000 элементов

## Условие

Напишите два бенчмарка для одной функции с разными входными данными и сравните производительность.

## Теория

Параметризованные бенчмарки через `b.Run`:
- Производительность алгоритма зависит от объема входных данных (\(O(1)\), \(O(N)\), \(O(N \log N)\), \(O(N^2)\)).
- Тестирование только на маленьких массивах скрывает квадратичную деградацию.
- Идиоматичный паттерн:
  `b.Run(name, func(b *testing.B) { ... })`
- Позволяет запускать бенчмарк для срезов разного размера (`Size=10`, `Size=1000`, `Size=100000`) в рамках одного запуска и визуально наблюдать изменение `ns/op`.

## Решение по шагам

1. Напишите функцию поиска дубликатов.
2. Создайте родительский бенчмарк с таблицей размеров (`10`, `1000`).
3. Вызовите `b.Run` для каждого размера с `b.ResetTimer()`.
4. Сравните изменение времени от размера.

## Код решения

**`contains_bench_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// LinearContains — линейный поиск элемента O(N)
func LinearContains(slice []int, target int) bool {
	for _, v := range slice {
		if v == target {
			return true
		}
	}
	return false
}

var globalFound bool

func BenchmarkLinearContains(b *testing.B) {
	sizes := []int{10, 1000, 100000}

	for _, size := range sizes {
		b.Run(fmt.Sprintf("Size_%d", size), func(b *testing.B) {
			data := make([]int, size)
			for i := range data {
				data[i] = i
			}
			target := -1 // Худший случай: элемента нет в слайсе (полный проход)

			b.ResetTimer()
			b.ReportAllocs()

			var found bool
			for i := 0; i < b.N; i++ {
				found = LinearContains(data, target)
			}
			globalFound = found
		})
	}
}
```

ℹ️ Параметризованный бенчмарк с субтестами b.Run

**`Терминал`**

```bash
go test -bench=BenchmarkLinearContains -run=^$
# Вывод:
# BenchmarkLinearContains/Size_10-16        254109812      4.71 ns/op     0 B/op   0 allocs/op
# BenchmarkLinearContains/Size_1000-16        2845101    419.0 ns/op     0 B/op   0 allocs/op
# BenchmarkLinearContains/Size_100000-16        28140  42100.0 ns/op     0 B/op   0 allocs/op
# PASS
# ok      mymodule    3.841s
```

## Под капотом

Каждый вызов `b.Run` создает независимый дочерний бенчмарк со своим собственным счетчиком `b.N`, гарантируя калибровку времени под каждый конкретный размер данных отдельно.

## Подводные камни

Выполнять подготовку `make([]int, size)` внутри `for i := 0; i < b.N; i++`: тогда замеряется не поиск, а выделение памяти.

## На собеседовании

**Вопрос с собеседования:** «Как с помощью флага -bench запустить только один конкретный размер из параметризованного бенчмарка?»
**Ответ:** Использовать регулярное выражение фильтра:
`go test -bench='BenchmarkLinearContains/Size_1000$' -run=^$`
Знак доллара `$` гарантирует совпадение строго с `Size_1000`, исключая `Size_100000`.
