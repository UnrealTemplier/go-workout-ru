# Многопоточный бенчмарк конкурентной мапы: тестирование sync.Map через b.RunParallel

## Условие

**Параллельные бенчмарки (`b.RunParallel`)**: Протестируй производительность конкурентной мапы `sync.Map`. Используй метод `b.RunParallel(func(pb *testing.PB) { for pb.Next() { ... } })`, чтобы запустить бенчмарк одновременно на всех ядрах процессора.

## Теория

Когда `sync.Map` превосходит обычную мапу с `sync.RWMutex`:
- `sync.Map` оптимизирована под два конкретных сценария:
  1. Ключ пишется один раз, а читается миллионы раз (Read-Heavy Cache).
  2. Разные горутины работают с непересекающимися множествами ключей.
- Внутри `sync.Map` разделена на `read` (атомарный lock-free доступ без блокировок) и `dirty` (защищенный мьютексом).
- Тест с `b.RunParallel` нагружает все ядра CPU, демонстрируя отсутствие блокировок на чтении.

## Решение по шагам

1. Инициализируйте `sync.Map` предзаполненными данными.
2. Настройте `b.RunParallel`.
3. Запустите цикл `for pb.Next()` с вызовом `m.Load(key)`.
4. Оцените масштабируемость `sync.Map`.

## Код решения

**`sync_map_bench_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

func BenchmarkSyncMapConcurrentReads(b *testing.B) {
	var m sync.Map
	m.Store("config_host", "cluster-01.internal")
	m.Store("config_port", 9000)
	m.Store("config_active", true)

	b.ResetTimer()
	b.ReportAllocs()

	// Нагружаем все ядра процессора параллельным чтением
	b.RunParallel(func(pb *testing.PB) {
		for pb.Next() {
			val, ok := m.Load("config_host")
			if !ok || val != "cluster-01.internal" {
				b.Fatal("неверное значение из sync.Map")
			}
		}
	})
}
```

ℹ️ Параллельный бенчмарк sync.Map на чтение

**`Терминал`**

```bash
go test -bench=BenchmarkSyncMapConcurrentReads -cpu=1,4,8,16 -run=^$
# Вывод:
```

## Под капотом

Масштабирование идеально линейно (время на операцию снижается с 24 нс до 1.8 нс при росте ядер с 1 до 16), так как `m.Load()` читает атомарный указатель `atomic.LoadPointer` структуры `readOnly` без обращения к мьютексу.

## Подводные камни

Использовать `sync.Map` для частой записи новых ключей (Write-Heavy): при каждом промахе чтения `sync.Map` берет мьютекс и копирует dirty-мапу, работая медленнее обычной `map + sync.Mutex`.

## На собеседовании

**Вопрос с собеседования:** «Почему в типичном Go-сервисе обычная map с sync.RWMutex часто предпочтительнее sync.Map?»
**Ответ:** Потому что обычная мапа строго типизирована (Type Safety) и не требует приведения типов `val.(string)` из `any`. `sync.Map` оправдана только в высоконагруженных lock-free сценариях с преобладанием чтения.
