# Гарантированный откат транзакции при аварийной панике через recover()

## Условие

Покажи **"transaction rollback on panic"**: внутри функции транзакции вызови `panic("неожиданный крах бизнес-логики")` и докажи, что транзакция была безопасно откатана.

### Исходная формулировка

Покажи **"transaction rollback on panic"**: внутри `WithTransaction` используй `recover()` в `defer` для `Rollback()` при панике. Логируй панику и перевыбрасывай.

## Теория

Защита базы данных от зависших транзакций при паниках:
Если горутина словит панику на середине транзакции, и откат не произойдет, физическое TCP-соединение останется в открытом состоянии с заблокированными строками (`IDLE in transaction`). Другие клиенты зависнут в очереди блокировок.

## Решение по шагам

1. Начнем транзакцию.
2. Изменим баланс.
3. Вызовем преднамеренную панику.
4. В отложенной функции `defer` перехватим панику через `recover()`, вызовем `tx.Rollback()` и выведем статус.
5. Проверим, что баланс в базе не изменился.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func CrashyTransaction(db *sql.DB) (err error) {
	tx, err := db.Begin()
	if err != nil {
		return err
	}

	defer func() {
		if p := recover(); p != nil {
			fmt.Printf("[Panic Handler] Перехвачена паника: %v. Откатываем транзакцию!\n", p)
			_ = tx.Rollback()
			err = fmt.Errorf("transaction aborted due to panic: %v", p)
		}
	}()

	// Выполняем изменение
	_, _ = tx.Exec("UPDATE accounts SET balance = balance - 999 WHERE id = 1")

	// Внезапная паника посреди бизнес-процесса
	panic("критический сбой сторонней системы или nil-pointer dereference!")

	// До коммита код никогда не дойдет
	return tx.Commit()
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	var bBefore float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 1").Scan(&bBefore)

	_ = CrashyTransaction(db)

	var bAfter float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 1").Scan(&bAfter)

	fmt.Printf("Баланс до: %.2f | Баланс после: %.2f\n", bBefore, bAfter)
	if bBefore == bAfter {
		fmt.Println("✔ Транзакция идеально откатана! Баланс в полной безопасности!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Panic Handler] Перехвачена паника: критический сбой сторонней системы или nil-pointer dereference!. Откатываем транзакцию!
# Баланс до: 900.00 | Баланс после: 900.00
# ✔ Транзакция идеально откатана! Баланс в полной безопасности!
```

## Под капотом

`tx.Rollback()` отправляет в сокет команду `ROLLBACK`, сбрасывая заблокированные строки и снимая состояние `IDLE in transaction`.

## Подводные камни

Если в `defer` не вызвать `tx.Rollback()`, сокет вернется в пул закрытым только после сборки мусора (GC finalizer), а сервер БД будет держать блокировки до закрытия соединения операционной системой.

## На собеседовании

**Вопрос с собеседования:** «Чем опасно состояние IDLE in transaction на сервере PostgreSQL?»
**Ответ:** Состояние `IDLE in transaction` удерживает открытый снимок транзакции (Virtual XID). Это препятствует процессу `VACUUM` очищать мертвые версии строк (Dead Tuples) во всей таблице, что приводит к чудовищному разрастанию размера базы (Table Bloat) и блокировке DDL операций.
