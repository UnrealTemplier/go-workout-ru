# Транзакции и ACID: гарантии согласованности финансового баланса

## Условие

**Транзакции (ACID)**: Начни транзакцию через `tx, err := db.Begin()`. Выполни два запроса: перевод 100 рублей со счета 1 на счет 2. Проверь баланс до и после транзакции.

### Исходная формулировка

**Транзакции (ACID)**: Начни транзакцию через `tx, err := db.Begin()`. Выполни два запроса: спиши деньги у одного юзера и добавь другому. Если на любом этапе ошибка — `tx.Rollback()`. Если всё ок — `tx.Commit()`.

## Теория

Четыре кита надежности СУБД (ACID):
1. **Atomicity (Атомарность):** либо оба счета изменились, либо ни один.
2. **Consistency (Согласованность):** сумма балансов постоянна, констрейнты целостности не нарушены.
3. **Isolation (Изоляция):** параллельные запросы не видят промежуточного состояния.
4. **Durability (Долговечность):** после коммита изменения гарантированно зафиксированы в WAL на энергонезависимом носителе.

## Решение по шагам

1. Запросим балансы обоих счетов до транзакции.
2. Выполним атомарный перевод в транзакции `db.Begin()`.
3. Запросим балансы после `tx.Commit()`.
4. Убедимся в сохранении общего инварианта.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func printBalances(db *sql.DB, label string) {
	var b1, b2 float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 1").Scan(&b1)
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 2").Scan(&b2)
	fmt.Printf("[%s] Счет #1: $%.2f | Счет #2: $%.2f | Сумма: $%.2f\n", label, b1, b2, b1+b2)
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	printBalances(db, "ДО ТРАНЗАКЦИИ")

	tx, err := db.Begin()
	if err != nil {
		panic(err)
	}
	defer tx.Rollback()

	// Шаг 1
	_, err = tx.Exec("UPDATE accounts SET balance = balance - 100 WHERE id = 1")
	if err != nil {
		panic(err)
	}

	// Шаг 2
	_, err = tx.Exec("UPDATE accounts SET balance = balance + 100 WHERE id = 2")
	if err != nil {
		panic(err)
	}

	if err := tx.Commit(); err != nil {
		panic(err)
	}

	printBalances(db, "ПОСЛЕ ТРАНЗАКЦИИ")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [ДО ТРАНЗАКЦИИ] Счет #1: $1000.00 | Счет #2: $500.00 | Сумма: $1500.00
# [ПОСЛЕ ТРАНЗАКЦИИ] Счет #1: $900.00 | Счет #2: $600.00 | Сумма: $1500.00
```

## Под капотом

Фиксация `tx.Commit()` заставляет ядро PostgreSQL сбросить буфер WAL через системный вызов `fdatasync()`. Только после подтверждения контроллера диска клиенту отправляется пакет `CommandComplete`.

## Подводные камни

Отключение `synchronous_commit = off` увеличивает RPS в 10 раз, но при внезапном сбое питания последние несколько сотен миллисекунд закоммиченных транзакций будут безвозвратно утеряны.

## На собеседовании

**Вопрос с собеседования:** «Что гарантирует Durability (долговечность) в архитектуре PostgreSQL?»
**Ответ:** Журнал упреждающей записи (Write-Ahead Logging / WAL). Любое изменение данных сначала последовательно записывается в журнал на диске и только потом применяется к страницам таблицы в буферном пуле памяти (Shared Buffers). При внезапном крахе СУБД восстанавливает состояние, проигрывая WAL от последнего чекпоинта.
