# Архитектурная настройка пула соединений под профиль микросервиса

## Условие

Настрой пул соединений: `db.SetMaxOpenConns(25)`, `db.SetMaxIdleConns(25)`, `db.SetConnMaxLifetime(5 * time.Minute)`. Обоснуй значения для Kubernetes пода.

### Исходная формулировка

Настрой пул соединений: `db.SetMaxOpenConns(25)`, `db.SetMaxIdleConns(25)`, `db.SetConnMaxLifetime(5 * time.Minute)`. Объясни каждый параметр. Покажи, что без настройки пула — дефолт `MaxOpenConns = 0` (unlimited) может исчерпать ресурсы PostgreSQL.

## Теория

Формула расчета соединений пула:
Количество соединений базы данных ограничено доступным CPU и RAM сервера:
\(MaxConnections \approx (CoreCount \times 2) + EffectiveSpindleCount\).
Если в кластере запущено 20 подов, а у базы лимит 200 соединений, каждый под не должен открывать больше \(200 / 20 = 10\) соединений.

## Решение по шагам

1. Зададим симметричные настройки пула.
2. Объясним назначение `SetConnMaxLifetime`.
3. Запустим и проверим конфигурацию.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func ConfigureProductionPool(db *sql.DB) {
	// 1. Максимум одновременных соединений для пода
	db.SetMaxOpenConns(25)

	// 2. Равно MaxOpenConns: держим сокеты теплыми, исключая оверхед на TCP/TLS хэндшейки
	db.SetMaxIdleConns(25)

	// 3. Ротация сокетов каждые 5 минут: обязательно для переподключения при смене IP в K8s Service / DNS
	db.SetConnMaxLifetime(5 * time.Minute)

	// 4. Закрывать соединения при простое более 2 минут
	db.SetConnMaxIdleTime(2 * time.Minute)
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ConfigureProductionPool(db)
	_ = db.Ping()

	fmt.Println("✔ Пул успешно настроен по стандартам Cloud Native / Kubernetes!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Пул успешно настроен по стандартам Cloud Native / Kubernetes!
```

## Под капотом

`SetConnMaxLifetime` предотвращает утечки памяти в долгих соединениях и форсирует повторное разрешение DNS-имени хоста БД при смене мастера (Failover).

## Подводные камни

Бесконечный `ConnMaxLifetime` приводит к тому, что при переключении базы данных (Patroni Failover) сервис продолжает долбиться в старый умерший хост.

## На собеседовании

**Вопрос с собеседования:** «Зачем выставлять SetMaxIdleConns равным SetMaxOpenConns?»
**Ответ:** Если `MaxIdleConns` меньше `MaxOpenConns` (например, 5 против 25), то при всплеске нагрузки откроются 25 сокетов, а после спада 20 из них будут тут же уничтожены. При следующем всплеске приложение снова потратит ресурсы на открытие 20 TCP/SSL сокетов (Churn). Равенство устраняет сокетный треш (Socket Churn).
