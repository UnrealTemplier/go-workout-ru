# Оптимистичная блокировка (Optimistic Locking): версионирование строк без дедлоков

## Условие

Напиши **"optimistic locking"**: таблица `products (id, name, price, version INTEGER DEFAULT 1)`. При обновлении: `UPDATE ... WHERE id = $1 AND version = $2`. Если запись изменена другим процессом — верни ошибку конфликта.

### Исходная формулировка

Напиши **"optimistic locking"**: таблица `products (id, name, price, version INTEGER DEFAULT 1)`. При обновлении: `UPDATE products SET price = $1, version = version + 1 WHERE id = $2 AND version = $3`. Если `RowsAffected() == 0` — верни ошибку `"concurrent modification detected"`.

## Теория

Оптимистичная блокировка (Optimistic Concurrency Control):
Вместо тяжелых блокировок `FOR UPDATE`, удерживающих сокеты СУБД, каждой строке присваивается колонка `version INT`.
При обновлении проверяется: `UPDATE products SET price = $1, version = version + 1 WHERE id = $2 AND version = $3`.
Если другая горутина уже изменила строку, условие `version = $3` не совпадет, и `RowsAffected()` вернет 0, сигнализируя о конфликте версий.

## Решение по шагам

1. Создадим таблицу `opt_products (id, name, price, version)`.
2. Напишем функцию безопасного обновления `UpdateProductPrice(id, newPrice, expectedVersion)`.
3. Смоделируем параллельный конфликт двух процессов.
4. Обработаем ошибку конфликта версий.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"errors"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

var ErrOptimisticLockConflict = errors.New("конфликт оптимистичной блокировки: данные были изменены другим пользователем")

func UpdateProductPrice(db *sql.DB, id int, newPrice float64, currentVersion int) error {
	query := `
	UPDATE opt_products 
	SET price = $1, version = version + 1 
	WHERE id = $2 AND version = $3;`

	res, err := db.Exec(query, newPrice, id, currentVersion)
	if err != nil {
		return err
	}

	affected, _ := res.RowsAffected()
	if affected == 0 {
		return ErrOptimisticLockConflict
	}

	return nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	_, _ = db.Exec(`
		CREATE TABLE IF NOT EXISTS opt_products (
			id SERIAL PRIMARY KEY,
			name TEXT,
			price NUMERIC(10,2),
			version INT DEFAULT 1
		);
		INSERT INTO opt_products (id, name, price, version) VALUES (1, 'Кроссовки', 100.0, 1)
		ON CONFLICT (id) DO UPDATE SET version = 1, price = 100.0;
	`)

	// Поток А читает товар (версия 1)
	versionA := 1

	// Поток Б читает товар (версия 1) и успевает обновить первым!
	_ = UpdateProductPrice(db, 1, 110.0, 1)
	fmt.Println("[Поток Б] Успешно обновил цену. Версия в БД стала 2.")

	// Поток А пытается обновить товар со старой версией 1
	err := UpdateProductPrice(db, 1, 120.0, versionA)
	if errors.Is(err, ErrOptimisticLockConflict) {
		fmt.Printf("✔ [Поток А] Перехвачен конфликт: %v\n", err)
		fmt.Println("  Действие: перечитать свежие данные из базы и повторить операцию!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:

#   Действие: перечитать свежие данные из базы и повторить операцию!
```

## Под капотом

Оптимистичная блокировка не создает локов в памяти PostgreSQL Lock Manager, исключает дедлоки и идеально подходит для систем с преобладанием чтения над записью (Read-Heavy).

## Подводные камни

При высокой частоте параллельных обновлений одной и той же строки (High Contention) оптимистичная блокировка приведет к постоянным ретраям (Retry Storm). В таких случаях лучше использовать пессимистичный `FOR UPDATE`.

## На собеседовании

**Вопрос с собеседования:** «Когда выбирать пессимистичную блокировку (FOR UPDATE), а когда оптимистичную (version column)?»
**Ответ:** Оптимистичную выбирают, когда конфликты редки (< 1-5% запросов): корзины пользователей, профили, статьи. Пессимистичную выбирают при высокой конкуренции за один ресурс: покупка последнего билета на концерт, списание с горячего счета, складские остатки на распродаже (Flash Sale).
