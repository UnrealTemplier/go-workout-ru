# Аномалия Lost Update: демонстрация потери обновлений при конкурентных операциях

## Условие

Покажи **"lost update"**: два параллельных `TransferMoney` без транзакции/блокировки. Баланс перезаписывается и деньги теряются.

### Исходная формулировка

Покажи **"lost update"**: два параллельных `TransferMoney` без транзакции/блокировки. Баланс "теряется". Запусти 100 параллельных переводов — итоговый баланс ≠ начальному. Исправь через транзакцию + `SELECT FOR UPDATE`.

## Теория

Аномалия потери обновления (Lost Update):
Происходит, когда две горутины одновременно читают баланс (например, \(100\)), локально вычисляют новое значение (\(100 - 10 = 90\) и \(100 - 20 = 80\)), и по очереди выполняют `UPDATE accounts SET balance = calculatedValue`. Второе обновление полностью затирает результат первого, и \(10\) списываются в пустоту!

## Решение по шагам

1. Напишем уязвимую функцию `UnsafeDeduct` (Read -> Modify -> Write).
2. Запустим две параллельные горутины со списанием \(50\).
3. Убедимся, что баланс уменьшился только на \(50\) вместо положенных \(100\).

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"sync"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

// UnsafeDeduct демонстрирует классический антипаттерн Lost Update
func UnsafeDeduct(db *sql.DB, accountID int, amount float64) {
	// 1. Читаем старый баланс
	var currentBalance float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = $1", accountID).Scan(&currentBalance)

	// Имитируем тяжелые вычисления в бизнес-логике
	time.Sleep(50 * time.Millisecond)

	// 2. Локально считаем новый баланс
	newBalance := currentBalance - amount

	// 3. Записываем обратно (перетирая любые чужие параллельные изменения!)
	_, _ = db.Exec("UPDATE accounts SET balance = $1 WHERE id = $2", newBalance, accountID)
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Сбрасываем баланс в 1000
	_, _ = db.Exec("UPDATE accounts SET balance = 1000 WHERE id = 1")

	var wg sync.WaitGroup
	// Запускаем 2 параллельных списания по 100
	wg.Add(2)
	go func() { defer wg.Done(); UnsafeDeduct(db, 1, 100) }()
	go func() { defer wg.Done(); UnsafeDeduct(db, 1, 100) }()
	wg.Wait()

	var finalBalance float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 1").Scan(&finalBalance)

	fmt.Printf("Исходный баланс: 1000. Списано дважды по 100.\n")
	fmt.Printf("Реальный итоговый баланс: %.2f (Вместо 800.00! Деньги потеряны!)\n", finalBalance)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходный баланс: 1000. Списано дважды по 100.
# Реальный итоговый баланс: 900.00 (Вместо 800.00! Деньги потеряны!)
```

## Под капотом

Обе транзакции прочитали один и тот же снимок кортежа в Heap Page. Кто записал последним, тот и перезаписал данные предыдущей транзакции.

## Подводные камни

Никогда не делайте вычисления балансов и остатков на складе в памяти приложения через предварительный `SELECT` без блокировок! Либо используйте атомарный SQL `balance = balance - $1`, либо пессимистичную блокировку `SELECT ... FOR UPDATE`.

## На собеседовании

**Вопрос с собеседования:** «Как на уровне базы данных решить проблему Lost Update?»
**Ответ:** 1. Атомарное обновление в одном выражении: `UPDATE accounts SET balance = balance - $1 WHERE id = $2`. 2. Пессимистичная блокировка строки: `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE`. 3. Оптимистичная блокировка с колонкой версии: `WHERE id = $1 AND version = $2`.
