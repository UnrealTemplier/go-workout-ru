# Унифицированная обработка отсутствия данных: маппинг в HTTP статус 404

## Условие

Обработай ошибку `sql.ErrNoRows` при поиске пользователя, которого нет в базе. Верни кастомную ошибку `ErrNotFound`.

### Исходная формулировка

Обработай ошибку `sql.ErrNoRows` при поиске пользователя, которого нет в базе. Верни кастомную ошибку `ErrUserNotFound`.

## Теория

Маппинг инфраструктурных ошибок в бизнес-ошибки:
Слой хранения данных (Repository) обязан транслировать внутренние детали СУБД (`sql.ErrNoRows`, `pq.Error`) в нейтральные ошибки домена (`domain.ErrNotFound`), понятные верхним слоям приложения (HTTP/gRPC хэндлерам).

## Решение по шагам

1. Объявим сигнальную ошибку `ErrNotFound`.
2. Реализуем метод выборки `FindUser`.
3. Обернем `sql.ErrNoRows`.
4. Проверим маппинг в статус 404.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"errors"
	"fmt"
	"net/http"

	_ "github.com/jackc/pgx/v5/stdlib"
)

var ErrNotFound = errors.New("domain: resource not found")

func GetUserName(db *sql.DB, id int) (string, error) {
	var name string
	err := db.QueryRow("SELECT name FROM users WHERE id = $1", id).Scan(&name)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return "", ErrNotFound
		}
		return "", err
	}
	return name, nil
}

// HttpHandlerSimulator имитирует поведение HTTP-роутера
func HttpHandlerSimulator(db *sql.DB, requestedID int) int {
	_, err := GetUserName(db, requestedID)
	if errors.Is(err, ErrNotFound) {
		return http.StatusNotFound // 404
	} else if err != nil {
		return http.StatusInternalServerError // 500
	}
	return http.StatusOK // 200
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	status := HttpHandlerSimulator(db, -1)
	fmt.Printf("✔ Запрос к несуществующему ID обработан: HTTP Status %d Not Found\n", status)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Запрос к несуществующему ID обработан: HTTP Status 404 Not Found
```

## Под капотом

`errors.Is` выполняет рекурсивную проверку цепочки ошибок, гарантируя правильный статус даже при глубоком логировании.

## Подводные камни

Возврат сырого `sql.ErrNoRows` наверх нарушает инкапсуляцию архитектуры и связывает контроллеры с `database/sql`.

## На собеседовании

**Вопрос с собеседования:** «Почему сервисный слой не должен импортировать database/sql?»
**Ответ:** Принцип разделения ответственности (SoC). Сервисный слой содержит чистую бизнес-логику компании. Если завтра данные пользователя будут кэшироваться в Redis или браться из внешнего gRPC микросервиса `auth-service`, интерфейс репозитория не должен меняться.
