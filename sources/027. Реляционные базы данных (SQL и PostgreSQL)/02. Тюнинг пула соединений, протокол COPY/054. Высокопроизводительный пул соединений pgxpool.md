# Высокопроизводительный пул соединений pgxpool: тонкая настройка пула

## Условие

Используйте `pgxpool` для управления пулом соединений, настройте максимальное количество соединений (`MaxConns`), минимальное количество (`MinConns`) и таймауты жизни.

### Исходная формулировка

Используйте `pgxpool` для управления пулом соединений, настройте максимальное количество соединений.

## Теория

Пул соединений pgxpool vs database/sql:
Пакет `github.com/jackc/pgx/v5/pgxpool` работает напрямую с протоколом PostgreSQL в обход абстракций `database/sql`, исключая лишние слои рефлексии и промежуточные интерфейсы. Он поддерживает бинарный протокол, автоматический Prepared Statement кэш и расширенное управление пулом.

## Решение по шагам

1. Разберем конфигурацию через `pgxpool.ParseConfig(connStr)`.
2. Настроим `MaxConns`, `MinConns`, `MaxConnLifetime`.
3. Создадим пул `pgxpool.NewWithConfig(ctx, config)`.
4. Выполним проверочный запрос.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	connStr := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"

	// 1. Парсим конфигурацию пула
	config, err := pgxpool.ParseConfig(connStr)
	if err != nil {
		panic(err)
	}

	// 2. Тонкая настройка HighLoad пула
	config.MaxConns = 30                      // Максимум активных TCP-сокетов
	config.MinConns = 5                       // Держать прогретыми в простое
	config.MaxConnLifetime = 30 * time.Minute // Периодически ротировать сокеты
	config.MaxConnIdleTime = 5 * time.Minute  // Закрывать лишние сокеты без нагрузки
	config.HealthCheckPeriod = 1 * time.Minute // Проверять живость сокетов

	ctx := context.Background()
	pool, err := pgxpool.NewWithConfig(ctx, config)
	if err != nil {
		panic(err)
	}
	defer pool.Close()

	// 3. Выполняем запрос напрямую через pgxpool
	var sum int
	err = pool.QueryRow(ctx, "SELECT 10 + 25").Scan(&sum)
	if err != nil {
		panic(err)
	}

	stat := pool.Stat()
	fmt.Printf("✔ pgxpool готов! Результат: %d\n", sum)
	fmt.Printf("  Статистика пула: TotalConns=%d, IdleConns=%d, MaxConns=%d\n",
		stat.TotalConns(), stat.IdleConns(), stat.MaxConns())
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ pgxpool готов! Результат: 35
#   Статистика пула: TotalConns=5, IdleConns=5, MaxConns=30
```

## Под капотом

`pgxpool` создает фоновую горутину, которая следит за тем, чтобы количество свободных соединений не падало ниже `MinConns`, прогревая сокеты заранее.

## Подводные камни

Установка `MaxConns` больше, чем лимит базы данных `max_connections` (по умолчанию 100 в PostgreSQL), приведет к ошибке `FATAL: sorry, too many clients already` при масштабировании подов.

## На собеседовании

**Вопрос с собеседования:** «Почему пул соединений не должен иметь MaxConns = 1000 для каждого микросервиса?»
**Ответ:** В PostgreSQL каждое соединение — это отдельный процесс операционной системы (`postgres: user db`), потребляющий до 10-20 МБ RAM на процесс и создающий конкуренцию за кэш процессора при переключении контекста (Context Switching). Пул соединений должен быть компактным (обычно 20-50 соединений на инстанс), а перед базой ставят пул транзакций `PgBouncer`.
