# Потоковая обработка миллиардных таблиц через серверные курсоры DECLARE CURSOR

## Условие

Реализуйте постраничное чтение огромной таблицы (миллионы строк) с помощью серверных курсоров (`DECLARE ... CURSOR`, `FETCH`).

### Исходная формулировка

Реализуйте постраничное чтение огромной таблицы (миллионы строк) с помощью серверных курсоров PostgreSQL (`DECLARE cursor`, `FETCH`), чтобы не загружать всю выборку в память Go-приложения.

## Теория

Серверные курсоры (Server-side Cursors):
Обычный запрос `SELECT * FROM big_table` заставляет драйвер загружать мегабайты данных в память.
Серверный курсор объявляется внутри транзакции `DECLARE cur CURSOR FOR SELECT ...` и позволяет Go-сервису забирать данные пачками ровно по \(N\) строк через команду `FETCH 500 FROM cur`.

## Решение по шагам

1. Начнем транзакцию `tx, _ := db.Begin()`.
2. Объявим курсор `DECLARE my_cursor CURSOR FOR SELECT id, name FROM users`.
3. В цикле будем вызывать `FETCH 2 FROM my_cursor`.
4. Закроем курсор `CLOSE my_cursor` и завершим транзакцию.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func StreamWithCursor(db *sql.DB, batchSize int) error {
	tx, err := db.Begin()
	if err != nil {
		return err
	}
	defer tx.Rollback()

	// 1. Объявляем серверный курсор внутри транзакции
	cursorName := "users_cursor"
	declareSQL := fmt.Sprintf("DECLARE %s CURSOR FOR SELECT id, name FROM users ORDER BY id ASC", cursorName)
	if _, err := tx.Exec(declareSQL); err != nil {
		return fmt.Errorf("declare cursor: %w", err)
	}

	totalFetched := 0
	for {
		// 2. Выбираем очередную пачку строк
		fetchSQL := fmt.Sprintf("FETCH %d FROM %s", batchSize, cursorName)
		rows, err := tx.Query(fetchSQL)
		if err != nil {
			return err
		}

		batchCount := 0
		for rows.Next() {
			var id int
			var name string
			if err := rows.Scan(&id, &name); err != nil {
				rows.Close()
				return err
			}
			batchCount++
			totalFetched++
			fmt.Printf("    -> [Курсор] Запись #%d: %s\n", id, name)
		}
		rows.Close()

		// Если пачка пуста, мы достигли конца таблицы
		if batchCount == 0 {
			break
		}
	}

	// 3. Закрываем курсор
	_, _ = tx.Exec(fmt.Sprintf("CLOSE %s", cursorName))
	return tx.Commit()
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	fmt.Println("✔ Потоковое чтение таблицы порциями по 2 записи через Server-side Cursor:")
	_ = StreamWithCursor(db, 2)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Потоковое чтение таблицы порциями по 2 записи через Server-side Cursor:
#     -> [Курсор] Запись #1: Алексей Смирнов
#     -> [Курсор] Запись #2: Ольга
#     -> [Курсор] Запись #3: Сергей Петров
```

## Под капотом

Серверный курсор сохраняет позицию указателя в плане выполнения запроса (Query Plan State) в оперативной памяти бэкэнда Postgres, отдавая клиенту строки порциями фиксированного размера.

## Подводные камни

Серверные курсоры существуют ТОЛЬКО внутри открытой транзакции. Как только транзакция завершается (`COMMIT` или `ROLLBACK`), курсор автоматически уничтожается.

## На собеседовании

**Вопрос с собеседования:** «Почему постраничная пагинация через OFFSET 1000000 убивает базу, а курсор — нет?»
**Ответ:** `OFFSET 1000000` заставляет СУБД физически прочитать и отбросить 1 000 000 строк с диска для каждого запроса (\(O(N)\)). Серверный курсор (или Keyset Pagination по `WHERE id > last_id`) использует индекс и моментально позиционируется на нужную страницу за \(O(\log N)\).
