# Утечка сокетов: исчерпание пула соединений при пропущенном rows.Close

## Условие

**[Каверзный кейс]**: Напиши `QueryContext`, но забудь вызвать `rows.Close()`. Запусти код в цикле и покажи, как пул соединений блокируется.

### Исходная формулировка

**[Каверзный кейс]**: Напиши `QueryContext`, но забудь вызвать `rows.Close()`. Запусти код в цикле 1000 раз. Используя `runtime.NumGoroutine()`, покажи, как утекает память и горутины (исчерпание пула соединений). Исправь код.

## Теория

Блокировка горутин в пуле:
Когда количество активных соединений достигает `SetMaxOpenConns(N)`, любой следующий вызов `Query/Exec` блокируется. Если предыдущие соединения удерживаются забытыми `rows`, наступает взаимная блокировка.

## Решение по шагам

1. Зададим жесткий лимит соединений `db.SetMaxOpenConns(2)`.
2. В цикле вызовем 3 раза `db.QueryContext` с таймаутом 200 мс без закрытия `rows`.
3. Зафиксируем падение 3-го запроса по таймауту ожидания сокета.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Ограничиваем пул строго 2 соединениями
	db.SetMaxOpenConns(2)

	for i := 1; i <= 3; i++ {
		ctx, cancel := context.WithTimeout(context.Background(), 250*time.Millisecond)
		fmt.Printf("[Итерация %d] Запрос к базе...", i)
		rows, err := db.QueryContext(ctx, "SELECT 1")
		if err != nil {
			fmt.Printf(" ОШИБКА: %v\n", err)
			cancel()
			break
		}
		// НАМЕРЕННО НЕ ЗАКРЫВАЕМ rows!
		_ = rows
		cancel()
		fmt.Printf(" Успешно. Занято сокетов: %d\n", db.Stats().InUse)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Итерация 1] Запрос к базе... Успешно. Занято сокетов: 1
# [Итерация 2] Запрос к базе... Успешно. Занято сокетов: 2
# [Итерация 3] Запрос к базе... ОШИБКА: context deadline exceeded
```

## Под капотом

На третьей итерации свободных соединений нет, а лимит `MaxOpenConns` исчерпан. Запрос встает в очередь ожидания и падает при истечении 250 мс.

## Подводные камни

В реальных приложениях без `QueryContext` горутины зависают навсегда (Goroutine Leak), приводя к нехватке памяти.

## На собеседовании

**Вопрос с собеседования:** «Как настроить пул соединений database/sql в продакшене?»
**Ответ:** Задать `SetMaxOpenConns` (обычно 25-100 в зависимости от доступных соединений в Postgres), `SetMaxIdleConns` (равным или близким к MaxOpenConns во избежание постоянных пересозданий TCP-сокетов), `SetConnMaxLifetime` (5-15 минут для ротации сокетов и учета DNS) и `SetConnMaxIdleTime` (5 минут).
