# Подготовленные выражения Prepared Statements: db.PrepareContext и безопасность

## Условие

Используйте `db.PrepareContext` для создания Prepared Statements. Поймите, как это снижает нагрузку на CPU базы данных при частых повторных запросах.

### Исходная формулировка

Используйте `db.PrepareContext` для создания Prepared Statements. Поймите, как это снижает нагрузку на парсер БД при частом выполнении одного и того же запроса.

## Теория

Жизненный цикл Prepared Statement:
При подготовке выражения (`db.PrepareContext`):
1. Запрос парсится в синтаксическое дерево (AST).
2. Выполняется семантический анализ и валидация схемы.
3. Оптимизатор строит готовый бинарный план выполнения (Query Plan).
При последующих вызовах `stmt.Exec(args...)` передаются только параметры, экономя время компиляции SQL на сервере.

## Решение по шагам

1. Создадим подготовленное выражение `stmt, err := db.PrepareContext(...)`.
2. Обеспечим освобождение памяти через `defer stmt.Close()`.
3. Выполним выражение в цикле 5 раз с разными аргументами.
4. Замерим стабильность работы.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	// 1. Создаем Prepared Statement
	query := "SELECT name FROM users WHERE id = $1"
	stmt, err := db.PrepareContext(ctx, query)
	if err != nil {
		panic(err)
	}
	defer stmt.Close() // Обязательное закрытие дескриптора на сервере

	// 2. Многократное выполнение скомпилированного плана
	ids := []int{1, 2, 3}
	for _, id := range ids {
		var name string
		err := stmt.QueryRowContext(ctx, id).Scan(&name)
		if err != nil {
			fmt.Printf("ID %d: не найден\n", id)
			continue
		}
		fmt.Printf("✔ Выполнен Prepared Statement: ID=%d -> Имя='%s'\n", id, name)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Выполнен Prepared Statement: ID=1 -> Имя='Алексей Смирнов'
# ✔ Выполнен Prepared Statement: ID=2 -> Имя='Ольга'
# ✔ Выполнен Prepared Statement: ID=3 -> Имя='Сергей Петров'
```

## Под капотом

В PostgreSQL сервер создает именованный стейтмент через протокол Parse (`P`). Вызов `stmt.Close()` отправляет пакет Close (`C`), удаляя план из оперативной памяти процесса базы.

## Подводные камни

В `database/sql` вызов `db.Prepare` создает стейтмент на ОДНОМ конкретном соединении. Если следующий запрос берет другое соединение из пула, драйвер незаметно создает стейтмент заново на новом соединении, что может приводить к утечкам при плохом управлении.

## На собеседовании

**Вопрос с собеседования:** «Почему при использовании PgBouncer в режиме Transaction Pooling вызов db.Prepare() приводит к ошибкам?»
**Ответ:** В режиме Transaction Pooling соединение между PgBouncer и PostgreSQL возвращается в пул после каждой транзакции. Следующая транзакция клиента попадает на другой физический бэкэнд Postgres, где этот Prepared Statement не существует (ошибка `prepared statement does not exist`). Для PgBouncer используют неименованные стейтменты или отключают кеш стейтментов.
