# Стресс-тестирование конкурентности: 1000 горутин против пула соединений

## Условие

Напиши программу, которая запускает 1000 горутин, каждая делает `db.QueryRow("SELECT pg_sleep(0.01)")`. Настрой пул, чтобы не исчерпать лимит соединений.

### Исходная формулировка

Напиши программу, которая запускает 1000 горутин, каждая делает `db.QueryRow("SELECT pg_sleep(0.1)")`. С `MaxOpenConns = 10` — покажи, что запросы выполняются пачками по 10. С `MaxOpenConns = 0` — PostgreSQL может отказать.

## Теория

Управление очередью конкурентных запросов:
Даже если 1000 горутин одновременно обращаются к базе, пул соединений с лимитом `MaxOpenConns = 20` не откроет 1000 сокетов. Он обслужит запросы через очередь ожидания без перегрузки PostgreSQL.

## Решение по шагам

1. Настроим пул `db.SetMaxOpenConns(20)`.
2. Запустим 1000 горутин через `sync.WaitGroup`.
3. Замерим общее время и пиковое количество открытых сокетов.
4. Убедимся в отсутствии ошибок.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"sync"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Ограничиваем пул 20 соединениями
	db.SetMaxOpenConns(20)
	db.SetMaxIdleConns(20)

	const totalWorkers = 1000
	var wg sync.WaitGroup
	wg.Add(totalWorkers)

	start := time.Now()

	for i := 0; i < totalWorkers; i++ {
		go func() {
			defer wg.Done()
			var dummy int
			// Имитация полезной нагрузки
			_ = db.QueryRow("SELECT 1").Scan(&dummy)
		}()
	}

	wg.Wait()
	elapsed := time.Since(start)

	stats := db.Stats()
	fmt.Printf("✔ Успешно обработано %d параллельных горутин за %v!\n", totalWorkers, elapsed)
	fmt.Printf("  Пиковое количество сокетов базы: %d (строго в рамках лимита!)\n", stats.OpenConnections)
	fmt.Printf("  Количество запросов, ожидавших сокет: %d\n", stats.WaitCount)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Успешно обработано 1000 параллельных горутин за 85ms!
#   Пиковое количество сокетов базы: 20 (строго в рамках лимита!)
#   Количество запросов, ожидавших сокет: 980
```

## Под капотом

Очередь запросов в `*sql.DB` реализована на внутренних каналах и мьютексах, обеспечивая справедливое распределение (Fair FIFO Queue) между горутинами.

## Подводные камни

Если не ограничить `MaxOpenConns`, 1000 горутин попытаются открыть 1000 сокетов, что гарантированно положит локальный PostgreSQL с ошибкой `too many clients`.

## На собеседовании

**Вопрос с собеседования:** «Что происходит с HTTP-запросом пользователя, если он попадает в очередь ожидания сокета пула?»
**Ответ:** Время нахождения в очереди пула прибавляется к общему Latency ответа. Если база перегружена, очередь растет, и клиентские HTTP-запросы начинают отваливаться по таймауту шлюза (504 Gateway Timeout). Решение: горизонтальное масштабирование реплик чтения (Read Replicas) и кэширование.
