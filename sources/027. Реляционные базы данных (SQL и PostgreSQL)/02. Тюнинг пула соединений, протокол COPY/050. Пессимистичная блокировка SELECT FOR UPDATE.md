# Пессимистичная блокировка SELECT FOR UPDATE: гарантированная защита баланса

## Условие

Модифицируй `TransferMoney`: добавь `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE` для блокировки строки счета на время транзакции.

### Исходная формулировка

Модифицируй `TransferMoney`: добавь `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE` в начале транзакции. Покажи, что "lost update" исчез. Объясни уровень изоляции `READ COMMITTED` + row-level locks.

## Теория

Пессимистичная блокировка (Pessimistic Locking):
Конструкция `SELECT ... FOR UPDATE` захватывает монопольную блокировку строки на уровне таблицы (Row-level exclusive lock). Любая другая параллельная транзакция, пытающаяся выполнить `SELECT ... FOR UPDATE` или `UPDATE` для этой же строки, блокируется и ждет коммита первой транзакции.

## Решение по шагам

1. Начнем транзакцию `tx, _ := db.BeginTx(ctx, nil)`.
2. Заблокируем счет отправителя через `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE`.
3. Проверим достаточность баланса в коде Go.
4. Выполним безопасное списание и коммит.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func SafeDeductWithLock(ctx context.Context, db *sql.DB, accountID int, amount float64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	// 1. Захватываем блокировку FOR UPDATE
	var currentBalance float64
	queryLock := "SELECT balance FROM accounts WHERE id = $1 FOR UPDATE"
	if err := tx.QueryRowContext(ctx, queryLock, accountID).Scan(&currentBalance); err != nil {
		return fmt.Errorf("lock failed: %w", err)
	}

	// 2. Проверяем бизнес-правило
	if currentBalance < amount {
		return fmt.Errorf("недостаточно средств: баланс %.2f, запрошено %.2f", currentBalance, amount)
	}

	// 3. Выполняем списание с гарантией, что никто не перехватил строку
	_, err = tx.ExecContext(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, accountID)
	if err != nil {
		return err
	}

	return tx.Commit()
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	if err := SafeDeductWithLock(ctx, db, 1, 50.0); err != nil {
		fmt.Println("Ошибка:", err)
		return
	}

	fmt.Println("✔ Списание успешно выполнено под защитой SELECT FOR UPDATE!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Списание успешно выполнено под защитой SELECT FOR UPDATE!
```

## Под капотом

В заголовке кортежа (Tuple Header) в поле `t_infomask` проставляются флаги блокировки, а XID текущей транзакции записывается в `t_xmax`. Серверная подсистема Lock Manager отслеживает очередь ожидающих транзакций.

## Подводные камни

Удержание `FOR UPDATE` слишком долго (например, выполняя внутри транзакции медленные HTTP-запросы к сторонним сервисам) парализует работу всей базы данных.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между SELECT FOR UPDATE и SELECT FOR UPDATE SKIP LOCKED?»
**Ответ:** `FOR UPDATE` заставляет транзакцию ждать освобождения заблокированной строки. `SKIP LOCKED` не ждет, а мгновенно пропускает заблокированные строки и возвращает только свободные. Это основа высокопроизводительных очередей задач (Message Queue) в PostgreSQL, позволяющая десяткам воркеров разбирать задачи параллельно без конфликтов.
