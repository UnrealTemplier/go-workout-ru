# Скрытая ловушка rows.Err(): перехват ошибок принудительного разрыва соединения

## Условие

**Скрытая ловушка rows.Err()**: После цикла `rows.Next()` добавь проверку `if err := rows.Err(); err != nil`. Продемонстрируй перехват ошибки разрыва соединения сервером.

### Исходная формулировка

**Скрытая ловушка `rows.Err()`**: После цикла `rows.Next()` добавь проверку `if err := rows.Err(); err != nil`. Узнай из документации, почему цикл мог прерваться досрочно (например, из-за обрыва сети), и почему эта проверка **обязательна**.

## Теория

Защита целостности при отмене бэкэнда:
Сервер PostgreSQL может принудительно оборвать сессию запроса (например, сработал `statement_timeout` или администратор выполнил `pg_terminate_backend()`). Метод `rows.Next()` возвращает `false`, а причина обрыва сохраняется в `rows.Err()`.

## Решение по шагам

1. Напишем функцию вычитки с обработкой `rows.Err()`.
2. Смоделируем принудительное завершение через вызов `pg_sleep` с маленьким таймаутом контекста.
3. Проверим точное сообщение ошибки из `rows.Err()`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func FetchStream(ctx context.Context, db *sql.DB) error {
	// Генерация 100 строк с искусственной паузой на сервере
	query := "SELECT generate_series(1, 100), pg_sleep(0.01)"
	rows, err := db.QueryContext(ctx, query)
	if err != nil {
		return err
	}
	defer rows.Close()

	count := 0
	for rows.Next() {
		count++
	}

	// Проверяем ошибку обрыва потока
	if err := rows.Err(); err != nil {
		return fmt.Errorf("поток оборван после %d строк: %w", count, err)
	}

	fmt.Printf("Все %d строк успешно получены\n", count)
	return nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Задаем жесткий таймаут 50 мс
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	if err := FetchStream(ctx, db); err != nil {
		fmt.Printf("✔ rows.Err() перехватил сбой: %v\n", err)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ rows.Err() перехватил сбой: поток оборван после 3 строк: context deadline exceeded
```

## Под капотом

При обрыве контекста рантайм `database/sql` закрывает сокет драйвера, в результате чего очередной вызов `rows.Next()` натыкается на закрытый дескриптор и выставляет `rows.lasterr`.

## Подводные камни

Если разработчик проверяет только `if err != nil` у `db.Query`, функция вернет `nil`, и вызывающий код ошибочно решит, что в базе всего 3 записи вместо 100!

## На собеседовании

**Вопрос с собеседования:** «Почему rows.Close() не очищает ошибку rows.Err()?»
**Ответ:** Потому что идиоматичный паттерн Go предполагает `defer rows.Close()` в начале функции. Если бы `Close()` очищал ошибку, то при выходе из функции мы бы потеряли информацию о сбое сетевого сокета.
