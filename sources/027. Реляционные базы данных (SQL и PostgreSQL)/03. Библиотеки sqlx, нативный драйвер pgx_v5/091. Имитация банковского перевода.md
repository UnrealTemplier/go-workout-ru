# Имитация банковского перевода: защита от дедлока через детерминированный порядок ID

## Условие

**Транзакции (Transactions)**: Напишите симуляцию банковского перевода. У вас есть таблица `accounts (id, balance)`. Переведите деньги от А к Б с защитой от дедлока при встречных переводах.

### Исходная формулировка

**Транзакции (Transactions)**: Напишите симуляцию банковского перевода. У вас есть таблица `accounts` с балансами. Начните транзакцию с помощью `db.BeginTx(ctx, nil)`. Сделайте списание с одного счета и начисление на другой. Если при каком-то из действий возникла ошибка, вызовите `tx.Rollback()`. Если всё прошло успешно, примените изменения через `tx.Commit()`.

## Теория

Проблема встречных взаимных блокировок (Deadlocks):
Если Клиент 1 переводит со счета 10 на счет 20, а Клиент 2 одновременно переводит со счета 20 на счет 10:
Поток 1 блокирует ID 10 и ждет ID 20.
Поток 2 блокирует ID 20 и ждет ID 10.
Оба потока блокируют друг друга навсегда! СУБД прерывает один из них с ошибкой `deadlock detected`.
Решение: всегда блокировать счета в порядке возрастания ID (`min(A, B)` затем `max(A, B)`).

## Решение по шагам

1. Вычислим `firstID = min(from, to)` и `secondID = max(from, to)`.
2. В транзакции заблокируем оба счета через `SELECT ... FOR UPDATE` строго в порядке возрастания.
3. Проверим баланс и выполним списание/зачисление.
4. Закоммитим транзакцию.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func DeadlockFreeTransfer(ctx context.Context, db *sql.DB, fromID, toID int, amount float64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	// Алгоритм предотвращения дедлока: упорядочивание захвата блокировок
	firstLock := fromID
	secondLock := toID
	if firstLock > secondLock {
		firstLock, secondLock = secondLock, firstLock
	}

	// Блокируем первый счет
	_, err = tx.ExecContext(ctx, "SELECT balance FROM accounts WHERE id = $1 FOR UPDATE", firstLock)
	if err != nil {
		return err
	}
	// Блокируем второй счет
	_, err = tx.ExecContext(ctx, "SELECT balance FROM accounts WHERE id = $1 FOR UPDATE", secondLock)
	if err != nil {
		return err
	}

	// Списание
	_, err = tx.ExecContext(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID)
	if err != nil {
		return err
	}
	// Зачисление
	_, err = tx.ExecContext(ctx, "UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID)
	if err != nil {
		return err
	}

	return tx.Commit()
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	err := DeadlockFreeTransfer(context.Background(), db, 2, 1, 15.00)
	if err != nil {
		panic(err)
	}

	fmt.Println("✔ Встречный перевод средств успешно выполнен с гарантией защиты от дедлока!")
}
```

**`Терминал`**

```bash

```

## Под капотом

Порядок блокировок устраняет циклы в графе ожидания транзакций (Wait-For Graph). Серверный детектор дедлоков `deadlock_timeout` никогда не сработает.

## Подводные камни

Захват блокировок в разнобой при сотнях параллельных горутин неизбежно приведет к ошибке `ERROR: deadlock detected (SQLSTATE 40P01)`.

## На собеседовании

**Вопрос с собеседования:** «Что делает PostgreSQL, когда обнаруживает дедлок транзакций?»
**Ответ:** Раз в `deadlock_timeout` (по умолчанию 1 секунда) фоновый процесс проверяет граф взаимных блокировок. При обнаружении цикла СУБД выбирает одну из транзакций жертвой (Victim), принудительно прерывает ее с ошибкой `40P01`, освобождая остальные транзакции.
