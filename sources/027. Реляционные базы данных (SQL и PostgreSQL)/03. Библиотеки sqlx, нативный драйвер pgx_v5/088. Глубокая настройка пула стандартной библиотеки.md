# Глубокая настройка пула стандартной библиотеки: жизненный цикл и DNS ротация

## Условие

**Пул соединений (Connection Pool)**: Настрой пул "под капотом" стандартной библиотеки: задай лимит, время жизни соединения и время простоя. Объясни влияние каждого параметра на сеть.

### Исходная формулировка

**Пул соединений (Connection Pool)**: Настрой пул "под капотом" стандартной библиотеки: задай `db.SetMaxOpenConns(20)` (макс. соединений), `db.SetMaxIdleConns(5)` (кол-во спящих) и `db.SetConnMaxLifetime(time.Minute * 5)`.

## Теория

Влияние параметров пула на сетевой стек Linux:
1. `SetMaxOpenConns(N)`: ограничивает число сокетов в `ESTABLISHED`. Предотвращает исчерпание эфемерных портов ядра (Ephemeral Port Exhaustion, диапазон 32768-60999).
2. `SetMaxIdleConns(N)`: держит теплые сокеты.
3. `SetConnMaxIdleTime(D)`: предотвращает сброс сокетов сетевым файрволом/NAT шлюзом по таймауту неактивности (TCP Idle Timeout).

## Решение по шагам

1. Настроим все 4 параметра пула.
2. Вызовем серию параллельных проверок.
3. Распечатаем подробные метрики.
4. Проверим закрытие сокетов.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	db.SetMaxOpenConns(15)
	db.SetMaxIdleConns(15)
	db.SetConnMaxLifetime(10 * time.Minute)
	db.SetConnMaxIdleTime(2 * time.Minute)

	_ = db.Ping()
	st := db.Stats()

	fmt.Println("✔ Конфигурация жизненного цикла пула завершена:")
	fmt.Printf("  • MaxOpen: %d | Idle: %d | InUse: %d\n", st.MaxOpenConnections, st.Idle, st.InUse)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Конфигурация жизненного цикла пула завершена:
#   • MaxOpen: 15 | Idle: 1 | InUse: 0
```

## Под капотом

При истечении `ConnMaxLifetime` соединение не обрывается агрессивно посреди запроса: оно спокойно дожидается завершения текущего запроса и закрывается при попытке возврата в пул.

## Подводные камни

Слишком короткий `ConnMaxLifetime` (например, 1 секунда) превращает пул в постоянный конвейер пересоздания сокетов, сжигая CPU на SSL Handshake.

## На собеседовании

**Вопрос с собеседования:** «Что такое TCP TIME_WAIT и как правильная настройка пула соединений в Go защищает от этой проблемы?»
**Ответ:** Когда TCP-соединение закрывается инициатором (клиентом), сокет зависает в состоянии `TIME_WAIT` на 60 секунд (2MSL). Если приложение на каждый запрос открывает и закрывает сокет (`MaxIdleConns = 0`), за 60 секунд тысячи портов окажутся в `TIME_WAIT`, и ОС откажет в создании новых сокетов (`bind: address already in use`). Пул с теплыми сокетами устраняет проблему.
