# Инженерная конфигурация пула соединений под профиль рабочей нагрузки

## Условие

**Настройка пула соединений (Connection Pool Configuration)**: Настройте параметры пула соединений: `SetMaxOpenConns(10)`, `SetMaxIdleConns(5)`, `SetConnMaxLifetime(time.Hour)`. Распечатайте статистику пула через `db.Stats()` и обоснуйте каждое значение.

### Исходная формулировка

**Настройка пула соединений (Connection Pool Configuration)**: Настройте параметры пула соединений вашего объекта `db`:
* Максимальное количество открытых соединений (`SetMaxOpenConns`).
* Максимальное количество простаивающих соединений (`SetMaxIdleConns`).
* Максимальное время жизни соединения (`SetConnMaxLifetime`).
Опишите в комментариях, как эти настройки помогают балансировать нагрузку на СУБД.

## Теория

Управление ресурсами базы данных:
Пул соединений предотвращает падение PostgreSQL от лавины одновременных подключений. Каждое соединение в PostgreSQL — это отдельный процесс ОС, потребляющий память и процессорное время.
- `MaxOpenConns`: верхняя граница открытых сокетов (защищает СУБД от перегрузки).
- `MaxIdleConns`: количество сокетов, готовых к мгновенному приему нагрузки.
- `ConnMaxLifetime`: время жизни сокета (ротация для перебалансировки DNS и очистки утечек памяти).

## Решение по шагам

1. Зададим параметры `SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime`.
2. Вызовем серию тестовых запросов.
3. Распечатаем текущую статистику пула `db.Stats()`.
4. Проверим отсутствие блокировок.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, err := sql.Open("pgx", dsn)
	if err != nil {
		panic(err)
	}
	defer db.Close()

	// Настройка пула
	db.SetMaxOpenConns(10)
	db.SetMaxIdleConns(5)
	db.SetConnMaxLifetime(1 * time.Hour)
	db.SetConnMaxIdleTime(15 * time.Minute)

	_ = db.Ping()

	stats := db.Stats()
	fmt.Println("✔ Пул соединений успешно сконфигурирован:")
	fmt.Printf("  • MaxOpenConnections: %d\n", stats.MaxOpenConnections)
	fmt.Printf("  • OpenConnections:    %d\n", stats.OpenConnections)
	fmt.Printf("  • Idle:               %d\n", stats.Idle)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Пул соединений успешно сконфигурирован:
#   • MaxOpenConnections: 10
#   • OpenConnections:    1
#   • Idle:               1
```

## Под капотом

При обращении к БД горутина пытается извлечь сокет из очереди свободных `freeConn`. Если свободных нет, а `numOpen < maxOpen`, создается новый TCP-сокет. Иначе запрос блокируется в ожидании канала.

## Подводные камни

Установка `MaxIdleConns > MaxOpenConns` автоматически урезается рантаймом Go до `MaxOpenConns`.

## На собеседовании

**Вопрос с собеседования:** «Почему в облачных средах (AWS Aurora, K8s) ConnMaxLifetime обязателен?»
**Ответ:** При смене мастера в Aurora или переключении K8s Service IP-адрес конечной точки базы данных меняется. Если сокет держится открытым часами, приложение продолжит слать запросы на старый узел или реплику только для чтения, получая ошибки `read-only transaction`.
