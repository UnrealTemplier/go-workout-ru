# Промышленный pgxpool: тонкая настройка пула под микросервисы

## Условие

**Нативный pgx**: Установи `github.com/jackc/pgx/v5`. Подключись к базе через `pgxpool.NewWithConfig`. Настрой `MaxConns=50`, `MinConns=10`, `HealthCheckPeriod`.

### Исходная формулировка

**Нативный pgx**: Установи `github.com/jackc/pgx/v5`. Подключись к базе через `pgxpool.New(ctx, connString)`. Обрати внимание, что `pgx` использует контекст везде, с самого первого вызова.

## Теория

Архитектура пула в Kubernetes:
В микросервисной архитектуре параметры пула настраиваются через переменные окружения. Важно включить периодический `HealthCheckPeriod`, чтобы пул своевременно закрывал сокеты, оборванные промежуточными NAT-шлюзами облака.

## Решение по шагам

1. Сформируем структуру `pgxpool.Config`.
2. Настроим лимиты `MaxConns`, `MinConns`, `HealthCheckPeriod`.
3. Создадим пул `pgxpool.NewWithConfig(ctx, cfg)`.
4. Проверим статистику сокетов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	ctx := context.Background()

	cfg, err := pgxpool.ParseConfig(dsn)
	if err != nil {
		panic(err)
	}

	// Тонкая настройка HighLoad пула
	cfg.MaxConns = 50
	cfg.MinConns = 10
	cfg.HealthCheckPeriod = 30 * time.Second
	cfg.MaxConnIdleTime = 5 * time.Minute

	pool, err := pgxpool.NewWithConfig(ctx, cfg)
	if err != nil {
		panic(err)
	}
	defer pool.Close()

	_ = pool.Ping(ctx)
	st := pool.Stat()

	fmt.Println("✔ Промышленный pgxpool инициализирован:")
	fmt.Printf("  • MaxConns: %d | TotalConns: %d | IdleConns: %d\n",
		st.MaxConns(), st.TotalConns(), st.IdleConns())
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Промышленный pgxpool инициализирован:
#   • MaxConns: 50 | TotalConns: 10 | IdleConns: 10
```

## Под капотом

Фоновая горутина `pgxpool` раз в 30 секунд шлет `Ping` по свободным сокетам. Если сервер перезагружался, битые сокеты удаляются без ошибок для пользователей.

## Подводные камни

Отсутствие `HealthCheckPeriod` приводит к тому, что первый реальный HTTP-запрос пользователя натыкается на умерший сокет (Broken Pipe).

## На собеседовании

**Вопрос с собеседования:** «Зачем нужен MinConns > 0 в облачном сервисе?»
**Ответ:** `MinConns` гарантирует, что в пуле всегда есть предварительно открытые и прогретые TCP-соединения с пройденной аутентификацией. При внезапном скачке трафика (Spike RPS) сервису не нужно тратить 10-30 мс на установку новых сокетов, что обеспечивает стабильный p99 Latency.
