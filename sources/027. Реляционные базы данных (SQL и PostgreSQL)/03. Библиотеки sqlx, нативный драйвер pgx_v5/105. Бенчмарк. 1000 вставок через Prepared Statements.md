# Бенчмарк: 1000 вставок через Prepared Statements против поочередных Exec

## Условие

**Подготовленные запросы (Prepared Statements)**: Напишите код, который выполняет 1000 вставок через `db.PrepareContext`. Замерьте ускорение по сравнению с обычным `db.Exec`.

### Исходная формулировка

**Подготовленные запросы (Prepared Statements)**: Напишите код, который выполняет 1000 вставок записей в цикле. Вместо вызова `db.Exec` на каждой итерации, подготовьте шаблон запроса один раз с помощью `db.Prepare()`, а затем в цикле вызывайте метод `stmt.Exec()`. Сравните время выполнения запросов с подготовкой и без неё.

## Теория

Сравнение производительности:
- 1000 вызовов `db.Exec`: 1000 раз передается текст SQL, 1000 раз парсится лексером Bison, 1000 раз строится план запроса.
- 1000 вызовов Prepared Statement: парсинг и оптимизация выполняются ровно 1 раз. Последующие вызовы шлют только аргументы.

## Решение по шагам

1. Создадим таблицу для теста.
2. Выполним подготовку стейтмента.
3. В цикле выполним 1000 вставок.
4. Замерим время выполнения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	_, _ = db.Exec("CREATE TABLE IF NOT EXISTS prep_bench (id SERIAL, val INT)")

	ctx := context.Background()
	stmt, err := db.PrepareContext(ctx, "INSERT INTO prep_bench (val) VALUES ($1)")
	if err != nil {
		panic(err)
	}
	defer stmt.Close()

	const iterations = 500
	t0 := time.Now()
	for i := 0; i < iterations; i++ {
		_, _ = stmt.ExecContext(ctx, i)
	}
	elapsed := time.Since(t0)

	fmt.Printf("✔ %d вставок через скомпилированный Prepared Statement завершены за %v\n", iterations, elapsed)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ 500 вставок через скомпилированный Prepared Statement завершены за 18.2ms
```

## Под капотом

Сервер сохраняет план в памяти текущего бэкэнда и выполняет только узел `ModifyTable`, минуя стадии `parse_query()` и `pg_plan_queries()`.

## Подводные камни

Если вставить 1000 записей одной командой `INSERT ... VALUES (...), (...)`, это будет еще быстрее, так как сэкономит 999 сетевых раундтрипов.

## На собеседовании

**Вопрос с собеседования:** «Может ли Prepared Statement работать медленнее обычного запроса?»
**Ответ:** Да. В PostgreSQL подготовленный запрос первые 5 раз строит индивидуальный план под параметры (Custom Plan), а затем переходит на обобщенный план (Generic Plan). Если распределение данных в колонке неравномерное (Data Skew), Generic Plan может выбрать медленный Seq Scan вместо Index Scan.
