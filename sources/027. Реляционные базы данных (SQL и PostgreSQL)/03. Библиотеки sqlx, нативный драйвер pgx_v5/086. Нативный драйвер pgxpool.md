# Нативный драйвер pgxpool: полный отказ от database/sql ради максимальной скорости

## Условие

Перепиши подключение на `github.com/jackc/pgx/v5/pgxpool`. Создай `pgxpool.New(ctx, connString)` и выполни запрос через `pool.QueryRow`.

### Исходная формулировка

Перепиши подключение на `github.com/jackc/pgx/v5/pgxpool`. Создай `pgxpool.New(ctx, connString)`. Покажи, что pgxpool управляет пулом соединений автоматически.

## Теория

Почему BigTech выбирает нативный pgxpool:
`database/sql` был разработан во времена Go 1.0 и накладывает ограничения:
1. Только интерфейс `any` со строковыми преобразованиями.
2. Отсутствие поддержки специфичных типов PostgreSQL (JSONB, hstore, ltree, сетевые типы cidr/inet).
3. Лишние блокировки и рефлексия.
Нативный `pgxpool` работает напрямую с протоколом, обеспечивая на 20-30% меньшую задержку (latency) и нулевые аллокации на чтение скаляров.

## Решение по шагам

1. Инициализируем `pool, err := pgxpool.New(ctx, dsn)`.
2. Вызовем `pool.QueryRow`.
3. Просканируем результат.
4. Закроем пул через `defer pool.Close()`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	ctx := context.Background()

	// Нативный пул соединений pgx
	pool, err := pgxpool.New(ctx, dsn)
	if err != nil {
		panic(fmt.Sprintf("pgxpool.New failed: %v", err))
	}
	defer pool.Close()

	// Быстрая выборка напрямую без database/sql
	var currentDb string
	err = pool.QueryRow(ctx, "SELECT current_database()").Scan(&currentDb)
	if err != nil {
		panic(err)
	}

	fmt.Printf("✔ Успешная работа через нативный pgxpool! Текущая база: '%s'\n", currentDb)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Успешная работа через нативный pgxpool! Текущая база: 'testdb'
```

## Под капотом

`pgx` взаимодействует с PostgreSQL по протоколу Frontend/Backend Protocol v3.0, напрямую парся бинарные сетевые пакеты в буфер `pgx.Conn`.

## Подводные камни

Методы `pgx` всегда требуют первым аргументом `context.Context`. Вызов без контекста синтаксически невозможен.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях database/sql все еще предпочтительнее pgxpool?»
**Ответ:** Только когда приложение обязано поддерживать мульти-СУБД архитектуру (например, работать и с PostgreSQL, и с ClickHouse/MySQL/SQLite через смену конфигурационного флага драйвера). Если сервис пишется строго под PostgreSQL, нативный `pgxpool` превосходит `database/sql` по всем параметрам.
