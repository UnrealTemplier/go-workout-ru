# Нативная работа с массивами TEXT[] в pgx/v5: срез []string без сторонних адаптеров

## Условие

Используй `pgx` с **array типами**: PostgreSQL `TEXT[]`. Сканируй напрямую в `[]string` через нативный механизм `pgx` без использования стороннего пакета `pq`.

### Исходная формулировка

Используй `pgx` с **array типами**: PostgreSQL `TEXT[]`. Сканируй в `[]string` через `pgtype.Array[string]`. Или вставляй `[]string` напрямую — pgx конвертирует автоматически.

## Теория

Нативная сериализация массивов в pgx/v5:
В отличие от `database/sql`, где для массивов требовалась обертка `pq.Array`, нативный драйвер `pgx` понимает срезы Go (`[]string`, `[]int`, `[]uuid.UUID`) напрямую как одномерные массивы PostgreSQL.

## Решение по шагам

1. Создадим таблицу с колонкой `features TEXT[]`.
2. Вставим срез строк `[]string` напрямую в `pool.Exec`.
3. Считаем массив обратно в чистый `[]string`.
4. Выведем результат.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	ctx := context.Background()
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	pool, err := pgxpool.New(ctx, dsn)
	if err != nil {
		panic(err)
	}
	defer pool.Close()

	_, _ = pool.Exec(ctx, `
	CREATE TABLE IF NOT EXISTS pgx_arrays (
		id SERIAL PRIMARY KEY,
		name TEXT,
		skills TEXT[]
	);`)

	skills := []string{"Concurrency", "PostgreSQL", "gRPC", "Kubernetes"}

	// 1. Вставляем срез напрямую без всяких pq.Array!
	var id int
	query := "INSERT INTO pgx_arrays (name, skills) VALUES ($1, $2) RETURNING id"
	err = pool.QueryRow(ctx, query, "Senior Go Engineer", skills).Scan(&id)
	if err != nil {
		panic(err)
	}

	// 2. Читаем напрямую в []string
	var fetchedSkills []string
	err = pool.QueryRow(ctx, "SELECT skills FROM pgx_arrays WHERE id = $1", id).Scan(&fetchedSkills)
	if err != nil {
		panic(err)
	}

	fmt.Printf("✔ pgx/v5 нативно прочитал массив (%d элементов): %v\n", len(fetchedSkills), fetchedSkills)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ pgx/v5 нативно прочитал массив (4 элементов): [Concurrency PostgreSQL gRPC Kubernetes]
```

## Под капотом

`pgx` кодирует массив в бинарном формате протокола (Array Header: dimensions, flags, element OID), что на 50% быстрее текстового парсинга `{...}`.

## Подводные камни

Массивы PostgreSQL индексируются с 1, а не с 0 (в SQL: `skills[1]` возвращает первый элемент).

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество хранения тегов в массиве text[] по сравнению со связующей таблицей Many-to-Many?»
**Ответ:** Массив `text[]` хранится прямо внутри строки (инлайн в кортеже), исключая дорогой `JOIN` связующей таблицы при выборке постов. В сочетании с GIN-индексом поиск по тегам происходит с экстремальной скоростью. Однако если у тега есть свои атрибуты (описание, иконка), связь Many-to-Many обязательна.
