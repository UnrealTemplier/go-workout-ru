# Механизм LISTEN / NOTIFY в pgx: реактивные Push-уведомления и Pub/Sub через БД

## Условие

Используй `pgx` для **LISTEN/NOTIFY**: `conn.Exec(ctx, "LISTEN channel_name")`. В горутине читай `conn.WaitForNotification(ctx)` — получи push-уведомления от PostgreSQL без поллинга.

### Исходная формулировка

Используй `pgx` для **LISTEN/NOTIFY**: `conn.Exec(ctx, "LISTEN channel_name")`. В горутине читай `conn.WaitForNotification(ctx)` — получишь push-уведомления от PostgreSQL. Напиши простой pub/sub через БД.

## Теория

Реактивный Pub/Sub поверх PostgreSQL:
Команды `LISTEN channel` и `NOTIFY channel, 'payload'` реализуют брокер сообщений внутри СУБД. Клиент Go встает в режим ожидания без постоянных запросов `SELECT` (Polling), мгновенно получая пуш при изменениях в таблицах.

## Решение по шагам

1. Откроем выделенное соединение `conn, _ := pool.Acquire(ctx)`.
2. Подпишемся на канал `LISTEN task_events`.
3. В горутине запустим `WaitForNotification`.
4. Отправим `NOTIFY` из другого соединения и поймаем сообщение.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	pool, err := pgxpool.New(ctx, dsn)
	if err != nil {
		panic(err)
	}
	defer pool.Close()

	// 1. Захватываем отдельное соединение для подписчика (Listener)
	listenerConn, err := pool.Acquire(ctx)
	if err != nil {
		panic(err)
	}
	defer listenerConn.Release()

	channel := "orders_feed"
	_, err = listenerConn.Exec(ctx, fmt.Sprintf("LISTEN %s", channel))
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Subscriber] Слушаем канал '%s'...\n", channel)

	// 2. В отдельной горутине шлем NOTIFY
	go func() {
		time.Sleep(200 * time.Millisecond)
		notifySQL := fmt.Sprintf("NOTIFY %s, 'Новый заказ #42 оформлен!'", channel)
		_, _ = pool.Exec(context.Background(), notifySQL)
	}()

	// 3. Ожидаем Push-уведомление от PostgreSQL
	notification, err := listenerConn.Conn().WaitForNotification(ctx)
	if err != nil {
		panic(err)
	}

	fmt.Printf("✔ Получено Push-уведомление: Channel='%s', Payload='%s'\n",
		notification.Channel, notification.Payload)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Subscriber] Слушаем канал 'orders_feed'...
# ✔ Получено Push-уведомление: Channel='orders_feed', Payload='Новый заказ #42 оформлен!'
```

## Под капотом

Уведомление передается по открытому сокету асинхронным пакетом `NotificationResponse` (`A`). Сервер отправляет пуш сразу после коммита транзакции, вызвавшей `NOTIFY`.

## Подводные камни

Соединение, слушающее `LISTEN`, нельзя использовать для обычных запросов в пуле, иначе оно заблокирует пул. Для LISTEN всегда берут отдельный выделенный сокет (`Acquire`).

## На собеседовании

**Вопрос с собеседования:** «Можно ли использовать PostgreSQL LISTEN/NOTIFY как замену Kafka/RabbitMQ?»
**Ответ:** Для простых очередей задач и инвалидации локальных кэшей в микросервисах — да. Для HighLoad брокера — нет: LISTEN/NOTIFY не имеет постоянной очереди на диске (если подписчик был в офлайне во время NOTIFY, сообщение безвозвратно теряется), и полезная нагрузка ограничена 8000 байтами.
