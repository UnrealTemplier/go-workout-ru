# Практика CLI golang-migrate: накатывание и откат версий схемы

## Условие

**Миграции**: Установи CLI-утилиту `golang-migrate/migrate`. Создай файлы `up.sql` (создание `posts`) и `down.sql` (удаление `posts`). Накати и откати.

### Исходная формулировка

**Миграции**: Установи CLI-утилиту `golang-migrate/migrate`. Создай файлы `up.sql` (создание таблицы) и `down.sql` (дроп таблицы). Напиши скрипт или команду для накатки и отката миграций. Никогда не создавай таблицы через `db.Exec` в продакшен-коде!

## Теория

Управление миграциями в командной строке:
Утилита `migrate` интегрируется в Makefile или Helm-чарты деплоя: `migrate -path migrations -database $DATABASE_URL up` и `migrate ... down 1`.

## Решение по шагам

1. Создадим структуру папки миграций.
2. Продемонстрируем накат `up`.
3. Продемонстрируем откат `down`.
4. Проверим фиксацию версий.

## Код решения

**`Терминал`**

```bash
# 1. Генерация пары файлов миграций
migrate create -ext sql -dir migrations -seq init_posts

# 2. Накат всех миграций (up)
migrate -path migrations -database "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable" up
# Вывод: 1/u init_posts (15.2ms)

# 3. Откат последней миграции (down 1)
migrate -path migrations -database "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable" down 1
# Вывод: 1/d init_posts (8.4ms)
```

**`verify.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Проверяем служебную таблицу версий
	var version int
	var dirty bool
	err := db.QueryRow("SELECT version, dirty FROM schema_migrations").Scan(&version, &dirty)
	if err != nil {
		fmt.Println("Миграции еще не инициализированы")
		return
	}

	fmt.Printf("✔ Текущая версия схемы БД: %d (Dirty: %v)\n", version, dirty)
}
```

## Под капотом

`migrate` захватывает Advisory Lock в PostgreSQL, исключая одновременное накатывание миграций несколькими подами сервиса.

## Подводные камни

Запуск миграций прямо при старте приложения (`main.go`) в 20 подах Kubernetes может вызвать гонку. Миграции должны запускаться отдельным `K8s Job` (Init-контейнером) перед развертыванием новой версии подов.

## На собеседовании

**Вопрос с собеседования:** «Почему запускать миграции из кода самого сервиса при старте подов в Kubernetes считается антипаттерном?»
**Ответ:** При деплое новой версии Kubernetes запускает сразу несколько подов (RollingUpdate). Если 10 подов одновременно попытаются применить миграции, возникнет блокировка на системных каталогах, дедлоки мигратора или ситуация, когда новые поды применили ломающие изменения, а старые поды еще обрабатывают трафик со старой схемой.
