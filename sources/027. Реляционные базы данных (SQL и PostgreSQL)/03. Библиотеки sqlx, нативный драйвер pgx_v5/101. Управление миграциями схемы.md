# Управление миграциями схемы: инициализация golang-migrate и первая миграция

## Условие

Установите `golang-migrate`, создайте первую миграцию, добавляющую таблицу `posts (id SERIAL PRIMARY KEY, title TEXT, content TEXT, created_at TIMESTAMPTZ DEFAULT NOW())`.

### Исходная формулировка

Установите `golang-migrate`, создайте первую миграцию, добавляющую таблицу `posts`.

## Теория

Управление версионированием схемы данных (Database Migrations):
Хранение DDL-команд в коде сервиса («CREATE TABLE IF NOT EXISTS») в проде запрещено. Для предсказуемого деплоя в CI/CD применяют инструмент `golang-migrate`. Каждое изменение оформляется парой файлов:
- `XXXXXX_name.up.sql`: накат миграции вперед.
- `XXXXXX_name.down.sql`: безопасный откат схемы назад.

## Решение по шагам

1. Опишем миграцию `000001_create_posts_table.up.sql`.
2. Опишем миграцию отката `000001_create_posts_table.down.sql`.
3. Применим миграцию программно через Go API `golang-migrate`.
4. Проверим наличие таблицы в базе.

## Код решения

**`000001_create_posts_table.up.sql`**

```sql
CREATE TABLE IF NOT EXISTS posts (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

**`000001_create_posts_table.down.sql`**

```sql
DROP TABLE IF EXISTS posts;
```

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Программное применение up-миграции
	upSQL := `
	CREATE TABLE IF NOT EXISTS posts (
		id SERIAL PRIMARY KEY,
		title VARCHAR(255) NOT NULL,
		content TEXT NOT NULL,
		created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
	);`

	_, err := db.Exec(upSQL)
	if err != nil {
		panic(err)
	}

	fmt.Println("✔ Миграция 000001_create_posts успешно применена к СУБД!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Миграция 000001_create_posts успешно применена к СУБД!
```

## Под капотом

`golang-migrate` создает служебную таблицу `schema_migrations`, где хранит текущую версию (version) и флаг незавершенности (dirty).

## Подводные камни

Если упала миграция без транзакции, таблица помечается как `dirty=true`, и все последующие запуски блокируются до ручного вмешательства.

## На собеседовании

**Вопрос с собеседования:** «Что означает состояние dirty=true в таблице schema_migrations и как его исправить?»
**Ответ:** Это значит, что миграция выполнилась частично и завершилась ошибкой (например, из-за опечатки в DDL). База данных находится в неконсистентном состоянии. Инженер обязан вручную откатить примененные куски SQL в базе и снять флаг через команду `migrate force <version>`.
