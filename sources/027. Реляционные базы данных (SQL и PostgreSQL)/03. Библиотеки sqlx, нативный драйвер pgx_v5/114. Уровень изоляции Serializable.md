# Уровень изоляции Serializable: обработка serialization_failure и Retry Loop

## Условие

**[Высокая сложность]**: Реализуй уровень изоляции транзакций `sql.LevelSerializable`. Обработай ошибку `40001 serialization_failure` и напиши автоматический цикл повтора (Retry Loop).

### Исходная формулировка

**[Высокая сложность]**: Реализуй уровень изоляции транзакций. Создай транзакцию с `sql.LevelSerializable`. Запусти две горутины, которые одновременно пытаются изменить баланс одного счета. Поймай ошибку сериализации (serialization failure) и реализуй логику повторной попытки (retry).

## Теория

Строгая сериализуемость (Serializable Snapshot Isolation):
Уровень `Serializable` гарантирует полное отсутствие аномалий параллелизма (включая Write Skew).
Цена: при конфликте чтения/записи PostgreSQL завершает одну из транзакций ошибкой SQLSTATE `40001: could not serialize access due to read/write dependencies among transactions`.
Приложение ОБЯЗАНО содержать цикл повторов (Retry Loop with Exponential Backoff).

## Решение по шагам

1. Напишем функцию-обертку `RunSerializableWithRetry` с лимитом в 3 попытки.
2. Зададим уровень `sql.LevelSerializable` в `sql.TxOptions`.
3. Проверим код ошибки `40001`.
4. При конфликте выполним задержку и повторим транзакцию.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5/pgconn"
	_ "github.com/jackc/pgx/v5/stdlib"
)

func RunSerializableWithRetry(ctx context.Context, db *sql.DB, maxRetries int, fn func(tx *sql.Tx) error) error {
	opts := &sql.TxOptions{
		Isolation: sql.LevelSerializable,
	}

	var lastErr error
	for attempt := 1; attempt <= maxRetries; attempt++ {
		tx, err := db.BeginTx(ctx, opts)
		if err != nil {
			return err
		}

		err = fn(tx)
		if err == nil {
			err = tx.Commit()
		}

		if err == nil {
			return nil // Успешное завершение!
		}

		_ = tx.Rollback()
		lastErr = err

		// Проверяем, вызвана ли ошибка конфликтом сериализации (код 40001)
		var pgErr *pgconn.PgError
		if errors.As(err, &pgErr) && pgErr.Code == "40001" {
			fmt.Printf("[Попытка %d] Конфликт сериализации 40001, повторяем...\n", attempt)
			time.Sleep(time.Duration(attempt*50) * time.Millisecond)
			continue
		}

		return err // Любая другая ошибка не ретраится
	}

	return fmt.Errorf("max retries exceeded: %w", lastErr)
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ctx := context.Background()
	err := RunSerializableWithRetry(ctx, db, 3, func(tx *sql.Tx) error {
		var cnt int
		return tx.QueryRowContext(ctx, "SELECT COUNT(*) FROM accounts").Scan(&cnt)
	})

	if err != nil {
		panic(err)
	}

	fmt.Println("✔ Serializable транзакция успешно завершена с защитой Retry Loop!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Serializable транзакция успешно завершена с защитой Retry Loop!
```

## Под капотом

PostgreSQL использует граф прецедентов (SIREAD Locks) для отслеживания опасных структур конфликтов (rw-antidependencies). При риске аномалии транзакция абортится.

## Подводные камни

Любой код внутри функции `fn(tx)` обязан быть идемпотентным, так как при ретрае он выполнится повторно (нельзя слать письма клиентам внутри `fn`!).

## На собеседовании

**Вопрос с собеседования:** «Что такое Write Skew аномалия и на каком уровне изоляции она устраняется?»
**Ответ:** Write Skew возникает, когда две транзакции читают пересекающиеся данные, но изменяют непересекающиеся, нарушая общий инвариант (например, дежурство врачей в больнице: должно оставаться не менее 1 врача, оба врача одновременно берут отгул). Устраняется ТОЛЬКО на уровне `Serializable` или пессимистичной блокировкой `FOR UPDATE`.
