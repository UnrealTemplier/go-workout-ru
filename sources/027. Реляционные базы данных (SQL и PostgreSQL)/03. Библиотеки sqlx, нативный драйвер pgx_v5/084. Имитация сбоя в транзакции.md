# Имитация сбоя в транзакции: атомарный откат и проверка инварианта целостности

## Условие

**[Каверзный кейс]**: Внутри транзакции сымитируй ошибку (например, деление на ноль или нарушение foreign key). Убедись, что транзакция полностью откатилась и балансы не изменились.

### Исходная формулировка

**[Каверзный кейс]**: Внутри транзакции из предыдущего задания сымитируй ошибку (например, деление на ноль или неверный SQL) после первого `INSERT`. Используй `defer tx.Rollback()` сразу после `BeginTx`. Убедись, что если произошла ошибка, транзакция откатывается, а если успех — `Rollback` возвращает `sql.ErrTxDone` (которую можно проигнорировать).

## Теория

Гарантия 'Все или ничего' (All-or-Nothing):
Если транзакция выполнила 5 успешных операций, а на 6 шаге упала с ошибкой, ни одно из предыдущих 5 изменений не должно сохраниться в базе. Вызов `tx.Rollback()` отменяет все промежуточные изменения.

## Решение по шагам

1. Прочитаем начальный баланс счета.
2. Начнем транзакцию.
3. Успешно обновим баланс.
4. Вызовем преднамеренную ошибку SQL `1 = 0/0`.
5. Откатим транзакцию и убедимся, что начальный баланс не пострадал.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	var initialBalance float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 1").Scan(&initialBalance)

	tx, err := db.Begin()
	if err != nil {
		panic(err)
	}
	defer tx.Rollback()

	// Шаг 1: успешное действие
	_, err = tx.Exec("UPDATE accounts SET balance = balance - 500 WHERE id = 1")
	if err != nil {
		panic(err)
	}

	// Шаг 2: ошибка SQL (деление на ноль)
	_, errFail := tx.Exec("SELECT 1/0")
	if errFail != nil {
		fmt.Printf("[Шаг 2] Ожидаемый сбой запроса: %v. Инициируем Rollback!\n", errFail)
		_ = tx.Rollback()
	}

	var currentBalance float64
	_ = db.QueryRow("SELECT balance FROM accounts WHERE id = 1").Scan(&currentBalance)

	fmt.Printf("Баланс до: %.2f | Баланс после сбоя: %.2f\n", initialBalance, currentBalance)
	if initialBalance == currentBalance {
		fmt.Println("✔ Полный откат подтвержден: база осталась в исходном согласованном состоянии!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Шаг 2] Ожидаемый сбой запроса: pq: division by zero. Инициируем Rollback!
# Баланс до: 900.00 | Баланс после сбоя: 900.00
# ✔ Полный откат подтвержден: база осталась в исходном согласованном состоянии!
```

## Под капотом

При откате транзакции PostgreSQL помечает XID транзакции в таблице `pg_xact` (старый `pg_clog`) как ABORTED. Все версии строк, созданные этой транзакцией, мгновенно становятся невидимыми для всех транзакций СУБД.

## Подводные камни

Попытка проигнорировать ошибку и вызвать `tx.Commit()` после упавшего запроса приведет к ошибке `sql: transaction has already been rolled back` или `25P02: current transaction is aborted`.

## На собеседовании

**Вопрос с собеседования:** «Как PostgreSQL физически откатывает транзакцию (Rollback)? Он возвращает старые значения назад?»
**Ответ:** Нет! PostgreSQL не перезаписывает данные обратно. Он просто делает статус транзакции `ABORTED` в журнале фиксации транзакций (`pg_xact`). Для MVCC этого достаточно: все кортежи, созданные этой транзакцией, теперь игнорируются при чтении как мертвые, а затем вычищаются демоном `VACUUM`.
