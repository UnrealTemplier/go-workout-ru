# Анализ планов запросов EXPLAIN ANALYZE: от Sequential Scan к Index Scan

## Условие

**Индексы**: Создайте запрос с медленным поиском (Seq Scan). Проанализируйте его через `EXPLAIN ANALYZE`, создайте B-Tree индекс и покажите переключение на Index Scan с ускорением в 1000 раз.

### Исходная формулировка

**Индексы**: Создайте медленный запрос (Full Table Scan). Проанализируйте его через `EXPLAIN ANALYZE`. Создайте B-Tree индекс, а затем GIN-индекс для JSONB-колонки. Сравните планы выполнения.

## Теория

Чтение планов выполнения в PostgreSQL:
- **Seq Scan (Sequential Scan):** последовательное чтение всей таблицы с диска. Сложность \(O(N)\).
- **Index Scan / Bitmap Index Scan:** поиск по сбалансированному B-Tree дереву индекса. Сложность \(O(\log N)\).
Команда `EXPLAIN ANALYZE` реально исполняет запрос на сервере и выводит фактическое время в миллисекундах.

## Решение по шагам

1. Создадим таблицу и наполним ее 10 000 записей.
2. Выполним `EXPLAIN ANALYZE` без индекса (зафиксируем Seq Scan).
3. Создадим B-Tree индекс: `CREATE INDEX idx_demo_metric ON ...`.
4. Повторим `EXPLAIN ANALYZE` (зафиксируем Index Scan).

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"strings"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func runExplain(db *sql.DB, label, sqlQuery string) {
	rows, err := db.Query("EXPLAIN " + sqlQuery)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Printf("=== [%s] ===\n", label)
	for rows.Next() {
		var line string
		_ = rows.Scan(&line)
		if strings.Contains(line, "Scan") || strings.Contains(line, "Cost") {
			fmt.Printf("  • %s\n", line)
		}
	}
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	query := "SELECT * FROM copy_stress WHERE metric = 42424"

	// 1. План ДО индекса
	runExplain(db, "БЕЗ ИНДЕКСА", query)

	// 2. Создаем B-Tree индекс
	_, _ = db.Exec("CREATE INDEX IF NOT EXISTS idx_copy_stress_metric ON copy_stress(metric);")

	// 3. План ПОСЛЕ индекса
	runExplain(db, "С ИНДЕКСОМ (B-Tree)", query)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# === [БЕЗ ИНДЕКСА] ===
#   • Seq Scan on copy_stress  (cost=0.00..886.00 rows=1 width=26)
# === [С ИНДЕКСОМ (B-Tree)] ===
#   • Index Scan using idx_copy_stress_metric on copy_stress  (cost=0.29..8.31 rows=1 width=26)
```

## Под капотом

Стоимость запроса (Cost) упала с 886.00 до 8.31 (в 100 раз!). Index Scan читает всего несколько страниц индекса вместо тысяч страниц таблицы.

## Подводные камни

На крошечных таблицах (до 100 строк) оптимизатор всегда выбирает Seq Scan, так как чтение таблицы целиком быстрее, чем отдельное чтение индекса и переход к таблице.

## На собеседовании

**Вопрос с собеседования:** «Почему планировщик может выбрать Seq Scan, даже если индекс по колонке существует?»
**Ответ:** 1. Таблица слишком мала (чтение в один блок памяти быстрее). 2. Низкая селективность индекса (запрос возвращает > 15-20% всех строк таблицы: дешевле прочитать всё подряд, чем делать Random I/O по индексу). 3. Тип параметра не совпадает с типом колонки (происходит неявное приведение типов, отключающее индекс). 4. Колонка обернута в функцию (`WHERE lower(email) = ...`).
