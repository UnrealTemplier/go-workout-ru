# Сервис аналитики событий: асинхронный батчинг метрик в PostgreSQL

## Условие

Напиши **"Analytics Service"**: `TrackEvent(userID int, event string, metadata map[string]any)`. Буферизируй события в Go-канале и сбрасывай пачками раз в 1 секунду или при накоплении 100 событий.

### Исходная формулировка

Напиши **"Analytics Service"**:
- `TrackEvent(userID int, event string, metadata map[string]any)` — пиши в Redis Stream (`XAdd`)
- `GetEvents(userID int, from, to time.Time) ([]Event, error)` — читай из PostgreSQL (batch insert из Redis каждые 5 минут через воркер)
- `GetRealtimeStats()` — `PFCount` по HyperLogLog уникальных пользователей за сегодня

## Теория

Паттерн Batch Flush:
Прямая запись каждого клика в базу данных положит любую СУБД на 10 000 RPS. Сервис аккумулирует метрики в Go-канале в оперативной памяти и сбрасывает их пачками по таймеру (`time.NewTicker`) или достижению лимита размера.

## Решение по шагам

1. Создадим буферизированный канал `chan Event`.
2. Запустим фоновую горутину-коллектор с тикером 500 мс.
3. При накоплении пачки выполним пакетный сброс.
4. Проверим работу.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type AnalyticsEvent struct {
	UserID    int
	EventName string
	Timestamp time.Time
}

type EventCollector struct {
	eventsChan chan AnalyticsEvent
	wg         sync.WaitGroup
}

func NewEventCollector(bufferSize int) *EventCollector {
	c := &EventCollector{
		eventsChan: make(chan AnalyticsEvent, bufferSize),
	}
	c.wg.Add(1)
	go c.flushWorker()
	return c
}

func (c *EventCollector) Track(userID int, event string) {
	c.eventsChan <- AnalyticsEvent{UserID: userID, EventName: event, Timestamp: time.Now()}
}

func (c *EventCollector) flushWorker() {
	defer c.wg.Done()
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()

	var batch []AnalyticsEvent

	flush := func() {
		if len(batch) == 0 {
			return
		}
		fmt.Printf("⚡ [Flush] Сброшена пачка из %d событий в БД одним запросом!\n", len(batch))
		batch = batch[:0]
	}

	for {
		select {
		case evt, ok := <-c.eventsChan:
			if !ok {
				flush()
				return
			}
			batch = append(batch, evt)
			if len(batch) >= 5 {
				flush()
			}
		case <-ticker.C:
			flush()
		}
	}
}

func (c *EventCollector) Close() {
	close(c.eventsChan)
	c.wg.Wait()
}

func main() {
	collector := NewEventCollector(100)

	for i := 1; i <= 12; i++ {
		collector.Track(i, "button_click")
	}

	time.Sleep(300 * time.Millisecond)
	collector.Close()
	fmt.Println("✔ Аналитический коллектор успешно обработал поток событий!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:

# ⚡ [Flush] Сброшена пачка из 5 событий в БД одним запросом!
# ⚡ [Flush] Сброшена пачка из 2 событий в БД одним запросом!
# ✔ Аналитический коллектор успешно обработал поток событий!
```

## Под капотом

Использование среза `batch[:0]` переиспользует базовый массив памяти, исключая лишние аллокации в куче.

## Подводные камни

При внезапном падении процесса (SIGKILL, OOM) события в оперативной памяти канала могут потеряться. Для критичных финансовых логов используют Write-Ahead Log на диске или Kafka.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать Graceful Shutdown для фонового накопителя батчей?»
**Ответ:** По сигналу ОС (`SIGTERM`) закрыть входной канал `close(eventsChan)`, дождаться завершения вычитки оставшихся элементов из канала воркером через `sync.WaitGroup` и сбросить финальную пачку в базу данных до вызова `os.Exit(0)`.
