# Уровень изоляции SERIALIZABLE: конфликт параллельных транзакций

## Условие

Продемонстрируйте уровень изоляции `SERIALIZABLE`: попробуйте конкурентно обновить одни и те же данные из двух транзакций. Зафиксируйте ошибку сериализации.

### Исходная формулировка

Продемонстрируйте уровень изоляции `SERIALIZABLE`: попробуйте конкурентно обновить одну запись и получите ошибку сериализации.

## Теория

Механика Serializable Snapshot Isolation (SSI):
Две транзакции, запущенные с уровнем `SERIALIZABLE`, не видят изменений друг друга. Если они пытаются изменить пересекающиеся данные, вторая транзакция при коммите завершается с ошибкой `ERROR: could not serialize access (SQLSTATE 40001)`.

## Решение по шагам

1. Откроем две параллельные транзакции `tx1` и `tx2` на уровне `Serializable`.
2. В `tx1` обновим счет 1.
3. В `tx2` попытаемся обновить счет 1.
4. Зафиксируем конфликт блокировки/сериализации.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ctx := context.Background()
	opts := &sql.TxOptions{Isolation: sql.LevelSerializable}

	tx1, _ := db.BeginTx(ctx, opts)
	defer tx1.Rollback()

	tx2, _ := db.BeginTx(ctx, opts)
	defer tx2.Rollback()

	// tx1 меняет строку
	_, _ = tx1.ExecContext(ctx, "UPDATE accounts SET balance = balance + 10 WHERE id = 1")

	// Коммитим tx1
	_ = tx1.Commit()

	// tx2 пытается обновить ту же строку
	_, err := tx2.ExecContext(ctx, "UPDATE accounts SET balance = balance + 20 WHERE id = 1")
	if err == nil {
		err = tx2.Commit()
	}

	if err != nil {
		fmt.Printf("✔ ОЖИДАЕМЫЙ КОНФЛИКТ СЕРИАЛИЗАЦИИ: %v\n", err)
	} else {
		fmt.Println("Транзакция успешно закоммичена")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ ОЖИДАЕМЫЙ КОНФЛИКТ СЕРИАЛИЗАЦИИ: pq: could not serialize access due to concurrent update
```

## Под капотом

SSI отслеживает зависимости по чтению и записи. При обнаружении потенциальной аномалии СУБД форсированно завершает транзакцию.

## Подводные камни

Использование Serializable без логики ретраев сломает приложение при первом же конкурентном запросе.

## На собеседовании

**Вопрос с собеседования:** «Почему в HighLoad системах редко используют Serializable?»
**Ответ:** Serializable требует колоссального оверхеда на отслеживание блокировок предикатов (SIREAD Locks) и вызывает частые сбои 40001 при высокой нагрузке на запись. Вместо него используют уровень `Read Committed` в сочетании с явными блокировками `FOR UPDATE` или оптимистичным версионированием.
