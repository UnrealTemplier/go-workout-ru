# Идемпотентные миграции схемы: создание файлов 000001_create_users

## Условие

Напишите пару миграций: `000001_create_users.up.sql` и `000001_create_users.down.sql`. Добавьте первичный ключ, уникальный индекс и таймстампы.

### Исходная формулировка

Напишите пару миграций: `000001_create_users.up.sql` и `000001_create_users.down.sql`.

## Теория

Анатомия промышленной DDL-миграции:
Таблицы обязаны содержать:
1. Первичный ключ `id SERIAL` или `UUID`.
2. Уникальные индексы на бизнес-ключи (`email`).
3. Поля аудита `created_at` и `updated_at`.
4. В файле `down.sql` обязательно безопасное удаление `DROP TABLE IF EXISTS`.

## Решение по шагам

1. Опишем файл `up.sql` со всеми индексами.
2. Опишем файл `down.sql`.
3. Проверим синтаксис SQL в PostgreSQL.

## Код решения

**`migrations/000001_create_users.up.sql`**

```sql
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_users_email ON users(email);
```

**`migrations/000001_create_users.down.sql`**

```sql
DROP INDEX IF EXISTS idx_users_email;
DROP TABLE IF EXISTS users;
```

## Под капотом

Создание уникального индекса `CREATE UNIQUE INDEX` одновременно обеспечивает и быстрый поиск, и гарантию целостности данных.

## Подводные камни

Создание индекса без `IF NOT EXISTS` на существующей таблице прервет миграцию с ошибкой.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между PRIMARY KEY и UNIQUE INDEX в PostgreSQL?»
**Ответ:** `PRIMARY KEY` автоматически запрещает значения `NULL` (`NOT NULL`) и в таблице может быть только один. `UNIQUE` допускает хранение нескольких значений `NULL` (так как по стандарту SQL `NULL != NULL`), и таких индексов может быть сколько угодно.
