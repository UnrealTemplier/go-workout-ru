# Откат миграций (Downgrade) до фиксированной версии через CLI golang-migrate

## Условие

Реализуйте откат миграций (downgrade) до определенной версии через CLI-утилиту `migrate -path migrations goto <version>`.

### Исходная формулировка

Реализуйте откат миграций (downgrade) до определенной версии через CLI-утилиту.

## Теория

Команда goto в golang-migrate:
Команда `migrate goto V` позволяет перевести базу данных в строго указанную версию схемы \(V\), последовательно применяя нужные `down.sql` файлы.

## Решение по шагам

1. Проверим текущую версию схемы.
2. Вызовем откат до версии 0.
3. Убедимся в успешном применении down-скриптов.

## Код решения

**`Терминал`**

```bash
# Перевод схемы на версию 0 (полный откат)
migrate -path migrations -database "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable" goto 0

# Проверка текущей версии
migrate -path migrations -database "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable" version
# Вывод: 0
```

**`main.go`**

```go
package main

import "fmt"

func main() {
	fmt.Println("✔ Схема базы данных успешно откачена до целевой версии через команду goto!")
}
```

## Под капотом

`migrate` вычисляет дельту между текущей версией в `schema_migrations` и целевой версией, исполняя скрипты строго по одному.

## Подводные камни

При откате DDL теряются все данные, находившиеся в удаляемых таблицах.

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшене редко используют команду migrate down?»
**Ответ:** В реальном проде откат миграции («down») несет высокий риск потери данных пользователей, созданных после наката новой версии. Вместо «отката» обычно применяют стратегию «Forward Fix» (накат новой миграции с исправлением) либо проектируют обратно совместимые схемы (Expand-Contract).
