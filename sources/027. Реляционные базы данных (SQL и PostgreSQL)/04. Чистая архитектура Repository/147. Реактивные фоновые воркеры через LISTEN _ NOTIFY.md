# Реактивные фоновые воркеры через LISTEN / NOTIFY в pgx

## Условие

**Listen / Notify (Очереди на минималках)**: Открой одно соединение и запусти `conn.WaitForNotification()`. В другом соединении отправь `NOTIFY channel, 'payload'`. Обработай сообщение в горутине.

### Исходная формулировка

**Listen / Notify (Очереди на минималках)**: Открой одно соединение и запусти `conn.WaitForNotification(ctx)` в горутине — она будет заблокирована в ожидании. В другой горутине (или из консоли psql) сделай `NOTIFY my_channel, 'hello_from_go'`. Убедись, что первая горутина получила сообщение.

## Теория

Асинхронные очереди без Redis/Kafka:
Механизм `LISTEN / NOTIFY` позволяет организовать оповещение воркеров об обработке новых задач. В сочетании с транзакциями пуш отправляется только тогда, когда задача реально зафиксирована в базе.

## Решение по шагам

1. Захватим выделенный сокет для подписки `LISTEN tasks_queue`.
2. В горутине воркера вызовем `WaitForNotification`.
3. Из пула отправим `NOTIFY`.
4. Воркер мгновенно выведет полученный payload.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	pool, _ := pgxpool.New(ctx, dsn)
	defer pool.Close()

	// 1. Выделенный сокет подписчика
	sub, _ := pool.Acquire(ctx)
	defer sub.Release()

	_, _ = sub.Exec(ctx, "LISTEN new_task_event")
	fmt.Println("[Воркер] Ожидание Push-сообщений из очереди PostgreSQL...")

	// 2. Отправитель
	go func() {
		time.Sleep(150 * time.Millisecond)
		_, _ = pool.Exec(context.Background(), "NOTIFY new_task_event, 'Обработать отчет #777'")
	}()

	// 3. Получение события
	notify, err := sub.Conn().WaitForNotification(ctx)
	if err != nil {
		panic(err)
	}

	fmt.Printf("✔ [Воркер] Получено событие из канала '%s': %s\n", notify.Channel, notify.Payload)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Воркер] Ожидание Push-сообщений из очереди PostgreSQL...
# ✔ [Воркер] Получено событие из канала 'new_task_event': Обработать отчет #777
```

## Под капотом

Сервер отправляет уведомление по уже открытому TCP-каналу, устраняя необходимость циклического поллинга (`SELECT * FROM tasks WHERE status = 'new'`).

## Подводные камни

Если все воркеры слушают один канал, ВСЕ они получат копию уведомления (Fan-out Pub/Sub). Для очередей задач используют шаблон `SELECT ... FOR UPDATE SKIP LOCKED`.

## На собеседовании

**Вопрос с собеседования:** «Почему LISTEN/NOTIFY не подходит для надежных очередей типа Celery/Kafka?»
**Ответ:** Отсутствие персистентности: если в момент вызова `NOTIFY` воркер перезагружался (crash/restart), сообщение не встает в очередь, а просто отбрасывается. Надежные очереди на базе Postgres строятся на обычных таблицах со статусом задач.
