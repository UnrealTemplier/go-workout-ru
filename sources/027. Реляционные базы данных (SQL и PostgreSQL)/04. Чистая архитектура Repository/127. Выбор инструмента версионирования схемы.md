# Выбор инструмента версионирования схемы: golang-migrate против goose

## Условие

Изучите концепцию версионирования схемы БД. Сравните `golang-migrate/migrate` и `pressly/goose`. Напишите критерии выбора.

### Исходная формулировка

Изучите концепцию версионирования схемы БД. Выберите инструмент: `golang-migrate/migrate` или `pressly/goose`.

## Теория

Сравнение миграторов схемы:
1. **golang-migrate:**
   - Де-факто индустриальный стандарт (15k+ звезд на GitHub).
   - Строго 2 отдельных файла: `001_name.up.sql` и `001_name.down.sql`.
   - Защита от гонок через Postgres Advisory Locks.
2. **pressly/goose:**
   - Хранит up и down в одном файле, разделяя аннотациями `-- +goose Up` и `-- +goose Down`.
   - Поддерживает миграции на чистом Go коде (для сложных конвертаций данных).

## Решение по шагам

1. Опишем структуру миграций обоих инструментов.
2. Сравним поведение при накатывании.
3. Составим матрицу выбора для команды разработки.

## Код решения

**`comparison.go`**

```go
package main

import "fmt"

func main() {
	fmt.Println("=== GOLANG-MIGRATE VS GOOSE ===")
	fmt.Println("• golang-migrate: лучше для CI/CD и чистых SQL файлов.")
	fmt.Println("• goose: удобнее для монорепозиториев и когда требуются миграции на Go-коде.")
	fmt.Println("РЕКОМЕНДАЦИЯ: Для большинства сервисов на Go — golang-migrate.")
}
```

**`Терминал`**

```bash
go run comparison.go
# Вывод:

```

## Под капотом

Оба инструмента используют транзакции вокруг DDL команд и служебную таблицу фиксации версий.

## Подводные камни

В PostgreSQL некоторые DDL (например, `CREATE INDEX CONCURRENTLY`) запрещено выполнять внутри транзакции. Для них в миграторе отключают авто-транзакцию.

## На собеседовании

**Вопрос с собеседования:** «Почему CREATE INDEX CONCURRENTLY нельзя выполнять внутри обычной миграции с BEGIN/COMMIT?»
**Ответ:** PostgreSQL требует, чтобы `CREATE INDEX CONCURRENTLY` выполнялся вне транзакционного блока, так как создание неблокирующего индекса требует двух проходов по таблице с ожиданием завершения всех параллельных транзакций. Если попытаться запустить его внутри `BEGIN...COMMIT`, СУБД вернет ошибку `25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.
