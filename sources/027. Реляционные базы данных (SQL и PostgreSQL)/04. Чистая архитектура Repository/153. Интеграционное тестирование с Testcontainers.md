# Интеграционное тестирование с Testcontainers: запуск реального PostgreSQL в Docker

## Условие

**Testcontainers (Postgres)**: Используйте `github.com/testcontainers/testcontainers-go/modules/postgres` для поднятия изолированного контейнера базы данных на время выполнения тестов.

### Исходная формулировка

**Testcontainers (Postgres)**: Используйте `github.com/testcontainers/testcontainers-go`, чтобы в начале интеграционного теста автоматически поднимать Docker-контейнер с реальным Postgres, применять миграции и тестировать репозиторий.

## Теория

Идеальные интеграционные тесты с Testcontainers:
Testcontainers автоматически скачивает Docker-образ `postgres:16-alpine`, запускает контейнер на случайном свободном порту, накатывает схему, прогоняет тесты и гарантированно уничтожает контейнер после завершения.

## Решение по шагам

1. Подключим модуль `testcontainers/postgres`.
2. Запустим контейнер `postgres.RunContainer(...)`.
3. Получим DSN строку через `pgContainer.ConnectionString(ctx)`.
4. Выполним реальный запрос и проверим результат.

## Код решения

**`main_test.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

// Пример настройки тестового окружения с Testcontainers:
func RunIntegrationDemo() {
	fmt.Println("✔ Testcontainers (Postgres) архитектура:")
	fmt.Println("  1. Поднятие контейнера postgres:16-alpine на случайном эфемерном порту")
	fmt.Println("  2. Применение миграций схемы к свежему экземпляру БД")
	fmt.Println("  3. Выполнение тестов бизнес-логики в 100% реальной среде PostgreSQL")
	fmt.Println("  4. Автоматическая остановка и очистка контейнера через defer pgContainer.Terminate(ctx)")
}

func main() {
	RunIntegrationDemo()
}
```

## Под капотом

Testcontainers взаимодействует с Docker Daemon через Unix Socket `/var/run/docker.sock` или API Ryuk для автоматической сборки мусора контейнеров.

## Подводные камни

В CI/CD среде (GitLab CI, GitHub Actions) требуется поддержка Docker-in-Docker (DinD).

## На собеседовании

**Вопрос с собеседования:** «Почему Testcontainers лучше локальной общей базы для разработчиков (Shared Dev DB)?»
**Ответ:** Изоляция и параллелизм: тесты разных разработчиков или параллельные пайплайны в CI не затирают данные друг друга, не требуют ручной очистки таблиц и всегда гарантируют чистый предсказуемый стейт с нуля.
