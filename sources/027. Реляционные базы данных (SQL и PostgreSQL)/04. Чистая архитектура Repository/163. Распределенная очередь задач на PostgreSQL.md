# Распределенная очередь задач на PostgreSQL: паттерн SELECT FOR UPDATE SKIP LOCKED

## Условие

Напиши **"Task Queue"** через PostgreSQL: таблица `tasks (id, payload, status)`. Воркеры выбирают задачи пачками через `SELECT ... FOR UPDATE SKIP LOCKED`, атомарно переводя их в статус `in_progress` без конкурентных конфликтов.

### Исходная формулировка

Напиши **"Task Queue"** через PostgreSQL + Redis:
- PostgreSQL: таблица `tasks (id, payload JSONB, status, scheduled_at, attempts, max_attempts)`
- Producer: `INSERT` задачу со `status = 'pending'`, `scheduled_at = NOW()`
- Worker: `SELECT ... FOR UPDATE SKIP LOCKED WHERE status = 'pending' AND scheduled_at <= NOW() LIMIT 1`, обнови `status = 'processing'`, выполни, `UPDATE status = 'completed'` или `'failed'` + `retry_at`
- Redis: `BLPop` для мгновенного уведомления воркеров о новых задачах (Pub/Sub или List)

## Теория

Паттерн SKIP LOCKED (Золотой стандарт очередей в PostgreSQL):
Обычный `FOR UPDATE` заставляет параллельных воркеров вставать в очередь и ждать освобождения заблокированных строк.
Модификатор `SKIP LOCKED` заставляет транзакцию пропускать уже заблокированные другими воркерами строки и брать только свободные!
Это позволяет десяткам параллельных воркеров разгребать очередь задач с предельной скоростью без дедлоков и ожидания.

## Решение по шагам

1. Создадим таблицу `task_queue (id SERIAL, payload TEXT, status TEXT)`.
2. Наполним тестовыми задачами со статусом `pending`.
3. Напишем функцию `FetchNextTasks(limit)` с `SELECT ... FOR UPDATE SKIP LOCKED`.
4. Обновим статус на `processing` и закоммитим.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type QueuedTask struct {
	ID      int
	Payload string
}

func FetchAndLockTasks(ctx context.Context, db *sql.DB, workerID int, batchSize int) ([]QueuedTask, error) {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return nil, err
	}
	defer tx.Rollback()

	// Золотой стандарт PostgreSQL очередей: FOR UPDATE SKIP LOCKED
	query := `
	SELECT id, payload 
	FROM task_queue 
	WHERE status = 'pending' 
	ORDER BY id ASC 
	LIMIT $1 
	FOR UPDATE SKIP LOCKED;`

	rows, err := tx.QueryContext(ctx, query, batchSize)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var tasks []QueuedTask
	var ids []any
	for rows.Next() {
		var t QueuedTask
		if err := rows.Scan(&t.ID, &t.Payload); err != nil {
			return nil, err
		}
		tasks = append(tasks, t)
		ids = append(ids, t.ID)
	}

	if len(tasks) == 0 {
		return nil, nil // Очередь пуста
	}

	// Переводим выбранные задачи в processing
	for _, t := range tasks {
		_, err = tx.ExecContext(ctx, "UPDATE task_queue SET status = 'processing' WHERE id = $1", t.ID)
		if err != nil {
			return nil, err
		}
	}

	if err := tx.Commit(); err != nil {
		return nil, err
	}

	return tasks, nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	_, _ = db.Exec(`
	CREATE TABLE IF NOT EXISTS task_queue (
		id SERIAL PRIMARY KEY,
		payload TEXT NOT NULL,
		status TEXT NOT NULL DEFAULT 'pending'
	);
	INSERT INTO task_queue (payload, status) VALUES
	('Сгенерировать PDF отчет', 'pending'),
	('Отправить чек покупателю', 'pending'),
	('Синхронизировать остатки', 'pending');
	`)

	ctx := context.Background()

	// Воркер 1 берет пачку
	tasks1, _ := FetchAndLockTasks(ctx, db, 1, 2)
	fmt.Printf("✔ [Воркер 1] Захватил %d задачи (SKIP LOCKED):\\n", len(tasks1))
	for _, t := range tasks1 {
		fmt.Printf("  • ID %d: %s\n", t.ID, t.Payload)
	}

	// Воркер 2 берет следующую пачку без блокировки
	tasks2, _ := FetchAndLockTasks(ctx, db, 2, 2)
	fmt.Printf("✔ [Воркер 2] Мгновенно захватил следующую свободную задачу:\\n")
	for _, t := range tasks2 {
		fmt.Printf("  • ID %d: %s\n", t.ID, t.Payload)
	}
}
```

## Под капотом

`SKIP LOCKED` инструктирует ядро PostgreSQL: «Если строка уже заблокирована параллельной транзакцией, не жди — просто пропусти её». Воркеры никогда не блокируют друг друга.

## Подводные камни

Если забыть `ORDER BY id ASC`, порядок выборки строк будет случайным, нарушая FIFO очередность.

## На собеседовании

**Вопрос с собеседования:** «Почему FOR UPDATE SKIP LOCKED лучше Redis или RabbitMQ для критичных фоновых задач?»
**Ответ:** Транзакционность (Transactional Outbox): создание задачи в таблице `task_queue` происходит в той же ACID-транзакции, что и изменение основных бизнес-сущностей (например, оформление заказа и постановка задачи на списание со склада). Исключена ситуация, когда заказ создался, а задача в RabbitMQ не отправилась из-за сбоя сети.
