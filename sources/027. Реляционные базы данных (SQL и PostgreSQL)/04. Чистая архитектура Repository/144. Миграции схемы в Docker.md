# Миграции схемы в Docker: паттерн Init-контейнера и миграционного контейнера

## Условие

Добавьте миграции в Dockerfile вашего приложения, опишите запуск отдельного init-контейнера для миграций перед запуском основного сервиса.

### Исходная формулировка

Добавьте миграции в Dockerfile вашего приложения, чтобы они применялись автоматически перед запуском бинарника (через `ENTRYPOINT` скрипт).

## Теория

Паттерн Kubernetes Init Container:
В Cloud Native архитектуре миграции базы данных запускаются отдельным Job или `initContainers` в Pod спецификации K8s. Основной веб-сервер стартует ТОЛЬКО после успешного завершения мигратора.

## Решение по шагам

1. Опишем легковесный Dockerfile для запуска `migrate`.
2. Опишем `docker-compose.yml` с зависимостью `depends_on: { migrate: { condition: service_completed_successfully } }`.
3. Продемонстрируем порядок старта.

## Код решения

**`docker-compose.yml`**

```yaml
version: '3.8'

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: secretpassword
      POSTGRES_DB: appdb
    ports:
      - "5432:5432"

  # Контейнер-мигратор: выполняет DDL и завершает работу
  migrator:
    image: migrate/migrate:v4.17.0
    volumes:
      - ./migrations:/migrations
    command:
      - -path=/migrations
      - -database=postgres://postgres:secretpassword@postgres:5432/appdb?sslmode=disable
      - up
    depends_on:
      - postgres

  # Основной Go сервис: ждет успешного завершения мигратора
  api-service:
    build: .
    ports:
      - "8080:8080"
    depends_on:
      migrator:
        condition: service_completed_successfully
```

**`main.go`**

```go
package main

import "fmt"

func main() {
	fmt.Println("✔ Сервис запущен: схема базы данных гарантированно готова и актуальна!")
}
```

## Под капотом

Свойство `service_completed_successfully` в Docker Compose блокирует старт сервиса до выхода мигратора с кодом 0.

## Подводные камни

Запуск миграций внутри каждого пода веб-сервера может вызвать состояние гонки (Race Condition).

## На собеседовании

**Вопрос с собеседования:** «Как организовать откат релиза в Kubernetes, если миграция схемы несовместима со старой версией сервиса?»
**Ответ:** Этого допускать нельзя. Применяется паттерн двухфазных обратно-совместимых миграций (Expand-Contract): схема базы должна поддерживать одновременно и старую (N-1), и новую (N) версии кода. Удаление старых колонок происходит только в релизе N+1.
