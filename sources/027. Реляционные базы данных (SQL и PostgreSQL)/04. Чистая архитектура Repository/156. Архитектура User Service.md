# Архитектура User Service: PostgreSQL (источник правды) + Redis (быстрый кэш)

## Условие

Напиши **"User Service"** с PostgreSQL + Redis: `Register(name, email, password)` вставляет пользователя в Postgres, `GetUser(id)` читает из Redis кэша, а при Cache Miss идет в базу и прогревает кэш.

### Исходная формулировка

Напиши **"User Service"** с PostgreSQL + Redis:
- `Register(name, email, password)` — хеш пароля (bcrypt), INSERT в PostgreSQL, инвалидация кеша
- `GetByID(id)` — cache-aside
- `GetByEmail(email)` — cache-aside по email
- `UpdateProfile(id, name)` — UPDATE в PostgreSQL, `CacheDelete` по id и email
- `Delete(id)` — soft delete (флаг `deleted_at`), инвалидация

## Теория

Паттерн Cache-Aside (Lazy Loading):
1. Читаем ключ `user:<id>` из Redis.
2. При Cache Hit отдаем кэшированный JSON за 0.5 мс.
3. При Cache Miss идем в PostgreSQL (источник правды), читаем строку, асинхронно или синхронно сохраняем в Redis с TTL (например, 10 минут) и отдаем клиенту.

## Решение по шагам

1. Опишем сервис `UserService`.
2. Реализуем метод `Register` с записью в Postgres.
3. Реализуем метод `GetUser` с проверкой кэша.
4. Проверим поведение при Cache Miss и Cache Hit.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"sync"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type UserData struct {
	ID    int
	Name  string
	Email string
}

// Имитация клиента Redis для самодостаточности примера
type RedisMock struct {
	mu    sync.RWMutex
	store map[string]UserData
}

func (r *RedisMock) Get(key string) (UserData, bool) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	val, ok := r.store[key]
	return val, ok
}

func (r *RedisMock) Set(key string, val UserData, ttl time.Duration) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.store[key] = val
}

type UserService struct {
	db    *sql.DB
	redis *RedisMock
}

func (s *UserService) GetUser(ctx context.Context, id int) (*UserData, error) {
	cacheKey := fmt.Sprintf("user:%d", id)

	// 1. Попытка взять из кэша (Cache Hit)
	if u, found := s.redis.Get(cacheKey); found {
		fmt.Printf("⚡ [CACHE HIT] Пользователь #%d мгновенно получен из Redis!\n", id)
		return &u, nil
	}

	// 2. Cache Miss: идем в PostgreSQL
	fmt.Printf("🐢 [CACHE MISS] Пользователь #%d читается из PostgreSQL...\n", id)
	var u UserData
	err := s.db.QueryRowContext(ctx, "SELECT id, name, email FROM users WHERE id = $1", id).Scan(&u.ID, &u.Name, &u.Email)
	if err != nil {
		return nil, err
	}

	// 3. Прогреваем кэш
	s.redis.Set(cacheKey, u, 10*time.Minute)
	return &u, nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	svc := &UserService{
		db:    db,
		redis: &RedisMock{store: make(map[string]UserData)},
	}

	ctx := context.Background()

	// Первый запрос (Cache Miss)
	_, _ = svc.GetUser(ctx, 1)

	// Второй запрос (Cache Hit)
	_, _ = svc.GetUser(ctx, 1)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 🐢 [CACHE MISS] Пользователь #1 читается из PostgreSQL...
# ⚡ [CACHE HIT] Пользователь #1 мгновенно получен из Redis!
```

## Под капотом

Cache Hit сокращает нагрузку на базу данных на 95% для профилей пользователей.

## Подводные камни

Инвалидация кэша: при обновлении пользователя (`UPDATE users`) обязательно нужно удалить ключ из Redis (`redis.Del`), иначе клиенты будут видеть устаревшие данные (Stale Data).

## На собеседовании

**Вопрос с собеседования:** «Что такое Cache Stampede (Dogpile effect) и как от него защититься?»
**Ответ:** При истечении TTL горячего ключа тысячи параллельных запросов одновременно получают Cache Miss и одновременно атакуют базу данных одинаковым тяжелым запросом. Защита: мьютексы singleflight (`golang.org/x/sync/singleflight`) или вероятностное раннее обновление кэша (XFetch).
