# Транзакционные интеграционные тесты: автоматический откат Rollback после каждого теста

## Условие

**Транзакционные тесты**: Реализуйте паттерн, где каждый интеграционный тест стартует транзакцию, выполняет любые изменения в реальной БД и откатывает её в `defer tx.Rollback()`, сохраняя базу абсолютно чистой.

### Исходная формулировка

**Транзакционные тесты**: Реализуйте паттерн, где каждый тест стартует транзакцию, выполняет действия, а в `defer` делает `ROLLBACK`. Это гарантирует, что каждый тест начинается с абсолютно чистой БД без затрат на очистку таблиц.

## Теория

Паттерн Transactional Test Isolation:
Вместо долгой очистки таблиц (`TRUNCATE CASCADE`) после каждого теста, тест выполняется внутри `tx, _ := db.Begin()`.
В конце теста вызывается `defer tx.Rollback()`.
Все добавленные и измененные строки мгновенно исчезают, а база остается девственно чистой для следующего параллельного теста!

## Решение по шагам

1. Откроем транзакцию в начале теста.
2. Передадим `tx` в тестируемый репозиторий.
3. Вставим тестовые данные и выполним assertions.
4. Вызовем отложенный откат `tx.Rollback()`.
5. Убедимся, что данные не сохранились.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func RunTransactionalTest(db *sql.DB) {
	// 1. Старт транзакции
	tx, err := db.Begin()
	if err != nil {
		panic(err)
	}
	// 2. Гарантированный откат в конце теста
	defer tx.Rollback()

	// 3. Тест выполняет вставки в реальную базу
	_, err = tx.Exec("INSERT INTO users (name, email) VALUES ('Тест Изоляции', 'tx_test@ya.ru')")
	if err != nil {
		panic(err)
	}

	var countInside int
	_ = tx.QueryRow("SELECT count(*) FROM users WHERE email = 'tx_test@ya.ru'").Scan(&countInside)
	fmt.Printf("Внутри транзакции теста запись видна: count = %d\n", countInside)

	// Здесь функция завершается, срабатывает defer tx.Rollback()
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	RunTransactionalTest(db)

	// Проверяем состояние базы снаружи
	var countOutside int
	_ = db.QueryRow("SELECT count(*) FROM users WHERE email = 'tx_test@ya.ru'").Scan(&countOutside)

	fmt.Printf("Снаружи теста после Rollback: count = %d\n", countOutside)
	if countOutside == 0 {
		fmt.Println("✔ База данных осталась абсолютно чистой! Паттерн отработал безупречно!")
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Внутри транзакции теста запись видна: count = 1
# Снаружи теста после Rollback: count = 0
# ✔ База данных осталась абсолютно чистой! Паттерн отработал безупречно!
```

## Под капотом

Откат транзакции освобождает все блокировки и помечает статус транзакции как `ABORTED`, делая очистку моментальной (\(O(1)\)).

## Подводные камни

Паттерн неприменим, если тестируемый бизнес-метод сам управляет жизненным циклом транзакции (`db.Begin`).

## На собеседовании

**Вопрос с собеседования:** «Почему транзакционные тесты работают быстрее очистки через TRUNCATE?»
**Ответ:** `TRUNCATE` захватывает тяжелый `AccessExclusiveLock`, сбрасывает счетчики и форсирует создание новых файлов сегментов на диске. Откат транзакции (`ROLLBACK`) просто меняет статус транзакции в оперативной памяти `pg_xact`, выполняясь за доли миллисекунды.
