# Ликвидация проблемы N+1 запросов: объединение через JOIN и слайсы WHERE IN

## Условие

**Проблема N+1**: Напишите код, который демонстрирует проблему N+1 запросов при выборке авторов и их постов. Перепишите его на один запрос с `JOIN`.

### Исходная формулировка

**Проблема N+1**: Напишите код, который получает список постов, а затем в цикле делает `GetUserByID` для каждого автора. "Вылечите" это, написав один `JOIN` запрос или используя `sqlc` с батчингом.

## Теория

Антипаттерн N+1:
При выборке 100 пользователей код делает 1 запрос на пользователей, а затем в цикле 100 отдельных запросов за их постами: итого \(1 + 100 = 101\) сетевой раундтрип!
Решение: один запрос с `LEFT JOIN` или один запрос `WHERE user_id IN ($1, $2, ...)`.

## Решение по шагам

1. Продемонстрируем неоптимальный подход N+1.
2. Напишем оптимальный единый SQL запрос с `LEFT JOIN`.
3. Сгруппируем посты по пользователям в памяти Go.
4. Замерим сокращение сетевых запросов.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type Post struct {
	ID    int
	Title string
}

type UserWithPosts struct {
	ID    int
	Name  string
	Posts []Post
}

func FetchUsersWithPostsOptimal(db *sql.DB) ([]UserWithPosts, error) {
	// Решение N+1: ровно 1 запрос с JOIN вместо сотен раундтрипов!
	query := `
	SELECT u.id, u.name, p.id, COALESCE(p.title, '')
	FROM users u
	LEFT JOIN posts p ON p.id = u.id
	WHERE u.id <= 3
	ORDER BY u.id ASC;`

	rows, err := db.Query(query)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	userMap := make(map[int]*UserWithPosts)
	var order []int

	for rows.Next() {
		var uID, pID sql.NullInt64
		var uName, pTitle string
		_ = rows.Scan(&uID, &uName, &pID, &pTitle)

		id := int(uID.Int64)
		if _, exists := userMap[id]; !exists {
			userMap[id] = &UserWithPosts{ID: id, Name: uName}
			order = append(order, id)
		}

		if pID.Valid {
			userMap[id].Posts = append(userMap[id].Posts, Post{ID: int(pID.Int64), Title: pTitle})
		}
	}

	result := make([]UserWithPosts, len(order))
	for i, id := range order {
		result[i] = *userMap[id]
	}
	return result, nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	users, err := FetchUsersWithPostsOptimal(db)
	if err != nil {
		panic(err)
	}

	fmt.Println("✔ Проблема N+1 ликвидирована: все авторы и посты выбраны за 1 запрос!")
	for _, u := range users {
		fmt.Printf("  • Пользователь [%s] (Постов: %d)\n", u.Name, len(u.Posts))
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:

#   • Пользователь [Алексей (Обновлен)] (Постов: 1)
#   • Пользователь [Ольга] (Постов: 0)
#   • Пользователь [Сергей Петров] (Постов: 0)
```

## Под капотом

СУБД выполняет `Hash Left Join` в оперативной памяти за один проход.

## Подводные камни

При выборке родителей со множеством потомков `LEFT JOIN` дублирует данные родителя в каждой строке, раздувая трафик. В таких случаях делают ровно 2 запроса: один за родителями, второй `WHERE parent_id IN (...)` за детьми.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисах предпочитают делать 2 запроса (WHERE IN) вместо одного огромного JOIN с 5 таблицами?»
**Ответ:** Декартово произведение (Cartesian Product): при JOIN 5 таблиц с отношениями One-to-Many размер сетевого ответа экспоненциально разрастается дублирующимися полями. Два-три раздельных запроса с `IN (...)` передают в разы меньше байт по сети и эффективнее кэшируются.
