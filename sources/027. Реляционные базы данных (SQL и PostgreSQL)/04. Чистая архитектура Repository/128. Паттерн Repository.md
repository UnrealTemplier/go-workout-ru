# Паттерн Repository: изоляция слоя работы с данными через интерфейс UserRepository

## Условие

Напиши **"repository pattern"** вручную: интерфейс `UserRepository` с методами `Create(user)` и `GetByID(id)`. Реализуй его для PostgreSQL.

### Исходная формулировка

Напиши **"repository pattern"** вручную: интерфейс `UserRepository` с методами `Create`, `GetByID`, `List`, `Update`, `Delete`. Реализация `PostgresUserRepository` через `*sql.DB`. Покажи, что бизнес-логика не зависит от БД.

## Теория

Архитектурный паттерн Repository:
Слой бизнес-логики (Use Cases / Services) не должен знать о деталях SQL, таблицах и сокетах.
Интерфейс репозитория инкапсулирует доступ к данным, позволяя легко подменять реализацию базы данных на In-Memory хранилище в юнит-тестах.

## Решение по шагам

1. Объявим интерфейс `UserRepository`.
2. Реализуем структуру `PostgresUserRepository`.
3. Создадим методы `Create` и `GetByID`.
4. Проверим вызовы через интерфейс.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type UserEntity struct {
	ID    int
	Name  string
	Email string
}

type UserRepository interface {
	Create(ctx context.Context, u *UserEntity) error
	GetByID(ctx context.Context, id int) (*UserEntity, error)
}

type PostgresUserRepository struct {
	db *sql.DB
}

func NewPostgresUserRepository(db *sql.DB) *PostgresUserRepository {
	return &PostgresUserRepository{db: db}
}

func (r *PostgresUserRepository) Create(ctx context.Context, u *UserEntity) error {
	query := "INSERT INTO users (name, email) VALUES ($1, $2) RETURNING id"
	return r.db.QueryRowContext(ctx, query, u.Name, u.Email).Scan(&u.ID)
}

func (r *PostgresUserRepository) GetByID(ctx context.Context, id int) (*UserEntity, error) {
	var u UserEntity
	query := "SELECT id, name, email FROM users WHERE id = $1"
	err := r.db.QueryRowContext(ctx, query, id).Scan(&u.ID, &u.Name, &u.Email)
	if err != nil {
		return nil, err
	}
	return &u, nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ctx := context.Background()
	// Сервис работает со строгим интерфейсом UserRepository
	var repo UserRepository = NewPostgresUserRepository(db)

	newUser := &UserEntity{Name: "Репозиторий Тест", Email: "repo@ya.ru"}
	_ = repo.Create(ctx, newUser)
	fmt.Printf("✔ Пользователь создан через Repository: ID=%d\n", newUser.ID)

	fetched, _ := repo.GetByID(ctx, newUser.ID)
	fmt.Printf("✔ Пользователь прочитан через Repository: %s (%s)\n", fetched.Name, fetched.Email)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Пользователь создан через Repository: ID=10
# ✔ Пользователь прочитан через Repository: Репозиторий Тест (repo@ya.ru)
```

## Под капотом

Интерфейс в Go удовлетворяется неявно (Duck Typing), что исключает жесткую связность пакетов.

## Подводные камни

Утечка SQL-типов в интерфейс (например, возврат `*sql.Rows` из репозитория) нарушает инкапсуляцию.

## На собеседовании

**Вопрос с собеседования:** «Где в чистой архитектуре (Clean Architecture) должен объявляться интерфейс репозитория?»
**Ответ:** Интерфейс репозитория должен объявляться в слое бизнес-логики (Domain / UseCase слой), которому он требуется (Dependency Inversion Principle). Слой базы данных (Infrastructure) находится снаружи и лишь реализует этот интерфейс.
