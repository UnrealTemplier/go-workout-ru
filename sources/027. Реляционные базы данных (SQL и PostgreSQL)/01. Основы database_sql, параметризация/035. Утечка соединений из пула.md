# Утечка соединений из пула: почему defer rows.Close() критически обязателен

## Условие

**defer rows.Close()**: Объясни, почему `defer rows.Close()` ОБЯЗАТЕЛЕН (утечка соединений из пула). Напиши пример.

### Исходная формулировка

**Каверзный случай: sql.ErrNoRows**: Запроси из упр. 370 несуществующий ID. Убедись, что `Scan` возвращает ошибку. Сравни её строго: `if errors.Is(err, sql.ErrNoRows) { fmt.Println("Юзер не найден") }`.

## Теория

Механика исчерпания пула соединений (Pool Exhaustion):
Каждый `*sql.Rows` держит монопольную блокировку на одном конкретном физическом TCP-соединении.
Если пул настроен на `MaxOpenConns = 10`, и в 10 HTTP-запросах разработчик забыл вызвать `rows.Close()`, все 10 соединений останутся занятыми навечно. 11-й запрос заблокируется в ожидании свободного сокета, и сервис полностью зависнет.

## Решение по шагам

1. Настроим базу с жестким лимитом `SetMaxOpenConns(2)`.
2. Покажем, как правильный `defer rows.Close()` моментально возвращает сокет.
3. Продемонстрируем повторное использование сокета.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func queryWithCleanClose(db *sql.DB) {
	rows, err := db.Query("SELECT 1")
	if err != nil {
		panic(err)
	}
	defer rows.Close() // Возвращает сокет в пул при выходе из функции
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Ограничиваем пул ровно 1 соединением
	db.SetMaxOpenConns(1)

	// Выполняем 10 последовательных запросов на 1 сокете
	for i := 1; i <= 5; i++ {
		queryWithCleanClose(db)
		stats := db.Stats()
		fmt.Printf("Запрос #%d: В использовании: %d, В пуле: %d\n",
			i, stats.InUse, stats.Idle)
	}

	fmt.Println("✔ Пул работает стабильно: соединения мгновенно возвращаются!")
}
```

**`Терминал`**

```bash

# Запрос #2: В использовании: 0, В пуле: 1

# Запрос #4: В использовании: 0, В пуле: 1

```

## Под капотом

`db.Stats().InUse` показывает количество соединений, занятых активными запросами или незакрытыми `*sql.Rows`.

## Подводные камни

Вызов `rows.Close()` вручную в конце функции без `defer` опасен: если внутри цикла произойдет ранний `return` по ошибке, вызов `Close()` пропустится, и сокет утечет.

## На собеседовании

**Вопрос с собеседования:** «Закрывается ли rows автоматически, если цикл for rows.Next() дошел до конца?»
**Ответ:** Да, стандартный рантайм `database/sql` закрывает `rows`, если `rows.Next()` вернул `false` по причине EOF. Однако полагаться на это категорически нельзя: если вы выйдете из цикла через `break` или вернете ошибку `return err` на середине, сокет утечет. Поэтому `defer rows.Close()` обязателен всегда!
