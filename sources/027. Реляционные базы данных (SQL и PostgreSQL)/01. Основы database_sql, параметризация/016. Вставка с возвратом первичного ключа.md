# Вставка с возвратом первичного ключа: конструкция RETURNING id против LastInsertId

## Условие

**Вставка с возвратом ID (RETURNING id)**: Вставь пользователя и получи его сгенерированный `id` через `db.QueryRow("INSERT ... RETURNING id", ...).Scan(&id)`. Объясни, почему `result.LastInsertId()` в PostgreSQL НЕ РАБОТАЕТ!

### Исходная формулировка

Напиши функцию `UpdateUserEmail(id int, email string) error`. Используй `db.Exec`. Проверь `RowsAffected()` — если 0, верни `sql.ErrNoRows` или кастомную ошибку `"user not found"`.

## Теория

Критическая архитектурная особенность PostgreSQL:
В драйвере PostgreSQL метод `result.LastInsertId()` ВСЕГДА возвращает ошибку:
`LastInsertId is not supported by this driver`.
Причина: архитектура PostgreSQL позволяет таблицам иметь составные ключи, UUID, генерацию через триггеры или вообще не иметь суррогатных автоинкрементов.
Единственный идиоматический способ получить ID созданной строки в PostgreSQL — суффикс `RETURNING id` в паре с `db.QueryRow`.

## Решение по шагам

1. Напишем SQL запрос с предложением `RETURNING id`.
2. Вызовем метод `db.QueryRow(query, args...)`.
3. Отсканируем результат напрямую в переменную `&id` через `.Scan(&id)`.
4. Убедимся в получении сгенерированного ID.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Демонстрация 1: Ошибка LastInsertId в PostgreSQL
	res, _ := db.Exec("INSERT INTO users (name, age, email) VALUES ($1, $2, $3)", "Иван", 30, "ivan@ya.ru")
	if res != nil {
		_, err := res.LastInsertId()
		fmt.Printf("[LastInsertId Check] Ожидаемая ошибка: %v\n", err)
	}

	// Демонстрация 2: Идиоматичный способ через RETURNING id
	var newID int
	query := `INSERT INTO users (name, age, email) VALUES ($1, $2, $3) RETURNING id`

	err := db.QueryRow(query, "Ольга", 27, "olga@ya.ru").Scan(&newID)
	if err != nil {
		fmt.Printf("Ошибка получения ID: %v\n", err)
		return
	}

	fmt.Printf("✔ Успешно вставлен пользователь! Сгенерированный ID = %d\n", newID)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [LastInsertId Check] Ожидаемая ошибка: LastInsertId is not supported by this driver
# ✔ Успешно вставлен пользователь! Сгенерированный ID = 42
```

## Под капотом

Конструкция `RETURNING` в PostgreSQL передается ядром базы в виде стандартного результирующего набора строк (Tuple), что позволяет сканировать его через обычный `QueryRow().Scan()`.

## Подводные камни

Если использовать `db.Exec` с запросом, содержащим `RETURNING id`, запрос выполнится, но возвращенный ID будет отброшен и потерян.

## На собеседовании

**Вопрос с собеседования:** «Почему в MySQL LastInsertId работает, а в PostgreSQL — нет?»
**Ответ:** MySQL хранит глобальный счетчик `LAST_INSERT_ID()` для соединения и возвращает его в пакете OK. PostgreSQL поддерживает произвольные типы первичных ключей (UUID, текстовые ключи, составные PK), поэтому не имеет глобального автоинкрементного счетчика сессии и требует явного указания `RETURNING <column>`.
