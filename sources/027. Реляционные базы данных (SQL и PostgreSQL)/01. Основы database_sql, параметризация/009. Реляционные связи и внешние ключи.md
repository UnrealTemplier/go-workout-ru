# Реляционные связи и внешние ключи: связывание users и orders через FOREIGN KEY

## Условие

**CREATE TABLE**: Создай таблицы `users` и `orders (id SERIAL PRIMARY KEY, user_id INT REFERENCES users(id), amount NUMERIC(10, 2), status TEXT)`. Проверь через `db.Exec`.

### Исходная формулировка

Изучите `sql.DB` как пул соединений. Настройте `SetMaxOpenConns`, `SetMaxIdleConns` и `SetConnMaxLifetime`. Объясните, почему `ConnMaxLifetime` критически важен для балансировщиков нагрузки и корректного сброса состояния сессий.

## Теория

Ограничение внешнего ключа (FOREIGN KEY):
`REFERENCES users(id) ON DELETE CASCADE` обеспечивает ссылочную целостность базы данных. СУБД физически запрещает создать заказ для несуществующего `user_id` и может автоматически удалять связанные заказы при удалении пользователя.

## Решение по шагам

1. Создадим таблицу пользователей `users`.
2. Создадим таблицу заказов `orders` с внешним ключом `REFERENCES users(id)`.
3. Проверим успешность выполнения пакета DDL команд.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	schema := `
	CREATE TABLE IF NOT EXISTS users (
		id SERIAL PRIMARY KEY,
		name TEXT NOT NULL
	);

	CREATE TABLE IF NOT EXISTS orders (
		id SERIAL PRIMARY KEY,
		user_id INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
		amount NUMERIC(10, 2) NOT NULL,
		status TEXT NOT NULL DEFAULT 'new'
	);`

	if _, err := db.Exec(schema); err != nil {
		fmt.Printf("Ошибка схемы: %v\n", err)
		return
	}

	fmt.Println("✔ Схема 'users -> orders' с внешним ключом успешно создана!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Схема 'users -> orders' с внешним ключом успешно создана!
```

## Под капотом

Внешний ключ `FOREIGN KEY` в PostgreSQL создает триггер проверки целостности на системном уровне, проверяющий наличие записи в индексе первичного ключа родительской таблицы.

## Подводные камни

Внешний ключ не создает индекс на поле `user_id` в таблице `orders` автоматически! Для быстрого поиска заказов по пользователю и предотвращения блокировок при каскадном удалении необходимо явно создать `CREATE INDEX idx_orders_user_id ON orders(user_id)`.

## На собеседовании

**Вопрос с собеседования:** «Почему в HighLoad системах иногда отказываются от FOREIGN KEY на уровне СУБД?»
**Ответ:** В шардированных базах данных (Citus, Vitess) данные пользователей и заказов могут лежать на физически разных серверах, где распределенный foreign key невозможен или создает чудовищный сетевой оверхед. Проверку целостности переносят на прикладной уровень микросервисов.
