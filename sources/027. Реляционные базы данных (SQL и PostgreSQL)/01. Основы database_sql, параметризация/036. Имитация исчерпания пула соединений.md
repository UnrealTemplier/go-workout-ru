# Имитация исчерпания пула соединений при пропущенном rows.Close

## Условие

**Утечка соединений**: Покажи, что произойдет, если не закрывать `rows` (пул исчерпается и приложение зависнет).

### Исходная формулировка

Реализуйте `DELETE` (soft delete через флаг `is_deleted` и hard delete).

## Теория

Воспроизведение дедлока пула:
Зададим `MaxOpenConns = 1`. Если открыть `rows` и не закрыть его, следующий запрос к `db.Query` заблокируется в ожидании освобождения сокета до истечения таймаута.

## Решение по шагам

1. Установим `db.SetMaxOpenConns(1)`.
2. Вызовем первый `db.Query` БЕЗ вызова `rows.Close()`.
3. Попытаемся выполнить второй запрос с таймаутом контекста.
4. Поймаем дедлок пула `context deadline exceeded`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	// Намеренно ставим лимит ровно в 1 физическое соединение
	db.SetMaxOpenConns(1)

	// 1. Первый запрос: НАМЕРЕННО НЕ ЗАКРЫВАЕМ rows!
	rows1, err := db.Query("SELECT 1")
	if err != nil {
		panic(err)
	}
	// defer rows1.Close() // ЗАБЫЛИ ЗАКРЫТЬ!
	_ = rows1

	fmt.Printf("[Leak Demo] Соединение захвачено. Stats.InUse = %d\n", db.Stats().InUse)

	// 2. Второй запрос пытается взять соединение из пула
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	fmt.Println("[Leak Demo] Пытаемся сделать второй запрос к базе...")
	_, err2 := db.QueryContext(ctx, "SELECT 2")
	if err2 != nil {
		fmt.Printf("✔ ОЖИДАЕМЫЙ ДЕДЛОК ПУЛА: Запрос завис и упал по таймауту: %v\n", err2)
	}

	// Освобождаем первое соединение для чистоты
	_ = rows1.Close()
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Leak Demo] Соединение захвачено. Stats.InUse = 1
# [Leak Demo] Пытаемся сделать второй запрос к базе...
# ✔ ОЖИДАЕМЫЙ ДЕДЛОК ПУЛА: Запрос завис и упал по таймауту: context deadline exceeded
```

## Под капотом

Внутри `sql.DB` горутина, запросившая соединение, встает в очередь ожидания канала `connRequest chan connRequest`. Если соединение не освобождается, горутина спит до отмены контекста.

## Подводные камни

В микросервисах без таймаутов контекста утечка соединений приводит к зависанию сотен горутин в статусе `select`, исчерпанию оперативной памяти и краху сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как выявить утечку соединений базы данных в Kubernetes?»
**Ответ:** По графикам метрик Prometheus экспортера `go_sql_db_connections_in_use`. Если график линейно растет и достигает `max_open_connections`, а `wait_count` и задержки запросов взлетают до потолка — в коде есть незакрытые `*sql.Rows` или незавершенные транзакции `*sql.Tx`.
