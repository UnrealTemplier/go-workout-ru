# Анатомия rows.Err: почему проверки ошибки db.Query недостаточно

## Условие

**rows.Err()**: Объясни, почему проверки `err` от `db.Query` НЕДОСТАТОЧНО и ОБЯЗАТЕЛЬНО проверять `rows.Err()` после цикла `for rows.Next()`. Напиши правильный код.

### Исходная формулировка

Напиши функцию `SearchUsers(namePattern string) ([]User, error)` с `ILIKE` (case-insensitive like): `WHERE name ILIKE $1`. Передай `"%" + namePattern + "%"`. Обработай SQL-инъекцию — покажи, что placeholder'ы (`$1`) защищают.

## Теория

Природа сетевой модели `database/sql`:
Вызов `db.Query` лишь отправляет запрос и ждет ответа с описанием колонок (`RowDescription`). Сами строки передаются потоком по TCP.
Если на 500-й строке из 10 000 база данных упадет, сетевой кабель оборвется или сработает таймаут, цикл `for rows.Next()` просто вернет `false`! Без проверки `rows.Err()` приложение посчитает, что выборка завершилась успешно, потеряв половину данных.

## Решение по шагам

1. Напишем функцию с образцовой обработкой ошибок.
2. Продемонстрируем место возникновения сетевых ошибок.
3. Проверим `rows.Err()` сразу после цикла.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"log"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func SafeQuery(db *sql.DB) error {
	rows, err := db.Query("SELECT id, name FROM users")
	if err != nil {
		// Ошибка на этапе отправки запроса или синтаксиса SQL
		return fmt.Errorf("initial query failed: %w", err)
	}
	defer rows.Close()

	count := 0
	for rows.Next() {
		var id int
		var name string
		if err := rows.Scan(&id, &name); err != nil {
			// Ошибка несовместимости типов в конкретной строке
			return fmt.Errorf("scan failed: %w", err)
		}
		count++
	}

	// КРИТИЧЕСКИ ВАЖНО: проверка сетевых сбоев стрима
	if err := rows.Err(); err != nil {
		return fmt.Errorf("stream interrupted: %w", err)
	}

	fmt.Printf("✔ Успешно вычитано без сетевых разрывов: %d строк\n", count)
	return nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	if err := SafeQuery(db); err != nil {
		log.Fatalf("Сбой: %v", err)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Успешно вычитано без сетевых разрывов: 3 строк
```

## Под капотом

Внутри `rows.Next()` ошибка сетевого сокета перехватывается и сохраняется в скрытое поле `rows.lasterr`. Вызов `rows.Err()` возвращает это значение.

## Подводные камни

Игнорирование `rows.Err()` — классический баг финансовых систем, когда отчет генерируется неполным из-за оборвавшейся сессии, а система не сообщает об ошибке.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях rows.Next() возвращает false?»
**Ответ:** 1. Все строки успешно вычитаны до конца (EOF). 2. Сработал таймаут контекста `ctx.Done()`. 3. Разорвалось сетевое TCP-соединение с СУБД. 4. Произошла ошибка десериализации типа на уровне драйвера.
