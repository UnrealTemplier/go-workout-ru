# Чистая архитектура работы с курсорами строк: чек-лист проверок

## Условие

**Зачем rows.Err()**: Напиши комментарий и код с правильной обработкой всех краевых случаев выборки.

### Исходная формулировка

Напиши функцию `GetUsersPaginated(page, pageSize int) ([]User, int, error)`. Используй `LIMIT $1 OFFSET $2` для пагинации. Верни общее количество через `SELECT COUNT(*)`. Обработай `pageSize > 100` — ограничь максимум.

## Теория

Чек-лист идеальной работы со строками в `database/sql`:
1. `QueryContext` вместо `Query`.
2. Проверка ошибки `if err != nil`.
3. Немедленный `defer rows.Close()`.
4. Проверка ошибки `Scan` внутри цикла.
5. Проверка `rows.Err()` после цикла.

## Решение по шагам

1. Оформим эталонный сниппет.
2. Прокомментируем назначение каждого блока.
3. Проверим компиляцию и выполнение.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

// GoldStandardQuery демонстрирует эталонный порядок работы с курсором
func GoldStandardQuery(ctx context.Context, db *sql.DB) ([]string, error) {
	// 1. Запрос с контекстом (защита от зависаний)
	rows, err := db.QueryContext(ctx, "SELECT name FROM users")
	if err != nil {
		return nil, fmt.Errorf("query: %w", err)
	}
	// 2. Гарантированный возврат сокета в пул при любом выходе из функции
	defer rows.Close()

	var names []string
	for rows.Next() {
		var name string
		// 3. Проверка десериализации строки
		if err := rows.Scan(&name); err != nil {
			return nil, fmt.Errorf("scan: %w", err)
		}
		names = append(names, name)
	}

	// 4. Проверка ошибок сети/таймаута, возникших во время чтения потока
	if err := rows.Err(); err != nil {
		return nil, fmt.Errorf("stream: %w", err)
	}

	return names, nil
}

func main() {
	dsn := "postgres://postgres:postgres@localhost:5432/testdb?sslmode=disable"
	db, _ := sql.Open("pgx", dsn)
	defer db.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	names, err := GoldStandardQuery(ctx, db)
	if err != nil {
		panic(err)
	}
	fmt.Printf("✔ Имена пользователей (%d): %v\n", len(names), names)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# ✔ Имена пользователей (3): [Алексей Смирнов Ольга Сергей Петров]
```

## Под капотом

`defer rows.Close()` идемпотентен: повторный вызов закрытия ничего не делает и безопасен.

## Подводные камни

Помещение `defer rows.Close()` ДО проверки `if err != nil` приведет к панике `nil pointer dereference`, если `rows == nil`!

## На собеседовании

**Вопрос с собеседования:** «Почему defer rows.Close() пишут строго ПОСЛЕ проверки if err != nil?»
**Ответ:** Если `db.Query` вернул ошибку, переменная `rows` равна `nil`. Вызов `rows.Close()` на nil-указателе вызовет фатальную панику рантайма (SIGSEGV). Поэтому сначала проверяют `err != nil`, и только убедившись, что `rows` валиден, вешают `defer`.
