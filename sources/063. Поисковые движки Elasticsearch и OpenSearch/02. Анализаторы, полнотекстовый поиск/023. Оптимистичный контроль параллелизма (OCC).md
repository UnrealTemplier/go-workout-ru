# Оптимистичный контроль параллелизма (OCC): seq_no и primary_term

## Условие

**CRUD operations**: Используйте `Index`, `Get`, `Update`, `Delete` API. Изучите `versioning` для optimistic concurrency control.

## Теория

При параллельном обновлении документов несколькими микросервисами возникает состояние гонки (Race Condition): сервис \(B\) может перезаписать изменения, внесенные миллисекундой ранее сервисом \(A\) (Lost Update Problem).

### Механизм Optimistic Concurrency Control в Elasticsearch:
Каждый документ сопровождается метаданными:
- `_seq_no` (Sequence Number): Порядковый номер изменения на данном шарде.
- `_primary_term`: Номер эпохи первичного шарда (меняется при смене мастера).

При отправке `_update` клиент передает ожидаемые значения `if_seq_no` и `if_primary_term`. Если за время раздумий клиента документ был изменен параллельным процессом, Elasticsearch вернет ошибку `409 Conflict`, защищая данные от перезаписи!

## Решение по шагам

1. Получите текущий документ и его `_seq_no` и `_primary_term`.
2. Сымитируйте параллельное обновление документа другим процессом.
3. Попробуйте обновить документ с устаревшим `if_seq_no`.
4. Обработайте статус `409 Conflict` и повторите чтение-модификацию.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type DocMetadata struct {
	SeqNo       int `json:"_seq_no"`
	PrimaryTerm int `json:"_primary_term"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// 1. Создание исходного документа
	_, _ = esapi.IndexRequest{
		Index:      "articles",
		DocumentID: "10",
		Body:       strings.NewReader(`{"title": "Initial Version", "views": 1}`),
		Refresh:    "true",
	}.Do(ctx, es)

	// 2. Чтение документа и получение его версии
	getRes, _ := esapi.GetRequest{Index: "articles", DocumentID: "10"}.Do(ctx, es)
	var meta DocMetadata
	_ = json.NewDecoder(getRes.Body).Decode(&meta)
	getRes.Body.Close()
	fmt.Printf("Получен документ: seq_no=%d, primary_term=%d\n", meta.SeqNo, meta.PrimaryTerm)

	// 3. Параллельный процесс успел изменить документ
	_, _ = esapi.IndexRequest{
		Index:      "articles",
		DocumentID: "10",
		Body:       strings.NewReader(`{"title": "Updated by Concurrent Process", "views": 2}`),
		Refresh:    "true",
	}.Do(ctx, es)

	// 4. Попытка обновления с устаревшими seq_no (OCC проверка)
	conflictReq := esapi.IndexRequest{
		Index:        "articles",
		DocumentID:   "10",
		IfSeqNo:      &meta.SeqNo,
		IfPrimaryTerm: &meta.PrimaryTerm,
		Body:         strings.NewReader(`{"title": "Stale Update Attempt", "views": 3}`),
	}
	conflictRes, err := conflictReq.Do(ctx, es)
	if err != nil {
		panic(err)
	}
	defer conflictRes.Body.Close()

	if conflictRes.StatusCode == 409 {
		fmt.Println("УСПЕХ: Обнаружен конфликт версий (HTTP 409 Conflict). Потерянное обновление предотвращено!")
	} else {
		fmt.Printf("Неожиданный статус: %d\n", conflictRes.StatusCode)
	}
}
```

ℹ️ Предотвращение Lost Updates через if_seq_no и if_primary_term (OCC)

**`Терминал`**

```bash
go run main.go
# Получен документ: seq_no=15, primary_term=1
# УСПЕХ: Обнаружен конфликт версий (HTTP 409 Conflict). Потерянное обновление предотвращено!
```

## Под капотом

В старых версиях Elasticsearch использовалось поле `_version`, но оно не гарантировало строгой согласованности при сбоях первичных шардов. Смена на связку `_seq_no` (счетчик транзакций на шарде) и `_primary_term` (эпоха лидера) устраняет аномалии распределенного журнала в соответствии с протоколом согласованности PacificA.

## Подводные камни

При получении ошибки `409 Conflict` Go-приложение не должно паниковать: необходимо повторить цикл чтения актуального документа, наложить изменения и повторить попытку записи с новым `_seq_no`.

## На собеседовании

**Вопрос:** Как настроить автоматический повтор конфликтов версий на стороне сервера Elasticsearch?
**Ответ:** Передать параметр `retry_on_conflict = N` в запросе `_update`. Elasticsearch сам перезачитает документ и повторно исполнит скрипт Painless до \(N\) раз при возникновении конфликта версий.
