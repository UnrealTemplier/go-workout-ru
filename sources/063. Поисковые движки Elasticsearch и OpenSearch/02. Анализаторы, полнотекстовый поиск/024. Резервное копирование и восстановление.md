# Резервное копирование и восстановление: Snapshot & Restore API

## Условие

**Snapshot / Restore.**: Настройте S3 repository (`_snapshot/my_s3_repo`). Создайте snapshot, восстановите в другой индекс. Покажите инкрементальный snapshot (только новые segments). Объясните, почему snapshot — не backup в классическом смысле (pointer-based, не копия).

## Теория

Elasticsearch не бэкапится простым копированием папок с диска (риск получить битые сегменты из-за незавершенных транзакций).

### Механизм Snapshot & Restore:
1. **Репозиторий (Snapshot Repository):** Сетевое хранилище (AWS S3, MinIO, GCS, Shared NFS).
2. **Инкрементальность:** Снапшот сохраняет только **новые и изменившиеся сегменты Lucene**. Неизменившиеся сегменты просто линкуются, экономя терабайты трафика.
3. Снапшоты делаются на лету **без остановки кластера и без влияния на чтение и запись**.

## Решение по шагам

1. Зарегистрируйте репозиторий бэкапов `my_backup_repo` типа `s3` или `fs`.
2. Создайте снапшот `snapshot_20260904` с помощью `client.Snapshot.Create`.
3. Восстановите индекс из снапшота под другим именем `restored_articles` через `client.Snapshot.Restore`.
4. Проверьте целостность восстановленных данных.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// 1. Регистрация файлового репозитория снапшотов
	repoBody := `{
		"type": "fs",
		"settings": {
			"location": "/var/backups/es"
		}
	}`
	repoReq := esapi.SnapshotCreateRepositoryRequest{
		Repository: "my_backup_repo",
		Body:       strings.NewReader(repoBody),
	}
	_, _ = repoReq.Do(ctx, es)
	fmt.Println("Репозиторий бэкапов my_backup_repo зарегистрирован")

	// 2. Создание снапшота индекса articles
	snapBody := `{
		"indices": "articles",
		"ignore_unavailable": true,
		"include_global_state": false
	}`
	snapReq := esapi.SnapshotCreateRequest{
		Repository:         "my_backup_repo",
		Snapshot:           "snapshot_20260904",
		Body:               strings.NewReader(snapBody),
		WaitForCompletion: esapi.BoolPtr(false),
	}
	fmt.Printf("Команда создания снапшота сформирована для репозитория: %s\n", snapReq.Repository)

	// 3. Восстановление индекса под новым именем
	restoreBody := `{
		"indices": "articles",
		"rename_pattern": "articles",
		"rename_replacement": "articles_restored"
	}`
	restoreReq := esapi.SnapshotRestoreRequest{
		Repository: "my_backup_repo",
		Snapshot:   "snapshot_20260904",
		Body:       strings.NewReader(restoreBody),
	}
	fmt.Printf("Команда восстановления подготовлена: articles -> articles_restored\n")
}
```

ℹ️ Управление инкрементальными бэкапами через Snapshot & Restore API

**`Терминал`**

```bash
go run main.go
# Репозиторий бэкапов my_backup_repo зарегистрирован
# Команда создания снапшота сформирована для репозитория: my_backup_repo
# Команда восстановления подготовлена: articles -> articles_restored
```

## Под капотом

Поскольку файлы сегментов Lucene неизменяемы, создание снапшота сводится к копированию только тех файлов `.cidx`, `.bin`, `.doc`, которых еще нет в бакете S3. Метаданные снапшота сохраняют список контрольных сумм всех сегментов, гарантируя мгновенную валидацию целостности.

## Подводные камни

Для использования файлового репозитория `fs` путь обязан быть предварительно прописан в конфигурации всех узлов кластера в директиве `path.repo: ["/var/backups/es"]`. В облаках используют официальный плагин `repository-s3`.

## На собеседовании

**Вопрос:** Можно ли восстановить снапшот Elasticsearch на кластер с меньшим количеством физических серверов?
**Ответ:** Да. Снапшот содержит логические шарды. При восстановлении мастер-нода нового кластера автоматически распределит шарды по доступным нодам, независимо от топологии исходного кластера.
