# Сравнение структур данных: Text против Keyword и их влияние на память

## Условие

**Text vs Keyword**: Поймите ключевую разницу: `text` анализируется (для full-text search), `keyword` — нет (для filtering, aggregations, sorting).

## Теория

Понимание разницы между `text` и `keyword` — фундаментальное знание архитектора поисковых движков:

| Характеристика | Тип `text` | Тип `keyword` |
| :--- | :--- | :--- |
| **Анализ текста** | Проходит через Analyzer (токенизация, lowercase, стемминг) | Сохраняется как единый монолитный токен |
| **Структура хранения** | Инвертированный индекс (Inverted Index) | Doc Values (колоночный файл на диске) |
| **Основное назначение** | Полнотекстовый поиск (`match`, `query_string`) | Точная фильтрация (`term`), агрегации, сортировка |
| **Расчет релевантности** | Вычисляет BM25 `_score` | Score не вычисляется (Filter Context, кэшируется) |
| **Потребление RAM** | FST-словарь в памяти | Кэш страниц ОС (Page Cache), минимальный оверхед |

## Решение по шагам

1. Создайте таблицу с обоими типами: `description text`, `category keyword`.
2. Продемонстрируйте поведение точного запроса `term` по полю `text` (почему он часто ничего не находит).
3. Продемонстрируйте корректный поиск `term` по `keyword`.
4. Сравните скорость и поведение поиска.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	_ = esapi.IndicesDeleteRequest{Index: []string{"test_types"}}.Do(ctx, es)
	mapping := `{
		"mappings": {
			"properties": {
				"title_text":    { "type": "text" },
				"title_keyword": { "type": "keyword" }
			}
		}
	}`
	_, _ = esapi.IndicesCreateRequest{Index: "test_types", Body: strings.NewReader(mapping)}.Do(ctx, es)

	// Индексирование строки в смешанном регистре с пробелами
	rawStr := "Golang HighLoad Architecture"
	doc := fmt.Sprintf(`{"title_text": "%s", "title_keyword": "%s"}`, rawStr, rawStr)
	_, _ = esapi.IndexRequest{Index: "test_types", DocumentID: "1", Body: strings.NewReader(doc), Refresh: "true"}.Do(ctx, es)

	// 1. Попытка term query по исходной строке в поле text (ПРОВАЛ!)
	// Причина: поле text было токенизировано в ["golang", "highload", "architecture"]
	query1 := `{"query": {"term": {"title_text": "Golang HighLoad Architecture"}}}`
	res1, _ := esapi.SearchRequest{Index: []string{"test_types"}, Body: strings.NewReader(query1)}.Do(ctx, es)
	var r1 map[string]any
	_ = json.NewDecoder(res1.Body).Decode(&r1)
	res1.Body.Close()
	hits1 := r1["hits"].(map[string]any)["total"].(map[string]any)["value"]
	fmt.Printf("1. Точный term запрос по полю text:    найдено %v док (ОЖИДАЕМО 0, токен разбит анализатором!)\n", hits1)

	// 2. Точный term query по полю keyword (УСПЕХ!)
	query2 := `{"query": {"term": {"title_keyword": "Golang HighLoad Architecture"}}}`
	res2, _ := esapi.SearchRequest{Index: []string{"test_types"}, Body: strings.NewReader(query2)}.Do(ctx, es)
	var r2 map[string]any
	_ = json.NewDecoder(res2.Body).Decode(&r2)
	res2.Body.Close()
	hits2 := r2["hits"].(map[string]any)["total"].(map[string]any)["value"]
	fmt.Printf("2. Точный term запрос по полю keyword: найдено %v док (УСПЕХ, сохранен точный оригинал)\n", hits2)
}
```

ℹ️ Практическое доказательство разницы между text и keyword структурами данных

**`Терминал`**

```bash
go run main.go
# 1. Точный term запрос по полю text:    найдено 0 док (ОЖИДАЕМО 0, токен разбит анализатором!)
# 2. Точный term запрос по полю keyword: найдено 1 док (УСПЕХ, сохранен точный оригинал)
```

## Под капотом

В поле `title_text` анализатор разбил фразу на 3 отдельных токена в нижнем регистре: `"golang"`, `"highload"`, `"architecture"`. Запрос `term` не использует анализатор и ищет точную строку `"Golang HighLoad Architecture"`, которой нет в инвертированном индексе. В поле `title_keyword` строка сохранена в неизменном виде в Doc Values.

## Подводные камни

Использование `keyword` на полях с длинными текстами (> 256 символов) приведет либо к их молчаливому игнорированию, либо к ошибке `ignore_above: 256` (параметр по умолчанию отсекает индексацию строк длиннее 256 символов).

## На собеседовании

**Вопрос:** Можно ли выполнять агрегацию по полю `text`?
**Ответ:** По умолчанию запрещено (вызовет ошибку). Если принудительно включить `fielddata: true`, Elasticsearch распакует весь инвертированный индекс поля в оперативную память JVM кучи (Heap), что в HighLoad продакшене гарантированно приведет к падению кластера по OOM/CircuitBreaker.
