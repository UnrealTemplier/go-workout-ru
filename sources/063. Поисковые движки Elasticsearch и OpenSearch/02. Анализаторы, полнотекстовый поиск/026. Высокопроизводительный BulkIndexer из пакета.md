# Высокопроизводительный BulkIndexer из пакета esutil

## Условие

**Bulk API**: Используйте `BulkIndexer` для массовой индексации документов (ключ к производительности).

## Теория

Вместо ручной склейки строк NDJSON в буферах официальный Go SDK предоставляет высокоуровневый промышленный компонент **`esutil.NewBulkIndexer`**:

### Архитектура `esutil.BulkIndexer`:
1. Воркер-пул горутин (`NumWorkers: runtime.NumCPU()`).
2. Автоматический сброс по лимиту байтов (`FlushBytes: 5 * 1024 * 1024` — 5 МБ).
3. Автоматический сброс по интервалу времени (`FlushInterval: 1 * time.Second`).
4. Индивидуальные колбэки `OnSuccess` и `OnFailure` для каждого документа, позволяющие логировать ошибки конкретных строк без остановки всего потока.

## Решение по шагам

1. Создайте экземпляр `esutil.NewBulkIndexer` с воркер-пулом из 4 горутин.
2. Реализуйте обработчики `OnSuccess` и `OnFailure`.
3. Добавьте 5 000 документов методом `bi.Add()`.
4. Закройте индексёр `bi.Close()` и выведите статистику переданных документов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"strings"
	"sync/atomic"
	"time"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esutil"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}

	var countSuccessful uint64

	// Инициализация промышленного BulkIndexer
	bi, err := esutil.NewBulkIndexer(esutil.BulkIndexerConfig{
		Index:         "articles",
		Client:        es,
		NumWorkers:    4,               // пул из 4 параллельных воркеров
		FlushBytes:    5 * 1024 * 1024, // сброс при накоплении 5 МБ
		FlushInterval: 500 * time.Millisecond,
		OnError: func(ctx context.Context, err error) {
			fmt.Printf("Критическая ошибка BulkIndexer: %v\n", err)
		},
	})
	if err != nil {
		panic(err)
	}

	start := time.Now()
	totalDocs := 5000

	ctx := context.Background()
	for i := 1; i <= totalDocs; i++ {
		docID := fmt.Sprintf("bulk_%d", i)
		docBody := fmt.Sprintf(`{"title": "Concurrent Article #%d", "views": %d}`, i, i)

		err := bi.Add(
			ctx,
			esutil.BulkIndexerItem{
				Action:     "index",
				DocumentID: docID,
				Body:       strings.NewReader(docBody),
				OnSuccess: func(ctx context.Context, item esutil.BulkIndexerItem, res esutil.BulkIndexerResponseItem) {
					atomic.AddUint64(&countSuccessful, 1)
				},
				OnFailure: func(ctx context.Context, item esutil.BulkIndexerItem, res esutil.BulkIndexerResponseItem, err error) {
					fmt.Printf("Ошибка индексации документа %s: %v\n", item.DocumentID, err)
				},
			},
		)
		if err != nil {
			panic(err)
		}
	}

	// Ожидание завершения отправки всех документов
	if err := bi.Close(ctx); err != nil {
		panic(err)
	}

	elapsed := time.Since(start)
	stats := bi.Stats()
	fmt.Printf("BulkIndexer завершил работу за %v:\n", elapsed)
	fmt.Printf("  Всего добавлено:  %d\n", stats.NumAdded)
	fmt.Printf("  Успешно записано: %d\n", stats.NumFlushed)
	fmt.Printf("  Сбоев:            %d\n", stats.NumFailed)
	fmt.Printf("  Скорость:         %.0f док/сек\n", float64(totalDocs)/elapsed.Seconds())
}
```

ℹ️ Массовая потоковая индексация через esutil.NewBulkIndexer с колбэками

**`Терминал`**

```bash
go run main.go
# BulkIndexer завершил работу за 128ms:
#   Всего добавлено:  5000
#   Успешно записано: 5000
#   Сбоев:            0
#   Скорость:         39062 док/сек
```

## Под капотом

`BulkIndexer` запускает внутренние очереди каналов Go и распределяет входящие элементы между воркерами без блокировок. Воркеры наполняют буферы и сбрасывают их по достижению лимита `FlushBytes` или тику таймера `FlushInterval`, обеспечивая оптимальную утилизацию HTTP-сокетов.

## Подводные камни

Обязательно вызывайте `bi.Close(ctx)` при завершении работы сервиса. Если не вызвать `Close()`, часть документов, оставшаяся во внутреннем буфере воркера, никогда не будет отправлена в Elasticsearch.

## На собеседовании

**Вопрос:** Как `BulkIndexer` защищает от переполнения памяти, если Elasticsearch временно отвечает ошибкой `429 Too Many Requests`?
**Ответ:** Драйвер поддерживает автоматический экспоненциальный Backoff: при получении HTTP 429 воркер приостанавливает отправку новых батчей и повторяет попытку через увеличивающиеся интервалы времени, предотвращая падение кластера по перегрузке очередей.
