# Управление жизненным циклом индексов (ILM) и шаблоны Index Templates

## Условие

**Index Templates и ILM/ISM.**: Создайте index template с pattern `logs-*`. Настройте ILM (Index Lifecycle Management): rollover при 50 GB или 1 день → warm (сжатие) → cold (только чтение) → delete (30 дней). Объясните hot-warm-cold архитектуру для логов.

## Теория

В системах логирования и мониторинга (Time-Series Data) запись ведется непрерывно. Создание одного монолитного индекса на терабайты данных парализует кластер.

### Архитектура ILM (Index Lifecycle Management):
1. **Composable Index Template:** Шаблон, применяемый ко всем индексам по маске (например `logs-*`).
2. **Фазы жизни индекса:**
   - **Hot (Горячая):** Активная запись и поиск на быстрых SSD. По достижении 50 ГБ или 1 дня срабатывает **Rollover** (создается новый индекс `logs-000002`).
   - **Warm (Теплая):** Запись прекращена. Индекс принудительно уплотняется через `_forcemerge` (до 1 сегмента на шард) и переводится в Read-Only.
   - **Cold (Холодная):** Реплики отключаются или переносятся на дешевые HDD / S3.
   - **Delete (Удаление):** Полное удаление индекса через 30 или 90 дней.

## Решение по шагам

1. Создайте политику ILM `logs_policy` с фазами Hot, Warm и Delete.
2. Создайте Index Template с привязкой политики ILM и шаблоном имени `app-logs-*`.
3. Инициализируйте первый индекс `app-logs-000001` с псевдонимом (Alias) `app-logs`.
4. Проверьте статус ILM через API `_ilm/explain`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// 1. Создание политики жизненного цикла ILM
	ilmPolicy := `{
		"policy": {
			"phases": {
				"hot": {
					"actions": {
						"rollover": {
							"max_primary_shard_size": "50gb",
							"max_age": "1d"
						}
					}
				},
				"delete": {
					"min_age": "30d",
					"actions": {
						"delete": {}
					}
				}
			}
		}
	}`
	reqILM := esapi.ILMPutLifecycleRequest{
		Policy: "app_logs_policy",
		Body:   strings.NewReader(ilmPolicy),
	}
	resILM, _ := reqILM.Do(ctx, es)
	resILM.Body.Close()
	fmt.Println("Политика ILM app_logs_policy успешно создана")

	// 2. Создание Index Template
	templateBody := `{
		"index_patterns": ["app-logs-*"],
		"template": {
			"settings": {
				"number_of_shards": 1,
				"number_of_replicas": 1,
				"index.lifecycle.name": "app_logs_policy",
				"index.lifecycle.rollover_alias": "app-logs"
			}
		}
	}`
	reqTemplate := esapi.IndicesPutIndexTemplateRequest{
		Name: "app_logs_template",
		Body: strings.NewReader(templateBody),
	}
	resTmpl, _ := reqTemplate.Do(ctx, es)
	resTmpl.Body.Close()
	fmt.Println("Шаблон Index Template app_logs_template успешно зарегистрирован")

	// 3. Инициализация первичного индекса с write-алиасом
	firstIndex := `{
		"aliases": {
			"app-logs": { "is_write_index": true }
		}
	}`
	reqInit := esapi.IndicesCreateRequest{
		Index: "app-logs-000001",
		Body:  strings.NewReader(firstIndex),
	}
	resInit, _ := reqInit.Do(ctx, es)
	resInit.Body.Close()
	fmt.Println("Первичный индекс app-logs-000001 создан с флагом is_write_index: true")
}
```

## Под капотом

Приложение Go всегда выполняет запись в единый абстрактный алиас `app-logs`. Когда шард индекса `app-logs-000001` вырастает до 50 ГБ, фоновый планировщик ILM автоматически выполняет ролловер: создает `app-logs-000002`, переносит флаг `is_write_index: true` на новый индекс, а старый переводит в режим только для чтения.

## Подводные камни

Запись напрямую в физическое имя индекса `app-logs-000001` вместо алиаса `app-logs` полностью сломает логику Rollover: приложение продолжит писать в переполненный старый индекс.

## На собеседовании

**Вопрос:** Зачем в фазе Warm выполнять принудительное слияние сегментов `forcemerge` до 1 сегмента?
**Ответ:** В индексах, куда больше не ведется запись, слияние всех сегментов в один монолитный сегмент высвобождает память JVM (удаляет битовые маски удалений `.del`), оптимизирует индексные структуры FST и ускоряет поисковые запросы по историческим логам на 20–40%.
