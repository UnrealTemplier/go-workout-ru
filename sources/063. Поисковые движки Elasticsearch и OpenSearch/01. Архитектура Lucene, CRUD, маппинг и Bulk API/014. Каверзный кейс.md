# Каверзный кейс: Глубокая пагинация и Search After против max_result_window

## Условие

**[Каверзный кейс — Deep Pagination]**: Попробуй сделать пагинацию через `from` и `size` (например, `from: 10000, size: 10`). Поймай ошибку Elasticsearch `max_result_window`. Перепиши пагинацию на `search_after` (используя sort values последнего документа).

## Теория

Классическая пагинация через `from` и `size` (например `from: 10000, size: 10`) в распределенных поисковых системах приводит к краху:

### Проблема Deep Pagination:
1. Чтобы вернуть 10 документов с 10 000-й позиции на кластере из 5 шардов, **каждый шард обязан отсортировать и вернуть координатору 10 010 документов**.
2. Координатор должен загрузить в оперативную память \(5 \times 10010 = 50050\) документов, отсортировать их в куче (PriorityQueue), отбросить первые 10 000 и отдать клиенту только 10 штук.
3. По умолчанию в Elasticsearch установлен защитный лимит `index.max_result_window = 10000`. При `from + size > 10000` запрос падает с ошибкой `Result window is too large`.

### Решение BigTech: `search_after`
Вместо смещения по номерам строк клиент передает значения сортировки последнего документа предыдущей страницы (`search_after: [last_timestamp, last_id]`). Шард начинает поиск сразу со следующей позиции за константное время O(1) и без расхода RAM!

## Решение по шагам

1. Сымитируйте ошибку `from + size > 10000`.
2. Перепишите пагинацию на курсорный механизм `search_after`.
3. Обязательно добавьте уникальный тайбрейкер сортировки `sort: [{"created_at": "desc"}, {"_id": "asc"}]`.
4. Продемонстрируйте потоковую выгрузку глубоких страниц в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type SearchAfterResponse struct {
	Hits struct {
		Hits []struct {
			ID     string   `json:"_id"`
			Sort   []any    `json:"sort"`
			Source struct {
				Title string `json:"title"`
			} `json:"_source"`
		} `json:"hits"`
	} `json:"hits"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// 1. Демонстрация ошибки max_result_window при from > 10000
	badQuery := `{"from": 10001, "size": 10}`
	badReq := esapi.SearchRequest{
		Index: []string{"articles"},
		Body:  strings.NewReader(badQuery),
	}
	badRes, _ := badReq.Do(ctx, es)
	fmt.Printf("Попытка from=10001: статус ответа %s (сработал max_result_window!)\n", badRes.Status())
	badRes.Body.Close()

	// 2. Идиоматичное решение: Пагинация через search_after
	fmt.Println("\nИдиоматичная глубокая пагинация через search_after:")
	var searchAfterValues []any

	for page := 1; page <= 3; page++ {
		var queryBody string
		if len(searchAfterValues) == 0 {
			// Первая страница
			queryBody = `{
				"size": 2,
				"sort": [
					{ "views": "desc" },
					{ "_id": "asc" }
				]
			}`
		} else {
			// Следующие страницы с курсором search_after
			saJSON, _ := json.Marshal(searchAfterValues)
			queryBody = fmt.Sprintf(`{
				"size": 2,
				"search_after": %s,
				"sort": [
					{ "views": "desc" },
					{ "_id": "asc" }
				]
			}`, string(saJSON))
		}

		req := esapi.SearchRequest{
			Index: []string{"articles"},
			Body:  strings.NewReader(queryBody),
		}
		res, err := req.Do(ctx, es)
		if err != nil {
			panic(err)
		}

		var pageRes SearchAfterResponse
		_ = json.NewDecoder(res.Body).Decode(&pageRes)
		res.Body.Close()

		hits := pageRes.Hits.Hits
		if len(hits) == 0 {
			break
		}

		fmt.Printf("Страница %d:\n", page)
		for _, h := range hits {
			fmt.Printf("  ID: %s | Просмотры: %v | Title: '%s'\n",
				h.ID, h.Sort[0], h.Source.Title)
		}

		// Запоминаем значения sort последнего элемента страницы
		searchAfterValues = hits[len(hits)-1].Sort
	}
}
```

## Под капотом

При использовании `search_after` Lucene не выполняет пропуск \(N\) документов. Векторный итератор по сегменту сразу позиционируется на первый документ, значение ключа которого строго больше/меньше переданного маркера, сохраняя константную сложность \(O(\text{size})\) независимо от глубины пагинации.

## Подводные камни

В секции `sort` обязательно должен присутствовать уникальный тайбрейкер (например `{"_id": "asc"}`). Если два документа имеют одинаковое значение `views`, без тайбрейкера порядок выдачи между ними может быть недетерминирован, что приведет к пропуску или дублированию записей.

## На собеседовании

**Вопрос:** Чем `search_after` отличается от старого механизма `Scroll API`?
**Ответ:** `Scroll API` создает снимок состояния поиска (Point in Time) и держит открытые ресурсы `IndexReader` в памяти на фиксированное время, что перегружает кластер при тысячах параллельных пользователей. `search_after` полностью stateless, не удерживает серверных ресурсов и является рекомендованным стандартом для веб-пагинации.
