# Многоуровневые аналитические агрегации: Bucket, Metric и Pipeline

## Условие

**Агрегации.**: Постройте dashboard-запрос: `date_histogram` (по дням) + `terms` (по статусу) + `avg` (rating) + `derivative` (рост от дня к дню). Объясните разницу между bucket aggregations (группировка) и metric aggregations (вычисления).

## Теория

Аналитический движок Elasticsearch разделяет агрегации на три фундаментальных типа:

1. **Bucket Aggregations (Бакетирование):** Группируют документы по корзинам (`date_histogram` по дням/месяцам, `terms` по статусам, `range` по ценовым диапазонам).
2. **Metric Aggregations (Метрики):** Вычисляют числовые показатели внутри каждого бакета (`avg`, `sum`, `min`, `max`, `stats`, `percentiles`).
3. **Pipeline Aggregations (Конвейерные агрегации):** Применяются к результатам других агрегаций (`derivative` для расчета темпа роста производной, `cumulative_sum` для накопительного итога, `moving_avg` для скользящего среднего).

## Решение по шагам

1. Составьте вложенный запрос агрегации: бакет `date_histogram` с интервалом `1d`.
2. Внутри каждого дня добавьте вложенную агрегацию `avg` рейтинга и бакет `terms` по статусу.
3. Добавьте конвейерную агрегацию `derivative` для вычисления суточного изменения рейтинга.
4. Выполните запрос из Go и распарсите полученное дерево агрегатов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// Двухуровневая агрегация: гистограмма по датам + средний рейтинг + производная
	aggQuery := `{
		"size": 0,
		"aggs": {
			"sales_per_day": {
				"date_histogram": {
					"field": "created_at",
					"calendar_interval": "day"
				},
				"aggs": {
					"avg_rating": {
						"avg": { "field": "rating" }
					},
					"by_status": {
						"terms": { "field": "status" }
					},
					"rating_derivative": {
						"derivative": { "buckets_path": "avg_rating" }
					}
				}
			}
		}
	}`

	req := esapi.SearchRequest{
		Index: []string{"articles"},
		Body:  strings.NewReader(aggQuery),
	}
	res, err := req.Do(ctx, es)
	if err != nil {
		panic(err)
	}
	defer res.Body.Close()

	var result map[string]any
	_ = json.NewDecoder(res.Body).Decode(&result)

	fmt.Println("Аналитические агрегации успешно выполнены на стороне Elasticsearch")
	if aggs, ok := result["aggregations"].(map[string]any); ok {
		buckets := aggs["sales_per_day"].(map[string]any)["buckets"].([]any)
		fmt.Printf("Получено временных бакетов: %d\n", len(buckets))
	}
}
```

## Под капотом

Секция `"size": 0` оптимизирует запрос: координатор шарда пропускает этап выгрузки исходных документов (`FETCH` фаза) и возвращает только предварительно рассчитанные в структурах Doc Values агрегаты, снижая объем сетевого трафика на 99%.

## Подводные камни

В конвейерных агрегациях путь `buckets_path` строго чувствителен к именам: если имя дочерней метрики указано с ошибкой, запрос упадет с исключением `Aggregation [name] not found for path`.

## На собеседовании

**Вопрос:** В чем разница между `calendar_interval` и `fixed_interval` в `date_histogram`?
**Ответ:** `calendar_interval` учитывает календарные особенности (переходы на летнее время, разное число дней в месяцах: `'1d'`, `'1M'`). `fixed_interval` использует строго фиксированное число секунд или миллисекунд (например, `'1h'` = ровно 3600 секунд), что критично для равномерных IoT метрик.
