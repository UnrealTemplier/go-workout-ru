# Архитектура драйвера: Строго типизированный TypedClient против esapi

## Условие

**Typed API vs Raw API**: В драйвере ESv8 есть два клиента. Изучи `esapi` (сырой, работает с JSON в виде `strings.Reader`) и `TypedClient` (строго типизированный, с билдерами запросов). Создай `TypedClient` и сделай пинг кластера.

## Теория

В официальном SDK `github.com/elastic/go-elasticsearch/v8` разработчикам доступны два подхода:

1. **`esapi` (Raw Client):**
   - Низкоуровневый клиент.
   - Запросы формируются в виде сырых строк JSON (`strings.Reader`) или байтовых буферов.
   - Ответ возвращает `io.ReadCloser`, который необходимо парсить вручную.
   - Плюсы: максимальная производительность, поддержка любых нестандартных или экспериментальных полей.
2. **`TypedClient` (`elasticsearch.NewTypedClient`):**
   - Высокоуровневый типизированный клиент с fluent-билдерами запросов.
   - Защита от опечаток в именах секций запросов на этапе компиляции Go.
   - Автоматическая сериализация и десериализация структур.

## Решение по шагам

1. Инициализируйте `TypedClient`.
2. Постройте типизированный поисковый запрос с помощью fluent API: `es.Search().Index(...).Request(...)`.
3. Распарсите типизированный ответ без ручного декодирования JSON.
4. Сравните читаемость и безопасность кода.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/typedapi/core/search"
	"github.com/elastic/go-elasticsearch/v8/typedapi/types"
)

func main() {
	// Инициализация строго типизированного клиента TypedClient
	typedES, err := elasticsearch.NewTypedClient(elasticsearch.Config{
		Addresses: []string{"http://localhost:9200"},
	})
	if err != nil {
		panic(err)
	}

	ctx := context.Background()

	// Построение запроса через типизированные структуры Go
	searchRes, err := typedES.Search().
		Index("articles").
		Request(&search.Request{
			Query: &types.Query{
				Bool: &types.BoolQuery{
					Must: []types.Query{
						{
							Match: map[string]types.MatchQuery{
								"title": {Query: "Go"},
							},
						},
					},
					Filter: []types.Query{
						{
							Range: map[string]types.RangeQuery{
								"views": types.NumberRangeQuery{Gte: types.Float64(10)},
							},
						},
					},
				},
			},
		}).
		Do(ctx)

	if err != nil {
		fmt.Printf("TypedClient search failed: %v\n", err)
		return
	}

	fmt.Printf("TypedClient успешно нашел документов: %d\n", searchRes.Hits.Total.Value)
	for _, hit := range searchRes.Hits.Hits {
		fmt.Printf("  Найдено: ID=%s, Score=%v\n", *hit.Id_, *hit.Score_)
	}
}
```

ℹ️ Построение поисковых запросов через строго типизированный TypedClient в Go

**`Терминал`**

```bash
go run main.go
# TypedClient успешно нашел документов: 1
#   Найдено: ID=1, Score=1.842
```

## Под капотом

`TypedClient` генерируется автоматически из официальной схемы Elasticsearch Specification. Он инкапсулирует тысячи сгенерированных структур, гарантируя строгое соответствие протоколу v8 на этапе компиляции `go build`.

## Подводные камни

`TypedClient` компилируется дольше и увеличивает размер бинарного файла Go на 15–25 МБ из-за огромного количества сгенерированных типов. В высокопроизводительных микросервисах с критичным размером бинарника часто используют сырой `esapi` с буферами NDJSON.

## На собеседовании

**Вопрос:** Когда в BigTech отдают предпочтение `esapi`, а не `TypedClient`?
**Ответ:** В высоконагруженных прокси-сервисах, шлюзах логирования и сервисах ingestion, где сервис просто пересылает входящий JSON из Kafka/HTTP в Elasticsearch без его глубокой валидации и модификации, избегая лишних аллокаций памяти на сериализацию структур.
