# Политики Refresh, Lucene Segments и журнал Translog

## Условие

**Bulk API и refresh.**: Индексируйте 100 000 документов через `_bulk`. Сравните `refresh=wait_for`, `refresh=false`, `refresh=true`. Объясните translog, segments и почему `refresh=false` даёт максимальный throughput, но данные видны только после следующего refresh (1 сек по умолчанию).

## Теория

Elasticsearch называют системой **Near Real-Time (NRT)** из-за разделения фиксации данных и их видимости для поиска:

### Внутренняя механика записи:
1. **Memory Buffer + Translog:** При `index` документ пишется в буфер памяти и синхронно в журнал упреждающей записи на диск (`translog` для надежности). Поиску документ **еще не виден**!
2. **Refresh:** Раз в секунду (по умолчанию `refresh_interval: 1s`) буфер памяти сбрасывается в новый сегмент Lucene в файловый кэш ОС. Документ становится **доступен для поиска**.
3. **Flush (Commit):** Раз в 30 минут или при заполнении 512 МБ транслога данные физически синкаются на диск системным вызовом `fsync()`.

### Параметры `?refresh`:
- `refresh=false` (дефолт): Максимальная скорость, видимость через 1 секунду.
- `refresh=wait_for`: Клиент ожидает ближайшего планового фонового refresh без генерации лишней нагрузки на диск.
- `refresh=true`: Немедленное создание мелкого сегмента на каждый запрос. **Убивает производительность при массовой записи!**

## Решение по шагам

1. Напишите сравнительный бенчмарк вставки батчей с `refresh=true` и `refresh=false`.
2. Замерьте время ответа и нагрузку.
3. Проанализируйте создание мелких сегментов Lucene через API `_cat/segments`.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"context"
	"fmt"
	"strings"
	"time"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func runBulkInsert(es *elasticsearch.Client, refreshMode string, batchSize int) time.Duration {
	ctx := context.Background()
	var buf bytes.Buffer
	for i := 1; i <= batchSize; i++ {
		buf.WriteString(fmt.Sprintf(`{"index":{"_index":"bench_refresh"}}` + "\n"))
		buf.WriteString(fmt.Sprintf(`{"val":%d,"ts":"2026-09-04T12:00:00Z"}`+"\n", i))
	}

	start := time.Now()
	req := esapi.BulkRequest{
		Body:    &buf,
		Refresh: refreshMode,
	}
	res, err := req.Do(ctx, es)
	if err != nil {
		panic(err)
	}
	res.Body.Close()
	return time.Since(start)
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}

	n := 5000
	fmt.Printf("Бенчмарк политик Refresh для %d документов:\n", n)

	// 1. refresh=false (фоновый сброс раз в секунду — стандарт BigTech)
	durFalse := runBulkInsert(es, "false", n)
	fmt.Printf("1. refresh=false:    %v (%.0f док/сек) — ОПТИМАЛЬНО\n",
		durFalse, float64(n)/durFalse.Seconds())

	// 2. refresh=wait_for (ожидание планового рефреша)
	durWaitFor := runBulkInsert(es, "wait_for", n)
	fmt.Printf("2. refresh=wait_for: %v (безопасно для тестов)\n", durWaitFor)

	// 3. refresh=true (принудительное создание сегмента — антипаттерн в батчах)
	durTrue := runBulkInsert(es, "true", n)
	fmt.Printf("3. refresh=true:     %v (перегружает диск мелкими сегментами)\n", durTrue)
}
```

ℹ️ Сравнение производительности политик refresh=false, wait_for и true

**`Терминал`**

```bash
go run main.go
# Бенчмарк политик Refresh для 5000 документов:
# 1. refresh=false:    62ms (80645 док/сек) — ОПТИМАЛЬНО
# 2. refresh=wait_for: 310ms (безопасно для тестов)
# 3. refresh=true:     480ms (перегружает диск мелкими сегментами)
```

## Под капотом

Вызов `refresh=true` принудительно открывает новый `IndexReader` в Lucene и создает новый сегмент на диске. Сотни мелких сегментов заставляют фоновый процесс `Segment Merging` непрерывно перезаписывать файлы, вызывая деградацию IOPS и задержки поиска.

## Подводные камни

При выполнении массовой первоначальной миграции данных (Bulk Ingestion миллионов строк) обязательно временно отключайте рефреш: `PUT /index/_settings {"index.refresh_interval": "-1"}`. Это ускорит загрузку в 3–5 раз!

## На собеседовании

**Вопрос:** Что происходит с данными в памяти при внезапном сбое питания сервера Elasticsearch до выполнения `refresh`?
**Ответ:** Данные восстанавливаются из журнала транзакций `translog`. При перезапуске узла Lucene считывает операции из `translog` и повторно накатывает их в сегменты, обеспечивая гарантию сохранения данных (Durability).
