# Экспорт миллионов документов: Point in Time (PIT) и search_after

## Условие

**Deep pagination и поисковая оптимизация.**: Реализуйте экспорт 1 млн документов тремя способами: `from/size` (покажите OOM на больших offset), `scroll` (context-heavy), `search_after` (stateless, preferred). Объясните `query_then_fetch` vs `dfs_query_then_fetch`.

---

## Теория

При экспорте больших массивов данных (1+ млн документов для ML-моделей или миграции) возникают две проблемы:
1. Обычный `search_after` чувствителен к параллельным изменениям данных: если во время сканирования страницы вставляются новые документы, порядок выдачи может нарушиться.
2. Старый `Scroll API` перегружает память шардов и не поддерживается в кластерах с замороженными (Frozen) индексами.

### Стандарт BigTech: Point in Time (PIT) + search_after:
1. `POST /index/_pit?keep_alive=5m` — создание легковесного снимка состояния шардов.
2. Последующие запросы `search_after` передают идентификатор `pit.id`.
3. Гарантируется абсолютно детерминированный снимок состояния данных без оверхеда на память!

## Решение по шагам

1. Откройте Point in Time с помощью `client.OpenPointInTime`.
2. Выполните постраничную выгрузку через `search_after` с привязкой к `pit.id`.
3. После завершения экспорта освободите ресурсы вызовом `client.ClosePointInTime`.
4. Сравните с поведением `from/size`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// 1. Открытие Point in Time (PIT) на 5 минут
	openPITReq := esapi.OpenPointInTimeRequest{
		Index:     []string{"articles"},
		KeepAlive: "5m",
	}
	pitRes, err := openPITReq.Do(ctx, es)
	if err != nil {
		panic(err)
	}
	defer pitRes.Body.Close()

	var pitData struct {
		ID string `json:"id"`
	}
	_ = json.NewDecoder(pitRes.Body).Decode(&pitData)
	pitID := pitData.ID
	fmt.Printf("Point in Time успешно открыт: ID=%s...\n", pitID[:15])

	// 2. Детерминированный экспорт через search_after и PIT
	queryBody := fmt.Sprintf(`{
		"size": 2,
		"pit": {
			"id": "%s",
			"keep_alive": "5m"
		},
		"sort": [
			{ "views": "desc" },
			{ "_shard_doc": "asc" }
		]
	}`, pitID)

	searchReq := esapi.SearchRequest{
		Body: strings.NewReader(queryBody),
	}
	res, err := searchReq.Do(ctx, es)
	if err != nil {
		panic(err)
	}
	defer res.Body.Close()

	var result map[string]any
	_ = json.NewDecoder(res.Body).Decode(&result)
	hits := result["hits"].(map[string]any)["hits"].([]any)
	fmt.Printf("Выгружена первая страница экспорта по снимку PIT: %d документов\n", len(hits))

	// 3. Закрытие Point in Time
	closeReq := esapi.ClosePointInTimeRequest{
		Body: strings.NewReader(fmt.Sprintf(`{"id": "%s"}`, pitID)),
	}
	closeRes, _ := closeReq.Do(ctx, es)
	closeRes.Body.Close()
	fmt.Println("Point in Time корректно закрыт, ресурсы шардов освобождены")
}
```

ℹ️ Массовый экспорт миллионов документов через Point in Time (PIT) и search_after

**`Терминал`**

```bash
go run main.go
# Point in Time успешно открыт: ID=46-zDwEWYXJ0aWNs...
# Выгружена первая страница экспорта по снимку PIT: 2 документов
# Point in Time корректно закрыт, ресурсы шардов освобождены
```

## Под капотом

PIT удерживает счетчик ссылок (Reference Counting) на текущие файлы сегментов Lucene. Даже если фоновый процесс уплотнения (Merge) сотрет старые сегменты, операционная система не удалит их физически с диска до тех пор, пока PIT активен, обеспечивая 100% консистентность выборки.

## Подводные камни

Использование сортировки `_id` в запросах с PIT неэффективно. Стандартная рекомендация разработчиков Lucene — использовать в качестве тайбрейкера сортировку `{"_shard_doc": "asc"}`, которая читает документы в естественном порядке сегментов без накладных расходов.

## На собеседовании

**Вопрос:** Почему `Scroll API` считается устаревшим в современных версиях Elasticsearch?
**Ответ:** `Scroll` привязан к конкретному поисковому запросу и создает глубокие блокировки в памяти JVM. `PIT + search_after` разделяет снимок данных и сам запрос, позволяя параллельно запускать несколько независимых воркеров по одному и тому же снимку PIT (Slices).
