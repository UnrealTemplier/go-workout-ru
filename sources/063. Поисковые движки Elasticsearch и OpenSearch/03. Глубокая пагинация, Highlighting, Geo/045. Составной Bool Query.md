# Составной Bool Query: Must vs Filter и битсет-кэширование

## Условие

**Bool Query (Must vs Filter)**: Тебе нужно найти "телефон" (поиск) в категории "электроника" (фильтр). Напиши составной `bool` запрос. В `must` положи `match`, а в `filter` положи `term` по категории. *Осознай архитектурное правило: блок `filter` кэшируется в ES и не влияет на `_score` (релевантность), что делает запрос сильно быстрее!*

## Теория

Запрос `bool` объединяет несколько условий в логическое выражение. Он поддерживает четыре секции:
1. `must`: Условие ОБЯЗАНО совпасть. Входит в расчет релевантности `_score` (Query Context).
2. `filter`: Условие ОБЯЗАНО совпасть. **НЕ влияет на `_score`** (Filter Context). Результаты кэшируются в оперативной памяти ноды в виде компактных битсетов (`Roaring Bitmaps`).
3. `should`: Если есть `must` или `filter`, `should` повышает релевантность. Если их нет, хотя бы одно из условий `should` должно выполниться (по умолчанию `minimum_should_match: 1`).
4. `must_not`: Инвертированное условие (логическое NOT). Выполняется в Filter Context (не считает score, кэшируется).

**Золотое правило HighLoad Elasticsearch:**
Любое условие точного совпадения (категория, статус, дата, цена, tenant_id, наличие на складе) **ВСЕГДА** помещается в `filter`, а полнотекстовый поиск — в `must`.

## Решение по шагам

1. Сформируйте запрос `bool`.
2. В блок `must` поместите `match` по полю `title` со значением `"телефон"`.
3. В блок `filter` поместите условие точного совпадения `term` по полю `category.keyword` со значением `"электроника"`.
4. Добавьте в `filter` диапазон цен `range` от 10000 до 150000.
5. Выполните запрос и убедитесь, что `_score` рассчитывается только на основе релевантности названия, а фильтры работают со скоростью битовых операций.

## Код решения

**`bool_query.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"

	"github.com/elastic/go-elasticsearch/v8"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка инициализации клиента: %v", err)
	}

	// must = расчет релевантности, filter = битсет без скоринга
	query := map[string]interface{}{
		"query": map[string]interface{}{
			"bool": map[string]interface{}{
				"must": []interface{}{
					map[string]interface{}{
						"match": map[string]interface{}{
							"title": "телефон",
						},
					},
				},
				"filter": []interface{}{
					map[string]interface{}{
						"term": map[string]interface{}{
							"category.keyword": "электроника",
						},
					},
					map[string]interface{}{
						"range": map[string]interface{}{
							"price": map[string]interface{}{
								"gte": 10000,
								"lte": 150000,
							},
						},
					},
				},
			},
		},
	}

	var buf bytes.Buffer
	if err := json.NewEncoder(&buf).Encode(query); err != nil {
		log.Fatalf("Ошибка маршалинга: %v", err)
	}

	res, err := es.Search(
		es.Search.WithContext(context.Background()),
		es.Search.WithIndex("products"),
		es.Search.WithBody(&buf),
	)
	if err != nil {
		log.Fatalf("Ошибка поиска: %v", err)
	}
	defer res.Body.Close()

	var result map[string]interface{}
	if err := json.NewDecoder(res.Body).Decode(&result); err != nil {
		log.Fatalf("Ошибка декодирования: %v", err)
	}

	hits := result["hits"].(map[string]interface{})["hits"].([]interface{})
	fmt.Printf("Успешно найдено товаров: %d\n", len(hits))
	for _, h := range hits {
		item := h.(map[string]interface{})
		src := item["_source"].(map[string]interface{})
		fmt.Printf("ID: %-10s | Score: %.4f | Товар: %s | Цена: %.2f\n",
			item["_id"], item["_score"].(float64), src["title"], src["price"].(float64))
	}
}
```

## Под капотом

Секция `filter` выполняется с использованием **Node Query Cache**.
Lucene строит сжатый битовый массив (`Roaring Bitmap`), где каждый бит обозначает совпадение документа в сегменте.
Когда несколько пользователей ищут разные слова в одной категории «электроника», битсет категории берется из кэша памяти за доли микросекунды и накладывается на результат `must` через битовую операцию AND (побитовое умножение в регистрах CPU).

## Подводные камни

1. Помещение точных фильтров (статус, ID автора, категория) в секцию `must`: заставляет движок производить расчет BM25 и засоряет кэш скоринга, снижая производительность кластера в 3–5 раз.
2. Использование `term` запроса по полю типа `text`: поле `text` токенизировано в нижний регистр, а `term` не проводит анализ. Если запросить `term: {"category": "Электроника"}`, ничего не найдется.
3. Размещение `filter` внутри `nested` без указания пути: фильтры родительского документа не имеют прямого доступа к вложенным сегментам.

## На собеседовании

В: Почему перевод условий из блока `must` в блок `filter` дает колоссальный прирост производительности в нагруженном API?
О: Причины две:
1) **Исключение скоринга:** В блоке `filter` алгоритм BM25 вообще не вызывается. Документу просто присваивается булевый статус (true/false), экономя миллионы операций с плавающей точкой в CPU.
2) **Кэширование битсетов:** Результат выполнения фильтра кэшируется на уровне сегмента в Roaring Bitmaps. При повторном запросе движок выполняет мгновенную битовую операцию AND вместо сканирования инвертированного индекса.
