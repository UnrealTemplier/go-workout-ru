# Отношения Родитель-Потомок (Parent-Child Join): Тип поля join

## Условие

**Parent-child relations**: Используйте `join` field type для parent-child связей (альтернатива nested).

## Теория

В отличие от типа `nested` (где дочерние объекты хранятся внутри одного документа и обновляются целиком), отношение **Parent-Child (тип поля `join`)** позволяет родительским и дочерним документам существовать совершенно независимо!

### Архитектура типа `join`:
1. Родительские и дочерние документы — это **полноценные независимые документы**.
2. Дочерний документ можно добавлять, изменять и удалять без перезаписи родителя.
3. **Жесткое архитектурное ограничение:** Родительский документ и все его дочерние документы **обязаны физически находиться на одном и том же шарде** (требуется одинаковый `_routing = parent_id`).
4. Запросы выполняются через `has_child` и `has_parent`.

## Решение по шагам

1. Создайте индекс `company` с полем `relations` типа `join` (`relations: {"company": "employee"}`).
2. Создайте компанию (родитель).
3. Создайте сотрудников с указанием `routing: company_id` и ссылкой на родителя.
4. Выполните поиск компании по должности сотрудника через запрос `has_child`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		panic(err)
	}
	ctx := context.Background()

	// 1. Создание индекса с полем отношения join
	mapping := `{
		"mappings": {
			"properties": {
				"name": { "type": "keyword" },
				"role": { "type": "keyword" },
				"company_relation": {
					"type": "join",
					"relations": {
						"company": "employee"
					}
				}
			}
		}
	}`
	createReq := esapi.IndicesCreateRequest{
		Index: "companies",
		Body:  strings.NewReader(mapping),
	}
	_, _ = createReq.Do(ctx, es)

	// 2. Индексирование родителя (Компания)
	compDoc := `{
		"name": "Acme Corp",
		"company_relation": { "name": "company" }
	}`
	_, _ = esapi.IndexRequest{
		Index:      "companies",
		DocumentID: "comp_1",
		Body:       strings.NewReader(compDoc),
		Refresh:    "true",
	}.Do(ctx, es)

	// 3. Индексирование потомка (Сотрудник) с обязательным routing на родителя
	empDoc := `{
		"name": "Алексей Смирнов",
		"role": "Go TechLead",
		"company_relation": {
			"name": "employee",
			"parent": "comp_1"
		}
	}`
	_, _ = esapi.IndexRequest{
		Index:      "companies",
		DocumentID: "emp_101",
		Routing:    "comp_1", // Гарантия ко-локации на одном шарде!
		Body:       strings.NewReader(empDoc),
		Refresh:    "true",
	}.Do(ctx, es)

	// 4. Поиск компании через has_child
	hasChildQuery := `{
		"query": {
			"has_child": {
				"type": "employee",
				"query": {
					"term": { "role": "Go TechLead" }
				}
			}
		}
	}`
	searchReq := esapi.SearchRequest{
		Index: []string{"companies"},
		Body:  strings.NewReader(hasChildQuery),
	}
	res, err := searchReq.Do(ctx, es)
	if err != nil {
		panic(err)
	}
	defer res.Body.Close()

	var searchRes map[string]any
	_ = json.NewDecoder(res.Body).Decode(&searchRes)
	hits := searchRes["hits"].(map[string]any)["hits"].([]any)

	fmt.Printf("Поиск компании через has_child успешно выполнен: найдено компаний: %d\n", len(hits))
}
```

ℹ️ Моделирование отношений Parent-Child через тип join и запрос has_child

**`Терминал`**

```bash
go run main.go
# Поиск компании через has_child успешно выполнен: найдено компаний: 1
```

## Под капотом

Связка Parent-Child поддерживается глобальными порядковыми номерами (Global Ordinals) родительских идентификаторов на уровне шарда. Запрос `has_child` сначала находит дочерние документы, извлекает ID родителей и по битовой маске фильтрует родительские документы на том же шарде.

## Подводные камни

Запросы `has_child` и `has_parent` работают в 5–10 раз медленнее, чем запросы `nested`, из-за необходимости загрузки Global Ordinals в оперативную память. Используйте `join` только в случаях, когда дочерние сущности обновляются непрерывно и независимо от родителя.

## На собеседовании

**Вопрос:** В чем разница между `nested` и `parent-child (join)` с точки зрения производительности?
**Ответ:** `nested` обеспечивает максимальную скорость поиска, так как родитель и дети хранятся в одном блоке сегмента, но любое изменение ребенка требует полной перезаписи всего родительского документа со всеми детьми. `join` обеспечивает независимое обновление детей, но требует обязательного ручного роутинга и замедляет поиск из-за динамического сопоставления связей.
