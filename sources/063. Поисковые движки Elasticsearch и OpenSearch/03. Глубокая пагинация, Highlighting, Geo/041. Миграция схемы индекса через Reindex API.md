# Миграция схемы индекса через Reindex API

## Условие

**Reindexing**: Используйте `_reindex` API для изменения mapping существующего индекса (создание нового + копирование).

## Теория

В Elasticsearch и Apache Lucene структура инвертированного индекса и типы полей иммутабельны. Нельзя изменить тип существующего поля (например, с `text` на `keyword` или изменить `analyzer`) «на лету» без полной перестройки структур данных.

Единственный корректный способ изменения маппинга в проде:
1. Создать целевой индекс (`v2`) с исправленным или расширенным маппингом.
2. Использовать `_reindex` API для фонового копирования документов из источника `v1` в приемник `v2`.
3. Опционально применить Painless скрипт для трансформации данных во время реиндексации.
4. Переключить алиас (атомарная операция `_aliases`) с `v1` на `v2`.

Параметр `wait_for_completion=false` позволяет запускать реиндексацию как асинхронную задачу (`Task API`), возвращающую Task ID. Прогресс можно отслеживать через `GET _tasks/<task_id>`.

## Решение по шагам

1. Создайте клиент Elasticsearch `elasticsearch.NewClient`.
2. Создайте новый индекс `products_v2` с явно заданным маппингом (поле `sku` как `keyword`, `price` как `scaled_float`).
3. Сформируйте запрос к `_reindex` API с указанием `source` (`products_v1`) и `dest` (`products_v2`).
4. Для больших индексов укажите `slices: "auto"` для параллельной выгрузки шардов.
5. Прочитайте статус выполнения реиндексации, общее количество перенесенных и созданных документов.
6. Выполните проверку совпадения количества документов (`_count`) в исходном и целевом индексах.

## Код решения

**`reindex.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type ReindexResponse struct {
	Took             int64 `json:"took"`
	TimedOut         bool  `json:"timed_out"`
	Total            int64 `json:"total"`
	Updated          int64 `json:"updated"`
	Created          int64 `json:"created"`
	Batches          int64 `json:"batches"`
	VersionConflicts int64 `json:"version_conflicts"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Создаем целевой индекс v2 с новым маппингом
	v2Mapping := `{
		"mappings": {
			"properties": {
				"sku": {"type": "keyword"},
				"title": {"type": "text", "analyzer": "standard"},
				"price": {"type": "double"}
			}
		}
	}`
	res, err := es.Indices.Create("products_v2", es.Indices.Create.WithBody(strings.NewReader(v2Mapping)))
	if err == nil {
		res.Body.Close()
	}

	// 2. Запуск реиндексации из v1 в v2
	reindexPayload := map[string]interface{}{
		"source": map[string]interface{}{
			"index": "products_v1",
			"size":  1000,
		},
		"dest": map[string]interface{}{
			"index": "products_v2",
			"op_type": "create",
		},
		"conflicts": "proceed",
	}

	bodyBytes, _ := json.Marshal(reindexPayload)
	reindexReq := esapi.ReindexRequest{
		Body:        bytes.NewReader(bodyBytes),
		WaitForCompletion: esapi.BoolPtr(true),
		Slices:      "auto",
	}

	resp, err := reindexReq.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка вызова _reindex: %v", err)
	}
	defer resp.Body.Close()

	if resp.IsError() {
		log.Fatalf("Ошибка реиндексации: %s", resp.Status())
	}

	var result ReindexResponse
	if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
		log.Fatalf("Ошибка парсинга ответа: %v", err)
	}

	fmt.Printf("Реиндексация завершена: Took=%dms, Total=%d, Created=%d, Conflicts=%d\n",
		result.Took, result.Total, result.Created, result.VersionConflicts)
}
```

ℹ️ Выполнение Reindex API со slices: auto для параллельной обработки шардов

**`Терминал`**

```bash
go run reindex.go
# Вывод:
# Реиндексация завершена: Took=412ms, Total=150000, Created=150000, Conflicts=0
```

## Под капотом

Под капотом `_reindex` использует внутренний Scroll API для сканирования исходного индекса пачками документов и пакует их в Bulk Indexing запросы к целевому индексу.
При `slices: "auto"` Elasticsearch делит исходный индекс на срезы (по числу primary шардов исходного индекса), и каждый воркер обрабатывает свой срез независимо.
Поскольку Lucene сегменты иммутабельны, исходный индекс читается без блокировок, а целевой индекс генерирует новые сегменты через LSM-структуру.

## Подводные камни

1. Запуск реиндексации на многомиллионных индексах с `wait_for_completion=true` приведет к HTTP timeout со стороны клиента или балансировщика. Всегда используйте `wait_for_completion=false` и отслеживайте `Task ID`.
2. Забытый параметр `conflicts: "proceed"`: при малейшем дубликате ID или конфликте версий вся реиндексация завершится аварийно с ошибкой.
3. Отсутствие прогрева кэшей и алиасов: переключение алиаса до завершения реиндексации приведет к тому, что клиенты увидят неполный набор документов.

## На собеседовании

В: Как произвести изменение типа поля с `keyword` на `text` в индексе размером 500 ГБ без простоя поискового сервиса?
О: 1) Создать индекс `products_v2` с нужным маппингом.
2) Настроить дублирование записи (dual write) в приложении или настроить Kafka consumer на параллельную запись в оба индекса.
3) Запустить асинхронный `_reindex` с `wait_for_completion=false` и `slices: "auto"`.
4) После завершения реиндексации выполнить атомарную смену указателя алиаса:
`POST /_aliases {"actions": [{"remove": {"index": "products_v1", "alias": "products"}}, {"add": {"index": "products_v2", "alias": "products"}}]}`.
5) Удалить старый индекс `products_v1` после верификации консистентности.
