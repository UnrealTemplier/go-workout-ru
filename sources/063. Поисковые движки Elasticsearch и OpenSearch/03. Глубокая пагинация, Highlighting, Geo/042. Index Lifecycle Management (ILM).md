# Index Lifecycle Management (ILM) и Hot-Warm-Cold архитектура

## Условие

**Index Lifecycle Management (ILM)**: Настройте hot-warm-cold-delete tiers для time-series данных. Автоматический rollover при достижении размера/возраста.

## Теория

При работе с временными рядами (time-series), логами и аудитом объемы данных непрерывно растут. Хранить старые логи на дорогих NVMe SSD дисках экономически нецелесообразно.
Для решения этой задачи в Elasticsearch используется **Index Lifecycle Management (ILM)**:
1. **Hot tier:** Быстрые SSD, высокая частота записи и поиска. Настроен rollover при достижении размера primary шарда (например, 50 ГБ) или возраста (например, 1 день).
2. **Warm tier:** Документы больше не изменяются (read-only). Выполняется `shrink` (уменьшение числа шардов), `forcemerge` (объединение в 1 сегмент) для освобождения памяти и ускорения поисковых агрегаций.
3. **Cold tier:** Реплики переводятся в `searchable snapshots` в дешевом объектном хранилище (S3/MinIO), освобождая локальные диски.
4. **Delete tier:** Автоматическое удаление индекса по истечении SLA (например, retention 90 дней).

## Решение по шагам

1. Создайте ILM политику `logs_policy` с фазами `hot`, `warm`, `cold` и `delete`.
2. В фазе `hot` определите условие rollover: `max_primary_shard_size: 50gb` или `max_age: 1d`.
3. В фазе `warm` задайте `min_age: 7d`, перевод в 1 реплику и объединение сегментов `forcemerge: { max_num_segments: 1 }`.
4. В фазе `delete` задайте `min_age: 90d` и действие `delete`.
5. Привяжите созданную политику к шаблонному индексу (Index Template) через алиас rollover.

## Код решения

**`ilm_policy.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	ctx := context.Background()

	ilmPolicy := `{
		"policy": {
			"phases": {
				"hot": {
					"min_age": "0ms",
					"actions": {
						"rollover": {
							"max_primary_shard_size": "50gb",
							"max_age": "1d"
						}
					}
				},
				"warm": {
					"min_age": "7d",
					"actions": {
						"forcemerge": {
							"max_num_segments": 1
						},
						"allocate": {
							"number_of_replicas": 1
						}
					}
				},
				"delete": {
					"min_age": "90d",
					"actions": {
						"delete": {}
					}
				}
			}
		}
	}`

	req := esapi.ILMPutLifecycleRequest{
		Policy: "app_logs_ilm_policy",
		Body:   strings.NewReader(ilmPolicy),
	}

	res, err := req.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка создания ILM: %v", err)
	}
	defer res.Body.Close()

	if res.IsError() {
		log.Fatalf("Ошибка API: %s", res.Status())
	}

	fmt.Println("ILM политика app_logs_ilm_policy успешно создана!")
}
```

## Под капотом

Фоновый поток `ilm` проверяет индексы с интервалом `indices.lifecycle.poll_interval` (по умолчанию 10 минут).
При переходе в фазу Warm выполняется `forcemerge`: все удаленные документы физически стираются, сегменты переписываются в единый файл `.cfs`/`.si`, что кардинально снижает накладные расходы JVM heap на дескрипторы сегментов и память FST терминов.

## Подводные камни

1. Запуск `forcemerge` на горячем индексе, в который еще идет запись: приводит к колоссальному всплеску I/O диска и может заблокировать запись новых логов.
2. Отсутствие начального индекса с суффиксом `-000001` при настройке Rollover: ILM не сможет автоматически инкрементировать номер индекса.
3. Установка слишком малого `poll_interval` в нагруженном кластере: создает постоянный оверхед на Cluster State метаданные.

## На собеседовании

В: Зачем выполнять Force Merge (до 1 сегмента) на фазе Warm в ILM?
О: При удалении или обновлении документов Lucene помечает их в bitset удаленных (`.del`), но физически память на диске и в кэшах не освобождается. Force Merge физически вычищает удаленные записи, сливает разрозненные сегменты в один монолитный файл. Это:
1) Высвобождает дисковое пространство.
2) Освобождает heap память (каждый сегмент держит свои FST словари терминов и фильтры Блума).
3) Ускоряет агрегации и поиск в read-only индексах в разы.
