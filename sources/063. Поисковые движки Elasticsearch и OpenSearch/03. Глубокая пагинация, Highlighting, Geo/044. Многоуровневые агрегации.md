# Многоуровневые агрегации: terms, histogram и nested

## Условие

**Агрегации: terms, histogram, nested.**: Подсчитайте количество товаров по категориям (terms agg). Постройте гистограмму цен с интервалом 10. Используйте `nested` агрегацию для работы с вложенными документами (например, варианты товара).

## Теория

Агрегации в Elasticsearch делятся на три основных типа:
1. **Bucketing (Группировка):** делит документы на «корзины» (buckets).
   - `terms`: группировка по уникальным значениям поля (использует структуру данных `doc_values`).
   - `histogram`: группировка числовых значений по фиксированному интервалу (шагу).
   - `nested`: переход в контекст вложенных объектов (необходим, когда массив объектов проиндексирован как `type: "nested"`).
2. **Metric (Метрики):** вычисление значений внутри бакетов (`avg`, `sum`, `min`, `max`, `stats`, `percentiles`).
3. **Pipeline (Конвейерные):** агрегации над результатами других агрегаций (например, производные, скользящие средние).

Для вычисления агрегаций по вложенным структурам данных (например, варианты размера и цвета у товара) обязательна агрегация `nested`, возвращающая бакеты вложенных документов.

## Решение по шагам

1. Сформируйте поисковый запрос с секцией `aggs`.
2. Добавьте бакет `categories` типа `terms` по полю `category.keyword`.
3. Добавьте бакет `price_histogram` с интервалом `interval: 10000`.
4. Добавьте бакет `variants_agg` типа `nested` с путем `variants`, внутри которого сгруппируйте по размерам `variants.size.keyword`.
5. Выполните запрос с `size: 0`, чтобы не передавать сами документы, экономя сеть и память.
6. Распарсите результирующую структуру `aggregations`.

## Код решения

**`complex_aggs.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"

	"github.com/elastic/go-elasticsearch/v8"
)

type AggsResponse struct {
	Aggregations struct {
		Categories struct {
			Buckets []struct {
				Key      string `json:"key"`
				DocCount int64  `json:"doc_count"`
			} `json:"buckets"`
		} `json:"categories"`
		PriceHistogram struct {
			Buckets []struct {
				Key      float64 `json:"key"`
				DocCount int64   `json:"doc_count"`
			} `json:"buckets"`
		} `json:"price_histogram"`
	} `json:"aggregations"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	query := map[string]interface{}{
		"size": 0, // Не запрашиваем документы, только агрегации
		"aggs": map[string]interface{}{
			"categories": map[string]interface{}{
				"terms": map[string]interface{}{
					"field": "category.keyword",
					"size":  10,
				},
			},
			"price_histogram": map[string]interface{}{
				"histogram": map[string]interface{}{
					"field":    "price",
					"interval": 10000,
				},
			},
		},
	}

	var buf bytes.Buffer
	if err := json.NewEncoder(&buf).Encode(query); err != nil {
		log.Fatalf("Ошибка кодирования: %v", err)
	}

	res, err := es.Search(
		es.Search.WithContext(context.Background()),
		es.Search.WithIndex("products"),
		es.Search.WithBody(&buf),
	)
	if err != nil {
		log.Fatalf("Ошибка поиска: %v", err)
	}
	defer res.Body.Close()

	var aggRes AggsResponse
	if err := json.NewDecoder(res.Body).Decode(&aggRes); err != nil {
		log.Fatalf("Ошибка парсинга ответа: %v", err)
	}

	fmt.Println("--- Топ категорий ---")
	for _, b := range aggRes.Aggregations.Categories.Buckets {
		fmt.Printf("Категория: %-15s | Товаров: %d\n", b.Key, b.DocCount)
	}

	fmt.Println("\n--- Гистограмма цен ---")
	for _, b := range aggRes.Aggregations.PriceHistogram.Buckets {
		fmt.Printf("Диапазон: %6.0f - %6.0f руб | Количество: %d\n", b.Key, b.Key+10000, b.DocCount)
	}
}
```

## Под капотом

Агрегации работают не по инвертированному индексу, а по структуре **doc_values** — колоночному хранилищу данных на диске, которое мапится в память ОС через page cache (`mmap`).
При выполнении агрегации Elasticsearch последовательно читает значения столбца `category` или `price` для документов, прошедших фильтрацию, собирая хэш-таблицы бакетов. Это обеспечивает нулевую фрагментацию JVM heap и высокую пропускную способность CPU.

## Подводные камни

1. Запуск `terms` агрегации по полю типа `text` без включенного `fielddata`: ES вернет ошибку `Fielddata is disabled on text fields`. Для агрегаций всегда используйте сабполе `.keyword`.
2. Запрос агрегаций с дефолтным `size: 10` без отключения `hits`: передача ненужных документов `_source` тратит CPU на сериализацию и забивает сеть. Всегда ставьте `size: 0` для чисто аналитических запросов.
3. Проблема точности `terms` агрегации на распределенных шардах: при малом значении параметра `size` координатор может отсечь редкие термины. Используйте параметр `shard_size` для повышения точности.

## На собеседовании

В: Почему в агрегациях terms для больших объемов данных результаты подсчета doc_count могут быть приблизительными (approximate)?
О: Каждый шард считает локальный топ-\(N\) терминов (`shard_size`) и отправляет его на ноду-координатор. Координатор суммирует только полученные топы. Если терм на одном из шардов не попал в локальный топ-\(N\), его количество с этого шарда будет утеряно при глобальном сложении.
Для гарантированной точности увеличивают `shard_size` или используют `composite aggregation` для постраничного сканирования всех бакетов без погрешности.
