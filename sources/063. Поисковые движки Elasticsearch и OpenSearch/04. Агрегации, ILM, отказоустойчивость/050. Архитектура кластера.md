# Архитектура кластера: шардирование, репликация и восстановление

## Условие

**Шардирование, репликация и восстановление.**: Настройте индекс с 3 primary shards и 2 replicas. Симулируйте падение узла, проверьте доступность данных. Выполните `_cat/recovery`.

## Теория

Elasticsearch — распределенная документоориентированная система.
Ключевые понятия архитектуры отказоустойчивости:
1. **Primary Shard (Основной шард):** экземпляр инвертированного индекса Apache Lucene. При создании индекса задается `number_of_shards` (по умолчанию 1 в современных версиях). Все операции записи сначала поступают на Primary шард.
2. **Replica Shard (Реплика):** точная копия Primary шарда. Реплика никогда не размещается на том же физическом узле, что и её Primary. Обеспечивает:
   - Отказоустойчивость: при падении узла с Primary шард-реплика мгновенно повышается до Primary.
   - Масштабирование чтения: поисковые запросы параллельно балансируются между Primary и Replica шардами.
3. **Cluster State:** мастер-нода отслеживает здоровье шардов:
   - `GREEN`: Все primary и replica шарды распределены и активны.
   - `YELLOW`: Все primary активны, но часть реплик не назначена (unassigned).
   - `RED`: Хотя бы один primary шард недоступен (потеря данных).
4. **Recovery API (`_cat/recovery`):** позволяет отслеживать синхронизацию сегментов между узлами при падении или ребалансировке.

## Решение по шагам

1. Создайте индекс `ha_catalog` с 3 primary шардами и 2 репликами (`number_of_shards: 3`, `number_of_replicas: 2`).
2. Проверьте статус здоровья кластера через `es.Cluster.Health`.
3. Запросите состояние восстановления шардов через API `_cat/recovery`.
4. Распарсите процент синхронизации байт и файлов (`stage`, `bytes_percent`, `files_percent`).
5. Убедитесь в отсутствии потерянных шардов (unassigned_shards).

## Код решения

**`cluster_ha.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type ClusterHealthResponse struct {
	ClusterName                 string  `json:"cluster_name"`
	Status                      string  `json:"status"`
	TimedOut                    bool    `json:"timed_out"`
	NumberOfNodes               int     `json:"number_of_nodes"`
	NumberOfDataNodes           int     `json:"number_of_data_nodes"`
	ActivePrimaryShards         int     `json:"active_primary_shards"`
	ActiveShards                int     `json:"active_shards"`
	RelocatingShards            int     `json:"relocating_shards"`
	InitializingShards          int     `json:"initializing_shards"`
	UnassignedShards            int     `json:"unassigned_shards"`
	ActiveShardsPercentAsNumber float64 `json:"active_shards_percent_as_number"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Создаем индекс с 3 primary шардами и 2 репликами
	indexSettings := `{
		"settings": {
			"number_of_shards": 3,
			"number_of_replicas": 2
		}
	}`

	createReq := esapi.IndicesCreateRequest{
		Index: "ha_catalog",
		Body:  strings.NewReader(indexSettings),
	}
	res, err := createReq.Do(ctx, es)
	if err == nil {
		res.Body.Close()
	}

	// 2. Проверяем здоровье кластера
	healthRes, err := es.Cluster.Health(
		es.Cluster.Health.WithContext(ctx),
		es.Cluster.Health.WithLevel("indices"),
	)
	if err != nil {
		log.Fatalf("Ошибка Cluster.Health: %v", err)
	}
	defer healthRes.Body.Close()

	var health ClusterHealthResponse
	if err := json.NewDecoder(healthRes.Body).Decode(&health); err != nil {
		log.Fatalf("Ошибка декодирования: %v", err)
	}

	fmt.Println("=== Здоровье кластера ===")
	fmt.Printf("Кластер: %s | Статус: %s\n", health.ClusterName, health.Status)
	fmt.Printf("Узлов: %d (Data: %d) | Активных шардов: %d (%.1f%%)\n",
		health.NumberOfNodes, health.NumberOfDataNodes, health.ActiveShards, health.ActiveShardsPercentAsNumber)
	fmt.Printf("Unassigned шардов: %d, Initializing: %d\n",
		health.UnassignedShards, health.InitializingShards)

	// 3. Запрашиваем Cat Recovery для отслеживания синхронизации
	catRes, err := es.Cat.Recovery(
		es.Cat.Recovery.WithContext(ctx),
		es.Cat.Recovery.WithFormat("json"),
		es.Cat.Recovery.WithIndex("ha_catalog"),
	)
	if err != nil {
		log.Fatalf("Ошибка Cat.Recovery: %v", err)
	}
	defer catRes.Body.Close()

	fmt.Println("\n=== Статус синхронизации шардов (Cat Recovery) ===")
	var recoveries []map[string]interface{}
	if err := json.NewDecoder(catRes.Body).Decode(&recoveries); err == nil && len(recoveries) > 0 {
		for _, rec := range recoveries {
			fmt.Printf("Шард: %v | Тип: %-8v | Стадия: %-6v | Файлы: %v | Байты: %v\n",
				rec["shard"], rec["type"], rec["stage"], rec["files_percent"], rec["bytes_percent"])
		}
	} else {
		fmt.Println("Все шарды стабильны, репликация завершена.")
	}
}
```

## Под капотом

Каждый шард — это независимый экземпляр Lucene со своими файлами сегментов и `translog` (журналом упреждающей записи).
Когда падает узел или добавляется новая нода:
Мастер-нода запускает процесс **Peer Recovery**.
Реплика копирует недостающие сегменты Lucene напрямую с Primary узла по протоколу TCP.
Затем докатываются свежие записи из `translog` Primary шарда, накопившиеся за время копирования файлов. Как только разница сведена к нулю, шард переходит в состояние `done` и включается в маршрутизацию поисковых запросов.

## Подводные камни

1. Овершардинг (Shard Over-allocation): создание 20 primary шардов для индекса размером 10 МБ. Каждый шард резервирует дескрипторы файлов и память под кэши в JVM heap. Лимит в кластере — не более 20–25 шардов на 1 ГБ выделенного Heap.
2. Слишком большой размер одного шарда: размер шарда свыше 50–60 ГБ крайне затрудняет peer recovery при сбоях (копирование 50 ГБ по сети создает огромный I/O лаг).
3. Игнорирование статуса YELLOW: кластер с yellow статусом потеряет данные при выходе из строя единственного узла с primary шардом.

## На собеседовании

В: Каковы практические рекомендации BigTech по выбору количества primary шардов и размера шарда для индексов?
О: 1) **Размер одного шарда:** Для поисковых индексов (e-commerce) оптимальный размер шарда — от **10 до 30 ГБ**. Для time-series логов — от **30 до 50 ГБ**.
2) **Количество шардов:** Рассчитывается как \(\text{Ожидаемый объем данных} / 30\text{ ГБ}\). Если данных 60 ГБ — создаем 2 primary шарда.
3) **Память:** На каждые 1 ГБ JVM Heap ноды должно приходиться не более 20 активных шардов.
