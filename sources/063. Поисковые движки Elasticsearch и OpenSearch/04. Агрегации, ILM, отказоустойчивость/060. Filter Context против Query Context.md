# Filter Context против Query Context: Оптимизация скоринга и битсетов

## Условие

**Filter context > Query context.**: В bool query используйте `filter` для того, что не влияет на score (кэшируется, быстрее).

## Теория

Понимание разницы между **Query Context** и **Filter Context** — главный маркер уровня Senior в вопросах архитектуры Elasticsearch:

1. **Query Context (Контекст запроса):**
   - Вопрос: «Насколько хорошо документ соответствует условию?»
   - Вычисляет `_score` (релевантность) по формуле BM25.
   - Задействует операции с плавающей точкой в CPU.
   - Результаты **НЕ кэшируются**, так как score уникален для каждого поискового запроса.
   - Используется в секциях `must` и `should`.

2. **Filter Context (Контекст фильтра):**
   - Вопрос: «Соответствует ли документ условию: ДА или НЕТ?»
   - `_score` НЕ вычисляется (score = 0).
   - Результаты автоматически кэшируются на уровне сегментов в **Node Query Cache** в виде сжатых битовых карт (`Roaring Bitmaps`).
   - Используется в секциях `filter` и `must_not`.

В любом реальном поисковом сервисе (e-commerce, поиск по резюме, каталог недвижимости) 80% параметров запроса (город, категория, статус, диапазон цен, наличие) обязаны находиться в **Filter Context**.

## Решение по шагам

1. Сформируйте неоптимальный поисковый запрос, где фильтрация по категории, статусу и цене находится в секции `must`.
2. Замерьте время выполнения неоптимального запроса и обратите внимание на искажение `_score`.
3. Перепишите запрос на правильную архитектуру: в `must` оставьте только полнотекстовый поиск по названию, а все фильтры перенесите в массив `filter`.
4. Замерьте время оптимизированного запроса с кэшированными битсетами.
5. Продемонстрируйте чистый расчет релевантности только по искомым словам.

## Код решения

**`filter_vs_query.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"time"

	"github.com/elastic/go-elasticsearch/v8"
)

func runSearch(es *elasticsearch.Client, query map[string]interface{}) (time.Duration, float64) {
	var buf bytes.Buffer
	_ = json.NewEncoder(&buf).Encode(query)

	start := time.Now()
	res, err := es.Search(
		es.Search.WithContext(context.Background()),
		es.Search.WithIndex("products"),
		es.Search.WithBody(&buf),
	)
	if err != nil {
		log.Fatalf("Ошибка поиска: %v", err)
	}
	defer res.Body.Close()

	var result map[string]interface{}
	_ = json.NewDecoder(res.Body).Decode(&result)
	elapsed := time.Since(start)

	hits := result["hits"].(map[string]interface{})["hits"].([]interface{})
	maxScore := 0.0
	if len(hits) > 0 {
		maxScore = hits[0].(map[string]interface{})["_score"].(float64)
	}

	return elapsed, maxScore
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	// 1. ПЛОХО: Все условия в Must (Query Context) -> лишний скоринг, нет кэша
	badQuery := map[string]interface{}{
		"query": map[string]interface{}{
			"bool": map[string]interface{}{
				"must": []interface{}{
					map[string]interface{}{"match": map[string]interface{}{"title": "ноутбук"}},
					map[string]interface{}{"term": map[string]interface{}{"category.keyword": "электроника"}},
					map[string]interface{}{"term": map[string]interface{}{"in_stock": true}},
					map[string]interface{}{"range": map[string]interface{}{"price": map[string]interface{}{"gte": 50000}}},
				},
			},
		},
	}

	// 2. ИДЕАЛЬНО: Поиск в Must, фильтры в Filter (Filter Context) -> быстрые битсеты
	goodQuery := map[string]interface{}{
		"query": map[string]interface{}{
			"bool": map[string]interface{}{
				"must": []interface{}{
					map[string]interface{}{"match": map[string]interface{}{"title": "ноутбук"}},
				},
				"filter": []interface{}{
					map[string]interface{}{"term": map[string]interface{}{"category.keyword": "электроника"}},
					map[string]interface{}{"term": map[string]interface{}{"in_stock": true}},
					map[string]interface{}{"range": map[string]interface{}{"price": map[string]interface{}{"gte": 50000}}},
				},
			},
		},
	}

	badDur, badScore := runSearch(es, badQuery)
	fmt.Printf("1. Неоптимальный (Must / Query Context):   Время = %v | MaxScore = %.4f\n", badDur, badScore)

	goodDur, goodScore := runSearch(es, goodQuery)
	fmt.Printf("2. Оптимизированный (Filter Context):      Время = %v | MaxScore = %.4f\n", goodDur, goodScore)

	fmt.Println("\nВывод: Filter Context исключает лишний скоринг фильтров и активирует битсет-кэширование!")
}
```

## Под капотом

В Filter Context нода создает `RoaringDocIdSet`.
Это структура данных, сочетающая массивы 16-битных целых чисел, битовые маски и RLE (Run-Length Encoding) в зависимости от плотности совпадений в сегменте.
При повторных запросах фильтр не выполняет доступ к диску или чтение словаря терминов: пересечение фильтров выполняется через аппаратные битовые инструкции процессора (AVX2/AVX-512 `VANDPS`), отбирая документы за доли микросекунды.

## Подводные камни

1. Помещение `filter` внутрь `must` вместо размещения `filter` на том же уровне `bool`: приводит к потере семантики кэширования.
2. Использование некэшируемых фильтров с динамическим временем `now`: фильтр `{"range": {"created_at": {"gte": "now-5m"}}}` имеет уникальную строку каждый раз и не кэшируется. Округляйте до минуты: `"now-5m/m"`.
3. Помещение полнотекстового поиска в `filter`: `match` в фильтре найдет документы, но они будут отсортированы случайно, так как их `_score` будет равен 0.

## На собеседовании

В: Почему фильтры с относительным временем `now` не кэшируются, и как правильно спроектировать кэшируемый range-фильтр по времени?
О: При запросе `{"range": {"timestamp": {"gte": "now-1h"}}}` выражение `now` преобразуется в точное количество миллисекунд эпохи Unix на момент получения запроса.
Каждую миллисекунду ключ кэша меняется, делая кэширование бесполезным и засоряя Node Query Cache.
Чтобы фильтр кэшировался, используют округление даты (Date Math Rounding):
`{"range": {"timestamp": {"gte": "now-1h/m"}}}` — округление до текущей минуты.
В течение всей минуты значение ключа неизменно, фильтр мгновенно попадает в кэш битсетов и обслуживает тысячи запросов из оперативной памяти.
