# Резервное копирование и восстановление через Snapshot API

## Условие

**Снапшоты и резервное копирование.**: Зарегистрируйте snapshot repository (например, fs). Создайте snapshot индекса, удалите индекс, восстановите из snapshot.

## Теория

Единственный поддерживаемый способ надежного резервного копирования в Elasticsearch — это **Snapshot and Restore API**.
Копирование файлов директории данных (`data/nodes`) на лету при запущенном кластере категорически запрещено и приводит к повреждению сегментов Lucene.

Принцип работы Snapshots:
1. Регистрируется **Репозиторий** (`Repository`): shared filesystem (NFS), AWS S3, Google Cloud Storage, Azure Blob Storage или MinIO.
2. Создается **Снапшот**:
   - Первый снапшот копирует все сегменты Lucene выбранных индексов.
   - Все последующие снапшоты являются **инкрементальными**: копируются только вновь созданные сегменты, не затрагивая неизменные.
3. Восстановление (`Restore`): позволяет восстановить весь индекс, переименовать его (`rename_pattern`) или восстановить в другой кластер.

## Решение по шагам

1. Зарегистрируйте файловый репозиторий `my_backup_repo` типа `fs` с указанием пути `/mount/backups`.
2. Создайте снапшот `snapshot_catalog_2026` с параметром `wait_for_completion: true`.
3. Проверьте статус создания снапшота и список включенных индексов.
4. Сымитируйте потерю данных (удалите индекс `catalog`).
5. Выполните запрос на восстановление индекса из снапшота `_restore`.
6. Проверьте восстановление документов и возвращение статуса индекса в `green`.

## Код решения

**`snapshot_restore.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type SnapshotCreateResponse struct {
	Snapshot struct {
		Snapshot string   `json:"snapshot"`
		Indices  []string `json:"indices"`
		State    string   `json:"state"`
	} `json:"snapshot"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Создаем снапшот индекса products
	reqBody := `{
		"indices": "products",
		"ignore_unavailable": true,
		"include_global_state": false
	}`

	snapReq := esapi.SnapshotCreateRequest{
		Repository:          "my_backup_repo",
		Snapshot:            "prod_backup_v1",
		Body:                strings.NewReader(reqBody),
		WaitForCompletion: esapi.BoolPtr(true),
	}

	res, err := snapReq.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка создания снапшота: %v", err)
	}
	defer res.Body.Close()

	var snapResp SnapshotCreateResponse
	if err := json.NewDecoder(res.Body).Decode(&snapResp); err != nil {
		log.Fatalf("Ошибка парсинга ответа: %v", err)
	}

	fmt.Printf("Снапшот '%s' успешно создан! Статус: %s, Индексы: %v\n",
		snapResp.Snapshot.Snapshot, snapResp.Snapshot.State, snapResp.Snapshot.Indices)

	// 2. Восстановление индекса из снапшота (Restore)
	restoreBody := `{
		"indices": "products",
		"rename_pattern": "products",
		"rename_replacement": "products_restored"
	}`

	restoreReq := esapi.SnapshotRestoreRequest{
		Repository:          "my_backup_repo",
		Snapshot:            "prod_backup_v1",
		Body:                strings.NewReader(restoreBody),
		WaitForCompletion: esapi.BoolPtr(true),
	}

	restoreRes, err := restoreReq.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка Restore: %v", err)
	}
	defer restoreRes.Body.Close()

	if restoreRes.IsError() {
		log.Fatalf("Ошибка восстановления: %s", restoreRes.Status())
	}

	fmt.Println("Индекс успешно восстановлен как 'products_restored'!")
}
```

## Под капотом

Снапшоты в Lucene опираются на иммутабельность сегментов.
Когда запускается снапшот, Elasticsearch опрашивает репозиторий: если сегмент с таким хэшем/именем уже загружен в предыдущем снапшоте, он пропускается.
Загружаются только дельты — новые сегменты, созданные с момента предыдущего бэкапа.
Метаданные снапшота (список сегментов и схема) сохраняются в JSON-файлах в корне репозитория.

## Подводные камни

1. Попытка восстановить индекс в индекс с уже существующим именем: восстанавливаемый индекс обязан быть предварительно закрыт (`_close`) или удален, иначе ES вернет ошибку конфликта.
2. Отсутствие пути в `path.repo` в `elasticsearch.yml`: для файлового репозитория (`fs`) путь обязан быть явно прописан в конфигурации всех узлов кластера.
3. Создание снапшотов с `include_global_state: true`: при восстановлении на другом кластере могут быть непреднамеренно перезаписаны глобальные кластерные настройки и шаблоны индексов.

## На собеседовании

В: Почему снятие снапшота в Elasticsearch не блокирует запись новых документов и практически не влияет на производительность поиска?
О: Сегменты Apache Lucene являются неизменяемыми (write-once, immutable).
При создании снапшота движок фиксирует текущий список сегментов (Commit Point). Новые операции индексации пишутся в новые сегменты, никак не затрагивая зафиксированные.
Чтение сегментов для отправки в объектное хранилище (S3) происходит с диска или page cache с троттлингом скорости (`max_restore_bytes_per_sec`, `max_snapshot_bytes_per_sec`), предотвращая насыщение дисковой подсистемы и сети.
