# ILM для Time-Series данных и Data Streams

## Условие

**ILM для time-series.**: Автоматический rollover, shrink, delete по возрасту. Без ILM вы утонете в management overhead.

## Теория

Для потоковых данных с временными метками (логи, метрики, события безопасности, IoT) создание индексов вручную приводит к непреодолимому эксплуатационному хаосу (management overhead).

В современных версиях Elasticsearch и OpenSearch стандартом является концепция **Data Streams** в связке с **Index Lifecycle Management (ILM)**:
1. **Data Stream:** единая логическая точка входа для записи и чтения (например, `logs-backend-prod`).
2. Под капотом Data Stream состоит из скрытых backing-индексов: `.ds-logs-backend-prod-2026.09.04-000001`.
3. Запись ВСЕГДА направляется в самый свежий backing-индекс.
4. Поиск прозрачно и параллельно опрашивает все подходящие по времени backing-индексы.
5. ILM автоматически:
   - Делает **Rollover** при превышении 50 ГБ или 24 часов.
   - Переводит старые backing-индексы в фазу Warm (force merge до 1 сегмента, 1 реплика).
   - Удаляет индексы старше установленного срока хранения (Retention policy).

## Решение по шагам

1. Создайте ILM политику `metrics_policy` с фазами `hot` (rollover при 50gb/1d) и `delete` (через 30 дней).
2. Создайте компонентный шаблон (Component Template) с маппингом временной метки `@timestamp: date`.
3. Создайте Index Template с шаблоном имени `metrics-*-*` и включенным режимом `"data_stream": {}`.
4. Запишите метрику в Data Stream `metrics-system-prod` без указания номера индекса.
5. Проверьте через `_data_stream` API созданный backing-индекс и привязанную политику ILM.

## Код решения

**`data_stream_ilm.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"
	"time"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Создаем политику ILM
	ilmPolicy := `{
		"policy": {
			"phases": {
				"hot": {
					"actions": {
						"rollover": {
							"max_primary_shard_size": "50gb",
							"max_age": "1d"
						}
					}
				},
				"delete": {
					"min_age": "30d",
					"actions": {
						"delete": {}
					}
				}
			}
		}
	}`
	res, _ := es.ILM.PutLifecycle("metrics_lifecycle_policy", es.ILM.PutLifecycle.WithBody(strings.NewReader(ilmPolicy)))
	if res != nil {
		res.Body.Close()
	}

	// 2. Создаем Index Template с поддержкой Data Stream
	templateBody := `{
		"index_patterns": ["metrics-system-*"],
		"data_stream": {},
		"template": {
			"settings": {
				"index.lifecycle.name": "metrics_lifecycle_policy"
			},
			"mappings": {
				"properties": {
					"@timestamp": {"type": "date"},
					"cpu_usage":  {"type": "float"},
					"host":       {"type": "keyword"}
				}
			}
		}
	}`
	tplReq := esapi.IndicesPutIndexTemplateRequest{
		Name: "metrics_system_template",
		Body: strings.NewReader(templateBody),
	}
	tplRes, err := tplReq.Do(ctx, es)
	if err == nil {
		tplRes.Body.Close()
	}

	// 3. Индексируем запись напрямую в Data Stream
	metricDoc := map[string]interface{}{
		"@timestamp": time.Now().Format(time.RFC3339),
		"cpu_usage":  42.5,
		"host":       "prod-srv-01",
	}
	var buf bytes.Buffer
	_ = json.NewEncoder(&buf).Encode(metricDoc)

	streamReq := esapi.CreateRequest{
		Index:      "metrics-system-prod",
		DocumentID: fmt.Sprintf("metric_%d", time.Now().UnixNano()),
		Body:       &buf,
	}
	sRes, err := streamReq.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка записи в Data Stream: %v", err)
	}
	defer sRes.Body.Close()

	fmt.Printf("Документ успешно записан в Data Stream! Статус: %s\n", sRes.Status())

	// 4. Проверяем состояние Data Stream
	dsRes, _ := es.Indices.GetDataStream(es.Indices.GetDataStream.WithName("metrics-system-prod"))
	var dsInfo map[string]interface{}
	_ = json.NewDecoder(dsRes.Body).Decode(&dsInfo)
	dsRes.Body.Close()

	dataStreams := dsInfo["data_streams"].([]interface{})
	if len(dataStreams) > 0 {
		stream := dataStreams[0].(map[string]interface{})
		backingIndices := stream["indices"].([]interface{})
		fmt.Printf("Имя стрима: %s | Активных backing-индексов: %d\n",
			stream["name"], len(backingIndices))
		for _, b := range backingIndices {
			bMap := b.(map[string]interface{})
			fmt.Printf(" -> Backing index: %s\n", bMap["index_name"])
		}
	}
}
```

## Под капотом

Data Stream — это абстракция над набором индексов, упорядоченных по времени.
Каждый документ обязан содержать поле `@timestamp`.
Elasticsearch автоматически перенаправляет операции записи только в текущий backing-индекс, где установлен флаг write index.
При наступлении условий rollover (по времени или размеру) ILM атомарно создает индекс с инкрементированным суффиксом `-000002` и переключает write pointer, не требуя никаких изменений в коде приложений.

## Подводные камни

1. Попытка записи в Data Stream документа без обязательного поля `@timestamp`: сервер немедленно вернет ошибку 400.
2. Попытка ручного удаления backing-индекса в обход ILM: ломает метаданные стрима и может привести к ошибкам маршрутизации поиска.
3. Использование одного гигантского стрима для сотен разнородных сервисов: приводит к неравномерному заполнению шардов и деградации производительности.

## На собеседовании

В: Чем Data Streams в современных версиях Elasticsearch превосходят традиционные индексы с датой в названии (например, `logs-2026-09-04`)?
О: 1) **Равномерность шардов:** Индексация по дате порождает шарды разного размера (в пятницу логов в 10 раз больше, чем в воскресенье), что приводит к перекосам шардов по дискам. Rollover в Data Streams отсекает индекс строго по размеру (например, каждые 50 ГБ), гарантируя идеальный баланс данных.
2) **Автоматизация:** Приложению не нужно знать сегодняшнюю дату и вычислять имя индекса — запись всегда идет в фиксированное имя потока (`logs-app`).
3) **Нативный ILM:** Управление жизненным циклом и удаление устаревших данных происходят «из коробки» без внешних cron-скриптов типа Elasticsearch Curator.
