# Mapping First: Защита от Mapping Explosion и Strict Mapping

## Условие

**Mapping first, data later.**: Dynamic mapping в production — это техдолг. Всегда определяйте explicit mapping.

## Теория

Elasticsearch по умолчанию использует **Dynamic Mapping**: при добавлении документа с новым полем движок автоматически определяет его тип (`text + keyword`, `long`, `boolean`).

В продакшене dynamic mapping — это **грубейший антипаттерн**, приводящий к катастрофе **Mapping Explosion**:
1. Клиент или баг в коде шлет JSON с динамическими ключами (например, `user_input_<id>` или даты в качестве ключей).
2. Кластер создает тысячи новых типов полей в схеме индекса.
3. Метаданные Cluster State разрастаются до сотен мегабайт. Мастер-нода тратит 100% CPU на синхронизацию Cluster State между узлами, и кластер падает в неустранимый Red.

Решение BigTech:
- Всегда объявлять `dynamic: "strict"` в маппинге индекса.
- Любой запрос с неизвестным полем немедленно отбрасывается с ошибкой 400 Bad Request.
- Явное задание типов оптимизирует дисковое пространство и объем JVM heap.

## Решение по шагам

1. Определите JSON-схему индекса `strict_catalog` со свойством `"dynamic": "strict"`.
2. Явно опишите разрешенные поля: `sku`, `title`, `price`, `in_stock`.
3. Создайте индекс в Elasticsearch.
4. Проверьте индексацию валидного документа — она должна пройти успешно.
5. Попробуйте проиндексировать документ с необъявленным полем (например, `hacked_field`).
6. Убедитесь, что сервер вернул ошибку `strict_dynamic_mapping_exception` с кодом 400.

## Код решения

**`strict_mapping.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Создаем индекс с динамическим маппингом STRICT
	schema := `{
		"mappings": {
			"dynamic": "strict",
			"properties": {
				"sku":      {"type": "keyword"},
				"title":    {"type": "text"},
				"price":    {"type": "scaled_float", "scaling_factor": 100},
				"in_stock": {"type": "boolean"}
			}
		}
	}`

	createReq := esapi.IndicesCreateRequest{
		Index: "strict_catalog",
		Body:  strings.NewReader(schema),
	}
	res, err := createReq.Do(ctx, es)
	if err == nil {
		res.Body.Close()
	}

	// 2. Пробуем вставить валидный документ
	validDoc := `{"sku": "SKU-100", "title": "Оригинальный товар", "price": 1999.00, "in_stock": true}`
	valReq := esapi.IndexRequest{
		Index:      "strict_catalog",
		DocumentID: "doc_1",
		Body:       strings.NewReader(validDoc),
	}
	valRes, err := valReq.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка вставки: %v", err)
	}
	fmt.Printf("Валидный документ: статус %s\n", valRes.Status())
	valRes.Body.Close()

	// 3. Пробуем вставить документ с неизвестным полем "promo_code"
	invalidDoc := `{"sku": "SKU-200", "title": "Товар с акцией", "price": 999.00, "in_stock": true, "promo_code": "DISCOUNT50"}`
	invReq := esapi.IndexRequest{
		Index:      "strict_catalog",
		DocumentID: "doc_2",
		Body:       strings.NewReader(invalidDoc),
	}
	invRes, err := invReq.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка запроса: %v", err)
	}
	defer invRes.Body.Close()

	var errResp map[string]interface{}
	_ = json.NewDecoder(invRes.Body).Decode(&errResp)

	if invRes.IsError() {
		fmt.Printf("Успешно заблокирована вставка некорректного документа!\nСтатус: %s\nПричина: %v\n",
			invRes.Status(), errResp["error"].(map[string]interface{})["reason"])
	}
}
```

ℹ️ Защита индекса от Mapping Explosion с помощью правила dynamic: strict

**`Терминал`**

```bash

# Вывод:

# Успешно заблокирована вставка некорректного документа!

```

## Под капотом

Кластерный статус (Cluster State) включает полную схему маппинга каждого шарда и индекса.
При dynamic mapping добавление каждого нового поля требует:
1. Отправки запроса на изменение мастер-ноде.
2. Сериализации нового Cluster State мастером.
3. Рассылки обновленного состояния всем нодам кластера по протоколу Raft/Zen Discovery.
Когда полей тысячи, Cluster State разрастается, ноды не успевают применять обновления (Cluster State Update Timeout), вызывая флаппинг нод и распад кластера.

## Подводные камни

1. Использование `"dynamic": true` на индексах, принимающих сырые логи (Fluentbit/Logstash/Vector) без жесткой валидации полей.
2. Автоматическое определение чисел с плавающей точкой: dynamic mapping делает их `float` или `double`, что занимает 8 байт. Использование `scaled_float` с фиксированной точкой экономит до 50% диска и RAM.
3. Использование `dynamic: false`: новые поля тихо игнорируются при индексации (не ищутся), но сохраняются в `_source`, что может сбить с толку разработчиков.

## На собеседовании

В: Что такое параметр `index.mapping.total_fields.limit` и почему он по умолчанию равен 1000?
О: Это защитный предохранитель (circuit breaker), введенный для защиты кластера от деградации памяти и сбоев мастер-нод при Mapping Explosion.
Если число уникальных полей в индексе превышает 1000, Elasticsearch отклоняет любые новые поля.
Увеличение этого лимита (например, до 5000) в продакшене считается антипаттерном: вместо расширения лимита необходимо перепроектировать модель данных (использовать `nested` пары ключ-значение или `flattened` тип данных).
