# Обязательность Bulk API в HighLoad: Архитектура и бенчмарки

## Условие

**Bulk API обязателен.**: Single-document indexing в 100x медленнее. Используйте `BulkIndexer` с оптимальным flush interval.

## Теория

В высоконагруженных системах одиночная индексация документов (`IndexRequest`) категорически неприемлема.
Разница в пропускной способности между одиночными вставками и Bulk API достигает **100–300 раз**:

Почему одиночные запросы медленные:
1. **Сетевой оверхед:** 10 000 HTTP запросов требуют 10 000 round-trips, парсинга HTTP заголовков и подтверждений TCP ACK.
2. **Накладные расходы Lucene:** Каждая отдельная операция открывает транзакционный лог (`translog`), выполняет блокировку сегмента и нагружает поток индексации.
3. **Пул потоков write:** Очередь потоков записи на нодах быстро переполняется (`EsRejectedExecutionException`).

Правила работы с Bulk в проде:
- Использовать `esutil.NewBulkIndexer`.
- Оптимальный размер пакета: 5–15 МБ (в зависимости от размера документа).
- Экспоненциальный backoff при получении HTTP статуса `429 Too Many Requests`.

## Решение по шагам

1. Напишите функцию одиночной индексации 500 документов в цикле с замером времени.
2. Напишите функцию пакетной загрузки тех же 500 документов через `esutil.NewBulkIndexer`.
3. Сравните затраченное время (ms) и скорость (docs/sec).
4. Настройте обработчик ошибки 429 с повторной отправкой документа в очередь.

## Код решения

**`bulk_benchmark.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"
	"time"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
	"github.com/elastic/go-elasticsearch/v8/esutil"
)

func runSingleIndexing(es *elasticsearch.Client, count int) time.Duration {
	start := time.Now()
	for i := 1; i <= count; i++ {
		doc := fmt.Sprintf(`{"id": %d, "title": "Товар %d"}`, i, i)
		req := esapi.IndexRequest{
			Index:      "bench_single",
			DocumentID: fmt.Sprintf("single_%d", i),
			Body:       strings.NewReader(doc),
		}
		res, err := req.Do(context.Background(), es)
		if err == nil {
			res.Body.Close()
		}
	}
	return time.Since(start)
}

func runBulkIndexing(es *elasticsearch.Client, count int) time.Duration {
	bi, err := esutil.NewBulkIndexer(esutil.BulkIndexerConfig{
		Index:         "bench_bulk",
		Client:        es,
		NumWorkers:    4,
		FlushBytes:    5 * 1024 * 1024,
		FlushInterval: 100 * time.Millisecond,
	})
	if err != nil {
		log.Fatalf("Ошибка BulkIndexer: %v", err)
	}

	start := time.Now()
	ctx := context.Background()

	for i := 1; i <= count; i++ {
		doc := map[string]interface{}{"id": i, "title": fmt.Sprintf("Товар %d", i)}
		data, _ := json.Marshal(doc)

		_ = bi.Add(ctx, esutil.BulkIndexerItem{
			Action:     "index",
			DocumentID: fmt.Sprintf("bulk_%d", i),
			Body:       bytes.NewReader(data),
		})
	}

	_ = bi.Close(ctx)
	return time.Since(start)
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	count := 500
	fmt.Printf("Сравнение производительности одиночной и Bulk индексации (%d документов)...\n\n", count)

	singleDur := runSingleIndexing(es, count)
	singleRps := float64(count) / singleDur.Seconds()
	fmt.Printf("1. Одиночная индексация: %v (%.1f docs/sec)\n", singleDur, singleRps)

	bulkDur := runBulkIndexing(es, count)
	bulkRps := float64(count) / bulkDur.Seconds()
	fmt.Printf("2. Пакетная Bulk индексация: %v (%.1f docs/sec)\n\n", bulkDur, bulkRps)

	speedup := singleDur.Seconds() / bulkDur.Seconds()
	fmt.Printf(">>> Ускорение с Bulk API: %.1fx быстрее! <<<\n", speedup)
}
```

## Под капотом

При Bulk-запросе нода-координатор парсит заголовки документов из потока и распределяет операции по шард-батчам (Shard Bulk Requests).
Каждый шард получает пачку операций и выполняет единую блокировку сегмента Lucene, единую запись в `translog` и батчевый сброс в память.
Это кардинально уменьшает число context switch ядра ОС и число системных вызовов `write`/`fsync`.

## Подводные камни

1. Отправка пакетов гигантского размера (например, 200 МБ в одном запросе): переполняет память нод, вызывает длительные GC паузы и HTTP 413.
2. Игнорирование ошибок конкретных элементов внутри батча: Bulk API возвращает HTTP 200, даже если 50% документов внутри батча упали с ошибкой. Необходимо всегда проверять поле `errors: true` и статус каждого элемента.
3. Отсутствие механизма повтора (retry) при HTTP 429: отвергнутые документы просто теряются.

## На собеседовании

В: Почему при ответе с кодом 200 OK на Bulk-запрос часть документов может не сохраниться?
О: Bulk API спроектирован по принципу частичного успеха: операция каждого документа внутри пакета изолирована.
Сам HTTP-запрос возвращает 200 OK, сигнализируя, что кластер принял и обработал пакет.
В теле JSON-ответа присутствует поле `"errors": true/false`.
Если хотя бы один документ вызвал ошибку маппинга (`strict_dynamic_mapping_exception`) или конфликт версий (`version_conflict_engine_exception`), статус этого конкретного элемента в массиве `items` будет 400 или 409.
Клиент обязан проверять `resp.Errors` и парсить статус каждого отдельного элемента.
