# Массовая модификация данных через Painless и UpdateByQuery

## Условие

**Паттерн Update By Query**: У тебя поменялась бизнес-логика. Тебе нужно добавить всем товарам из категории "X" новое поле `is_archived: true`. Напиши скрипт на языке Painless (встроенный в ES) и выполни его для миллионов документов через API `UpdateByQuery` прямо из Go.

---

## Теория

При эволюции схемы базы данных или бизнес-логики часто требуется обогатить старые документы:
Например, пометить все товары категории «Распродажа» флагом `is_archived: true` или нормализовать телефонные номера.

Паттерн массовой модификации:
1. Построение `UpdateByQuery` запроса с фильтром по категории.
2. Написание inline Painless скрипта:
   `ctx._source.is_archived = true; ctx._source.archived_at = params.now;`
3. Использование `wait_for_completion=false` для длительных операций на миллионы строк: запрос возвращает `Task ID`.
4. Клиент на Go поллит Task API (`_tasks/<task_id>`) до завершения операции, отображая прогресс в терминале.
5. Указание `conflicts=proceed` для игнорирования версионных гонок.

## Решение по шагам

1. Сформируйте `UpdateByQuery` запрос с фильтром `term` по полю `category.keyword: "Архив"`.
2. Напишите Painless скрипт, устанавливающий `ctx._source.is_archived = true`.
3. Установите `wait_for_completion: false`, чтобы получить `task_id` немедленно.
4. В цикле опрашивайте `es.Tasks.Get(task_id)` раз в 1 секунду.
5. Проверяйте флаг `completed: true`.
6. Распечатайте количество обновленных документов и суммарное время работы задачи.

## Код решения

**`painless_update.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"time"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type TaskStartResponse struct {
	Task string `json:"task"`
}

type TaskStatusResponse struct {
	Completed bool  `json:"completed"`
	Task      struct {
		Action string `json:"action"`
		Status struct {
			Total   int64 `json:"total"`
			Updated int64 `json:"updated"`
			Created int64 `json:"created"`
		} `json:"status"`
	} `json:"task"`
	Response struct {
		Took int64 `json:"took"`
	} `json:"response"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Формируем запрос с Painless скриптом
	payload := map[string]interface{}{
		"script": map[string]interface{}{
			"source": "ctx._source.is_archived = params.flag; ctx._source.archived_at = params.timestamp;",
			"lang":   "painless",
			"params": map[string]interface{}{
				"flag":      true,
				"timestamp": time.Now().Format(time.RFC3339),
			},
		},
		"query": map[string]interface{}{
			"term": map[string]interface{}{
				"category.keyword": "Распродажа",
			},
		},
	}

	var buf bytes.Buffer
	_ = json.NewEncoder(&buf).Encode(payload)

	// 2. Запускаем асинхронную задачу через wait_for_completion=false
	req := esapi.UpdateByQueryRequest{
		Index:             []string{"products"},
		Body:              &buf,
		Conflicts:         "proceed",
		WaitForCompletion: esapi.BoolPtr(false),
	}

	res, err := req.Do(ctx, es)
	if err != nil {
		log.Fatalf("Ошибка запуска задачи: %v", err)
	}
	defer res.Body.Close()

	var taskStart TaskStartResponse
	_ = json.NewDecoder(res.Body).Decode(&taskStart)
	taskID := taskStart.Task
	fmt.Printf("Асинхронная задача запущена. Task ID: %s\n", taskID)

	// 3. Поллинг Task API до завершения
	for {
		time.Sleep(1 * time.Second)
		taskRes, err := es.Tasks.Get(taskID)
		if err != nil {
			log.Printf("Ошибка получения статуса: %v", err)
			continue
		}

		var status TaskStatusResponse
		_ = json.NewDecoder(taskRes.Body).Decode(&status)
		taskRes.Body.Close()

		fmt.Printf("Прогресс: обработано %d из %d документов...\n",
			status.Task.Status.Updated, status.Task.Status.Total)

		if status.Completed {
			fmt.Printf("Задача %s успешно выполнена за %dms! Обновлено: %d\n",
				taskID, status.Response.Took, status.Task.Status.Updated)
			break
		}
	}
}
```

## Под капотом

Асинхронный `_update_by_query` регистрирует Task в кластерном реестре задач (Task Manager).
Координатор распределяет подзадачи по шардам данных, где каждый шард берет внутренний scroll и исполняет Painless через JIT-скомпилированный класс.
Парсинг документа, исполнение скрипта и упаковка в bulk-update происходят непосредственно в памяти ноды без пересылки документов по сети в Go-приложение.

## Подводные камни

1. Забытый `params` при передаче временной метки `time.Now()`: если интерполировать время строкой в текст скрипта, каждый запуск создаст новый класс скрипта, что моментально вызовет `CircuitBreakingException` по кэшу скриптов.
2. Обращение к несуществующему полю без проверки `ctx._source.containsKey('field')`: в Painless скрипт выбросит `NullPointerException` и аварийно завершит партию.
3. Отсутствие параметра `requests_per_second` (throttling) при обновлении 100 млн документов: может вызвать деградацию пользовательского поиска из-за предельной нагрузки на диск.

## На собеседовании

В: Как ограничить нагрузку на кластер при выполнении огромного `_update_by_query` на 500 миллионов документов в пиковые часы?
О: 1) Использовать параметр `requests_per_second` (throttling): например, `requests_per_second=500` распределяет нагрузку, замедляя сброс пакетов и гарантируя, что дисковая подсистема не будет монополизирована фоновым процессом.
2) Использовать динамическое изменение троттлинга на лету через `_tasks/<task_id>/_rethrottle?requests_per_second=1000`.
3) Запускать задачу со `slices: auto` для параллельной обработки шардов без перекосов между узлами.
