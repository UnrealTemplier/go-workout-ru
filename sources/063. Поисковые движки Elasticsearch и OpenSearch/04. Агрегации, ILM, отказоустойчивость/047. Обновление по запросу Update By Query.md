# Обновление по запросу Update By Query и Painless скрипты

## Условие

**Обновление по запросу и скрипты.**: Увеличьте цену всех товаров определённой категории на 10% с помощью `update_by_query` и Painless скрипта. Проверьте атомарность.

## Теория

Когда требуется обновить миллионы документов по критерию (например, поднять цену на 10% для категории «смартфоны»), выполнять выборку в приложение и отправку bulk update неэффективно.
Для этого используется `_update_by_query`:
1. Elasticsearch локально находит все подходящие документы с помощью внутреннего snapshot scroll.
2. Для каждого документа исполняется скрипт на встроенном языке **Painless**.
3. Painless — это строго типизированный, безопасный и оптимизированный язык, компилируемый напрямую в байткод JVM.
4. В скрипте доступен контекст `ctx._source`, через который модифицируются поля документа.

Для предотвращения падения всей операции при конкурентном изменении документов указывается параметр `conflicts=proceed`.

## Решение по шагам

1. Сформируйте поисковый фильтр (например, `category.keyword: "смартфоны"`).
2. Напишите Painless скрипт: `ctx._source.price = ctx._source.price * params.multiplier`.
3. Передайте параметры через объект `params` (это критически важно для кэширования скомпилированного скрипта).
4. Вызовите `es.UpdateByQuery` с передачей индекса, фильтра и скрипта.
5. Распарсите статистику ответа: количество обновленных документов, конфликтов версий и затраченное время.

## Код решения

**`update_by_query.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

type UpdateByQueryResponse struct {
	Took             int64 `json:"took"`
	TimedOut         bool  `json:"timed_out"`
	Total            int64 `json:"total"`
	Updated          int64 `json:"updated"`
	Batches          int64 `json:"batches"`
	VersionConflicts int64 `json:"version_conflicts"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	// Обновление цены на 10% через параметризованный Painless скрипт
	payload := map[string]interface{}{
		"script": map[string]interface{}{
			"source": "ctx._source.price = ctx._source.price * params.multiplier",
			"lang":   "painless",
			"params": map[string]interface{}{
				"multiplier": 1.10,
			},
		},
		"query": map[string]interface{}{
			"term": map[string]interface{}{
				"category.keyword": "смартфоны",
			},
		},
	}

	var buf bytes.Buffer
	if err := json.NewEncoder(&buf).Encode(payload); err != nil {
		log.Fatalf("Ошибка кодирования: %v", err)
	}

	req := esapi.UpdateByQueryRequest{
		Index:     []string{"products"},
		Body:      &buf,
		Conflicts: "proceed",
	}

	res, err := req.Do(context.Background(), es)
	if err != nil {
		log.Fatalf("Ошибка UpdateByQuery: %v", err)
	}
	defer res.Body.Close()

	var resp UpdateByQueryResponse
	if err := json.NewDecoder(res.Body).Decode(&resp); err != nil {
		log.Fatalf("Ошибка парсинга: %v", err)
	}

	fmt.Printf("Обновление завершено за %dms\n", resp.Took)
	fmt.Printf("Всего документов: %d, Обновлено: %d, Конфликтов версий: %d\n",
		resp.Total, resp.Updated, resp.VersionConflicts)
}
```

## Под капотом

Под капотом `_update_by_query` берет снимок индекса на момент старта.
Поскольку документы в Lucene неизменяемы, физически обновление представляет собой soft-delete старого документа (пометка бита в `.del` файле) и создание нового документа с инкрементированным `_version`.
Если во время выполнения скрипта сторонний запрос обновил документ, его версия изменится, что вызовет Version Conflict. При `conflicts: proceed` такой конфликт фиксируется в счетчике, но операция не прерывается.

## Подводные камни

1. Конкатенация значений в строку скрипта вместо использования `params`:
Каждый уникальный скрипт компилируется в байткод JVM. При динамической строке скриптов лимит кэша компилятора (`script.max_compilations_rate`) быстро исчерпается и ES вернет ошибку `circuit_breaking_exception`.
2. Запуск долгого `_update_by_query` синхронно: приведет к разрыву HTTP соединения. Используйте `wait_for_completion=false`.
3. Ожидание транзакционной атомарности: `_update_by_query` НЕ является транзакцией. Если в середине процесса упадет узел, часть документов уже будет обновлена, а часть — нет.

## На собеседовании

В: Почему в Painless скриптах критически важно передавать переменные через `params`, а не подставлять их строковой интерполяцией?
О: Движок Painless компилирует исходный код скрипта в исполняемый байткод JVM и кэширует скомпилированные классы по хэшу текста скрипта.
Если подставлять значения строкой (`source: "ctx._source.price += " + val`), каждый вызов создает уникальный текст, засоряя память метаданных JVM и вызывая дорогостоящую перекомпиляцию.
При передаче через `params` код скрипта статичен, компилируется один раз и мгновенно исполняется из кэша для миллионов записей.
