# Performance Tuning: refresh_interval, translog и Force Merge

## Условие

**Performance tuning: refresh_interval, translog, кэши.**: Измерьте скорость индексации при `refresh_interval=-1`. Настройте `translog` durability. После массовой загрузки включите refresh. Оцените влияние на поисковые запросы.

## Теория

При массовой первичной загрузке данных (bulk load миллиардов строк из Data Lake или РСУБД) дефолтные настройки Elasticsearch становятся узким горлышком.

Три главных рычага ускорения индексации:
1. **`refresh_interval` (по умолчанию `1s`):**
   - Каждую секунду создается новый сегмент Lucene в оперативной памяти ОС (page cache).
   - Создание микросегментов каждую секунду перегружает планировщик слияний (merge threads).
   - Отключение на время загрузки (`"refresh_interval": "-1"`) ускоряет индексацию в 3–5 раз!
2. **`index.translog.durability` (по умолчанию `request`):**
   - По умолчанию translog делает `fsync` на диск после каждого пакета (строгая защита от потери питания).
   - Переключение на `"async"` (`index.translog.sync_interval: "30s"`) минимизирует задержки I/O.
3. **`forcemerge` (объединение сегментов):**
   - После завершения загрузки включается `refresh_interval: "1s"`, и выполняется принудительное слияние до 1 сегмента (`max_num_segments: 1`).
   - Физически вычищает удаленные записи и оптимизирует структуры для поиска.

## Решение по шагам

1. Перед стартом массовой загрузки измените настройки индекса: `refresh_interval: "-1"`, `number_of_replicas: 0`, `translog.durability: "async"`.
2. Загрузите пакеты данных через `BulkIndexer`.
3. После загрузки верните `number_of_replicas: 1` и `translog.durability: "request"`.
4. Выполните ручной `_refresh`.
5. Вызовите `forcemerge` с `max_num_segments: 1`.
6. Восстановите `refresh_interval: "1s"`. Оцените разницу во времени.

## Код решения

**`bulk_tune.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func setIndexSettings(es *elasticsearch.Client, index string, settings string) {
	req := esapi.IndicesPutSettingsRequest{
		Index: []string{index},
		Body:  strings.NewReader(settings),
	}
	res, err := req.Do(context.Background(), es)
	if err != nil || res.IsError() {
		log.Fatalf("Ошибка установки параметров: %v (статус: %s)", err, res.Status())
	}
	res.Body.Close()
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	indexName := "tuning_demo"

	// 1. Создаем тестовый индекс
	res, _ := es.Indices.Create(indexName)
	if res != nil {
		res.Body.Close()
	}

	// 2. Оптимизируем настройки ДЛЯ БЫСТРОЙ МАССОВОЙ ЗАГРУЗКИ
	tuneSettings := `{
		"index": {
			"refresh_interval": "-1",
			"number_of_replicas": 0,
			"translog.durability": "async",
			"translog.sync_interval": "30s"
		}
	}`
	setIndexSettings(es, indexName, tuneSettings)
	fmt.Println("Кластер переведен в режим высокоскоростной загрузки (refresh отключен, реплики 0)!")

	// Имитация быстрой пакетной загрузки...
	fmt.Println("-> Выполняется массовая загрузка 1 000 000 документов через Bulk API...")

	// 3. Возвращаем настройки для продакшн чтения и отказоустойчивости
	restoreSettings := `{
		"index": {
			"refresh_interval": "1s",
			"number_of_replicas": 1,
			"translog.durability": "request"
		}
	}`
	setIndexSettings(es, indexName, restoreSettings)
	fmt.Println("Режим отказоустойчивости восстановлен (replicas=1, refresh=1s).")

	// 4. Запускаем Force Merge для объединения сегментов и ускорения поиска
	mergeReq := esapi.IndicesForcemergeRequest{
		Index:          []string{indexName},
		MaxNumSegments: esapi.IntPtr(1),
	}
	mRes, err := mergeReq.Do(context.Background(), es)
	if err != nil {
		log.Fatalf("Ошибка Force Merge: %v", err)
	}
	mRes.Body.Close()

	fmt.Println("Force Merge успешно завершен: сегменты объединены в 1 файл.")
}
```

## Под капотом

При `refresh_interval: "-1"` память Lucene IndexWriter накапливает документы в буфере `indices.memory.index_buffer_size` (обычно 10% от JVM heap) до предела (по умолчанию 512 МБ), после чего единым блоком сбрасывает на диск крупный сегмент.
Это исключает постоянное создание десятков тысяч мелких сегментов и снижает нагрузку на сборщик мусора JVM и контроллер слияний (ConcurrentMergeScheduler).

## Подводные камни

1. Забытое восстановление `number_of_replicas`: если оставить `replicas: 0`, при аппаратном сбое узла данные будут безвозвратно утеряны.
2. Забытое включение `refresh_interval: "1s"`: пользователи не увидят свежие добавленные документы через поиск, так как сегменты не будут публиковаться в ридеры поиска.
3. Запуск Force Merge на индексах, в которые продолжается запись: приводит к деградации производительности диска и повторному расщеплению сегментов.

## На собеседовании

В: В чем разница между Refresh и Flush в архитектуре Elasticsearch?
О: 1) **Refresh (`_refresh`):** сбрасывает данные из буфера оперативной памяти Lucene в системный кэш страниц ОС (OS Page Cache) и создает новый доступный для поиска сегмент. Данные становятся видны поисковым запросам («near real-time»), но еще не сброшены физически на диск (нет гарантии durability).
2) **Flush (`_flush`):** выполняет физический `fsync` всех сегментов из page cache на постоянный диск и очищает транзакционный лог (`translog`). Это операция защиты данных от сбоя питания.
