# Text vs Keyword: Архитектурный выбор и подводные камни

## Условие

**Text vs Keyword.**: 90% ошибок новичков — использование `text` для filtering/aggregations. Используйте `keyword` для точных совпадений.

## Теория

Более 90% ошибок проектирования и проблем с производительностью в Elasticsearch связаны с непониманием разницы между `text` и `keyword`:

| Характеристика | Тип `text` | Тип `keyword` |
| :--- | :--- | :--- |
| **Назначение** | Полнотекстовый поиск (статьи, отзывы, описания) | Точные значения (UUID, email, статус, тэг, IP) |
| **Анализ/Токенизация**| Проходит через Analyzer (разбивка на слова, lowercase) | Сохраняется байт-в-байт как единый неделимый токен |
| **Основная структура**| Инвертированный индекс (Inverted Index) | Колоночные `doc_values` + инвертированный индекс |
| **Фильтрация/Сортировка**| Запрещена (или дорогая `fielddata` в heap) | Мгновенная сортировка и фильтрация по `doc_values` |
| **Агрегации** | Требует опасный `fielddata` (риск OOM) | Нативная поддержка через `doc_values` |
| **Нормализация длины**| Хранит `norms` (веса длины поля для BM25) | `norms: false` по умолчанию (колоссальная экономия) |

Дефолтное поведение `text` + `fields.keyword` (multifield) удваивает объем хранимых индексов. В BigTech для каждого поля выбирается **строго один тип**.

## Решение по шагам

1. Создайте индекс `articles` с полем `slug` типа `keyword` и `content` типа `text`.
2. Добавьте документ со `slug: "Golang-Best-Practices-2026"` и текстом статьи.
3. Продемонстрируйте точный поиск `term` по полю `slug` (учитывая регистр).
4. Продемонстрируйте полнотекстовый поиск `match` по полю `content` с автоматическим приведением к нижнему регистру и стеммингом.
5. Выполните агрегацию `terms` по полю `slug` и покажите, что агрегация по `content` вернет ошибку.

## Код решения

**`text_vs_keyword.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
	"github.com/elastic/go-elasticsearch/v8/esapi"
)

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка инициализации клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Создаем индекс с четким разделением text и keyword
	schema := `{
		"mappings": {
			"properties": {
				"slug":    {"type": "keyword"},
				"content": {"type": "text", "analyzer": "standard"}
			}
		}
	}`
	res, _ := es.Indices.Create("articles_types", es.Indices.Create.WithBody(strings.NewReader(schema)))
	if res != nil {
		res.Body.Close()
	}

	// 2. Индексируем документ
	doc := `{"slug": "Go-HighLoad-Tips", "content": "Изучаем архитектуру рантайма Go и многопоточность."}`
	idxRes, _ := es.Index("articles_types", strings.NewReader(doc), es.Index.WithDocumentID("1"), es.Index.WithRefresh("true"))
	idxRes.Body.Close()

	// 3. Точный поиск Term по Keyword (требует точного совпадения регистра)
	termQuery := map[string]interface{}{
		"query": map[string]interface{}{
			"term": map[string]interface{}{
				"slug": "Go-HighLoad-Tips",
			},
		},
	}
	var buf bytes.Buffer
	_ = json.NewEncoder(&buf).Encode(termQuery)
	termRes, _ := es.Search(es.Search.WithIndex("articles_types"), es.Search.WithBody(&buf))
	var termResult map[string]interface{}
	_ = json.NewDecoder(termRes.Body).Decode(&termResult)
	termRes.Body.Close()

	totalHits := termResult["hits"].(map[string]interface{})["total"].(map[string]interface{})["value"].(float64)
	fmt.Printf("Поиск Term по keyword ('Go-HighLoad-Tips'): найдено %0.f документов\n", totalHits)

	// 4. Полнотекстовый поиск Match по Text (регистронезависимый)
	matchQuery := map[string]interface{}{
		"query": map[string]interface{}{
			"match": map[string]interface{}{
				"content": "АРХИТЕКТУРУ РАНТАЙМА",
			},
		},
	}
	buf.Reset()
	_ = json.NewEncoder(&buf).Encode(matchQuery)
	matchRes, _ := es.Search(es.Search.WithIndex("articles_types"), es.Search.WithBody(&buf))
	var matchResult map[string]interface{}
	_ = json.NewDecoder(matchRes.Body).Decode(&matchResult)
	matchRes.Body.Close()

	matchHits := matchResult["hits"].(map[string]interface{})["total"].(map[string]interface{})["value"].(float64)
	fmt.Printf("Поиск Match по text ('АРХИТЕКТУРУ РАНТАЙМА'): найдено %0.f документов\n", matchHits)
}
```

## Под капотом

Для поля `keyword` создаются `doc_values` — структуры сжатых столбцов с фиксированным размером записи, мапируемые в память ОС.
Для поля `text` создаются инвертированные списки постинга (Posting Lists) и позиции терминов, плюс 1 байт на документ для структуры `norms` (хранящей длину поля).
Попытка отсортировать выдачу по `text` без doc_values требует поднятия всех токенов из инвертированного индекса в JVM heap (`fielddata`), что вызывает мгновенный всплеск аллокаций и зависание Garbage Collector.

## Подводные камни

1. Использование multifield `text` + `fields: {"keyword": ...}` на всех полях без разбора: удваивает нагрузку на диск и процессор при индексации.
2. Попытка фильтрации `term` по полю типа `text`: поле в индексе приведено к нижнему регистру стандартным анализатором, поэтому поиск `term: "Moscow"` ничего не найдет.
3. Включение `fielddata: true` на production кластере для сортировки по тексту: гарантированный путь к регулярным падениям кластера с OOM.

## На собеседовании

В: Что произойдет, если в индексе с 50 миллионами документов попытаться выполнить terms агрегацию по полю типа `text`?
О: По умолчанию Elasticsearch выбросит исключение:
`Fielddata is disabled on [field] in [index]. Set fielddata=true on [field] in order to load fielddata in memory`.
Если неопытный инженер включит `fielddata: true`, при первом же запросе нода попытается загрузить словарь терминов всех 50 млн документов из инвертированного индекса прямо в JVM heap.
Это вызовет сработку `Fielddata Circuit Breaker` (если он включен) или исчерпает кучу JVM, отправив ноду в глубокую GC-паузу на десятки секунд с последующим исключением ноды из кластера.
