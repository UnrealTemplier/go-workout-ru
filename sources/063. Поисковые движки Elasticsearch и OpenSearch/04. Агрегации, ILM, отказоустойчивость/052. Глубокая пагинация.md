# Глубокая пагинация: Point In Time (PIT) и search_after

## Условие

**Scroll / Point in Time (Глубокая пагинация)**: По умолчанию ES не отдает больше 10 000 результатов (параметры `from` и `size` падают с ошибкой). Чтобы выгрузить весь индекс (миллионы записей), используй API `Scroll` или современный `Point In Time (PIT)` в цикле (передавая `search_after`).

## Теория

По умолчанию Elasticsearch запрещает пагинацию глубже 10 000 результатов:
Параметр `index.max_result_window` по умолчанию равен 10 000. Попытка запросить `from=10000, size=10` приведет к ошибке:
`Result window is too large, from + size must be less than or equal to: [10000]`.

Причина — экспоненциальный рост нагрузки: чтобы отдать результаты с 100 000 по 100 010, каждый шард обязан найти и отсортировать в памяти 100 010 документов, переслать их на координатор, где координатор проведет слияние \(100010 \times N\) записей.

Современное решение для глубокой выгрузки данных:
1. **Point in Time (PIT):** замораживает состояние индекса на момент открытия (`OpenPointInTime`). Изменения в индексе не влияют на срез данных.
2. **`search_after`:** курсорная пагинация, где следующий запрос передает значения полей сортировки последней записи предыдущей страницы.
3. По сравнению с устаревшим `Scroll API`, PIT со `search_after` не удерживает тяжелые контексты поиска на шардах и поддерживает параллельные сортировки.

## Решение по шагам

1. Откройте Point in Time с помощью `es.OpenPointInTime` с параметром `keep_alive: "2m"`. Получите `id` PIT.
2. Настройте запрос с передачей `pit.id`, обязательной сортировкой по уникальному полю (например, `id: asc` или `_shard_doc: asc`), и размером страницы `size: 1000`.
3. В цикле выполняйте `es.Search`.
4. Извлекайте из последнего элемента `hits.hits` массив `sort` значений.
5. Передавайте этот массив в параметр `search_after` следующего запроса.
6. При получении пустого списка хитов закройте PIT методом `es.ClosePointInTime`.

## Код решения

**`pit_search_after.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"
	"strings"

	"github.com/elastic/go-elasticsearch/v8"
)

type PitOpenResponse struct {
	ID string `json:"id"`
}

type PitSearchResponse struct {
	Hits struct {
		Hits []struct {
			ID     string        `json:"_id"`
			Source map[string]any `json:"_source"`
			Sort   []interface{} `json:"sort"`
		} `json:"hits"`
	} `json:"hits"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка создания клиента: %v", err)
	}

	ctx := context.Background()

	// 1. Открываем Point in Time на 2 минуты
	pitRes, err := es.OpenPointInTime(
		es.OpenPointInTime.WithContext(ctx),
		es.OpenPointInTime.WithIndex("products"),
		es.OpenPointInTime.WithKeepAlive("2m"),
	)
	if err != nil {
		log.Fatalf("Ошибка OpenPointInTime: %v", err)
	}
	defer pitRes.Body.Close()

	var pitOpen PitOpenResponse
	if err := json.NewDecoder(pitRes.Body).Decode(&pitOpen); err != nil {
		log.Fatalf("Ошибка декодирования PIT: %v", err)
	}
	pitID := pitOpen.ID
	fmt.Printf("PIT открыт успешно. ID: %s...\n", pitID[:20])

	// 2. Цикл глубокой выгрузки с поиском по search_after
	var lastSort []interface{}
	pageSize := 1000
	totalExported := 0

	for {
		searchBody := map[string]interface{}{
			"size": pageSize,
			"pit": map[string]interface{}{
				"id":         pitID,
				"keep_alive": "2m",
			},
			"sort": []map[string]string{
				{"_shard_doc": "asc"},
			},
		}

		if len(lastSort) > 0 {
			searchBody["search_after"] = lastSort
		}

		var buf bytes.Buffer
		_ = json.NewEncoder(&buf).Encode(searchBody)

		res, err := es.Search(
			es.Search.WithContext(ctx),
			es.Search.WithBody(&buf),
		)
		if err != nil {
			log.Fatalf("Ошибка Search: %v", err)
		}

		var searchRes PitSearchResponse
		_ = json.NewDecoder(res.Body).Decode(&searchRes)
		res.Body.Close()

		hitsCount := len(searchRes.Hits.Hits)
		if hitsCount == 0 {
			break // Все документы выгружены
		}

		totalExported += hitsCount
		lastHit := searchRes.Hits.Hits[hitsCount-1]
		lastSort = lastHit.Sort

		// Обновляем pitID (Elasticsearch может возвращать обновленный ID)
		if len(searchRes.Hits.Hits) > 0 {
			fmt.Printf("Выгружено документов: %d (последний ID: %s)\n", totalExported, lastHit.ID)
		}
	}

	// 3. Закрываем PIT
	closeBody := strings.NewReader(fmt.Sprintf(`{"id": "%s"}`, pitID))
	closeRes, err := es.ClosePointInTime(es.ClosePointInTime.WithContext(ctx), es.ClosePointInTime.WithBody(closeBody))
	if err == nil {
		closeRes.Body.Close()
	}

	fmt.Printf("Глубокая выгрузка завершена! Всего записей: %d. PIT закрыт.\n", totalExported)
}
```

ℹ️ Полноценный цикл выгрузки сотен тысяч записей через Point In Time и search_after

## Под капотом

PIT удерживает ридеры сегментов Lucene (`IndexReader`), запрещая удаление старых файлов сегментов сборщиком мусора Elasticsearch даже при слияниях (segment merge).
Сортировка по `{"_shard_doc": "asc"}` оптимизирована на аппаратном уровне: движок сканирует документы строго в порядке их внутреннего размещения в сегментах без загрузки `doc_values` и сравнения строк, обеспечивая максимальную скорость чтения.

## Подводные камни

1. Забытое закрытие PIT (`ClosePointInTime`): удерживает сегменты на диске. Если в кластер идет интенсивная запись, старые сегменты не удаляются, вызывая исчерпание дискового пространства (Disk Watermark Exceeded).
2. Использование `search_after` без уникального tie-breaker в поле сортировки: если документы имеют одинаковые значения в `sort`, часть документов с одинаковыми ключами будет пропущена между страницами.
3. Попытка использовать устаревший `Scroll API` в новых версиях: Scroll замораживает состояние шардов и не поддерживается многими фичами Elastic Cloud.

## На собеседовании

В: Почему параметр `from + size` ограничен значением 10 000 по умолчанию, и почему увеличение `max_result_window` до 1 000 000 — катастрофическая ошибка?
О: При `from: 999900, size: 100` нода-координатор запрашивает у **каждого** шарда индекса топ-1 000 000 результатов.
Если в индексе 10 шардов, кластер вынужден аллоцировать в куче 10 000 000 объектов `PriorityQueueElement`, сериализовать их по сети на координатор и отсортировать 10 млн элементов ради возврата 100 записей.
Это гарантированно приводит к длинным STW GC-паузам JVM, OOM-падению координатора и отказу всего кластера. Для глубокой пагинации необходимо использовать только `search_after` + PIT.
