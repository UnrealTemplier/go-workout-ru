# Продвинутая агрегация Terms и вложенные субагрегации

## Условие

**Агрегации (Terms Aggregation)**: Сделай запрос (без поиска, или поиск `match_all`). Добавь в тело запроса агрегацию по полю `category`. В ответе (в поле `aggregations`) распарси список категорий и количество товаров в каждой (это основа для сайдбара с фильтрами в любом интернет-магазине).

## Теория

Агрегация `terms` строит гистограмму распределения документов по значениям конкретного поля.
Она лежит в основе сайдбаров интернет-магазинов, систем аналитики и дашбордов Kibana.

Продвинутые возможности `terms`:
1. **Размер выборки (`size`):** определяет количество возвращаемых бакетов (по умолчанию 10). В больших каталогах увеличивается до нужного числа категорий.
2. **Сортировка бакетов (`order`):**
   - `{"_count": "desc"}`: по количеству документов в категории (по умолчанию).
   - `{"_key": "asc"}`: по алфавиту названий категорий.
   - `{"avg_price": "desc"}`: по значению внутренней субагрегации (например, от самых дорогих категорий к дешевым).
3. **Вложенные субагрегации (Sub-aggregations):** внутри каждого бакета категории можно вычислить среднюю цену (`avg`), максимальную цену (`max`), или сгруппировать по брендам (`terms`).
4. **Параметр `min_doc_count`:** отсекает редкие категории с числом товаров меньше заданного порога.

## Решение по шагам

1. Сформируйте поисковый запрос с `size: 0` (только вычисление агрегаций без пересылки документов).
2. Настройте бакет `categories` типа `terms` по полю `category.keyword` с сортировкой по алфавиту.
3. Внутрь `categories` добавьте субагрегацию `avg_price` типа `avg` по полю `price`.
4. Выполните запрос через `es.Search`.
5. Распарсите массив `buckets`: извлеките имя категории (`key`), количество товаров (`doc_count`) и среднюю стоимость товаров в категории (`avg_price.value`).

## Код решения

**`terms_subaggs.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log"

	"github.com/elastic/go-elasticsearch/v8"
)

type TermsSubAggResponse struct {
	Aggregations struct {
		Categories struct {
			DocCountErrorUpperBound int64 `json:"doc_count_error_upper_bound"`
			SumOtherDocCount         int64 `json:"sum_other_doc_count"`
			Buckets                  []struct {
				Key      string `json:"key"`
				DocCount int64  `json:"doc_count"`
				AvgPrice struct {
					Value float64 `json:"value"`
				} `json:"avg_price"`
			} `json:"buckets"`
		} `json:"categories"`
	} `json:"aggregations"`
}

func main() {
	es, err := elasticsearch.NewDefaultClient()
	if err != nil {
		log.Fatalf("Ошибка клиента: %v", err)
	}

	query := map[string]interface{}{
		"size": 0,
		"aggs": map[string]interface{}{
			"categories": map[string]interface{}{
				"terms": map[string]interface{}{
					"field": "category.keyword",
					"size":  10,
					"order": map[string]string{"_key": "asc"},
				},
				"aggs": map[string]interface{}{
					"avg_price": map[string]interface{}{
						"avg": map[string]interface{}{
							"field": "price",
						},
					},
				},
			},
		},
	}

	var buf bytes.Buffer
	if err := json.NewEncoder(&buf).Encode(query); err != nil {
		log.Fatalf("Ошибка кодирования: %v", err)
	}

	res, err := es.Search(
		es.Search.WithContext(context.Background()),
		es.Search.WithIndex("products"),
		es.Search.WithBody(&buf),
	)
	if err != nil {
		log.Fatalf("Ошибка поиска: %v", err)
	}
	defer res.Body.Close()

	var resp TermsSubAggResponse
	if err := json.NewDecoder(res.Body).Decode(&resp); err != nil {
		log.Fatalf("Ошибка парсинга: %v", err)
	}

	fmt.Println("=== Статистика по категориям каталога ===")
	for _, b := range resp.Aggregations.Categories.Buckets {
		fmt.Printf("Категория: %-15s | Товаров: %5d | Средняя цена: %10.2f руб\n",
			b.Key, b.DocCount, b.AvgPrice.Value)
	}
}
```

## Под капотом

Для выполнения terms агрегации Elasticsearch использует колоночную структуру `doc_values`.
Значения полей читаются из файла `.dvd` (Doc Values Data), который отображается в системную память через `mmap`.
Внутренний механизм `GlobalOrdinals` строит биективное отображение строк в целочисленные идентификаторы (`ordinals`), благодаря чему субагрегации и подсчет бакетов производятся по компактным массивам `int32`, минуя создание объектов строк в куче JVM.

## Подводные камни

1. Забытый `size: 0`: если не указать `size: 0`, Elasticsearch вернет топ-10 документов `hits`, тратя ресурсы на извлечение `_source` из дисковых сегментов.
2. Использование `terms` агрегации по полю с уникальными значениями (UUID, email): порождает миллионы бакетов и вызывает OOM (Out Of Memory) на ноде-координаторе.
3. Ошибка нехватки точности `sum_other_doc_count`: если количество категорий превышает `size`, сумма оставшихся документов попадает в `sum_other_doc_count`. Увеличивайте `size` или переходите на `composite aggregation`.

## На собеседовании

В: Что такое Global Ordinals в Elasticsearch и в каких случаях они вызывают заметную задержку (latency spike) первого запроса?
О: Global Ordinals — это сквозная структура данных, отображающая уникальные строковые термины всех сегментов шарда в единый массив целочисленных индексов (`0, 1, 2...`).
Они строятся «лениво» при первом выполнении агрегации `terms` по полю.
Если сегменты индекса только что обновились (после refresh или merge), первый поисковый запрос тратит время на построение Global Ordinals, вызывая скачок задержки.
Для предотвращения этого в проде настраивают `eager_global_ordinals: true` в маппинге поля: тогда ординалы пересчитываются в фоне сразу во время refresh.
