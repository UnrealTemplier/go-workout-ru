# Потокобезопасная структура счетчика SafeCounter с sync.Mutex

## Условие

Исправьте гонку с помощью `sync.Mutex`: общая структура со счётчиком и метод `Inc`.

## Теория

Инкапсуляция разделяемого состояния и мьютекса в единую структуру — фундаментальный объектно-ориентированный паттерн конкурентности в Go (Monitor Pattern).

## Решение по шагам

1. Создадим структуру `SafeCounter struct { mu sync.Mutex; value int }`.
2. Реализуем методы `Inc()` и `Value() int` на pointer receiver `*SafeCounter`.
3. Запустим 1000 горутин.
4. Проверим отсутствие гонок.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type SafeCounter struct {
	mu    sync.Mutex
	value int
}

func (c *SafeCounter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}

func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.value
}

func main() {
	counter := &SafeCounter{}
	var wg sync.WaitGroup

	const total = 1000
	wg.Add(total)

	for i := 0; i < total; i++ {
		go func() {
			defer wg.Done()
			counter.Inc()
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговое значение SafeCounter: %d (ровно %d)\n", counter.Value(), total)
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# Итоговое значение SafeCounter: 1000 (ровно 1000)
```

## Под капотом

Использование Pointer Receiver `(c *SafeCounter)` гарантирует, что мьютекс `c.mu` не будет скопирован при вызове методов.

## Подводные камни

Метод `Value()` также обязан захватывать мьютекс `Lock()`, иначе возникнет гонка между чтением и параллельной записью в `Inc()`.

## На собеседовании

**Вопрос с собеседования:** «Почему метод чтения Value() в структуре с sync.Mutex обязательно должен вызывать Lock(), а не просто return c.value?»
**Ответ:** Потому что на многоядерных архитектурах (ARM, x86) без мьютекса или атомика чтение может прочитать частично записанное значение (Torn Read) или старое закэшированное значение из L1/L2 кэша процессора.
