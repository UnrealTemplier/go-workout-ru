# Анатомия фатальной ошибки: all goroutines are asleep - deadlock!

## Условие

Создайте программу, которая падает с `fatal error: all goroutines are asleep - deadlock!`. Разберитесь, почему планировщик Go обнаружил дедлок.

## Теория

Планировщик Go непрерывно отслеживает состояние всех M-потоков. Если все горутины перешли в режим ожидания (Waiting/Blocked) и нет ни одной готовой к запуску горутины, рантайм гарантированно фиксирует дедлок и аварийно завершает процесс.

## Решение по шагам

1. Создадим `wg.Add(1)`.
2. Вызовем `wg.Wait()` без запуска горутин.
3. Разберем текст фатальной ошибки рантайма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	// Добавили задачу, но не запустили горутину
	wg.Add(1)

	fmt.Println("Попытка ожидания в wg.Wait() без активных воркеров...")

	// Рантайм Go немедленно обнаружит дедлок, так как некому вызвать wg.Done()
	wg.Wait()

	fmt.Println("Этот код никогда не выполнится")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Попытка ожидания в wg.Wait() без активных воркеров...
# fatal error: all goroutines are asleep - deadlock!
# 
# goroutine 1 [semacquire]:
# sync.runtime_Semacquire(0x...)
# sync.(*WaitGroup).Wait(0x...)
# main.main()
#     /home/ut/work/go-workout/main.go:16 +0x65
# exit status 2
```

## Под капотом

Функция `checkdead()` в планировщике рантайма проверяет условие: `if sched.gcount == sched.nwait { throw("all goroutines are asleep - deadlock!") }`.

## Подводные камни

Дедлоки, вызванные зависанием сетевых сокетов, рантайм Go обнаружить не может (так как сокет привязан к дескриптору `epoll`).

## На собеседовании

**Вопрос с собеседования:** «Почему в юнит-тестах Go дедлок падает с exit status 2?»
**Ответ:** Потому что это системная авария уровня рантайма (`panic` -> `throw`), которую невозможно перехватить через `recover()`. Она немедленно завершает весь процесс с дампом стеков всех горутин.
