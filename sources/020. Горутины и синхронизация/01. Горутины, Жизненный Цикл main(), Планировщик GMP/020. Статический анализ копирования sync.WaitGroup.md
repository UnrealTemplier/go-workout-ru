# Статический анализ копирования sync.WaitGroup с помощью go vet

## Условие

Передайте `WaitGroup` в функцию по значению и изучите ошибку компилятора (`go vet` ругается на копирование `sync.WaitGroup`). Всегда передавайте `WaitGroup` по указателю!

## Теория

Линтер `go vet` содержит анализатор `copylocks`, который проверяет AST программы на наличие типов, реализующих метод `Lock()` / `Unlock()`, и запрещает передачу таких структур по значению.

## Решение по шагам

1. Напишем функцию с правильной передачей `*sync.WaitGroup`.
2. Объясним правило компиляции и статического анализа `go vet`.
3. В `main` убедимся в корректной работе.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

// Передача по указателю гарантирует работу с оригинальным счетчиком
func safeTask(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Printf("Задача %d выполнена\n", id)
}

func main() {
	var wg sync.WaitGroup

	wg.Add(2)
	go safeTask(1, &wg)
	go safeTask(2, &wg)

	wg.Wait()
	fmt.Println("go vet copylocks: проверка пройдена успешно!")
}
```

**`Терминал`**

```bash
go vet main.go
go run main.go
# Вывод:
# Задача 1 выполнена
# Задача 2 выполнена
# go vet copylocks: проверка пройдена успешно!
```

## Под капотом

`go vet` анализирует типы параметров функций и помечает ошибкой любую передачу структур с типом `sync.noCopy`.

## Подводные камни

Встраивание структуры с `sync.Mutex` или `sync.WaitGroup` в другую структуру делает внешнюю структуру также не подлежащей копированию!

## На собеседовании

**Вопрос с собеседования:** «Почему компилятор Go сам не запрещает копирование WaitGroup при компиляции?»
**Ответ:** По спецификации Go структуры являются значениями и могут свободно копироваться. Семантический запрет копирования мьютексов вынесен в статический анализатор `go vet`, чтобы не усложнять базовую систему типов языка.
