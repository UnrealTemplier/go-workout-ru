# Неблокирующий захват мьютекса через TryLock (Go 1.18+)

## Условие

Реализуй **"try lock"** через `sync.Mutex` + канал: `TryLock()` захватывает мьютекс с `select` и `default` (или используй `atomic` для флага). Объясни, почему в `sync.Mutex` нет встроенного `TryLock` (до Go 1.18; с 1.18 есть `TryLock()` — покажи его).

## Теория

Метод `mu.TryLock()` (внедрен в Go 1.18) пытается немедленно захватить мьютекс. Если мьютекс свободен, он захватывает его и возвращает `true`. Если мьютекс занят другой горутиной, `TryLock()` не блокирует поток, а мгновенно возвращает `false`.

## Решение по шагам

1. Создадим фоновый процесс, удерживающий мьютекс.
2. Во второй горутине вызовем `mu.TryLock()`.
3. Обработаем занятость ресурса в ветке `else`.
4. Разберем сценарии применения.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type BackgroundJobRunner struct {
	mu sync.Mutex
}

func (r *BackgroundJobRunner) RunJob(jobName string) {
	// Неблокирующая попытка захвата мьютекса
	if !r.mu.TryLock() {
		fmt.Printf("[%s] Задача пропущена: предыдущая итерация еще выполняется\n", jobName)
		return
	}
	defer r.mu.Unlock()

	fmt.Printf("[%s] Старт выполнения тяжелой периодической задачи...\n", jobName)
	time.Sleep(30 * time.Millisecond)
	fmt.Printf("[%s] Задача успешно завершена\n", jobName)
}

func main() {
	runner := &BackgroundJobRunner{}
	var wg sync.WaitGroup

	wg.Add(2)

	// Первая горутина захватывает задачу
	go func() {
		defer wg.Done()
		runner.RunJob("Task #1")
	}()

	// Вторая горутина пытается запуститься одновременно
	go func() {
		defer wg.Done()
		time.Sleep(5 * time.Millisecond)
		runner.RunJob("Task #2 (параллельный запуск)")
	}()

	wg.Wait()
	fmt.Println("Тестирование TryLock завершено успешно!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Task #1] Старт выполнения тяжелой периодической задачи...
# [Task #2 (параллельный запуск)] Задача пропущена: предыдущая итерация еще выполняется
# [Task #1] Задача успешно завершена
# Тестирование TryLock завершено успешно!
```

## Под капотом

`mu.TryLock()` выполняет единственную быструю операцию `atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)`.

## Подводные камни

Не стройте спинлоки на базе `for !mu.TryLock() {}` — это сжигает 100% CPU. Для ожидания используйте обычный `mu.Lock()`.

## На собеседовании

**Вопрос с собеседования:** «Где метод TryLock() оправдан в реальных проектах?»
**Ответ:** В периодических фоновых задачах (Cron Jobs / Background Flushers): если предыдущий цикл очистки еще не завершился, следующему запуску лучше пропустить итерацию, чем выстраивать очередь из заблокированных воркеров.
