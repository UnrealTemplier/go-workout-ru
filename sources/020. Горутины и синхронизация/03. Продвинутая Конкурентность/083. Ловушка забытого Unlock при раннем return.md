# Ловушка забытого Unlock при раннем return: дедлок и исправление через defer

## Условие

**Забытый Unlock (Deadlock)**: В упр. 284 напиши условие `if counter == 5000 { return }` внутри горутины, до `Unlock()`. Увидь, как все остальные горутины зависают навсегда.

## Теория

Если горутина захватывает `mu.Lock()` и выходит из функции по условию (`return`, `panic`, `break`) без вызова `mu.Unlock()`, мьютекс навсегда остается заблокированным. Все последующие горутины навсегда зависают при попытке захватить `mu.Lock()`.

## Решение по шагам

1. Продемонстрируем ошибку забытого `Unlock` при раннем выходе.
2. Покажем, как `defer mu.Unlock()` гарантирует разблокировку.
3. Проверим стабильное выполнение всех горутин.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type SafeRegistry struct {
	mu    sync.Mutex
	items map[int]string
}

func (r *SafeRegistry) Register(id int, name string) {
	r.mu.Lock()
	// ИСПРАВЛЕНИЕ: defer гарантирует вызов Unlock при любых return
	defer r.mu.Unlock()

	if id == 5000 {
		fmt.Printf("[Registry] Пропуск служебного ID %d (ранний return)\n", id)
		return // Без defer здесь мьютекс остался бы заблокированным навсегда!
	}

	r.items[id] = name
}

func main() {
	registry := &SafeRegistry{items: make(map[int]string)}
	var wg sync.WaitGroup

	ids := []int{100, 5000, 200, 300}
	wg.Add(len(ids))

	for _, id := range ids {
		go func(targetID int) {
			defer wg.Done()
			registry.Register(targetID, fmt.Sprintf("Item_%d", targetID))
		}(id)
	}

	wg.Wait()
	fmt.Printf("Все элементы успешно обработаны, зарегистрировано в мапе: %d\n", len(registry.items))
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Registry] Пропуск служебного ID 5000 (ранний return)
# Все элементы успешно обработаны, зарегистрировано в мапе: 3
```

## Под капотом

`defer mu.Unlock()` гарантирует освобождение семафора рантайма `runtime_Semrelease` перед выходом из кадра функции.

## Подводные камни

В функциях с десятками строк кода никогда не управляйте мьютексом вручную без `defer`.

## На собеседовании

**Вопрос с собеседования:** «Каковы главные причины утечек блокировок (Mutex Leak / Orphan Lock) в Go?»
**Ответ:** 1) Ранний `return` по ошибке до ручного вызова `Unlock()`. 2) Неперехваченная паника (`panic`), прерывающая выполнение до `Unlock()`. Паттерн `mu.Lock(); defer mu.Unlock()` полностью устраняет обе проблемы.
