# Ловушка двойного Lock: дедлок из-за отсутствия реентерабельности мьютексов

## Условие

**[Каверзный кейс]**: Попробуй заблокировать `Mutex`, который уже заблокирован этой же горутиной (двойной Lock). Поймай дедлок. (В Go нет реентерабельных мьютексов).

## Теория

В Go мьютексы не имеют понятия владельца. Повторный вызов `Lock()` из того же потока пытается захватить уже заблокированный семафор, вызывая дедлок.

## Решение по шагам

1. Создадим мьютекс `var mu sync.Mutex`.
2. Захватим его первый раз `mu.Lock()`.
3. Продемонстрируем неблокирующую проверку `mu.TryLock() == false`.
4. Объясним архитектурные причины.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex

	fmt.Println("1. Первый захват mu.Lock()...")
	mu.Lock()
	fmt.Println("   Мьютекс успешно заблокирован.")

	fmt.Println("2. Проверка повторного захвата через TryLock()...")
	if !mu.TryLock() {
		fmt.Println("   TryLock вернул false: мьютекс уже заблокирован!")
		fmt.Println("   Внимание: вызов обычного mu.Lock() здесь вызвал бы фатальный дедлок!")
	}

	mu.Unlock()
	fmt.Println("3. Мьютекс успешно освобожден.")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 1. Первый захват mu.Lock()...
#    Мьютекс успешно заблокирован.
# 2. Проверка повторного захвата через TryLock()...
#    TryLock вернул false: мьютекс уже заблокирован!
#    Внимание: вызов обычного mu.Lock() здесь вызвал бы фатальный дедлок!
# 3. Мьютекс успешно освобожден.
```

## Под капотом

`sync.Mutex` в Go намеренно спроектирован без хранения Goroutine ID для минимального размера (8 байт) и максимальной скорости.

## Подводные камни

Если структуре требуется вызывать свои методы, разделяйте их на публичные с блокировкой и приватные `*Locked()` без нее.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go нет реентерабельных мьютексов?»
**Ответ:** Потому что рекурсивные мьютексы маскируют нарушение инвариантов и усложняют код. В Go поощряется явное проектирование критических секций.
