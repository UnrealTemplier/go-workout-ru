# Идиоматичная замена ручного Unlock на defer mu.Unlock()

## Условие

**Правильный `defer`**: Замени ручной вызов на `defer mu.Unlock()` сразу после `mu.Lock()`.

## Теория

Сравнение ручного управления блокировкой и паттерна `defer`: явный `defer` исключает человеческий фактор при рефакторинге и добавлении новых условий возврата.

## Решение по шагам

1. Создадим метод с несколькими ветками `if`.
2. Заблокируем мьютекс и сразу напишем `defer mu.Unlock()`.
3. Продемонстрируем надежность освобождения блокировки.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type SafeStore struct {
	mu   sync.Mutex
	data map[string]int
}

func (s *SafeStore) UpdateScore(player string, delta int) {
	s.mu.Lock()
	defer s.mu.Unlock() // Золотой стандарт: блокировка освобождается при любых исходах

	if delta == 0 {
		return // Безопасный возврат
	}

	s.data[player] += delta
}

func main() {
	store := &SafeStore{data: make(map[string]int)}

	store.UpdateScore("player1", 100)
	store.UpdateScore("player1", 0) // Ранний выход
	store.UpdateScore("player1", 50)

	fmt.Printf("Финальный счет player1: %d\n", store.data["player1"])
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Финальный счет player1: 150
```

## Под капотом

`defer` оптимизируется компилятором и встраивается без аллокаций в куче.

## Подводные камни

Не ставьте `defer mu.Unlock()` до вызова `mu.Lock()`, иначе мьютекс будет разблокирован без предварительного захвата, что вызовет панику.

## На собеседовании

**Вопрос с собеседования:** «Почему defer mu.Unlock() должен идти строго СЛЕДУЮЩЕЙ строкой после mu.Lock()?»
**Ответ:** Чтобы между захватом мьютекса и регистрацией его освобождения не было кода, способного вызвать панику (например, разыменование nil-указателя), из-за которой мьютекс остался бы заблокированным.
