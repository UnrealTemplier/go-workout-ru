# Устранение Data Race в счетчике с помощью sync.Mutex

## Условие

Исправь предыдущее задание с помощью `sync.Mutex` (`Lock()` перед инкрементом, `Unlock()` после).

## Теория

Защита разделяемой переменной мьютексом гарантирует строгую последовательную согласованность.

## Решение по шагам

1. Создадим переменную `var total int` и `var mu sync.Mutex`.
2. Запустим 500 горутин.
3. Обернем операцию в `mu.Lock()` и `mu.Unlock()`.
4. Проверим с `-race`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var total int
	var mu sync.Mutex
	var wg sync.WaitGroup

	const count = 500
	wg.Add(count)

	for i := 0; i < count; i++ {
		go func() {
			defer wg.Done()
			mu.Lock()
			total++
			mu.Unlock()
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговое значение через sync.Mutex: %d\n", total)
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# Итоговое значение через sync.Mutex: 500
```

## Под капотом

`sync.Mutex` сериализует операции, устраняя конкуренцию на уровне кэш-линий памяти.

## Подводные камни

Для простых числовых счетчиков `atomic` предпочтительнее мьютексов по скорости и объему кода.

## На собеседовании

**Вопрос с собеседования:** «Когда Mutex лучше Atomic, а когда наоборот?»
**Ответ:** `Atomic` идеален для простых скаляров (счетчики метрик, флаги). `Mutex` необходим, когда нужно атомарно изменить несколько связанных полей (например, баланс счета и статус транзакции) или защитить сложные структуры (мапы, срезы).
