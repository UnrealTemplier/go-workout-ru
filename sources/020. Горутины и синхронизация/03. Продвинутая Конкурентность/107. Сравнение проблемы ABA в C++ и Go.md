# Сравнение проблемы ABA в C++ и Go: влияние сборщика мусора (GC)

## Условие

Напиши программу с `atomic.Pointer` и **ABA-problem**: покажи, что `CompareAndSwap` может "пропустить" изменение, если указатель вернулся к тому же значению. Обсуди, почему в Go managed memory это менее критично, чем в C++.

## Теория

Проблема ABA возникает в Lock-Free алгоритмах: 1) Поток считывает указатель \(A\), 2) Другой поток меняет на \(B\), затем возвращает на \(A\) (но с другим содержимым), 3) Первый поток выполняет CAS(\(A\), \(C\)), успешно меняя указатель, но нарушая инвариант. В Go GC не переиспользует память старого \(A\), пока есть ссылка, снижая риск повреждения структур.

## Решение по шагам

1. Создадим структуру `DataNode struct { val string }`.
2. Создадим `var ptr atomic.Pointer[DataNode]`.
3. Смоделируем сценарий смены \(A \to B \to A\).
4. Объясним различия с языками без сборщика мусора.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
)

type ConfigState struct {
	Version int
	Name    string
}

func main() {
	var ptr atomic.Pointer[ConfigState]

	nodeA := &ConfigState{Version: 1, Name: "Alpha"}
	nodeB := &ConfigState{Version: 2, Name: "Beta"}

	ptr.Store(nodeA)

	// 1. Поток 1 считывает nodeA
	observed := ptr.Load()
	fmt.Printf("1. Поток 1 прочитал указатель A: %+v (адрес: %p)\n", observed, observed)

	// 2. Поток 2 меняет A -> B -> A
	ptr.Store(nodeB)
	fmt.Printf("2. Поток 2 заменил на B: %+v\n", ptr.Load())
	ptr.Store(nodeA)
	fmt.Printf("3. Поток 2 вернул назад указатель A: %+v\n", ptr.Load())

	// 3. Поток 1 делает CAS в предположении, что изменений не было
	nodeC := &ConfigState{Version: 3, Name: "Gamma"}
	swapped := ptr.CompareAndSwap(observed, nodeC)

	fmt.Printf("4. Результат CAS(observed, nodeC): %v (указатель совпадал, CAS успешен)\n", swapped)
	fmt.Printf("5. Итоговое состояние: %+v\n", ptr.Load())
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 1. Поток 1 прочитал указатель A: &{Version:1 Name:Alpha} (адрес: 0x...)
# 2. Поток 2 заменил на B: &{Version:2 Name:Beta}
# 3. Поток 2 вернул назад указатель A: &{Version:1 Name:Alpha}
# 4. Результат CAS(observed, nodeC): true (указатель совпадал, CAS успешен)
# 5. Итоговое состояние: &{Version:3 Name:Gamma}
```

## Под капотом

В C++ память \(A\) могла быть освобождена через `free()` и выделена заново под новый объект с тем же адресом. В Go \(A\) не удаляется из памяти, пока `observed` держит ссылку.

## Подводные камни

Если сам объект \(A\) является мутабельным, его внутренние поля могли измениться во время \(A \to B \to A\).

## На собеседовании

**Вопрос с собеседования:** «Как решается проблема ABA в C++ и почему в Go она встречается реже?»
**Ответ:** В C++ используют Tagged Pointers (Double-Word CAS со счетчиком версий или `std::atomic<std::shared_ptr>`). В Go автоматическое управление памятью (Garbage Collector) исключает повторное перевыделение одного адреса памяти под другой тип объекта во время удержания ссылки.
