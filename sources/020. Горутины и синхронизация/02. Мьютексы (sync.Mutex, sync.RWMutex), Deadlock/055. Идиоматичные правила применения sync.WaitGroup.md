# Идиоматичные правила применения sync.WaitGroup: Add, Done и Wait

## Условие

**Использование `sync.WaitGroup`**: Перепишите задачу с горутиной. Вместо использования костылей в виде `time.Sleep` для ожидания горутины, примените `sync.WaitGroup`. Объясните правила вызова методов `Add()`, `Done()` и `Wait()`.

## Теория

Свод 3 главных правил `sync.WaitGroup`:
1. `wg.Add(n)` вызывается строго ДО запуска горутин в вызывающем потоке.
2. `defer wg.Done()` вызывается первой инструкцией внутри горутины.
3. `wg.Wait()` вызывается в точке синхронизации.

## Решение по шагам

1. Создадим `var wg sync.WaitGroup`.
2. Запустим задачу с гарантированным ожиданием.
3. Убедимся в мгновенном завершении без лишних задержек.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func performTask(name string, duration time.Duration, wg *sync.WaitGroup) {
	defer wg.Done()
	time.Sleep(duration)
	fmt.Printf("[Task] Задача '%s' успешно выполнена за %v\n", name, duration)
}

func main() {
	var wg sync.WaitGroup

	start := time.Now()

	wg.Add(2)
	go performTask("Генерация отчета", 25*time.Millisecond, &wg)
	go performTask("Отправка вебхука", 15*time.Millisecond, &wg)

	// Ожидание ровно столько, сколько требуется самой медленной задаче
	wg.Wait()

	fmt.Printf("Все задачи выполнены за %v (без фиксированного time.Sleep)\n", time.Since(start))
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Task] Задача 'Отправка вебхука' успешно выполнена за 15ms
# [Task] Задача 'Генерация отчета' успешно выполнена за 25ms
# Все задачи выполнены за 25.12ms (без фиксированного time.Sleep)
```

## Под капотом

`wg.Wait()` использует семафор `runtime_Semacquire`, возвращая управление в микросекунду обнуления счетчика.

## Подводные камни

Никогда не используйте `time.Sleep` для ожидания асинхронных задач.

## На собеседовании

**Вопрос с собеседования:** «Что быстрее: sync.WaitGroup или канал chan struct{} для ожидания 1 горутины?»
**Ответ:** Для одной горутины канал `done := make(chan struct{})` и `close(done)` по скорости сопоставим с `WaitGroup`, но `sync.WaitGroup` оптимальнее и читаемее для групп из N параллельных задач.
