# Переиспользование тяжелых структур Buffer через sync.Pool для снижения пауз GC

## Условие

**Пул объектов (`sync.Pool`)**: Создайте структуру `Buffer` большого размера. Напишите код, который часто создает и уничтожает эти буферы, перегружая сборщик мусора (GC). Оптимизируйте программу, используя `sync.Pool` для переиспользования выделенной памяти под буферы.

## Теория

Постоянное создание больших структур (например, буферов по 1 МБ) заставляет сборщик мусора Go непрерывно запускать фазы Mark-and-Sweep. `sync.Pool` переиспользует уже выделенные слайсы памяти, сокращая нагрузку на аллокатор mcache/mcentral.

## Решение по шагам

1. Создадим тяжелую структуру `LargePacket struct { Payload [64 * 1024]byte; Length int }`.
2. Настроим `sync.Pool`.
3. Запустим обработку 100 пакетов с переиспользованием.
4. Проверим стабильность памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type LargePacket struct {
	Payload [64 * 1024]byte // 64 КБ на объект
	Length  int
}

var packetPool = sync.Pool{
	New: func() any {
		return new(LargePacket)
	},
}

func processNetworkPacket(dataID int) {
	pkt := packetPool.Get().(*LargePacket)
	defer packetPool.Put(pkt) // Возврат в пул после обработки

	pkt.Length = 1024
	pkt.Payload[0] = byte(dataID % 255)
}

func main() {
	var wg sync.WaitGroup
	const totalPackets = 50

	wg.Add(totalPackets)
	for i := 0; i < totalPackets; i++ {
		go func(id int) {
			defer wg.Done()
			processNetworkPacket(id)
		}(i)
	}

	wg.Wait()
	fmt.Printf("Успешно обработано %d тяжелых пакетов без нагрузки на GC через sync.Pool!\n", totalPackets)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Успешно обработано 50 тяжелых пакетов без нагрузки на GC через sync.Pool!
```

## Под капотом

`sync.Pool` выделяет память на арене `mheap` один раз и циклически распределяет её по локальным кешам `poolLocal`.

## Подводные камни

Всегда обнуляйте поля структуры перед использованием, так как объект из пула содержит остаточные данные от предыдущего владельца.

## На собеседовании

**Вопрос с собеседования:** «Почему sync.Pool не подходит для пулов сетевых соединений (Connection Pool)?»
**Ответ:** Потому что `sync.Pool` не гарантирует сохранение объектов: во время сборки мусора (GC) неиспользуемые объекты из пула могут быть удалены в любой момент. Для соединений к БД используют специализированные пулы (`database/sql`).
