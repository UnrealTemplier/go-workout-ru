# Практикум: воспроизведение и анализ отчета ThreadSanitizer (-race)

## Условие

**[Каверзный кейс]**: Создай глобальную переменную `counter = 0`. Запусти 1000 горутин, каждая делает `counter++`. Выведи результат (он будет меньше 1000). Запусти программу с флагом `-race`, чтобы увидеть ошибку.

## Теория

ThreadSanitizer отслеживает каждое обращение к памяти. Отчет детектора гонок содержит стектрейсы горутин, адреса памяти и точные номера строк конфликтующих операций чтения и записи.

## Решение по шагам

1. Создадим глобальный `var counter int`.
2. Запустим 1000 горутин.
3. Запустим с флагом `go run -race main.go`.
4. Проанализируем структуру предупреждения `WARNING: DATA RACE`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

var counter int

func main() {
	var wg sync.WaitGroup
	const total = 1000
	wg.Add(total)

	for i := 0; i < total; i++ {
		go func() {
			defer wg.Done()
			counter++ // Точка конфликта
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговое несинхронизированное значение: %d\n", counter)
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# WARNING: DATA RACE
# Write at 0x... by goroutine ...
# Previous write at 0x... by goroutine ...
# Итоговое несинхронизированное значение: 954
```

## Под капотом

ThreadSanitizer выделяет 4 слова теневой памяти (Shadow Memory) на каждые 8 байт памяти приложения для хранения метаданных синхронизации.

## Подводные камни

Детектор гонок не гарантирует нахождение всех гонок в кодовой базе: он обнаруживает только те гонки, которые реально произошли во время конкретного прогона программы/теста.

## На собеседовании

**Вопрос с собеседования:** «Почему флаг -race нельзя включать в продакшен-сборках highload сервисов?»
**Ответ:** Флаг `-race` увеличивает потребление оперативной памяти в 5–10 раз и замедляет выполнение CPU-инструкций в 2–5 раз из-за непрерывного аудита теневой памяти.
