# In-Memory БД на базе sync.RWMutex для Read-Heavy нагрузки

## Условие

**Оптимизация чтения с `sync.RWMutex`**: Создайте структуру "База данных в памяти" (под капотом обычная мапа). Напишите методы записи и чтения. Предполагая, что чтение происходит в 99% случаев, а запись — в 1%, используйте `sync.RWMutex`. Продемонстрируйте параллельный вызов методов чтения (`RLock` / `RUnlock`), не блокирующих друг друга.

## Теория

При Read-Heavy нагрузке (99% чтений) `sync.RWMutex` обеспечивает максимальную пропускную способность, так как десятки ядер процессора могут одновременно параллельно считывать данные из мапы без взаимных блокировок.

## Решение по шагам

1. Создадим структуру `InMemoryDB struct { mu sync.RWMutex; items map[string]string }`.
2. Реализуем метод `Read(key string) (string, bool)` с `mu.RLock()`.
3. Реализуем метод `Write(key, val string)` с `mu.Lock()`.
4. Запустим 100 параллельных читателей.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type InMemoryDB struct {
	mu    sync.RWMutex
	items map[string]string
}

func NewInMemoryDB() *InMemoryDB {
	return &InMemoryDB{items: make(map[string]string)}
}

func (db *InMemoryDB) Read(key string) (string, bool) {
	db.mu.RLock()
	defer db.mu.RUnlock()
	val, exists := db.items[key]
	return val, exists
}

func (db *InMemoryDB) Write(key, val string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.items[key] = val
}

func main() {
	db := NewInMemoryDB()
	db.Write("config:theme", "dark_cyberpunk")

	var wg sync.WaitGroup
	const totalReaders = 20

	wg.Add(totalReaders)
	for i := 1; i <= totalReaders; i++ {
		go func(id int) {
			defer wg.Done()
			val, _ := db.Read("config:theme")
			if id == 1 || id == 20 {
				fmt.Printf("[Читатель #%d] Получил тему: %s\n", id, val)
			}
		}(i)
	}

	wg.Wait()
	fmt.Println("Все параллельные чтения выполнены без единой задержки!")
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# [Читатель #1] Получил тему: dark_cyberpunk
# [Читатель #20] Получил тему: dark_cyberpunk
# Все параллельные чтения выполнены без единой задержки!
```

## Под капотом

`RLock()` изменяет атомарный счетчик читателей без блокировки планировщика, позволяя ядрам процессора исполнять код параллельно.

## Подводные камни

Обычная `map` в Go вызывает моментальную панику `fatal error: concurrent map read and map write`, если попытаться читать без `RLock` во время записи.

## На собеседовании

**Вопрос с собеседования:** «Почему мапа в Go не потокобезопасна по умолчанию?»
**Ответ:** Создатели Go решили, что 90% сценариев использования мап происходят в пределах одной горутины. Встраивание мьютекса в каждую мапу замедлило бы абсолютно все операции чтения/записи в однопоточных программах.
