# Снижение нагрузки на GC через пул объектов sync.Pool

## Условие

Изучите `sync.Pool`. Создайте пул объектов (например, `bytes.Buffer`), чтобы переиспользовать их в горутинах и снизить нагрузку на Garbage Collector.

## Теория

`sync.Pool` — это потокобезопасный пул повторно используемых временных объектов. Он позволяет избежать постоянных аллокаций памяти в куче (Heap) в высоконагруженных сетевых обработчиках, существенно снижая паузы сборщика мусора (GC Stop-The-World).

## Решение по шагам

1. Создадим `sync.Pool` с фабричной функцией `New`.
2. В горутине запросим буфер через `bufPool.Get().(*bytes.Buffer)`.
3. Очистим буфер через `buf.Reset()` и вернем в пул через `defer bufPool.Put(buf)`.
4. Запустим несколько параллельных задач.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"sync"
)

var bufPool = sync.Pool{
	New: func() any {
		// Создается только при нехватке свободных объектов в пуле
		fmt.Println("[POOL] Аллокация нового буфера в куче")
		return new(bytes.Buffer)
	},
}

func formatMessage(user string, id int) string {
	// Берем объект из пула
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset() // Обязательная очистка перед повторным использованием
	defer bufPool.Put(buf) // Возврат объекта в пул

	fmt.Fprintf(buf, "User: %s (ID: %d)", user, id)
	return buf.String()
}

func main() {
	var wg sync.WaitGroup

	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			msg := formatMessage("developer", id)
			fmt.Println(" ->", msg)
		}(i)
	}

	wg.Wait()
	fmt.Println("Обработка через sync.Pool завершена успешно!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# [POOL] Аллокация нового буфера в куче
#  -> User: developer (ID: 3)
#  -> User: developer (ID: 1)
#  -> User: developer (ID: 2)
# Обработка через sync.Pool завершена успешно!
```

## Под капотом

`sync.Pool` привязан к локальным структурам `P` процессора (Local Pool per-P). Забор объекта из локального пула текущего `P` происходит без глобальных блокировок через lock-free очереди `poolLocal`.

## Подводные камни

Объекты в `sync.Pool` могут быть в любой момент очищены сборщиком мусора во время цикла GC. Не храните в `sync.Pool` постоянные ресурсы (соединения с БД или открытые файлы).

## На собеседовании

**Вопрос с собеседования:** «Когда сборщик мусора очищает объекты из sync.Pool?»
**Ответ:** Начиная с Go 1.13, объекты живут минимум два полных цикла GC (механизм `poolVictim`). При первом цикле GC объекты переносятся в резервный пул `victim`, а при втором (если не были запрошены) — окончательно удаляются.
