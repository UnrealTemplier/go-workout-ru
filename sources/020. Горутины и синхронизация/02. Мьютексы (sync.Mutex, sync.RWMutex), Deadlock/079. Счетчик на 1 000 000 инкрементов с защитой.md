# Счетчик на 1 000 000 инкрементов с защитой sync.Mutex

## Условие

**Исправление через `sync.Mutex`**: Добавь мьютекс. Делай `mu.Lock()` перед инкрементом и `mu.Unlock()` после. Убедись, что счетчик равен миллиону и `-race` молчит.

## Теория

Экстремальный тест параллельности: 100 горутин по 10 000 операций инкремента через `sync.Mutex` гарантирует точное сохранение всех \(1\,000\,000\) значений.

## Решение по шагам

1. Создадим переменную `var total int` и `var mu sync.Mutex`.
2. Запустим 100 горутин, выполняющих по 10 000 инкрементов.
3. Обернем `total++` в `mu.Lock()` и `mu.Unlock()`.
4. Проверим с флагом `-race`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var total int
	var mu sync.Mutex
	var wg sync.WaitGroup

	const numWorkers = 100
	const iterations = 10000

	wg.Add(numWorkers)
	for i := 0; i < numWorkers; i++ {
		go func() {
			defer wg.Done()
			for j := 0; j < iterations; j++ {
				mu.Lock()
				total++
				mu.Unlock()
			}
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговый счетчик: %d (ровно %d)\n", total, numWorkers*iterations)
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# Итоговый счетчик: 1000000 (ровно 1000000)
```

## Под капотом

`mu.Lock()` и `Unlock()` выполняют неделимые атомарные операции синхронизации шины процессора.

## Подводные камни

Внутри горячего цикла `for` не используйте `defer mu.Unlock()` — это создает миллион стековых записей `defer`.

## На собеседовании

**Вопрос с собеседования:** «Почему в цикле for на 10 000 итераций defer mu.Unlock() хуже явного mu.Unlock()?»
**Ответ:** Потому что `defer` привязан к завершению всей функции, а не к итерации цикла. Использование `defer` внутри цикла оставит мьютекс заблокированным до конца функции и вызовет переполнение стека defer-записей.
