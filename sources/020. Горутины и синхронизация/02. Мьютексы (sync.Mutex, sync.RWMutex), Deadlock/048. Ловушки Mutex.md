# Ловушки Mutex: паника при Unlock незаблокированного мьютекса и дедлок при повторном Lock

## Условие

Что произойдет, если вызвать `Unlock()` на мьютексе, который не был заблокирован? Что будет при двойном `Lock()` в одной горутине? (Поймайте Deadlock).

## Теория

1) Вызов `Unlock()` на незаблокированном `sync.Mutex` вызывает немедленную панику `panic: sync: unlock of unlocked mutex`. 2) В Go мьютексы **не являются реентерабельными** (Non-reentrant / Non-recursive). Повторный вызов `Lock()` из той же горутины приводит к дедлоку.

## Решение по шагам

1. Продемонстрируем перехват паники при `Unlock()` незаблокированного мьютекса.
2. Продемонстрируем дедлок при повторном вызове `mu.Lock()`.
3. Объясним правила безопасного проектирования.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func demoUnlockPanic() {
	var mu sync.Mutex

	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("[1. ПЕРЕХВАЧЕНА ПАНИКА]: %v\n", r)
		}
	}()

	fmt.Println("Попытка вызвать Unlock() без предварительного Lock()...")
	mu.Unlock() // Паника: sync: unlock of unlocked mutex
}

func demoDoubleLockDeadlock() {
	var mu sync.Mutex

	mu.Lock()
	fmt.Println("2. Первый Lock() успешно захвачен.")

	// Попытка захватить мьютекс повторно через TryLock (в Go 1.18+)
	acquired := mu.TryLock()
	fmt.Printf("3. Попытка повторного Lock() вернула: %v (мьютекс уже занят этой же горутиной)\n", acquired)

	mu.Unlock()
	fmt.Println("4. Мьютекс освобожден.")
}

func main() {
	demoUnlockPanic()
	demoDoubleLockDeadlock()
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Попытка вызвать Unlock() без предварительного Lock()...
# [1. ПЕРЕХВАЧЕНА ПАНИКА]: sync: unlock of unlocked mutex
# 2. Первый Lock() успешно захвачен.
# 3. Попытка повторного Lock() вернула: false (мьютекс уже занят этой же горутиной)
# 4. Мьютекс освобожден.
```

## Под капотом

`sync.Mutex` не сохраняет идентификатор владеющей горутины (Goroutine ID). Это сознательное архитектурное решение команды Go.

## Подводные камни

Никогда не вызывайте экспортируемые методы структуры с `mu.Lock()` из других методов этой же структуры, которые уже держат `mu.Lock()`.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go намеренно отказались от реентерабельных (Recursive) мьютексов (как в Java ReentrantLock)?»
**Ответ:** Расс Кокс (Russ Cox) объяснил: реентерабельные мьютексы маскируют нарушение инвариантов программы. Если метод вызывается повторно при удержании блокировки, структуры данных могут находиться в промежуточном, несогласованном состоянии.
