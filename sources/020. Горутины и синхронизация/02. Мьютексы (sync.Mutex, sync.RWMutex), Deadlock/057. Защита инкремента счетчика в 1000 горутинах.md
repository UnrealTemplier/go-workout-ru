# Защита инкремента счетчика в 1000 горутинах через sync.Mutex

## Условие

**Защита данных через `sync.Mutex`**: Исправьте предыдущую задачу на инкремент счетчика. Добавьте `sync.Mutex` и защитите операцию инкремента критической секцией (`mutex.Lock()` / `mutex.Unlock()`). Убедитесь, что теперь результат всегда равен 1000, а детектор гонок больше не выдает предупреждений.

## Теория

Защита критической секции через `sync.Mutex` сериализует доступ к памяти, превращая операцию `counter++` в неделимый и безопасный шаг.

## Решение по шагам

1. Создадим переменную `counter := 0` и `var mu sync.Mutex`.
2. Запустим 1000 горутин.
3. Обернем операцию в `mu.Lock()` и `mu.Unlock()`.
4. Проверим с флагом `-race`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var (
		counter int
		mu      sync.Mutex
		wg      sync.WaitGroup
	)

	const total = 1000
	wg.Add(total)

	for i := 0; i < total; i++ {
		go func() {
			defer wg.Done()

			mu.Lock()
			counter++
			mu.Unlock()
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговое защищенное значение: %d (из 1000)\n", counter)
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# Итоговое защищенное значение: 1000 (из 1000)
```

## Под капотом

`sync.Mutex` в состоянии starvation mode (режим голодания) передает владение блокировкой напрямую первой горутине в очереди FIFO, предотвращая задержки под высокой нагрузкой.

## Подводные камни

Не вызывайте блокирующие сетевые функции внутри секции `mu.Lock()`, иначе все остальные горутины выстроятся в очередь ожидания.

## На собеседовании

**Вопрос с собеседования:** «Что такое Starvation Mode в sync.Mutex Go 1.9+?»
**Ответ:** Если ожидающая горутина не может захватить мьютекс более 1 миллисекунды, мьютекс переходит в режим голодания: новые горутины не спинят на CPU, а сразу встают в хвост очереди, а владение мьютексом передается строго по FIFO.
