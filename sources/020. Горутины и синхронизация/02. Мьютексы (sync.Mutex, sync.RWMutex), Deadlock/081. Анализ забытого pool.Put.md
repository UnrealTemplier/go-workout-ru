# Анализ забытого pool.Put: потеря оптимизации без утечки памяти и мониторинг ReadMemStats

## Условие

Напиши программу с `sync.Pool`, где забываешь `Put` — покажи, что это не утечка памяти (GC соберёт), но теряется преимущество пула. Замерь аллокации через `runtime.ReadMemStats`.

## Теория

Если объект забран из `sync.Pool.Get()`, но не возвращен через `Put()`, он превращается в обычный объект кучи. Сборщик мусора корректно удалит его при следующем цикле GC. Утечки памяти не произойдет, но программа потеряет выигрыш от пулинга, постоянно выполняя новые аллокации `mallocgc`.

## Решение по шагам

1. Замерим аллокации через `runtime.ReadMemStats` до запуска.
2. Вызовем 100 раз `pool.Get()` без `pool.Put()`.
3. Замерим `TotalAlloc` и количество созданных объектов `Mallocs`.
4. Сравним со сценарием с возвратом в пул.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

var testPool = sync.Pool{
	New: func() any {
		return make([]byte, 1024*1024) // 1 МБ
	},
}

func main() {
	var m1, m2 runtime.MemStats

	// 1. Сценарий: забыли Put
	runtime.GC()
	runtime.ReadMemStats(&m1)

	for i := 0; i < 5; i++ {
		buf := testPool.Get().([]byte)
		_ = buf[0]
		// Забыли вызвать testPool.Put(buf)
	}

	runtime.ReadMemStats(&m2)
	allocWithoutPut := m2.TotalAlloc - m1.TotalAlloc
	fmt.Printf("Аллокаций памяти БЕЗ Put: %d КБ (создано 5 новых объектов)\n", allocWithoutPut/1024)

	// 2. Сценарий: правильный Put
	runtime.GC()
	runtime.ReadMemStats(&m1)

	for i := 0; i < 5; i++ {
		buf := testPool.Get().([]byte)
		_ = buf[0]
		testPool.Put(buf) // Возврат в пул
	}

	runtime.ReadMemStats(&m2)
	allocWithPut := m2.TotalAlloc - m1.TotalAlloc
	fmt.Printf("Аллокаций памяти С Put:   %d КБ (объект переиспользован)\n", allocWithPut/1024)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# Аллокаций памяти БЕЗ Put: 5120 КБ (создано 5 новых объектов)
# Аллокаций памяти С Put:   1024 КБ (объект переиспользован)
```

## Под капотом

`m.TotalAlloc` считает совокупный объем выделенной памяти за все время работы программы.

## Подводные камни

Не забывайте `defer pool.Put()`, иначе выигрыш от пула сойдет на нет.

## На собеседовании

**Вопрос с собеседования:** «Приводит ли забытый pool.Put() к Goroutine Leak или Memory Leak?»
**Ответ:** Нет! Невозвращенный объект просто теряет ссылку после выхода из функции и собирается штатным сборщиком мусора GC без утечки памяти.
