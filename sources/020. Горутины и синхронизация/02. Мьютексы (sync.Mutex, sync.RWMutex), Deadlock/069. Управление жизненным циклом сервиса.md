# Управление жизненным циклом сервиса через atomic.LoadInt64 и StoreInt64

## Условие

Используйте `atomic.LoadInt64` и `atomic.StoreInt64` для потокобезопасного чтения и записи флагов состояния (например, `isRunning`).

## Теория

Использование атомарных операций `atomic.LoadInt64` / `atomic.StoreInt64` (или `atomic.Int64`) позволяет реализовывать флаги состояния сервиса (0 = Stopped, 1 = Running, 2 = Draining) с максимальной производительностью без захвата тяжелых мьютексов.

## Решение по шагам

1. Создадим структуру `ServiceState` с `status int64`.
2. Реализуем методы `SetRunning()`, `SetStopped()`, `IsRunning() bool`.
3. Запустим фоновый цикл воркера.
4. В `main` изменим состояние и дождемся остановки.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

const (
	StateStopped = 0
	StateRunning = 1
)

type WorkerService struct {
	state int64
}

func (s *WorkerService) Start() {
	atomic.StoreInt64(&s.state, StateRunning)
}

func (s *WorkerService) Stop() {
	atomic.StoreInt64(&s.state, StateStopped)
}

func (s *WorkerService) IsRunning() bool {
	return atomic.LoadInt64(&s.state) == StateRunning
}

func main() {
	service := &WorkerService{}
	service.Start()

	var wg sync.WaitGroup
	wg.Add(1)

	// Фоновый процесс
	go func() {
		defer wg.Done()
		fmt.Println("[Service] Сервис запущен и обрабатывает события...")
		ticks := 0
		for service.IsRunning() {
			ticks++
			time.Sleep(10 * time.Millisecond)
		}
		fmt.Printf("[Service] Сервис корректно остановлен (обработано тиков: %d)\n", ticks)
	}()

	time.Sleep(35 * time.Millisecond)
	fmt.Println("[Main] Отправка команды Stop()...")
	service.Stop()

	wg.Wait()
	fmt.Println("[Main] Сервис успешно завершил жизненный цикл")
}
```

**`Терминал`**

```bash
go run -race main.go
# Вывод:
# [Service] Сервис запущен и обрабатывает события...
# [Main] Отправка команды Stop()...
# [Service] Сервис корректно остановлен (обработано тиков: 3)
# [Main] Сервис успешно завершил жизненный цикл
```

## Под капотом

`atomic.StoreInt64` генерирует барьер памяти (Memory Barrier), гарантируя, что все предшествующие записи в память станут видны другим ядрам CPU до обновления флага.

## Подводные камни

На 32-битных архитектурах `int64` должен быть строго выровнен по 8-байтной границе.

## На собеседовании

**Вопрос с собеседования:** «Почему чтение незащищенной переменной bool в цикле for running {} может привести к бесконечному зависанию?»
**Ответ:** Компилятор Go при оптимизации (SSA) помещает переменную `running` в регистр процессора один раз перед циклом. Изменение переменной в памяти из другой горутины никогда не обновит этот регистр, и горутина зависнет в вечном цикле.
