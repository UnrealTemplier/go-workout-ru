# Изолированный подкаталог mypkg и экспортные границы

## Условие

Создайте в проекте подкаталог `mypkg` с файлом `helper.go` (пакет `mypkg`). Экспортируйте из него функцию и вызовите её из `main`.

## Теория

Разделение кодовой базы на независимые функциональные пакеты — основа поддерживаемости микросервисов.
Каждый пакет в Go представляет собой отдельное пространство имен (namespace).

## Решение по шагам

1. Создаем директорию `mypkg/`.
2. Создаем файл `mypkg/helper.go` с функцией `FormatLog(level, message string) string`.
3. Импортируем `"hello_mod/mypkg"` в `main.go`.
4. Вызываем `mypkg.FormatLog("INFO", "Сервер стартовал")`.

## Код решения

**`mypkg/helper.go`**

```go
package mypkg

import "fmt"

// FormatLog форматирует строковое сообщение лога с меткой уровня
func FormatLog(level, message string) string {
	return fmt.Sprintf("[%s] %s", level, message)
}
```

ℹ️ Пакет mypkg

**`main.go`**

```go
package main

import (
	"fmt"
	"hello_mod/mypkg"
)

func main() {
	logMsg := mypkg.FormatLog("DEBUG", "Чтение конфигурационного файла завершено.")
	fmt.Println(logMsg)
}
```

ℹ️ Импорт и вызов mypkg

**`Терминал`**

```bash
go run .
# Вывод:
# [DEBUG] Чтение конфигурационного файла завершено.
```

ℹ️ Вывод

## Под капотом

При импорте компилятор проверяет наличие циклов в зависимостях. Если `mypkg` попытается импортировать `main`, компилятор выдаст фатальную ошибку `import cycle not allowed`.

## Подводные камни

- В Go циклические зависимости строго запрещены на уровне компилятора. Если пакет A импортирует B, то B ни прямо, ни косвенно не может импортировать A.

## На собеседовании

**Вопрос с собеседования:** «Как разрешить циклическую зависимость между пакетами в Go?»
**Ответ:** 1. Вынести общие интерфейсы/модели в отдельный третий пакет (например, `domain` или `models`). 2. Использовать инверсию зависимостей (Dependency Inversion) через интерфейсы.
