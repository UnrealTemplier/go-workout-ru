# Запрет time.Sleep в продакшен-коде

## Условие

**Запрет time.Sleep**: Линтер для продакшен кода, запрещающий `time.Sleep` (признак плохой синхронизации).

## Теория

Вызов `time.Sleep` в высоконагруженных микросервисах — признак архитектурного антипаттерна:
1. Попытка синхронизации конкурентных процессов «на глазок» вместо использования каналов, `sync.WaitGroup`, `sync.Cond` или мьютексов.
2. Неуправляемые паузы в цикле ожидания вместо `time.NewTicker` с обработкой `ctx.Done()`.
3. Блокировка горутины, удерживающей системные ресурсы при получении SIGTERM (невозможность Graceful Shutdown).

## Решение по шагам

1. Создайте `*analysis.Analyzer` с именем `nosleep`.
2. В файлах, не оканчивающихся на `_test.go`, найдите вызовы `ast.CallExpr`.
3. Проверьте селектор вызова: пакет `time` и метод `Sleep`.
4. Сгенерируйте диагностику с предложением использовать таймеры или каналы синхронизации.

## Код решения

**`nosleep.go`**

```go
package main

import (
	"go/ast"
	"strings"

	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var NoSleepAnalyzer = &analysis.Analyzer{
	Name: "nosleep",
	Doc:  "forbids time.Sleep in production code in favor of context-aware timers and synchronization primitives",
	Run:  runNoSleep,
}

func runNoSleep(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		fileName := pass.Fset.Position(file.Pos()).Filename
		if strings.HasSuffix(fileName, "_test.go") {
			continue // В тестах sleep допустим для эмуляции задержек
		}

		ast.Inspect(file, func(n ast.Node) bool {
			call, ok := n.(*ast.CallExpr)
			if !ok {
				return true
			}

			sel, ok := call.Fun.(*ast.SelectorExpr)
			if !ok {
				return true
			}

			ident, ok := sel.X.(*ast.Ident)
			if ok && ident.Name == "time" && sel.Sel.Name == "Sleep" {
				pass.Reportf(call.Pos(), "time.Sleep is prohibited in production code; use time.NewTimer with ctx.Done() or sync primitives")
			}

			return true
		})
	}
	return nil, nil
}

func main() {
	singlechecker.Main(NoSleepAnalyzer)
}
```

ℹ️ Линтер запрета time.Sleep в производственном коде

**`Терминал`**

```bash
go run nosleep.go polling.go
# polling.go:34:3: time.Sleep is prohibited in production code; use time.NewTimer with ctx.Done() or sync primitives
```

## Под капотом

`time.Sleep` переводит текущую горутину в состояние `_Gwaiting` с причиной `waitReasonSleep` и регистрирует таймер в рантайм-пуле таймеров P (`pp.timers`). При завершении приложения через отмену контекста горутина, спящая в `time.Sleep`, не просыпается до истечения всего интервала, блокируя быстрый Graceful Shutdown пода в Kubernetes.

## Подводные камни

Вспомогательные утилиты или фоновые CLI-скрипты могут требовать периодических пауз. Для таких случаев линтер должен поддерживать подавление директивой `//nolint:nosleep`.

## На собеседовании

**Вопрос с собеседования:** Чем `select { case <-time.After(d): case <-ctx.Done(): }` опасен внутри бесконечного цикла, и что использовать вместо него?
**Ответ:** `time.After(d)` создает новый таймер `*time.Timer` на каждой итерации цикла. Пока таймер не сработает, он удерживается рантаймом в памяти и не может быть собран GC. При частых итерациях это приводит к утечке памяти. Вместо `time.After` следует использовать `time.NewTimer` с явным сбросом `Reset()` или `time.NewTicker`.
