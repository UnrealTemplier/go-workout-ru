# Интеграция кастомного линтера в golangci-lint

## Условие

**golangci-lint integration**: Интегрируйте ваш кастомный линтер в golangci-lint как plugin.

## Теория

`golangci-lint` — де-факто стандарт линтинга в индустрии Go. Он поддерживает расширение сторонними анализаторами через механизм плагинов (`module plugins` и `Go plugins`).

Современный способ интеграции кастомных линтеров:
1. Анализатор оформляется в виде стандартного пакета Go, экспортирующего экземпляр `*analysis.Analyzer` или структуру, реализующую `plugin.Linter` (Go Plugin).
2. В файле `.golangci.yml` описывается секция `linters-settings.custom`, указывающая путь к анализатору.
3. Утилита `golangci-lint custom` компилирует кастомный бинарник линтера, объединяя официальные линтеры и ваши корпоративные плагины.

## Решение по шагам

1. Создайте Go-пакет с анализатором, экспортирующим функцию `New(conf any) ([]*analysis.Analyzer, error)`.
2. Опишите конфигурацию `.golangci.yml`.
3. Подключите секцию `custom` с указанием пути к модулю.
4. Выполните сборку приватного `golangci-lint` с помощью команды `golangci-lint custom`.

## Код решения

**`plugin.go`**

```go
package plugin

import (
	"golang.org/x/tools/go/analysis"
)

// AnalyzerPlugin экспортируется для golangci-lint module plugin system
func New(settings any) ([]*analysis.Analyzer, error) {
	return []*analysis.Analyzer{
		CustomRuleAnalyzer,
	}, nil
}

var CustomRuleAnalyzer = &analysis.Analyzer{
	Name: "corprule",
	Doc:  "enforces corporate code style guidelines",
	Run: func(pass *analysis.Pass) (interface{}, error) {
		// Логика линтинга
		return nil, nil
	},
}
```

ℹ️ Экспорт кастомного анализатора для интеграции в golangci-lint

**`.golangci.yml`**

```yaml
version: "2"
linters:
  enable:
    - corprule
linters-settings:
  custom:
    corprule:
      path: ./plugin.so
      description: Corporate architectural rules
      original-url: github.com/mycompany/linters/corprule
```

**`Терминал`**

```bash
# Сборка кастомного раннера golangci-lint с вшитыми плагинами
golangci-lint custom --plugins="github.com/mycompany/linters/corprule" -o ./custom-golangci-lint
./custom-golangci-lint run ./...
```

## Под капотом

Команда `golangci-lint custom` динамически генерирует файл `main.go`, импортирующий все указанные плагины, и вызывает `go build`. В отличие от старых динамических библиотек `.so` (требующих идентичных версий CGO и компилятора), статическая компиляция через `module plugin` полностью исключает паники рантайма из-за несовместимости ABI.

## Подводные камни

Использование Go-плагинов (`plugin.Open`, `.so`) в Linux требует строжайшего совпадения версии Go, компилятора, `GOPATH` и всех зависимостей. Малейшее расхождение версий приводит к панике `plugin was built with a different version of package`. Поэтому в BigTech используют подход со статической пересборкой `golangci-lint custom`.

## На собеседовании

**Вопрос с собеседования:** Почему в CI/CD монорепозиториев предпочитают единый агрегатор линтеров `golangci-lint`, а не запуск 20 отдельных утилит по очереди?
**Ответ:** `golangci-lint` выполняет парсинг исходных файлов в AST и построение семантического графа типов `go/types` ровно один раз, сохраняя структуры в оперативной памяти и переиспользуя их между всеми 50+ линтерами. Последовательный запуск отдельных утилит парсил бы кодовую базу заново на каждом шаге, увеличивая время прогона CI в 10–20 раз.
