# Обнаружение context.Background() в хэндлерах

## Условие

**Обнаружение context.Background()**: Линтер, предупреждающий об использовании `context.Background()` в хендлерах (должен быть `req.Context()`).

## Теория

В веб-серверах Go каждый входящий HTTP-запрос инкапсулирует свой собственный жизненный цикл в `r.Context()`. Этот контекст автоматически отменяется при разрыве TCP-соединения клиентом, закрытии вкладки браузера или срабатывании серверного таймаута.

Использование `context.Background()` или `context.TODO()` внутри HTTP-хэндлеров или gRPC-методов:
1. Разрывает цепочку контекста трассировки OpenTelemetry (теряются `trace_id` и спаны).
2. Приводит к выполнению «зомби-запросов»: если клиент отменил запрос, сервер продолжает выполнять тяжелые SQL-запросы в БД и тратить CPU/память.

## Решение по шагам

1. Создайте анализатор `noctxbg`.
2. Идентифицируйте функции хэндлеров по сигнатуре `func(http.ResponseWriter, *http.Request)`.
3. Внутри тела такого хэндлера найдите вызовы `*ast.CallExpr`.
4. Проверьте, вызывается ли `context.Background()` или `context.TODO()`.
5. Сформируйте предупреждение: `use req.Context() instead of context.Background()`.

## Код решения

**`noctxbg.go`**

```go
package main

import (
	"go/ast"

	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var NoCtxBgAnalyzer = &analysis.Analyzer{
	Name: "noctxbg",
	Doc:  "detects context.Background() usage inside HTTP handler functions",
	Run:  runNoCtxBg,
}

func isHTTPHandler(ft *ast.FuncType) bool {
	if ft.Params == nil || len(ft.Params.List) != 2 {
		return false
	}

	p1 := ft.Params.List[0]
	p2 := ft.Params.List[1]

	// Проверка первого параметра: http.ResponseWriter (SelectorExpr)
	sel1, ok := p1.Type.(*ast.SelectorExpr)
	if !ok || sel1.Sel.Name != "ResponseWriter" {
		return false
	}

	// Проверка второго параметра: *http.Request (StarExpr -> SelectorExpr)
	star, ok := p2.Type.(*ast.StarExpr)
	if !ok {
		return false
	}
	sel2, ok := star.X.(*ast.SelectorExpr)
	if !ok || sel2.Sel.Name != "Request" {
		return false
	}

	return true
}

func runNoCtxBg(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			fn, ok := n.(*ast.FuncDecl)
			if !ok || fn.Body == nil || !isHTTPHandler(fn.Type) {
				return true
			}

			ast.Inspect(fn.Body, func(inner ast.Node) bool {
				call, ok := inner.(*ast.CallExpr)
				if !ok {
					return true
				}

				sel, ok := call.Fun.(*ast.SelectorExpr)
				if !ok {
					return true
				}

				ident, ok := sel.X.(*ast.Ident)
				if ok && ident.Name == "context" && (sel.Sel.Name == "Background" || sel.Sel.Name == "TODO") {
					pass.Reportf(call.Pos(), "do not use context.%s() in HTTP handler; use req.Context() to preserve deadlines and tracing", sel.Sel.Name)
				}
				return true
			})

			return true
		})
	}
	return nil, nil
}

func main() {
	singlechecker.Main(NoCtxBgAnalyzer)
}
```

**`Терминал`**

```bash

```

## Под капотом

`r.Context()` связан с отменой сокета на уровне сетевого поллера Go (`netpoller`). При получении события `EPOLLRDHUP` (клиент разорвал соединение) рантайм вызывает функцию `cancel()` внутреннего контекста запроса. Игнорирование этого контекста в пользу `context.Background()` полностью изолирует бизнес-логику от сетевых событий ОС.

## Подводные камни

Если разработчик порождает асинхронную фоновую задачу, которая должна жить дольше HTTP-запроса (fire-and-forget), использование `r.Context()` приведет к преждевременной отмене задачи при завершении ответа. В таких специфических случаях используют `context.WithoutCancel(r.Context())` (начиная с Go 1.21).

## На собеседовании

**Вопрос с собеседования:** Что делает функция `context.WithoutCancel` из Go 1.21, и зачем она нужна?
**Ответ:** Она создает дочерний контекст, который сохраняет все значения (`context.Value`, такие как TraceID, пользовательские метаданные), но отвязывается от родительского дедлайна и отмены (`Done() = nil`). Это идеальное решение для запуска фоновых горутин из HTTP-запроса без потери метаданных телеметрии.
