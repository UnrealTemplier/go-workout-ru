# Обязательная обработка ошибок (errcheck)

## Условие

**Обязательные ошибки**: Линтер, проверяющий, что вызовы функций, возвращающих error, всегда обрабатывают этот error.

## Теория

Игнорирование ошибок в Go — источник скрытых критических сбоев. Ошибка может быть проигнорирована двумя способами:
1. Вызов функции оформлен как чистый `ast.ExprStmt` (результат возврата вообще не присваивается переменной).
2. Ошибка присваивается пустому идентификатору `_` в операторе присваивания `*ast.AssignStmt`.

Для точной проверки требуется `go/types`:
- Семантический тип последнего возвращаемого значения должен реализовывать встроенный интерфейс `error` (`implementsError(T)`).

## Решение по шагам

1. Создайте `*analysis.Analyzer` с именем `errcheck`.
2. В `run` обойдите узлы `*ast.ExprStmt`.
3. Проверьте, является ли выражение вызовом функции `*ast.CallExpr`.
4. Используйте `pass.TypesInfo.Types[call].Type` для получения типа результата.
5. Проверьте тип: если это одиночный `error` или `*types.Tuple`, у которого последний элемент реализует `error`, сгенерируйте `pass.Reportf`.

## Код решения

**`errcheck.go`**

```go
package main

import (
	"go/ast"
	"go/types"

	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var ErrCheckAnalyzer = &analysis.Analyzer{
	Name: "errcheck",
	Doc:  "checks for unhandled errors returned by function and method calls",
	Run:  runErrCheck,
}

var errorType = types.Universe.Lookup("error").Type().Underlying().(*types.Interface)

func returnsError(t types.Type) bool {
	if t == nil {
		return false
	}
	switch v := t.(type) {
	case *types.Named:
		if types.Implements(v, errorType) {
			return true
		}
	case *types.Tuple:
		if v.Len() > 0 {
			last := v.At(v.Len() - 1).Type()
			if types.Implements(last, errorType) {
				return true
			}
		}
	}
	return false
}

func runErrCheck(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			// Случай 1: Вызов как отдельный statement (res = f() пропущен)
			exprStmt, ok := n.(*ast.ExprStmt)
			if !ok {
				return true
			}

			call, ok := exprStmt.X.(*ast.CallExpr)
			if !ok {
				return true
			}

			// Игнорируем стандартные безопасные функции вывода (например fmt.Println)
			if sel, ok := call.Fun.(*ast.SelectorExpr); ok {
				if id, ok := sel.X.(*ast.Ident); ok && id.Name == "fmt" {
					return true
				}
			}

			typeAndVal := pass.TypesInfo.Types[call]
			if returnsError(typeAndVal.Type) {
				pass.Reportf(call.Pos(), "unhandled error: function call returns error that must be checked")
			}

			return true
		})
	}
	return nil, nil
}

func main() {
	singlechecker.Main(ErrCheckAnalyzer)
}
```

**`Терминал`**

```bash

```

## Под капотом

`types.Universe.Lookup("error")` возвращает канонический тип встроенного интерфейса `error` из глобальной области видимости `Universe`. Функция `types.Implements(T, iface)` проверяет, реализует ли тип `T` все методы интерфейса (метод `Error() string`), даже если тип `T` является кастомным псевдонимом или структурой.

## Подводные камни

Не все вызовы, возвращающие `error`, требуют обязательной обработки: например, вызовы `fmt.Fprintf`, `io.Closer` внутри `defer` часто вызывают ложные срабатывания. В продакшен-линтерах настраивают список исключений (exclude-list).

## На собеседовании

**Вопрос с собеседования:** Почему в Go нет исключений (exceptions) и вместо них используется явный возврат ошибок?
**Ответ:** Явный возврат ошибок заставляет разработчика продумывать каждый путь отказа (failure mode) непосредственно в месте вызова. Исключения создают невидимые потоки управления (invisible control flow jumps), усложняя аудит конкурентного кода, освобождение блокировок и транзакций.
