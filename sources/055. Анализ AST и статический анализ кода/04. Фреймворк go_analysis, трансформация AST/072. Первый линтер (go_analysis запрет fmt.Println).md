# Первый линтер (go/analysis запрет fmt.Println)

## Условие

**Первый линтер**: Создайте линтер, который обнаруживает `fmt.Println` в продакшен коде и предлагает использовать structured logging.

## Теория

Фреймворк `golang.org/x/tools/go/analysis` является стандартным ядром для создания статических анализаторов в экосистеме Go (включая `go vet` и `golangci-lint`).

Каждый анализатор инкапсулируется в структуру `*analysis.Analyzer`:
- `Name`: краткий системный идентификатор линтера (например, `"nofmtprint"`).
- `Doc`: документация и описание проверяемого правила.
- `Run`: функция вида `func(pass *analysis.Pass) (interface{}, error)`.

Внутри функции `Run` объект `pass` предоставляет доступ к:
- `pass.Fset`: файловый набор позиций `*token.FileSet`.
- `pass.Files`: срез распарсенных синтаксических деревьев `[]*ast.File`.
- `pass.TypesInfo`: семантическая информация о типах и идентификаторах (если линтер использует `go/types`).
- `pass.Reportf(pos token.Pos, format string, args ...interface{})`: метод для генерации диагностических сообщений с точной позицией в коде.

## Решение по шагам

1. Опишите `*analysis.Analyzer` с именем `Analyzer` для экспорта.
2. В `run(pass *analysis.Pass)` пройдите по всем файлам с помощью `ast.Inspect`.
3. Для каждого узла `*ast.CallExpr` проверьте, является ли вызываемая функция `*ast.SelectorExpr`.
4. Сверьте семантику или идентификаторы: имя пакета `fmt` и имя метода `Println` (или `Printf`, `Print`).
5. В продакшен-коде вызывайте `pass.Reportf(call.Pos(), "use structured logger (e.g. slog) instead of fmt.Println")`.
6. Оберните в `unitchecker.Main(Analyzer)` для создания исполняемой утилиты линтинга.

## Код решения

**`nofmtprint.go`**

```go
package main

import (
	"go/ast"
	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/unitchecker"
)

var Analyzer = &analysis.Analyzer{
	Name: "nofmtprint",
	Doc:  "reports direct calls to fmt.Println/Printf in favor of structured logging",
	Run:  run,
}

func run(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			call, ok := n.(*ast.CallExpr)
			if !ok {
				return true
			}

			sel, ok := call.Fun.(*ast.SelectorExpr)
			if !ok {
				return true
			}

			ident, ok := sel.X.(*ast.Ident)
			if !ok {
				return true
			}

			if ident.Name == "fmt" && (sel.Sel.Name == "Println" || sel.Sel.Name == "Printf" || sel.Sel.Name == "Print") {
				pass.Reportf(call.Pos(), "prohibited call to fmt.%s: use slog or zap for structured logging", sel.Sel.Name)
			}

			return true
		})
	}
	return nil, nil
}

func main() {
	unitchecker.Main(Analyzer)
}
```

ℹ️ Полноценный автономный анализатор go/analysis

**`Терминал`**

```bash
# Запуск анализатора через go vet
go build -o nofmtprint nofmtprint.go
go vet -vettool=./nofmtprint ./...
# main.go:14:2: prohibited call to fmt.Println: use slog or zap for structured logging
```

## Под капотом

`unitchecker.Main` реализует стандартный протокол взаимодействия с утилитой `go vet`. Компилятор Go запускает `unitchecker`, передавая сериализованные данные о пакетах через флаги командной строки (например, `-flags`, пути к AST, метаданные экспорта). Внутри `pass.Reportf` формирует структуры `analysis.Diagnostic`, которые затем выводятся в stderr в стандартном формате компилятора (`file:line:col: message`), поддерживаемом всеми современными IDE.

## Подводные камни

Проверка только текстовых имен AST (`ident.Name == "fmt"`) уязвима для затенения имен: если разработчик назовет переменную `fmt := customStruct{}`, анализатор выдаст ложное срабатывание. Для 100% надежности на уровне BigTech используют `pass.TypesInfo.Uses[sel.Sel]`, чтобы убедиться, что вызываемый объект принадлежит стандартному пакету `"fmt"`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между написанием линтера через чистый `ast.Inspect` и через фреймворк `go/analysis`?
**Ответ:** `go/analysis` берет на себя всю тяжелую системную инфраструктуру: параллельный обход пакетов, кэширование фактов экспорта (`analysis.Fact`), модульное тестирование через `analysistest`, автоисправления (`SuggestedFixes`), интеграцию с `go vet` и `golangci-lint`. Чистый `ast.Inspect` требует ручного парсинга, ручной обработки зависимостей и не масштабируется на большие кодовые базы монорепозиториев.
