# Продвинутый анализатор утечек дескрипторов (os.Open / os.Create)

## Условие

**[Высокая сложность — Детектор утечек]**: Напиши линтер, который ищет `os.Open(...)` или `os.Create(...)` и проверяет, есть ли в теле той же функции вызов `defer ...Close()`. Если нет — репорти об утечке файлового дескриптора.

## Теория

Глубокий статический анализ утечек ресурсов (Resource Leak Analysis):
1. Функции создания ресурсов: `os.Open`, `os.Create`, `os.OpenFile`.
2. Алгоритм проверки:
   - Анализатор находит присваивание `f, err := os.Open(path)` или `f, err = os.Create(path)`.
   - Извлекается идентификатор переменной дескриптора (`f`).
   - Анализируются все пути завершения функции (Exit Paths): операторы `return` и завершение тела функции.
   - На каждом пути проверяется: гарантирован ли вызов `defer f.Close()` или прямой вызов `f.Close()`.
   - Если существует путь выполнения, на котором функция выходит без освобождения `f`, формируется отчет об ошибке.

## Решение по шагам

1. Распарсите код с утечками в `os.Create` и `os.Open`.
2. Создайте трекер открытых ресурсов в функции.
3. Обойдите все операторы функции.
4. Проверьте регистрацию вызовов `defer *.Close()`.
5. Сгенерируйте отчет об утечке дескрипторов файлов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

const leakSource = `package io

import "os"

func WriteReport(data []byte) error {
	// Утечка: os.Create без defer f.Close()
	file, err := os.Create("/tmp/report.txt")
	if err != nil {
		return err
	}
	_, err = file.Write(data)
	return err
}

func SafeRead(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close() // Закрытие присутствует
	return nil, nil
}
`

var ResourceOpeners = map[string]bool{
	"Open":     true,
	"Create":   true,
	"OpenFile": true,
}

func DetectDescriptorLeaks(src string) []string {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "io.go", src, 0)
	if err != nil {
		return []string{fmt.Sprintf("Ошибка парсинга: %v", err)}
	}

	var issues []string

	for _, decl := range file.Decls {
		fn, ok := decl.(*ast.FuncDecl)
		if !ok || fn.Body == nil {
			continue
		}

		openedVars := make(map[string]token.Pos)
		closedVars := make(map[string]bool)

		// 1. Ищем открытие ресурсов
		for _, stmt := range fn.Body.List {
			if assign, ok := stmt.(*ast.AssignStmt); ok && len(assign.Lhs) > 0 && len(assign.Rhs) > 0 {
				if call, ok := assign.Rhs[0].(*ast.CallExpr); ok {
					if sel, ok := call.Fun.(*ast.SelectorExpr); ok {
						if pkg, ok := sel.X.(*ast.Ident); ok && pkg.Name == "os" {
							if ResourceOpeners[sel.Sel.Name] {
								if varIdent, ok := assign.Lhs[0].(*ast.Ident); ok {
									openedVars[varIdent.Name] = assign.Pos()
								}
							}
						}
					}
				}
			}
		}

		// 2. Ищем вызовы defer Close()
		ast.Inspect(fn.Body, func(n ast.Node) bool {
			if def, ok := n.(*ast.DeferStmt); ok {
				if sel, ok := def.Call.Fun.(*ast.SelectorExpr); ok && sel.Sel.Name == "Close" {
					if varIdent, ok := sel.X.(*ast.Ident); ok {
						closedVars[varIdent.Name] = true
					}
				}
			}
			return true
		})

		// 3. Сверяем открытые и закрытые переменные
		for varName, pos := range openedVars {
			if !closedVars[varName] {
				p := fset.Position(pos)
				issues = append(issues, fmt.Sprintf(
					"%s:%d: обнаружена утечка файлового дескриптора: переменная %q открыта через os.%s, но отсутствует defer %s.Close()!",
					p.Filename, p.Line, varName, "Create/Open", varName,
				))
			}
		}
	}

	return issues
}

func main() {
	fmt.Println("Запуск расширенного детектора утечек дескрипторов:")
	leaks := DetectDescriptorLeaks(leakSource)
	for _, l := range leaks {
		fmt.Printf("🚨 %s\n", l)
	}
}
```

## Под капотом

Проблема утечек файлов усугубляется тем, что сборщик мусора Go не вызывает системный `close(2)` немедленно при выходе переменной из области видимости: сборка мусора недетерминирована. Дескриптор освобождается только тогда, когда GC запустит финализатор `runtime.SetFinalizer` объекта `*os.File`, что в HighLoad системах происходит слишком поздно.

## Подводные камни

1. Забытое закрытие при раннем выходе (Early Return): если defer объявлен после раннего return, ресурс успеет утечь.
2. Возврат дескриптора из функции: если функция является конструктором (`func OpenFile() *os.File`), закрывать дескриптор внутри нее нельзя, так как владение передается вызывающему коду.
3. Переприсваивание переменной дескриптора.

## На собеседовании

**Вопрос с собеседования:** Как линтер должен обрабатывать функции-фабрики, возвращающие открытый ресурс (`func OpenDB() (*sql.DB, error)`)?
**Ответ:** Линтер анализирует возвращаемые типы функции `fn.Type.Results`. Если тип созданного дескриптора совпадает с одним из возвращаемых типов функции, и в операторе `return` возвращается эта переменная, владение ресурсом передается вызывающему коду (Transfer of Ownership), и отсутствие `defer Close()` внутри фабрики не является ошибкой.
