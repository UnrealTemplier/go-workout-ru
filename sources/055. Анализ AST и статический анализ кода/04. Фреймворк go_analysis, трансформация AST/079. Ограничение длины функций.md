# Ограничение длины функций

## Условие

**Длина функций**: Линтер, который предупреждает, если функция длиннее N строк.

## Теория

Принцип единственной ответственности (SRP) требует разбиения монолитных функций на компактные, легко тестируемые фрагменты. Чистый код в Go рекомендует держать функции в пределах 40–60 строк.

Вычисление физической длины функции в AST:
1. `fset := pass.Fset`.
2. Начальная позиция функции: `fn.Pos()`.
3. Конечная позиция функции: `fn.End()`.
4. Номера строк вычисляются через `fset.Position(fn.Pos()).Line` и `fset.Position(fn.End()).Line`.
5. Разница \(Line_{end} - Line_{start} + 1\) определяет количество строк.

## Решение по шагам

1. Определите `*analysis.Analyzer` с флагом `max-lines` (по умолчанию 50).
2. Обойдите функции `*ast.FuncDecl`.
3. Вычислите количество строк с помощью `pass.Fset.Position`.
4. Сформируйте предупреждение, если длина превышает порог.
5. Исключите тесты `_test.go`, если требуется анализировать только продакшен-код.

## Код решения

**`funclen.go`**

```go
package main

import (
	"flag"
	"go/ast"
	"strings"

	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var maxLines int

func init() {
	FuncLenAnalyzer.Flags.IntVar(&maxLines, "max", 50, "maximum permitted lines of code per function")
}

var FuncLenAnalyzer = &analysis.Analyzer{
	Name:  "funclen",
	Doc:   "reports functions exceeding maximum allowed length",
	Flags: flag.FlagSet{},
	Run:   runFuncLen,
}

func runFuncLen(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		// Опционально пропускаем файлы тестов
		fileName := pass.Fset.Position(file.Pos()).Filename
		if strings.HasSuffix(fileName, "_test.go") {
			continue
		}

		for _, decl := range file.Decls {
			fn, ok := decl.(*ast.FuncDecl)
			if !ok || fn.Body == nil {
				continue
			}

			start := pass.Fset.Position(fn.Pos()).Line
			end := pass.Fset.Position(fn.End()).Line
			totalLines := end - start + 1

			if totalLines > maxLines {
				pass.Reportf(fn.Pos(), "function %s is too long (%d lines, max allowed is %d)", fn.Name.Name, totalLines, maxLines)
			}
		}
	}
	return nil, nil
}

func main() {
	singlechecker.Main(FuncLenAnalyzer)
}
```

ℹ️ Линтер ограничения длины функций с флагом командной строки

**`Терминал`**

```bash
go run funclen.go -max=30 handler.go
# handler.go:15:1: function HandleCheckout is too long (48 lines, max allowed is 30)
```

## Под капотом

`token.FileSet` хранит отображение плоских смещений `token.Pos` (целые числа от 1 до \(2^{31}-1\)) на конкретные файлы и номера строк с помощью слайса позиций символов новой строки `lines []int`. Метод `Position(pos)` выполняет бинарный поиск по срезу строк конкретного `*token.File`, работая за время \(O(\log L)\), где \(L\) — число строк в файле.

## Подводные камни

Вычисление строк как \(End - Start\) включает пустые строки и комментарии. Продвинутые линтеры (такие как `funclen` в `golangci-lint`) считают только эффективные операторы (`Statements`), обходя `fn.Body.List`.

## На собеседовании

**Вопрос с собеседования:** Почему длинные функции в Go считаются антипаттерном с точки зрения escape-анализа компилятора?
**Ответ:** Длинная функция обычно аккумулирует большое количество локальных переменных и замыканий. Компилятору становится сложнее доказать ограниченность жизненного цикла переменной стеком (inlining budget быстро исчерпывается), что приводит к непреднамеренным аллокациям в кучу (heap escape) и увеличению нагрузки на сборщик мусора GC.
