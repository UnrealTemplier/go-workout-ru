# Обязательные комментарии к экспортируемым сущностям

## Условие

**Обязательные комментарии**: Линтер, требующий комментарии ко всем экспортируемым функциям и типам.

## Теория

По стандартам Effective Go и `golint`, каждый экспортируемый идентификатор (начинающийся с заглавной буквы) обязан иметь комментарий документации `Doc`. Комментарий должен быть полным предложением и начинаться с имени самого идентификатора.

В AST:
- У функций `*ast.FuncDecl` комментарий находится в `fn.Doc`.
- У типов в `*ast.GenDecl` комментарий может быть либо в `genDecl.Doc` (если объявление одиночное), либо в `typeSpec.Doc`.

## Решение по шагам

1. Создайте анализатор `exportedcomments`.
2. Обойдите узлы файла.
3. При встрече `*ast.FuncDecl` проверьте `fn.Name.IsExported()`.
4. Если `fn.Doc == nil` или текст комментария пуст, вызовите `pass.Reportf`.
5. Проверьте первую строку комментария: она должна начинаться с префикса `fn.Name.Name + " "`.
6. Аналогично проверьте `*ast.GenDecl` с `Tok == token.TYPE`.

## Код решения

**`doclint.go`**

```go
package main

import (
	"go/ast"
	"strings"

	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var DocAnalyzer = &analysis.Analyzer{
	Name: "exporteddoc",
	Doc:  "verifies that all exported functions and types have doc comments starting with the identifier name",
	Run:  runDoc,
}

func runDoc(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		for _, decl := range file.Decls {
			switch d := decl.(type) {
			case *ast.FuncDecl:
				if !d.Name.IsExported() {
					continue
				}
				// Игнорируем методы неэкспортированных типов
				if d.Recv != nil && len(d.Recv.List) > 0 {
					recvType := d.Recv.List[0].Type
					if star, ok := recvType.(*ast.StarExpr); ok {
						recvType = star.X
					}
					if id, ok := recvType.(*ast.Ident); ok && !id.IsExported() {
						continue
					}
				}

				validateDoc(pass, d.Doc, d.Name.Pos(), d.Name.Name, "function")

			case *ast.GenDecl:
				for _, spec := range d.Specs {
					ts, ok := spec.(*ast.TypeSpec)
					if !ok || !ts.Name.IsExported() {
						continue
					}

					doc := ts.Doc
					if doc == nil {
						doc = d.Doc
					}
					validateDoc(pass, doc, ts.Name.Pos(), ts.Name.Name, "type")
				}
			}
		}
	}
	return nil, nil
}

func validateDoc(pass *analysis.Pass, doc *ast.CommentGroup, pos ast.Node, name, kind string) {
	if doc == nil || strings.TrimSpace(doc.Text()) == "" {
		pass.Reportf(pos.Pos(), "exported %s %s must have comment", kind, name)
		return
	}

	text := strings.TrimSpace(doc.Text())
	if !strings.HasPrefix(text, name+" ") && !strings.HasPrefix(text, name+"\n") {
		pass.Reportf(doc.Pos(), "comment for exported %s %s should begin with '%s ...'", kind, name, name)
	}
}

func main() {
	singlechecker.Main(DocAnalyzer)
}
```

ℹ️ Линтер проверки комментариев документации

**`Терминал`**

```bash
go run doclint.go api.go
# api.go:12:1: exported function ProcessPayment must have comment
# api.go:25:1: comment for exported type Config should begin with 'Config ...'
```

## Под капотом

`ast.CommentGroup.Text()` автоматически очищает комментарии от синтаксического шума: удаляет префиксы `//`, маркеры блока `/*` и `*/`, нормализует пробелы и переводы строк. Это позволяет инспектировать чистый текст документации без ручного парсинга регулярок.

## Подводные камни

В блочных объявлениях `type ( Foo int \n Bar string )` комментарий может находиться на уровне `GenDecl` (общий для всего блока) или `TypeSpec` (индивидуальный). Если линтер проверяет только `TypeSpec.Doc`, он ошибочно посчитает, что у спецификаций нет комментария.

## На собеседовании

**Вопрос с собеседования:** Почему Go-сообщество строго требует, чтобы комментарий начинался с имени функции, а не с формата JSDoc/Javadoc `@param`?
**Ответ:** 1) Инструмент `godoc` и `pkgsite` генерируют краткие сводки пакетов, беря первое предложение документации. Если оно начинается с имени функции, сводка читается как естественное грамматическое повествование: *«ProcessPayment executes authorization against gateway...»*. 2) При переименовании функции разработчик видит имя в первой строке комментария и не забывает обновить документацию.
