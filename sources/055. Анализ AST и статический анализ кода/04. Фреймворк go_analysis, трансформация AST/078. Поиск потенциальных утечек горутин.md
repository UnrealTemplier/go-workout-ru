# Поиск потенциальных утечек горутин

## Условие

**Поиск потенциальных утечек горутин.**: Найдите в AST все вызовы `go func()` и проверьте, что внутри горутины есть чтение из `context.Context` или канала для возможности завершения.

### Исходная формулировка

**Поиск потенциальных утечек горутин.**: Найдите в AST все вызовы `go func()` и проверьте, что внутри горутины есть чтение из `context.Context` или канала для возможности завершения. Выведите предупреждение, если нет.

## Теория

Утечка горутин (goroutine leak) — одна из главных причин деградации памяти и аварийных остановок Go-сервисов под нагрузкой. Горутина, запущенная без механизма прерывания (отмена контекста или канал `stopCh`), навсегда остается в рантайме, удерживая свой стек (от 2 КБ до гигабайт) и ссылки на объекты в куче.

В AST запуск горутины представлен узлом `*ast.GoStmt`.
Для обнаружения утечки проверяется:
1. Вызывается ли анонимная функция `*ast.FuncLit` или именованная функция.
2. В теле горутины ищется конструкция выхода:
   - Прием из канала: оператор унарной стрелки `*ast.UnaryExpr` с `Op == token.ARROW`.
   - Конструкция `*ast.SelectStmt`, содержащая ветку с `<-ctx.Done()` или `<-stopCh`.
   - Если горутина содержит бесконечный цикл `for {}` без канала завершения, регистрируется критическая уязвимость.

## Решение по шагам

1. Создайте анализатор `leakcheck`.
2. Найдите все узлы `*ast.GoStmt`.
3. Извлеките тело вызываемой функции (рассмотрите случай `*ast.FuncLit`).
4. Проверьте наличие бесконечного цикла `for` без условия (`stmt.Cond == nil`).
5. Убедитесь, что внутри горутины присутствует чтение из канала (`<-ctx.Done()`).
6. Если цикл бесконечный и каналы отмены не опрашиваются, сформируйте предупреждение.

## Код решения

**`leakcheck.go`**

```go
package main

import (
	"go/ast"
	"go/token"

	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var LeakAnalyzer = &analysis.Analyzer{
	Name: "leakcheck",
	Doc:  "detects infinite goroutines lacking context or channel cancellation",
	Run:  runLeak,
}

func hasChannelReceive(body *ast.BlockStmt) bool {
	found := false
	ast.Inspect(body, func(n ast.Node) bool {
		if found {
			return false
		}
		// Проверка <-ch
		if u, ok := n.(*ast.UnaryExpr); ok && u.Op == token.ARROW {
			found = true
			return false
		}
		// Проверка case <-ch в select
		if comm, ok := n.(*ast.CommClause); ok && comm.Comm != nil {
			if _, ok := comm.Comm.(*ast.ExprStmt); ok {
				found = true
				return false
			}
		}
		return true
	})
	return found
}

func runLeak(pass *analysis.Pass) (interface{}, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			goStmt, ok := n.(*ast.GoStmt)
			if !ok {
				return true
			}

			fnLit, ok := goStmt.Call.Fun.(*ast.FuncLit)
			if !ok || fnLit.Body == nil {
				return true
			}

			// Ищем бесконечные циклы for without condition
			for _, stmt := range fnLit.Body.List {
				forStmt, ok := stmt.(*ast.ForStmt)
				if ok && forStmt.Cond == nil && forStmt.Init == nil && forStmt.Post == nil {
					// Бесконечный цикл for {}
					if !hasChannelReceive(forStmt.Body) {
						pass.Reportf(goStmt.Pos(), "potential goroutine leak: infinite loop without channel or context cancellation")
					}
				}
			}
			return true
		})
	}
	return nil, nil
}

func main() {
	singlechecker.Main(LeakAnalyzer)
}
```

ℹ️ Статический детектор потенциальных утечек горутин

**`Терминал`**

```bash

# worker.go:18:2: potential goroutine leak: infinite loop without channel or context cancellation
```

## Под капотом

Горутина, заблокированная на канале или в бесконечном цикле без системных вызовов/точек прерывания рантайма Go, не может быть собрана GC. Сборщик мусора отслеживает объекты в куче, но активный стек горутины является корневым объектом (GC root). Пока жива горутина, все переменные, на которые ссылается ее стек, остаются в куче, провоцируя OOM-утечку.

## Подводные камни

Статический анализ AST не видит динамического поведения каналов: если горутина читает из канала `<-ch`, но писатель в канал никогда не отправит значение и не закроет его, горутина все равно утечет в рантайме. Полноценный анализ утечек дополняется тестами с `go.uber.org/goleak`.

## На собеседовании

**Вопрос с собеседования:** Как в production-коде защититься от утечек горутин на архитектурном уровне?
**Ответ:** 1) Правило первого аргумента: любая долгоживущая или фоновая функция обязана принимать `ctx context.Context`. 2) Использование `errgroup.WithContext` вместо `sync.WaitGroup` для автоматического каскадного завершения горутин при первой ошибке. 3) Интеграция `goleak.VerifyNone(t)` в модульные тесты.
