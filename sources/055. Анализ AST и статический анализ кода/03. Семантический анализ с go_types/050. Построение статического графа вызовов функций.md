# Построение статического графа вызовов функций пакета (Caller → Callee Graph)

## Условие

Построение графа вызовов: Напишите инструмент, который строит caller → callee граф для всех функций в пакете. Объясните, как различать вызовы методов (SelectorExpr.X.Method), функций пакета (SelectorExpr с Ident) и встроенные вызовы (CallExpr.Fun — Ident).

### Исходная формулировка

**Построение графа вызовов.**: Напишите инструмент, который строит `caller → callee` граф для всех функций в пакете. Объясните, как различать вызовы методов (`SelectorExpr.X.Method`), функций пакета (`SelectorExpr` с `Ident`) и встроенные вызовы (`CallExpr.Fun` — `Ident`).

## Теория

Граф вызовов (Call Graph) — фундамент статического анализа архитектуры, обнаружения dead code и построения деревьев трассировки:
1. Вершины графа (Nodes): объявленные функции и методы пакета.
2. Ребра графа (Edges): вызовы других функций из тела текущей функции (`caller -> callee`).
3. Классификация целевой функции `call.Fun`:
   - `*ast.Ident`: прямой вызов пакетной или встроенной функции (`Helper()`, `len()`).
   - `*ast.SelectorExpr`: вызов метода структуры (`obj.Method()`) или функции импортированного пакета (`pkg.Func()`).
4. Граф представляется структурой смежности: `map[string][]string`.

## Решение по шагам

1. Распарсите Go-код с цепочкой вызовов между функциями.
2. Инициализируйте `callGraph := make(map[string][]string)`.
3. Для каждого `*ast.FuncDecl` зафиксируйте имя вызывающей функции (`caller`).
4. Обойдите тело функции и соберите имена всех вызываемых функций (`callees`).
5. Выведите ориентированный граф вызовов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

const pipelineSource = `package pipeline

func Entrypoint() {
	ValidateInput()
	ProcessPayload()
}

func ProcessPayload() {
	EnrichData()
	SaveToStorage()
}

func ValidateInput() {}
func EnrichData() {}
func SaveToStorage() {}
`

func BuildCallGraph(src string) map[string][]string {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "pipeline.go", src, 0)
	if err != nil {
		panic(err)
	}

	graph := make(map[string][]string)

	for _, decl := range file.Decls {
		fn, ok := decl.(*ast.FuncDecl)
		if !ok || fn.Body == nil {
			continue
		}

		callerName := fn.Name.Name
		if fn.Recv != nil && len(fn.Recv.List) > 0 {
			callerName = fmt.Sprintf("(%v).%s", fn.Recv.List[0].Type, callerName)
		}

		ast.Inspect(fn.Body, func(n ast.Node) bool {
			call, ok := n.(*ast.CallExpr)
			if !ok {
				return true
			}

			callee := ""
			switch f := call.Fun.(type) {
			case *ast.Ident:
				callee = f.Name
			case *ast.SelectorExpr:
				if xIdent, ok := f.X.(*ast.Ident); ok {
					callee = xIdent.Name + "." + f.Sel.Name
				} else {
					callee = f.Sel.Name
				}
			}

			if callee != "" {
				graph[callerName] = append(graph[callerName], callee)
			}

			return true
		})
	}

	return graph
}

func main() {
	graph := BuildCallGraph(pipelineSource)

	fmt.Println("Статический граф вызовов функций (Caller -> Callees):")
	fmt.Println("===================================================")

	for caller, callees := range graph {
		fmt.Printf("Функция %s:\n", caller)
		if len(callees) == 0 {
			fmt.Println("  (нет исходящих вызовов)")
		}
		for _, callee := range callees {
			fmt.Printf("  └──> %s()\n", callee)
		}
		fmt.Println()
	}
}
```

## Под капотом

Для точного построения графа вызовов с учетом полиморфизма интерфейсов (Dynamic Dispatch) и функциональных указателей применяется пакет `golang.org/x/tools/go/callgraph/cha` (Class Hierarchy Analysis) или `rta` (Rapid Type Analysis). Они используют SSA-представление и типы для определения всех возможных получателей интерфейсного вызова.

## Подводные камни

1. Вызовы через интерфейс: в AST синтаксис `svc.Execute()` указывает на метод интерфейса, но реальная структура-исполнитель неизвестна без семантического анализа.
2. Рекурсивные вызовы: могут создать циклы в графе вызовов (`A -> B -> A`).
3. Вызовы в анонимных горутинах: вызов `go fn()` также должен связываться с родительской функцией.

## На собеседовании

**Вопрос с собеседования:** Чем статический Call Graph отличается от графа вызовов pprof?
**Ответ:** Статический граф строится анализом исходного кода компилятором без запуска программы; он охватывает все потенциально возможные пути выполнения. Граф `pprof` (динамический профилировщик) строится семплированием стека работающего процесса; он отражает только фактически совершенные вызовы под реальной нагрузкой с точной статистикой затраченного процессорного времени (CPU samples).
