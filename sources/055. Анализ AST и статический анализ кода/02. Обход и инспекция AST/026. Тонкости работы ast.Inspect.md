# Тонкости работы ast.Inspect: порядок вызовов и фильтрация ветвей

## Условие

**ast.Inspect**: Более удобная альтернатива Walk: `ast.Inspect(node, func(n ast.Node) bool { ... })`.

## Теория

Функция `ast.Inspect(node ast.Node, f func(ast.Node) bool)` — самый популярный инструмент работы с AST:
1. Семантика возвращаемого значения:
   - `true`: парсер продолжает рекурсивный спуск в дочерние узлы.
   - `false`: парсер пропускает все дочерние узлы текущей ветки дерева и переходит к следующему соседнему узлу (sibling).
2. Завершающий вызов:
   - В конце обработки поддерева функция `f` вызывается с `n == nil`.
   - Это необходимо для отката состояния, если замыкание отслеживает стек вызовов.
3. Порядок обхода:
   - Прямой обход в глубину (pre-order DFS).

## Решение по шагам

1. Напишите код с глубокой вложенностью операторов.
2. Продемонстрируйте, как возврат `false` отсекает обход всего поддерева функции.
3. Продемонстрируйте получение вызова с `n == nil`.
4. Сравните количество проинспектированных узлов с фильтрацией и без.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

const demoCode = `package demo

func HeavyFunction() {
	x := 10
	if x > 0 {
		for i := 0; i < x; i++ {
			println(i)
		}
	}
}

func LightweightFunction() {
	println("fast")
}
`

func main() {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "demo.go", demoCode, 0)
	if err != nil {
		panic(err)
	}

	// Вариант 1: Полный обход всех узлов
	totalNodes := 0
	ast.Inspect(file, func(n ast.Node) bool {
		if n != nil {
			totalNodes++
		}
		return true
	})

	// Вариант 2: Пропуск тела HeavyFunction
	filteredNodes := 0
	ast.Inspect(file, func(n ast.Node) bool {
		if n != nil {
			filteredNodes++
		}

		if fn, ok := n.(*ast.FuncDecl); ok && fn.Name.Name == "HeavyFunction" {
			// Отсекаем все внутренности функции HeavyFunction!
			return false
		}
		return true
	})

	fmt.Printf("Полный обход дерева:             %d узлов\n", totalNodes)
	fmt.Printf("Обход с пропуском HeavyFunction: %d узлов\n", filteredNodes)
	fmt.Printf("Сэкономлено узлов:               %d\n", totalNodes-filteredNodes)
}
```

ℹ️ Управление ветвлением и оптимизация скорости обхода в ast.Inspect

**`Терминал`**

```bash

# Обход с пропуском HeavyFunction: 12 узлов
# Сэкономлено узлов:               16
```

## Под капотом

В реализации `ast.Walk` проверка возврата выглядит так:
```go
if v = v.Visit(n); v == nil {
    return
}
for _, child := range children(n) {
    Walk(v, child)
}
v.Visit(nil)
```
Когда визитор возвращает `nil` (или `ast.Inspect` возвращает `false`), цикл по детям узла не выполняется вообще. Это ключевой механизм ускорения статических анализаторов: например, если линтер ищет только сигнатуры типов, возврат `false` на уровне тел функций сокращает время парсинга на 90%.

## Подводные камни

1. Забытый возврат `true` по умолчанию: если функция по ошибке возвращает `false` в ветке `default`, обход прервется сразу на корневом узле `*ast.File`.
2. Неучет вызова с `n == nil`: если в замыкании вызываются методы `n.Pos()`, проверка `if n == nil { return false }` обязательна во избежание паники.
3. Модификация AST во время работы `ast.Inspect`: удаление узлов во время обхода может привести к `index out of range` в срезах парсера.

## На собеседовании

**Вопрос с собеседования:** Почему при поиске импортов в файле не стоит использовать `ast.Inspect` по всему дереву?
**Ответ:** Потому что импорты файла Go хранятся в двух местах: напрямую в срезе `file.Imports []*ast.ImportSpec` и в начале списка `file.Decls`. Обход всего синтаксического дерева через `ast.Inspect` приведет к бессмысленному перебору всех сотен инструкций функций файла. Достаточно просто прочитать срез `file.Imports` за \(O(1)\).
