# Сборка единого мультичекера (multichecker) и архитектура golangci-lint

## Условие

Мультичекер: Соберите 3 линтера (из упр. 109, 110, 111) в один бинарник через multichecker. Объясните, как golangci-lint использует этот же подход для объединения hundreds of checks.

### Исходная формулировка

**Мультичекер.**: Соберите 3 линтера (из упр. 109, 110, 111) в один бинарник через `multichecker`. Объясните, как `golangci-lint` использует этот же подход для объединения hundreds of checks.

## Теория

Запуск десятков независимых линтеров по отдельности неэффективен: каждый процесс заново открывает файлы, парсит AST, строит кэш типов `go/types` и аллоцирует гигабайты памяти.
Фреймворк `golang.org/x/tools/go/analysis/multichecker`:
1. Принимает список независимых анализаторов: `multichecker.Main(A1, A2, A3, ...)`.
2. Архитектура работы:
   - Единая фаза загрузки исходников пакета (`go/packages`).
   - Однократное построение AST-деревьев файлов.
   - Однократный семантический прогон `go/types` с общим кэшем типов.
   - Параллельное выполнение функции `Run` всех анализаторов по построенному дереву.
3. Это лежит в основе таких инструментов, как `golangci-lint` и `go vet`.

## Решение по шагам

1. Объявите три независимых анализатора: `NoPanicAnalyzer`, `NoFmtPrintlnAnalyzer`, `DocCommentsAnalyzer`.
2. Настройте точку входа через `multichecker.Main`.
3. Объясните схему параллельного исполнения.
4. Продемонстрируйте структуру кода мультичекера.

## Код решения

**`multicheck.go`**

```go
package main

import (
	"go/ast"
	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/multichecker"
)

// Анализатор 1: Запрет panic
var AnalyzerNoPanic = &analysis.Analyzer{
	Name: "nopanic",
	Doc:  "запрещает вызовы panic",
	Run: func(pass *analysis.Pass) (any, error) {
		for _, file := range pass.Files {
			ast.Inspect(file, func(n ast.Node) bool {
				if call, ok := n.(*ast.CallExpr); ok {
					if id, ok := call.Fun.(*ast.Ident); ok && id.Name == "panic" {
						pass.Reportf(call.Pos(), "вызов panic() запрещен")
					}
				}
				return true
			})
		}
		return nil, nil
	},
}

// Анализатор 2: Запрет fmt.Println
var AnalyzerNoFmt = &analysis.Analyzer{
	Name: "nofmt",
	Doc:  "запрещает прямой вывод через fmt.Println",
	Run: func(pass *analysis.Pass) (any, error) {
		for _, file := range pass.Files {
			ast.Inspect(file, func(n ast.Node) bool {
				if call, ok := n.(*ast.CallExpr); ok {
					if sel, ok := call.Fun.(*ast.SelectorExpr); ok {
						if pkg, ok := sel.X.(*ast.Ident); ok && pkg.Name == "fmt" && sel.Sel.Name == "Println" {
							pass.Reportf(call.Pos(), "замените fmt.Println на structured logging")
						}
					}
				}
				return true
			})
		}
		return nil, nil
	},
}

func main() {
	// multichecker объединяет проверки в единый супер-линтер
	multichecker.Main(
		AnalyzerNoPanic,
		AnalyzerNoFmt,
	)
}
```

## Под капотом

`multichecker.Main` строит ориентированный ациклический граф (DAG) зависимостей между анализаторами (`Analyzer.Requires`). Если нескольким чекерам требуется семантический инспектор (`inspect.Analyzer`), мультичекер запускает его ровно один раз, сохраняет построенный индекс в оперативной памяти и передает готовые результаты всем зависимым чекерам через механизм результатов `pass.ResultOf`.

## Подводные камни

1. Циклические зависимости анализаторов (`A` требует `B`, а `B` требует `A`): приведет к панике при старте `multichecker.Main`.
2. Модификация AST внутри `Run`: анализаторы разделяют одно и то же AST в памяти, мутация узла одним чекером повредит работу остальных параллельных чекеров.
3. Несоответствие имен флагов командной строки: флаги формируются автоматически из `Analyzer.Name`.

## На собеседовании

**Вопрос с собеседования:** Почему `golangci-lint` работает в 5–10 раз быстрее запуска отдельных линтеров?
**Ответ:** `golangci-lint` использует концепцию единого графа пакетов (Single Pass Loader). Он один раз загружает пакеты в память через `go/packages`, парсит AST в пул горутин, один раз строит структуры типов `go/types`, а затем параллельно запускает сотни чекеров по разделяемым структурам данных, полностью исключая избыточный I/O диска и повторный парсинг.
