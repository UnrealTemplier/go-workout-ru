# Линтер валидации конвенций именования идентификаторов и формата комментариев

## Условие

Напишите линтер, который проверяет, что все экспортируемые функции, методы и типы имеют комментарий в формате // FuncName does something.. Используйте go/ast.Inspect.

### Исходная формулировка

**Проверка именования экспортируемых идентификаторов.**: Напишите линтер, который проверяет, что все экспортируемые функции, методы и типы имеют комментарий в формате `// FuncName does something.`. Используйте `go/ast.Inspect`.

## Теория

Единый стиль кодовой базы в BigTech поддерживается жесткими правилами линтинга (stylecheck, revive):
1. Экспортируемые сущности:
   - Функции: `*ast.FuncDecl`.
   - Типы: `*ast.TypeSpec` внутри `*ast.GenDecl`.
   - Константы и переменные: `*ast.ValueSpec`.
2. Для каждой сущности проверяется наличие `Doc`.
3. Текст комментария обязан начинаться с `Name + " "` и содержать глагол действия в настоящем времени (`// UserStore manages...`).
4. Точка в конце комментария обязательна согласно Effective Go.

## Решение по шагам

1. Распарсите Go-код с различными типами объявлений.
2. Используйте `ast.Inspect` для проверки `FuncDecl` и `TypeSpec`.
3. Для каждого экспортируемого узла проверьте формат комментария.
4. Выдайте предупреждения при нарушении структуры GoDoc.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"strings"
)

const sampleModule = `package store

// DatabaseSession представляет пул соединений с базой данных.
type DatabaseSession struct{}

// неверный формат: не с заглавной буквы и без точки в конце
type CacheManager struct{}

// Ping проверяет доступность узла кластера.
func (DatabaseSession) Ping() error { return nil }

// Close закрывает соединения
func (DatabaseSession) Close() error { return nil }
`

func CheckDocFormat(src string) []string {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "store.go", src, parser.ParseComments)
	if err != nil {
		return []string{fmt.Sprintf("Ошибка парсинга: %v", err)}
	}

	var issues []string

	ast.Inspect(file, func(n ast.Node) bool {
		var name string
		var doc *ast.CommentGroup
		var pos token.Pos

		switch node := n.(type) {
		case *ast.FuncDecl:
			if !ast.IsExported(node.Name.Name) {
				return true
			}
			name = node.Name.Name
			doc = node.Doc
			pos = node.Pos()

		case *ast.TypeSpec:
			if !ast.IsExported(node.Name.Name) {
				return true
			}
			name = node.Name.Name
			doc = node.Doc
			pos = node.Pos()
		}

		if name == "" {
			return true
		}

		position := fset.Position(pos)

		if doc == nil || len(doc.List) == 0 {
			issues = append(issues, fmt.Sprintf(
				"%s:%d: отсутствуют комментарии к %s", position.Filename, position.Line, name,
			))
			return true
		}

		rawText := strings.TrimSpace(doc.Text())
		expectedPrefix := name + " "

		if !strings.HasPrefix(rawText, expectedPrefix) {
			issues = append(issues, fmt.Sprintf(
				"%s:%d: комментарий к %s обязан начинаться с %q",
				position.Filename, position.Line, name, expectedPrefix,
			))
		}

		if !strings.HasSuffix(rawText, ".") {
			issues = append(issues, fmt.Sprintf(
				"%s:%d: комментарий к %s обязан завершаться точкой '.'",
				position.Filename, position.Line, name,
			))
		}

		return true
	})

	return issues
}

func main() {
	fmt.Println("Запуск проверки формата GoDoc комментариев:")
	problems := CheckDocFormat(sampleModule)
	for _, p := range problems {
		fmt.Printf("⚠️  %s\n", p)
	}
}
```

## Под капотом

В AST узлы `*ast.TypeSpec` могут получать комментарий двумя путями: через поле `node.Doc` (если комментарий относится конкретно к типу) или через `genDecl.Doc` (если комментарий расположен над ключевым словом `type`). Полноценный анализатор проверяет оба поля: `if node.Doc == nil { doc = parentGenDecl.Doc }`.

## Подводные камни

1. Забытый учет комментариев над `*ast.GenDecl`: для одиночных типов `type Foo struct{}` комментарий часто привязывается к `GenDecl`, а не к `TypeSpec`.
2. Префиксы в многоязычных проектах: строгий поиск `Name + " "` требует корректной обработки кириллицы и знаков препинания.
3. Пропуск точки при многострочных комментариях с блоками кода или списками.

## На собеседовании

**Вопрос с собеседования:** Почему в Go линтерах рекомендуется избегать регулярных выражений при проверке синтаксиса комментариев?
**Ответ:** Регулярные выражения (`regexp.Regexp`) в Go компилируются в автоматы с динамическими аллокациями памяти и работают на порядки медленнее простых строковых функций (`strings.HasPrefix`, `strings.HasSuffix`, `strings.TrimSpace`). В проектах на миллионы строк кода замена regex на строковые срезы ускоряет линтинг в десятки раз.
