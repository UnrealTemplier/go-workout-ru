# In-memory парсинг исходного кода из строки через parser.ParseFile

## Условие

**Парсинг из строки**: Используйте `parser.ParseFile(fset, "", source, 0)` для парсинга кода из строки.

## Теория

При написании юнит-тестов, веб-песочниц (Playground) или плагинов динамического анализа часто требуется анализировать код без создания временных файлов на диске:
1. Вызов `parser.ParseFile(fset, filename, src, mode)`:
   - Если `filename == ""` и `src != nil` (строка, срез байт или `io.Reader`), парсер создает виртуальный узел `*token.File` с безымянным путем.
   - Позиции строк и колонок вычисляются корректно относительно начала строки `src`.
   - Это на порядки быстрее работы с дисковой файловой системой и не требует очистки временных файлов (`os.Remove`).
2. Метод `fset.File(node.Pos()).Name()` вернет переданный псевдоним файла.

## Решение по шагам

1. Создайте Go-код в виде строкового литерала.
2. Инициализируйте `fset := token.NewFileSet()`.
3. Вызовите `file, err := parser.ParseFile(fset, "virtual_test.go", src, 0)`.
4. Извлеките имя пакета и количество объявлений.
5. Продемонстрируйте корректность номеров строк виртуального файла.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/parser"
	"go/token"
)

func main() {
	inMemorySrc := `package playground

import "fmt"

func Greet(name string) {
	fmt.Printf("Hello, %s!\n", name)
}
`

	fset := token.NewFileSet()
	// Парсинг напрямую из оперативной памяти без записи на диск
	file, err := parser.ParseFile(fset, "memory_input.go", inMemorySrc, parser.ParseComments)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Имя распарсенного пакета: %s\n", file.Name.Name)
	fmt.Printf("Число top-level деклараций: %d\n", len(file.Decls))

	fn := file.Decls[1].(*astFuncDeclAlias) // вторая декларация - функция
	pos := fset.Position(fn.Pos())
	fmt.Printf("Функция %s расположена в %s на строке %d\n",
		fn.Name.Name, pos.Filename, pos.Line)
}

// Псевдоним для компактности
type astFuncDeclAlias = struct {
	Doc  any
	Recv any
	Name *struct{ Name string }
	Type any
	Body any
}
```

ℹ️ Парсинг Go-кода напрямую из памяти без обращения к файловой системе

**`main_real.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

func main() {
	inMemorySrc := `package playground

import "fmt"

func Greet(name string) {
	fmt.Printf("Hello, %s!\n", name)
}
`

	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "memory_input.go", inMemorySrc, parser.ParseComments)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Имя распарсенного пакета: %s\n", file.Name.Name)
	for _, decl := range file.Decls {
		if fn, ok := decl.(*ast.FuncDecl); ok {
			pos := fset.Position(fn.Pos())
			fmt.Printf("Функция %s расположена в %s на строке %d\n",
				fn.Name.Name, pos.Filename, pos.Line)
		}
	}
}
```

ℹ️ Идиоматичный in-memory парсинг через go/parser

**`Терминал`**

```bash
go run main_real.go
# Вывод:
# Имя распарсенного пакета: playground
# Функция Greet расположена в memory_input.go на строке 5
```

## Под капотом

Когда `src` передается как `string`, `parser.ParseFile` конвертирует её в срез байт `[]byte(src)` и создает `token.File` в переданном `token.FileSet`. Сканер считывает байты из слайса памяти, разделяя строки по байту `\n` (`0x0A`). Все координаты в точности соответствуют реальному файлу, что делает in-memory парсинг эталоном для модульного тестирования линтеров.

## Подводные камни

1. Передача `src = nil`: парсер попытается открыть файл с именем `filename` на диске. Если передать `""` и `nil`, возникнет ошибка `open : no such file or directory`.
2. Огромные строки в памяти: передача гигабайтных файлов в виде одной строки вызовет всплеск потребления памяти (лучше передавать `io.Reader`).
3. Синтаксические ошибки прерывают создание полного дерева: поле `file` может быть частично заполнено даже при возврате `err != nil`.

## На собеседовании

**Вопрос с собеседования:** Как юнит-тестировать линтеры без создания временных файлов на диске?
**Ответ:** Передавать тестовые фрагменты Go-кода строковыми литералами в `parser.ParseFile(fset, "test.go", testCode, 0)`. Это ускоряет выполнение тестов в десятки раз, исключает деградацию I/O диска и гарантирует отсутствие артефактов файловой системы в Git-репозитории.
