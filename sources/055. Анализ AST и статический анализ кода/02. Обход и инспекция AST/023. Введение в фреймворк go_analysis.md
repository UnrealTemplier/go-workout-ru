# Введение в фреймворк go/analysis: создание модульного Analyzer

### Исходная формулировка

**Фреймворк `go/analysis`.**: Перепишите линтер из упр. 109 с использованием `golang.org/x/tools/go/analysis`. Объясните структуру `analysis.Analyzer`: `Run`, `Pass`, `Reportf`, `Fact`. Покажите, как запустить через `singlechecker.Main` и `multichecker`.

## Теория

Фреймворк `golang.org/x/tools/go/analysis` — официальный стандарт создания линтеров в Go (используется в `go vet`, `gopls` и `golangci-lint`):
1. `analysis.Analyzer`:
   - `Name string`: уникальный идентификатор правила (например `nofmt`).
   - `Doc string`: документация линтера.
   - `Requires []*Analyzer`: список анализаторов-зависимостей (например, для доступа к `inspect.Analyzer`).
   - `Run func(pass *Pass) (any, error)`: главная точка входа.
2. `*analysis.Pass`: контекст выполнения проверки для одного пакета:
   - `Fset *token.FileSet`: набор файлов.
   - `Files []*ast.File`: распарсенные AST файлов пакета.
   - `TypesInfo *types.Info`: семантическая информация о типах.
   - `Reportf(pos token.Pos, format string, args ...any)`: вывод диагностического сообщения с привязкой к позиции.
3. Запуск:
   - `singlechecker.Main(MyAnalyzer)`: автономный бинарник линтера.
   - `multichecker.Main(A1, A2, A3)`: объединенный набор анализаторов.

## Решение по шагам

1. Создайте структуру `analysis.Analyzer`.
2. Реализуйте функцию `run(pass *analysis.Pass) (any, error)`.
3. Обойдите файлы пакета `pass.Files`.
4. Используйте `pass.Reportf(node.Pos(), "сообщение")` при нахождении дефекта.
5. Продемонстрируйте структуру запуска.

## Код решения

**`analyzer.go`**

```go
package main

import (
	"go/ast"
	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

// NoPanicAnalyzer запрещает вызовы встроенной функции panic
var NoPanicAnalyzer = &analysis.Analyzer{
	Name: "nopanic",
	Doc:  "запрещает использование встроенной функции panic в продакшен коде",
	Run:  run,
}

func run(pass *analysis.Pass) (any, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			call, ok := n.(*ast.CallExpr)
			if !ok {
				return true
			}

			// Проверяем вызов встроенной функции panic()
			if ident, ok := call.Fun.(*ast.Ident); ok && ident.Name == "panic" {
				pass.Reportf(call.Pos(), "использование panic() запрещено; возвращайте типизированную error")
			}

			return true
		})
	}
	return nil, nil
}

func main() {
	// Точка входа для сборки standalone CLI линтера:
	// Сборка: go build -o nopanic-lint .
	// Запуск: ./nopanic-lint ./...
	singlechecker.Main(NoPanicAnalyzer)
}
```

## Под капотом

Фреймворк `go/analysis` берет на себя оркестрацию: параллельный парсинг пакетов, построение кэша типов через `go/types`, инкрементальную проверку и экспорт фактов (`Facts`) между зависимыми пакетами. Метод `pass.Reportf` автоматически интегрируется со флагами `-json`, поддержкой автофикса (`SuggestedFixes`) и протоколом LSP в `gopls`.

## Подводные камни

1. Забытый возврат `nil, nil` из `Run`: анализатор обязан возвращать результат (или `nil`) и ошибку выполнения.
2. Ручной парсинг файлов внутри `Run`: файлы пакета уже распарсены и доступны в `pass.Files`, повторный парсинг приведет к потере производительности.
3. Паника внутри `Run`: авария в одном файле прервет проверку всех пакетов проекта.

## На собеседовании

**Вопрос с собеседования:** Что такое `analysis.Fact` во фреймворке `go/analysis`?
**Ответ:** `Fact` — это механизм межпакетного анализа (cross-package analysis). Например, если пакет `A` объявляет функцию `MustDo()`, которая внутри вызывает `panic()`, анализатор может привязать к объекту функции факт `PanicsFact`. Когда пакет `B` импортирует пакет `A` и вызывает `A.MustDo()`, анализатор пакета `B` читает экспортированный факт и обнаруживает скрытую угрозу паники, не имея исходников пакета `A`.
