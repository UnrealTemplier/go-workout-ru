# Создание собственного линтера на базе фреймворка go/analysis (запрет panic)

## Условие

**Свой собственный Линтер (База)**: Забудь про ручной парсинг для линтеров. Импортируй фреймворк `golang.org/x/tools/go/analysis`. Создай свой `Analyzer`. Напиши правило: линтер должен ругаться (вызывать `pass.Reportf`), если в коде используется функция `panic()`.

## Теория

Стандартный способ разработки линтеров современного Go:
1. `golang.org/x/tools/go/analysis`:
   - Модульность: каждый чекер оформляется как независимая переменная `*analysis.Analyzer`.
   - Тестируемость: стандартная утилита `analysistest` позволяет тестировать линтеры на тестовых пакетах с комментариями `// want "message"`.
   - Интеграция: анализатор совместим со стандартным `go vet`, `golangci-lint` и `gopls`.
2. Функция `pass.Reportf(pos token.Pos, format string, args ...any)`:
   - Регистрирует диагностическое сообщение.
   - Автоматически связывает ошибку с файлом, строкой и колонкой.
   - Поддерживает структурированный вывод в JSON.

## Решение по шагам

1. Объявите анализатор `PanicLinterAnalyzer`.
2. Реализуйте функцию `run(pass *analysis.Pass) (any, error)`.
3. Обойдите файлы `pass.Files` через `ast.Inspect`.
4. Найдите вызовы `panic()`.
5. Зарегистрируйте диагностику через `pass.Reportf`.

## Код решения

**`linter.go`**

```go
package main

import (
	"go/ast"
	"golang.org/x/tools/go/analysis"
	"golang.org/x/tools/go/analysis/singlechecker"
)

var PanicLinterAnalyzer = &analysis.Analyzer{
	Name: "nopanic",
	Doc:  "находит и запрещает использование встроенной функции panic()",
	Run:  runAnalyzer,
}

func runAnalyzer(pass *analysis.Pass) (any, error) {
	for _, file := range pass.Files {
		ast.Inspect(file, func(n ast.Node) bool {
			call, ok := n.(*ast.CallExpr)
			if !ok {
				return true
			}

			// Проверяем вызов по идентификатору
			if ident, ok := call.Fun.(*ast.Ident); ok && ident.Name == "panic" {
				// Убеждаемся, что это встроенная функция, а не локальная переменная
				if pass.TypesInfo != nil {
					if obj := pass.TypesInfo.Uses[ident]; obj != nil {
						// Если объект объявлен пользователем, пропускаем
						if obj.Pkg() != nil {
							return true
						}
					}
				}

				pass.Reportf(call.Pos(), "недопустимое использование функции panic(): замените на возврат типизированной ошибки error")
			}

			return true
		})
	}

	return nil, nil
}

func main() {
	singlechecker.Main(PanicLinterAnalyzer)
}
```

ℹ️ Полнофункциональный анализатор go/analysis с фильтрацией встроенных функций

**`Терминал`**

```bash
# Сборка анализатора:
# go build -o nopanic-checker linter.go
# 
# Запуск через go vet:
# go vet -vettool=./nopanic-checker ./...
# 
# Пример вывода:
# ./service/payment.go:88:3: недопустимое использование функции panic(): замените на возврат типизированной ошибки error
```

## Под капотом

Проверка `pass.TypesInfo.Uses[ident]` обеспечивает семантическую точность: встроенная функция `panic` принадлежит скоупу `types.Universe`, где `obj.Pkg() == nil`. Если разработчик локально объявил переменную или функцию с именем `panic` (`func panic() {}`), `obj.Pkg() != nil`, и линтер не будет выдавать ложное предупреждение.

## Подводные камни

1. Ложные срабатывания на методах структур: `obj.Panic()` имеет тип `*ast.SelectorExpr`, а не `*ast.Ident`, поэтому не будет ложно перехвачен.
2. Попытка вывода в stdout через `fmt.Println`: линтеры `go/analysis` обязаны использовать `pass.Reportf`, иначе нарушится вывод в форматах JSON и LSP.
3. Отсутствие обработки nil в `pass.TypesInfo`: если анализатор запущен без семантического контекста, `pass.TypesInfo` может быть `nil`.

## На собеседовании

**Вопрос с собеседования:** Как тестировать линтеры, написанные на базе `golang.org/x/tools/go/analysis`?
**Ответ:** С помощью стандартного пакета `analysistest.Run(t, testdataDir, MyAnalyzer, "pkg_name")`. В каталоге `testdata` создаются тестовые Go-файлы с ожидаемыми ошибками, помеченными комментариями `// want "regex pattern"`. Тестовый раннер автоматически проверяет совпадение позиций и текста ошибок.
