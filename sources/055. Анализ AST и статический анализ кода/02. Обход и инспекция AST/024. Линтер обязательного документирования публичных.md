# Линтер обязательного документирования публичных функций (Doc comments)

## Условие

Найди все экспортируемые функции (имя начинается с большой буквы). Проверь, есть ли у них узел Doc (комментарий над функцией). Если нет — выводи ошибку "Exported function must have a doc comment".

### Исходная формулировка

**[Линтер — Проверка комментариев]**: Найди все экспортируемые функции (имя начинается с большой буквы). Проверь, есть ли у них узел `Doc` (комментарий над функцией). Если нет — выводи ошибку "Exported function must have a doc comment".

## Теория

Стандартный инструмент `golint` и `revive` требуют документирования всех публичных элементов API:
1. Функция считается экспортируемой, если `ast.IsExported(fn.Name.Name) == true`.
2. Узел документации: поле `fn.Doc *ast.CommentGroup`.
3. Если функция не имеет комментария непосредственно перед объявлением, `fn.Doc` равен `nil`.
4. Правило оформления GoDoc: комментарий к функции `Foo` обязан начинаться со слова `// Foo ...`.
5. Исключения: методы тестовых файлов (`TestXxx`, `BenchmarkXxx`), встроенные функции `main` и `init`.

## Решение по шагам

1. Распарсите файл с флагом `parser.ParseComments`.
2. Обойдите верхнеуровневые функции `file.Decls`.
3. Отфильтруйте экспортируемые функции (`ast.IsExported`).
4. Проверьте `fn.Doc == nil` или отсутствие текста.
5. Выведите предупреждение с именем функции и позицией.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
	"strings"
)

const sampleCode = `package auth

// HashPassword хеширует пароль пользователя алгоритмом Argon2id.
func HashPassword(raw string) (string, error) {
	return "", nil
}

// Плохой кейс: нет комментария
func VerifyToken(token string) bool {
	return true
}

func internalHelper() {}
`

func AuditExportedDocs(src string) []string {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "auth.go", src, parser.ParseComments)
	if err != nil {
		return []string{fmt.Sprintf("Ошибка парсинга: %v", err)}
	}

	var issues []string

	for _, decl := range file.Decls {
		fn, ok := decl.(*ast.FuncDecl)
		if !ok {
			continue
		}

		name := fn.Name.Name

		// Игнорируем приватные функции, init и main
		if !ast.IsExported(name) || name == "main" || name == "init" {
			continue
		}

		pos := fset.Position(fn.Pos())

		if fn.Doc == nil || len(fn.Doc.List) == 0 {
			issues = append(issues, fmt.Sprintf(
				"%s:%d:%d: экспортируемая функция %s обязана иметь doc-комментарий",
				pos.Filename, pos.Line, pos.Column, name,
			))
			continue
		}

		// Проверка конвенции: комментарий должен начинаться с имени функции
		docText := strings.TrimSpace(fn.Doc.Text())
		if !strings.HasPrefix(docText, name+" ") && !strings.HasPrefix(docText, name+"\n") {
			issues = append(issues, fmt.Sprintf(
				"%s:%d:%d: doc-комментарий для %s должен начинаться с %q (получено: %q)",
				pos.Filename, pos.Line, pos.Column, name, "// "+name+" ...", fn.Doc.List[0].Text,
			))
		}
	}

	return issues
}

func main() {
	fmt.Println("Запуск проверки документации публичного API:")
	problems := AuditExportedDocs(sampleCode)
	for _, p := range problems {
		fmt.Printf("⚠️  %s\n", p)
	}
}
```

## Под капотом

Метод `fn.Doc.Text()` автоматически нормализует комментарии: он удаляет символы `//`, убирает маркеры `/*` и `*/`, выравнивает отступы и объединяет строки в единый связный текст. Это избавляет разработчика линтера от ручной очистки регулярными выражениями.

## Подводные камни

1. Забытый флаг `parser.ParseComments`: `fn.Doc` всегда будет `nil`.
2. Комментарий, отделенный пустой строкой: если между комментарием и `func` есть пустая строка `\n\n`, парсер считает комментарий свободным (free comment), и `fn.Doc` останется равным `nil`!
3. Ложные срабатывания на методах с неэкспортированным типом получателя: `func (s service) PublicMethod()` не экспортируется за пределы пакета.

## На собеседовании

**Вопрос с собеседования:** Почему GoDoc требует, чтобы комментарий начинался строго с имени функции (`// FuncName ...`)?
**Ответ:** Для удобства автогенерации документации (`godoc`, `pkg.go.dev`) и текстового поиска (grep). Первая строка комментария используется как краткое резюме (summary) функции в оглавлении пакета. Конвенция `// Name ...` формирует грамматически корректное предложение английского/русского языка при отображении в веб-интерфейсе документации.
