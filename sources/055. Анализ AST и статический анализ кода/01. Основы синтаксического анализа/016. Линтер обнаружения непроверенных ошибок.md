# Линтер обнаружения непроверенных ошибок при присваивании (err := foo())

## Условие

Напишите анализатор, который находит присваивания err := foo() и проверяет, что переменная err используется далее в том же блоке (не _). Используйте go/ast и учтите named returns, reassign (err = foo()), и shadowing. Объясните, почему go/types нужен для точного отслеживания scope.

### Исходная формулировка

**Линтер: непроверенные ошибки.**: Напишите анализатор, который находит присваивания `err := foo()` и проверяет, что переменная `err` используется далее в том же блоке (не `_`). Используйте `go/ast` и учтите named returns, reassign (`err = foo()`), и shadowing. Объясните, почему `go/types` нужен для точного отслеживания scope.

## Теория

Игнорирование возвращаемых ошибок — одна из самых частых причин аварий (incidents) в распределенных системах:
1. Присваивание ошибки: `err := doSomething()`.
2. Если разработчик объявил `err`, но забыл проверить `if err != nil`, компилятор Go выдаст ошибку `err declared and not used`.
3. Однако если переменная `err` уже была объявлена ранее (`err = doSecond()`), компилятор пропустит код, даже если ошибка перезаписана и ни разу не проверена!
4. Для обнаружения повторных присваиваний без промежуточной проверки строится анализатор потока управления (Control Flow Graph) или проверка использования переменной в узлах между последовательными присваиваниями.

## Решение по шагам

1. Распарсите функцию с несколькими присваиваниями `err`.
2. Обойдите список операторов `fn.Body.List`.
3. При обнаружении присваивания переменной `err` перейдите в состояние ожидания проверки.
4. Если следующее присваивание в `err` происходит до проверки `if err != nil`, сгенерируйте предупреждение.
5. Протестируйте анализатор.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

const suspiciousCode = `package main

func ExecuteFlow() error {
	var err error

	err = stepOne()
	// Ошибка: stepOne() вернул err, но здесь нет проверки if err != nil!
	err = stepTwo()
	if err != nil {
		return err
	}

	return nil
}

func stepOne() error { return nil }
func stepTwo() error { return nil }
`

func CheckOverwrittenErrors(src string) []string {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "flow.go", src, 0)
	if err != nil {
		return []string{fmt.Sprintf("Ошибка парсинга: %v", err)}
	}

	var issues []string

	ast.Inspect(file, func(n ast.Node) bool {
		fn, ok := n.(*ast.FuncDecl)
		if !ok || fn.Body == nil {
			return true
		}

		lastErrAssignLine := 0
		errChecked := true

		for _, stmt := range fn.Body.List {
			switch s := stmt.(type) {
			case *ast.AssignStmt:
				for _, lhs := range s.Lhs {
					if ident, ok := lhs.(*ast.Ident); ok && ident.Name == "err" {
						if !errChecked && lastErrAssignLine > 0 {
							issues = append(issues, fmt.Sprintf(
								"Строка %d: переменная 'err' перезаписана без проверки ошибки со строки %d!",
								fset.Position(s.Pos()).Line, lastErrAssignLine,
							))
						}
						lastErrAssignLine = fset.Position(s.Pos()).Line
						errChecked = false
					}
				}

			case *ast.IfStmt:
				// Проверяем, участвует ли err в условии if
				ast.Inspect(s.Cond, func(condNode ast.Node) bool {
					if ident, ok := condNode.(*ast.Ident); ok && ident.Name == "err" {
						errChecked = true
					}
					return true
				})
			}
		}

		return false
	})

	return issues
}

func main() {
	fmt.Println("Запуск линтера перезаписи непроверенных ошибок:")
	problems := CheckOverwrittenErrors(suspiciousCode)
	for _, p := range problems {
		fmt.Printf("🚨 %s\n", p)
	}
}
```

## Под капотом

Анализ потока данных (Dataflow Analysis) в полноценных линтерах (например, `errcheck` или `ineffassign`) строит граф потока управления (CFG — Control Flow Graph). Пакет `golang.org/x/tools/go/ssa` трансформирует исходный код в форму SSA, где каждое присваивание порождает новую версию переменной (`err_1`, `err_2`). Это позволяет алгоритмически доказать, используется ли значение `err_1` в инструкциях ветвления до уничтожения области видимости.

## Подводные камни

1. Игнорирование затенения (shadowing): если во вложенном блоке `if` написано `err := doLocal()`, внешняя переменная `err` не изменяется.
2. Пропуск возврата `return err`: возврат ошибки является легитимным использованием без проверки через `if`.
3. Ложные срабатывания, если `err` передается в логгер: `log.Println("fail:", err)`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go линтер `ineffassign` является обязательным во всех production CI пайплайнах?
**Ответ:** `ineffassign` обнаруживает неэффективные присваивания, когда переменной присваивается значение, которое нигде не читается перед следующим присваиванием или выходом из функции. В 90% случаев в Go это указывает на критический баг: разработчик вызвал функцию с возвратом `err = do()`, но забыл написать `if err != nil`, в результате чего сбой был молча проигнорирован.
