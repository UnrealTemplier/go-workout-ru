# Сравнительный анализ структур узлов AST: GenDecl, FuncDecl, TypeSpec

## Условие

Выведите AST через ast.Print() и изучите структуру (GenDecl, FuncDecl, TypeSpec и т.д.).

### Исходная формулировка

**ast.Print**: Выведите AST через `ast.Print()` и изучите структуру (GenDecl, FuncDecl, TypeSpec и т.д.).

## Теория

Для эффективной разработки линтеров необходимо четко понимать взаимосвязь трех фундаментальных типов объявлений в Go AST:
1. `*ast.GenDecl` (General Declaration): контейнер верхнего уровня для `import`, `const`, `type` или `var`.
   - Поле `Tok token.Token`: определяет категорию (например `token.TYPE` или `token.CONST`).
   - Поле `Specs []ast.Spec`: список спецификаций (например, блок `type (...)` или `const (...)`).
2. `*ast.TypeSpec`: элемент внутри `GenDecl` при `Tok == token.TYPE`.
   - `Name *ast.Ident`: имя объявляемого типа.
   - `Type ast.Expr`: тело типа (структура, интерфейс, срез, базовый тип).
3. `*ast.FuncDecl`: объявление функции или метода. Не является `GenDecl`, а является самостоятельным типом `ast.Decl`.
   - Содержит `Recv` (получатель), `Name` (имя), `Type` (сигнатуру) и `Body` (тело).

## Решение по шагам

1. Напишите компактный код, включающий константу, структуру, интерфейс и метод.
2. Распарсите его в AST.
3. Напишите классификатор узлов, сопоставляющий `GenDecl` и его спецификации.
4. Выведите подробный отчет об иерархии типов узлов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

const demoSource = `package catalog

const DefaultTaxRate = 0.20

type Product struct {
	SKU   string
	Price float64
}

type PriceCalculator interface {
	CalculateTotal(p Product) float64
}

func (p Product) DisplayName() string {
	return "SKU: " + p.SKU
}
`

func main() {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "catalog.go", demoSource, 0)
	if err != nil {
		panic(err)
	}

	fmt.Println("Инспекция типов объявлений (Decls) верхнего уровня:")
	for i, decl := range file.Decls {
		switch d := decl.(type) {
		case *ast.GenDecl:
			fmt.Printf("[%d] *ast.GenDecl | Ключевое слово (Tok): %-6s | Элементов (Specs): %d\n",
				i+1, d.Tok, len(d.Specs))
			for j, spec := range d.Specs {
				switch s := spec.(type) {
				case *ast.ValueSpec:
					fmt.Printf("      (%d) *ast.ValueSpec -> Имя: %s\n", j+1, s.Names[0].Name)
				case *ast.TypeSpec:
					fmt.Printf("      (%d) *ast.TypeSpec  -> Имя: %-15s | Тело типа: %T\n",
						j+1, s.Name.Name, s.Type)
				}
			}
		case *ast.FuncDecl:
			isMethod := d.Recv != nil
			fmt.Printf("[%d] *ast.FuncDecl| Имя: %-18s | Является методом: %v\n",
				i+1, d.Name.Name, isMethod)
		}
	}
}
```

## Под капотом

Грамматика Go объединяет `import`, `const`, `var` и `type` в общую категорию `General Declaration` (`GenDecl`), поскольку все они поддерживают группировку круглыми скобками: `const (...)`, `var (...)`, `type (...)`. Функции не могут быть сгруппированы в скобки, поэтому они имеют собственный выделенный узел грамматики `FuncDecl`.

## Подводные камни

1. Ошибочный поиск интерфейсов через `*ast.GenDecl`: сам `GenDecl` не говорит, что объявляется интерфейс, необходимо анализировать вложенный `ts.Type.(*ast.InterfaceType)`.
2. Путаница между `*ast.ValueSpec` для констант и переменных: токен `d.Tok` определяет, `const` это или `var`.
3. Блоки объявлений с несколькими элементами: `len(d.Specs)` может быть больше 1 при `type ( A struct{}; B struct{} )`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go AST функции не входят в состав `ast.GenDecl`?
**Ответ:** `GenDecl` предназначен для синтаксических конструкций с общим синтаксисом спецификаций (`Specs`), допускающих блочную форму объявления через круглые скобки `( ... )`. Функции имеют принципиально иной синтаксис: сигнатуру с параметрами, опциональный receiver, возвращаемые значения и исполняемый блок тела `Body (*ast.BlockStmt)`.
