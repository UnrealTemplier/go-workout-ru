# Линтер обнаружения проигнорированных возвращаемых ошибок (Unhandled Errors)

## Условие

Напишите кастомный статический анализатор (линтер). Линтер должен сканировать AST-дерево файла и искать вызовы функций, которые возвращают тип error, но вызывающий код полностью игнорирует этот возврат (например, не присваивает результат переменной или присваивает его пустому идентификатору _ без последующей проверки на nil). Выводите предупреждения с указанием имени файла и номера строки (используя token.FileSet).

### Исходная формулировка

**Линтер: Обнаружение проигнорированных ошибок**: Напишите кастомный статический анализатор (линтер). Линтер должен сканировать AST-дерево файла и искать вызовы функций, которые возвращают тип `error`, но вызывающий код полностью игнорирует этот возврат (например, не присваивает результат переменной или присваивает его пустому идентификатору `_` без последующей проверки на `nil`). Выводите предупреждения с указанием имени файла и номера строки (используя `token.FileSet`).

## Теория

Игнорирование возвращаемого значения вызова функции в Go проявляется в двух синтаксических формах:
1. Вызов как самостоятельное выражение-оператор `*ast.ExprStmt`:
   `res := fn()` — присваивание, а просто `fn()` — `ExprStmt`. Если `fn` возвращает `error`, этот возврат полностью проигнорирован.
2. Присваивание пустому идентификатору:
   `_ = fn()` или `_, _ = fn()`.
Для выявления таких дефектов:
- На синтаксическом уровне инспектируются узлы `*ast.ExprStmt` с `X.(*ast.CallExpr)`.
- Для точного определения, возвращает ли функция `error`, в полноценных линтерах применяется `go/types`.
- На уровне эвристики AST можно проверять вызовы известных функций (`os.Remove`, `file.Close`, `json.Unmarshal`), возврат которых обязан обрабатываться.

## Решение по шагам

1. Распарсите Go-код с одиночными вызовами функций `file.Close()`, `os.Remove()`.
2. Найдите в AST узлы `*ast.ExprStmt`.
3. Извлеките `call := exprStmt.X.(*ast.CallExpr)`.
4. Определите вызываемую функцию (`Close`, `Remove`, `Unmarshal`).
5. Выведите предупреждение о необработанной ошибке.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

const suspiciousCode = `package storage

import (
	"encoding/json"
	"os"
)

func CleanupData(path string, data []byte) {
	file, _ := os.Open(path)
	
	// Ошибка 1: Close возвращает error, но вызов оставлен как ExprStmt
	file.Close()

	// Ошибка 2: os.Remove возвращает error, но возврат проигнорирован
	os.Remove(path)

	// Ошибка 3: явный сброс в пустой идентификатор _
	var target map[string]any
	_ = json.Unmarshal(data, &target)
}
`

// Список критических функций, возврат error которых нельзя игнорировать
var errorReturningMethods = map[string]bool{
	"Close":     true,
	"Remove":    true,
	"Unmarshal": true,
	"Write":     true,
	"Sync":      true,
}

func AuditIgnoredErrors(src string) []string {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "storage.go", src, 0)
	if err != nil {
		return []string{fmt.Sprintf("Ошибка парсинга: %v", err)}
	}

	var issues []string

	ast.Inspect(file, func(n ast.Node) bool {
		switch stmt := n.(type) {
		case *ast.ExprStmt:
			// Одиночный вызов функции без присваивания
			if call, ok := stmt.X.(*ast.CallExpr); ok {
				fnName := getCallTargetName(call)
				if errorReturningMethods[fnName] {
					pos := fset.Position(call.Pos())
					issues = append(issues, fmt.Sprintf(
						"%s:%d:%d: вызов %s() возвращает error, но результат полностью проигнорирован!",
						pos.Filename, pos.Line, pos.Column, fnName,
					))
				}
			}

		case *ast.AssignStmt:
			// Присваивание в пустой идентификатор: _ = call()
			if len(stmt.Lhs) == 1 {
				if ident, ok := stmt.Lhs[0].(*ast.Ident); ok && ident.Name == "_" {
					if call, ok := stmt.Rhs[0].(*ast.CallExpr); ok {
						fnName := getCallTargetName(call)
						if errorReturningMethods[fnName] {
							pos := fset.Position(call.Pos())
							issues = append(issues, fmt.Sprintf(
								"%s:%d:%d: результат вызова %s() сброшен в пустой идентификатор '_' без обработки!",
								pos.Filename, pos.Line, pos.Column, fnName,
							))
						}
					}
				}
			}
		}

		return true
	})

	return issues
}

func getCallTargetName(call *ast.CallExpr) string {
	switch fn := call.Fun.(type) {
	case *ast.Ident:
		return fn.Name
	case *ast.SelectorExpr:
		return fn.Sel.Name
	}
	return ""
}

func main() {
	fmt.Println("Запуск анализатора необработанных ошибок:")
	problems := AuditIgnoredErrors(suspiciousCode)
	for _, p := range problems {
		fmt.Printf("⚠️  %s\n", p)
	}
}
```

## Под капотом

В компиляторе Go любое выражение, стоящее как отдельная строка без сохранения результата (`x()`), заворачивается парсером в узел инструкции выражения `*ast.ExprStmt { X: ast.Expr }`. Популярный инструмент `errcheck` использует `go/types` для проверки сигнатуры функции: если последний возвращаемый тип реализует встроенный интерфейс `error`, нахождение вызова внутри `ExprStmt` генерирует диагностику.

## Подводные камни

1. Ложные срабатывания на методах, не возвращающих ошибки: без `go/types` простая проверка по имени `Close` выдаст ошибку на кастомном объекте, у которого метод `Close()` ничего не возвращает.
2. Исключение для `defer file.Close()`: в defer вызовы оборачиваются в `*ast.DeferStmt`, а не `*ast.ExprStmt`, поэтому их нужно анализировать отдельно.
3. Множественные присваивания: конструкция `val, _ = get()` требует проверки всех элементов `Lhs` и `Rhs`.

## На собеседовании

**Вопрос с собеседования:** Почему в production коде часто запрещают даже явное игнорирование ошибки через `_ = json.Unmarshal(...)`?
**Ответ:** Конструкция `_ = err` часто маскирует опасные предположения разработчика. Если JSON придет поврежденным, неполным или изменит схему, десериализация завершится ошибкой, а структура останется в частично инициализированном состоянии. Последующий доступ к неинициализированным полям или указателям приведет к панике nil pointer dereference глубоко в бизнес-логике.
