# Учебный деплой по SSH: автоматизация запуска через docker compose на удаленном сервере

## Условие

**Simple CD (Deploy via SSH)**: *Учебный деплой.* Добавь шаг, который с помощью SSH-ключа логинится на твой удаленный сервер (VPS), делает `docker pull` нового образа, останавливает старый контейнер и запускает новый.

## Теория

Для простых учебных проектов, пет-проектов и небольших сервисов развертывание полноценного кластера Kubernetes часто избыточно. В таких сценариях применяется классический деплой по SSH на выделенный VPS/VDS сервер.

Безопасная архитектура деплоя по SSH:
1. Выделенный приватный SSH-ключ (`SSH_PRIVATE_KEY`) добавляется в GitHub Secrets.
2. На сервере создается отдельный непривилегированный пользователь `deployer`, входящий в группу `docker`.
3. В CI-пайплайне запускается SSH-агент (`webfactory/ssh-agent` или нативная команда `ssh`).
4. По SSH на сервер передается обновленный файл `docker-compose.yml`, после чего выполняется команда:
   `docker compose pull && docker compose up -d --remove-orphans`.

## Решение по шагам

1. Сгенерируйте пару SSH-ключей: `ssh-keygen -t ed25519 -C "ci-deploy"`.
2. Добавьте публичный ключ на сервер в `~/.ssh/authorized_keys`, а приватный — в GitHub Secrets `SSH_KEY`.
3. Добавьте адрес сервера в секрет `SERVER_HOST` и пользователя в `SERVER_USER`.
4. Настройте workflow с шагами: настройка SSH, копирование конфига через `scp`, выполнение `docker compose up -d` через `ssh`.
5. Проверьте запуск контейнера на удаленном сервере.

## Код решения

**`.github/workflows/ssh-deploy.yml`**

```yaml
name: Simple SSH Deploy

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    name: Deploy to Remote VPS
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup SSH Agent
        uses: webfactory/ssh-agent@v0.9.0
        with:
          ssh-private-key: ${{ secrets.SSH_KEY }}

      - name: Add Known Hosts
        run: |
          mkdir -p ~/.ssh
          ssh-keyscan -H ${{ secrets.SERVER_HOST }} >> ~/.ssh/known_hosts

      - name: Copy Compose Config to Server
        run: |
          scp docker-compose.prod.yml ${{ secrets.SERVER_USER }}@${{ secrets.SERVER_HOST }}:/opt/app/docker-compose.yml

      - name: Pull and Restart Application
        run: |
          ssh ${{ secrets.SERVER_USER }}@${{ secrets.SERVER_HOST }} "cd /opt/app && docker compose pull && docker compose up -d --remove-orphans" 
```

**`docker-compose.prod.yml`**

```yaml
services:
  web:
    image: ghcr.io/company/web-app:latest
    restart: always
    ports:
      - "80:8080"
    environment:
      - APP_ENV=production
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte("Привет из продакшна, развернутого по SSH!"))
	})

	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	fmt.Printf("Сервер запущен на :%s\n", port)
	_ = http.ListenAndServe(":"+port, nil)
}
```

## Под капотом

Экшен `webfactory/ssh-agent` запускает процесс `ssh-agent` в памяти раннера и регистрирует приватный ключ через `ssh-add`. 

Команда `ssh-keyscan` опрашивает открытый публичный ключ хоста сервера и заносит его отпечаток (fingerprint) в `~/.ssh/known_hosts`, предотвращая блокировку SSH-клиента диалоговым запросом `Are you sure you want to continue connecting (yes/no)?`.

## Подводные камни

1. Использование root-пользователя для SSH-деплоя: уязвимость в скрипте CI может привести к полному удалению ОС сервера (`rm -rf /`).
2. Отсутствие `known_hosts`: использование флага `-o StrictHostKeyChecking=no` делает пайплайн уязвимым для MITM-перехвата SSH-сессии.
3. Простой приложения (Downtime) при перезапуске `docker compose up -d`: без обратного прокси (Nginx/Traefik) происходит кратковременный сброс соединений.

## На собеседовании

**Вопрос с собеседования:** Почему в production BigTech инфраструктуре категорически запрещен деплой по прямому SSH из CI-пайплайна?
**Ответ:** 
1. **Пробивание сетевого периметра:** Прямой SSH требует открытия 22 порта наружу в публичный интернет или создания туннелей, что запрещено политиками информационной безопасности (Zero Trust).
2. **Отсутствие аудита и масштабируемости:** SSH не масштабируется на парк из 10 000 серверов; сбой на одном хосте оставляет систему в неконсистентном состоянии.
3. **Хранение долгоживущих SSH-ключей в CI:** Утечка ключа дает злоумышленнику доступ к интерактивной shell-сессии на сервере. Вместо SSH используются декларативные контроллеры (K8s/Nomad/GitOps).
