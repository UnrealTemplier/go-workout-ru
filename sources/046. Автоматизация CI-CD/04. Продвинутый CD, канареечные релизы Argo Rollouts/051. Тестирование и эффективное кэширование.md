# Тестирование и эффективное кэширование Go-зависимостей в CI

## Условие

**Тестирование и кэширование зависимостей**: Добавьте в ваш пайплайн CI шаг автоматического запуска тестов `go test -v ./...` [471]. Чтобы не скачивать заново все внешние библиотеки при каждом запуске CI (что сильно замедляет сборку), настройте кэширование папок `~/.cache/go-build` и `~/go/pkg/mod` в вашем CI-пайплайне [471].

## Теория

Запуск тестов — центральный этап проверки бизнес-логики. Для ускорения времени выполнения пайплайна критично кэшировать скачанные модули Go.

Эволюция кэширования в GitHub Actions:
- Ранее использовался экшен `actions/cache` с ручным указанием путей `~/go/pkg/mod` и ключей хешей `go.sum`.
- В современном `actions/setup-go@v5` кэширование встроено из коробки: параметр `cache: true` (включен по умолчанию) автоматически кэширует как зависимости (`go mod`), так и кэш сборщика Go (`go build cache`).

Тестирование с флагами `-race` и `-cover` обеспечивает одновременный контроль корректности многопоточности и полноты покрытия кодовой базы.

## Решение по шагам

1. Включите автоматический кэш в `actions/setup-go@v5` через `cache: true`.
2. Настройте команду запуска тестов: `go test -v -race -cover ./...`.
3. Убедитесь, что при повторном запуске пайплайна в логах появляется сообщение `Cache restored successfully`.
4. Сравните время выполнения холодного и теплого прогона.

## Код решения

**`.github/workflows/test-cache.yml`**

```yaml
name: Tests with Caching

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    name: Run Unit Tests
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Go with Built-in Cache
        uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true
          cache-dependency-path: go.sum

      - name: Run Tests
        run: go test -v -race -cover ./...
```

**`string_utils.go`**

```go
package main

import "strings"

// Reverse переворачивает строку с учетом Unicode рун.
func Reverse(s string) string {
	runes := []rune(s)
	for i, j := 0, len(runes)-1; i < j; i, j = i+1, j-1 {
		runes[i], runes[j] = runes[j], runes[i]
	}
	return string(runes)
}

func main() {
	println(Reverse("Привет, Go!"))
}
```

**`string_utils_test.go`**

```go
package main

import "testing"

func TestReverse(t *testing.T) {
	cases := []struct {
		in, want string
	}{
		{"Hello", "olleH"},
		{"Мир", "риМ"},
		{"", ""},
	}
	for _, c := range cases {
		got := Reverse(c.in)
		if got != c.want {
			t.Errorf("Reverse(%q) == %q, want %q", c.in, got, c.want)
		}
	}
}
```

## Под капотом

`actions/setup-go` при завершении джобы вычисляет SHA-256 хеш от файла `go.sum` и упаковывает директории:
- `~/go/pkg/mod` (исходные тексты скачанных зависимостей)
- `~/.cache/go-build` (скомпилированные объектные `.a` архивы пакетов)
в архив tar.zst и выгружает в GitHub Cache Storage. При следующем запуске с тем же `go.sum` этот архив восстанавливается за 1-2 секунды, исключая сетевые запросы к `proxy.golang.org`.

## Подводные камни

1. Забытый файл `go.sum`: если `go.sum` не закоммичен в репозиторий, ключ кэша не может быть детерминирован, и кэш будет пересоздаваться на каждый коммит.
2. Ручное удаление модулей в пайплайне: выполнение команд вроде `go clean -modcache` сводит на нет работу кэша.
3. Кэширование папки `vendor`: если проект использует vendoring (`go mod vendor`), кэшировать `~/go/pkg/mod` не имеет смысла, так как зависимости уже лежат в Git.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `GOCACHE` (кэш сборщика) и `GOPATH/pkg/mod` (кэш модулей) в Go?
**Ответ:** 
- **`GOPATH/pkg/mod`** содержит скачанные из интернета неизменяемые архивы и исходные коды сторонних библиотек.
- **`GOCACHE`** содержит скомпилированные машинные объектные файлы (`.a`), результаты работы компилятора и линковщика, а также кэшированные результаты успешных тестов (`go test` выводит `(cached)`). 
Кэширование обоих каталогов в CI дает максимальный прирост скорости.
