# Настройка Branch Protection Rules: обязательные Status Checks и код-ревью

## Условие

**Branch Protection**: Настрой репозиторий (в UI GitHub/GitLab). Запрети прямой пуш в ветку `main`. Обяжи делать Pull Requests, и поставь галочку: "Слить код можно только если CI-пайплайн (линтер и тесты) пройден успешно".

---

## Теория

Защита главной ветки (`main`/`master`) — фундаментальное правило разработки в любой IT-компании. Прямой коммит или push в `main` («Push to master») категорически блокируется на уровне настроек репозитория.

Ключевые политики **Branch Protection Rules (GitHub / GitLab)**:
1. **Require a pull request before merging:** Весь код поступает в `main` исключительно через Pull Request / Merge Request.
2. **Require approvals:** Обязательное подтверждение PR минимум одним или двумя коллегами (Peer Code Review).
3. **Require status checks to pass before merging:** Слияние заблокировано, пока не завершатся зеленым все критические джобы CI:
   - `test` (юнит-тесты и детектор гонок),
   - `golangci-lint` (статический анализ),
   - `security-scan` (поиск уязвимостей).
4. **Require branches to be up to date before merging:** Гарантирует, что PR протестирован на актуальной версии ветки `main`.

## Решение по шагам

1. В репозитории GitHub перейдите в Settings -> Branches -> Add branch protection rule.
2. В поле Branch name pattern укажите `main`.
3. Отметьте чекбокс `Require a pull request before merging` (минимум 1 approval).
4. Отметьте `Require status checks to pass before merging`.
5. В строке поиска найдите точные имена джобов вашего workflow (например, `test`, `lint`).
6. Включите `Do not allow bypassing the above settings` (применять правила даже к администраторам).

## Код решения

**`.github/workflows/mandatory-checks.yml`**

```yaml
name: Mandatory Branch Protection Checks

on:
  pull_request:
    branches: [ main ]

jobs:
  lint:
    name: Mandatory Linter
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
      - name: Run golangci-lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: v1.64.5

  test:
    name: Mandatory Unit Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
      - name: Run Tests with Race Detector
        run: go test -v -race -cover ./...
```

**`service.go`**

```go
package main

import (
	"errors"
	"fmt"
)

// CalculateDiscount вычисляет размер скидки для клиента.
func CalculateDiscount(total float64, isVIP bool) (float64, error) {
	if total < 0 {
		return 0, errors.New("сумма не может быть отрицательной")
	}
	if isVIP {
		return total * 0.20, nil
	}
	return total * 0.05, nil
}

func main() {
	discount, _ := CalculateDiscount(1000, true)
	fmt.Printf("Размер скидки: %.2f руб.\n", discount)
}
```

**`service_test.go`**

```go
package main

import "testing"

func TestCalculateDiscount(t *testing.T) {
	d, err := CalculateDiscount(100, true)
	if err != nil {
		t.Fatalf("Ошибка: %v", err)
	}
	if d != 20.0 {
		t.Fatalf("Ожидалось 20.0, получено %.2f", d)
	}
}
```

## Под капотом

Когда PR создается, GitHub связывает коммит PR с объектом Commit Status API (`POST /repos/:owner/:repo/statuses/:sha`). 

Каждая джоба GitHub Actions отправляет обновления статуса: `state: pending`, затем `state: success` или `state: failure`. 

Кнопка «Merge pull request» в веб-интерфейсе GitHub программно заблокирована на уровне API, пока все контексты статусов, зарегистрированные в правилах Branch Protection, не перейдут в статус `success`.

## Подводные камни

1. Несовпадение имен статусов: если переименовать `name:` у джобы в YAML-файле, GitHub будет бесконечно ждать статуса со старым именем, блокируя слияние PR.
2. Исключение администраторов из правил: лид команды в спешке может случайно запушить ломающий коммит напрямую в `main`.
3. Отсутствие `Dismiss stale pull request approvals when new commits are pushed`: если автор запушит новые изменения после получения аппрува, они попадут в `main` без повторного ревью.

## На собеседовании

**Вопрос с собеседования:** Что такое «Merge Queue» (Очередь слияния) в GitHub и какую проблему она решает в высоконагруженных монорепозиториях?
**Ответ:** Когда сотни разработчиков одновременно мерджат PR в `main`, возникает проблема: PR A и PR B по отдельности проходят все тесты на своей ветке, но при одновременном слиянии их изменения конфликтуют на уровне бизнес-логики, ломая `main`. 
Merge Queue автоматически выстраивает одобренные PR в очередь, применяет их последовательно на временной ветке, прогоняет тесты для каждого объединенного состояния и только при успехе сливает в `main`. Если чей-то PR ломает билд, он автоматически выбрасывается из очереди без остановки работы остальных коллег.
