# GitOps триггер: автоматическое обновление манифестов в конфигурационном репозитории

## Условие

**[GitOps trigger]**: После успешного пуша образа в registry, пайплайн должен клонировать отдельный репозиторий с Kubernetes-манифестами (Infrastructure Repo), заменить в нем тег образа на новый, сделать коммит и запушить. (Это триггер для ArgoCD).

## Теория

В зрелой архитектуре микросервисов репозитории разделены на два типа:
1. **Application Repository (App Repo):** Содержит исходный код Go, юнит-тесты и Dockerfile.
2. **Configuration Repository (GitOps/Infra Repo):** Содержит манифесты K8s, Helm-чарты или Kustomize overlays для всех окружений (`dev`, `stage`, `prod`).

Пайплайн в App Repo при успешной публикации OCI-образа:
- Клонирует GitOps-репозиторий по SSH-ключу или GitHub App токену.
- Использует утилиту `kustomize edit set image` или `yq` для обновления тега образа.
- Создает коммит `chore: update image to sha-XXXXX` и пушит в GitOps-репозиторий.
- ArgoCD/Flux замечает коммит в GitOps-репозитории и синхронизирует кластер.

## Решение по шагам

1. Создайте deploy key или Personal Access Token с правами записи в GitOps-репозиторий.
2. В пайплайне App Repo после сборки добавьте шаг клонирования `config-repo`.
3. Установите `kustomize`.
4. Обновите тег образа: `kustomize edit set image api-service=ghcr.io/org/app:${{ github.sha }}`.
5. Закоммитьте и запушите изменение от имени бота `ci-bot`.

## Код решения

**`.github/workflows/gitops-trigger.yml`**

```yaml
name: Update GitOps Repository

on:
  push:
    branches: [ main ]

jobs:
  publish-and-notify-gitops:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Build and Push Docker Image
        run: |
          echo "Building and pushing ghcr.io/company/auth-service:${{ github.sha }}..."

      - name: Checkout GitOps Infrastructure Repo
        uses: actions/checkout@v4
        with:
          repository: company/gitops-manifests
          token: ${{ secrets.GITOPS_REPO_PAT }}
          path: gitops-manifests

      - name: Update Image Tag via Kustomize
        run: |
          cd gitops-manifests/apps/auth-service/overlays/production
          curl -s "https://raw.githubusercontent.com/kubernetes-sigs/kustomize/master/hack/install_kustomize.sh" | bash
          ./kustomize edit set image auth-service=ghcr.io/company/auth-service:${{ github.sha }}

      - name: Commit and Push Changes to GitOps
        run: |
          cd gitops-manifests
          git config user.name "gitops-bot"
          git config user.email "gitops-bot@company.com"
          git add .
          git commit -m "chore(release): update auth-service to commit ${{ github.sha }}"
          git push origin main
```

**`kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
images:
  - name: auth-service
    newName: ghcr.io/company/auth-service
    newTag: a1b2c3d4e5
```

## Под капотом

`kustomize edit set image` не просто перезаписывает строку regex-заменой, а безопасно парсит AST YAML-файла `kustomization.yaml` и обновляет поля `newName` и `newTag`. 

Это исключает повреждение структуры файла или форматирования комментариев. При пуше коммита в GitOps-репозиторий ArgoCD считывает обновленный тег через вебхук и запускает накатку изменений в Kubernetes.

## Подводные камни

1. Использование команды `sed -i` для правки YAML: случайное изменение других полей или повреждение отступов ломает манифест. Всегда используйте `kustomize` или `yq`.
2. Конфликты одновременных коммитов: если 5 микросервисов параллельно обновляют один GitOps-репозиторий, `git push` упадет с конфликтом. Требуется `git pull --rebase` перед коммитом или разнесение сервисов по разным репозиториям.
3. Отсутствие защиты от коммитов с упавшими сборками: шаг обновления GitOps должен строго зависеть от успешного завершения всех тестов.

## На собеседовании

**Вопрос с собеседования:** Почему монорепозиторий конфигураций для GitOps часто разделяют по веткам или каталогам для разных сред (Dev/Stage/Prod)?
**Ответ:** Разделение по веткам (`branch-per-environment`) считается антипаттерном в GitOps из-за конфликтов слияния при мердже веток между средами. 
Лучшая мировая практика — **разграничение по каталогам (Directory/Overlay-per-environment)** в рамках единой ветки `main`: `apps/auth/overlays/dev`, `apps/auth/overlays/prod`. Это позволяет использовать Kustomize для наследования базовых манифестов и изолированно управлять конфигурациями контуров без риска случайного перезатирания настроек при Git Merge.
