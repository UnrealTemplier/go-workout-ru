# Platform Engineering: Self-Service портал разработчика (IDP) и автоматизация через PR

## Условие

**Platform Engineering**: internal developer platform (IDP). Self-service: `kubectl apply` → Git PR → automated pipeline. Golden paths, paved roads. Developers focus on code, platform team on infrastructure.

## Теория

С ростом штата инженеров традиционная модель взаимодействия «Разработчик ставит тикет в Jira системным администраторам/DevOps на создание базы данных или развертывание сервиса» становится главным узким местом компании.

**Platform Engineering** создает внутреннюю платформу разработки (**Internal Developer Platform — IDP**, например Spotify Backstage):
- **Self-Service:** Разработчик через веб-портал или шаблонный репозиторий за 2 клика заказывает новый микросервис со всем окружением.
- **GitOps Automation:** Платформа автоматически создает Git-репозиторий с кодом на Go, генерирует Helm-чарты, пайплайны CI/CD и создает Pull Request в репозиторий инфраструктуры.
- **Golden Paths (Золотые пути):** Стандартизированные шаблоны сервисов со встроенным логированием, трейсингом, метриками и безопасностью.

## Решение по шагам

1. Разработайте шаблон микросервиса на Go с преднастроенными Dockerfile, Makefile и CI-пайплайнами.
2. Создайте GitHub Action или скрипт автоматизации, генерирующий манифесты инфраструктуры при создании нового сервиса.
3. Настройте генерацию K8s Namespace, ResourceQuota и Deployment.
4. Создайте автоматический Pull Request в GitOps-репозиторий кластера.
5. Продемонстрируйте сценарий Self-Service создания сервиса.

## Код решения

**`template/scaffold.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"text/template"
)

type ServiceMetadata struct {
	ServiceName string
	OwnerTeam   string
	Port        int
}

const k8sTemplate = `apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .ServiceName }}
  labels:
    app.kubernetes.io/name: {{ .ServiceName }}
    team: {{ .OwnerTeam }}
spec:
  replicas: 2
  selector:
    matchLabels:
      app: {{ .ServiceName }}
  template:
    metadata:
      labels:
        app: {{ .ServiceName }}
    spec:
      containers:
        - name: app
          image: ghcr.io/company/{{ .ServiceName }}:latest
          ports:
            - containerPort: {{ .Port }}
`

func GenerateManifest(meta ServiceMetadata) (string, error) {
	tmpl, err := template.New("manifest").Parse(k8sTemplate)
	if err != nil {
		return "", err
	}
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, meta); err != nil {
		return "", err
	}
	return buf.String(), nil
}

func main() {
	meta := ServiceMetadata{
		ServiceName: "loyalty-api",
		OwnerTeam:   "marketing-tech",
		Port:        8080,
	}
	manifest, err := GenerateManifest(meta)
	if err != nil {
		panic(err)
	}
	fmt.Println("Сгенерированный платформенный манифест:")
	fmt.Println(manifest)
}
```

**`.github/workflows/idp-scaffold.yml`**

```yaml
name: Platform Self-Service Provisioner

on:
  workflow_dispatch:
    inputs:
      service_name:
        description: 'Имя нового микросервиса'
        required: true
        default: 'order-processor'
      team:
        description: 'Команда владелец'
        required: true
        default: 'core-backend'

jobs:
  scaffold:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Scaffold Platform Manifests
        run: |
          echo "Создание инфраструктурных манифестов для ${{ github.event.inputs.service_name }}..."
          mkdir -p output/${{ github.event.inputs.service_name }}

      - name: Create Pull Request to Infrastructure Repo
        uses: peter-evans/create-pull-request@v6
        with:
          token: ${{ secrets.INFRA_REPO_PAT }}
          commit-message: "feat(idp): scaffold new service ${{ github.event.inputs.service_name }}"
          title: "IDP: New Service Onboarding - ${{ github.event.inputs.service_name }}"
          body: "Автоматически сгенерированный PR платформенной командой для регистрации сервиса ${{ github.event.inputs.service_name }}."
          branch: "idp/${{ github.event.inputs.service_name }}" 
```

## Под капотом

В концепции Platform as a Product портал разработки (Backstage) отправляет webhook или вызывает GitHub Actions API (`POST /repos/:owner/:repo/actions/workflows/:id/dispatches`). 

Платформенный пайплайн генерирует стандартизированные манифесты Kubernetes, регистрирует DNS-записи во внутреннем Route53/CoreDNS, настраивает дашборд Grafana и заводит проект в Sentry без единого обращения к живым администраторам.

## Подводные камни

1. Навязывание жестких ограничений («золотой наручник» вместо «золотого пути»): если платформа запрещает любые нестандартные параметры, разработчики будут обходить ее стороной.
2. Отсутствие контроля удаления ресурсов (Day 2 Operations): создание сервисов автоматизировано, но заброшенные тестовые сервисы годами тратят ресурсы облака.
3. Недостаточная документация API платформы для разработчиков.

## На собеседовании

**Вопрос с собеседования:** В чем принципиальная разница между классической ролью DevOps-инженера и современным Platform Engineer?
**Ответ:** 
- Классический **DevOps-инженер** часто работал в проектной команде («DevOps в каждой команде») и занимался ручной настройкой пайплайнов, написанием Dockerfile и деплоем конкретных приложений.
- **Platform Engineer** относится к платформе как к **внутреннему продукту (Platform as a Product)**, клиентами которого являются сотни продуктовых разработчиков компании. Он создает инструменты самообслуживания (IDP, CLI, фреймворки, API), позволяющие продуктовым инженерам самостоятельно развертывать, мониторить и масштабировать сервисы за считанные минуты без тикетов и очередей.
