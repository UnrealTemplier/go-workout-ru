# GitLab Container Registry и автоматический деплой в Kubernetes

## Условие

Настройте GitLab Container Registry и automatic deploy на Kubernetes через GitLab CI/CD.

## Теория

GitLab предлагает нативную интеграцию между встроенным реестром контейнеров (GitLab Container Registry) и кластером Kubernetes через GitLab Agent for Kubernetes или переменные окружения CI/CD:
- Авторизация во встроенном реестре выполняется автоматически через предопределенные переменные `$CI_REGISTRY_USER` и `$CI_REGISTRY_PASSWORD`.
- Публикация образа происходит по адресу `$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA`.
- Деплой в Kubernetes осуществляется с использованием инструмента `kubectl` или `helm` в контексте кластера.

Переменные окружения `$KUBECONFIG` или подключение раннера в том же кластере позволяют исключить передачу паролей вручную.

## Решение по шагам

1. Включите Container Registry в настройках проекта GitLab.
2. В файле `.gitlab-ci.yml` создайте стадию `publish` для сборки и пуша OCI-образа через Kaniko (без root-прав).
3. Создайте стадию `deploy` с образом `bitnami/kubectl:latest`.
4. Обновите образ в Deployment кластера: `kubectl set image deployment/app app=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA`.
5. Проконтролируйте статус развертывания через `kubectl rollout status`.

## Код решения

**`.gitlab-ci.yml`**

```yaml
stages:
  - publish
  - deploy

build_image:
  stage: publish
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]
  script:
    - /kaniko/executor
      --context "${CI_PROJECT_DIR}"
      --dockerfile "${CI_PROJECT_DIR}/Dockerfile"
      --destination "${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHORT_SHA}"
      --destination "${CI_REGISTRY_IMAGE}:latest"

deploy_k8s:
  stage: deploy
  image: bitnami/kubectl:1.31
  script:
    - kubectl set image deployment/api-server api-server=${CI_REGISTRY_IMAGE}:${CI_COMMIT_SHORT_SHA} -n staging
    - kubectl rollout status deployment/api-server -n staging --timeout=120s
  only:
    - main
```

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app/server .

FROM alpine:3.21
COPY --from=builder /app/server /server
ENTRYPOINT ["/server"]
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte("OK"))
	})
	fmt.Println("K8s microservice ready")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Kaniko запускается в пространстве пользователя (rootless) без демона Docker. Он парсит Dockerfile, распаковывает базовую файловую систему в память/диск, компилирует Go-код и делает снапшоты изменений каждого слоя. 

Затем Kaniko формирует OCI tarball и отправляет его в GitLab Container Registry по адресу `registry.gitlab.com`. При деплое `kubectl` отправляет PATCH-запрос в K8s API сервер, который обновляет `spec.template.spec.containers[0].image`, и Kubelet начинает rolling update.

## Подводные камни

1. Использование Docker-in-Docker на Kubernetes раннере без настроенного TLS/Certificates: ошибки соединения демона.
2. Отсутствие таймаута на `kubectl rollout status`: при ImagePullBackOff джоба CI будет висеть до глобального таймаута GitLab (1 час).
3. Отсутствие `imagePullSecrets`: приватный реестр GitLab Container Registry требует K8s Secret типа `docker-registry` в целевом namespace.

## На собеседовании

**Вопрос с собеседования:** Почему в enterprise Kubernetes средах предпочтительнее использовать GitOps (ArgoCD/Flux), а не прямую команду `kubectl set image` из GitLab CI?
**Ответ:** Команда `kubectl set image` изменяет состояние кластера напрямую в рантайме, минуя Git. В результате возникает рассинхронизация (Configuration Drift): манифест в Git-репозитории по-прежнему содержит старый тег, а в кластере работает новый. Если под упадет или нода перезапустится с восстановлением из Git, K8s откатится назад. GitOps гарантирует, что любое изменение версии фиксируется коммитом в Git перед применением в кластере.
