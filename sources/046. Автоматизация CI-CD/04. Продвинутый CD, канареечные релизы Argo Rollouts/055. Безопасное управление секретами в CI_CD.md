# Безопасное управление секретами в CI/CD: маскирование, Vault и GitHub Secrets

## Условие

**Управление секретами в CI/CD**: Представьте, что для прохождения интеграционных тестов в CI вашему приложению нужен токен доступа к стороннему сервису. Настройте передачу этого токена: добавьте его в секреты репозитория (GitHub Secrets) [474], а в пайплайне пробросьте его в тест через переменную окружения `env` [474]. Напишите комментарий о том, почему категорически запрещено коммитить реальные пароли и токены в Git-репозиторий.

## Теория

Утечка учетных данных (API-ключей, токенов БД, приватных ключей SSH) через логи CI/CD — одна из наиболее распространенных причин инцидентов ИБ в корпорациях.

Принципы безопасного управления секретами:
1. **GitHub Secrets:** Шифруются асимметричным ключом (libsodium sealed box) перед сохранением в базе GitHub.
2. **Автоматическое маскирование (Secret Masking):** Значения секретов автоматически заменяются на `***` в консольных логах.
3. **Команда `::add-mask::`:** Позволяет динамически маскировать секреты, сгенерированные или полученные в рантайме.
4. **Внешние хранилища секретов (HashiCorp Vault):** В enterprise-системах долгоживущие секреты не хранятся в GitHub, а запрашиваются динамически через Vault OIDC JWT аутентификацию.

## Решение по шагам

1. Добавьте секрет `DATABASE_PASSWORD` в Settings -> Secrets and variables -> Actions.
2. В файле workflow передайте секрет в джобу через секцию `env:`.
3. Для динамически генерируемых секретов используйте директиву `echo "::add-mask::$DYNAMIC_SECRET"`.
4. Запустите тесты с чтением секрета из переменной окружения.
5. Убедитесь, что при попытке вывода в консоль значение маскируется звездочками `***`.

## Код решения

**`.github/workflows/secrets.yml`**

```yaml
name: Secure Secrets Handling

on:
  push:
    branches: [ main ]

jobs:
  secure-job:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.24'

      - name: Demonstrate Dynamic Masking
        run: |
          TOKEN=$(openssl rand -hex 16)
          # Регистрация динамического секрета в системе маскирования GitHub Actions:
          echo "::add-mask::$TOKEN"
          echo "DYNAMIC_API_TOKEN=$TOKEN" >> $GITHUB_ENV
          echo "Секрет сгенерирован и защищен: $TOKEN"

      - name: Run Tests with Encrypted Secrets
        env:
          DB_PASS: ${{ secrets.DATABASE_PASSWORD }}
        run: |
          go test -v ./...
```

**`db.go`**

```go
package main

import (
	"errors"
	"fmt"
	"os"
)

// ConnectDB имитирует защищенное подключение к базе данных.
func ConnectDB() error {
	pass := os.Getenv("DB_PASS")
	if pass == "" {
		return errors.New("пароль базы данных не передан через окружение")
	}
	fmt.Printf("Подключение к базе данных успешно установлено [Длина секрета: %d символов]\n", len(pass))
	return nil
}

func main() {
	if err := ConnectDB(); err != nil {
		fmt.Printf("Ошибка: %v\n", err)
		os.Exit(1)
	}
}
```

**`db_test.go`**

```go
package main

import (
	"os"
	"testing"
)

func TestConnectDB(t *testing.T) {
	_ = os.Setenv("DB_PASS", "super_secret_ci_password_123")
	defer os.Unsetenv("DB_PASS")

	if err := ConnectDB(); err != nil {
		t.Fatalf("ConnectDB failed: %v", err)
	}
}
```

## Под капотом

Раннер GitHub Actions перехватывает весь поток stdout/stderr всех запускаемых команд. Движок раннера содержит таблицу зарегистрированных секретов. 

Перед отправкой строки лога на сервер GitHub демон раннера прогоняет текст через алгоритм поиска подстрок (Aho-Corasick) и заменяет любые точные совпадения со значениями секретов на `***`.

## Подводные камни

1. Вывод секретов в формате Base64 или URL-encoded: если зашифровать пароль в base64 (`echo $SECRET | base64`), раннер не распознает закодированную строку и выведет ее в открытый лог!
2. Использование `set -x` в bash: трассировка bash может раскрыть секреты при подстановке аргументов команд.
3. Доступность секретов в PR из форков: по умолчанию GitHub Actions не передает секреты в PR из форков репозитория для защиты от вредоносных скриптов контрибьюторов.

## На собеседовании

**Вопрос с собеседования:** Как устроен механизм OpenID Connect (OIDC) для аутентификации GitHub Actions в HashiCorp Vault или AWS/GCP без использования статических паролей?
**Ответ:** Раннер GitHub Actions запрашивает у провайдера GitHub криптографически подписанный JSON Web Token (JWT), подтверждающий контекст сборки (репозиторий, ветку, коммит). 
Затем раннер отправляет этот JWT в Vault или AWS STS. Облачный сервис проверяет подпись открытым ключом GitHub (`https://token.actions.githubusercontent.com`), валидирует правила доступа (например, «только ветка main репозитория company/payments») и выдает временные краткосрочные учетные данные (срок жизни 15 минут). Это полностью устраняет статические долгоживущие секреты.
