# Полный сквозной CI/CD конвейер: от коммита до Production с ручным подтверждением

## Условие

Создайте полный CI/CD пайплайн: push в main → сборка образа → деплой в staging-кластер → acceptance-тесты → promotion в production (ручное подтверждение).

## Теория

Промышленный эталонный пайплайн CI/CD связывает воедино все стадии жизненного цикла ПО:
1. **Lint & Test:** Параллельная проверка качества кода, линтеров и юнит-тестов.
2. **Build OCI Image:** Сборка неизменяемого контейнера с тегированием по SHA.
3. **Deploy to Staging:** Автоматическое развертывание в тестовый кластер.
4. **Acceptance / E2E Tests:** Запуск сквозных функциональных тестов против развернутого Staging-окружения.
5. **Approval Gate:** Ожидание подтверждения релиз-инженером через GitHub Environment Protection Rules.
6. **Deploy to Production:** Развертывание проверенного образа в боевой кластер с канареечной валидацией.

## Решение по шагам

1. Создайте `.github/workflows/full-pipeline.yml`.
2. Опишите цепочку зависимостей через `needs: [...]`.
3. Настройте джобы: `verify` -> `build-image` -> `deploy-staging` -> `e2e-tests` -> `deploy-production`.
4. Для `deploy-production` укажите `environment: production`.
5. Протестируйте прохождение конвейера со симуляцией всех этапов.

## Код решения

**`.github/workflows/full-pipeline.yml`**

```yaml
name: End-to-End Enterprise CI/CD

on:
  push:
    branches: [ main ]

jobs:
  verify:
    name: Quality Gate (Lint & Tests)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true
      - run: go vet ./...
      - run: go test -v -race -cover ./...

  build-image:
    name: Build & Push Image
    needs: verify
    runs-on: ubuntu-latest
    outputs:
      image_tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - id: meta
        run: echo "tag=ghcr.io/${{ github.repository }}:${{ github.sha }}" >> $GITHUB_OUTPUT
      - run: echo "Building container with tag ${{ steps.meta.outputs.tag }}..."

  deploy-staging:
    name: Deploy to Staging
    needs: build-image
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: echo "Deploying image ${{ needs.build-image.outputs.image_tag }} to Staging K8s cluster..."

  acceptance-tests:
    name: Run E2E Acceptance Tests
    needs: deploy-staging
    runs-on: ubuntu-latest
    steps:
      - run: echo "Running Newman / Cypress / Go integration tests against Staging API..."

  deploy-production:
    name: Deploy to Production (Approval Gate)
    needs: acceptance-tests
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://api.production.company.com
    steps:
      - run: echo "Deploying verified image ${{ needs.build-image.outputs.image_tag }} to Production cluster!" 
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/api/v1/health", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(`{"status":"UP","version":"2.4.0"}`))
	})
	fmt.Println("Production API Server starting...")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Граф выполнения GitHub Actions связывает джобы через `needs`. Выходные переменные (`outputs`) передаются между джобами через контекст `${{ needs.<job_id>.outputs.<name> }}`. 

На шаге `deploy-production` рантайм GitHub ставит джобу на паузу до тех пор, пока назначенные в настройках окружения ревьюеры не подтвердят запуск через веб-интерфейс или мобильное приложение GitHub.

## Подводные камни

1. Запуск E2E тестов параллельно с деплоем на Staging вместо использования `needs: [deploy-staging]`: тесты начнут стучаться в еще не обновившийся сервис.
2. Пересборка контейнера перед деплоем в Production: в прод должен идти строго тот же тег образа, который прошел Staging и E2E тесты.
3. Отсутствие мониторинга метрик после деплоя в Production.

## На собеседовании

**Вопрос с собеседования:** Что такое «Rollback Strategy» и как организовать моментальный откат продакшна при сбое в рамках сквозного CI/CD конвейера?
**Ответ:** 
1. **На уровне GitOps:** Откат выполняется простым коммитом `git revert <commit_hash>` в репозиторий манифестов; ArgoCD мгновенно возвращает предыдущую версию образа.
2. **На уровне Kubernetes:** Вызов `kubectl rollout undo deployment/<name>`.
3. **На уровне Argo Rollouts:** Автоматический откат на основе `AnalysisTemplate` при превышении процента ошибок в Prometheus. 
Главное правило: никогда не чинить production «вперед» новым спешным коммитом с коленки (Hotfix), а сначала мгновенно откатить трафик на гарантированно рабочую предыдущую версию.
