# CI линтинг на страже: тонкая настройка .golangci.yml и локальный кэш

## Условие

**CI: Линтер на страже**: Никогда не мерджи грязный код! Добавь шаг с использованием `golangci-lint` (есть готовый GitHub Action `golangci/golangci-lint-action`). Намеренно закоммить код с неиспользуемой переменной. Убедись, что пайплайн **падает** и не дает коду пройти дальше.

## Теория

Качественный линтинг в CI не должен раздражать разработчиков ложными срабатываниями (false positives) или падать по 10 минут. Для этого требуется тонкая настройка исключений и параметров в `.golangci.yml`.

Ключевые практики enterprise-конфигурации:
1. **Исключение тестовых файлов из строгих правил:** Например, в тестах допустимо игнорировать ошибки закрытия `defer resp.Body.Close()`. Это настраивается через `issues.exclude-rules`.
2. **Параллельное исполнение:** `run.concurrency: 4` позволяет утилизировать многоядерность CI-раннера.
3. **Строгий контроль импортов (`gci` / `goimports`):** Автоматическая группировка импортов (стандартная библиотека, сторонние пакеты, внутренние модули компании).
4. **Контроль сложности кода (`gocyclo` / `cyclop`):** Ограничение цикломатической сложности функций (обычно не более 15), стимулирующее рефакторинг.

## Решение по шагам

1. Настройте секцию `linters-settings` для `gci` с явным разделением на `standard`, `default`, `prefix(my-module)`.
2. Добавьте линтер `gocyclo` с порогом `min-complexity: 15`.
3. Добавьте в `issues.exclude-rules` исключение ошибок `errcheck` для файлов `*_test.go`.
4. Включите шаг запуска `golangci-lint run --new-from-rev=origin/main` для быстрой проверки только изменений в PR.

## Код решения

**`.golangci.yml`**

```yaml
run:
  timeout: 5m
  concurrency: 4
  issues-exit-code: 1

linters:
  disable-all: true
  enable:
    - errcheck
    - gosimple
    - govet
    - ineffassign
    - staticcheck
    - unused
    - gocyclo
    - gci

linters-settings:
  gocyclo:
    min-complexity: 15
  gci:
    sections:
      - standard
      - default
      - prefix(example.com/project)

issues:
  exclude-rules:
    - path: _test\.go
      linters:
        - errcheck
        - gocyclo
```

**`.github/workflows/fast-lint.yml`**

```yaml
name: Fast PR Linter

on:
  pull_request:
    branches: [ main ]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'

      - name: Install golangci-lint
        run: go install github.com/golangci/golangci-lint/cmd/golangci-lint@v1.64.5

      - name: Run Linter on Changed Code Only
        run: |
          golangci-lint run --new-from-rev=origin/main --timeout=3m
```

**`order.go`**

```go
package main

import (
	"errors"
	"fmt"
)

// ProcessOrder проверяет статус заказа и сумму.
func ProcessOrder(status string, amount float64) error {
	if amount <= 0 {
		return errors.New("некорректная сумма заказа")
	}

	if status != "PENDING" {
		return fmt.Errorf("недопустимый статус заказа: %s", status)
	}

	return nil
}
```

## Под капотом

Флаг `--new-from-rev=origin/main` выполняет `git diff` между веткой PR и базовой веткой `main`. `golangci-lint` запускает полный статический анализ всего проекта для построения точной таблицы типов и связей, но в итоговый отчет выводит **исключительно те ошибки, которые локализованы в измененных строках**. 

Для работы этой команды в `actions/checkout` обязательно требуется `fetch-depth: 0`, иначе shallow-клон репозитория не будет содержать историю коммитов базовой ветки.

## Подводные камни

1. Shallow checkout: при `fetch-depth: 1` команда `git merge-base` не может найти общего предка, и флаг `--new-from-rev` падает с фатальной ошибкой git.
2. Устаревание версии линтера: использование локальной версии `golangci-lint` на машине разработчика 1.55, а в CI — 1.64, что приводит к «у меня локально все работает, а CI красный». Версии должны быть строго зафиксированы через Makefile или toolchain.
3. Отсутствие линтера `gci` / `gofumpt`: разработчики тратят время на споры о форматировании импортов во время Code Review.

## На собеседовании

**Вопрос с собеседования:** Как решить проблему «Legacy Codebase», когда при включении нового линтера в `.golangci.yml` падает 5 000 старых предупреждений во всем репозитории?
**Ответ:**
1. Использовать флаг `--new-from-rev=origin/main` в CI, чтобы блокировать появление предупреждений **только в новом и изменяемом коде**.
2. Использовать генерацию базовой линии (baseline/todo list): исключить старые предупреждения через секцию `issues.exclude` или сгенерированный список исключений.
3. Внедрить в команду правило «Boy Scout Rule» (оставь место чище, чем нашел): если инженер прикасается к файлу с легаси-кодом, он исправляет линтер-ошибки в рамках отдельного рефакторинг-коммита.
