# Декларативный пайплайн в Jenkins (Jenkinsfile): stages, junit и parallel

## Условие

Настрой **Jenkins pipeline** (declarative): `Jenkinsfile`. Stages: `Checkout`, `Test`, `Build`, `Deploy`. Agents: `docker` agent `golang:1.24`. Shared library for common steps. Покажи enterprise CI.

## Теория

Несмотря на популярность GitHub Actions и GitLab CI, Jenkins остается основой CI/CD во многих Enterprise-корпорациях благодаря десяткам тысяч плагинов и зрелой системе управления доступом (RBAC).

Современный стандарт Jenkins — **Declarative Pipeline** (`Jenkinsfile`), пришедший на смену хрупким Scripted Groovy пайплайнам:
- Жесткая декларативная структура блоков: `pipeline`, `agent`, `stages`, `steps`, `post`.
- `agent { docker { ... } }`: выполнение каждого этапа внутри чистого контейнера без засорения ОС агента.
- Секция `post { ... }`: гарантированное выполнение блоков `always`, `success`, `failure`, `cleanup` (например, отправка алертов и сбор JUnit XML отчетов).
- Блок `parallel`: одновременный запуск независимых проверок (юнит-тесты и статический анализ).

## Решение по шагам

1. Создайте в корне репозитория файл `Jenkinsfile`.
2. Объявите агента с базовым образом `golang:1.24`.
3. Добавьте утилиту `go-junit-report` для конвертации вывода `go test` в стандартный XML-формат JUnit.
4. В секции `stages` организуйте параллельное выполнение тестов и линтера через блок `parallel`.
5. В секции `post.always` добавьте шаг `junit 'reports/**/*.xml'` для отображения графиков тестов в веб-интерфейсе Jenkins.

## Код решения

**`Jenkinsfile`**

```groovy
pipeline {
    agent {
        docker {
            image 'golang:1.24-alpine'
            args '-v /var/cache/go:/go/pkg/mod'
        }
    }
    options {
        timeout(time: 30, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '20'))
    }
    environment {
        CGO_ENABLED = '0'
        GOPATH = '/go'
    }
    stages {
        stage('Prepare') {
            steps {
                sh 'apk add --no-cache git make'
                sh 'go install github.com/jstemmer/go-junit-report/v2@latest'
                sh 'mkdir -p reports'
            }
        }
        stage('Quality Checks') {
            parallel {
                stage('Unit Tests') {
                    steps {
                        sh 'go test -v -coverprofile=reports/coverage.out ./... 2>&1 | go-junit-report -set-exit-code > reports/junit.xml'
                    }
                }
                stage('Compile Binary') {
                    steps {
                        sh 'go build -ldflags="-s -w" -o bin/app .'
                    }
                }
            }
        }
    }
    post {
        always {
            junit testResults: 'reports/junit.xml', allowEmptyResults: true
            archiveArtifacts artifacts: 'bin/app', fingerprint: true, allowEmptyArchive: true
        }
        failure {
            echo 'Пайплайн завершился ошибкой! Уведомляем команду...'
        }
    }
}
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func HealthCheck() string {
	return "healthy"
}

func main() {
	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte(HealthCheck()))
	})
	fmt.Println("Сервис запущен...")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`main_test.go`**

```go
package main

import "testing"

func TestHealthCheck(t *testing.T) {
	if got := HealthCheck(); got != "healthy" {
		t.Fatalf("HealthCheck() = %s; want healthy", got)
	}
}
```

## Под капотом

Когда Jenkins выполняет директиву `agent { docker { ... } }`, мастер-нода отправляет на агент команду:
`docker run -d -u 1000:1000 -v /workspace:/workspace golang:1.24-alpine cat`
Контейнер удерживается в запущенном состоянии командой `cat`. Каждый последующий блок `sh '...'` исполняется внутри контейнера через `docker exec`. 

Плагин JUnit парсит результирующий XML и записывает статистику в SQL/H2 базу данных Jenkins, формируя графики динамики тестов (Test Result Trend).

## Подводные камни

1. Забытый флаг `-set-exit-code` в `go-junit-report`: без него утилита считывает `FAIL` от `go test`, генерирует XML, но завершается с кодом `0`, и Jenkins считает шаг успешным.
2. Проблема прав доступа к смонтированным папкам: контейнер по умолчанию работает под тем же UID, что и демон Jenkins на хосте; несовпадение UID приводит к ошибкам `Permission denied`.
3. Смешивание Scripted и Declarative синтаксиса без блока `script { ... }` внутри шагов `steps`.

## На собеседовании

**Вопрос с собеседования:** В чем преимущества и недостатки перехода с Jenkins на современные облачные CI-решения (GitHub Actions / GitLab CI / Tekton)?
**Ответ:** 
- **Преимущества перехода:** Отсутствие необходимости администрировать собственный мастер-сервер Jenkins (патчи уязвимостей, падения плагинов, утечки памяти JVM), конфигурация как код (Pipeline as Code) хранится рядом с приложением в репозитории, простота масштабирования ephemeral-агентов.
- **Недостатки перехода:** Сложность миграции тысяч кастомных Groovy-скриптов и корпоративных плагинов, в банках часто требуется строгая изоляция в закрытом контуре без выхода в интернет, где Jenkins с локальными агентами разворачивается проще всего.
