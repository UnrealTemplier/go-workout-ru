# Управление GitLab CI Runners: Shared против Specific и тегирование

## Условие

Настрой **GitLab CI with runners**: shared runners vs specific runners (tagged `docker`, `k8s`). Self-hosted runner on Kubernetes (`gitlab-runner` Helm chart). Покажи scaling runners.

## Теория

В инфраструктуре GitLab CI исполнители задач (GitLab Runners) делятся на два типа:
1. **Shared Runners:** Общий пул раннеров, доступный всем проектам организации. Подходит для простых проверок, но имеет очереди и разделяемые ресурсы.
2. **Specific (Project/Group) Runners:** Выделенные виртуальные машины или поды Kubernetes, зарегистрированные для конкретного проекта или департамента. Необходимы для:
   - Доступа к закрытым контурам сети (VPN, базы данных в VPC, внутренние OCI-реестры).
   - Специфического оборудования (GPU для ML, ARM bare-metal, SSD NVMe).
   - Изоляции чувствительных сборок со строгими требованиями безопасности.

Связывание джобы с раннером осуществляется через **теги (`tags`)**. Если у раннера указаны теги `[docker, k8s, high-cpu]`, джоба с директивой `tags: [docker, high-cpu]` будет направлена строго на него.

## Решение по шагам

1. Зарегистрируйте раннер на выделенном сервере или в Kubernetes кластере с тегами `go-builder`, `k8s-infra`.
2. В файле `.gitlab-ci.yml` добавьте секцию `tags` в каждую джобу.
3. Для тяжелых сборок укажите теги высокопроизводительных раннеров.
4. Настройте `executor = "kubernetes"` в файле `config.toml` раннера для динамического создания подов под каждую джобу.

## Код решения

**`.gitlab-ci.yml`**

```yaml
stages:
  - lint
  - test
  - deploy

job:linter:
  stage: lint
  image: golangci/golangci-lint:v1.64.5-alpine
  tags:
    - shared-docker
  script:
    - golangci-lint run --timeout=5m

job:integration_tests:
  stage: test
  image: golang:1.24
  tags:
    - high-perf
    - bare-metal
  script:
    - go test -v -race -timeout=15m ./internal/integration/...

job:deploy_k8s:
  stage: deploy
  tags:
    - k8s-prod-access
  script:
    - kubectl rollout status deployment/auth-service -n production
```

**`config.toml`**

```toml
concurrent = 8
check_interval = 0

[session_server]
  session_timeout = 1800

[[runners]]
  name = "k8s-cluster-runner"
  url = "https://gitlab.example.com"
  id = 42
  token = "glrt-t1_runner_registration_token"
  token_obtained_at = 2026-01-01T00:00:00Z
  token_expires_at = 0001-01-01T00:00:00Z
  executor = "kubernetes"
  [runners.kubernetes]
    host = ""
    bearer_token_overwrite_allowed = false
    image = "alpine:3.21"
    namespace = "gitlab-runners"
    privileged = false
    cpu_limit = "4"
    memory_limit = "8Gi"
    cpu_request = "1"
    memory_request = "2Gi" 
```

## Под капотом

GitLab Runner периодически опрашивает GitLab API (`POST /api/v4/jobs/request`). В теле запроса раннер передает свои теги. 

GitLab CI Scheduler сравнивает теги свободной джобы с тегами запросившего раннера. Джоба назначается только при строгом совпадении подмножества тегов. 

В Kubernetes Executor раннер создает Pod с несколькими контейнерами: `build` (выполняет скрипт), `helper` (клонирует git, загружает/скачивает кэш и артефакты) и sidecar-контейнеры сервисов (базы данных, Redis).

## Подводные камни

1. Зависание джобы в статусе `Pending` (Stuck job): если в `.gitlab-ci.yml` указать несуществующий тег, например `tags: [gpu]`, а такого раннера нет в проекте, пайплайн будет висеть бесконечно.
2. Включение `privileged = true` на shared-раннерах: компрометация одной сборки позволяет злоумышленнику вырваться из Docker-контейнера на хостовую ноду кластера.
3. Использование одного runner token на сотне серверов: затрудняет аудит и аннулирование доступа при компрометации отдельного хоста.

## На собеседовании

**Вопрос с собеседования:** Почему в production-кластерах запрещено использовать Docker-in-Docker (`dind`) с привилегированным режимом (`privileged = true`) на GitLab раннерах, и чем его заменяют?
**Ответ:** Флаг `privileged = true` отключает изоляцию ядра Linux (AppArmor, seccomp, сбрасывает ограничения cgroups), давая контейнеру полные права суперпользователя на ноде K8s. Любой разработчик через скрипт сборки может смонтировать диск ноды `/dev/sda1` и украсть секреты всех соседних подов. 
Вместо DinD в enterprise используют **беспривилегированные сборщики**:
1. **Kaniko** от Google: собирает Docker-образы в пространстве пользователя без демона Docker.
2. **Buildah / Podman**: сборка без root-прав через user namespaces.
3. **BuildKit daemonless** в режиме `rootless`.
