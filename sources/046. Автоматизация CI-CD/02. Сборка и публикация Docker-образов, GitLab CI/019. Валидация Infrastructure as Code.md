# Валидация Infrastructure as Code: terraform validate и kubeconform

## Условие

Добавь **infrastructure as code validation**: `terraform validate`, `terraform plan` (comment on PR). `kubeval` / `kubeconform` для Kubernetes manifests. Gate: invalid config = build failure.

## Теория

С развитием GitOps и Platform Engineering инфраструктура описывается кодом (IaC — Terraform/OpenTofu, Kubernetes Manifests, Helm, Kustomize). Ошибки в манифестах или опечатки в типах ресурсов, дошедшие до продакшна, приводят к авариям масштаба всего кластера.

Пайплайн валидации IaC обязан проверять:
1. **Синтаксис и схему манифестов Kubernetes (`kubeconform`):** Быстрый инструмент на Go, валидирующий YAML-манифесты по официальным JSON-схемам Kubernetes OpenAPI целевой версии (например, `1.31.0`), выявляя устаревшие или несуществующие поля.
2. **Синтаксис Terraform (`terraform validate` / `tflint`):** Проверка структуры HCL, типов входных переменных и обязательных аргументов провайдеров без обращения к удаленному состоянию (state).
3. **Безопасность (`checkov` или `tfsec`):** Поиск открытых портов (0.0.0.0/0), отсутствия шифрования дисков и дефолтных паролей.

## Решение по шагам

1. Создайте `.github/workflows/iac-check.yml`, срабатывающий на Pull Request при изменении файлов `*.tf` или `k8s/**.yaml`.
2. Настройте шаг валидации Terraform: `terraform fmt -check` и `terraform validate`.
3. Установите `kubeconform` и запустите проверку каталога с манифестами: `kubeconform -strict -kubernetes-version 1.31.0 k8s/`.
4. Заблокируйте PR при обнаружении синтаксических ошибок или невалидных полей.

## Код решения

**`.github/workflows/iac-check.yml`**

```yaml
name: IaC and Kubernetes Validation

on:
  pull_request:
    paths:
      - 'deploy/**'
      - 'terraform/**'

jobs:
  kubeconform:
    name: Validate K8s Manifests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Kubeconform
        run: |
          curl -sL https://github.com/yannh/kubeconform/releases/download/v0.6.7/kubeconform-linux-amd64.tar.gz | tar xz
          sudo mv kubeconform /usr/local/bin/

      - name: Validate Manifests
        run: |
          kubeconform -strict -summary -kubernetes-version 1.31.0 deploy/k8s/

  terraform:
    name: Validate Terraform
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.9.0

      - name: Terraform Init & Validate
        run: |
          cd terraform
          terraform init -backend=false
          terraform fmt -check
          terraform validate
```

## Под капотом

`kubeconform` не требует подключения к живому API-серверу кластера. Он парсит YAML в структуру памяти и сопоставляет каждое поле с JSON Schema, скачиваемой из реестра `https://raw.githubusercontent.com/yannh/kubernetes-json-schema`. Флаг `-strict` запрещает наличие неопределенных (лишних) полей, что предотвращает ошибки опечаток в названиях ключей.

`terraform validate` строит граф зависимостей локальных модулей, валидирует внутреннюю совместимость ссылок на атрибуты и блоки ресурсов.

## Подводные камни

1. Использование команды `kubectl apply --dry-run=client` в CI: она имеет ограниченные проверки и требует громоздкой настройки kubectl с валидным kubeconfig.
2. Пропуск флага `-backend=false` при `terraform init` в CI: попытка подключиться к S3 бэкенду без прод-секретов приведет к падению сборки на публичных PR.
3. Игнорирование валидации Custom Resource Definitions (CRD) операторов (PrometheusRule, VirtualService): необходимо передавать флаг `-schema-location default -schema-location 'https://...'`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между инструментами `conftest` (OPA), `kubeconform` и `polaris` при проверке манифестов Kubernetes в CI?
**Ответ:** 
- **`kubeconform`** проверяет **структурную валидность** схемы: соответствие полей спецификации K8s OpenAPI (типы, обязательные атрибуты).
- **`conftest` (Open Policy Agent / Rego)** проверяет **бизнес-политики и безопасность**: например, «запретить запуск под root», «обязательно наличие лейбла `owner`», «запретить image:latest».
- **`polaris`** специализируется на **best practices** аудита надежности и эффективности использования ресурсов (наличие probes, resources limits/requests). В зрелом CI они дополняют друг друга.
