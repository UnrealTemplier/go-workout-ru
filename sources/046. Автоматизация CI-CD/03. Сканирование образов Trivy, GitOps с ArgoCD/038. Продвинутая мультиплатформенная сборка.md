# Продвинутая мультиплатформенная сборка Docker-образов через QEMU и Buildx

## Условие

Настройте multi-arch Docker образы через `docker/setup-qemu-action` и `docker/setup-buildx-action`.

## Теория

При промышленной сборке мульти-архитектурных образов (`amd64` и `arm64`) критично оптимизировать время работы CI. Эмуляция инструкций ARM через QEMU медленнее нативной компиляции в 5–10 раз.

Продвинутый подход совмещает:
1. **`binfmt` эмуляцию:** Регистрация эмуляторов QEMU в ядре раннера через `docker/setup-qemu-action`.
2. **BuildKit Multi-Platform Cross-Compilation:** Использование нативных возможностей Go кросс-компиляции (`GOOS=linux GOARCH=arm64`), исключая запуск самого компилятора Go внутри QEMU.
3. **Общий экспорт манифеста:** Создание единого мульти-архитектурного OCI-дескриптора.

## Решение по шагам

1. Добавьте шаги `setup-qemu-action` и `setup-buildx-action`.
2. В Dockerfile организуйте stage сборки с флагом `--platform=$BUILDPLATFORM`.
3. Используйте аргументы `TARGETPLATFORM`, `TARGETOS`, `TARGETARCH`.
4. В GitHub Actions укажите `platforms: linux/amd64,linux/arm64`.
5. Протестируйте итоговый образ на обеих архитектурах.

## Код решения

**`.github/workflows/advanced-multiarch.yml`**

```yaml
name: Advanced Multi-Arch CI

on:
  push:
    branches: [ main ]

jobs:
  multiarch:
    name: Build & Push AMD64/ARM64
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3
        with:
          platforms: all

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build & Push Image
        uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ghcr.io/${{ github.repository }}:latest
```

**`Dockerfile`**

```dockerfile
# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:1.24-alpine AS builder
ARG TARGETOS
ARG TARGETARCH

WORKDIR /src
COPY go.mod go.sum* ./
RUN go mod download

COPY . .
# Нативная кросс-компиляция компилятором хоста:
RUN CGO_ENABLED=0 GOOS=${TARGETOS} GOARCH=${TARGETARCH} \
    go build -ldflags="-s -w" -o /out/app .

FROM alpine:3.21
WORKDIR /app
COPY --from=builder /out/app /app/server
USER 65534:65534
ENTRYPOINT ["/app/server"]
```

## Под капотом

Модуль ядра Linux `binfmt_misc` перехватывает системный вызов `execve`. Когда ОС пытается запустить бинарник ARM64 на процессоре x86_64, ядро определяет сигнатуру ELF-заголовка и автоматически передает исполнение эмулятору `/usr/bin/qemu-aarch64-static`. 

Благодаря флагу `--platform=$BUILDPLATFORM` BuildKit скачивает компилятор Go родной архитектуры хоста (x86_64), поэтому Go компилирует ARM64-код на полной скорости процессора хоста без единого вызова QEMU!

## Подводные камни

1. Ошибочный запуск тестов `go test` на этапе сборки контейнера под чужую архитектуру: тесты будут исполняться внутри QEMU, что замедлит сборку в разы. Тесты следует прогонять в отдельной нативной джобе CI до сборки контейнера.
2. Пропуск аргументов `ARG TARGETOS` и `ARG TARGETARCH`: Go скомпилирует бинарник под платформу билдера (`amd64`), и образ упадет на ARM-ноде.
3. Проблемы с CGO: при кросс-компиляции CGO отключен по умолчанию, попытка включить его без кросс-тулчейнов C приведет к ошибкам компилятора.

## На собеседовании

**Вопрос с собеседования:** Почему запуск юнит-тестов Go внутри эмулируемого через QEMU контейнера считается антипаттерном в CI?
**Ответ:** QEMU транслирует инструкции гостевой архитектуры в команды хоста на лету. Это приводит к колоссальному падению производительности CPU (в 5–10 раз) и искажению таймингов синхронизации (гонки данных и дедлоки могут либо маскироваться, либо проявляться ложно). 
Правильный подход — прогонять все тесты и линтеры на нативных раннерах x86_64, а компиляцию под ARM64 выполнять кросс-компилятором Go, тестируя бинарник на настоящих ARM-нодах только на этапе E2E/Smoke.
