# Релизный пайплайн по Git-тегам: сборка и выгрузка ассетов в GitHub Release

## Условие

**[Релизный пайплайн (Tags)]**: Настрой триггер на создание Git-тега (например, `v1.0.0`). Пайплайн должен собрать бинарники под разные ОС (linux, windows, darwin), заархивировать их и создать Release в GitHub.

## Теория

Формирование официального релиза в Git — ключевой момент поставки артефактов пользователям и downstream-системам.

Релизный пайплайн обязан:
1. Срабатывать строго при создании аннотированного Git-тега (`git tag -a v1.0.0 -m "Release 1.0.0"`).
2. Выполнять строгую компиляцию без отладочных данных с инъекцией версии.
3. Создавать запись GitHub Release через API (`softprops/action-gh-release`).
4. Автоматически генерировать контрольные суммы (SHA-256) для предотвращения подмены бинарников.
5. Прикреплять архив и хэши в релизные ассеты.

## Решение по шагам

1. Настройте триггер workflow на событие `push.tags: ['v*.*.*']`.
2. Настройте компиляцию утилиты под целевую ОС (Linux amd64).
3. Сгенерируйте контрольную сумму: `sha256sum binary > binary.sha256`.
4. Используйте экшен `softprops/action-gh-release@v2` для публикации релиза и загрузки файлов.
5. Проверьте права токена `permissions: contents: write`.

## Код решения

**`.github/workflows/tag-release.yml`**

```yaml
name: Publish Tagged Release

on:
  push:
    tags:
      - 'v*.*.*'

permissions:
  contents: write

jobs:
  build-and-release:
    name: Build & Attach Release Assets
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.24'

      - name: Build Binary
        run: |
          mkdir -p dist
          CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-s -w -X main.version=${{ github.ref_name }}" -o dist/mycli-linux-amd64 .
          cd dist
          sha256sum mycli-linux-amd64 > mycli-linux-amd64.sha256

      - name: Create GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          files: |
            dist/mycli-linux-amd64
            dist/mycli-linux-amd64.sha256
          draft: false
          prerelease: false
          generate_release_notes: true
```

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
)

var version = "dev"

func main() {
	if len(os.Args) > 1 && os.Args[1] == "--version" {
		fmt.Printf("MyCLI version %s\n", version)
		return
	}
	fmt.Println("CLI инструмент готов к выполнению команд.")
}
```

## Под капотом

Экшен `softprops/action-gh-release` взаимодействует с GitHub REST API:
`POST /repos/{owner}/{repo}/releases`
Параметр `generate_release_notes: true` задействует встроенный движок генерации описания релизов GitHub, который парсит заголовки объединенных PR со времени предыдущего релиза и формирует аккуратный Markdown-список изменений с указанием авторов коммитов.

## Подводные камни

1. Забытый `permissions: contents: write`: джоба завершится с `403 Forbidden` при попытке создать релиз.
2. Создание релиза без файла SHA-256: безопасность цепочки поставок нарушается, пользователи не могут проверить целостность скачанного исполняемого файла.
3. Использование `draft: false` для непротестированных тегов: если тег запушен по ошибке, релиз моментально станет доступен пользователям.

## На собеседовании

**Вопрос с собеседования:** В чем разница между легковесным тегом (`lightweight tag`) и аннотированным тегом (`annotated tag`) в Git, и какой из них следует использовать в CI/CD?
**Ответ:** Легковесный тег — это просто указатель на конкретный коммит (подобно ветке, которая не двигается). Аннотированный тег (`git tag -a`) сохраняется в базе Git как полноценный объект: он содержит имя автора тега, email, дату создания, сообщение релиза и опционально криптографическую GPG-подпись. В релизных пайплайнах CI/CD следует использовать **только аннотированные подписанные теги**, поскольку они гарантируют подлинность автора релиза.
