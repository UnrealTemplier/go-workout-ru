# Генерация отчета о покрытии тестами в HTML и загрузка артефакта в CI

## Условие

**CI: Test Coverage Artifacts**: Добавь генерацию отчета о покрытии кода тестами (`go test -coverprofile=coverage.out`). Настрой пайплайн так, чтобы он сохранял этот файл как Artifact (артефакт сборки), который можно скачать после завершения пайплайна.

## Теория

Хотя консольный процент покрытия (`go tool cover -func`) полезен для гейтов, инженерам часто требуется детально видеть, какие именно строки, граничные условия и ветки ошибок не были покрыты тестами.

Утилита стандартной поставки `go tool cover -html=coverage.out -o coverage.html`:
- Генерирует автономный HTML-файл с CSS и JS.
- Подсвечивает исходный код цветами: зеленый (блок кода выполнен), красный (блок не был вызван), серый (декларации/комментарии).
- Встроенный выпадающий список позволяет переключаться между всеми файлами и пакетами репозитория.

В GitHub Actions экшен `actions/upload-artifact` сохраняет сформированный HTML-отчет в виде загружаемого ZIP-архива, доступного для скачивания разработчиками прямо из интерфейса сборки.

## Решение по шагам

1. Запустите тесты с генерацией профиля: `go test -coverprofile=coverage.out ./...`.
2. Преобразуйте профиль в HTML: `go tool cover -html=coverage.out -o coverage.html`.
3. Добавьте шаг `actions/upload-artifact@v4` для загрузки `coverage.html`.
4. Настройте срок жизни артефакта `retention-days: 14`.

## Код решения

**`.github/workflows/coverage-artifact.yml`**

```yaml
name: Coverage HTML Artifact

on:
  pull_request:
    branches: [ main ]

jobs:
  coverage:
    name: Generate HTML Coverage
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.24'

      - name: Run Tests and Generate Profile
        run: |
          go test -race -coverprofile=coverage.out ./...

      - name: Convert Profile to HTML Report
        run: |
          go tool cover -html=coverage.out -o coverage.html

      - name: Upload HTML Coverage Report
        uses: actions/upload-artifact@v4
        with:
          name: html-coverage-report
          path: coverage.html
          retention-days: 14
```

**`validator.go`**

```go
package main

import "errors"

func CheckAge(age int) error {
	if age < 0 {
		return errors.New("возраст не может быть отрицательным")
	}
	if age > 150 {
		return errors.New("нереалистичный возраст")
	}
	return nil
}
```

**`validator_test.go`**

```go
package main

import "testing"

func TestCheckAge(t *testing.T) {
	if err := CheckAge(25); err != nil {
		t.Fatalf("CheckAge(25) вернул ошибку: %v", err)
	}
}
```

## Под капотом

`go tool cover` парсит AST каждого Go-файла и считывает диапазоны из `coverage.out`. 

При рендеринге HTML утилита кодирует исходные файлы Go в escape-последовательности и оборачивает каждый блок в теги `<span class="cov8">...</span>` или `<span class="cov0">...</span>`, где цифра соответствует частоте выполнения блока (от 0 до 10). Результирующий файл является полностью самодостаточным (inlined styles) и открывается в любом браузере локально без веб-сервера.

## Подводные камни

1. Отсутствие параметра `retention-days`: тяжелые артефакты быстро забьют дисковую квоту организации.
2. Попытка открыть `coverage.html` на машине, где нет исходного кода: если HTML сгенерирован встроенной утилитой, исходный код уже зашит внутрь HTML, но если использовать сторонние генераторы, они могут ссылаться на внешние пути.
3. Генерация coverage без флага `-covermode=atomic` при многопоточном коде приводит к фатальным падениям тестов.

## На собеседовании

**Вопрос с собеседования:** В чем ограничение метрики «Line Coverage» (покрытие строк) и почему «Branch Coverage» (покрытие ветвей) надежнее?
**Ответ:** Покрытие строк просто фиксирует, выполнилась ли строка кода. В конструкции вида `if a && b { doSomething() }`, если тест проверяет только случай `a=true, b=true`, строка `if` будет помечена как 100% покрытая. 
Однако ветка `b=false` протестирована не была, и логическая ошибка останется незамеченной. Branch Coverage требует протестировать все возможные исходы каждого булева условия (`true` и `false`), гарантируя отсутствие слепых зон в критической логике.
