# Оптимизация графа стадий в GitLab CI через Directed Acyclic Graph (DAG)

## Условие

**GitLab CI аналог**: Создайте `.gitlab-ci.yml` с stages: `lint`, `test`, `build`, `deploy`. Используйте `kaniko` для build Docker-образа без Docker daemon.

## Теория

По умолчанию в GitLab CI стадии (`stages`) выполняются строго последовательно: все джобы стадии `test` обязаны завершиться, прежде чем стартует хотя бы одна джоба стадии `build`.

Если в стадии `test` есть долгий тест (15 минут), а параллельно выполняется быстрый линтер (1 минута), джоба сборки контейнера будет простаивать 14 минут!

Директива **`needs: [...]`** внедряет модель **Directed Acyclic Graph (DAG)**:
- Разрывает жесткую линейную зависимость стадий.
- Джоба стартует **немедленно**, как только завершатся строго указанные в `needs` предшественники, игнорируя незавершенные джобы текущей или предыдущих стадий.
- Это сокращает общее время прохождения конвейера (Pipeline Wall-Clock Time) в разы.

## Решение по шагам

1. Создайте `.gitlab-ci.yml` с четырьмя стадиями: `lint`, `test`, `build`, `deploy`.
2. В джобе сборки Docker-образа укажите `needs: ["job:linter"]`, чтобы она не ждала долгих тестов.
3. В джобе деплоя укажите зависимость от сборки образа и интеграционных тестов: `needs: ["job:docker_build", "job:integration_tests"]`.
4. Сравните время выполнения линейного пайплайна и DAG-графа.

## Код решения

**`.gitlab-ci.yml`**

```yaml
stages:
  - lint
  - test
  - build
  - deploy

job:linter:
  stage: lint
  image: golangci/golangci-lint:v1.64.5-alpine
  script:
    - golangci-lint run --timeout=2m

job:unit_tests:
  stage: test
  image: golang:1.24-alpine
  script:
    - go test -v -short ./...

job:integration_tests:
  stage: test
  image: golang:1.24-alpine
  script:
    - sleep 60 # Симуляция долгих тестов с базой данных
    - go test -v ./internal/database/...

job:docker_build:
  stage: build
  # Джоба стартует сразу после линтера, не дожидаясь долгих интеграционных тестов!
  needs:
    - job:linter
  image: docker:27-cli
  services:
    - docker:27-dind
  script:
    - docker build -t myapp:$CI_COMMIT_SHA .

job:deploy_staging:
  stage: deploy
  needs:
    - job:docker_build
    - job:integration_tests
  script:
    - echo "Deploying to Staging after both Docker Build and Integration Tests finish!" 
```

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server .

FROM alpine:3.21
COPY --from=builder /app/server /server
ENTRYPOINT ["/server"]
```

**`main.go`**

```go
package main

import "fmt"

func main() {
	fmt.Println("DAG Pipeline Demo Service")
}
```

## Под капотом

GitLab CI планировщик строит топологический граф (DAG). Каждому узлу графа соответствует джоба, а ребрам — связи `needs`. 

Как только входящие ребра узла переходят в состояние `Success`, планировщик мгновенно отправляет джобу в очередь выполнения раннеров. По умолчанию `needs` также передает артефакты только указанных джобов, что снижает нагрузку на сеть при скачивании промежуточных файлов.

## Подводные камни

1. Циклические зависимости (`A needs B`, а `B needs A`): GitLab отклонит `.gitlab-ci.yml` с ошибкой валидации схемы.
2. Непреднамеренная потеря артефактов: если джоба использует `needs`, она больше не скачивает артефакты всех предыдущих стадий по умолчанию — нужно явно перечислить источники артефактов.
3. Преждевременный деплой: если забыть связать `deploy` с `test` через `needs`, сервис задеплоится даже при упавших тестах!

## На собеседовании

**Вопрос с собеседования:** В каких случаях использование `needs` (DAG) в GitLab CI может привести к инциденту на продакшне при невнимательной настройке?
**Ответ:** Если в пайплайне джоба `deploy` настроена с `needs: [docker_build]`, но инженер забыл добавить в `needs` джобу `security_audit` или `integration_tests`. В такой конфигурации деплой запустится и успешно завершится, как только соберется Docker-образ, даже если интеграционные тесты параллельно упали с ошибкой. В джобе деплоя обязаны быть перечислены все критические барьеры качества.
