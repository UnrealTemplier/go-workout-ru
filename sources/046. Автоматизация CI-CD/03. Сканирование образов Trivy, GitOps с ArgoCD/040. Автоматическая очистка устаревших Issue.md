# Автоматическая очистка устаревших Issue и PR с помощью actions/stale

## Условие

Добавьте `stale` workflow для автоматического закрытия неактивных issues и PR.

## Теория

В крупных проектах с открытым исходным кодом или монорепозиториях компании накапливаются сотни заброшенных Pull Request и тикетов (Issue), на запросы дополнительной информации по которым авторы не отвечают месяцами.

Экшен **`actions/stale`**:
- Запускается по расписанию (cron).
- Автоматически помечает тикеты и PR лейблом `stale` после заданного периода неактивности (например, 60 дней).
- Отправляет вежливое уведомление автору с просьбой подтвердить актуальность.
- Если в течение следующих 7 дней активности нет, тикет/PR автоматически закрывается.
- Любой новый комментарий пользователя автоматически снимает лейбл `stale`.

## Решение по шагам

1. Создайте `.github/workflows/stale.yml`.
2. Настройте триггер `schedule` на запуск раз в сутки (например, в полночь).
3. Используйте экшен `actions/stale@v9`.
4. Задайте `days-before-stale: 60` и `days-before-close: 7`.
5. Настройте исключение тикетов с лейблом `pinned` или `security`.

## Код решения

**`.github/workflows/stale.yml`**

```yaml
name: Mark Stale Issues and PRs

on:
  schedule:
    - cron: '0 0 * * *'
  workflow_dispatch:

permissions:
  issues: write
  pull-requests: write

jobs:
  stale:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/stale@v9
        with:
          repo-token: ${{ secrets.GITHUB_TOKEN }}
          stale-issue-message: 'Этот тикет помечен как устаревший из-за отсутствия активности в течение 60 дней. Он будет закрыт через 7 дней, если не поступит новых комментариев.'
          stale-pr-message: 'Этот Pull Request помечен как устаревший из-за неактивности. Он будет автоматически закрыт через 7 дней.'
          stale-issue-label: 'stale'
          stale-pr-label: 'stale'
          days-before-stale: 60
          days-before-close: 7
          exempt-issue-labels: 'pinned,security,roadmap'
          exempt-pr-labels: 'work-in-progress,blocked'
```

## Под капотом

Экшен опрашивает GitHub Issues API:
`GET /repos/{owner}/{repo}/issues?state=open&sort=updated&direction=asc`
Экшен фильтрует записи по полю `updated_at`. Если время последнего обновления превышает `days-before-stale`, экшен выполняет `POST` запрос на добавление лейбла и комментария. 

При следующем запуске, если дата комментария с пометкой stale превышает `days-before-close`, экшен отправляет `PATCH /issues/{id}` со статусом `state: closed`.

## Подводные камни

1. Слишком агрессивные тайминги (например, 7 дней до stale): раздражает контрибьюторов, которые ушли в отпуск.
2. Отсутствие исключений (`exempt-issue-labels`): бот закрывает важные долгосрочные задачи из дорожной карты (roadmap).
3. Забытые права `permissions: issues: write, pull-requests: write`: падение с ошибкой прав доступа.

## На собеседовании

**Вопрос с собеседования:** Какую роль играет автоматизация жизненного цикла Issues/PR в поддержании гигиены репозиториев (Repo Hygiene) в BigTech?
**Ответ:** Открытые заброшенные PR создают иллюзию незавершенной работы, засоряют поиск, создают конфликты слияния и требуют регулярного внимания мейнтейнеров. 
Автоматизация закрытия неактивных тикетов высвобождает время ведущих инженеров, стимулирует авторов доводить код до конца и поддерживает актуальность бэклога без ручной рутины.
