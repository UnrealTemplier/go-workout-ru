# Cloud-Native CI/CD с Tekton: Task, Pipeline и декларативные PipelineRun

## Условие

Настрой **Tekton** (cloud-native CI/CD): `Task`, `TaskRun`, `Pipeline`, `PipelineRun`. Reusable tasks: `git-clone`, `buildah`, `kubectl-deploy`. Покажи Kubernetes-native CI/CD.

---

## Теория

**Tekton** — облачный движок непрерывной интеграции и доставки (CI/CD), разработанный под эгидой Continuous Delivery Foundation (CDF):
- Полностью K8s-native: нет центрального CI-сервера; каждый шаг пайплайна исполняется как отдельный контейнер внутри Kubernetes Pod.
- Основные строительные блоки:
  - **`Task`:** Набор последовательных шагов (`steps`), выполняемых внутри одного Pod на одной ноде (шаги разделяют общее дисковое пространство через `workspace`).
  - **`Pipeline`:** Граф задач (DAG из `Task`), определяющий порядок и зависимости выполнения.
  - **`PipelineRun`:** Экземпляр запуска пайплайна с конкретными параметрами, ветками Git и хранилищем.

## Решение по шагам

1. Создайте CRD `Task` для сборки Go-приложения (`go test` и `go build`).
2. Опишите `Pipeline`, объединяющий задачу клонирования репозитория и задачу сборки.
3. Настройте общий `workspace` на базе PersistentVolumeClaim.
4. Создайте `PipelineRun` для запуска конвейера.
5. Отслеживайте выполнение через Tekton CLI: `tkn pipelinerun logs -f`.

## Код решения

**`tekton-task.yaml`**

```yaml
apiVersion: tekton.dev/v1beta1
kind: Task
metadata:
  name: golang-build
  namespace: ci
spec:
  workspaces:
    - name: source
  steps:
    - name: test
      image: golang:1.24-alpine
      workingDir: $(workspaces.source.path)
      script: |
        go test -v ./...

    - name: compile
      image: golang:1.24-alpine
      workingDir: $(workspaces.source.path)
      script: |
        CGO_ENABLED=0 go build -ldflags="-s -w" -o bin/server .
```

**`tekton-pipeline.yaml`**

```yaml
apiVersion: tekton.dev/v1beta1
kind: Pipeline
metadata:
  name: app-ci-pipeline
  namespace: ci
spec:
  workspaces:
    - name: shared-workspace
  tasks:
    - name: fetch-repo
      taskRef:
        name: git-clone
      workspaces:
        - name: output
          workspace: shared-workspace
      params:
        - name: url
          value: "https://github.com/company/app.git"
        - name: revision
          value: "main"

    - name: build-app
      taskRef:
        name: golang-build
      runAfter:
        - fetch-repo
      workspaces:
        - name: source
          workspace: shared-workspace
```

**`tekton-run.yaml`**

```yaml
apiVersion: tekton.dev/v1beta1
kind: PipelineRun
metadata:
  generateName: app-run-
  namespace: ci
spec:
  pipelineRef:
    name: app-ci-pipeline
  workspaces:
    - name: shared-workspace
      volumeClaimTemplate:
        spec:
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 2Gi
```

## Под капотом

При создании ресурса `PipelineRun` Tekton Controller анализирует граф зависимостей `runAfter`. Для каждого Task создается Kubernetes Pod. 

Все контейнеры шагов (`steps`) внутри этого пода монтируются к общей директории `emptyDir` или `PersistentVolumeClaim` (workspace). Порядок выполнения шагов строго гарантируется контроллером через инициализационные контейнеры и точки синхронизации файловой блокировки.

## Подводные камни

1. Использование нескольких Task с workspace типа `ReadWriteOnce` (RWO) на разных нодах кластера: K8s не может смонтировать один RWO-том на два пода на разных физических серверах одновременно.
2. Отсутствие сборщика мусора (Tekton Pruner): завершенные объекты `PipelineRun` и `TaskRun` накапливаются в Etcd, вызывая деградацию K8s API.
3. Долгий cold-start: каждый шаг скачивает свои образы контейнеров, если они не закешированы на ноде.

## На собеседовании

**Вопрос с собеседования:** В чем ключевое различие между Tekton и традиционными системами CI/CD вроде GitHub Actions или GitLab CI?
**Ответ:** GitHub Actions и GitLab CI — это монолитные SaaS/готовые платформы со своими агентами и серверами координации. 
Tekton — это **низкоуровневый K8s-фреймворк/спецификация**. Он не предназначен для конечного разработчика напрямую, а служит строительным фундаментом для Platform Engineering команд, строящих внутренние порталы разработки (IDP) в enterprise-компаниях. Многие платформы (OpenShift Pipelines, Jenkins X) работают на базе Tekton.
