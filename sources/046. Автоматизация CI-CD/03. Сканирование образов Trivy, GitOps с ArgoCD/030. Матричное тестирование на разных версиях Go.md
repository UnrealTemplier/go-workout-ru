# Матричное тестирование на разных версиях Go и операционных системах

## Условие

**[Матричное тестирование]**: Настрой матричный билд в CI: прогон тестов одновременно на Go 1.21, 1.22 и 1.23.

## Теория

При разработке библиотек, CLI-утилит и фундаментальных сервисов критически важно гарантировать работоспособность на разных версиях языка Go (поддержка N и N-1 по официальной политике Go) и различных операционных системах (Linux, macOS, Windows).

Матричная стратегия (`strategy: matrix`):
- Автоматически порождает декартово произведение параметров: 4 версии Go × 2 ОС = 8 параллельных джобов.
- `fail-fast: false`: падение одной комбинации не прерывает тестирование остальных, позволяя инженеру увидеть полный спектр несовместимостей.
- `max-parallel: 4`: позволяет ограничить число одновременно выполняемых джобов, чтобы не исчерпать лимиты раннеров организации.

## Решение по шагам

1. Создайте `.github/workflows/matrix-test.yml`.
2. В секции `strategy.matrix` укажите массив версий `go-version: ['1.21', '1.22', '1.23', '1.24']` и платформ `os: [ubuntu-latest, macos-latest]`.
3. Задайте `fail-fast: false`.
4. Настройте запуск тестов с флагом гонок: `go test -v -race ./...`.
5. Проверьте запуск 8 параллельных задач в интерфейсе GitHub Actions.

## Код решения

**`.github/workflows/matrix-test.yml`**

```yaml
name: Cross-Platform Matrix Test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    name: Go ${{ matrix.go-version }} on ${{ matrix.os }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        go-version: ['1.21', '1.22', '1.23', '1.24']
        os: [ubuntu-latest, macos-latest]

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: ${{ matrix.go-version }}

      - name: Verify Go Version
        run: go version

      - name: Run Tests with Race Detector
        run: go test -v -race ./...
```

**`sysinfo.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

// GetSystemInfo возвращает текущую ОС и архитектуру.
func GetSystemInfo() string {
	return fmt.Sprintf("OS: %s, Arch: %s, Go: %s", runtime.GOOS, runtime.GOARCH, runtime.Version())
}

func main() {
	fmt.Println(GetSystemInfo())
}
```

**`sysinfo_test.go`**

```go
package main

import (
	"runtime"
	"strings"
	"testing"
)

func TestGetSystemInfo(t *testing.T) {
	info := GetSystemInfo()
	if !strings.Contains(info, runtime.GOOS) {
		t.Fatalf("Ожидалось упоминание ОС %s, получено: %s", runtime.GOOS, info)
	}
}
```

## Под капотом

Раннер GitHub Actions преобразует матрицу в JSON-массив контекстов. Каждая джоба получает свой собственный изолированный runner environment.

При компиляции с флагом `-race` на macOS и Linux используется LLVM ThreadSanitizer. На архитектурах x86-64 и ARM64 флаг `-race` доступен из коробки, однако на 32-битных ОС или Windows ARM он может не поддерживаться, поэтому матрица позволяет изолировать ОС-специфичные тесты через `include` / `exclude` блоки.

## Подводные камни

1. Запуск флага `-race` на неподдерживаемых платформах (например, 32-битный x86): падение сборки с ошибкой `race detector not supported`.
2. Забытый `fail-fast: false`: если одна джоба на Go 1.21 падает, все остальные 7 джобов моментально прерываются, не давая понять, работает ли код на Go 1.24.
3. Исчерпание минут бесплатного GitHub Actions: матрица 5x5 на каждый коммит съедает квоту аккаунта за несколько дней.

## На собеседовании

**Вопрос с собеседования:** Что изменилось в семантике цикла `for ... := range` в Go 1.22, и почему матричное тестирование на версиях 1.21 и 1.22+ критично для открытых библиотек?
**Ответ:** В Go 1.22 была исправлена историческая проблема разделения переменной цикла (Loop Variable Scoping): теперь на каждой итерации цикла создается новая переменная, а не переиспользуется один и тот же адрес памяти. 
Если библиотека запускает горутины внутри `for val := range items`, в Go 1.21 без передачи `val` аргументом возникнет data race / замыкание на последнее значение, а в Go 1.22+ тот же код выполнится корректно. Матричный тест моментально вскрывает этот скрытый баг на Go 1.21.
