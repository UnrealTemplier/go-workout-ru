# Пайплайн по пушу в main: автоматический запуск тестов и сборки артефакта

## Условие

**[GitHub Actions / GitLab CI]**: Напиши пайплайн, который срабатывает при пуше в ветку `main`. Пайплайн должен запускать `go test ./...` и `golangci-lint run`.

## Теория

Ветка `main` (или `master`) в современной разработке рассматривается как защищенный релизный транк (Trunk-Based Development). Любой коммит в `main` обязан быть протестирован, проверен и собран в готовый бинарный артефакт.

Типовой конвейер по пушу в `main`:
1. Триггер: `on.push.branches: [main]`.
2. Job 1 (`test`): скачивание зависимостей, прогон unit-тестов с флагом `-race`.
3. Job 2 (`build`): сборка продакшн-бинарника с флагами оптимизации (`CGO_ENABLED=0 go build -ldflags="-w -s"`).
4. Загрузка собранного бинарника в хранилище артефактов GitHub Actions через `actions/upload-artifact@v4` для последующего деплоя.

## Решение по шагам

1. Создайте `.github/workflows/main.yml`.
2. Ограничьте триггер только веткой `main`.
3. Настройте зависимость задач через `needs: [test]`.
4. Соберите статический бинарник и выгрузите его как артефакт.

## Код решения

**`.github/workflows/main.yml`**

```yaml
name: Main Branch Pipeline

on:
  push:
    branches:
      - main

jobs:
  test:
    name: Run Unit Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true
      - name: Run Tests
        run: go test -v -race ./...

  build:
    name: Compile Release Binary
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true

      - name: Build Binary
        run: |
          mkdir -p dist
          CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-w -s" -o dist/app-linux-amd64 .

      - name: Upload Artifact
        uses: actions/upload-artifact@v4
        with:
          name: release-binary
          path: dist/app-linux-amd64
          retention-days: 7
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Main branch build ready for deployment!")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Директива `needs: test` строит направленный граф (DAG) выполнения. GitHub Actions не выделяет раннер для задачи `build`, пока `test` не завершится с кодом 0. Выгруженные через `upload-artifact` файлы передаются через защищенное S3-хранилище GitHub и доступны для скачивания или использования на этапе deploy.

## Подводные камни

1. Забытый `needs`: задачи `test` и `build` запустятся параллельно, и бинарник будет собран даже при падении тестов!
2. Слишком длинный срок хранения артефактов (`retention-days`), исчерпывающий дисковую квоту репозитория.

## На собеседовании

**Вопрос с собеседования:** «Зачем разделять пайплайн на две отдельные job (`test` и `build`) с директивой `needs`, а не выполнить всё в одной job последовательными шагами `run`?»
**Ответ:** 1) Принцип Fail-Fast: разделение изолирует логику и позволяет не тратить ресурсы раннера на сборку артефактов при падении тестов. 2) Параллелизм и независимость окружений: тесты могут требовать CGO и GCC, а билд компилируется в статическом чистом контейнере. 3) Четкая визуализация в UI: инженер мгновенно видит на графе, на каком именно этапе произошел сбой (тесты или компиляция).
