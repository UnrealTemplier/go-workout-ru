# Безопасность в CI: статический анализ уязвимостей через gosec, nancy и Trivy

## Условие

Добавь **security scan**: `gosec` (SAST), `nancy` (dependency vulnerabilities), `trivy` (container scan). Gate: `HIGH`/`CRITICAL` = failure. Покажи security-first pipeline.

## Теория

Концепция **DevSecOps (Shift-Left Security)** требует переноса проверок информационной безопасности на самые ранние этапы разработки.

Комплексный сканирующий пайплайн объединяет три уровня защиты:
1. **SAST (Static Application Security Testing) — `gosec`:**
   Анализирует исходный Go-код на известные паттерны уязвимостей (CWE): жестко зашитые пароли, небезопасные вызовы `os/exec`, использование слабых хэш-функций (MD5, SHA1), SQL-инъекции, незащищенный парсинг TLS.
2. **SCA (Software Composition Analysis) — `nancy` / `govulncheck`:**
   Проверяет дерево зависимостей (`go.mod`, `go.sum`) по базе известных уязвимостей.
3. **Container Image Scan — `trivy`:**
   Сканирует собранный Docker-образ на уязвимости системных пакетов ОС.

Security Gate: при обнаружении уязвимостей уровня `HIGH` или `CRITICAL` пайплайн автоматически падает с ошибкой (`exit code 1`), блокируя слияние кода.

## Решение по шагам

1. Создайте `.github/workflows/security.yml`.
2. Настройте запуск `gosec` с порогом строгости `-severity high`.
3. Добавьте шаг проверки зависимостей через `govulncheck`.
4. Настройте генерацию отчетов в формате SARIF для интеграции с вкладкой Security в GitHub.

## Код решения

**`.github/workflows/security.yml`**

```yaml
name: Security Audit & SAST

on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  security-audit:
    name: Run SAST & Dependency Scans
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true

      # 1. Запуск gosec (SAST)
      - name: Run Gosec Security Scanner
        uses: securego/gosec@master
        with:
          args: '-severity high -confidence high -fmt sarif -out results.sarif ./'

      # 2. Проверка зависимостей через официальный govulncheck
      - name: Run Govulncheck
        run: |
          go install golang.org/x/vuln/cmd/govulncheck@latest
          govulncheck ./...
```

ℹ️ Workflow статического анализа безопасности

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math/big"
)

// Безопасная генерация криптографически стойкого случайного токена
func generateSecureToken() (int64, error) {
	nBig, err := rand.Int(rand.Reader, big.NewInt(1000000))
	if err != nil {
		return 0, err
	}
	return nBig.Int64(), nil
}

func main() {
	token, _ := generateSecureToken()
	fmt.Printf("Cryptographically secure token: %d\n", token)
}
```

ℹ️ Безопасный код без использования уязвимого math/rand

**`Терминал`**

```bash
# Локальная проверка уязвимостей
go install github.com/securego/gosec/v2/cmd/gosec@latest
gosec -severity high ./...
```

## Под капотом

`gosec` анализирует AST-дерево программы по набору правил CWE (Common Weakness Enumeration). Например, правило `G404` отлавливает использование `math/rand` вместо `crypto/rand` в контекстах генерации токенов, а правило `G201` находит строковую конкатенацию в SQL-запросах вместо параметризованных placeholders (`$1`, `?`).

## Подводные камни

1. Использование `math/rand` для генерации паролей или session ID.
2. Подавление предупреждений безопасности директивами `// #nosec` без письменного согласования с отделом ИБ.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие SAST сканирования (gosec) от анализа зависимостей SCA (govulncheck/nancy)?»
**Ответ:** SAST анализирует код, написанный разработчиками вашей компании: он ищет дефекты безопасности в реализации логики (небезопасный парсинг путей к файлам, конкатенация SQL, слабые шифры, захардкоженные API-ключи). SCA (Software Composition Analysis) не анализирует вашу бизнес-логику, а проверяет внешние Open Source библиотеки из `go.mod` на наличие уже известных опубликованных уязвимостей (CVE) в мировых базах данных.
