# Оптимизация времени CI: раздельное кэширование ~/go/pkg/mod и ~/.cache/go-build

## Условие

**Кэширование в CI**: Скачивание модулей (`go mod download`) при каждом запуске пайплайна тратит время. Добавь шаг кэширования директорий `~/.cache/go-build` и `~/go/pkg/mod` (в GitHub Actions у `setup-go` есть встроенный флаг `cache: true`). Замерь, на сколько секунд ускорилась сборка.

## Теория

При проектировании высокопроизводительных пайплайнов в больших монорепозиториях время прохождения проверок напрямую влияет на скорость релиза (DORA метрика Time to Restore / Lead Time for Changes).

Скачивание модулей (`go mod download`) и компиляция занимают значительную часть времени.
Использование связки двух каталогов кэша:
- `~/go/pkg/mod`
- `~/.cache/go-build`

с раздельными ключами кэширования:
1. Кэш модулей привязывается строго к хэшу файла `go.sum`:
   `key: ${{ runner.os }}-go-mod-${{ hashFiles('**/go.sum') }}`
2. Кэш компиляции привязывается к хэшу `go.sum` и коммиту Git, с fallback на предыдущий кэш:
   `restore-keys: ${{ runner.os }}-go-build-`

Это позволяет добиться максимального коэффициента попадания в кэш (Cache Hit Ratio > 95%).

## Решение по шагам

1. Опишите независимые шаги кэширования для модулей и для build cache.
2. Проверьте время первого «холодного» запуска.
3. Проверьте время повторного «горячего» запуска пайплайна.

## Код решения

**`.github/workflows/optimized-cache.yml`**

```yaml
name: Production Optimized Cache

on: [push, pull_request]

jobs:
  fast-ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: false

      # 1. Кэш Go Modules (инвалидируется ТОЛЬКО при изменении go.sum)
      - name: Cache Go Modules
        uses: actions/cache@v4
        with:
          path: ~/go/pkg/mod
          key: ${{ runner.os }}-gomod-${{ hashFiles('**/go.sum') }}
          restore-keys: |
            ${{ runner.os }}-gomod-

      # 2. Кэш компилятора Go Build Cache
      - name: Cache Go Build
        uses: actions/cache@v4
        with:
          path: ~/.cache/go-build
          key: ${{ runner.os }}-gobuild-${{ github.sha }}
          restore-keys: |
            ${{ runner.os }}-gobuild-

      - name: Fast Test Run
        run: go test -v ./...
```

ℹ️ Раздельное высокоэффективное кэширование

## Под капотом

Разделение кэшей изолирует сетевой кэш от компиляционного. Если изменился один `.go` файл, кэш `gomod` совпадает на 100% (мгновенное попадание), а кэш `gobuild` восстанавливается по префиксу `restore-keys`, перекомпилируя только дельту измененного пакета.

## Подводные камни

1. Кэширование всей директории `~/.cache` целиком, что может захватить нерелевантные временные файлы ОС.
2. Неверный путь к кэшу компилятора на macOS (`~/Library/Caches/go-build`) или Windows (`%LocalAppData%\go-build`).

## На собеседовании

**Вопрос с собеседования:** «Где физически располагаются директории `GOPATH` и `GOCACHE` на операционных системах Linux, macOS и Windows по умолчанию?»
**Ответ:** По умолчанию:
- `GOPATH`: `~/go` на Linux и macOS; `%USERPROFILE%\go` на Windows. Модули лежат в `$GOPATH/pkg/mod`.
- `GOCACHE`: `~/.cache/go-build` на Linux; `~/Library/Caches/go-build` на macOS; `%LocalAppData%\go-build` на Windows. Точный путь в любой ОС можно узнать командой `go env GOCACHE`.
