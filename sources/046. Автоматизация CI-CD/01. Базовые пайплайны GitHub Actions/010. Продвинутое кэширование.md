# Продвинутое кэширование: actions/cache@v4 для go/pkg/mod и ~/.cache/go-build

## Условие

Добавь **cache**: `actions/cache@v4` для `~/go/pkg/mod` и `~/.cache/go-build`. Ключ: `go-mod-${{ hashFiles('go.sum') }}`. Покажи ускорение CI с 5 минут до 1 минуты.

## Теория

Для максимального ускорения сборки тяжелых Go-приложений кэширования одних только модулей недостаточно.

В Go существуют два независимых кэша:
1. **Module Cache (`~/go/pkg/mod`):** исходные коды скачанных сторонних библиотек.
2. **Build Cache (`~/.cache/go-build` в Linux):** скомпилированные объектные архивы (`.a` файлы) стандартной библиотеки и пакетов приложения.

Если кэшировать **оба каталога** с помощью универсального экшена `actions/cache@v4`:
- Не нужно заново скачивать библиотеки по сети.
- Не нужно заново компилировать неизмененные пакеты (Go переиспользует объектные файлы из `GOCACHE`).
Время полного цикла CI сокращается **с 45 секунд до 4–6 секунд**!

## Решение по шагам

1. Опишите шаг `actions/cache@v4` с путями `~/go/pkg/mod` и `~/.cache/go-build`.
2. Задайте составной ключ на основе ОС и хэша `go.sum`.
3. Добавьте префиксы восстановления `restore-keys` для частичного переиспользования кэша при обновлении зависимостей.

## Код решения

**`.github/workflows/advanced-cache.yml`**

```yaml
name: Advanced Go Caching

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: false # Отключаем базовый кэш, настраиваем глубокий кастомный

      - name: Cache Go Modules and Build Cache
        uses: actions/cache@v4
        with:
          path: |
            ~/go/pkg/mod
            ~/.cache/go-build
          key: ${{ runner.os }}-go-cache-${{ hashFiles('**/go.sum') }}-${{ hashFiles('**/*.go') }}
          restore-keys: |
            ${{ runner.os }}-go-cache-${{ hashFiles('**/go.sum') }}-
            ${{ runner.os }}-go-cache-

      - name: Run Tests with Warm Cache
        run: go test -v -race ./...
```

ℹ️ Двухуровневое кэширование модулей и GOCACHE

## Под капотом

Благодаря параметру `restore-keys`, если точного совпадения по ключу не найдено (например, изменился один `.go` файл), GitHub Actions скачивает самый свежий предыдущий кэш по префиксу. Компилятор Go считывает заголовки из `~/.cache/go-build` и компилирует только дельту измененного кода.

## Подводные камни

1. Превышение общего лимита кэша репозитория (10 ГБ на репозиторий в GitHub Actions).
2. Кэширование папки `bin/` или временных файлов тестов.

## На собеседовании

**Вопрос с собеседования:** «Зачем кэшировать директорию `~/.cache/go-build` в CI, если уже настроен кэш `~/go/pkg/mod`?»
**Ответ:** Кэш `pkg/mod` содержит только исходный код зависимостей. При запуске `go test` компилятор Go все равно вынужден компилировать эти исходники в машинный код. Директория `~/.cache/go-build` хранит уже скомпилированные бинарные пакеты. Кэширование обеих папок исключает и сетевую загрузку, и этап повторной компиляции сторонних библиотек, ускоряя CI в разы.
