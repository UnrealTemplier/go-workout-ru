# Ловушка сборщика мусора при арифметике указателей: разрыв строки вычисления

## Условие

Попробуйте сделать арифметику указателей через конверсию unsafe.Pointer -> uintptr -> прибавить offset -> обратно в unsafe.Pointer с разрывом строки. Объясните фатальную ошибку сохранения uintptr во временную переменную.

### Исходная формулировка

**Pointer arithmetic (опасно!)**: Попробуйте сделать "арифметику указателей" через конверсию `unsafe.Pointer` → `uintptr` → прибавить offset → обратно в `unsafe.Pointer`. **Почему это сломается с moving GC?**

## Теория

Смертельная ошибка в unsafe Go:
```go
// АНТИПАТТЕРН: ВЫЗОВЕТ ПАДЕНИЕ В ПРОДАКШЕНЕ!
u := uintptr(unsafe.Pointer(obj)) // 1. Конверсия в число
// ... здесь GC может запустить сборку или стек может вырасти! ...
p := unsafe.Pointer(u + offset)   // 2. Обратная конверсия
```

Почему это гарантированная катастрофа:
1. **Сборщик мусора НЕ видит `uintptr`:** Переменная `u` — обычное целое число. Если объект `obj` больше нигде не используется, GC признает его мусором и удалит прямо между строкой 1 и 2!
2. **Перемещение стека горутины (Stack Growth):** Если горутина расширяет стек, рантайм копирует фрейм в новый буфер. Все указатели `*T` и `unsafe.Pointer` обновляются на новые адреса. Переменная `u` сохранит старый невалидный адрес стека!
3. **Легальный способ:**
   ```go
   p := unsafe.Pointer(uintptr(unsafe.Pointer(obj)) + offset)
   ```
   В одном выражении компилятор гарантирует сохранение объекта живым до завершения строки.

## Решение по шагам

1. Напишите код с разрывом строки и поясняющими комментариями.
2. Продемонстрируйте легальный однострочный синтаксис.
3. Продемонстрируйте современную замену через `unsafe.Add`.

## Код решения

**`uintptr_trap.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type DataBlock struct {
	A int64
	B int64
}

func main() {
	d := &DataBlock{A: 10, B: 20}

	fmt.Println("=== Ловушка сохранения uintptr во временную переменную ===")

	// ❌ ОПАСНО: разделение на несколько строк
	// u := uintptr(unsafe.Pointer(d))
	// runtime.GC() // здесь GC может переместить или удалить объект!
	// ptrB := (*int64)(unsafe.Pointer(u + 8))

	//  ПРАВИЛЬНО (по спецификации Go): вычисление строго в одной строке
	ptrB := (*int64)(unsafe.Pointer(uintptr(unsafe.Pointer(d)) + unsafe.Offsetof(d.B)))
	fmt.Printf("Поле B (вычислено в одну строку): %d\n", *ptrB)

	//  ИДЕАЛЬНО (Go 1.17+): использование встроенной unsafe.Add
	ptrBModern := (*int64)(unsafe.Add(unsafe.Pointer(d), unsafe.Offsetof(d.B)))
	fmt.Printf("Поле B (через unsafe.Add):       %d\n", *ptrBModern)
}
```

ℹ️ Сравнение опасного разрыва uintptr и безопасных методов арифметики указателей

## Под капотом

В компиляторе Go фаза `escape analysis` и `liveness analysis` отслеживает времена жизни указателей. Правило «все в одной строке» специально распознается компилятором, продлевая liveness объекта до конца стейтмента.

## Подводные камни

Утилита `go vet` автоматически выявляет этот баг: предупреждение `possible misuse of unsafe.Pointer` строго запрещает сохранение `uintptr`.

## На собеседовании

**Вопрос:** Почему go vet выдает ошибку `possible misuse of unsafe.Pointer` на код `u := uintptr(p); p2 := unsafe.Pointer(u)`?
**Ответ:** Потому что хранение адреса в переменной типа uintptr разрывает цепочку отслеживания объекта сборщиком мусора. Между строками объект может быть перемещен рантаймом (при росте стека горутины) или утилизирован сборщиком как недостижимый. Спецификация Go разрешает конверсию unsafe.Pointer -> uintptr только внутри единого выражения арифметики или системного вызова.
