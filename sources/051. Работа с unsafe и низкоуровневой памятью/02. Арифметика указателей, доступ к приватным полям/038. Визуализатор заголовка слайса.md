# Визуализатор заголовка слайса

## Условие

Напишите «визуализатор заголовка слайса»: создайте структуру, дублирующую `reflect.SliceHeader`, и через `unsafe.Pointer` покажите, что слайс — это указатель на память, длина и емкость. Измените `len` слайса через эту структуру и покажите, что `len()` встроенной функции изменился.

### Исходная формулировка

Напишите «визуализатор заголовка слайса»: создайте структуру, дублирующую `reflect.SliceHeader`, и через `unsafe.Pointer` приведите `[]int` к этой структуре. Выведите адрес underlying array, Len и Cap. Объясните, почему `Data` имеет тип `uintptr` в `reflect`, но вы должны работать с `unsafe.Pointer`.

## Теория

В рантайме Go слайс представляется внутренней структурой `slice`:
```go
type slice struct {
    array unsafe.Pointer
    len   int
    cap   int
}
```
Исторически в пакете `reflect` существовал тип `reflect.SliceHeader`, однако начиная с Go 1.20 он объявлен deprecated из-за проблем с отслеживанием `uintptr Data`.
Создание собственной эквивалентной структуры позволяет наглядно изучить устройство слайса и продемонстрировать мутацию метаданных напрямую через память.

## Решение по шагам

1. Определите структуру `CustomSliceHeader struct { Data unsafe.Pointer; Len int; Cap int }`.
2. Создайте слайс `s := make([]int, 3, 10)` со значениями `{10, 20, 30}`.
3. Получите указатель на заголовок слайса: `header := (*CustomSliceHeader)(unsafe.Pointer(&s))`.
4. Распечатайте поля `Data`, `Len`, `Cap`.
5. Измените `header.Len = 5` и присвойте значения новым элементам.
6. Вызовите `len(s)` и `fmt.Println(s)`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// CustomSliceHeader отражает внутреннее представление слайса в рантайме Go
type CustomSliceHeader struct {
	Data unsafe.Pointer
	Len  int
	Cap  int
}

func main() {
	s := make([]int, 3, 10)
	s[0] = 100
	s[1] = 200
	s[2] = 300

	fmt.Printf("Исходный слайс: %v (len=%d, cap=%d)\n", s, len(s), cap(s))

	// Получаем доступ к заголовку слайса
	header := (*CustomSliceHeader)(unsafe.Pointer(&s))
	fmt.Printf("Slice Header -> Data: %p, Len: %d, Cap: %d\n", header.Data, header.Len, header.Cap)

	// Расширяем видимую длину слайса без вызова append()
	header.Len = 5

	// Заполняем новые элементы
	s[3] = 400
	s[4] = 500

	fmt.Printf("После хака длины: %v (len=%d, cap=%d)\n", s, len(s), cap(s))
}
```

ℹ️ Увеличение длины слайса в пределах его емкости (Len <= Cap) полностью валидно с точки зрения выделенной памяти.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходный слайс: [100 200 300] (len=3, cap=10)
# Slice Header -> Data: 0x..., Len: 3, Cap: 10
# После хака длины: [100 200 300 400 500] (len=5, cap=10)
```

## Под капотом

Переменная типа `[]T` на стеке занимает 24 байта (3 слова по 8 байт). При передаче в функции или получении адреса `&s` компилятор работает именно с этим 24-байтным блоком. Изменение поля `Len` по смещению `+8` байт от адреса `&s` немедленно отражается на поведении встроенных функций `len()` и операторов среза `s[...]`.

## Подводные камни

Ни в коем случае нельзя устанавливать `Len > Cap`. Это приведет к тому, что операции со слайсом выйдут за пределы аллоцированного буфера памяти, повредив соседние объекты в куче или вызвав panic.

## На собеседовании

**Вопрос с собеседования:** Почему `reflect.SliceHeader` был помечен как deprecated в Go 1.20 и что предложено взамен?
**Ответ:** `reflect.SliceHeader` использовал `uintptr Data`. Если слайс был единственным держателем объекта в куче, каст к `SliceHeader` терял указатель для GC, что могло спровоцировать освобождение памяти прямо во время работы. Взамен появились функции `unsafe.Slice` и `unsafe.SliceData`, оперирующие типизированными указателями.
