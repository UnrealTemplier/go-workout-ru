# Checking Alignment и оптимизация padding структур

## Условие

Используйте `unsafe.Alignof` для проверки выравнивания типов.
Создайте структуру с плохим alignment и изучите padding:
```go
type BadStruct struct {
    a bool   // 1 byte
    b int64  // 8 bytes
    c bool   // 1 byte
    d int64  // 8 bytes
}
```
Сравните размер с `GoodStruct`, в которой поля переупорядочены. Выведите размер обоих через `unsafe.Sizeof`.

### Исходная формулировка

**Checking alignment**: Используйте `unsafe.Alignof` для проверки выравнивания типов. Создайте структуру с плохим alignment и изучите padding.

## Теория

Процессоры обращаются к памяти наиболее эффективно, когда адрес переменной кратен её естественному выравниванию (`alignment`). Для 64-битных чисел (`int64`, указатели) выравнивание равно 8 байтам, для `int32` — 4 байта, для `bool`/`byte` — 1 байт.

Если поле не выровнено, компилятор вынужден вставлять пустые байты (**padding** — внутренние и хвостовые отступы). 
Неоптимальный порядок полей в структуре может увеличить размер объекта в 2–3 раза, что приводит к раздуванию кэша процессора L1/L2/L3 и лишним аллокациям памяти.

## Решение по шагам

1. Объявите `BadStruct` с чередованием `bool` и `int64`.
2. Объявите `GoodStruct`, сгруппировав `int64` вместе и `bool` вместе.
3. Проверьте `unsafe.Alignof` для каждого поля и всей структуры.
4. Выведите `unsafe.Sizeof` и смещения `unsafe.Offsetof` каждого поля.
5. Продемонстрируйте экономию памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type BadStruct struct {
	a bool  // 1 байт + 7 байт padding
	b int64 // 8 байт
	c bool  // 1 байт + 7 байт padding
	d int64 // 8 байт
}

type GoodStruct struct {
	b int64 // 8 байт
	d int64 // 8 байт
	a bool  // 1 байт
	c bool  // 1 байт + 6 байт tail padding
}

func main() {
	var bad BadStruct
	var good GoodStruct

	fmt.Printf("BadStruct:  размер = %2d байт, alignment = %d\n", unsafe.Sizeof(bad), unsafe.Alignof(bad))
	fmt.Printf("  a: offset = %2d, size = %d\n", unsafe.Offsetof(bad.a), unsafe.Sizeof(bad.a))
	fmt.Printf("  b: offset = %2d, size = %d\n", unsafe.Offsetof(bad.b), unsafe.Sizeof(bad.b))
	fmt.Printf("  c: offset = %2d, size = %d\n", unsafe.Offsetof(bad.c), unsafe.Sizeof(bad.c))
	fmt.Printf("  d: offset = %2d, size = %d\n", unsafe.Offsetof(bad.d), unsafe.Sizeof(bad.d))

	fmt.Println("----------------------------------------")
	fmt.Printf("GoodStruct: размер = %2d байт, alignment = %d\n", unsafe.Sizeof(good), unsafe.Alignof(good))
	fmt.Printf("  b: offset = %2d, size = %d\n", unsafe.Offsetof(good.b), unsafe.Sizeof(good.b))
	fmt.Printf("  d: offset = %2d, size = %d\n", unsafe.Offsetof(good.d), unsafe.Sizeof(good.d))
	fmt.Printf("  a: offset = %2d, size = %d\n", unsafe.Offsetof(good.a), unsafe.Sizeof(good.a))
	fmt.Printf("  c: offset = %2d, size = %d\n", unsafe.Offsetof(good.c), unsafe.Sizeof(good.c))

	saving := float64(unsafe.Sizeof(bad)-unsafe.Sizeof(good)) / float64(unsafe.Sizeof(bad)) * 100
	fmt.Printf("\nЭкономия памяти: %.1f%% (32 байта -> 24 байта)\n", saving)
}
```

ℹ️ Упорядочивание полей от большего размера к меньшему сводит padding к минимуму.

**`Терминал`**

```bash
go run main.go
# Вывод:
# BadStruct:  размер = 32 байт, alignment = 8
#   a: offset =  0, size = 1
#   b: offset =  8, size = 8
#   c: offset = 16, size = 1
#   d: offset = 24, size = 8
# ----------------------------------------
# GoodStruct: размер = 24 байт, alignment = 8
#   b: offset =  0, size = 8
#   d: offset =  8, size = 8
#   a: offset = 16, size = 1
#   c: offset = 17, size = 1
#
# Экономия памяти: 25.0% (32 байта -> 24 байта)
```

## Под капотом

Размер структуры обязан быть кратен ее максимальному выравниванию (`max(alignof(field_i))`). Для `GoodStruct` максимальное выравнивание равно 8 (`int64`). Сумма полей: \(8 + 8 + 1 + 1 = 18\) байт. Ближайшее число, кратное 8 — это 24. Компилятор добавляет 6 байт хвостового отступа (tail padding), чтобы в массиве `[]GoodStruct` каждый следующий элемент также начинался с адреса, кратного 8.

## Подводные камни

Пустые структуры (`struct{}`) в конце другой структуры имеют размер 0, но компилятор добавляет 1 байт отступа, чтобы указатель за пределами структуры не указывал на следующий аллоцированный объект в куче.

## На собеседовании

**Вопрос с собеседования:** Какими линтерами в CI/CD автоматизируют поиск неоптимального выравнивания полей структур?
**Ответ:** Линтерами `fieldalignment` (из пакета `golang.org/x/tools/go/analysis/passes/fieldalignment`) или мета-линтером `golangci-lint` с включенным правилом `govet` (`fieldalignment`). Он умеет автоматически переупорядочивать поля с флагом `-fix`.
