# Арифметика указателей через uintptr

## Условие

Создайте массив `arr := [4]int32{10, 20, 30, 40}`.
* Получите адрес первого элемента `&arr[0]`.
* Преобразуйте его в `unsafe.Pointer`, затем в `uintptr`.
* Прибавьте `2 * unsafe.Sizeof(arr[0])` для получения адреса 3-го элемента (индекс 2).
* Преобразуйте обратно в `*int32` и прочитайте значение (должно быть 30).
* Измените значение через указатель на 99. Убедитесь, что `arr[2]` изменился.

### Исходная формулировка

**Арифметика указателей**: Создайте массив `arr := [4]int32{10, 20, 30, 40}`.
* Получите адрес первого элемента `&arr[0]`.
* Преобразуйте его в `uintptr`.
* Прибавьте к этому значению размер типа `int32` с помощью `unsafe.Sizeof(arr[0])`.
* Преобразуйте полученный результат обратно в `unsafe.Pointer` и затем в указатель `*int32`.
* Считайте значение и убедитесь, что вы получили доступ ко второму элементу массива (`20`).

## Теория

В языке Go намеренно отсутствует прямая синтаксическая арифметика указателей (`ptr++` или `ptr + offset`), как в C/C++, для обеспечения типобезопасности и корректной работы сборщика мусора (GC).

Однако в низкоуровневом системном программировании доступ к смежным элементам памяти осуществляется через переходный тип `uintptr`. 
Паттерн вычисления адреса строго регламентирован спецификацией Go (unsafe Rule 3):
`unsafe.Pointer(uintptr(p) + offset)`
Сложение с `uintptr` обязано происходить **в рамках одного выражения** без промежуточного сохранения `uintptr` в переменную, чтобы рантим и GC не потеряли ссылку на живой объект при возможном перемещении стека.

## Решение по шагам

1. Создайте массив `[4]int32` со значениями `{10, 20, 30, 40}`.
2. Возьмите адрес нулевого элемента `&arr[0]`, приведите к `unsafe.Pointer`, затем к целочисленному типу адреса `uintptr`.
3. Добавьте к адресу смещение `2 * unsafe.Sizeof(arr[0])` (в одном выражении).
4. Преобразуйте результат обратно в `unsafe.Pointer` и затем в `*int32`.
5. Прочитайте значение по указателю, убедитесь, что оно равно 30, и запишите новое значение 99.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	arr := [4]int32{10, 20, 30, 40}
	fmt.Printf("Исходный массив: %v\n", arr)

	// Шаг 1-4: Арифметика указателей в одном выражении
	elemSize := unsafe.Sizeof(arr[0]) // 4 байта для int32
	ptrThird := (*int32)(unsafe.Pointer(uintptr(unsafe.Pointer(&arr[0])) + 2*elemSize))

	fmt.Printf("Значение по смещению (индекс 2): %d\n", *ptrThird)

	// Шаг 5: Мутация памяти через указатель
	*ptrThird = 99
	fmt.Printf("Массив после модификации: %v (arr[2] = %d)\n", arr, arr[2])
}
```

ℹ️ Паттерн unsafe.Pointer(uintptr(p) + offset) гарантирует атомарность операции с точки зрения компилятора.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходный массив: [10 20 30 40]
# Значение по смещению (индекс 2): 30
# Массив после модификации: [10 20 99 40] (arr[2] = 99)
```

## Под капотом

Компилятор Go при трансляции `unsafe.Pointer(uintptr(p) + offset)` генерирует обычную ассемблерную инструкцию LEAQ/ADDQ. 
Тип `uintptr` — это обычное беззнаковое целое число, размер которого равен машинному слову архитектуры (8 байт на x86_64/arm64). GC не считает `uintptr` указателем (не сканирует его в write barrier и mark phase). Если между получением `uintptr` и обратным кастом в `unsafe.Pointer` произойдет аллокация или рост стека, GC может переместить стек или освободить память в куче, сделав адрес висячим.

## Подводные камни

Никогда не сохраняйте промежуточный `uintptr` в локальную переменную перед вызовом функции или между строками. Если горутина переключится или выделит память на стеке, адрес в `uintptr` станет невалидным (stale pointer), что приведет к скрытому повреждению памяти (silent memory corruption).

## На собеседовании

**Вопрос с собеседования:** Почему в Go нельзя разделить выражение `p = unsafe.Pointer(uintptr(p) + offset)` на две строки `u := uintptr(p); p = unsafe.Pointer(u + offset)`?
**Ответ:** Переменная `u` имеет тип `uintptr`, который GC считает обычным числом. Во время выполнения между строками может случиться GC safepoint, уплотнение или перемещение стека горутины. Указатель на оригинальный объект сдвинется, а число `u` останется прежним. Обратное преобразование создаст указатель на старый (уже чужой или освобожденный) участок памяти.
