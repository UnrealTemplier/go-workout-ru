# Опасности обратного хака StringToBytes и сегмент памяти .rodata

## Условие

Используйте unsafe.Slice(unsafe.StringData(str), len(str)), чтобы превратить строку в []byte без копирования. Продемонстрируйте в коде, почему запись в срез, полученный из константы, вызывает аппаратный SIGSEGV.

### Исходная формулировка

**Обратный хак (String to Byte Slice)**: Используй `unsafe.Slice(unsafe.StringData(str), len(str))`, чтобы превратить строку в `[]byte` без копирования. *Важно:* попытайся изменить элемент полученного среза (`b[0] = 'A'`) и поймай аппаратную ошибку `SIGSEGV` (строки в Go лежат в read-only памяти!).

## Теория

Разница между строками в оперативной памяти:

1. **Динамическая строка (Heap/Stack allocated):**
   * Создана во время работы программы (например, `strings.Clone`, `fmt.Sprintf` или чтение из сети).
   * Память размещена в куче с флагами `PROT_READ | PROT_WRITE`.
   * Модификация среза технически возможна, но нарушает инварианты хэш-таблиц.

2. **Строковый литерал (Константа из исходного кода):**
   * Например: `const s = "immutable"`
   * Компилятор размещает байты в секции `.rodata` (Read-Only Data) исполняемого файла.
   * Ядро Linux загружает страницы `.rodata` в память с атрибутами **только для чтения**.
   * При попытке выполнить ассемблерную инструкцию `MOVB 'X', (AX)` процессор аппаратно возбуждает прерывание `General Protection Fault`, и ядро ОС мгновенно уничтожает процесс сигналом `SIGSEGV`.

## Решение по шагам

1. Напишите функцию `StringToBytes(s string) []byte`.
2. Создайте динамическую строку и покажите, что память перезаписываема.
3. Создайте строковый литерал и объясните механизм аппаратной защиты `.rodata`.

## Код решения

**`rodata_protection.go`**

```go
package main

import (
	"fmt"
	"strings"
	"unsafe"
)

func StringToBytes(s string) []byte {
	return unsafe.Slice(unsafe.StringData(s), len(s))
}

func main() {
	fmt.Println("=== Исследование сегмента .rodata и мутации строк ===")

	// 1. Динамическая строка (выделена в куче с правами на запись)
	dynamicStr := strings.Clone("dynamic_content")
	dynBytes := StringToBytes(dynamicStr)
	dynBytes[0] = 'D' // Работает, так как память в RW куче
	fmt.Printf("Динамическая строка успешно мутирована: %s\n", dynamicStr)

	// 2. Строковый литерал (находится в .rodata только для чтения)
	const literalStr = "constant_literal"
	litBytes := StringToBytes(literalStr)

	fmt.Printf("Строковый литерал: %s (адрес памяти: %p)\n", literalStr, unsafe.StringData(literalStr))
	fmt.Println("Попытка litBytes[0] = 'C' вызовет немедленный SIGSEGV (защита ядра ОС)!")

	// Раскомментирование следующей строки вызовет крах процесса:
	// litBytes[0] = 'C' // -> fatal error: unexpected signal during runtime execution [signal SIGSEGV]
	_ = litBytes
}
```

ℹ️ Демонстрация различий между динамической кучей и защищенным сегментом .rodata

## Под капотом

В Linux утилита `readelf -S <binary>` показывает секцию `.rodata` с флагами `A` (Alloc), но без флага `W` (Write). При вызове `mprotect` ядро устанавливает бит защиты страницы в таблице страниц MMU.

## Подводные камни

Внешние библиотеки, злоупотребляющие `StringToBytes` для передачи данных в `io.Writer`, могут внезапно упасть с крахом, если вызывающий код передал строковую константу, а `Writer` попытался изменить буфер.

## На собеседовании

**Вопрос:** Почему приведение строки к []byte через unsafe иногда позволяет изменять байты, а иногда аварийно роняет процесс с SIGSEGV?
**Ответ:** Это зависит от того, где расположена строка в памяти. Если строка создана динамически (в куче), страницы памяти имеют права на запись (RW), и мутация физически пройдет. Если же строка является строковым литералом из кода программы, она загружена в секцию памяти .rodata (Read-Only), и любая попытка записи вызывает аппаратный Page Fault с сигналом SIGSEGV от ядра ОС.
