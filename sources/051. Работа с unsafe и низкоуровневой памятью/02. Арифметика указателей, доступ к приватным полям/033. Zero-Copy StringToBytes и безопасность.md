# Zero-Copy StringToBytes и безопасность иммутабельности

## Условие

Реализуйте обратное преобразование — `StringToBytes(s string) []byte` без копирования. Объясните, почему Go не позволяет изменять такой срез и к чему приведет запись в него.

### Исходная формулировка

Реализуйте обратное преобразование — `StringToBytes(s string) []byte` без копирования. Объясните, почему Go не позволяет модифицировать результат (runtime не паникует, но это UB), и как `unsafe` обходит контракт языка.

## Теория

Преобразование `string` в `[]byte` через стандартный синтаксис `[]byte(s)` всегда выполняет аллокацию памяти в куче и копирование байт (`runtime.stringtoslicebyte`), поскольку строки в Go иммутабельны, а срезы байт мутабельны.

Zero-copy трюк позволяет получить `[]byte`, указывающий на те же байты строки, используя `unsafe.StringData` и `unsafe.Slice` (в Go 1.20+).
Однако запись в такой срез байт нарушает инвариант иммутабельности строк и может вызвать `SIGSEGV` (Segmentation Fault), если строка расположена в секции `.rodata` бинарного файла.

## Решение по шагам

1. Напишите функцию `StringToBytes(s string) []byte`.
2. Используйте `unsafe.StringData(s)` для получения указателя `*byte` на данные строки.
3. Сконструируйте срез байт с помощью `unsafe.Slice(dataPtr, len(s))`.
4. Продемонстрируйте чтение данных без единой аллокации.
5. Объясните опасность попытки записи в полученный срез.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// StringToBytes выполняет zero-copy преобразование строки в байты
func StringToBytes(s string) []byte {
	if len(s) == 0 {
		return nil
	}
	return unsafe.Slice(unsafe.StringData(s), len(s))
}

func main() {
	msg := "Hello, HighLoad Zero-Copy!"
	b := StringToBytes(msg)

	fmt.Printf("Строка: %q\n", msg)
	fmt.Printf("Байты: %s (len=%d, cap=%d)\n", b, len(b), cap(b))

	// Проверяем совпадение адресов памяти
	strPtr := unsafe.StringData(msg)
	bytePtr := unsafe.SliceData(b)
	fmt.Printf("Адрес строки: %p, адрес среза: %p (совпадают: %t)\n", strPtr, bytePtr, strPtr == bytePtr)

	// ВНИМАНИЕ: Попытка записи b[0] = 'X' для строкового литерала приведет к crash:
	// "unexpected fault address ... fatal error: fault"
}
```

ℹ️ unsafe.StringData и unsafe.SliceData — стандартный и безопасный способ работы с указателями в Go 1.20+.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Строка: "Hello, HighLoad Zero-Copy!"
# Байты: Hello, HighLoad Zero-Copy! (len=26, cap=26)
# Адрес строки: 0x..., адрес среза: 0x... (совпадают: true)
```

## Под капотом

Строковые литералы (`"Hello"`) запекаются компилятором в неизменяемую область памяти ELF/Mach-O бинарника — секцию `.rodata` (read-only data). Страницы виртуальной памяти для `.rodata` помечены флагом защиты памяти `PROT_READ` (без `PROT_WRITE`). Когда процессор пытается выполнить инструкцию `MOV [rax], dl` по адресу в read-only странице, MMU генерирует аппаратное прерывание Page Fault, и ядро ОС завершает процесс сигналом `SIGSEGV`.

## Подводные камни

Использовать `StringToBytes` допустимо ТОЛЬКО для операций чтения (например, передача в сетевой сокет, вычисление контрольной суммы CRC32/SHA256, сериализация). Любая запись в полученный слайс является грубейшей ошибкой.

## На собеседовании

**Вопрос с собеседования:** Почему стандартная библиотека Go не предоставляет публичную функцию `StringToBytes(s string) []byte` без аллокаций?
**Ответ:** Потому что Go проектировался как типобезопасный язык с гарантией неизменяемости строк. Наличие общедоступной функции `StringToBytes` открывает возможность непреднамеренной модификации строк, что разрушит безопасность параллельного доступа к строкам из разных горутин и сломает гарантии ключей в `map`.
