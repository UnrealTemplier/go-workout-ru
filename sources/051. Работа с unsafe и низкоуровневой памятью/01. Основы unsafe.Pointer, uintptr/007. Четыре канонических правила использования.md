# Четыре канонических правила использования unsafe.Pointer

## Условие

Изучите официальную спецификацию пакета unsafe. Реализуйте и объясните 4 легальных паттерна конверсий unsafe.Pointer, гарантирующих корректность работы компилятора и GC.

### Исходная формулировка

**Правила конверсии**: Изучите 4 легальных способа конверсии в unsafe:
* `*T` → `unsafe.Pointer` (и обратно)
* `unsafe.Pointer` → `uintptr` (и обратно, но опасно!)
* `unsafe.Pointer` → `unsafe.Pointer` другого типа
* `reflect.SliceHeader`/`StringHeader` → `unsafe.Pointer`

## Теория

Официальная документация `package unsafe` строго регламентирует допустимые паттерны. Нарушение правил ведет к Undefined Behavior:

1. **Правило 1:** Конверсия `*T1` в `unsafe.Pointer` и затем в `*T2` (при условии совместимости размеров и выравнивания).
2. **Правило 2:** Конверсия `unsafe.Pointer` в `uintptr` ИСКЛЮЧИТЕЛЬНО для вызова системных функций (например, `syscall.Syscall(..., uintptr(p))`).
3. **Правило 3:** Арифметика указателей в одном выражении:
   `p = unsafe.Pointer(uintptr(p) + offset)`
   **Строго в одной строке!** Нельзя разделять на отдельные переменные.
4. **Правило 4:** Преобразование `reflect.SliceHeader.Data` / `reflect.StringHeader.Data` (в Go 1.20+ заменено на `unsafe.Slice` и `unsafe.String`).

## Решение по шагам

1. Продемонстрируйте правило 1 (приведение указателей типов).
2. Продемонстрируйте правило 3 (арифметика в одной строке).
3. Продемонстрируйте безопасный вызов системных функций по правилу 2.

## Код решения

**`canonical_rules.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type Header struct {
	Magic uint32
	Len   uint32
}

func main() {
	fmt.Println("=== 4 Канонических правила использования unsafe.Pointer ===")

	// Правило 1: *T1 -> unsafe.Pointer -> *T2
	h := Header{Magic: 0xDEADBEEF, Len: 128}
	rawMagic := *(*uint32)(unsafe.Pointer(&h))
	fmt.Printf("Правило 1 (*T1 -> *T2): Magic = 0x%X\n", rawMagic)

	// Правило 3: Арифметика указателей СТРОГО в одном выражении
	basePtr := unsafe.Pointer(&h)
	// Смещение ко второму полю Len (4 байта)
	lenPtr := (*uint32)(unsafe.Pointer(uintptr(basePtr) + unsafe.Offsetof(h.Len)))
	fmt.Printf("Правило 3 (арифметика в строке): Len = %d\n", *lenPtr)

	// Правило 4: Использование unsafe.Slice (Go 1.17+)
	arr := [4]byte{'G', 'O', 'L', 'D'}
	slice := unsafe.Slice(&arr[0], 4)
	fmt.Printf("Правило 4 (unsafe.Slice): %s\n", string(slice))
}
```

## Под капотом

Компилятор Go имеет специальный оптимизатор liveness-анализа: он гарантирует сохранение объекта живым во время вычисления составного выражения `unsafe.Pointer(uintptr(p) + offset)`. Но если разбить это на две строки (`u := uintptr(p); p = unsafe.Pointer(u + off)`), компилятор может вызвать GC между строками и освободить память!

## Подводные камни

Сохранение промежуточного `uintptr` в переменную структуры или локальную переменную с последующей обратной конверсией — самая частая фатальная ошибка начинающих авторов unsafe-кода.

## На собеседовании

**Вопрос:** Почему выражение p = unsafe.Pointer(uintptr(p) + offset) обязано вычисляться в одну строку?
**Ответ:** Потому что `uintptr` не является указателем для сборщика мусора. Если разделить вычисление на две строки (`u := uintptr(p)` и затем на следующей строке `p = unsafe.Pointer(u)`), то в точке между строками сборщик мусора имеет право переместить стек горутины или утилизировать объект в куче. В результате переменная `u` станет указывать на освобожденную или чужую память (Dangling Pointer).
