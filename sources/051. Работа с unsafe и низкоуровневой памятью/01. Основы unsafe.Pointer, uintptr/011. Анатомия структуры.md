# Анатомия структуры: смещения полей через unsafe.Offsetof

## Условие

Используйте функцию unsafe.Offsetof, чтобы узнать точный сдвиг (в байтах) каждого поля структуры относительно ее начала. Докажите наличие холостых байт (padding) между полями.

### Исходная формулировка

**Анатомия структуры (`unsafe.Offsetof`)**: Используй `unsafe.Offsetof`, чтобы узнать точный сдвиг (в байтах) каждого поля структуры относительно её начала. Докажи с помощью этих цифр, почему порядок полей влияет на итоговый размер структуры (из-за паддингов).

## Теория

Функция `unsafe.Offsetof(structVal.Field)` возвращает смещение поля структуры в байтах от начального адреса экземпляра структуры.

Механика расчета смещений:
* Поле 0 всегда имеет смещение 0.
* Каждое следующее поле должно начинаться со смещения, кратного его выравниванию:
  $$\text{Offset}_{k} = \text{AlignUp}(\text{Offset}_{k-1} + \text{Size}_{k-1}, \text{Align}_{k})$$

Если между концом предыдущего поля и началом следующего образуется зазор, это **Padding**.

## Решение по шагам

1. Создайте структуру `LayoutAudit` с полями `int8`, `int64`, `int16`, `int32`.
2. Выведите смещение каждого поля через `unsafe.Offsetof`.
3. Вычислите размер промежуточных зазоров между полями.
4. Сопоставьте с общим размером структуры.

## Код решения

**`offsetof_audit.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type LayoutAudit struct {
	F1 int8   // 1 байт
	// 7 байт padding
	F2 int64  // 8 байт
	F3 int16  // 2 байта
	// 2 байта padding
	F4 int32  // 4 байта
}

func main() {
	var s LayoutAudit

	fmt.Println("=== Аудит анатомии структуры через unsafe.Offsetof ===")
	off1 := unsafe.Offsetof(s.F1)
	off2 := unsafe.Offsetof(s.F2)
	off3 := unsafe.Offsetof(s.F3)
	off4 := unsafe.Offsetof(s.F4)

	fmt.Printf("F1 (int8) : Offset = %2d байт (размер %d B)\n", off1, unsafe.Sizeof(s.F1))
	fmt.Printf("   -> Пустой зазор (padding): %d байт\n", off2-(off1+unsafe.Sizeof(s.F1)))
	fmt.Printf("F2 (int64): Offset = %2d байт (размер %d B)\n", off2, unsafe.Sizeof(s.F2))
	fmt.Printf("F3 (int16): Offset = %2d байт (размер %d B)\n", off3, unsafe.Sizeof(s.F3))
	fmt.Printf("   -> Пустой зазор (padding): %d байт\n", off4-(off3+unsafe.Sizeof(s.F3)))
	fmt.Printf("F4 (int32): Offset = %2d байт (размер %d B)\n", off4, unsafe.Sizeof(s.F4))

	total := unsafe.Sizeof(s)
	sumFields := unsafe.Sizeof(s.F1) + unsafe.Sizeof(s.F2) + unsafe.Sizeof(s.F3) + unsafe.Sizeof(s.F4)
	fmt.Printf("\nСумма размеров полезных полей: %d байт\n", sumFields)
	fmt.Printf("Реальный размер структуры:    %d байт (из них %d байт padding!)\n",
		total, total-sumFields)
}
```

ℹ️ Детальный аудит смещений полей структуры и обнаружение padding

## Под капотом

`unsafe.Offsetof` вычисляется компилятором на этапе компиляции в виде числовой константы. В бинарнике смещение жестко зашито в операнды инструкций адресации памяти `MOVQ 8(AX), BX`.

## Подводные камни

Аргументом `unsafe.Offsetof` должно быть прямое обращение к полю структуры (dot selector). Нельзя передавать поля встроенных безымянных структур без явного пути.

## На собеседовании

**Вопрос:** Как с помощью пакета unsafe динамически рассчитать процент холостой памяти (padding) в структуре данных?
**Ответ:** Вычисляют полный размер структуры через `unsafe.Sizeof(s)`, а затем суммируют `unsafe.Sizeof(field)` для каждого поля. Разница `unsafe.Sizeof(s) - sum(fieldSizes)` дает точный объем потерянных на padding байт.
