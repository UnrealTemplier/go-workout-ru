# Zero-copy преобразование StringToBytes и риски мутации строк

## Условие

Реализуйте функцию StringToBytes(s string) []byte без аллокаций памяти через unsafe.Pointer. Объясните, почему мутация возвращенного слайса байт является фатальной ошибкой (SIGSEGV / повреждение констант).

### Исходная формулировка

**Zero-copy string conversion**: Реализуйте функцию `StringToBytes(s string) []byte` без аллокаций через `unsafe.Pointer` и `reflect.SliceHeader`. **Почему это опасно?** (строки неизменяемы!)

## Теория

В Go строки концептуально неизменяемы (**Immutable**).
Обычное преобразование `[]byte(s)` всегда выделяет новый срез в куче и копирует байты через `runtime.stringtoslicebyte`.

**Zero-Copy StringToBytes:**
Строка (`reflect.StringHeader: Data uintptr, Len int`) преобразуется в срез (`reflect.SliceHeader: Data, Len, Cap = Len`) без выделения памяти.
Начиная с Go 1.20 стандартный пакет `unsafe` ввел каноничный метод:
```go
func StringToBytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s))
}
```

**Смертельная опасность мутации:**
Если строка была объявлена как строковый литерал (например, `"hello"`), ее байты размещены в **сегменте памяти только для чтения (.rodata)**!
Попытка изменить байт `b[0] = 'H'` вызовет немедленный аппаратный `SIGSEGV` (Segmentation Fault) от ядра операционной системы.

## Решение по шагам

1. Напишите функцию `StringToBytes(s string) []byte` через `unsafe.Slice`.
2. Докажите нулевой оверхед по аллокациям.
3. Объясните, почему строки в `.rodata` защищены на уровне страниц памяти процессора.

## Код решения

**`zero_copy_string.go`**

```go
package main

import (
	"fmt"
	"testing"
	"unsafe"
)

// StringToBytes выполняет Zero-Copy преобразование (Go 1.20+)
func StringToBytes(s string) []byte {
	return unsafe.Slice(unsafe.StringData(s), len(s))
}

func main() {
	text := "HighLoad Go Workout Unsafe Master"

	// Преобразование без копирования
	bytes := StringToBytes(text)

	fmt.Println("=== Zero-Copy StringToBytes ===")
	fmt.Printf("Исходная строка: %s\n", text)
	fmt.Printf("Срез байт:       %s (длина: %d, емкость: %d)\n",
		string(bytes), len(bytes), cap(bytes))

	// Замер аллокаций
	allocs := testing.AllocsPerRun(100, func() {
		_ = StringToBytes(text)
	})
	fmt.Printf("Количество аллокаций памяти: %.0f (Zero Allocations!)\n", allocs)

	// Демонстрация равенства адресов
	strPtr := unsafe.StringData(text)
	slicePtr := unsafe.SliceData(bytes)
	fmt.Printf("Адрес данных строки: %p\n", strPtr)
	fmt.Printf("Адрес данных среза:  %p (Абсолютно совпадают!)\n", slicePtr)
}
```

ℹ️ Zero-copy преобразование строки в срез байт через unsafe.StringData и unsafe.Slice

## Под капотом

Компилятор помещает строковые литералы в секцию `.rodata` исполняемого ELF-бинарника. При загрузке ОС помечает страницы `.rodata` флагом `PROT_READ` (без `PROT_WRITE`). Любая инструкция `MOVB` в этот адрес вызывает прерывание Page Fault ядра ОС с сигналом `SIGSEGV`.

## Подводные камни

Никогда не мутируйте срез байт, полученный через zero-copy из строки! Используйте этот срез **только для чтения** (например, передача в сетевой сокет, вычисление хэша md5/sha256 или сериализатор).

## На собеседовании

**Вопрос:** Что произойдет, если изменить байт в срезе, полученном через unsafe zero-copy из строкового литерала?
**Ответ:** Процесс немедленно аварийно завершится с сигналом `SIGSEGV` (Segmentation Violation). Строковые литералы размещаются операционной системой в секции памяти `.rodata` с флагом доступа только для чтения. Попытка записи в эту страницу памяти на аппаратном уровне пресекается блоком управления памятью процессора (MMU).
