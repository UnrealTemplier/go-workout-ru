# Построение карты памяти структуры: bool, int32, int64, byte

## Условие

Создайте структуру с полями bool, int32, int64, byte. Используя unsafe.Sizeof, unsafe.Alignof и unsafe.Offsetof, выведите пошаговую графическую карту расположения каждого байта в памяти.

### Исходная формулировка

Создайте структуру с полями `bool`, `int32`, `int64`, `byte`. Используя `unsafe.Sizeof`, `unsafe.Alignof` и `unsafe.Offsetof`, выведите layout в памяти (адрес каждого поля). Переставьте поля для минимизации padding и покажите разницу в размере.

## Теория

Построение точной карты памяти структуры на 64-битной архитектуре:

Пусть структура имеет вид:
```go
type Sample struct {
    A bool  // 1 байт
    B int32 // 4 байта
    C int64 // 8 байт
    D byte  // 1 байт
}
```

Расчет смещений:
1. `A (bool)`: смещение 0, размер 1. Следующее поле `B` требует выравнивания 4. Добавляется 3 байта padding `[1..3]`.
2. `B (int32)`: смещение 4, размер 4 `[4..7]`.
3. `C (int64)`: требует выравнивания 8. Смещение 8, размер 8 `[8..15]`.
4. `D (byte)`: требует выравнивания 1. Смещение 16, размер 1 `[16]`.
5. Максимальное выравнивание структуры = 8 (от поля `C`). Полный размер структуры обязан делиться на 8. Текущий конец 17 байт дополняется 7 байтами tail padding до **24 байт**.

## Решение по шагам

1. Объявите структуру `SampleLayout`.
2. Извлеките смещения каждого поля.
3. Постройте массив из 24 байтовых маркеров.
4. Выведите визуальную шкалу адресов с разметкой полезных данных и padding.

## Код решения

**`memory_map.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type SampleLayout struct {
	A bool  // Offset: 0, Size: 1
	B int32 // Offset: 4, Size: 4
	C int64 // Offset: 8, Size: 8
	D byte  // Offset: 16, Size: 1
}

func main() {
	var s SampleLayout
	total := unsafe.Sizeof(s)

	fmt.Printf("=== Карта памяти SampleLayout (Размер: %d байт, Выравнивание: %d) ===\n",
		total, unsafe.Alignof(s))

	offsets := []struct {
		name string
		off  uintptr
		size uintptr
	}{
		{"A (bool)", unsafe.Offsetof(s.A), unsafe.Sizeof(s.A)},
		{"B (int32)", unsafe.Offsetof(s.B), unsafe.Sizeof(s.B)},
		{"C (int64)", unsafe.Offsetof(s.C), unsafe.Sizeof(s.C)},
		{"D (byte)", unsafe.Offsetof(s.D), unsafe.Sizeof(s.D)},
	}

	byteMap := make([]string, total)
	for i := range byteMap {
		byteMap[i] = "[PAD]"
	}

	for _, f := range offsets {
		for i := f.off; i < f.off+f.size; i++ {
			byteMap[i] = fmt.Sprintf("[%s]", f.name[:1])
		}
	}

	fmt.Println("\nБайтовая линейка памяти (0 .. 23):")
	for i, marker := range byteMap {
		fmt.Printf("%02d: %-6s ", i, marker)
		if (i+1)%4 == 0 {
			fmt.Println()
		}
	}
}
```

ℹ️ Побайтная визуализация карты памяти структуры и пустых зазоров выравнивания

## Под капотом

Аппаратная причина паддинга: процессор читает память словами по 32 или 64 бита по адресам, кратным размеру слова. Невыровненный доступ (Misaligned Access) на старых архитектурах приводил к аппаратному прерыванию Bus Error, а на современных x86/ARM снижает скорость выборки из L1 кэша.

## Подводные камни

Попытка сериализовать структуру напрямую через дамп памяти (`unsafe.Slice((*byte)(&s), 24)`) приведет к отправке мусорных байт из паддинга по сети, что создает уязвимость утечки данных (Information Leakage).

## На собеседовании

**Вопрос:** Почему прямая бинарная передача структур Go по сети без сериализаторов (Protobuf/JSON) опасна?
**Ответ:** 1. Поля содержат неинициализированные байты padding, которые могут содержать фрагменты старых паролей или ключей из памяти; 2. Порядок полей и padding различаются между 32-битными и 64-битными архитектурами; 3. Различия порядка байт (Endianness) между клиентом и сервером приведут к искажению числовых данных.
