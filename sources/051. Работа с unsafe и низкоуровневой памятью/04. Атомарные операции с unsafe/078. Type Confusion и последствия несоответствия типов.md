# Type Confusion и последствия несоответствия типов памяти

## Условие

Приведите `*int` к `*float64` через `unsafe.Pointer` и прочитайте значение. Запишите в него `math.NaN()` и объясните, почему Type Confusion опасен для структур со скрытыми инвариантами.

### Исходная формулировка

**Type confusion**: Приведите `*int` к `*float64` и прочитайте значение. Получите NaN или мусор.

## Теория

**Type Confusion** (путаница типов) возникает, когда программа обращается к области памяти одного типа, интерпретируя ее как совершенно другой несовместимый тип.
Хотя `int` и `float64` на 64-битной платформе занимают по 8 байт, их битовая семантика радикально отличается:
- Значение целого числа \(0\) в `float64` интерпретируется как \(+0.0\).
- Значение \(1\) в целом числе для `float64` является денормализованным субнормальным числом порядка \(10^{-324}\).
- Запись битовой маски `NaN` в `float64` делает невозможными сравнения (`x == x` возвращает `false`).

## Решение по шагам

1. Создайте переменную `var n int = 1`.
2. Приведите адрес к `*float64` через `(*float64)(unsafe.Pointer(&n))`.
3. Распечатайте полученное число с плавающей точкой.
4. Запишите `*f = math.NaN()`.
5. Выведите значение целого числа `n` в шестнадцатеричном виде.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"unsafe"
)

func main() {
	var n int = 1

	// Type Confusion: интерпретируем int как float64
	f := (*float64)(unsafe.Pointer(&n))

	fmt.Printf("Исходный int:      %d\n", n)
	fmt.Printf("Как float64:       %e (субнормальное число)\n", *f)

	// Записываем NaN (Not a Number)
	*f = math.NaN()

	fmt.Printf("После записи NaN:  %f\n", *f)
	fmt.Printf("Целое n в hex:     0x%016X\n", uint64(n))
	fmt.Printf("Сравнение f == f:  %t (нарушение рефлексивности равенства!)\n", *f == *f)
}
```

ℹ️ Битовое представление NaN нарушает аксиому рефлексивности отношения эквивалентности.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходный int:      1
# Как float64:       4.940656e-324 (субнормальное число)
# После записи NaN:  NaN
# Целое n в hex:     0x7FF8000000000001
# Сравнение f == f:  false (нарушение рефлексивности равенства!)
```

## Под капотом

Стандарт IEEE 754 определяет, что любое значение с экспонентой `0x7FF` и ненулевой мантиссой является `NaN`, и любое сравнение с `NaN` (даже `NaN == NaN`) аппаратно возвращает ложь на уровне инструкций процессора `UCOMISD`.

## Подводные камни

Если выполнить Type Confusion между структурой с указателем и структурой с числом, сборщик мусора Go упадет с фатальной ошибкой рантайма при попытке разыменовать число как адрес объекта.

## На собеседовании

**Вопрос с собеседования:** К чему приведет в рантайме Go каст структуры `struct { p *int }` к структуре `struct { n int64 }` и запись произвольного числа в `n`?
**Ответ:** При следующей сборке мусора GC просканирует оригинальную структуру, считая поле указателем. Он попытается обратиться по этому числу как по адресу в куче для маркировки серого объекта. Если число не является валидным адресом span'а рантайма, процесс упадет с паникой `fatal error: bad pointer in heap`.
