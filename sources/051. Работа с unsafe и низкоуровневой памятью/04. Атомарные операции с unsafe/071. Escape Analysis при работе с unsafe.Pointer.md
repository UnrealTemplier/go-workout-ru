# Escape Analysis при работе с unsafe.Pointer и флаг -gcflags=-m

## Условие

Напиши функцию, которая возвращает `unsafe.Pointer` на локальную переменную. Запусти `go build -gcflags="-m"`. Убедись, что переменная "escapes to heap". Объясни, как компилятор трактует `unsafe.Pointer` при анализе побегов.

### Исходная формулировка

**[Каверзный кейс — Escape Analysis и `unsafe`]**: Напиши функцию, которая возвращает `unsafe.Pointer` на локальную переменную. Запусти `go build -gcflags="-m"`. Убедись, что переменная утекла в кучу, иначе при возврате из функции стек очистился бы, и указатель стал бы висячим (dangling pointer).

## Теория

Компилятор Go выполняет Escape Analysis для всех типов, включая `unsafe.Pointer`.
Если функция возвращает `unsafe.Pointer`, компилятор распознает, что возвращаемое значение является **указателем** (в отличие от `uintptr`), и принудительно переносит локальную переменную в кучу:
`moved to heap: x`.

Это принципиальная разница между `unsafe.Pointer` и `uintptr`:
- `unsafe.Pointer` сохраняет семантику указателя для Escape Analysis и сборщика мусора.
- `uintptr` полностью теряет семантику указателя.

## Решение по шагам

1. Напишите функцию `safeHeapEscape() unsafe.Pointer`, возвращающую `unsafe.Pointer(&localVal)`.
2. Напишите функцию `unsafeNumberEscape() uintptr`, возвращающую `uintptr(unsafe.Pointer(&localVal))`.
3. Скомпилируйте файл с флагом `-gcflags="-m"`.
4. Сравните вердикты компилятора для обеих функций.
5. Объясните поведение алгоритма анализа побегов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// safeHeapEscape возвращает unsafe.Pointer -> компилятор отправит val1 в кучу
func safeHeapEscape() unsafe.Pointer {
	val1 := 42
	return unsafe.Pointer(&val1)
}

// unsafeNumberEscape возвращает uintptr -> компилятор считает val2 не убегающей!
func unsafeNumberEscape() uintptr {
	val2 := 84
	return uintptr(unsafe.Pointer(&val2))
}

func main() {
	p1 := safeHeapEscape()
	u2 := unsafeNumberEscape()

	fmt.Printf("p1 (в куче):  %d\n", *(*int)(p1))
	fmt.Printf("u2 (на стеке): %d\n", *(*int)(unsafe.Pointer(u2)))
}
```

ℹ️ Флаг -gcflags=-m покажет точные решения компилятора по размещению переменных.

**`Терминал`**

```bash
go build -gcflags="-m" main.go
# Вывод анализатора побегов (Escape Analysis):
# ./main.go:10:2: moved to heap: val1
# ./main.go:16:2: val2 does not escape
```

## Под капотом

В исходном коде компилятора Go (`cmd/compile/internal/escape/escape.go`) тип `unsafe.Pointer` имеет флаг указательного типа (`HasPointers() == true`). Алгоритм обхода графа потока данных (flow graph) рассматривает возврат `unsafe.Pointer` как побег адреса в корень вызывающей стороны. Тип `uintptr` является скаляром (`HasPointers() == false`), поэтому связь обрывается, и `val2` ошибочно оставляется на стеке.

## Подводные камни

Полагаться на то, что `uintptr` удержит объект от побега для мнимой «оптимизации» — грубейшая ошибка, приводящая к разрушению стека.

## На собеседовании

**Вопрос с собеседования:** Чем с точки зрения Escape Analysis отличаются возвращаемые типы `unsafe.Pointer` и `uintptr`?
**Ответ:** `unsafe.Pointer` сообщает компилятору о наличии живой ссылки на память, поэтому переменная гарантированно отправляется в кучу (`moved to heap`). Для `uintptr` компилятор не видит утечки указателя и оставляет переменную на стеке (`does not escape`), что приведет к Use-After-Free при попытке чтения по возвращенному адресу.
