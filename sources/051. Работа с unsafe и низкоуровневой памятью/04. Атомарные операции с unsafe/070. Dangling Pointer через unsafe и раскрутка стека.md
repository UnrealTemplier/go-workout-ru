# Dangling Pointer через unsafe и раскрутка стека

## Условие

Напишите программу, которая демонстрирует **dangling pointer** через `unsafe`: аллоцируйте объект в функции, сохраните `uintptr` в глобальную переменную, завершите функцию, вызовите несколько других функций (чтобы перезаписать стек), восстановите указатель из `uintptr` и прочитайте значение. Запустите.

### Исходная формулировка

Напишите программу, которая демонстрирует **dangling pointer** через `unsafe`: аллоцируйте объект в функции, сохраните `uintptr`, выйдите из функции (стек должен быть уничтожен), затем попытайтесь разыменовать. Объясните, почему это UB, и как moving GC (концептуально, не в текущем Go) делает `uintptr` ещё опаснее.

## Теория

**Dangling Pointer** (висячий указатель) — указатель, ссылающийся на область памяти, которая уже была освобождена или переиспользована для других целей.
В безопасном Go создание висячих указателей невозможно: компилятор выполняет Escape Analysis и автоматически выносит объект в кучу.
Однако принудительное сохранение адреса в `uintptr` разрывает цепочку анализа компилятора, превращая указатель в классический C-стиль висячий указатель.

## Решение по шагам

1. Объявите глобальный `var danglingAddr uintptr`.
2. Создайте функцию `setupDangling()`, где инициализируется локальная переменная `secret := 123456`.
3. Сохраните адрес `&secret` в `danglingAddr`.
4. В `main` вызовите функцию `polluteStack()`, интенсивно пишущую произвольные байты на стек.
5. Восстановите указатель и распечатайте испорченное значение.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

var danglingAddr uintptr

//go:noinline
func setupDangling() {
	val := 123456
	// Сохраняем адрес стековой переменной
	danglingAddr = uintptr(unsafe.Pointer(&val))
}

//go:noinline
func polluteStack() {
	var junk [16]int
	for i := range junk {
		junk[i] = 0xDEADBEEF
	}
	_ = junk
}

func main() {
	setupDangling()

	// В этот момент фрейм setupDangling завершился
	// Вызываем polluteStack, фрейм которого перезапишет тот же участок стека
	polluteStack()

	// Читаем по висячему указателю
	danglingPtr := (*int)(unsafe.Pointer(danglingAddr))

	fmt.Printf("Адрес: 0x%X\n", danglingAddr)
	fmt.Printf("Значение по висячему указателю: 0x%X (ожидалось 123456, получено 0xDEADBEEF)\n", *danglingPtr)
}
```

ℹ️ Стек повторно использует адресное пространство завершившихся функций.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Адрес: 0x...
# Значение по висячему указателю: 0xDEADBEEF (ожидалось 123456, получено 0xDEADBEEF)
```

## Под капотом

Регистр процессора `RSP` указывает на верхушку стека. При вызове `setupDangling` переменная `val` размещается по адресу `RSP - 8`. При выходе `RSP` восстанавливается. Следующий вызов `polluteStack` снова выделяет память от того же `RSP`, записывая `0xDEADBEEF` ровно в ту же физическую ячейку оперативной памяти.

## Подводные камни

В реальных многопоточных сервисах чтение по Dangling Pointer приводит к спорадическим паникам `SIGSEGV` или критическим уязвимостям безопасности (Memory Disclosure).

## На собеседовании

**Вопрос с собеседования:** Как компилятор Go гарантирует отсутствие висячих указателей в обычном безопасном коде?
**Ответ:** Благодаря статическому Escape Analysis. Если функция возвращает указатель `&x` или передает его в канал/интерфейс, компилятор видит, что время жизни переменной превышает время жизни фрейма стека, и заменяет стековое выделение на вызов `runtime.newobject` в куче.
