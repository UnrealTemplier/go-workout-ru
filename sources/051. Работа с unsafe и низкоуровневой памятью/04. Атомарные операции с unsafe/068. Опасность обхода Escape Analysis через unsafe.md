# Опасность обхода Escape Analysis через unsafe

## Условие

Попробуйте "обмануть" escape analysis через `unsafe` (сохранив указатель на локальную переменную стека в глобальную переменную через `uintptr`). Продемонстрируйте, как рантайм разрушает этот стек при завершении функции, приводя к фатальным багам.

### Исходная формулировка

**Escape analysis bypass**: Попробуйте "обмануть" escape analysis через unsafe. Изучите, почему это плохая идея.

## Теория

**Escape Analysis** компилятора Go решает, где выделить память: на быстром стеке функции или в куче. Если переменная «убегает» (ссылка возвращается наружу или сохраняется в куче), компилятор перемещает аллокацию в кучу.
Если попытаться скрыть факт утечки адреса через `uintptr` (компилятор не отслеживает скалярные числа), переменная ошибочно останется на стеке.
После возврата из функции фрейм стека аннулируется, а последующие вызовы функций перезаписывают этот участок памяти чужими аргументами.

## Решение по шагам

1. Создайте глобальную переменную `var leakedAddr uintptr`.
2. Напишите функцию `leakStackVariable()`, создающую массив `[4]int` на стеке и сохраняющую его адрес в `leakedAddr`.
3. Вызовите функцию `leakStackVariable()`.
4. Вызовите другую функцию `overwriteStack()`, интенсивно использующую стек.
5. Распечатайте память по `leakedAddr` и покажите искажение данных.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

var leakedAddr uintptr

//go:noinline
func leakStackVariable() {
	// Локальный массив на стеке
	stackArr := [4]int{111, 222, 333, 444}

	// Обманываем escape analysis через uintptr:
	// Компилятор думает, что массив не убегает, и оставляет его на стеке!
	leakedAddr = uintptr(unsafe.Pointer(&stackArr[0]))
}

//go:noinline
func overwriteStack(a, b, c, d int) {
	var filler [4]int = [4]int{a, b, c, d}
	_ = filler
}

func main() {
	leakStackVariable()

	// На этом этапе стек функции leakStackVariable уничтожен
	ptr := (*[4]int)(unsafe.Pointer(leakedAddr))
	fmt.Printf("Данные сразу после возврата: %v\n", *ptr)

	// Перезаписываем освободившийся фрейм стека новыми данными
	overwriteStack(999, 888, 777, 666)

	fmt.Printf("Данные после вызова overwriteStack: %v\n", *ptr)
	fmt.Println("Память разрушена: исходный массив перезаписан фреймом чужой функции!")
}
```

ℹ️ Директива //go:noinline запрещает встраивание функции, гарантируя создание отдельного фрейма стека.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Данные сразу после возврата: [111 222 333 444]
# Данные после вызова overwriteStack: [999 888 777 666]
# Память разрушена: исходный массив перезаписан фреймом чужой функции!
```

## Под капотом

При возврате из `leakStackVariable` указатель стека `RSP` сдвигается назад. Физически память не обнуляется. Следующий вызов `overwriteStack` аллоцирует свой фрейм ровно по тем же адресам стека. Инструкции `MOVQ` записывают значения `999, 888, 777, 666` прямо поверх старого массива.

## Подводные камни

Подобные ошибки в продакшене вызывают тихие повреждения данных (silent data corruption), когда вызов совершенно сторонней функции в другом модуле меняет значения чужих переменных.

## На собеседовании

**Вопрос с собеседования:** Почему программисты иногда пытаются обмануть Escape Analysis и почему в Go это строжайшее табу?
**Ответ:** Разработчики пытаются избежать аллокации в куче для снижения нагрузки на GC. В Go это категорическое табу: компилятор не дает гарантий сохранности стека после выхода из функции. Для предотвращения аллокаций в Go следует использовать пулы `sync.Pool`, переиспользование слайсов или архитектуру арен, а не трюки с сокрытием указателей.
