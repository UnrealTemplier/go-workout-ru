# Безопасность возврата указателей в Go vs висячие указатели в C

## Условие

Создайте указатель на локальную переменную функции, верните его и используйте после возврата. Объясните, почему в Go это абсолютно безопасно (Escape Analysis), в то время как в C это классический висячий указатель (UB).

### Исходная формулировка

**Dangling pointers**: Создайте указатель на локальную переменную функции, верните его и используйте после возврата. В Go это работает (escape analysis), но с unsafe можно создать настоящий dangling pointer.

## Теория

В языке C следующий код является грубейшей ошибкой:
```c
int* bad() {
    int x = 42;
    return &x; // UB: адрес локального стека!
}
```
В языке Go возврат указателя на локальную переменную `return &x` является абсолютно легальной и поощряемой идиомой.
Компилятор Go во время компиляции анализирует граф потока управления (Escape Analysis): если адрес `&x` покидает пределы функции, компилятор автоматически выделяет память под переменную в управляемой куче (`runtime.newobject`).

## Решение по шагам

1. Напишите функцию `safeReturnPointer() *int`.
2. Объявите в ней локальную переменную `x := 42` и верните `&x`.
3. В `main` вызовите функцию и прочитайте значение по указателю.
4. Проверьте с помощью `go build -gcflags="-m"`, как компилятор принял решение о побеге в кучу.
5. Сравните гарантии безопасности Go с ручным управлением памятью в C.

## Код решения

**`main.go`**

```go
package main

import "fmt"

// safeReturnPointer возвращает указатель на локальную переменную
func safeReturnPointer() *int {
	x := 42
	return &x // В Go это безопасно!
}

func main() {
	ptr := safeReturnPointer()

	fmt.Printf("Значение по указателю: %d\n", *ptr)
	fmt.Printf("Адрес в куче:         %p\n", ptr)
}
```

ℹ️ Escape analysis компилятора Go гарантирует, что переменная переживет фрейм функции.

**`Терминал`**

```bash
go build -gcflags="-m" main.go
# Вывод компилятора:
# ./main.go:7:2: moved to heap: x
# ./main.go:14:12: ... argument does not escape

go run main.go
# Вывод:
# Значение по указателю: 42
# Адрес в куче:         0x...
```

## Под капотом

Компилятор Go заменяет локальную переменную `x` на неявный вызов аллокатора кучи. Память выделяется в mspan рантайма, а указатель отслеживается сборщиком мусора. Объект будет жить до тех пор, пока на него есть хотя бы одна ссылка.

## Подводные камни

Иллюзия «все на стеке»: программисты часто не замечают, что возврат `&x` создает аллокацию кучи. В высоконагруженных циклах тысячи таких вызовов генерируют избыточный мусор для GC.

## На собеседовании

**Вопрос с собеседования:** Как устроен Escape Analysis в Go и что приводит к аллокации в куче?
**Ответ:** Escape Analysis строит граф направленных зависимостей между переменными. Переменная убегает в кучу, если: 1) Ее указатель возвращается из функции; 2) Она передается в аргумент типа `any`/`interface{}`; 3) Ее размер динамический или слишком велик для стека (> 64 КБ); 4) Ее указатель сохраняется в замыкании (closure) или канале/глобальной переменной.
