# Модификация Len и Cap слайса и опасность выхода за границы

## Условие

Модифицируйте `Len` и `Cap` слайса через структуру заголовка слайса. Покажите, как увеличение `Cap` за реальные границы аллокации приводит к повреждению памяти или runtime panic.

### Исходная формулировка

**Slice bounds через unsafe**: Модифицируйте `Len` и `Cap` слайса через `reflect.SliceHeader`. Вызовите панику при выходе за реальные границы массива.

## Теория

Слайс в Go управляется структурой из 3 слов: `{ Data, Len, Cap }`.
Оператор `append` опирается на значение `Cap`: пока `Len < Cap`, Go пишет в существующий буфер. Если `Len == Cap`, Go вызывает `runtime.growslice` для выделения нового массива.

Если через `unsafe` искусственно установить `Cap` больше, чем выделил аллокатор памяти, последующие записи не вызовут переаллокацию, а перезапишут чужую память кучи, принадлежащую соседним объектам!

## Решение по шагам

1. Создайте слайс `s := make([]int, 2, 2)` (буфер ровно на 2 элемента).
2. Создайте теневую структуру `SliceHeader struct { Data unsafe.Pointer; Len int; Cap int }`.
3. Установите `header.Cap = 100` (фальсификация емкости).
4. Выполните `s = append(s, 999)`.
5. Покажите, что запись произошла за пределы исходного буфера без `growslice`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type SliceHeader struct {
	Data unsafe.Pointer
	Len  int
	Cap  int
}

func main() {
	// Создаем слайс емкостью ровно 2 элемента
	s := make([]int, 2, 2)
	s[0] = 10
	s[1] = 20

	hdr := (*SliceHeader)(unsafe.Pointer(&s))
	fmt.Printf("До хака:     len=%d, cap=%d, data=%p\n", hdr.Len, hdr.Cap, hdr.Data)

	// ФАЛЬСИФИКАЦИЯ: увеличиваем cap до 10 в обход аллокатора кучи
	hdr.Cap = 10

	fmt.Printf("После хака:  len=%d, cap=%d, data=%p\n", len(s), cap(s), hdr.Data)

	// append теперь думает, что буфер вмещает 10 элементов!
	s = append(s, 30)
	s = append(s, 40)

	fmt.Printf("Слайс после append: %v (len=%d, cap=%d)\n", s, len(s), cap(s))
	fmt.Printf("Адрес не изменился (growslice не вызывался!): %p\n", hdr.Data)
	fmt.Println("ВНИМАНИЕ: Память за пределами первых 2 элементов была повреждена!")
}
```

ℹ️ Фальсификация Cap обманывает проверку в append, заставляя писать в чужие слоты памяти.

**`Терминал`**

```bash
go run main.go
# Вывод:
# До хака:     len=2, cap=2, data=0x...
# После хака:  len=2, cap=10, data=0x...
# Слайс после append: [10 20 30 40] (len=4, cap=10)
# Адрес не изменился (growslice не вызывался!): 0x...
# ВНИМАНИЕ: Память за пределами первых 2 элементов была повреждена!
```

## Под капотом

Аллокатор Go `mallocgc` выделяет память блоками определенного размера (`sizeclass`). Для слайса `[2]int` (16 байт) выделяется слот в 16-байтном классе. Принудительная запись элементов `s[2]` и `s[3]` перезаписывает следующий 16-байтный слот в `mspan`, который может содержать метаданные другой переменной или указатель объекта кучи.

## Подводные камни

Повреждение метаданных `mspan` приводит к аварийному завершению сборщика мусора с сообщением `fatal error: found pointer to free object` или `bad sweepgen`.

## На собеседовании

**Вопрос с собеседования:** Что произойдет со сборщиком мусора, если перезаписать память за границами слайса кучи?
**Ответ:** Аллокатор кучи размещает объекты в span'ах непрерывно. Запись за пределы слайса повредит соседний объект или заголовок span. Во время следующей фазы Concurrent Mark GC попытается прочитать поврежденный указатель, что вызовет фатальную панику рантайма `fatal error: bad pointer in heap` с полным крашем процесса.
