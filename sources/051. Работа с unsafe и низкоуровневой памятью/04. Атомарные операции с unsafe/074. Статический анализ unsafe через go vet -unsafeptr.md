# Статический анализ unsafe через go vet -unsafeptr

## Условие

Запустите статический анализатор вашего кода с проверкой некорректного использования unsafe-указателей: `go vet` (правило `unsafeptr`). Напишите код с ошибкой (сохранение uintptr) и покажите, как `go vet` находит её.

### Исходная формулировка

**Статический анализатор `go vet`**: Запустите статический анализатор вашего кода с флагом проверки некорректного использования unsafe-указателей: `go vet -unsafeptr ./...`. Объясните, какие потенциально опасные конструкции в коде (например, нарушение правил преобразования `unsafe.Pointer` к `uintptr` и обратно) способен находить этот инструмент.

---

## Теория

Стандартный инструмент `go vet` включает анализатор `unsafeptr`, который проверяет строгое соблюдение правил спецификации `unsafe.Pointer`:
1. Преобразование `*T1` в `unsafe.Pointer` и обратно в `*T2`.
2. Преобразование `unsafe.Pointer` в `uintptr` только в момент арифметики `unsafe.Pointer(uintptr(p) + add)`.
3. Преобразование `unsafe.Pointer` в `uintptr` только в аргументах `syscall.Syscall`.

Любое промежуточное сохранение `u := uintptr(p)` с последующим `p = unsafe.Pointer(u)` классифицируется анализатором как дефект `possible misuse of unsafe.Pointer`.

## Решение по шагам

1. Напишите файл `bad_unsafe.go` с некорректным сохранением `uintptr`.
2. Напишите корректную версию с `unsafe.Add`.
3. Запустите `go vet bad_unsafe.go`.
4. Изучите вывод статического анализатора.
5. Исправьте код согласно рекомендациям.

## Код решения

**`bad_unsafe.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

func brokenPointerArithmetic() {
	arr := [2]int{10, 20}
	p := unsafe.Pointer(&arr[0])

	// ОШИБКА: разрыв арифметики на две строки
	u := uintptr(p)
	u += unsafe.Sizeof(arr[0])
	next := (*int)(unsafe.Pointer(u))

	fmt.Println(*next)
}

func main() {
	brokenPointerArithmetic()
}
```

ℹ️ go vet обнаружит переменную u и выдаст диагностическое сообщение.

**`Терминал`**

```bash
go vet bad_unsafe.go
# Вывод go vet:
# bad_unsafe.go:15:17: possible misuse of unsafe.Pointer
```

## Под капотом

Анализатор `unsafeptr` строит AST (абстрактное синтаксическое дерево) и проверяет, является ли аргумент вызова `unsafe.Pointer(expr)` синтаксическим выражением сложения с `uintptr(...)`. Если в выражении фигурирует идентификатор переменной типа `uintptr`, анализатор сигнализирует об ошибке.

## Подводные камни

Никогда не подавляйте предупреждения `unsafeptr` в CI/CD без абсолютной уверенности, так как именно они защищают production-системы от скрытых GC-паник.

## На собеседовании

**Вопрос с собеседования:** Какие 6 легальных паттернов использования `unsafe.Pointer` описаны в спецификации Go?
**Ответ:** 1) Преобразование `*T1` в `unsafe.Pointer` в `*T2`; 2) Преобразование `unsafe.Pointer` в `uintptr` (для логирования или вывода адреса); 3) Преобразование `unsafe.Pointer` в `uintptr`, арифметика и обратный каст в том же выражении; 4) Передача в системные вызовы `syscall.Syscall`; 5) Преобразование результата `reflect.Value.Pointer` / `UnsafeAddr` в `unsafe.Pointer`; 6) Преобразование `reflect.SliceHeader.Data` / `StringHeader.Data` (устарело в Go 1.20 в пользу `unsafe.Slice`/`String`).
