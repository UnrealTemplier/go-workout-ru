# In-Place мутация строк в куче vs Segfault в секции .rodata

## Условие

Используя `unsafe`, измените байты строки, аллоцированной в куче (например, созданной через `strings.Builder` или `fmt.Sprintf`), и покажите, что мутация проходит успешно. Объясните, почему аналогичная попытка для строкового литерала приводит к крашу `SIGSEGV`.

### Исходная формулировка

**Переопределение строк на уровне памяти.**: Используя unsafe, измените байты строки в куче (получите указатель на data через `reflect.StringHeader` или `unsafe.StringData`), модифицируйте их и покажите, что строка поменялась, нарушая соглашение.

## Теория

Память в операционной системе разделена на сегменты с разными правами доступа:
1. **Секция `.rodata` (Read-Only Data)**: в нее компилятор помещает строковые литералы (например, `"hello"`). Страницы памяти имеют защиту `PROT_READ`. Любая запись генерирует исключение процессора `Page Fault` и завершение процесса `SIGSEGV` (Segmentation Fault).
2. **Сегмент кучи (Heap)**: динамически выделяемые строки (например, результат `fmt.Sprintf` или конкатенации) располагаются в страницах памяти с флагами `PROT_READ | PROT_WRITE`. Запись байт через `unsafe` в такую строку технически возможна, хотя и нарушает инварианты языка Go.

## Решение по шагам

1. Создайте динамическую строку `dynStr := fmt.Sprintf("Dynamic_%d", 123)`.
2. Получите указатель `*byte` на данные строки через `unsafe.StringData(dynStr)`.
3. Создайте слайс байт через `unsafe.Slice(ptr, len(dynStr))`.
4. Мутируйте первый байт `slice[0] = 'H'`.
5. Выведите `dynStr` и продемонстрируйте изменение.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	// Строка, аллоцированная динамически в куче (Heap)
	heapStr := fmt.Sprintf("Secret_%s", "Token")
	fmt.Printf("Исходная строка в куче: %s\n", heapStr)

	// Получаем мутабельный срез памяти на данные строки
	ptr := unsafe.StringData(heapStr)
	bytes := unsafe.Slice(ptr, len(heapStr))

	// Модифицируем память кучи
	bytes[0] = 'M'
	bytes[1] = 'y'

	fmt.Printf("Строка после мутации:  %s\n", heapStr)
	fmt.Println("Мутация в куче прошла успешно, так как страницы кучи имеют флаг PROT_WRITE.")

	// ВАЖНО: Строковые литералы лежат в .rodata:
	// literal := "ReadOnly"
	// unsafe.Slice(unsafe.StringData(literal), 8)[0] = 'X' -> SIGSEGV / crash!
}
```

ℹ️ Страницы кучи поддерживают запись, в то время как секция .rodata аппаратно защищена от записи MMU.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходная строка в куче: Secret_Token
# Строка после мутации:  Mycret_Token
# Мутация в куче прошла успешно, так как страницы кучи имеют флаг PROT_WRITE.
```

## Под капотом

Ядро Linux управляет правами доступа к страницам через структуру `vm_area_struct`. При загрузке бинарного файла страницы `.rodata` мапятся системным вызовом `mmap` без флага `PROT_WRITE`. Страницы кучи аллокатора Go мапятся рантаймом с флагами `PROT_READ | PROT_WRITE`.

## Подводные камни

Мутация строк в куче все равно нарушает спецификацию Go: если компилятор оптимизировал код или закэшировал хэш строки, программа начнет вести себя непредсказуемо.

## На собеседовании

**Вопрос с собеседования:** Почему при попытке записи в строковый литерал через `unsafe` процесс падает с `fatal error: fault`, а не обычной паникой Go?
**Ответ:** Потому что аппаратное прерывание генерируется процессором (Memory Management Unit) на уровне физической страницы памяти (`PROT_READ`). Ядро ОС посылает процессу сигнал `SIGSEGV`. Рантайм Go перехватывает сигнал в функции `runtime.sigtramp`, но не может преобразовать его в recoverable panic, завершая процесс фатальной ошибкой `fault`.
