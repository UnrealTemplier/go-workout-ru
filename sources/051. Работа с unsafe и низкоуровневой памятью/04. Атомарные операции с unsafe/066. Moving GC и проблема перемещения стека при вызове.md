# Moving GC и проблема перемещения стека при вызове функций

## Условие

Создайте программу, где вы сохраняете `uintptr` локальной переменной на стеке, вызываете глубокую рекурсивную функцию, вызывающую рост стека горутины, и пытаетесь использовать сохранённый `uintptr`. Объясните результат.

### Исходная формулировка

**Moving GC problem**: Создайте программу, где вы сохраняете `uintptr` (не `unsafe.Pointer`), запускаете GC и пытаетесь использовать сохранённый адрес. **Программа упадёт или вернёт мусор.**

## Теория

Горутины в Go стартуют с крошечным стеком (2 КБ в Go 1.4+).
Когда глубина вызовов функций или размер локальных фреймов исчерпывает текущий стек, рантайм Go выполняет операцию **Stack Growth** (`runtime.morestack` / `runtime.newstack`):
1. В куче выделяется новый блок памяти стека удвоенного размера (например, 4 КБ, 8 КБ).
2. Все фреймы старого стека копируются в новый стек.
3. Рантайм корректирует все валидные указатели на переменные стека.
4. Старый стек освобождается.

Если адрес переменной был сохранен в виде числа `uintptr`, рантайм **не знает**, что это указатель, и не обновит его! Число `uintptr` останется указывать на освобожденный старый стек!

## Решение по шагам

1. Создайте локальную переменную на стеке `var x int = 42`.
2. Сохраните адрес переменной в `rawAddr := uintptr(unsafe.Pointer(&x))`.
3. Вызовите функцию `growStack(depth int)`, которая рекурсивно аллоцирует фреймы и форсирует переезд стека.
4. Прочитайте значение по адресу `rawAddr` через `*(*int)(unsafe.Pointer(rawAddr))`.
5. Продемонстрируйте искажение данных или падение программы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// growStack рекурсивно выделяет память на стеке, вынуждая рантайм перенести стек горутины
func growStack(depth int) {
	var buffer [1024]byte // 1 КБ на каждый фрейм вызова
	buffer[0] = byte(depth)
	if depth > 0 {
		growStack(depth - 1)
	}
}

func main() {
	var x int = 777

	// Сохраняем адрес стековой переменной в число uintptr
	// ВНИМАНИЕ: Это фундаментальная ошибка при наличии stack copying в Go!
	savedAddr := uintptr(unsafe.Pointer(&x))

	fmt.Printf("Исходный адрес x на стеке: 0x%x, значение: %d\n", savedAddr, x)

	// Форсируем рост стека горутины (более 30 КБ суммарно)
	growStack(30)

	// Переменная x переехала на новый стек вместе с фреймом main!
	newAddr := uintptr(unsafe.Pointer(&x))
	fmt.Printf("Текущий адрес x на новом стеке: 0x%x\n", newAddr)
	fmt.Printf("Стек переместился: %t\n", savedAddr != newAddr)

	// Чтение по старому адресу в освобожденной памяти
	stalePtr := (*int)(unsafe.Pointer(savedAddr))
	fmt.Printf("Значение по старому savedAddr (Dangling Pointer): %d (может быть перезаписано мусором!)\n", *stalePtr)
}
```

ℹ️ savedAddr != newAddr доказывает, что стек физически переместился в другой регион памяти.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходный адрес x на стеке: 0xc0000...
# Текущий адрес x на новом стеке: 0xc0001...
# Стек переместился: true
# Значение по старому savedAddr (Dangling Pointer): мусор или 0
```

## Под капотом

Функция `runtime.copystack` обходит стек и использует стековые карты типов (stack maps), чтобы скорректировать указатели: `*p = newLoc + (*p - oldLoc)`. Поскольку переменная `savedAddr` имеет тип `uintptr`, в карте типов она помечена как целое число, и рантайм оставляет число неизменным. Старый сегмент стека отдается в пул свободных стеков рантайма.

## Подводные камни

Любое преобразование указателя на локальную переменную стека в `uintptr` с последующим вызовом любой функции рискует попасть под `morestack` и стать висячим указателем.

## На собеседовании

**Вопрос с собеседования:** Почему в Go сборщик мусора не является перемещающим (non-moving/non-compacting GC), а стек является перемещающим (moving stack)?
**Ответ:** Объекты в куче не перемещаются сборщиком мусора, чтобы упростить взаимодействие с CGO и снизить STW паузы. Однако стек горутины обязан перемещаться при росте, так как горутины стартуют с 2 КБ для поддержки миллионов горутин. Рантайм может перемещать стек, потому что точно знает расположение всех указателей на стеке благодаря компиляторным картам типов.
