# GC Visibility: сборка объекта, удерживаемого только через uintptr

## Условие

Создайте объект, на который есть только ссылка через `uintptr`. Запустите GC с помощью `runtime.GC()` и наблюдайте через финализатор `runtime.SetFinalizer`, как объект удаляется, потому что GC не видит ссылку в `uintptr`.

### Исходная формулировка

**GC visibility**: Создайте объект, на который есть только ссылка через `uintptr`. Запустите GC и наблюдайте, как объект удаляется (GC не видит uintptr как указатель).

## Теория

Сборщик мусора Go использует алгоритм точной маркировки памяти.
Для каждой функции и типа данных компилятор генерирует битовую карту указателей:
- Бит `1` — в данном слоте находится валидный указатель на память, подлежащий сканированию.
- Бит `0` — в слоте находится скаляр (число, булево значение или `uintptr`).

Если единственный путь к объекту памяти сохранен в переменной `uintptr`, сборщик мусора полностью слеп к нему. Объект признается недостижимым и немедленно передается финализатору или возвращается в пул памяти.

## Решение по шагам

1. Создайте тип `HeavyPayload struct { data [1024]int }`.
2. Выделите объект и повесьте финализатор через `runtime.SetFinalizer`.
3. Сохраните адрес в `uintptr` и обнулите оригинальный типизированный указатель.
4. Вызовите `runtime.GC()` и сделайте паузу `time.Sleep`.
5. Убедитесь в срабатывании финализатора.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

type HeavyObject struct {
	ID int
}

func main() {
	obj := &HeavyObject{ID: 42}

	// Регистрируем финализатор для фиксации момента удаления
	runtime.SetFinalizer(obj, func(o *HeavyObject) {
		fmt.Printf(">>> [GC ALERT] HeavyObject ID=%d УНИЧТОЖЕН СБОРЩИКОМ МУСОРА! <<<\n", o.ID)
	})

	// Сохраняем адрес только в uintptr
	rawAddr := uintptr(unsafe.Pointer(obj))

	// Затираем оригинальный указатель
	obj = nil

	fmt.Printf("Оригинальный указатель obj обнулен. rawAddr = 0x%X\n", rawAddr)
	fmt.Println("Запускаем runtime.GC()...")

	// Форсируем полный цикл сборки мусора
	runtime.GC()
	runtime.GC() // второй проход для гарантированного запуска финализаторов
	time.Sleep(100 * time.Millisecond)

	fmt.Println("Работа программы завершена.")
}
```

ℹ️ Срабатывание финализатора доказывает, что uintptr не предотвращает уничтожение объекта.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Оригинальный указатель obj обнулен. rawAddr = 0x...
# Запускаем runtime.GC()...
# >>> [GC ALERT] HeavyObject ID=42 УНИЧТОЖЕН СБОРЩИКОМ МУСОРА! <<<
# Работа программы завершена.
```

## Под капотом

В фазе `gcDrain` горутины-маркировщики читают корни из регистров и стеков. Для фрейма функции `main` переменная `obj` равна `nil`, а `rawAddr` помечена как скаляр в стековой карте. Объект не попадает в рабочую очередь (workbuf), а его бит в `gcBits` остается нулевым (белым). Фаза Sweep забирает его.

## Подводные камни

Попытка прочитать память по `rawAddr` после срабатывания финализатора — это классический Use-After-Free.

## На собеседовании

**Вопрос с собеседования:** Что такое conservative GC и почему Go использует precise GC?
**Ответ:** Консервативный GC (как в Boehm GC для C/C++) сканирует все машинные слова, считая любое число, попадающее в диапазон адресов кучи, потенциальным указателем. Точный (precise) GC в Go точно знает типы всех ячеек памяти благодаря метаданным компилятора. Это предотвращает утечки памяти и позволяет безопасно перемещать стек.
