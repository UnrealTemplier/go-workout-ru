# Lock-Free Bucket Map на atomic.CompareAndSwapPointer

## Условие

Создайте «свой sync.Map» на `unsafe`: массив buckets из `unsafe.Pointer`, используйте `atomic.CompareAndSwapPointer` для lock-free вставки и обновления значений. Запустите 100 параллельных горутин.

### Исходная формулировка

Создайте «свой `sync.Map`» на `unsafe`: массив buckets из `unsafe.Pointer`, используйте `atomic.CompareAndSwapPointer` для lock-free вставки. Объясните, почему в `atomic` операциях нельзя использовать `uintptr` — только `unsafe.Pointer`.

## Теория

Для сверхвысоких нагрузок (HighLoad) мьютексы `sync.Mutex` создают накладные расходы на context switch горутин в ядре планировщика при сильном contention.
Lock-free структуры данных опираются на атомарные аппаратные инструкции CPU (CMPXCHG на x86).

Пакет `sync/atomic` предоставляет функцию `CompareAndSwapPointer(addr *unsafe.Pointer, old, new unsafe.Pointer) bool`.
Она атомарно проверяет текущий адрес в ячейке и заменяет его на новый, гарантируя отсутствие гонок данных без блокировок.

## Решение по шагам

1. Определите структуру `Node struct { key string; val int; next unsafe.Pointer }`.
2. Создайте структуру `LockFreeMap` с массивом buckets типа `[]unsafe.Pointer`.
3. Реализуйте метод `Put(key string, val int)` с CAS-циклом (`for { CAS... }`).
4. Реализуйте `Get(key string) (int, bool)`.
5. Запустите 100 горутин параллельной записи и чтения, проверив целостность данных.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sync"
	"sync/atomic"
	"unsafe"
)

type Node struct {
	key  string
	val  int
	next unsafe.Pointer // *Node
}

type LockFreeMap struct {
	buckets []unsafe.Pointer
	mask    uint32
}

func NewLockFreeMap(size int) *LockFreeMap {
	return &LockFreeMap{
		buckets: make([]unsafe.Pointer, size),
		mask:    uint32(size - 1),
	}
}

func (m *LockFreeMap) hash(key string) uint32 {
	h := fnv.New32a()
	h.Write([]byte(key))
	return h.Sum32() & m.mask
}

func (m *LockFreeMap) Put(key string, val int) {
	idx := m.hash(key)
	newNode := &Node{key: key, val: val}
	newPtr := unsafe.Pointer(newNode)

	for {
		headPtr := atomic.LoadPointer(&m.buckets[idx])
		newNode.next = headPtr
		if atomic.CompareAndSwapPointer(&m.buckets[idx], headPtr, newPtr) {
			return
		}
	}
}

func (m *LockFreeMap) Get(key string) (int, bool) {
	idx := m.hash(key)
	curPtr := atomic.LoadPointer(&m.buckets[idx])

	for curPtr != nil {
		node := (*Node)(curPtr)
		if node.key == key {
			return node.val, true
		}
		curPtr = atomic.LoadPointer(&node.next)
	}
	return 0, false
}

func main() {
	m := NewLockFreeMap(16)
	var wg sync.WaitGroup

	// 100 параллельных горутин пишут и читают
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			key := fmt.Sprintf("k-%d", id%10)
			m.Put(key, id)
			_, _ = m.Get(key)
		}(i)
	}

	wg.Wait()
	fmt.Println("Все 100 горутин успешно выполнили CAS-операции!")
	for i := 0; i < 10; i++ {
		key := fmt.Sprintf("k-%d", i)
		if val, ok := m.Get(key); ok {
			fmt.Printf("%s -> %d\n", key, val)
		}
	}
}
```

ℹ️ atomic.CompareAndSwapPointer исключает необходимость мьютексов в bucket.


## Под капотом

`atomic.CompareAndSwapPointer` транслируется компилятором в инструкцию `LOCK CMPXCHGQ`. Префикс `LOCK` на x86 захватывает строку кэша (Cache Line Lock через протокол MESI/MOESI), делая операцию атомарной на уровне многоядерного процессора без участия планировщика ОС.

## Подводные камни

В lock-free односвязных списках при удалении узлов возникает классическая проблема ABA. Для простых append-only или immutable head-replace таблиц CAS-цикл работает безопасно.

## На собеседовании

**Вопрос с собеседования:** Как устроен `sync.Map` в стандартной библиотеке Go и какую роль там играет `atomic.Pointer`?
**Ответ:** `sync.Map` разделен на `read` (только чтение без блокировок через атомарный `atomic.Pointer`) и `dirty` (запись под `sync.Mutex`). Чтение и обновление существующих ключей происходит lock-free через атомарные операции со ссылками на значения (`entry.p`), что обеспечивает линейную масштабируемость на многоядерных машинах.
