# Zero-Allocation Object Pool на монолитной байтовой арене

## Условие

Создайте «object pool» без `sync.Pool`, используя `unsafe`: выделите большой `[]byte` (arena), разбейте на chunks фиксированного размера и возвращайте указатели через свободный список (free list). Покажите повторное использование блоков.

### Исходная формулировка

Создайте «object pool» без `sync.Pool`, используя `unsafe`: выделите большой `[]byte` (arena), разбейте на chunks фиксированного размера, ведите free list через `unsafe.Pointer`. Объясните, почему объекты без указателей не сканируются GC и как это ускоряет аллокацию при фиксированном размере.

## Теория

Стандартный `sync.Pool` сбрасывает свое содержимое при каждом запуске сборщика мусора (GC STW phase), если к пулу не было обращений. Для критичных к задержкам систем (HFT, сетевые шлюзы) это порождает периодические всплески latency (GC spikes).
Собственный пул фиксированных блоков на непрерывной арене памяти аллоцирует память один раз на старте сервиса.
Управление занятыми и свободными блоками реализуется через связный список индексов/указателей в свободном списке (Free List) за \(O(1)\) без аллокаций.

## Решение по шагам

1. Создайте структуру `ChunkPool struct { arena []byte; freeHead unsafe.Pointer; chunkSize uintptr }`.
2. В каждом свободном блоке разместите указатель на следующий свободный блок.
3. Реализуйте метод `Acquire() unsafe.Pointer`.
4. Реализуйте метод `Release(ptr unsafe.Pointer)`.
5. Продемонстрируйте выделение, возврат и переиспользование адресов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type ChunkPool struct {
	storage   []byte
	freeHead  unsafe.Pointer
	chunkSize uintptr
	capacity  int
}

func NewChunkPool(chunkSize uintptr, count int) *ChunkPool {
	totalSize := chunkSize * uintptr(count)
	buf := make([]byte, totalSize)

	pool := &ChunkPool{
		storage:   buf,
		chunkSize: chunkSize,
		capacity:  count,
	}

	// Инициализируем free list: в начале каждого блока сохраняем указатель на следующий блок
	base := unsafe.Pointer(&buf[0])
	for i := 0; i < count-1; i++ {
		cur := unsafe.Add(base, uintptr(i)*chunkSize)
		next := unsafe.Add(base, uintptr(i+1)*chunkSize)
		*(*unsafe.Pointer)(cur) = next
	}
	// Последний блок указывает на nil
	last := unsafe.Add(base, uintptr(count-1)*chunkSize)
	*(*unsafe.Pointer)(last) = nil

	pool.freeHead = base
	return pool
}

func (p *ChunkPool) Acquire() unsafe.Pointer {
	if p.freeHead == nil {
		panic("pool exhausted")
	}
	chunk := p.freeHead
	// Голова переходит на следующий свободный блок
	p.freeHead = *(*unsafe.Pointer)(chunk)
	return chunk
}

func (p *ChunkPool) Release(chunk unsafe.Pointer) {
	// Возвращенный блок становится новой головой
	*(*unsafe.Pointer)(chunk) = p.freeHead
	p.freeHead = chunk
}

type TaskPacket struct {
	ID   uint64
	Data [24]byte
}

func main() {
	chunkSize := unsafe.Sizeof(TaskPacket{})
	pool := NewChunkPool(chunkSize, 5)

	fmt.Printf("Создан пул на 5 чанков по %d байт\n", chunkSize)

	// Берем 2 объекта из пула
	p1 := (*TaskPacket)(pool.Acquire())
	p2 := (*TaskPacket)(pool.Acquire())
	p1.ID = 1001
	p2.ID = 1002

	fmt.Printf("Получен объект p1: %p (ID=%d)\n", p1, p1.ID)
	fmt.Printf("Получен объект p2: %p (ID=%d)\n", p2, p2.ID)

	// Возвращаем p1 обратно в пул
	pool.Release(unsafe.Pointer(p1))

	// Следующий Acquire вернет переиспользованный адрес p1!
	p3 := (*TaskPacket)(pool.Acquire())
	fmt.Printf("Получен объект p3: %p (должен совпадать с p1: %t)\n", p3, p3 == p1)
}
```

ℹ️ Техника intrusively linked free list не требует дополнительной памяти на указатели списка.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Создан пул на 5 чанков по 32 байт
# Получен объект p1: 0x...
# Получен объект p2: 0x...
# Получен объект p3: 0x... (должен совпадать с p1: true)
```

## Под капотом

Свободный список является интрузивным (Intrusive Free List): пока блок свободен, его первые 8 байт используются как указатель на следующий свободный блок. Когда блок выдается приложению, эти 8 байт перезаписываются пользовательскими данными. Это гарантирует нулевой overhead по памяти.

## Подводные камни

Двойное освобождение (Double Free) одного и того же блока разрушит цепочку связного списка, создав бесконечный цикл. Пул требует строгого контроля владения ресурсом.

## На собеседовании

**Вопрос с собеседования:** В чем ключевое отличие арены с Free List от стандартного `sync.Pool`?
**Ответ:** `sync.Pool` управляется рантаймом Go и очищается сборщиком мусора для предотвращения утечек памяти при изменении нагрузки. Кастомная арена с Free List держит память постоянно выделенной, гарантируя отсутствие пауз GC и нулевые аллокации даже при редких вызовах.
