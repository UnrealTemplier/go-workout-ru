# Zero-Copy со строками через unsafe.String и unsafe.StringData

## Условие

Создайте строку из слайса байт без копирования через `unsafe.String`, измените исходный слайс и посмотрите, изменится ли строка. Объясните, почему в Go 1.20+ `unsafe.String` заменил устаревший `reflect.StringHeader`.

### Исходная формулировка

**Работа с `unsafe.String` и `unsafe.StringData`.**: Создайте строку из слайса байт без копирования через `unsafe.String`, измените исходный слайс и посмотрите, изменится ли строка (нарушение иммутабельности). Обсудите последствия.

## Теория

До Go 1.20 разработчики использовали конструкцию:
```go
s := *(*string)(unsafe.Pointer(&slice))
```
или манипулировали типом `reflect.StringHeader`. Это нарушало безопасность типов и вызывало ложные срабатывания детектора GC.

В Go 1.20 были добавлены стандартные функции:
- `unsafe.String(ptr *byte, len IntegerType) string`
- `unsafe.StringData(str string) *byte`
Они официально легализуют zero-copy преобразования срезов и строк.

## Решение по шагам

1. Создайте мутабельный слайс `buf := []byte{'G', 'o', 'l', 'a', 'n', 'g'}`.
2. Сконструируйте строку zero-copy: `str := unsafe.String(&buf[0], len(buf))`.
3. Убедитесь, что `str == "Golang"`.
4. Мутируйте первый байт слайса `buf[0] = 'H'`.
5. Распечатайте строку `str` и объясните мутацию.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	buf := []byte{'G', 'o', 'l', 'a', 'n', 'g'}

	// Создание строки без копирования (Zero-Copy)
	str := unsafe.String(&buf[0], len(buf))
	fmt.Printf("Исходная строка: %s\n", str)

	// Модифицируем байтовый буфер
	buf[0] = 'H'
	buf[1] = 'e'

	fmt.Printf("Строка после изменения буфера: %s\n", str)
	fmt.Printf("Указатели совпадают: %t\n", unsafe.SliceData(buf) == unsafe.StringData(str))
}
```

ℹ️ Строка str ссылается прямо на буфер buf, поэтому изменение слайса мутирует строку.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходная строка: Golang
# Строка после изменения буфера: Helang
# Указатели совпадают: true
```

## Под капотом

`unsafe.String` конструирует двухсловный заголовок строки `{ data: ptr, len: len }` на регистрах CPU за 1 инструкцию без вызова `runtime.rawstring`. Если базовый буфер `buf` аллоцирован на стеке или в куче, строка читает те же байты памяти.

## Подводные камни

Мутация строки задним числом через исходный слайс опасна в многопоточных программах: если строка используется как ключ мапы `map[string]T`, мутация байт сломает хэш и сделает значение в мапе недостижимым.

## На собеседовании

**Вопрос с собеседования:** Почему в Go 1.20 `reflect.StringHeader` и `reflect.SliceHeader` официально объявлены устаревшими (deprecated)?
**Ответ:** Поле `Data` в них имело тип `uintptr`. Преобразование указателя в `uintptr` скрывало объект от сборщика мусора. Функции `unsafe.String`, `unsafe.StringData`, `unsafe.Slice`, `unsafe.SliceData` принимают и возвращают настоящие указатели (`*byte`), гарантируя корректность работы GC.
