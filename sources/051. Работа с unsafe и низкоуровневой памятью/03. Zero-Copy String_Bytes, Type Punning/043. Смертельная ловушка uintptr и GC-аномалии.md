# Смертельная ловушка uintptr и GC-аномалии

## Условие

*Теоретически-практическое.* `uintptr` — это просто число, а не указатель. Если ты сохранишь адрес объекта в `uintptr`, а затем в Go-коде не останется живых ссылок на исходный объект, GC может переиспользовать или освободить эту память.
Напиши функцию, которая возвращает `uintptr` на аллоцированную переменную. В `main` вызови `runtime.GC()` и попробуй прочитать значение. Объясни, почему это UB (неопределенное поведение).

### Исходная формулировка

**Смертельная ловушка `uintptr` (GC-аномалия)**: *Теоретически-практическое.* `uintptr` — это просто число, а не указатель. Если ты сохранишь адрес объекта в `uintptr`, Garbage Collector не будет знать об этой связи. Если GC запустится и решит переместить объект (например, при сжатии стека), твой `uintptr` будет указывать на мусор. Осознай правило: **преобразования Pointer -> uintptr -> Pointer должны происходить в рамках одного выражения!**

## Теория

Тип `uintptr` в Go предназначен исключительно для вычисления целочисленных смещений и низкоуровневых системных вызовов (`syscall.Syscall`). 
Сборщик мусора Go использует точный (precise) трехцветный алгоритм маркировки. Во время сканирования стека и кучи GC анализирует метаданные типов:
- Если слот памяти имеет тип указателя (`*T`, `unsafe.Pointer`), GC помечает целевой объект серым/черным и добавляет в очередь обхода.
- Если слот памяти имеет тип `uintptr`, GC игнорирует его значение, воспринимая его как обычное число (скаляр).

Следовательно, функция, возвращающая `uintptr` на локально выделенный объект, возвращает висячий адрес: объект уничтожается сразу после завершения функции.

## Решение по шагам

1. Напишите функцию `allocInt() uintptr`, которая выделяет `new(int)`, записывает в него значение 1337 и возвращает `uintptr(unsafe.Pointer(ptr))`.
2. В функции `main` получите этот `uintptr`.
3. Запустите принудительную сборку мусора `runtime.GC()`.
4. Создайте множество других аллокаций, чтобы перезаписать освобожденную память.
5. Попробуйте разыменовать `uintptr` через `unsafe.Pointer` и покажите искажение данных.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

// allocEscape возвращает адрес объекта, но в виде числа uintptr
// ВНИМАНИЕ: Это антипаттерн и UB!
func allocEscape() uintptr {
	x := new(int)
	*x = 1337
	return uintptr(unsafe.Pointer(x))
}

func main() {
	addr := allocEscape()

	// На момент вызова GC на объект x нет ни одного указателя
	runtime.GC()

	// Перезаписываем освобожденную страницу кучи
	for i := 0; i < 1000; i++ {
		_ = fmt.Sprintf("мусорные аллокации %d", i)
	}

	// Попытка прочитать память по мертвому адресу
	p := (*int)(unsafe.Pointer(addr))
	fmt.Printf("Адрес: 0x%x, Значение: %d (ожидалось 1337, но получили повреждение памяти!)\n", addr, *p)
}
```

ℹ️ Компилятор Go и go vet распознают этот паттерн как грубое нарушение правил unsafe.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Адрес: 0x...c0000180b0, Значение: 0 или произвольный мусор
```

## Под капотом

В фазе Sweep сборщика мусора блок `mspan`, содержащий объект `x`, отмечается как свободный. Следующий вызов `runtime.makeslice` или `newobject` выделяет в этом слоте памяти совершенно другие данные (строки форматирования). Чтение по старому адресу возвращает чужие байты или приводит к панике сегментации.

## Подводные камни

Никогда не возвращайте `uintptr` из функции, если он получен из локального указателя на память Go. Возвращать `uintptr` допустимо только для mmap-областей ОС или адресов C-библиотек.

## На собеседовании

**Вопрос с собеседования:** В каких единственных случаях допустимо преобразовывать `unsafe.Pointer` в `uintptr` согласно правилам unsafe.Pointer?
**Ответ:** 1) Внутри выражения адресной арифметики `unsafe.Pointer(uintptr(p) + offset)` на одной строке; 2) При передаче аргументов в `syscall.Syscall(trap, uintptr(p), ...)`, где компилятор генерирует скрытые гарантии удержания указателя до завершения syscall; 3) При использовании функции `reflect.Value.Pointer` / `UnsafeAddr` с немедленным кастом.
