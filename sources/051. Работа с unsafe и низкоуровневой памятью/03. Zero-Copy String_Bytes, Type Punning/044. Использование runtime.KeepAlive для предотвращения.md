# Использование runtime.KeepAlive для предотвращения ранней сборки мусора

## Условие

Запиши адрес Go-объекта в `uintptr` переменную. Сделай так, чтобы объект больше не использовался в Go-коде. Вызови `runtime.GC()`. Продемонстрируй, как `runtime.KeepAlive` защищает память от преждевременного сбора.

### Исходная формулировка

**[Каверзный кейс — Сборщик мусора и `uintptr`]**: Запиши адрес Go-объекта в `uintptr` переменную. Сделай так, чтобы объект больше не использовался в Go-коде. Вызови `runtime.GC()`. Попробуй разыменовать `uintptr` (через `unsafe.Pointer`). Пойми, почему `uintptr` — это просто число, и GC не считает его корнем (указатель мог быть перемещен или удален).

## Теория

Оптимизатор компилятора Go производит анализ времени жизни переменных (Liveness Analysis). Если компилятор видит, что переменная больше синтаксически не читается в оставшейся части функции, он исключает её указатель из стековой карты (stack map) прямо посреди выполнения функции!
Если указатель сохранен в дескрипторе ОС или `uintptr`, GC считает объект мертвым и может вызвать финализатор (`runtime.SetFinalizer`) или освободить буфер памяти.

Для предотвращения ранней утилизации объекта используется функция `runtime.KeepAlive(x)`. Она гарантирует, что объект `x` считается живым вплоть до точки вызова `KeepAlive`.

## Решение по шагам

1. Создайте структуру `Resource struct { data []byte }`.
2. Установите финализатор через `runtime.SetFinalizer`.
3. Сохраните адрес буфера в `uintptr`.
4. Продемонстрируйте раннюю утилизацию объекта без `KeepAlive`.
5. Добавьте `runtime.KeepAlive(res)` в конец и покажите корректное удержание памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

type SafeBuffer struct {
	data []byte
}

func main() {
	buf := &SafeBuffer{data: make([]byte, 64)}
	buf.data[0] = 42

	// Устанавливаем финализатор
	runtime.SetFinalizer(buf, func(b *SafeBuffer) {
		fmt.Println("[GC Finalizer] SafeBuffer уничтожен сборщиком мусора!")
	})

	rawPtr := uintptr(unsafe.Pointer(&buf.data[0]))

	// Запускаем GC
	runtime.GC()
	time.Sleep(50 * time.Millisecond)

	// Читаем через rawPtr
	val := *(*byte)(unsafe.Pointer(rawPtr))
	fmt.Printf("Значение через rawPtr: %d\n", val)

	// Гарантируем, что buf не собран до этой строки
	runtime.KeepAlive(buf)
	fmt.Println("Программа завершена успешно с KeepAlive!")
}
```

ℹ️ runtime.KeepAlive(buf) заставляет компилятор удерживать ссылку на buf до самого конца функции.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Значение через rawPtr: 42
# Программа завершена успешно с KeepAlive!
```

## Под капотом

`runtime.KeepAlive` реализована как пустая функция с директивой `//go:noinline`. Передача переменной в нее создает искусственное использование (use-def chain), благодаря которому компилятор Go сохраняет указатель в стековой карте живых корней (roots) вплоть до этой точки вызова.

## Подводные камни

В коде с CGO и `syscall` отсутствие `runtime.KeepAlive` — самая частая причина плавающих segfault. Дескриптор файла или C-указатель закрывается финализатором прямо во время системного вызова.

## На собеседовании

**Вопрос с собеседования:** В каких случаях в production-коде обязательно вызывать `runtime.KeepAlive`?
**Ответ:** 1) При передаче указателя на память Go в системные вызовы или CGO через дескриптор или `uintptr`; 2) При использовании объектов с `runtime.SetFinalizer`, закрывающим нативный ресурс (сокет, дескриптор файла); 3) В кастомных пулах памяти и arena-аллокаторах.
