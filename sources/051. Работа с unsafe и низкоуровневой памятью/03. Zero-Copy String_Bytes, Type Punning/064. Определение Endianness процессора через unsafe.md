# Определение Endianness процессора через unsafe

## Условие

Определи архитектуру своего процессора (Little Endian или Big Endian). Создай `var i int32 = 0x01020304`. С помощью `unsafe.Pointer` прочитай первый байт памяти. Если там `0x04` — это Little-Endian, если `0x01` — Big-Endian. Напиши тест-функцию `IsLittleEndian() bool`.

### Исходная формулировка

**Endianness (Порядок байт)**: Определи архитектуру своего процессора (Little Endian или Big Endian). Создай `var i int32 = 0x01020304`. С помощью `unsafe.Pointer` приведи указатель к `*byte` (указателю на 1 байт), разыменуй и выведи. Если выведет `4` — у тебя Little Endian (как у большинства), если `1` — Big Endian.

## Теория

Порядок байт (**Endianness**) определяет последовательность размещения байт многобайтовых чисел в оперативной памяти:
- **Little-Endian** (младший байт по младшему адресу): характерно для x86-64, AMD64, ARM64 (Apple Silicon, современные серверы). Число `0x01020304` в памяти лежит как `[04, 03, 02, 01]`.
- **Big-Endian** (старший байт по младшему адресу, Network Byte Order): характерно для мэйнфреймов IBM s390x, сетевых маршрутизаторов. Число лежит как `[01, 02, 03, 04]`.

С помощью `unsafe.Pointer` первый физический байт переменной читается мгновенно без вызова системных утилит.

## Решение по шагам

1. Объявите функцию `IsLittleEndian() bool`.
2. Создайте переменную `var val int32 = 0x01020304`.
3. Получите указатель `*byte` на её адрес через `(*byte)(unsafe.Pointer(&val))`.
4. Сравните значение первого байта с `0x04`.
5. Выведите архитектуру текущей среды исполнения.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

// IsLittleEndian определяет порядок байт процессора
func IsLittleEndian() bool {
	var val int32 = 0x01020304
	firstByte := *(*byte)(unsafe.Pointer(&val))
	return firstByte == 0x04
}

func main() {
	var val int32 = 0x01020304
	bytePtr := (*byte)(unsafe.Pointer(&val))
	rawBytes := unsafe.Slice(bytePtr, 4)

	fmt.Printf("Число int32: 0x%08X\n", val)
	fmt.Printf("Расположение байтов в RAM: [% x]\n", rawBytes)
	fmt.Printf("Первый байт (младший адрес): 0x%02X\n", firstByte(val))

	if IsLittleEndian() {
		fmt.Printf("Порядок байт: Little-Endian (Архитектура: %s/%s)\n", runtime.GOOS, runtime.GOARCH)
	} else {
		fmt.Printf("Порядок байт: Big-Endian (Архитектура: %s/%s)\n", runtime.GOOS, runtime.GOARCH)
	}
}

func firstByte(v int32) byte {
	return *(*byte)(unsafe.Pointer(&v))
}
```

ℹ️ Пакет unsafe позволяет читать физические ячейки RAM точно в порядке их адресации шиной данных.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Число int32: 0x01020304
# Расположение байтов в RAM: [04 03 02 01]
# Первый байт (младший адрес): 0x04
# Порядок байт: Little-Endian (Архитектура: linux/amd64)
```

## Под капотом

Шина адреса процессора обращается к памяти байтами по возрастанию адресов: \(A, A+1, A+2, A+3\). В Little-Endian младшие разряды числа (LSB — Least Significant Byte) помещаются в ячейку с наименьшим адресом \(A\), что упрощает арифметические операции сложения с переносом на уровне кремниевой логики АЛУ.

## Подводные камни

При чтении сетевых пакетов (TCP/IP) протоколы всегда требуют Big-Endian. Чтение многобайтовых целых чисел напрямую через `unsafe` на машинах x86 приведет к перевернутым значениям портов и длин пакетов. Для сетевых полей используйте `binary.BigEndian`.

## На собеседовании

**Вопрос с собеседования:** Почему сетевой порядок байт (Network Byte Order) — это Big-Endian, а серверы x86/ARM работают в Little-Endian?
**Ответ:** Исторически ранние сетевые протоколы ARPANET/RFC 1700 приняли Big-Endian, так как он соответствует чтению чисел человеком слева направо. Микропроцессоры x86 и современные ARM используют Little-Endian для ускорения сложения чисел переменной длины в АЛУ. Для совместимости сокеты конвертируют числа функциями `htons`/`ntohs` или `binary.BigEndian`.
