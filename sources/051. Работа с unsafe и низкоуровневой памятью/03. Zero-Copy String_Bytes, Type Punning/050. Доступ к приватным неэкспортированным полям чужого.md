# Доступ к приватным неэкспортированным полям чужого пакета

## Условие

Создай пакет `secret`, в нем структуру с полем `password string` (с маленькой буквы). Импортируй её в `main`. Используя `unsafe.Pointer` и смещения, прочитай и измени это поле. Покажи, что инкапсуляция Go — соглашение компилятора, а не защита памяти.

### Исходная формулировка

**Чтение приватных полей**: Создай пакет `secret`, в нем структуру с полем `password string` (с маленькой буквы). Импортируй её в `main`. Используя `unsafe.Pointer` и арифметику указателей (зная смещение поля), прочитай и измени этот "недоступный" пароль.

## Теория

Инкапсуляция в языке Go (экспортируемые идентификаторы с заглавной буквы и неэкспортируемые с маленькой) является ограничением на уровне компилятора и AST-парсера, а не аппаратной защитой памяти.
На уровне машинного кода структура в Go — это просто блок смежных байт памяти.
Если известна внутренняя раскладка полей структуры, `unsafe.Pointer` позволяет прочитать или модифицировать абсолютно любое приватное поле любого стороннего пакета.

## Решение по шагам

1. Создайте структуру `Account` с приватным полем `token string`.
2. Создайте дублирующую теневую структуру `AccountShadow` с тем же расположением полей.
3. Преобразуйте `*Account` в `*AccountShadow` через `unsafe.Pointer`.
4. Прочитайте и измените значение приватного поля.
5. Продемонстрируйте изменение исходного объекта.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// Имитируем тип из внешнего пакета с приватными полями
type SecretVault struct {
	ID        int
	apiKey    string // приватное неэкспортированное поле
	isBlocked bool   // приватное поле
}

func NewVault(id int, key string) SecretVault {
	return SecretVault{ID: id, apiKey: key, isBlocked: true}
}

// Shadow-структура с идентичной раскладкой памяти, но публичными полями
type SecretVaultShadow struct {
	ID        int
	ApiKey    string
	IsBlocked bool
}

func main() {
	vault := NewVault(101, "SUPER_SECRET_TOKEN_999")
	fmt.Printf("Исходный vault (ID=%d, apiKey скрыт компилятором)\n", vault.ID)

	// Взлом приватных полей через приведение теневой структуры
	shadow := (*SecretVaultShadow)(unsafe.Pointer(&vault))

	fmt.Printf("Прочитанный приватный apiKey: %q\n", shadow.ApiKey)
	fmt.Printf("Прочитанный приватный isBlocked: %t\n", shadow.IsBlocked)

	// Модифицируем приватные поля
	shadow.ApiKey = "HACKED_BY_UNSAFE"
	shadow.IsBlocked = false

	// Проверяем изменение через теневой указатель
	fmt.Printf("Новый apiKey: %q, статус: isBlocked=%t\n", shadow.ApiKey, shadow.IsBlocked)
}
```

ℹ️ Теневая структура (Shadow Struct) — самый удобный способ маппинга приватных полей.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Исходный vault (ID=101, apiKey скрыт компилятором)
# Прочитанный приватный apiKey: "SUPER_SECRET_TOKEN_999"
# Прочитанный приватный isBlocked: true
# Новый apiKey: "HACKED_BY_UNSAFE", статус: isBlocked=false
```

## Под капотом

Компилятор Go генерирует адресацию полей структуры как `base_ptr + offset`. Имя поля и модификатор доступа отбрасываются на этапе генерации SSA/машинного кода (сохраняясь лишь в таблицах отладки DWARF и `reflect.Type`). Поэтому в рантайме нет никакой разницы между обращением к публичному или приватному полю.

## Подводные камни

Внутренняя раскладка полей библиотек не является стабильным публичным API (SemVer). Обновление минорной версии чужого пакета может изменить порядок полей, тип или выравнивание, что молча сломает вашу программу.

## На собеседовании

**Вопрос с собеседования:** Допустимо ли в production Go-сервисах использовать доступ к приватным полям через `unsafe`?
**Ответ:** Категорически не рекомендуется в бизнес-логике. Допустимо исключительно в узкоспециализированных системных библиотеках (например, monkey-patching для unit-тестов, fast-path сериализаторы, глубокая телеметрия), с обязательными тестами на совместимость раскладки памяти структуры.
