# Сборка и статическая линковка библиотеки .a через #cgo LDFLAGS

## Условие

Реализуйте «калькулятор» на C с простыми операциями в отдельном `.c` файле. Соберите как static library (`.a`) через `ar rcs`, положите рядом и слинкуйте через директиву `#cgo LDFLAGS: -L. -lcalc`. Продемонстрируйте вызов из Go.

### Исходная формулировка

Реализуйте «калькулятор» на C с простыми операциями. Соберите как **static library** (`.a`) и слинкуйте через `#cgo LDFLAGS`. Объясните разницу между static и dynamic linking в контексте самодостаточного Go-бинарника.

## Теория

В реальных enterprise-проектах Си-код редко пишут в комментариях преамбулы: обычно линкуют уже существующие Си-библиотеки (OpenSSL, SQLite, zstd, libcurl).
Линковка может быть:
- **Статической (`.a`)**: объектный код библиотеки Си на этапе сборки копируется внутрь итогового исполняемого файла Go. Бинарник становится автономным.
- **Динамической (`.so` / `.dylib` / `.dll`)**: бинарник требует наличия установленного файла библиотеки в операционной системе во время запуска.

Директива `#cgo LDFLAGS: -L${SRCDIR} -lmylib` указывает компоновщику искать библиотеку `libmylib.a` в текущей директории проекта.

## Решение по шагам

1. Создайте файл `calc.h` с объявлением `int c_add(int a, int b);`.
2. Создайте файл `calc.c` с реализацией.
3. Скомпилируйте объектный файл: `gcc -c calc.c -o calc.o`.
4. Соберите статическую библиотеку: `ar rcs libcalc.a calc.o`.
5. В Go файле добавьте `#cgo LDFLAGS: -L${SRCDIR} -lcalc` и подключите `"calc.h"`.
6. Вызовите `C.c_add(50, 70)` и проверьте работу.

## Код решения

**`calc.h`**

```c
#ifndef CALC_H
#define CALC_H

int c_add(int a, int b);
int c_sub(int a, int b);

#endif
```

**`calc.c`**

```c
#include "calc.h"

int c_add(int a, int b) {
    return a + b;
}

int c_sub(int a, int b) {
    return a - b;
}
```

**`main.go`**

```go
package main

/*
#cgo LDFLAGS: -L${SRCDIR} -lcalc
#include "calc.h"
*/
import "C"
import "fmt"

func main() {
	x, y := 100, 45
	sum := C.c_add(C.int(x), C.int(y))
	diff := C.c_sub(C.int(x), C.int(y))

	fmt.Printf("Вызов из статической библиотеки libcalc.a:\n")
	fmt.Printf("  %d + %d = %d\n", x, y, int(sum))
	fmt.Printf("  %d - %d = %d\n", x, y, int(diff))
}
```

ℹ️ ${SRCDIR} автоматически заменяется CGO на абсолютный путь к папке с исходным кодом пакета.

**`Терминал`**

```bash
gcc -c calc.c -o calc.o
ar rcs libcalc.a calc.o
go run main.go
# Вывод:
# Вызов из статической библиотеки libcalc.a:
#   100 + 45 = 145
#   100 - 45 = 55
```

## Под капотом

Переменная `${SRCDIR}` вычисляется утилитой `go build`. Компоновщик `ld` извлекает объектный код функций `c_add` и `c_sub` из архива `libcalc.a` и внедряет их прямо в сегмент `.text` исполняемого файла Go. В результате итоговый бинарник не требует присутствия `libcalc.a` на сервере при развертывании.

## Подводные камни

Если забыть флаг `-L${SRCDIR}`, компоновщик будет искать библиотеку только в системных путях `/usr/lib`, `/usr/local/lib` и выдаст фатальную ошибку `cannot find -lcalc`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `#cgo LDFLAGS: -L. -lfoo` и `#cgo LDFLAGS: -L${SRCDIR} -lfoo`?
**Ответ:** Относительный путь `-L.` указывает на текущую рабочую директорию запуска команды (CWD). Если запустить сборку из другой директории или использовать кэш `go build`, линковка сломается. Макрос `${SRCDIR}` гарантирует абсолютный путь к каталогу пакета Go независимо от того, откуда запущена сборка.
