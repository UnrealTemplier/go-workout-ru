# Сравнение производительности: Go vs CGO vs Pure C

## Условие

Напишите бенчмарк, сравнивающий вызов C-функции с пустой Go-функцией. Измерьте накладные расходы на переход между мирами. Сравните время выполнения плотного цикла вычислений на чистом Go и через CGO.

### Исходная формулировка

**Накладные расходы cgo.**: Напишите бенчмарк, сравнивающий вызов C-функции с пустой Go-функцией. Измерьте накладные расходы на переход между мирами. Сравните с чисто C-программой.

## Теория

CGO переход имеет фиксированную стоимость ~50–100 нс на вызов.
Если Си-функция выполняет элементарную операцию (сложение, поиск символа), вызов через CGO будет в **десятки раз медленнее**, чем чистая реализация на Go!

Однако если Си-функция выполняет тяжелую математику (вычисление хеша SHA-256 на 10 МБ буфере, матричное умножение \(1000 \times 1000\)), время работы функции Си (миллисекунды) многократно перекрывает накладные расходы CGO (наносекунды), и использование CGO становится оправданным.

## Решение по шагам

1. Напишите на Go функцию вычисления факториала или суммы ряда.
2. Напишите аналогичную функцию на Си в преамбуле.
3. Проведите сравнительный замер времени на 1 000 000 итераций для легкой операции (одно сложение).
4. Проведите замер для тяжелой операции (сумма ряда на 10 000 итераций внутри Си).
5. Сделайте инженерный вывод о границах применимости CGO.

## Код решения

**`main.go`**

```go
package main

/*
// Легкая операция
static inline int c_add(int a, int b) {
    return a + b;
}

// Тяжелая операция (батчинг внутри C)
long long c_heavy_sum(int n) {
    long long s = 0;
    for (int i = 0; i < n; i++) {
        s += i;
    }
    return s;
}
*/
import "C"
import (
	"fmt"
	"time"
)

//go:noinline
func goAdd(a, b int) int {
	return a + b
}

func main() {
	const iters = 2_000_000

	// Тест 1: Мелкие вызовы
	startGo := time.Now()
	for i := 0; i < iters; i++ {
		_ = goAdd(i, 1)
	}
	durGo := time.Since(startGo)

	startC := time.Now()
	for i := 0; i < iters; i++ {
		_ = C.c_add(C.int(i), 1)
	}
	durC := time.Since(startC)

	fmt.Println("=== Тест 1: Легкие операции (2 млн вызовов) ===")
	fmt.Printf("Go Add:  %v (%.2f нс/оп)\n", durGo, float64(durGo.Nanoseconds())/iters)
	fmt.Printf("CGO Add: %v (%.2f нс/оп)\n", durC, float64(durC.Nanoseconds())/iters)
	fmt.Printf("Штраф CGO: %.1fx раз медленнее!\n\n", float64(durC)/float64(durGo))

	// Тест 2: Тяжелая пакетная операция (один вызов CGO на 10 млн циклов внутри C)
	startHeavy := time.Now()
	sum := C.c_heavy_sum(10_000_000)
	durHeavy := time.Since(startHeavy)

	fmt.Println("=== Тест 2: Пакетная тяжелая операция ===")
	fmt.Printf("1 вызов C.c_heavy_sum(10M): %v (сумма: %d)\n", durHeavy, int64(sum))
	fmt.Println("Вывод: Векторизация и батчинг полностью нивелируют overhead CGO!")
}
```

ℹ️ Батчинг вычислений внутри Си — ключевой паттерн оптимизации систем с CGO.

**`Терминал`**

```bash
go run main.go
# Вывод:
# === Тест 1: Легкие операции (2 млн вызовов) ===
# Go Add:  3.2ms (1.60 нс/оп)
# CGO Add: 98.5ms (49.25 нс/оп)
# Штраф CGO: 30.8x раз медленнее!
#
# === Тест 2: Пакетная тяжелая операция ===
# 1 вызов C.c_heavy_sum(10M): 5.1ms (сумма: 49999995000000)
# Вывод: Векторизация и батчинг полностью нивелируют overhead CGO!
```

## Под капотом

Тест 1 наглядно показывает закон Амдала в CGO: накладные расходы переключения контекста `asmcgocall` полностью доминируют над полезной нагрузкой функции `add`. В тесте 2 накладные расходы CGO (50 нс) составляют менее 0.001% от общего времени выполнения цикла Си (5 мс).

## Подводные камни

Замена чистых Go библиотек на Си-обертки «ради производительности» часто приводит к противоположному эффекту — сервис начинает работать значительно медленнее из-за постоянного переключения стеков.

## На собеседовании

**Вопрос с собеседования:** Почему в Go SQLite драйвер `modernc.org/sqlite` (транслированный из C в чистый Go через ccgo) часто работает конкурентнее, чем популярный `mattn/go-sqlite3` на CGO?
**Ответ:** Потому что чистый Go бинарник не тратит 50-100 нс на каждый вызов sqlite API, не переключает стеки, не отцепляет процессор P от потока M и не создает дополнительной нагрузки на системный планировщик потоков ОС при сотнях параллельных запросов.
