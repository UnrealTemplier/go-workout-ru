# Утечка памяти при C.CString и безопасный defer C.free

## Условие

Тебе нужно передать Go-строку в C-функцию `puts`. Передай её через `C.CString(goStr)`. Пойми, что `C.CString` выделяет память через `malloc` в куче C, которую Go GC не видит! Обязательно добавь `defer C.free(unsafe.Pointer(cStr))` (потребуется импорт `stdlib.h`). Продемонстрируй утечку памяти в цикле без free.

### Исходная формулировка

**Go String -> C String (Утечки памяти!)**: Тебе нужно передать Go-строку в C-функцию `puts`. Передай её через `C.CString(goStr)`. Пойми, что `C.CString` выделяет память через `malloc` в куче C, которую Go GC не видит! Обязательно добавь `defer C.free(unsafe.Pointer(cStr))` (потребуется импорт `stdlib.h`).

## Теория

Каждый вызов `C.CString(s)` запрашивает у системного аллокатора кучи Си `len(s) + 1` байт памяти.
Если в коде забыть освободить память через `C.free`:
```go
for i := 0; i < 1_000_000; i++ {
    _ = C.CString("leaking memory") // утечка 15 байт на каждой итерации!
}
```
Сборщик мусора Go (`runtime.GC()`) не имеет никакой информации об этих аллокациях, так как они находятся в адресном пространстве glibc. Память процесса будет монотонно расти, пока не сработает лимит Kubernetes cgroup.

## Решение по шагам

1. Подключите `<stdlib.h>`.
2. Напишите функцию `safeCall()`, которая выделяет C-строку и немедленно регистрирует `defer C.free()`.
3. Напишите функцию `leakDemo()`, иллюстрирующую прирост памяти.
4. Проверьте замер потребления памяти операционной системы через `/proc/self/status` или `runtime.MemStats`.
5. Объясните важность детерминированного освобождения.

## Код решения

**`main.go`**

```go
package main

/*
#include <stdio.h>
#include <stdlib.h>
*/
import "C"
import (
	"fmt"
	"unsafe"
)

func safePrint(msg string) {
	// Выделяем C-строку
	cMsg := C.CString(msg)

	// Гарантированное освобождение в LIFO-порядке при выходе из safePrint
	defer C.free(unsafe.Pointer(cMsg))

	C.puts(cMsg)
}

func main() {
	messages := []string{
		"Сообщение 1: Память выделена в куче Си",
		"Сообщение 2: Память освобождена через defer C.free",
		"Сообщение 3: GC Go не участвует в управлении этой памятью",
	}

	for _, m := range messages {
		safePrint(m)
	}

	fmt.Println("Все строки успешно выведены без единой утечки памяти!")
}
```

ℹ️ defer C.free внутри локальной функции гарантирует мгновенное освобождение после каждого вызова.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Сообщение 1: Память выделена в куче Си
# Сообщение 2: Память освобождена через defer C.free
# Сообщение 3: GC Go не участвует в управлении этой памятью
# Все строки успешно выведены без единой утечки памяти!
```

## Под капотом

`defer C.free` помещает структуру вызова `_defer` в стек текущей горутины. При возврате из функции компилятор генерирует вызов функции очистки, которая передает указатель Си-аллокатору. `glibc malloc` возвращает блок памяти в свободный двусвязный список `bins` для повторного использования.

## Подводные камни

Передача `nil` в `C.free` в C99 разрешена (no-op), но если передать в `C.free` невалидный указатель (например, указатель на память Go или указатель со смещением), glibc немедленно завершит процесс аварийной ошибкой `free(): invalid pointer`.

## На собеседовании

**Вопрос с собеседования:** Какими профилировщиками можно обнаружить утечку памяти в CGO, если `go tool pprof heap` показывает плоский стабильный график?
**Ответ:** Стандартный `pprof heap` видит только аллокации Go кучи. Для поиска утечек в Си-коде и `C.CString` используются профилировщики нативного уровня: **Valgrind (Memcheck)**, Google **TCMalloc / Heap Profiler**, jemalloc profiling, а также санитайзеры компилятора Clang/GCC **AddressSanitizer (ASan)** и ebpf-утилиты `memleak` из пакета BCC.
