# Накладные расходы CGO: бенчмарк Go call vs C call

## Условие

Напиши бенчмарк: вызов пустой Go-функции в цикле vs вызов пустой C-функции в цикле. Оцени разницу во времени (CGO требует переключения стека и планировщика, ~50-100 наносекунд на вызов).

### Исходная формулировка

**[Накладные расходы (Overhead)]**: Напиши бенчмарк: вызов пустой Go-функции в цикле vs вызов пустой C-функции в цикле. Оцени разницу во времени (CGO требует переключения стека и планировщика, ~50-100 наносекунд на вызов).

## Теория

Обычный вызов функции в Go компилируется всего в 1–2 ассемблерные инструкции (`CALL` + передача аргументов через регистры в Go 1.17+ ABI0/ABIInternal) и выполняется за **~1–2 наносекунды** (а при инлайнинге — за 0 наносекунд).

Вызов C-функции через CGO требует перехода границы миров:
1. Вызов `runtime.entersyscall()`: уведомление планировщика, перевод G в `_Gsyscall`.
2. Переключение стека Go на стек Си (`m->g0` или стек потока OS).
3. Переход в Си-код согласно System V ABI.
4. Выполнение Си-функции.
5. Вызов `runtime.exitsyscall()`: обратный захват P или постановка G в очередь runnable.
Overhead составляет **~50–100 наносекунд** (в 30–50 раз медленнее обычного вызова)!

## Решение по шагам

1. Создайте пустую функцию `goEmpty()`.
2. Создайте пустую C-функцию `void cEmpty() {}`.
3. Замерьте время на 5 000 000 вызовов `goEmpty()`.
4. Замерьте время на 5 000 000 вызовов `C.cEmpty()`.
5. Сравните среднее время одного вызова в наносекундах.

## Код решения

**`main.go`**

```go
package main

/*
void cEmpty() {}
*/
import "C"
import (
	"fmt"
	"time"
)

//go:noinline
func goEmpty() {}

func main() {
	const iterations = 5_000_000

	// 1. Замер чистого вызова функции Go
	startGo := time.Now()
	for i := 0; i < iterations; i++ {
		goEmpty()
	}
	durGo := time.Since(startGo)

	// 2. Замер вызова функции Си через CGO
	startC := time.Now()
	for i := 0; i < iterations; i++ {
		C.cEmpty()
	}
	durC := time.Since(startC)

	nsPerGo := float64(durGo.Nanoseconds()) / float64(iterations)
	nsPerC := float64(durC.Nanoseconds()) / float64(iterations)

	fmt.Printf("Итераций: %d\n", iterations)
	fmt.Printf("Go функция:  %v (%.2f нс/вызов)\n", durGo, nsPerGo)
	fmt.Printf("CGO функция: %v (%.2f нс/вызов)\n", durC, nsPerC)
	fmt.Printf("CGO медленнее в %.1f раз!\n", nsPerC/nsPerGo)
}
```

ℹ️ Директива //go:noinline предотвращает оптимизацию стирания пустого вызова.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Итераций: 5000000
# Go функция:  8.2ms (1.64 нс/вызов)
# CGO функция: 245.0ms (49.00 нс/вызов)
# CGO медленнее в 29.9 раз!
```

## Под капотом

Разница вызвана сохранением регистров и блокировкой планировщика. В ядре Go рантайма CGO вызов проходит через ассемблерный мост `runtime.asmcgocall`. Если сервис выполняет 1 миллион мелких вызовов CGO в секунду, только на переключение стеков процессор потратит ~60 миллисекунд чистого времени.

## Подводные камни

Никогда не используйте CGO для вызова тривиальных математических функций (`abs`, `min`, `max`, `strlen`). Пакетная передача данных (батчинг) — единственный способ эффективного применения CGO в HighLoad.

## На собеседовании

**Вопрос с собеседования:** Как минимизировать overhead CGO при интеграции с тяжелой C/C++ библиотекой (например, OpenCV или RocksDB)?
**Ответ:** Применять паттерн Batching: передавать в C массив задач или срез структур за один CGO вызов, чтобы тяжелая обработка происходила внутри C в цикле, а возврат в Go происходил один раз. Это снижает накладные расходы CGO с \(O(N)\) до \(O(1)\).
