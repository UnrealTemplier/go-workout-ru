# Безопасность данных: Dangling Pointers при удержании Go-памяти в Си

## Условие

Покажите классическую ошибку безопасности: передайте указатель на Go-переменную в C, сохраните его там в глобальной статической переменной, а в Go выйдите из функции. Запустите сборщик мусора `runtime.GC()` и покажите, почему Си-указатель стал висячим (Dangling Pointer).

### Исходная формулировка

**Безопасность данных при передаче указателей.**: Покажите ошибку: передайте указатель на Go-переменную в C, сохраните его там глобально, а в Go освободите память (например, выйдите из функции). Позже C попытается обратиться по висячему указателю. Обсудите правила `cgo` о передаче указателей в C.

## Теория

Сборщик мусора Go отслеживает только те объекты, на которые есть ссылки из корневого набора (Roots: регистры, стеки активных горутин, глобальные переменные пакетов Go).
Если адрес объекта кучи Go передан в Си и сохранен **только в статической памяти Си**:
```c
static void* global_c_ptr;
void store_ptr(void* p) { global_c_ptr = p; }
```
Сборщик мусора Go не сканирует глобальные переменные Си!
При следующем цикле GC объект в куче Go будет признан мертвым и уничтожен, а глобальный C-указатель превратится в фатальный **Dangling Pointer**.

## Решение по шагам

1. В преамбуле объявите глобальную Си-переменную `static int* cached_ptr;`.
2. Напишите Си-функцию `void cache_pointer(int* p)` и `int read_cached()`.
3. В Go локально выделите `data := new(int); *data = 777`.
4. Сохраните адрес в Си через `C.cache_pointer`.
5. Обнулите локальный указатель, вызовите `runtime.GC()` и продемонстрируйте разрушение данных.

## Код решения

**`main.go`**

```go
package main

/*
#include <stdio.h>

// Статический указатель в мире Си
static int* cached_ptr = NULL;

void cache_pointer(int* p) {
    cached_ptr = p;
}

int read_cached() {
    if (cached_ptr == NULL) return -1;
    return *cached_ptr;
}
*/
import "C"
import (
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

func storeInC() {
	// Объект выделяется в куче Go
	val := new(int)
	*val = 777

	// Сохраняем адрес в C-мире
	// ВНИМАНИЕ: Нарушение правил CGO!
	C.cache_pointer((*C.int)(unsafe.Pointer(val)))

	// val выходит из области видимости фрейма Go
}

func main() {
	storeInC()

	fmt.Println("Объект сохранен в Си. Запускаем сборщик мусора Go...")
	runtime.GC()
	runtime.GC()
	time.Sleep(50 * time.Millisecond)

	// Аллоцируем мусорные объекты для перезаписи освобожденного спана
	for i := 0; i < 1000; i++ {
		_ = fmt.Sprintf("перезапись спана кучи %d", i)
	}

	// Чтение из C по мертвому адресу
	result := C.read_cached()
	fmt.Printf("Результат чтения из Си: %d (ожидалось 777, но объект собран GC!)\n", int(result))
}
```

ℹ️ GC Go не сканирует память Си, поэтому хранение Go-указателей в C запрещено правилами CGO.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Объект сохранен в Си. Запускаем сборщик мусора Go...
# Результат чтения из Си: 0 или мусорное значение
```

## Под капотом

Во время фазы Mark фазы сборщик мусора обходит только графы объектов Go. Статическая секция `.bss` библиотеки Си не включена в список корней GC Go. Блок памяти в `mspan` отмечается свободным в `allocBits`. Следующий вызов `newobject` переиспользует этот слот, перезаписывая память другими данными.

## Подводные камни

В режиме `GODEBUG=cgocheck=1` рантайм Go пытается обнаружить подобные нарушения во время вызова функции, но долговременное удержание указателя в фоновых C-потоках отследить невозможно.

## На собеседовании

**Вопрос с собеседования:** Как безопасно связать долгоживущий Go-объект со структурой в Си без риска сборки мусора?
**Ответ:** 1) Использовать `cgo.NewHandle(obj)` (рекомендуемый стандарт Go 1.17+); 2) Сохранять объект в глобальной переменной Go (`var Registry sync.Map`), чтобы сборщик мусора видел живой корень из мира Go; 3) Использовать `runtime.Pinner` (Go 1.21+), явно запрещающий сборщику мусора перемещать или освобождать объект кучи.
