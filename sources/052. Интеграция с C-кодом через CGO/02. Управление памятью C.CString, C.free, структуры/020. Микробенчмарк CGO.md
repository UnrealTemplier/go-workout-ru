# Микробенчмарк CGO: анализ entersyscall, m-stack и cgocheck

## Условие

Напишите микробенчмарк на накладные расходы `cgo`: вызов пустой C-функции в цикле 1 млн раз. Сравните с вызовом пустой Go-функции. Объясните, откуда берутся ~100 нс задержки (переключение стеков, `runtime·entersyscall`, `pthread` locks, проверки `cgocheck`).

### Исходная формулировка

Напишите микробенчмарк на накладные расходы `cgo`: вызов пустой C-функции в цикле 1 млн раз. Сравните с вызовом пустой Go-функции. Объясните, откуда берутся ~100–200 ns (переключение стеков, `runtime·entersyscall`, `pthread` locks, проверки `cgocheck`).

## Теория

При каждом вызове функции Си рантайм Go выполняет сложный протокол безопасности:
1. **Переключение стеков**: Стек горутины (g-stack, с динамическим ростом) несовместим с требованиями Си ABI (фиксированный стек потока ОС от 2 до 8 МБ). Рантайм обязан переключить указатель стека `RSP` на системный стек потока `g0`.
2. **entersyscall / exitsyscall**: Горутина переводится в статус `_Gsyscall`. Планировщик фиксирует факт ухода потока в C.
3. **CGO Check (`GODEBUG=cgocheck=1`)**: Рантайм проверяет, не передает ли Go-код указатели на память Go, содержащую другие указатели на память Go (защита от подвисания указателей).
4. **Обработка сигналов**: Подготовка обработчиков `sigaction` на случай сбоя в Си.

## Решение по шагам

1. Создайте пустую C-функцию `void c_noop() {}`.
2. Создайте пустую Go-функцию `func goNoop()`.
3. Запустите 1 000 000 итераций в цикле.
4. Запустите программу с `GODEBUG=cgocheck=0` и `GODEBUG=cgocheck=2`.
5. Сравните влияние проверок памяти на latency.

## Код решения

**`main.go`**

```go
package main

/*
void c_noop() {}
*/
import "C"
import (
	"fmt"
	"time"
)

//go:noinline
func goNoop() {}

func main() {
	const count = 1_000_000

	// 1. Вызов Go
	t0 := time.Now()
	for i := 0; i < count; i++ {
		goNoop()
	}
	durGo := time.Since(t0)

	// 2. Вызов CGO
	t1 := time.Now()
	for i := 0; i < count; i++ {
		C.c_noop()
	}
	durC := time.Since(t1)

	fmt.Printf("1 000 000 вызовов pure Go:  %v (%.2f нс/оп)\n", durGo, float64(durGo.Nanoseconds())/count)
	fmt.Printf("1 000 000 вызовов CGO noop: %v (%.2f нс/оп)\n", durC, float64(durC.Nanoseconds())/count)
	fmt.Printf("Накладные расходы CGO:      +%.2f нс на каждый вызов\n",
		float64(durC.Nanoseconds()-durGo.Nanoseconds())/count)
}
```

ℹ️ GODEBUG=cgocheck=0 отключает глубокую валидацию указателей, немного ускоряя CGO.

**`Терминал`**

```bash
go run main.go
# Вывод:
# 1 000 000 вызовов pure Go:  1.6ms (1.60 нс/оп)
# 1 000 000 вызовов CGO noop: 52.4ms (52.40 нс/оп)
# Накладные расходы CGO:      +50.80 нс на каждый вызов
```

## Под капотом

В исходном коде `src/runtime/cgocall.go` функция `cgocall` выполняет:
- `entersyscall()` — логический процессор P отцепляется, чтобы поток ОС M мог блокироваться в C.
- Вызов ассемблерной функции `asmcgocall(fn, arg)`.
- `exitsyscall()` — горутина пытается снова захватить свободный процессор P. Если все P заняты другими горутинами, текущая горутина принудительно засыпает, увеличивая задержку до сотен микросекунд!

## Подводные камни

В системах с большим количеством горутин частые вызовы CGO могут привести к лавинообразному разрастанию потоков ядра ОС (`pthread`), превышая системный лимит `max_user_watches` или `threads-max`.

## На собеседовании

**Вопрос с собеседования:** Что делает флаг `GODEBUG=cgocheck=2` и зачем он нужен при отладке?
**Ответ:** Режим `cgocheck=2` включает тотальную и дорогую проверку всех передаваемых в Си указателей на каждом вызове. Он валидирует, что память Go не передается в Си с нарушением правил CGO (например, передача структуры Go, содержащей указатель на другую структуру Go). При обнаружении нарушения рантайм мгновенно завершает процесс с паникой и полным stacktrace.
