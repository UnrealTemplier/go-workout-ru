# Управление Си-памятью: аллокация в C и финализаторы Go

## Условие

Напишите функцию на C, которая аллоцирует буфер памяти через `malloc` и возвращает указатель. В Go создайте структуру-обёртку и используйте `runtime.SetFinalizer`, чтобы память Си автоматически освобождалась при сборке мусора Go-объекта.

### Исходная формулировка

Напишите функцию на C, которая аллоцирует память (`malloc`) и возвращает указатель. Go-код должен использовать эту память, затем явно освободить через `C.free`. Объясните, почему Go GC не управляет C-памятью, и как `C.CBytes`/`C.CString` создают копии, чтобы избежать проблем.

## Теория

Для предотвращения утечек Си-памяти в долгоживущих сервисах можно связать время жизни нативного C-ресурса со сборщиком мусора Go с помощью **финализаторов** (`runtime.SetFinalizer`).
Когда Go-структура-обертка становится недостижимой в куче Go:
1. GC переводит объект в очередь финализации.
2. Фоновая горутина финализаторов вызывает зарегистрированную функцию.
3. Функция вызывает `C.free()`, освобождая нативную Си-память.

## Решение по шагам

1. В преамбуле напишите Си-функцию `void* allocate_c_buffer(size_t size)`.
2. В Go создайте структуру `type NativeBuffer struct { ptr unsafe.Pointer; size int }`.
3. В конструкторе `NewNativeBuffer` зарегистрируйте `runtime.SetFinalizer(buf, cleanup)`.
4. Реализуйте метод `Close()` для детерминированного освобождения.
5. Продемонстрируйте автоматическое освобождение Си-памяти при вызове `runtime.GC()`.

## Код решения

**`main.go`**

```go
package main

/*
#include <stdlib.h>
#include <stdio.h>

void* allocate_c_buffer(size_t size) {
    void* p = malloc(size);
    printf("[C Malloc] Выделено %zu байт по адресу %p\n", size, p);
    return p;
}

void free_c_buffer(void* p) {
    printf("[C Free]   Освобождение памяти по адресу %p\n", p);
    free(p);
}
*/
import "C"
import (
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

type NativeBuffer struct {
	ptr unsafe.Pointer
}

func NewNativeBuffer(size int) *NativeBuffer {
	p := C.allocate_c_buffer(C.size_t(size))
	buf := &NativeBuffer{ptr: p}

	// Регистрируем финализатор для автоматической очистки
	runtime.SetFinalizer(buf, func(b *NativeBuffer) {
		if b.ptr != nil {
			C.free_c_buffer(b.ptr)
			b.ptr = nil
		}
	})

	return buf
}

func main() {
	// Создаем буфер внутри области видимости
	func() {
		buf := NewNativeBuffer(1024)
		_ = buf
		fmt.Println("Буфер создан и выходит из области видимости...")
	}()

	// Форсируем сборку мусора Go
	runtime.GC()
	runtime.GC()
	time.Sleep(50 * time.Millisecond)

	fmt.Println("Программа завершена.")
}
```

ℹ️ SetFinalizer связывает время жизни C-памяти с циклом сборщика мусора Go.

**`Терминал`**

```bash
go run main.go
# Вывод:
# [C Malloc] Выделено 1024 байт по адресу 0x...
# Буфер создан и выходит из области видимости...
# [C Free]   Освобождение памяти по адресу 0x...
# Программа завершена.
```

## Под капотом

Сборщик мусора во время фазы Sweep находит объекты с установленным флагом `hasfin`. Указатель помещается в очередь `finq`. Специальная системная горутина рантайма запускает функцию очистки. Однако финализаторы не гарантируют мгновенного запуска, поэтому для критических ресурсов всегда следует реализовывать метод `Close()`.

## Подводные камни

Полагаться исключительно на `SetFinalizer` опасно: при высокой скорости создания объектов память Си может исчерпаться раньше, чем Go GC решит запустить сборку мусора (так как GC оценивает только объем памяти кучи Go!).

## На собеседовании

**Вопрос с собеседования:** Почему полагаться на `runtime.SetFinalizer` для освобождения CGO-памяти в HighLoad сервисах считается антипаттерном?
**Ответ:** Потому что триггер запуска GC в Go (`GOGC`, `GOMEMLIMIT`) рассчитывается исключительно на основе аллокаций в Go-куче. Если сервис выделяет гигабайты памяти в Си через `malloc`, а в Go создает лишь крошечные 16-байтные структуры-хэндлы, Go GC не видит давления на память и не запускает сборку мусора, что приводит к OOM-киллу контейнера ОС.
