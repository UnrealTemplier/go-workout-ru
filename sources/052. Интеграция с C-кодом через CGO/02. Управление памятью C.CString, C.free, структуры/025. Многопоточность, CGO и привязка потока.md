# Многопоточность, CGO и привязка потока runtime.LockOSThread

## Условие

Запустите несколько горутин, вызывающих C-функцию, работающую с Thread-Local Storage (TLS). Используйте `runtime.LockOSThread()` для привязки горутины к конкретному системному потоку ОС (`pthread`). Объясните, почему для библиотек с TLS (OpenGL, CUDA, UI) привязка обязательна.

### Исходная формулировка

**Многопоточность и CGO.**: Запустите несколько горутин, вызывающих C-функцию. Используйте `runtime.LockOSThread()` для привязки горутины к потоку, если это необходимо. Обсудите проблему планировщика Go и потоков ОС при cgo-вызовах.

## Теория

Планировщик Go GMP свободно перемещает горутины между различными системными потоками ядра `M` во время кооперативных пауз или системных вызовов.
Однако многие Си-библиотеки полагаются на **Thread-Local Storage (TLS)** или контексты потоков:
- **OpenGL / Vulkan**: контекст рендеринга привязан к конкретному `pthread`.
- **GUI (Cocoa, Win32, GTK)**: оконные сообщения обязаны обрабатываться только в главном потоке ОС (Thread 0).
- **SQLite / CUDA**: некоторые режимы требуют, чтобы транзакция завершалась ровно в том же потоке, где была открыта.

Функция `runtime.LockOSThread()` намертво привязывает текущую горутину к текущему потоку `M`. Никакая другая горутина не будет запущена на этом потоке, пока не будет вызван `runtime.UnlockOSThread()`.

## Решение по шагам

1. В преамбуле объявите Си-функцию, использующую поток:
   `unsigned long get_tid() { return (unsigned long)pthread_self(); }`.
2. В Go запустите функцию с `runtime.LockOSThread()`.
3. Зафиксируйте ID потока до и после серии CGO-вызовов.
4. Продемонстрируйте постоянство системного потока ОС.
5. Освободите привязку через `runtime.UnlockOSThread()`.

## Код решения

**`main.go`**

```go
package main

/*
#include <pthread.h>

unsigned long get_c_thread_id() {
    return (unsigned long)pthread_self();
}
*/
import "C"
import (
	"fmt"
	"runtime"
	"sync"
)

func runWorker(id int, wg *sync.WaitGroup) {
	defer wg.Done()

	// Привязываем горутину к конкретному потоку ОС M
	runtime.LockOSThread()
	defer runtime.UnlockOSThread()

	tid1 := C.get_c_thread_id()
	// Имитация работы
	runtime.Gosched()
	tid2 := C.get_c_thread_id()

	fmt.Printf("[Worker %d] Thread ID до: 0x%X, после: 0x%X (совпадают: %t)\n",
		id, uint64(tid1), uint64(tid2), tid1 == tid2)
}

func main() {
	var wg sync.WaitGroup
	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go runWorker(i, &wg)
	}
	wg.Wait()
}
```

ℹ️ runtime.LockOSThread гарантирует, что горутина не сменит поток ОС при вызовах Си-библиотек.

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Worker 1] Thread ID до: 0x... after: 0x... (совпадают: true)
# [Worker 2] Thread ID до: 0x... after: 0x... (совпадают: true)
# [Worker 3] Thread ID до: 0x... after: 0x... (совпадают: true)
```

## Под капотом

Когда горутина вызывает `LockOSThread`, рантайм Go устанавливает флаг `lockedg` у структуры потока `m`. Если горутина засыпает на канале или системном вызове, планировщик паркует поток `m` целиком и не пускает на него чужие горутины, сохраняя TLS-переменные Си в целостности.

## Подводные камни

Если забыть вызвать `UnlockOSThread` перед завершением горутины, рантайм Go уничтожит привязанный поток ядра ОС (`pthread_exit`), что вызовет лишние накладные расходы на пересоздание нового потока.

## На собеседовании

**Вопрос с собеседования:** Почему инициализация GUI-библиотек или графических движков в Go всегда начинается с `runtime.LockOSThread()` в функции `init()` или начале `main()`?
**Ответ:** Потому что подсистемы оконного интерфейса операционных систем (Cocoa на macOS, Win32 на Windows, X11/Wayland на Linux) требуют, чтобы цикл обработки сообщений (Event Loop / Message Pump) выполнялся строго в главном первичном потоке процесса (Thread ID 0). Без `LockOSThread` планировщик Go может перебросить `main` на вспомогательный рабочий поток, вызвав краш графической подсистемы.
