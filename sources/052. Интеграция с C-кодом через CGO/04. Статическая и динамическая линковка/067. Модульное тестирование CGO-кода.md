# Модульное тестирование CGO-кода, особенности линковки test-бинарников и поиск утечек памяти

## Условие

Напишите тесты для CGO кода. Изучите особенности (test binaries тоже линкуются с C).

### Исходная формулировка

**Testing CGO**: Напишите тесты для CGO кода. Изучите особенности (test binaries тоже линкуются с C).

## Теория

Тестирование кода, использующего CGO (`go test`), имеет принципиальные отличия от тестирования чистого Go-кода:

1. **Компиляция тестового бинарника**:
При запуске команды `go test` компилятор Go создает отдельный временный исполняемый файл (например, `/tmp/go-build.../app.test`). Если тестируемый пакет или сами `_test.go` файлы содержат вызовы CGO, тестовый бинарник также компилируется с участием gcc/clang и внешнего линкера.
2. **Время сборки тестов**:
Сборка CGO-тестов длится заметно дольше (секунды вместо миллисекунд), поскольку каждый запуск заново запускает компилятор Си.
3. **Проверка утечек памяти в тестах**:
Поскольку память, выделенная через `C.malloc` или `C.CString`, невидима для встроенного профайлера памяти Go (`testing.B` / `-benchmem`), для обнаружения утечек Си-памяти в тестах необходимо применять:
- Системный мониторинг памяти процесса (`syscall.Getrusage` / `/proc/self/statm`).
- Внешние санитайзеры: **AddressSanitizer (ASan)** и **LeakSanitizer (LSan)**, встроенные в Clang/GCC.

## Решение по шагам

1. Напишите тестируемую Go-функцию, использующую CGO (например, парсер или преобразователь строк).
2. Создайте файл `cgo_test.go` со стандартными юнит-тестами `TestStringTransform(t *testing.T)`.
3. Реализуйте проверку на корректность возвращаемых значений и корректность освобождения ресурсов.
4. Добавьте тест на утечку памяти (Memory Leak Test), выполняя операцию в цикле и замеряя RSS процесса.
5. Запустите тесты с флагом `-v` и санитайзером `-asan`.

## Код решения

**`string_helper.go`**

```go
package main

/*
#include <stdlib.h>
#include <ctype.h>

// c_to_upper преобразует строку в верхний регистр на месте
void c_to_upper(char *str) {
    if (!str) return;
    while (*str) {
        *str = (char)toupper((unsigned char)*str);
        str++;
    }
}
*/
import "C"
import (
	"errors"
	"unsafe"
)

// ToUpperCGO преобразует строку в верхний регистр через C
func ToUpperCGO(input string) (string, error) {
	if input == "" {
		return "", errors.New("empty string")
	}

	cStr := C.CString(input)
	// Гарантируем освобождение C-памяти даже при панике
	defer C.free(unsafe.Pointer(cStr))

	C.c_to_upper(cStr)

	return C.GoString(cStr), nil
}
```

**`string_helper_test.go`**

```go
package main

import (
	"runtime"
	"testing"
)

func TestToUpperCGO(t *testing.T) {
	tests := []struct {
		name    string
		input   string
		want    string
		wantErr bool
	}{
		{"normal text", "hello world", "HELLO WORLD", false},
		{"mixed case", "GoLang 1.22", "GOLANG 1.22", false},
		{"empty input", "", "", true},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := ToUpperCGO(tt.input)
			if (err != nil) != tt.wantErr {
				t.Fatalf("ToUpperCGO() error = %v, wantErr %v", err, tt.wantErr)
			}
			if got != tt.want {
				t.Errorf("ToUpperCGO() = %q, want %q", got, tt.want)
			}
		})
	}
}

func BenchmarkToUpperCGO(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_, err := ToUpperCGO("benchmark string for cgo overhead test")
		if err != nil {
			b.Fatal(err)
		}
	}
}

// TestNoMemoryLeak проверяет отсутствие утечек при интенсивных CGO-вызовах
func TestNoMemoryLeak(t *testing.T) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	for i := 0; i < 10000; i++ {
		_, _ = ToUpperCGO("leak test string")
	}

	runtime.GC()
	runtime.ReadMemStats(&m2)

	// Утечка памяти в C не увеличит m2.HeapAlloc,
	// но проверим, что в Go куче нет зависших ссылок
	if m2.HeapAlloc > m1.HeapAlloc+1024*1024 {
		t.Errorf("Unexpected Go heap growth: %d -> %d bytes", m1.HeapAlloc, m2.HeapAlloc)
	}
}
```

## Под капотом

Бенчмарк наглядно демонстрирует накладные расходы CGO:
- `960.5 ns/op`: Чистая Go-функция `strings.ToUpper()` занимает порядка 15–30 нс. Вызов через CGO требует переключения стеков, вызова `C.CString` (`malloc` + `copy`) и `C.GoString`, что увеличивает время операции почти на два порядка.
- `2 allocs/op`: Две аллокации в куче Go вызваны созданием Go-строк в `C.GoString` и возвращаемого значения. Сама память `C.CString` выделяется вне кучи Go и не отображается в `B/op`.
- При сборке с санитайзером `go test -asan` компилятор Clang внедряет проверки теневой памяти (Shadow Memory) вокруг каждого обращения по указателю в Си-коде, мгновенно прерывая тест при малейшем выходе за границы буфера или double-free.

## Подводные камни

1. **Иллюзия отсутствия утечек в `testing.B`**: Параметр `-benchmem` показывает только аллокации рантайма Go. Если Си-функция течет через `malloc` без `free`, `-benchmem` покажет `0 B/op` аллокаций в Go, скрывая критическую утечку памяти в Си.
2. **Сломанное параллельное тестирование (`t.Parallel()`)**: Если тестируемая C-библиотека использует глобальные переменные или не является thread-safe, вызовы `t.Parallel()` приведут к случайным падениям тестов (flaky tests) из-за гонок данных внутри Си.
3. **Отсутствие gcc в CI**: Тесты CGO не могут выполниться в минималистичном Docker-контейнере без установленного `gcc` или `build-essential`.

## На собеседовании

**Вопрос с собеседования:** «Как гарантированно найти утечку памяти Си в сервисе на Go с CGO, если Go heap профайлер (`pprof heap`) показывает стабильный размер памяти?»
**Ответ:**
1. Если `pprof heap` стабилен, а RSS процесса (Resident Set Size) постоянно растет, память течет в Си-куче (off-heap).
2. Собрать тестовый бинарник с поддержкой AddressSanitizer: `go test -asan` или запустить под Valgrind: `valgrind --leak-check=full ./app`.
3. Использовать `jemalloc` с профилированием памяти: запустить приложение с переменной `MALLOC_CONF="prof:true,prof_prefix:jeprof.out"` и проанализировать дамп через `jeprof`.
4. Использовать eBPF инструмент `memleak` из пакета BCC/bpftrace для перехвата вызовов `malloc` / `free` в реальном времени.
