# Отладка смешанного Go/C кода с помощью GDB и Delve и установка точек останова в C-функциях

## Условие

Используйте `gdb` или `delve` для отладки mixed Go/C кода. Настройте breakpoints в C-функциях.

### Исходная формулировка

**Debugging CGO**: Используйте `gdb` или `delve` для отладки mixed Go/C кода. Настройте breakpoints в C-функциях.

## Теория

Отладка программ со смешанным кодом (Mixed Go/C Code) представляет уникальную сложность, поскольку в одном процессе сосуществуют две принципиально разные парадигмы выполнения:
- **Go**: Управляемый рантайм, кооперативный планировщик GMP, сегментированные перемещаемые стеки горутин, DWARFv4 отладочная информация с кастомными расширениями Go.
- **C/C++**: Нативные потоки ОС (POSIX threads), фиксированные стеки ОС, стандартная таблица символов DWARF/ELF.

**Инструменты отладки**:
1. **Delve (`dlv`)**: Специализированный отладчик для Go. Отлично понимает горутины, срезы, интерфейсы и каналы Go, но имеет ограниченную поддержку шагания внутри Си-кода (C step-in).
2. **GDB (`GNU Debugger`)**: Универсальный системный отладчик. Превосходно отлаживает Си-функции, ассемблерные инструкции, регистры процессора и сигналы ОС, но требует специальных Python-скриптов для понимания горутин Go.

**Ключевые флаги сборки для отладки CGO**:
```bash
go build -gcflags="all=-N -l" -ldflags="-w=false" .
```
- `-gcflags="all=-N -l"`: Отключает оптимизации компилятора (`-N`) и инлайнинг функций (`-l`), чтобы переменные не выбрасывались из регистров.
- CGO CFLAGS: Обязательно указывать `-g -O0` для включения C-отладочной информации DWARF и отключения C-оптимизаций.

## Решение по шагам

1. Напишите Си-функцию со сложной логикой или обработкой указателей.
2. Скомпилируйте Go-приложение с флагами отладки `-gcflags="all=-N -l"` и `#cgo CFLAGS: -g -O0`.
3. Запустите отладчик `gdb ./app` или `dlv exec ./app`.
4. Установите точку останова в Си-функции через `break c_function_name`.
5. Установите точку останова в функции Go через `break main.main`.
6. Выполните команду `run`, перейдите к шагу выполнения и исследуйте значения локальных переменных (`print var`, `info registers`, `backtrace`).

## Код решения

**`main.go`**

```go
package main

/*
#cgo CFLAGS: -g -O0
#include <stdio.h>

int c_compute_factorial(int n) {
    int result = 1;
    for (int i = 1; i <= n; i++) {
        result *= i; // Точка останова в C
    }
    return result;
}
*/
import "C"
import "fmt"

func main() {
	input := 5
	fmt.Printf("[Go] Computing factorial for n = %d\n", input)

	// Вызов Си-функции
	res := C.c_compute_factorial(C.int(input))

	fmt.Printf("[Go] Result from C function: %d\n", int(res))
}
```

ℹ️ Go-код с CGO директивой -g -O0 для генерации полной DWARF отладочной информации

**`debug_session.sh`**

```bash
# 1. Сборка бинарника без оптимизаций и с символами отладки
go build -gcflags="all=-N -l" -o debug_app main.go

# 2. Запуск GDB
gdb ./debug_app << 'EOF'
# Установка точки останова в функции Go
break main.main

# Установка точки останова в Си-функции
break c_compute_factorial

# Запуск программы
run

# Продолжение выполнения до входа в C-функцию
continue

# Печать аргумента n в C-функции
print n

# Построчный шаг внутри C-кода
step
print result

# Вывод полного стека вызовов (mixed Go and C frames)
backtrace

# Завершение
continue
quit
EOF
```

## Под капотом

Под капотом GDB читает секции `.debug_info`, `.debug_line`, `.debug_frame` из исполняемого ELF файла:
1. При остановке в точке `c_compute_factorial` отладчик находится в нативном C-фрейме стека потока ОС.
2. Команда `backtrace` отображает цепочку вызовов:
   `#0 c_compute_factorial (...) at main.go:8`
   `#1 _cgo_..._Cfunc_c_compute_factorial (...) at cgo-generated.c`
   `#2 runtime.asmcgocall (...) at asm_amd64.s`
   `#3 main.main () at main.go:21`
3. Видно, как `runtime.asmcgocall` осуществляет переход с сегментированного стека Go-горутины на стек потока M операционной системы.

## Подводные камни

1. **Сборка с флагами стриппинга `-ldflags="-s -w"`**: Флаг `-s` удаляет таблицу символов, а `-w` удаляет отладочные DWARF-данные. В таком бинарнике невозможно поставить breakpoint по имени функции.
2. **Оптимизации компилятора (`-O2` в Си или инлайнинг в Go)**: При оптимизациях компилятор инлайнит мелкие C-функции и переупорядочивает инструкции, из-за чего отладчик перескакивает через строки и выводит `<optimized out>`. Всегда используйте `-O0` и `-N -l` при отладке.
3. **Обработка сигналов Go в GDB**: Рантайм Go активно использует сигнал `SIGURG` для preemptive scheduling (вытесняющей многозадачности). В старых версиях GDB программа постоянно прерывалась по `SIGURG`. Необходимо настроить в GDB: `handle SIGURG nostop noprint pass`.

## На собеседовании

**Вопрос с собеседования:** «Как отладить падение `SIGSEGV` в production CGO-бинарнике, если у вас есть только core dump файл?»
**Ответ:**
1. Открыть дамп в GDB: `gdb ./my_app core.dump`.
2. Выполнить `bt full` (backtrace) для просмотра стека упавшего потока и значений локальных переменных.
3. Определить адрес сбойной инструкции `rip` и адрес недействительной памяти в регистре (например, `0x0` при разыменовании `NULL`).
4. Найти соответствующий C-фрейм и Go-горутину, вызвавшую падение, сопоставив адреса с отладочной таблицей символов.
