# Off-heap аллокация через C.malloc и обертка в unsafe.Slice для снятия нагрузки с GC

## Условие

Откажись от Garbage Collector'а. Вызови `ptr := C.malloc(1024 * 1024)` (1 МБ). Оберни его в слайс `unsafe.Slice((*byte)(ptr), 1024*1024)`. Работай с ним как с обычным срезом. В конце не забудь `C.free(ptr)`. Это супер-трюк для кэшей, которые не должны напрягать Go GC.

### Исходная формулировка

**Ручное управление памятью в Go**: Откажись от Garbage Collector'а. Вызови `ptr := C.malloc(1024 * 1024)` (1 МБ). Оберни его в слайс `unsafe.Slice((*byte)(ptr), 1024*1024)`. Работай с ним как с обычным срезом. В конце не забудь `C.free(ptr)`. Это супер-трюк для кэшей, которые не должны напрягать Go GC.

## Теория

Сборщик мусора Go (GC) работает по алгоритму concurrent tri-color mark & sweep. Длительность фазы сканирования кучи напрямую пропорциональна количеству живых указателей (pointers) в памяти. Если сервис создает гигантский кэш на десятки миллионов объектов в памяти Go, GC вынужден обходить миллионы указателей при каждом цикле сборки, что приводит к деградации CPU и всплескам латентности (GC wall clock latency).

Для решения этой проблемы в высоконагруженных системах (кэши данных, базы данных in-memory) используется **off-heap аллокация** — выделение памяти вне кучи Go (out-of-heap) через системный `malloc()` си-рантайма:
```go
ptr := C.malloc(C.size_t(size))
defer C.free(ptr)
```
Память, выделенная через `C.malloc`, полностью невидима для Go GC:
1. GC никогда не сканирует эту область памяти, что исключает накладные расходы на Mark-фазу.
2. GC никогда автоматически не освободит эту память — программист обязан явно вызвать `C.free()` для предотвращения утечки.

С версии Go 1.17 функция `unsafe.Slice((*T)(ptr), len)` позволяет безопасно сконструировать заголовок слайса Go (`reflect.SliceHeader` / `internal/abi.Slice`) поверх сырого указателя `*T` без копирования данных. Срез получает указатель `Data = ptr`, `Len = len`, `Cap = len`. При обращении по индексам `[0..len-1]` Go компилятор осуществляет стандартные проверки границ (bounds checks), но не управляет временем жизни underlying array.

## Решение по шагам

1. Подключите преамбулу `#include <stdlib.h>` для доступа к `malloc` и `free`.
2. Выделите блок памяти заданного размера (например, 1 МБ = 1 048 576 байт) с проверкой возвращенного указателя на `nil` (OOM).
3. Используйте `defer C.free(ptr)` сразу после успешного выделения памяти.
4. Преобразуйте `unsafe.Pointer(ptr)` в типизированный указатель `(*byte)` и вызовите `unsafe.Slice((*byte)(ptr), 1024*1024)`.
5. Заполните слайс байтами или запишите в него структурированные данные.
6. Убедитесь, что слайс не используется после вызова `C.free(ptr)`, иначе произойдет use-after-free.

## Код решения

**`main.go`**

```go
package main

/*
#include <stdlib.h>
#include <string.h>
*/
import "C"
import (
	"fmt"
	"unsafe"
)

// OffHeapCache представляет off-heap кэш фиксированного размера
type OffHeapCache struct {
	ptr  unsafe.Pointer
	data []byte
	size int
}

// NewOffHeapCache выделяет память через C.malloc вне кучи Go
func NewOffHeapCache(size int) (*OffHeapCache, error) {
	cPtr := C.malloc(C.size_t(size))
	if cPtr == nil {
		return nil, fmt.Errorf("failed to allocate %d bytes off-heap (out of memory)", size)
	}

	// Инициализируем нулями
	C.memset(cPtr, 0, C.size_t(size))

	// Создаем Go-слайс поверх памяти Си без аллокаций в куче Go
	slice := unsafe.Slice((*byte)(cPtr), size)

	return &OffHeapCache{
		ptr:  cPtr,
		data: slice,
		size: size,
	}, nil
}

// Write записывает байты в кэш по смещению
func (c *OffHeapCache) Write(offset int, payload []byte) error {
	if offset < 0 || offset+len(payload) > c.size {
		return fmt.Errorf("buffer overflow: offset %d + len %d > size %d", offset, len(payload), c.size)
	}
	copy(c.data[offset:], payload)
	return nil
}

// Read возвращает срез байт по смещению
func (c *OffHeapCache) Read(offset, length int) ([]byte, error) {
	if offset < 0 || offset+length > c.size {
		return nil, fmt.Errorf("index out of bounds")
	}
	// Возвращаем копию, чтобы данные были защищены от use-after-free
	res := make([]byte, length)
	copy(res, c.data[offset:offset+length])
	return res, nil
}

// Close освобождает off-heap память
func (c *OffHeapCache) Close() {
	if c.ptr != nil {
		C.free(c.ptr)
		c.ptr = nil
		c.data = nil
	}
}

func main() {
	const mb = 1024 * 1024
	cache, err := NewOffHeapCache(mb)
	if err != nil {
		panic(err)
	}
	defer cache.Close()

	msg := []byte("HighLoad BigTech Off-Heap Cache Data")
	if err := cache.Write(0, msg); err != nil {
		panic(err)
	}

	readBack, err := cache.Read(0, len(msg))
	if err != nil {
		panic(err)
	}

	fmt.Printf("Off-heap buffer capacity: %d bytes (1 MB)\n", cache.size)
	fmt.Printf("Read from off-heap: %s\n", string(readBack))
}
```

ℹ️ Выделение 1 МБ памяти через C.malloc с конструированием среза Go через unsafe.Slice

**`Терминал`**

```bash

# Вывод:
# Off-heap buffer capacity: 1048576 bytes (1 MB)
# Read from off-heap: HighLoad BigTech Off-Heap Cache Data
```

## Под капотом

Когда Go GC сканирует память, он просматривает страницы кучи (heap arena / mspan) и битовую карту разметки указателей (heap arena bitmap). Если объект размещен в куче Go через `make([]byte, 1024*1024)`, сборщик мусора помечает срез как `noscan` (поскольку тип элемента `byte` не содержит указателей). Но сам дескриптор среза и страница памяти учитываются в счетчиках активной кучи (`mstats.heap_live`), влияя на триггер запуска GC (`GOGC`).

При использовании `C.malloc()`:
1. Вызов делегируется системному аллокатору glibc `ptmalloc` или jemalloc. Память выделяется через `brk` или анонимный `mmap()`.
2. Рантайм Go вообще не вносит эту память в `runtime.mheap_`. `mstats.heap_live` и `mstats.heap_alloc` не увеличиваются.
3. GC не тратит ни одного такта CPU на сканирование или утилизацию этих страниц.
4. Опасность: Если ссылка на срез `c.data` переживет вызов `C.free()`, обращение к элементам среза вызовет `SIGSEGV` или чтение испорченной памяти (silent corruption).

## Подводные камни

1. **Use-After-Free**: Обращение к `c.data` после `C.free(ptr)`. Любая горутина, сохранившая ссылку на слайс, получит Segfault при обращении к освобожденной виртуальной памяти.
2. **Утечки памяти (Memory Leaks)**: Срезы Go, созданные через `unsafe.Slice`, не имеют финализатора (`runtime.SetFinalizer` не работает со срезами и не отслеживает C-указатели). Пропущенный `C.free()` приводит к неуклонному росту RSS процесса.
3. **Фрагментация glibc ptmalloc**: При частых выделениях и освобождениях блоков разного размера в `malloc` может возникнуть фрагментация кучи операционной системы.

## На собеседовании

**Вопрос с собеседования:** «Как в Go реализовать in-memory кэш на 50 ГБ данных без чудовищных пауз GC и деградации производительности?»
**Ответ:** Есть три основных подхода:
1. **Off-heap память через CGO/mmap**: Память аллоцируется через `C.malloc` или системный вызов `unix.Mmap(MAP_ANON)`. Go работает с памятью через `unsafe.Slice` или байтовые смещения. GC полностью слеп к этой памяти.
2. **Слайсы без указателей (`[]byte`)**: Использовать структуры без ссылочных типов (например, бинарный буфер байт `[]byte` или монолитный массив) и сериализовать данные в бинарный формат (FlatBuffers, Protobuf). Память `[]byte` помечается в Go как `noscan`, и GC не рекурсирует внутрь элементов, хотя учитывает объем в `GOGC`.
3. **Хранение данных в shared memory или tmpfs**: Использование unix IPC shared memory или файлов на `/dev/shm`.
