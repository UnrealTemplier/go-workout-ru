# Потокобезопасность CGO и ограничение системных потоков M

## Условие

Изучите, как CGO взаимодействует с горутинами. Напишите тест, который запускает 50 параллельных горутин с CGO-вызовами. Проверьте число системных потоков процесса через `runtime.NumGoroutine()` и `/proc/self/status` (Threads).

### Исходная формулировка

**Thread safety**: Изучите, как CGO взаимодействует с горутинами. Каждый CGO вызов может блокировать OS thread. Используйте `runtime.LockOSThread()` при необходимости.

## Теория

Каждая горутина, находящаяся внутри CGO-вызова, блокирует под собой физический поток операционной системы (OS Thread `M`).
Если 50 горутин одновременно вошли в CGO:
- Планировщик Go обязан создать **50 системных потоков ОС** `pthread`.
- Это принципиально отличается от чистых Go-горутин, где миллионы горутин выполняются на `GOMAXPROCS` (например, 8) потоках!

В HighLoad системах неконтролируемые вызовы CGO могут быстро исчерпать системный лимит дескрипторов потоков Linux (`/proc/sys/kernel/threads-max`), приведя к отказу сервиса.

## Решение по шагам

1. В преамбуле объявите Си-функцию со сном: `void c_sleep_ms(int ms) { usleep(ms * 1000); }`.
2. Запустите 30 горутин, одновременно вызывающих `C.c_sleep_ms(200)`.
3. Замерьте количество горутин `runtime.NumGoroutine()`.
4. Проверьте реальное количество системных потоков операционной системы.
5. Покажите паттерн защиты через Semaphore worker pool.

## Код решения

**`main.go`**

```go
package main

/*
#include <unistd.h>

void c_sleep_ms(int ms) {
    usleep(ms * 1000);
}
*/
import "C"
import (
	"fmt"
	"os"
	"runtime"
	"strings"
	"sync"
	"time"
)

func getOSThreadCount() int {
	data, err := os.ReadFile("/proc/self/status")
	if err != nil {
		return -1
	}
	for _, line := range strings.Split(string(data), "\n") {
		if strings.HasPrefix(line, "Threads:") {
			var threads int
			fmt.Sscanf(line, "Threads:\t%d", &threads)
			return threads
		}
	}
	return -1
}

func main() {
	fmt.Printf("Потоков ОС на старте: %d\n", getOSThreadCount())

	const workers = 30
	var wg sync.WaitGroup

	// Запускаем 30 горутин, одновременно блокирующихся в CGO
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			C.c_sleep_ms(150)
		}()
	}

	time.Sleep(50 * time.Millisecond)
	fmt.Printf("Во время CGO вызовов: Горутин = %d, Системных потоков ОС M = %d\n",
		runtime.NumGoroutine(), getOSThreadCount())

	wg.Wait()
	fmt.Println("Все вызовы завершены. Потоки возвращены в пул рантайма.")
}
```

ℹ️ Количество потоков ОС резко возрастает пропорционально числу параллельных CGO-вызовов.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Потоков ОС на старте: 5
# Во время CGO вызовов: Горутин = 31, Системных потоков ОС M = 35
# Все вызовы завершены. Потоки возвращены в пул рантайма.
```

## Под капотом

Планировщик Go видит, что поток M ушел в `_Psyscall`. Чтобы не останавливать обработку готовых горутин, `sysmon` вызывает `startm()`, создавая новые `pthread` через вызов ядра Linux `clone()`. Создание каждого потока ОС потребляет от 2 до 8 МБ виртуальной памяти под системный стек.

## Подводные камни

В микросервисах с параллелизмом в 5000 горутин вызов некешированного CGO без семафора приведет к немедленному исчерпанию лимита ОС и крашу процесса.

## На собеседовании

**Вопрос с собеседования:** Как предотвратить неконтролируемый рост потоков ядра ОС при интеграции с блокирующими CGO библиотеками?
**Ответ:** Использовать паттерн Worker Pool или весовой семафор `golang.org/x/sync/semaphore` с ограниченной емкостью (например, не более \(2 \times GOMAXPROCS\)), ограничивая максимальное число одновременно исполняемых CGO вызовов фиксированным числом потоков.
