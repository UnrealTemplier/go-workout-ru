# Zero-allocation мост между Go и Си через Shared Memory и Lock-free Ring Buffer для HFT систем

## Условие

Напишите **zero-allocation bridge** между Go и C: используйте разделяемую память (C-аллоцированный `mmap` или ring buffer), через `unsafe` Go читает/пишет без `cgo`-вызовов на каждую операцию. Объясните, как это используется в high-frequency trading для снижения latency.

### Исходная формулировка

Напишите **zero-allocation bridge** между Go и C: используйте разделяемую память (C-аллоцированный `mmap` или ring buffer), через `unsafe` Go читает/пишет без `cgo`-вызовов на каждую операцию. Объясните, как это используется в high-frequency trading для снижения latency.

## Теория

Каждый отдельный вызов функции CGO стоит от 40 до 150 наносекунд из-за необходимости смены стека, сохранения регистров и синхронизации с планировщиком Go. В системах высокочастотного трейдинга (High-Frequency Trading, HFT) и телекоммуникациях (DPDK, сетевые пакеты), где бюджет латентности составляет сотни наносекунд на сообщение, совершать CGO-вызов на каждую операцию категорически недопустимо.

**Архитектурный паттерн: Zero-Allocation Lock-Free Shared Memory Bridge**:
1. Память выделяется один раз при старте через системный вызов `mmap(MAP_SHARED | MAP_ANONYMOUS)` или POSIX Shared Memory (`shm_open`).
2. В этой разделяемой памяти организуется кольцевой буфер (Ring Buffer / Disruptor pattern) с atomic-счетчиками чтения (`head`) и записи (`tail`).
3. Код на Си и код на Go получают прямой указатель на эту память через `unsafe.Pointer`.
4. **Передача сообщений происходит без единого CGO-вызова**:
   - Go-писатель атомарно инкрементирует `tail` и записывает структуру напрямую в разделяемую память через `unsafe`.
   - C-читатель (работающий в выделенном pinned thread на отдельном ядре CPU) непрерывно опрашивает `tail` (busy-spin polling) без блокировок и системных вызовов.
5. Латентность передачи данных падает до **10–20 наносекунд** (время доступа к L3/L2 кэшу процессора) с **нулевыми аллокациями** и полным отсутствием переключений контекста.

## Решение по шагам

1. Опишите структуру `RingBuffer` со слотами сообщений фиксированного размера и полями `head`, `tail`, выровненными по границе кэш-линии процессора (64 байта).
2. Выделите разделяемую память через системный вызов `mmap` (или C-аллокатор `posix_memalign`).
3. Напишите функцию отправки сообщения на Go: запись payload через `unsafe.Pointer` и атомарный коммит указателя `tail` с memory barrier (`sync/atomic.StoreUint64`).
4. Напишите Си-функцию потребителя, непрерывно читающую слоты из буфера.
5. Убедитесь в отсутствии аллокаций памяти (`0 allocs/op`) и мгновенной передаче данных.

## Код решения

**`hft_bridge.h`**

```c
#ifndef HFT_BRIDGE_H
#define HFT_BRIDGE_H

#include <stdint.h>
#include <stddef.h>

#define RING_BUFFER_CAPACITY 1024
#define CACHE_LINE_SIZE 64

// Структура рыночного ордера (Market Order) фиксированного размера
typedef struct {
    uint64_t order_id;
    double price;
    uint32_t quantity;
    char symbol[8];
} MarketOrder;

// RingBuffer с выравниванием по границе кэш-линии (предотвращение false sharing)
typedef struct {
    MarketOrder slots[RING_BUFFER_CAPACITY];
    
    // Выравнивание tail по кэш-линии 64 байта
    _Alignas(CACHE_LINE_SIZE) volatile uint64_t tail;
    
    // Выравнивание head по отдельной кэш-линии 64 байта
    _Alignas(CACHE_LINE_SIZE) volatile uint64_t head;
} SharedRingBuffer;

SharedRingBuffer* create_shared_ring_buffer();
void free_shared_ring_buffer(SharedRingBuffer *rb);
int c_consume_order(SharedRingBuffer *rb, MarketOrder *out_order);

#endif
```

**`hft_bridge.c`**

```c
#include "hft_bridge.h"
#include <stdlib.h>
#include <string.h>

SharedRingBuffer* create_shared_ring_buffer() {
    SharedRingBuffer *rb = NULL;
    // Выделение памяти с выравниванием по 64 байта
    if (posix_memalign((void**)&rb, CACHE_LINE_SIZE, sizeof(SharedRingBuffer)) != 0) {
        return NULL;
    }
    memset(rb, 0, sizeof(SharedRingBuffer));
    rb->head = 0;
    rb->tail = 0;
    return rb;
}

void free_shared_ring_buffer(SharedRingBuffer *rb) {
    if (rb) free(rb);
}

// c_consume_order читает следующий доступный ордер без CGO вызовов
int c_consume_order(SharedRingBuffer *rb, MarketOrder *out_order) {
    uint64_t current_head = rb->head;
    uint64_t current_tail = __atomic_load_n(&rb->tail, __ATOMIC_ACQUIRE);

    if (current_head == current_tail) {
        return 0; // Буфер пуст
    }

    uint64_t idx = current_head % RING_BUFFER_CAPACITY;
    *out_order = rb->slots[idx];

    __atomic_store_n(&rb->head, current_head + 1, __ATOMIC_RELEASE);
    return 1;
}
```

**`main.go`**

```go
package main

/*
#cgo CFLAGS: -I. -O3
#include "hft_bridge.h"
*/
import "C"
import (
	"fmt"
	"sync/atomic"
	"time"
	"unsafe"
)

type ZeroAllocBridge struct {
	rawPtr *C.SharedRingBuffer
}

func NewZeroAllocBridge() (*ZeroAllocBridge, error) {
	ptr := C.create_shared_ring_buffer()
	if ptr == nil {
		return nil, fmt.Errorf("failed to allocate aligned shared ring buffer")
	}
	return &ZeroAllocBridge{rawPtr: ptr}, nil
}

// PublishOrder публикует ордер напрямую в C-память без cgo-переходов
func (b *ZeroAllocBridge) PublishOrder(orderID uint64, price float64, qty uint32, symbol string) bool {
	// Атомарно загружаем указатели
	tail := atomic.LoadUint64((*uint64)(unsafe.Pointer(&b.rawPtr.tail)))
	head := atomic.LoadUint64((*uint64)(unsafe.Pointer(&b.rawPtr.head)))

	if tail-head >= C.RING_BUFFER_CAPACITY {
		return false // Буфер переполнен (backpressure)
	}

	idx := tail % C.RING_BUFFER_CAPACITY
	slot := &b.rawPtr.slots[idx]

	// Прямая запись в память без CGO переходов и аллокаций
	slot.order_id = C.uint64_t(orderID)
	slot.price = C.double(price)
	slot.quantity = C.uint32_t(qty)

	for i := 0; i < len(symbol) && i < 7; i++ {
		slot.symbol[i] = C.char(symbol[i])
	}
	slot.symbol[len(symbol)] = 0

	// Release memory barrier: публикуем обновленный tail
	atomic.StoreUint64((*uint64)(unsafe.Pointer(&b.rawPtr.tail)), tail+1)
	return true
}

func (b *ZeroAllocBridge) Close() {
	if b.rawPtr != nil {
		C.free_shared_ring_buffer(b.rawPtr)
		b.rawPtr = nil
	}
}

func main() {
	bridge, err := NewZeroAllocBridge()
	if err != nil {
		panic(err)
	}
	defer bridge.Close()

	fmt.Println("Zero-allocation HFT bridge initialized.")

	// Пишем ордер из Go
	success := bridge.PublishOrder(1001, 42150.50, 5, "BTCUSDT")
	fmt.Printf("[Go Producer] Order published to shared ring buffer: %v\n", success)

	// Читаем ордер на стороне C
	var consumedOrder C.MarketOrder
	if C.c_consume_order(bridge.rawPtr, &consumedOrder) == 1 {
		fmt.Printf("[C Consumer] Read Order: ID=%d, Price=%.2f, Qty=%d, Symbol=%s\n",
			uint64(consumedOrder.order_id),
			float64(consumedOrder.price),
			uint32(consumedOrder.quantity),
			C.GoString(&consumedOrder.symbol[0]))
	} else {
		fmt.Println("[C Consumer] Buffer was empty!")
	}

	// Бенчмарк ультрабыстрой отправки 100 000 сообщений
	start := time.Now()
	const total = 100000
	for i := 0; i < total; i++ {
		bridge.PublishOrder(uint64(i), 100.0, 1, "ETH")
		var dummy C.MarketOrder
		C.c_consume_order(bridge.rawPtr, &dummy)
	}
	elapsed := time.Since(start)
	fmt.Printf("Processed %d orders in %v (avg %.2f ns/order) with ZERO Go heap allocs!\n",
		total, elapsed, float64(elapsed.Nanoseconds())/float64(total))
}
```

## Под капотом

Почему этот мост работает на порядки быстрее классического CGO:
1. **Отсутствие вызова `runtime.cgocall`**: Запись данных происходит через обычные процессорные инструкции `MOV` по указателю `unsafe.Pointer`. Процессор не тратит сотни тактов на переключение стеков и сохранение регистров Go.
2. **Атомарные барьеры памяти (Memory Barriers)**:
   - `atomic.StoreUint64` генерирует на x86_64 инструкцию `XCHG` или `MOV` с семантикой Store-Release, гарантируя, что все поля структуры ордера записаны в кэш процессора до того, как счетчик `tail` станет видимым ядру Си.
   - Си-читатель использует `__atomic_load_n(&rb->tail, __ATOMIC_ACQUIRE)`, гарантируя чтение актуальных данных без кэш-инвалидации.
3. **Выравнивание по кэш-линии (Cache Line Padding / Alignas)**:
   Поля `head` и `tail` разнесены по разным 64-байтовым кэш-линиям процессора (`_Alignas(64)`). Это предотвращает эффект **False Sharing** (ложное разделение кэша), при котором запись в `tail` инвалидировала бы строку кэша ядра, читающего `head`.

## Подводные камни

1. **False Sharing**: Если разместить `head` и `tail` в смежных байтах памяти, ядра процессора будут постоянно инвалидировать кэш-линии друг друга по протоколу MESI, увеличивая задержку в 10–20 раз. Выравнивание по 64 байта строго обязательно.
2. **Отсутствие контроля выхода за пределы**: При работе через `unsafe.Pointer` компилятор Go отключает bounds checking. Любая ошибка в расчете смещения приведет к тихому повреждению памяти или аварийному падению процесса.
3. **Правила cgocheck**: Начиная с Go 1.6, рантайм следит, чтобы в память Си не передавались указатели на объекты в куче Go (`Go pointer to Go pointer`). Передача примитивных типов или структур, не содержащих Go-указателей, полностью валидна.

## На собеседовании

**Вопрос с собеседования:** «Как построить архитектуру обмена данными между Go и Си/C++ с латентностью субмикросекундного уровня (sub-microsecond latency) в HFT?»
**Ответ:**
1. **Исключить CGO из горячего пути (Hot Path)**: CGO-вызов имеет неустранимый оверхед 40–100 нс.
2. **Shared Memory + Single-Producer Single-Consumer (SPSC) Ring Buffer**: Выделить общую память через `mmap` / hugetlbfs (Huge Pages 2MB/1GB).
3. **Lock-Free Atomic Counters**: Использовать семантику Acquire/Release для указателей `head` и `tail`.
4. **CPU Pinning (Thread Affinity)**: Привязать поток читателя Си и поток писателя Go (`runtime.LockOSThread()`) к изолированным физическим ядрам процессора одного NUMA-узла (`taskset` / `pthread_setaffinity_np`) для минимизации задержек межъядерной шины QPI/UPI.
