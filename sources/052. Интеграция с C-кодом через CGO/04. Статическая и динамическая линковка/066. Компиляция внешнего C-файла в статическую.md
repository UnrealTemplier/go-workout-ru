# Компиляция внешнего C-файла в статическую библиотеку libmath.a и линковка через #cgo CFLAGS и LDFLAGS

## Условие

Создай отдельный C-файл `math.c`, скомпилируй его в объектный файл, затем в статическую библиотеку `libmath.a`. В Go-коде используй директивы `#cgo CFLAGS: -I.` и `#cgo LDFLAGS: -L. -lmath`, чтобы слинковать свою кастомную C-библиотеку прямо в Go-бинарник.

### Исходная формулировка

**Статическая линковка `.a` и `.so`**: Создай отдельный C-файл `math.c`, скомпилируй его в объектный файл, затем в статическую библиотеку `libmath.a`. В Go-коде используй директивы `#cgo CFLAGS: -I.` и `#cgo LDFLAGS: -L. -lmath`, чтобы слинковать свою кастомную C-библиотеку прямо в Go-бинарник.

## Теория

В реальных корпоративных проектах код на Си/C++ редко оформляется в виде строк в преамбуле `import "C"`. Обычно используются готовые скомпилированные библиотеки — статические (`.a` / `.lib`) или динамические (`.so` / `.dylib` / `.dll`).

**Статическая библиотека (`.a` — Archive)**:
- Представляет собой архив объектных файлов (`.o`), упакованный утилитой `ar`.
- При сборке компоновщик Go (`go tool link` / `gcc`) извлекает нужные объектные файлы из `.a` архива и **вшивает их прямо в тело результирующего бинарника Go**.
- **Преимущество**: Результирующий исполняемый файл самодостаточен — не требует наличия стороннего `.so` файла в целевой операционной системе (в `/usr/lib` или `LD_LIBRARY_PATH`).

**Директивы CGO для линковки**:
- `#cgo CFLAGS: -I${SRCDIR}/include`: Указывает препроцессору C путь поиска заголовочных файлов (`.h`). Переменная `${SRCDIR}` автоматически раскрывается CGO в абсолютный путь к папке с Go-файлом.
- `#cgo LDFLAGS: -L${SRCDIR} -lmath`:
  - `-L${SRCDIR}`: Добавляет указанную папку в пути поиска библиотек компоновщиком.
  - `-lmath`: Указывает компоновщику искать библиотеку с именем `libmath.a` (или `libmath.so`). Префикс `lib` и суффикс `.a` подставляются автоматически.

## Решение по шагам

1. Создайте заголовочный файл `custom_math.h` с объявлением функций.
2. Создайте файл реализации `custom_math.c`.
3. Скомпилируйте `custom_math.c` в объектный файл: `gcc -c custom_math.c -o custom_math.o`.
4. Создайте статический архив: `ar rcs libmath.a custom_math.o`.
5. В Go-файле укажите `#cgo CFLAGS: -I.` и `#cgo LDFLAGS: -L. -lmath`.
6. Соберите и запустите Go-приложение.

## Код решения

**`custom_math.h`**

```c
#ifndef CUSTOM_MATH_H
#define CUSTOM_MATH_H

long long int fast_power(long long int base, int exp);
int gcd(int a, int b);

#endif
```

**`custom_math.c`**

```c
#include "custom_math.h"

// fast_power вычисляет степень за O(log N)
long long int fast_power(long long int base, int exp) {
    long long int result = 1;
    while (exp > 0) {
        if (exp % 2 == 1) result *= base;
        base *= base;
        exp /= 2;
    }
    return result;
}

// gcd вычисляет наибольший общий делитель по алгоритму Евклида
int gcd(int a, int b) {
    while (b != 0) {
        int t = b;
        b = a % b;
        a = t;
    }
    return a;
}
```

**`main.go`**

```go
package main

/*
#cgo CFLAGS: -I.
#cgo LDFLAGS: -L. -lmath
#include "custom_math.h"
*/
import "C"
import "fmt"

func main() {
	base := 2
	exp := 10
	powerRes := C.fast_power(C.longlong(base), C.int(exp))

	a := 48
	b := 18
	gcdRes := C.gcd(C.int(a), C.int(b))

	fmt.Printf("Custom C Static Library (libmath.a) Linkage:\n")
	fmt.Printf("%d ^ %d = %d\n", base, exp, int64(powerRes))
	fmt.Printf("GCD(%d, %d) = %d\n", a, b, int(gcdRes))
}
```

ℹ️ Линковка статической библиотеки libmath.a через директивы #cgo LDFLAGS: -L. -lmath

**`build_and_run.sh`**

```bash
# 1. Компиляция C-кода в объектный файл
gcc -O2 -c custom_math.c -o custom_math.o

# 2. Создание статического архива libmath.a
ar rcs libmath.a custom_math.o

# 3. Сборка и запуск Go-программы со статической линковкой
go run main.go
# Вывод:
# Custom C Static Library (libmath.a) Linkage:
# 2 ^ 10 = 1024
# GCD(48, 18) = 6
```

## Под капотом

Что происходит во время линковки:
1. `go build` вызывает внешний компилятор Си (`gcc` или `clang`) в качестве линкера.
2. Директива `-L.` заставляет `gcc` искать файлы библиотек в текущей папке.
3. Директива `-lmath` приводит к поиску файла `libmath.a`.
4. Компоновщик сканирует таблицу символов `libmath.a`, находит определения функций `fast_power` и `gcd`, копирует их бинарные инструкции в секцию `.text` итогового исполняемого файла и разрешает адреса переходов (relocations).
5. После сборки файл `libmath.a` больше не требуется для запуска бинарника — он полностью интегрирован.

## Подводные камни

1. **Относительный путь `-L.`**: Если запустить `go build` из другой директории, относительный путь `-L.` укажет на неверный каталог. Рекомендуется использовать специальную переменную CGO: `#cgo LDFLAGS: -L${SRCDIR} -lmath`.
2. **Порядок линковки библиотек**: В GCC порядок указания библиотек имеет значение (слева направо). Если библиотека `A` зависит от библиотеки `B`, в LDFLAGS сначала должна идти `-lA`, а затем `-lB`.
3. **Несовпадение архитектур**: Если `libmath.a` скомпилирован под x86_64, а Go собирается под arm64 (например, Apple Silicon или серверный Graviton), линкер выдаст ошибку несовместимости формата файла.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между статической (`.a`) и динамической (`.so`) линковкой CGO-библиотеки в продакшене?»
**Ответ:**
- **Статическая линковка (`.a`)**: Код библиотеки копируется внутрь Go-бинарника. Размер бинарника увеличивается, но процесс деплоя максимально прост: один самодостаточный исполняемый файл, запускающийся в любом совместимом окружении.
- **Динамическая линковка (`.so`)**: Бинарник содержит только ссылку на имя библиотеки. При старте динамический загрузчик ОС (`ld.so`) ищет `.so` в системных директориях. Если библиотеки нет или её версия не совпадает, приложение не запустится (`error while loading shared libraries`). Динамическая линковка усложняет Docker-образы и CI/CD.
