# Локальная статическая линковка Си-библиотеки в директории пакета

## Условие

Скомпилируй простую C-библиотеку в `.a` файл. Напиши CGO-код, который линкует её локально через директиву `#cgo LDFLAGS: -L${SRCDIR} -lmylib`. Проверьте вызовы функций.

### Исходная формулировка

**[Статическая линковка C-библиотеки]**: Скомпилируй простую C-библиотеку в `.a` файл. Напиши CGO-код, который линкует её локально (через `#cgo LDFLAGS: -L./lib -lmylib`). Собери Go-бинарник.

## Теория

При распространении Go-модулей с встроенным C-кодом (vendoring native libraries) хорошей практикой является хранение заголовочных файлов и статических библиотек прямо внутри репозитория Go-пакета.
Директива:
`#cgo LDFLAGS: -L${SRCDIR} -lmylib`
гарантирует, что компоновщик найдет файл `libmylib.a` в той же папке, где находится `.go` файл, исключая необходимость предварительной установки библиотеки в систему через `apt/brew`.

## Решение по шагам

1. Создайте `mylib.c` с функцией `int multiply(int a, int b) { return a * b; }`.
2. Скомпилируйте `gcc -c mylib.c -o mylib.o`.
3. Создайте архив: `ar rcs libmylib.a mylib.o`.
4. В `main.go` укажите `#cgo LDFLAGS: -L${SRCDIR} -lmylib` и прототип функции.
5. Вызовите `C.multiply(6, 7)` и проверьте результат 42.

## Код решения

**`mylib.c`**

```c
int multiply(int a, int b) {
    return a * b;
}
```

**`main.go`**

```go
package main

/*
#cgo LDFLAGS: -L${SRCDIR} -lmylib

extern int multiply(int a, int b);
*/
import "C"
import "fmt"

func main() {
	res := C.multiply(6, 7)
	fmt.Printf("Результат вызова из локальной libmylib.a: 6 * 7 = %d\n", int(res))
}
```

ℹ️ Файл libmylib.a линкуется статически прямо из исходной директории пакета.

**`Терминал`**

```bash
gcc -c mylib.c -o mylib.o
ar rcs libmylib.a mylib.o
go run main.go
# Вывод:
# Результат вызова из локальной libmylib.a: 6 * 7 = 42
```

## Под капотом

Символы из `libmylib.a` копируются компоновщиком `ld` в секцию `.text` финального исполняемого файла. После успешной сборки бинарник можно переносить на другие машины: исходные файлы `mylib.c`, `mylib.o` и `libmylib.a` больше не требуются.

## Подводные камни

Статическая библиотека `.a`, скомпилированная под архитектуру x86-64, не слинкуется на сервере ARM64 (Apple Silicon или AWS Graviton). Для мультиплатформенности библиотеки должны компилироваться под каждую архитектуру.

## На собеседовании

**Вопрос с собеседования:** В чем преимущества и недостатки вендоринга статических библиотек `.a` в Git-репозитории Go-проекта?
**Ответ:** Преимущества: воспроизводимость сборки (Hermetic Build), независимость от пакетных менеджеров ОС и простота `go build`. Недостатки: раздувание размера Git-репозитория, невозможность автоматического применения патчей безопасности (CVE) системных библиотек и необходимость хранения бинарных артефактов под разные ОС и архитектуры (`linux/amd64`, `linux/arm64`, `darwin/arm64`).
