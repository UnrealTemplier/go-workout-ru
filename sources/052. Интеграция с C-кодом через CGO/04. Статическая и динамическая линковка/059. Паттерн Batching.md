# Паттерн Batching: сжатие 1000 мелких CGO вызовов в один пакетный

## Условие

Вместо 1000 мелких CGO вызовов, сделайте один пакетный вызов, который обрабатывает batch данных. Напишите сравнительный бенчмарк и покажите многократное ускорение пропускной способности.

### Исходная формулировка

**Batching CGO calls**: Вместо 1000 мелких CGO вызовов, сделайте один вызов, который обрабатывает batch данных.

## Теория

Главный архитектурный закон HighLoad систем с CGO:
$$\text{Общие накладные расходы} = N \times T_{\text{cgo\_overhead}}.$$
Если алгоритм выполняет \(N = 10\,000\) операций:
- **Поэлементный вызов (Naive):** \(10\,000 \times 60\,\text{ns} = 600\,000\,\text{ns} = 0.6\,\text{ms}\) только на переключение стеков!
- **Пакетный вызов (Batching):** 1 вызов CGO со срезом из \(10\,000\) элементов \(= 60\,\text{ns}\) на переключение стеков.
Ускорение межъязыкового взаимодействия достигает **сотен и тысяч раз**!

## Решение по шагам

1. В преамбуле напишите функцию для одного элемента: `int c_hash_single(int val)`.
2. В преамбуле напишите пакетную функцию: `void c_hash_batch(const int* in, int* out, int count)`.
3. Создайте массив из 5 000 чисел.
4. Замерьте время 5 000 поштучных CGO вызовов.
5. Замерьте время 1 пакетного вызова.
6. Выведите коэффициент ускорения.

## Код решения

**`main.go`**

```go
package main

/*
static inline int hash_single(int x) {
    x = ((x >> 16) ^ x) * 0x45d9f3b;
    x = ((x >> 16) ^ x) * 0x45d9f3b;
    x = (x >> 16) ^ x;
    return x;
}

static inline void hash_batch(const int* in, int* out, int count) {
    for (int i = 0; i < count; i++) {
        out[i] = hash_single(in[i]);
    }
}
*/
import "C"
import (
	"fmt"
	"time"
	"unsafe"
)

func main() {
	const count = 10_000
	input := make([]int32, count)
	outputNaive := make([]int32, count)
	outputBatch := make([]int32, count)

	for i := range input {
		input[i] = int32(i)
	}

	// 1. Наивный подход: 10 000 вызовов CGO
	t0 := time.Now()
	for i := 0; i < count; i++ {
		outputNaive[i] = int32(C.hash_single(C.int(input[i])))
	}
	durNaive := time.Since(t0)

	// 2. Пакетный подход: ровно 1 вызов CGO
	t1 := time.Now()
	inPtr := (*C.int)(unsafe.Pointer(&input[0]))
	outPtr := (*C.int)(unsafe.Pointer(&outputBatch[0]))
	C.hash_batch(inPtr, outPtr, C.int(count))
	durBatch := time.Since(t1)

	fmt.Printf("Обработка %d элементов:\n", count)
	fmt.Printf("1. Поэлементно (10 000 вызовов CGO): %v\n", durNaive)
	fmt.Printf("2. Батчинг      (1 вызов CGO):        %v\n", durBatch)
	fmt.Printf("Ускорение благодаря батчингу:        %.1fx раз!\n",
		float64(durNaive)/float64(durBatch))
}
```

ℹ️ Батчинг устраняет накладные расходы переключения контекста CGO на 99.9%.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Обработка 10000 элементов:
# 1. Поэлементно (10 000 вызовов CGO): 520.4µs
# 2. Батчинг      (1 вызов CGO):        18.2µs
# Ускорение благодаря батчингу:        28.6x раз!
```

## Под капотом

В батч-версии Си-цикл полностью оптимизируется компилятором `gcc`: конвейеризуется, разворачивается и не прерывается вызовами рантайма Go. Накладные расходы `asmcgocall` уплачиваются ровно 1 раз, превращая CGO в высокоэффективный сопроцессор для Go.

## Подводные камни

Размер одного батча не должен быть слишком большим (например, 10 секунд непрерывного C-расчета), иначе горутина не сможет дойти до GC safepoint, задерживая наступление фазы Stop-The-World сборщика мусора.

## На собеседовании

**Вопрос с собеседования:** Каков оптимальный размер батча при передаче задач из Go в CGO под нагрузкой?
**Ответ:** Оптимальный размер батча подбирается так, чтобы один вызов CGO длился от 100 микросекунд до 5 миллисекунд. Менее 10 микросекунд — накладные расходы CGO составляют заметный процент. Более 10 миллисекунд — монопольный захват потока M задерживает сборку мусора Go (GC Preemption Latency), так как вызовы CGO прерываются только кооперативно.
