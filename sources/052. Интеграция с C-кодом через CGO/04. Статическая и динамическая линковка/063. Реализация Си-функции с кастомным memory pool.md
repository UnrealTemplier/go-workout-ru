# Реализация Си-функции с кастомным memory pool аллокатором для снижения GC pressure

## Условие

Реализуйте C-функцию с custom allocator, вызывайте её из Go для снижения GC pressure.

### Исходная формулировка

**Custom allocators в C**: Реализуйте C-функцию с custom allocator, вызывайте её из Go для снижения GC pressure.

## Теория

В системах обработки сетевых пакетов или стриминга сообщений создание сотен тысяч мелких объектов в секунду создает огромную нагрузку на аллокатор Go и GC. Стандартный системный `malloc` также страдает от блокировок мьютексов при высокой конкурентности.

Паттерн **Arena / Chunk Memory Pool** (пул памяти с монолитной аллокацией):
1. В памяти Си заранее выделяется крупный монолитный блок (арена, например, 16 МБ).
2. Выделение памяти под объекты (`arena_alloc`) сводится к инкременту указателя смещения (`offset += size`) с выравниванием (alignment), что выполняется за единицы наносекунд без системных вызовов и мьютексов.
3. Индивидуальное освобождение объектов не требуется. По завершении пачки задач (request-scoped processing) вся арена сбрасывается в ноль (`arena_reset`) мгновенно.
4. Куча Go и GC вообще не участвуют в распределении этих объектов, снижая GC pressure до нуля.

## Решение по шагам

1. Создайте структуру `MemoryArena` в преамбуле C с буфером фиксированного размера и указателем смещения `offset`.
2. Реализуйте Си-функции `arena_create`, `arena_alloc`, `arena_reset` и `arena_free`.
3. Реализуйте Си-структуру объекта (например, `LogEntry` или `Packet`).
4. Напишите Go-обертку, которая циклически аллоцирует объекты через Си-арену, заполняет их и сбрасывает арену.
5. Замерьте отсутствие аллокаций в куче Go.

## Код решения

**`main.go`**

```go
package main

/*
#include <stdlib.h>
#include <stdint.h>
#include <string.h>

typedef struct {
    char *buffer;
    size_t capacity;
    size_t offset;
} MemoryArena;

static MemoryArena* arena_create(size_t capacity) {
    MemoryArena *arena = (MemoryArena*)malloc(sizeof(MemoryArena));
    if (!arena) return NULL;
    arena->buffer = (char*)malloc(capacity);
    if (!arena->buffer) {
        free(arena);
        return NULL;
    }
    arena->capacity = capacity;
    arena->offset = 0;
    return arena;
}

static void* arena_alloc(MemoryArena *arena, size_t size) {
    // Выравнивание по 8 байт
    size_t aligned_size = (size + 7) & ~7;
    if (arena->offset + aligned_size > arena->capacity) {
        return NULL; // Out of arena memory
    }
    void *ptr = &arena->buffer[arena->offset];
    arena->offset += aligned_size;
    return ptr;
}

static void arena_reset(MemoryArena *arena) {
    arena->offset = 0;
}

static void arena_free(MemoryArena *arena) {
    if (arena) {
        if (arena->buffer) free(arena->buffer);
        free(arena);
    }
}

typedef struct {
    uint64_t timestamp;
    uint32_t event_id;
    char payload[32];
} EventRecord;
*/
import "C"
import (
	"fmt"
	"runtime"
	"unsafe"
)

func main() {
	const arenaSize = 4 * 1024 * 1024 // 4 МБ
	arena := C.arena_create(C.size_t(arenaSize))
	if arena == nil {
		panic("failed to create C memory arena")
	}
	defer C.arena_free(arena)

	var memStatsBefore runtime.MemStats
	runtime.ReadMemStats(&memStatsBefore)

	const numEvents = 50000
	fmt.Printf("Allocating %d events using C custom arena allocator...\n", numEvents)

	for i := 0; i < numEvents; i++ {
		ptr := C.arena_alloc(arena, C.size_t(unsafe.Sizeof(C.EventRecord{})))
		if ptr == nil {
			// Сбрасываем арену при заполнении (пакетная обработка)
			C.arena_reset(arena)
			ptr = C.arena_alloc(arena, C.size_t(unsafe.Sizeof(C.EventRecord{})))
		}

		event := (*C.EventRecord)(ptr)
		event.timestamp = C.uint64_t(1700000000 + i)
		event.event_id = C.uint32_t(i)
	}

	var memStatsAfter runtime.MemStats
	runtime.ReadMemStats(&memStatsAfter)

	goAllocs := memStatsAfter.Mallocs - memStatsBefore.Mallocs
	fmt.Printf("Successfully processed %d events!\n", numEvents)
	fmt.Printf("Go Heap Allocations count during loop: %d\n", goAllocs)
	fmt.Printf("Go GC Total Pause: %v\n", memStatsAfter.PauseTotalNs)
}
```

## Под капотом

Встроенный аллокатор Go (`runtime.mallocgc`) делит память на spans и использует локальный кэш `mcache`. При выделении миллионов короткоживущих объектов:
1. Заполняются размерные классы (size classes) в `mcache` и `mcentral`.
2. Растет счетчик выделенной памяти `heap_live`.
3. По достижении триггера `GOGC` инициируется принудительная фаза Mark, отбирающая до 25% CPU у рабочих горутин (Mark Workers).

Арена в Си:
1. Выполняет `arena_alloc` всего за несколько инструкций ассемблера: `ADD`, `AND`, сравнение `CMP` и инкремент `offset`.
2. Локальность данных в кэше процессора (L1/L2 Cache Locality) максимальна, так как структуры располагаются в памяти строго последовательно без разрывов.
3. Очистка `arena_reset` — это единичная инструкция `arena->offset = 0`, освобождающая миллионы объектов за 1 такт CPU.

## Подводные камни

1. **Потокобезопасность арены**: Базовая реализация арены не является thread-safe. Если несколько горутин вызывают `arena_alloc` одновременно без мьютекса или lock-free CAS, произойдет data race и порча структур.
2. **Dangling Pointers**: Если Go-код сохранит указатель `*C.EventRecord` после вызова `arena_reset`, последующие аллокации перезапишут данные по этому адресу.
3. **Выравнивание памяти (Alignment)**: На архитектурах ARM64 или x86_64 невыровненный доступ к `uint64_t` может приводить к штрафам производительности или аппаратному исключению `SIGBUS`.

## На собеседовании

**Вопрос с собеседования:** «В каких сценариях кастомный Arena-аллокатор эффективнее стандартного `sync.Pool` в Go?»
**Ответ:**
`sync.Pool` отлично переиспользует объекты одинакового типа, но:
1. Ссылки в `sync.Pool` могут сбрасываться GC при каждом цикле сборки мусора (через `poolCleanup`).
2. `sync.Pool` по-прежнему удерживает Go-указатели, которые GC обязан просканировать.
3. Arena аллокатор позволяет размещать разнородные структуры данных в рамках одной транзакции/запроса и освобождать всё за \(O(1)\) без единого GC-скана. Это критично в HighLoad RPC-серверах с миллионами RPS.
