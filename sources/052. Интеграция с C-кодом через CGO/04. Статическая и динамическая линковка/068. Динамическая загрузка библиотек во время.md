# Динамическая загрузка библиотек во время выполнения через dlopen, dlsym и dlclose

## Условие

Реализуйте `dlopen`/`dlsym` на чистом Go через `cgo`: загрузите `.so` во время выполнения, найдите символ и вызовите. Объясните разницу с `plugin.Open` и когда нужен ручной `dlopen` (например, опциональные зависимости).

## Теория

Обычно внешние библиотеки линкуются статически во время компиляции или динамически при старте бинарника загрузчиком ОС. Однако в ряде сценариев требуется загружать библиотеки **во время выполнения (at runtime)**:
- **Опциональные аппаратные зависимости**: Драйверы GPU (NVIDIA CUDA `libcuda.so`), графические API (Vulkan, OpenGL), аппаратные крипто-акселераторы. Если у клиента нет видеокарты, сервис должен продолжить работу в режиме CPU, не падая при старте из-за отсутствия `.so` файла.
- **Динамические плагины**: Загрузка сторонних расширений без перезапуска сервера.

**Стандартный POSIX API динамической загрузки (`<dlfcn.h>`)**:
- `dlopen(filename, flags)`: Загружает динамическую библиотеку в адресное пространство процесса (`RTLD_LAZY` / `RTLD_NOW`).
- `dlsym(handle, symbol_name)`: Ищет адрес функции или переменной по строковому имени в таблице экспорта библиотеки.
- `dlerror()`: Возвращает строку с описанием последней ошибки загрузки.
- `dlclose(handle)`: Уменьшает счетчик ссылок библиотеки и выгружает её из памяти, если счетчик достиг нуля.

**Почему не стандартный `plugin.Open` в Go?**
Пакет `plugin` в стандартной библиотеке Go крайне хрупок: он работает только на Linux, требует **абсолютно идентичной** версии компилятора Go, всех транзитивных зависимостей и флагов сборки между хостом и плагином. Ручной вызов `dlopen` через CGO работает с **любыми** нативными библиотеками на C, C++, Rust, Zig и Fortran без каких-либо ограничений версий Go.

## Решение по шагам

1. Подключите заголовочный файл `<dlfcn.h>` в CGO преамбуле и укажите `#cgo LDFLAGS: -ldl`.
2. Создайте вспомогательную C-функцию-трамплин для вызова динамически найденного указателя на функцию с нужной сигнатурой.
3. В Go вызовите `C.dlopen()` с флагом `C.RTLD_LAZY`. Проверьте результат на `nil`.
4. В случае ошибки получите текст через `C.GoString(C.dlerror())`.
5. Найдите символ через `C.dlsym()`.
6. Вызовите функцию через C-трамплин.
7. Закройте дескриптор через `C.dlclose()`.

## Код решения

**`plugin_lib.c`**

```c
// Компилируется в plugin_lib.so
#include <stdio.h>

int compute_multiplier(int val) {
    return val * 42;
}
```

**`main.go`**

```go
package main

/*
#cgo LDFLAGS: -ldl
#include <dlfcn.h>
#include <stdlib.h>

// Сигнатура функции: int (*)(int)
typedef int (*calc_fn)(int);

// Вспомогательный C-мост для вызова указателя на функцию
static int call_calc_fn(void *func_ptr, int arg) {
    calc_fn fn = (calc_fn)func_ptr;
    return fn(arg);
}
*/
import "C"
import (
	"errors"
	"fmt"
	"unsafe"
)

// DynamicLibrary инкапсулирует работу с нативной .so библиотекой
type DynamicLibrary struct {
	handle unsafe.Pointer
}

// LoadLibrary загружает библиотеку в рантайме через dlopen
func LoadLibrary(path string) (*DynamicLibrary, error) {
	cPath := C.CString(path)
	defer C.free(unsafe.Pointer(cPath))

	// RTLD_LAZY разрешает символы по мере первого обращения
	handle := C.dlopen(cPath, C.RTLD_LAZY)
	if handle == nil {
		cErr := C.dlerror()
		return nil, fmt.Errorf("dlopen failed: %s", C.GoString(cErr))
	}

	return &DynamicLibrary{handle: handle}, nil
}

// CallFunction находит функцию и вызывает её
func (lib *DynamicLibrary) CallFunction(symbol string, arg int) (int, error) {
	cSymbol := C.CString(symbol)
	defer C.free(unsafe.Pointer(cSymbol))

	// Очищаем предыдущие ошибки dlerror
	C.dlerror()

	sym := C.dlsym(lib.handle, cSymbol)
	if sym == nil {
		cErr := C.dlerror()
		return 0, fmt.Errorf("dlsym failed for %s: %s", symbol, C.GoString(cErr))
	}

	// Вызываем через C-трамплин
	result := C.call_calc_fn(sym, C.int(arg))
	return int(result), nil
}

// Close выгружает библиотеку через dlclose
func (lib *DynamicLibrary) Close() error {
	if lib.handle != nil {
		res := C.dlclose(lib.handle)
		lib.handle = nil
		if res != 0 {
			return errors.New("dlclose failed")
		}
	}
	return nil
}

func main() {
	// Попытка загрузить опциональную библиотеку
	libPath := "./plugin_lib.so"
	lib, err := LoadLibrary(libPath)
	if err != nil {
		fmt.Printf("Dynamic library not found (%v). Falling back to pure Go implementation!\n", err)
		return
	}
	defer lib.Close()

	val := 10
	res, err := lib.CallFunction("compute_multiplier", val)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Successfully loaded %s via dlopen!\n", libPath)
	fmt.Printf("Invoked dynamic symbol 'compute_multiplier(%d)' = %d\n", val, res)
}
```

## Под капотом

Как работает `dlopen` на уровне ядра Linux:
1. Системный вызов `openat()` открывает `.so` файл на диске.
2. Ядро с помощью `mmap()` отображает ELF-сегменты библиотеки (`.text`, `.rodata`, `.data`, `.bss`) в виртуальное адресное пространство процесса Go.
3. Динамический компоновщик `ld-linux.so` выполняет связывание символов (relocations) и вызывает функции инициализации библиотеки `__attribute__((constructor))` (аналог `init()` в Go).
4. `dlsym` парсит секцию `.dynsym` (dynamic symbol table) библиотеки и возвращает абсолютный адрес целевой функции в памяти.
5. `dlclose` вызывает деструкторы `__attribute__((destructor))` и размонтирует память через `munmap()`.

## Подводные камни

1. **Выгрузка библиотеки (`dlclose`) при активных ссылках**: Если закрыть библиотеку через `dlclose`, а в Go-коде останется горутина, продолжающая выполнять код из этой `.so`, произойдет мгновенный `SIGSEGV`, так как виртуальные страницы памяти `.text` будут освобождены.
2. **Флаги линковщика `-ldl`**: В старых дистрибутивах Linux (glibc < 2.34) функции `dlopen` находились в отдельной библиотеке `libdl.so`. Необходимо явно указывать `#cgo LDFLAGS: -ldl`.
3. **Многопоточность и `dlerror()`**: Функция `dlerror()` возвращает указатель на статическую строку в TLS потока. Вызывать её нужно сразу после сбоя `dlopen`/`dlsym` до переключения контекста горутины.

## На собеседовании

**Вопрос с собеседования:** «Почему в enterprise Go-бэкендах избегают `plugin.Open` из стандартной библиотеки и используют CGO `dlopen` или микросервисы/gRPC/Wasm?»
**Ответ:**
Стандартный пакет `plugin` имеет непреодолимые ограничения:
1. Требует точнейшего совпадения версии Go, компилятора, хэшей всех пакетов зависимостей. При малейшем несовпадении (например, минорный патч Go 1.22.1 vs 1.22.2) вызов `plugin.Open` падает с фатальной паникой.
2. Не поддерживает выгрузку плагинов из памяти (no plugin unload).
3. Не поддерживается на Windows и имеет проблемы на macOS.
`dlopen` через CGO стабилен десятилетиями, стандартизирован стандартом POSIX и позволяет динамически подключать любые нативные модули (C, C++, Rust, Zig). Для полной изоляции современные архитектуры используют Wasm (Wasmtime, Wazero) или вынос в отдельные микросервисы через gRPC.
