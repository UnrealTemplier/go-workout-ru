# Создание фоновых C-потоков через pthread_create и вызовы в Go

## Условие

Напишите программу с CGO, которая создаёт C-thread (`pthread_create`) из Си-кода. Реализуйте функцию обратного вызова в Go (`//export WorkerReport`), вызываемую из фонового Си-потока. Объясните, как Go обрабатывает вызовы из не-Go потоков.

### Исходная формулировка

Напишите программу с `cgo`, которая создаёт C-thread (`pthread_create`) из Go. Объясните, почему это опасно: C-thread не знает о Go-scheduler, а Go-signal handler может конфликтовать. Покажите использование `runtime.LockOSThread` для goroutine, работающей с C-thread.

## Теория

Когда Си-библиотека (например, аудио-движок, сетевой сокет epoll или драйвер устройства) создает собственный поток ОС через `pthread_create`, этот поток **не был инициализирован рантаймом Go**.
У него нет структуры `m`, нет привязанного стека горутины, и он не зарегистрирован в планировщике Go.

Однако если этот фоновый C-поток вызывает функцию, экспортированную из Go (`//export WorkerReport`):
1. Вызов попадает в рантайм `runtime.cgocallback`.
2. Рантайм Go немедленно выполняет инициализацию потока (`runtime.needm`): выделяет временную структуру `m`, настраивает стек и регистрирует поток.
3. Безопасно выполняет Go-код.
4. По окончании вызывает `runtime.dropm`.

## Решение по шагам

1. В преамбуле подключите `<pthread.h>` и `<unistd.h>`.
2. Экспортируйте Go функцию: `//export WorkerReport(workerID int)`.
3. Реализуйте Си-функцию, запускающую `pthread_create(&tid, NULL, thread_entry, NULL)`.
4. В Си-потоке вызовите `WorkerReport`.
5. В `main` дождитесь завершения потока через `pthread_join`.

## Код решения

**`main.go`**

```go
package main

/*
#include <pthread.h>
#include <unistd.h>
#include <stdio.h>

extern void WorkerReport(int thread_num);

void* c_thread_worker(void* arg) {
    int id = (int)(intptr_t)arg;
    printf("[pthread #%d] Фоновый поток Си запущен, готовлю вызов в Go...\n", id);
    usleep(100000); // 100 мс работы в Си

    // Обратный вызов в Go из чужого Си-потока!
    WorkerReport(id);

    printf("[pthread #%d] Возврат из Go callback, завершение потока.\n", id);
    return NULL;
}

static inline void launch_c_thread(int id) {
    pthread_t tid;
    pthread_create(&tid, NULL, c_thread_worker, (void*)(intptr_t)id);
    pthread_join(tid, NULL); // Дожидаемся завершения
}
*/
import "C"
import "fmt"

//export WorkerReport
func WorkerReport(threadNum C.int) {
	fmt.Printf(">>> [Go Callback] Успешно вызван из pthread #%d! Рантайм Go создал контекст m.\n", int(threadNum))
}

func main() {
	fmt.Println("Старт: запуск фонового системного потока Си...")
	C.launch_c_thread(C.int(777))
	fmt.Println("Программа завершена без сбоев.")
}
```

ℹ️ needm / dropm в рантайме Go позволяют безопасно обслуживать вызовы из любых внешних потоков ОС.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Старт: запуск фонового системного потока Си...
# [pthread #777] Фоновый поток Си запущен, готовлю вызов в Go...
# >>> [Go Callback] Успешно вызван из pthread #777! Рантайм Go создал контекст m.
# [pthread #777] Возврат из Go callback, завершение потока.
# Программа завершена без сбоев.
```

## Под капотом

При вызове из стороннего потока `crosscall2` вызывает `runtime.needm()`. Функция захватывает глобальный мьютекс планировщика `sched.lock`, достает структуру `m` из свободного пула `sched.midle` (или аллоцирует новую) и настраивает стек. Накладные расходы такого первого вызова составляют ~10–20 микросекунд.

## Подводные камни

Если сторонний C-поток вызывает Go-функции с частотой 100 000 раз в секунду, постоянный захват `needm`/`dropm` вызовет колоссальный contention на глобальном локе рантайма Go. Для частых callback'ов поток лучше регистрировать постоянно.

## На собеседовании

**Вопрос с собеседования:** Что произойдет со сборщиком мусора Go, если сторонний поток C вызовет Go-функцию во время фазы Stop-The-World (STW)?
**Ответ:** Поток Си остановится в функции `runtime.needm` или `runtime.cgocallback`, ожидая завершения STW паузы на глобальном семафоре `worldsema`. Он не сможет войти в мир Go, пока сборщик мусора не закончит работу и не выполнит `runtime.startTheWorld()`, что гарантирует безопасность памяти.
