# Блокировка горутин при долгих C-вызовах и поведение планировщика GMP

## Условие

Вызови долгую C-функцию (`sleep(2)`). Во время её выполнения запусти параллельные горутины в Go, выполняющие фоновую работу. Убедись, что долгий вызов в Си не замораживает планировщик Go, и другие горутины продолжают работать.

### Исходная формулировка

**[Каверзный кейс — Блокировка горутин]**: Вызови долгую C-функцию (например, `sleep(5)`). Во время её выполнения запусти другую горутину в Go. Убедись, что поток ОС (M) заблокирован в C-коде. Посмотри через `runtime.NumGoroutine()` и `GOMAXPROCS`, как планировщик создает новый поток, чтобы не остановить работу Go-программы.

## Теория

Когда горутина вызывает медленную или блокирующую C-функцию (сетевой I/O, системный `sleep`, тяжелый расчет):
1. Рантайм Go вызывает `entersyscall()`: текущий поток ядра `M` переходит в мир Си и блокируется.
2. Логический процессор `P` немедленно **отцепляется** от потока `M` (hand-off P).
3. Системный монитор планировщика (`sysmon`) видит, что `P` свободен, и будит другой рабочий поток `M` (или создает новый поток `M`), чтобы продолжить выполнение других готовых горутин из очереди RunQueue!

Таким образом, блокирующий Си-вызов **не блокирует** всю программу на Go.

## Решение по шагам

1. В преамбуле подключите `<unistd.h>`.
2. Объявите функцию `void c_sleep(int sec) { sleep(sec); }`.
3. В `main` запустите фоновую горутину, печатающую сообщения каждые 200 мс.
4. В главной горутине вызовите `C.c_sleep(1)`.
5. Убедитесь, что фоновая горутина успела напечатать сообщения во время сна Си.

## Код решения

**`main.go`**

```go
package main

/*
#include <unistd.h>
#include <stdio.h>

void c_heavy_blocking_call(int seconds) {
    printf("[C Thread] Начало блокирующего вызова sleep(%d)...\n", seconds);
    sleep(seconds);
    printf("[C Thread] Блокирующий вызов sleep(%d) завершен!\n", seconds);
}
*/
import "C"
import (
	"fmt"
	"sync"
	"time"
)

func main() {
	var wg sync.WaitGroup
	stopCh := make(chan struct{})

	// Фоновая горутина на Go
	wg.Add(1)
	go func() {
		defer wg.Done()
		ticker := time.NewTicker(200 * time.Millisecond)
		defer ticker.Stop()

		for {
			select {
			case <-stopCh:
				return
			case t := <-ticker.C:
				fmt.Printf("  [Go Goroutine] Жива и работает в фоне: %s\n", t.Format("15:04:05.000"))
			}
		}
	}()

	fmt.Println("Go: Запуск блокирующей функции Си...")
	// Блокирующий вызов Си на 1 секунду
	C.c_heavy_blocking_call(1)
	fmt.Println("Go: Си-функция вернула управление.")

	close(stopCh)
	wg.Wait()
}
```

ℹ️ entersyscall() освобождает процессор P для других горутин на время блокировки в Си.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Go: Запуск блокирующей функции Си...
# [C Thread] Начало блокирующего вызова sleep(1)...
#   [Go Goroutine] Жива и работает в фоне: ...
#   [Go Goroutine] Жива и работает в фоне: ...
#   [Go Goroutine] Жива и работает в фоне: ...
# [C Thread] Блокирующий вызов sleep(1) завершен!
# Go: Си-функция вернула управление.
```

## Под капотом

Во время вызова CGO поток ядра M физически спит в системном вызове `nanosleep`. Функция `sysmon` в рантайме Go каждые 10 мс опрашивает потоки: видя поток в состоянии `_Psyscall`, она вызывает `handoffp(p)`, передавая процессор другому свободному потоку M. Когда Си просыпается, горутина пытается снова найти процессор P; если все P заняты, она встает в глобальную очередь runnable.

## Подводные камни

Если запустить 10 000 горутин, каждая из которых вызовет блокирующую Си-функцию, рантайм Go попытается создать 10 000 настоящих потоков ОС `pthread`, что приведет к исчерпанию лимита ОС и панике `fatal error: runtime: program exceeds 10000-thread limit`.

## На собеседовании

**Вопрос с собеседования:** Что произойдет, если в Go запустить тысячи горутин с блокирующими вызовами CGO?
**Ответ:** Поскольку каждая блокирующаяся в CGO горутина удерживает физический поток ядра ОС `M`, рантайм Go будет непрерывно создавать новые потоки `M`. По умолчанию в Go установлен лимит `debug.SetMaxThreads(10000)`. При превышении этого лимита процесс мгновенно завершается фатальной паникой. Для защиты сервиса блокирующие вызовы CGO оборачивают в ограниченный семафор или worker pool.
