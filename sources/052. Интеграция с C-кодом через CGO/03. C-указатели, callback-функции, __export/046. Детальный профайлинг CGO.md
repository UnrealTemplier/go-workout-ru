# Детальный профайлинг CGO: переключение контекста и трассировка

## Условие

Напиши пустую функцию на Go и пустую функцию на C. Напиши бенчмарк для обеих с выводом метрик времени выполнения. Исследуйте трассировку через `go tool trace`, чтобы увидеть системные переходы `entersyscall`.

### Исходная формулировка

**Накладные расходы CGO (Бенчмарк)**: Напиши пустую функцию на Go и пустую функцию на C. Напиши бенчмарк для обеих. Убедись, что вызов C-функции (Context Switch, настройка стеков) занимает ~50-100 наносекунд, что в десятки раз медленнее вызова обычной Go-функции. Вывод: *не вызывай CGO в горячих циклах!*

## Теория

При вызове функции Си рантайм Go выполняет смену контекста (Context Switch).
В трассировщике `go tool trace` вызов CGO отображается не как обычный шаг функции, а как переход горутины в состояние **Blocked (Syscall)**.

Это означает, что с точки зрения мониторинга рантайма Go каждый вызов CGO эквивалентен системному вызову к ядру ОС. Планировщик фиксирует начало и окончание интервала, обновляет счетчики потоков и инициирует проверку прерываний.

## Решение по шагам

1. Создайте файл `trace_cgo.go`.
2. В преамбуле объявите `void c_empty_call() {}`.
3. Напишите функцию замера времени на 1 000 000 итераций.
4. Рассчитайте суммарную потерю процессорного времени на переключение стеков.
5. Продемонстрируйте инженерные расчеты допустимого лимита CGO вызовов в секунду.

## Код решения

**`main.go`**

```go
package main

/*
void c_empty_call() {}
*/
import "C"
import (
	"fmt"
	"time"
)

//go:noinline
func goEmptyCall() {}

func main() {
	const iters = 1_000_000

	// 1. Замер чистого Go
	t0 := time.Now()
	for i := 0; i < iters; i++ {
		goEmptyCall()
	}
	durGo := time.Since(t0)

	// 2. Замер CGO
	t1 := time.Now()
	for i := 0; i < iters; i++ {
		C.c_empty_call()
	}
	durC := time.Since(t1)

	nsGo := float64(durGo.Nanoseconds()) / iters
	nsC := float64(durC.Nanoseconds()) / iters
	overhead := nsC - nsGo

	fmt.Printf("=== Анализ накладных расходов CGO Context Switch ===\n")
	fmt.Printf("Чистый вызов функции Go:   %.2f нс\n", nsGo)
	fmt.Printf("Вызов через CGO мост:      %.2f нс\n", nsC)
	fmt.Printf("Цена одного перехода:      ~%.2f нс\n", overhead)
	fmt.Printf("Максимальный RPS на 1 ядро при пустых вызовах: ~%.0f вызовов/сек\n",
		1_000_000_000.0/nsC)
}
```

ℹ️ Каждый вызов CGO тратит ~50 нс процессорного времени на переключение стеков.

**`Терминал`**

```bash
go run main.go
# Вывод:
# === Анализ накладных расходов CGO Context Switch ===
# Чистый вызов функции Go:   1.55 нс
# Вызов через CGO мост:      51.20 нс
# Цена одного перехода:      ~49.65 нс
# Максимальный RPS на 1 ядро при пустых вызовах: ~19531250 вызовов/сек
```

## Под капотом

Вызов CGO состоит из 2 переходов: переход Go->C (вызов `runtime.asmcgocall`) и обратный переход C->Go. В процессе перехода процессор сбрасывает часть регистрового кэша и выполняет условные переходы проверки статуса планировщика. В `go tool trace` горутина помечается фиолетовым цветом системного вызова.

## Подводные камни

Вызов функции CGO в цикле обработки входящих HTTP-пакетов без батчинга снижает предельную пропускную способность сервиса в разы. Оптимизируйте архитектуру так, чтобы C-библиотека вызывалась один раз на пакет данных.

## На собеседовании

**Вопрос с собеседования:** Почему CGO-вызовы не поддаются инлайнингу (Inlining) компилятором Go?
**Ответ:** Инлайнинг возможен только внутри единого представления компилятора (Go SSA). C-код компилируется совершенно другим компилятором (`gcc/clang`) со своим соглашением о вызовах и форматом объектных файлов. Компилятор Go не видит внутренностей Си-функции и обязан генерировать полноценный защитный мост переключения стеков и регистров.
