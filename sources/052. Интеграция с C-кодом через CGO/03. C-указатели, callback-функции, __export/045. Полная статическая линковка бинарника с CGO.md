# Полная статическая линковка бинарника с CGO (-extldflags -static)

## Условие

Соберите полностью статически слинкованный бинарник Go с CGO, не зависящий от разделяемых библиотек `.so`. Используйте флаги сборки `go build --ldflags="-extldflags '-static'"`. Проверьте результат утилитой `file` и `ldd`.

### Исходная формулировка

**Static linking**: Соберите статически линкованный бинарник через `CGO_LDFLAGS="-static"`.

## Теория

По умолчанию бинарник с CGO требует динамический линкер операционной системы (`libc.so.6`).
Для развертывания в минималистичных контейнерах (`FROM scratch`) требуется **статическая линковка**:
`go build -ldflags="-extldflags '-static'"`

Этот флаг заставляет системный компоновщик `gcc/ld` вшить все функции `libc` прямо в исполняемый файл.
В результате `ldd` выводит `not a dynamic executable`, а бинарник можно запустить на любом Linux-сервере с тем же ядром без установки зависимостей!

## Решение по шагам

1. Создайте файл `static_cgo.go` с вызовом простой C-функции.
2. Скомпилируйте со статическими флагами:
   `go build -ldflags="-extldflags '-static'" -o static_app static_cgo.go`.
3. Запустите `ldd static_app` и убедитесь в сообщении `not a dynamic executable`.
4. Запустите `file static_app` и проверьте флаг `statically linked`.
5. Запустите бинарник и проверьте корректную работу.

## Код решения

**`static_cgo.go`**

```go
package main

/*
#include <stdio.h>

void print_static_banner() {
    printf(">>> Hello from Fully Statically Linked CGO Binary! <<<\n");
}
*/
import "C"

func main() {
	C.print_static_banner()
}
```

ℹ️ Сборка со статическим glibc/musl создает полностью автономный бинарник.

**`Терминал`**

```bash
go build -ldflags="-extldflags '-static'" -o static_app static_cgo.go
file static_app
# Вывод:
# static_app: ELF 64-bit LSB executable, ..., statically linked

ldd static_app
# Вывод:
# not a dynamic executable

./static_app
# Вывод:
# >>> Hello from Fully Statically Linked CGO Binary! <<<
```

## Под капотом

Флаг `-extldflags '-static'` инструктирует внешний компоновщик `ld` использовать архивы статических библиотек `libc.a` и `libpthread.a` вместо разделяемых `.so` файлов. В итоговом ELF файле отсутствуют секции `.interp` и `.dynamic`. Ядро ОС может запустить такой процесс напрямую без динамического загрузчика.

## Подводные камни

В `glibc` некоторые функции (например, резолвер DNS `getaddrinfo` и функции `nsswitch`) требуют динамической загрузки даже при статической сборке, выводя предупреждение компоновщика `Using 'getaddrinfo' in statically linked applications requires at runtime the shared libraries from the glibc version used for linking`. Для чистой статики лучше использовать Alpine `musl`.

## На собеседовании

**Вопрос с собеседования:** Почему при статической сборке Go сервисов с CGO для Docker контейнеров предпочтительнее компилятор `musl-gcc` (Alpine), а не `glibc`?
**Ответ:** Потому что `glibc` исторически плохо приспособлен для полной статической линковки (подсистема NSS требует загрузки динамических плагинов `libnss_*.so` для резолва DNS и пользователей). Библиотека `musl` изначально спроектирована под чистую статическую линковку без скрытых runtime-зависимостей, давая ультракомпактные и надежные контейнеры `FROM scratch`.
