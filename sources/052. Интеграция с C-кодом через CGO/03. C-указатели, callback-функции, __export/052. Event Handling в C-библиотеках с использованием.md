# Event Handling в C-библиотеках с использованием cgo.Handle

## Условие

Создайте C-библиотеку таймеров, которая принимает интервал и callback для event handling. В Go используйте `//export` и `cgo.Handle` для передачи подписчика на события. Продемонстрируйте доставку 3 событий в Go-канал.

### Исходная формулировка

**Go callbacks в C**: Создайте C-библиотеку, которая вызывает Go-функции для event handling. Используйте `//export` и `CgoHandle` для передачи контекста.

## Теория

При интеграции с событийными библиотеками (libevent, libuv, драйверы брокеров сообщений Kafka/RabbitMQ librdkafka) Си-библиотека подписывается на события сокетов или таймеров.
Паттерн архитектуры:
1. Go регистрирует структуру подписчика `Subscriber` через `cgo.NewHandle(sub)`.
2. В C передается числовой хэндл `uintptr(h)` и указатель на статический C-callback.
3. Си-библиотека при наступлении события вызывает callback, передавая хэндл.
4. Go извлекает `sub` и передает событие в канал `chan Event`.

## Решение по шагам

1. В преамбуле напишите Си-функцию таймера: `void trigger_ticks(int count, void (*cb)(uintptr_t, int), uintptr_t ctx)`.
2. В Go создайте структуру `EventHub { events chan int }`.
3. Создайте `handle := cgo.NewHandle(hub)`.
4. Экспортируйте Go-функцию: `//export OnTick(h C.uintptr_t, tick C.int)`.
5. Прочитайте события из Go-канала в цикле.

## Код решения

**`main.go`**

```go
package main

/*
#include <stdint.h>
#include <unistd.h>

typedef void (*tick_cb)(uintptr_t handle, int tick);

static inline void run_timer_events(int total_ticks, tick_cb cb, uintptr_t ctx) {
    for (int i = 1; i <= total_ticks; i++) {
        usleep(50000); // 50 мс
        cb(ctx, i);
    }
}
*/
import "C"
import (
	"fmt"
	"runtime/cgo"
)

type EventHub struct {
	events chan int
}

//export OnTick
func OnTick(h C.uintptr_t, tick C.int) {
	// Восстанавливаем EventHub из хэндла
	hub := cgo.Handle(h).Value().(*EventHub)
	hub.events <- int(tick)
}

func main() {
	hub := &EventHub{events: make(chan int, 10)}
	handle := cgo.NewHandle(hub)
	defer handle.Delete()

	// Запускаем Си-генератор событий в отдельной горутине
	go func() {
		C.run_timer_events(3, (C.tick_cb)(C.OnTick), C.uintptr_t(handle))
		close(hub.events)
	}()

	fmt.Println("Ожидание событий из Си-таймера через канал Go:")
	for evt := range hub.events {
		fmt.Printf("  Получено событие #%d в Go-горутине!\n", evt)
	}

	fmt.Println("Все события успешно обработаны.")
}
```

ℹ️ Связка cgo.Handle и Go-каналов превращает Си-события в идиоматичный Go concurrency поток.

**`Терминал`**

```bash
go run main.go
# Вывод:
# Ожидание событий из Си-таймера через канал Go:
#   Получено событие #1 в Go-горутине!
#   Получено событие #2 в Go-горутине!
#   Получено событие #3 в Go-горутине!
# Все события успешно обработаны.
```

## Под капотом

Каждый вызов `cb(ctx, i)` из Си выполняет переход через `crosscall2` в рантайм Go. Экспортированная функция `OnTick` выполняется в контексте горутины и отправляет значение в канал `hub.events`. Канал разблокирует читающую горутину в функции `main`.

## Подводные камни

Если канал не буферизирован (`make(chan int)`), а Си-поток вызывает callback синхронно, отправка в канал заблокирует Си-поток до тех пор, пока читатель не прочитает значение. Буферизация каналов необходима для изоляции Си-потоков от блокировок.

## На собеседовании

**Вопрос с собеседования:** Как архитектурно связать событийно-ориентированную C-библиотеку (libuv/epoll) с конкурентной моделью Go (CSP/Channels)?
**Ответ:** Через шаблон Event Bridge: C-колбэки не должны выполнять бизнес-логику Go. Они должны минимально упаковать данные события, отправить их через `cgo.Handle` в буферизированный канал `chan Event` Go и немедленно вернуть управление Си-циклу (Event Loop). Вся обработка происходит в пуле Go-горутин-потребителей.
