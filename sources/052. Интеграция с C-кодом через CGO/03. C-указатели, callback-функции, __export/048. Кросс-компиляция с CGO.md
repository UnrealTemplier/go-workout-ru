# Кросс-компиляция с CGO (Cross-Compilation Toolchains)

## Условие

Изучите механику кросс-компиляции CGO-кода: почему простая смена `GOOS=windows` или `GOARCH=arm64` не работает при `CGO_ENABLED=1`. Напишите пример сборки с использованием кросс-компилятора `CC` и современного решения на базе `zig cc`.

### Исходная формулировка

**Cross-compilation с CGO**: Попробуйте cross-compile CGO код (это сложно!). Используйте Docker или cross-compiler toolchains.

## Теория

При отключенном CGO (`CGO_ENABLED=0`) кросс-компиляция в Go работает мгновенно «из коробки»:
`GOOS=linux GOARCH=arm64 go build`
Однако при `CGO_ENABLED=1` компилятор Go сам по себе не умеет собирать C-код под чужую архитектуру: ему требуется целевой C-компилятор и стандартная библиотека C целевой ОС.

Для кросс-компиляции CGO необходимо:
1. Задать переменную `CC`: целевой Си-компилятор (например, `CC=aarch64-linux-gnu-gcc` или `CC=x86_64-w64-mingw32-gcc`).
2. Либо использовать современный универсальный кросс-компилятор **Zig**:
`CC="zig cc -target x86_64-windows-gnu" CGO_ENABLED=1 go build`.

## Решение по шагам

1. Создайте CGO-программу `cross_demo.go`.
2. Попробуйте выполнить `GOOS=windows go build cross_demo.go` и зафиксируйте ошибку `gcc: not found`.
3. Напишите Makefile/скрипт с правильным указанием переменной `CC`.
4. Покажите синтаксис использования `zig cc` для компиляции под Linux ARM64 и Windows x86-64.
5. Объясните концепцию sysroot и заголовочных файлов целевой системы.

## Код решения

**`cross_demo.go`**

```go
package main

/*
#include <stdio.h>

void print_arch() {
    #if defined(__x86_64__)
    printf("[C] Архитектура: x86_64 (AMD64)\n");
    #elif defined(__aarch64__)
    printf("[C] Архитектура: AArch64 (ARM64)\n");
    #else
    printf("[C] Неизвестная архитектура\n");
    #endif
}
*/
import "C"
import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Printf("Go runtime OS/ARCH: %s/%s\n", runtime.GOOS, runtime.GOARCH)
	C.print_arch()
}
```

ℹ️ Код адаптируется под архитектуру целевого C-компилятора через директивы препроцессора.

**`Терминал`**

```bash
# 1. Попытка собрать под Windows без кросс-компилятора завершится ошибкой:
# GOOS=windows go build cross_demo.go
# exit status 1: ... gcc: not found

# 2. Кросс-компиляция с использованием Zig (под Linux ARM64):
CGO_ENABLED=1 GOOS=linux GOARCH=arm64 CC="zig cc -target aarch64-linux-musl" go build -o app-arm64 cross_demo.go
file app-arm64
# app-arm64: ELF 64-bit LSB executable, ARM aarch64, ...
```

## Под капотом

Переменная `CC` передается препроцессору CGO. CGO компилирует преамбулу целевым компилятором в целевой объектный формат. Затем компоновщик Go собирает целевой исполняемый файл. Если целевая `libc` отсутствует, компоновка завершается неудачей.

## Подводные камни

Кросс-компиляция под macOS (`GOOS=darwin`) с хоста Linux невозможна стандартным `gcc`, так как требует закрытых SDK Apple (Xcode). Для нее требуются проекты `osxcross` или `zig cc` с macOS SDK.

## На собеседовании

**Вопрос с собеседования:** Как решить проблему кросс-компиляции CGO-сервисов в enterprise CI/CD пайплайнах?
**Ответ:** 1) Использовать `zig cc` в качестве $CC, так как Zig содержит заголовочные файлы и библиотеки `musl/glibc` для 30+ архитектур прямо в бинарнике; 2) Использовать Docker контейнеры с эмуляцией QEMU (`docker buildx --platform linux/amd64,linux/arm64`), собирая бинарник нативно внутри целевого окружения; 3) Избавиться от CGO (`CGO_ENABLED=0`), если это возможно.
