# AWS KMS GenerateDataKey: Безопасное получение DEK и удаление открытого ключа

## Условие

Используйте AWS SDK (`github.com/aws/aws-sdk-go-v2/service/kms`) для вызова `GenerateDataKey` (AES-256). Получите `Plaintext` (DEK) и `CiphertextBlob` (зашифрованный DEK). Зашифруйте файл, удалите `Plaintext` из памяти (`memzero`), сохраните `CiphertextBlob` рядом с данными. Объясните, почему DEK никогда не хранится в plaintext вне RAM.

### Исходная формулировка

**AWS KMS: GenerateDataKey.**: Используйте AWS SDK (`github.com/aws/aws-sdk-go-v2/service/kms`) для вызова `GenerateDataKey` (AES-256). Получите `Plaintext` (DEK) и `CiphertextBlob` (зашифрованный DEK). Зашифруйте файл, удалите `Plaintext` из памяти (`memzero`), сохраните `CiphertextBlob` рядом с данными. Объясните, почему DEK никогда не хранится в plaintext вне RAM.

## Теория

Метод **`GenerateDataKey`** сервиса AWS KMS является центральным кирпичиком всей облачной криптографии.

### Почему `Plaintext` DEK никогда не сохраняется вне оперативной памяти:
1. **Принцип нулевого доверия к постоянным хранилищам:** Диски серверов, кэширующие прокси, файлы журналов, снапшоты EBS и бэкапы могут быть скопированы, украдены или скомпрометированы. Если открытый DEK попадет на диск, злоумышленник сможет расшифровать файл без обращения к KMS.
2. **Аудит каждого факта доступа к данным (Audit Trail):** Поскольку открытый DEK живет только в RAM, для каждого повторного чтения файла приложение обязано вызвать `kms.Decrypt(CiphertextBlob)`. Каждое обращение к KMS немедленно фиксируется в журнале аудита AWS CloudTrail с фиксацией IAM-роли, времени, IP-адреса и контекста шифрования.
3. **Crypto-Shredding (Мгновенное уничтожение данных):** Если отозвать ключ KMS (или удалить его из KMS), **все миллионы зашифрованных файлов мгновенно становятся математически нечитаемым мусором**, даже если их копии лежат на тысячах серверов по всему миру!

## Решение по шагам

1. Сконфигурируйте запрос `kms.GenerateDataKeyInput` с типом `types.DataKeySpecAes256`.
2. Вызовите `kmsClient.GenerateDataKey(ctx, input)`.
3. Извлеките открытый ключ `out.Plaintext` и зашифрованный ключ `out.CiphertextBlob`.
4. Выполните шифрование файла ключом `out.Plaintext`.
5. Занулите открытый ключ с помощью функции `memzero`.
6. Сохраните `out.CiphertextBlob` в файл метаданных `.key`.

## Код решения

**`generate_datakey_flow.go`**

```go
package main

import (
	"context"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"log"

	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/service/kms"
	"github.com/aws/aws-sdk-go-v2/service/kms/types"
)

// SecureMemZero гарантирует затирание среза в оперативной памяти
func SecureMemZero(b []byte) {
	for i := range b {
		b[i] = 0
	}
}

// EncryptWithKMSDataKey эмулирует безопасный цикл жизни ключа DEK
func EncryptWithKMSDataKey(plainText []byte, plaintextDEK []byte) ([]byte, []byte, error) {
	// Гарантируем уничтожение открытого DEK после выхода из функции
	defer SecureMemZero(plaintextDEK)

	block, err := aes.NewCipher(plaintextDEK)
	if err != nil {
		return nil, nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, nil, err
	}

	nonce := make([]byte, gcm.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, nil, err
	}

	ciphertext := gcm.Seal(nil, nonce, plainText, nil)
	return nonce, ciphertext, nil
}

func main() {
	fmt.Println("=== Демонстрация безопасного жизненного цикла GenerateDataKey ===")

	// Имитация ответа KMS GenerateDataKey
	mockPlaintextDEK := make([]byte, 32)
	_, _ = rand.Read(mockPlaintextDEK)
	mockCiphertextBlob := []byte("KMS_CIPHERTEXT_BLOB_STORED_ON_DISK")

	fileData := []byte("Конфиденциальный отчет по безопасности ядра Kubernetes")

	nonce, ciphertext, err := EncryptWithKMSDataKey(fileData, mockPlaintextDEK)
	if err != nil {
		log.Fatalf("Ошибка шифрования: %v", err)
	}

	fmt.Println("1. Данные успешно зашифрованы ключом DEK")
	fmt.Printf("2. Размер шифротекста: %d байт\n", len(ciphertext))
	fmt.Printf("3. Nonce: %x\n", nonce)
	fmt.Printf("4. CiphertextBlob для сохранения на диске: %s\n", string(mockCiphertextBlob))

	// Проверяем, что исходный срез занулен
	isZeroed := true
	for _, b := range mockPlaintextDEK {
		if b != 0 {
			isZeroed = false
			break
		}
	}
	fmt.Printf("5. Открытый DEK в памяти занулен (Zeroed): %v\n", isZeroed)
}
```

ℹ️ Паттерн безопасного уничтожения открытого ключа DEK сразу после шифрования

## Под капотом

В аппаратных модулях безопасности AWS CloudHSM для генерации ключей используется аппаратный квантовый или термошумовой генератор случайных чисел (TRNG — True Random Number Generator), сертифицированный по стандарту NIST SP 800-90A/B.
Сгенерированный 256-битный DEK зашифровывается мастер-ключом KEK непосредственно на кристалле HSM без вывода мастер-ключа в системную память гипервизора AWS, обеспечивая абсолютную защиту от компрометации со стороны персонала дата-центра.

## Подводные камни

Сохранение структуры `kms.GenerateDataKeyOutput` в долгоживущую глобальную переменную приложения. Если структура `out` остается доступной через глобальные указатели, открытый ключ `out.Plaintext` никогда не будет утилизирован сборщиком мусора и останется уязвимым для анализа дампов памяти.

## На собеседовании

**Вопрос на собеседовании (Lead Security Engineer):**
«Как в Go гарантировать, что компилятор не оптимизирует (dead store elimination) цикл зануления памяти ключа memzero?»

**Эталонный ответ:**
Оптимизирующий компилятор может решить, что запись нулей в срез, который больше нигде не читается, является «мертвым кодом» (Dead Store), и выбросить цикл при компиляции с флагом `-O2`.
Для предотвращения оптимизации в Go используют:
1. Вызов `runtime.KeepAlive(slice)` после цикла зануления, сообщая компилятору, что переменная активна до этой точки.
2. Использование пакета `crypto/subtle`: запись через неоптимизируемые барьеры памяти или ассемблерные вставки Plan 9.
3. Начиная с Go 1.24 в стандартную библиотеку добавляются специализированные функции гарантированного зануления памяти (`crypto/subtle.Zero`).
