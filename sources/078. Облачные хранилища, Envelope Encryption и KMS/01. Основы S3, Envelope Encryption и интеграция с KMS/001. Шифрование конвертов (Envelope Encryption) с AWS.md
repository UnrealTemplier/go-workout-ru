## Теория

При проектировании облачных систем хранения конфиденциальных данных (финансовые транзакции, медицинские карты, персональные данные по 152-ФЗ / GDPR) разработчики сталкиваются с вопросом: **почему нельзя напрямую отправить файл размером 5 ГБ в облачный сервис управления ключами (AWS KMS, GCP Cloud KMS, Yandex Cloud KMS)?**

### Ограничения облачных Key Management Services:
1. **Жесткий лимит размера полезной нагрузки (Payload Limit):** В AWS KMS метод `Encrypt()` принимает на вход данные размером **не более 4 КБ** (`4096 bytes`). Сервис KMS физически аппаратно не предназначен для пересылки медиафайлов, архивов или дампов баз данных.
2. **Сетевые накладные расходы (Network Bottleneck):** Передача терабайтов пользовательских данных через API KMS создала бы колоссальный сетевой трафик, перегрузила каналы и многократно увеличила задержку (RTT).
3. **Квоты и стоимость вызовов (KMS Rate Limits & Billing):** Стоимость KMS тарифицируется поштучно за каждый API-вызов, а квота на аккаунт обычно ограничена 10 000–50 000 запросов в секунду.

### Архитектура Envelope Encryption (Шифрование конвертов):
Envelope Encryption решает эту проблему за счет двухуровневой иерархии криптографических ключей:
```
                                 [ Облако AWS KMS ]
                                         │
                                         ▼ GenerateDataKey(CMK)
                      ┌──────────────────────────────────────┐
                      │ KMS возвращает пару:                 │
                      │ 1. Plaintext DEK (в открытом виде)   │
                      │ 2. CiphertextBlob (зашифрованный DEK)│
                      └──────────────────┬───────────────────┘
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
      [ В оперативной памяти Go ]                      [ Сохранение на диск / S3 ]
  Шифрование 5 ГБ файла локальным                     Зашифрованный файл (Ciphertext)
  алгоритмом AES-256-GCM ключом DEK                              +
                 │                                    Зашифрованный ключ (CiphertextBlob)
                 ▼                                               │
  ОЧИСТКА Plaintext DEK из памяти!                               ▼
  (memzero: for i := range dek { dek[i] = 0 })        Хакер не сможет расшифровать
                                                      данные без прав в AWS KMS!
```

- **KEK (Key Encryption Key / Customer Master Key — CMK):** Долгоживущий асимметричный или симметричный мастер-ключ, который физически никогда не покидает аппаратный модуль безопасности (Hardware Security Module — HSM) облачного провайдера.
- **DEK (Data Encryption Key):** Одноразовый симметричный ключ (AES-256, 32 байта), генерируемый для конкретного объекта данных. Данные шифруются на стороне клиента (Client-Side Encryption) локальным процессором с аппаратным ускорением AES-NI со скоростью гигабайт в секунду!

## Решение по шагам

1. Сконфигурируйте клиент AWS KMS SDK v2 (`github.com/aws/aws-sdk-go-v2/service/kms`).
2. Вызовите метод `kmsClient.GenerateDataKey(ctx, &kms.GenerateDataKeyInput{KeyId: ..., KeySpec: types.DataKeySpecAes256})`.
3. Получите открытый ключ `res.Plaintext` и зашифрованный мастер-ключом `res.CiphertextBlob`.
4. Выполните локальное шифрование данных алгоритмом AES-256-GCM с уникальным криптографическим Nonce (12 байт).
5. Гарантированно занулите открытый ключ `res.Plaintext` в оперативной памяти (Zeroing).
6. Сохраните зашифрованные данные вместе с `CiphertextBlob` и `Nonce`.

## Код решения

**`envelope_kms.go`**

```go
package main

import (
	"context"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"log"

	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/service/kms"
	"github.com/aws/aws-sdk-go-v2/service/kms/types"
)

// EncryptedEnvelope представляет защищенный конверт данных
type EncryptedEnvelope struct {
	EncryptedDEK []byte // Зашифрованный мастер-ключом DEK (CiphertextBlob)
	Nonce        []byte // Одноразовый номер GCM (12 байт)
	Ciphertext   []byte // Полезная нагрузка, зашифрованная DEK
}

// MockKMSClient эмулирует поведение AWS KMS API для автономного запуска и тестирования
type MockKMSClient struct {
	MasterKey []byte
}

func NewMockKMSClient() *MockKMSClient {
	mk := make([]byte, 32)
	_, _ = rand.Read(mk)
	return &MockKMSClient{MasterKey: mk}
}

// GenerateDataKey генерирует 32-байтный ключ DEK и возвращает его в открытом и зашифрованном виде
func (m *MockKMSClient) GenerateDataKey(ctx context.Context, params *kms.GenerateDataKeyInput, optFns ...func(*kms.Options)) (*kms.GenerateDataKeyOutput, error) {
	// 1. Генерируем случайный DEK (AES-256 = 32 байта)
	plaintextDEK := make([]byte, 32)
	if _, err := io.ReadFull(rand.Reader, plaintextDEK); err != nil {
		return nil, fmt.Errorf("генерация DEK: %w", err)
	}

	// 2. Шифруем DEK мастер-ключом (KEK) через AES-GCM
	block, err := aes.NewCipher(m.MasterKey)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}

	nonce := make([]byte, gcm.NonceSize())
	_, _ = io.ReadFull(rand.Reader, nonce)
	encryptedDEK := gcm.Seal(nonce, nonce, plaintextDEK, nil)

	return &kms.GenerateDataKeyOutput{
		KeyId:          params.KeyId,
		Plaintext:      plaintextDEK,
		CiphertextBlob: encryptedDEK,
	}, nil
}

// MemZero перезаписывает срез байтов нулями для защиты от дампов памяти
func MemZero(b []byte) {
	for i := range b {
		b[i] = 0
	}
}

// EncryptWithEnvelope выполняет процедуру Envelope Encryption
func EncryptWithEnvelope(ctx context.Context, kmsClient *MockKMSClient, keyID string, plaintextData []byte) (*EncryptedEnvelope, error) {
	// 1. Запрашиваем у KMS генерацию одноразового ключа данных DEK
	out, err := kmsClient.GenerateDataKey(ctx, &kms.GenerateDataKeyInput{
		KeyId:   aws.String(keyID),
		KeySpec: types.DataKeySpecAes256,
	})
	if err != nil {
		return nil, fmt.Errorf("kms GenerateDataKey: %w", err)
	}

	// КРИТИЧЕСКИ ВАЖНО: гарантируем очистку открытого DEK из памяти при выходе
	plaintextDEK := out.Plaintext
	defer MemZero(plaintextDEK)

	// 2. Локальное шифрование данных ключом DEK (AES-256-GCM)
	block, err := aes.NewCipher(plaintextDEK)
	if err != nil {
		return nil, fmt.Errorf("aes.NewCipher: %w", err)
	}

	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, fmt.Errorf("cipher.NewGCM: %w", err)
	}

	nonce := make([]byte, gcm.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, fmt.Errorf("генерация nonce: %w", err)
	}

	ciphertext := gcm.Seal(nil, nonce, plaintextData, nil)

	return &EncryptedEnvelope{
		EncryptedDEK: out.CiphertextBlob,
		Nonce:        nonce,
		Ciphertext:   ciphertext,
	}, nil
}

func main() {
	ctx := context.Background()
	kmsClient := NewMockKMSClient()
	keyID := "arn:aws:kms:us-east-1:123456789012:key/custom-master-key-id"

	secretPayload := []byte("TOP_SECRET_CREDIT_CARD_DATA: 4111-2222-3333-4444")
	fmt.Printf("Исходные конфиденциальные данные: %s\n", string(secretPayload))

	envelope, err := EncryptWithEnvelope(ctx, kmsClient, keyID, secretPayload)
	if err != nil {
		log.Fatalf("Ошибка Envelope Encryption: %v", err)
	}

	fmt.Println("\n=== Конверт успешно сформирован ===")
	fmt.Printf("1. Зашифрованный DEK (CiphertextBlob): %x... (%d байт)\n", envelope.EncryptedDEK[:16], len(envelope.EncryptedDEK))
	fmt.Printf("2. Случайный Nonce (AES-GCM):          %x (%d байт)\n", envelope.Nonce, len(envelope.Nonce))
	fmt.Printf("3. Зашифрованные данные:              %x... (%d байт)\n", envelope.Ciphertext[:16], len(envelope.Ciphertext))
	fmt.Println("4. Открытый DEK (Plaintext) гарантированно удален из оперативной памяти!")
}
```

ℹ️ Реализация паттерна Envelope Encryption с вызовом GenerateDataKey и занулением памяти

## Под капотом

Почему зануление памяти `MemZero` обязательно:
В среде выполнения Go сборщик мусора (GC) не зануляет освобожденную память немедленно; он лишь возвращает аллоцированные страницы в свободные пролеты (`mcache`/`mcentral`). 
Если открытый 32-байтный ключ DEK останется в памяти, он может сохраняться в куче минутами или часами. В случае создания дампа памяти при аварии приложения (`core dump`), при профилировании `pprof` или при атаке класса Heartbleed/Cold Boot злоумышленник сможет извлечь открытый DEK из RAM. 
Явный цикл `for i := range b { b[i] = 0 }` (или `runtime.KeepAlive`) затирает криптографический материал физическими нулями перед тем, как отдать память сборщику мусора.

## Подводные камни

Опасная ошибка: повторное использование одного и того же DEK для миллионов файлов. Если одним и тем же ключом AES-GCM зашифровать более \(2^{32}\) сообщений со случайным 96-битным Nonce, из-за парадокса дней рождения возникнет коллизия Nonce (`Nonce Reuse`), что приведет к мгновенной математической компрометации ключа AES-GCM и возможности дешифрования всех данных! В Envelope Encryption для каждого объекта **обязан генерироваться уникальный DEK**.

## На собеседовании

**Вопрос на собеседовании (Cloud Security Architect / Staff Engineer):**
«В чем разница между Server-Side Encryption с KMS (SSE-KMS в AWS S3) и Client-Side Envelope Encryption с KMS (CSE-KMS)? Каковы требования регуляторов (PCI DSS, HIPAA)?»

**Эталонный ответ:**
- **SSE-KMS (Server-Side Encryption):** Клиент передает данные в открытом виде по TLS в облачный бакет S3. Сервис AWS S3 сам вызывает KMS `GenerateDataKey`, шифрует файл на серверной стороне AWS и сохраняет зашифрованный объект. Провайдер облака кратковременно видит данные в открытом виде в памяти своих серверов.
- **CSE-KMS (Client-Side Encryption):** Приложение в своем защищенном контуре запрашивает у KMS только зашифрованный DEK, шифрует файл на локальном процессоре и отправляет в S3 **уже зашифрованные байты**. Облачный провайдер AWS/Yandex Cloud не видит открытые данные ни на один микросекундный такт. Это строго обязательно для соответствия требованиям финансовой безопасности (PCI DSS Tier 1) и суверенитета данных.
