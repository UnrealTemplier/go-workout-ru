# Хранение зашифрованного DEK: Метаданные объектов S3 и реляционные базы данных

## Условие

Сохраните encrypted DEK и encrypted data вместе (например, в S3 object metadata или в БД).

### Исходная формулировка

**Store encrypted DEK + data**: Сохраните encrypted DEK и encrypted data вместе (например, в S3 object metadata или в БД).

## Теория

Где физически хранить зашифрованный ключ `CiphertextBlob (DEK)` и сопутствующие криптографические параметры (`Nonce`, `KeyID`, `Algorithm`)?

В современной архитектуре существует два доминирующих подхода:

1. **В метаданных объекта S3 (S3 User Metadata):**
   - Заголовки `x-amz-meta-encrypted-dek`, `x-amz-meta-nonce`, `x-amz-meta-key-id`.
   - *Плюсы:* Объект абсолютно автономен (Self-Contained Envelope). Файл можно перемещать между бакетами, копировать или архивировать в Glacier — его ключ шифрования всегда путешествует вместе с ним.
   - *Минусы:* Ограничение на общий размер метаданных в S3 (не более 2 КБ).

2. **В реляционной базе данных (PostgreSQL / MySQL):**
   - Таблица файлов: `id`, `s3_key`, `encrypted_dek`, `nonce`, `kms_key_id`, `created_at`.
   - *Плюсы:* Возможность пакетной выборки, индексации и ротации ключей через обычные SQL-запросы (`UPDATE files SET encrypted_dek = ...`).
   - *Минусы:* Рассинхронизация: при удалении записи из БД файл в S3 остается «сиротой».

## Решение по шагам

1. Сформируйте словарь метаданных для сохранения в S3.
2. Закодируйте бинарные срезы `EncryptedDEK` и `Nonce` в формат Base64 (так как HTTP-заголовки S3 поддерживают только ASCII символы).
3. Загрузите объект через `PutObject` с метаданными.
4. Прочитайте метаданные через `HeadObject`, декодируйте Base64 и восстановите криптографический контекст.

## Код решения

**`metadata_storage.go`**

```go
package main

import (
	"encoding/base64"
	"fmt"
)

// EnvelopeMetadata инкапсулирует криптографические заголовки
type EnvelopeMetadata struct {
	KeyID        string
	EncryptedDEK []byte
	Nonce        []byte
	Algorithm    string
}

// ToS3Metadata преобразует криптографические параметры в ASCII-заголовки для S3
func (m *EnvelopeMetadata) ToS3Metadata() map[string]string {
	return map[string]string{
		"key-id":        m.KeyID,
		"algorithm":     m.Algorithm,
		"encrypted-dek": base64.StdEncoding.EncodeToString(m.EncryptedDEK),
		"nonce":         base64.StdEncoding.EncodeToString(m.Nonce),
	}
}

// FromS3Metadata восстанавливает структуру из заголовков S3
func FromS3Metadata(s3Meta map[string]string) (*EnvelopeMetadata, error) {
	encDEKBytes, err := base64.StdEncoding.DecodeString(s3Meta["encrypted-dek"])
	if err != nil {
		return nil, fmt.Errorf("невалидный base64 encrypted-dek: %w", err)
	}

	nonceBytes, err := base64.StdEncoding.DecodeString(s3Meta["nonce"])
	if err != nil {
		return nil, fmt.Errorf("невалидный base64 nonce: %w", err)
	}

	return &EnvelopeMetadata{
		KeyID:        s3Meta["key-id"],
		Algorithm:    s3Meta["algorithm"],
		EncryptedDEK: encDEKBytes,
		Nonce:        nonceBytes,
	}, nil
}

func main() {
	originalMeta := &EnvelopeMetadata{
		KeyID:        "arn:aws:kms:us-east-1:123456789:key/prod-cmk",
		EncryptedDEK: []byte{0xDE, 0xAD, 0xBE, 0xEF, 0x01, 0x02, 0x03, 0x04},
		Nonce:        []byte{0xAA, 0xBB, 0xCC, 0xDD, 0x11, 0x22, 0x33, 0x44, 0x55, 0x66, 0x77, 0x88},
		Algorithm:    "AES-256-GCM",
	}

	// Кодирование для HTTP заголовков S3
	s3Headers := originalMeta.ToS3Metadata()
	fmt.Println("=== S3 Object Metadata Headers (ASCII) ===")
	for k, v := range s3Headers {
		fmt.Printf("x-amz-meta-%s: %s\n", k, v)
	}

	// Декодирование при чтении из S3
	restored, err := FromS3Metadata(s3Headers)
	if err != nil {
		panic(err)
	}

	fmt.Println("\n=== Метаданные успешно восстановлены из S3 ===")
	fmt.Printf("KeyID:        %s\n", restored.KeyID)
	fmt.Printf("Algorithm:    %s\n", restored.Algorithm)
	fmt.Printf("EncryptedDEK: %x\n", restored.EncryptedDEK)
	fmt.Printf("Nonce:        %x\n", restored.Nonce)
}
```

ℹ️ Сериализация криптографических метаданных в Base64 для безопасного хранения в S3

## Под капотом

Спецификация HTTP/1.1 (RFC 7230) и ограничения Amazon S3 запрещают передачу произвольных бинарных байтов в заголовках запроса. Заголовки `x-amz-meta-*` обязаны содержать только печатные символы US-ASCII. Кодирование бинарных срезов `EncryptedDEK` и `Nonce` в формат Base64 увеличивает их размер ровно на 33%, что абсолютно незначительно для 32-байтных ключей, но гарантирует отсутствие повреждений символов при прохождении через веб-серверы и прокси.

## Подводные камни

Хранение незашифрованного `Plaintext DEK` в метаданных S3 по ошибке программиста: `x-amz-meta-dek: <plaintext>`. В этом случае все шифрование теряет смысл, так как любой сотрудник с правами на просмотр бакета S3 сможет прочитать ключ и расшифровать файл.

## На собеседовании

**Вопрос на собеседовании (Cloud Data Architect):**
«Каковы ограничения на объем пользовательских метаданных в Amazon S3, и что делать, если нужно сохранить сложную криптографическую структуру?»

**Эталонный ответ:**
Amazon S3 накладывает строгое ограничение: суммарный размер всех имен и значений заголовков `x-amz-meta-*` для одного объекта не может превышать **2 КБ (2048 байт)**.
Если криптографический конверт включает длинные цепочки сертификатов, списки контроля доступа или цифровые подписи размером более 2 КБ:
1. Метаданные сохраняются в отдельный companion-объект рядом с файлом (например, `file.mp4.meta.json`).
2. Либо метаданные упаковываются непосредственно в начало самого бинарного файла в виде фиксированного бинарного префикса (Header Framing).
