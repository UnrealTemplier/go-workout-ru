# AWS KMS Grants: Делегирование прав доступа без изменения Key Policy

## Условие

Используйте KMS grants для делегирования доступа к ключу другим AWS accounts или services.

### Исходная формулировка

**KMS grants**: Используйте KMS grants для делегирования доступа к ключу другим AWS accounts или services.

## Теория

В корпоративных системах модификация корневой политики ключа (Key Policy) требует наивысших административных привилегий и чревата ошибками. Для временного или программного делегирования доступа в AWS KMS используются **Grants**.

### Применение KMS Grants:
1. **Делегирование ролям и сервисам:** Разрешение конкретному IAM Role или сервису (например, Amazon EBS, Amazon RDS или внешнему аккаунту) выполнять операции `Decrypt` или `GenerateDataKey`.
2. **Grant Tokens (Read-After-Write Consistency):**
   - Распространение изменений в KMS по всему региону занимает секунды (eventual consistency).
   - При создании гранта KMS возвращает `GrantToken`.
   - Если клиент передает `GrantToken` в последующем запросе (`GenerateDataKeyRequest.GrantTokens`), операция выполняется немедленно без ожидания конвергенции региона.
3. **Отзыв прав (RevokeGrant):**
   - Грант можно отозвать в любой момент по `GrantId`, мгновенно блокируя доступ.

## Решение по шагам

1. Спроектируйте модель структуры `KMSGrant` с атрибутами `GranteePrincipal`, `Operations` и `GrantToken`.
2. Реализуйте проверку прав при вызове операций шифрования с учетом активных грантов.
3. Добавьте поддержку отзыва грантов по `GrantId`.
4. Протестируйте поведение сервиса до создания гранта, с грантом и после отзыва.

## Код решения

**`kms_grants.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"sync"
	"time"
)

type KMSOperation string

const (
	OpEncrypt         KMSOperation = "Encrypt"
	OpDecrypt         KMSOperation = "Decrypt"
	OpGenerateDataKey KMSOperation = "GenerateDataKey"
)

// GrantRecord хранит информацию о выданных полномочиях
type GrantRecord struct {
	GrantID          string
	GranteePrincipal string
	Operations       []KMSOperation
	CreatedAt        time.Time
}

// ManagedKMS симулирует хранилище ключей с поддержкой Grants
type ManagedKMS struct {
	mu     sync.RWMutex
	grants map[string]map[string]GrantRecord // keyID -> grantID -> GrantRecord
}

func NewManagedKMS() *ManagedKMS {
	return &ManagedKMS{grants: make(map[string]map[string]GrantRecord)}
}

// CreateGrant создает временное разрешение для Principal
func (k *ManagedKMS) CreateGrant(ctx context.Context, keyID, grantee string, ops []KMSOperation) (grantID string, grantToken string, err error) {
	k.mu.Lock()
	defer k.mu.Unlock()

	if _, ok := k.grants[keyID]; !ok {
		k.grants[keyID] = make(map[string]GrantRecord)
	}

	grantID = fmt.Sprintf("grant-%d", time.Now().UnixNano())
	grantToken = fmt.Sprintf("token-%s-%s", keyID, grantID)

	k.grants[keyID][grantID] = GrantRecord{
		GrantID:          grantID,
		GranteePrincipal: grantee,
		Operations:       ops,
		CreatedAt:        time.Now(),
	}

	return grantID, grantToken, nil
}

// RevokeGrant аннулирует выданный грант
func (k *ManagedKMS) RevokeGrant(ctx context.Context, keyID, grantID string) error {
	k.mu.Lock()
	defer k.mu.Unlock()

	keyGrants, ok := k.grants[keyID]
	if !ok {
		return errors.New("key not found")
	}
	if _, exists := keyGrants[grantID]; !exists {
		return errors.New("grant not found")
	}

	delete(keyGrants, grantID)
	return nil
}

// AuthorizeAction проверяет, разрешена ли операция данному Principal
func (k *ManagedKMS) AuthorizeAction(keyID, principal string, op KMSOperation) bool {
	k.mu.RLock()
	defer k.mu.RUnlock()

	keyGrants, ok := k.grants[keyID]
	if !ok {
		return false
	}

	for _, grant := range keyGrants {
		if grant.GranteePrincipal == principal {
			for _, allowedOp := range grant.Operations {
				if allowedOp == op {
					return true
				}
			}
		}
	}
	return false
}

func main() {
	kms := NewManagedKMS()
	keyID := "arn:aws:kms:us-east-1:111122223333:key/payments-vault"
	workerRole := "arn:aws:iam::444455556666:role/CrossAccountWorker"

	ctx := context.Background()

	fmt.Println("1. Проверка доступа до выдачи гранта:")
	allowed := kms.AuthorizeAction(keyID, workerRole, OpGenerateDataKey)
	fmt.Printf("Разрешен доступ: %v (ожидается false)\n", allowed)

	fmt.Println("\n2. Создаем KMS Grant для CrossAccountWorker...")
	grantID, token, err := kms.CreateGrant(ctx, keyID, workerRole, []KMSOperation{OpGenerateDataKey, OpDecrypt})
	if err != nil {
		log.Fatalf("CreateGrant error: %v", err)
	}
	fmt.Printf("Грант создан. ID: %s, Token: %s\n", grantID, token)

	allowed = kms.AuthorizeAction(keyID, workerRole, OpGenerateDataKey)
	fmt.Printf("Разрешен доступ GenerateDataKey: %v (ожидается true)\n", allowed)
	allowedEncrypt := kms.AuthorizeAction(keyID, workerRole, OpEncrypt)
	fmt.Printf("Разрешен доступ Encrypt: %v (ожидается false, так как не был запрошен)\n", allowedEncrypt)

	fmt.Println("\n3. Отзываем грант...")
	if err := kms.RevokeGrant(ctx, keyID, grantID); err != nil {
		log.Fatalf("RevokeGrant error: %v", err)
	}
	allowedAfterRevoke := kms.AuthorizeAction(keyID, workerRole, OpGenerateDataKey)
	fmt.Printf("Разрешен доступ после отзыва: %v (ожидается false)\n", allowedAfterRevoke)
}
```

## Под капотом

KMS Grants работают через распределенный кэш авторизации AWS IAM. Чтобы преодолеть задержку eventual consistency (которая может составлять до 5 секунд в масштабах региона), KMS генерирует криптографический GrantToken — HMAC-подписанный мандат, который клиент передает в заголовке запроса для немедленного доступа.

## Подводные камни

Забывание передать `GrantTokens` в первом запросе сразу после вызова `CreateGrant`. Это может вызвать спорадические ошибки `AccessDenied` из-за того, что региональные ноды KMS еще не успели синхронизировать политику.

## На собеседовании

**Вопрос на собеседовании (Яндекс / Авито Platform Team):**
«Когда следует использовать KMS Grants вместо прямого изменения Key Policy?»

**Эталонный ответ:**
Когда права доступа нужно делегировать динамически с ограниченным жизненным циклом (например, временный воркер обработки данных, или предоставление доступа стороннему AWS аккаунту на время сессии). Модификация Key Policy статична, требует прав администратора и медленно инвалидируется.

## Лучшие практики

- Используйте Grants вместо прямого изменения Key Policy при интеграции микросервисов с динамическими жизненными циклами
- Передавайте `GrantTokens` в SDK-запросах сразу после `CreateGrant`, чтобы избежать задержек распространения IAM/KMS в AWS
- Регулярно проводите аудит активных грантов через AWS Config или скрипты инвентаризации

## Самопроверка

1. Проверьте, что операции без выданного гранта блокируются.
2. Убедитесь, что передаваемый `grantToken` используется при строгой изоляции.
3. Проверьте успешное удаление полномочий при вызове `RevokeGrant`.

## Тест-кейсы

- **GrantLifecycle**
  - Вход: `Create -> Authorize -> Revoke`
  - Ожидается: `Allowed before revoke: true, after: false`
