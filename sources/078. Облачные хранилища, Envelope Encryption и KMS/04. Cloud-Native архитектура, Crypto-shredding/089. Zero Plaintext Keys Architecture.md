# Zero Plaintext Keys Architecture: Полный запрет хранения открытых ключей в коде и БД

## Условие

Никогда не храните plaintext keys в приложении. Используйте KMS для KEK, DEK для data encryption. Это даёт key rotation без re-encryption данных.

### Исходная формулировка

**Envelope Encryption — это standard.**: Никогда не храните plaintext keys в приложении. Используйте KMS для KEK, DEK для data encryption. Это даёт key rotation без re-encryption данных.

## Теория

Золотое правило криптографической безопасности:
**Никогда не хранить открытые ключи (Plaintext Keys) в долговременных хранилищах, исходном коде, файлах конфигурации или переменных окружения.**

### Архитектурная триада безопасности:
1. **KEK (Key Encryption Key):** Изолирован внутри аппаратного модуля HSM (AWS KMS / CloudHSM). Ключ физически неизвлекаем.
2. **DEK (Data Encryption Key):** Генерируется на лету для одного объекта. Сразу после шифрования открытая копия DEK стирается из памяти.
3. **Encrypted DEK:** Хранится в метаданных рядом с зашифрованным файлом. Безопасен даже при полной публичной утечке базы данных или S3 бакета.

## Решение по шагам

1. Спроектируйте статический чекер безопасности `SecurityAuditAnalyzer`.
2. Реализуйте проверку объектов конфигурации на отсутствие открытых 32-байтных ключей.
3. Проверьте обязательное наличие признака `is_encrypted_by_kms`.
4. Протестируйте блокировку деплоя при обнаружении открытого ключа.

## Код решения

**`zero_plaintext_keys.go`**

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

type ConfigEntry struct {
	Name             string
	Value            string
	IsKMSEncrypted   bool
	EncryptionScheme string
}

// AuditConfigSecurity проверяет соответствие правилу Zero Plaintext Keys
func AuditConfigSecurity(entries []ConfigEntry) error {
	for _, entry := range entries {
		// Проверка на хардкод открытых секретов
		if !entry.IsKMSEncrypted {
			if strings.Contains(strings.ToLower(entry.Name), "key") ||
				strings.Contains(strings.ToLower(entry.Name), "secret") ||
				strings.Contains(strings.ToLower(entry.Name), "password") {
				return fmt.Errorf("CRITICAL SECURITY VIOLATION: Plaintext credential found in field '%s'! Must be encrypted via KMS", entry.Name)
			}
		}
	}
	return nil
}

func main() {
	// Небезопасная конфигурация
	badConfig := []ConfigEntry{
		{Name: "DB_HOST", Value: "db.internal", IsKMSEncrypted: false},
		{Name: "MASTER_KEY", Value: "super-secret-raw-key-12345", IsKMSEncrypted: false}, // НАРУШЕНИЕ!
	}

	errBad := AuditConfigSecurity(badConfig)
	fmt.Printf("1. Результат аудита небезопасной конфигурации:\n   %v\n\n", errBad)

	// Безопасная конфигурация (Zero Plaintext Keys)
	secureConfig := []ConfigEntry{
		{Name: "DB_HOST", Value: "db.internal", IsKMSEncrypted: false},
		{
			Name:             "ENCRYPTED_DEK",
			Value:            "AQICAHh...kms-ciphertext-blob...",
			IsKMSEncrypted:   true,
			EncryptionScheme: "AWS-KMS-AES-GCM",
		},
	}

	errSecure := AuditConfigSecurity(secureConfig)
	if errSecure == nil {
		fmt.Println("2. Результат аудита безопасной конфигурации: 100% СООТВЕТСТВИЕ!")
		fmt.Println("Успех: Принцип Zero Plaintext Keys соблюден во всех микросервисах.")
	}
}
```

## Под капотом

Механика реализации 'Zero Plaintext Keys Architecture: Полный запрет хранения открытых ключей в коде и БД':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

«Как масштабировать архитектуру 'Zero Plaintext Keys Architecture: Полный запрет хранения открытых ключей в коде и БД' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

- Никогда не логируйте значения ключей и переменных окружения при падении сервиса
