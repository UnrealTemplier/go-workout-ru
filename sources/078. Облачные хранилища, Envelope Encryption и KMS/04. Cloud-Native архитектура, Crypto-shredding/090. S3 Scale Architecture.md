# S3 Scale Architecture: Преодоление 5 ГБ лимита Single PUT и масштабирование до 5 ТБ

## Условие

Single PUT имеет 5GB limit и не поддерживает resume. Multipart upload даёт parallel upload, resume при failure, и обходит size limits.

### Исходная формулировка

**Multipart Upload для файлов >100MB.**: Single PUT имеет 5GB limit и не поддерживает resume. Multipart upload даёт parallel upload, resume при failure, и обходит size limits.

## Теория

Фундаментальные архитектурные ограничения AWS S3:
1. **Single PUT (`PutObject`):**
   - Максимальный размер объекта: ровно **5 ГБ** (5 368 709 120 байт). Попытка отправить 5 ГБ + 1 байт завершится ошибкой `EntityTooLarge`.
   - Не поддерживает возобновление при обрыве сети.
   - Ограничен одним сетевым TCP-потоком.
2. **Multipart Upload:**
   - Максимальный размер объекта: **5 ТБ** (5 497 558 138 880 байт).
   - Число частей: от 1 до 10 000 частей.
   - Размер одной части: от 5 МБ до 5 ГБ.
   - Полная поддержка параллелизма и Resume при сетевых сбоях.

## Решение по шагам

1. Спроектируйте валидатор размера запроса `S3UploadStrategyRouter`.
2. Реализуйте автоматический выбор стратегии: Single PUT для файлов \(< 100\) МБ, Multipart Upload для файлов от 100 МБ до 5 ТБ.
3. Реализуйте блокировку файлов более 5 ТБ.
4. Протестируйте маршрутизацию для различных объемов файлов.

## Код решения

**`s3_size_router.go`**

```go
package main

import (
	"errors"
	"fmt"
)

const (
	MaxSinglePutLimit = int64(5) * 1024 * 1024 * 1024    // 5 GB
	MaxMultipartLimit = int64(5) * 1024 * 1024 * 1024 * 1024 // 5 TB
	AutoMultipartThreshold = int64(100) * 1024 * 1024   // 100 MB
)

type UploadPlan struct {
	Strategy       string // "SinglePut" | "MultipartUpload"
	RecommendedPartSize int64
	EstimatedParts int64
}

func DetermineUploadStrategy(fileSize int64) (*UploadPlan, error) {
	if fileSize <= 0 {
		return nil, errors.New("file size must be greater than 0")
	}
	if fileSize > MaxMultipartLimit {
		return nil, fmt.Errorf("EntityTooLarge: file size %d exceeds AWS S3 absolute limit of 5 TB", fileSize)
	}

	if fileSize < AutoMultipartThreshold {
		return &UploadPlan{
			Strategy:       "SinglePut",
			EstimatedParts: 1,
		}, nil
	}

	// Выбираем размер части так, чтобы не превысить 10 000 частей
	partSize := int64(32 * 1024 * 1024) // 32 MB default
	if fileSize/partSize >= 10000 {
		partSize = (fileSize / 10000) + 1024*1024
	}

	parts := (fileSize + partSize - 1) / partSize
	return &UploadPlan{
		Strategy:            "MultipartUpload",
		RecommendedPartSize: partSize,
		EstimatedParts:      parts,
	}, nil
}

func main() {
	testSizes := []struct {
		desc string
		size int64
	}{
		{"Аватарка пользователя (2 МБ)", 2 * 1024 * 1024},
		{"Видеоклип (250 МБ)", 250 * 1024 * 1024},
		{"Резервная копия БД (6 ГБ — превышает Single PUT!)", 6 * 1024 * 1024 * 1024},
		{"Огромный архив хранилища (3 ТБ)", 3 * 1024 * 1024 * 1024 * 1024},
		{"Недопустимый объем (6 ТБ — превышает лимит S3!)", 6 * 1024 * 1024 * 1024 * 1024},
	}

	fmt.Println("=== Маршрутизатор стратегий загрузки в S3 ===")
	for _, tc := range testSizes {
		plan, err := DetermineUploadStrategy(tc.size)
		if err != nil {
			fmt.Printf("\nФайл: %s\n  -> Ошибка: %v\n", tc.desc, err)
			continue
		}
		fmt.Printf("\nФайл: %s\n  -> Стратегия: %s | Размер части: %d MB | Число частей: %d\n",
			tc.desc, plan.Strategy, plan.RecommendedPartSize/(1024*1024), plan.EstimatedParts)
	}
}
```

## Под капотом

Механика реализации 'S3 Scale Architecture: Преодоление 5 ГБ лимита Single PUT и масштабирование до 5 ТБ':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

**Вопрос на собеседовании (Senior / Staff Go Architect):**
«Как масштабировать архитектуру 'S3 Scale Architecture: Преодоление 5 ГБ лимита Single PUT и масштабирование до 5 ТБ' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Автоматически переключайтесь с Single PUT на Multipart при достижении размера 100 МБ
- Никогда не пытайтесь загружать файлы более 5 ГБ одним `PutObject`
- Проверяйте размер файла перед началом загрузки
