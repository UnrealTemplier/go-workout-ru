# Storage Benchmarking: Сравнительный анализ Single PUT vs Parallel Multipart Upload

## Условие

Сравните производительность:
    * Single PUT vs multipart upload
    * Sequential vs parallel parts
    * Разные part sizes
    * Разные concurrency levels

### Исходная формулировка

**Multipart upload benchmarking**: Сравните производительность:
* Single PUT vs multipart upload
* Sequential vs parallel parts
* Разные part sizes
* Разные concurrency levels

## Теория

Выбор между одиночным `PutObject` и параллельным `Multipart Upload`:
1. **Single PUT:**
   - Преимущества: Минимальный оверхед на координацию (один HTTP-запрос).
   - Недостатки: Однопоточный I/O, не утилизирует многоядерные процессоры и агрегированные каналы, при обрыве теряется весь файл.
   - Рекомендован: Для файлов \(< 16\) МБ.
2. **Parallel Multipart Upload:**
   - Преимущества: Утилизация 8–16 потоков, ускорение в 3–8 раз, отказоустойчивость чанков.
   - Недостатки: Накладные расходы на вызовы `Create` и `Complete`.
   - Рекомендован: Для файлов \(\ge 16\) МБ.

## Решение по шагам

1. Спроектируйте бенчмарк-движок `StorageUploadBenchmark`.
2. Реализуйте сценарий одиночной загрузки `SinglePUT`.
3. Реализуйте сценарий параллельной загрузки 4 потоками `MultipartParallel`.
4. Выведите сравнительный отчет времени выполнения и ускорения.

## Код решения

**`s3_benchmark_strategies.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SimulateSinglePut симулирует последовательную однопоточную загрузку
func SimulateSinglePut(sizeMB int) time.Duration {
	start := time.Now()
	// Однопоточная скорость условно 20 МБ/с
	time.Sleep(time.Duration(sizeMB*5) * time.Millisecond)
	return time.Since(start)
}

// SimulateParallelMultipart симулирует параллельную загрузку 4 потоками
func SimulateParallelMultipart(sizeMB int, parts int, concurrency int) time.Duration {
	start := time.Now()
	partSizeMB := sizeMB / parts

	sem := make(chan struct{}, concurrency)
	var wg sync.WaitGroup

	for i := 0; i < parts; i++ {
		wg.Add(1)
		sem <- struct{}{}
		go func() {
			defer wg.Done()
			defer func() { <-sem }()
			// Параллельная загрузка чанка
			time.Sleep(time.Duration(partSizeMB*5) * time.Millisecond)
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	fileSizeMB := 100 // 100 МБ файл

	fmt.Printf("=== Бенчмаркинг стратегий загрузки в S3 (Размер: %d МБ) ===\n\n", fileSizeMB)

	// 1. Single PUT
	dSingle := SimulateSinglePut(fileSizeMB)
	fmt.Printf("1. Single PUT (1 поток):             %v\n", dSingle)

	// 2. Sequential Multipart (без конкурентности)
	dSeq := SimulateParallelMultipart(fileSizeMB, 5, 1)
	fmt.Printf("2. Sequential Multipart (5 частей):   %v\n", dSeq)

	// 3. Parallel Multipart (4 потока)
	dPar4 := SimulateParallelMultipart(fileSizeMB, 5, 4)
	fmt.Printf("3. Parallel Multipart (4 потока):     %v\n", dPar4)

	speedup := float64(dSingle.Milliseconds()) / float64(dPar4.Milliseconds())
	fmt.Printf("\nУскорение параллельного Multipart: в %.1fx раз быстрее Single PUT!\n", speedup)
}
```

## Под капотом

Механика реализации 'Storage Benchmarking: Сравнительный анализ Single PUT vs Parallel Multipart Upload':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## Лучшие практики

- Используйте `Single PUT` для аватарок, иконок и небольших документов (<16 МБ)
- Переключайтесь на `Multipart Upload` с параллелизмом 4–8 горутин для файлов \(\ge 16\) МБ
- Тюнингуйте параметры на основе реальных сетевых замеров в целевом облачном регионе
