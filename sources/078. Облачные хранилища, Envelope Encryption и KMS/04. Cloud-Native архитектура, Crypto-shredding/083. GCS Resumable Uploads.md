# GCS Resumable Uploads: Возобновляемые сессии по уникальному Session URI

## Условие

Используйте resumable upload для больших файлов в GCS. Это позволяет resume при network failure.

### Исходная формулировка

**GCS resumable upload**: Используйте resumable upload для больших файлов в GCS. Это позволяет resume при network failure.

## Теория

В Google Cloud Storage официальным протоколом для загрузки больших файлов является **Resumable Upload**:
1. Клиент делает POST запрос на эндпоинт загрузки с заголовком `X-Upload-Content-Type` и получает `Session URI`.
2. Клиент отправляет чанки через PUT запросы на полученный `Session URI` с заголовком `Content-Range: bytes 0-1048575/total`.
3. При срыве соединения клиент отправляет пустой PUT запрос `Content-Range: bytes */total`.
4. Сервер GCS возвращает заголовок `Range: bytes=0-524287`, сообщая точный смещение последнего успешно принятого байта.
5. Клиент продолжает загрузку со следующего байта без потери прогресса!

## Решение по шагам

1. Спроектируйте структуру сессии `GCSResumableSession` с отслеживанием `ReceivedBytes`.
2. Реализуйте метод проверки статуса `QueryProgress`.
3. Смоделируйте сбой передачи и запрос смещения для докачки.
4. Протестируйте успешное завершение после восстановления.

## Код решения

**`gcs_resumable_upload.go`**

```go
package main

import (
	"fmt"
	"time"
)

type GCSResumableServer struct {
	sessionURI    string
	totalSize     int64
	receivedBytes int64
	isCompleted   bool
}

func NewGCSResumableServer(uri string, totalSize int64) *GCSResumableServer {
	return &GCSResumableServer{
		sessionURI: uri,
		totalSize:  totalSize,
	}
}

// UploadChunk симулирует отправку PUT с диапазоном байт
func (s *GCSResumableServer) UploadChunk(startByte, endByte int64, data []byte) error {
	if startByte != s.receivedBytes {
		return fmt.Errorf("400 Bad Range: Server expected start byte %d, got %d",
			s.receivedBytes, startByte)
	}

	s.receivedBytes = endByte + 1
	if s.receivedBytes == s.totalSize {
		s.isCompleted = true
	}
	return nil
}

// QueryOffset симулирует проверку статуса (отправка PUT с Content-Range: bytes */total)
func (s *GCSResumableServer) QueryOffset() int64 {
	return s.receivedBytes
}

func main() {
	var totalFileSize int64 = 10 * 1024 * 1024 // 10 MB
	server := NewGCSResumableServer("https://storage.googleapis.com/upload/resumable-session-12345", totalFileSize)

	fmt.Printf("1. Инициализирована сессия GCS Resumable Upload. URI: %s\n", server.sessionURI)

	// Передаем первый чанк 4 МБ (0..4194303)
	_ = server.UploadChunk(0, 4*1024*1024-1, make([]byte, 4*1024*1024))
	fmt.Printf("2. Загружен первый чанк. Сервер принял: %d байт\n", server.QueryOffset())

	// Имитация аварии сети во время загрузки второго чанка
	fmt.Println("\n[NETWORK INTERRUPTION] Сетевой сокет закрыт во время передачи...")
	time.Sleep(20 * time.Millisecond)

	// Клиент восстанавливает сессию: опрашивает сервер о текущем смещении
	resumedOffset := server.QueryOffset()
	fmt.Printf("3. Запрос статуса (Recovery): Сервер подтвердил наличие %d байт.\n", resumedOffset)

	// Клиент передает оставшийся хвост от resumedOffset до конца файла
	remainingBytes := totalFileSize - resumedOffset
	err := server.UploadChunk(resumedOffset, totalFileSize-1, make([]byte, remainingBytes))
	if err != nil {
		panic(err)
	}

	fmt.Printf("4. Финальный чанк успешно отправлен!\n")
	if server.isCompleted {
		fmt.Println("Успех: GCS Resumable Upload завершен со 100% сохранением целостности!")
	}
}
```

## Под капотом

Механика реализации 'GCS Resumable Uploads: Возобновляемые сессии по уникальному Session URI':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## Лучшие практики

- Используйте Resumable Uploads в GCS для любых файлов размером более 10 МБ

- Используйте размер чанка, кратный 256 КБ (требование Google Cloud Storage)
