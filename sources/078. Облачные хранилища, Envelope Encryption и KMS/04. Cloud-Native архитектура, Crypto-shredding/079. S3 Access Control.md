# S3 Access Control: Управление ACL при Multipart Upload (private vs bucket-owner-full-control)

## Условие

Устанавливайте ACL для multipart upload (например, `private`, `public-read`).

### Исходная формулировка

**Multipart upload + ACL**: Устанавливайте ACL для multipart upload (например, `private`, `public-read`).

## Теория

При междоменной загрузке файлов в чужой бакет (Cross-Account Upload) часто возникает критическая проблема:
- Если Account A загружает объект в бакет Account B без указания ACL, владельцем объекта остается Account A.
- Владелец бакета (Account B) **не имеет доступа к скачиванию этого объекта**, даже если бакет принадлежит ему!

### Решение: Canned ACL `bucket-owner-full-control`
При вызове `CreateMultipartUpload`:
`ACL: types.ObjectCannedACLBucketOwnerFullControl`
Это передает полные права собственности на загружаемый файл владельцу целевого бакета.

## Решение по шагам

1. Спроектируйте валидатор стандартных S3 Canned ACL (`private`, `public-read`, `bucket-owner-full-control`).
2. Реализуйте привязку ACL на этапе инициализации multipart upload.
3. Смоделируйте сценарий Cross-Account доступа с проверкой прав.
4. Протестируйте блокировку несанкционированного доступа.

## Код решения

**`s3_acl_management.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type S3CannedACL string

const (
	ACLPrivate                S3CannedACL = "private"
	ACLPublicRead             S3CannedACL = "public-read"
	ACLBucketOwnerFullControl S3CannedACL = "bucket-owner-full-control"
)

type ManagedS3Object struct {
	BucketOwnerAccount string
	UploaderAccount    string
	ACL                S3CannedACL
}

func CanBucketOwnerRead(obj ManagedS3Object) (bool, string) {
	if obj.UploaderAccount == obj.BucketOwnerAccount {
		return true, "Владелец бакета и загрузчик совпадают (доступ разрешен)"
	}

	// Межаккаунтная загрузка!
	if obj.ACL == ACLBucketOwnerFullControl {
		return true, "Разрешено благодаря ACL 'bucket-owner-full-control'"
	}

	return false, "ЗАБЛОКИРОВАНО: Объект принадлежит загрузчику, владелец бакета не имеет прав!"
}

func main() {
	bucketOwner := "111111111111"
	crossAccountUploader := "222222222222"

	// Сценарий 1: Загрузка с дефолтным private ACL (типичная ошибка!)
	objDefault := ManagedS3Object{
		BucketOwnerAccount: bucketOwner,
		UploaderAccount:    crossAccountUploader,
		ACL:                ACLPrivate,
	}
	canRead1, reason1 := CanBucketOwnerRead(objDefault)
	fmt.Printf("Тест 1 (Default Private ACL): %v -> %s\n", canRead1, reason1)

	// Сценарий 2: Загрузка с правильным BucketOwnerFullControl
	objCorrect := ManagedS3Object{
		BucketOwnerAccount: bucketOwner,
		UploaderAccount:    crossAccountUploader,
		ACL:                ACLBucketOwnerFullControl,
	}
	canRead2, reason2 := CanBucketOwnerRead(objCorrect)
	fmt.Printf("Тест 2 (BucketOwnerFullControl): %v -> %s\n", canRead2, reason2)
}
```

## Под капотом

Механика реализации 'S3 Access Control: Управление ACL при Multipart Upload (private vs bucket-owner-full-control)':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

**Вопрос на собеседовании (Senior / Staff Go Architect):**
«Как масштабировать архитектуру 'S3 Access Control: Управление ACL при Multipart Upload (private vs bucket-owner-full-control)' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Всегда передавайте `ACL: bucket-owner-full-control` при междоменной передаче файлов в S3
- Включайте `S3 Object Ownership: Bucket owner enforced` на бакете для автоматического отключения ACL и передачи всех прав владельцу бакета
- Никогда не используйте `public-read` для конфиденциальных бэкапов и персональных данных
