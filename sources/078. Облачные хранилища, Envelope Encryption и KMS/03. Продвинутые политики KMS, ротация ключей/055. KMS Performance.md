## Теория

Сравнение производительности криптографических операций демонстрирует колоссальную разницу между сетью и CPU:
1. **Сетевой вызов `GenerateDataKey` к облачному KMS:**
   - Latency: **30–150 мс** (RTT через интернет или AWS Direct Connect).
   - Квота пропускной способности: стандартно **10 000 запросов/сек** на весь AWS регион.
   - Ошибка при превышении: `400 ThrottlingException`.
2. **Локальное симметричное шифрование (AES-GCM-256):**
   - Latency: **50–200 наносекунд** на блок при поддержке инструкций процессора AES-NI.
   - Пропускная способность: **несколько гигабайт в секунду** на одно ядро CPU.

Именно поэтому Envelope Encryption является единственно возможной архитектурой для HighLoad.

## Код решения

**`kms_benchmark_rate.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"sync"
	"time"
)

// SimulatedKMSClient эмулирует задержку сети и ограничение RPS
type SimulatedKMSClient struct {
	networkDelay time.Duration
	tokens       chan struct{}
}

func NewSimulatedKMSClient(delay time.Duration, rpsLimit int) *SimulatedKMSClient {
	c := &SimulatedKMSClient{
		networkDelay: delay,
		tokens:       make(chan struct{}, rpsLimit),
	}
	// Заполняем токен-бакет
	for i := 0; i < rpsLimit; i++ {
		c.tokens <- struct{}{}
	}
	// Регулярное восполнение токенов
	go func() {
		ticker := time.NewTicker(time.Second / time.Duration(rpsLimit))
		for range ticker.C {
			select {
			case c.tokens <- struct{}{}:
			default:
			}
		}
	}()
	return c
}

func (c *SimulatedKMSClient) GenerateDataKey() ([]byte, error) {
	// Ожидаем доступный токен (Rate Limiting)
	<-c.tokens
	// Сетевая задержка
	time.Sleep(c.networkDelay)

	dek := make([]byte, 32)
	io.ReadFull(rand.Reader, dek)
	return dek, nil
}

func main() {
	kms := NewSimulatedKMSClient(5*time.Millisecond, 200) // 5мс сеть, 200 RPS лимит
	localKey := make([]byte, 32)
	io.ReadFull(rand.Reader, localKey)
	block, _ := aes.NewCipher(localKey)
	gcm, _ := cipher.NewGCM(block)
	nonce := make([]byte, gcm.NonceSize())
	io.ReadFull(rand.Reader, nonce)
	samplePayload := []byte("Benchmark payload testing encryption speed")

	// 1. Замер локального AES-GCM (10 000 операций)
	localIterations := 10000
	startLocal := time.Now()
	for i := 0; i < localIterations; i++ {
		_ = gcm.Seal(nil, nonce, samplePayload, nil)
	}
	localDuration := time.Since(startLocal)
	avgLocalNs := localDuration.Nanoseconds() / int64(localIterations)

	// 2. Замер вызовов KMS (10 операций)
	kmsIterations := 10
	startKMS := time.Now()
	var wg sync.WaitGroup
	for i := 0; i < kmsIterations; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			_, _ = kms.GenerateDataKey()
		}()
	}
	wg.Wait()
	kmsDuration := time.Since(startKMS)
	avgKMSMs := float64(kmsDuration.Milliseconds()) / float64(kmsIterations)

	fmt.Println("=== Сравнительный анализ производительности ===")
	fmt.Printf("Локальный AES-GCM:   %d операций за %v (в среднем: %d ns на операцию)\n",
		localIterations, localDuration, avgLocalNs)
	fmt.Printf("Сетевой вызов KMS:   %d операций за %v (в среднем: %.2f ms на вызов)\n",
		kmsIterations, kmsDuration, avgKMSMs)

	speedup := (avgKMSMs * 1_000_000) / float64(avgLocalNs)
	fmt.Printf("\nВывод: Локальное шифрование быстрее вызова KMS в ~%.0f раз!\n", speedup)
}
```

## Под капотом

Механика реализации 'KMS Performance: Замеры задержки GenerateDataKey vs локальный Encrypt и Rate Limiting':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

«Как масштабировать архитектуру 'KMS Performance: Замеры задержки GenerateDataKey vs локальный Encrypt и Rate Limiting' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Всегда настраивайте клиентский Rate Limiting для запросов к KMS, чтобы гарантированно не превышать региональную квоту AWS
- Никогда не вызывайте KMS в горячем цикле обработки пакетов
- Используйте `x/time/rate.Limiter` для гладкого троттлинга запросов
