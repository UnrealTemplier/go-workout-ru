# Resumable Upload: Сохранение UploadId и докачка недостающих частей при рестарте

## Условие

При failure сохраняйте upload ID и completed parts. Resume upload через `UploadPartCopy` или повторный `UploadPart` для failed parts.

### Исходная формулировка

**Resume failed upload**: При failure сохраняйте upload ID и completed parts. Resume upload через `UploadPartCopy` или повторный `UploadPart` для failed parts.

## Теория

При загрузке файлов размером в сотни гигабайт рестарт пода Kubernetes или сбой сети не должен приводить к перезагрузке файла с нуля.

### Паттерн Resumable S3 Upload:
1. Перед стартом вызывается `ListParts(UploadId)`:
   - S3 возвращает список уже успешно загруженных частей `{PartNumber, ETag}`.
2. Локальный клиент сравнивает требуемый список частей с уже загруженными.
3. Загружаются **только недостающие части** (missing parts).
4. Вызывается `CompleteMultipartUpload` с объединенным списком всех частей.
5. Загрузка возобновляется мгновенно без повторной передачи ранее закачанных гигабайт!

## Решение по шагам

1. Спроектируйте трекер сессий загрузки `ResumableUploadTracker`.
2. Смоделируйте прерывание процесса после загрузки части 1 и 2.
3. При повторном старте вызовите `ListParts` и отфильтруйте оставшиеся части.
4. Докачайте часть 3 и завершите сборку объекта.

## Код решения

**`resumable_upload.go`**

```go
package main

import (
	"crypto/md5"
	"encoding/hex"
	"fmt"
	"sort"
)

type UploadedPart struct {
	PartNum int
	ETag    string
}

type ResumableSession struct {
	UploadID       string
	CompletedParts map[int]string
}

func NewResumableSession(uploadID string) *ResumableSession {
	return &ResumableSession{
		UploadID:       uploadID,
		CompletedParts: make(map[int]string),
	}
}

// ResumeUpload докачивает только отсутствующие части
func ResumeUpload(session *ResumableSession, chunks [][]byte) ([]UploadedPart, error) {
	fmt.Printf("[Resume] Возобновление сессии %s...\n", session.UploadID)
	fmt.Printf("[Resume] Уже загружено частей в S3: %d из %d\n", len(session.CompletedParts), len(chunks))

	for i, chunk := range chunks {
		partNum := i + 1
		if etag, exists := session.CompletedParts[partNum]; exists {
			fmt.Printf("  -> Часть #%d уже есть в S3 (ETag: %s). Пропускаем передачу!\n", partNum, etag)
			continue
		}

		// Загружаем недостающую часть
		fmt.Printf("  -> Загрузка недостающей части #%d (%d байт)...\n", partNum, len(chunk))
		hash := md5.Sum(chunk)
		etag := fmt.Sprintf("\"%s\"", hex.EncodeToString(hash[:]))
		session.CompletedParts[partNum] = etag
	}

	// Формируем финальный отсортированный список
	var result []UploadedPart
	for pNum, etag := range session.CompletedParts {
		result = append(result, UploadedPart{PartNum: pNum, ETag: etag})
	}

	sort.Slice(result, func(i, j int) bool {
		return result[i].PartNum < result[j].PartNum
	})

	return result, nil
}

func main() {
	chunks := [][]byte{
		[]byte("Part 1: 50MB Database Segment A"),
		[]byte("Part 2: 50MB Database Segment B"),
		[]byte("Part 3: 50MB Database Segment C"),
	}

	session := NewResumableSession("upload-crash-resilient-4455")

	// Симулируем, что части 1 и 2 уже были загружены до падения процесса
	session.CompletedParts[1] = "\"etag-part-1-md5\""
	session.CompletedParts[2] = "\"etag-part-2-md5\""

	// Запуск процесса возобновления
	completed, err := ResumeUpload(session, chunks)
	if err != nil {
		panic(err)
	}

	fmt.Println("\nФинальный манифест для CompleteMultipartUpload:")
	for _, p := range completed {
		fmt.Printf("  Part %d: %s\n", p.PartNum, p.ETag)
	}
	fmt.Println("Успех: Сэкономлено 100 МБ сетевого трафика благодаря механизму Resume!")
}
```

## Под капотом

Механика реализации 'Resumable Upload: Сохранение UploadId и докачка недостающих частей при рестарте':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Сохраняйте `UploadID` в Redis или базе данных для возможности возобновления после рестарта воркера
- Вызывайте `s3Client.ListParts` для получения актуального состояния частей из S3
- Устанавливайте TTL на незавершенные сессии, чтобы очищать брошенные загрузки через `AbortMultipartUpload`
