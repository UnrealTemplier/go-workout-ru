# Оптимизация Part Size: Баланс между API overhead и сетевыми потерями при retry

## Условие

Оптимальный part size: 16-64MB. Меньше — overhead от API calls. Больше — wasted bandwidth при retry.

### Исходная формулировка

**Part size optimization**: Оптимальный part size: 16-64MB. Меньше — overhead от API calls. Больше — wasted bandwidth при retry.

## Теория

Выбор размера части в Multipart Upload является компромиссом между двумя крайностями:
1. **Слишком маленький Part Size (5 МБ):**
   - На файл 100 ГБ потребуется 20 000 частей (превышение лимита 10 000 частей S3!).
   - Колоссальный overhead на HTTP/TLS хендшейки и RPS к S3.
2. **Слишком большой Part Size (500 МБ):**
   - При сбое сети на 499-м мегабайте теряется весь полугигабайтный трафик, и часть передается заново.
   - Огромный расход оперативной памяти на буферы.
3. **Золотая середина (16–64 МБ):**
   - Для файлов до 50 ГБ: 16–32 МБ.
   - Для файлов от 50 ГБ до 500 ГБ: 64 МБ.
   - Для терабайтных файлов: 128 МБ.

## Решение по шагам

1. Спроектируйте калькулятор `AnalyzePartSizeStrategy(fileSizeBytes)`.
2. Реализуйте проверку лимита 10 000 частей AWS.
3. Рассчитайте число HTTP-запросов и оценку потерь при сетевом сбое (Wasted Bandwidth).
4. Протестируйте расчет для файлов размером 500 МБ, 50 ГБ и 1 ТБ.

## Код решения

**`part_size_optimizer.go`**

```go
package main

import (
	"fmt"
)

type StrategyResult struct {
	TotalSizeBytes int64
	PartSizeBytes  int64
	TotalParts     int64
	WasteOnFailure string
	IsAWSCompliant bool
}

func OptimizePartSize(fileSize int64) StrategyResult {
	const (
		MinPartSize = 5 * 1024 * 1024       // 5 MB
		MaxParts    = 10000                 // AWS Limit
		DefaultPart = 32 * 1024 * 1024      // 32 MB recommended
	)

	partSize := int64(DefaultPart)

	// Для терабайтных файлов увеличиваем размер части
	if fileSize > 300*1024*1024*1024 { // > 300 GB
		partSize = 64 * 1024 * 1024
	}
	if fileSize > 600*1024*1024*1024 { // > 600 GB
		partSize = 128 * 1024 * 1024
	}

	// Гарантия непревышения лимита 10 000 частей
	if fileSize/partSize >= MaxParts {
		partSize = (fileSize / MaxParts) + (1024 * 1024) // +1MB buffer
	}

	totalParts := (fileSize + partSize - 1) / partSize

	return StrategyResult{
		TotalSizeBytes: fileSize,
		PartSizeBytes:  partSize,
		TotalParts:     totalParts,
		WasteOnFailure: fmt.Sprintf("макс. %d MB трафика при обрыве", partSize/(1024*1024)),
		IsAWSCompliant: totalParts <= MaxParts && partSize >= MinPartSize,
	}
}

func main() {
	scenarios := []struct {
		name string
		size int64
	}{
		{"Архив логов 500 МБ", 500 * 1024 * 1024},
		{"Дамп базы данных 50 ГБ", 50 * 1024 * 1024 * 1024},
		{"Резервная копия аналитики 1 ТБ", 1024 * 1024 * 1024 * 1024},
		{"Сверхбольшой датасет 4.5 ТБ", 4500 * 1024 * 1024 * 1024},
	}

	fmt.Println("=== Анализ оптимальной стратегии Part Size в S3 ===")
	for _, sc := range scenarios {
		res := OptimizePartSize(sc.size)
		fmt.Printf("\nФайл: %s (%d GB)\n", sc.name, sc.size/(1024*1024*1024))
		fmt.Printf("  Рекомендованный PartSize: %d MB\n", res.PartSizeBytes/(1024*1024))
		fmt.Printf("  Всего частей:             %d (Лимит AWS: 10 000)\n", res.TotalParts)
		fmt.Printf("  Цена сбоя сети:           %s\n", res.WasteOnFailure)
		fmt.Printf("  Соответствует лимитам S3: %v\n", res.IsAWSCompliant)
	}
}
```

## Под капотом

Механика реализации 'Оптимизация Part Size: Баланс между API overhead и сетевыми потерями при retry':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

«Как масштабировать архитектуру 'Оптимизация Part Size: Баланс между API overhead и сетевыми потерями при retry' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Используйте 32–64 МБ как размер по умолчанию для современных серверов и сетей
- Для файлов более 500 ГБ обязательно динамически увеличивайте `PartSize`, чтобы не упереться в лимит 10 000 частей
- Учитывайте доступную оперативную память: \(N \text{ воркеров} \times \text{PartSize}\) должны помещаться в контейнер
