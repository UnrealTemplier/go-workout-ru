# Part-Level Encryption: Независимый DEK для каждого чанка в распределенной архитектуре

## Условие

Шифруйте каждую part через envelope encryption перед upload. Сохраняйте encrypted DEK per part.

### Исходная формулировка

**Multipart upload + envelope encryption**: Шифруйте каждую part через envelope encryption перед upload. Сохраняйте encrypted DEK per part.

## Теория

В распределенных системах с параллельной распределенной загрузкой (например, когда 10 независимых воркеров в Kubernetes загружают параллельные части одного большого файла) единый Master DEK может стать точкой синхронизации.

### Архитектура Part-Level Envelope Encryption:
1. Каждый воркер генерирует свой собственный уникальный `PartDEK`.
2. Воркер шифрует только свою часть.
3. Воркер упаковывает `[EncryptedPartDEK (64B)][Nonce (12B)][Ciphertext]` прямо в тело части `UploadPart`.
4. При скачивании любой воркер может параллельно прочитать и расшифровать произвольный фрагмент (Range Request) без чтения всего файла!

## Решение по шагам

1. Спроектируйте упаковщик части `PackEncryptedPart(kek, partNum, data)`.
2. Зашифруйте часть уникальным DEK и поместите зашифрованный DEK в заголовок блока части.
3. Реализуйте распаковку и дешифрование части `UnpackEncryptedPart(kek, rawChunk)`.
4. Протестируйте независимое произвольное чтение произвольной части (Random Access).

## Код решения

**`part_level_envelope.go`**

```go
package main

import (
	"bytes"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"encoding/binary"
	"errors"
	"fmt"
	"io"
	"log"
)

// PackPartWithIndependentDEK шифрует часть собственным DEK и упаковывает в единый чанк
func PackPartWithIndependentDEK(kek []byte, partNum int32, plaintext []byte) ([]byte, error) {
	// 1. Уникальный DEK для данной части
	partDEK := make([]byte, 32)
	io.ReadFull(rand.Reader, partDEK)

	// 2. Шифруем тело части
	pBlock, err := aes.NewCipher(partDEK)
	if err != nil {
		return nil, err
	}
	pGCM, err := cipher.NewGCM(pBlock)
	if err != nil {
		return nil, err
	}
	pNonce := make([]byte, pGCM.NonceSize())
	io.ReadFull(rand.Reader, pNonce)
	partCiphertext := pGCM.Seal(nil, pNonce, plaintext, []byte(fmt.Sprintf("part-%d", partNum)))

	// 3. Шифруем partDEK с помощью мастер-ключа KEK
	kBlock, err := aes.NewCipher(kek)
	if err != nil {
		return nil, err
	}
	kGCM, err := cipher.NewGCM(kBlock)
	if err != nil {
		return nil, err
	}
	kNonce := make([]byte, kGCM.NonceSize())
	io.ReadFull(rand.Reader, kNonce)
	encPartDEK := kGCM.Seal(kNonce, kNonce, partDEK, nil)

	// Сборка бинарного пакета части:
	// [PartNum (uint32)][EncDEK Len (uint16)][EncDEK][Nonce (12B)][Ciphertext]
	buf := new(bytes.Buffer)
	binary.Write(buf, binary.BigEndian, partNum)
	binary.Write(buf, binary.BigEndian, uint16(len(encPartDEK)))
	buf.Write(encPartDEK)
	buf.Write(pNonce)
	buf.Write(partCiphertext)

	return buf.Bytes(), nil
}

// UnpackPartWithIndependentDEK расшифровывает произвольный чанк
func UnpackPartWithIndependentDEK(kek []byte, packedPart []byte) (int32, []byte, error) {
	if len(packedPart) < 6 {
		return 0, nil, errors.New("chunk too short")
	}

	buf := bytes.NewReader(packedPart)
	var partNum int32
	var encDEKLen uint16

	binary.Read(buf, binary.BigEndian, &partNum)
	binary.Read(buf, binary.BigEndian, &encDEKLen)

	encPartDEK := make([]byte, encDEKLen)
	io.ReadFull(buf, encPartDEK)

	// Расшифровываем partDEK через KEK
	kBlock, err := aes.NewCipher(kek)
	if err != nil {
		return 0, nil, err
	}
	kGCM, err := cipher.NewGCM(kBlock)
	if err != nil {
		return 0, nil, err
	}
	kNonceSize := kGCM.NonceSize()
	partDEK, err := kGCM.Open(nil, encPartDEK[:kNonceSize], encPartDEK[kNonceSize:], nil)
	if err != nil {
		return 0, nil, fmt.Errorf("decrypt part dek failed: %w", err)
	}

	pBlock, _ := aes.NewCipher(partDEK)
	pGCM, _ := cipher.NewGCM(pBlock)
	pNonce := make([]byte, pGCM.NonceSize())
	io.ReadFull(buf, pNonce)

	partCipher, _ := io.ReadAll(buf)
	plaintext, err := pGCM.Open(nil, pNonce, partCipher, []byte(fmt.Sprintf("part-%d", partNum)))
	if err != nil {
		return 0, nil, fmt.Errorf("decrypt part ciphertext failed: %w", err)
	}

	return partNum, plaintext, nil
}

func main() {
	kek := []byte("master-kek-32bytes-secret-key-9!")

	// Создаем 3 независимых чанка
	chunk1, _ := PackPartWithIndependentDEK(kek, 1, []byte("Data block 1 from worker A"))
	chunk2, _ := PackPartWithIndependentDEK(kek, 2, []byte("Data block 2 from worker B"))
	chunk3, _ := PackPartWithIndependentDEK(kek, 3, []byte("Data block 3 from worker C"))

	fmt.Printf("Создано 3 независимых зашифрованных чанка:\n")
	fmt.Printf("  Chunk 1: %d байт\n  Chunk 2: %d байт\n  Chunk 3: %d байт\n",
		len(chunk1), len(chunk2), len(chunk3))

	// Читаем произвольный чанк №2 (Random Access) напрямую, не читая чанк №1!
	num, data, err := UnpackPartWithIndependentDEK(kek, chunk2)
	if err != nil {
		log.Fatalf("Unpack error: %v", err)
	}

	fmt.Printf("\nПроизвольное чтение Чанка #%d:\n  Payload: '%s'\n", num, string(data))
	if string(data) == "Data block 2 from worker B" {
		fmt.Println("Успех: Part-Level Envelope Encryption обеспечивает параллельный Random Access!")
	}
}
```

## Под капотом

Механика реализации 'Part-Level Encryption: Независимый DEK для каждого чанка в распределенной архитектуре':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

**Вопрос на собеседовании (Senior / Staff Go Architect):**
«Как масштабировать архитектуру 'Part-Level Encryption: Независимый DEK для каждого чанка в распределенной архитектуре' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Используйте Part-Level шифрование, если видео или база данных требуют произвольного чтения частей (Range Requests)
- Привязывайте номер части и имя файла в AAD каждого чанка
- Для терабайтных архивов комбинируйте Part-Level шифрование с параллельным пулом воркеров
