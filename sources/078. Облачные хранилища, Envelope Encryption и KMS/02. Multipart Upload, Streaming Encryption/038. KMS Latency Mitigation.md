# KMS Latency Mitigation: Асинхронный Prefetching и пакетная генерация DEK

## Условие

KMS вызовы имеют latency 50-200ms. Кэшируйте DEKs, используйте batch operations, минимизируйте KMS calls.

### Исходная формулировка

**KMS latency optimization**: KMS вызовы имеют latency 50-200ms. Кэшируйте DEKs, используйте batch operations, минимизируйте KMS calls.

## Теория

Сетевой вызов к облачному KMS (AWS KMS, GCP Cloud KMS, Azure Key Vault) занимает от 50 до 200 миллисекунд из-за необходимости TLS-хендшейка, аутентификации Signature V4 и криптографических операций внутри аппаратного модуля (HSM).

### Как избежать деградации latency при обработке потока событий:
1. **Асинхронный пул предварительной генерации (Prefetch Pool):**
   - Фоновая горутина поддерживает в буферизованном канале запас свежих DEK (например, 50 штук).
   - Обработчик HTTP-запроса или Kafka-консьюмер мгновенно забирает готовый DEK из канала за 50 наносекунд без ожидания сетевого вызова KMS!
2. **Пакетная обработка (Batching):**
   - Использование одного DEK для пачки (batch) из \(N\) сообщений или партиции с уникальным Nonce для каждого сообщения.

## Решение по шагам

1. Спроектируйте структуру `DEKPrefetchPool` с буферизованным каналом `chan *SecureDataKey`.
2. Реализуйте фоновый воркер `refillLoop`, восполняющий пул при опустошении.
3. Добавьте метод `GetDEK(ctx context.Context)` с мгновенным извлечением.
4. Протестируйте сокращение времени получения DEK с 100 мс до долей миллисекунды.

## Код решения

**`dek_prefetch_pool.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"fmt"
	"io"
	"sync"
	"time"
)

type PrefetchedDEK struct {
	Plaintext  []byte
	Ciphertext []byte
}

// DEKPrefetchPool поддерживает постоянный буфер готовых ключей в памяти
type DEKPrefetchPool struct {
	poolChan  chan *PrefetchedDEK
	closeOnce sync.Once
	stopChan  chan struct{}
}

func NewDEKPrefetchPool(capacity int) *DEKPrefetchPool {
	p := &DEKPrefetchPool{
		poolChan: make(chan *PrefetchedDEK, capacity),
		stopChan: make(chan struct{}),
	}
	go p.refillWorker()
	return p
}

// refillWorker в фоновом режиме восполняет канал ключами
func (p *DEKPrefetchPool) refillWorker() {
	for {
		select {
		case <-p.stopChan:
			return
		default:
		}

		// Имитация задержки сетевого вызова к AWS KMS (100 мс)
		time.Sleep(100 * time.Millisecond)

		plain := make([]byte, 32)
		io.ReadFull(rand.Reader, plain)
		cipher := append([]byte("kms-enc-dek:"), plain[:6]...)

		dek := &PrefetchedDEK{
			Plaintext:  plain,
			Ciphertext: cipher,
		}

		select {
		case p.poolChan <- dek:
			// Успешно добавлен в пул
		case <-p.stopChan:
			return
		}
	}
}

// GetDEK мгновенно возвращает ключ из пула
func (p *DEKPrefetchPool) GetDEK(ctx context.Context) (*PrefetchedDEK, error) {
	select {
	case dek := <-p.poolChan:
		return dek, nil
	case <-ctx.Done():
		return nil, ctx.Err()
	}
}

func (p *DEKPrefetchPool) Close() {
	p.closeOnce.Do(func() {
		close(p.stopChan)
	})
}

func main() {
	pool := NewDEKPrefetchPool(10)
	defer pool.Close()

	// Даем фоновому воркеру наполнить пул несколькими ключами
	time.Sleep(350 * time.Millisecond)

	ctx := context.Background()
	fmt.Println("Запрашиваем 3 DEK из Prefetch Pool...")

	for i := 1; i <= 3; i++ {
		start := time.Now()
		dek, err := pool.GetDEK(ctx)
		elapsed := time.Since(start)

		if err != nil {
			fmt.Printf("Ошибка: %v\n", err)
			continue
		}

		fmt.Printf("  Запрос #%d: получен DEK (prefix=%x...) за %v (вместо 100ms!)\n",
			i, dek.Plaintext[:4], elapsed)
	}

	fmt.Println("Успех: Фоновый Prefetch Pool полностью устранил сетевую задержку KMS для прикладного кода!")
}
```

## Под капотом

Механика реализации 'KMS Latency Mitigation: Асинхронный Prefetching и пакетная генерация DEK':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Используйте prefetch-пулы для высоконагруженных очередей сообщений (Kafka, RabbitMQ)
- Ограничивайте размер пула, чтобы не держать в памяти избыточное число открытых ключей
- Устанавливайте время жизни (TTL) для невостребованных элементов в пуле
