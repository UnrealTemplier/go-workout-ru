# Data Key Lifecycle: Безопасное стирание открытого DEK из памяти процесса

## Условие

Сгенерируйте DEK через KMS (`GenerateDataKey`), который возвращает открытый и зашифрованный DEK. Зашифруйте файл открытым DEK, сохраните зашифрованный DEK. При расшифровке сначала расшифруйте DEK через KMS, затем файл.

### Исходная формулировка

**Envelope Encryption с AWS KMS.**: Сгенерируйте DEK через KMS (`GenerateDataKey`), который возвращает открытый и зашифрованный DEK. Зашифруйте файл открытым DEK, сохраните зашифрованный DEK. При расшифровке сначала расшифруйте DEK через KMS, затем файл.

## Теория

При работе с криптографическими ключами в оперативной памяти Go-приложений возникает специфический риск: сборщик мусора (GC) не гарантирует немедленной очистки физических страниц RAM после выхода объекта из области видимости.

### Опасность сохранения DEK в памяти:
- При генерации Core Dump (падение с паникой).
- При чтении виртуальной памяти `/proc/<pid>/mem`.
- При вытеснении страниц памяти в Swap-раздел ОС.

### Практика Zeroization (Зануление):
Сразу после вызова `gcm.Seal(...)` байтовый срез открытого DEK обязан быть занулен циклом перезаписи нулями:
```go
for i := range plaintextDEK {
    plaintextDEK[i] = 0
}
```
Это гарантирует, что в оперативной памяти останется исключительно зашифрованный блоб `encryptedDEK`, который безопасен даже при утечке дампа памяти.

## Решение по шагам

1. Спроектируйте тип `SecureDEK`, инкапсулирующий открытый и зашифрованный срезы байт.
2. Реализуйте метод `Destroy()`, зануляющий открытый ключ в памяти.
3. Напишите функцию `EncryptAndWipe`, которая шифрует полезную нагрузку и гарантированно уничтожает открытый ключ через `defer`.
4. Проверьте с помощью тестов, что срез открытого ключа содержит строго нули после выполнения функции.

## Код решения

**`zeroize_dek.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"log"
)

// SecureDataKey представляет DEK с поддержкой гарантированного зануления
type SecureDataKey struct {
	Plaintext    []byte
	Ciphertext   []byte
	isDestroyed  bool
}

func NewSecureDataKey(plain, cipher []byte) *SecureDataKey {
	return &SecureDataKey{
		Plaintext:  plain,
		Ciphertext: cipher,
	}
}

// Destroy перезаписывает область памяти нулями
func (k *SecureDataKey) Destroy() {
	if k.isDestroyed || k.Plaintext == nil {
		return
	}
	for i := range k.Plaintext {
		k.Plaintext[i] = 0
	}
	k.isDestroyed = true
}

// EncryptWithSafeWipe выполняет шифрование и гарантирует уничтожение открытого DEK
func EncryptWithSafeWipe(key *SecureDataKey, payload []byte) ([]byte, error) {
	defer key.Destroy() // Зануление сработает даже при возникновении паники!

	block, err := aes.NewCipher(key.Plaintext)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}

	nonce := make([]byte, gcm.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, err
	}

	ciphertext := gcm.Seal(nonce, nonce, payload, nil)
	return ciphertext, nil
}

func main() {
	// Симуляция ответа KMS GenerateDataKey
	plain := make([]byte, 32)
	io.ReadFull(rand.Reader, plain)
	enc := append([]byte("kms-wrapped-blob-"), plain[:8]...)

	key := NewSecureDataKey(plain, enc)
	fmt.Printf("DEK до шифрования (первые 4 байта): %x...\n", key.Plaintext[:4])

	secretMessage := []byte("Top Secret Corporate M&A Strategy Document")
	cipherData, err := EncryptWithSafeWipe(key, secretMessage)
	if err != nil {
		log.Fatalf("Encrypt error: %v", err)
	}

	fmt.Printf("Шифрование завершено. Длина шифротекста: %d байт\n", len(cipherData))
	fmt.Printf("DEK после EncryptWithSafeWipe:       %x (память занулена!)\n", key.Plaintext)

	allZeros := true
	for _, b := range key.Plaintext {
		if b != 0 {
			allZeros = false
			break
		}
	}

	if allZeros {
		fmt.Println("Успех: Открытый ключ DEK полностью и гарантированно уничтожен из RAM.")
	}
}
```

## Под капотом

Механика реализации 'Data Key Lifecycle: Безопасное стирание открытого DEK из памяти процесса':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

**Вопрос на собеседовании (Senior / Staff Go Architect):**
«Как масштабировать архитектуру 'Data Key Lifecycle: Безопасное стирание открытого DEK из памяти процесса' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Всегда используйте `defer key.Destroy()` сразу после получения открытого DEK
- Для сверхкритичных систем используйте сторонние пакеты защиты памяти (например, `awnumar/memguard`), вызывающие `mlock` для запрета сброса в Swap
- Никогда не присваивайте открытый DEK глобальным переменным

## Самопроверка

1. Проверьте зануление байт через `defer key.Destroy()`.
2. Убедитесь, что зашифрованный блоб `Ciphertext` сохраняется для последующей отправки в хранилище.
3. Проверьте поведение при повторном вызове `Destroy`.
