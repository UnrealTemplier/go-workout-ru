# Sidecar Key Storage: Раздельное хранение зашифрованных данных (.enc) и ключа (.key)

## Условие

Отправь свой сгенерированный DEK в KMS, чтобы зашифровать его (Wrap). Сохрани в S3 два объекта: зашифрованный файл (данные) и зашифрованный DEK (ключ от данных). Теперь, даже если хакер украдет данные из S3, он не сможет их расшифровать без доступа к AWS KMS.

### Исходная формулировка

**Шифрование Конвертом (Wrap)**: Отправь свой сгенерированный DEK в KMS, чтобы зашифровать его (Wrap). Сохрани в S3 два объекта: зашифрованный файл (данные) и зашифрованный DEK (ключ от данных). Теперь, даже если хакер украдет данные из S3, он не сможет их расшифровать без доступа к AWS KMS.

## Теория

В ряде корпоративных сценариев (например, в распределенных файловых системах, Ceph, MinIO или S3 без поддержки кастомных метаданных) вместо заголовков объекта используется паттерн **Sidecar Key**:
1. Файл с зашифрованными данными сохраняется как `filename.enc`.
2. Зашифрованный ключ DEK и криптографические атрибуты сохраняются как `filename.key`.

### Преимущества паттерна:
- Позволяет скачивать или проверять ключ `.key` (весом ~100 байт) до загрузки гигантского файла `.enc` (весом десятки гигабайт).
- Позволяет настроить разные права доступа IAM на `.enc` и `.key` объекты в бакете (например, права на ключ есть только у финансового отдела).

## Решение по шагам

1. Спроектируйте структуру хранилища `SidecarStorageManager`.
2. Реализуйте метод сохранения `SaveEncrypted(path string, data []byte)` с созданием парных файлов `.enc` и `.key`.
3. Реализуйте метод чтения `ReadDecrypted(path string)` с чтением ключа и тела.
4. Протестируйте поведение при отсутствии `.key` файла.

## Код решения

**`sidecar_keys.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"log"
)

// KeySidecarMetadata описывает структуру .key файла
type KeySidecarMetadata struct {
	KeyID        string `json:"key_id"`
	EncryptedDEK []byte `json:"encrypted_dek"`
	Nonce        []byte `json:"nonce"`
}

// SidecarStorage эмулирует бакет с поддержкой sidecar файлов
type SidecarStorage struct {
	objects map[string][]byte
}

func NewSidecarStorage() *SidecarStorage {
	return &SidecarStorage{objects: make(map[string][]byte)}
}

func (s *SidecarStorage) Put(path string, data []byte) {
	s.objects[path] = data
}

func (s *SidecarStorage) Get(path string) ([]byte, error) {
	data, ok := s.objects[path]
	if !ok {
		return nil, fmt.Errorf("object %s not found", path)
	}
	return data, nil
}

// SaveWithSidecar сохраняет данные в .enc и метаданные в .key
func SaveWithSidecar(storage *SidecarStorage, basePath string, plaintext []byte, kek []byte) error {
	// 1. Генерируем DEK
	dek := make([]byte, 32)
	io.ReadFull(rand.Reader, dek)

	// 2. Шифруем полезную нагрузку
	block, _ := aes.NewCipher(dek)
	gcm, _ := cipher.NewGCM(block)
	nonce := make([]byte, gcm.NonceSize())
	io.ReadFull(rand.Reader, nonce)
	ciphertext := gcm.Seal(nil, nonce, plaintext, nil)

	// 3. Шифруем DEK мастер-ключом
	kBlock, _ := aes.NewCipher(kek)
	kGCM, _ := cipher.NewGCM(kBlock)
	kNonce := make([]byte, kGCM.NonceSize())
	io.ReadFull(rand.Reader, kNonce)
	encDEK := kGCM.Seal(kNonce, kNonce, dek, nil)

	// 4. Записываем .enc файл
	storage.Put(basePath+".enc", ciphertext)

	// 5. Записываем .key файл
	sidecar := KeySidecarMetadata{
		KeyID:        "master-kek-v1",
		EncryptedDEK: encDEK,
		Nonce:        nonce,
	}
	sidecarBytes, _ := json.Marshal(sidecar)
	storage.Put(basePath+".key", sidecarBytes)

	return nil
}

// ReadWithSidecar читает парные файлы и восстанавливает открытый текст
func ReadWithSidecar(storage *SidecarStorage, basePath string, kek []byte) ([]byte, error) {
	// Читаем ключ
	keyData, err := storage.Get(basePath + ".key")
	if err != nil {
		return nil, fmt.Errorf("read sidecar key failed: %w", err)
	}

	var meta KeySidecarMetadata
	if err := json.Unmarshal(keyData, &meta); err != nil {
		return nil, err
	}

	// Расшифровываем DEK
	kBlock, _ := aes.NewCipher(kek)
	kGCM, _ := cipher.NewGCM(kBlock)
	kNonceSize := kGCM.NonceSize()
	if len(meta.EncryptedDEK) < kNonceSize {
		return nil, errors.New("invalid encrypted dek length")
	}
	dek, err := kGCM.Open(nil, meta.EncryptedDEK[:kNonceSize], meta.EncryptedDEK[kNonceSize:], nil)
	if err != nil {
		return nil, fmt.Errorf("decrypt DEK failed: %w", err)
	}

	// Читаем зашифрованные данные
	encData, err := storage.Get(basePath + ".enc")
	if err != nil {
		return nil, fmt.Errorf("read encrypted file failed: %w", err)
	}

	// Расшифровываем данные
	block, _ := aes.NewCipher(dek)
	gcm, _ := cipher.NewGCM(block)
	plaintext, err := gcm.Open(nil, meta.Nonce, encData, nil)
	if err != nil {
		return nil, fmt.Errorf("decrypt data failed: %w", err)
	}

	return plaintext, nil
}

func main() {
	storage := NewSidecarStorage()
	masterKEK := []byte("master-kek-32bytes-secret-key-1!")

	filePath := "backups/2026/db_dump"
	secretData := []byte("Sensitive customer database export table rows...")

	// Сохранение пары файлов
	if err := SaveWithSidecar(storage, filePath, secretData, masterKEK); err != nil {
		log.Fatalf("Save failed: %v", err)
	}

	fmt.Printf("Файлы успешно сохранены:\n")
	fmt.Printf("  - %s.enc (размер: %d байт)\n", filePath, len(storage.objects[filePath+".enc"]))
	fmt.Printf("  - %s.key (размер: %d байт)\n", filePath, len(storage.objects[filePath+".key"]))

	// Чтение и расшифровка
	recovered, err := ReadWithSidecar(storage, filePath, masterKEK)
	if err != nil {
		log.Fatalf("Read failed: %v", err)
	}

	fmt.Printf("\nРасшифрованные данные:\n  %s\n", string(recovered))
}
```

## Под капотом

Механика реализации 'Sidecar Key Storage: Раздельное хранение зашифрованных данных (.enc) и ключа (.key)':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.
