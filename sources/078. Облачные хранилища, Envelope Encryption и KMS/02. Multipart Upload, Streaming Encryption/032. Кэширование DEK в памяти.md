# Кэширование DEK в памяти: Оптимизация KMS квот, TTL и риски компрометации

## Условие

Для производительности кэшируйте plaintext DEK в памяти (с TTL). Но помните: при compromise приложения все cached DEKs скомпрометированы.

### Исходная формулировка

**DEK caching**: Для производительности кэшируйте plaintext DEK в памяти (с TTL). Но помните: при compromise приложения все cached DEKs скомпрометированы.

## Теория

Каждый вызов `GenerateDataKey` или `Decrypt` в AWS KMS тарифицируется ($0.03 за 10 000 запросов) и имеет жесткие региональные квоты (например, 10 000–50 000 RPS).
При нагрузке 100 000 RPS прямое обращение в KMS на каждый запрос приведет к исчерпанию квот (`ThrottlingException`) и огромным счетам.

### Паттерн Cryptographic Materials Caching:
1. **Plaintext DEK Cache:** Открытые ключи DEK кэшируются в оперативной памяти приложения с ограниченным TTL (например, 5 минут) и лимитом на количество зашифрованных сообщений (например, 1 000 000 сообщений на один ключ).
2. **Компромисс безопасности (Security Trade-off):**
   - Плюс: Сокращение RPS к KMS на 99.9% и снижение задержки с 15 мс до 50 нс.
   - Минус: В случае компрометации процесса (через core dump, чтение `/proc/self/mem` или уязвимости типа Heartbleed) злоумышленник получает доступ ко всем закэшированным DEK.

## Решение по шагам

1. Спроектируйте структуру `DEKCacheEntry` с полями `PlaintextDEK`, `CreatedAt`, `UsageCount`.
2. Реализуйте потокобезопасный кэш `CryptographicCache` с ограничениями по TTL и максимальному числу использований.
3. Добавьте метод инвалидации и очистки устаревших ключей.
4. Протестируйте автоматическое обновление ключа при превышении лимита вызовов.

## Код решения

**`dek_cache.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"fmt"
	"io"
	"sync"
	"sync/atomic"
	"time"
)

// CachedDEK запись закэшированного ключа
type CachedDEK struct {
	Plaintext  []byte
	Ciphertext []byte
	CreatedAt  time.Time
	UseCount   int64
}

// CryptographicCache управляет жизненным циклом DEK в памяти
type CryptographicCache struct {
	mu         sync.RWMutex
	store      map[string]*CachedDEK
	ttl        time.Duration
	maxUses    int64
	kmsCallNum int64 // Счетчик реальных сетевых вызовов KMS
}

func NewCryptographicCache(ttl time.Duration, maxUses int64) *CryptographicCache {
	return &CryptographicCache{
		store:   make(map[string]*CachedDEK),
		ttl:     ttl,
		maxUses: maxUses,
	}
}

// GetOrGenerateDataKey возвращает DEK из кэша либо запрашивает новый у KMS
func (c *CryptographicCache) GetOrGenerateDataKey(ctx context.Context, cacheKey string) ([]byte, []byte, error) {
	c.mu.RLock()
	entry, found := c.store[cacheKey]
	c.mu.RUnlock()

	// Проверяем валидность: наличие, TTL и лимит использований
	if found && time.Since(entry.CreatedAt) < c.ttl {
		count := atomic.AddInt64(&entry.UseCount, 1)
		if count <= c.maxUses {
			return entry.Plaintext, entry.Ciphertext, nil
		}
	}

	// Промах кэша или ключ устарел: обращаемся в KMS
	c.mu.Lock()
	defer c.mu.Unlock()

	// Double-check locking
	entry, found = c.store[cacheKey]
	if found && time.Since(entry.CreatedAt) < c.ttl && atomic.LoadInt64(&entry.UseCount) <= c.maxUses {
		atomic.AddInt64(&entry.UseCount, 1)
		return entry.Plaintext, entry.Ciphertext, nil
	}

	// Симулируем сетевой вызов в KMS
	atomic.AddInt64(&c.kmsCallNum, 1)
	plain := make([]byte, 32)
	io.ReadFull(rand.Reader, plain)
	cipher := append([]byte("kms-wrapped-dek:"), plain[:8]...)

	c.store[cacheKey] = &CachedDEK{
		Plaintext:  plain,
		Ciphertext: cipher,
		CreatedAt:  time.Now(),
		UseCount:   1,
	}

	return plain, cipher, nil
}

func main() {
	// Настройка кэша: TTL 2 секунды, максимум 5 использований
	cache := NewCryptographicCache(2*time.Second, 5)
	ctx := context.Background()

	fmt.Println("Выполняем 12 последовательных запросов на получение DEK...")
	for i := 1; i <= 12; i++ {
		plain, _, _ := cache.GetOrGenerateDataKey(ctx, "payment-records-partition-1")
		fmt.Printf("Запрос #%2d: DEK prefix=%x... (KMS обращений: %d)\n",
			i, plain[:4], atomic.LoadInt64(&cache.kmsCallNum))
	}

	fmt.Printf("\nИтог: из 12 криптографических операций реальных обращений в KMS было всего %d!\n",
		atomic.LoadInt64(&cache.kmsCallNum))
}
```

## Под капотом

Механика реализации 'Кэширование DEK в памяти: Оптимизация KMS квот, TTL и риски компрометации':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Ограничивайте как время жизни кэша (TTL), так и максимальное число сообщений (`maxUses`), зашифрованных одним DEK
- Для многопоточных сервисов используйте официальный AWS Encryption SDK for Go с компонентом `materials.NewCachingCryptoMaterialsManager`
- Никогда не кэшируйте DEK бессрочно — это грубейшее нарушение стандартов PCI DSS

## Самопроверка

1. Проверьте корректность работы double-check locking.
2. Убедитесь в атомарном инкременте счетчика использований `atomic.AddInt64`.
3. Проверьте инвалидацию ключа при превышении `maxUses`.
