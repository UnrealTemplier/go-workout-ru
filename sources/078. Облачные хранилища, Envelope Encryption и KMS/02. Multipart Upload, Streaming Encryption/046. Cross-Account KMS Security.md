# Cross-Account KMS Security: Организация междоменного доступа к ключам между AWS аккаунтами

## Условие

Для multi-account AWS setup используйте cross-account KMS access через key policies.

### Исходная формулировка

**KMS cross-account**: Для multi-account AWS setup используйте cross-account KMS access через key policies.

## Теория

В корпоративной архитектуре AWS (AWS Organizations) сервисы разделяются по независимым аккаунтам:
- `Account A (Security / Central KMS Account)`: Хранилище мастер-ключей и журналов аудита.
- `Account B (Workload / Application Account)`: Вычислительные ресурсы (EKS, Lambda, EC2).

### Требования для успешного Cross-Account доступа:
Для доступа сервиса из Account B к ключу в Account A требуются **ОБА** разрешения:
1. **Key Policy в Account A:** Политика самого ключа обязана явно разрешать доступ IAM-роли или корню Account B (`Principal: arn:aws:iam::<AccountB>:role/AppRole`).
2. **IAM Policy в Account B:** Роль в Account B обязана иметь IAM-политику с разрешением `kms:Decrypt`, `kms:GenerateDataKey` на целевой ARN ключа в Account A.
Если отсутствует хотя бы одно из двух правил — AWS вернет `AccessDenied`.

## Решение по шагам

1. Спроектируйте валидатор Cross-Account политик `CrossAccountPolicyChecker`.
2. Смоделируйте проверку разрешения со стороны Key Policy (Account A) и IAM Policy (Account B).
3. Протестируйте ситуацию, когда разрешена только одна из политик (ожидается отказ).
4. Протестируйте успешный доступ при наличии обоих разрешений.

## Код решения

**`cross_account_kms.go`**

```go
package main

import (
	"fmt"
)

type IAMPolicy struct {
	AllowedKeyARNs []string
}

type KeyPolicy struct {
	AllowedPrincipals []string
}

// CheckCrossAccountAccess реализует проверку двойного рукопожатия AWS IAM и KMS
func CheckCrossAccountAccess(callerAccountID, callerRoleARN, targetKeyARN string, callerIAM IAMPolicy, targetKey KeyPolicy) (bool, string) {
	// 1. Проверяем разрешение в IAM политике вызывающего аккаунта (Account B)
	iamAllowed := false
	for _, arn := range callerIAM.AllowedKeyARNs {
		if arn == targetKeyARN || arn == "*" {
			iamAllowed = true
			break
		}
	}
	if !iamAllowed {
		return false, "DENIED by Account B IAM Policy (отсутствует разрешение на target Key ARN)"
	}

	// 2. Проверяем разрешение в Key Policy ключевого аккаунта (Account A)
	keyPolicyAllowed := false
	for _, p := range targetKey.AllowedPrincipals {
		if p == callerRoleARN || p == fmt.Sprintf("arn:aws:iam::%s:root", callerAccountID) {
			keyPolicyAllowed = true
			break
		}
	}
	if !keyPolicyAllowed {
		return false, "DENIED by Account A Key Policy (ключ не доверяет вызывающему Principal)"
	}

	return true, "ALLOWED (Оба правила удовлетворены: IAM Policy и Key Policy)"
}

func main() {
	targetKeyARN := "arn:aws:kms:eu-central-1:111111111111:key/central-fin-key"
	callerAccountID := "222222222222"
	callerRoleARN := "arn:aws:iam::222222222222:role/PaymentService"

	// Сценарий 1: IAM разрешил, но Key Policy в Account A забыли настроить
	callerIAM1 := IAMPolicy{AllowedKeyARNs: []string{targetKeyARN}}
	targetKey1 := KeyPolicy{AllowedPrincipals: []string{}} // Пусто!
	ok1, reason1 := CheckCrossAccountAccess(callerAccountID, callerRoleARN, targetKeyARN, callerIAM1, targetKey1)
	fmt.Printf("Тест 1 (Только IAM): %v -> %s\n", ok1, reason1)

	// Сценарий 2: Key Policy разрешила, но у роли нет IAM прав
	callerIAM2 := IAMPolicy{AllowedKeyARNs: []string{}} // Пусто!
	targetKey2 := KeyPolicy{AllowedPrincipals: []string{callerRoleARN}}
	ok2, reason2 := CheckCrossAccountAccess(callerAccountID, callerRoleARN, targetKeyARN, callerIAM2, targetKey2)
	fmt.Printf("Тест 2 (Только KeyPolicy): %v -> %s\n", ok2, reason2)

	// Сценарий 3: Оба правила настроены корректно
	callerIAM3 := IAMPolicy{AllowedKeyARNs: []string{targetKeyARN}}
	targetKey3 := KeyPolicy{AllowedPrincipals: []string{callerRoleARN}}
	ok3, reason3 := CheckCrossAccountAccess(callerAccountID, callerRoleARN, targetKeyARN, callerIAM3, targetKey3)
	fmt.Printf("Тест 3 (Cross-Account OK): %v -> %s\n", ok3, reason3)
}
```

## Под капотом

Механика реализации 'Cross-Account KMS Security: Организация междоменного доступа к ключам между AWS аккаунтами':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

**Вопрос на собеседовании (Senior / Staff Go Architect):**
«Как масштабировать архитектуру 'Cross-Account KMS Security: Организация междоменного доступа к ключам между AWS аккаунтами' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.

## Лучшие практики

- Используйте выделенный Security Account для хранения централизованных KMS ключей корпорации
- Предоставляйте доступ конкретным IAM ролям (`arn:aws:iam::...:role/...`), избегая разрешения на весь аккаунт `root` без условий
- Включайте условие `kms:CallerAccount` для защиты от атак типа Confused Deputy
