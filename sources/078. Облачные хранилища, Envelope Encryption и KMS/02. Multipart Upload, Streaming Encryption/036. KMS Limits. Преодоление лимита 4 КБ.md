# KMS Limits: Преодоление лимита 4 КБ через генерацию 32-байтного DEK

## Условие

*Нельзя отправлять 5 ГБ данных в KMS.* Архитектура конверта: сгенерируй случайный 32-байтный Data Encryption Key (DEK) прямо в Go. Зашифруй большой файл локально с помощью AES-GCM (из Блока 68), используя этот DEK.

### Исходная формулировка

**Envelope Encryption (Концепция)**: *Нельзя отправлять 5 ГБ данных в KMS.* Архитектура конверта: сгенерируй случайный 32-байтный Data Encryption Key (DEK) прямо в Go. Зашифруй большой файл локально с помощью AES-GCM (из Блока 68), используя этот DEK.

## Теория

Почему нельзя отправить 5 ГБ файл напрямую в AWS KMS?
1. **Жесткий лимит полезной нагрузки:** KMS API допускает размер параметра `Plaintext` не более **4096 байт**. При попытке отправить 5 ГБ KMS немедленно вернет ошибку `ValidationException: 1 validation error detected: Value at 'plaintext' failed to satisfy constraint: Member must have length less than or equal to 4096`.
2. **Сетевой оверхед и RPS:** Отправка гигабайтов в KMS через RPC парализует сеть и исчерпает лимиты полосы пропускания HSM модулей.

### Единственное верное архитектурное решение: Envelope Encryption
1. Запрос в KMS `GenerateDataKey(KeyId, KeySpec: "AES_256")`:
   - Передается 0 байт данных.
   - KMS возвращает открытый DEK (32 байта) и зашифрованный DEK (~64–128 байт).
2. Файл 5 ГБ шифруется **локально** на процессоре сервера с помощью AES-256-GCM.
3. Открытый DEK удаляется из памяти.
4. Зашифрованный DEK сохраняется вместе с 5 ГБ шифротекстом в S3.

## Решение по шагам

1. Напишите валидатор размера данных, отклоняющий прямую отправку в KMS более 4096 байт.
2. Реализуйте процедуру `GenerateDataKey` для получения 32-байтного DEK.
3. Смоделируйте локальное шифрование 5 ГБ объекта с помощью сгенерированного DEK.
4. Протестируйте итоговый пакет: тело данных зашифровано локально, DEK зашифрован в KMS.

## Код решения

**`kms_limits_envelope.go`**

```go
package main

import (
	"context"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"log"
)

const KMSDirectDataLimit = 4096 // 4 KB

// FakeKMSClient симулирует ограничения реального сервиса AWS KMS
type FakeKMSClient struct{}

func (k *FakeKMSClient) EncryptDirect(ctx context.Context, data []byte) ([]byte, error) {
	if len(data) > KMSDirectDataLimit {
		return nil, fmt.Errorf("ValidationException: data size %d exceeds KMS limit of %d bytes",
			len(data), KMSDirectDataLimit)
	}
	// Имитация шифрования
	return append([]byte("kms-direct:"), data...), nil
}

func (k *FakeKMSClient) GenerateDataKey(ctx context.Context, keyID string) (plainDEK []byte, encDEK []byte, err error) {
	// KMS генерирует 32 байта для AES-256
	plainDEK = make([]byte, 32)
	if _, err := io.ReadFull(rand.Reader, plainDEK); err != nil {
		return nil, nil, err
	}
	encDEK = append([]byte("kms-wrapped:"), plainDEK...)
	return plainDEK, encDEK, nil
}

func main() {
	kms := &FakeKMSClient{}
	ctx := context.Background()

	// 1. Попытка отправить большой файл (например, 5 ГБ, эмулируем срезом 10 КБ) напрямую в KMS
	largeFileData := make([]byte, 10240)
	_, errDirect := kms.EncryptDirect(ctx, largeFileData)
	if errDirect != nil {
		fmt.Printf("1. Ожидаемый отказ KMS при попытке прямого шифрования большого объема:\n   -> %v\n\n", errDirect)
	}

	// 2. Правильный паттерн: Envelope Encryption
	fmt.Println("2. Применяем паттерн Envelope Encryption:")
	plainDEK, encDEK, err := kms.GenerateDataKey(ctx, "alias/prod-large-files")
	if err != nil {
		log.Fatalf("GenerateDataKey error: %v", err)
	}
	fmt.Printf("   a) Получен DEK от KMS: открытый=%d байт, зашифрованный=%d байт\n", len(plainDEK), len(encDEK))

	// 3. Локальное шифрование данных произвольного размера
	block, _ := aes.NewCipher(plainDEK)
	gcm, _ := cipher.NewGCM(block)
	nonce := make([]byte, gcm.NonceSize())
	io.ReadFull(rand.Reader, nonce)

	ciphertext := gcm.Seal(nonce, nonce, largeFileData, nil)
	fmt.Printf("   b) Данные 10 КБ успешно зашифрованы локально на CPU сервера. Размер: %d байт\n", len(ciphertext))

	// 4. Обнуление открытого DEK
	for i := range plainDEK {
		plainDEK[i] = 0
	}
	fmt.Println("   c) Открытый DEK стерт из оперативной памяти.")
	fmt.Println("   d) Зашифрованный DEK и шифротекст готовы для отправки в S3.")
}
```

## Под капотом

Механика реализации 'KMS Limits: Преодоление лимита 4 КБ через генерацию 32-байтного DEK':
В рантайме Go и сетевом стеке низкоуровневые операции ввода-вывода абстрагируются через интерфейсы `io.Reader` и `io.Writer`. При работе с криптографическими алгоритмами задействуются аппаратные инструкции процессора (AES-NI / CLMUL на x86-64 и ARM Cryptography Extensions), что обеспечивает скорость обработки до 3–5 ГБ/с на ядро CPU с околонулевым оверхедом планировщика GMP.

## Подводные камни

Типичная ошибка при проектировании: утечка неуправляемых ресурсов и памяти. При работе с S3 сетевыми потоками обязателен вызов `defer response.Body.Close()`, иначе сокеты TCP останутся в состоянии CLOSE_WAIT, что приведет к исчерпанию лимита файловых дескрипторов ОС (`too many open files`). Также недопустимо сохранять открытые криптографические ключи в глобальных структурах данных.

## На собеседовании

**Вопрос на собеседовании (Senior / Staff Go Architect):**
«Как масштабировать архитектуру 'KMS Limits: Преодоление лимита 4 КБ через генерацию 32-байтного DEK' для обработки миллионов запросов в секунду с минимальным TCO?»

**Эталонный ответ:**
Ключевой принцип — минимизация сетевых RTT к внешним сервисам управления ключами через кэширование открытых DEK (с лимитом по TTL и числу операций), использование пулов буферов памяти `sync.Pool` для предотвращения аллокаций в куче, и асинхронный возобновляемый конвейер передачи данных с экспоненциальным бэкоффом и защитой от перегрузки сети.
