# Размер массива как часть сигнатуры типа: почему нельзя передать [4]int в [3]int

## Условие

Напишите функцию, принимающую массив `[3]int`. Попробуйте передать ей массив `[4]int` и изучите ошибку компилятора (размер массива — часть его типа).

## Теория

Статическая защита компилятора Go:
- `func ProcessTriple(data [3]int)` требует ровно 3 элемента;
- Передача `[4]int` невозможна без создания среза.

## Решение по шагам

1. Пишем функцию `ProcessTriple(data [3]int)`.
2. Вызываем с корректным массивом `[3]int`.
3. Показываем ошибку при передаче массива другой длины.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func ProcessTriple(data [3]int) {
	fmt.Printf("Обработка тройки чисел: %v (сумма: %d)\n",
		data, data[0]+data[1]+data[2])
}

func main() {
	valid := [3]int{10, 20, 30}
	ProcessTriple(valid)

	// invalid := [4]int{10, 20, 30, 40}
	// ProcessTriple(invalid) // ОШИБКА: cannot use invalid (type [4]int) as type [3]int in argument to ProcessTriple
}
```

ℹ️ Строгая проверка типа аргументов

**`Терминал`**

```bash
go run main.go
# Обработка тройки чисел: [10 20 30] (сумма: 60)
```

ℹ️ Результат

## Под капотом

Компилятор резервирует ровно 24 байта в стековом фрейме для аргумента `data`.

## Подводные камни

- Проектирование API библиотек с жестко фиксированными массивами `[10]T` вместо универсальных срезов `[]T`.

## На собеседовании

**Вопрос с собеседования:** «В каких редких случаях в продакшене выгодно использовать массив фиксированной длины `[32]byte` вместо среза `[]byte`?»
**Ответ:** Для криптографических хэшей (например SHA-256: `[32]byte` или UUID: `[16]byte`). Это гарантирует отсутствие аллокаций в куче, фиксированный размер и возможность использования хэша как ключа в `map`.
