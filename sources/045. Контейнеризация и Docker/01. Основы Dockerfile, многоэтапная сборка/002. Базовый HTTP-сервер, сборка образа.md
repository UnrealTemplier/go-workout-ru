# Базовый HTTP-сервер, сборка образа и проброс портов (Port Forwarding)

## Условие

**Базовый Dockerfile**: Напиши простой HTTP-сервер на Go. Создай файл `Dockerfile`. Используй базовый образ `golang:1.22` (или новее). Скопируй исходники (`COPY . .`), скачай зависимости, скомпилируй бинарник внутри контейнера и укажи `CMD` для запуска. Собери образ (`docker build`) и запусти контейнер с пробросом портов (`docker run -p 8080:8080`).

## Теория

Сетевая модель Docker изолирует контейнер в собственном сетевом пространстве имен (`Network Namespace`). По умолчанию контейнер подключен к виртуальному мосту `bridge` (`docker0`) и получает приватный IP-адрес вида `172.17.0.x`.

Инструкция `EXPOSE 8080` в `Dockerfile` носит исключительно **декларативный характер**: она документирует порт для других разработчиков и систем оркестрации, но физически не открывает сетевой порт на хосте.
Чтобы входящий трафик с сетевого интерфейса хоста попал в процесс контейнера, используется проброс портов (`Port Mapping` / `Port Forwarding` флаг `-p <host_port>:<container_port>`).

При выполнении `docker run -p 8080:8080`:
1. Демон Docker настраивает в ядре Linux цепочку правил `iptables` / `nftables` в таблице `nat` (цепочка `PREROUTING` и `DOCKER`).
2. Входящие TCP-пакеты на порт 8080 хостового интерфейса транслируются (DNAT — Destination Network Address Translation) на приватный IP контейнера `172.17.0.2:8080`.
3. Приложение внутри контейнера обязано слушать адрес `0.0.0.0:8080` (все интерфейсы), а не `127.0.0.1:8080`, иначе трафик с хоста будет отвергнут ядром.

## Решение по шагам

1. Напишите HTTP-сервер на Go, который слушает `:8080` (эквивалентно `0.0.0.0:8080`).
2. Опишите `Dockerfile` со сборкой бинарника и декларацией `EXPOSE 8080`.
3. Соберите образ командой `docker build -t go-web-server:latest .`.
4. Запустите контейнер: `docker run -d -p 8080:8080 --name web-instance go-web-server:latest`.
5. Проверьте правила iptables или обратитесь через curl/браузер к `http://localhost:8080`.
6. Остановите и удалите контейнер.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"log"
	"net/http"
	"time"
)

type StatusResponse struct {
	Status    string    `json:"status"`
	Timestamp time.Time `json:"timestamp"`
	Service   string    `json:"service"`
}

func main() {
	mux := http.NewServeMux()

	mux.HandleFunc("/api/v1/ping", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		resp := StatusResponse{
			Status:    "pong",
			Timestamp: time.Now().UTC(),
			Service:   "go-docker-demo",
		}
		_ = json.NewEncoder(w).Encode(resp)
	})

	server := &http.Server{
		Addr:         ":8080", // Важно: слушать 0.0.0.0:8080 внутри контейнера
		Handler:      mux,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
	}

	log.Println("Web server started on :8080")
	if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
		log.Fatalf("Server failed: %v", err)
	}
}
```

ℹ️ Production-ready HTTP-сервер с таймаутами и JSON API

**`Dockerfile`**

```dockerfile
FROM golang:1.24

WORKDIR /workspace

# Копируем исходный код
COPY main.go .

# Собираем оптимизированный бинарник
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o webapp main.go

# Документируем порт контейнера
EXPOSE 8080

# Точка входа в формате exec (JSON-array)
CMD ["/workspace/webapp"]
```

```bash
# Сборка

# Проверка логов контейнера
docker logs web-instance

# Остановка контейнера

```

## Под капотом

Служба `docker-proxy` (userspace proxy) или правила iptables ядра выполняют перенаправление TCP-сессий. Если Go-сервер слушает `127.0.0.1:8080`, он слушает loopback-интерфейс `lo` *внутри* контейнера. Пакеты, пришедшие от docker0 через виртуальный veth-интерфейс `eth0`, имеют адрес назначения `172.17.0.2`, поэтому ядро контейнера сбросит их с флагом RST (Connection Refused). Всегда указывайте `:8080` (`0.0.0.0:8080`).

## Подводные камни

1. Запуск сервера на `127.0.0.1:8080` внутри контейнера: запросы снаружи не будут доходить.
2. Заблуждение, что `EXPOSE` автоматически пробрасывает порт во внешнюю сеть хоста без флага `-p` или `-P`.
3. Использование `CMD /workspace/webapp` вместо exec-формы `CMD ["/workspace/webapp"]`: при запуске через shell процесс не получит сигналы `SIGTERM` для Graceful Shutdown.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между `EXPOSE` в Dockerfile и флагом `-p` при запуске контейнера? Что произойдет, если указать `EXPOSE 8080`, но запустить `docker run -d myimage`?»
**Ответ:** `EXPOSE` — это метаданные образа (документация), сообщающие, на каком порту приложение ожидает подключения. Без флага `-p` (или флага `-P`, который биндит все exposed-порты на случайные порты хоста) порт на хосте не открывается, и снаружи обратиться к контейнеру по IP хоста невозможно. Доступ к нему останется только у других контейнеров из той же Docker-сети по внутреннему IP.
