# Multi-stage сборка: Золотой стандарт продакшн-контейнеризации

## Условие

**Multi-stage сборка (Золотой стандарт)**: Образ из упр. 576 весит около 800+ МБ (потому что содержит исходники Go, компилятор, ОС Linux). Напиши Dockerfile из двух этапов (stages):
* Этап 1 (`builder`): образ `golang`, собираем бинарник.
* Этап 2: берем легковесный образ `alpine:latest`. Копируем туда бинарник из `builder`. Убедись, что итоговый образ весит около 15-20 МБ!

## Теория

«Золотой стандарт» Dockerfile для Go в продакшне объединяет все лучшие практики оптимизации и безопасности:
1. **Два этапа сборки (Builder + Minimal Runtime).**
2. **Селективное кэширование зависимостей (`go.mod` перед кодом).**
3. **Отключение CGO (`CGO_ENABLED=0`) и флаги компилятора (`-ldflags="-w -s"`).**
4. **Непривилегированный пользователь (Non-root user).**
5. **Наличие корневых сертификатов CA и базы таймзон.**

Такой подход гарантирует:
- Размер образа **15–25 МБ**.
- Время сборки при изменении кода: **< 2 секунд**.
- Защиту от атак повышения привилегий.

## Решение по шагам

1. Опишите законченный production Dockerfile с этапом сборщика и легковесным этапом Alpine.
2. Создайте non-root пользователя.
3. Добавьте сертификаты и зону времени.
4. Проверьте запуск и корректность прав процесса.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Production Grade Go Container!\n")
	})

	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}

	log.Printf("Application running on port :%s\n", port)
	_ = http.ListenAndServe(":"+port, nil)
}
```

ℹ️ Production микросервис

**`Dockerfile`**

```dockerfile
# === Stage 1: Build ===
FROM golang:1.24-alpine AS builder

RUN apk add --no-cache ca-certificates tzdata

WORKDIR /app

# Кэширование модулей
COPY go.mod go.sum* ./
RUN go mod download

# Копирование исходного кода и сборка
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build \
    -ldflags="-w -s" \
    -o /app/server .

# Создание непривилегированного пользователя
RUN adduser -D -u 10001 -s /sbin/nologin appuser

# === Stage 2: Production Runtime ===
FROM alpine:3.20

WORKDIR /app

# Сертификаты и таймзоны
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /usr/share/zoneinfo /usr/share/zoneinfo
COPY --from=builder /etc/passwd /etc/passwd
COPY --from=builder /etc/group /etc/group

# Бинарник
COPY --from=builder --chown=10001:10001 /app/server /app/server

# Переключение на non-root
USER 10001:10001

EXPOSE 8080

ENTRYPOINT ["/app/server"]
```

ℹ️ Золотой стандарт продакшн Dockerfile

**`Терминал`**

```bash
# Сборка
docker build -t app-gold-standard:v1 .

# Проверка размера
docker images app-gold-standard:v1

# Запуск
docker run -d -p 8080:8080 --name test-gold app-gold-standard:v1
curl http://localhost:8080
docker exec test-gold id
docker rm -f test-gold
```

## Под капотом

Флаг `--chown=10001:10001` в команде `COPY` сразу назначает правильного владельца файла в файловой системе слоя без создания дополнительного тяжелого слоя `RUN chown ...`.

## Подводные камни

1. Выполнение `RUN chown -R appuser /app` в runtime этапе: это дублирует размер всех файлов в новом слое. Всегда используйте `COPY --chown=...`.
2. Запуск от пользователя, у которого нет прав на чтение бинарника (права должны быть 0755).

## На собеседовании

**Вопрос с собеседования:** «Почему антипаттерном считается использование команды `RUN chown -R appuser:appgroup /app` после команды `COPY` в Dockerfile?»
**Ответ:** В архитектуре файловой системы OverlayFS команда `chown` модифицирует метаданные файлов, из-за чего механизм Copy-on-Write полностью копирует все изменяемые файлы из нижнего слоя в новый верхний слой. Если бинарник или статика весили 100 МБ, образ увеличится еще на 100 МБ. Правильное решение — использовать флаг `COPY --chown=UID:GID`.
