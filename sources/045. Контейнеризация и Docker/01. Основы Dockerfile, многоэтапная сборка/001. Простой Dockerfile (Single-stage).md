# Простой Dockerfile (Single-stage) и анализ избыточного веса образа

## Условие

**Простой Dockerfile (Single-stage)**: Напишите базовый `Dockerfile` для вашего Go-приложения. Скопируйте туда весь исходный код, установите Go SDK внутри контейнера, выполните `RUN go build` и запустите бинарный файл. Соберите образ и посмотрите на его вес (он должен составить около 800 МБ–1 ГБ). Объясните в комментариях, почему не стоит тащить компилятор Go и исходный код в финальный продакшн-образ.

## Теория

Контейнеризация на базе Docker использует пространства имен (Linux namespaces: pid, net, ipc, mnt, uts, user) и контрольные группы (cgroups) для изолированного исполнения процессов на общем ядре хост-системы.
Классический одноэтапный `Dockerfile` (Single-stage build) выполняет компиляцию и исполнение внутри одного и того же образа.

Когда для сборки используется официальный базовый образ `golang:1.22` или `golang:1.24` (на базе Debian Linux), итоговый контейнер наследует:
1. Полный дистрибутив операционной системы (glibc, пакетный менеджер `apt`, утилиты bash, coreutils, curl, git, python и т.д.).
2. Компилятор Go (`go`, `gofmt`, тулчейн компилятора, ассемблер, линковщик).
3. Стандартную библиотеку в исходных кодах (`$GOROOT/src`) и промежуточный кэш модулей/пакетов (`$GOPATH/pkg`).
4. Все исходные `.go` файлы проекта, историю репозитория и тестовые артефакты.

В результате минимальный сервис «Hello World» весит **от 800 МБ до 1.2 ГБ**. В продакшн-эксплуатации такой образ несет фатальные недостатки:
- **Огромный Attack Surface (вектор атак):** наличие пакетных менеджеров, отладчиков (`gdb`) и компиляторов позволяет злоумышленнику при RCE (Remote Code Execution) скомпилировать и запустить любой эксплойт или бэкдор прямо в контейнере.
- **Медленный деплой:** скачивание гигабайтных образов в Kubernetes-кластерах с сотнями нод приводит к сетевому троттлингу, задержкам холодного старта (Cold Start) и переполнению дискового пространства нод (DiskPressure).

## Решение по шагам

1. Создайте минимальный Go HTTP-сервер в файле `main.go`.
2. Создайте файл `Dockerfile` с одноэтапной сборкой от базового образа `golang:1.24`.
3. Соберите Docker-образ командой `docker build -t app-single:v1 .`.
4. Проверьте размер созданного образа через `docker images app-single:v1`.
5. Запустите контейнер с пробросом портов: `docker run -d -p 8080:8080 --name single-test app-single:v1`.
6. Выполните проверку работоспособности через `curl http://localhost:8080` и остановите контейнер.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		hostname, _ := os.Hostname()
		fmt.Fprintf(w, "Hello from Single-stage Go Container! Host: %s\n", hostname)
	})

	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("OK"))
	})

	log.Println("Server listening on :8080...")
	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatalf("Server error: %v", err)
	}
}
```

ℹ️ Минимальный HTTP-сервер для демонстрации сборки в контейнере

**`Dockerfile`**

```dockerfile
# Базовый образ Debian с предустановленным Go 1.24
FROM golang:1.24

# Установка рабочей директории
WORKDIR /app

# Копирование исходного кода в образ
COPY . .

# Скачивание зависимостей и компиляция бинарника
RUN go mod init example.com/singleapp || true
RUN go build -o /app/server main.go

# Проброс сетевого порта
EXPOSE 8080

# Команда запуска процесса в контейнере
CMD ["/app/server"]
```

ℹ️ Одноэтапный неоптимальный Dockerfile

**`Терминал`**

```bash
# Сборка образа
docker build -t app-single:v1 .

# Проверка размера образа (видим ~800MB-1GB)
docker images app-single:v1 --format "REPOSITORY: {{.Repository}} | TAG: {{.Tag}} | SIZE: {{.Size}}"

# Запуск контейнера
docker run -d -p 8080:8080 --name test-single app-single:v1

# Тестовый запрос
curl -i http://localhost:8080/healthz

# Очистка
docker rm -f test-single
```

## Под капотом

С точки зрения файловой системы OverlayFS каждый шаг `RUN` и `COPY` создает отдельный неизменяемый слой (layer). В одноэтапном билде слой с дистрибутивом Go (`/usr/local/go`) фиксируется в нижних слоях (lowerdir). Даже если в конце выполнить `RUN rm -rf /usr/local/go`, размер итогового образа не уменьшится: удаленные файлы лишь помечаются специальными символами скрытия (whiteout files) в верхнем слое (upperdir), оставаясь физически упакованными во всех нижележащих tar-архивах слоев.

## Подводные камни

1. Оставление исходников и `.git` папки в продакшн-образе — утечка интеллектуальной собственности и секретов (API-ключи в истории коммитов).
2. Огромное время pull/push образов в CI/CD пайплайнах.
3. Уязвимости CVE в предустановленных системных библиотеках Linux, которые не нужны для работы Go-сервиса.

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшн запрещено отправлять single-stage Docker-образы для Go-сервисов, даже если они собраны на минимальном дистрибутиве?»
**Ответ:** Go компилируется в самодостаточный машинный код. В runtime ему не требуются ни компилятор Go, ни заголовочные файлы, ни исходники. Single-stage образ тянет сотни мегабайт лишних файлов и утилит (sh, apt, curl), что катастрофически расширяет поверхность атаки (CVE) и замедляет холодный старт подов в Kubernetes при автомасштабировании.
