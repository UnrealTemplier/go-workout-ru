# Инструкция HEALTHCHECK: автоматический мониторинг здоровья контейнера

## Условие

Добавь **health check**: `HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1`. Docker автоматически перезапускает unhealthy контейнер.

## Теория

Инструкция `HEALTHCHECK` в Dockerfile определяет, как Docker проверяет работоспособность приложения внутри контейнера.

Параметры директивы:
- `--interval=30s`: частота выполнения проверки (по умолчанию 30 секунд).
- `--timeout=3s`: максимальное время ожидания ответа на команду проверки.
- `--start-period=5s`: льготный период для инициализации приложения (неудачи в этот период не переводят контейнер в статус `unhealthy`).
- `--retries=3`: количество последовательных неудачных проверок, после которого контейнеру присваивается статус `unhealthy`.

Команда проверки возвращает код выхода (Exit Code):
- `0`: Success — контейнер здоров (`healthy`).
- `1`: Unhealthy — контейнер неисправен (`unhealthy`).

Docker демон отслеживает статус и отображает его в выводе `docker ps`. Системы Docker Compose и оркестраторы (Swarm/Kubernetes) используют этот статус для автоматического перезапуска или исключения контейнера из балансировки нагрузки.

## Решение по шагам

1. Напишите HTTP-сервис с эндпоинтом `/healthz`.
2. Добавьте в `Dockerfile` инструкцию `HEALTHCHECK` с использованием встроенной в Alpine утилиты `wget`.
3. Соберите образ и запустите контейнер.
4. Отследите смену статуса с `health: starting` на `healthy` через `docker ps`.
5. Изучите историю проверок через `docker inspect --format='{{json .State.Health}}' <container>`.

## Код решения

**`main.go`**

```go
package main

import (
	"log"
	"net/http"
	"sync/atomic"
)

var isReady int32 = 1

func main() {
	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		if atomic.LoadInt32(&isReady) == 1 {
			w.WriteHeader(http.StatusOK)
			w.Write([]byte("OK"))
			return
		}
		http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
	})

	// Эндпоинт для искусственной эмуляции сбоя сервиса
	http.HandleFunc("/fail", func(w http.ResponseWriter, r *http.Request) {
		atomic.StoreInt32(&isReady, 0)
		w.Write([]byte("Service marked as failing"))
	})

	log.Println("Server running on :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервер с эндпоинтом /health и ручным триггером сбоя /fail

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

FROM alpine:3.20
WORKDIR /app
COPY --from=builder /bin/app /app/app

EXPOSE 8080

# Определение проверки здоровья через wget (входит в busybox в Alpine)
HEALTHCHECK --interval=5s --timeout=3s --start-period=2s --retries=2 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1

ENTRYPOINT ["/app/app"]
```

ℹ️ Dockerfile с декларацией HEALTHCHECK

**`Терминал`**

```bash
# Сборка
docker build -t app-health:v1 .

# Запуск контейнера
docker run -d -p 8080:8080 --name test-health app-health:v1

# Ждем 3-5 секунд и проверяем статус (будет '(healthy)')
docker ps --filter "name=test-health" --format "table {{.Names}}\t{{.Status}}"

# Эмулируем поломку
curl http://localhost:8080/fail

# Ждем 10-12 секунд и снова смотрим статус (перейдет в '(unhealthy)')
docker ps --filter "name=test-health" --format "table {{.Names}}\t{{.Status}}"

# Очистка
docker rm -f test-health
```

## Под капотом

Демон dockerd периодически порождает процесс проверки внутри пространства имен контейнера через системный вызов `execve` рантайма `runc`. Логи последних пяти проверок здоровья и коды выхода сохраняются во внутренней структуре контейнера `ContainerState.Health` и доступны через Docker API.

## Подводные камни

1. Забытый флаг `--spider` у `wget`: утилита попытается сохранить файл ответа на диск вместо простой проверки заголовков.
2. Слишком короткий `--timeout`, из-за чего под нагрузкой контейнер ложно признается `unhealthy`.

## На собеседовании

**Вопрос с собеседования:** «Почему в образах на базе `scratch` стандартная инструкция `HEALTHCHECK CMD wget ...` не работает и как решить эту задачу без внешних утилит?»
**Ответ:** В `scratch` нет ни `/bin/sh`, ни `wget`, ни `curl`. Попытка выполнить команду проверки завершится ошибкой отсутствия шелла. Решение: 1) Встроить проверку здоровья прямо в Go-бинарник в виде подкоманды: `HEALTHCHECK CMD ["/app", "healthcheck"]`, где бинарник сам делает HTTP GET запрос к `127.0.0.1:8080/health` и возвращает `os.Exit(0)` или `os.Exit(1)`. 2) Использовать нативные `livenessProbe` / `readinessProbe` в Kubernetes, которые проверяют сетевой сокет снаружи.
