# Разделение на builder и runtime окружение: детальный аудит

## Условие

**Multi-stage build**: Разделите Dockerfile на `builder` stage (с полным Go) и `runtime` stage (с минимальным базовым образом). Сравните размеры.

## Теория

Разделение на `builder` и `runtime` реализует фундаментальный принцип безопасности и надежности: **минимизация привилегий и зависимостей (Least Privilege & Minimal Dependencies)**.

На этапе сборки (`builder`):
- Требуются: компилятор Go, Git, SSH-ключи (для загрузки модулей из приватных репозиториев GitLab/GitHub), исходные коды, линтеры и тесты.
- Окружение работает временно и изолированно на билд-агенте CI/CD.

На этапе исполнения (`runtime`):
- Требуются: один единственный бинарный артефакт, конфигурационные файлы по умолчанию и корневые сертификаты TLS.
- Недопустимо наличие секретов сборки, приватных ключей, исходников или инструментов отладки.

Благодаря этому архитектурному паттерну обеспечивается изоляция процесса разработки от эксплуатации.

## Решение по шагам

1. Подготовьте проект с зависимостями.
2. Сформируйте `Dockerfile`, четко разграничивающий этап сборки и этап рантайма.
3. Соберите образ и убедитесь, что в итоговом образе отсутствуют файлы `main.go`, `go.mod` и тулчейн Go.
4. Проверьте содержимое файловой системы запущенного контейнера.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/info", func(w http.ResponseWriter, r *http.Request) {
		// Проверяем наличие компилятора go в runtime
		_, err := os.Stat("/usr/local/go/bin/go")
		hasGo := err == nil

		fmt.Fprintf(w, "Runtime isolation check. Go compiler present: %v\n", hasGo)
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Код для проверки отсутствия компилятора в рантайме

**`Dockerfile`**

```dockerfile
# === Stage 1: Build Environment ===
FROM golang:1.24-alpine AS builder
WORKDIR /workspace
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /workspace/app main.go

# === Stage 2: Runtime Environment ===
FROM alpine:3.20 AS runtime
WORKDIR /app
COPY --from=builder /workspace/app /app/app
EXPOSE 8080
ENTRYPOINT ["/app/app"]
```

ℹ️ Разделение builder и runtime

**`Терминал`**

```bash
# Сборка
docker build -t app-isolated:latest .

# Запуск
docker run -d -p 8080:8080 --name test-iso app-isolated:latest

# Проверка: Go compiler present: false
curl http://localhost:8080/info

# Проверка файлов в контейнере (нет исходников!)
docker exec test-iso ls -la /app

# Очистка
docker rm -f test-iso
```

## Под капотом

В Docker v2 (BuildKit) промежуточные стадии сборки кешируются отдельно. Если в коде поменялся только `main.go`, этап установки базовых пакетов в builder не пересчитывается. На шаге экспорта в OCI image tarball упаковщик сериализует только дельту последнего этапа `runtime`.

## Подводные камни

1. Случайное использование одного и того же тега базового образа для обоих этапов без очистки рабочей директории.
2. Использование директивы `ADD` вместо `COPY`, что может непреднамеренно распаковывать локальные архивы tar в рантайм.

## На собеседовании

**Вопрос с собеседования:** «Каким образом использование Multi-stage build предотвращает утечку приватных SSH-ключей и токенов доступа при сборке Go-модулей из закрытых репозиториев?»
**Ответ:** При передаче SSH-ключа или токена на этапе `builder` (например, через `--mount=type=secret` или `ARG`), эти данные используются только на первом этапе для `go mod download`. Финальный этап `runtime` стартует с чистого базового образа, куда копируется только скомпилированный бинарник. Секреты и промежуточные слои builder'а не попадают в граф слоев финального продакшн-образа.
