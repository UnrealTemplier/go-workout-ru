# Многоэтапный билд (Multi-stage build) на базе Alpine Linux

## Условие

Напиши **базовый Dockerfile** для Go-приложения: `FROM golang:1.24-alpine AS builder`, `WORKDIR /app`, `COPY go.mod go.sum .`, `RUN go mod download`, `COPY . .`, `RUN CGO_ENABLED=0 GOOS=linux go build -o main ./cmd/app`. Собери: `docker build -t myapp:v1 .`. Запусти: `docker run -p 8080:8080 myapp:v1`.

## Теория

Многоэтапная сборка (Multi-stage build), появившаяся в Docker 17.05+, позволяет использовать несколько директив `FROM` в одном файле `Dockerfile`.

Каждая инструкция `FROM` начинает новый этап сборки (stage) с отдельным базовым образом. Предыдущие этапы могут быть поименованы директивой `AS <name>` (например, `FROM golang:1.24-alpine AS builder`).
Ключевая возможность: селективное копирование артефактов из одного этапа в другой с помощью команды:
`COPY --from=builder /source/path /destination/path`

В контексте Go:
1. **Этап 1 (Builder):** используется образ `golang:1.24-alpine`. Здесь присутствуют все инструменты разработчика: компилятор Go, git для загрузки приватных модулей, заголовочные файлы.
2. **Флаг `CGO_ENABLED=0`:** критически важен при кросс-компиляции под Alpine (musl libc) или scratch. Он отключает динамическую линковку с libc, формируя 100% автономный ELF-бинарник.
3. **Этап 2 (Runtime):** используется минимальный образ `alpine:latest` (~5 МБ). В него копируется *только* бинарный файл приложения.

Результат: размер продакшн-образа снижается с **800+ МБ до 15–20 МБ**!

## Решение по шагам

1. Создайте структуру проекта: директория `cmd/app/main.go` и `go.mod`.
2. Напишите `Dockerfile` с этапами `AS builder` и финальным `FROM alpine:3.20`.
3. Убедитесь в наличии флага `CGO_ENABLED=0 GOOS=linux`.
4. Соберите образ: `docker build -t myapp:v1 .`.
5. Запустите: `docker run -d -p 8080:8080 myapp:v1`.
6. Проверьте размер через `docker images myapp:v1`.

## Код решения

**`cmd/app/main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Hello from Multi-stage Alpine Container!\n")
	})

	log.Println("Starting service on port :8080...")
	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatalf("Fatal error: %v", err)
	}
}
```

ℹ️ Точка входа Go-приложения

**`go.mod`**

```go
module example.com/multistage

go 1.24
```

ℹ️ Файл описания модуля Go

**`Dockerfile`**

```dockerfile
# Stage 1: Сборка бинарника
FROM golang:1.24-alpine AS builder

WORKDIR /app

# Кэширование загрузки модулей
COPY go.mod go.sum* ./
RUN go mod download

# Копирование исходного кода
COPY . .

# Компиляция чистого статического бинарника без CGO
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o main ./cmd/app

# Stage 2: Минимальный рантайм на Alpine
FROM alpine:3.20

WORKDIR /app

# Копирование только скомпилированного бинарника из builder stage
COPY --from=builder /app/main /app/main

EXPOSE 8080

ENTRYPOINT ["/app/main"]
```

ℹ️ Многоэтапный Dockerfile со сборкой в Alpine

**`Терминал`**

```bash
# Сборка образа myapp:v1
docker build -t myapp:v1 .

# Сравнение размера
docker images myapp:v1

# Запуск контейнера
docker run -d -p 8080:8080 --name app-v1 myapp:v1

# Проверка
curl http://localhost:8080

# Удаление
docker rm -f app-v1
```

## Под капотом

Сборщик Docker (BuildKit) строит направленный ациклический граф (DAG) этапов сборки. Все слои этапа `builder`, которые не были скопированы через `COPY --from=builder`, полностью отбрасываются из финального тарбола образа. Финальный образ состоит только из базовых слоев `alpine` и единственного слоя, добавляющего бинарник `/app/main`.

## Подводные камни

1. Забытый `CGO_ENABLED=0`: если компилировать в Debian-образе с glibc, а запускать в Alpine (musl), приложение упадет с ошибкой `standard_init_linux.go: exec user process caused "no such file or directory"`.
2. Копирование лишних файлов из builder stage (например, `COPY --from=builder /app .`), что снова загрязняет runtime.

## На собеседовании

**Вопрос с собеседования:** «Почему ошибка при запуске Go бинарника в Alpine контейнере часто выглядит как `no such file or directory`, хотя файл точно скопирован и имеет права 0755?»
**Ответ:** Это происходит, когда бинарник собран с включенным CGO на системе с GNU libc (`/lib/ld-linux-x86-64.so.2`). В Alpine Linux используется другая реализация стандартной библиотеки C — musl libc (`/lib/ld-musl-x86_64.so.1`). Ядро Linux пытается найти динамический загрузчик (ELF interpreter) для бинарника, не находит его и возвращает ошибку `ENOENT` (No such file or directory). Решение: собирать с `CGO_ENABLED=0`.
