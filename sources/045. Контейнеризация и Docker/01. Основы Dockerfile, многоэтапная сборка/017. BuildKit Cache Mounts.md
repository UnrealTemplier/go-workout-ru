# BuildKit Cache Mounts: ускорение сборки зависимостей в 10 раз

## Условие

Напиши **Dockerfile с BuildKit cache mounts**: `RUN --mount=type=cache,target=/go/pkg/mod go mod download`. Кэшируй `go mod download` между сборками даже при изменении кода. Ускорь CI сборку в 10 раз.

## Теория

Начиная с Docker 18.09 и сборщика **BuildKit** (включен по умолчанию в современных версиях Docker), появилась поддержка монтирования кэша:
`RUN --mount=type=cache,target=<path>`

В Go-разработке есть две ключевые директории кэша:
1. `/go/pkg/mod`: кэш скачанных исходных кодов Go-модулей (`GOPATH/pkg/mod`).
2. `/root/.cache/go-build`: кэш скомпилированных пакетов Go (`GOCACHE`).

Проблема классического кэширования слоев:
Если обновилась хотя бы одна библиотека в `go.mod`, весь слой `RUN go mod download` пересчитывается с нуля, скачивая все 100% зависимостей.

Преимущество `type=cache`:
Директория монтируется из специального хранилища BuildKit на хосте. Модули, скачанные в предыдущих сборках, **сохраняются на хосте даже при изменении `go.mod` и `main.go`**!
Компилятор Go переиспользует уже скомпилированные `.a` архивы из `GOCACHE`, что ускоряет сборку в CI/CD в 5–10 раз.

## Решение по шагам

1. Включите BuildKit (если не включен по умолчанию): `export DOCKER_BUILDKIT=1`.
2. Добавьте синтаксическую директиву `# syntax=docker/dockerfile:1` в начало Dockerfile.
3. Используйте `--mount=type=cache,target=/go/pkg/mod` для шага `go mod download`.
4. Используйте `--mount=type=cache,target=/root/.cache/go-build` для шага `go build`.
5. Проверьте скорость повторной сборки при изменении кода.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "BuildKit cache mount demo!\n")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Минимальный микросервис

**`Dockerfile`**

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.24-alpine AS builder

WORKDIR /src

COPY go.mod go.sum* ./

# Кэширование загрузки модулей через специальный mount
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .

# Кэширование скомпилированных пакетов компилятора Go
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app .

FROM alpine:3.20
COPY --from=builder /bin/app /bin/app
EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

ℹ️ Dockerfile с использованием BuildKit Cache Mounts

**`Терминал`**

```bash
# Включаем BuildKit
export DOCKER_BUILDKIT=1

# Сборка с BuildKit
docker build -t app-buildkit:v1 .

# Вносим изменение в код
touch main.go

# Повторная сборка использует кэш компилятора из /root/.cache/go-build мгновенно!
docker build -t app-buildkit:v2 .
```

## Под капотом

BuildKit монтирует локальное файловое хранилище хоста (`/var/lib/docker/buildkit/cache`) в указанную точку монтирования на время исполнения контейнера сборщика. Содержимое этого каталога не записывается в итоговый слой образа (в слое остается только бинарник `/bin/app`), что дает максимальную скорость без раздувания размера образа.

## Подводные камни

1. Забыть указать монтирование кэша модулей на шаге `go build`: если `go build` обратится к модулям, а смонтирован только `GOCACHE`, модули не будут найдены в слое.
2. Недоступность BuildKit на устаревших версиях демона Docker.

## На собеседовании

**Вопрос с собеседования:** «В чем принципиальная разница между кэшированием слоев через `COPY go.mod . && RUN go mod download` и кэшированием через `RUN --mount=type=cache` в BuildKit?»
**Ответ:** Кэширование слоев инвалидируется целиком при изменении файла `go.mod` (добавлении или обновлении хотя бы одной библиотеки), требуя повторной загрузки всех модулей. Кэш-маунты BuildKit сохраняют директорию кэша на диске хоста независимо от состояния слоев. При изменении `go.mod` скачивается только новая дельта зависимостей, а все старые библиотеки и скомпилированные пакеты мгновенно берутся из кэша хоста.
