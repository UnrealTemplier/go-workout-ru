# Использование golang:alpine вместо golang:latest в builder stage

## Условие

Используйте `golang:1.22-alpine` вместо `golang:1.22` для builder stage — это уменьшит размер и ускорит сборку.

## Теория

Выбор базового образа для этапа `builder` оказывает колоссальное влияние на производительность сборочных конвейеров (CI/CD pipelines).

Сравнение базовых builder-образов:
1. `golang:1.24` (на базе Debian):
   - Размер: **~850 МБ**.
   - Пакетный менеджер: `apt` (медленный, требует `apt-get update`).
   - Используется, когда приложению необходим CGO с GNU libc или сложные системные библиотеки сборки.
2. `golang:1.24-alpine`:
   - Размер: **~250 МБ** (в 3.5 раза меньше!).
   - Пакетный менеджер: `apk` (молниеносная установка пакетов).
   - Идеален для сборки чистых Go-приложений (`CGO_ENABLED=0`).

В CI-агентах (GitLab Runner, GitHub Actions) скачивание `golang:alpine` занимает 2–4 секунды вместо 25–40 секунд для полного Debian-образа, что суммарно экономит часы времени команды при десятках сборок в день.

## Решение по шагам

1. Создайте файл `Dockerfile` с этапом `FROM golang:1.24-alpine AS builder`.
2. При необходимости установите утилиты сборки через `apk add --no-cache git ca-certificates tzdata`.
3. Соберите приложение с флагом `CGO_ENABLED=0`.
4. Сравните скорость pull базового образа и итоговую легковесность сборочного пайплайна.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Built with golang:alpine builder!\n")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Тестовый HTTP сервис

**`Dockerfile`**

```dockerfile
# Быстрый и легковесный builder на базе Alpine Linux (~250MB)
FROM golang:1.24-alpine AS builder

# Установка git и корневых сертификатов без сохранения кэша apk
RUN apk add --no-cache git ca-certificates tzdata

WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

# Финальный runtime
FROM alpine:3.20
COPY --from=builder /usr/share/zoneinfo /usr/share/zoneinfo
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /bin/app /bin/app

EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

ℹ️ Dockerfile с оптимальным builder'ом на Alpine

**`Терминал`**

```bash
# Сборка
docker build -t app-alpine-builder:latest .

# Сравнение базовых образов в локальном кэше
docker images "golang:*"

# Запуск
docker run -d -p 8080:8080 --name test-alp app-alpine-builder:latest
curl http://localhost:8080
docker rm -f test-alp
```

## Под капотом

Дистрибутив Alpine построен на базе `musl libc` и `busybox`. Он не содержит тяжелых библиотек локализации (`glibc-locale`), документации (`man-pages`) и громоздких утилит. Установка пакетов через `apk --no-cache` не создает временных индексных файлов на диске, уменьшая нагрузку на дисковый ввод-вывод.

## Подводные камни

1. Забытый флаг `--no-cache` в `apk add`: индекс пакетов `/var/cache/apk/*` остается в слое builder'а.
2. Попытка сборки CGO-кода, завязанного на специфические расширения GNU glibc, без предварительной проверки совместимости с musl.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях нельзя использовать `golang:alpine` для сборки Go-приложений и приходится оставаться на стандартном образе `golang:debian`?»
**Ответ:** Когда проекту необходим CGO с динамической линковкой под хостовые системы на базе glibc (например, проприетарные драйверы Oracle, специфические криптобиблиотеки, биндинги C++ библиотек с libstdc++, или плагины `go plugin`, требующие строго совпадающих версий компилятора и glibc).
