# Полностью статический бинарник: флаги компилятора -ldflags='-w -s' и CGO_ENABLED=0

## Условие

Соберите полностью статический бинарник: `CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -ldflags="-w -s" -o app`.

## Теория

Сборка полностью автономного статического бинарника в Go опирается на две ключевые концепции:

1. **`CGO_ENABLED=0`:**
   По умолчанию компилятор Go может динамически линковаться с libc хоста при использовании стандартных пакетов `net` (системный DNS резолвер `cgo`) и `os/user`.
   Переменная `CGO_ENABLED=0` принудительно переключает Go на чистый внутренний Go-резолвер (`netgo`) и внутреннюю реализацию работы с пользователями (`osusergo`). Бинарник становится абсолютно статическим ELF-файлом (`statically linked`).

2. **Флаги линковщика `-ldflags="-w -s"`:**
   - `-w`: отключает генерацию отладочной DWARF-информации (размер стектрейсов и отладчика `gdb`).
   - `-s`: удаляет таблицу символов (Symbol Table) из бинарника.
   Эти флаги сокращают размер скомпилированного файла на **30–50%** без влияния на производительность и вывод имен функций в runtime-паниках Go.

Утилита `file <binary>` в Linux позволяет подтвердить статический статус: вывод `statically linked` гарантирует запуск в любом дистрибутиве и в `scratch`.

## Решение по шагам

1. Напишите Go-сервис.
2. Скомпилируйте бинарник стандартной командой `go build` и проверьте его через `file` и `ldd`.
3. Скомпилируйте бинарник с `CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s"`.
4. Сравните размеры файлов и убедитесь, что `ldd` возвращает `not a dynamic executable`.
5. Упакуйте полученный бинарник в контейнер.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Statically linked Go application running!")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Минимальный микросервис

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

WORKDIR /src
COPY main.go .

# Сборка полностью статического бинарника со сжатием символов
RUN CGO_ENABLED=0 GOOS=linux go build \
    -a \
    -installsuffix cgo \
    -ldflags="-w -s" \
    -o /bin/app main.go

FROM scratch
COPY --from=builder /bin/app /app
EXPOSE 8080
ENTRYPOINT ["/app"]
```

ℹ️ Статическая сборка для scratch

**`Терминал`**

```bash
# Локальная проверка связывания
CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o app-static main.go
file app-static
# Вывод: ELF 64-bit LSB executable, ..., statically linked, stripped

# Проверка динамических библиотек (должно вернуть 'not a dynamic executable')
ldd app-static || echo "Verified: Fully static!"

# Сборка контейнера
docker build -t app-static:latest .
docker images app-static:latest
```

## Под капотом

В ELF заголовке файла (`readelf -l app-static`) при статической линковке отсутствует сегмент `INTERP` (путь к динамическому загрузчику `/lib64/ld-linux-x86-64.so.2`). Ядро загружает код сразу в адресное пространство процесса без участия userspace-линковщика, что исключает любые зависимости от библиотек файловой системы контейнера.

## Подводные камни

1. Флаг `-s` удаляет таблицу символов, из-за чего профилировщики `pprof` без исходного бинарника не смогут восстановить символические имена функций в сторонних тулах.
2. При использовании CGO (например, go-sqlite3) `CGO_ENABLED=0` вызовет ошибку компиляции.

## На собеседовании

**Вопрос с собеседования:** «Что делает флаг `-ldflags="-w -s"` при сборке Go и влияет ли он на способность Go выводить стек вызовов при panic?»
**Ответ:** Флаг `-w` вырезает DWARF-информацию для внешних отладчиков, а `-s` удаляет стандартную таблицу символов ELF. Однако рантайм Go сохраняет свою внутреннюю таблицу pclntab (program counter line table), поэтому при `panic()` Go по-прежнему выводит полный стек вызовов с именами функций, именами файлов и номерами строк. Производительность приложения также не меняется.
