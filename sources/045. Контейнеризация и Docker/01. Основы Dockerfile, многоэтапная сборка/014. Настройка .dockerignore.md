# Настройка .dockerignore: оптимизация build context и безопасность

## Условие

Настрой **.dockerignore**: исключи `*.md`, `.git/`, `vendor/`, `*_test.go`, `.env`, `docker-compose.yml`. Покажи, что уменьшает build context и ускоряет сборку.

## Теория

При выполнении команды `docker build .` клиент Docker упаковывает всю текущую директорию в tar-архив и передает его демону Docker по протоколу HTTP/gRPC. Этот объем данных называется **Build Context** (контекст сборки).

Если в проекте нет файла `.dockerignore`:
1. В контекст сборки попадает папка `.git/` (сотни мегабайт истории, коммитов и веток).
2. Попадают локальные бинарники, дампы памяти (`core`), логи, папка `vendor/` и временные файлы IDE (`.idea/`, `.vscode/`).
3. Попадают конфиденциальные файлы окружения: `.env`, приватные ключи `.pem`, `id_rsa`.

Файл `.dockerignore` работает аналогично `.gitignore` и исключает указанные файлы и директории еще на стороне клиента Docker до отправки контекста демону.

Преимущества `.dockerignore`:
- Ускорение старта сборки (передача контекста за 0.05 сек вместо 15–30 сек).
- Предотвращение случайной утечки паролей и секретов в слои образа.
- Эффективное кэширование (изменение локального README не сбрасывает кэш сборки).

## Решение по шагам

1. Создайте в корне проекта файл `.dockerignore`.
2. Добавьте в него исключения для `.git`, `.env`, `*.md`, `bin/`, `tmp/`, `docker-compose*.yml`.
3. Запустите `docker build` и посмотрите на размер отправленного контекста: `Sending build context to Docker daemon ...`.
4. Убедитесь, что контекст сборки уменьшился до десятков килобайт.

## Код решения

**`.dockerignore`**

```dockerignore
# Системы контроля версий
.git
.gitignore

# Секреты и локальные переменные окружения
.env*
*.pem
*.key

# Локальные бинарники и кэш сборки
bin/
build/
*.exe
*.test

# Тесты и документация
*_test.go
*.md
docs/

# IDE и редакторы
.idea/
.vscode/
*.swp

# Docker и Compose файлы
docker-compose*.yml
Dockerfile*
Makefile
```

ℹ️ Production-шаблон .dockerignore для Go-проекта

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app main.go

FROM scratch
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile, использующий отфильтрованный контекст

**`Терминал`**

```bash
# Создадим фиктивный тяжелый файл, который должен игнорироваться
dd if=/dev/zero of=large_dump.bin bs=1M count=100

# Добавим его в .dockerignore
echo "large_dump.bin" >> .dockerignore

# Сборка: обратите внимание на объем контекста сборки (менее 100KB)
docker build -t test-ignore:latest .

# Очистка
rm -f large_dump.bin
```

## Под капотом

CLI-клиент Docker перед отправкой запроса к Docker Daemon парсит `.dockerignore` с помощью синтаксиса filepath.Match. Файлы, удовлетворяющие шаблонам, исключаются из формируемого потока (stream) tar-архива в памяти. Демон даже не узнает о существовании этих файлов на хосте.

## Подводные камни

1. Отсутствие `.env` в `.dockerignore`: файл попадает в слой образа при выполнении `COPY . .`, раскрывая пароли от production БД любому, у кого есть доступ к registry.
2. Не исключен `.git`: образ становится гигантским, а кэш инвалидируется при каждом `git commit`.

## На собеседовании

**Вопрос с собеседования:** «К каким последствиям приводит отсутствие файла `.dockerignore` в репозитории с активной разработкой при сборках в CI/CD?»
**Ответ:** 1) Утечка секретов и истории `.git` в продакшн-образы. 2) Резкое замедление сборок из-за передачи сотен мегабайт локального мусора по сети на Docker daemon. 3) Полный сброс кэша слоев на шаге `COPY . .` при изменении любого несущественного файла (например, обновление документации `README.md` или изменение локальной ветки в `.git/HEAD`).
