# Многоэтапная сборка с переходом на scratch / alpine

## Условие

Напишите `Dockerfile` для Go-приложения с multi-stage сборкой: первый stage собирает бинарник, второй — минимальный образ на `scratch` или `alpine`.

## Теория

Образ `scratch` — это специальный псевдо-базовый образ Docker, который имеет **нулевой размер** (`0 bytes`).
Директива `FROM scratch` сообщает Docker, что следующий этап сборки не наследует никакую операционную систему, пакеты или файловую иерархию.

При сборке в `scratch`:
- В образе нет ничего: ни `/bin/sh`, ни `/bin/ls`, ни менеджеров пакетов, ни стандартных C-библиотек.
- Исполняемый файл приложения является единственным файлом в контейнере.
- Итоговый размер образа равен точно размеру скомпилированного Go-бинарника (обычно 8–15 МБ).

Для успешной работы в `scratch` бинарник обязан быть статически слинкован (`CGO_ENABLED=0`).
Если сервису требуется утилита для отладки или `sh` для выполнения команд health check в Kubernetes/Docker, вместо `scratch` выбирают `alpine` (~5 МБ).

## Решение по шагам

1. Напишите HTTP-сервер на Go.
2. Создайте `Dockerfile` с этапом сборки `AS builder` на `golang:1.24-alpine`.
3. Укажите компиляцию со статическим связыванием `CGO_ENABLED=0`.
4. Во втором этапе укажите `FROM scratch`.
5. Скопируйте скомпилированный бинарник через `COPY --from=builder /app/service /service`.
6. Укажите точку входа `ENTRYPOINT ["/service"]` и соберите образ.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Running on pure scratch image!\n")
	})

	log.Println("Server running on port 8080...")
	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatalf("Server error: %v", err)
	}
}
```

ℹ️ Минималистичный сервис для запуска в scratch

**`Dockerfile`**

```dockerfile
# Этап 1: Сборка
FROM golang:1.24-alpine AS builder

WORKDIR /build

COPY main.go .

# Собираем статический бинарник без CGO с удалением DWARF и таблицы символов
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o service main.go

# Этап 2: Пустой образ scratch
FROM scratch

# Копируем бинарник из первого этапа
COPY --from=builder /build/service /service

# Порт
EXPOSE 8080

# Запуск напрямую
ENTRYPOINT ["/service"]
```

ℹ️ Dockerfile с целевым образом scratch

**`Терминал`**

```bash
# Сборка образа
docker build -t app-scratch:latest .

# Проверка размера (размер будет около 6-10 MB!)
docker images app-scratch:latest

# Запуск
docker run -d -p 8080:8080 --name test-scratch app-scratch:latest

# Проверка ответа
curl http://localhost:8080

# Очистка
docker rm -f test-scratch
```

## Под капотом

Когда ядро Linux стартует контейнер на базе `scratch`, оно создает корневой каталог (`rootfs`) из единственного слоя, где лежит только `/service`. Процесс стартует напрямую через системный вызов `execve("/service", ...)`. Никаких оболочек bash/sh не вызывается, что дает мгновенный старт контейнера (миллисекунды).

## Подводные камни

1. Использование shell-формы `CMD /service`: в scratch нет `/bin/sh`, поэтому контейнер немедленно упадет с ошибкой `exec: "/bin/sh": stat /bin/sh: no such file or directory`. Обязательно используйте exec-форму `ENTRYPOINT ["/service"]`.
2. Попытка выполнить `docker exec -it <container> sh` для отладки: в scratch нет командной строки.

## На собеседовании

**Вопрос с собеседования:** «Почему в образе `FROM scratch` невозможно запустить скрипт или команду вида `CMD /app`?»
**Ответ:** Запись `CMD /app` интерпретируется Docker как вызов через шелл: `/bin/sh -c "/app"`. В образе `scratch` нет ни одного системного файла и отсутствует `/bin/sh`. Docker вернет ошибку отсутствия файла `/bin/sh`. Запуск возможен только через exec-синтаксис JSON-массива: `ENTRYPOINT ["/app"]`.
