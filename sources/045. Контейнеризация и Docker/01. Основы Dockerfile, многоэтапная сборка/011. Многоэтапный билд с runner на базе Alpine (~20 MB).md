# Многоэтапный билд с runner на базе Alpine (~20 MB)

## Условие

**[Multi-stage build]**: Раздели Dockerfile на 2 этапа: `builder` (где компилируется бинарник) и `runner` (где бинарник запускается, например, `FROM alpine`). Убедись, что размер образа уменьшился до ~20MB.

## Теория

Схема `builder -> runner (Alpine)` является общепринятым стандартом для микросервисов, которым требуется минимальная операционная среда.

В отличие от `scratch`, образ `alpine:3.20`:
1. Предоставляет утилиту командной строки `sh` (BusyBox) для запуска скриптов миграций, ожидания баз данных (`wait-for-it`) и проверки здоровья (`wget --spider`).
2. Имеет встроенную структуру каталогов `/etc`, `/tmp`, `/var/run`.
3. Позволяет установить дополнительные утилиты (`ca-certificates`, `tzdata`, `curl`) при необходимости.
4. Весит всего **~7 МБ** в распакованном виде, а вместе с оптимизированным Go-бинарником итоговый размер образа составляет около **15–20 МБ**.

## Решение по шагам

1. Напишите HTTP-сервис на Go с обработчиком graceful shutdown.
2. Создайте `Dockerfile` с этапами `builder` и `runner`.
3. В этапе `runner` используйте образ `alpine:3.20`.
4. Соберите образ и убедитесь, что размер не превышает 20 МБ.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		fmt.Fprintln(w, "healthy")
	})

	log.Println("Runner started on :8080")
	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatal(err)
	}
}
```

ℹ️ Микросервис с эндпоинтом проверки здоровья

**`Dockerfile`**

```dockerfile
# Stage 1: Builder
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

# Stage 2: Runner
FROM alpine:3.20 AS runner
WORKDIR /app
COPY --from=builder /bin/app /app/app

EXPOSE 8080
ENTRYPOINT ["/app/app"]
```

ℹ️ Двухэтапная сборка: builder + runner на Alpine

**`Терминал`**

```bash
# Сборка
docker build -t app-runner:v1 .

# Проверка размера образа (должно быть < 20MB)
docker images app-runner:v1 --format "{{.Repository}}: {{.Size}}"

# Запуск
docker run -d -p 8080:8080 --name test-run app-runner:v1
curl http://localhost:8080/health
docker rm -f test-run
```

## Под капотом

Финальный тарбол образа состоит всего из двух слоев: нижний слой — это образ Alpine (rootfs с busybox, musl и базовыми конфигами), а верхний слой — единственный файл `/app/app`. Суммарная контрольная сумма манифеста OCI регистрируется в Docker Registry с минимальным сетевым оверхедом.

## Подводные камни

1. Забыть скомпилировать бинарник с `CGO_ENABLED=0`: динамически слинкованный бинарник под glibc не запустится на Alpine (musl).
2. Запуск контейнера под пользователем root без необходимости.

## На собеседовании

**Вопрос с собеседования:** «Когда в качестве runner-образа следует предпочесть `alpine`, а не `scratch`?»
**Ответ:** `alpine` выбирают, если: 1) Требуется запуск вспомогательных шелл-скриптов перед стартом сервиса (например, ожидание готовности СУБД или генерация конфигураций). 2) Нужен шелл для проведения регламентных работ или отладки в dev/stage окружениях. 3) Сервис использует Health Check через системную утилиту `wget` или `curl`. Если ничего из этого не требуется, выбирают `scratch` или `distroless`.
