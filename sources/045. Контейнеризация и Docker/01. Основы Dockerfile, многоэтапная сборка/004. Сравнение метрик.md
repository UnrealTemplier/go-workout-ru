# Сравнение метрик: Single-stage образ против Multi-stage и аудит размера

## Условие

Напиши простейший `Dockerfile` для Go-приложения (один этап `FROM golang:1.22`, `go build`, `CMD`). Запусти через `docker run`. Обрати внимание на размер образа (он будет огромным, ~800MB).

## Теория

Размер Docker-образа напрямую влияет на жизненный цикл приложения в продакшне:
1. **Network I/O & Registry Bandwidth:** При раскатке нового релиза на 50 нод Kubernetes передача 800 МБ потребует 40 ГБ сетевого трафика. Для 15 МБ образа — всего 750 МБ (разница более чем в 50 раз!).
2. **Утилизация диска нод (Disk I/O & Storage):** Контейнерный рантайм (containerd / CRI-O) хранит слои образов в `/var/lib/containerd`. Тяжелые образы быстрее приводят к срабатыванию Garbage Collection образов кублета и eviction подов.
3. **Безопасность (Vulnerabilities):** Одноэтапный образ `golang:1.22` тянет за собой около 100-200 известных уязвимостей (CVE) в пакетах Debian (systemd, openssl, tar, bash, coreutils). Минимальный образ содержит от 0 до 2 CVE.

Команда `docker history <image>` позволяет послойно проанализировать вклад каждой директивы в суммарный объем образа.

## Решение по шагам

1. Создайте файл `Dockerfile.heavy` для одноэтапной сборки.
2. Создайте файл `Dockerfile.light` для multi-stage сборки.
3. Соберите оба образа: `myapp:heavy` и `myapp:light`.
4. Сравните их размер через `docker images | grep myapp`.
5. Выполните детальный послойный аудит через `docker history myapp:heavy` и `docker history myapp:light`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/ping", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "pong")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Минимальный микросервис

**`Dockerfile.heavy`**

```dockerfile
FROM golang:1.24
WORKDIR /src
COPY main.go .
RUN go build -o /bin/app main.go
CMD ["/bin/app"]
```

ℹ️ Одноэтапный тяжелый Dockerfile (~850 MB)

**`Dockerfile.light`**

```dockerfile
FROM golang:1.24-alpine AS build
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /bin/app main.go

FROM alpine:3.20
COPY --from=build /bin/app /bin/app
CMD ["/bin/app"]
```

ℹ️ Multi-stage легкий Dockerfile (~15 MB)

**`Терминал`**

```bash
# Сборка тяжелого образа
docker build -f Dockerfile.heavy -t myapp:heavy .

# Сборка легкого образа
docker build -f Dockerfile.light -t myapp:light .

# Сравнение размеров
docker images myapp:heavy myapp:light --format "table {{.Repository}}:{{.Tag}}\t{{.Size}}"

# Послойный аудит
docker history myapp:heavy
docker history myapp:light
```

## Под капотом

В `docker history` видно, что базовый слой `golang:1.24` добавляет свыше 700 МБ еще до выполнения каких-либо команд пользователя. Команда `go build` внутри контейнера также генерирует промежуточный кэш компилятора в `$HOME/.cache/go-build`, который в single-stage сборке навсегда остается зафиксированным в слое `RUN`.

## Подводные камни

1. Попытка очистить кэш в отдельном `RUN`: `RUN rm -rf /root/.cache` после `RUN go build` создает новый слой с whiteout-записями, не освобождая место в предыдущем слое.
2. Неиспользование флагов линковщика `-ldflags="-w -s"`, что оставляет в бинарнике отладочную DWARF-информацию (увеличивает размер бинарника на 25-40%).

## На собеседовании

**Вопрос с собеседования:** «Каковы практические последствия использования тяжелых Docker-образов в HighLoad кластере Kubernetes на 500 нод?»
**Ответ:** 1) Высокая нагрузка на сеть и локальный Registry (Saturation). 2) Длинный Time-To-Ready при Horizontal Pod Autoscaler (HPA), когда поды не успевают подняться во время всплеска трафика (Spike). 3) Быстрое заполнение дисков нод (`DiskPressure`), приводящее к аварийному выселению (Eviction) других критических подов.
