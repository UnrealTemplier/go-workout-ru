# ENTRYPOINT против CMD: корректная передача CLI-аргументов и сигналов

## Условие

Используйте `ENTRYPOINT` вместо `CMD` для бинарника, чтобы аргументы при запуске контейнера добавлялись к основной команде, а не заменяли её.

## Теория

Различие между директивами `ENTRYPOINT` и `CMD` часто вызывает путаницу, но является базой проектирования контейнеров:

1. **`ENTRYPOINT` (Исполняемый бинарник):**
   - Задает неизменяемую команду/бинарник, который будет запущен при старте контейнера.
   - Все аргументы, переданные в команду `docker run <image> [args...]`, **добавляются к ENTRYPOINT**, а не замещают его.

2. **`CMD` (Аргументы по умолчанию):**
   - Задает аргументы по умолчанию для `ENTRYPOINT`.
   - Если пользователь передает аргументы в `docker run`, они **полностью перезаписывают `CMD`**.

3. **Exec-форма против Shell-формы:**
   - **Exec-форма (JSON array):** `ENTRYPOINT ["/app", "serve"]` — процесс запускается напрямую как **PID 1**, корректно получая сигналы `SIGTERM` для Graceful Shutdown.
   - **Shell-форма:** `ENTRYPOINT /app serve` — процесс запускается как дочерний для `/bin/sh -c`. Сигналы ОС не доходят до Go-процесса, и Docker убивает контейнер через 10 секунд по `SIGKILL`!

## Решение по шагам

1. Напишите Go CLI-приложение с поддержкой флагов и подкоманд (`serve`, `migrate`, `version`).
2. Опишите `Dockerfile`, где `ENTRYPOINT` указывает на бинарник, а `CMD` задает параметры по умолчанию (`["--port", "8080"]`).
3. Запустите контейнер без аргументов: проверьте запуск с дефолтными параметрами.
4. Запустите контейнер с кастомными аргументами: `docker run myapp --port 9090`.

## Код решения

**`main.go`**

```go
package main

import (
	"flag"
	"fmt"
	"net/http"
	"os"
)

func main() {
	port := flag.String("port", "8080", "HTTP server port")
	mode := flag.String("mode", "production", "Application run mode")
	flag.Parse()

	// Если передана подкоманда
	if len(flag.Args()) > 0 && flag.Args()[0] == "version" {
		fmt.Println("App Version: v1.0.0")
		os.Exit(0)
	}

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "App running in %s mode on port :%s\n", *mode, *port)
	})

	fmt.Printf("Starting server on port :%s in %s mode...\n", *port, *mode)
	_ = http.ListenAndServe(":"+*port, nil)
}
```

ℹ️ Go CLI сервис с поддержкой флагов командной строки

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /bin/app main.go

FROM scratch

COPY --from=builder /bin/app /app

EXPOSE 8080

# ENTRYPOINT задает исполняемый файл
ENTRYPOINT ["/app"]

# CMD задает аргументы по умолчанию (могут быть переопределены пользователем)
CMD ["--port", "8080", "--mode", "default"]
```

ℹ️ Идеальное сочетание ENTRYPOINT и CMD

**`Терминал`**

```bash
# Сборка
docker build -t app-cli-demo:v1 .

# Запуск по умолчанию (используются аргументы из CMD: --port 8080)
docker run -d -p 8080:8080 --name test-def app-cli-demo:v1
curl http://localhost:8080
docker rm -f test-def

# Запуск с переопределением флагов командной строки
docker run -d -p 9090:9090 --name test-custom app-cli-demo:v1 --port 9090 --mode test
curl http://localhost:9090
docker rm -f test-custom

# Запуск подкоманды
docker run --rm app-cli-demo:v1 version
```

## Под капотом

Docker объединяет массивы `Entrypoint` и `Cmd` из метаданных контейнера в единый срез аргументов `args = append(Entrypoint, Cmd...)` и передает его в системный вызов `execve(args[0], args, env)`. При этом процесс Go становится процессом-инициализатором (PID 1) в изолированном пространстве имен PID.

## Подводные камни

1. Использование shell-формы `CMD /app`: контейнер не реагирует на `SIGTERM` при `docker stop`.
2. Путаница между замещением `ENTRYPOINT` (требуется флаг `--entrypoint`) и `CMD` (достаточно дописать аргументы в конце команды `docker run`).

## На собеседовании

**Вопрос с собеседования:** «Что произойдет при выполнении команды `docker stop <container>`, если в Dockerfile использовалась shell-форма `CMD ./app` вместо exec-формы `CMD ["./app"]`?»
**Ответ:** При shell-форме Docker запускает команду через командный процессор: `/bin/sh -c "./app"`. В результате PID 1 получает процесс `sh`, а само Go-приложение становится дочерним процессом. Процесс `/bin/sh` в Linux по умолчанию не пересылает сигналы `SIGTERM` своим дочерним процессам. Go-сервер не получит сигнал, не сможет выполнить Graceful Shutdown и завершить активные транзакции. Через 10 секунд (дефолтный таймаут) Docker принудительно убьет процесс сигналом `SIGKILL`.
