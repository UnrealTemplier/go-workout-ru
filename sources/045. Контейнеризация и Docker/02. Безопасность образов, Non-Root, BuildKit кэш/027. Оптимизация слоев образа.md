# Оптимизация слоев образа: объединение команд RUN и минимизация размера

## Условие

Оптимизируй **image layers**: минимизируй количество `RUN` команд (но не жертвуй читаемостью). Используй `&&` для объединения. Покажи `docker history myapp:v1` — каждый слой добавляет размер.

## Теория

Каждая инструкция `RUN`, `COPY` и `ADD` в `Dockerfile` создает новый физический слой в файловой системе OverlayFS.

Антипаттерн создания мусорных слоев:
```dockerfile
RUN apk update
RUN apk add curl
RUN rm -rf /var/cache/apk/*
```
В этой конфигурации создаются **3 отдельных слоя**.
Пакеты, установленные в слое 2, физически останутся в tar-архиве слоя 2! Команда `rm` в слое 3 лишь создаст whiteout-записи, скрывающие файлы, но **не уменьшит размер образа ни на байт**.

Паттерн оптимизации (Layer Flattening):
Команды обновления, установки и немедленной очистки кэша объединяются через логический оператор `&&` в рамках одного шага `RUN`:
```dockerfile
RUN apk update && \
    apk add --no-cache ca-certificates tzdata && \
    rm -rf /var/cache/apk/*
```
Это гарантирует, что временные файлы и индексы удаляются ДО фиксации слоя на диске.

## Решение по шагам

1. Напишите неоптимальный Dockerfile с несколькими командами `RUN`.
2. Напишите оптимизированный Dockerfile с объединенным `RUN`.
3. Соберите оба образа и сравните послойную историю через `docker history`.

## Код решения

**`Dockerfile.bad`**

```dockerfile
FROM alpine:3.20
# Плохой подход: создает 3 слоя, временные файлы зафиксированы в слое 2
RUN apk update
RUN apk add curl
RUN rm -rf /var/cache/apk/*
```

ℹ️ Неоптимальный Dockerfile с раздутыми слоями

**`Dockerfile.good`**

```dockerfile
FROM alpine:3.20
# Хороший подход: все выполняется в одном слое с немедленной очисткой
RUN apk add --no-cache curl ca-certificates
```

ℹ️ Оптимизированный Dockerfile с чистым слоем

**`Терминал`**

```bash
# Сборка обоих образов
docker build -f Dockerfile.bad -t test-layers:bad .
docker build -f Dockerfile.good -t test-layers:good .

# Сравнение послойного размера
docker history test-layers:bad
docker history test-layers:good
```

## Под капотом

OverlayFS фиксирует состояние верхнего каталога `upperdir` только в момент завершения выполнения текущей директивы `RUN`. Если файл был создан и удален в рамках одной bash-сессии, он никогда не будет записан в результирующий diff-архив слоя.

## Подводные камни

1. Чрезмерное объединение команд в ущерб читаемости Dockerfile.
2. Пропуск флага `--no-cache` в пакетном менеджере `apk` (Alpine) или отсутствие очистки `/var/lib/apt/lists/*` в Debian/Ubuntu.

## На собеседовании

**Вопрос с собеседования:** «Почему удаление временных файлов сборщика в отдельной инструкции `RUN rm -rf ...` не уменьшает размер итогового Docker-образа?»
**Ответ:** Слои в Docker иммутабельны (неизменяемы). Каждый слой хранит только дельту (diff) относительно предыдущего. Если файл был записан в слое N, он физически присутствует в архиве слоя N. Инструкция `RUN rm` в слое N+1 лишь помещает специальную метку whiteout в слой N+1, скрывающую файл при монтировании файловой системы, но общий вес контейнера увеличивается на размер самого слоя N+1.
