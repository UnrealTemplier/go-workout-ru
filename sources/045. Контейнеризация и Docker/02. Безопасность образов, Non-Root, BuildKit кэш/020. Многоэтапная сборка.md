# Многоэтапная сборка: оптимизация с переходом на Alpine и сравнение веса

## Условие

**Многоэтапная сборка (Multi-stage Dockerfile)**: Оптимизируйте Dockerfile из предыдущей задачи с помощью многоэтапной сборки (Multi-stage):
* Этап 1 (`AS builder`): Используйте тяжелый образ `golang:1.26-alpine` для загрузки зависимостей и компиляции бинарника.
* Этап 2: Возьмите чистый легковесный образ `alpine:latest`, скопируйте в него *только* скомпилированный на первом этапе бинарный файл и укажите его в `ENTRYPOINT`.
Соберите образ и сравните его размер с предыдущим (размер должен упасть до 15–30 МБ).

## Теория

Многоэтапная сборка (Multi-stage build) позволяет объединить в одном репозитории тяжелое окружение компиляции и чистое легковесное окружение исполнения.

На первом этапе (`FROM golang:1.24-alpine AS builder`) используются компилятор Go, заголовочные файлы и кэш пакетов.
На втором этапе (`FROM alpine:3.20`) создается чистый образ, куда из builder-этапа переносится исключительно бинарный файл через `COPY --from=builder /app/main /app/main`.

Такое разделение позволяет сократить размер итогового контейнера с 800+ МБ до **15–30 МБ**, сохраняя при этом наличие командной оболочки `sh` и утилит Busybox, необходимых для эксплуатации в ряде систем.

## Решение по шагам

1. Создайте Go-приложение с веб-сервером.
2. Напишите `Dockerfile` с этапами `builder` на базе `golang:1.24-alpine` и `alpine:3.20` для рантайма.
3. Укажите флаги компиляции `CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s"`.
4. Соберите образ и сравните его размер с тяжелым single-stage образом.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "High-performance Go service in Alpine runtime!\n")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Минимальный веб-сервис

**`Dockerfile`**

```dockerfile
# Этап 1: Builder
FROM golang:1.24-alpine AS builder

WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

# Этап 2: Минимальный Runtime
FROM alpine:3.20

WORKDIR /app
COPY --from=builder /bin/app /app/app

EXPOSE 8080
ENTRYPOINT ["/app/app"]
```

ℹ️ Многоэтапный Dockerfile для перехода на Alpine

**`Терминал`**

```bash
# Сборка многоэтапного образа
docker build -t app-alpine-optimized:v1 .

# Проверка размера (образ весит ~15-20 MB)
docker images app-alpine-optimized:v1 --format "{{.Repository}}: {{.Size}}"

# Запуск
docker run -d -p 8080:8080 --name test-alp-opt app-alpine-optimized:v1
curl http://localhost:8080
docker rm -f test-alp-opt
```

## Под капотом

Сборщик Docker BuildKit анализирует дерево зависимостей этапов. Он видит, что из этапа `builder` во второй этап запрашивается только файл `/bin/app`. Все остальные временные слои, сгенерированные шагами `RUN go build` и скачиванием компилятора, остаются в builder cache и не включаются в экспортируемый tar-манифест.

## Подводные камни

1. Забыть скомпилировать бинарник со статическим связыванием: если CGO включен, бинарник будет требовать динамические библиотеки musl соответствующей версии.
2. Копирование всей папки `/src` вместо скомпилированного бинарника.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go многоэтапная сборка дает больший выигрыш в размере и безопасности, чем в языках Python или Node.js?»
**Ответ:** Go — компилируемый язык со статической типизацией и автономным рантаймом. На этапе исполнения Go не требует виртуальной машины, интерпретатора, исходных кодов (`node_modules`, `site-packages`) и системных динамических библиотек. В образ помещается один скомпилированный машинный код, что позволяет уменьшить размер образа до единиц мегабайт и свести attack surface к нулю.
