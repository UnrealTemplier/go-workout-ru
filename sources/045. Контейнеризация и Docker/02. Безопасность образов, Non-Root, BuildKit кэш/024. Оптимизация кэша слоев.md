# Оптимизация кэша слоев: изоляция go.mod/go.sum от исходного кода

## Условие

Оптимизируйте кэш Docker-слоёв: скопируйте сначала `go.mod` и `go.sum`, сделайте `go mod download`, затем копируйте остальной код. Теперь изменения в коде не будут вызывать перекачку зависимостей.

## Теория

При проектировании эффективного `Dockerfile` критически важно понимать жизненный цикл изменений в кодовой базе:
- **Исходный код (`*.go`):** меняется разработчиками десятки раз в день (каждый коммит, фикс бага или новая фича).
- **Внешние зависимости (`go.mod` и `go.sum`):** меняются редко (раз в несколько дней или недель).

Если обе группы файлов копируются одновременно:
`COPY . .`
то любое редактирование исходников приводит к инвалидации слоя кэша с `COPY`, заставляя Docker повторно выполнять `RUN go mod download`.

Правильная стратегия изоляции слоев:
1. `COPY go.mod go.sum ./` — копируются только файлы с перечнем зависимостей.
2. `RUN go mod download` — зависимости скачиваются и фиксируются в отдельном слое кэша.
3. `COPY . .` — копируется остальной код проекта.
4. `RUN go build ...` — быстрая компиляция приложения.

Благодаря этому время пересборки при изменении кода сокращается с минут до **1–3 секунд**!

## Решение по шагам

1. Создайте проект с модулями и несколькими зависимостями.
2. Опишите правильный порядок команд в `Dockerfile`.
3. Соберите образ `app:v1`.
4. Внесите правку в комментарий `main.go`.
5. Соберите `app:v2` и обратите внимание на вывод `CACHED` у директивы `RUN go mod download`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Fast cached layer build!")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Исходный код микросервиса

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

WORKDIR /app

# 1. Копируем только файлы манифеста зависимостей
COPY go.mod go.sum* ./

# 2. Скачиваем библиотеки в изолированный кэшируемый слой
RUN go mod download

# 3. Копируем исходники (кэш шага 2 НЕ инвалидируется при изменении кода!)
COPY . .

# 4. Компилируем бинарник
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /app/server main.go

FROM alpine:3.20
COPY --from=builder /app/server /app/server
ENTRYPOINT ["/app/server"]
```

ℹ️ Эталонная структура кэширования слоев

**`Терминал`**

```bash
# Первая сборка (скачивание зависимостей)
docker build -t app-cache-demo:v1 .

# Меняем исходный код
echo "// minor change" >> main.go

# Вторая сборка — шаг скачивания берется из кэша мгновенно!
docker build -t app-cache-demo:v2 .
```

## Под капотом

Послойная файловая система UnionFS/OverlayFS сравнивает хеш-суммы файлов. Шаг 1 зависит исключительно от содержимого `go.mod` и `go.sum`. Пока контрольные суммы sha256 этих файлов идентичны, Docker пропускает выполнение шага 2 и берет готовый снимок файловой системы из кэша слоев.

## Подводные камни

1. Использование маски `COPY *.go .` до `go mod download`.
2. Изменение форматирования в `go.mod`, которое меняет его sha256 и непреднамеренно инвалидирует кэш.

## На собеседовании

**Вопрос с собеседования:** «Почему в директиве `COPY go.mod go.sum* ./` рекомендуется ставить звездочку `*` у файла `go.sum`?»
**Ответ:** Если проект абсолютно новый или не имеет внешних сторонних библиотек, файл `go.sum` может физически отсутствовать в репозитории. Инструкция `COPY go.mod go.sum ./` в таком случае завершится ошибкой сборки `file not found`. Использование glob-паттерна `go.sum*` делает наличие файла опциональным: Docker скопирует его, если он существует, и не упадет с ошибкой, если его нет.
