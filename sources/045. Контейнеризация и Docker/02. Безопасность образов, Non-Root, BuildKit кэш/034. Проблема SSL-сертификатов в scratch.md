# Проблема SSL-сертификатов в scratch: диагностика и безопасный импорт

## Условие

**Проблема SSL-сертификатов в `scratch`**: Добавь в приложение HTTP-запрос к любому HTTPS-сайту (например, `google.com`). Собери в `scratch` и запусти. Получишь ошибку проверки сертификата! В этапе сборки скопируй файл `/etc/ssl/certs/ca-certificates.crt` из `builder` в `scratch`. Проверь, что HTTPS заработал.

## Теория

При проектировании микросервисной архитектуры абсолютное большинство сервисов взаимодействуют по HTTPS (вызовы платежных шлюзов, сторонних REST API, OAuth-провайдеров).

Если в контейнере `FROM scratch` не настроены корневые сертификаты, любой сетевой вызов завершается ошибкой:
`x509: certificate signed by unknown authority`

С точки зрения архитектуры безопасности Docker-образов:
1. Запрещено отключать верификацию сертификатов через `InsecureSkipVerify: true` (это открывает возможность атаки Man-in-the-Middle).
2. Сертификаты должны быть установлены через официальный пакет `ca-certificates` в этапе сборки.
3. Бандл `/etc/ssl/certs/ca-certificates.crt` копируется в `scratch`.

## Решение по шагам

1. Напишите HTTP-клиент, отправляющий запрос на `https://api.github.com`.
2. Соберите образ без сертификатов и продемонстрируйте сбой.
3. Добавьте копирование `ca-certificates.crt`.
4. Проверьте успешное выполнение защищенного соединения.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func main() {
	client := &http.Client{Timeout: 5 * time.Second}

	http.HandleFunc("/external", func(w http.ResponseWriter, r *http.Request) {
		resp, err := client.Get("https://api.github.com/zen")
		if err != nil {
			http.Error(w, fmt.Sprintf("External TLS Call Failed: %v", err), http.StatusBadGateway)
			return
		}
		defer resp.Body.Close()

		w.WriteHeader(resp.StatusCode)
		fmt.Fprintf(w, "Success! GitHub Zen API answered with status: %s\n", resp.Status)
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис с внешним HTTPS запросом

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

RUN apk add --no-cache ca-certificates

WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

FROM scratch

# Импорт доверенных сертификатов удостоверяющих центров
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt

COPY --from=builder /bin/app /bin/app

EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

ℹ️ Dockerfile с безопасным импортом сертификатов в scratch

**`Терминал`**

```bash
# Сборка
docker build -t app-ssl-diag:v1 .

# Запуск
docker run -d -p 8080:8080 --name test-ssl app-ssl-diag:v1

# Проверка успешного TLS вызова
curl http://localhost:8080/external

# Очистка
docker rm -f test-ssl
```

## Под капотом

Go стандартно проверяет цифровую подпись X.509 сертификата удаленного сервера по алгоритмам RSA/ECDSA, сверяя открытый ключ подписи с корневыми открытыми ключами из файла `ca-certificates.crt`. При совпадении хэшей цепочка считается доверенной.

## Подводные камни

1. Использование `InsecureSkipVerify: true` в коде в качестве «быстрого решения» — критическая уязвимость в продакшне.
2. Неверный путь копирования сертификата в scratch.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go коде категорически запрещено использовать `tls.Config{InsecureSkipVerify: true}` даже во внутреннем контуре Kubernetes кластера?»
**Ответ:** `InsecureSkipVerify: true` полностью отключает валидацию сертификата удаленного узла (проверку срока действия, SAN/CN и доверия CA). В распределенной среде это делает сервис уязвимым для MITM-атак со стороны любого соседнего скомпрометированного пода, DNS-спуфинга во внутренней сети CoreDNS или подмены трафика при использовании Service Mesh без взаимной проверки mTLS.
