# Каверзный кейс CGO: сборка с SQLite, статическая линковка и конфликт musl/glibc

## Условие

**[Каверзный кейс — CGO]**: Включи CGO в своем коде (например, используй `github.com/mattn/go-sqlite3`). Попробуй запустить бинарник, собранный в `golang:alpine`, в `FROM scratch`. Поймай ошибку динамического линковера (libc). Исправь, включив `CGO_ENABLED=0` или использовав `alpine` как runner.

## Теория

Большинство Go-приложений компилируются с `CGO_ENABLED=0`. Однако при использовании библиотек, содержащих код на C/C++ (например, драйвер базы данных `github.com/mattn/go-sqlite3`), **включение CGO обязательно (`CGO_ENABLED=1`)**.

Подводный камень CGO в контейнерах:
1. Если собрать бинарник в стандартном образе на базе Debian/Ubuntu (`glibc`), он динамически связывается с `/lib/x86_64-linux-gnu/libc.so.6`.
2. Если скопировать этот бинарник в минимальный образ на базе Alpine Linux (`musl libc`) или `scratch`, при запуске произойдет сбой:
   `exec /app: no such file or directory`

Решение для статического CGO:
Использование компилятора GCC в Alpine Linux со специальными флагами статического связывания:
`-ldflags="-linkmode external -extldflags '-static'"`
Это принудительно линкует `musl libc` статически внутрь Go-бинарника, позволяя запускать даже CGO-приложения в абсолютно пустом образе `FROM scratch`!

## Решение по шагам

1. Напишите Go-сервис, использующий SQLite через CGO драйвер.
2. В этапе builder установите пакеты `gcc` и `musl-dev`.
3. Укажите параметры сборки: `CGO_ENABLED=1` и `-ldflags="-linkmode external -extldflags '-static'"`.
4. Скопируйте полученный бинарник в чистый `scratch` или `alpine`.
5. Убедитесь, что бинарник успешно открывает SQLite БД и выполняет SQL-запросы.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"log"
	"net/http"

	_ "github.com/mattn/go-sqlite3"
)

func main() {
	// Инициализация in-memory SQLite базы данных
	db, err := sql.Open("sqlite3", ":memory:")
	if err != nil {
		log.Fatalf("Failed to open SQLite: %v", err)
	}
	defer db.Close()

	_, err = db.Exec("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT);")
	if err != nil {
		log.Fatalf("Migration failed: %v", err)
	}
	_, _ = db.Exec("INSERT INTO users (name) VALUES ('Alice'), ('Bob');")

	http.HandleFunc("/users", func(w http.ResponseWriter, r *http.Request) {
		rows, err := db.Query("SELECT name FROM users")
		if err != nil {
			http.Error(w, err.Error(), 500)
			return
		}
		defer rows.Close()

		for rows.Next() {
			var name string
			_ = rows.Scan(&name)
			fmt.Fprintf(w, "User: %s\n", name)
		}
	})

	log.Println("SQLite CGO service started on :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

# Установка GCC и заголовочных файлов musl, необходимых для сборки CGO
RUN apk add --no-cache gcc musl-dev

WORKDIR /app

COPY go.mod go.sum* ./
RUN go mod download

COPY . .

# Статическая внешняя линковка C-библиотеки в Alpine
RUN CGO_ENABLED=1 GOOS=linux go build \
    -a \
    -ldflags="-linkmode external -extldflags '-static' -w -s" \
    -o /bin/sqlite-app .

# Запуск в пустом образе scratch!
FROM scratch
COPY --from=builder /bin/sqlite-app /sqlite-app
EXPOSE 8080
ENTRYPOINT ["/sqlite-app"]
```

**`Терминал`**

```bash
# Сборка CGO приложения в scratch
docker build -t app-cgo-static:latest .

# Проверка размера (образ весит около 15 MB со встроенным SQLite движком)

# Проверка чтения из SQLite
curl http://localhost:8080/users

# Очистка
docker rm -f test-cgo
```

## Под капотом

Флаг `-linkmode external` заставляет Go передать финальную сборку внешнему линковщику хоста (`gcc` / `ld`). Параметр `-extldflags '-static'` инструктирует gcc связать стандартную библиотеку C (в Alpine это `libc.a` из musl) статически в исполняемый сегмент `.text`. В результате бинарник не содержит динамических ссылок на `.so` библиотеки.

## Подводные камни

1. Попытка статической линковки с GNU glibc: glibc крайне плохо поддерживает статическую линковку (`nsswitch` и сетевой резолвер по-прежнему требуют `dlopen`). Для статического CGO всегда используйте Alpine с musl.
2. Увеличение времени сборки из-за компиляции исходного C-кода SQLite.

## На собеседовании

**Вопрос с собеседования:** «Почему сборка статического бинарника с CGO на базе Debian/Ubuntu часто приводит к предупреждению `Using 'getaddrinfo' in statically linked applications requires at runtime the shared libraries from the glibc version used for linking`?»
**Ответ:** GNU libc архитектурно разработана с расчетом на динамическую загрузку библиотек через Name Service Switch (`libnss_files.so`, `libnss_dns.so`). При статической компиляции сетевой резолвер glibc в рантайме все равно пытается выполнить `dlopen()` этих библиотек. Если их нет в контейнере, DNS перестает работать. Поэтому для полностью автономных статических CGO-бинарников стандартом является Alpine Linux с библиотекой musl libc, которая не использует динамический NSS.
