# Сетевое взаимодействие: пользовательские Docker-сети и внутренний DNS

## Условие

Настрой **Docker network**: `docker network create mynet`. Запусти `app` и `postgres` в одной сети. Обращайся по имени контейнера: `postgres:5432`. Покажи DNS resolution в Docker.

## Теория

Docker поддерживает несколько драйверов сетей:
1. `bridge`: виртуальный мост (драйвер по умолчанию).
2. `host`: отключение сетевой изоляции (контейнер использует сетевой стек хоста).
3. `none`: полное отключение сети у контейнера.
4. `overlay`: многохостовая сеть (Swarm/Kubernetes).

Критическое отличие стандартного bridge (`docker0`) от пользовательской сети (`user-defined bridge`):
- В стандартной сети bridge **внутренний DNS-резолвинг имен контейнеров ОТКЛЮЧЕН** (обращение возможно только по IP-адресам или устаревшим `--link`).
- В пользовательской сети (`docker network create mynet`) **автоматический DNS-резолвинг включен по умолчанию**. Контейнеры мгновенно находят друг друга по имени контейнера (`container_name`).

## Решение по шагам

1. Создайте изолированную сеть: `docker network create mynet`.
2. Запустите контейнер базы данных в этой сети с именем `postgres-db`.
3. Запустите Go-сервис в той же сети.
4. Убедитесь, что Go-сервис успешно разрешает имя `postgres-db` через DNS.
5. Проинспектируйте сеть через `docker network inspect mynet`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"net/http"
	"os"
)

func main() {
	targetHost := os.Getenv("TARGET_HOST")
	if targetHost == "" {
		targetHost = "db-server"
	}

	http.HandleFunc("/resolve", func(w http.ResponseWriter, r *http.Request) {
		ips, err := net.LookupIP(targetHost)
		if err != nil {
			http.Error(w, fmt.Sprintf("DNS Lookup Failed for %s: %v", targetHost, err), http.StatusInternalServerError)
			return
		}

		fmt.Fprintf(w, "DNS Resolved successfully! Host: %s, IPs: %v\n", targetHost, ips)
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис, выполняющий DNS-резолвинг имени соседнего контейнера

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /bin/app main.go

FROM alpine:3.20
COPY --from=builder /bin/app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile

**`Терминал`**

```bash
# Создаем пользовательскую сеть
docker network create mynet

# Запускаем фиктивный сервер базы данных с именем 'db-server'
docker run -d --name db-server --network mynet alpine:3.20 sleep 3600

# Собираем и запускаем наше Go приложение в сети mynet
docker build -t app-net:latest .
docker run -d -p 8080:8080 --name test-app --network mynet -e TARGET_HOST=db-server app-net:latest

# Проверяем DNS-резолвинг
curl http://localhost:8080/resolve

# Очистка
docker rm -f test-app db-server
docker network rm mynet
```

## Под капотом

При создании пользовательской сети Docker запускает встроенный DNS-резолвер на виртуальном IP `127.0.0.11`. В контейнере в файле `/etc/resolv.conf` прописывается `nameserver 127.0.0.11`. Любой DNS-запрос перехватывается демоном Docker: если имя совпадает с именем контейнера в сети, возвращается его IP в подсети моста.

## Подводные камни

1. Запуск контейнеров в разных сетях: если `app` находится в `net1`, а `db` в `net2`, они не смогут связаться без явного подключения контейнера ко второй сети (`docker network connect`).
2. Попытка использования имен контейнеров в стандартной сети по умолчанию (`bridge`).

## На собеседовании

**Вопрос с собеседования:** «Почему в стандартной сети Docker `bridge` (по умолчанию) контейнеры не могут обращаться друг к другу по имени, а в сети `docker network create` — могут?»
**Ответ:** В сети по умолчанию `bridge` (docker0) для сохранения обратной совместимости со старыми версиями Docker (до 1.10) встроенный embedded DNS-сервер отключен. В ней резолвинг имен работал только через статический файл `/etc/hosts` и устаревший флаг `--link`. Во всех пользовательских сетях (`user-defined networks`) встроенный DNS-сервер `127.0.0.11` активен всегда и динамически обновляет записи при добавлении/удалении контейнеров.
