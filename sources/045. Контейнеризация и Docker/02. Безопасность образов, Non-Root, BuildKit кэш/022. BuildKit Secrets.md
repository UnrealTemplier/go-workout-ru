# BuildKit Secrets: безопасная передача токенов и ключей без утечки в слои

## Условие

Напиши **Dockerfile с secrets**: `RUN --mount=type=secret,id=github_token cat /run/secrets/github_token`. Используй `docker build --secret id=github_token,env=GITHUB_TOKEN`. Покажи, что secrets не попадают в image layers (безопасно).

## Теория

При сборке Go-приложений часто требуется загружать приватные модули из закрытых репозиториев (GitLab, GitHub, Bitbucket).

Антипаттерны передачи секретов:
1. `ARG GITHUB_TOKEN`: значение аргумента сборки навсегда сохраняется в метаданных образа (в истории `docker history` и OCI манифесте). Любой пользователь, скачавший образ, может легко прочитать токен!
2. `COPY id_rsa /root/.ssh/ && go mod download && rm /root/.ssh/id_rsa`: приватный ключ навсегда останется в нижнем слое OverlayFS.

Решение: **BuildKit Secrets Mounts** (`--mount=type=secret,id=...`).
Секрет монтируется во временную файловую систему в оперативной памяти (tmpfs) по пути `/run/secrets/<id>` **исключительно на время выполнения конкретной команды `RUN`**.
После завершения команды tmpfs размонтируется, и секрет **никогда не сохраняется ни в одном слое или метаданных образа**!

## Решение по шагам

1. Включите сборщик BuildKit: `export DOCKER_BUILDKIT=1`.
2. Создайте файл с секретом (например, `token.txt` или переменную окружения).
3. В `Dockerfile` укажите директиву `RUN --mount=type=secret,id=gh_token ...`.
4. Соберите образ командой `docker build --secret id=gh_token,src=token.txt -t app-secret:v1 .`.
5. Проверьте через `docker history app-secret:v1`, что секрет отсутствует в метаданных.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Built securely with BuildKit secrets!\n")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Микросервис

**`Dockerfile`**

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.24-alpine AS builder

WORKDIR /src

# Безопасное монтирование секрета для авторизации в приватном registry
RUN --mount=type=secret,id=github_token \
    TOKEN=$(cat /run/secrets/github_token) && \
    echo "Simulating secure go mod download with token: ${#TOKEN} chars" && \
    true

COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

FROM scratch
COPY --from=builder /bin/app /bin/app
EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

ℹ️ Dockerfile с BuildKit secret mount

**`Терминал`**

```bash
# Создаем секрет в файле на хосте
echo "ghp_super_secret_production_token_12345" > /tmp/gh_token.txt

# Сборка с передачей секрета
DOCKER_BUILDKIT=1 docker build \
  --secret id=github_token,src=/tmp/gh_token.txt \
  -t app-secret:v1 .

# Проверяем историю образа — токен нигде не зафиксирован!
docker history app-secret:v1

# Удаляем файл секрета с хоста
rm -f /tmp/gh_token.txt
```

## Под капотом

BuildKit создает защищенный gRPC-канал между клиентом Docker CLI и сборочным демоном. Содержимое секрета передается по TLS в поток демона и монтируется через системный вызов `mount(..., "tmpfs", ...)` в каталог `/run/secrets`. При формировании snapshot слоя файловая система tmpfs игнорируется OCI-экспортером.

## Подводные камни

1. Запись секрета во временный файл в файловой системе образа: `cat /run/secrets/token > /app/token.txt`. Файл `/app/token.txt` попадет в слой образа!
2. Использование старого синтаксиса `ARG GITHUB_TOKEN`.

## На собеседовании

**Вопрос с собеседования:** «Почему аргумент `ARG` в Dockerfile категорически запрещено использовать для передачи паролей от баз данных, API-токенов или SSH-ключей?»
**Ответ:** Значения всех `ARG` сохраняются в открытом виде в JSON-метаданных конфигурации образа (в секции `history` и `config.Env`), а также отображаются в выводе команды `docker history --no-trunc <image>`. Любой разработчик или система, имеющая доступ на скачивание образа (`docker pull`), может без труда извлечь все аргументы сборки в открытом виде.
