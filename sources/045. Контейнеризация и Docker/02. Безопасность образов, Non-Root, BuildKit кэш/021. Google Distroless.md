# Google Distroless: безопасность без шелла и системных утилит

## Условие

**Distroless**: Используйте `gcr.io/distroless/static-debian12` — минимальный образ от Google с базовыми библиотеками, но без shell (лучше для безопасности).

## Теория

**Google Distroless** (`gcr.io/distroless/static-debian12`) — это специализированная линейка базовых образов, содержащих только файлы, критически необходимые для запуска программы.

В образе Distroless Static присутствуют:
- Корневой бандл сертификатов SSL/TLS (`/etc/ssl/certs/ca-certificates.crt`).
- Файл описания системных пользователей `/etc/passwd` с непривилегированным пользователем `nonroot` (UID 65532).
- База данных временных зон (`/usr/share/zoneinfo`).

Чего в Distroless НЕТ:
- Нет оболочки (`/bin/sh`, `/bin/bash`).
- Нет пакетных менеджеров (`apt`, `dpkg`, `apk`).
- Нет стандартных утилит ядра (`ls`, `cat`, `rm`, `ps`, `curl`, `wget`).

Такая конфигурация делает эксплуатацию большинства классических уязвимостей типа RCE (Remote Code Execution) практически невозможной, так как атакующий не может породить командную строку или скачать эксплойт из сети.

## Решение по шагам

1. Напишите Go-сервис.
2. В первом этапе скомпилируйте статический бинарник (`CGO_ENABLED=0`).
3. Во втором этапе используйте образ `gcr.io/distroless/static-debian12`.
4. Скопируйте бинарник и запустите контейнер.
5. Продемонстрируйте, что запуск `docker exec -it <container> sh` невозможен.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Running safely on Google Distroless!\nTime: %s\n", time.Now().UTC())
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Безопасный сервис

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app main.go

# Минимальный безопасный образ от Google
FROM gcr.io/distroless/static-debian12

WORKDIR /app
COPY --from=builder /bin/app /app/app

# Запуск от встроенного непривилегированного пользователя nonroot (65532)
USER nonroot:nonroot

EXPOSE 8080
ENTRYPOINT ["/app/app"]
```

ℹ️ Dockerfile с базовым образом Distroless

**`Терминал`**

```bash
# Сборка
docker build -t app-distroless-safe:v1 .

# Запуск
docker run -d -p 8080:8080 --name test-distro-safe app-distroless-safe:v1
curl http://localhost:8080

# Попытка взлома/входа в контейнер через shell
docker exec -it test-distro-safe /bin/sh
# Вывод: OCI runtime exec failed: exec: "/bin/sh": stat /bin/sh: no such file or directory

docker rm -f test-distro-safe
```

## Под капотом

При попытке выполнить `docker exec` демон Docker обращается к `containerd`, который через системный вызов `setns` присоединяется к пространствам имен контейнера и пытается вызвать `execve("/bin/sh", ...)`. Поскольку в файловой системе контейнера нет файла `/bin/sh`, ядро возвращает ошибку `ENOENT`, блокируя любую попытку интерактивного доступа.

## Подводные камни

1. Использование shell-формы директив `CMD /app/app` или `ENTRYPOINT /app/app`. Без `/bin/sh` запуск упадет сразу.
2. Необходимость отладки: для исследования падающего контейнера необходимо применять Kubernetes ephemeral debug containers или локальные bind mounts.

## На собеседовании

**Вопрос с собеседования:** «Как отладить Go-приложение в продакшн-контейнере на базе Distroless, если в нем нет shell и стандартных утилит (`ps`, `netstat`, `curl` )?»
**Ответ:** В современной инфраструктуре Kubernetes используется механизм эфемерных контейнеров (`kubectl debug pod-name -it --image=nicolaka/netshoot --target=container-name`). Эфемерный контейнер со всеми сетевыми и отладочными утилитами подключается к тем же пространствам имен (Network, PID, IPC), позволяя исследовать трафик, сокеты и процессы без нарушения иммутабельности и безопасности основного рабочего контейнера.
