# Хранилища данных: Bind Mounts, Named Volumes и tmpfs mounts

## Условие

Настрой **bind mounts vs volumes**: bind mount `./config:/app/config` для development (live sync). named volume для production data. tmpfs mount `/tmp` для sensitive data (не пишется на диск).

## Теория

Контейнеры по умолчанию иммутабельны и эфемерны: при удалении контейнера все данные, записанные в его верхний слой (writable layer), безвозвратно уничтожаются.

В Docker существует три основных механизма монтирования:

1. **Bind Mounts (`./config:/app/config`):**
   - Монтирует произвольный файл или каталог хост-машины напрямую в контейнер.
   - Идеально для локальной разработки (live-sync конфигураций, горячая перезагрузка кода).
   - Зависит от структуры каталогов конкретной хостовой ОС.

2. **Named Volumes (`docker volume create pgdata` / `pgdata:/var/lib/postgresql/data`):**
   - Управляются Docker и хранятся в `/var/lib/docker/volumes/`.
   - Изолированы от структуры хоста, обладают высокой производительностью.
   - Золотой стандарт для баз данных (PostgreSQL, MySQL, Redis).

3. **tmpfs mounts (`--tmpfs /tmp`):**
   - Хранятся исключительно в оперативной памяти хоста (RAM), никогда не записываются на диск.
   - Идеальны для секретов, временных файлов и чувствительных данных.

## Решение по шагам

1. Создайте локальный файл конфигурации `config.json`.
2. Создайте именованный том: `docker volume create my_data_vol`.
3. Запустите Go-контейнер, использующий bind mount для чтения конфигурации и named volume для сохранения состояния.
4. Продемонстрируйте сохранение данных после перезапуска контейнера.

## Код решения

**`config.json`**

```json
{
  "app_name": "StorageDemo",
  "environment": "development"
}
```

ℹ️ Файл конфигурации для bind mount

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
	"path/filepath"
	"time"
)

func main() {
	// Чтение конфигурации из bind mount
	cfgData, _ := os.ReadFile("/app/config/config.json")

	// Запись состояния в named volume
	dataPath := "/app/data/counter.txt"
	_ = os.MkdirAll(filepath.Dir(dataPath), 0755)

	http.HandleFunc("/write", func(w http.ResponseWriter, r *http.Request) {
		msg := fmt.Sprintf("Saved at: %s\n", time.Now().UTC().Format(time.RFC3339))
		f, _ := os.OpenFile(dataPath, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
		defer f.Close()
		_, _ = f.WriteString(msg)
		fmt.Fprintf(w, "Appended to volume: %s", msg)
	})

	http.HandleFunc("/read", func(w http.ResponseWriter, r *http.Request) {
		data, _ := os.ReadFile(dataPath)
		fmt.Fprintf(w, "Config: %s\nData from Volume:\n%s\n", string(cfgData), string(data))
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис, работающий с bind mount и volume

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /bin/app main.go

FROM alpine:3.20
WORKDIR /app
COPY --from=builder /bin/app /app/app
EXPOSE 8080
ENTRYPOINT ["/app/app"]
```

ℹ️ Dockerfile

**`Терминал`**

```bash
# Создаем именованный том
docker volume create storage_data_vol

# Сборка
docker build -t app-storage:v1 .

# Запуск с bind mount для конфига и named volume для данных
docker run -d -p 8080:8080 --name test-store \
  -v $(pwd)/config.json:/app/config/config.json:ro \
  -v storage_data_vol:/app/data \
  app-storage:v1

# Запись данных в volume
curl http://localhost:8080/write
curl http://localhost:8080/read

# Удаляем контейнер и создаем новый с тем же volume — данные сохраняются!
docker rm -f test-store
docker run -d -p 8080:8080 --name test-store-2 \
  -v $(pwd)/config.json:/app/config/config.json:ro \
  -v storage_data_vol:/app/data \
  app-storage:v1

curl http://localhost:8080/read

# Очистка
docker rm -f test-store-2
docker volume rm storage_data_vol
```

## Под капотом

Docker использует системный вызов ядра Linux `mount(source, target, "none", MS_BIND, NULL)` для bind mount и создает каталог в `/var/lib/docker/volumes/<name>/_data` для named volume. При этом OverlayFS обходит эти точки монтирования, передавая I/O операции напрямую драйверу файловой системы хоста (ext4/xfs), что обеспечивает максимальный IOPS.

## Подводные камни

1. Монтирование bind mount без флага `:ro` (read-only): скомпрометированный контейнер может перезаписать критические файлы на хосте.
2. Проблемы с правами доступа (permission denied): пользователь `appuser` (UID 10001) в контейнере не имеет прав на запись в каталог хоста, принадлежащий root.

## На собеседовании

**Вопрос с собеседования:** «В чем фундаментальные отличия Bind Mount от Named Volume и почему в продакшн-окружениях запрещено использовать Bind Mounts для баз данных?»
**Ответ:** Bind Mount жестко привязан к конкретному абсолютному пути файловой системы хоста, что нарушает переносимость образов и может вызывать проблемы с правами UID/GID и блокировками файлов (особенно в Docker Desktop на macOS через gRPC-FUSE/VirtioFS). Named Volume изолирован в служебной директории Docker, управляется через Docker API/CSI-драйверы, обеспечивает максимальную скорость дискового ввода-вывода (IOPS) и переносим между нодами кластера.
