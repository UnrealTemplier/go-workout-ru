# Кэширование модулей Go: секреты оптимизации времени CI/CD сборок

## Условие

**[Кэширование модулей]**: Оптимизируй Dockerfile: скопируй сначала только `go.mod` и `go.sum`, выполни `go mod download`, и только потом копируй остальной код. Убедись, что при изменении кода этап `download` берется из кэша.

## Теория

При частых сборках в конвейерах непрерывной интеграции (GitLab CI, GitHub Actions, Jenkins) время скачивания зависимостей Go может составлять до 80% всего времени билда.

Стратегия максимального ускорения включает:
1. Раздельное копирование манифеста зависимостей.
2. Использование переменной `GOPROXY` (например, корпоративный Nexus / Artifactory или публичный `https://proxy.golang.org,direct`).
3. Использование команды `go mod download -x` для верификации загружаемых архивов.

Благодаря правильному разделению, билд-агенты CI переиспользуют закэшированные слои Docker Registry, сводя операцию загрузки зависимостей к нулевому времени.

## Решение по шагам

1. Подготовьте проект с несколькими внешними библиотеками.
2. Настройте `Dockerfile` с оптимальным кэшированием модулей.
3. Продемонстрируйте время сборки с кэшем и без кэша.

## Код решения

**`go.mod`**

```go
module example.com/fastcache

go 1.24

require (
	github.com/google/uuid v1.6.0
	golang.org/x/sync v0.10.0
)
```

ℹ️ Файл модулей с зависимостями

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

WORKDIR /workspace

# Переменные проксирования для стабильности загрузки модулей
ENV GOPROXY=https://proxy.golang.org,direct

# Копируем исключительно метаданные модулей
COPY go.mod go.sum ./
RUN go mod download

# Копируем код
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/service .

FROM alpine:3.20
COPY --from=builder /bin/service /service
ENTRYPOINT ["/service"]
```

ℹ️ Dockerfile с оптимизированным кэшированием модулей

**`Терминал`**

```bash
# Сборка с замером времени
time docker build -t test-mod-cache:v1 .

# Повторная сборка без изменения зависимостей (время < 1 сек)
time docker build -t test-mod-cache:v2 .
```

## Под капотом

Команда `go mod download` загружает zip-архивы модулей в каталог `$GOPATH/pkg/mod/cache/download` и проверяет их контрольные суммы по `go.sum`. После завершения этого шага слой фиксируется. Даже если в проекте изменяется логика бизнес-функций в `main.go`, кэшированный каталог `$GOPATH/pkg/mod` сохраняется в локальном графе слоев Docker.

## Подводные камни

1. Вызов `RUN go get ./...` вместо `RUN go mod download`: `go get` пытается компилировать пакеты, для чего требуются исходные файлы проекта, которые еще не скопированы.
2. Несоответствие хэшей в `go.sum` и `go.mod`.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между командами `go mod download` и `go mod vendor` в контексте контейнеризации?»
**Ответ:** `go mod download` скачивает модули в глобальный кэш `$GOPATH/pkg/mod` в виде сжатых zip-архивов. `go mod vendor` копирует исходные коды всех внешних зависимостей напрямую в локальную директорию `vendor/` проекта. Если проект использует vendor-режим (`go build -mod=vendor`), скачивать зависимости из сети в Dockerfile не требуется вовсе — достаточно скопировать локальную папку `vendor/`, что гарантирует полностью оффлайновую сборку.
