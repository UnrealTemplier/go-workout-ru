# Кросс-платформенная сборка: Multi-arch образы через Docker Buildx

## Условие

Собери **cross-platform image**: `docker buildx build --platform linux/amd64,linux/arm64 -t myapp:v1 --push`. Используй `buildx` с QEMU эмуляцией или нативными builder'ами. Покажи multi-arch manifest.

## Теория

Современная инфраструктура гетерогенна: разработчики часто работают на MacBook с архитектурой Apple Silicon (**ARM64**), а продакшн-серверы в облаках работают на процессорах Intel/AMD (**AMD64**) или ARM-серверах (AWS Graviton, Яндекс Cloud).

Если собрать образ локально на Mac без указания платформы, он не сможет запуститься на сервере Linux x86_64 (`exec format error`).

Инструмент **Docker Buildx** (на базе BuildKit) позволяет собирать кросс-платформенные образы (`Multi-arch images`) для нескольких архитектур одновременно:
`docker buildx build --platform linux/amd64,linux/arm64 -t myapp:v1 --push .`

Благодаря компилятору Go, у которого встроенная кросс-компиляция (`GOOS=linux GOARCH=arm64` или `GOARCH=amd64`), сборка под разные платформы выполняется нативно, быстро и не требует медленной эмуляции через QEMU.

## Решение по шагам

1. Убедитесь в наличии билдера buildx: `docker buildx ls`.
2. Создайте новый экземпляр билдера: `docker buildx create --use --name mybuilder`.
3. Опишите `Dockerfile`, использующий автоматические аргументы `TARGETOS` и `TARGETARCH`.
4. Соберите multi-arch манифест под `linux/amd64` и `linux/arm64`.
5. Проинспектируйте сформированный манифест через `docker buildx imagetools inspect`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"runtime"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Multi-arch Go App running on: %s/%s\n", runtime.GOOS, runtime.GOARCH)
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис, сообщающий архитектуру процессора

**`Dockerfile`**

```dockerfile
# Автоматические аргументы платформы, передаваемые buildx
FROM --platform=$BUILDPLATFORM golang:1.24-alpine AS builder

ARG TARGETOS
ARG TARGETARCH

WORKDIR /src
COPY main.go .

# Нативная быстрая кросс-компиляция средствами самого Go без QEMU эмуляции!
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build \
    -ldflags="-w -s" \
    -o /bin/app main.go

FROM scratch
COPY --from=builder /bin/app /bin/app
EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

ℹ️ Кросс-платформенный Dockerfile с поддержкой TARGETARCH

**`Терминал`**

```bash
# Создание билдера
docker buildx create --use --name multi-arch-builder

# Инициализация
docker buildx inspect --bootstrap

# Сборка под amd64 и arm64 (эмуляция или нативный тулчейн Go)
docker buildx build --platform linux/amd64,linux/arm64 -t test-multiarch:v1 .

# Проверка поддерживаемых платформ
docker buildx ls
```

## Под капотом

В реестре Docker (Registry) multi-arch образ хранится в виде Manifest List (OCI Index). Это JSON-документ со списком дайджестов для конкретных архитектур (`os: linux, architecture: amd64` и `architecture: arm64`). Когда нода Kubernetes выполняет `docker pull`, контейнерный демон считывает архитектуру хостового процессора и скачивает только подходящий бинарный образ.

## Подводные камни

1. Сборка CGO-кода под другую архитектуру: требуется кросс-компилятор GCC (`aarch64-linux-gnu-gcc`), иначе сборка завершится сбоем.
2. Попытка сохранить мультиархитектурный образ локально в Docker daemon через `docker buildx build --load` (Docker daemon не поддерживает одновременное хранение Manifest List нескольких платформ под одним тегом; используйте `--push`).

## На собеседовании

**Вопрос с собеседования:** «Почему директива `FROM --platform=$BUILDPLATFORM golang:...` в сочетании с `GOARCH=$TARGETARCH` собирает образы под ARM64/AMD64 в 10 раз быстрее, чем стандартный `docker buildx build`?»
**Ответ:** Стандартный buildx запускает весь контейнер сборки под эмуляцией QEMU (инструкции x86 эмулируются на ARM программно). Директива `FROM --platform=$BUILDPLATFORM` запускает компилятор Go нативно на архитектуре хоста билдера на полной скорости CPU, а компилятор Go сам создает целевой машинный код под `$TARGETARCH`, так как Go изначально поддерживает кросс-компиляцию из коробки.
