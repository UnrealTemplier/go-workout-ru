# Тестирование внутри контейнера: выделенный этап сборки (test stage)

## Условие

Соберите образ и запустите интеграционные тесты внутри контейнера (отдельный stage для тестов).

## Теория

Запуск юнит- и интеграционных тестов внутри контейнера гарантирует 100% повторяемость тестового окружения независимо от ОС разработчика (Linux, macOS, Windows).

Архитектура многоэтапного тестирования в Dockerfile:
1. `AS builder`: загрузка зависимостей и компиляция.
2. `AS test`: специальный этап сборки, запускающий `go test -v -race ./...`.
3. `AS runtime`: финальный продакшн-образ.

Если хотя бы один тест падает, сборка Dockerfile завершается с ошибкой на этапе `test`, и продакшн-образ физически **не будет собран**!
Целевой этап можно вызвать в CI командой:
`docker build --target test -t app-test .`

## Решение по шагам

1. Напишите функцию Go и модульный тест к ней.
2. В `Dockerfile` выделите отдельный этап `FROM builder AS test`.
3. Задайте команду запуска тестов с проверкой гонок данных (`-race`).
4. Соберите этап `test` и убедитесь, что билд прерывается при падении тестов.

## Код решения

**`calc.go`**

```go
package main

func Add(a, b int) int {
	return a + b
}
```

ℹ️ Бизнес-логика

**`calc_test.go`**

```go
package main

import "testing"

func TestAdd(t *testing.T) {
	if Add(2, 3) != 5 {
		t.Errorf("Expected 5, got %d", Add(2, 3))
	}
}
```

ℹ️ Модульный тест

**`Dockerfile`**

```dockerfile
# Базовый этап сборщика
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY . .

# Выделенный этап тестирования
FROM builder AS test
RUN CGO_ENABLED=1 apk add --no-cache gcc musl-dev && \
    go test -v -race ./...

# Финальный продакшн этап
FROM builder AS prod-builder
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /bin/app .

FROM scratch AS release
COPY --from=prod-builder /bin/app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile с выделенным тестовым этапом

**`Терминал`**

```bash
# Запуск только этапа тестов в CI/CD
docker build --target test -t myapp-tests .

# Сборка финального релиза (автоматически выполнит тесты при правильной зависимости)
docker build --target release -t myapp-release:v1 .
```

## Под капотом

BuildKit строит граф выполнения. При указании флага `--target test` сборщик вычисляет путь в графе только до целевого этапа `test`, пропуская генерацию финального этапа `release`, что экономит время CI пайплайна.

## Подводные камни

1. Запуск детекторов гонок (`-race`) при `CGO_ENABLED=0`: Race Detector в Go требует CGO и компилятора GCC.
2. Пропуск кэша тестов при повторных сборках.

## На собеседовании

**Вопрос с собеседования:** «Зачем выделять отдельный этап `AS test` в Dockerfile, если тесты можно запустить на CI-раннере командой `go test ./...` до вызова `docker build`?»
**Ответ:** 1) Изоляция окружения: запуск внутри Docker гарантирует идентичные версии Go, системных библиотек, glibc/musl и заголовочных файлов, исключая ситуацию «на ноутбуке разработчика работает, а в CI падает». 2) Возможность поднятия в тестовом контейнере необходимых локальных сервисов (например, тестового SQLite или моков). 3) Унификация CI пайплайна: раннеру не требуется установленный тулчейн Go — достаточно только наличия Docker демона.
