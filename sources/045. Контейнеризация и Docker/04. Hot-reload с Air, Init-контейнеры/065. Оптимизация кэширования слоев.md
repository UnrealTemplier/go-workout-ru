# Оптимизация кэширования слоев: продвинутые техники BuildKit

## Условие

**Оптимизация кэширования слоев**: Каждый шаг в `Dockerfile` создает слой, который кэшируется. Напишите команды копирования и сборки в таком порядке, чтобы при изменении файлов с кодом Go вам не приходилось заново скачивать все внешние зависимости из `go.mod`. (Подсказка: сначала копируйте только `go.mod` и `go.sum`, запускайте `RUN go mod download`, а уже потом копируйте остальной код и запускайте компиляцию).

## Теория

Максимальная скорость сборки контейнеров достигается глубоким пониманием механики кэширования BuildKit:

1. **Минимизация частоты инвалидации:**
   Команды, которые меняются реже всего (`RUN apk add`, `COPY go.mod`), размещаются в самом начале `Dockerfile`. Команды, меняющиеся постоянно (`COPY . .`, `RUN go build`), — в самом конце.

2. **Inline кэширование и Remote Cache:**
   В CI/CD билд-агенты часто создаются с нуля (Stateless Runners). Чтобы не качать зависимости заново, BuildKit умеет сохранять кэш сборки прямо в Docker Registry:
   `docker buildx build --cache-to type=registry,ref=myreg/app:cache --cache-from type=registry,ref=myreg/app:cache .`

3. **Mounting кэша компилятора:**
   `--mount=type=cache,target=/root/.cache/go-build` обеспечивает инкрементальную компиляцию Go-кода даже при чистом запуске.

## Решение по шагам

1. Настройте эталонный порядок директив в `Dockerfile`.
2. Используйте BuildKit cache mounts.
3. Продемонстрируйте время инкрементальной сборки при изменении одной функции.

## Код решения

**`Dockerfile`**

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.24-alpine AS builder

WORKDIR /src

# 1. Системные пакеты (кэшируются почти навсегда)
RUN apk add --no-cache git ca-certificates tzdata

# 2. Модули Go
COPY go.mod go.sum* ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

# 3. Исходный код
COPY . .

# 4. Инкрементальная компиляция
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /bin/app .

FROM scratch
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /bin/app /app
ENTRYPOINT ["/app"]
```

ℹ️ Идеально оптимизированный по кэшу Dockerfile

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Fast cached compile!")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Go микросервис

**`Терминал`**

```bash
# Включение BuildKit
export DOCKER_BUILDKIT=1

# Сборка
docker build -t app-cache-opt:latest .
```

## Под капотом

BuildKit строит граф выполнения в виде низкоуровневого формата LLB (Low-Level Builder). Сборщик вычисляет хэши операций параллельно и запускает независимые стадии сборки одновременно в разных потоках CPU.

## Подводные камни

1. Использование неявных временных меток в аргументах `ARG TIMESTAMP=$(date)` в начале Dockerfile, что сбрасывает кэш всех последующих слоев при каждом запуске.
2. Неиспользование `.dockerignore`.

## На собеседовании

**Вопрос с собеседования:** «Почему директиву `ARG BUILD_DATE` следует помещать как можно ближе к концу Dockerfile, непосредственно перед финальной компиляцией?»
**Ответ:** Если объявить `ARG BUILD_DATE` в начале файла, то при передаче текущей даты/времени в каждом CI пайплайне значение аргумента меняется. Это приведет к полной инвалидации кэша Docker на самом первом шаге, заставляя заново скачивать базовые образы, пакеты и все Go-модули. Размещение аргумента в самом конце сохраняет кэш всех предыдущих тяжелых слоев нетронутым.
