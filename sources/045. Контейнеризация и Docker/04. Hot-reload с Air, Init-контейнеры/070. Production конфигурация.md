# Production конфигурация: docker-compose.prod.yml с жестким харденингом

## Условие

Создайте отдельный `docker-compose.prod.yml` с production-настройками и используйте `docker compose -f docker-compose.yml -f docker-compose.prod.yml up` для продакшн-like тестирования.

## Теория

Для запуска сервисов на выделенных продакшн-серверах (например, standalone VM или периферийных edge-нодах) создается файл `docker-compose.prod.yml`.

Он реализует максимальные требования промышленной надежности:
1. `restart: always` — автоматический подъем сервиса при сбоях и перезагрузках ОС.
2. `read_only: true` — защита от модификации файлов контейнера.
3. `cap_drop: [ALL]` — отзыв всех привилегий ядра.
4. `security_opt: ["no-new-privileges:true"]` — запрет эскалации прав.
5. `logging` — ротация логов (не более 3 файлов по 10 МБ).
6. `deploy.resources.limits` — жесткие квоты cgroups на CPU и память.

## Решение по шагам

1. Создайте `docker-compose.prod.yml`.
2. Проверьте слияние конфигурации: `docker compose -f docker-compose.yml -f docker-compose.prod.yml config`.
3. Убедитесь в отсутствии проброшенных наружу портов БД и наличии лимитов ресурсов.

## Код решения

**`docker-compose.prod.yml`**

```yaml
services:
  app:
    image: myregistry.example.com/shop/app:v1.0.0
    restart: always
    read_only: true
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=32m
    deploy:
      resources:
        limits:
          cpus: '2.00'
          memory: 512M
        reservations:
          cpus: '0.50'
          memory: 128M
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"
    environment:
      - ENV=production
      - LOG_LEVEL=warn
```

ℹ️ Эталонный docker-compose.prod.yml

**`Терминал`**

```bash
# Валидация продакшн манифеста
docker compose -f docker-compose.prod.yml config --quiet && echo "Configuration is 100% valid!" 
```

## Под капотом

Спецификация Compose трансформируется в вызовы OCI runtime (runc), накладывая на процесс ограничения Linux namespaces, cgroups v2, seccomp и AppArmor/SELinux профили хостовой системы.

## Подводные камни

1. Использование тега `:latest` в продакшне вместо фиксированного семантического тега (например, `:v1.0.0`) или sha256 дайджеста.
2. Отсутствие мониторинга метрик OOMKilled.

## На собеседовании

**Вопрос с собеседования:** «Почему использование тега `:latest` в продакшн манифестах Docker Compose и Kubernetes считается грубейшей ошибкой?»
**Ответ:** Тег `:latest` является мутабельным указателем. Он не дает никакой гарантии, какой именно коммит и сборка кода запущены в данный момент. Это делает невозможным воспроизводимый откат (Rollback) на предыдущую версию, приводит к рассинхронизации версий между разными нодами кластера при рестарте подов и ломает аудит безопасности.
