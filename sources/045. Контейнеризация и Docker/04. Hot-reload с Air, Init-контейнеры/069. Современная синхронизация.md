# Современная синхронизация: docker compose watch для мгновенного обновления кода

## Условие

Используйте `docker compose watch` (новая фича Docker Compose v2.22+) для автоматической синхронизации кода и rebuild при изменениях.

## Теория

Начиная с версии Docker Compose v2.22+, появилась встроенная нативная функциональность **`docker compose watch`**.

Она решает проблему классического bind mount:
- Не требует установки сторонних утилит hot-reload внутри контейнера (таких как nodemon или air).
- Позволяет настроить гранулярные правила для разных типов файлов:
  1. `action: sync` — мгновенная синхронизация статических файлов, конфигураций и шаблонов прямо в работающий контейнер без перезапуска.
  2. `action: rebuild` — автоматическая пересборка образа и замена контейнера при изменении манифестов зависимостей (`go.mod`, `go.sum`).
  3. `action: sync+restart` — копирование обновленного файла и перезапуск процесса контейнера.

## Решение по шагам

1. В `docker-compose.yml` добавьте секцию `develop.watch`.
2. Настройте правила `sync` для шаблонов и `rebuild` для файлов `go.mod`.
3. Запустите команду `docker compose watch`.
4. Измените файл и убедитесь в автоматической фоновой синхронизации.

## Код решения

**`docker-compose.yml`**

```yaml
services:
  web:
    build: .
    ports:
      - "8080:8080"
    # Секция декларации правил автоматического отслеживания изменений
    develop:
      watch:
        # Синхронизация статики и шаблонов без перезапуска
        - action: sync
          path: ./static
          target: /app/static

        # Синхронизация кода и перезапуск контейнера
        - action: sync+restart
          path: ./cmd
          target: /app/cmd

        # Полная пересборка образа при обновлении модулей
        - action: rebuild
          path: ./go.mod
```

ℹ️ docker-compose.yml с секцией develop.watch

**`Терминал`**

```bash
# Запуск сервисов в режиме непрерывного отслеживания файлов
docker compose watch
```

## Под капотом

CLI Docker Compose запускает локальный файловый watcher на хосте. При фиксации изменения файла Compose вызывает стриминговый tar-эндпоинт Docker Engine API (`PUT /containers/{id}/archive`), копируя измененный файл непосредственно в файловую систему запущенного контейнера на лету.

## Подводные камни

1. Требуется версия Docker Compose 2.22.0 или новее.
2. Неверно указанные целевые пути `target`, приводящие к копированию файлов в неожиданные каталоги.

## На собеседовании

**Вопрос с собеседования:** «Чем `docker compose watch` лучше стандартного монтирования рабочей директории через `volumes: [".:/app"]`?»
**Ответ:** Стандартный bind mount монтирует всю директорию целиком, включая локальные артефакты хоста (например, бинарники, несовместимые с Linux, локальные логи, мусорные файлы IDE), и может вызывать серьезные просадки дискового ввода-вывода (особенно на macOS). `docker compose watch` синхронизирует только указанные файлы в одну сторону, не блокирует диск постоянным двусторонним монтированием и поддерживает интеллектуальные триггеры (`rebuild` при изменении зависимостей).
