# Горячая перезагрузка (Hot Reload) в Docker: использование утилиты Air

## Условие

Настройте hot-reload для разработки: используйте `air` (github.com/air-verse/air) в контейнере с volume mount для исходников.

## Теория

При локальной разработке внутри контейнеров необходимость вручную перезапускать `docker compose restart app` после каждого изменения кода замедляет цикл обратной связи (Feedback Loop).

Утилита **Air** (`github.com/air-verse/air`) реализует паттерн горячей перезагрузки (Hot Reload) для языка Go:
1. Отслеживает изменения файлов проекта (`*.go`, `*.yaml`, `*.html`) через файловые нотификации ядра Linux `inotify`.
2. Автоматически перекомпилирует бинарник на лету при сохранении файла.
3. Корректно останавливает старый процесс и запускает новый скомпилированный бинарник за доли секунды.

В связке с Docker Compose исходные коды монтируются в контейнер через **Bind Mount** (`./:/app`), а кэш компилятора сохраняется в отдельном Named Volume для максимальной скорости пересборки.

## Решение по шагам

1. Создайте конфигурационный файл `.air.toml`.
2. Напишите `Dockerfile.dev` с установкой утилиты `air`.
3. Опишите сервис в `docker-compose.yml` с bind mount исходников.
4. Запустите контейнер `docker compose up`.
5. Измените строку в `main.go` и пронаблюдайте автоматическую пересборку в логах Air.

## Код решения

**`.air.toml`**

```toml
root = "."
tmp_dir = "tmp"

[build]
  cmd = "go build -o ./tmp/main ."
  bin = "tmp/main"
  full_bin = ""
  include_ext = ["go", "tpl", "tmpl", "html", "yaml", "yml"]
  exclude_dir = ["assets", "tmp", "vendor", ".git"]
  include_dir = []
  exclude_file = []
  delay = 500 # ms
  stop_on_error = true
  log = "air.log"

[log]
  time = true

[color]
  main = "magenta"
  watcher = "cyan"
  build = "yellow"
  runner = "green" 
```

ℹ️ Файл конфигурации Air

**`Dockerfile.dev`**

```dockerfile
FROM golang:1.24-alpine

# Установка git и утилиты air для live-reload
RUN go install github.com/air-verse/air@v1.61.5

WORKDIR /app

# Кэширование модулей
COPY go.mod go.sum* ./
RUN go mod download

# Запуск air вместо прямого go run
CMD ["air", "-c", ".air.toml"]
```

ℹ️ Dockerfile для разработки с Air

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Live reload with Air is working! Version 1.0\n")
	})

	log.Println("Server running on :8080 with Air hot-reload...")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Микросервис

**`docker-compose.yml`**

```yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "8080:8080"
    volumes:
      - ./:/app
      - /app/tmp # Изолируем папку tmp от хоста
```

ℹ️ Compose с bind mount для Air

**`Терминал`**

```bash
# Запуск dev-окружения
docker compose up -d

# Проверка ответа
curl http://localhost:8080/

# Меняем строку в коде
sed -i 's/Version 1.0/Version 2.0 (HOT RELOADED)/g' main.go

# Ждем 1 секунду и проверяем: ответ изменился без перезапуска контейнера!
curl http://localhost:8080/

docker compose down
```

## Под капотом

Air подписывается на события `IN_MODIFY`, `IN_CREATE` и `IN_DELETE` подсистемы ядра `inotify` для смонтированного каталога. При получении события Air отправляет дочернему процессу сигнал `SIGTERM`, ожидает его завершения и вызывает `fork/execve` нового бинарника из каталога `tmp/`.

## Подводные камни

1. Проблемы с inotify на macOS при использовании старых драйверов файловой системы Docker Desktop (требуется включить VirtioFS).
2. Забытое исключение папки `tmp/` из bind mount, что может приводить к циклическим срабатываниям watcher'а.

## На собеседовании

**Вопрос с собеседования:** «Почему образ с `air` используется исключительно для локальной разработки и категорически запрещен к деплою в production?»
**Ответ:** 1) Образ содержит полный компилятор Go, исходные коды и тулчейн сборщика (размер 800+ МБ), что резко расширяет attack surface. 2) Процесс компиляции внутри контейнера под нагрузкой может потреблять 100% CPU и памяти. 3) В продакшне действует принцип иммутабельной инфраструктуры: все инстансы должны работать на предварительно скомпилированных, протестированных и проверенных сканерами безопасности бинарниках.
