# Использование Init Containers для выполнения миграций БД перед стартом

## Условие

Используйте `Init Containers` для выполнения миграций БД перед запуском основного приложения.

## Теория

Архитектурный паттерн **Init Containers** обеспечивает соблюдение принципа разделения ответственности (Separation of Concerns).

Схема исполнения:
1. СУБД PostgreSQL инициализируется и сообщает о статусе `healthy`.
2. Запускается эфемерный init-контейнер мигратора (`migrate/migrate`).
3. Init-контейнер выполняет проверку версий схемы, накладывает DDL-миграции, фиксирует номер версии в таблице `schema_migrations` и завершает работу с кодом 0.
4. Основное приложение стартует с гарантией, что все необходимые таблицы, колонки и индексы уже существуют в БД.

Это исключает падения сервиса из-за ошибок `relation "users" does not exist`.

## Решение по шагам

1. Создайте SQL файлы миграций.
2. Настройте сервис `init-migrations` в Docker Compose.
3. Свяжите основной сервис с `init-migrations` через `condition: service_completed_successfully`.
4. Запустите стек и проверьте логи.

## Код решения

**`docker-compose.yml`**

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: main_db
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U dev -d main_db"]
      interval: 2s
      timeout: 2s
      retries: 5

  # Init Container
  db-migrations:
    image: migrate/migrate:v4.17.0
    volumes:
      - ./migrations:/migrations
    entrypoint:
      - "migrate"
      - "-path=/migrations"
      - "-database=postgres://dev:secret@db:5432/main_db?sslmode=disable"
      - "up"
    depends_on:
      db:
        condition: service_healthy

  # Рабочий сервис
  app:
    image: alpine:3.20
    command: ["echo", "Database migrations completed successfully! Service is starting..."]
    depends_on:
      db-migrations:
        condition: service_completed_successfully
```

ℹ️ Паттерн Init Containers в Docker Compose

**`Терминал`**

```bash
# Запуск стека
docker compose up

# Очистка
docker compose down -v
```

## Под капотом

Compose отслеживает состояние процессов через Docker Socket. Завершение контейнера `db-migrations` с кодом 0 генерирует событие `container:die`, которое переводит триггер зависимости `service_completed_successfully` в активное состояние.

## Подводные камни

1. Отсутствие обработки ошибок: если миграция падает, весь деплой должен быть немедленно остановлен.
2. Неидемпотентные миграции (отсутствие `IF NOT EXISTS`).

## На собеседовании

**Вопрос с собеседования:** «Как обеспечить Zero-Downtime миграцию базы данных при непрерывном деплое новой версии Go-сервиса?»
**Ответ:** Применять паттерн Expand and Contract (Параллельное изменение). Миграции разбиваются на этапы: 1) Expand (Расширение): добавление новых колонок/таблиц без изменения старых (совместимо со старой и новой версиями сервиса). 2) Развертывание новой версии Go-приложения, пишущего в оба места. 3) Contract (Сужение): удаление старых колонок отдельной отложенной миграцией только после успешного переключения трафика.
