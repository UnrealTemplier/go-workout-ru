# CI аудит уязвимостей: сканирование через govulncheck и Trivy

## Условие

Добавьте в CI этап проверки уязвимостей: `govulncheck` и сканирование Docker-образа (`trivy`).

## Теория

Комплексный аудит уязвимостей в CI/CD пайплайне состоит из двух взаимодополняющих уровней:

1. **`govulncheck` (Анализ кода Go на уровне AST):**
   Официальная утилита команды Go (`golang.org/x/vuln/cmd/govulncheck`).
   В отличие от простых сканеров, govulncheck выполняет глубокий статический анализ графа вызовов (Call Graph). Если уязвимая функция сторонней библиотеки физически **не вызывается** вашим кодом, govulncheck не создает ложной тревоги!

2. **`trivy` (Анализ Docker-образа и ОС):**
   Проверяет готовый контейнер на наличие уязвимостей в системных библиотеках (libc, openssl, ca-certificates) и файлах конфигурации.

Объединение обоих инструментов в CI конвейере гарантирует 100% безопасность исходного кода и рантайма.

## Решение по шагам

1. Установите `govulncheck`: `go install golang.org/x/vuln/cmd/govulncheck@latest`.
2. Запустите анализ кода: `govulncheck ./...`.
3. Соберите Docker-образ.
4. Выполните сканирование контейнера через Trivy.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Audited clean codebase!")
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Микросервис

**`ci-audit.sh`**

```bash
#!/bin/sh
set -e

echo "==> 1. Running govulncheck on Go source code..."
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...

echo "==> 2. Building Docker Image..."
docker build -t app-audit-test:latest .

echo "==> 3. Scanning Docker Image with Trivy..."
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image --severity CRITICAL --exit-code 1 app-audit-test:latest

echo "==> All security checks passed successfully!" 
```

# Запуск проверки

## Под капотом

`govulncheck` строит SSA (Static Single Assignment) представление Go-кода и ищет пути в графе потока управления от функций `main()` и `init()` к символам, зарегистрированным в базе Go Vulnerability Database (`vuln.go.dev`).

## Подводные камни

1. Использование устаревших версий Go, содержащих известные уязвимости в рантайме.
2. Игнорирование предупреждений govulncheck о стандартной библиотеке.

## На собеседовании

**Вопрос с собеседования:** «Почему `govulncheck` дает значительно меньше ложных срабатываний (False Positives), чем стандартные сканеры зависимостей типа Snyk или Dependabot?»
**Ответ:** Стандартные сканеры просто анализируют манифест `go.mod` и выдают предупреждение, если в проекте подключена библиотека уязвимой версии. Однако библиотека может содержать уязвимость в редкой вспомогательной функции, которую ваш сервис вообще не использует. `govulncheck` анализирует AST и граф вызовов бинарника и рапортует об уязвимости только в том случае, если уязвимый участок кода действительно вызывается в рантайме вашей программы.
