# Локальное событийно-ориентированное окружение: Redis, Kafka и NATS в Compose

## Условие

Добавьте Redis, Kafka и NATS в docker-compose для локальной разработки event-driven приложений.

## Теория

Event-Driven архитектура (EDA) на Go часто использует специализированные брокеры сообщений под разные задачи:
1. **Redis:** оперативный кэш, распределенные блокировки (`redsync`) и Pub/Sub для веб-сокетов.
2. **Apache Kafka (или Redpanda):** долговечный лог событий (Log-centric Event Streaming) с гарантией порядка и партиционированием для аналитики и аудита.
3. **NATS JetStream:** сверхбыстрый легковесный брокер сообщений для межсервисной коммуникации в реальном времени с низкой задержкой (Sub-millisecond Latency).

Поднятие всех этих компонентов в едином `docker-compose.yml` позволяет разработчику локально воспроизвести весь стек взаимодействия перед отправкой кода в кластер.

## Решение по шагам

1. Напишите `docker-compose.yml` с сервисами Redis, Kafka (в режиме KRaft без Zookeeper) и NATS JetStream.
2. Настройте внутреннюю сеть `event_net`.
3. Запустите стек и проверьте готовность портов всех брокеров.

## Код решения

**`docker-compose.yml`**

```yaml
services:
  # Быстрый кэш и Pub/Sub
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    networks:
      - event_net

  # NATS с поддержкой JetStream
  nats:
    image: nats:2.10-alpine
    command: ["-js", "-m", "8222"]
    ports:
      - "4222:4222" # Клиентский порт
      - "8222:8222" # HTTP мониторинг
    networks:
      - event_net

  # Kafka в современном легковесном режиме KRaft (без Zookeeper)
  kafka:
    image: apache/kafka:3.8.0
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0
    ports:
      - "9092:9092"
    networks:
      - event_net

networks:
  event_net:
    driver: bridge
```

ℹ️ docker-compose.yml для полного Event-Driven стека

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"net/http"
	"time"
)

func checkPort(addr string) string {
	conn, err := net.DialTimeout("tcp", addr, 1*time.Second)
	if err != nil {
		return fmt.Sprintf("DOWN (%v)", err)
	}
	conn.Close()
	return "UP"
}

func main() {
	http.HandleFunc("/brokers", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Redis: %s\nNATS:  %s\nKafka: %s\n",
			checkPort("redis:6379"), checkPort("nats:4222"), checkPort("kafka:9092"))
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис проверки доступности брокеров

**`Терминал`**

```bash
# Запуск брокеров
docker compose up -d

# Проверка статуса контейнеров
docker compose ps

# Остановка
docker compose down
```

## Под капотом

Apache Kafka в режиме KRaft использует собственный кворум на алгоритме Raft для управления метаданными топиков без отдельного кластера Apache ZooKeeper. NATS JetStream запускается с флагом `-js` и выделяет in-memory буферы для сохранения истории сообщений.

## Подводные камни

1. Высокое потребление оперативной памяти JVM внутри Kafka (для локальной разработки часто заменяют на легковесный аналог Redpanda на C++).
2. Неверная настройка `KAFKA_ADVERTISED_LISTENERS`, из-за чего клиенты снаружи Docker не могут получить метаданные брокера.

## На собеседовании

**Вопрос с собеседования:** «В каких сценариях распределенной архитектуры на Go целесообразно использовать NATS JetStream вместо Apache Kafka?»
**Ответ:** NATS JetStream выбирают, когда критически важны: 1) Ультранизкая задержка передачи сообщений (десятки микросекунд против миллисекунд в Kafka). 2) Минимальное потребление ресурсов (один статический бинарник на Go весом 20 МБ, потребляющий 30 МБ RAM против тяжелой JVM Kafka на 1-2 ГБ). 3) Простота развертывания и встроенная поддержка Request-Reply паттерна и Key-Value/Object Store из коробки.
