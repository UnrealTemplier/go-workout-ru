# Политики перезапуска: restart unless-stopped, always и on-failure

## Условие

Настрой **restart policy**: `restart: unless-stopped` (development), `restart: always` (production), `restart: on-failure:3` (CI). Покажи поведение при `docker stop` vs crash.

## Теория

Политика перезапуска (`restart policy`) контейнера определяет поведение Docker демона при аварийном падении процесса или перезагрузке операционной системы хоста.

Основные политики:
1. `no`: (по умолчанию) не перезапускать контейнер ни при каких обстоятельствах.
2. `on-failure[:max-retries]`: перезапускать контейнер только в случае ненулевого кода возврата (Exit Code != 0). Рекомендуется для батч-воркеров и утилит миграций.
3. `always`: всегда перезапускать контейнер при падении, а также автоматически запускать его при старте/перезагрузке Docker демона и всей хостовой ОС.
4. `unless-stopped`: аналогично `always`, за исключением случая, когда контейнер был явно остановлен вручную инженером (`docker stop`). Золотой стандарт для большинства веб-сервисов.

## Решение по шагам

1. Опишите сервис в `docker-compose.yml` с политикой `restart: unless-stopped`.
2. Запустите контейнер.
3. Сымитируйте аварийное падение процесса изнутри (код возврата 1 или panic).
4. Убедитесь, что Docker автоматически перезапустил контейнер.

## Код решения

**`main.go`**

```go
package main

import (
	"log"
	"net/http"
	"os"
	"time"
)

func main() {
	startTime := time.Now()

	http.HandleFunc("/uptime", func(w http.ResponseWriter, r *http.Request) {
		log.Printf("Uptime check. Running since: %s\n", startTime.Format(time.RFC3339))
		w.Write([]byte("Service active. Start: " + startTime.Format(time.RFC3339)))
	})

	// Эндпоинт искусственного краша сервиса
	http.HandleFunc("/crash", func(w http.ResponseWriter, r *http.Request) {
		log.Println("Simulating fatal crash!")
		go func() {
			time.Sleep(500 * time.Millisecond)
			os.Exit(1) // Аварийный выход
		}()
		w.Write([]byte("Crashing now..."))
	})

	log.Println("Listening on :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис с возможностью вызова контролируемого сбоя

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /app main.go

FROM alpine:3.20
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile

**`docker-compose.yml`**

```yaml
services:
  web:
    build: .
    ports:
      - "8080:8080"
    restart: unless-stopped
```

ℹ️ Compose с политикой restart: unless-stopped

**`Терминал`**

```bash
# Запуск
docker compose up -d

# Проверяем начальное время старта
curl http://localhost:8080/uptime

# Провоцируем падение сервиса
curl http://localhost:8080/crash

# Ждем 3 секунды: Docker перезапускает контейнер
sleep 3

# Проверяем uptime — контейнер жив, время старта обновилось!
curl http://localhost:8080/uptime

# Очистка
docker compose down
```

## Под капотом

Демон Docker отслеживает события выхода процессов через события cgroups/pidfd. При получении уведомления о завершении процесса демон проверяет назначенную политику и при необходимости заново инициирует системный вызов старта контейнера через containerd, применяя экспоненциальный бэкофф (backoff) при частых циклических падениях (CrashLoop).

## Подводные камни

1. Использование `restart: always` для контейнеров-миграций: миграция завершится с кодом 0, но Docker перезапустит ее снова, вызвав бесконечный цикл.
2. Бесконечный CrashLoop: при фатальной ошибке конфигурации контейнер будет непрерывно рестартовать, нагружая CPU сервера.

## На собеседовании

**Вопрос с собеседования:** «В чем практическая разница между `restart: always` и `restart: unless-stopped` в продакшне?»
**Ответ:** Если физический сервер или служба Docker перезагрузится, обе политики поднимут контейнеры автоматически. Разница проявляется, если дежурный инженер вручную остановил контейнер командой `docker stop`. Контейнер с политикой `always` после перезагрузки демона Docker/сервера снова автоматически запустится вопреки воле инженера. Контейнер с политикой `unless-stopped` запомнит, что он был остановлен вручную, и останется в статусе stopped.
