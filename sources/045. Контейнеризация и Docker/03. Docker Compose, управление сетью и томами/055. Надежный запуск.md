# Надежный запуск: depends_on с условием condition: service_healthy

## Условие

Используйте `depends_on` с health check, чтобы Go-сервис стартовал только после готовности БД.

## Теория

Классическая директива `depends_on: [db]` лишь гарантирует, что контейнер `db` будет создан и запущен *до* контейнера приложения. Она **не ждет**, пока СУБД внутри контейнера инициализирует таблицы и откроет сетевой порт для приема клиентских соединений.

В современном стандарте Docker Compose (v2) используется условие **`condition: service_healthy`**:
```yaml
depends_on:
  postgres:
    condition: service_healthy
```

Как это работает:
1. В сервисе `postgres` объявляется секция `healthcheck` (например, вызов `pg_isready`).
2. Docker Compose запускает `postgres` и ждет, пока статус здоровья не станет `healthy`.
3. Только после этого Compose запускает контейнер Go-сервиса `app`.
4. Сервис гарантированно подключается к уже готовой к приему трафика базе данных!

## Решение по шагам

1. Опишите в `docker-compose.yml` сервис `postgres` с `healthcheck`.
2. В сервисе `app` укажите `depends_on` с условием `condition: service_healthy`.
3. Запустите `docker compose up` и пронаблюдайте ожидание готовности базы в консоли.

## Код решения

**`docker-compose.yml`**

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: myuser
      POSTGRES_PASSWORD: mypassword
      POSTGRES_DB: appdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myuser -d appdb"]
      interval: 2s
      timeout: 2s
      retries: 5
      start_period: 2s

  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      - DB_ADDR=postgres:5432
    depends_on:
      postgres:
        condition: service_healthy
```

ℹ️ Compose с зависимостью по healthcheck

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net"
	"net/http"
	"os"
)

func main() {
	dbAddr := os.Getenv("DB_ADDR")
	conn, err := net.Dial("tcp", dbAddr)
	if err != nil {
		log.Fatalf("Fatal: Database is not ready: %v", err)
	}
	conn.Close()
	log.Println("Successfully connected to Database on first attempt!")

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "App running! DB %s is verified healthy!\n", dbAddr)
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис, мгновенно подключающийся к БД

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /app main.go

FROM alpine:3.20
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile

**`Терминал`**

```bash
# Запуск: Compose покажет 'Waiting for postgres to become healthy...'
docker compose up -d

# Проверка
curl http://localhost:8080/

# Очистка
docker compose down -v
```

## Под капотом

Compose подписывается на поток событий Docker Engine (`docker events`). При получении события `health_status: healthy` для контейнера `postgres` внутренний конечный автомат Compose разблокирует переход сервиса `app` в состояние запуска.

## Подводные камни

1. Забытый `test` в секции `healthcheck` у базы данных: контейнер никогда не станет `healthy`, и Compose зависнет по таймауту.
2. Слишком короткий таймаут `start_period`: на медленных машинах база не успеет инициализироваться.

## На собеседовании

**Вопрос с собеседования:** «Чем `depends_on: { condition: service_healthy }` принципиально лучше скриптов ожидания вроде `wait-for-it.sh` внутри образа приложения?»
**Ответ:** 1) Чистота образов: приложению не нужно тащить в свой продакшн-образ сторонние bash-скрипты, `nc`, `curl` или `wget` (что особенно важно для `FROM scratch` и `distroless`). 2) Семантическая точность: `wait-for-it.sh` проверяет только открытие TCP-порта, тогда как база данных может слушать порт, но еще не завершить внутреннюю процедуру recovery/migration. Healthcheck проверяет реальную готовность СУБД выполнять SQL-запросы (`pg_isready` или `SELECT 1`).
