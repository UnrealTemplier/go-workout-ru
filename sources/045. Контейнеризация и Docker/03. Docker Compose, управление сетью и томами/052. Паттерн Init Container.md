# Паттерн Init Container: выполнение миграций базы данных перед запуском приложения

## Условие

Напиши **init-контейнер**: `migrations` контейнер запускается перед `app`, выполняет `golang-migrate`, завершается. `app` зависит от `migrations` (`depends_on` + condition). Покажи job pattern в Compose.

## Теория

Запуск миграций базы данных прямо из кода основного веб-сервиса — опасный антипаттерн в масштабируемых системах:
- При горизонтальном масштабировании (HPA) 10 реплик сервиса одновременно попытаются выполнить `db.AutoMigrate()` или применить DDL-скрипты, что приведет к дедлокам в таблицах блокировок (`pg_locks`).
- Если у сервиса нет прав DDL (создание таблиц, изменение индексов), а есть только DML (`SELECT`, `INSERT`), сервис не сможет стартовать.

Архитектурный паттерн **Init Container**:
1. Отдельный легковесный контейнер (например, с утилитой `golang-migrate`) запускается **строго до** старта основного сервиса.
2. Он применяет миграции и успешно завершается (`exit 0`).
3. Только после успешного завершения init-контейнера Docker Compose или Kubernetes запускает основной контейнер сервиса.

В Docker Compose это реализуется через условие:
```yaml
depends_on:
  migrations:
    condition: service_completed_successfully
```

## Решение по шагам

1. Создайте SQL-файл миграции `000001_init.up.sql`.
2. Опишите в `docker-compose.yml` сервис `migrations` на базе образа `migrate/migrate`.
3. Настройте зависимость основного сервиса `app` от `migrations` с условием `service_completed_successfully`.
4. Запустите стек и проследите порядок исполнения в логах.

## Код решения

**`migrations/000001_create_users_table.up.sql`**

```sql
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO users (email) VALUES ('admin@example.com') ON CONFLICT DO NOTHING;
```

ℹ️ SQL файл начальной миграции

**`docker-compose.yml`**

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: devuser
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: devdb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U devuser -d devdb"]
      interval: 3s
      timeout: 2s
      retries: 5

  # Init-контейнер для наката миграций
  migrations:
    image: migrate/migrate:v4.17.0
    volumes:
      - ./migrations:/migrations
    entrypoint:
      - "migrate"
      - "-path=/migrations"
      - "-database=postgres://devuser:devpass@postgres:5432/devdb?sslmode=disable"
      - "up"
    depends_on:
      postgres:
        condition: service_healthy

  # Основной веб-сервер
  app:
    image: alpine:3.20
    command: ["echo", "App started safely after migrations!"]
    depends_on:
      migrations:
        condition: service_completed_successfully
```

ℹ️ docker-compose.yml с паттерном Init Container для миграций

**`Терминал`**

```bash
# Запуск стека: обратите внимание на последовательность
# 1. postgres (healthy) -> 2. migrations (completed) -> 3. app
docker compose up

# Очистка
docker compose down -v
```

## Под капотом

Compose отслеживает состояние жизненного цикла контейнеров. Контейнер `migrations` переходит в статус `exited` с кодом 0. Compose проверяет условие `service_completed_successfully`, после чего инициирует создание и старт контейнера `app`.

## Подводные камни

1. Ошибка в SQL-миграции: init-контейнер завершится с кодом 1, и основной сервис никогда не будет запущен (Fail-Fast принцип).
2. Забытый healthcheck у PostgreSQL: мигратор попытается подключиться к еще не готовой базе данных.

## На собеседовании

**Вопрос с собеседования:** «Почему выполнять автоматические миграции БД внутри функции `init()` или `main()` Go-микросервиса считается антипаттерном в продакшне?»
**Ответ:** 1) Гонка блокировок (Race Condition): при одновременном старте нескольких реплик сервиса (Rolling Update) они конкурируют за накат миграций, что может приводить к взаимным блокировкам (Deadlock) или повреждению схемы. 2) Нарушение принципа наименьших привилегий: рабочий микросервис должен иметь только права DML (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), тогда как миграции требуют DDL (`CREATE`, `ALTER`, `DROP`). Предоставление DDL-прав приложению увеличивает ущерб при SQL-инъекциях. Миграции должны запускаться изолированно через Init Containers или CI/CD пайплайн.
