# Безопасность: запуск процессов от непривилегированного пользователя

## Условие

**Безопасность: запуск от не-root пользователя**: По умолчанию процессы в контейнере запускаются с правами суперпользователя `root`, что является критической уязвимостью в продакшене. Модифицируйте ваш `Dockerfile`: на этапе компиляции создайте системного пользователя `appuser` без домашних директорий, скопируйте файл `/etc/passwd` на финальный этап сборки и добавьте директиву `USER appuser`. Убедитесь, что приложение успешно работает без прав root.

## Теория

Запуск контейнеров от root по умолчанию — историческое наследие ранних версий Docker.
В современных корпоративных средах действует принцип нулевого доверия (Zero Trust) и модель наименьших привилегий (POLP — Principle of Least Privilege).

Процесс, исполняющийся под пользователем `appuser` (UID > 1000):
- Не может изменять системные файлы (`/etc`, `/usr`).
- Не может устанавливать или модифицировать пакеты ядра.
- Не имеет capability для перехвата сетевого трафика (`CAP_NET_RAW`, `CAP_NET_ADMIN`).
- При попытке побега из контейнера на хост злоумышленник сталкивается с ограничениями прав непривилегированного пользователя хоста.

## Решение по шагам

1. Напишите Go-сервер.
2. В `Dockerfile` создайте пользователя `appuser` с UID 10001.
3. Переключитесь на пользователя `USER 10001:10001`.
4. Проверьте через `docker exec <container> id`, что процесс запущен не под root.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/id", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Current Process UID: %d\n", os.Getuid())
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис проверки UID

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /app main.go

# Создаем пользователя с фиксированным ID
RUN adduser -D -u 10001 -s /sbin/nologin nonrootuser

FROM alpine:3.20
COPY --from=builder /etc/passwd /etc/passwd
COPY --from=builder /app /app

USER 10001:10001

EXPOSE 8080
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile с non-root пользователем

**`Терминал`**

```bash
# Сборка
docker build -t test-nonroot-audit:v1 .

# Запуск
docker run -d -p 8080:8080 --name test-nra test-nonroot-audit:v1
curl http://localhost:8080/id
docker rm -f test-nra
```

## Под капотом

Демон containerd перед запуском процесса читает OCI Spec (`config.json`), где в поле `process.user` установлен `uid: 10001`. Вызывается системный вызов ядра `setresuid(10001, 10001, 10001)`, навсегда сбрасывающий привилегии суперпользователя для процесса и всех его будущих потомков.

## Подводные камни

1. Запуск бинарника, которому требуется писать в смонтированный volume, принадлежащий root (решается назначением владельца тома `chown`).
2. Попытка слушать привилегированный порт 80.

## На собеседовании

**Вопрос с собеседования:** «Может ли процесс внутри контейнера с UID 10001 читать файлы на хост-машине при использовании Bind Mount?»
**Ответ:** Только если эти файлы на хосте имеют права на чтение для всех пользователей (флаг `others read`, например `0644` или `0755`), либо если на хосте существует пользователь/группа с тем же числовым идентификатором UID/GID 10001, имеющий доступ к этим файлам. Если файл на хосте принадлежит `root` с правами `0600` или `0700`, процесс с UID 10001 получит ошибку `Permission denied`.
