# Безопасность контейнеров: защита от атак Container Escape через Non-root user

## Условие

**Безопасность (Non-root user)**: Запускать приложение в контейнере от имени пользователя `root` — угроза безопасности. В `alpine` (или другом образе) создай пользователя `appuser`, дай ему права на приложение и укажи директиву `USER appuser` перед `CMD`.

## Теория

Запуск приложений под учетной записью суперпользователя `root` (UID 0) в контейнере представляет собой критический риск безопасности:
1. Если атакующий находит уязвимость (RCE) в коде приложения или сторонней зависимости, он получает права root внутри контейнера.
2. При наличии ошибок конфигурации (например, монтирование хостового сокета `/var/run/docker.sock` или флага `--privileged`) злоумышленник с root-правами может мгновенно скомпрометировать весь физический сервер хоста (Container Breakout).

Для предотвращения этого в Dockerfile создается отдельный пользователь (например, `appuser` с UID 10001):
`RUN adduser -D -u 10001 -s /sbin/nologin appuser`
и активируется директивой:
`USER 10001:10001`
Такой процесс не может модифицировать файлы системы, устанавливать пакеты или совершать привилегированные системные вызовы ядра.

## Решение по шагам

1. Создайте HTTP-сервер на Go.
2. В этапе builder создайте пользователя `appuser` с UID 10001.
3. Скопируйте `/etc/passwd` в runtime-образ.
4. Укажите `USER 10001:10001`.
5. Запустите контейнер и убедитесь, что попытки записи в корень `/` отклоняются операционной системой.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/security", func(w http.ResponseWriter, r *http.Request) {
		uid := os.Getuid()
		isRoot := uid == 0
		fmt.Fprintf(w, "Process UID: %d (Is Root: %v)\n", uid, isRoot)
	})

	http.HandleFunc("/try-write", func(w http.ResponseWriter, r *http.Request) {
		// Попытка создать файл в корневом каталоге /
		err := os.WriteFile("/root-exploit.txt", []byte("pwned"), 0644)
		if err != nil {
			http.Error(w, fmt.Sprintf("Access Denied (Expected for non-root): %v", err), http.StatusForbidden)
			return
		}
		fmt.Fprintln(w, "WARNING: Root write succeeded!")
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис для проверки непривилегированного доступа

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder

WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /bin/app main.go

# Создание непривилегированного пользователя в builder
RUN adduser -D -u 10001 -s /sbin/nologin appuser

FROM alpine:3.20

# Копирование учетных записей
COPY --from=builder /etc/passwd /etc/passwd
COPY --from=builder /etc/group /etc/group
COPY --from=builder /bin/app /bin/app

# Переключение пользователя
USER 10001:10001

EXPOSE 8080
ENTRYPOINT ["/bin/app"]
```

ℹ️ Dockerfile с non-root пользователем

**`Терминал`**

```bash
# Сборка
docker build -t app-security-nonroot:v1 .

# Запуск
docker run -d -p 8080:8080 --name test-sec app-security-nonroot:v1

# Проверка UID (вернет UID: 10001)
curl http://localhost:8080/security

# Проверка запрета записи в корень (вернет 403 Access Denied)
curl http://localhost:8080/try-write

# Очистка
docker rm -f test-sec
```

## Под капотом

Ядро Linux проверяет мандатные права доступа (Discretionary Access Control — DAC). Каталог `/` принадлежит `root:root` с правами `0755`. Процесс с UID 10001 подпадает под категорию `others` (только чтение и исполнение `r-x`), поэтому системный вызов `open("/root-exploit.txt", O_CREAT|O_WRONLY, 0644)` немедленно отклоняется с ошибкой `EACCES` (Permission denied).

## Подводные камни

1. Запуск от имени пользователя `root` по недосмотру.
2. Необходимость записи логов: если приложению требуется писать логи в файл, для него должна быть заранее создана директория с правами владельца `chown 10001:10001 /app/logs`.

## На собеседовании

**Вопрос с собеседования:** «Почему даже при наличии `USER nonroot` в Dockerfile в production-кластерах Kubernetes дополнительно настраивают `securityContext.allowPrivilegeEscalation: false`?»
**Ответ:** Если в контейнере случайно останется бинарник с битом SUID (SetUID, например утилиты `su`, `sudo`, `mount`), непривилегированный пользователь может выполнить этот бинарник и временно повысить свои права до root. Флаг `allowPrivilegeEscalation: false` запрещает ядру Linux активировать механизм SUID для всех процессов контейнера, гарантируя, что процесс никогда не сможет получить больше прав, чем у него было при старте.
