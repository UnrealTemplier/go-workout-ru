# Усиление безопасности (Hardening): no-new-privileges, cap-drop=ALL и read-only rootfs

## Условие

Настрой **Docker security**: `--security-opt=no-new-privileges`, `--cap-drop=ALL`, `--cap-add=NET_BIND_SERVICE` (если нужен порт <1024), `--read-only` root filesystem + tmpfs для `/tmp`. Покажи hardened container.

## Теория

Комплексное усиление безопасности контейнеров (**Container Hardening**) в соответствии с рекомендациями CIS Benchmarks и NSA/CISA Container Security Guide включает три ключевых барьера:

1. **`--security-opt=no-new-privileges`:**
   Запрещает процессу и его дочерним процессам получать новые привилегии через вызовы `setuid`/`setgid` программ.

2. **`--cap-drop=ALL` (с селективным добавлением):**
   Ядро Linux разделяет привилегии root на отдельные возможности (Linux Capabilities, `CAP_*`).
   Сброс всех capabilities (`cap-drop: ALL`) отбирает у процесса возможность менять системное время (`CAP_SYS_TIME`), управлять сетевыми интерфейсами (`CAP_NET_ADMIN`), перехватывать сокеты (`CAP_NET_RAW`) и отлаживать другие процессы (`CAP_SYS_PTRACE`).

3. **`--read-only` (Read-only Root Filesystem):**
   Корневая файловая система контейнера монтируется в режиме только для чтения (`ro`). Злоумышленник физически не может изменить ни один бинарный файл, скрипт или конфигурацию в контейнере!
   Временные файлы, необходимые для работы приложения, монтируются в оперативную память через `tmpfs` (`--tmpfs /tmp`).

## Решение по шагам

1. Напишите Go-сервер.
2. Создайте `docker-compose.yml` с максимальными настройками защиты: `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges:true`.
3. Запустите контейнер.
4. Продемонстрируйте, что создание файлов в файловой системе контейнера блокируется ядром на уровне файловой системы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("/test-fs", func(w http.ResponseWriter, r *http.Request) {
		// Попытка записать файл в корень
		err := os.WriteFile("/hack.sh", []byte("#!/bin/sh\n"), 0755)
		if err != nil {
			fmt.Fprintf(w, "Security Working: Root FS is READ-ONLY! (%v)\n", err)
			return
		}
		fmt.Fprintln(w, "SECURITY ALERT: Root FS is writable!")
	})

	http.HandleFunc("/test-tmpfs", func(w http.ResponseWriter, r *http.Request) {
		// Запись во временный tmpfs каталог /tmp разрешена
		err := os.WriteFile("/tmp/valid_temp.txt", []byte("in-memory-temp"), 0644)
		if err != nil {
			http.Error(w, err.Error(), 500)
			return
		}
		fmt.Fprintln(w, "Tmpfs write OK: Temporary files function normally in RAM.")
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис для тестирования Hardened контейнера

**`docker-compose.yml`**

```yaml
services:
  hardened_app:
    build: .
    ports:
      - "8080:8080"
    # 1. Запрет повышения привилегий
    security_opt:
      - no-new-privileges:true
    # 2. Полный сброс всех Capabilities ядра Linux
    cap_drop:
      - ALL
    # 3. Файловая система контейнера только для чтения
    read_only: true
    # 4. Монтирование RAM-диска для временных файлов приложения
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=64m
    restart: unless-stopped
```

ℹ️ Эталонная конфигурация максимальной безопасности в Docker Compose

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /app main.go

FROM alpine:3.20
COPY --from=builder /app /app
USER 10001:10001
EXPOSE 8080
ENTRYPOINT ["/app"]
```

## Под капотом

Флаг `read_only: true` инструктирует `runc` смонтировать корневую файловую систему с флагом `MS_RDONLY`. Любая операция `write()` или `open(..., O_WRONLY)` мгновенно отвергается драйвером файловой системы ядра Linux с кодом ошибки `EROFS` (Read-only file system). В свою очередь `cap_drop: ALL` устанавливает маску capabilities `prctl(PR_CAPBSET_DROP)` для всех битов.

## Подводные камни

1. Забыть смонтировать `tmpfs` в `/tmp`: если приложению требуется создать временный файл (например, парсер multipart/form-data при загрузке файлов в Go), запрос упадет с ошибкой `read-only file system`.
2. Попытка использования библиотек, требующих создания временных файлов в несмонтированных каталогах.

## На собеседовании

**Вопрос с собеседования:** «Какую защиту обеспечивает комбинация `read_only: true`, `cap_drop: [ALL]` и `no-new-privileges: true` в продакшн-контейнере?»
**Ответ:** Эта комбинация реализует защиту от подавляющего большинства векторов атак: 1) Атакующий не может модифицировать файлы контейнера или записать вредоносный бинарник/бэкдор на диск (`read_only: true`). 2) Отсутствие Linux capabilities блокирует низкоуровневые атаки на сеть ядра, перехват пакетов и манипуляции с пространством памяти (`cap_drop: ALL`). 3) Запрет `no-new-privileges` гарантирует, что даже при наличии уязвимостей SUID в системных утилитах процесс не сможет повысить привилегии до root хоста.
