# Полнофункциональный Docker Compose: Go, PostgreSQL и Redis кэш

## Условие

**[Docker Compose]**: Напиши `docker-compose.yml`, который поднимает твое Go-приложение, PostgreSQL и Redis. Настрой `depends_on` с `condition: service_healthy` (healthcheck для БД).

## Теория

В HighLoad системах реляционная база данных PostgreSQL дополняется кэширующим слоем в оперативной памяти на базе Redis.

Архитектура стека:
1. `app`: Go HTTP-сервер, реализующий паттерн Cache-Aside.
2. `postgres`: основное долговременное хранилище (Named Volume).
3. `redis`: быстрый кэш для сессий и горячих запросов.

Преимущества использования Docker Compose:
- Единая команда поднятия всей инфраструктуры (`docker compose up -d`).
- Изоляция сетевого трафика.
- Воспроизводимость окружения для всех разработчиков команды.

## Решение по шагам

1. Напишите сервис на Go, подключающийся к Postgres и Redis.
2. Опишите `docker-compose.yml` с тремя сервисами.
3. Протестируйте запись данных в Postgres и чтение из кэша Redis.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	dbURL := os.Getenv("DATABASE_URL")
	redisURL := os.Getenv("REDIS_URL")

	http.HandleFunc("/ping-all", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "All systems operational! DB: %s | Redis: %s\n", dbURL, redisURL)
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Go микросервис

**`docker-compose.yml`**

```yaml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      - DATABASE_URL=postgres://user:pass@postgres:5432/appdb
      - REDIS_URL=redis:6379
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine

volumes:
  pgdata:
```

ℹ️ docker-compose.yml с тремя сервисами

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /app main.go

FROM alpine:3.20
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile

**`Терминал`**

```bash
# Запуск всех трех сервисов
docker compose up -d

# Проверка статуса
docker compose ps

# Проверка связи
curl http://localhost:8080/ping-all

# Остановка
docker compose down -v
```

## Под капотом

Все три контейнера получают виртуальные интерфейсы `eth0` в одной подсети (например, `172.20.0.0/16`). Трафик между `app`, `postgres` и `redis` передается через ядро Linux без выхода на физические сетевые адаптеры хоста, что обеспечивает максимальную пропускную способность (до 40-50 Гбит/с в памяти хоста).

## Подводные камни

1. Забытый volume для Postgres: при перезапуске данные стираются.
2. Проброс порта Redis (`6379:6379`) на хост в продакшне без пароля — частый вектор взлома через Redis RCE.

## На собеседовании

**Вопрос с собеседования:** «Зачем скрывать порты внутренних баз данных (`postgres`, `redis`) в продакшн docker-compose и не указывать секцию `ports` наружу?»
**Ответ:** Если порт указан в секции `ports: ["5432:5432"]`, Docker создает правило DNAT в `iptables`, открывая порт 5432 на всех внешних сетевых интерфейсах хоста (`0.0.0.0:5432`), часто в обход локального файрвола (UFW). Это создает угрозу прямого сканирования и брутфорса паролей базы данных из глобального интернета. Доступ к БД должен быть только у контейнеров внутри изолированной Docker-сети.
