# Ротация логов: драйвер json-file, ограничение max-size и max-file

## Условие

Настрой **log rotation**: `logging.driver: "json-file"`, `logging.options.max-size: "10m"`, `logging.options.max-file: "3"`. Предотвращи заполнение диска логами. Альтернатива: `logging.driver: fluentd` для centralized logging.

## Теория

По умолчанию Docker перехватывает все потоки стандартного вывода `stdout` и ошибок `stderr` процессов контейнера и записывает их на диск хоста с помощью драйвера **`json-file`** по пути `/var/lib/docker/containers/<id>/<id>-json.log`.

Опасность отсутствия ротации:
Если приложение активно пишет логи (особенно под высокой нагрузкой или в цикле ошибок), один единственный контейнер может сгенерировать **десятки и сотни гигабайт логов**, полностью заполнив диск хостовой системы (`No space left on device`). Это приводит к остановке Docker демона и падению всех соседних сервисов!

Настройка жесткой ротации:
```yaml
logging:
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "3"
```
При превышении размера файла в 10 МБ Docker архивирует его и начинает новый. Хранится максимум 3 файла, гарантируя, что логи сервиса **никогда не займут более 30 МБ диска**.

## Решение по шагам

1. Создайте Go-сервис, непрерывно генерирующий логи в stdout.
2. В `docker-compose.yml` настройте секцию `logging` с ограничением `max-size: 1m` и `max-file: 2`.
3. Запустите контейнер и убедитесь в ограничении дискового пространства логов.

## Код решения

**`main.go`**

```go
package main

import (
	"log"
	"net/http"
	"time"
)

func main() {
	go func() {
		for {
			log.Println("Production event log: processing incoming highload telemetry stream...")
			time.Sleep(200 * time.Millisecond)
		}
	}()

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("Logging active"))
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервис с активным логированием

**`docker-compose.yml`**

```yaml
services:
  logger_app:
    build: .
    ports:
      - "8080:8080"
    logging:
      driver: "json-file"
      options:
        max-size: "1m"
        max-file: "2"
    restart: unless-stopped
```

ℹ️ Compose с ротацией логов

**`Dockerfile`**

```dockerfile
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
RUN CGO_ENABLED=0 go build -o /app main.go

FROM alpine:3.20
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

ℹ️ Dockerfile

**`Терминал`**

```bash
# Запуск
docker compose up -d

# Проверка настроек логов контейнера
docker inspect --format='{{json .HostConfig.LogConfig}}' $(docker compose ps -q logger_app)

# Просмотр последних логов
docker compose logs --tail 10 logger_app

# Очистка
docker compose down
```

## Под капотом

Демон Docker перенаправляет файловые дескрипторы 1 и 2 (stdout/stderr) контейнера в FIFO pipe. Горутина демона считывает строки, упаковывает их в JSON с меткой времени и пишет в текущий файл лога. При достижении `max-size` файл переименовывается в `.1`, а самый старый файл сверх лимита `max-file` удаляется системным вызовом `unlink`.

## Подводные камни

1. Запись логов в локальный файл внутри контейнера (`/app/app.log`): такой файл не виден в `docker logs` и при отсутствии ротации раздувает верхний слой контейнера.
2. Отсутствие глобальной конфигурации ротации в `/etc/docker/daemon.json` на хост-сервере.

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшн-контейнерах категорически запрещено писать логи в локальные файлы на диск контейнера и требуется писать только в `stdout`/`stderr`?»
**Ответ:** 1) 12-Factor App (Фактор 11 — Потоки событий): контейнер не должен управлять маршрутизацией или хранением своих логов. 2) Запись в файлы внутри контейнера раздувает writable layer OverlayFS, что снижает производительность I/O и переполняет диск без ротации. 3) При выводе в `stdout`/`stderr` инфраструктура (Docker Daemon, Fluentbit, Vector, Promtail) централизованно собирает логи, выполняет ротацию и отправляет их в ElasticSearch / ClickHouse / Grafana Loki.
