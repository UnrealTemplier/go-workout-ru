# Body size limiting (MaxBytesReader)

## Условие

Настройте http.MaxBytesReader для ограничения размера request body. Без этого ваш сервер уязвим к DoS через большие payload'ы. Реализуйте проверку типа ошибки через errors.As и верните HTTP 413 Payload Too Large.

### Исходная формулировка

**Body size limiting**: Настройте `http.MaxBytesReader` для ограничения размера request body. Без этого ваш сервер уязвим к DoS через большие payload'ы.

## Теория

Неконтролируемое чтение входящего потока данных — классический вектор DoS-атак.
Если HTTP-сервер принимает JSON-запрос и парсит его:
```go
var payload Data
_ = json.NewDecoder(r.Body).Decode(&payload)
```
Злоумышленник может открыть соединение и передавать бесконечный непрерывный поток байт (`{"key": "aaaaaaaaa...}`). По умолчанию `json.Decoder` будет накапливать данные во внутреннем буфере, пока у процесса не закончится память (OOM crash).

Функция `http.MaxBytesReader(w ResponseWriter, r io.ReadCloser, n int64) io.ReadCloser` решает эту проблему на уровне стандартной библиотеки:
1. Она считает количество вычитанных байт.
2. При попытке прочесть байт с номером `n + 1` вызов `Read()` возвращает ошибку `*http.MaxBytesError`.
3. Флаг в `ResponseWriter` сигнализирует серверу разорвать соединение с клиентом.

## Решение по шагам

1. Напишите HTTP-обработчик с ограничением размера тела до 1 МБ (или 10 КБ для тестов).
2. Оберните `r.Body` в `http.MaxBytesReader(w, r.Body, maxBytes)`.
3. Вызовите декодер JSON с включенной опцией `DisallowUnknownFields()`.
4. Перехватите ошибку: проверьте `errors.As(err, &maxBytesErr)`.
5. Верните структурированный ответ со статусом `413 Request Entity Too Large`.
6. Продемонстрируйте тестами корректную обработку валидного запроса и отклонение избыточного payload.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

type UserInput struct {
	Name  string `json:"name"`
	Email string `json:"email"`
}

func SafeBodyHandler(maxBytes int64) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// Ограничиваем размер входящего потока
		r.Body = http.MaxBytesReader(w, r.Body, maxBytes)

		decoder := json.NewDecoder(r.Body)
		decoder.DisallowUnknownFields()

		var input UserInput
		if err := decoder.Decode(&input); err != nil {
			var maxBytesErr *http.MaxBytesError
			if errors.As(err, &maxBytesErr) {
				w.Header().Set("Content-Type", "application/json")
				w.WriteHeader(http.StatusRequestEntityTooLarge) // 413
				_, _ = fmt.Fprintf(w, `{"error":"payload too large","max_bytes":%d}`, maxBytesErr.Limit)
				return
			}

			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusBadRequest) // 400
			_, _ = fmt.Fprintf(w, `{"error":"malformed json: %s"}`, err.Error())
			return
		}

		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusOK)
		_, _ = fmt.Fprintf(w, `{"status":"ok","user":"%s"}`, input.Name)
	}
}

func main() {
	const limit = 256 // Лимит 256 байт для наглядного теста

	handler := SafeBodyHandler(limit)

	// Тест 1: Валидный запрос нормального размера
	validJSON := `{"name":"Alice","email":"alice@example.com"}`
	req1 := httptest.NewRequest(http.MethodPost, "/api/user", strings.NewReader(validJSON))
	rec1 := httptest.NewRecorder()
	handler(rec1, req1)
	fmt.Printf("Test 1 (Valid): Status=%d, Body=%s\n", rec1.Code, strings.TrimSpace(rec1.Body.String()))

	// Тест 2: DoS атака через огромный payload
	hugeJSON := `{"name":"` + strings.Repeat("A", 1000) + `","email":"spam@evil.com"}`
	req2 := httptest.NewRequest(http.MethodPost, "/api/user", strings.NewReader(hugeJSON))
	rec2 := httptest.NewRecorder()
	handler(rec2, req2)
	fmt.Printf("Test 2 (Oversized): Status=%d, Body=%s\n", rec2.Code, strings.TrimSpace(rec2.Body.String()))
}
```

ℹ️ Ограничение размера тела с корректной проверкой errors.As(*http.MaxBytesError)

## Под капотом

В Go 1.19+ ошибка `*http.MaxBytesError` содержит поле `Limit int64`.
Когда `MaxBytesReader` видит, что лимит исчерпан, он устанавливает флаг `sawEOF = true` и возвращает ошибку.
Внутри стандартного HTTP/1.1 сервера Go проверяется этот признак. Если тело запроса не было дочитано до конца (из-за ошибки превышения лимита), сервер не может безопасно использовать это же TCP-соединение для следующего запроса (HTTP Pipelining/Keep-Alive), так как в сокете остались непрочитанные байты предыдущего тела. Поэтому сервер автоматически закрывает TCP-соединение (`Connection: close`).

## Подводные камни

1. Проверка только заголовка `Content-Length`: атакующий может отправить запрос с `Transfer-Encoding: chunked`, опустив заголовок `Content-Length`. Только `MaxBytesReader` обеспечивает реальный подсчет вычитанных байтов из сокета.
2. Игнорирование ошибки: если проигнорировать ошибку `errors.As(err, &maxBytesErr)` и попытаться вернуть ответ 200 OK, клиент получит поврежденные или частичные данные.

## На собеседовании

**Вопрос с собеседования:** В чем разница между таймаутом `ReadTimeout` у `http.Server` и ограничением `MaxBytesReader`?
**Ответ:** `ReadTimeout` ограничивает **время** (в секундах), за которое клиент обязан передать весь запрос (заголовки и тело). Однако при высокоскоростном гигабитном канале злоумышленник может передать 500 мегабайт данных всего за 1 секунду!
`ReadTimeout` предотвратит атаку медленного соединения (Slowloris), но не защитит от быстрого исчерпания оперативной памяти. `MaxBytesReader` контролирует **объем** данных (в байтах), дополняя сетевые таймауты.
