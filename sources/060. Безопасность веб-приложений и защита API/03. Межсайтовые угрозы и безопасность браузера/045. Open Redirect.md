# Open Redirect: валидация redirect URLs по whitelist

## Условие

Покажите, как параметр ?redirect=evil.com в login flow используется для phishing атак. Валидируйте redirect URLs по whitelist доверенных доменов и разрешайте относительные переходы.

### Исходная формулировка

**Open Redirect**: Покажите, как параметр `?redirect=evil.com` в login flow используется для phishing. Валидируйте redirect URLs по whitelist.

## Теория

Open Redirect в потоке аутентификации (Login Flow):
1. Пользователь заходит на сайт интернет-банка по ссылке:
   `https://bank.com/login?redirect=https://evil-phishing-bank.com`
2. Пользователь видит адрес `bank.com`, зеленый замок TLS и вводит свой логин и пароль.
3. Сервер успешно авторизует пользователя и перенаправляет браузер:
   `http.Redirect(w, r, r.URL.Query().Get("redirect"), http.StatusFound)`
4. Браузер переходит на `evil-phishing-bank.com`, где отображается страница с сообщением: «Сессия истекла из соображений безопасности. Введите SMS-код подтверждения».
5. Пользователь уверен, что находится в банке, и передает одноразовый SMS-код злоумышленнику.

Безопасная стратегия перенаправлений:
- Разрешать только относительные пути (Relative URLs: `/account/dashboard`), блокируя попытки внедрения протокола (`//evil.com`, `javascript:`).
- Если требуются внешние переходы (SSO, OAuth), сверять хост по строгому белому списку (Whitelist).

## Решение по шагам

1. Создайте функцию `GetSafeRedirectURL(raw string, defaultURL string, whitelist []string) string`.
2. Проверьте крайние случаи: protocol-relative ссылки `//evil.com` и обратные слэши `/\\evil.com`.
3. Распарсите URL через `url.Parse(raw)`.
4. Если схема и хост отсутствуют, убедитесь, что путь начинается с `/`.
5. Если схема указана, разрешайте только `https://` и проверяйте точное совпадение хоста со списком доверенных партнеров.
6. Продемонстрируйте тестами нейтрализацию фишинговых ссылок.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
)

var trustedDomains = map[string]bool{
	"app.company.com":     true,
	"support.company.com": true,
}

func SafeRedirectTarget(rawTarget string, fallback string) string {
	if strings.TrimSpace(rawTarget) == "" {
		return fallback
	}

	// Защита от protocol-relative bypass: //evil.com или /\evil.com
	if strings.HasPrefix(rawTarget, "//") || strings.HasPrefix(rawTarget, "/\\") || strings.HasPrefix(rawTarget, "\\") {
		return fallback
	}

	u, err := url.Parse(rawTarget)
	if err != nil {
		return fallback
	}

	// 1. Относительный путь в рамках текущего домена (Safe Relative URL)
	if u.Scheme == "" && u.Host == "" {
		if strings.HasPrefix(u.Path, "/") {
			// Возвращаем Path с сохранением Query параметров
			return u.RequestURI()
		}
		return fallback
	}

	// 2. Внешний абсолютный URL: только HTTPS и строгий whitelist хостов
	if u.Scheme != "https" {
		return fallback
	}

	hostname := strings.ToLower(u.Hostname())
	if trustedDomains[hostname] {
		return u.String()
	}

	return fallback
}

func AuthCallbackHandler(w http.ResponseWriter, r *http.Request) {
	redirectParam := r.URL.Query().Get("redirect")
	target := SafeRedirectTarget(redirectParam, "/home")
	http.Redirect(w, r, target, http.StatusFound)
}

func main() {
	tests := []struct {
		name     string
		param    string
		expected string
	}{
		{"Legitimate Relative", "/settings/profile?tab=security", "/settings/profile?tab=security"},
		{"Legitimate External Whitelist", "https://app.company.com/workspace", "https://app.company.com/workspace"},
		{"Phishing Evil Domain", "https://evil-bank.com/steal", "/home"},
		{"Protocol Relative Trick", "//evil-bank.com", "/home"},
		{"Backslash Trick", "/\\evil-bank.com", "/home"},
		{"Javascript URI", "javascript:alert(document.cookie)", "/home"},
		{"Subdomain Spoofing", "https://app.company.com.evil.com/page", "/home"},
	}

	for _, tt := range tests {
		req := httptest.NewRequest(http.MethodGet, "/login?redirect="+url.QueryEscape(tt.param), nil)
		rec := httptest.NewRecorder()
		AuthCallbackHandler(rec, req)

		location := rec.Header().Get("Location")
		success := location == tt.expected
		fmt.Printf("[Test: %-28s] Target: %-32s -> Location: %-26s | Passed: %v\n",
			tt.name, tt.param, location, success)
	}
}
```

## Под капотом

Почему злоумышленники используют `//evil.com`?
В стандарте RFC 3986 URL, начинающийся с двух слэшей `//`, называется Network-Path Reference.
Когда браузер встречает тег `<a href="//evil.com">` или получает заголовок `Location: //evil.com`, он заимствует текущую схему (`https:`) и переходит по адресу `https://evil.com`.
Если бэкенд проверяет только `strings.HasPrefix(raw, "/")`, строка `//evil.com` успешно пройдет проверку (так как начинается с `/`), но браузер пользователя выполнит переход на внешний сайт! Поэтому проверка обязана явно отсекать `//`.

## Подводные камни

1. Использование регулярных выражений без экранирования точки: `.*\.company\.com` совпадает с `attacker-company.com`.
2. Валидация хоста через `strings.Contains`: `https://evil.com/?target=app.company.com` содержит строку `app.company.com`, но ведет на `evil.com`! Всегда парсите URL через `url.Parse` и проверяйте строго `u.Hostname()`.

## На собеседовании

**Вопрос с собеседования:** Как Open Redirect может привести к компрометации access token при неявном потоке OAuth 2.0 (Implicit Flow) или Authorization Code с PKCE?
**Ответ:** В протоколе OAuth 2.0 Identity Provider (IdP) проверяет совпадение `redirect_uri` со списком зарегистрированных адресов приложения клиента.
Если у клиента зарегистрирован `https://client.com/oauth/callback`, но на этом эндпоинте присутствует Open Redirect, атакующий передает `redirect_uri=https://client.com/oauth/callback?redirect=https://evil.com`.
IdP считает redirect_uri легитимным и возвращает токен или authorization code в hash-фрагменте `#access_token=...` или параметре. Браузер клиента перенаправляется на `evil.com`, передавая токен в заголовке `Referer` или фрагменте URL серверу злоумышленника.
