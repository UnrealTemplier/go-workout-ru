# Защита от утечки технической информации (Information Disclosure)

## Условие

Напишите middleware обработки паник (Panic Recovery). Если в кодовой базе произошла паника, middleware должно записать подробный стек вызовов во внутреннюю систему логирования (для разработчиков), а клиенту вернуть обезличенный JSON с request_id и HTTP-статусом 500 без технических подробностей.

### Исходная формулировка

**Защита от утечки технической информации (Information Disclosure)**: Напишите middleware обработки паник. Если в кодовой базе произошла паника, middleware должно записать подробный стек вызовов во внутреннюю систему логирования (для разработчиков), но пользователю вернуть строго стандартизированный JSON вида `{"error": "Internal Server Error"}` со статусом 500 [553]. Убедитесь, что наружу не просачиваются пути к файлам сервера, версии пакетов Go и технические детали ошибок.

## Теория

Information Disclosure (утечка технической информации) — распространенная уязвимость, возникающая при падении сервера или непредвиденных ошибках. Если стандартный recovery обработчик возвращает клиенту сырой стек вызовов (`runtime/debug.Stack()`), злоумышленник узнает:
- Внутреннюю файловую структуру сервера (`/home/deploy/project/internal/...`).
- Точные версии сторонних Go-модулей и зависимостей.
- Имена приватных функций, структур, полей и внутренних методов.
- Иногда фрагменты запросов к БД, конфигурационные переменные или фрагменты SQL-запросов.

Стандарт Enterprise-безопасности:
1. Каждому входящему HTTP-запросу присваивается уникальный `Request-ID` (UUIDv4 или 16 байт random).
2. При возникновении паники через `recover()` полный стек вызовов, ошибка и `Request-ID` логируются во внутренний защищенный лог (ELK, Loki, ClickHouse, Datadog).
3. Клиенту возвращается строго обезличенный ответ с кодом `500 Internal Server Error` и публичным `request_id`, по которому инженер поддержки сможет найти лог.

## Решение по шагам

1. Создайте middleware `RecoveryWithSanitization(logger InternalLogger) func(http.Handler) http.Handler`.
2. В `defer` функции вызовите `recover()`.
3. Если паника произошла, получите сырой стек трейс через `debug.Stack()`.
4. Залогируйте инцидент во внутренний журнал с уровнем ERROR.
5. Проверьте, не были ли уже отправлены заголовки клиенту.
6. Отправьте безопасный JSON: `{"error": "Internal Server Error", "request_id": reqID}` со статусом 500.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"net/http/httptest"
	"os"
	"runtime/debug"
)

type ErrorResponse struct {
	Error     string `json:"error"`
	RequestID string `json:"request_id"`
}

func generateRequestID() string {
	b := make([]byte, 8)
	_, _ = rand.Read(b)
	return hex.EncodeToString(b)
}

func PanicRecoveryMiddleware(internalLog *log.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			reqID := r.Header.Get("X-Request-ID")
			if reqID == "" {
				reqID = generateRequestID()
			}
			w.Header().Set("X-Request-ID", reqID)

			defer func() {
				if rec := recover(); rec != nil {
					// 1. Полный детальный стек трейс для инженеров пишется ТОЛЬКО во внутренний лог
					stackTrace := debug.Stack()
					internalLog.Printf("[PANIC RECOVERED] RequestID=%s Path=%s Error=%v\nStack:\n%s",
						reqID, r.URL.Path, rec, string(stackTrace))

					// 2. Клиенту возвращается строго обезличенный JSON
					w.Header().Set("Content-Type", "application/json; charset=utf-8")
					w.WriteHeader(http.StatusInternalServerError) // 500

					resp := ErrorResponse{
						Error:     "Internal server error. Please contact support with request_id.",
						RequestID: reqID,
					}
					_ = json.NewEncoder(w).Encode(resp)
				}
			}()

			next.ServeHTTP(w, r)
		})
	}
}

func BuggyHandler(w http.ResponseWriter, r *http.Request) {
	// Симуляция критической ошибки (nil pointer dereference)
	var ptr *string
	fmt.Println(*ptr) // ВЫЗЫВАЕТ ПАНИКУ
}

func main() {
	internalLogger := log.New(os.Stderr, "[INTERNAL-SECURITY-LOG] ", log.LstdFlags)

	handler := PanicRecoveryMiddleware(internalLogger)(http.HandlerFunc(BuggyHandler))

	req := httptest.NewRequest(http.MethodGet, "/api/crash-me", nil)
	rec := httptest.NewRecorder()

	fmt.Println("Выполняем запрос к обработчику с паникой...")
	handler.ServeHTTP(rec, req)

	fmt.Printf("\n--- ОТВЕТ КЛИЕНТУ (HTTP %d) ---\n", rec.Code)
	fmt.Println(rec.Body.String())
}
```

ℹ️ Middleware безопасной обработки паник с сокрытием технического стека

## Под капотом

В Go рантайме каждая горутина имеет собственный стек вызовов.
Когда вызывается `panic()`, рантайм начинает размотку стека текущей горутины (stack unwinding), поочередно вызывая все зарегистрированные операторы `defer` в порядке LIFO.
Если паника не перехвачена через `recover()`, рантайм завершает весь процесс приложения с ненулевым кодом выхода и дампом стека в `stderr`.
Критически важный нюанс: `recover()` работает **только в той же самой горутине**, где возникла паника! Если обработчик запустил фоновую горутину `go func() { panic(...) }()`, middleware внешнего HTTP-сервера ее не перехватит, и всё приложение упадет.

## Подводные камни

1. Запуск неконтролируемых фоновых горутин без `recover()`: `go doWork()` без внутреннего перехвата паники приведет к аварийной остановке всего HTTP-сервера. Всегда оборачивайте фоновые горутины в безопасный `safeGo`.
2. Попытка вызова `w.WriteHeader(500)` после того, как обработчик уже начал отправлять тело клиенту (`Flush` / потоковый вывод): заголовки уже ушли в сокет, и повторная запись вызовет предупреждение `superfluous response.WriteHeader call`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go панику нельзя перехватить внешним middleware, если она произошла в дочерней горутине `go func()`?
**Ответ:** Механизм `recover()` в Go runtime привязан к структуре `g` (текущей горутине). Каждая горутина управляет собственной цепочкой фреймов вызовов `_defer`. Паника раскручивает только стек текущей горутины `g`. Если стек исчерпан и паника не обработана внутри этой горутины, рантайм вызывает функцию `fatalpanic()`, которая аварийно завершает весь процесс операционной системы. Поэтому любая порожденная горутина обязана иметь собственный `defer func() { recover() }()`.
