# Secure Cookies и HSTS

## Условие

Настройте выдачу cookie с обязательными флагами безопасности: HttpOnly, Secure, SameSite=Strict, Path, MaxAge. Добавьте middleware, которое устанавливает заголовок Strict-Transport-Security: max-age=31536000; includeSubDomains; preload.

### Исходная формулировка

**[Secure Cookies & HSTS]**: Настрой выдачу cookie с флагами `HttpOnly`, `Secure`, `SameSite=Strict`. Добавьте middleware, которое устанавливает заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` для принудительного использования HTTPS.

## Теория

Куки аутентификации (Session Cookies) — главная мишень злоумышленников при атаках на веб-приложения.

Атрибуты безопасности HTTP Cookie:
1. `HttpOnly`: Запрещает доступ к cookie через JavaScript API (`document.cookie`). Защищает сессию от кражи при успешной XSS-атаке.
2. `Secure`: Предписывает браузеру передавать cookie **только по защищенному TLS/HTTPS соединению**. Предотвращает перехват сессии в незашифрованных сетях (открытый Wi-Fi, MITM).
3. `SameSite`:
   - `SameSite=Strict`: cookie не отправляется ни при каких межсайтовых переходах (даже при клике по ссылке с внешнего сайта).
   - `SameSite=Lax`: cookie отправляется только при безопасной навигации верхнего уровня (top-level GET).
   - `SameSite=None`: требуется обязательный флаг `Secure`.
4. `Path=/`: явно ограничивает область действия cookie.
5. `MaxAge` / `Expires`: предотвращает сохранение «вечных» сессий.

Заголовок `Strict-Transport-Security (HSTS)` принуждает браузер использовать HTTPS для всех последующих обращений к сайту и его поддоменам.

## Решение по шагам

1. Создайте функцию `IssueSecureCookie(w http.ResponseWriter, name, value string, duration time.Duration)`.
2. Задайте параметры: `HttpOnly: true`, `Secure: true`, `SameSite: http.SameSiteStrictMode`, `Path: "/"`.
3. Напишите middleware `HSTSMiddleware(next http.Handler) http.Handler`, устанавливающий строгий HSTS-заголовок.
4. Создайте HTTP-тест и проверьте атрибуты установленных кук через `rec.Result().Cookies()`.
5. Убедитесь в наличии заголовка `Strict-Transport-Security`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func IssueSecureSessionCookie(w http.ResponseWriter, sessionToken string, ttl time.Duration) {
	cookie := &http.Cookie{
		Name:     "__Host-SessionID", // Использование защищенного префикса __Host-
		Value:    sessionToken,
		Path:     "/",
		MaxAge:   int(ttl.Seconds()),
		HttpOnly: true,                   // Защита от кражи через XSS
		Secure:   true,                   // Передача СТРОГО по HTTPS
		SameSite: http.SameSiteStrictMode, // Максимальная защита от CSRF
	}
	http.SetCookie(w, cookie)
}

func HSTSMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// HSTS заголовок на 1 год с включением поддоменов и preload
		w.Header().Set("Strict-Transport-Security", "max-age=31536000; includeSubDomains; preload")
		next.ServeHTTP(w, r)
	})
}

func LoginHandler(w http.ResponseWriter, r *http.Request) {
	// Симуляция успешной аутентификации
	token := "sec_tok_98f12a3b4c5d6e7f8a9b0c1d2e3f4a5b"
	IssueSecureSessionCookie(w, token, 24*time.Hour)
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("Authenticated successfully"))
}

func main() {
	handler := HSTSMiddleware(http.HandlerFunc(LoginHandler))

	req := httptest.NewRequest(http.MethodPost, "/auth/login", nil)
	rec := httptest.NewRecorder()

	handler.ServeHTTP(rec, req)

	fmt.Println("HTTP Status Code:", rec.Code)
	fmt.Println("HSTS Header:     ", rec.Header().Get("Strict-Transport-Security"))

	cookies := rec.Result().Cookies()
	if len(cookies) > 0 {
		c := cookies[0]
		fmt.Printf("\nПараметры выданной Cookie:\n")
		fmt.Println("Name:    ", c.Name)
		fmt.Println("Value:   ", c.Value)
		fmt.Println("HttpOnly:", c.HttpOnly)
		fmt.Println("Secure:  ", c.Secure)
		fmt.Println("SameSite:", c.SameSite) // 3 = SameSiteStrictMode
		fmt.Println("Path:    ", c.Path)
		fmt.Println("MaxAge:  ", c.MaxAge)
	}
}
```

## Под капотом

Что такое Cookie Prefixes (`__Host-` и `__Secure-`)?
Браузеры поддерживают стандарт IETF Cookie Prefixes:
Если cookie называется с префиксом `__Host-` (например `__Host-SessionID`):
1. Она обязана иметь флаг `Secure: true`.
2. Она обязана быть установлена со страницы, загруженной по HTTPS.
3. Она обязана иметь `Path: /`.
4. Она **не может** содержать атрибут `Domain` (что запрещает поддоменам `sub.company.com` перезаписывать или перехватывать cookie основного домена).
Если сервер попытается нарушить хоть одно из этих правил, браузер отвергнет установку куки.

## Подводные камни

1. Забывать флаг `Secure` на localhost при разработке: если разработчик ставит условие `if env == "prod" { cookie.Secure = true }`, при ошибке конфигурации окружения флаг может быть случайно отключен в проде.
2. Использование `SameSite=None` без флага `Secure`: современные браузеры (Chrome, Firefox) отклоняют любые куки с `SameSite=None`, если флаг `Secure` отсутствует.

## На собеседовании

**Вопрос с собеседования:** В чем разница между префиксом `__Secure-` и префиксом `__Host-` для cookie?
**Ответ:**
- `__Secure-` требует только наличия флага `Secure: true` и защищенного HTTPS-соединения. Кука с таким префиксом может иметь `Domain: company.com` и быть доступна всем поддоменам.
- `__Host-` гораздо строже: помимо флага `Secure` он требует `Path=/` и **запрещает** установку атрибута `Domain`. Это гарантирует, что кука привязана исключительно к конкретному хосту и не может быть перезаписана (Cookie Tossing) скомпрометированным поддоменом.
