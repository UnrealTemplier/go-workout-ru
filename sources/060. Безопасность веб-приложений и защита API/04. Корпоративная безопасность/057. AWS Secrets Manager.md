# AWS Secrets Manager: интеграция через IAM Roles (IRSA)

## Условие

Интегрируйтесь с AWS Secrets Manager с использованием AWS SDK for Go v2. Используйте IAM Roles for Service Accounts (IRSA) вместо хардкода статичных Access Key и Secret Key. Реализуйте кэширование секрета в оперативной памяти с автоматическим обновлением.

### Исходная формулировка

**AWS Secrets Manager**: Интегрируйтесь с AWS Secrets Manager. Используйте IAM roles вместо access keys.

## Теория

AWS Secrets Manager — сервис безопасного хранения, ротации и аудита секретов в облаке Amazon Web Services.

Главное правило облачной безопасности:
**Никогда не использовать статические ключи доступа (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) внутри контейнеров.**
Статические ключи забывают ротировать, их случайно коммитят в git, а при взломе контейнера злоумышленник получает постоянный доступ ко всему облачному аккаунту.

Современный стандарт: **IAM Roles for Service Accounts (IRSA) в Amazon EKS**:
1. Pod в Kubernetes связывается с Kubernetes `ServiceAccount`.
2. AWS OpenID Connect (OIDC) Identity Provider валидирует служебный токен пода.
3. AWS Security Token Service (STS) генерирует временные короткоживущие учетные данные роли IAM (ротация каждый час).
4. Go SDK `aws-sdk-go-v2` с помощью `config.LoadDefaultConfig(ctx)` автоматически обнаруживает IRSA окружение без единой строчки дополнительного кода!

## Решение по шагам

1. Создайте структуру кэша секрета `CachedSecret` со временем экспирации и мьютексом.
2. Напишите функцию получения секрета из AWS Secrets Manager с поддержкой in-memory кэширования (TTL = 15 минут).
3. Смоделируйте клиент AWS Secrets Manager через интерфейс `SecretsManagerAPI`.
4. Реализуйте разбор JSON-секрета в DTO конфигурации.
5. Продемонстрируйте тестами кэширование и обновление при истечении TTL.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"sync"
	"time"
)

type DatabaseConfig struct {
	Host     string `json:"host"`
	Port     int    `json:"port"`
	Username string `json:"username"`
	Password string `json:"password"`
	DBName   string `json:"dbname"`
}

// Интерфейс совместимый с AWS SDK v2 SecretsManagerClient
type SecretsManagerAPI interface {
	GetSecretValue(ctx context.Context, secretID string) (string, error)
}

// Кэширующий декоратор для AWS Secrets Manager
type CachedSecretsManager struct {
	api       SecretsManagerAPI
	ttl       time.Duration
	mu        sync.RWMutex
	cache     map[string]cachedItem
}

type cachedItem struct {
	value     string
	expiresAt time.Time
}

func NewCachedSecretsManager(api SecretsManagerAPI, ttl time.Duration) *CachedSecretsManager {
	return &CachedSecretsManager{
		api:   api,
		ttl:   ttl,
		cache: make(map[string]cachedItem),
	}
}

func (c *CachedSecretsManager) GetSecret(ctx context.Context, secretName string) (string, error) {
	c.mu.RLock()
	item, ok := c.cache[secretName]
	c.mu.RUnlock()

	// Если значение есть в кэше и не просрочено — возвращаем моментально из RAM
	if ok && time.Now().Before(item.expiresAt) {
		return item.value, nil
	}

	c.mu.Lock()
	defer c.mu.Unlock()

	// Double-check locking паттерн
	if item, ok := c.cache[secretName]; ok && time.Now().Before(item.expiresAt) {
		return item.value, nil
	}

	// Запрашиваем секрет из AWS
	fmt.Printf("🌐 [AWS Network Request] Запрос секрета '%s' из Secrets Manager API...\n", secretName)
	val, err := c.api.GetSecretValue(ctx, secretName)
	if err != nil {
		return "", err
	}

	c.cache[secretName] = cachedItem{
		value:     val,
		expiresAt: time.Now().Add(c.ttl),
	}

	return val, nil
}

// Симулятор AWS Secrets Manager API
type MockAWSSecretsManagerClient struct {
	secrets map[string]string
}

func (m *MockAWSSecretsManagerClient) GetSecretValue(ctx context.Context, secretID string) (string, error) {
	val, ok := m.secrets[secretID]
	if !ok {
		return "", errors.New("ResourceNotFoundException: secret not found")
	}
	return val, nil
}

func main() {
	mockAWS := &MockAWSSecretsManagerClient{
		secrets: map[string]string{
			"prod/rds/postgres": `{
				"host": "postgres.internal.cluster",
				"port": 5432,
				"username": "admin_app",
				"password": "AWS_Secret_P@ssw0rd_Generated_By_KMS_2026",
				"dbname": "payments"
			}`,
		},
	}

	// Инициализируем менеджер с TTL кэша 1 секунда для теста
	cachedManager := NewCachedSecretsManager(mockAWS, 1*time.Second)

	ctx := context.Background()

	// 1. Первый вызов — сетевой запрос в AWS
	rawSecret1, err := cachedManager.GetSecret(ctx, "prod/rds/postgres")
	if err != nil {
		panic(err)
	}

	var dbCfg DatabaseConfig
	_ = json.Unmarshal([]byte(rawSecret1), &dbCfg)
	fmt.Printf("Секрет успешно получен: User=%s, Host=%s\n\n", dbCfg.Username, dbCfg.Host)

	// 2. Второй вызов — чтение из локального кэша RAM (без сетевого RTT!)
	fmt.Println("Повторный запрос того же секрета:")
	_, _ = cachedManager.GetSecret(ctx, "prod/rds/postgres")
	fmt.Println("Второй запрос выполнен мгновенно из кэша памяти.")

	// 3. Ждем истечения TTL
	time.Sleep(1100 * time.Millisecond)
	fmt.Println("\nПосле истечения TTL кэша:")
	_, _ = cachedManager.GetSecret(ctx, "prod/rds/postgres")
}
```

ℹ️ Паттерн интеграции с AWS Secrets Manager с in-memory кэшированием и защитой от перерасхода API

## Под капотом

Зачем обязательно кэшировать секреты из AWS Secrets Manager?
1. **Стоимость (Billing):** Каждый вызов `GetSecretValue` стоит $0.05 за 10 000 вызовов. Если микросервис с 10 000 RPS будет запрашивать секрет на каждый входящий HTTP-запрос, счет за облако составит тысячи долларов в день!
2. **API Throttling Limits:** По умолчанию AWS Secrets Manager имеет жесткий региональный лимит TPS (обычно 5000-10000 запросов в секунду). При превышении лимита AWS вернет ошибку `ThrottlingException`, что вызовет лавинообразный отказ всех микросервисов кластера.
Кэширование на 5-15 минут устраняет обе проблемы.

## Подводные камни

1. Хардкод AWS Credentials в переменных `AWS_ACCESS_KEY_ID`: используйте дефолтную цепочку провайдеров (`DefaultCredentialsProvider`), которая автоматически подтягивает токены из метаданных EC2 / IRSA EKS.
2. Бесконечный кэш: если закэшировать секрет навсегда (`time.Hour * 1000`), сервис не сможет узнать об автоматической ротации пароля в AWS Secrets Manager без перезапуска подов.

## На собеседовании

**Вопрос с собеседования:** Как устроен механизм IAM Roles for Service Accounts (IRSA) под капотом в Kubernetes?
**Ответ:**
1. В pod монтируется projected volume с OIDC токеном служебного аккаунта ServiceAccount (`/var/run/secrets/eks.amazonaws.com/serviceaccount/token`).
2. В pod выставляются переменные `AWS_ROLE_ARN` и `AWS_WEB_IDENTITY_TOKEN_FILE`.
3. При старте AWS SDK в Go обнаруживает эти переменные и вызывает метод `sts:AssumeRoleWithWebIdentity`, передавая JWT токен пода в AWS STS.
4. STS проверяет криптографическую подпись токена через публичные ключи OIDC провайдера EKS кластера.
5. STS возвращает временные учетные данные (`AccessKeyId`, `SecretAccessKey`, `SessionToken`) с правами запрошенной IAM роли, которые SDK автоматически обновляет по таймеру.
