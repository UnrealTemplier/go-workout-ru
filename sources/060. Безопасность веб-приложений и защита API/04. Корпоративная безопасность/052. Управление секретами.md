# Управление секретами: предотвращение утечек и интеграция с Secrets Manager

## Условие

Покажите, как секреты (пароли БД, API-ключи, JWT-секреты) утекают в Git-репозитории, дампы логов, переменные окружения через /proc/self/environ. Реализуйте архитектуру безопасного чтения секретов, очистку памяти (Memory Zeroing) и интеграцию с Secrets Manager.

### Исходная формулировка

**Никогда не хранить секреты в коде/ENV в plain**: Покажите, как секреты утекают в Git, логи, error messages. Используйте Secret Managers.

## Теория

Почему хранение секретов в plaintext в исходном коде или переменных окружения опасно:
1. **Утечки в Git:** Случайный `git commit` с файлом `.env` или конфигом `config.yaml` навсегда сохраняет секрет в истории коммитов git.
2. **Дампы окружения через /proc/self/environ:** В Linux любой локальный процесс с правами пользователя может прочесть переменные окружения другого процесса через псевдофайловую систему `/proc/<PID>/environ`.
3. **Логирование и метрики:** При панике или отладке переменные окружения часто попадают в системы сбора логов (Sentry, Datadog).
4. **Остатки в оперативной памяти (Core Dumps):** При аварийном завершении ОС сбрасывает образ памяти (Core Dump) на диск.

Архитектура корпоративного управления секретами (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager):
1. Никаких статичных секретов в коде.
2. Секреты запрашиваются при старте сервиса через mTLS/IAM-роль по защищенному каналу.
3. Чувствительные данные в памяти хранятся в виде срезов байт `[]byte` и зануляются сразу после использования (`subtle` или цикл обнуления) для предотвращения их сохранения в heap-дампах.

## Решение по шагам

1. Создайте интерфейс `SecretsProvider` с методом `GetSecret(ctx context.Context, key string) ([]byte, error)`.
2. Реализуйте симулятор Secret Manager (интеграция с Vault/AWS).
3. Реализуйте функцию безопасного обнуления среза байт в памяти `ZeroMemory(b []byte)`.
4. Покажите, как правильно инициализировать криптографические ключи без сохранения их в глобальных строковых переменных.
5. Продемонстрируйте предотвращение утечек секретов в логах.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"crypto/subtle"
	"errors"
	"fmt"
	"sync"
	"time"
)

// ZeroMemory гарантированно зануляет память среза для защиты от дампа памяти
func ZeroMemory(b []byte) {
	for i := range b {
		b[i] = 0
	}
}

type SecretsProvider interface {
	GetSecret(ctx context.Context, secretName string) ([]byte, error)
}

// Симулятор интеграции с корпоративным HashiCorp Vault / AWS Secrets Manager
type MockVaultClient struct {
	mu      sync.RWMutex
	storage map[string][]byte
}

func NewMockVaultClient() *MockVaultClient {
	return &MockVaultClient{
		storage: map[string][]byte{
			"db/credentials":  []byte("postgres://app_user:Kx9#mZ$29_vault_secret@db.prod:5432/main"),
			"jwt/signing-key": []byte("prod_jwt_super_secret_signing_key_2026_09"),
		},
	}
}

func (v *MockVaultClient) GetSecret(ctx context.Context, secretName string) ([]byte, error) {
	v.mu.RLock()
	defer v.mu.RUnlock()

	val, exists := v.storage[secretName]
	if !exists {
		return nil, errors.New("secret not found in vault")
	}

	// Возвращаем копию байт, чтобы вызывающий код мог безопасно занулить ее после использования
	copied := make([]byte, len(val))
	copy(copied, val)
	return copied, nil
}

type DatabaseConnection struct {
	dsn []byte
}

func ConnectToDatabase(provider SecretsProvider) (*DatabaseConnection, error) {
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	rawSecret, err := provider.GetSecret(ctx, "db/credentials")
	if err != nil {
		return nil, fmt.Errorf("failed to fetch database secret: %w", err)
	}

	// Создаем подключение
	conn := &DatabaseConnection{dsn: rawSecret}

	return conn, nil
}

func (c *DatabaseConnection) Close() {
	// При закрытии соединения обнуляем секрет в оперативной памяти!
	ZeroMemory(c.dsn)
	c.dsn = nil
}

func main() {
	vault := NewMockVaultClient()

	fmt.Println("=== 1. ПОЛУЧЕНИЕ СЕКРЕТА ИЗ VAULT ===")
	conn, err := ConnectToDatabase(vault)
	if err != nil {
		panic(err)
	}

	// Секрет находится в оперативной памяти
	fmt.Printf("Подключение активно. Размер DSN в памяти: %d байт\n", len(conn.dsn))

	// Проверяем работу с секретом константным временем (защита от timing attacks)
	expectedPrefix := []byte("postgres://")
	matches := subtle.ConstantTimeCompare(conn.dsn[:len(expectedPrefix)], expectedPrefix) == 1
	fmt.Println("Проверка валидности протокола DSN:", matches)

	// Закрываем соединение и очищаем память
	conn.Close()

	fmt.Println("\n=== 2. ОЧИСТКА ПАМЯТИ (ZEROING) ===")
	fmt.Println("Соединение закрыто, секрет гарантированно занулен в RAM.")
}
```

## Под капотом

Почему обычные строки `string` в Go опасны для хранения паролей?
Строки в Go являются иммутабельными (неизменяемыми).
Если создать строку `password := "SuperSecret123"`, Go рантайм выделяет под нее память в куче.
Вы не можете изменить или стереть эти байты: при выходе переменной из области видимости память остается в куче до тех пор, пока сборщик мусора GC не выполнит sweep-фазу. Даже после работы GC байты пароля могут оставаться в физической памяти операционной системы вплоть до перезаписи новыми аллокациями.
Использование срезов байт `[]byte` позволяет разработчику явно затереть конфиденциальные данные нулями (`b[i] = 0`) сразу после использования.

## Подводные камни

1. Оптимизации компилятора: в некоторых компиляторах (C/C++) компилятор может удалить цикл зануления памяти (`Dead Store Elimination`), посчитав, что память больше не читается. В Go для гарантированного обнуления чувствительных структур можно использовать функции из пакета `crypto/subtle`.
2. Коммит тестовых токенов в публичные репозитории: используйте pre-commit хуки (GitGuardian, Trufflehog, Gitleaks) для автоматической блокировки коммитов с секретами.

## На собеседовании

**Вопрос с собеседования:** В чем преимущества динамических секретов (Dynamic Secrets) в HashiCorp Vault по сравнению со статическими паролями?
**Ответ:** Статический секрет (например, фиксированный пароль к базе данных) живет месяцами или годами, и в случае компрометации его ротация требует ручного вмешательства и перезапуска всех сервисов.
Vault поддерживает **Dynamic Secrets**:
Микросервис запрашивает у Vault учетные данные к PostgreSQL. Vault на лету генерирует в базе данных уникального временного пользователя с ограниченным временем жизни (TTL = 1 час): `v-token-app-12345`. По истечении срока действия Vault автоматически отзывает пользователя и удаляет его из базы данных. Если секрет утечет, он станет недействительным через считанные минуты.
