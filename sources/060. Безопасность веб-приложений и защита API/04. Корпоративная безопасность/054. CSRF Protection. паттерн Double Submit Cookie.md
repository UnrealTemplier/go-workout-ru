# CSRF Protection: паттерн Double Submit Cookie

## Условие

Реализуйте паттерн Double Submit Cookie: при GET-запросе выдавайте псевдослучайный криптографический CSRF-токен в Cookie и в заголовке ответа. При небезопасных запросах (POST, PUT, DELETE) middleware должно сравнивать токен из Cookie и токен из заголовка X-CSRF-Token константным временем.

### Исходная формулировка

**[CSRF Protection]**: Реализуй паттерн Double Submit Cookie: при GET запросе выдавай CSRF-токен в куки и в мета-тег. При POST запросе middleware должно сравнивать токен из куки и из заголовка `X-CSRF-Token`.

## Теория

Паттерн Double Submit Cookie — эффективный Stateless механизм защиты от CSRF.
В отличие от Synchronizer Token Pattern, серверу не требуется хранить токены в Redis или базе данных сессий.

Механика работы:
1. При первом GET-запросе сервер генерирует случайный токен (32 байта `crypto/rand`).
2. Токен отправляется клиенту в cookie: `csrf_token=<token>` (флаги: `SameSite=Lax`, `Secure=true`, но **без** `HttpOnly`, чтобы клиентский JavaScript мог его прочесть).
3. При отправке формы или AJAX-запроса клиентский JavaScript считывает куку и дублирует ее значение в кастомный HTTP-заголовок `X-CSRF-Token: <token>`.
4. Серверный middleware извлекает значение из Cookie и из заголовка `X-CSRF-Token` и сравнивает их через `subtle.ConstantTimeCompare`.
5. Почему атака невозможна: по правилам Same-Origin Policy (SOP) вредоносный сайт `evil.com` не может прочитать Cookie целевого домена `bank.com`, а значит, атакующий не знает токена и не может добавить правильный заголовок `X-CSRF-Token`.

## Решение по шагам

1. Создайте генератор токенов `generateToken() (string, error)` через `crypto/rand`.
2. Реализуйте middleware `DoubleSubmitCSRFMiddleware(next http.Handler) http.Handler`.
3. При GET-запросе проверьте наличие cookie `csrf_token`. Если отсутствует, сгенерируйте и установите.
4. При POST/PUT/DELETE запросах извлеките cookie `csrf_token` и заголовок `X-CSRF-Token`.
5. Сравните значения через `subtle.ConstantTimeCompare`.
6. При несовпадении верните статус `403 Forbidden`.
7. Протестируйте сценарий атаки и сценарий легитимного клиента.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

const CSRFCookieName = "csrf_token"
const CSRFHeaderName = "X-CSRF-Token"

func generateCSRFToken() string {
	b := make([]byte, 32)
	_, _ = rand.Read(b)
	return hex.EncodeToString(b)
}

func DoubleSubmitCSRFMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		cookie, err := r.Cookie(CSRFCookieName)
		var cookieToken string

		if err == nil && cookie.Value != "" {
			cookieToken = cookie.Value
		} else {
			// Если cookie нет, генерируем новый токен
			cookieToken = generateCSRFToken()
			http.SetCookie(w, &http.Cookie{
				Name:     CSRFCookieName,
				Value:    cookieToken,
				Path:     "/",
				Secure:   true,
				HttpOnly: false, // Фронтенд должен иметь возможность прочитать токен для XHR
				SameSite: http.SameSiteLaxMode,
			})
		}

		// Безопасные методы по RFC (не меняющие состояние)
		if r.Method == http.MethodGet || r.Method == http.MethodHead || r.Method == http.MethodOptions {
			w.Header().Set(CSRFHeaderName, cookieToken)
			next.ServeHTTP(w, r)
			return
		}

		// Для небезопасных методов (POST, PUT, DELETE) требуем заголовок X-CSRF-Token
		headerToken := r.Header.Get(CSRFHeaderName)
		if headerToken == "" || cookieToken == "" {
			http.Error(w, "Forbidden: Missing CSRF token", http.StatusForbidden)
			return
		}

		// Сравнение токенов константным временем
		if subtle.ConstantTimeCompare([]byte(headerToken), []byte(cookieToken)) != 1 {
			http.Error(w, "Forbidden: CSRF token mismatch", http.StatusForbidden)
			return
		}

		next.ServeHTTP(w, r)
	})
}

func main() {
	handler := DoubleSubmitCSRFMiddleware(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("Action completed successfully"))
	}))

	// Шаг 1: Клиент делает GET запрос и получает CSRF cookie
	getReq := httptest.NewRequest(http.MethodGet, "/dashboard", nil)
	getRec := httptest.NewRecorder()
	handler.ServeHTTP(getRec, getReq)

	csrfCookie := getRec.Result().Cookies()[0]
	token := csrfCookie.Value
	fmt.Println("Issued CSRF Token:", token[:16]+"...")

	// Шаг 2: Легитимный POST запрос (кука + правильный заголовок X-CSRF-Token)
	legitReq := httptest.NewRequest(http.MethodPost, "/update-email", strings.NewReader("email=user@work.com"))
	legitReq.AddCookie(csrfCookie)
	legitReq.Header.Set(CSRFHeaderName, token)
	recLegit := httptest.NewRecorder()
	handler.ServeHTTP(recLegit, legitReq)
	fmt.Printf("Legitimate Request: Status=%d, Body=%s\n", recLegit.Code, recLegit.Body.String())

	// Шаг 3: CSRF Атака (кука отправлена браузером автоматически, но злоумышленник не знает заголовок)
	evilReq := httptest.NewRequest(http.MethodPost, "/update-email", strings.NewReader("email=hacker@evil.com"))
	evilReq.AddCookie(csrfCookie)
	// Злоумышленник либо не передал заголовок, либо передал наугад
	evilReq.Header.Set(CSRFHeaderName, "fake_token_attempt_123")
	recEvil := httptest.NewRecorder()
	handler.ServeHTTP(recEvil, evilReq)
	fmt.Printf("CSRF Attack:        Status=%d, Body=%s\n", recEvil.Code, strings.TrimSpace(recEvil.Body.String()))
}
```

## Под капотом

Слабое место наивного Double Submit Cookie:
Если злоумышленник контролирует какой-либо поддомен (например, уязвимость в блоге на `blog.company.com`), он может применить технику **Cookie Tossing**:
Скрипт на `blog.company.com` устанавливает cookie `csrf_token=attacker_value` с атрибутом `Domain=company.com`.
Затем скрипт посылает форму на `api.company.com` с заголовком `X-CSRF-Token: attacker_value`.
Оба значения совпадут, и наивный Double Submit будет обойден!

Для защиты от Cookie Tossing в Enterprise-системах используют **Signed Double Submit Cookie** (HMAC):
Сервер подписывает значение CSRF токена секретным ключом: `csrf_token = token + "." + HMAC(token, secret)`. При POST запросе сервер сначала валидирует подпись куки, что исключает подделку токена через поддомены.

## Подводные камни

1. Установка флага `HttpOnly: true` на CSRF cookie: если установить `HttpOnly`, фронтенд (React, Vue, Axios) не сможет прочитать значение из `document.cookie` и не сможет прикрепить заголовок `X-CSRF-Token`.
2. Использование обычного оператора `==`: всегда сравнивайте токены через `crypto/subtle.ConstantTimeCompare`.

## На собеседовании

**Вопрос с собеседования:** В чем преимущества Signed Double Submit Cookie по сравнению с хранением токенов в сессии Redis?
**Ответ:**
1. **Stateless масштабирование:** Серверам не нужно обращаться в сетевое хранилище Redis при каждом HTTP-запросе для проверки токена, что снижает нагрузку на сеть и БД.
2. **Нулевая задержка (Zero latency):** Валидация криптографической HMAC-подписи происходит локально в CPU за доли микросекунды.
3. **Отказоустойчивость:** Падение или перезагрузка Redis-кластера не приводит к инвалидации пользовательских форм и сбою активных сессий.
