# HashiCorp Vault: аутентификация через AppRole

## Условие

Реализуйте интеграцию приложения Go с HashiCorp Vault по протоколу AppRole. Покажите обмен RoleID и SecretID на клиентский Vault Token и чтение секретов по пути secret/data/myapp.

### Исходная формулировка

**HashiCorp Vault integration**: Настройте Vault в Docker, получите секреты из Go-приложения через AppRole аутентификацию.

## Теория

HashiCorp Vault — индустриальный стандарт управления секретами, шифрованием данных и PKI в Enterprise и Cloud-Native архитектурах.

Метод аутентификации **AppRole**:
Спроектирован специально для автоматизированных сервисов и микросервисов (Machine-to-Machine authentication).
1. `RoleID`: публичный идентификатор роли сервиса (аналог логина, зашивается в манифест развертывания или образ контейнера).
2. `SecretID`: защищенный конфиденциальный секрет с коротким TTL (аналог пароля, доставляется через CI/CD pipeline, Kubernetes Secret или Ansible).
3. При старте Go-приложение отправляет POST запрос к Vault:
   `POST /v1/auth/approle/login {"role_id": "...", "secret_id": "..."}`
4. Vault проверяет учетные данные, права доступа по политикам (ACL) и возвращает временный `client_token`.
5. С этим токеном приложение обращается к эндпоинту KV Secrets Engine v2:
   `GET /v1/secret/data/myapp` с заголовком `X-Vault-Token`.

## Решение по шагам

1. Создайте структуры JSON-запросов и ответов API Vault: `AppRoleLoginRequest`, `VaultLoginResponse`, `KVSecretResponse`.
2. Создайте HTTP-сервер mock-Vault для симуляции реального окружения Vault.
3. Реализуйте клиент Vault на Go с методом `LoginAppRole(roleID, secretID string) (string, error)`.
4. Реализуйте метод `ReadSecret(token, secretPath string) (map[string]string, error)`.
5. Продемонстрируйте безопасный процесс аутентификации и извлечения паролей БД.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"time"
)

type VaultClient struct {
	baseURL    string
	httpClient *http.Client
}

func NewVaultClient(baseURL string) *VaultClient {
	return &VaultClient{
		baseURL: baseURL,
		httpClient: &http.Client{
			Timeout: 5 * time.Second,
		},
	}
}

type AppRoleLoginRequest struct {
	RoleID   string `json:"role_id"`
	SecretID string `json:"secret_id"`
}

type VaultAuthResponse struct {
	Auth struct {
		ClientToken   string   `json:"client_token"`
		Policies      []string `json:"policies"`
		LeaseDuration int      `json:"lease_duration"`
	} `json:"auth"`
}

type KVSecretV2Response struct {
	Data struct {
		Data map[string]string `json:"data"`
	} `json:"data"`
}

// 1. Обмен RoleID и SecretID на клиентский Vault токен
func (c *VaultClient) LoginAppRole(roleID, secretID string) (string, error) {
	reqBody, _ := json.Marshal(AppRoleLoginRequest{
		RoleID:   roleID,
		SecretID: secretID,
	})

	url := fmt.Sprintf("%s/v1/auth/approle/login", c.baseURL)
	resp, err := c.httpClient.Post(url, "application/json", bytes.NewReader(reqBody))
	if err != nil {
		return "", err
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		body, _ := io.ReadAll(resp.Body)
		return "", fmt.Errorf("vault login failed (status %d): %s", resp.StatusCode, string(body))
	}

	var authResp VaultAuthResponse
	if err := json.NewDecoder(resp.Body).Decode(&authResp); err != nil {
		return "", err
	}

	return authResp.Auth.ClientToken, nil
}

// 2. Чтение секретов из KV v2 Secrets Engine
func (c *VaultClient) ReadSecretKV2(token, path string) (map[string]string, error) {
	url := fmt.Sprintf("%s/v1/secret/data/%s", c.baseURL, path)
	req, err := http.NewRequest(http.MethodGet, url, nil)
	if err != nil {
		return nil, err
	}

	// Токен передается в специальном заголовке X-Vault-Token
	req.Header.Set("X-Vault-Token", token)

	resp, err := c.httpClient.Do(req)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("vault read secret failed with status: %d", resp.StatusCode)
	}

	var secretResp KVSecretV2Response
	if err := json.NewDecoder(resp.Body).Decode(&secretResp); err != nil {
		return nil, err
	}

	return secretResp.Data.Data, nil
}

func main() {
	// Симулятор HashiCorp Vault API
	mockVault := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path == "/v1/auth/approle/login" {
			var body AppRoleLoginRequest
			_ = json.NewDecoder(r.Body).Decode(&body)
			if body.RoleID == "order-service-role" && body.SecretID == "sec-id-9812-4123" {
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(`{"auth":{"client_token":"s.vault_client_token_abc123","lease_duration":3600}}`))
				return
			}
			http.Error(w, "invalid role or secret id", http.StatusBadRequest)
			return
		}

		if r.URL.Path == "/v1/secret/data/order-service" {
			if r.Header.Get("X-Vault-Token") == "s.vault_client_token_abc123" {
				w.WriteHeader(http.StatusOK)
				_, _ = w.Write([]byte(`{
					"data": {
						"data": {
							"db_password": "SuperSecurePostgresPassword2026",
							"stripe_key": "sk_live_51M0MockStripeSecretKey"
						}
					}
				}`))
				return
			}
			http.Error(w, "permission denied", http.StatusForbidden)
			return
		}

		http.NotFound(w, r)
	}))
	defer mockVault.Close()

	client := NewVaultClient(mockVault.URL)

	fmt.Println("=== 1. АУТЕНТИФИКАЦИЯ В VAULT ЧЕРЕЗ APPROLE ===")
	token, err := client.LoginAppRole("order-service-role", "sec-id-9812-4123")
	if err != nil {
		panic(err)
	}
	fmt.Printf("Аутентификация успешна! Получен токен: %s\n\n", token)

	fmt.Println("=== 2. ПОЛУЧЕНИЕ ДАННЫХ ИЗ KV-V2 СЕКРЕТОВ ===")
	secrets, err := client.ReadSecretKV2(token, "order-service")
	if err != nil {
		panic(err)
	}

	for k, v := range secrets {
		fmt.Printf("Secret Key: %-15s -> Value: %s\n", k, v)
	}
}
```

## Под капотом

В KV v2 (Key-Value Engine Version 2) путь к данным всегда содержит префикс `/data/` в API (`/v1/secret/data/<path>`), а структура JSON содержит двойную вложенность `{"data": {"data": {...}}}`.
Это связано с версионированием: KV v2 хранит метаданные версий секрета (`version`, `created_time`, `deletion_time`).
При обновлении секрета старые версии не затираются, что позволяет выполнять мгновенный откат (Rollback) при случайном повреждении конфигурации.

## Подводные камни

1. Хранение `SecretID` в том же репозитории Git, где лежит код: `RoleID` и `SecretID` должны доставляться независимыми каналами (Secret Zero Problem).
2. Забывать про продление аренды (Token Renewal): если токен имеет `lease_duration = 3600` (1 час), сервис должен запускать фоновую горутину для вызова `/v1/auth/token/renew-self` до истечения срока действия.

## На собеседовании

**Вопрос с собеседования:** Как решить проблему «Secret Zero» при развертывании приложений в Kubernetes с HashiCorp Vault?
**Ответ:** Проблема Secret Zero — это вопрос того, как доставить первоначальный секрет приложению, не имея секретов.
В Kubernetes стандартным решением является **Vault Kubernetes Auth Method**:
1. Приложению не нужны статичные `RoleID` и `SecretID`.
2. Pod использует свой автоматически смонтированный Kubernetes ServiceAccount Token (`/var/run/secrets/kubernetes.io/serviceaccount/token`).
3. Приложение отправляет этот JWT в Vault (`/v1/auth/kubernetes/login`).
4. Vault обращается к Kubernetes TokenReview API для подтверждения подлинности Pod'а, проверяет его Namespace и ServiceAccount, и выдает временный токен доступа Vault. Никаких паролей в конфигурационных файлах!
