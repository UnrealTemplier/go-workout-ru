# SQL-инъекция в ORDER BY и динамических идентификаторах

## Условие

Вы знаете про параметризованные запросы (WHERE id = $1). Но попробуйте подставить пользовательский ввод в сортировку: SELECT * FROM users ORDER BY $1. Убедитесь, что это НЕ работает (БД экранирует $1 как строковую константу 'id', а не имя столбца). Покажите, почему разработчики конкатенируют строки и допускают SQL-инъекцию, и реализуйте безопасный Whitelist маппинг.

### Исходная формулировка

**SQL-инъекция в ORDER BY**: Ты знаешь про плейсхолдеры (`WHERE id = $1`). Но попробуй подставить пользовательский ввод в сортировку: `SELECT * FROM users ORDER BY $1`. Убедись, что это НЕ работает (БД экранирует это как строку). Из-за этого джуны склеивают строки `ORDER BY ` + userInput (уязвимость!). Напиши безопасный `switch / whitelist` в Go, который строго маппит пользовательские слова ("date_asc") в захардкоженные SQL-куски.

## Теория

Параметризованные запросы (Prepared Statements) работают только для **значений данных** (Data Literals), передаваемых в `WHERE`, `VALUES`, `SET`.
Движок SQL (PostgreSQL, MySQL, SQLite) компилирует AST-дерево запроса до подстановки параметров.
Поэтому параметры **нельзя использовать** для структурных элементов синтаксиса:
- Имен таблиц (`FROM $1`)
- Имен столбцов (`SELECT $1`)
- Направлений сортировки (`ORDER BY $1 ASC`)

Если написать: `db.Query("SELECT * FROM users ORDER BY $1", "salary")`, база данных превратит это в: `SELECT * FROM users ORDER BY 'salary'`. Запрос отсортирует строки по константной строке `'salary'`, что эквивалентно отсутствию сортировки!

Разработчики часто "решают" эту проблему конкатенацией:
`query := fmt.Sprintf("SELECT * FROM users ORDER BY %s", userSort)`
Это открывает критическую уязвимость **SQL Injection в ORDER BY**:
Атакующий передает: `(CASE WHEN (SELECT ascii(substr(password,1,1)) FROM admin)=97 THEN id ELSE username END)`
и с помощью слепой инъекции (Blind SQLi) посимвольно вытаскивает пароли администраторов по изменению порядка сортировки!

Единственное надежное решение: **Строгий Whitelist Mapping** на уровне приложения.

## Решение по шагам

1. Создайте структуру запроса списка пользователей с параметрами `sort_by` и `order`.
2. Объявите мапу разрешенных столбцов: `allowedColumns = map[string]string{"name": "full_name", "created": "created_at"}`.
3. Проверьте направление сортировки: разрешены строго `ASC` и `DESC`.
4. Если пользователь передал недопустимое значение, верните безопасный столбец по умолчанию.
5. Соберите SQL-запрос, используя только проверенные идентификаторы из мапы.
6. Продемонстрируйте защиту от попытки инъекции через `ORDER BY`.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

// Белый список допустимых полей сортировки: публичное имя -> безопасное имя колонки в БД
var allowedSortFields = map[string]string{
	"id":         "users.id",
	"name":       "users.full_name",
	"email":      "users.email",
	"created_at": "users.created_at",
	"balance":    "users.account_balance",
}

type QueryFilter struct {
	SortBy    string
	Direction string
}

func BuildSafeOrderClause(filter QueryFilter) (string, error) {
	// 1. Валидация поля сортировки по строгому словарю
	safeColumn, exists := allowedSortFields[strings.ToLower(strings.TrimSpace(filter.SortBy))]
	if !exists {
		// Либо возвращаем дефолтное поле, либо возвращаем ошибку валидации
		return "", fmt.Errorf("invalid sort field '%s'. Allowed: id, name, email, created_at, balance", filter.SortBy)
	}

	// 2. Валидация направления сортировки (строго ASC или DESC)
	dir := strings.ToUpper(strings.TrimSpace(filter.Direction))
	if dir != "ASC" && dir != "DESC" {
		dir = "ASC" // Дефолтное безопасное направление
	}

	return fmt.Sprintf("ORDER BY %s %s", safeColumn, dir), nil
}

func main() {
	testCases := []QueryFilter{
		{SortBy: "name", Direction: "asc"},
		{SortBy: "balance", Direction: "DESC"},
		// Попытка Blind SQL Injection в ORDER BY
		{SortBy: "(CASE WHEN (1=1) THEN full_name ELSE email END)", Direction: "ASC"},
		// Попытка stacked queries injection
		{SortBy: "id; DROP TABLE users; --", Direction: "ASC"},
	}

	fmt.Println("=== ТЕСТИРОВАНИЕ ЗАЩИТЫ ОТ SQL-ИНЪЕКЦИЙ В ORDER BY ===")
	for _, tc := range testCases {
		orderClause, err := BuildSafeOrderClause(tc)
		if err != nil {
			fmt.Printf("Input Sort: %-52s -> 🛡️ BLOCKED: %v\n", tc.SortBy, err)
		} else {
			query := fmt.Sprintf("SELECT id, full_name, email FROM users %s LIMIT 50;", orderClause)
			fmt.Printf("Input Sort: %-52s -> ✅ SAFE SQL: %s\n", tc.SortBy, query)
		}
	}
}
```

ℹ️ Защита от SQL-инъекций в ORDER BY с использованием безопасного Whitelist Mapping

## Под капотом

Почему СУБД не может параметризовать `ORDER BY $1`?
Протокол PostgreSQL Extended Query (команды Parse, Bind, Execute) производит синтаксический анализ и планирование запроса на этапе Parse.
Оптимизатор запросов PostgreSQL (Cost-based Query Planner) должен знать имена индексов и физические столбцы для выбора подходящего плана исполнения (Index Scan vs Seq Scan). Если столбец сортировки неизвестен до этапа Bind, оптимизатор не сможет построить дерево плана выполнения запроса.

## Подводные камни

1. Попытка санитизировать имена столбцов через экранирование кавычками `fmt.Sprintf("\"%s\"", input)`. Если имя содержит кавычки (`name" OR 1=1`), это может разрушить синтаксис.
2. Использование параметров для названий таблиц в миграциях или динамических шардах без строгого whitelist enum.

## На собеседовании

**Вопрос с собеседования:** Как работает атака Blind SQL Injection через предложение `ORDER BY`?
**Ответ:** Если бэкенд конкатенирует ввод в `ORDER BY`, атакующий внедряет условное выражение:
`ORDER BY (CASE WHEN (ASCII(SUBSTRING((SELECT secret FROM tokens LIMIT 1), 1, 1)) = 65) THEN id ELSE created_at END) ASC`
Если первый символ секрета равен 'A' (код 65), база данных отсортирует записи по полю `id`. Если условие ложно, записи будут отсортированы по `created_at`.
Анализируя порядок возвращенных записей в первом и втором случае, злоумышленник бит за битом восстанавливает любые секретные данные из БД, даже не имея прямого вывода данных на экран.
