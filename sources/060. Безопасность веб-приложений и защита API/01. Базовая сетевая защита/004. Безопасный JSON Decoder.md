# Безопасный JSON Decoder (Глубина вложенности и UseNumber)

## Условие

Напишите обёртку над `json.Decoder`, которая: (1) ограничивает глубину вложенности (защита от stack exhaustion через deeply nested JSON), (2) использует `UseNumber` для предотвращения float64 truncation, (3) проверяет количество ключей в объекте. Объясните, почему `encoding/json` по умолчанию не защищён от этих атак.

### Исходная формулировка

**Безопасный JSON Decoder.**: Напишите обёртку над `json.Decoder`, которая: (1) ограничивает глубину вложенности (защита от stack exhaustion через deeply nested JSON), (2) использует `UseNumber` для предотвращения float64 truncation, (3) проверяет количество ключей в объекте. Объясните, почему `encoding/json` по умолчанию не защищён от этих атак.

## Теория

Стандартный пакет Go `encoding/json` разрабатывался для общего использования и по умолчанию содержит ряд архитектурных особенностей, создающих риски безопасности:

### 1. Stack Exhaustion (Атака глубокой вложенностью):
Если атакующий пришлет JSON с 10 000 вложенных объектов:
`{"a":{"a":{"a":{"a": ... }}}}`,
рекурсивный парсер парсит каждую структуру рекурсивным спуском. Это вызывает исчерпание стека горутины и взрывной рост памяти рантайма.

### 2. Float64 Truncation (Потеря точности чисел):
По умолчанию `encoding/json` парсит все числовые значения в `float64` (IEEE 754 двойной точности). 64-битные целые числа больше \(2^{53} - 1\) (\(9\,007\,199\,254\,740\,991\), например Snowflake ID, Twitter ID или балансы в копейках/сатоши) теряют младшие значащие разряды! Атакующий может манипулировать финансовыми суммами или идентификаторами транзакций. Метод `decoder.UseNumber()` парсит числа как сырую строку `json.Number`.

### 3. Hash Collision / Key Bombing:
Объекты с тысячами ключей перегружают хэш-таблицы Go, вызывая деградацию производительности до \(O(N^2)\).

## Решение по шагам

1. Создайте обертку `SecureJSONDecoder` на базе потокового парсинга `json.Decoder.Token()`.
2. Реализуйте счетчик текущей глубины стека с жестким лимитом (например, не более 10 уровней вложенности).
3. Активируйте метод `UseNumber()` для исключения искажения 64-битных чисел.
4. Добавьте счетчик суммарного количества ключей в объекте.
5. Протестируйте отказ при превышении глубины и корректный парсинг гигантского 64-битного числа без потери точности.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"strings"
)

type SecureDecoderConfig struct {
	MaxDepth   int
	MaxKeys    int
	UseNumbers bool
}

// ValidateJSONStream сканирует JSON поток и валидирует безопасность структуры
func ValidateJSONStream(r io.Reader, cfg SecureDecoderConfig) error {
	dec := json.NewDecoder(r)
	if cfg.UseNumbers {
		dec.UseNumber()
	}

	currentDepth := 0
	totalKeys := 0

	for {
		t, err := dec.Token()
		if err == io.EOF {
			break
		}
		if err != nil {
			return fmt.Errorf("синтаксическая ошибка JSON: %w", err)
		}

		switch delim := t.(type) {
		case json.Delim:
			switch delim {
			case '{', '[':
				currentDepth++
				if currentDepth > cfg.MaxDepth {
					return fmt.Errorf("превышена максимальная глубина вложенности (%d > %d)", currentDepth, cfg.MaxDepth)
				}
			case '}', ']':
				currentDepth--
			}
		case string:
			// Внутри объекта чтение строки может быть ключом
			totalKeys++
			if totalKeys > cfg.MaxKeys {
				return fmt.Errorf("превышено допустимое количество ключей в объекте (> %d)", cfg.MaxKeys)
			}
		}
	}

	return nil
}

func main() {
	cfg := SecureDecoderConfig{
		MaxDepth:   4,
		MaxKeys:    100,
		UseNumbers: true,
	}

	// 1. Атака глубокой вложенностью (Billion Brackets)
	deepJSON := `{"a":{"b":{"c":{"d":{"e":{"f":"boom"}}}}}}`
	fmt.Println("=== 1. Проверка глубокой вложенности JSON ===")
	errDeep := ValidateJSONStream(strings.NewReader(deepJSON), cfg)
	fmt.Printf("Результат валидации: %v\n\n", errDeep)

	// 2. Демонстрация проблемы точности float64 без UseNumber
	// Число 9007199254740993 (на 2 больше максимального безопасного целого float64)
	idJSON := `{"transaction_id": 9007199254740993}`

	// Без UseNumber:
	var naiveMap map[string]interface{}
	_ = json.Unmarshal([]byte(idJSON), &naiveMap)
	fmt.Println("=== 2. Сравнение точности парсинга чисел ===")
	fmt.Printf("Исходное число в JSON: 9007199254740993\n")
	fmt.Printf("Без UseNumber (float64): %.0f (ИСКАЖЕНО!)\n", naiveMap["transaction_id"].(float64))

	// C UseNumber:
	dec := json.NewDecoder(strings.NewReader(idJSON))
	dec.UseNumber()
	var secureMap map[string]interface{}
	_ = dec.Decode(&secureMap)
	numVal := secureMap["transaction_id"].(json.Number)
	intVal, _ := numVal.Int64()
	fmt.Printf("C UseNumber (json.Number): %d (ТОЧНОЕ СОВПАДЕНИЕ!)\n", intVal)
}
```

## Под капотом

В стандарте IEEE 754 числа одинарной и двойной точности кодируют мантиссу (53 бита значащих цифр). Любое целое число, превышающее \(2^{53}-1 = 9\,007\,199\,254\,740\,991\), при конвертации в `float64` округляется к ближайшему четному числу. В финансовых транзакциях или системах с 64-битными идентификаторами баз данных (UUID v7, Snowflake) такое неявное округление приводит к переводу денег на чужие счета или подмене сущностей. `json.Number` сохраняет число в виде сырой строки `string`, позволяя безопасно конвертировать его в `int64` или `big.Int`.

## Подводные камни

1. **Слепое использование `json.Unmarshal`:** Функция `json.Unmarshal` всегда использует внутренний декодер без `UseNumber`, приводя к автоматическому округлению всех больших чисел.
2. **Игнорирование неизвестных полей (Unknown Fields):** Рекомендуется вызывать `decoder.DisallowUnknownFields()`, что защищает от атак подделки полей и опечаток в критических параметрах.
3. **Парсинг без ограничения размера:** Валидатор токенов обязан применяться **после** `http.MaxBytesReader`, иначе поток токенов может быть бесконечным.

## На собеседовании

**Вопрос с собеседования:** Почему вызов `decoder.DisallowUnknownFields()` считается критически важной практикой безопасности API при разборе JSON-запросов?
**Ответ:** 1) **Защита от опечаток и обхода бизнес-правил:** Если клиент отправил `{"user_id": 10, "is_admim": true}` (опечатка в слове `admin`), разработчик может не заметить ошибку конфигурации.
2) **Защита от Mass Assignment атак:** Атакующий может попытаться передать служебные поля, которые разработчик не рассчитывал получать от пользователя (например, `"role": "admin"` или `"verified": true`). `DisallowUnknownFields()` немедленно отклонит запрос с ошибкой `json: unknown field "role"`, предотвращая повышение привилегий.
