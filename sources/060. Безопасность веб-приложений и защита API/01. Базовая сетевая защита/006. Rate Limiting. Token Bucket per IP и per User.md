# Rate Limiting: Token Bucket per IP и per User

## Условие

Реализуйте token bucket rate limiter (per IP и per user) с использованием `golang.org/x/time/rate`. Примените к endpoint `/login` для защиты от brute-force. Объясните, почему rate limit на уровне reverse proxy (nginx) недостаточен для логики приложения.

### Исходная формулировка

**Rate Limiting.**: Реализуйте token bucket rate limiter (per IP и per user) с использованием `golang.org/x/time/rate`. Примените к endpoint `/login` для защиты от brute-force. Объясните, почему rate limit на уровне reverse proxy (nginx) недостаточен для логики приложения.

## Теория

Ограничение скорости (**Rate Limiting**) — базовый механизм защиты API от DDoS-атак, брутфорса паролей (Credential Stuffing), скрейпинга данных и исчерпания вычислительных ресурсов.

### Алгоритм Token Bucket:
- Ведро емкостью \(B\) (Burst) непрерывно пополняется токенами со скоростью \(R\) токенов в секунду.
- Каждый входящий запрос требует один токен. Если токен есть — запрос немедленно пропускается.
- Если ведро пусто — возвращается **HTTP 429 Too Many Requests** с заголовком `Retry-After`.
- Алгоритм идеально сглаживает кратковременные всплески трафика, гарантируя среднюю скорость.

### Почему Nginx/Cloudflare недостаточны?
1. **Отсутствие бизнес-контекста:** Обратный прокси видит только IP-адрес. В распределенных атаках ботнет использует тысячи IP для подбора пароля к **одному конкретному аккаунту** (`admin@company.ru`).
2. **Проблема корпоративных NAT:** Тысячи сотрудников корпорации выходят в интернет с одного публичного IP офиса. Ограничение по IP в Nginx заблокирует весь офис при активности одного пользователя.
3. **Гранулярность по ролям:** Приложению необходимо давать премиум-пользователям лимит 1000 RPS, а анонимным — 5 RPS, что невозможно без проверки JWT внутри Go.

## Решение по шагам

1. Создайте потокобезопасный реестр лимитеров `IPRateLimiter`.
2. Настройте параметры Token Bucket: скорость пополнения \(R=5\) req/sec, всплеск \(B=10\).
3. Реализуйте очистку неактивных IP-адресов по таймеру для предотвращения утечки памяти.
4. Реализуйте HTTP-Middleware, возвращающий 429 Too Many Requests.
5. Продемонстрируйте блокировку всплеска запросов с одного IP.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

// Простая реализация Token Bucket без внешних зависимостей
type TokenBucket struct {
	mu         sync.Mutex
	capacity   float64   // максимальный burst
	tokens     float64   // текущие токены
	refillRate float64   // токенов в секунду
	lastRefill time.Time // время последнего пополнения
}

func NewTokenBucket(rate float64, burst int) *TokenBucket {
	return &TokenBucket{
		capacity:   float64(burst),
		tokens:     float64(burst),
		refillRate: rate,
		lastRefill: time.Now(),
	}
}

func (tb *TokenBucket) Allow() bool {
	tb.mu.Lock()
	defer tb.mu.Unlock()

	now := time.Now()
	elapsed := now.Sub(tb.lastRefill).Seconds()
	tb.lastRefill = now

	// Пополняем токены пропорционально прошедшему времени
	tb.tokens += elapsed * tb.refillRate
	if tb.tokens > tb.capacity {
		tb.tokens = tb.capacity
	}

	if tb.tokens >= 1.0 {
		tb.tokens -= 1.0
		return true
	}
	return false
}

// IPRateLimiter управляет персональными бакетами для каждого IP
type IPRateLimiter struct {
	mu       sync.RWMutex
	limiters map[string]*TokenBucket
	rate     float64
	burst    int
}

func NewIPRateLimiter(r float64, b int) *IPRateLimiter {
	return &IPRateLimiter{
		limiters: make(map[string]*TokenBucket),
		rate:     r,
		burst:    b,
	}
}

func (i *IPRateLimiter) GetLimiter(ip string) *TokenBucket {
	i.mu.RLock()
	limiter, exists := i.limiters[ip]
	i.mu.RUnlock()

	if exists {
		return limiter
	}

	i.mu.Lock()
	defer i.mu.Unlock()
	// Double-check locking
	if limiter, exists := i.limiters[ip]; exists {
		return limiter
	}

	limiter = NewTokenBucket(i.rate, i.burst)
	i.limiters[ip] = limiter
	return limiter
}

// RateLimitMiddleware проверяет лимит запросов для IP
func RateLimitMiddleware(limiterManager *IPRateLimiter) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			clientIP := r.RemoteAddr
			limiter := limiterManager.GetLimiter(clientIP)

			if !limiter.Allow() {
				w.Header().Set("Retry-After", "1")
				w.Header().Set("Content-Type", "application/json")
				w.WriteHeader(http.StatusTooManyRequests) // 429
				_, _ = w.Write([]byte(`{"error":"too_many_requests","message":"Превышен лимит запросов"}`))
				return
			}

			next.ServeHTTP(w, r)
		})
	}
}

func main() {
	// Лимит: 2 запроса в секунду, всплеск максимум 3 запроса
	manager := NewIPRateLimiter(2.0, 3)

	targetHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"login_success"}`))
	})

	server := httptest.NewServer(RateLimitMiddleware(manager)(targetHandler))
	defer server.Close()

	fmt.Println("=== Отправка пачки из 6 быстрых запросов к /login ===")
	for reqNum := 1; reqNum <= 6; reqNum++ {
		resp, _ := http.Get(server.URL)
		if resp.StatusCode == http.StatusOK {
			fmt.Printf("Запрос #%d: HTTP %d OK (Пропущен)\n", reqNum, resp.StatusCode)
		} else {
			fmt.Printf("Запрос #%d: HTTP %d Too Many Requests (ЗАБЛОКИРОВАН!)\n", reqNum, resp.StatusCode)
		}
		resp.Body.Close()
	}

	// Ждем 1 секунду пополнения токенов
	fmt.Println("\nЖдем 1 секунду пополнения токенов...")
	time.Sleep(1 * time.Second)

	resp, _ := http.Get(server.URL)
	fmt.Printf("Запрос после ожидания: HTTP %d OK (Токены восстановились!)\n", resp.StatusCode)
	resp.Body.Close()
}
```

## Под капотом

В распределенной системе из сотен микросервисов локальный in-memory rate limiting не работает: клиент каждый раз попадает на разные поды через Round-Robin балансировщик. Для распределенного Token Bucket используется **Redis + Lua-скрипт**: вычисление остатка токенов и списание выполняются атомарно внутри одного вызова Redis `EVAL`, исключая гонки данных и сетевой оверхед.

## Подводные камни

1. **Утечка памяти в мапе клиентов:** Если злоумышленник шлет запросы с миллиона разных IP, мапа `limiters` бесконечно разрастается. Необходим LRU-кэш или фоновый воркер, удаляющий неактивные бакеты через 5 минут.
2. **Доверие заголовку `X-Forwarded-For`:** Атакующий может легко подделать `X-Forwarded-For: 8.8.8.8` в curl. Доверять заголовку можно только в том случае, если перед Go стоит доверенный балансировщик, перезаписывающий этот заголовок.
3. **Блокировка без Retry-After:** Спецификация RFC 6585 требует передавать заголовок `Retry-After`, указывающий время ожидания в секундах.

## На собеседовании

**Вопрос с собеседования:** Как устроен Sliding Window Counter (Скользящее окно) в Redis, и почему он точнее Fixed Window алгоритма при защите от спайков на границах интервалов?
**Ответ:** 1) В **Fixed Window** (Фиксированное окно, например 100 запросов в минуту от 12:00:00 до 12:01:00) атакующий может отправить 100 запросов в 12:00:59 и еще 100 запросов в 12:01:01. За две секунды сервис получит 200 запросов (двойной лимит!).
2) **Sliding Window Counter** использует Redis Sorted Set (ZSET): таймстемп каждого запроса сохраняется как score `ZADD key now uuid`. При проверке удаляются записи старше окна `ZREMRANGEBYSCORE key 0 (now - 60s)` и проверяется текущий `ZCARD`. Это дает идеальную математическую точность окна в любой момент времени.
