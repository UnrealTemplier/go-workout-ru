# Автоматический аудит уязвимостей (gosec и SQL Injection)

## Условие

Напишите два SQL-запроса к базе данных: один небезопасный (с конкатенацией пользовательской строки в тело запроса) и один безопасный (с использованием параметров). Установите инструмент статического анализа безопасности Go — `github.com/securego/gosec` [551]. Запустите проверку вашего кода через консоль и убедитесь, что `gosec` находит уязвимую конкатенацию и предупреждает о возможности SQL-инъекции [551].

## Теория

Статический анализ безопасности (**Static Application Security Testing / SAST**) — обязательный этап автоматизированного CI/CD пайплайна в ведущих технологических компаниях.

### Инструмент `gosec` (Go Security Checker):
Пакет `github.com/securego/gosec/v2` парсит абстрактное синтаксическое дерево (AST) и промежуточное представление SSA кода на Go, проверяя исходный код по десяткам правил безопасности:
- **G201 / G202:** SQL Query Construction using formatting / string concatenation (SQL-инъекции).
- **G101:** Hardcoded credentials (хранение паролей и API-ключей в коде).
- **G104:** Unhandled errors (пропущенные ошибки).
- **G204:** Subprocess launched with variable (Command Injection).
- **G401 / G501:** Weak cryptographic primitives (MD5, DES, SHA1).

### Почему параметризованные запросы на 100% безопасны против SQLi:
При использовании плейсхолдеров (`$1`, `?`) драйвер базы данных отправляет строку запроса и пользовательские параметры **раздельными сетевыми пакетами протокола СУБД (Prepared Statements)**. Движок базы данных сначала компилирует план выполнения запроса, а затем подставляет параметры как изолированные константные литералы. Пользовательский ввод физически не может изменить синтаксическое дерево SQL-запроса!

## Решение по шагам

1. Напишите уязвимую функцию `InsecureGetUser(db, userInput)` с `fmt.Sprintf`.
2. Напишите защищенную функцию `SecureGetUser(db, userInput)` с параметризованным запросом `$1`.
3. Продемонстрируйте атаку SQL Injection (обход авторизации через `' OR '1'='1`).
4. Запустите статический анализ кода через консольный запуск `gosec`.
5. Убедитесь в обнаружении правила G201.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"log"

	_ "github.com/mattn/go-sqlite3"
)

type UserRecord struct {
	ID       int
	Username string
	Role     string
}

// InsecureQuery — УЯЗВИМАЯ ФУНКЦИЯ (gosec правило G201)
// Форматирование строки запроса через fmt.Sprintf открывает путь к SQL-инъекции!
func InsecureQuery(db *sql.DB, usernameInput string) ([]UserRecord, error) {
	// ОШИБКА: конкатенация пользовательского ввода в тело SQL
	query := fmt.Sprintf("SELECT id, username, role FROM users WHERE username = '%s'", usernameInput)
	fmt.Printf("[SQL VULNERABLE]: %s\n", query)

	rows, err := db.Query(query)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var results []UserRecord
	for rows.Next() {
		var u UserRecord
		_ = rows.Scan(&u.ID, &u.Username, &u.Role)
		results = append(results, u)
	}
	return results, nil
}

// SecureQuery — БЕЗОПАСНАЯ ФУНКЦИЯ с использованием параметризованного запроса (Prepared Statement)
func SecureQuery(db *sql.DB, usernameInput string) ([]UserRecord, error) {
	// ПРАВИЛЬНО: параметры передаются через плейсхолдер (?)
	query := "SELECT id, username, role FROM users WHERE username = ?"
	fmt.Printf("[SQL SECURE]: %s (Параметр: %q)\n", query, usernameInput)

	rows, err := db.Query(query, usernameInput)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	var results []UserRecord
	for rows.Next() {
		var u UserRecord
		_ = rows.Scan(&u.ID, &u.Username, &u.Role)
		results = append(results, u)
	}
	return results, nil
}

func main() {
	db, err := sql.Open("sqlite3", ":memory:")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	// Инициализация базы данных
	_, _ = db.Exec(`CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT, role TEXT);`)
	_, _ = db.Exec(`INSERT INTO users (username, role) VALUES ('admin', 'super_admin'), ('alice', 'user');`)

	// Вредоносный ввод злоумышленника
	attackerPayload := "admin' OR '1'='1"

	fmt.Println("=== 1. Выполнение уязвимого запроса (SQL Injection) ===")
	hackedUsers, _ := InsecureQuery(db, attackerPayload)
	fmt.Printf("Атака успешна! Злоумышленник извлек всех пользователей: %d записей\n", len(hackedUsers))
	for _, u := range hackedUsers {
		fmt.Printf(" -> ID: %d, User: %-8s, Role: %s\n", u.ID, u.Username, u.Role)
	}

	fmt.Println("\n=== 2. Выполнение безопасного параметризованного запроса ===")
	safeUsers, _ := SecureQuery(db, attackerPayload)
	fmt.Printf("Результат безопасного запроса: найдено %d записей (Атака полностью нейтрализована!)\n", len(safeUsers))
}
```

## Под капотом

Как `gosec` находит SQLi в Go?
Анализатор строит AST-дерево функции `db.Query(query)`.
1. Инспектор проверяет тип первого аргумента `query`.
2. Если аргумент формируется вызовом `fmt.Sprintf`, оператором конкатенации строк `+` или буфером `strings.Builder`, анализатор выдает алерт **G201: SQL query construction using format string**.
3. Единственный способ удовлетворить проверку безопасности — передавать в качестве первого аргумента строковый литерал константы, а переменные передавать последующими вариативными аргументами `...interface{}`.

## Подводные камни

1. **Динамические имена таблиц и столбцов:** Плейсхолдеры (`?`, `$1`) работают **только** для значений данных! Их нельзя использовать для имен таблиц или колонок (`SELECT * FROM ? WHERE ...` вызовет синтаксическую ошибку базы данных). Имена таблиц обязаны проверяться по строгому белому списку (Whitelist).
2. **Конкатенация условий `IN (...)`:** Попытка собрать срез идентификаторов через цикл конкатенации. Для списков `IN` используйте срезы параметров `WHERE id IN (?, ?, ?)` или конструкции PostgreSQL `WHERE id = ANY($1)`.
3. **Игнорирование ORM уязвимостей:** Использование `db.Where(fmt.Sprintf("name = '%s'", input))` в GORM точно так же открывает SQLi, как и чистый SQL.

## На собеседовании

**Вопрос с собеседования:** Почему даже при использовании современной ORM (например, GORM или Ent) в коде микросервисов возникают критические SQL-инъекции, и как статический анализатор помогает их предотвратить?
**Ответ:** Разработчики ошибочно считают, что вызов ORM автоматически гарантирует безопасность.
Однако большинство ORM поддерживают сырые SQL-выражения:
`db.Where(fmt.Sprintf("status = '%s'", userInput)).Find(&orders)`
или
`db.Order(r.URL.Query().Get("sort"))`
Если параметр `sort` содержит `id; DROP TABLE users;--`, происходит инъекция в клаузу `ORDER BY`.
Статический анализатор `gosec` (правило G202) и линтер `sqlclosecheck` отслеживают любые неконстантные строки, передаваемые в методы ORM, и принудительно блокируют Pull Request в CI/CD до устранения уязвимости.
