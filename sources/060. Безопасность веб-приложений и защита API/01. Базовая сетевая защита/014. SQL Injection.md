# SQL Injection: Параметризация запросов в database/sql

## Условие

Покажите, что Go `database/sql` с placeholders защищён от SQLi по дизайну. Но конкатенация строк всё ещё опасна.

### Исходная формулировка

**SQL Injection через Go**: Покажите, что Go `database/sql` с placeholders защищён от SQLi по дизайну. Но конкатенация строк всё ещё опасна.

## Теория

В стандартной библиотеке Go пакет `database/sql` спроектирован с учетом архитектурной безопасности:

### Почему плейсхолдеры (`?`, `$1`) неуязвимы:
Когда разработчик использует:
```go
db.Query("SELECT * FROM users WHERE email = ? AND status = ?", email, status)
```
Драйвер базы данных НЕ занимается подстановкой строк в Go!
Вместо этого драйвер отправляет в PostgreSQL/MySQL сетевую команду **Prepare**:
1. СУБД парсит синтаксическое дерево запроса (SQL AST) и фиксирует структуру логики.
2. Параметры `email` и `status` передаются отдельным двоичным пакетом протокола (Bind).
3. Даже если параметр содержит `' OR '1'='1' --; DROP DATABASE`, для СУБД это просто строка текста, которая сравнивается со значением в таблице. Изменить логику запроса невозможно!

### Когда возникает уязвимость:
Уязвимость возникает, если разработчик использует конкатенацию или интерполяцию ДО передачи строки в `database/sql`:
`query := fmt.Sprintf("SELECT * FROM users WHERE email = '%s'", input)`.

## Решение по шагам

1. Создайте базу данных SQLite в памяти.
2. Продемонстрируйте попытку внедрения вредоносной SQL-инъекции через плейсхолдер `?`.
3. Убедитесь, что база данных ищет буквальное строковое значение, а не выполняет код инъекции.
4. Продемонстрируйте уязвимость при форматировании через `fmt.Sprintf`.
5. Сравните результаты двух подходов.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"log"

	_ "github.com/mattn/go-sqlite3"
)

func main() {
	db, err := sql.Open("sqlite3", ":memory:")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	// Создаем тестовую таблицу пользователей
	_, _ = db.Exec(`
		CREATE TABLE accounts (
			id INTEGER PRIMARY KEY AUTOINCREMENT,
			username TEXT NOT NULL,
			password_hash TEXT NOT NULL,
			is_superadmin BOOLEAN NOT NULL
		);
		INSERT INTO accounts (username, password_hash, is_superadmin) VALUES 
		('admin', 'hash_secret_admin', 1),
		('editor', 'hash_secret_editor', 0);
	`)

	// Вредоносный ввод атакующего
	maliciousInput := "admin' OR '1'='1"

	// 1. Безопасный вызов через плейсхолдер database/sql
	fmt.Println("=== 1. Параметризованный запрос (Prepared Statement) ===")
	safeQuery := "SELECT username, is_superadmin FROM accounts WHERE username = ?"
	rowsSafe, err := db.Query(safeQuery, maliciousInput)
	if err != nil {
		log.Fatal(err)
	}
	defer rowsSafe.Close()

	countSafe := 0
	for rowsSafe.Next() {
		countSafe++
	}
	fmt.Printf("Запрос: %s\nПараметр: %q\nНайдено записей: %d (База искала пользователя с именем \"admin' OR '1'='1\")\n\n",
		safeQuery, maliciousInput, countSafe)

	// 2. Уязвимый вызов через форматирование строки
	fmt.Println("=== 2. Уязвимый запрос (Конкатенация строк) ===")
	insecureQuery := fmt.Sprintf("SELECT username, is_superadmin FROM accounts WHERE username = '%s'", maliciousInput)
	rowsInsecure, err := db.Query(insecureQuery)
	if err != nil {
		log.Fatal(err)
	}
	defer rowsInsecure.Close()

	fmt.Printf("Сформированный SQL: %s\n", insecureQuery)
	for rowsInsecure.Next() {
		var user string
		var isAdmin bool
		_ = rowsInsecure.Scan(&user, &isAdmin)
		fmt.Printf(" -> Утечка данных: User=%-8s SuperAdmin=%v\n", user, isAdmin)
	}
}
```

ℹ️ Демонстрация иммунитета параметризованных запросов database/sql против конкатенации строк

**`Терминал`**

```bash
go run main.go
# === 1. Параметризованный запрос (Prepared Statement) ===
# Запрос: SELECT username, is_superadmin FROM accounts WHERE username = ?
# Параметр: "admin' OR '1'='1"
# Найдено записей: 0 (База искала пользователя с именем "admin' OR '1'='1")
# 
# === 2. Уязвимый запрос (Конкатенация строк) ===
# Сформированный SQL: SELECT username, is_superadmin FROM accounts WHERE username = 'admin' OR '1'='1'
#  -> Утечка данных: User=admin    SuperAdmin=true
#  -> Утечка данных: User=editor   SuperAdmin=false
```

## Под капотом

На уровне бинарного сетевого протокола PostgreSQL (Frontend/Backend Protocol):
- При использовании конкатенации отправляется сообщение `Simple Query ('Q')`, содержащее сырой текст.
- При использовании плейсхолдеров отправляется последовательность:
  `Parse ('P')` -> СУБД компилирует дерево выражений.
  `Bind ('B')` -> передаются сырые байты параметров с указанием их точных типов данных (например, `INT4_OID`, `VARCHAR_OID`).
  `Execute ('E')` -> выполнение плана.
Параметры никогда не смешиваются с грамматикой SQL!

## Подводные камни

1. **Неправильный синтаксис плейсхолдеров:** В PostgreSQL используются `$1, $2`, в MySQL и SQLite — `?`, в Oracle — `:1`. Попытка использовать `?` в драйвере `lib/pq` или `pgx` приведет к синтаксической ошибке.
2. **Динамические операторы `LIKE`:** Опасность конкатенации: `WHERE name LIKE '%` + input + `%'`. Правильно: передавать знак процента как часть самого параметра: `db.Query("WHERE name LIKE ?", "%"+input+"%")`.
3. **Использование `db.Exec` для нескольких команд:** Разрешение multi-statements в DSN (например, `multiStatements=true` в MySQL) многократно увеличивает разрушительность инъекции.

## На собеседовании

**Вопрос с собеседования:** Если проект использует генератор типобезопасного SQL-кода `sqlc`, может ли в кодовой базе появиться SQL-инъекция?
**Ответ:** При стандартном использовании `sqlc` появление SQLi **математически невозможно**:
1) `sqlc` компилирует `.sql` файлы во время сборки с помощью реального парсера AST PostgreSQL/MySQL.
2) Все динамические аргументы принудительно превращаются в строго типизированные плейсхолдеры `$1, $2` в сигнатурах сгенерированных методов Go.
3) Единственное исключение: если разработчик намеренно обойдет сгенерированный код и вручную выполнит `db.Exec(fmt.Sprintf(...))`.
