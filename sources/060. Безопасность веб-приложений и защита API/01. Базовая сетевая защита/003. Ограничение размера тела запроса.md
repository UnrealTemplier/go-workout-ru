# Ограничение размера тела запроса (http.MaxBytesReader)

## Условие

Реализуйте middleware с `http.MaxBytesReader` (например, 1 MB). Покажите, что JSON на 100 MB вызывает `http: request body too large`. Объясните, почему `json.NewDecoder(r).Decode(&v)` без лимита — уязвимость.

### Исходная формулировка

**Ограничение размера тела.**: Реализуйте middleware с `http.MaxBytesReader` (например, 1 MB). Покажите, что JSON на 100 MB вызывает `http: request body too large`. Объясните, почему `json.NewDecoder(r).Decode(&v)` без лимита — уязвимость.

## Теория

Многие разработчики ошибочно полагают, что использование потокового декодера `json.NewDecoder(r.Body).Decode(&v)` защищает от переполнения памяти, так как «он парсит поток, а не читает все в память сразу».

### Почему `json.NewDecoder` без лимита — критическая уязвимость?
1. **Внутренний буфер декодера:** Для поддержания лексического анализатора `json.Decoder` использует внутренний буфер `buf []byte`.
2. **Атака строковыми литералами:** Если злоумышленник отправит JSON вида:
   `{"description": "AAAAAA... [100 МБ без пробелов] ..."}`, декодер вынужден расширять внутренний буфер до тех пор, пока не встретит закрывающую кавычку `"`. Буфер разрастается до сотен мегабайт на один запрос!
3. **Атака глубокими массивами:** Передача массива из миллионов чисел `[1, 2, 3, ...]` заставляет структуру среза в Go непрерывно выполнять `append`, фрагментируя кучу.
4. При 100 конкурентных соединениях от одного атакующего потребление памяти достигает десятков гигабайт, приводя к моментальному краху операционной системы.

## Решение по шагам

1. Создайте HTTP-сервер с глобальным middleware ограничения размера.
2. Продемонстрируйте попытку отправки 100 МБ потока через `io.Reader`.
3. Убедитесь, что `json.NewDecoder` немедленно завершает работу с ошибкой `http: request body too large`.
4. Настройте корректный заголовок ответа `Connection: close` для закрытия сокета.
5. Продемонстрируйте сохранение стабильности памяти сервера.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
)

// EndlessZeroReader симулирует атакующего, шлющего 100 МБ поток
type EndlessZeroReader struct {
	Remaining int64
}

func (r *EndlessZeroReader) Read(p []byte) (n int, err error) {
	if r.Remaining <= 0 {
		return 0, io.EOF
	}
	toRead := int64(len(p))
	if toRead > r.Remaining {
		toRead = r.Remaining
	}
	for i := int64(0); i < toRead; i++ {
		p[i] = 'A'
	}
	r.Remaining -= toRead
	return int(toRead), nil
}

func main() {
	const limit = 1024 * 1024 // 1 MB

	// Защищенный HTTP-хэндлер
	mux := http.NewServeMux()
	mux.HandleFunc("/api/upload", func(w http.ResponseWriter, r *http.Request) {
		// Принудительное ограничение размера
		r.Body = http.MaxBytesReader(w, r.Body, limit)

		var payload map[string]interface{}
		err := json.NewDecoder(r.Body).Decode(&payload)
		if err != nil {
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(http.StatusRequestEntityTooLarge)
			_, _ = fmt.Fprintf(w, `{"status":"error","message":%q}`, err.Error())
			return
		}

		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"success"}`))
	})

	ts := httptest.NewServer(mux)
	defer ts.Close()

	// Имитируем отправку 100 МБ данных
	attackSize := int64(100 * 1024 * 1024) // 100 MB
	fmt.Printf("=== Отправка атаки: поток размером %d МБ ===\n", attackSize/(1024*1024))

	attackStream := io.MultiReader(
		strings.NewReader(`{"large_field":"`),
		&EndlessZeroReader{Remaining: attackSize},
		strings.NewReader(`"}`),
	)

	resp, err := http.Post(ts.URL+"/api/upload", "application/json", attackStream)
	if err != nil {
		fmt.Printf("Соединение прервано сервером: %v\n", err)
		return
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("HTTP Status: %d\n", resp.StatusCode)
	fmt.Printf("Ответ сервера: %s\n", string(body))
}
```

ℹ️ Блокировка 100 МБ вредоносного потока декодером с использованием http.MaxBytesReader

## Под капотом

Что происходит на уровне TCP сокета, когда срабатывает `MaxBytesReader`?
Если клиент продолжает слать мегабайты данных после того, как сервер уже понял, что лимит превышен, сервер не может просто «проигнорировать» их: незачитанные байты будут засорять буфер сокета ядра ОС. Поэтому метод `requestTooLarge()` в `net/http` выставляет флаг `w.closeNotify`, отправляет HTTP-ответ с кодом 413 и жестко закрывает TCP-соединение пакетом `RST` или `FIN`, освобождая сетевые ресурсы.

## Подводные камни

1. **Попытка повторного чтения Body:** После того как `MaxBytesReader` сработал, поток `r.Body` закрыт навсегда. Любая попытка прочитать его снова вернет ошибку.
2. **Неверный порядок middleware:** Если middleware логирования читает `r.Body` без ограничения, `MaxBytesReader`, установленный ниже по цепочке, не защитит сервис.
3. **Забытый Content-Length:** Злоумышленник может убрать заголовок `Content-Length` и передавать данные по `Transfer-Encoding: chunked`. `MaxBytesReader` одинаково надежно защищает как от явных, так и от chunked потоков.

## На собеседовании

**Вопрос с собеседования:** В чем разница между защитой через `http.MaxBytesReader` и `r.Body = io.LimitReader(r.Body, limit)`?
**Ответ:** 1) `io.LimitReader` — это универсальный интерфейс стандартной библиотеки, который при превышении лимита возвращает обычный `io.EOF`. Прикладной код не может понять, закончился ли файл нормально или его оборвали из-за превышения размера! Это приводит к ошибкам «неожиданный конец JSON» (400 Bad Request).
2) `http.MaxBytesReader` спроектирован специально для HTTP: он возвращает типизированную ошибку `*http.MaxBytesError`, сообщает объекту `http.ResponseWriter` о необходимости прервать TCP-сессию и позволяет вернуть канонический статус 413 Payload Too Large.
