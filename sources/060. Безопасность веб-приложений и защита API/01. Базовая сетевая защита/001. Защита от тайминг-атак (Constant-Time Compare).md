# Защита от тайминг-атак (Constant-Time Compare)

## Условие

Реализуйте собственную (уязвимую) функцию сравнения строк через `==` и безопасную через `crypto/subtle.ConstantTimeCompare`. Покажите разницу в поведении через измерение времени (искусственно, с пояснением опасности).

### Исходная формулировка

**Защита от тайминг-атак.**: Реализуйте собственную (уязвимую) функцию сравнения строк через `==` и безопасную через `crypto/subtle.ConstantTimeCompare`. Покажите разницу в поведении через измерение времени (искусственно, с пояснением опасности).

## Теория

Атака по сторонним каналам на основе времени (**Timing Attack / Side-Channel Attack**) основана на физической утечке информации о времени работы центрального процессора:

### Механика уязвимости оператора `==`:
В стандартном Go (и большинстве языков программирования) оператор сравнения срезов или строк `a == b` оптимизирован для максимальной производительности:
```go
// Псевдокод стандартного оператора ==
if len(a) != len(b) { return false }
for i := 0; i < len(a); i++ {
    if a[i] != b[i] {
        return false // РАННИЙ ВЫХОД (Early Exit)!
    }
}
return true
```
Если первый байт пароля или API-ключа не совпадает, функция завершается за \(T_0 \approx 5\) наносекунд. Если совпали первые 10 байт, функция сделает 10 итераций цикла и завершится за \(T_{10} \approx 50\) наносекунд.

### Как злоумышленник восстанавливает секрет:
Удаленный атакующий отправляет миллионы HTTP-запросов и статистически усредняет время ответа сервера (устраняя сетевой джиттер):
1. Перебирает первый байт от `0x00` до `0xFF`. Байт с максимальным средним временем отклика — это первый символ секрета!
2. Фиксирует первый байт и начинает подбирать второй.
3. Время взлома падает с экспоненциального \(256^{32}\) (триллионы лет) до линейного \(256 \times 32 = 8192\) запроса (несколько минут)!

### Решение: `crypto/subtle.ConstantTimeCompare`
Функция выполняет побитовое сложение XOR над **всеми** байтами без единого условного перехода (`if`), затрачивая строго константное количество тактов CPU независимо от того, в какой позиции находится несовпадение.

## Решение по шагам

1. Напишите уязвимую функцию `InsecureCompare(a, b string) bool` с ранним выходом.
2. Напишите защищенную функцию `SecureCompare(a, b string) bool` на базе `crypto/subtle.ConstantTimeCompare`.
3. Смоделируйте уязвимость с искусственной задержкой на символ, наглядно демонстрирующей утечку времени.
4. Продемонстрируйте, как злоумышленник по времени ответа может посимвольно подобрать секретный токен.
5. Продемонстрируйте постоянство времени в `crypto/subtle`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/subtle"
	"fmt"
	"time"
)

// InsecureCompare — уязвимое сравнение с ранним выходом (Early Exit)
func InsecureCompare(secret, guess string) bool {
	if len(secret) != len(guess) {
		return false
	}
	// Имитируем микрозадержку на каждый совпавший символ для наглядности
	for i := 0; i < len(secret); i++ {
		if secret[i] != guess[i] {
			return false // Утечка времени!
		}
		time.Sleep(100 * time.Microsecond)
	}
	return true
}

// SecureCompare — безопасное сравнение за константное время
func SecureCompare(secret, guess string) bool {
	return subtle.ConstantTimeCompare([]byte(secret), []byte(guess)) == 1
}

func main() {
	realToken := "CORP-SEC-KEY-9988"

	fmt.Println("=== 1. Анализ уязвимого сравнения (InsecureCompare) ===")
	guesses := []struct {
		desc  string
		value string
	}{
		{"Полностью неверный", "XXXX-XXXX-XXXX-XXXX"},
		{"Совпали 4 символа", "CORP-XXXX-XXXX-XXXX"},
		{"Совпали 8 символов", "CORP-SEC-XXXX-XXXX"},
		{"Совпали 12 символов", "CORP-SEC-KEY-XXXX"},
		{"Идеальное совпадение", "CORP-SEC-KEY-9988"},
	}

	for _, g := range guesses {
		start := time.Now()
		matched := InsecureCompare(realToken, g.value)
		dur := time.Since(start)
		fmt.Printf("%-22s -> Result: %-5v | Время проверки: %v\n", g.desc, matched, dur.Round(time.Microsecond))
	}

	fmt.Println("\n=== 2. Анализ безопасного сравнения (crypto/subtle) ===")
	for _, g := range guesses {
		start := time.Now()
		matched := SecureCompare(realToken, g.value)
		dur := time.Since(start)
		fmt.Printf("%-22s -> Result: %-5v | Время: %v\n", g.desc, matched, dur)
	}

	fmt.Println("\nВывод: subtle.ConstantTimeCompare исключает side-channel утечки времени.")
}
```

## Под капотом

Как устроен `subtle.ConstantTimeCompare(x, y []byte) int` в ассемблере Go?
В функции не используется ни одной ветвящейся инструкции `JMP`/`JZ`/`JNZ`, которые зависят от данных:
```go
var v byte
for i := 0; i < len(x); i++ {
    v |= x[i] ^ y[i]
}
return constantTimeByteEq(v, 0)
```
Операция побитового `XOR` и `OR` выполняется для абсолютно каждого элемента массива. Переменная `v` будет равна нулю тогда и только тогда, когда все байты совпали. Процессор выполняет строго одинаковое число микроинструкций и тактов кэша L1 независимо от содержимого.

## Подводные камни

1. **Утечка по длине:** `ConstantTimeCompare` возвращает 0 сразу, если `len(x) != len(y)`. Если длина секрета является тайной, перед сравнением следует приводить строки к HMAC-SHA256 хешу одинаковой длины (32 байта).
2. **Использование `bytes.Equal` для токенов:** Функция `bytes.Equal` оптимизирована под SIMD (AVX-512) и имеет ранний выход при первом несовпадающем блоке памяти, поэтому подвержена тайминг-атакам.
3. **Компиляторные оптимизации:** Никогда не пишите свои константные циклы без ассемблерных директив, так как оптимизатор компилятора (`dead code elimination`) может превратить константный цикл обратно в ранний выход!

## На собеседовании

**Вопрос с собеседования:** Если сетевой пинг до сервера варьируется от 20 до 50 миллисекунд (джиттер сети), действительно ли злоумышленник может измерить наносекундную разницу во времени проверки одного символа пароля?
**Ответ:** Да, на 100%! Это доказано академическими исследованиями и практическими эксплойтами (например, атака Crosby-Wallach):
1) Сетевой шум подчиняется нормальному распределению Гаусса.
2) Согласно **Закону больших чисел**, при усреднении \(N\) измерений (например, 10 000 – 100 000 запросов на символ) дисперсия случайного шума падает пропорционально \(1/\sqrt{N}\).
3) В результате статистический шум сглаживается, и наносекундная разница выполнения инструкции процессора четко выявляется в виде смещения математического ожидания.
