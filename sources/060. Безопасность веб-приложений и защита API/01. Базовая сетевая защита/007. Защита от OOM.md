# Защита от OOM: Billion Laughs и ограничение Large Body

## Условие

Ты принимаешь JSON от пользователя. Если хакер пришлет 10 ГБ файл, `io.ReadAll(r.Body)` вызовет Out Of Memory и сервер упадет. Оберни чтение в `http.MaxBytesReader(w, r.Body, 1024*1024)` (лимит 1 МБ). Убедись, что при превышении лимита запрос прерывается.

### Исходная формулировка

**Защита от OOM (Billion Laughs / Large Body)**: Ты принимаешь JSON от пользователя. Если хакер пришлет 10 ГБ файл, `io.ReadAll(r.Body)` вызовет Out Of Memory и сервер упадет. Оберни чтение в `http.MaxBytesReader(w, r.Body, 1024*1024)` (лимит 1 МБ). Убедись, что при превышении лимита запрос прерывается.

## Теория

Атака на переполнение памяти (**Billion Laughs / Memory Exhaustion Attack**) использует диспропорцию между малым объемом передаваемых байт и огромным объемом аллокаций, требуемых для их распаковки или сохранения.

### Опасность `io.ReadAll(r.Body)`:
Функция `io.ReadAll` начинает с буфера размером 512 байт и динамически удваивает срез при заполнении:
\(512\text{ B} \to 1\text{ KB} \to \dots \to 512\text{ MB} \to 1\text{ GB} \to 2\text{ GB}\).
При каждом удвоении старый массив остается в памяти до завершения работы GC, поэтому для чтения 2 ГБ потребуется выделить более 4 ГБ физической оперативной памяти!

### Защита через двухуровневый барьер:
1. `http.MaxBytesReader(w, r.Body, limit)` — аппаратно прерывает чтение на уровне HTTP-сервера.
2. `io.LimitReader(r, limit)` — для не-HTTP потоков (например, при чтении из `tar`, `zip` или gRPC).
3. При превышении лимита сервер обязан не просто прекратить чтение, но и уведомить вызывающую сторону статусом 413, закрыв поток.

## Решение по шагам

1. Создайте HTTP-обработчик с оборачиванием `r.Body` в `http.MaxBytesReader`.
2. Реализуйте функцию чтения с перехватом `*http.MaxBytesError`.
3. Смоделируйте генератор бесконечного входящего потока данных.
4. Продемонстрируйте, что потребление памяти остается в пределах 1 МБ.
5. Убедитесь в возврате клиенту статуса HTTP 413 Payload Too Large.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
)

func SafeReadBodyHandler(w http.ResponseWriter, r *http.Request) {
	const maxAllowedBytes = 1024 * 1024 // 1 MB

	// Защита от OOM: ограничиваем чтение 1 мегабайтом
	r.Body = http.MaxBytesReader(w, r.Body, maxAllowedBytes)

	data, err := io.ReadAll(r.Body)
	if err != nil {
		var maxErr *http.MaxBytesError
		if errors.As(err, &maxErr) {
			w.WriteHeader(http.StatusRequestEntityTooLarge)
			_, _ = fmt.Fprintf(w, "Ошибка: тело запроса превышает лимит %d байт", maxErr.Limit)
			return
		}
		w.WriteHeader(http.StatusBadRequest)
		_, _ = fmt.Fprintf(w, "Ошибка чтения: %v", err)
		return
	}

	w.WriteHeader(http.StatusOK)
	_, _ = fmt.Fprintf(w, "Успешно прочитано %d байт", len(data))
}

// EndlessByteStream генерирует бесконечный поток байт
type EndlessByteStream struct {
	remaining int64
}

func (s *EndlessByteStream) Read(p []byte) (n int, err error) {
	if s.remaining <= 0 {
		return 0, io.EOF
	}
	chunk := int64(len(p))
	if chunk > s.remaining {
		chunk = s.remaining
	}
	s.remaining -= chunk
	return int(chunk), nil
}

func main() {
	server := httptest.NewServer(http.HandlerFunc(SafeReadBodyHandler))
	defer server.Close()

	// 1. Попытка отправить 10 ГБ поток (симуляция DoS атаки)
	fmt.Println("=== 1. Отправка 10 ГБ потока на сервер ===")
	tenGBStream := &EndlessByteStream{remaining: 10 * 1024 * 1024 * 1024} // 10 GB

	resp, err := http.Post(server.URL, "application/octet-stream", tenGBStream)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("HTTP Status: %d (Payload Too Large)\n", resp.StatusCode)
	fmt.Printf("Ответ сервера: %s\n\n", string(body))

	// 2. Отправка корректного запроса 50 КБ
	fmt.Println("=== 2. Отправка легитимного запроса 50 КБ ===")
	validData := strings.Repeat("X", 50*1024)
	resp2, _ := http.Post(server.URL, "application/octet-stream", strings.NewReader(validData))
	body2, _ := io.ReadAll(resp2.Body)
	resp2.Body.Close()

	fmt.Printf("HTTP Status: %d (OK)\n", resp2.StatusCode)
	fmt.Printf("Ответ сервера: %s\n", string(body2))
}
```

## Под капотом

Почему чтение бесконечного потока не зависает?
Когда `http.MaxBytesReader` видит превышение лимита, он не читает оставшиеся 9.999 ГБ. Он немедленно возвращает ошибку в прикладной код. После отправки ответа сервер закрывает TCP сокет, отправляя TCP RST пакет. Клиентская операционная система получает ошибку `connection reset by peer`, и передача данных немедленно прекращается на сетевом уровне ядра.

## Подводные камни

1. **Неправильный HTTP статус:** Возврат 400 Bad Request или 500 Internal Server Error вместо 413 Payload Too Large затрудняет отладку легитимным клиентам и скрывает DoS атаку от мониторинга.
2. **Игнорирование gzip/bzip2 (Decompression Bomb / Zip Bomb):** Если клиент шлет сжатое тело `Content-Encoding: gzip`, маленький архив в 1 МБ может распаковаться в 100 ГБ памяти! Распаковщик `gzip.Reader` также обязан оборачиваться в `io.LimitReader`.
3. **Вызов `io.ReadAll` до парсинга JSON:** Всегда передавайте поток напрямую в `json.NewDecoder`, не читая промежуточный `[]byte` массив в память.

## На собеседовании

**Вопрос с собеседования:** Что такое Decompression Bomb (Архивная бомба) в контексте веб-сервисов, принимающих сжатые gzip-запросы, и как от нее защититься в Go?
**Ответ:** 1) Злоумышленник генерирует 1 ГБ нулей, который сжимается в gzip всего в несколько килобайт (`gzip ratio > 1000:1`).
2) Когда сервис получает микро-запрос в 50 КБ и вызывает `gzip.NewReader(r.Body)`, при распаковке буфер моментально раздувается до гигабайтов, сбивая под в OOM.
3) Защита: поток распаковщика `gzip.NewReader` ОБЯЗАТЕЛЬНО оборачивается в `io.LimitReader(gzipReader, maxDecompressedBytes)` (например, не более 10 МБ). При превышении распакованного лимита чтение прерывается.
