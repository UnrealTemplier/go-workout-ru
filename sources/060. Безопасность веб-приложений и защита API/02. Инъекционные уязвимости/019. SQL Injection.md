# SQL Injection: Prepared Statements как единственный надежный рубеж

## Условие

Напишите уязвимый запрос через `fmt.Sprintf("SELECT * FROM users WHERE id = %s", userInput)`. Покажите инъекцию `' OR '1'='1`. Исправьте через `db.QueryRow("SELECT * FROM users WHERE id = ?", id)`. Объясните, почему prepared statements — единственный надёжный способ.

### Исходная формулировка

**SQL Injection.**: Напишите уязвимый запрос через `fmt.Sprintf("SELECT * FROM users WHERE id = %s", userInput)`. Покажите инъекцию `' OR '1'='1`. Исправьте через `db.QueryRow("SELECT * FROM users WHERE id = ?", id)`. Объясните, почему prepared statements — единственный надёжный способ.

## Теория

Среди всех уязвимостей веб-приложений **SQL-инъекции (CWE-89)** исторически занимают лидирующее место в рейтинге OWASP Top 10 по разрушительности последствий.

### Почему экранирование строк (Sanitization / Blacklisting) не работает?
Многие начинающие программисты пытаются «чистить» ввод:
`cleanInput = strings.ReplaceAll(input, "'", "\\'")`
Такой подход обречен на провал:
1. **Кодировки символов:** Атаки через мультибайтовые кодировки (GBK / Big5) превращают `0xbf5c` в валидный символ и съедают обратный слэш экранирования.
2. **Числовые контексты:** В запросе `WHERE id = ` + input кавычки вообще не требуются! Инъекция `1 OR 1=1` не содержит кавычек и легко обходит фильтр.
3. **Вложенные инъекции:** В СУБД существуют сотни встроенных функций (`CHAR()`, `HEX()`, комментирование `/* */`, подзапросы), позволяющих составить пейлоад без ключевых слов.

### Единственный надежный способ: Prepared Statements
Подготовленные выражения полностью устраняют смешение **кода программы (SQL-команд)** и **пользовательских данных**. Движок базы данных компилирует синтаксическое дерево (AST) один раз. Данные подставляются в стек виртуальной машины СУБД напрямую в ячейки регистров, где они не могут быть проинтерпретированы как синтаксические конструкции языка SQL.

## Решение по шагам

1. Создайте базу данных SQLite с таблицей пользователей.
2. Продемонстрируйте уязвимый запрос `fmt.Sprintf("... WHERE id = %s", userInput)`.
3. Покажите успешную инъекцию с извлечением чужих данных.
4. Перепишите запрос на параметризованный `db.QueryRow("... WHERE id = ?", id)`.
5. Продемонстрируйте полную безопасность параметризованного запроса.

## Код решения

**`main.go`**

```go
package main

import (
	"database/sql"
	"fmt"
	"log"

	_ "github.com/mattn/go-sqlite3"
)

type User struct {
	ID    int
	Email string
}

func main() {
	db, err := sql.Open("sqlite3", ":memory:")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	_, _ = db.Exec(`
		CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT);
		INSERT INTO users (id, email) VALUES (1, 'ceo@company.com'), (2, 'intern@company.com');
	`)

	// Ввод злоумышленника в числовое поле ID
	hackerInput := "2 OR id = 1"

	// 1. УЯЗВИМЫЙ КОД: интерполяция строки в числовой контекст
	fmt.Println("=== 1. Уязвимый запрос (Конкатенация без кавычек) ===")
	insecureSQL := fmt.Sprintf("SELECT id, email FROM users WHERE id = %s", hackerInput)
	fmt.Printf("Выполняется SQL: %s\n", insecureSQL)

	rows, err := db.Query(insecureSQL)
	if err != nil {
		log.Fatal(err)
	}
	defer rows.Close()

	for rows.Next() {
		var u User
		_ = rows.Scan(&u.ID, &u.Email)
		fmt.Printf(" -> Утечка аккаунта: ID=%d, Email=%s\n", u.ID, u.Email)
	}

	// 2. БЕЗОПАСНЫЙ КОД: Параметризованный запрос
	fmt.Println("\n=== 2. Безопасный запрос через плейсхолдер (?) ===")
	safeSQL := "SELECT id, email FROM users WHERE id = ?"
	fmt.Printf("Выполняется SQL: %s (Параметр: %q)\n", safeSQL, hackerInput)

	var u User
	// Передаем параметр в безопасный метод QueryRow
	errSafe := db.QueryRow(safeSQL, hackerInput).Scan(&u.ID, &u.Email)
	if errSafe == sql.ErrNoRows {
		fmt.Println("Результат: Запись не найдена (База безопасно искала id со строкой \"2 OR id = 1\")")
	} else if errSafe != nil {
		fmt.Printf("Ошибка СУБД: %v\n", errSafe)
	} else {
		fmt.Printf("Найдено: ID=%d, Email=%s\n", u.ID, u.Email)
	}
}
```

ℹ️ Сравнение уязвимой конкатенации в числовых запросах и параметризованного db.QueryRow

## Под капотом

Почему типизация в Go дополнительно защищает от SQLi?
Если бы функция принимала строго целочисленный тип `id int`, компилятор Go на этапе компиляции отверг бы передачу строки `"2 OR id = 1"`. Уязвимости чаще всего возникают, когда разработчики принимают строковые параметры из HTTP-запроса (`r.URL.Query().Get("id")`) и подставляют их в SQL без предварительной строгой конвертации через `strconv.Atoi()`.

## Подводные камни

1. **Использование `fmt.Sprintf` внутри ORM:** Использование `db.Where(fmt.Sprintf("id = %s", id))` в GORM создает точно такую же уязвимость.
2. **Внедрение в имена процедур и схем:** Плейсхолдеры не защищают имена хранимых процедур (`CALL my_proc(?)`). Имя процедуры обязано проверяться по белому списку.
3. **Second-Order SQL Injection:** Сохранение неочищенного пользовательского ввода в базу данных и последующее использование этого значения в другом небезопасном динамическом SQL-запросе.

## На собеседовании

**Вопрос с собеседования:** В каких редких случаях параметризованный запрос (Prepared Statement) в PostgreSQL может привести к ухудшению производительности (Slow Query) и как это решается?
**Ответ:** Из-за создания **Generic Plan (Обобщенного плана)** выполнения:
1) По умолчанию после 5 выполнений Prepared Statement PostgreSQL строит единый обобщенный план выполнения запроса, не зная конкретных значений параметров.
2) Если распределение данных в таблице сильно неравномерно (Skewed Data), планировщик может выбрать сканирование всей таблицы (Seq Scan) вместо использования индекса (Index Scan).
3) Решение: в драйвере `pgx` или настройках сессии выставляется параметр `plan_cache_mode = force_custom_plan`, принуждающий планировщик строить кастомный план под конкретные параметры без потери безопасности!
