# SSRF (Server-Side Request Forgery) базовый кейс

## Условие

Напишите код, который принимает URL от пользователя и делает HTTP-запрос. Покажите, как атакующий обращается к http://169.254.169.254/ (AWS metadata service) для получения credentials или к http://localhost:6379 (Redis). Покажите уязвимый код и объясните последствия.

### Исходная формулировка

**SSRF (Server-Side Request Forgery) базовый кейс**: Напишите код, который принимает URL от пользователя и делает HTTP-запрос. Покажите, как атакующий обращается к `http://169.254.169.254/` (AWS metadata service) для получения credentials.

## Теория

SSRF (Server-Side Request Forgery) возникает, когда сервер загружает удаленный ресурс по предоставленному пользователем URL без валидации сетевого адреса.

Классические цели SSRF:
1. **Cloud Metadata Services:**
   - AWS IMDSv1: `http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>` отдает временные ключи `AccessKeyId`, `SecretAccessKey`, `Token` с правами роли инстанса EC2/EKS.
   - GCP Metadata: `http://metadata.google.internal/computeMetadata/v1/` (требует заголовок `Metadata-Flavor: Google`, но в старых API или при инъекции заголовков уязвим).
   - Azure IMDS: `http://169.254.169.254/metadata/instance?api-version=2021-02-01`.
2. **Внутренние сервисы компании (Internal Infrastructure):**
   - Redis: `http://127.0.0.1:6379/` (атакующий может выполнять команды протокола RESP через перевод строки или инъекцию gopher://).
   - Kubernetes kubelet API: `http://127.0.0.1:10250/pods`.
   - Локальные панели мониторинга и метрик без авторизации: `http://localhost:9090/metrics`.

## Решение по шагам

1. Создайте уязвимый эндпоинт `/fetch-url?url=...`.
2. Вызовите стандартный `http.Get(rawURL)`.
3. Смоделируйте атаку на метаданные AWS `http://169.254.169.254/latest/meta-data/`.
4. Смоделируйте атаку на внутренний сервис Redis/DB `http://localhost:6379`.
5. Опишите последствия компрометации облачной инфраструктуры и шаги защиты (IMDSv2, сетевая изоляция).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
	"time"
)

// УЯЗВИМЫЙ ОБРАБОТЧИК: принимает любой URL и делает запрос от лица сервера
func VulnerableProxyHandler(w http.ResponseWriter, r *http.Request) {
	targetURL := r.URL.Query().Get("url")
	if targetURL == "" {
		http.Error(w, "missing 'url' parameter", http.StatusBadRequest)
		return
	}

	client := &http.Client{Timeout: 3 * time.Second}
	resp, err := client.Get(targetURL)
	if err != nil {
		http.Error(w, fmt.Sprintf("Error fetching URL: %v", err), http.StatusBadGateway)
		return
	}
	defer resp.Body.Close()

	w.Header().Set("Content-Type", resp.Header.Get("Content-Type"))
	w.WriteHeader(resp.StatusCode)
	_, _ = io.Copy(w, resp.Body)
}

func main() {
	// 1. Создаем симулятор Cloud Metadata Service (169.254.169.254)
	mockAWSMetadata := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if strings.Contains(r.URL.Path, "/iam/security-credentials") {
			w.Header().Set("Content-Type", "application/json")
			_, _ = w.Write([]byte(`{
				"Code": "Success",
				"AccessKeyId": "ASIAQAAAAAAAZSAMPLEKEY",
				"SecretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",
				"Token": "AQoDYXdzEJr11111111111111111111111111111111111111111111111",
				"Expiration": "2026-09-04T18:00:00Z"
			}`))
			return
		}
		_, _ = w.Write([]byte("s3-full-access-role"))
	}))
	defer mockAWSMetadata.Close()

	// 2. Запускаем уязвимый прокси-сервер
	proxyServer := httptest.NewServer(http.HandlerFunc(VulnerableProxyHandler))
	defer proxyServer.Close()

	fmt.Println("=== СИМУЛЯЦИЯ SSRF АТАКИ НА ОБЛАЧНЫЕ МЕТАДАННЫЕ ===")
	// Атакующий отправляет запрос к уязвимому прокси, указывая URL метаданных
	exploitURL := fmt.Sprintf("%s/fetch-url?url=%s/latest/meta-data/iam/security-credentials/prod-role",
		proxyServer.URL, mockAWSMetadata.URL)

	resp, err := http.Get(exploitURL)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	data, _ := io.ReadAll(resp.Body)
	fmt.Printf("HTTP Status: %d\n", resp.StatusCode)
	fmt.Println("УТЕКШИЕ IAM CREDENTIALS АДМИНИСТРАТОРА ОБЛАКА:")
	fmt.Println(string(data))
}
```

## Под капотом

В AWS EC2/ECS сервис Instance Metadata Service v1 (IMDSv1) работает по фиксированному IP `169.254.169.254` (Link-Local адрес, доступный напрямую с сетевого интерфейса виртуалки без шлюза). По умолчанию IMDSv1 не требует никакой аутентификации: простой HTTP GET возвращает всё окружение.
Именно через SSRF в приложении Capital One в 2019 году хакер скачал AWS IAM ключи роли WAF-инстанса и выкачал из S3 более 100 миллионов персональных данных и банковских счетов клиентов.

Для защиты AWS выпустила **IMDSv2**: он требует предварительного получения session token через `PUT /latest/api/token` с заголовком `X-aws-ec2-metadata-token-ttl-seconds: 21600` и ограничением IP hop limit = 1 (что предотвращает обращение из docker-контейнеров с bridge-сетью). Большинство простых SSRF не могут сформировать кастомный `PUT` запрос с нужными заголовками.

## Подводные камни

1. Использование функции `http.Get` напрямую с пользовательским вводом без валидации схемы (`http://` vs `file://`, `gopher://`, `dict://`).
2. Слепое доверие внутренним сетевым сегментам: разработчики часто считают, что внутренняя сеть (`10.0.0.0/8`) полностью безопасна и не требует TLS и паролей на базах Redis/Postgres/Kafka.

## На собеседовании

**Вопрос с собеседования:** Как архитектурно защитить инфраструктуру Kubernetes от SSRF-атак на Cloud Metadata Service?
**Ответ:**
1. **Переход на IMDSv2** с установкой `http-put-response-hop-limit: 1` на уровне AWS EC2. Пакет из pod'а делает один сетевой хоп через виртуальный интерфейс контейнера (veth) до хоста, и счетчик TTL пакета обнуляется, блокируя доступ.
2. **Kubernetes NetworkPolicy:** Запретить всем pod'ам, кроме служебных операторов, сетевой egress-трафик на IP `169.254.169.254/32`.
3. **Egress Proxy / Service Mesh (Envoy/Istio):** Весь внешний трафик пропускать через централизованный egress-gateway с блокировкой приватных подсетей.
