# CORS preflight attacks

## Условие

Покажите, как атакующий может использовать CORS misconfiguration для data exfiltration.

### Исходная формулировка

**CORS preflight attacks**: Покажите, как атакующий может использовать CORS misconfiguration для data exfiltration.

## Теория

CORS Misconfiguration (ошибка конфигурации CORS) — один из наиболее частых векторов утечки конфиденциальных данных в современных веб-приложениях.

Типичные уязвимые шаблоны конфигурации:
1. **Blind Origin Reflection:** Сервер безоговорочно возвращает `Access-Control-Allow-Origin: <any_origin>` и `Access-Control-Allow-Credentials: true`.
2. **Ошибки регулярных выражений:** Разработчик разрешает `.*\.target\.com`, но забывает экранировать точку: `attacker-target.com` совпадает с регулярным выражением. Либо забыты символы `^` и `$`.
3. **Разрешение `null` origin:** Сервер считает `"null"` безопасным. Атакующий размещает эксплойт внутри `iframe sandbox="allow-scripts"` — в этом случае браузер отправляет `Origin: null`, сервер отдает данные, и атакующий считывает их.

Сценарий атаки:
Жертва авторизована в личном кабинете банка. Она переходит по ссылке на вредоносный сайт `evil.com`. JavaScript на `evil.com` делает асинхронный `fetch('https://api.bank.com/user/private-keys', {credentials: 'include'})`. Уязвимый CORS API отдает заголовки доступа, JS читает приватные ключи и отправляет их на сервер злоумышленника.

## Решение по шагам

1. Создайте уязвимый HTTP-сервер, который слепо отражает `Origin` и разрешает `Credentials`.
2. Напишите эндпоинт `/api/secret-data`, возвращающий конфиденциальную информацию.
3. Смоделируйте атакующий скрипт на стороне вредоносного домена (`https://evil-attacker.com`).
4. Покажите, как атакующий успешно эксфильтрует данные жертвы.
5. Покажите исправленный защищенный сервер, который отклоняет чужой Origin.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

// УЯЗВИМЫЙ ОБРАБОТЧИК: Blind Origin Reflection
func VulnerableCORSHandler(w http.ResponseWriter, r *http.Request) {
	origin := r.Header.Get("Origin")
	if origin != "" {
		// КРИТИЧЕСКАЯ УЯЗВИМОСТЬ: слепое отражение недоверенного Origin с Credentials!
		w.Header().Set("Access-Control-Allow-Origin", origin)
		w.Header().Set("Access-Control-Allow-Credentials", "true")
	}

	w.Header().Set("Content-Type", "application/json")
	_, _ = w.Write([]byte(`{"account_number":"40817810000012345678","balance":1500000.00,"owner":"VIP Client"}`))
}

// ЗАЩИЩЕННЫЙ ОБРАБОТЧИК: Strict Whitelist
func SecureCORSHandler(w http.ResponseWriter, r *http.Request) {
	origin := r.Header.Get("Origin")
	allowed := "https://trusted-bank-frontend.com"

	w.Header().Add("Vary", "Origin")
	if origin == allowed {
		w.Header().Set("Access-Control-Allow-Origin", allowed)
		w.Header().Set("Access-Control-Allow-Credentials", "true")
	}

	w.Header().Set("Content-Type", "application/json")
	_, _ = w.Write([]byte(`{"account_number":"40817810000012345678","balance":1500000.00,"owner":"VIP Client"}`))
}

func main() {
	// Симуляция атаки на уязвимый сервер
	fmt.Println("=== СИМУЛЯЦИЯ АТАКИ НА УЯЗВИМЫЙ CORS API ===")
	evilReq := httptest.NewRequest(http.MethodGet, "/api/secret-data", nil)
	evilReq.Header.Set("Origin", "https://evil-attacker.com")
	evilReq.Header.Set("Cookie", "session_id=secret-authenticated-user-session")

	recVuln := httptest.NewRecorder()
	VulnerableCORSHandler(recVuln, evilReq)

	allowOrigin := recVuln.Header().Get("Access-Control-Allow-Origin")
	allowCreds := recVuln.Header().Get("Access-Control-Allow-Credentials")

	fmt.Println("Ответ уязвимого сервера:")
	fmt.Printf("  Access-Control-Allow-Origin: %s\n", allowOrigin)
	fmt.Printf("  Access-Control-Allow-Credentials: %s\n", allowCreds)

	if allowOrigin == "https://evil-attacker.com" && allowCreds == "true" {
		fmt.Println("💥 ЭКСПЛУАТАЦИЯ УСПЕШНА: Браузер разрешит JavaScript на evil-attacker.com прочитать:")
		fmt.Println("  Утекшие данные:", recVuln.Body.String())
	}

	// Симуляция атаки на защищенный сервер
	fmt.Println("\n=== ПРОВЕРКА ЗАЩИЩЕННОГО CORS API ===")
	recSec := httptest.NewRecorder()
	SecureCORSHandler(recSec, evilReq)

	secOrigin := recSec.Header().Get("Access-Control-Allow-Origin")
	fmt.Printf("  Access-Control-Allow-Origin: '%s'\n", secOrigin)

	if secOrigin == "" {
		fmt.Println("🛡️ ЗАЩИТА СРАБОТАЛА: Заголовок CORS не установлен. Браузер заблокирует чтение ответа evil-attacker.com!")
	}
}
```

ℹ️ Демонстрация эксфильтрации данных через уязвимый CORS и механизм блокировки

## Под капотом

Что происходит внутри движка браузера (Blink / Gecko / WebKit) при эксфильтрации?
1. Скрипт на `evil-attacker.com` выполняет `fetch("https://api.bank.com/api/secret-data", {credentials: "include"})`.
2. Браузер замечает cross-origin запрос и отправляет его на `api.bank.com`, автоматически прикрепляя куки жертвы.
3. Сервер возвращает ответ со статусом `200 OK` и заголовками CORS.
4. Перед тем как передать тело ответа в JavaScript промис `fetch().then(r => r.json())`, браузер проверяет:
   `Allow-Origin == Origin` ИЛИ `Allow-Origin == "*" (если credentials: false)`.
5. В уязвимом случае совпадение найдено -> промис успешно разрешается -> данные отправляются на сервер злоумышленника.
6. В защищенном случае заголовок отсутствует -> браузер выбрасывает `TypeError: Failed to fetch (CORS policy violation)` и стирает тело ответа из памяти рендерера.

## Подводные камни

1. Разрешение `Access-Control-Allow-Origin: null`. Хакер может запустить атаку через `<iframe sandbox="allow-scripts" src="...">` или data: URI, заставив браузер отправить заголовок `Origin: null`. Если бэкенд разрешает `null`, атака успешно выполнится.
2. Небезопасные парсеры хоста: проверка `strings.HasSuffix(origin, ".company.com")` может быть обойдена регистрацией домена `notcompany.com`.

## На собеседовании

**Вопрос с собеседования:** Если API защищен JWT токеном в заголовке `Authorization: Bearer ...`, уязвимо ли приложение к CORS misconfiguration?
**Ответ:** Да! Если на клиенте JWT токен хранится в `localStorage` и передается вручную скриптом, CSRF невозможен. Но если бэкенд уязвим к CORS misconfiguration и разрешает кастомные заголовки `Access-Control-Allow-Headers: Authorization`, а токен хранится в cookie с флагом `HttpOnly` (что является best practice против XSS), то CORS misconfiguration позволяет злоумышленнику полностью прочитать закрытые данные жертвы с автоматической подстановкой сессионной куки.
