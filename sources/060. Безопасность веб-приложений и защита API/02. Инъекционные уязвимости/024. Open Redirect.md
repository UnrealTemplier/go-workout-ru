# Open Redirect

## Условие

Реализуйте эндпоинт /login?redirect=https://evil.com. Покажите phishing-атаку. Реализуйте защиту: whitelist allowed hosts, использование relative paths only (/dashboard), или валидация через url.Parse с проверкой схемы и хоста.

### Исходная формулировка

**Open Redirect.**: Реализуйте `/login?redirect=https://evil.com`. Покажите phishing-атаку. Защита: whitelist allowed hosts, использование relative paths only (`/dashboard`), или проверка `url.Parse` + `Hostname` against списка доверенных.

## Теория

Open Redirect (небезопасное перенаправление) возникает, когда веб-приложение принимает недоверенный URL в параметре запроса (например, `?redirect=...` или `?return_url=...`) и перенаправляет пользователя по этому адресу без должной валидации (`http.Redirect(w, r, target, http.StatusFound)`).

Анатомия фишинг-атаки:
1. Злоумышленник рассылает жертвам ссылку вида `https://trusted-bank.com/login?redirect=https://evil-bank-clone.com`.
2. Пользователь видит легитимный домен доверенного банка `trusted-bank.com` и смело нажимает на ссылку.
3. После ввода логина и пароля сервер банка редиректит пользователя на `evil-bank-clone.com`.
4. Злоумышленник показывает поддельную форму «Подтвердите повторно пароль от учетной записи» и ворует учетные данные.

Защита строится на двух уровнях:
- Разрешение только относительных путей (Relative URIs), начинающихся строго с `/` (но не `//`, который интерпретируется браузером как protocol-relative URL).
- Строгий белый список (whitelist) разрешенных доменов для абсолютных URL.

## Решение по шагам

1. Создайте функцию санитизации и валидации `SanitizeRedirectURL(target string, allowedHosts []string) string`.
2. Выполните парсинг целевой строки с помощью `url.Parse(target)`.
3. Отклоните URL со схемами кроме `http` и `https` (защита от `javascript:` псевдосхемы).
4. Проверьте относительные пути: если хост пустой, убедитесь, что путь начинается с одного `/` и не начинается с `//` или `/\`.
5. Если хост указан, проверьте его точное соответствие списку `allowedHosts`.
6. При обнаружении угрозы верните безопасный дефолтный путь (например, `/dashboard`).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
)

var allowedHosts = map[string]bool{
	"company.com":        true,
	"auth.company.com":   true,
	"portal.company.com": true,
}

func SanitizeRedirectURL(rawURL string) string {
	defaultRedirect := "/dashboard"
	if strings.TrimSpace(rawURL) == "" {
		return defaultRedirect
	}

	// Защита от protocol-relative редиректов (например, "//evil.com")
	if strings.HasPrefix(rawURL, "//") || strings.HasPrefix(rawURL, "/\\") {
		return defaultRedirect
	}

	parsed, err := url.Parse(rawURL)
	if err != nil {
		return defaultRedirect
	}

	// 1. Относительный путь (начинается с /, нет хоста и нет схемы)
	if parsed.Scheme == "" && parsed.Host == "" {
		if strings.HasPrefix(parsed.Path, "/") {
			return parsed.RequestURI()
		}
		return defaultRedirect
	}

	// 2. Абсолютный URL: схема обязана быть строго http или https
	if parsed.Scheme != "http" && parsed.Scheme != "https" {
		return defaultRedirect
	}

	// 3. Проверка хоста по строгому whitelist
	host := strings.ToLower(parsed.Hostname())
	if allowedHosts[host] {
		return parsed.String()
	}

	return defaultRedirect
}

func LoginHandler(w http.ResponseWriter, r *http.Request) {
	// Симуляция успешного логина
	redirectParam := r.URL.Query().Get("redirect")
	safeURL := SanitizeRedirectURL(redirectParam)
	http.Redirect(w, r, safeURL, http.StatusFound)
}

func main() {
	testCases := []struct {
		name string
		raw  string
	}{
		{"Legitimate Relative", "/profile/settings"},
		{"Legitimate Whitelisted Host", "https://portal.company.com/home"},
		{"Phishing Evil Domain", "https://evil.com/fake-login"},
		{"Protocol Relative Bypass", "//evil.com/phishing"},
		{"Backslash Trick", "/\\evil.com"},
		{"Javascript URI XSS", "javascript:alert(document.cookie)"},
		{"Subdomain Trick", "https://company.com.evil.com/steal"},
	}

	for _, tc := range testCases {
		req := httptest.NewRequest(http.MethodGet, "/login?redirect="+url.QueryEscape(tc.raw), nil)
		rec := httptest.NewRecorder()
		LoginHandler(rec, req)

		location := rec.Header().Get("Location")
		fmt.Printf("%-26s | Input: %-36s | Redirected To: %s\n", tc.name, tc.raw, location)
	}
}
```

ℹ️ Надежная санитизация URL редиректа с защитой от protocol-relative и javascript URL

## Под капотом

Браузеры по стандарту RFC 3986 поддерживают Protocol-Relative URLs. Если сервер возвратит `Location: //evil.com`, браузер подставит текущую схему (`https:`) и выполнит переход на `https://evil.com`.
Также некоторые браузеры нормализуют обратные слэши: `/\evil.com` интерпретируется как `//evil.com`.
Именно поэтому простая наивная проверка `strings.HasPrefix(raw, "/")` является классической уязвимостью в веб-приложениях! Проверка обязана явно исключать префиксы `//` и `/\`.

## Подводные камни

1. Использование суффиксных проверок хоста: `strings.HasSuffix(parsed.Host, "company.com")`. Хакер зарегистрирует `attackercompany.com` или `mycompany.com` и обойдет валидацию.
2. Игнорирование проверки схемы: редирект на `javascript:alert(1)` в старых веб-вью или браузерах приводит к мгновенному выполнению XSS в контексте страницы приложения.

## На собеседовании

**Вопрос с собеседования:** В чем опасность Open Redirect для OAuth 2.0 / OpenID Connect потоков?
**Ответ:** В протоколе OAuth 2.0 Authorization Code Flow провайдер аутентификации перенаправляет пользователя на `redirect_uri` клиента с секретным одноразовым кодом `code` в query-параметрах. Если у клиента есть уязвимость Open Redirect на эндпоинте обратного вызова, атакующий передает ссылку `redirect_uri=https://client.com/oauth/callback?redirect=https://evil.com`. Провайдер выдает код авторизации клиенту, а тот немедленно перенаправляет браузер с этим кодом на сервер злоумышленника, что приводит к полной компрометации сессии пользователя.
