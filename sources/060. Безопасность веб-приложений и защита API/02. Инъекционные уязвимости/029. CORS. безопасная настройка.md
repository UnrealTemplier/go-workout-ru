# CORS: безопасная настройка

## Условие

Напишите middleware, который обрабатывает Access-Control-Allow-Origin (строгий whitelist, не *), Access-Control-Allow-Methods, Access-Control-Allow-Credentials. Объясните, почему нельзя использовать регулярные выражения без якорей ^ и $.

### Исходная формулировка

**CORS: безопасная настройка.**: Напишите middleware, который обрабатывает `Access-Control-Allow-Origin` (строгий whitelist, не `*`), `Access-Control-Allow-Methods`, `Access-Control-Allow-Credentials`. Объясните, почему `*` + `Allow-Credentials: true` — уязвимость (CSRF с CORS bypass для публичных API).

## Теория

Безопасная настройка CORS в Enterprise-приложениях требует соблюдения строгой гигиены конфигурации:

1. **Точное соответствие Origin:** Никаких подстановок `*` для конфиденциальных API.
2. **Опасность регулярных выражений без якорей:**
   Если вы напишете regex `regexp.MustCompile(`https://.*\\.example\\.com`)`:
   - Без якоря `^` в начале: совпадет с `https://evil-https://sub.example.com`.
   - Без якоря `$` в конце: совпадет с `https://sub.example.com.evil.com`.
   - Без экранирования точки: точка означает «любой символ», поэтому `https://sub-exampleXcom` совпадет с выражением!
3. **Кэширование Preflight (`Access-Control-Max-Age`):** Значительно снижает latency веб-приложения и нагрузку на бэкенд, позволяя браузеру не отправлять `OPTIONS` перед каждым API-запросом в течение заданного интервала (например, 10 минут или 24 часа).

## Решение по шагам

1. Определите строгие правила для валидации: список точных доменов и безопасный скомпилированный regex с якорями `^https:\/\/([a-zA-Z0-9-]+\.)?example\.com$`.
2. Реализуйте функцию `isOriginAllowed(origin string) bool`.
3. В middleware извлеките `Origin` и проверьте его.
4. Выставьте заголовки `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials`, `Vary: Origin`.
5. Корректно обработайте Preflight-запрос `OPTIONS` с кодом `204 No Content` и выставлением `Access-Control-Max-Age`.
6. Продемонстрируйте тестами попытки обхода через `attacker-example.com` и `example.com.attacker.com`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"regexp"
)

// Безопасное регулярное выражение со строгими якорями ^ и $ и экранированными точками
var trustedOriginRegex = regexp.MustCompile(`^https://([a-zA-Z0-9-]+\.)*company\.com$`)

func IsOriginAllowed(origin string) bool {
	// Домен должен соответствовать регулярному выражению целиком
	return trustedOriginRegex.MatchString(origin)
}

func EnterpriseCORSMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		origin := r.Header.Get("Origin")

		// Запрос без заголовка Origin (same-origin или desktop клиент)
		if origin == "" {
			next.ServeHTTP(w, r)
			return
		}

		// Всегда выставляем Vary: Origin для кэшей
		w.Header().Add("Vary", "Origin")

		if !IsOriginAllowed(origin) {
			// Недоверенный Origin: прерываем preflight или не ставим CORS заголовки
			if r.Method == http.MethodOptions {
				w.WriteHeader(http.StatusForbidden)
				return
			}
			next.ServeHTTP(w, r)
			return
		}

		// Выставляем проверенный Origin
		w.Header().Set("Access-Control-Allow-Origin", origin)
		w.Header().Set("Access-Control-Allow-Credentials", "true")

		if r.Method == http.MethodOptions {
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Authorization, Content-Type, X-CSRF-Token")
			w.Header().Set("Access-Control-Max-Age", "86400") // Кэшировать preflight на 24 часа
			w.WriteHeader(http.StatusNoContent)               // 204
			return
		}

		next.ServeHTTP(w, r)
	})
}

func main() {
	handler := EnterpriseCORSMiddleware(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte(`{"data":"secure enterprise payload"}`))
	}))

	testOrigins := []struct {
		origin   string
		expected bool
	}{
		{"https://company.com", true},
		{"https://api.company.com", true},
		{"https://staging.internal.company.com", true},
		{"https://company.com.attacker.com", false},  // Обход без $
		{"https://attackercompany.com", false},       // Обход без экранирования точки / границ
		{"http://company.com", false},                // HTTP вместо HTTPS
		{"https://evil.com/?company.com", false},     // Попытка внедрения в query
	}

	for _, tc := range testOrigins {
		req := httptest.NewRequest(http.MethodOptions, "/api", nil)
		req.Header.Set("Origin", tc.origin)
		rec := httptest.NewRecorder()
		handler.ServeHTTP(rec, req)

		allowed := rec.Header().Get("Access-Control-Allow-Origin") != ""
		status := "BLOCKED"
		if allowed {
			status = "ALLOWED"
		}
		fmt.Printf("Origin: %-38s -> [%s] (Correct: %v)\n", tc.origin, status, allowed == tc.expected)
	}
}
```

ℹ️ Enterprise CORS Middleware со строгой регуляркой и preflight кэшированием

## Под капотом

Заголовок `Access-Control-Max-Age: 86400` указывает браузеру кэшировать результат preflight OPTIONS-запроса на 86400 секунд (24 часа).
В современных браузерах действуют внутренние жесткие лимиты на максимальное значение `Access-Control-Max-Age`:
- Google Chrome (Chromium): максимум 7200 секунд (2 часа). Любое большее значение усекается до 2 часов.
- Mozilla Firefox: максимум 86400 секунд (24 часа).
- WebKit (Safari): максимум 3600 секунд (1 час).
Кэширование preflight критически важно в HighLoad системах, так как без него каждый HTTP-запрос фронтенда превращается в два сетевых RTT (Round Trip Time) обращения к бэкенду.

## Подводные камни

1. Использование регулярных выражений вида `.*company\.com`. Если забыть `^`, домен `https://evil-company.com` успешно пройдет проверку. Если забыть `$`, пройдет `https://company.com.evil.com`.
2. Компиляция регулярного выражения внутри тела HTTP-обработчика: `regexp.Compile` внутри `ServeHTTP` приводит к огромным аллокациям памяти и деградации производительности. Регулярные выражения обязаны компилироваться один раз на этапе инициализации (`var rx = regexp.MustCompile(...)`).

## На собеседовании

**Вопрос с собеседования:** Почему в production-системах многие компании предпочитают строгий map-whitelist вместо регулярных выражений для проверки Origin?
**Ответ:**
1. **Безопасность:** Регулярные выражения подвержены человеческим ошибкам (забытый слэш, точка, якорь) и уязвимости ReDoS (Regular Expression Denial of Service) при катастрофическом бэктрекинге на длинных строках.
2. **Производительность:** Поиск по хэш-таблице (`map[string]struct{}`) выполняется за константное время \(O(1)\) без аллокаций памяти и работы конечного автомата регулярного выражения.
