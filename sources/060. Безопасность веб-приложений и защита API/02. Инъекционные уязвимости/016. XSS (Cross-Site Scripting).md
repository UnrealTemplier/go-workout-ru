# XSS (Cross-Site Scripting): html/template vs text/template и CSP

## Условие

Напишите код с XSS-уязвимостью в template и исправьте её через `html/template` (автоматический escape) и CSP header.

### Исходная формулировка

**XSS (Cross-Site Scripting)**: Напишите код с XSS-уязвимостью в template и исправьте её через `html/template` (автоматический escape) и CSP header.

## Теория

Атака **XSS (Cross-Site Scripting)** заключается во внедрении вредоносного JavaScript-кода в веб-страницу, просматриваемую другими пользователями.

### Разница между `text/template` и `html/template`:
1. **`text/template` (ОПАСЕН для HTML):**
   Выполняет строковую интерполяцию без экранирования. Если пользователь введет:
   `<script>alert(document.cookie)</script>`,
   строка попадет в HTML-разметку как исполняемый тег!
2. **`html/template` (БЕЗОПАСЕН):**
   Выполняет **контекстно-зависимое экранирование (Context-Aware Auto-Escaping)**:
   - Внутри HTML-тела: `<` превращается в `&lt;`, `>` в `&gt;`.
   - Внутри атрибутов `href="..."`: фильтрует опасные схемы `javascript:`.
   - Внутри тегов `<script>`: сериализует данные в безопасный JSON-литерал.

### Заголовок Content Security Policy (CSP):
Второй рубеж обороны:
```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```
Запрещает браузеру исполнять любые инлайн-скрипты `<script>` и загружать ресурсы со сторонних недоверенных доменов!

## Решение по шагам

1. Создайте уязвимый рендеринг через `text/template`.
2. Продемонстрируйте успешное внедрение XSS-вектора.
3. Замените на безопасный пакет `html/template`.
4. Настройте middleware с заголовком `Content-Security-Policy`.
5. Проверьте экранирование опасных символов в сгенерированном HTML.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"fmt"
	htmltmpl "html/template"
	"net/http"
	"net/http/httptest"
	texttmpl "text/template"
)

type PageData struct {
	UserName string
}

func main() {
	userData := PageData{
		UserName: `<script>alert('XSS-ATTACK! Cookie: ' + document.cookie);</script>`,
	}

	// 1. УЯЗВИМЫЙ РЕНДЕРИНГ: text/template НЕ экранирует HTML теги
	textTmpl := texttmpl.Must(texttmpl.New("insecure").Parse("<h1>Привет, {{.UserName}}!</h1>"))
	var insecureBuf bytes.Buffer
	_ = textTmpl.Execute(&insecureBuf, userData)

	fmt.Println("=== 1. Уязвимый рендеринг через text/template ===")
	fmt.Println(insecureBuf.String())
	fmt.Println("Результат: Вредоносный скрипт попал в разметку в открытом виде!")

	// 2. БЕЗОПАСНЫЙ РЕНДЕРИНГ: html/template автоматически экранирует спецсимволы
	htmlTmpl := htmltmpl.Must(htmltmpl.New("secure").Parse("<h1>Привет, {{.UserName}}!</h1>"))
	var secureBuf bytes.Buffer
	_ = htmlTmpl.Execute(&secureBuf, userData)

	fmt.Println("\n=== 2. Безопасный рендеринг через html/template ===")
	fmt.Println(secureBuf.String())
	fmt.Println("Результат: Специфические символы < и > превращены в безопасные HTML entities (&lt; &gt;)")

	// 3. Защита на уровне браузера через Content Security Policy (CSP)
	mux := http.NewServeMux()
	mux.HandleFunc("/profile", func(w http.ResponseWriter, r *http.Request) {
		// Строгая политика CSP: запрет инлайн-скриптов
		w.Header().Set("Content-Security-Policy", "default-src 'self'; script-src 'self'")
		w.Header().Set("Content-Type", "text/html; charset=utf-8")
		_ = htmlTmpl.Execute(w, userData)
	})

	server := httptest.NewServer(mux)
	defer server.Close()

	resp, _ := http.Get(server.URL + "/profile")
	fmt.Println("\n=== 3. Проверка заголовка CSP ответа сервера ===")
	fmt.Printf("Content-Security-Policy: %s\n", resp.Header.Get("Content-Security-Policy"))
	resp.Body.Close()
}
```

ℹ️ Автоматическое контекстное экранирование html/template и заголовок Content-Security-Policy

**`Терминал`**

```bash
go run main.go
# === 1. Уязвимый рендеринг через text/template ===

# Результат: Вредоносный скрипт попал в разметку в открытом виде!
#

#

# Content-Security-Policy: default-src 'self'; script-src 'self'
```

## Под капотом

Как работает контекстный парсер в `html/template`?
Пакет реализует конечный автомат (FSM), отслеживающий текущее лексическое состояние HTML-документа:
- Если плейсхолдер находится внутри HTML-тела: применяется `htmlEscaper`.
- Если плейсхолдер находится внутри атрибута `href="{{.URL}}"`: проверяется схема URL; если там `javascript:...`, значение заменяется на безопасный `#ZgotmplZ`.
- Если плейсхолдер находится внутри `<script>var x = {{.Data}};</script>`: применяется `jsValEscaper`, сериализующий строку в безопасный JSON-литерал.

## Подводные камни

1. **Использование `template.HTML` для обхода экранирования:** Тип `template.HTML(untrustedInput)` отключает защиту. Никогда не оборачивайте пользовательский ввод в `template.HTML`!
2. **XSS в DOM на фронтенде (DOM-based XSS):** Если SPA на React/Vue наивно берет данные из API и вставляет их через `innerHTML` или `dangerouslySetInnerHTML`, защита бэкенда не спасет.
3. **CSP с `'unsafe-inline'`:** Использование директивы `'unsafe-inline'` в CSP полностью нивелирует защиту от внедрения скриптов.

## На собеседовании

**Вопрос с собеседования:** Что такое Nonce-based Content Security Policy (CSP v3) и почему она превосходит классическую доменную whitelist CSP?
**Ответ:** Whitelist CSP (`script-src 'self' https://trusted.cdn.com`) уязвима к атакам через уязвимости JSONP на доверенном CDN (например, злоумышленник находит на Google CDN скрипт с колбэком и исполняет произвольный JS).
**Nonce-based CSP:**
1) На каждый HTTP-запрос сервер генерирует криптографически случайный 128-битный токен (Nonce): `Content-Security-Policy: script-src 'nonce-rAnd0m123'`.
2) Сервер проставляет этот же атрибут в легитимные теги `<script nonce="rAnd0m123">`.
3) Браузер выполняет скрипт **только** если nonce совпал. Любой внедренный атакующим тег `<script>` не содержит правильного одноразового nonce и блокируется браузером!
