# CSRF: Double Submit Cookie и заголовок X-CSRF-Token

## Условие

Реализуйте CSRF protection через double submit cookie + custom header. Покажите, почему SameSite=Strict/Lax в cookies тоже помогает.

### Исходная формулировка

**CSRF (Cross-Site Request Forgery)**: Реализуйте CSRF protection через double submit cookie + custom header. Покажите, почему SameSite=Strict/Lax в cookies тоже помогает.

## Теория

Атака **CSRF (Cross-Site Request Forgery / Межсайтовая подделка запроса)** заставляет браузер авторизованного пользователя выполнить нежелательное действие на доверенном сайте (например, отправить деньги или изменить email).

### Почему браузер уязвим:
Если сайт `bank.ru` использует стандартные куки сессии, браузер автоматически прикрепляет их к **любому** исходящему запросу на `bank.ru`, даже если запрос отправлен скрытой формой с вредоносного сайта `evil.com`!

### Механизм Double Submit Cookie Pattern:
1. Сервер генерирует криптографически случайный токен `csrf_token` (например, 32 байта hex).
2. Токен отправляется клиенту в куке `XSRF-TOKEN` (доступной для чтения из JavaScript: `HttpOnly: false`).
3. При отправке мутирующего запроса (POST/PUT/DELETE) клиентский JavaScript считывает куку и отправляет то же самое значение в кастомном HTTP-заголовке:
   `X-CSRF-Token: <token>`.
4. Серверный Middleware сверяет:
   `cookie.Value == req.Header.Get("X-CSRF-Token")`.

**Почему сторонний сайт `evil.com` не может провести атаку?**
Благодаря правилу **Same-Origin Policy (SOP)** браузер запрещает JavaScript с сайта `evil.com` читать куки домена `bank.ru`. Злоумышленник не знает токен и не может выставить заголовок `X-CSRF-Token`!

## Решение по шагам

1. Реализуйте функцию генерации токена CSRF.
2. Создайте Middleware, устанавливающее куку `XSRF-TOKEN` для безопасных методов (GET/HEAD).
3. Для мутирующих методов (POST/PUT/DELETE) добавьте сверку токена из заголовка `X-CSRF-Token` и куки через `subtle.ConstantTimeCompare`.
4. Продемонстрируйте блокировку поддельного POST-запроса без заголовка.
5. Продемонстрируйте успешное выполнение запроса с валидным токеном.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
)

const (
	CSRFCookieName = "XSRF-TOKEN"
	CSRFHeaderName = "X-CSRF-Token"
)

func generateCSRFToken() string {
	b := make([]byte, 16)
	_, _ = io.ReadFull(rand.Reader, b)
	return hex.EncodeToString(b)
}

// DoubleSubmitCSRFMiddleware реализует stateless защиту от CSRF
func DoubleSubmitCSRFMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// 1. Безопасные методы (GET, HEAD, OPTIONS) только выставляют куку при ее отсутствии
		if r.Method == http.MethodGet || r.Method == http.MethodHead || r.Method == http.MethodOptions {
			if _, err := r.Cookie(CSRFCookieName); err != nil {
				token := generateCSRFToken()
				http.SetCookie(w, &http.Cookie{
					Name:     CSRFCookieName,
					Value:    token,
					Path:     "/",
					Secure:   true,
					HttpOnly: false, // JavaScript ДОЛЖЕН иметь возможность прочитать куку для заголовка
					SameSite: http.SameSiteLaxMode,
				})
			}
			next.ServeHTTP(w, r)
			return
		}

		// 2. Мутирующие методы (POST, PUT, DELETE, PATCH) требуют сверки токенов
		cookie, err := r.Cookie(CSRFCookieName)
		if err != nil || cookie.Value == "" {
			w.WriteHeader(http.StatusForbidden)
			_, _ = w.Write([]byte(`{"error":"csrf_token_missing_in_cookie"}`))
			return
		}

		headerToken := r.Header.Get(CSRFHeaderName)
		if headerToken == "" {
			w.WriteHeader(http.StatusForbidden)
			_, _ = w.Write([]byte(`{"error":"csrf_token_missing_in_header"}`))
			return
		}

		// 3. Сверка значения куки и заголовка за константное время
		if subtle.ConstantTimeCompare([]byte(cookie.Value), []byte(headerToken)) != 1 {
			w.WriteHeader(http.StatusForbidden)
			_, _ = w.Write([]byte(`{"error":"csrf_token_mismatch"}`))
			return
		}

		next.ServeHTTP(w, r)
	})
}

func main() {
	transferHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"money_transferred"}`))
	})

	server := httptest.NewServer(DoubleSubmitCSRFMiddleware(transferHandler))
	defer server.Close()

	// 1. Первичный GET запрос: получаем CSRF куку
	respGet, _ := http.Get(server.URL)
	var csrfCookie *http.Cookie
	for _, c := range respGet.Cookies() {
		if c.Name == CSRFCookieName {
			csrfCookie = c
			break
		}
	}
	respGet.Body.Close()

	fmt.Println("=== 1. Получен CSRF токен в куке ===")
	fmt.Printf("Значение куки: %s\n\n", csrfCookie.Value)

	// 2. Атака CSRF: вредоносный сайт отправляет POST с кукой жертвы, но без заголовка
	fmt.Println("=== 2. Атака CSRF (POST с кукой, но БЕЗ кастомного заголовка) ===")
	reqAttack, _ := http.NewRequest("POST", server.URL, strings.NewReader(`amount=1000`))
	reqAttack.AddCookie(csrfCookie) // Браузер автоматически прикрепил куку!
	respAttack, _ := http.DefaultClient.Do(reqAttack)
	bodyAttack, _ := io.ReadAll(respAttack.Body)
	respAttack.Body.Close()

	fmt.Printf("HTTP Status: %d\nОтвет сервера: %s\n\n", respAttack.StatusCode, string(bodyAttack))

	// 3. Легитимный запрос: фронтенд прочитал куку и подставил ее в заголовок X-CSRF-Token
	fmt.Println("=== 3. Легитимный вызов (Кука + совпадающий заголовок X-CSRF-Token) ===")
	reqLegit, _ := http.NewRequest("POST", server.URL, strings.NewReader(`amount=1000`))
	reqLegit.AddCookie(csrfCookie)
	reqLegit.Header.Set(CSRFHeaderName, csrfCookie.Value)
	respLegit, _ := http.DefaultClient.Do(reqLegit)
	bodyLegit, _ := io.ReadAll(respLegit.Body)
	respLegit.Body.Close()

	fmt.Printf("HTTP Status: %d (OK)\nОтвет сервера: %s\n", respLegit.StatusCode, string(bodyLegit))
}
```

## Под капотом

Почему Double Submit Cookie работает без сохранения токена в базе данных (stateless)?
Серверу не нужно хранить токен в Redis или сессии: он лишь проверяет **криптографическое совпадение двух независимых каналов доставки** (куки и кастомного заголовка). Сторонний сайт при CSRF может заставить браузер отправить куку, но из-за политики Same-Origin Policy (SOP) JavaScript стороннего сайта не может прочитать чужую куку и подставить ее в заголовок.

## Подводные камни

1. **Флаг HttpOnly: true на CSRF-куке:** Если выставить `HttpOnly: true`, ваш собственный фронтенд-скрипт не сможет прочитать токен и вставить в заголовок `X-CSRF-Token`.
2. **Атака через поддомены (Cookie Tossing):** Если поддомен `blog.company.com` скомпрометирован, он может установить куку для `company.com`. Для защиты от Cookie Tossing в куку помещают криптографически подписанный HMAC-токен (Signed Double Submit Cookie).
3. **Отсутствие флага Secure:** Передача CSRF куки по незашифрованному HTTP открывает вектор перехвата в сети Wi-Fi.

## На собеседовании

**Вопрос с собеседования:** Если все современные браузеры по умолчанию включают флаг `SameSite=Lax` для сессионных кук, зачем компаниям по-прежнему внедрять CSRF-токены в API?
**Ответ:** 1) **Lax разрешает отправку кук при Top-Level Navigation:** Если уязвимое действие на сервере случайно или намеренно вызывается методом `GET` (`GET /api/v1/delete_account?id=1`), браузер отправит куки `SameSite=Lax` при обычном клике по ссылке на сайте атакующего!
2) **Окно 2 минут в Chrome (Lax-by-default + POST exception):** В старых версиях Chrome для новых кук без явного SameSite первые 2 минуты разрешалась отправка даже в POST-запросах.
3) **Defense-in-Depth:** Полагаться исключительно на политику браузера рискованно: CSRF-токены гарантируют защиту на уровне протокола приложения независимо от настроек клиента.
