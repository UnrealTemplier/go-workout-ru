# Многоуровневое ограничение частоты запросов (Rate Limiting Defense-in-Depth)

## Условие

Реализуйте эшелонированное ограничение скорости (Defense-in-Depth): на уровне сетевого IP (Token Bucket) и на прикладном уровне (API Key / User ID) в Go HTTP middleware.

### Исходная формулировка

**Rate limiting на всех уровнях:**
* Application level (per user/API key)
* Network level (per IP через iptables)
* Infrastructure level (через Envoy/HAProxy)

## Теория

Ограничение скорости (Rate Limiting) должно работать на нескольких эшелонах:
1. Сетевой уровень: отсечка DDoS по IP-адресу или подсети (IPTables / Nginx / Envoy).
2. Прикладной уровень: защита бизнес-логики по идентификатору пользователя или API-токену (внутри Go сервиса через Redis / Token Bucket).
Такая многослойная защита гарантирует, что даже в случае пробития внешнего шлюза внутренний сервис не ляжет под всплеском запросов скомпрометированного клиента.

## Решение по шагам

Используйте алгоритм Token Bucket (`golang.org/x/time/rate`).
Создайте HTTP middleware, извлекающее API-токен из заголовка `Authorization`.
Свяжите лимитер с каждым уникальным токеном.
Верните статус `429 Too Many Requests` с заголовком `Retry-After` при превышении лимита.

## Код решения

**`rate_limiter.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync"
	"golang.org/x/time/rate"
)

type ClientLimiter struct {
	mu      sync.Mutex
	clients map[string]*rate.Limiter
}

func NewClientLimiter() *ClientLimiter {
	return &ClientLimiter{clients: make(map[string]*rate.Limiter)}
}

func (cl *ClientLimiter) GetLimiter(clientID string) *rate.Limiter {
	cl.mu.Lock()
	defer cl.mu.Unlock()

	limiter, exists := cl.clients[clientID]
	if !exists {
		// 10 запросов в секунду с бурстом до 20
		limiter = rate.NewLimiter(10, 20)
		cl.clients[clientID] = limiter
	}
	return limiter
}

func RateLimitMiddleware(cl *ClientLimiter, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		token := r.Header.Get("X-API-Key")
		if token == "" {
			token = r.RemoteAddr // Fallback на IP
		}

		limiter := cl.GetLimiter(token)
		if !limiter.Allow() {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "Too Many Requests", http.StatusTooManyRequests) // 429
			return
		}
		next(w, r)
	}
}

func main() {
	limiter := NewClientLimiter()
	_ = RateLimitMiddleware(limiter, func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "OK")
	})
	fmt.Println("[RATE-LIMIT] Middleware ограничения частоты запросов успешно инициализирован.")
}
```

ℹ️ Защитное middleware ограничения запросов на базе алгоритма Token Bucket

## Под капотом

Token Bucket накапливает токены с фиксированной скоростью \(r\) до емкости \(b\). Метод `limiter.Allow()` атомарно списывает токен или возвращает false за \(O(1)\) без аллокаций памяти.

## Подводные камни

Хранение лимитеров в оперативной памяти одного инстанса не защищает распределенный кластер; для кластера требуется распределенный лимитер на базе Redis или Envoy Rate Limit Service.

## На собеседовании

В чем разница между алгоритмами Token Bucket, Leaky Bucket и Sliding Window Counter? Token Bucket допускает короткие всплески трафика (burst), что оптимально для пользовательских API.
