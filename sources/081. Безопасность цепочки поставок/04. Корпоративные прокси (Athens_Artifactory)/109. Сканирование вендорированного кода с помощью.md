# Сканирование вендорированного кода с помощью govulncheck

## Условие

Запустите утилиту govulncheck с явным указанием флага -mod=vendor для сканирования кода зависимостей, фактически находящегося в директории vendor/ проекта.

### Исходная формулировка

**Vendor + govulncheck**: Запустите `govulncheck ./vendor/...` для сканирования vendored dependencies.

## Теория

При анализе безопасности критически важно сканировать именно тот код, который будет включен в релизный бинарник. Если разработчик локально модифицировал файл внутри `vendor/` или откатил версию вручную, обычный сканер `go.mod` этого не заметит. Утилита `govulncheck` поддерживает сборку и анализ графа вызовов с флагом `-mod=vendor`.

## Решение по шагам

Подготовьте проект с каталогом `vendor/`.
Запустите сканирование: `govulncheck -mod=vendor ./...`.
Изучите отчет о достижимых уязвимостях.
Убедитесь, что анализ учитывает локальное состояние файлов вендора.

## Код решения

**`vuln_vendor.sh`**

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "[GOVULNCHECK] Сканирование локального вендора зависимостей..."

# Флаг -mod=vendor принуждает анализатор строить AST по коду из папки vendor/
if govulncheck -mod=vendor ./... ; then
    echo "[OK] В коде вендора уязвимостей не найдено."
else
    echo "[ALERT] В вендорированном коде обнаружены уязвимые вызовы!"
    exit 1
fi
```

ℹ️ Запуск govulncheck с использованием локального вендора

## Под капотом

govulncheck компилирует AST-представление пакетов, подставляя символы из `vendor/modules.txt`, а затем опрашивает базу `vuln.go.dev` по реальным ревизиям модулей.

## Подводные камни

Если файлы в `vendor/` рассинхронизированы с `modules.txt`, govulncheck упадет с синтаксической ошибкой загрузчика пакетов.

## На собеседовании

Почему аудит исходников vendor предпочтительнее аудита lock-файлов? Lock-файл декларирует намерения, а исходники в vendor представляют собой фактический код, идущий в прод.
