# Автоматический аудит уязвимостей в GitHub Actions перед компиляцией Docker

## Условие

Напишите законченный Dockerfile и пайплайн GitHub Actions, в котором этап сборки Docker-образа запускается только после успешного прохождения аудита govulncheck.

### Исходная формулировка

**Автоматический аудит уязвимостей в GitHub Actions**: Интегрируйте `govulncheck` в ваш пайплайн сборки CI (из раздела №39) [657]. Добавьте шаг автоматического запуска `govulncheck` перед этапом компиляции Docker-образа. Пайплайн должен завершаться ошибкой и блокировать слияние кода в ветку `main`, если в кодовой базе обнаружены транзитивные уязвимости с известными CVE.

## Теория

Сборка уязвимого бинарника и упаковка его в контейнерный образ — напрасная трата вычислительных ресурсов раннеров. Архитектурный принцип Shift-Left Security требует строгого порядка этапов (Stages): 1. `Lint & Unit Test`: проверка корректности синтаксиса и бизнес-логики; 2. `Security Audit`: запуск `govulncheck ./...` и проверка `go mod verify`; 3. `Build & Containerize`: только если шаги 1 и 2 завершились успешно, запускается `docker build` и публикация образа в Container Registry (Harbor, Yandex Container Registry, Docker Hub). Это гарантирует, что ни один образ с известными RCE уязвимостями не попадет в registry компании.

## Решение по шагам

Создайте multi-stage Dockerfile для Go приложения.
Настройте GitHub Actions workflow с зависимостью needs: [security-audit].
Убедитесь, что при падении аудита сборка контейнера не запускается.
Проверьте публикацию только валидированных образов.

## Код решения

**`secure_pipeline.yaml`**

```yaml
name: Secure Build and Publish Pipeline

on:
  push:
    branches: [ main ]

jobs:
  security-audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.23'
      - name: Verify Dependencies Integrity
        run: go mod verify
      - name: Run govulncheck
        run: |
          go install golang.org/x/vuln/cmd/govulncheck@latest
          govulncheck ./...

  docker-build:
    needs: [security-audit] # ЗАПУСКАЕТСЯ ТОЛЬКО ПОСЛЕ УСПЕШНОГО АУДИТА!
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build Secure Docker Image
        run: |
          echo "Security checks passed. Commencing container build..."
          docker build -t mycorp/secure-service:latest -f Dockerfile .
```

ℹ️ Блокировка сборки Docker-образа при обнаружении уязвимостей в кодовой базе

**`Dockerfile`**

```dockerfile
# Multi-stage build для максимальной безопасности
FROM golang:1.23-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download && go mod verify
COPY . .
# Сборка статического бинарника без CGO с удалением отладочной информации
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /app/server .

# Финальный образ на базе scratch (нулевая площадь атаки)
FROM scratch
COPY --from=builder /app/server /server
USER 65534:65534
ENTRYPOINT ["/server"]
```

ℹ️ Минималистичный безопасный Dockerfile на базе scratch

## Под капотом

Флаг `-trimpath` удаляет абсолютные пути локальной файловой системы разработчика из скомпилированного бинарника, а образ `scratch` не содержит утилит sh, bash, curl, libc, лишая злоумышленника инструментов при попытке побега из контейнера.

## Подводные камни

Использование одного большого Dockerfile, где сборка и запуск происходят в одном тяжелом образе golang:alpine. В таком образе остаются компилятор, утилиты сборки и пакетный менеджер apk, что создает колоссальную площадь атаки.

## На собеседовании

Вопрос на собеседовании в Wildberries: 'Почему для Go бинарников в продакшене выбирают base image scratch или distroless?' Ответ: 'Потому что Go компилируется в самодостаточный статический бинарник. В образе scratch нет ни шелла (/bin/sh), ни пакетных менеджеров, ни libc. Даже если злоумышленник найдет RCE в приложении, он не сможет выполнить системную команду или скачать эксплойт'.
