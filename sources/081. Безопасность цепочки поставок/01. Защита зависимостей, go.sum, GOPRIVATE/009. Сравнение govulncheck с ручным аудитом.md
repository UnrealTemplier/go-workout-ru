# Сравнение govulncheck с ручным аудитом: go list, go mod graph и база OSV

## Условие

Реализуйте Go-скрипт, который строит полный граф модулей через go mod graph, находит зависимости с известными CVE и сравнивает результаты с точным графом вызовов govulncheck.

### Исходная формулировка

**Сравнение с ручным аудитом.**: Выполните `go list -m all | grep <vulnerable_pkg>` и `go mod graph`. Покажите, как `govulncheck` использует OSV (Open Source Vulnerabilities) database и `vulncheck.Binary` для бинарников. Объясните, почему `govulncheck ./...` анализирует исходники, а `govulncheck -mode binary ./app` — скомпилированный бинарник.

## Теория

Команда `go list -m all` выводит плоский список всех модулей в сборке. Команда `go mod graph` выводит ориентированный граф зависимостей в формате `Parent Child`. Однако оба этих инструмента работают исключительно на уровне модулей (`MVS`). Они не знают, скомпилировался ли хоть один байт этого модуля в итоговый бинарник! Модуль может быть подключен для запуска тестов (`_test.go`), являться частью неиспользуемого пакета или предназначаться для другой операционной системы (под тегом сборки `//go:build windows`). Ручной аудит по `go mod graph` приводит к сотням бессмысленных задач на обновление, тогда как `govulncheck` анализирует AST с учетом активных build tags (`GOOS`, `GOARCH`).

## Решение по шагам

Распарсите вывод go mod graph в структуру графа смежности.
Найдите путь от корневого модуля к целевой зависимости.
Проверьте теги сборки (build tags).
Покажите, почему статический граф вызовов точнее модульного графа.

## Код решения

**`graph_audit_comparison.go`**

```go
package main

import (
	"bufio"
	"fmt"
	"strings"
)

// DependencyGraph хранит связи между модулями
type DependencyGraph struct {
	edges map[string][]string
}

func NewDependencyGraph() *DependencyGraph {
	return &DependencyGraph{edges: make(map[string][]string)}
}

func (g *DependencyGraph) AddEdge(from, to string) {
	g.edges[from] = append(g.edges[from], to)
}

// FindPathToPackage находит цепочку импортов (Breadth-First Search)
func (g *DependencyGraph) FindPathToPackage(start, target string) []string {
	queue := [][]string{{start}}
	visited := make(map[string]bool)

	for len(queue) > 0 {
		path := queue[0]
		queue = queue[1:]
		node := path[len(path)-1]

		if strings.HasPrefix(node, target) {
			return path
		}

		if visited[node] {
			continue
		}
		visited[node] = true

		for _, neighbor := range g.edges[node] {
			newPath := append([]string{}, path...)
			newPath = append(newPath, neighbor)
			queue = append(queue, newPath)
		}
	}
	return nil
}

func main() {
	rawGraph := `mycorp/app github.com/gin-gonic/gin@v1.9.0
mycorp/app github.com/stretchr/testify@v1.8.2
github.com/gin-gonic/gin@v1.9.0 golang.org/x/crypto@v0.0.0-20201221181555-eec23a3978ad
`
	g := NewDependencyGraph()
	scanner := bufio.NewScanner(strings.NewReader(rawGraph))
	for scanner.Scan() {
		parts := strings.Fields(scanner.Text())
		if len(parts) == 2 {
			g.AddEdge(parts[0], parts[1])
		}
	}

	path := g.FindPathToPackage("mycorp/app", "golang.org/x/crypto")
	fmt.Println("Module Dependency Path (via go mod graph):")
	for i, step := range path {
		fmt.Printf("  [%d] %s\n", i+1, step)
	}

	fmt.Println("\nArchitectural Conclusion:")
	fmt.Println("go mod graph finds the module chain, but CANNOT verify whether the vulnerable function is actually executed.")
	fmt.Println("govulncheck completes the audit by inspecting the AST call graph.")
}
```

ℹ️ Сравнение графа зависимостей модулей и анализа вызовов функций

## Под капотом

`go mod why -m <package>` в терминале выполняет похожий поиск кратчайшего пути по графу импортов, помогая понять, кто именно затянул подозрительный пакет в проект.

## Подводные камни

Удаление зависимости из `go.mod` без `go mod tidy`. Если зависимость осталась в `go.sum`, сканеры манифестов продолжат рапортовать о ней.

## На собеседовании

Вопрос на собеседовании в Kasperskу: 'Как узнать, почему пакет оказался в зависимостях моего проекта?' Ответ: 'Выполнить команду `go mod why <import_path>`. Она выведет кратчайшую цепочку импортов от основного пакета до целевого пакета'.
