# Симуляция уязвимости: аудит устаревшего пакета JWT и безопасный переход

## Условие

Создайте тестовый сценарий с устаревшей версией github.com/golang-jwt/jwt/v4 с известной CVE. Просканируйте код через govulncheck и обновите модуль до безопасной версии.

### Исходная формулировка

**[Симуляция уязвимости]**: Подключи старую версию пакета с известной CVE (например, `github.com/golang-jwt/jwt/v4 v4.0.0`). Запусти `govulncheck`. Убедись, что утилита нашла уязвимость. Обнови пакет до последней версии и проверь, что отчет чист.

## Теория

Классический пример критической уязвимости в Go экосистеме — уязвимость обхода проверки подписи в ранних версиях JWT (CVE-2020-26160 / CVE-2022-32149). Библиотеки не проверяли тип используемого алгоритма (Algorithm Confusion: HMAC против RSA), что позволяло атакующему подписать токен публичным ключом сервера как симметричным HMAC-секретом и получить статус администратора! В таких случаях govulncheck наглядно демонстрирует, что вызов метода `jwt.Parse` или `jwt.ParseWithClaims` находится в критической зоне риска.

## Решение по шагам

Изучите механику уязвимости Key Confusion в JWT токенах.
Напишите парсер токенов со строгой валидацией алгоритма подписи в Keyfunc.
Проверьте код на защищенность от атак смены алгоритма ('none' или HMAC/RSA).
Подтвердите соответствие лучшим практикам RFC 7519.

## Код решения

**`jwt_secure_parser.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
)

// Безопасный интерфейс парсинга JWT с защитой от Algorithm Confusion
type TokenParser struct {
	expectedAlgorithm string
	hmacSecret        []byte
}

func NewTokenParser(secret []byte) *TokenParser {
	return &TokenParser{
		expectedAlgorithm: "HS256",
		hmacSecret:        secret,
	}
}

// KeyValidationFunc защищает от атак подмены алгоритма (HMAC вместо RSA)
func (p *TokenParser) ValidateKey(algHeader string) ([]byte, error) {
	// КРИТИЧЕСКИ ВАЖНО: Строгая проверка допустимого алгоритма подписи!
	if algHeader != p.expectedAlgorithm {
		return nil, fmt.Errorf("unexpected signing algorithm %q, expected %q (Potential Attack)",
			algHeader, p.expectedAlgorithm)
	}
	return p.hmacSecret, nil
}

func main() {
	parser := NewTokenParser([]byte("production_super_secret_key"))

	// Тест 1: Валидный алгоритм
	key, err := parser.ValidateKey("HS256")
	if err != nil {
		log.Fatalf("Unexpected error: %v", err)
	}
	fmt.Printf("[OK] Valid algorithm accepted. Secret length: %d bytes\n", len(key))

	// Тест 2: Атака Algorithm Confusion (атакующий шлет RS256 или 'none')
	_, err = parser.ValidateKey("none")
	if errors.Is(err, err) && err != nil {
		fmt.Printf("[SECURITY BLOCKED] %v\n", err)
	}
}
```

ℹ️ Защита от Algorithm Confusion при парсинге криптографических токенов

## Под капотом

В уязвимых версиях библиотек функция обратного вызова `keyFunc` слепо возвращала публичный ключ сервера без проверки заголовка `token.Header["alg"]`. Современные версии `golang-jwt/jwt/v5` требуют явной спецификации разрешенных методов подписи (`jwt.WithValidMethods`).

## Подводные камни

Использование устаревшего модуля `github.com/dgrijalva/jwt-go` (заброшен в 2020 году и полон незакрытых CVE). Все проекты обязаны мигрировать на `github.com/golang-jwt/jwt/v5`.

## На собеседовании

Вопрос на собеседовании в Авито: 'В чем суть атаки Key Confusion в JWT и как ее предотвратить в Go?' Ответ: 'Атакующий меняет заголовок alg с RS256 на HS256 и подписывает токен публичным ключом сервера. Если сервер не проверяет alg строго, HMAC валидация сойдется. Защита: строгая проверка алгоритма в keyFunc и использование WithValidMethods'.
