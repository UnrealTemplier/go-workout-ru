# Каверзный кейс: транзитивные зависимости (Transitive Dependencies) и Reachability

## Условие

Смоделируйте ситуацию, когда уязвимость находится не в прямом импорте вашего кода, а в глубокой транзитивной зависимости (библиотека C, вызванная библиотекой B). Покажите, как govulncheck анализирует цепочку вызовов сквозь границы пакетов.

### Исходная формулировка

**[Каверзный кейс — Transitive Dependency]**: Ты не используешь уязвимый пакет напрямую, но его использует одна из твоих зависимостей. Запусти `govulncheck`. Если уязвимая функция не вызывается в твоем графе вызовов, `govulncheck` выдаст предупреждение, но не ошибку. Объясни, почему это безопаснее, чем просто сканировать `go.sum`.

## Теория

В современных проектах на Go до 80-90% кодовой базы составляют транзитивные (косвенные) зависимости. Если сервис импортирует популярный веб-фреймворк или ORM, тот под капотом тянет десятки сторонних модулей. Когда в одном из глубоких транзитивных модулей регистрируется CVE, классический сканер (Dependabot/Snyk) поднимает тревогу: 'В вашем проекте обнаружена Critical CVE!'. Однако фреймворк может использовать этот модуль только для специфического формата данных, который ваше приложение никогда не включает. govulncheck выполняет межмодульный анализ графа вызовов (Inter-procedural Call Graph Analysis): он проверяет, существует ли путь от функции `main()` вашего сервиса через методы фреймворка к конкретной функции уязвимого транзитивного пакета.

## Решение по шагам

Определите цепочку модулей: App -> GatewayPkg -> VulnerableTransitivePkg.
Напишите код, вызывающий безопасный метод GatewayPkg.
Покажите, что уязвимый метод транзитивного пакета не вызывается.
Проанализируйте статус проверки в govulncheck (Unreachable).

## Код решения

**`transitive_reachability.go`**

```go
package main

import (
	"fmt"
	"log"
)

// Имитация транзитивной зависимости 3-го уровня:
// App -> BusinessService -> ThirdPartyLib -> VulnerableLegacyHelper

type VulnerableLegacyHelper struct{}

// SafeUtility вызывается приложением
func (h *VulnerableLegacyHelper) SafeUtility(input string) string {
	return "Clean: " + input
}

// ExploitCVE2024 содержит критическую уязвимость RCE, но НЕ вызывается приложением
func (h *VulnerableLegacyHelper) ExploitCVE2024(cmd string) {
	panic("Unsafe RCE triggered! Should never be reachable.")
}

type BusinessService struct {
	helper VulnerableLegacyHelper
}

func (s *BusinessService) ProcessOrder(id string) string {
	// Вызываем только безопасный метод
	return s.helper.SafeUtility(id)
}

func main() {
	svc := &BusinessService{}
	result := svc.ProcessOrder("ord-7841")

	log.Printf("[Application] Result: %s", result)
	fmt.Println("Call Graph Result: ExploitCVE2024() is NOT reachable. Build deemed secure.")
}
```

ℹ️ Транзитивная зависимость: безопасный путь вызова без активации уязвимого символа

## Под капотом

Алгоритм RTA (Rapid Type Analysis) компилятора Go исследует только реально инстанцированные типы и вызываемые интерфейсные методы. Мертвые ветви транзитивных зависимостей отсекаются, не попадая в срез вызовов.

## Подводные камни

Обновление всей цепочки зависимостей через `go get -u` без тестирования. Обновление транзитивных пакетов может изменить поведение фреймворка и привести к скрытым багам в runtime.

## На собеседовании

Вопрос на собеседовании в Kasperskу: 'В транзитивной зависимости найдена уязвимость, но автор родительской библиотеки задерживает релиз. Как поступить?' Ответ: '1) Проверить через govulncheck, вызывается ли уязвимая функция в нашем приложении. Если нет — риск принят (Accepted Risk); 2) Если вызывается — форсировать безопасную версию транзитивного пакета через директиву `replace` в go.mod'.
