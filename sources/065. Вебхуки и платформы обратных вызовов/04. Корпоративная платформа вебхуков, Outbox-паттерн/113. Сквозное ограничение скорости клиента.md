# Сквозное ограничение скорости клиента (Unified Rate Limiting per Client)

## Условие

Rate limiting per client, не per protocol. Клиент с 1000 RPS лимитом не должен иметь 1000 RPS на REST + 1000 на Connect + 1000 на SSE. Unified quota across protocols.

### Исходная формулировка

**Rate limiting per client, не per protocol.**: Клиент с 1000 RPS лимитом не должен иметь 1000 RPS на REST + 1000 на Connect + 1000 на SSE. Unified quota across protocols.

## Теория

Распространенная архитектурная дыра в безопасности шлюзов: настройка независимых лимитеров скорости на каждый транспортный интерфейс.

### Уязвимость раздельных квот:
Если компания предоставила клиенту тарифный план на **1 000 RPS**, а шлюз настроен так:
- REST Limiter: 1000 RPS
- GraphQL Limiter: 1000 RPS
- Connect-RPC Limiter: 1000 RPS
- Webhooks API Limiter: 1000 RPS
Хитрый клиент может запустить атаку с интенсивностью **4 000 RPS**, распределив трафик по 4 разным протоколам, и ни один лимитер не сработает!

### Единая квота клиента (Unified Client Quota):
1. **Единый идентификатор квоты:** `rate_limit_key = hash(tenant_id)`.
2. **Централизованный токен-бакет:** Все запросы клиента независимо от того, пришли ли они по REST, Connect или SSE, списывают токены из **одного общего баланса**.
3. **Веса операций (Cost-Based Rate Limiting):**
   - Простой REST GET: вес = 1 токен.
   - Тяжелый GraphQL запрос со сложным графом: вес = 5 токенов.
   - Открытие долгоживущей SSE сессии: вес = 10 токенов.

## Решение по шагам

1. Создайте структуру единого менеджера квот `UnifiedClientLimiter`.
2. Реализуйте метод `Allow(tenantID string, cost int) bool`.
3. Смоделируйте конкурентные запросы одного клиента через REST и Connect.
4. Докажите, что суммарная нагрузка не превышает общий лимит.

## Код решения

**`unified_rate_limiter.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

type UnifiedClientLimiter struct {
	mu       sync.Mutex
	limiters map[string]*rate.Limiter
	baseRPS  rate.Limit
	burst    int
}

func NewUnifiedClientLimiter(rps float64, burst int) *UnifiedClientLimiter {
	return &UnifiedClientLimiter{
		limiters: make(map[string]*rate.Limiter),
		baseRPS:  rate.Limit(rps),
		burst:    burst,
	}
}

func (l *UnifiedClientLimiter) Allow(tenantID string, cost int) bool {
	l.mu.Lock()
	lim, exists := l.limiters[tenantID]
	if !exists {
		lim = rate.NewLimiter(l.baseRPS, l.burst)
		l.limiters[tenantID] = lim
	}
	l.mu.Unlock()

	// Списываем N токенов в зависимости от стоимости протокола
	return lim.AllowN(time.Now(), cost)
}

func main() {
	// Единый лимит на клиента: 10 токенов в секунду, максимальный всплеск 10
	limiter := NewUnifiedClientLimiter(10.0, 10)
	tenant := "tenant_mega_shop"

	fmt.Println("=== Тестирование единой квоты клиента (Лимит: 10 токенов) ===")

	// 1. Клиент делает 6 легких REST запросов (cost = 1)
	fmt.Println("\nШаг 1: 6 запросов через REST (вес = 1)")
	for i := 1; i <= 6; i++ {
		ok := limiter.Allow(tenant, 1)
		fmt.Printf("  REST запрос #%d: разрешен = %v\n", i, ok)
	}

	// 2. В эту же секунду клиент делает тяжелый GraphQL запрос (cost = 3)
	fmt.Println("\nШаг 2: 1 тяжелый GraphQL запрос (вес = 3)")
	okGQL := limiter.Allow(tenant, 3)
	fmt.Printf("  GraphQL запрос: разрешен = %v (потрачено суммарно 6 + 3 = 9 токенов)\n", okGQL)

	// 3. Попытка открыть SSE стрим (cost = 5) в ту же секунду
	fmt.Println("\nШаг 3: Попытка открыть SSE поток (вес = 5) при остатке 1 токен")
	okSSE := limiter.Allow(tenant, 5)
	fmt.Printf("  SSE подключение: разрешено = %v (ОТКЛОНЕНО: единая квота исчерпана!)\n", okSSE)
}
```

## Под капотом

В распределенной среде Redis сквозной весовой лимитер реализуется атомарным скриптом на языке Lua:
```lua
local key = KEYS[1]
local cost = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local current = redis.call('GET', key) or capacity
if tonumber(current) >= cost then
    redis.call('DECRBY', key, cost)
    return 1
else
    return 0
end
```
Это исключает сетевые race conditions между параллельными нодами шлюза.

## Подводные камни

1. **Одинаковый вес для всех запросов:** Приравнивать 5-байтный пинг к тяжелому аналитическому GraphQL-запросу несправедливо и приведет к истощению ресурсов базы данных.
2. **Отсутствие заголовка `RateLimit-Remaining`:** Клиенты должны видеть остаток своей глобальной квоты в ответах всех протоколов.

## На собеседовании

**Вопрос:** Как синхронизировать единый лимит между сотнями подов шлюза без сетевых задержек к Redis на каждый HTTP-запрос?

**Ответ:** Применяется алгоритм **Кредитного резервирования (Credit-Based Token Leases)**:
Поды локально списывают токены из локального кэша. Каждые 100 мс под связывается с Redis и «берет в кредит» пачку из 50 токенов для данного клиента. Если клиент неактивен, кредит не запрашивается. Это сокращает количество сетевых обращений к Redis на 95%.
