# Принцип Right Tool for the Job в архитектуре сетевых протоколов

## Условие

Right tool for the job:
* Public API, ресурсы → REST
* Mobile, flexible queries → GraphQL
* Межсервисное → gRPC/Connect
* Real-time server→client → SSE
* Third-party events → Webhooks
* Bidirectional chat → WebSocket

### Исходная формулировка

**Right tool for the job:**
- Public API, ресурсы → REST
- Mobile, flexible queries → GraphQL  
- Межсервисное → gRPC/Connect
- Real-time server→client → SSE
- Third-party events → Webhooks
- Bidirectional chat → WebSocket

## Теория

«Серебряной пули» в сетевых протоколах не существует. Попытка построить всю систему на одном протоколе (например, делать весь бэкенд и уведомления только на WebSockets) приводит к катастрофическим архитектурным перекосам.

### Архитектурный манифест правильного применения протоколов:
1. **REST (JSON over HTTP/1.1 or HTTP/2):**
   - Общепринятый язык интернета.
   - Идеален для публичных CRUD-ресурсов, интеграции с внешними разработчиками, нативного кэширования на CDN (Cloudflare).
2. **GraphQL:**
   - Предотвращает Overfetching (избыточные данные) и Underfetching (десятки запросов для одного экрана).
   - Идеален для комплексных мобильных приложений с нестабильной сетью.
3. **gRPC / Connect RPC:**
   - Высокопроизводительный бинарный транспорт с кодогенерацией.
   - Идеален для внутреннего East-West взаимодействия микросервисов.
4. **Server-Sent Events (SSE):**
   - Однонаправленный стриминг поверх обычного HTTP.
   - Идеален для live-дашбордов, стриминга токенов нейросетей (LLM), биржевых котировок.
5. **Webhooks:**
   - Асинхронный серверный Push.
   - Золотой стандарт B2B-интеграций без удержания сокетов.
6. **WebSockets:**
   - Полнодуплексный низколатентный канал.
   - Идеален для игр, трейдинговых стаканов и двунаправленных мессенджеров.

## Решение по шагам

1. Создайте интерактивный матричный классификатор протоколов.
2. Реализуйте алгоритм выбора на основе входных требований.
3. Продемонстрируйте корректный выбор для шести типовых сценариев.

## Код решения

**`protocol_selector.go`**

```go
package main

import "fmt"

type ProtocolChoice struct {
	UseScenario string
	Protocol    string
	CoreReason  string
}

func GetArchitectureGuidelines() []ProtocolChoice {
	return []ProtocolChoice{
		{
			UseScenario: "Публичное API для сторонних разработчиков (CRUD)",
			Protocol:    "REST / OpenAPI",
			CoreReason:  "Универсальная совместимость, простота отладки, развитая экосистема документации.",
		},
		{
			UseScenario: "Мобильное приложение с гибкой выборкой экранов",
			Protocol:    "GraphQL",
			CoreReason:  "Устранение overfetching, сборка данных с 10 микросервисов за 1 HTTP RTT.",
		},
		{
			UseScenario: "Внутренний обмен между микросервисами компании",
			Protocol:    "gRPC / Connect",
			CoreReason:  "Максимальная скорость, бинарный Protobuf, строгие типизированные контракты.",
		},
		{
			UseScenario: "Стриминг токенов от LLM или ленты новостей",
			Protocol:    "Server-Sent Events (SSE)",
			CoreReason:  "Легковесный HTTP-поток, нативный автореконнект, работа через корпоративные прокси.",
		},
		{
			UseScenario: "Уведомление внешних партнеров о бизнес-событиях",
			Protocol:    "Webhooks",
			CoreReason:  "Асинхронный Push без удержания постоянных TCP-соединений.",
		},
		{
			UseScenario: "Двунаправленный чат или онлайн-игра в реальном времени",
			Protocol:    "WebSockets",
			CoreReason:  "Минимальный оверхед фрейма (2 байта), полнодуплексный обмен в обе стороны.",
		},
	}
}

func main() {
	guidelines := GetArchitectureGuidelines()

	fmt.Println("=== Инженерный манифест выбора протоколов (Right Tool for the Job) ===")
	for i, g := range guidelines {
		fmt.Printf("\n[%d] Задача:      %s\n", i+1, g.UseScenario)
		fmt.Printf("    Протокол:    %s\n", g.Protocol)
		fmt.Printf("    Обоснование: %s\n", g.CoreReason)
	}
}
```

## Под капотом

Осознанный выбор протокола основывается на сетевой модели OSI:
- REST/SSE/Webhooks работают на уровне L7 HTTP семантики (статус-коды, кэширование, заголовки авторизации).
- WebSocket после рукопожатия `101 Switching Protocols` переходит на чистый L4 транспорт поверх TCP со своим микро-фреймингом, теряя семантику HTTP кодов ошибок.

## Подводные камни

1. **Выбор WebSocket для всего подряд:** Поддержание 500 000 постоянных сокетов требует кластера серверов, даже если 95% времени по ним не передается никаких данных.
2. **Использование REST Polling вместо Webhooks:** Опрос каждые 2 секунды быстро положит базу данных при росте числа клиентов.

## На собеседовании

**Вопрос:** Почему BigTech компании не используют GraphQL для межсервисного общения внутри бэкенда?

**Ответ:** GraphQL проектировался для границы Edge/Client-to-Backend. Внутри закрытого кластера парсинг текстовых GraphQL запросов, построение AST-дерева и динамическое разрешение полей создают избыточную нагрузку на CPU. Внутренний трафик оптимизируется статически компилируемым бинарным Protobuf в gRPC, работающим в разы быстрее без накладных расходов на парсинг текста.
