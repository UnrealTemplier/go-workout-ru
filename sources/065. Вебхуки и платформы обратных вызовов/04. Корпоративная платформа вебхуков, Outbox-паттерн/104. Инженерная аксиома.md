# Инженерная аксиома: Запрет синхронной доставки вебхуков

## Условие

Никогда не доставляйте webhooks синхронно. Всегда через background worker queue. Slow endpoint не должен блокировать весь delivery pipeline.

### Исходная формулировка

**Никогда не доставляйте webhooks синхронно.**: Всегда через background worker queue. Slow endpoint не должен блокировать весь delivery pipeline.

## Теория

Главное правило надежности высоконагруженного бэкенда: **Сетевые вызовы во внешние недоверенные системы НИКОГДА не должны выполняться синхронно в контексте основного HTTP-запроса пользователя**.

### Что происходит при синхронной отправке:
1. Покупатель нажимает кнопку «Оплатить заказ».
2. Бэкенд списал деньги и внутри этого же HTTP-хендлера делает:
   `http.Post("https://partner-shop.ru/webhook", payload)`
3. Сервер магазина `partner-shop.ru` подвис на 30 секунд.
4. Покупатель в браузере видит белый экран и крутящийся спиннер 30 секунд!
5. Покупатель нажимает кнопку «Оплатить» еще 5 раз, генерируя повторные транзакции.
6. Воркеры API бэкенда исчерпываются, и платформа ложится целиком!

### Единственно правильный паттерн:
- Основной запрос фиксирует транзакцию в БД и Outbox/Kafka за 2 мс и мгновенно возвращает покупателю `HTTP 200 OK: {"order_id": 123, "status": "paid"}`.
- Доставка вебхука происходит **полностью асинхронно** независимым пулом фоновых воркеров.

## Решение по шагам

1. Реализуйте HTTP-хендлер заказа, использующий асинхронную постановку в очередь.
2. Замерьте время ответа пользователю: оно должно быть строго < 5 мс независимо от задержки вебхука.
3. Продемонстрируйте изоляцию сбоя внешнего эндпоинта от пользователя.

## Код решения

**`async_delivery_rule.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

type AsyncWebhookQueue struct {
	queue chan string
}

func (q *AsyncWebhookQueue) Push(msg string) {
	select {
	case q.queue <- msg:
	default:
		// В реальной системе сброс в Kafka/Outbox
	}
}

// UserOrderHandler обрабатывает покупку пользователя
func UserOrderHandler(q *AsyncWebhookQueue) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// 1. Быстрая бизнес-логика и запись в БД (1-2 мс)
		orderID := "ord_77441"

		// 2. АСИНХРОННАЯ постановка вебхука в очередь
		q.Push(fmt.Sprintf("Event: order %s captured", orderID))

		// 3. Мгновенный ответ пользователю
		w.WriteHeader(http.StatusOK)
		w.Write([]byte(`{"status":"success","order_id":"` + orderID + `"}`))
	}
}

func main() {
	queue := &AsyncWebhookQueue{queue: make(chan string, 100)}

	// Фоновый воркер, доставляющий вебхуки во внешнюю сеть
	go func() {
		for msg := range queue.queue {
			// Имитируем медленный зависший партнерский сервер (500 мс)
			time.Sleep(500 * time.Millisecond)
			fmt.Printf("[BACKGROUND WORKER] Вебхук доставлен партнеру: %s\n", msg)
		}
	}()

	ts := httptest.NewServer(UserOrderHandler(queue))
	defer ts.Close()

	fmt.Println("=== Измерение времени отклика пользовательского API ===")
	start := time.Now()
	resp, _ := http.Post(ts.URL, "application/json", nil)
	resp.Body.Close()
	userLatency := time.Since(start)

	fmt.Printf("Пользователь получил подтверждение покупки за: %v!\n", userLatency.Round(time.Millisecond))
	fmt.Println("Пользователь свободен, а доставка вебхука идет в фоне...")

	time.Sleep(600 * time.Millisecond)
}
```

ℹ️ Мгновенный ответ пользователю и гарантированная изоляция фоновой доставки

## Под капотом

В микросервисной архитектуре разделение критического пути (Hot Critical Path) и побочных эффектов (Side Effects) является базовым принципом масштабируемости. Путь пользователя (User Request-Response) оптимизируется на минимальную задержку (p99 < 50ms), а все интеграционные нотификации выносятся в асинхронную шину событий.

## Подводные камни

1. **Запуск через `go deliver()` без очередей:** При падении пода все недоставленные горутины бесследно испарятся. Очередь обязана быть персистентной (Kafka/Outbox).
2. **Передача отменяемого `r.Context()` в фоновую горутину:** Когда HTTP-хендлер завершается, контекст запроса отменяется, прерывая фоновую доставку. Используйте `context.WithoutCancel(ctx)` в Go 1.21+.

## На собеседовании

**Вопрос:** Как гарантировать, что асинхронный вебхук не потеряется при внезапном сбое питания ноды?

**Ответ:** Применяется паттерн **Transactional Outbox**. Запись о необходимости отправки вебхука коммитится в реляционную базу данных в той же ACID-транзакции, что и бизнес-изменение. Даже если сервер мгновенно обесточится, при перезапуске фоновый демон вычитает строку из Outbox и выполнит доставку.
