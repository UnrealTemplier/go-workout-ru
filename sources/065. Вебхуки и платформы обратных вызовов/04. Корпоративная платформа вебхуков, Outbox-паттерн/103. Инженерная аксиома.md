# Инженерная аксиома: Экспоненциальный бэкофф с джиттером обязателен

## Условие

Exponential backoff + jitter — не опция, а must. Без jitter массовый сбой у крупного клиента DoS-нет его сервера retries от всех ваших webhook'ов одновременно.

### Исходная формулировка

**Exponential backoff + jitter — не опция, а must.**: Без jitter массовый сбой у крупного клиента DoS-нет его сервера retries от всех ваших webhook'ов одновременно.

## Теория

Детерминированные ретраи (например, фиксированная пауза ровно 5 секунд) — грубейшая инженерная ошибка в распределенных системах.

Если клиентская система кратковременно отключилась, 10 000 вебхуков накопятся в очереди. В момент восстановления все эти 10 000 запросов ударят по клиентскому бэкенду с точностью до миллисекунды, мгновенно вернув его в состояние нокдауна.

### Обязательные компоненты надежного бэкоффа:
1. **Экспоненциальное замедление:** Интервалы растут: 1с, 2с, 4с, 8с, 16с...
2. **Верхняя граница (Cap):** Ограничение максимальной паузы (например, не более 1 часа).
3. **Full Jitter:** Случайное рассеивание интервала \(\text{rand}(0, delay)\), ликвидирующее резонансные всплески нагрузки.

## Решение по шагам

1. Напишите эталонный калькулятор Full Jitter на Go.
2. Смоделируйте поведение очереди из 5 000 задач при восстановлении упавшего сервиса.
3. Докажите отсутствие пиковых всплесков на графике распределения.

## Код решения

**`must_jitter.go`**

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

// CalculateMandatoryBackoff вычисляет надежную задержку с Full Jitter
func CalculateMandatoryBackoff(attempt int, base, maxCap time.Duration) time.Duration {
	if attempt < 1 {
		attempt = 1
	}
	// Ограничиваем attempt во избежание переполнения 1 << attempt
	if attempt > 15 {
		attempt = 15
	}

	temp := int64(base) * (1 << attempt)
	if temp > int64(maxCap) {
		temp = int64(maxCap)
	}

	// Full Jitter: равномерный шум от 0 до вычисленного предела
	return time.Duration(rand.Int64N(temp))
}

func main() {
	base := 1 * time.Second
	maxCap := 30 * time.Second

	fmt.Println("=== Обязательный экспоненциальный бэкофф с Full Jitter ===")
	for attempt := 1; attempt <= 5; attempt++ {
		fmt.Printf("Попытка #%d: 5 случайных выборок Full Jitter:\n  ", attempt)
		for i := 0; i < 5; i++ {
			d := CalculateMandatoryBackoff(attempt, base, maxCap)
			fmt.Printf("%v ", d.Round(time.Millisecond))
		}
		fmt.Println()
	}
}
```

## Под капотом

Математическое доказательство эффективности Full Jitter строится на теореме о свертке случайных величин. Детерминированный бэкофф формирует дельта-функцию Дирака \(\delta(t - T)\), вызывая бесконечную спектральную плотность мощности в моменты \(T, 2T, 4T\). Добавление равномерного шума превращает спектр в равномерную константу низкой амплитуды, защищая входящие буферы сокетов клиентов.

## Подводные камни

1. **Джиттер без верхнего предела:** При \(2^{30}\) попытке задержка составит 34 года. Верхний предел (Cap, например 60 минут) обязателен.
2. **Использование отрицательного джиттера:** Случайное вычитание может привести к отрицательной задержке, если не проверять границы.

## На собеседовании

**Вопрос:** Что делать, если сервер клиента в ответе 429 передал заголовок `Retry-After: 120`?

**Ответ:** Заголовок `Retry-After` от клиента имеет наивысший приоритет над локальными алгоритмами бэкоффа! Если клиент явно просит подождать 120 секунд, воркер обязан заснуть на указанное время (с добавлением небольшого джиттера в 1–3 секунды), чтобы не нарушать явный контракт защиты клиентского шлюза.
