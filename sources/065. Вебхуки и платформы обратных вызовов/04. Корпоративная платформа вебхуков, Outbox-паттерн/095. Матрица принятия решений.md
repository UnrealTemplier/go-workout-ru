# Матрица принятия решений: Архитектурные стили API (API Styles Matrix)

## Условие

**Матрица выбора API стилей:**
| Use Case | Стиль |
|----------|-------|
| CRUD ресурсы, public API | REST |
| Flexible queries, mobile clients | GraphQL |
| Межсервисное общение, streaming | gRPC/Connect |
| Browser → backend, type-safe | Connect |
| Много "действий", batch calls | JSON-RPC |
| Event notification third parties | Webhooks |

## Теория

Выбор стиля межсервисного и клиентского API определяет производительность, поддерживаемость и масштабируемость системы на годы вперед.

### Глубокий сравнительный анализ стилей API:

| Стиль API | Транспорт | Контракт / Схема | Производительность | Типичный Use Case |
| :--- | :--- | :--- | :--- | :--- |
| **REST (OpenAPI)** | HTTP/1.1, HTTP/2 | JSON Schema / OpenAPI 3.0 | Средняя (текстовый JSON) | Публичные CRUD API, интеграции, мобильные клиенты |
| **GraphQL** | HTTP POST | GraphQL Schema Language | Ниже среднего (парсинг AST, Overfetching фикс) | Сложные веб-порталы, SPA, агрегация микросервисов для мобилок |
| **gRPC / Connect**| HTTP/2, HTTP/3 | Protocol Buffers (proto3) | Экстремально высокая (бинарная) | HighLoad межсервисное общение (East-West traffic) |
| **JSON-RPC 2.0** | HTTP / WebSocket | Неформальная / JSON-RPC spec| Средняя (батчинг в одном запросе)| Блокчейн-узлы (Ethereum API), сложные RPC-команды |
| **Webhooks** | HTTP POST | JSON / Event Envelope | Асинхронная, высокая | Асинхронные уведомления внешних B2B партнеров |

## Решение по шагам

1. Создайте структуру описания архитектурных характеристик `APIStyleSpec`.
2. Реализуйте справочник стилей и функцию поиска `FindOptimalAPIStyle(requirements string)`.
3. Опишите плюсы и компромиссы каждого подхода.
4. Продемонстрируйте вывод рекомендаций в консоль.

## Под капотом

В микросервисной архитектуре BigTech применяется гибридный подход:
- **North-South Traffic (Клиент \(\to\) API Gateway):** REST / GraphQL / Connect-RPC по HTTPS. Балансировщик расшифровывает TLS и переводит вызовы во внутренний протокол.
- **East-West Traffic (Микросервис \(\leftrightarrow\) Микросервис):** Строго gRPC с protobuf поверх постоянных HTTP/2 соединений с mTLS.
- **Outbound Notifications (Система \(\to\) Внешние клиенты):** Webhook Dispatcher на базе Kafka/Outbox.

## Подводные камни

1. **Использование gRPC напрямую из браузера без шлюза:** Браузерный движок `fetch` не дает прямого доступа к сырым HTTP/2 фреймам. Необходим Envoy с модулем `grpc-web` или использование протокола Connect (`connectrpc.com`).
2. **GraphQL для тяжелых ETL-операций:** GraphQL парсит AST-дерево каждого входящего запроса на CPU, что делает его в 3–5 раз медленнее чистого gRPC на больших объемах данных.

## На собеседовании

**Вопрос:** В чем преимущества Connect RPC перед классическим gRPC от Google?

**Ответ:** Connect RPC полностью совместим со спецификацией gRPC, но поддерживает тройной протокол:
1. Классический gRPC по HTTP/2.
2. gRPC-Web для старых браузеров.
3. Простой Connect-протокол: стандартный HTTP POST с JSON-телом, который можно вызывать прямо из `cURL` без специальных утилит вроде `grpcurl`! При этом сохраняется строгая кодогенерация из `.proto` файлов.
