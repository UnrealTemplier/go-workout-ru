# Бюджеты производительности и профилирование ресурсов (Performance Budgets per Protocol)

## Условие

Performance budgets per protocol. SSE connection overhead ~10KB memory, WebSocket ~20KB, REST request ~1KB. При 1M concurrent connections это разница в 10GB vs 20GB vs 1GB.

### Исходная формулировка

**Performance budgets per protocol.**: SSE connection overhead ~10KB memory, WebSocket ~20KB, REST request ~1KB. При 1M concurrent connections это разница в 10GB vs 20GB vs 1GB.

## Теория

При проектировании инфраструктуры масштаба 1 000 000 одновременных пользователей (1M Concurrency) архитектурный выбор протокола напрямую определяет счет за облачную инфраструктуру и количество серверов в дата-центре.

### Математика памяти на 1 000 000 одновременных соединений:

1. **REST / Stateless HTTP:**
   - Соединения закрываются сразу после ответа (Keep-Alive пул ~1 000 сокетов).
   - Нагрузка на память: **~1 ГБ RAM** на весь кластер воркеров.
2. **Server-Sent Events (SSE):**
   - 1 000 000 открытых постоянных TCP-сокетов.
   - Память буферов сокета ядра Linux + начальный стек горутины Go (~2 КБ) + буферы `net/http`: **~10 КБ на соединение**.
   - Суммарное потребление памяти: **~10 ГБ RAM**.
3. **WebSockets:**
   - 1 000 000 открытых дуплексных TCP-сокетов.
   - Двойные буферы чтения/записи (Read/Write Buffers по 4–8 КБ) + состояние сессии + стек 2 горутин (ридер и райтер): **~20 КБ на соединение**.
   - Суммарное потребление памяти: **~20 ГБ RAM**.

### Системный тюнинг ОС Linux для 1M соединений:
- `fs.file-max = 2097152` (лимит файловых дескрипторов ядра).
- `net.ipv4.ip_local_port_range = 1024 65535` (диапазон исходящих портов).
- `net.core.somaxconn = 65535` (глубина очереди syn-backlog).

## Решение по шагам

1. Создайте калькулятор бюджетов производительности `ProtocolBudgetCalculator`.
2. Реализуйте математический расчет памяти, количества серверов и сетевого стека для масштабов от 10k до 1M соединений.
3. Продемонстрируйте сравнительную таблицу бюджетов ресурсов.

## Код решения

**`performance_budgets.go`**

```go
package main

import (
	"fmt"
)

type ProtocolBudget struct {
	Protocol           string
	MemoryPerConnKB    float64
	TotalMemoryGB_1M   float64
	RecommendedServers int // Серверы с 16 GB RAM (с запасом 50% под ОС и пики)
	ArchitectureNotes  string
}

func CalculatePerformanceBudgets() []ProtocolBudget {
	const scale = 1_000_000 // 1 миллион пользователей

	// 1. REST: сокеты не удерживаются, только активные воркеры
	restMemPerReq := 1.0 // ~1 КБ
	restTotalGB := (50_000 * restMemPerReq) / (1024 * 1024) // При 50k одновременных вызовов
	restServers := 2

	// 2. SSE: 1 сокет, 1 горутина, read-only kernel buffer
	sseMemPerConn := 10.0 // 10 КБ
	sseTotalGB := (float64(scale) * sseMemPerConn) / (1024 * 1024)
	sseServers := int(sseTotalGB/8.0) + 1 // ~8 GB полезной памяти на ноду 16 GB

	// 3. WebSocket: 1 сокет, 2 горутины (read/write), дуплексные буферы
	wsMemPerConn := 20.0 // 20 КБ
	wsTotalGB := (float64(scale) * wsMemPerConn) / (1024 * 1024)
	wsServers := int(wsTotalGB/8.0) + 1

	return []ProtocolBudget{
		{
			Protocol:           "REST API (Stateless)",
			MemoryPerConnKB:    restMemPerReq,
			TotalMemoryGB_1M:   restTotalGB,
			RecommendedServers: restServers,
			ArchitectureNotes:  "Stateless вызовы. Минимальный футпринт памяти. Высокая масштабируемость.",
		},
		{
			Protocol:           "Server-Sent Events (SSE)",
			MemoryPerConnKB:    sseMemPerConn,
			TotalMemoryGB_1M:   sseTotalGB,
			RecommendedServers: sseServers,
			ArchitectureNotes:  "1 горутина на сокет. Идеален для push. Память уходит в буфер ядра и стек.",
		},
		{
			Protocol:           "WebSockets (Full-Duplex)",
			MemoryPerConnKB:    wsMemPerConn,
			TotalMemoryGB_1M:   wsTotalGB,
			RecommendedServers: wsServers,
			ArchitectureNotes:  "2 горутины (ридер/райтер). Полнодуплексные буферы. Требует кластер нод.",
		},
	}
}

func main() {
	budgets := CalculatePerformanceBudgets()

	fmt.Println("=== Бюджеты производительности протоколов на 1 000 000 соединений (1M Scale) ===")
	fmt.Printf("%-24s | %-12s | %-12s | %-12s\n",
		"Протокол", "Память/Сокет", "RAM на 1M", "Серверы (16G)")
	fmt.Println("----------------------------------------------------------------------")

	for _, b := range budgets {
		fmt.Printf("%-24s | %-9.1f KB | %-9.2f GB | %-12d нод\n",
			b.Protocol, b.MemoryPerConnKB, b.TotalMemoryGB_1M, b.RecommendedServers)
	}

	fmt.Println("\nРекомендация системного инженера:")
	fmt.Println("Для 1M пользователей переход с WebSockets на SSE экономит ~10 ГБ оперативной памяти ядра,")
	fmt.Println("сокращая требуемое количество серверов ровно в 2 раза!")
}
```

## Под капотом

Как уменьшить потребление памяти до 1 КБ на сокет в WebSocket/SSE?
В Go стандартный `net/http` выделяет буферы фиксированного размера (4 КБ `bufio.Reader` + 4 КБ `bufio.Writer`).
Библиотеки уровня `gobwas/ws` или фреймворки `gnet` используют **Zero-Copy с динамическими слайсами памяти**. Буферы выделяются только в момент прихода данных из системного `epoll`, снижая пассивное потребление памяти сокета с 20 КБ до 1.5 КБ, что позволяет удерживать 1 миллион соединений на одной ноде с 4 ГБ RAM!

## Подводные камни

1. **Забыть поднять `ulimit -n` в операционной системе:** По умолчанию лимит открытых файлов в Linux равен 1024. При 1025-м подключении сервер упадет с ошибкой `accept: too many open files`.
2. **Неконтролируемый рост размера стека горутин:** Если горутина обработчика сокета вызывает глубокую цепочку функций с аллокациями на стеке, стек горутины расширится с 2 КБ до 64 КБ и не сожмется обратно, вызвав OOM кластера.

## На собеседовании

**Вопрос:** Как протестировать сервер на способность удерживать 1 000 000 соединений (C1000k Problem) на одном нагрузочном генераторе, если максимальное количество локальных портов ограничено 65 535?

**Ответ:** Кортеж TCP-соединения определяется 4 параметрами: `(SrcIP, SrcPort, DstIP, DstPort)`.
Чтобы обойти лимит 65 535 портов:
1. На серверной машине вешается несколько IP-алиасов на сетевой интерфейс (`eth0:1 10.0.0.1`, `eth0:2 10.0.0.2`... до 20 IP).
2. Либо на клиентской машине-генераторе поднимается 20 виртуальных IP-адресов.
3. \(20\text{ IP} \times 50\,000\text{ портов} = 1\,000\,000\) уникальных 4-кортежей TCP, позволяя одному хосту открыть миллион одновременных сокетов к серверу!
