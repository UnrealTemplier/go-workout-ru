# Инфраструктурная стоимость и профиль ресурсов (Cost & Resource Comparison)

## Условие

**Cost comparison:**
* Webhooks: outbound HTTP calls, cheap per delivery
* SSE: persistent connection, требует connection tracking
* WebSocket: persistent, bidirectional, более сложный state
SSE/WebSocket требуют больше server resources per client.

## Теория

При проектировании архитектуры на миллионы пользователей финансовый директор и техлид обязаны оценивать совокупную стоимость владения инфраструктурой (**Total Cost of Ownership, TCO**):
1. **Стоимость вычислений (Compute & Memory):** Сколько подов/памяти нужно для удержания соединений?
2. **Стоимость сетевого трафика (Cloud Egress & NAT Gateway):** В AWS/GCP исходящий трафик стоит $0.05–$0.09 за ГБ, а обработка в NAT Gateway — $0.045 за ГБ.

### Карта потребления ресурсов на 100 000 одновременных пользователей:

| Технология | Постоянные соединения | Потребление RAM сервера | Сложность балансировки | Затраты на Egress трафик |
| :--- | :--- | :--- | :--- | :--- |
| **Webhooks** | 0 (только в момент отправки) | Низкое (Worker Pool на 200 горутин ~50 МБ) | Простая (Stateless HTTP) | Оплата только за реальные полезные события |
| **SSE** | 100 000 открытых HTTP сокетов | Среднее (~300–600 МБ под сокеты и горутины) | Средняя (Sticky Sessions не нужны, но сокет долгий) | Минимальные heartbeat пинги (`:\n\n`) |
| **WebSocket** | 100 000 TCP сессий | Высокое (~1–2 ГБ RAM + распределенный Redis Pub/Sub) | Высокая (L4/L7 sticky, drain при деплоях) | Постоянный трафик ping/pong каждые 30 сек |

## Решение по шагам

1. Создайте калькулятор ресурсов `InfrastructureCostCalculator`.
2. Смоделируйте затраты RAM, процессорных ядер и стоимости облака для 100 000 клиентов.
3. Проанализируйте финансовую выгоду вебхуков для редких событий.
4. Выведите сравнительную таблицу затрат.

## Код решения

**`cost_calculator.go`**

```go
package main

import (
	"fmt"
)

type ArchitectureCost struct {
	TechName          string
	RequiredNodes     int     // Количество серверов (например, 4 vCPU, 8 GB RAM)
	ServerCostPerMonth float64 // $50 за ноду
	EgressGBPerMonth  float64 // Исходящий трафик в ГБ
	BandwidthCost     float64 // $0.08 за ГБ
	TotalMonthlyCost  float64
}

func CalculateCosts(activeUsers int, eventsPerUserPerDay int) []ArchitectureCost {
	// Условие: 100 000 пользователей, в среднем 5 событий в день на пользователя.
	totalEventsMonth := float64(activeUsers * eventsPerUserPerDay * 30)

	// 1. Webhooks: серверов нужно мало (воркеры справляются пулом), трафик строго полезный
	whNodes := 2
	whEgressGB := (totalEventsMonth * 1024) / (1024 * 1024 * 1024) // 1 КБ на вебхук
	whServerCost := float64(whNodes) * 50.0
	whBandwidthCost := whEgressGB * 0.08

	// 2. Server-Sent Events (SSE): нужно удерживать 100k постоянных соединений
	// 1 сервер держит безопасно ~30k соединений -> нужно 4 сервера
	sseNodes := 4
	// Трафик: полезные события + heartbeat пинг каждые 45 сек (30 байт)
	heartbeatsMonth := float64(activeUsers) * (86400 / 45) * 30
	sseEgressGB := ((totalEventsMonth * 1024) + (heartbeatsMonth * 30)) / (1024 * 1024 * 1024)
	sseServerCost := float64(sseNodes) * 50.0
	sseBandwidthCost := sseEgressGB * 0.08

	// 3. WebSocket: 100k соединений, дуплексный state, частый ping/pong (каждые 20 сек)
	wsNodes := 5
	wsPingsMonth := float64(activeUsers) * (86400 / 20) * 30
	wsEgressGB := ((totalEventsMonth * 1024) + (wsPingsMonth * 40)) / (1024 * 1024 * 1024)
	wsServerCost := float64(wsNodes) * 50.0
	wsBandwidthCost := wsEgressGB * 0.08

	return []ArchitectureCost{
		{
			TechName:          "Webhooks Platform",
			RequiredNodes:     whNodes,
			ServerCostPerMonth: whServerCost,
			EgressGBPerMonth:  whEgressGB,
			BandwidthCost:     whBandwidthCost,
			TotalMonthlyCost:  whServerCost + whBandwidthCost,
		},
		{
			TechName:          "Server-Sent Events (SSE)",
			RequiredNodes:     sseNodes,
			ServerCostPerMonth: sseServerCost,
			EgressGBPerMonth:  sseEgressGB,
			BandwidthCost:     sseBandwidthCost,
			TotalMonthlyCost:  sseServerCost + sseBandwidthCost,
		},
		{
			TechName:          "WebSockets Cluster",
			RequiredNodes:     wsNodes,
			ServerCostPerMonth: wsServerCost,
			EgressGBPerMonth:  wsEgressGB,
			BandwidthCost:     wsBandwidthCost,
			TotalMonthlyCost:  wsServerCost + wsBandwidthCost,
		},
	}
}

func main() {
	costs := CalculateCosts(100000, 5)

	fmt.Println("=== Финансовый и инфраструктурный расчет стоимости (100k клиентов, 15M событий/мес) ===")
	fmt.Printf("%-24s | %-6s | %-12s | %-12s | %-12s\n",
		"Технология", "Нод", "Серверы ($)", "Трафик ($)", "ИТОГО в месяц")
	fmt.Println("-------------------------------------------------------------------------------")

	for _, c := range costs {
		fmt.Printf("%-24s | %-6d | $%-11.2f | $%-11.2f | $%-11.2f\n",
			c.TechName, c.RequiredNodes, c.ServerCostPerMonth, c.BandwidthCost, c.TotalMonthlyCost)
	}
}
```

## Под капотом

В облачных инфраструктурах (AWS EKS) развертывание 100 000 долгоживущих WebSocket сессий сталкивается со сложностью Rolling Update деплоев. При деплое нового релиза пода все 100k клиентов одновременно переподключаются (Reconnection Storm), вызывая 100-кратный всплеск нагрузки на CPU и TLS Termination шлюзы. В вебхуках воркеры stateless: при деплое они штатно завершают отправку текущих задач (`Graceful Shutdown`) за пару секунд без всплесков.

## Подводные камни

1. **Недооценка стоимости NAT Gateway в Cloud:** Передача терабайт вебхуков через дефолтный AWS NAT Gateway стоит дополнительных денег ($0.045 за ГБ). Направляйте публичный трафик через дешевые прямые Internet Gateway интерфейсы нод.
2. **Heartbeat-трафик в мобильных сетях:** Слишком частый пинг в WebSocket (например, каждые 5 секунд) не дает радиомодулю мобильного телефона перейти в спящий режим, разряжая батарею пользователя за пару часов.

## На собеседовании

**Вопрос:** Как минимизировать затраты на поддержание 1 000 000 открытых SSE-соединений в компании уровня Wildberries или Ozon?

**Ответ:** 
1. Использовать легковесные шлюзы на Go/Rust с кастомным сетевым стеком на базе `epoll/kqueue` (фреймворки `gnet` или `cloudwego/netpoll`), где на 1 открытый сокет тратится менее 1 КБ памяти (вместо стандартных 4–8 КБ в `net/http`).
2. Увеличить интервал heartbeat до 45–60 секунд.
3. Размещать SSE-шлюзы на Edge-нодах (CDN/Anycast) максимально близко к пользователям.
