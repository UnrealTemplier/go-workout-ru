# Матрица принятия решений: Сравнение Real-time технологий

## Условие

**Матрица выбора real-time технологий:**
| Use Case | Технология |
|----------|-----------|
| Server→Client updates, auto-reconnect нужен | SSE |
| Bidirectional чат, игры | WebSocket |
| Streaming LLM tokens | SSE или Connect streaming |
| Server→Client, corporate proxies | SSE |
| Bidirectional, binary data | WebSocket |
| Server→Client с multiplexing (HTTP/2) | SSE over HTTP/2 |

## Теория

При проектировании современных сервисов реального времени архитекторы часто ошибочно выбирают WebSocket «по привычке», сталкиваясь затем с проблемами масштабирования, балансировки нагрузки и корпоративных файрволов.

### Сравнительный анализ архитектур Real-Time:

| Критерий | Webhooks | Server-Sent Events (SSE) | WebSockets | gRPC Streaming |
| :--- | :--- | :--- | :--- | :--- |
| **Инициатор** | Сервер (Push к клиенту) | Клиент (Persistent GET) | Клиент (HTTP Upgrade) | Клиент (HTTP/2) |
| **Направление** | Однонаправленное (S \(\to\) C) | Однонаправленное (S \(\to\) C) | Полнодуплексное (C \(\leftrightarrow\) S) | Дуплексное (C \(\leftrightarrow\) S) |
| **Транспорт** | Стандартный HTTP POST | Текстовый HTTP/1.1 или HTTP/2 | Бинарный/текстовый фрейминг TCP | HTTP/2 Streams (Protobuf) |
| **Корпоративные прокси** | 100% совместимо | 100% (стандартный HTTP) | Часто блокируется DPI/прокси | Требует поддержки HTTP/2 gRPC |
| **Авто-переподключение** | Ретраи диспетчера | Встроено в браузер (`EventSource`)| Ручная реализация в JS/Go | Встроено в клиент gRPC |
| **Формат данных** | JSON / XML | UTF-8 текст (`text/event-stream`)| Текст / Произвольный Binary | Строго типизированный Protobuf |
| **Лучшее применение** | Third-party интеграции B2B | Стриминг LLM, дашборды, уведомления | Онлайн-игры, трейдинг, чаты | Высоконагруженный микросервисный бэкенд |

## Решение по шагам

1. Создайте универсальную модель классификатора потребностей проекта `RealtimeRequirements`.
2. Напишите функцию экспертной оценки `RecommendRealtimeTech(req RealtimeRequirements) string`.
3. Опишите правила ветвления логики выбора технологии.
4. Протестируйте сценарии: LLM генерация, онлайн-игра, B2B платежи, внутренний микросервис.

## Код решения

**`tech_matrix.go`**

```go
package main

import (
	"fmt"
)

type RealtimeRequirements struct {
	IsBidirectional   bool // Требуется ли частый обмен в обе стороны
	IsBinaryData      bool // Передаются ли сырые байты/аудио/видео
	IsThirdPartyB2B   bool // Интеграция со сторонними внешними серверами
	NeedsAutoReconnect bool // Критично ли встроенное восстановление сессии
	IsCorporateNetwork bool // Работа через строгие корпоративные прокси
	IsLLMStreaming     bool // Стриминг токенов ИИ
}

func RecommendRealtimeTech(r RealtimeRequirements) (string, string) {
	if r.IsThirdPartyB2B {
		return "Webhooks", "Асинхронные HTTP POST вызовы: не требуют постоянных сокетов, идеальны для межсистемных B2B интеграций."
	}

	if r.IsBidirectional || r.IsBinaryData {
		return "WebSockets", "Полнодуплексный бинарный протокол с минимальным оверхедом фреймов (2-10 байт). Оптимально для игр и сокетов."
	}

	if r.IsLLMStreaming || (r.NeedsAutoReconnect && !r.IsBidirectional) {
		if r.IsCorporateNetwork {
			return "SSE (Server-Sent Events)", "Текстовый поток по HTTP/1.1 или HTTP/2. Нативно поддерживается браузерами, проходит любые корпоративные прокси."
		}
		return "SSE over HTTP/2", "Мультиплексирование сотен стримов в едином TCP-соединении, встроенный Last-Event-ID и нулевые накладные расходы."
	}

	return "gRPC Streaming", "Двунаправленный бинарный HTTP/2 транспорт для высокопроизводительного межсервисного взаимодействия."
}

func main() {
	scenarios := []struct {
		title string
		req   RealtimeRequirements
	}{
		{
			title: "Стриминг ответов нейросети (ChatGPT / YandexGPT)",
			req:   RealtimeRequirements{IsLLMStreaming: true, NeedsAutoReconnect: true, IsCorporateNetwork: true},
		},
		{
			title: "Мультиплеерный экшен и шутеры в браузере",
			req:   RealtimeRequirements{IsBidirectional: true, IsBinaryData: true},
		},
		{
			title: "Уведомление интернет-магазина об успешной оплате в банке",
			req:   RealtimeRequirements{IsThirdPartyB2B: true},
		},
		{
			title: "Финансовый дашборд котировок внутри корпоративного интранета",
			req:   RealtimeRequirements{NeedsAutoReconnect: true, IsCorporateNetwork: true},
		},
	}

	fmt.Println("=== Экспертная матрица выбора Real-Time технологий в Go ===")
	for i, sc := range scenarios {
		tech, reason := RecommendRealtimeTech(sc.req)
		fmt.Printf("\n[%d] Сценарий: %s\n", i+1, sc.title)
		fmt.Printf("    -> Рекомендация: %s\n", tech)
		fmt.Printf("    -> Обоснование:   %s\n", reason)
	}
}
```

ℹ️ Результат работы матрицы выбора технологий

## Под капотом

Почему SSE через HTTP/2 превосходит WebSocket для однонаправленных потоков?
В WebSocket каждое соединение требует отдельного TCP-сокета со своим буфером ядра (от 4 до 64 КБ). При 10 000 клиентах это сотни мегабайт памяти сокетов ядра ОС.
В HTTP/2 протокол SSE мультиплексирует десятки независимых потоков данных (Streams) поверх **одного** TCP-соединения, кардинально снижая потребление системных ресурсов сервера.

## Подводные камни

1. **Использование WebSockets для простых push-уведомлений:** WebSocket требует поддержания heartbeat (Ping/Pong), сложной балансировки на L7 прокси и ручного кода реконнекта на фронтенде. Для unidirectional push SSE проще и надежнее.
2. **Лимит HTTP/1.1 соединений в браузере:** В Chrome/Firefox действует лимит в 6 одновременных SSE соединений на один домен по протоколу HTTP/1.1. Для SSE обязателен переход на HTTP/2.

## На собеседовании

**Вопрос:** Почему для стриминга токенов больших языковых моделей (LLM, OpenAI API) был выбран SSE, а не WebSocket?

**Ответ:** 
1. **Простота протокола:** Генерация текста — строго однонаправленный процесс (\(Server \to Client\)). Дуплексность WebSocket избыточна.
2. **Инфраструктурная прозрачность:** SSE передается как стандартный `HTTP 200 OK` с `Content-Type: text/event-stream`. Он без проблем кэшируется, маршрутизируется API Gateway (Kong, Envoy) и не требует настроек `Upgrade` заголовков.
3. **Нативный EventSource:** Браузерный JS API автоматически восстанавливает соединение при разрывах и передает `Last-Event-ID` для досылки непрочитанных токенов.
