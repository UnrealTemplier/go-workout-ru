# Инженерная аксиома: Управление очередью мертвых сообщений (DLQ Lifecycle)

## Условие

Dead letter queue и manual retry. После N failures отключайте endpoint и алертите клиента. Дайте ему UI для просмотра failed deliveries и manual retry.

### Исходная формулировка

**Dead letter queue и manual retry.**: После N failures отключайте endpoint и алертите клиента. Дайте ему UI для просмотра failed deliveries и manual retry.

## Теория

Очередь мертвых сообщений (DLQ) — это не просто «корзина для мусора», а критически важный инструмент обеспечения прозрачности и самообслуживания (Self-Service) клиентов:

### Жизненный цикл инцидента доставки вебхука:
1. **Автоматическая фаза:** 5–10 попыток доставки в течение 24 часов с экспоненциальным бэкоффом и джиттером.
2. **Эскалация в DLQ:**
   - Задача маркируется статусом `EXHAUSTED`.
   - Если 100% доставок на эндпоинт падают непрерывно в течение 24 часов, эндпоинт переводится в режим `DEGRADED` или `PAUSED`.
3. **Оповещение разработчиков клиента:**
   - Автоматический email / Telegram-алерт техническому контакту с ссылкой на лог ошибки и HTTP-дамп.
4. **Инструменты самообслуживания в Dashboard:**
   - Просмотр точного тела запроса и ответа сервера клиента.
   - Кнопка **«Send Test Webhook»** (Ping).
   - Кнопка **«Retry Failed Webhook»** (ручной перезапуск).

## Решение по шагам

1. Реализуйте конечный автомат состояний вебхука (`Pending` -> `Retrying` -> `Exhausted` -> `Replayed`).
2. Напишите сервис сбора статистики здоровья эндпоинтов.
3. Продемонстрируйте сценарий ручной повторной доставки из DLQ.

## Код решения

**`dlq_lifecycle.go`**

```go
package main

import (
	"fmt"
	"time"
)

type DeliveryState string

const (
	StatePending   DeliveryState = "PENDING"
	StateRetrying  DeliveryState = "RETRYING"
	StateExhausted DeliveryState = "EXHAUSTED" // В очереди DLQ
	StateReplayed  DeliveryState = "REPLAYED"  // Восстановлен вручную
)

type WebhookIncident struct {
	EventID    string
	EndpointID string
	State      DeliveryState
	Failures   int
	LastCode   int
	LastError  string
	MovedToDLQ time.Time
}

type IncidentManager struct {
	incidents map[string]*WebhookIncident
}

func (m *IncidentManager) FailDelivery(eventID, endpointID string, code int, errText string) {
	inc, exists := m.incidents[eventID]
	if !exists {
		inc = &WebhookIncident{EventID: eventID, EndpointID: endpointID, State: StateRetrying}
		m.incidents[eventID] = inc
	}

	inc.Failures++
	inc.LastCode = code
	inc.LastError = errText

	if inc.Failures >= 3 {
		inc.State = StateExhausted
		inc.MovedToDLQ = time.Now()
		fmt.Printf("[INCIDENT ESCALATED] Событие %s перемещено в DLQ! (Сбоев: %d, Ошибка: %s)\n",
			eventID, inc.Failures, errText)
	}
}

func (m *IncidentManager) CustomerManualRetry(eventID string) bool {
	inc, exists := m.incidents[eventID]
	if !exists || inc.State != StateExhausted {
		return false
	}
	inc.State = StateReplayed
	fmt.Printf("[CUSTOMER RETRY SUCCESS] Клиент перезапустил событие %s из Dashboard! Возврат в очередь.\n", eventID)
	return true
}

func main() {
	mgr := IncidentManager{incidents: make(map[string]*WebhookIncident)}

	evtID := "evt_sub_fail_441"
	endID := "ep_client_shop"

	fmt.Println("=== Симуляция перехода жизненного цикла в DLQ ===")
	mgr.FailDelivery(evtID, endID, 500, "Internal Server Error")
	mgr.FailDelivery(evtID, endID, 502, "Bad Gateway")
	mgr.FailDelivery(evtID, endID, 504, "Gateway Timeout")

	// Клиент починил баг и нажал кнопку в UI
	fmt.Println("\n=== Действие клиента в личном кабинете ===")
	mgr.CustomerManualRetry(evtID)
}
```

## Под капотом

В промышленных системах хранение записей DLQ организуется с партиционированием по `tenant_id` и `date`. Для предотвращения бесконечного роста таблиц устанавливается скользящее окно хранения (Data Retention): записи старше 30 дней архивируются в холодный S3 Glacier или удаляются, о чем клиенты предупреждаются в договоре оферты.

## Подводные камни

1. **Отсутствие метаданных ошибки в DLQ:** Если сохранить только тело вебхука без HTTP-статуса и заголовков ответа клиента, клиент не сможет понять, почему его сервер падал 24 часа назад.
2. **Потеря исходного `event_id` при ручном перезапуске:** При ручном перезапуске ОБЯЗАТЕЛЬНО сохранять исходный `event_id`, чтобы клиентский сервер дедуплицировал его при наличии частичной обработки.

## На собеседовании

**Вопрос:** Как защитить диспетчер вебхуков от злоупотребления кнопкой «Manual Retry All», если клиент решит перезапустить 500 000 зависших вебхуков одновременно?

**Ответ:** Для массового перезапуска из DLQ вводится строгий Rate Limiter на уровне UI/API:
1. Задачи перезапуска направляются в отдельную низкоприоритетную очередь (Low-Priority Batch).
2. Скорость вычитывания из этой очереди ограничивается безопасным лимитом (например, 10–20 RPS на клиента), исключая перегрузку как инфраструктуры платформы, так и бэкенда клиента.
