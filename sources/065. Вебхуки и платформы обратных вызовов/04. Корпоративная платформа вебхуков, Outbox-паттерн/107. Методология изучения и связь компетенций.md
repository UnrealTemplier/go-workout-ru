# Методология изучения и связь компетенций: Блок 18 (Webhooks)

## Условие

**Блок 18 (Webhooks)**: — начните после Блока 13 (AppSec), так как Webhooks напрямую используют HMAC из Блока 10 и защиту от SSRF из Блока 13. Понимание retry/backoff требует знаний о concurrency из Блока 1 (GMP).

## Теория

Проектирование систем доставки вебхуков находится на стыке фундаментальных инженерных дисциплин:
1. **Прикладная безопасность (AppSec):**
   - Криптографические хеш-функции и HMAC-SHA256.
   - Защита сокетов от SSRF и DNS Rebinding на уровне `syscall`.
   - Защита от тайминг-атак по сторонним каналам (`crypto/subtle`).
2. **Модель конкурентности рантайма Go (GMP Runtime):**
   - Управление пулами горутин (Worker Pool) и семафорами.
   - Неблокирующие таймеры и планирование задержек ретраев.
   - Модель памяти Go (Memory Model) и атомики `sync/atomic`.
3. **Распределенные системы (Distributed Systems):**
   - Семантика доставки At-Least-Once и идемпотентность.
   - Предотвращение резонанса Thundering Herd (Full Jitter).
   - Транзакционный паттерн Outbox и брокеры сообщений (Kafka).

Только глубокая синергия этих знаний позволяет создавать отказоустойчивые решения, выдерживающие миллионные нагрузки BigTech.

## Решение по шагам

1. Создайте граф зависимостей инженерных компетенций главы 65.
2. Напишите валидатор архитектурных требований к продакшен-решению вебхуков.
3. Продемонстрируйте автоматическую проверку готовности сервиса к релизу.

```go
package main

import (
	"fmt"
)

type ProductionReadinessCheck struct {
	Component   string
	Requirement string
	Criticality string
	Verified    bool
}

func AuditWebhookPlatformReadiness() []ProductionReadinessCheck {
	return []ProductionReadinessCheck{
		{"AppSec", "Криптографическая подпись HMAC-SHA256 с Timestamp", "P0 (Critical)", true},
		{"AppSec", "Защита сокетов от SSRF / DNS Rebinding в net.Dialer.Control", "P0 (Critical)", true},
		{"AppSec", "Сравнение хешей за константное время (subtle.ConstantTimeCompare)", "P1 (High)", true},
		{"Concurrency", "Worker Pool постоянного размера (Bounded Memory)", "P0 (Critical)", true},
		{"Reliability", "Экспоненциальный бэкофф с обязательным Full Jitter", "P0 (Critical)", true},
		{"Architecture", "Асинхронная доставка через Transactional Outbox / Kafka", "P0 (Critical)", true},
		{"Operations", "Очередь мертвых сообщений (DLQ) и кнопка Manual Retry", "P1 (High)", true},
		{"Observability", "Сквозной W3C Trace-ID и метрики Prometheus", "P1 (High)", true},
	}
}

func main() {
	checklist := AuditWebhookPlatformReadiness()

	fmt.Println("=== Чек-лист готовности платформы вебхуков к продакшену (Production Readiness Review) ===")
	allPassed := true

	for i, item := range checklist {
		status := "✅ ГОТОВО"
		if !item.Verified {
			status = "❌ СБОЙ"
			allPassed = false
		}
		fmt.Printf("[%d] %-12s | %-14s | %-62s | %s\n",
			i+1, item.Component, item.Criticality, item.Requirement, status)
	}

	fmt.Printf("\nИТОГОВЫЙ СТАТУС ПРОВЕРКИ: Готовность к HighLoad проду: %v\n", allPassed)
}
```

## Под капотом

В ведущих технологических компаниях (Яндекс, Ozon, Stripe) перед выводом нового интеграционного сервиса в продакшен проводится обязательная процедура **PRR (Production Readiness Review)**. Команда безопасности и архитектурный комитет проверяют сервис по чеклисту отказоустойчивости, исключая появление сервисов с синхронной блокирующей доставкой или дырами SSRF.

## Подводные камни

1. **Изолированная разработка без учета смежных блоков:** Разработчик, не понимающий работу GMP планировщика, может создать миллион горутин, а разработчик без знаний AppSec оставит сервис беззащитным перед SSRF.
2. **Игнорирование метрик задержки доставки:** Задержка от момента возникновения события до первой попытки отправки обязана быть в пределах SLA (\(p99 < 1s\)).

## На собеседовании

**Вопрос:** Какими тремя главными метриками Prometheus вы будете оценивать здоровье платформы вебхуков на дашборде в Grafana?

**Ответ:** 
1. **Delivery Success Rate (SLO):** Процент успешных доставок с первого раза и итоговый процент успеха после ретраев (\(\ge 99.99\%\)).
2. **Delivery Latency Quantiles (p50, p95, p99):** Время от публикации события во внутренней системе до получения HTTP-ответа от внешнего эндпоинта.
3. **Queue Lag / DLQ Growth Rate:** Скорость накопления неотправленных сообщений в Kafka/Outbox и количество задач, переходящих в статус `EXHAUSTED` в минуту.
