# Очередь мертвых сообщений и ручной перезапуск (Dead Letter Queue & Manual Retry)

## Условие

Если вебхук не доставился после всех попыток, не выкидывай его. Сохрани его в таблицу БД `failed_webhooks` со статусом `exhausted`. Напиши админский эндпоинт, который позволяет нажать кнопку и переотправить протухший вебхук вручную.

### Исходная формулировка

**Dead Letter Queue (DLQ)**: Если вебхук не доставился после всех попыток, не выкидывай его. Сохрани его в таблицу БД `failed_webhooks` со статусом `exhausted`. Напиши админский эндпоинт, который позволяет нажать кнопку и переотправить протухший вебхук вручную.

## Теория

Когда все автоматические попытки доставки (например, 5 ретраев в течение 24 часов) исчерпаны, а клиентский сервер так и не ответил успехом, вебхук не должен бесследно исчезнуть.

### Концепция Dead Letter Queue (DLQ):
1. **Перевод в статус `EXHAUSTED` (Истощено):** Задача извлекается из регулярного диспетчера ретраев и персистится в таблицу `failed_webhooks` (или DLQ Kafka/RabbitMQ).
2. **Сохранение полного контекста сбоя:**
   - URL эндпоинта и ID подписки.
   - Последний HTTP-статус (`500 Internal Server Error`, `504 Gateway Timeout`).
   - Тело последнего ошибочного ответа клиента (диагностика для разработчиков клиента).
   - Тело и подпись исходного события.
3. **Ручной перезапуск (Manual Replay API):**
   - Клиент починил баг на своем бэкенде.
   - Клиент нажимает кнопку «Повторить доставку» в Dashboard или вызывает API:
     `POST /api/v1/webhooks/dead-letter/{id}/retry`.
   - Система сбрасывает счетчик попыток и помещает задачу в приоритетную очередь доставки.

## Решение по шагам

1. Создайте модель `FailedWebhook` со статусом `exhausted` и диагностическими полями.
2. Реализуйте репозиторий DLQ с методами сохранения и повторной активации.
3. Напишите HTTP-эндпоинт для администратора `POST /admin/dlq/{id}/retry`.
4. Продемонстрируйте сценарий исчерпания попыток, помещение в DLQ и успешный ручной перезапуск.

## Код решения

**`dlq_manager.go`**

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type FailedWebhook struct {
	ID             string    `json:"id"`
	SubscriptionID string    `json:"subscription_id"`
	TargetURL      string    `json:"target_url"`
	Payload        string    `json:"payload"`
	AttemptsCount  int       `json:"attempts_count"`
	LastStatusCode int       `json:"last_status_code"`
	LastError      string    `json:"last_error"`
	Status         string    `json:"status"` // "EXHAUSTED", "REPLAYED"
	ExhaustedAt    time.Time `json:"exhausted_at"`
}

type DLQService struct {
	mu      sync.RWMutex
	storage map[string]*FailedWebhook
	requeue chan string // Канал возврата в активный воркер-пул
}

func NewDLQService() *DLQService {
	return &DLQService{
		storage: make(map[string]*FailedWebhook),
		requeue: make(chan string, 100),
	}
}

// MoveToDLQ вызывается, когда все ретраи исчерпаны
func (s *DLQService) MoveToDLQ(w FailedWebhook) {
	s.mu.Lock()
	defer s.mu.Unlock()

	w.Status = "EXHAUSTED"
	w.ExhaustedAt = time.Now()
	s.storage[w.ID] = &w
	fmt.Printf("[DLQ ALERT] Вебхук %s исчерпал все попытки и перемещен в DLQ (Last Code: %d)!\n", w.ID, w.LastStatusCode)
}

// ReplayManual переотправляет зависший вебхук по запросу администратора
func (s *DLQService) ReplayManual(id string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	item, exists := s.storage[id]
	if !exists {
		return errors.New("webhook not found in DLQ")
	}

	if item.Status != "EXHAUSTED" {
		return errors.New("webhook is not in EXHAUSTED state")
	}

	item.Status = "REPLAYED"
	s.requeue <- item.ID
	fmt.Printf("[DLQ REPLAY] Вебхук %s успешно возвращен в очередь доставки администратором!\n", id)
	return nil
}

// Admin API Handler
func AdminDLQHandler(dlq *DLQService) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if r.Method != http.MethodPost {
			http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
			return
		}

		id := r.URL.Query().Get("id")
		if id == "" {
			http.Error(w, "Missing 'id' query param", http.StatusBadRequest)
			return
		}

		err := dlq.ReplayManual(id)
		if err != nil {
			http.Error(w, err.Error(), http.StatusBadRequest)
			return
		}

		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{
			"status":  "requeued",
			"message": fmt.Sprintf("Webhook %s queued for redelivery", id),
		})
	}
}

func main() {
	dlq := NewDLQService()
	ts := httptest.NewServer(AdminDLQHandler(dlq))
	defer ts.Close()

	// 1. Имитируем падение вебхука после 5 попыток
	failedEvt := FailedWebhook{
		ID:             "wh_dead_9001",
		SubscriptionID: "sub_market_88",
		TargetURL:      "https://partner.ru/webhook",
		Payload:        `{"order_id": 9991, "action": "refund"}`,
		AttemptsCount:  5,
		LastStatusCode: 504,
		LastError:      "Gateway Timeout after 5 retries",
	}
	dlq.MoveToDLQ(failedEvt)

	// 2. Администратор нажимает кнопку в UI (POST /admin/dlq/retry?id=wh_dead_9001)
	replayURL := fmt.Sprintf("%s?id=%s", ts.URL, failedEvt.ID)
	resp, err := http.Post(replayURL, "application/json", nil)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	var result map[string]string
	json.NewDecoder(resp.Body).Decode(&result)
	fmt.Printf("HTTP Ответ админского эндпоинта: статус %d | %v\n", resp.StatusCode, result)

	// 3. Проверяем, что задача попала в канал ре-доставки
	requeuedID := <-dlq.requeue
	fmt.Printf("Воркер доставки получил задачу на повторную отправку: %s\n", requeuedID)
}
```

ℹ️ Результат работы DLQ и ручного перезапуска

## Под капотом

В распределенных брокерах (AWS SQS, RabbitMQ) DLQ реализуется как отдельная изолированная очередь. Когда атрибут `ApproximateReceiveCount` превышает `maxReceiveCount`, брокер сообщений атомарно перемещает сообщение из основной очереди в `dead-letter-queue` без участия приложения. Для переотправки используются инструменты Redrive (например, SQS StartMessageMoveTask), которые пачками возвращают сообщения в исходную очередь.

## Подводные камни

1. **Бесконечный цикл ошибок в DLQ (Poison Pill):** Если вебхук содержит невалидный JSON, ручной перезапуск снова упадет с ошибкой и вернется в DLQ. Для таких сообщений необходимо предоставить в UI возможность редактирования эндпоинта или отмены.
2. **Отсутствие алертов на рост DLQ:** Если упал крупный банк-эквайер, DLQ может вырасти до 100 000 сообщений за час. Без алерта в Prometheus/PagerDuty инженеры узнают о проблеме только от разгневанных пользователей.

## На собеседовании

**Вопрос:** Как реализовать массовый повтор сообщений (Bulk DLQ Replay) для 100 000 событий без повторного Thundering Herd на клиентский сервер?

**Ответ:** 
1. При запуске массового перезапуска задачи не отправляются в регулярную очередь с высоким приоритетом.
2. Они направляются в специальную **Low-Priority Batch Queue**.
3. Воркеры обрабатывают эту очередь с жестким лимитом скорости (например, 10 RPS на клиента), чтобы клиентский бэкенд успевал обрабатывать исторические события без риска повторного падения.
