# Архитектурное сравнение: Webhooks vs Short/Long Polling vs SSE

## Условие

**Webhooks vs Polling vs SSE:**
* Webhooks: server-initiated, требует public endpoint у клиента
* Polling: simple, но wasteful
* SSE: client-initiated persistent connection
Используйте webhooks для third-party integrations, SSE для own-client real-time.

## Теория

Выбор между Webhooks, Polling и SSE зависит от сетевой топологии участников обмена:

### Топологические ограничения участников:
1. **Проблема NAT и серых IP (NAT Traversal):**
   - Браузеры пользователей, мобильные телефоны и офисные компьютеры находятся за NAT/файрволами. У них **нет белого публичного IP-адреса**.
   - Сервер платформы **физически не может** отправить им входящий HTTP POST (Webhook)!
   - Для них единственное решение — соединение, инициированное клиентом: **Short Polling**, **Long Polling** или **SSE**.
2. **B2B-интеграции (Сервер \(\leftrightarrow\) Сервер):**
   - У партнера (интернет-магазина) есть собственный сервер с белым IP или доменом (`https://shop.ru/webhook`).
   - Использовать Polling со стороны магазина (запрашивать статус платежа каждые 2 секунды) — расточительство ресурсов обоих серверов.
   - Здесь оптимальны **Webhooks**: банк отправляет ровно один запрос в момент завершения транзакции.

### Анализ эффективности расхода ресурсов:
- **Short Polling:** 99% запросов возвращают «ничего не изменилось» (`304 Not Modified` или пустой JSON). Колоссальная трата CPU и полосы.
- **Long Polling:** Сервер держит запрос подвешенным до появления данных. Порог задержки низкий, но каждое событие требует повторного HTTP-рукопожатия.
- **SSE (Server-Sent Events):** Одно постоянное HTTP-соединение. Данные пушатся мгновенно в текстовом формате. Идеально для собственных SPA-клиентов.

## Решение по шагам

1. Создайте симулятор трех подходов: Polling, SSE и Webhook.
2. Замерьте количество HTTP-запросов и сетевой оверхед за период наблюдения при редких событиях (1 событие в 10 секунд).
3. Продемонстрируйте колоссальную экономию ресурсов вебхуками и SSE по сравнению с опросом.

## Код решения

**`delivery_comparison.go`**

```go
package main

import (
	"fmt"
	"time"
)

type SimulationResult struct {
	Strategy       string
	RequestsCount  int
	BytesSentTotal int
	LatencyToEvent time.Duration
}

func SimulateComparison() []SimulationResult {
	// Симуляция: период наблюдения 60 секунд.
	// Событие произошло ровно в момент t = 47.3 секунд.
	observationWindow := 60 * time.Second
	eventOccurredAt := 47300 * time.Millisecond

	// 1. Short Polling (опрос каждые 2 секунды)
	pollingInterval := 2 * time.Second
	pollCount := int(observationWindow / pollingInterval)
	// Оверхед HTTP заголовков ~ 400 байт на запрос
	pollBytes := pollCount * 400
	// Задержка: событие на 47.3с, следующий опрос на 48.0с -> задержка 700 мс
	pollLatency := 700 * time.Millisecond

	// 2. Server-Sent Events (SSE)
	// 1 подключение (GET), держится 60 сек. При наступлении события пушится 1 фрейм.
	sseRequests := 1
	sseBytes := 400 + 80 // Хендшейк + само событие
	sseLatency := 2 * time.Millisecond // Практически мгновенно

	// 3. Webhook
	// 0 запросов до события. Ровно 1 HTTP POST в момент 47.3с
	webhookRequests := 1
	webhookBytes := 450 // 1 POST запрос с телом
	webhookLatency := 15 * time.Millisecond // Время на сетевой RTT POST запроса

	return []SimulationResult{
		{Strategy: "Short Polling (2s)", RequestsCount: pollCount, BytesSentTotal: pollBytes, LatencyToEvent: pollLatency},
		{Strategy: "Server-Sent Events", RequestsCount: sseRequests, BytesSentTotal: sseBytes, LatencyToEvent: sseLatency},
		{Strategy: "Webhooks (Push)", RequestsCount: webhookRequests, BytesSentTotal: webhookBytes, LatencyToEvent: webhookLatency},
	}
}

func main() {
	results := SimulateComparison()

	fmt.Println("=== Сравнение сетевой эффективности: Polling vs SSE vs Webhooks ===")
	fmt.Println("Условие: Период 60 секунд, ровно 1 бизнес-событие на 47-й секунде.")
	fmt.Printf("%-25s | %-15s | %-12s | %-10s\n", "Стратегия", "Кол-во HTTP", "Трафик (байт)", "Задержка")
	fmt.Println("-------------------------------------------------------------------------")

	for _, r := range results {
		fmt.Printf("%-25s | %-15d | %-12d | %v\n",
			r.Strategy, r.RequestsCount, r.BytesSentTotal, r.LatencyToEvent)
	}

	fmt.Println("\nВывод архитектора:")
	fmt.Println("1. Polling совершил 30 пустых запросов, потратив 12 КБ трафика с худшей задержкой 700 мс.")
	fmt.Println("2. SSE идеален для браузера клиента (мгновенная доставка, 1 долгоживущее соединение).")
	fmt.Println("3. Webhook идеален для сторонних серверов (0 постоянных соединений, ровно 1 вызов).")
}
```

## Под капотом

Внутри ядра Linux каждое постоянное соединение (SSE/WebSocket) удерживает структуру `struct sock` и буферы `sk_rmem_alloc` / `sk_wmem_alloc`. Для 1 миллиона постоянных соединений требуется минимум 2–4 ГБ системной памяти ядра (kernel memory), не подлежащей свопингу.
Вебхуки не удерживают постоянных сокетов: сокет открывается, отправляет пакет и закрывается, освобождая ресурсы ОС.

## Подводные камни

1. **Попытка слать Webhooks в браузер:** Браузер не может слушать порт и принимать входящие POST-запросы без промежуточных туннелей. В браузер можно слать только SSE или WebSocket.
2. **Выбор Polling для высоконагруженных систем:** При 100 000 клиентов 2-секундный поллинг создаст 50 000 RPS паразитной нагрузки на базу данных и балансировщики.

## На собеседовании

**Вопрос:** Когда Short Polling всё еще является оправданным архитектурным решением?

**Ответ:** 
1. При сверхнизкой частоте обращений (например, проверка обновлений версии desktop-приложения 1 раз в 24 часа).
2. В изолированных средах без возможности удерживать постоянные TCP-сессии или открыть входящие порты.
3. В простых MVP, где разработка инфраструктуры очередей доставки вебхуков экономически нецелесообразна на раннем этапе.
