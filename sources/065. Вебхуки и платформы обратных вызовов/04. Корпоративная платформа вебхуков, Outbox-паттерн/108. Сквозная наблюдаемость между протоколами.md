# Сквозная наблюдаемость между протоколами (Cross-Protocol Observability & W3C Traceparent)

## Условие

Один request может пройти через REST → gRPC → webhook delivery. Сквозной `trace_id` через все protocols — это must have для debugging.

### Исходная формулировка

**Observability across protocols.**: Один request может пройти через REST → gRPC → webhook delivery. Сквозной `trace_id` через все protocols — это must have для debugging.

## Теория

В распределенной микросервисной архитектуре жизненный цикл бизнес-действия пересекает границы множества разнородных протоколов:
1. Клиент делает внешний вызов по **REST/JSON** в API Gateway.
2. Gateway транслирует запрос по бинарному **gRPC/HTTP/2** в сервис биллинга.
3. Сервис биллинга коммитит событие в **Transactional Outbox / Kafka**.
4. Воркер диспетчера вычитывает событие и отправляет внешний **Webhook HTTPS POST** на сервер партнера.

Если каждый протокол генерирует собственный изолированный лог, расследование инцидента («Почему партнер не получил хук по платежу № 888?») превращается в многочасовой поиск по сотням дашбордов.

### Стандарт W3C Trace Context (`traceparent`):
Сквозной контекст передается через заголовок `traceparent` формата:
`version-trace_id-parent_id-trace_flags`
Например: `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`.
- `trace_id` (32 hex-символа): неизменен на всем пути от REST до конечного вебхука.
- Диспетчер вебхука обязан передавать заголовок `traceparent` в исходящем HTTP POST запросе, позволяя партнеру связать свои серверные логи с трассировкой платформы!

## Решение по шагам

1. Реализуйте генератор и парсер структуры W3C `Traceparent`.
2. Смоделируйте сквозной проброс через контекст Go (`context.Context`).
3. Реализуйте цепочку: REST хендлер -> имитация gRPC вызова -> отправка исходящего вебхука.
4. Продемонстрируйте сохранение единого `trace_id` на всех стадиях конвейера.

## Код решения

**`cross_protocol_tracing.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

type TraceContext struct {
	TraceID string
	SpanID  string
}

// GenerateTraceID генерирует случайный 16-байтный W3C TraceID
func GenerateTraceID() string {
	b := make([]byte, 16)
	rand.Read(b)
	return hex.EncodeToString(b)
}

func GenerateSpanID() string {
	b := make([]byte, 8)
	rand.Read(b)
	return hex.EncodeToString(b)
}

func FormatTraceparent(tc TraceContext) string {
	return fmt.Sprintf("00-%s-%s-01", tc.TraceID, tc.SpanID)
}

func ParseTraceparent(h string) (TraceContext, bool) {
	parts := strings.Split(h, "-")
	if len(parts) != 4 || parts[0] != "00" {
		return TraceContext{}, false
	}
	return TraceContext{TraceID: parts[1], SpanID: parts[2]}, true
}

// 1. Входящий REST шлюз
func RESTIngressHandler(outboundURL string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		tc, ok := ParseTraceparent(r.Header.Get("traceparent"))
		if !ok {
			tc = TraceContext{TraceID: GenerateTraceID(), SpanID: GenerateSpanID()}
		}

		ctx := context.WithValue(r.Context(), "trace", tc)
		fmt.Printf("[1. REST INGRESS] Получен запрос клиента. TraceID = %s\n", tc.TraceID)

		// 2. Вызов внутреннего gRPC сервиса (проброс контекста)
		simulateInternalGRPC(ctx, outboundURL)

		w.WriteHeader(http.StatusOK)
		w.Write([]byte(`{"status":"ok","trace_id":"` + tc.TraceID + `"}`))
	}
}

// 2. Внутренний gRPC сервис
func simulateInternalGRPC(ctx context.Context, outboundURL string) {
	tc := ctx.Value("trace").(TraceContext)
	// Создаем новый child span для gRPC
	grpcSpan := TraceContext{TraceID: tc.TraceID, SpanID: GenerateSpanID()}
	fmt.Printf("[2. INTERNAL gRPC] Обработка в сервисе биллинга. TraceID = %s, SpanID = %s\n",
		grpcSpan.TraceID, grpcSpan.SpanID)

	// 3. Отправка исходящего вебхука партнеру
	simulateWebhookDispatch(grpcSpan, outboundURL)
}

// 3. Исходящий вебхук диспетчер
func simulateWebhookDispatch(tc TraceContext, outboundURL string) {
	webhookSpan := TraceContext{TraceID: tc.TraceID, SpanID: GenerateSpanID()}
	headerVal := FormatTraceparent(webhookSpan)

	req, _ := http.NewRequest(http.MethodPost, outboundURL, strings.NewReader(`{"event":"payment.done"}`))
	req.Header.Set("traceparent", headerVal)
	req.Header.Set("Content-Type", "application/json")

	resp, err := http.DefaultClient.Do(req)
	if err == nil {
		resp.Body.Close()
	}
	fmt.Printf("[3. WEBHOOK DISPATCH] Отправлен POST партнеру с заголовком: traceparent: %s\n", headerVal)
}

func main() {
	// Сервер партнера, принимающий вебхук
	partnerServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		tp := r.Header.Get("traceparent")
		tc, _ := ParseTraceparent(tp)
		fmt.Printf("[4. PARTNER RECEIVER] Партнер принял вебхук! Связанный TraceID = %s\n", tc.TraceID)
		w.WriteHeader(http.StatusOK)
	}))
	defer partnerServer.Close()

	gateway := httptest.NewServer(RESTIngressHandler(partnerServer.URL))
	defer gateway.Close()

	fmt.Println("=== Старт сквозного тестирования трассировки (REST -> gRPC -> Webhook) ===")
	resp, _ := http.Get(gateway.URL)
	resp.Body.Close()
}
```

## Под капотом

Стандарт OpenTelemetry использует интерфейсы `propagation.TextMapPropagator` (такие как `propagation.TraceContext`). При переходе из HTTP в gRPC контекст внедряется в метаданные gRPC (`metadata.MD`), а при записи в Kafka — в бинарные заголовки записи (`RecordHeaders`). Воркер вебхука извлекает заголовки из Kafka и внедряет их в исходящие HTTP-заголовки `req.Header`, гарантируя непрерывность распределенного графа вызовов в Jaeger / Tempo.

## Подводные камни

1. **Генерация нового `trace_id` на каждом звене цепи:** Если генерировать новый ID в каждом микросервисе, связь между действием пользователя и отправкой вебхука будет безвозвратно утеряна.
2. **Игнорирование флагов семплирования (`trace_flags`):** Если флаг семплирования равен `00`, трассировщик не должен сохранять подробные спаны на диск, чтобы не перегружать базу трассировок при 100 000 RPS.

## На собеседовании

**Вопрос:** Как организовать сквозную трассировку вебхуков, если отправка отложена на 2 часа из-за ретраев и бэкоффа?

**Ответ:** 
1. Исходный `trace_id` и родительский `span_id` персистятся в базе данных Outbox вместе с полезной нагрузкой вебхука.
2. Когда через 2 часа воркер ретраев просыпается, он восстанавливает контекст через `trace.NewSpanContext(TraceID, SpanID)` и создает дочерний спан с атрибутами `retry_attempt: 3`, связывая попытку доставки с оригинальной транзакцией заказа 2-часовой давности в Jaeger.
