# Идемпотентная обработка вебхуков на стороне получателя (Receiver Idempotency)

## Условие

Твой Dispatcher может отправить один и тот же вебхук дважды (ошибка сети при получении 200 OK). На стороне Получателя (Receiver) добавь проверку по `Webhook-ID` в базу данных. Убедись, что бизнес-логика (например, зачисление бонусов) отрабатывает только один раз.

### Исходная формулировка

**Идемпотентность Получателя (Receiver Idempotency)**: Твой Dispatcher может отправить один и тот же вебхук дважды (ошибка сети при получении 200 OK). На стороне Получателя (Receiver) добавь проверку по `Webhook-ID` в базу данных. Убедись, что бизнес-логика (например, зачисление бонусов) отрабатывает только один раз.

## Теория

В распределенных сетевых системах действует фундаментальная теорема: **доставка сообщений возможна либо «At-most-once», либо «At-least-once»**. Честная доставка «Exactly-once» на физическом сетевом уровне невозможна из-за проблемы двух генералов.

### Сценарий дублирования вебхуков:
1. Диспетчер платформы отправил запрос `POST /webhook` с событием списания денег.
2. Сервер клиента успешно обработал запрос, начислил бонус и сформировал HTTP-ответ `200 OK`.
3. В этот момент на обратном пути сетевой пакет `TCP ACK` с ответом `200 OK` теряется на маршрутизаторе провайдера.
4. Диспетчер платформы фиксирует ошибку `net/http: connection reset by peer` или сетевой таймаут.
5. Согласно политике ретраев, диспетчер через 5 секунд отправляет этот же вебхук повторно!
6. Если у клиента нет идемпотентности, бонус будет начислен **второй раз**!

### Паттерн Idempotent Consumer:
1. Каждый вебхук сопровождается уникальным глобальным идентификатором в заголовке: `Webhook-ID: evt_01HJ...` (или `X-Event-ID`).
2. Приемник начинает обработку с атомарной проверки наличия этого ID в таблице идемпотентности (`processed_events` с `PRIMARY KEY (event_id)`).
3. Бизнес-логика и сохранение `Webhook-ID` выполняются в **одной транзакции БД**.
4. При обнаружении дубликата возвращается `HTTP 200 OK` (чтобы платформа прекратила ретраи), но бизнес-логика повторно **НЕ выполняется**!

## Решение по шагам

1. Создайте структуру хранилища идемпотентности с таблицей `processed_events`.
2. Реализуйте HTTP-обработчик входящих вебхуков клиента.
3. Извлеките заголовок `Webhook-ID`.
4. Проверьте уникальность ID перед выполнением начисления бонусов.
5. Продемонстрируйте повторную отправку одного и того же вебхука: бизнес-действие выполнится ровно один раз.

## Код решения

**`receiver_idempotency.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"time"
)

type BonusEventPayload struct {
	UserID string `json:"user_id"`
	Points int    `json:"points"`
}

type IdempotentReceiver struct {
	mu              sync.Mutex
	userBalances    map[string]int
	processedEvents map[string]time.Time
}

func NewIdempotentReceiver() *IdempotentReceiver {
	return &IdempotentReceiver{
		userBalances:    make(map[string]int),
		processedEvents: make(map[string]time.Time),
	}
}

func (r *IdempotentReceiver) ServeHTTP(w http.ResponseWriter, req *http.Request) {
	eventID := req.Header.Get("Webhook-ID")
	if eventID == "" {
		http.Error(w, "Missing Webhook-ID header", http.StatusBadRequest)
		return
	}

	var payload BonusEventPayload
	if err := json.NewDecoder(req.Body).Decode(&payload); err != nil {
		http.Error(w, "Bad Request JSON", http.StatusBadRequest)
		return
	}

	r.mu.Lock()
	defer r.mu.Unlock()

	// 1. Проверка на дубликат (Idempotency Check)
	if processedAt, exists := r.processedEvents[eventID]; exists {
		fmt.Printf("[DUPLICATE DETECTED] Событие %s уже было обработано в %s! Бизнес-логика пропущена.\n",
			eventID, processedAt.Format("15:04:05.000"))

		// ОБЯЗАТЕЛЬНО возвращаем 200 OK, чтобы диспетчер успокоился и закрыл задачу!
		w.WriteHeader(http.StatusOK)
		w.Write([]byte(`{"status":"already_processed"}`))
		return
	}

	// 2. Выполнение критической бизнес-логики
	r.userBalances[payload.UserID] += payload.Points
	r.processedEvents[eventID] = time.Now()

	fmt.Printf("[PROCESSED] Событие %s: Пользователю %s успешно начислено %d бонусов. Новый баланс = %d\n",
		eventID, payload.UserID, payload.Points, r.userBalances[payload.UserID])

	w.WriteHeader(http.StatusOK)
	w.Write([]byte(`{"status":"success"}`))
}

func main() {
	receiver := NewIdempotentReceiver()
	ts := httptest.NewServer(receiver)
	defer ts.Close()

	payloadJSON := `{"user_id":"user_42","points":500}`
	eventID := "evt_loyalty_bonus_99418"

	fmt.Println("=== Попытка 1: Первичная отправка вебхука ===")
	req1, _ := http.NewRequest(http.MethodPost, ts.URL, strings.NewReader(payloadJSON))
	req1.Header.Set("Webhook-ID", eventID)
	resp1, _ := http.DefaultClient.Do(req1)
	resp1.Body.Close()

	fmt.Println("\n=== Попытка 2: Повторная отправка диспетчером того же вебхука (Сетевой ретрай) ===")
	req2, _ := http.NewRequest(http.MethodPost, ts.URL, strings.NewReader(payloadJSON))
	req2.Header.Set("Webhook-ID", eventID)
	resp2, _ := http.DefaultClient.Do(req2)
	resp2.Body.Close()

	fmt.Println("\n=== Попытка 3: Третья отправка вебхука ===")
	req3, _ := http.NewRequest(http.MethodPost, ts.URL, strings.NewReader(payloadJSON))
	req3.Header.Set("Webhook-ID", eventID)
	resp3, _ := http.DefaultClient.Do(req3)
	resp3.Body.Close()

	fmt.Printf("\nИТОГОВЫЙ БАЛАНС ПОЛЬЗОВАТЕЛЯ user_42: %d бонусов (Ожидается ровно 500!)\n", receiver.userBalances["user_42"])
}
```

ℹ️ Результат работы идемпотентного приемника

## Под капотом

В реляционных базах данных идемпотентность реализуется через конструкцию `INSERT INTO processed_events (event_id, processed_at) VALUES ($1, NOW()) ON CONFLICT (event_id) DO NOTHING`.
Если запрос вставил 0 строк, транзакция понимает, что запись уже существует, и выполняет `SELECT` предыдущего сохраненного результата, возвращая идентичный ответ без повторения побочных эффектов.

## Подводные камни

1. **Возврат ошибки `409 Conflict` или `400 Bad Request` при дубликате:** Если вернуть ошибку на дубликат, диспетчер платформы решит, что вебхук упал, и продолжит слать его повторно в соответствии с политикой ретраев! На дубликаты ОБЯЗАТЕЛЬНО возвращать `200 OK`.
2. **Проверка в Redis отдельно от БД:** Если сделать `SETNX event_id` в Redis, а запись в SQL-БД упадет, событие пометится как обработанное, но деньги не начислятся. Проверка идемпотентности обязана быть в той же транзакции, что и бизнес-изменение.

## На собеседовании

**Вопрос:** Как организовать очистку (Retention) таблицы идемпотентности `processed_events`, если в нее пишется по 10 миллионов записей в сутки?

**Ответ:** Вебхуки имеют максимальный срок автоматических ретраев платформы (обычно 24–72 часа). После этого срока старый дубликат прийти физически не может. Применяются:
1. Партиционирование таблицы по дням `PARTITION BY RANGE (processed_at)` со сбросом партиций старше 7 дней (`DROP TABLE`).
2. В Redis: использование ключей с явным TTL: `SET idempotency:evt_123 "done" EX 604800 NX` (7 дней).
