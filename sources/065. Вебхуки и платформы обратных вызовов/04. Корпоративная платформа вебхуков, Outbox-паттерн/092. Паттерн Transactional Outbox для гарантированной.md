# Паттерн Transactional Outbox для гарантированной доставки вебхуков

## Условие

Напиши сервис, который сохраняет вебхук в таблицу `webhooks_outbox` в рамках основной бизнес-транзакции. Фоновый воркер читает таблицу, отправляет вебхуки и помечает строки как `delivered`. Если воркер упал, при рестарте он продолжит с места остановки.

### Исходная формулировка

**[Высокая сложность — Webhook Outbox]**: Напиши сервис, который сохраняет вебхук в таблицу `webhooks_outbox` в рамках основной бизнес-транзакции. Фоновый воркер читает таблицу, отправляет вебхуки и помечает строки как `delivered`. Если воркер упал, при рестарте он продолжит с места остановки.

## Теория

Классическая архитектурная проблема при публикации событий: **Dual-Write Problem** (Проблема двойной записи).

### Катастрофический сценарий без Outbox:
```go
tx.Exec("UPDATE accounts SET balance = balance - 1000 WHERE id = 1")
tx.Commit()
// В этот момент нода падает по OOM / SIGKILL!
// Деньги списаны в БД, но вебхук партнеру так и не был отправлен!
http.Post("https://partner/webhook", payload)
```
Либо наоборот: вебхук отправлен партнеру, а транзакция базы данных упала по deadlock и откатилась (`Rollback`). Партнер отгрузил товар за несостоявшийся платеж!

### Решение: Паттерн Transactional Outbox:
1. В реляционной БД создается таблица `webhooks_outbox`.
2. В рамках **единой ACID-транзакции** выполняются:
   - Бизнес-изменение (`INSERT INTO orders`).
   - Сохранение неотправленного вебхука (`INSERT INTO webhooks_outbox (status = 'PENDING')`).
3. Транзакция коммитится атомарно. Гарантия: если заказ создался, запись в Outbox **гарантированно существует**!
4. Фоновый воркер вычитывает пачки через `SELECT ... FOR UPDATE SKIP LOCKED`, отправляет во внешнюю сеть и переводит статус в `DELIVERED`.

## Решение по шагам

1. Создайте структуру транзакционного репозитория Outbox.
2. Напишите бизнес-метод создания заказа, атомарно добавляющий событие в таблицу `webhooks_outbox`.
3. Реализуйте воркер опроса Outbox (Poller) с механизмом блокировки строк (`SKIP LOCKED`).
4. Обеспечьте сохранение состояния при сбое и возобновление работы с места остановки при перезапуске.

## Код решения

**`transactional_outbox.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type OutboxRecord struct {
	ID          int64
	EventID     string
	EventType   string
	Payload     string
	Status      string // "PENDING", "PROCESSING", "DELIVERED", "FAILED"
	CreatedAt   time.Time
	ProcessedAt *time.Time
}

// In-memory симулятор БД с поддержкой транзакций и блокировок строк
type MockDatabase struct {
	mu     sync.Mutex
	outbox []OutboxRecord
	nextID int64
}

func (db *MockDatabase) CreateOrderWithOutbox(orderID string, amount int64, eventType, payload string) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Создание заказа (бизнес-логика)
	// INSERT INTO orders ...

	// 2. В этой же транзакции создаем запись в Outbox
	db.nextID++
	record := OutboxRecord{
		ID:        db.nextID,
		EventID:   fmt.Sprintf("evt_%s_%d", orderID, db.nextID),
		EventType: eventType,
		Payload:   payload,
		Status:    "PENDING",
		CreatedAt: time.Now(),
	}
	db.outbox = append(db.outbox, record)
	fmt.Printf("[DB TX COMMIT] Заказ %s и вебхук-событие %s атомарно закоммичены в БД\n", orderID, record.EventID)
	return nil
}

// FetchPendingWithLock имитирует SELECT ... FOR UPDATE SKIP LOCKED LIMIT batchSize
func (db *MockDatabase) FetchPendingWithLock(batchSize int) []*OutboxRecord {
	db.mu.Lock()
	defer db.mu.Unlock()

	var batch []*OutboxRecord
	for i := range db.outbox {
		if db.outbox[i].Status == "PENDING" {
			db.outbox[i].Status = "PROCESSING"
			batch = append(batch, &db.outbox[i])
			if len(batch) >= batchSize {
				break
			}
		}
	}
	return batch
}

func (db *MockDatabase) MarkDelivered(id int64) {
	db.mu.Lock()
	defer db.mu.Unlock()

	now := time.Now()
	for i := range db.outbox {
		if db.outbox[i].ID == id {
			db.outbox[i].Status = "DELIVERED"
			db.outbox[i].ProcessedAt = &now
			break
		}
	}
}

// OutboxWorker фоново доставляет события
type OutboxWorker struct {
	db     *MockDatabase
	stopCh chan struct{}
}

func NewOutboxWorker(db *MockDatabase) *OutboxWorker {
	return &OutboxWorker{
		db:     db,
		stopCh: make(chan struct{}),
	}
}

func (w *OutboxWorker) Start(ctx context.Context) {
	ticker := time.NewTicker(50 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-w.stopCh:
			return
		case <-ticker.C:
			// Забираем пачку задач с блокировкой
			batch := w.db.FetchPendingWithLock(10)
			for _, rec := range batch {
				w.deliverWebhook(rec)
			}
		}
	}
}

func (w *OutboxWorker) deliverWebhook(rec *OutboxRecord) {
	// Имитация успешной отправки HTTP POST клиенту
	time.Sleep(10 * time.Millisecond)
	w.db.MarkDelivered(rec.ID)
	fmt.Printf("[OUTBOX DISPATCH] Вебхук %s (%s) доставлен! Статус в БД = DELIVERED\n", rec.EventID, rec.EventType)
}

func main() {
	db := &MockDatabase{}
	worker := NewOutboxWorker(db)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	// Запускаем воркер в фоне
	go worker.Start(ctx)

	// Создаем 3 заказа через транзакции
	db.CreateOrderWithOutbox("ORD-101", 5000, "order.created", `{"order_id":"ORD-101","price":5000}`)
	db.CreateOrderWithOutbox("ORD-102", 7200, "order.created", `{"order_id":"ORD-102","price":7200}`)
	db.CreateOrderWithOutbox("ORD-103", 1100, "order.created", `{"order_id":"ORD-103","price":1100}`)

	// Даем воркеру время вычитать Outbox
	time.Sleep(150 * time.Millisecond)
}
```

## Под капотом

В PostgreSQL конструкция `SELECT id, payload FROM webhooks_outbox WHERE status = 'PENDING' ORDER BY id LIMIT 50 FOR UPDATE SKIP LOCKED` является промышленным стандартом.
Опция `SKIP LOCKED` заставляет транзакцию пропускать строки, которые уже заблокированы другими параллельно работающими воркерами. Это позволяет запускать десятки экземпляров воркеров Outbox без конфликтов блокировок (Row Lock Contention) и взаимоблокировок (Deadlocks).

## Подводные камни

1. **Очистка исторической таблицы Outbox:** Если не удалять доставленные строки, таблица разрастется до сотен миллионов строк, замедляя индексы. Применяйте партиционирование по дням (`PARTITION BY RANGE (created_at)`) с удалением старых партиций (`DROP TABLE outbox_y2026m01d15`).
2. **Polling Overhead:** Опрос таблицы каждые 50 мс создает постоянную паразитную нагрузку на БД. В HighLoad системах опрос заменяют на **CDC (Change Data Capture)** через Debezium / pgoutput, читающий Outbox напрямую из WAL-лога PostgreSQL.

## На собеседовании

**Вопрос:** В чем разница между Transactional Outbox с Polling Publisher и Transactional Outbox с Transaction Log Tailing (CDC)?

**Ответ:** 
- **Polling Publisher:** Приложение периодически делает `SELECT ... FOR UPDATE SKIP LOCKED`. Плюс: простота реализации. Минус: накладные расходы на диск БД при высокой частоте опроса, задержка доставки (polling interval).
- **Transaction Log Tailing (CDC):** Специальный коннектор (Debezium) подключается к слоту логической репликации PostgreSQL и вычитывает изменения строк `webhooks_outbox` напрямую из WAL с задержкой < 5 мс без каких-либо SQL-запросов к БД. Это высший стандарт архитектуры в BigTech.
