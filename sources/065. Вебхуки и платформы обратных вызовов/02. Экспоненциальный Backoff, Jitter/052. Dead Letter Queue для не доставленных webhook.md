# Dead Letter Queue для не доставленных webhook: сохранение контекста и аудит отказов

## Условие

52. **Dead Letter Queue для не доставленных webhook.**: После исчерпания попыток поместите webhook-сообщение в отдельную таблицу БД или Kafka-топик «dead-letters» для ручного анализа и возможности повторной отправки администратором.

### Исходная формулировка

**Dead Letter Queue для не доставленных webhook.**: После исчерпания попыток поместите webhook-сообщение в отдельную таблицу БД или Kafka-топик «dead-letters» для ручного анализа и возможности повторной отправки администратором.

## Теория

Очередь недоставленных сообщений (Dead Letter Queue, DLQ) в платформе вебхуков должна не просто сохранять факт ошибки, а аккумулировать полный контекст инцидента:
1. Исходное доменное событие (Payload, Headers, EventID).
2. Историю всех попыток (коды статусов, сообщения об ошибках, время каждой попытки).
3. Причину окончательного сброса (`EXHAUSTED_RETRIES`, `UNSUBSCRIBED_410`, `MALFORMED_URL`).
4. Метаданные подписчика (URL, ID аккаунта).
Это позволяет операторам платформы анализировать системные сбои и осуществлять повторную доставку (DLQ Replay) после исправления проблем на стороне интегратора.

## Решение по шагам

1. Опишите структуру `DetailedDLQRecord` с коллекцией трейсов попыток.
2. Создайте сервис `DLQStore` с потокобезопасным добавлением и получением записей по ID.
3. Продемонстрируйте перемещение задачи в DLQ с сохранением истории 3 попыток.

## Код решения

**`detailed_dlq_store.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type AttemptTrace struct {
	AttemptNumber int       `json:"attempt_number"`
	ExecutedAt    time.Time `json:"executed_at"`
	StatusCode    int       `json:"status_code"`
	ErrorMessage  string    `json:"error_message"`
}

type DetailedDLQRecord struct {
	ID           string         `json:"id"`
	EventID      string         `json:"event_id"`
	WebhookID    string         `json:"webhook_id"`
	TargetURL    string         `json:"target_url"`
	RawPayload   string         `json:"raw_payload"`
	DroppedAt    time.Time      `json:"dropped_at"`
	DropReason   string         `json:"drop_reason"`
	AttemptTraces []AttemptTrace `json:"attempt_traces"`
}

type DLQService struct {
	mu      sync.RWMutex
	records map[string]DetailedDLQRecord
}

func NewDLQService() *DLQService {
	return &DLQService{records: make(map[string]DetailedDLQRecord)}
}

func (s *DLQService) PushToDLQ(record DetailedDLQRecord) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.records[record.ID] = record
	fmt.Printf("[DLQ Engine] Recorded dead-letter message: ID=%s (Event=%s, Traces=%d)\n",
		record.ID, record.EventID, len(record.AttemptTraces))
}

func main() {
	dlq := NewDLQService()

	traces := []AttemptTrace{
		{AttemptNumber: 1, ExecutedAt: time.Now().Add(-15 * time.Minute), StatusCode: 503, ErrorMessage: "Service Unavailable"},
		{AttemptNumber: 2, ExecutedAt: time.Now().Add(-10 * time.Minute), StatusCode: 504, ErrorMessage: "Gateway Timeout"},
		{AttemptNumber: 3, ExecutedAt: time.Now().Add(-5 * time.Minute), StatusCode: 0, ErrorMessage: "dial tcp: i/o timeout"},
	}

	record := DetailedDLQRecord{
		ID:            "dlq_item_771",
		EventID:       "evt_payment_captured_11",
		WebhookID:     "sub_merchant_42",
		TargetURL:     "https://partner.bank.ru/webhook",
		RawPayload:    `{"amount": 15000, "currency": "RUB"}`,
		DroppedAt:     time.Now().UTC(),
		DropReason:    "MAX_RETRIES_EXCEEDED",
		AttemptTraces: traces,
	}

	dlq.PushToDLQ(record)

	data, _ := json.MarshalIndent(record, "", "  ")
	fmt.Printf("Persisted DLQ Structure:\n%s\n", string(data))
}
```

## Под капотом

В корпоративных системах DLQ топики выносятся в отдельный Kafka топик (`webhooks.dlq`) с retention period = 30 дней. Это позволяет обрабатывать инциденты пакетными скриптами без риска забить оперативную память основных очередей брокера.

## Подводные камни

1. Запись в DLQ без исходного payload: если не сохранить тело события, повторная отправка будет невозможна.
2. Бесконечное хранение без мониторинга: рост размера DLQ должен триггерить алерты в Grafana/PagerDuty.
3. Отсутствие версионирования схемы payload в DLQ.

## На собеседовании

**Вопрос (Stripe/Amazon):** Как устроен процесс Redrive (повторного прогона) сообщений из Dead Letter Queue?
**Ответ:** Процесс Redrive состоит из двух этапов:
1. Инженер поддержки или клиент через API инициирует `RedriveJob` с фильтром по `webhook_id` и диапазону дат.
2. Сервер вычитывает записи из DLQ, оборачивает их в свежие задачи с новым `timestamp` и текущей HMAC-подписью (сохраняя оригинальный `event.id` и `payload`), после чего отправляет их в стандартную очередь воркеров с ограниченной скоростью (Rate Limiting), чтобы не залить сервер клиента лавиной старых событий.
