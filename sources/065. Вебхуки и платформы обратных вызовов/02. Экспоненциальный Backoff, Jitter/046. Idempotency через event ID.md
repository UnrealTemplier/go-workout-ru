# Idempotency через event ID: дедупликация на стороне базы данных клиента

## Условие

46. **Idempotency через event ID**: Клиент должен использовать `event.id` для deduplication. Один и тот же event может быть доставлен несколько раз (at-least-once semantics).

### Исходная формулировка

**Idempotency через event ID**: Клиент должен использовать `event.id` для deduplication. Один и тот же event может быть доставлен несколько раз (at-least-once semantics).

## Теория

Самый надежный способ реализации идемпотентности на стороне получателя — фиксация уникального `event_id` в реляционной базе данных в единой транзакции с изменениями бизнес-данных.
Таблица `processed_events`:
```sql
CREATE TABLE processed_events (
    event_id VARCHAR(64) PRIMARY KEY,
    event_type VARCHAR(64) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
Паттерн транзакционной вставки:
```sql
BEGIN;
INSERT INTO processed_events (event_id, event_type) VALUES ($1, $2)
ON CONFLICT (event_id) DO NOTHING;
-- Проверяем: если запись не вставилась, значит событие уже обработано!
-- Иначе: выполняем бизнес-операцию (начисление денег, обновление статуса)
COMMIT;
```
Этот подход исключает состояние гонки даже при конкурентном поступлении двух одинаковых вебхуков на разные поды сервиса.

## Код решения

**`db_event_dedup.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type ProcessedEventsDB struct {
	mu    sync.Mutex
	table map[string]string // event_id -> event_type
}

func NewProcessedEventsDB() *ProcessedEventsDB {
	return &ProcessedEventsDB{table: make(map[string]string)}
}

// TryRecordEvent эмулирует INSERT ... ON CONFLICT DO NOTHING
// Возвращает true, если запись была успешно вставлена (событие новое)
func (db *ProcessedEventsDB) TryRecordEvent(eventID, eventType string) bool {
	db.mu.Lock()
	defer db.mu.Unlock()

	if _, exists := db.table[eventID]; exists {
		return false // Дубликат
	}
	db.table[eventID] = eventType
	return true
}

func HandleWebhookWithDB(db *ProcessedEventsDB, eventID, eventType string, businessAction func()) {
	// Атомарная проверка уникальности
	inserted := db.TryRecordEvent(eventID, eventType)
	if !inserted {
		fmt.Printf("[Idempotency Guard] Event %s already recorded in DB. Skipping business logic.\n", eventID)
		return
	}

	businessAction()
	fmt.Printf("[DB Transaction Committed] Event %s processed successfully.\n", eventID)
}

func main() {
	db := NewProcessedEventsDB()
	eventID := "evt_order_paid_999"

	var wg sync.WaitGroup
	fmt.Println("--- Simulating 4 concurrent deliveries of the exact same event ---")

	for i := 1; i <= 4; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			HandleWebhookWithDB(db, eventID, "order.paid", func() {
				fmt.Printf(">>> [Worker %d] EXECUTING PAYMENT LOGIC (Charging customer once)\n", workerID)
			})
		}(i)
	}

	wg.Wait()
}
```

## Под капотом

В реляционных СУБД с изоляцией транзакций `READ COMMITTED` и выше, уникальный индекс на первичном ключе `PRIMARY KEY (event_id)` накладывает блокировку на уровне B-Tree страницы. Первая транзакция захватывает слот, а все остальные транзакции при попытке вставки немедленно получают статус конфликта уникальности без возможности выполнения побочных эффектов.

## Подводные камни

1. Запись `event_id` в базу после выполнения бизнес-логики: если бизнес-логика выполнилась, но процесс упал до коммита `processed_events`, повторный вебхук снова выполнит бизнес-логику! Запись `event_id` и бизнес-операция обязаны выполняться в **одной транзакции**.
2. Бесконечный рост таблицы `processed_events`: необходимо настроить периодическое секционирование (Partition pruning) или удаление записей старше 30–90 дней.
3. Отсутствие уникального индекса.

## На собеседовании

**Вопрос (Wildberries/T-Банк):** Почему дедупликация через таблицу в PostgreSQL надежнее проверки через Redis `SETNX`?
**Ответ:** Redis и PostgreSQL представляют собой две разные распределенные системы без поддержки двухфазного коммита (2PC). Если проверить ключ в Redis, а затем попытаться сохранить заказ в PostgreSQL, при аварии сервера или сбое сети между шагами состояние кэша и состояние БД рассинхронизируются. Фиксация `event_id` в таблице PostgreSQL внутри той же транзакции, что и изменение баланса, гарантирует свойство **ACID (Atomicity)**: либо фиксируются и событие, и изменения в БД, либо не фиксируется ничего.
