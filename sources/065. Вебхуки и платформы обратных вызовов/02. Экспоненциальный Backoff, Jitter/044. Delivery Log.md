## Теория

Журнал доставок (Delivery Log) — это фундаментальный инструмент наблюдаемости (Observability) платформы.
Пользовательский интерфейс разработчика требует возможности:
1. Фильтровать логи по `webhook_id`, `event_type`, диапазону дат и статусу доставки (`SUCCESS`, `FAILED`, `DEAD_LETTER`).
2. Получать пагинированный список с курсором (Cursor-based Pagination).
3. Просматривать детальные заголовки отправки, тело запроса и сниппет ответа.
Для обеспечения высокой производительности при миллиардах записей логи шардируются по временным партициям (Partitioning by Day/Month в PostgreSQL или ClickHouse).

## Код решения

**`delivery_log_store.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type LogStatus string

const (
	LogSuccess LogStatus = "SUCCESS"
	LogFailed  LogStatus = "FAILED"
)

type DeliveryLogEntry struct {
	ID         int64     `json:"id"`
	WebhookID  string    `json:"webhook_id"`
	EventType  string    `json:"event_type"`
	Status     LogStatus `json:"status"`
	StatusCode int       `json:"status_code"`
	LatencyMS  int64     `json:"latency_ms"`
	CreatedAt  time.Time `json:"created_at"`
}

type DeliveryLogRepository struct {
	mu      sync.RWMutex
	entries []DeliveryLogEntry
}

func (r *DeliveryLogRepository) Insert(entry DeliveryLogEntry) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.entries = append(r.entries, entry)
}

func (r *DeliveryLogRepository) Query(webhookID string, status LogStatus, limit int, afterID int64) []DeliveryLogEntry {
	r.mu.RLock()
	defer r.mu.RUnlock()

	var results []DeliveryLogEntry
	for _, e := range r.entries {
		if e.WebhookID != webhookID {
			continue
		}
		if status != "" && e.Status != status {
			continue
		}
		if e.ID <= afterID {
			continue
		}
		results = append(results, e)
		if len(results) >= limit {
			break
		}
	}
	return results
}

func main() {
	repo := &DeliveryLogRepository{}

	// Наполняем тестовыми логами
	for i := 1; i <= 6; i++ {
		st := LogSuccess
		code := 200
		if i%2 == 0 {
			st = LogFailed
			code = 502
		}
		repo.Insert(DeliveryLogEntry{
			ID:         int64(i),
			WebhookID:  "sub_alpha",
			EventType:  "order.created",
			Status:     st,
			StatusCode: code,
			LatencyMS:  int64(15 * i),
			CreatedAt:  time.Now().UTC().Add(time.Duration(i) * time.Minute),
		})
	}

	// Запрашиваем только ошибки (FAILED) с лимитом 2 записи
	failedLogs := repo.Query("sub_alpha", LogFailed, 2, 0)

	out, _ := json.MarshalIndent(failedLogs, "", "  ")
	fmt.Printf("Filtered Failed Delivery Logs (Page 1):\n%s\n", string(out))
}
```

## Под капотом

Курсорная пагинация по монотонному ID (`WHERE id > afterID LIMIT 20`) работает за константное время \(O(\log N)\) благодаря B-Tree индексу, в отличие от пагинации через `OFFSET 100000`, которая заставляет СУБД сканировать и отбрасывать сотни тысяч строк.

## Подводные камни

1. Использование пагинации `OFFSET / LIMIT` на больших объемах логов: глубокая пагинация (страница 5 000) приведет к деградации СУБД и таймаутам.
2. Отсутствие индекса по `(webhook_id, status, id)`: полнотабличное сканирование (Seq Scan) многомиллионной таблицы логов.
3. Отсутствие автоматической ротации партиций.

## На собеседовании

**Вопрос (Ozon/PostgreSQL):** Почему для логов вебхуков неприемлема реляционная пагинация `OFFSET` и как правильно организовать курсорную пагинацию?
**Ответ:** При запросе `OFFSET 100 000 LIMIT 20` база данных вынуждена физически прочитать с диска 100 020 строк и отбросить первые 100 000, что создает колоссальный ввод-вывод. Курсорная пагинация (Keyset Pagination) использует предикат `WHERE (created_at, id) < ($cursor_time, $cursor_id) ORDER BY created_at DESC, id DESC LIMIT 20`, моментально спускаясь по B-Tree индексу к нужной позиции за \(O(\log N)\) без оверхеда.
