# Idempotency-Key header: сквозная передача ключа идемпотентности в HTTP-запросе

## Условие

47. **Idempotency-Key header**: Отправляйте `Idempotency-Key: evt_...` header, чтобы клиенты могли использовать свои idempotency libraries.

### Исходная формулировка

**Idempotency-Key header**: Отправляйте `Idempotency-Key: evt_...` header, чтобы клиенты могли использовать свои idempotency libraries.

## Теория

Согласно спецификации IETF draft "The Idempotency-Key HTTP Header Field", заголовок `Idempotency-Key` (или `X-Idempotency-Key`) предназначен для предотвращения дублирования запросов на транспортном уровне.
Платформа отправки вебхуков обязана:
1. Выставлять заголовок `Idempotency-Key: <event_id>` для каждого исходящего HTTP POST запроса.
2. Гарантировать, что при всех автоматических повторных попытках (retries) значение заголовка `Idempotency-Key` остается **абсолютно неизменным**!
Приемник читает этот заголовок в первом middleware и использует его для поиска сохраненного ответа в кэше/БД.

## Решение по шагам

1. Реализуйте отправитель с установкой заголовка `Idempotency-Key`.
2. Реализуйте middleware получателя, сохраняющее код статуса и тело первого ответа в кэше по `Idempotency-Key`.
3. Продемонстрируйте возврат сохраненного ответа при повторном запросе без вызова целевого хэндлера.

## Код решения

**`idempotency_header_middleware.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"sync"
)

type CachedResponse struct {
	StatusCode int
	Body       []byte
}

type IdempotencyMiddleware struct {
	mu    sync.Mutex
	cache map[string]CachedResponse
}

func NewIdempotencyMiddleware() *IdempotencyMiddleware {
	return &IdempotencyMiddleware{cache: make(map[string]CachedResponse)}
}

func (m *IdempotencyMiddleware) Handler(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := r.Header.Get("Idempotency-Key")
		if key == "" {
			// Если ключ не передан — продолжаем обычную обработку
			next.ServeHTTP(w, r)
			return
		}

		m.mu.Lock()
		cached, exists := m.cache[key]
		m.mu.Unlock()

		if exists {
			// Возвращаем сохраненный ответ напрямую из кэша
			fmt.Printf("[Middleware] Returning CACHED response for Idempotency-Key: %s\n", key)
			w.Header().Set("X-Cache-Lookup", "HIT")
			w.WriteHeader(cached.StatusCode)
			_, _ = w.Write(cached.Body)
			return
		}

		// Перехватываем ответ целевого хэндлера
		rec := httptest.NewRecorder()
		next.ServeHTTP(rec, r)

		m.mu.Lock()
		m.cache[key] = CachedResponse{
			StatusCode: rec.Code,
			Body:       rec.Body.Bytes(),
		}
		m.mu.Unlock()

		// Записываем клиенту
		w.Header().Set("X-Cache-Lookup", "MISS")
		w.WriteHeader(rec.Code)
		_, _ = w.Write(rec.Body.Bytes())
	})
}

func main() {
	idempotency := NewIdempotencyMiddleware()

	businessHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Println("--> [Target Handler] EXECUTING HEAVY TRANSACTION IN DATABASE")
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"result":"order_created_123"}`))
	})

	server := httptest.NewServer(idempotency.Handler(businessHandler))
	defer server.Close()

	send := func(key string) {
		req, _ := http.NewRequest(http.MethodPost, server.URL, bytes.NewBufferString(`{}`))
		req.Header.Set("Idempotency-Key", key)
		resp, _ := http.DefaultClient.Do(req)
		body, _ := io.ReadAll(resp.Body)
		defer resp.Body.Close()
		fmt.Printf("Response: %d | Cache: %s | Body: %s\n",
			resp.StatusCode, resp.Header.Get("X-Cache-Lookup"), string(body))
	}

	fmt.Println("--- Request 1 (New Key) ---")
	send("idem_tx_4411")

	fmt.Println("\n--- Request 2 (Duplicate Key) ---")
	send("idem_tx_4411")
}
```

## Под капотом

Использование паттерна `ResponseRecorder` в middleware позволяет перехватить статус-код и бинарное тело ответа до его отправки в сетевой сокет, сохранить их в кэше и воспроизвести точь-в-точь при повторном запросе с тем же `Idempotency-Key`.

## Подводные камни

1. Генерация нового `Idempotency-Key` при каждой попытке ретрая: ломает смысл идемпотентности, так как получатель сочтет каждый повтор новым уникальным запросом.
2. Кэширование ошибок 500: если первый запрос упал с 500 Internal Server Error из-за падения базы, кэшировать его нельзя! Кэшируются только успешные ответы (2xx) или терминальные ошибки валидации (4xx).
3. Отсутствие TTL на кэш идемпотентности.

## На собеседовании

**Вопрос (Stripe/IETF):** Должен ли при повторном запросе с тем же `Idempotency-Key` проверяться payload запроса?
**Ответ:** Да! Согласно спецификации IETF Idempotency-Key, если входящий запрос содержит тот же `Idempotency-Key`, но другое тело запроса (payload mismatch), сервер обязан вернуть ошибку `422 Unprocessable Entity` или `409 Conflict`. Это защищает от опасной коллизии, когда разработчик по ошибке использовал один и тот же ключ для двух принципиально разных операций.
