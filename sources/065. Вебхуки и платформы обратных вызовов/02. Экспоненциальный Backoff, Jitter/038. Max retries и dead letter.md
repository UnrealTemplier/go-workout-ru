# Max retries и dead letter: маршрутизация в DLQ и оповещение клиентов

## Условие

38. **Max retries и dead letter**: После N неудачных попыток (обычно 15-20) помечайте webhook как disabled и отправляйте событие в dead letter queue для ручного разбора.

### Исходная формулировка

**Max retries и dead letter**: После N неудачных попыток (обычно 15-20) помечайте webhook как disabled и отправляйте событие в dead letter queue для ручного разбора.

## Теория

Когда число попыток доставки вебхука превышает максимальный лимит (`attempt_count >= max_retries`, обычно 5–10 попыток в течение 24–72 часов), событие признается окончательно недоставленным.
Платформа не должна молча удалять событие:
1. Запись переводится в статус `DEAD_LETTER`.
2. Событие перемещается в таблицу/топик **Dead Letter Queue (DLQ)** для постоянного хранения.
3. Инициируется оповещение владельца подписки:
   - Отправка системного Email ("Доставка вебхука на URL https://... приостановлена").
   - Генерация security/ops алерта в личный кабинет.
   - Опциональная временная деактивация подписки (`status = disabled`), если все последние 50 событий попали в DLQ.

## Решение по шагам

1. Опишите структуру `DLQRecord` с причиной отказа и историей попыток.
2. Реализуйте сервис `DeadLetterManager`, переводящий задачи в DLQ.
3. Реализуйте интерфейс нотификатора `ClientNotifier` (эмуляция отправки email).
4. Протестируйте обработку превышения лимита попыток и вызов нотификации.

## Код решения

**`dead_letter_queue.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type DLQRecord struct {
	DeliveryID string
	WebhookID  string
	EventID    string
	TargetURL  string
	TotalFails int
	LastHTTP   int
	LastError  string
	MovedAt    time.Time
}

type ClientNotifier interface {
	NotifyDeliveryFailed(ctx context.Context, record DLQRecord)
}

type EmailNotifier struct{}

func (n *EmailNotifier) NotifyDeliveryFailed(ctx context.Context, record DLQRecord) {
	fmt.Printf("[Email Alert to Merchant] WARNING: Webhook %s permanently failed after %d attempts! Target URL: %s. Last status: %d. Error: %s\n",
		record.WebhookID, record.TotalFails, record.TargetURL, record.LastHTTP, record.LastError)
}

type DeadLetterManager struct {
	mu       sync.Mutex
	records  []DLQRecord
	notifier ClientNotifier
}

func NewDeadLetterManager(n ClientNotifier) *DeadLetterManager {
	return &DeadLetterManager{notifier: n}
}

func (m *DeadLetterManager) MoveToDLQ(ctx context.Context, deliveryID, webhookID, eventID, targetURL string, fails, lastHTTP int, lastErr string) {
	record := DLQRecord{
		DeliveryID: deliveryID,
		WebhookID:  webhookID,
		EventID:    eventID,
		TargetURL:  targetURL,
		TotalFails: fails,
		LastHTTP:   lastHTTP,
		LastError:  lastErr,
		MovedAt:    time.Now().UTC(),
	}

	m.mu.Lock()
	m.records = append(m.records, record)
	m.mu.Unlock()

	fmt.Printf("[DLQ Engine] Moved event %s to Dead Letter Queue.\n", eventID)
	m.notifier.NotifyDeliveryFailed(ctx, record)
}

func main() {
	notifier := &EmailNotifier{}
	dlqManager := NewDeadLetterManager(notifier)

	ctx := context.Background()
	dlqManager.MoveToDLQ(ctx, "deliv_992", "sub_merch_01", "evt_order_881", "https://broken.merchant.com/hook", 6, 502, "Bad Gateway: upstream connect error")

	fmt.Printf("Total DLQ records: %d\n", len(dlqManager.records))
}
```

## Под капотом

События в DLQ хранятся в течение длительного срока (от 14 до 30 дней) в холодном хранилище. Это дает интегратору возможность исправить сбой в своем приложении, развернуть патч и затем одной кнопкой в UI запустить процедуру "Replay all DLQ events" без потери критических бизнес-данных.

## Подводные камни

1. Удаление событий без DLQ: безвозвратная потеря финансовых данных и жалобы клиентов.
2. Бесконечная отправка email на каждое упавшее событие: если упало 100 000 вебхуков, клиент получит 100 000 писем и отправит платформу в спам. Нотификации должны агрегироваться и снабжаться throttling (не более 1 письма в час на подписку).
3. Отсутствие TTL на хранение записей в DLQ: риск переполнения диска через несколько месяцев.

## На собеседовании

**Вопрос (Shopify/Stripe):** Как платформа должна поступить с подпиской мерчанта, если 100% его вебхуков в течение 48 часов падают в DLQ?
**Ответ:** Платформа переводит подписку в статус `auto_disabled` (автоматически приостановлена). Это:
1. Защищает инфраструктуру платформы от бессмысленной траты ресурсов на ретраи.
2. Защищает упавший сервер мерчанта от постоянного спама запросами.
3. Отправляет мерчанту уведомление с просьбой проверить доступность эндпоинта и повторно активировать подписку после устранения аварии.
