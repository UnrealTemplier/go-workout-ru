### Исходная формулировка

**Добавление случайного шума (Jitter)**: Если у клиента упал сервер, а затем восстановился, сотни запланированных повторных вебхуков со всех серверов вашей платформы могут одновременно ринуться к нему и обрушить его снова (проблема Thundering Herd). $$\text{Задержка} = \text{random}(0.5, 1.5) \times \left(2^{\text{попытка}} \times \text{базовый\_интервал}\right)$$

## Теория

Среди всех алгоритмов рандомизации задержек повторов особое место занимает **Decorrelated Jitter (Декоррелированное дрожание)**:
Каждый последующий интервал задержки вычисляется не от номера попытки `attempt`, а от **предыдущего фактического времени сна** \(T_{\text{prev}}\):
$$T_{i+1} = \min\Big(\text{cap}, \text{random\_between}(\text{base}, 3 \times T_i)\Big)$$
Преимущество Decorrelated Jitter:
- Задержка возрастает стохастически (случайным блужданием), что полностью исключает корреляцию даже между задачами, начавшимися с одного и того же события.
- Алгоритм не требует хранения точного номера попытки (достаточно передавать предыдущую задержку).
- Доказано исследователями, что Decorrelated Jitter обеспечивает наименьшее время восстановления при нестабильных сетях с плавающим джиттером.

## Код решения

**`decorrelated_jitter.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math/big"
	"time"
)

// DecorrelatedJitter: sleep = min(cap, rand(base, 3 * prevSleep))
func DecorrelatedJitter(prevSleep, base, capLimit time.Duration) time.Duration {
	low := int64(base)
	high := int64(3 * prevSleep)

	if high < low {
		high = low
	}

	delta := high - low
	if delta <= 0 {
		delta = 1
	}

	n, _ := rand.Int(rand.Reader, big.NewInt(delta+1))
	sleep := time.Duration(low + n.Int64())

	if sleep > capLimit {
		return capLimit
	}
	return sleep
}

func main() {
	base := 100 * time.Millisecond
	capLimit := 10 * time.Second

	fmt.Println("--- Simulating Decorrelated Jitter Sequence (3 independent runs) ---")

	for run := 1; run <= 3; run++ {
		fmt.Printf("Run #%d:\n", run)
		sleep := base
		for step := 1; step <= 6; step++ {
			sleep = DecorrelatedJitter(sleep, base, capLimit)
			fmt.Printf("  Step %d: %v\n", step, sleep.Round(time.Millisecond))
		}
	}
}
```

## Под капотом

Множитель 3 в формуле \(3 \times T_i\) выбран эмпирически в исследовании Amazon Web Services: он обеспечивает математическое ожидание роста \(\mathbb{E}[T_{i+1}] = \frac{1 + 3}{2} T_i = 2 T_i\), что точно соответствует коэффициенту экспоненциального удвоения классического бинарного бэк-оффа, но с полным устранением корреляции между параллельными потоками.

## Подводные камни

1. Неправильный диапазон случайного числа: если сгенерировать число от 0 до \(3 T_i\), задержка может упасть до единиц миллисекунд. Нижняя граница обязана быть не меньше `base`.
2. Отсутствие ограничения потолком `capLimit`.
3. Отрицательные значения при арифметическом переполнении.

## На собеседовании

**Вопрос (Amazon/Wildberries):** В каких случаях Decorrelated Jitter предпочтительнее Full Jitter?
**Ответ:** Decorrelated Jitter предпочтительнее в сценариях, когда клиентский сервис испытывает кратковременные сетевые сбои (flapping network) и способен быстро восстанавливаться. Он агрессивнее пробует доставить сообщение на ранних шагах, сокращая среднее время доставки (latency) по сравнению с Full Jitter, где задержка на любом шаге может случайно упасть до 0 миллисекунд.
