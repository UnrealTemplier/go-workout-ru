# Concurrent delivery limiting: ограничение параллелизма на хост через семафоры

## Условие

45. **Concurrent delivery limiting**: Ограничьте количество одновременных deliveries на один endpoint (например, не более 10). Иначе burst событий положит клиентский сервер.

### Исходная формулировка

**Concurrent delivery limiting**: Ограничьте количество одновременных deliveries на один endpoint (например, не более 10). Иначе burst событий положит клиентский сервер.

## Теория

Если у одного мерчанта происходит массовое событие (распродажа Black Friday — 50 000 заказов за секунду), платформа не должна открывать 50 000 одновременных TCP-соединений на сервер этого мерчанта.
Небольшой веб-сервер интегратора моментально упадет под DDoS от платформы!
Для защиты серверов подписчиков вводится ограничение параллелизма — **Per-Host Concurrency Limiting**:
Для каждого уникального хоста (`hostname`) создается семафор на базе буферизированного канала `chan struct{}` емкостью `max_concurrent_connections` (например, 10–20 параллельных запросов на хост).
Если все 20 слотов заняты, новые задачи для этого хоста ожидают или возвращаются в очередь, защищая инфраструктуру клиента.

## Решение по шагам

1. Создайте структуру `HostLimiter` с пулом семафоров по хостам.
2. Реализуйте метод `Acquire(host string) func()` возвращающий функцию освобождения слота.
3. Ограничьте число одновременных запросов числом 3.
4. Запустите 6 параллельных горутин и продемонстрируйте, что единовременно исполняются строго 3 запроса.

## Код решения

**`host_concurrency_limiter.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type HostConcurrencyLimiter struct {
	mu          sync.Mutex
	semaphores  map[string]chan struct{}
	maxPerHost  int
	activeConns int32
}

func NewHostConcurrencyLimiter(maxPerHost int) *HostConcurrencyLimiter {
	return &HostConcurrencyLimiter{
		semaphores: make(map[string]chan struct{}),
		maxPerHost: maxPerHost,
	}
}

func (l *HostConcurrencyLimiter) getSem(host string) chan struct{} {
	l.mu.Lock()
	defer l.mu.Unlock()
	sem, exists := l.semaphores[host]
	if !exists {
		sem = make(chan struct{}, l.maxPerHost)
		l.semaphores[host] = sem
	}
	return sem
}

func (l *HostConcurrencyLimiter) Execute(host string, fn func()) {
	sem := l.getSem(host)

	// Захват слота
	sem <- struct{}{}
	atomic.AddInt32(&l.activeConns, 1)

	defer func() {
		atomic.AddInt32(&l.activeConns, -1)
		<-sem // Освобождение слота
	}()

	fn()
}

func main() {
	limiter := NewHostConcurrencyLimiter(3) // Максимум 3 одновременных запроса на хост
	targetHost := "api.merchant-shop.ru"

	var wg sync.WaitGroup
	fmt.Printf("--- Dispatching 6 parallel deliveries to %s (Max Concurrency: 3) ---\n", targetHost)

	for i := 1; i <= 6; i++ {
		wg.Add(1)
		go func(taskID int) {
			defer wg.Done()
			limiter.Execute(targetHost, func() {
				active := atomic.LoadInt32(&limiter.activeConns)
				fmt.Printf("[Task %d] Running HTTP request (Active parallel on host: %d)\n", taskID, active)
				time.Sleep(50 * time.Millisecond) // эмуляция работы
				fmt.Printf("[Task %d] Completed.\n", taskID)
			})
		}(i)
	}

	wg.Wait()
	fmt.Println("All tasks finished respecting host concurrency limits.")
}
```

## Под капотом

Буферизованный канал `chan struct{}` емкостью \(N\) в Go выступает эффективным счетным семафором (Counting Semaphore). Запись `sem <- struct{}{}` аллоцирует ровно 0 байт памяти (структура `struct{}` имеет нулевой размер в рантайме), а планировщик Go усыпляет горутину без активного ожидания (busy wait), когда буфер заполнен.

## Подводные камни

1. Отсутствие таймаута на ожидание захвата семафора: если все слоты заняты, горутина воркера может зависнуть на `sem <- struct{}{}`. Необходимо использовать `select` с `ctx.Done()`.
2. Ограничение по URL вместо Host: если клиент зарегистрировал два URL `https://api.site.ru/hook1` и `https://api.site.ru/hook2`, ограничение должно действовать на общий хост `api.site.ru`.
3. Утечка каналов семафоров для динамических хостов.

## На собеседовании

**Вопрос (Stripe/Shopify):** Почему платформа вебхуков ограничивает параллелизм (concurrency) доставки на один хост мерчанта, даже если у мерчанта оплачен тариф с миллионами событий?
**Ответ:** Если не ограничить параллелизм на хост, платформа во время пика событий (например, распродажи) мгновенно откроет тысячи параллельных соединений к бэкенду мерчанта. Это переполнит пул соединений к БД мерчанта, исчерпает лимиты его Ingress/Nginx контроллера и приведет к HTTP 502/504 аварии на стороне клиента. Ограничение параллелизма (например, 25 одновременных сокетов) обеспечивает максимальную пропускную способность без риска обрушить клиентскую инфраструктуру.
