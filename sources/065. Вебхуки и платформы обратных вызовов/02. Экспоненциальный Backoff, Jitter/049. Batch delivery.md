# Batch delivery: пакетирование событий для снижения оверхеда сетевых сокетов

## Условие

49. **Batch delivery (опционально)**: Для high-volume клиентов группируйте события в batch webhook: `{"events": [...]}`. Снижает overhead в 100x.

### Исходная формулировка

**Batch delivery (опционально)**: Для high-volume клиентов группируйте события в batch webhook: `{"events": [...]}`. Снижает overhead в 100x.

## Теория

При отправке сотен тысяч событий одному и тому же корпоративному партнеру (например, крупному банку или маркетплейсу) индивидуальная отправка каждого события в отдельном HTTP POST запросе создает колоссальный оверхед:
- Миллионы TCP/TLS рукопожатий и заголовков.
- Перегрузка веб-сервера интегратора сотнями тысяч параллельных сокетов.
Паттерн **Batch Delivery (Пакетная доставка)** объединяет события в пачки:
```json
{
  "batch_id": "btc_9901",
  "events": [
    {"id": "evt_1", "type": "order.paid", "data": {...}},
    {"id": "evt_2", "type": "order.paid", "data": {...}}
  ]
}
```
События накапливаются в буфере по двум триггерам:
1. `max_batch_size` (например, 100 событий).
2. `flush_interval` (например, каждые 200 мс при неполном буфере).

## Решение по шагам

1. Создайте структуру `BatchCollector` с буфером и таймером сброса (`flush_interval`).
2. Реализуйте метод добавления события `AddEvent(evt WebhookPayload)`.
3. Сбрасывайте пачку при достижении лимита или по тикеру таймера.
4. Продемонстрируйте сборку 5 событий в единый пакет.

## Код решения

**`batch_delivery_collector.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type EventItem struct {
	ID   string `json:"id"`
	Type string `json:"type"`
	Data any    `json:"data"`
}

type EventBatch struct {
	BatchID   string      `json:"batch_id"`
	Timestamp int64       `json:"timestamp"`
	Events    []EventItem `json:"events"`
}

type BatchCollector struct {
	mu           sync.Mutex
	buffer       []EventItem
	maxSize      int
	flushTimeout time.Duration
	outputCh     chan EventBatch
	batchSeq     int
}

func NewBatchCollector(maxSize int, flushTimeout time.Duration) *BatchCollector {
	c := &BatchCollector{
		buffer:       make([]EventItem, 0, maxSize),
		maxSize:      maxSize,
		flushTimeout: flushTimeout,
		outputCh:     make(chan EventBatch, 10),
	}
	go c.timerLoop()
	return c
}

func (c *BatchCollector) Add(evt EventItem) {
	c.mu.Lock()
	defer c.mu.Unlock()

	c.buffer = append(c.buffer, evt)
	if len(c.buffer) >= c.maxSize {
		c.flushLocked()
	}
}

func (c *BatchCollector) timerLoop() {
	ticker := time.NewTicker(c.flushTimeout)
	defer ticker.Stop()

	for range ticker.C {
		c.mu.Lock()
		if len(c.buffer) > 0 {
			c.flushLocked()
		}
		c.mu.Unlock()
	}
}

func (c *BatchCollector) flushLocked() {
	c.batchSeq++
	batch := EventBatch{
		BatchID:   fmt.Sprintf("batch_%d", c.batchSeq),
		Timestamp: time.Now().Unix(),
		Events:    make([]EventItem, len(c.buffer)),
	}
	copy(batch.Events, c.buffer)
	c.buffer = c.buffer[:0] // Очищаем с сохранением капасити

	c.outputCh <- batch
}

func main() {
	collector := NewBatchCollector(3, 500*time.Millisecond)

	// Добавляем 5 событий: первые 3 сформируют батч по лимиту размера, остальные 2 — по таймеру
	for i := 1; i <= 5; i++ {
		collector.Add(EventItem{
			ID:   fmt.Sprintf("evt_%d", i),
			Type: "inventory.updated",
			Data: map[string]int{"qty": i * 10},
		})
	}

	// Читаем батчи из канала
	batch1 := <-collector.outputCh
	b1JSON, _ := json.Marshal(batch1)
	fmt.Printf("Flush 1 (Triggered by Size): %s\n", string(b1JSON))

	batch2 := <-collector.outputCh
	b2JSON, _ := json.Marshal(batch2)
	fmt.Printf("Flush 2 (Triggered by Timer): %s\n", string(b2JSON))
}
```

## Под капотом

Очистка среза `c.buffer = c.buffer[:0]` обнуляет длину, но сохраняет ранее выделенную емкость базового массива (capacity). При непрерывном потоке событий это полностью устраняет нагрузку на аллокатор кучи и сборщик мусора Go (Zero-allocation reuse).

## Подводные камни

1. Слишком большой размер пакета: при батче в 10 000 событий размер JSON может составить 50 МБ, что вызовет ошибку `413 Payload Too Large` на клиентском веб-сервере. Оптимальный размер батча — 50–500 событий.
2. Неполная обработка батча клиентом: если из 100 событий клиент обработал 99, а на одном упал, ретрай всего батча приведет к дублированию 99 событий. Требуется поддержка частичного подтверждения (Partial Acknowledgment).
3. Зависание событий при отсутствии таймера сброса.

## На собеседовании

**Вопрос (Kafka/Shopify):** Как клиент должен возвращать результат при обработке пакетного вебхука (Batch Webhook), если часть событий в батче упала?
**Ответ:** Применяется схема **Partial Batch Response**:
Вместо бинарного 200/500 сервер клиента возвращает структурированный JSON:
```json
{
  "acknowledged": ["evt_1", "evt_2"],
  "failed": [{"id": "evt_3", "error": "insufficient funds"}]
}
```
Платформа помечает `evt_1` и `evt_2` как успешно доставленные, а упавшее `evt_3` изолированно отправляет на ретрай в следующем батче, исключая повторную обработку успешных событий.
