# Jitter (обязательно!): добавление рандомизации в цикл повторов

## Условие

34. **Jitter (обязательно!)**: Добавьте случайный jitter (±20%) к каждому delay. Без jitter при массовом сбое все retries "схлопываются" в один момент и DoS-ят failing endpoint.

### Исходная формулировка

**Jitter (обязательно!)**: Добавьте случайный jitter (±20%) к каждому delay. Без jitter при массовом сбое все retries "схлопываются" в один момент и DoS-ят failing endpoint.

## Теория

Без Jitter распределенные очереди повторов гарантированно подвергаются волновому резонансу:
Если падение сети произошло в момент времени \(T\), то пачки сообщений перемещаются синхронными кластерами.
Добавление случайности (Jitter) обязательно в любой промышленной платформе доставки событий.
Формула с симметричным дрожанием (Proportional Jitter):
$$T_{\text{jittered}} = T \times (1 \pm \text{jitter\_ratio})$$
Например, при \(\text{jitter\_ratio} = 0.2\) (20%) задержка 10 секунд превращается в случайное значение в диапазоне \([8.0\text{с}, 12.0\text{с}]\).
Это разрушает фазовую синхронизацию очередей и делает поток сетевых запросов ламинарным.

## Решение по шагам

1. Реализуйте функцию `ApplyJitter(baseDuration time.Duration, jitterPercent float64) time.Duration`.
2. Сгенерируйте случайный коэффициент в диапазоне \([-\text{pct}, +\text{pct}]\).
3. Убедитесь, что результирующая задержка не становится отрицательной.
4. Продемонстрируйте разброс задержек для 5 независимых задач с одинаковым базовым интервалом.

## Код решения

**`proportional_jitter.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math/big"
	"time"
)

// ApplyJitter добавляет случайное отклонение +-jitterPct (например 0.2 = +-20%)
func ApplyJitter(base time.Duration, jitterPct float64) time.Duration {
	if jitterPct <= 0 {
		return base
	}

	// Диапазон: [1.0 - jitterPct, 1.0 + jitterPct]
	// Генерируем случайное число от 0 до 1000
	n, _ := rand.Int(rand.Reader, big.NewInt(1001))
	ratio := float64(n.Int64()) / 1000.0 // [0.0, 1.0]

	// Смещение: от -jitterPct до +jitterPct
	delta := (ratio*2.0 - 1.0) * jitterPct
	multiplier := 1.0 + delta

	result := time.Duration(float64(base) * multiplier)
	if result < 0 {
		return 0
	}
	return result
}

func main() {
	baseInterval := 10 * time.Second
	fmt.Printf("Base Interval: %v (+-20%% Jitter)\n", baseInterval)

	for i := 1; i <= 8; i++ {
		j := ApplyJitter(baseInterval, 0.20)
		fmt.Printf("Task %d retry delay: %v\n", i, j.Round(time.Millisecond))
	}
}
```

## Под капотом

Симметричный Jitter сохраняет математическое ожидание времени задержки равным \(\mathbb{E}[T_{\text{jittered}}] = T_{\text{base}}\), так как математическое ожидание симметричного отклонения равно нулю. Это позволяет прогнозировать среднюю скорость разгребания очереди повторов без сдвига суммарного времени доставки.

## Подводные камни

1. Jitter, приводящий к отрицательной задержке: при `jitterPct > 1.0` возможна ситуация `result < 0`. Обязательна проверка `if result < 0`.
2. Синхронизация генератора случайных чисел: `math/rand` без локального `rand.New(rand.NewSource(...))` имеет общий глобальный мьютекс, что создает contention при тысячах горутин. `crypto/rand` потокобезопасен и использует системные вызовы ядра.
3. Отсутствие Jitter в первой попытке.

## На собеседовании

**Вопрос (Яндекс/Wildberries):** Чем опасен глобальный мьютекс в старом пакете `math/rand` при расчете Jitter в 10 000 горутин?
**Ответ:** До Go 1.20 вызов глобальных функций `rand.Intn()` или `rand.Float64()` захватывал глобальный `sync.Mutex` в рантайме. При 10 000 параллельно работающих воркерах вебхуков этот мьютекс становился бутылочным горлышком: горутины тратили 80% процессорного времени на ожидание лока (lock contention), снижая общую пропускную способность диспетчера. В Go 1.22+ используется потокобезопасный `math/rand/v2` без глобальных блокировок.
