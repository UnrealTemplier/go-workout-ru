# Batch Webhooks: надежная схема пакетной отправки и обработка частичных сбоев

### Исходная формулировка

**Batch Webhooks.**: Реализуйте batch-режим: накапливайте события 500 мс или до 100 штук, отправляйте одним POST с массивом payloads. Приёмник обрабатывает атомарно (все или ни одного) или поштучно с индивидуальными статусами в ответе. Объясните throughput/latency компромисс.

## Теория

При проектировании Batch Webhooks схема пакета должна поддерживать:
1. Метаданные пакета: `batch_id`, `timestamp`, `events_count`.
2. Массив событий: `events: []Event`.
3. Контракт ответа интегратора (Partial Failure Contract):
Если из 10 событий 8 обработаны успешно, а 2 упали из-за временных сбоев интегратора (например, блокировка строки в БД), клиент возвращает:
```json
{
  "status": "partial_success",
  "processed_event_ids": ["evt_1", "evt_2", ...],
  "retryable_event_ids": ["evt_5", "evt_9"]
}
```
Диспетчер платформы помечает `processed_event_ids` как `SUCCESS`, а `retryable_event_ids` возвращает в очередь ретраев, предотвращая повторную доставку успешных событий.

## Решение по шагам

1. Создайте структуры `BatchRequest` и `BatchResponse`.
2. Реализуйте диспетчер, разбирающий частичный ответ клиента.
3. Разделите события на доставленные и требующие ретрая.
4. Продемонстрируйте обработку частичного сбоя батча.

## Код решения

**`batch_partial_failure.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Event struct {
	ID   string `json:"id"`
	Type string `json:"type"`
}

type BatchRequest struct {
	BatchID string  `json:"batch_id"`
	Events  []Event `json:"events"`
}

type BatchResponse struct {
	Status             string   `json:"status"` // success, partial_success, failed
	ProcessedEventIDs  []string `json:"processed_event_ids"`
	RetryableEventIDs  []string `json:"retryable_event_ids"`
}

func ProcessBatchResult(req BatchRequest, resp BatchResponse) (successCount int, retryCount int) {
	processedSet := make(map[string]bool)
	for _, id := range resp.ProcessedEventIDs {
		processedSet[id] = true
	}

	for _, evt := range req.Events {
		if processedSet[evt.ID] {
			fmt.Printf("[Batch Resolver] Event %s successfully processed. Marking DONE.\n", evt.ID)
			successCount++
		} else {
			fmt.Printf("[Batch Resolver] Event %s failed or marked retryable. Rescheduling.\n", evt.ID)
			retryCount++
		}
	}
	return successCount, retryCount
}

func main() {
	batch := BatchRequest{
		BatchID: "batch_4001",
		Events: []Event{
			{ID: "evt_101", Type: "order.created"},
			{ID: "evt_102", Type: "order.created"},
			{ID: "evt_103", Type: "order.created"},
		},
	}

	// Эмулируем ответ клиента: evt_101 и evt_103 успешно, evt_102 требует ретрая
	clientResponseJSON := []byte(`{
		"status": "partial_success",
		"processed_event_ids": ["evt_101", "evt_103"],
		"retryable_event_ids": ["evt_102"]
	}`)

	var clientResp BatchResponse
	_ = json.Unmarshal(clientResponseJSON, &clientResp)

	s, r := ProcessBatchResult(batch, clientResp)
	fmt.Printf("\nBatch Resolution: %d Success, %d Retried\n", s, r)
}
```

## Под капотом

Схема частичного подтверждения предотвращает лавинообразное дублирование событий. Если бы платформа повторно отправляла весь батч целиком при единичной ошибке, успешно обработанные 99 событий доставлялись бы снова и снова, многократно нагружая базу данных клиента.

## Подводные камни

1. Клиент вернул HTTP 500 без JSON тела: в этом случае весь батч вынужденно уходит на ретрай целиком, так как платформа не знает, какие события успели зафиксироваться.
2. Несоответствие ID событий в ответе: проверка пересечения множеств обязательна для защиты от ошибок в коде клиента.
3. Слишком длинный размер массива `events`.

## На собеседовании

**Вопрос (Shopify/Ozon):** Что делать, если клиентский сервер при пакетной отправке вернул HTTP 200 OK, но в JSON-ответе массив `processed_event_ids` не содержит половину отправленных событий?
**Ответ:** Все события, отсутствующие в списке явно подтвержденных (`processed_event_ids`), считаются недоставленными и немедленно ставятся на повторную отправку в следующем батче. Это строго следует принципу At-Least-Once доставки: лучше отправить дубликат, чем допустить потерю бизнес-события.
