# Жесткие таймауты: многоуровневая настройка TCP, TLS и HTTP таймаутов

## Условие

51. **Жесткие таймауты**: Клиентский сервер завис и не закрывает соединение. Если твой воркер будет висеть в ожидании, у тебя кончатся горутины. Оберни отправку вебхука в `context.WithTimeout(ctx, 3*time.Second)`. Никогда не жди клиента долго!

### Исходная формулировка

**Жесткие таймауты**: Клиентский сервер завис и не закрывает соединение. Если твой воркер будет висеть в ожидании, у тебя кончатся горутины. Оберни отправку вебхука в `context.WithTimeout(ctx, 3*time.Second)`. Никогда не жди клиента долго!

## Теория

При отправке запросов на сторонние клиентские серверы установка одного лишь общего `http.Client.Timeout` недостаточна для высоконагруженных систем.
Сетевой стек Go предоставляет гранулярную настройку таймаутов в `http.Transport`:
1. `net.Dialer.Timeout`: таймаут на установление TCP-соединения (3-way handshake). Рекомендуется 2–3 секунды.
2. `TLSHandshakeTimeout`: таймаут на криптографическое рукопожатие TLS 1.3 / SNI. Рекомендуется 3–4 секунды.
3. `ResponseHeaderTimeout`: максимальное время ожидания первых байт заголовков ответа после полной отправки запроса. Рекомендуется 5 секунд.
4. `http.Client.Timeout`: общий глобальный дедлайн на весь запрос от начала до конца (обычно 10 секунд).
Если клиент намеренно или случайно держит соединение открытым, но не отправляет заголовки (атака Slowloris), `ResponseHeaderTimeout` мгновенно прерывает сессию.

## Решение по шагам

1. Создайте специализированный HTTP-клиент с тюнингом всех четырех параметров таймаутов.
2. Реализуйте функцию безопасной отправки с дополнительным дедлайном через `context.WithTimeout`.
3. Протестируйте прерывание запроса на зависшем мок-сервере.

## Код решения

**`hard_timeouts.go`**

```go
package main

import (
	"bytes"
	"context"
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"time"
)

func NewHardenedWebhookClient() *http.Client {
	transport := &http.Transport{
		DialContext: (&net.Dialer{
			Timeout:   3 * time.Second,  // TCP Handshake
			KeepAlive: 30 * time.Second,
		}).DialContext,
		TLSHandshakeTimeout:   3 * time.Second,  // TLS Negotiation
		ResponseHeaderTimeout: 5 * time.Second,  // Ждем первый байт ответа
		ExpectContinueTimeout: 1 * time.Second,
		MaxIdleConns:          500,
		MaxIdleConnsPerHost:   50,
		IdleConnTimeout:       90 * time.Second,
	}

	return &http.Client{
		Transport: transport,
		Timeout:   10 * time.Second, // Общий лимит на весь запрос
	}
}

func main() {
	// Сервер, который принимает TCP, но висит и не отдает заголовки ответа
	hangingServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(10 * time.Second) // эмуляция зависания
		w.WriteHeader(http.StatusOK)
	}))
	defer hangingServer.Close()

	client := NewHardenedWebhookClient()

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	req, _ := http.NewRequestWithContext(ctx, http.MethodPost, hangingServer.URL, bytes.NewBufferString(`{}`))
	start := time.Now()
	_, err := client.Do(req)
	duration := time.Since(start)

	fmt.Printf("Request aborted after: %v\n", duration.Round(time.Millisecond))
	fmt.Printf("Error: %v\n", err)
}
```

## Под капотом

Под капотом `ResponseHeaderTimeout` запускает внутренний таймер в горутине `persistConn.readLoop()`. Если за отведенный интервал сокет не передал символы `\r\n\r\n` (конец HTTP-заголовков), рантайм закрывает TCP сокет вызовом `pc.close(errTimeout)`, возвращая управление без ожидания полного таймаута клиента.

## Подводные камни

1. Использование нулевого таймаута (`client.Timeout = 0`): гарантированная утечка горутин и сокетов при зависании стороннего сервера.
2. Слишком длинный `ResponseHeaderTimeout` (например, 60 секунд): забивает пул воркеров платформы.
3. Отсутствие контекстного дедлайна при формировании `http.RequestWithContext`.

## На собеседовании

**Вопрос (Cloudflare/Ozon):** Чем отличается `ResponseHeaderTimeout` от общего `client.Timeout`?
**Ответ:** `client.Timeout` измеряет время от момента вызова `client.Do()` до полного окончания вычитывания тела ответа (`resp.Body`). Если сторонний сервер вернул заголовки за 100 мс, но отдает тяжелое тело ответа со скоростью 1 байт в секунду, `ResponseHeaderTimeout` не сработает. `client.Timeout` защищает от медленной отдачи тела (Trickle attacks), а `ResponseHeaderTimeout` — от зависания на этапе ожидания начала ответа.
