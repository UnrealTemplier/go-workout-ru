# [Exponential Backoff]: реализация ретраев с таймерами time.Timer и контекстами

## Условие

43. **[Exponential Backoff]**: Если сервер-приемник вернул `500` или таймаут, реализуй ретраи: 1 попытка сразу, 2-я через 2 сек, 3-я через 4 сек, 4-я через 8 сек.

### Исходная формулировка

**[Exponential Backoff]**: Если сервер-приемник вернул `500` или таймаут, реализуй ретраи: 1 попытка сразу, 2-я через 2 сек, 3-я через 4 сек, 4-я через 8 сек.

## Теория

При реализации ретраев в Go-воркере частой ошибкой является использование блокирующего вызова `time.Sleep()`.
`time.Sleep` невозможно прервать при получении сигнала отмены контекста (`ctx.Done()`), что приводит к зависанию горутины при остановке сервиса (Graceful Shutdown).
Идиоматичный подход в Go:
1. Использование таймера `timer := time.NewTimer(delay)`.
2. Ожидание через `select`:
```go
select {
case <-ctx.Done():
    if !timer.Stop() { <-timer.C }
    return ctx.Err()
case <-timer.C:
    // Повторить попытку
}
```
Это гарантирует мгновенное прерывание ожидания ретрая при выключении пода или отмене родительской транзакции.

## Решение по шагам

1. Создайте функцию `RetryWithContext(ctx context.Context, maxAttempts int, baseDelay time.Duration, op func() error) error`.
2. В цикле попыток рассчитывайте экспоненциальную задержку.
3. Ожидайте истечения задержки через `time.NewTimer` и `select` с `ctx.Done()`.
4. Протестируйте досрочное прерывание ретрая через отмену контекста.

## Код решения

**`cancellable_backoff.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"math"
	"time"
)

func RetryWithContext(ctx context.Context, maxAttempts int, baseDelay time.Duration, op func(attempt int) error) error {
	for attempt := 1; attempt <= maxAttempts; attempt++ {
		err := op(attempt)
		if err == nil {
			return nil
		}

		if attempt == maxAttempts {
			return fmt.Errorf("exhausted all %d attempts, last error: %w", maxAttempts, err)
		}

		delay := time.Duration(float64(baseDelay) * math.Pow(2, float64(attempt-1)))
		fmt.Printf("[Attempt %d failed] Retrying in %v...\n", attempt, delay)

		timer := time.NewTimer(delay)
		select {
		case <-ctx.Done():
			if !timer.Stop() {
				select {
				case <-timer.C:
				default:
				}
			}
			return fmt.Errorf("retry loop cancelled by context: %w", ctx.Err())
		case <-timer.C:
			// Таймер истек, переходим к следующей попытке
		}
	}
	return nil
}

func main() {
	// 1. Тест с успешным восстановлением
	fmt.Println("--- Test 1: Succeed on attempt 3 ---")
	ctx1 := context.Background()
	_ = RetryWithContext(ctx1, 4, 100*time.Millisecond, func(attempt int) error {
		if attempt < 3 {
			return errors.New("temporary 503")
		}
		fmt.Printf("Attempt %d succeeded!\n", attempt)
		return nil
	})

	// 2. Тест с прерыванием по таймауту контекста
	fmt.Println("\n--- Test 2: Cancelled by context deadline ---")
	ctx2, cancel := context.WithTimeout(context.Background(), 250*time.Millisecond)
	defer cancel()

	err := RetryWithContext(ctx2, 5, 200*time.Millisecond, func(attempt int) error {
		return errors.New("persistent 500")
	})
	fmt.Printf("Final result: %v\n", err)
}
```

## Под капотом

Паттерн остановки таймера `if !timer.Stop() { select { case <-timer.C: default: } }` предотвращает утечку канала таймера в сборщике мусора Go при досрочном выходе из `select`. Если таймер уже успел выстрелить в момент отмены контекста, вычитывание из `timer.C` освобождает буфер.

## Подводные камни

1. Использование `time.Sleep()`: делает сервис нечувствительным к сигналам `SIGTERM` в Kubernetes, приводя к принудительному `SIGKILL` по истечении `terminationGracePeriodSeconds`.
2. Утечка таймеров при создании `time.After()` в бесконечном цикле: `time.After` не может быть остановлен до истечения своего срока, забивая память горутинами таймеров.
3. Пропуск дренажа канала `timer.C` после вызова `timer.Stop()`.

## На собеседовании

**Вопрос (Яндекс/VK):** В чем опасность использования `time.After(delay)` внутри циклов ретраев?
**Ответ:** `time.After` создает новый объект `time.Timer`, чей внутренний канал не освобождается сборщиком мусора до тех пор, пока таймер полностью не истечет. Если в цикле ретраев или селекте с коротким контекстом многократно вызывается `time.After(10 * time.Minute)`, в памяти будут скапливаться тысячи неосвобожденных таймеров, вызывая скрытую утечку памяти (Memory Leak). Всегда следует использовать явный `time.NewTimer` с последующим вызовом `timer.Stop()`.
