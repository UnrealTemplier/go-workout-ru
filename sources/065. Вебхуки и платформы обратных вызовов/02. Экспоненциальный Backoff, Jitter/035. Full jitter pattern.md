# Full jitter pattern: реализация каноничного алгоритма AWS Architecture

## Условие

### Исходная формулировка

**Full jitter pattern**: Используйте `delay = random(0, base * 2^attempt)` — более агрессивная версия jitter, рекомендованная AWS Architecture Blog.

## Теория

Каноничный паттерн **Full Jitter**, предложенный инженерами Amazon Web Services:
$$\text{temp} = \min(\text{cap}, \text{base} \times 2^{\text{attempt}})$$
$$\text{sleep} = \text{random\_between}(0, \text{temp})$$
В отличие от симметричного дрожания, Full Jitter выбирает случайную величину на всем интервале от нуля до текущего экспоненциального потолка.
Преимущества Full Jitter:
1. Полное отсутствие фазовой корреляции между очередями.
2. Суммарная задержка пачки сообщений минимальна, так как среднее время задержки составляет половину от верхнего предела (\(\frac{\text{temp}}{2}\)).
3. Мгновенная реакция при освобождении ресурсов: часть запросов попытается пройти почти сразу (\(sleep \to 0\)).

## Решение по шагам

1. Реализуйте алгоритм `AWSFullJitter(attempt int, base, capLimit time.Duration) time.Duration`.
2. Обеспечьте безопасную работу с `math/rand/v2` или `crypto/rand`.
3. Смоделируйте 1 000 попыток доставки и рассчитайте среднюю задержку.

## Код решения

**`aws_full_jitter.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math"
	"math/big"
	"time"
)

// AWSFullJitter реализует каноничный алгоритм AWS Architecture:
// sleep = random(0, min(cap, base * 2^attempt))
func AWSFullJitter(attempt int, base, capLimit time.Duration) time.Duration {
	maxInterval := float64(base) * math.Pow(2, float64(attempt))
	if maxInterval > float64(capLimit) {
		maxInterval = float64(capLimit)
	}

	maxNanos := int64(maxInterval)
	if maxNanos <= 0 {
		return 0
	}

	n, _ := rand.Int(rand.Reader, big.NewInt(maxNanos+1))
	return time.Duration(n.Int64())
}

func main() {
	base := 100 * time.Millisecond
	capLimit := 10 * time.Second

	fmt.Println("--- AWS Full Jitter per Attempt (5 samples each) ---")
	for attempt := 0; attempt <= 5; attempt++ {
		fmt.Printf("Attempt %d (Max possible: %v):\n  Samples: ", attempt, time.Duration(float64(base)*math.Pow(2, float64(attempt))))
		for s := 0; s < 5; s++ {
			d := AWSFullJitter(attempt, base, capLimit)
			fmt.Printf("%v ", d.Round(time.Millisecond))
		}
		fmt.Println()
	}
}
```

## Под капотом

Математическое доказательство AWS показывает, что Full Jitter минимизирует интеграл конкуренции за серверные ресурсы (Server Contention Time). При падении сервиса клиенты с Full Jitter создают гладкое равномерное распределение нагрузки от 0 до \(T_{\max}\), позволяя серверу интегратора спокойно подняться и прогреть свои кэши.

## Подводные камни

1. Забытый `+1` в `big.NewInt(maxNanos+1)`: функция `rand.Int(reader, max)` возвращает полуинтервал `[0, max-1)`. Чтобы верхняя граница была включена, требуется `+1`.
2. Начало отсчета `attempt` с 1 вместо 0: при `attempt = 0` задержка составляет `[0, base]`, что позволяет мгновенно повторить микросбой.
3. Отрицательные значения при переполнении `maxInterval`.

## На собеседовании

**Вопрос (Amazon/Ozon):** Почему Full Jitter считается лучшим алгоритмом повторов для распределенных вебхуков по сравнению с Decorrelated Jitter?
**Ответ:** Хотя Decorrelated Jitter быстрее доставляет отдельные сообщения при быстро восстанавливающихся сервисах, он имеет тенденцию агрессивно наращивать задержки при затяжных сбоях. Full Jitter статистически обеспечивает наименьшую совокупную нагрузку (total work) на серверную инфраструктуру и защищает падающий сервис от добивания повторными запросами.
