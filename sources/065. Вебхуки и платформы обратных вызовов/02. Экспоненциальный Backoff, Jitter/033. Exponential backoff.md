# Exponential backoff: математическая модель и конфигурация коэффициентов

## Условие

33. **Exponential backoff**: Реализуйте retries по формуле `delay = base * 2^attempt`: 1min, 5min, 30min, 2h, 8h, 24h, 3 days, 7 days (типичный Stripe schedule).

### Исходная формулировка

**Exponential backoff**: Реализуйте retries по формуле `delay = base * 2^attempt`: 1min, 5min, 30min, 2h, 8h, 24h, 3 days, 7 days (типичный Stripe schedule).

## Теория

Экспоненциальная шкала задержек настраивается тремя параметрами:
1. `initial_interval` (\(T_0\)): базовая задержка первой попытки (например, 500 мс или 1 с).
2. `multiplier` (\(M\)): коэффициент умножения (обычно 2.0).
3. `max_interval` (\(T_{\max}\)): потолок задержки (например, 30 минут или 2 часа).
Формула для попытки \(i \ge 1\):
$$T_i = \min(T_{\max}, T_0 \times M^{i-1})$$
Такая шкала гарантирует быстрое восстановление при кратковременных микро-сбоях сети (ретрай через 1–2 секунды успешен в 95% случаев) и бережное отношение к ресурсам при длительных авариях (паузы в десятки минут).

## Решение по шагам

1. Создайте структуру `BackoffConfig` с параметрами `InitialInterval`, `Multiplier`, `MaxInterval`, `MaxAttempts`.
2. Реализуйте метод `NextInterval(attempt int) time.Duration`.
3. Постройте таблицу задержек для 10 попыток подряд.
4. Продемонстрируйте корректную работу ограничения `MaxInterval`.

## Код решения

**`backoff_calculator.go`**

```go
package main

import (
	"fmt"
	"math"
	"time"
)

type BackoffConfig struct {
	InitialInterval time.Duration
	Multiplier      float64
	MaxInterval     time.Duration
	MaxAttempts     int
}

func (c *BackoffConfig) NextInterval(attempt int) time.Duration {
	if attempt <= 1 {
		return c.InitialInterval
	}

	factor := math.Pow(c.Multiplier, float64(attempt-1))
	interval := float64(c.InitialInterval) * factor

	if interval > float64(c.MaxInterval) || interval <= 0 {
		return c.MaxInterval
	}
	return time.Duration(interval)
}

func main() {
	cfg := BackoffConfig{
		InitialInterval: 500 * time.Millisecond,
		Multiplier:      2.0,
		MaxInterval:     15 * time.Minute,
		MaxAttempts:     10,
	}

	fmt.Printf("%-8s | %-15s | %-15s\n", "Attempt", "Interval", "Cumulative")
	fmt.Println("-------------------------------------------")

	var cumulative time.Duration
	for i := 1; i <= cfg.MaxAttempts; i++ {
		interval := cfg.NextInterval(i)
		cumulative += interval
		fmt.Printf("%-8d | %-15v | %-15v\n", i, interval, cumulative)
	}
}
```

## Под капотом

Проверка `interval <= 0` предотвращает ошибки при переполнении `float64` или переполнении разрядной сетки знакового `int64` типа `time.Duration`. При очень больших степенях (`math.Pow`) значение превысит `math.MaxInt64`, что в Go приведет к неопределенному поведению или отрицательному значению времени.

## Подводные камни

1. Мультипликатор меньше или равный единице (\(M \le 1.0\)): задержка перестанет расти, и сервис будет ретраить с постоянным интервалом.
2. Слишком много попыток с коротким интервалом: перегружает брокер очередей и базу данных.
3. Отсутствие суммарного таймаута жизни сообщения (Message TTL): сообщение не должно ретраиться неделями, стандартное время жизни задачи доставки — от 24 до 72 часов.

## На собеседовании

**Вопрос (VK/Avito):** Почему в распределенных системах мультипликатор бэк-оффа выбирают равным 2.0 (степень двойки), а не 1.5 или 3.0?
**Ответ:** Мультипликатор 2.0 — это классический алгоритм двоичного экспоненциального отката (Binary Exponential Backoff), пришедший из сетевого протокола Ethernet (CSMA/CD). Степень двойки оптимальна с точки зрения теории вероятностей: она достаточно быстро уводит систему от перегрузки (при 3.0 задержки росли бы слишком резко, лишая систему шанса на быстрое восстановление, а при 1.5 рост слишком медленный, сохраняющий риск перегрузки).
