# Custom headers per webhook: передача статических заголовков авторизации интегратора

## Условие

59. **Custom headers per webhook**: Позвольте клиентам задавать custom headers (например, `X-Api-Key` для их internal routing).

### Исходная формулировка

**Custom headers per webhook**: Позвольте клиентам задавать custom headers (например, `X-Api-Key` для их internal routing).

## Теория

Многие интеграционные сервисы (например, внутренние корпоративные шлюзы или legacy API) требуют передачи специфических заголовков авторизации:
- `Authorization: Bearer <api_token>`
- `X-API-Key: <key>`
- `X-Custom-Tenant-ID: <tenant>`
Платформа вебхуков должна позволять клиенту при настройке подписки задавать словарь пользовательских заголовков (`custom_headers: map[string]string`).
Правила безопасности:
1. Запрет переопределения системных заголовков (`Host`, `Content-Length`, `User-Agent`, `X-Webhook-*`).
2. Скрытие значений заголовков в UI (маскирование `Bearer *******`).
3. Защита от CRLF Injection: проверка значений заголовков на отсутствие символов перевода строки `\r` и `\n`.

## Решение по шагам

1. Создайте валидатор заголовков `ValidateCustomHeaders(headers map[string]string) error`.
2. Заблокируйте попытки перезаписи системных заголовков и внедрения CRLF.
3. Реализуйте внедрение заголовков в исходящий запрос `http.Request`.
4. Протестируйте отправку вебхука с Bearer-токеном.

## Код решения

**`custom_headers_delivery.go`**

```go
package main

import (
	"bytes"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

var prohibitedHeaders = map[string]bool{
	"host":                true,
	"content-length":      true,
	"x-webhook-signature": true,
	"x-webhook-timestamp": true,
	"connection":          true,
}

func ValidateCustomHeaders(headers map[string]string) error {
	for k, v := range headers {
		lowerK := strings.ToLower(strings.TrimSpace(k))
		if prohibitedHeaders[lowerK] {
			return fmt.Errorf("header %s is reserved and cannot be customized", k)
		}
		// Защита от HTTP Response Splitting / CRLF Injection
		if strings.ContainsAny(k, "\r\n") || strings.ContainsAny(v, "\r\n") {
			return errors.New("CRLF characters detected in header key or value")
		}
	}
	return nil
}

func SendWithCustomHeaders(targetURL string, payload []byte, customHeaders map[string]string) (*http.Response, error) {
	if err := ValidateCustomHeaders(customHeaders); err != nil {
		return nil, err
	}

	req, err := http.NewRequest(http.MethodPost, targetURL, bytes.NewReader(payload))
	if err != nil {
		return nil, err
	}

	req.Header.Set("Content-Type", "application/json")
	for k, v := range customHeaders {
		req.Header.Set(k, v)
	}

	return http.DefaultClient.Do(req)
}

func main() {
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		auth := r.Header.Get("Authorization")
		tenant := r.Header.Get("X-Tenant-ID")
		fmt.Printf("[Client Server] Received Auth: %s | Tenant: %s\n", auth, tenant)
		w.WriteHeader(http.StatusOK)
	}))
	defer server.Close()

	customHeaders := map[string]string{
		"Authorization": "Bearer secret_api_token_12345",
		"X-Tenant-ID":   "tenant_corp_alpha",
	}

	resp, err := SendWithCustomHeaders(server.URL, []byte(`{"event":"ping"}`), customHeaders)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	fmt.Printf("Delivery Status: %d\n", resp.StatusCode)
}
```

## Под капотом

Символы `\r` (CR) и `\n` (LF) в заголовках HTTP/1.1 позволяют злоумышленнику инжектировать произвольные HTTP-заголовки или фальсифицировать тело запроса (HTTP Header Injection / Response Splitting). Проверка `strings.ContainsAny(..., "\r\n")` предотвращает эту уязвимость на этапе валидации.

## Подводные камни

1. Разрешение переопределения `Host`: злоумышленник может подменить заголовок `Host`, вызвав сбой маршрутизации на виртуальных хостах Nginx.
2. Логирование значений `Authorization` в открытом виде в логах отправки: утечка токенов клиента в Elasticsearch.
3. Отсутствие ограничения на количество заголовков (не более 10) и их размер (не более 4 КБ суммарно).

## На собеседовании

**Вопрос (Shopify/VK):** Зачем клиентам передавать пользовательские заголовки, если у них уже есть проверка подписи HMAC?
**Ответ:** Многие enterprise-клиенты разворачивают свои приемники вебхуков за стандартными API Gateway (AWS API Gateway, Kong, Apisix), которые требуют передачи статического `X-API-Key` или JWT `Authorization: Bearer` для допуска запроса во внутреннюю сеть компании. Возможность указать custom headers позволяет интегратору использовать существующий API Gateway без необходимости писать кастомные прокси для обхода правил авторизации.
