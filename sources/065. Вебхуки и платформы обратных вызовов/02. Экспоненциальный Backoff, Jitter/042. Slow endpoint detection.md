# Slow endpoint detection: выявление медленных клиентов и выделение в Slow Lane

## Условие

42. **Slow endpoint detection**: Установите жесткий timeout на доставку (10-15 секунд). Slow endpoints не должны блокировать delivery других клиентов.

### Исходная формулировка

**Slow endpoint detection**: Установите жесткий timeout на доставку (10-15 секунд). Slow endpoints не должны блокировать delivery других клиентов.

## Теория

Одна из самых коварных проблем webhook-систем — **Slow Endpoints (Медленные клиенты)**.
Если здоровый клиент отвечает за 20 мс, а медленный интегратор обрабатывает запрос 4.9 секунды (при таймауте 5.0с), то медленный клиент занимает соединение и воркера в 250 раз дольше!
При всплеске событий медленные подписчики монополизируют весь пул воркеров, вызывая голодание (Starvation) и многоминутные задержки доставки для быстрых клиентов.
Решение — архитектурный паттерн **Traffic Segregation (Slow Lane / Fast Lane)**:
1. Система замеряет скользящую медиану времени ответа (p90/p99 latency) для каждого эндпоинта.
2. Если латентность эндпоинта превышает порог (например, > 1.5 с), он динамически помечается как `SLOW`.
3. Задачи для `SLOW` эндпоинтов маршрутизируются в отдельную изолированную очередь (Slow Queue) с ограниченным числом воркеров (например, 10% от общего пула), гарантируя 100% производительность быстрой магистрали (Fast Lane).

## Решение по шагам

1. Опишите структуру `EndpointLatencyTracker` со скользящим средним времени ответа.
2. Реализуйте метод `ClassifyLane(latency time.Duration) string` (FAST vs SLOW).
3. Создайте маршрутизатор задач `LaneRouter`, направляющий задачи в `fastQueue` или `slowQueue`.
4. Продемонстрируйте, что пачка медленных задач не задерживает выполнение быстрой задачи.

## Код решения

**`slow_endpoint_lane.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Lane string

const (
	LaneFast Lane = "FAST_LANE"
	LaneSlow Lane = "SLOW_LANE"
)

type LatencyStats struct {
	mu       sync.Mutex
	avgMS    int64
	samples  int
}

func (s *LatencyStats) Record(d time.Duration) {
	s.mu.Lock()
	defer s.mu.Unlock()
	ms := d.Milliseconds()
	if s.samples == 0 {
		s.avgMS = ms
		s.samples = 1
		return
	}
	// Скользящее среднее с коэффициентом затухания
	s.avgMS = (s.avgMS*4 + ms) / 5
	s.samples++
}

func (s *LatencyStats) GetLane(thresholdMS int64) Lane {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.samples >= 3 && s.avgMS > thresholdMS {
		return LaneSlow
	}
	return LaneFast
}

type LaneDispatcher struct {
	statsMap sync.Map // endpoint_id -> *LatencyStats
	fastCh   chan string
	slowCh   chan string
}

func NewLaneDispatcher(buf int) *LaneDispatcher {
	return &LaneDispatcher{
		fastCh: make(chan string, buf),
		slowCh: make(chan string, buf),
	}
}

func (d *LaneDispatcher) Route(endpointID, eventID string) Lane {
	val, _ := d.statsMap.LoadOrStore(endpointID, &LatencyStats{})
	stats := val.(*LatencyStats)

	lane := stats.GetLane(1000) // Порог медленного эндпоинта — 1000 мс
	if lane == LaneSlow {
		d.slowCh <- fmt.Sprintf("[%s] %s -> SLOW QUEUE", endpointID, eventID)
	} else {
		d.fastCh <- fmt.Sprintf("[%s] %s -> FAST QUEUE", endpointID, eventID)
	}
	return lane
}

func main() {
	dispatcher := NewLaneDispatcher(50)

	// Эмулируем замеры для медленного и быстрого клиентов
	slowVal, _ := dispatcher.statsMap.LoadOrStore("client_slow", &LatencyStats{})
	slowStats := slowVal.(*LatencyStats)
	slowStats.Record(2500 * time.Millisecond)
	slowStats.Record(3100 * time.Millisecond)
	slowStats.Record(2800 * time.Millisecond)

	fastVal, _ := dispatcher.statsMap.LoadOrStore("client_fast", &LatencyStats{})
	fastStats := fastVal.(*LatencyStats)
	fastStats.Record(30 * time.Millisecond)
	fastStats.Record(45 * time.Millisecond)
	fastStats.Record(25 * time.Millisecond)

	lane1 := dispatcher.Route("client_slow", "evt_001")
	lane2 := dispatcher.Route("client_fast", "evt_002")

	fmt.Printf("client_slow routed to: %s (msg: %s)\n", lane1, <-dispatcher.slowCh)
	fmt.Printf("client_fast routed to: %s (msg: %s)\n", lane2, <-dispatcher.fastCh)
}
```

## Под капотом

Выделение Slow Lane физически изолирует пулы горутин: быстрые события обслуживаются пулом из 100 воркеров с короткими таймаутами (1 сек), а медленные эндпоинты уходят в пул из 10 воркеров с расширенным таймаутом (10 сек). Это устраняет Head-of-Line Blocking на уровне прикладной платформы.

## Подводные камни

1. Классификация в Slow Lane по единичному замеру: разовый кратковременный всплеск задержки не должен переводить подписчика в медленную очередь. Требуется экспоненциальное скользящее среднее (EMA) или квантиль p90.
2. Отсутствие возврата в Fast Lane: если интегратор оптимизировал свой код, алгоритм обязан автоматически вернуть его в Fast Lane после серии быстрых ответов.
3. Переполнение медленной очереди: Slow Lane требует строгого rate limiting.

## На собеседовании

**Вопрос (Stripe/VK):** Что такое Head-of-Line (HoL) Blocking в очередях доставки вебхуков и как изоляция пулов воркеров решает эту проблему?
**Ответ:** Если все задачи доставки помещаются в единую общую очередь (FIFO), медленные задачи клиентов (время ответа 5–10 сек) занимают все слоты свободных воркеров. Быстрые задачи (время ответа 15 мс) вынуждены простаивать в хвосте очереди в ожидании освобождения воркеров. Изоляция пулов (Bulkhead pattern / Lanes) гарантирует, что медленные клиенты утилизируют строго отведенную им квоту ресурсов (например, не более 10% воркеров), обеспечивая нулевые задержки для 90% здоровых интеграторов.
