# Ретраи с Exponential Backoff и Jitter: полный производственный конвейер

## Условие

39. **Ретраи (повторная отправка) с Exponential Backoff и Jitter.**: Если получатель webhook возвращает ошибку 5xx или не отвечает, отправитель должен повторить попытку через 1с, 2с, 4с, 8с, 16с (с jitter ±15%). Реализуйте очередь повторов с ограничением максимального числа попыток.

### Исходная формулировка

**Ретраи (повторная отправка) с Exponential Backoff и Jitter.**: Если получатель webhook возвращает ошибку 5xx или не отвечает, отправитель должен повторить попытку через 1с, 2с, 4с, 8с, 16с (с jitter ±15%). Реализуйте очередь повторов с ограничением максимального числа попыток.

## Теория

Полный производственный цикл отправки вебхуков объединяет:
1. Классификацию кодов ответов (2xx — успех, 4xx — отказ без ретрая, 5xx/таймаут — ретрай).
2. Экспоненциальный рост задержки: \(T = \text{base} \times 2^{\text{attempt}}\).
3. Наложение Full Jitter для защиты от Thundering Herd.
4. Ограничение верхнего предела задержки (`maxCap`).
5. Перемещение в Dead Letter Queue при исчерпании `maxRetries`.

## Решение по шагам

1. Опишите законченный модуль доставки `DeliveryPipeline`.
2. Реализуйте функцию вычисления следующей попытки `NextAttemptDelay(attempt int) time.Duration`.
3. Реализуйте симуляцию доставки с автоматическим переходом между попытками.
4. Протестируйте жизненный цикл задачи от первой попытки до DLQ.

## Код решения

**`full_retry_pipeline.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math"
	"math/big"
	"time"
)

type RetryPolicy struct {
	BaseDelay  time.Duration
	MaxDelay   time.Duration
	MaxRetries int
}

func (p *RetryPolicy) ComputeDelay(attempt int) time.Duration {
	backoff := float64(p.BaseDelay) * math.Pow(2, float64(attempt))
	if backoff > float64(p.MaxDelay) {
		backoff = float64(p.MaxDelay)
	}

	maxNanos := int64(backoff)
	if maxNanos <= 0 {
		return 0
	}

	// Full Jitter: random(0, backoff)
	n, _ := rand.Int(rand.Reader, big.NewInt(maxNanos+1))
	return time.Duration(n.Int64())
}

type DeliveryTask struct {
	ID         string
	Attempt    int
	MaxRetries int
	State      string // PENDING, RETRYING, SUCCESS, DLQ
}

func ProcessDelivery(task *DeliveryTask, policy RetryPolicy, serverStatus int) {
	fmt.Printf("[%s] Executing attempt #%d...\n", task.ID, task.Attempt+1)

	if serverStatus >= 200 && serverStatus < 300 {
		task.State = "SUCCESS"
		fmt.Printf("  -> Result: 200 OK! Task completed.\n")
		return
	}

	task.Attempt++
	if task.Attempt >= policy.MaxRetries {
		task.State = "DLQ"
		fmt.Printf("  -> Result: Max retries reached (%d). Moved to Dead Letter Queue.\n", policy.MaxRetries)
		return
	}

	delay := policy.ComputeDelay(task.Attempt)
	task.State = "RETRYING"
	fmt.Printf("  -> Result: Error %d. Next retry scheduled with jitter in %v\n", serverStatus, delay.Round(time.Millisecond))
}

func main() {
	policy := RetryPolicy{
		BaseDelay:  200 * time.Millisecond,
		MaxDelay:   5 * time.Second,
		MaxRetries: 4,
	}

	task := &DeliveryTask{ID: "task_order_77", MaxRetries: 4, State: "PENDING"}

	// Эмулируем 3 ошибки 503 и затем 4-ю ошибку
	for task.State != "SUCCESS" && task.State != "DLQ" {
		ProcessDelivery(task, policy, 503)
	}
}
```

## Под капотом

При проектировании очереди повторов в базе данных колонка `next_retry_at` индексируется методом B-Tree:
`CREATE INDEX idx_webhooks_retry ON webhook_deliveries (next_retry_at) WHERE state = 'RETRYING';`
Наличие частичного индекса (Partial Index) гарантирует, что выборка созревших задач сканирует только активные ретраи, не затрагивая миллионы уже доставленных исторических строк.

## Подводные камни

1. Ретраи без задержки при первой ошибке: вызов немедленного ретрая при сетевом сбое (Immediate Retry) перегружает инфраструктуру при флапе сети.
2. Повторная отправка без проверки статуса отмены: если клиент удалил подписку, запланированные ретраи должны отменяться.
3. Отсутствие уникального индекса для дедупликации ретраев.

## На собеседовании

**Вопрос (Stripe/Ozon):** Почему полезно логировать не только факт ошибки, но и рассчитанный `jittered_delay` каждой попытки?
**Ответ:** При расследовании инцидентов и споров с интеграторами ("Почему ваш вебхук пришел только через 40 минут?") точный лог каждой попытки с миллисекундами задержки и кодами ответов позволяет визуализировать хронологию аварии и доказать, что платформа действовала строго по спецификации SLA.
