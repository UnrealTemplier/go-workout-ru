# Очередь отправки вебхуков: организация персистентной очереди с приоритетами

## Условие

37. **Очередь отправки вебхуков**: Прямая отправка вебхуков в основном потоке бизнес-логики заблокирует работу сервера при медленном ответе клиента. Напишите неблокирующую систему: при возникновении события в системе оно складывается в буферизованную очередь (или в топик брокера сообщений), а пул фоновых горутин-воркеров (Workers) последовательно вычитывает задачи и выполняет HTTP POST запросы к серверам клиентов.

Напишите неблокирующую систему: при возникновении события в системе оно складывается в буферизованную очередь (или в топик брокера сообщений), а пул фоновых горутин-воркеров (Workers) последовательно вычитывает задачи и выполняет HTTP POST запросы к серверам клиентов.

## Теория

В корпоративных системах вебхуки разделяются по приоритетам доставки:
1. **Critical / High Priority:** Финансовые транзакции (`payment.succeeded`, `fraud.detected`). Максимальное время доставки < 1 сек.
2. **Standard / Normal Priority:** Изменения профиля (`user.updated`, `cart.item_added`). Доставка за 5–30 сек.
3. **Bulk / Low Priority:** Массовый экспорт каталога или ночные синхронизации.
Для предотвращения ситуации, когда массовый экспорт 1 000 000 товаров заблокирует доставку срочных платежей, очередь организуется в несколько приоритетных очередей (Priority Lanes) с взвешенным распределением воркеров (Weighted Fair Queuing):
- 70% воркеров обслуживают High Priority.
- 20% воркеров — Standard.
- 10% воркеров — Low.

## Решение по шагам

1. Опишите структуру `PrioritizedWebhook` с полями `Priority` (High, Normal, Low), `Payload`, `TargetURL`.
2. Создайте многоканальный диспетчер `PriorityDispatcher`.
3. В цикле воркера используйте `select` с приоритетным опросом каналов (High опрашивается первым).
4. Продемонстрируйте, что высокоприоритетные события доставляются вне очереди.

## Код решения

**`priority_queue_dispatcher.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Priority int

const (
	PriorityLow Priority = iota
	PriorityNormal
	PriorityHigh
)

type WebhookMessage struct {
	ID        string
	Priority  Priority
	TargetURL string
	Event     string
}

type PriorityDispatcher struct {
	highCh   chan WebhookMessage
	normalCh chan WebhookMessage
	lowCh    chan WebhookMessage
	wg       sync.WaitGroup
	quit     chan struct{}
}

func NewPriorityDispatcher(bufSize int) *PriorityDispatcher {
	return &PriorityDispatcher{
		highCh:   make(chan WebhookMessage, bufSize),
		normalCh: make(chan WebhookMessage, bufSize),
		lowCh:    make(chan WebhookMessage, bufSize),
		quit:     make(chan struct{}),
	}
}

func (d *PriorityDispatcher) Enqueue(msg WebhookMessage) {
	switch msg.Priority {
	case PriorityHigh:
		d.highCh <- msg
	case PriorityNormal:
		d.normalCh <- msg
	case PriorityLow:
		d.lowCh <- msg
	}
}

func (d *PriorityDispatcher) StartWorker(id int) {
	d.wg.Add(1)
	go func() {
		defer d.wg.Done()
		for {
			// Приоритетная выборка: High опрашивается строго в первую очередь
			select {
			case <-d.quit:
				return
			case msg := <-d.highCh:
				d.process(id, "HIGH", msg)
				continue
			default:
			}

			select {
			case <-d.quit:
				return
			case msg := <-d.highCh:
				d.process(id, "HIGH", msg)
			case msg := <-d.normalCh:
				d.process(id, "NORMAL", msg)
			default:
				select {
				case <-d.quit:
					return
				case msg := <-d.highCh:
					d.process(id, "HIGH", msg)
				case msg := <-d.normalCh:
					d.process(id, "NORMAL", msg)
				case msg := <-d.lowCh:
					d.process(id, "LOW", msg)
				case <-time.After(20 * time.Millisecond):
				}
			}
		}
	}()
}

func (d *PriorityDispatcher) process(workerID int, queueName string, msg WebhookMessage) {
	fmt.Printf("[Worker %d] [%s QUEUE] Delivered Event %s (ID=%s)\n", workerID, queueName, msg.Event, msg.ID)
	time.Sleep(15 * time.Millisecond) // эмуляция сетевого вызова
}

func (d *PriorityDispatcher) Stop() {
	close(d.quit)
	d.wg.Wait()
}

func main() {
	dispatcher := NewPriorityDispatcher(100)

	// Заполняем очередь: сначала пачка Low, затем один High
	for i := 1; i <= 5; i++ {
		dispatcher.Enqueue(WebhookMessage{ID: fmt.Sprintf("low_%d", i), Priority: PriorityLow, Event: "catalog.export"})
	}
	dispatcher.Enqueue(WebhookMessage{ID: "crit_999", Priority: PriorityHigh, Event: "payment.succeeded"})

	dispatcher.StartWorker(1)

	time.Sleep(200 * time.Millisecond)
	dispatcher.Stop()
}
```

## Под капотом

В языке Go оператор `select` при наличии нескольких готовых каналов выбирает ветку **псевдослучайно** (псевдорандомизация для предотвращения starvation). Чтобы реализовать строгий приоритет (Strict Priority), применяется паттерн с вложенными `select` и веткой `default`: сначала проверяется только `highCh`, и лишь при его пустоте управление переходит к остальным каналам.

## Подводные камни

1. Стандартный `select` без каскада: если написать `select { case high: ... case low: ... }`, рантайм Go будет выбирать ветки с вероятностью 50/50, и приоритет будет потерян.
2. Голодание низкоприоритетной очереди (Starvation): если поток High-событий непрерывен, Low-очередь может не обработаться никогда. Необходим механизм Weighted Fair Queuing (например, гарантированно брать минимум 1 Low на каждые 10 High).
3. In-memory очереди без персистентности: при аварии задачи теряются.

## На собеседовании

**Вопрос (T-Банк/Ozon):** Как в Go реализовать Priority Queue на каналах, если стандартный `select` выбирает готовые каналы случайным образом?
**Ответ:** Применяется идиоматичный паттерн двухфазного селекта:
В первой фазе выполняется неблокирующий `select` только по приоритетному каналу с веткой `default`:
```go
select {
case msg := <-highCh:
    return msg
default:
}
```
Если в приоритетном канале есть данные, они возвращаются немедленно. И только если он пуст, вызывается блокирующий `select`, слушающий все каналы одновременно.
