# Jitter: предотвращение проблемы Thundering Herd при массовых сбоях сети

### Исходная формулировка

**Jitter.**: Добавьте к backoff случайную составляющую: Full Jitter (`random(0, base)`) или Equal Jitter (`base/2 + random(0, base/2)`). Сымитируйте 1000 одновременных failed webhooks и покажите, что pure exponential создаёт thundering herd, а jitter — распределяет нагрузку.

## Теория

Если при сбое внешнего сервиса или магистрального провайдера одновременно упало 50 000 доставок вебхуков, чистый экспоненциальный бэк-офф приведет к катастрофическому эффекту **Thundering Herd (Набегающее стадо)**.
Все 50 000 задач получат ровно одинаковые интервалы повторов:
- ровно через 1.0 сек: 50 000 одновременных запросов (первый всплеск).
- ровно через 2.0 сек: 50 000 одновременных запросов (второй всплеск).
- ровно через 4.0 сек: 50 000 одновременных запросов.
Такие циклические цунами трафика мгновенно добьют восстанавливающийся сервер клиента или сетевой шлюз.
Решение — добавление **Jitter (случайного дрожания)**: к рассчитанному интервалу добавляется псевдослучайное смещение, размазывающее запросы по времени равномерным слоем.

## Решение по шагам

1. Реализуйте алгоритм `CalculateBackoffWithJitter(attempt int, base, maxCap time.Duration) time.Duration`.
2. Используйте `crypto/rand` или `math/rand/v2` для генерации случайного коэффициента.
3. Продемонстрируйте статистическое распределение 10 000 вызовов: покажите, что запросы распределяются равномерно, а не синхронно в одну миллисекунду.

## Код решения

**`jitter_simulation.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math"
	"math/big"
	"time"
)

// FullJitter вычисляет задержку по формуле: sleep = rand(0, min(cap, base * 2^attempt))
func FullJitter(attempt int, baseDelay, maxCap time.Duration) time.Duration {
	backoff := float64(baseDelay) * math.Pow(2, float64(attempt))
	if backoff > float64(maxCap) {
		backoff = float64(maxCap)
	}

	maxNanos := int64(backoff)
	if maxNanos <= 0 {
		return baseDelay
	}

	// Равномерно распределенный случайный интервал от 0 до maxNanos
	n, _ := rand.Int(rand.Reader, big.NewInt(maxNanos))
	return time.Duration(n.Int64())
}

func main() {
	base := 1 * time.Second
	capLimit := 30 * time.Second
	attempt := 4 // base * 2^4 = 16 секунд

	fmt.Printf("--- Calculating 10 retry delays for attempt %d (Cap: %v) ---\n", attempt, capLimit)
	for i := 1; i <= 10; i++ {
		delay := FullJitter(attempt, base, capLimit)
		fmt.Printf("Sample %2d: %v\n", i, delay.Round(time.Millisecond))
	}
}
```

## Под капотом

Статья AWS Architecture Blog "Exponential Backoff And Jitter" математически доказывает, что Full Jitter снижает суммарное время ожидания очереди (Client Workload) и полностью устраняет циклические пики утилизации CPU на серверах-приемниках при массовых инцидентах доступности.

## Подводные камни

1. Использование фиксированного Jitter (например, ровно +500мс ко всем запросам): это просто сдвигает фазу шторма на полсекунды, не устраняя резонанс.
2. Неинициализированный генератор `math/rand`: до Go 1.20 `rand.Seed(time.Now().UnixNano())` был обязателен, иначе все инстансы воркеров генерировали одинаковые псевдослучайные последовательности. Начиная с Go 1.22 рекомендуется `math/rand/v2` или `crypto/rand`.
3. Jitter, превышающий SLA доставки: задержка не должна бесконтрольно расти за пределы бизнес-ограничений.

## На собеседовании

**Вопрос (Amazon/Ozon):** В чем разница между Full Jitter, Equal Jitter и Decorrelated Jitter?
**Ответ:**
1. **Full Jitter:** \(T = \text{random}(0, \min(\text{cap}, \text{base} \cdot 2^a))\). Максимальное размазывание по времени, лучший выбор для независимых вебхуков.
2. **Equal Jitter:** Половина задержки фиксирована, вторая половина случайна: \(T = \frac{\text{temp}}{2} + \text{random}(0, \frac{\text{temp}}{2})\). Гарантирует минимальный шаг ожидания.
3. **Decorrelated Jitter:** Каждая следующая задержка зависит от предыдущей: \(T_{i+1} = \min(\text{cap}, \text{random}(\text{base}, 3 \cdot T_i))\). Оптимально для соединений с высокими колебаниями задержек.
