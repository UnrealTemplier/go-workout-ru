# [Jitter (Дрожание)]: сглаживание сетевого трафика в цикле диспетчеризации

### Исходная формулировка

**[Jitter (Дрожание)]**: Добавь случайную задержку (jitter) к экспоненциальному backoff (например, `delay + rand(0, 500ms)`). Объясни, почему это критически важно, если у тебя 1000 вебхуков упало одновременно (предотвращение "thundering herd").

## Теория

При проектировании высоконагруженного диспетчера доставки вебхуков добавление случайного шума (Jitter) защищает не только серверы интеграторов, но и **собственные сетевые интерфейсы платформы**.
Если 10 000 вебхуков одновременно завершились с ошибкой в 12:00:00, то без Jitter в 12:00:01 сетевой интерфейс платформы испытает импульсный скачок (Micro-burst) исходящего трафика:
- Всплеск буфера сокетов (Socket Buffer Overflow).
- Дроп пакетов на уровне виртуального коммутатора Kubernetes (CNI Cilium/Calico).
- Резкий рост latency в рантайме Go.
Jitter преобразует импульсный ступенчатый график исходящего трафика в гладкую горизонтальную прямую.

## Решение по шагам

## Код решения

**`traffic_smoothing_jitter.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"math/big"
	"sync"
	"time"
)

func JitteredDelay(base time.Duration, maxCap time.Duration) time.Duration {
	maxNanos := int64(maxCap)
	if maxNanos <= 0 {
		return base
	}
	n, _ := rand.Int(rand.Reader, big.NewInt(maxNanos))
	return time.Duration(n.Int64())
}

func main() {
	var wg sync.WaitGroup
	totalTasks := 10
	baseInterval := 100 * time.Millisecond
	capLimit := 500 * time.Millisecond

	startTime := time.Now()
	fmt.Println("--- Starting 10 retried webhook deliveries with Jitter ---")

	for i := 1; i <= totalTasks; i++ {
		wg.Add(1)
		go func(taskID int) {
			defer wg.Done()
			delay := JitteredDelay(baseInterval, capLimit)
			time.Sleep(delay)
			elapsed := time.Since(startTime).Milliseconds()
			fmt.Printf("[Task %2d] Dispatched after %d ms delay (Total elapsed: %d ms)\n", taskID, delay.Milliseconds(), elapsed)
		}(i)
	}

	wg.Wait()
	fmt.Println("All tasks smoothly dispatched.")
}
```

## Под капотом

Размазывание трафика снижает вероятность переполнения очередей сетевых карт (Ring Buffers). В Linux сетевые драйверы (например, `ixgbe` или виртуальный `virtio_net`) имеют ограниченный размер очереди дескрипторов передачи (`tx_ring`). Микро-всплески трафика приводят к ошибкам `tx_dropped`, которые полностью устраняются с помощью Jitter.

## Подводные камни

1. Jitter, увеличивающий задержку за рамки допустимого SLA: случайная задержка должна быть ограничена жестким верхним лимитом `capLimit`.
2. Блокирующий `rand.Int` при дефиците энтропии ОС: `crypto/rand` в современном Linux никогда не блокируется после инициализации ядра.
3. Отсутствие логирования фактической задержки.

## На собеседовании

**Вопрос (Яндекс/Avito):** Почему Jitter важен не только для клиентского сервера, но и для балансировщиков нагрузки (Load Balancers) самой платформы отправки?
**Ответ:** Балансировщики нагрузки (Envoy, Nginx, AWS ALB) отслеживают состояние соединений по таблицам Conntrack в ядре Linux. Резкий синхронный выброс 50 000 одновременных TCP SYN пакетов за 1 миллисекунду может переполнить таблицу `nf_conntrack` ядра ОС (`nf_conntrack: table full, dropping packet`), что вызовет сетевой отказ всей платформы. Jitter размазывает исходящие пакеты равномерно, удерживая размер таблицы соединений на стабильном уровне.
