# Базовый Webhook Dispatcher: каналы, горутины и конкурентная обработка

## Условие

4. **Базовый Webhook Dispatcher**: Напиши воркер (горутину), который читает события из канала (например, `OrderPaid`), сериализует их в JSON и делает `http.Post` на URL, сохраненный в настройках клиента.

### Исходная формулировка

**Базовый Webhook Dispatcher**: Напиши воркер (горутину), который читает события из канала (например, `OrderPaid`), сериализует их в JSON и делает `http.Post` на URL, сохраненный в настройках клиента.

## Теория

Webhook Dispatcher — это асинхронный компонент архитектуры, который изолирует обработчики входящих HTTP-запросов бизнес-приложения от процесса сетевой отправки уведомлений сторонним подписчикам.
Если отправлять вебхуки синхронно внутри обработчика заказа (например, `POST /checkout`), медленный сторонний сервер клиента (задержка 5 секунд) заблокирует системный поток/горутину API, приведет к исчерпанию соединений к базе данных и вызовет каскадный отказ (cascading failure) всей платформы.
В Go простейший диспетчер строится на базе буферизированных каналов (`chan WebhookTask`), пула воркеров-горутин и контекстов отмены (`context.Context`).

## Решение по шагам

1. Опишите структуру задачи доставки `DeliveryTask` (событие, target URL, secret).
2. Реализуйте диспетчер `WebhookDispatcher`, управляющий пулом воркеров.
3. Реализуйте функцию воркера, которая вычитывает задачи из канала до его закрытия и выполняет `http.Post`.
4. Реализуйте метод `GracefulStop()`, ожидающий завершения текущих задач через `sync.WaitGroup`.

## Код решения

**`dispatcher_worker.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type OrderPaidEvent struct {
	OrderID   string  `json:"order_id"`
	UserID    string  `json:"user_id"`
	Amount    float64 `json:"amount"`
	Timestamp int64   `json:"timestamp"`
}

type DeliveryTask struct {
	TargetURL string
	Event     OrderPaidEvent
}

type WebhookDispatcher struct {
	taskChan chan DeliveryTask
	wg       sync.WaitGroup
	client   *http.Client
}

func NewWebhookDispatcher(bufferSize int, workers int) *WebhookDispatcher {
	d := &WebhookDispatcher{
		taskChan: make(chan DeliveryTask, bufferSize),
		client:   &http.Client{Timeout: 5 * time.Second},
	}
	for i := 1; i <= workers; i++ {
		d.wg.Add(1)
		go d.worker(i)
	}
	return d
}

func (d *WebhookDispatcher) worker(id int) {
	defer d.wg.Done()
	for task := range d.taskChan {
		d.deliver(id, task)
	}
}

func (d *WebhookDispatcher) deliver(workerID int, task DeliveryTask) {
	body, err := json.Marshal(task.Event)
	if err != nil {
		fmt.Printf("[Worker %d] Serialization error: %v\n", workerID, err)
		return
	}

	req, err := http.NewRequest(http.MethodPost, task.TargetURL, bytes.NewReader(body))
	if err != nil {
		fmt.Printf("[Worker %d] Request creation error: %v\n", workerID, err)
		return
	}
	req.Header.Set("Content-Type", "application/json")

	resp, err := d.client.Do(req)
	if err != nil {
		fmt.Printf("[Worker %d] Failed to deliver to %s: %v\n", workerID, task.TargetURL, err)
		return
	}
	resp.Body.Close()
	fmt.Printf("[Worker %d] Successfully delivered order %s -> status %d\n", workerID, task.Event.OrderID, resp.StatusCode)
}

func (d *WebhookDispatcher) Enqueue(task DeliveryTask) {
	d.taskChan <- task
}

func (d *WebhookDispatcher) Stop() {
	close(d.taskChan)
	d.wg.Wait()
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	}))
	defer ts.Close()

	dispatcher := NewWebhookDispatcher(100, 3)

	for i := 1; i <= 5; i++ {
		dispatcher.Enqueue(DeliveryTask{
			TargetURL: ts.URL,
			Event: OrderPaidEvent{
				OrderID:   fmt.Sprintf("ord_%d", 100+i),
				UserID:    fmt.Sprintf("usr_%d", i),
				Amount:    float64(i * 1500),
				Timestamp: time.Now().Unix(),
			},
		})
	}

	dispatcher.Stop()
	fmt.Println("Dispatcher gracefully stopped.")
}
```

## Под капотом

Использование паттерна Worker Pool предотвращает неконтролируемый рост горутин (Goroutine Explosion). Если бы на каждое событие создавалась новая горутина `go d.deliver(...)`, при всплеске нагрузки (100k событий/сек) рантайм Go создал бы сотни тысяч горутин, что вызвало бы исчерпание памяти (каждая горутина требует минимум 2 КБ стека), насыщение планировщика GMP и падение по OOM.

## Подводные камни

1. Потеря задач в памяти при аварийном перезапуске: каналы Go живут только в оперативной памяти процесса. Для продакшн-систем задачи должны сохраняться в устойчивом брокере (Kafka, Redis, Postgres Outbox).
2. Блокировка вызова `Enqueue`: если буфер канала переполнен, отправляющий поток заблокируется. Необходимо использовать `select` с веткой `default` для отслеживания backpressure или переполнения.
3. Отсутствие таймаута при остановке (`Graceful Shutdown`): если сторонний сервер не отвечает, `Stop()` может зависнуть до истечения HTTP-таймаута.

## На собеседовании

**Вопрос (T-Банк/Ozon):** Что произойдет, если в диспетчере на каналах Go сервер получит сигнал SIGTERM во время высокой нагрузки?
**Ответ:** Если не реализован Graceful Shutdown через закрытие канала и ожидание `sync.WaitGroup`, все задачи, находящиеся в буфере канала, будут безвозвратно утеряны. Для защиты от потери данных in-memory очереди дополняют персистентным хранилищем (Transactional Outbox в PostgreSQL), а воркеры фиксируют статус доставки в БД только после подтверждения HTTP-ответа.
