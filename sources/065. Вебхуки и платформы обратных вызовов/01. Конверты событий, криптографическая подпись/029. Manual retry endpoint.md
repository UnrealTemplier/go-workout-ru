# Manual retry endpoint: API ручного перезапуска доставки вебхуков

## Условие

29. **Manual retry endpoint**: Дайте клиентам кнопку "Retry" для failed webhook delivery. Это критично для debugging.

### Исходная формулировка

**Manual retry endpoint**: Дайте клиентам кнопку "Retry" для failed webhook delivery. Это критично для debugging.

## Теория

Когда эндпоинт клиента долгое время лежал (например, авария в ЦОД клиента длилась 12 часов), все автоматические попытки Exponential Backoff исчерпываются, и события перемещаются в очередь недоставленных сообщений (**Dead Letter Queue / DLQ**).
После устранения аварии интегратор не должен терять события. Платформа обязана предоставить административный API ручного перезапуска:
`POST /webhooks/deliveries/{id}/retry` или пакетный `POST /webhooks/subscriptions/{id}/retry_all_dead`
Этот API:
1. Загружает оригинальное событие и подписку из БД.
2. Сбрасывает счетчик попыток `attempt_count = 0`.
3. Меняет статус с `DEAD_LETTER` на `PENDING`.
4. Ставит задачу в приоритетную очередь доставки диспетчера.

## Решение по шагам

1. Опишите модель задачи доставки в DLQ.
2. Реализуйте HTTP-обработчик `POST /api/webhooks/deliveries/{id}/retry`.
3. Проверьте валидность состояния (повторять можно только завершившиеся с ошибкой задачи).
4. Сбросьте статус задачи и отправьте её в канал воркера доставки.
5. Протестируйте ручной перезапуск через `httptest`.

## Код решения

**`manual_retry_api.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"time"
)

type DeliveryItem struct {
	ID        string    `json:"id"`
	EventID   string    `json:"event_id"`
	TargetURL string    `json:"target_url"`
	Status    string    `json:"status"` // PENDING, SUCCESS, DEAD_LETTER
	Attempts  int       `json:"attempts"`
	UpdatedAt time.Time `json:"updated_at"`
}

type DeliveryService struct {
	mu       sync.Mutex
	store    map[string]*DeliveryItem
	retryCh  chan string
}

func (s *DeliveryService) ManualRetryHandler(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}

	// Извлекаем ID из URL: /webhooks/deliveries/{id}/retry
	path := strings.Trim(r.URL.Path, "/")
	parts := strings.Split(path, "/")
	if len(parts) < 3 {
		http.Error(w, "Invalid URL path", http.StatusBadRequest)
		return
	}
	deliveryID := parts[2]

	s.mu.Lock()
	item, exists := s.store[deliveryID]
	if !exists {
		s.mu.Unlock()
		http.Error(w, "Delivery task not found", http.StatusNotFound)
		return
	}

	if item.Status != "DEAD_LETTER" && item.Status != "FAILED" {
		s.mu.Unlock()
		http.Error(w, fmt.Sprintf("Cannot retry delivery in status: %s", item.Status), http.StatusConflict)
		return
	}

	// Сброс состояния для повторной доставки
	item.Status = "PENDING"
	item.Attempts = 0
	item.UpdatedAt = time.Now().UTC()
	s.mu.Unlock()

	// Постановка в очередь
	s.retryCh <- deliveryID

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusAccepted)
	_ = json.NewEncoder(w).Encode(map[string]any{
		"message":     "Manual retry enqueued successfully",
		"delivery_id": deliveryID,
		"status":      "PENDING",
	})
}

func main() {
	service := &DeliveryService{
		store: map[string]*DeliveryItem{
			"deliv_dead_99": {
				ID:        "deliv_dead_99",
				EventID:   "evt_001",
				TargetURL: "https://api.merchant.ru/wh",
				Status:    "DEAD_LETTER",
				Attempts:  5,
				UpdatedAt: time.Now().Add(-2 * time.Hour),
			},
		},
		retryCh: make(chan string, 10),
	}

	ts := httptest.NewServer(http.HandlerFunc(service.ManualRetryHandler))
	defer ts.Close()

	// Выполняем ручной ретрай
	req, _ := http.NewRequest(http.MethodPost, ts.URL+"/webhooks/deliveries/deliv_dead_99/retry", nil)
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	var res map[string]any
	_ = json.NewDecoder(resp.Body).Decode(&res)
	fmt.Printf("HTTP Status: %d | Response: %v\n", resp.StatusCode, res)

	// Проверяем, что задача упала в канал отправки
	enqueuedID := <-service.retryCh
	fmt.Printf("Task %s successfully routed to dispatcher queue!\n", enqueuedID)
}
```

## Под капотом

Статус ответа `202 Accepted` согласно RFC 9110 сообщает клиенту, что запрос принят в обработку, но сама сетевая доставка еще не завершена. Это предотвращает блокировку интерфейса оператора поддержки при массовом ретрае тысяч зависших вебхуков.

## Подводные камни

1. Разрешение ручного ретрая для уже успешных доставок (`SUCCESS`): если администратор случайно нажмет кнопку retry для доставленного события, интегратор получит сетевой дубликат.
2. Отсутствие Rate Limiting на manual retry endpoint: оператор или бот может положить сторонний сервер клиента, отправив 50 000 повторов одновременно.
3. Повторная отправка с устаревшим `X-Webhook-Timestamp`: при ручном перезапуске подпись и timestamp обязаны генерироваться заново от текущего времени, иначе клиент отклонит запрос по проверке Clock Skew.

## На собеседовании

**Вопрос (Ozon/Wildberries):** При ручном перезапуске старого вебхука (прошло 2 дня), должен ли отправитель использовать оригинальный `event.created_at` или текущий `timestamp` в подписи?
**Ответ:**
- В теле события `event.created_at` сохраняется оригинальное время возникновения бизнес-факта (2 дня назад), чтобы клиент сохранил историческую правду в своей учетной системе.
- В HTTP-заголовках безопасности (`X-Webhook-Timestamp` и HMAC-подписи) используется **текущее время** момента фактической отправки сетевого пакета. Если передать в заголовок старое время, клиентский бэкенд немедленно отклонит вебхук как устаревший по проверке Clock Skew (> 5 минут).
