# HMAC-подпись на стороне отправителя: безопасная сборка заголовков и канонизация

## Условие

13. **HMAC-подпись на стороне отправителя**: Чтобы злоумышленники не прислали ложные данные на сервер вашего клиента, все вебхуки должны подписываться. Напишите функцию на стороне вашей платформы, которая:
    * Вычисляет HMAC-SHA256 подпись от тела запроса (`Payload`) с использованием секретного ключа клиента.
    * Добавляет временную метку (timestamp) в заголовок `X-Webhook-Timestamp` (для защиты от Replay-атак — повторной отправки перехваченного валидного запроса).
    * Склеивает метку и тело запроса для вычисления подписи и упаковывает результат в заголовок `X-Webhook-Signature`.

### Исходная формулировка

**HMAC-подпись на стороне отправителя**: Чтобы злоумышленники не прислали ложные данные на сервер вашего клиента, все вебхуки должны подписываться. Напишите функцию на стороне вашей платформы, которая:
* Вычисляет HMAC-SHA256 подпись от тела запроса (`Payload`) с использованием секретного ключа клиента.
* Добавляет временную метку (timestamp) в заголовок `X-Webhook-Timestamp` (для защиты от Replay-атак — повторной отправки перехваченного валидного запроса).
* Склеивает метку и тело запроса для вычисления подписи и упаковывает результат в заголовок `X-Webhook-Signature`.

## Теория

Для исключения ошибок интеграции платформа должна предоставлять четкий каноничный формат подписи:
1. Метка времени передается в `X-Webhook-Timestamp`.
2. Подпись формируется строго по формуле `HMAC-SHA256(secret, timestamp + "." + payload)`.
3. Результат передается в заголовке `X-Webhook-Signature` со схемой `t=<timestamp>,v1=<hex_signature>`.
Такой формат (аналогичный Stripe Webhooks v1) решает сразу три задачи:
- Позволяет клиенту извлечь `timestamp` прямо из заголовка подписи без необходимости парсить тело JSON.
- Указывает версию схемы подписи (`v1`), давая возможность одновременно передавать `v2` в будущем.
- Исключает неконсистентность при передаче заголовков через прокси/WAF, которые могут изменять регистр имен HTTP-заголовков.

## Решение по шагам

1. Реализуйте функцию `SignPayload(payload []byte, secret string) (headerName, headerValue, timestamp string)`.
2. Получите текущий Unix timestamp.
3. Сформируйте склеенную строку `timestamp + "." + string(payload)`.
4. Рассчитайте HMAC-SHA256 хэш и сформируйте заголовок `X-Webhook-Signature: t=<ts>,v1=<hex>`.
5. Продемонстрируйте работу на примере.

## Код решения

**`canonical_signer.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strconv"
	"time"
)

type SignedHeaders struct {
	Timestamp string
	Signature string
}

func SignWebhookPayload(payload []byte, secret string, t time.Time) SignedHeaders {
	tsStr := strconv.FormatInt(t.UTC().Unix(), 10)

	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write([]byte(tsStr))
	mac.Write([]byte("."))
	mac.Write(payload)
	sigHex := hex.EncodeToString(mac.Sum(nil))

	return SignedHeaders{
		Timestamp: tsStr,
		Signature: fmt.Sprintf("t=%s,v1=%s", tsStr, sigHex),
	}
}

func main() {
	secret := "whsec_live_secret_key_888999"
	body := []byte(`{"event_id":"evt_01","type":"customer.created","data":{"id":"cust_42"}}`)

	headers := SignWebhookPayload(body, secret, time.Now())
	fmt.Printf("X-Webhook-Timestamp: %s\n", headers.Timestamp)
	fmt.Printf("X-Webhook-Signature: %s\n", headers.Signature)
}
```

## Под капотом

Запись в `hash.Hash` через последовательные вызовы `mac.Write([]byte(tsStr))`, `mac.Write([]byte("."))`, `mac.Write(payload)` не создает промежуточных аллокаций объединенных строк в куче (heap allocations). Это существенно эффективнее использования `fmt.Sprintf` или конкатенации строк оператором `+` в условиях HighLoad.

## Подводные камни

1. Передача секретного ключа в параметрах URL: секреты никогда не должны присутствовать в Query-параметрах GET/POST запросов, так как URL логируются в access.log Nginx/прокси.
2. Использование локального времени сервера без UTC: при смене часового пояса или переходе на летнее время верификация сломается у всех клиентов.
3. Пропуск точки-разделителя при вычислении хэша.

## На собеседовании

**Вопрос (Avito/T-Банк):** Почему передача нескольких параметров в одном заголовке `t=...,v1=...` предпочтительнее передачи двух отдельных заголовков `X-Webhook-Timestamp` и `X-Webhook-Signature`?
**Ответ:** Некоторые корпоративные прокси-серверы, WAF (Web Application Firewall) и старые балансировщики HTTP/1.0 вырезают или видоизменяют нестандартные HTTP-заголовки. Наличие `t=` внутри единого заголовка `X-Webhook-Signature` гарантирует, что timestamp и подпись не могут быть разорваны, удалены по отдельности или рассинхронизированы промежуточными прокси.
