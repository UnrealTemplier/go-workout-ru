## Теория

При проектировании корпоративной webhook-платформы (в стиле Stripe, GitHub или Shopify) схема исходящего события (Event Envelope) является неизменяемым контрактом между платформой и внешними интеграторами. Стандартный конверт события должен содержать:
1. `id`: глобально уникальный идентификатор события (например, с префиксом `evt_` + ULID/UUIDv4) для обеспечения идемпотентности на стороне получателя.
2. `type`: точечный строковый классификатор доменного события в нотации `domain.entity.action` (например, `payment.charge.succeeded`, `order.created`).
3. `created_at`: Unix timestamp в секундах или миллисекундах UTC, предотвращающий рассинхронизацию часовых поясов.
4. `payload`: типизированное доменное тело или произвольный объект (`any` / `json.RawMessage`).

Для аутентификации отправителя каждому зарегистрированному эндпоинту генерируется уникальный криптографический секрет (Shared Secret, префикс `whsec_`). Секрет обязан формироваться через криптографически стойкий ГПСЧ операционной системы (`crypto/rand`, использующий `getrandom(2)` в Linux или `/dev/urandom`), закодированный в base64 или hex. Использование `math/rand` категорически недопустимо, так как его псевдослучайные последовательности легко предсказуемы.

## Решение по шагам

1. Опишите структуру `WebhookEvent` с полями `ID`, `Type`, `CreatedAt`, `Payload`, аннотированными json-тегами.
2. Реализуйте функцию `GenerateWebhookSecret(byteLen int) (string, error)`, считывающую энтропию из `crypto/rand.Read`.
3. Закодируйте случайные байты в Base64 (RFC 4648 URL-safe или standard hex/base64) и добавьте префикс `whsec_`.
4. В функции `main` инициализируйте тестовое событие, сгенерируйте секретный ключ клиента и сериализуйте событие в JSON.

## Код решения

**`event_schema.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/base64"
	"encoding/json"
	"fmt"
	"time"
)

// WebhookEvent представляет стандартный каноничный конверт исходящего вебхука.
type WebhookEvent struct {
	ID        string `json:"id"`
	Type      string `json:"type"`
	CreatedAt int64  `json:"created_at"`
	Payload   any    `json:"payload"`
}

// PaymentPayload — пример доменных данных события.
type PaymentPayload struct {
	OrderID  string  `json:"order_id"`
	Amount   float64 `json:"amount"`
	Currency string  `json:"currency"`
	Status   string  `json:"status"`
}

// GenerateWebhookSecret создает криптографически стойкий секретный ключ для клиента.
func GenerateWebhookSecret(byteLen int) (string, error) {
	b := make([]byte, byteLen)
	if _, err := rand.Read(b); err != nil {
		return "", fmt.Errorf("crypto/rand failure: %w", err)
	}
	return "whsec_" + base64.RawURLEncoding.EncodeToString(b), nil
}

func main() {
	secret, err := GenerateWebhookSecret(32)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Generated Client Secret: %s\n", secret)

	event := WebhookEvent{
		ID:        "evt_01HZX8N29KQW4VBM8YZ",
		Type:      "order.payment.succeeded",
		CreatedAt: time.Now().UTC().Unix(),
		Payload: PaymentPayload{
			OrderID:  "ord_994821",
			Amount:   2490.50,
			Currency: "RUB",
			Status:   "COMPLETED",
		},
	}

	body, err := json.MarshalIndent(event, "", "  ")
	if err != nil {
		panic(err)
	}
	fmt.Printf("Event Envelope JSON:\n%s\n", string(body))
}
```

## Под капотом

Под капотом `crypto/rand` в Linux обращается к системному вызову `getrandom(2)` с флагом `GRND_NONBLOCK` (при наличии инициализированного пула энтропии ядра ChaCha20/CSPRNG) либо читает `/dev/urandom`. Это гарантирует, что ключ энтропии невозможно спрогнозировать даже при полном знании исходного кода и времени генерации. Использование префикса `whsec_` облегчает работу секрет-сканеров (GitHub Secret Scanning, TruffleHog) для предотвращения утечек в открытые репозитории.

## Подводные камни

1. Использование `math/rand` вместо `crypto/rand`: псевдослучайный генератор инициализируется seed-значением и дает линейно предсказуемые последовательности, что позволяет атакующему сгенерировать идентичный секрет и подделывать подписи.
2. Передача `Payload` как `string` без валидации json: если `Payload` содержит невалидный JSON или экранированные символы, клиент может получить ошибку десериализации. Рекомендуется использовать строгие структуры или `json.RawMessage`.
3. Отсутствие префикса типа ключа: без строгих префиксов (`whsec_`, `pk_test_`, `sk_live_`) инженеры безопасности не могут автоматически настраивать регулярные выражения DLP/WAF.

## На собеседовании

**Вопрос (Stripe/Ozon):** Почему в схеме вебхука поле `created_at` рекомендуется передавать как целочисленный Unix timestamp, а не ISO-8601 строку?
**Ответ:** Разные языки программирования и парсеры (Python, Go, Java, JS) по-разному парсят наносекунды, миллисекунды, часовые пояса (Z vs +00:00 vs GMT) и високосные секунды в ISO-8601. Целочисленный Unix timestamp (в секундах или миллисекундах) гарантирует абсолютную кроссплатформенную совместимость, не зависит от локали и позволяет получателю тривиально вычислить разницу времени `time.Now().Unix() - event.CreatedAt` для защиты от Replay-атак.
