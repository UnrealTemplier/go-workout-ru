# Проектирование отправителя webhook с криптографической HMAC-SHA256 подписью

### Исходная формулировка

**Проектирование отправителя webhook с HMAC-подписью.**: Реализуйте HTTP-клиент, который отправляет webhook с JSON-телом. Подпишите тело с помощью HMAC-SHA256, используя общий секрет. Передайте подпись в заголовке `X-Webhook-Signature`.

## Теория

Поскольку вебхуки отправляются через публичный Интернет на общедоступные URL интеграторов, злоумышленник может отправить поддельный HTTP POST запрос на URL клиента (например, имитируя успешную оплату заказа `order.paid`).
Для подтверждения подлинности (аутентичности) и целостности сообщения отправитель подписывает тело запроса симметричным кодом аутентификации сообщений — **HMAC-SHA256** (Hash-based Message Authentication Code по RFC 2104).
HMAC использует разделяемый секретный ключ (`Shared Secret`), известный только платформе и клиенту:
$$\text{HMAC}(K, m) = \text{SHA256}\Big((K' \oplus \text{opad}) \parallel \text{SHA256}\big((K' \oplus \text{ipad}) \parallel m\big)\Big)$$
Результат хэширования кодируется в шестнадцатеричный вид (hex) и передается в HTTP-заголовке `X-Webhook-Signature` (или `X-Hub-Signature-256: sha256=...`). Приемник вычисляет HMAC от полученного тела и сверяет его со значением в заголовке.

## Решение по шагам

1. Напишите функцию `ComputeHMACSHA256(payload []byte, secret string) string` с использованием пакетов `crypto/hmac`, `crypto/sha256` и `encoding/hex`.
2. Реализуйте структуру `WebhookSender` с методами отправки.
3. В методе отправки сериализуйте данные, вычислите подпись и добавьте заголовок `X-Webhook-Signature: hex_signature`.
4. Проверьте формирование запроса с помощью мок-сервера `httptest.Server`.

## Код решения

**`hmac_sender.go`**

```go
package main

import (
	"bytes"
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

func ComputeHMACSHA256(payload []byte, secret string) string {
	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write(payload)
	return hex.EncodeToString(mac.Sum(nil))
}

func SendSignedWebhook(targetURL string, payload []byte, secret string) (*http.Response, error) {
	signature := ComputeHMACSHA256(payload, secret)

	req, err := http.NewRequest(http.MethodPost, targetURL, bytes.NewReader(payload))
	if err != nil {
		return nil, err
	}
	req.Header.Set("Content-Type", "application/json")
	req.Header.Set("X-Webhook-Signature", signature)

	client := &http.Client{}
	return client.Do(req)
}

func main() {
	secret := "whsec_super_secret_signing_key_2026"
	payload := []byte(`{"id":"evt_101","event":"user.signup","email":"dev@ozon.ru"}`)

	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		recSignature := r.Header.Get("X-Webhook-Signature")
		body, _ := io.ReadAll(r.Body)

		expectedSignature := ComputeHMACSHA256(body, secret)
		if recSignature == expectedSignature {
			fmt.Printf("Receiver: Signature verified successfully! [sig=%s]\n", recSignature[:16]+"...")
			w.WriteHeader(http.StatusOK)
		} else {
			fmt.Printf("Receiver: Signature mismatch!\n")
			w.WriteHeader(http.StatusUnauthorized)
		}
	}))
	defer ts.Close()

	resp, err := SendSignedWebhook(ts.URL, payload, secret)
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	fmt.Printf("Response Status: %d %s\n", resp.StatusCode, resp.Status)
}
```

## Под капотом

В `crypto/hmac` имплементирован каноничный алгоритм RFC 2104. При создании нового HMAC через `hmac.New` секретный ключ дополняется нулями или хэшируется до размера блока функции хэширования (64 байта для SHA-256), после чего ксорится с константами `ipad` (0x36) и `opad` (0x5c). Это предотвращает атаки удлинением сообщения (Length Extension Attacks), которым подвержены простые схемы `SHA256(secret + message)`.

## Подводные камни

1. Подписание `SHA256(secret + body)` вместо `crypto/hmac`: простая конкатенация уязвима к атакам расширения длины (Length Extension Attack), позволяющим злоумышленнику дописать данные в конец сообщения без знания ключа.
2. Повторная сериализация JSON перед подписью: если отправить одни байты, а подписать результат повторного вызова `json.Marshal`, порядок ключей словаря или пробелы могут измениться, и подпись перестанет сходиться. Подписывать необходимо строго тот байтовый слайс, который уходит в сокет.
3. Логирование секретного ключа в логах отладки: секреты клиентов никогда не должны попадать в stdout/APM трассировки.

## На собеседовании

**Вопрос (Яндекс/Wildberries):** Почему для подписи вебхуков используется симметричный HMAC, а не асимметричная цифровая подпись (RSA/ECDSA/Ed25519)?
**Ответ:** 1. **Производительность:** Вычисление HMAC-SHA256 в разы быстрее генерации и проверки RSA/ECDSA подписей, что критично при отправке миллионов событий в секунду.
2. **Простота интеграции для клиентов:** HMAC поддерживается стандартными библиотеками любого языка программирования (Go, Node.js, Python, PHP, Ruby) без необходимости подключать сложные криптографические библиотеки, валидировать сертификаты x509 или управлять цепочками доверия (PKI).
