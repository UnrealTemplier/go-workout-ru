# Асинхронная доставка: decoupling HTTP API от клиентских эндпоинтов

## Условие

14. **Асинхронная доставка**: Никогда не доставляйте webhooks синхронно в request handler. Всегда через background worker — иначе slow endpoints заблокируют ваш API.

### Исходная формулировка

**Асинхронная доставка**: Никогда не доставляйте webhooks синхронно в request handler. Всегда через background worker — иначе slow endpoints заблокируют ваш API.

## Теория

Главная архитектурная заповедь при проектировании Webhook-платформ — **Никогда не доставлять вебхуки синхронно внутри запроса пользователя**.
Если клиентский эндпоинт "повис" или имеет высокий round-trip time (RTT 5 секунд), синхронная отправка приведет к:
1. Зависанию клиентского запроса (`POST /checkout` или `POST /payments`).
2. Исчерпанию пула HTTP-воркеров и соединений к базе данных PostgreSQL.
3. Каскадному отказу и падению SLA основного платежного шлюза.
Правильная архитектура разделяет процесс на две фазы:
- **Фаза 1 (Синхронная):** Сохранение бизнес-сущности и запись события в локальную таблицу `outbox` в единой транзакции БД (Transactional Outbox). Возврат 200/201 пользователю за < 10 мс.
- **Фаза 2 (Асинхронная):** Фоновый воркер (или пул воркеров) асинхронно считывает события из Outbox/очереди и выполняет HTTP-доставку с собственными таймаутами и изолированными ресурсами.

## Решение по шагам

1. Создайте структуру `OrderService`, эмулирующую обработку платежа.
2. В синхронном хэндлере `ProcessPayment` зафиксируйте успешную оплату и поместите задачу в асинхронную очередь за микросекунды.
3. Реализуйте фоновый сервис доставки `AsyncDeliveryWorker`, отправляющий HTTP-запрос независимо от клиентского потока.
4. Продемонстрируйте, что медленный эндпоинт получателя (задержка 2 сек) не замедляет время ответа основного API.

## Код решения

**`async_decoupling.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

type WebhookJob struct {
	URL     string
	Payload []byte
}

type WebhookQueue struct {
	jobs chan WebhookJob
}

func NewWebhookQueue(bufferSize int) *WebhookQueue {
	return &WebhookQueue{
		jobs: make(chan WebhookJob, bufferSize),
	}
}

func (q *WebhookQueue) Push(job WebhookJob) {
	q.jobs <- job
}

func StartBackgroundDeliveryWorker(q *WebhookQueue) {
	client := &http.Client{Timeout: 5 * time.Second}
	go func() {
		for job := range q.jobs {
			// Выполняется изолированно в фоновом потоке
			resp, err := client.Post(job.URL, "application/json", bytes.NewReader(job.Payload))
			if err != nil {
				fmt.Printf("[Background Worker] Failed to send: %v\n", err)
				continue
			}
			resp.Body.Close()
			fmt.Printf("[Background Worker] Delivered webhook -> %d OK\n", resp.StatusCode)
		}
	}()
}

// PaymentHandler — основной синхронный HTTP API
func PaymentHandler(q *WebhookQueue, webhookURL string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()

		// 1. Бизнес-логика (транзакция в БД)
		// ... выполняется моментально ...

		// 2. Асинхронная постановка в очередь
		q.Push(WebhookJob{
			URL:     webhookURL,
			Payload: []byte(`{"event":"order.paid","amount":5000}`),
		})

		// 3. Мгновенный ответ пользователю
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"payment_accepted"}`))

		fmt.Printf("[API Handler] Finished in %v\n", time.Since(start))
	}
}

func main() {
	// Эмулируем медленный сервер клиента с искусственной задержкой 1 секунда
	slowClientServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(1 * time.Second)
		w.WriteHeader(http.StatusOK)
	}))
	defer slowClientServer.Close()

	queue := NewWebhookQueue(100)
	StartBackgroundDeliveryWorker(queue)

	apiHandler := PaymentHandler(queue, slowClientServer.URL)
	req := httptest.NewRequest(http.MethodPost, "/api/checkout", nil)
	rec := httptest.NewRecorder()

	// Вызываем API
	apiHandler(rec, req)

	// Ждем, пока фоновый воркер завершит доставку
	time.Sleep(1500 * time.Millisecond)
}
```

## Под капотом

Задержка основного обработчика составляет единицы микросекунд (постановка ссылки на структуру в буферизованный кольцевой буфер канала Go), в то время как фоновый вызов занимает более 1 000 000 микросекунд (1 секунда). При 10 000 RPS синхронная доставка исчерпала бы стек горутин и сокеты за доли секунды.

## Подводные камни

1. Запуск неконтролируемой горутины `go sendWebhook(...)` в хэндлере: при падении процесса или отключении питания задачи теряются.
2. Отсутствие мониторинга длины очереди: если воркеры не успевают разгребать очередь, буфер канала переполнится, и API снова заблокируется.
3. Отсутствие механизма повторов для фонового воркера.

## На собеседовании

**Вопрос (Яндекс/Stripe):** В чем фундаментальная опасность запуска `go deliverWebhook(...)` прямо из HTTP-хэндлера?
**Ответ:** 1. **Утечка памяти и CPU:** При скачке входящих запросов количество горутин вырастет бесконтрольно, перегрузив планировщик Go.
2. **Потеря событий:** При рестарте контейнера (rolling update в Kubernetes или OOMKilled) все горутины будут мгновенно уничтожены ядром ОС, и клиентские вебхуки потеряются без возможности восстановления.
3. **Отсутствие backpressure и rate limiting:** Сервер рискует заDDoSить клиентские эндпоинты тысячами одновременных параллельных соединений.
