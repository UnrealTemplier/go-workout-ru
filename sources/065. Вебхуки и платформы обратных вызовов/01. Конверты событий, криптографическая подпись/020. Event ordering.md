# Event ordering: обеспечение строгой очередности доставки событий по сущностям

## Условие

20. **Event ordering**: Обеспечьте доставку событий для одной сущности (`user_id`, `order_id`) в порядке возникновения. Используйте Kafka partition key или Redis stream с ordering.

### Исходная формулировка

**Event ordering**: Обеспечьте доставку событий для одной сущности (`user_id`, `order_id`) в порядке возникновения. Используйте Kafka partition key или Redis stream с ordering.

## Теория

В распределенной системе вебхуков часто возникает проблема гонки событий (Race Condition):
1. Происходит событие `order.created`.
2. Через 50 миллисекунд происходит `order.cancelled`.
Если воркеры отправляют вебхуки параллельно без сохранения порядка, событие `order.cancelled` может прийти на сервер клиента **раньше**, чем `order.created`!
Клиент обработает отмену несуществующего заказа, а затем создаст заказ как активный, что приведет к рассинхронизации данных.
Для гарантии строгой очередности (FIFO ordering per entity):
- Все события для одной доменной сущности (`order_id`, `user_id`, `account_id`) обязаны обрабатываться строго последовательно.
- В Kafka это достигается выбором `entity_id` в качестве Partition Key (`kafka.Key = []byte(orderID)`).
- В локальном диспетчере Go применяется партиционирование задач по шардированным очередям:
$$\text{WorkerID} = \text{Hash}(\text{EntityID}) \pmod{\text{NumWorkers}}$$
Каждый воркер обрабатывает события своего шардового канала последовательно, исключая параллельную доставку событий одного заказа.

## Решение по шагам

1. Создайте структуру `EntityEvent` с полями `EntityID`, `Sequence`, `Type`.
2. Реализуйте функцию хэширования строки `hashKey(key string) int` (FNV-1a хэш).
3. Создайте шардированный диспетчер `OrderedDispatcher` с фиксированным пулом горутин и персональными каналами для каждого воркера.
4. Отправьте пачку событий с одинаковым `EntityID` и убедитесь, что они доставляются строго по возрастанию `Sequence`.

## Код решения

**`ordered_dispatcher.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sync"
	"time"
)

type EntityEvent struct {
	EntityID  string
	Sequence  int
	Type      string
	Timestamp int64
}

type PartitionedWorker struct {
	id     int
	ch     chan EntityEvent
	done   chan struct{}
	record []string
	mu     sync.Mutex
}

func (w *PartitionedWorker) Start() {
	go func() {
		for evt := range w.ch {
			msg := fmt.Sprintf("[Worker %d] Processed Entity=%s Seq=%d Type=%s", w.id, evt.EntityID, evt.Sequence, evt.Type)
			fmt.Println(msg)
			w.mu.Lock()
			w.record = append(w.record, msg)
			w.mu.Unlock()
			time.Sleep(10 * time.Millisecond) // эмуляция работы
		}
		close(w.done)
	}()
}

type OrderedDispatcher struct {
	numPartitions int
	workers       []*PartitionedWorker
}

func NewOrderedDispatcher(numPartitions int, bufferPerPartition int) *OrderedDispatcher {
	d := &OrderedDispatcher{
		numPartitions: numPartitions,
		workers:       make([]*PartitionedWorker, numPartitions),
	}
	for i := 0; i < numPartitions; i++ {
		w := &PartitionedWorker{
			id:   i,
			ch:   make(chan EntityEvent, bufferPerPartition),
			done: make(chan struct{}),
		}
		w.Start()
		d.workers[i] = w
	}
	return d
}

func (d *OrderedDispatcher) partitionFor(entityID string) int {
	h := fnv.New32a()
	h.Write([]byte(entityID))
	return int(h.Sum32()) % d.numPartitions
}

func (d *OrderedDispatcher) Submit(evt EntityEvent) {
	partition := d.partitionFor(evt.EntityID)
	d.workers[partition].ch <- evt
}

func (d *OrderedDispatcher) Stop() {
	for _, w := range d.workers {
		close(w.ch)
		<-w.done
	}
}

func main() {
	dispatcher := NewOrderedDispatcher(4, 50)

	events := []EntityEvent{
		{EntityID: "order_101", Sequence: 1, Type: "order.created"},
		{EntityID: "order_202", Sequence: 1, Type: "order.created"},
		{EntityID: "order_101", Sequence: 2, Type: "order.payment_attempted"},
		{EntityID: "order_101", Sequence: 3, Type: "order.paid"},
		{EntityID: "order_202", Sequence: 2, Type: "order.cancelled"},
		{EntityID: "order_101", Sequence: 4, Type: "order.shipped"},
	}

	for _, evt := range events {
		dispatcher.Submit(evt)
	}

	dispatcher.Stop()
	fmt.Println("All events processed in strictly ordered partitions.")
}
```

## Под капотом

Шардирование по ключу сущности через FNV-1a хэш гарантирует, что все события для `order_101` всегда попадают в один и тот же канал воркера. Поскольку канал в Go обрабатывается одной горутиной строго последовательно, физически невозможно доставить `order.shipped` раньше `order.paid`.

## Подводные камни

1. Изменение количества партиций во время работы: изменение `numPartitions` без предварительного дренажа очередей приведет к тому, что старые события останутся в одном воркере, а новые уйдут в другой, нарушив очередность.
2. Неравномерное распределение нагрузки (Hot Partitioning): если один крупный клиент генерирует 90% событий, один воркер захлебнется, а остальные будут простаивать. Для "горячих" сущностей применяются составные ключи (`entity_id + sub_id`).
3. Блокировка всей партиции при зависании одного запроса: если доставка одного события в партиции зависла на таймауте (10 секунд), все последующие события этой партиции встанут в очередь.

## На собеседовании

**Вопрос (Kafka/Ozon):** Как обеспечить строгий порядок событий вебхука, если воркер упал с ошибкой и должен сделать ретрай с экспоненциальной задержкой?
**Ответ:** Существует два архитектурных подхода:
1. **Strict Ordering (Stop-the-World per Entity):** Партиция или сущность блокируется, пока неудачное событие не будет доставлено или не отправится в DLQ после N попыток. Все последующие события этого заказа ждут.
2. **Event Versioning на стороне клиента:** События снабжаются монотонно возрастающим номером версии (`version: 4`). Приемник игнорирует события с `version <= current_version` в своей БД, допуская доставку с нарушением порядка без повреждения бизнес-состояния.
