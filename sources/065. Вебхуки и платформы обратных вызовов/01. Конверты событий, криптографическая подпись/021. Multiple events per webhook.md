# Multiple events per webhook: подписка по wildcard-маскам и топикам

## Условие

21. **Multiple events per webhook**: Позвольте клиентам подписываться на `*` (все события) или на конкретные типы (`order.*`, `payment.failed`).

### Исходная формулировка

**Multiple events per webhook**: Позвольте клиентам подписываться на `*` (все события) или на конкретные типы (`order.*`, `payment.failed`).

## Теория

Клиентам платформы часто требуется подписываться не на один узкий тип события, а на целую категорию или на абсолютно все события аккаунта.
Стандартный механизм маршрутизации поддерживает:
1. **Точное совпадение (Exact Match):** `payment.charge.succeeded`.
2. **Wildcard-суффикс (Prefix / Namespace Match):** `order.*` перехватывает `order.created`, `order.paid`, `order.cancelled`.
3. **Глобальный Wildcard (All Events):** `*` перехватывает любые события платформы.
Для эффективного сопоставления шаблонов в Go используются структуры регулярных выражений, `path.Match` или специализированные префиксные деревья (Trie / Radix Tree).

## Решение по шагам

1. Создайте функцию сопоставления маски топиков `MatchTopic(pattern, eventType string) bool`.
2. Поддержите шаблоны `*` и `domain.*` с разделением по точке.
3. Реализуйте структуру `SubscriptionFilter` с проверкой набора подписок.
4. Протестируйте сопоставление различных шаблонов и событий в `main`.

## Код решения

**`wildcard_topics.go`**

```go
package main

import (
	"fmt"
	"strings"
)

// MatchTopic проверяет соответствие типа события маске подписки.
// Поддерживает "*", "order.*", "payment.*.failed", точные совпадения.
func MatchTopic(pattern, eventType string) bool {
	if pattern == "*" || pattern == eventType {
		return true
	}

	pParts := strings.Split(pattern, ".")
	eParts := strings.Split(eventType, ".")

	if len(pParts) != len(eParts) {
		// Обработка префикса вида "order.*"
		if len(pParts) == 2 && pParts[1] == "*" && pParts[0] == eParts[0] {
			return true
		}
		return false
	}

	for i := range pParts {
		if pParts[i] != "*" && pParts[i] != eParts[i] {
			return false
		}
	}
	return true
}

func MatchesAny(patterns []string, eventType string) bool {
	for _, p := range patterns {
		if MatchTopic(p, eventType) {
			return true
		}
	}
	return false
}

func main() {
	clientTopics := []string{"order.*", "customer.created", "payment.refund.*"}

	tests := []string{
		"order.paid",
		"order.shipped.delivered",
		"customer.created",
		"customer.deleted",
		"payment.refund.initiated",
		"invoice.generated",
	}

	for _, evt := range tests {
		matched := MatchesAny(clientTopics, evt)
		fmt.Printf("Event: %-25s -> Matched: %v\n", evt, matched)
	}
}
```

## Под капотом

Разбиение строк на части через `strings.Split` создает промежуточный срез строк. В высокопроизводительных диспетчерах парсинг выполняется через сканирование байтов без аллокаций (Zero-allocation byte scanning) либо предварительно компилируется в конечный автомат (FSM), что позволяет обрабатывать миллионы событий в секунду на одно ядро процессора.

## Подводные камни

1. Подписка `*` для крупных клиентов без фильтрации: клиент, подписанный на все события, может быть непреднамеренно зафлужен внутренними системными событиями (например, метриками или heartbeat).
2. Дублирование доставки: если клиент указал `order.*` и `order.paid`, валидатор диспетчера должен исключать повторный вызов одного и того же вебхука.
3. Нечувствительность к регистру: типы событий должны быть нормализованы к нижнему регистру (`strings.ToLower`) при регистрации и публикации.

## На собеседовании

**Вопрос (Shopify/Kafka):** Как организовать сопоставление 100 000 wildcard-подписок мерчантов с минимальной задержкой?
**Ответ:** Применяется структура данных **Topic Trie (префиксное дерево топиков)**, аналогичная используемой в MQTT и RabbitMQ Exchange. Каждый узел дерева соответствует сегменту топика (например, `order` -> `payment` -> `succeeded`). При поступлении события диспетчер проходит по веткам дерева за время \(O(L)\), где \(L\) — глубина вложенности топика (обычно 2–4 сегмента), полностью минуя линейный перебор всех 100 000 подписок.
