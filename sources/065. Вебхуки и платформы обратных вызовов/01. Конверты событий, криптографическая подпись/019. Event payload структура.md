# Event payload структура: проектирование универсального конверта события

## Условие

19. **Event payload структура**: Стандартизируйте payload: `{"id": "evt_...", "type": "order.paid", "created_at": "...", "data": {...}}`. ID события критичен для idempotency.

### Исходная формулировка

**Event payload структура**: Стандартизируйте payload: `{"id": "evt_...", "type": "order.paid", "created_at": "...", "data": {...}}`. ID события критичен для idempotency.

## Теория

Корпоративный стандарт Event Payload должен быть консистентным для всех сервисов компании.
Рекомендуемый отраслевой стандарт (CloudEvents v1.0 или Stripe-style Event Schema) включает:
1. `id`: строковый идентификатор события с префиксом типа (например, `evt_01HZX8N...`).
2. `type`: иерархический тип события в нижнем регистре через точку (`order.refund.created`).
3. `created_at`: целое число (Unix timestamp в секундах).
4. `api_version`: версия схемы данных события (например, `2026-03-01`).
5. `data`: объект данных события. Содержит сущность (`object`) в её текущем состоянии.
6. `request`: контекст инициатора (ID запроса `req_...` или `idempotency_key`), позволяющий сопоставить вебхук с исходящим API-запросом клиента.

## Решение по шагам

1. Разработайте обобщенную (generic) структуру `EventEnvelope[T any]`.
2. Реализуйте конструктор `NewEventEnvelope[T any](eventType string, data T) EventEnvelope[T]`.
3. Реализуйте сериализацию и десериализацию для доменной структуры `Invoice`.
4. Продемонстрируйте валидацию структуры конверта.

## Код решения

**`event_envelope.go`**

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"time"
)

type RequestContext struct {
	ID             string `json:"id,omitempty"`
	IdempotencyKey string `json:"idempotency_key,omitempty"`
}

type EventEnvelope[T any] struct {
	ID         string         `json:"id"`
	Type       string         `json:"type"`
	APIVersion string         `json:"api_version"`
	CreatedAt  int64          `json:"created_at"`
	Request    RequestContext `json:"request"`
	Data       T              `json:"data"`
}

type InvoiceData struct {
	InvoiceID string  `json:"invoice_id"`
	Customer  string  `json:"customer_id"`
	Amount    float64 `json:"amount"`
	Currency  string  `json:"currency"`
}

func generateEventID() string {
	b := make([]byte, 12)
	_, _ = rand.Read(b)
	return "evt_" + hex.EncodeToString(b)
}

func NewEvent[T any](eventType string, data T, reqCtx RequestContext) EventEnvelope[T] {
	return EventEnvelope[T]{
		ID:         generateEventID(),
		Type:       eventType,
		APIVersion: "2026-01-01",
		CreatedAt:  time.Now().UTC().Unix(),
		Request:    reqCtx,
		Data:       data,
	}
}

func main() {
	invoice := InvoiceData{
		InvoiceID: "in_884920",
		Customer:  "cus_99120",
		Amount:    12500.00,
		Currency:  "RUB",
	}

	event := NewEvent("invoice.payment_succeeded", invoice, RequestContext{
		ID:             "req_01HPX79A",
		IdempotencyKey: "client_idem_555",
	})

	jsonData, err := json.MarshalIndent(event, "", "  ")
	if err != nil {
		panic(err)
	}

	fmt.Printf("Standardized Webhook Event JSON:\n%s\n", string(jsonData))
}
```

## Под капотом

Использование Go generics `EventEnvelope[T any]` обеспечивает полную статическую типизацию на этапе компиляции: сериализатор знает конкретную структуру данных внутри `Data`, предотвращая накладные расходы на рефлексию при маршалинге нетипизированного `any` / `interface{}`.

## Подводные камни

1. Помещение метаданных внутрь объекта `data`: если смешать метаданные конверта (`id`, `created_at`) и поля доменной модели (`amount`, `status`), клиентам сложно парсить события стандартными SDK.
2. Изменение схемы `data` без инкремента `api_version`: удаление полей или переименование типов без версионирования ломает интеграции существующих клиентов.
3. Отсутствие `id` на верхнем уровне: делает невозможной универсальную дедупликацию в middleware клиентов.

## На собеседовании

**Вопрос (CloudEvents/Yandex):** Что такое спецификация CloudEvents от CNCF, и чем она похожа на конверт вебхуков?
**Ответ:** CloudEvents — это открытый отраслевой стандарт описания событий в событийно-ориентированных архитектурах. Он регламентирует обязательные атрибуты: `id` (уникальность), `source` (URI источника), `specversion` (версия формата), `type` (тип события) и `data` (тело). Использование схемы CloudEvents позволяет стандартизировать обработку событий между HTTP-вебхуками, Kafka, NATS и Serverless-функциями (AWS Lambda, Yandex Cloud Functions).
