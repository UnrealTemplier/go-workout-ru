# Webhook dispatcher: роутинг по типам событий и постановка в очередь задач

## Условие

12. **Webhook dispatcher**: Создайте систему, которая при возникновении события (`order.paid`) находит все подписанные endpoints и ставит delivery задачи в очередь (Redis/Kafka).

### Исходная формулировка

**Webhook dispatcher**: Создайте систему, которая при возникновении события (`order.paid`) находит все подписанные endpoints и ставит delivery задачи в очередь (Redis/Kafka).

## Теория

В корпоративной системе один тип события (например, `order.paid`) может быть интересен десяткам независимых подписчиков: 1C/ERP системе склада, CRM, аналитической платформе и партнерскому API логистики.
Webhook Dispatcher выполняет роль Pub/Sub маршрутизатора:
1. Получает доменное событие из шины данных (Kafka, RabbitMQ, Redis).
2. Запрашивает из кэша (или БД) активные подписки на данный тип события (`topic` / `pattern matching`).
3. Для каждого совпавшего эндпоинта формирует изолированную задачу доставки (`DeliveryTask`) с уникальным `id`, адресом и клиентским секретом.
4. Отправляет задачи в устойчивую очередь задач для асинхронной параллельной отправки воркерами.

## Решение по шагам

1. Опишите модель подписки `Subscription` (ID, TargetURL, Secret, EventTypes).
2. Создайте реестр подписок `SubscriptionStore` с потокобезопасным поиском подписчиков.
3. Реализуйте диспетчер `Dispatcher`, получающий события и формирующий пачку задач доставки.
4. Протестируйте fan-out распределение одного события `order.paid` трем разным получателям.

## Код решения

**`fanout_dispatcher.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Subscription struct {
	ID        string
	TargetURL string
	Secret    string
	Topics    []string
}

type Event struct {
	ID        string `json:"id"`
	Type      string `json:"type"`
	Timestamp int64  `json:"timestamp"`
	Payload   any    `json:"payload"`
}

type DispatchTask struct {
	EventID   string
	EventType string
	TargetURL string
	Secret    string
	Payload   any
}

type SubscriptionRegistry struct {
	mu            sync.RWMutex
	subscriptions []Subscription
}

func (r *SubscriptionRegistry) Add(sub Subscription) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.subscriptions = append(r.subscriptions, sub)
}

func (r *SubscriptionRegistry) FindSubscribers(eventType string) []Subscription {
	r.mu.RLock()
	defer r.mu.RUnlock()
	var matches []Subscription
	for _, sub := range r.subscriptions {
		for _, topic := range sub.Topics {
			if topic == "*" || topic == eventType {
				matches = append(matches, sub)
				break
			}
		}
	}
	return matches
}

type EventDispatcher struct {
	registry *SubscriptionRegistry
	outQueue chan DispatchTask
}

func NewEventDispatcher(reg *SubscriptionRegistry, queueSize int) *EventDispatcher {
	return &EventDispatcher{
		registry: reg,
		outQueue: make(chan DispatchTask, queueSize),
	}
}

func (d *EventDispatcher) Dispatch(event Event) int {
	subscribers := d.registry.FindSubscribers(event.Type)
	for _, sub := range subscribers {
		task := DispatchTask{
			EventID:   event.ID,
			EventType: event.Type,
			TargetURL: sub.TargetURL,
			Secret:    sub.Secret,
			Payload:   event.Payload,
		}
		d.outQueue <- task
	}
	return len(subscribers)
}

func main() {
	reg := &SubscriptionRegistry{}
	reg.Add(Subscription{ID: "sub_1", TargetURL: "https://crm.corp.ru/hooks", Secret: "sec_1", Topics: []string{"order.paid"}})
	reg.Add(Subscription{ID: "sub_2", TargetURL: "https://warehouse.ru/wh", Secret: "sec_2", Topics: []string{"order.*", "order.paid"}})
	reg.Add(Subscription{ID: "sub_3", TargetURL: "https://audit.ru/log", Secret: "sec_3", Topics: []string{"*"}})
	reg.Add(Subscription{ID: "sub_4", TargetURL: "https://billing.ru/invoices", Secret: "sec_4", Topics: []string{"invoice.created"}})

	dispatcher := NewEventDispatcher(reg, 100)

	evt := Event{
		ID:        "evt_99812",
		Type:      "order.paid",
		Timestamp: time.Now().Unix(),
		Payload:   map[string]any{"order_id": "ord_555", "total": 4500},
	}

	count := dispatcher.Dispatch(evt)
	fmt.Printf("Event %s dispatched to %d subscribers\n", evt.Type, count)

	// Вычитываем задачи из очереди доставки
	for i := 0; i < count; i++ {
		task := <-dispatcher.outQueue
		fmt.Printf("  -> Queue Task: target=%s, secret=%s\n", task.TargetURL, task.Secret)
	}
}
```

## Под капотом

При наличии сотен тысяч подписок линейный перебор `O(N)` становится узким местом. В высоконагруженных системах подписки организуются в Trie (префиксное дерево топиков) или инвертированный индекс по шаблонам событий `map[string][]SubscriptionID`, что сокращает время поиска до \(O(1)\) или \(O(K)\), где \(K\) — количество сегментов топика.

## Подводные камни

1. Синхронная отправка задач в блокирующий канал: если очередь переполнена, диспетчер заблокирует чтение сообщений из брокера Kafka/RabbitMQ.
2. Неуникальные подписки: если клиент подписан на `order.*` и `order.paid`, он может получить дубликат задачи доставки. Проверка `break` внутри цикла предотвращает дублирование.
3. Гонка данных при чтении подписок: добавление подписок и диспетчеризация происходят параллельно, поэтому доступ к хранилищу обязан синхронизироваться через `sync.RWMutex`.

## На собеседовании

**Вопрос (Wildberries/Ozon):** Как масштабировать Webhook Dispatcher, если одно событие (например, изменение цен распродажи) должно быть доставлено 50 000 мерчантов одновременно?
**Ответ:** Используется двухступенчатый Fan-Out:
1. Диспетчер разбивает список 50 000 подписчиков на пачки (банки по 500 штук) и отправляет в Kafka топик `webhook.dispatch.chunks`.
2. Группа воркеров параллельно считывает эти пачки и порождает гранулярные задания доставки в топики отправки `webhook.deliveries`.
Это предотвращает взрывной рост памяти на одном узле и равномерно распределяет нагрузку по кластеру Kubernetes.
