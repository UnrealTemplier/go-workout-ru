# Idempotency-Key: проектирование идемпотентного приёмника с Redis-блокировками

## Условие

18. **Idempotency-Key.**: Генерируйте `Idempotency-Key` (UUID v4) для каждого события. Приёмник хранит обработанные ключи в Redis с TTL 24 часа. При повторном получении — возвращает 200, но не обрабатывает. Объясните разницу между idempotency на уровне HTTP и на уровне бизнес-логики.

### Исходная формулировка

**Idempotency-Key.**: Генерируйте `Idempotency-Key` (UUID v4) для каждого события. Приёмник хранит обработанные ключи в Redis с TTL 24 часа. При повторном получении — возвращает 200, но не обрабатывает. Объясните разницу между idempotency на уровне HTTP и на уровне бизнес-логики.

## Теория

Поскольку доставка вебхуков работает по модели **At-Least-Once** (хотя бы один раз), повторные отправки неизбежны при сбоях сети, таймаутах или рестартах воркеров.
Каждое событие снабжается уникальным `Idempotency-Key` (UUIDv4 или каноничный `id` события).
Приемник обязан гарантировать, что повторное получение одного и того же события не приведет к дублированию бизнес-операций (например, двойному списанию средств или повторной отправке SMS клиенту).
Разделяют два уровня идемпотентности:
1. **HTTP-уровень (Транспортный):** Приемник сохраняет результат первого ответа (status code и body) в кэше. При повторном получении того же `Idempotency-Key` возвращается сохраненный 200 OK без повторного запуска логики.
2. **Бизнес-уровень (Доменный):** Проверка состояния доменной сущности в БД (например, статус заказа уже `PAID`). Если заказ уже оплачен, операция завершается успехом без изменения данных.

## Решение по шагам

1. Создайте структуру `IdempotentReceiver` с подключением к кэшу ключей идемпотентности.
2. Реализуйте метод `ProcessEvent(ctx context.Context, idempotencyKey string, processFn func() error) (bool, error)`.
3. Используйте атомарный `SetNX` с TTL 24 часа.
4. Различайте состояния: "впервые обработано", "дубликат (уже обработано)", "ошибка обработки (ключ освобождается для ретрая)".

## Код решения

**`idempotent_receiver.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type EventStatus string

const (
	StatusProcessing EventStatus = "PROCESSING"
	StatusCompleted  EventStatus = "COMPLETED"
)

type MockRedisStorage struct {
	mu   sync.Mutex
	data map[string]EventStatus
}

func NewMockRedisStorage() *MockRedisStorage {
	return &MockRedisStorage{data: make(map[string]EventStatus)}
}

// LockKey эмулирует SET key StatusProcessing NX EX 86400
func (r *MockRedisStorage) LockKey(key string) (bool, EventStatus) {
	r.mu.Lock()
	defer r.mu.Unlock()
	if status, exists := r.data[key]; exists {
		return false, status
	}
	r.data[key] = StatusProcessing
	return true, StatusProcessing
}

func (r *MockRedisStorage) CompleteKey(key string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.data[key] = StatusCompleted
}

func (r *MockRedisStorage) ReleaseKey(key string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	delete(r.data, key)
}

type WebhookConsumer struct {
	storage *MockRedisStorage
}

func (c *WebhookConsumer) HandleWebhook(ctx context.Context, idempotencyKey string, payload string) (string, error) {
	acquired, status := c.storage.LockKey(idempotencyKey)
	if !acquired {
		if status == StatusCompleted {
			// Идемпотентный возврат: операция уже выполнена успешно
			return fmt.Sprintf("Event %s already processed. Returning cached SUCCESS.", idempotencyKey), nil
		}
		// Запрос в процессе выполнения параллельным потоком
		return "", errors.New("concurrent processing detected, please retry later")
	}

	// Выполнение бизнес-логики
	fmt.Printf("-> Executing business logic for key: %s (payload: %s)\n", idempotencyKey, payload)
	
	// Фиксация завершения
	c.storage.CompleteKey(idempotencyKey)
	return fmt.Sprintf("Event %s processed freshly.", idempotencyKey), nil
}

func main() {
	storage := NewMockRedisStorage()
	consumer := &WebhookConsumer{storage: storage}

	key := "idem_evt_990011"

	// 1. Первая попытка
	res1, err := consumer.HandleWebhook(context.Background(), key, `{"payment": 1000}`)
	fmt.Printf("Attempt 1: %s (err: %v)\n", res1, err)

	// 2. Повторная доставка дубликата через 1 секунду
	res2, err := consumer.HandleWebhook(context.Background(), key, `{"payment": 1000}`)
	fmt.Printf("Attempt 2: %s (err: %v)\n", res2, err)
}
```

## Под капотом

В распределенной системе двухфазный статус `PROCESSING -> COMPLETED` критически важен. Если воркер упадет в процессе выполнения бизнес-логики, ключ в статусе `PROCESSING` должен истечь по TTL (например, через 60 секунд), чтобы следующий ретрай смог повторно попытаться выполнить операцию. Фиксация `COMPLETED` выставляется с большим TTL (24–72 часа).

## Подводные камни

1. Сохранение ключа только в локальной памяти: дублирующий вебхук может прийти на соседний инстанс в Kubernetes и выполниться дважды.
2. Отсутствие разблокировки при ошибке: если бизнес-логика завершилась ошибкой БД, а ключ остался заблокированным навсегда, повторная доставка вебхука никогда не сможет выполниться.
3. Использование `Idempotency-Key` в качестве первичного ключа бизнес-таблицы без проверки типа события: разные типы событий могут случайно получить одинаковый ID при сбое генератора.

## На собеседовании

**Вопрос (Stripe/Ozon):** В чем разница между идемпотентностью на уровне HTTP-транспорта и идемпотентностью на уровне базы данных?
**Ответ:**
- **HTTP-уровень:** Защищает от сетевых дублей. При получении того же `Idempotency-Key` сервер сразу возвращает сохраненный результат (200 OK), не нагружая базу данных.
- **Бизнес-уровень (БД):** Защищает от нарушения целостности данных при конкурентных запросах или сбоях кэша. Реализуется через `INSERT INTO orders ... ON CONFLICT (order_id) DO NOTHING` или проверку статуса в транзакции с блокировкой `SELECT ... FOR UPDATE`. Даже если кэш идемпотентности очистится, БД гарантирует отсутствие дублирования.
