# HMAC signature генерация: префиксные схемы подписи sha256=...

## Условие

8. **HMAC signature генерация**: При отправке webhook события подписывайте body через HMAC-SHA256 с общим secret. Добавляйте подпись в header `X-Webhook-Signature: sha256=...`.

### Исходная формулировка

**HMAC signature генерация**: При отправке webhook события подписывайте body через HMAC-SHA256 с общим secret. Добавляйте подпись в header `X-Webhook-Signature: sha256=...`.

## Теория

Общепринятым индустриальным стандартом (GitHub, Stripe, Shopify, Twilio) является передача подписи в формате префикса алгоритма:
`X-Webhook-Signature: sha256=525718688d648b142c6432e01b0e2e8e603d8534772b3a9e116a3de1ad222374`
Или для нескольких версий алгоритмов (при плановом переходе с sha1 на sha256):
`X-Hub-Signature-256: sha256=...`
Префикс `sha256=` позволяет:
1. Однозначно идентифицировать хэш-алгоритм без двусмысленности.
2. Обеспечивать гибкую миграцию (например, поддержка `sha256=` и `ed25519=` в одном заголовке через запятую).
3. Избегать коллизий между шестнадцатеричным (hex) и base64 форматами представления дайджеста.

## Решение по шагам

1. Создайте структуру `HMACSigner` с полем `secret []byte`.
2. Реализуйте метод `Sign(payload []byte) string`, возвращающий строку вида `sha256=<hex_hash>`.
3. Реализуйте метод валидации `Verify(payload []byte, headerValue string) bool`.
4. Используйте `subtle.ConstantTimeCompare` для защиты от тайминг-атак при сравнении подписей.

## Код решения

**`prefixed_signer.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	"strings"
)

type HMACSigner struct {
	secret []byte
}

func NewHMACSigner(secret string) *HMACSigner {
	return &HMACSigner{secret: []byte(secret)}
}

func (s *HMACSigner) Sign(payload []byte) string {
	mac := hmac.New(sha256.New, s.secret)
	mac.Write(payload)
	sum := mac.Sum(nil)
	return "sha256=" + hex.EncodeToString(sum)
}

func (s *HMACSigner) Verify(payload []byte, headerValue string) bool {
	if !strings.HasPrefix(headerValue, "sha256=") {
		return false
	}
	expectedSig := s.Sign(payload)
	return subtle.ConstantTimeCompare([]byte(headerValue), []byte(expectedSig)) == 1
}

func main() {
	signer := NewHMACSigner("whsec_prod_secret_token_123")
	payload := []byte(`{"event":"charge.refunded","amount":500}`)

	header := signer.Sign(payload)
	fmt.Printf("Generated Header: %s\n", header)

	valid := signer.Verify(payload, header)
	fmt.Printf("Verification result (valid): %v\n", valid)

	tamperedPayload := []byte(`{"event":"charge.refunded","amount":99999}`)
	invalid := signer.Verify(tamperedPayload, header)
	fmt.Printf("Verification result (tampered): %v\n", invalid)
}
```

## Под капотом

`subtle.ConstantTimeCompare` побайтово сравнивает два слайса, выполняя операцию побитового ИЛИ (`|`) над разностями байтов за фиксированное число процессорных тактов вне зависимости от того, в каком именно байте встретилось первое несовпадение. Обычное сравнение строк `headerValue == expectedSig` прерывается на первом несовпадающем символе (`early return`), что позволяет злоумышленнику с помощью точного таймера измерить время ответа и символ за символом подобрать валидную подпись.

## Подводные камни

1. Использование оператора `==` вместо `subtle.ConstantTimeCompare`: критическая уязвимость класса Remote Timing Attack.
2. Неверная обработка разной длины строк: `subtle.ConstantTimeCompare` сразу возвращает 0, если длины слайсов различаются, что в данном случае безопасно, так как длина hex-хэша SHA256 всегда фиксирована (64 символа + 7 символов префикса = 71 символ).
3. Пропуск префикса `sha256=`: если клиент ожидает префикс, а сервер шлет сырой hex, верификация упадет на стороне получателя.

## На собеседовании

**Вопрос (GitHub/Stripe):** Зачем в спецификациях подписей вебхуков (GitHub Webhooks, Stripe) заголовок подписи содержит префикс версии или алгоритма (например, `v1=` или `sha256=`)?
**Ответ:** Это фундаментальный паттерн эволюции криптографических схем. Если в алгоритме SHA-256 в будущем будет обнаружена слабость или индустрия перейдет на квантово-устойчивые алгоритмы / Ed25519, платформа сможет одновременно отправлять старую и новую подписи через запятую: `X-Signature: sha256=..., v2=...`. Получатели смогут плавно обновить код без простоя и разрыва обратной совместимости.
