## Теория

При временных сбоях эндпоинта клиента (500 Internal Error, 502 Bad Gateway, сетевой таймаут) повторные запросы должны выполняться с возрастающей экспоненциальной задержкой — **Exponential Backoff**:
$$T_{\text{wait}} = \min\Big(T_{\text{max}}, T_{\text{base}} \times 2^{\text{attempt}}\Big)$$
Пример интервалов:
- Попытка 1: через 1 секунду
- Попытка 2: через 2 секунды
- Попытка 3: через 4 секунды
- Попытка 4: через 8 секунд
- Попытка 5: через 16 секунд (и так далее до верхнего предела \(T_{\text{max}}\), например 1 час).

Для надежности состояние доставки сохраняется в реляционной СУБД (PostgreSQL) со схемой:
`attempt_count INT`, `next_retry_at TIMESTAMPTZ`, `status VARCHAR`.
Фоновый диспетчер периодически выбирает упавшие задачи:
`SELECT id FROM webhook_deliveries WHERE status = 'RETRY' AND next_retry_at <= NOW() LIMIT 100 FOR UPDATE SKIP LOCKED;`

## Код решения

**`exponential_backoff_db.go`**

```go
package main

import (
	"fmt"
	"math"
	"sync"
	"time"
)

type DeliveryStatus string

const (
	StatusPending DeliveryStatus = "PENDING"
	StatusSuccess DeliveryStatus = "SUCCESS"
	StatusFailed  DeliveryStatus = "FAILED"
	StatusDead    DeliveryStatus = "DEAD_LETTER"
)

type DeliveryRecord struct {
	ID           string
	TargetURL    string
	AttemptCount int
	MaxAttempts  int
	NextRetryAt  time.Time
	Status       DeliveryStatus
}

func CalculateBackoff(attempt int, baseDelay, maxDelay time.Duration) time.Duration {
	backoff := float64(baseDelay) * math.Pow(2, float64(attempt))
	if backoff > float64(maxDelay) {
		return maxDelay
	}
	return time.Duration(backoff)
}

type DatabaseQueue struct {
	mu      sync.Mutex
	records []*DeliveryRecord
}

func (db *DatabaseQueue) FailAndReschedule(id string, baseDelay, maxDelay time.Duration) {
	db.mu.Lock()
	defer db.mu.Unlock()

	for _, rec := range db.records {
		if rec.ID == id {
			rec.AttemptCount++
			if rec.AttemptCount >= rec.MaxAttempts {
				rec.Status = StatusDead
				fmt.Printf("[%s] Exceeded max attempts (%d). Moved to DEAD_LETTER.\n", rec.ID, rec.MaxAttempts)
				return
			}

			delay := CalculateBackoff(rec.AttemptCount, baseDelay, maxDelay)
			rec.NextRetryAt = time.Now().Add(delay)
			rec.Status = StatusFailed
			fmt.Printf("[%s] Attempt %d failed. Next retry in %v (at %s)\n",
				rec.ID, rec.AttemptCount, delay, rec.NextRetryAt.Format("15:04:05"))
			return
		}
	}
}

func main() {
	base := 1 * time.Second
	maxLimit := 1 * time.Hour

	rec := &DeliveryRecord{
		ID:          "deliv_1001",
		TargetURL:   "https://broken-client.org/hook",
		MaxAttempts: 6,
		Status:      StatusPending,
	}

	queue := &DatabaseQueue{records: []*DeliveryRecord{rec}}

	fmt.Println("--- Simulating 6 consecutive delivery failures ---")
	for i := 0; i < 6; i++ {
		queue.FailAndReschedule(rec.ID, base, maxLimit)
	}
}
```

## Под капотом

Ограничение \(T_{\text{max}}\) (Cap) математически необходимо, так как при формуле \(2^{\text{attempt}}\) уже на 30-й попытке задержка составила бы \(2^{30} \approx 10^9\) секунд (более 34 лет), что приведет к переполнению целых чисел в представлении `time.Duration` (`int64` наносекунд переполнится при попытке 63). Ограничение в 1 час обеспечивает баланс между разгрузкой клиентского сервера и актуальностью доставки.

## Подводные камни

1. Отсутствие верхнего предела \(T_{\text{max}}\): целочисленное переполнение `time.Duration` приводит к установке отрицательных задержек или немедленным непрерывным попыткам.
2. Использование линейных повторов (ретрай каждую секунду): при сбое на стороне клиента тысячи повторных запросов в секунду создают DDoS и не дают серверу восстановиться.
3. Блокировка всей таблицы `UPDATE ...`: в PostgreSQL необходимо использовать `FOR UPDATE SKIP LOCKED`, чтобы параллельные воркеры не блокировали друг друга на одних строках.

## На собеседовании

**Вопрос (Avito/Ozon):** Почему в базе данных при конкурентной выборке задач на ретрай необходимо использовать конструкцию `FOR UPDATE SKIP LOCKED`?
**Ответ:** Без `SKIP LOCKED` при запуске 20 параллельных воркеров каждый запрос `SELECT ... FOR UPDATE` будет блокироваться на первой же залоченной другим воркером строке, создавая очередь ожидания и высокий contention. Флаг `SKIP LOCKED` инструктирует PostgreSQL пропустить уже заблокированные другими транзакциями строки и немедленно вернуть воркеру свободные задачи, обеспечивая идеальное горизонтальное масштабирование пула воркеров.
