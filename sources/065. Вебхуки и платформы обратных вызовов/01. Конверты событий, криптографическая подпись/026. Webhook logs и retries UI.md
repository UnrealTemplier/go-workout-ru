# Webhook logs и retries UI: структура журнала аудита и телеметрии попыток доставки

## Условие

26. **Webhook logs и retries UI**: Создайте dashboard, где клиенты видят историю доставок: timestamp, status code, response body, retry count, next attempt.

### Исходная формулировка

**Webhook logs и retries UI**: Создайте dashboard, где клиенты видят историю доставок: timestamp, status code, response body, retry count, next attempt.

## Теория

Разработчикам клиентских интеграций жизненно необходима панель управления (Dashboard / UI) с полным журналом попыток доставки (Delivery Logs).
Каждая запись о попытке доставки (`WebhookDeliveryAttempt`) должна фиксировать:
1. `id`: ID попытки (ULID / UUIDv4).
2. `webhook_id`: ID подписки.
3. `event_id`: ID доменного события.
4. `attempt_number`: порядковый номер попытки (1, 2, 3...).
5. `request_headers` и `request_body`: точные отправленные заголовки и тело.
6. `response_status`: HTTP-код ответа (200, 500, 503) или 0 при сетевом сбое.
7. `response_duration_ms`: время ответа клиентского сервера в миллисекундах.
8. `response_body_snippet`: первые 1–4 КБ тела ответа для анализа ошибки клиентом.
9. `error_message`: системная ошибка сетевого уровня (например, `i/o timeout` или `connection refused`).

## Решение по шагам

1. Опишите структуры данных `DeliveryAttemptLog` и `WebhookAuditService`.
2. Реализуйте обертку отправки запроса, замеряющую время отклика через `time.Since`.
3. Сохраняйте усеченный сниппет тела ответа во избежание разрастания базы данных.
4. Выведите отформатированный аудит-лог для отображения в интерфейсе разработчика.

## Код решения

**`delivery_audit_logs.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"time"
)

type DeliveryAttemptLog struct {
	ID                 string            `json:"id"`
	WebhookID          string            `json:"webhook_id"`
	EventID            string            `json:"event_id"`
	AttemptNumber      int               `json:"attempt_number"`
	ExecutedAt         time.Time         `json:"executed_at"`
	ResponseDurationMS int64             `json:"response_duration_ms"`
	ResponseStatus     int               `json:"response_status"`
	ResponseBody       string            `json:"response_body"`
	ErrorMessage       string            `json:"error_message,omitempty"`
	RequestHeaders     map[string]string `json:"request_headers"`
}

func ExecuteAndLogDelivery(ctx context.Context, client *http.Client, webhookID, eventID string, attempt int, targetURL string, payload []byte) DeliveryAttemptLog {
	log := DeliveryAttemptLog{
		ID:             fmt.Sprintf("att_%d_%s", attempt, eventID),
		WebhookID:      webhookID,
		EventID:        eventID,
		AttemptNumber:  attempt,
		ExecutedAt:     time.Now().UTC(),
		RequestHeaders: map[string]string{"Content-Type": "application/json"},
	}

	req, err := http.NewRequestWithContext(ctx, http.MethodPost, targetURL, bytes.NewReader(payload))
	if err != nil {
		log.ErrorMessage = fmt.Sprintf("request creation error: %v", err)
		return log
	}
	req.Header.Set("Content-Type", "application/json")

	start := time.Now()
	resp, err := client.Do(req)
	log.ResponseDurationMS = time.Since(start).Milliseconds()

	if err != nil {
		log.ErrorMessage = err.Error()
		return log
	}
	defer resp.Body.Close()

	log.ResponseStatus = resp.StatusCode
	// Читаем сниппет ответа до 2 КБ
	snippet, _ := io.ReadAll(io.LimitReader(resp.Body, 2048))
	log.ResponseBody = string(snippet)

	return log
}

func main() {
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(25 * time.Millisecond)
		w.WriteHeader(http.StatusInternalServerError)
		_, _ = w.Write([]byte(`{"error":"database connection pool exhausted"}`))
	}))
	defer ts.Close()

	client := &http.Client{Timeout: 2 * time.Second}
	log := ExecuteAndLogDelivery(context.Background(), client, "wh_sub_42", "evt_9911", 1, ts.URL, []byte(`{"ping":1}`))

	logJSON, _ := json.MarshalIndent(log, "", "  ")
	fmt.Printf("Delivery Audit Log (UI ready):\n%s\n", string(logJSON))
}
```

## Под капотом

В масштабных webhook-платформах логи попыток сохраняются не в реляционную транзакционную базу, а асинхронно сбрасываются через Kafka в колоночные аналитические хранилища (ClickHouse) или Elasticsearch/OpenSearch с TTL ротации 14–30 дней. Это исключает деградацию производительности OLTP базы данных платформы.

## Подводные камни

1. Сохранение полного тела ответа без лимита: сторонний сервер может вернуть 100 МБ HTML-дамп стектрейса, что моментально забьет диск базы логов.
2. Сохранение секретных токенов в логах: заголовки авторизации (`Authorization`, секретные токены) должны маскироваться перед записью в лог (`whsec_***`).
3. Блокирующий синхронный INSERT логов в БД доставки: если база логов тормозит, воркеры отправки прекратят доставлять вебхуки.

## На собеседовании

**Вопрос (Stripe/VK):** Зачем платформа вебхуков предоставляет клиентам UI со сниппетами ответов их же собственных серверов?
**Ответ:** Это снижает нагрузку на службу технической поддержки на 80%. Разработчик интегратора может зайти в Dashboard, увидеть точный HTTP 500 от своего сервера, текст ошибки (например, `panic: runtime error: invalid memory address`) и время задержки, локализовав баг в своем бэкенде без обращения к инженерам платформы.
