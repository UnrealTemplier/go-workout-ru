# [HMAC-Подпись]: промышленный стандарт заголовка X-Signature-256: sha256=<hex>

## Условие

17. **[HMAC-Подпись]**: Перед отправкой вычисли HMAC-SHA256 от тела запроса с использованием секрета. Добавь заголовок `X-Signature-256: sha256=<hex>`.

### Исходная формулировка

**[HMAC-Подпись]**: Перед отправкой вычисли HMAC-SHA256 от тела запроса с использованием секрета. Добавь заголовок `X-Signature-256: sha256=<hex>`.

## Теория

Формат заголовка `X-Signature-256: sha256=<hex>` является де-факто стандартом экосистемы GitHub API.
Спецификация требует:
1. Имя заголовка: `X-Signature-256` (или `X-Hub-Signature-256`).
2. Префикс значения: строго строчными буквами `sha256=`.
3. Тело подписи: шестнадцатеричный дайджест (64 символа hex в нижнем регистре `[0-9a-f]`).
4. Подписание строго сырого тела запроса (`raw body`). Никакие модификации пробелов, форматирования или перекодирования не допускаются.

## Решение по шагам

1. Создайте функцию `GenerateGitHubSignature(payload []byte, secret string) string`.
2. Реализуйте функцию парсинга и проверки `ValidateGitHubSignature(payload []byte, secret string, header string) bool`.
3. Обработайте граничные случаи: отсутствие префикса, некорректная длина hex-хэша, повреждение тела.

## Код решения

**`github_style_signer.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	"strings"
)

const HeaderSignature256 = "X-Signature-256"

func GenerateGitHubSignature(payload []byte, secret string) string {
	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write(payload)
	return "sha256=" + hex.EncodeToString(mac.Sum(nil))
}

func ValidateGitHubSignature(payload []byte, secret string, header string) bool {
	if !strings.HasPrefix(header, "sha256=") {
		return false
	}

	receivedHex := strings.TrimPrefix(header, "sha256=")
	if len(receivedHex) != 64 {
		return false
	}

	expectedSig := GenerateGitHubSignature(payload, secret)
	return subtle.ConstantTimeCompare([]byte(header), []byte(expectedSig)) == 1
}

func main() {
	secret := "github_webhook_secret_key"
	payload := []byte(`{"action":"opened","issue":{"number":42}}`)

	sig := GenerateGitHubSignature(payload, secret)
	fmt.Printf("%s: %s\n", HeaderSignature256, sig)

	fmt.Println("Valid:", ValidateGitHubSignature(payload, secret, sig))
	fmt.Println("Invalid prefix:", ValidateGitHubSignature(payload, secret, "sha1=abcd"))
	fmt.Println("Invalid body:", ValidateGitHubSignature([]byte(`{}`), secret, sig))
}
```

## Под капотом

Проверка длины hex-строки (`len(receivedHex) != 64`) выполняется до вызова `subtle.ConstantTimeCompare`. Длина SHA-256 дайджеста математически строго составляет 32 байта, что дает ровно 64 hex-символа. Если длина строки отличается, запрос можно отбросить немедленно без риска утечки по сторонним каналам тайминга.

## Подводные камни

1. Использование верхнего регистра в hex-строке (`EncodeToString` дает lower-case, но некоторые клиенты конвертируют в upper-case): при сравнении hex-строк регистр должен быть нормализован к нижнему (`strings.ToLower`).
2. Неполная передача тела: если при чтении HTTP-потока произошел обрыв связи (`unexpected EOF`), проверка подписи должна упасть с ошибкой, а не с ложноположительным результатом.
3. Пропуск пробелов: заголовок вида `sha256 = ...` с пробелами не должен ломать парсер.

## На собеседовании

**Вопрос (GitHub/VK):** Почему GitHub перешел с заголовка `X-Hub-Signature` (SHA-1) на `X-Signature-256` (SHA-256)?
**Ответ:** Алгоритм SHA-1 был признан криптографически уязвимым к атакам нахождения коллизий (атака SHAttered в 2017 году). Хотя в составе HMAC алгоритм SHA-1 всё ещё сохраняет определенную стойкость, индустриальные стандарты безопасности (NIST, PCI DSS) требуют полного отказа от SHA-1 в пользу SHA-256 для исключения любых рисков компрометации данных.
