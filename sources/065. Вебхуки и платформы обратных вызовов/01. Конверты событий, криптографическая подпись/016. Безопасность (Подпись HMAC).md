# Безопасность (Подпись HMAC): использование уникальных клиентских ключей и заголовка X-Signature

## Условие

16. **Безопасность (Подпись HMAC)**: Твой клиент должен знать, что вебхук пришел именно от тебя, а не от хакера. Перед отправкой вычисли HMAC-SHA256 подпись от тела (body) JSON, используя уникальный `secret_key` клиента. Добавь эту подпись в HTTP-заголовок `X-Signature`.

### Исходная формулировка

**Безопасность (Подпись HMAC)**: Твой клиент должен знать, что вебхук пришел именно от тебя, а не от хакера. Перед отправкой вычисли HMAC-SHA256 подпись от тела (body) JSON, используя уникальный `secret_key` клиента. Добавь эту подпись в HTTP-заголовок `X-Signature`.

## Теория

Каждый клиент webhook-платформы должен иметь собственный независимый секретный ключ (`secret_key`).
Использование одного глобального ключа для всех клиентов платформы недопустимо: компрометация секрета одного клиента позволит ему генерировать поддельные запросы от имени платформы для всех остальных клиентов сервиса.
Архитектурная схема отправки:
1. Загрузка конфигурации подписчика по его `EndpointID` из защищенного хранилища (Postgres/Vault/KMS).
2. Вычисление `HMAC-SHA256(client_secret, body)`.
3. Добавление подписи в заголовок `X-Signature`.
4. Передача запроса клиенту.

## Решение по шагам

1. Создайте структуру `EndpointConfig` с уникальным секретом для каждого клиента.
2. Напишите функцию `SignForClient(body []byte, clientSecret string) string`.
3. Продемонстрируйте вычисление разных подписей для одного и того же тела события при отправке разным клиентам.

## Код решения

**`multi_client_hmac.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

type ClientEndpoint struct {
	ID        string
	TargetURL string
	SecretKey string
}

func SignForClient(payload []byte, secretKey string) string {
	mac := hmac.New(sha256.New, []byte(secretKey))
	mac.Write(payload)
	return hex.EncodeToString(mac.Sum(nil))
}

func main() {
	payload := []byte(`{"event":"balance.replenished","amount":15000}`)

	clientA := ClientEndpoint{ID: "client_alpha", SecretKey: "whsec_alpha_key_111"}
	clientB := ClientEndpoint{ID: "client_beta", SecretKey: "whsec_beta_key_222"}

	sigA := SignForClient(payload, clientA.SecretKey)
	sigB := SignForClient(payload, clientB.SecretKey)

	fmt.Printf("Client Alpha [ID: %s] Signature: %s\n", clientA.ID, sigA)
	fmt.Printf("Client Beta  [ID: %s] Signature: %s\n", clientB.ID, sigB)
	fmt.Printf("Signatures are distinct: %v\n", sigA != sigB)
}
```

## Под капотом

Ключи `client_secret` в базе данных платформы должны храниться в зашифрованном виде (Envelope Encryption с использованием HashiCorp Vault или AWS KMS). Если база данных подвергнется утечке, злоумышленники не смогут прочитать секреты клиентов в открытом виде и скомпрометировать их вебхуки.

## Подводные камни

1. Хранение секретов клиентов в открытом виде (plaintext) в реляционной БД: риск массовой компрометации при SQL-инъекции.
2. Одинаковый секрет для тестового (sandbox) и боевого (production) контура: тестирование на sandbox приведет к возможности подделки запросов на проде.
3. Отсутствие валидации длины ключа: ключ короче 128 бит (16 байт) уязвим к полному перебору (brute-force). Минимальный размер секрета — 256 бит (32 байта).

## На собеседовании

**Вопрос (Ozon/Stripe):** Как безопасно хранить секреты вебхуков клиентов в базе данных платформы?
**Ответ:** Секреты клиентов нельзя хэшировать в одну сторону как пароли (`bcrypt`), так как платформе необходимо использовать исходный секрет для вычисления исходящего HMAC. Применяется **Envelope Encryption (конвертное шифрование)**: каждый секрет шифруется уникальным ключом данных (Data Encryption Key, DEK) по алгоритму AES-256-GCM, а DEK шифруется мастер-ключом (Master Key, KEK) в аппаратном модуле безопасности (HSM / KMS / Vault).
