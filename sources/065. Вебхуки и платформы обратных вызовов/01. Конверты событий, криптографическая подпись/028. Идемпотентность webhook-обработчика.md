## Теория

Идемпотентность бизнес-логики на стороне получателя вебхука должна быть гарантирована на уровне СУБД (PostgreSQL / MySQL) через **State Machine (конечный автомат состояний)** и транзакционные блокировки.
Типичный жизненный цикл заказа:
`NEW -> PENDING -> PAID -> SHIPPED -> DELIVERED`
Если приходит вебхук `order.paid`:
1. Если заказ в состоянии `NEW` или `PENDING`: статус обновляется на `PAID`, создаются бухгалтерские проводки, транзакция коммитится.
2. Если заказ **уже** в состоянии `PAID`, `SHIPPED` или `DELIVERED`: вебхук признается дубликатом. Транзакция завершается успехом (`ROLLBACK` изменений или пустой `SELECT`), и хэндлер возвращает `200 OK` отправителю.
3. Если заказ в терминальном статусе `CANCELLED`: перевод в `PAID` недопустим (конфликт бизнес-логики, логирование инцидента).

## Решение по шагам

1. Опишите доменную структуру заказа `Order` со статусами.
2. Реализуйте функцию обработки вебхука с проверкой допустимости перехода в конечный автомат.
3. Защитите операцию мьютексом (эмулируя `SELECT ... FOR UPDATE` в СУБД).
4. Протестируйте повторную доставку события оплаты для уже оплаченного заказа.

## Код решения

**`state_machine_idempotency.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type OrderStatus string

const (
	OrderCreated   OrderStatus = "CREATED"
	OrderPaid      OrderStatus = "PAID"
	OrderShipped   OrderStatus = "SHIPPED"
	OrderCancelled OrderStatus = "CANCELLED"
)

type Order struct {
	ID     string
	Status OrderStatus
	Total  float64
}

type OrderRepository struct {
	mu     sync.Mutex
	orders map[string]*Order
}

func NewOrderRepository() *OrderRepository {
	return &OrderRepository{
		orders: map[string]*Order{
			"ord_101": {ID: "ord_101", Status: OrderCreated, Total: 3500.0},
		},
	}
}

// ProcessPaymentWebhook обрабатывает событие оплаты идемпотентно
func (r *OrderRepository) ProcessPaymentWebhook(ctx context.Context, orderID string) (actionTaken bool, err error) {
	r.mu.Lock() // Эквивалент BEGIN; SELECT * FROM orders WHERE id = $1 FOR UPDATE;
	defer r.mu.Unlock()

	order, exists := r.orders[orderID]
	if !exists {
		return false, fmt.Errorf("order %s not found", orderID)
	}

	switch order.Status {
	case OrderCreated:
		order.Status = OrderPaid
		fmt.Printf("[DB Commit] Order %s transitioned to PAID. Triggering shipping.\n", orderID)
		return true, nil
	case OrderPaid, OrderShipped:
		// Идемпотентный возврат: заказ уже оплачен
		fmt.Printf("[DB No-Op] Order %s is already %s. Acknowledging duplicate webhook without side effects.\n", orderID, order.Status)
		return false, nil
	case OrderCancelled:
		return false, fmt.Errorf("illegal state transition: cannot pay cancelled order %s", orderID)
	default:
		return false, fmt.Errorf("unknown status %s", order.Status)
	}
}

func main() {
	repo := NewOrderRepository()
	ctx := context.Background()

	// 1. Первая доставка вебхука
	fmt.Println("--- Event Delivery 1 ---")
	action1, err1 := repo.ProcessPaymentWebhook(ctx, "ord_101")
	fmt.Printf("Result 1: actionTaken=%v, err=%v\n\n", action1, err1)

	// 2. Повторная доставка того же вебхука (сетевой ретрай)
	fmt.Println("--- Event Delivery 2 (Duplicate) ---")
	action2, err2 := repo.ProcessPaymentWebhook(ctx, "ord_101")
	fmt.Printf("Result 2: actionTaken=%v, err=%v\n", action2, err2)
}
```

## Под капотом

В PostgreSQL идемпотентное обновление реализуется через условный SQL-запрос:
`UPDATE orders SET status = 'PAID' WHERE id = $1 AND status = 'CREATED' RETURNING id;`
Если строка обновилась (`rows affected == 1`), сервис инициирует создание отгрузки. Если `rows affected == 0`, проверяется текущий статус: если заказ уже `PAID`, операция считается успешно завершенной (no-op success), предотвращая отправку повторных нотификаций клиенту.

## Подводные камни

1. Возврат ошибки 400/500 при получении дубликата: если вернуть ошибку на уже оплаченный заказ, платформа отправителя продолжит ретраить вебхук до исчерпания лимита попыток. На дубликаты необходимо возвращать HTTP 200 OK!
2. Отсутствие блокировки строки (`FOR UPDATE`): два параллельно пришедших запроса на оплату могут одновременно вычитать статус `CREATED` и дважды инициировать отгрузку.
3. Забытая проверка терминальных статусов: оплата отмененного (`CANCELLED`) заказа должна вести к созданию задачи на возврат средств.

## На собеседовании

**Вопрос (Яндекс/Stripe):** Почему вебхук-приемник должен возвращать HTTP 200 OK, даже если полученный вебхук является дубликатом и никаких изменений в БД не производилось?
**Ответ:** Для платформы вебхуков код 200 OK означает: «Событие доставлено, внешняя система приняла его и не требует повторных отправок». Если вернуть ошибку (например, `409 Conflict`), платформа сочтет доставку неудачной и продолжит присылать повторы согласно политике Exponential Backoff, создавая бесполезную нагрузку на сеть и базу данных интегратора.
