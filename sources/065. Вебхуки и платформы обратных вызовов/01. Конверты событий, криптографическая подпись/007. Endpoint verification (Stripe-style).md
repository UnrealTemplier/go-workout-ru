# Endpoint verification (Stripe-style): рукопожатие Challenge-Response

## Условие

7. **Endpoint verification (Stripe-style)**: При регистрации отправляйте GET-запрос с `challenge` параметром. Клиент должен вернуть challenge в теле ответа — это подтверждает владение доменом.

### Исходная формулировка

**Endpoint verification (Stripe-style)**: При регистрации отправляйте GET-запрос с `challenge` параметром. Клиент должен вернуть challenge в теле ответа — это подтверждает владение доменом.

## Теория

При регистрации вебхука в современных API (Stripe, Slack, Meta/WhatsApp API) используется механизм подтверждения владения эндпоинтом — **Challenge-Response Verification**.
До того, как на URL начнут поступать реальные конфиденциальные события (например, финансовые транзакции), платформа отправляет проверочный GET или POST запрос с криптографическим параметром `challenge` (случайная строка или токен).
Сервер клиента обязан:
1. Принять входящий запрос проверки.
2. Проверить параметры (или подпись).
3. Вернуть точное значение `challenge` в теле ответа со статусом 200 OK.
Если эндпоинт вернул неверный ответ, таймаут или 4xx/5xx, регистрация подписки отклоняется. Это гарантирует, что пользователь не указал чужой URL в качестве мишени для спама или DoS-атаки.

## Решение по шагам

1. Реализуйте функцию `VerifyEndpointChallenge(ctx context.Context, client *http.Client, endpointURL string) (bool, error)`.
2. Сгенерируйте случайный 32-символьный challenge-токен.
3. Отправьте GET-запрос на `endpointURL?challenge=...` с коротким таймаутом (3 секунды).
4. Проверьте статус ответа 200 OK и сравните тело ответа с исходным токеном.
5. Продемонстрируйте работу механизма на сервере-клиенте с помощью `httptest.Server`.

## Код решения

**`challenge_verification.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/url"
	"strings"
	"time"
)

func GenerateChallengeToken() string {
	b := make([]byte, 16)
	_, _ = rand.Read(b)
	return hex.EncodeToString(b)
}

func VerifyEndpointChallenge(ctx context.Context, client *http.Client, rawTargetURL string) (bool, error) {
	challenge := GenerateChallengeToken()

	parsedURL, err := url.Parse(rawTargetURL)
	if err != nil {
		return false, fmt.Errorf("invalid URL: %w", err)
	}

	q := parsedURL.Query()
	q.Set("challenge", challenge)
	parsedURL.RawQuery = q.Encode()

	req, err := http.NewRequestWithContext(ctx, http.MethodGet, parsedURL.String(), nil)
	if err != nil {
		return false, err
	}
	req.Header.Set("User-Agent", "GoWorkout-Verification-Bot/1.0")

	resp, err := client.Do(req)
	if err != nil {
		return false, fmt.Errorf("verification request failed: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return false, fmt.Errorf("unexpected status code: %d", resp.StatusCode)
	}

	body, err := io.ReadAll(io.LimitReader(resp.Body, 512))
	if err != nil {
		return false, err
	}

	receivedChallenge := strings.TrimSpace(string(body))
	if receivedChallenge != challenge {
		return false, fmt.Errorf("challenge mismatch: expected %s, got %s", challenge, receivedChallenge)
	}

	return true, nil
}

func main() {
	clientServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		challenge := r.URL.Query().Get("challenge")
		if challenge == "" {
			w.WriteHeader(http.StatusBadRequest)
			return
		}
		w.Header().Set("Content-Type", "text/plain")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(challenge))
	}))
	defer clientServer.Close()

	httpClient := &http.Client{Timeout: 3 * time.Second}
	ok, err := VerifyEndpointChallenge(context.Background(), httpClient, clientServer.URL)
	if err != nil {
		fmt.Printf("Verification error: %v\n", err)
	} else {
		fmt.Printf("Endpoint Verified Successfully: %v\n", ok)
	}
}
```

ℹ️ Проверка рукопожатия

## Под капотом

Процедура верификации предотвращает ситуацию, когда злоумышленник указывает в качестве URL вебхука адрес сторонней жертвы, инициируя распределенную атаку типа HTTP-флуд за счет трафика платформы. Кроме того, это гарантирует, что клиентский бэкенд уже задеплоен, его сетевые порты открыты, а TLS-сертификат валиден.

## Подводные камни

1. Длинный таймаут верификации: если клиентский сервер недоступен, веб-интерфейс регистрации подписки зависнет. Таймаут challenge-запроса должен быть жестко ограничен (2–3 секунды).
2. Разрешение редиректов (301/302): при проверке эндпоинта следование редиректам может увести запрос на сторонний сервер или во внутреннюю сеть. `client.CheckRedirect` должен блокировать перенаправления.
3. Проверка без очистки пробелов (`TrimSpace`): некоторые веб-фреймворки добавляют символ новой строки `\n` в конец ответа plain text, что может приводить к ложным ошибкам сравнения строк.

## На собеседовании

**Вопрос (Slack/T-Банк):** Какие существуют альтернативы синхронному GET Challenge-Response при регистрации вебхуков?
**Ответ:** 1. **DNS TXT верификация:** интегратор добавляет специальную TXT запись в свой домен (`_webhook-verify.client.com = token`).
2. **Meta-файл по HTTPS:** клиент выкладывает токен по фиксированному пути `/.well-known/webhook-verification.txt`.
3. **Асинхронная верификация первым вебхуком:** подписка создается в статусе `pending_verification`, платформа отправляет тестовое событие `webhook.verify` с кодом подтверждения, а разработчик вручную вводит этот код в UI панели управления платформы.
