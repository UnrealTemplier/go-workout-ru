# Защита диспетчера от атак Slowloris со стороны приемников

## Условие

Если сервер-приемник отвечает медленно (читает по 1 байту в секунду), твой воркер заблокируется. Настрой `http.Client` с жесткими `Timeout` (например, 5 сек) и `ResponseHeaderTimeout`.

### Исходная формулировка

**[Защита от Slow Loris]**: Если сервер-приемник отвечает медленно (читает по 1 байту в секунду), твой воркер заблокируется. Настрой `http.Client` с жесткими `Timeout` (например, 5 сек) и `ResponseHeaderTimeout`.

## Теория

Атака **Slowloris** со стороны вредоносного клиента:
Злоумышленник регистрирует вебхук-эндпоинт на сервере, который намеренно открывает TCP-соединение и вычитывает входящий HTTP-запрос по 1 байту в 10 секунд, либо отправляет заголовки ответа с колоссальными паузами.

### Катастрофические последствия для платформы:
Если HTTP-клиент диспетчера использует дефолтные настройки:
```go
client := &http.Client{} // Timeout = 0 (БЕСКОНЕЧНЫЙ!)
```
Каждый воркер платформы зависнет на часы в системном вызове `write()` или `read()`. Очень быстро все 100-1000 воркеров диспетчера окажутся заблокированными на одном медленном клиенте, и доставка вебхуков ВСЕМ остальным клиентам платформы полностью остановится!

### Тюнинг таймаутов `http.Client` в Go:
1. **`Transport.ResponseHeaderTimeout`:** Время от отправки полного тела запроса до получения первого байта заголовков ответа (например, 3–5 секунд).
2. **`Transport.TLSHandshakeTimeout`:** Лимит на рукопожатие TLS (например, 4 секунды).
3. **`Transport.ExpectContinueTimeout`:** Лимит на `100-continue`.
4. **`Client.Timeout`:** Суммарный жесткий дедлайн на весь цикл доставки (например, 5–10 секунд). Оборачивает весь запрос с установлением соединения, отправкой и полным вычитыванием ответа.

## Решение по шагам

1. Сконфигурируйте `http.Transport` со строгими сетевыми таймаутами.
2. Установите `ResponseHeaderTimeout = 3 * time.Second`.
3. Установите общий `http.Client.Timeout = 5 * time.Second`.
4. Напишите эмулятор сервера Slowloris, удерживающего ответ, и убедитесь, что клиент прерывает зависшее соединение.

## Код решения

**`slowloris_defense.go`**

```go
package main

import (
	"context"
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"time"
)

// NewHardenedWebhookClient создает устойчивый к Slowloris HTTP-клиент
func NewHardenedWebhookClient(totalTimeout time.Duration) *http.Client {
	transport := &http.Transport{
		DialContext: (&net.Dialer{
			Timeout:   2 * time.Second, // Максимум 2 секунды на открытие TCP-сокета
			KeepAlive: 30 * time.Second,
		}).DialContext,
		TLSHandshakeTimeout:   2 * time.Second, // Лимит на TLS handshake
		ResponseHeaderTimeout: 3 * time.Second, // Сервер обязан отдать заголовки за 3 сек!
		ExpectContinueTimeout: 1 * time.Second,
		MaxIdleConns:          100,
		IdleConnTimeout:       30 * time.Second,
	}

	return &http.Client{
		Transport: transport,
		Timeout:   totalTimeout, // Жесткий общий дедлайн на весь жизненный цикл запроса
	}
}

func main() {
	// Создаем тестовый вредоносный сервер Slowloris, который зависает на 10 секунд
	slowServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Println("[SLOW SERVER] Входящее соединение принято, намеренно засыпаем на 10 секунд...")
		time.Sleep(10 * time.Second)
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("too late"))
	}))
	defer slowServer.Close()

	client := NewHardenedWebhookClient(3 * time.Second)

	fmt.Println("=== Отправка вебхука на медленный сервер (Timeout = 3 сек) ===")
	start := time.Now()

	req, _ := http.NewRequestWithContext(context.Background(), http.MethodPost, slowServer.URL, nil)
	resp, err := client.Do(req)

	elapsed := time.Since(start)

	if err != nil {
		fmt.Printf("УСПЕХ ЗАЩИТЫ: Запрос прерван по таймауту ровно через %v!\n", elapsed.Round(time.Millisecond))
		fmt.Printf("Текст ошибки клиента: %v\n", err)
	} else {
		resp.Body.Close()
		fmt.Println("Ошибка: Запрос не был вовремя прерван!")
	}
}
```

## Под капотом

Внутри `http.Transport` параметр `ResponseHeaderTimeout` запускает внутренний таймер сразу после завершения отправки тела запроса `req.Body`. Если целевой сервер не успел прислать валидную строку HTTP-статуса и заголовки до истечения таймера, транспорт насильно закрывает сокет через вызов `tcpConn.Close()`, возвращая ошибку `net/http: timeout awaiting response headers`. Воркер мгновенно возвращается в пул, готовый обслуживать других клиентов.

## Подводные камни

1. **Использование `http.DefaultClient` в продакшене:** `http.DefaultClient` имеет `Timeout = 0`. Никогда не используйте дефолтный клиент для внешних сетевых вызовов, это главная причина зависания микросервисов в продакшене.
2. **Не вычитывать `io.Copy(io.Discard, resp.Body)`:** При получении ошибочных статусов от клиентов необходимо вычитывать остаток ответа и закрывать `Body`, иначе TCP-соединение не вернется в пул переиспользования.

## На собеседовании

**Вопрос:** Чем отличается `http.Client.Timeout` от таймаута контекста `context.WithTimeout(ctx, duration)`?

**Ответ:** `http.Client.Timeout` — это высокоуровневый таймер, управляемый самим клиентом. Он включает все этапы: DNS-резолв, TCP-коннект, TLS-хендшейк, отправку тела, ожидание заголовков и чтение тела ответа до EOF.
`context.WithTimeout` делает то же самое, но дает вызывающей стороне внешний контроль: запрос можно прервать досрочно при отмене клиентского запроса или получении сигнала остановки сервиса (SIGTERM). В качественном коде рекомендуется комбинировать оба подхода.
