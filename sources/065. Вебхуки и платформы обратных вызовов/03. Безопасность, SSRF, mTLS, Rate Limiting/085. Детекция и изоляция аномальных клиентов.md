# Детекция и изоляция аномальных клиентов (Hot Endpoint Detection)

## Условие

Детектируйте endpoints, которые генерируют disproportional трафик (один клиент потребляет 50% delivery capacity). Предлагайте им batch mode или отдельный tier.

### Исходная формулировка

**Hot endpoint detection**: Детектируйте endpoints, которые генерируют disproportional трафик (один клиент потребляет 50% delivery capacity). Предлагайте им batch mode или отдельный tier.

## Теория

В мультиарендных (Multi-Tenant) платформах вебхуков возникает проблема «шумного соседа» (**Noisy Neighbor Problem**).

Если один крупный клиент (например, гигантский маркетплейс) генерирует 10 000 событий в секунду, а все остальные 500 клиентов — по 1–2 события в секунду, неизолированная очередь доставки будет на 99% забита задачами крупного клиента. Мелкие клиенты испытают колоссальные задержки доставки (Starvation).

### Архитектура Hot Endpoint Detection & Fair Queuing:
1. **Анализ распределения трафика (Heavy Hitters / Top-K):**
   - Использование вероятностных алгоритмов (Count-Min Sketch или Space-Saving) в скользящем окне 60 секунд.
   - Выявление эндпоинтов, чья доля превышает порог \(T = 20\%\) от общей емкости кластера.
2. **Динамическая изоляция:**
   - **Dedicated Tier (Изолированная очередь):** Задачи горячего клиента автоматически переводятся из очереди общего пула (`shared-pool`) в выделенную очередь (`tenant-hot-pool`).
   - **Batch Suggestion:** Платформа автоматически отправляет рекомендацию перейти на пакетный эндпоинт (`POST /webhooks/batch`), где до 100 событий передаются в одном HTTP-запросе.

## Решение по шагам

1. Создайте структуру `TrafficTracker` для подсчета доставок по клиентам за скользящее окно времени.
2. Реализуйте метод `RecordDelivery(tenantID string)`.
3. Напишите детектор `DetectHotTenants(thresholdPercent float64) []string`.
4. Реализуйте маршрутизатор очереди, направляющий горячих клиентов в изолированный воркер-пул.

## Код решения

**`hot_tenant_detector.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type TenantTrafficTracker struct {
	mu           sync.RWMutex
	totalRequests atomic.Int64
	tenantCounts map[string]*atomic.Int64
}

func NewTenantTrafficTracker() *TenantTrafficTracker {
	return &TenantTrafficTracker{
		tenantCounts: make(map[string]*atomic.Int64),
	}
}

func (t *TenantTrafficTracker) Record(tenantID string) {
	t.totalRequests.Add(1)

	t.mu.RLock()
	counter, exists := t.tenantCounts[tenantID]
	t.mu.RUnlock()

	if exists {
		counter.Add(1)
		return
	}

	t.mu.Lock()
	defer t.mu.Unlock()
	if counter, exists = t.tenantCounts[tenantID]; exists {
		counter.Add(1)
		return
	}

	var newCounter atomic.Int64
	newCounter.Store(1)
	t.tenantCounts[tenantID] = &newCounter
}

// DetectHotTenants возвращает список клиентов, потребляющих больше thresholdRatio (например, > 30%)
func (t *TenantTrafficTracker) DetectHotTenants(thresholdRatio float64) map[string]float64 {
	total := float64(t.totalRequests.Load())
	if total == 0 {
		return nil
	}

	hotTenants := make(map[string]float64)

	t.mu.RLock()
	defer t.mu.RUnlock()

	for tenantID, counter := range t.tenantCounts {
		count := float64(counter.Load())
		ratio := count / total
		if ratio >= thresholdRatio {
			hotTenants[tenantID] = ratio * 100.0
		}
	}

	return hotTenants
}

func main() {
	tracker := NewTenantTrafficTracker()

	// Симулируем трафик:
	// Клиент "mega_corp" генерирует 700 запросов
	// Клиенты "shop_1" .. "shop_3" генерируют по 100 запросов
	for i := 0; i < 700; i++ {
		tracker.Record("tenant_mega_corp")
	}
	for i := 0; i < 100; i++ {
		tracker.Record("tenant_shop_alpha")
		tracker.Record("tenant_shop_beta")
		tracker.Record("tenant_shop_gamma")
	}

	fmt.Println("=== Анализ профиля нагрузки вебхук-платформы ===")
	fmt.Printf("Всего доставлено событий: %d\n", tracker.totalRequests.Load())

	// Ищем тех, кто занимает более 25% емкости
	hotList := tracker.DetectHotTenants(0.25)

	for tenant, share := range hotList {
		fmt.Printf("[ALERT: HOT ENDPOINT DETECTED] Клиент '%s' потребляет %.1f%% емкости платформы!\n", tenant, share)
		fmt.Println("  -> Действие: Маршрутизация в dedicated очередь 'hot-tenants-queue'.")
		fmt.Println("  -> Предложение клиенту: Автоматическое переключение на Batch Webhooks API.")
	}
}
```

ℹ️ Детекция аномального трафика клиентов для справедливой изоляции ресурсов (Fair Sharing)

## Под капотом

В распределенных брокерах (Kafka) проблема шумного соседа решается механизмом **Weighted Fair Queuing (WFQ)** или встроенными **Client Quotas**. На уровне брокера настраивается квота `request_percentage` или `byte_rate` по clientId. Если `tenant_mega_corp` превышает квоту, Kafka начинает задерживать (throttle) ответы на запросы этого клиента, не давая ему монополизировать сетевые потоки брокера.

## Подводные камни

1. **Утечка памяти при миллионах уникальных клиентов:** Ведение точного счетчика в `map[string]*atomic.Int64` для миллионов клиентов приведет к переполнению памяти. В проде следует использовать вероятностный алгоритм **Count-Min Sketch** фиксированного размера (например, 2 МБ на массив хешей).
2. **Блокировка легитимного трафика:** Изоляция не должна означать отбрасывание запросов. Горячего клиента нужно изолировать в отдельную очередь, чтобы его задержки не влияли на остальных.

## На собеседовании

**Вопрос:** Что такое алгоритм Round-Robin Fair Queueing (DRR) и как он предотвращает голодание (Starvation) вебхуков мелких клиентов?

**Ответ:** Алгоритм Deficit Round Robin (DRR) организует отдельные логические очереди для каждого клиента. Диспетчер обходит очереди по кругу, извлекая из очереди каждого клиента строго квант сообщений (например, 5 задач). Если у гиганта в очереди 100 000 задач, а у мелкого магазина — 1 задача, мелкий магазин гарантированно получит доставку на первом же круге обхода, не дожидаясь разбора завала гиганта.
