# Webhook с подписью тела (Signature v2: payload digest): стандарт RFC 3230

## Условие

63. **Webhook с подписью тела (Signature v2: payload digest).**: Модифицируйте подпись, включив в неё HTTP-метод, путь и digest тела (SHA-256), чтобы избежать подделки на уровне прокси.

### Исходная формулировка

**Webhook с подписью тела (Signature v2: payload digest).**: Модифицируйте подпись, включив в неё HTTP-метод, путь и digest тела (SHA-256), чтобы избежать подделки на уровне прокси.

## Теория

В корпоративных спецификациях API (RFC 3230 "Instance Digests in HTTP" и IETF draft "HTTP Message Signatures") схема подписи v2 отделяет дайджест содержимого тела от подписи заголовков:
1. Заголовок `Digest`: содержит криптографический хэш тела:
`Digest: SHA-256=<base64_sha256_hash>`
2. Заголовок `Signature` (или `X-Webhook-Signature-V2`): подписывает псевдо-заголовки запроса и сам дайджест:
`X-Webhook-Signature-V2: sig=HMAC-SHA256(secret, "(request-target): post /wh\ndigest: SHA-256=...\ndate: ...")`
Преимущества схемы v2:
- Промежуточные шлюзы (API Gateway) могут верифицировать неизменность тела по заголовку `Digest`, не имея доступа к секретному ключу клиента.
- Подпись защищает не только тело, но и путь HTTP-запроса (`URL path`), предотвращая атаки подмены маршрута.

## Решение по шагам

1. Реализуйте расчет заголовка `Digest` по RFC 3230: вычисление SHA-256 и кодирование в Base64.
2. Сформируйте подпись v2 над методом, путем, датой и дайджестом.
3. Напишите валидатор на стороне получателя.
4. Протестируйте устойчивость схемы к подмене HTTP-пути.

## Код решения

**`digest_signature_v2.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/base64"
	"encoding/hex"
	"fmt"
	"strings"
	"time"
)

func ComputeRFC3230Digest(body []byte) string {
	sum := sha256.Sum256(body)
	return "SHA-256=" + base64.StdEncoding.EncodeToString(sum[:])
}

func ComputeSignatureV2(secret, method, path, dateStr, digestHeader string) string {
	// Каноничная строка для подписи
	canonical := fmt.Sprintf("(request-target): %s %s\ndate: %s\ndigest: %s",
		strings.ToLower(method), path, dateStr, digestHeader)

	mac := hmac.New(sha256.New, []byte(secret))
	mac.Write([]byte(canonical))
	return hex.EncodeToString(mac.Sum(nil))
}

func VerifySignatureV2(secret, method, path, dateStr, digestHeader, receivedSig string, body []byte) (bool, string) {
	// 1. Проверяем целостность Digest тела
	expectedDigest := ComputeRFC3230Digest(body)
	if digestHeader != expectedDigest {
		return false, "Digest header does not match raw body SHA-256"
	}

	// 2. Проверяем HMAC-подпись заголовков
	expectedSig := ComputeSignatureV2(secret, method, path, dateStr, digestHeader)
	if subtle.ConstantTimeCompare([]byte(receivedSig), []byte(expectedSig)) != 1 {
		return false, "HMAC signature mismatch"
	}

	return true, "OK"
}

func main() {
	secret := "whsec_v2_enterprise_secret_88"
	method := "POST"
	path := "/api/v1/webhooks/orders"
	date := time.Now().UTC().Format(http.TimeFormat)
	body := []byte(`{"order_id":"ord_771","status":"settled"}`)

	digest := ComputeRFC3230Digest(body)
	signature := ComputeSignatureV2(secret, method, path, date, digest)

	fmt.Printf("HTTP Headers for Delivery:\n")
	fmt.Printf("  Digest: %s\n", digest)
	fmt.Printf("  Date: %s\n", date)
	fmt.Printf("  X-Webhook-Signature-V2: %s\n\n", signature)

	// Проверка 1: Валидный запрос
	valid, reason := VerifySignatureV2(secret, method, path, date, digest, signature, body)
	fmt.Printf("Validation 1 (Valid): %v (Reason: %s)\n", valid, reason)

	// Проверка 2: Атака подмены URL path (запрос отправлен на другой эндпоинт)
	valid2, reason2 := VerifySignatureV2(secret, method, "/api/v1/webhooks/refunds", date, digest, signature, body)
	fmt.Printf("Validation 2 (Path Tampered): %v (Reason: %s)\n", valid2, reason2)
}
```

## Под капотом

Включение `(request-target)` в подписываемую строку предотвращает атаку **Request Target Confusion**: если злоумышленник перехватит валидный вебхук, адресованный на эндпоинт `/webhook/low_priority`, он не сможет перенаправить его на `/webhook/high_priority_payment`, так как изменение пути запроса сделает подпись недействительной.

## Подводные камни

1. Несовпадение регистра HTTP-метода: канонизация требует нормализации метода к нижнему регистру (`post`).
2. Разные форматы даты: использование нестандартного формата даты вместо RFC 7231 (`http.TimeFormat`).
3. Использование Hex вместо Base64 в заголовке `Digest`: по RFC 3230 дайджест в заголовке `Digest` обязан кодироваться в Base64.

## На собеседовании

**Вопрос (IETF/Stripe):** В чем преимущество схемы Digest (RFC 3230) над классической схемой Stripe `HMAC(timestamp.body)`?
**Ответ:** Классическая схема Stripe подписывает только тело и время, но не защищает HTTP-заголовки и URI запроса. Схема Digest + HTTP Signature позволяет подписать произвольный набор HTTP-заголовков (`Host`, `Date`, `Content-Type`), метод (`POST`) и конкретный путь (`Path`). Это делает невозможной подмену контекста запроса промежуточными балансировщиками и WAF.
