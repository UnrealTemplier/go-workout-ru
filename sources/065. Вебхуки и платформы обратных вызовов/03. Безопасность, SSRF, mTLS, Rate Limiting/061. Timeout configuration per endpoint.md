# Timeout configuration per endpoint: гранулярные таймауты в настройках подписки

## Условие

61. **Timeout configuration per endpoint**: Дайте клиентам настраивать timeout под их SLA (1s для real-time, 30s для batch processing).

### Исходная формулировка

**Timeout configuration per endpoint**: Дайте клиентам настраивать timeout под их SLA (1s для real-time, 30s для batch processing).

## Теория

Разные типы интеграторов требуют разных таймаутов доставки:
- Serverless-функции (AWS Lambda / Cloud Functions): просыпаются за 200–500 мс, но при холодном старте (Cold Start) могут отвечать 3–5 секунд.
- Крупные ERP-системы (1С, SAP): выполняют проверку складских остатков и могут требовать до 15 секунд.
- Real-time трейдинговые платформы: требуют жесткого таймаута не более 500 мс.
Платформа должна позволять настраивать `delivery_timeout_seconds` индивидуально для каждого зарегистрированного эндпоинта (с системным лимитом, например, от 1 до 30 секунд).
При отправке запроса воркер создает `context.WithTimeout(parentCtx, endpoint.Timeout)`.

## Решение по шагам

1. Добавьте поле `Timeout time.Duration` в профиль подписки `SubscriptionProfile`.
2. Напишите функцию отправки `DeliverWithDynamicTimeout(ctx context.Context, sub SubscriptionProfile, payload []byte) error`.
3. Валидируйте пользовательский таймаут в диапазоне \([1\text{с}, 30\text{с}]\).
4. Протестируйте поведение при превышении индивидуального таймаута.

## Код решения

**`dynamic_timeout.go`**

```go
package main

import (
	"bytes"
	"context"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

type EndpointProfile struct {
	ID        string
	TargetURL string
	Timeout   time.Duration
}

func ValidateTimeout(t time.Duration) (time.Duration, error) {
	if t < 1*time.Second {
		return 0, errors.New("timeout too low: minimum allowed is 1s")
	}
	if t > 30*time.Second {
		return 0, errors.New("timeout too high: maximum allowed is 30s")
	}
	return t, nil
}

func DeliverEvent(parentCtx context.Context, client *http.Client, ep EndpointProfile, payload []byte) error {
	ctx, cancel := context.WithTimeout(parentCtx, ep.Timeout)
	defer cancel()

	req, err := http.NewRequestWithContext(ctx, http.MethodPost, ep.TargetURL, bytes.NewReader(payload))
	if err != nil {
		return err
	}
	req.Header.Set("Content-Type", "application/json")

	resp, err := client.Do(req)
	if err != nil {
		if errors.Is(ctx.Err(), context.DeadlineExceeded) {
			return fmt.Errorf("delivery exceeded endpoint configured timeout (%v)", ep.Timeout)
		}
		return err
	}
	defer resp.Body.Close()

	if resp.StatusCode < 200 || resp.StatusCode >= 300 {
		return fmt.Errorf("remote status %d", resp.StatusCode)
	}
	return nil
}

func main() {
	// Сервер с искусственной задержкой в 800 мс
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(800 * time.Millisecond)
		w.WriteHeader(http.StatusOK)
	}))
	defer server.Close()

	client := &http.Client{}

	// Клиент 1 с коротким таймаутом (500 мс) — должен упасть
	epFast := EndpointProfile{ID: "ep_fast", TargetURL: server.URL, Timeout: 500 * time.Millisecond}
	err1 := DeliverEvent(context.Background(), client, epFast, []byte(`{}`))
	fmt.Printf("Endpoint 1 (500ms timeout) result: %v\n", err1)

	// Клиент 2 с достаточным таймаутом (2000 мс) — должен успешно выполниться
	epSlow := EndpointProfile{ID: "ep_slow", TargetURL: server.URL, Timeout: 2 * time.Second}
	err2 := DeliverEvent(context.Background(), client, epSlow, []byte(`{}`))
	fmt.Printf("Endpoint 2 (2000ms timeout) result: %v\n", err2)
}
```

ℹ️ Проверка работы индивидуальных таймаутов

## Под капотом

Создание `context.WithTimeout(parentCtx, ep.Timeout)` привязывает к запросу таймер времени выполнения. Воркер не пересоздает `http.Client` (что привело бы к сбросу пула TCP-соединений), а использует один глобальный `http.Client` со свободным таймаутом, делегируя контроль времени контексту конкретного запроса.

## Подводные камни

1. Создание нового `http.Client` на каждый запрос: приводит к уничтожению пула TCP-соединений и колоссальному расходу системных портов.
2. Разрешение пользователям указывать таймаут 5 минут: заблокирует пул воркеров платформы. Максимальный порог обязан быть жестко ограничен (не более 30 с).
3. Забытый вызов `defer cancel()`: утечка таймера контекста в рантайме Go.

## На собеседовании

**Вопрос (Ozon/Wildberries):** Почему не рекомендуется менять поле `client.Timeout` у глобального `http.Client` динамически для каждого запроса?
**Ответ:** Поле `Timeout` структуры `http.Client` не защищено внутренними мьютексами и читается конкурентно всеми горутинами, использующими данный клиент. Изменение `client.Timeout = dynamicTimeout` во время работы приведет к состоянию гонки данных (Data Race), детектируемому флагом `-race`. Корректный подход — настраивать `http.Client` без общего таймаута или с максимальным потолком, а индивидуальный таймаут каждого запроса передавать через `context.WithTimeout` в `http.NewRequestWithContext`.
