### Исходная формулировка

## Теория

Когда система получателя вебхуков развернута в сотнях реплик в нескольких Kubernetes-кластерах, обычная проверка в локальной памяти не защищает от параллельного выполнения двух одинаковых запросов, пришедших с разницей в 1 миллисекунду.
Для обеспечения глобальной межсерверной идемпотентности применяется **Distributed Lock (Распределенная блокировка)** в Redis:
```
SET lock:webhook:<event_id> <worker_uuid> NX PX 30000
```
- `NX`: операция выполняется только если ключ не существует (атомарный захват).
- `PX 30000`: автоматическое освобождение блокировки через 30 секунд при аварийном падении воркера (защита от Deadlock).
- При успешном завершении обработки статус переводится в `COMPLETED` с длительным TTL.

## Решение по шагам

1. Реализуйте распределенный лок `DistributedIdempotencyLock`.
2. Напишите безопасный метод захвата блокировки и ее освобождения через сверку уникального токена владельца (Fence Token).
3. Продемонстрируйте защиту от состояния гонки при параллельном запуске обработки.

## Код решения

**`distributed_idempotency_lock.go`**

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"time"
)

type RedisLockStore struct {
	mu    sync.Mutex
	locks map[string]string // key -> ownerToken
}

func NewRedisLockStore() *RedisLockStore {
	return &RedisLockStore{locks: make(map[string]string)}
}

func (s *RedisLockStore) SetNX(key, token string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if _, exists := s.locks[key]; exists {
		return false
	}
	s.locks[key] = token
	return true
}

func (s *RedisLockStore) Release(key, token string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if current, exists := s.locks[key]; exists && current == token {
		delete(s.locks, key)
		return true
	}
	return false
}

type IdempotentProcessor struct {
	store *RedisLockStore
}

func (p *IdempotentProcessor) ProcessOnce(ctx context.Context, eventID string, task func() error) error {
	tokenBytes := make([]byte, 16)
	_, _ = rand.Read(tokenBytes)
	ownerToken := hex.EncodeToString(tokenBytes)

	key := "lock:event:" + eventID

	// 1. Атомарный захват распределенного лока
	if !p.store.SetNX(key, ownerToken) {
		return errors.New("concurrent execution blocked: event is already locked by another worker")
	}

	defer func() {
		// 2. Освобождение только своим токеном
		p.store.Release(key, ownerToken)
	}()

	fmt.Printf("[Lock Acquired] Processing event: %s\n", eventID)
	return task()
}

func main() {
	store := NewRedisLockStore()
	processor := &IdempotentProcessor{store: store}

	var wg sync.WaitGroup
	eventID := "evt_concurrent_77"

	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			err := processor.ProcessOnce(context.Background(), eventID, func() error {
				fmt.Printf(">>> Worker %d inside critical section!\n", workerID)
				time.Sleep(30 * time.Millisecond)
				return nil
			})
			if err != nil {
				fmt.Printf("Worker %d failed: %v\n", workerID, err)
			}
		}(i)
	}

	wg.Wait()
}
```

## Под капотом

Освобождение лока в Redis через Lua-скрипт `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end` критически важно: если задача воркера 1 затянулась дольше времени аренды (TTL), и лок автоматически снялся, то воркер 2 захватит лок со своим новым токеном. Без сверки токена воркер 1 при завершении удалил бы чужой активный лок воркера 2!

## Подводные камни

1. Освобождение блокировки командой `DEL key` без проверки владельца токена: приводит к снятию чужого активного лока.
2. Отсутствие TTL на лок: если узел упадет по аварии питания, лок останется заблокированным навсегда (Deadlock).
3. Слишком короткий TTL: если обработка занимает 2 секунды, а TTL равен 1 секунде, блокировка истечет до завершения работы.

## На собеседовании

**Вопрос (Redis/Martin Kleppmann):** Почему при реализации распределенного замка для идемпотентности в Redis обязательно проверять `token` владельца при удалении?
**Ответ:** Если воркер А захватил блокировку с TTL = 10 секунд, но подвис на сборке мусора (GC pause) на 11 секунд, Redis автоматически снимет замок по таймеру. Воркер Б успешно захватит этот же замок. Когда воркер А очнется от паузы GC и выполнит обычный `DEL key`, он удалит замок, принадлежащий воркеру Б! Это позволит воркеру В параллельно войти в критическую секцию. Сверка токена через атомарный скрипт предотвращает эту уязвимость.
