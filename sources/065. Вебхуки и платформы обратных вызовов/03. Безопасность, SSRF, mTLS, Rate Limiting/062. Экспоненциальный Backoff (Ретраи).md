# Экспоненциальный Backoff (Ретраи): управление жизненным циклом через Redis Sorted Set

## Условие

62. **Экспоненциальный Backoff (Ретраи)**: Клиент ответил 503 или отвалился по таймауту. Напиши логику повторных попыток. Попытайся отправить вебхук 4 раза с паузами: 2 сек, 4 сек, 8 сек, 16 сек.

### Исходная формулировка

**Экспоненциальный Backoff (Ретраи)**: Клиент ответил 503 или отвалился по таймауту. Напиши логику повторных попыток. Попытайся отправить вебхук 4 раза с паузами: 2 сек, 4 сек, 8 сек, 16 сек.

## Теория

В распределенной системе с миллионами отложенных ретраев хранение расписания в реляционной базе данных может создавать чрезмерную нагрузку на диск.
Высокопроизводительной альтернативой является использование **Redis Sorted Set (ZSET)**:
1. Задачи на ретрай добавляются в ZSET:
`ZADD webhook_retry_schedule <next_timestamp_unix> <delivery_task_json_or_id>`
В качестве score выступает время будущего запуска в секундах/миллисекундах.
2. Воркеры диспетчера периодически (каждые 100 мс) вызывают команду с атомарным извлечением созревших задач:
`ZRANGEBYSCORE webhook_retry_schedule 0 <now_timestamp> LIMIT 0 100`
3. Выбранные задачи удаляются через `ZREM` и отправляются в очередь доставки.
Это обеспечивает производительность в десятки тысяч операций выборки в секунду при минимальном потреблении CPU.

## Решение по шагам

1. Создайте структуру планировщика `RedisRetryScheduler` (эмуляция Redis ZSET на базе отсортированного среза).
2. Реализуйте метод `ScheduleRetry(taskID string, executeAt time.Time)`.
3. Реализуйте метод `PollReadyTasks(now time.Time, limit int) []string`.
4. Продемонстрируйте корректную выборку задач по наступлению времени исполнения.

## Код решения

**`redis_zset_scheduler.go`**

```go
package main

import (
	"fmt"
	"sort"
	"sync"
	"time"
)

type ScheduledTask struct {
	TaskID    string
	ExecuteAt time.Time
}

type InMemoryZSetScheduler struct {
	mu    sync.Mutex
	tasks []ScheduledTask
}

func (s *InMemoryZSetScheduler) ScheduleRetry(taskID string, executeAt time.Time) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.tasks = append(s.tasks, ScheduledTask{TaskID: taskID, ExecuteAt: executeAt})
	// Сортировка по времени исполнения (эквивалент ZSET score)
	sort.Slice(s.tasks, func(i, j int) bool {
		return s.tasks[i].ExecuteAt.Before(s.tasks[j].ExecuteAt)
	})
	fmt.Printf("[ZSET Scheduler] Scheduled task %s for execution at %s\n", taskID, executeAt.Format("15:04:05.000"))
}

func (s *InMemoryZSetScheduler) PollReady(now time.Time, limit int) []string {
	s.mu.Lock()
	defer s.mu.Unlock()

	var ready []string
	remainingIdx := 0

	for i, t := range s.tasks {
		if t.ExecuteAt.Before(now) || t.ExecuteAt.Equal(now) {
			ready = append(ready, t.TaskID)
			remainingIdx = i + 1
			if len(ready) >= limit {
				break
			}
		} else {
			break
		}
	}

	if remainingIdx > 0 {
		s.tasks = s.tasks[remainingIdx:]
	}
	return ready
}

func main() {
	scheduler := &InMemoryZSetScheduler{}
	now := time.Now()

	// Планируем задачи на +100мс, +200мс, +500мс
	scheduler.ScheduleRetry("task_urgent", now.Add(100*time.Millisecond))
	scheduler.ScheduleRetry("task_medium", now.Add(200*time.Millisecond))
	scheduler.ScheduleRetry("task_delayed", now.Add(500*time.Millisecond))

	// Проверяем через 150 мс
	time.Sleep(150 * time.Millisecond)
	ready1 := scheduler.PollReady(time.Now(), 10)
	fmt.Printf("Ready tasks at T+150ms: %v\n", ready1)

	// Проверяем через еще 400 мс
	time.Sleep(400 * time.Millisecond)
	ready2 := scheduler.PollReady(time.Now(), 10)
	fmt.Printf("Ready tasks at T+550ms: %v\n", ready2)
}
```

## Под капотом

В реальном Redis Sorted Set реализован на базе Skip List (вероятностного списка с пропусками) и Hash Map. Поиск и вставка элементов по score (`ZADD` и `ZRANGEBYSCORE`) выполняются за время \(O(\log N)\), что позволяет без задержек оперировать миллионами запланированных ретраев в памяти Redis.

## Подводные камни

1. Гонка данных между `ZRANGEBYSCORE` и `ZREM` при нескольких воркерах: несколько воркеров выберут одни и те же задачи. Для атомарного извлечения задач из ZSET в Redis используется Lua-скрипт или команда `ZPOPMIN`.
2. Потеря данных при рестарте Redis: для очереди ретраев в Redis необходимо включать AOF (Append-Only File) с `appendfsync everysec`.
3. Слишком частый поллинг пустыми запросами: создает избыточную нагрузку на сеть Redis.

## На собеседовании

**Вопрос (T-Банк/Redis):** Как в Redis атомарно выбрать и удалить созревшие задачи из Sorted Set, чтобы два параллельных воркера не получили одну и ту же задачу?
**Ответ:** Применяется атомарный **Lua-скрипт**:
```lua
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
if #tasks > 0 then
    redis.call('ZREM', KEYS[1], unpack(tasks))
end
return tasks
```
Redis выполняет Lua-скрипты строго однопоточно в монопольном режиме, гарантируя, что выбранные задачи удаляются до того, как следующий воркер выполнит свой запрос.
