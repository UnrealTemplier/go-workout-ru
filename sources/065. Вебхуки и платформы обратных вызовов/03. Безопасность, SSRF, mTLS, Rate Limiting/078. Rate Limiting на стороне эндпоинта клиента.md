# Rate Limiting на стороне эндпоинта клиента (Per-Endpoint Token Bucket)

## Условие

Защищайте клиентов от burst'ов: не более N deliveries/сек на один endpoint, даже если у вас миллион событий в очереди.

### Исходная формулировка

**Rate limiting per endpoint**: Защищайте клиентов от burst'ов: не более N deliveries/сек на один endpoint, даже если у вас миллион событий в очереди.

## Теория

Представьте интернет-магазин с сервером на 2 ядра CPU, подписанный на вебхуки маркетплейса. Маркетплейс проводит акцию, и в очередь падает 100 000 событий изменения заказов за 5 секунд.

Если диспетчер начнет молотить с максимальной скоростью кластера (например, 5 000 запросов в секунду на этот эндпоинт), сервер клиента мгновенно погибнет с ошибкой `504 Gateway Timeout` или `502 Bad Gateway`.

### Per-Endpoint Throttling (Управление скоростью доставки на эндпоинт):
Webhook-платформа обязана гарантировать клиенту: *«Мы никогда не пошлем на ваш URL более \(N\) запросов в секунду (RPS)»*.
Стандартный лимит: например, 50 RPS на один домен/эндпоинт по умолчанию, с возможностью увеличения через тикет в саппорт.

### Алгоритм Token Bucket в Go:
Пакет `golang.org/x/time/rate` реализует высокоэффективный потокобезопасный Token Bucket без внешних зависимостей. Для каждого активного `EndpointURL` создается свой лимитер с параметрами:
- `Limit`: количество токенов в секунду (\(r\)).
- `Burst`: максимальный размер всплеска (\(b\)).
Перед отправкой воркер вызывает `limiter.Wait(ctx)`, приостанавливая выполнение горутины до появления токена.

## Решение по шагам

1. Создайте структуру `EndpointRateLimiterRegistry`, хранящую мапу `map[string]*rate.Limiter` с `sync.RWMutex`.
2. Реализуйте метод получения или создания лимитера `GetLimiter(endpoint string) *rate.Limiter`.
3. Добавьте фоновую очистку устаревших лимитеров (TTL Cache) для предотвращения утечки памяти.
4. В диспетчере вызывайте `limiter.Wait(ctx)` перед вызовом `http.Client.Do`.

## Код решения

**`endpoint_limiter.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

type EndpointLimiterRegistry struct {
	defaultRPS   rate.Limit
	defaultBurst int
	limiters     map[string]*rate.Limiter
	mu           sync.RWMutex
}

func NewEndpointLimiterRegistry(rps float64, burst int) *EndpointLimiterRegistry {
	return &EndpointLimiterRegistry{
		defaultRPS:   rate.Limit(rps),
		defaultBurst: burst,
		limiters:     make(map[string]*rate.Limiter),
	}
}

// GetLimiter возвращает или инициализирует персональный Token Bucket для эндпоинта
func (r *EndpointLimiterRegistry) GetLimiter(endpointKey string) *rate.Limiter {
	r.mu.RLock()
	limiter, exists := r.limiters[endpointKey]
	r.mu.RUnlock()

	if exists {
		return limiter
	}

	r.mu.Lock()
	defer r.mu.Unlock()

	// Double-check locking
	if limiter, exists = r.limiters[endpointKey]; exists {
		return limiter
	}

	limiter = rate.NewLimiter(r.defaultRPS, r.defaultBurst)
	r.limiters[endpointKey] = limiter
	return limiter
}

// WebhookSender демонстрирует отправку с задержкой по Token Bucket
type WebhookSender struct {
	registry *EndpointLimiterRegistry
}

func (s *WebhookSender) Deliver(ctx context.Context, endpoint string, eventID string) error {
	limiter := s.registry.GetLimiter(endpoint)

	// Wait блокирует горутину до тех пор, пока токен не станет доступен
	startWait := time.Now()
	if err := limiter.Wait(ctx); err != nil {
		return fmt.Errorf("rate limit wait cancelled: %w", err)
	}
	waitDuration := time.Since(startWait)

	// Имитация быстрой отправки
	fmt.Printf("[%s] Отправлен %s на %s (Ожидание токена: %v)\n",
		time.Now().Format("15:04:05.000"), eventID, endpoint, waitDuration.Round(time.Millisecond))
	return nil
}

func main() {
	// Лимит: 5 запросов в секунду на эндпоинт, максимальный burst = 2
	registry := NewEndpointLimiterRegistry(5.0, 2)
	sender := WebhookSender{registry: registry}

	ctx := context.Background()
	endpointA := "https://api.small-shop.ru/webhook"
	endpointB := "https://api.big-corp.ru/webhook"

	var wg sync.WaitGroup

	// Запускаем всплеск из 6 одновременных событий на endpointA
	fmt.Println("=== Старт всплеска из 6 событий на endpointA (Лимит: 5 RPS, Burst: 2) ===")
	for i := 1; i <= 6; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			sender.Deliver(ctx, endpointA, fmt.Sprintf("evt-A-%d", id))
		}(i)
	}

	// Параллельно отправляем событие на независимый endpointB
	wg.Add(1)
	go func() {
		defer wg.Done()
		time.Sleep(50 * time.Millisecond)
		sender.Deliver(ctx, endpointB, "evt-B-1")
	}()

	wg.Wait()
	fmt.Println("=== Все события успешно доставлены без превышения скорости ===")
}
```

## Под капотом

Как устроен `rate.Limiter` внутри?
Вместо запуска таймеров или горутин, `rate.Limiter` хранит всего 3 поля: `last time.Time`, `tokens float64` и `limit rate.Limit`.
При вызове `.Wait(ctx)` или `.Reserve()` лимитер вычисляет дельту времени \(\Delta t = now - last\) и мгновенно пересчитывает количество накопившихся токенов:
$$tokens = \min(burst, tokens + \Delta t \cdot limit)$$
Если токенов недостаточно, он вычисляет точную длительность сна $delay = (required - tokens) / limit$ и создает одноразовый таймер ожидания `time.NewTimer(delay)`, не создавая паразитной нагрузки на планировщик Go.

## Подводные камни

1. **Утечка памяти в мапе реестра:** Если в системе регистрируются миллионы динамических URL, мапа `limiters` будет непрерывно расти, вызывая утечку оперативной памяти. Обязательно используйте кэш с вытеснением по времени (TTL/LRU, например `sync.Map` с периодической очисткой неактивных лимитеров).
2. **Блокировка воркеров в очереди:** Если вызов `Wait(ctx)` задерживает воркера на несколько минут из-за переполнения лимита, воркер удерживается в памяти. Ограничивайте максимальное ожидание контекстом: `context.WithTimeout(ctx, 30*time.Second)`.

## На собеседовании

**Вопрос:** Что делать, если воркеров вебхука не один инстанс, а распределенный кластер из 50 подов в Kubernetes? Локальный `rate.Limiter` каждого пода не знает о других!

**Ответ:** Для распределенного ограничения скорости применяются:
1. **Шардирование по ключу:** Все вебхуки одного эндпоинта попадают в одну партицию Kafka. Эту партицию читает ровно один инстанс воркера, сохраняя локальный строгий контроль скорости.
2. **Распределенный Token Bucket в Redis:** Скрипт на Lua выполняет атомарный инкремент и проверку токенов в Redis-кластере (например, через ячейку скользящего окна Redis Cell или `SET key ... EX ... NX`).
