# Ограничение размера полезной нагрузки (Large Payload Handling)

## Условие

Установите max payload size (например, 256KB). Большие payloads DoS-ят клиентские endpoints и вашу сеть.

### Исходная формулировка

**Large payload handling**: Установите max payload size (например, 256KB). Большие payloads DoS-ят клиентские endpoints и вашу сеть.

## Теория

При проектировании вебхуков возникает дилемма: что отправлять в теле события?
1. **Fat Webhook:** Полный слепок сущности (со всеми вложенными позициями заказа, историей изменений и метаданными).
2. **Thin Webhook (Event Notification):** Только идентификатор и тип события (`{"id": "ord_123", "event": "order.completed"}`), после чего клиент идет в REST API за полными данными.

Если разрешить неконтролируемый размер тела Fat Webhook (например, заказ с 10 000 товарных позиций на 15 МБ JSON), возникают следующие проблемы:
- **DoS клиентского сервера:** Буферизация и парсинг 15 МБ JSON на стороне клиента исчерпают память или упрутся в стандартный лимит веб-сервера (nginx `client_max_body_size 1m`).
- **Исчерпание сетевого канала диспетчера:** Отправка 1000 таких вебхуков забьет гигабитный интерфейс ноды.

### Стандарты BigTech (Stripe, GitHub):
- Максимальный лимит размера полезной нагрузки вебхука: **256 КБ** (или 512 КБ).
- Если размер превышает лимит:
  1. Тело усекается, либо
  2. Объект сохраняется в S3/MinIO, а в вебхуке передается короткоживущая Presigned URL ссылка на скачивание.

## Решение по шагам

1. Задайте константу максимального размера полезной нагрузки: `MaxPayloadSize = 256 * 1024` (256 KB).
2. Реализуйте middleware / валидатор полезной нагрузки перед помещением в очередь доставки.
3. Напишите потоковый лимитер на стороне приемника через `http.MaxBytesReader` для защиты от переполнения буфера.
4. Реализуйте стратегию оффлоадинга в S3 (Claim Check Pattern) для тел, превышающих лимит.

## Код решения

**`payload_guard.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

const (
	// MaxWebhookPayloadSize - жесткий лимит полезной нагрузки (256 KB)
	MaxWebhookPayloadSize = 256 * 1024
)

var (
	ErrPayloadTooLarge = errors.New("webhook payload exceeds maximum permitted size of 256KB")
)

// WebhookEnvelope представляет метаданные события
type WebhookEnvelope struct {
	EventID   string          `json:"event_id"`
	EventType string          `json:"event_type"`
	Payload   json.RawMessage `json:"payload,omitempty"`
	BlobURL   string          `json:"blob_url,omitempty"` // Заполняется, если тело превысило 256КБ
}

// ValidateAndPreparePayload проверяет размер и при необходимости переключается на S3-ссылку
func ValidateAndPreparePayload(eventID, eventType string, rawData []byte) (*WebhookEnvelope, error) {
	if len(rawData) <= MaxWebhookPayloadSize {
		return &WebhookEnvelope{
			EventID:   eventID,
			EventType: eventType,
			Payload:   rawData,
		}, nil
	}

	// Если полезная нагрузка превышает 256КБ, применяем паттерн Claim Check (S3 Offloading)
	blobURL := fmt.Sprintf("https://s3.company.ru/webhook-payloads/%s.json", eventID)
	fmt.Printf("[OFFLOAD] Размер полезной нагрузки %d байт > 256КБ! Сохранено в S3: %s\n", len(rawData), blobURL)

	return &WebhookEnvelope{
		EventID:   eventID,
		EventType: eventType,
		BlobURL:   blobURL,
	}, nil
}

// ClientReceiverHandler демонстрирует защиту приемника через http.MaxBytesReader
func ClientReceiverHandler(w http.ResponseWriter, r *http.Request) {
	// Защита приемника: читаем максимум 256KB + 1 байт для обнаружения превышения
	r.Body = http.MaxBytesReader(w, r.Body, MaxWebhookPayloadSize)

	body, err := io.ReadAll(r.Body)
	if err != nil {
		http.Error(w, "Payload Too Large or Read Error", http.StatusRequestEntityTooLarge)
		return
	}

	w.WriteHeader(http.StatusOK)
	w.Write([]byte(fmt.Sprintf("Received %d bytes", len(body))))
}

func main() {
	// Кейс 1: Маленький вебхук (500 байт)
	smallData := []byte(`{"order_id": "ord_1001", "amount": 2500.50}`)
	envSmall, _ := ValidateAndPreparePayload("evt_1", "order.created", smallData)
	encodedSmall, _ := json.Marshal(envSmall)
	fmt.Printf("Кейс 1 (Норма): Готов к отправке, размер JSON = %d байт\n", len(encodedSmall))

	// Кейс 2: Огромный вебхук (500 КБ данных)
	hugeData := bytes.Repeat([]byte("A"), 500*1024)
	envHuge, _ := ValidateAndPreparePayload("evt_2", "catalog.synced", hugeData)
	encodedHuge, _ := json.Marshal(envHuge)
	fmt.Printf("Кейс 2 (S3 Offload): Итоговый размер конверта вебхука = %d байт\n", len(encodedHuge))

	// Кейс 3: Проверка защиты приемника через httptest
	ts := httptest.NewServer(http.HandlerFunc(ClientReceiverHandler))
	defer ts.Close()

	// Отправляем тело размером 300 КБ прямо в эндпоинт приемника
	oversizedBody := bytes.NewReader(bytes.Repeat([]byte("X"), 300*1024))
	resp, _ := http.Post(ts.URL, "application/json", oversizedBody)
	defer resp.Body.Close()

	fmt.Printf("Кейс 3 (Защита сервера): HTTP Статус при отправке 300КБ = %d %s\n",
		resp.StatusCode, http.StatusText(resp.StatusCode))
}
```

## Под капотом

`http.MaxBytesReader(w, r.Body, n)` — это обертка над входящим потоком `io.ReadCloser`.
При попытке вычитать из тела больше чем \(n\) байт:
1. `MaxBytesReader` немедленно прекращает чтение и возвращает ошибку `*http.MaxBytesError`.
2. Устанавливает внутренний флаг в структуре HTTP-сервера Go, который закрывает underlying TCP-соединение, не вычитывая гигабайты мусора из сокета ОС.
3. Это предотвращает медленные атаки Slowloris и переполнение памяти кучи Go (OOM) до вызова парсера JSON.

## Подводные камни

1. **Использование `io.ReadAll(r.Body)` без лимитера:** Если клиентский сервис вызывает `io.ReadAll(r.Body)` без `MaxBytesReader`, злоумышленник может передать заголовок `Content-Length: 1000000000` (1 GB) и направить бесконечный поток байт, уронив сервер по нехватке памяти.
2. **Расчет HMAC на усеченных данных:** Если вы урезаете тело вебхука, подпись HMAC обязана вычисляться строго от финального урезанного JSON, иначе верификация на стороне клиента провалится.

## На собеседовании

**Вопрос:** Как называется паттерн, при котором тяжелые бинарные или JSON данные не передаются напрямую через очередь сообщений / вебхук, а сохраняются во внешнее объектное хранилище?

**Ответ:** Это паттерн **Claim Check** (Квитанция на багаж). В очередь сообщений или вебхук кладется легковесный конверт, содержащий метаданные и ссылку («квитанцию», например Presigned S3 URL с TTL 1 час). Получатель обрабатывает уведомление и при необходимости асинхронно выкачивает тяжелые данные напрямую из S3, не нагружая брокер сообщений и диспетчер вебхуков.
