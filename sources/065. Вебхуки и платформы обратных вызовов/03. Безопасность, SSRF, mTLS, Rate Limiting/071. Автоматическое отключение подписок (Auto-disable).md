# Автоматическое отключение подписок (Auto-disable)

## Условие

Напишите логику ведения лога доставок вебхуков. Если сервер конкретного клиента возвращает ошибку `410 Gone` или `404 Not Found` непрерывно в течение 48 часов, веб-платформа должна автоматически деактивировать эту подписку на вебхуки, сделать запись в лог и отправить уведомление на email администратора клиента.

### Исходная формулировка

**Автоматическое отключение подписок (Auto-disable)**: Напишите логику ведения лога доставок вебхуков. Если сервер конкретного клиента возвращает ошибку `410 Gone` или `404 Not Found` непрерывно в течение 48 часов, веб-платформа должна автоматически деактивировать эту подписку на вебхуки, сделать запись в лог и отправить уведомление на email администратора клиента.

---

## Теория

В масштабных webhook-платформах (Stripe, GitHub, Shopify) мертвые или удаленные клиентские эндпоинты создают колоссальную паразитную нагрузку на диспетчер очередей. Если клиент удалил обработчик или сменил домен, продолжать ретраить каждый вебхук тысячами сообщений в сутки — расточительно и опасно для сетевой пропускной способности платформы.

### Политика автоматического отключения (Subscription Auto-Disable Policy):
1. **Явный отказ (`410 Gone`):** Означает перманентное удаление ресурса на стороне подписчика. При получении серии таких кодов подписка помечается как `Failing` с ускоренным таймером деактивации.
2. **Ненайденный путь (`404 Not Found`):** Может быть временной опечаткой при деплое, но если ошибка сохраняется непрерывно в течение 48 часов, статус переводится в `Disabled`.
3. **Хранение состояния в БД:**
   - `FirstFailedAt *time.Time`: метка первой непрерывной ошибки.
   - `LastFailedAt *time.Time`: метка последнего сбоя.
   - `ConsecutiveFailures int`: счетчик непрерывных ошибок. При успешной доставке (`2xx`) метки и счетчик сбрасываются в `nil` / `0`.
   - `Status`: `Active`, `Failing`, `Disabled`.
4. **Аудит и нотификация:** При переводе в `Disabled` генерируется событие для сервиса почтовых нотификаций (`NotificationService.SendSubscriptionDisabledEmail`), а доставка последующих вебхуков для этой подписки немедленно блокируется.

## Решение по шагам

1. Определите структуру `Subscription` со статусом, счетчиком ошибок и временными метками `FirstFailedAt`.
2. Реализуйте метод `RecordDeliveryResult(statusCode int, deliveryErr error) (disabled bool)`.
3. Если статус `404` или `410`, проверьте `FirstFailedAt`. Если с момента первой ошибки прошло более 48 часов (или при превышении лимита ошибок), деактивируйте подписку.
4. При успешном ответе (код `200..299`) обнулите счетчик ошибок и метку `FirstFailedAt`.
5. Добавьте вызов mock-нотификации для администратора и структурированное логирование.

## Код решения

**`subscription_manager.go`**

```go
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
	"sync"
	"time"
)

type SubscriptionStatus string

const (
	StatusActive   SubscriptionStatus = "ACTIVE"
	StatusFailing  SubscriptionStatus = "FAILING"
	StatusDisabled SubscriptionStatus = "DISABLED"
)

type Subscription struct {
	ID                  string
	ClientEmail         string
	EndpointURL         string
	Status              SubscriptionStatus
	ConsecutiveFailures int
	FirstFailedAt       *time.Time
	LastFailedAt        *time.Time
	DisabledAt          *time.Time
	mu                  sync.Mutex
}

type DeliveryManager struct {
	logger *slog.Logger
}

func NewDeliveryManager(logger *slog.Logger) *DeliveryManager {
	return &DeliveryManager{logger: logger}
}

func (m *DeliveryManager) RecordDelivery(ctx context.Context, sub *Subscription, statusCode int, err error) bool {
	sub.mu.Lock()
	defer sub.mu.Unlock()

	now := time.Now()

	// Успешная доставка (2xx)
	if err == nil && statusCode >= 200 && statusCode < 300 {
		if sub.ConsecutiveFailures > 0 || sub.Status == StatusFailing {
			m.logger.InfoContext(ctx, "subscription recovered to healthy state",
				"sub_id", sub.ID,
				"prev_failures", sub.ConsecutiveFailures)
		}
		sub.ConsecutiveFailures = 0
		sub.FirstFailedAt = nil
		sub.LastFailedAt = nil
		sub.Status = StatusActive
		return false
	}

	// Фиксация ошибки
	sub.ConsecutiveFailures++
	sub.LastFailedAt = &now
	if sub.FirstFailedAt == nil {
		sub.FirstFailedAt = &now
	}

	isHardFailure := statusCode == 404 || statusCode == 410
	failDuration := now.Sub(*sub.FirstFailedAt)

	// Правило автоотключения: непрерывные 404/410 в течение 48 часов
	// (Для теста используем 48 часов или > 5 непрерывных фатальных ошибок)
	shouldDisable := isHardFailure && (failDuration >= 48*time.Hour || sub.ConsecutiveFailures >= 5)

	if shouldDisable && sub.Status != StatusDisabled {
		sub.Status = StatusDisabled
		sub.DisabledAt = &now
		m.logger.WarnContext(ctx, "subscription automatically disabled due to persistent endpoint errors",
			"sub_id", sub.ID,
			"status_code", statusCode,
			"fail_duration", failDuration.String(),
			"failures", sub.ConsecutiveFailures)

		// Отправка уведомления администратору
		m.notifyAdminEmail(ctx, sub, statusCode)
		return true
	}

	sub.Status = StatusFailing
	m.logger.InfoContext(ctx, "subscription recorded failure",
		"sub_id", sub.ID,
		"status_code", statusCode,
		"status", sub.Status)

	return false
}

func (m *DeliveryManager) notifyAdminEmail(ctx context.Context, sub *Subscription, lastCode int) {
	// В реальном проде: вызов SendGrid / AWS SES / Postmark
	m.logger.InfoContext(ctx, "sent email notification to client admin",
		"to", sub.ClientEmail,
		"subject", fmt.Sprintf("Action Required: Webhook endpoint %s disabled", sub.EndpointURL),
		"reason_code", lastCode)
}

func main() {
	logger := slog.New(slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
	dm := NewDeliveryManager(logger)

	sub := &Subscription{
		ID:          "sub_ozon_9918",
		ClientEmail: "devops@client-domain.ru",
		EndpointURL: "https://api.client-domain.ru/webhooks",
		Status:      StatusActive,
	}

	ctx := context.Background()

	// Имитируем падение эндпоинта клиентом (410 Gone)
	for i := 1; i <= 5; i++ {
		disabled := dm.RecordDelivery(ctx, sub, 410, nil)
		fmt.Printf("Попытка %d: Статус подписки = %s, Отключена = %v\n", i, sub.Status, disabled)
	}
}
```

## Под капотом

При проектировании многопользовательской webhook-платформы критически важно не обновлять статус подписки в базе данных синхронно при каждом HTTP-ответе воркера. При сотнях тысяч запросов в секунду частые `UPDATE subscriptions SET failures = ...` вызовут блокировки строк (row contention) и перегрузку WAL.

Enterprise-решение: воркеры отправляют события о результате доставки в Kafka-топик `webhook-delivery-results`. Специальный микросервис `subscription-health-aggregator` агрегирует метрики с помощью скользящего окна в Redis или Flink/ClickHouse и лишь при переходе порогового значения (State Transition) выполняет единичный апдейт статуса в реляционной БД (`PostgreSQL`).

## Подводные камни

1. **Немедленное отключение при первом `404`:** Во время Rolling Update или сетевого рестарта клиентского шлюза nginx может кратковременно вернуть 404/502 на 5–10 секунд. Немедленное отключение подписки разобьет доверие клиентов. Обязателен временной порог (например, минимум 24–48 часов непрерывных неудач).
2. **Отсутствие веб-интерфейса реактивации:** Клиент исправил ошибку и хочет снова получать вебхуки. Платформа обязана предоставить API метод `POST /subscriptions/{id}/reactivate` и кнопку в личном кабинете с отправкой тестового пинга `ping`.

## На собеседовании

**Вопрос:** Как защититься от race conditions, если параллельно 10 воркеров обрабатывают вебхуки одной подписки, и 9 из них упали с 410 Gone, а 1 завершился успехом (200 OK)?

**Ответ:** Если воркеры выполняют конкурентные апдейты без синхронизации версий, запоздавший ответ `410 Gone` может ошибочно перезаписать успешный результат `200 OK`. Решение:
1. Использовать оптимистическую блокировку (`version_id` или `updated_at`) при записи в БД.
2. Применять шардирование очередей по `subscription_id`: все вебхуки одного клиента направляются в одну партицию Kafka, поэтому обрабатываются строго последовательно.
3. В логике агрегатора: если время успешного ответа `T_success > T_fail`, статус безоговорочно восстанавливается в `ACTIVE`.
