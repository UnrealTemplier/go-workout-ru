# Защита от атак по времени при проверке подписи (Constant-Time Verification)

## Условие

Всегда вычисляйте signature, даже если timestamp expired или невалидный. Иначе timing difference раскроет, какая проверка провалилась.

### Исходная формулировка

**Webhook signature timing attack protection**: Всегда вычисляйте signature, даже если timestamp expired или невалидный. Иначе timing difference раскроет, какая проверка провалилась.

## Теория

Атаки по сторонним каналам (Side-Channel Timing Attacks) позволяют злоумышленнику восстановить секретный ключ или узнать структуру внутренней валидации, измеряя время ответа сервера с точностью до наносекунд.

### Два критических вектора тайминг-атак на вебхуки:
1. **Быстрый выход при проверке времени (Early Return Leak):**
   Если код написан так:
   ```go
   if time.Since(timestamp) > 5*time.Minute {
       return ErrExpired // Завершилось за 10 наносекунд!
   }
   if !verifyHMAC(signature, body) {
       return ErrBadSig // Завершилось за 50 микросекунд (вычисление SHA-256)!
   }
   ```
   Злоумышленник по разнице во времени ответа (10 нс против 50 мкс) точно знает, дошел ли его запрос до проверки криптографии, даже если сервер всегда возвращает одинаковый generic HTTP `400 Bad Request`.
2. **Побайтовое сравнение строк (`==`):**
   Оператор `a == b` в Go сравнивает байты слева направо и прерывается на первом несовпадении. Атакующий подбирает первый байт хеша, отслеживая увеличение времени ответа на 2-3 нс, затем второй, третий — полностью вскрывая HMAC за секунды!

### Принцип Constant-Time Execution:
- Всегда вычислять HMAC независимо от валидности заголовков.
- Для сравнения байтовых срезов использовать строго `crypto/subtle.ConstantTimeCompare`.

## Решение по шагам

1. Извлеките метку времени и подпись из входящего запроса.
2. Даже если метка времени некорректна или устарела, **не делайте немедленный `return`**!
3. Вычислите HMAC от тела запроса.
4. Сравните подписи через `subtle.ConstantTimeCompare`.
5. Скомбинируйте флаги ошибок побитовыми операторами и верните отказ в единой временной точке.

## Код решения

**`constant_time_validator.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"errors"
	"fmt"
	"strconv"
	"time"
)

var (
	ErrWebhookAuthenticationFailed = errors.New("webhook authentication failed")
)

// ConstantTimeVerifyWebhook исключает утечки информации по времени
func ConstantTimeVerifyWebhook(secret []byte, payload []byte, timestampHeader string, signatureHeader string, tolerance time.Duration) error {
	now := time.Now()
	var timeValid int = 1

	// 1. Проверяем timestamp БЕЗ раннего выхода
	tsInt, err := strconv.ParseInt(timestampHeader, 10, 64)
	if err != nil {
		timeValid = 0
		tsInt = now.Unix() // Фиктивное время для продолжения алгоритма
	}

	eventTime := time.Unix(tsInt, 0)
	diff := now.Sub(eventTime)
	if diff > tolerance || diff < -tolerance {
		timeValid = 0
	}

	// 2. ОБЯЗАТЕЛЬНО вычисляем HMAC независимо от валидности времени!
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(strconv.FormatInt(tsInt, 10)))
	mac.Write([]byte("."))
	mac.Write(payload)
	expectedMAC := mac.Sum(nil)

	expectedHex := hex.EncodeToString(expectedMAC)

	// 3. Сравнение подписи за строго константное время
	sigValid := subtle.ConstantTimeCompare([]byte(expectedHex), []byte(signatureHeader))

	// 4. Комбинируем результаты проверки: оба флага обязаны быть равны 1
	if (timeValid & sigValid) != 1 {
		// Единая безликая ошибка для исключения раскрытия деталей валидации
		return ErrWebhookAuthenticationFailed
	}

	return nil
}

func main() {
	secret := []byte("corp_super_secret_webhook_key_2026")
	payload := []byte(`{"event":"user.created","id":"u1"}`)

	validTs := strconv.FormatInt(time.Now().Unix(), 10)
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(validTs + "."))
	mac.Write(payload)
	validSig := hex.EncodeToString(mac.Sum(nil))

	// Тест 1: Все валидно
	err1 := ConstantTimeVerifyWebhook(secret, payload, validTs, validSig, 5*time.Minute)
	fmt.Printf("Тест 1 (Валидный запрос):    Ошибка = %v\n", err1)

	// Тест 2: Протухший timestamp
	oldTs := strconv.FormatInt(time.Now().Add(-1*time.Hour).Unix(), 10)
	err2 := ConstantTimeVerifyWebhook(secret, payload, oldTs, validSig, 5*time.Minute)
	fmt.Printf("Тест 2 (Протухший timestamp): Ошибка = %v\n", err2)

	// Тест 3: Неверная сигнатура
	err3 := ConstantTimeVerifyWebhook(secret, payload, validTs, "bad_signature", 5*time.Minute)
	fmt.Printf("Тест 3 (Неверный HMAC):      Ошибка = %v\n", err3)
}
```

ℹ️ Константная по времени проверка времени и HMAC-подписи без ранних выходов

**`Терминал`**

```bash
go run constant_time_validator.go
# Все типы ошибок возвращают единый статус без раскрытия деталей атакующему:
# Тест 1 (Валидный запрос):    Ошибка = <nil>
# Тест 2 (Протухший timestamp): Ошибка = webhook authentication failed
# Тест 3 (Неверный HMAC):      Ошибка = webhook authentication failed
```

## Под капотом

`subtle.ConstantTimeCompare(x, y []byte)` написан на ассемблере и C-подобном коде без ветвлений `if`.
Он выполняет побитовое сложение по модулю 2 `XOR` всех элементов среза в аккумуляторе `v`:
```go
for i := 0; i < len(x); i++ {
    v |= x[i] ^ y[i]
}
return int((uint32(v)-1) >> 31)
```
Процессор выполняет строго одинаковое количество инструкций независимо от того, совпали ли байты в начале, в середине или не совпали вовсе. Это делает спектральный тайминг-анализ запроса бесполезным.

## Подводные камни

1. **Возврат подробных сообщений об ошибках клиенту:** Возврат `{"error": "signature expired"}` против `{"error": "invalid signature"}` сводит на нет защиту по времени, отдавая атакующему результат проверки прямым текстом. Всегда возвращайте единый HTTP `401 Unauthorized`.
2. **Разная длина сравниваемых срезов:** `subtle.ConstantTimeCompare` сразу вернет 0, если длины срезов не совпадают. Поэтому сравнивайте хеши одинаковой фиксированной длины (например, всегда hex от sha256 = 64 символа).

## На собеседовании

**Вопрос:** Достаточно ли защиты на уровне Go-кода, если перед бэкендом стоит Nginx или Cloudflare?

**Ответ:** Сетевой джиттер (Network Jitter) в интернете действительно добавляет миллисекунды случайного шума. Однако статистическими методами (Box-Whisker, усреднение по миллиону запросов) атакующий может отфильтровать гауссовский шум сети и детектировать разницу в наносекундах. Поэтому криптографически стойкий код на бэкенде обязателен даже при наличии CDN.
