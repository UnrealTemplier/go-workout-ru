# Алгоритм Full Jitter для предотвращения Thundering Herd

## Условие

Если упал крупный клиент, у тебя скопятся тысячи вебхуков. Когда клиент оживет, твои ретраи ударят по нему одновременно, снова положив сервер (Thundering Herd). Модифицируй паузу: добавляй к каждому интервалу случайный шум (Jitter). Например, вместо строго 4 секунд жди от 2 до 4 секунд (`random(0, delay/2) + delay/2`).

### Исходная формулировка

**Full Jitter (Предотвращение шторма)**: Если упал крупный клиент, у тебя скопятся тысячи вебхуков. Когда клиент оживет, твои ретраи ударят по нему одновременно, снова положив сервер (Thundering Herd). Модифицируй паузу из упр. 781: добавляй к каждому интервалу случайный шум (Jitter). Например, вместо строго 4 секунд жди от 2 до 4 секунд (`random(0, delay/2) + delay/2`).

## Теория

При массовом сбое на стороне клиента или магистрального провайдера тысячи вебхуков одновременно завершаются ошибкой (например, в 12:00:00). Если диспетчер использует детерминированный экспоненциальный бэкофф (\(T_i = 2^i\) секунд: 1с, 2с, 4с, 8с), все эти тысячи запросов повторятся строго синхронно: сначала ровно через 1 секунду, затем ровно через 2 секунды, через 4 и т.д.

### Проблема Thundering Herd (Набегающее стадо):
Всплески трафика образуют волнообразные пики колоссальной амплитуды. Едва восстановившись, клиентский сервер получает волну из 10 000 повторных запросов в одну и ту же миллисекунду и немедленно снова падает по OOM или CPU 100%.

### Классификация алгоритмов рандомизации (исследование AWS Architecture):
1. **No Jitter:** \(Sleep = Base \cdot 2^{attempt}\). Ужасно, формирует жесткие резонансные пики.
2. **Equal Jitter:** Половина задержки фиксирована, половина рандомизирована:
   $$Sleep = \frac{Backoff}{2} + \text{rand}(0, \frac{Backoff}{2})$$
3. **Full Jitter:** Случайное значение равномерно распределено от 0 до вычисленного верхнего предела бэкоффа:
   $$Sleep = \text{rand}(0, \min(MaxDelay, Base \cdot 2^{attempt}))$$
   Исследования AWS доказали, что именно **Full Jitter** минимизирует конкуренцию за ресурсы и суммарное время ожидания очереди, равномерно «размазывая» запросы по временной шкале.

## Решение по шагам

1. Создайте структуру `BackoffCalculator` с параметрами `BaseDelay`, `MaxDelay` и генератором псевдослучайных чисел `math/rand/v2`.
2. Реализуйте метод `CalculateFullJitter(attempt int) time.Duration`.
3. Ограничьте максимальную задержку сверху `MaxDelay` во избежание целочисленного переполнения степени двойки (`1 << attempt`).
4. Напишите сравнительный симулятор распределения задержек для 1000 одновременных сбоев.

## Код решения

**`jitter_backoff.go`**

```go
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"time"
)

type BackoffStrategy struct {
	BaseDelay time.Duration
	MaxDelay  time.Duration
}

// NoJitter возвращает строгую экспоненциальную задержку: Base * 2^attempt
func (s *BackoffStrategy) NoJitter(attempt int) time.Duration {
	if attempt > 30 {
		return s.MaxDelay
	}
	multiplier := math.Pow(2, float64(attempt))
	delay := time.Duration(float64(s.BaseDelay) * multiplier)
	if delay > s.MaxDelay {
		return s.MaxDelay
	}
	return delay
}

// EqualJitter возвращает задержку: Delay/2 + rand(0, Delay/2)
func (s *BackoffStrategy) EqualJitter(attempt int) time.Duration {
	ceiling := s.NoJitter(attempt)
	half := ceiling / 2
	if half <= 0 {
		return ceiling
	}
	randomPart := time.Duration(rand.Int64N(int64(half)))
	return half + randomPart
}

// FullJitter возвращает задержку: rand(0, min(MaxDelay, Base * 2^attempt))
func (s *BackoffStrategy) FullJitter(attempt int) time.Duration {
	ceiling := s.NoJitter(attempt)
	if ceiling <= 0 {
		return s.BaseDelay
	}
	// rand.Int64N возвращает значение в полуинтервале [0, n)
	return time.Duration(rand.Int64N(int64(ceiling)))
}

func main() {
	strategy := BackoffStrategy{
		BaseDelay: 1 * time.Second,
		MaxDelay:  30 * time.Second,
	}

	fmt.Println("=== Сравнение стратегий бэкоффа для попытки № 3 (Детерминированный предел = 8 сек) ===")
	fmt.Printf("No Jitter:    %v\n", strategy.NoJitter(3))

	fmt.Println("\nВыборка Equal Jitter (диапазон 4с .. 8с):")
	for i := 0; i < 5; i++ {
		fmt.Printf("  Запуск %d: %v\n", i+1, strategy.EqualJitter(3).Round(time.Millisecond))
	}

	fmt.Println("\nВыборка Full Jitter (диапазон 0с .. 8с):")
	for i := 0; i < 5; i++ {
		fmt.Printf("  Запуск %d: %v\n", i+1, strategy.FullJitter(3).Round(time.Millisecond))
	}

	// Симуляция распределения для 1000 горутин
	const samples = 1000
	var buckets [8]int // корзины по 1 секунде (0..1с, 1..2с, ..., 7..8с)

	for i := 0; i < samples; i++ {
		delay := strategy.FullJitter(3)
		sec := int(delay.Seconds())
		if sec >= 8 {
			sec = 7
		}
		buckets[sec]++
	}

	fmt.Println("\nГистограмма распределения 1000 повторов (Full Jitter) по секундам:")
	for sec, count := range buckets {
		bar := ""
		for b := 0; b < count/15; b++ {
			bar += "█"
		}
		fmt.Printf("  [%dс - %dс]: %3d запросов | %s\n", sec, sec+1, count, bar)
	}
}
```

## Под капотом

В Go 1.22+ стандартная библиотека включает пакет `math/rand/v2`. В отличие от устаревшего `math/rand`, в v2 глобальные функции (`rand.Int64N`, `rand.Float64`) используют неблокирующий lock-free генератор случайных чисел `ChaCha8` или `PCG`, привязанный к thread-local хранилищу M-потока рантайма.

В высоконагруженном диспетчере вебхуков вызов `rand.Int64N()` в сотнях горутин больше не упирается в глобальный `sync.Mutex` старого генератора, обеспечивая нулевые накладные расходы при вычислении случайного джиттера.

## Подводные камни

1. **Опасность переполнения `1 << attempt`:** Если счетчик попыток достигнет 64, сдвиг `1 << 64` в 64-битной арифметике переполнится и вернет 0, что приведет к мгновенным непрерывным ретраям (busy loop). Всегда ограничивайте `attempt` максимальным значением (например, `min(attempt, 30)`).
2. **Использование `math/rand` без Seed в старых версиях Go (<1.20):** В старых версиях Go генератор без вызова `rand.Seed(time.Now().UnixNano())` всегда возвращал детерминированную последовательность чисел, что сводило защиту от Thundering Herd к нулю.

## На собеседовании

**Вопрос:** Почему стратегия `Full Jitter` предпочтительнее `Equal Jitter`, несмотря на то, что при Full Jitter минимальная задержка может оказаться близкой к нулю?

**Ответ:** По результатам математического моделирования AWS Lab, `Equal Jitter` всегда гарантирует паузу минимум `ceiling / 2`, что искусственно затягивает доставку в спокойное время. `Full Jitter` обеспечивает максимально возможное энтропийное рассеивание: математическое ожидание задержки вдвое ниже, а суммарная нагрузка на целевой сервер при выходе из строя распределяется равномерным прямоугольным спектром, что предотвращает фазовую синхронизацию очередей.
