# Redirect Following Policy и защита от Open Redirect SSRF

## Условие

Не следуйте за redirect'ами при webhook delivery или следуйте максимум 1 redirect на тот же host. Open redirect может быть использован для SSRF.

### Исходная формулировка

**Redirect following policy**: Не следуйте за redirect'ами при webhook delivery или следуйте максимум 1 redirect на тот же host. Open redirect может быть использован для SSRF.

## Теория

Поведение `http.Client` по умолчанию в Go — следовать по HTTP-перенаправлениям (301 Moved Permanently, 302 Found, 307 Temporary Redirect, 308 Permanent Redirect) вплоть до 10 переходов.

Для вебхуков такое поведение — **критическая уязвимость**!

### Векторы атак через HTTP Redirects:
1. **SSRF через Open Redirect:** Клиент регистрирует валидный публичный URL: `https://evil-customer.com/webhook`. При получении запроса его сервер возвращает `302 Found` с заголовком `Location: http://169.254.169.254/latest/meta-data/`. Если HTTP-клиент платформы слепо переходит по редиректу, он отправляет запрос во внутренний закрытый контур.
2. **Утечка секретов и HMAC-сигнатур:** Вебхук отправляется с заголовками `X-Hub-Signature-256`, `Authorization: Bearer <secret>`. При кросс-доменном редиректе на сервер третьего лица эти секретные заголовки могут утечь в открытом виде.
3. **Бесконечные циклы перенаправлений (Redirect Loops):** Атакующий настраивает цикличный редирект A -> B -> A, удерживая воркер вебхука до исчерпания таймаута.

### Best Practice политики вебхуков:
- **Default Policy (Stripe, GitHub):** Запрет любых перенаправлений! Возврат `3xx` трактуется как ошибка конфигурации эндпоинта клиента.
- **Strict Same-Host Policy:** Разрешается максимум 1 редирект строго на тот же самый Scheme и Host (например, `http -> https` на том же домене).

## Решение по шагам

1. Настройте поле `CheckRedirect` в структуре `http.Client`.
2. Реализуйте политику запрета любых редиректов через возвращение ошибки `http.ErrUseLastResponse`.
3. Реализуйте альтернативную политику `StrictSameHostRedirectPolicy`:
   - Проверьте количество переходов (`len(via) >= 1`).
   - Сравните `newURL.Host == via[0].URL.Host`.
   - Запретите смену HTTPS на HTTP.
   - Очистите чувствительные авторизационные заголовки при переходе.

## Код решения

**`redirect_policy.go`**

```go
package main

import (
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
)

var (
	ErrRedirectDisallowed = errors.New("webhook delivery: redirects are strictly prohibited for security reasons")
	ErrCrossHostRedirect  = errors.New("webhook delivery: cross-host redirect detected (SSRF protection)")
	ErrInsecureDowngrade  = errors.New("webhook delivery: protocol downgrade from HTTPS to HTTP is forbidden")
)

// PolicyNoRedirects полностью запрещает любые перенаправления (как в Stripe API)
func NewNoRedirectClient() *http.Client {
	return &http.Client{
		CheckRedirect: func(req *http.Request, via []*http.Request) error {
			// Возврат http.ErrUseLastResponse останавливает клиент и возвращает ответ 3xx как есть
			return http.ErrUseLastResponse
		},
	}
}

// PolicyStrictSameHost разрешает ровно 1 редирект в рамках одного и того же хоста
func NewStrictSameHostClient() *http.Client {
	return &http.Client{
		CheckRedirect: func(req *http.Request, via []*http.Request) error {
			if len(via) >= 1 {
				return fmt.Errorf("%w: maximum 1 redirect allowed", ErrRedirectDisallowed)
			}

			originURL := via[0].URL
			targetURL := req.URL

			// Запрещаем переход на другой домен
			if originURL.Host != targetURL.Host {
				return fmt.Errorf("%w: cannot redirect from %s to %s",
					ErrCrossHostRedirect, originURL.Host, targetURL.Host)
			}

			// Запрещаем понижение безопасности с HTTPS до HTTP
			if originURL.Scheme == "https" && targetURL.Scheme == "http" {
				return ErrInsecureDowngrade
			}

			// Очищаем чувствительные токены при перенаправлении
			req.Header.Del("Authorization")

			return nil
		},
	}
}

func main() {
	// Создаем тестовый сервер, имитирующий уязвимый редирект на метаданные AWS
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path == "/redirect-to-metadata" {
			http.Redirect(w, r, "http://169.254.169.254/secret", http.StatusFound)
			return
		}
		if r.URL.Path == "/redirect-same-host" {
			http.Redirect(w, r, "/valid-endpoint", http.StatusFound)
			return
		}
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("Payload delivered successfully"))
	}))
	defer ts.Close()

	fmt.Println("=== Тестирование NoRedirectClient (Политика Stripe) ===")
	noRedirClient := NewNoRedirectClient()
	resp, err := noRedirClient.Get(ts.URL + "/redirect-to-metadata")
	if err != nil {
		fmt.Printf("Ошибка: %v\n", err)
	} else {
		fmt.Printf("Статус ответа: %d (Редирект НЕ совершен, возвращен 302 как результат)\n", resp.StatusCode)
		resp.Body.Close()
	}

	fmt.Println("\n=== Тестирование StrictSameHostClient (Защита от SSRF) ===")
	sameHostClient := NewStrictSameHostClient()

	// Попытка междоменного редиректа на внутреннюю сеть
	_, err = sameHostClient.Get(ts.URL + "/redirect-to-metadata")
	if err != nil {
		var urlErr *url.Error
		if errors.As(err, &urlErr) {
			fmt.Printf("Успешно заблокировано: %v\n", urlErr.Err)
		} else {
			fmt.Printf("Ошибка: %v\n", err)
		}
	}

	// Легитимный редирект на тот же хост
	respValid, err := sameHostClient.Get(ts.URL + "/redirect-same-host")
	if err != nil {
		fmt.Printf("Неожиданная ошибка: %v\n", err)
	} else {
		fmt.Printf("Успешный редирект на тот же хост, финальный статус: %d\n", respValid.StatusCode)
		respValid.Body.Close()
	}
}
```

## Под капотом

Что происходит внутри метода `http.Client.Do` при обработке редиректа?
После получения ответа со статусом `3xx` рантайм Go проверяет наличие функции `CheckRedirect`. Если она возвращает специальную сигнальную ошибку `http.ErrUseLastResponse`, цикл обработки редиректов немедленно прерывается, а вызывающей стороне возвращается сам исходный HTTP-ответ с кодом 301/302 и телом.

Если возвращается любая другая ошибка, рантайм закрывает тело промежуточного ответа `resp.Body.Close()` и возвращает объект ошибки типа `*url.Error`. Это гарантирует отсутствие утечек файловых дескрипторов сокетов.

## Подводные камни

1. **Возврат `nil` в `CheckRedirect` без проверок:** Если не задать поле `CheckRedirect`, Go по умолчанию перейдет по адресу из заголовка `Location`, полностью игнорируя смену протокола, домена и безопасность подсетей.
2. **Неудаление заголовка `Authorization`:** Стандартный клиент Go при редиректе на другой домен может автоматически скопировать заголовки, если не предусмотреть явное удаление чувствительных данных.

## На собеседовании

**Вопрос:** Почему подавляющее большинство enterprise-платформ (Stripe, Slack, Shopify) вообще запрещают любые HTTP-редиректы для вебхуков (`ErrUseLastResponse`)?

**Ответ:** 
1. **Безопасность:** Любой редирект расширяет поверхность атаки (SSRF, утечка подписей).
2. **Производительность:** Каждый редирект удваивает сетевые накладные расходы (DNS + TCP Shake + TLS Handshake + HTTP RTT), что замедляет работу воркеров очереди в 2–3 раза.
3. **Строгость контракта:** Клиент обязан сразу указать финальный действующий URL своего шлюза. Если клиент переехал, он обязан обновить адрес эндпоинта в панели управления.
