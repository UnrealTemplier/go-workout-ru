# Хранение и аудит истории событий (Webhook Event Retention в ClickHouse)

## Условие

Храните историю events 30-90 дней для manual retries и audit. Используйте ClickHouse для efficient storage.

### Исходная формулировка

**Webhook event retention**: Храните историю events 30-90 дней для manual retries и audit. Используйте ClickHouse для efficient storage.

## Теория

При объемах в 50–100 миллионов вебхуков в сутки хранение истории всех попыток доставок (заголовки запроса, тело, HTTP-статус ответа, latency, заголовки ответа) в реляционной СУБД (PostgreSQL/MySQL) приведет к катастрофическому росту размера таблиц (десятки терабайт в месяц) и деградации B-Tree индексов.

### Почему ClickHouse идеален для Webhook Delivery Log:
1. **Колоночное сжатие (Columnar Compression):** Алгоритмы LZ4/ZSTD сжимают повторяющиеся URL, JSON-тела и HTTP-заголовки в 5–10 раз.
2. **Партиционирование по датам (`PARTITION BY toYYYYMM(event_time)`):** Позволяет мгновенно удалять старые данные за пределами политики хранения без блокировок таблицы.
3. **Автоматический TTL (`TTL event_time + INTERVAL 90 DAY`):** ClickHouse на уровне движка MergeTree удаляет куски данных (data parts) старше 90 дней в фоновом режиме.
4. **Батчинг вставок (Bulk Inserts):** Воркеры собирают логи в памяти и сбрасывают пачками по 5 000–10 000 строк раз в секунду.

## Решение по шагам

1. Спроектируйте DDL-таблицу ClickHouse с движком `MergeTree` и выражением `TTL event_time + INTERVAL 90 DAY`.
2. Создайте структуру лога доставки `DeliveryLogEntry`.
3. Реализуйте асинхронный батч-буфер в Go на базе таймера и слайса.
4. Напишите метод сброса пачки логов в хранилище при достижении лимита строк или таймаута.

## Код решения

**`clickhouse_retention.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// DDL для ClickHouse:
// CREATE TABLE webhook_delivery_logs (
//     event_id UUID,
//     tenant_id LowCardinality(String),
//     endpoint_url String,
//     attempt UInt8,
//     status_code UInt16,
//     latency_ms UInt32,
//     request_payload String CODEC(ZSTD(3)),
//     response_body String CODEC(ZSTD(3)),
//     error_message String,
//     event_time DateTime64(3, 'UTC')
// ) ENGINE = MergeTree()
// PARTITION BY toYYYYMM(event_time)
// ORDER BY (tenant_id, event_time, event_id)
// TTL event_time + INTERVAL 90 DAY DELETE;

type DeliveryLogEntry struct {
	EventID        string
	TenantID       string
	EndpointURL    string
	Attempt        uint8
	StatusCode     uint16
	LatencyMS      uint32
	RequestPayload string
	ResponseBody   string
	ErrorMessage   string
	EventTime      time.Time
}

type ClickHouseBatchLogger struct {
	batchSize   int
	flushPeriod time.Duration
	buffer      []DeliveryLogEntry
	mu          sync.Mutex
	flushChan   chan []DeliveryLogEntry
}

func NewClickHouseBatchLogger(batchSize int, flushPeriod time.Duration) *ClickHouseBatchLogger {
	l := &ClickHouseBatchLogger{
		batchSize:   batchSize,
		flushPeriod: flushPeriod,
		buffer:      make([]DeliveryLogEntry, 0, batchSize),
		flushChan:   make(chan []DeliveryLogEntry, 20),
	}
	go l.backgroundFlusher()
	go l.writerRoutine()
	return l
}

func (l *ClickHouseBatchLogger) Log(entry DeliveryLogEntry) {
	l.mu.Lock()
	defer l.mu.Unlock()

	l.buffer = append(l.buffer, entry)
	if len(l.buffer) >= l.batchSize {
		toFlush := l.buffer
		l.buffer = make([]DeliveryLogEntry, 0, l.batchSize)
		l.flushChan <- toFlush
	}
}

func (l *ClickHouseBatchLogger) backgroundFlusher() {
	ticker := time.NewTicker(l.flushPeriod)
	defer ticker.Stop()

	for range ticker.C {
		l.mu.Lock()
		if len(l.buffer) > 0 {
			toFlush := l.buffer
			l.buffer = make([]DeliveryLogEntry, 0, l.batchSize)
			l.flushChan <- toFlush
		}
		l.mu.Unlock()
	}
}

func (l *ClickHouseBatchLogger) writerRoutine() {
	for batch := range l.flushChan {
		// В реальном приложении: chConn.AsyncInsert(ctx, "INSERT INTO webhook_delivery_logs VALUES ...", batch)
		fmt.Printf("[CLICKHOUSE INSERT] Сброшена пачка из %d логов в ClickHouse (TTL: 90 дней)\n", len(batch))
	}
}

func main() {
	logger := NewClickHouseBatchLogger(5, 100*time.Millisecond)

	ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
	defer cancel()

	fmt.Println("=== Отправка логов доставки вебхуков в ClickHouse Buffer ===")
	for i := 1; i <= 12; i++ {
		logger.Log(DeliveryLogEntry{
			EventID:        fmt.Sprintf("evt_uuid_%03d", i),
			TenantID:       "ozon_seller_100",
			EndpointURL:    "https://api.seller.ru/webhook",
			Attempt:        1,
			StatusCode:     200,
			LatencyMS:      45,
			RequestPayload: `{"order_id":"123","status":"paid"}`,
			EventTime:      time.Now(),
		})
	}

	<-ctx.Done()
	time.Sleep(50 * time.Millisecond)
}
```

## Под капотом

Почему одиночные `INSERT INTO ...` губительны для ClickHouse?
Каждая операция `INSERT` в ClickHouse создает отдельный каталог данных (part) на диске файловой системы. Если слать по 10 000 одиночных INSERT в секунду, количество parts превысит лимит операционной системы, и ClickHouse выдаст ошибку `Too many parts in all data parts in table (2000+)`. Батчинг в Go объединяет тысячи записей в единый компактный part сжатия ZSTD.

## Подводные камни

1. **Использование тяжелых JSON-полей без сжатия:** Тела запросов и ответов содержат повторяющиеся ключи. Без кодека `CODEC(ZSTD(3))` база займет в 6 раз больше диска.
2. **Потеря данных при падении процесса воркера:** Если процесс убивается по OOM, буфер в памяти теряется. В критичных системах логи сначала сбрасываются в локальный WAL (Write-Ahead Log) или Kafka-топик логов.

## На собеседовании

**Вопрос:** Как организовать поиск по содержимому JSON в теле вебхуков в ClickHouse с миллиардами строк без full scan?

**Ответ:** ClickHouse поддерживает тип данных `JSON` (Object('json')) и гранулярные индексы пропуска данных (Data Skipping Indexes): `INDEX idx_order_id JSONExtractString(request_payload, 'order_id') TYPE bloom_filter GRANULARITY 4`. Индекс на базе фильтра Блума позволяет ClickHouse пропускать 99% блоков диска, находя нужный вебхук за миллисекунды.
