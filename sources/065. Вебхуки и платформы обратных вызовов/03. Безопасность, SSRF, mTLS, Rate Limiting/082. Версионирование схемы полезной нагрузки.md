# Версионирование схемы полезной нагрузки (Payload Versioning)

## Условие

Добавляйте `api_version` в payload. При breaking changes в схеме увеличивайте версию, чтобы клиенты могли мигрировать постепенно.

### Исходная формулировка

**Webhook payload versioning**: Добавляйте `api_version` в payload. При breaking changes в схеме увеличивайте версию, чтобы клиенты могли мигрировать постепенно.

## Теория

С течением времени бизнес-модель сервиса эволюционирует: поля переименовываются, типы меняются (например, `amount: int` в копейках заменяется на структурированный объект `{ "value": "100.50", "currency": "RUB" }`), удаляются устаревшие атрибуты.

Если отправить обновленный JSON клиентам без версионирования, клиентские парсеры упадут с ошибками десериализации, парализовав прием платежей и интеграции.

### Архитектура версионирования вебхуков (Stripe Model):
1. **Явное поле версии:** Каждый вебхук содержит атрибут `api_version`: `"2024-06-01"` или целое число `version: 2`.
2. **Привязка к аккаунту/подписке:** При создании подписки клиент фиксирует версию API, которую понимает его бэкенд (поле `Subscription.APIVersion`).
3. **Паттерн Envelope & Transformers:**
   - Внутренняя система всегда генерирует единую каноническую последнюю модель события (`CanonicalEvent`).
   - Перед отправкой диспетчер прогоняет событие через цепочку обратных трансформаторов (`EventTransformer`), преобразуя современную структуру в устаревшую схему, которую ждет клиент.

## Решение по шагам

1. Создайте каноническую модель платежного события `CanonicalOrderEvent`.
2. Реализуйте интерфейс `PayloadTransformer` с методом `Transform(event CanonicalOrderEvent) (any, error)`.
3. Реализуйте адаптеры для версии `v1` (плоская структура) и `v2` (вложенная денежная структура).
4. Напишите фабрику сериализатора, которая по запрошенной клиентом версии генерирует требуемый JSON.

## Код решения

**`payload_versioning.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

// CanonicalOrderEvent - внутренняя современная модель события в компании
type CanonicalOrderEvent struct {
	ID        string    `json:"id"`
	CreatedAt time.Time `json:"created_at"`
	Amount    int64     `json:"amount_cents"` // Сумма в копейках
	Currency  string    `json:"currency"`
	Customer  struct {
		ID    string `json:"id"`
		Email string `json:"email"`
	} `json:"customer"`
}

// PayloadV1 - устаревшая схема для старых клиентов (плоские поля)
type PayloadV1 struct {
	APIVersion    string  `json:"api_version"`
	EventID       string  `json:"event_id"`
	TotalRub      float64 `json:"total_rub"` // Было в рублях с плавающей точкой
	CustomerEmail string  `json:"customer_email"`
}

// PayloadV2 - современная строгая схема (строго типизированные деньги)
type PayloadV2 struct {
	APIVersion string `json:"api_version"`
	EventID    string `json:"event_id"`
	Money      struct {
		Units    int64  `json:"units"`
		Currency string `json:"currency"`
	} `json:"money"`
	CustomerID string `json:"customer_id"`
}

// WebhookVersionManager управляет трансформацией схем
type WebhookVersionManager struct{}

func (m *WebhookVersionManager) FormatForClient(canonical CanonicalOrderEvent, clientVersion string) ([]byte, error) {
	switch clientVersion {
	case "2022-11-01", "v1":
		v1 := PayloadV1{
			APIVersion:    "2022-11-01",
			EventID:       canonical.ID,
			TotalRub:      float64(canonical.Amount) / 100.0,
			CustomerEmail: canonical.Customer.Email,
		}
		return json.MarshalIndent(v1, "", "  ")

	case "2026-01-01", "v2":
		fallthrough
	default:
		v2 := PayloadV2{
			APIVersion: "2026-01-01",
			EventID:    canonical.ID,
		}
		v2.Money.Units = canonical.Amount
		v2.Money.Currency = canonical.Currency
		v2.CustomerID = canonical.Customer.ID
		return json.MarshalIndent(v2, "", "  ")
	}
}

func main() {
	manager := &WebhookVersionManager{}

	// Внутреннее каноническое событие
	canonical := CanonicalOrderEvent{
		ID:        "evt_ord_99482",
		CreatedAt: time.Now(),
		Amount:    159050, // 1590 рублей 50 копеек
		Currency:  "RUB",
	}
	canonical.Customer.ID = "cust_55"
	canonical.Customer.Email = "client@corp.ru"

	// Клиент А работает на старой интеграции v1
	bodyV1, _ := manager.FormatForClient(canonical, "v1")
	fmt.Printf("=== Вебхук для клиента А (Схема v1 / 2022-11-01) ===\n%s\n\n", string(bodyV1))

	// Клиент Б обновился на актуальную версию v2
	bodyV2, _ := manager.FormatForClient(canonical, "v2")
	fmt.Printf("=== Вебхук для клиента Б (Схема v2 / 2026-01-01) ===\n%s\n", string(bodyV2))
}
```

## Под капотом

Как устроена миграция схем в Stripe под капотом?
В Stripe написано более 100 версий API, датированных днями релизов (например, `2019-02-19`, `2020-08-27`). Вместо написания \(N\) независимых сериализаторов используется **цепочка инкрементальных мутаторов (Schema Rollback Pipeline)**.
Событие сериализуется в самую свежую версию \(V_{now}\), после чего проходит последовательно через цепочку шагов понижения: \(V_{now} \to V_{now-1} \to \dots \to V_{target}\). Каждый шаг меняет только те 2-3 поля, которые изменились в конкретном релизе.

## Подводные камни

1. **Использование глобальной версии для всех пользователей одновременно:** Если обновить версию вебхуков глобально на проде, у половины клиентов упадут бэкграунд-обработчики. Версия схемы обязана быть атрибутом конкретной подписки (`Subscription`).
2. **Сериализация float для денег в старых схемах:** Значения типа `1590.50` во float могут превратиться в `1590.4999999999998`. Для финансовых данных всегда используйте целочисленные копейки или строковые представления (`decimal.Decimal`).

## На собеседовании

**Вопрос:** Как организовать процесс устаревания (Deprecation) старых версий webhook API без внезапных поломок у клиентов?

**Ответ:** 
1. **Sunset Header:** При отправке событий старых версий в HTTP-заголовки добавляется `Sunset: Wed, 11 Nov 2026 00:00:00 GMT` (RFC 8594) и `Deprecation: true`.
2. **Дашборд в личном кабинете:** Вывод плашки с предупреждением и логом устаревших вызовов.
3. **Периодические учения (Brownouts):** За 3 месяца до окончательного отключения устаревшая версия отключается на 1 час ночью, чтобы клиенты вовремя обнаружили сбои в своих алертах.
