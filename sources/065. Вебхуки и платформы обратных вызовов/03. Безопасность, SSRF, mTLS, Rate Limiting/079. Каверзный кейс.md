# Каверзный кейс: Защита от Replay Attack через Timestamp и Nonce

## Условие

Злоумышленник перехватил валидный вебхук и шлет его снова и снова. Добавь заголовок `X-Timestamp`. Включи timestamp в HMAC-подпись. На стороне приемника отклоняй запросы, timestamp которых старше 5 минут.

### Исходная формулировка

**[Каверзный кейс — Replay Attack]**: Злоумышленник перехватил валидный вебхук и шлет его снова и снова. Добавь заголовок `X-Timestamp`. Включи timestamp в HMAC-подпись. На стороне приемника отклоняй запросы, timestamp которых старше 5 минут.

## Теория

Атака повторного воспроизведения (**Replay Attack**) — критическая угроза безопасности вебхуков.

### Сценарий атаки:
1. Платформа отправляет подписчику вебхук о начислении средств:
   `{"event": "balance.credited", "user_id": "usr_77", "amount": 50000}`.
2. Даже если запрос защищен подписью `X-Signature: <hmac>`, злоумышленник (например, скомпрометировавший промежуточный прокси или логи клиента) перехватывает оригинальное тело и сигнатуру.
3. Атакующий отправляет эту же пару (тело + сигнатура) на эндпоинт приемника еще 100 раз.
4. Поскольку подпись валидна для этого тела, приемник без защиты от replay повторно начислит 5 000 000 рублей!

### Алгоритм защиты стандарта Stripe/GitHub:
1. **Заголовок `X-Timestamp` (или `t=` в заголовке `Stripe-Signature`):** Метка времени в формате Unix Epoch (секунды).
2. **Связывание подписи:** Подпись HMAC вычисляется **НЕ** от чистого тела, а от конкатенации:
   $$\text{SignedPayload} = \text{Timestamp} + "." + \text{RawBody}$$
   $$\text{Signature} = \text{HMAC-SHA256}(\text{SignedPayload}, \text{Secret})$$
   Злоумышленник не может подделать метку времени, так как изменение даже одной цифры времени инвалидирует HMAC!
3. **Правила верификации на стороне приемника:**
   - Извлечь \(t\) и подпись.
   - Проверить допустимое окно времени: \(|now - t| \le 300\text{ секунд}\) (5 минут) для учета рассинхронизации часов (Clock Skew).
   - Вычислить HMAC от $t + "." + body$ и сверить с полученной сигнатурой через `subtle.ConstantTimeCompare`.
   - Для абсолютной защиты в пределах 5-минутного окна: сохранить хеш сигнатуры в Redis с TTL=5 минут (защита от повторов внутри допустимого окна).

## Решение по шагам

1. Реализуйте генератор подписи отправителя `SignWebhook(secret, payload, timestamp)`.
2. Сформируйте строку вида `${timestamp}.${payload}` для HMAC.
3. Реализуйте верификатор приемника `VerifyWebhook(secret, payload, timestampHeader, sigHeader, tolerance)`.
4. Проверьте разницу между текущим временем и `timestamp`. Если она превышает 5 минут, отклоните запрос.
5. Проверьте совпадение подписи константным сравнением.

## Код решения

**`replay_guard.go`**

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"errors"
	"fmt"
	"strconv"
	"time"
)

var (
	ErrTimestampTooOld   = errors.New("webhook rejected: timestamp is older than tolerance window (potential replay attack)")
	ErrTimestampInFuture = errors.New("webhook rejected: timestamp is too far in future (clock skew issue)")
	ErrInvalidSignature  = errors.New("webhook rejected: HMAC signature verification failed")
)

// SignWithTimestamp генерирует подпись от timestamp.body
func SignWithTimestamp(secret []byte, payload []byte, t time.Time) (string, string) {
	timestampStr := strconv.FormatInt(t.Unix(), 10)
	mac := hmac.New(sha256.New, secret)

	// Конкатенируем метку времени и полезную нагрузку через точку
	mac.Write([]byte(timestampStr))
	mac.Write([]byte("."))
	mac.Write(payload)

	signature := hex.EncodeToString(mac.Sum(nil))
	return timestampStr, signature
}

// VerifyWebhookAndReplay валидирует подпись и проверяет допустимое окно времени
func VerifyWebhookAndReplay(secret []byte, payload []byte, timestampHeader, signatureHeader string, tolerance time.Duration) error {
	// 1. Парсинг метки времени
	tsInt, err := strconv.ParseInt(timestampHeader, 10, 64)
	if err != nil {
		return fmt.Errorf("invalid timestamp format: %w", err)
	}

	eventTime := time.Unix(tsInt, 0)
	now := time.Now()

	// 2. Проверка окна устаревания (Tolerance Window)
	if now.Sub(eventTime) > tolerance {
		return fmt.Errorf("%w: delta=%v > tolerance=%v", ErrTimestampTooOld, now.Sub(eventTime), tolerance)
	}
	// Защита от сообщений из "будущего" (при рассинхронизации NTP серверов)
	if eventTime.Sub(now) > tolerance {
		return fmt.Errorf("%w: message is from the future", ErrTimestampInFuture)
	}

	// 3. Вычисление ожидаемого HMAC
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(timestampHeader))
	mac.Write([]byte("."))
	mac.Write(payload)
	expectedMAC := mac.Sum(nil)

	expectedSigHex := hex.EncodeToString(expectedMAC)

	// 4. Безопасное сравнение подписей с защитой от тайминг-атак
	if subtle.ConstantTimeCompare([]byte(expectedSigHex), []byte(signatureHeader)) != 1 {
		return ErrInvalidSignature
	}

	return nil
}

func main() {
	secret := []byte("whsec_SuperSecureSigningKey2026")
	payload := []byte(`{"event":"wallet.credited","amount":50000}`)
	tolerance := 5 * time.Minute

	// Кейс 1: Нормальная валидная отправка
	now := time.Now()
	tsStr, sig := SignWithTimestamp(secret, payload, now)
	err := VerifyWebhookAndReplay(secret, payload, tsStr, sig, tolerance)
	fmt.Printf("Кейс 1 (Свежий запрос): Ошибка = %v (Успешно принят)\n", err)

	// Кейс 2: Попытка Replay Attack перехваченного запроса через 15 минут
	oldTime := time.Now().Add(-15 * time.Minute)
	oldTsStr, oldSig := SignWithTimestamp(secret, payload, oldTime)
	err = VerifyWebhookAndReplay(secret, payload, oldTsStr, oldSig, tolerance)
	fmt.Printf("Кейс 2 (Replay атака через 15 мин): Ошибка = %v\n", err)

	// Кейс 3: Злоумышленник пытается обновить X-Timestamp на текущий, не зная секретный ключ
	currentTsStr := strconv.FormatInt(time.Now().Unix(), 10)
	err = VerifyWebhookAndReplay(secret, payload, currentTsStr, oldSig, tolerance)
	fmt.Printf("Кейс 3 (Подмена timestamp без знания ключа): Ошибка = %v\n", err)
}
```

## Под капотом

Почему простой проверки `now - timestamp <= 5 min` недостаточно для 100% защиты от replay?
Внутри 5-минутного окна злоумышленник всё еще может переслать запрос 100 раз за секунду, и проверка времени пройдет!

Для абсолютной защиты применяется двухуровневый барьер:
1. Первый уровень: проверка `Timestamp` отсекает 99.9% старых запросов без обращения к хранилищам.
2. Второй уровень (Дедупликация Nonce/Signature): при успешной валидации подписи приемник сохраняет полученный `signature` (или `event_id`) в Redis командой:
   `SET webhook:seen:<signature> 1 EX 300 NX`
   Если Redis возвращает `nil` (ключ уже был записан ранее в течение последних 5 минут), запрос мгновенно отбрасывается как повторный! Через 5 минут ключ сам исчезнет из Redis, когда запрос уже перестанет проходить первый уровень проверки времени.

## Подводные камни

1. **Подписание только тела без метки времени:** Если вычислять `HMAC(rawBody)`, злоумышленник сможет повторять запрос бесконечно в любое время в течение всего срока жизни секретного ключа.
2. **Нестрогий парсинг времени:** Использование текстовых форматов даты с временными зонами (`RFC1123`, `RFC3339`) может приводить к ошибкам парсинга из-за расхождений локалей. Всегда используйте плоский Unix Epoch в секундах (`time.Now().Unix()`).

## На собеседовании

**Вопрос:** Почему в заголовке `Stripe-Signature` передается значение вида `t=1614555555,v1=5257a869e7eee...`, а не два раздельных HTTP-заголовка?

**Ответ:** Объединение в один структурированный заголовок решает три задачи:
1. **Атомарность:** Гарантирует, что заголовок не будет потерян или переименован промежуточными прокси-серверами.
2. **Версионирование схемы:** Позволяет передавать сразу несколько версий подписей (например, `v1=...` для SHA-256 и `v2=...` для Ed25519) для бесшовной ротации алгоритмов шифрования без даунтайма.
3. **Бесшовная ротация ключей:** Можно передать несколько подписей `v1`, подписанных старым и новым секретным ключом одновременно.
