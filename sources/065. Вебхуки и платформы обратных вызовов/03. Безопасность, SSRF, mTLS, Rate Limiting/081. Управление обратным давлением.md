# Управление обратным давлением (Backpressure при перегрузке)

## Условие

Если delivery queue переполнена, временно переставайте принимать новые webhook registrations или переводите на degraded mode.

### Исходная формулировка

**Backpressure при перегрузке**: Если delivery queue переполнена, временно переставайте принимать новые webhook registrations или переводите на degraded mode.

## Теория

Когда входящий поток бизнес-событий превышает пропускную способность диспетчера доставки вебхуков (например, при падении внешних каналов или пиковой распродаже 11.11), очередь неотправленных сообщений начинает лавинообразно расти.

### Проблема отсутствия Backpressure:
Если система продолжает слепо принимать запросы на отправку и регистрацию вебхуков, оперативная память очередей исчерпывается (OOM), а задержка доставки возрастает с миллисекунд до десятков часов.

### Стратегии применения Backpressure:
1. **HTTP 429 Too Many Requests / 503 Service Unavailable:** При заполнении очереди более чем на 80–90% API-эндпоинт отправки вебхуков возвращает `HTTP 429` с заголовком `Retry-After: 30`, заставляя продюсеров притормозить.
2. **Degraded Mode (Деградация сервиса):**
   - Блокировка регистрации новых подписок (`POST /api/v1/webhooks/subscriptions` возвращает `503 Maintenance`).
   - Отключение несрочных типов событий (уведомления об изменении профиля глушатся, приоритет отдается финансовым транзакциям `payment.*`).
   - Сброс или откладывание в долговременное холодное хранилище (S3 / Kafka Cold Topic).

## Решение по шагам

1. Создайте структуру `DeliveryQueue` с ограниченной емкостью `capacity` и порогом перегрузки `highWatermark` (например, 80%).
2. Реализуйте атомарный мониторинг текущего размера очереди.
3. Напишите HTTP-шлюз, который перед постановкой события в очередь проверяет ее наполненность.
4. При перегрузке возвращайте статус `429 Too Many Requests` с заголовком `Retry-After` и переводите систему в режим деградации.

## Код решения

**`backpressure_gateway.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"time"
)

type WebhookTask struct {
	ID        string `json:"id"`
	Priority  string `json:"priority"` // "HIGH" (платежи) или "LOW" (аналитика)
	Payload   string `json:"payload"`
	CreatedAt time.Time
}

type BackpressureQueue struct {
	tasks         chan WebhookTask
	capacity      int64
	highWatermark int64 // 80% от capacity
	currentSize   atomic.Int64
	isDegraded    atomic.Bool
}

func NewBackpressureQueue(capacity int64) *BackpressureQueue {
	return &BackpressureQueue{
		tasks:         make(chan WebhookTask, capacity),
		capacity:      capacity,
		highWatermark: int64(float64(capacity) * 0.8),
	}
}

func (q *BackpressureQueue) Enqueue(task WebhookTask) bool {
	cur := q.currentSize.Load()

	// Если достигли критического уровня 80%, активируем degraded mode
	if cur >= q.highWatermark {
		q.isDegraded.Store(true)

		// В деградированном режиме принимаем только критические платежные события
		if task.Priority != "HIGH" {
			return false // Отклоняем низкоприоритетные задачи
		}
	} else {
		q.isDegraded.Store(false)
	}

	select {
	case q.tasks <- task:
		q.currentSize.Add(1)
		return true
	default:
		// Очередь физически полна на 100%
		return false
	}
}

func (q *BackpressureQueue) Dequeue() (WebhookTask, bool) {
	select {
	case task := <-q.tasks:
		q.currentSize.Add(-1)
		return task, true
	default:
		return WebhookTask{}, false
	}
}

// HTTP API Gateway с механизмом Backpressure
func WebhookIngestHandler(q *BackpressureQueue) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		var task WebhookTask
		if err := json.NewDecoder(r.Body).Decode(&task); err != nil {
			http.Error(w, "Bad Request", http.StatusBadRequest)
			return
		}
		task.CreatedAt = time.Now()

		accepted := q.Enqueue(task)
		if !accepted {
			w.Header().Set("Retry-After", "10")
			w.Header().Set("X-System-Status", "Degraded")
			http.Error(w, "Service Overloaded: delivery queue high watermark reached", http.StatusTooManyRequests)
			return
		}

		w.WriteHeader(http.StatusAccepted)
		w.Write([]byte(`{"status":"enqueued"}`))
	}
}

func main() {
	// Создаем компактную очередь на 10 элементов с порогом 8 элементов
	queue := NewBackpressureQueue(10)
	handler := WebhookIngestHandler(queue)
	ts := httptest.NewServer(handler)
	defer ts.Close()

	fmt.Println("=== Симуляция наполнения очереди до порога перегрузки (Backpressure) ===")

	// Наполняем очередь 8 обычными задачами
	for i := 1; i <= 8; i++ {
		queue.Enqueue(WebhookTask{ID: fmt.Sprintf("task-%d", i), Priority: "LOW"})
	}
	fmt.Printf("Текущий размер очереди: %d / %d (High Watermark = %d, Degraded = %v)\n",
		queue.currentSize.Load(), queue.capacity, queue.highWatermark, queue.isDegraded.Load())

	// Попытка отправить LOW приоритет через HTTP в момент перегрузки
	reqLow, _ := http.NewRequest(http.MethodPost, ts.URL,
		jsonReader(`{"id":"task-9-low","priority":"LOW","payload":"user.avatar_updated"}`))
	respLow, _ := http.DefaultClient.Do(reqLow)
	fmt.Printf("Отправка LOW приоритета: HTTP Статус = %d %s (Retry-After: %s)\n",
		respLow.StatusCode, http.StatusText(respLow.StatusCode), respLow.Header.Get("Retry-After"))

	// Отправка HIGH приоритета (платеж) в тот же момент
	reqHigh, _ := http.NewRequest(http.MethodPost, ts.URL,
		jsonReader(`{"id":"task-10-high","priority":"HIGH","payload":"payment.captured"}`))
	respHigh, _ := http.DefaultClient.Do(reqHigh)
	fmt.Printf("Отправка HIGH приоритета: HTTP Статус = %d %s\n",
		respHigh.StatusCode, http.StatusText(respHigh.StatusCode))
}

func jsonReader(s string) *http.Request {
	req, _ := http.NewRequest(http.MethodPost, "", nil)
	return req
}
```

## Под капотом

В распределенных системах реактивное обратное давление реализуется протоколами Reactive Streams и TCP Flow Control. На уровне Go-рантайма буферизированный канал размера \(N\) блокирует горутину при переполнении `q.tasks <- task`. Если HTTP-хендлер блокируется, пул воркеров веб-сервера (`http.Server`) перестает читать входящие байты из сокета. Буфер TCP-окна на хосте заполняется, и ОС отправляет пакет `TCP Zero Window`, аппаратно заставляя балансировщик нагрузки (Nginx/HAProxy/Envoy) притормозить передачу трафика.

## Подводные камни

1. **Неограниченные очереди (`make(chan Task)` без размера или слайс в памяти):** В памяти может накопиться миллион сообщений, что неминуемо приведет к Linux OOM Killer (`signal: killed`). Очередь всегда обязана иметь жесткий предел емкости (Bounded Queue).
2. **Возврат ошибки `500 Internal Server Error` вместо `429 Too Many Requests`:** Код 500 клиенты и прокси могут трактовать как фатальный баг сервиса, тогда как 429 с `Retry-After` корректно сообщает о временной перегрузке.

## На собеседовании

**Вопрос:** В чем разница между стратегиями Backpressure: `Drop Tail`, `Drop Head` и `CoDel` (Controlled Delay)?

**Ответ:** 
- **Drop Tail:** Отбрасываются новые входящие запросы при заполнении очереди. Плюс: старые события будут доставлены. Минус: новые актуальные события теряются.
- **Drop Head:** Удаляются самые старые сообщения из начала очереди, освобождая место для свежих. Применяется в real-time мониторинге, где актуальность свежих данных важнее устаревших.
- **CoDel:** Оценивается время нахождения задачи в очереди. Если задержка превышает SLA (например, 500 мс), пакеты адаптивно сбрасываются для предотвращения явления Bufferbloat.
