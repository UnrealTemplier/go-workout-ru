# Delivery attempts tracking: сбор детальной статистики попыток доставки

## Условие

### Исходная формулировка

**Delivery attempts tracking**: Сохраняйте каждый attempt: timestamp, request body, response code, response body, latency. Это gold для debugging.

## Теория

Для предоставления SLA и прозрачной аналитики платформа должна отслеживать метрики каждой подписки:
- `total_deliveries`: общее количество событий.
- `successful_deliveries`: количество подтвержденных доставок (2xx).
- `failed_deliveries`: количество ошибок (4xx, 5xx, таймауты).
- `success_rate`: процент успешных доставок: \(\frac{\text{Success}}{\text{Total}} \times 100\%\).
- `consecutive_failures`: счетчик ошибок подряд (триггер для Circuit Breaker и Auto-disable).
Счетчики ведутся атомарно в Redis (`HINCRBY`) или в памяти с периодическим сбросом в PostgreSQL.

## Решение по шагам

1. Опишите структуру метрик подписки `SubscriptionMetrics`.
2. Реализуйте потокобезопасный трекер статистики с атомарным учетом успехов и сбоев.
3. Продемонстрируйте обновление счетчиков и расчет `SuccessRate`.
4. Смоделируйте 100 попыток и выведите итоговую статистику.

## Код решения

**`attempts_tracker.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
)

type DeliveryStatsTracker struct {
	TotalEvents        int64
	SuccessCount       int64
	FailureCount       int64
	ConsecutiveFails   int64
}

func (t *DeliveryStatsTracker) RecordSuccess() {
	atomic.AddInt64(&t.TotalEvents, 1)
	atomic.AddInt64(&t.SuccessCount, 1)
	atomic.StoreInt64(&t.ConsecutiveFails, 0) // Сброс ошибок подряд
}

func (t *DeliveryStatsTracker) RecordFailure() {
	atomic.AddInt64(&t.TotalEvents, 1)
	atomic.AddInt64(&t.FailureCount, 1)
	atomic.AddInt64(&t.ConsecutiveFails, 1)
}

func (t *DeliveryStatsTracker) SuccessRate() float64 {
	total := atomic.LoadInt64(&t.TotalEvents)
	if total == 0 {
		return 100.0
	}
	success := atomic.LoadInt64(&t.SuccessCount)
	return (float64(success) / float64(total)) * 100.0
}

func main() {
	tracker := &DeliveryStatsTracker{}

	// Симулируем 85 успехов и 15 ошибок
	for i := 0; i < 85; i++ {
		tracker.RecordSuccess()
	}
	for i := 0; i < 15; i++ {
		tracker.RecordFailure()
	}

	fmt.Printf("Total Deliveries:     %d\n", atomic.LoadInt64(&tracker.TotalEvents))
	fmt.Printf("Successes:            %d\n", atomic.LoadInt64(&tracker.SuccessCount))
	fmt.Printf("Failures:             %d\n", atomic.LoadInt64(&tracker.FailureCount))
	fmt.Printf("Consecutive Failures: %d\n", atomic.LoadInt64(&tracker.ConsecutiveFails))
	fmt.Printf("Calculated SLA:       %.2f%%\n", tracker.SuccessRate())
}
```

## Под капотом

Использование функций пакета `sync/atomic` (`AddInt64`, `StoreInt64`, `LoadInt64`) транслируется компилятором Go в аппаратные атомарные инструкции процессора `LOCK XADD` и `LOCK CMPXCHG` на архитектурах x86-64. Это работает на порядок быстрее захвата мьютексов и не вызывает переключения контекста горутин планировщиком GMP.

## Подводные камни

1. Использование обычных переменных без синхронизации: Data Race при конкурентной фиксации результатов воркерами.
2. Слишком частые синхронные `UPDATE` в реляционную БД на каждый запрос: приводит к блокировкам строк в таблице подписок. Счетчики агрегируются в Redis или оперативной памяти и сбрасываются в БД пачками раз в 10–30 секунд.
3. Деление на ноль при пустой статистике.

## На собеседовании

**Вопрос (Ozon/Stripe):** Как отображать мерчанту график успешности доставок вебхуков за последние 24 часа без тяжелых аналитических SQL-запросов `COUNT(*)` к таблице логов?
**Ответ:** Применяется кольцевой буфер минутных срезов (Time-Bucketed Counters) в Redis:
Каждая минута образует ключ `stats:endpoint_id:YYYYMMDDHHmm`, куда воркеры атомарно инкрементируют счетчики `success` и `fail`.
При открытии Dashboard бэкенд вычитывает 1440 минутных ключей за последние сутки через `MGET` за 2 миллисекунды, мгновенно строя график без нагрузки на основную базу данных.
