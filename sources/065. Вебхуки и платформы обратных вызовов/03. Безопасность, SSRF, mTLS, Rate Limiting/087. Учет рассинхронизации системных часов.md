# Учет рассинхронизации системных часов (Clock Skew Tolerance)

## Условие

При timestamp verification допускайте ±5 минут clock skew между вашим и клиентским сервером.

### Исходная формулировка

**Clock skew tolerance**: При timestamp verification допускайте ±5 минут clock skew между вашим и клиентским сервером.

## Теория

Серверы отправителя и приемника вебхука физически находятся в разных дата-центрах и даже на разных континентах.

Хотя в современных облаках службы синхронизации времени NTP (Network Time Protocol) или PTP (Precision Time Protocol) работают непрерывно, в реальности всегда присутствует явление **Clock Skew** (дрейф часов):
- Задержки обновления NTP.
- Виртуализация (дрейф тактовой частоты TSC внутри гостевой виртуальной машины под нагрузкой).
- Прыжки високосных секунд (Leap Seconds).

### Проблема строгого окна времени:
Если платформа отправила вебхук в `12:00:00`, а часы сервера клиента спешат на 15 секунд (`12:00:15`), при строгом условии `now >= eventTime` сервер клиента решит, что сообщение пришло «из будущего», и отклонит его!

### Стандарт допуска рассинхронизации (Tolerance Window):
Приемник обязан проверять **абсолютное значение разницы**:
$$|\text{ServerNow} - \text{Timestamp}| \le \text{ToleranceWindow}$$
Стандартное отраслевое значение допуска: **\(\pm 5\) минут** (300 секунд). Все запросы, укладывающиеся в диапазон $[now - 300s, now + 300s]$, признаются валидными по времени.

## Решение по шагам

1. Реализуйте функцию `ValidateTimestampTolerance(headerTimestamp int64, tolerance time.Duration) error`.
2. Получите текущее время `time.Now()`.
3. Вычислите разницу `now.Sub(eventTime)`.
4. Проверьте два условия: сообщение не должно быть старше `+tolerance` и не должно опережать время более чем на `-tolerance`.

## Код решения

**`clock_skew.go`**

```go
package main

import (
	"errors"
	"fmt"
	"math"
	"time"
)

var (
	ErrMessageTooOld   = errors.New("webhook rejected: event timestamp is too old (expired)")
	ErrMessageInFuture = errors.New("webhook rejected: event timestamp is too far in future (unacceptable clock skew)")
)

// CheckClockSkew проверяет попадание метки времени в допустимый интервал [-tolerance, +tolerance]
func CheckClockSkew(headerUnixTime int64, tolerance time.Duration) error {
	eventTime := time.Unix(headerUnixTime, 0)
	now := time.Now()

	diff := now.Sub(eventTime)

	// Проверка на устаревание (сообщение из прошлого)
	if diff > tolerance {
		return fmt.Errorf("%w: delta = %v (max allowed: %v)", ErrMessageTooOld, diff, tolerance)
	}

	// Проверка на сообщение из будущего (часы отправителя спешат)
	if diff < -tolerance {
		ahead := time.Duration(math.Abs(float64(diff)))
		return fmt.Errorf("%w: message is %v in the future (max allowed: %v)", ErrMessageInFuture, ahead, tolerance)
	}

	return nil
}

func main() {
	tolerance := 5 * time.Minute
	now := time.Now()

	testCases := []struct {
		name      string
		timestamp time.Time
	}{
		{"Синхронно (0 сек разницы)", now},
		{"Отправитель отстал на 2 минуты", now.Add(-2 * time.Minute)},
		{"Отправитель спешит на 3 минуты", now.Add(3 * time.Minute)},
		{"Устарело (Отправитель отстал на 10 минут)", now.Add(-10 * time.Minute)},
		{"Аномалия (Отправитель спешит на 8 минут)", now.Add(8 * time.Minute)},
	}

	fmt.Printf("=== Валидация Clock Skew с допуском ±%v ===\n", tolerance)
	for _, tc := range testCases {
		err := CheckClockSkew(tc.timestamp.Unix(), tolerance)
		if err != nil {
			fmt.Printf("FAIL: %-45s -> %v\n", tc.name, err)
		} else {
			fmt.Printf("OK:   %-45s -> Принято\n", tc.name)
		}
	}
}
```

## Под капотом

В Go 1.9+ структура `time.Time` содержит два механизма отсчета времени: **Wall Clock** (календарное время) и **Monotonic Clock** (монотонные часы процессора).
При сравнении времени через `now.Sub(eventTime)`: если `eventTime` сконструирован из сырого Unix Timestamp (`time.Unix(sec, 0)`), он не имеет монотонного счетчика. Go корректно сравнивает только настенное время. Настенное время может скакать при корректировке NTP, поэтому зазор в \(\pm 5\) минут спасает вебхуки от ложных срабатываний во время NTP-коррекций (Slewing/Stepping).

## Подводные камни

1. **Односторонняя проверка `now - timestamp > tolerance`:** Если забыть про отрицательную дельту, злоумышленник сможет отправить сообщение со временем `Timestamp = 2030 год`. Такое сообщение будет проходить валидацию в течение последующих 4 лет, допуская масштабные атаки воспроизведения!
2. **Использование локального времени вместо UTC:** Передача `time.Now().Format("2006-01-02 15:04:05")` без таймзоны приведет к сбою верификации из-за разницы часовых поясов серверов.

## На собеседовании

**Вопрос:** Как высоконагруженные базы данных (Google Spanner) решают проблему неизбежного Clock Skew?

**Ответ:** Google Spanner использует API **TrueTime**, опирающийся на атомные часы и GPS-приемники в каждом ЦОД. TrueTime возвращает время не как точку, а как интервал неопределенности $[earliest, latest]$ (обычно \(\pm 1–7\) мс). Для сериализуемости транзакций система ждет время \(\epsilon\) перед коммитом (Commit Wait), гарантируя глобальный порядок событий во всем мире.
