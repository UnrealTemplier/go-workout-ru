# Пул воркеров для вебхуков фиксированного размера (Worker Pool)

## Условие

Не создавай новую горутину на каждый вебхук, иначе всплеск событий выест всю память. Напиши Worker Pool на 100 воркеров. Они должны читать задачи из очереди (канала) и выполнять логику с ретраями.

### Исходная формулировка

**Пул воркеров для вебхуков**: Не создавай новую горутину на каждый вебхук, иначе всплеск событий выест всю память. Напиши Worker Pool на 100 воркеров. Они должны читать задачи из очереди (канала) и выполнять логику с ретраями.

## Теория

Распространенная ошибка начинающих Go-разработчиков — запускать `go sendWebhook(w)` на каждое входящее событие.

### Почему создание горутины на каждый запрос опасно:
1. **Память стека:** Начальный стек горутины равен 2 КБ. При всплеске в 500 000 событий это \(500\,000 \times 2\text{ KB} \approx 1\text{ GB}\) памяти только под стеки, без учета полезной нагрузки!
2. **Планировщик GMP:** Переключение контекста между 500 000 горутинами перегрузит планировщик рантайма Go, вызвав лавинообразный рост задержки (Scheduling Latency).
3. **Сокеты и дескрипторы:** Слишком много одновременных вызовов `connect(2)` приведет к ошибкам ядра Linux `EMFILE` и `EADDRNOTAVAIL`.

### Архитектура пула воркеров (Worker Pool Pattern):
Фиксированное количество долгоживущих горутин (\(W = 100\)), которые в цикле `for job := range jobQueue` непрерывно вычитывают задачи из единого буферизированного канала, гарантируя строгий потолок потребления памяти и дескрипторов.

## Решение по шагам

1. Создайте структуру `DeliveryTask` с метаданными вебхука и счетчиком попыток.
2. Инициализируйте структуру `WorkerPool` с очередью `tasks chan DeliveryTask` и контекстом отмены.
3. Запустите \(N\) горутин-воркеров (`workerID = 1..N`), читающих из общего канала.
4. Реализуйте безопасное завершение (Graceful Shutdown): закрытие канала задач и ожидание завершения воркеров через `sync.WaitGroup`.

## Код решения

**`worker_pool.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type WebhookJob struct {
	ID        string
	TargetURL string
	Attempt   int
	MaxRetry  int
}

type WebhookWorkerPool struct {
	numWorkers  int
	jobQueue    chan WebhookJob
	wg          sync.WaitGroup
	ctx         context.Context
	cancel      context.CancelFunc
	completed   atomic.Int64
	retriedJobs atomic.Int64
}

func NewWebhookWorkerPool(numWorkers int, queueSize int) *WebhookWorkerPool {
	ctx, cancel := context.WithCancel(context.Background())
	return &WebhookWorkerPool{
		numWorkers: numWorkers,
		jobQueue:   make(chan WebhookJob, queueSize),
		ctx:        ctx,
		cancel:     cancel,
	}
}

func (p *WebhookWorkerPool) Start() {
	for i := 1; i <= p.numWorkers; i++ {
		p.wg.Add(1)
		go p.worker(i)
	}
}

func (p *WebhookWorkerPool) worker(id int) {
	defer p.wg.Done()

	for {
		select {
		case <-p.ctx.Done():
			return
		case job, ok := <-p.jobQueue:
			if !ok {
				return // Канал закрыт при штатной остановке
			}
			p.processJob(id, job)
		}
	}
}

func (p *WebhookWorkerPool) processJob(workerID int, job WebhookJob) {
	// Симуляция доставки: первая попытка падает, вторая успешна
	success := job.Attempt > 1

	if success {
		p.completed.Add(1)
	} else {
		if job.Attempt < job.MaxRetry {
			p.retriedJobs.Add(1)
			job.Attempt++
			// В реальной системе: откладываем повтор с задержкой
			go func(retryJob WebhookJob) {
				time.Sleep(10 * time.Millisecond)
				p.Submit(retryJob)
			}(job)
		} else {
			p.completed.Add(1) // Достигнут лимит попыток
		}
	}
}

func (p *WebhookWorkerPool) Submit(job WebhookJob) bool {
	select {
	case p.jobQueue <- job:
		return true
	case <-p.ctx.Done():
		return false
	}
}

func (p *WebhookWorkerPool) Stop() {
	p.cancel()        // Сигнализируем об остановке
	close(p.jobQueue) // Закрываем очередь
	p.wg.Wait()       // Ждем завершения текущих задач
}

func main() {
	const workerCount = 5
	const taskCount = 20

	pool := NewWebhookWorkerPool(workerCount, 100)
	pool.Start()

	fmt.Printf("Запущен Worker Pool: %d воркеров. Отправка %d задач...\n", workerCount, taskCount)

	for i := 1; i <= taskCount; i++ {
		pool.Submit(WebhookJob{
			ID:        fmt.Sprintf("job-%02d", i),
			TargetURL: "https://api.partner.ru/hook",
			Attempt:   1,
			MaxRetry:  3,
		})
	}

	// Даем время на обработку и ретраи
	time.Sleep(100 * time.Millisecond)
	pool.Stop()

	fmt.Printf("=== Обработка завершена ===\n")
	fmt.Printf("Всего успешно завершено задач: %d\n", pool.completed.Load())
	fmt.Printf("Ретраи выполнено:            %d\n", pool.retriedJobs.Load())
}
```

## Под капотом

В Go чтение из одного буферизированного канала несколькими воркерами `job, ok := <-p.jobQueue` является потокобезопасным и реализовано через мьютекс очереди внутри рантайма `hchan.lock`.
Когда канал пуст, воркер переходит в состояние ожидания (`gopark`), добавляя свою структуру G в список ожидания `recvq`. При появлении новой задачи в канале вызывающая горутина будит ровно одного воркера через `goready()`, исключая напрасную трату тактов CPU (No Busy-Wait).

## Подводные камни

1. **Блокировка `pool.Stop()` при закрытии канала:** Если сначала закрыть `close(jobQueue)`, а параллельные горутины продолжают писать в него через `Submit()`, возникнет паника `panic: send on closed channel`. Всегда используйте отмену контекста перед закрытием канала.
2. **Потеря задач при мгновенном `cancel()`:** Если прервать выполнение через `ctx.Cancel()`, задачи, уже лежащие в канале, не будут обработаны. Для честного Graceful Shutdown закрывайте только канал и ждите `wg.Wait()`, пока буфер не опустеет.

## На собеседовании

**Вопрос:** Как масштабировать Worker Pool динамически (Dynamic Pool Resizing) в зависимости от размера очереди задач?

**Ответ:** Создается фоновый координатор (Scaler loop), проверяющий `len(jobQueue) / cap(jobQueue)` каждые 500 мс:
- Если заполненность > 70%, запускаются дополнительные горутины воркеров вплоть до `maxWorkers`.
- Если заполненность < 20% в течение 30 секунд, воркеры считывают команду остановки из специального канала `quit` или завершаются по таймауту ожидания задачи `select { case job := <-queue: ... case <-time.After(idleTimeout): return }`, сокращая пул до `minWorkers`.
