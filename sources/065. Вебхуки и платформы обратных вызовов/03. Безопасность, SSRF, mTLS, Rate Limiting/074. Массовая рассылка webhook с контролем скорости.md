# Массовая рассылка webhook с контролем скорости через семафор

## Условие

Реализуйте диспетчер, который отправляет webhooks нескольким подписчикам, ограничивая количество одновременных исходящих запросов (rate limiting на уровне горутин через семафор).

### Исходная формулировка

**Массовая рассылка webhook с контролем скорости.**: Реализуйте диспетчер, который отправляет webhooks нескольким подписчикам, ограничивая количество одновременных исходящих запросов (rate limiting на уровне горутин через семафор).

## Теория

При возникновении глобального бизнес-события (например, «Новогодняя распродажа активирована» или «Изменение политики цен») система обязана разослать вебхук 50 000 подписчикам одновременно (Fan-Out).

Если запустить по горутине на каждого подписчика (`go deliverWebhook(sub)`), мы мгновенно создадим 50 000 горутин и 50 000 исходящих TCP-соединений.

### Катастрофические последствия неуправляемого Fan-Out:
1. **Исчерпание файловых дескрипторов (`EMFILE: too many open files`):** ОС прервет процесс.
2. **Исчерпание динамических портов (Ephemeral Port Exhaustion):** В ОС Linux диапазон локальных портов ограничен (~32 768 – 60 999). При превышении лимита системный вызов `connect()` возвращает ошибку `EADDRNOTAVAIL`.
3. **Перегрузка исходящего сетевого канала (Egress Bottleneck).**

### Решение: Ограничение параллелизма через Семафор:
Паттерн Weighted Semaphore на базе буферизированного канала `chan struct{}` или `golang.org/x/sync/semaphore`. Платформа гарантирует, что в любой момент времени выполняется не более \(W\) одновременных HTTP-запросов.

## Решение по шагам

1. Создайте структуру `WebhookDispatcher` с максимальным лимитом параллелизма `maxWorkers`.
2. Используйте канал `chan struct{}` емкостью `maxWorkers` в качестве взвешенного семафора.
3. Используйте `sync.WaitGroup` для безопасного ожидания завершения всех задач рассылки.
4. Добавьте поддержку отмены всей рассылки через `context.Context`.
5. Соберите статистику успешных и проваленных доставок с потокобезопасными счетчиками (`sync/atomic`).

## Код решения

**`semaphore_dispatcher.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type TargetSubscriber struct {
	ID  string
	URL string
}

type DispatchResult struct {
	TotalSent  int64
	Successful int64
	Failed     int64
	Duration   time.Duration
}

type BroadcastDispatcher struct {
	maxConcurrency int
	sem            chan struct{}
}

func NewBroadcastDispatcher(maxConcurrency int) *BroadcastDispatcher {
	return &BroadcastDispatcher{
		maxConcurrency: maxConcurrency,
		sem:            make(chan struct{}, maxConcurrency),
	}
}

// Broadcast отправляет полезную нагрузку всем подписчикам с жестким ограничением параллелизма
func (d *BroadcastDispatcher) Broadcast(ctx context.Context, payload []byte, subs []TargetSubscriber) DispatchResult {
	start := time.Now()
	var (
		totalSent  atomic.Int64
		successful atomic.Int64
		failed     atomic.Int64
		wg         sync.WaitGroup
	)

	for _, sub := range subs {
		// Проверяем, не отменен ли общий контекст перед запуском
		if ctx.Err() != nil {
			break
		}

		// Захватываем слот семафора с учетом отмены контекста
		select {
		case <-ctx.Done():
			break
		case d.sem <- struct{}{}:
		}

		wg.Add(1)
		go func(target TargetSubscriber) {
			defer func() {
				<-d.sem // Освобождаем слот семафора
				wg.Done()
			}()

			totalSent.Add(1)
			err := d.sendToSubscriber(ctx, target, payload)
			if err != nil {
				failed.Add(1)
			} else {
				successful.Add(1)
			}
		}(sub)
	}

	wg.Wait()

	return DispatchResult{
		TotalSent:  totalSent.Load(),
		Successful: successful.Load(),
		Failed:     failed.Load(),
		Duration:   time.Since(start),
	}
}

// Симуляция отправки HTTP POST запроса
func (d *BroadcastDispatcher) sendToSubscriber(ctx context.Context, target TargetSubscriber, payload []byte) error {
	// Имитация сетевой задержки от 10 до 30 мс
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-time.After(20 * time.Millisecond):
	}
	return nil
}

func main() {
	// Подготавливаем 100 подписчиков
	subscribers := make([]TargetSubscriber, 100)
	for i := 0; i < 100; i++ {
		subscribers[i] = TargetSubscriber{
			ID:  fmt.Sprintf("client-%03d", i+1),
			URL: fmt.Sprintf("https://partner-%03d.ru/webhook", i+1),
		}
	}

	// Ограничиваем параллелизм 10 одновременными запросами
	dispatcher := NewBroadcastDispatcher(10)

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	fmt.Printf("Старт рассылки по %d подписчикам с семафором на %d горутин...\n", len(subscribers), dispatcher.maxConcurrency)
	res := dispatcher.Broadcast(ctx, []byte(`{"event":"flash_sale.started"}`), subscribers)

	fmt.Printf("\n=== Результаты рассылки ===\n")
	fmt.Printf("Всего запущено:  %d\n", res.TotalSent)
	fmt.Printf("Успешно:         %d\n", res.Successful)
	fmt.Printf("Ошибок:          %d\n", res.Failed)
	fmt.Printf("Время рассылки:  %v\n", res.Duration.Round(time.Millisecond))
}
```

## Под капотом

Почему семафор на `chan struct{}` эффективнее создания пула горутин постоянного размера (Worker Pool) в сценарии массовой веерной рассылки?
1. В Worker Pool задачи передаются через единый канал задач (`jobsChan <- task`). Это создает конкуренцию на очереди задач.
2. При семафоре горутина создается по мере необходимости и уничтожается сразу после завершения, не удерживая память под стек, когда рассылки нет.
3. Семафор захватывается в главном цикле `d.sem <- struct{}{}`. Если все слоты заняты, главный цикл блокируется, естественным образом реализуя **Backpressure** без разрастания оперативной памяти.

## Подводные камни

1. **Захват слота семафора ВНУТРИ горутины:** Если написать `go func() { d.sem <- struct{}{}; ... }()`, горутины будут созданы мгновенно в количестве 50 000 штук, исчерпав память под стеки еще до того, как они начнут ждать в канале! Захват обязателен **до** ключевого слова `go`.
2. **Утечка слота при панике:** Если функция доставки запаникует, слот в канале не освободится, что со временем приведет к вечному зависанию диспетчера. Освобождение слота `<-d.sem` обязано находиться в блоке `defer`.

## На собеседовании

**Вопрос:** Как избежать утечки сокетов в состоянии `TIME_WAIT` при высокочастотной рассылке десятков тысяч вебхуков на различные внешние домены?

**Ответ:** По умолчанию в `http.Transport` включен `DisableKeepAlives = false`, но `MaxIdleConnsPerHost` по умолчанию равен всего 2! При рассылке на 1000 разных хостов соединения закрываются со стороны клиента после каждого запроса, заполняя таблицу состояний ядра тысячами сокетов в `TIME_WAIT`. Решение:
1. Тюнить `MaxIdleConns` (до 10 000) и `MaxIdleConnsPerHost` (до 50-100).
2. Обязательно вычитывать `io.Copy(io.Discard, resp.Body)` и закрывать `resp.Body.Close()`, иначе соединение не вернется в пул переиспользования `Keep-Alive`.
