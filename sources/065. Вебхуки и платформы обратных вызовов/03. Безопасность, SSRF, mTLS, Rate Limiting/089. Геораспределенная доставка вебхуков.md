# Геораспределенная доставка вебхуков (Multi-Region Delivery)

## Условие

Для low-latency delivery клиентам в разных регионах используйте regional webhook sender'ы (US, EU, APAC).

### Исходная формулировка

**Webhook delivery from multiple regions**: Для low-latency delivery клиентам в разных регионах используйте regional webhook sender'ы (US, EU, APAC).

## Теория

Если клиенты платформы распределены по всему миру (Европа, Северная Америка, Сингапур/APAC), а диспетчер вебхуков расположен только в одном дата-центре (например, в Москве или Франкфурте), возникают колоссальные сетевые задержки:
- RTT между Европой и Сингапуром: ~180–220 мс.
- Полный цикл доставки HTTPS вебхука требует:
  1. DNS-резолв (~20 мс).
  2. TCP 3-Way Handshake (~200 мс).
  3. TLS 1.3 Handshake (~200 мс).
  4. HTTP Request + Response (~200 мс).
  Итого: **~620–800 миллисекунд** на один запрос! Это снижает пропускную способность воркеров в 10 раз.

### Архитектура Multi-Region Delivery:
1. **Региональные кластеры воркеров:** Развертывание легких sender-воркеров в регионах `us-east`, `eu-central`, `ap-southeast`.
2. **Маршрутизация по геолокации эндпоинта:**
   - При регистрации подписки определяется GeoIP целевого домена (или клиент явно выбирает `preferred_region`).
   - Событие направляется в брокер Kafka регионального хаба.
3. **Результат:** RTT сокращается с 200 мс до 5–15 мс, а общая скорость доставки ускоряется до 10 раз!

## Решение по шагам

1. Создайте перечисление географических регионов (`RegionEU`, `RegionUS`, `RegionAPAC`).
2. Реализуйте геомаршрутизатор `RegionRouter`, определяющий оптимальный регион по URL.
3. Смоделируйте локальную доставку с измерением региональной задержки.
4. Продемонстрируйте выбор оптимального шлюза.

## Код решения

**`multi_region_dispatcher.go`**

```go
package main

import (
	"fmt"
	"strings"
	"time"
)

type Region string

const (
	RegionEU   Region = "eu-central"   // Франкфурт
	RegionUS   Region = "us-east"      // Вирджиния
	RegionAPAC Region = "ap-southeast" // Сингапур
)

type RegionalSender struct {
	Region     Region
	BaseRTT    time.Duration // Имитация средней сетевой задержки внутри региона
}

func (s *RegionalSender) Deliver(endpoint string) time.Duration {
	// Локальная доставка внутри региона: 15-30 мс
	time.Sleep(s.BaseRTT)
	return s.BaseRTT
}

type GlobalGeoRouter struct {
	senders map[Region]*RegionalSender
}

func NewGlobalGeoRouter() *GlobalGeoRouter {
	return &GlobalGeoRouter{
		senders: map[Region]*RegionalSender{
			RegionEU:   {Region: RegionEU, BaseRTT: 20 * time.Millisecond},
			RegionUS:   {Region: RegionUS, BaseRTT: 25 * time.Millisecond},
			RegionAPAC: {Region: RegionAPAC, BaseRTT: 30 * time.Millisecond},
		},
	}
}

// ResolveRegion определяет регион по доменной зоне или явной настройке
func (r *GlobalGeoRouter) ResolveRegion(endpointURL string) Region {
	switch {
	case strings.Contains(endpointURL, ".us") || strings.Contains(endpointURL, "aws-us"):
		return RegionUS
	case strings.Contains(endpointURL, ".sg") || strings.Contains(endpointURL, ".jp") || strings.Contains(endpointURL, "apac"):
		return RegionAPAC
	default:
		return RegionEU // Дефолтный регион
	}
}

func (r *GlobalGeoRouter) RouteAndDeliver(endpointURL string) {
	targetRegion := r.ResolveRegion(endpointURL)
	sender := r.senders[targetRegion]

	start := time.Now()
	latency := sender.Deliver(endpointURL)
	total := time.Since(start)

	fmt.Printf("Цель: %-35s -> Регион отправки: [%-12s] | RTT: %v | Total: %v\n",
		endpointURL, targetRegion, latency, total.Round(time.Millisecond))
}

func main() {
	router := NewGlobalGeoRouter()

	endpoints := []string{
		"https://tokyo-payment.jp/webhook",
		"https://newyork-fintech.us/api/v1/wh",
		"https://berlin-logistics.eu/notifications",
		"https://singapore-gateway.sg/events",
	}

	fmt.Println("=== Маршрутизация вебхуков через геораспределенные региональные сендеры ===")
	for _, ep := range endpoints {
		router.RouteAndDeliver(ep)
	}
}
```

ℹ️ Геораспределенная маршрутизация вебхуков для минимизации сетевого RTT

## Под капотом

В архитектуре Multi-Region Delivery базы данных обычно реплицируются асинхронно между регионами (Cross-Region Replication). Однако при доставке вебхуков строгая синхронизация не требуется: событие сериализуется в домашнем регионе и пересылается через глобальную магистраль (AWS Global Accelerator или выделенный gRPC-туннель) в локальный кэш регионального воркера, откуда выстреливается в локальный интернет клиента.

## Подводные камни

1. **Ротация секретных ключей подписи между регионами:** Если клиент сменил секретный ключ в личном кабинете в регионе EU, региональный сендер в Сингапуре обязан узнать об этом мгновенно. Используйте глобально синхронизируемый распределенный кэш ключей (Redis Enterprise CRDT или etcd).
2. **Соблюдение законов о персональных данных (GDPR / 152-ФЗ):** Передача персональных данных пользователей из EU в регион US без согласия нарушает GDPR. Маршрутизатор обязан учитывать регуляторные ограничения.

## На собеседовании

**Вопрос:** Как организовать отказоустойчивость, если региональный дата-центр `us-east` полностью отключился?

**Ответ:** Применяется **Cross-Region Failover**:
1. Health-check мониторинг (Route53 DNS Failover или Consul) фиксирует недоступность региона `us-east`.
2. Входящие потоки задач региона `us-east` мгновенно перенаправляются в соседний регион `us-west` или `eu-central`.
3. Задержка (RTT) временно вырастает на 70 мс, но ни одно событие не теряется, сохраняя доступность 99.99%.
