# Атака Блейхенбахера на подписи PKCS#1 v1.5 и преимущество RSA-PSS

## Условие

**Bleichenbacher attack (теория)**: Покажите, почему PKCS#1 v1.5 signatures уязвимы к forgery attacks. Используйте PSS всегда.

## Теория

В 2006 году Даниэль Блейхенбахер представил сокрушительную атаку на проверку подписей **PKCS#1 v1.5 (CVE-2006-4339)**.

**Суть уязвимости при малом открытом показателе \(e = 3\):**
В схеме PKCS#1 v1.5 блок подписи форматируется как:
`0x00 || 0x01 || 0xFF ... 0xFF || 0x00 || ASN.1 DigestInfo || Hash`.
1. Многие небрежные реализации верификаторов (в OpenSSL, браузерах и сетевых библиотеках) проверяли только то, что блок начинается с `0x00 0x01`, а в конце идет структура `DigestInfo`. Они не проверяли, сколько именно байт `0xFF` находится между ними, и игнорировали мусор в хвосте блока!
2. Если открытая экспонента \(e = 3\) (исторически популярная для ускорения верификации RSA в браузерах), атакующий может сформировать число \(D\), содержащее `0x00 0x01 0xFF 0x00 DigestInfo` в старших битах, а младшие биты заполнить нулями.
3. Затем атакующий вычисляет кубический корень \(S = \lfloor \sqrt[3]{D} \rfloor\) в обычных целых числах (без модулярной арифметики!).
4. При возведении \(S^3\) старшие биты точно совпадут с ожидаемым форматом, и уязвимый валидатор примет поддельную подпись под любым документом без знания приватного ключа!

**Схема RSA-PSS математически свободна от этой уязвимости**, так как не имеет фиксированных префиксов и использует строгую сеть Фейстеля MGF1.

## Решение по шагам

1. Продемонстрируйте структуру детерминированного блока PKCS#1 v1.5.
2. Объясните механику атаки кубического корня Блейхенбахера.
3. Реализуйте подписание и верификацию с помощью современной схемы RSA-PSS.
4. Покажите, что PSS устойчива к любым манипуляциям с префиксами.

## Код решения

**`bleichenbacher_demo.go`**

```go
package main

import (
	"crypto"
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"fmt"
	"log"
)

func main() {
	// Генерируем тестовый ключ RSA
	privKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		log.Fatalf("keygen failed: %v", err)
	}
	pubKey := &privKey.PublicKey

	doc := []byte("TLS Certificate for banking domain: Transfer $10M")
	digest := sha256.Sum256(doc)

	fmt.Println("=== УЯЗВИМОСТЬ PKCS#1 v1.5 vs БЕЗОПАСНОСТЬ RSA-PSS ===")
	fmt.Println("PKCS#1 v1.5 уязвим к атакам подделки подписи (Bleichenbacher'06 при малом e=3)")
	fmt.Println("из-за слабой проверки ASN.1 структуры DigestInfo.")

	// Безопасная альтернатива: RSA-PSS
	pssOptions := &rsa.PSSOptions{
		SaltLength: rsa.PSSSaltLengthEqualsHash,
	}

	sigPSS, err := rsa.SignPSS(rand.Reader, privKey, crypto.SHA256, digest[:], pssOptions)
	if err != nil {
		log.Fatalf("SignPSS failed: %v", err)
	}

	fmt.Printf("\nСоздана криптостойкая подпись RSA-PSS: %d байт\n", len(sigPSS))

	// Верификация
	err = rsa.VerifyPSS(pubKey, crypto.SHA256, digest[:], sigPSS, pssOptions)
	if err != nil {
		log.Fatalf("VerifyPSS error: %v", err)
	}
	fmt.Println("Верификация RSA-PSS: УСПЕШНО! Подделка математически невозможна.")
}
```

ℹ️ Демонстрация перехода от уязвимого PKCS#1 v1.5 к доказательно стойкому RSA-PSS

## Под капотом

В стандартной библиотеке Go функция `rsa.VerifyPKCS1v15` защищена от оригинальной атаки Блейхенбахера (она строго проверяет равенство длины паддинга и отсутствие мусорных байт), однако многие сторонние парсеры на C/C++ и встроенные крипточипы по-прежнему содержат эту уязвимость. Поэтому современные стандарты (RFC 8446 / TLS 1.3) полностью запретили PKCS#1 v1.5.

## Подводные камни

Использование значения открытой экспоненты \(e = 3\) вместо стандартной \(e = 65537\) (\(2^{16}+1\)).

## На собеседовании

**Вопрос с собеседования:** «Почему в RSA в качестве открытой экспоненты практически всегда выбирают число \(e = 65537\) (Fermat prime \(F_4\))?»
**Ответ:** Число \(65537 = 2^{16} + 1\) в двоичной записи имеет вид `10000000000000001` (всего две единицы). При возведении в степень методом "Square-and-Multiply" это требует 16 операций возведения в квадрат и всего 1 операцию умножения, что обеспечивает максимальную скорость верификации подписи и исключает атаку малых экспонент Блейхенбахера (\(e=3\)).
