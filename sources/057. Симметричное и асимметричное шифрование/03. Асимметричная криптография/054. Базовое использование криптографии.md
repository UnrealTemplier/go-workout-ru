# Базовое использование криптографии на эллиптических кривых: ECDSA P-256

## Условие

**ECDSA базовое использование**: Сгенерируйте пару ключей на кривой P-256 через `crypto/ecdsa`. P-256 в ~10 раз быстрее RSA-2048 для signatures.

## Теория

**ECDSA (Elliptic Curve Digital Signature Algorithm)** — стандарт цифровой подписи (FIPS 186-4 / ANSI X9.62) на базе алгебраической геометрии эллиптических кривых над конечными полями:

**Почему ECDSA P-256 вытеснил RSA:**
1. **Размер ключа**: 256-битный ключ эллиптической кривой обеспечивает криптостойкость 128 бит — ровно столько же, сколько огромный 2048-битный ключ RSA!
2. **Скорость**: генерация подписи ECDSA P-256 выполняется в 10–20 раз быстрее RSA-2048, существенно экономя процессорные мощности серверов при установке TLS-соединений.
3. **Размер подписи**: подпись представляет собой пару чисел \((r, s)\) по 32 байта каждое (суммарно всего 64 байта в бинарном виде).

В стандартной библиотеке Go пакет `crypto/ecdsa` поддерживает кривую `elliptic.P256()`, оптимизированную на ассемблере для x86_64 и ARM64.

## Решение по шагам

1. Сгенерируйте пару ключей `privKey, err := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)`.
2. Вычислите SHA-256 хеш документа.
3. Подпишите хеш через `ecdsa.SignASN1(rand.Reader, privKey, hash[:])`.
4. Проверьте подпись через `ecdsa.VerifyASN1(&privKey.PublicKey, hash[:], sig)`.
5. Сравните размеры ключей с RSA.

## Код решения

**`ecdsa_demo.go`**

```go
package main

import (
	"crypto/ecdsa"
	"crypto/elliptic"
	"crypto/rand"
	"crypto/sha256"
	"fmt"
	"log"
)

func main() {
	// Генерация ключевой пары на кривой NIST P-256
	privKey, err := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	if err != nil {
		log.Fatalf("ECDSA keygen error: %v", err)
	}
	pubKey := &privKey.PublicKey

	fmt.Println("=== ЭЛЕКТРОННАЯ ПОДПИСЬ ECDSA (КРИВАЯ P-256) ===")
	fmt.Printf("Размер приватного ключа: %d бит (32 байта скаляр D)\n", privKey.D.BitLen())
	fmt.Printf("Публичный ключ: точка X (%d бит), Y (%d бит)\n", pubKey.X.BitLen(), pubKey.Y.BitLen())

	document := []byte("TLS Handshake Authentication: Server Name Indication api.ozon.ru")
	hash := sha256.Sum256(document)

	// Подписание: в Go 1.15+ функция SignASN1 кодирует подпись (r, s) в стандартный DER ASN.1
	signature, err := ecdsa.SignASN1(rand.Reader, privKey, hash[:])
	if err != nil {
		log.Fatalf("Sign error: %v", err)
	}

	fmt.Printf("Размер подписи DER ASN.1: %d байт (в сравнении с 256 байтами RSA-2048)\n", len(signature))

	// Верификация
	isValid := ecdsa.VerifyASN1(pubKey, hash[:], signature)
	fmt.Printf("Подпись валидна? %v\n", isValid)

	// Проверка устойчивости к подмене
	tamperedHash := sha256.Sum256([]byte("Tampered Document"))
	isTamperedValid := ecdsa.VerifyASN1(pubKey, tamperedHash[:], signature)
	fmt.Printf("Поддельный хеш валиден? %v (Надежно отброшено)\n", isTamperedValid)
}
```

## Под капотом

Внутри `elliptic.P256()` в Go операции сложения и удвоения точек реализованы на чистом ассемблере с использованием инструкций `ADCX`/`ADOX` (Multi-Precision Add-Carry). Координаты точек вычисляются в проективном пространстве Якоби (Jacobian coordinates), исключая модульное деление в поле до финального шага верификации.

## Подводные камни

Использование устаревшего метода `ecdsa.Sign`, возвращающего два отдельных `*big.Int` (r, s), вместо `ecdsa.SignASN1`: это приводит к проблемам совместимости с OpenSSL и сертификатами X.509.

## На собеседовании

**Вопрос с собеседования:** «Почему при генерации подписи в классическом ECDSA сбой генератора случайных чисел (повтор числа k) приводит к мгновенной компрометации приватного ключа?»
**Ответ:** При подписании двух сообщений \(m_1\) и \(m_2\) одним эфемерным числом \(k\) вычисляются подписи:
\(s_1 = k^{-1}(z_1 + r \cdot d) \pmod n\)
\(s_2 = k^{-1}(z_2 + r \cdot d) \pmod n\).
Вычитая одно уравнение из другого, атакующий моментально находит \(k = \frac{z_1 - z_2}{s_1 - s_2} \pmod n\), а затем вычисляет приватный ключ \(d = \frac{s_1 \cdot k - z_1}{r} \pmod n\). Именно так хакеры из fail0verflow взломали мастер-ключ Sony PS3 в 2010 году.
