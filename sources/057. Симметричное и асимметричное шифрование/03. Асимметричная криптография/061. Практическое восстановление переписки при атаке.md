# Практическое восстановление переписки при атаке Two-Time Pad (CTR Nonce Reuse)

## Условие

**[Каверзный кейс — Reuse of Nonce]**: Зашифруй два разных сообщения одним ключом и *одним nonce*. Реализуй XOR двух шифртекстов. Покажи, что результат равен XOR открытых текстов (катастрофическое нарушение конфиденциальности).

## Теория

Классическая криптографическая уязвимость **Two-Time Pad**:
Если шифрование выполняется операцией \(C = P \oplus K_{stream}\), то для двух сообщений на одинаковой гамме:
\(C_1 \oplus C_2 = (P_1 \oplus K_{stream}) \oplus (P_2 \oplus K_{stream}) = P_1 \oplus P_2\).

**Почему это катастрофа в промышленном коде:**
В протоколах передачи данных (HTTP, JSON API, gRPC) первые байты сообщений часто стандартны:
`{"status":"ok","data":` или `GET /api/v1/users/`.
Если атакующий знает хотя бы часть текста одного сообщения (\(P_1\)), он мгновенно вычисляет текст второго сообщения:
\(P_2 = (C_1 \oplus C_2) \oplus P_1\).
Знание ключа шифрования для этого **вообще не требуется**!

## Решение по шагам

1. Создайте ключ AES-256 и единый 16-байтный IV.
2. Зашифруйте сообщение 1: `"CONFIDENTIAL_TOKEN_SECRET_A"`.
3. Зашифруйте сообщение 2: `"FINANCIAL_REPORT_BUDGET_2026"`.
4. Вычислите побайтовый XOR двух шифротекстов.
5. Покажите, что `xorCipher == xorPlain`.
6. Восстановите сообщение 2, используя только шифротексты и известную строку 1.

## Код решения

**`two_time_pad_case.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
)

func encryptCTR(plaintext, key, iv []byte) []byte {
	block, _ := aes.NewCipher(key)
	stream := cipher.NewCTR(block, iv)
	ciphertext := make([]byte, len(plaintext))
	stream.XORKeyStream(ciphertext, plaintext)
	return ciphertext
}

func main() {
	key := make([]byte, 32)
	_ = rand.Read(key)

	// ОДИН И ТОТ ЖЕ IV/NONCE
	sharedIV := make([]byte, 16)
	_ = rand.Read(sharedIV)

	msg1 := []byte("HTTP/1.1 200 OK\r\nSecret-Token: AliceKey_99")
	msg2 := []byte("HTTP/1.1 200 OK\r\nSecret-Token: BobAdmin_42")

	c1 := encryptCTR(msg1, key, sharedIV)
	c2 := encryptCTR(msg2, key, sharedIV)

	fmt.Println("=== КАВЕРЗНЫЙ КЕЙС: NONCE REUSE В ПОТОКОВОМ ШИФРЕ ===")
	fmt.Printf("Размер сообщения 1: %d байт\n", len(c1))
	fmt.Printf("Размер сообщения 2: %d байт\n", len(c2))

	// Атакующий перехватил c1 и c2 в сети
	xorCipher := make([]byte, len(c1))
	for i := range c1 {
		xorCipher[i] = c1[i] ^ c2[i]
	}

	// Предположим, атакующий знает структуру HTTP ответа первого сервиса
	recoveredMsg2 := make([]byte, len(c1))
	for i := range xorCipher {
		recoveredMsg2[i] = xorCipher[i] ^ msg1[i]
	}

	fmt.Printf("\nПерехваченный открытый текст второго сообщения БЕЗ ЗНАНИЯ КЛЮЧА:\n'%s'\n",
		string(recoveredMsg2))
}
```

## Под капотом

В потоковом режиме CTR операция шифрования тождественна One-Time Pad с детерминированным генератором гаммы. Закон сохранения информации показывает, что сложение \(C_1 \oplus C_2\) полностью исключает псевдослучайную составляющую, оставляя аналитику чистый сигнал разности сообщений.

## Подводные камни

Использование детерминированного счетчика nonce, сбрасывающегося при каждом рестарте контейнера в Kubernetes.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить повтор nonce в распределенной микросервисной системе с 500 подами, шифрующими данные одним мастер-ключом?»
**Ответ:** Есть три надежных подхода:
1. **Разбиение пространства nonce (Partitioned Nonce)**: первые 4 байта nonce содержат уникальный `PodID`, следующие 8 байт — локальный монотонный счетчик атомика. Коллизии между подами математически невозможны.
2. **Переход на шифры с расширенным 192-битным nonce (XChaCha20-Poly1305)**: вероятность случайной коллизии при 192 битах ничтожна даже при триллионах сообщений.
3. **Использование Envelope Encryption**: каждый под генерирует свой одноразовый ключ DEK, поэтому коллизии nonce на разных ключах безопасны.
