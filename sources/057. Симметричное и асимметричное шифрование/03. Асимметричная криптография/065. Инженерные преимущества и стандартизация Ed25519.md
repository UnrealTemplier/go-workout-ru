# Инженерные преимущества и стандартизация Ed25519 в современном Go

## Условие

**Ed25519 signatures**: Используйте `crypto/ed25519` — современные signatures, быстрее ECDSA, без проблем с nonce, constant-time. **Предпочитайте Ed25519 для signatures в новых проектах.**

## Теория

В современной криптографической инженерии пакет **`crypto/ed25519`** является главным стандартом цифровых подписей:

**Архитектурные преимущества Ed25519:**
1. **Constant-Time по умолчанию**: математические операции над точками кривой Эдвардса не содержат особых точек (нет точек исключений, точек перегиба или точек на бесконечности). Все формулы сложения являются полными (Complete Addition Formulas), исключая утечки по времени.
2. **Простота и безопасность API**:
   - `ed25519.Sign(privKey, message)` не принимает параметров хэшей или опций.
   - Невозможно ошибиться с выбором кривой или алгоритма хеширования.
3. **Минимальный сетевой оверхед**:
   - Размер публичного ключа: 32 байта.
   - Размер подписи: 64 байта.
4. **Стандарт де-факто**: используется в OpenSSH (начиная с OpenSSH 6.5), протоколе Git (подписание коммитов `git tag -s`), защищенном хранилище токенов PASETO и протоколе Signal.

## Решение по шагам

1. Создайте ключевую пару через `ed25519.GenerateKey(rand.Reader)`.
2. Подпишите полезную нагрузку.
3. Сохраните публичный ключ в сжатом бинарном виде (32 байта).
4. Проверьте подпись через `ed25519.Verify`.
5. Сравните лаконичность кода с громоздкими вызовами RSA-PSS и ECDSA.

## Код решения

**`ed25519_standard.go`**

```go
package main

import (
	"crypto/ed25519"
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"log"
)

// SignBinaryArtifact формирует цифровую подпись релиза
func SignBinaryArtifact(artifactPayload []byte, privKey ed25519.PrivateKey) []byte {
	return ed25519.Sign(privKey, artifactPayload)
}

// VerifyBinaryArtifact проверяет подлинность бинарного релиза
func VerifyBinaryArtifact(artifactPayload, sig []byte, pubKey ed25519.PublicKey) bool {
	return ed25519.Verify(pubKey, artifactPayload, sig)
}

func main() {
	pub, priv, err := ed25519.GenerateKey(rand.Reader)
	if err != nil {
		log.Fatalf("keygen failed: %v", err)
	}

	buildArtifact := []byte("Docker Image Digest: sha256:4f18e9a2c019df... tag=v2.10.0-production")

	sig := SignBinaryArtifact(buildArtifact, priv)

	fmt.Println("=== ЭТАЛОННАЯ ЦИФРОВАЯ ПОДПИСЬ ED25519 ===")
	fmt.Printf("Публичный ключ (32B): %s\n", hex.EncodeToString(pub))
	fmt.Printf("Подпись (64B):        %s\n", hex.EncodeToString(sig))

	isVerified := VerifyBinaryArtifact(buildArtifact, sig, pub)
	fmt.Printf("Результат проверки в CI/CD: %v (Release Verified)\n", isVerified)
}
```

## Под капотом

В Go 1.20+ реализация Ed25519 полностью переписана на базе специализированного пакета `crypto/internal/edwards25519`, где полевые операции сгруппированы в 5 слов по 51 биту (Radix \(2^{51}\)), что исключает промежуточные переполнения 64-битных регистров процессора и обеспечивает максимальную производительность.

## Подводные камни

Использование приватного ключа Ed25519 для операции обмена ключами Диффи-Хеллмана напрямую: для ECDH используется кривая Монтгомери X25519 (`crypto/ecdh`). Для конвертации ключей требуется изоморфизм Бирча.

## На собеседовании

**Вопрос с собеседования:** «Почему в новых стандартах аутентификации (Cosign / Sigstore для проверки контейнеров Kubernetes) используют ключи Ed25519 или ECDSA P-256 вместо RSA-4096?»
**Ответ:** Из-за размера и скорости. В микросервисных архитектурах контейнеры скачиваются тысячами подов одновременно. Публичный ключ Ed25519 занимает 32 байта, а подпись — 64 байта, что легко помещается в OCI-аннотации Docker образов. Верификация RSA-4096 требует миллисекунд интенсивных модульных вычислений, создавая CPU-спайки на узлах Kubernetes, в то время как Ed25519 валидируется за микросекунды.
