# Цифровые подписи RSA: вероятностный PSS против устаревшего PKCS#1 v1.5

## Условие

**RSA-подписи: PSS vs PKCS#1 v1.5.**: Подпишите хеш SHA-256 через `rsa.SignPSS` и `rsa.SignPKCS1v15`. Проверьте обе. Объясните, почему PSS (Probabilistic Signature Scheme) рекомендуется для новых систем.

## Теория

Электронная цифровая подпись (Digital Signature) обеспечивает:
1. **Аутентичность автора (Signer Authentication)**.
2. **Неотказуемость (Non-repudiation)**: автор не может заявить, что подпись сгенерирована кем-то другим.
3. **Целостность документа (Integrity)**.

**Сравнение схем подписи RSA:**
1. **PKCS#1 v1.5 (`rsa.SignPKCS1v15`)**: детерминированная схема подписи.
   - Один и тот же документ всегда дает абсолютно одинаковую подпись.
   - Уязвима к атакам на парсеры ASN.1 структуры DigestInfo (атака Блейхенбахера на подписи RSA, уязвимость CVE-2006-4339), когда атакующий генерирует подписи с малым открытым показателем \(e=3\) из-за неполной проверки паддинга в парсерах X.509.
2. **RSA-PSS (`rsa.SignPSS` — Probabilistic Signature Scheme)**:
   - Стандарт PKCS#1 v2.1 / RFC 8017.
   - Вероятностная схема: при каждой подписи генерируется случайная криптографическая соль (`salt`).
   - Подписание одного и того же файла 10 раз даст 10 совершенно разных подписей!
   - Имеет строгое математическое доказательство безопасности в модели случайного оракула (Random Oracle Model). Рекомендована NIST, FIPS и BSI для всех новых систем.

## Решение по шагам

1. Сгенерируйте пару ключей RSA-2048.
2. Вычислите SHA-256 хеш исходного документа.
3. Подпишите хеш через `rsa.SignPKCS1v15(rand.Reader, privKey, crypto.SHA256, hashed)`.
4. Подпишите тот же хеш через `rsa.SignPSS(rand.Reader, privKey, crypto.SHA256, hashed, &rsa.PSSOptions{SaltLength: rsa.PSSSaltLengthEqualsHash})`.
5. Проверьте подписи через `rsa.VerifyPKCS1v15` и `rsa.VerifyPSS`.
6. Покажите, что повторный вызов PSS дает новую подпись, а PKCS#1 v1.5 — идентичную.

## Код решения

**`signatures_comparison.go`**

```go
package main

import (
	"bytes"
	"crypto"
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"fmt"
	"log"
)

func main() {
	privKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		log.Fatalf("key gen error: %v", err)
	}
	pubKey := &privKey.PublicKey

	document := []byte("Executive Decision #409: Approve release of v2.5.0 to production")
	hasher := sha256.New()
	hasher.Write(document)
	hashed := hasher.Sum(nil)

	// 1. Устаревшая подпись PKCS#1 v1.5
	sigV15_1, _ := rsa.SignPKCS1v15(rand.Reader, privKey, crypto.SHA256, hashed)
	sigV15_2, _ := rsa.SignPKCS1v15(rand.Reader, privKey, crypto.SHA256, hashed)

	fmt.Println("=== PKCS#1 v1.5 ДЕТЕРМИНИРОВАННАЯ ПОДПИСЬ ===")
	fmt.Printf("Подпись 1 равна Подписи 2? %v (Всегда детерминированно!)\n", bytes.Equal(sigV15_1, sigV15_2))

	err = rsa.VerifyPKCS1v15(pubKey, crypto.SHA256, hashed, sigV15_1)
	if err != nil {
		log.Fatalf("VerifyPKCS1v15 error: %v", err)
	}
	fmt.Println("Верификация PKCS#1 v1.5 успешна!")

	// 2. Современная вероятностная подпись RSA-PSS
	pssOpts := &rsa.PSSOptions{
		SaltLength: rsa.PSSSaltLengthEqualsHash, // Длина соли равна длине хеша SHA-256 (32 байта)
	}

	sigPSS_1, _ := rsa.SignPSS(rand.Reader, privKey, crypto.SHA256, hashed, pssOpts)
	sigPSS_2, _ := rsa.SignPSS(rand.Reader, privKey, crypto.SHA256, hashed, pssOpts)

	fmt.Println("\n=== RSA-PSS ВЕРОЯТНОСТНАЯ ПОДПИСЬ ===")
	fmt.Printf("Подпись 1 равна Подписи 2? %v (Каждая подпись уникальна!)\n", bytes.Equal(sigPSS_1, sigPSS_2))

	err = rsa.VerifyPSS(pubKey, crypto.SHA256, hashed, sigPSS_1, pssOpts)
	if err != nil {
		log.Fatalf("VerifyPSS error: %v", err)
	}
	fmt.Println("Верификация RSA-PSS успешна!")
}
```

## Под капотом

В схеме PSS входное сообщение дополняется случайной солью `salt`, хэшируется и кодируется через функцию маскирования MGF1.
При верификации `rsa.VerifyPSS` публичный ключ извлекает маскированное представление, восстанавливает соль `salt` и проверяет точное совпадение хеша. Это исключает любые атаки изменения формата ASN.1.

## Подводные камни

1. Передача открытого текста документа вместо его криптографического хеша в функции `rsa.SignPSS`: функция ожидает уже посчитанный хеш фиксированной длины (например 32 байта для SHA-256).
2. Несогласованная длина соли `SaltLength` между подписывающей стороной и проверяющей стороной.

## На собеседовании

**Вопрос с собеседования:** «Почему в стандарте TLS 1.3 для подписей RSA разрешено использовать только RSA-PSS (схемы `rsa_pss_rsae_sha256`), а PKCS#1 v1.5 запрещен?»
**Ответ:** В PKCS#1 v1.5 исторически регулярно находили уязвимости реализации в криптографических библиотеках (Bleichenbacher'06, Berglund'14). Детерминированный паддинг PKCS#1 v1.5 требует парсинга вложенных структур ASN.1, где ошибки валидации лидирующих нулей приводили к подделке подписей. PSS математически доказан на уровне редукции к стойкости RSA и свободен от ASN.1 парсинга внутри блока подписи.
