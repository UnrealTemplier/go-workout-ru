# Проектирование безопасного формата API-ключей (Stripe/GitHub Style)

## Условие

**API key format**: Реализуйте генерацию API ключей в формате `prefix_random_checksum` (например, `sk_live_3xK9mN_abc`). Префикс помогает в логах, чексумма — детектирует опечатки.

## Теория

В ведущих API-платформах (Stripe, GitHub, OpenAI, Slack) API-ключи не являются просто случайными hex-строками. Они структурированы: `[Префикс]_[СлучайнаяЧасть]_[КонтрольнаяСумма]`:
1. **Префикс (`prefix`)**: позволяет человеку и секрет-сканерам (GitHub Secret Scanning, Trufflehog) мгновенно определить тип и скоуп ключа (`sk_live_` — боевой секретный ключ, `pk_test_` — тестовый публичный ключ).
2. **Случайная энтропия (`random`)**: не менее 160-256 бит криптографической случайности из `crypto/rand`, закодированных в Base62/Base58 (без неоднозначных символов `0/O`, `1/l`).
3. **Контрольная сумма (`checksum`)**: полиномиальный хеш (например, CRC32-IEEE или быстрый HMAC-префикс), закодированный в конце ключа.
Благодаря контрольной сумме бэкенд мгновенно отсекает опечатки клиентов со статусом 400 Bad Request еще до обращения в базу данных или кэш Redis, защищаясь от лишней нагрузки.

## Решение по шагам

1. Определите префикс окружения (`sk_live_`, `sk_test_`).
2. Сгенерируйте 24 или 32 байта случайных данных через `crypto/rand`.
3. Закодируйте случайную часть в Base62 (алфавит `[0-9a-zA-Z]`).
4. Посчитайте CRC32 от полученной случайной строки.
5. Преобразуйте контрольную сумму в Base62 строку фиксированной длины (например, 6 символов).
6. Реализуйте функцию верификации формата и контрольной суммы ключа.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"errors"
	"fmt"
	"hash/crc32"
	"math/big"
	"strings"
)

const base62Chars = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

// toBase62 кодирует срез байт в Base62 строку
func toBase62(data []byte) string {
	var num big.Int
	num.SetBytes(data)

	var res []byte
	base := big.NewInt(62)
	zero := big.NewInt(0)
	mod := new(big.Int)

	for num.Cmp(zero) > 0 {
		num.DivMod(&num, base, mod)
		res = append(res, base62Chars[mod.Int64()])
	}

	// Разворачиваем срез
	for i, j := 0, len(res)-1; i < j; i, j = i+1, j-1 {
		res[i], res[j] = res[j], res[i]
	}
	return string(res)
}

// GenerateAPIKey генерирует ключ формата: prefix_entropy_checksum
func GenerateAPIKey(prefix string, entropyBytes int) (string, error) {
	raw := make([]byte, entropyBytes)
	if _, err := rand.Read(raw); err != nil {
		return "", fmt.Errorf("failed to generate entropy: %w", err)
	}

	entropyStr := toBase62(raw)
	// Дополняем при необходимости
	for len(entropyStr) < 32 {
		entropyStr = "0" + entropyStr
	}

	// Вычисляем CRC32 от энтропийной части
	checksum := crc32.ChecksumIEEE([]byte(entropyStr))
	checksumBytes := []byte{
		byte(checksum >> 24),
		byte(checksum >> 16),
		byte(checksum >> 8),
		byte(checksum),
	}
	checksumStr := toBase62(checksumBytes)
	for len(checksumStr) < 6 {
		checksumStr = "0" + checksumStr
	}

	return fmt.Sprintf("%s_%s_%s", prefix, entropyStr, checksumStr), nil
}

// ValidateAPIKeyStructure проверяет корректность префикса и контрольной суммы
func ValidateAPIKeyStructure(key string, expectedPrefix string) error {
	parts := strings.Split(key, "_")
	if len(parts) != 3 {
		return errors.New("invalid API key structure: expected prefix_entropy_checksum")
	}

	prefix, entropyStr, checksumStr := parts[0], parts[1], parts[2]
	if prefix != expectedPrefix {
		return fmt.Errorf("prefix mismatch: got %s, expected %s", prefix, expectedPrefix)
	}

	// Проверяем контрольную сумму
	expectedChecksum := crc32.ChecksumIEEE([]byte(entropyStr))
	expectedBytes := []byte{
		byte(expectedChecksum >> 24),
		byte(expectedChecksum >> 16),
		byte(expectedChecksum >> 8),
		byte(expectedChecksum),
	}
	calculatedChecksumStr := toBase62(expectedBytes)
	for len(calculatedChecksumStr) < 6 {
		calculatedChecksumStr = "0" + calculatedChecksumStr
	}

	if checksumStr != calculatedChecksumStr {
		return errors.New("checksum validation failed: key is corrupted or typo present")
	}

	return nil
}

func main() {
	apiKey, err := GenerateAPIKey("sk_live", 24)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Сгенерированный API-ключ: %s\n", apiKey)

	// Проверка валидного ключа
	if err := ValidateAPIKeyStructure(apiKey, "sk_live"); err != nil {
		fmt.Printf("Ошибка валидации: %v\n", err)
	} else {
		fmt.Println("Ключ успешно прошел проверку структуры и контрольной суммы!")
	}

	// Проверка поврежденного ключа с опечаткой
	corruptedKey := apiKey[:len(apiKey)-2] + "X" + apiKey[len(apiKey)-1:]
	if err := ValidateAPIKeyStructure(corruptedKey, "sk_live"); err != nil {
		fmt.Printf("Корректно обнаружена ошибка в ключе: %v\n", err)
	}
}
```

## Под капотом

Внутренний формат Stripe и GitHub использует CRC32 или модифицированный Adler-32 с Base62 кодированием. Преимущество Base62 перед Hex заключается в том, что на 1 байт приходится 1.33 символа вместо 2 символов в Hex, что делает ключ компактнее при той же криптостойкости (256 бит = 43 символа Base62 против 64 символов Hex).
При сохранении в базу данных API-ключ никогда не хранится в открытом виде: сохраняется префикс и хеш SHA-256 от всего ключа.

## Подводные камни

1. Хранение исходных API-ключей в базе данных в plaintext: при SQL-инъекции или утечке бэкапа все ключи мгновенно компрометируются.
2. Проверка контрольной суммы как доказательства подлинности: контрольная сумма предназначена *только* для фильтрации опечаток пользователей на сетевом шлюзе (API Gateway). Доступ к ресурсам дается только после поиска SHA-256 хеша в БД.

## На собеседовании

**Вопрос с собеседования:** «Зачем сервис API Gateway должен валидировать контрольную сумму API-ключа до похода в хранилище (Redis/Postgres)?»
**Ответ:** Это фундаментальный паттерн защиты от DoS-атак на базу данных и шину кэширования. Если ботнет отправляет миллионы случайных ключей, проверка CRC32/HMAC выполняется за ~10 наносекунд в оперативной памяти шлюза в userspace без единого обращения к сети, защищая сервисы аутентификации от деградации.
