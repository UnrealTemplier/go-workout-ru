# Сравнение RSA схем: уязвимости PKCS#1 v1.5 и стандарт OAEP

## Условие

**RSA: генерация и OAEP.**: Сгенерируйте пару RSA 2048/4096 бит. Зашифруйте сообщение через `rsa.EncryptOAEP`, расшифруйте. Объясните, почему PKCS#1 v1.5 устарел (Bleichenbacher attacks) и почему OAEP — стандарт.

## Теория

Схема шифрования **PKCS#1 v1.5** была предложена в начале 1990-х годов и форматировала блок как: `0x00 || 0x02 || RandomPadding || 0x00 || Data`.

В 1998 году швейцарский криптограф Даниэль Блейхенбахер (Daniel Bleichenbacher) опубликовал сокрушительную атаку **Million Message Attack**:
1. Атакующий отправляет серверу случайно модифицированные шифротексты \(c' = c \cdot s^e \pmod n\).
2. Если расшифрованный блок начинается с `0x00 0x02`, сервер выдает ошибку одного типа (например, "Bad Application Data"), а если паддинг нарушен — другого типа ("Decryption Error") или возвращает ответ с разницей во времени в несколько микросекунд.
3. Сервер выступает в роли оракула соответствия паддинга (Padding Oracle).
4. Методом адаптивного сужения интервалов атакующий полностью восстанавливает открытый текст (например, pre-master secret в TLS) примерно за \(10^6\) запросов без знания приватного ключа!

**Почему OAEP неуязвим:**
В OAEP открытый текст перемешивается со случайным сидом через двустороннюю сеть Фейстеля на базе хеш-функций (MGF1). Любое изменение даже одного бита в шифротексте приводит к лавинному эффекту: на этапе распаковки получается равномерно распределенный мусор, и проверка целостности отвергает сообщение за строго константное время.

## Решение по шагам

1. Сгенерируйте ключ RSA-2048 через `rsa.GenerateKey`.
2. Зашифруйте тестовую строку алгоритмом `rsa.EncryptOAEP` с SHA-256.
3. Продемонстрируйте корректное дешифрование.
4. Сымитируйте атаку Блейхенбахера: модифицируйте шифротекст и покажите, что `rsa.DecryptOAEP` защищает систему, возвращая `crypto/rsa: decryption error` в строго константном времени благодаря встроенному blind masking.

## Код решения

**`oaep_vs_pkcs1.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"fmt"
	"log"
)

func main() {
	// Генерация 2048-битного RSA ключа
	privKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		log.Fatalf("key generation error: %v", err)
	}
	pubKey := &privKey.PublicKey

	secretData := []byte("SessionToken:SecureBankTransfer_Auth2026")

	// 1. Стандартное шифрование RSA-OAEP
	ciphertext, err := rsa.EncryptOAEP(sha256.New(), rand.Reader, pubKey, secretData, nil)
	if err != nil {
		log.Fatalf("encryption error: %v", err)
	}
	fmt.Printf("Шифротекст OAEP создан: %d байт (2048 бит)\n", len(ciphertext))

	// 2. Успешная дешифрация
	plaintext, err := rsa.DecryptOAEP(sha256.New(), rand.Reader, privKey, ciphertext, nil)
	if err != nil {
		log.Fatalf("decryption error: %v", err)
	}
	fmt.Printf("Успешно расшифровано: %s\n", string(plaintext))

	// 3. Демонстрация защиты от атаки Блейхенбахера:
	// Повреждаем байт шифротекста
	corrupted := make([]byte, len(ciphertext))
	copy(corrupted, ciphertext)
	corrupted[10] ^= 0xFF

	_, err = rsa.DecryptOAEP(sha256.New(), rand.Reader, privKey, corrupted, nil)
	if err != nil {
		fmt.Printf("Отказ дешифрования поврежденного блока: %v\n", err)
		fmt.Println("Защита OAEP сработала: оракул паддинга устранен!")
	}
}
```

## Под капотом

В исходном коде Go (`crypto/rsa/pkcs1v15.go` и `oaep.go`) дешифрование OAEP защищено на уровне константного времени: проверка хешей и паддинга не использует условных переходов, вычисляясь через побитовые маски в `subtle.ConstantTimeByteEq`. Даже при несовпадении контрольных сумм ошибка `ErrDecryption` возвращается по единому тайминг-пути.

## Подводные камни

1. Использование одной и той же ключевой пары RSA и для шифрования (OAEP), и для цифровой подписи (PSS): это грубейшее нарушение принципа разделения криптографических контекстов. Для шифрования и подписи должны быть разные ключи.
2. Использование пустого хэша или MD5/SHA-1 в OAEP.

## На собеседовании

**Вопрос с собеседования:** «Почему в TLS 1.3 полностью вырезали обмен ключами через RSA (RSA Key Exchange), оставив RSA только для цифровых подписей сертификатов?»
**Ответ:** Во-первых, классический RSA Key Exchange не обеспечивает свойства **Forward Secrecy (PFS)**: если злоумышленник запишет весь зашифрованный трафик датацентра сегодня, а через 5 лет скомпрометирует приватный ключ сервера, он сможет задним числом расшифровать абсолютно все записанные сессии. Во-вторых, RSA-шифрование страдало от постоянных вариаций атак Блейхенбахера (ROBOT attack в 2017 году). В TLS 1.3 обмен ключами выполняется исключительно через эфемерные эллиптические кривые (ECDHE).
