# AES-GCM с дополнительными аутентифицированными данными (AAD)

## Условие

**AES-GCM с AAD (Associated Data).**: Зашифруйте payload, передав в `Seal` AAD — например, `user_id:123`. Покажите, что изменение AAD при расшифровке (`user_id:999`) вызывает ошибку. Объясните, зачем нужен AAD в API-токенах и TLS-записях.

## Теория

В системах хранения данных и API-токенах часто требуется защитить метаданные от подделки, не зашифровывая их (например, чтобы маршрутизатор или шлюз базы данных мог прочитать ID пользователя без знания мастер-ключа шифрования).

Для этого концепция **AEAD (Authenticated Encryption with Associated Data)** предоставляет механизм **AAD (Additional Authenticated Data)**:
1. **Plaintext** — шифруется и аутентифицируется.
2. **AAD** — передается в открытом виде, **не шифруется**, но **участвует в расчете тега аутентификации GHASH**.
Если злоумышленник попытается подменить AAD (например, изменить `user_id:123` на привилегированного `user_id:1`), тег аутентификации не сойдется, и метод `gcm.Open` отвергнет сообщение.

**Где используется AAD:**
- В **TLS 1.3**: заголовки сетевых записей (тип протокола, длина, номер версии) передаются как AAD.
- В **JWT/PASETO**: незашифрованные заголовки токена (алгоритм, kid ключа) связываются криптографически с полезной нагрузкой.
- В **мультитенантных БД**: привязка зашифрованных полей к `tenant_id` или `row_id`, что предотвращает атаку переноса зашифрованных данных одного клиента в запись другого клиента (Ciphertext Relocation Attack).

## Решение по шагам

1. Инициализируйте AES-GCM шифр с 256-битным ключом.
2. Задайте `aad := []byte("tenant_id:ozon-global;user_id:4581")`.
3. Передайте `aad` четвертым аргументом в `gcm.Seal(nonce, nonce, plaintext, aad)`.
4. Попробуйте расшифровать данные с исходным `aad` — убедитесь в успехе.
5. Попробуйте расшифровать данные с поддельным `tamperedAAD := []byte("tenant_id:ozon-global;user_id:1")` — убедитесь, что `gcm.Open` возвращает ошибку аутентификации.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
)

func main() {
	key := make([]byte, 32)
	if _, err := rand.Read(key); err != nil {
		panic(err)
	}

	block, err := aes.NewCipher(key)
	if err != nil {
		panic(err)
	}

	gcm, err := cipher.NewGCM(block)
	if err != nil {
		panic(err)
	}

	nonce := make([]byte, gcm.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		panic(err)
	}

	payload := []byte("User bank balance: 1,500,000 RUB")
	validAAD := []byte("account_id:ACC-998822;client_id:USR-123")

	// Шифруем данные, привязывая их к validAAD
	ciphertext := gcm.Seal(nil, nonce, payload, validAAD)
	fmt.Printf("Шифротекст успешно сформирован с AAD (%s)\n", string(validAAD))

	// 1. Успешная дешифрация с валидным AAD
	decrypted, err := gcm.Open(nil, nonce, ciphertext, validAAD)
	if err != nil {
		fmt.Printf("Ошибка дешифрования: %v\n", err)
	} else {
		fmt.Printf("Успешно расшифровано: %s\n", string(decrypted))
	}

	// 2. Попытка подмены метаданных AAD (атака смены владельца счета)
	maliciousAAD := []byte("account_id:ACC-998822;client_id:USR-999")
	_, err = gcm.Open(nil, nonce, ciphertext, maliciousAAD)
	if err != nil {
		fmt.Printf("Атака успешно заблокирована! Ошибка аутентификации: %v\n", err)
	} else {
		fmt.Println("УЯЗВИМОСТЬ: поддельный AAD был принят!")
	}
}
```

ℹ️ Криптографическая привязка данных к контексту через AAD

**`Терминал`**

```bash
go run main.go
# Шифротекст успешно сформирован с AAD (account_id:ACC-998822;client_id:USR-123)
# Успешно расшифровано: User bank balance: 1,500,000 RUB
# Атака успешно заблокирована! Ошибка аутентификации: cipher: message authentication failed
```

## Под капотом

В алгоритме GCM блоки AAD разбиваются на 128-битные сегменты и подаются на вход функции GHASH до начала обработки блоков шифротекста.
В самом конце вычисляется итоговый хеш от объединенных блоков: \(GHASH(AAD \parallel C \parallel len(AAD) \parallel len(C))\).
Итоговый тег \(T = MSB_{128}(GHASH \oplus E_K(J_0))\).
Таким образом, любое несовпадение хотя бы одного бита в открытом AAD гарантирует фундаментальное расхождение тега аутентификации.

## Подводные камни

1. Забывать включать идентификатор контекста (например, `tenant_id` или `user_id`) в AAD: если злоумышленник скопирует зашифрованное поле чужого пользователя в свою запись в БД, при отсутствии AAD сервис успешно расшифрует его.
2. Передача динамически сериализуемых структур в AAD без канонического порядка полей: если JSON-поля поменяются местами (`{"a":1,"b":2}` vs `{"b":2,"a":1}`), AAD не сойдется.

## На собеседовании

**Вопрос с собеседования:** «Что такое атака повторного связывания (Ciphertext Relocation Attack) в базах данных и как AAD предотвращает её?»
**Ответ:** Если зашифрованные колонки в базе данных (например, паспортные данные или номера кредитных карт) шифруются одним мастер-ключом сервиса без AAD, злоумышленник с доступом к записи может скопировать зашифрованный срез из строки жертвы `User A` в строку подконтрольного аккаунта `User B`. Затем он обращается к API профиля пользователя B и получает расшифрованные данные жертвы. Добавление Primary Key или `user_id` в качестве AAD намертво связывает шифротекст со строкой таблицы: расшифровка в контексте другого ID вызовет `cipher: message authentication failed`.
