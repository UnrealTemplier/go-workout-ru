# Архитектурная защита от Padding Oracle: парадигма Authenticated Encryption (AEAD)

## Условие

**Защита от Padding Oracle**: Покажите, как аутентифицированное шифрование (AEAD) решает эту проблему. **Всегда проверяйте MAC/Tag перед decrypt.**

## Теория

Атаки типа Padding Oracle возникают исключительно тогда, когда система нарушает золотое правило криптографии:
**Никогда не выполняйте дешифрование и разбор паддинга до проверки аутентичности и целостности сообщения!**

Исторически существовали три схемы композиции шифрования и аутентификации:
1. **Encrypt-and-MAC (SSH)**: \(C = Enc(P)\), \(T = MAC(P)\). Плохо: MAC вычисляется от открытого текста, может раскрывать информацию о \(P\).
2. **MAC-then-Encrypt (TLS 1.0–1.2)**: \(P' = P \parallel MAC(P)\), \(C = Enc(P')\). Катастрофа: чтобы проверить MAC, сервер сначала обязан расшифровать данные и снять паддинг, открывая окно для оракула паддинга!
3. **Encrypt-then-MAC (IPsec / AEAD)**: \(C = Enc(P)\), \(T = MAC(C)\). **Идеально**: получатель первым делом в константном времени проверяет \(MAC(C)\). Если тег не сошелся, пакет отбрасывается без малейших попыток расшифровать его или проверить паддинг.

Современные AEAD шифры (AES-GCM, ChaCha20-Poly1305) реализуют Encrypt-then-MAC на уровне математического примитива.

## Решение по шагам

1. Напишите безопасный конвейер дешифрования.
2. Продемонстрируйте проверку тега аутентификации ДО любых операций над полезной нагрузкой.
3. Покажите, что при любом повреждении данных дешифратор даже не прикасается к разбору полезной нагрузки, делая оракулы невозможными.

## Код решения

**`aead_defense.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"errors"
	"fmt"
	"io"
)

// SafeAEADService гарантирует защиту от Padding Oracle
type SafeAEADService struct {
	aead cipher.AEAD
}

func NewSafeAEADService(key []byte) (*SafeAEADService, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}
	return &SafeAEADService{aead: gcm}, nil
}

func (s *SafeAEADService) Encrypt(plaintext []byte) ([]byte, error) {
	nonce := make([]byte, s.aead.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, err
	}
	// [Nonce][Ciphertext][Tag]
	return s.aead.Seal(nonce, nonce, plaintext, nil), nil
}

func (s *SafeAEADService) Decrypt(packet []byte) ([]byte, error) {
	nonceSize := s.aead.NonceSize()
	if len(packet) < nonceSize+s.aead.Overhead() {
		return nil, errors.New("packet too short")
	}

	nonce := packet[:nonceSize]
	ciphertextWithTag := packet[nonceSize:]

	// Open атомарно проверяет GHASH тег перед возвратом данных.
	// Никакого промежуточного паддинга нет в принципе!
	plaintext, err := s.aead.Open(nil, nonce, ciphertextWithTag, nil)
	if err != nil {
		// Единая, обезличенная ошибка в константном времени
		return nil, errors.New("cryptographic authentication failed")
	}

	return plaintext, nil
}

func main() {
	key := make([]byte, 32)
	_ = rand.Read(key)

	service, _ := NewSafeAEADService(key)
	packet, _ := service.Encrypt([]byte("Sensitive Medical Record: Diagnosis OK"))

	// Легитимная расшифровка
	data, err := service.Decrypt(packet)
	fmt.Printf("1. Легитимный запрос: %s (err: %v)\n", string(data), err)

	// Попытка атаки: модификация байтов злоумышленником
	packet[len(packet)-1] ^= 0xAA
	_, err = service.Decrypt(packet)
	fmt.Printf("2. Атака модификации: err = '%v'\n", err)
	fmt.Println("Результат: атака отбита на этапе аутентификации, оракул невозможен!")
}
```

## Под капотом

В интерфейсе `cipher.AEAD` метод `Open(dst, nonce, ciphertext, additionalData)` спроектирован так, что он возвращает ошибку и пустой срез, если тег аутентификации неверен. При этом алгоритм GCM не использует PKCS паддинг вообще: длина выходного открытого текста строго равна длине входного шифротекста за вычетом 16 байт тега.

## Подводные камни

Попытка вручную реализовать конструкцию Encrypt-then-MAC с отдельным ключом AES-CBC и ключом HMAC-SHA256 без учета правильного формата порядка байт и длины IV. Всегда используйте готовые примитивы `cipher.NewGCM` или `chacha20poly1305`.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между схемами MAC-then-Encrypt и Encrypt-then-MAC с точки зрения криптографической устойчивости к атакам активного посредника?»
**Ответ:** При MAC-then-Encrypt злоумышленник заставляет сервер тратить ресурсы процессора на расшифровку непроверенного шифротекста и проверку паддинга, создавая оракулы утечки ошибок и паддинга. При Encrypt-then-MAC шифротекст сначала проходит проверку аутентификационного тега. Если тег неверен, обработка немедленно прекращается за константное время, предотвращая любые манипуляции с открытым текстом.
