# Потоковое шифрование больших файлов через `cipher.StreamWriter` и `cipher.StreamReader`

## Условие

**Потоковое шифрование больших файлов.**: Зашифруйте большой файл (>100MB) с использованием AES-CTR. Реализуйте потоковое чтение/запись через `cipher.StreamWriter` и `cipher.StreamReader`, не загружая весь файл в память.

## Теория

При работе с большими объемами данных (видеофайлы, дампы баз данных, бэкапы размером в десятки гигабайт) единовременная загрузка файла в память через `os.ReadFile` приводит к исчерпанию оперативной памяти и падению процесса по OOM.

Для потоковой обработки стандартная библиотека Go предоставляет потоковые адаптеры интерфейсов `io.Reader` и `io.Writer`:
1. **`cipher.StreamWriter`**: принимает базовый `io.Writer` и объект потокового шифра `cipher.Stream` (например, `cipher.NewCTR`). Все данные, передаваемые в метод `Write(p)`, прозрачно шифруются гаммой и записываются в нижележащий поток.
2. **`cipher.StreamReader`**: принимает базовый `io.Reader` и расшифровывает поток данных на лету по мере вызова метода `Read(p)`.
3. Потребление памяти при этом константно: `O(1)` (буфер фиксированного размера, например 32–64 КБ в `io.Copy`).

## Решение по шагам

1. Создайте 32-байтный ключ AES-256.
2. Для шифрования откройте исходный файл на чтение и целевой файл на запись.
3. Сгенерируйте 16-байтный IV (`aes.BlockSize`) и запишите его в начало выходного файла.
4. Инициализируйте блочный шифр `aes.NewCipher(key)` и потоковый режим `cipher.NewCTR(block, iv)`.
5. Оберните целевой файл в `writer := cipher.StreamWriter{S: stream, W: dstFile}`.
6. Вызовите `io.Copy(writer, srcFile)` для эффективной потоковой передачи.
7. Для расшифровки прочитайте 16 байт IV из начала зашифрованного файла, оберните файл в `cipher.StreamReader` и передайте поток в `os.Create`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"os"
)

// EncryptStreamLargeFile потоково шифрует файл с минимальным расходом памяти
func EncryptStreamLargeFile(srcPath, dstPath string, key []byte) error {
	srcFile, err := os.Open(srcPath)
	if err != nil {
		return fmt.Errorf("failed to open src: %w", err)
	}
	defer srcFile.Close()

	dstFile, err := os.Create(dstPath)
	if err != nil {
		return fmt.Errorf("failed to create dst: %w", err)
	}
	defer dstFile.Close()

	block, err := aes.NewCipher(key)
	if err != nil {
		return err
	}

	// В режиме CTR размер IV равен размеру блока AES (16 байт)
	iv := make([]byte, aes.BlockSize)
	if _, err := io.ReadFull(rand.Reader, iv); err != nil {
		return fmt.Errorf("failed to read IV: %w", err)
	}

	// Записываем IV в начало зашифрованного файла
	if _, err := dstFile.Write(iv); err != nil {
		return fmt.Errorf("failed to write IV: %w", err)
	}

	stream := cipher.NewCTR(block, iv)
	writer := cipher.StreamWriter{S: stream, W: dstFile}

	// Копируем через 32KB буфер io.Copy без расхода памяти
	bytesWritten, err := io.Copy(writer, srcFile)
	if err != nil {
		return fmt.Errorf("stream copy failed: %w", err)
	}

	fmt.Printf("Потоково зашифровано: %d байт данных\n", bytesWritten)
	return nil
}

// DecryptStreamLargeFile потоково расшифровывает файл
func DecryptStreamLargeFile(srcPath, dstPath string, key []byte) error {
	srcFile, err := os.Open(srcPath)
	if err != nil {
		return fmt.Errorf("failed to open src: %w", err)
	}
	defer srcFile.Close()

	iv := make([]byte, aes.BlockSize)
	if _, err := io.ReadFull(srcFile, iv); err != nil {
		return fmt.Errorf("failed to read IV from stream: %w", err)
	}

	block, err := aes.NewCipher(key)
	if err != nil {
		return err
	}

	dstFile, err := os.Create(dstPath)
	if err != nil {
		return fmt.Errorf("failed to create dst: %w", err)
	}
	defer dstFile.Close()

	stream := cipher.NewCTR(block, iv)
	reader := cipher.StreamReader{S: stream, R: srcFile}

	bytesDecrypted, err := io.Copy(dstFile, reader)
	if err != nil {
		return fmt.Errorf("stream decrypt failed: %w", err)
	}

	fmt.Printf("Потоково расшифровано: %d байт данных\n", bytesDecrypted)
	return nil
}

func main() {
	key := make([]byte, 32)
	_ = rand.Read(key)

	// Создаем тестовый файл
	testData := []byte("HighLoad Stream Encryption in Go 1.22+. Streaming chunks without RAM allocations.\n")
	_ = os.WriteFile("stream_input.bin", testData, 0644)
	defer os.Remove("stream_input.bin")
	defer os.Remove("stream_encrypted.bin")
	defer os.Remove("stream_output.bin")

	if err := EncryptStreamLargeFile("stream_input.bin", "stream_encrypted.bin", key); err != nil {
		panic(err)
	}

	if err := DecryptStreamLargeFile("stream_encrypted.bin", "stream_output.bin", key); err != nil {
		panic(err)
	}

	res, _ := os.ReadFile("stream_output.bin")
	fmt.Printf("Результат: %s", string(res))
}
```

## Под капотом

Метод `io.Copy(dst, src)` внутри рантайма Go использует пул внутренних буферов размером 32 КБ (`copyBuffer`). Если тип источника или приемника поддерживает интерфейс `io.WriterTo` или `io.ReaderFrom`, Go оптимизирует системные вызовы.
В режиме CTR дешифрование математически абсолютно идентично шифрованию: \(P = C \oplus E_K(IV \parallel Counter)\). Поэтому один и тот же потоковый объект `cipher.NewCTR` используется и в `StreamWriter`, и в `StreamReader`.

## Подводные камни

1. Отсутствие аутентификации данных в голом CTR: чистый `cipher.StreamWriter` с CTR не защищен от битовых подмен. Если атакующий знает структуру файла, он может изменить байты на лету. В промышленном коде поток разбивают на чанки (например по 64 КБ) и каждый чанк защищают HMAC или используют потоковый AEAD (схема STREAM из библиотеки Tink / MinIO).
2. Повторное использование IV при потоковом шифровании.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя использовать стандартный `cipher.NewGCM` в потоковом режиме `io.Copy` для 50-гигабайтного файла по сети?»
**Ответ:** В GCM тег аутентификации GHASH вычисляется от всего объема переданных данных и прикрепляется в самом конце сообщения. Получатель не имеет права отдавать приложению ни единого байта расшифрованного текста до тех пор, пока не проверит этот итоговый тег. Если отдавать данные потоком до проверки тега, атакующий сможет прислать зловредный payload, обработанный системой, и лишь в конце соединение оборвется по ошибке аутентификации. Поэтому потоковый GCM требует разбиения потока на независимые AEAD-фреймы с индивидуальными тегами.
