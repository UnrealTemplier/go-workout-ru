# Сравнение режимов блочного шифрования: GCM vs CTR vs CBC

## Условие

**Сравнение режимов: GCM vs CTR vs CBC.**: Реализуйте шифрование одного и того же сообщения тремя способами. Объясните, почему CBC требует padding и уникальный IV, CTR — уникальный nonce, а GCM — аутентифицированное шифрование (AEAD) и предпочтителен.

## Теория

При проектировании криптосистем выбор режима шифрования определяет стойкость ко взлому:

1. **CBC (Cipher Block Chaining)**:
   - Каждый блок открытого текста XOR-ится с предыдущим блоком шифротекста перед шифрованием.
   - Первый блок требует непредсказуемого вектора инициализации (IV, 16 байт).
   - **Требует Padding** (PKCS#7), так как размер данных обязан быть строго кратен 16 байтам.
   - Уязвим к **Padding Oracle Attacks**, если проверка целостности отсутствует или выполняется после дешифрации.
2. **CTR (Counter Mode)**:
   - Превращает блочный шифр в потоковый: шифрует значения счетчика `IV || Counter`, а результат XOR-ит с открытым текстом.
   - **Не требует padding**, длина шифротекста равна длине открытого текста.
   - Обеспечивает конфиденциальность, но **не защищает от подделки (Malleability)**: инверсия бита в шифротексте инвертирует ровно тот же бит в расшифрованном тексте!
3. **GCM (Galois/Counter Mode)**:
   - Базируется на CTR, но совмещает его с вычислением имитовставки GHASH (16 байт).
   - Это режим **AEAD (Authenticated Encryption with Associated Data)**.
   - Защищает и от чтения, и от подделки, и от атак типа Padding Oracle.
   - Является абсолютным стандартом современной криптографии.

## Решение по шагам

1. Создайте 32-байтный ключ AES-256.
2. Реализуйте функцию шифрования в режиме CBC с добавлением PKCS#7 паддинга.
3. Реализуйте функцию шифрования в режиме CTR через `cipher.NewCTR`.
4. Реализуйте функцию шифрования в режиме GCM через `cipher.NewGCM`.
5. Сравните размеры и структуру полученных шифротекстов.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
)

// pkcs7Pad дополняет срез до кратности blockSize
func pkcs7Pad(data []byte, blockSize int) []byte {
	padding := blockSize - len(data)%blockSize
	padtext := bytes.Repeat([]byte{byte(padding)}, padding)
	return append(data, padtext...)
}

func encryptCBC(plaintext, key []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}

	padded := pkcs7Pad(plaintext, aes.BlockSize)
	ciphertext := make([]byte, aes.BlockSize+len(padded))
	iv := ciphertext[:aes.BlockSize]
	if _, err := io.ReadFull(rand.Reader, iv); err != nil {
		return nil, err
	}

	mode := cipher.NewCBCEncrypter(block, iv)
	mode.CryptBlocks(ciphertext[aes.BlockSize:], padded)
	return ciphertext, nil
}

func encryptCTR(plaintext, key []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}

	ciphertext := make([]byte, aes.BlockSize+len(plaintext))
	iv := ciphertext[:aes.BlockSize]
	if _, err := io.ReadFull(rand.Reader, iv); err != nil {
		return nil, err
	}

	stream := cipher.NewCTR(block, iv)
	stream.XORKeyStream(ciphertext[aes.BlockSize:], plaintext)
	return ciphertext, nil
}

func encryptGCM(plaintext, key []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}

	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}

	nonce := make([]byte, gcm.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, err
	}

	return gcm.Seal(nonce, nonce, plaintext, nil), nil
}

func main() {
	key := make([]byte, 32)
	_ = rand.Read(key)

	message := []byte("Benchmark message payload (len = 29 bytes)")

	cbcRes, _ := encryptCBC(message, key)
	ctrRes, _ := encryptCTR(message, key)
	gcmRes, _ := encryptGCM(message, key)

	fmt.Printf("Исходный размер сообщения: %d байт\n", len(message))
	fmt.Printf("CBC: длина = %d байт (IV: 16 + Padded: 32)\n", len(cbcRes))
	fmt.Printf("CTR: длина = %d байт (IV: 16 + Stream: 29)\n", len(ctrRes))
	fmt.Printf("GCM: длина = %d байт (Nonce: 12 + Data: 29 + Tag: 16)\n", len(gcmRes))
}
```

## Под капотом

В режиме CBC операция шифрования не поддается параллелизации: каждый блок \(C_i = E_K(P_i \oplus C_{i-1})\) зависит от предыдущего блока шифротекста.
В режимах CTR и GCM все блоки счетчика независимы: \(C_i = P_i \oplus E_K(IV \parallel Counter_i)\), что позволяет процессору использовать векторные конвейеры SIMD/AVX для одновременного параллельного шифрования множества блоков данных.

## Подводные камни

1. Использование CBC или CTR без отдельной проверки HMAC: злоумышленник может модифицировать зашифрованные данные прямо на лету в сетевом сокете или в БД.
2. Предсказуемый IV в CBC: использование последовательных или константных IV делает CBC уязвимым к атакам по выбранному открытому тексту (CPA, например, BEAST атака в TLS 1.0).

## На собеседовании

**Вопрос с собеседования:** «Почему в современном сетевом стеке (TLS 1.3, QUIC, WireGuard) полностью удалили поддержку режима AES-CBC, оставив только AEAD-шифры (GCM, ChaCha20-Poly1305)?»
**Ответ:** Исторически режим CBC в протоколах TLS 1.0–1.2 породил непрерывную череду катастрофических уязвимостей (BEAST, Lucky Thirteen, POODLE), вызванных раздельной схемой MAC-then-Encrypt и проверкой PKCS#7 паддинга. Атаки по времени на валидацию паддинга позволяли атакующим полностью дешифровать трафик. AEAD-шифры устранили концепцию паддинга в принципе и гарантируют строгую аутентификацию шифротекста до начала любых манипуляций с данными.
