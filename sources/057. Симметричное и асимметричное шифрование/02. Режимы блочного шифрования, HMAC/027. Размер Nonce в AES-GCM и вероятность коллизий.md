# Размер Nonce в AES-GCM и вероятность коллизий парадокса дней рождения

## Условие

**GCM nonce size**: Используйте стандартные 96 бит nonce для GCM. Покажите, как 32-бит nonce в 32-бит счётчик даёт ~2^32 безопасных шифрований под одним ключом.

## Теория

Размер вектора инициализации (Nonce) в AES-GCM жестко регламентирован стандартом **NIST SP 800-38D**:
1. **Канонический размер nonce — ровно 96 бит (12 байт)**.
2. Блок счетчика AES имеет размер 128 бит (16 байт) и компонуется как:
   `J_0 = Nonce[96 бит] || Counter[32 бита]`.
3. Начальное значение счетчика равно `0x00000001`. Для каждого зашифрованного 16-байтного блока счетчик инкрементируется на 1: `0x00000002`, `0x00000003`...
4. 32-битный счетчик позволяет зашифровать до \(2^{32}-2\) блоков (около 64 ГБ) в рамках одного сообщения.

**Парадокс дней рождения и лимит шифрований:**
Если 96-битный nonce генерируется **случайно** через `crypto/rand`, вероятность коллизии подчиняется формуле парадокса дней рождения:
\(P_{collision} \approx \frac{N^2}{2 \times 2^{96}} = \frac{N^2}{2^{97}}\).
По рекомендациям NIST, вероятность повтора nonce не должна превышать \(2^{-32}\). Отсюда следует жесткий предел:
\(N \le 2^{32}\) сообщений на одном ключе при случайных 96-битных nonce!
После достижения этого порога ключ шифрования **обязан быть ротирован**.

## Решение по шагам

1. Создайте экземпляр `cipher.NewGCM(block)`.
2. Проверьте размер, возвращаемый методом `gcm.NonceSize()` (должен быть равен 12).
3. Покажите формирование детерминированного счетчика (например, 64 бита ID машины + 32 бита инкрементального счетчика пакетов).
4. Продемонстрируйте расчет безопасного лимита объема шифрования на один ключ.

## Код решения

**`nonce_limits.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"encoding/binary"
	"fmt"
	"math"
	"sync/atomic"
)

// DeterministicNonceGenerator генерирует гарантированно неколлидирующие nonce
type DeterministicNonceGenerator struct {
	nodeID  uint64 // 64 бита уникального ID сервера/пода
	counter uint32 // 32 бита строго монотонного счетчика сообщений
}

func NewDeterministicNonceGenerator(nodeID uint64) *DeterministicNonceGenerator {
	return &DeterministicNonceGenerator{nodeID: nodeID}
}

// NextNonce формирует ровно 12 байт (96 бит)
func (g *DeterministicNonceGenerator) NextNonce() ([]byte, error) {
	cnt := atomic.AddUint32(&g.counter, 1)
	if cnt == math.MaxUint32 {
		return nil, fmt.Errorf("nonce space exhausted: mandatory key rotation required!")
	}

	nonce := make([]byte, 12)
	binary.BigEndian.PutUint64(nonce[0:8], g.nodeID)
	binary.BigEndian.PutUint32(nonce[8:12], cnt)
	return nonce, nil
}

func main() {
	key := make([]byte, 32)
	_ = rand.Read(key)
	block, _ := aes.NewCipher(key)
	gcm, _ := cipher.NewGCM(block)

	fmt.Printf("Канонический размер GCM Nonce: %d байт (%d бит)\n", gcm.NonceSize(), gcm.NonceSize()*8)

	// Генератор для сервиса с NodeID = 0xABCD112233445566
	gen := NewDeterministicNonceGenerator(0xABCD112233445566)

	n1, _ := gen.NextNonce()
	n2, _ := gen.NextNonce()
	n3, _ := gen.NextNonce()

	fmt.Printf("Nonce 1: %x\n", n1)
	fmt.Printf("Nonce 2: %x\n", n2)
	fmt.Printf("Nonce 3: %x\n", n3)

	fmt.Println("\n=== АНАЛИЗ ПАРАДОКСА ДНЕЙ РОЖДЕНИЯ (NIST SP 800-38D) ===")
	fmt.Println("1. При СЛУЧАЙНЫХ 96-битных nonce лимит шифрований на одном ключе: не более 2^32 сообщений.")
	fmt.Println("2. При ДЕТЕРМИНИРОВАННЫХ счетчиках (Counter-based) лимит: строго 2^32 сообщений на инстанс без риска коллизий.")
}
```

## Под капотом

Если передать в `cipher.NewGCM` nonce длиной не 12 байт, Go применит вычисление \(J_0 = GHASH(H, {}, Nonce)\). Это создает дополнительную нагрузку на процессор и теоретически может вызвать совпадение значения \(J_0\) с другим сообщением из-за мультипликативных свойств GHASH. Поэтому в HighLoad-системах использование non-96-bit nonce является антипаттерном.

## Подводные камни

Использование 64-битного случайного nonce: при размере 64 бита коллизия по закону дней рождения произойдет уже через \(2^{32}\) пакетов с вероятностью 50%, что приведет к компрометации системы.

## На собеседовании

**Вопрос с собеседования:** «Почему в протоколе TLS 1.3 вектор инициализации для каждой записи не передается по сети, а вычисляется локально обеими сторонами?»
**Ответ:** Для экономии сетевого трафика (12 байт на каждый TCP-пакет) и предотвращения любых атак на генератор случайных чисел. В TLS 1.3 обе стороны берут статический 96-битный IV, полученный при рукопожатии, и перед отправкой каждой записи выполняют операцию XOR этого IV с 64-битным монотонным порядковым номером сетевой записи (Sequence Number). Это гарантирует строгую уникальность nonce без передачи по сети.
