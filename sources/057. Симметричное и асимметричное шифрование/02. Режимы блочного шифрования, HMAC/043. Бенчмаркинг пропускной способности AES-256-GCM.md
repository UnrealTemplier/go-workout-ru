# Бенчмаркинг пропускной способности AES-256-GCM и влияние аппаратного ускорения AES-NI

## Условие

**AES-GCM 256-bit key benchmark**: Замерьте скорость AES-256-GCM на вашем железе. На современных CPU с AES-NI это ~3 GB/s.

## Теория

Современные серверные микропроцессоры (Intel Xeon Scalable, AMD EPYC, Apple Silicon M-серии, AWS Graviton) содержат кремниевые аппаратные блоки ускорения криптографии:
1. **Intel/AMD AES-NI**: специализированные процессорные инструкции (`AESENC`, `AESDEC`, `AESENCLAST`), реализующие раундовые преобразования шифра на аппаратном уровне.
2. **CLMUL / PCLMULQDQ**: инструкция беспереносного умножения полиномов, ускоряющая вычисление тега аутентификации GHASH.
3. Благодаря аппаратной поддержке скорость шифрования AES-256-GCM в Go достигает **3–6 ГБ/с на одно ядро CPU**, а потребление тактов процессора падает до \(\sim 0.6–1.0\) cycles per byte.
4. Программная эмуляция без AES-NI работает со скоростью всего 150–300 МБ/с, расходуя до 15–25 cycles per byte.

## Решение по шагам

1. Создайте буфер данных фиксированного размера (например, 1 МБ или 16 КБ).
2. Инициализируйте AES-256-GCM шифратор.
3. Запустите цикл шифрования на \(N\) итераций с замером времени через `time.Now()`.
4. Рассчитайте пропускную способность: \(\text{Throughput (GB/s)} = \frac{\text{Bytes Processed}}{\text{Elapsed Seconds} \times 10^9}\).
5. Выведите результаты замера производительности.

## Код решения

**`aes_benchmark.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"fmt"
	"io"
	"time"
)

func BenchmarkAESGCM(bufferSize int, iterations int) {
	key := make([]byte, 32) // AES-256
	_, _ = io.ReadFull(rand.Reader, key)

	block, err := aes.NewCipher(key)
	if err != nil {
		panic(err)
	}

	gcm, err := cipher.NewGCM(block)
	if err != nil {
		panic(err)
	}

	nonce := make([]byte, gcm.NonceSize())
	_, _ = io.ReadFull(rand.Reader, nonce)

	payload := make([]byte, bufferSize)
	_, _ = io.ReadFull(rand.Reader, payload)

	// Аллоцируем буфер под шифротекст
	dst := make([]byte, 0, bufferSize+gcm.Overhead())

	// Прогрев CPU кэшей
	for i := 0; i < 100; i++ {
		_ = gcm.Seal(dst[:0], nonce, payload, nil)
	}

	// Основной замер
	start := time.Now()
	for i := 0; i < iterations; i++ {
		_ = gcm.Seal(dst[:0], nonce, payload, nil)
	}
	elapsed := time.Since(start)

	totalBytes := int64(bufferSize) * int64(iterations)
	gigabytes := float64(totalBytes) / (1024 * 1024 * 1024)
	gbPerSec := gigabytes / elapsed.Seconds()

	fmt.Printf("Буфер: %6d КБ | Итераций: %6d | Время: %8v | Скорость: %6.2f ГБ/с\n",
		bufferSize/1024, iterations, elapsed, gbPerSec)
}

func main() {
	fmt.Println("=== БЕНЧМАРК ПРОИЗВОДИТЕЛЬНОСТИ AES-256-GCM (Go 1.22+) ===")
	BenchmarkAESGCM(16*1024, 50_000)   // 16 КБ пакеты (сетевой трафик)
	BenchmarkAESGCM(64*1024, 20_000)   // 64 КБ пакеты (дисковый I/O)
	BenchmarkAESGCM(1024*1024, 2_000)  // 1 МБ блоки (bulk data)
}
```

ℹ️ Бенчмаркинг скорости AES-256-GCM на различном размере буферов

**`Терминал`**

```bash
go run aes_benchmark.go
# === БЕНЧМАРК ПРОИЗВОДИТЕЛЬНОСТИ AES-256-GCM (Go 1.22+) ===
# Буфер:     16 КБ | Итераций:  50000 | Время: 215.4ms | Скорость:   3.64 ГБ/с
# Буфер:     64 КБ | Итераций:  20000 | Время: 278.1ms | Скорость:   4.39 ГБ/с
# Буфер:   1024 КБ | Итераций:   2000 | Время: 412.3ms | Скорость:   4.74 ГБ/с
```

## Под капотом

В функции `aes.NewCipher` пакет `crypto/aes` на этапе инициализации вызывает низкоуровневую проверку флагов CPUID: `cpu.X86.HasAES && cpu.X86.HasPCLMULQDQ`. Если флаги установлены, указатель на метод шифрования переключается на оптимизированную ассемблерную процедуру `encryptBlockGoAsm`.

## Подводные камни

Выделение нового среза `make([]byte, ...)` внутри горячего цикла бенчмарка: в этом случае вы будете замерять не скорость криптографического шифратора, а скорость аллокатора кучи Go (`runtime.mallocgc`).

## На собеседовании

**Вопрос с собеседования:** «Почему при переходе с размера буфера 1 КБ на 64 КБ скорость шифрования AES-GCM возрастает в 2–3 раза?»
**Ответ:** При малых буферах (1 КБ) накладные расходы на инициализацию контекста функции, генерацию первого блока счетчика \(J_0\) и финализацию тега GHASH сопоставимы с временем шифрования полезных данных. На больших буферах (64 КБ–1 МБ) процессор работает на полную мощность конвейера конвейеризованных векторных инструкций `AESENC` без пауз, а накладные расходы нивелируются.
