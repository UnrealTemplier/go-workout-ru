# Усиление безопасности TLS (TLS Hardening) и взаимная аутентификация mTLS

## Условие

**TLS hardening.**: Настройте `http.Server` с `tls.Config`: минимум TLS 1.2 (или 1.3), строгий список cipher suites (только AEAD), отключение `InsecureSkipVerify` в клиенте. Объясните, почему `tls.Config` с `ClientAuth: tls.RequireAndVerifyClientCert` нужен для mTLS.

### Исходная формулировка

**TLS hardening.**: Настройте `http.Server` с `tls.Config`: минимум TLS 1.2 (или 1.3), строгий список cipher suites (только AEAD), отключение `InsecureSkipVerify` в клиенте. Объясните, почему `tls.Config` с `ClientAuth: tls.RequireAndVerifyClientCert` нужен для mTLS.

## Теория

Безопасность сетевых сервисов на транспортном уровне требует строгого конфигурирования `tls.Config`:

**Правила TLS Hardening для BigTech бэкендов:**
1. **Минимальная версия TLS**: строго `tls.VersionTLS12` или `tls.VersionTLS13`. Старые версии TLS 1.0 и TLS 1.1 запрещены стандартами безопасности (RFC 8996).
2. **Только AEAD шифры**: исключение всех CBC-шифров (например `TLS_RSA_WITH_AES_128_CBC_SHA`), оставление только `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384` и `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`. В TLS 1.3 небезопасные шифры удалены на уровне протокола.
3. **Безопасность клиента**: флаг `InsecureSkipVerify: true` **категорически запрещен** в production, так как полностью отключает проверку подлинности сервера и делает трафик уязвимым к Man-in-the-Middle.

**Взаимная аутентификация (mTLS — Mutual TLS):**
В классическом TLS только сервер подтверждает свою подлинность клиенту.
В архитектуре Zero Trust и Service Mesh (Istio, Linkerd) сервер обязан требовать подтверждения личности и от клиента:
Политика `ClientAuth: tls.RequireAndVerifyClientCert` заставляет сервер проверять X.509 сертификат клиента против пула доверенных сертификатов `ClientCAs`. Соединения без валидного сертификата разрываются на этапе TLS handshake.

## Решение по шагам

1. Создайте эталонную структуру `tls.Config` для защищенного сервера.
2. Установите `MinVersion = tls.VersionTLS12`.
3. Задайте список доверенных шифронаборов `CipherSuites` с исключительным использованием ECDHE и GCM/ChaCha20.
4. Настройте политику mTLS: `ClientAuth: tls.RequireAndVerifyClientCert` с указанием пула `ClientCAs`.
5. Сконфигурируйте безопасный клиент `http.Client` с собственным сертификатом и защитой от перехвата.

## Код решения

**`tls_hardened.go`**

```go
package main

import (
	"crypto/tls"
	"crypto/x509"
	"fmt"
	"net/http"
	"time"
)

// BuildHardenedServerTLSConfig создает промышленный конфиг TLS для серверов
func BuildHardenedServerTLSConfig(clientCAPool *x509.CertPool) *tls.Config {
	return &tls.Config{
		// 1. Запрещаем устаревшие протоколы SSLv3, TLS 1.0, TLS 1.1
		MinVersion: tls.VersionTLS12,
		MaxVersion: tls.VersionTLS13,

		// 2. Строгий список только AEAD шифров для TLS 1.2
		// (В TLS 1.3 набор шифров зафиксирован спецификацией и безопасен по умолчанию)
		CipherSuites: []uint16{
			tls.TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
			tls.TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,
			tls.TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305,
			tls.TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305,
			tls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,
			tls.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,
		},

		// 3. Предпочитаем кривые X25519 и P-256
		CurvePreferences: []tls.CurveID{
			tls.X25519,
			tls.CurveP256,
		},

		// 4. Включение mTLS: требуем и проверяем клиентский сертификат
		ClientAuth: tls.RequireAndVerifyClientCert,
		ClientCAs:  clientCAPool,

		// 5. Ограничение времени сессии
		SessionTicketsDisabled: false,
	}
}

// BuildHardenedClient создает защищенный HTTP клиент
func BuildHardenedClient(rootCAs *x509.CertPool, clientCert tls.Certificate) *http.Client {
	tlsConfig := &tls.Config{
		MinVersion: tls.VersionTLS12,
		// КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО: InsecureSkipVerify: true
		InsecureSkipVerify: false,
		RootCAs:            rootCAs,
		Certificates:       []tls.Certificate{clientCert},
	}

	transport := &http.Transport{
		TLSClientConfig:     tlsConfig,
		ForceAttemptHTTP2:   true,
		MaxIdleConns:        100,
		IdleConnTimeout:     90 * time.Second,
		TLSHandshakeTimeout: 10 * time.Second,
	}

	return &http.Client{
		Transport: transport,
		Timeout:   15 * time.Second,
	}
}

func main() {
	caPool := x509.NewCertPool()

	serverTLS := BuildHardenedServerTLSConfig(caPool)

	fmt.Println("=== УСИЛЕННАЯ КОНФИГУРАЦИЯ TLS 1.2 / 1.3 ===")
	fmt.Printf("MinVersion:         0x%04x (TLS 1.2)\n", serverTLS.MinVersion)
	fmt.Printf("Разрешено шифров:   %d (Исключительно AEAD)\n", len(serverTLS.CipherSuites))
	fmt.Printf("Режим mTLS:         tls.RequireAndVerifyClientCert (Код: %d)\n", serverTLS.ClientAuth)
	fmt.Println("Клиентские сокеты защищены от даунгрейд-атак и атак перехвата трафика!")
}
```

## Под капотом

В Go 1.14+ при установке соединения TLS 1.3 поле `CipherSuites` в `tls.Config` игнорируется для фильтрации шифров TLS 1.3: рантайм Go автоматически согласует лучший поддерживаемый шифр из безопасного списка TLS 1.3 (`TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`), а фильтр `CipherSuites` применяется строго к клиентам, подключающимся по TLS 1.2.

## Подводные камни

Включение `InsecureSkipVerify: true` во внутренних сервисах компании с самоподписанными сертификатами. Вместо этого нужно загрузить корневой сертификат компании в `RootCAs: certPool`.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисной архитектуре BigTech переходят на mTLS между всеми внутренними подами Kubernetes, даже если весь трафик находится внутри приватной VPC?»
**Ответ:** Это реализация модели Zero Trust (нулевого доверия). Во-первых, при компрометации одного пода или узла злоумышленник не может пассивно слушать сетевой трафик через `tcpdump`. Во-вторых, mTLS обеспечивает строгую криптографическую идентичность сервисов: сервер точно знает, что запрос пришел именно от сервиса `billing-service` (по SAN в клиентском сертификате), предотвращая подделку заголовков `X-User-Id` и несанкционированные RPC-вызовы.
