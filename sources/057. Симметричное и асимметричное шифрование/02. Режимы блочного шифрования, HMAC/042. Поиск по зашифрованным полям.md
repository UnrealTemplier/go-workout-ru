# Поиск по зашифрованным полям: слепой индекс (Blind Index) против детерминированного шифрования

## Условие

**Поиск по зашифрованным данным**: Реализуйте deterministic encryption для полей, по которым нужен поиск (с пониманием trade-off в безопасности).

## Теория

При шифровании конфиденциальных баз данных возникает инженерный парадокс:
- **Вероятностное шифрование (AES-GCM)**: максимально безопасно, но делает невозможным поиск `WHERE email = ?`, так как один и тот же email каждый раз шифруется по-разному.
- **Детерминированное шифрование (AES-ECB или AES-CTR со статическим IV)**: позволяет строить B-Tree индекс, но раскрывает паттерны и частотные распределения (утечка частоты встречаемости).

**Современный компромисс: Архитектура Blind Index (Слепой индекс)**:
1. Само поле (например, `ssn` или `phone`) шифруется безопасным вероятностным алгоритмом **AES-GCM со случайным nonce**.
2. Рядом в отдельную колонку сохраняется **Слепой индекс**: результат вычисления `HMAC-SHA256(Normalize(value), BlindIndexKey)`.
3. Ключ `BlindIndexKey` независим от мастер-ключа шифрования данных.
4. Поиск в БД выполняется по слепому индексу:
   `SELECT * FROM users WHERE ssn_bindex = ?`.
5. База данных видит только псевдослучайные хеши и не может восстановить открытые значения.

## Решение по шагам

1. Создайте мастер-ключ шифрования `dataKey` и независимый ключ индексирования `blindKey`.
2. Реализуйте функцию нормализации входных данных (приведение к нижнему регистру, удаление пробелов).
3. Реализуйте функцию `ComputeBlindIndex(val string, blindKey []byte) string`.
4. Зашифруйте данные через AES-GCM.
5. Продемонстрируйте сценарий поиска записи по открытому значению через сопоставление слепых индексов.

## Код решения

**`blind_index.go`**

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"strings"
)

type SecureDatabaseRow struct {
	ID             int
	EncryptedEmail string // AES-GCM (недетерминированный, со случайным nonce)
	EmailBlindIdx  string // HMAC-SHA256 слепой индекс для быстрого поиска
}

// NormalizeEmail приводит email к каноническому виду перед индексацией
func NormalizeEmail(email string) string {
	return strings.ToLower(strings.TrimSpace(email))
}

// ComputeBlindIndex вычисляет криптографический слепой индекс
func ComputeBlindIndex(value string, blindKey []byte) string {
	mac := hmac.New(sha256.New, blindKey)
	mac.Write([]byte(NormalizeEmail(value)))
	return hex.EncodeToString(mac.Sum(nil))
}

// EncryptData шифрует данные безопасным AES-GCM
func EncryptData(plaintext string, dataKey []byte) (string, error) {
	block, _ := aes.NewCipher(dataKey)
	gcm, _ := cipher.NewGCM(block)
	nonce := make([]byte, gcm.NonceSize())
	_, _ = io.ReadFull(rand.Reader, nonce)

	ciphertext := gcm.Seal(nonce, nonce, []byte(plaintext), nil)
	return hex.EncodeToString(ciphertext), nil
}

func main() {
	dataKey := make([]byte, 32)
	blindKey := make([]byte, 32)
	_, _ = rand.Read(dataKey)
	_, _ = rand.Read(blindKey)

	userEmail := "Security-Officer@Ozon.ru"

	// 1. Сохранение в БД
	encryptedVal, _ := EncryptData(userEmail, dataKey)
	blindIdx := ComputeBlindIndex(userEmail, blindKey)

	row := SecureDatabaseRow{
		ID:             101,
		EncryptedEmail: encryptedVal,
		EmailBlindIdx:  blindIdx,
	}

	fmt.Println("=== АРХИТЕКТУРА СЛЕПОГО ИНДЕКСА (BLIND INDEX) ===")
	fmt.Printf("Исходный email:      %s\n", userEmail)
	fmt.Printf("Encrypted (AES-GCM): %s...\n", row.EncryptedEmail[:32])
	fmt.Printf("Blind Index (B-Tree):%s\n", row.EmailBlindIdx)

	// 2. Пользователь выполняет поиск в API: найти пользователя по email "security-officer@ozon.ru"
	searchQuery := "  security-officer@ozon.ru "
	searchIndex := ComputeBlindIndex(searchQuery, blindKey)

	fmt.Printf("\nВычислен поисковый индекс: %s\n", searchIndex)
	if searchIndex == row.EmailBlindIdx {
		fmt.Println("УСПЕХ ПОИСКА: Запись в БД найдена по B-Tree индексу без раскрытия данных!")
	} else {
		fmt.Println("Запись не найдена.")
	}
}
```

## Под капотом

Слепой индекс устраняет атаку расшифрования базы данных при компрометации SQL-сервера. Атакующий видит только зашифрованные поля и псевдослучайные хеши слепых индексов. Без ключа `blindKey` (хранящегося во внешнем Vault) невозможно составить соответствие между открытыми значениями и индексами.

## Подводные камни

Использование прямого ненормализованного значения: если один пользователь ввел `test@mail.ru`, а искали `Test@mail.ru `, хеши не совпадут.

## На собеседовании

**Вопрос с собеседования:** «В чем компромисс безопасности (Security Trade-off) при использовании слепого индекса для поиска по равенству?»
**Ответ:** Слепой индекс защищает от восстановления открытого текста, но сохраняет информацию об эквивалентности записей (Equality Leakage). Атакующий, проанализировав таблицу, видит, что строки 10 и 25 имеют одинаковый `bindex` (то есть один и тот же email). Если поле имеет малое количество вариантов (например, `gender` или `country`), частотный анализ позволяет сопоставить индексы с реальными значениями. Поэтому слепые индексы рекомендуются только для полей с высокой уникальностью (SSN, Phone, Email).
