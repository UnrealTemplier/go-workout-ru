# Иерархический вывод множества ключей через HKDF и Info-контексты

## Условие

**HKDF для derivation множества ключей**: Из одного мастер-ключа получите разные ключи для шифрования и аутентификации через HKDF с разными info-параметрами.

## Теория

Стандарт **HKDF (RFC 5869 — HMAC-based Extract-and-Expand Key Derivation Function)** является фундаментом безопасности современных протоколов (TLS 1.3, Noise Protocol, Signal, WhatsApp):

**Двухфазная архитектура HKDF:**
1. **Extract**: \(PRK = HMAC-Hash(Salt, IKM)\).
   Исходный ключевой материал (Input Keying Material — IKM) сжимается с солью в псевдослучайный псевдо-мастер ключ фиксированной длины \(PRK\).
2. **Expand**: $OKM = HKDF-Expand(PRK, info, L)$.
   Из одного \(PRK\) можно получить неограниченное количество криптографически независимых выходных ключей (Output Keying Material — OKM).

**Магия параметра `info` (Domain Separation):**
Параметр `info` обеспечивает строгое разделение криптографических контекстов.
Если передать `info="tls13 client in"`, получится ключ клиента.
Если передать `info="tls13 server in"`, получится ключ сервера.
Даже если один из выведенных ключей будет раскрыт, математические свойства односторонней функции HMAC гарантируют, что атакующий не сможет скомпрометировать мастер-секрет или другие ключи.

## Решение по шагам

1. Сгенерируйте 32-байтный псевдослучайный Master Secret.
2. Используйте `hkdf.Extract(sha256.New, masterSecret, salt)` для получения PRK.
3. Выведите ключ шифрования `encKey` с `info = []byte("App-Database-AES-256-Key")`.
4. Выведите ключ аутентификации `macKey` с `info = []byte("App-Message-HMAC-Auth-Key")`.
5. Выведите ключ экспорта данных `exportKey` с `info = []byte("App-External-Export-Token")`.
6. Покажите, что все три ключа абсолютно независимы и уникальны.

## Код решения

**`hkdf_subkeys.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"fmt"
	"io"

	"golang.org/x/crypto/hkdf"
)

// SubkeyManager управляет иерархией производных ключей
type SubkeyManager struct {
	prk []byte
}

func NewSubkeyManager(masterSecret, salt []byte) *SubkeyManager {
	// Фаза 1: HKDF-Extract
	prk := hkdf.Extract(sha256.New, masterSecret, salt)
	return &SubkeyManager{prk: prk}
}

// DeriveSubkey выполняет фазу HKDF-Expand с уникальным контекстом info
func (m *SubkeyManager) DeriveSubkey(contextInfo string, keyLen int) ([]byte, error) {
	reader := hkdf.Expand(sha256.New, m.prk, []byte(contextInfo))
	key := make([]byte, keyLen)
	if _, err := io.ReadFull(reader, key); err != nil {
		return nil, fmt.Errorf("hkdf expand failed: %w", err)
	}
	return key, nil
}

func main() {
	// Исходный мастер-секрет высокой энтропии
	masterSecret := make([]byte, 32)
	_ = rand.Read(masterSecret)

	salt := make([]byte, 16)
	_ = rand.Read(salt)

	km := NewSubkeyManager(masterSecret, salt)

	// Получаем 3 абсолютно независимых функциональных ключа
	encKey, _ := km.DeriveSubkey("v1/storage/aes-256-gcm-encryption", 32)
	macKey, _ := km.DeriveSubkey("v1/network/hmac-sha256-message-auth", 32)
	exportKey, _ := km.DeriveSubkey("v1/audit/export-token-signing", 32)

	fmt.Println("=== ИЕРАРХИЧЕСКИЙ ВЫВОД КЛЮЧЕЙ (HKDF RFC 5869) ===")
	fmt.Printf("Encryption Key: %x\n", encKey)
	fmt.Printf("MAC Key:        %x\n", macKey)
	fmt.Printf("Export Key:     %x\n", exportKey)

	// Проверка детерминированности: при том же info получаем тот же ключ
	encKeyCopy, _ := km.DeriveSubkey("v1/storage/aes-256-gcm-encryption", 32)
	fmt.Printf("\nДетерминированность подтверждена: %x\n", encKeyCopy)
}
```

## Под капотом

В фазе Expand алгоритм HKDF вычисляет блоки:
\(T(1) = HMAC(PRK, info \parallel 0x01)\)
\(T(2) = HMAC(PRK, T(1) \parallel info \parallel 0x02)\)
...
Выходной поток формируется объединением блоков: \(T(1) \parallel T(2) \dots\). Длина одного производного ключа может достигать \(255 \times HashLen\) (для SHA-256 это более 8 килобайт ключей).

## Подводные камни

Использование пустого или одинакового параметра `info` для разных задач: если для шифрования и для подписи использовать `info=""`, оба ключа совпадут, что нарушит изоляцию криптографических примитивов.

## На собеседовании

**Вопрос с собеседования:** «Зачем в протоколах безопасности (TLS 1.3, Signal) обязательно выполняется фаза HKDF-Extract, если исходный секрет Диффи-Хеллмана уже имеет размер 256 бит?»
**Ответ:** Результат операции Diffie-Hellman (\(g^{xy}\)) хотя и трудно вычислить атакующему, распределен по кривой неравномерно (не является равномерным белым шумом). Фаза Extract с солью выполняет роль «криптографического экстрактора энтропии», концентрируя энтропию в строго равномерно распределенный псевдослучайный ключ \(PRK\), пригодный для безопасного расширения.
