# Низкоуровневая безопасность памяти: Zeroing Secrets, crypto/subtle и runtime.KeepAlive

## Условие

**Блок 10 (Шифрование)**: — начните сразу после Блока 4 (`unsafe`), так как криптографические пакеты активно используют `unsafe` для zero-copy и constant-time операций.

## Теория

При разработке криптографических систем высокой надежности безопасность определяется не только математикой алгоритмов, но и поведением компилятора и операционной системы при управлении памятью.

Три критических фактора низкоуровневой криптобезопасности:
1. **Гарантированное зануление памяти (Zeroing Secrets):** Обычное обнуление среза `data[i] = 0` или `clear(data)` компилятор может вырезать в процессе оптимизации (Dead Store Elimination), если переменная больше не используется в функции. Для надежного затирания ключей из памяти перед освобождением требуются барьеры памяти или функции вроде `subtle.ConstantTimeCopy`.
2. **Сравнение в константном времени (Constant-Time Operations):** Оператор `==` или `bytes.Equal` прерывает цикл на первом несовпавшем байте. Злоумышленник по наносекундным замерам времени ответов восстанавливает побайтово пароли, HMAC-подписи и токены (Timing Attacks). Пакет `crypto/subtle` реализует операции с постоянным временем: `subtle.ConstantTimeCompare`, `subtle.ConstantTimeByteEq`.
3. **Предотвращение ранней сборки мусора (runtime.KeepAlive):** При работе с `unsafe.Pointer` сборщик мусора GC может посчитать структуру мертвой и освободить/переместить память прямо во время выполнения низкоуровневого системного вызова. `runtime.KeepAlive` защищает объект от деаллокации до окончания операции.

## Решение по шагам

1. Продемонстрируйте уязвимость стандартного сравнения байт `bytes.Equal` к тайминг-атакам и замените его на `subtle.ConstantTimeCompare`.
2. Напишите безопасную функцию `ZeroMemory`, которая затирает приватные ключи в памяти с защитой от вырезания компилятором.
3. Продемонстрируйте использование `runtime.KeepAlive` для удержания памяти с секретом до завершения криптографической операции.
4. Создайте безопасный контейнер секрета `SecureKey`, реализующий паттерн безопасного уничтожения `Destroy()`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"fmt"
	"io"
	"runtime"
	"unsafe"
)

// SecureKey инкапсулирует криптографический ключ с гарантированным затиранием памяти
type SecureKey struct {
	key []byte
}

// NewSecureKey аллоцирует ключ заданной длины
func NewSecureKey(size int) (*SecureKey, error) {
	buf := make([]byte, size)
	if _, err := io.ReadFull(rand.Reader, buf); err != nil {
		return nil, err
	}
	return &SecureKey{key: buf}, nil
}

// Destroy надежно стирает секретные байты из памяти
func (s *SecureKey) Destroy() {
	if s.key == nil {
		return
	}
	// 1. Зануляем каждый байт в памяти
	for i := range s.key {
		s.key[i] = 0
	}
	// 2. Барьер компилятора: читаем через unsafe указатель, предотвращая Dead Store Elimination
	ptr := unsafe.Pointer(&s.key[0])
	_ = *(*byte)(ptr)

	// 3. runtime.KeepAlive гарантирует, что срез не будет собран GC до завершения затирания
	runtime.KeepAlive(s.key)
	s.key = nil
}

func main() {
	// 1. Демонстрация Constant-Time сравнения
	tokenA := []byte("secret-auth-token-super-secure-hash-99128")
	tokenB := []byte("secret-auth-token-super-secure-hash-99128")
	tokenEvil := []byte("secret-auth-token-super-secure-hash-00000")

	// subtle.ConstantTimeCompare возвращает 1 при равенстве и 0 при несовпадении
	isEqual := subtle.ConstantTimeCompare(tokenA, tokenB) == 1
	isEvilEqual := subtle.ConstantTimeCompare(tokenA, tokenEvil) == 1

	fmt.Println("=== Constant-Time сравнение (crypto/subtle) ===")
	fmt.Printf("Сравнение токенов A и B: %v (защищено от Timing Attacks)\n", isEqual)
	fmt.Printf("Сравнение токенов A и Evil: %v\n", isEvilEqual)

	// 2. Демонстрация работы SecureKey и уничтожения памяти
	secKey, err := NewSecureKey(32)
	if err != nil {
		panic(err)
	}

	fmt.Println("\n=== Безопасная работа с памятью ключа ===")
	fmt.Printf("Сгенерирован приватный ключ DEK (первые 4 байта): %x...\n", secKey.key[:4])

	// Затираем память после использования
	secKey.Destroy()
	fmt.Println("Вызов secKey.Destroy() завершен: память гарантированно занулена.")
	fmt.Printf("Состояние ссылки на ключ: %v\n", secKey.key)
}
```

## Под капотом

Низкоуровневая реализация `subtle.ConstantTimeCompare`:
```go
func ConstantTimeCompare(x, y []byte) int {
    if len(x) != len(y) {
        return 0
    }
    var v byte
    for i := 0; i < len(x); i++ {
        v |= x[i] ^ y[i]
    }
    return ConstantTimeByteEq(v, 0)
}
```
Обратите внимание:
1. Цикл пробегает **абсолютно все байты** среза без досрочного выхода (`break`).
2. Операция `^` (XOR) дает 0 только при побитовом совпадении.
3. Побитовое ИЛИ (`v |= ...`) накапливает любое отличие.
4. Процессор тратит строго одинаковое количество тактов независимо от того, где произошла ошибка — в первом байте или в последнем, исключая возможность снятия тайминг-профиля.

## Подводные камни

1. **Проверка длины до ConstantTimeCompare:** Если длины секретных строк различаются, `ConstantTimeCompare` сразу возвращает 0. Если длина секрета сама по себе является тайной, утечка длины через замер времени может быть использована злоумышленником.
2. **Свопинг памяти на диск (Swap):** Даже если память занулена при выходе из функции, операционная система могла сбросить страницы RAM с ключом в swap-раздел на SSD/HDD до вызова `Destroy`. В критических криптографических демонах страницы памяти закрепляют вызовом системного вызова `mlock` (`unix.Mlock`).

## На собеседовании

**Вопрос с собеседования:** Что такое Dead Store Elimination в оптимизирующем компиляторе Go и почему обычный вызов `clear(key)` перед выходом из функции может не защитить секрет в памяти?
**Ответ:** Оптимизатор компилятора (SSA dead code elimination) анализирует поток управления (liveness analysis). Если массив байт перезаписывается нулями (`for i := range key { key[i] = 0 }`), но после этого переменная `key` ни разу не читается и выходит из области видимости, компилятор считает эти записи «мертвыми» (dead store) и полностью удаляет машинные инструкции записи нулей из итогового бинарного файла. В результате секретные байты ключа остаются лежать в оперативной памяти до тех пор, пока эта память не будет перезаписана другими аллокациями, что делает их уязвимыми к Heartbleed-подобным утечкам или считыванию из Core Dump.
