# Верификация цифровой подписи публичным ключом (rsa.VerifyPSS)

## Условие

**Верификация цифровой подписи публичным ключом (rsa.VerifyPSS)**: Проверь подпись публичным ключом (`rsa.VerifyPSS`).

### Исходная формулировка

Проверь подпись публичным ключом (`rsa.VerifyPSS`).

## Теория

Проверка цифровой подписи публичным ключом — критически важная процедура аутентификации источника и контроля целостности данных в распределенных системах (проверка подлинности вебхуков, обновлений прошивок, JWT токенов).

В схеме RSA-PSS верификатор обладает только открытым ключом `*rsa.PublicKey` и выполняет следующие действия:
1. Вычисляет криптографический хэш проверяемого сообщения с тем же алгоритмом, который использовался при подписании (например, `sha256.Sum256`).
2. Вызывает функцию `rsa.VerifyPSS(pubKey, crypto.SHA256, digest, signature, opts)`.
3. Функция `rsa.VerifyPSS` возвращает `nil` при успешной верификации. Если подпись искажена, сообщение изменено или использован чужой публичный ключ, возвращается ошибка `rsa.ErrVerification`.
4. В коде верификатора критически важно использовать `errors.Is(err, rsa.ErrVerification)` для однозначной диагностики фальсификации.

## Решение по шагам

1. Сгенерируйте пару ключей RSA и подпишите хэш транзакции с помощью `rsa.SignPSS`.
2. Извлеките открытый ключ `&privKey.PublicKey` для имитации независимой проверяющей стороны.
3. Вызовите `rsa.VerifyPSS` для подтверждения подлинности оригинального сообщения.
4. Протестируйте три сценария сбоя проверки:
   - Подмена хотя бы одного байта в теле сообщения.
   - Повреждение одного байта в срезе цифровой подписи.
   - Проверка подписи с использованием другого валидного открытого ключа RSA.
5. Убедитесь, что во всех трех случаях возвращается ошибка `rsa.ErrVerification`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto"
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"errors"
	"fmt"
	"log"
)

func main() {
	// 1. Сторона отправителя: генерация ключей и подпись
	senderPrivKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		log.Fatalf("Ошибка генерации ключа: %v", err)
	}

	payload := []byte("ACTION=TRANSFER&FROM=USER_101&TO=USER_909&AMOUNT=45000")
	digest := sha256.Sum256(payload)

	pssOpts := &rsa.PSSOptions{
		SaltLength: rsa.PSSSaltLengthAuto,
		Hash:       crypto.SHA256,
	}

	signature, err := rsa.SignPSS(rand.Reader, senderPrivKey, crypto.SHA256, digest[:], pssOpts)
	if err != nil {
		log.Fatalf("Ошибка создания подписи: %v", err)
	}

	// 2. Сторона получателя: проверка открытым ключом отправителя
	pubKey := &senderPrivKey.PublicKey

	fmt.Println("=== Сценарий 1: Проверка легитимного сообщения ===")
	err = rsa.VerifyPSS(pubKey, crypto.SHA256, digest[:], signature, pssOpts)
	if err == nil {
		fmt.Println("Результат: ПОДПИСЬ ВАЛИДНА (Целостность и авторство гарантированы)")
	}

	fmt.Println("\n=== Сценарий 2: Подмена данных (Tampering) ===")
	tamperedPayload := []byte("ACTION=TRANSFER&FROM=USER_101&TO=USER_909&AMOUNT=99000")
	tamperedDigest := sha256.Sum256(tamperedPayload)
	err = rsa.VerifyPSS(pubKey, crypto.SHA256, tamperedDigest[:], signature, pssOpts)
	if errors.Is(err, rsa.ErrVerification) {
		fmt.Println("Результат: ОТКЛОНЕНО (Обнаружена подмена исходного текста)")
	}

	fmt.Println("\n=== Сценарий 3: Повреждение байтов самой подписи ===")
	corruptedSig := make([]byte, len(signature))
	copy(corruptedSig, signature)
	corruptedSig[10] ^= 0xFF // инвертируем биты одного байта
	err = rsa.VerifyPSS(pubKey, crypto.SHA256, digest[:], corruptedSig, pssOpts)
	if errors.Is(err, rsa.ErrVerification) {
		fmt.Println("Результат: ОТКЛОНЕНО (Подпись повреждена или сфальсифицирована)")
	}

	fmt.Println("\n=== Сценарий 4: Проверка чужим открытым ключом ===")
	anotherKey, _ := rsa.GenerateKey(rand.Reader, 2048)
	err = rsa.VerifyPSS(&anotherKey.PublicKey, crypto.SHA256, digest[:], signature, pssOpts)
	if errors.Is(err, rsa.ErrVerification) {
		fmt.Println("Результат: ОТКЛОНЕНО (Подпись не соответствует данному открытому ключу)")
	}
}
```

## Под капотом

Что происходит внутри `rsa.VerifyPSS`:
1. Проверяется соответствие длины среза подписи размеру модуля \(N\) (для 2048-битного ключа длина должна быть ровно 256 байт).
2. Подпись интерпретируется как большое целое число \(S\) и возводится в степень публичной экспоненты: \(EM = S^e \pmod N\).
3. Извлекается закодированное сообщение \(EM\) (Encoded Message). Проверяется младший байт (он обязан равняться `0xbc`).
4. Из \(EM\) извлекаются замаскированный блок \(maskedDB\) и контрольный хэш \(H\).
5. Вычисляется \(dbMask = \text{MGF1}(H, \text{len}(maskedDB))\) и восстанавливается \(DB = maskedDB \oplus dbMask\).
6. Проверяются старшие биты и разделитель `0x01`, после чего извлекается соль \(salt\).
7. Заново вычисляется \(H' = \text{Hash}(00\ 00\ 00\ 00\ 00\ 00\ 00\ 00 \parallel mHash \parallel salt)\).
8. Значения \(H\) и \(H'\) сравниваются через `subtle.ConstantTimeCompare`.

## Подводные камни

1. **Несовпадение параметров SaltLength:** Если подпись сформирована с `SaltLength: rsa.PSSSaltLengthEqualsHash` (32 байта для SHA-256), а верификатор ожидает фиксированную длину соли другой размерности, верификация вернет ошибку. Рекомендуется использовать `rsa.PSSSaltLengthAuto`.
2. **Игнорирование ошибок:** Ошибочное предположение, что любая ошибка означает сетевой сбой. Ошибка `rsa.ErrVerification` свидетельствует о попытке атаки или повреждении данных.

## На собеседовании

**Вопрос с собеседования:** Почему цифровая подпись гарантирует неотказуемость (non-repudiation), а HMAC — нет?
**Ответ:** HMAC использует симметричный общий секрет (shared secret), известный как отправителю, так и получателю. Получатель, зная секрет, может сам сгенерировать любой валидный HMAC, поэтому в суде или арбитраже он не сможет доказать третьей стороне, что сообщение пришло именно от отправителя. В цифровой подписи закрытый ключ есть исключительно у отправителя, а у всех остальных — только открытый ключ, позволяющий только проверять, но не создавать подпись. Это обеспечивает математически строгую неотказуемость.
