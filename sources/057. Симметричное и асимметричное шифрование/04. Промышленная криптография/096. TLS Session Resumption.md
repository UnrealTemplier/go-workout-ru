# TLS Session Resumption: Session Tickets (RFC 5077) и оптимизация Handshake Latency

## Условие

**TLS session tickets**: Настройте session resumption для снижения handshake latency.

## Теория

Полное TLS-рукопожатие (Full Handshake) требует от 1 до 2 сетевых RTT (Round Trip Time) и тяжелых криптографических вычислений асимметричной математики (ECDHE / RSA). При пинге до мобильного клиента 50–100 мс рукопожатие может занимать 200–300 мс до отправки первого полезного байта данных.

**TLS Session Resumption (возобновление сессии):**
1. **Session IDs (RFC 5246):** Сервер сохраняет ID сессии в оперативной памяти (Stateful). Не масштабируется на распределенные кластеры без распределенного кэша Redis/Memcached.
2. **Session Tickets (RFC 5077 / TLS 1.3 PSK):** Сервер шифрует параметры сессии (сессионный ключ, версию TLS, шифр) специальным симметричным ключом сервера (Session Ticket Encryption Key, STEK) и отдает зашифрованный тикет клиенту (Stateless). При повторном визите клиент отправляет тикет обратно, сервер расшифровывает его локально и возобновляет защищенную сессию за **0-RTT или 1-RTT**!

В Go в `tls.Config`:
- `SessionTicketsDisabled: false` (включено по умолчанию).
- `SetSessionTicketKeys([][32]byte)` — установка и ротация ключей шифрования тикетов для группы серверов.

## Решение по шагам

1. Сгенерируйте общий 32-байтный сессионный ключ STEK.
2. Настройте `tls.Config` сервера с установкой этого ключа через `SetSessionTicketKeys`.
3. Сконфигурируйте клиента с включенным `ClientSessionCache` (`tls.NewLRUClientSessionCache(64)`).
4. Выполните первое подключение (Full Handshake) и зафиксируйте факт отсутствия возобновления (`DidResume = false`).
5. Выполните второе подключение по тому же адресу и зафиксируйте успешное возобновление сессии (`DidResume = true`).

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"crypto/tls"
	"crypto/x509"
	"crypto/x509/pkix"
	"fmt"
	"log"
	"math/big"
	"net"
	"time"
)

func main() {
	// 1. Генерация серверного TLS сертификата
	priv, _ := rsa.GenerateKey(rand.Reader, 2048)
	template := x509.Certificate{
		SerialNumber: big.NewInt(1001),
		Subject:      pkix.Name{CommonName: "127.0.0.1"},
		IPAddresses:  []net.IP{net.ParseIP("127.0.0.1")},
		NotBefore:    time.Now().Add(-time.Hour),
		NotAfter:     time.Now().Add(time.Hour),
	}
	der, _ := x509.CreateCertificate(rand.Reader, &template, &template, &priv.PublicKey, priv)
	serverCert := tls.Certificate{Certificate: [][]byte{der}, PrivateKey: priv}

	// 2. Единый ключ шифрования сессионных тикетов (STEK)
	// В кластере этот ключ синхронизируется между всеми инстансами
	var sessionTicketKey [32]byte
	rand.Read(sessionTicketKey[:])

	serverCfg := &tls.Config{
		Certificates:           []tls.Certificate{serverCert},
		SessionTicketsDisabled: false, // Включаем Session Tickets
	}
	serverCfg.SetSessionTicketKeys([][32]byte{sessionTicketKey})

	// 3. Запуск сервера
	listener, err := tls.Listen("tcp", "127.0.0.1:0", serverCfg)
	if err != nil {
		log.Fatalf("Ошибка слушателя: %v", err)
	}
	defer listener.Close()
	serverAddr := listener.Addr().String()

	go func() {
		for {
			conn, err := listener.Accept()
			if err != nil {
				return
			}
			go func(c net.Conn) {
				defer c.Close()
				tlsConn := c.(*tls.Conn)
				_ = tlsConn.Handshake()
			}(conn)
		}
	}()

	// 4. Настройка клиента с LRU-кэшем сессий
	clientCache := tls.NewLRUClientSessionCache(32)
	clientCfg := &tls.Config{
		InsecureSkipVerify: true,
		ClientSessionCache: clientCache, // Кэшируем тикеты для повторного использования
	}

	// Первое рукопожатие: Full Handshake
	conn1, err := tls.Dial("tcp", serverAddr, clientCfg)
	if err != nil {
		log.Fatalf("Ошибка соединения 1: %v", err)
	}
	state1 := conn1.ConnectionState()
	conn1.Close()

	fmt.Println("=== Первое рукопожатие (Начальная сессия) ===")
	fmt.Printf("Версия TLS:     %s\n", tls.VersionName(state1.Version))
	fmt.Printf("Сессия возобновлена (DidResume): %v (Ожидался полный Full Handshake)\n", state1.DidResume)

	// Второе рукопожатие: Resumed Session через Session Ticket
	conn2, err := tls.Dial("tcp", serverAddr, clientCfg)
	if err != nil {
		log.Fatalf("Ошибка соединения 2: %v", err)
	}
	state2 := conn2.ConnectionState()
	conn2.Close()

	fmt.Println("\n=== Второе рукопожатие (Повторное подключение) ===")
	fmt.Printf("Версия TLS:     %s\n", tls.VersionName(state2.Version))
	fmt.Printf("Сессия возобновлена (DidResume): %v (Сессия мгновенно восстановлена!)\n", state2.DidResume)
}
```

## Под капотом

Под капотом Session Tickets в Go:
1. Ключ тикета `[32]byte` делится на две части: первые 16 байт — ключ AES-128 (или AES-256), вторые 16 байт — ключ HMAC-SHA256.
2. В конце первого успешного рукопожатия сервер генерирует сообщение `NewSessionTicket`. Сервер упаковывает структуру сессии (Master Secret, Client Identity, CipherSuite), шифрует её через AES-GCM/CBC и подписывает HMAC с помощью STEK.
3. Клиент сохраняет полученный зашифрованный блоб в памяти (`ClientSessionCache`).
4. При повторном коннекте клиент отправляет этот тикет в расширении `session_ticket` (или PSK identities в TLS 1.3).
5. Сервер расшифровывает тикет своим STEK без обращения к БД и без повторного выполнения дорогостоящих криптографических операций на эллиптических кривых.

## Подводные камни

1. **Отсутствие ротации ключей STEK:** Если STEK статичен и никогда не меняется, компрометация этого ключа в будущем позволит злоумышленнику расшифровать все сессии, сохраненные с использованием этих тикетов, нарушая Forward Secrecy. В Go `SetSessionTicketKeys` принимает срез ключей: первый используется для шифрования, остальные — только для расшифрования старых сессий.
2. **Атаки повторного воспроизведения (0-RTT Replay Attack):** В TLS 1.3 данные раннего старта 0-RTT не защищены от повторной отправки злоумышленником. Неидемпотентные POST-запросы (списание денег) категорически запрещено обрабатывать в 0-RTT.

## На собеседовании

**Вопрос с собеседования:** В чем угроза нарушения Perfect Forward Secrecy при использовании статических ключей Session Ticket Encryption Key (STEK) на балансировщиках нагрузки?
**Ответ:** Если злоумышленник перехватывает и записывает весь входящий трафик дата-центра, а через 6 месяцев похищает со статически сконфигурированного балансировщика ключ STEK, он сможет расшифровать тикеты всех сессий, извлечь из них закэшированные Master Secret и полностью расшифровать весь терабайтный архив перехваченного TLS-трафика. Чтобы этого не произошло, ключи STEK обязаны автоматически ротироваться каждые несколько часов с безопасным уничтожением старых ключей из оперативной памяти.
