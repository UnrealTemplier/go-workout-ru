# Конфигурация TLS версий и наборов шифров (Cipher Suites) в tls.Config

## Условие

**TLS версии и cipher suites**: Настройте `tls.Config` с минимумом TLS 1.2, предпочитаемо TLS 1.3. Уберите слабые cipher suites.

## Теория

Неправильная конфигурация протокола Transport Layer Security (TLS) на серверах и клиентах приводит к уязвимостям класса POODLE, BEAST, SWEET32 и атакам на понижение версии (Downgrade attacks).

Современные требования Enterprise безопасности:
1. **Запрет устаревших протоколов:** SSLv3, TLS 1.0 и TLS 1.1 должны быть безусловно запрещены. Минимальная допустимая версия — **TLS 1.2**, приоритетная — **TLS 1.3**.
2. **Исключение небезопасных шифров:** Запрещены шифры с алгоритмами RC4, DES/3DES, неаутентифицированные режимы CBC (уязвимые к padding oracle атакам Lucky Thirteen) и статический обмен ключами RSA без Forward Secrecy.
3. **Разрешенные шифры для TLS 1.2:** Только шифры на базе **ECDHE** (эллиптический обмен Диффи-Хеллмана) с аутентифицированным шифрованием **AEAD** (AES-GCM или ChaCha20-Poly1305).
4. **Особенность TLS 1.3:** В протоколе TLS 1.3 наборы шифров больше не настраиваются через параметр `tls.Config.CipherSuites`! IETF удалил все небезопасные шифры из стандарта TLS 1.3, оставив исключительно AEAD-шифры с Forward Secrecy.

## Решение по шагам

1. Создайте структуру `tls.Config`.
2. Установите `MinVersion: tls.VersionTLS12` и `MaxVersion: tls.VersionTLS13`.
3. Сконфигурируйте список стойких шифров для TLS 1.2 (`CipherSuites`), включив только ECDHE с AES-GCM и ChaCha20-Poly1305.
4. Продемонстрируйте проверку согласованного протокола и шифра при установке соединения с сервером.
5. Напишите тестовый запуск локального TLS-сервера и клиента с валидацией согласованных параметров через `tls.ConnectionState`.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/rand"
	"crypto/rsa"
	"crypto/tls"
	"crypto/x509"
	"crypto/x509/pkix"
	"fmt"
	"log"
	"math/big"
	"net"
	"time"
)

// secureTLSConfig возвращает эталонную безопасную конфигурацию TLS для HighLoad сервисов
func secureTLSConfig(cert tls.Certificate) *tls.Config {
	return &tls.Config{
		Certificates: []tls.Certificate{cert},
		// 1. Запрещаем устаревшие протоколы (TLS 1.0, 1.1)
		MinVersion: tls.VersionTLS12,
		MaxVersion: tls.VersionTLS13,

		// 2. Безопасные шифры для TLS 1.2 (строго ECDHE + AEAD)
		CipherSuites: []uint16{
			tls.TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
			tls.TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,
			tls.TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305,
			tls.TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305,
			tls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,
			tls.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,
		},

		// 3. Отдаем приоритет эллиптическим кривым X25519 и P-256
		CurvePreferences: []tls.CurveID{
			tls.X25519,
			tls.CurveP256,
		},
	}
}

func main() {
	// Генерация самоподписанного сертификата на лету для демонстрации
	priv, _ := rsa.GenerateKey(rand.Reader, 2048)
	template := x509.Certificate{
		SerialNumber: big.NewInt(1),
		Subject:      pkix.Name{CommonName: "127.0.0.1"},
		IPAddresses:  []net.IP{net.ParseIP("127.0.0.1")},
		NotBefore:    time.Now().Add(-time.Hour),
		NotAfter:     time.Now().Add(time.Hour),
	}
	der, _ := x509.CreateCertificate(rand.Reader, &template, &template, &priv.PublicKey, priv)
	serverCert := tls.Certificate{Certificate: [][]byte{der}, PrivateKey: priv}

	serverCfg := secureTLSConfig(serverCert)

	// Запуск защищенного TLS слушателя
	listener, err := tls.Listen("tcp", "127.0.0.1:0", serverCfg)
	if err != nil {
		log.Fatalf("Ошибка запуска TLS сервера: %v", err)
	}
	defer listener.Close()

	serverAddr := listener.Addr().String()

	// Серверная горутина
	go func() {
		conn, err := listener.Accept()
		if err != nil {
			return
		}
		defer conn.Close()
		tlsConn := conn.(*tls.Conn)
		_ = tlsConn.Handshake()
		state := tlsConn.ConnectionState()
		fmt.Printf("[Сервер] Согласован TLS: %s, Шифр: %s\n",
			tls.VersionName(state.Version),
			tls.CipherSuiteName(state.CipherSuite))
	}()

	// Запуск защищенного TLS клиента
	clientCfg := &tls.Config{
		InsecureSkipVerify: true, // для самоподписанного IP сертификата
		MinVersion:         tls.VersionTLS12,
		MaxVersion:         tls.VersionTLS13,
	}

	conn, err := tls.Dial("tcp", serverAddr, clientCfg)
	if err != nil {
		log.Fatalf("Ошибка подключения клиента: %v", err)
	}
	defer conn.Close()

	state := conn.ConnectionState()
	fmt.Printf("[Клиент] Успешное соединение!\n")
	fmt.Printf("[Клиент] Версия TLS: %s\n", tls.VersionName(state.Version))
	fmt.Printf("[Клиент] Cipher Suite: %s\n", tls.CipherSuiteName(state.CipherSuite))
	fmt.Printf("[Клиент] Perfect Forward Secrecy: да (согласована сессия)\n")
}
```

## Под капотом

Почему в TLS 1.3 поле `CipherSuites` в структуре `tls.Config` не действует?
В TLS 1.2 набор шифров (например, `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`) определял сразу 4 вещи:
1. Алгоритм обмена ключами (ECDHE).
2. Алгоритм аутентификации сертификата (RSA).
3. Симметричный шифр и режим (AES-256-GCM).
4. Хэш-функцию PRF для вычисления сессионных ключей (SHA-384).

В TLS 1.3 архитекторы IETF ортогонализовали протокол:
- Обмен ключами вынесен в отдельное расширение `Key Share` (всегда (EC)DHE: X25519 или P-256).
- Подпись сертификата вынесена в расширение `Signature Algorithms`.
- Набор `CipherSuite` теперь определяет исключительно пару (AEAD-шифр + HMAC-хэш): `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`.
Поэтому в Go стандартные шифры TLS 1.3 включены всегда и не могут быть случайно ослаблены разработчиком.

## Подводные камни

1. **Использование PreferServerCipherSuites:** Начиная с Go 1.17+, флаг `PreferServerCipherSuites` объявлен устаревшим и игнорируется рантаймом, так как выбор лучшего шифра теперь оптимизирован аппаратно на клиенте и сервере с учетом AES-NI.
2. **Включение CBC шифров:** Шифры вроде `TLS_RSA_WITH_AES_128_CBC_SHA` катастрофически уязвимы к атакам перехвата сессии (Lucky Thirteen). Их наличие в `CipherSuites` немедленно проваливает аудит безопасности по стандартам PCI-DSS.

## На собеседовании

**Вопрос с собеседования:** Почему в современных распределенных сервисах запрещен шифр `TLS_RSA_WITH_AES_256_GCM_SHA384` без ECDHE (то есть чистый статический RSA key exchange)?
**Ответ:** Статический RSA key exchange не обеспечивает **Perfect Forward Secrecy (PFS)**. Если трафик сервиса записывается спецслужбами или злоумышленником в течение нескольких лет («Store now, decrypt later»), а затем приватный RSA-ключ сервера утечет или будет скомпрометирован по ордеру суда, весь ранее записанный терабайтный трафик за все годы будет мгновенно расшифрован. В схеме ECDHE для каждой отдельной сессии генерируются одноразовые эфемерные ключи, которые уничтожаются сразу после завершения хэндшейка, делая ретроспективное расшифрование невозможным.
