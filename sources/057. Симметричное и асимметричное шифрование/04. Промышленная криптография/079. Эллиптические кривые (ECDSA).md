# Эллиптические кривые (ECDSA): генерация ключа P-256 и подпись

## Условие

**Эллиптические кривые (ECDSA)**: RSA — медленный и ключи у него огромные. Сгенерируй ключ с помощью `crypto/ecdsa` (кривая P-256). Подпиши сообщение. Обрати внимание, насколько подпись и ключ меньше по размеру по сравнению с RSA.

## Теория

Асимметричная криптография на основе эллиптических кривых (Elliptic Curve Cryptography, ECC) базируется на сложности задачи дискретного логарифмирования в группе точек эллиптической кривой (ECDLP). 

В отличие от RSA, где стойкость опирается на факторизацию составных чисел \(N = p \cdot q\) (для которой субэкспоненциальный решеточный алгоритм GNFS требует ключи размером от 2048 до 4096 бит), в ECC наилучшие известные атаки (алгоритм \(\rho\)-Полларда) имеют экспоненциальную сложность \(O(\sqrt{n})\). В результате:
1. Ключ **P-256** (256 бит, 32 байта) обеспечивает криптостойкость ~128 бит, что эквивалентно **RSA-3072** (384 байта).
2. Подпись ECDSA состоит из пары больших целых чисел \((r, s)\) и при ASN.1 DER кодировании занимает всего 70–72 байта (против 256–512 байт у RSA).
3. Скорость генерации ключей и генерации подписи на порядки превосходит RSA.

В стандартной библиотеке Go пакет `crypto/ecdsa` предоставляет функцию `ecdsa.GenerateKey(elliptic.P256(), rand.Reader)`. Подписание осуществляется функцией `ecdsa.SignASN1(rand.Reader, privKey, digest[:])`, принимающей 32-байтный хэш (SHA-256) и возвращающей компактный срез байт в формате ASN.1 DER.

## Решение по шагам

1. Сгенерируйте пару ключей ECDSA с кривой NIST P-256 (`elliptic.P256()`).
2. Для наглядного сравнения сгенерируйте ключ RSA-2048 и сопоставьте размеры публичных ключей и приватных структур в памяти.
3. Вычислите криптографический хэш SHA-256 от исходного сообщения.
4. Создайте цифровую подпись с помощью `ecdsa.SignASN1(rand.Reader, priv, hash[:])`.
5. Проверьте размер полученной подписи (обычно 70-72 байта) и выведите её шестнадцатеричное представление.

## Код решения

**`main.go`**

```go
package main

import (
	"crypto/ecdsa"
	"crypto/elliptic"
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"crypto/x509"
	"fmt"
	"log"
)

func main() {
	// 1. Генерация ключа ECDSA P-256
	ecdsaKey, err := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	if err != nil {
		log.Fatalf("Ошибка генерации ECDSA ключа: %v", err)
	}

	// 2. Для сравнения: генерация ключа RSA-2048
	rsaKey, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		log.Fatalf("Ошибка генерации RSA ключа: %v", err)
	}

	ecdsaPubBytes, _ := x509.MarshalPKIXPublicKey(&ecdsaKey.PublicKey)
	rsaPubBytes, _ := x509.MarshalPKIXPublicKey(&rsaKey.PublicKey)

	fmt.Println("=== Сравнение размеров ключей ===")
	fmt.Printf("ECDSA P-256 Public Key (PKIX DER): %d байт\n", len(ecdsaPubBytes))
	fmt.Printf("RSA-2048 Public Key (PKIX DER):    %d байт\n\n", len(rsaPubBytes))

	// 3. Подготовка данных и вычисление хэша
	msg := []byte("Аудит транзакции #490219: перевод 500_000 RUB утвержден.")
	hash := sha256.Sum256(msg)

	// 4. Подпись сообщения через ecdsa.SignASN1
	sig, err := ecdsa.SignASN1(rand.Reader, ecdsaKey, hash[:])
	if err != nil {
		log.Fatalf("Ошибка формирования подписи ECDSA: %v", err)
	}

	fmt.Println("=== Цифровая подпись ECDSA ===")
	fmt.Printf("Размер подписи (ASN.1 DER): %d байт\n", len(sig))
	fmt.Printf("Hex подписи: %x\n", sig)

	// 5. Верификация подписи
	valid := ecdsa.VerifyASN1(&ecdsaKey.PublicKey, hash[:], sig)
	fmt.Printf("Результат верификации: %v\n", valid)
}
```

## Под капотом

Под капотом `ecdsa.SignASN1` выполняет следующие математические операции над эллиптической кривой \(y^2 = x^3 - 3x + b \pmod p\):
1. Генерируется эфемерный случайный скаляр \(k \in [1, n-1]\) с помощью криптографического ГСЧ `rand.Reader`.
2. Вычисляется точка \(R = k \cdot G = (x_1, y_1)\), где \(G\) — базовая порождающая точка кривой.
3. Координата \(r = x_1 \pmod n\). Если \(r = 0\), выбирается новое \(k\).
4. Вычисляется скаляр \(s = k^{-1} (z + r \cdot d) \pmod n\), где \(z\) — числовое значение хэша сообщения, \(d\) — приватный ключ.
5. Пара \((r, s)\) упаковывается в стандартную ASN.1 SEQUENCE из двух INTEGER.

В Go 1.20+ реализация P-256 переписана на ассемблере с использованием инструкций постоянного времени (constant-time), полностью предотвращая тайминг-атаки по сторонним каналам (Cache-timing side channels).

## Подводные камни

1. **Повторное использование \(k\) (Nonce Reuse):** Если для двух разных сообщений подписать хэши с одним и тем же \(k\), приватный ключ \(d\) тривиально восстанавливается элементарной алгеброй: \(d = (s_1 z_2 - s_2 z_1) / (s_2 r - s_1 r) \pmod n\). Именно эта ошибка привела к взлому консоли Sony PlayStation 3.
2. **Передача сырого сообщения вместо хэша:** `ecdsa.SignASN1` ожидает дайджест фиксированной длины (хэш), а не произвольный текст. Если передать длинный текст напрямую, он будет урезан до размера порядка кривой.
3. **Malleability (пластичность) подписи:** Для точки \((r, s)\) пара \((r, -s \pmod n)\) также является валидной подписью. В финансовых протоколах (Bitcoin, Ethereum) это предотвращается требованием «Low-S» (s <= n/2).

## На собеседовании

**Вопрос с собеседования:** Почему в мобильных клиентах и IoT-устройствах BigTech-компании переходят с RSA на ECDSA/Ed25519?
**Ответ:** 1) **Размер трафика и пропускная способность:** Ключ ECDSA P-256 занимает ~91 байт против 294 байт у RSA-2048, а подпись — ~71 байт против 256 байт. При миллионах TLS-хэндшейков или сетевых запросов в секунду это экономит терабайты сетевого трафика. 2) **Энергоэффективность и CPU:** Генерация ключей и подпись на эллиптических кривых требуют значительно меньше процессорных циклов и батареи мобильного устройства, чем возведение в степень 2048-битных чисел RSA.
