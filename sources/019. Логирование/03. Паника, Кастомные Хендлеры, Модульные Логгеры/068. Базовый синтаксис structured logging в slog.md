# Базовый синтаксис structured logging в slog с парами ключ-значение

## Условие

**Структурированный `slog` (База)**: Сделайте импорт современного пакета `log/slog` (доступен в современных версиях Go). Напишите вывод информационного лога `slog.Info`, передав туда сообщение и дополнительные параметры в виде пар "ключ-значение" (например, `slog.Info("user logged in", "user_id", 42, "ip", "127.0.0.1")`).

## Теория

Вариативные аргументы в `slog.Info(msg, ...any)` чередуются парами: нечетные параметры являются строковыми именами ключей, четные — значениями любых типов.

## Решение по шагам

1. Импортируем `"log/slog"`.
2. Вызовем `slog.Info("user logged in", "user_id", 42, "ip", "127.0.0.1", "is_admin", true)`.
3. В `main` убедимся в правильности форматирования.

## Код решения

**`main.go`**

```go
package main

import (
	"log/slog"
)

func main() {
	// Базовый вывод пар ключ-значение
	slog.Info("user logged in",
		"user_id", 42,
		"ip", "127.0.0.1",
		"is_admin", true,
	)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 2026/09/02 18:40:00 INFO user logged in user_id=42 ip=127.0.0.1 is_admin=true
```

## Под капотом

`slog` не использует строковую интерполяцию, передавая ключи и значения напрямую в парсер хендлера.

## Подводные камни

Ключи всегда должны быть строками (`string`). Передача числа в качестве ключа приведет к автоматическому форматированию имени ключа `!BADKEY`.

## На собеседовании

**Вопрос с собеседования:** «Почему slog.Info("user login", "id", 42) лучше, чем log.Printf("user login: id=%d", 42)?»
**Ответ:** Потому что поля `id` и `42` сохраняют свою семантическую структуру. При смене хендлера на JSON лог запишется как `{"id": 42}`, готовый к фильтрации в Kibana/Loki без регулярных выражений.
