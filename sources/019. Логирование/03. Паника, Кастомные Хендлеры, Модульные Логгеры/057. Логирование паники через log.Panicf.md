# Логирование паники через log.Panicf и восстановление через recover

## Условие

Используй `log.Panicf("Unexpected: %v", err)`. Покажи разницу с `Fatalf`: `panic` можно `recover`, `log.Fatalf` — нет (мгновенный выход).

### Исходная формулировка

Используй `log.Panicf("Unexpected: %v", err)`. Покажи разницу с `Fatalf`: `panic` можно `recover`, `log.Fatalf` — нет (мгновенный выход).

---

## Теория

`log.Panicf` форматирует строку, записывает её в поток логов и вызывает встроенную панику `panic(msg)`. Это позволяет раскрутить стек вызовов и перехватить ошибку через `recover()` в `defer` функции.

## Решение по шагам

1. Запустим защищенную функцию с `defer func() { if r := recover(); r != nil { ... } }()`.
2. Вызовем `log.Panicf`.
3. Перехватим панику и продолжим выполнение программы.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
)

func safeWorker() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("[RECOVERED] Паника успешно перехвачена: %v\n", r)
		}
	}()

	err := errors.New("некорректный формат токена JWT")
	log.Panicf("Фатальная ошибка парсинга: %v", err)

	fmt.Println("Этот код не выполнится")
}

func main() {
	log.Println("Старт программы")
	safeWorker()
	log.Println("Программа успешно продолжила работу после recover!")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 2026/09/02 18:40:00 Старт программы
# 2026/09/02 18:40:00 Фатальная ошибка парсинга: некорректный формат токена JWT
# [RECOVERED] Паника успешно перехвачена: Фатальная ошибка парсинга: некорректный формат токена JWT
# 2026/09/02 18:40:00 Программа успешно продолжила работу после recover!
```

## Под капотом

`log.Panicf` генерирует панику со строкой, сформированной `fmt.Sprintf`.

## Подводные камни

`log.Fatalf` невозможно перехватить через `recover()`, так как `os.Exit` не вызывает панику, а напрямую прерывает процесс.

## На собеседовании

**Вопрос с собеседования:** «Когда следует использовать log.Panicf вместо log.Fatalf?»
**Ответ:** `log.Panicf` используется внутри транзакционных обработчиков или фоновых воркеров, где сбой одной горутины должен быть залогирован и изолирован через `recover()`, не роняя весь HTTP-сервер.
