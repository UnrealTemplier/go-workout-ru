# Комплексная связка: UserService с валидацией, хранилищем и логированием slog

## Условие

Свяжите всё вместе: создайте структуру `UserService` с методом `CreateUser`. Он должен валидировать данные (возвращая кастомную ошибку), записывать пользователя в мапу (эмуляция БД) и логировать успех или провал через `slog`.

### Исходная формулировка

Свяжите всё вместе: создайте структуру `UserService` с методом `CreateUser`. Он должен валидировать данные (возвращая кастомную ошибку), записывать пользователя в мапу (эмуляция БД) и логировать успех или провал через `slog`.

## Теория

Архитектура бизнес-сервиса объединяет валидацию входных данных (DTO Validation), доменные ошибки, хранилище данных и структурированное логирование всех операций.

## Решение по шагам

1. Объявим структуру `UserDTO{Email, Role}` и кастомную ошибку `ValidationError`.
2. Создадим `UserService` с `sync.RWMutex`, `map[int]UserDTO` и `*slog.Logger`.
3. В методе `CreateUser` выполним валидацию, запись и логирование.
4. В `main` протестируем успешный и ошибочный сценарии.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log/slog"
	"os"
	"strings"
	"sync"
)

var (
	ErrInvalidEmail = errors.New("некорректный email адрес")
	ErrInvalidRole  = errors.New("недопустимая роль пользователя")
)

type UserDTO struct {
	ID    int
	Email string
	Role  string
}

type UserService struct {
	mu     sync.RWMutex
	users  map[int]UserDTO
	nextID int
	logger *slog.Logger
}

func NewUserService(logger *slog.Logger) *UserService {
	return &UserService{
		users:  make(map[int]UserDTO),
		nextID: 1,
		logger: logger.With(slog.String("service", "UserService")),
	}
}

func (s *UserService) CreateUser(email, role string) (UserDTO, error) {
	// 1. Валидация
	if !strings.Contains(email, "@") {
		s.logger.Warn("Неуспешная попытка создания пользователя: невалидный email",
			slog.String("email", email),
			slog.String("error", ErrInvalidEmail.Error()),
		)
		return UserDTO{}, ErrInvalidEmail
	}

	if role != "admin" && role != "user" {
		s.logger.Warn("Неуспешная попытка создания: неизвестная роль",
			slog.String("email", email),
			slog.String("role", role),
		)
		return UserDTO{}, ErrInvalidRole
	}

	// 2. Запись в хранилище под блокировкой
	s.mu.Lock()
	user := UserDTO{ID: s.nextID, Email: email, Role: role}
	s.users[user.ID] = user
	s.nextID++
	s.mu.Unlock()

	// 3. Успешный лог
	s.logger.Info("Пользователь успешно зарегистрирован",
		slog.Int("user_id", user.ID),
		slog.String("email", user.Email),
		slog.String("role", user.Role),
	)

	return user, nil
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	svc := NewUserService(logger)

	fmt.Println("=== 1. Успешное создание пользователя ===")
	_, _ = svc.CreateUser("alex@company.ru", "admin")

	fmt.Println("\n=== 2. Ошибка валидации email ===")
	_, _ = svc.CreateUser("bad-email-format", "user")

	fmt.Println("\n=== 3. Ошибка валидации роли ===")
	_, _ = svc.CreateUser("john@corp.io", "superhero")
}
```

## Под капотом

`sync.RWMutex` защищает внутреннюю мапу от состояния гонки при параллельных запросах.

## Подводные камни

Не логируйте ошибки валидации с уровнем `ERROR` — ошибки пользовательского ввода являются штатной ситуацией (`LevelWarn` или `LevelInfo`). Уровень `ERROR` резервируется для системных сбоев инфраструктуры.

## На собеседовании

**Вопрос с собеседования:** «Почему ошибки клиентской валидации (4xx) нужно логировать как WARN/INFO, а не ERROR?»
**Ответ:** Ошибки уровня ERROR служат триггером для алертов дежурным инженерам SRE. Если логировать неверные пароли пользователей как ERROR, сервис будет генерировать ложные ночные алерты.
