# Аварийное завершение процесса через log.Fatalf с кодом 1

## Условие

Вызови `log.Fatalf("Fatal error: %v", err)`. Убедись, что программа завершается с кодом 1 после записи лога.

## Теория

`log.Fatalf` записывает форматированное сообщение в лог и немедленно завершает работу всей программы вызовом `os.Exit(1)`. При этом ни один зарегистрированный оператор `defer` **не выполняется**.

## Решение по шагам

1. Зарегистрируем отложенный вызов `defer fmt.Println("Этот defer НЕ выполнится!")`.
2. Запишем лог через `log.Fatalf(...)`.
3. Убедимся, что процесс завершился с кодом 1.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
)

func main() {
	defer fmt.Println("[DEFER] Этот код никогда не выполнится из-за os.Exit(1)")

	err := errors.New("порт 8080 уже занят другим процессом")

	log.Println("[INFO] Попытка запуска HTTP-сервера...")
	log.Fatalf("Критический сбой инициализации: %v", err)

	fmt.Println("Этот код также недостижим")
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# 2026/09/02 18:40:00 [INFO] Попытка запуска HTTP-сервера...
# 2026/09/02 18:40:00 Критический сбой инициализации: порт 8080 уже занят другим процессом
# exit status 1
```

## Под капотом

`log.Fatalf` внутри выполняет `l.Output(2, fmt.Sprintf(format, v...))` и затем вызывает `os.Exit(1)`.

## Подводные камни

Никогда не используйте `log.Fatal` внутри библиотечных пакетов или вспомогательных функций — фатальный выход разрешен только в функции `main()`.

## На собеседовании

**Вопрос с собеседования:** «Почему вызов log.Fatal в HTTP-обработчике является грубейшей ошибкой?»
**Ответ:** Потому что `log.Fatal` не просто прерывает обработку одного HTTP-запроса, а мгновенно роняет весь веб-сервер и все параллельно выполняющиеся запросы тысяч пользователей.
