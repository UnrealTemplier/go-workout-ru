# Реализация архитектуры Incident Response Workflow в SRE

## Условие

Реализуй **Incident Response Workflow**:
- Alert fires: `HighLatency p95 > 500ms`
- Automated: create incident in PagerDuty, Slack channel `#incidents-2026-07-03`
- Runbook: "1. Check Grafana dashboard. 2. Check recent deployments. 3. Check error logs."
- Human: identify root cause (bad deployment), rollback
- Post-mortem: timeline, root cause, action items, publish in Wiki
- Metrics: MTTR (Mean Time To Recovery), MTBF (Mean Time Between Failures)

## Теория

Incident Response Workflow — стандарт управления инцидентами в BigTech (Google SRE, Яндекс, Ozon). При срабатывании алерта автоматика создает инцидент, инженер выполняет шаги по Runbook, организуется Rollback и формируется Post-Mortem.

## Решение по шагам

1. Создадим структуру `IncidentWorkflow`.
2. Реализуем фазы: `TriggerAlert`, `CreateChannels`, `ExecuteRunbook`, `MitigateRollback`, `GeneratePostMortem`.
3. В `main` смоделируем прохождение полного инцидента.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log/slog"
	"os"
	"time"
)

type Incident struct {
	ID        string
	AlertName string
	StartTime time.Time
	EndTime   time.Time
	RootCause string
}

func (inc *Incident) Resolve(cause string) {
	inc.EndTime = time.Now()
	inc.RootCause = cause
}

func (inc *Incident) MTTR() time.Duration {
	return inc.EndTime.Sub(inc.StartTime)
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	// 1. Alert fires
	incident := Incident{
		ID:        "INC-88912",
		AlertName: "HighLatency p95 > 500ms",
		StartTime: time.Now().Add(-12 * time.Minute),
	}

	logger.Error("PAGERDUTY ALERT TRIGGERED",
		slog.String("incident_id", incident.ID),
		slog.String("alert", incident.AlertName),
		slog.String("slack_channel", "#incidents-2026-09-02"),
	)

	// 2. Runbook & Mitigation
	fmt.Println("\n--- Runbook Checklist ---")
	fmt.Println(" [x] 1. Check Grafana dashboard (Latency spike detected)")
	fmt.Println(" [x] 2. Check recent deployments (v2.14.1 deployed 15m ago)")
	fmt.Println(" [x] 3. Check error logs (DB index missing)")
	fmt.Println(" [x] 4. Mitigation: Rollback to v2.14.0 executed")

	// 3. Resolution
	incident.Resolve("Bad deployment v2.14.1 (unindexed query)")

	logger.Info("INCIDENT RESOLVED",
		slog.String("incident_id", incident.ID),
		slog.Duration("mttr", incident.MTTR()),
		slog.String("root_cause", incident.RootCause),
	)

	// 4. Post-Mortem Summary
	fmt.Println("\n=== Post-Mortem Summary ===")
	fmt.Printf("Incident ID: %s\n", incident.ID)
	fmt.Printf("MTTR (Mean Time To Recovery): %v\n", incident.MTTR())
	fmt.Printf("Root Cause: %s\n", incident.RootCause)
	fmt.Println("Action Items: Add linter check for missing DB indexes in CI/CD pipeline")
}
```

## Под капотом

Метрика MTTR (Mean Time To Recovery) измеряет время от момента возникновения инцидента до полного восстановления сервиса.

## Подводные камни

Культура Blameless Post-Mortem (безупречный разбор полетов) фокусируется на улучшении процессов и автоматики, а не на поиске виноватых людей.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между MTTR и MTBF в SRE?»
**Ответ:** MTTR (Mean Time To Recovery) — среднее время ликвидации аварии. MTBF (Mean Time Between Failures) — среднее время безаварийной работы системы между сбоями.
