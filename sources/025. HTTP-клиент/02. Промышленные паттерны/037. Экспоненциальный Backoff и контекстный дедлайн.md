# Экспоненциальный Backoff и контекстный дедлайн в цикле повторных запросов

## Условие

Напиши **retry logic** для HTTP-клиента: при ошибке сети или статусе `5xx` — повтори запрос с exponential backoff (100ms, 200ms, 400ms, max 3 попытки). Используй `context` для ограничения общего времени.

## Теория

Паттерн Exponential Backoff with Jitter: интервал между повторными попытками увеличивается вдвое на каждом шаге (\(T, 2T, 4T\)), предотвращая эффект громоподобного стада (Thundering Herd Problem) при восстановлении упавшего сервиса.

## Решение по шагам

1. Создадим контекст с общим дедлайном 500 мс.
2. Реализуем цикл ретраев с удвоением `backoff *= 2`.
3. Сервер имитирует 503 на первых 2 попытках и 200 OK на 3-й.
4. Проверим успешную доставку.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"time"
)

func executeWithBackoff(ctx context.Context, client *http.Client, url string) (string, error) {
	backoff := 25 * time.Millisecond
	const maxRetries = 3

	for attempt := 1; attempt <= maxRetries; attempt++ {
		req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
		if err != nil {
			return "", err
		}

		resp, err := client.Do(req)
		if err == nil && resp.StatusCode < 500 {
			defer resp.Body.Close()
			body, _ := io.ReadAll(resp.Body)
			return string(body), nil
		}

		if resp != nil {
			_, _ = io.Copy(io.Discard, resp.Body)
			_ = resp.Body.Close()
		}

		fmt.Printf(" [!] Попытка #%d не удалась. Пауза %v перед повтором...\n", attempt, backoff)

		select {
		case <-time.After(backoff):
			backoff *= 2
		case <-ctx.Done():
			return "", ctx.Err()
		}
	}
	return "", fmt.Errorf("все попытки исчерпаны")
}

func main() {
	tries := 0
	ts := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		tries++
		if tries < 3 {
			w.WriteHeader(http.StatusBadGateway) // 502
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("FINAL_SUCCESS_RESULT"))
	}))
	defer ts.Close()

	client := &http.Client{}
	ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
	defer cancel()

	result, err := executeWithBackoff(ctx, client, ts.URL)
	if err != nil {
		panic(err)
	}

	fmt.Printf("[Client] Успешный результат после ретраев: %s\n", result)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
#  [!] Попытка #1 не удалась. Пауза 25ms перед повтором...
#  [!] Попытка #2 не удалась. Пауза 50ms перед повтором...
# [Client] Успешный результат после ретраев: FINAL_SUCCESS_RESULT
```

## Под капотом

`select` с `ctx.Done()` гарантирует, что сон `time.After` прервется немедленно, если истечет общий дедлайн родительской операции.

## Подводные камни

В реальных HighLoad сервисах к backoff обязательно добавляют случайный шум (Jitter: \(\pm 20\%\)), чтобы тысячи клиентов не просыпались синхронно.

## На собеседовании

**Вопрос с собеседования:** «Зачем нужен Full Jitter при реализации алгоритма Exponential Backoff?»
**Ответ:** Если сервер упал и перезагрузился, клиенты с фиксированным backoff будут слать повторные запросы синхронными волнами (Thundering Herd), снова роняя сервер. Full Jitter распределяет время ретраев равномерно по интервалу \([0, \text{backoff}]\), размазывая нагрузку во времени.
