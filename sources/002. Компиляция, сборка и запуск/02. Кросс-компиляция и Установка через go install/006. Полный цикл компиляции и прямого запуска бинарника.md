# Полный цикл компиляции и прямого запуска бинарника

## Условие

Скомпилируй программу в бинарный файл с помощью `go build`. Запусти полученный исполняемый файл напрямую из консоли.

## Теория

Закрепляем разницу в жизненном цикле:
1. `go build` выполняется на машине разработчика или в сборочном контуре CI;
2. На сервер деплоится **только один бинарник**;
3. Запуск осуществляется через systemd, Docker или напрямую `./app`.

## Решение по шагам

1. Компилируем проект: `go build -o app .`.
2. Запускаем: `./app`.

## Код решения

**`Терминал`**

```bash
go build -o app .
./app
# Hello, World!
```

ℹ️ Сборка и вызов

## Под капотом

Операционная система через системный вызов `execve` загружает ELF-файл в адресное пространство нового процесса, инициализирует регистры и передает управление точке входа `_rt0_amd64_linux`.

## Подводные камни

- Попытка запуска бинарника другой архитектуры (например, запуск ARM64-бинарника на x86_64) приведет к ошибке ядра: `cannot execute binary file: Exec format error`.

## На собеседовании

**Вопрос с собеседования:** «Что делает системная точка входа `_rt0_amd64_linux` в рантайме Go?»
**Ответ:** Она считывает аргументы `argc`/`argv` из стека ядра, инициализирует структуру `m0` (главный поток ОС), `g0` (системная горутина стека), настраивает сборщик мусора и запускает планировщик `runtime.schedinit()`.
