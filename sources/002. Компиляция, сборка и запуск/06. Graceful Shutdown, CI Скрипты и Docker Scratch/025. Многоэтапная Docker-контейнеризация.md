# Многоэтапная Docker-контейнеризация: от Alpine к 5 МБ Scratch

## Условие

Создай Docker-контейнер для Go-приложения (multi-stage build). Первый этап — сборка, второй — минимальный образ scratch или alpine с бинарником.

### Исходная формулировка

Создай Docker-контейнер для Go-приложения (multi-stage build). Первый этап — сборка, второй — минимальный образ `scratch` или `alpine` с бинарником.

## Теория

**Multi-Stage Builds (Многоэтапная сборка Docker):**
В Go нет необходимости тащить компилятор, Git и Go SDK в продакшен-образ контейнера!

Двухэтапная сборка:
1. **Этап 1 (Builder):** образ `golang:1.22-alpine` компилирует статический бинарник (`CGO_ENABLED=0`).
2. **Этап 2 (Runner):** абсолютно пустой образ `FROM scratch` (размер 0 байт) или минимальный `alpine` (5 МБ). В него копируется **только один скомпилированный бинарник** и системные SSL-сертификаты (`ca-certificates`).

Итоговый размер Docker-образа составляет всего **10–15 МБ** вместо 1 ГБ!

## Решение по шагам

1. Создаем файл `Dockerfile`.
2. Описываем стадию сборщика `AS builder`.
3. Описываем стадию финального образа `FROM scratch`.
4. Собираем и проверяем размер образа командой `docker build -t myapp:latest .`.

## Код решения

**`Dockerfile`**

```dockerfile
# ==========================================
# ЭТАП 1: Сборщик (Builder)
# ==========================================
FROM golang:1.22-alpine AS builder

# Установка корневых сертификатов для исходящих HTTPS-запросов
RUN apk --no-cache add ca-certificates tzdata

WORKDIR /app

# Кэширование слоя зависимостей
COPY go.mod go.sum* ./
RUN go mod download

# Копирование исходного кода
COPY . .

# Статическая компиляция бинарника без CGO
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build \
    -ldflags="-s -w -X main.Version=v1.0.0" \
    -o /bin/server .

# ==========================================
# ЭТАП 2: Минимальный продакшен-образ
# ==========================================
FROM scratch

# Копируем сертификаты и таймзоны из сборочного образа
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /usr/share/zoneinfo /usr/share/zoneinfo
COPY --from=builder /bin/server /server

# Запуск от непривилегированного пользователя nobody (UID 65534)
USER 65534:65534

EXPOSE 8080

ENTRYPOINT ["/server"]
```

ℹ️ Production-grade Dockerfile для Go

**`Терминал`**

```bash
# Сборка Docker-образа
docker build -t go-service:v1 .

# Проверка размера образа
docker images go-service:v1
# REPOSITORY   TAG       IMAGE ID       SIZE
# go-service   v1        a1b2c3d4e5f6   12.4MB

# Запуск контейнера
docker run -p 8080:8080 go-service:v1
```

## Под капотом

Образ `scratch` — зарезервированное ключевое слово Docker, означающее пустую файловую систему. Статический Go-бинарник общается с ядром хостовой Linux-машины напрямую через системные вызовы syscall, не требуя ни `glibc`, ни оболочки `/bin/sh`.

## Подводные камни

- Если ваше приложение делает исходящие HTTPS-запросы к внешним API (например, к Telegram Bot API или платежному шлюзу), в образе `FROM scratch` **обязательно должен быть файл `ca-certificates.crt`**, иначе любые TLS-рукопожатия завершатся ошибкой `x509: certificate signed by unknown authority`.

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшен Dockerfile на этапе `FROM scratch` обязательно указывают `USER 65534:65534`?»
**Ответ:** По умолчанию контейнеры запускаются от пользователя `root` (UID 0). Если злоумышленник найдет уязвимость в приложении и выполнит побег из контейнера (Container Escape), он получит права root на хостовой ноде Kubernetes. Запуск от непривилегированного пользователя `nobody` (UID 65534) — базовый стандарт безопасности DevSecOps.
