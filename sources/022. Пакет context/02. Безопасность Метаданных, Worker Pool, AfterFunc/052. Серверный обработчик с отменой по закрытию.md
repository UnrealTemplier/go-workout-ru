# Серверный обработчик с отменой по закрытию соединения браузером (Высокая сложность)

## Условие

**[Высокая сложность]**: Напиши HTTP-сервер (используй `net/http`). Внутри обработчика бери `r.Context()`. Запусти долгую обработку (sleep 10s). Закрой клиент браузер до завершения. Убедись, что контекст запроса отменяется, и обработчик на сервере завершается досрочно.

## Теория

Комплексный production-сценарий: полноценный HTTP-сервер на базе `net/http` с обработчиком, реагирующим на обрыв клиентского соединения. Если клиент закрыл вкладку или потерял сеть, `r.Context().Done()` закрывается, сервер логирует обрыв и немедленно прекращает нагружать БД и процессор.

## Решение по шагам

1. Создадим HTTP-сервер с обработчиком `/api/long-process`.
2. Внутри обработчика считываем `ctx := r.Context()`.
3. В цикле с шагами по 20 мс проверяем `<-ctx.Done()`.
4. Запустим тестовый HTTP-клиент, который отправляет запрос и обрывает TCP-соединение через 30 мс.
5. Зафиксируем на стороне сервера досрочную отмену запроса.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func longRunningAPIHandler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	fmt.Println("[HTTP-Server] Начало выполнения тяжелой бизнес-транзакции...")

	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	for step := 1; step <= 10; step++ {
		select {
		case <-ctx.Done(): // СРАБАТЫВАЕТ, КОГДА КЛИЕНТ ЗАКРЫЛ ВКЛАДКУ / СОЕДИНЕНИЕ!
			fmt.Printf("[HTTP-Server] КЛИЕНТ ОТВАЛИЛСЯ (%v)! Откат транзакции на шаге %d/10.\n", ctx.Err(), step)
			return
		case <-ticker.C:
			fmt.Printf(" [HTTP-Server] Обработка шага %d/10...\n", step)
		}
	}

	fmt.Fprintln(w, "Успешный результат")
}

func main() {
	// 1. Запуск тестового сервера
	server := httptest.NewServer(http.HandlerFunc(longRunningAPIHandler))
	defer server.Close()

	fmt.Printf("[Main] Тестовый сервер запущен на %s\n\n", server.URL)

	// 2. Имитация клиента, обрывающего соединение через 45 мс
	clientCtx, clientCancel := context.WithTimeout(context.Background(), 45*time.Millisecond)
	defer clientCancel()

	req, err := http.NewRequestWithContext(clientCtx, http.MethodGet, server.URL+"/api/long-process", nil)
	if err != nil {
		panic(err)
	}

	fmt.Println("[HTTP-Client] Отправка запроса с жестким таймаутом клиента 45мс...")
	_, err = http.DefaultClient.Do(req)
	if err != nil {
		fmt.Printf("[HTTP-Client] Клиент разорвал соединение: %v\n\n", err)
	}

	// Даем серверу время зафиксировать отмену и очистить ресурсы
	time.Sleep(50 * time.Millisecond)
	fmt.Println("[Main] Тест успешно завершен: сервер предотвратил бесполезную трату CPU и RAM.")
}
```

## Под капотом

Транспортный слой сервера перехватывает разрыв TCP сокета (`io.EOF`/`RST`) и вызывает внутреннюю функцию отмены контекста запроса `cancelCtx.cancel()`.

## Подводные камни

Если передавать `context.Background()` в подзапросы БД вместо `r.Context()`, то база данных продолжит выполнять тяжелый SQL-запрос даже после отключения клиента.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисной архитектуре жизненно необходимо пробрасывать r.Context() во все нижележащие вызовы (SQL, Redis, gRPC)?»
**Ответ:** Это предотвращает феномен лавинной перегрузки (Cascading Failures / Thundering Herd): при отмене клиентского запроса на балансировщике отмена мгновенно распространяется по всему дереву вызовов, разгружая тысячи серверов базы данных и внутренних сервисов.
