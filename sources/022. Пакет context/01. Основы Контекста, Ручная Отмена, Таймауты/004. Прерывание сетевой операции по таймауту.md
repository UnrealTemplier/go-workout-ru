# Прерывание сетевой операции по таймауту context.WithTimeout

## Условие

Используй `context.WithTimeout()`. Запусти HTTP-запрос (или `time.Sleep`) в горутине. Если не успевает за 2 секунды — `ctx.Done()` срабатывает, программа выводит `"timeout"`.

## Теория

Шаблон асинхронного ожидания: запуск задачи в горутине с одновременным прослушиванием `<-ctx.Done()` в главном потоке.

## Решение по шагам

1. Создадим `ctx, cancel := context.WithTimeout(context.Background(), 30*time.Millisecond)`.
2. Запустим фоновую задачу, длящуюся 100 мс, возвращающую результат в канал.
3. В `select` дождемся либо результата, либо `<-ctx.Done()`.
4. Выведем сообщение `"timeout"`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Millisecond)
	defer cancel()

	resultChan := make(chan string, 1) // Буфер = 1 исключает утечку горутины

	go func() {
		time.Sleep(100 * time.Millisecond) // Симуляция долгого I/O
		resultChan <- "HTTP 200 OK: Data Received"
	}()

	select {
	case res := <-resultChan:
		fmt.Printf("Результат: %s\n", res)
	case <-ctx.Done():
		fmt.Printf("timeout: Операция прервана по дедлайну (%v)\n", ctx.Err())
	}
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# timeout: Операция прервана по дедлайну (context deadline exceeded)
```

## Под капотом

`<-ctx.Done()` разблокирует `select` без аллокаций памяти.

## Подводные камни

Всегда делайте канал `resultChan` буферизованным (`make(chan T, 1)`), чтобы фоновая горутина не зависла навсегда при срабатывании таймаута.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если вызвать cancel() дважды на одном контексте?»
**Ответ:** Ничего плохого: функция `cancel()` абсолютно идемпотентна. Повторные вызовы мгновенно завершаются без паник и повторных блокировок.
