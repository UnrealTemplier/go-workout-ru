# Сага с паттерном Outbox (Saga with Outbox): атомарный коммит в БД и гарантированная публикация

## Условие

Реализуй **Saga с Outbox Pattern**: `Order Service` транзакция: `INSERT INTO orders ...` + `INSERT INTO outbox (topic, payload) ...`. Отдельный worker читает outbox, публикует в Kafka, удаляет. Покажи atomicity: БД commit = event published (eventually).

## Теория

Симбиоз распределенных саг и Transactional Outbox:
- Шаг саги \(T_i\) меняет состояние локального агрегата и должен отправить событие следующему участнику саги.
- **Проблема атомарности:**
  - Если закоммитить БД, а брокер Kafka недоступен — сага зависнет навсегда.
- **Решение Saga + Outbox:**
  - Изменение агрегата заказа и запись в таблицу `saga_outbox` выполняются в **одной локальной ACID-транзакции**.
  - Фоновый воркер (Outbox Processor) считывает таблицу и отправляет сообщение в Kafka с гарантией At-Least-Once.
  - Гарантируется, что событие следующего шага саги **обязательно будет опубликовано**.

## Решение по шагам

1. Создайте структуру транзакционного контекста заказа и Outbox.
2. Реализуйте атомарную запись в обе таблицы.
3. Смоделируйте фоновый воркер публикации в шину событий.
4. Верифицируйте согласованность состояния саги.

## Код решения

**`saga_outbox_integration_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SagaOutboxRecord struct {
	ID        int
	Topic     string
	Payload   string
	Published bool
}

type OrderSagaDB struct {
	orders []string
	outbox []SagaOutboxRecord
}

func (db *OrderSagaDB) CommitOrderWithSagaEvent(orderID, payload string) {
	// АТОМАРНАЯ ТРАНЗАКЦИЯ В ОДНОЙ БД
	db.orders = append(db.orders, orderID)
	db.outbox = append(db.outbox, SagaOutboxRecord{
		ID:        len(db.outbox) + 1,
		Topic:     "saga.orders.created",
		Payload:   payload,
		Published: false,
	})
}

func (db *OrderSagaDB) ProcessOutboxQueue(kafkaSimulator *[]string) {
	for i := range db.outbox {
		if !db.outbox[i].Published {
			// Отправка в Kafka
			*kafkaSimulator = append(*kafkaSimulator, db.outbox[i].Payload)
			db.outbox[i].Published = true
		}
	}
}

func TestSagaOutboxIntegration(t *testing.T) {
	db := &OrderSagaDB{}
	var kafkaEvents []string

	// 1. Атомарное сохранение шага саги
	db.CommitOrderWithSagaEvent("ord-saga-007", `{"order_id":"ord-saga-007","amount":12000}`)

	if len(db.orders) != 1 || len(db.outbox) != 1 || len(kafkaEvents) != 0 {
		t.Fatal("Сбой атомарного коммита шага саги")
	}

	// 2. Фоновый воркер переносит события в Kafka
	db.ProcessOutboxQueue(&kafkaEvents)

	if len(kafkaEvents) != 1 || !db.outbox[0].Published {
		t.Fatal("Событие саги не доставлено в Kafka")
	}

	fmt.Println("Saga с паттерном Outbox успешно подтверждена:")
	fmt.Printf("  • Заказ закоммичен в БД: %s\n", db.orders[0])
	fmt.Printf("  • Событие передано в Kafka топик saga.orders.created: %s\n", kafkaEvents[0])
	fmt.Println("  • Атомарность гарантирована: коммит БД гарантирует итоговую публикацию шага саги")
}
```

## Под капотом

Для исключения дублирования событий при сетевых сбоях воркера каждый шаг саги генерирует уникальный `SagaStepID`. Консьюмеры следующих сервисов проверяют этот ID в своей таблице `Inbox` (Idempotent Consumer).

## Подводные камни

Удалять строки из Outbox сразу же после отправки: это создает высокую нагрузку на VACUUM в Postgres. Лучше использовать Soft Delete (`published = true`) с периодической очисткой старых партиций.

## На собеседовании

**Вопрос с собеседования:** «Как обеспечить строгий порядок (Ordering) событий одного заказа при использовании Outbox воркера?»
**Ответ:** Таблицу Outbox партиционируют или отправляют события в Kafka с ключом `MessageKey = OrderID`. Это гарантирует, что все события одного заказа попадут строго в одну партицию Kafka, сохраняя строгий порядок FIFO.
