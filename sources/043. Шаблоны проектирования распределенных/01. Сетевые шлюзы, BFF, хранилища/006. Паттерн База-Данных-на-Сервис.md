# Паттерн База-Данных-на-Сервис (Database-per-Service): устранение разделяемой БД и защита автономии

## Условие

Спроектируй **Database-per-Service**: `User Service` → PostgreSQL (users, auth), `Order Service` → PostgreSQL (orders, items), `Inventory Service` → PostgreSQL (products, stock), `Analytics Service` → ClickHouse (events, aggregations). Покажи, что shared database — антипаттерн.

## Теория

Почему Shared Database — это антипаттерн в микросервисах:
1. **Жесткая связанность (Tight Coupling):** смена имени колонки в одной таблице ломает сразу 4 независимых сервиса.
2. **Блокировки и падения (Lock Contention):** тяжелый аналитический отчет сервиса аналитики блокирует таблицы заказов, парализуя прием платежей.
3. **Единая точка отказа (Single Point of Failure):** падение одной СУБД останавливает работу всей компании.
- **Стандарт Database-per-Service:**
  - Каждый сервис имеет **свою изолированную базу данных**.
  - Прямой доступ к чужой БД категорически заблокирован на уровне firewall и прав СУБД.
  - Любой обмен данными происходит **строго через публичные API или события**.

## Решение по шагам

1. Создайте модели автономных сервисов и их независимых хранилищ.
2. Продемонстрируйте изоляцию данных Order Service и Inventory Service.
3. Смоделируйте аналитическую агрегацию в ClickHouse через поток событий.
4. Верифицируйте автономию каждого домена.

## Код решения

**`database_per_service_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type UserPostgresDB struct {
	usersTable map[string]string
}

type OrderPostgresDB struct {
	ordersTable map[string]float64
}

type ClickHouseAnalyticsDB struct {
	eventsLog []string
}

func TestDatabasePerService(t *testing.T) {
	userDB := &UserPostgresDB{usersTable: map[string]string{"u-1": "Иван"}}
	orderDB := &OrderPostgresDB{ordersTable: map[string]float64{"ord-1": 4900.0}}
	chDB := &ClickHouseAnalyticsDB{eventsLog: []string{"OrderPlaced: ord-1: 4900.0"}}

	if userDB.usersTable["u-1"] == "" || orderDB.ordersTable["ord-1"] == 0 || len(chDB.eventsLog) == 0 {
		t.Fatal("Сбой данных автономных сервисов")
	}

	fmt.Println("Паттерн Database-per-Service успешно подтвержден:")
	fmt.Printf("  • User Service DB:      usersTable[%s] = %s\n", "u-1", userDB.usersTable["u-1"])
	fmt.Printf("  • Order Service DB:     ordersTable[%s] = %.2f\n", "ord-1", orderDB.ordersTable["ord-1"])
	fmt.Printf("  • ClickHouse Analytics: %s\n", chDB.eventsLog[0])
	fmt.Println("  • Ни один сервис не делает прямых SQL JOIN к чужой базе данных!")
}
```

## Под капотом

Физическая изоляция позволяет выполнять независимые бесшовные миграции баз данных (Flyway / Goose) без координации между командами: миграция схемы `Order Service` не затрагивает схемы `User Service`.

## Подводные камни

Использовать одну базу данных, но «с разными таблицами»: при росте нагрузки общие ресурсы процессора и дискового I/O приведут к взаимному влиянию сервисов (Noisy Neighbor).

## На собеседовании

**Вопрос с собеседования:** «Как получить список заказов с именами пользователей, если базы данных разделены (нельзя сделать SQL JOIN)?»
**Ответ:** 
1. **API Composition:** сервис заказов запрашивает заказы, затем батчем запрашивает имена у UserService по gRPC и склеивает в памяти.
2. **CQRS Репликация:** Order Service подписывается на события `UserUpdated` и хранит локальную денормализованную копию имени пользователя.
3. **Витрина в ClickHouse:** для отчетов данные стримятся в общую аналитическую витрину через CDC.
