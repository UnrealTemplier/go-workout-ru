# Захват изменений данных (Change Data Capture / CDC): Debezium, чтение WAL и zero-code пайплайн

## Условие

Реализуй **Change Data Capture (CDC)**: Debezium читает PostgreSQL WAL (`pgoutput`), публикует `dbserver1.public.orders` в Kafka. `Search Service` (Elasticsearch) и `Cache Service` (Redis) — consumers. Покажи zero-code data pipeline.

## Теория

Концепция Change Data Capture (CDC) и Debezium:
- В традиционных системах разработчики вынуждены вручную писать код публикации событий после каждого SQL-запроса.
- **Архитектура CDC:**
  - База данных (PostgreSQL) пишет все изменения в журнал опережающей записи (Write-Ahead Log, WAL).
  - Debezium коннектор подключается через протокол логической репликации (`pgoutput`).
  - Без единой строчки кода бэкенда любое действие (`INSERT`, `UPDATE`, `DELETE`) превращается в поток событий в Kafka.
  - `Search Service` читает поток и обновляет индексы Elasticsearch.
  - `Cache Service` инвалидирует ключи в Redis.

## Решение по шагам

1. Создайте структуру WAL-записи изменения данных.
2. Реализуйте трансляцию изменений в стрим событий Kafka.
3. Подключите подписчиков Redis и Elasticsearch.
4. Верифицируйте синхронную доставку изменений.

## Код решения

**`cdc_debezium_pipeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PostgresWALRecord struct {
	Operation string // "c" = create, "u" = update, "d" = delete
	Table     string
	Key       string
	After     map[string]string
}

type DebeziumCDCEngine struct {
	kafkaTopic chan PostgresWALRecord
}

func (d *DebeziumCDCEngine) StreamWAL(record PostgresWALRecord) {
	d.kafkaTopic <- record
}

func TestCDCDebeziumPipeline(t *testing.T) {
	topic := make(chan PostgresWALRecord, 10)
	cdc := &DebeziumCDCEngine{kafkaTopic: topic}

	// Имитация записи в WAL PostgreSQL
	walEntry := PostgresWALRecord{
		Operation: "c",
		Table:     "public.orders",
		Key:       "ord-cdc-101",
		After:     map[string]string{"status": "PAID", "amount": "9900"},
	}

	cdc.StreamWAL(walEntry)

	// Консьюмер 1: Redis Cache Invalidation
	event := <-topic
	redisKey := fmt.Sprintf("cache:%s:%s", event.Table, event.Key)

	// Консьюмер 2: Elasticsearch Indexer
	esDocumentID := event.Key

	if redisKey != "cache:public.orders:ord-cdc-101" || esDocumentID != "ord-cdc-101" {
		t.Fatalf("Сбой CDC пайплайна: %s %s", redisKey, esDocumentID)
	}

	fmt.Println("Change Data Capture (CDC / Debezium) успешно подтвержден:")
	fmt.Printf("  • WAL операция: %s в таблице %s\n", event.Operation, event.Table)
	fmt.Printf("  • Redis инвалидировал ключ: %s\n", redisKey)
	fmt.Printf("  • Elasticsearch проиндексировал документ ID: %s\n", esDocumentID)
	fmt.Println("  • Zero-Code архитектура: сервис сохранил данные в БД без ручного кода отправки в брокер")
}
```

## Под капотом

Debezium использует механизм слотов логической репликации (Replication Slots) в PostgreSQL. База данных гарантирует, что сегменты WAL не будут удалены с диска, пока коннектор Debezium не подтвердит их успешное прочтение (Replication LSN Acknowledgment).

## Подводные камни

Забыть настроить `REPLICA IDENTITY FULL` для таблиц: при операции `UPDATE` PostgreSQL по умолчанию пишет в WAL только новые значения, и вы не узнаете, какие старые значения полей были перезаписаны.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если коннектор Debezium упадет на 12 часов?»
**Ответ:** Слот репликации в PostgreSQL будет удерживать WAL-файлы на диске. Если объем изменений велик, это может полностью исчерпать свободное дисковое пространство сервера СУБД (Disk Full Panic). В продакшене обязательно настраивают параметр `max_slot_wal_keep_size` и алерты на размер слота репликации.
