# Федеративный GraphQL шлюз (Apollo Federation): объединение распределенных схем User и Order

## Условие

Реализуй **GraphQL Gateway (Apollo Federation)**: `User Service` предоставляет `type User @key(fields: "id")`. `Order Service` extends `User` полем `orders: [Order]`. Gateway агрегирует schema'ы, маршрутизирует queries. Покажи federated graph.

## Теория

Принципы Apollo Federation в распределенной архитектуре:
- В микросервисной среде единая монолитная схема GraphQL неприменима, так как требует координации всех команд при каждом изменении.
- **Федерация (Federation) позволяет:**
  1. Сервису `UserService` владеть сущностью `User`: `{ id, name, email }`.
  2. Сервису `OrderService` расширять чужую сущность: `extend type User { orders: [Order] }`.
  3. Федеративный шлюз (Federated Gateway) автоматически строит объединенный граф запросов (Query Plan) и параллельно запрашивает оба сервиса через внутренние резолверы сущностей `_entities`.

## Решение по шагам

1. Создайте эмулятор `UserServiceFederated` (владелец User).
2. Создайте эмулятор `OrderServiceFederated` (расширяет User заказами).
3. Смоделируйте движок федеративного объединения `FederatedGateway`.
4. Верифицируйте сквозной граф данных.

## Код решения

**`graphql_federation_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FederatedUser struct {
	ID    string
	Name  string
	Orders []string // Расширяемое поле из другого сервиса!
}

type UserSubservice struct{}

func (s *UserSubservice) ResolveUser(id string) (string, string) {
	return id, "Александр Морозов"
}

type OrderSubservice struct{}

func (s *OrderSubservice) ResolveOrdersForUser(userID string) []string {
	return []string{"ORD-FED-1", "ORD-FED-2"}
}

type FederatedGraphEngine struct {
	users  *UserSubservice
	orders *OrderSubservice
}

func (g *FederatedGraphEngine) ExecuteUserWithOrders(userID string) FederatedUser {
	id, name := g.users.ResolveUser(userID)
	userOrders := g.orders.ResolveOrdersForUser(userID)

	return FederatedUser{
		ID:     id,
		Name:   name,
		Orders: userOrders,
	}
}

func TestGraphQLFederation(t *testing.T) {
	engine := &FederatedGraphEngine{
		users:  &UserSubservice{},
		orders: &OrderSubservice{},
	}

	res := engine.ExecuteUserWithOrders("usr-77")

	if res.ID != "usr-77" || res.Name != "Александр Морозов" || len(res.Orders) != 2 {
		t.Fatalf("Сбой сборки федеративного графа: %+v", res)
	}

	fmt.Println("Федеративный GraphQL шлюз успешно подтвержден:")
	fmt.Printf("  • Сущность User (UserService): ID=%s, Имя=%s\n", res.ID, res.Name)
	fmt.Printf("  • Расширение Orders (OrderService): %v\n", res.Orders)
	fmt.Println("  • Граф склеен шлюзом без прямого связывания сервисов между собой")
}
```

## Под капотом

В Go библиотеках `99designs/gqlgen` директива `@key(fields: "id")` генерирует резолвер `FindUserByID()`, который федеративный шлюз вызывает батчами через GraphQL запросы к служебному полю `_entities(representations: [...])`, исключая проблему N+1 сетевых вызовов.

## Подводные камни

Допускать циклические зависимости между подграфами (User расширяет Order, а Order расширяет User без DataLoader): шлюз может зависнуть в бесконечной рекурсии планирования графа.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Federation v1 от Apollo Federation v2?»
**Ответ:** Federation v2 сняла требование жесткого соответствия типов и позволила нескольким сервисам делить владение одними и теми же полями через директивы `@shareable` и `@inaccessible`, а также устранила необходимость обязательного дублирования полей в `extend type`.
