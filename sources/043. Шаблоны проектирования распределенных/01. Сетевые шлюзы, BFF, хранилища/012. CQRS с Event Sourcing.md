# CQRS с Event Sourcing: независимые материализованные проекции Redis, ClickHouse и Elasticsearch

## Условие

Реализуй **CQRS с Event Sourcing**: `Command Side` — Event Store (Kafka/NATS JetStream, append-only). `Query Side` — multiple projections: `OrderSummaryView` (Redis), `OrderAnalyticsView` (ClickHouse), `OrderSearchView` (Elasticsearch). Покажи, что projections независимы, replayable.

### Исходная формулировка

---

## Теория

Симбиоз CQRS, Event Sourcing и множественных проекций:
- Источником абсолютной истины является **Append-Only журнал событий (Event Store)**.
- Ни один клиент не читает Event Store напрямую для отображения UI.
- **Полиглотные проекции читателей (Read Projections):**
  1. `Redis Projection`: хранит быстрый key-value срез `order:{id}:summary` для мобильного экрана.
  2. `Elasticsearch Projection`: индексирует текстовые описания и категории для поисковой строки.
  3. `ClickHouse Projection`: аккумулирует финансовые агрегации выручки по дням и городам.
- Каждая проекция вычитывает один и тот же Kafka-топик независимо со своей скоростью!

## Решение по шагам

1. Создайте событие `OrderEventPayload`.
2. Реализуйте три независимых обработчика проекций.
3. Прогоните поток событий через все проекции.
4. Продемонстрируйте независимость и возможность пересоздания (Replay).

## Код решения

**`cqrs_multi_projections_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SourcedEvent struct {
	OrderID  string
	Customer string
	Amount   float64
}

type RedisSummaryProjection struct {
	cache map[string]float64
}

type ElasticSearchProjection struct {
	index map[string]string
}

type ClickHouseAnalyticsProjection struct {
	totalRevenue float64
}

func TestCQRSMultiProjections(t *testing.T) {
	// Event Store stream
	events := []SourcedEvent{
		{OrderID: "ord-1", Customer: "Мария", Amount: 3000.0},
		{OrderID: "ord-2", Customer: "Дмитрий", Amount: 7000.0},
	}

	redisProj := &RedisSummaryProjection{cache: make(map[string]float64)}
	elasticProj := &ElasticSearchProjection{index: make(map[string]string)}
	chProj := &ClickHouseAnalyticsProjection{}

	// Независимое наполнение трех проекций из одного стрима событий
	for _, e := range events {
		// 1. Redis
		redisProj.cache[e.OrderID] = e.Amount
		// 2. Elastic
		elasticProj.index[e.OrderID] = e.Customer
		// 3. ClickHouse
		chProj.totalRevenue += e.Amount
	}

	if redisProj.cache["ord-1"] != 3000.0 || elasticProj.index["ord-2"] != "Дмитрий" || chProj.totalRevenue != 10000.0 {
		t.Fatal("Сбой проекций")
	}

	fmt.Println("CQRS с Event Sourcing и множественными проекциями подтвержден:")
	fmt.Printf("  • Redis View:      Кэш заказа ord-1 = %.2f руб\n", redisProj.cache["ord-1"])
	fmt.Printf("  • Elastic View:    Поиск по клиенту ord-2 = %s\n", elasticProj.index["ord-2"])
	fmt.Printf("  • ClickHouse View: Общая выручка = %.2f руб\n", chProj.totalRevenue)
	fmt.Println("  • Все 3 витрины одноразовые (disposable) и могут быть пересозданы с нуля через Replay")
}
```

ℹ️ Параллельное построение трех независимых специализированных витрин данных из единого потока событий

## Под капотом

Каждая проекция хранит свой собственный сохраненный оффсет в БД (Consumer Offset). Если Redis упал, при перезапуске он продолжает чтение с сохраненного оффсета, не влияя на работу Elasticsearch и ClickHouse.

## Подводные камни

Выполнять синхронный HTTP-запрос к стороннему сервису внутри проектора: если внешний сервис затормозит, консьюмер отстанет от Kafka (Consumer Lag вырастет), и витрина станет неактуальной.

## На собеседовании

**Вопрос с собеседования:** «Как добавить новую четвертую проекцию через год после запуска системы в продакшене?»
**Ответ:** Запускается новый консьюмер с новой группой `consumer-group: new-view-v1` и настройкой `auto.offset.reset = earliest`. Консьюмер вычитывает всю годовую историю событий с самого начала, строит новую базу данных и переключает на нее трафик.
