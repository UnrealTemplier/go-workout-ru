# Синхронное межсервисное взаимодействие (Sync gRPC): каскадные сбои, стек задержек и жесткая связность

## Условие

Реализуй **Synchronous Communication (gRPC)**: `Order Service` вызывает `Inventory Service.Reserve()` synchronously. Покажи coupling: latency stack, cascading failure, tight runtime dependency. Когда уместно: simple operations, strong consistency needed.

## Теория

Архитектурные риски синхронного RPC (Стек задержек и каскадные сбои):
- **Стек задержек (Latency Stack):**
  Если сервис A вызывает B (50 мс), B вызывает C (100 мс), C вызывает D (150 мс):
  $$\text{TotalLatency} = 50 + 100 + 150 = 300\text{ мс}$$
  Задержка накапливается мультипликативно.
- **Каскадный сбой (Cascading Failure):**
  Если сервис D начал отвечать за 5 секунд, горутины в сервисах C, B и A зависают в ожидании ответов. Пул соединений исчерпывается, и вся цепочка сервисов падает по домино-эффекту.
- **Когда синхронный gRPC оправдан:**
  1. Операция требует строгой мгновенной консистентности (проверка баланса перед холдированием).
  2. Простые линейные запросы без глубоких цепочек вызовов.

## Решение по шагам

1. Создайте эмулятор цепочки сервисов Order \(\to\) Inventory.
2. Продемонстрируйте сложение сетевых задержек.
3. Смоделируйте каскадный сбой при отказе нижележащего сервиса.
4. Верифицируйте необходимость защиты таймаутами.

## Код решения

**`sync_grpc_coupling_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"
)

type InventoryClientSync interface {
	ReserveItem(ctx context.Context, sku string) (int, error)
}

type SlowInventoryService struct {
	delay time.Duration
}

func (s *SlowInventoryService) ReserveItem(ctx context.Context, sku string) (int, error) {
	select {
	case <-time.After(s.delay):
		return 1, nil
	case <-ctx.Done():
		return 0, ctx.Err()
	}
}

type OrderServiceSyncCoordinator struct {
	inventory InventoryClientSync
}

func (s *OrderServiceSyncCoordinator) PlaceOrder(ctx context.Context, sku string) error {
	_, err := s.inventory.ReserveItem(ctx, sku)
	if err != nil {
		return fmt.Errorf("каскадный сбой заказа: %w", err)
	}
	return nil
}

func TestSyncGRPCCoupling(t *testing.T) {
	// Имитация зависшего инвентарного сервиса (задержка 500 мс)
	slowInventory := &SlowInventoryService{delay: 500 * time.Millisecond}
	orderSvc := &OrderServiceSyncCoordinator{inventory: slowInventory}

	// Клиент задает жесткий таймаут 50 мс
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	err := orderSvc.PlaceOrder(ctx, "sku-notebook")
	if err == nil || !errors.Is(err, context.DeadlineExceeded) {
		t.Fatalf("Ожидался срыв по таймауту context.DeadlineExceeded: %v", err)
	}

	fmt.Println("Синхронное взаимодействие (Sync RPC Coupling) подтверждено:")
	fmt.Printf("  • Ошибка вызова: %v\n", err)
	fmt.Println("  • Жесткая зависимость во времени: медленный downstream вызвал отказ upstream сервиса")
}
```

## Под капотом

При использовании `context.WithTimeout` Go запускает системный таймер рантайма `runtime.timer`. По истечении срока таймер закрывает внутренний канал `ctx.Done()`, что прерывает блокирующий системный вызов сетевого сокета.

## Подводные камни

Использовать синхронные RPC вызовы глубиной более 3 уровней (A \(\to\) B \(\to\) C \(\to\) D): доступность системы падает по формуле \(A_{total} = A_1 \times A_2 \times A_3 \times A_4\). Если у каждого сервиса SLA 99.9%, суммарный SLA упадет до 99.6%.

## На собеседовании

**Вопрос с собеседования:** «Что такое Deadline Propagation в распределенном gRPC?»
**Ответ:** Это механизм автоматической передачи оставшегося времени таймаута через сетевые метаданные gRPC (заголовок `grpc-timeout`). Если клиент выделил на весь сценарий 1000 мс, а первый вызов занял 300 мс, то следующему сервису в контексте автоматически прокинется таймаут 700 мс.
