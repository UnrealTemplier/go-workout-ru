# Паттерн Transactional Outbox: надежная публикация доменных событий с гарантией At-Least-Once

## Условие

**Transactional Outbox для надёжной публикации событий**. Сервис сохраняет событие в таблицу `outbox` в той же транзакции, что и изменение агрегата. Отдельный процесс отправляет события в брокер с гарантией at-least-once.

## Теория

Архитектурные гарантии паттерна Transactional Outbox:
- **Проблема атомарности двух систем:** База данных и брокер сообщений не могут быть объединены в распределенную транзакцию 2PC без катастрофической потери производительности.
- **Решение Transactional Outbox:**
  - База данных берет на себя роль буфера сообщений.
  - Таблица `outbox_table` хранит: `id`, `aggregate_id`, `event_type`, `payload_json`, `created_at`.
  - Фоновый Relay воркер считывает таблицу пакетами (Batch) и отправляет сообщения в брокер.
  - При сбое сети воркер повторяет отправку (At-Least-Once).

## Решение по шагам

1. Создайте структуру транзакционного репозитория с таблицей `outbox`.
2. Реализуйте метод `SaveAggregateWithOutbox`.
3. Смоделируйте работу воркера ретрансляции.
4. Верифицируйте гарантию публикации событий.

## Код решения

**`transactional_outbox_reliable_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OutboxRecordItem struct {
	ID        int
	EventType string
	Payload   string
	Sent      bool
}

type OutboxStorage struct {
	records []OutboxRecordItem
}

func (s *OutboxStorage) SaveInTransaction(eventType, payload string) {
	s.records = append(s.records, OutboxRecordItem{
		ID:        len(s.records) + 1,
		EventType: eventType,
		Payload:   payload,
		Sent:      false,
	})
}

func (s *OutboxStorage) RelayToBroker(broker *[]string) {
	for i := range s.records {
		if !s.records[i].Sent {
			// Отправка в Kafka топик
			*broker = append(*broker, s.records[i].Payload)
			s.records[i].Sent = true
		}
	}
}

func TestTransactionalOutboxReliable(t *testing.T) {
	storage := &OutboxStorage{}
	var brokerStream []string

	// Шаг 1: Атомарная фиксация в БД
	storage.SaveInTransaction("UserRegistered", `{"user_id":"u-100","email":"a@b.ru"}`)

	if len(storage.records) != 1 || len(brokerStream) != 0 {
		t.Fatal("Событие обязано быть в Outbox, но еще не в брокере")
	}

	// Шаг 2: Воркер передает в брокер
	storage.RelayToBroker(&brokerStream)

	if len(brokerStream) != 1 || !storage.records[0].Sent {
		t.Fatal("Событие не отправлено в брокер")
	}

	fmt.Println("Transactional Outbox успешно подтвержден:")
	fmt.Printf("  • Запись Outbox ID=%d зафиксирована в БД\n", storage.records[0].ID)
	fmt.Printf("  • Воркер доставил событие в брокер: %s\n", brokerStream[0])
	fmt.Println("  • Доставка At-Least-Once гарантирована даже при падении брокера в момент сохранения")
}
```

## Под капотом

При опросе таблицы Outbox методом Polling воркер использует SQL запрос: `SELECT * FROM outbox WHERE sent = false ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`. Конструкция `SKIP LOCKED` позволяет десяткам параллельных воркеров вычитывать разные пачки строк без взаимных блокировок!

## Подводные камни

Использовать обычный `SELECT ... FOR UPDATE` без `SKIP LOCKED`: воркеры будут выстраиваться в очередь за одной и той же заблокированной первой строкой, снижая пропускную способность до минимума.

## На собеседовании

**Вопрос с собеседования:** «Почему CDC (Debezium) считается более производительной альтернативой Polling Publisher в Transactional Outbox?»
**Ответ:** Polling Publisher постоянно нагружает базу запросами `SELECT/UPDATE`, расходуя IOPS диска и создавая Dead Tuples. Debezium читает бинарный журнал WAL асинхронно, создавая нулевую дополнительную нагрузку на процессор СУБД.
