# Мультитенантность с раздельными схемами (Shared DB, Separate Schemas): изоляция и поиск по Search Path

## Условие

**Multi-tenancy (Shared DB, Separate Schemas)**: Каждый тенант имеет свою схему в одной БД. Более изолированно, но сложнее управлять миграциями.

## Теория

Модель мультитенантности на уровне схем (Separate Schemas):
- База данных одна, но для каждого клиента создается персональная схема:
  `CREATE SCHEMA tenant_alfa;`, `CREATE SCHEMA tenant_beta;`
- Таблицы в схемах идентичны (`orders`, `users`).
- **Как переключать контекст в Go:**
  - При обработке HTTP-запроса извлекается субдомен: `alfa.crm.ru` \(\implies\) тенант `tenant_alfa`.
  - В начале транзакции выполняется:
    `SET LOCAL search_path TO tenant_alfa, public;`
  - Любой SQL-запрос `SELECT * FROM orders` автоматически направляется в схему `tenant_alfa.orders`!
- **Преимущество:** абсолютная физическая изоляция данных без оверхеда на сотни баз данных.

## Решение по шагам

1. Создайте эмулятор схем `tenant_alfa` и `tenant_beta`.
2. Реализуйте переключение `search_path` в сессии.
3. Выполните запрос к таблице без префикса схемы.
4. Верифицируйте изоляцию между схемами клиентов.

## Код решения

**`multi_tenancy_schemas_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MultiSchemaPostgresDB struct {
	schemas map[string]map[string]string // schemaName -> (key -> val)
}

func (db *MultiSchemaPostgresDB) QueryWithSearchPath(activeSchema, key string) string {
	schemaData, ok := db.schemas[activeSchema]
	if !ok {
		return ""
	}
	return schemaData[key]
}

func TestMultiTenancySchemas(t *testing.T) {
	db := &MultiSchemaPostgresDB{
		schemas: map[string]map[string]string{
			"tenant_alfa": {"config_theme": "dark_alfa_theme"},
			"tenant_beta": {"config_theme": "light_beta_theme"},
		},
	}

	themeAlfa := db.QueryWithSearchPath("tenant_alfa", "config_theme")
	themeBeta := db.QueryWithSearchPath("tenant_beta", "config_theme")

	if themeAlfa != "dark_alfa_theme" || themeBeta != "light_beta_theme" {
		t.Fatalf("Сбой изоляции схем: %s, %s", themeAlfa, themeBeta)
	}

	fmt.Println("Мультитенантность с раздельными схемами подтверждена:")
	fmt.Printf("  • Схема tenant_alfa: config_theme = %s\n", themeAlfa)
	fmt.Printf("  • Схема tenant_beta: config_theme = %s\n", themeBeta)
	fmt.Println("  • search_path автоматически изолирует пространство таблиц тенантов")
}
```

## Под капотом

В PostgreSQL поиск таблиц без указания схемы идет по списку `search_path`. Если указать `SET search_path = tenant_1, public`, то при отсутствии таблицы в схеме тенанта база автоматически обратится к общей схеме `public`, что позволяет держать справочные таблицы общими.

## Подводные камни

Миграции базы данных: если у вас 500 тенантов (500 схем), утилита миграций должна накатить SQL-скрипт 500 раз в цикле. При 10 000 схем миграция может занимать несколько часов.

## На собеседовании

**Вопрос с собеседования:** «Каковы ограничения архитектуры Separate Schemas в PostgreSQL?»
**Ответ:** Основное ограничение — каталог метаданных PostgreSQL (`pg_class`, `pg_attribute`). При наличии 1000 схем по 100 таблиц в базе появляется 100 000 таблиц. Системные каталоги разрастаются, автовакуум и планировщик запросов начинают деградировать по памяти.
