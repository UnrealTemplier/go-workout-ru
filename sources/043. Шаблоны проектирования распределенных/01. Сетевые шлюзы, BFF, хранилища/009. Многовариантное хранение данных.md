# Многовариантное хранение данных (Polyglot Persistence): подбор оптимальной СУБД под задачи домена

## Условие

Спроектируй **Polyglot Persistence**: `User Service` — PostgreSQL (relational data), `Session Service` — Redis (TTL, fast access), `Search Service` — Elasticsearch (full-text), `Analytics` — ClickHouse (OLAP), `Logs` — Loki/Elasticsearch (time-series). Покажи правильный инструмент для задачи.

## Теория

Принцип Polyglot Persistence в Enterprise-архитектуре:
- Золотое правило архитектора: «Не существует идеальной универсальной базы данных для всех задач».
- **Матрица выбора СУБД:**
  1. **PostgreSQL (ACID OLTP):** реляционные сущности, пользователи, строгие финансовые транзакции.
  2. **Redis (In-Memory Key-Value):** сессии, счетчики, лидерборды, TTL-кэши со временем отклика < 1 мс.
  3. **Elasticsearch / MeiliSearch (Inverted Index):** полнотекстовый поиск, фасетные фильтры товаров, опечатки.
  4. **ClickHouse (Columnar OLAP):** аналитика, расчет конверсий, сканирование миллиардов строк в секунду со сжатием данных в 10 раз.
  5. **Grafana Loki (Log Aggregation):** структурированные логи с фильтрацией по меткам.

## Решение по шагам

1. Создайте реестр типов СУБД под задачи подсистем.
2. Продемонстрируйте маршрутизацию операций в соответствующее хранилище.
3. Проверьте валидность выбора инструмента.
4. Верифицируйте преимущества Polyglot Persistence.

## Код решения

**`polyglot_persistence_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type StorageTypeRole struct {
	DomainService string
	DatabaseName  string
	EngineType    string
	PrimaryReason string
}

func GetEnterprisePersistenceMap() []StorageTypeRole {
	return []StorageTypeRole{
		{"UserService", "PostgreSQL", "Relational ACID OLTP", "Транзакционная консистентность пользователей"},
		{"SessionService", "Redis", "In-Memory Key-Value", "TTL экспирация сессий и задержка < 1 мс"},
		{"SearchService", "Elasticsearch", "Inverted Index Full-Text", "Полнотекстовый поиск с учетом морфологии"},
		{"AnalyticsService", "ClickHouse", "Column-Oriented OLAP", "Векторные агрегации миллиардов строк"},
	}
}

func TestPolyglotPersistence(t *testing.T) {
	roles := GetEnterprisePersistenceMap()

	if len(roles) != 4 {
		t.Fatal("Ожидалось 4 специализированных хранилища")
	}

	fmt.Println("Паттерн Polyglot Persistence успешно подтвержден:")
	for _, r := range roles {
		fmt.Printf("  • %-18s -> %-14s (%s)\n", r.DomainService, r.DatabaseName, r.PrimaryReason)
	}
	fmt.Println("  • Каждый микросервис использует оптимальную модель данных без компромиссов")
}
```

## Под капотом

Колоночные СУБД (ClickHouse) читают с диска только те колонки, которые указаны в `SELECT`, пропуская гигабайты ненужных данных, в то время как строчные СУБД (Postgres) вынуждены читать строки целиком, проигрывая в аналитике в 100+ раз.

## Подводные камни

Внедрять 6 разных СУБД в стартапе из 2 разработчиков: оверхед на бэкапы, мониторинг и поддержку разных типов баз обрушит производительность команды. Polyglot Persistence внедряют по мере реального масштабирования.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя использовать ClickHouse в качестве основной транзакционной базы данных для интернет-магазина?»
**Ответ:** ClickHouse оптимизирован для пакетных вставок большими пачками (Batch Insert) и не поддерживает точечные ACID транзакции с быстрыми `UPDATE/DELETE` отдельных строк. Попытка слать одиночные транзакции приведет к миллионам несмерженных кусков (Parts) и ошибке `Too many parts in all data in table`.
