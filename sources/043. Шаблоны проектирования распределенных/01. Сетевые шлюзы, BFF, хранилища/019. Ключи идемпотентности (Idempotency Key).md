# Ключи идемпотентности (Idempotency Key): кэширование ответов в Redis с TTL для семантики Exactly-Once

## Условие

Реализуй **Idempotency Key**: клиент генерирует `Idempotency-Key: uuid` для `CreateOrder`. Сервер хранит обработанные ключи (Redis, TTL=24h). При повторе с тем же ключом — возвращает cached response, не создаёт дубликат. Покажи exactly-once обработка.

## Теория

Семантика Exactly-Once на транспортном уровне:
- Сеть ненадежна: клиент отправил `POST /orders`, сервер создал заказ, но TCP ACK потерялся из-за сбоя Wi-Fi.
- Клиент повторяет запрос с тем же `Idempotency-Key: 7b34-41ad-99f2`.
- **Механика на сервере:**
  1. Атомарный захват блокировки ключа: `SET key PROCESSING NX EX 60`.
  2. Если ключ уже существует и статус `COMPLETED` \(\implies\) возврат сохраненного JSON.
  3. Если статус `PROCESSING` \(\implies\) возврат `409 Conflict` (запрос уже выполняется).
  4. Если ключа нет \(\implies\) создаем заказ, сохраняем JSON ответа в Redis с `TTL = 24 часа` и отдаем клиенту.

## Решение по шагам

1. Создайте хранилище ключей идемпотентности.
2. Реализуйте метод `ExecuteIdempotentOrder`.
3. Смоделируйте первый вызов и последующий повтор.
4. Верифицируйте идентичность ответа и отсутствие дублирования заказа.

## Код решения

**`redis_idempotency_key_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type CachedResponse struct {
	Body       string
	StatusCode int
}

type IdempotencyManager struct {
	mu          sync.Mutex
	redisMock   map[string]CachedResponse
	createdOrders int
}

func (m *IdempotencyManager) CreateOrder(idemKey, payload string) (string, int) {
	m.mu.Lock()
	defer m.mu.Unlock()

	// 1. Проверяем кэш ключей
	if resp, found := m.redisMock[idemKey]; found {
		return resp.Body, resp.StatusCode // Возврат закэшированного ответа!
	}

	// 2. Реальное создание заказа
	m.createdOrders++
	responseBody := fmt.Sprintf("Order #%d created for payload: %s", m.createdOrders, payload)
	status := 201

	m.redisMock[idemKey] = CachedResponse{Body: responseBody, StatusCode: status}
	return responseBody, status
}

func TestRedisIdempotencyKey(t *testing.T) {
	mgr := &IdempotencyManager{redisMock: make(map[string]CachedResponse)}
	key := "idem-uuid-777-abc"

	// 1. Первый сетевой запрос
	res1, code1 := mgr.CreateOrder(key, "MacBook M3 Pro")
	if code1 != 201 || mgr.createdOrders != 1 {
		t.Fatalf("Сбой первого создания: %s", res1)
	}

	// 2. Повторный запрос клиента (ретрай мобильного приложения)
	res2, code2 := mgr.CreateOrder(key, "MacBook M3 Pro")
	if code2 != 201 || mgr.createdOrders != 1 {
		t.Fatalf("Повторный запрос создал дубликат! count=%d", mgr.createdOrders)
	}

	if res1 != res2 {
		t.Fatal("Ответы обязаны быть побайтово идентичными")
	}

	fmt.Println("Ключи идемпотентности (Idempotency Key) успешно подтверждены:")
	fmt.Printf("  • Первый ответ:    %s\n", res1)
	fmt.Printf("  • Повторный ответ: %s (Мгновенно из Redis)\n", res2)
	fmt.Println("  • Количество созданных заказов в БД: ровно 1 (Дубликаты исключены!)")
}
```

## Под капотом

Если клиент присылает одинаковый `Idempotency-Key`, но другое тело запроса (хэш SHA-256 полезной нагрузки изменился), сервер не должен возвращать старый кэш. Сервер возвращает ошибку `HTTP 422 Unprocessable Entity: Idempotency key reused with different payload`.

## Подводные камни

Использовать составной первичный ключ по UUID без индекса: поиск по неиндексированному ключу приведет к Full Table Scan в Postgres при повторах.

## На собеседовании

**Вопрос с собеседования:** «Какой срок TTL выставлять ключам идемпотентности в Redis?»
**Ответ:** Обычно от 24 до 72 часов. Сетевые ретраи мобильных клиентов и шлюзов происходят в первые секунды или часы после сбоя. Хранить ключи годами бессмысленно: через неделю тот же самый UUID считается новым запросом.
