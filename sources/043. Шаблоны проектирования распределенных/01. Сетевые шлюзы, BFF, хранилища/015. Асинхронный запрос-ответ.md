# Асинхронный запрос-ответ (Asynchronous Request-Response): команды, события ответа и таймаут-компенсация

## Условие

Реализуй **Asynchronous Request-Response (Commands)**: `Order Service` отправляет `ReserveInventoryCommand` в queue, ждёт `InventoryReserved` или `InventoryReservationFailed` event. Timeout: если нет ответа за 5s → compensation. Покажи async saga.

## Теория

Асинхронный паттерн Запрос-Ответ (Request-Reply over Messaging):
- В брокерах сообщений нет прямого сетевого ответа.
- **Механика через очереди:**
  1. Сервис A отправляет команду в очередь `inventory.commands` с метаданными:
     `CorrelationID = "uuid-123"`, `ReplyTo = "order.replies"`.
  2. Сервис B вычитывает команду, резервирует товар и публикует событие в очередь `order.replies` с тем же `CorrelationID`.
  3. Сервис A слушает свою очередь ответов и матчит ответ по `CorrelationID`.
  4. **Таймаут (Timeout & Compensation):** если за 5 секунд ответ не получен — горутина выходит по таймауту и запускает компенсирующую транзакцию.

## Решение по шагам

1. Создайте структуру команды с `CorrelationID` и каналом ответа.
2. Смоделируйте диспетчер сопоставления ответов по ID.
3. Продемонстрируйте обработку ответа в отведенное время.
4. Продемонстрируйте срабатывание таймаута и компенсации.

## Код решения

**`async_request_reply_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
	"time"
)

type AsyncCommand struct {
	CorrelationID string
	Payload       string
}

type AsyncResponse struct {
	CorrelationID string
	Success       bool
}

type AsyncRequestReplyCoordinator struct {
	mu      sync.Mutex
	pending map[string]chan AsyncResponse
}

func NewAsyncRequestReplyCoordinator() *AsyncRequestReplyCoordinator {
	return &AsyncRequestReplyCoordinator{pending: make(map[string]chan AsyncResponse)}
}

func (c *AsyncRequestReplyCoordinator) SendAndWait(ctx context.Context, cmd AsyncCommand) (bool, error) {
	respCh := make(chan AsyncResponse, 1)

	c.mu.Lock()
	c.pending[cmd.CorrelationID] = respCh
	c.mu.Unlock()

	defer func() {
		c.mu.Lock()
		delete(c.pending, cmd.CorrelationID)
		c.mu.Unlock()
	}()

	select {
	case resp := <-respCh:
		return resp.Success, nil
	case <-ctx.Done():
		return false, errors.New("timeout waiting for async reply: triggering compensation")
	}
}

func (c *AsyncRequestReplyCoordinator) ReceiveReply(resp AsyncResponse) {
	c.mu.Lock()
	ch, ok := c.pending[resp.CorrelationID]
	c.mu.Unlock()
	if ok {
		ch <- resp
	}
}

func TestAsyncRequestReply(t *testing.T) {
	coord := NewAsyncRequestReplyCoordinator()

	// 1. Успешный асинхронный ответ
	cmd := AsyncCommand{CorrelationID: "corr-101", Payload: "ReserveSKU"}
	go func() {
		time.Sleep(10 * time.Millisecond)
		coord.ReceiveReply(AsyncResponse{CorrelationID: "corr-101", Success: true})
	}()

	ctxOk, cancelOk := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancelOk()

	success, err := coord.SendAndWait(ctxOk, cmd)
	if err != nil || !success {
		t.Fatalf("Ожидался успешный ответ: %v", err)
	}

	// 2. Сценарий таймаута (downstream не ответил)
	cmdTimeout := AsyncCommand{CorrelationID: "corr-999", Payload: "ReserveSlowSKU"}
	ctxFail, cancelFail := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancelFail()

	_, errTimeout := coord.SendAndWait(ctxFail, cmdTimeout)
	if errTimeout == nil {
		t.Fatal("Ожидалась ошибка таймаута и запуск компенсации")
	}

	fmt.Println("Асинхронный запрос-ответ (Async Request-Reply) подтвержден:")
	fmt.Printf("  • Успешный ответ по CorrelationID: corr-101 (Success=%v)\n", success)
	fmt.Printf("  • Сбой по таймауту corr-999: %v\n", errTimeout)
}
```

## Под капотом

Для сохранения надежности при рестарте сервиса таблица ожидающих запросов сохраняется в Redis со значением ключа `pending:correlation_id`. При перезапуске пода консьюмер ответов находит запись в Redis и продолжает процесс.

## Подводные камни

Забывать удалять `CorrelationID` из мапы при таймауте: это приведет к медленной утечке памяти (Memory Leak), когда миллионы зависших каналов навсегда останутся в памяти.

## На собеседовании

**Вопрос с собеседования:** «Почему в асинхронном Request-Reply брокер RabbitMQ использует временные эксклюзивные очереди (Direct Reply-to)?»
**Ответ:** Чтобы не создавать тяжелую постоянную очередь на каждый инстанс сервиса. Опция `amq.rabbitmq.reply-to` позволяет клиенту слушать псевдоочередь прямо через открытый сетевой канал без накладных расходов на кластерные метаданные.
