# Паттерн изолированных отсеков (Bulkhead Pattern): раздельные пулы горутин для защиты от каскадного истощения

## Условие

Реализуй **Bulkhead Pattern**: `Order Service` имеет пулы: `Pool A` (10 goroutines) для `Inventory Service`, `Pool B` (10 goroutines) для `Payment Service`, `Pool C` (5 goroutines) для `Email Service`. Если `Payment Service` медленный — `Pool B` заполнен, но `Pool A` и `Pool C` работают.

## Теория

Морская метафора Bulkhead (Водонепроницаемые переборки трюма):
- Если корпус корабля пробит в одном отсеке, переборки не дают воде затопить соседние отсеки, и корабль остается на плаву.
- **В микросервисах без Bulkhead:**
  - Зависший платежный шлюз захватывает все 5 000 горутин веб-сервера.
  - Сервис перестает отвечать даже на проверку здоровья `/healthz`.
- **Архитектура Bulkhead в Go:**
  - Для каждого внешнего сервиса выделяется **строго изолированный семафор/воркер-пул**:
    - `Pool A (Inventory)`: 10 слотов.
    - `Pool B (Payment)`: 10 слотов.
    - `Pool C (Email)`: 5 слотов.
  - Если `Payment` завис — его 10 слотов исчерпаны, но `Inventory` и `Email` продолжают работать на 100% мощности!

## Решение по шагам

1. Создайте изолированные каналы-семафоры для каждого отсека.
2. Смоделируйте переполнение пула Payment Service.
3. Докажите, что пул Inventory Service продолжает успешно обрабатывать запросы.
4. Верифицируйте изоляцию ресурсов.

## Код решения

**`bulkhead_isolation_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type BulkheadPool struct {
	sem chan struct{}
}

func NewBulkhead(capacity int) *BulkheadPool {
	return &BulkheadPool{sem: make(chan struct{}, capacity)}
}

func (b *BulkheadPool) Execute(task func() error) error {
	select {
	case b.sem <- struct{}{}:
		defer func() { <-b.sem }()
		return task()
	default:
		return errors.New("bulkhead compartment capacity exceeded")
	}
}

func TestBulkheadIsolation(t *testing.T) {
	// Изолированные переборки ресурсов
	poolInventory := NewBulkhead(2)
	poolPayment := NewBulkhead(1)

	// Заполняем отсек Payment (завис)
	poolPayment.sem <- struct{}{}

	// Попытка вызвать Payment должна мгновенно получить отказ
	errPayment := poolPayment.Execute(func() error { return nil })
	if errPayment == nil {
		t.Fatal("Отсек Payment обязан быть заблокирован")
	}

	// При этом отсек Inventory обязан работать БЕЗ СБОЕВ!
	inventoryOk := false
	errInventory := poolInventory.Execute(func() error {
		inventoryOk = true
		return nil
	})

	if errInventory != nil || !inventoryOk {
		t.Fatalf("Отсек Inventory должен был успешно выполниться: %v", errInventory)
	}

	fmt.Println("Паттерн Bulkhead (Изолированные отсеки) успешно подтвержден:")
	fmt.Printf("  • Отсек Payment: %v (Заблокирован и изолирован)\n", errPayment)
	fmt.Printf("  • Отсек Inventory: Выполнен успешно (%v)\n", inventoryOk)
	fmt.Println("  • Зависание одного downstream сервиса не затронуло работу других подсистем")
}
```

ℹ️ Изоляция конкурентных ресурсов по независимым отсекам с помощью каналов-семафоров

## Под капотом

В отличие от Java thread pool, где каждый поток весит 1–2 МБ стека, горутина Go весит 2 КБ. Однако ограничение слотов Bulkhead защищает не столько память Go, сколько **сокеты downstream сервиса и пул TCP соединений `http.Transport`** от исчерпания.

## Подводные камни

Использовать один общий `http.Client` со стандартным транспортом для всех внешних вызовов: лимит соединений `MaxIdleConnsPerHost` станет общей точкой отказа. Каждому внешнему сервису выделяют свой собственный сконфигурированный `http.Client`.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Bulkhead от Rate Limiting?»
**Ответ:** 
- **Rate Limiting:** ограничивает входящую скорость запросов во времени (например 100 запросов в секунду).
- **Bulkhead:** ограничивает количество **одновременно выполняющихся в данный момент** запросов (Concurrency Limit), защищая память и потоки приложения от зависания.
