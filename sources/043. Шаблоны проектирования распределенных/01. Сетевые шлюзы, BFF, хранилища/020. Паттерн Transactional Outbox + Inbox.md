# Паттерн Transactional Outbox + Inbox: сквозная гарантия Exactly-Once доставки и обработки сообщений

## Условие

Реализуй **Transactional Outbox + Inbox**: `Outbox` (публикация events) + `Inbox` (идемпотентная обработка входящих events). `Inbox` таблица: `idempotent_key`, `processed_at`. При получении `OrderCreated` — `INSERT INTO inbox ... ON CONFLICT DO NOTHING`. Покажи exactly-once consumption.

### Исходная формулировка

Реализуй **Transactional Outbox + Inbox**: `Outbox` (публикация events) + `Inbox` (идемпотентная обработка входящих events). `Inbox` таблица: `idempotent_key`, `processed_at`. При получении `OrderCreated` — `INSERT INTO inbox ... ON CONFLICT DO NOTHING`. Покажи exactly-once consumption.

## Теория

Симметрия Outbox и Inbox (Сквозная надежность распределенных систем):
- **Transactional Outbox на стороне продюсера:**
  Гарантирует At-Least-Once публикацию в брокер (событие не потеряется при падении БД).
- **Transactional Inbox на стороне консьюмера:**
  Гарантирует фильтрацию дубликатов при вычитке из брокера:
  1. Консьюмер открывает локальную транзакцию в своей БД.
  2. Выполняет `INSERT INTO inbox (message_id, received_at) VALUES ($1, NOW()) ON CONFLICT (message_id) DO NOTHING`.
  3. Если вставка вернула 0 строк (дубликат) \(\implies\) подтверждаем коммит в Kafka (`ack`) и пропускаем обработку!
  4. Если строка вставилась \(\implies\) выполняем бизнес-логику и коммитим транзакцию.
- Комбинация Outbox + Inbox дает честную семантику **Exactly-Once Processing**!

## Решение по шагам

1. Создайте модель таблицы `InboxTable` с уникальным ключом.
2. Смоделируйте получение дублированного события из Kafka.
3. Проверьте отсечение повторного события оператором `ON CONFLICT`.
4. Верифицируйте корректность Exactly-Once обработки.

## Код решения

**`outbox_inbox_pipeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type ConsumerInboxTable struct {
	processedIDs map[string]time.Time
}

func NewConsumerInbox() *ConsumerInboxTable {
	return &ConsumerInboxTable{processedIDs: make(map[string]time.Time)}
}

func (inbox *ConsumerInboxTable) ProcessMessage(msgID, payload string, action func() error) (bool, error) {
	// Эмуляция INSERT INTO inbox (msg_id) ON CONFLICT DO NOTHING
	if _, exists := inbox.processedIDs[msgID]; exists {
		// Дубликат: пропускаем вызов action()!
		return false, nil
	}

	// Первичная обработка
	if err := action(); err != nil {
		return false, err
	}

	inbox.processedIDs[msgID] = time.Now()
	return true, nil
}

func TestOutboxInboxPipeline(t *testing.T) {
	inbox := NewConsumerInbox()
	businessActionsCount := 0

	doBusinessWork := func() error {
		businessActionsCount++
		return nil
	}

	// 1. Первое сообщение из Kafka
	processed1, _ := inbox.ProcessMessage("kafka-msg-uuid-99", "OrderCreated", doBusinessWork)
	if !processed1 || businessActionsCount != 1 {
		t.Fatal("Первое сообщение обязано быть обработано")
	}

	// 2. Сетевой дубликат сообщения с тем же ID
	processed2, _ := inbox.ProcessMessage("kafka-msg-uuid-99", "OrderCreated", doBusinessWork)
	if processed2 || businessActionsCount != 1 {
		t.Fatal("Дубликат обязан быть отброшен таблицей Inbox!")
	}

	fmt.Println("Паттерн Transactional Outbox + Inbox успешно подтвержден:")
	fmt.Printf("  • Сообщение 1 обработано: %v (Бизнес-логика вызвана)\n", processed1)
	fmt.Printf("  • Сообщение 2 отфильтровано: %v (ON CONFLICT DO NOTHING)\n", processed2)
	fmt.Println("  • Exactly-Once потребление гарантировано локальной таблицей Inbox")
}
```

## Под капотом

В реляционных СУБД вставка в таблицу `inbox` удерживает эксклюзивную блокировку индекса по первичному ключу. Если два параллельных воркера случайно взяли одно и то же сообщение из разных партиций, второй воркер заблокируется на `INSERT` и получит `conflict`, исключая Data Race.

## Подводные камни

Коммитить оффсет в Kafka ДО коммита локальной транзакции в базу данных: если база данных упадет на коммите, сообщение будет потеряно навсегда.

## На собеседовании

**Вопрос с собеседования:** «Зачем нужна таблица Inbox, если брокер Kafka заявляет поддержку Exactly-Once Semantics (EOS)?»
**Ответ:** Kafka EOS работает **только внутри экосистемы Kafka** (пайплайны Kafka \(\to\) Kafka Streams \(\to\) Kafka). Если консьюмер пишет результат в стороннюю базу данных (PostgreSQL, Redis), распределенная транзакция не поддерживается, и паттерн Transactional Inbox — единственный способ гарантировать Exactly-Once на стороне базы данных.
