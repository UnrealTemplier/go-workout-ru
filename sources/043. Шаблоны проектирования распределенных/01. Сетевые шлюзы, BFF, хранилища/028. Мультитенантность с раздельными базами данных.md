# Мультитенантность с раздельными базами данных (Separate Databases): максимальная изоляция и безопасность

## Условие

**Multi-tenancy (Separate DB)**: Каждый тенант имеет свою БД. Максимальная изоляция, но дорого и сложно масштабировать.

## Теория

Модель мультитенантности на уровне раздельных баз данных (Separate Databases):
- Премиальный уровень изоляции (Enterprise Tier):
  - Каждому корпоративному клиенту (банку, госструктуре) выделяется **отдельный физический инстанс или база данных PostgreSQL**:
    `postgres://db-sberbank.corp:5432/crm`
    `postgres://db-vtb.corp:5432/crm`
- **Преимущества:**
  1. **100% изоляция безопасности:** физически невозможно случайно прочитать чужие данные.
  2. **Индивидуальный бэкап и Restore:** возможность восстановить базу одного клиента из бэкапа без остановки остальных.
  3. **Соответствие регуляторам:** возможность разместить БД конкретного клиента в определенном дата-центре.
- **Минусы:** высокая стоимость инфраструктуры и сложный роутинг пулов соединений.

## Решение по шагам

1. Создайте реестр пулов баз данных тенантов `TenantConnectionPoolRegistry`.
2. Реализуйте динамическую маршрутизацию по идентификатору клиента.
3. Продемонстрируйте изоляцию подключений.
4. Верифицируйте безопасность модели.

## Код решения

**`separate_databases_tenancy_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type TenantDatabaseConnection struct {
	DSN      string
	StoreMap map[string]string
}

type TenantConnectionRegistry struct {
	tenants map[string]*TenantDatabaseConnection
}

func (r *TenantConnectionRegistry) GetConnection(tenantID string) (*TenantDatabaseConnection, error) {
	conn, ok := r.tenants[tenantID]
	if !ok {
		return nil, errors.New("неизвестный тенант: доступ заблокирован")
	}
	return conn, nil
}

func TestSeparateDatabasesTenancy(t *testing.T) {
	registry := &TenantConnectionRegistry{
		tenants: map[string]*TenantDatabaseConnection{
			"bank-alfa": {
				DSN:      "postgres://alfa-cluster:5432/db_alfa",
				StoreMap: map[string]string{"secret_key": "alfa-corp-secret"},
			},
			"bank-tinkoff": {
				DSN:      "postgres://tinkoff-cluster:5432/db_tinkoff",
				StoreMap: map[string]string{"secret_key": "tinkoff-corp-secret"},
			},
		},
	}

	// Запрос от клиента bank-alfa
	connAlfa, errAlfa := registry.GetConnection("bank-alfa")
	if errAlfa != nil || connAlfa.StoreMap["secret_key"] != "alfa-corp-secret" {
		t.Fatalf("Сбой получения БД Alfa: %v", errAlfa)
	}

	// Попытка доступа к несуществующей БД
	_, errUnknown := registry.GetConnection("bank-unknown")
	if errUnknown == nil {
		t.Fatal("Ожидался отказ в доступе")
	}

	fmt.Println("Мультитенантность с раздельными базами данных подтверждена:")
	fmt.Printf("  • Тенант bank-alfa:    DSN=%s (Секрет: %s)\n", connAlfa.DSN, connAlfa.StoreMap["secret_key"])
	fmt.Println("  • Абсолютная физическая изоляция: каждый тенант работает в независимом инстансе СУБД")
}
```

## Под капотом

При наличии 500 отдельных баз данных сервис не может держать открытыми по 20 соединений к каждой (это 10 000 открытых TCP сокетов). В Go пулы соединений инициализируются лениво (Lazy Connection Pool) и закрываются по таймауту неактивности `IdleTimeout = 5 * time.Minute`.

## Подводные камни

Хардкодить список DSN в конфиг-файле: при регистрации нового тенанта придется перезапускать все поды сервиса. Реестр DSN хранят в распределенном хранилище конфигураций (Consul / Vault) с динамической подгрузкой.

## На собеседовании

**Вопрос с собеседования:** «Какую модель мультитенантности выбрать для B2B SaaS продукта: Shared DB или Separate DB?»
**Ответ:** Применяют **гибридную модель (Tiered Multi-Tenancy)**:
- Бесплатные и мелкие клиенты (Free / Starter Tier) живут в **Shared DB, Shared Schema** с RLS.
- Крупные Enterprise клиенты (Enterprise Tier с SLA 99.99%) за отдельную высокую плату получают выделенный инстанс **Separate DB**.
