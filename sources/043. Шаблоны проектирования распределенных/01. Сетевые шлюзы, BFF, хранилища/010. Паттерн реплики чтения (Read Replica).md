# Паттерн реплики чтения (Read Replica): балансировка нагрузки, replication lag и стратегия read-your-own-writes

## Условие

Реализуй **Read Replica Pattern**: `Order Service` пишет в PostgreSQL primary, читает из read replicas (load balancing). Replication lag: `SELECT pg_last_xact_replay_timestamp()` — покажи eventual consistency. Стратегия: "read own writes" (писатель читает primary).

## Теория

Масштабирование чтения через реплики и борьба с лагом репликации:
- В большинстве систем нагрузка на чтение в 10–50 раз превышает запись (Read-Heavy workload).
- Решение: 1 Master (Primary) принимает `INSERT/UPDATE/DELETE`, а 3 реплики обслуживают `SELECT`.
- **Проблема Replication Lag (Лаг репликации):**
  - Пользователь создал заказ, нажал «Обновить страницу», но балансировщик направил `GET` на реплику, которая отстает на 200 мс.
  - Пользователь видит ошибку «Заказ не найден» и в панике создает дубликат!
- **Стратегия Read-Your-Own-Writes:**
  - При любой записи клиенту ставится cookie или флаг `recent_write_timestamp`.
  - В течение следующих 3 секунд все запросы чтения этого пользователя направляются **напрямую в Primary**!

## Решение по шагам

1. Создайте кластер с Master и Read Replica.
2. Смоделируйте лаг репликации.
3. Реализуйте переключатель `ReadYourOwnWritesRouter`.
4. Верифицируйте корректность чтения свежих данных создателем записи.

## Код решения

**`read_replica_lag_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DatabaseCluster struct {
	primaryStore map[string]string
	replicaStore map[string]string
}

type ReadOwnWritesRouter struct {
	cluster         *DatabaseCluster
	userLastWriteAt map[string]time.Time
}

func (r *ReadOwnWritesRouter) Write(userID, key, val string) {
	r.cluster.primaryStore[key] = val
	r.userLastWriteAt[userID] = time.Now()
	// Реплика еще не обновилась (Replication Lag!)
}

func (r *ReadOwnWritesRouter) Read(userID, key string) (string, string) {
	lastWrite, hasWritten := r.userLastWriteAt[userID]
	// Если пользователь писал в последние 2 секунды — читаем из PRIMARY!
	if hasWritten && time.Since(lastWrite) < 2*time.Second {
		return r.cluster.primaryStore[key], "READ_FROM_PRIMARY"
	}
	return r.cluster.replicaStore[key], "READ_FROM_REPLICA"
}

func TestReadReplicaLag(t *testing.T) {
	cluster := &DatabaseCluster{
		primaryStore: make(map[string]string),
		replicaStore: make(map[string]string),
	}
	router := &ReadOwnWritesRouter{
		cluster:         cluster,
		userLastWriteAt: make(map[string]time.Time),
	}

	// 1. Пользователь сохраняет заказ
	router.Write("usr-1", "order-123", "Created")

	// 2. Читает создатель (в течение 2 секунд) -> попадает в Primary!
	dataUser1, sourceUser1 := router.Read("usr-1", "order-123")
	if sourceUser1 != "READ_FROM_PRIMARY" || dataUser1 != "Created" {
		t.Fatalf("Создатель должен был прочитать из Primary: %s", sourceUser1)
	}

	// 3. Другой пользователь (читатель) -> идет в реплику (лаг)
	dataUser2, sourceUser2 := router.Read("usr-2", "order-123")
	if sourceUser2 != "READ_FROM_REPLICA" || dataUser2 != "" {
		t.Fatalf("Обычный читатель должен был пойти в реплику: %s", sourceUser2)
	}

	fmt.Println("Паттерн Read Replica и Read-Your-Own-Writes подтвержден:")
	fmt.Printf("  • Создатель записи: данные=%q (Источник: %s)\n", dataUser1, sourceUser1)
	fmt.Printf("  • Другой читатель:  данные=%q (Источник: %s, лаг репликации)\n", dataUser2, sourceUser2)
	fmt.Println("  • Стратегия ликвидирует эффект «исчезнувших данных» сразу после сохранения")
}
```

ℹ️ Устранение негативных эффектов лага репликации через стратегию Read-Your-Own-Writes

## Под капотом

В PostgreSQL лаг репликации в байтах вычисляется системным запросом: `SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) FROM pg_stat_replication`. Если лаг превышает 10 МБ, балансировщик временно исключает реплику из пула чтения.

## Подводные камни

Отправлять критичные финансовые проверки на реплику: проверка баланса счета перед списанием обязана выполняться **строго на мастере** в транзакции `SELECT ... FOR UPDATE`, иначе двойное списание неизбежно.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие асинхронной репликации от полусинхронной (Semi-Synchronous)?»
**Ответ:** 
- **Асинхронная:** Master коммитит транзакцию локально и не ждет реплик (максимальная скорость, но риск потери данных при аварии мастера).
- **Полусинхронная:** Master ждет подтверждения записи в WAL хотя бы от **одной реплики** перед отправкой ответа клиенту (гарантия сохранности данных при RPO = 0).
