# Асинхронный обмен событиями (Asynchronous Messaging): временная слабая связанность и автономность

## Условие

Реализуй **Asynchronous Messaging (Events)**: `Order Service` публикует `OrderCreated`. `Inventory Service` подписывается, обрабатывает. Покажи decoupling: services evolve independently, temporal decoupling (consumer offline OK). Когда уместно: eventual consistency acceptable.

## Теория

Принцип временной слабой связанности (Temporal Decoupling):
- В асинхронной модели Event-Driven продюсер не знает, кто и когда обработает его событие.
- **Ключевые преимущества:**
  1. **Автономия жизненного цикла:** `Inventory Service` может быть выключен для развертывания новой версии на 30 минут.
  2. `Order Service` продолжает принимать заказы клиентов с пиковой скоростью 10 000 RPS, складывая события в брокер очередей.
  3. После перезапуска `Inventory Service` спокойно вычитывает накопленные сообщения.
  4. Ни один клиент не получает ошибок!

## Решение по шагам

1. Создайте буферизированную очередь событий.
2. Опубликуйте событие заказа при отключенном сервисе склада.
3. Запустите сервис склада и вычитайте накопившиеся события.
4. Верифицируйте временную независимость.

## Код решения

**`async_temporal_decoupling_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OrderCreatedAsyncEvent struct {
	OrderID string
	SKU     string
	Qty     int
}

type EventBrokerChannel struct {
	buffer chan OrderCreatedAsyncEvent
}

func (b *EventBrokerChannel) Publish(evt OrderCreatedAsyncEvent) {
	b.buffer <- evt
}

func TestAsyncTemporalDecoupling(t *testing.T) {
	broker := &EventBrokerChannel{buffer: make(chan OrderCreatedAsyncEvent, 10)}

	// 1. OrderService публикует 2 заказа, когда InventoryService ОФФЛАЙН!
	broker.Publish(OrderCreatedAsyncEvent{OrderID: "ord-async-1", SKU: "sku-phone", Qty: 1})
	broker.Publish(OrderCreatedAsyncEvent{OrderID: "ord-async-2", SKU: "sku-watch", Qty: 2})

	// 2. InventoryService запускается позже и вычитывает очередь
	var processedOrders []string
	for len(broker.buffer) > 0 {
		evt := <-broker.buffer
		processedOrders = append(processedOrders, evt.OrderID)
	}

	if len(processedOrders) != 2 {
		t.Fatalf("Ожидалось 2 обработанных заказа: %v", processedOrders)
	}

	fmt.Println("Асинхронный обмен событиями (Temporal Decoupling) подтвержден:")
	fmt.Printf("  • Обработано заказов после подъема консьюмера: %v\n", processedOrders)
	fmt.Println("  • Продюсер и консьюмер разделены во времени: даунтайм склада не остановил прием заказов")
}
```

ℹ️ Автономия работы сервисов при временной недоступности одного из участников

## Под капотом

В Apache Kafka сообщения сохраняются в неизменяемый Commit Log с настраиваемым retention period (например `retention.ms = 7 days`). Это позволяет консьюмерам безопасно отставать в обработке на дни без риска потери данных.

## Подводные камни

Полагаться на асинхронные события там, где пользователю требуется немедленный синхронный ответ (например, проверка валидности пароля при входе): асинхронность неоправданно усложнит интерфейс.

## На собеседовании

**Вопрос с собеседования:** «Что такое Backpressure в асинхронных очередях и как Kafka защищает консьюмеров от перегрузки?»
**Ответ:** В отличие от push-брокеров (RabbitMQ), Kafka использует **pull-модель**. Консьюмер сам запрашивает сообщения методом `poll(timeout)` ровно в том темпе, в котором он способен их переварить, физически исключая переполнение оперативной памяти консьюмера при всплесках нагрузки.
