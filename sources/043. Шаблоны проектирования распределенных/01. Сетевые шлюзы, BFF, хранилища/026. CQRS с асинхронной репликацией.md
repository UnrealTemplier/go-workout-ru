# CQRS с асинхронной репликацией: CommandService на PostgreSQL и QueryService на сверхбыстром Redis

## Условие

**CQRS (Command and Query Responsibility Segregation)**: Раздели сервис на две части. `CommandService` обрабатывает POST/PUT, реализует сложную логику и пишет в PostgreSQL. `QueryService` обрабатывает GET, читает данные из сверхбыстрого Redis (или ElasticSearch), куда данные асинхронно перекладываются после записи.

## Теория

Физическое разделение сервисов по паттерну CQRS:
- При экстремальной нагрузке разделяют не просто методы в коде, а **создают два разных физических микросервиса**:
  1. `Command Service (Write)`:
     - Оптимизирован под транзакции, блокировки и ACID.
     - Масштабируется до 2–4 подов.
     - Пишет в PostgreSQL.
  2. `Query Service (Read)`:
     - Оптимизирован под чтение (In-Memory).
     - Масштабируется горизонтально до 50 подов в Kubernetes HPA.
     - Читает плоские JSON DTO из Redis за 0.5 мс.
  3. Асинхронная шина событий синхронизирует базы данных.

## Решение по шагам

1. Создайте `CommandService` с записью в нормализованное хранилище.
2. Реализуйте перенос проекции в `QueryService` хранилище Redis.
3. Продемонстрируйте быстрое чтение из QueryService.
4. Верифицируйте разделение сервисов.

## Код решения

**`cqrs_command_query_services_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CommandService struct {
	postgresDB map[string]float64
	syncEvents chan string
}

func (c *CommandService) HandlePostOrder(id string, amount float64) {
	c.postgresDB[id] = amount
	// Асинхронное событие репликации
	c.syncEvents <- id
}

type QueryService struct {
	redisCache map[string]string
}

func (q *QueryService) HandleGetOrder(id string) (string, bool) {
	val, ok := q.redisCache[id]
	return val, ok
}

func TestCQRSCommandQueryServices(t *testing.T) {
	syncCh := make(chan string, 1)
	cmdSvc := &CommandService{postgresDB: make(map[string]float64), syncEvents: syncCh}
	querySvc := &QueryService{redisCache: make(map[string]string)}

	// 1. Команда записи (Command Service)
	cmdSvc.HandlePostOrder("ord-26", 18500.0)

	// 2. Асинхронный воркер обновляет Redis витрину
	updatedID := <-syncCh
	querySvc.redisCache[updatedID] = fmt.Sprintf("{\"id\":\"%s\",\"total\":%.2f}", updatedID, cmdSvc.postgresDB[updatedID])

	// 3. Запрос чтения (Query Service)
	jsonResp, found := querySvc.HandleGetOrder("ord-26")
	if !found || jsonResp != "{\"id\":\"ord-26\",\"total\":18500.00}" {
		t.Fatalf("Сбой чтения из QueryService: %s", jsonResp)
	}

	fmt.Println("CQRS (CommandService vs QueryService) успешно подтвержден:")
	fmt.Println("  • CommandService записал транзакцию в PostgreSQL")
	fmt.Printf("  • QueryService мгновенно прочитал денормализованный JSON из Redis: %s\n", jsonResp)
	fmt.Println("  • Независимое горизонтальное масштабирование чтения и записи реализовано")
}
```

ℹ️ Разделение микросервисов команд (PostgreSQL) и запросов (Redis) с асинхронной репликацией

## Под капотом

В QueryService запросы `GET` читаются из Redis через MGET пайплайнинг: за один TCP round-trip сервис считывает сразу 50 заказов для страницы пользователя, обеспечивая время генерации страницы менее 3 мс.

## Подводные камни

Пытаться синхронизировать Redis синхронным HTTP-вызовом прямо из CommandService: падение Redis приведет к отказу создания заказов, уничтожая преимущество слабой связанности.

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать, что старое событие из очереди не перезапишет более свежие данные в Redis витрине (Out-of-Order Delivery)?»
**Ответ:** Каждое событие содержит монотонно растущую версию или timestamp агрегата (`version = 5`). Перед обновлением Redis воркер выполняет Lua-скрипт: `if new_version > current_version then redis.set(...) end`. События со старыми версиями отбрасываются.
