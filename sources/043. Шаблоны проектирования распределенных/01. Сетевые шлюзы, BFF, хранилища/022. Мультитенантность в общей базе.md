# Мультитенантность в общей базе и общей схеме (Shared DB, Shared Schema): tenant_id и Row-Level Security

## Условие

**Multi-tenancy (Shared DB, Shared Schema)**: Все тенанты в одной БД, каждая таблица имеет `tenant_id`. Используйте Row-Level Security (RLS) в PostgreSQL для изоляции.

## Теория

Архитектура SaaS с разделяемой схемой (Shared Database, Shared Schema):
- Все клиенты (Тенанты) хранятся в **одной таблице одной базы данных**.
- Каждая строка помечается колонкой `tenant_id`.
- **Риск утечки данных:** если программист забудет написать `WHERE tenant_id = 'org-123'`, компания А увидит счета компании Б!
- **Защита через PostgreSQL Row-Level Security (RLS):**
  1. Включается защита таблицы: `ALTER TABLE orders ENABLE ROW LEVEL SECURITY;`
  2. Создается политика безопасности:
     `CREATE POLICY tenant_isolation ON orders USING (tenant_id = current_setting('app.current_tenant_id'));`
  3. Go-сервис перед выполнением запроса выставляет переменную сессии:
     `SET LOCAL app.current_tenant_id = 'org-123';`
  4. PostgreSQL на уровне ядра базы данных **физически блокирует** доступ к чужим строкам, даже если в SQL запросе забыли `WHERE`!

## Решение по шагам

1. Создайте эмулятор таблицы с колонкой `TenantID`.
2. Реализуйте сессионный контекст текущего тенанта.
3. Смоделируйте фильтрацию RLS на уровне хранилища.
4. Верифицируйте невозможность чтения чужих данных.

## Код решения

**`multi_tenancy_rls_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type RLSOrderRow struct {
	TenantID string
	OrderID  string
	Amount   float64
}

type DatabaseWithRLSEmulator struct {
	rows []RLSOrderRow
}

type tenantCtxKey struct{}

func WithTenantID(ctx context.Context, tenant string) context.Context {
	return context.WithValue(ctx, tenantCtxKey{}, tenant)
}

func (db *DatabaseWithRLSEmulator) QueryOrdersRLS(ctx context.Context) []RLSOrderRow {
	tenant, _ := ctx.Value(tenantCtxKey{}).(string)

	var filtered []RLSOrderRow
	// Ядро СУБД применяет политику RLS: tenant_id = current_tenant
	for _, r := range db.rows {
		if r.TenantID == tenant {
			filtered = append(filtered, r)
		}
	}
	return filtered
}

func TestMultiTenancyRLS(t *testing.T) {
	db := &DatabaseWithRLSEmulator{
		rows: []RLSOrderRow{
			{TenantID: "tenant-yandex", OrderID: "ord-ya-1", Amount: 5000.0},
			{TenantID: "tenant-ozon", OrderID: "ord-oz-2", Amount: 7500.0},
		},
	}

	// Запрос от имени Яндекс
	ctxYandex := WithTenantID(context.Background(), "tenant-yandex")
	ordersYandex := db.QueryOrdersRLS(ctxYandex)

	if len(ordersYandex) != 1 || ordersYandex[0].OrderID != "ord-ya-1" {
		t.Fatalf("Сбой RLS изоляции: %+v", ordersYandex)
	}

	fmt.Println("Мультитенантность (Shared DB, Shared Schema с RLS) подтверждена:")
	fmt.Printf("  • Тенант tenant-yandex видит только свои записи: %s (%.2f руб)\n",
		ordersYandex[0].OrderID, ordersYandex[0].Amount)
	fmt.Println("  • Доступ к записям tenant-ozon полностью заблокирован политикой безопасности")
}
```

ℹ️ Изоляция данных тенантов в общей схеме с помощью механизмов Row-Level Security

## Под капотом

В пуле соединений `pgxpool` переменная `SET LOCAL` действует строго в пределах текущей транзакции. После коммита транзакции сессия очищается, предотвращая утечку чужого `tenant_id` следующей горутине, взявшей это соединение из пула.

## Подводные камни

Выполнять запросы под суперпользователем `postgres`: в PostgreSQL суперпользователь по умолчанию **игнорирует политики RLS** (`BYPASSRLS`). Go-сервис обязан подключаться под ограниченной сервисной ролью приложения.

## На собеседовании

**Вопрос с собеседования:** «В чем главное преимущество Shared Schema перед отдельными базами данных для SaaS на 100 000 клиентов?»
**Ответ:** Стоимость и масштабируемость инфраструктуры. Поднять 100 000 отдельных баз данных или схем в PostgreSQL невозможно (исчерпание файловых дескрипторов и памяти shared_buffers). Shared Schema позволяет обслуживать сотни тысяч бесплатных клиентов на одном сервере БД.
