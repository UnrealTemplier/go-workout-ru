# Паттерн Backend-for-Frontend (BFF): оптимизация контрактов для Mobile, Web и Admin клиентов

## Условие

Реализуй **Backend-for-Frontend (BFF)**: `Mobile BFF` (агрегирует данные для iOS/Android: мало полей, оптимизированные запросы), `Web BFF` (больше данных, SSR-ready), `Admin BFF` (все поля, фильтры, экспорт). Покажи, что generic API плох для всех клиентов.

## Теория

Проблема универсального Generic API и решение через BFF:
- Попытка сделать «один API на всех»:
  - Мобильные приложения получают огромные JSON с десятками ненужных полей по медленному 3G (Over-fetching).
  - Веб-приложения вынуждены делать 5 последовательных запросов для отображения одной страницы (Under-fetching).
  - Админ-панель требует детализированные аудиторские данные, которые засоряют публичный API.
- **Паттерн BFF:**
  - Каждый фронтенд имеет свой персональный бэкенд.
  - `Mobile BFF`: агрегирует 4 запроса в 1 плоский JSON, сжимает изображения.
  - `Web BFF`: формирует структурированный граф данных для React Server Components.
  - `Admin BFF`: отдает полную историю изменений, системные метки и права доступа.

## Решение по шагам

1. Создайте доменный источник данных `OrderData`.
2. Реализуйте презентер `MobileBFFPresenter` со сжатыми полями.
3. Реализуйте презентер `AdminBFFPresenter` с аудитом.
4. Продемонстрируйте разницу объемов и специфику данных.

## Код решения

**`bff_multi_client_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type FullOrderEntity struct {
	ID             string
	CustomerName   string
	SecretAdminNote string
	InternalAuditID string
	TotalRub       float64
}

// Mobile BFF DTO (Экономия батареи и мобильного интернета)
type MobileOrderDTO struct {
	ID    string  `json:"id"`
	Total float64 `json:"total"`
}

// Admin BFF DTO (100% данных для оператора)
type AdminOrderDTO struct {
	ID        string  `json:"id"`
	Customer  string  `json:"customer"`
	Total     float64 `json:"total"`
	AdminNote string  `json:"admin_note"`
	AuditID   string  `json:"audit_id"`
}

func RenderForMobile(o FullOrderEntity) []byte {
	dto := MobileOrderDTO{ID: o.ID, Total: o.TotalRub}
	b, _ := json.Marshal(dto)
	return b
}

func RenderForAdmin(o FullOrderEntity) []byte {
	dto := AdminOrderDTO{
		ID:        o.ID,
		Customer:  o.CustomerName,
		Total:     o.TotalRub,
		AdminNote: o.SecretAdminNote,
		AuditID:   o.InternalAuditID,
	}
	b, _ := json.Marshal(dto)
	return b
}

func TestBFFMultiClient(t *testing.T) {
	order := FullOrderEntity{
		ID:             "ord-9988",
		CustomerName:   "Виктор Корнеплод",
		SecretAdminNote: "Подозрение на фрод, проверить паспорт",
		InternalAuditID: "AUDIT-SEC-77123",
		TotalRub:       14990.0,
	}

	mobileBytes := RenderForMobile(order)
	adminBytes := RenderForAdmin(order)

	if len(mobileBytes) >= len(adminBytes) {
		t.Fatalf("Mobile DTO обязан быть меньше Admin DTO: %d >= %d", len(mobileBytes), len(adminBytes))
	}

	fmt.Println("Паттерн Backend-for-Frontend (BFF) успешно подтвержден:")
	fmt.Printf("  • Mobile BFF JSON (%d байт): %s\n", len(mobileBytes), string(mobileBytes))
	fmt.Printf("  • Admin BFF JSON  (%d байт): %s\n", len(adminBytes), string(adminBytes))
	fmt.Println("  • Конфиденциальные заметки и аудит изолированы от мобильного клиента")
}
```

## Под капотом

BFF избавляет мобильные устройства от проблемы «Radio State Machine»: каждый отдельный HTTP-запрос переводит 4G/5G модем смартфона в энергозатратный режим Full Power. Схлопывание 5 вызовов в 1 через BFF экономит до 40% заряда батареи пользователя.

## Подводные камни

Размещать в BFF бизнес-логику расчетов: BFF должен быть тонким оркестратором представления. Расчеты налогов и списаний принадлежат Domain Core микросервисам.

## На собеседовании

**Вопрос с собеседования:** «Кто должен разрабатывать и поддерживать сервис Mobile BFF: команда мобильной разработки или бэкендеры?»
**Ответ:** В лучших практиках BigTech (SoundCloud, Netflix) BFF принадлежит **команде мобильного клиента**. Мобильные разработчики сами определяют удобный контракт и вносят изменения без ожидания релиза бэкенд-команд монолита.
