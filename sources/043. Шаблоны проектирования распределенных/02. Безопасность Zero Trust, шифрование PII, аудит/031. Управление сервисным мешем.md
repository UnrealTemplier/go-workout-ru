# Управление сервисным мешем (Service Mesh Traffic Management): канареечные релизы и взвешенный роутинг

## Условие

**Service Mesh (Istio)**: Настройте `VirtualService` для canary-деплоя: 90% трафика на `v1`, 10% на `v2`. Добавьте зеркалирование трафика (mirroring/shadowing) для тестирования под нагрузкой.

### Исходная формулировка

**Tenant-aware Routing**: В API Gateway извлекайте `tenant_id` из JWT/subdomain и роутите запрос к нужной БД или региону.

## Теория

Маршрутизация трафика в Service Mesh (Istio / Envoy):
- **Canary Deployment (Канареечный релиз):**
  - Новая версия сервиса `v2` развертывается рядом со стабильной `v1`.
  - Istio `VirtualService` делит входящий трафик по весам: `v1 = 90%`, `v2 = 10%`.
  - Если метрики ошибок на `v2` в норме, вес плавно увеличивают: \(10\% \to 50\% \to 100\%\).
- **Теневое зеркалирование трафика (Traffic Shadowing / Mirroring):**
  - 100% реальных клиентских запросов отправляются на `v1` (клиент получает ответ от v1).
  - Копия (тень) 100% запросов асинхронно пересылается на `v2`.
  - Ответ от `v2` отбрасывается.
  - Позволяет безопасно протестировать новую версию под боевой нагрузкой без риска для клиентов!

## Решение по шагам

1. Создайте эмулятор маршрутизатора с процентным распределением весов.
2. Реализуйте канареечное ветвление 90/10.
3. Реализуйте теневое зеркалирование запросов.
4. Проверьте поведение под нагрузкой в 100 запросов.

## Код решения

**`service_mesh_traffic_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TrafficWeightRouter struct {
	v1Calls int
	v2Calls int
	shadowCalls int
}

func (r *TrafficWeightRouter) RouteRequest(requestID int, shadowEnabled bool) string {
	// Теневое зеркалирование (Shadowing)
	if shadowEnabled {
		r.shadowCalls++
	}

	// Канареечное распределение 90% на v1, 10% на v2
	if requestID%10 == 0 {
		r.v2Calls++
		return "Handled by v2 (Canary 10%)"
	}

	r.v1Calls++
	return "Handled by v1 (Stable 90%)"
}

func TestServiceMeshTraffic(t *testing.T) {
	router := &TrafficWeightRouter{}

	for i := 1; i <= 100; i++ {
		_ = router.RouteRequest(i, true)
	}

	if router.v1Calls != 90 || router.v2Calls != 10 || router.shadowCalls != 100 {
		t.Fatalf("Сбой распределения трафика: v1=%d, v2=%d, shadow=%d",
			router.v1Calls, router.v2Calls, router.shadowCalls)
	}

	fmt.Println("Управление трафиком в Service Mesh успешно подтверждено:")
	fmt.Printf("  • Версия v1 (Стабильная): %d вызовов (90%%)\n", router.v1Calls)
	fmt.Printf("  • Версия v2 (Канареечная): %d вызовов (10%%)\n", router.v2Calls)
	fmt.Printf("  • Теневые копии запросов: %d зеркалировано на v2 для тестирования\n", router.shadowCalls)
}
```

ℹ️ Канареечное распределение трафика 90/10 и зеркалирование запросов (Traffic Shadowing)

## Под капотом

Envoy выполняет зеркалирование через фильтр `envoy.filters.http.router` с параметром `request_mirror_policies`. Дубликат запроса отправляется в фоновом режиме, а таймауты или падения теневого сервиса никак не влияют на время ответа клиенту.

## Подводные камни

Зеркалировать запросы, изменяющие состояние (POST/PUT), если теневой сервис пишет в реальную базу данных: это приведет к порче данных и дублированию транзакций. Зеркалируют либо только GET запросы, либо подключают теневой сервис к тестовой копии БД.

## На собеседовании

**Вопрос с собеседования:** «Как направить на канареечную версию v2 запросы только определенных пользователей (например сотрудников компании)?»
**Ответ:** В манифесте `VirtualService` настраивают правило соответствия заголовков HTTP: `match: - headers: x-user-role: exact: employee`. Все сотрудники попадают на `v2`, а 100% внешних клиентов продолжают работать с проверенной `v1`.
