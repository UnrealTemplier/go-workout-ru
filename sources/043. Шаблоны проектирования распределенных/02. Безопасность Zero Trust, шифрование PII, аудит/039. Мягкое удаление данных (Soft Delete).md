# Мягкое удаление данных (Soft Delete): пометка deleted_at, фильтрация выборок и восстановление

## Условие

**Soft Delete**: Не удаляйте данные физически, помечайте как `deleted_at`. Это нужно для audit и восстановления.

## Теория

Паттерн мягкого удаления (Soft Delete):
- В корпоративных системах физическое удаление (`DELETE FROM table`) категорически запрещено для большинства бизнес-сущностей.
- **Причины:**
  1. Случайное удаление пользователем: возможность мгновенного восстановления кликом «Восстановить» в техподдержке.
  2. Разрушение целостности связей: физическое удаление клиента сломает историю финансовых проводок и чеков за прошлый год.
  3. Требования налогового и финансового аудита.
- **Реализация:**
  - В таблицу добавляется колонка `deleted_at TIMESTAMPTZ NULL`.
  - Удаление: `UPDATE orders SET deleted_at = NOW() WHERE id = $1`.
  - Чтение: `SELECT * FROM orders WHERE deleted_at IS NULL`.

## Решение по шагам

1. Создайте структуру сущности с полем `DeletedAt *time.Time`.
2. Реализуйте метод мягкого удаления `SoftDelete()`.
3. Реализуйте фильтрацию активных записей.
4. Продемонстрируйте возможность восстановления записи.

## Код решения

**`soft_delete_pattern_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type SoftDeletableEntity struct {
	ID        string
	Title     string
	DeletedAt *time.Time
}

func (e *SoftDeletableEntity) IsActive() bool {
	return e.DeletedAt == nil
}

func (e *SoftDeletableEntity) MarkDeleted() {
	now := time.Now()
	e.DeletedAt = &now
}

func (e *SoftDeletableEntity) Restore() {
	e.DeletedAt = nil
}

func TestSoftDeletePattern(t *testing.T) {
	doc := &SoftDeletableEntity{ID: "doc-101", Title: "Годовой финансовый отчет"}

	if !doc.IsActive() {
		t.Fatal("Новый документ обязан быть активен")
	}

	// 1. Мягкое удаление
	doc.MarkDeleted()

	if doc.IsActive() || doc.DeletedAt == nil {
		t.Fatal("Документ должен быть помечен как удаленный")
	}

	// 2. Восстановление
	doc.Restore()

	if !doc.IsActive() || doc.DeletedAt != nil {
		t.Fatal("Документ успешно восстановлен")
	}

	fmt.Println("Паттерн Мягкого удаления (Soft Delete) успешно подтвержден:")
	fmt.Printf("  • Документ %s: Статус активности = %v\n", doc.ID, doc.IsActive())
	fmt.Println("  • Записи сохраняются на диске для аудита и мгновенного восстановления без потери связей")
}
```

## Под капотом

Для оптимизации выборок с Soft Delete в PostgreSQL создают **частичный индекс (Partial Index)**: `CREATE INDEX idx_orders_active ON orders (customer_id) WHERE deleted_at IS NULL;`. Индекс не тратит память на удаленные записи и работает в разы быстрее обычного B-Tree индекса.

## Подводные камни

Нарушение уникальности `UNIQUE(email)`: если пользователь удалил аккаунт, а затем регистрируется заново с тем же email, обычный уникальный индекс вызовет ошибку. Решение: частичный индекс `CREATE UNIQUE INDEX uniq_active_email ON users (email) WHERE deleted_at IS NULL;`.

## На собеседовании

**Вопрос с собеседования:** «Как соблюдать требования GDPR 'Право на забвение' при использовании Soft Delete?»
**Ответ:** При запросе на удаление аккаунта по закону GDPR персональные данные (email, ФИО, телефон) **анонимизируют (Data Scrubbing)**: `email = 'deleted_user_42@anonymized.local'`, хэшируются или затираются нулями, а сама строка помечается `deleted_at`. Это удаляет PII, но сохраняет финансовую целостность бухгалтерских проводок.
