# Многоуровневая валидация входных данных (Input Validation Defense): Whitelist подход, экранирование и защита от инъекций

## Условие

Реализуй **Input Validation Defense**: `whitelist` approach (accept known-good), not `blacklist` (reject known-bad). Validate at edge (API Gateway), validate at service, validate at database (constraints). Sanitize: HTML escape, SQL parameterization, path traversal prevention.

## Теория

Принцип глубокой защиты валидации (Whitelist Validation):
- **Blacklist (Антипаттерн):** попытка заблокировать известные плохие символы (`<script>`, `' OR 1=1`). Хакеры всегда найдут способ обойти черный список через Unicode, шестнадцатеричные коды или нулевые байты.
- **Whitelist (Enterprise стандарт):** разрешать **строго то, что соответствует формату**.
  - Имя пользователя: строго `^[a-zA-Z0-9_]{3,20}$`.
- **Трехуровневая валидация (Three-Tier Defense):**
  1. `Edge (Gateway)`: проверка размера тела (до 10 МБ), Content-Type и JSON-схемы.
  2. `Service Domain`: валидация бизнес-правил и инвариантов.
  3. `Database`: проверка `CHECK`, `NOT NULL`, параметризованные запросы `$1, $2` (защита от SQL-инъекций).

## Решение по шагам

1. Создайте Whitelist-валидатор для логинов и файловых путей.
2. Продемонстрируйте блокировку Path Traversal атаки (`../../etc/passwd`).
3. Продемонстрируйте блокировку XSS инъекций через HTML экранирование.
4. Верифицируйте чистоту входных данных.

## Код решения

**`input_validation_defense_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"html"
	"path/filepath"
	"regexp"
	"strings"
	"testing"
)

var usernameWhitelistRegex = regexp.MustCompile(`^[a-zA-Z0-9_]{3,16}$`)

func ValidateUsernameWhitelist(username string) error {
	if !usernameWhitelistRegex.MatchString(username) {
		return errors.New("invalid username: only alphanumeric and underscore allowed (3-16 chars)")
	}
	return nil
}

func SanitizeFilePath(baseDir, requestedPath string) (string, error) {
	// Защита от Path Traversal (../../etc/passwd)
	cleanPath := filepath.Clean(requestedPath)
	fullPath := filepath.Join(baseDir, cleanPath)

	if !strings.HasPrefix(fullPath, filepath.Clean(baseDir)) {
		return "", errors.New("security violation: path traversal detected")
	}
	return fullPath, nil
}

func TestInputValidationDefense(t *testing.T) {
	// 1. Whitelist валидация логина
	if err := ValidateUsernameWhitelist("artur_2026"); err != nil {
		t.Fatalf("Валидный логин отклонен: %v", err)
	}

	errBadLogin := ValidateUsernameWhitelist("<script>alert(1)</script>")
	if errBadLogin == nil {
		t.Fatal("XSS инъекция обязана быть заблокирована Whitelist-регуляркой")
	}

	// 2. Защита от Path Traversal
	_, errTraversal := SanitizeFilePath("/var/app/uploads", "../../etc/shadow")
	if errTraversal == nil {
		t.Fatal("Path Traversal атака обязана быть перехвачена")
	}

	// 3. Экранирование HTML
	dangerousInput := "<b>Привет & 'пока'</b>"
	safeHTML := html.EscapeString(dangerousInput)

	fmt.Println("Многоуровневая валидация (Input Validation Defense) подтверждена:")
	fmt.Printf("  • XSS логин заблокирован: %v\n", errBadLogin)
	fmt.Printf("  • Path Traversal заблокирован: %v\n", errTraversal)
	fmt.Printf("  • HTML экранирован: %s\n", safeHTML)
}
```

## Под капотом

В драйверах баз данных Go (`database/sql`, `pgx`) параметризованные запросы `db.Query("SELECT * FROM users WHERE name = $1", name)` отправляют SQL-запрос и параметры в разных пакетах протокола PostgreSQL (`Parse` и `Bind`). База компилирует AST дерева запроса до получения параметров, что делает SQL-инъекции физически невозможными.

## Подводные камни

Использовать конкатенацию строк `fmt.Sprintf("SELECT * FROM users WHERE id = '%s'", id)`: это критическая уязвимость SQL Injection (CWE-89), позволяющая злоумышленнику украсть всю базу данных.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go валидацию не стоит строить только на тегах структур (например go-playground/validator)?»
**Ответ:** Теги структур отлично подходят для синтаксической проверки DTO на входе (длина строки, regex). Но они не способны проверить семантические доменные инварианты («Дата окончания не может быть раньше даты начала», «Сумма перевода не превышает суточный лимит»). Доменную валидацию реализуют методами сущностей в ядре бизнеса.
