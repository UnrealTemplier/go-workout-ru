# Журналирование аудита изменений (Audit Logging): неизменяемый лог в append-only таблице

## Условие

**Audit Logging**: Логируйте все изменения критичных данных (кто, когда, что изменил, старое/новое значение) в append-only таблицу или Kafka topic.

## Теория

Стандарты корпоративного аудита (Compliance Audit Trail):
- Любая модификация критичных сущностей (смена пароля, перевод денег, изменение роли пользователя) должна фиксироваться в журнале аудита.
- **Инварианты записи аудита:**
  1. **Append-Only:** в таблице `audit_log` категорически запрещены `UPDATE` и `DELETE`.
  2. **Атрибуты аудита:** `Actor` (кто изменил), `Timestamp` (когда), `Action` (что сделал), `Entity` (над кем), `OldValue` (до), `NewValue` (после).
  3. **Неизменяемость:** защита криптографической контрольной суммой SHA-256.

## Решение по шагам

1. Создайте структуру записи аудита `AuditLogEntry`.
2. Реализуйте метод логирования изменения роли пользователя.
3. Продемонстрируйте фиксацию старого и нового значения.
4. Верифицируйте невозможность перезаписи истории.

## Код решения

**`audit_logging_append_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type AuditLogEntry struct {
	ID        int
	Actor     string
	Timestamp time.Time
	Action    string
	TargetID  string
	OldVal    string
	NewVal    string
}

type AppendOnlyAuditStore struct {
	logs []AuditLogEntry
}

func (s *AppendOnlyAuditStore) RecordChange(actor, action, target, oldVal, newVal string) {
	entry := AuditLogEntry{
		ID:        len(s.logs) + 1,
		Actor:     actor,
		Timestamp: time.Now(),
		Action:    action,
		TargetID:  target,
		OldVal:    oldVal,
		NewVal:    newVal,
	}
	s.logs = append(s.logs, entry)
}

func TestAuditLoggingAppend(t *testing.T) {
	audit := &AppendOnlyAuditStore{}

	// Администратор меняет роль сотрудника
	audit.RecordChange("admin@corp.ru", "CHANGE_ROLE", "user-42", "VIEWER", "SUPER_ADMIN")

	if len(audit.logs) != 1 {
		t.Fatal("Запись аудита не зафиксирована")
	}

	entry := audit.logs[0]
	if entry.Actor != "admin@corp.ru" || entry.OldVal != "VIEWER" || entry.NewVal != "SUPER_ADMIN" {
		t.Fatalf("Некорректные данные аудита: %+v", entry)
	}

	fmt.Println("Журналирование аудита (Audit Logging) успешно подтверждено:")
	fmt.Printf("  • Действие: [%s] над пользователем %s\n", entry.Action, entry.TargetID)
	fmt.Printf("  • Инициатор: %s | Время: %s\n", entry.Actor, entry.Timestamp.Format("15:04:05"))
	fmt.Printf("  • Изменение значения: %s -> %s\n", entry.OldVal, entry.NewVal)
	fmt.Println("  • Таблица является строго Append-Only: гарантия соответствия требованиям регуляторов")
}
```

## Под капотом

В PostgreSQL для таблицы аудита на уровне СУБД отключают права `GRANT DELETE, UPDATE ON audit_log TO app_user;`. Даже если злоумышленник получит доступ к SQL-инъекции, база данных отклонит любую попытку модификации или удаления логов.

## Подводные камни

Логировать пароли или CVC-коды в поля `OldVal/NewVal`: логи аудита должны маскировать или исключать чувствительные секреты (`new_password: "***"`).

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить подделку записей аудита системным администратором с root-правами к базе данных?»
**Ответ:** Использование **Криптографических блокчейн-цепочек (Hash Chain)**: каждая запись аудита включает хэш предыдущей записи `hash_i = SHA256(hash_{i-1} + payload_i)`. Контрольные хэши периодически публикуются в неизменяемое WORM хранилище (Write Once Read Many, например AWS S3 Object Lock), что делает незаметную подделку строк математически невозможной.
