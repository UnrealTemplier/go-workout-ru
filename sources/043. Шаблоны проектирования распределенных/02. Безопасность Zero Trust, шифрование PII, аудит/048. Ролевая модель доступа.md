# Ролевая модель доступа (Role-Based Access Control / RBAC): роли, разрешения и проверка прав на ресурсы

## Условие

**RBAC (Role-Based Access Control)**: Реализуйте систему ролей (`admin`, `manager`, `user`) с permissions на уровне ресурсов (`orders:read`, `orders:write`).

## Теория

Принципы Role-Based Access Control (RBAC):
- Пользователям **не назначают права напрямую**.
- **Двухуровневая модель:**
  1. Пользователю назначается одна или несколько **Ролей** (`admin`, `manager`, `customer`).
  2. Каждая роль содержит набор дискретных **Разрешений (Permissions)**:
     - `orders:read` — право просматривать заказы.
     - `orders:write` — право создавать и изменять заказы.
     - `orders:delete` — право отменять заказы.
- Проверка в коде выполняется **строго по Permissions**, а не по именам ролей:
  `if !user.HasPermission("orders:write") { return 403 Forbidden }`.

## Решение по шагам

1. Создайте карту связывания ролей и прав доступа.
2. Создайте модель пользователя со списком ролей.
3. Реализуйте метод проверки прав `HasPermission`.
4. Верифицируйте разграничение доступа для разных ролей.

## Код решения

**`rbac_access_control_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type Permission string

const (
	PermOrdersRead   Permission = "orders:read"
	PermOrdersWrite  Permission = "orders:write"
	PermOrdersDelete Permission = "orders:delete"
)

var RolePermissions = map[string][]Permission{
	"user":    {PermOrdersRead},
	"manager": {PermOrdersRead, PermOrdersWrite},
	"admin":   {PermOrdersRead, PermOrdersWrite, PermOrdersDelete},
}

type RBACSubject struct {
	ID    string
	Roles []string
}

func (s *RBACSubject) HasPermission(perm Permission) bool {
	for _, role := range s.Roles {
		for _, p := range RolePermissions[role] {
			if p == perm {
				return true
			}
		}
	}
	return false
}

func TestRBACAccessControl(t *testing.T) {
	regularUser := &RBACSubject{ID: "u-reg", Roles: []string{"user"}}
	managerUser := &RBACSubject{ID: "u-mgr", Roles: []string{"manager"}}

	if !regularUser.HasPermission(PermOrdersRead) {
		t.Fatal("User должен иметь право orders:read")
	}

	if regularUser.HasPermission(PermOrdersWrite) {
		t.Fatal("User НЕ должен иметь право orders:write")
	}

	if !managerUser.HasPermission(PermOrdersWrite) {
		t.Fatal("Manager должен иметь право orders:write")
	}

	if managerUser.HasPermission(PermOrdersDelete) {
		t.Fatal("Manager НЕ должен иметь право orders:delete")
	}

	fmt.Println("Ролевая модель доступа (RBAC) успешно подтверждена:")
	fmt.Printf("  • Пользователь User:    orders:read=%v, orders:write=%v\n",
		regularUser.HasPermission(PermOrdersRead), regularUser.HasPermission(PermOrdersWrite))
	fmt.Printf("  • Менеджер Manager:     orders:write=%v, orders:delete=%v\n",
		managerUser.HasPermission(PermOrdersWrite), managerUser.HasPermission(PermOrdersDelete))
}
```

ℹ️ Разграничение прав доступа к ресурсам на основе ролевой матрицы RBAC

## Под капотом

В микросервисах на Go права пользователя упаковываются в claims JWT-токена: `{"sub": "123", "permissions": ["orders:read", "orders:write"]}`. Микросервис проверяет права локально за 10 наносекунд без обращения к базе данных авторизации.

## Подводные камни

Хардкодить проверку ролей `if user.Role == "admin"`: если завтра появится роль `super_manager` с теми же правами, вам придется искать и переписывать все `if` по всему коду. Проверяют строго разрешение: `HasPermission(PermOrdersWrite)`.

## На собеседовании

**Вопрос с собеседования:** «В чем фундаментальное ограничение модели RBAC перед ABAC?»
**Ответ:** RBAC не может выразить контекстные условия. Например: «Менеджер может редактировать заказ только в том случае, если этот заказ относится к его региональному филиалу и сумма меньше 1 000 000 рублей». Для таких правил требуется **ABAC (Attribute-Based Access Control)**.
