# Сага на основе хореографии событий (Saga Choreography): цепочка событий и компенсирующий откат заказа

## Условие

**Saga Pattern (Распределенная транзакция)**: Пользователь покупает товар. Участвуют `OrderService` (создает заказ) и `BillingService` (списывает деньги). Напиши Сагу (через хореографию событий). Если `BillingService` отвечает "Денег нет", он шлет событие `PaymentFailed`. `OrderService` ловит его и запускает *компенсирующую транзакцию* — меняет статус заказа на "Отменен".

## Теория

Децентрализованная Сага (Saga Choreography):
- В хореографии нет единого оркестратора-босса. Сервисы реагируют на события соседей:
  1. `OrderService`: создает заказ со статусом `PENDING`, публикует событие `OrderCreated`.
  2. `BillingService`: слушает `OrderCreated`, пытается списать баланс.
  3. **Ветка сбоя (Компенсация):**
     - Если на счете недостаточно средств \(\implies\) `BillingService` публикует `PaymentFailed`.
     - `OrderService` слушает `PaymentFailed` и запускает компенсирующее действие: переводит статус заказа в `CANCELLED`.
- Система возвращается в согласованное состояние без единой распределенной блокировки!

## Решение по шагам

1. Создайте модели состояний заказа в `OrderService`.
2. Реализуйте генерацию события `PaymentFailed` в `BillingService`.
3. Реализуйте обработчик компенсации в `OrderService`.
4. Верифицируйте корректный переход статуса в CANCELLED.

## Код решения

**`saga_choreography_compensation_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ChoreographyOrderState struct {
	ID     string
	Status string
}

type OrderServiceChoreography struct {
	orders map[string]*ChoreographyOrderState
}

func (s *OrderServiceChoreography) HandleOrderCreate(id string) {
	s.orders[id] = &ChoreographyOrderState{ID: id, Status: "PENDING"}
}

func (s *OrderServiceChoreography) OnPaymentFailedEvent(orderID string) {
	// Компенсирующая транзакция Саги
	if order, exists := s.orders[orderID]; exists {
		order.Status = "CANCELLED"
	}
}

func TestSagaChoreographyCompensation(t *testing.T) {
	orderSvc := &OrderServiceChoreography{orders: make(map[string]*ChoreographyOrderState)}

	// 1. Создание заказа
	orderSvc.HandleOrderCreate("ord-choreo-101")
	if orderSvc.orders["ord-choreo-101"].Status != "PENDING" {
		t.Fatal("Заказ обязан быть в статусе PENDING")
	}

	// 2. BillingService шлет событие сбоя оплаты
	orderSvc.OnPaymentFailedEvent("ord-choreo-101")

	if orderSvc.orders["ord-choreo-101"].Status != "CANCELLED" {
		t.Fatalf("Компенсация не сработала: статус=%s", orderSvc.orders["ord-choreo-101"].Status)
	}

	fmt.Println("Saga Choreography с компенсирующей транзакцией подтверждена:")
	fmt.Printf("  • Итоговый статус заказа ord-choreo-101: %s\n", orderSvc.orders["ord-choreo-101"].Status)
	fmt.Println("  • Децентрализованная реакция на событие PaymentFailed успешно вернула систему в консистентный статус")
}
```

ℹ️ Децентрализованный компенсирующий откат заказа при сбое в сервисе оплаты

## Под капотом

В хореографии события связываются с помощью метаданных трассировки: заголовок `Saga-ID: uuid` передается во всех топиках Kafka, позволяя отслеживать распределенный граф исполнения саги в Jaeger.

## Подводные камни

Циклические зависимости событий: если сервис A слушает событие B, а сервис B слушает событие A, ошибка в логике может вызвать бесконечную петлю генерации событий, которая завалит брокер миллионами сообщений.

## На собеседовании

**Вопрос с собеседования:** «Когда количество шагов в бизнес-процессе превышает 5, почему рекомендуют переходить с Choreography на Orchestration?»
**Ответ:** При 5+ шагах граф хореографии превращается в запутанный «распределенный монолит спагетти»: невозможно понять, кто от кого зависит, и крайне сложно визуализировать текущее состояние зависшего заказа. Оркестратор держит весь граф переходов в одном месте.
