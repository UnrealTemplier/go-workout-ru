# Обратный прокси API Gateway на Go: префиксная маршрутизация и агрегация данных

## Условие

**API Gateway на Go**. Напишите обратный прокси, который маршрутизирует запросы к разным микросервисам по префиксам (`/users`, `/orders`). Добавьте агрегацию ответов: один endpoint собирает данные из двух сервисов и возвращает клиенту.

## Теория

Паттерн агрегации запросов (API Composition / Request Aggregator):
- Вместо того чтобы мобильное приложение делало два раздельных сетевых запроса (`GET /users/me` и `GET /orders/active`), оно вызывает один составной эндпоинт на шлюзе:
  `GET /dashboard`
- **Шлюз выполняет параллельный сбор (Scatter-Gather):**
  - Горутина 1 вызывает `UserService` по внутреннему gRPC/HTTP.
  - Горутина 2 вызывает `OrderService`.
  - Синхронизация через `sync.WaitGroup` или `golang.org/x/sync/errgroup`.
  - Сборка объединенного JSON-ответа клиенту.
- Время ответа клиенту равно максимуму из двух сервисов, а не их сумме: \(\max(T_1, T_2)\).

## Решение по шагам

1. Создайте эмуляторы UserService и OrderService.
2. Реализуйте функцию параллельной агрегации `AggregateDashboardData`.
3. Соберите итоговый JSON ответ.
4. Верифицируйте корректность агрегированных данных.

## Код решения

**`gateway_aggregator_go_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"testing"
)

type DashboardAggregatedResult struct {
	UserName string   `json:"user_name"`
	Orders   []string `json:"orders"`
}

type InternalUsersClient struct{}

func (c *InternalUsersClient) GetProfile(userID string) string {
	return "Ольга Смирнова"
}

type InternalOrdersClient struct{}

func (c *InternalOrdersClient) GetUserOrders(userID string) []string {
	return []string{"ORD-5501", "ORD-5502"}
}

func AggregateDashboard(userID string) DashboardAggregatedResult {
	usersClient := &InternalUsersClient{}
	ordersClient := &InternalOrdersClient{}

	var wg sync.WaitGroup
	var name string
	var orders []string

	wg.Add(2)

	// Параллельный опрос микросервиса пользователей
	go func() {
		defer wg.Done()
		name = usersClient.GetProfile(userID)
	}()

	// Параллельный опрос микросервиса заказов
	go func() {
		defer wg.Done()
		orders = ordersClient.GetUserOrders(userID)
	}()

	wg.Wait()

	return DashboardAggregatedResult{
		UserName: name,
		Orders:   orders,
	}
}

func TestGatewayAggregatorGo(t *testing.T) {
	result := AggregateDashboard("usr-88")

	if result.UserName != "Ольга Смирнова" || len(result.Orders) != 2 {
		t.Fatalf("Ошибка агрегации данных: %+v", result)
	}

	jsonBytes, _ := json.Marshal(result)

	fmt.Println("API Gateway агрегация ответов (API Composition) успешно подтверждена:")
	fmt.Printf("  • Агрегированный JSON ответ: %s\n", string(jsonBytes))
	fmt.Println("  • Параллельный сбор через горутины сократил задержку для мобильного клиента")
}
```

ℹ️ Параллельная композиция ответов от нескольких микросервисов в единый JSON

## Под капотом

В Go для параллельного сбора запросов с контролем таймаута используют пакет `errgroup.WithContext(ctx)`. Если один из сервисов возвращает критическую ошибку, контекст немедленно отменяется (`cancel()`), обрывая ненужные сетевые запросы к остальным сервисам.

## Подводные камни

Выполнять запросы к сервисам последовательно: суммарная задержка сложит задержки всех сервисов (\(T_1 + T_2 + T_3\)). Все независимые выборки обязаны выполняться параллельно в отдельных горутинах.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если при агрегации дашборда сервис рекомендаций упал, а профиль и заказы успешно получены?»
**Ответ:** Стратегия частичного ответа (Partial Failure / Graceful Degradation): шлюз отдает профиль и заказы, а поле `recommendations` возвращает как пустой массив `[]`, не ломая весь экран приложения ошибкой 500.
