# Атрибутивная модель доступа (Attribute-Based Access Control / ABAC): контекстные правила и предикаты

## Условие

**ABAC (Attribute-Based Access Control)**: Более гибкая модель: "пользователь может редактировать заказ, если он его владелец И заказ в статусе draft".

## Теория

Принципы Attribute-Based Access Control (ABAC):
- В отличие от жесткого RBAC, ABAC оценивает **динамические атрибуты** всех четырех сущностей:
  1. `Subject Attributes`: роль пользователя, его ID, отдел, должность.
  2. `Resource Attributes`: владелец заказа (`owner_id`), текущий статус (`status = draft`), сумма.
  3. `Action Attributes`: `EDIT`, `VIEW`, `DELETE`.
  4. `Environment Attributes`: текущее время суток, рабочий день недели, IP-адрес (VPN).
- **Бизнес-правило:**
  $$\text{Allow} \iff (\text{user.id} == \text{order.owner\_id}) \land (\text{order.status} == \text{"draft"})$$

## Решение по шагам

1. Создайте структуры субъекта и ресурса с атрибутами.
2. Реализуйте функцию проверки предикатов ABAC.
3. Продемонстрируйте разрешение редактирования черновика владельцем.
4. Продемонстрируйте отказ при смене статуса заказа на `paid`.

## Код решения

**`abac_policy_engine_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ABACUserSubject struct {
	ID string
}

type ABACOrderResource struct {
	ID      string
	OwnerID string
	Status  string // "draft", "submitted", "paid"
}

func CanEditOrder(user ABACUserSubject, order ABACOrderResource) bool {
	// Правило ABAC: пользователь является владельцем И заказ в статусе draft
	return user.ID == order.OwnerID && order.Status == "draft"
}

func TestABACPolicyEngine(t *testing.T) {
	alice := ABACUserSubject{ID: "usr-alice"}
	bob := ABACUserSubject{ID: "usr-bob"}

	draftOrder := ABACOrderResource{ID: "ord-1", OwnerID: "usr-alice", Status: "draft"}
	paidOrder := ABACOrderResource{ID: "ord-2", OwnerID: "usr-alice", Status: "paid"}

	// 1. Алиса может редактировать свой черновик
	if !CanEditOrder(alice, draftOrder) {
		t.Fatal("Алиса должна иметь право редактировать свой черновик")
	}

	// 2. Боб НЕ может редактировать чужой черновик
	if CanEditOrder(bob, draftOrder) {
		t.Fatal("Боб не должен иметь доступа к чужому заказу")
	}

	// 3. Алиса НЕ может редактировать уже оплаченный заказ
	if CanEditOrder(alice, paidOrder) {
		t.Fatal("Оплаченный заказ не может быть отредактирован")
	}

	fmt.Println("Атрибутивная модель доступа (ABAC) успешно подтверждена:")
	fmt.Printf("  • Алиса -> Свой черновик: Разрешено (%v)\n", CanEditOrder(alice, draftOrder))
	fmt.Printf("  • Боб   -> Черновик Алисы: Отклонено (%v)\n", CanEditOrder(bob, draftOrder))
	fmt.Printf("  • Алиса -> Оплаченный заказ: Отклонено (%v)\n", CanEditOrder(alice, paidOrder))
}
```

ℹ️ Динамическая оценка прав доступа на основе атрибутов субъекта и ресурса

## Под капотом

В Enterprise-архитектурах политики ABAC выносят в специализированный движок **Open Policy Agent (OPA)** на языке Rego. Go-микросервис передает контекст в библиотеку `open-policy-agent/opa/rego` и получает моментальное булево решение `allow: true/false` без хардкода правил в Go.

## Подводные камни

Выполнять ABAC проверки после тяжелых вычислений: проверку прав всегда производят в самом начале метода Use Case, чтобы не тратить ресурсы на неавторизованные операции.

## На собеседовании

**Вопрос с собеседования:** «Как фильтровать списки из 10 000 записей по правилам ABAC без выгрузки всех строк в память Go?»
**Ответ:** Правила ABAC транслируют в условия SQL-запроса (Query Rewriting / Policy Pushdown). Если правило гласит `user == owner && status == draft`, репозиторий добавляет `WHERE owner_id = $1 AND status = 'draft'` напрямую в SQL-запрос, делегируя фильтрацию СУБД.
