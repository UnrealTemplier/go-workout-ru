# Сага бронирования остатков склада: компенсация отмены резерва при недоступности доставки

## Условие

**Saga (Choreography) для распределённой транзакции**. Сервис заказов создаёт заказ, публикует событие. Сервис резервирования товара слушает событие, резервирует, публикует своё событие. Если резервирование не удалось, сервис заказов компенсирует, отменяя заказ.

## Теория

Двухшаговая цепочка хореографии складского учета:
- **Прямой сценарий (Happy Path):**
  1. `OrderPlaced` \(\implies\) `InventoryService` бронирует остаток на складе \(\implies\) `StockReserved`.
  2. `StockReserved` \(\implies\) `DeliveryService` назначает курьера.
- **Компенсирующий сценарий (Compensating Path):**
  1. Если на складе 0 штук товара \(\implies\) `InventoryService` публикует `StockReservationFailed`.
  2. `OrderService` получает событие и отменяет заказ: `OrderCancelled`.
  3. Клиент получает push-уведомление «Товар закончился».

## Решение по шагам

1. Создайте эмулятор склада с проверкой остатков.
2. Смоделируйте исчерпание остатков и генерацию `StockReservationFailed`.
3. Опишите реакцию `OrderService` на отказ склада.
4. Продемонстрируйте автоматическую отмену заказа.

## Код решения

**`saga_inventory_reservation_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type InventoryWarehouse struct {
	stockCount map[string]int
}

func (w *InventoryWarehouse) TryReserve(sku string, qty int) bool {
	available := w.stockCount[sku]
	if available >= qty {
		w.stockCount[sku] -= qty
		return true
	}
	return false
}

func TestSagaInventoryReservation(t *testing.T) {
	warehouse := &InventoryWarehouse{stockCount: map[string]int{"sku-macbook": 0}} // остаток 0!

	sku := "sku-macbook"
	qty := 1

	reserved := warehouse.TryReserve(sku, qty)
	orderStatus := "PENDING"

	if !reserved {
		// Реакция на StockReservationFailed
		orderStatus = "CANCELLED_OUT_OF_STOCK"
	}

	if orderStatus != "CANCELLED_OUT_OF_STOCK" {
		t.Fatalf("Заказ должен быть отменен: %s", orderStatus)
	}

	fmt.Println("Сага бронирования складских остатков успешно подтверждена:")
	fmt.Printf("  • Попытка брони %s (кол-во: %d) -> Доступно: %d шт\n", sku, qty, warehouse.stockCount[sku])
	fmt.Printf("  • Заказ переведен в статус: %s\n", orderStatus)
	fmt.Println("  • Компенсация выполнена без блокировки таблиц базы данных")
}
```

## Под капотом

В распределенных складах остаток делят на две величины: `Физический остаток` (Physical Stock) и `Доступный остаток` (Available Stock). Бронирование уменьшает доступный остаток, а физическое списание происходит только в момент отгрузки коробки со склада.

## Подводные камни

Использовать положительный баланс склада без ограничения `CHECK (stock >= 0)` в PostgreSQL: гонка двух параллельных заказов может загнать остаток в минус (`-1`), приведя к овербукингу.

## На собеседовании

**Вопрос с собеседования:** «Что такое семантическая компенсация в e-commerce?»
**Ответ:** Если товар закончился, а деньги уже списаны, вместо сухого возврата денег клиенту начисляют промокод на 500 рублей или предлагают аналогичный товар со скидкой, сохраняя лояльность покупателя.
