# Развертывание Blue-Green (Сине-Зеленый деплой): нулевой даунтайм и мгновенный откат трафика

## Условие

Реализуй **Blue-Green Deployment**: two identical environments. Blue = current, Green = new. Test green, switch traffic (DNS/load balancer), blue stays for instant rollback. Zero downtime, but double resources.

## Теория

Стратегия развертывания Blue-Green:
- В кластере одновременно существуют две **полноценные идентичные копии среды**:
  - `Environment Blue`: текущая стабильная версия `v1.0` (несет 100% пользовательского трафика).
  - `Environment Green`: новая версия `v1.1` (трафик пользователей отсутствует).
- **Порядок релиза:**
  1. Команда развертывает новую версию в окружение `Green`.
  2. QA-инженеры проводят Smoke-тесты напрямую через тестовый домен `test-green.corp.ru`.
  3. Балансировщик NGINX/ALB переключает 100% трафика с `Blue` на `Green` за 0.1 секунды.
  4. **Мгновенный откат (Instant Rollback):** если через 10 минут обнаружен критический баг, балансировщик моментально переключается обратно на `Blue`!

## Решение по шагам

1. Создайте эмулятор балансировщика трафика с активной целью (Blue/Green).
2. Разверните версию Green и проведите верификацию.
3. Переключите активное окружение.
4. Продемонстрируйте мгновенный откат при обнаружении дефекта.

## Код решения

**`blue_green_deployment_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type EnvironmentColor string

const (
	EnvBlue  EnvironmentColor = "BLUE (v1.0)"
	EnvGreen EnvironmentColor = "GREEN (v1.1)"
)

type BlueGreenLoadBalancer struct {
	activeTarget EnvironmentColor
}

func (lb *BlueGreenLoadBalancer) Route() EnvironmentColor {
	return lb.activeTarget
}

func (lb *BlueGreenLoadBalancer) SwitchTraffic(target EnvironmentColor) {
	lb.activeTarget = target
}

func TestBlueGreenDeployment(t *testing.T) {
	lb := &BlueGreenLoadBalancer{activeTarget: EnvBlue}

	// 1. Исходное состояние: весь трафик на Blue
	if lb.Route() != EnvBlue {
		t.Fatal("Трафик обязан идти на Blue")
	}

	// 2. Новая версия развернута в Green и протестирована QA -> Переключение!
	lb.SwitchTraffic(EnvGreen)
	if lb.Route() != EnvGreen {
		t.Fatal("Трафик обязан переключиться на Green")
	}

	// 3. Обнаружен критический баг в Green -> Мгновенный откат на Blue!
	lb.SwitchTraffic(EnvBlue)
	if lb.Route() != EnvBlue {
		t.Fatal("Откат обязан вернуть трафик на Blue")
	}

	fmt.Println("Стратегия Blue-Green Deployment успешно подтверждена:")
	fmt.Printf("  • Активное окружение после отката: %s\n", lb.Route())
	fmt.Println("  • Переключение трафика выполнено за миллисекунды без единой секунды простоя (Zero Downtime)")
}
```

ℹ️ Мгновенное переключение трафика между синим и зеленым окружениями

## Под капотом

В Kubernetes Blue-Green реализуется через смену селектора в `Service`: `kubectl patch service app-service -p '{"spec":{"selector":{"version":"green"}}}'`. Kube-Proxy и балансировщик обновляют эндпоинты за 100 миллисекунд без перезапуска подов.

## Подводные камни

Миграции базы данных с удалением колонок: если Green применит `ALTER TABLE DROP COLUMN`, старая версия Blue мгновенно упадет с ошибкой, сделав быстрый откат невозможным. Применяют правило обратной совместимости схемы БД (Expand and Contract).

## На собеседовании

**Вопрос с собеседования:** «В чем главный недостаток Blue-Green развертывания по сравнению с Rolling Update?»
**Ответ:** Стоимость ресурсов. Blue-Green требует **удвоения инфраструктуры (Double Resources)** во время деплоя: в кластере должны одновременно помещаться 100% подов Blue и 100% подов Green, что дорого для крупных систем из 10 000 нод.
