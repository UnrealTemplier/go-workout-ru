# Изоляция тенантов в облачной инфраструктуре (Tenant Isolation): compute, storage и network

## Условие

**Изоляция тенантов**: Реализуйте изоляцию на трех уровнях: compute (отдельные поды/неймспейсы для VIP-тенантов), storage (отдельные БД/схемы), network (NetworkPolicy).

### Исходная формулировка

**Паттерн Outbox (Транзакционный Outbox)**: При отправке сообщений в Kafka сразу после записи в БД может возникнуть сбой: запись сохранилась, а сообщение не ушло (или наоборот). Решите проблему:
* В рамках одной SQL-транзакции сохраните пользователя в таблицу `users` и событие `"UserCreated"` в служебную таблицу `outbox` в PostgreSQL.
* Напишите фонового демона (CDC-воркер), который раз в секунду опрашивает таблицу `outbox`, публикует новые события в Kafka и удаляет (или помечает как отправленные) обработанные строки.

## Теория

Трехуровневая модель изоляции тенантов в Enterprise Kubernetes:
1. **Compute Isolation (Вычисления):**
   - Стандартные тенанты делят общий пул воркеров.
   - VIP-тенанты развертываются в выделенных K8s Namespaces с привязкой к отдельным физическим нодам (`nodeSelector`, `taints/tolerations`).
2. **Storage Isolation (Данные):**
   - Выделенная база данных PostgreSQL на отдельном дисковом PV (Persistent Volume).
3. **Network Isolation (Сеть):**
   - K8s `NetworkPolicy` блокирует любой входящий и исходящий трафик между подами разных тенантов на уровне сетевого стека CNI (Calico/Cilium).

## Решение по шагам

1. Создайте модель уровня изоляции тенанта (Standard vs VIP).
2. Реализуйте селектор инфраструктурных ресурсов.
3. Продемонстрируйте изоляцию вычислительных нод и базы данных.
4. Верифицируйте соответствие корпоративным политикам.

## Код решения

**`tenant_infra_isolation_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TenantTier string

const (
	TierStandard TenantTier = "STANDARD_SHARED"
	TierVIP      TenantTier = "VIP_DEDICATED"
)

type TenantInfraProfile struct {
	TenantID      string
	Tier          TenantTier
	K8sNamespace  string
	DedicatedNode string
	DatabaseDSN   string
}

func ResolveInfraProfile(tenantID string, isVIP bool) TenantInfraProfile {
	if isVIP {
		return TenantInfraProfile{
			TenantID:      tenantID,
			Tier:          TierVIP,
			K8sNamespace:  fmt.Sprintf("tenant-vip-%s", tenantID),
			DedicatedNode: "dedicated-pool-c6i-4xlarge",
			DatabaseDSN:   fmt.Sprintf("postgres://db-vip-%s.corp:5432", tenantID),
		}
	}
	return TenantInfraProfile{
		TenantID:      tenantID,
		Tier:          TierStandard,
		K8sNamespace:  "shared-tenants-prod",
		DedicatedNode: "shared-worker-pool",
		DatabaseDSN:   "postgres://db-shared-cluster.corp:5432",
	}
}

func TestTenantInfraIsolation(t *testing.T) {
	vipProfile := ResolveInfraProfile("gazprom", true)
	stdProfile := ResolveInfraProfile("small-shop", false)

	if vipProfile.DedicatedNode == stdProfile.DedicatedNode {
		t.Fatal("VIP тенант не должен делить вычислительные ноды со стандартным")
	}

	fmt.Println("Изоляция тенантов (Compute, Storage, Network) подтверждена:")
	fmt.Printf("  • VIP Тенант %s: Нода=%s | База=%s\n",
		vipProfile.TenantID, vipProfile.DedicatedNode, vipProfile.DatabaseDSN)
	fmt.Printf("  • Standard Тенант %s: Нода=%s | База=%s\n",
		stdProfile.TenantID, stdProfile.DedicatedNode, stdProfile.DatabaseDSN)
}
```

## Под капотом

В Kubernetes NetworkPolicy транслируется в правила Linux eBPF или `iptables` ядра ноды, отбрасывая сетевые пакеты на уровне L3/L4 до того, как они достигнут сокета контейнера Go.

## Подводные камни

Использовать общие секреты (K8s Secrets) для всех неймспейсов: тенант со взломанным подом сможет прочитать сертификаты соседнего тенанта. Секреты строго изолируются по неймспейсам.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить проблему шумного соседа (Noisy Neighbor) среди стандартных тенантов?»
**Ответ:** Настройка жестких K8s `ResourceQuota` и `LimitRange` для контейнеров (CPU/RAM limits), использование cgroups v2 с Memory QoS, а также Rate Limiting на уровне шлюза API по ключу `tenant_id`.
