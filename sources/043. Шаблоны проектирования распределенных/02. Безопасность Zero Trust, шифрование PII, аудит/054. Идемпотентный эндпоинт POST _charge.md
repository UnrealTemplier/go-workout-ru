# Идемпотентный эндпоинт POST /charge: защита мобильных клиентов от двойных списаний

## Условие

**Idempotency Key (Идемпотентный API)**: Спроектируй HTTP-эндпоинт `POST /charge`. Клиент (мобилка) может случайно отправить запрос дважды из-за лагов сети. Требуй заголовок `Idempotency-Key`. Кэшируй результат первого успешного выполнения по этому ключу. При дубле — просто отдавай закешированный HTTP-ответ 200 OK (без повторного списания!).

## Теория

Сценарий дублирования запросов мобильных приложений:
- Пользователь в метро нажимает «Оплатить 5 000 руб».
- Поезд въезжает в тоннель, 4G сигнал пропадает.
- Мобильное приложение показывает спиннер и через 5 секунд автоматически делает сетевой повтор (Retry).
- **Результат без Idempotency-Key:** два списания по 5 000 руб (скандал и чарджбэк).
- **С Idempotency-Key:** второй запрос находит запись в кэше и возвращает `HTTP 200 OK` с тем же чеком, не обращаясь к банковскому шлюзу повторно!

## Решение по шагам

1. Создайте эмулятор платежного процессора.
2. Реализуйте проверку обязательного заголовка `Idempotency-Key`.
3. Смоделируйте два одинаковых POST запроса подряд.
4. Верифицируйте ровно один факт реального списания.

## Код решения

**`idempotent_charge_endpoint_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"testing"
)

type ChargeService struct {
	mu           sync.Mutex
	cachedTx     map[string]string
	realCharges  int
}

func (s *ChargeService) HandleCharge(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "Idempotency-Key header is required", http.StatusBadRequest)
		return
	}

	s.mu.Lock()
	defer s.mu.Unlock()

	// Если запрос повторный — отдаем готовый результат
	if receipt, found := s.cachedTx[key]; found {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusOK)
		w.Write([]byte(receipt))
		return
	}

	// Реальное списание денег
	s.realCharges++
	receipt := fmt.Sprintf(`{"status":"SUCCESS","charge_id":"ch_%d","amount":5000}`, s.realCharges)
	s.cachedTx[key] = receipt

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	w.Write([]byte(receipt))
}

func TestIdempotentChargeEndpoint(t *testing.T) {
	service := &ChargeService{cachedTx: make(map[string]string)}
	idemKey := "uuid-mobile-charge-777"

	// 1. Первый запрос (Реальное списание)
	req1 := httptest.NewRequest(http.MethodPost, "/charge", nil)
	req1.Header.Set("Idempotency-Key", idemKey)
	rec1 := httptest.NewRecorder()
	service.HandleCharge(rec1, req1)

	if rec1.Code != http.StatusOK || service.realCharges != 1 {
		t.Fatalf("Сбой первого списания: %d", rec1.Code)
	}

	// 2. Сетевой ретрай из тоннеля метро с тем же ключом
	req2 := httptest.NewRequest(http.MethodPost, "/charge", nil)
	req2.Header.Set("Idempotency-Key", idemKey)
	rec2 := httptest.NewRecorder()
	service.HandleCharge(rec2, req2)

	if rec2.Code != http.StatusOK || service.realCharges != 1 {
		t.Fatalf("Второй запрос вызвал повторное списание! charges=%d", service.realCharges)
	}

	if rec1.Body.String() != rec2.Body.String() {
		t.Fatal("Ответы обязаны совпадать")
	}

	fmt.Println("Идемпотентный эндпоинт POST /charge успешно подтвержден:")
	fmt.Printf("  • Ответ на запрос 1: %s\n", rec1.Body.String())
	fmt.Printf("  • Ответ на запрос 2: %s (Мгновенно из кэша идемпотентности)\n", rec2.Body.String())
	fmt.Printf("  • Количество реальных списаний средств: %d\n", service.realCharges)
}
```

## Под капотом

В мобильных SDK (iOS/Android) ключ идемпотентности генерируется в момент нажатия пользователем кнопки в UI: `UUIDv4()`. Этот ключ сохраняется в локальной SQLite базе телефона до тех пор, пока сервер не ответит HTTP 200 OK, гарантируя сохранность ключа даже при принудительном закрытии приложения.

## Подводные камни

Генерировать Idempotency-Key на сервере при открытии формы: если пользователь откроет две вкладки браузера, они разделят один ключ и перезапишут данные друг друга. Ключ генерируется строго на клиенте для конкретного факта отправки формы.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если первый запрос упал с паникой рантайма или фатальной ошибкой OOM?»
**Ответ:** Запись блокировки ключа в Redis всегда выставляется с коротким TTL (например 30 секунд). Если сервер аварийно умер и не обновил статус до `COMPLETED`, ключ автоматически разблокируется, позволяя клиенту повторить попытку на другом живом поде.
