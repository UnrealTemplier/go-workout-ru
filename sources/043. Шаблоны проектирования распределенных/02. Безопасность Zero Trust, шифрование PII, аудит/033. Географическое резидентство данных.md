# Географическое резидентство данных (Data Residency): изоляция EU и US тенантов через Geo-Routing

## Условие

**Data Residency**: Храните данные EU-тенантов в EU-регионе, US-тенантов — в US. Реализуйте через geo-routing и separate deployments.

## Теория

Соблюдение законов о суверенитете данных (GDPR, 152-ФЗ, CCPA):
- Международные законы запрещают передавать персональные данные граждан Евросоюза (EU) на серверы в США (US) и наоборот.
- **Архитектура Data Residency:**
  1. **Anycast DNS / Cloudflare Geo-Routing:** определяет регион пользователя по IP-адресу.
  2. Раздельные деплои (Separate Deployments): кластер K8s `eu-central-1` (Франкфурт) и кластер `us-east-1` (Вирджиния).
  3. Базы данных физически изолированы в своих регионах.
  4. Запрещены межрегиональные репликации персональных данных (PII).

## Решение по шагам

1. Создайте профили регионов размещения данных.
2. Реализуйте роутер резидентства `DataResidencyRouter`.
3. Смоделируйте маршрутизацию клиента из Германии и клиента из США.
4. Верифицируйте соответствие закону о хранении данных.

## Код решения

**`data_residency_georouting_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RegionDeployment struct {
	RegionName string
	DBCluster  string
}

type GeoDataRouter struct {
	deployments map[string]RegionDeployment
}

func (r *GeoDataRouter) RouteTenant(jurisdiction string) (RegionDeployment, error) {
	d, ok := r.deployments[jurisdiction]
	if !ok {
		return RegionDeployment{}, fmt.Errorf("unsupported jurisdiction: %s", jurisdiction)
	}
	return d, nil
}

func TestDataResidencyGeorouting(t *testing.T) {
	router := &GeoDataRouter{
		deployments: map[string]RegionDeployment{
			"EU": {RegionName: "eu-central-1 (Frankfurt)", DBCluster: "pg-eu.corp.internal"},
			"US": {RegionName: "us-east-1 (N. Virginia)", DBCluster: "pg-us.corp.internal"},
			"RU": {RegionName: "ru-central1 (Moscow)", DBCluster: "pg-ru.corp.internal"},
		},
	}

	germanClient, _ := router.RouteTenant("EU")
	americanClient, _ := router.RouteTenant("US")

	if germanClient.DBCluster == americanClient.DBCluster {
		t.Fatal("Нарушение суверенитета данных: кластеры обязаны быть физически разделены!")
	}

	fmt.Println("Географическое резидентство данных (Data Residency) подтверждено:")
	fmt.Printf("  • Тенант из ЕС (GDPR): %s -> Кластер: %s\n", germanClient.RegionName, germanClient.DBCluster)
	fmt.Printf("  • Тенант из США:       %s -> Кластер: %s\n", americanClient.RegionName, americanClient.DBCluster)
	fmt.Println("  • Хранение персональных данных строго изолировано в рамках юрисдикций")
}
```

## Под капотом

В глобальных распределенных системах аутентификация пользователя (Auth SSO) может быть глобальной, но токен JWT содержит claim `residency: "eu"`. Все внутренние микросервисы проверяют этот claim и направляют запросы к локальному региональному хранилищу.

## Подводные камни

Собирать централизованные логи со всех регионов в один ELK кластер в США: логи, содержащие email и IP пользователей из ЕС, также подпадают под действие GDPR и должны храниться в европейском регионе.

## На собеседовании

**Вопрос с собеседования:** «Как поддерживать глобальную аналитику (Global Dashboard) при строгом Data Residency?»
**Ответ:** Локальные кластеры в регионах выполняют **анонимизацию и агрегацию данных на месте**. В глобальный ClickHouse передаются только обезличенные суммы и счетчики (`{"date": "2026-09-04", "total_sales_eur": 50000}`), не содержащие персональных данных пользователей.
