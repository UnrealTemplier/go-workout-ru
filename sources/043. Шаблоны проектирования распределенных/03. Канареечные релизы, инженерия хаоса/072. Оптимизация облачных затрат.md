# Оптимизация облачных затрат (FinOps & Cost Optimization): Right-Sizing, Spot-инстансы и KEDA scale-to-zero

## Условие

Реализуй **Cost Optimization**: right-sizing (monitor CPU/memory usage, adjust requests/limits), spot instances for batch jobs, reserved instances for baseline, auto-scaling to zero (KEDA for dev environments). FinOps: team accountability for cloud spend.

---

## Теория

Методология FinOps (Финансовая оптимизация облака):
1. **Right-Sizing (Подгонка ресурсов):**
   - Устранение завышенных лимитов: сервис запрашивает 8 CPU и 16 ГБ RAM, а реально использует 0.5 CPU.
   - Использование K8s Vertical Pod Autoscaler (VPA) для точной подгонки `requests/limits`.
2. **Spot / Preemptible Instances (Экономия до 80%):**
   - Временные серверы со скидкой 70–80% для фоновых задач перекодирования видео и пакетных расчетов (Batch Jobs).
3. **Scale-to-Zero с KEDA:**
   - Тестовые среды Dev/Staging и консьюмеры очередей масштабируются в **0 реплик**, когда в очереди Kafka нет сообщений. Ноль затрат ночью!

## Решение по шагам

1. Создайте модель расчета облачных затрат сервиса.
2. Смоделируйте экономию от перехода на Spot-инстансы.
3. Реализуйте масштабирование в 0 реплик при пустой очереди задач.
4. Верифицируйте снижение стоимости инфраструктуры.

## Код решения

**`cost_optimization_finops_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CloudResourceCostCalculator struct {
	OnDemandHourlyRate float64
	SpotHourlyRate     float64
}

func (c *CloudResourceCostCalculator) CalculateBatchJobCost(hours float64, useSpot bool) float64 {
	if useSpot {
		return hours * c.SpotHourlyRate
	}
	return hours * c.OnDemandHourlyRate
}

func GetActiveReplicasKEDA(queueDepth int) int {
	if queueDepth == 0 {
		return 0 // Scale-to-Zero!
	}
	return 3
}

func TestCostOptimizationFinOps(t *testing.T) {
	calc := CloudResourceCostCalculator{
		OnDemandHourlyRate: 1.00,
		SpotHourlyRate:     0.25,
	}

	onDemandCost := calc.CalculateBatchJobCost(100, false)
	spotCost := calc.CalculateBatchJobCost(100, true)

	savingsPercent := (1.0 - (spotCost / onDemandCost)) * 100.0

	if savingsPercent < 70.0 {
		t.Fatalf("Экономия на Spot должна быть >= 70%%: %.1f%%", savingsPercent)
	}

	replicasIdle := GetActiveReplicasKEDA(0)
	replicasBusy := GetActiveReplicasKEDA(50)

	if replicasIdle != 0 || replicasBusy != 3 {
		t.Fatal("Сбой KEDA Scale-to-Zero логики")
	}

	fmt.Println("Оптимизация облачных затрат (FinOps Strategy) успешно подтверждена:")
	fmt.Printf("  • Стоимость On-Demand: $%.2f | Стоимость Spot: $%.2f (Экономия: %.1f%%)\n",
		onDemandCost, spotCost, savingsPercent)
	fmt.Printf("  • KEDA Scale-to-Zero: Очередь 0 -> %d подов (Очередь 50 -> %d подов)\n",
		replicasIdle, replicasBusy)
}
```

## Под капотом

Spot-инстансы получают уведомление о досрочном завершении (Termination Notice) за 2 минуты до остановки через метаданные хоста `http://169.254.169.254/latest/meta-data/spot/instance-action`. Go-приложение перехватывает сигнал и выполняет Graceful Shutdown.

## Подводные камни

Развертывать мастер-базу данных PostgreSQL на Spot-инстансах: регулярные внезапные отключения хостов приведут к постоянным аварийным переключениям. Spot используют строго для stateless воркеров.
