# Предотвращение лавины запросов к БД (Cache Stampede): подавление дубликатов через singleflight

## Условие

**Cache Stampede & Singleflight**: При резком сбросе кэша популярного товара (например, во время распродажи) тысячи параллельных запросов могут одновременно ринуться в базу данных, обрушив её. Решите эту проблему с помощью пакета `golang.org/x/sync/singleflight` [450]. Напишите логику: при промахе кэша используйте метод `sf.Do()`, чтобы в базу данных ушел ровно один запрос, а все остальные параллельные горутины заблокировались, дождались его ответа и получили готовый результат [450].

## Теория

Проблема Cache Stampede (Собачья свора / Thundering Herd):
- Во время распродажи ключ популярного товара `item:iphone16` в Redis истекает по TTL.
- В ту же миллисекунду приходят 10 000 параллельных запросов.
- Все 10 000 горутин видят Cache Miss и одновременно шлют тяжелый SQL-запрос в PostgreSQL!
- Процессор СУБД подскакивает до 100%, база падает.
- **Решение через `singleflight.Group`:**
  - Метод `sf.Do(key, fn)` гарантирует, что для одинакового ключа функция `fn` (поход в БД) **выполняется ровно в одном экземпляре**.
  - Остальные 9 999 горутин блокируются на канале и получают готовый результат первого вызова.
  - База данных получает **ровно 1 запрос** вместо 10 000!

## Решение по шагам

1. Создайте эмулятор структуры `singleflight.Group`.
2. Запустите 10 конкурентных горутин, запрашивающих один и тот же ключ товара.
3. Продемонстрируйте, что счетчик обращений к базе данных равен ровно 1.
4. Верифицируйте корректность раздачи результата всем горутинам.

## Код решения

**`singleflight_cache_stampede_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type SingleflightCall struct {
	wg  sync.WaitGroup
	val interface{}
	err error
}

type LocalSingleflightGroup struct {
	mu sync.Mutex
	m  map[string]*SingleflightCall
}

func (g *LocalSingleflightGroup) Do(key string, fn func() (interface{}, error)) (interface{}, error) {
	g.mu.Lock()
	if g.m == nil {
		g.m = make(map[string]*SingleflightCall)
	}
	if c, ok := g.m[key]; ok {
		g.mu.Unlock()
		c.wg.Wait() // Ждем выполнения первого запроса
		return c.val, c.err
	}

	c := new(SingleflightCall)
	c.wg.Add(1)
	g.m[key] = c
	g.mu.Unlock()

	c.val, c.err = fn()
	c.wg.Done()

	g.mu.Lock()
	delete(g.m, key)
	g.mu.Unlock()

	return c.val, c.err
}

func TestSingleflightCacheStampede(t *testing.T) {
	var sf LocalSingleflightGroup
	var dbQueriesCount int64

	// Тяжелый запрос к БД при промахе кэша
	fetchFromDB := func() (interface{}, error) {
		atomic.AddInt64(&dbQueriesCount, 1)
		time.Sleep(20 * time.Millisecond) // Имитация времени SQL запроса
		return "Product: iPhone 16 Pro (Price: 120 000)", nil
	}

	const concurrentClients = 10
	var wg sync.WaitGroup
	wg.Add(concurrentClients)

	// 10 параллельных клиентов одновременно запрашивают один ключ
	for i := 0; i < concurrentClients; i++ {
		go func() {
			defer wg.Done()
			val, err := sf.Do("product:iphone16", fetchFromDB)
			if err != nil || val != "Product: iPhone 16 Pro (Price: 120 000)" {
				t.Errorf("Некорректный ответ: %v", val)
			}
		}()
	}

	wg.Wait()

	if dbQueriesCount != 1 {
		t.Fatalf("Singleflight сбой: в базу ушло %d запросов вместо 1!", dbQueriesCount)
	}

	fmt.Println("Подавление Cache Stampede через Singleflight успешно подтверждено:")
	fmt.Printf("  • Клиентов обратилось одновременно: %d\n", concurrentClients)
	fmt.Printf("  • Реальных запросов отправлено в БД: %d (100%% защита от перегрузки)\n", dbQueriesCount)
	fmt.Println("  • Все 10 горутин получили идентичный результат первого запроса")
}
```

## Под капотом

В пакете `golang.org/x/sync/singleflight` вызов `sf.DoChan()` возвращает канал `<-chan Result`, что позволяет комбинировать Singleflight с контекстным таймаутом `select { case res := <-ch: ... case <-ctx.Done(): ... }`.

## Подводные камни

Мутировать возвращенный указатель структуры: если `fn()` возвращает указатель `*User`, все 10 горутин получают один и тот же указатель на одну область памяти. Модификация полей без копирования вызовет Data Race.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Singleflight от Distributed Lock (Redis Redlock)?»
**Ответ:** 
- **Singleflight:** работает строго **внутри одного процесса Go** (пода), защищая БД от локального всплеска горутин с нулевой задержкой.
- **Distributed Lock:** синхронизирует действия **между сотнями подов** через сеть, но требует сетевых round-trips к Redis и накладных расходов на TTL лизинга.
