# План аварийного восстановления (Disaster Recovery Plan): RPO=5m, RTO=15m и автоматический Failover баз данных

## Условие

Реализуй **Disaster Recovery**: RPO (Recovery Point Objective) = 5 min, RTO (Recovery Time Objective) = 15 min. Multi-AZ: synchronous replication (RPO=0). Multi-region: asynchronous replication (RPO=5min). Automated failover: Patroni/HAProxy for PostgreSQL. Regular DR drills.

## Теория

Гибридная архитектура непрерывности бизнеса (Business Continuity):
1. **Уровень Multi-AZ (Внутри региона):**
   - Синхронная репликация между 3 дата-центрами.
   - \(\text{RPO} = 0\), \(\text{RTO} < 10\text{ сек}\).
   - Защищает от локальных аварий (отключение электроподстанции, пожар в серверной).
2. **Уровень Multi-Region (Межрегиональный):**
   - Асинхронная потоковая репликация PostgreSQL WAL между Москвой и Екатеринбургом.
   - \(\text{RPO} \le 5\text{ минут}\), \(\text{RTO} \le 15\text{ минут}\).
   - Защищает от глобальных катастроф (разрыв магистральных кабелей, природные катаклизмы).

## Решение по шагам

1. Создайте конфигурацию целевых показателей надежности RPO и RTO.
2. Реализуйте проверку соответствия фактического лага репликации лимиту RPO.
3. Смоделируйте сценарий межрегионального переключения.
4. Верифицируйте соблюдение регламентов непрерывности бизнеса.

## Код решения

**`dr_multiregion_plan_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DRPolicyTarget struct {
	TargetRPO time.Duration
	TargetRTO time.Duration
}

type MultiRegionDRCluster struct {
	policy            DRPolicyTarget
	asyncLag          time.Duration
	failoverDuration  time.Duration
}

func (c *MultiRegionDRCluster) VerifyDrillReadiness() (bool, string) {
	if c.asyncLag > c.policy.TargetRPO {
		return false, fmt.Sprintf("FAILED: Replication lag %v exceeds target RPO %v",
			c.asyncLag, c.policy.TargetRPO)
	}
	if c.failoverDuration > c.policy.TargetRTO {
		return false, fmt.Sprintf("FAILED: Failover time %v exceeds target RTO %v",
			c.failoverDuration, c.policy.TargetRTO)
	}
	return true, "READY_FOR_DR_FAILOVER"
}

func TestDRMultiregionPlan(t *testing.T) {
	cluster := &MultiRegionDRCluster{
		policy: DRPolicyTarget{
			TargetRPO: 5 * time.Minute,
			TargetRTO: 15 * time.Minute,
		},
		asyncLag:         45 * time.Second,  // лаг 45 сек (< 5 мин)
		failoverDuration: 6 * time.Minute,   // время переключения 6 мин (< 15 мин)
	}

	ready, status := cluster.VerifyDrillReadiness()
	if !ready {
		t.Fatalf("Кластер не готов к аварийному восстановлению: %s", status)
	}

	fmt.Println("План аварийного восстановления (Disaster Recovery Drill) подтвержден:")
	fmt.Printf("  • Статус готовности: %s\n", status)
	fmt.Printf("  • Фактический RPO: %v (Норматив: <= 5 мин)\n", cluster.asyncLag)
	fmt.Printf("  • Фактический RTO: %v (Норматив: <= 15 мин)\n", cluster.failoverDuration)
	fmt.Println("  • Регулярные учения DR подтверждают готовность к переключению на резервный регион")
}
```

ℹ️ Контроль соответствия метрик межрегиональной репликации нормативам RPO и RTO

## Под капотом

В PostgreSQL для передачи WAL в удаленный регион используют `archive_command` с выгрузкой в S3 через утилиту `pgBackRest` или потоковую асинхронную репликацию с компрессией lz4/zstd, снижающей межрегиональный трафик в 4–5 раз.

## Подводные камни

Никогда не проводить тестовые учения (DR Drills): в 80% компаний при реальной аварии оказывается, что бэкапы повреждены, скрипты автоматического переключения DNS содержат ошибки синтаксиса, а сертификаты просрочены. Учения проводят минимум раз в квартал.

## На собеседовании

**Вопрос с собеседования:** «Что такое Split-Brain при межрегиональном фейловере и как его предотвратить?»
**Ответ:** Разрыв связи между Москвой и Екатеринбургом может заставить оба региона объявить себя мастерами. Для исключения Split-Brain третий узел-арбитр (Witness / Quorum node) размещают в независимой третьей локации (например в Санкт-Петербурге). Регион может промоутиться только с согласия арбитра.
