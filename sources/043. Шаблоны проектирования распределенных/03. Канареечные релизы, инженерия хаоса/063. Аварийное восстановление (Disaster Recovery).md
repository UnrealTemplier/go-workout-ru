# Аварийное восстановление (Disaster Recovery): метрики RPO и RTO, межрегиональная репликация

## Условие

**Disaster Recovery**: Спроектируйте DR-стратегию для Tier-1 сервиса: RPO = 0 (no data loss) для транзакций, RTO < 1 min (automated failover). Multi-region active-passive с межрегиональной репликацией.

### Исходная формулировка

Реализуй **Infrastructure as Code (Terraform/Pulumi)**: PostgreSQL cluster, Redis cluster, Kubernetes cluster, load balancer, DNS, TLS certificates. Version controlled, code-reviewed, tested (terratest). Drift detection: `terraform plan` shows differences.

## Теория

Метрики устойчивости к катастрофам (Disaster Recovery Metrics):
1. **RPO (Recovery Point Objective — Точка восстановления):**
   - Допустимый объем потерянных данных при аварии дата-центра, измеряемый во времени.
   - \(\text{RPO} = 0\): ни одна завершенная финансовая транзакция не должна быть потеряна. Достигается полусинхронной репликацией.
2. **RTO (Recovery Time Objective — Время восстановления):**
   - Допустимое время простоя сервиса до полного возврата в строй.
   - \(\text{RTO} < 1\text{ мин}\): достигается автоматическим DNS-переключением и готовым резервным кластером (Warm Standby / Pilot Light).

## Решение по шагам

1. Создайте модель оценки метрик RPO и RTO.
2. Смоделируйте аварийное переключение на резервный регион при потере основного.
3. Рассчитайте фактическое время восстановления системы.
4. Верифицируйте соответствие корпоративному SLA Tier-1.

## Код решения

**`disaster_recovery_metrics_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DRRegionState struct {
	RegionName    string
	IsActive      bool
	LastSyncLSN   int
	ReplicationLag time.Duration
}

type DisasterRecoveryOrchestrator struct {
	primaryRegion *DRRegionState
	drRegion      *DRRegionState
}

func (o *DisasterRecoveryOrchestrator) ExecuteDisasterFailover() (time.Duration, error) {
	start := time.Now()

	// 1. Фиксация RPO (потерянные данные)
	rpoDataLoss := o.drRegion.ReplicationLag
	if rpoDataLoss > 0 {
		return 0, fmt.Errorf("RPO violation: data lag is %v (Tier-1 requires RPO=0)", rpoDataLoss)
	}

	// 2. Промоушен DR региона в активный
	o.primaryRegion.IsActive = false
	o.drRegion.IsActive = true

	rtoRecoveryTime := time.Since(start)
	return rtoRecoveryTime, nil
}

func TestDisasterRecoveryMetrics(t *testing.T) {
	primary := &DRRegionState{RegionName: "DC-Moscow", IsActive: true, LastSyncLSN: 50000, ReplicationLag: 0}
	standby := &DRRegionState{RegionName: "DC-Saint-Petersburg", IsActive: false, LastSyncLSN: 50000, ReplicationLag: 0}

	orchestrator := &DisasterRecoveryOrchestrator{primaryRegion: primary, drRegion: standby}

	rto, err := orchestrator.ExecuteDisasterFailover()
	if err != nil {
		t.Fatalf("Сбой аварийного переключения: %v", err)
	}

	if !standby.IsActive || primary.IsActive {
		t.Fatal("DR регион обязан стать активным")
	}

	fmt.Println("Аварийное восстановление (Disaster Recovery Strategy) подтверждено:")
	fmt.Printf("  • Первичный ДЦ: %s (Отключен)\n", primary.RegionName)
	fmt.Printf("  • Резервный ДЦ: %s (Успешно активирован)\n", standby.RegionName)
	fmt.Printf("  • Фактический RTO: %v (Норматив < 1 мин)\n", rto)
	fmt.Println("  • RPO = 0: Потери финансовых транзакций отсутствуют")
}
```

ℹ️ Расчет и верификация метрик непрерывности бизнеса RPO=0 и RTO<1min при аварии ЦОД

## Под капотом

Для автоматического переключения клиентов между регионами используют **Anycast BGP маршрутизацию**: при отказе региона BGP-анонс маршрута снимается, и интернет-провайдеры направляют трафик на резервный ЦОД на сетевом уровне ядра за 15–30 секунд.

## Подводные камни

Использовать синхронную репликацию между Москвой и Владивостоком (расстояние 9000 км): задержка света в оптоволокне составляет ~100 мс на каждый коммит транзакции, что обрушит скорость работы базы до 10 транзакций в секунду. Синхронную репликацию применяют строго в радиусе до 100 км (Multi-AZ).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Active-Passive от Active-Active архитектуры мультирегионального развертывания?»
**Ответ:** 
- **Active-Passive:** только один регион принимает запись, второй простаивает как горячий резерв (простота и 100% консистентность).
- **Active-Active:** оба региона одновременно принимают запись. Требует распределенных баз данных (CockroachDB, YugabyteDB) или алгоритмов разрешения конфликтов CRDT, так как одновременное изменение одной строки в двух регионах неизбежно создает конфликт.
