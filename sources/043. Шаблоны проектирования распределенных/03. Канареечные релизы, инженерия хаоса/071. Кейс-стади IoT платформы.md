# Кейс-стади IoT платформы: брокер MQTT, временные ряды (TimescaleDB) и цифровые двойники (Device Twins)

## Условие

**Case Study: IoT Platform (Massive Scale, Time-series):**
* Device connectivity: MQTT broker (например, EMQX) для миллионов устройств.
* Time-series storage: TimescaleDB или InfluxDB для метрик.
* Rule engine: CEP (Complex Event Processing) для триггеров на основе правил.
* Device management: OTA updates, device twins.

## Теория

Архитектура интернета вещей (IoT Architecture на миллионы устройств):
1. **MQTT Protocol (EMQX / VerneMQ):**
   - Легковесный бинарный протокол поверх TCP с минимальным заголовком в 2 байта.
   - Поддерживает Keep-Alive пинги и уровни качества доставки (QoS 0, QoS 1, QoS 2).
2. **Цифровые двойники (Device Twins):**
   - Виртуальное представление физического устройства в облаке (JSON-документ).
   - Хранит желаемое состояние (`desired`) и сообщенное датчиком (`reported`).
   - Если датчик оффлайн, приложение обновляет `desired: {temp: 22}`. Когда кондиционер выйдет в сеть, он синхронизирует состояние.
3. **TimescaleDB / ClickHouse:**
   - Хранение миллиардов телеметрических точек с автоматическим сжатием (Compression Ratio до 95%).

## Решение по шагам

1. Создайте модель цифрового двойника устройства `DeviceTwinState`.
2. Реализуйте логику синхронизации Desired и Reported состояний.
3. Продемонстрируйте выявление дельты для отправки на устройство.
4. Верифицируйте корректность работы цифрового двойника.

## Код решения

**`iot_device_twin_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DeviceTwinState struct {
	DeviceID string
	Desired  map[string]interface{}
	Reported map[string]interface{}
}

func (t *DeviceTwinState) GetPendingDelta() map[string]interface{} {
	delta := make(map[string]interface{})
	for k, desiredVal := range t.Desired {
		reportedVal, exists := t.Reported[k]
		if !exists || reportedVal != desiredVal {
			delta[k] = desiredVal
		}
	}
	return delta
}

func TestIoTDeviceTwin(t *testing.T) {
	twin := &DeviceTwinState{
		DeviceID: "smart-thermostat-101",
		Desired:  map[string]interface{}{"target_temp": 24, "fan_mode": "eco"},
		Reported: map[string]interface{}{"target_temp": 20, "fan_mode": "eco"},
	}

	delta := twin.GetPendingDelta()

	if len(delta) != 1 || delta["target_temp"] != 24 {
		t.Fatalf("Некорректная дельта параметров: %+v", delta)
	}

	twin.Reported["target_temp"] = 24
	syncedDelta := twin.GetPendingDelta()

	if len(syncedDelta) != 0 {
		t.Fatal("Дельта должна быть пустой после синхронизации Reported состояния")
	}

	fmt.Println("Архитектура IoT Платформы (Device Twins) успешно подтверждена:")
	fmt.Printf("  • Обнаружена рассинхронизация параметров: %+v\n", delta)
	fmt.Println("  • Цифровой двойник обеспечивает надежное управление устройствами с нестабильной связью")
}
```

## Под капотом

В TimescaleDB телеметрические данные распределяются по гипертаблицам (Hypertables). База автоматически нарезает данные на временные партиции («чанки» по 1 дню). Фоновый воркер переводит закрытые чанки в колоночный формат (Columnar Compression), снижая потребление диска в 15 раз.

## Подводные камни

Использовать QoS 2 для передачи регулярной телеметрии: оверхед сетевого стека огромен. Для регулярных датчиков используют QoS 0, а для критичных команд управления клапанами — QoS 1.

## На собеседовании

**Вопрос с собеседования:** «Что такое Complex Event Processing (CEP) в IoT платформах?»
**Ответ:** Это движок обработки потоковых событий в скользящем окне реального времени. Например: «Если средняя температура двигателя превышает 95°C в течение 3 минут подряд \(\implies\) отправить аварийный сигнал».
