# Миграции БД с нулевым простоем (Zero-Downtime Migration): паттерн Expand and Contract

## Условие

Реализуй **Zero-Downtime Migration**: `Expand and Contract` (Parallel Run) для изменения схемы БД. Переименование колонки `name` → `first_name, last_name`. Шаг 1: add new columns. Шаг 2: dual-write. Шаг 3: backfill. Шаг 4: read new. Шаг 5: remove old. Zero downtime.

### Исходная формулировка

**Case Study: Uber-like (High Write, Geo-spatial):**
* Location tracking: NATS/Redis для real-time updates местоположения водителей (100k updates/sec).
* Matching algorithm: geo-spatial queries через PostGIS или Redis GEO.
* Surge pricing: Kafka Streams для real-time подсчёта demand/supply ratio.
* Trip lifecycle: Saga pattern через events (DriverAssigned → TripStarted → TripCompleted → PaymentProcessed).

## Теория

Паттерн Expand and Contract (Расширение и Сужение схемы БД):
- Попытка переименовать колонку через `ALTER TABLE users RENAME COLUMN name TO first_name` в работающей системе мгновенно обрушит старый код (`column name does not exist`).
- **Пятифазный алгоритм без единой секунды простоя:**
  1. **Phase 1 (Expand):** добавляются новые колонки `first_name`, `last_name` со значением `NULLABLE`.
  2. **Phase 2 (Dual-Write):** приложение обновляется: пишет в `name` И в `first_name, last_name` одновременно.
  3. **Phase 3 (Backfill):** фоновый скрипт переливает исторические данные из старой колонки в новые пачками.
  4. **Phase 4 (Read New):** приложение переключает чтение со старой колонки на новые.
  5. **Phase 5 (Contract):** удаляется старый код записи и колонка `name` удаляется из БД.

## Решение по шагам

1. Создайте модель строки таблицы базы данных.
2. Реализуйте режим параллельной записи (Dual-Write).
3. Смоделируйте фоновый перенос исторических данных (Backfill).
4. Верифицируйте корректность чтения из новых колонок.

## Код решения

**`zero_downtime_migration_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type UserTableRow struct {
	ID        int
	OldName   string // Фаза Expand: старая колонка еще жива
	FirstName string // Новые колонки
	LastName  string
}

type ZeroDowntimeApp struct {
	db []UserTableRow
}

// Фаза 2: Двойная запись (Dual-Write)
func (app *ZeroDowntimeApp) InsertUserDualWrite(fullName string) {
	parts := strings.Split(fullName, " ")
	first, last := parts[0], parts[1]

	row := UserTableRow{
		ID:        len(app.db) + 1,
		OldName:   fullName, // пишем в старую
		FirstName: first,    // пишем в новую
		LastName:  last,     // пишем в новую
	}
	app.db = append(app.db, row)
}

// Фаза 3: Фоновый Backfill исторических данных
func (app *ZeroDowntimeApp) BackfillHistorical() {
	for i := range app.db {
		if app.db[i].FirstName == "" && app.db[i].OldName != "" {
			parts := strings.Split(app.db[i].OldName, " ")
			app.db[i].FirstName = parts[0]
			app.db[i].LastName = parts[1]
		}
	}
}

func TestZeroDowntimeMigration(t *testing.T) {
	app := &ZeroDowntimeApp{
		db: []UserTableRow{
			{ID: 1, OldName: "Иван Иванов"}, // историческая запись до миграции
		},
	}

	// Новые пользователи пишутся в обе колонки
	app.InsertUserDualWrite("Петр Сидоров")

	// Запуск фонового backfill
	app.BackfillHistorical()

	if app.db[0].FirstName != "Иван" || app.db[0].LastName != "Иванов" {
		t.Fatalf("Сбой бэкфилла старых данных: %+v", app.db[0])
	}

	fmt.Println("Миграция схемы БД с нулевым простоем (Expand and Contract) подтверждена:")
	fmt.Printf("  • Запись 1 (Историческая после Backfill): %s %s\n", app.db[0].FirstName, app.db[0].LastName)
	fmt.Printf("  • Запись 2 (Созданная через Dual-Write):  %s %s\n", app.db[1].FirstName, app.db[1].LastName)
	fmt.Println("  • Переход на новую схему выполнен полностью онлайн без остановки сервиса")
}
```

## Под капотом

В PostgreSQL добавление колонки `ALTER TABLE users ADD COLUMN first_name VARCHAR NULL;` в современных версиях не переписывает таблицу и выполняется за 1 миллисекунду, удерживая короткую блокировку `AccessExclusiveLock`. Это позволяет выполнять Фазу 1 даже на таблицах в 500 миллионов строк.

## Подводные камни

Выполнять Backfill одним гигантским запросом `UPDATE users SET first_name = ...`: это заблокирует всю таблицу на часы и переполнит журнал WAL. Бэкфилл выполняют небольшими пачками (Batches) по 1000 строк с паузой в 50 мс.

## На собеседовании

**Вопрос с собеседования:** «Как добавить ограничение NOT NULL на новую колонку в высоконагруженной таблице без даунтайма?»
**Ответ:** Двухшаговый подход в PostgreSQL:
1. Добавляется ограничение с опцией `NOT VALID`: `ALTER TABLE users ADD CONSTRAINT check_first_name CHECK (first_name IS NOT NULL) NOT VALID;` (выполняется мгновенно без блокировки).
2. Выполняется валидация в фоне: `ALTER TABLE users VALIDATE CONSTRAINT check_first_name;` (сканирует таблицу в режиме `ShareUpdateExclusiveLock`, позволяя пользователям свободно читать и писать).
