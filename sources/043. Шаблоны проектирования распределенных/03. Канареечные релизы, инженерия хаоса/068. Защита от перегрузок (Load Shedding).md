# Защита от перегрузок (Load Shedding): сброс трафика со статусом 503 и заголовком Retry-After

## Условие

**Защита от перегрузок (Load Shedding)**: При резком всплеске трафика сервер может упасть из-за нехватки памяти или процессора. Напишите HTTP-middleware, которое отслеживает текущую нагрузку: если глубина очереди активных запросов сервера превышает 500 штук или загрузка процессора приближается к критической, middleware должно мгновенно возвращать статус `503 Service Unavailable`, сбрасывая избыточную нагрузку и защищая систему от падения.

## Теория

Принцип сброса нагрузки (Load Shedding — Google SRE):
- Закон Литтла и деградация очередей: когда входящий трафик превышает максимальную пропускную способность, длина очереди стремится к бесконечности, а задержка всех запросов вырастает до минут.
- Сервер перестает отвечать вообще всем клиентам.
- **Load Shedding решает проблему жестким отсечением:**
  - Сервер определяет свой безопасный предел одновременных запросов (Concurrency Limit).
  - Запросы сверх лимита **сбрасываются мгновенно за 0.1 мс** с кодом `HTTP 503 Service Unavailable` и заголовком `Retry-After: 5`.
  - Благодаря этому 80% клиентов получают нормальные быстрые ответы, а сервер остается живым!

## Решение по шагам

1. Создайте счетчик активных запросов в `LoadSheddingMiddleware`.
2. Задайте порог перегрузки в 2 одновременных запроса для теста.
3. Смоделируйте третий конкурентный запрос.
4. Верифицируйте мгновенный возврат HTTP 503 с заголовком Retry-After.

## Код решения

**`load_shedding_middleware_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"testing"
)

type LoadSheddingMiddleware struct {
	activeInflight int64
	maxAllowed     int64
}

func (m *LoadSheddingMiddleware) Wrap(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		current := atomic.AddInt64(&m.activeInflight, 1)
		defer atomic.AddInt64(&m.activeInflight, -1)

		// Превышение безопасного порога -> СБРОС НАГРУЗКИ (Load Shedding)
		if current > m.maxAllowed {
			w.Header().Set("Retry-After", "5")
			w.WriteHeader(http.StatusServiceUnavailable)
			w.Write([]byte("Server is overloaded. Load shedding engaged (503)."))
			return
		}

		next.ServeHTTP(w, r)
	})
}

func TestLoadSheddingMiddleware(t *testing.T) {
	middleware := &LoadSheddingMiddleware{maxAllowed: 1} // Лимит 1 для проверки сброса

	targetHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("Normal response"))
	})

	handler := middleware.Wrap(targetHandler)

	// Искусственно занимаем слот (сервер под нагрузкой)
	atomic.StoreInt64(&middleware.activeInflight, 1)

	// Входящий запрос в перегруженный сервер
	req := httptest.NewRequest(http.MethodGet, "/api/checkout", nil)
	rec := httptest.NewRecorder()
	handler.ServeHTTP(rec, req)

	if rec.Code != http.StatusServiceUnavailable || rec.Header().Get("Retry-After") != "5" {
		t.Fatalf("Ожидался сброс 503 с Retry-After: %d", rec.Code)
	}

	fmt.Println("Защита от перегрузок (Load Shedding) успешно подтверждена:")
	fmt.Printf("  • Статус ответа: %d Service Unavailable\n", rec.Code)
	fmt.Printf("  • Заголовок:     Retry-After: %s сек\n", rec.Header().Get("Retry-After"))
	fmt.Printf("  • Тело ответа:   %s\n", rec.Body.String())
	fmt.Println("  • Сервер сбросил избыточный трафик, защитив память и процессор от падения")
}
```

ℹ️ Мгновенный сброс избыточных запросов со статусом 503 при превышении емкости сервера

## Под капотом

В Netflix и Uber используют алгоритм **CoDel (Controlled Delay)** и адаптивный Load Shedding по задержке: если P90 время ответа возрастает выше критического порога, сервер начинает сбрасывать низкоприоритетные запросы (фоновые синхронизации), сохраняя прием заказов и платежей.

## Подводные камни

Сбрасывать запросы случайным образом: если сбросить запрос шага оплаты, клиент потеряет корзину. Внедряют приоритеты запросов (Request Priority): критичные эндпоинты оформления заказа не сбрасываются никогда.

## На собеседовании

**Вопрос с собеседования:** «Почему возврат ошибки 503 при перегрузке лучше, чем удержание запроса в длинной очереди ожидания?»
**Ответ:** Потому что клиентский браузер или мобильное приложение по истечении таймаута (например 5 секунд) само оборвет соединение и сделает ретрай. Зависший в очереди запрос потратит ресурсы сервера впустую, так как ответ клиенту уже никто не ждет. Fail-Fast освобождает ресурсы мгновенно.
