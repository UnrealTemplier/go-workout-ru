# Кейс-стади Финтех и Банкинг: двойная бухгалтерская запись (Double-Entry Bookkeeping) и аудит балансов

## Условие

**Case Study: Fintech/Banking (ACID, Compliance):**
* Double-entry bookkeeping: каждая транзакция — это debit и credit записи.
* Fraud detection: real-time scoring через ML model ( TensorFlow Serving).
* Audit trail: immutable log всех операций.
* Regulatory reporting: batch jobs для генерации отчётов.

## Теория

Принцип двойной бухгалтерской записи (Double-Entry Bookkeeping — Лука Пачоли, 1494):
- В финансовых системах баланс счета **никогда не меняется одной операцией `balance = balance - 100`**.
- Деньги не могут появиться из ниоткуда или исчезнуть в никуда.
- **Инвариант бухгалтерского баланса:**
  Каждая финансовая транзакция состоит минимум из двух проводок:
  $$\sum \text{Debit} = \sum \text{Credit}$$
- **Пример перевода 5 000 руб со счета Алисы на счет Боба:**
  1. `Entry 1`: Списание со счета Алисы \(\implies\) `Account: Alice, Debit: 5000`.
  2. `Entry 2`: Зачисление на счет Боба \(\implies\) `Account: Bob, Credit: 5000`.
- Сумма дебета равна сумме кредита. Проверка этого равенства гарантирует отсутствие бухгалтерских ошибок!

## Решение по шагам

1. Создайте структуру финансовой проводки `LedgerEntry`.
2. Реализуйте валидатор нулевой суммы баланса (Zero-Sum Invariant).
3. Продемонстрируйте корректный перевод средств.
4. Продемонстрируйте отклонение несбалансированной проводки.

## Код решения

**`double_entry_bookkeeping_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type LedgerEntry struct {
	AccountID string
	AmountRub int64 // Положительное = Debit, Отрицательное = Credit
}

type BankTransaction struct {
	TxID    string
	Entries []LedgerEntry
}

func (tx *BankTransaction) ValidateDoubleEntry() error {
	var balanceSum int64
	for _, e := range tx.Entries {
		balanceSum += e.AmountRub
	}
	// Фундаментальное правило финтеха: сумма проводок обязана быть строго равна 0!
	if balanceSum != 0 {
		return fmt.Errorf("double-entry violation: transaction sum is %d (must be 0)", balanceSum)
	}
	return nil
}

func TestDoubleEntryBookkeeping(t *testing.T) {
	// 1. Валидный перевод 5000 рублей от Алисы к Бобу
	validTx := &BankTransaction{
		TxID: "tx-bank-9901",
		Entries: []LedgerEntry{
			{AccountID: "acc-alice", AmountRub: -5000}, // Credit (списание)
			{AccountID: "acc-bob", AmountRub: 5000},    // Debit (пополнение)
		},
	}

	if err := validTx.ValidateDoubleEntry(); err != nil {
		t.Fatalf("Валидная банковская транзакция отклонена: %v", err)
	}

	// 2. Несбалансированная мошенническая транзакция (попытка нарисовать 1000 руб из воздуха)
	fraudTx := &BankTransaction{
		TxID: "tx-fraud-007",
		Entries: []LedgerEntry{
			{AccountID: "acc-alice", AmountRub: -5000},
			{AccountID: "acc-bob", AmountRub: 6000}, // +1000 руб из воздуха!
		},
	}

	errFraud := fraudTx.ValidateDoubleEntry()
	if errFraud == nil {
		t.Fatal("Несбалансированная транзакция обязана быть отклонена!")
	}

	fmt.Println("Финтех и Банкинг (Double-Entry Bookkeeping) подтверждены:")
	fmt.Printf("  • Валидная транзакция: Дебет = Кредит (Сумма = 0)\n")
	fmt.Printf("  • Несбалансированная попытка: %v\n", errFraud)
	fmt.Println("  • Бухгалтерский инвариант исключает потерю или несанкционированную эмиссию денег")
}
```

## Под капотом

В финтех-системах деньги хранят в целочисленных копейках/центах (`int64`), категорически исключая типы с плавающей точкой `float32/float64`, которые накапливают ошибки округления двоичной мантиссы IEEE-754 (\(0.1 + 0.2 = 0.30000000000000004\)).

## Подводные камни

Хранить текущий баланс в виде изменяемой колонки `UPDATE accounts SET balance = balance + 100`: при блокировках строки деградирует скорость. Баланс вычисляют как сумму проводок `SELECT SUM(amount) FROM ledger_entries WHERE account_id = $1` с периодическим сохранением снепшотов.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить дедлок в базе данных при одновременных встречных переводах (Алиса переводит Бобу, а Боб в ту же миллисекунду переводит Алисе)?»
**Ответ:** Принцип детерминированного порядка блокировок (Lock Ordering): аккаунты сортируются по их ID (`order by account_id`). Обе транзакции всегда блокируют аккаунты строго в одинаковом порядке (сначала меньший ID, затем больший ID), что математически исключает циклические взаимные блокировки Deadlock.
