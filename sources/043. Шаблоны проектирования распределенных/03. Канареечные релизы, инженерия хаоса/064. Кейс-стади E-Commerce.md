# Кейс-стади E-Commerce: распределенные блокировки Redis от овербукинга и движок промокодов

## Условие

**Case Study: E-commerce (Complex Business Logic):**
* Inventory management: distributed locks через Redis для предотвращения overselling.
* Pricing engine: правила скидок, промокоды, dynamic pricing.
* Order processing: Saga с компенсирующими действиями.
* Payment gateway integration: idempotency, webhook handling, reconciliation.

## Теория

Комплексная архитектура Enterprise E-Commerce (Ozon, Wildberries):
1. **Предотвращение овербукинга (Overselling Prevention):**
   - Во время распродажи («Черная пятница») на 1 оставшийся iPhone претендуют 5 000 покупателей.
   - Решение: распределенная блокировка (Distributed Lock / Redlock) или атомарный Lua-скрипт в Redis:
     `if redis.call('get', KEYS[1]) >= ARGV[1] then return redis.call('decrby', KEYS[1], ARGV[1]) else return -1 end`
2. **Pricing Engine (Движок ценообразования):**
   - Расчет финальной цены: базовая цена \(\to\) накопительная скидка покупателя \(\to\) акционный промокод \(\to\) списание бонусов.
3. **Reconciliation (Сверка платежей):**
   - Ежедневный ночной джоб сверяет успешные проводки банка с базой данных магазина, выявляя расхождения.

## Решение по шагам

1. Создайте атомарный менеджер бронирования остатков.
2. Реализуйте движок применения промокодов и скидок.
3. Смоделируйте конкурентную попытку выкупа последнего товара.
4. Верифицируйте корректность расчета цен и защиту от овербукинга.

## Код решения

**`ecommerce_architecture_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type ECommerceStockManager struct {
	mu         sync.Mutex
	stockCount map[string]int
}

func (m *ECommerceStockManager) AtomicReserve(sku string, qty int) bool {
	m.mu.Lock()
	defer m.mu.Unlock()

	if m.stockCount[sku] >= qty {
		m.stockCount[sku] -= qty
		return true
	}
	return false
}

type PricingEngine struct{}

func (p *PricingEngine) CalculatePrice(basePrice float64, promoCode string) float64 {
	discount := 0.0
	if promoCode == "BLACK_FRIDAY_2026" {
		discount = 0.20 // Скидка 20%
	}
	return basePrice * (1.0 - discount)
}

func TestECommerceArchitecture(t *testing.T) {
	stock := &ECommerceStockManager{stockCount: map[string]int{"iphone-16": 1}}
	pricing := &PricingEngine{}

	finalPrice := pricing.CalculatePrice(100000.0, "BLACK_FRIDAY_2026")
	if finalPrice != 80000.0 {
		t.Fatalf("Некорректная скидка: %.2f", finalPrice)
	}

	// 2 параллельных покупателя пытаются забрать последний iPhone
	buyer1 := stock.AtomicReserve("iphone-16", 1)
	buyer2 := stock.AtomicReserve("iphone-16", 1)

	if !buyer1 || buyer2 {
		t.Fatalf("Оверселлинг не предотвращен: b1=%v, b2=%v", buyer1, buyer2)
	}

	fmt.Println("Архитектура E-Commerce платформы успешно подтверждена:")
	fmt.Printf("  • Базовая цена 100 000 руб с промокодом BLACK_FRIDAY_2026: %.2f руб\n", finalPrice)
	fmt.Printf("  • Конкурентная бронь: Покупатель 1 = %v, Покупатель 2 = %v\n", buyer1, buyer2)
	fmt.Println("  • Овербукинг предотвращен: остаток товара на складе равен 0 шт")
}
```

## Под капотом

В распределенном Redis блокировка захватывается через `SET lock:sku-16 unique_worker_id NX PX 5000`. Освобождение блокировки выполняется строго через Lua-скрипт, проверяющий совпадение `unique_worker_id`, чтобы воркер не снял чужую блокировку по истечении таймаута.

## Подводные камни

Считать скидки на стороне фронтенда: злоумышленник подменит JSON в запросе и отправит заказ с `price = 1 рубль`. Все расчеты цен, скидок и бонусов производятся **исключительно на бэкенде**.

## На собеседовании

**Вопрос с собеседования:** «Как обрабатывать Webhook от банка об успешной оплате, если банк шлет его 3 раза подряд?»
**Ответ:** Прием вебхука строится по паттерну Idempotent Consumer: в таблице `payment_transactions` статус обновляется только если текущий статус `PENDING`. Повторные вебхуки мгновенно возвращают HTTP 200 OK без повторного начисления товаров или запуска отправки заказа.
