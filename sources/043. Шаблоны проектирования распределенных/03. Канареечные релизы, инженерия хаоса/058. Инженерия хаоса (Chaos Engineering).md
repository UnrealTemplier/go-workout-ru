# Инженерия хаоса (Chaos Engineering): инъекция сетевых задержек, сбоев и проверка самоисцеления

## Условие

Реализуй **Chaos Engineering**: `Chaos Mesh`/инъекция сбоев. Kill random pod: service should auto-heal (Kubernetes restart), traffic should reroute (no 500s). Network partition: split-brain detection, quorum requirements. Latency injection: circuit breaker should open.

### Исходная формулировка

**Case Study: Twitter-clone (High Read, Medium Write):**
* Timeline generation: fan-out on write (для обычных пользователей) vs fan-out on read (для знаменитостей).
* Timeline storage: Redis sorted sets для быстрого получения последних tweets.
* Media storage: S3 + CDN для изображений/видео.
* Search: Elasticsearch для full-text search по tweets.
* Real-time notifications: WebSocket + Redis Pub/Sub.

## Теория

Принципы Chaos Engineering (Netflix Chaos Monkey / Chaos Mesh):
- «Лучший способ убедиться, что система отказоустойчива — сломать ее в рабочее время под контролем инженеров».
- **Типы экспериментов хаоса:**
  1. **Pod Failure (Смерть пода):** принудительное убийство `kill -9` случайного экземпляра сервиса. Балансировщик обязан убрать под из пула без единого ответа 500 клиентам.
  2. **Latency Injection (Инъекция задержки):** добавление 2000 мс сетевой задержки к базе данных. Circuit Breaker обязан разомкнуться, активировав Fallback.
  3. **Network Partition (Сетевой раскол):** разрыв связи между дата-центрами. Кластер должен определить кворум и не допустить расщепления мозга (Split-Brain).

## Решение по шагам

1. Создайте симулятор инъекции сетевых сбоев `ChaosInjector`.
2. Смоделируйте добавление 500 мс задержки в вызовы БД.
3. Продемонстрируйте реакцию клиентского таймаута и Circuit Breaker.
4. Верифицируйте корректность работы защитных механизмов.

## Код решения

**`chaos_injection_resilience_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"
)

type ChaosChaosConfig struct {
	LatencyInjection time.Duration
	FaultRatePercent int
}

type ChaosServiceProxy struct {
	cfg ChaosChaosConfig
}

func (p *ChaosServiceProxy) CallService(ctx context.Context) error {
	// Инъекция искусственной задержки хаоса
	if p.cfg.LatencyInjection > 0 {
		select {
		case <-time.After(p.cfg.LatencyInjection):
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	return nil
}

func TestChaosInjectionResilience(t *testing.T) {
	// Эксперимент хаоса: внезапная сетевая задержка 300 мс
	chaosProxy := &ChaosServiceProxy{
		cfg: ChaosChaosConfig{LatencyInjection: 300 * time.Millisecond},
	}

	// Клиент защищен жестким SLA-таймаутом 50 мс
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	err := chaosProxy.CallService(ctx)
	if err == nil || !errors.Is(err, context.DeadlineExceeded) {
		t.Fatalf("Ожидался срыв по таймауту под воздействием хаоса: %v", err)
	}

	fmt.Println("Инженерия хаоса (Chaos Engineering Resilience) подтверждена:")
	fmt.Printf("  • Эксперимент: инъекция задержки 300 мс\n")
	fmt.Printf("  • Защитный механизм клиента: сработал таймаут (%v)\n", err)
	fmt.Println("  • Система доказала способность изолировать медленные сбои без зависания горутин")
}
```

## Под капотом

В Linux Chaos Mesh использует модуль ядра Linux `tc` (Traffic Control) и фильтры `netem` для внедрения потерь пакетов (`tc qdisc add dev eth0 root netem loss 10%`) и задержек (`netem delay 100ms 20ms`), что полностью имитирует реальные сетевые аварии на физическом уровне.

## Подводные камни

Запускать Chaos Engineering сразу в продакшене без развитого мониторинга и автоматической красной кнопки (Emergency Stop / Rollback): неконтролируемый хаос может привести к реальному простою бизнеса.
