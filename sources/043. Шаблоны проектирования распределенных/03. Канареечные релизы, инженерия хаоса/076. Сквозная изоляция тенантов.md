# Сквозная изоляция тенантов: инъекция tenant_id из JWT и квоты вычислительных ресурсов

## Условие

Реализуй **Tenant Isolation**: `tenant_id` in every table, `WHERE tenant_id = current_tenant()` in every query (RLS policy in PostgreSQL). JWT contains `tenant_id`, service extracts and enforces. Cross-tenant queries forbidden. Resource quotas per tenant.

## Теория

Сквозной конвейер изоляции тенанта от шлюза до ядра базы данных:
1. **Периметр:** Пользователь отправляет JWT токен с клеймом `{"sub": "user-5", "tenant_id": "org-avito"}`.
2. **Go Middleware:**
   - Извлекает `tenant_id` из JWT.
   - Помещает его в `context.Context`.
   - Запрещает запросы, если `tenant_id` отсутствует.
3. **Repository Layer:**
   - Выполняет в транзакции: `SET LOCAL app.current_tenant = 'org-avito'`.
4. **PostgreSQL Kernel:**
   - Политика RLS `USING (tenant_id = current_setting('app.current_tenant'))` гарантирует, что ни один SQL-запрос не вернет данные чужой организации.

## Решение по шагам

1. Создайте HTTP Middleware для извлечения `tenant_id` из контекста токена.
2. Реализуйте проверку прав доступа к ресурсам.
3. Смоделируйте блокировку попытки межтенантного доступа (Cross-Tenant Access).
4. Верифицируйте изоляцию данных.

## Код решения

**`tenant_isolation_pipeline_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

type tenantKeyType struct{}

func InjectTenantContext(ctx context.Context, tenantID string) context.Context {
	return context.WithValue(ctx, tenantKeyType{}, tenantID)
}

func ExtractTenantContext(ctx context.Context) (string, error) {
	tenant, ok := ctx.Value(tenantKeyType{}).(string)
	if !ok || tenant == "" {
		return "", errors.New("security error: missing tenant_id in request context")
	}
	return tenant, nil
}

type SecureTenantDocumentRepository struct {
	storage map[string]string // docID -> tenantID
}

func (r *SecureTenantDocumentRepository) GetDocument(ctx context.Context, docID string) (string, error) {
	currentTenant, err := ExtractTenantContext(ctx)
	if err != nil {
		return "", err
	}

	docTenant, found := r.storage[docID]
	if !found {
		return "", errors.New("document not found")
	}

	// Проверка принадлежности документа тенанту (Cross-tenant check)
	if docTenant != currentTenant {
		return "", errors.New("security violation: cross-tenant access forbidden (403)")
	}

	return fmt.Sprintf("Document %s content for tenant %s", docID, currentTenant), nil
}

func TestTenantIsolationPipeline(t *testing.T) {
	repo := &SecureTenantDocumentRepository{
		storage: map[string]string{
			"doc-1": "tenant-avito",
			"doc-2": "tenant-ozon",
		},
	}

	// 1. Легитимный запрос от Авито к своему документу
	ctxAvito := InjectTenantContext(context.Background(), "tenant-avito")
	doc, err := repo.GetDocument(ctxAvito, "doc-1")
	if err != nil {
		t.Fatalf("Авито должно иметь доступ к своему документу: %v", err)
	}

	// 2. Попытка Авито прочитать чужой документ Озона (IDOR / Cross-Tenant Attack)
	_, errCross := repo.GetDocument(ctxAvito, "doc-2")
	if errCross == nil {
		t.Fatal("Межтенантный доступ обязан быть заблокирован!")
	}

	fmt.Println("Сквозная изоляция тенантов (Tenant Isolation Pipeline) подтверждена:")
	fmt.Printf("  • Легитимный доступ: %s\n", doc)
	fmt.Printf("  • Попытка чтения чужих данных: %v\n", errCross)
	fmt.Println("  • Любые перекрестные вызовы между тенантами надежно блокируются")
}
```

## Под капотом

Для исключения ошибок разработчиков во многих фреймворках используют GORM или ent хуки: перед генерацией SQL-запроса библиотека автоматически принудительно дописывает `AND tenant_id = ?` ко всем запросам `SELECT`, `UPDATE` и `DELETE`.

## Подводные камни

Позволять клиенту передавать `tenant_id` в query-параметрах `GET /orders?tenant_id=123`: злоумышленник подменит число в браузере и прочитает чужие данные. Идентификатор тенанта извлекают **строго из криптографически подписанного JWT токена**.

## На собеседовании

**Вопрос с собеседования:** «Как ограничить потребление ресурсов (Resource Quotas) для конкретного агрессивного тенанта?»
**Ответ:** Rate Limiter на базе Redis Token Bucket: для каждого `tenant_id` задается персональный лимит (например 500 RPS). При превышении запросы именно этого тенанта получают `HTTP 429`, в то время как остальные клиенты продолжают работать без задержек.
