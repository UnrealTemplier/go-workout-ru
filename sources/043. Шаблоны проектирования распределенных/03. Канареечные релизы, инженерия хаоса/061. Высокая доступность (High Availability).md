# Высокая доступность (High Availability): Multi-AZ кластеризация, Patroni и автоматический Failover

## Условие

**High Availability**: Настройте multi-AZ deployment: 3 реплики приложения в разных зонах доступности. PostgreSQL HA с Patroni (leader election через etcd, streaming replication). Покажи, что при падении AZ система продолжает работать.

### Исходная формулировка

Реализуй **Observability-Driven Deployment**: deploy → monitor SLO for 30 min → auto-promote or rollback. Metrics: error rate, latency p95, business metrics (orders/min). If any metric degrades → automatic rollback to previous version.

## Теория

Принципы построения High Availability (SLA 99.99%):
- **Разделение по зонам доступности (Multi-AZ Deployment):**
  - Дата-центры AZ-A, AZ-B, AZ-C расположены на расстоянии 20–50 км друг от друга с независимыми каналами питания и оптоволокна.
  - Поды Go-приложения распределяются с помощью K8s `topologySpreadConstraints`.
- **Автоматический Failover СУБД с Patroni и etcd:**
  1. Patroni на мастере непрерывно продлевает TTL ключа-лидера в распределенном хранилище etcd.
  2. Если дата-центр AZ-A полностью обесточен, аренда ключа истекает через 10 секунд.
  3. Реплики в AZ-B и AZ-C проводят голосование (Raft Leader Election) в etcd.
  4. Самая свежая реплика автоматически промоутится в нового мастера `Primary`.
  5. HAProxy / pgBouncer перенаправляет трафик записи за секунды.

## Решение по шагам

1. Создайте модель кластера Patroni с распределенным лидером.
2. Смоделируйте аварию в первичной зоне доступности AZ-A.
3. Продемонстрируйте автоматические выборы нового лидера в AZ-B.
4. Верифицируйте бесперебойную доступность кластера.

## Код решения

**`patroni_failover_ha_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DatabaseNodeRole string

const (
	RolePrimary DatabaseNodeRole = "PRIMARY"
	RoleStandby DatabaseNodeRole = "STANDBY"
)

type PatroniNode struct {
	AZ       string
	Role     DatabaseNodeRole
	IsAlive  bool
	LSN      int // Log Sequence Number (свежесть данных)
}

type PatroniClusterManager struct {
	nodes []*PatroniNode
}

func (m *PatroniClusterManager) ElectNewLeader() *PatroniNode {
	var bestCandidate *PatroniNode
	for _, n := range m.nodes {
		if !n.IsAlive {
			continue
		}
		if bestCandidate == nil || n.LSN > bestCandidate.LSN {
			bestCandidate = n
		}
	}
	if bestCandidate != nil {
		bestCandidate.Role = RolePrimary
	}
	return bestCandidate
}

func TestPatroniFailoverHA(t *testing.T) {
	nodeA := &PatroniNode{AZ: "zone-a", Role: RolePrimary, IsAlive: true, LSN: 1000}
	nodeB := &PatroniNode{AZ: "zone-b", Role: RoleStandby, IsAlive: true, LSN: 1000}
	nodeC := &PatroniNode{AZ: "zone-c", Role: RoleStandby, IsAlive: true, LSN: 990}

	cluster := &PatroniClusterManager{nodes: []*PatroniNode{nodeA, nodeB, nodeC}}

	// Авария дата-центра: Zone A обесточена!
	nodeA.IsAlive = false

	// Patroni + etcd автоматически выбирают нового лидера с максимальным LSN
	newLeader := cluster.ElectNewLeader()

	if newLeader == nil || newLeader.AZ != "zone-b" || newLeader.Role != RolePrimary {
		t.Fatalf("Сбой автоматического failover: %+v", newLeader)
	}

	fmt.Println("Высокая доступность (High Availability с Patroni) подтверждена:")
	fmt.Printf("  • Авария в zone-a: Мастер отключен\n")
	fmt.Printf("  • Новый выбранный Primary: %s (Роль: %s, LSN: %d)\n",
		newLeader.AZ, newLeader.Role, newLeader.LSN)
	fmt.Println("  • Автоматический Failover завершен без потери транзакций")
}
```

## Под капотом

Для исключения Split-Brain (когда два узла одновременно считают себя мастерами) Patroni использует кворумный консенсус Raft в etcd: узел может объявить себя лидером только при поддержке строгого большинства участников \((N/2 + 1)\).

## Подводные камни

Развертывать кластер etcd из четного числа нод (например 2 или 4 ноды): при падении 1 ноды в 2-нодовом кластере кворум \(2/2+1=2\) теряется, и кластер полностью блокирует выборы. Кластеры консенсуса строят строго из **3 или 5 нод**.

## На собеседовании

**Вопрос с собеседования:** «Что такое Fencing (STONITH) при автоматическом фейловере баз данных?»
**Ответ:** STONITH (Shoot The Other Node In The Head) — это аппаратный или облачный механизм принудительной изоляции старого мастера (отключение питания через IPMI или отрыв облачного диска EBS). Это гарантирует, что старый «зависший» мастер случайно не проснется и не начнет принимать параллельные транзакции записи.
