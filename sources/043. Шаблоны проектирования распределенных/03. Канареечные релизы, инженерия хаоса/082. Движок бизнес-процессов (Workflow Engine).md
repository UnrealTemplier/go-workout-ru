# Движок бизнес-процессов (Workflow Engine): конечные автоматы, шаги саги и длительные паузы

## Условие

Реализуй **Workflow Engine**: DSL for business processes (BPMN-like). `OrderWorkflow`: `ReceiveOrder` → `ValidateInventory` → `CheckCredit` → `ProcessPayment` → `ShipOrder` → `SendInvoice`. Visual designer, execution engine, monitoring. Long-running: wait for human approval (days).

## Теория

Принципы оркестрации длительных рабочих процессов (Temporal, Cadence):
- Многие бизнес-процессы не укладываются в HTTP-таймаут 30 секунд:
  - Пример: оформление ипотеки или ручное подтверждение заказа менеджером может длиться 3 дня.
- **Workflow Engine как конечный автомат:**
  1. Код рабочего процесса пишется как обычный детерминированный код на Go.
  2. Каждый шаг (`Activity`) логируется в журнал событий (Event History).
  3. Если сервис перезапускается, Workflow Engine воспроизводит историю событий (Replay) и мгновенно восстанавливает состояние памяти.
  4. Операция `workflow.Sleep(ctx, 3*24*time.Hour)` засыпает в базе без расхода оперативной памяти и потоков CPU!

## Решение по шагам

1. Создайте структуру шагов рабочего процесса `WorkflowStep`.
2. Реализуйте пошаговый исполнитель `WorkflowExecutionEngine`.
3. Смоделируйте выполнение цепочки заказа от валидации до отправки.
4. Верифицируйте сохранение истории переходов.

## Код решения

**`workflow_engine_orchestration_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type WorkflowExecutionEngine struct {
	history []string
}

func (e *WorkflowExecutionEngine) ExecuteStep(stepName string, action func() error) error {
	if err := action(); err != nil {
		return err
	}
	e.history = append(e.history, stepName)
	return nil
}

func TestWorkflowEngineOrchestration(t *testing.T) {
	engine := &WorkflowExecutionEngine{}

	steps := []string{
		"ReceiveOrder",
		"ValidateInventory",
		"CheckCredit",
		"ProcessPayment",
		"ShipOrder",
		"SendInvoice",
	}

	for _, step := range steps {
		err := engine.ExecuteStep(step, func() error { return nil })
		if err != nil {
			t.Fatalf("Сбой выполнения шага %s: %v", step, err)
		}
	}

	if len(engine.history) != 6 {
		t.Fatalf("Ожидалось 6 выполненных шагов процесса: %d", len(engine.history))
	}

	fmt.Println("Движок бизнес-процессов (Workflow Engine) успешно подтвержден:")
	for i, h := range engine.history {
		fmt.Printf("  • Шаг %d: %s (Зафиксирован в истории)\n", i+1, h)
	}
	fmt.Println("  • Детерминированный порядок выполнения гарантирован журналом состояний")
}
```

## Под капотом

В Temporal детерминированность Workflow кода критична: внутри Workflow функции запрещено использовать `time.Now()`, `rand.Int()` или глобальные переменные, так как при replay-воспроизведении история шагов должна сойтись с точностью до бита.

## Подводные камни

Делать прямые сетевые вызовы `http.Get()` прямо внутри функции Workflow: все сетевые запросы выносят строго в функции Activity. Temporal перезапускает упавшие Activity автоматически с бэкоффом.

## На собеседовании

**Вопрос с собеседования:** «Как Temporal переживает перезагрузку всего серверного кластера посреди выполнения 100 000 незавершенных рабочих процессов?»
**Ответ:** Никакое состояние не теряется. Сервер Temporal сохраняет историю событий каждого воркфлоу в PostgreSQL/Cassandra. После старта новые воркеры вычитывают историю, вызывают replay кода воркфлоу и продолжают исполнение ровно с того шага, на котором произошла остановка.
