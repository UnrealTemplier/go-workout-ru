# Системный дизайн банковского ядра (Banking Core): надежность 99.999%, Event Sourcing и аудит

## Условие

Спроектируй **Banking Core System**:
- Services: `Account`, `Transaction`, `Transfer`, `Loan`, `KYC`, `Compliance`, `Reporting`
- Patterns: Strong consistency (synchronous), Event Sourcing (audit), CQRS (reporting)
- Security: mTLS, HSM, field-level encryption, audit trail, fraud detection (real-time ML)
- Compliance: PCI-DSS, SOX, Basel III, GDPR
- Availability: 99.999% (5 minutes downtime/year), multi-region active-active

## Теория

Проектирование банковского ядра с доступностью 5 девяток (SLA 99.999%):
- Допустимый простой: **менее 5 минут 15 секунд в год**!
- **Принципы архитектуры Core Banking:**
  1. **Строгая консистентность (Strong Consistency):** синхронные финансовые транзакции с сериализуемой изоляцией (Serializable Snapshot Isolation / SSI).
  2. **Event Sourcing:** баланс счета — это результат свертки журнала проводок (Ledger Entries). Перезапись или удаление проводок невозможны.
  3. **Аппаратная безопасность (HSM / Hardware Security Module):** мастер-ключи шифрования хранятся в защищенном чипе, стирающем память при попытке физического вскрытия.

## Решение по шагам

1. Создайте спецификацию банковского ядра с требованиями регуляторов.
2. Продемонстрируйте проверку пяти девяток надежности.
3. Опишите эшелоны безопасности HSM и mTLS.
4. Верифицируйте соответствие стандартам PCI-DSS и Basel III.

**`banking_core_system_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type BankingCoreArchitecture struct {
	MaxYearlyDowntime time.Duration
	ComplianceStandards []string
	SecurityEnforcements []string
}

func GetBankingCoreDesign() BankingCoreArchitecture {
	return BankingCoreArchitecture{
		MaxYearlyDowntime: 5 * time.Minute, // 99.999% Five Nines
		ComplianceStandards: []string{"PCI-DSS", "SOX", "Basel III", "GDPR"},
		SecurityEnforcements: []string{"mTLS Everywhere", "HSM Key Custody", "Field-Level AES-256", "Immutable Audit"},
	}
}

func TestBankingCoreSystem(t *testing.T) {
	design := GetBankingCoreDesign()

	if design.MaxYearlyDowntime > 6*time.Minute {
		t.Fatal("SLA 99.999% требует не более 5.25 минут простоя в год!")
	}

	fmt.Println("Архитектурный проект банковского ядра (Banking Core System):")
	fmt.Printf("  • Допустимый простой в год (SLA 99.999%%): %v\n", design.MaxYearlyDowntime)
	fmt.Printf("  • Стандарты соответствия: %v\n", design.ComplianceStandards)
	fmt.Printf("  • Инженерные средства безопасности: %v\n", design.SecurityEnforcements)
	fmt.Println("  • Event Sourcing гарантирует 100% математическую доказуемость балансов для ЦБ")
}
```

## Под капотом

Для доступности 99.999% банковские кластеры развертывают в топологии Active-Active на базе CockroachDB с синхронным репликационным консенсусом Raft, разнесенным по 3 независимым городам с выделенными темными оптоволоконными линиями (Dark Fiber).

## Подводные камни

Использовать асинхронную репликацию для переводов средств: авария мастера приведет к потере подтвержденных транзакций (RPO > 0), что запрещено финансовыми регуляторами.

## На собеседовании

**Вопрос с собеседования:** «Как в банках разделяют горячий транзакционный учет от тяжелых регуляторных отчетов для регулятора?»
**Ответ:** Через паттерн CQRS и CDC репликацию: транзакционное ядро пишет только проводки в PostgreSQL/CockroachDB. Debezium передает поток проводок в аналитический ClickHouse, где ночные батч-джобы строят 500-страничные отчеты без влияния на процессор ядра банка.
