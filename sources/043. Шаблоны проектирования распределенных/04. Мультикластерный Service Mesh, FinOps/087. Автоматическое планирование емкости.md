# Автоматическое планирование емкости (Capacity Planning): прогнозное масштабирование и подгонка ресурсов

## Условие

Реализуй **Automated Capacity Planning**: predictive scaling, historical trend analysis, automated resource request adjustments. Спрогнозируй нагрузку на черную пятницу на основе тренда прошлой недели.

### Исходная формулировка

**CQRS с разными хранилищами для чтения и записи**. Команды пишут в PostgreSQL (нормализованно), запросы читают из Elasticsearch или MongoDB. Реализуйте асинхронную синхронизацию через брокер.

## Теория

Прогнозное масштабирование инфраструктуры (Predictive Capacity Planning):
- Обычный реактивный автоскейлинг HPA реагирует **с опозданием на 3–5 минут**: пока CPU превысит 80%, пока Kubelet заметит всплеск, пока облако выделит новую ноду — сервер успеет упасть под волной трафика.
- **Predictive Auto-Scaling (Прогнозное масштабирование):**
  - Анализирует исторические суточные паттерны: утренний пик в 09:00, пятничный вечер в 19:00.
  - Машинное обучение или полиномиальная экстраполяция тренда прогнозирует скачок нагрузки за 15 минут до его начала.
  - Кластер Kubernetes **заранее прогревает ноды и поды**, встречая волну трафика на 100% готовых мощностях!

## Решение по шагам

1. Создайте модель экстраполяции тренда нагрузки.
2. Рассчитайте прогнозный пик трафика на распродажу.
3. Вычислите необходимое число подов с запасом безопасности Headroom 30%.
4. Верифицируйте упреждающее масштабирование.

## Код решения

**`predictive_capacity_planning_test.go`**

```go
package main

import (
	"fmt"
	"math"
	"testing"
)

type CapacityPlanner struct {
	podRPSCapacity int
	headroomRatio  float64
}

func (p *CapacityPlanner) PredictRequiredReplicas(baselineRPS float64, growthMultiplier float64) int {
	predictedPeakRPS := baselineRPS * growthMultiplier
	// Добавляем буфер безопасности (Headroom 30%) на случай аномалий
	safeTargetRPS := predictedPeakRPS * (1.0 + p.headroomRatio)
	replicas := math.Ceil(safeTargetRPS / float64(p.podRPSCapacity))
	return int(replicas)
}

func TestPredictiveCapacityPlanning(t *testing.T) {
	planner := &CapacityPlanner{
		podRPSCapacity: 500, // 1 под держит 500 RPS
		headroomRatio:  0.30, // 30% запас мощности
	}

	baselineRPS := 2000.0       // штатная нагрузка в четверг
	blackFridayGrowth := 3.5    // прогнозный рост в 3.5 раза в Черную Пятницу

	requiredPods := planner.PredictRequiredReplicas(baselineRPS, blackFridayGrowth)

	// safeTargetRPS = 2000 * 3.5 * 1.3 = 9100 RPS -> 9100 / 500 = 18.2 -> 19 подов
	if requiredPods != 19 {
		t.Fatalf("Некорректный расчет подов: %d (ожидалось 19)", requiredPods)
	}

	fmt.Println("Прогнозное планирование емкости (Predictive Capacity Planning) подтверждено:")
	fmt.Printf("  • Базовый трафик: %.0f RPS -> Прогноз пика: %.0f RPS\n", baselineRPS, baselineRPS*blackFridayGrowth)
	fmt.Printf("  • Запланировано реплик с запасом 30%% Headroom: %d подов\n", requiredPods)
	fmt.Println("  • Кластер прогрет заранее до начала распродажи без риска отказа сервиса")
}
```

ℹ️ Упреждающий расчет необходимого количества реплик на основе тренда и коэффициента Headroom

## Под капотом

В AWS и Kubernetes для предиктивного скейлинга используют AWS Auto Scaling Predictive Scaling или оператор KEDA с интеграцией Prometheus PromQL: модель Holt-Winters (`holt_winters(rate(http_requests_total[1h]), 0.2, 0.1)`) прогнозирует значения временного ряда на следующий час.

## Подводные камни

Держать коэффициент запаса Headroom равным 0%: любой непредвиденный скачок трафика (упоминание у популярного блогера) обрушит систему до того, как сработает дополнительное масштабирование. В продакшене Headroom держат на уровне 20–30%.

## На собеседовании

**Вопрос с собеседования:** «Что такое Overprovisioning в Kubernetes и зачем в кластере держат пустые поды с низким приоритетом (Pause Pods)?»
**Ответ:** Выделение новой виртуальной машины в облаке занимает 2–3 минуты. Чтобы поды приложения поднимались мгновенно за 2 секунды, в кластере запускают пустые "поды-заглушки" (Pause Pods) с минимальным PriorityClass. При всплеске нагрузки Kubelet мгновенно вытесняет (evicts) заглушки, освобождая готовые ядра CPU для боевых подов.
