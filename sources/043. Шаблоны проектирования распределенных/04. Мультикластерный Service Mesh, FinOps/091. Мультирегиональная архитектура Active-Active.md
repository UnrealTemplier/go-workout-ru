# Мультирегиональная архитектура Active-Active: двунаправленная репликация и разрешение конфликтов LWW

## Условие

Реализуй **Multi-Region Active-Active**: bidirectional replication, conflict resolution (LWW / CRDT), latency-based routing. Пользователь в EU пишет в EU, пользователь в US пишет в US. Синхронизация данных с разрешением конфликтов.

### Исходная формулировка

Реализуй **Event Sourcing + Snapshotting**: 1M events per aggregate → replay takes 10s. Snapshot every 100 events: `Snapshot{Version, State}`. Replay: load latest snapshot + events after version. Compaction: archive old events, keep recent + snapshots.

## Теория

Сложности распределенной архитектуры Active-Active:
- В отличие от Active-Passive, оба региона одновременно принимают и чтение, и запись:
  - Пользователь в Берлине меняет имя профиля на «Алекс» в 12:00:00.100.
  - В ту же миллисекунду служба поддержки в Нью-Йорке меняет имя на «Александр» в 12:00:00.150.
- **Стратегии разрешения конфликтов (Conflict Resolution):**
  1. **Last-Write-Wins (LWW):** побеждает запись с наибольшим монотонным физическим или гибридным логическим временем (HLC / Hybrid Logical Clock).
  2. **CRDT (Conflict-free Replicated Data Types):** состояние объединяется математически без потерь (например, объединение множеств прав доступа).

## Решение по шагам

1. Создайте структуру записи с меткой времени Hybrid Logical Clock.
2. Реализуйте функцию разрешения конфликтов по стратегии Last-Write-Wins.
3. Смоделируйте встречное обновление одной записи в EU и US регионах.
4. Верифицируйте детерминированную сходимость данных.

## Код решения

**`multi_region_active_active_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type RegionRecord struct {
	Key       string
	Value     string
	Timestamp time.Time
	RegionID  string
}

func ResolveConflictLWW(recA, recB RegionRecord) RegionRecord {
	// Last-Write-Wins (LWW): побеждает более свежая временная метка
	if recA.Timestamp.After(recB.Timestamp) {
		return recA
	} else if recB.Timestamp.After(recA.Timestamp) {
		return recB
	}
	// При абсолютно одинаковом времени — детерминированный тай-брейкер по имени региона
	if recA.RegionID > recB.RegionID {
		return recA
	}
	return recB
}

func TestMultiRegionActiveActive(t *testing.T) {
	t1 := time.Date(2026, 9, 4, 12, 0, 0, 100000000, time.UTC)
	t2 := time.Date(2026, 9, 4, 12, 0, 0, 200000000, time.UTC) // на 100 мс позже!

	recordEU := RegionRecord{Key: "user:42:name", Value: "Алекс", Timestamp: t1, RegionID: "eu-central-1"}
	recordUS := RegionRecord{Key: "user:42:name", Value: "Александр", Timestamp: t2, RegionID: "us-east-1"}

	resolved := ResolveConflictLWW(recordEU, recordUS)

	if resolved.Value != "Александр" || resolved.RegionID != "us-east-1" {
		t.Fatalf("Стратегия LWW должна была выбрать запись из US: %+v", resolved)
	}

	fmt.Println("Мультирегиональная архитектура Active-Active подтверждена:")
	fmt.Printf("  • Запись EU (t1): %s\n", recordEU.Value)
	fmt.Printf("  • Запись US (t2): %s (Победитель LWW)\n", recordUS.Value)
	fmt.Printf("  • Разрешенный конфликт: %s (Регион: %s)\n", resolved.Value, resolved.RegionID)
	fmt.Println("  • Двунаправленная репликация сошлась к единому значению без дедлоков")
}
```

## Под капотом

Обычные системные часы серверов подвержены рассинхронизации (Clock Drift / NTP Jitter). В распределенных базах данных (Google Spanner, CockroachDB) вместо обычного NTP используют TrueTime API с атомными часами и GPS или алгоритм Hybrid Logical Clocks (HLC), сочетающий физическое время с логическими счетчиками Лампорта.

## Подводные камни

Использовать инкрементные целочисленные ID (`SERIAL / AUTO_INCREMENT`) в Active-Active кластере: оба региона сгенерируют ID = 1 для разных заказов, вызвав неустранимую коллизию первичных ключей. Используют строго распределенные UUIDv7 или Snowflake ID.

## На собеседовании

**Вопрос с собеседования:** «Почему Last-Write-Wins (LWW) считается опасной стратегией для финансовых проводок?»
**Ответ:** Потому что LWW молчаливо затирает одну из записей («победитель забирает все»). Если два пользователя одновременно перевели деньги, запись одного из них будет безвозвратно уничтожена. Для денег применяют строго аддитивные счетчики CRDT (PN-Counter) или распределенный двухфазный коммит 2PC.
