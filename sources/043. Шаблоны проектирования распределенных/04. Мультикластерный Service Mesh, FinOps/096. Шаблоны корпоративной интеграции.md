# Шаблоны корпоративной интеграции (Enterprise Integration Patterns / EIP): Content-Based Router и Splitter/Aggregator

## Условие

Реализуй **Enterprise Integration Patterns (EIP)**: Content-Based Router (маршрутизация по телу сообщения), Message Filter, Splitter (разбиение батча на сообщения), Aggregator (сборка ответов), Recipient List.

### Исходная формулировка

Реализуй **Data Mesh**: domain-oriented data ownership. `User Domain` owns `user data`, publishes `user events`. `Order Domain` owns `order data`. `Analytics Domain` consumes events, builds datasets. Self-serve data platform: discover, access, quality, governance.

## Теория

Канонические паттерны корпоративной интеграции (Грегор Хоп, Бобби Вульф — EIP):
1. **Content-Based Router (Маршрутизатор по содержимому):**
   - Анализирует полезную нагрузку сообщения: если `currency == "RUB"` \(\implies\) в очередь `rub-payments`, если `currency == "USD"` \(\implies\) в `swift-payments`.
2. **Splitter (Разделитель):**
   - Получает оптовый заказ на 100 позиций `BulkOrder` и разбивает его на 100 одиночных сообщений `OrderItemCommand` для параллельной обработки.
3. **Aggregator (Сборщик):**
   - Дожидается обработки всех 100 позиций, объединяет результаты и публикует итоговый `OrderProcessedEvent`.

## Решение по шагам

1. Создайте модель сообщения с заголовками и телом.
2. Реализуйте Content-Based Router по типу валюты.
3. Реализуйте Splitter пакетного заказа.
4. Верифицируйте корректность маршрутизации и разделения.

## Код решения

**`enterprise_integration_patterns_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type IntegrationPaymentMessage struct {
	PaymentID string
	Currency  string
	Amount    float64
}

// 1. Content-Based Router
func RoutePaymentByCurrency(msg IntegrationPaymentMessage) string {
	switch msg.Currency {
	case "RUB":
		return "queue.payments.mir_spb"
	case "USD", "EUR":
		return "queue.payments.swift_crossborder"
	case "BTC", "ETH":
		return "queue.payments.crypto_custody"
	default:
		return "queue.payments.manual_review"
	}
}

// 2. Splitter
func SplitOrderItems(orderID string, items []string) []string {
	var individualMessages []string
	for _, it := range items {
		individualMessages = append(individualMessages, fmt.Sprintf("Order: %s | Item: %s", orderID, it))
	}
	return individualMessages
}

func TestEnterpriseIntegrationPatterns(t *testing.T) {
	// Проверка маршрутизатора
	rubQueue := RoutePaymentByCurrency(IntegrationPaymentMessage{PaymentID: "p-1", Currency: "RUB", Amount: 1500})
	usdQueue := RoutePaymentByCurrency(IntegrationPaymentMessage{PaymentID: "p-2", Currency: "USD", Amount: 50})

	if rubQueue != "queue.payments.mir_spb" || usdQueue != "queue.payments.swift_crossborder" {
		t.Fatalf("Сбой Content-Based маршрутизации: %s, %s", rubQueue, usdQueue)
	}

	// Проверка разделителя (Splitter)
	itemsBatch := []string{"Клавиатура", "Мышь", "Монитор"}
	splitResults := SplitOrderItems("ord-bulk-500", itemsBatch)

	if len(splitResults) != 3 {
		t.Fatalf("Splitter обязан разделить батч на 3 сообщения: %d", len(splitResults))
	}

	fmt.Println("Шаблоны корпоративной интеграции (Enterprise Integration Patterns) подтверждены:")
	fmt.Printf("  • Маршрут RUB: %s\n", rubQueue)
	fmt.Printf("  • Маршрут USD: %s\n", usdQueue)
	fmt.Printf("  • Splitter разбил батч на %d независимых сообщений: %v\n", len(splitResults), splitResults)
}
```

## Под капотом

В распределенных брокерах (Apache Camel / Kafka Streams) Splitter обогащает каждое сообщение метаданными: `SequenceNumber = 1`, `SequenceSize = 3`, `CorrelationID = ord-bulk-500`. Паттерн Aggregator использует эти метаданные, чтобы понять, когда все дочерние фрагменты батча собраны.

## Подводные камни

Потеря части фрагментов в Aggregator: если 1 из 100 сообщений потерялось, агрегатор может зависнуть в ожидании. В агрегаторы обязательно закладывают таймаут (Completion Timeout), по истечении которого батч обрабатывается как частично завершенный.

## На собеседовании

**Вопрос с собеседования:** «Что такое паттерн Wire Tap в корпоративной интеграции?»
**Ответ:** Это паттерн перехвата сообщений (ответвитель): брокер копирует поток сообщений в дополнительный канал (например для аудита или аналитики) абсолютно прозрачно, не влияя на основной поток между продюсером и консьюмером.
