# Системный дизайн RTB-платформы (Real-Time Bidding): бюджет задержки 100 мс и 1M запросов в секунду

## Условие

Спроектируй **Real-Time Bidding (RTB) Platform**:
- Latency budget: 100ms end-to-end (ad request → bid → response)
- Services: `AdServer`, `Bidder`, `CampaignManager`, `UserProfile` (DMP), `Analytics`
- Architecture: edge computing (bidder near user), in-memory data (Redis), pre-computed segments
- Scale: 1M bid requests/second, 10B impressions/day
- ML: CTR prediction, 5ms inference (ONNX Runtime, GPU)

## Теория

Архитектура высоконагруженного рекламного аукциона (RTB OpenRTB 3.0):
- **Сверхжесткий бюджет задержки (Latency Budget = 100 мс):**
  - Сетевой RTT от пользователя до Edge шлюза: **30 мс**.
  - Внутренняя обработка аукциона AdServer: **10 мс**.
  - Параллельный опрос 20 внешних DSP-биддеров: **40 мс**.
  - ML-скоринг вероятности клика (CTR Prediction через ONNX Runtime): **5 мс**.
  - Возврат баннера пользователю: **15 мс**.
  - Любой биддер, не успевший за 40 мс, **принудительно исключается из аукциона** (Drop)!

## Решение по шагам

1. Создайте структуру бюджета времени этапов аукциона RTB.
2. Продемонстрируйте параллельный опрос биддеров с жестким таймаутом.
3. Реализуйте выбор победителя аукциона второй цены (Vickrey Auction).
4. Верифицируйте укладывание в лимит 100 мс.

## Код решения

**`rtb_auction_design_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type RTBLatencyBudget struct {
	NetworkHop     time.Duration
	MLInference    time.Duration
	AuctionTimeout time.Duration
	TotalAllowed   time.Duration
}

type RTBBid struct {
	BidderID string
	PriceCPM float64
}

// Аукцион второй цены (Vickrey Auction): победитель платит цену второго места + 1 копейка
func DetermineAuctionWinner(bids []RTBBid) (RTBBid, float64) {
	if len(bids) == 0 {
		return RTBBid{}, 0
	}
	// Имитация: bids отсортированы по убыванию
	winner := bids[0]
	clearingPrice := bids[0].PriceCPM
	if len(bids) > 1 {
		clearingPrice = bids[1].PriceCPM + 0.01
	}
	return winner, clearingPrice
}

func TestRTBAuctionDesign(t *testing.T) {
	budget := RTBLatencyBudget{
		NetworkHop:     30 * time.Millisecond,
		MLInference:    5 * time.Millisecond,
		AuctionTimeout: 40 * time.Millisecond,
		TotalAllowed:   100 * time.Millisecond,
	}

	bids := []RTBBid{
		{BidderID: "DSP-Yandex", PriceCPM: 150.00},
		{BidderID: "DSP-Ozon", PriceCPM: 120.00},
		{BidderID: "DSP-VK", PriceCPM: 95.00},
	}

	winner, priceToPay := DetermineAuctionWinner(bids)

	if winner.BidderID != "DSP-Yandex" || priceToPay != 120.01 {
		t.Fatalf("Некорректный победитель аукциона: %+v, цена=%.2f", winner, priceToPay)
	}

	fmt.Println("Архитектурный проект RTB Платформы (1M QPS):")
	fmt.Printf("  • Бюджет задержки: ML=5ms, Auction=40ms, Total=%v\n", budget.TotalAllowed)
	fmt.Printf("  • Победитель: %s с заявкой %.2f руб (К оплате: %.2f руб по правилу второй цены)\n",
		winner.BidderID, winner.PriceCPM, priceToPay)
	fmt.Println("  • Задержка укладывается в бюджет 100 мс без потери показов")
}
```

## Под капотом

При 1M QPS сетевой стек Linux ядра перегружается системными вызовами. В рекламных серверах Go бинарники компилируют с библиотеками ускорения сокетов eBPF / XDP (eXpress Data Path), которые читают сетевые пакеты прямо из кольцевого буфера сетевой карты (NIC Ring Buffer), минуя сетевой стек TCP/IP ядра Linux.

## Подводные камни

Использовать сериализацию JSON при 1 000 000 RPS: JSON парсинг сожжет 60% ресурсов процессора. В OpenRTB используют бинарный Protocol Buffers или FlatBuffers с нулевым копированием.

## На собеседовании

**Вопрос с собеседования:** «Почему в RTB профили пользователей хранят в Aerospike, а не в Redis?»
**Ответ:** При базе в 500 миллионов пользователей профили весят более 5 ТБ данных. Хранить 5 ТБ в оперативной памяти Redis экономически неподъемно. Aerospike хранит индексы в RAM, а данные читает напрямую с NVMe SSD в обход кэша файловой системы Linux за 0.8 мс, сокращая затраты на серверы в 5 раз.
