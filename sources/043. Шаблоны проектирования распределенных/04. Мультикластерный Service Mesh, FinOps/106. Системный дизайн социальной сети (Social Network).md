# Системный дизайн социальной сети (Social Network): гибридная лента новостей Fan-Out on Write и Fan-Out on Read

## Условие

Спроектируй **Social Network** (Twitter-like):
- Services: `User`, `Tweet`, `Timeline`, `Search`, `Notification`, `Media`
- `Timeline`: fan-out on write (push) for celebrities, fan-out on read (pull) for normal users. Hybrid approach.
- `Search`: inverted index (Elasticsearch), real-time indexing (< 1s)
- `Media`: image/video processing pipeline, CDN, adaptive bitrate
- Scale: 500M users, 100M tweets/day, 1M timeline requests/second

## Теория

Гибридная архитектура генерации ленты новостей (Twitter / VK Newsfeed):
1. **Fan-Out on Write (Push-модель):**
   - Когда обычный пользователь с 200 подписчиками публикует пост, воркер раскладывает ID поста в персональные ленты Redis всех 200 друзей.
   - Чтение ленты моментально: `LRANGE timeline:user_id 0 20`.
2. **Проблема знаменитостей (Celebrity Problem):**
   - Если у Илона Маска 150 миллионов подписчиков, Fan-Out on Write потребует 150 000 000 вставок в Redis на каждый твит, парализуя кластер!
3. **Гибридный подход (Hybrid Fan-Out):**
   - Для обычных пользователей (\(< 20\,000\) подписчиков) используется **Push**.
   - Для знаменитостей (\(> 20\,000\) подписчиков) посты **не раскладываются**.
   - При открытии ленты клиентом сервис склеивает (Merge) кэшированную ленту пользователя с последними постами знаменитостей на лету за 5 мс!

## Решение по шагам

1. Создайте модель пользователя с порогом знаменитости.
2. Реализуйте алгоритм гибридного формирования ленты.
3. Продемонстрируйте мгновенную публикацию поста селебрити без тяжелого Fan-Out.
4. Верифицируйте корректность сборки ленты у подписчика.

## Код решения

**`social_network_timeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SocialPost struct {
	AuthorID string
	Text     string
}

type HybridTimelineEngine struct {
	celebrityPosts map[string][]SocialPost // author -> posts
	userHomeFeeds  map[string][]SocialPost // user -> timeline
}

func (e *HybridTimelineEngine) PublishPost(authorID string, followersCount int, text string) string {
	post := SocialPost{AuthorID: authorID, Text: text}

	// Если автор — селебрити (> 20 000 фолловеров), Fan-Out НЕ ДЕЛАЕТСЯ!
	if followersCount > 20000 {
		e.celebrityPosts[authorID] = append(e.celebrityPosts[authorID], post)
		return "STORED_IN_CELEBRITY_BUCKET_NO_FANOUT"
	}

	// Обычный пользователь: Push во все ленты друзей
	return "FAN_OUT_ON_WRITE_PUSHED"
}

func (e *HybridTimelineEngine) ReadUserFeed(userID string, followedCelebrities []string) []SocialPost {
	var feed []SocialPost
	// 1. Посты обычных друзей из Redis
	feed = append(feed, e.userHomeFeeds[userID]...)

	// 2. Подмешивание постов знаменитостей на лету
	for _, cel := range followedCelebrities {
		feed = append(feed, e.celebrityPosts[cel]...)
	}
	return feed
}

func TestSocialNetworkTimeline(t *testing.T) {
	engine := &HybridTimelineEngine{
		celebrityPosts: make(map[string][]SocialPost),
		userHomeFeeds:  make(map[string][]SocialPost),
	}

	// Публикация от знаменитости с 50 000 000 подписчиков
	strategy := engine.PublishPost("elon_musk", 50000000, "Go 1.24 is blazing fast!")
	if strategy != "STORED_IN_CELEBRITY_BUCKET_NO_FANOUT" {
		t.Fatal("Для селебрити должен сработать Pull-подход")
	}

	// Пользователь читает ленту
	feed := engine.ReadUserFeed("user_alex", []string{"elon_musk"})
	if len(feed) != 1 || feed[0].AuthorID != "elon_musk" {
		t.Fatalf("Сбой сборки гибридной ленты: %+v", feed)
	}

	fmt.Println("Архитектурный проект Social Network (Hybrid Timeline) подтвержден:")
	fmt.Printf("  • Стратегия публикации: %s\n", strategy)
	fmt.Printf("  • Лента пользователя:   Автор=%s, Текст=%q\n", feed[0].AuthorID, feed[0].Text)
	fmt.Println("  • Гибридный подход ликвидировал проблему Celebrity Fan-Out")
}
```

ℹ️ Гибридная модель генерации ленты новостей (Push для обычных пользователей и Pull для селебрити)

## Под капотом

В Redis персональные ленты пользователей хранятся в структурах Sorted Set (`ZADD timeline:user_id timestamp post_id`), ограниченных длиной `ZREMRANGEBYRANK timeline:user_id 0 -800`. Пользователь редко листает ленту глубже 800 постов, что жестко ограничивает потребление оперативной памяти.

## Подводные камни

Хранить полный текст поста в персональной ленте каждого друга: дублирование текста на миллионы пользователей раздует базу до петабайтов. В лентах хранят **строго 64-битные `post_id`**, а текст подтягивается батчем из кэша постов (Cache Hydration).

## На собеседовании

**Вопрос с собеседования:** «Как социальная сеть генерирует ID постов, если монотонный автоинкремент базы данных не масштабируется?»
**Ответ:** Используют алгоритм **Twitter Snowflake**: 64-битный ID состоит из 41 бита времени миллисекунд (хватит на 69 лет), 10 бит ID дата-центра/машины и 12 бит счетчика последовательности. Посты можно сортировать по ID хронологически без обращения к полю `created_at`.
