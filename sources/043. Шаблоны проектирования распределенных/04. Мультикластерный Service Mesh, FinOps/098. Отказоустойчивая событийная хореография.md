# Отказоустойчивая событийная хореография: повторное воспроизведение событий и обнаружение зависших саг

## Условие

Реализуй **Resilient Microservices Choreography**: event-driven choreography with dead-letter topics, replay capability, distributed timeout detection. Сага `OrderPlaced` → `PaymentProcessed` → `InventoryReserved`. Если `InventoryReserved` не пришел за 30s → timeout watcher отменяет сагу.

### Исходная формулировка

**Readiness/Liveness Probes**: Настройте health checks для корректного traffic routing и auto-restart при hang.

## Теория

Архитектура тайм-аут вотчеров (Distributed Timeout Watcher in Saga):
- Главная слабость чистой хореографии — **зависшие сценарии**:
  - `OrderCreated` отправлен, деньги списаны, но сервис склада упал и не ответил ни успехом, ни ошибкой.
  - Без оркестратора некому зафиксировать факт отсутствия ответа!
- **Паттерн Distributed Timeout Watcher:**
  1. Сервис заказов при старте саги сохраняет тайм-аут: `deadline = time.Now() + 30*time.Second`.
  2. Фоновый воркер (Timeout Watcher) непрерывно опрашивает подвисшие саги со статусом `IN_PROGRESS`.
  3. Если дедлайн истек, а финальное событие не получено \(\implies\) воркер генерирует событие `SagaTimeoutDetected` и запускает компенсирующие транзакции возврата средств!

## Решение по шагам

1. Создайте модель саги заказа с полем дедлайна.
2. Реализуйте сканер зависших процессов `TimeoutWatcher`.
3. Смоделируйте истечение 30 секунд ожидания ответа склада.
4. Верифицируйте запуск автоматической компенсации.

## Код решения

**`saga_timeout_watcher_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type ActiveSagaRecord struct {
	SagaID    string
	Status    string // "IN_PROGRESS", "COMPLETED", "TIMED_OUT_COMPENSATED"
	Deadline  time.Time
}

type DistributedTimeoutWatcher struct {
	sagas map[string]*ActiveSagaRecord
}

func (w *DistributedTimeoutWatcher) ScanAndCompensateTimeouts(now time.Time) []string {
	var timedOutSagas []string
	for _, s := range w.sagas {
		if s.Status == "IN_PROGRESS" && now.After(s.Deadline) {
			s.Status = "TIMED_OUT_COMPENSATED"
			timedOutSagas = append(timedOutSagas, s.SagaID)
		}
	}
	return timedOutSagas
}

func TestSagaTimeoutWatcher(t *testing.T) {
	now := time.Now()

	watcher := &DistributedTimeoutWatcher{
		sagas: map[string]*ActiveSagaRecord{
			// Нормальная сага: дедлайн через 20 секунд
			"saga-active-1": {SagaID: "saga-active-1", Status: "IN_PROGRESS", Deadline: now.Add(20 * time.Second)},
			// Зависшая сага: склад молчит уже 45 секунд (дедлайн был 15 сек назад)
			"saga-stuck-99": {SagaID: "saga-stuck-99", Status: "IN_PROGRESS", Deadline: now.Add(-15 * time.Second)},
		},
	}

	compensated := watcher.ScanAndCompensateTimeouts(now)

	if len(compensated) != 1 || compensated[0] != "saga-stuck-99" {
		t.Fatalf("Ожидался откат зависшей саги: %v", compensated)
	}

	if watcher.sagas["saga-stuck-99"].Status != "TIMED_OUT_COMPENSATED" {
		t.Fatal("Статус саги обязан смениться на TIMED_OUT_COMPENSATED")
	}

	fmt.Println("Отказоустойчивая хореография (Saga Timeout Watcher) подтверждена:")
	fmt.Printf("  • Обнаружена зависшая сага: %v\n", compensated)
	fmt.Printf("  • Статус переведен в: %s\n", watcher.sagas["saga-stuck-99"].Status)
	fmt.Println("  • Запущен компенсирующий откат списания денег, зависание заказа предотвращено")
}
```

## Под капотом

В распределенных брокерах тайм-ауты часто реализуют через Delayed Message Exchange в RabbitMQ или Kafka с топиками задержки (Scheduled Topics): сообщение с таймером в 30 секунд попадает в очередь отмены, если за это время не пришло подтверждающее событие успеха.

## Подводные камни

Выполнять компенсацию без проверки идемпотентности: если ответ от склада пришел ровно в ту же миллисекунду, когда сработал тайм-аут, сага может одновременно закоммитить и компенсировать заказ. Проверка статуса саги обязана быть строго атомарной через транзакцию БД.

## На собеседовании

**Вопрос с собеседования:** «Что такое Semantic Lock в распределенных сагах?»
**Ответ:** Это флаг в агрегате заказа `is_pending_saga = true`. Пока сага выполняется, заказ нельзя отменить вручную пользователю или отправить на склад. Семантический замок защищает бизнес-состояние от неконсистентных изменений до завершения всех шагов саги.
