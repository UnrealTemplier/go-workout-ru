# Двухуровневое распределенное кэширование (Two-Level Cache): L1 в локальной памяти и L2 в Redis с инвалидацией

## Условие

Реализуй **Distributed Cache Architecture**: two-level cache (L1 in-memory, L2 Redis), cache coherence, stampede protection. L1 hits in < 100μs, L2 hits in < 2ms, DB fallback in < 50ms. Pub/Sub for L1 invalidation across instances.

### Исходная формулировка

**Горизонтальное шардирование на уровне приложения**: Представьте, что объем данных превышает возможности одного сервера СУБД. Напишите в Go абстракцию над базой данных. На основе хэша от UUID пользователя (например, алгоритм MurmurHash или простой остаток от деления хэша на количество баз) роутер запросов в Go должен автоматически направлять запросы на запись и чтение к одному из трех физически независимых серверов PostgreSQL.

## Теория

Иерархия двухуровневого кэширования (L1 In-Memory + L2 Redis):
- Даже самый быстрый сетевой Redis требует 0.5–2 мс на сетевой TCP round-trip.
- При 100 000 RPS походы в Redis начинают нагружать сетевую карту.
- **Архитектура L1/L2:**
  1. **L1 Cache (Локальная память Go):** `sync.Map` или Ristretto/ccache. Время отклика **< 100 наносекунд** (в 10 000 раз быстрее Redis!).
  2. **L2 Cache (Кластер Redis):** общее распределенное хранилище, время отклика 1–2 мс.
  3. **Синхронизация через Redis Pub/Sub:**
     - Когда экземпляр А обновляет товар в базе данных, он публикует сообщение в канал `cache:invalidate:item_42`.
     - Все остальные 50 подов слушают канал и мгновенно сбрасывают свои локальные кэши L1!

## Решение по шагам

1. Создайте структуру двухуровневого кэша `TwoLevelCache`.
2. Смоделируйте попадание в локальный кэш L1.
3. Продемонстрируйте инвалидацию L1 через шину сообщений.
4. Верифицируйте подгрузку свежего значения из L2/DB.

## Код решения

**`two_level_cache_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type TwoLevelCache struct {
	mu      sync.RWMutex
	l1Local map[string]string // RAM приложения
	l2Redis map[string]string // Внешний Redis
}

func (c *TwoLevelCache) Get(key string) (string, string) {
	c.mu.RLock()
	// 1. Проверка L1
	if val, found := c.l1Local[key]; found {
		c.mu.RUnlock()
		return val, "HIT_L1_MEMORY"
	}
	c.mu.RUnlock()

	// 2. Проверка L2 Redis
	c.mu.Lock()
	defer c.mu.Unlock()

	if val, found := c.l2Redis[key]; found {
		c.l1Local[key] = val // Прогрев L1
		return val, "HIT_L2_REDIS"
	}

	return "", "MISS_DB"
}

func (c *TwoLevelCache) InvalidateL1ViaPubSub(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	delete(c.l1Local, key)
}

func TestTwoLevelCache(t *testing.T) {
	cache := &TwoLevelCache{
		l1Local: make(map[string]string),
		l2Redis: map[string]string{"item-1": "Apple iPad Pro"},
	}

	// 1. Первый запрос: L1 промах -> берем из L2 Redis и прогреваем L1
	val1, source1 := cache.Get("item-1")
	if source1 != "HIT_L2_REDIS" || val1 != "Apple iPad Pro" {
		t.Fatalf("Ожидался HIT_L2: %s", source1)
	}

	// 2. Второй запрос: мгновенно из локальной памяти L1!
	val2, source2 := cache.Get("item-1")
	if source2 != "HIT_L1_MEMORY" || val2 != "Apple iPad Pro" {
		t.Fatalf("Ожидался HIT_L1: %s", source2)
	}

	// 3. Другой сервис изменил цену -> прилетает сигнал Pub/Sub инвалидации
	cache.InvalidateL1ViaPubSub("item-1")

	// L1 очищен, следующий запрос снова пойдет в L2
	_, source3 := cache.Get("item-1")
	if source3 != "HIT_L2_REDIS" {
		t.Fatalf("После инвалидации ожидался поход в L2: %s", source3)
	}

	fmt.Println("Двухуровневое кэширование (Two-Level Cache L1/L2) подтверждено:")
	fmt.Printf("  • Запрос 1: %s (Источник: %s)\n", val1, source1)
	fmt.Printf("  • Запрос 2: %s (Источник: %s, Наносекундный доступ!)\n", val2, source2)
	fmt.Printf("  • Запрос 3: После Pub/Sub инвалидации -> Источник: %s\n", source3)
}
```

ℹ️ Иерархическое кэширование L1 (память) и L2 (Redis) с оповещением через Pub/Sub

## Под капотом

В Redis 6+ встроен механизм **Client-Side Caching (Tracking)**: Redis сам отслеживает ключи, запрошенные клиентом, и при их изменении автоматически отправляет в Go сокет специальное управляющее сообщение инвалидации (Invalidation Push Message) без необходимости ручной настройки Pub/Sub каналов.

## Подводные камни

Хранить в L1 неограниченное число ключей: локальный кэш без алгоритма вытеснения (LRU / TinyLFU) приведет к исчерпанию оперативной памяти и падению процесса от Linux OOM Killer. В L1 всегда задают жесткий лимит `max_items: 10000`.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если в момент инвалидации L1 Pub/Sub сообщение потерялось из-за сетевого сбоя?»
**Ответ:** Задавать L1 кэшу короткий жесткий TTL (например 10–30 секунд). Даже если Pub/Sub сообщение потеряется, локальный узел продолжит отдавать устаревшие данные (Stale Data) максимум 30 секунд, после чего L1 гарантированно обновится из L2 Redis.
