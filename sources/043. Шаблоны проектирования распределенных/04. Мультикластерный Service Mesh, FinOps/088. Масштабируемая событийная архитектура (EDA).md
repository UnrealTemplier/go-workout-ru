# Масштабируемая событийная архитектура (EDA): реестр схем Confluent Schema Registry и Dead Letter Queue

## Условие

Реализуй **Event-Driven Architecture (EDA) at Scale**: Schema Registry (Avro/Protobuf), schema evolution (backward/forward compatibility), dead letter queue (DLQ) for poisoned messages, event replay capability.

### Исходная формулировка

**GitOps (ArgoCD/Flux)**: Настройте автоматический деплой при мердже в main branch через GitOps.

## Теория

Стандарты масштабируемой событийной шины (Kafka Enterprise EDA):
1. **Schema Registry (Контракты событий):**
   - Продюсер и консьюмер не передают JSON с дублирующимися строковыми именами полей.
   - Схемы регистрируются в Schema Registry в формате Protocol Buffers или Apache Avro.
   - Сообщение содержит только 5 байт заголовка (Magic Byte + Schema ID) и бинарную полезную нагрузку.
2. **Schema Evolution (Эволюция схем):**
   - Правило Backward Compatibility: новая версия схемы обязана уметь читать старые события из архива. Новые поля объявляются строго с дефолтными значениями.
3. **Dead Letter Queue (DLQ / Очередь ядовитых сообщений):**
   - Если сообщение повреждено и вызывает панику консьюмера (Poison Pill), после 3 неудачных попыток оно пересылается в топик `orders.DLQ`, не блокируя обработку всей партиции!

## Решение по шагам

1. Создайте модель реестра схем с контролем совместимости.
2. Реализуйте консьюмер с перехватом Poison Pill сообщений.
3. Перенаправьте поврежденное сообщение в Dead Letter Queue (DLQ).
4. Верифицируйте непрерывность обработки последующих сообщений.

## Код решения

**`eda_schema_registry_dlq_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type EventMessage struct {
	ID       string
	SchemaID int
	Payload  string
}

type EDAQueueConsumer struct {
	dlqTopic   []EventMessage
	processed  []string
	maxRetries int
}

func (c *EDAQueueConsumer) ConsumeMessage(msg EventMessage, handler func(EventMessage) error) {
	var lastErr error
	for attempt := 1; attempt <= c.maxRetries; attempt++ {
		lastErr = handler(msg)
		if lastErr == nil {
			c.processed = append(c.processed, msg.ID)
			return
		}
	}

	// Все ретраи исчерпаны -> Пересылка в Dead Letter Queue (DLQ)
	c.dlqTopic = append(c.dlqTopic, msg)
}

func TestEDASchemaRegistryDLQ(t *testing.T) {
	consumer := &EDAQueueConsumer{maxRetries: 2}

	goodMsg := EventMessage{ID: "msg-101", SchemaID: 1, Payload: "Valid payload"}
	poisonMsg := EventMessage{ID: "msg-poison-999", SchemaID: 1, Payload: "CORRUPTED_PAYLOAD"}

	handler := func(m EventMessage) error {
		if m.Payload == "CORRUPTED_PAYLOAD" {
			return errors.New("unmarshal error: corrupted schema payload")
		}
		return nil
	}

	// 1. Обработка ядовитого сообщения (Poison Pill)
	consumer.ConsumeMessage(poisonMsg, handler)

	if len(consumer.dlqTopic) != 1 || consumer.dlqTopic[0].ID != "msg-poison-999" {
		t.Fatal("Поврежденное сообщение обязано быть изолировано в DLQ")
	}

	// 2. Следующее валидное сообщение успешно обрабатывается без застревания очереди!
	consumer.ConsumeMessage(goodMsg, handler)

	if len(consumer.processed) != 1 || consumer.processed[0] != "msg-101" {
		t.Fatal("Валидное сообщение должно быть успешно обработано")
	}

	fmt.Println("Событийная архитектура (EDA Schema Registry & DLQ) подтверждена:")
	fmt.Printf("  • Ядовитое сообщение msg-poison-999 изолировано в DLQ (Ретраи исчерпаны)\n")
	fmt.Printf("  • Валидное сообщение msg-101 успешно обработано: %v\n", consumer.processed)
	fmt.Println("  • Очередь Kafka не заблокирована ядовитым сообщением")
}
```

ℹ️ Изоляция ядовитых сообщений в Dead Letter Queue (DLQ) без остановки конвейера Kafka

## Под капотом

В заголовке сообщения в топике DLQ консьюмер сохраняет диагностические метаданные: `x-original-topic`, `x-exception-message`, `x-exception-stacktrace`. Разработчики могут изучить причину сбоя в UI Kafka и после исправления бага вернуть сообщения из DLQ обратно в основной поток (DLQ Replay).

## Подводные камни

Бесконечно ретраить ядовитое сообщение в основном потоке: консьюмер зависнет на одном сообщении навсегда, смещение (Consumer Offset) перестанет двигаться, и задержка очереди (Consumer Lag) вырастет до миллионов сообщений.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие режима Full Compatibility от Backward Compatibility в Confluent Schema Registry?»
**Ответ:** 
- **Backward:** новые сервисы могут читать старые события.
- **Full:** новые сервисы могут читать старые события, а старые сервисы могут читать новые события. Это позволяет обновлять сервисы в любой произвольной последовательности без нарушения контрактов данных.
