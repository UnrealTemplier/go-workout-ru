# Системный дизайн масштабной IoT-платформы: 10M устройств, поток 1M сообщений в секунду и ClickHouse

## Условие

Спроектируй **IoT Platform**:
- 10M devices, each sends telemetry every 10 seconds
- Ingestion: MQTT broker → Kafka → stream processing (Flink/Go)
- Storage: time-series DB (TimescaleDB/InfluxDB) for raw data, aggregated in ClickHouse
- Real-time: anomaly detection, alerting, device commands
- Scale: 1M messages/second, retention 1 year raw, 5 years aggregated

## Теория

Инженерия потоковой обработки телеметрии масштаба 1M сообщений/сек:
- **Расчет входящего потока данных:**
  - \(10\,000\,000\text{ устройств} / 10\text{ секунд} = \mathbf{1\,000\,000\text{ сообщений в секунду}}\).
  - При среднем размере пакета 200 байт входящий сетевой трафик составляет **200 МБ/с (1.6 Гбит/с)**.
- **Трехслойная архитектура пайплайна:**
  1. `Ingestion Layer`: кластер EMQX брокеров (100 нод) принимает миллионы TCP MQTT соединений.
  2. `Buffering Layer`: Apache Kafka кластер (50 брокеров, 200 партиций) буферизирует поток.
  3. `Processing & Storage`: Go-воркеры считывают батчами по 10 000 событий и вставляют в ClickHouse.

## Решение по шагам

1. Создайте структуру расчета емкости и нагрузки IoT платформы.
2. Продемонстрируйте агрегацию телеметрических батчей.
3. Рассчитайте суточный объем дискового пространства.
4. Верифицируйте устойчивость конвейера.

## Код решения

**`iot_platform_scale_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type IoTCapacityEstimate struct {
	TotalDevices         int
	ReportIntervalSec    int
	MessageSizeBytes     int
	MessagesPerSecond    int
	DailyIngestDataGB    float64
}

func CalculateIoTEstimates() IoTCapacityEstimate {
	devices := 10000000
	interval := 10
	msgSize := 200

	mps := devices / interval
	dailyBytes := float64(mps) * float64(msgSize) * 86400
	dailyGB := dailyBytes / (1024 * 1024 * 1024)

	return IoTCapacityEstimate{
		TotalDevices:      devices,
		ReportIntervalSec: interval,
		MessageSizeBytes:  msgSize,
		MessagesPerSecond: mps,
		DailyIngestDataGB: dailyGB,
	}
}

func TestIoTPlatformScale(t *testing.T) {
	est := CalculateIoTEstimates()

	if est.MessagesPerSecond != 1000000 {
		t.Fatalf("Ожидался 1M сообщений в сек: %d", est.MessagesPerSecond)
	}

	fmt.Println("Архитектурный проект масштабной IoT-платформы (10M устройств):")
	fmt.Printf("  • Поток данных в секунду: %d сообщений/сек\n", est.MessagesPerSecond)
	fmt.Printf("  • Суточный объем сырых данных: %.1f ГБ/день (~%.2f ТБ/день)\n",
		est.DailyIngestDataGB, est.DailyIngestDataGB/1024.0)
	fmt.Println("  • ClickHouse колоночное сжатие zstd уменьшает хранение до 1.5 ТБ/день")
}
```

## Под капотом

При вставке 1M сообщений в секунду в ClickHouse одиночные запросы `INSERT INTO` категорически запрещены. Go-консьюмеры буферизируют сообщения в оперативной памяти и сбрасывают пачками по 50 000 строк каждые 2 секунды, обеспечивая максимальную скорость записи SSD.

## Подводные камни

Создавать отдельный топик Kafka на каждое IoT устройство: брокер Kafka упадет при попытке создать 10 000 000 топиков. Используют **один общий топик** `iot.telemetry.raw` со 128 партициями, а ключ сообщения `device_id` гарантирует порядок.

## На собеседовании

**Вопрос с собеседования:** «Как поддерживать миллионы открытых постоянных TCP соединений на брокерах MQTT?»
**Ответ:** Тюнинг ядра Linux: параметры `sysctl -w fs.file-max=2097152`, увеличение лимитов дескрипторов `ulimit -n 1048576`, оптимизация размера TCP буферов `net.ipv4.tcp_rmem = 4096 87380 4194304`, что позволяет одному серверу на базе Erlang (EMQX) держать до 1 000 000 одновременных WebSocket/MQTT подключений.
