## Теория

Архитектура промышленной платформы машинного обучения (MLOps на 1M predictions/sec):
1. **Двухуровневый Feature Store (Feast):**
   - **Offline Store (ClickHouse / S3):** терабайты исторических фичей для обучения моделей пачками.
   - **Online Store (Redis / Dragonfly):** актуальный снимок фичей пользователя (`user:age`, `user:last_purchases`) с задержкой чтения \(< 1\text{ мс}\) для онлайн-предсказаний.
2. **Model Serving (NVIDIA Triton Inference Server):**
   - Динамический батчинг (Dynamic Batching): склеивание входящих запросов за 2 мс в одну пачку для эффективного параллельного умножения матриц на тензорных ядрах GPU.
3. **Shadow Deployment (Теневой инференс):**
   - Новая версия модели `v2` получает копию реального трафика в фоновом режиме. Качество предсказаний сравнивается с `v1` без показа клиентам.

## Решение по шагам

1. Создайте архитектурную спецификацию MLOps платформы.
2. Продемонстрируйте разделение Online и Offline Feature Store.
3. Реализуйте симуляцию динамического батчинга в Inference Service.
4. Верифицируйте масштабируемость платформы до 1M предсказаний в секунду.

## Под капотом

В микросервисах инференса на Go клиент связывается с Triton по протоколу KServe v2 gRPC: полезная нагрузка передается в виде плоского бинарного массива тензоров без JSON-оверхеда, что позволяет делать 1 000 000 предсказаний в секунду с временем инференса < 5 мс.

## Подводные камни

Обучать модель на фичах, которые недоступны в момент реального онлайн-запроса (Data Leakage / Train-Serve Skew): модель показывает 99% точности на тестах, но полностью проваливается в продакшене. Feature Store гарантирует идентичность формул расчета фичей онлайн и офлайн.

## На собеседовании

**Вопрос с собеседования:** «Что такое Dynamic Batching в NVIDIA Triton и почему он кардинально снижает затраты на GPU?»
**Ответ:** Запуск инференса на GPU для одного одиночного запроса крайне неэффективен (задействовано 2% ядер). Triton буферизирует входящие запросы в течение короткого окна (например 2 мс), объединяет 64 запроса в один батч и отправляет его на GPU одной операцией, увеличивая пропускную способность сервера в 20–30 раз при сохранении SLA по задержке.
