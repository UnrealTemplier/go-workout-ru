# Динамическое распределение ресурсов в Multi-Tenant: подавление Noisy Neighbor через cgroups и лимиты

## Условие

Реализуй **Dynamic Multi-Tenant Resource Allocation**: dynamic CPU/memory limits per tenant, noisy neighbor suppression. Если tenant-A потребляет > 80% своих ресурсов — throttled, tenant-B продолжает работать на полной скорости.

### Исходная формулировка

**Resource Requests/Limits**: Правильно настройте CPU/memory requests и limits для предсказуемого scheduling и предотвращения OOM.

## Теория

Проблема шумного соседа (Noisy Neighbor Problem) в SaaS:
- Один гиперактивный клиент (Тенант А) запускает массовую выгрузку отчетов и забивает все 100% CPU сервера.
- Другие клиенты (Тенант Б и В) не могут войти в систему из-за 10-секундных зависаний.
- **Архитектура подавления Noisy Neighbor:**
  1. Каждый тенант получает виртуальный профиль квот: `Quota{MaxConcurrency: 10, MaxRPS: 100}`.
  2. Middleware отслеживает нагрузку по ключу `tenant_id`.
  3. Если Тенант А исчерпал свои 10 конкурентных слотов \(\implies\) его новые запросы троттлятся (Throttled HTTP 429).
  4. Тенанты Б и В продолжают получать ответы за 5 миллисекунд!

## Решение по шагам

1. Создайте семафоры конкурентности для каждого тенанта.
2. Смоделируйте исчерпание квоты тенантом А.
3. Докажите, что тенант Б обслуживается без задержек.
4. Верифицируйте изоляцию ресурсов.

## Код решения

**`noisy_neighbor_suppression_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"testing"
)

type TenantQuotaManager struct {
	mu           sync.Mutex
	activeSlots  map[string]int
	maxSlotsEach int
}

func (m *TenantQuotaManager) TryAcquireSlot(tenantID string) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	current := m.activeSlots[tenantID]
	if current >= m.maxSlotsEach {
		return fmt.Errorf("tenant %s exceeded concurrency quota (%d slots): THROTTLED",
			tenantID, m.maxSlotsEach)
	}

	m.activeSlots[tenantID]++
	return nil
}

func (m *TenantQuotaManager) ReleaseSlot(tenantID string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.activeSlots[tenantID]--
}

func TestNoisyNeighborSuppression(t *testing.T) {
	mgr := &TenantQuotaManager{
		activeSlots:  make(map[string]int),
		maxSlotsEach: 2, // Лимит 2 слота на организацию
	}

	// Тенант А занимает все свои 2 слота
	_ = mgr.TryAcquireSlot("tenant-noisy-A")
	_ = mgr.TryAcquireSlot("tenant-noisy-A")

	// 3-й запрос тенанта А должен быть жестко ограничен
	errThrottledA := mgr.TryAcquireSlot("tenant-noisy-A")
	if errThrottledA == nil {
		t.Fatal("Шумный тенант А обязан был получить отказ по квоте")
	}

	// При этом спокойный тенант Б свободно получает доступ!
	errOkB := mgr.TryAcquireSlot("tenant-quiet-B")
	if errOkB != nil {
		t.Fatalf("Спокойный тенант Б не должен страдать: %v", errOkB)
	}

	fmt.Println("Подавление шумного соседа (Noisy Neighbor Suppression) подтверждено:")
	fmt.Printf("  • Попытка Тенанта А сверх квоты: %v\n", errThrottledA)
	fmt.Printf("  • Запрос Тенанта Б: Успешно выделен слот (%v)\n", errOkB == nil)
	fmt.Println("  • Агрессивное поведение одного клиента не оказало влияния на соседей")
}
```

ℹ️ Динамическое ограничение конкурентных слотов тенантов для защиты от взаимного влияния

## Под капотом

В операционной системе Linux изоляция реализуется через **cgroups v2**: подсистема `cpu.weight` и `memory.high` позволяет плавно замедлять фоновые потоки шумного тенанта при превышении лимита, не убивая процесс аварийным сигналом SIGKILL.

## Подводные камни

Использовать глобальные мьютексы без шардирования для учета квот: при 100 000 RPS сам мьютекс счетчика квот станет бутылочным горлышком CPU Cache Coherence. Счетчики шардируют по хэшу `tenant_id`.

## На собеседовании

**Вопрос с собеседования:** «Что такое Fair Queuing (Справедливое распределение очередей) в обработке задач тенантов?»
**Ответ:** Это алгоритм (Weighted Fair Queuing / Round-Robin), при котором воркер берет по одному сообщению по очереди из очередей каждого тенанта. Если Тенант А насыпал в очередь 1 000 000 задач, а Тенант Б прислал 1 задачу, задача Тенанта Б выполнится немедленно, а не через 3 часа ожидания.
