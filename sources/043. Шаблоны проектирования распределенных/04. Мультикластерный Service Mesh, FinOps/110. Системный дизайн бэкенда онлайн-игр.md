# Системный дизайн бэкенда онлайн-игр (Gaming Backend): 10M игроков, Battle Royale и тикрейт 20Hz

## Условие

Спроектируй **Gaming Backend** (MMO/Fortnite-like):
- Services: `Matchmaking`, `GameServer`, `PlayerProfile`, `Leaderboard`, `Inventory`, `Social`
- `Matchmaking`: skill-based, latency-based, party support, battle royale 100 players
- `GameServer`: authoritative simulation, 20Hz tick rate, state reconciliation
- `Leaderboard`: global, regional, friends; real-time updates
- Scale: 10M concurrent players, 1M concurrent matches

## Теория

Архитектура игрового сервера реального времени (Authoritative Game Server):
1. **Авторитетный сервер (Authoritative Simulation):**
   - Клиентский код игры считается скомпрометированным (чит-программы, Wallhack).
   - Клиент шлет серверу **только нажатия клавиш (Player Inputs)**: `MoveForward`, `FireWeapon`.
   - Сервер сам физически симулирует мир (коллизии, баллистику пуль) с фиксированным тикрейтом (например 20Hz = 20 тиков в секунду / 50 мс на тик).
   - Игровой сервер рассылает клиентам дельту снапшота мира по UDP/WebTransport.
2. **Лидерборды (Global Leaderboard):**
   - Redis Sorted Sets (`ZADD leaderboards score player_id`) ранжируют миллионы игроков за \(O(\log N)\).

## Решение по шагам

1. Создайте цикл игрового тика с частотой 20Hz.
2. Реализуйте симуляцию обработки действий игроков на авторитетном сервере.
3. Продемонстрируйте обновление глобального лидерборда.
4. Верифицируйте соответствие временным рамкам игрового тика.

## Код решения

**`gaming_authoritative_server_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type GamePlayerInput struct {
	PlayerID string
	MoveX    float64
	MoveY    float64
}

type AuthoritativeGameEngine struct {
	currentTick int
	positions   map[string]float64
}

func (e *AuthoritativeGameEngine) ProcessServerTick(inputs []GamePlayerInput) time.Duration {
	start := time.Now()
	e.currentTick++

	// Авторитетный пересчет координат миром
	for _, inp := range inputs {
		e.positions[inp.PlayerID] += inp.MoveX
	}

	tickProcessingTime := time.Since(start)
	return tickProcessingTime
}

func TestGamingAuthoritativeServer(t *testing.T) {
	engine := &AuthoritativeGameEngine{positions: make(map[string]float64)}

	inputs := []GamePlayerInput{
		{PlayerID: "player-cyber-1", MoveX: 5.5, MoveY: 0},
		{PlayerID: "player-ninja-2", MoveX: -2.0, MoveY: 0},
	}

	// Тикрейт 20Hz -> бюджет одного тика равен 50 мс!
	duration := engine.ProcessServerTick(inputs)

	if duration > 50*time.Millisecond {
		t.Fatalf("Игровой тик превысил бюджет 50 мс: %v", duration)
	}

	fmt.Println("Архитектурный проект бэкенда онлайн-игр (Authoritative Game Server 20Hz):")
	fmt.Printf("  • Игровой тик #%d обработан за: %v (Бюджет: 50 мс для 20Hz)\n", engine.currentTick, duration)
	fmt.Printf("  • Новые авторитетные позиции игроков: %+v\n", engine.positions)
	fmt.Println("  • Серверная симуляция защищает матч от читов на изменение скорости и телепортации")
}
```

## Под капотом

Игровые сервера развертываются в Kubernetes через фреймворк **Agones**: он превращает поды в выделенные Dedicated Game Servers (DGS), блокируя их удаление во время активного матча и управляя жизненным циклом игровых сессий.

## Подводные камни

Использовать TCP протокол для передачи координат игроков в шутерах: потеря одного пакета в TCP блокирует чтение всего потока (Head-of-Line Blocking), вызывая ретрансмиты и задержки. Координаты передают строго по **UDP** без подтверждения доставки.

## На собеседовании

**Вопрос с собеседования:** «Что такое Client-Side Prediction и Server Reconciliation в онлайн-играх?»
**Ответ:** Чтобы игрок не чувствовал сетевую задержку 50 мс при нажатии клавиш, клиент немедленно двигает персонажа локально (Prediction). Когда с сервера приходит авторитетный снапшот мира, клиент плавно интерполирует расхождение между локальной и серверной позицией (Reconciliation).
