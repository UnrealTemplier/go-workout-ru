# Корпоративный мониторинг 4 золотых сигналов (Golden Signals): Latency, Traffic, Errors и Saturation

## Условие

Реализуй **Enterprise Observability**: Golden Signals (latency, traffic, errors, saturation), unified dashboard, SLO alert. `SLO`: 99.9% requests < 200ms, error rate < 0.1%. Alert on burn rate: 1h burn rate > 14.4 (burn 10% budget in 1h).

### Исходная формулировка

Реализуй **Event-Driven Architecture (EDA)**: все state changes — events. `Event Store` (Kafka/NATS) = source of truth. `Projections` = read models. `Process Managers` = orchestrate sagas. `Event Replayers` = rebuild state, debug, audit. No direct DB writes from handlers.

## Теория

Четыре золотых сигнала Google SRE (The Four Golden Signals):
1. **Latency (Задержка):** время ответа на запрос (раз раздельно для успешных и ошибочных ответов).
2. **Traffic (Трафик):** объем входящей нагрузки (RPS, сетевой трафик).
3. **Errors (Ошибки):** частота отказов (HTTP 5xx, паники рантайма).
4. **Saturation (Насыщение):** степень загрузки ресурсов (заполнение очередей, % использования CPU, пула коннектов к БД).
- **Alert on Error Budget Burn Rate:**
  - При SLA 99.9% у сервиса есть бюджет ошибок 0.1% в месяц.
  - Если за последний час скорость сгорания бюджета превышает коэффициент 14.4 \(\implies\) дежурный инженер получает Page-алерт немедленно!

## Решение по шагам

1. Создайте структуру сбора четырех золотых сигналов `GoldenSignalsReport`.
2. Реализуйте расчет скорости сгорания бюджета ошибок (Burn Rate).
3. Смоделируйте алерт при критической аварии.
4. Верифицируйте соответствие SLO.

## Код решения

**`golden_signals_slo_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type GoldenSignalsReport struct {
	P99Latency     time.Duration
	RPS            int
	ErrorRate      float64 // в процентах
	CPUSaturation  float64 // в процентах
}

func EvaluateSLOBurnRate(report GoldenSignalsReport) (bool, string) {
	// SLO: 99.9% requests < 200ms, ErrorRate < 0.1%
	if report.ErrorRate > 1.44 {
		// 14.4x Burn Rate: сожжет 10% месячного бюджета ошибок всего за 1 час!
		return true, fmt.Sprintf("CRITICAL PAGE: Error budget burn rate is 14.4x (Current Error Rate: %.2f%%)", report.ErrorRate)
	}
	if report.P99Latency > 200*time.Millisecond {
		return true, fmt.Sprintf("WARNING: P99 Latency %v violated SLO limit (200ms)", report.P99Latency)
	}
	return false, "SLO_HEALTHY"
}

func TestGoldenSignalsSLO(t *testing.T) {
	normalMetrics := GoldenSignalsReport{
		P99Latency:    45 * time.Millisecond,
		RPS:           1500,
		ErrorRate:     0.02,
		CPUSaturation: 38.5,
	}

	isAlert1, status1 := EvaluateSLOBurnRate(normalMetrics)
	if isAlert1 {
		t.Fatal("Штатные метрики не должны вызывать алерт")
	}

	criticalMetrics := GoldenSignalsReport{
		P99Latency:    350 * time.Millisecond,
		RPS:           2000,
		ErrorRate:     2.50, // 2.5% ошибок!
		CPUSaturation: 92.0,
	}

	isAlert2, status2 := EvaluateSLOBurnRate(criticalMetrics)
	if !isAlert2 {
		t.Fatal("Аварийные метрики обязаны поднять Critical Alert")
	}

	fmt.Println("Мониторинг 4 золотых сигналов (Four Golden Signals) подтвержден:")
	fmt.Printf("  • Норма:   %s\n", status1)
	fmt.Printf("  • Инцидент: %s\n", status2)
	fmt.Println("  • Контроль скорости сжигания Error Budget предотвращает исчерпание месячного SLA")
}
```

ℹ️ Расчет 4 золотых сигналов и вычисление скорости сжигания бюджета ошибок (Error Budget Burn Rate)

## Под капотом

В Prometheus для точного замера Latency используют гистограммы `prometheus.NewHistogramVec(prometheus.HistogramOpts{Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10}})`. На стороне Grafana квантиль P99 вычисляется функцией `histogram_quantile(0.99, sum(rate(http_duration_seconds_bucket[5m])) by (le))`.

## Подводные камни

Считать среднее арифметическое время ответа (Average Latency): если 999 запросов выполнились за 1 мс, а один завис на 60 секунд, среднее будет отличным (~60 мс), но один из клиентов потерпел катастрофический сбой. Задержку оценивают **строго по перцентилям P95, P99, P99.9**.

## На собеседовании

**Вопрос с собеседования:** «Почему алерты по Burn Rate лучше классических алертов 'Error Rate > 1%'?»
**Ответ:** Классический алерт сработает ночью на 2 запросах из 100 и разбудит дежурного (ложное срабатывание). Burn Rate сопоставляет процент ошибок с объемом реального трафика и оставшимся бюджетом SLO: он будит инженера только тогда, когда инцидент реально угрожает нарушить контракт доступности перед бизнесом.
