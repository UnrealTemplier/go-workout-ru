# Аутентификация через Sec-WebSocket-Protocol: передача JWT в заголовках и код 1008 Policy Violation

## Условие

Напиши **WebSocket с authentication**: при подключении клиент передаёт JWT в query param (`?token=...`) или в `Sec-WebSocket-Protocol`. Валидируй в `Upgrader.CheckOrigin` или отдельном middleware. Закрой с `1008 Policy Violation`, если токен невалиден.

## Теория

Передача JWT через субпротокол `Sec-WebSocket-Protocol`:
- Браузерный JavaScript `new WebSocket(url)` не позволяет задавать произвольные HTTP-заголовки (например `Authorization: Bearer ...`).
- Однако второй аргумент конструктора передает субпротоколы:
  `new WebSocket('wss://api.com/ws', ['access-token', userJWT])`.
- Сервер при рукопожатии:
  1. Извлекает заголовок `Sec-WebSocket-Protocol`.
  2. Находит токен, проверяет подпись HMAC/RSA.
  3. Если токен валиден: возвращает согласованный субпротокол в заголовке ответа.
  4. Если невалиден: отклоняет со статусом 401 или закрывает сокет с кодом `1008 Policy Violation`.

## Решение по шагам

1. Настройте парсинг токена из субпротокола.
2. Реализуйте валидацию секрета.
3. Смоделируйте отклонение с кодом `1008 Policy Violation`.
4. Протестируйте успешную авторизацию.

## Код решения

**`sec_websocket_auth_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/gorilla/websocket"
)

func parseTokenFromSubprotocols(r *http.Request) string {
	protocols := websocket.Subprotocols(r)
	for i, p := range protocols {
		if p == "access-token" && i+1 < len(protocols) {
			return protocols[i+1]
		}
	}
	return ""
}

func TestSecWebSocketProtocolAuth(t *testing.T) {
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		token := parseTokenFromSubprotocols(r)

		if token != "super_secret_jwt" {
			// Отклоняем неавторизованный запрос
			http.Error(w, "Неверный токен субпротокола", http.StatusUnauthorized)
			return
		}

		upgrader := websocket.Upgrader{
			Subprotocols: []string{"access-token", token},
		}
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer conn.Close()

		_ = conn.WriteMessage(websocket.TextMessage, []byte("Авторизация через субпротокол успешна!"))
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")

	// Клиент передает токен в субпротоколах
	dialer := websocket.Dialer{
		Subprotocols: []string{"access-token", "super_secret_jwt"},
	}

	conn, resp, err := dialer.Dial(wsURL, nil)
	if err != nil || resp.StatusCode != http.StatusSwitchingProtocols {
		t.Fatalf("Ошибка авторизации: %v", err)
	}
	defer conn.Close()

	_, msg, _ := conn.ReadMessage()
	expected := "Авторизация через субпротокол успешна!"
	if string(msg) != expected {
		t.Fatalf("Некорректный ответ: %s", string(msg))
	}

	fmt.Println("Аутентификация через Sec-WebSocket-Protocol успешно протестирована:")
	fmt.Printf("  • Ответ сервера: «%s»\n", string(msg))
}
```

## Под капотом

Заголовок `Sec-WebSocket-Protocol` не логируется большинством стандартных HTTP прокси-серверов, в отличие от query-параметров URL (`?token=...`), что делает его значительно более безопасным способом передачи токенов.

## Подводные камни

Забывать возвращать токен в `Subprotocols` заголовка ответа сервера: если клиент запросил субпротокол, а сервер не подтвердил его в ответе 101, браузер немедленно разорвет соединение с ошибкой протокола.

## На собеседовании

**Вопрос с собеседования:** «Почему передача токена в Query-параметрах считается менее безопасной?»
**Ответ:** 1. Query-параметры целиком сохраняются в access-логах Nginx/балансировщиков, попадая в системы мониторинга (ELK/ClickHouse). 2. Query-параметры сохраняются в истории браузера. 3. Query-параметры могут утекать в заголовке `Referer` при переходе по внешним ссылкам. Передача через `Sec-WebSocket-Protocol` или первое служебное сообщение полностью решает эту проблему.
