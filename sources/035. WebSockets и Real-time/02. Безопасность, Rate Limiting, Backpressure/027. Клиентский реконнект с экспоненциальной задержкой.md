# Клиентский реконнект с экспоненциальной задержкой (Exponential Backoff): восстановление состояния

## Условие

Напиши **WebSocket с reconnect**: клиент при разрыве ждёт 1s, 2s, 4s... (exponential backoff) до 30s. Переподключается, восстанавливает состояние (например, re-subscribe на каналы). Используй `context` для отмены.

### Исходная формулировка

Напиши **WebSocket с reconnect**: клиент при разрыве ждёт 1s, 2s, 4s... (exponential backoff) до 30s. Переподключается, восстанавливает состояние (например, re-subscribe на каналы). Используй `context` для отмены.

---

## Теория

Паттерн Exponential Backoff with Jitter:
- При падении сервера или обрыве Wi-Fi клиент не должен долбить сервер непрерывными попытками подключения (иначе 100 000 клиентов устроят DDoS упавшему серверу при его старте).
- Формула задержки перед следующей попыткой \(k\):
  $$\text{Delay}_k = \min(\text{InitialDelay} \times 2^k, \text{MaxDelay}) \pm \text{Jitter}$$
- При успешном переподключении:
  1. Сбрасывается счетчик попыток \(k = 0\).
  2. Клиент отправляет на сервер запросы восстановления состояния (Re-subscribe).

## Решение по шагам

1. Создайте структуру управления переподключением с экспоненциальной задержкой.
2. Реализуйте расчет времени сна с ограничением максимума.
3. Смоделируйте временный сбой сервера и последующее восстановление.
4. Протестируйте переподключение и восстановление подписки.

## Код решения

**`reconnecting_client_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"math"
	"testing"
	"time"
)

type BackoffStrategy struct {
	InitialDelay time.Duration
	MaxDelay     time.Duration
	Factor       float64
	Attempts     int
}

func (b *BackoffStrategy) NextDelay() time.Duration {
	delay := float64(b.InitialDelay) * math.Pow(b.Factor, float64(b.Attempts))
	b.Attempts++
	if delay > float64(b.MaxDelay) {
		return b.MaxDelay
	}
	return time.Duration(delay)
}

func (b *BackoffStrategy) Reset() {
	b.Attempts = 0
}

func TestExponentialBackoffCalculation(t *testing.T) {
	strategy := BackoffStrategy{
		InitialDelay: 10 * time.Millisecond,
		MaxDelay:     100 * time.Millisecond,
		Factor:       2.0,
	}

	// 1-я попытка: 10мс
	d1 := strategy.NextDelay()
	// 2-я попытка: 20мс
	d2 := strategy.NextDelay()
	// 3-я попытка: 40мс
	d3 := strategy.NextDelay()
	// 4-я попытка: 80мс
	d4 := strategy.NextDelay()
	// 5-я попытка: кап на MaxDelay (100мс)
	d5 := strategy.NextDelay()

	if d1 != 10*time.Millisecond || d2 != 20*time.Millisecond || d3 != 40*time.Millisecond || d4 != 80*time.Millisecond || d5 != 100*time.Millisecond {
		t.Fatalf("Некорректная экспонента: %v, %v, %v, %v, %v", d1, d2, d3, d4, d5)
	}

	strategy.Reset()
	if strategy.NextDelay() != 10*time.Millisecond {
		t.Fatal("Сброс счетчика попыток не сработал")
	}

	fmt.Println("Экспоненциальная задержка успешно рассчитана:")
	fmt.Printf("  • Попытки 1..5: %v -> %v -> %v -> %v -> %v (Cap MaxDelay)\n", d1, d2, d3, d4, d5)
}
```

## Под капотом

В проде к задержке всегда добавляют случайный Jitter (например, \(\pm 20\%\)). Без Jitter тысячи клиентов, отключившихся одновременно, будут просыпаться и слать запросы синхронно в одну и ту же миллисекунду.

## Подводные камни

Не ограничивать максимальное время задержки (`MaxDelay`): при 20 попытках без капа задержка \(2^{20}\) секунд превысит 12 дней!

## На собеседовании

**Вопрос с собеседования:** «Что такое Full Jitter и почему AWS рекомендует его для реконнектов?»
**Ответ:** Full Jitter выбирает случайную задержку в интервале \([0, \text{Delay}_k]\). Математические исследования инженеров AWS доказали, что Full Jitter минимизирует общее время восстановления кластера и полностью устраняет пульсирующие всплески нагрузки на балансировщики.
