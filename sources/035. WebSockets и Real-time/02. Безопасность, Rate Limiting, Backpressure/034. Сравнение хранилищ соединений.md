# Сравнение хранилищ соединений: sync.Map против map + RWMutex в реальных бенчмарках

## Условие

Создайте WebSocket-сервер, который принимает соединения и хранит их в потокобезопасной мапе (`sync.Map` или `map + RWMutex`).

## Теория

Выбор между `sync.Map` и `map + sync.RWMutex` в Go:
- `map + sync.RWMutex`:
  - Идеально, когда соединения часто добавляются и удаляются (равное соотношение чтения и записи).
  - Типобезопасно: нет оверхеда на приведение типов `any`.
- `sync.Map`:
  - Оптимизирована для двух сценариев:
    1. Ключ пишется один раз, а читается миллионы раз (Cache-like).
    2. Множество горутин читают, пишут и обновляют непересекающиеся ключи.
  - Минус: боксинг значений в `any` создает дополнительную нагрузку на Garbage Collector.

## Решение по шагам

1. Создайте реестр на базе `sync.Map`.
2. Реализуйте добавление, проверку и удаление соединений.
3. Протестируйте итерацию по активным подключениям через `Range`.
4. Сравните с классической реализацией `RWMutex`.

## Код решения

**`sync_map_registry_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type DummyConn struct {
	ID string
}

type SyncMapRegistry struct {
	conns sync.Map
}

func (r *SyncMapRegistry) Add(conn *DummyConn) {
	r.conns.Store(conn, struct{}{})
}

func (r *SyncMapRegistry) Remove(conn *DummyConn) {
	r.conns.Delete(conn)
}

func (r *SyncMapRegistry) Count() int {
	count := 0
	r.conns.Range(func(key, value any) bool {
		count++
		return true
	})
	return count
}

func TestSyncMapRegistry(t *testing.T) {
	reg := &SyncMapRegistry{}

	c1 := &DummyConn{ID: "c1"}
	c2 := &DummyConn{ID: "c2"}
	c3 := &DummyConn{ID: "c3"}

	reg.Add(c1)
	reg.Add(c2)
	reg.Add(c3)

	if reg.Count() != 3 {
		t.Fatalf("Ожидалось 3 соединения, получено: %d", reg.Count())
	}

	reg.Remove(c2)

	if reg.Count() != 2 {
		t.Fatalf("Ожидалось 2 соединения после удаления, получено: %d", reg.Count())
	}

	fmt.Printf("Реестр соединений на базе sync.Map успешно протестирован: активных сокетов = %d\n", reg.Count())
}
```

ℹ️ Потокобезопасный реестр соединений на базе sync.Map

## Под капотом

Внутри `sync.Map` разделена на две части: атомарную структуру `read` (для быстрого чтения без блокировок через `atomic.Pointer`) и структуру `dirty` (требующую мьютекса). При частых удалениях и вставках `sync.Map` постоянно сбрасывает кэш, работая медленнее обычного `map + RWMutex`.

## Подводные камни

Использовать `sync.Map` повсеместно в надежде на «магическое ускорение»: в большинстве прикладных сценариев сокетов `map + sync.RWMutex` работает быстрее и потребляет меньше памяти.

## На собеседовании

**Вопрос с собеседования:** «Что быстрее для WebSocket Registry на 100 000 соединений: sync.Map или Sharded Map (шардированная мапа)?»
**Ответ:** Шардированная мапа (`ShardedMap` из 32–64 независимых корзин `map + sync.RWMutex`). Хэш от ID соединения `hash(connID) % shards` определяет шарду. Это устраняет борьбу за мьютекс между ядрами процессора, исключает боксинг `any` и обеспечивает максимальную пропускную способность.
