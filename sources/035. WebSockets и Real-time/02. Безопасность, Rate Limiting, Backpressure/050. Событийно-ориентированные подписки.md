# Событийно-ориентированные подписки (Event-Driven Subscriptions): полная изоляция через брокер сообщений

## Условие

Реализуй **event-driven subscriptions**: `createUser` mutation пишет событие в Redis Pub/Sub или NATS. Subscription resolver подписывается на канал, транслирует в WebSocket. Покажи decoupling: mutation не знает о подписчиках.

## Теория

Принцип слабой связанности (Decoupling) в Real-time архитектуре:
- **Антипаттерн:** Резолвер мутации напрямую вызывает WebSocket-менеджер и знает о подключенных сокетах.
- **Паттерн Event-Driven:**
  1. Мутация пишет доменное событие в абстрактный интерфейс `EventPublisher`:
     `publisher.Publish(ctx, "users.created", event)`.
  2. Мутация ничего не знает о WebSocket, клиентах, протоколах и форматах фронтенда.
  3. Резолвер подписки подписывается на `EventSubscriber`:
     `subStream := subscriber.Subscribe(ctx, "users.created")`.
  4. Полная изоляция бизнес-логики от транспортного уровня.

## Решение по шагам

1. Определите интерфейсы `EventPublisher` и `EventSubscriber`.
2. Реализуйте слабосвязанный сервис пользователей.
3. Подключите независимый WebSocket адаптер.
4. Продемонстрируйте изоляцию мутации от сокетов.

## Код решения

**`decoupled_subscriptions_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type EventPublisher interface {
	PublishEvent(ctx context.Context, topic string, payload any) error
}

type EventSubscriber interface {
	SubscribeEvent(ctx context.Context, topic string) (<-chan any, error)
}

type InMemoryMessageBus struct {
	mu     sync.RWMutex
	topics map[string][]chan any
}

func NewMessageBus() *InMemoryMessageBus {
	return &InMemoryMessageBus{topics: make(map[string][]chan any)}
}

func (b *InMemoryMessageBus) PublishEvent(ctx context.Context, topic string, payload any) error {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for _, ch := range b.topics[topic] {
		select {
		case ch <- payload:
		default:
		}
	}
	return nil
}

func (b *InMemoryMessageBus) SubscribeEvent(ctx context.Context, topic string) (<-chan any, error) {
	b.mu.Lock()
	defer b.mu.Unlock()
	ch := make(chan any, 10)
	b.topics[topic] = append(b.topics[topic], ch)
	return ch, nil
}

// Доменный сервис ничего не знает о WebSocket!
type DomainUserService struct {
	bus EventPublisher
}

func (s *DomainUserService) CreateUser(ctx context.Context, name string) error {
	// Сохранение в базу...
	event := map[string]string{"name": name, "status": "CREATED"}
	return s.bus.PublishEvent(ctx, "users.events", event)
}

func TestDecoupledSubscriptions(t *testing.T) {
	bus := NewMessageBus()
	userSvc := &DomainUserService{bus: bus}

	// Независимый WebSocket резолвер оформляет подписку
	stream, err := bus.SubscribeEvent(context.Background(), "users.events")
	if err != nil {
		t.Fatalf("Ошибка подписки: %v", err)
	}

	// Вызываем чистый доменный метод
	_ = userSvc.CreateUser(context.Background(), "Дмитрий")

	select {
	case raw := <-stream:
		ev := raw.(map[string]string)
		if ev["name"] != "Дмитрий" {
			t.Fatalf("Некорректное событие: %+v", ev)
		}
		fmt.Printf("Event-Driven Subscriptions успешно протестирован:\n")
		fmt.Printf("  • Доменный сервис опубликовал событие без ведома о сокетах\n")
		fmt.Printf("  • Подписчик принял событие: Имя=%s, Статус=%s\n", ev["name"], ev["status"])
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Таймаут ожидания события")
	}
}
```

ℹ️ Слабая связанность доменных сервисов и подписок через EventPublisher

## Под капотом

Интерфейс `EventPublisher` легко подменяется на мок в юнит-тестах бизнес-логики без поднятия тяжелых сетевых WebSocket сокетов.

## Подводные камни

Внедрять зависимости WebSocket-менеджера в доменные модели: это грубейшее нарушение Clean Architecture и принципа инверсии зависимостей (DIP).

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать порядок событий (FIFO Ordering) в распределенной шине NATS / Kafka для одного пользователя?»
**Ответ:** Использовать партиционирование по ключу (Partitioning by Partition Key). Ключом партиции выбирается `userID`. В Kafka все события одного пользователя попадают строго в одну партицию топика, что гарантирует абсолютный порядок доставки подписчикам.
