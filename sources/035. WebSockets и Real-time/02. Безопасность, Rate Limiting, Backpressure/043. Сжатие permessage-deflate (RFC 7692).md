# Сжатие permessage-deflate (RFC 7692): настройка компрессии и баланс CPU против сетевого трафика

## Условие

Настройте **compression** (permessage-deflate) для снижения трафика: `websocket.AcceptOptions{CompressionMode: websocket.CompressionContextual}`.

## Теория

Сжатие в протоколе WebSocket (RFC 7692 permessage-deflate):
- Позволяет серверу и браузеру прозрачно сжимать текстовые JSON сообщения алгоритмом Deflate/zlib.
- Включение в Gorilla WebSocket:
  - `Upgrader.EnableCompression = true`.
  - Метод `conn.EnableWriteCompression(true)` / `conn.SetCompressionLevel(level)`.
- **Инженерный компромисс (Trade-Off):**
  - Сжатие экономит до 70–80% сетевого трафика на больших JSON ответах.
  - Однако Deflate требует заметных аллокаций памяти и тактов CPU на каждый сжатый фрейм.
  - В HighLoad системах компрессию включают только для сообщений размером \(> 512\) байт.

## Решение по шагам

1. Настройте `Upgrader` со свойством `EnableCompression: true`.
2. Установите уровень сжатия `flate.BestSpeed`.
3. Отправьте объемный JSON документ.
4. Убедитесь в прозрачной декомпрессии клиентом.

## Код решения

**`ws_compression_test.go`**

```go
package main

import (
	"compress/flate"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/gorilla/websocket"
)

func TestPermessageDeflateCompression(t *testing.T) {
	upgrader := websocket.Upgrader{
		EnableCompression: true,
	}

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer conn.Close()

		// Включаем сжатие и настраиваем уровень скорости
		conn.EnableWriteCompression(true)
		_ = conn.SetCompressionLevel(flate.BestSpeed)

		// Отправляем повторяющийся текст, который отлично сжимается deflate
		largePayload := strings.Repeat("JSON_DATA_FIELD_VALUE_1234567890_", 50)
		_ = conn.WriteMessage(websocket.TextMessage, []byte(largePayload))
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")

	dialer := websocket.Dialer{
		EnableCompression: true,
	}

	conn, _, err := dialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка Dial: %v", err)
	}
	defer conn.Close()

	_, received, err := conn.ReadMessage()
	if err != nil {
		t.Fatalf("Ошибка чтения: %v", err)
	}

	expectedPrefix := "JSON_DATA_FIELD_VALUE_1234567890_"
	if !strings.HasPrefix(string(received), expectedPrefix) || len(received) < 1500 {
		t.Fatalf("Данные повреждены при распаковке: len=%d", len(received))
	}

	fmt.Printf("Permessage-deflate сжатие успешно отработало:\n")
	fmt.Printf("  • Исходный размер: %d байт\n", len(received))
	fmt.Printf("  • Алгоритм BestSpeed передал и прозрачно распаковал данные в сокете!\n")
}
```

## Под капотом

При рукопожатии клиент и сервер согласуют заголовок `Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits`. Если расширение согласовано, фреймы помечаются битом `RSV1 = 1` в заголовке кадра RFC 6455.

## Подводные камни

Использовать максимальный уровень сжатия `flate.BestCompression`: это перегрузит ядра CPU сервера при микроскопической экономии трафика по сравнению с `flate.BestSpeed`.

## На собеседовании

**Вопрос с собеседования:** «Что такое атака CRIME / BREACH на сжатые WebSocket соединения?»
**Ответ:** Это атака на основе сайд-ченнелов (Side-channel Attack): злоумышленник внедряет в поток свои данные и замеряет изменение размера сжатого фрейма. Чем лучше сжался фрейм, тем больше символов совпало с секретным токеном сессии жертвы. В критических защищенных каналах сжатие секретных заголовков принудительно отключают.
