# Паттерн Client с буферизацией: отправка сообщений через send chan []byte

## Условие

**Паттерн Hub (Чат-комната)**: Создай структуру `Hub`, которая хранит мапу активных клиентов `map[*Client]bool` и имеет канал `broadcast`. Любое сообщение, попадающее в `broadcast`, должно в цикле рассылаться всем клиентам из мапы. (Не забудь защитить мапу мьютексом или управлять ей через отдельную горутину, как в официальном туториале Gorilla).

## Теория

Индивидуальный буфер клиента:
- Если писать в `conn.WriteMessage` прямо из цикла рассылки Hub'а, самый медленный сокет затормозит весь цикл для всех остальных.
- Поэтому каждый `Client` имеет персональную очередь:
  `send chan []byte` (буфер 256 сообщений).
- Диспетчер Hub просто кладет слайс байт в канал:
  `client.send <- message`.
- Отправку в сокет делает собственная горутина клиента `writePump`.

## Решение по шагам

1. Создайте структуру `BufferedClient` с каналом `send chan []byte`.
2. Реализуйте метод отправки сообщения в клиентский буфер.
3. Смоделируйте независимое вычитывание сообщений из буфера.
4. Протестируйте устойчивость Hub к сетевым задержкам.

## Код решения

**`buffered_client_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BufferedClient struct {
	ID   string
	send chan []byte
}

func NewBufferedClient(id string, bufSize int) *BufferedClient {
	return &BufferedClient{
		ID:   id,
		send: make(chan []byte, bufSize),
	}
}

func (c *BufferedClient) Enqueue(msg []byte) bool {
	select {
	case c.send <- msg:
		return true
	default:
		return false // Буфер переполнен
	}
}

func TestBufferedClient(t *testing.T) {
	client := NewBufferedClient("user_vip", 2)

	// Заполняем буфер
	ok1 := client.Enqueue([]byte("Сообщение 1"))
	ok2 := client.Enqueue([]byte("Сообщение 2"))
	// Третье сообщение не должно поместиться
	ok3 := client.Enqueue([]byte("Сообщение 3 (переполнение)"))

	if !ok1 || !ok2 || ok3 {
		t.Fatalf("Ожидалось переполнение буфера: ok1=%v, ok2=%v, ok3=%v", ok1, ok2, ok3)
	}

	m1 := <-client.send
	m2 := <-client.send

	if string(m1) != "Сообщение 1" || string(m2) != "Сообщение 2" {
		t.Fatalf("Нарушен порядок сообщений: %s, %s", m1, m2)
	}

	fmt.Println("Буферизированный клиент успешно защитил память очереди сообщений!")
}
```

ℹ️ Управление очередью сообщений клиента через буферизированный канал

```bash

```

## Под капотом

Размер буфера `send` (например, 256 элементов) позволяет клиенту сглаживать временные микро-всплески сетевого джиттера (Network Jitter) без потери пакетов.

## Подводные камни

Аллоцировать слишком большой буфер (например, 10 000 элементов на клиента): при 50 000 клиентов пустые каналы займут сотни мегабайт памяти.

## На собеседовании

**Вопрос с собеседования:** «Почему в channel отправляют срез []byte, а не готовую структуру?»
**Ответ:** Сериализацию сообщения в JSON (`json.Marshal`) Hub выполняет **ровно один раз** перед началом рассылки. Все 10 000 клиентов получают ссылку на один и тот же байтовый срез в куче, экономя 99.99% тактов CPU на сериализации.
