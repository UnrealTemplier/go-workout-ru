# Метрики производительности Echo-сервера: подсчет байт, латентности и пропускной способности

## Условие

Создайте WebSocket-сервер с помощью `gorilla/websocket`. Реализуйте эхо: сервер возвращает любое полученное сообщение обратно отправителю.

## Теория

Мониторинг метрик WebSocket сервера:
- В отличие от HTTP, где запрос и ответ строго связаны одним контекстом, в WebSocket сессия живет часами.
- Ключевые метрики:
  - `bytes_read_total` / `bytes_written_total` — сетевой трафик.
  - `messages_count` — количество обработанных сообщений.
  - `active_connections` — текущее число открытых сокетов (gauge).
  - `echo_latency_seconds` — время задержки от чтения до отправки.

## Решение по шагам

1. Создайте счетчики метрик через атомики `sync/atomic`.
2. В эхо-цикле замеряйте размер прочитанных сообщений.
3. Отправьте 50 сообщений и соберите статистику.
4. Выведите метрики пропускной способности.

## Код решения

**`monitored_echo_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync/atomic"
	"testing"
	"time"

	"github.com/gorilla/websocket"
)

type ServerMetrics struct {
	messagesCount int64
	bytesRead     int64
	bytesWritten  int64
}

func TestMonitoredEchoMetrics(t *testing.T) {
	metrics := &ServerMetrics{}
	upgrader := websocket.Upgrader{}

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer conn.Close()

		for {
			mt, p, err := conn.ReadMessage()
			if err != nil {
				break
			}
			atomic.AddInt64(&metrics.messagesCount, 1)
			atomic.AddInt64(&metrics.bytesRead, int64(len(p)))

			start := time.Now()
			_ = conn.WriteMessage(mt, p)
			_ = time.Since(start)

			atomic.AddInt64(&metrics.bytesWritten, int64(len(p)))
		}
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка Dial: %v", err)
	}
	defer clientConn.Close()

	payload := []byte("Метрика-Тест")
	for i := 0; i < 20; i++ {
		_ = clientConn.WriteMessage(websocket.TextMessage, payload)
		_, _, _ = clientConn.ReadMessage()
	}

	msgs := atomic.LoadInt64(&metrics.messagesCount)
	readBytes := atomic.LoadInt64(&metrics.bytesRead)
	writtenBytes := atomic.LoadInt64(&metrics.bytesWritten)

	if msgs != 20 || readBytes != int64(20*len(payload)) {
		t.Fatalf("Некорректные метрики: msgs=%d, readBytes=%d", msgs, readBytes)
	}

	fmt.Println("Echo-сервер с метриками успешно собрал телеметрию:")
	fmt.Printf("  • Обработано сообщений: %d\n", msgs)
	fmt.Printf("  • Прочитано байт:       %d B\n", readBytes)
	fmt.Printf("  • Записано байт:        %d B\n", writtenBytes)
}
```

## Под капотом

Атомарные операции `atomic.AddInt64` выполняются с помощью процессорной инструкции `LOCK XADD`, не требуя системных вызовов и мьютексов.

## Подводные камни

Использовать неатомарные операции `metrics.count++`: при параллельных сокетах гонка данных приведет к потере части значений.

## На собеседовании

**Вопрос с собеседования:** «Как отслеживать латентность раундтрипа (Round-Trip Time, RTT) до клиента через WebSocket?»
**Ответ:** Сервер отправляет фрейм `PingMessage` с 8-байтным таймстампом текущего времени `time.Now().UnixNano()` в полезной нагрузке. Клиент по стандарту RFC 6455 ОБЯЗАН вернуть ровно те же данные в ответном фрейме `PongMessage`. В `SetPongHandler` сервер вычитает сохраненный таймстамп из текущего времени: `rtt := time.Now().UnixNano() - sentTimestamp`.
