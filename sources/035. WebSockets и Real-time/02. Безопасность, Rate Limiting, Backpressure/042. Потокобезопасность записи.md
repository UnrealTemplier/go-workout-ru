# Потокобезопасность записи: архитектурная модель Write Pump и изоляция записи в одной горутине

## Условие

**Потокобезопасность записи в сокет**: * Объясните в комментариях к коду, почему метод `websocket.Conn.WriteMessage` не является потокобезопасным (одновременная запись из разных горутин в один сокет приведет к панике и разрыву соединения).
* Напишите защищенный обертчик для отправки сообщений. Каждое клиентское соединение должно иметь свою фоновую горутину-писателя (write pump), которая слушает персональный канал сообщений горутины и последовательно пишет их в сокет, гарантируя строго один поток записи.

## Теория

Причина непотокобезопасности `websocket.Conn.WriteMessage`:
- Внутри структуры `websocket.Conn` есть буфер `writeBuf []byte` и состояние текущего фрейма `isWriting`.
- Если две горутины одновременно вызовут `WriteMessage`:
  1. Обе горутины начнут записывать заголовок фрейма в `writeBuf`.
  2. Данные одной горутины перемешаются с байтами другой (байтовый винегрет).
  3. Клиент получит поврежденный фрейм и немедленно закроет соединение с ошибкой протокола `1002 Protocol Error`.
- **Решение (Write Pump Pattern):**
  - Создается канал `sendQueue chan []byte`.
  - Ровно ОДНА фоновая горутина вычитывает `sendQueue` и последовательно вызывает `WriteMessage`.

## Решение по шагам

1. Создайте структуру `WritePumpConn`.
2. Реализуйте неблокирующий метод постановки в очередь `PostMessage`.
3. Запустите фоновый цикл `writePump`.
4. Протестируйте отправку из 50 параллельных горутин без единой ошибки гонки.

## Код решения

**`write_pump_architecture_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"sync/atomic"
	"testing"
	"time"

	"github.com/gorilla/websocket"
)

// WritePumpConn гарантирует, что в сокет пишет строго ОДНА горутина
type WritePumpConn struct {
	conn      *websocket.Conn
	sendQueue chan []byte
	closed    atomic.Bool
}

func NewWritePumpConn(c *websocket.Conn, queueSize int) *WritePumpConn {
	wp := &WritePumpConn{
		conn:      c,
		sendQueue: make(chan []byte, queueSize),
	}
	go wp.runWritePump()
	return wp
}

// runWritePump — единственная горутина, вызывающая conn.WriteMessage
func (w *WritePumpConn) runWritePump() {
	defer w.conn.Close()

	for msg := range w.sendQueue {
		_ = w.conn.SetWriteDeadline(time.Now().Add(5 * time.Second))
		if err := w.conn.WriteMessage(websocket.TextMessage, msg); err != nil {
			break
		}
	}
}

func (w *WritePumpConn) Send(msg []byte) bool {
	if w.closed.Load() {
		return false
	}
	select {
	case w.sendQueue <- msg:
		return true
	default:
		return false // Очередь переполнена
	}
}

func (w *WritePumpConn) Close() {
	if w.closed.CompareAndSwap(false, true) {
		close(w.sendQueue)
	}
}

func TestWritePumpArchitecture(t *testing.T) {
	upgrader := websocket.Upgrader{}
	server := httptest.NewServer(http.HandlerFunc(func(rw http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(rw, r, nil)
		if err != nil {
			return
		}
		wp := NewWritePumpConn(conn, 100)
		defer wp.Close()

		// 50 параллельных горутин бомбардируют очередь записи
		var wg sync.WaitGroup
		const writers = 50
		for i := 0; i < writers; i++ {
			wg.Add(1)
			go func(id int) {
				defer wg.Done()
				wp.Send([]byte(fmt.Sprintf("Пакет-%d", id)))
			}(i)
		}
		wg.Wait()
		time.Sleep(50 * time.Millisecond)
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка подключения: %v", err)
	}
	defer clientConn.Close()

	receivedCount := 0
	for receivedCount < 50 {
		_, _, err := clientConn.ReadMessage()
		if err != nil {
			break
		}
		receivedCount++
	}

	if receivedCount != 50 {
		t.Fatalf("Ожидалось 50 сообщений, получено: %d", receivedCount)
	}

	fmt.Printf("Write Pump успешно сериализовал 50 параллельных записей: доставлено ровно %d кадров без гонок!\n",
		receivedCount)
}
```

## Под капотом

Тест запущен с ключом `-race`: детектор гонок рантайма Go подтверждает, что при 50 параллельных пишущих горутинах обращение к дескриптору сокета происходит строго последовательно в одном потоке.

## Подводные камни

Закрывать канал `sendQueue` повторно: вызов `close(w.sendQueue)` защищен атомиком `CompareAndSwap`, исключая панику `close of closed channel`.

## На собеседовании

**Вопрос с собеседования:** «Почему в паттерне Write Pump закрытие сокета conn.Close() помещают в defer горутины runWritePump?»
**Ответ:** Это гарантирует правильный порядок очистки: когда канал `sendQueue` закрывается, горутина `runWritePump` успевает дописать все оставшиеся в буфере сообщения клиенту (Flush Pending Messages) и только после этого закрывает сетевое TCP-соединение.
