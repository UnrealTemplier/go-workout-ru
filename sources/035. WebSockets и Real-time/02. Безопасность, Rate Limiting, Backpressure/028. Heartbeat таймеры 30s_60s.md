# Heartbeat таймеры 30s/60s: отправка WriteControl PingMessage и детекция таймаутов

## Условие

Напиши **WebSocket с heartbeat (ping/pong)**: сервер шлёт `ping` каждые 30 секунд (`conn.WriteControl(websocket.PingMessage, ...)`). Клиент отвечает `pong` автоматически (или вручную через `SetPongHandler`). Если pong не получен за 60 секунд — закрой соединение.

## Теория

Промышленные интервалы Heartbeat (30s / 60s):
- Соотношение периодов:
  - `pingPeriod = 30 * time.Second`
  - `pongWait = 60 * time.Second`
  - Сервер успевает отправить 2 пинга до истечения дедлайна, давая клиенту запас на временные лаги сети.
- Метод `conn.WriteControl(websocket.PingMessage, nil, deadline)`:
  - Отправляет служебный управляющий фрейм вне очереди обычных сообщений.
  - Управляющие фреймы имеют максимальный размер полезной нагрузки 125 байт по RFC 6455.

## Решение по шагам

1. Создайте тестовые настройки Heartbeat (масштабированные для быстрого теста).
2. Настройте `WriteControl(websocket.PingMessage)` по тикеру.
3. Реализуйте сдвиг дедлайна в `SetPongHandler`.
4. Проверьте разрыв соединения при отсутствии ответов Pong.

## Код решения

**`heartbeat_deadlock_guard_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
	"time"

	"github.com/gorilla/websocket"
)

func TestHeartbeatTimeoutDetection(t *testing.T) {
	// Масштабируем секунды в миллисекунды для быстрого теста:
	// ping каждые 30мс, таймаут 60мс
	pingPeriod := 30 * time.Millisecond
	pongWait := 60 * time.Millisecond

	connClosed := make(chan struct{})

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		upgrader := websocket.Upgrader{}
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer func() {
			conn.Close()
			close(connClosed)
		}()

		_ = conn.SetReadDeadline(time.Now().Add(pongWait))
		conn.SetPongHandler(func(string) error {
			_ = conn.SetReadDeadline(time.Now().Add(pongWait))
			return nil
		})

		// Фоновый тикер пингов
		ticker := time.NewTicker(pingPeriod)
		defer ticker.Stop()

		go func() {
			for range ticker.C {
				// WriteControl отправляет управляющий фрейм вне очереди
				err := conn.WriteControl(websocket.PingMessage, []byte("ping"), time.Now().Add(10*time.Millisecond))
				if err != nil {
					return
				}
			}
		}()

		for {
			if _, _, err := conn.ReadMessage(); err != nil {
				// Дедлайн истек -> разрыв!
				break
			}
		}
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка подключения: %v", err)
	}

	// Клиент НАМЕРЕННО отключает авто-ответ на Ping (симулируем «зависший» клиент)
	clientConn.SetPingHandler(func(string) error {
		// Ничего не отвечаем!
		return nil
	})

	// Ждем срабатывания таймаута на сервере
	select {
	case <-connClosed:
		fmt.Println("Сервер успешно обнаружил «мертвый» сокет по таймауту Pong (60ms) и закрыл соединение!")
	case <-time.After(300 * time.Millisecond):
		t.Fatal("Таймаут обнаружения зависшего соединения не сработал")
	}

	clientConn.Close()
}
```

## Под капотом

`conn.WriteControl` не блокируется на записи больших данных, так как управляющие фреймы (Control Frames) могут вклиниваться между чанками обычных фрагментированных сообщений согласно RFC 6455 Section 5.5.

## Подводные камни

Использовать обычный `conn.WriteMessage(websocket.PingMessage, ...)`: обычная запись блокируется, если в этот момент отправляется большое бинарное сообщение, из-за чего пинг опоздает и сокет разорвется ложно.

## На собеседовании

**Вопрос с собеседования:** «Почему Nginx часто закрывает WebSocket соединения через 60 секунд после открытия?»
**Ответ:** По умолчанию в Nginx директива `proxy_read_timeout` равна 60 секундам. Если по соединению в течение 60 секунд не проходит ни одного пакета, Nginx считает соединение мертвым и сбрасывает TCP-сокет. Настройка серверного Heartbeat с интервалом менее 60 секунд (например 30s или 15s) решает эту проблему.
