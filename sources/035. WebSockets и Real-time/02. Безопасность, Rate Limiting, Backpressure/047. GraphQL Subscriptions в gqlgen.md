# GraphQL Subscriptions в gqlgen: реактивный пуш событий при вызове мутации createUser

## Условие

Настрой **GraphQL subscriptions через WebSocket** в gqlgen: `transport.SSE` или `transport.Websocket`. Клиент отправляет `subscription { userCreated { id name } }`. Сервер пушит события при `createUser` mutation.

## Теория

Сквозной сценарий реакции на мутации в GraphQL:
1. Клиент А оформляет подписку: `subscription { userCreated { id name } }`.
2. Клиент Б вызывает мутацию: `mutation { createUser(name: "Михаил") { id } }`.
3. Резолвер мутации:
   - Сохраняет пользователя.
   - Отправляет событие в шину: `r.UserEventBus.Publish(user)`.
4. Сервер автоматически формирует GraphQL фрейм и отправляет его Клиенту А по открытому WebSocket соединению.

## Решение по шагам

1. Создайте структуры данных пользователя и шины событий.
2. Реализуйте метод мутации `CreateUser` с публикацией события.
3. Реализуйте метод подписки `UserCreated` со слушающим каналом.
4. Протестируйте реактивную доставку события подписчику.

## Код решения

**`reaction_mutation_sub_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type User struct {
	ID   string
	Name string
}

type ReactiveApp struct {
	mu          sync.RWMutex
	subscribers []chan *User
	users       map[string]*User
}

func NewReactiveApp() *ReactiveApp {
	return &ReactiveApp{users: make(map[string]*User)}
}

// Резолвер мутации
func (a *ReactiveApp) MutationCreateUser(name string) *User {
	a.mu.Lock()
	id := fmt.Sprintf("u_%d", len(a.users)+1)
	user := &User{ID: id, Name: name}
	a.users[id] = user

	// Публикация события всем подписчикам
	for _, sub := range a.subscribers {
		select {
		case sub <- user:
		default:
		}
	}
	a.mu.Unlock()
	return user
}

// Резолвер подписки
func (a *ReactiveApp) SubscriptionUserCreated(ctx context.Context) <-chan *User {
	ch := make(chan *User, 5)
	a.mu.Lock()
	a.subscribers = append(a.subscribers, ch)
	a.mu.Unlock()

	go func() {
		<-ctx.Done()
		a.mu.Lock()
		defer a.mu.Unlock()
		for i, sub := range a.subscribers {
			if sub == ch {
				a.subscribers = append(a.subscribers[:i], a.subscribers[i+1:]...)
				close(ch)
				break
			}
		}
	}()

	return ch
}

func TestReactiveMutationSubscription(t *testing.T) {
	app := NewReactiveApp()

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	userStream := app.SubscriptionUserCreated(ctx)

	// Выполняем мутацию создания
	created := app.MutationCreateUser("Михаил")

	select {
	case received := <-userStream:
		if received.ID != created.ID || received.Name != "Михаил" {
			t.Fatalf("Подписчик получил неверные данные: %+v", received)
		}
		fmt.Printf("Сквозной реактивный поток GraphQL отработал штатно:\n")
		fmt.Printf("  • Мутация создала: ID=%s, Имя=%s\n", created.ID, created.Name)
		fmt.Printf("  • Подписка доставила событие подписчику в реальном времени!\n")
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Таймаут ожидания события в подписке")
	}
}
```

ℹ️ Сквозной реактивный поток: вызов мутации триггерит отправку в subscription

## Под капотом

Внутри `gqlgen` подписчики регистрируются в менеджере `graphql.ExecutableSchema`. При возврате канала рантайм gqlgen форматирует ответ с соблюдением Selection Set запроса подписчика.

## Подводные камни

Блокировать мутацию при отправке в канал медленного подписчика: отправка в канал подписчика обязана быть неблокирующей (`select default`).

## На собеседовании

**Вопрос с собеседования:** «Почему в продакшене не держат список subscribers в памяти одного процесса?»
**Ответ:** Если под с мутацией и под с веб-сокетом подписчика — это разные поды в Kubernetes, подписчик никогда не получит событие из памяти. В продакшене `MutationCreateUser` пишет событие в Kafka/Redis, а поды сокетов вычитывают его из топика и пересылают своим клиентам.
