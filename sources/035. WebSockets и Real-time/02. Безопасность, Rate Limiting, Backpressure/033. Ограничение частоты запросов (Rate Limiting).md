# Ограничение частоты запросов (Rate Limiting) на соединение: алгоритм Token Bucket и защита от спама

## Условие

Напиши **WebSocket rate limiter**: per-connection limit — не более 10 сообщений/секунду. Используй token bucket или sliding window. При превышении — закрой соединение или отправь ошибку.

## Теория

Защита от спама и DoS на уровне отдельного WebSocket соединения:
- Без лимитера спам-бот может слать 10 000 сообщений в секунду в один открытый сокет.
- **Алгоритм Token Bucket (Корзина токенов):**
  - Емкость ведра: \(B = 10\) токенов.
  - Скорость пополнения: \(R = 10\) токенов в секунду.
  - Каждое входящее сообщение забирает 1 токен.
  - Если токенов нет:
    - Вариант А: отправка ошибки клиенту `RATE_LIMITED`.
    - Вариант Б: немедленное закрытие сокета с кодом `1008 Policy Violation`.

## Решение по шагам

1. Создайте структуру `ConnectionRateLimiter` на базе алгоритма Token Bucket.
2. Реализуйте метод `Allow()` с пополнением токенов по времени.
3. Смоделируйте отправку 15 сообщений подряд.
4. Убедитесь в отсечении запросов сверх лимита 10 msg/sec.

## Код решения

**`ws_rate_limiter_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type TokenBucketLimiter struct {
	mu         sync.Mutex
	capacity   float64
	tokens     float64
	refillRate float64 // токенов в секунду
	lastRefill time.Time
}

func NewTokenBucketLimiter(rate float64, capacity float64) *TokenBucketLimiter {
	return &TokenBucketLimiter{
		capacity:   capacity,
		tokens:     capacity,
		refillRate: rate,
		lastRefill: time.Now(),
	}
}

func (l *TokenBucketLimiter) Allow() bool {
	l.mu.Lock()
	defer l.mu.Unlock()

	now := time.Now()
	elapsed := now.Sub(l.lastRefill).Seconds()
	l.lastRefill = now

	// Пополняем токены
	l.tokens += elapsed * l.refillRate
	if l.tokens > l.capacity {
		l.tokens = l.capacity
	}

	if l.tokens >= 1.0 {
		l.tokens -= 1.0
		return true
	}
	return false
}

func TestWSTokenBucketRateLimiter(t *testing.T) {
	// Лимит: 10 сообщений в секунду, емкость 10 токенов
	limiter := NewTokenBucketLimiter(10.0, 10.0)

	allowedCount := 0
	rejectedCount := 0

	// Пытаемся отправить 15 сообщений мгновенно (Burst)
	for i := 1; i <= 15; i++ {
		if limiter.Allow() {
			allowedCount++
		} else {
			rejectedCount++
		}
	}

	if allowedCount != 10 || rejectedCount != 5 {
		t.Fatalf("Некорректная работа лимитера: allowed=%d, rejected=%d", allowedCount, rejectedCount)
	}

	fmt.Println("Rate Limiter соединения успешно заблокировал спам:")
	fmt.Printf("  • Пропущено сообщений: %d (в рамках лимита)\n", allowedCount)
	fmt.Printf("  • Заблокировано спам-сообщений: %d (превышение Burst!)\n", rejectedCount)
}
```

## Под капотом

В отличие от тяжелых таймеров, алгоритм Token Bucket требует всего 2 числа (`tokens` и `lastRefill`) и одну математическую операцию вычитания времени, расходуя доли наносекунды на вызов.

## Подводные камни

Использовать глобальный Rate Limiter на весь сервер: спамящий бот заблокирует всех добросовестных пользователей сервиса. Лимитер должен быть строго индивидуальным на каждое соединение (`per-connection`).

## На собеседовании

**Вопрос с собеседования:** «Какой код закрытия WebSocket возвращают при превышении Rate Limit по стандарту RFC 6455?»
**Ответ:** Код `1008 Policy Violation`. Он информирует клиентское приложение, что соединение разорвано из-за нарушения политики сервера (слишком частые запросы, спам, неавторизованные действия).
