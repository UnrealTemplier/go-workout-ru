# Управление обратным давлением (Backpressure): переполнение буфера, неблокирующий select и отключение медленных клиентов

## Условие

**[Каверзный кейс — Backpressure]**: Если клиент читает медленно, а сервер пишет быстро, буфер соединения переполнится. Реализуй буферизированный канал для исходящих сообщений (размер 10). Если канал полон, разрывай соединение (`closeChan <- conn`), чтобы не блокировать Hub.

## Теория

Проблема «Медленного потребителя» (Slow Consumer Problem):
- Если у клиента медленный интернет (3G в лифте), а сервер шлет 100 сообщений в секунду:
  - Память буфера канала `send chan []byte` стремительно растет.
  - Если канал переполнится, блокирующий вызов `client.send <- msg` заморозит горутину Hub'а.
  - **Решение:** неблокирующая отправка через `select default`:
    ```go
    select {
    case client.send <- msg:
    default:
        // Буфер переполнен! Отключаем зависшего клиента
        hub.dropClient(client)
    }
    ```
- Это предотвращает каскадный отказ всей системы.

## Решение по шагам

1. Создайте клиента с ограниченным размером буфера (10 элементов).
2. Реализуйте отправку сообщений через `select default`.
3. Смоделируйте переполнение буфера при медленном чтении.
4. Проверьте отключение медленного клиента без блокировки Hub.

## Код решения

**`slow_consumer_backpressure_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BackpressureClient struct {
	ID       string
	send     chan []byte
	isClosed bool
}

type SafeHub struct {
	clients map[*BackpressureClient]bool
}

func (h *SafeHub) Broadcast(msg []byte) {
	for client := range h.clients {
		select {
		case client.send <- msg:
			// Успешно помещено в очередь
		default:
			// Буфер переполнен! Разрываем соединение с медленным клиентом
			close(client.send)
			client.isClosed = true
			delete(h.clients, client)
		}
	}
}

func TestSlowConsumerBackpressure(t *testing.T) {
	hub := &SafeHub{clients: make(map[*BackpressureClient]bool)}

	// Быстрый клиент
	fastClient := &BackpressureClient{ID: "fast_client", send: make(chan []byte, 10)}
	// Медленный клиент с заполненным буфером
	slowClient := &BackpressureClient{ID: "slow_client", send: make(chan []byte, 2)}

	// Забиваем буфер медленного клиента
	slowClient.send <- []byte("msg1")
	slowClient.send <- []byte("msg2")

	hub.clients[fastClient] = true
	hub.clients[slowClient] = true

	// Рассылаем новое сообщение
	hub.Broadcast([]byte("Свежая котировка BTC/USDT"))

	// Быстрый клиент получил сообщение
	if len(fastClient.send) != 1 {
		t.Fatal("Быстрый клиент должен был получить сообщение")
	}

	// Медленный клиент отключен
	if !slowClient.isClosed {
		t.Fatal("Медленный клиент должен был быть закрыт из-за переполнения буфера")
	}

	if _, exists := hub.clients[slowClient]; exists {
		t.Fatal("Медленный клиент должен быть удален из Hub")
	}

	fmt.Println("Паттерн Backpressure успешно защитил сервер:")
	fmt.Printf("  • Быстрый клиент:   работает в штатном режиме (в буфере %d сообщ.)\n", len(fastClient.send))
	fmt.Printf("  • Медленный клиент: изолирован и отключен во избежание зависания Hub!\n")
}
```

## Под капотом

В `gorilla/websocket` при переполнении буфера сокета отправляют Close фрейм с кодом `1008 Policy Violation` или `1011 Internal Error` и закрывают TCP дескриптор, освобождая память сетевого стека ядра ОС.

## Подводные камни

Делать размер буфера канала бесконечным (`chan []byte` без лимита): медленный клиент сожрет все гигабайты оперативной памяти сервера, вызвав OOM Killer.

## На собеседовании

**Вопрос с собеседования:** «Какие еще стратегии обработки Slow Consumer существуют, помимо отключения клиента?»
**Ответ:** 1. **Coalescing (Объединение обновлений):** для биржевых котировок или GPS координат можно не отключать клиента, а перезаписывать старое значение новым (Conflated Queue). 2. **Sampling / Throttling:** прореживание сообщений (отправка каждого 10-го тика). 3. **Dynamic Buffer / Eviction:** вытеснение самых старых сообщений из очереди в пользу самых свежих (Ring Buffer).
