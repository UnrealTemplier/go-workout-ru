# Паттерн Hub/Client для чатов: потокобезопасная регистрация, отписка и широковещательная рассылка

## Условие

**[Паттерн Hub/Client (Чат)]**: Создай структуру `Hub`, которая хранит карту всех активных подключений (`map[*Client]bool`). Реализуй метод `Register` и `Broadcast` (рассылка сообщения всем клиентам).

## Теория

Классический паттерн Hub (Event Bus) для WebSocket:
- Центральный компонент `Hub` управляет множеством клиентов:
  - `clients map[*Client]bool`: реестр активных подключений.
  - `broadcast chan []byte`: канал сообщений, подлежащих рассылке всем участникам.
  - `register chan *Client`: канал запросов на добавление нового клиента.
  - `unregister chan *Client`: канал запросов на удаление отключившегося клиента.
- **Главный архитектурный принцип:** вся мутация мапы `clients` происходит строго **в одной горутине `hub.Run()`** через цикл `select`!
  - Это исключает необходимость мьютексов для мапы клиентов и предотвращает Data Races.

## Решение по шагам

1. Определите структуры `Client` и `Hub`.
2. Реализуйте каналы `broadcast`, `register`, `unregister`.
3. Запустите бесконечный цикл `select` в методе `hub.Run()`.
4. Протестируйте регистрацию 3 клиентов и широковещательную доставку.

## Код решения

**`hub_pattern_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type Client struct {
	ID   string
	send chan []byte
}

type Hub struct {
	clients    map[*Client]bool
	broadcast  chan []byte
	register   chan *Client
	unregister chan *Client
	quit       chan struct{}
}

func NewHub() *Hub {
	return &Hub{
		clients:    make(map[*Client]bool),
		broadcast:  make(chan []byte),
		register:   make(chan *Client),
		unregister: make(chan *Client),
		quit:       make(chan struct{}),
	}
}

func (h *Hub) Run() {
	for {
		select {
		case client := <-h.register:
			h.clients[client] = true
		case client := <-h.unregister:
			if _, ok := h.clients[client]; ok {
				delete(h.clients, client)
				close(client.send)
			}
		case message := <-h.broadcast:
			for client := range h.clients {
				select {
				case client.send <- message:
				default:
					// Клиент переполнен или отвалился
					close(client.send)
					delete(h.clients, client)
				}
			}
		case <-h.quit:
			for client := range h.clients {
				close(client.send)
				delete(h.clients, client)
			}
			return
		}
	}
}

func TestHubPattern(t *testing.T) {
	hub := NewHub()
	go hub.Run()

	c1 := &Client{ID: "client_1", send: make(chan []byte, 5)}
	c2 := &Client{ID: "client_2", send: make(chan []byte, 5)}
	c3 := &Client{ID: "client_3", send: make(chan []byte, 5)}

	hub.register <- c1
	hub.register <- c2
	hub.register <- c3

	var wg sync.WaitGroup
	wg.Add(3)

	received := make(map[string]string)
	var mu sync.Mutex

	readClient := func(c *Client) {
		defer wg.Done()
		msg := <-c.send
		mu.Lock()
		received[c.ID] = string(msg)
		mu.Unlock()
	}

	go readClient(c1)
	go readClient(c2)
	go readClient(c3)

	testMessage := []byte("Всем привет в чате!")
	hub.broadcast <- testMessage

	wg.Wait()

	if len(received) != 3 {
		t.Fatalf("Ожидалось 3 получателя, получено: %d", len(received))
	}

	close(hub.quit)
	fmt.Println("Паттерн Hub успешно разослал широковещательное сообщение всем 3 клиентам:")
	for id, txt := range received {
		fmt.Printf("  • [%s] принял: %s\n", id, txt)
	}
}
```

ℹ️ Однопоточный диспетчер Hub на каналах Go без блокировок мьютексами

## Под капотом

Паттерн «Actor Model на каналах»: концентрация всех операций над состоянием `map[*Client]bool` внутри одного горутинного цикла `select` гарантирует 100% потокобезопасность по принципу Go: *«Do not communicate by sharing memory; instead, share memory by communicating»*.

## Подводные камни

Блокирующая отправка `client.send <- message` без `select default`: если один клиент зависнет и не читает свой буфер, весь `Hub` заблокируется на этой строке, и остальные 10 000 клиентов перестанут получать сообщения!

## На собеседовании

**Вопрос с собеседования:** «Почему в высоконагруженных чатах (на миллионы пользователей) Hub не держат в одном процессе Go?»
**Ответ:** Один процесс ограничен памятью сервера и не выдержит более 500 000 – 1 000 000 открытых файловых дескрипторов. Для масштабирования используют распределенный Hub: соединения распределяются по нодам кластера через балансировщик, а синхронизация между хабами выполняется через Redis Pub/Sub или Apache Kafka.
