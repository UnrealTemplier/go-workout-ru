# Канонический паттерн Client (readPump и writePump): разделение ролей горутин чтения и записи

## Условие

**Потокобезопасный WS-клиент**: Чтобы избежать паники из упр. 486, создай для каждого подключения структуру `Client` с каналом `send chan []byte`. Запусти для каждого клиента ОДНУ горутину-писатель (которая читает из `send` и делает `WriteMessage`) и ОДНУ горутину-читатель. Это классический паттерн работы с WS в Go.

## Теория

Каноническая архитектура Gorilla WebSocket (Client Pumps):
- На каждое WebSocket подключение выделяется ровно **две горутины**:
  1. **`readPump` (Горутина-читатель):**
     - Единственная горутина, вызывающая `conn.ReadMessage()`.
     - Настраивает лимиты чтения, дедлайны (`SetReadDeadline`) и обработку Pong.
     - При ошибке чтения дерегистрирует клиента из Hub и закрывает канал `send`.
  2. **`writePump` (Горутина-писатель):**
     - Единственная горутина, вызывающая `conn.WriteMessage()`.
     - Читает сообщения из канала `send chan []byte`.
     - По тикеру отправляет периодические `PingMessage`.
- Эта архитектура гарантирует 0 Data Races и минимальное потребление ресурсов.

## Решение по шагам

1. Создайте структуру `PumpClient` с полями `conn` и `send`.
2. Реализуйте метод `readPump` с циклом чтения.
3. Реализуйте метод `writePump` с циклом записи из канала `send`.
4. Протестируйте передачу сообщений через пару горутин.

## Код решения

**`client_pumps_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"testing"
	"time"

	"github.com/gorilla/websocket"
)

type PumpClient struct {
	conn *websocket.Conn
	send chan []byte
}

func (c *PumpClient) readPump(onMessage func([]byte), onDone func()) {
	defer func() {
		c.conn.Close()
		onDone()
	}()

	c.conn.SetReadLimit(4096)
	_ = c.conn.SetReadDeadline(time.Now().Add(60 * time.Second))

	for {
		_, message, err := c.conn.ReadMessage()
		if err != nil {
			break
		}
		onMessage(message)
	}
}

func (c *PumpClient) writePump() {
	defer c.conn.Close()

	for message := range c.send {
		_ = c.conn.SetWriteDeadline(time.Now().Add(5 * time.Second))
		if err := c.conn.WriteMessage(websocket.TextMessage, message); err != nil {
			break
		}
	}
}

func TestClientPumpsPattern(t *testing.T) {
	var wg sync.WaitGroup
	wg.Add(1)

	var receivedOnServer string

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		upgrader := websocket.Upgrader{}
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}

		client := &PumpClient{
			conn: conn,
			send: make(chan []byte, 10),
		}

		go client.writePump()
		go client.readPump(func(msg []byte) {
			receivedOnServer = string(msg)
			// Отправляем ответ через writePump
			client.send <- []byte("ACK: " + string(msg))
			wg.Done()
		}, func() {})
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка подключения: %v", err)
	}
	defer clientConn.Close()

	// Клиент шлет сообщение
	_ = clientConn.WriteMessage(websocket.TextMessage, []byte("Тестовый запрос в readPump"))

	wg.Wait()

	// Читаем ответ, сформированный writePump
	_, ackMsg, _ := clientConn.ReadMessage()

	if receivedOnServer != "Тестовый запрос в readPump" {
		t.Fatalf("readPump не принял сообщение: %s", receivedOnServer)
	}

	expectedACK := "ACK: Тестовый запрос в readPump"
	if string(ackMsg) != expectedACK {
		t.Fatalf("writePump вернул неверный ACK: %s", string(ackMsg))
	}

	fmt.Printf("Паттерн readPump / writePump успешно протестирован:\n")
	fmt.Printf("  • readPump принял:  «%s»\n", receivedOnServer)
	fmt.Printf("  • writePump ответил: «%s»\n", string(ackMsg))
}
```

## Под капотом

Симметричное разделение на две горутины идеально согласуется с архитектурой ОС: сетевая карта и стек ядра Linux имеют независимые кольцевые буферы TX (передача) и RX (прием). Две горутины работают полностью параллельно без блокировок.

## Подводные камни

Закрывать сокет `conn.Close()` из нескольких мест одновременно: закрытие должно координироваться через `defer` в одной из горутин.

## На собеседовании

**Вопрос с собеседования:** «Сколько памяти потребляет 100 000 клиентов, работающих по схеме readPump + writePump?»
**Ответ:** Каждая горутина в Go требует минимум ~2 КБ стека. 100 000 клиентов \(\times\) 2 горутины = 200 000 горутин \(\approx 400\) МБ RAM на стек. Плюс буферы чтения/записи (по 4 КБ) \(\approx 800\) МБ. Суммарно около 1.2–1.5 ГБ оперативной памяти, что легко помещается даже на скромном виртуальном сервере.
