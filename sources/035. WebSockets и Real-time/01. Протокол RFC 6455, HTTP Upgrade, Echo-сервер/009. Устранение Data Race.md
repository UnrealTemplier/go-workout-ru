# Устранение Data Race: два подхода к потокобезопасной записи (sync.Mutex vs выделенный канал)

## Условие

**[Каверзный кейс]**: Конкурентная запись в WebSocket. Запусти 2 горутины, которые одновременно пытаются написать в один `conn`. Поймай панику/ошибку (горилла не позволяет конкурентную запись). Исправь, обернув соединение в мьютекс или создав канал для исходящих сообщений, а запись делать в одной горутине.

## Теория

Два паттерна обеспечения потокобезопасности записи в WebSocket:
1. **Подход 1: Защита через мьютекс (`SafeConn` с `sync.Mutex`):**
   - Просто реализовать, подходит для микросервисов с невысокой интенсивностью сообщений.
   - Метод: `mu.Lock(); defer mu.Unlock(); conn.WriteMessage(...)`.
2. **Подход 2: Изоляция в горутине-писателе (Actor/Channel Pattern):**
   - Золотой стандарт для высоконагруженных систем:
   - Соединением владеет ровно одна горутина `writePump`.
   - Все остальные горутины отправляют сообщения в буферизированный канал `send chan []byte`.
   - Нулевой contention мьютексов сокета.

## Решение по шагам

1. Создайте структуру-обертку `SafeWebSocketConn` с мьютексом.
2. Реализуйте метод `SafeWriteMessage`.
3. Запустите параллельную запись из 20 горутин.
4. Убедитесь в отсутствии ошибок и Data Race при запуске с `-race`.

## Код решения

**`safe_ws_write_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"testing"

	"github.com/gorilla/websocket"
)

type SafeWebSocketConn struct {
	conn *websocket.Conn
	mu   sync.Mutex
}

func NewSafeConn(c *websocket.Conn) *SafeWebSocketConn {
	return &SafeWebSocketConn{conn: c}
}

func (s *SafeWebSocketConn) WriteMessage(messageType int, data []byte) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.conn.WriteMessage(messageType, data)
}

func (s *SafeWebSocketConn) Close() error {
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.conn.Close()
}

func TestSafeConcurrentWrite(t *testing.T) {
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		upgrader := websocket.Upgrader{}
		c, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}

		safeConn := NewSafeConn(c)
		defer safeConn.Close()

		var wg sync.WaitGroup
		writers := 20

		for i := 0; i < writers; i++ {
			wg.Add(1)
			go func(id int) {
				defer wg.Done()
				_ = safeConn.WriteMessage(websocket.TextMessage, []byte(fmt.Sprintf("Сообщение %d", id)))
			}(i)
		}

		wg.Wait()
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка подключения: %v", err)
	}
	defer clientConn.Close()

	received := 0
	for received < 20 {
		_, _, err := clientConn.ReadMessage()
		if err != nil {
			break
		}
		received++
	}

	if received != 20 {
		t.Fatalf("Ожидалось 20 сообщений, получено: %d", received)
	}

	fmt.Printf("Потокобезопасная запись успешно защитила соединение: принято ровно %d из 20 сообщений без гонок!\n",
		received)
}
```

ℹ️ Потокобезопасная обертка SafeWebSocketConn с мьютексом

## Под капотом

Использование `sync.Mutex` полностью устраняет гонки на уровне рантайма Go, упорядочивая запись фреймов в сетевой сокет.

## Подводные камни

Удерживать мьютекс соединения во время долгих вычислений или форматирования JSON: сериализацию данных нужно делать ДО захвата мьютекса сокета.

## На собеседовании

**Вопрос с собеседования:** «Когда мьютекс уступает каналу send chan []byte?»
**Ответ:** При медленном канале связи клиента. Если сокет клиента медленно вычитывает данные, вызов `conn.WriteMessage` внутри критической секции мьютекса заблокирует его на десятки миллисекунд. Все остальные горутины сервиса выстроятся в очередь к этому мьютексу (Lock Contention). Буферизированный канал `send` позволяет мгновенно скинуть сообщение в память без блокировки вызывающей горутины.
