# Горизонтальное масштабирование подписок через Redis Pub/Sub: синхронизация событий между инстансами

## Условие

Интегрируйте subscriptions с **Redis Pub/Sub**, чтобы подписки работали across нескольких инстансов вашего GraphQL-сервера (горизонтальное масштабирование).

## Теория

Архитектура распределенных подписок в мульти-под кластере:
- Проблема:
  - Клиент А подключен по WebSocket к Инстансу №1.
  - Клиент Б подключен к Инстансу №2.
  - Мутация выполняется на Инстансе №3. Локальный Go-канал Инстанса №3 не видит клиентов на других подах!
- **Решение через Redis Pub/Sub:**
  1. Инстанс №3 выполняет мутацию и делает `PUBLISH user_events '{"id": "1", "name": "Анна"}'` в Redis.
  2. Все инстансы (№1, №2, №3) при старте держат долгоживущую подписку `SUBSCRIBE user_events`.
  3. Получив сообщение из Redis, каждый инстанс рассылает его только своим локально подключенным WebSocket клиентам.
  4. Линейная масштабируемость на сотни подов.

## Решение по шагам

1. Создайте модель брокера сообщений на базе Redis Pub/Sub.
2. Реализуйте метод `Publish` для публикации события в топик.
3. Реализуйте распределение события между двумя независимыми узлами.
4. Проверьте доставку клиенту на другом узле кластера.

## Код решения

**`redis_pubsub_cluster_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type ClusterEvent struct {
	Topic   string
	Payload string
}

// Мок распределенного Redis Pub/Sub брокера
type MockRedisPubSub struct {
	mu    sync.RWMutex
	nodes map[string]chan *ClusterEvent
}

func NewMockRedisPubSub() *MockRedisPubSub {
	return &MockRedisPubSub{nodes: make(map[string]chan *ClusterEvent)}
}

func (r *MockRedisPubSub) SubscribeNode(nodeID string) chan *ClusterEvent {
	r.mu.Lock()
	defer r.mu.Unlock()
	ch := make(chan *ClusterEvent, 10)
	r.nodes[nodeID] = ch
	return ch
}

func (r *MockRedisPubSub) Publish(event *ClusterEvent) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	for _, ch := range r.nodes {
		select {
		case ch <- event:
		default:
		}
	}
}

func TestRedisPubSubClustering(t *testing.T) {
	broker := NewMockRedisPubSub()

	// Инстанс сервера 1 в Kubernetes
	node1Events := broker.SubscribeNode("pod-srv-1")
	// Инстанс сервера 2 в Kubernetes
	node2Events := broker.SubscribeNode("pod-srv-2")

	// Клиент подключен к Pod 2
	var clientOnNode2Received string
	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()
		ev := <-node2Events
		clientOnNode2Received = ev.Payload
	}()

	// Мутация создания пользователя выполняется на Pod 3 (отправляет PUBLISH в Redis)
	broker.Publish(&ClusterEvent{
		Topic:   "user_created",
		Payload: `{"id": "usr_99", "name": "Ольга"}`,
	})

	wg.Wait()

	// Убеждаемся, что Pod 1 тоже получил событие из Redis
	select {
	case ev1 := <-node1Events:
		if ev1.Payload != `{"id": "usr_99", "name": "Ольга"}` {
			t.Fatalf("Pod 1 получил неверные данные: %s", ev1.Payload)
		}
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Pod 1 не получил событие")
	}

	if clientOnNode2Received != `{"id": "usr_99", "name": "Ольга"}` {
		t.Fatalf("Клиент на Pod 2 не получил событие: %s", clientOnNode2Received)
	}

	fmt.Println("Горизонтальное масштабирование подписок через Redis Pub/Sub подтверждено:")
	fmt.Printf("  • Событие опубликовано нодой Pod 3\n")
	fmt.Printf("  • Доставлено на Pod 1 и Pod 2: %s\n", clientOnNode2Received)
}
```

## Под капотом

В библиотеке `github.com/redis/go-redis/v9` метод `rdb.Subscribe(ctx, topic)` запускает фоновую горутину, постоянно читающую фреймы протокола RESP. Каждое сообщение демаршалится и пересылается локальным подписчикам через канал Go `pubsub.Channel()`.

## Подводные камни

Использовать Redis Pub/Sub для критических финансовых транзакций без гарантии доставки: у Redis Pub/Sub модель «Fire and Forget» (нет сохранения истории, если под упал, событие потеряно). Для гарантированной доставки используют Redis Streams или NATS JetStream.

## На собеседовании

**Вопрос с собеседования:** «Почему NATS или Redis Pub/Sub эффективнее, чем RabbitMQ или Kafka для доставки WebSocket сообщений?»
**Ответ:** RabbitMQ и Kafka создают тяжелые очереди с записью на диск, подтверждениями ACK и координацией оффсетов. Для real-time сообщений (чат, котировки) важна микросекундная латентность в памяти и минимальный оверхед. Легковесный брокер памяти (Redis Pub/Sub / NATS Core) обрабатывает более 1 000 000 сообщений в секунду с задержкой < 100 мкс.
