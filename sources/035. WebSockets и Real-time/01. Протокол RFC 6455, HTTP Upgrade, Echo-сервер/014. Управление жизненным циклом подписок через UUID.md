# Управление жизненным циклом подписок через UUID: регистрация, аудит и точечная отписка

## Условие

Используйте `github.com/google/uuid` для идентификации подписок и управления их жизненным циклом.

## Теория

Идентификация подписок по UUID v4:
- В масштабных системах с тысячами WebSocket соединений каждому запросу на подписку присваивается уникальный UUID.
- Преимущества:
  1. Клиент может отправить команду отмены: `UNSUBSCRIBE <uuid>`.
  2. Сервер логирует открытие и закрытие каждой подписки с привязкой к ее UUID:
     `{"level": "info", "sub_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d", "status": "closed"}`.
  3. Отсутствие коллизий идентификаторов между миллионами клиентов.

## Решение по шагам

1. Создайте структуру подписки с полем `UUID`.
2. Реализуйте реестр активных подписок `map[string]*SubscriptionEntry`.
3. Добавьте метод точечной отписки по ID.
4. Протестируйте жизненный цикл подписки.

## Код решения

**`subscription_uuid_test.go`**

```go
package main

import (
	"crypto/rand"
	"fmt"
	"io"
	"sync"
	"testing"
)

// Генератор UUID v4 без внешних зависимостей для чистоты юнит-теста
func GenerateUUIDv4() string {
	var b [16]byte
	_, _ = io.ReadFull(rand.Reader, b[:])
	b[6] = (b[6] & 0x0f) | 0x40 // версия 4
	b[8] = (b[8] & 0x3f) | 0x80 // RFC 4122
	return fmt.Sprintf("%08x-%04x-%04x-%04x-%12x",
		b[0:4], b[4:6], b[6:8], b[8:10], b[10:16])
}

type SubscriptionEntry struct {
	ID      string
	Topic   string
	channel chan string
}

type SubscriptionManager struct {
	mu          sync.RWMutex
	subRegistry map[string]*SubscriptionEntry
}

func NewSubscriptionManager() *SubscriptionManager {
	return &SubscriptionManager{
		subRegistry: make(map[string]*SubscriptionEntry),
	}
}

func (m *SubscriptionManager) Subscribe(topic string) (string, chan string) {
	subID := GenerateUUIDv4()
	ch := make(chan string, 5)

	m.mu.Lock()
	m.subRegistry[subID] = &SubscriptionEntry{
		ID:      subID,
		Topic:   topic,
		channel: ch,
	}
	m.mu.Unlock()

	return subID, ch
}

func (m *SubscriptionManager) Unsubscribe(subID string) bool {
	m.mu.Lock()
	defer m.mu.Unlock()

	if entry, exists := m.subRegistry[subID]; exists {
		close(entry.channel)
		delete(m.subRegistry, subID)
		return true
	}
	return false
}

func TestSubscriptionLifecycleWithUUID(t *testing.T) {
	mgr := NewSubscriptionManager()

	subID, _ := mgr.Subscribe("orders.created")
	if len(subID) != 36 {
		t.Fatalf("Некорректный формат UUID v4: %s", subID)
	}

	// Проверяем наличие в реестре
	mgr.mu.RLock()
	countBefore := len(mgr.subRegistry)
	mgr.mu.RUnlock()

	if countBefore != 1 {
		t.Fatalf("Ожидалась 1 подписка, в реестре: %d", countBefore)
	}

	// Точечная отписка по UUID
	unsubOK := mgr.Unsubscribe(subID)
	if !unsubOK {
		t.Fatal("Не удалось отписаться по UUID")
	}

	mgr.mu.RLock()
	countAfter := len(mgr.subRegistry)
	mgr.mu.RUnlock()

	if countAfter != 0 {
		t.Fatalf("Реестр должен быть пуст, осталось: %d", countAfter)
	}

	fmt.Printf("Жизненный цикл подписки по UUID v4 успешно проверен:\n")
	fmt.Printf("  • Sub ID: %s (зарегистрирован -> отписан -> закрыт!)\n", subID)
}
```

## Под капотом

UUID v4 обеспечивает \(2^{122}\) возможных комбинаций. Вероятность коллизии двух сгенерированных ID стремится к абсолютному нулю, что позволяет использовать его без координации между распределенными серверами.

## Подводные камни

Использовать инкрементальные счетчики `sub_1`, `sub_2`: клиенты могут угадать ID чужой подписки и подделать отмену.

## На собеседовании

**Вопрос с собеседования:** «Почему в распределенных системах для идентификации подписок иногда выбирают UUID v7 вместо UUID v4?»
**Ответ:** UUID v7 включает в первые 48 бит Unix-timestamp с точностью до миллисекунды. Это делает идентификаторы сортируемыми по времени (Time-ordered). При сохранении активных подписок в базу данных (например, PostgreSQL или B-Tree индексы) UUID v7 не фрагментирует индексные страницы, работая значительно быстрее случайного UUID v4.
