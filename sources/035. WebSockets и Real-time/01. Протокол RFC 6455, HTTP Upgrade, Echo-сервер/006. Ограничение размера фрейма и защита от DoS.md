# Ограничение размера фрейма и защита от DoS: SetReadLimit(1024) и обнаружение ErrReadLimit

## Условие

**[Каверзный кейс]**: У WebSocket-соединения есть лимиты на чтение и запись. Установи `conn.SetReadLimit(1024)` и отправь сообщение размером 2KB. Поймай ошибку и разрыв соединения.

## Теория

Защита сервера от атак переполнения памяти (OOM DoS):
- По умолчанию в WebSocket размер сообщения может достигать гигабайт, если клиент отправляет гигантский фрейм.
- `conn.SetReadLimit(maxBytes)`:
  - Устанавливает максимальный объем полезной нагрузки (Payload) для одного сообщения.
  - Если клиент отправляет сообщение размером больше `maxBytes`, библиотека прерывает чтение, немедленно отправляет клиенту Close-фрейм `1009 Message Too Big` и возвращает ошибку чтения.
- Это обязательный защитный механизм при работе с внешними клиентами в интернете.

## Решение по шагам

1. В обработчике установите `conn.SetReadLimit(1024)` (1 КБ).
2. На клиенте сформируйте payload размером 2048 байт (2 КБ).
3. Попытайтесь прочитать ответ на сервере.
4. Убедитесь в возникновении ошибки превышения лимита и разрыве соединения.

## Код решения

**`ws_read_limit_test.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/gorilla/websocket"
)

func TestWebSocketReadLimit(t *testing.T) {
	serverErrChan := make(chan error, 1)

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		upgrader := websocket.Upgrader{}
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer conn.Close()

		// Жесткий лимит: не более 1024 байт (1 КБ)
		conn.SetReadLimit(1024)

		_, _, readErr := conn.ReadMessage()
		serverErrChan <- readErr
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка Dial: %v", err)
	}
	defer clientConn.Close()

	// Отправляем сообщение 2048 байт (превышает лимит в 2 раза!)
	oversizedPayload := bytes.Repeat([]byte("A"), 2048)
	err = clientConn.WriteMessage(websocket.TextMessage, oversizedPayload)
	if err != nil {
		t.Fatalf("Ошибка записи клиентом: %v", err)
	}

	serverErr := <-serverErrChan
	if serverErr == nil {
		t.Fatal("Ожидалась ошибка сервера из-за превышения SetReadLimit")
	}

	// Читаем CloseMessage со стороны клиента
	_, _, clientReadErr := clientConn.ReadMessage()
	if clientReadErr == nil {
		t.Fatal("Ожидался разрыв соединения на клиенте")
	}

	fmt.Printf("Атака большим payload успешно заблокирована!\n")
	fmt.Printf("  • Ошибка на сервере: %v\n", serverErr)
	fmt.Printf("  • Ошибка на клиенте: %v\n", clientReadErr)
}
```

ℹ️ Установка жесткого лимита чтения для предотвращения атак исчерпания памяти

## Под капотом

Внутри `gorilla/websocket` счетчик байтов инкрементируется по мере чтения чанков сокета. Как только `r.remaining < 0`, парсер фрейма мгновенно переходит в терминальное состояние ошибки, не аллоцируя память под оставшуюся часть сообщения.

## Подводные камни

Устанавливать `SetReadLimit` слишком маленьким без учета служебных JSON-полей: если клиент пришлет валидный аватар или base64, превышающий 1024 байта, он получит неожиданный дисконнект.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между ReadBufferSize в Upgrader и SetReadLimit в Conn?»
**Ответ:** `ReadBufferSize` — это размер кольцевого буфера `bufio.Reader` для системных вызовов `read()` (обычно 4 КБ). `SetReadLimit` — это максимальный суммарный размер одного логического WebSocket-сообщения (может быть 64 КБ или 1 МБ), которое может собираться из множества мелких 4-килобайтных TCP-пакетов.
