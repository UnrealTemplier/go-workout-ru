# Шина событий Pub/Sub на каналах Go: уведомление подписчиков о мутациях сущностей

## Условие

Реализуйте pub/sub систему на каналах Go: когда создается пользователь (в mutation), отправляйте его в канал, из которого читают все подписчики.

## Теория

Связка Mutation \(\to\) Event Bus \(\to\) Subscription:
- Мутация `createUser`:
  1. Выполняет сохранение в базу данных / память.
  2. Публикует созданную сущность в общую шину событий: `broker.Publish(newUser)`.
- Подписчики подписки `userCreated`:
  - Каждый подписчик регистрирует свой персональный канал `chan *User`.
  - Шина рассылает событие по всем зарегистрированным каналам.
  - Это реализует реактивное обновление интерфейсов пользователей в реальном времени.

## Решение по шагам

1. Создайте потокобезопасный брокер `UserEventBroker`.
2. Реализуйте методы `Subscribe` и `Publish`.
3. Смоделируйте создание пользователя в мутации.
4. Проверьте мгновенное получение события двумя независимыми подписчиками.

## Код решения

**`pubsub_event_bus_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type UserEvent struct {
	ID   string
	Name string
}

type EventBroker struct {
	mu   sync.RWMutex
	subs map[chan *UserEvent]struct{}
}

func NewEventBroker() *EventBroker {
	return &EventBroker{
		subs: make(map[chan *UserEvent]struct{}),
	}
}

func (b *EventBroker) Subscribe() (chan *UserEvent, func()) {
	ch := make(chan *UserEvent, 5)
	b.mu.Lock()
	b.subs[ch] = struct{}{}
	b.mu.Unlock()

	unsubscribe := func() {
		b.mu.Lock()
		defer b.mu.Unlock()
		if _, ok := b.subs[ch]; ok {
			delete(b.subs, ch)
			close(ch)
		}
	}

	return ch, unsubscribe
}

func (b *EventBroker) Publish(u *UserEvent) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for ch := range b.subs {
		select {
		case ch <- u:
		default:
			// Защита от переполнения буфера
		}
	}
}

func TestPubSubEventBus(t *testing.T) {
	broker := NewEventBroker()

	sub1, unsub1 := broker.Subscribe()
	defer unsub1()

	sub2, unsub2 := broker.Subscribe()
	defer unsub2()

	// Имитация вызова Mutation createUser(...)
	createdUser := &UserEvent{ID: "usr_pub_42", Name: "Катерина"}
	broker.Publish(createdUser)

	msg1 := <-sub1
	msg2 := <-sub2

	if msg1.ID != "usr_pub_42" || msg2.ID != "usr_pub_42" {
		t.Fatalf("Ошибка доставки событий подписчикам: %+v, %+v", msg1, msg2)
	}

	fmt.Println("Шина событий Pub/Sub успешно разослала мутацию всем подписчикам:")
	fmt.Printf("  • Подписчик 1 принял: %s (ID=%s)\n", msg1.Name, msg1.ID)
	fmt.Printf("  • Подписчик 2 принял: %s (ID=%s)\n", msg2.Name, msg2.ID)
}
```

## Под капотом

Идиома возврата замыкания `unsubscribe func()` инкапсулирует логику отписки и удаление из внутренней мапы, предотвращая утечки неиспользуемых каналов.

## Подводные камни

Закрывать канал дважды при отписке: вызов `close()` на уже закрытом канале приводит к фатальной панике в Go.

## На собеседовании

**Вопрос с собеседования:** «Почему мутация должна публиковать событие в шину только ПОСЛЕ успешного коммита транзакции в базу?»
**Ответ:** Если опубликовать событие до коммита, а транзакция базы данных откатится (Rollback due to conflict), подписчики получат «фантомное» событие о пользователе, которого в базе данных не существует. Это критическое нарушение консистентности.
