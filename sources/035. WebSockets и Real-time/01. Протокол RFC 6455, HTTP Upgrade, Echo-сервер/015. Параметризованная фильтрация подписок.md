# Параметризованная фильтрация подписок: аргументы схемы userCreated(role: ADMIN) и предикаты

## Условие

Реализуйте **фильтрацию подписок**: клиент может подписаться только на события определенного типа (`userCreated(role: ADMIN)`).

## Теория

Фильтрация событий на стороне сервера (Server-side Event Filtering):
- В SDL:
```graphql
enum Role {
  ADMIN
  USER
  GUEST
}

type Subscription {
  userCreated(role: Role): User!
}
```
- Резолвер принимает аргумент `role *Role`:
  - Если `role == nil`: клиент получает всех создаваемых пользователей.
  - Если `role != nil`: сервер проверяет `if user.Role == *role` перед отправкой в канал клиента.
- **Плюсы:** мобильный клиент не тратит батарею и трафик на вычитывание нерелевантных событий.

## Решение по шагам

1. Создайте тип `Role` и сущность `User`.
2. Реализуйте функцию фильтрации событий подписки.
3. Протестируйте подписку с фильтром `role = ADMIN`.
4. Убедитесь, что события пользователей с ролью `USER` отфильтровываются.

## Код решения

**`subscription_filtering_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type Role string

const (
	RoleAdmin Role = "ADMIN"
	RoleUser  Role = "USER"
)

type User struct {
	ID   string
	Name string
	Role Role
}

func FilteredUserSubscription(ctx context.Context, sourceChan <-chan *User, targetRole *Role) <-chan *User {
	out := make(chan *User, 5)

	go func() {
		defer close(out)
		for {
			select {
			case <-ctx.Done():
				return
			case u, ok := <-sourceChan:
				if !ok {
					return
				}
				// Предикат фильтрации
				if targetRole == nil || u.Role == *targetRole {
					out <- u
				}
			}
		}
	}()

	return out
}

func TestSubscriptionFiltering(t *testing.T) {
	sourceChan := make(chan *User, 10)
	defer close(sourceChan)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	adminFilter := RoleAdmin
	adminStream := FilteredUserSubscription(ctx, sourceChan, &adminFilter)

	// Публикуем обычного пользователя и администратора
	sourceChan <- &User{ID: "u1", Name: "Обычный пользователь", Role: RoleUser}
	sourceChan <- &User{ID: "u2", Name: "Главный Администратор", Role: RoleAdmin}

	select {
	case received := <-adminStream:
		if received.Role != RoleAdmin || received.Name != "Главный Администратор" {
			t.Fatalf("Фильтр пропустил неверного пользователя: %+v", received)
		}
		fmt.Printf("Фильтр подписки успешно отработал: принят только [%s] с ролью %s!\n",
			received.Name, received.Role)
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Таймаут ожидания отфильтрованного события")
	}

	// Убеждаемся, что других сообщений в потоке нет
	select {
	case extra := <-adminStream:
		t.Fatalf("Лишнее сообщение в потоке: %+v", extra)
	case <-time.After(50 * time.Millisecond):
		// Корректно: обычный пользователь отфильтрован
	}
}
```

ℹ️ Серверная фильтрация потока событий подписки по заданному предикату

**`Терминал`**

```bash
go test -v subscription_filtering_test.go
# Вывод:
# === RUN   TestSubscriptionFiltering
# Фильтр подписки успешно отработал: принят только [Главный Администратор] с ролью ADMIN!
# --- PASS: TestSubscriptionFiltering (0.00s)
# PASS
```

## Под капотом

Фильтрация в отдельной промежуточной горутине изолирует логику каждого подписчика: медленный подписчик не замедляет общую шину событий благодаря буферизации выходного канала.

## Подводные камни

Фильтровать события на клиенте: если пересылать все приватные события администраторов на телефоны обычных пользователей, вскрытие трафика позволит прочитать чужие данные.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать фильтрацию подписок, если в кластере 100 000 подписчиков с разными сложными фильтрами?»
**Ответ:** Применять потоковые фильтры на базе **Inverted Index (Обратный индекс предикатов)** или специализированные движки подписок (Redis Pub/Sub с каналами вида `events.user_created.ADMIN`, Apache Kafka Consumer Groups с partition-ключами). Событие направляется только в тот топик брокера, на который подписаны соответствующие клиенты.
