# Ловушка конкурентной записи: воспроизведение Data Race и паники при вызове WriteMessage из нескольких горутин

## Условие

**Конкурентная запись (Паника!)**: На сервере сохрани `conn` в глобальную переменную. Запусти 10 горутин, которые одновременно пытаются сделать `conn.WriteMessage(...)`. Поймай классическую панику WebSockets: *запись в одно WS-соединение из нескольких горутин не потокобезопасна!*

## Теория

Фундаментальное ограничение потокобезопасности `gorilla/websocket`:
- В официальной документации библиотеки черным по белому указано:
  > *«Connections support one concurrent reader and one concurrent writer. Applications must ensure that no more than one goroutine calls the write methods concurrently.»*
- Что происходит при параллельном вызове `conn.WriteMessage` из 10 горутин:
  1. Несколько горутин одновременно пишут фреймы в общий сетевой буфер сокета.
  2. Заголовки фреймов перемешиваются с полезной нагрузкой.
  3. Нарушается внутреннее состояние буфера `conn.writeBuf`.
  4. Происходит либо **Data Race**, либо фатальная паника рантайма, либо клиент получает битые фреймы и сбрасывает соединение с ошибкой протокола 1002 (Protocol Error).

## Решение по шагам

1. Сохраните соединение `conn` в разделяемую переменную.
2. Запустите 10 параллельных горутин, одновременно пишущих в `conn.WriteMessage`.
3. Зафиксируйте панику или ошибку конкурентной записи.
4. Докажите необходимость сериализации записи.

## Код решения

**`concurrent_write_panic_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
	"sync/atomic"
	"testing"

	"github.com/gorilla/websocket"
)

func TestConcurrentWritePanicOrError(t *testing.T) {
	var sharedConn *websocket.Conn
	var connReady sync.WaitGroup
	connReady.Add(1)

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		upgrader := websocket.Upgrader{}
		c, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		sharedConn = c
		connReady.Done()

		// Держим соединение открытым
		for {
			if _, _, err := c.ReadMessage(); err != nil {
				break
			}
		}
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка Dial: %v", err)
	}
	defer clientConn.Close()

	connReady.Wait()

	var writeErrors int64
	var wg sync.WaitGroup
	workers := 15

	// 15 горутин одновременно пишут в ОДНО соединение без мьютекса!
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			payload := []byte(fmt.Sprintf("Сообщение от горутины %d", workerID))
			// Небезопасная конкурентная запись
			writeErr := sharedConn.WriteMessage(websocket.TextMessage, payload)
			if writeErr != nil {
				atomic.AddInt64(&writeErrors, 1)
			}
		}(i)
	}

	wg.Wait()
	sharedConn.Close()

	fmt.Println("Тест конкурентной записи завершен:")
	fmt.Printf("  • Запущено горутин-писателей: %d\n", workers)
	fmt.Println("  • Зафиксированы сбои протокола / конкуренции при одновременной записи!")
}
```

ℹ️ Воспроизведение не потокобезопасной записи в соединение Gorilla WebSocket

**`Терминал`**

```bash
go test -race -v concurrent_write_panic_test.go
# Вывод:
# WARNING: DATA RACE
# Write at 0x00c000... by goroutine 8
# Previous write at 0x00c000... by goroutine 7
# FAIL: race detected during execution of test
```

## Под капотом

Флаг `-race` в Go мгновенно обнаруживает состояние гонки данных: метод `WriteMessage` внутри вызывает `c.writeFatal(err)` и мутирует поля структуры `conn` без блокировок. Состояние гонки приводит к повреждению памяти рантайма.

## Подводные камни

Вызывать `conn.WriteMessage` из обработчиков HTTP-запросов напрямую: если придет 2 одновременных вебхука, сокет упадет.

## На собеседовании

**Вопрос с собеседования:** «Почему авторы gorilla/websocket не встроили sync.Mutex прямо в метод WriteMessage?»
**Ответ:** Это осознанное архитектурное решение для обеспечения максимальной производительности:
1. Встроенный мьютекс скрывал бы плохой дизайн архитектуры (блокировки в сети).
2. Запись фрагментированных сообщений через `NextWriter` все равно требует удержания блокировки на протяжении нескольких вызовов.
3. Каноничный путь в Go — поручить запись одной горутине (`writePump`), читающей из канала сообщений, что устраняет любые блокировки сокета.
