# WebSocket Echo-сервер: дуплексное чтение и отправка сообщений через ReadMessage и WriteMessage

## Условие

Реализуй Echo-сервер: в бесконечном цикле читай сообщение от клиента (`conn.ReadMessage`) и отправляй его обратно (`conn.WriteMessage`).

## Теория

Анатомия дуплексного обмена сообщениями в WebSocket:
- В отличие от байтовых потоков TCP (`net.Conn`), WebSocket — это протокол, ориентированный на **сообщения (Frame-based)**:
  - `conn.ReadMessage()` блокирует горутину до получения цельного сообщения (даже если оно фрагментировано на уровне нескольких фреймов RFC 6455).
  - Возвращает: `messageType int` (`TextMessage`, `BinaryMessage`, `CloseMessage`, `PingMessage`, `PongMessage`), срез `[]byte` и ошибку.
  - `conn.WriteMessage(messageType, payload)` сериализует сообщение во фреймы и отправляет в сокет.
- Цикл эхо-сервера обязан обрабатывать завершение соединения: при отключении клиента `ReadMessage` вернет ошибку (например, `websocket.CloseNormalClosure` или `io.EOF`), и цикл должен завершиться с освобождением ресурсов.

## Решение по шагам

1. Создайте обработчик с бесконечным циклом чтения сообщений.
2. Проверьте тип полученного сообщения (Text / Binary).
3. Отправьте клиенту идентичный payload через `conn.WriteMessage`.
4. Обработайте ошибку разрыва соединения и обеспечьте корректный выход из цикла.

## Код решения

**`echo_server_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/gorilla/websocket"
)

func echoHandler(w http.ResponseWriter, r *http.Request) {
	upgrader := websocket.Upgrader{
		CheckOrigin: func(r *http.Request) bool { return true },
	}
	conn, err := upgrader.Upgrade(w, r, nil)
	if err != nil {
		return
	}
	defer conn.Close()

	for {
		messageType, message, err := conn.ReadMessage()
		if err != nil {
			// Ошибка чтения возникает при закрытии соединения клиентом
			if websocket.IsUnexpectedCloseError(err, websocket.CloseGoingAway, websocket.CloseNormalClosure) {
				fmt.Printf("Неожиданное закрытие соединения: %v\n", err)
			}
			break
		}

		// Отправляем эхо-ответ
		err = conn.WriteMessage(messageType, message)
		if err != nil {
			break
		}
	}
}

func TestEchoServer(t *testing.T) {
	server := httptest.NewServer(http.HandlerFunc(echoHandler))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	conn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка подключения к серверу: %v", err)
	}
	defer conn.Close()

	testPayload := "Привет, Gopher! Тест Echo сервера."
	err = conn.WriteMessage(websocket.TextMessage, []byte(testPayload))
	if err != nil {
		t.Fatalf("Ошибка отправки: %v", err)
	}

	msgType, respBytes, err := conn.ReadMessage()
	if err != nil {
		t.Fatalf("Ошибка получения эхо-ответа: %v", err)
	}

	if msgType != websocket.TextMessage || string(respBytes) != testPayload {
		t.Fatalf("Несовпадение ответа: got %s, want %s", string(respBytes), testPayload)
	}

	fmt.Printf("Echo-сервер успешно вернул сообщение: «%s»\n", string(respBytes))
}
```

## Под капотом

`conn.ReadMessage()` скрывает низкоуровневый разбор маски фреймов (Frame Masking). По спецификации RFC 6455 все фреймы от клиента к серверу ОБЯЗАНЫ маскироваться случайным 4-байтным ключом с помощью операции XOR. `gorilla/websocket` автоматически снимает эту маску на лету в оптимизированном цикле.

## Подводные камни

Игнорировать ошибку `conn.ReadMessage()` и не делать `break`: горутина войдет в бесконечный горячий цикл, пожирая 100% CPU ядра при закрытом сокете.

## На собеседовании

**Вопрос с собеседования:** «Почему клиентские WebSocket фреймы обязательно маскируются по стандарту RFC 6455, а серверные — нет?»
**Ответ:** Маскирование клиентских фреймов защищает от атаки отравления кэша промежуточных прозрачных прокси-серверов (Proxy Cache Poisoning). Если бы маскирования не было, злоумышленник через JavaScript в браузере мог бы сформировать тело фрейма, имитирующее чужой HTTP-ответ, и закэшировать его на общем корпоративном прокси для других пользователей сети.
