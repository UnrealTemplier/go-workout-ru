# Фильтрация подписок по статусу (status: ACTIVE): предикаты на уровне шины событий и резолвера

## Условие

Реализуй **subscription filtering**: клиент подписывается `subscription { userCreated(status: ACTIVE) { ... } }`. Только пользователи со статусом `ACTIVE` доставляются. Фильтр применяй на уровне event bus или resolver'а.

## Теория

Многоуровневая фильтрация подписок:
- Вариант 1 (На уровне резолвера):
  - Резолвер вычитывает все события и проверяет `if u.Status == targetStatus`.
  - Просто реализовать, но тратит CPU на отсеивание мусорных событий.
- Вариант 2 (На уровне Event Bus):
  - Клиент регистрируется в специализированный топик: `users.created.ACTIVE`.
  - Шина отправляет событие только в соответствующий топик.
  - Высокая производительность при миллионах событий.

## Решение по шагам

1. Создайте сущность с полем `Status`.
2. Реализуйте функцию фильтрации потока событий.
3. Протестируйте подписку на статус `ACTIVE`.
4. Убедитесь, что события со статусом `PENDING` или `BLOCKED` не доходят до клиента.

## Код решения

**`status_filter_sub_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type UserStatus string

const (
	StatusActive  UserStatus = "ACTIVE"
	StatusPending UserStatus = "PENDING"
	StatusBlocked UserStatus = "BLOCKED"
)

type StatusUser struct {
	ID     string
	Name   string
	Status UserStatus
}

func FilterByStatus(ctx context.Context, in <-chan *StatusUser, target UserStatus) <-chan *StatusUser {
	out := make(chan *StatusUser, 5)
	go func() {
		defer close(out)
		for {
			select {
			case <-ctx.Done():
				return
			case u, ok := <-in:
				if !ok {
					return
				}
				if u.Status == target {
					out <- u
				}
			}
		}
	}()
	return out
}

func TestSubscriptionStatusFilter(t *testing.T) {
	inEvents := make(chan *StatusUser, 5)
	defer close(inEvents)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	activeStream := FilterByStatus(ctx, inEvents, StatusActive)

	// Шлем пользователей разных статусов
	inEvents <- &StatusUser{ID: "1", Name: "Иван", Status: StatusPending}
	inEvents <- &StatusUser{ID: "2", Name: "Сергей", Status: StatusActive}
	inEvents <- &StatusUser{ID: "3", Name: "Петр", Status: StatusBlocked}

	select {
	case received := <-activeStream:
		if received.Status != StatusActive || received.Name != "Сергей" {
			t.Fatalf("Фильтр пропустил не того пользователя: %+v", received)
		}
		fmt.Printf("Фильтр статуса ACTIVE успешно отобрал нужного пользователя: %s (%s)\n",
			received.Name, received.Status)
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Таймаут ожидания события")
	}
}
```

ℹ️ Предикатная фильтрация потока событий подписки по значению статуса

## Под капотом

Проверка на равенство констант типа string/enum выполняется за доли наносекунды, гарантируя нулевые аллокации памяти при фильтрации.

## Подводные камни

Блокировать входящий канал `inEvents`, если буфер выходного канала `out` переполнен: для высоконагруженных очередей в `out <- u` добавляют `select default`.

## На собеседовании

**Вопрос с собеседования:** «Как фильтровать подписки на уровне Redis Pub/Sub без передачи нерелевантных событий по сети?»
**Ответ:** Использовать структурированные имена топиков (Hierarchical Channel Names): вместо общего топика `users` публиковать в `users.status.ACTIVE`. Клиент с фильтром `status: ACTIVE` подписывается напрямую на топик `users.status.ACTIVE`, полностью устраняя холостой сетевой трафик между Redis и приложением.
