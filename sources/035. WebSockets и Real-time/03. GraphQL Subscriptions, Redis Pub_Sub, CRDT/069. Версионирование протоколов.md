# Версионирование протоколов через Sec-WebSocket-Protocol: поддержка chat.v1 и chat.v2

## Условие

Используйте **WebSocket subprotocols** (`Sec-WebSocket-Protocol`), если ваше приложение поддерживает несколько версий протокола.

## Теория

Согласование версий API через Subprotocols:
- Проблема: мобильные приложения старых версий (v1) ожидают плоский JSON, а новые версии (v2) передают сжатый Protobuf.
- Заголовок `Sec-WebSocket-Protocol`:
  - Клиент отправляет список поддерживаемых версий: `Sec-WebSocket-Protocol: chat.v2, chat.v1`.
  - Сервер сопоставляет со своим списком `Upgrader.Subprotocols` и выбирает наивысшую поддерживаемую версию.
  - Согласованная версия возвращается клиенту в заголовке ответа 101.
- Обеспечивает бесшовную плавную миграцию клиентов без поломки обратной совместимости.

## Решение по шагам

1. Настройте `Upgrader` со списком версий `chat.v2`, `chat.v1`.
2. Реализуйте проверку согласованной версии в коде хендлера.
3. Подключите клиента с запросом версий.
4. Протестируйте согласование оптимальной версии.

## Код решения

**`subprotocols_versioning_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/gorilla/websocket"
)

func TestSubprotocolVersioning(t *testing.T) {
	upgrader := websocket.Upgrader{
		Subprotocols: []string{"chat.v2", "chat.v1"},
	}

	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer conn.Close()

		protocol := conn.Subprotocol()
		_ = conn.WriteMessage(websocket.TextMessage, []byte("Согласованная версия: "+protocol))
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")

	// Клиент поддерживает и v1, и v2
	dialer := websocket.Dialer{
		Subprotocols: []string{"chat.v1", "chat.v2"},
	}

	conn, _, err := dialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка Dial: %v", err)
	}
	defer conn.Close()

	negotiated := conn.Subprotocol()
	if negotiated != "chat.v2" && negotiated != "chat.v1" {
		t.Fatalf("Несогласованный субпротокол: %s", negotiated)
	}

	_, msg, _ := conn.ReadMessage()
	fmt.Printf("Согласование версий API успешно отработало:\n")
	fmt.Printf("  • Выбранный сервером субпротокол: %s\n", negotiated)
	fmt.Printf("  • Ответ сервера: «%s»\n", string(msg))
}
```

ℹ️ Согласование версий субпротокола chat.v1/chat.v2 при рукопожатии

**`Терминал`**

```bash

# Вывод:

# Согласование версий API успешно отработало:
#   • Выбранный сервером субпротокол: chat.v2

```

## Под капотом

Сервер сопоставляет субпротоколы в порядке приоритета своего массива `Upgrader.Subprotocols`, отдавая предпочтение более свежей версии `chat.v2`.

## Подводные камни

Не проверять результат `conn.Subprotocol()` в коде обработчика: сервер должен знать, в каком формате общаться с подключенным клиентом.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если клиент запросил субпротокол, которого нет в списке сервера?»
**Ответ:** По спецификации RFC 6455 сервер просто оставляет заголовок `Sec-WebSocket-Protocol` в ответе пустым (соединение открывается по умолчанию без субпротокола). Однако если клиент в браузере строго требовал субпротокол (`new WebSocket(url, 'custom-proto')`), браузер немедленно разорвет соединение с ошибкой протокола.
