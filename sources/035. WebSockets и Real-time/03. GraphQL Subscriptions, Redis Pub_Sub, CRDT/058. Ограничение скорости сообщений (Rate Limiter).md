# Ограничение скорости сообщений (Rate Limiter): скользящее окно и защита от DoS атак

## Условие

Добавьте **rate limiting** для WebSocket-сообщений: клиент не может отправлять больше N сообщений в секунду (защищает от спама и DoS).

## Теория

Защита от флуда в реальном времени (Sliding Window Counter):
- Лимит: не более \(N\) сообщений за скользящий интервал 1 секунда.
- При каждом входящем сообщении:
  1. Время события записывается в циклический буфер.
  2. События старше 1 секунды отбрасываются.
  3. Если в буфере \(> N\) событий:
     - Сообщение игнорируется.
     - Клиенту отправляется предупреждение: `{"error": "RATE_LIMIT_EXCEEDED"}`.
     - При повторных нарушениях сокет разрывается.

## Решение по шагам

1. Создайте структуру лимитера со скользящим окном.
2. Реализуйте проверку порога \(N\) сообщений.
3. Протестируйте отсечение спама при интенсивной отправке.
4. Убедитесь в восстановлении лимита по истечении секунды.

## Код решения

**`sliding_window_limiter_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type SlidingWindowLimiter struct {
	mu         sync.Mutex
	limit      int
	window     time.Duration
	timestamps []time.Time
}

func NewSlidingWindowLimiter(limit int, window time.Duration) *SlidingWindowLimiter {
	return &SlidingWindowLimiter{
		limit:  limit,
		window: window,
	}
}

func (l *SlidingWindowLimiter) Allow() bool {
	l.mu.Lock()
	defer l.mu.Unlock()

	now := time.Now()
	cutoff := now.Add(-l.window)

	// Очищаем устаревшие таймстампы
	validIdx := 0
	for _, ts := range l.timestamps {
		if ts.After(cutoff) {
			l.timestamps[validIdx] = ts
			validIdx++
		}
	}
	l.timestamps = l.timestamps[:validIdx]

	if len(l.timestamps) < l.limit {
		l.timestamps = append(l.timestamps, now)
		return true
	}
	return false
}

func TestSlidingWindowRateLimiter(t *testing.T) {
	// Лимит: 5 сообщений за окно 50 миллисекунд
	limiter := NewSlidingWindowLimiter(5, 50*time.Millisecond)

	passed := 0
	blocked := 0

	// Пытаемся отправить 8 сообщений подряд
	for i := 1; i <= 8; i++ {
		if limiter.Allow() {
			passed++
		} else {
			blocked++
		}
	}

	if passed != 5 || blocked != 3 {
		t.Fatalf("Ошибка лимитирования: passed=%d, blocked=%d", passed, blocked)
	}

	// Ждем окончания окна
	time.Sleep(60 * time.Millisecond)

	// Должно снова разрешить отправку
	if !limiter.Allow() {
		t.Fatal("Лимитер должен восстановить лимит после истечения окна")
	}

	fmt.Println("Sliding Window Rate Limiter успешно защитил сокет:")
	fmt.Printf("  • Пропущено в окне: %d\n", passed)
	fmt.Printf("  • Заблокировано спама: %d\n", blocked)
	fmt.Println("  • Лимит успешно восстановлен после паузы!")
}
```

## Под капотом

Алгоритм скользящего окна устраняет недостаток фиксированного окна (Fixed Window Reset Attack), при котором атакующий шлет 2x лимита на границе двух секунд.

## Подводные камни

Хранить срез `timestamps` без очистки: память среза будет расти бесконечно. Срез должен обрезаться `l.timestamps = l.timestamps[:validIdx]`.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать распределенный Rate Limiter для WebSockets на кластере из 50 нод?»
**Ответ:** Использовать Redis с Lua-скриптом на основе Sliding Window Logs или Redis Cell (модуль generic cell rate algorithm). При каждом запросе клиентский сокет выполняет `EVALSHA` в локальную реплику Redis. Это обеспечивает общий лимит на пользователя независимо от того, к какому поду он подключился.
