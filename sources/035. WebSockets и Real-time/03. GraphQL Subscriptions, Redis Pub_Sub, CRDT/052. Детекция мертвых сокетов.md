# Детекция мертвых сокетов: периодическая отправка Ping сервером раз в 10 секунд и SetPongHandler

## Условие

**Контроль мертвых соединений (Heartbeats/Ping-Pong)**: Если у клиента пропал интернет без явного закрытия вкладки браузера, сервер может держать сокет открытым бесконечно (утечка ресурсов). Настройте механизм пингов на сервере:
* Сервер должен периодически (например, раз в 10 секунд) отправлять клиенту PING-кадр с помощью `conn.WriteControl(websocket.PingMessage, ...)`.
* Настройте обработчик PONG-сообщений от клиента с помощью `conn.SetPongHandler`. Если от клиента не пришел PONG в течение заданного интервала ожидания (read deadline), сервер должен принудительно разорвать соединение.

## Теория

Защита от утечки сокетов (Half-Open TCP Detection):
- Интервал проверки:
  - Сервер отправляет PING каждые 10 секунд.
  - Окно ожидания PONG: 15 секунд (`readDeadline = time.Now().Add(15 * time.Second)`).
  - При получении PONG дедлайн обновляется.
  - Если за 15 секунд ни одного сообщения или PONG не получено, сокет принудительно разрывается.

## Решение по шагам

1. Настройте цикл отправки PING кадров через `WriteControl`.
2. Зарегистрируйте `SetPongHandler` с продлением дедлайна.
3. Проверьте разрыв зависшего сокета.
4. Убедитесь в освобождении ресурсов.

## Код решения

**`server_ping_dead_detection_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
	"time"

	"github.com/gorilla/websocket"
)

func TestDeadSocketDetection(t *testing.T) {
	pingInterval := 25 * time.Millisecond
	pongTimeout := 50 * time.Millisecond

	socketDead := make(chan struct{})

	upgrader := websocket.Upgrader{}
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer func() {
			conn.Close()
			close(socketDead)
		}()

		_ = conn.SetReadDeadline(time.Now().Add(pongTimeout))
		conn.SetPongHandler(func(string) error {
			_ = conn.SetReadDeadline(time.Now().Add(pongTimeout))
			return nil
		})

		ticker := time.NewTicker(pingInterval)
		defer ticker.Stop()

		go func() {
			for range ticker.C {
				if err := conn.WriteControl(websocket.PingMessage, []byte("hb"), time.Now().Add(10*time.Millisecond)); err != nil {
					return
				}
			}
		}()

		for {
			if _, _, err := conn.ReadMessage(); err != nil {
				break
			}
		}
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка Dial: %v", err)
	}

	// Имитируем пропажу интернета (клиент не отвечает на пинги)
	clientConn.SetPingHandler(func(string) error { return nil })

	select {
	case <-socketDead:
		fmt.Println("Сервер успешно обнаружил зависший полуоткрытый сокет и разорвал соединение!")
	case <-time.After(300 * time.Millisecond):
		t.Fatal("Таймаут обнаружения мертвого сокета не сработал")
	}

	clientConn.Close()
}
```

## Под капотом

Сетевой поллер Go использует системный таймер ядра, который пробуждает горутину с ошибкой `i/o timeout` ровно по истечении `readDeadline`.

## Подводные камни

Забывать вызывать `SetReadDeadline` перед входом в цикл: без первичного дедлайна сервер будет ждать первого сообщения вечно, если клиент завис сразу после апгрейда.

## На собеседовании

**Вопрос с собеседования:** «Почему стандартный TCP Keep-Alive не решает проблему мертвых сокетов в WebSockets?»
**Ответ:** Стандартный TCP Keepalive работает на уровне 4-го уровня OSI (L4). Если приложение на стороне клиента зависло (Deadlock в UI-потоке браузера), стек TCP операционной системы клиента будет исправно отвечать на TCP Keep-Alive пакеты на уровне ядра, хотя само приложение мертво. Heartbeat на уровне WebSocket (L7) проверяет жизнеспособность именно прикладного процесса.
