# Синхронизация состояния при реконнекте: досыл пропущенных сообщений по last_msg_id

## Условие

Реализуйте **reconnection with state sync**: при реконнекте клиент отправляет ID последнего полученного сообщения, сервер досылает пропущенные.

## Теория

Паттерн Reconnect with Catch-Up (Досыл истории при обрыве):
- При разрыве связи на 5 секунд клиент теряет сообщения.
- Механизм синхронизации:
  1. Клиент хранит `last_received_msg_id = 100`.
  2. При переподключении отправляет: `{"action": "sync", "last_id": 100}`.
  3. Сервер достает из кольцевого буфера памяти все сообщения с `id > 100` (например 101, 102, 103) и досылает их клиенту.
  4. После этого клиент переводится в live-режим.
- Гарантирует непрерывность истории сообщений без потери контекста.

## Решение по шагам

1. Создайте структуру истории сообщений `MessageBuffer`.
2. Реализуйте метод `GetMissed(lastID)`.
3. Смоделируйте отключение клиента на 3 сообщения.
4. Протестируйте досыл пропущенных сообщений при реконнекте.

## Код решения

**`state_sync_reconnect_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type HistoryMessage struct {
	ID   uint64
	Text string
}

type MessageHistoryStore struct {
	mu       sync.RWMutex
	messages []HistoryMessage
}

func (s *MessageHistoryStore) Append(text string) uint64 {
	s.mu.Lock()
	defer s.mu.Unlock()
	id := uint64(len(s.messages) + 1)
	s.messages = append(s.messages, HistoryMessage{ID: id, Text: text})
	return id
}

func (s *MessageHistoryStore) GetMissedMessages(lastID uint64) []HistoryMessage {
	s.mu.RLock()
	defer s.mu.RUnlock()

	var missed []HistoryMessage
	for _, m := range s.messages {
		if m.ID > lastID {
			missed = append(missed, m)
		}
	}
	return missed
}

func TestReconnectionStateSync(t *testing.T) {
	store := &MessageHistoryStore{}

	// Сервер отправил сообщения 1, 2
	store.Append("Сообщение 1")
	store.Append("Сообщение 2")

	// Клиент успешно принял ID=2, затем связь оборвалась!
	lastReceivedID := uint64(2)

	// За время отсутствия клиента в чат пришли сообщения 3, 4, 5
	store.Append("Сообщение 3 (во время обрыва)")
	store.Append("Сообщение 4 (во время обрыва)")
	store.Append("Сообщение 5 (во время обрыва)")

	// Клиент переподключился и запросил синхронизацию с lastReceivedID=2
	missed := store.GetMissedMessages(lastReceivedID)

	if len(missed) != 3 {
		t.Fatalf("Ожидалось 3 пропущенных сообщения, получено: %d", len(missed))
	}

	if missed[0].ID != 3 || missed[2].ID != 5 {
		t.Fatalf("Нарушен порядок досыла: %+v", missed)
	}

	fmt.Println("Синхронизация состояния при реконнекте успешно выполнена:")
	fmt.Printf("  • Клиент отключился на ID=%d\n", lastReceivedID)
	fmt.Printf("  • Сервер дослал %d пропущенных сообщений (с ID %d по %d)!\n",
		len(missed), missed[0].ID, missed[len(missed)-1].ID)
}
```

## Под капотом

В производственных системах буфер истории ограничивают (например, хранят последние 1000 сообщений или сообщения за последние 10 минут). Если клиент отсутствовал дольше, сервер возвращает код `FULL_RELOAD_REQUIRED`.

## Подводные камни

Хранить историю сообщений в памяти без лимита размера: через месяц непрерывной работы память сервера будет исчерпана.

## На собеседовании

**Вопрос с собеседования:** «Как организовать досыл сообщений, если клиент отсутствовал несколько часов?»
**Ответ:** При длительном отсутствии память сокета не поможет. Клиент обращается к постоянной базе данных (PostgreSQL / ScyllaDB) через стандартный HTTP/GraphQL запрос `messages(after: $lastId, limit: 100)`. Получив историю пачками, сокет переключается в режим подписки на новые сообщения.
