# Передача структурированных данных: удобные методы conn.ReadJSON и conn.WriteJSON

## Условие

**Передача структурированных данных (JSON по WebSockets)**: Измените ваш Echo-сервер так, чтобы он работал не с голым текстом, а со структурами. Объявите структуру `Event` с полями `Type string` и `Payload any`. Используйте методы `conn.ReadJSON` и `conn.WriteJSON` для автоматической сериализации/десериализации данных при передаче по сокету.

## Теория

Встроенные JSON-хелперы в Gorilla WebSocket:
- Вместо ручной связки `json.Unmarshal(conn.ReadMessage())`:
  - Метод `conn.ReadJSON(&dest)`:
    - Считывает следующее текстовое сообщение из сокета.
    - Напрямую декодирует JSON в целевую структуру через `json.NewDecoder`.
  - Метод `conn.WriteJSON(v)`:
    - Сериализует переданную структуру в JSON и отправляет как `TextMessage`.
- Сокращает бойлерплейт-код в 3 раза.

## Решение по шагам

1. Определите структуру `Event[T]` с типизированным `Payload`.
2. Реализуйте эхо-хендлер с вызовами `conn.ReadJSON` и `conn.WriteJSON`.
3. Отправьте структурированное событие с клиента.
4. Проверьте корректность сериализации и десериализации.

## Код решения

**`ws_read_write_json_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/gorilla/websocket"
)

type Event struct {
	Type    string         `json:"type"`
	Payload map[string]any `json:"payload"`
}

func TestReadWriteJSONHelpers(t *testing.T) {
	upgrader := websocket.Upgrader{}
	server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		defer conn.Close()

		var ev Event
		// Автоматический демаршалинг из сокета!
		if err := conn.ReadJSON(&ev); err != nil {
			return
		}

		// Модифицируем и отправляем обратно через WriteJSON
		ev.Type = "ACK_" + ev.Type
		_ = conn.WriteJSON(ev)
	}))
	defer server.Close()

	wsURL := "ws" + strings.TrimPrefix(server.URL, "http")
	clientConn, _, err := websocket.DefaultDialer.Dial(wsURL, nil)
	if err != nil {
		t.Fatalf("Ошибка подключения: %v", err)
	}
	defer clientConn.Close()

	outEvent := Event{
		Type: "ORDER_CREATED",
		Payload: map[string]any{
			"orderId": "ord_9901",
			"total":   4500.0,
		},
	}

	// Отправка структуры через WriteJSON
	if err := clientConn.WriteJSON(outEvent); err != nil {
		t.Fatalf("Ошибка WriteJSON: %v", err)
	}

	var respEvent Event
	// Чтение структуры через ReadJSON
	if err := clientConn.ReadJSON(&respEvent); err != nil {
		t.Fatalf("Ошибка ReadJSON: %v", err)
	}

	if respEvent.Type != "ACK_ORDER_CREATED" || respEvent.Payload["orderId"] != "ord_9901" {
		t.Fatalf("Некорректное событие: %+v", respEvent)
	}

	fmt.Printf("Методы ReadJSON и WriteJSON успешно отработали:\n")
	fmt.Printf("  • Ответный тип: %s\n", respEvent.Type)
	fmt.Printf("  • Payload orderId: %v, total: %v руб\n", respEvent.Payload["orderId"], respEvent.Payload["total"])
}
```

## Под капотом

`WriteJSON` внутри использует `c.NextWriter(websocket.TextMessage)` в связке с `json.NewEncoder`, исключая создание промежуточного большого среза `[]byte` в памяти при сериализации.

## Подводные камни

Забывать, что `WriteJSON` тоже не является потокобезопасным: параллельный вызов `WriteJSON` из нескольких горутин приведет к той же гонке данных, что и `WriteMessage`.

## На собеседовании

**Вопрос с собеседования:** «Когда ReadJSON / WriteJSON уступают ручному парсингу json.Marshal / json.Unmarshal?»
**Ответ:** При широковещательной рассылке (Broadcast): `conn.WriteJSON(v)` выполнит сериализацию одной и той же структуры 10 000 раз для каждого клиента! В рассылках сообщение сериализуют один раз вручную в `[]byte`, а затем рассылают готовый срез байт через `conn.WriteMessage`.
