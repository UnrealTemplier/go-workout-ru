# Надежная широковещательная рассылка: изоляция ошибок, защита от зависших клиентов и устойчивость Hub

## Условие

Создайте **broadcast system**: функция, которая отправляет сообщение всем подключенным клиентам с обработкой ошибок (если один клиент "мертвый", это не должно блокировать остальных).

## Теория

Изоляция отказов при широковещательной рассылке (Fault-Tolerant Broadcast):
- В наивной реализации цикл `for conn := range conns` последовательно пишет в сокеты:
  - Если 5-й клиент завис, остальные 995 клиентов ждут таймаута сокета (до нескольких секунд!).
- **Отказоустойчивая система рассылки:**
  1. Неблокирующая отправка в клиентские очереди: `select { case c.send <- msg: default: ... }`.
  2. Если клиент не может принять сообщение, он помечается как кандидат на удаление.
  3. Ошибочный клиент изолируется и закрывается, не затрагивая соседей.

## Решение по шагам

1. Создайте систему широковещательной рассылки `FaultTolerantBroadcaster`.
2. Реализуйте сбор списка зависших клиентов.
3. Проверьте изоляцию зависшего клиента и успешную доставку остальным.
4. Протестируйте автоматическое удаление сбойных сокетов.

## Код решения

**`fault_tolerant_broadcast_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type ReliableClient struct {
	ID     string
	queue  chan string
	failed bool
}

type ReliableBroadcaster struct {
	mu      sync.Mutex
	clients map[*ReliableClient]bool
}

func (b *ReliableBroadcaster) Broadcast(message string) int {
	b.mu.Lock()
	var toDrop []*ReliableClient

	successCount := 0
	for c := range b.clients {
		select {
		case c.queue <- message:
			successCount++
		default:
			// Клиент переполнен или заблокирован -> изолируем
			c.failed = true
			toDrop = append(toDrop, c)
		}
	}

	// Очищаем зависших клиентов
	for _, c := range toDrop {
		delete(b.clients, c)
		close(c.queue)
	}
	b.mu.Unlock()

	return successCount
}

func TestFaultTolerantBroadcast(t *testing.T) {
	b := &ReliableBroadcaster{clients: make(map[*ReliableClient]bool)}

	cHealthy1 := &ReliableClient{ID: "node1", queue: make(chan string, 5)}
	cHealthy2 := &ReliableClient{ID: "node2", queue: make(chan string, 5)}
	cBlocked := &ReliableClient{ID: "blocked_node", queue: make(chan string, 1)}

	// Забиваем очередь заблокированного клиента
	cBlocked.queue <- "stale"

	b.clients[cHealthy1] = true
	b.clients[cHealthy2] = true
	b.clients[cBlocked] = true

	delivered := b.Broadcast("Важное обновление котировок")

	if delivered != 2 {
		t.Fatalf("Ожидалась доставка 2 здоровым клиентам, получено: %d", delivered)
	}

	if !cBlocked.failed {
		t.Fatal("Заблокированный клиент должен быть помечен как failed")
	}

	if _, exists := b.clients[cBlocked]; exists {
		t.Fatal("Сбойный клиент должен быть удален из реестра рассылки")
	}

	fmt.Println("Отказоустойчивая рассылка успешно изолировала сбой:")
	fmt.Printf("  • Успешно доставлено здоровым клиентам: %d\n", delivered)
	fmt.Printf("  • Зависший сокет изолирован и удален без задержки системы!\n")
}
```

## Под капотом

Сбор кандидатов на удаление во временный срез `toDrop` и удаление после цикла обхода предотвращает ошибку изменения мапы во время итерации (Concurrent Map Iteration).

## Подводные камни

Вызывать сетевой `conn.WriteMessage` внутри цикла обхода всех клиентов: один TCP таймаут на 5 секунд заморозит всех клиентов сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как рассылать broadcast на 500 000 клиентов за время < 10 миллисекунд?»
**Ответ:** Применять древовидную рассылку (Fan-Out Tree): главный диспетчер рассылает сообщение не 500 000 клиентам напрямую, а 50 локальным воркерам по каналам Go. Каждый воркер владеет пачкой из 10 000 соединений и параллельно на своих ядрах CPU производит системные вызовы `writev()`.
