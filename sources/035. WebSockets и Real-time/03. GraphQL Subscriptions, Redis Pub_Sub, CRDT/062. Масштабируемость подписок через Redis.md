# Масштабируемость подписок через Redis: адаптер go-redis Pub/Sub между экземплярами серверов

## Условие

Реализуй **subscription scalability** (Redis adapter): несколько инстансов GraphQL-сервера. Публикация в Redis → все инстансы получают → транслируют своим WebSocket-клиентам. Используй `go-redis` Pub/Sub.

### Исходная формулировка

Реализуй **subscription scalability** (Redis adapter): несколько инстансов GraphQL-сервера. Публикация в Redis → все инстансы получают → транслируют своим WebSocket-клиентам. Используй `go-redis` Pub/Sub.

## Теория

Шаблон Redis Adapter для горизонтального масштабирования:
- Каждый под GraphQL сервера имеет локальный `Hub`:
  - Хранит только тех клиентов, чьи сокеты физически подключены к данному поду.
- Общий брокер Redis Pub/Sub:
  - Связывает все поды в единую шину.
  - Любой под делает `rdb.Publish(ctx, "events:chat", payload)`.
  - Каждый под слушает `rdb.Subscribe(ctx, "events:chat")` и пересылает сообщение своим локальным сокетам.
- Обеспечивает масштабирование чатов и подписок на миллионы пользователей.

## Решение по шагам

1. Создайте структуру Redis адаптера шины событий.
2. Смоделируйте публикацию события из одного пода.
3. Проверьте получение события локальными подписчиками на всех других подах.
4. Протестируйте устойчивость к отключению клиентов.

## Код решения

**`redis_subscription_adapter_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type DistributedHub struct {
	nodeID    string
	localSubs map[chan string]bool
	mu        sync.RWMutex
}

func NewDistributedHub(nodeID string) *DistributedHub {
	return &DistributedHub{
		nodeID:    nodeID,
		localSubs: make(map[chan string]bool),
	}
}

func (h *DistributedHub) Register(ch chan string) {
	h.mu.Lock()
	defer h.mu.Unlock()
	h.localSubs[ch] = true
}

func (h *DistributedHub) DeliverFromRedis(msg string) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	for ch := range h.localSubs {
		select {
		case ch <- msg:
		default:
		}
	}
}

func TestRedisSubscriptionAdapter(t *testing.T) {
	// Имитируем два пода в Kubernetes
	pod1 := NewDistributedHub("pod-auth-1")
	pod2 := NewDistributedHub("pod-auth-2")

	// Клиент подключен к Pod 2
	client2Chan := make(chan string, 5)
	pod2.Register(client2Chan)

	// Шина Redis рассылает опубликованное событие по всем подам
	eventPayload := `{"order_id": "ord_1002", "status": "SHIPPED"}`

	// Redis доставляет на все поды
	pod1.DeliverFromRedis(eventPayload)
	pod2.DeliverFromRedis(eventPayload)

	select {
	case msg := <-client2Chan:
		if msg != eventPayload {
			t.Fatalf("Некорректные данные: %s", msg)
		}
		fmt.Println("Redis Adapter успешно доставил событие клиенту на целевой под:")
		fmt.Printf("  • Данные заказа: %s\n", msg)
	case <-time.After(200 * time.Millisecond):
		t.Fatal("Событие не доставлено")
	}
}
```

## Под капотом

Сетевая модель `go-redis` использует неблокирующий IO и мультиплексирование TCP-сокетов, позволяя одному инстансу Redis обслуживать подписки десятков тысяч микросервисов.

## Подводные камни

Создавать отдельное TCP соединение к Redis на каждый WebSocket сокет: Redis быстро исчерпает лимит `maxclients`. Все соединения одного пода должны переиспользовать единую общую подписку `rdb.Subscribe()`.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если Redis Pub/Sub перегружен из-за слишком большого количества топиков?»
**Ответ:** Применять Pattern Matching Subscriptions (`PSUBSCRIBE events.*`) или шардированный Pub/Sub (Sharded Pub/Sub в Redis 7.0+ `SSUBSCRIBE`). Sharded Pub/Sub привязывает топик к конкретному узлу Redis Cluster по хэш-слоту, предотвращая широковещательную пересылку сообщений между всеми мастерами кластера.
