# Очередь сообщений на клиента: сглаживание пиков нагрузки и асинхронная отправка

## Условие

Реализуйте **message queue per client**: если клиент медленно читает, складывайте сообщения в буфер (канал) и отправляйте их асинхронно, чтобы не блокировать broadcast.

## Теория

Асинхронная доставка через персональные очереди:
- Внезапный всплеск нагрузки (Flash Crowd, например гол в футбольном матче):
  - 10 000 сообщений в секунду летят в чат.
  - Скорость сети клиента ограничена.
- Персональная очередь `Client.mailbox`:
  - Впитывает всплеск сообщений как амортизатор.
  - Асинхронный воркер равномерно вычитывает сообщения и пишет в сокет со скоростью пропускной способности канала клиента.

## Решение по шагам

1. Создайте структуру очереди `ClientMailbox`.
2. Реализуйте неблокирующее добавление сообщений.
3. Протестируйте сглаживание пикового всплеска из 10 сообщений.
4. Проверьте последовательную асинхронную доставку.

## Код решения

**`client_mailbox_queue_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type AsyncClientQueue struct {
	mailbox chan string
	drainWg sync.WaitGroup
}

func NewAsyncClientQueue(size int) *AsyncClientQueue {
	return &AsyncClientQueue{
		mailbox: make(chan string, size),
	}
}

func (q *AsyncClientQueue) Push(msg string) bool {
	select {
	case q.mailbox <- msg:
		return true
	default:
		return false
	}
}

func (q *AsyncClientQueue) StartWorker(onDelivered func(string)) {
	q.drainWg.Add(1)
	go func() {
		defer q.drainWg.Done()
		for msg := range q.mailbox {
			// Имитация скорости отправки в сокет
			time.Sleep(5 * time.Millisecond)
			onDelivered(msg)
		}
	}()
}

func (q *AsyncClientQueue) Stop() {
	close(q.mailbox)
	q.drainWg.Wait()
}

func TestAsyncClientQueue(t *testing.T) {
	queue := NewAsyncClientQueue(20)

	var delivered []string
	var mu sync.Mutex

	queue.StartWorker(func(m string) {
		mu.Lock()
		delivered = append(delivered, m)
		mu.Unlock()
	})

	// Мгновенно закидываем 10 сообщений (пиковый всплеск)
	for i := 1; i <= 10; i++ {
		ok := queue.Push(fmt.Sprintf("Пакет-%d", i))
		if !ok {
			t.Fatalf("Очередь должна вместить всплеск: i=%d", i)
		}
	}

	queue.Stop()

	mu.Lock()
	count := len(delivered)
	mu.Unlock()

	if count != 10 {
		t.Fatalf("Ожидалось 10 доставленных пакетов, получено: %d", count)
	}

	fmt.Printf("Персональная очередь клиента успешно сгладила пик нагрузки:\n")
	fmt.Printf("  • Принято всплеском: 10 пакетов\n")
	fmt.Printf("  • Доставлено асинхронным воркером: %d пакетов без блокировки издателя!\n", count)
}
```

ℹ️ Асинхронная очередь сообщений на клиента для сглаживания сетевых пиков

## Под капотом

Очередь изолирует сетевой цикл издателя Hub'а от системных вызовов `write()`, распределяя сетевой ввод-вывод по ядрам процессора.

## Подводные камни

Не вызывать `close(mailbox)` при отключении клиента: горутина воркера останется заблокированной на `range q.mailbox` навсегда.

## На собеседовании

**Вопрос с собеседования:** «Каковы риски слишком большой очереди сообщений на одного клиента?»
**Ответ:** 1. **Увеличение задержки:** клиент видит устаревшие сообщения с задержкой в секунды (Stale UI). 2. **OOM сервера:** при 100 000 клиентов очереди по 1 000 сообщений займут гигабайты оперативной памяти. Размер очереди должен быть минимально достаточным (например, 64–256 элементов).
