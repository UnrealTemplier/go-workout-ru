# Архитектурная дилемма: рефлексия времени выполнения против кодогенерации

## Условие

**Code generation vs reflection**: Для критичных по производительности участков рассмотрите кодогенерацию вместо runtime reflect (пример: `easyjson`, `ffjson`).

## Теория

При проектировании Enterprise-систем на Go выбор между **Runtime Reflection** и **Compile-Time Code Generation** — одно из ключевых архитектурных решений:

| Критерий | Runtime Reflection (`reflect`) | Кодогенерация (`easyjson`, `stringer`) |
| :--- | :--- | :--- |
| **Производительность** | Медленно (в 10–100 раз медленнее) | Максимально возможная (нативный C-подобный код) |
| **Аллокации памяти** | Десятки аллокаций на запрос в куче | Нулевые аллокации (Zero-Alloc) |
| **Поддержка сборки** | Не требует дополнительных утилит | Требует генерации перед компиляцией (`go generate`) |
| **Безопасность типов** | Ошибки падают в рантайме (`panic`) | Ошибки ловятся компилятором (`compile error`) |
| **Размер бинарника** | Компактный | Бинарный файл больше из-за сгенерированного кода |

### Золотое правило индустрии:
- Используйте **рефлексию** для: прототипирования, инструментов разработки, unit-тестов, CLI-утилит и редко вызываемых путей администрирования.
- Используйте **кодогенерацию** для: критических путей HighLoad RPC, сериализации данных (Protobuf, JSON) и работы с БД.

## Решение по шагам

1. Реализуем структуру `UserEvent`.
2. Напишем рефлексивный сериализатор в строковый формат `key=val`.
3. Напишем сгенерированный специализированный сериализатор `AppendToBuffer`.
4. Сравним производительность обоих подходов.
5. Сформулируем архитектурные рекомендации.

## Код решения

**`codegen_vs_reflect_arch.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"strconv"
	"time"
)

type UserEvent struct {
	UserID    int64
	Action    string
	Timestamp int64
}

// 1. Рефлексивный сериализатор (медленный, но универсальный)
func SerializeReflect(v any) string {
	val := reflect.ValueOf(v)
	typ := val.Type()

	var res string
	for i := 0; i < val.NumField(); i++ {
		if i > 0 {
			res += "&"
		}
		res += fmt.Sprintf("%s=%v", typ.Field(i).Name, val.Field(i).Interface())
	}
	return res
}

// 2. Сгенерированный сериализатор (быстрый, zero-alloc буфер)
func (u UserEvent) SerializeCodegen(dst []byte) []byte {
	dst = append(dst, "UserID="...)
	dst = strconv.AppendInt(dst, u.UserID, 10)
	dst = append(dst, "&Action="...)
	dst = append(dst, u.Action...)
	dst = append(dst, "&Timestamp="...)
	dst = strconv.AppendInt(dst, u.Timestamp, 10)
	return dst
}

func main() {
	event := UserEvent{
		UserID:    880011,
		Action:    "LOGIN_SUCCESS",
		Timestamp: 1718005500,
	}

	const N = 200_000

	// 1. Рефлексия
	start := time.Now()
	var dummyReflect string
	for i := 0; i < N; i++ {
		dummyReflect = SerializeReflect(event)
	}
	tReflect := time.Since(start)

	// 2. Кодогенерация
	buf := make([]byte, 0, 128)
	start = time.Now()
	for i := 0; i < N; i++ {
		buf = event.SerializeCodegen(buf[:0])
	}
	tCodegen := time.Since(start)

	fmt.Printf("Результат сериализации:\n  %s\n\n", dummyReflect)
	fmt.Printf("1. Рефлексия:    %10v (%.2f нс/оп)\n", tReflect, float64(tReflect.Nanoseconds())/N)
	fmt.Printf("2. Кодогенерация:%10v (%.2f нс/оп)\n\n", tCodegen, float64(tCodegen.Nanoseconds())/N)

	fmt.Printf("Сгенерированный код быстрее в %.1f раз!\n",
		float64(tReflect)/float64(tCodegen))
}
```

ℹ️ Сравнение архитектурных подходов: рефлексия против сгенерированного кода

**`Терминал`**

```bash
go run codegen_vs_reflect_arch.go
# Результат сериализации:
#   UserID=880011&Action=LOGIN_SUCCESS&Timestamp=1718005500
# 
# 1. Рефлексия:       118.5ms (592.50 нс/оп)
# 2. Кодогенерация:     4.8ms (24.00 нс/оп)
# 
# Сгенерированный код быстрее в 24.7 раз!
```

## Под капотом

Сгенерированный метод `SerializeCodegen` работает напрямую со срезом байт, вызывая оптимизированную функцию `strconv.AppendInt`. Она переводит целое число в символы ASCII с помощью битовых сдвигов и прямого заполнения памяти без создания промежуточных строк и интерфейсов.

## Подводные камни

1. **Устаревание сгенерированного кода:** Главная проблема кодогенерации — рассинхронизация: разработчик изменил поля в структуре `UserEvent`, но забыл запустить `go generate ./...`. Для предотвращения этого в CI/CD пайплайн обязательно добавляют шаг проверки `git diff --exit-code` после запуска генераторов.

## На собеседовании

**Вопрос с собеседования в Wildberries:** «Как настроить CI/CD пайплайн в GitLab, чтобы предотвратить деплой сервиса с устаревшим сгенерированным кодом?»
**Ответ:** На этапе линтинга запускают скрипт:
```bash
go generate ./...
if [ -n "$(git status --porcelain)" ]; then
    echo "ERROR: Сгенерированный код устарел! Запустите go generate локально и закоммитьте изменения."
    exit 1
fi
```
Если после генерации в репозитории появились измененные файлы, сборка прерывается с ошибкой.
