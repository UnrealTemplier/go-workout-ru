# Сравнение Type Switch и рефлексии: таблица переходов против инспекции

## Условие

**Type switches vs reflect**: Сравните `switch v := x.(type)` vs reflect. Type switch компилируется в быстрый jump table.

## Теория

При проверке типа в рантайме существуют два подхода:
1. **Статический свитч типов (`switch v := x.(type)`):**
   - Компилятор анализирует все варианты `case` во время сборки.
   - Если вариантов много, компилятор строит оптимизированную бинарную таблицу переходов (Jump Table) или идеальную хэш-таблицу по хэшам типов `_type.hash`.
   - Время проверки: **~1–3 наносекунды**, нулевые аллокации.
2. **Рефлексивная проверка (`reflect.TypeOf(x).Kind()`):**
   - Требует вызова функции `TypeOf`, чтения заголовка интерфейса, проверки флагов.
   - Время проверки: **~8–15 наносекунд**.

## Решение по шагам

1. Реализуем функцию диспетчеризации через `switch v := x.(type)`.
2. Реализуем функцию диспетчеризации через `reflect.TypeOf(x).Kind()`.
3. Замерим время выполнения 1 000 000 проверок на различных типах данных (`int`, `string`, `bool`, `float64`).
4. Сравним задержки и объясним преимущества `type switch`.

## Код решения

**`type_switch_vs_reflect.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"time"
)

func dispatchTypeSwitch(val any) string {
	switch v := val.(type) {
	case int:
		return fmt.Sprintf("int:%d", v)
	case string:
		return fmt.Sprintf("str:%s", v)
	case bool:
		return fmt.Sprintf("bool:%v", v)
	case float64:
		return fmt.Sprintf("float:%.1f", v)
	default:
		return "unknown"
	}
}

func dispatchReflect(val any) string {
	t := reflect.TypeOf(val)
	switch t.Kind() {
	case reflect.Int:
		return fmt.Sprintf("int:%d", val.(int))
	case reflect.String:
		return fmt.Sprintf("str:%s", val.(string))
	case reflect.Bool:
		return fmt.Sprintf("bool:%v", val.(bool))
	case reflect.Float64:
		return fmt.Sprintf("float:%.1f", val.(float64))
	default:
		return "unknown"
	}
}

func main() {
	inputs := []any{100, "golang", true, 3.14}
	const N = 500_000

	// 1. Type Switch
	start := time.Now()
	for i := 0; i < N; i++ {
		_ = dispatchTypeSwitch(inputs[i%4])
	}
	tSwitch := time.Since(start)

	// 2. Reflect Kind Switch
	start = time.Now()
	for i := 0; i < N; i++ {
		_ = dispatchReflect(inputs[i%4])
	}
	tReflect := time.Since(start)

	fmt.Printf("Бенчмарк диспетчеризации типов (%d итераций):\n\n", N)
	fmt.Printf("1. switch v := x.(type): %10v (%.2f нс/оп)\n",
		tSwitch, float64(tSwitch.Nanoseconds())/N)
	fmt.Printf("2. reflect.TypeOf.Kind: %10v (%.2f нс/оп)\n\n",
		tReflect, float64(tReflect.Nanoseconds())/N)

	fmt.Printf("Нативный Type Switch быстрее в %.1f раз!\n",
		float64(tReflect)/float64(tSwitch))
}
```

ℹ️ Сравнение эффективности нативного Type Switch и reflect.TypeOf().Kind()


## Под капотом

В ассемблерном коде компилятор Go разворачивает `switch x.(type)` в проверку хеша типа `typ.hash`.
Если вариантов больше 4, компилятор применяет бинарный поиск по отсортированным хэшам типов, избегая последовательных проверок. Переменная `v` в ветке `case int:` сразу типизирована как `int`, что исключает повторное приведение типов.

## Подводные камни

1. **Невозможность покрытия неизвестных типов:** `switch x.(type)` требует перечисления конкретных типов во время компиляции. Если вам нужно поддержать произвольные структуры, объявленные пользователями библиотеки, без рефлексии не обойтись.

## На собеседовании

**Вопрос с собеседования в Яндекс:** «Как компилятор Go оптимизирует switch v := x.(type), если в свитче 50 различных типов?»
**Ответ:** Компилятор строит бинарное дерево поиска (Binary Search Tree) или прыжковую таблицу (Jump Table) по 32-битным хэшам типов `_type.hash`. Время поиска совпадения составляет \(O(\log N)\) инструкций процессора без линейного перебора веток.
