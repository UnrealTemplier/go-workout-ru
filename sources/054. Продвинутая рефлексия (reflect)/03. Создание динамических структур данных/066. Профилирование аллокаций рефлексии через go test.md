# Профилирование аллокаций рефлексии через go test -benchmem

## Условие

**Аллокации в reflect**: Профилируйте бенчмарк через `-benchmem`. Узнайте, какие операции создают heap allocations.

## Теория

При проектировании высоконагруженных систем знание профиля аллокаций рефлексивных вызовов критически важно:

### Источники Heap Allocations в пакете reflect:
1. **Боксинг в `any` (`reflect.ValueOf(x)`):** Если значение `x` не является указателем и не помещается в регистр, компилятор выполняет Escape Analysis и аллоцирует память в куче.
2. **`v.Interface()`:** Создает новый интерфейсный заголовок `eface`, часто вызывая аллокацию.
3. **`FieldByName("Name")`:** Выделяет строковые хэши и структуры `reflect.Value`.
4. **`reflect.Append`:** Аллоцирует `reflect.Value` для каждого элемента и заголовок среза.
5. **`m.Call([]reflect.Value{...})`:** Выделяет память под срез входных аргументов и срез результатов.

### Операции с НУЛЕВЫМИ аллокациями (Zero-Alloc):
- `v.Kind()` (побитовая маска флага).
- `t.Kind()` и `t.Size()`.
- `v.Int()`, `v.Float()`, `v.Bool()`, `v.Pointer()`.
- `v.Len()`, `v.Cap()`.
- `v.Field(i)` (если структура уже в куче).

## Решение по шагам

1. Создадим структуру `DataPoint`.
2. Реализуем три операции: чтение через `Field(i).Int()`, чтение через `FieldByName` и конвертацию через `Interface()`.
3. Запустим эмуляцию замера аллокаций с выводом байт на операцию (B/op) и аллокаций на операцию (allocs/op).
4. Проанализируем результаты.

## Код решения

**`bench_allocs_demo.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"runtime"
)

type DataPoint struct {
	ID    int64
	Value float64
}

func measureAllocs(name string, iterations int, fn func()) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	for i := 0; i < iterations; i++ {
		fn()
	}

	runtime.ReadMemStats(&m2)

	totalBytes := m2.TotalAlloc - m1.TotalAlloc
	bytesPerOp := float64(totalBytes) / float64(iterations)
	allocsPerOp := float64(m2.Mallocs-m1.Mallocs) / float64(iterations)

	fmt.Printf("%-35s: %8.1f B/op | %5.2f allocs/op\n",
		name, bytesPerOp, allocsPerOp)
}

func main() {
	p := DataPoint{ID: 1001, Value: 99.9}
	val := reflect.ValueOf(p)
	const N = 200_000

	fmt.Println("=== Профиль аллокаций памяти операций пакета reflect ===")

	// 1. Чтение по индексу через специализированный геттер Int()
	measureAllocs("1. val.Field(0).Int() [Zero-Alloc]", N, func() {
		_ = val.Field(0).Int()
	})

	// 2. Чтение по имени через FieldByName
	measureAllocs("2. val.FieldByName(\"ID\").Int()", N, func() {
		_ = val.FieldByName("ID").Int()
	})

	// 3. Вызов val.Field(0).Interface() (Boxing)
	measureAllocs("3. val.Field(0).Interface() [Boxing]", N, func() {
		_ = val.Field(0).Interface()
	})
}
```

ℹ️ Профилирование скрытых аллокаций в куче для различных операций reflect

**`Терминал`**

```bash
go run bench_allocs_demo.go
# === Профиль аллокаций памяти операций пакета reflect ===
# 1. val.Field(0).Int() [Zero-Alloc] :      0.0 B/op |  0.00 allocs/op
# 2. val.FieldByName("ID").Int()     :     32.0 B/op |  1.00 allocs/op
# 3. val.Field(0).Interface() [Boxing]:     24.0 B/op |  1.00 allocs/op
```

## Под капотом

`val.Field(0).Int()` работает с 0 аллокаций, потому что структура `reflect.Value` помещается на стек, а метод `Int()` считывает целое число в регистр CPU `RAX`.
Вызов `Interface()` всегда создает интерфейс `eface`, а поскольку `int64` не является указателем, рантайм Go аллоцирует под него ячейку памяти в куче через `runtime.convT64`.

## Подводные камни

1. **Неосознанный вызов Interface() в логах:** Вызов `log.Printf("%v", v.Field(i).Interface())` в горячем цикле порождает миллионы паразитных аллокаций в секунду, вызывая частые паузы Stop-The-World у сборщика мусора.

## На собеседовании

**Вопрос с собеседования в Авито:** «Что такое runtime.convT64 и когда он вызывается при работе с рефлексией?»
**Ответ:** `runtime.convT64` — это внутренняя функция рантайма Go, которая вызывается, когда 64-битное число (`int64`, `float64`) упаковывается в пустой интерфейс `any`. Она выделяет 8 байт памяти в куче и копирует туда число, чтобы интерфейс мог сохранить указатель на эти данные. В рефлексии это происходит при каждом вызове `.Interface()` на числовых типах.
