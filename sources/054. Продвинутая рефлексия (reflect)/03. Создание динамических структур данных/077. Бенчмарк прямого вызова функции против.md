# Бенчмарк прямого вызова функции против reflect.Call

## Условие

**[Производительность]**: Напиши бенчмарк: прямой вызов функции vs вызов через `reflect.Call`. Оцени разницу в скорости (рефлексия медленнее в 10-100 раз).

## Теория

При проектировании высоконагруженных систем разработчики должны четко понимать аппаратную разницу между статическим и динамическим вызовами:

1. **Прямой вызов функции:**
   - Компилятор генерирует прямую инструкцию `CALL symbol` или выполняет инлайнинг (встраивание тела функции прямо в вызывающий код).
   - Аргументы передаются в регистрах процессора (`RAX`, `RBX`, `RCX`).
   - Время вызова: **~0.5–1.5 наносекунды**.

2. **Вызов через reflect.Call:**
   - Формирование среза аргументов `[]reflect.Value` (аллокация в куче).
   - Построение фрейма аргументов согласно соглашению о вызовах ABI.
   - Проверка типов каждого аргумента в цикле.
   - Вызов низкоуровневой функции рантайма `reflectcall`.
   - Заворачивание возвращенных значений в новый срез `[]reflect.Value`.
   - Время вызова: **~40–100 наносекунд** (в 30–80 раз медленнее!).

## Решение по шагам

1. Создадим функцию сложения `Add(a, b int) int`.
2. Реализуем замер 1 000 000 итераций прямого вызова.
3. Реализуем замер вызова через `reflect.ValueOf(Add).Call()`.
4. Сравним задержки на операцию и выведем коэффициент замедления.

## Код решения

**`bench_func_call.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"time"
)

//go:noinline
func Add(a, b int) int {
	return a + b
}

func main() {
	const iterations = 1_000_000

	// 1. Прямой вызов
	start := time.Now()
	var sumDirect int
	for i := 0; i < iterations; i++ {
		sumDirect += Add(i, 2)
	}
	tDirect := time.Since(start)

	// 2. Вызов через reflect.Call
	fnVal := reflect.ValueOf(Add)
	args := []reflect.Value{reflect.ValueOf(0), reflect.ValueOf(2)}

	start = time.Now()
	var sumReflect int
	for i := 0; i < iterations; i++ {
		args[0] = reflect.ValueOf(i)
		res := fnVal.Call(args)
		sumReflect += int(res[0].Int())
	}
	tReflect := time.Since(start)

	fmt.Printf("Контроль сумм: %d == %d\n\n", sumDirect, sumReflect)

	nsDirect := float64(tDirect.Nanoseconds()) / float64(iterations)
	nsReflect := float64(tReflect.Nanoseconds()) / float64(iterations)

	fmt.Printf("1. Прямой вызов функции: %10v (%.2f нс/оп)\n", tDirect, nsDirect)
	fmt.Printf("2. Вызов reflect.Call:   %10v (%.2f нс/оп)\n\n", tReflect, nsReflect)

	fmt.Printf("Рефлексивный вызов функции медленнее в %.1f раз!\n", nsReflect/nsDirect)
}
```

ℹ️ Бенчмарк накладных расходов вызова функций через reflect.Call

**`Терминал`**

```bash
go run bench_func_call.go
# Контроль сумм: 500001500000 == 500001500000
# 
# 1. Прямой вызов функции:     1.2ms (1.20 нс/оп)
# 2. Вызов reflect.Call:      48.5ms (48.50 нс/оп)
# 
# Рефлексивный вызов функции медленнее в 40.4 раз!
```

## Под капотом

При вызове `fnVal.Call(args)` рантайм Go обращается к ассемблерному стабу `reflectcall(frame, argsize, retoff, regArgs)`. Стаб сохраняет регистры вызывающей функции, копирует стек и переносит данные из среза `args` в регистры процессора. Возврат значений снова оборачивается в структуры `Value`, порождая двойной барьер сериализации аргументов.

## Подводные камни

1. **Аллокация среза аргументов внутри цикла:** Если создавать `[]reflect.Value{...}` на каждой итерации, время вырастет еще в 2–3 раза из-за нагрузки на Garbage Collector.

## На собеседовании

**Вопрос с собеседования в VK:** «Почему даже если предварительно аллоцировать срез args []reflect.Value, вызов fn.Call(args) все равно выделяет память в куче?»
**Ответ:** Потому что метод `Call` возвращает новый срез результатов `[]reflect.Value`. Этот срез создается внутри тела метода `Call` динамически и неизбежно утекает в вызывающий код, вызывая одну аллокацию памяти на каждый вызов.
