# Глубокий бенчмаркинг прямого доступа против FieldByName

## Условие

**Benchmark reflect vs direct access**: Сравните производительность доступа к полю структуры напрямую vs через `Value.FieldByName()`. Разница должна быть в 100-1000x.

## Теория

Сравнение производительности прямого доступа к памяти процессора и рефлексивного поиска демонстрирует архитектурную цену динамического полиморфизма:

1. **Прямой доступ (`val := user.Age`):**
   Компилятор точно знает структуру в памяти: поле `Age` находится по смещению `+8` байт от адреса структуры.
   Генерируется одна ассемблерная инструкция: `MOVQ 8(RAX), RBX`.
   Время выполнения: **~0.3–0.5 наносекунды** (скорость кэша L1 CPU).

2. **Рефлексивный доступ (`v.FieldByName("Age")`):**
   - Упаковка структуры в пустой интерфейс `any` (боксинг).
   - Вызов функции поиска `FieldByName`.
   - Хеширование строки `"Age"` и линейный перебор всех полей структуры.
   - Аллокация нового объекта `reflect.Value` в куче.
   - Вызов метода `v.Int()`.
   Время выполнения: **~40–120 наносекунд**.

Разница в скорости составляет от **80 до 300 раз**!

## Решение по шагам

1. Определим структуру `Employee` с несколькими полями.
2. Реализуем цикл прямого чтения на 1 000 000 итераций.
3. Реализуем цикл рефлексивного чтения через `FieldByName`.
4. Замерим время работы обоих подходов с высокой точностью.
5. Выведем детальный коэффициент замедления.

## Код решения

**`direct_vs_reflect_bench.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"time"
)

type WorkerProfile struct {
	ID       int64
	FullName string
	Role     string
	Salary   int64
}

func main() {
	worker := WorkerProfile{
		ID:       101,
		FullName: "Сергей Смирнов",
		Role:     "Senior Go Engineer",
		Salary:   450_000,
	}

	const iterations = 1_000_000

	// 1. Прямой доступ
	var directSum int64
	start := time.Now()
	for i := 0; i < iterations; i++ {
		directSum += worker.Salary
	}
	tDirect := time.Since(start)

	// 2. Рефлексивный доступ через FieldByName
	v := reflect.ValueOf(worker)
	var reflectSum int64
	start = time.Now()
	for i := 0; i < iterations; i++ {
		reflectSum += v.FieldByName("Salary").Int()
	}
	tReflect := time.Since(start)

	fmt.Printf("Контрольные суммы (Direct=%d, Reflect=%d)\n\n", directSum, reflectSum)

	nsPerDirect := float64(tDirect.Nanoseconds()) / float64(iterations)
	nsPerReflect := float64(tReflect.Nanoseconds()) / float64(iterations)

	fmt.Printf("1. Прямой доступ к полю:   %10v (%.2f нс/оп)\n", tDirect, nsPerDirect)
	fmt.Printf("2. Рефлексивный FieldByName:%10v (%.2f нс/оп)\n\n", tReflect, nsPerReflect)

	ratio := nsPerReflect / nsPerDirect
	fmt.Printf("Замедление рефлексии: в %.1f раз!\n", ratio)
}
```

ℹ️ Бенчмарк производительности: нативный доступ против рефлексии

**`Терминал`**

```bash
go run direct_vs_reflect_bench.go
# Контрольные суммы (Direct=450000000000, Reflect=450000000000)
# 
# 1. Прямой доступ к полю:        850µs (0.85 нс/оп)
# 2. Рефлексивный FieldByName:    68.2ms (68.20 нс/оп)
# 
# Замедление рефлексии: в 80.2 раз!
```

## Под капотом

Компилятор Go способен оптимизировать прямой доступ, помещая значение поля в регистр процессора (`register allocation`).
В случае рефлексии компилятор обязан рассматривать вызов `FieldByName` как непрозрачную черную коробку: генерируются инструкции вызова функции `CALL`, создается фрейм стека, сбрасываются регистры и происходит обращение к памяти метаданных типов.

## Подводные камни

1. **Ложное профилирование без Escape Analysis:** Если объект рефлексии создается внутри цикла `reflect.ValueOf(worker).FieldByName(...)`, оверхед вырастает еще в 3 раза из-за миллиона аллокаций в куче.

## На собеседовании

**Вопрос с собеседования в Яндекс:** «Если рефлексия в 100 раз медленнее прямого доступа, почему стандартный пакет encoding/json использует её вместо кодогенерации?»
**Ответ:** Стандартная библиотека Go ориентирована на простоту, надежность и отсутствие внешних зависимостей сборки (Out-of-the-box experience). Рефлексия позволяет сериализовать любую структуру без необходимости запускать сторонние утилиты кодогенерации. 
Однако в критических по RPS сервисах BigTech используют кодогенераторы (например, `easyjson` или `vtprotobuf`), генерирующие нативный код с нулевым оверхедом.
