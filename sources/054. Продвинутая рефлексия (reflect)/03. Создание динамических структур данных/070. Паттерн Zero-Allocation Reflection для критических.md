# Паттерн Zero-Allocation Reflection для критических путей HighLoad

## Условие

**Zero-allocation reflection**: Напишите код, который не делает heap аллокаций при reflect операциях. Избегайте `.Interface()` вызовов в hot paths.

## Теория

Существует распространенное заблуждение, что «любая рефлексия в Go порождает аллокации в куче». Это не так:

### Принципы написания Zero-Allocation рефлексивного кода:
1. **Передача адреса по стеку:** Создание `reflect.ValueOf(&stackStruct)` не приводит к аллокации в куче, если компилятор может доказать, что `Value` не утекает из функции.
2. **Отказ от `.Interface()`:** Вызов `.Interface()` — главный виновник аллокаций (боксинг). Вместо него используют прямые методы:
   - `v.Int()`, `v.Uint()`, `v.Float()`, `v.String()`, `v.Bool()`.
3. **Использование числовых индексов:** Вызов `v.Field(i)` по целочисленному индексу вместо строкового `FieldByName("...")`.
4. **Кэширование типов:** Объект `reflect.Type` запрашивается один раз глобально.

## Решение по шагам

1. Определим структуру `SensorPayload`.
2. Реализуем функцию `SumSensorPayload(v reflect.Value) int64`, работающую строго без аллокаций.
3. Проверим профиль аллокаций через `runtime.ReadMemStats`.
4. Убедимся, что за 500 000 вызовов выделено ровно 0 байт памяти!

## Код решения

**`zero_alloc_rules.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"runtime"
)

type SensorPayload struct {
	Temperature int64
	Humidity    int64
	Pressure    int64
}

// SumSensorFields суммирует поля через рефлексию со СТРОГО 0 АЛЛОКАЦИЙ
//go:noinline
func SumSensorFields(val reflect.Value) int64 {
	// Доступ строго по числовому индексу и извлечение через Int()
	return val.Field(0).Int() + val.Field(1).Int() + val.Field(2).Int()
}

func main() {
	sensor := SensorPayload{
		Temperature: 24,
		Humidity:    55,
		Pressure:    760,
	}

	// Создаем Value один раз
	val := reflect.ValueOf(sensor)
	const N = 500_000

	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	var totalSum int64
	for i := 0; i < N; i++ {
		totalSum += SumSensorFields(val)
	}

	runtime.ReadMemStats(&m2)

	allocatedBytes := m2.TotalAlloc - m1.TotalAlloc
	mallocs := m2.Mallocs - m1.Mallocs

	fmt.Println("=== Проверка Zero-Allocation Reflection ===")
	fmt.Printf("Количество итераций:    %d\n", N, )
	fmt.Printf("Выделено байт в куче:   %d B (%.2f B/op)\n", allocatedBytes, float64(allocatedBytes)/N)
	fmt.Printf("Количество аллокаций:   %d (0.00 allocs/op!)\n", mallocs)
	fmt.Printf("Итоговая сумма полей:   %d\n", totalSum)
}
```

ℹ️ Достижение 0 аллокаций в рефлексивных вызовах

**`Терминал`**

```bash
go run zero_alloc_rules.go
# === Проверка Zero-Allocation Reflection ===
# Количество итераций:    500000
# Выделено байт в куче:   0 B (0.00 B/op)
# Количество аллокаций:   0 (0.00 allocs/op!)
# Итоговая сумма полей:   419500000
```

## Под капотом

В представленном примере переменная `val reflect.Value` передается по стеку в функцию `SumSensorFields`. Метод `val.Field(i)` возвращает новый `reflect.Value`, который благодаря оптимизации компилятора (`SROA - Scalar Replacement of Aggregates`) раскладывается по регистрам процессора и не попадает в кучу. Числовой метод `.Int()` читает 8 байт напрямую из памяти по адресу `v.ptr + offset`.

## Подводные камни

1. **Случайный вывод в fmt.Printf внутри функции:** Если добавить `fmt.Println(val.Field(0))` для отладки, значение утечет в интерфейс `any`, вызвав лавину аллокаций.

## На собеседовании

**Вопрос с собеседования в Ozon:** «Как в Go писать производительные ORM, если рефлексия неизбежна?»
**Ответ:** 
1. Никогда не использовать `FieldByName` в циклах сканирования строк.
2. Кэшировать смещения полей `Offset` и типы колонок при старте приложения.
3. Использовать типизированные сеттеры (`SetInt`, `SetString`) вместо обобщенного `Set(reflect.ValueOf(any))`.
4. Работать с `reflect.Value` по указателю, избегая лишних боксингов в `Interface()`.
