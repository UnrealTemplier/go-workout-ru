# Симбиоз рефлексии и дженериков: где Generic бессильны

## Условие

**Рефлексия и дженерики: мост.**: Напишите обобщённую функцию, которая использует рефлексию для проверки, что тип реализует интерфейс, и если да, вызывает один из его методов. Покажите, где дженерики не могут заменить рефлексию (например, итерация по полям).

## Теория

Появление параметров типа (Generics) в Go 1.18 решило множество задач типизации коллекций, однако **дженерики не заменяют рефлексию**:
1. **Что могут дженерики:** Обеспечить строгую компилируемую проверку контрактов типов без аллокаций памяти (`[T any]`, `[T constraints.Ordered]`).
2. **Чего НЕ могут дженерики:**
   - Дженерики не могут обойти поля структуры в цикле `for`.
   - Дженерики не могут прочитать структурные теги (`json:"..."`, `db:"..."`).
   - Дженерики не могут динамически вызвать метод по строковому имени, полученному из конфигурационного файла или сети.

### Паттерн «Мост между Дженериками и Рефлексией»:
Обобщенная функция принимает строгий тип `T`, гарантируя типобезопасность на входе, а затем внутри использует `reflect.ValueOf` для структурного анализа полей.

## Решение по шагам

1. Объявим интерфейс `Validatable` с методом `Validate() error`.
2. Реализуем обобщенную функцию `ProcessEntity[T any](entity T) error`.
3. С помощью рефлексии проверим, реализует ли тип `Validatable`.
4. С помощью рефлексии обойдем все поля структуры `T` и залогируем их типы (то, что невозможно сделать на чистых дженериках!).
5. Протестируем на структуре с методом валидации.

## Код решения

**`generics_reflect_bridge.go`**

```go
package main

import (
	"errors"
	"fmt"
	"reflect"
)

type Validatable interface {
	Validate() error
}

type OrderDTO struct {
	OrderID int64
	Amount  float64
}

func (o OrderDTO) Validate() error {
	if o.Amount <= 0 {
		return errors.New("сумма заказа должна быть строго положительной")
	}
	return nil
}

// ProcessEntity совмещает строгую параметрическую типизацию дженериков и глубину рефлексии
func ProcessEntity[T any](entity T) error {
	val := reflect.ValueOf(entity)
	typ := reflect.TypeOf(entity)

	fmt.Printf("=== Обработка сущности типа [%s] через Generic+Reflect ===\n", typ.String())

	// 1. Проверка реализации интерфейса во время выполнения
	validatableType := reflect.TypeOf((*Validatable)(nil)).Elem()
	if typ.Implements(validatableType) {
		// Приводим к интерфейсу и вызываем
		if err := any(entity).(Validatable).Validate(); err != nil {
			return fmt.Errorf("ошибка бизнес-валидации: %w", err)
		}
		fmt.Println("Интерфейс Validatable успешно проверен.")
	}

	// 2. Итерация по полям структуры (НЕВОЗМОЖНО сделать на чистых дженериках!)
	if val.Kind() == reflect.Struct {
		fmt.Printf("Автоматический аудит полей структуры (всего %d):\n", val.NumField())
		for i := 0; i < val.NumField(); i++ {
			fMeta := typ.Field(i)
			fVal := val.Field(i)
			fmt.Printf("  • Поле %-10s (%-8s) = %v\n", fMeta.Name, fMeta.Type, fVal.Interface())
		}
	}

	return nil
}

func main() {
	validOrder := OrderDTO{OrderID: 1001, Amount: 450.0}
	if err := ProcessEntity(validOrder); err != nil {
		fmt.Println("Ошибка:", err)
	}

	fmt.Println()

	invalidOrder := OrderDTO{OrderID: 1002, Amount: -10.0}
	if err := ProcessEntity(invalidOrder); err != nil {
		fmt.Println("Ошибка:", err)
	}
}
```

## Под капотом

Когда инстанцируется функция `ProcessEntity[OrderDTO]`, компилятор Go генерирует специализированную версию функции с конкретным типом `OrderDTO` в словаре типов (Type Dictionary).
Однако на этапе выполнения внутри функции `reflect.TypeOf(entity)` извлекает дескриптор `_type` из словаря типов без необходимости дополнительного боксинга, сохраняя высокую скорость работы.

## Подводные камни

1. **Попытка обойти поля через type parameters:** В Go 1.18–1.24 нельзя написать `for field := range T`, так как параметры типа существуют только во время компиляции. Любая инспекция формы структуры требует вызова пакета `reflect`.

## На собеседовании

**Вопрос с собеседования в Яндекс:** «Почему появление дженериков в Go не сделало пакет reflect устаревшим (deprecated)?»
**Ответ:** Дженерики в Go обеспечивают параметрический полиморфизм во время компиляции, но не предоставляют возможностей интроспекции во время выполнения:
- Нельзя исследовать поля и теги структур (критично для JSON/SQL ORM).
- Нельзя динамически создать тип по описанию из файла схемы.
- Нельзя вызвать метод по строковому имени из сетевого запроса.
Для всех этих сценариев рантайм-рефлексия остается единственным решением в Go.
