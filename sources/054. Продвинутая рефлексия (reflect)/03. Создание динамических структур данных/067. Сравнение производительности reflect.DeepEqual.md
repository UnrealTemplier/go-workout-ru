# Сравнение производительности reflect.DeepEqual против кодогенерации на структурах с time.Time

## Условие

**`reflect.DeepEqual` vs кастомный компаратор.**: Напишите бенчмарк: сравнение двух больших структур с `time.Time` через `reflect.DeepEqual` и через generated `Equal`. Объясните, почему `DeepEqual` медленный (аллокации, рекурсия, interface dispatch) и почему в production предпочитают codegen.

## Теория

Особое коварство `reflect.DeepEqual` проявляется на структурах со сложными типами, такими как `time.Time`:
1. Структура `time.Time` содержит приватные поля `wall uint64`, `ext int64` и указатель на локацию `loc *Location`.
2. При вызове `reflect.DeepEqual(t1, t2)`:
   - Рефлексия сравнивает приватные поля побитово.
   - Сравнивает указатели на часовой пояс `loc`. Два одинаковых времени в UTC могут иметь разные указатели на локацию, и `DeepEqual` вернет `false`!
   - Время с монотонным таймером и без него (после сериализации) не равно по `DeepEqual`, хотя `t1.Equal(t2) == true`!
3. **Скорость:** Сгенерированный метод `Equal` сравнивает поля напрямую за **1 наносекунду**, а `DeepEqual` работает **200–500 наносекунд**.

## Решение по шагам

1. Определим структуру `AuditLog` с полями идентификатора, описания и `time.Time`.
2. Реализуем метод `(a AuditLog) Equal(b AuditLog) bool` с корректным вызовом `a.CreatedAt.Equal(b.CreatedAt)`.
3. Замерим время выполнения 500 000 сравнений через `reflect.DeepEqual` и через `Equal`.
4. Сравним задержки и объясним преимущества кодогенерации.

## Код решения

**`deep_equal_vs_codegen.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"time"
)

type AuditLog struct {
	ID        int64
	Action    string
	IPAddress string
	CreatedAt time.Time
}

// Написанный вручную (или сгенерированный) компаратор
func (a AuditLog) Equal(b AuditLog) bool {
	return a.ID == b.ID &&
		a.Action == b.Action &&
		a.IPAddress == b.IPAddress &&
		a.CreatedAt.Equal(b.CreatedAt) // Корректное сравнение времени по стандарту Go
}

func main() {
	now := time.Now()
	log1 := AuditLog{ID: 1001, Action: "USER_LOGIN", IPAddress: "192.168.1.1", CreatedAt: now}
	log2 := AuditLog{ID: 1001, Action: "USER_LOGIN", IPAddress: "192.168.1.1", CreatedAt: now}

	const iterations = 500_000

	// 1. Нативный сгенерированный Equal
	start := time.Now()
	var dummyGenerated bool
	for i := 0; i < iterations; i++ {
		dummyGenerated = log1.Equal(log2)
	}
	tGenerated := time.Since(start)

	// 2. Стандартный reflect.DeepEqual
	start = time.Now()
	var dummyReflect bool
	for i := 0; i < iterations; i++ {
		dummyReflect = reflect.DeepEqual(log1, log2)
	}
	tReflect := time.Since(start)

	fmt.Printf("Результаты валидации: generated=%v, reflect=%v\n\n", dummyGenerated, dummyReflect)

	fmt.Printf("1. Generated Equal:        %10v (%.2f нс/оп)\n",
		tGenerated, float64(tGenerated.Nanoseconds())/iterations)
	fmt.Printf("2. reflect.DeepEqual:      %10v (%.2f нс/оп)\n\n",
		tReflect, float64(tReflect.Nanoseconds())/iterations)

	fmt.Printf("Кодогенерация быстрее в %.1f раз!\n",
		float64(tReflect)/float64(tGenerated))
}
```

## Под капотом

Сгенерированный метод `Equal` инлайнится компилятором Go (`inline optimization`) в последовательность регистровых сравнений `CMPQ` и вызов `time.Time.Equal`.
Вызов `reflect.DeepEqual` вынужден строить карту `visited`, упаковывать оба объекта в интерфейсы, аллоцировать память под стек рекурсии и побитово исследовать каждое приватное поле `time.Time`.

## Подводные камни

1. **Ложные ошибки в тестах с time.Time:** Если сохранить `time.Now()` в базу данных PostgreSQL/MongoDB и перечитать, наносекундная часть округлится, а монотонные часы сбросятся. `reflect.DeepEqual` вернет `false`, сломав тесты, хотя логически времена абсолютно равны.

## На собеседовании

**Вопрос с собеседования в Lamoda:** «Почему Google разработал инструмент protoc-gen-go, генерирующий метод proto.Equal вместо использования reflect.DeepEqual для protobuf-сообщений?»
**Ответ:** Сообщения Protobuf содержат служебные поля (состояние кэша сериализации `state`, срез неизвестных полей `unknownFields`, счетчики размера `sizeCache`). 
Вызов `reflect.DeepEqual` будет сравнивать эти внутренние поля, что приводит к ложным несовпадениям и дикому замедлению (в 100 раз). Сгенерированный `proto.Equal` сравнивает только значимые бизнес-поля сообщения.
