# Оптимизация рефлексивных аллокаций: кэш индексов полей Field.Index

## Условие

**Оптимизация рефлексивных аллокаций**: Работа с рефлексией в критических путях высоконагруженных систем может сильно замедлять работу из-за частых аллокаций в куче.
* Напишите бенчмарк сравнения прямого доступа к полю структуры и доступа через рефлексивный метод `FieldByName`.
* Оптимизируйте рефлексивный доступ: напишите кэш типов, который при первом обращении сохраняет смещения полей структуры (`Field.Index`), чтобы в дальнейшем получать значения полей мгновенно по индексу, минуя ресурсоемкий поиск по строковому имени. Сравните результаты бенчмарков.

## Теория

Почему `FieldByName("Field")` так медлителен?
1. Поиск выполняет линейный перебор всех полей структуры \(O(N)\).
2. На каждом шаге выполняется строковое сравнение имен.
3. Поиск генерирует временные объекты в куче.

### Техника Field Index Caching:
При старте сервиса (или при первом обращении к типу) метаданные структуры парсятся один раз:
- Имена полей сопоставляются с их индексными путями: `map[string][]int`.
- При обработке каждого запроса обращение к полю выполняется мгновенно через:
  `v.FieldByIndex(cachedIndex)`.
Это ускоряет доступ в **10–15 раз** и снижает аллокации до абсолютного нуля!

## Решение по шагам

1. Создадим структуру `TelemetryRecord` с 5 полями.
2. Реализуем функцию прямого доступа.
3. Реализуем доступ через наивный `FieldByName`.
4. Реализуем кэш типов `TypeCache` с сохранением `[]int` индексов.
5. Проведем замер времени на 500 000 обращений и сравним результаты.

## Код решения

**`field_cache_bench.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"time"
)

type TelemetryRecord struct {
	DeviceID  string
	Timestamp int64
	Voltage   float64
	Current   float64
	Status    string
}

// Кэш индексов полей: [ИмяПоля] -> IndexSlice
type StructIndexCache map[string][]int

func BuildIndexCache(t reflect.Type) StructIndexCache {
	cache := make(StructIndexCache)
	for i := 0; i < t.NumField(); i++ {
		f := t.Field(i)
		cache[f.Name] = f.Index
	}
	return cache
}

func main() {
	record := TelemetryRecord{
		DeviceID:  "DEV-9988",
		Timestamp: 1718000000,
		Voltage:   220.5,
		Current:   1.45,
		Status:    "OK",
	}

	const N = 500_000

	// 1. Прямой доступ (эталон)
	start := time.Now()
	var dummyDirect float64
	for i := 0; i < N; i++ {
		dummyDirect = record.Voltage
	}
	tDirect := time.Since(start)

	// 2. Наивный FieldByName
	v := reflect.ValueOf(record)
	start = time.Now()
	var dummyReflect float64
	for i := 0; i < N; i++ {
		dummyReflect = v.FieldByName("Voltage").Float()
	}
	tReflect := time.Since(start)

	// 3. Оптимизированный FieldByIndex с кэшем
	cache := BuildIndexCache(reflect.TypeOf(record))
	idx := cache["Voltage"]
	start = time.Now()
	var dummyCached float64
	for i := 0; i < N; i++ {
		dummyCached = v.FieldByIndex(idx).Float()
	}
	tCached := time.Since(start)

	fmt.Printf("Результаты бенчмарка (%d итераций, Voltage = %.1f):\n\n", N, dummyDirect+dummyReflect+dummyCached)
	fmt.Printf("1. Прямой доступ:             %10v (%.2f нс/оп)\n", tDirect, float64(tDirect.Nanoseconds())/N)
	fmt.Printf("2. FieldByName (наивный):     %10v (%.2f нс/оп)\n", tReflect, float64(tReflect.Nanoseconds())/N)
	fmt.Printf("3. FieldByIndex (кэшированный):%10v (%.2f нс/оп)\n\n", tCached, float64(tCached.Nanoseconds())/N)

	fmt.Printf("Ускорение кэширования по сравнению с FieldByName: %.1fx!\n",
		float64(tReflect)/float64(tCached))
}
```

ℹ️ Экстремальная оптимизация рефлексивного доступа через кэширование индексов полей

## Под капотом

`FieldByIndex([]int{2})` выполняет один переход по числовому смещению массива полей структуры `structType.fields[2]`. 
В противоположность этому `FieldByName` на каждой итерации выделяет память под хэш строки, сравнивает срез байт с каждым полем структуры по очереди и только затем возвращает `Value`. Кэширование устраняет весь строковый оверхед.

## Подводные камни

1. **Непотокобезопасная запись в кэш:** Если кэш `map` наполняется параллельно из разных горутин без `sync.RWMutex` или `sync.Map`, программа упадет с паникой `concurrent map read and map write`.

## На собеседовании

**Вопрос с собеседования в Wildberries (HighLoad Core):** «Как устроена оптимизация полей в библиотеке jsoniter (json-iterator/go)? Почему она работает быстрее encoding/json?»
**Ответ:** Библиотека `jsoniter` на этапе старта строит скомпилированные кодовые пути: для каждого типа структуры предварительно вычисляет точные физические смещения `Offset` каждого поля и кэширует скомпилированные функции декодирования. Во время разбора JSON она не вызывает строковые методы `FieldByName`, а производит прямую запись по вычисленным адресам.
