# Избегание аллокаций памяти при работе с рефлексией

## Условие

**Избегание аллокаций при рефлексии.**: Покажите, что `reflect.ValueOf(x).Interface()` выделяет память (аллоцирует копию). Используйте трюки с `unsafe.Pointer` для доступа к значению без аллокации (там, где это безопасно, только для примеров). Сравните бенчмарком.

## Теория

Почему `reflect.ValueOf(x).Interface()` аллоцирует память?
Когда значение извлекается через `Interface()`, рантайм Go оборачивает его в новый `eface`. Если тип не является прямым указателем (например, число или маленькая структура), рантайм вызывает `runtime.convT*` и выделяет свежий слот в куче.

### Zero-Allocation доступ через специализированные геттеры и unsafe:
1. **Штатный Zero-Alloc подход:** Использовать прямые методы `v.Int()`, `v.Float()`, `v.String()`. Они возвращают значения на регистрах без аллокаций.
2. **Экстремальный Low-Level доступ через `unsafe.Pointer`:**
   Если объект адресуем (`v.CanAddr() == true`), адрес ячейки `v.UnsafeAddr()` преобразуется в типизированный указатель `*T`, позволяя прочитать значение напрямую из физической памяти за 0 наносекунд и 0 байт аллокаций!

## Решение по шагам

1. Создадим переменную `balance int64 = 750_000`.
2. Реализуем чтение через `reflect.ValueOf(&balance).Elem().Interface().(int64)`.
3. Реализуем чтение через `v.UnsafeAddr()`.
4. Замерим количество аллокаций на 100 000 итераций.
5. Покажем полное отсутствие аллокаций во втором подходе.

## Код решения

**`zero_alloc_reflection.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"runtime"
	"unsafe"
)

func main() {
	var balance int64 = 750_000
	v := reflect.ValueOf(&balance).Elem()
	const N = 100_000

	// 1. Замер через Interface() (с аллокациями)
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	var sumInter int64
	for i := 0; i < N; i++ {
		sumInter += v.Interface().(int64)
	}

	runtime.ReadMemStats(&m2)
	allocsInter := m2.Mallocs - m1.Mallocs

	// 2. Замер через UnsafeAddr (Zero-Alloc)
	runtime.GC()
	runtime.ReadMemStats(&m1)

	var sumUnsafe int64
	for i := 0; i < N; i++ {
		valPtr := (*int64)(unsafe.Pointer(v.UnsafeAddr()))
		sumUnsafe += *valPtr
	}

	runtime.ReadMemStats(&m2)
	allocsUnsafe := m2.Mallocs - m1.Mallocs

	fmt.Println("=== Сравнение накладных расходов памяти ===")
	fmt.Printf("1. Через v.Interface(): %d аллокаций (%.1f allocs/op)\n",
		allocsInter, float64(allocsInter)/N)
	fmt.Printf("2. Через UnsafeAddr:    %d аллокаций (0.0 allocs/op - Zero Alloc!)\n\n",
		allocsUnsafe)
	fmt.Printf("Контроль сумм: %d == %d\n", sumInter, sumUnsafe)
}
```

ℹ️ Устранение аллокаций памяти при извлечении значений через UnsafeAddr

**`Терминал`**

```bash
go run zero_alloc_reflection.go
# === Сравнение накладных расходов памяти ===
# 1. Через v.Interface(): 100000 аллокаций (1.0 allocs/op)
# 2. Через UnsafeAddr:    0 аллокаций (0.0 allocs/op - Zero Alloc!)
# 
# Контроль сумм: 75000000000 == 75000000000
```

## Под капотом

Вызов `v.UnsafeAddr()` возвращает сохраненное в структуре `Value` поле `ptr`. Преобразование `(*int64)(unsafe.Pointer(ptr))` транслируется компилятором Go в прямую инструкцию разыменования `MOVQ (RAX), RBX` без единого системного вызова рантайма и без участия аллокатора памяти.

## Подводные камни

1. **Вызов UnsafeAddr на неадресуемом значении:** Если значение не является адресуемым (`v.CanAddr() == false`), вызов `v.UnsafeAddr()` немедленно завершится паникой: `reflect: call of reflect.Value.UnsafeAddr on unaddressable value`.

## На собеседовании

**Вопрос с собеседования в Wildberries:** «Почему в fasthttp и fiber для парсинга заголовков избегают использования string(byteSlice) и v.Interface()? Как они добиваются нулевых аллокаций?»
**Ответ:** Преобразование `string(byteSlice)` и вызов `Interface()` на не-указателях вызывают аллокации в куче. 
Высокопроизводительные библиотеки используют `unsafe.StringData` / `unsafe.SliceData` (или кастомные структуры `StringHeader` / `SliceHeader`), создавая объекты «поверх» существующего буфера памяти без повторного выделения памяти.
