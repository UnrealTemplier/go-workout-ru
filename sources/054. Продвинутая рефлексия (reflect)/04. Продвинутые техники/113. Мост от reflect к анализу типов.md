# Мост от reflect к анализу типов: сравнение reflect vs go/types vs go/ast

### Исходная формулировка

**Блок 8 (AST)**: — требует уверенного знания синтаксиса Go и типовой системы. Проходите после Блока 7, чтобы понимать, что `go/types` — это «type checker», а `go/ast` — только синтаксис.

## Теория

В экосистеме Go существуют три уровня анализа типов и кода:
1. **`reflect` (Runtime Reflection):**
   - Работает во время исполнения бинарника.
   - Оперирует структурами `runtime._type`.
   - Не имеет доступа к исходному коду, комментариям, именам локальных переменных и неиспользуемым типам.
2. **`go/ast` (Abstract Syntax Tree):**
   - Работает на этапе статического анализа исходников.
   - Представляет собой дерево синтаксических токенов (идентификаторы, литералы, бинарные выражения).
   - Не знает семантики типов: узел `ast.Ident` с именем `User` для AST — просто строка `"User"`, он не знает, структура это или интерфейс.
3. **`go/types` (Type Checker):**
   - Мост между синтаксисом AST и типовой системой компилятора.
   - Вычисляет типы выражений, проверяет правила присваивания, разрешает зависимости пакетов, определяет method sets и размеры структур в байтах на этапе компиляции без запуска программы.

## Решение по шагам

1. Напишите программу, сравнивающую возможности `reflect`, `go/ast` и `go/types`.
2. Распарсите синтаксис через `parser.ParseFile`.
3. Запустите type-checker через `types.Config.Check`.
4. Получите точный тип и размер структуры без запуска самого анализируемого кода.
5. Сделайте выводы о применимости каждого инструмента.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/importer"
	"go/parser"
	"go/token"
	"go/types"
)

const sourceCode = `package demo

type Metric struct {
	ID    int64
	Name  string
	Value float64
}

func (m Metric) IsValid() bool {
	return m.ID > 0
}
`

func main() {
	fset := token.NewFileSet()
	file, err := parser.ParseFile(fset, "demo.go", sourceCode, 0)
	if err != nil {
		panic(err)
	}

	// 1. Уровень go/ast: чисто синтаксический анализ
	fmt.Println("--- 1. Уровень go/ast (Синтаксис) ---")
	for _, decl := range file.Decls {
		if gen, ok := decl.(*ast.GenDecl); ok && gen.Tok == token.TYPE {
			for _, spec := range gen.Specs {
				ts := spec.(*ast.TypeSpec)
				fmt.Printf("Обнаружено объявление типа в коде: %s (узел AST: %T)\n", ts.Name.Name, ts.Type)
			}
		}
	}

	// 2. Уровень go/types: семантический тайп-чекинг
	fmt.Println("\n--- 2. Уровень go/types (Семантическая проверка типов) ---")
	conf := types.Config{
		Importer: importer.Default(),
	}

	info := &types.Info{
		Defs: make(map[*ast.Ident]types.Object),
	}

	pkg, err := conf.Check("demo", fset, []*ast.File{file}, info)
	if err != nil {
		panic(err)
	}

	metricObj := pkg.Scope().Lookup("Metric")
	namedType := metricObj.Type().(*types.Named)
	structType := namedType.Underlying().(*types.Struct)

	fmt.Printf("Тип объекта: %s, Количество полей: %d\n", namedType, structType.NumFields())
	fmt.Printf("Количество методов типа: %d (Метод: %s)\n", namedType.NumMethods(), namedType.Method(0).Name())

	// Вычисление размера структуры на этапе компиляции
	sizes := types.SizesFor("gc", "amd64")
	fmt.Printf("Размер структуры на amd64: %d байт\n", sizes.Sizeof(structType))
}
```

## Под капотом

`go/types` выполняет фазу typechecking компилятора `cmd/compile/internal/types2`. Он строит граф зависимостей пакетов, определяет выравнивание полей и конструирует `types.Package` и `types.Scope`. В отличие от `reflect`, `go/types` не требует компиляции и запуска кода, что делает его безопасным и быстрым для линтеров (`golangci-lint`) и IDE Language Server (`gopls`).

## Подводные камни

1. Попытка выяснить тип переменной только через `go/ast`: в AST есть только имя идентификатора, для определения типа обязателен прогон `go/types.Info`.
2. Зависимости сторонних пакетов: для работы `go/types` необходим валидный импортер (`importer.Default()` или `golang.org/x/tools/go/packages`), иначе тайп-чекер упадет при встрече внешнего пакета.
3. Путаница между типами рантайма и compile-time типами: `reflect.Type` и `types.Type` — несовместимые структуры из разных фаз жизненного цикла программы.

## На собеседовании

**Вопрос с собеседования:** Чем архитектурно отличаются `go/ast` и `go/types`?
**Ответ:** `go/ast` — это синтаксический анализатор (парсер), создающий дерево исходного текста без понимания связей между файлами и семантики языка. `go/types` — семантический анализатор (type checker). Он берет AST, разрешает идентификаторы в конкретные типы (`types.Object`), связывает вызовы методов с декларациями, проверяет правила типизации и строит символьные таблицы области видимости (`Scope`).
