# Архитектура модульной системы плагинов на базе рефлексии

## Условие

Создайте систему плагинов, где каждый плагин регистрирует функции, а приложение вызывает их по событиям.

### Исходная формулировка

**Plugin system**: Создайте систему плагинов, где каждый плагин регистрирует функции, а приложение вызывает их по событиям.

## Теория

Модульные приложения (CMS, API Gateway, микросервисные пайплайны) используют архитектуру плагинов:
1. `Plugin`: сущность, содержащая имя, метаданные и набор хуков (функций).
2. `PluginManager`:
   - Выполняет поиск и загрузку плагинов.
   - Инспектирует методы плагина через рефлексию: методы с префиксом `Hook_` или реализующие определенные сигнатуры автоматически регистрируются в таблице хуков.
3. При срабатывании жизненного цикла (например, `OnRequest`, `BeforeSave`, `OnShutdown`) менеджер последовательно или параллельно вызывает зарегистрированные функции плагинов.

## Решение по шагам

1. Создайте интерфейс `Plugin` с методом `Name() string`.
2. Напишите `PluginHost`, инспектирующий методы переданного объекта через `reflect.TypeOf(p).Method(i)`.
3. Автоматически регистрируйте методы, начинающиеся с `On` (например, `OnUserLogin`).
4. Реализуйте запуск события через `Dispatch(hook string, payload any)`.
5. Протестируйте работу двух плагинов: аудита и нотификаций.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"strings"
)

type Plugin interface {
	Name() string
}

type PluginEngine struct {
	hooks map[string][]reflect.Value
}

func NewPluginEngine() *PluginEngine {
	return &PluginEngine{
		hooks: make(map[string][]reflect.Value),
	}
}

func (pe *PluginEngine) RegisterPlugin(p Plugin) {
	val := reflect.ValueOf(p)
	typ := val.Type()

	fmt.Printf("[PluginEngine] Загрузка плагина: %s\n", p.Name())

	for i := 0; i < typ.NumMethod(); i++ {
		method := typ.Method(i)
		if strings.HasPrefix(method.Name, "On") {
			hookName := method.Name
			pe.hooks[hookName] = append(pe.hooks[hookName], val.Method(i))
			fmt.Printf("  -> Зарегистрирован хук: %s\n", hookName)
		}
	}
}

func (pe *PluginEngine) DispatchEvent(hookName string, args ...any) {
	handlers := pe.hooks[hookName]
	if len(handlers) == 0 {
		return
	}

	inArgs := make([]reflect.Value, len(args))
	for i, arg := range args {
		inArgs[i] = reflect.ValueOf(arg)
	}

	for _, handler := range handlers {
		handler.Call(inArgs)
	}
}

// Плагин 1: Аудит безопасности
type AuditPlugin struct{}

func (AuditPlugin) Name() string { return "SecurityAuditor" }

func (AuditPlugin) OnUserLogin(username string, ip string) {
	fmt.Printf("[AuditPlugin] 🔒 Зафиксирован вход: %s с IP: %s\n", username, ip)
}

// Плагин 2: Отправка метрик в мониторинг
type MetricsPlugin struct{}

func (MetricsPlugin) Name() string { return "PrometheusCollector" }

func (MetricsPlugin) OnUserLogin(username string, ip string) {
	fmt.Printf("[MetricsPlugin] 📈 Метрика auth_events_total{user=%s} увеличена на 1\n", username)
}

func main() {
	engine := NewPluginEngine()

	engine.RegisterPlugin(&AuditPlugin{})
	engine.RegisterPlugin(&MetricsPlugin{})

	fmt.Println("\nЭмуляция событий авторизации:")
	engine.DispatchEvent("OnUserLogin", "vitaly_lead", "192.168.1.105")
}
```

ℹ️ Автоматическая инспекция и регистрация хуков плагинов по конвенции имен On*

**`Терминал`**

```bash

#   -> Зарегистрирован хук: OnUserLogin
# [PluginEngine] Загрузка плагина: PrometheusCollector
#   -> Зарегистрирован хук: OnUserLogin
#
```

## Под капотом

Инспекция `typ.Method(i)` возвращает только экспортированные методы типа. Для получения метода с приемником вызывается `val.Method(i)`, который возвращает связанный метод (bound method value), где указатель на структуру уже сохранен в замыкании. При вызове `handler.Call(inArgs)` аргумент `receiver` передавать не требуется.

## Подводные камни

1. Передача структуры по значению `engine.RegisterPlugin(AuditPlugin{})`: если методы объявлены с pointer-receiver `(p *AuditPlugin)`, `typ.NumMethod()` не увидит их.
2. Несовпадение сигнатур одноименных хуков в разных плагинах: если один плагин ждет 2 аргумента, а второй 1, вызов `handler.Call` запаникует.
3. Отсутствие обработки ошибок и `recover` вокруг `handler.Call`: паника в одном плагине обрушит весь хост-процесс.

## На собеседовании

**Вопрос с собеседования:** Почему в production Go-сервисах (например, HashiCorp Nomad, Vault, Caddy) плагины запускают через gRPC подпроцессы (`go-plugin`), а не встроенный пакет `plugin` или рефлексию?
**Ответ:** Встроенный пакет `plugin` (`.so`) требует совпадения версий компилятора Go и всех зависимостей вплоть до коммита, не работает на Windows, а сбой в коде плагина роняет весь процесс. HashiCorp `go-plugin` запускает плагины как изолированные ОС-процессы и связывается с ними по gRPC/Unix-сокетам, обеспечивая защиту от падений, независимый стек зависимостей и версионирование API.
