# Ограничения динамического создания типов структур в runtime

## Условие

Изучите ограничения reflect — вы не можете создать новый struct type в runtime (только в compile-time). Поймите, почему.

### Исходная формулировка

**Dynamic struct creation**: Изучите ограничения reflect — вы не можете создать новый struct type в runtime (только в compile-time). Поймите, почему.

## Теория

В Go все типы данных транслируются в статические структуры метаданных `runtime._type`, размещаемые линковщиком в секции данных бинарного файла (`.rodata`).

Причины фундаментальных ограничений:
1. **Отсутствие JIT компилятора:** Рантайм Go не содержит компилятора, способного транслировать код новых методов в машинный код архитектуры во время исполнения процесса.
2. **Селекторы и сборка мусора (GC):** Каждому типу структуры соответствует битовая маска указателей (`gcdata`), используемая сборщиком мусора для обхода ссылок в памяти.
3. **Хотя `reflect.StructOf` существует**, он создает лишь анонимный дескриптор типа:
   - Нельзя прикрепить методы: у полученного типа нет method set (набора методов).
   - Нельзя использовать как тип интерфейса: структура не может удовлетворять интерфейсу, требующему методов.
   - Невозможно объявить именованный тип: тип всегда остается анонимным `struct { ... }`.

## Решение по шагам

1. Исследуйте структуру `reflect.Type` и метод `reflect.StructOf`.
2. Продемонстрируйте, что `StructOf` создает безымянный тип (`typ.Name() == ""`).
3. Попытайтесь проверить методы нового типа (`typ.NumMethod() == 0`).
4. Объясните, почему для решения задач динамической типизации в BigTech применяются кодогенерация (`go generate`) и Protobuf/JSON.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"reflect"
)

func main() {
	// Создаем динамический тип структуры во время выполнения
	fields := []reflect.StructField{
		{
			Name: "ID",
			Type: reflect.TypeOf(int64(0)),
			Tag:  reflect.StructTag(`json:"id"`),
		},
		{
			Name: "Title",
			Type: reflect.TypeOf(""),
			Tag:  reflect.StructTag(`json:"title"`),
		},
	}

	dynType := reflect.StructOf(fields)

	fmt.Printf("Динамический тип: %v\n", dynType)
	fmt.Printf("Имя типа (Name): %q (пусто, так как тип анонимный!)\n", dynType.Name())
	fmt.Printf("Количество методов: %d (к нему НЕЛЬЗЯ добавить методы!)\n", dynType.NumMethod())
	fmt.Printf("Размер типа в байтах: %d\n", dynType.Size())
	fmt.Printf("Выравнивание (Align): %d\n", dynType.Align())

	// Создаем экземпляр структуры этого типа
	dynVal := reflect.New(dynType).Elem()
	dynVal.FieldByName("ID").SetInt(501)
	dynVal.FieldByName("Title").SetString("Dynamic Struct Spec")

	fmt.Printf("Значение: %+v\n", dynVal.Interface())
}
```

ℹ️ Исследование ограничений анонимного типа reflect.StructOf

```bash
# Размер типа в байтах: 24

# Значение: {ID:501 Title:Dynamic Struct Spec}
```

## Под капотом

`reflect.StructOf` вычисляет смещения полей (`offset`), выравнивание (`align`) и размер (`size`), а также компилирует рантаймовую битовую маску указателей `gcdata` для сборщика мусора. Сконструированный дескриптор регистрируется во внутренней хэш-таблице `runtime.lookupType`, предотвращая дублирование дескрипторов одинаковых анонимных структур.

## Подводные камни

1. Заблуждение о возможности создать замену интерфейсной реализации: `StructOf` не позволяет привязать функции в качестве методов, поэтому тип не может удовлетворять интерфейсам.
2. Неэкспортированные поля в `reflect.StructOf`: в Go 1.7+ `StructOf` запрещает создавать неэкспортированные поля с чужими пакетами во избежание взлома инкапсуляции.
3. Утечка памяти при бесконечной генерации уникальных типов в цикле: созданные дескрипторы типов кэшируются рантаймом навсегда.

## На собеседовании

**Вопрос с собеседования:** Почему в Go дескрипторы типов, созданные через `reflect.StructOf`, никогда не удаляются сборщиком мусора?
**Ответ:** Метаданные типов регистрируются во внутренних глобальных таблицах рантайма (`runtime.lookupType`), на которые ссылаются структуры интерфейсов (`itab`, `_type`). Рантайм Go не реализует выгрузку классов/типов (class unloading), как JVM, поэтому создание неограниченного числа уникальных типов в цикле приведет к перманентной утечке памяти в `runtime`.
