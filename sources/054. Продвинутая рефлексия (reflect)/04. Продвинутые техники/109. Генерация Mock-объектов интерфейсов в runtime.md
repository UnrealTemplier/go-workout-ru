# Генерация Mock-объектов интерфейсов в runtime

## Условие

Напишите функцию, которая генерирует mock-объект для любого интерфейса в runtime.

### Исходная формулировка

**Mock generator через reflect**: Напишите функцию, которая генерирует mock-объект для любого интерфейса в runtime.

## Теория

Библиотеки тестирования (например, `testify/mock`, `gomock`) создают имитации зависимостей (моки).
При рефлексивном подходе без кодогенерации:
1. Мок-объект хранит реестр вызовов и настроенных ответов (`Calls map[string][]any`, `Expectations map[string][]any`).
2. Для каждого метода интерфейса создается функция перехвата через `reflect.MakeFunc`.
3. При вызове:
   - Записываются аргументы вызова.
   - Проверяется счетчик вызовов (`CalledTimes`).
   - Возвращаются заранее сконфигурированные значения.
4. В конце теста выполняется верификация (`AssertExpectations`).

## Решение по шагам

1. Создайте структуру `MockRecorder` для фиксации истории вызовов.
2. Реализуйте метод `On(methodName string, returnVals ...any)`.
3. Реализуйте метод `MakeMockFunc(methodName string, targetFuncType reflect.Type) reflect.Value`.
4. Настройте возвращаемые значения и протестируйте вызовы.
5. Проверьте assert на вызовы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"sync"
)

type RuntimeMock struct {
	mu           sync.Mutex
	calls        map[string][][]any
	returnValues map[string][]any
}

func NewRuntimeMock() *RuntimeMock {
	return &RuntimeMock{
		calls:        make(map[string][][]any),
		returnValues: make(map[string][]any),
	}
}

func (m *RuntimeMock) On(methodName string, returnVals ...any) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.returnValues[methodName] = returnVals
}

func (m *RuntimeMock) BindMethod(methodName string, fnType reflect.Type) reflect.Value {
	wrapper := func(in []reflect.Value) []reflect.Value {
		m.mu.Lock()
		defer m.mu.Unlock()

		// Логируем переданные аргументы
		var args []any
		for _, arg := range in {
			args = append(args, arg.Interface())
		}
		m.calls[methodName] = append(m.calls[methodName], args)

		retVals := m.returnValues[methodName]
		if len(retVals) != fnType.NumOut() {
			panic(fmt.Sprintf("Mock error: метод %s ожидает %d выходных значений, настроено %d",
				methodName, fnType.NumOut(), len(retVals)))
		}

		out := make([]reflect.Value, len(retVals))
		for i, rv := range retVals {
			if rv == nil {
				out[i] = reflect.Zero(fnType.Out(i))
			} else {
				out[i] = reflect.ValueOf(rv)
			}
		}
		return out
	}

	return reflect.MakeFunc(fnType, wrapper)
}

func (m *RuntimeMock) AssertCalled(methodName string, expectedTimes int) error {
	m.mu.Lock()
	defer m.mu.Unlock()
	actual := len(m.calls[methodName])
	if actual != expectedTimes {
		return fmt.Errorf("метод %s вызван %d раз, ожидалось %d", methodName, actual, expectedTimes)
	}
	return nil
}

func main() {
	mock := NewRuntimeMock()

	// Конфигурируем поведение для метода GetUserBalance
	mock.On("GetUserBalance", int64(75000), nil)

	// Создаем функцию с сигнатурой func(userID int64) (int64, error)
	targetSig := reflect.TypeOf(func(int64) (int64, error) { return 0, nil })
	mockFn := mock.BindMethod("GetUserBalance", targetSig).Interface().(func(int64) (int64, error))

	// Вызовы в тестируемом коде
	bal1, err1 := mockFn(101)
	bal2, err2 := mockFn(102)

	fmt.Printf("Вызов 1: Balance=%d, err=%v\n", bal1, err1)
	fmt.Printf("Вызов 2: Balance=%d, err=%v\n", bal2, err2)

	// Проверка вызовов
	if err := mock.AssertCalled("GetUserBalance", 2); err != nil {
		fmt.Println("Ошибка утверждения:", err)
	} else {
		fmt.Println("Успех: проверка вызовов мока пройдена!")
	}
}
```

## Под капотом

`reflect.Zero(fnType.Out(i))` используется для генерации типизированного `nil` для интерфейсов или указателей (например `error`), предотвращая панику при попытке создать `reflect.ValueOf(nil)`. Запись аргументов в слайс `m.calls` позволяет инспектировать параметры каждого конкретного вызова (`AssertCalledWith`).

## Подводные камни

1. Передача нетипизированного `nil` в `reflect.ValueOf`: вызовет невалидный `reflect.Value`, при попытке возврата произойдет паника.
2. Гонка данных: если тестируемый код вызывает мок из нескольких параллельных горутин, обращение к `m.calls` без мьютекса приведет к data race.
3. Несоответствие типов возвращаемых значений типам в сигнатуре интерфейса.

## На собеседовании

**Вопрос с собеседования:** Почему в Go-сообществе для моков чаще используют генерацию кода (`mockgen`, `minimock`), чем чисто рефлексивный подход?
**Ответ:** Статическая типизация и надежность. Сгенерированный код мока реализует интерфейс на уровне компилятора: если сигнатура метода интерфейса изменится при рефакторинге, сгенерированный мок сразу вызовет ошибку компиляции тестов. Рефлексивный мок упадет только во время прогона теста в рантайме. Кроме того, автодополнение IDE работает только со статическими моками.
