# Архитектурный диспетчер методов и бенчмаркинг накладных расходов

## Условие

**Динамический вызов метода.**: Напишите диспетчер: по имени метода (строка) и `any` (получатель) вызывайте метод через `reflect.Type.MethodByName` + `Value.Method(i).Call`. Сравните latency с `type switch` на конкретные типы. Объясните, когда `reflect` оправдан, а когда — нет.

## Теория

При проектировании высоконагруженных шлюзов сообщений и RPC-обработчиков часто встает выбор архитектуры диспетчеризации:
1. **Статическая диспетчеризация (Type Switch / Интерфейс):**
   Компилятор генерирует таблицу виртуальных методов (itab). Вызов выполняется за одну косвенную инструкцию процессора `CALL [RAX + offset]`. Время вызова: **~2 наносекунды**.
2. **Динамическая диспетчеризация через Reflect (`MethodByName` + `Call`):**
   - Поиск по строке в массиве методов: \(O(N)\) строковых сравнений.
   - Аллокация среза аргументов `[]reflect.Value`.
   - Проверка типов параметров на каждый аргумент.
   - Вызов через рантайм-батут `reflectcall`.
   Время вызова: **~50–150 наносекунд** (в 30–70 раз медленнее!).

### Когда рефлексия оправдана:
- Универсальные RPC-серверы (gRPC gateway, JSON-RPC), где сигнатуры методов заранее неизвестны во время компиляции фреймворка.
- Генераторы моков, плагины и динамические скриптовые движки.
### Когда рефлексия НЕ оправдана:
- Высоконагруженные конвейеры обработки данных (HighLoad Pipelines, торговые шлюзы, брокеры сообщений), где критична каждая наносекунда latency.

## Решение по шагам

1. Создадим интерфейс `Handler` с методом `Process() int`.
2. Реализуем тип `Service`, удовлетворяющий интерфейсу.
3. Реализуем вызов через `type switch` / интерфейс.
4. Реализуем вызов через рефлексию `MethodByName().Call()`.
5. Проведем замер времени на 1 000 000 итераций и выведем наглядную разницу.

## Код решения

**`dispatcher_bench.go`**

```go
package main

import (
	"fmt"
	"reflect"
	"time"
)

type Worker interface {
	DoWork() int
}

type HeavyService struct{}

func (s HeavyService) DoWork() int {
	return 42
}

func benchmarkStatic(w Worker, iterations int) time.Duration {
	start := time.Now()
	for i := 0; i < iterations; i++ {
		_ = w.DoWork()
	}
	return time.Since(start)
}

func benchmarkReflect(target any, iterations int) time.Duration {
	v := reflect.ValueOf(target)
	m := v.MethodByName("DoWork")

	start := time.Now()
	for i := 0; i < iterations; i++ {
		res := m.Call(nil)
		_ = res[0].Int()
	}
	return time.Since(start)
}

func main() {
	svc := HeavyService{}
	const N = 1_000_000

	fmt.Printf("Запуск сравнительного бенчмарка (%d итераций)...\n\n", N)

	dStatic := benchmarkStatic(svc, N)
	dReflect := benchmarkReflect(svc, N)

	fmt.Printf("1. Статический вызов через интерфейс: %10v (%.2f нс/оп)\n",
		dStatic, float64(dStatic.Nanoseconds())/N)
	fmt.Printf("2. Динамический вызов через reflect:   %10v (%.2f нс/оп)\n\n",
		dReflect, float64(dReflect.Nanoseconds())/N)

	ratio := float64(dReflect) / float64(dStatic)
	fmt.Printf("Рефлексивный вызов медленнее в %.1f раз!\n", ratio)
}
```

## Под капотом

Статический интерфейсный вызов разворачивается компилятором в вызов через `itab`:
`MOVQ 24(RAX), RBX; CALL RBX`.
В рефлексивном же вызове `m.Call(nil)`:
1. Аллоцируется слайс результатов `[]Value`.
2. Функция `reflectcall` переключает контекст регистров, копирует стек и проверяет флаги GC.
3. Каждое возвращенное значение заворачивается в отдельный `reflect.Value` в куче.

## Подводные камни

1. **Поиск MethodByName внутри горячего цикла:** Поиск метода по имени — тяжелая строковая операция. Если динамический вызов необходим, метод `MethodByName` нужно вызывать **один раз** при инициализации, кэшируя `reflect.Value` метода.

## На собеседовании

**Вопрос с собеседования в Wildberries (HighLoad Core):** «Почему в высокопроизводительных микросервисах на Go избегают использования reflect.Call в пользу кодогенерации (например, protoc-gen-go, easyjson)?»
**Ответ:** Потому что `reflect.Call` создает до 5–10 аллокаций в куче на каждый вызов и работает в десятки раз медленнее прямого машинного кода. 
Кодогенераторы генерируют чистый Go-код с прямыми вызовами методов и строгой типизацией во время компиляции, обеспечивая нулевые накладные расходы рантайма и отсутствие пауз сборщика мусора.
