# Адресуемость (CanAddr) и изменяемость (CanSet) в рантайме

## Условие

**Settability и адресуемость.**: Напишите программу, которая демонстрирует панику при `reflect.ValueOf(x).SetInt(42)` и корректную работу при `reflect.ValueOf(&x).Elem().SetInt(42)`. Объясните разницу между `CanAddr`, `CanSet` и почему `ValueOf` по значению возвращает неадресуемую копию.

## Теория

Концепция **Settability (изменяемости)** — один из самых частых источников ошибок при работе с рефлексией.

### Механика работы:
1. Когда мы вызываем `reflect.ValueOf(x)`, переменная `x` передается в функцию по значению. Внутри функции создается копия данных.
2. Объект `reflect.Value`, созданный из копии, не знает адрес исходной переменной. Если бы рантайм позволил вызвать `.SetInt(42)`, изменилась бы временная копия внутри интерфейса, а исходная переменная `x` осталась бы неизменной. Во избежание таких коварных багов Go генерирует фатальную панику.
3. Чтобы изменить переменную, мы передаем ее адрес: `reflect.ValueOf(&x)`. Здесь `ValueOf` получает указатель. Указатель по-прежнему не является изменяемым напрямую (мы не хотим заменять сам адрес).
4. Вызов `.Elem()` разыменовывает указатель и возвращает `reflect.Value`, представляющий **саму исходную переменную `x`**. Теперь `CanAddr() == true` и `CanSet() == true`!

## Решение по шагам

1. Объявим переменную `count := 10`.
2. Попробуем изменить `count` напрямую через `reflect.ValueOf(count).SetInt(42)` внутри блока `recover()`.
3. Исследуем флаги `CanAddr()` и `CanSet()` для `reflect.ValueOf(count)`.
4. Исследуем флаги для `reflect.ValueOf(&count)`.
5. Вызовем `.Elem()` и изменим значение переменной на `42`.
6. Убедимся, что `count` действительно изменился.

## Код решения

**`settability_deep.go`**

```go
package main

import (
	"fmt"
	"reflect"
)

func main() {
	var count int = 10

	// 1. Попытка изменения по значению
	vVal := reflect.ValueOf(count)
	fmt.Printf("[По значению] CanAddr: %-5v | CanSet: %-5v\n", vVal.CanAddr(), vVal.CanSet())

	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("[Ожидаемая паника]: %v\n", r)
			}
		}()
		vVal.SetInt(42) // Вызовет панику!
	}()

	// 2. Исследование указателя
	vPtr := reflect.ValueOf(&count)
	fmt.Printf("[Указатель]    CanAddr: %-5v | CanSet: %-5v\n", vPtr.CanAddr(), vPtr.CanSet())

	// 3. Разыменование через Elem()
	vElem := vPtr.Elem()
	fmt.Printf("[vPtr.Elem()]  CanAddr: %-5v | CanSet: %-5v\n", vElem.CanAddr(), vElem.CanSet())

	if vElem.CanSet() {
		vElem.SetInt(42)
		fmt.Printf("Успешное изменение! Исходная переменная count = %d\n", count)
	}
}
```

ℹ️ Пошаговая проверка CanAddr и CanSet при мутации значений

**`Терминал`**

```bash
go run settability_deep.go
# [По значению] CanAddr: false | CanSet: false
# [Ожидаемая паника]: reflect: reflect.Value.SetInt using unaddressable value
# [Указатель]    CanAddr: false | CanSet: false
# [vPtr.Elem()]  CanAddr: true  | CanSet: true 
# Успешное изменение! Исходная переменная count = 42
```

## Под капотом

Во внутреннем представлении `reflect.Value`:
- `vVal = reflect.ValueOf(count)`: флаг `flagAddr` равен 0. Метод `CanAddr()` реализован как:
  ```go
  func (v Value) CanAddr() bool {
      return v.flag&flagAddr != 0
  }
  ```
- `vPtr = reflect.ValueOf(&count)`: поле `ptr` содержит адрес `&count`, но флаг `flagAddr` по-прежнему 0, так как сам указатель передан как значение.
- `vPtr.Elem()`: считывает адрес из `ptr`, сохраняет его как целевой адрес данных нового `Value` и выставляет бит `flagAddr = 1 << 8`.

## Подводные камни

1. **Изменение элемента мапы:** Элементы мапы в Go не являются адресуемыми (`CanAddr() == false`). Нельзя сделать `reflect.ValueOf(myMap).MapIndex(key).Set(...)`. Изменение элемента мапы требует извлечения значения, изменения и повторного вызова `SetMapIndex`.

## На собеседовании

**Вопрос с собеседования в Яндекс:** «Почему элементы среза являются адресуемыми (slice[i].CanAddr() == true), а элементы хеш-таблицы (map[k].CanAddr() == false)?»
**Ответ:** Элементы среза расположены в непрерывном фиксированном массиве памяти, и их физический адрес стабилен.
Элементы мапы могут перемещаться в памяти во время эвакуации бакетов при росте хеш-таблицы (map growth / rehashing). Если бы язык позволил взять указатель на значение внутри бакета мапы, этот указатель стал бы невалидным при следующей вставке в мапу, вызвав повреждение памяти.
