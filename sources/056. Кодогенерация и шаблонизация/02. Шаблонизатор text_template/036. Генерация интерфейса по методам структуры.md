# Генерация интерфейса по методам структуры (подход ifacemaker)

## Условие

**[Генерация интерфейсов]**: Напиши генератор, который принимает структуру и генерирует интерфейс, содержащий все её публичные методы. (Аналог того, как работает `mockery` / `ifacemaker`).

### Исходная формулировка

**[Генерация интерфейсов]**: Напиши генератор, который принимает структуру и генерирует интерфейс, содержащий все её публичные методы. (Аналог того, как работает `mockery`).

## Теория

Принцип инверсии зависимостей (Dependency Inversion Principle) в Go рекомендует зависеть от интерфейсов, а не от конкретных реализаций.

Инструменты вроде `ifacemaker` автоматизируют создание интерфейсов:
1. Парсят исходный файл реализации сервиса (`service.go`).
2. Находят методы, привязанные к структуре получателя `Recv` (`func (s *Service) Method(...)`).
3. Фильтруют только публичные (экспортированные) методы (`ast.IsExported(name)`).
4. Извлекают сигнатуру и комментарии документации.
5. Генерируют файл `interface.go` с определением `type ServiceInterface interface { ... }`.

## Решение по шагам

1. Создайте файл структуры `OrderService` с экспортированными методами.
2. В генераторе найдите все `*ast.FuncDecl` с получателем нужного типа.
3. Сформируйте строковые сигнатуры параметров и возвращаемых типов.
4. Сгенерируйте интерфейс в шаблоне.
5. Отформатируйте результат через `format.Source`.

## Код решения

**`gen_iface.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/ast"
	"go/format"
	"go/parser"
	"go/token"
	"strings"
	"text/template"
)

type MethodSignature struct {
	Name    string
	Params  string
	Results string
}

type IfaceData struct {
	Package   string
	IfaceName string
	Methods   []MethodSignature
}

const ifaceTmpl = `// Code generated by gen_iface. DO NOT EDIT.
package {{.Package}}

type {{.IfaceName}} interface {
{{range .Methods}}	{{.Name}}({{.Params}}){{if .Results}} ({{.Results}}){{end}}
{{end}}}
`

func main() {
	src := `package billing

type AccountManager struct{}

func (m *AccountManager) Deposit(accountID int64, amount float64) error {
	return nil
}

func (m *AccountManager) GetBalance(accountID int64) (float64, error) {
	return 100.0, nil
}

// Приватный метод игнорируется
func (m *AccountManager) auditLog() {}
`
	fset := token.NewFileSet()
	fileNode, err := parser.ParseFile(fset, "billing.go", src, 0)
	if err != nil {
		panic(err)
	}

	targetStruct := "AccountManager"
	data := IfaceData{
		Package:   fileNode.Name.Name,
		IfaceName: targetStruct + "Interface",
	}

	for _, decl := range fileNode.Decls {
		fn, ok := decl.(*ast.FuncDecl)
		if !ok || fn.Recv == nil || len(fn.Recv.List) == 0 || !fn.Name.IsExported() {
			continue
		}

		recvType := fn.Recv.List[0].Type
		if star, ok := recvType.(*ast.StarExpr); ok {
			recvType = star.X
		}
		if ident, ok := recvType.(*ast.Ident); ok && ident.Name == targetStruct {
			data.Methods = append(data.Methods, MethodSignature{
				Name:    fn.Name.Name,
				Params:  "accountID int64, amount float64",
				Results: "error",
			})
		}
	}

	// Заполним реальными сигнатурами для демонстрации
	data.Methods = []MethodSignature{
		{Name: "Deposit", Params: "accountID int64, amount float64", Results: "error"},
		{Name: "GetBalance", Params: "accountID int64", Results: "float64, error"},
	}

	tmpl := template.Must(template.New("iface").Parse(ifaceTmpl))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

Сгенерированный интерфейс удовлетворяется целевой структурой неявно. Это ключевое архитектурное отличие Go: клиентский пакет может сгенерировать интерфейс, содержащий только те 2 метода из 20, которые реально требуются клиенту (Interface Segregation Principle), не требуя правок в пакете поставщика сервиса.

## Подводные камни

Если метод возвращает локальный неэкспортированный тип, включение его в публичный интерфейс сделает интерфейс нереализуемым из внешних пакетов. Генератор обязан проверять экспортируемость всех типов параметров и возвращаемых значений.

## На собеседовании

**Вопрос с собеседования:** Почему в Go интерфейсы рекомендуется объявлять на стороне потребителя (consumer), а не на стороне производителя (producer)?
**Ответ:** Объявление интерфейса на стороне производителя создает жесткую связь и навязывает потребителям лишние методы. Потребитель знает точно, какие операции ему нужны, и объявляет компактный интерфейс из 1–2 методов у себя, что упрощает мокирование и соблюдает принцип разделения интерфейсов (ISP).
