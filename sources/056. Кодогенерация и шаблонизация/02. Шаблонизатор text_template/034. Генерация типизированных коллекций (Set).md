# Генерация типизированных коллекций (Set) через text/template

## Условие

**Генерация типизированных коллекций через `text/template`**: Напишите генератор строго типизированных множеств (Set). Напишите шаблон кода для структуры множества в виде текста с плейсхолдерами, который содержит методы `Add()`, `Contains()`, `Remove()`. Сгенерируйте множества для `int` и `string`.

### Исходная формулировка

**Генерация типизированных коллекций через `text/template`**: Напишите генератор строго типизированных множеств (Set). Напишите шаблон кода для структуры множества в виде текста с использованием пакета `text/template` [532]. Напишите утилиту, которая принимает на вход имя типа (например, `User` или `Order`) и на основе шаблона генерирует готовый файл коллекции (например, `user_set.go` с методами `Add`, `Remove`, `Contains`), заменяя параметры шаблона на реальное имя типа.

## Теория

До появления дженериков в Go 1.18 кодогенерация являлась главным официальным механизмом создания обобщенных структур данных (Set, Queue, LinkedList, RingBuffer).

Даже с появлением дженериков кодогенерация коллекций остается востребованной:
- Для генерации сериализуемых и специализированных структур данных (например, BitSet на базе среза `[]uint64`).
- Для обратной совместимости библиотек со старыми версиями компилятора Go.
- Для устранения оверхеда полиморфных вызовов интерфейсных ограничений.

## Решение по шагам

1. Опишите шаблон `Set` со структурой `type {{.Name}}Set struct { m map[{{.Type}}]struct{} }`.
2. Реализуйте методы `New{{.Name}}Set()`, `Add(item {{.Type}})`, `Contains(item {{.Type}}) bool`, `Remove(item {{.Type}})`.
3. Сгенерируйте `IntSet` и `StringSet`.
4. Отформатируйте сгенерированный файл через `format.Source`.

## Код решения

**`gen_set.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/format"
	"text/template"
)

type SetSpec struct {
	Prefix string
	Type   string
}

type SetGeneratorData struct {
	Package string
	Sets    []SetSpec
}

const setTemplate = `// Code generated by gen_set. DO NOT EDIT.
package {{.Package}}

{{range .Sets}}
type {{.Prefix}}Set struct {
	items map[{{.Type}}]struct{}
}

func New{{.Prefix}}Set() *{{.Prefix}}Set {
	return &{{.Prefix}}Set{
		items: make(map[{{.Type}}]struct{}),
	}
}

func (s *{{.Prefix}}Set) Add(val {{.Type}}) {
	if s.items == nil {
		s.items = make(map[{{.Type}}]struct{})
	}
	s.items[val] = struct{}{}
}

func (s *{{.Prefix}}Set) Contains(val {{.Type}}) bool {
	if s.items == nil {
		return false
	}
	_, ok := s.items[val]
	return ok
}

func (s *{{.Prefix}}Set) Remove(val {{.Type}}) {
	if s.items != nil {
		delete(s.items, val)
	}
}

func (s *{{.Prefix}}Set) Len() int {
	return len(s.items)
}
{{end}}
`

func main() {
	data := SetGeneratorData{
		Package: "collections",
		Sets: []SetSpec{
			{Prefix: "Int", Type: "int"},
			{Prefix: "String", Type: "string"},
			{Prefix: "Int64", Type: "int64"},
		},
	}

	tmpl := template.Must(template.New("set").Parse(setTemplate))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

Использование пустой структуры `struct{}` в качестве значения мапы `map[T]struct{}` — канонический способ реализации Set в Go. Значение `struct{}` занимает ровно 0 байт памяти (`unsafe.Sizeof(struct{}{}) == 0`), поэтому хэш-таблица хранит исключительно ключи без накладных расходов на хранение флагов `bool`.

## Подводные камни

Коллекции на базе стандартных мап не являются потокобезопасными: одновременный вызов `Add` и `Contains` из разных горутин приведет к фатальной панике `fatal error: concurrent map read and map write`. Если коллекция предназначена для многопоточного использования, в генератор добавляют поле `sync.RWMutex`.

## На собеседовании

**Вопрос с собеседования:** В каких случаях генерация специализированных коллекций (например, `IntSet`) превосходит generic-коллекцию `Set[T comparable]`?
**Ответ:** Для примитивных целочисленных типов сгенерированный `BitSet` на базе битовых масок `[]uint64` с битовыми операциями (`AND`, `OR`) работает в 10–20 раз быстрее хэш-мапы и потребляет в 64 раза меньше оперативной памяти. Сделать такую битовую оптимизацию через универсальный дженерик `[T comparable]` невозможно из-за отсутствия битовых операций в ограничении `comparable`.
