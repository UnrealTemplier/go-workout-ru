# Генератор DI-контейнера времени сборки (подход Google Wire)

## Условие

**Генератор DI-контейнера (упрощённый).**: Сканируйте пакет, находите конструкторы (`func NewXxx(...) *Xxx`), стройте граф зависимостей по типам параметров, генерируйте `func InitializeApp() (*App, error)`. Объясните преимущество compile-time DI перед runtime DI (uber-go/dig).

### Исходная формулировка

**Генератор DI-контейнера (упрощённый).**: Сканируйте пакет, находите конструкторы (`func NewXxx(...) *Xxx`), стройте граф зависимостей по типам параметров, генерируйте `func InitializeApp() *App` с правильным порядком вызовов. Используйте `go/ast` + `go/types`. Объясните, как `dig`/`wire` решают проблему циклических зависимостей.

## Теория

Внедрение зависимостей (Dependency Injection) в Go реализуется двумя путями:
1. **Runtime DI (Uber Dig, FX):** граф зависимостей строится в рантайме через рефлексию `reflect.ValueOf`. Минусы: ошибки отсутствующих зависимостей падают в рантайме при старте пода, замедляется запуск, сложно отлаживать.
2. **Compile-time DI (Google Wire):** граф строится статическим анализом AST конструкторов `New...`. Генератор разрешает зависимости в топологическом порядке и генерирует обычный линейный Go-код `db := NewDB(); repo := NewRepo(db); app := NewApp(repo)`. Ошибки отсутствующих зависимостей выявляются во время сборки.

## Решение по шагам

1. Опишите набор конструкторов: `NewDB() *sql.DB`, `NewRepo(db *sql.DB) *Repository`, `NewService(r *Repository) *Service`.
2. В генераторе постройте направленный ациклический граф (DAG).
3. Выполните топологическую сортировку вершин графа.
4. Сгенерируйте функцию инициализации приложения `InitializeApp() (*Service, error)`.
5. Отформатируйте код через `format.Source`.

## Код решения

**`gen_di.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/format"
	"text/template"
)

type StepInfo struct {
	VarName     string
	Constructor string
	Args        string
}

type DIGeneratorData struct {
	PackageName string
	Steps       []StepInfo
	TargetVar   string
	TargetType  string
}

const diTmpl = `// Code generated by gen_di (Google Wire style). DO NOT EDIT.
package {{.PackageName}}

func InitializeApp() (*{{.TargetType}}, error) {
{{range .Steps}}	{{.VarName}}, err := {{.Constructor}}({{.Args}})
	if err != nil {
		return nil, err
	}
{{end}}
	return {{.TargetVar}}, nil
}
`

func main() {
	data := DIGeneratorData{
		PackageName: "app",
		TargetType:  "Server",
		TargetVar:   "server",
		Steps: []StepInfo{
			{VarName: "db", Constructor: "NewDatabase", Args: ""},
			{VarName: "repo", Constructor: "NewUserRepository", Args: "db"},
			{VarName: "service", Constructor: "NewAuthService", Args: "repo"},
			{VarName: "server", Constructor: "NewServer", Args: "service"},
		},
	}

	tmpl := template.Must(template.New("di").Parse(diTmpl))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

`google/wire` использует топологическую сортировку Кана (Kahn's algorithm) или поиск в глубину (DFS) для обнаружения циклов в зависимостях (`A -> B -> A`). Если обнаружен цикл или провайдер для определенного типа не найден, генератор выдает ошибку с указанием полной цепочки несоответствия еще до компиляции приложения.

## Подводные камни

Если в конструкторах возвращаются два одинаковых базовых типа (например, `NewPort() int` и `NewTimeout() int`), DI-генератор не сможет различить их по типу без использования уникальных псевдонимов (`type Port int`, `type Timeout int`). Всегда создавайте семантические типы для конфигураций.

## На собеседовании

**Вопрос с собеседования:** Почему в production-архитектурах Google, Wildberries и Ozon выбирают Google Wire (compile-time DI), а не Uber FX (runtime DI)?
**Ответ:** 1) Полная прозрачность: сгенерированный файл `wire_gen.go` содержит чистый, линейный, понятный человеку Go-код, который легко отлаживать по стектрейсам. 2) Нулевой рантайм-оверхед: отсутствие рефлексии ускоряет холодный запуск контейнеров в Kubernetes. 3) Невозможность пропустить незарегистрированную зависимость в продакшен: бинарник просто не скомпилируется.
