# Генератор mock-интерфейсов (упрощенный mockgen)

## Условие

**Генератор mock-интерфейсов (упрощённый `mockgen`).**: Напишите tool, который принимает `.go`-файл с интерфейсом и генерирует `struct MockXxx` с методами-заглушками, возвращающими zero values. Используйте `go/ast` для парсинга `ast.InterfaceType` и `text/template` для вывода.

## Теория

Мокирование интерфейсов — основа изолированного модульного тестирования. Утилиты вроде `mockgen` (GoMock) или `minimock` автоматизируют создание заглушек.

Принцип работы генератора моков на базе AST:
1. Парсинг файла через `parser.ParseFile`.
2. Поиск узла `*ast.InterfaceType` внутри спецификации типа `*ast.TypeSpec`.
3. Для каждого метода из `InterfaceType.Methods.List`:
   - Извлечение имени метода из `field.Names[0].Name`.
   - Анализ параметров и возвращаемых значений из `*ast.FuncType`.
4. Генерация структуры мока с полями-замыканиями вида `Func func(...) (...)` для переопределения поведения в тестах или возврат zero values по умолчанию.

## Решение по шагам

1. Создайте входной файл с интерфейсом `UserRepository` с методами `FindByID(id int64) (*User, error)` и `Save(u *User) error`.
2. В генераторе найдите интерфейс по имени.
3. Соберите список методов и типы возвращаемых значений.
4. Сгенерируйте структуру `MockUserRepository` с реализацией всех методов интерфейса.
5. Отформатируйте сгенерированный код через `go/format.Source`.

## Код решения

**`gen_mock.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/ast"
	"go/format"
	"go/parser"
	"go/token"
	"text/template"
)

type MethodDesc struct {
	Name       string
	Params     string
	Returns    string
	ZeroReturn string
}

type MockData struct {
	PackageName   string
	InterfaceName string
	MockName      string
	Methods       []MethodDesc
}

const mockTemplate = `// Code generated by gen_mock. DO NOT EDIT.
package {{.PackageName}}

type {{.MockName}} struct {
{{range .Methods}}	{{.Name}}Func func({{.Params}}) ({{.Returns}})
{{end}}}

{{range .Methods}}
func (m *{{$.MockName}}) {{.Name}}({{.Params}}) ({{.Returns}}) {
	if m.{{.Name}}Func != nil {
		return m.{{.Name}}Func({{.Params}})
	}
	return {{.ZeroReturn}}
}
{{end}}
`

func main() {
	src := `package service

type PaymentGateway interface {
	Charge(amount int64) error
	Refund(txID string) bool
}
`
	fset := token.NewFileSet()
	node, err := parser.ParseFile(fset, "gateway.go", src, 0)
	if err != nil {
		panic(err)
	}

	data := MockData{
		PackageName:   node.Name.Name,
		InterfaceName: "PaymentGateway",
		MockName:      "MockPaymentGateway",
		Methods: []MethodDesc{
			{
				Name:       "Charge",
				Params:     "amount int64",
				Returns:    "error",
				ZeroReturn: "nil",
			},
			{
				Name:       "Refund",
				Params:     "txID string",
				Returns:    "bool",
				ZeroReturn: "false",
			},
		},
	}

	tmpl := template.Must(template.New("mock").Parse(mockTemplate))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

Встроенный полиморфизм интерфейсов Go работает по принципу утиной типизации (structural subtyping). Если сгенерированная структура `MockPaymentGateway` реализует точные сигнатуры всех методов `Charge` и `Refund`, компилятор Go принимает ее везде, где ожидается интерфейс `PaymentGateway`, без необходимости ключевых слов `implements`.

## Подводные камни

Интерфейс может содержать встроенные интерфейсы (`io.Reader`, `context.Context`). Простой обход `ast.InterfaceType.Methods.List` видит встроенные интерфейсы как поля без `Names` (`Field.Type = ast.Ident`). Генератор должен уметь рекурсивно резолвить методы встроенных интерфейсов через семантическую таблицу `go/types`.

## На собеседовании

**Вопрос с собеседования:** Почему в Go-тестировании ручные моки (hand-written mocks) на базе полей-функций (`Func func(...)`) часто предпочитают громоздким фреймворкам с рефлексией (типа testify/mock или gomock)?
**Ответ:** 1) 100% статическая типизация: ошибки параметров и возвратов обнаруживаются компилятором, а не во время теста. 2) Быстродействие: вызов обычной структуры-заглушки в 50–100 раз быстрее рефлексивного перехвата аргументов `mock.Called()`. 3) Читаемость: в тесте поведение задается прямой лямбдой `mock.ChargeFunc = func(...) { return nil }` без строковых имен методов.
