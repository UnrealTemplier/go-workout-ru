# Генерация моков с историей вызовов и ассертами вызовов

## Условие

**Генерация mock-объектов для интерфейсов.**: Реализуйте упрощённый аналог `mockgen`: программа читает файл, находит интерфейс, генерирует структуру-мок с методами, которые записывают все вызовы (имя метода, аргументы) в историю и позволяют проверять их в тестах (`AssertCalled`).

### Исходная формулировка

**Генерация mock-объектов для интерфейсов.**: Реализуйте упрощённый аналог `mockgen`: программа читает файл, находит интерфейс, генерирует структуру-мок с методами, которые записывают факт вызова и возвращают предопределённые значения.

## Теория

Для тестирования взаимодействия (Behavior Verification) тестам требуется не только подменять результат, но и проверять:
- Был ли вызван метод вообще.
- Сколько именно раз он был вызван (`AssertCalled(t, "Send", 1)`).
- С какими конкретно параметрами он вызывался.

Генератор истории вызовов создает:
- Структуру вызова `Invocation{Method string, Args []any}`.
- Срез `Invocations []Invocation`.
- Вспомогательные методы верификации `AssertCalled(t testing.TB, method string, count int)`.

## Решение по шагам

1. Создайте структуру описания вызова `CallRecord`.
2. В структуре мока заведите поле `Calls []CallRecord`.
3. В методе интерфейса сохраняйте переданные аргументы в историю.
4. Сгенерируйте метод `AssertCalled(t testing.TB, method string, times int)`.
5. Отформатируйте сгенерированный код через `format.Source`.

## Код решения

**`gen_assert_mock.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/format"
	"text/template"
)

type MockAssertData struct {
	Package string
	Iface   string
	Mock    string
}

const assertMockTmpl = `// Code generated by gen_assert_mock. DO NOT EDIT.
package {{.Package}}

import (
	"sync"
	"testing"
)

type CallRecord struct {
	Method string
	Args   []any
}

type {{.Mock}} struct {
	mu    sync.Mutex
	calls []CallRecord
}

func New{{.Mock}}() *{{.Mock}} {
	return &{{.Mock}}{}
}

func (m *{{.Mock}}) SendEmail(to string, body string) error {
	m.mu.Lock()
	m.calls = append(m.calls, CallRecord{
		Method: "SendEmail",
		Args:   []any{to, body},
	})
	m.mu.Unlock()
	return nil
}

func (m *{{.Mock}}) AssertCalled(t testing.TB, method string, expectedCount int) {
	t.Helper()
	m.mu.Lock()
	defer m.mu.Unlock()

	actualCount := 0
	for _, call := range m.calls {
		if call.Method == method {
			actualCount++
		}
	}

	if actualCount != expectedCount {
		t.Errorf("expected %s to be called %d times, but called %d times", method, expectedCount, actualCount)
	}
}
`

func main() {
	data := MockAssertData{
		Package: "mailer",
		Iface:   "EmailSender",
		Mock:    "MockEmailSender",
	}

	tmpl := template.Must(template.New("mock_assert").Parse(assertMockTmpl))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

Вызов `t.Helper()` внутри сгенерированного метода `AssertCalled` сообщает тестовому раннеру Go, что данная функция является вспомогательной. При возникновении ошибки вывода (`t.Errorf`) в отчете теста будет указан номер строки в самом тесте разработчика, а не внутри файла сгенерированного мока, что критически важно для удобства DX (Developer Experience).

## Подводные камни

Сохранение аргументов по указателю `args: []any{req}` может привести к искажению истории: если вызывающий код после вызова метода мутирует объект `req`, в сохраненной истории мока значение тоже изменится. Для безопасного логирования аргументы глубоко клонируют или валидируют на месте.

## На собеседовании

**Вопрос с собеседования:** Зачем в сигнатуре ассертов тестирования используют интерфейс `testing.TB`, а не конкретный указатель `*testing.T`?
**Ответ:** Интерфейс `testing.TB` объединяет `*testing.T` (модульные тесты) и `*testing.B` (бенчмарки). Использование `testing.TB` позволяет переиспользовать вспомогательные методы проверки ассертов и моков как в стандартных тестах, так и внутри нагрузочных бенчмарков без дублирования кода.
