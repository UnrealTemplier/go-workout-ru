# Генерация HTTP-обработчиков по спецификации API

## Условие

**Генерация HTTP-обработчиков по спеке.**: Создайте YAML-спеку (метод, путь, request/response struct). Напишите генератор, который создаёт Go-код: интерфейс сервиса, middleware-обёртку, парсинг JSON-запроса, валидацию и вызов метода сервиса.

### Исходная формулировка

**Генерация HTTP-обработчиков по спеке.**: Создайте YAML-спеку (метод, путь, request/response struct). Напишите генератор, который создаёт Go-код: интерфейс сервиса, middleware-обёртки, chi/gin-роуты и типы request/response. Объясните, почему `go-swagger`/`oapi-codegen` используют `text/template` + `go/ast` в комбинации.

---

## Теория

Фреймворки генерации API (oapi-codegen, goa, grpc-gateway) автоматизируют рутинный HTTP-транспорт:
- Декодирование JSON-тела входящего запроса.
- Валидация входных данных.
- Вызов метода интерфейса бизнес-логики.
- Сериализация ответа с кодом 200 OK или возврат ошибки HTTP 400/500.
Разработчик пишет только чистую бизнес-логику интерфейса, не касаясь деталей HTTP-протокола.

## Решение по шагам

1. Опишите эндпоинт `CreateUser` (метод `POST`, путь `/users`).
2. В генераторе опишите интерфейс сервиса `UserService`.
3. Сгенерируйте HTTP-хэндлер с декодированием `json.NewDecoder(r.Body).Decode`.
4. Сгенерируйте регистратор маршрутов `RegisterRoutes(mux *http.ServeMux, svc UserService)`.
5. Отформатируйте сгенерированный код через `format.Source`.

## Код решения

**`gen_http_api.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/format"
	"text/template"
)

type EndpointMeta struct {
	Method      string
	Path        string
	HandlerName string
	ReqType     string
	RespType    string
}

type ServiceAPIMeta struct {
	Package   string
	IfaceName string
	Endpoints []EndpointMeta
}

const apiTmpl = `// Code generated by gen_http_api. DO NOT EDIT.
package {{.Package}}

import (
	"context"
	"encoding/json"
	"net/http"
)

type {{.IfaceName}} interface {
{{range .Endpoints}}	{{.HandlerName}}(ctx context.Context, req *{{.ReqType}}) (*{{.RespType}}, error)
{{end}}}

type HTTPHandler struct {
	svc {{.IfaceName}}
}

func NewHTTPHandler(svc {{.IfaceName}}) *HTTPHandler {
	return &HTTPHandler{svc: svc}
}

{{range .Endpoints}}
func (h *HTTPHandler) {{.HandlerName}}(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.Method{{.Method}} {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}

	var req {{.ReqType}}
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, "Bad Request: " + err.Error(), http.StatusBadRequest)
		return
	}

	resp, err := h.svc.{{.HandlerName}}(r.Context(), &req)
	if err != nil {
		http.Error(w, "Internal Error: " + err.Error(), http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	_ = json.NewEncoder(w).Encode(resp)
}
{{end}}
`

func main() {
	meta := ServiceAPIMeta{
		Package:   "transport",
		IfaceName: "OrderService",
		Endpoints: []EndpointMeta{
			{
				Method:      "Post",
				Path:        "/orders",
				HandlerName: "CreateOrder",
				ReqType:     "CreateOrderRequest",
				RespType:    "CreateOrderResponse",
			},
		},
	}

	tmpl := template.Must(template.New("api").Parse(apiTmpl))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, meta); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

Сгенерированный хэндлер передает `r.Context()` непосредственно в бизнес-метод сервиса. Это гарантирует сохранение цепочки отмены при разрыве клиентского соединения, а также перенос спанов распределенной трассировки OpenTelemetry без потерь контекста.

## Подводные камни

Использование `json.NewDecoder(r.Body).Decode` без ограничения размера `http.MaxBytesReader` делает сервис уязвимым к DoS-атакам путем отправки бесконечного потока байт в теле запроса. В продакшен-генераторах декодирование оборачивают в `io.LimitReader`.

## На собеседовании

**Вопрос с собеседования:** Почему в микросервисах архитектуры BigTech генерацию транспортных обработчиков HTTP/REST предпочитают ручному написанию контроллеров?
**Ответ:** 1) 100% соблюдение контракта API: контроллер не может случайно проигнорировать валидацию или вернуть несогласованный код ошибки. 2) Стандартизация логирования, трассировки и метрик на уровне всего кластера. 3) Экономия до 40% рабочего времени продуктовых инженеров на написании шаблонного транспортного кода.
