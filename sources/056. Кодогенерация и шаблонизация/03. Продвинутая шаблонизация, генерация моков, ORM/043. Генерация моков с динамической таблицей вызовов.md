# Генерация моков с динамической таблицей вызовов (MockName)

## Условие

**[Генерация моков]**: Расширь предыдущий генератор. Для сгенерированного интерфейса создай структуру `MockName`, которая хранит мапу `map[string]func(args) returns` и реализует методы интерфейса через вызов зарегистрированной функции.

### Исходная формулировка

**[Генерация моков]**: Расширь предыдущий генератор. Для сгенерированного интерфейса создай структуру `MockName`, которая хранит мапу `map[string]func(args) returns` и реализует методы интерфейса, вызывая коллбэки из мапы.

## Теория

Для создания гибких тестовых дублеров применяется паттерн Function Registry (реестр функций-перехватчиков):
- Мок содержит мапу обработчиков `handlers map[string]any`.
- Метод `On(methodName string, fn any)` регистрирует поведение для конкретного метода в данном тесте.
- Реализация метода извлекает функцию из мапы, приводит к правильному типу сигнатуры и выполняет ее, либо возвращает дефолтный zero value.

## Решение по шагам

1. Создайте шаблон структуры `MockClient` со словарем обработчиков `map[string]any`.
2. Реализуйте хелпер `On(method string, fn any)`.
3. В сгенерированных методах интерфейса добавьте извлечение функции из мапы с тайп-ассертом.
4. Отформатируйте сгенерированный код через `format.Source`.

## Код решения

**`gen_dynamic_mock.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/format"
	"text/template"
)

type DynamicMockData struct {
	Package   string
	IfaceName string
	MockName  string
}

const dynMockTmpl = `// Code generated by gen_dynamic_mock. DO NOT EDIT.
package {{.Package}}

import (
	"fmt"
	"sync"
)

type {{.MockName}} struct {
	mu       sync.RWMutex
	handlers map[string]any
}

func New{{.MockName}}() *{{.MockName}} {
	return &{{.MockName}}{
		handlers: make(map[string]any),
	}
}

func (m *{{.MockName}}) On(method string, fn any) *{{.MockName}} {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.handlers[method] = fn
	return m
}

func (m *{{.MockName}}) Execute(taskID string) (string, error) {
	m.mu.RLock()
	fn, ok := m.handlers["Execute"]
	m.mu.RUnlock()

	if !ok {
		return "", fmt.Errorf("unexpected call to Execute(%q)", taskID)
	}

	typedFn, ok := fn.(func(string) (string, error))
	if !ok {
		panic(fmt.Sprintf("invalid mock handler type for Execute: %T", fn))
	}

	return typedFn(taskID)
}
`

func main() {
	data := DynamicMockData{
		Package:   "executor",
		IfaceName: "TaskExecutor",
		MockName:  "MockTaskExecutor",
	}

	tmpl := template.Must(template.New("dyn_mock").Parse(dynMockTmpl))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

ℹ️ Генератор Mock с динамической регистрацией вызовов через метод On

## Под капотом

Использование `sync.RWMutex` позволяет безопасно регистрировать моки в главном потоке теста (`mock.On(...)`) и параллельно читать их из фоновых воркеров (`mock.Execute(...)`) с минимальными затратами на чтение без взаимных блокировок.

## Подводные камни

Динамическое приведение типов `fn.(func(string) ...)` переносит ошибки несоответствия типов сигнатуры из compile-time в runtime: если в тесте передать функцию с неверным количеством аргументов, произойдет паника во время прогона теста. Для критических сервисов лучше использовать строго типизированные поля `ExecuteFn func(...)`.

## На собеседовании

**Вопрос с собеседования:** В чем преимущества и недостатки генераторов моков на основе `mock.On(name, fn)` по сравнению с генерацией явных полей-функций?
**Ответ:** Преимущество `mock.On`: лаконичный синтаксис настройки поведения в цепочечном стиле (Fluent API). Недостаток: потеря статической проверки типов аргументов во время компиляции теста и риск получить панику `invalid type assertion` в рантайме. Поэтому в BigTech предпочитают генераторы со строго типизированными полями (типа `minimock`).
