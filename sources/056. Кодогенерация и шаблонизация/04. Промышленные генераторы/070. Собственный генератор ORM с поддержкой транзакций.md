# Собственный генератор ORM с поддержкой транзакций

## Условие

**Собственный ORM:**
    Создайте полноценный ORM с:
    * Парсингом struct tags через reflect (`db:"column"`, `db:"primary_key"`, `db:"index"`)
    * Автоматическим построением SQL схем и DDL миграций
    * Поддержкой транзакций `db.BeginTx()`.

### Исходная формулировка

**Собственный ORM:**
Создайте полноценный ORM с:
* Парсингом struct tags через reflect (`db:"column"`, `db:"primary_key"`, `db:"index"`)
* Автоматическим построением SQL queries
* Migration generator (из структур → SQL schema)
* Type-safe query builder через кодогенерацию
* Reflection-free runtime (весь маппинг через сгенерированный код)

## Теория

Промышленный ORM-генератор связывает слои приложения:
1. Анализирует теги полей `db:"..."`.
2. Создает DDL-миграцию `CREATE TABLE ... (id BIGSERIAL PRIMARY KEY, ...)`.
3. Создает методы репозитория, принимающие общий интерфейс `DBExecutor`:
   ```go
   type DBExecutor interface {
       ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
       QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
   }
   ```
   Это позволяет выполнять сгенерированные CRUD-методы как напрямую через `*sql.DB`, так и внутри открытой транзакции `*sql.Tx`!

## Решение по шагам

1. Опишите интерфейс `DBExecutor`.
2. Создайте структуру `Product` с первичным ключом.
3. Сгенерируйте методы `InsertTx` и `FindByIDTx`.
4. Отформатируйте код через `format.Source`.

## Код решения

**`gen_tx_orm.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"go/format"
	"text/template"
)

type FullORMData struct {
	Package string
	Entity  string
	Table   string
}

const txOrmTmpl = `// Code generated by gen_tx_orm. DO NOT EDIT.
package {{.Package}}

import (
	"context"
	"database/sql"
)

// DBExecutor абстрагирует *sql.DB и *sql.Tx
type DBExecutor interface {
	ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
	QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
}

type {{.Entity}}Repo struct{}

func New{{.Entity}}Repo() *{{.Entity}}Repo {
	return &{{.Entity}}Repo{}
}

func (r *{{.Entity}}Repo) Create(ctx context.Context, exec DBExecutor, item *{{.Entity}}) error {
	query := "INSERT INTO {{.Table}} (title, price) VALUES ($1, $2) RETURNING id"
	return exec.QueryRowContext(ctx, query, item.Title, item.Price).Scan(&item.ID)
}

func (r *{{.Entity}}Repo) Delete(ctx context.Context, exec DBExecutor, id int64) error {
	query := "DELETE FROM {{.Table}} WHERE id = $1"
	_, err := exec.ExecContext(ctx, query, id)
	return err
}
`

func main() {
	data := FullORMData{
		Package: "store",
		Entity:  "Product",
		Table:   "products",
	}

	tmpl := template.Must(template.New("tx_orm").Parse(txOrmTmpl))
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		panic(err)
	}

	formatted, err := format.Source(buf.Bytes())
	if err != nil {
		panic(err)
	}

	fmt.Println(string(formatted))
}
```

## Под капотом

Интерфейс `DBExecutor` одновременно реализуется стандартными структурами `*sql.DB` и `*sql.Tx`. Передача `DBExecutor` первым параметром метода репозитория позволяет повторно использовать один и тот же метод как в одиночных независимых запросах, так и в рамках сложных распределенных саг и транзакций с `tx.Rollback()`.

## Подводные камни

Если разработчик передаст в метод закрытую транзакцию `tx`, драйвер базы данных вернет ошибку `sql: transaction has already been committed or rolled back`. Репозиторий должен просто пробрасывать ошибку вызывающему слою.

## На собеседовании

**Вопрос с собеседования:** Как архитектурно элегантно передавать открытую транзакцию базы данных через слои UseCase / Service, не нарушая Чистую Архитектуру?
**Ответ:** Использовать паттерн Transaction Manager с хранением активной транзакции в контексте `ctx = context.WithValue(ctx, txKey{}, tx)`. Сгенерированный репозиторий проверяет `if tx := ctx.Value(txKey{}); tx != nil`, автоматически выбирая транзакцию из контекста или откатываясь к обычному пулу соединений `db`.
