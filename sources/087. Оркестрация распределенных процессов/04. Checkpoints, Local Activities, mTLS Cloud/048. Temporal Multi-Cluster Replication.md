# Temporal Multi-Cluster Replication: Построение Active-Passive гео-распределения

## Условие

Сконфигурируйте клиентское приложение и воркеры для работы в отказоустойчивой мультикластерной среде с репликацией между датацентрами (Active-Passive Geo-Redundancy). Смоделируйте аварийное переключение пространства имен (Namespace Failover) на резервный кластер: покажите, как активные рабочие процессы продолжают исполнение на резервной площадке с сохраненным состоянием.

### Исходная формулировка

**Temporal Multi-Cluster Replication: Построение Active-Passive гео-распределения**: Сконфигурируйте клиентское приложение и воркеры для работы в отказоустойчивой мультикластерной среде с репликацией между датацентрами. Смоделируйте аварийное переключение пространства имен (Namespace Failover) на резервный кластер: покажите, как активные рабочие процессы продолжают исполнение на резервной площадке с сохраненным состоянием.

## Теория

В критических банковских и телеком-системах отказ одного датацентра не должен прерывать исполнение бизнес-процессов.

**Temporal Multi-Cluster Replication** обеспечивает гео-распределенную отказоустойчивость:
1. Кластеры Temporal развертываются в двух независимых датацентрах (например, `dc-primary` и `dc-standby`).
2. Пространство имен (Namespace) настраивается как Global Namespace с репликацией истории событий через асинхронный Replication Queue.
3. Воркеры запущены в ОБОИХ датацентрах и подключены к своим локальным кластерам.
4. При аварии датацентра Primary администратор выполняет одну команду переключения: `temporal operator namespace update --active-cluster dc-standby`.
5. Резервный кластер становится Active, воркеры в Standby подхватывают исполнение задач ровно с той точки, где произошел сбой, без потери данных!

## Решение по шагам

1. Спроектируйте архитектурную схему Global Namespace с двумя кластерами.
2. Напишите код подключения воркера к локальному кластеру площадки.
3. Смоделируйте переключение Active Cluster.
4. Продемонстрируйте подхватывание процесса резервным воркером.

## Код решения

**`multi_cluster.go`**

```go
package main

import (
	"fmt"
	"time"

	"go.temporal.io/sdk/client"
	"go.temporal.io/sdk/workflow"
)

// GeoResilientWorkflow устойчив к падению целого датацентра.
func GeoResilientWorkflow(ctx workflow.Context, orderID string) error {
	logger := workflow.GetLogger(ctx)
	logger.Info("Процесс запущен в глобальном пространстве имен с репликацией", "order_id", orderID)

	// Долгий процесс с несколькими шагами
	_ = workflow.Sleep(ctx, 5*time.Second)

	logger.Info("Процесс пережил гео-переключение кластера и успешно финализирован!")
	return nil
}

// MultiClusterTopologyDemo иллюстрирует архитектуру Active-Passive.
func MultiClusterTopologyDemo() {
	fmt.Println("=== Архитектура Temporal Multi-Cluster Replication ===")
	fmt.Println("1. Кластер DC-1 (Primary): активен, пишет историю в БД Spanner/Postgres.")
	fmt.Println("2. Кластер DC-2 (Standby): принимает репликацию событий через gRPC Replication Stream.")
	fmt.Println("3. Воркеры запущены в обоих DC и слушают единую очередь 'geo-orders'.")
	fmt.Println("4. При падении DC-1 выполняется команда: temporal operator namespace update --active-cluster dc-2")
	fmt.Println("5. DC-2 мгновенно переходит в режим Active и начинает раздавать задачи воркерам в DC-2!")
}

func main() {
	MultiClusterTopologyDemo()
}
```

## Под капотом

History Service кластера генерирует репликационные задачи для каждого зафиксированного события. Сервер на резервной площадке непрерывно вычитывает этот поток изменений и применяет их к своей копии базы данных. При переключении площадки (Failover) кластер генерирует маркер `VersionHistory`, разрешая возможные конфликты параллельных записей и гарантируя линеаризуемость.

## Подводные камни

Репликация между датацентрами является асинхронной. При внезапной полной физической гибели первичного ЦОД возможна потеря нескольких последних миллисекунд событий, которые еще не успели долететь по сети до резервной площадки (RPO > 0, но стремится к долям секунды).

## На собеседовании

В: Могут ли воркеры в резервном датацентре исполнять задачи до выполнения команды Failover?
О: Нет! Пока Namespace находится в статусе Standby в данном кластере, Matching Service этого кластера не выдает задачи на исполнение воркерам, чтобы исключить риск конфликтов (Split-Brain). Задачи начнут выдаваться только после того, как кластер станет Active.
