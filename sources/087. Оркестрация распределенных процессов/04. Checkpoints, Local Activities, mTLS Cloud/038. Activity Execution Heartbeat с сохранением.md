# Activity Execution Heartbeat с сохранением прогресса (Checkpoints)

## Условие

Спроектируйте долгоживущую Activity по пакетной обработке терабайтного CSV-файла: воркер каждые несколько секунд отправляет контрольные сигналы жизнедеятельности `activity.RecordHeartbeat(ctx, currentOffset)`. Продемонстрируйте, как при аварийном падении узла воркера новая попытка (retry attempt) извлекает последнее зафиксированное смещение через `activity.GetHeartbeatDetails` и возобновляет обработку без потерь и повторов.

### Исходная формулировка

**Activity Execution Heartbeat с сохранением прогресса (Checkpoints)**: Спроектируйте долгоживущую Activity по пакетной обработке терабайтного файла: воркер каждые несколько секунд отправляет контрольные сигналы жизнедеятельности `activity.RecordHeartbeat(ctx, currentOffset)`. Продемонстрируйте, как при аварийном падении узла воркера новая попытка (retry attempt) извлекает последнее зафиксированное смещение через `activity.GetHeartbeatDetails` и возобновляет обработку без потерь и повторов.

## Теория

При обработке огромных массивов данных (миграция 10 миллионов строк из legacy БД, обработка 50 ГБ логов) Activity может выполняться несколько часов. Если воркер упадет на 99% выполнения, повторный запуск задачи с самого начала приведет к чудовищной потере ресурсов и времени.

Паттерн **Activity Checkpointing** позволяет возобновлять тяжелые операции с последней контрольной точки:
1. Activity считывает данные пачками (батчами).
2. После каждого батча вызывается `activity.RecordHeartbeat(ctx, checkpointState)`.
3. Данные контрольной точки сохраняются кластером Temporal.
4. При аварийном падении воркера кластер запускает повторную попытку на другом сервере.
5. Новая попытка проверяет `activity.HasHeartbeatDetails(ctx)` и мгновенно возобновляет работу ровно с того места, где упал погибший воркер!

## Решение по шагам

1. Опишите структуру `MigrationCheckpoint` (LastProcessedID, TotalRowsProcessed).
2. Реализуйте чтение контрольной точки при старте Activity.
3. В цикле имитируйте постраничную обработку строк.
4. Фиксируйте прогресс через `activity.RecordHeartbeat`.
5. Завершите задачу с итоговым отчетом.

## Код решения

**`checkpointing.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.temporal.io/sdk/activity"
)

type MigrationCheckpoint struct {
	LastRecordID int64 `json:"last_record_id"`
	TotalRows    int64 `json:"total_rows"`
}

// MigrateTableActivity демонстрирует надежную обработку больших данных с чекпоинтами.
func MigrateTableActivity(ctx context.Context, targetTable string) error {
	logger := activity.GetLogger(ctx)

	// Инициализация точки старта: по умолчанию с нуля
	checkpoint := MigrationCheckpoint{
		LastRecordID: 0,
		TotalRows:    0,
	}

	// 1. Проверяем наличие предыдущей контрольной точки после возможного сбоя
	if activity.HasHeartbeatDetails(ctx) {
		var saved MigrationCheckpoint
		if err := activity.GetHeartbeatDetails(ctx, &saved); err == nil {
			checkpoint = saved
			logger.Info("Возобновление обработки с контрольной точки!",
				"last_id", checkpoint.LastRecordID, "processed", checkpoint.TotalRows)
			fmt.Printf(" [ACTIVITY] 🔄 Восстановление с чекпоинта: ID=%d, строк=%d\n",
				checkpoint.LastRecordID, checkpoint.TotalRows)
		}
	}

	const batchSize = 100
	const maxBatches = 10

	for batch := 0; batch < maxBatches; batch++ {
		// Проверка на случай отмены задачи
		if ctx.Err() != nil {
			logger.Warn("Обработка прервана по контексту")
			return ctx.Err()
		}

		// Имитация чтения и записи батча строк
		time.Sleep(100 * time.Millisecond)
		checkpoint.LastRecordID += batchSize
		checkpoint.TotalRows += batchSize

		// 2. Отправка Heartbeat с актуальным чекпоинтом в кластер Temporal!
		activity.RecordHeartbeat(ctx, checkpoint)

		fmt.Printf(" [ACTIVITY] ✅ Зафиксирован чекпоинт: обработано %d строк (LastID: %d)\n",
			checkpoint.TotalRows, checkpoint.LastRecordID)
	}

	logger.Info("Миграция таблицы успешно завершена", "table", targetTable, "total", checkpoint.TotalRows)
	return nil
}

func main() {
	fmt.Println("Демонстрация чекпоинтов и возобновления тяжелых Activities через Heartbeat.")
}
```

## Под капотом

Кластер Temporal хранит последнее значение `HeartbeatDetails` в оперативной памяти History Service и сбрасывает его в БД при закрытии попытки. Когда воркер падает по таймауту `HeartbeatTimeout`, кластер генерирует новую задачу и вкладывает эти детали в ответ `PollActivityTaskQueue`. Таким образом, состояние чекпоинта передается новому воркеру гарантированно и без внешних баз данных.

## Подводные камни

Не используйте сложные циклические указатели в объекте чекпоинта. Структура должна легко и однозначно сериализоваться в JSON/Protobuf.

## На собеседовании

В: Как часто нужно вызывать RecordHeartbeat при пакетной обработке 1 000 000 записей?
О: Не на каждую отдельную запись, а пачками: например, раз в 500–1000 записей или раз в 1–2 секунды. Хотя Go SDK автоматически выполняет троттлинг сетевых запросов к кластеру, слишком частые вызовы функции внутри горячего цикла создают ненужную нагрузку на CPU воркера.
