# Политики повторного использования Workflow ID

## Условие

Сконфигурируйте `WorkflowIdReusePolicy`: `ALLOW_DUPLICATE`, `ALLOW_DUPLICATE_FAILED_ONLY`, `REJECT_DUPLICATE`. Продемонстрируйте, как использование осмысленного бизнес-идентификатора заказа (например, `order-uuid-12345`) в качестве `WorkflowID` защищает систему от случайного повторного запуска одного и того же заказа (Deduping) на уровне кластера Temporal.

### Исходная формулировка

**Политики повторного использования Workflow ID**: Сконфигурируйте `WorkflowIdReusePolicy`: `ALLOW_DUPLICATE`, `ALLOW_DUPLICATE_FAILED_ONLY`, `REJECT_DUPLICATE`. Продемонстрируйте, как использование бизнес-идентификатора заказа в качестве `WorkflowID` защищает систему от случайного повторного запуска одного и того же заказа.

## Теория

В Temporal каждый запущенный процесс идентифицируется парой `(WorkflowID, RunID)`:
- `WorkflowID` — бизнес-идентификатор, задаваемый клиентом (например, `order-7721` или `user-reg-ivan`).
- `RunID` — уникальный системный UUID конкретного запуска.

В один момент времени в кластере может существовать ТОЛЬКО ОДИН активный (Running) процесс с данным `WorkflowID`! Попытка запустить второй процесс с тем же ID вернет ошибку `WorkflowExecutionAlreadyStarted`.

Что происходит, когда предыдущий процесс с этим ID уже завершился? Это определяется политикой **`WorkflowIdReusePolicy`**:
1. `WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE`: разрешить повторный запуск всегда.
2. `WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE_FAILED_ONLY`: разрешить повторный запуск только если предыдущий процесс упал, был отменен или завершился по таймауту.
3. `WORKFLOW_ID_REUSE_POLICY_REJECT_DUPLICATE`: никогда повторно не запускать с таким ID.

## Решение по шагам

1. Сконфигурируйте `client.StartWorkflowOptions` с осмысленным `WorkflowID`.
2. Установите политику `WorkflowIdReusePolicy: enums.WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE_FAILED_ONLY`.
3. Продемонстрируйте вызов `client.ExecuteWorkflow`.
4. Покажите перехват ошибки дублирующего запуска.

## Код решения

**`id_reuse.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"

	"go.temporal.io/api/enums/v1"
	"go.temporal.io/sdk/client"
	"go.temporal.io/sdk/workflow"
)

func DummyOrderWorkflow(ctx workflow.Context, orderID string) (string, error) {
	return "ORDER_PROCESSED: " + orderID, nil
}

// StartDeduplicatedOrder запускает заказ с защитой от дублей.
func StartDeduplicatedOrder(c client.Client, orderID string) error {
	workflowOptions := client.StartWorkflowOptions{
		ID:        fmt.Sprintf("order-%s", orderID), // Бизнес-идентификатор
		TaskQueue: "order-tasks",
		// Если предыдущий заказ с таким ID был успешно выполнен — повторный запуск ЗАПРЕЩЕН!
		// Если же он упал — повторный запуск РАЗРЕШЕН.
		WorkflowIDReusePolicy: enums.WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE_FAILED_ONLY,
	}

	we, err := c.ExecuteWorkflow(context.Background(), workflowOptions, DummyOrderWorkflow, orderID)
	if err != nil {
		return fmt.Errorf("ошибка запуска Workflow: %w", err)
	}

	fmt.Printf(" [SUCCESS] Workflow запущен! WorkflowID: %s, RunID: %s\n", we.GetID(), we.GetRunID())
	return nil
}

func main() {
	fmt.Println("Демонстрация политик WorkflowIdReusePolicy для идеальной дедупликации.")
}
```

## Под капотом

Кластер Temporal гарантирует уникальность `WorkflowID` на уровне распределенных транзакций в СУБД (ACID). Таблица `executions` имеет составной первичный ключ по `shard_id` и `workflow_id`. Это означает, что дедупликация работает со 100% гарантией даже при одновременной атаке миллионом параллельных одинаковых HTTP-запросов.

## Подводные камни

Генерация случайного `uuid.New().String()` в качестве `WorkflowID` лишает вас важнейшего встроенного механизма дедупликации Temporal! Всегда привязывайте `WorkflowID` к реальным бизнес-ключам сущности (ID заказа, ID транзакции, ID пользователя).
