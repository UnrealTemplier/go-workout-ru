# ReplacingMergeTree: Идемпотентность и восстановление после сбоев

## Условие

**ReplacingMergeTree и дедупликация**: При повторных вставках пакетов (например, после сетевых сбоев) в ClickHouse могут образовываться дубликаты строк. Создайте таблицу на движке `ReplacingMergeTree`. Напишите код записи событий с уникальным идентификатором и версией (timestamp), а также напишите запрос чтения данных, использующий ключевое слово `FINAL` или агрегацию для получения строго уникальных актуальных состояний.

---

## Теория

В распределенных пайплайнах сбои сети неизбежны. Если Go-воркер отправил батч из 100 000 строк, ClickHouse записал парт, но сетевой ответ `OK` потерялся из-за разрыва TCP, воркер выполнит повторную отправку (Retry).

При стандартном `MergeTree` данные продублируются. Использование `ReplacingMergeTree` решает эту проблему:
1. Ключом дедупликации служит `ORDER BY (entity_id, ...)`.
2. При повторной отправке идентичных строк фоновый процесс слияния или модификатор `FINAL` схлопывает дубликаты, восстанавливая консистентность без ручного вмешательства инженера.

## Решение по шагам

1. Создайте таблицу `transactions_replacing` (ReplacingMergeTree).
2. Сымитируйте отправку одного и того же батча дважды.
3. Продемонстрируйте устранение дублей при запросе с `FINAL` или через `argMax()`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS transactions_replacing (
			tx_id UInt64,
			amount Float64,
			status LowCardinality(String),
			updated_at DateTime
		) ENGINE = ReplacingMergeTree(updated_at)
		ORDER BY tx_id;
	`)

	// Функция отправки батча
	sendBatch := func() {
		batch, err := conn.PrepareBatch(ctx, "INSERT INTO transactions_replacing")
		if err != nil {
			panic(err)
		}
		now := time.Now()
		_ = batch.Append(uint64(99001), 2500.0, "SUCCESS", now)
		_ = batch.Append(uint64(99002), 120.0, "PENDING", now)
		if err := batch.Send(); err != nil {
			panic(err)
		}
	}

	// Имитация сетевого ретрая: отправляем один и тот же батч дважды
	sendBatch()
	sendBatch()

	// 1. Подсчет без дедупликации (видны 2 физических парта)
	var rawCount uint64
	_ = conn.QueryRow(ctx, "SELECT count() FROM transactions_replacing").Scan(&rawCount)

	// 2. Идемпотентный результат через FINAL
	var finalCount uint64
	_ = conn.QueryRow(ctx, "SELECT count() FROM transactions_replacing FINAL").Scan(&finalCount)

	fmt.Printf("Идемпотентная обработка повторов:\n")
	fmt.Printf("  Физических строк на диске до слияния: %d (2 копии батча)\n", rawCount)
	fmt.Printf("  Уникальных транзакций (FINAL):       %d (дубликаты схлопнуты)\n", finalCount)
}
```

ℹ️ Гарантия идемпотентности при повторной отправке батчей через ReplacingMergeTree

**`Терминал`**

```bash
go run main.go
# Идемпотентная обработка повторов:
#   Физических строк на диске до слияния: 4 (2 копии батча)
#   Уникальных транзакций (FINAL):       2 (дубликаты схлопнуты)
```

## Под капотом

Два вызова `sendBatch()` сформировали два разных парта `all_1_1_0` и `all_2_2_0`. До тех пор, пока фоновый поток слияния `BackgroundProcessingPool` не объединит их в `all_1_2_1`, обе копии занимают место на диске. Модификатор `FINAL` на этапе чтения на лету объединяет потоки и выдает единственную версию каждой транзакции.

## Подводные камни

Если при повторной отправке батча значение колонки версии `updated_at` случайно сгенерируется меньшим, чем при первой отправке, ClickHouse сохранит старую строку. Версия должна либо совпадать, либо монотонно возрастать.

## На собеседовании

**Вопрос:** Как работает настройка `do_not_merge_across_partitions_select_final`?
**Ответ:** По умолчанию `FINAL` считывает парты по всем партициям. Данная оптимизация позволяет ClickHouse выполнять слияние параллельно внутри каждой отдельной партиции, что значительно ускоряет `SELECT ... FINAL` на больших партиционированных таблицах.
