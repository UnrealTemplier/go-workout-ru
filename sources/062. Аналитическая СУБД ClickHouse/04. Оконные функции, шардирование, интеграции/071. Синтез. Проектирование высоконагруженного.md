# Синтез: Проектирование высоконагруженного аналитического конвейера в Go

## Условие

**Блок 15 (ClickHouse)**: — проходите после Блока 14, так как ClickHouse требует переосмысления подхода к схеме (денормализация вместо JOIN). Параллельно смотрите Блок 2 (аллокатор) — поймёте, почему columnar storage быстрее для аналитики.

## Теория

Финальный синтез знаний по ClickHouse в BigTech бэкенде:

### Архитектурный манифест аналитического бэкенда:
1. **Денормализация:** Широкие таблицы, отказ от динамических JOIN в пользу массивов `Array(...)`, кортежей и словарей `Dictionaries`.
2. **Буферизация:** Асинхронные пакетные вставки из Go с контролем по размеру (100k строк) и времени (1 сек) или через промежуточную Kafka.
3. **Сжатие и кодеки:** Использование специализированных алгоритмов `Gorilla`, `DoubleDelta`, `LowCardinality` для минимизации объема диска.
4. **Сквозной мониторинг:** Снятие метрик через `system.parts`, `system.merges`, отслеживание прогресса тяжелых запросов через `WithProgress`.
5. **Многоуровневое хранение (Tiered Storage):** Автоматический перенос исторических данных в S3 Data Lake по истечении TTL.

## Решение по шагам

1. Спроектируйте законченный аналитический конвейер:
   - DDL таблицы событий с кодеками и TTL.
   - Batch Ingestion с контекстным таймаутом и LZ4.
   - Materialized View с суточными агрегатами.
   - Аналитический запрос с оконными функциями и вероятностными униками.
2. Проверьте компиляцию и выполнение конвейера в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
		Compression: &clickhouse.Compression{
			Method: clickhouse.CompressionLZ4,
		},
		MaxOpenConns: 15,
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// 1. DDL: Промышленная таблица событий с кодеками
	ddl := `
	CREATE TABLE IF NOT EXISTS production_events (
		event_id UUID,
		user_id UInt64 CODEC(T64, LZ4),
		event_time DateTime CODEC(DoubleDelta, LZ4),
		action LowCardinality(String),
		latency_ms Float32 CODEC(Gorilla, ZSTD(1))
	) ENGINE = MergeTree()
	PARTITION BY toYYYYMM(event_time)
	ORDER BY (action, event_time, user_id)
	TTL event_time + INTERVAL 90 DAY DELETE;
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}

	// 2. Batch Ingestion: Пакетная вставка с компрессией
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO production_events")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	for i := 0; i < 5000; i++ {
		_ = batch.Append(
			uuid.New(),
			uint64(20000+i),
			now.Add(time.Duration(i)*time.Millisecond),
			"checkout_complete",
			float32(15.5+float32(i%20)*0.5),
		)
	}
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// 3. Аналитический запрос: SLI перцентили и уники
	query := `
		SELECT 
			action,
			count() AS total_ops,
			uniq(user_id) AS unique_clients,
			quantiles(0.5, 0.95)(latency_ms) AS latency_p
		FROM production_events
		WHERE event_time >= now() - INTERVAL 1 HOUR
		GROUP BY action
	`
	var (
		action   string
		totalOps uint64
		uClients uint64
		latP     []float64
	)
	if err := conn.QueryRow(ctx, query).Scan(&action, &totalOps, &uClients, &latP); err != nil {
		panic(err)
	}

	fmt.Printf("=== АНАЛИТИЧЕСКИЙ КОНВЕЙЕР CLICKHOUSE В GO ===\n")
	fmt.Printf("Действие:               %s\n", action)
	fmt.Printf("Всего операций:         %d\n", totalOps)
	fmt.Printf("Уникальных клиентов:    %d\n", uClients)
	fmt.Printf("Медиана latency (p50):  %.2f ms\n", latP[0])
	fmt.Printf("95-й перцентиль (p95):  %.2f ms\n", latP[1])
	fmt.Printf("Статус конвейера:       100%% ГОТОВ К ВЫСОКИМ НАГРУЗКАМ (BIGTECH PRODUCTION)\n")
}
```

## Под капотом

Архитектура полного цикла объединяет клиентский пул соединений с непрерывным TCP-сокетом, сжатие LZ4 поверх сокета, распределение по партициям и гранулам, специализированные бинарные кодеки столбцов и векторное исполнение агрегатных функций с помощью инструкций SIMD.

## Подводные камни

Никогда не забывайте выставлять таймауты запросов `max_execution_time` в настройках подключения, чтобы некорректно составленный запрос аналитика не заблокировал процессорные мощности всего кластера.

## На собеседовании

**Вопрос:** Каковы ключевые метрики здоровья кластера ClickHouse при мониторинге в Prometheus/VictoriaMetrics?
**Ответ:** 1. `PartsCount` (количество партов на таблицу, порог тревоги > 150). 2. `BackgroundMergesAndMutationsPoolTask` (очередь слияний). 3. `QueryPreempted` / `MemoryTracking` (превышение лимитов памяти). 4. `ReplicasMaxAbsoluteDelay` (отставание репликации в секундах).
