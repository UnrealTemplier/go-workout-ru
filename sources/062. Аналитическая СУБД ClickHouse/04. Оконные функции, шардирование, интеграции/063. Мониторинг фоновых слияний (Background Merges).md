# Мониторинг фоновых слияний (Background Merges) через system.merges

## Условие

**Тюнинг слияния кусков и фоновые операции.**: Настройте параметры `merge_with_ttl_timeout`, `max_bytes_to_merge_at_max_space_in_pool`. Наблюдайте за фоновыми слияниями через `system.merges`.

## Теория

Фоновый процесс слияния кусков данных (Background Merge) — сердце производительности ClickHouse.

### Системные таблицы для диагностики здоровья ClickHouse:
1. **`system.merges`:** Показывает текущие активные операции слияния, прогресс выполнения в процентах, задействованную память и скорость диска.
2. **`system.parts`:** Статистика всех партов таблицы (активные, удаленные, размеры, количество строк).
3. При приближении к лимиту `parts_to_throw_insert` мониторинг должен генерировать алерт о замедлении дисковой подсистемы.

## Решение по шагам

1. Запросите список активных слияний из `system.merges`.
2. Запросите системные метрики ожидания слияний из `system.metrics` (`BackgroundMergesAndMutationsPoolTask`).
3. Сформируйте отчет о состоянии фоновых пулов ClickHouse в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Инспекция текущих операций слияния
	query := `
		SELECT 
			database,
			table,
			result_part_name,
			elapsed,
			progress,
			num_parts,
			total_size_bytes_compressed
		FROM system.merges
	`
	rows, err := conn.Query(ctx, query)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("Активные фоновые слияния (system.merges):")
	var count int
	for rows.Next() {
		count++
		var (
			db, table, resPart string
			elapsed, progress  float64
			numParts           uint64
			sizeBytes          uint64
		)
		if err := rows.Scan(&db, &table, &resPart, &elapsed, &progress, &numParts, &sizeBytes); err != nil {
			panic(err)
		}
		fmt.Printf("  Таблица %s.%s -> Парт %s | Исходных партов: %d | Размер: %.2f МБ | Прогресс: %.1f%%\n",
			db, table, resPart, numParts, float64(sizeBytes)/(1024*1024), progress*100)
	}

	if count == 0 {
		fmt.Println("  В данный момент активных слияний нет (дисковая подсистема спокойна)")
	}

	// Проверка глобальной метрики задач слияния в очереди
	var bgTasks int64
	_ = conn.QueryRow(ctx, "SELECT value FROM system.metrics WHERE metric = 'BackgroundMergesAndMutationsPoolTask'").Scan(&bgTasks)
	fmt.Printf("Задач в пуле фоновой обработки: %d\n", bgTasks)
}
```

ℹ️ Мониторинг фоновых слияний через system.merges и системные метрики ClickHouse

**`Терминал`**

```bash

# Активные фоновые слияния (system.merges):
#   В данный момент активных слияний нет (дисковая подсистема спокойна)
# Задач в пуле фоновой обработки: 0
```

## Под капотом

Пул потоков `BackgroundProcessingPool` запускает алгоритм эвристического выбора партов для слияния: отбираются парты близкого размера внутри одной партиции, чтобы минимизировать коэффициент перезаписи данных (Write Amplification). Суммарный объем слияния не должен превышать свободное место на диске.

## Подводные камни

Если диски медленные (HDD или сетевые блочные хранилища EBS с низким IOPS), фоновые слияния отстают от темпа входящих вставок. Это неминуемо приводит к ошибке `Too many parts`.

## На собеседовании

**Вопрос:** Какими настройками можно ускорить фоновые слияния при пиковых нагрузках?
**Ответ:** Увеличить размер пула `background_pool_size` в `config.xml` (по умолчанию 16), повысить `max_bytes_to_merge_at_max_space_in_pool`, а также перенести логи и временные данные на более быстрые диски NVMe.
