# Философия Batch Everything: архитектура надежной буферизации

## Условие

**Batch everything.**: ClickHouse оптимизирован для batch inserts (тысячи-миллионы строк). Single-row inserts — это антипаттерн (в 100-1000x медленнее).

## Теория

ClickHouse кардинально меняет подход к проектированию архитектуры сервисов:

### Парадигма Batch Everything:
1. **Никаких поштучных вставок:** Запись в ClickHouse обязана выполняться крупными пакетами (от 10 000 до 500 000 строк).
2. **Внешние буферы сообщений (Apache Kafka):** Сервисы пишут события в Kafka поштучно (где Kafka оптимизирована для append-only логов). Вычитка из Kafka и запись в ClickHouse производятся пакетными воркерами крупными чанками.
3. **Защита от сбоев:** При падении воркера оффсеты в Kafka не коммитятся, обеспечивая отсутствие потери данных при перезапуске.

## Решение по шагам

1. Разработайте архитектурный шаблон Go worker для вычитки сообщений пачками.
2. Сформируйте локальный буфер накопления.
3. Реализуйте сброс батча в ClickHouse с фиксацией смещений.
4. Продемонстрируйте пропускную способность.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

type PipelineWorker struct {
	conn       clickhouseConn
	bufferSize int
}

type clickhouseConn = interface{}

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Имитация конвейера накопления батча из шины сообщений
	batchSize := 10000
	events := make([]uint64, batchSize)
	for i := 0; i < batchSize; i++ {
		events[i] = uint64(100000 + i)
	}

	start := time.Now()
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO events (id, user_id, event_time, payload)")
	if err != nil {
		panic(err)
	}

	now := time.Now()
	for _, uid := range events {
		_ = batch.Append(uuid.New(), uid, now, "batch_everything_philosophy")
	}

	if err := batch.Send(); err != nil {
		panic(err)
	}

	elapsed := time.Since(start)
	fmt.Printf("Батч из %d событий зафиксирован за %v (%.0f строк/сек)\n",
		batchSize, elapsed, float64(batchSize)/elapsed.Seconds())
	fmt.Println("Архитектурный принцип: один батч в 1 секунду вместо 10 000 сетевых запросов!")
}
```

ℹ️ Архитектурный паттерн Batch Everything для обеспечения максимального RPS

**`Терминал`**

```bash
go run main.go
# Батч из 10000 событий зафиксирован за 22ms (454545 строк/сек)
# Архитектурный принцип: один батч в 1 секунду вместо 10 000 сетевых запросов!
```

## Под капотом

Запись 10 000 строк одним батчем создает один файл данных и одну запись в логе репликации ZooKeeper. Запись тех же 10 000 строк поштучно создает 80 000 файлов на диске и перегружает метаданные СУБД, снижая пропускную способность системы в сотни раз.

## Подводные камни

Слишком большой размер батча (например, 10 миллионов строк в одном вызове) может превысить лимит таймаута контекста или привести к OOM на стороне клиента Go. Балансируйте размер батча в пределах 50 000 – 250 000 строк.

## На собеседовании

**Вопрос:** Как проектировать API сервиса сбора аналитики, чтобы клиентские мобильные приложения не перегружали бэкенд одиночными запросами?
**Ответ:** Мобильный SDK накапливает аналитические события в локальной базе SQLite/Realm на устройстве и отправляет их на бэкенд пачками по 50–100 событий раз в 30 секунд или при закрытии приложения (Client-side Batching). Бэкенд сбрасывает их в Kafka, откуда они крупными блоками попадают в ClickHouse.
