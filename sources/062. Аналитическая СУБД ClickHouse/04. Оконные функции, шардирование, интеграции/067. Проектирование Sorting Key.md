# Проектирование Sorting Key: Правило префикса и кардинальности

## Условие

**Sorting key**: Поймите, как sorting key влияет на производительность запросов. Первые поля в ORDER BY должны быть в WHERE.

## Теория

Ключ сортировки `ORDER BY` — самый ответственный архитектурный выбор при проектировании схемы ClickHouse:

### Главные правила проектирования ORDER BY:
1. **Порядок колонок (Rule of Prefix):** Первыми должны идти колонки, которые наиболее часто присутствуют в фильтрах `WHERE` (`tenant_id`, `date`, `event_type`).
2. **Кардинальность (Low-to-High):** Колонки с низкой кардинальностью (мало уникальных значений) должны стоять раньше колонок с высокой кардинальностью. Это максимизирует сжатие последующих колонок кодеками LZ4/DoubleDelta.
3. **Монотонность:** Монотонно возрастающие даты (`event_date`) на втором-третьем месте упорядочивают данные по времени внутри каждого клиента.

## Решение по шагам

1. Спроектируйте таблицу мультитенантной аналитики с правильным `ORDER BY (tenant_id, toDate(event_time), user_id)`.
2. Продемонстрируйте работу фильтрации по префиксу через `EXPLAIN indexes = 1`.
3. Покажите, почему фильтрация только по `user_id` без указания `tenant_id` приведет к полному перебору.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Идеальный композитный ORDER BY для SaaS платформы
	ddl := `
	CREATE TABLE IF NOT EXISTS saas_events (
		tenant_id UInt32,
		event_date Date,
		user_id UInt64,
		action LowCardinality(String)
	) ENGINE = MergeTree()
	ORDER BY (tenant_id, event_date, user_id);
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}

	// Запрос с префиксным фильтром по первичному ключу
	explainQuery := `
		EXPLAIN indexes = 1
		SELECT count() 
		FROM saas_events 
		WHERE tenant_id = 42 AND event_date = '2026-09-04'
	`
	rows, err := conn.Query(ctx, explainQuery)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("Инспекция плана: использование префикса первичного ключа:")
	for rows.Next() {
		var line string
		if err := rows.Scan(&line); err != nil {
			panic(err)
		}
		fmt.Println(" ", line)
	}
}
```

ℹ️ Проектирование композитного ключа сортировки ORDER BY с соблюдением правила префикса

#       Indexes:

## Под капотом

Разреженный индекс упорядочен лексикографически по кортежу `(col1, col2, col3)`. Бинарный поиск по индексу может отсекать диапазоны гранул только до тех пор, пока условия в `WHERE` соответствуют непрерывному префиксу ключа сортировки.

## Подводные камни

Помещение колонки `user_id` (миллионы уникальных значений) на первое место в `ORDER BY (user_id, tenant_id)` разрушит возможность фильтровать по `tenant_id` без полного сканирования таблицы.

## На собеседовании

**Вопрос:** Как эффективно искать данные по альтернативным ключам без дублирования всей таблицы?
**Ответ:** 1. Использовать вторичные индексы пропуска данных (`bloom_filter`). 2. Создать материализованное представление с другим `ORDER BY` (`CREATE MATERIALIZED VIEW mv TO target_table ... ORDER BY (user_id, event_date)`).
