# Кластерная архитектура: Шардирование и ReplicatedMergeTree

## Условие

**Distributed tables**: Создайте `Distributed` таблицу для шардирования по кластеру. Используйте `ReplicatedMergeTree` для HA.

## Теория

Полноценная корпоративная топология ClickHouse в BigTech строится по формуле **\(N\) шардов \(\times\) \(M\) реплик**:

### Архитектурный стек:
1. **Каждый шард** отвечает за свою часть данных (горизонтальное партиционирование).
2. **Внутри каждого шарда** работают 2 или 3 реплики с движком `ReplicatedMergeTree` для высокой доступности (HA) и автоматического failover.
3. Поверх разворачивается фасад `ENGINE = Distributed(cluster_name, db, table_local, sharding_key)`.
4. Запись батчей из Go направляется непосредственно в локальные таблицы конкретного шарда (`events_local`), а аналитические запросы выполняются через `events_all` (Distributed).

## Решение по шагам

1. Создайте кластерную локальную таблицу `events_cluster_local` с `ReplicatedMergeTree`.
2. Создайте распределенную таблицу `events_cluster_all` на движке `Distributed`.
3. Реализуйте в Go балансировку вставок по шардам на базе алгоритма консистентного хэширования.
4. Выполните распределенный `SELECT count()` со сбором данных со всех узлов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// 1. Создание локальной таблицы на каждом узле кластера
	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS events_cluster_local (
			id UInt64,
			user_id UInt64,
			event_name String
		) ENGINE = MergeTree()
		ORDER BY (user_id, id);
	`)

	// 2. Создание распределенного фасада Distributed
	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS events_cluster_all AS events_cluster_local
		ENGINE = Distributed(default, default, events_cluster_local, cityHash64(user_id));
	`)

	// 3. Инспекция кластерных узлов в системной таблице system.clusters
	rows, err := conn.Query(ctx, "SELECT cluster, shard_num, replica_num, host_name FROM system.clusters")
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("Топология кластера ClickHouse (system.clusters):")
	for rows.Next() {
		var (
			cluster, host string
			shard, rep    uint32
		)
		if err := rows.Scan(&cluster, &shard, &rep, &host); err != nil {
			panic(err)
		}
		fmt.Printf("  Кластер: %-10s | Шард: %d | Реплика: %d | Хост: %s\n",
			cluster, shard, rep, host)
	}
}
```

ℹ️ Построение двухуровневой топологии хранения с Distributed и локальными таблицами

**`Терминал`**

```bash
go run main.go
# Топология кластера ClickHouse (system.clusters):
#   Кластер: default    | Шард: 1 | Реплика: 1 | Хост: 127.0.0.1
```

## Под капотом

Когда координатор выполняет `SELECT` из `Distributed` таблицы, он парсит SQL AST, преобразует имя таблицы в локальное `events_cluster_local`, сериализует запрос и рассылает его по TCP сокетам на все реплики шардов. Промежуточные агрегаты стекаются обратно и объединяются в один поток.

## Подводные камни

Не выполняйте тяжелые `JOIN` между двумя разными `Distributed` таблицами без явного `GLOBAL JOIN`. Классический распределенный `JOIN` приведет к квадратичному умножению запросов (\(N \times M\) сетевых вызовов) и падению кластера по таймауту.

## На собеседовании

**Вопрос:** Как организовать запись в шардированный кластер ClickHouse без использования Distributed таблиц?
**Ответ:** Разработчик на стороне Go использует хэш-функцию (например `jump.Hash(cityHash64(user_id), numShards)`), определяет целевой узел и отправляет батч по нативному протоколу напрямую в `table_local` конкретного шарда. Это исключает двойной сетевой трафик и разгружает координаторы.
