# ClickHouse не для OLTP: Архитектурные ограничения и границы применимости

## Условие

**ClickHouse не для OLTP.**: Не используйте ClickHouse для transactional workload'ов с частыми updates. Это read-optimized БД.

## Теория

ClickHouse — выдающаяся аналитическая СУБД (OLAP), но категорически непригодна для транзакционной нагрузки (OLTP).

### Почему ClickHouse нельзя использовать как основную базу веб-приложения:
1. **Отсутствие ACID-транзакций между таблицами:** Нет операторов `BEGIN`, `COMMIT`, `ROLLBACK`. Нельзя атомарно перевести деньги с одного счета на другой.
2. **Тяжелые мутации (No in-place UPDATE):** Команда `ALTER TABLE ... UPDATE` не изменяет запись на месте, а переписывает весь файл столбца парта на диске. Десяток параллельных апдейтов парализует диск.
3. **Отсутствие строгой ссылочной целостности:** Нет `FOREIGN KEY`, нет проверки уникальности на лету (`UNIQUE CONSTRAINT`).
4. **Неэффективность точечных запросов:** Запрос `SELECT * FROM users WHERE id = 42` сканирует минимум одну гранулу (8192 строки) и считывает десятки файлов колонок, расходуя несоизмеримо больше ресурсов, чем B-Tree поиск в PostgreSQL.

## Решение по шагам

1. Напишите код демонстрации медленной мутации через `ALTER TABLE ... UPDATE`.
2. Исследуйте системную таблицу `system.mutations`.
3. Сравните архитектурные границы применимости ClickHouse и реляционных СУБД.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS oltp_test (
			id UInt64,
			status String,
			updated_at DateTime
		) ENGINE = MergeTree()
		ORDER BY id;
	`)

	// Демонстрация мутации ALTER TABLE UPDATE (асинхронная тяжелая операция)
	mutationSQL := `ALTER TABLE oltp_test UPDATE status = 'BANNED' WHERE id = 100`
	start := time.Now()
	if err := conn.Exec(ctx, mutationSQL); err != nil {
		panic(err)
	}
	fmt.Printf("Команда мутации принята ClickHouse за %v\n", time.Since(start))

	// Инспекция статуса выполнения мутации в system.mutations
	query := `
		SELECT mutation_id, command, is_done 
		FROM system.mutations 
		WHERE table = 'oltp_test' 
		ORDER BY create_time DESC 
		LIMIT 1
	`
	var (
		mutID, cmd string
		isDone     uint8
	)
	if err := conn.QueryRow(ctx, query).Scan(&mutID, &cmd, &isDone); err == nil {
		fmt.Printf("Мутация %s в очереди: Команда='%s', Завершена=%d\n",
			mutID, cmd, isDone)
	}

	fmt.Println("\nВЫВОД АРХИТЕКТОРА: ClickHouse предназначен для аналитических выборок по миллиардам строк.")
	fmt.Println("Для пользовательских сессий, профилей и финансовых транзакций используйте PostgreSQL / Redis!")
}
```

ℹ️ Демонстрация асинхронной природы мутаций ALTER UPDATE и границ применимости ClickHouse

## Под капотом

Команда `ALTER TABLE ... UPDATE` создает файл мутации `mutation_N.txt`. Сервер ClickHouse планирует фоновую задачу, которая читает затронутые парты, вычисляет новые значения, формирует совершенно новые папки партов на диске и заменяет старые парты новыми. Это генерирует огромный Write Amplification.

## Подводные камни

Вызов сотен `ALTER TABLE UPDATE / DELETE` в секунду из Go-приложения приведет к переполнению очереди мутаций (`Too many mutations in table`) и полной остановке сервера ClickHouse.

## На собеседовании

**Вопрос:** Как в ClickHouse обновлять данные без использования тяжелых мутаций `ALTER TABLE UPDATE`?
**Ответ:** 1. Использовать `ReplacingMergeTree` (вставлять новую строку с большим версионным номером). 2. Использовать `CollapsingMergeTree` (вставлять строку отмены `-1` и строку нового значения `+1`). 3. Использовать словари для часто меняющихся атрибутов.
