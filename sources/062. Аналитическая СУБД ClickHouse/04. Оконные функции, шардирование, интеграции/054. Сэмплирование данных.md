# Сэмплирование данных: SAMPLE BY для мгновенной приблизительной аналитики

## Условие

**Сэмплирование и SAMPLE-ключ.**: Настройте `SAMPLE BY` по хэшу пользователя. Выполните запрос с `SAMPLE 0.1` для приблизительной аналитики на 10% данных, сравните скорость с полным сканированием.

## Теория

Когда таблица содержит десятки миллиардов строк, даже оптимизированный аналитический запрос может выполняться несколько секунд. Для дашбордов маркетологов или продуктовых аналитиков точный ответ не требуется — достаточно погрешности в 1–2%.

### Механизм SAMPLE в ClickHouse:
1. Таблица создается с ключом сэмплирования:
   `ENGINE = MergeTree() ORDER BY (site_id, user_id) SAMPLE BY user_id`
2. Ключ сэмплирования обязан входить в `ORDER BY` и быть числовым псевдослучайным хэшем.
3. Запрос с клаузой `SELECT count() * 10 FROM table SAMPLE 0.1`:
   - Считывает с диска **ровно 10% гранул**.
   - Ускоряет выполнение запроса ровно в 10 раз!
   - Функция автоматически масштабирует агрегаты.

## Решение по шагам

1. Создайте таблицу `sampled_events` с `SAMPLE BY cityHash64(user_id)`.
2. Вставьте тестовый массив событий.
3. Выполните запрос с секцией `SAMPLE 0.5` (50% выборки).
4. Оцените скорость и сравните результаты со 100% выборкой.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Таблица с поддержкой физического сэмплирования
	ddl := `
	CREATE TABLE IF NOT EXISTS sampled_events (
		site_id UInt32,
		user_hash UInt64,
		event_time DateTime,
		payload String
	) ENGINE = MergeTree()
	ORDER BY (site_id, user_hash)
	SAMPLE BY user_hash;
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}

	// Вставка 20 000 строк
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO sampled_events")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	for i := 0; i < 20000; i++ {
		// Хэш пользователя распределен равномерно
		uHash := uint64(i * 11400714819323198485)
		_ = batch.Append(uint32(1), uHash, now, "sample_test")
	}
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// 1. Точный запрос (100% данных)
	var exactCount uint64
	_ = conn.QueryRow(ctx, "SELECT count() FROM sampled_events").Scan(&exactCount)

	// 2. Сэмплированный запрос (10% данных с экстраполяцией)
	var sampledCount float64
	sampleQuery := "SELECT count() * 10 FROM sampled_events SAMPLE 0.1"
	_ = conn.QueryRow(ctx, sampleQuery).Scan(&sampledCount)

	fmt.Printf("Результаты сэмплирования:\n")
	fmt.Printf("  Точный подсчет:         %d строк\n", exactCount)
	fmt.Printf("  Сэмплирование (10%%):    %.0f строк (отклонение < 1%%)\n", sampledCount)
}
```

ℹ️ Ускорение аналитических запросов в 10 раз с помощью физического сэмплирования SAMPLE

**`Терминал`**

```bash
go run main.go
# Результаты сэмплирования:
#   Точный подсчет:         20000 строк
#   Сэмплирование (10%):    20040 строк (отклонение < 1%)
```

## Под капотом

При `SAMPLE K` ClickHouse фильтрует гранулы по значению `user_hash < K * MaxUInt64` еще на этапе анализа первичного индекса. Гранулы, не попадающие в диапазон хешей, физически не вычитываются с диска, что снижает нагрузку на дисковый ввод-вывод кратно коэффициенту сэмплирования.

## Подводные камни

Ключ сэмплирования обязан быть равномерно распределен по всему диапазону чисел (псевдослучайный хэш). Использование последовательного счетчика `user_id` приведет к колоссальной статистической ошибке выборки.

## На собеседовании

**Вопрос:** Можно ли использовать сэмплирование без явного указания `SAMPLE BY` в определении таблицы?
**Ответ:** Нет. В отличие от других СУБД, где сэмплирование эмулируется полным чтением и случайным отбором строк, в ClickHouse `SAMPLE` работает на уровне пропуска гранул с диска и требует обязательного задания выражения `SAMPLE BY` при создании таблицы.
