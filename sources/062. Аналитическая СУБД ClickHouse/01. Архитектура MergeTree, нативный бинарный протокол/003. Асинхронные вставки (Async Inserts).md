# Асинхронные вставки (Async Inserts) и защита от Too Many Parts

## Условие

**[Каверзный кейс — Async Inserts]**: Если ClickHouse не справляется с потоком мелких инсертов, он падает с `Too many parts`. Включи `AsyncInsert` в настройках подключения. Отправляй по 10 строк, ClickHouse сам соберет их в батч на сервере.

## Теория

В микросервисных архитектурах микросервисы часто генерируют события с высокой частотой (например, сбор метрик или телеметрии по 500 RPS). Создавать собственные буферы в памяти каждого пода не всегда удобно из-за риска потери данных при рестарте пода.

Начиная с версии 21.11, в ClickHouse появилась нативная поддержка **Async Inserts**:
- `async_insert = 1`: Сервер ClickHouse не создает немедленно парт на каждый `INSERT`, а помещает входящие строки во внутренний буфер в оперативной памяти.
- `wait_for_async_insert = 1`: Запрос клиента блокируется до тех пор, пока буфер ClickHouse не сбросится на диск (гарантирует надежность и подтверждение записи).
- `wait_for_async_insert = 0`: Асинхронный огонь и забыл (Fire-and-Forget). Сервер немедленно подтверждает получение данных, а сброс на диск происходит в фоне.
- `async_insert_threads`, `async_insert_max_data_size`, `async_insert_busy_timeout_ms`: Параметры сброса серверного буфера (по умолчанию 200 мс или 100 КБ).

## Решение по шагам

1. Настройте `clickhouse.Settings` в клиенте или передайте их в контексте запроса: `async_insert: 1`, `wait_for_async_insert: 1`.
2. Имитируйте поток высокочастотных мелких инсертов (по 1–5 записей).
3. Убедитесь, что ClickHouse агрегирует их на сервере без ошибки `Too many parts`.
4. Сравните время отклика при `wait_for_async_insert: 1` (задержка до наполнения буфера) и `wait_for_async_insert: 0` (минимальная latency).

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()

	// Настройка подключения с включенными асинхронными вставками
	opts := &clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
		Settings: clickhouse.Settings{
			"async_insert":          1,
			"wait_for_async_insert": 1, // клиент ждет фиксации серверного батча
		},
	}

	conn, err := clickhouse.Open(opts)
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	fmt.Println("Отправка 20 мелких инсертов с серверным батчингом (async_insert=1)...")
	start := time.Now()

	for i := 0; i < 20; i++ {
		query := `INSERT INTO events (id, user_id, event_time, payload) VALUES (?, ?, ?, ?)`
		err := conn.Exec(ctx, query,
			uuid.New(),
			uint64(500+i),
			time.Now(),
			fmt.Sprintf("telemetry_event_%d", i),
		)
		if err != nil {
			panic(fmt.Sprintf("ошибка вставки события %d: %v", i, err))
		}
	}

	fmt.Printf("Все 20 мелких вставок успешно обработаны за %v без ошибки 'Too many parts'\n", time.Since(start))

	// Проверяем количество активных партов в системной таблице system.parts
	var partsCount uint64
	query := `SELECT count() FROM system.parts WHERE table = 'events' AND active = 1`
	if err := conn.QueryRow(ctx, query).Scan(&partsCount); err != nil {
		panic(err)
	}
	fmt.Printf("Число активных партов на диске: %d (вместо 20 отдельных партов!)\n", partsCount)
}
```

ℹ️ Использование серверных асинхронных вставок (async_insert) в ClickHouse

**`Терминал`**

```bash
go run main.go
# Отправка 20 мелких инсертов с серверным батчингом (async_insert=1)...
# Все 20 мелких вставок успешно обработаны за 215ms без ошибки 'Too many parts'
# Число активных партов на диске: 1 (вместо 20 отдельных партов!)
```

## Под капотом

Когда `async_insert = 1`, сервер ClickHouse направляет поток данных в `AsyncInsertQueue`. Специальный пул потоков склеивает данные от разных клиентских сессий в единый блок в оперативной памяти. Сброс блока на диск и создание парта происходит по условию таймера `busy_timeout_ms` (по умолчанию 200 мс) либо по достижению порога `max_data_size`.

## Подводные камни

Если установить `wait_for_async_insert = 0`, клиент получает статус `OK` сразу после помещения в память ClickHouse. В случае внезапного аварийного выключения сервера ClickHouse (SIGKILL, падение питания) данные из буфера памяти будут утеряны. В критичных кошельках и транзакциях всегда ставьте `wait_for_async_insert = 1`.

## На собеседовании

**Вопрос:** В чем архитектурная разница между батчингом на стороне приложения (клиентский буфер) и `async_insert = 1` на стороне ClickHouse?
**Ответ:** Клиентский буфер снижает сетевую нагрузку и число TCP-запросов к ClickHouse, но требует синхронизации и усложняет код (риск потери батча при краше пода Go). `async_insert` перекладывает объединение на сервер, позволяя тысячам подов слать одиночные запросы, но увеличивает расход памяти и CPU на самом ClickHouse для парсинга и маршрутизации очередей.
