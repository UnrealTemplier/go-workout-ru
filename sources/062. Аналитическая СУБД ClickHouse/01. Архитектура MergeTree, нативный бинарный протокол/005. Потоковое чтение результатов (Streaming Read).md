# Потоковое чтение результатов (Streaming Read) через rows.Next()

## Условие

**[Streaming Read]**: Напиши запрос `SELECT * FROM events WHERE user_id = 123`. Читай результат стримингом через `rows.Next()`, не загружая весь результат в память.

## Теория

Аналитические запросы в ClickHouse часто возвращают миллионы строк (выгрузка отчетов, обучение моделей ML, экспорт в data lake). Если загрузить результат запроса в память целиком (например, слайс структур), сервис неизбежно упадет с ошибкой OOM (Out Of Memory).

### Архитектура Streaming Read в clickhouse-go:
1. Метод `conn.Query(ctx, query, args...)` возвращает интерфейс `driver.Rows`.
2. Сервер ClickHouse отправляет данные клиенту порциями — **блоками (Blocks)** по 65 536 строк.
3. Метод `rows.Next()` итерируется по строкам текущего блока в памяти клиента, а когда блок заканчивается, драйвер прозрачно вычитывает из сетевого сокета следующий блок.
4. Потребление памяти приложением остается константным \(O(1)\) независимо от того, сколько миллиардов строк возвращает запрос.

## Решение по шагам

1. Сформируйте аналитический запрос с фильтром по `user_id`.
2. Вызовите `conn.Query(ctx, "SELECT id, user_id, event_time, payload FROM events WHERE user_id = ?", targetUser)`.
3. Обязательно добавьте `defer rows.Close()` для предотвращения утечки сетевого сокета.
4. В цикле `for rows.Next()` выполняйте `rows.Scan(&id, &userID, &eventTime, &payload)`.
5. Обрабатывайте каждую строку потоково (агрегация, стриминг клиенту через HTTP chunked transfer или запись в файл).
6. Проверьте ошибку `rows.Err()` после завершения цикла.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	targetUserID := uint64(1001)

	// Запрос на потоковое чтение
	query := `
		SELECT id, user_id, event_time, payload 
		FROM events 
		WHERE user_id = ? 
		ORDER BY event_time ASC
	`

	rows, err := conn.Query(ctx, query, targetUserID)
	if err != nil {
		panic(fmt.Sprintf("ошибка выполнения Query: %v", err))
	}
	defer rows.Close()

	var count int
	var lastEventTime time.Time

	// Потоковая обработка: O(1) памяти в Go
	for rows.Next() {
		var (
			id        uuid.UUID
			userID    uint64
			eventTime time.Time
			payload   string
		)

		if err := rows.Scan(&id, &userID, &eventTime, &payload); err != nil {
			panic(fmt.Sprintf("ошибка Scan: %v", err))
		}

		count++
		lastEventTime = eventTime
		// Потоковая обработка без накопления в слайсе
		if count%50000 == 0 {
			fmt.Printf("Прочитано потоком %d строк, текущая дата: %v\n", count, eventTime)
		}
	}

	if err := rows.Err(); err != nil {
		panic(fmt.Sprintf("ошибка в процессе стриминга: %v", err))
	}

	fmt.Printf("Успешно обработано потоком строк: %d. Последнее событие: %v\n", count, lastEventTime)
}
```

ℹ️ Потоковая обработка аналитической выборки с константной памятью через rows.Next()

**`Терминал`**

```bash
go run main.go
# Прочитано потоком 50000 строк, текущая дата: 2026-09-04 12:00:00 +0000 UTC
# Успешно обработано потоком строк: 85240. Последнее событие: 2026-09-04 18:30:15 +0000 UTC
```

## Под капотом

Когда приложение вызывает `rows.Scan()`, драйвер извлекает значения из предварительно аллоцированного колоночного вектора в памяти. Сетевой буфер читает следующий пакет `ProtocolServerData` только когда индекс текущего блока достигает его размера. Если приложение читает медленно, срабатывает TCP Flow Control (zero window), приостанавливая отправку данных со стороны ClickHouse.

## Подводные камни

Забытый `rows.Close()` оставляет сокет в заблокированном состоянии ожидания чтения оставшихся блоков. Соединение не возвращается в пул соединений, что быстро приводит к исчерпанию пула `max_open_conns`.

## На собеседовании

**Вопрос:** Чем отличается `conn.Query()` от `conn.Select()` в `clickhouse-go/v2`?
**Ответ:** `conn.Select(ctx, &slice, query)` вычитывает все строки целиком в слайс структур в памяти, выполняя автоматический рефлексивный маппинг полей. `conn.Query(ctx, query)` возвращает курсор `driver.Rows` для потокового чтения по одной строке, исключая риск OOM при обработке больших выборок.
