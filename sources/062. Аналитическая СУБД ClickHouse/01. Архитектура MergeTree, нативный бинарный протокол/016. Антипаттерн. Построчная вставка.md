# Антипаттерн: Построчная вставка (Single-row Inserts) и анализ Too Many Parts

## Условие

**Антипаттерн (Построчная запись)**: Напиши цикл, который 10 000 раз вызывает `conn.Exec("INSERT INTO events ... VALUES ...")`. Изучи метрики БД или просто посмотри, как долго это работает. ClickHouse ненавидит частые маленькие инсерты (это порождает кучу мелких файлов на диске — parts).

## Теория

Самая частая и разрушительная ошибка разработчиков, переходящих на ClickHouse из реляционных баз данных (PostgreSQL, MySQL) — выполнение одиночных вставок `INSERT INTO table VALUES (...)` в цикле.

### Почему это катастрофа для ClickHouse?
1. **Создание партов:** Каждый вызов `INSERT` создает отдельную директорию на диске (парт) со всеми файлами колонок (`col.bin`, `col.mrk2`, `default_compression_codec.txt`).
2. **Перегрузка файловой системы:** 10 000 вставок создают 10 000 директорий и 80 000+ файлов.
3. **Лимит партов:** В ClickHouse установлен жесткий защитный лимит `parts_to_throw_insert = 300` (по умолчанию). Как только число неслитых партов в одной партиции превышает 300, ClickHouse полностью блокирует запись с ошибкой `Too many parts in all data parts in table`.

## Решение по шагам

1. Напишите код, демонстрирующий замер скорости построчной вставки 1 000 строк.
2. Обратите внимание на резкий рост времени выполнения и задержки ответа.
3. Запросите метрики из системной таблицы `system.parts` и `system.events`.
4. Сравните с пакетной вставкой тех же 1 000 строк.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS test_antipattern (
			id UUID,
			val UInt32
		) ENGINE = MergeTree()
		ORDER BY id;
	`)

	// Демонстрация антипаттерна: 100 поштучных вставок
	count := 100
	fmt.Println("Выполнение антипаттерна: поштучные одиночные вставки...")
	startSingle := time.Now()
	for i := 0; i < count; i++ {
		err := conn.Exec(ctx, "INSERT INTO test_antipattern VALUES (?, ?)", uuid.New(), uint32(i))
		if err != nil {
			panic(err)
		}
	}
	durSingle := time.Since(startSingle)

	// Замер правильной пакетной вставки тех же 100 строк
	startBatch := time.Now()
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO test_antipattern")
	if err != nil {
		panic(err)
	}
	for i := 0; i < count; i++ {
		_ = batch.Append(uuid.New(), uint32(i))
	}
	_ = batch.Send()
	durBatch := time.Since(startBatch)

	fmt.Printf("Результаты сравнения для %d строк:\n", count)
	fmt.Printf("  Поштучный INSERT: %v (%.1f строк/сек) — ОПАСНО (порождает сотни мелких партов)\n",
		durSingle, float64(count)/durSingle.Seconds())
	fmt.Printf("  Пакетный Batch:   %v (%.1f строк/сек) — БЫСТРЕЕ В %d РАЗ!\n",
		durBatch, float64(count)/durBatch.Seconds(), durSingle/durBatch)
}
```

ℹ️ Экспериментальное доказательство неэффективности поштучной записи в ClickHouse

**`Терминал`**

```bash
go run main.go
# Выполнение антипаттерна: поштучные одиночные вставки...
# Результаты сравнения для 100 строк:
#   Поштучный INSERT: 420ms (238.1 строк/сек) — ОПАСНО (порождает сотни мелких партов)
#   Пакетный Batch:   4ms (25000.0 строк/сек) — БЫСТРЕЕ В 105 РАЗ!
```

## Под капотом

При каждом одиночном `INSERT` сервер ClickHouse выполняет системные вызовы создания файлов, записи контрольных сумм `checksums.txt`, добавления записи в лог репликации в ZooKeeper (для ReplicatedMergeTree) и пробуждает поток `BackgroundProcessingPool` для слияния. 1 000 вставок в секунду перегружают очередь слияний и диск на 100%.

## Подводные камни

Никогда не используйте ORM (вроде GORM), настроенные на стандартные `Create(&item)` для ClickHouse. ClickHouse требует специализированного паттерна буферизации данных перед записью.

## На собеседовании

**Вопрос:** Что делать, если сервис не может собирать батчи в памяти (например, критичные финансовые события или stateless лямбды), а ClickHouse падает с `Too many parts`?
**Ответ:** 1. Использовать промежуточный буфер сообщений — Apache Kafka или RabbitMQ, откуда специализированный потребитель (Kafka Engine или Go worker) вычитывает данные крупными батчами. 2. Включить нативные серверные `async_insert = 1` и `wait_for_async_insert = 1`.
