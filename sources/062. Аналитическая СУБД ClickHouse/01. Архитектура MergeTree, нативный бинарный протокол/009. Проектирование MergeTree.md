# Проектирование MergeTree: ORDER BY, разреженный индекс и гранулярность

## Условие

**DDL (MergeTree)**: Создай таблицу `events` с движком `MergeTree`. Обязательно укажи `ORDER BY` (ключ сортировки, он же первичный индекс в CH) — например, по `(app_id, timestamp)`.

## Теория

Движок `MergeTree` — основа хранения данных в ClickHouse. В отличие от традиционных B-деревьев (PostgreSQL/MySQL), где на каждую строку есть указатель в индексе, ClickHouse использует **разреженный первичный индекс (Sparse Primary Index)**.

### Механика работы разреженного индекса:
1. Данные в файлах `.bin` физически отсортированы согласно выражению `ORDER BY (app_id, timestamp)`.
2. Каждые 8192 строки (по умолчанию параметр `index_granularity = 8192`) образуют **гранулу (Granule)**.
3. В файл первичного индекса `primary.cidx` записывается только одно значение ключа — первая строка каждой гранулы!
4. Благодаря этому весь индекс для миллиарда строк занимает всего несколько мегабайт и целиком помещается в RAM.
5. При запросе `WHERE app_id = 42 AND timestamp >= '2026-01-01'` ClickHouse бинарным поиском по `primary.cidx` находит номера гранул, а по марк-файлам `.mrk2` определяет точные смещения байт в сжатых файлах данных.

## Решение по шагам

1. Создайте таблицу `app_events` с композитным `ORDER BY (app_id, toDate(event_time), user_id)`.
2. Настройте гранулярность `SETTINGS index_granularity = 8192`.
3. Напишите Go-код проверки плана выполнения запроса через `EXPLAIN indexes = 1`.
4. Убедитесь, что фильтр по префиксу `app_id` отсекает 99% гранул без полного сканирования таблицы.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Создание таблицы с оптимальным ORDER BY
	ddl := `
	CREATE TABLE IF NOT EXISTS app_events (
		app_id UInt32,
		event_date Date,
		user_id UInt64,
		event_type LowCardinality(String),
		payload String
	) ENGINE = MergeTree()
	ORDER BY (app_id, event_date, user_id)
	SETTINGS index_granularity = 8192;
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}
	fmt.Println("Таблица app_events успешно сконфигурирована с композитным ORDER BY")

	// Проверка работы разреженного индекса через EXPLAIN
	explainQuery := `
		EXPLAIN indexes = 1
		SELECT count() 
		FROM app_events 
		WHERE app_id = 105 AND event_date = '2026-09-04'
	`
	rows, err := conn.Query(ctx, explainQuery)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("План фильтрации по первичному индексу:")
	for rows.Next() {
		var explainLine string
		if err := rows.Scan(&explainLine); err != nil {
			panic(err)
		}
		fmt.Println(" ", explainLine)
	}
}
```

ℹ️ Создание таблицы MergeTree с разреженным первичным индексом и инспекция EXPLAIN

## Под капотом

ClickHouse считывает данные строго блоками гранул. Даже если критерию `WHERE` соответствует ровно 1 строка, ClickHouse прочитает с диска и распакует все 8192 строки гранулы. Именно поэтому ClickHouse не подходит для OLTP с точечными запросами по первичному ключу (`SELECT * FROM table WHERE id = 123` на высокой частоте).

## Подводные камни

Размещение высококардинального поля (например, случайного `UUID` или `timestamp` в наносекундах) на первом месте в `ORDER BY (event_id, app_id)` приведет к тому, что вторичный фильтр по `app_id` будет бесполезен, и ClickHouse выполнит полный перебор таблицы.

## На собеседовании

**Вопрос:** В чем разница между `PRIMARY KEY` и `ORDER BY` в определении MergeTree?
**Ответ:** `ORDER BY` определяет физический порядок сортировки колонок на диске. `PRIMARY KEY` определяет, какие именно колонки войдут в файл разреженного индекса `primary.cidx`. `PRIMARY KEY` обязан являться префиксом `ORDER BY` (например, `ORDER BY (a, b, c) PRIMARY KEY (a, b)`). Это позволяет хранить компактный индекс в памяти, упорядочивая на диске дополнительные колонки для лучшей компрессии.
