# AggregatingMergeTree: промежуточные состояния функций (-State и -Merge)

## Условие

**Материализованные представления.**: Создайте MV, которая при вставке в `events` автоматически агрегирует `count(), sum(amount)` в `events_mv` с `ENGINE = SummingMergeTree`. Объясните, что MV — это trigger на insert, а не view на select.

## Теория

Для агрегаций, которые невозможно просто сложить (как в `SummingMergeTree`), ClickHouse предлагает движок `AggregatingMergeTree`.

### Комбинаторы функций:
- **-State:** Вычисляет промежуточное бинарное состояние агрегатной функции (например, `uniqState(user_id)`, `avgState(duration)`, `quantilesExactState(0.5, 0.95)(latency)`). Возвращает тип данных `AggregateFunction(...)`.
- **-Merge:** Объединяет промежуточные бинарные состояния разных партов во время финального запроса `SELECT uniqMerge(user_id_state)` без необходимости сканирования исходных миллиардов строк!

## Решение по шагам

1. Создайте целевую таблицу `latency_agg` с колонкой `p95 AggregateFunction(quantilesExact(0.95), Float64)` и `ENGINE = AggregatingMergeTree()`.
2. Создайте Materialized View с расчетом `quantilesExactState(0.95)(latency_ms)`.
3. Вставьте сырые события.
4. Выполните финальный запрос с `quantilesExactMerge(0.95)(p95)` для расчета точного 95-го перцентиля за выбранный период.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// 1. Сырая таблица сетевых вызовов
	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS http_requests (
			service LowCardinality(String),
			latency_ms Float64,
			created_at DateTime
		) ENGINE = MergeTree()
		ORDER BY (service, created_at);
	`)

	// 2. Агрегирующая таблица с AggregateFunction
	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS http_requests_stats (
			hour DateTime,
			service LowCardinality(String),
			p95 AggregateFunction(quantilesExact(0.95), Float64)
		) ENGINE = AggregatingMergeTree()
		ORDER BY (service, hour);
	`)

	// 3. Materialized View с комбинатором -State
	_ = conn.Exec(ctx, `
		CREATE MATERIALIZED VIEW IF NOT EXISTS http_requests_stats_mv 
		TO http_requests_stats AS
		SELECT 
			toStartOfHour(created_at) AS hour,
			service,
			quantilesExactState(0.95)(latency_ms) AS p95
		FROM http_requests
		GROUP BY service, hour;
	`)

	// 4. Вставка сырых данных
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO http_requests")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	latencies := []float64{10.2, 12.5, 14.1, 15.0, 95.4, 250.0}
	for _, lat := range latencies {
		_ = batch.Append("auth_service", lat, now)
	}
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// 5. Финальный расчет перцентиля через комбинатор -Merge
	query := `
		SELECT 
			service,
			quantilesExactMerge(0.95)(p95)[1] AS latency_p95
		FROM http_requests_stats
		GROUP BY service
	`
	var (
		service    string
		latencyP95 float64
	)
	if err := conn.QueryRow(ctx, query).Scan(&service, &latencyP95); err != nil {
		panic(err)
	}

	fmt.Printf("Сервис: %s | Вычисленный p95 latency: %.2f ms\n", service, latencyP95)
}
```

ℹ️ Расчет перцентилей за секунды через AggregatingMergeTree и функции -State / -Merge

**`Терминал`**

```bash
go run main.go
# Сервис: auth_service | Вычисленный p95 latency: 250.00 ms
```

## Под капотом

В колонке `AggregateFunction` хранится компактная бинарная структура C++ объекта состояния агрегатора (в случае t-digest или quantilesExact — сериализованный срез отсортированных значений или бакетов). Функция `-Merge` объединяет эти промежуточные бинарные представления алгоритмом слияния, экономя колоссальное количество CPU и ввода-вывода.

## Подводные камни

Вставить данные напрямую через `INSERT` в колонку типа `AggregateFunction` из Go невозможно обычным числом или строкой. Такие таблицы наполняются либо через Materialized Views с вызовом функции `-State`, либо запросом `INSERT INTO ... SELECT ... -State()`.

## На собеседовании

**Вопрос:** В чем разница между `SummingMergeTree` и `AggregatingMergeTree`?
**Ответ:** `SummingMergeTree` применим только для тривиальных аддитивных операций: сложения чисел (`sum`) с автоматическим суммированием при совпадении `ORDER BY`. `AggregatingMergeTree` универсален: он поддерживает любые сложные агрегаты (уники HLL, перцентили, множества, bloom filters) благодаря хранению бинарных состояний `-State`.
