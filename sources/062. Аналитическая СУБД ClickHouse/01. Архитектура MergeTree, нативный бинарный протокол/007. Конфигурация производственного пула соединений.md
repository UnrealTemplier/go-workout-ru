# Конфигурация производственного пула соединений ClickHouse

## Условие

**Бинарное подключение к ClickHouse**: Установите современный нативный драйвер ClickHouse `github.com/ClickHouse/clickhouse-go/v2`. Напишите код подключения к БД через нативный TCP-порт (обычно `9000`), используя бинарный протокол. Объясните в комментариях преимущества бинарного протокола перед HTTP-интерфейсом при передаче больших объемов данных.

## Теория

В высоконагруженных микросервисах корректная настройка пула соединений драйвера ClickHouse имеет критическое значение для устойчивости к спайкам нагрузки (Traffic Spikes).

### Ключевые параметры `clickhouse.Options`:
- `Addr`: Срез адресов нод кластера `[]string{"ch01:9000", "ch02:9000"}` для встроенной балансировки Round-Robin.
- `MaxOpenConns`: Максимальное количество открытых TCP-сокетов. ClickHouse — аналитическая база, где параллелизм запросов на один узел обычно ограничен числом CPU-ядер (слишком много параллельных `SELECT` приведет к деградации). Обычно задается от 10 до 30.
- `MaxIdleConns`: Число простаивающих соединений в пуле (рекомендуется держать равным `MaxOpenConns`, чтобы избежать постоянных TCP handshakes).
- `ConnMaxLifetime`: Максимальное время жизни сокета (например, 1 час) для плавной смены IP при DNS-ротации.
- `Compression`: Алгоритм сжатия трафика (`CompressionLZ4` для баланса CPU/Traffic, `CompressionZSTD` для максимального сжатия).

## Решение по шагам

1. Сформируйте конфигурацию `clickhouse.Options` с пулом нод и сжатием LZ4.
2. Задайте лимиты пула соединений `MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime`.
3. Настройте таймауты подключения: `DialTimeout`, `ConnOpenStrategy: clickhouse.ConnOpenRoundRobin`.
4. Реализуйте проверку состояния соединений через Healthcheck-функцию.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/ClickHouse/clickhouse-go/v2/lib/driver"
)

func NewClickHousePool() (driver.Conn, error) {
	opts := &clickhouse.Options{
		Addr: []string{
			"127.0.0.1:9000",
		},
		Auth: clickhouse.Auth{
			Database: "default",
			Username: "default",
			Password: "",
		},
		DialTimeout:      3 * time.Second,
		MaxOpenConns:     20,
		MaxIdleConns:     20,
		ConnMaxLifetime:  1 * time.Hour,
		ConnOpenStrategy: clickhouse.ConnOpenRoundRobin,
		Compression: &clickhouse.Compression{
			Method: clickhouse.CompressionLZ4,
		},
		Settings: clickhouse.Settings{
			"max_threads":        8,
			"max_execution_time": 30,
		},
	}

	conn, err := clickhouse.Open(opts)
	if err != nil {
		return nil, fmt.Errorf("ошибка clickhouse.Open: %w", err)
	}

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	if err := conn.Ping(ctx); err != nil {
		return nil, fmt.Errorf("ClickHouse ping failed: %w", err)
	}

	return conn, nil
}

func main() {
	pool, err := NewClickHousePool()
	if err != nil {
		panic(err)
	}
	defer pool.Close()

	stats := pool.Stats()
	fmt.Printf("ClickHouse пул инициализирован: Open=%d, Idle=%d\n",
		stats.Open, stats.Idle)
}
```

ℹ️ Настройка промышленного пула соединений clickhouse-go с LZ4 и RoundRobin

**`Терминал`**

```bash
go run main.go
# ClickHouse пул инициализирован: Open=1, Idle=1
```

## Под капотом

В отличие от OLTP СУБД (PostgreSQL), где нормальным считается держать 200–500 соединений, один сложный аналитический запрос в ClickHouse способен утилизировать все доступные процессорные ядра сервера (`max_threads`). Установка `MaxOpenConns: 100` на 10 сервисах может полностью парализовать кластер ClickHouse тысячами конкурирующих потоков.

## Подводные камни

Использование `ConnOpenInOrder` вместо `ConnOpenRoundRobin` при наличии списка адресов приведет к тому, что весь трафик будет идти исключительно на первую ноду, пока она жива, лишая кластер балансировки нагрузки.

## На собеседовании

**Вопрос:** Почему при работе с ClickHouse не рекомендуется использовать стандартный `database/sql` через `clickhouse-go`, а лучше использовать нативный интерфейс `driver.Conn`?
**Ответ:** Стандартный `database/sql` интерфейс проектировался под OLTP базы данных: он ориентирован на построчную работу (`Scan(&a, &b)`), транзакции (`Begin/Commit`), не поддерживает колоночный API (`Column.Append`), асинхронные вставки и прямое управление серверными настройками запроса (`clickhouse.Settings`).
