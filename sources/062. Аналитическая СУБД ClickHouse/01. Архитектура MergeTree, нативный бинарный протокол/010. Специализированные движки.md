# Специализированные движки: ReplacingMergeTree, SummingMergeTree и AggregatingMergeTree

## Условие

**Специализированные движки.**: Создайте таблицы: `ReplacingMergeTree` (deduplication по `order_id`), `SummingMergeTree` (суммирование `amount` при merge), `AggregatingMergeTree` (хранение `SimpleState`). Покажите, что `SELECT * FROM table FINAL` выполняет dedup/sum на лету, а `OPTIMIZE TABLE` — фоново.

## Теория

Семейство `MergeTree` включает специализированные движки, решающие типовые аналитические задачи во время фонового слияния партов (Background Merge):

1. **ReplacingMergeTree([ver], [is_deleted]):** Удаляет дубликаты строк с одинаковым `ORDER BY`. Если указана колонка `ver`, оставляет строку с наибольшей версией. Решает задачу дедупликации и эмуляции `UPSERT`.
2. **SummingMergeTree([columns]):** Автоматически суммирует числовые колонки для строк с одинаковым `ORDER BY`. Заменяет предварительный расчет счетчиков.
3. **AggregatingMergeTree():** Сохраняет промежуточные состояния агрегатных функций (`AggregateFunction(uniq, UInt64)`, `AggregateFunction(quantile(0.95), Float64)`), позволяя строить инкрементальные материализованные представления (Materialized Views).

## Решение по шагам

1. Создайте таблицу заказов на движке `ReplacingMergeTree(updated_at)`.
2. Создайте таблицу балансов пользователей на движке `SummingMergeTree(amount)`.
3. Вставьте несколько обновлений по одному и тому же `order_id` / `user_id`.
4. Выполните запрос с модификатором `FINAL` (`SELECT * FROM orders FINAL`), принудительно схлопывающим дубликаты на этапе чтения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// 1. ReplacingMergeTree для заказов
	createOrders := `
	CREATE TABLE IF NOT EXISTS orders_replacing (
		order_id UInt64,
		status LowCardinality(String),
		amount Decimal64(2),
		updated_at DateTime
	) ENGINE = ReplacingMergeTree(updated_at)
	ORDER BY order_id;
	`
	if err := conn.Exec(ctx, createOrders); err != nil {
		panic(err)
	}

	// 2. Вставка начального состояния и обновления с более свежей версией
	now := time.Now()
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO orders_replacing")
	if err != nil {
		panic(err)
	}
	// Первоначальный статус
	_ = batch.Append(uint64(5001), "CREATED", 1500.50, now.Add(-10*time.Minute))
	// Обновление статуса (больший updated_at)
	_ = batch.Append(uint64(5001), "PAID", 1500.50, now)
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// 3. Выборка с секцией FINAL гарантирует возврат актуальной версии
	var (
		orderID   uint64
		status    string
		updatedAt time.Time
	)
	query := `SELECT order_id, status, updated_at FROM orders_replacing FINAL WHERE order_id = 5001`
	if err := conn.QueryRow(ctx, query).Scan(&orderID, &status, &updatedAt); err != nil {
		panic(err)
	}

	fmt.Printf("ReplacingMergeTree FINAL результат: OrderID=%d, Status=%s (версия: %v)\n",
		orderID, status, updatedAt.Format(time.RFC3339))
}
```

ℹ️ Дедупликация и эмуляция UPSERT через ReplacingMergeTree с модификатором FINAL

**`Терминал`**

```bash
go run main.go
# ReplacingMergeTree FINAL результат: OrderID=5001, Status=PAID (версия: 2026-09-04T18:30:00Z)
```

## Под капотом

Схлопывание дубликатов в `ReplacingMergeTree` происходит асинхронно во время слияния партов. До слияния на диске физически присутствуют обе строки. Модификатор `FINAL` заставляет ClickHouse объединять и дедуплицировать потоки данных непосредственно на лету во время выполнения `SELECT`, что дает точный результат, но увеличивает время запроса.

## Подводные камни

Чрезмерное использование `SELECT ... FINAL` на больших таблицах без фильтрации по первичному ключу приводит к резкому замедлению запросов, так как ClickHouse отключает многопоточное чтение отдельных партов.

## На собеседовании

**Вопрос:** Как избежать деградации производительности от `FINAL` при использовании `ReplacingMergeTree` в высоконагруженных API?
**Ответ:** 1. Использовать `argMax(status, updated_at)` в запросе с `GROUP BY order_id` вместо `FINAL`. 2. Использовать `optimize_on_insert = 1` или запускать слияние `OPTIMIZE TABLE ... PARTITION ... FINAL` только по регламенту в часы минимальной нагрузки.
