# Колоночная вставка (Column-oriented Inserts) для экстремальных объемов

## Условие

**Column-oriented inserts**: Используйте column-oriented inserts (`appendColumn`) для максимальной производительности при вставке миллионов строк.

## Теория

При вставке сотен миллионов записей (например, при начальной миграции данных или ежедневном ETL) узким местом в Go часто становится аллокация структур данных в памяти.

### Колоночное представление в памяти:
Вместо слайса из миллиона структур `[]Event` (где каждая структура содержит свои указатели и выравнивание полей) данные организуются как **Struct of Arrays (SoA)**:
- `ids := make([]uuid.UUID, N)`
- `userIDs := make([]uint64, N)`
- `timestamps := make([]time.Time, N)`

Такой формат:
1. Занимает непрерывный участок памяти в L1/L2/L3 кэше процессора.
2. Исключает Fragmented Garbage Collection.
3. Напрямую копируется в сетевые буферы через `batch.Column(i).Append(slice)`.

## Решение по шагам

1. Подготовьте генератор SoA-структур на 100 000 записей.
2. Проинициализируйте батч через `conn.PrepareBatch`.
3. Добавьте каждый слайс в соответствующий индекс колонки `batch.Column(idx).Append()`.
4. Отправьте батч через `batch.Send()` и замерьте память через `runtime.ReadMemStats`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	n := 200_000

	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// Выделение памяти под плоские векторы колонок (Struct of Arrays)
	colIDs := make([]uuid.UUID, n)
	colUsers := make([]uint64, n)
	colTimes := make([]time.Time, n)
	colPayloads := make([]string, n)

	now := time.Now()
	for i := 0; i < n; i++ {
		colIDs[i] = uuid.New()
		colUsers[i] = uint64(100000 + i)
		colTimes[i] = now
		colPayloads[i] = "soa_bench_metric"
	}

	runtime.ReadMemStats(&m2)
	memAllocated := float64(m2.Alloc-m1.Alloc) / (1024 * 1024)
	fmt.Printf("Аллоцировано памяти под %d строк: %.2f МБ\n", n, memAllocated)

	start := time.Now()
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO events (id, user_id, event_time, payload)")
	if err != nil {
		panic(err)
	}

	// Прямая колоночная передача
	_ = batch.Column(0).Append(colIDs)
	_ = batch.Column(1).Append(colUsers)
	_ = batch.Column(2).Append(colTimes)
	_ = batch.Column(3).Append(colPayloads)

	if err := batch.Send(); err != nil {
		panic(err)
	}

	elapsed := time.Since(start)
	fmt.Printf("Успешно передано %d строк за %v (%.0f строк/сек)\n",
		n, elapsed, float64(n)/elapsed.Seconds())
}
```

ℹ️ Экстремальная вставка колоночных массивов Struct of Arrays с замером памяти

**`Терминал`**

```bash
go run main.go
# Аллоцировано памяти под 200000 строк: 13.73 МБ
# Успешно передано 200000 строк за 148ms (1351351 строк/сек)
```

## Под капотом

При передаче слайса примитивного типа (например `[]uint64`) драйвер выполняет операцию `unsafe.Slice` или прямое копирование байт в сетевой сокет, минуя цикл обхода элементов в Go. Это позволяет утилизировать 100% пропускной способности интерфейса loopback или 10GbE сети.

## Подводные камни

Попытка передать слайс несовместимого типа (например `[]int` вместо `[]uint64` для колонки `UInt64`) завершится паникой или возвратом ошибки типов во время вызова `batch.Column(i).Append()`, так как колоночные драйверы строго типизированы.

## На собеседовании

**Вопрос:** Почему организация данных Struct of Arrays (SoA) эффективнее Array of Structs (AoS) для колоночных баз данных?
**Ответ:** В AoS данные разных полей чередуются в памяти, поэтому процессору для сбора значений одного столбца приходится совершать постоянные кэш-промахи (Cache Misses). В SoA столбец лежит монолитным куском байт, что позволяет процессору задействовать аппаратный префетчер (Hardware Prefetcher) и векторные инструкции SIMD.
