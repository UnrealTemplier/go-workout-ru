# ReplacingMergeTree: Особенности фоновой дедупликации

## Условие

**ReplacingMergeTree**: Используйте для deduplication. Поймите, что дедупликация происходит только при background merge.

## Теория

`ReplacingMergeTree` часто ошибочно воспринимают как классическую реляционную таблицу с `UNIQUE PRIMARY KEY`.

### Важнейшие особенности ReplacingMergeTree:
1. Дедупликация происходит **только во время фонового слияния (Background Merge)**.
2. Слияние партов в ClickHouse является **эвентуальным (eventual)**: точный момент слияния сервером не гарантируется (может занять минуты или часы).
3. До момента слияния запрос `SELECT * FROM table` без дополнительных модификаторов возвратит **все дубликаты**!
4. Для получения актуальных данных используются:
   - Модификатор `FINAL` (`SELECT * FROM table FINAL`) — точно, но замедляет чтение больших таблиц.
   - Агрегации с `argMax(col, ver)` и `GROUP BY primary_key` — стандарт для высоконагруженных витрин.

## Решение по шагам

1. Создайте таблицу профилей пользователей на движке `ReplacingMergeTree(version)`.
2. Вставьте пользователя с версией 1, затем с версией 2.
3. Продемонстрируйте возврат обоих дубликатов обычным запросом `SELECT`.
4. Продемонстрируйте корректный возврат свежей версии через `SELECT ... FINAL` и через `argMax()`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS user_profiles (
			user_id UInt64,
			email String,
			version UInt64,
			updated_at DateTime
		) ENGINE = ReplacingMergeTree(version)
		ORDER BY user_id;
	`)

	// Вставка двух версий профиля пользователя
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO user_profiles")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	_ = batch.Append(uint64(7001), "old_email@example.com", uint64(1), now.Add(-time.Hour))
	_ = batch.Append(uint64(7001), "new_email@example.com", uint64(2), now)
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// 1. Обычный запрос без FINAL (видит дубликаты до слияния)
	var count uint64
	_ = conn.QueryRow(ctx, "SELECT count() FROM user_profiles WHERE user_id = 7001").Scan(&count)
	fmt.Printf("Строк до слияния без FINAL: %d\n", count)

	// 2. Запрос с модификатором FINAL
	var emailFinal string
	var verFinal uint64
	queryFinal := `SELECT email, version FROM user_profiles FINAL WHERE user_id = 7001`
	_ = conn.QueryRow(ctx, queryFinal).Scan(&emailFinal, &verFinal)
	fmt.Printf("Результат с FINAL: Email=%s, Version=%d\n", emailFinal, verFinal)

	// 3. Высокопроизводительный вариант через argMax без оверхеда FINAL
	var emailArgMax string
	queryArgMax := `
		SELECT argMax(email, version) 
		FROM user_profiles 
		WHERE user_id = 7001 
		GROUP BY user_id
	`
	_ = conn.QueryRow(ctx, queryArgMax).Scan(&emailArgMax)
	fmt.Printf("Результат через argMax: Email=%s (рекомендуется для HighLoad)\n", emailArgMax)
}
```

ℹ️ Сравнение чтения из ReplacingMergeTree: обычный SELECT, FINAL и argMax

**`Терминал`**

```bash
go run main.go
# Строк до слияния без FINAL: 2
# Результат с FINAL: Email=new_email@example.com, Version=2
# Результат через argMax: Email=new_email@example.com (рекомендуется для HighLoad)
```

## Под капотом

При выполнении `SELECT ... FINAL` ClickHouse строит на лету очередь с приоритетом (K-way Priority Queue / Min-Heap) из итераторов по всем активным партам, сравнивая ключи сортировки и версии. Для терабайтных таблиц это потребляет процессорное время и отключает параллельное блочное чтение.

## Подводные камни

Использование `OPTIMIZE TABLE table FINAL` для принудительного слияния — тяжелая блокирующая операция, перезаписывающая терабайты данных на диске. Категорически запрещено вызывать `OPTIMIZE FINAL` из веб-обработчиков Go!

## На собеседовании

**Вопрос:** Что делает колонка `is_deleted` в ReplacingMergeTree?
**Ответ:** Начиная с версии ClickHouse 23.2, `ReplacingMergeTree(ver, is_deleted)` поддерживает "мягкое" физическое удаление (Soft Delete). Если строка имеет флаг `is_deleted = 1`, во время фонового слияния или при запросе с `FINAL` она полностью отбрасывается и исчезает из таблицы.
