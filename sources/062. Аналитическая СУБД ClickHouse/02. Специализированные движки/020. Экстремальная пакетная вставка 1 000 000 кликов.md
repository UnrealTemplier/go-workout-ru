# Экстремальная пакетная вставка 1 000 000 кликов с оптимизацией пула

## Условие

**Пакетная вставка через нативный протокол.**: Реализуйте запись 1 миллиона строк аналитических событий (клики) с помощью `Append` в батч драйвера. Оптимизируйте: настройте размер батча, параллельные вставки.

## Теория

При записи потоков событий кликстрима (Clickstream, 1+ млн событий) решающее значение имеют:
1. **Размер батча:** Оптимальный размер батча для вставки в MergeTree — от 100 000 до 250 000 строк. Слишком маленький батч перегружает ClickHouse партами, слишком большой — исчерпывает RAM в Go.
2. **Пул горутин (Parallel Batches):** ClickHouse прекрасно масштабирует параллельные вставки в разные парты, но количество параллельных потоков не должно превышать число физических дисков или ядер сервера.
3. **Сжатие LZ4:** Сетевая карта не должна становиться узким горлышком.

## Решение по шагам

1. Создайте таблицу `clicks` с полями `(click_id UUID, user_id UInt64, banner_id UInt32, click_time DateTime)`.
2. Реализуйте многопоточную генерацию и отправку 1 000 000 записей через воркер-пул из 4 горутин.
3. Настройте размер пачки воркера в 250 000 строк.
4. Замерьте общую пропускную способность (RPS) и убедитесь в отсутствии блокировок.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
		Compression: &clickhouse.Compression{
			Method: clickhouse.CompressionLZ4,
		},
		MaxOpenConns: 10,
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS clicks (
			click_id UUID,
			user_id UInt64,
			banner_id UInt32,
			click_time DateTime
		) ENGINE = MergeTree()
		ORDER BY (banner_id, click_time);
	`)

	totalRows := 1_000_000
	workers := 4
	rowsPerWorker := totalRows / workers

	var insertedCount uint64
	var wg sync.WaitGroup

	start := time.Now()
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			batch, err := conn.PrepareBatch(ctx, "INSERT INTO clicks")
			if err != nil {
				panic(err)
			}
			now := time.Now()
			for i := 0; i < rowsPerWorker; i++ {
				_ = batch.Append(
					uuid.New(),
					uint64(10000+i),
					uint32(100+(workerID*10)+i%5),
					now,
				)
			}
			if err := batch.Send(); err != nil {
				panic(fmt.Sprintf("Worker %d send error: %v", workerID, err))
			}
			atomic.AddUint64(&insertedCount, uint64(rowsPerWorker))
			fmt.Printf("Воркер %d успешно вставил %d записей\n", workerID, rowsPerWorker)
		}(w)
	}

	wg.Wait()
	elapsed := time.Since(start)
	fmt.Printf("Всего успешно вставлено %d кликов за %v (%.0f строк/сек)\n",
		insertedCount, elapsed, float64(totalRows)/elapsed.Seconds())
}
```

ℹ️ Параллельная вставка миллиона кликов через воркер-пул с компрессией LZ4

**`Терминал`**

```bash
go run main.go
# Воркер 0 успешно вставил 250000 записей
# Воркер 1 успешно вставил 250000 записей
# Воркер 2 успешно вставил 250000 записей
# Воркер 3 успешно вставил 250000 записей
# Всего успешно вставлено 1000000 кликов за 1.12s (892857 строк/сек)
```

## Под капотом

Каждый воркер открывает независимое TCP-соединение из пула соединений. На стороне сервера ClickHouse 4 параллельных батча формируют 4 независимых парта в памяти и сбрасывают их на диск параллельными потоками ввода-вывода. Фоновый планировщик слияний впоследствии объединит их в один крупный парт.

## Подводные камни

Запуск сотен параллельных горутин с батчами по 100 строк приведет к ошибке `Too many parts`. Оптимальная формула параллелизма: число воркеров от 4 до 8 с крупными батчами от 100 000 строк.

## На собеседовании

**Вопрос:** Как избежать скачков нагрузки на ClickHouse, если несколько сервисов одновременно отправляют батчи по 1 000 000 строк?
**Ответ:** Использовать джиттер (Jitter) в интервалах сброса буферов на клиентах, а также ограничить максимальную скорость вставки на стороне ClickHouse с помощью квот и настроек `max_insert_block_size` и `max_execution_time`.
