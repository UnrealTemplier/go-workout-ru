# Конфигурация параметров Async Inserts в DSN и контексте

## Условие

**Асинхронные инсерты (Go -> CH)**: Начиная с версии CH 21.11, БД умеет батчить данные сама! Включи настройку `async_insert=1` в DSN подключения. Теперь ты можешь спокойно делать `conn.Exec` по одной строке, а ClickHouse сам накопит их в памяти (на сервере) и сбросит на диск большим куском. Проверь эту магию.

## Теория

Асинхронные вставки (Async Inserts) можно настраивать глобально на уровне пользователя, в строке подключения DSN или динамически для каждого отдельного запроса через `clickhouse.WithSettings`:

### Параметры тонкой настройки буфера:
- `async_insert = 1`: Включение серверной очереди буферизации.
- `wait_for_async_insert = 1`: Клиент блокируется до физического сброса на диск.
- `async_insert_busy_timeout_ms = 500`: Максимальное время удержания в памяти (мс) перед сбросом.
- `async_insert_max_data_size = 1048576`: Максимальный размер буфера в байтах (1 МБ).

## Решение по шагам

1. Сконфигурируйте DSN с параметрами `async_insert=1&wait_for_async_insert=1&async_insert_busy_timeout_ms=300`.
2. Подключитесь к ClickHouse.
3. Отправьте одиночные строки через `conn.Exec(...)`.
4. Убедитесь, что ClickHouse буферизует строки на сервере без создания отдельных партов на каждый вызов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()

	// Конфигурация параметров буферизации прямо в строке подключения DSN
	dsn := "clickhouse://default:@127.0.0.1:9000/default?" +
		"async_insert=1&" +
		"wait_for_async_insert=1&" +
		"async_insert_busy_timeout_ms=250&" +
		"async_insert_max_data_size=2097152"

	opts, err := clickhouse.ParseDSN(dsn)
	if err != nil {
		panic(err)
	}

	conn, err := clickhouse.Open(opts)
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	fmt.Println("Отправка одиночных событий с автоматической серверной буферизацией...")
	start := time.Now()

	for i := 0; i < 5; i++ {
		query := `INSERT INTO events (id, user_id, event_time, payload) VALUES (?, ?, ?, ?)`
		err := conn.Exec(ctx, query,
			uuid.New(),
			uint64(8000+i),
			time.Now(),
			fmt.Sprintf("async_event_%d", i),
		)
		if err != nil {
			panic(err)
		}
	}

	fmt.Printf("Все события отправлены за %v\n", time.Since(start))
}
```

ℹ️ Управление серверными параметрами Async Inserts через параметры DSN

**`Терминал`**

```bash
go run main.go
# Отправка одиночных событий с автоматической серверной буферизацией...
# Все события отправлены за 265ms
```

## Под капотом

Сервер ClickHouse группирует входящие вставки по хэшу целевой таблицы и структуры SQL запроса. Данные нескольких конкурентных сессий сливаются в единый блок, после чего отправляются в стандартный пайплайн вставки `InterpreterInsertQuery` как один целостный блок.

## Подводные камни

Если передавать параметры запроса не через плейсхолдеры (`?`), а конкатенацией строк (`INSERT INTO events VALUES ('uuid', 123)`), ClickHouse посчитает каждый запрос уникальным шаблоном, что отключит эффективное слияние разных вставок в один блок.

## На собеседовании

**Вопрос:** В каких случаях `async_insert=1` может ухудшить общую производительность ClickHouse?
**Ответ:** Если входящие запросы имеют разный набор колонок или генерируются сотнями тысяч клиентов с огромным количеством уникальных таблиц, память очередей `AsyncInsertQueue` и переключение контекста между тысячами очередей могут перегрузить процессор ClickHouse.
