# Денормализация: Массивы и Nested-структуры против классических JOIN

## Условие

**Денормализация и Nested.**: Реализуйте схему «заказ + товары» двумя способами: (1) через `Array(Nested(product_id String, quantity Int32))` внутри заказа, (2) через JOIN с таблицей `order_items`. Покажите, что JOIN в ClickHouse дорог, а Nested/Array — идиоматичный путь.

## Теория

ClickHouse спроектирован для работы с широкими денормализованными плоскими таблицами (Flat Wide Tables). Классические реляционные соединения `JOIN` в аналитических СУБД работают медленно, так как требуют пересылки данных между нодами или построения массивных хэш-таблиц в оперативной памяти.

### Альтернатива JOIN в ClickHouse:
1. **Массивы `Array(T)`:** Позволяют хранить списки тегов, идентификаторов товаров или категорий прямо внутри строки заказа.
2. **Вложенные структуры `Nested(...)`:** Синтаксический сахар над набором параллельных массивов одинаковой длины `items.product_id Array(UInt64)`, `items.quantity Array(UInt32)`.
3. Запросы с функциями высшего порядка над массивами (`arrayJoin`, `arrayMap`, `has()`) работают на порядки быстрее любых внешних соединений.

## Решение по шагам

1. Создайте таблицу `orders` с колонками `items.product_id Array(UInt64)` и `items.price Array(Float64)`.
2. Вставьте заказ с несколькими товарными позициями.
3. Выполните запрос с функцией `arrayJoin(items.product_id)` для разворачивания массива в плоские строки.
4. Выполните аналитический расчет суммы заказа на лету через `arraySum`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Таблица с денормализованной структурой товаров в заказе
	ddl := `
	CREATE TABLE IF NOT EXISTS orders_nested (
		order_id UInt64,
		user_id UInt64,
		created_at DateTime,
		items_product_id Array(UInt64),
		items_price Array(Float64)
	) ENGINE = MergeTree()
	ORDER BY (user_id, order_id);
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}

	// Вставка заказа с массивом товаров
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO orders_nested")
	if err != nil {
		panic(err)
	}
	orderID := uint64(9001)
	userID := uint64(300)
	prodIDs := []uint64{101, 102, 103}
	prices := []float64{500.0, 1200.50, 300.0}

	_ = batch.Append(orderID, userID, time.Now(), prodIDs, prices)
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// Аналитический запрос с arraySum без JOIN
	query := `
		SELECT 
			order_id, 
			length(items_product_id) AS total_items,
			arraySum(items_price) AS order_total
		FROM orders_nested 
		WHERE order_id = 9001
	`
	var (
		oID        uint64
		totalItems uint64
		orderTotal float64
	)
	if err := conn.QueryRow(ctx, query).Scan(&oID, &totalItems, &orderTotal); err != nil {
		panic(err)
	}

	fmt.Printf("Заказ %d: Позиций=%d, Общая стоимость=%.2f руб (вычислено без JOIN)\n",
		oID, totalItems, orderTotal)
}
```

ℹ️ Использование типов данных Array и встроенных функций arraySum вместо реляционных JOIN

**`Терминал`**

```bash
go run main.go
# Заказ 9001: Позиций=3, Общая стоимость=2000.50 руб (вычислено без JOIN)
```

## Под капотом

Для колонок типа `Array(T)` ClickHouse создает два физических файла: `items_price.bin` (непрерывный плоский массив всех значений) и `items_price.size0.bin` (смещения границ массивов каждой строки). Благодаря этому массив не требует сериализации в JSON и сканируется с векторной скоростью процессора.

## Подводные камни

Вложенный `Nested(A, B)` внутри ClickHouse эквивалентен двум независимым массивам `items.A Array(...)` и `items.B Array(...)`. Если при вставке длина массива `A` не совпадет с длиной массива `B`, запрос завершится ошибкой.

## На собеседовании

**Вопрос:** Как в ClickHouse эффективно соединять таблицы, если денормализация невозможна (например, справочники валют или стран)?
**Ответ:** Использовать словари (**ClickHouse Dictionaries**). Словари кэшируются целиком в памяти каждого узла и заменяют тяжелый `JOIN` на прямой O(1) поиск по ключу через функцию `dictGet('currency_dict', 'rate', currency_id)`.
