# Продвинутый тюнинг серверных очередей Async Inserts

## Условие

**Асинхронные вставки (Async Inserts)**: Начиная с версии 21.11, ClickHouse умеет буферизовать вставки на своей стороне. Настройте параметры подключения в вашем Go-драйвере, передав опции `async_insert=1` и `wait_for_async_insert=0`. Напишите бенчмарк сравнения скорости обычной поштучной вставки и асинхронной вставки.

## Теория

Серверные асинхронные вставки (Async Inserts) управляются множеством параметров, которые можно передавать через Go context:

1. `async_insert_use_adaptive_busy_timeout`: Автоматическая адаптация времени ожидания буфера под текущую интенсивность нагрузки.
2. `async_insert_threads`: Размер пула серверных потоков, ответственных за сброс очередей асинхронных вставок.
3. `wait_for_async_insert_timeout`: Максимальное время ожидания ответа клиентом (если сброс затянулся, возвращается таймаут).

## Решение по шагам

1. Создайте вызов с кастомным контекстом `clickhouse.WithSettings`.
2. Установите `async_insert = 1`, `wait_for_async_insert = 1`.
3. Установите лимит `async_insert_busy_timeout_ms = 100`.
4. Выполните серию параллельных вставок из нескольких горутин.
5. Замерьте задержку ответа.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	ctx := context.Background()

	// Динамическая настройка параметров вставки в контексте конкретного запроса
	asyncCtx := clickhouse.Context(ctx, clickhouse.WithSettings(clickhouse.Settings{
		"async_insert":                 1,
		"wait_for_async_insert":        1,
		"async_insert_busy_timeout_ms": 150,
		"wait_for_async_insert_timeout": 5,
	}))

	var wg sync.WaitGroup
	workers := 5

	start := time.Now()
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			query := `INSERT INTO events (id, user_id, event_time, payload) VALUES (?, ?, ?, ?)`
			err := conn.Exec(asyncCtx, query,
				uuid.New(),
				uint64(9000+workerID),
				time.Now(),
				fmt.Sprintf("worker_%d_telemetry", workerID),
			)
			if err != nil {
				panic(err)
			}
		}(w)
	}

	wg.Wait()
	fmt.Printf("5 параллельных асинхронных вставок сброшены сервером за %v\n", time.Since(start))
}
```

ℹ️ Тонкая настройка контекстных параметров async_insert и таймаутов очереди

**`Терминал`**

```bash
go run main.go
# 5 параллельных асинхронных вставок сброшены сервером за 162ms
```

## Под капотом

Когда 5 горутин одновременно отправляют `INSERT` с `wait_for_async_insert = 1`, сервер объединяет их строки в один блок в `AsyncInsertQueue`. По истечении 150 мс (`busy_timeout_ms`) фоновый поток сбрасывает блок на диск, после чего одновременно разблокирует и возвращает успех всем 5 ожидающим сетевым соединениям.

## Подводные камни

Если установить `async_insert_busy_timeout_ms` слишком маленьким (например 5 мс), сервер будет сбрасывать полупустые блоки, что сведет на нет преимущества батчинга и увеличит количество партов на диске.

## На собеседовании

**Вопрос:** Как отслеживать состояние очередей асинхронных вставок на сервере ClickHouse?
**Ответ:** Запросом к системной таблице `system.asynchronous_inserts`, которая показывает размер текущих очередей в памяти, количество ожидающих запросов и метрику `flushed_batches`.
