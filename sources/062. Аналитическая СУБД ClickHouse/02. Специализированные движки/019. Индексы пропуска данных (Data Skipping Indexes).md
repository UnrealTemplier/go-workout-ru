# Индексы пропуска данных (Data Skipping Indexes): MinMax и Bloom Filter

## Условие

**Индексы и pruning.**: Создайте таблицу с `minmax` индексом на `event_time` и `bloom_filter` на `user_id`. Выполните запрос с `WHERE user_id = 'x'` и покажите в `EXPLAIN indexes = 1`, что bloom filter отсекает гранулы. Объясните разницу между primary key (sparse index) и secondary data skipping indexes.

## Теория

Поскольку в ClickHouse первичный ключ `ORDER BY` может быть только один, фильтрация по другим колонкам (например, поиск по `user_id`, когда таблица отсортирована по `event_time`) привела бы к полному сканированию всех гранул.

Для ускорения таких запросов используются **Data Skipping Indexes (Индексы пропуска данных)**:
1. **minmax:** Сохраняет минимальное и максимальное значение колонки для каждого блока гранул (`GRANULARITY N`). Если искомое значение не попадает в диапазон `[min, max]`, вся пачка гранул пропускается.
2. **bloom_filter([false_positive]):** Строит вероятностную битовую карту Блума для значений колонки. Позволяет мгновенно отклонить гранулы, в которых элемента гарантированно нет.
3. **tokenbf_v1:** Фильтр Блума по токенам (подходит для поиска подстрок и логов `LIKE '%error%'`).

## Решение по шагам

1. Создайте таблицу `logs` с `ORDER BY timestamp`.
2. Добавьте индекс пропуска данных `INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 4`.
3. Добавьте индекс `INDEX idx_url url TYPE minmax GRANULARITY 4`.
4. Выполните запрос с фильтром по `user_id` и исследуйте план выполнения `EXPLAIN indexes = 1`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Таблица с вторичными индексами пропуска данных (Data Skipping Indexes)
	ddl := `
	CREATE TABLE IF NOT EXISTS audit_logs (
		timestamp DateTime,
		user_id UInt64,
		action LowCardinality(String),
		url String,
		INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 4,
		INDEX idx_url url TYPE minmax GRANULARITY 2
	) ENGINE = MergeTree()
	ORDER BY timestamp;
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}
	fmt.Println("Таблица audit_logs успешно создана с индексами Bloom Filter и MinMax")

	// Инспекция работы индекса Блума в плане запроса
	explainQuery := `
		EXPLAIN indexes = 1
		SELECT count() 
		FROM audit_logs 
		WHERE user_id = 9999999
	`
	rows, err := conn.Query(ctx, explainQuery)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("План запроса с фильтром Блума:")
	for rows.Next() {
		var line string
		if err := rows.Scan(&line); err != nil {
			panic(err)
		}
		fmt.Println(" ", line)
	}
}
```

## Под капотом

Параметр `GRANULARITY K` в Data Skipping индексе задает количество гранул первичного индекса, объединяемых в один блок вторичного индекса. Например, при `index_granularity = 8192` и `GRANULARITY = 4` один фильтр Блума строится на \(8192 \times 4 = 32768\) строк. Если хеш `user_id` отсутствует в фильтре, ClickHouse пропускает чтение сразу 32 768 строк.

## Подводные камни

Индексы пропуска данных увеличивают размер парта на диске и замедляют вставку (`INSERT`), так как ClickHouse должен вычислять хэши и строить фильтры на лету. Не создавайте индексы Блума на колонки с монотонно растущими данными или слишком низкой селективностью.

## На собеседовании

**Вопрос:** Может ли фильтр Блума в ClickHouse отсечь гранулу, содержащую искомый ключ (False Negative)?
**Ответ:** Нет, фильтр Блума математически гарантирует отсутствие ложноотрицательных срабатываний (No False Negatives). Если ключ присутствует в грануле, фильтр Блума всегда вернет `true`. Возможны лишь ложноположительные срабатывания (False Positives), контролируемые параметром вероятности ошибки (например, `0.01` для 1% погрешности).
