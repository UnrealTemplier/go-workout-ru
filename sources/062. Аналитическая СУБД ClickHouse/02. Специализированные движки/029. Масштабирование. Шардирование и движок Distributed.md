# Масштабирование: Шардирование и движок Distributed

## Условие

**Distributed Engine.**: Создайте локальные таблицы `events_local` на 2 шардах. Создайте `events_dist` (`ENGINE = Distributed`). Вставляйте в `events_dist`, читайте из неё. Объясните, как sharding key (`rand()` или `user_id`) определяет шард, и почему `Distributed` отправляет запрос на все шарды при `SELECT *`.

## Теория

Для горизонтального масштабирования таблиц на десятки серверов ClickHouse использует движок `Distributed`:

### Архитектура Distributed Engine:
1. Таблица `Distributed` сама по себе не хранит данных на диске! Она представляет собой **умный прокси-фасад (Routing View)**.
2. На каждом узле создается локальная таблица `events_local` (движок `MergeTree` или `ReplicatedMergeTree`).
3. Поверх создается распределенная таблица:
   `CREATE TABLE events_dist AS events_local ENGINE = Distributed(cluster_name, current_db, events_local, sharding_key)`
4. **Ключ шардирования (Sharding Key):** Например, `cityHash64(user_id)`. Определяет, на какой шард попадет запись.
5. При `SELECT` из `events_dist` узел-координатор рассылает подзапросы на все шарды кластера параллельно (Scatter-Gather), собирает частичные результаты и возвращает клиенту готовый ответ.

## Решение по шагам

1. Создайте локальную таблицу `events_local` (MergeTree).
2. Создайте распределенную таблицу `events_dist` с `ENGINE = Distributed(default, default, events_local, rand())`.
3. Выполните вставку через распределенную таблицу или напрямую в локальные таблицы.
4. Выполните агрегационный запрос `SELECT count()` из `events_dist`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// 1. Создание локальной таблицы для хранения данных
	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS events_local (
			id UUID,
			user_id UInt64,
			event_time DateTime,
			payload String
		) ENGINE = MergeTree()
		ORDER BY (user_id, event_time);
	`)

	// 2. Создание распределенной таблицы Distributed поверх локальной
	// В тестовом окружении используем кластер 'default'
	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS events_dist AS events_local
		ENGINE = Distributed(default, default, events_local, cityHash64(user_id));
	`)

	// 3. Вставка данных в Distributed таблицу
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO events_dist")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	for i := 0; i < 5; i++ {
		_ = batch.Append(uuid.New(), uint64(5000+i), now, "sharded_payload")
	}
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// 4. Запрос через распределенный фасад
	var totalEvents uint64
	if err := conn.QueryRow(ctx, "SELECT count() FROM events_dist").Scan(&totalEvents); err != nil {
		panic(err)
	}
	fmt.Printf("Всего событий в распределенной таблице events_dist: %d\n", totalEvents)
}
```

ℹ️ Создание и запрос к распределенной таблице с движком Distributed

**`Терминал`**

```bash
go run main.go
# Всего событий в распределенной таблице events_dist: 5
```

## Под капотом

При вставке в `Distributed` таблицу узел ClickHouse сохраняет блок данных в локальную директорию буфера `/var/lib/clickhouse/data/.../table@shard/` и отдельным фоновым потоком отправляет данные на удаленные шарды. В BigTech вставка через Distributed считается неоптимальной — приложение Go само рассчитывает `shard = cityHash64(user_id) % numShards` и пишет напрямую в `events_local` целевого шарда.

## Подводные камни

Вставка больших батчей в `Distributed` таблицу создает двойную нагрузку на сеть и диск: сначала данные пишутся на узел-координатор, а затем пересылаются на целевой шард. Для максимального RPS пишите напрямую в `*_local` таблицы!

## На собеседовании

**Вопрос:** Что такое Global IN и Global JOIN в распределенных запросах ClickHouse?
**Ответ:** При обычном `IN (SELECT id FROM ...)` на каждый шард отправляется исходный подзапрос, что приводит к многократному дублированию вычислений. Секция `GLOBAL IN` заставляет координатор выполнить подзапрос один раз, собрать результат в оперативную память и разослать готовое множество идентификаторов всем шардам кластера.
