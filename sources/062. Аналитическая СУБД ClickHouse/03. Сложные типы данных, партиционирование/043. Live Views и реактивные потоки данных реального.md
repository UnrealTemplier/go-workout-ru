# Live Views и реактивные потоки данных реального времени

## Условие

**Live views**: Используйте Live Views для real-time dashboards (экспериментальная фича).

## Теория

Для построения интерактивных дашбордов реального времени (Monitoring dashboards, Live Charts) ClickHouse поддерживает механизм **Live Views**:
1. `CREATE LIVE VIEW lv AS SELECT ...`
2. Клиент открывает запрос с модификатором `WATCH lv`.
3. Соединение удерживается открытым.
4. При каждой новой вставке в базовую таблицу ClickHouse вычисляет дельту и мгновенно отправляет обновленный результат подписчику в виде потока событий!
5. Позволяет организовать Server-Sent Events (SSE) или WebSocket стриминг клиентам без периодического polling базы раз в секунду.

## Решение по шагам

1. Включите настройку `allow_experimental_live_view = 1`.
2. Создайте таблицу `sensor_readings` и `LIVE VIEW sensor_lv AS SELECT device_id, max(temperature) FROM sensor_readings GROUP BY device_id`.
3. Подключитесь и выполните команду подписки `WATCH sensor_lv`.
4. Реализуйте чтение реактивных событий в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
		Settings: clickhouse.Settings{
			"allow_experimental_live_view": 1,
		},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS sensor_data (
			device_id UInt32,
			temperature Float32,
			created_at DateTime
		) ENGINE = MergeTree()
		ORDER BY created_at;
	`)

	// Создание Live View для мониторинга в реальном времени
	_ = conn.Exec(ctx, `
		CREATE LIVE VIEW IF NOT EXISTS sensor_live_view AS
		SELECT device_id, max(temperature) AS max_temp
		FROM sensor_data
		GROUP BY device_id;
	`)

	// Вставка данных
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO sensor_data")
	if err != nil {
		panic(err)
	}
	_ = batch.Append(uint32(42), float32(78.5), time.Now())
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// Считывание снимка Live View
	var (
		devID   uint32
		maxTemp float32
	)
	query := `SELECT device_id, max_temp FROM sensor_live_view WHERE device_id = 42`
	if err := conn.QueryRow(ctx, query).Scan(&devID, &maxTemp); err != nil {
		fmt.Printf("Live View снимок: %v\n", err)
		return
	}

	fmt.Printf("Реактивный снимок Live View: Device=%d, MaxTemp=%.1f°C\n", devID, maxTemp)
}
```

ℹ️ Использование Live Views для real-time реактивных витрин данных

**`Терминал`**

```bash
go run main.go
# Реактивный снимок Live View: Device=42, MaxTemp=78.5°C
```

## Под капотом

При выполнении `WATCH` ClickHouse регистрирует подписку в оперативной памяти. При каждой вставке новых блоков данных парсер отслеживает затронутые ключи группировки и пушит новые строки прямо в сетевой сокет клиента через управляющий протокол `ProtocolServerData`.

## Подводные камни

Live Views в современных версиях ClickHouse считаются устаревающими (deprecated) в пользу более мощного и масштабируемого механизма **Window Views** (оконные стриминговые представления) или связки ClickHouse + Kafka/NATS.

## На собеседовании

**Вопрос:** Почему в HighLoad продакшене избегают держать тысячи постоянных подписок `WATCH` на ClickHouse?
**Ответ:** Тысячи открытых сетевых сокетов и непрерывный перерасчет запросов при каждой вставке создают колоссальную нагрузку на планировщик памяти ClickHouse. Вместо этого в архитектуре используют стриминговые брокеры (Kafka/Redis Pub/Sub) или WebSockets шлюзы с кэшированием.
