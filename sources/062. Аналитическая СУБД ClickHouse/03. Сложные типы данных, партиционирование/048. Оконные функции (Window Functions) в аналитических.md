# Оконные функции (Window Functions) в аналитических запросах

## Условие

**Window functions**: Используйте `rowNumberInAllBlocks()`, `anyLast`, window functions (ClickHouse 22+).

## Теория

Начиная с версии 21.3, ClickHouse поддерживает стандартные ANSI SQL оконные функции (Window Functions):
`FUNCTION(...) OVER (PARTITION BY ... ORDER BY ... [ROWS/RANGE ...])`

### Популярные оконные функции в ClickHouse:
1. `row_number()`: Порядковый номер строки внутри партиции.
2. `rank()`, `dense_rank()`: Ранжирование с учетом одинаковых значений.
3. `lagInFrame(col, offset)`, `leadInFrame(col, offset)`: Доступ к предыдущей или следующей строке (расчет конверсий и пауз между действиями пользователя).
4. `sum(amount) OVER (PARTITION BY user_id ORDER BY event_time ROWS UNBOUNDED PRECEDING)`: Расчет нарастающего итога (Running Total) с векторной оптимизацией.

## Решение по шагам

1. Создайте таблицу платежей `user_payments`.
2. Вставьте серии платежей для нескольких пользователей.
3. Составьте запрос с оконной функцией расчета нарастающего итога и вычисления времени с предыдущего платежа через `lagInFrame`.
4. Выполните запрос из Go и распарсите результаты.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS user_payments (
			user_id UInt64,
			payment_time DateTime,
			amount Float64
		) ENGINE = MergeTree()
		ORDER BY (user_id, payment_time);
	`)

	batch, err := conn.PrepareBatch(ctx, "INSERT INTO user_payments")
	if err != nil {
		panic(err)
	}
	t0, _ := time.Parse("2006-01-02 15:04:05", "2026-09-04 10:00:00")
	_ = batch.Append(uint64(501), t0, 100.0)
	_ = batch.Append(uint64(501), t0.Add(time.Hour), 250.0)
	_ = batch.Append(uint64(501), t0.Add(2*time.Hour), 50.0)
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// Запрос с оконными функциями: нарастающий итог и номер транзакции
	query := `
		SELECT 
			user_id,
			payment_time,
			amount,
			row_number() OVER (PARTITION BY user_id ORDER BY payment_time) AS tx_num,
			sum(amount) OVER (PARTITION BY user_id ORDER BY payment_time ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
		FROM user_payments
		WHERE user_id = 501
		ORDER BY payment_time
	`
	rows, err := conn.Query(ctx, query)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("История платежей с оконным нарастающим итогом:")
	for rows.Next() {
		var (
			uid          uint64
			pTime        time.Time
			amount       float64
			txNum        uint64
			runningTotal float64
		)
		if err := rows.Scan(&uid, &pTime, &amount, &txNum, &runningTotal); err != nil {
			panic(err)
		}
		fmt.Printf("  Транзакция #%d: Время=%s | Сумма=%.2f | Баланс накопленный=%.2f руб\n",
			txNum, pTime.Format("15:04"), amount, runningTotal)
	}
}
```

ℹ️ Использование оконных функций row_number и sum OVER в аналитических запросах


## Под капотом

Оконные функции в ClickHouse используют специализированные структуры `WindowTransform`. Если данные уже физически отсортированы на диске по ключу окна `(user_id, payment_time)`, ClickHouse выполняет расчет в один потоковый проход без предварительной фазы сортировки в оперативной памяти.

## Подводные камни

Если сортировка в оконной секции `ORDER BY` не совпадает с первичным ключом таблицы, ClickHouse вынужден загружать все данные окна в оперативную память для сортировки, что может вызвать `DB::Exception: Memory limit exceeded`.

## На собеседовании

**Вопрос:** Чем `lagInFrame` отличается от классического `lag` в ClickHouse?
**Ответ:** `lag` принимает всю партицию целиком, тогда как `lagInFrame` строго уважает границы текущего фрейма окна (`ROWS BETWEEN ...`), возвращая значение по умолчанию, если смещение выходит за пределы видимого фрейма.
