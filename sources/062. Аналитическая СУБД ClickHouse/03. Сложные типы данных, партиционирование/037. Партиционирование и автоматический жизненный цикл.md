# Партиционирование и автоматический жизненный цикл данных (TTL)

## Условие

**Partitioning**: Партицируйте по времени (`toYYYYMM(timestamp)`) для эффективного TTL и pruning.

## Теория

В аналитических хранилищах данные старше определенного возраста (например, 30 или 90 дней) требуется либо автоматически удалять, либо переносить на дешевые медленные диски (HDD или S3 Cold Storage).

### Механизмы TTL в ClickHouse:
1. **TTL на уровне таблицы (Table TTL):**
   `TTL event_time + INTERVAL 30 DAY DELETE`
   Автоматически удаляет устаревшие строки во время фонового слияния партов.
2. **Tiered Storage (Многоуровневое хранение):**
   `TTL event_time + INTERVAL 7 DAY TO VOLUME 'cold'`
   Перемещает данные с быстрых NVMe SSD на емкие HDD или в S3 Object Storage через 7 дней.
3. Партиционирование по месяцам `PARTITION BY toYYYYMM(event_time)` позволяет удалить весь устаревший месяц целиком одной командой `DROP PARTITION`.

## Решение по шагам

1. Создайте таблицу `metrics_with_ttl` с `TTL metric_time + INTERVAL 30 DAY DELETE`.
2. Настройте партиционирование `PARTITION BY toYYYYMM(metric_time)`.
3. Вставьте тестовые метрики с текущей датой и устаревшей датой.
4. Выполните запрос слияния `OPTIMIZE TABLE ... FINAL` для демонстрации удаления по TTL.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Создание таблицы с правилом автоматического удаления данных старше 30 дней
	ddl := `
	CREATE TABLE IF NOT EXISTS metrics_ttl (
		device_id UInt64,
		metric_time DateTime,
		temperature Float32
	) ENGINE = MergeTree()
	PARTITION BY toYYYYMM(metric_time)
	ORDER BY (device_id, metric_time)
	TTL metric_time + INTERVAL 30 DAY DELETE;
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}
	fmt.Println("Таблица metrics_ttl успешно настроена с правилом автоматического TTL")

	// Вставка свежей и устаревшей записи
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO metrics_ttl")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	oldTime := now.Add(-35 * 24 * time.Hour) // 35 дней назад (подлежит удалению)

	_ = batch.Append(uint64(101), now, float32(23.5))
	_ = batch.Append(uint64(102), oldTime, float32(99.9))
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// Принудительное выполнение фонового слияния для демонстрации работы TTL
	_ = conn.Exec(ctx, "OPTIMIZE TABLE metrics_ttl FINAL")

	var count uint64
	_ = conn.QueryRow(ctx, "SELECT count() FROM metrics_ttl").Scan(&count)
	fmt.Printf("Активных записей после применения TTL: %d (устаревшая удалена)\n", count)
}
```

ℹ️ Настройка TTL для автоматического удаления устаревших аналитических данных

**`Терминал`**

```bash
go run main.go
# Таблица metrics_ttl успешно настроена с правилом автоматического TTL
# Активных записей после применения TTL: 1 (устаревшая удалена)
```

## Под капотом

Для каждой партиции ClickHouse вычисляет минимальную и максимальную дату TTL и сохраняет ее в метаданных парта. Если все строки парта старше TTL, ClickHouse удаляет парт целиком без чтения строк. Если в парте есть как свежие, так и устаревшие строки, удаление происходит только во время планового слияния (Merge).

## Подводные камни

TTL в ClickHouse не гарантирует мгновенного удаления секунда в секунду. Строка может оставаться на диске до тех пор, пока фоновый процесс слияния не затронет соответствующий парт. Если требуется гарантированное немедленное удаление, используйте `ALTER TABLE ... DROP PARTITION`.

## На собеседовании

**Вопрос:** Как работает колоночный TTL (Column TTL) в ClickHouse?
**Ответ:** Колоночный TTL (`col String TTL time + INTERVAL 7 DAY`) очищает только конкретный столбец (заменяет его на дефолтное значение), оставляя саму строку в таблице. Это позволяет хранить тяжелые пейлоады 7 дней, а легкие идентификаторы и счетчики хранить годами.
