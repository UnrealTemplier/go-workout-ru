# Оптимизация типов: LowCardinality против Nullable

## Условие

**Nullable и LowCardinality.**: Спроектируйте таблицу с колонками `LowCardinality(String)` для статусов и `Nullable(Int32)` для опционального кода ответа. Сравните потребление памяти с обычным `String`.

## Теория

Выбор типов данных в ClickHouse оказывает решающее влияние на объем диска и скорость сканирования:

1. **`LowCardinality(T)` (Словарь низкой кардинальности):**
   - Применяется для строковых или числовых колонок с ограниченным числом уникальных значений (< 10 000): статусы, страны, HTTP-методы, типы событий.
   - ClickHouse заменяет строки на компактный числовой словарь (1 байт `UInt8` для < 256 уникальных значений).
   - Снижает расход памяти и диска в 5–10 раз, а фильтрация и `GROUP BY` выполняются на скорости работы с простыми байтами.

2. **`Nullable(T)` (Опциональные значения):**
   - ClickHouse для каждой `Nullable` колонки создает **отдельный файл битовой маски `col.null.bin`**, где 1 байт хранит признак `NULL/NOT NULL`.
   - Замедляет векторные вычисления SIMD и ухудшает сжатие.
   - **Правило BigTech:** Избегайте `Nullable` везде, где это возможно. Вместо `Nullable(String)` используйте пустую строку `""`, а вместо `Nullable(UInt32)` — дефолтное значение `0`.

## Решение по шагам

1. Создайте таблицу `http_logs` с колонками `method LowCardinality(String)` и `status_code Nullable(Int32)`.
2. Вставьте тестовые строки, включая значения с `nil` кодом ответа.
3. Исследуйте размер парта и файлов на диске через `system.parts_columns`.
4. Сравните скорость группировки по обычной строке и по `LowCardinality(String)`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	ddl := `
	CREATE TABLE IF NOT EXISTS http_logs (
		event_time DateTime,
		method LowCardinality(String),
		status_code Nullable(Int32),
		url String
	) ENGINE = MergeTree()
	ORDER BY event_time;
	`
	if err := conn.Exec(ctx, ddl); err != nil {
		panic(err)
	}

	// Вставка данных с использованием указателя для Nullable
	batch, err := conn.PrepareBatch(ctx, "INSERT INTO http_logs")
	if err != nil {
		panic(err)
	}
	now := time.Now()
	var code200 int32 = 200
	var codeNil *int32 = nil // Истинный NULL в ClickHouse

	_ = batch.Append(now, "GET", &code200, "/api/v1/user")
	_ = batch.Append(now.Add(time.Second), "POST", codeNil, "/api/v1/checkout")
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// Чтение с обработкой Nullable в Go через указатель
	rows, err := conn.Query(ctx, "SELECT method, status_code, url FROM http_logs")
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	fmt.Println("Прочитанные логи HTTP:")
	for rows.Next() {
		var (
			method string
			status *int32
			url    string
		)
		if err := rows.Scan(&method, &status, &url); err != nil {
			panic(err)
		}
		if status == nil {
			fmt.Printf("  [%s] %s -> Status: NULL (соединение сброшено клиентом)\n", method, url)
		} else {
			fmt.Printf("  [%s] %s -> Status: %d\n", method, url, *status)
		}
	}
}
```

ℹ️ Использование LowCardinality для строк и обработка Nullable через указатели в Go

**`Терминал`**

```bash
go run main.go

#   [GET] /api/v1/user -> Status: 200
#   [POST] /api/v1/checkout -> Status: NULL (соединение сброшено клиентом)
```

## Под капотом

При использовании `LowCardinality` ClickHouse динамически строит локальный словарь для каждого парта. Если число уникальных строк не превышает 256, значения столбца хранятся как плоский массив 8-битных индексов `col.bin` плюс небольшой словарь `col.dict.null.bin`. Векторный движок СУБД агрегирует индексы напрямую без сравнения строк.

## Подводные камни

Использование `LowCardinality` на колонках с высокой кардинальностью (например, случайные URL, email или UUID с миллионами уникальных значений) приведет к разрастанию словарей и резкому замедлению вставки.

## На собеседовании

**Вопрос:** Почему колонка `Nullable` не может входить в состав первичного ключа `ORDER BY` в старых версиях ClickHouse?
**Ответ:** Для корректной сортировки в разреженном индексе значения должны быть строго сравнимы. Значения `NULL` требуют специальной обработки (NULLS FIRST / NULLS LAST), что усложняет бинарный поиск по марк-файлам. Начиная с версии 20.3 `Nullable` в `ORDER BY` поддерживается, но не рекомендуется из-за накладных расходов.
