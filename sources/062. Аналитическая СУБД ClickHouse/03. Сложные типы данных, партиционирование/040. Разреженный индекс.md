# Разреженный индекс: Внутреннее устройство primary.cidx и .mrk2

## Условие

**Primary key**: Изучите, как sparse primary key (каждые 8192 строк) ускоряет поиск.

## Теория

Понимание физического формата файлов партов ClickHouse — ключевой навык Senior Backend инженера:

Внутри директории парта (например `/var/lib/clickhouse/data/default/events/202609_1_1_0/`) находятся файлы:
1. `col.bin`: Сжатые потоки данных столбцов.
2. `primary.cidx`: **Разреженный первичный индекс**. Содержит только значения первичного ключа для каждой 8192-й строки таблицы.
3. `col.mrk2`: **Марк-файлы (Marks)**. Связывают индекс с диском. Каждая засечка (Mark) содержит два смещения:
   - Смещение сжатого блока в файле `col.bin`.
   - Смещение распакованной гранулы внутри блока.

Благодаря марк-файлам ClickHouse считывает с диска строго нужные гранулы, полностью минуя остальные мегабайты!

## Решение по шагам

1. Запросите метаданные индекса из `system.parts` и `system.columns`.
2. Получите размер первичного индекса в памяти (`primary_key_bytes_in_memory`).
3. Оцените коэффициент сжатия данных.
4. Продемонстрируйте вычисление количества гранул для заданного числа строк.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// Запрос метрик разреженного индекса из системной таблицы system.parts
	query := `
		SELECT 
			name,
			rows,
			marks,
			primary_key_bytes_in_memory,
			bytes_on_disk,
			data_uncompressed_bytes
		FROM system.parts 
		WHERE table = 'events' AND active = 1
		LIMIT 1
	`
	var (
		partName                  string
		rowsCount, marksCount     uint64
		indexBytes, bytesOnDisk   uint64
		uncompressedBytes         uint64
	)
	if err := conn.QueryRow(ctx, query).Scan(
		&partName, &rowsCount, &marksCount,
		&indexBytes, &bytesOnDisk, &uncompressedBytes,
	); err != nil {
		fmt.Printf("Парт еще не сформирован или пуст: %v\n", err)
		return
	}

	compressionRatio := float64(uncompressedBytes) / float64(bytesOnDisk)
	fmt.Printf("Анализ парта %s:\n", partName)
	fmt.Printf("  Всего строк:                %d\n", rowsCount)
	fmt.Printf("  Число засечек (гранул):     %d (по ~8192 строк на гранулу)\n", marksCount)
	fmt.Printf("  Размер индекса в RAM:       %d байт (микроскопический!)\n", indexBytes)
	fmt.Printf("  Размер на диске (сжатый):   %.2f КБ\n", float64(bytesOnDisk)/1024)
	fmt.Printf("  Коэффициент сжатия кодеком: %.2fx\n", compressionRatio)
}
```

ℹ️ Инспекция метрик разреженного первичного индекса и марк-файлов через system.parts

**`Терминал`**

```bash
go run main.go
# Анализ парта 202609_1_1_0:
#   Всего строк:                1000000
#   Число засечек (гранул):     123 (по ~8192 строк на гранулу)
#   Размер индекса в RAM:       1968 байт (микроскопический!)
#   Размер на диске (сжатый):   1820.45 КБ
#   Коэффициент сжатия кодеком: 4.85x
```

## Под капотом

Если бы ClickHouse использовал традиционный B-Tree индекс (как PostgreSQL), индекс для 1 млрд строк с указателями на каждую строку занимал бы 30–50 ГБ оперативной памяти. Разреженный индекс для того же миллиарда строк содержит всего 122 070 засечек и занимает в памяти менее 10 МБ.

## Подводные камни

Уменьшение `index_granularity` до 100 строк увеличит точность выборки одной строки, но раздует размер индексных файлов в 80 раз и замедлит сканирование больших массивов данных.

## На собеседовании

**Вопрос:** Почему в ClickHouse марк-файлы имеют расширение `.mrk2`, а не `.mrk`?
**Ответ:** Формат `.mrk` использовался в старых версиях для несжатых данных. Формат `.mrk2` поддерживает адаптивную гранулярность (`adaptive index granularity`), сохраняя как смещения сжатых блоков в `.bin`, так и смещения внутри распакованных блоков.
