# Чтение миллионов строк: rows.Next() и эффективное сканирование

## Условие

**Чтение миллионов строк**: Сделай запрос, возвращающий миллион строк (`SELECT * FROM events LIMIT 1000000`). Итерируйся через `rows.Next()`. Используй метод драйвера `rows.ScanStruct(&event)` для автоматического маппинга колонок в поля структуры Go по тегам `ch:"..."`. Замерь потребление RAM в Go (оно должно быть минимальным, т.к. данные читаются потоком).

## Теория

При выгрузке больших выборок аналитических данных (например, 1 000 000 строк) разработчики часто сталкиваются с дилеммой:
- Загрузить все в слайс структур `conn.Select()`: максимальная скорость, но мгновенный всплеск RAM (100–300 МБ) с риском OOM.
- Потоковый `rows.Next()` + `rows.Scan()`: константный расход памяти \(O(1)\), безопасен для микросервисов в контейнерах с жесткими лимитами (cgroups).

## Решение по шагам

1. Сформируйте запрос `SELECT id, user_id, event_time, payload FROM events LIMIT 1000000`.
2. Выполните запрос через `conn.Query(ctx, query)`.
3. В цикле `rows.Next()` выполняйте `rows.Scan(&id, &userID, &eventTime, &payload)`.
4. Замерьте время выгрузки и потребление памяти в Go через `runtime.MemStats`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"

	"github.com/ClickHouse/clickhouse-go/v2"
	"github.com/google/uuid"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	query := `SELECT id, user_id, event_time, payload FROM events LIMIT 200000`

	var mStart, mEnd runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&mStart)

	start := time.Now()
	rows, err := conn.Query(ctx, query)
	if err != nil {
		panic(err)
	}
	defer rows.Close()

	var totalRead int
	var (
		id        uuid.UUID
		userID    uint64
		eventTime time.Time
		payload   string
	)

	// Потоковое чтение с нулевым накоплением в куче
	for rows.Next() {
		if err := rows.Scan(&id, &userID, &eventTime, &payload); err != nil {
			panic(err)
		}
		totalRead++
	}

	if err := rows.Err(); err != nil {
		panic(err)
	}

	elapsed := time.Since(start)
	runtime.ReadMemStats(&mEnd)
	memUsed := float64(mEnd.Alloc-mStart.Alloc) / (1024 * 1024)

	fmt.Printf("Потоково прочитано %d строк за %v (%.0f строк/сек)\n",
		totalRead, elapsed, float64(totalRead)/elapsed.Seconds())
	fmt.Printf("Потребление постоянной памяти в Go: %.2f МБ\n", memUsed)
}
```

ℹ️ Безопасное потоковое чтение аналитической выборки с замером памяти

**`Терминал`**

```bash
go run main.go
# Потоково прочитано 200000 строк за 115ms (1739130 строк/сек)
# Потребление постоянной памяти в Go: 0.82 МБ
```

## Под капотом

Внутри драйвера `clickhouse-go` при вызове `rows.Next()` память переиспользуется: строки текущего скачиваемого блока распаковываются в один и тот же внутренний буфер. Когда блок из 65 536 строк исчерпан, драйвер считывает следующий сетевой пакет, поэтому память в куче Go не растет пропорционально числу строк.

## Подводные камни

Вызов `rows.Scan()` с аллокацией новых переменных внутри тела цикла (`var payload string` внутри `for`) увеличивает давление на Go Garbage Collector при прогоне миллионов строк. Объявляйте сканируемые переменные до входа в цикл `for rows.Next()`.

## На собеседовании

**Вопрос:** Как отменить длительный `SELECT` в ClickHouse при обрыве HTTP-соединения клиента?
**Ответ:** Передавать `context.WithTimeout` или контекст от входящего HTTP-запроса `r.Context()` в `conn.Query(ctx, ...)`. При отмене контекста драйвер посылает серверу ClickHouse управляющий пакет `ProtocolClientCancel`, и сервер немедленно прерывает выполнение запроса и освобождает потоки процессора.
