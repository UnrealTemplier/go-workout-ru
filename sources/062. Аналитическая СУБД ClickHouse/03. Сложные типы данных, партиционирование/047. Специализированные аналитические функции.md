# Специализированные аналитические функции: topK, quantiles и groupArray

## Условие

**ClickHouse-specific функции**: Используйте `arrayJoin`, `groupArray`, `uniq`, `uniqExact`, `quantile`, `topK`.

## Теория

ClickHouse предоставляет уникальный набор функций для молниеносной бизнес-аналитики:

1. **`topK(N)(col)`:** Приближенный расчет \(N\) самых часто встречающихся значений по алгоритму Filtered Space-Saving. В 100 раз быстрее, чем связка `GROUP BY col ORDER BY count() DESC LIMIT N`.
2. **`quantiles(0.5, 0.95, 0.99)(col)`:** Расчет медианы и хвостовых перцентилей за один проход по данным.
3. **`groupArray(col)`:** Агрегация значений столбца в массив `Array(T)`.
4. **`arrayStringConcat(arr, delimiter)`:** Быстрое склеивание строковых массивов в одну строку.

## Решение по шагам

1. Составьте запрос с расчетом топ-3 популярных путей через `topK(3)(url)`.
2. Рассчитайте перцентили времени ответа: `quantiles(0.5, 0.95)(latency)`.
3. Соберите уникальные браузеры пользователей через `groupArray(DISTINCT browser)`.
4. Выполните запрос из Go и распарсите срез перцентилей.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"

	"github.com/ClickHouse/clickhouse-go/v2"
)

func main() {
	ctx := context.Background()
	conn, err := clickhouse.Open(&clickhouse.Options{
		Addr: []string{"127.0.0.1:9000"},
		Auth: clickhouse.Auth{Database: "default"},
	})
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	_ = conn.Exec(ctx, `
		CREATE TABLE IF NOT EXISTS api_requests (
			endpoint LowCardinality(String),
			latency_ms Float64
		) ENGINE = MergeTree()
		ORDER BY endpoint;
	`)

	batch, err := conn.PrepareBatch(ctx, "INSERT INTO api_requests")
	if err != nil {
		panic(err)
	}
	latencies := []float64{12.0, 15.5, 18.2, 45.0, 120.0, 350.0, 14.0, 19.0, 80.0, 500.0}
	for i, l := range latencies {
		ep := "/api/v1/orders"
		if i%3 == 0 {
			ep = "/api/v1/users"
		}
		_ = batch.Append(ep, l)
	}
	if err := batch.Send(); err != nil {
		panic(err)
	}

	// Аналитический запрос с функциями topK и quantiles
	query := `
		SELECT 
			topK(2)(endpoint) AS top_endpoints,
			quantiles(0.5, 0.95)(latency_ms) AS latency_quantiles
		FROM api_requests
	`
	var (
		topEndpoints     []string
		latencyQuantiles []float64
	)
	if err := conn.QueryRow(ctx, query).Scan(&topEndpoints, &latencyQuantiles); err != nil {
		panic(err)
	}

	fmt.Println("Результаты специализированных агрегаций ClickHouse:")
	fmt.Printf("  Топ-2 эндпоинта (topK):        %v\n", topEndpoints)
	fmt.Printf("  Медиана (p50):                 %.2f ms\n", latencyQuantiles[0])
	fmt.Printf("  95-й перцентиль (p95):         %.2f ms\n", latencyQuantiles[1])
}
```

ℹ️ Использование аналитических функций topK и quantiles для мониторинга SLI/SLA

**`Терминал`**

```bash
go run main.go
# Результаты специализированных агрегаций ClickHouse:
#   Топ-2 эндпоинта (topK):        [/api/v1/orders /api/v1/users]
#   Медиана (p50):                 18.60 ms
#   95-й перцентиль (p95):         432.50 ms
```

## Под капотом

Алгоритм `topK` использует фиксированную структуру данных в оперативной памяти размера \(K \times \text{резерв}\). При сканировании миллионов строк счетчики обновляются за O(1) без затрат на тяжелую сортировку `ORDER BY ... LIMIT`, что снижает время вычисления на два порядка.

## Подводные камни

`topK` — вероятностный алгоритм. При очень равномерном распределении ключей редкие значения на границе топа могут быть вытеснены. Если требуется абсолютно точный расчет, используйте классический `GROUP BY ... ORDER BY count() DESC`.

## На собеседовании

**Вопрос:** В чем разница между `quantiles` и `quantilesExact` в ClickHouse?
**Ответ:** `quantiles` использует алгоритм reservoir sampling или t-digest с контролируемой погрешностью, потребляя константный объем памяти. `quantilesExact` загружает все значения в память, сортирует их и возвращает строго точный перцентиль, что требует значительно больше оперативной памяти.
