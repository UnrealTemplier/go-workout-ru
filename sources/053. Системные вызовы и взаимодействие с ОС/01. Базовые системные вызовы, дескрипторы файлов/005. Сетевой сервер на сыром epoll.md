# Сетевой сервер на сыром epoll (EpollCreate1, EpollCtl, EpollWait) с неблокирующим сокетом

## Условие

**Использование `epoll` для асинхронного ввода-вывода.**: Напишите TCP-сервер с использованием `epoll` напрямую (через `unix.EpollCreate`, `unix.EpollCtl`, `unix.EpollWait`). Реализуйте неблокирующий accept и чтение. Сравните с обычным `net` пакетом по задержке.

## Теория

Сетевая подсистема Go известна своей непревзойденной производительностью благодаря встроенному механизму **Netpoller**. Под капотом на Linux рантайм Go использует системный интерфейс мультиплексирования ввода-вывода **epoll**.

**Эволюция мультиплексирования в Linux**:
- `select` / `poll`: Алгоритмическая сложность \(O(N)\). При каждом вызове массив всех дескрипторов копируется из User Space в Kernel Space, и ядро линейно сканирует все сокеты. При 10 000 соединениях CPU тратит 99% времени на пустой перебор.
- `epoll`: Алгоритмическая сложность \(O(1)\). Ядро регистрирует структуры сокетов в красно-черном дереве (RB-Tree). Когда на сетевую карту поступает пакет, драйвер через механизм аппаратных прерываний и callback помещает готовый дескриптор в двусвязный список готовности (Ready List). `epoll_wait` возвращает **только готовые** сокеты мгновенно.

**Архитектура работы с epoll**:
1. `epoll_create1(flags)`: Создает инстанс epoll и возвращает дескриптор `epfd`.
2. `socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK, 0)`: Создает сокет в неблокирующем режиме.
3. `bind()` и `listen()`: Переводит сокет в режим ожидания подключений.
4. `epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event)`: Регистрирует интерес к событиям `EPOLLIN` (готовность к чтению) на слушающем сокете.
5. `epoll_wait(epfd, events, maxevents, timeout)`: Блокирует поток до появления готовых событий.
6. При срабатывании на listener-сокете вызывается неблокирующий `accept4()`. Полученный клиентский сокет переводится в non-blocking и добавляется в epoll.
7. При срабатывании на клиентском сокете выполняется чтение `read()`.

## Решение по шагам

1. Создайте TCP listener сокет через системный вызов `syscall.Socket(syscall.AF_INET, syscall.SOCK_STREAM, 0)`.
2. Переведите сокет в неблокирующий режим с помощью `syscall.SetNonblock(listenFd, true)`.
3. Привяжите адрес (`bind`) и запустите прослушивание (`listen`).
4. Создайте дескриптор epoll: `epfd, err := syscall.EpollCreate1(0)`.
5. Добавьте слушающий сокет в epoll через `syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, listenFd, &event)`.
6. Запустите цикл опроса `syscall.EpollWait(epfd, events, timeout)`.
7. Обрабатывайте события: для listener делайте `syscall.Accept`, для клиентов — `syscall.Read` и ответ через `syscall.Write`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"syscall"
	"time"
)

func main() {
	// 1. Создаем сокет AF_INET, SOCK_STREAM
	listenFd, err := syscall.Socket(syscall.AF_INET, syscall.SOCK_STREAM, 0)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(listenFd)

	// Разрешаем повторное использование адреса (SO_REUSEADDR)
	if err := syscall.SetsockoptInt(listenFd, syscall.SOL_SOCKET, syscall.SO_REUSEADDR, 1); err != nil {
		panic(err)
	}

	// Переводим сокет в неблокирующий режим (O_NONBLOCK)
	if err := syscall.SetNonblock(listenFd, true); err != nil {
		panic(err)
	}

	// Привязываем адрес 127.0.0.1:9099
	sockAddr := &syscall.SockaddrInet4{Port: 9099, Addr: [4]byte{127, 0, 0, 1}}
	if err := syscall.Bind(listenFd, sockAddr); err != nil {
		panic(err)
	}

	// Запускаем прослушивание
	if err := syscall.Listen(listenFd, 128); err != nil {
		panic(err)
	}
	fmt.Printf("[Raw Epoll Server] Listening on 127.0.0.1:9099 (Listen FD: %d)\n", listenFd)

	// 2. Создаем инстанс epoll через EpollCreate1
	epfd, err := syscall.EpollCreate1(0)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(epfd)

	// Регистрируем событие EPOLLIN на слушающем сокете
	listenEvent := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(listenFd),
	}
	if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, listenFd, &listenEvent); err != nil {
		panic(err)
	}

	// 3. Запускаем фонового TCP-клиента для тестирования
	go func() {
		time.Sleep(100 * time.Millisecond)
		conn, err := net.Dial("tcp", "127.0.0.1:9099")
		if err != nil {
			fmt.Printf("Client dial error: %v\n", err)
			return
		}
		defer conn.Close()

		_, _ = conn.Write([]byte("PING_FROM_EPOLL_CLIENT"))
		reply := make([]byte, 64)
		n, _ := conn.Read(reply)
		fmt.Printf("[Test Client] Received response: %q\n", string(reply[:n]))
	}()

	// 4. Главный Event Loop на epoll_wait
	events := make([]syscall.EpollEvent, 64)
	buf := make([]byte, 1024)

	fmt.Println("[Raw Epoll Server] Entering EpollWait event loop...")

	for i := 0; i < 2; i++ { // Обрабатываем accept и ping
		nEvents, err := syscall.EpollWait(epfd, events, 2000) // timeout 2000ms
		if err != nil {
			if err == syscall.EINTR {
				continue
			}
			panic(err)
		}

		for j := 0; j < nEvents; j++ {
			ev := events[j]
			fd := int(ev.Fd)

			if fd == listenFd {
				// Новое входящее клиентское подключение
				clientFd, _, err := syscall.Accept(listenFd)
				if err != nil {
					continue
				}
				_ = syscall.SetNonblock(clientFd, true)

				// Добавляем клиентский сокет в epoll
				clientEvent := syscall.EpollEvent{
					Events: syscall.EPOLLIN,
					Fd:     int32(clientFd),
				}
				_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, clientFd, &clientEvent)
				fmt.Printf("[Server Event] Accepted new client FD: %d\n", clientFd)
			} else {
				// Готовность к чтению данных от клиента
				n, err := syscall.Read(fd, buf)
				if n > 0 {
					fmt.Printf("[Server Event] Read %d bytes from client FD %d: %q\n", n, fd, string(buf[:n]))
					// Отправляем эхо-ответ
					response := append([]byte("ACK: "), buf[:n]...)
					_, _ = syscall.Write(fd, response)
				}
				if err != nil || n == 0 {
					// Клиент отключился
					_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_DEL, fd, nil)
					_ = syscall.Close(fd)
					fmt.Printf("[Server Event] Client FD %d closed\n", fd)
				}
			}
		}
	}
}
```

## Под капотом

Как встроенный Netpoller Go взаимодействует с epoll:
1. Когда вы вызываете `net.Listen` или `conn.Read()`, сокет переводится в неблокирующий режим (`O_NONBLOCK`).
2. Если данных нет в буфере приема сокета, системный вызов `read()` возвращает ошибку `EAGAIN` / `EWOULDBLOCK`.
3. Рантайм Go не блокирует поток ОС! Вместо этого он регистрирует дескриптор во внутреннем epoll-инстансе (`runtime.netpollopen`) и паркует текущую горутину: `gopark(netpollblockcommit, ...)` со статусом `_Gwaiting`.
4. Поток `M` освобождается и берет другую готовую горутину из очереди `runq`.
5. Фоновый поток `sysmon` или поток, перешедший в фазу кражи работы (`findrunnable`), вызывает `runtime.netpoll(delay)`.
6. Как только пакет поступает в сетевой стек, `epoll_wait` пробуждается, рантайм находит спящую горутину по адресу в структуре дескриптора и переводит её в статус `_Grunnable`, возвращая в очередь исполнения.

## Подводные камни

1. **Edge-Triggered (EPOLLET) vs Level-Triggered**: По умолчанию epoll работает в режиме Level-Triggered (генерирует события, пока в буфере есть данные). В режиме EPOLLET событие генерируется только при изменении состояния. В режиме Edge-Triggered необходимо читать сокет в цикле до получения ошибки `EAGAIN`, иначе оставшиеся байты зависнут навсегда.
2. **Блокирующий сокет в epoll**: Если забыть сделать `syscall.SetNonblock(fd, true)`, вызов `accept` или `read` может заблокировать весь системный поток операционной системы при спаде трафика или race condition.
3. **Thundering Herd Problem (Проблема громогласного стада)**: Если несколько потоков слушают один epfd или несколько epoll-инстансов следят за одним listenFd без флага `EPOLLEXCLUSIVE`, ядро при одном входящем SYN-пакете разбудит все потоки одновременно, вызвав скачок переключения контекста.

## На собеседовании

**Вопрос с собеседования:** «Зачем популярные фреймворки типа `fasthttp` или `gnet` используют кастомный epoll loop вместо стандартного пакета `net/http`?»
**Ответ:**
Стандартная модель Go выделяет **одну горутину на каждое соединение** (`go handleConn(c)`). При 1 000 000 открытых WebSocket соединений:
1. 1 миллион горутин расходуют минимум 2–4 ГБ оперативной памяти только на начальные стеки (по 2–4 КБ на горутину).
2. Нагрузка на планировщик GMP при переключении миллионов контекстов возрастает.
Фреймворки на базе Reactor pattern (`gnet`, `evio`) используют фиксированный пул потоков/горутин (по числу ядер CPU) и один общий epoll event loop, обрабатывая сотни тысяч соединений с минимальным потреблением памяти и задержкой.
