# Прямое чтение переменных окружения через syscall.Getenv и анализ памяти процесса

## Условие

**Environment variables**: Получите переменные окружения через `syscall.Getenv()` (не путать с `os.Getenv()`).

## Теория

Переменные окружения (Environment Variables) процесса в Linux хранятся в специальной области памяти в верхней части стека процесса сразу за аргументами командной строки `argv`.

При старте программы загрузчик ELF (`ld-linux.so`) передает функции `main` три параметра:
1. `argc`: Число аргументов командной строки.
2. `argv`: Массив указателей на строки аргументов.
3. `envp`: Массив указателей на строки вида `KEY=VALUE`, завершающийся указателем `NULL`.

**Разница между `os.Getenv` и `syscall.Getenv`**:
- `os.Getenv(key)`: Высокоуровневая функция. При старте рантайма Go сканирует массив `envp`, парсит все строки и сохраняет их во внутреннюю мапу `map[string]string` под мьютексом `syscall.envLock`.
- `syscall.Getenv(key)`: Возвращает значение переменной и булевый флаг наличия `(value string, found bool)`. В отличие от `os.Getenv`, возвращающей просто пустую строку `""` (из-за чего невозможно отличить несуществующую переменную от переменной со значением `""`), `syscall.Getenv` явно возвращает `found = false`.
- `syscall.Environ()`: Возвращает сырой массив строк `[]string` в формате `"KEY=VALUE"` напрямую из рантайма.

## Решение по шагам

1. Задайте новую переменную окружения через `syscall.Setenv("BIGTECH_CLUSTER_ID", "dc-spb-01")`.
2. Считайте её с помощью `syscall.Getenv("BIGTECH_CLUSTER_ID")`.
3. Проверьте булевый флаг `found`.
4. Проверьте поведение на заведомо отсутствующей переменной.
5. Прочитайте системную переменную `PATH` или `HOME` через `syscall.Getenv`.
6. Выведите первые 3 записи из сырого среза `syscall.Environ()`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"strings"
	"syscall"
)

func main() {
	// 1. Устанавливаем тестовую переменную окружения на системном уровне
	testKey := "HIGHLOAD_NODE_ROLE"
	testVal := "STORAGE_LEADER_PRIMARY"

	if err := syscall.Setenv(testKey, testVal); err != nil {
		panic(err)
	}

	// 2. Получаем значение через syscall.Getenv
	val, found := syscall.Getenv(testKey)
	fmt.Printf("[syscall.Getenv] Key: %s | Val: %s | Found: %v\n", testKey, val, found)

	// 3. Проверяем отсутствующую переменную
	missingKey := "NON_EXISTENT_VAR_12345"
	valMiss, foundMiss := syscall.Getenv(missingKey)
	fmt.Printf("[syscall.Getenv] Key: %s | Val: %q | Found: %v\n", missingKey, valMiss, foundMiss)

	// 4. Проверяем переменную с пустым значением
	emptyKey := "EMPTY_FLAG_VAR"
	_ = syscall.Setenv(emptyKey, "")
	valEmpty, foundEmpty := syscall.Getenv(emptyKey)
	fmt.Printf("[syscall.Getenv] Key: %s | Val: %q | Found: %v (Distinguishes empty from missing!)\n",
		emptyKey, valEmpty, foundEmpty)

	// 5. Читаем системный PATH
	pathVal, pathFound := syscall.Getenv("PATH")
	if pathFound {
		parts := strings.Split(pathVal, ":")
		fmt.Printf("[syscall.Getenv] System PATH has %d directory entries\n", len(parts))
	}

	// 6. Дамп сырых переменных окружения через syscall.Environ()
	rawEnvs := syscall.Environ()
	fmt.Printf("Total process environments count: %d. First 3 raw entries:\n", len(rawEnvs))
	for i := 0; i < 3 && i < len(rawEnvs); i++ {
		fmt.Printf("  [%d] %s\n", i, rawEnvs[i])
	}
}
```

## Под капотом

Как устроена таблица окружения в памяти Linux ELF:
1. При старте ядра Linux функция `create_elf_tables()` формирует стек процесса:
   - `[Top of Stack]`
   - `NULL`
   - Строки окружения (`"HOME=/root"`, `"PATH=/usr/bin"`)
   - Строки аргументов (`"arg0"`, `"arg1"`)
   - `envp[0]`, `envp[1]`, ..., `NULL`
   - `argv[0]`, `argv[1]`, ..., `NULL`
   - `argc`
2. В Go переменные окружения копируются во внутреннее хранилище рантайма Go.
3. При вызове `syscall.Setenv()` рантайм Go обновляет внутреннюю хэш-таблицу.
4. Если приложение использует CGO, Go автоматически вызывает C-функцию `setenv()` в libc, чтобы C-библиотеки видели обновленные переменные окружения.

## Подводные камни

1. **Гонка данных при параллельном `Setenv` / `Getenv`**: До Go 1.21 частые вызовы `Setenv` и `Getenv` из параллельных горутин могли приводить к гонкам данных в рантайме. В продакшене все переменные окружения считывают **один раз при старте сервиса** в неизменяемую структуру конфигурации.
2. **Изменение окружения дочерних процессов**: Вызов `syscall.Setenv` изменяет окружение текущего процесса и всех **будущих** дочерних процессов, создаваемых после него. Уже запущенные сторонние процессы окружение не изменяют.
3. **Скрытые секреты в `/proc/PID/environ`**: В Linux любой процесс с тем же UID может прочитать все переменные окружения вашего процесса через псевдофайл `/proc/<PID>/environ`. Никогда не передавайте долгоживущие секретные токены и мастер-ключи через env в multi-tenant системах.

## На собеседовании

**Вопрос с собеседования:** «Почему передача секретов (паролей БД, API-токенов) через переменные окружения считается антипаттерном в DevSecOps, и как их безопасно пробрасывать в Go-сервисы?»
**Ответ:**
1. **Уязвимость к утечкам**: Переменные окружения часто попадают в лог-файлы при падении приложения (crash dumps), видны через `/proc/$PID/environ` и выводятся командами `ps e` или инспекцией `docker inspect`.
2. **Безопасная альтернатива**:
   - Монтирование секретов в память через `tmpfs` файлы (Kubernetes Secrets / HashiCorp Vault Agent) и чтение с диска.
   - Динамическое получение токенов через gRPC/mTLS по мере необходимости с хранением в защищенной памяти (Protected Memory через `mlock` / `memfd_secret`).
