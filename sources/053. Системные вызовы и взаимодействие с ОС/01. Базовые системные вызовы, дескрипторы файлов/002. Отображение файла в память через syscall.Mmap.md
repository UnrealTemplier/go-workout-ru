# Отображение файла в память через syscall.Mmap, in-place модификация и сброс на диск через Msync

## Условие

**Работа с `mmap`.**: Реализуйте чтение файла через отображение в память (`syscall.Mmap`). Прочитайте содержимое файла, измените байты в слайсе, синхронизируйте (`syscall.Msync`) и убедитесь, что изменения записаны на диск.

## Теория

Системный вызов `mmap` (Memory Map) отображает содержимое файла на диске напрямую в виртуальное адресное пространство процесса пользователя.

**Классический ввод-вывод (`read / write`)**:
1. Ядро считывает страницу файла с диска в Page Cache ядра.
2. Ядро копирует данные из Page Cache в буфер пространства пользователя в памяти Go.
3. При записи происходит обратное копирование: память Go -> Page Cache ядра -> диск.
Это приводит к двойному копированию (Double Buffering) и накладным расходам на context switch при каждом вызове.

**Ввод-вывод через `mmap`**:
1. Вызывается `syscall.Mmap(fd, offset, length, prot, flags)`:
   - `prot`: Права доступа к страницам (`PROT_READ | PROT_WRITE`).
   - `flags`: `MAP_SHARED` (изменения отражаются в файле и видны другим процессам) или `MAP_PRIVATE` (Copy-On-Write, изменения локальны для процесса).
2. Ядро резервирует диапазон виртуальных адресов (`VMA` — Virtual Memory Area), но **не загружает** файл целиком в оперативную память.
3. При первом чтении или записи по адресу процессор фиксирует аппаратное исключение **Page Fault** (отсутствие страницы в TLB).
4. Обработчик Page Fault ядра ОС подгружает нужную страницу (4 КБ) с диска в память и обновляет таблицу страниц (PTE).
5. Запись в срез `[]byte` изменяет страницу прямо в Page Cache.
6. Вызов `syscall.Msync(data, syscall.MS_SYNC)` принудительно синхронизирует dirty-страницы памяти с постоянным накопителем (SSD/NVMe).
7. По завершении память размонтируется через `syscall.Munmap(data)`.

## Решение по шагам

1. Создайте временный тестовый файл и запишите в него начальные данные фиксированного размера.
2. Откройте файл в режиме чтения и записи: `syscall.Open(path, syscall.O_RDWR, 0666)`.
3. Получите размер файла через `syscall.Fstat(fd, &stat)`.
4. Отобразите файл в память: `data, err := syscall.Mmap(fd, 0, int(stat.Size), syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_SHARED)`.
5. Модифицируйте байты непосредственно в срезе `data`.
6. Вызовите `syscall.Msync(data, syscall.MS_SYNC)` для гарантированного сброса кэша на диск.
7. Освободите отображение через `syscall.Munmap(data)` и закройте дескриптор.
8. Прочитайте файл заново обычным способом и убедитесь, что данные на диске изменились.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	filePath := "mmap_test.bin"
	initialData := []byte("DATABASE_PAGE_001_VERSION_1.0_INITIAL_PAYLOAD")

	// 1. Создаем файл на диске
	if err := os.WriteFile(filePath, initialData, 0644); err != nil {
		panic(err)
	}
	defer os.Remove(filePath)

	// 2. Открываем файловый дескриптор для mmap (чтение + запись)
	fd, err := syscall.Open(filePath, syscall.O_RDWR, 0666)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(fd)

	// 3. Получаем размер файла
	var stat syscall.Stat_t
	if err := syscall.Fstat(fd, &stat); err != nil {
		panic(err)
	}
	fileSize := int(stat.Size)

	// 4. Отображаем файл в память через syscall.Mmap
	// MAP_SHARED гарантирует, что запись в память отразится в файле на диске
	mmapSlice, err := syscall.Mmap(
		fd,
		0,
		fileSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(err)
	}
	defer syscall.Munmap(mmapSlice)

	fmt.Printf("File mapped into memory. Size: %d bytes\n", len(mmapSlice))
	fmt.Printf("Initial content: %s\n", string(mmapSlice))

	// 5. In-place изменение данных прямо в памяти без системных вызовов write()
	patch := []byte("VERSION_2.0_UPDATED")
	targetOffset := 18
	copy(mmapSlice[targetOffset:], patch)

	// 6. Синхронизируем грязные страницы (dirty pages) с физическим диском
	// MS_SYNC блокирует выполнение до окончания физической записи контроллером диска
	if err := syscall.Msync(mmapSlice, syscall.MS_SYNC); err != nil {
		panic(err)
	}

	fmt.Println("Memory modified and synchronized to disk via syscall.Msync (MS_SYNC).")

	// 7. Проверяем файл обычным os.ReadFile
	diskContent, err := os.ReadFile(filePath)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Read from disk:  %s\n", string(diskContent))
}
```

## Под капотом

Как `mmap` функционирует внутри ядра Linux:
1. `syscall.Mmap` транслируется в ассемблерную инструкцию `SYSCALL` с кодом `SYS_MMAP` (номер 9 на x86_64).
2. Подсистема управления памятью ядра (`mm/mmap.c`) создает объект структуры `vm_area_struct` в адресном пространстве процесса. Поле `vm_file` указывает на дескриптор открытого файла.
3. Возвращаемый срез Go `[]byte` конструируется рантаймом Go поверх базового адреса виртуальной памяти: указатель `Data` указывает на адрес VMA, а `Len` и `Cap` равны размеру маппинга.
4. При записи `copy(mmapSlice, ...)` процессор аппаратно выставляет бит `Dirty` в Page Table Entry (PTE).
5. `syscall.Msync` обходит dirty-страницы в Page Cache и вызывает операцию файловой системы `writepages()`, отправляя I/O запросы в очередь блочного устройства через DMA-контроллер.

## Подводные камни

1. **Усечение файла другим процессом (SIGBUS Crash)**: Если размер файла на диске уменьшится (например, другой процесс вызовет `ftruncate`), обращение к срезу `mmapSlice` за пределами нового размера файла приведет к получению сигнала `SIGBUS` (Bus Error), который мгновенно роняет Go-процесс без возможности перехвата через `recover()`.
2. **Файлы нулевого размера**: Попытка вызвать `syscall.Mmap` с длиной `length = 0` вернет ошибку `EINVAL`. Размер файла обязан быть больше 0.
3. **Флаг `MAP_PRIVATE` вместо `MAP_SHARED`**: При использовании `MAP_PRIVATE` любые изменения страниц памяти копируются в анонимную память (Copy-on-Write) и **никогда** не запишутся в исходный файл на диске.

## На собеседовании

**Вопрос с собеседования:** «Почему высокопроизводительные embedded базы данных (BoltDB, LMDB, BadgerDB) используют `mmap` для чтения и записи файлов БД?»
**Ответ:**
1. **Zero-Copy чтение**: Данные читаются прямо из Page Cache ядра операционной системы без копирования в буферы пользовательского пространства.
2. **Управление кэшем на уровне ОС**: Не требуется реализовывать собственный сложный LRU-буфер в приложении — ядро Linux автоматически вытесняет холодные страницы и кэширует горячие.
3. **Эффективный Random Access**: Доступ к B+ Tree нодам или LSM-блокам осуществляется за \(O(1)\) по смещениям указателей без повторных вызовов `seek()` и `read()`.
