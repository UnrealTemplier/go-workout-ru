# Прямой вызов getpid через syscall.Syscall6 и анализ причин отказа от inline asm в Go

## Условие

Напишите программу, которая использует `syscall.Syscall6` для вызова `getpid` (или `getuid`) на Linux. Сравните с `os.Getpid()`. Объясните, почему в Go предпочтительнее пакеты `syscall`/`golang.org/x/sys/unix` вместо прямого inline-asm.

## Теория

Семейство функций `syscall.Syscall`, `syscall.Syscall6`, `syscall.Syscall9` предназначено для выполнения системных вызовов с разным количеством аргументов:
- `Syscall`: До 3 аргументов (на x86_64 регистры RDI, RSI, RDX).
- `Syscall6`: До 6 аргументов (RDI, RSI, RDX, R10, R8, R9).
- `Syscall9`: До 9 аргументов (дополнительные параметры передаются через стек).

Вызов `getpid` (получение идентификатора текущего процесса) в Linux x86_64 имеет номер `SYS_GETPID = 39`. Он не принимает аргументов, поэтому неиспользуемые аргументы в `Syscall6` передаются как `0`:
```go
pid, _, err := syscall.Syscall6(syscall.SYS_GETPID, 0, 0, 0, 0, 0, 0)
```

**Почему в Go нет и не будет классического inline assembly (`asm volatile`) как в C?**
1. **Кооперативный планировщик GMP и стеки горутин**:
В C каждый поток имеет фиксированный стек ОС (8–10 МБ). В Go горутины имеют миниатюрные перемещаемые стеки (начиная с 2 КБ). Если бы компилятор позволял вставлять произвольный ассемблерный код прямо в Go-функцию, компилятор не мог бы рассчитать объем фрейма стека перед компиляцией, что привело бы к переполнению стека (Stack Overflow) без возможности динамического роста.
2. **Сборщик мусора и безопасные точки (GC Safepoints)**:
Сборщик мусора Go требует точной информации о размещении всех указателей на стеке (Stack Maps). Произвольный inline-asm ломает генерацию stack maps, превращая сборку мусора в невозможную задачу.
3. **Кроссплатформенность и переносимость**:
Вместо inline-asm Go использует четко документированные системные пакеты `syscall` и `golang.org/x/sys/unix`, скомпилированные с правильными ABI-трамплинами и build tags для каждой архитектуры (amd64, arm64, riscv64, ppc64).

## Решение по шагам

1. Получите константу системного вызова `syscall.SYS_GETPID`.
2. Вызовите `syscall.Syscall6(syscall.SYS_GETPID, 0, 0, 0, 0, 0, 0)`.
3. Получите PID из первого возвращаемого регистра `r1`.
4. Вызовите стандартную функцию `os.Getpid()`.
5. Сравните полученные значения — они должны быть идентичны.
6. Вызовите `syscall.SYS_GETUID` для получения идентификатора пользователя (UID) текущего процесса.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	// 1. Вызов getpid через syscall.Syscall6
	// SYS_GETPID на Linux x86_64 = 39
	r1Pid, _, errNo := syscall.Syscall6(
		syscall.SYS_GETPID,
		0, 0, 0, 0, 0, 0,
	)
	if errNo != 0 {
		panic(fmt.Sprintf("SYS_GETPID failed: %v", errNo))
	}
	rawPid := int(r1Pid)

	// 2. Вызов через стандартный пакет os
	standardPid := os.Getpid()

	fmt.Printf("Direct Syscall6 SYS_GETPID (%d): %d\n", syscall.SYS_GETPID, rawPid)
	fmt.Printf("Standard os.Getpid():              %d\n", standardPid)

	if rawPid == standardPid {
		fmt.Println("PID matches perfectly!")
	} else {
		panic("PID mismatch!")
	}

	// 3. Вызов getuid (SYS_GETUID = 102 на Linux x86_64)
	r1Uid, _, errNo := syscall.Syscall6(
		syscall.SYS_GETUID,
		0, 0, 0, 0, 0, 0,
	)
	if errNo != 0 {
		panic(fmt.Sprintf("SYS_GETUID failed: %v", errNo))
	}
	fmt.Printf("Direct Syscall6 SYS_GETUID (%d): %d\n", syscall.SYS_GETUID, int(r1Uid))
	fmt.Printf("Standard os.Getuid():              %d\n", os.Getuid())
}
```

ℹ️ Использование syscall.Syscall6 для получения PID и UID процесса

**`Терминал`**

```bash
go run main.go
# Вывод:
# Direct Syscall6 SYS_GETPID (39): 24510
# Standard os.Getpid():              24510
# PID matches perfectly!
# Direct Syscall6 SYS_GETUID (102): 1000
# Standard os.Getuid():              1000
```

## Под капотом

Как устроен `syscall.Syscall6` в исходниках Go (`src/syscall/asm_linux_amd64.s`):
```assembly
TEXT ·Syscall6(SB),NOSPLIT,$0-80
    CALL    runtime·entersyscall(SB)
    MOVQ    a1+8(FP), DI
    MOVQ    a2+16(FP), SI
    MOVQ    a3+24(FP), DX
    MOVQ    a4+32(FP), R10
    MOVQ    a5+40(FP), R8
    MOVQ    a6+48(FP), R9
    MOVQ    trap+0(FP), AX  // Номер системного вызова
    SYSCALL
    CMPQ    AX, $0xfffffffffffff001
    JLS     ok
    MOVQ    $-1, r1+56(FP)
    MOVQ    $0, r2+64(FP)
    NEGQ    AX
    MOVQ    AX, err+72(FP)  // Код ошибки errno
    CALL    runtime·exitsyscall(SB)
    RET
ok:
    MOVQ    AX, r1+56(FP)
    MOVQ    DX, r2+64(FP)
    MOVQ    $0, err+72(FP)
    CALL    runtime·exitsyscall(SB)
    RET
```
Обратите внимание на директиву `NOSPLIT`: она запрещает компилятору вставлять пролог проверки размера стека, гарантируя непрерывное выполнение инструкции `SYSCALL`.

## Подводные камни

1. **Использование `Syscall` вместо `Syscall6` для функций с >3 аргументами**: Если вызвать системный вызов, требующий 4 или более аргументов (например, `mmap`, `epoll_pwait`, `accept4`), через `Syscall` вместо `Syscall6`, регистры `R10`, `R8`, `R9` останутся неопределенными (мусор из предыдущих инструкций), что приведет к ошибке `EINVAL` или непредвиденному поведению ядра.
2. **Коды ошибок в отрицательном диапазоне**: Ядро Linux возвращает ошибки в диапазоне `-1 ... -4095`. Ассемблерный код Go проверяет это условие (`CMPQ AX, 0xfffffffffffff001`), берет модуль (`NEGQ AX`) и возвращает положительное число в поле `err`. Ручной парсинг сырых возвратов без этой нормализации приведет к ошибкам.
3. **vDSO (Virtual Dynamic Shared Object)**: В современных дистрибутивах Linux вызовы `gettimeofday` и `time` выполняются в пространстве пользователя через vDSO без входа в Ring 0. Прямой `syscall.Syscall(SYS_CLOCK_GETTIME)` работает в 5–10 раз медленнее, чем стандартный `time.Now()` из-за игнорирования страниц vDSO.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных версиях Go пакет `syscall` объявлен deprecated (заморожен), и разработчикам рекомендуется использовать `golang.org/x/sys/unix`?»
**Ответ:**
Пакет `syscall` входит в гарантию обратной совместимости Go 1 Compatibility Promise. Из-за этого:
1. Сигнатуры функций и константы в `syscall` невозможно изменить или расширить без риска поломать миллионы старых программ.
2. Новые системные вызовы Linux (например, `io_uring`, `pidfd_open`, `clone3`, новые флаги `openat2`) не добавляются в замороженный `syscall`.
3. Пакет `golang.org/x/sys/unix` развивается динамически синхронно с релизами ядра Linux, содержит актуальные типы данных, точные константы и поддержку всех архитектур процессоров.
