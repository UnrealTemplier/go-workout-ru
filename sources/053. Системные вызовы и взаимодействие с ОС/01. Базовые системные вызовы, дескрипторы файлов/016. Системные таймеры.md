# Системные таймеры: syscall.Gettimeofday, CLOCK_MONOTONIC и монотонность времени в Go

## Условие

**Time syscalls**: Получите текущее время через `syscall.Gettimeofday()` (точнее, чем `time.Now()` для некоторых use cases).

## Теория

В операционных системах существует два принципиально разных вида времени:

1. **Wall-Clock Time (Календарное время)**:
   - Привязано к реальному астрономическому времени (UTC, эпоха Unix с 1 января 1970 года).
   - Системный вызов `syscall.Gettimeofday(&tv, nil)` возвращает структуру:
     ```go
     type Timeval struct {
         Sec  int64 // Секунды с 1970 г.
         Usec int64 // Микросекунды (0..999999)
     }
     ```
   - **Критическая особенность**: Календарное время **не монотонно**! Оно может прыгать вперед и назад при синхронизации через NTP (Network Time Protocol), при смене часовых поясов или введении високосных секунд (Leap Seconds). Замерять интервалы работы кода через календарное время нельзя.
2. **Monotonic Time (Монотонное время)**:
   - Системный вызов `clock_gettime(CLOCK_MONOTONIC, &ts)`.
   - Время отсчитывается от произвольной фиксированной точки в прошлом (обычно с момента загрузки хоста / Boot Time).
   - Монотонные часы **никогда не идут назад**. Любое последующее значение строго больше или равно предыдущему.

С версии Go 1.9 стандартный тип `time.Time` содержит одновременно два показания: монотонное время для расчета длительности (`time.Since`, `sub`) и астрономическое время для форматирования даты.

## Решение по шагам

1. Создайте экземпляр `var tv syscall.Timeval`.
2. Вызовите системный вызов `syscall.Gettimeofday(&tv)`.
3. Рассчитайте метку времени в микросекундах и секундах.
4. Вызовите `time.Now()` и сравните полученные значения.
5. Рассмотрите разбор структуры `syscall.Timespec` (наносекундная точность).
6. Объясните механизм аппаратного таймера TSC (Time Stamp Counter).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
	"time"
)

func main() {
	// 1. Системный вызов gettimeofday (микросекундная точность)
	var tv syscall.Timeval
	if err := syscall.Gettimeofday(&tv); err != nil {
		panic(fmt.Sprintf("syscall.Gettimeofday failed: %v", err))
	}

	// Переводим секунды и микросекунды в time.Time
	goTimeFromSyscall := time.Unix(tv.Sec, tv.Usec*1000)

	// 2. Стандартный time.Now()
	goTimeStandard := time.Now()

	fmt.Println("=== TIME SYSTEM CALL COMPARISON ===")
	fmt.Printf("syscall.Gettimeofday Sec:  %d\n", tv.Sec)
	fmt.Printf("syscall.Gettimeofday Usec: %d (microsecond component)\n", tv.Usec)
	fmt.Printf("Parsed Wall-Clock Time:    %s\n", goTimeFromSyscall.Format(time.RFC3339Nano))
	fmt.Printf("Standard time.Now():       %s\n", goTimeStandard.Format(time.RFC3339Nano))

	// Разница между двумя замерами (должна составлять доли микросекунды)
	diff := goTimeStandard.Sub(goTimeFromSyscall)
	fmt.Printf("Delta between calls:       %v\n", diff)

	// 3. Демонстрация монотонного таймера
	startMono := time.Now()
	time.Sleep(10 * time.Millisecond)
	elapsedMono := time.Since(startMono)
	fmt.Printf("Monotonic elapsed duration: %v (Immune to NTP jumps!)\n", elapsedMono)
}
```

## Под капотом

Как работает чтение времени без входа в ядро через vDSO:
1. Выполнять полноценный системный вызов `sys_gettimeofday` с переключением контекста в ядро сотни тысяч раз в секунду было бы катастрофически дорого (~150 нс на вызов).
2. Ядро Linux монтирует в память каждого процесса специальную виртуальную страницу **vDSO (Virtual Dynamic Shared Object)**.
3. Ядро непрерывно обновляет текущие коэффициенты аппаратного таймера процессора TSC (Time Stamp Counter) в разделяемой памяти vDSO.
4. Вызов `time.Now()` в Go выполняется за **15–20 наносекунд** без единого перехода кольца защиты процессора (без инструкции `SYSCALL`): процессор просто считывает регистр `RDTSC` и производит умножение на калибровочный множитель в пользовательском пространстве.

## Подводные камни

1. **Использование `Gettimeofday` для замера бенчмарков**: Если во время длительного замера NTP-демон (chrony, ntpd) скорректирует системные часы назад на 500 мс, разность времени `end.Sec - start.Sec` окажется **отрицательной**, вызвав панику или некорректную логику таймаутов.
2. **Устаревание `gettimeofday` в POSIX**: Стандарт POSIX.1-2008 пометил `gettimeofday()` как obsolescent (устаревший) в пользу вызова `clock_gettime()`, поддерживающего наносекундную точность (`struct timespec`).
3. **Дрейф таймера TSC при переходе процессора в режим энергосбережения**: На старых процессорах частота TSC менялась при троттлинге частоты ядер. Современные процессоры имеют флаг `constant_tsc` / `nonstop_tsc` в `/proc/cpuinfo`.

## На собеседовании

**Вопрос с собеседования:** «Почему в распределенных базах данных (Google Spanner, CockroachDB, YugabyteDB) проблема точного времени является ключевым вызовом консенсуса?»
**Ответ:**
1. Никакие программные часы серверов не синхронны абсолютно: сетевые задержки NTP дают неопределенность от единиц до десятков миллисекунд (Clock Skew).
2. Без единого монотонного времени невозможно определить, какая транзакция произошла раньше (сериализуемость транзакций, Linearizability).
3. Google Spanner решил эту проблему технологией **TrueTime API**: использование атомных часов (Atomic Clocks) и GPS-приемников в каждом дата-центре, гарантируя, что ошибка времени \(\epsilon \le 7\) мс. Транзакции выжидают окно неопределенности \(2\epsilon\), гарантируя строгий порядок без распределенных блокировок.
