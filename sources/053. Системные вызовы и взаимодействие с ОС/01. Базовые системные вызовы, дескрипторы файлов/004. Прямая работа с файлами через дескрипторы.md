# Прямая работа с файлами через дескрипторы: unix.Open, Write, Seek, Read и Close

## Условие

**[Прямая работа с файлами]**: Открой файл через `unix.Open(path, unix.O_RDWR|unix.O_CREAT, 0666)`. Запиши в него байты через `unix.Write(fd, data)`. Прочитай через `unix.Read(fd, buf)`. Закрой через `unix.Close(fd)`.

## Теория

Пакет `os` в Go предоставляет удобные высокоуровневые типы `os.File`, `os.Open`, `os.Create`. Под капотом каждый открытый файл в POSIX-совместимой операционной системе идентифицируется целочисленным **файловым дескриптором** (File Descriptor, FD) — неотрицательным числом, являющимся индексом в таблице открытых файлов процесса в структуре `files_struct` ядра Linux.

Использование низкоуровневых системных вызовов через `syscall` / `unix`:
- `syscall.Open(path, flags, mode)`: Открывает файл или создает новый.
  - Флаги: `O_RDONLY`, `O_WRONLY`, `O_RDWR`, `O_CREAT` (создать при отсутствии), `O_TRUNC` (усечь при открытии), `O_APPEND` (дозапись в конец), `O_NONBLOCK` (неблокирующий I/O), `O_SYNC` (синхронный сброс метаданных и данных).
  - Mode: Права доступа при создании файла (например, `0666` & ~umask).
- `syscall.Write(fd, data)`: Отправляет байты в файл, возвращает количество фактически записанных байт.
- `syscall.Seek(fd, offset, whence)`: Перемещает внутренний файловый указатель (File Offset Pointer). Флаги `whence`: `0` (`SEEK_SET` — от начала), `1` (`SEEK_CUR` — от текущей позиции), `2` (`SEEK_END` — от конца).
- `syscall.Read(fd, buf)`: Считывает данные из текущей позиции в переданный буфер.
- `syscall.Close(fd)`: Закрывает дескриптор, уменьшая счетчик ссылок на файл в ядре.

## Решение по шагам

1. Сформируйте путь к файлу и флаги открытия: `syscall.O_RDWR | syscall.O_CREAT | syscall.O_TRUNC`.
2. Откройте файл через `syscall.Open(path, flags, 0644)`.
3. Запишите бинарные данные через `syscall.Write(fd, payload)`.
4. Переместите файловый указатель обратно в начало файла через `syscall.Seek(fd, 0, 0)`.
5. Выделите буфер и прочитайте данные через `syscall.Read(fd, readBuf)`.
6. Закройте дескриптор через `syscall.Close(fd)` с проверкой ошибки.
7. Проверьте совпадение записанных и прочитанных данных.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	filePath := "raw_io_test.txt"
	defer os.Remove(filePath)

	// 1. Открываем файл через прямой системный вызов open()
	flags := syscall.O_RDWR | syscall.O_CREAT | syscall.O_TRUNC
	mode := uint32(0644) // rw-r--r--

	fd, err := syscall.Open(filePath, flags, mode)
	if err != nil {
		panic(fmt.Sprintf("syscall.Open failed: %v", err))
	}
	// Гарантируем закрытие дескриптора
	defer func() {
		if err := syscall.Close(fd); err != nil {
			fmt.Printf("Error closing fd: %v\n", err)
		}
	}()

	fmt.Printf("File opened successfully. File Descriptor: %d\n", fd)

	// 2. Запись данных в файл через syscall.Write
	dataToWrite := []byte("Direct Kernel File I/O via POSIX Descriptors!")
	totalWritten := 0

	// Цикл на случай частичной записи (partial write)
	for totalWritten < len(dataToWrite) {
		n, err := syscall.Write(fd, dataToWrite[totalWritten:])
		if err != nil {
			panic(fmt.Sprintf("syscall.Write failed: %v", err))
		}
		totalWritten += n
	}
	fmt.Printf("Written %d bytes to FD %d\n", totalWritten, fd)

	// 3. Перемещаем указатель файла в начало (SEEK_SET = 0)
	newOffset, err := syscall.Seek(fd, 0, 0)
	if err != nil {
		panic(fmt.Sprintf("syscall.Seek failed: %v", err))
	}
	fmt.Printf("Seeked to offset: %d\n", newOffset)

	// 4. Чтение данных из файла через syscall.Read
	readBuffer := make([]byte, 128)
	bytesRead, err := syscall.Read(fd, readBuffer)
	if err != nil {
		panic(fmt.Sprintf("syscall.Read failed: %v", err))
	}

	result := string(readBuffer[:bytesRead])
	fmt.Printf("Read %d bytes from FD %d: %q\n", bytesRead, fd, result)
}
```

## Под капотом

Что происходит в ядре Linux при работе с файловыми дескрипторами:
1. Вызов `open` аллоцирует запись в `struct files_struct` текущего процесса. Возвращается минимальный свободный целочисленный индекс (начиная с 3, так как 0=stdin, 1=stdout, 2=stderr).
2. Запись в таблице указывает на структуру `struct file` в памяти ядра, содержащую:
   - `f_pos`: Текущее смещение указателя в файле (64-битный счетчик).
   - `f_inode`: Указатель на метаданные файла (inode).
   - `f_op`: Таблица указателей на функции файловой системы (`read`, `write`, `llseek`).
3. Вызов `syscall.Seek(fd, offset, 0)` изменяет значение `f_pos` напрямую в ядре без дискового I/O.
4. Вызов `syscall.Close(fd)` удаляет запись из таблицы дескрипторов процесса и уменьшает счетчик ссылок `f_count` структуры `struct file`. Если счетчик равен 0, ядро освобождает ресурсы.

## Подводные камни

1. **Утечка файловых дескрипторов (FD Leak)**: Если не вызвать `syscall.Close(fd)`, дескрипторы накапливаются в процессе. При достижении системного лимита `ulimit -n` (обычно 1024 по умолчанию) любой последующий вызов `open`, `accept` или `socket` завершится ошибкой `EMFILE: too many open files`.
2. **Забытый Seek перед чтением**: После вызова `Write` файловый указатель смещается в конец записанных данных. Если попытаться вызвать `Read` без предварительного `Seek(fd, 0, 0)`, `Read` вернет `0` байт (EOF), создавая ложное впечатление, что файл пуст.
3. **Неатомарность чтения/записи в многопоточной среде**: Файловый дескриптор хранит единый указатель смещения `f_pos`. Если две горутины пишут в один дескриптор параллельно, их вызовы `Write` и `Seek` перемешаются, испортив данные. Для параллельного доступа используют `syscall.Pread` / `syscall.Pwrite`.

## На собеседовании

**Вопрос с собеседования:** «Чем отличаются системные вызовы `read`/`write` от `pread`/`pwrite` и почему высоконагруженные СУБД предпочитают вторые?»
**Ответ:**
1. `read(fd, buf, len)` и `write(fd, buf, len)` используют и изменяют общий файловый указатель смещения `f_pos`, защищенный мьютексом ядра (`f_pos_lock`). Это порождает межпоточный lock contention при параллельном чтении из файла.
2. `pread(fd, buf, len, offset)` и `pwrite(fd, buf, len, offset)` принимают явное смещение `offset` в качестве аргумента. Они не изменяют и не используют `f_pos`, что позволяет десяткам потоков или горутин безопасно и параллельно читать разные страницы одного файла базы данных без блокировок ядра.
