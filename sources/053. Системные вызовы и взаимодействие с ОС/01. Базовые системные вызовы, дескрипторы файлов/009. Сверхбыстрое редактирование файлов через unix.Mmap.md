# Сверхбыстрое редактирование файлов через unix.Mmap с флагом MAP_SHARED без вызовов Write

## Условие

**[mmap — Memory Mapped Files]**: Открой файл. Используй `unix.Mmap(fd, 0, length, unix.PROT_READ|unix.PROT_WRITE, unix.MAP_SHARED)`. Измени байты прямо в возвращенном слайсе `[]byte`. Вызови `unix.Munmap(b)`. Открой файл в редакторе — изменения должны быть сохранены на диск без вызова `Write`.

## Теория

Флаг `MAP_SHARED` в системном вызове `mmap` создает разделяемое отображение:
1. Изменения, вносимые в буфер памяти, становятся мгновенно видимыми всем остальным процессам, отобразившим этот же файл в память.
2. Ядро Linux автоматически синхронизирует измененные страницы памяти с файловой системой при вызове `munmap()`, периодическом сбросе демоном `kswapd`/`pdflush` или закрытии процесса.

**Механика работы без системного вызова `write`**:
- При записи данных через обычный срез Go `slice[i] = 0x58` процессор выполняет стандартную инструкцию ассемблера `MOV [RAX + RCX], DL`.
- Никакого переключения контекста User Space -> Kernel Space в момент записи не происходит. Это в десятки раз быстрее вызова функции `write()`.
- Аппаратный модуль управления памятью процессора (MMU) отмечает бит `Dirty` в дескрипторе страницы таблицы PTE.
- Вызов `Munmap(slice)` освобождает диапазон адресов виртуальной памяти, инициируя обратную запись грязных страниц в дисковый кэш.

## Решение по шагам

1. Создайте текстовый файл фиксированной длины (например, 64 байта) на диске.
2. Откройте файл через `syscall.Open(path, syscall.O_RDWR, 0666)`.
3. Получите точный размер файла через `syscall.Fstat(fd, &stat)`.
4. Отобразите файл в память: `buf, err := syscall.Mmap(fd, 0, int(stat.Size), syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_SHARED)`.
5. Измените байты среза на месте (in-place modification).
6. Вызовите `syscall.Munmap(buf)` и `syscall.Close(fd)`.
7. Прочитайте файл обычным способом с диска и убедитесь, что модификация сохранилась без единого вызова `write`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	fileName := "mmap_shared_demo.txt"
	initialText := "HEADER: [UNTOUCHED_STATUS] | COUNTER: 0000 | TAIL: OK"

	if err := os.WriteFile(fileName, []byte(initialText), 0644); err != nil {
		panic(err)
	}
	defer os.Remove(fileName)

	// 1. Открываем файл для чтения и записи
	fd, err := syscall.Open(fileName, syscall.O_RDWR, 0666)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(fd)

	// 2. Определяем размер файла
	var stat syscall.Stat_t
	if err := syscall.Fstat(fd, &stat); err != nil {
		panic(err)
	}
	fileLen := int(stat.Size)

	// 3. Вызываем mmap с флагом MAP_SHARED
	mmapBytes, err := syscall.Mmap(
		fd,
		0,
		fileLen,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Before edit via mmap: %s\n", string(mmapBytes))

	// 4. Изменяем байты прямо в слайсе Go (чистые процессорные инструкции MOV)
	newStatus := []byte("ACTIVE_MODIFIED_")
	copy(mmapBytes[9:25], newStatus)

	counter := []byte("9999")
	copy(mmapBytes[38:42], counter)

	// 5. Размонтируем память - ядро гарантирует сброс dirty страниц в Page Cache
	if err := syscall.Munmap(mmapBytes); err != nil {
		panic(err)
	}
	fmt.Println("Memory unmapped successfully via syscall.Munmap.")

	// 6. Читаем файл с диска сторонним вызовом
	updatedDiskContent, err := os.ReadFile(fileName)
	if err != nil {
		panic(err)
	}

	fmt.Printf("After edit (from disk): %s\n", string(updatedDiskContent))
}
```

ℹ️ In-place редактирование дискового файла без вызовов write через MAP_SHARED и Munmap

**`Терминал`**

```bash
go run main.go
# Вывод:
# Before edit via mmap: HEADER: [UNTOUCHED_STATUS] | COUNTER: 0000 | TAIL: OK
# Memory unmapped successfully via syscall.Munmap.
# After edit (from disk): HEADER: [ACTIVE_MODIFIED_] | COUNTER: 9999 | TAIL: OK
```

## Под капотом

Что происходит при размонтировании памяти `syscall.Munmap`:
1. Ядро Linux находит соответствующую структуру `vm_area_struct`.
2. Ядро проверяет биты `PTE_DIRTY` в таблицах страниц процесса. Страницы с выставленным битом помечаются как `PageDirty` в глобальном кэше страниц (Page Cache).
3. Виртуальные адреса удаляются из дерева адресного пространства процесса, освобождая адресный диапазон.
4. Фоновые потоки ядра (`flusher threads` / `writeback`) асинхронно сбрасывают измененные страницы Page Cache на физический диск блоками по 4 КБ.
5. Если в этот момент произойдет аварийное отключение питания сервера до сброса Page Cache контроллером диска, данные могут быть потеряны. Для 100% гарантии долговечности (Durability) перед `Munmap` вызывают `Msync(MS_SYNC)`.

## Подводные камни

1. **Изменение размера файла через слайс `mmap`**: Нельзя увеличить размер файла с диска, просто сделав `append()` к mmap-слайсу. Попытка записи за пределы первоначального `fileLen` вызовет сигнал `SIGBUS`. Чтобы увеличить файл, необходимо предварительно вызвать `syscall.Ftruncate(fd, newSize)`, и лишь затем пересоздать `mmap`.
2. **Флаги открытия файла**: Если файл открыт в режиме `O_RDONLY`, а в `mmap` передан `PROT_WRITE`, ядро вернет ошибку `EACCES` (Permission Denied). Режимы открытия дескриптора и защиты страниц обязаны совпадать.
3. **Обращение к слайсу после `Munmap`**: Вызов `Munmap` инвалидирует страницы памяти. Любое последующее чтение или запись в этот срез вызовет немедленный `SIGSEGV`.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между `syscall.Msync` с флагом `MS_ASYNC` и `MS_SYNC`?»
**Ответ:**
- `MS_ASYNC`: Инициирует сброс dirty-страниц в очередь планировщика ввода-вывода ядра и возвращает управление **немедленно**. Операция не блокирует горутину, но не дает гарантии, что данные физически записаны на диск на момент возврата.
- `MS_SYNC`: Блокирует поток выполнения до тех пор, пока контроллер накопителя (SSD/HDD) не подтвердит физическую запись всех измененных страниц. Гарантирует соблюдение требования Durability в ACID-транзакциях баз данных, но работает на несколько порядков медленнее.
