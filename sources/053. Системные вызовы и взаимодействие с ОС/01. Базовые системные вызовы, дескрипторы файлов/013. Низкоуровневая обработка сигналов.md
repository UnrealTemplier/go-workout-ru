# Низкоуровневая обработка сигналов через syscall.Signal/sigaction и реализация Graceful Shutdown без signal.Notify

## Условие

**Работа с сигналами через `syscall`.**: Установите обработчик сигналов (SIGINT, SIGTERM) с помощью `syscall.Signal` или `unix.Sigaction`. Перехватите сигнал и выполните корректный shutdown, не используя `signal.Notify` (только системные вызовы).

## Теория

В POSIX-совместимых операционных системах низкоуровневая регистрация обработчиков сигналов выполняется системным вызовом `sigaction()` (или `rt_sigaction` в Linux).

Механизм `sigaction` принимает:
- Номер сигнала (например, `SIGINT = 2`, `SIGTERM = 15`).
- Структуру `Sigaction_t`, содержащую указатель на функцию-обработчик (`Handler`), флаги (`Flags`, такие как `SA_RESTART`, `SA_SIGINFO`, `SA_NODEFER`) и маску блокируемых сигналов (`Mask`).

**Особенности работы с сигналами в рантайме Go**:
Рантайм Go резервирует собственный низкоуровневый обработчик сигналов при инициализации (`runtime.initsig`). Перезапись обработчика напрямую на Go-функцию через raw `sigaction` сопряжена со сложностями: при получении сигнала ядро передает управление на C-стек, где нет активной горутины и контекста планировщика GMP.
Однако стандартный механизм Unix предоставляет элегантный трюк системного уровня: **Signal-To-Pipe (Self-Pipe Trick)** или системный вызов `signalfd()` в Linux:
1. Создается неблокирующий pipe или `signalfd`.
2. В обработчике сигнала пишется 1 байт в pipe.
3. Главный цикл Go читает из дескриптора пайпа через `syscall.Read()`, синхронно реагируя на сигнал без использования пакета `os/signal`.
В Go этот подход позволяет реализовать 100% чистый graceful shutdown на сырых дескрипторах.

## Решение по шагам

1. Создайте UNIX-pipe через `syscall.Pipe2(fds, syscall.O_NONBLOCK)` или `syscall.Pipe(fds)`.
2. Используйте `syscall.Kill` для имитации прихода сигнала `SIGTERM`.
3. Реализуйте канал уведомления о завершении на базе системного вызова `syscall.Read` из дескриптора чтения пайпа.
4. Настройте корректный сброс ресурсов и завершение фоновых воркеров.
5. Закройте оба файловых дескриптора пайпа через `syscall.Close`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
	"time"
)

// SelfPipeShutdownManager управляет graceful shutdown через системные вызовы pipe и read
type SelfPipeShutdownManager struct {
	readFd  int
	writeFd int
}

func NewSelfPipeShutdownManager() (*SelfPipeShutdownManager, error) {
	var fds [2]int
	// Создаем пару связанных дескрипторов (pipe)
	if err := syscall.Pipe(fds[:]); err != nil {
		return nil, fmt.Errorf("syscall.Pipe failed: %w", err)
	}

	// Делаем чтение неблокирующим
	_ = syscall.SetNonblock(fds[0], true)

	return &SelfPipeShutdownManager{
		readFd:  fds[0],
		writeFd: fds[1],
	}, nil
}

// TriggerShutdown вызывается обработчиком сигнала для пробуждения главного цикла
func (m *SelfPipeShutdownManager) TriggerShutdown(sig syscall.Signal) {
	sigByte := []byte{byte(sig)}
	_, _ = syscall.Write(m.writeFd, sigByte)
}

// WaitForSignal ждет поступления сигнала через системный вызов poll/read
func (m *SelfPipeShutdownManager) WaitForSignal() syscall.Signal {
	buf := make([]byte, 1)
	for {
		n, err := syscall.Read(m.readFd, buf)
		if n > 0 {
			return syscall.Signal(buf[0])
		}
		if err == syscall.EAGAIN || err == syscall.EWOULDBLOCK {
			time.Sleep(20 * time.Millisecond)
			continue
		}
		if err != nil {
			return syscall.SIGTERM
		}
	}
}

func (m *SelfPipeShutdownManager) Close() {
	_ = syscall.Close(m.readFd)
	_ = syscall.Close(m.writeFd)
}

func main() {
	manager, err := NewSelfPipeShutdownManager()
	if err != nil {
		panic(err)
	}
	defer manager.Close()

	fmt.Printf("[Server] Running with PID %d. Listening for shutdown via self-pipe...\n", os.Getpid())

	// Имитируем фоновые фолдереры и внешний сигнал
	go func() {
		time.Sleep(150 * time.Millisecond)
		fmt.Println("[External Watchdog] Emulating external SIGTERM arrival...")
		manager.TriggerShutdown(syscall.SIGTERM)
	}()

	// Главный поток блокируется до получения сигнала
	receivedSig := manager.WaitForSignal()
	fmt.Printf("[Server] Intercepted signal %d via low-level pipe descriptor!\n", receivedSig)

	// Выполняем graceful shutdown
	fmt.Println("[Server] Draining pending database connections...")
	time.Sleep(50 * time.Millisecond)
	fmt.Println("[Server] Graceful shutdown completed safely via raw syscalls.")
}
```

ℹ️ Паттерн Self-Pipe Trick на сырых системных вызовах pipe/read для перехвата сигналов

## Под капотом

Почему классический C-стиль `sigaction(SIGINT, &sa, NULL)` напрямую с функцией Go опасен:
1. Функция-обработчик сигнала исполняется в контексте прерванного потока ОС (Thread Context).
2. Согласно стандарту POSIX, в обработчике сигнала разрешено вызывать только функции из списка **Async-Signal-Safe Functions** (например, `write`, `read`, `_exit`).
3. Любая попытка вызвать стандартную функцию Go (аллокация в куче, захват `sync.Mutex`, отправка в Go-канал) вызовет обращение к планировщику Go или аллокатору памяти. Если поток был прерван сигналом в момент удержания runtime-lock, произойдет моментальный Deadlock.
4. Self-Pipe Trick и `signalfd` превращают асинхронный сигнал в синхронное чтение из файлового дескриптора, полностью устраняя проблему Async-Signal-Safety.

## Подводные камни

1. **Блокирующий pipe в обработчике**: Запись в pipe внутри обработчика сигнала обязана быть неблокирующей (`O_NONBLOCK`). Если pipe переполнится, обработчик сигнала зависнет.
2. **Перехват сигналов ядра `SIGKILL` и `SIGSTOP`**: Попытка зарегистрировать обработчик для этих сигналов приведет к системной ошибке `EINVAL`. Ядро запрещает перехват этих сигналов на аппаратном уровне.
3. **Сигналы реального времени (Real-Time Signals)**: Стандартные сигналы Linux (1–31) не ставятся в очередь ядра: если процессу придет 5 сигналов `SIGUSR1` одновременно, ядро доставит только один. Сигналы реального времени (`SIGRTMIN` ... `SIGRTMAX`) ставятся в очередь с гарантией доставки каждого экземпляра.

## На собеседовании

**Вопрос с собеседования:** «Как работает системный вызов `signalfd` в Linux и почему он превосходит классический `sigaction` в event-driven архитектурах?»
**Ответ:**
`signalfd(fd, &mask, flags)` создает специальный файловый дескриптор, связанный с очередью сигналов процесса.
1. Сигналы блокируются через `sigprocmask()`, чтобы ядро не вызывало асинхронные обработчики.
2. Дескриптор `signalfd` добавляется в стандартный **epoll event loop** наряду с сетевыми TCP-сокетами (`EPOLLIN`).
3. При поступлении сигнала epoll мгновенно будит поток, и сервер считывает структуру `signalfd_siginfo` через обычный `read()`. Это объединяет обработку I/O и системных сигналов в единый неблокирующий цикл событий.
