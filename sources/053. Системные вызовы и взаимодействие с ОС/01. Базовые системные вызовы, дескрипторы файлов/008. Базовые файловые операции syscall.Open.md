# Базовые файловые операции syscall.Open, syscall.Read, syscall.Close и обработка EOF

## Условие

**File operations**: Откройте файл через `syscall.Open()`, прочитайте через `syscall.Read()`, закройте через `syscall.Close()`.

## Теория

При работе на уровне системных вызовов разработчик напрямую сталкивается с контрактами ядра операционной системы POSIX.

**Семантика системного вызова `read`**:
```go
n, err := syscall.Read(fd int, p []byte)
```
1. Если `n > 0`: Ядро успешно прочитало `n` байт и поместило их в буфер `p`. Значение `n` может быть строго меньше `len(p)` (например, если до конца файла осталось меньше байт или при чтении из сети/пайпа).
2. Если `n == 0` и `err == nil`: **End of File (EOF)**. Файловый указатель достиг конца файла. Обратите внимание: в отличие от метода `io.Reader.Read()` в Go, который возвращает ошибку `io.EOF`, низкоуровневый `syscall.Read` возвращает `err = nil` и `n = 0`!
3. Если `n == -1` (в Go `n == 0` и `err != nil`): Произошла ошибка ядра (`syscall.Errno`).

**Типичные коды ошибок файловых вызовов (`syscall.Errno`)**:
- `ENOENT` (2): No such file or directory (файл или директория не существует).
- `EACCES` (13): Permission denied (нет прав на чтение/запись).
- `EBADF` (9): Bad file descriptor (попытка чтения из невалидного или закрытого дескриптора).
- `EINTR` (4): Interrupted system call (вызов прерван сигналом ОС, требуется повторить операцию).

## Решение по шагам

1. Создайте файл на диске с тестовыми данными.
2. Откройте файл только для чтения: `fd, err := syscall.Open(path, syscall.O_RDONLY, 0)`.
3. Обязательно проверьте `err != nil`.
4. Организуйте цикл чтения фиксированными порциями (чанками) по 16 байт: `n, err := syscall.Read(fd, chunk)`.
5. Обработайте условие `n == 0` как достижение конца файла (EOF) и прервите цикл.
6. Аккумулируйте прочитанные байты.
7. Закройте дескриптор через `syscall.Close(fd)`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

// ReadEntireFileViaSyscall считывает файл полностью через сырые системные вызовы
func ReadEntireFileViaSyscall(path string) ([]byte, error) {
	// Открываем дескриптор в режиме Read-Only
	fd, err := syscall.Open(path, syscall.O_RDONLY, 0)
	if err != nil {
		return nil, fmt.Errorf("open failed: %w", err)
	}
	defer func() {
		_ = syscall.Close(fd)
	}()

	var content []byte
	chunk := make([]byte, 16) // Читаем небольшими порциями для демонстрации цикла

	for {
		n, err := syscall.Read(fd, chunk)
		if err != nil {
			// Если вызов был прерван сигналом ядра, пробуем снова
			if err == syscall.EINTR {
				continue
			}
			return nil, fmt.Errorf("read failed: %w", err)
		}

		// n == 0 при err == nil означает чистый POSIX EOF
		if n == 0 {
			break
		}

		content = append(content, chunk[:n]...)
	}

	return content, nil
}

func main() {
	testFile := "syscall_read_demo.txt"
	originalText := "Linux System Calls Masterclass: Raw POSIX File Descriptors in Go!"

	if err := os.WriteFile(testFile, []byte(originalText), 0644); err != nil {
		panic(err)
	}
	defer os.Remove(testFile)

	data, err := ReadEntireFileViaSyscall(testFile)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Successfully read %d bytes via raw syscall.Read:\n%s\n", len(data), string(data))

	// Демонстрация ошибки ENOENT (файл не найден)
	_, errMissing := ReadEntireFileViaSyscall("non_existent_file_999.xyz")
	if errMissing != nil {
		fmt.Printf("Expected error caught: %v\n", errMissing)
	}
}
```

ℹ️ Полноценный цикл чтения файла с обработкой EINTR, частичных чтений и POSIX EOF

## Под капотом

Что происходит при чтении из файла:
1. `syscall.Read` передает в ядро дескриптор `fd`, адрес буфера в пользовательской памяти и его размер.
2. Ядро проверяет права доступа дескриптора на чтение (`f_mode & FMODE_READ`).
3. Ядро обращается к кэшу страниц (Page Cache) inode файла. Если запрашиваемые страницы уже находятся в оперативной памяти (cache hit), ядро копирует данные из памяти ядра в буфер Go с помощью процессорной инструкции `rep movsb` (copy_to_user).
4. Если страниц в памяти нет (cache miss), ядро инициирует асинхронный блочный запрос к диску через драйвер накопителя, а текущий поток `M` переводится в состояние сна (Uninterruptible Sleep `D`), пока контроллер диска не пришлет аппаратное прерывание о готовности данных.
5. `sysmon` в Go детектирует длительное блокирование потока `M` и отцепляет процессор `P`.

## Подводные камни

1. **Ожидание ошибки `io.EOF` от `syscall.Read`**: Ошибка `io.EOF` генерируется пакетом `io` в стандартной библиотеке Go. Нативный `syscall.Read` возвращает `n = 0` и `err = nil`. Проверка `if err == io.EOF` никогда не сработает и приведет к бесконечному циклу зависания программы.
2. **Игнорирование `syscall.EINTR`**: При получении любого сигнала операционной системы (например, таймера или `SIGWINCH`) блокирующий системный вызов прерывается с ошибкой `EINTR`. Программа обязана повторить вызов, а не считать это фатальной ошибкой.
3. **Double Close Bug**: Повторный вызов `syscall.Close(fd)` на уже закрытом дескрипторе может закрыть дескриптор, который ядро только что перевыделило в другой горутине для нового сетевого соединения.

## На собеседовании

**Вопрос с собеседования:** «Почему повторное закрытие одного и того же файлового дескриптора (Double Close) считается критической уязвимостью в многопоточных сервисах?»
**Ответ:**
Файловые дескрипторы — это просто целые числа, которые ядро переиспользует по принципу минимального свободного номера:
1. Горутина А открывает сокет `fd = 5`.
2. Горутина А закрывает `fd = 5`.
3. В этот же момент Горутина Б открывает файл БД или платежный сокет, и ядро выделяет освободившийся `fd = 5`.
4. Горутина А из-за бага повторно вызывает `Close(5)`.
5. В результате закрывается совершенно чужой сокет Горутины Б. Горутина Б пытается писать в сокет, получает ошибку или пишет в дескриптор, который ядро успело перевыделить в третий раз. Это приводит к тихой порче данных и уязвимостям безопасности.
