# Создание дочерних процессов через syscall.ForkExec, clone() и безопасность fork в многопоточном рантайме

## Условие

**Process creation**: Создайте дочерний процесс через `syscall.ForkExec()` (или `syscall.Clone()` на Linux).

## Теория

В операционных системах Unix создание нового процесса традиционно выполняется в два этапа:
1. `fork()`: Клонирует текущий процесс (создает точную копию адресного пространства, дескрипторов и регистров через механизм Copy-On-Write).
2. `execve()`: Заменяет текущий образ процесса новым исполняемым файлом.

**Фундаментальная проблема `fork()` в многопоточном Go**:
Согласно стандарту POSIX, системный вызов `fork()` в многопоточном процессе копирует **только тот поток**, который вызвал `fork()`. Все остальные потоки ОС (потоки `M` планировщика Go, поток GC, sysmon) в дочернем процессе просто **исчезают**.
Если в момент `fork()` другой поток Go удерживал внутренний мьютекс (например, блокировку аллокатора `mheap` или runtime lock), в дочернем процессе этот мьютекс навсегда останется в заблокированном состоянии, что приведет к немедленному взаимному зависанию (deadlock).

**Решение в Go: `syscall.ForkExec` / `clone()`**:
Для безопасного создания процессов Go использует системный вызов ядра Linux `clone()` с флагами `CLONE_VFORK | CLONE_VM` или специальный ассемблерный трамплин `runtime.forkAndExecInChild`:
1. Родительский процесс приостанавливается до тех пор, пока дочерний процесс не выполнит `execve()` или не завершится.
2. Память не копируется, что обеспечивает мгновенное создание дочернего процесса даже при занятых гигабайтах оперативной памяти.
3. Дочерний процесс немедленно заменяет свой образ через `SYS_EXECVE`.

## Решение по шагам

1. Укажите абсолютный путь к исполняемому файлу (например, `/bin/echo` или `/usr/bin/id`).
2. Сформируйте массив аргументов `argv` (нулевой аргумент — имя программы).
3. Настройте атрибуты процесса `syscall.ProcAttr`: рабочая директория, переменные окружения `Env`, маппинг файловых дескрипторов `Files` (stdin=0, stdout=1, stderr=2).
4. Вызовите `pid, err := syscall.ForkExec(binaryPath, args, &procAttr)`.
5. Дождитесь завершения дочернего процесса с помощью `syscall.Wait4(pid, &wstatus, 0, nil)`.
6. Проверьте код завершения процесса `wstatus.ExitStatus()`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	// Путь к исполняемому бинарнику
	binaryPath := "/bin/echo"

	// Аргументы процесса: argv[0] по соглашению имя программы
	args := []string{"echo", "[Child Process] Executed safely via syscall.ForkExec!"}

	// Настройка дескрипторов ввода-вывода (пробрасываем stdout и stderr родителя)
	procAttr := syscall.ProcAttr{
		Dir: "/",
		Env: os.Environ(),
		Files: []uintptr{
			uintptr(syscall.Stdin),  // fd 0
			uintptr(syscall.Stdout), // fd 1
			uintptr(syscall.Stderr), // fd 2
		},
	}

	fmt.Printf("[Parent Process] Current PID: %d. Spawning child process...\n", os.Getpid())

	// Запуск дочернего процесса через ForkExec
	childPid, err := syscall.ForkExec(binaryPath, args, &procAttr)
	if err != nil {
		panic(fmt.Sprintf("syscall.ForkExec failed: %v", err))
	}

	fmt.Printf("[Parent Process] Spawned Child PID: %d. Waiting for completion...\n", childPid)

	// Ожидаем завершения дочернего процесса через syscall.Wait4
	var waitStatus syscall.WaitStatus
	var rusage syscall.Rusage

	wpid, err := syscall.Wait4(childPid, &waitStatus, 0, &rusage)
	if err != nil {
		panic(fmt.Sprintf("syscall.Wait4 failed: %v", err))
	}

	fmt.Printf("[Parent Process] Child PID %d exited. Exit Status: %d\n", wpid, waitStatus.ExitStatus())
	fmt.Printf("User CPU time consumed by child: %v\n", rusage.Utime.Nano())
}
```

```bash

# Вывод:

# [Parent Process] Spawned Child PID: 31205. Waiting for completion...
```

## Под капотом

Что происходит внутри `runtime.forkAndExecInChild`:
1. Функция написана на чистом ассемблере без аллокаций памяти и вызовов функций рантайма Go.
2. Вызывается `SYS_CLONE` с флагами `CLONE_VFORK | CLONE_VM | SIGCHLD`.
3. Дочерний процесс временно делит адресное пространство родителя, а родитель блокируется ядром на аппаратном уровне.
4. Дочерний поток перенастраивает файловые дескрипторы через `SYS_DUP3` и закрывает лишние (`close-on-exec`).
5. Вызывается `SYS_EXECVE`. Ядро полностью заменяет адресное пространство дочернего процесса новым бинарником, после чего родительский процесс разблокируется и продолжает работу.
6. При завершении процесса ядро отправляет родителю сигнал `SIGCHLD`.

## Подводные камни

1. **Процессы-зомби (Zombie Processes)**: Если дочерний процесс завершится, а родитель не вызовет `syscall.Wait4()` (или `cmd.Wait()`), дескриптор завершенного процесса останется в таблице процессов ядра со статусом `Z` (Zombie). Зомби-процессы занимают слоты в таблице PID ядра (`/proc/sys/kernel/pid_max`).
2. **Утечка открытых файловых дескрипторов**: По умолчанию дочерний процесс наследует открытые дескрипторы родителя (файлы, сокеты, соединения с БД). Все дескрипторы в Go открываются с флагом `O_CLOEXEC` (`FD_CLOEXEC`), чтобы они автоматически закрывались при `execve`.
3. **Ошибки PATH resolution**: `syscall.ForkExec` требует **абсолютный путь** к исполняемому файлу (`/bin/echo`, а не просто `echo`). Поиск файла по переменной окружения `PATH` должен выполняться предварительно (например, через `exec.LookPath`).

## На собеседовании

**Вопрос с собеседования:** «Почему вызов `exec.Command` в огромном процессе на Go (потребляющем 50 ГБ RAM) не вызывает ошибку `ENOMEM: Cannot allocate memory`, в то время как аналогичный скрипт на Python/Ruby может уронить сервер по OOM?»
**Ответ:**
Классический `fork()` в Python/Ruby создает виртуальную копию таблиц страниц процесса. Если у процесса занято 50 ГБ, ядро проверяет наличие свободной памяти для клонирования структур и при строгом `vm.overcommit_memory = 2` завершает `fork()` с ошибкой `ENOMEM`.
Go не использует чистый `fork()`. Go использует `vfork()` / `CLONE_VFORK | CLONE_VM`, который вообще не дублирует таблицы страниц памяти родителя, а сразу выполняет `execve`. Это гарантирует мгновенный старт дочернего процесса независимо от объема памяти, занятого родительским процессом Go.
