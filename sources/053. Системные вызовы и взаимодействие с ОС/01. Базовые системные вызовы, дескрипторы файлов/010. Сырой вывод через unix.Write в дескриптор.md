# Сырой вывод через unix.Write в дескриптор unix.Stdout и атомарность операций вывода

## Условие

**Сырой Write (Без пакета `fmt`)**: Напиши "Hello, OS!" в консоль, используя только функцию `unix.Write(unix.Stdout, []byte("..."))`. Ты обращаешься напрямую к файловому дескриптору `1` (STDOUT).

## Теория

Файловый дескриптор `1` (`syscall.Stdout` / `unix.Stdout`) в POSIX-системах представляет стандартный поток вывода процесса.

Когда процесс запускается в оболочке bash:
- Дескриптор 1 по умолчанию ассоциирован с символьным псевдотерминалом (`/dev/pts/X` или `/dev/tty`).
- Если пользователь перенаправляет вывод (`./app > output.txt`), дескриптор 1 связывается с регулярным файлом на файловой системе.
- Если вывод перенаправлен в канал (`./app | grep foo`), дескриптор 1 связывается с анонимным пайпом (pipe).

**Преимущества прямого обращения к `syscall.Stdout`**:
1. Полное отсутствие накладных расходов на создание объектов Go (zero-alloc).
2. Независимость от структуры `os.File`, не требующая аллокаций в куче для runtime финализаторов.
3. Возможность вывода отладочных сообщений в критических секциях рантайма (например, обработчики сигналов, паники, низкоуровневые хуки), где высокоуровневые пакеты `fmt` или `log` могут вызвать взаимную блокировку (deadlock) мьютексов.

## Решение по шагам

1. Подготовьте байтовый срез `data := []byte("Hello, OS!\n")`.
2. Используйте константу `syscall.Stdout` (равную `1`).
3. Вызовите `syscall.Write(syscall.Stdout, data)`.
4. Реализуйте проверку частичной записи (partial write loop) на случай сигналов или переполнения tty-буфера.
5. Проверьте код завершения.

## Код решения

**`main.go`**

```go
package main

import (
	"syscall"
)

// SafeRawWrite гарантирует полную запись буфера в указанный файловый дескриптор
func SafeRawWrite(fd int, payload []byte) error {
	total := 0
	for total < len(payload) {
		n, err := syscall.Write(fd, payload[total:])
		if err != nil {
			if err == syscall.EINTR {
				continue // Повторяем при прерывании сигналом
			}
			return err
		}
		total += n
	}
	return nil
}

func main() {
	// Обращаемся напрямую к файловому дескриптору 1 (STDOUT)
	message := []byte("Hello, OS!\n")

	if err := SafeRawWrite(syscall.Stdout, message); err != nil {
		// В случае ошибки пишем в дескриптор 2 (STDERR)
		errMsg := []byte("Failed to write to stdout\n")
		_ = SafeRawWrite(syscall.Stderr, errMsg)
	}

	// Вывод многострочного отчета без единого импорта fmt или os
	report := []byte("System Information:\n- Direct FD: 1\n- Zero Allocation: true\n- Ring 0 Transition: sys_write\n")
	_ = SafeRawWrite(syscall.Stdout, report)
}
```

ℹ️ Прямая запись сообщения 'Hello, OS!' в дескриптор 1 без пакетов fmt и os

**`Терминал`**

```bash
go run main.go
# Вывод:
# Hello, OS!
# System Information:
# - Direct FD: 1
# - Zero Allocation: true
# - Ring 0 Transition: sys_write
```

## Под капотом

Что происходит при вызове `syscall.Write(1, ...)` в консоли:
1. Системный вызов `sys_write` передает данные драйверу терминала tty (Line Discipline).
2. Драйвер tty обрабатывает специальные символы (перевод строк `\n` -> `\r\n`, обработка клавиш, ANSI escape последовательности).
3. Драйвер помещает байты в кольцевой буфер вывода tty.
4. Эмулятор терминала (GNOME Terminal, Alacritty, xterm) читает эти байты через парный дескриптор мастер-стороны псевдотерминала (`/dev/ptmx`) и отрисовывает символы с помощью графической подсистемы (GPU/OpenGL/Wayland).

## Подводные камни

1. **Блокировка на заполненном пайпе**: Если стандартный вывод направлен в pipe, а читатель перестал читать, емкость буфера пайпа (обычно 64 КБ в Linux) заполнится. Вызов `syscall.Write(1, ...)` заблокирует горутину и поток ОС до тех пор, пока буфер не освободится.
2. **Отсутствие потокобезопасности порядка строк**: Если две горутины вызывают `syscall.Write(1, ...)` параллельно с длинными строками (> PIPE_BUF), символы двух сообщений могут перемешаться в консоли. Для предотвращения этого требуется сериализация через мьютекс или каналы.
3. **Hardcoded дескриптор `1`**: В даемонизированных процессах (systemd daemon / background service) дескрипторы 0, 1, 2 часто закрываются или перенаправляются в `/dev/null`. Прямая запись без проверки может приводить к ошибке `EBADF`.

## На собеседовании

**Вопрос с собеседования:** «Почему запись в дескриптор `1` (Stdout) в Docker-контейнерах Kubernetes может стать причиной резкого падения пропускной способности сервиса?»
**Ответ:**
В Kubernetes и Docker весь вывод в `stdout` и `stderr` перехватывается демоном контейнеризации (containerd / dockerd) через pipe/pty и сохраняется в JSON-лог файлы на хост-ноде (`/var/log/pods/...`).
Если сервис пишет в stdout сотни тысяч логов в секунду:
1. Заполняются буферы пайпов ядра Linux.
2. Возникает backpressure: системные вызовы `write(1, ...)` начинают блокироваться на дисковом I/O демона dockerd.
3. В приложении кончаются свободные потоки `M`, наступает деградация латентности API (p99 latency spikes).
