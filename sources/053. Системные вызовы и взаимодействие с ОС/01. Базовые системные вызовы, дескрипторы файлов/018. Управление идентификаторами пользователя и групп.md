# Управление идентификаторами пользователя и групп: syscall.Getuid, Getgid, Geteuid, Getegid

## Условие

**User/Group ID**: Получите UID/GID текущего процесса через `syscall.Getuid()`, `syscall.Getgid()`.

## Теория

Модель безопасности POSIX базируется на идентификаторах пользователей и групп:

1. **Real UID / Real GID (`Getuid()`, `Getgid()`)**:
   - Реальный идентификатор пользователя и группы, от имени которого был запущен процесс (например, пользователь `1000` в терминале).
   - Определяет, кто является фактическим владельцем процесса и кто имеет право отправлять ему сигналы (`kill`).
2. **Effective UID / Effective GID (`Geteuid()`, `Getegid()`)**:
   - **Эффективный** идентификатор пользователя и группы.
   - Именно эффективный UID используется ядром Linux для **проверки прав доступа** к файлам, сокетам и системным ресурсам при вызовах `open()`, `read()`, `write()`.
   - Обычно Real UID равен Effective UID. Однако, если исполняемый файл имеет специальный флаг **SetUID (SUID)** (как утилита `/usr/bin/passwd` или `sudo`), при запуске ядро устанавливает Effective UID равным владельцу файла (`root`, UID 0), наделяя обычного пользователя правами суперпользователя на время выполнения бинарника.

## Решение по шагам

1. Вызовите `syscall.Getuid()` для получения Real UID.
2. Вызовите `syscall.Getgid()` для получения Real GID.
3. Вызовите `syscall.Geteuid()` для получения Effective UID.
4. Вызовите `syscall.Getegid()` для получения Effective GID.
5. Получите список дополнительных групп через `syscall.Getgroups()`.
6. Проверьте, запущен ли процесс с привилегиями root (`euid == 0`).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	// 1. Получение Real идентификаторов
	realUID := syscall.Getuid()
	realGID := syscall.Getgid()

	// 2. Получение Effective идентификаторов
	effUID := syscall.Geteuid()
	effGID := syscall.Getegid()

	fmt.Println("=== POSIX USER & GROUP SECURITY CREDENTIALS ===")
	fmt.Printf("Real UID (ruid):      %d\n", realUID)
	fmt.Printf("Real GID (rgid):      %d\n", realGID)
	fmt.Printf("Effective UID (euid): %d\n", effUID)
	fmt.Printf("Effective GID (egid): %d\n", effGID)

	if effUID == 0 {
		fmt.Println("[SECURITY WARNING] Process is running with ROOT/SUPERUSER privileges!")
	} else {
		fmt.Printf("[SECURITY] Process is running as unprivileged user (UID %d)\n", effUID)
	}

	// 3. Получение дополнительных групп (Supplementary Groups)
	groups, err := syscall.Getgroups()
	if err != nil {
		panic(err)
	}
	fmt.Printf("Supplementary Groups (%d groups): %v\n", len(groups), groups)
}
```

## Под капотом

Как ядро проверяет права доступа:
1. В ядре каждому процессу соответствует структура `struct cred` (Credentials).
2. При вызове `open("protected.txt", O_RDWR)` ядро проверяет:
   - Если `cred->euid == 0`: Доступ разрешен безусловно (CAP_DAC_OVERRIDE).
   - Если `cred->euid == inode->i_uid`: Проверяются биты владельца файла (`User Permissions` rwx).
   - Если `cred->egid == inode->i_gid` или совпадает с одной из дополнительных групп `cred->group_info`: Проверяются биты группы (`Group Permissions` rwx).
   - Иначе: Проверяются биты остальных пользователей (`Other Permissions`).

## Подводные камни

1. **Смена UID в многопоточном Go (`setuid`)**: В Linux системный вызов `setuid()` традиционно изменяет UID **только для текущего потока ОС** (`task_struct`), а не для всего процесса! Если одна горутина вызовет `syscall.Setuid(1000)`, только один поток `M` сменит пользователя, а остальные потоки Go останутся `root`.
2. **Безопасный drop privileges в Go**: С версии Go 1.16 стандартная библиотека Go использует специальный механизм `syscall.AllThreadsSyscall` для отправки сигналов всем потокам `M` рантайма, гарантируя согласованную смену UID во всем процессе.
3. **Забытый сброс групп**: При сбросе привилегий с root на непривилегированного пользователя необходимо сбрасывать не только UID, но и список дополнительных групп через `syscall.Setgroups([]int{})`, иначе процесс сохранит права доступа к привилегированным группам (например, `docker` или `sudo`).

## На собеседовании

**Вопрос с собеседования:** «Почему запуск контейнеров в Kubernetes от пользователя `root` (UID 0) категорически запрещен политиками PodSecurityStandard (Restricted), даже если контейнер изолирован?»
**Ответ:**
1. Изоляция контейнеров в Linux строится на пространствах имен (Namespaces) и cgroups. Однако UID 0 внутри контейнера по умолчанию отображается на физический UID 0 (root) хостовой ноды ядра Linux.
2. При наличии малейшей уязвимости побега из контейнера (Container Escape CVE в ядре, монтирование сокета `/var/run/docker.sock` или хостовых директорий `/proc`, `/sys`) атакующий получает мгновенный неограниченный контроль над физическим сервером.
3. Стандарт требует явного указания директив `runAsNonRoot: true` и `runAsUser: 10001` в секции `securityContext` манифеста Pod.
