# Низкоуровневая отправка сигналов процессам через syscall.Kill и принудительное завершение SIGKILL

## Условие

**Низкоуровневая отправка сигналов ОС**: Напишите программу, которая отправляет сигнал процессам операционной системы с помощью низкоуровневого системного вызова `syscall.Kill`. Запустите параллельный процесс и принудительно завершите его, отправив сигнал `syscall.SIGKILL`.

## Теория

Системный вызов `kill(pid, sig)` в Linux:
- Вопреки названию («убить»), является универсальным системным интерфейсом **отправки произвольных межпроцессных сигналов**.
- `syscall.SIGKILL` (номер 9):
  - Безусловное немедленное завершение процесса ядром Linux.
  - Процесс **не может** перехватить, проигнорировать или заблокировать сигнал `SIGKILL`.
  - У процесса не вызываются обработчики `defer`, не закрываются соединения с базами данных, не сбрасываются буферы файлов. Ядро мгновенно отзывает все виртуальные страницы памяти, закрывает файловые дескрипторы и переводит процесс в статус Zombie до вызова `wait4()` родителем.

**Отслеживание статуса завершения через `syscall.Wait4`**:
```go
wpid, err := syscall.Wait4(pid, &waitStatus, 0, &rusage)
```
- Проверяет, был ли процесс завершен сигналом: `waitStatus.Signaled() == true`.
- Получает номер сигнала-убийцы: `waitStatus.Signal() == syscall.SIGKILL`.
- Считывает потребленные ресурсы CPU и памяти через структуру `syscall.Rusage`.

## Решение по шагам

1. Запустите фоновый дочерний процесс (например, команду `sleep 60`) с помощью `os/exec.Command`.
2. Получите PID дочернего процесса: `childPid := cmd.Process.Pid`.
3. Отправьте системный вызов `syscall.Kill(childPid, syscall.SIGKILL)`.
4. Дождитесь завершения через `syscall.Wait4(childPid, &wstatus, 0, nil)`.
5. Убедитесь, что `wstatus.Signaled()` возвращает `true`, а сигнал равен `SIGKILL`.
6. Выведите подробный отчет об уничтожении процесса.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os/exec"
	"syscall"
	"time"
)

func main() {
	// 1. Запускаем дочерний процесс, который должен уснуть на 60 секунд
	cmd := exec.Command("sleep", "60")
	if err := cmd.Start(); err != nil {
		panic(fmt.Sprintf("Failed to spawn target process: %v", err))
	}

	childPid := cmd.Process.Pid
	fmt.Printf("[Process Reaper] Spawned target process: PID %d (Running 'sleep 60')...\n", childPid)

	// Даем процессу инициализироваться в ядре
	time.Sleep(50 * time.Millisecond)

	// 2. Отправляем беспощадный системный сигнал SIGKILL (Signal 9) через syscall.Kill
	fmt.Printf("[Process Reaper] Sending raw syscall.Kill(PID: %d, SIGKILL)...\n", childPid)
	if err := syscall.Kill(childPid, syscall.SIGKILL); err != nil {
		panic(fmt.Sprintf("syscall.Kill failed: %v", err))
	}

	// 3. Собираем статус завершения через syscall.Wait4
	var waitStatus syscall.WaitStatus
	var rusage syscall.Rusage

	wpid, err := syscall.Wait4(childPid, &waitStatus, 0, &rusage)
	if err != nil {
		panic(fmt.Sprintf("syscall.Wait4 failed: %v", err))
	}

	fmt.Println("\n=== KERNEL PROCESS TERMINATION REPORT ===")
	fmt.Printf("Reaped PID:         %d\n", wpid)
	fmt.Printf("Exited normally:    %v\n", waitStatus.Exited())
	fmt.Printf("Signaled:           %v (Killed by OS signal)\n", waitStatus.Signaled())
	fmt.Printf("Termination Signal: %v (Signal Number: %d)\n",
		waitStatus.Signal(), int(waitStatus.Signal()))
	fmt.Printf("Core Dumped:        %v\n", waitStatus.CoreDump())

	if waitStatus.Signaled() && waitStatus.Signal() == syscall.SIGKILL {
		fmt.Println("[Verification] Process was unconditionally eradicated by SIGKILL as expected!")
	}
}
```

ℹ️ Принудительное уничтожение дочернего процесса сигналом SIGKILL через системный вызов syscall.Kill

**`Терминал`**

## Под капотом

Что происходит внутри ядра Linux при отправке SIGKILL:
1. Выполняется системный вызов `sys_kill`.
2. Ядро проверяет права отправителя: отправитель должен иметь тот же UID или привилегию `CAP_KILL`.
3. Ядро находит структуру `task_struct` целевого процесса по PID в хэш-таблице `pid_hash`.
4. Функция ядра `send_signal()` добавляет сигнал `SIGKILL` в очередь сигналов процесса и принудительно пробуждает поток, если он спал в прерываемом сне (`TASK_INTERRUPTIBLE`).
5. Поскольку `SIGKILL` не имеет обработчиков, планировщик ядра немедленно вызывает функцию `do_exit(SIGKILL)`.
6. Потоки процесса уничтожаются, освобождаются таблицы страниц `mm_struct`, а статус процесса становится `EXIT_ZOMBIE` до вызова `sys_wait4` родителем.

## Подводные камни

1. **Процессы в состоянии D (Uninterruptible Sleep)**: Если процесс завис в системном вызове дискового ввода-вывода или зависшей сетевой файловой системы NFS (статус `D` в выводе `ps`), даже сигнал `SIGKILL` **не сможет завершить процесс**! Процесс будет висеть в ядре до тех пор, пока драйвер диска не завершит операцию I/O.
2. **Убийство дочерних процессов демонов**: `syscall.Kill(pid, SIGKILL)` завершает только указанный процесс. Если процесс успел запустить своих детей, его дети не завершатся, а будут усыновлены `PID 1`. Чтобы завершить всю группу процессов, передают отрицательный PID: `syscall.Kill(-pgid, syscall.SIGKILL)`.
3. **PID Reuse (Переиспользование PID)**: Если процесс уже завершился, а вы вызываете `Kill(pid)`, ядро может к этому моменту выделить этот же PID новому системному процессу, вызвав случайное завершение чужого сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как Kubernetes Pod Termination Lifecycle использует цепочку сигналов SIGTERM и SIGKILL при удалении пода?»
**Ответ:**
1. Когда под удаляется (`kubectl delete pod`), Kubelet сначала исключает его из Endpoints сервиса, чтобы новый трафик не поступал.
2. Kubelet отправляет главному процессу контейнера сигнал **`SIGTERM`** (Graceful Shutdown).
3. Запускается таймер обратного отсчета: `terminationGracePeriodSeconds` (по умолчанию 30 секунд). Приложение обязано завершить активные HTTP/gRPC запросы и корректно закрыть соединения.
4. Если приложение не завершилось по истечении 30 секунд (зависло в дедлоке или медленной операции), ядро принудительно уничтожает контейнер сигналом **`SIGKILL`** (код выхода 137).
