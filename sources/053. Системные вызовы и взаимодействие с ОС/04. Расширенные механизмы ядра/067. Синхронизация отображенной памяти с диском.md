# Синхронизация отображенной памяти с диском через системный вызов msync

## Условие

**msync**: Принудительно сбросьте mmap changes на диск через `unix.Msync()`.

## Теория

Когда файл отображается в память с флагом `MAP_SHARED` системным вызовом `mmap(2)`, операции записи в срез Go модифицируют **Page Cache ядра ОС**, но не гарантируют немедленной физической записи на энергонезависимый накопитель (SSD/HDD). В случае внезапного отключения питания или сбоя ОС данные могут быть безвозвратно утеряны.

Системный вызов **`msync(2)`** принудительно синхронизирует измененные (грязные / dirty) страницы памяти с дисковым файлом.

### Флаги синхронизации:
- **`MS_ASYNC`**: инициирует асинхронную запись грязных страниц планировщиком ввода-вывода ядра и возвращает управление немедленно.
- **`MS_SYNC`**: выполняет синхронную блокирующую запись всех измененных страниц на физический диск (аналог `fsync(2)` для файлового дескриптора) до полного подтверждения контроллером диска.
- **`MS_INVALIDATE`**: указывает ядру инвалидировать другие копии этих же страниц в кэше, чтобы последующие чтения читали свежие данные непосредственно из файла.

## Решение по шагам

1. Создадим временный файл фиксированного размера и запишем в него начальные данные.
2. Отобразим файл в память через `syscall.Mmap` с флагами `PROT_READ|PROT_WRITE` и `MAP_SHARED`.
3. Изменим содержимое среза памяти в Go.
4. Вызовем `syscall.Msync` с флагом `syscall.MS_SYNC`, гарантируя сброс на диск.
5. Освободим память через `syscall.Munmap` и закроем файл.
6. Перечитаем файл обычным `os.ReadFile` и убедимся, что изменения сохранены.

## Код решения

**`msync_demo.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
	"syscall"
)

func main() {
	// 1. Создаем тестовый файл
	f, err := os.CreateTemp("", "mmap_msync_*.dat")
	if err != nil {
		log.Fatalf("Ошибка создания файла: %v", err)
	}
	filePath := f.Name()
	defer os.Remove(filePath)
	defer f.Close()

	// Задаем начальный размер 4096 байт
	pageSize := syscall.Getpagesize()
	if err := f.Truncate(int64(pageSize)); err != nil {
		log.Fatalf("Ошибка truncate: %v", err)
	}

	// 2. Отображаем файл в память (MAP_SHARED)
	data, err := syscall.Mmap(
		int(f.Fd()),
		0,
		pageSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_SHARED,
	)
	if err != nil {
		log.Fatalf("Ошибка mmap: %v", err)
	}
	defer syscall.Munmap(data)

	// 3. Модифицируем данные в памяти через срез
	payload := []byte("ACID Transaction Commit: Checkpoint OK!\n")
	copy(data, payload)
	fmt.Println("Данные успешно записаны в Page Cache через mmap.")

	// 4. Принудительно сбрасываем грязные страницы на диск
	// Системный вызов msync блокирует выполнение до завершения физической записи
	if err := syscall.Msync(data, syscall.MS_SYNC); err != nil {
		log.Fatalf("Ошибка msync: %v", err)
	}
	fmt.Println("Системный вызов msync(MS_SYNC) успешно сбросил данные на физический диск.")

	// 5. Проверяем содержимое файла с диска
	readBack, err := os.ReadFile(filePath)
	if err != nil {
		log.Fatalf("Ошибка чтения файла: %v", err)
	}

	fmt.Printf("Прочитано с диска: %s", string(readBack[:len(payload)]))
}
```

# Системный вызов msync(MS_SYNC) успешно сбросил данные на физический диск.

## Под капотом

Внутри ядра Linux вызов `msync` ищет соответствующие страницы памяти в адресном пространстве структуры `inode->i_mapping`. Каждая страница, помеченная аппаратным флагом `_PAGE_DIRTY`, передается в файловую систему через вызов `writepage` или `writepages`.

Флаг `MS_SYNC` ждет завершения ввода-вывода на уровне блочного устройства (Block Layer I/O Request), посылая диску команду `FLUSH CACHE` (для SATA/NVMe). Это гарантирует свойство надежности **Durability (буква D в ACID)** во встраиваемых СУБД, таких как **BoltDB**, **LMDB** или **BadgerDB**.

## Подводные камни

1. **Вызов msync на MAP_PRIVATE:** Если память отображена с флагом `MAP_PRIVATE`, ядро использует механизм Copy-on-Write (COW). Модификации никогда не сбрасываются в исходный файл, а вызов `msync` либо завершится с ошибкой, либо проигнорирует изменения.
2. **Производительность:** Частый вызов `msync(MS_SYNC)` на каждый мелкий коммит превращает быстрый mmap в крайне медленный I/O, упирающийся в IOPS накопителя. В production-системах сброс группируют (Group Commit) или вызывают `MS_ASYNC` с периодическим фоновым чекпоинтом.

## На собеседовании

**Вопрос с собеседования в Яндекс (СУБД и инфраструктура хранения):** «Как embedded-база данных BoltDB (используемая в etcd/Kubernetes) использует mmap и msync? Почему чтение в ней происходит без системных вызовов, а запись требует msync?»
**Ответ:** BoltDB отображает весь файл базы данных в память через `mmap(MAP_SHARED, PROT_READ)`. Чтение B+ дерева и поиск ключей происходят напрямую по указателям памяти процесса без единого системного вызова `read()` и без аллокаций в куче Go.
При транзакциях записи BoltDB формирует измененные страницы памяти и сбрасывает их на диск системным вызовом `msync()` или `fdatasync()` для обеспечения гарантий долговечности WAL/страниц в соответствии со стандартом ACID.
