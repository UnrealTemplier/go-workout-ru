# Управление правами доступа и атрибутами inode: системные вызовы chmod и chown

## Условие

**Изменение прав доступа и владельца (Chmod/Chown)**: Напишите утилиту, которая изменяет права доступа к файлу с помощью системного вызова `syscall.Chmod`. Настройте права доступа, используя числовые маски Unix (например, установив права `0644` — чтение/запись для владельца и только чтение для группы/остальных). Обработайте возможные ошибки отсутствия привилегий.

## Теория

Права доступа к файлам и каталогам в Unix-подобных операционных системах хранятся в метаданных индексного дескриптора (**inode**) файловой системы.

### Системные вызовы:
1. **`chmod(const char *path, mode_t mode)`** — изменяет битовую маску прав доступа (Permissions Mode) к файлу.
2. **`fchmod(int fd, mode_t mode)`** — аналог `chmod`, оперирующий открытым файловым дескриптором (защищает от атак класса TOCTOU — Time-of-Check to Time-of-Use).
3. **`chown(const char *path, uid_t owner, gid_t group)`** — изменяет идентификатор пользователя-владельца (UID) и группы-владельца (GID).

### Структура числовой маски Unix (восьмеричная система):
Маска `0644` расшифровывается как:
- `0` — префикс восьмеричной константы в Go.
- `6` (двоичное `110`) — Владелец (User): Read (4) + Write (2) = 6.
- `4` (двоичное `100`) — Группа (Group): Read (4).
- `4` (двоичное `100`) — Остальные (Others): Read (4).

### Привилегии и ошибки:
- Изменять права через `chmod` может только владелец файла либо суперпользователь (`root` / `CAP_FOWNER`).
- Изменять владельца файла через `chown` на произвольного пользователя в большинстве современных Linux-дистрибутивов разрешено исключительно суперпользователю (`root` / `CAP_CHOWN`). Попытка вызова обычным пользователем возвращает ошибку **`EPERM` (Operation not permitted)**.

## Решение по шагам

1. Создадим временный тестовый файл с помощью `os.CreateTemp`.
2. Изменим права доступа на `0644` через системный вызов `syscall.Chmod`.
3. Получим информацию об inode файла через `syscall.Stat` и проверим битовую маску `Mode & 0777`.
4. Попробуем вызвать `syscall.Chown` и корректно обработаем возможную ошибку `syscall.EPERM`.
5. Удалим временный файл.

## Код решения

**`chmod_chown.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
	"os"
	"syscall"
)

func main() {
	// 1. Создаем временный файл
	f, err := os.CreateTemp("", "sec_file_*.txt")
	if err != nil {
		log.Fatalf("Ошибка создания файла: %v", err)
	}
	path := f.Name()
	_ = f.Close()
	defer os.Remove(path)

	// 2. Устанавливаем права 0644 (rw-r--r--)
	const targetMode uint32 = 0644
	if err := syscall.Chmod(path, targetMode); err != nil {
		log.Fatalf("Ошибка syscall.Chmod: %v", err)
	}
	fmt.Printf("Права доступа к файлу успешно изменены на %04o\n", targetMode)

	// 3. Проверяем установленные права через stat
	var stat syscall.Stat_t
	if err := syscall.Stat(path, &stat); err != nil {
		log.Fatalf("Ошибка stat: %v", err)
	}

	actualMode := stat.Mode & 0777
	fmt.Printf("Фактические права файла в inode: %04o\n", actualMode)
	fmt.Printf("Владелец файла: UID=%d, GID=%d\n", stat.Uid, stat.Gid)

	// 4. Попытка смены владельца файла (chown)
	// Для непривилегированного пользователя это должно вернуть EPERM
	err = syscall.Chown(path, 0, 0) // попытка передать файл пользователю root (UID=0)
	if err != nil {
		if errors.Is(err, syscall.EPERM) {
			fmt.Println("Ожидаемая ошибка EPERM: смена владельца файла требует прав суперпользователя (CAP_CHOWN).")
		} else {
			fmt.Printf("Ошибка syscall.Chown: %v\n", err)
		}
	} else {
		fmt.Println("Владелец файла успешно изменен на root (программа запущена с правами суперпользователя).")
	}
}
```

## Под капотом

При вызове `chmod` ядро Linux обращается к объекту `inode` в виртуальной файловой системе (VFS).
Ядро проверяет привилегии вызывающего процесса:
1. Совпадает ли эффективный UID процесса (`current_euid()`) с полем `inode->i_uid`.
2. Обладает ли процесс Linux-возможностью `CAP_FOWNER` в текущем User Namespace.

Если проверка пройдена, ядро обновляет поле `i_mode` в памяти и инициирует обновление блока метаданных на диске через механизм журналирования файловой системы (Ext4 JBD2 / XFS log).

## Подводные камни

1. **Влияние umask:** При создании файлов через `os.Create` или `syscall.Open` с флагом `O_CREAT` результирующие права фильтруются битовой маской `umask` текущего процесса (`mode & ~umask`). Прямой вызов `syscall.Chmod` игнорирует `umask` и выставляет маску в точности.
2. **Атаки TOCTOU при использовании путей:** Если путь к файлу проверяется, а затем модифицируется через `syscall.Chmod(path, ...)`, злоумышленник может подменить файл символической ссылкой между вызовами. Для безопасного программирования рекомендуется открывать файл и применять `syscall.Fchmod(fd, ...)`.

## На собеседовании

**Вопрос с собеседования в Касперский (DevSecOps):** «Что такое биты SUID, SGID и Sticky Bit в числовой маске прав Unix, и почему они представляют угрозу информационной безопасности?»
**Ответ:** 
- **SUID (`04000`):** Запуск бинарного файла выполняется с привилегиями владельца файла, а не пользователя, запустившего процесс (например, утилита `passwd` имеет SUID root). Ошибка переполнения буфера в SUID-бинарнике приводит к мгновенной эскалации привилегий до root.
- **SGID (`02000`):** Выполнение с правами группы файла либо автоматическое наследование группы каталога для всех создаваемых файлов.
- **Sticky Bit (`01000`):** Используется в каталогах общего доступа (например, `/tmp`), запрещая пользователям удалять или переименовывать чужие файлы, даже если каталог имеет права `0777`.
