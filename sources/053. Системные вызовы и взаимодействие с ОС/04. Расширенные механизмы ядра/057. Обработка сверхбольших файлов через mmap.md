# Обработка сверхбольших файлов через mmap: работа с объемами данных больше физической RAM

## Условие

**mmap large files**: Работайте с файлами больше RAM через mmap (OS управляет page cache).

## Теория

Один из главных архитектурных триумфов `mmap` — способность прозрачно работать с файлами, **размер которых превышает объем физической оперативной памяти сервера** (например, обработка файла базы данных на 500 ГБ на сервере с 32 ГБ RAM).

**Почему это работает в 64-битных ОС**:
1. На архитектурах x86_64 виртуальное адресное пространство процесса составляет **256 Терабайт** (48 бит адресации) или **4 Петабайта** (5-уровневые таблицы страниц, 57 бит адресации).
2. Замапить файл на 500 ГБ — это лишь резервирование 500 ГБ адресов в виртуальной памяти. Физическая память не расходуется.
3. При сканировании файла ядро Linux автоматически выполняет **Paging**:
   - Читаемые страницы подкачиваются с SSD в свободную RAM.
   - Когда оперативная память хоста заполняется, фоновый демон ядра **`kswapd`** вытесняет старые неиспользуемые страницы из Page Cache (алгоритм LRU — Least Recently Used).
   - Если страницы были изменены (dirty), ядро сбрасывает их на диск перед вытеснением.
Приложение обрабатывает файл любого размера, используя константный объем физической RAM!

## Решение по шагам

1. Создайте разреженный файл (Sparse File) большого размера (например, 1 ГБ), не занимающий реального места на диске.
2. Запишите контрольные данные в начало и конец разреженного файла.
3. Отобразите 1 ГБ файл через `syscall.Mmap(fd, 0, 1024*1024*1024, syscall.PROT_READ, syscall.MAP_SHARED)`.
4. Считайте данные из среза с разных концов файла.
5. Продемонстрируйте вызов `syscall.Madvise` с флагом `MADV_SEQUENTIAL`.
6. Освободите отображение через `syscall.Munmap`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	sparseFile := "large_sparse_dataset.bin"
	const targetSize = 1024 * 1024 * 1024 // 1 ГБ

	// 1. Создаем Sparse File (разреженный файл) через ftruncate
	// Файл имеет логический размер 1 ГБ, но занимает 0 байт на диске
	f, err := os.Create(sparseFile)
	if err != nil {
		panic(err)
	}
	if err := f.Truncate(targetSize); err != nil {
		panic(err)
	}

	// Записываем маркеры в начало и самый конец файла
	startMarker := []byte("START_RECORD_DATA_001")
	endMarker := []byte("END_RECORD_DATA_99999")
	_, _ = f.WriteAt(startMarker, 0)
	_, _ = f.WriteAt(endMarker, targetSize-int64(len(endMarker)))
	_ = f.Close()
	defer os.Remove(sparseFile)

	// 2. Открываем дескриптор для mmap
	fd, err := syscall.Open(sparseFile, syscall.O_RDONLY, 0)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(fd)

	// 3. Отображаем 1 ГБ файл целиком в виртуальную память процесса
	mmapData, err := syscall.Mmap(
		fd,
		0,
		targetSize,
		syscall.PROT_READ,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(fmt.Sprintf("syscall.Mmap failed: %v", err))
	}
	defer func() {
		_ = syscall.Munmap(mmapData)
	}()

	fmt.Printf("[Large Mmap] Successfully mapped %d GB file into virtual address space.\n", targetSize/(1024*1024*1024))
	fmt.Printf("Length of Go slice: %d bytes (24-byte SliceHeader in Go heap!)\n", len(mmapData))

	// 4. Оповещаем ядро о последовательном сканировании через madvise
	// syscall.MADV_SEQUENTIAL включает агрессивный Read-Ahead и немедленное вытеснение прочитанных страниц
	_ = syscall.Madvise(mmapData, syscall.MADV_SEQUENTIAL)

	// 5. Мгновенное чтение маркеров из разных концов гигантского файла
	readStart := string(mmapData[:len(startMarker)])
	readEnd := string(mmapData[targetSize-len(endMarker):])

	fmt.Printf("[Read Verification] Start Marker: %q\n", readStart)
	fmt.Printf("[Read Verification] End Marker:   %q\n", readEnd)
	fmt.Println("Large file processing via kernel page cache paging demonstrated successfully!")
}
```

## Под капотом

Как ядро Linux управляет памятью при файлах больше RAM:
1. Алгоритм **Two-List Strategy** (Active List и Inactive List):
   - Новые страницы Page Cache попадают в Inactive List.
   - Если к странице обращаются повторно, она повышается в Active List.
   - Демон ядра `kswapd` сканирует Inactive List и вытесняет страницы, к которым не было повторных обращений (Page Reclaim).
2. Флаг `MADV_SEQUENTIAL`:
   - Подсказывает ядру, что после прочтения страницы `i` она больше не понадобится.
   - Ядро вытесняет прочитанные страницы немедленно, не забивая оперативную память сервера.

## Подводные камни

1. **Page Thrashing (Пробуксовка страниц)**: Если случайный доступ (Random Access) идет по всему объему 500 ГБ файла при 32 ГБ RAM, ядро будет тратить 99% времени на непрерывную выгрузку и загрузку страниц с SSD (I/O Thrashing), обрушая производительность.
2. **Блокировки чтения**: При промахе страницы поток засыпает в ядре до окончания чтения блочного устройства.
3. **Фрагментация диска**: При работе с разреженными файлами реальные блоки выделяются только при записи.

## На собеседовании

**Вопрос с собеседования:** «Как СУБД MongoDB в движке WiredTiger использует mmap и собственный кэш?»
**Ответ:**
Исторически ранние версии MongoDB (движок MMAPv1) полностью полагались на `mmap` для всего управления памятью. Это приводило к проблемам:
- Приложение не контролировало, когда ядро решит сбросить грязные страницы на диск.
- Глобальная блокировка `mmap_lock` в ядре вызывала деградацию при высокой конкурентности.
Современный движок WiredTiger использует собственный кэш в пространстве пользователя (WiredTiger Cache) с явным сбросом через `pwrite()`, а `mmap` использует выборочно для неизменяемых сегментов.
