# Прецизионная периодическая диспетчеризация через файловый дескриптор timerfd

## Условие

## Теория

Системный вызов ядра Linux **`timerfd_create(2)`** создает специальный файловый дескриптор, который генерирует события готовности к чтению при срабатывании высокоточного таймера ядра (**POSIX Timers**).

### Преимущества timerfd над обычным `time.Sleep` / `time.Ticker`:
1. **Интеграция в Event Loop (Epoll):** Таймер представлен обычным файловым дескриптором `int`. Его можно добавить в единый цикл `epoll_wait` наряду с сокетами и пайпами. Один поток может одновременно ждать сетевых пакетов и срабатывания таймеров без фоновых горутин.
2. **Абсолютная точность и монотонность:** Поддержка часов `CLOCK_MONOTONIC` (не подверженных переводу системного времени) и флага `TFD_NONBLOCK`.
3. **Минимум накладных расходов рантайма:** Стандартный `time.Ticker` в Go создает запись в квадродереве таймеров планировщика рантайма (runtime timers heap), что при миллионах таймеров нагружает рантайм Go. `timerfd` управляется непосредственно планировщиком ядра Linux (hr-timers).

## Решение по шагам

1. Создадим дескриптор таймера через системный вызов `timerfd_create` с флагами `CLOCK_MONOTONIC` и `TFD_NONBLOCK`.
2. Настроим периодичность срабатывания (например, каждые 100 миллисекунд) через системный вызов `timerfd_settime`.
3. Зарегистрируем дескриптор таймера в `epoll`.
4. В цикле `epoll_wait` отследим тики таймера, вычитывая 8-байтовое число срабатываний (`uint64`).
5. Закроем дескриптор таймера по завершении.

## Код решения

**`timerfd_demo.go`**

```go
package main

import (
	"encoding/binary"
	"fmt"
	"log"
	"syscall"
	"time"
	"unsafe"
)

// Структуры времени для timerfd_settime
type itimerspec struct {
	it_interval syscall.Timespec // Интервал периодического таймера
	it_value    syscall.Timespec // Начальное время первого срабатывания
}

func main() {
	const (
		SYS_TIMERFD_CREATE  = 283
		SYS_TIMERFD_SETTIME = 286
		CLOCK_MONOTONIC     = 1
		TFD_NONBLOCK        = 0x800
		TFD_CLOEXEC         = 0x80000
	)

	// 1. Создаем timerfd
	tfd, _, errno := syscall.Syscall(
		SYS_TIMERFD_CREATE,
		uintptr(CLOCK_MONOTONIC),
		uintptr(TFD_NONBLOCK|TFD_CLOEXEC),
		0,
	)
	if errno != 0 {
		log.Fatalf("Ошибка timerfd_create: %v", errno)
	}
	defer syscall.Close(int(tfd))
	fmt.Printf("Timerfd успешно создан с флагом TFD_NONBLOCK (fd=%d)\n", tfd)

	// 2. Настраиваем таймер: первый запуск через 50 мс, затем каждые 100 мс
	newVal := itimerspec{
		it_interval: syscall.Timespec{Sec: 0, Nsec: 100 * 1000 * 1000}, // 100 мс
		it_value:    syscall.Timespec{Sec: 0, Nsec: 50 * 1000 * 1000},  // 50 мс
	}

	_, _, errno = syscall.Syscall6(
		SYS_TIMERFD_SETTIME,
		tfd,
		0, // относительное время
		uintptr(unsafe.Pointer(&newVal)),
		0, 0, 0,
	)
	if errno != 0 {
		log.Fatalf("Ошибка timerfd_settime: %v", errno)
	}
	fmt.Println("Таймер взведен на периодический тик каждые 100 мс.")

	// 3. Создаем epoll и добавляем timerfd
	epfd, err := syscall.EpollCreate1(0)
	if err != nil {
		log.Fatalf("Ошибка epoll: %v", err)
	}
	defer syscall.Close(epfd)

	ev := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(tfd),
	}
	if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, int(tfd), &ev); err != nil {
		log.Fatalf("Ошибка EpollCtl: %v", err)
	}

	// 4. Ожидаем срабатывания таймера в цикле событий
	events := make([]syscall.EpollEvent, 1)
	buf := make([]byte, 8) // timerfd возвращает 8-байтовое число пропущенных тиков

	fmt.Println("Запуск ожидания тиков таймера в epoll_wait...")
	start := time.Now()

	for tickCount := 1; tickCount <= 3; tickCount++ {
		n, err := syscall.EpollWait(epfd, events, 2000)
		if err != nil {
			log.Fatalf("Ошибка epoll_wait: %v", err)
		}

		if n > 0 && events[0].Fd == int32(tfd) {
			nRead, err := syscall.Read(int(tfd), buf)
			if err != nil {
				log.Fatalf("Ошибка чтения timerfd: %v", err)
			}
			if nRead == 8 {
				expirations := binary.LittleEndian.Uint64(buf)
				elapsed := time.Since(start)
				fmt.Printf("[Тик %d] Срабатываний таймера ядра: %d | Прошло: %v\n", tickCount, expirations, elapsed)
			}
		}
	}
	fmt.Println("Прецизионный цикл таймера timerfd успешно завершен.")
}
```

## Под капотом

В ядре Linux механизм `timerfd` базируется на подсистеме высокоточных таймеров **hrtimers (High-Resolution Timers)**.
В отличие от классических джиттерных тиков системных часов (`jiffies` с шагом 1–4 мс), hrtimers программируют аппаратные прерывания локального таймера APIC процессора с наносекундным разрешением.

При наступлении заданного времени обработчик прерывания ядра инкрементирует внутренний 64-битный счетчик срабатываний `ctx->ticks` и пробуждает список ожидания `ctx->wqh`. Системный вызов `read()` возвращает значение этого счетчика и сбрасывает его в ноль.

## Подводные камни

1. **Пропуск чтения (Buffer Underflow):** Чтение из `timerfd` всегда обязано принимать буфер размером **не менее 8 байт** (`sizeof(uint64)`). Если передать буфер меньшего размера, `syscall.Read` вернет ошибку `EINVAL`.
2. **Переполнение тиков при задержке потока:** Если поток обработчика был занят другой задачей и опоздал на 3 интервала, последующее чтение вернет значение `3` (число пропущенных интервалов), что позволяет приложению обнаружить отставание от реального времени (Drift Detection).

## На собеседовании

**Вопрос с собеседования в Wildberries (HighLoad Core):** «Когда в Go-сервисе целесообразно использовать timerfd вместо стандартного time.NewTicker / time.AfterFunc?»
**Ответ:** 
Стандартный `time.Ticker` отлично подходит для 99% стандартных задач бэкенда. Однако `timerfd` незаменим в двух сценариях:
1. **Единый цикл epoll без горутин (Реакторная модель / C-binding):** Когда сетевой движок (например, на базе epoll) должен мультиплексировать миллионы сокетов и сетевые таймауты в одном потоке без накладных расходов на переключение контекста горутин.
2. **Защита от дрифта часов и пробуждение по CLOCK_BOOTTIME / CLOCK_REALTIME_ALARM:** `timerfd` умеет пробуждать систему даже из режима энергосбережения (Suspend/Sleep), что невозможно сделать средствами рантайма Go.
