# Межпроцессное взаимодействие через разделяемую память (shm_open и mmap)

## Условие

**Shared memory (shm)**: Создайте shared memory segment через `shm_open()` + `mmap()` для IPC между процессами.

## Теория

**Разделяемая память (Shared Memory / POSIX SHM)** — это самый быстрый и высокопроизводительный механизм межпроцессного взаимодействия (IPC) в операционных системах семейств Linux/Unix. 

В отличие от сокетов, пайпов или очередей сообщений, где передача данных требует двукратного копирования через буферы ядра (user space → kernel space → user space) и системных вызовов `read`/`write`, разделяемая память отображает **одни и те же физические страницы ОЗУ** в виртуальные адресные пространства нескольких независимых процессов.

### Механика POSIX SHM в Linux:
1. Вызов `shm_open(name, O_CREAT | O_RDWR, 0666)` создает специальный виртуальный файл в псевдофайловой системе `tmpfs`, смонтированной в каталог **/dev/shm/**.
2. Размер сегмента задается системным вызовом `ftruncate(fd, size)`.
3. Память отображается в процесс вызовом `mmap(..., MAP_SHARED, fd, 0)`.
4. Поскольку `/dev/shm` является стандартной файловой системой в Linux, в Go полноценный POSIX SHM реализуется на чистых системных вызовах через `syscall.Open("/dev/shm/имя", ...)` без необходимости подключения CGO!

## Решение по шагам

1. Откроем или создадим именованный сегмент разделяемой памяти в `/dev/shm/go_shm_demo`.
2. Установим размер сегмента (4096 байт) через `syscall.Ftruncate`.
3. Отобразим память через `syscall.Mmap` с флагом `MAP_SHARED`.
4. Запишем сообщение от «Процесса-писателя».
5. Продемонстрируем мгновенное чтение данных без системных вызовов из «Процесса-читателя».
6. Очистим ресурсы через `syscall.Munmap` и `syscall.Unlink`.

## Код решения

**`shm_demo.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
	"sync"
	"syscall"
	"time"
)

const (
	shmPath = "/dev/shm/go_workout_shm"
	shmSize = 4096
)

func main() {
	// 1. Создаем сегмент разделяемой памяти в /dev/shm (POSIX SHM)
	fd, err := syscall.Open(
		shmPath,
		syscall.O_CREAT|syscall.O_RDWR|syscall.O_TRUNC,
		0666,
	)
	if err != nil {
		log.Fatalf("Ошибка создания shm: %v", err)
	}
	defer func() {
		syscall.Close(fd)
		_ = os.Remove(shmPath) // shm_unlink
	}()

	// 2. Устанавливаем размер сегмента разделяемой памяти
	if err := syscall.Ftruncate(fd, shmSize); err != nil {
		log.Fatalf("Ошибка ftruncate: %v", err)
	}

	// 3. Отображаем память (MAP_SHARED)
	mem, err := syscall.Mmap(
		fd,
		0,
		shmSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_SHARED,
	)
	if err != nil {
		log.Fatalf("Ошибка mmap: %v", err)
	}
	defer syscall.Munmap(mem)

	var wg sync.WaitGroup
	wg.Add(2)

	// Читатель (эмулирует независимый процесс)
	go func() {
		defer wg.Done()
		fmt.Println("[Reader] Ожидание поступления данных в SHM...")
		for {
			if mem[0] != 0 {
				// Данные появились!
				msgLen := int(mem[0])
				message := string(mem[1 : 1+msgLen])
				fmt.Printf("[Reader] Мгновенно прочитано из SHM (Zero-Copy): «%s»\n", message)
				return
			}
			time.Sleep(10 * time.Millisecond)
		}
	}()

	// Писатель (эмулирует процесс-генератор данных)
	go func() {
		defer wg.Done()
		time.Sleep(50 * time.Millisecond)
		msg := "Высокоскоростное IPC-сообщение без участия ядра!"
		mem[0] = byte(len(msg))
		copy(mem[1:], []byte(msg))
		fmt.Println("[Writer] Данные атомарно записаны в разделяемую память.")
	}()

	wg.Wait()
	fmt.Println("Сегмент разделяемой памяти успешно отработал и закрыт.")
}
```

## Под капотом

Псевдофайловая система `/dev/shm` управляется драйвером ядра `tmpfs`. Когда два независимых процесса отображают один и тот же файл `/dev/shm/имя` с флагом `MAP_SHARED`, ядро связывает записи таблиц страниц обоих процессов с **одними и теми же физическими страницами ОЗУ** (Page Frames).

Операции чтения и записи выполняются напрямую на уровне микроархитектуры шины процессора через команды `MOV`/`AVX`, минуя планировщик ввода-вывода и системные прерывания. Задержка обмена данными снижается с десятков микросекунд (в случае сокетов) до наносекундных таймингов доступа к L3-кэшу процессора.

## Подводные камни

1. **Необходимость внешней синхронизации:** Разделяемая память не предоставляет встроенных средств синхронизации. Если два процесса пишут одновременно, возникнет гонка данных. Требуется использовать межпроцессные мьютексы (`pthread_mutexattr_setpshared`), атомики (`sync/atomic`) или спинлоки.
2. **Утечка разделяемой памяти:** Файлы в `/dev/shm` сохраняются в оперативной памяти даже после аварийного завершения всех процессов. Их необходимо явно удалять через `os.Remove()` (аналог `shm_unlink(3)`).

## На собеседовании

**Вопрос с собеседования в Lamoda (Core Performance):** «Каковы задержки передачи 1 МБ данных между двумя процессами на одном сервере через Unix Domain Sockets по сравнению с Shared Memory?»
**Ответ:** 
- При передаче через **Unix Domain Sockets** данные копируются дважды (из памяти первого процесса в буфер сокета ядра, затем из ядра в буфер второго процесса), что на 1 МБ создает существенную нагрузку на шину памяти и занимает порядка 50–150 микросекунд плюс переключение контекста.
- В **Shared Memory** данные не копируются вовсе (Zero-Copy): второй процесс просто читает те же физические адреса. Время задержки определяется исключительно скоростью синхронизации (например, атомарным флагом) и составляет менее 1 микросекунды.
