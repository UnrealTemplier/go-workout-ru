# Оптимизация подкачки страниц памяти: системный вызов madvise

## Условие

**madvise**: Дайте подсказки ядру через `unix.Madvise()` (например, `MADV_SEQUENTIAL` для sequential access).

## Теория

Системный вызов **`madvise(2)`** позволяет приложению дать ядру операционной системы подсказки (advice) о планируемом характере доступа к диапазону виртуальной памяти. Это позволяет подсистеме управления виртуальной памятью ядра оптимизировать упреждающее чтение (readahead) и вытеснение страниц (page reclamation).

### Основные флаги madvise:
1. **`MADV_NORMAL`**: стандартное поведение ядра по умолчанию со средней агрессивностью упреждающего чтения.
2. **`MADV_SEQUENTIAL`**: сообщает ядру, что данные будут читаться строго последовательно от начала к концу. Ядро максимизирует размер окна упреждающего чтения (Readahead Window) и агрессивно освобождает уже прочитанные страницы из Page Cache.
3. **`MADV_RANDOM`**: отключает упреждающее чтение страниц, так как обращения будут носить случайный характер (актуально для B-деревьев, LSM-деревьев и хеш-индексов).
4. **`MADV_WILLNEED`**: заставляет ядро немедленно инициировать асинхронную подкачку страниц с диска в память (Prefetching), снижая задержки при последующих обращениях.
5. **`MADV_DONTNEED`**: указывает ядру, что приложение больше не нуждается в содержимом диапазона памяти. Для анонимной памяти ядро немедленно освобождает физические фреймы памяти, обнуляя страницы при следующем обращении (активно используется в рантайме Go аллокатором `mheap`).

## Решение по шагам

1. Выделим крупный регион анонимной памяти размером несколько страниц через `syscall.Mmap`.
2. Применим подсказку `MADV_SEQUENTIAL` через `syscall.Madvise`.
3. Применим подсказку `MADV_DONTNEED` для демонстрации немедленного возврата страниц операционной системе.
4. Освободим регион с помощью `syscall.Munmap`.

## Код решения

**`madvise_demo.go`**

```go
package main

import (
	"fmt"
	"log"
	"syscall"
)

func main() {
	pageSize := syscall.Getpagesize()
	regionSize := pageSize * 16 // 64 КБ (16 страниц)

	// 1. Выделяем анонимную память через mmap
	mem, err := syscall.Mmap(
		-1,
		0,
		regionSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANONYMOUS|syscall.MAP_PRIVATE,
	)
	if err != nil {
		log.Fatalf("Ошибка mmap: %v", err)
	}
	defer syscall.Munmap(mem)

	// 2. Сообщаем ядру, что планируем последовательное чтение большого объема
	// MADV_SEQUENTIAL оптимизирует алгоритм Readahead
	if err := syscall.Madvise(mem, syscall.MADV_SEQUENTIAL); err != nil {
		log.Fatalf("Ошибка madvise(MADV_SEQUENTIAL): %v", err)
	}
	fmt.Println("Успешно применена подсказка MADV_SEQUENTIAL для ядра Linux.")

	// Заполняем память данными
	for i := range mem {
		mem[i] = byte(i % 256)
	}
	fmt.Printf("Память заполнена данными. Байт по индексу 42: %d\n", mem[42])

	// 3. Сообщаем ядру, что данные страниц больше не нужны (MADV_DONTNEED)
	// Ядро освобождает физические фреймы памяти без освобождения диапазона VMA
	if err := syscall.Madvise(mem, syscall.MADV_DONTNEED); err != nil {
		log.Fatalf("Ошибка madvise(MADV_DONTNEED): %v", err)
	}
	fmt.Println("Успешно применена подсказка MADV_DONTNEED. Физическая память возвращена ОС.")

	// При следующем чтении ядро выделит нулевую страницу (Zero Page)
	fmt.Printf("Чтение после MADV_DONTNEED (байт 42 сброшен в ноль): %d\n", mem[42])
}
```

## Под капотом

Внутри аллокатора рантайма Go (`src/runtime/mem_linux.go`) системный вызов `madvise` играет ключевую роль:
Функция `sysUnusedOS(v unsafe.Pointer, n uintptr)` вызывает `madvise(v, n, _MADV_DONTNEED)`. В Go 1.12 разработчики пробовали переключиться на `MADV_FREE`, однако это приводило к тому, что утилиты мониторинга (`top`, Prometheus) продолжали показывать завышенное потребление RSS, так как Linux лениво освобождает страницы `MADV_FREE` только при наступлении нехватки свободной памяти (Memory Pressure). Начиная с Go 1.16, рантайм вернулся к детерминированному `MADV_DONTNEED`.

## Подводные камни

1. **Потеря модификаций на MAP_SHARED:** Использование `MADV_DONTNEED` на отображенном общем файле (`MAP_SHARED`) может привести к тому, что несохраненные (грязные) страницы будут отброшены ядром без записи на диск.
2. **Адресное выравнивание:** Как и в случае с `mprotect`, переданный буфер обязан начинаться строго с границы страницы памяти.

## На собеседовании

**Вопрос с собеседования в Wildberries:** «Что делает рантайм Go, когда освобождает память из-под неиспользуемых спанов кучи обратно операционной системе? Почему размер виртуальной памяти VIRT при этом не уменьшается?»
**Ответ:** Рантайм Go вызывает `madvise(addr, size, MADV_DONTNEED)`. Этот вызов не удаляет диапазон виртуальных адресов из таблицы VMA процесса (поэтому размер VIRT в `top` остается прежним), но заставляет ядро немедленно отвязать физические страницы памяти (Page Frames) и вернуть их в пул свободной памяти ОС, уменьшая Resident Set Size (RSS). Если процесс впоследствии снова обратится к этому адресу, ядро выделит свежую обнуленную физическую страницу.
