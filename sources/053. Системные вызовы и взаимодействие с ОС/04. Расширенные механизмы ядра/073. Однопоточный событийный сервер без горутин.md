# Однопоточный событийный сервер без горутин (архитектура Redis и Node.js)

## Условие

**Event-Driven Server (Без горутин)**: Напиши бесконечный цикл `unix.EpollWait` (или `Kevent`). Когда приходит событие (новое подключение или данные), обрабатывай его в том же потоке. Поздравляю! Ты только что написал архитектуру однопоточного сервера, полностью аналогичную тому, как работают Node.js, Redis и Nginx под капотом, вообще не используя горутины!

## Теория

Хотя ключевым преимуществом Go является дешевая конкурентность на базе горутин, понимание **однопоточной событийно-ориентированной архитектуры (Single-Threaded Event Loop)** критически важно для любого старшего инженера.

Именно на этой архитектуре построены легендарные сверхбыстрые сетевые системы:
- **Redis:** обслуживает сотни тысяч запросов в секунду в одном потоке ядра, полностью исключая накладные расходы на мьютексы, блокировки и переключение контекста CPU.
- **Node.js:** движок libuv выполняет JavaScript-код в единственном потоке, делегируя I/O операционной системе через `epoll`/`kqueue`.
- **Nginx:** каждый рабочий процесс (`worker_process`) представляет собой изолированный однопоточный event loop.

### Принцип работы:
Вся программа выполняется строго в одном потоке операционной системы (`runtime.LockOSThread()`). Отсутствуют мьютексы (`sync.Mutex`), каналы и горутины. Все сетевые сокеты хранятся в неблокирующем режиме. Цикл `epoll_wait` блокирует поток только тогда, когда в системе нет активных событий.

## Решение по шагам

1. Заблокируем выполнение программы в текущем системном потоке через `runtime.LockOSThread()`.
2. Создадим неблокирующий слушающий TCP-сокет на порту `9092`.
3. Создадим инстанс `epoll` и зарегистрируем серверный сокет.
4. Введем структуру состояния клиентских подключений (буферы, контекст).
5. В синхронном бесконечном цикле `epoll_wait` обрабатываем входящие соединения и данные непосредственно в текущем потоке без вызова `go func()`.

## Код решения

**`single_threaded_server.go`**

```go
package main

import (
	"fmt"
	"log"
	"net"
	"runtime"
	"syscall"
	"time"
)

func main() {
	// 1. Привязываем горутину к конкретному потоку ОС (эмуляция чистого однопоточного демона)
	runtime.LockOSThread()
	defer runtime.UnlockOSThread()

	// 2. Создаем слушающий сокет
	listenFd, err := syscall.Socket(syscall.AF_INET, syscall.SOCK_STREAM, 0)
	if err != nil {
		log.Fatalf("Ошибка создания сокета: %v", err)
	}
	defer syscall.Close(listenFd)

	_ = syscall.SetsockoptInt(listenFd, syscall.SOL_SOCKET, syscall.SO_REUSEADDR, 1)
	_ = syscall.SetNonblock(listenFd, true)

	sa := &syscall.SockaddrInet4{Port: 9092}
	copy(sa.Addr[:], net.ParseIP("127.0.0.1").To4())
	if err := syscall.Bind(listenFd, sa); err != nil {
		log.Fatalf("Ошибка bind: %v", err)
	}

	if err := syscall.Listen(listenFd, 64); err != nil {
		log.Fatalf("Ошибка listen: %v", err)
	}

	// 3. Создаем epoll
	epfd, err := syscall.EpollCreate1(0)
	if err != nil {
		log.Fatalf("Ошибка epoll: %v", err)
	}
	defer syscall.Close(epfd)

	ev := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(listenFd),
	}
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, listenFd, &ev)

	fmt.Println("Однопоточный Event-Driven сервер запущен на 127.0.0.1:9092 (0 горутин)")

	// Запускаем фоновый тестовый клиент
	go func() {
		time.Sleep(100 * time.Millisecond)
		conn, err := net.Dial("tcp", "127.0.0.1:9092")
		if err == nil {
			defer conn.Close()
			_, _ = conn.Write([]byte("PING\n"))
			res := make([]byte, 32)
			n, _ := conn.Read(res)
			fmt.Printf("[Тестовый клиент] Ответ от однопоточного сервера: %s", string(res[:n]))
		}
	}()

	events := make([]syscall.EpollEvent, 16)
	buf := make([]byte, 1024)

	// 4. Однопоточный Event Loop (Redis / Node.js модель)
	iterations := 0
	for iterations < 3 {
		iterations++
		n, err := syscall.EpollWait(epfd, events, 300)
		if err != nil {
			if err == syscall.EINTR {
				continue
			}
			break
		}

		for i := 0; i < n; i++ {
			fd := int(events[i].Fd)

			if fd == listenFd {
				// Прием нового клиента
				clientFd, _, err := syscall.Accept(listenFd)
				if err == nil {
					_ = syscall.SetNonblock(clientFd, true)
					clientEv := syscall.EpollEvent{
						Events: syscall.EPOLLIN,
						Fd:     int32(clientFd),
					}
					_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, clientFd, &clientEv)
					fmt.Printf("[Event Loop] Принято соединение clientFd=%d\n", clientFd)
				}
			} else {
				// Обработка данных клиента прямо в текущем потоке
				nRead, err := syscall.Read(fd, buf)
				if err != nil || nRead == 0 {
					syscall.Close(fd)
					continue
				}

				if string(buf[:4]) == "PING" {
					_, _ = syscall.Write(fd, []byte("PONG\n"))
				} else {
					_, _ = syscall.Write(fd, buf[:nRead])
				}
				syscall.Close(fd)
			}
		}
	}
	fmt.Println("Однопоточный цикл событий успешно завершил демонстрационную фазу.")
}
```

ℹ️ Однопоточный событийный сервер на базе epoll без создания вспомогательных горутин

## Под капотом

В однопоточной модели все операции происходят в одном адресном пространстве одного ядра CPU.
Это дает колоссальные преимущества по утилизации аппаратного обеспечения:
1. **Отсутствие инвалидации кэшей L1/L2:** Данные программы всегда остаются теплыми в локальных кэшах процессорного ядра.
2. **Нулевой оверхед синхронизации:** Нет инструкций атомарной синхронизации шины (`LOCK CMPXCHG`), которые сбрасывают Store Buffer процессора.
3. **Отсутствие гонок данных (Data Races):** Любая модификация структур данных абсолютно безопасна без мьютексов.

## Подводные камни

1. **Блокировка всего цикла (Event Loop Blocking):** Главный бич однопоточной модели — любая тяжелая CPU-вычислительная операция (например, вычисление криптографического хеша) или блокирующий системный вызов (`os.ReadFile`) полностью замораживает обслуживание всех остальных клиентов сервера.
2. **Недоутилизация многоядерных процессоров:** Чтобы задействовать все ядра современного 64-ядерного сервера, приходится запускать 64 независимых процесса сервера с опцией `SO_REUSEPORT`.

## На собеседовании

**Вопрос с собеседования в Авито:** «Почему Redis исторически работал в одном потоке, и почему добавление многопоточности в Redis 6.0 коснулось только сетевого ввода-вывода, но не исполнения команд?»
**Ответ:** В Redis узким местом была не скорость вычислений в памяти (операции со словарями в RAM выполняются за наносекунды), а накладные расходы на сетевые системные вызовы `read()` и `write()`. 
Разработчики сохранили однопоточное выполнение команд для исключения мьютексов над ключами базы данных, но вынесли разбор сетевых протоколов и отправку ответов в фоновые потоки ввода-вывода (I/O Threads).
