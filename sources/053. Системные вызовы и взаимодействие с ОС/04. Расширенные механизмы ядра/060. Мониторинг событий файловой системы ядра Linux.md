# Мониторинг событий файловой системы ядра Linux через inotify: inotify_init1 и inotify_add_watch

## Условие

**[inotify (Filesystem Events)]**: Используй `unix.InotifyInit1()`. Зарегистрируй директорию для слежения (`unix.InotifyAddWatch`). Читай события (создание, удаление файлов) в цикле.

## Теория

Для отслеживания изменений на диске (создание, модификация, удаление файлов) наивный опрос (`polling` через `os.ReadDir` каждые 500 мс) неприемлем: он нагружает диск миллионами холостых операций `readdir` и создает задержку.

**Подсистема ядра Linux `inotify`**:
- Позволяет приложению регистрировать интерес к событиям файловой системы на уровне структур `inode` ядра Linux:
- `inotify_init1(flags)`: Создает дескриптор очереди inotify (`IN_NONBLOCK | IN_CLOEXEC`).
- `inotify_add_watch(fd, path, mask)`: Добавляет файл или директорию под наблюдение.
  - Маски событий:
    - `IN_CREATE`: Создан файл или директория внутри отслеживаемой папки.
    - `IN_DELETE`: Файл удален.
    - `IN_MODIFY`: Файл изменен (`write`).
    - `IN_MOVED_FROM` / `IN_MOVED_TO`: Файл переименован или перемещен.
- Чтение событий выполняется через обычный `syscall.Read(inotifyFd, buf)`.
- Ядро возвращает одну или несколько структур `syscall.InotifyEvent`:
  ```go
  type InotifyEvent struct {
      Wd     int32  // Watch Descriptor
      Mask   uint32 // Битовая маска произошедшего события
      Cookie uint32 // Уникальный идентификатор для связки rename
      Len    uint32 // Длина имени файла (с выравниванием до null)
  }
  ```
- Сразу за структурой в буфере следует имя затронутого файла (`Len` байт).

## Решение по шагам

1. Создайте временную директорию для тестирования.
2. Инициализируйте inotify через системный вызов `SYS_INOTIFY_INIT1`.
3. Добавьте директорию под наблюдение с маской `IN_CREATE | IN_DELETE` через `SYS_INOTIFY_ADD_WATCH`.
4. В фоновой горутине создайте и удалите файл внутри отслеживаемой папки.
5. Считайте структуру `syscall.InotifyEvent` из дескриптора inotify.
6. Извлеките маску события и имя файла.
7. Закройте дескриптор inotify и удалите временную директорию.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/binary"
	"fmt"
	"os"
	"path/filepath"
	"strings"
	"syscall"
	"time"
	"unsafe"
)

// Константы inotify для Linux x86_64
const (
	SYS_INOTIFY_INIT1     = 294
	SYS_INOTIFY_ADD_WATCH = 254
	IN_CLOEXEC            = 0x80000
	IN_CREATE             = 0x00000100
	IN_DELETE             = 0x00000200
)

func main() {
	// Создаем временную директорию для наблюдения
	watchDir, err := os.MkdirTemp("", "inotify_watch_test_*")
	if err != nil {
		panic(err)
	}
	defer os.RemoveAll(watchDir)

	// 1. Инициализируем inotify
	r1, _, errNo := syscall.Syscall(
		SYS_INOTIFY_INIT1,
		uintptr(IN_CLOEXEC),
		0, 0,
	)
	if errNo != 0 {
		panic(fmt.Sprintf("inotify_init1 failed: %v", errNo))
	}
	inotifyFd := int(r1)
	defer syscall.Close(inotifyFd)

	fmt.Printf("[Inotify Engine] Initialized inotify FD: %d\n", inotifyFd)

	// 2. Регистрируем директорию для отслеживания событий создания и удаления
	mask := uint32(IN_CREATE | IN_DELETE)
	dirPtr, _ := syscall.BytePtrFromString(watchDir)

	rWd, _, errNo := syscall.Syscall(
		SYS_INOTIFY_ADD_WATCH,
		uintptr(inotifyFd),
		uintptr(unsafe.Pointer(dirPtr)),
		uintptr(mask),
	)
	if errNo != 0 {
		panic(fmt.Sprintf("inotify_add_watch failed: %v", errNo))
	}
	watchDescriptor := int(rWd)
	fmt.Printf("[Inotify Engine] Watching directory: %s (WD: %d)\n", watchDir, watchDescriptor)

	// 3. Фоновая горутина генерирует события файловой системы
	testFileName := "config_update.yaml"
	fullPath := filepath.Join(watchDir, testFileName)

	go func() {
		time.Sleep(100 * time.Millisecond)
		fmt.Printf("[Worker] Creating file: %s\n", testFileName)
		_ = os.WriteFile(fullPath, []byte("version: 2.0"), 0644)

		time.Sleep(100 * time.Millisecond)
		fmt.Printf("[Worker] Deleting file: %s\n", testFileName)
		_ = os.Remove(fullPath)
	}()

	// 4. Считываем события из inotifyFd
	buffer := make([]byte, 4096)
	eventsCount := 0

	for eventsCount < 2 {
		n, err := syscall.Read(inotifyFd, buffer)
		if err != nil {
			panic(err)
		}

		offset := 0
		for offset < n {
			// Размер базовой структуры InotifyEvent = 16 байт
			if offset+16 > n {
				break
			}

			eventMask := binary.LittleEndian.Uint32(buffer[offset+4 : offset+8])
			nameLen := binary.LittleEndian.Uint32(buffer[offset+12 : offset+16])

			fileName := ""
			if nameLen > 0 && offset+16+int(nameLen) <= n {
				rawName := buffer[offset+16 : offset+16+int(nameLen)]
				fileName = strings.TrimRight(string(rawName), "\x00")
			}

			if eventMask&IN_CREATE != 0 {
				fmt.Printf("[Inotify Event] File CREATED: %q (Mask: 0x%X)\n", fileName, eventMask)
				eventsCount++
			} else if eventMask&IN_DELETE != 0 {
				fmt.Printf("[Inotify Event] File DELETED: %q (Mask: 0x%X)\n", fileName, eventMask)
				eventsCount++
			}

			offset += 16 + int(nameLen)
		}
	}

	fmt.Println("Inotify filesystem monitoring finished successfully!")
}
```

## Под капотом

Как устроен inotify в ядре Linux:
1. Вызов `inotify_add_watch` привязывает структуру `inotify_inode_mark` к целевому `struct inode` директории в ядре.
2. Когда системный вызов `openat(O_CREAT)` или `unlinkat()` изменяет директорию, подсистема VFS ядра вызывает хук `fsnotify_create()` / `fsnotify_unlink()`.
3. Ядро формирует событие `inotify_kernel_event`, помещает его в очередь `inotify_device` и будит читающий процесс.
4. Популярные библиотеки слежения за файлами на Go (например, `fsnotify/fsnotify`) под капотом на Linux используют ровно этот механизм `inotify`.

## Подводные камни

1. **Не рекурсивный характер inotify**: Вызов `inotify_add_watch` на директорию отслеживает только файлы внутри неё. Он **не отслеживает подпапки**! Для рекурсивного слежения библиотека обязана вручную обходить всё дерево папок и регистрировать watch descriptor на каждую поддиректорию.
2. **Лимит очередей (`/proc/sys/fs/inotify/max_user_watches`)**: По умолчанию в Linux лимит составляет от 8 192 до 524 288 дескрипторов. При попытке следить за деревом с миллионом файлов `inotify_add_watch` вернет ошибку `ENOSPC`.
3. **Переполнение буфера событий (`IN_Q_OVERFLOW`)**: Если события генерируются быстрее, чем приложение их считывает, очередь ядра переполнится, и ядро отправит событие `IN_Q_OVERFLOW`, потеряв промежуточные события.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных Kubernetes контроллерах и системах безопасности ядра переходят с `inotify` на `fanotify` или `eBPF`?»
**Ответ:**
1. **Отсутствие контроля доступа**: `inotify` только пассивно уведомляет о факте события, но не может **заблокировать или запретить** операцию.
2. **`fanotify` (Filesystem Access Notification)**: Позволяет антивирусам и audit-системам синхронно перехватывать системный вызов `open()` / `execve()` до его исполнения и возвращать ядру вердикт: `FAN_ALLOW` (разрешить) или `FAN_DENY` (запретить с `EPERM`).
3. **eBPF (LSM Hooks)**: eBPF позволяет отслеживать и фильтровать системные вызовы с нулевым оверхедом прямо в ядре без создания пользователей дескрипторов.
