# Детальный разбор Edge-Triggered против Level-Triggered epoll и обязательный цикл вычитки до EAGAIN

## Условие

Напишите программу, демонстрирующую **edge-triggered** (`EPOLLET`) vs **level-triggered** (`EPOLLIN`) `epoll`. Объясните, почему ET требует неблокирующих fd и цикл чтения до `EAGAIN`.

## Теория

Разница между Level-Triggered (LT) и Edge-Triggered (ET) является классическим вопросом архитектуры сетевых серверов:

**Level-Triggered (LT)**:
- Модель **состояния**: Событие активно, пока условие истинно (буфер не пуст).
- Если в сокете есть 100 байт, а программа прочитала 10 байт, следующий `epoll_wait` **снова немедленно проснется**, напоминая о 90 оставшихся байтах.
- Опасность: Избыточные context switches ядра при частичном чтении.

**Edge-Triggered (ET / `EPOLLET`)**:
- Модель **изменения состояния (фронт импульса)**: Событие генерируется **только один раз** в момент прихода новых данных по сети.
- Если программа прочитала 10 байт из 100 и уснула, `epoll_wait` **больше не проснется никогда** (оставшиеся 90 байт зависнут в ядре навсегда, пока клиент не пришлет еще один пакет).
- **Железные правила Edge-Triggered режима**:
  1. Дескриптор сокета **обязан** быть неблокирующим (`O_NONBLOCK`).
  2. Чтение **обязано** выполняться в бесконечном цикле `for { read() }` строго до получения ошибки `EAGAIN` / `EWOULDBLOCK`.
  3. Только после получения `EAGAIN` поток имеет право снова засыпать в `epoll_wait`.

## Решение по шагам

1. Создайте пару неблокирующих дескрипторов pipe.
2. Зарегистрируйте дескриптор чтения в epoll с флагом `syscall.EPOLLET`.
3. Запишите в pipe 30 байт данных.
4. Вызовите `syscall.EpollWait` — событие сработает один раз.
5. Реализуйте правильный цикл вычитки: в цикле `for` читайте порциями по 8 байт до получения ошибки `syscall.EAGAIN`.
6. Убедитесь, что все 30 байт вычитаны полностью без зависания.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"syscall"
)

// DrainEdgeTriggeredFD полностью вычитывает все доступные байты из ET дескриптора
func DrainEdgeTriggeredFD(fd int) ([]byte, error) {
	var totalData []byte
	chunk := make([]byte, 8) // Читаем небольшими порциями для демонстрации цикла

	for {
		n, err := syscall.Read(fd, chunk)
		if n > 0 {
			totalData = append(totalData, chunk[:n]...)
		}

		if err != nil {
			// На неблокирующем сокете EAGAIN сигнализирует о полном исчерпании буфера
			if errors.Is(err, syscall.EAGAIN) || errors.Is(err, syscall.EWOULDBLOCK) {
				// Буфер полностью пуст - корректный выход из цикла!
				break
			}
			// Реальная ошибка I/O
			return totalData, err
		}

		if n == 0 {
			// Удаленный конец закрыт (EOF)
			break
		}
	}

	return totalData, nil
}

func main() {
	// 1. Создаем pipe
	var fds [2]int
	_ = syscall.Pipe(fds[:])
	readFd := fds[0]
	writeFd := fds[1]
	defer syscall.Close(readFd)
	defer syscall.Close(writeFd)

	// ОБЯЗАТЕЛЬНОЕ ПРАВИЛО: Дескриптор обязан быть неблокирующим!
	_ = syscall.SetNonblock(readFd, true)

	// 2. Создаем epoll и регистрируем с EPOLLET
	epfd, _ := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	defer syscall.Close(epfd)

	ev := syscall.EpollEvent{
		Events: syscall.EPOLLIN | syscall.EPOLLET, // Режим Edge-Triggered
		Fd:     int32(readFd),
	}
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, readFd, &ev)
	fmt.Println("[EPOLLET Engine] Registered descriptor with EPOLLIN | EPOLLET.")

	// 3. Отправляем 32 байта данных
	msg := []byte("EDGE_TRIGGERED_STREAM_PACKET_001")
	_, _ = syscall.Write(writeFd, msg)
	fmt.Printf("[Producer] Written %d bytes into pipe.\n", len(msg))

	// 4. Ожидаем событие в epoll_wait
	events := make([]syscall.EpollEvent, 4)
	nEvents, err := syscall.EpollWait(epfd, events, 1000)
	if err != nil {
		panic(err)
	}
	fmt.Printf("[EPOLLET Engine] EpollWait returned %d ready event(s).\n", nEvents)

	// 5. Вызываем правильный цикл вычитки до EAGAIN
	drainedData, err := DrainEdgeTriggeredFD(readFd)
	if err != nil {
		panic(err)
	}

	fmt.Printf("[Consumer] Fully drained %d bytes until EAGAIN: %q\n", len(drainedData), string(drainedData))
	fmt.Println("Edge-Triggered drain pattern executed flawlessly!")
}
```

ℹ️ Правильный паттерн вычитки данных в цикле до EAGAIN в режиме Edge-Triggered

## Под капотом

Почему Edge-Triggered быстрее Level-Triggered в HighLoad:
1. В Level-Triggered режиме при каждом вызове `epoll_wait` ядро проверяет статус сокета (`poll`). Если буфер еще не вычитан до конца, ядро тратит время на повторное копирование дескриптора в массив событий.
2. В Edge-Triggered режиме дескриптор удаляется из очереди готовности ядра `rdllist` сразу после первого пробуждения.
3. Программа за один системный переход в пространство пользователя вычитывает все накопившиеся байты в цикле `read()`, минимизируя общее количество вызовов `epoll_wait`.

## Подводные камни

1. **Блокирующий сокет в цикле ET**: Если забыть сделать `SetNonblock(true)`, последняя итерация цикла чтения (когда данных больше нет) **заблокирует весь системный поток намертво**!
2. **Неполное чтение**: Если выйти из цикла до получения `EAGAIN`, оставшиеся байты останутся в буфере, а epoll больше никогда не проснется.
3. **Голодание других сокетов**: Если один клиент шлет терабайты данных, цикл вычитки до `EAGAIN` может монополизировать поток. Вводят счетчик максимального числа итераций (например, не более 64 КБ за один раунд).

## На собеседовании

**Вопрос с собеседования:** «Какой режим epoll (LT или ET) использует Go Netpoller под капотом и почему?»
**Ответ:**
Рантайм Go Netpoller (`runtime/netpoll_epoll.go`) регистрирует сокеты **строго с флагом `_EPOLLIN | _EPOLLOUT | _EPOLLRDHUP | _EPOLLET` (Edge-Triggered)**!
Причины:
1. Сокеты в Go всегда неблокирующие (`O_NONBLOCK`).
2. Рантайм Go самостоятельно управляет парковкой горутин: горутина паркуется только тогда, когда системный вызов вернул `EAGAIN`.
3. Режим `EPOLLET` исключает избыточные системные пробуждения ядра при частичной передаче данных, обеспечивая наивысшую масштабируемость планировщика GMP.
