# Масштабируемый EpollWait: одновременное мультиплексирование сотен сокетов (Fan-In I/O)

## Условие

**Epoll wait**: Используйте `unix.EpollWait()` для ожидания событий на множестве сокетов одновременно.

## Теория

Главное преимущество `epoll` над традиционными механизмами ввода-вывода проявляется при росте числа дескрипторов от десятков до сотен тысяч.

**Паттерн Fan-In Multiplexing**:
- Один рабочий поток может эффективно отслеживать готовность сотен независимых источников данных (сетевые клиенты, UNIX-сокеты, пайпы, таймеры `timerfd`, очереди сигналов `signalfd`).
- Системный вызов:
  ```go
  nEvents, err := syscall.EpollWait(epfd, eventsSlice, timeout)
  ```
- Ядро Linux заполняет срез `eventsSlice` только теми структурами `EpollEvent`, на которых произошли события.
- Алгоритмическая сложность выборки готовых событий составляет строго **\(O(K)\)**, где \(K\) — число реально готовых сокетов, независимо от того, сколько сотен тысяч сокетов зарегистрировано в epoll (\(N\)).

## Решение по шагам

1. Создайте инстанс epoll через `syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)`.
2. Создайте массив из 10 пар дескрипторов pipe (симулирующих 10 активных сетевых соединений).
3. Зарегистрируйте все 10 дескрипторов чтения в epoll.
4. В фоновой горутине отправьте данные в 3 произвольных пайпа из 10.
5. Вызовите `syscall.EpollWait` с буфером событий.
6. Убедитесь, что `EpollWait` вернул ровно 3 готовых события за один системный вызов.
7. Считайте данные и освободите все дескрипторы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
	"time"
)

func main() {
	// 1. Создаем общий epoll instance
	epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(epfd)

	const numChannels = 10
	var readFds [numChannels]int
	var writeFds [numChannels]int

	// 2. Создаем 10 независимых каналов (pipes)
	for i := 0; i < numChannels; i++ {
		var p [2]int
		if err := syscall.Pipe(p[:]); err != nil {
			panic(err)
		}
		readFds[i] = p[0]
		writeFds[i] = p[1]
		defer syscall.Close(p[0])
		defer syscall.Close(p[1])

		_ = syscall.SetNonblock(p[0], true)

		// Регистрируем каждый дескриптор в epoll
		event := syscall.EpollEvent{
			Events: syscall.EPOLLIN,
			Fd:     int32(p[0]),
		}
		if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, p[0], &event); err != nil {
			panic(err)
		}
	}
	fmt.Printf("[Multiplexer] Successfully registered %d channel descriptors in EPFD %d.\n", numChannels, epfd)

	// 3. Отправляем данные только в каналы с индексами 2, 5 и 8
	activeIndices := []int{2, 5, 8}
	go func() {
		time.Sleep(50 * time.Millisecond)
		for _, idx := range activeIndices {
			payload := []byte(fmt.Sprintf("BURST_PACKET_FOR_CHANNEL_%d", idx))
			_, _ = syscall.Write(writeFds[idx], payload)
		}
		fmt.Printf("[Producers] Dispatched 3 packets to channels %v.\n", activeIndices)
	}()

	// 4. Ожидаем события через EpollWait
	events := make([]syscall.EpollEvent, numChannels)
	fmt.Println("[Multiplexer] Calling EpollWait (waiting for any socket activity)...")

	nReady, err := syscall.EpollWait(epfd, events, 2000)
	if err != nil {
		panic(err)
	}

	fmt.Printf("[Multiplexer] EpollWait returned %d ready channels:\n", nReady)
	buf := make([]byte, 128)
	for i := 0; i < nReady; i++ {
		ev := events[i]
		readyFd := int(ev.Fd)

		n, _ := syscall.Read(readyFd, buf)
		fmt.Printf("  -> Ready FD %2d triggered EPOLLIN (0x%X) | Payload: %q\n",
			readyFd, ev.Events, string(buf[:n]))
	}

	fmt.Println("Multi-socket epoll multiplexing verified successfully!")
}
```

ℹ️ Масштабируемый опрос множества сокетов за один системный вызов EpollWait

## Под капотом

Как ядро Linux формирует список готовых дескрипторов:
1. В структуре `eventpoll` ядра дескрипторы сокетов хранятся в двусвязном списке `rdllist` (Ready List).
2. Когда сокет 2, 5 и 8 получают данные, их callback-функции `ep_poll_callback` добавляют дескрипторы в `rdllist`.
3. Поток, спящий в `epoll_wait`, пробуждается.
4. Ядро копирует структуры `epoll_event` из `rdllist` напрямую в пользовательский массив `events` в памяти Go через `copy_to_user()`.
5. Поток возвращается в пространство пользователя за считанные микросекунды, обработав только активные сокеты без холостого перебора неактивных каналов.

## Подводные камни

1. **Недостаточный размер массива `events`**: Если произошло 100 событий, а срез `events` имеет длину 16, ядро вернет только 16 событий. Остальные 84 события останутся в очереди и будут возвращены на следующих итерациях `epoll_wait`.
2. **Голодание дескрипторов (Starvation)**: Если один клиент шлет гигантский непрерывный поток данных, а сервер читает его в цикле до конца, остальные 99 клиентов не получат процессорного времени. В продакшене вводят лимит на количество чтений за одну итерацию (например, не более 64 КБ на соединение).
3. **Закрытие дескрипторов другими потоками**: Если закрыть дескриптор в одном потоке, пока другой поток ожидает его в `epoll_wait`, в старых версиях ядер это могло приводить к race conditions.

## На собеседовании

**Вопрос с собеседования:** «Что такое системный вызов `epoll_pwait` / `epoll_pwait2` и зачем он нужен?»
**Ответ:**
`epoll_pwait(epfd, events, maxevents, timeout, sigmask)` позволяет **атомарно** установить временную маску сигналов на время ожидания событий. Это устраняет фундаментальное состояние гонки (Race Condition): если сигнал поступает ровно между снятием маски сигналов и входом в `epoll_wait`, обычный `epoll_wait` пропустит сигнал и зависнет. `epoll_pwait` гарантирует безопасную обработку сигналов и I/O событий. `epoll_pwait2` (Linux 5.11+) дополнительно добавляет поддержку наносекундных таймаутов (`struct timespec`).
