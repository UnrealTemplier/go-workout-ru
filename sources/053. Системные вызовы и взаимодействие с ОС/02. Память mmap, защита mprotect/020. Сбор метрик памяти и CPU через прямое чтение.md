# Сбор метрик памяти и CPU через прямое чтение /proc/meminfo и /proc/loadavg без сторонних библиотек

## Условие

**Получение информации о системе через syscall.**: Выведите количество свободной памяти, загрузку CPU и другие метрики, используя `syscall.Sysctl` (на macOS/BSD) или чтение `/proc/meminfo` на Linux с парсингом, но с использованием низкоуровневых вызовов (`open`, `read`).

## Теория

В операционной системе Linux виртуальная файловая система `/proc` (procfs) является фундаментальным шлюзом к структурам данных ядра. Файлы в `/proc` физически не существуют на диске: при их чтении ядро динамически генерирует текст на основе текущего состояния внутренних счетчиков.

**Ключевые источники метрик Linux**:
1. `/proc/meminfo`:
   - `MemTotal`: Полный объем физической оперативной памяти.
   - `MemFree`: Полностью неиспользуемая память.
   - `MemAvailable`: Реально доступная память для запуска новых приложений без ухода в Swap (учитывает Page Cache и буферы, которые ядро может мгновенно сбросить).
   - `Cached` / `Buffers`: Память, занятая кэшем файловой системы.
2. `/proc/loadavg`:
   - Три числа: средняя длина очереди выполнения (Run Queue Length) за последние 1, 5 и 15 минут (Load Average).
   - Число активных и общих потоков планировщика ядра Linux.

Использование низкоуровневых системных вызовов `syscall.Open` и `syscall.Read` для чтения `/proc` позволяет агентам мониторинга (Prometheus node-exporter, Datadog agent) собирать метрики хоста с минимальными затратами CPU и нулевыми аллокациями памяти.

## Решение по шагам

1. Откройте `/proc/meminfo` через `syscall.Open("/proc/meminfo", syscall.O_RDONLY, 0)`.
2. Выделите статический буфер байт (например, 2048 байт) и прочитайте данные через `syscall.Read(fd, buf)`.
3. Закройте дескриптор через `syscall.Close(fd)`.
4. Распарсите строки `MemTotal` и `MemAvailable` простым сканированием байт без тяжелых регулярок.
5. Откройте `/proc/loadavg` и прочитайте показатели Load Average.
6. Рассчитайте процент свободной и занятой памяти сервера.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"strconv"
	"syscall"
)

// ReadProcFile читает содержимое псевдофайла procfs через сырой системный вызов read()
func ReadProcFile(path string, maxBytes int) ([]byte, error) {
	fd, err := syscall.Open(path, syscall.O_RDONLY, 0)
	if err != nil {
		return nil, err
	}
	defer func() {
		_ = syscall.Close(fd)
	}()

	buf := make([]byte, maxBytes)
	n, err := syscall.Read(fd, buf)
	if err != nil {
		return nil, err
	}
	return buf[:n], nil
}

// ParseMeminfoValue извлекает числовое значение в килобайтах по имени ключа
func ParseMeminfoValue(data []byte, key string) uint64 {
	keyBytes := []byte(key + ":")
	idx := bytes.Index(data, keyBytes)
	if idx == -1 {
		return 0
	}

	lineEnd := bytes.IndexByte(data[idx:], '\n')
	if lineEnd == -1 {
		lineEnd = len(data[idx:])
	}
	line := string(data[idx : idx+lineEnd])

	fields := bytes.Fields([]byte(line))
	if len(fields) >= 2 {
		val, _ := strconv.ParseUint(string(fields[1]), 10, 64)
		return val
	}
	return 0
}

func main() {
	// 1. Читаем /proc/meminfo через сырые дескрипторы
	memData, err := ReadProcFile("/proc/meminfo", 4096)
	if err != nil {
		panic(fmt.Sprintf("Failed to read /proc/meminfo: %v", err))
	}

	memTotalKB := ParseMeminfoValue(memData, "MemTotal")
	memAvailableKB := ParseMeminfoValue(memData, "MemAvailable")
	memFreeKB := ParseMeminfoValue(memData, "MemFree")
	cachedKB := ParseMeminfoValue(memData, "Cached")

	usedKB := memTotalKB - memAvailableKB
	usedPercent := float64(usedKB) * 100.0 / float64(memTotalKB)

	fmt.Println("=== HOST MEMORY METRICS (/proc/meminfo) ===")
	fmt.Printf("MemTotal:      %8d MB\n", memTotalKB/1024)
	fmt.Printf("MemAvailable:  %8d MB\n", memAvailableKB/1024)
	fmt.Printf("MemFree:       %8d MB\n", memFreeKB/1024)
	fmt.Printf("Cached Buffer: %8d MB\n", cachedKB/1024)
	fmt.Printf("RAM Usage:     %.2f%% utilized\n", usedPercent)

	// 2. Читаем /proc/loadavg
	loadData, err := ReadProcFile("/proc/loadavg", 128)
	if err == nil {
		fmt.Println("\n=== CPU LOAD AVERAGE (/proc/loadavg) ===")
		fmt.Printf("Raw load metrics: %s", string(loadData))
	}
}
```

## Под капотом

Почему чтение `/proc` через `os.Stat` или размер файла возвращает 0:
1. Если выполнить `stat /proc/meminfo`, размер файла в поле `st_size` всегда равен `0`.
2. Ядро Linux не хранит эти данные на диске и не рассчитывает размер заранее. Данные генерируются «на лету» в момент вызова `sys_read`.
3. Функция `os.ReadFile()` внутри делает оптимизацию: узнает размер файла через `stat` и выделяет буфер размера `st_size + 1`. Для procfs файлов `st_size == 0`, поэтому `os.ReadFile` вынужден постоянно реаллоцировать слайс через `append()`.
4. Прямой `syscall.Read` со статическим буфером 2–4 КБ считывает всю информацию за ровно **один системный вызов** без единой реаллокации памяти.

## Подводные камни

1. **Использование `MemFree` вместо `MemAvailable`**: `MemFree` показывает только страницы, вообще не содержащие никаких данных. Ядро Linux использует почти всю свободную память под Page Cache (`Cached`). Правильным индикатором доступной памяти является строго `MemAvailable` (появился в Linux 3.14).
2. **Парсинг в контейнерах cgroups**: Внутри Docker/Kubernetes контейнера чтение `/proc/meminfo` возвращает объем памяти **хостовой ноды**, а не лимит контейнера! Для получения лимитов пода необходимо читать псевдофайлы cgroups: `/sys/fs/cgroup/memory.max` (cgroups v2) или `/sys/fs/cgroup/memory/memory.limit_in_bytes` (cgroups v1).
3. **Sysctl на macOS**: На macOS и FreeBSD псевдофайловой системы `/proc` нет. Там системные метрики запрашиваются через вызов `syscall.Sysctl` с MIB-массивами (`CTL_HW`, `HW_MEMSIZE`).

## На собеседовании

**Вопрос с собеседования:** «Почему приложение в контейнере Kubernetes падает с ошибкой OOMKilled (Exit Code 137), хотя мониторинг `/proc/meminfo` показывал наличие 100 ГБ свободной памяти на сервере?»
**Ответ:**
1. Механизм Procfs не изолирован для контейнеров: контейнер видит память всей физической ноды (128 ГБ).
2. Ограничение ресурсов контейнера задается через механизм **Linux cgroups** (например, `resources.limits.memory: 2Gi`).
3. При превышении лимита cgroups (2 ГБ) ядро инициирует OOM Killer конкретной контрольной группы контейнера, убивая под, независимо от того, сколько свободной памяти есть на физической машине.
Для решения этой проблемы в контейнерах используют утилиту `lxcfs`, которая виртуализирует `/proc` в соответствии с лимитами cgroups.
