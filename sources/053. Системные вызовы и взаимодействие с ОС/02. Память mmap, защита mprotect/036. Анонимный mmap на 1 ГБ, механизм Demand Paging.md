# Анонимный mmap на 1 ГБ, механизм Demand Paging и анализ виртуальной памяти VSS против RSS

## Условие

Напишите программу с **anonymous mmap** (`MAP_ANONYMOUS`) для аллокации 1 GB. Объясните, как ОС лениво подкладывает физические страницы (demand paging). Покажите разницу `VSS` vs `RSS` через `/proc/self/status`.

## Теория

Для эффективного управления памятью ядро Linux разделяет понятия виртуальной и физической памяти:

1. **VSS (Virtual Set Size / VmSize)**:
   - Полный объем виртуального адресного пространства, зарезервированного процессом.
   - Включает все выделенные области: стек, кучу Go, библиотеки `.so` и регионы `mmap`.
   - Резервирование 1 ГБ или 1 ТБ виртуальной памяти в 64-битной ОС практически бесплатно: ядро лишь создает записи диапазонов адресов в структуре `mm_struct`.
2. **RSS (Resident Set Size / VmRSS)**:
   - Реальный объем **физической оперативной памяти (RAM)**, которую процесс занимает в микросхемах памяти в данный момент.

**Механика Demand Paging (Ленивая подкачка страниц)**:
- Когда программа вызывает `syscall.Mmap(-1, 0, 1024*1024*1024, PROT_READ|PROT_WRITE, MAP_ANON|MAP_PRIVATE)`:
  - `VmSize` (VSS) процесса мгновенно вырастает на **1 048 576 КБ (1 ГБ)**.
  - `VmRSS` (RSS) процесса **не увеличивается ни на один байт**!
  - Все страницы мапятся на единую глобальную физическую страницу нулей ядра (Zero Page).
- Только когда процесс выполняет реальную запись `slice[i] = 42`:
  - Процессор фиксирует аппаратное исключение **Page Fault**.
  - Обработчик ядра Linux выделяет одну физическую страницу RAM (4 КБ), обнуляет её и связывает с виртуальным адресом.
  - `VmRSS` увеличивается ровно на 4 КБ.

## Решение по шагам

1. Напишите функцию для парсинга `VmSize` и `VmRSS` из `/proc/self/status`.
2. Замерьте исходные показатели памяти процесса.
3. Выделите 1 ГБ (1024 * 1024 * 1024 байт) через анонимный `syscall.Mmap`.
4. Замерьте показатели: VmSize вырос на 1 ГБ, VmRSS остался прежним.
5. Запишите данные в 10 000 страниц (40 МБ) с шагом 4096 байт.
6. Замерьте показатели: VmRSS вырос ровно на 40 МБ.
7. Освободите память через `syscall.Munmap`.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"os"
	"strconv"
	"strings"
	"syscall"
)

// GetProcessMemoryMetrics считывает VmSize и VmRSS из /proc/self/status
func GetProcessMemoryMetrics() (vssKB uint64, rssKB uint64) {
	data, err := os.ReadFile("/proc/self/status")
	if err != nil {
		return 0, 0
	}

	lines := bytes.Split(data, []byte("\n"))
	for _, line := range lines {
		s := string(line)
		if strings.HasPrefix(s, "VmSize:") {
			fields := strings.Fields(s)
			if len(fields) >= 2 {
				vssKB, _ = strconv.ParseUint(fields[1], 10, 64)
			}
		} else if strings.HasPrefix(s, "VmRSS:") {
			fields := strings.Fields(s)
			if len(fields) >= 2 {
				rssKB, _ = strconv.ParseUint(fields[1], 10, 64)
			}
		}
	}
	return vssKB, rssKB
}

func main() {
	const oneGB = 1024 * 1024 * 1024 // 1 ГБ
	pageSize := syscall.Getpagesize()

	fmt.Println("=== DEMAND PAGING: VSS (VIRTUAL) VS RSS (PHYSICAL RAM) ===")

	// 1. Исходное состояние процесса
	vss0, rss0 := GetProcessMemoryMetrics()
	fmt.Printf("[Baseline]    VSS (VmSize): %8d MB | RSS (VmRSS): %6d MB\n", vss0/1024, rss0/1024)

	// 2. Выделяем 1 ГБ анонимной памяти через mmap
	mmapBuf, err := syscall.Mmap(
		-1,
		0,
		oneGB,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		panic(err)
	}
	defer func() {
		_ = syscall.Munmap(mmapBuf)
	}()

	vss1, rss1 := GetProcessMemoryMetrics()
	fmt.Printf("[After 1GB Mmap] VSS: %8d MB (+%d MB) | RSS: %6d MB (+%d MB)\n",
		vss1/1024, (vss1-vss0)/1024, rss1/1024, (rss1-rss0)/1024)
	fmt.Println("  -> Linux reserved 1 GB of Virtual Address Space with 0 MB Physical RAM allocated!")

	// 3. Касаемся (Touch) ровно 10 240 страниц по 4 КБ = 40 МБ
	const touchPages = 10240
	for i := 0; i < touchPages; i++ {
		offset := i * pageSize
		mmapBuf[offset] = 0x5A // Запись триггерит аппаратный Page Fault
	}

	vss2, rss2 := GetProcessMemoryMetrics()
	expectedMB := (touchPages * pageSize) / (1024 * 1024)
	fmt.Printf("[After Touching 40MB] VSS: %8d MB | RSS: %6d MB (+%d MB Physical RAM)\n",
		vss2/1024, rss2/1024, (rss2-rss1)/1024)
	fmt.Printf("  -> Demand Paging allocated exactly %d MB of physical RAM pages on first write!\n", expectedMB)
}
```

## Под капотом

Что происходит внутри ядра Linux при первом обращении к странице:
1. Виртуальный адрес мапится в архитектурное дерево VMA.
2. В PTE выставляется флаг `PTE_SPECIAL`, указывающий на статическую глобальную страницу нулей `empty_zero_page`. Любое чтение возвращает нули без выделения RAM.
3. При первой инструкции записи процессор фиксирует ошибку Page Fault (`do_anonymous_page()` в ядре).
4. Аллокатор ядра (`alloc_zeroed_user_highpage_movable`) выделяет физический фрейм памяти из списка свободных страниц (Buddy Allocator).
5. Ядро прописывает физический адрес фрейма в PTE, снимает защиту от записи и возобновляет выполнение инструкции процессора.

## Подводные камни

1. **Иллюзия бесконечной памяти**: Если приложение зарезервирует 100 ГБ памяти через `mmap` на сервере с 16 ГБ RAM, аллокация пройдет мгновенно. Но когда процесс начнет заполнять эти страницы данными, физическая RAM исчерпается, и ядро запустит OOM Killer.
2. **Метрики контейнеров**: Kubernetes следит за метрикой `container_memory_working_set_bytes` (на базе RSS). Резервирование VSS не влияет на лимиты пода, но рост RSS приводит к выселению (Eviction) пода.
3. **Очистка памяти через `MADV_DONTNEED`**: Вызов `syscall.Madvise(ptr, len, syscall.MADV_DONTNEED)` сообщает ядру, что данные страниц больше не нужны. Ядро мгновенно сбрасывает RSS обратно в 0, сохраняя VSS.

## На собеседовании

**Вопрос с собеседования:** «Чем отличаются метрики памяти VSS, RSS, PSS и USS в профилировании Linux процессов?»
**Ответ:**
- **VSS (Virtual Set Size)**: Полная виртуальная память процесса (включая невыделенные страницы).
- **RSS (Resident Set Size)**: Физическая память процесса, включая разделяемые библиотеки (`libc.so`), которые используются десятками других процессов.
- **PSS (Proportional Set Size)**: Физическая память, где размер разделяемых библиотек делится пропорционально между всеми процессами, которые их используют (наиболее точная оценка реального расхода RAM).
- **USS (Unique Set Size)**: Память, которая принадлежит **исключительно** этому процессу (будет немедленно возвращена ОС при его завершении).
