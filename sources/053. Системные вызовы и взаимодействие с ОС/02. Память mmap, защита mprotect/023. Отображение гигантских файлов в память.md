# Отображение гигантских файлов в память через unix.Mmap вместо io.ReadAll для экономии RAM

## Условие

**Memory-Mapped Files (`mmap`)**: Открой большой файл через `os.OpenFile`. Вместо `io.ReadAll` (который копирует данные в RAM), вызови `unix.Mmap`. Это системный вызов, который "проецирует" файл прямо на виртуальную память процесса. Ты получишь `[]byte`. Чтение этого среза будет автоматически читать данные с диска силами ОС! (Не забудь `unix.Munmap`).

## Теория

Чтение больших файлов (например, дампа базы данных, ML-модели на 10 ГБ или видеофайла) стандартным методом `io.ReadAll(file)` — распространенная ошибка начинающих разработчиков:
1. `io.ReadAll` циклически выделяет буферы в куче Go, постоянно реаллоцируя срез (`growslice`).
2. Для чтения 10 ГБ файла приложению потребуется выделить 10–20 ГБ физической оперативной памяти в куче Go.
3. Процесс с высокой вероятностью упадет по OOM (Out Of Memory) или заморозит сервис гигантской паузой сборщика мусора при сканировании миллиардов байт.

**Техника Zero-Copy чтения через Memory-Mapped Files (`mmap`)**:
- Вместо загрузки файла в кучу вызывается системный вызов `syscall.Mmap(fd, 0, fileSize, syscall.PROT_READ, syscall.MAP_SHARED)`.
- Возвращенный срез `[]byte` занимает в куче Go ровно **24 байта** (размер заголовка слайса: указатель на память, длина и емкость).
- Физическая память расходуется постранично силами ядра Linux через Page Cache.
- При сканировании среза процессор подгружает только текущую страницу памяти (4 КБ). Уже прочитанные страницы операционная система автоматически вытесняет при нехватке RAM.

## Решение по шагам

1. Создайте файл большого размера (например, 16 МБ) с тестовыми маркерами в начале, середине и конце.
2. Откройте файл через `os.OpenFile(path, os.O_RDONLY, 0)`.
3. Получите дескриптор `int(file.Fd())` и размер файла.
4. Вызовите `syscall.Mmap(fd, 0, int(size), syscall.PROT_READ, syscall.MAP_SHARED)`.
5. Читайте данные по произвольным индексам среза `[]byte` без промежуточных аллокаций.
6. Замерьте, что потребление кучи Go `runtime.MemStats.HeapAlloc` равно 0 байт.
7. Освободите память через `syscall.Munmap(data)`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"syscall"
)

func main() {
	fileName := "large_dataset.dat"
	const dataSize = 16 * 1024 * 1024 // 16 МБ

	// 1. Создаем тестовый файл фиксированного размера
	f, err := os.Create(fileName)
	if err != nil {
		panic(err)
	}
	// Устанавливаем размер файла 16 МБ
	if err := f.Truncate(dataSize); err != nil {
		panic(err)
	}
	// Записываем маркеры
	_, _ = f.WriteAt([]byte("START_MAGIC_HEADER_0xCAFE"), 0)
	_, _ = f.WriteAt([]byte("MIDDLE_MAGIC_RECORD_0xBEEF"), dataSize/2)
	_, _ = f.WriteAt([]byte("END_MAGIC_FOOTER_0xDEAD"), dataSize-32)
	_ = f.Close()
	defer os.Remove(fileName)

	// 2. Открываем файл для mmap
	file, err := os.OpenFile(fileName, os.O_RDONLY, 0)
	if err != nil {
		panic(err)
	}
	defer file.Close()

	stat, err := file.Stat()
	if err != nil {
		panic(err)
	}
	fileSize := int(stat.Size())

	// 3. Замеряем память до mmap
	var memBefore, memAfter runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&memBefore)

	// 4. Проецируем файл в виртуальную память через syscall.Mmap
	// PROT_READ гарантирует защиту страниц от случайной перезаписи
	mmapData, err := syscall.Mmap(
		int(file.Fd()),
		0,
		fileSize,
		syscall.PROT_READ,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(err)
	}
	defer func() {
		_ = syscall.Munmap(mmapData)
	}()

	runtime.ReadMemStats(&memAfter)
	heapAllocated := int64(memAfter.HeapAlloc) - int64(memBefore.HeapAlloc)

	fmt.Printf("File size mapped:      %d bytes (%.2f MB)\n", fileSize, float64(fileSize)/(1024*1024))
	fmt.Printf("Go Heap allocated:     %d bytes (Zero Heap Allocation!)\n", heapAllocated)

	// 5. Произвольный мгновенный доступ к данным в срезе
	startMarker := string(mmapData[:25])
	middleMarker := string(mmapData[dataSize/2 : dataSize/2+26])
	endMarker := string(mmapData[dataSize-32 : dataSize-9])

	fmt.Printf("\nRead Header from mmap: %s\n", startMarker)
	fmt.Printf("Read Middle from mmap: %s\n", middleMarker)
	fmt.Printf("Read Footer from mmap: %s\n", endMarker)
}
```

ℹ️ Zero-Copy чтение файлов произвольного размера через syscall.Mmap без аллокаций в куче Go

**`Терминал`**

```bash
go run main.go
# Вывод:
# File size mapped:      16777216 bytes (16.00 MB)
# Go Heap allocated:     0 bytes (Zero Heap Allocation!)
#
# Read Header from mmap: START_MAGIC_HEADER_0xCAFE
# Read Middle from mmap: MIDDLE_MAGIC_RECORD_0xBEEF
# Read Footer from mmap: END_MAGIC_FOOTER_0xDEAD
```

## Под капотом

Сравнение алгоритмической сложности:
- `io.ReadAll`: Временная сложность \(O(N)\), пространственная сложность в памяти Go \(O(N)\) физической RAM. Для каждого чтения ядро копирует страницы из кэша в буфер Go.
- `mmap`: Время выполнения системного вызова \(O(1)\) (константное создание записи VMA в ядре), пространственная сложность в куче Go \(O(1)\) (24 байта для структуры среза).
- Подкачка данных с диска выполняется аппаратно блоком MMU процессора по мере реального обращения к индексам массива.

## Подводные камни

1. **Изменение размера файла во время чтения**: Если другой фоновый процесс выполнит усечение (`truncate`) проецируемого файла, обращение к срезу `mmapData` за пределами новой границы мгновенно убьет процесс сигналом `SIGBUS`.
2. **Флаг защиты `PROT_READ`**: Если файл спроецирован только для чтения (`PROT_READ`), попытка записать в срез `mmapData[0] = 0` вызовет немедленный аппаратный `SIGSEGV` (Segmentation Fault).
3. **Лимит адресного пространства в 32-битных системах**: В 32-битных ОС виртуальное адресное пространство процесса ограничено 2–3 ГБ, из-за чего спроецировать 4 ГБ файл целиком невозможно. В 64-битных системах (48 бит адресации = 256 ТБ) этого ограничения нет.

## На собеседовании

**Вопрос с собеседования:** «Как системный вызов `madvise()` помогает ускорить работу с файлами, отображенными через `mmap`?»
**Ответ:**
Системный вызов `madvise(addr, len, advice)` сообщает ядру о планируемом паттерне доступа к памяти:
- `MADV_SEQUENTIAL`: Сообщает ядру, что файл будет читаться последовательно. Ядро агрессивно включает алгоритм упреждающего чтения (Read-Ahead), заранее подгружая следующие страницы с диска до того, как процесс к ним обратится.
- `MADV_RANDOM`: Отключает Read-Ahead, экономя I/O при случайном доступе (например, поиск по B-дереву индекса).
- `MADV_WILLNEED`: Принудительно инициирует асинхронную предварительную загрузку диапазона страниц в RAM.
