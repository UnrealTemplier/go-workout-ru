# Управление лимитами ресурсов: syscall.Getrlimit, syscall.Setrlimit и снятие лимита открытых дескрипторов

## Условие

**Resource limits**: Установите/получите resource limits через `syscall.Getrlimit()`, `syscall.Setrlimit()` (например, max open files).

## Теория

Ядро Linux защищает операционную систему от исчерпания ресурсов с помощью механизма **Resource Limits (rlimits)**.

Каждый ресурс процесса описывается структурой `syscall.Rlimit`:
```go
type Rlimit struct {
    Cur uint64 // Soft Limit (мягкий лимит)
    Max uint64 // Hard Limit (жесткий лимит)
}
```
- **Soft Limit (`rlim_cur`)**: Текущее действующее ограничение для процесса. При превышении этого порога ядро возвращает ошибку (например, `EMFILE`) или отправляет сигнал (`SIGXCPU`). Обычный непривилегированный процесс может произвольно изменять `Cur` в диапазоне от `0` до `Max`.
- **Hard Limit (`rlim_max`)**: Потолок, выше которого нельзя поднять Soft Limit. Увеличить Hard Limit может **только суперпользователь root** (или процесс с привилегией `CAP_SYS_RESOURCE`).

**Ключевые ресурсы (`RLIMIT_*`)**:
- `RLIMIT_NOFILE`: Максимальное количество открытых файловых дескрипторов на процесс (сокеты, файлы, пайпы). В большинстве дистрибутивов по умолчанию равно всего 1024. Для HighLoad сервера, принимающего 100 000 соединений, этот лимит необходимо поднимать при старте программы.
- `RLIMIT_AS`: Максимальный размер виртуальной памяти процесса.
- `RLIMIT_CORE`: Максимальный размер coredump файла (установка в `unlimited` включает генерацию дампов при авариях).

## Решение по шагам

1. Объявите экземпляр `var rlim syscall.Rlimit`.
2. Получите текущий лимит открытых файлов через `syscall.Getrlimit(syscall.RLIMIT_NOFILE, &rlim)`.
3. Выведите значения Soft Limit и Hard Limit.
4. Увеличьте `rlim.Cur` до максимально разрешенного `rlim.Max` (или безопасного значения, например 65535).
5. Примените новые лимиты системным вызовом `syscall.Setrlimit(syscall.RLIMIT_NOFILE, &rlim)`.
6. Проверьте повторным вызовом `Getrlimit`, что лимит успешно применился.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
)

// MaximizeOpenFileLimit поднимает лимит дескрипторов до максимального жесткого предела
func MaximizeOpenFileLimit() (uint64, error) {
	var rLim syscall.Rlimit

	// 1. Получаем текущие лимиты
	if err := syscall.Getrlimit(syscall.RLIMIT_NOFILE, &rLim); err != nil {
		return 0, fmt.Errorf("getrlimit failed: %w", err)
	}

	fmt.Printf("[Resource Limits] Initial NOFILE: Soft=%d, Hard=%d\n", rLim.Cur, rLim.Max)

	targetLimit := rLim.Max
	// Если жесткий лимит равен бесконечности, устанавливаем разумный максимум
	if targetLimit > 1048576 {
		targetLimit = 1048576
	}

	// 2. Устанавливаем Soft Limit равным целевому пределу
	rLim.Cur = targetLimit
	if err := syscall.Setrlimit(syscall.RLIMIT_NOFILE, &rLim); err != nil {
		return 0, fmt.Errorf("setrlimit failed: %w", err)
	}

	// 3. Проверяем обновленные значения
	var verifiedRLim syscall.Rlimit
	if err := syscall.Getrlimit(syscall.RLIMIT_NOFILE, &verifiedRLim); err != nil {
		return 0, fmt.Errorf("verification getrlimit failed: %w", err)
	}

	return verifiedRLim.Cur, nil
}

func main() {
	newLimit, err := MaximizeOpenFileLimit()
	if err != nil {
		panic(err)
	}

	fmt.Printf("[Resource Limits] Successfully boosted max open files limit to: %d\n", newLimit)
	fmt.Println("HighLoad TCP server is now ready to handle tens of thousands of concurrent connections!")
}
```

ℹ️ Программное повышение лимита открытых файловых дескрипторов процесса через Getrlimit и Setrlimit

**`Терминал`**

```bash

# Вывод:

```

## Под капотом

Что происходит внутри ядра при `syscall.Setrlimit`:
1. Ядро проверяет, не превышает ли запрошенный `rlim_cur` текущий `rlim_max`. Если превышает, ядро требует привилегию `capable(CAP_SYS_RESOURCE)`. Если прав нет, возвращается ошибка `EPERM` (Operation not permitted).
2. Ядро проверяет глобальный системный лимит файловых дескрипторов хоста `/proc/sys/fs/file-max`. Лимит процесса не может превышать глобальный пул дескрипторов ядра.
3. Обновляется структура `current->signal->rlim[resource]`. Все последующие проверки при вызовах `open()`, `accept()`, `socket()` будут использовать новое увеличенное значение.

## Подводные камни

1. **Попытка поднять `rlim.Cur` выше `rlim.Max` без root**: Непривилегированный процесс не может поднять лимит выше Hard Limit. Попытка вызовет `EPERM`. В Linux production окружении базовый Hard Limit настраивают в файле `/etc/security/limits.conf` или в systemd unit файле (`LimitNOFILE=1048576`).
2. **Лимит дескрипторов в Docker/K8s**: Контейнеры наследуют лимиты от демона dockerd/containerd. Если в Kubernetes манифесте ноды установлен лимит 1024, сервис не сможет принимать больше 1000 клиентов.
3. **Понижение Hard Limit**: Если непривилегированный процесс уменьшит `rlim_max`, он **никогда не сможет поднять его обратно** в рамках текущей сессии процесса.

## На собеседовании

**Вопрос с собеседования:** «Какие три параметра ядра Linux необходимо настроить для подготовки сервера к нагрузке в 1 000 000 активных TCP-соединений (C1000K challenge)?»
**Ответ:**
1. **Лимит файловых дескрипторов процесса**: `ulimit -n 1048576` (`RLIMIT_NOFILE`) и общесистемный `fs.file-max = 2097152`.
2. **Диапазон эфемерных портов и timewait**: `net.ipv4.ip_local_port_range = 1024 65535` и включение `net.ipv4.tcp_tw_reuse = 1`.
3. **Память TCP-буферов**: Ограничить минимальный размер буферов сокетов `net.ipv4.tcp_rmem = 4096 87380 4194304` и `net.ipv4.tcp_wmem = 4096 65536 4194304`, иначе 1 миллион соединений по 1 МБ буфера исчерпают 1 ТБ оперативной памяти.
