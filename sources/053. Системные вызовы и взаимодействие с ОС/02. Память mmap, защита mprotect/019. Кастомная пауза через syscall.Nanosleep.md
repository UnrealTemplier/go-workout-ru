# Кастомная пауза через syscall.Nanosleep и сравнение с time.Sleep (gopark и timers)

## Условие

Реализуйте «свой `sleep`» через `syscall.Nanosleep`. Объясните, почему raw syscall блокирует ОС-поток, и как Go-планировщик оборачивает это в `time.Sleep` (через `gopark` + timer thread).

## Теория

Системный вызов `syscall.Nanosleep(&req, &rem)`:
- Принимает структуру `Timespec{Sec, Nsec}` с желаемым временем задержки с наносекундной точностью.
- Если вызов прерывается сигналом ОС, в структуру `rem` записывается оставшееся неотгулянное время.
- **Главная проблема raw syscall**: Вызов `nanosleep` переводит текущий **поток операционной системы (M)** в состояние глубокого сна (`TASK_INTERRUPTIBLE`). Поток ОС замораживается ядром и не может выполнять никакой полезный код.

**Архитектурное превосходство `time.Sleep` в Go**:
В рантайме Go горутины — это дешевые легковесные абстракции (User-Level Threads). Было бы катастрофической растратой ресурсов блокировать реальный поток ОС `M` из-за того, что одна горутина решила уснуть на 10 миллисекунд.
Поэтому `time.Sleep(d)` устроен принципиально иначе:
1. Создается объект системного таймера `runtime.timer` и добавляется в локальную 4-арную кучу таймеров (P-timer heap).
2. Вызывается процедура планировщика **`runtime.gopark()`**.
3. Статус горутины переводится из `_Grunning` в `_Gwaiting` с причиной `waitReasonSleep`.
4. Горутина отвязывается от потока `M`.
5. Поток `M` **немедленно берет другую готовую горутину** и продолжает полезную работу на 100% CPU!
6. Когда таймер срабатывает, планировщик переводит горутину в `_Grunnable` и возвращает в очередь исполнения `runq`.

## Решение по шагам

1. Напишите функцию `RawSyscallSleep(d time.Duration) error`.
2. Переведите длительность в секунды и наносекунды для структуры `syscall.Timespec`.
3. Вызовите `syscall.Nanosleep(&req, &rem)` в цикле для обработки прерываний `EINTR`.
4. Запустите 100 параллельных горутин с `RawSyscallSleep` и замерьте количество потоков ОС.
5. Запустите 100 000 параллельных горутин с `time.Sleep` и убедитесь, что количество потоков ОС не возрастает.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
	"time"
)

// RawSyscallSleep блокирует системный поток ОС через ядро Linux
func RawSyscallSleep(d time.Duration) error {
	sec := int64(d / time.Second)
	nsec := int64(d % time.Second)

	req := syscall.Timespec{
		Sec:  sec,
		Nsec: nsec,
	}
	var rem syscall.Timespec

	for {
		err := syscall.Nanosleep(&req, &rem)
		if err == nil {
			return nil
		}
		// Если прервано сигналом ОС, досыпаем оставшееся время
		if err == syscall.EINTR {
			req = rem
			continue
		}
		return err
	}
}

func main() {
	fmt.Println("=== COMPARISON: RAW NANOSLEEP VS GO RUNTIME TIME.SLEEP ===")

	// 1. Тест сырого системного вызова nanosleep
	startRaw := time.Now()
	sleepDur := 150 * time.Millisecond

	fmt.Printf("Starting RawSyscallSleep for %v (locks current OS thread M)...\n", sleepDur)
	if err := RawSyscallSleep(sleepDur); err != nil {
		panic(err)
	}
	fmt.Printf("RawSyscallSleep finished in %v\n", time.Since(startRaw))

	// 2. Демонстрация time.Sleep на 10 000 горутинах
	fmt.Println("\nSpawning 10,000 concurrent sleeping goroutines via time.Sleep...")
	startGo := time.Now()
	done := make(chan struct{}, 10000)

	for i := 0; i < 10000; i++ {
		go func() {
			// gopark() паркует горутину без создания 10000 потоков ОС!
			time.Sleep(100 * time.Millisecond)
			done <- struct{}{}
		}()
	}

	for i := 0; i < 10000; i++ {
		<-done
	}
	fmt.Printf("10,000 goroutines slept and woke up concurrently in %v!\n", time.Since(startGo))
}
```

ℹ️ Сравнение блокирующего syscall.Nanosleep и кооперативного time.Sleep на 10 000 горутин

## Под капотом

Что происходит внутри планировщика Go:
1. Если бы в цикле из 10 000 горутин вызывался `RawSyscallSleep`:
   - Каждый вызов блокировал бы поток `M`.
   - Фоновый монитор `sysmon` видел бы заблокированные потоки и создавал новые потоки `M` через `newm()` для обслуживания оставшихся процессоров `P`.
   - Процесс быстро уперся бы в системный лимит `debug.SetMaxThreads` (по умолчанию 10 000 потоков) и упал с фатальной паникой `runtime: program exceeds 10000-thread limit`.
2. С `time.Sleep`:
   - Создается ровно столько потоков `M`, сколько задано в `GOMAXPROCS` (например, 8 или 16).
   - Все 10 000 спящих горутин хранятся как структуры данных в оперативной памяти (~20 МБ RAM).
   - Механизм таймеров Go интегрирован напрямую в Netpoller и цикл планировщика `stealWork`, пробуждая горутины с точностью до десятков микросекунд.

## Подводные камни

1. **Блокировка пула потоков CGO**: Вызов Си-функции, содержащей внутри `sleep()`, аналогичен `RawSyscallSleep`: поток `M` блокируется в Си-коде, заставляя Go порождать новые потоки `M`.
2. **Точность таймеров в Linux**: По умолчанию разрешение таймеров в ядре Linux зависит от параметра `CONFIG_HZ` (1000 Гц = 1 мс). Задержки менее 1 мс в `nanosleep` требуют поддержки таймеров высокого разрешения `High-Resolution Timers (HRT)`.
3. **Утечки `time.After` в циклах**: Конструкция `select { case <-time.After(time.Hour): }` внутри бесконечного цикла создает таймер, который удерживается в памяти до истечения полного часа, вызывая утечку памяти. Используйте `time.NewTimer` с явным сбросом `Stop()`.

## На собеседовании

**Вопрос с собеседования:** «Как эволюционировала подсистема таймеров в Go от Go 1.13 к Go 1.14+?»
**Ответ:**
- **До Go 1.14**: Все таймеры хранились в глобальном массиве из 64 шардированных куч под общими мьютексами, а их обслуживание выполняли выделенные потоки `timerproc`. Это приводило к чудовищной конкуренции за блокировки (Lock Contention) на многоядерных машинах (64–128 ядер).
- **Начиная с Go 1.14**: Таймеры были интегрированы **напрямую в каждый логический процессор P** (`p.timers`). Каждый P управляет своими таймерами без межпроцессорных блокировок. Если у P нет работы, он может украсть таймеры у другого P (Work Stealing). Это снизило накладные расходы на таймеры практически до нуля.
