# Реализация бесконечного Event Loop на базе unix.EpollWait и архитектура Go Netpoller

## Условие

**[Epoll: Event Loop]**: Напиши бесконечный цикл, который вызывает `unix.EpollWait(epfd, events, -1)`. Выводи в консоль, когда сокет готов к чтению. Это базовая механика того, как `net/http` работает под капотом в Go.

## Теория

Паттерн **Event Loop (Цикл обработки событий / Reactor Pattern)** является архитектурным ядром всех современных высоконагруженных сетевых систем (Node.js libuv, Redis, Netty, Go Netpoller).

Вместо создания одного блокирующего потока на каждого клиента:
1. Все дескрипторы сокетов переводятся в неблокирующий режим (`O_NONBLOCK`).
2. Дескрипторы регистрируются в едином экземпляре `epoll`.
3. Один рабочий поток вызывает системный вызов `epoll_wait(epfd, events, maxevents, -1)`.
   - Значение таймаута `-1` означает: поток засыпает в ядре и **не расходует ни одного такта CPU**, пока не поступит хотя бы один сетевой пакет.
4. При поступлении события `epoll_wait` мгновенно возвращает массив только тех дескрипторов, на которых есть активность (`n > 0`).
5. Цикл Event Loop диспетчеризует события: читает данные, обрабатывает запрос и отправляет ответ.
В Go этот цикл выполняется внутри рантайма функцией `runtime.netpoll()`, прозрачно для прикладного программиста связывая сигналы epoll с планировщиком горутин GMP.

## Решение по шагам

1. Создайте экземпляр epoll через `syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)`.
2. Создайте пару дескрипторов пайпа для симуляции сетевых сообщений.
3. Зарегистрируйте дескриптор чтения в epoll с маской `syscall.EPOLLIN`.
4. Запустите фоновую горутину, генерирующую периодические события с задержкой.
5. Запустите Event Loop, вызывающий `syscall.EpollWait(epfd, events, -1)` с таймаутом `-1`.
6. При срабатывании выводите информацию о событии и считывайте данные.
7. Прервите цикл по специальному сообщению остановки.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"strings"
	"syscall"
	"time"
)

func main() {
	// 1. Создаем epoll дескриптор
	epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(epfd)

	// 2. Создаем pipe для демонстрации асинхронных событий
	var fds [2]int
	if err := syscall.Pipe(fds[:]); err != nil {
		panic(err)
	}
	readFd := fds[0]
	writeFd := fds[1]
	defer syscall.Close(readFd)
	defer syscall.Close(writeFd)

	_ = syscall.SetNonblock(readFd, true)

	// 3. Регистрируем интерес к чтению
	ev := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(readFd),
	}
	if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, readFd, &ev); err != nil {
		panic(err)
	}

	fmt.Println("[Event Loop] Epoll initialized. Simulating Go Netpoller engine...")

	// 4. Фоновый эмулятор сетевых клиентов
	go func() {
		messages := []string{"CLIENT_HTTP_REQUEST_01", "CLIENT_HTTP_REQUEST_02", "TERMINATE"}
		for _, msg := range messages {
			time.Sleep(100 * time.Millisecond)
			_, _ = syscall.Write(writeFd, []byte(msg+"\n"))
		}
	}()

	// 5. Главный неблокирующий Event Loop (как в net/http рантайма Go)
	events := make([]syscall.EpollEvent, 16)
	buf := make([]byte, 256)

	for {
		// epoll_wait с таймаутом -1 блокирует поток в ядре без расхода CPU
		nEvents, err := syscall.EpollWait(epfd, events, -1)
		if err != nil {
			if err == syscall.EINTR {
				continue
			}
			panic(err)
		}

		for i := 0; i < nEvents; i++ {
			activeFd := int(events[i].Fd)
			fmt.Printf("[Event Loop] Woke up! Socket FD %d is READY FOR READING (Events: 0x%X)\n",
				activeFd, events[i].Events)

			n, err := syscall.Read(activeFd, buf)
			if n > 0 {
				line := strings.TrimSpace(string(buf[:n]))
				fmt.Printf("[Event Dispatcher] Dispatched payload: %q\n", line)

				if line == "TERMINATE" {
					fmt.Println("[Event Loop] Termination signal received. Exiting loop.")
					return
				}
			}
			if err != nil {
				fmt.Printf("[Event Loop] Read error: %v\n", err)
			}
		}
	}
}
```

ℹ️ Базовый Event Loop на EpollWait с таймаутом -1, эмулирующий Netpoller рантайма Go

## Под капотом

Сравнение Go Netpoller с Node.js:
- В **Node.js** Event Loop крутится строго в одном системном потоке ОС. Любая длительная вычислительная операция (CPU-bound) замораживает весь event loop, блокируя обработку всех остальных клиентов.
- В **Go** Netpoller интегрирован в многопоточный планировщик GMP:
  1. Вызов `netpoll()` может осуществляться любым свободным потоком `M`, перешедшим в поиск работы (`findrunnable`).
  2. Если поток `M` занят тяжелыми вычислениями на Go, другие потоки `M` продолжают опрашивать `epoll_wait`.
  3. Разбуженная горутина помещается в локальную очередь `runq` логического процессора `P` и начинает исполняться мгновенно на свободном ядре CPU.

## Подводные камни

1. **Зависание в обработчике события**: Если внутри Event Loop выполнить длительную блокирующую операцию (например, синхронный дисковый I/O или тяжелый криптографический расчет), обработка всех остальных готовых событий в очереди задержится.
2. **Ошибки переполнения буфера событий**: Размер среза `events := make([]syscall.EpollEvent, 16)` определяет максимальное количество событий, возвращаемых за один вызов. Если активных сокетов больше 16, ядро вернет первые 16, а остальные вернет на следующей итерации цикла.
3. **Обработка `EINTR`**: Любой поступивший системный сигнал прерывает `epoll_wait` с ошибкой `EINTR`. Цикл обязан игнорировать `EINTR` и немедленно повторять вызов.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go сетевые сокеты работают асинхронно через epoll, а файловые операции (`os.File`) блокируют системные потоки ОС?»
**Ответ:**
В Linux интерфейс `epoll` фундаментально **не поддерживает регулярные файлы на диске** (попытка добавить дескриптор дискового файла в epoll вернет ошибку `EPERM`).
Ядро считает, что диск «всегда готов к чтению/записи», хотя в реальности блочный I/O может зависать на сотни миллисекунд.
Поэтому Go-рантайм обрабатывает файлы через блокирующие системные вызовы: поток `M` входит в вызов через `entersyscall()`, а монитор `sysmon` при необходимости порождает новый поток `M` для обслуживания оставшихся горутин. Для истинно неблокирующего дискового I/O в современном Linux используют **io_uring**.
