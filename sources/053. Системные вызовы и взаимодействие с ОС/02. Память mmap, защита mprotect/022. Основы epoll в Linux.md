# Основы epoll в Linux: EpollCreate1 с флагом EPOLL_CLOEXEC и регистрация через EpollCtl

## Условие

**Epoll basics (Linux)**: Создайте epoll instance через `unix.EpollCreate1()`, добавьте файловые дескрипторы через `unix.EpollCtl()`.

## Теория

Системный интерфейс `epoll` был разработан инженерами Linux ядра как замена устаревшим `select` и `poll` для решения проблемы **C10K** (одновременное обслуживание десятков тысяч клиентов).

**Создание экземпляра epoll**:
- `epoll_create(size)`: Устаревший вызов. Параметр `size` исторически подсказывал ядру размер хэш-таблицы, но в современном Linux игнорируется (ядро использует динамическое красно-черное дерево).
- `epoll_create1(flags)`: Современный стандартный вызов. Принимает флаг `EPOLL_CLOEXEC` (`Close-On-Exec`). Флаг гарантирует, что дескриптор epoll автоматически закроется, если текущий процесс выполнит `execve()` дочерней программы, предотвращая утечку дескрипторов в дочерние процессы.

**Управление событиями через `epoll_ctl`**:
```go
err := syscall.EpollCtl(epfd, op, fd, &event)
```
Операции `op`:
- `EPOLL_CTL_ADD`: Зарегистрировать интерес к событиям на дескрипторе `fd`.
- `EPOLL_CTL_MOD`: Изменить маску отслеживаемых событий.
- `EPOLL_CTL_DEL`: Удалить дескриптор из epoll.

События `event.Events`:
- `EPOLLIN`: Доступны данные для чтения без блокировки (`read`).
- `EPOLLOUT`: Буфер сокета свободен, можно писать без блокировки (`write`).
- `EPOLLERR`: Аппаратная ошибка на сокете.
- `EPOLLHUP`: Разрыв соединения удаленной стороной (Hang Up).
- `EPOLLET`: Edge-Triggered режим.

## Решение по шагам

1. Создайте экземпляр epoll: `epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)`.
2. Создайте неблокирующую пару дескрипторов пайпа через `syscall.Pipe(fds)`.
3. Сконфигурируйте структуру `syscall.EpollEvent` с флагом `syscall.EPOLLIN`.
4. Зарегистрируйте дескриптор чтения пайпа в epoll через `syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, fds[0], &ev)`.
5. Запишите тестовый байт в дескриптор записи пайпа.
6. Вызовите `syscall.EpollWait` и убедитесь, что событие готовности чтения мгновенно поймано.
7. Закройте все созданные дескрипторы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	// 1. Создаем epoll instance с флагом EPOLL_CLOEXEC
	epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	if err != nil {
		panic(fmt.Sprintf("syscall.EpollCreate1 failed: %v", err))
	}
	defer syscall.Close(epfd)

	fmt.Printf("[Epoll Core] Created epoll instance. EPFD: %d\n", epfd)

	// 2. Создаем пару дескрипторов pipe для эмуляции I/O событий
	var pipeFds [2]int
	if err := syscall.Pipe(pipeFds[:]); err != nil {
		panic(err)
	}
	readFd := pipeFds[0]
	writeFd := pipeFds[1]
	defer syscall.Close(readFd)
	defer syscall.Close(writeFd)

	_ = syscall.SetNonblock(readFd, true)

	// 3. Регистрируем интерес к чтению (EPOLLIN) на readFd
	event := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(readFd),
	}

	if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, readFd, &event); err != nil {
		panic(fmt.Sprintf("syscall.EpollCtl ADD failed: %v", err))
	}
	fmt.Printf("[Epoll Core] Registered Read FD %d into epoll with EPOLLIN.\n", readFd)

	// 4. Отправляем полезную нагрузку в writeFd
	msg := []byte("DATA_PACKET_01")
	_, _ = syscall.Write(writeFd, msg)
	fmt.Println("[Pipe Producer] Emitted data packet into pipe.")

	// 5. Опрашиваем epoll через EpollWait
	events := make([]syscall.EpollEvent, 8)
	nEvents, err := syscall.EpollWait(epfd, events, 1000) // таймаут 1000 мс
	if err != nil {
		panic(err)
	}

	fmt.Printf("[Epoll Wait] Woke up! Detected %d active ready events:\n", nEvents)
	for i := 0; i < nEvents; i++ {
		ev := events[i]
		fmt.Printf("  Event [%d]: Triggered FD=%d, EventsMask=0x%X\n", i, ev.Fd, ev.Events)

		if int(ev.Fd) == readFd && (ev.Events&syscall.EPOLLIN != 0) {
			buf := make([]byte, 64)
			n, _ := syscall.Read(readFd, buf)
			fmt.Printf("  Consumer read %d bytes: %q\n", n, string(buf[:n]))
		}
	}

	// 6. Удаляем дескриптор из epoll
	if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_DEL, readFd, nil); err != nil {
		panic(err)
	}
	fmt.Printf("[Epoll Core] Successfully deregistered FD %d from epoll.\n", readFd)
}
```

## Под капотом

Что происходит внутри ядра Linux при работе с epoll:
1. `epoll_create1` создает структуру `struct eventpoll` в памяти ядра.
2. Внутри `eventpoll` находятся:
   - `rbr`: Красно-черное дерево (RB-Tree), индексируемое парами `(file*, fd)`. Обеспечивает добавление/поиск/удаление дескриптора за \(O(\log N)\).
   - `rdllist`: Двусвязный список готовых дескрипторов (Ready List).
   - `wq`: Очередь ожидания потоков ядра (Wait Queue).
3. При вызове `EpollCtl(ADD)` ядро регистрирует внутреннюю функцию обратного вызова ядра `ep_poll_callback` в очереди ожидания самого файла сокета.
4. Когда сетевая карта или pipe генерируют данные, вызывается `ep_poll_callback`, который добавляет элемент в `rdllist` и будит поток, спящий в `epoll_wait` за \(O(1)\).

## Подводные камни

1. **Передача `nil` вместо структуры события при удалении (`EPOLL_CTL_DEL`)**: В ядрах Linux до версии 2.6.9 вызов `epoll_ctl(..., EPOLL_CTL_DEL, fd, NULL)` возвращал ошибку `EFAULT`. В современном Linux передача `nil` валидна, но для старых ядер передавали указатель на пустую структуру.
2. **Автоматическое удаление при `close()`**: Когда файловый дескриптор закрывается через `close()`, ядро автоматически удаляет его из всех epoll-инстансов только в том случае, если на соответствующую структуру `struct file` не осталось других открытых дескрипторов (например, созданных через `dup()` или унаследованных после `fork`).
3. **Лимит экземпляров epoll (`/proc/sys/fs/epoll/max_user_watches`)**: Ядро ограничивает суммарное число зарегистрированных дескрипторов на пользователя. При превышении лимита `EpollCtl(ADD)` вернет ошибку `ENOSPC`.

## На собеседовании

**Вопрос с собеседования:** «Почему в Linux предпочтительнее использовать `EpollCreate1(EPOLL_CLOEXEC)` вместо обычного `EpollCreate()`?»
**Ответ:**
В многопоточном приложении, если один поток выполняет `EpollCreate()`, а другой поток в этот же момент выполняет `ForkExec()` сторонней утилиты (например, ImageMagick или ffmpeg), дескриптор `epfd` по умолчанию утекает в дочерний процесс (FD Leak).
Дочерний процесс удерживает открытый epfd, из-за чего родительский процесс при закрытии epfd не сможет освободить ресурсы ядра, пока жив дочерний процесс. Флаг `EPOLL_CLOEXEC` гарантирует атомарную установку бита `close-on-exec` в момент создания дескриптора, предотвращая гонки утечек.
