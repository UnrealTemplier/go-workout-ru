# Прямой ввод-вывод O_DIRECT в обход кэша операционной системы с выравниванием памяти

## Условие

**Создание собственного буфера ввода-вывода с `O_DIRECT`.**: Откройте файл с флагом `O_DIRECT` (прямой ввод-вывод без кэша ОС), выполните чтение/запись с выровненными буферами, выделенными через `mmap` или специально выровненными слайсами. Измерьте разницу с обычным файловым I/O.

## Теория

По умолчанию все операции ввода-вывода в Linux проходят через **Page Cache** (кэш страниц ядра):
- При записи ядро сохраняет данные в оперативную память и возвращает успех, откладывая сброс на диск (Dirty Writeback).
- При чтении данные кэшируются в RAM.
Для баз данных корпоративного уровня (Oracle, PostgreSQL, ScyllaDB, ClickHouse) стандартный Page Cache ядра является источником проблем:
1. **Двойное кэширование (Double Buffering)**: База данных хранит свои данные в собственном Shared Buffer Pool, а ядро дублирует те же блоки в Page Cache, расходуя в 2 раза больше дорогой RAM.
2. Непредсказуемые паузы при массовом сбросе dirty-страниц ядром.

**Флаг `O_DIRECT`**:
- Открывает файл для **прямого I/O в обход Page Cache ядра**.
- Данные передаются напрямую между буфером в памяти процесса пользователя и контроллером накопителя через аппаратный механизм **DMA (Direct Memory Access)**.
- **Критическое аппаратное требование `O_DIRECT`**:
  1. Адрес буфера в памяти обязан быть выровнен по границе сектора диска (обычно 4096 байт).
  2. Файловое смещение (offset) обязано быть кратно 4096 байт.
  3. Размер читаемого/записываемого блока обязан быть строго кратен 4096 байт.
Нарушение любого из этих условий приведет к немедленной ошибке `EINVAL` (Invalid argument).

## Решение по шагам

1. Создайте выровненный по 4096 байт буфер памяти с помощью анонимного `syscall.Mmap`.
2. Откройте файл с флагами `syscall.O_RDWR | syscall.O_CREAT | syscall.O_DIRECT`.
3. Заполните выровненный буфер тестовыми данными размером 4096 байт.
4. Выполните прямую запись через `syscall.Write(fd, alignedBuf)`.
5. Переместите смещение на начало через `syscall.Seek(fd, 0, 0)`.
6. Выполните прямое чтение через `syscall.Read(fd, alignedBuf)`.
7. Освободите память через `syscall.Munmap` и закройте дескриптор.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

// AllocDirectIOAlignedBuffer выделяет буфер, выровненный по границе 4 КБ через mmap
func AllocDirectIOAlignedBuffer(size int) ([]byte, error) {
	// Анонимный mmap всегда выравнивает начальный адрес по размеру страницы (4096 байт)
	return syscall.Mmap(
		-1,
		0,
		size,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
}

func main() {
	filePath := "direct_io_test.bin"
	defer os.Remove(filePath)

	const sectorSize = 4096 // 4 КБ - размер сектора современных NVMe/SSD дисков

	// 1. Выделяем строго выровненный по 4096 байт буфер памяти
	alignedBuffer, err := AllocDirectIOAlignedBuffer(sectorSize)
	if err != nil {
		panic(err)
	}
	defer func() {
		_ = syscall.Munmap(alignedBuffer)
	}()

	// Заполняем буфер данными
	msg := []byte("HIGHLOAD_DATABASE_RAW_DIRECT_IO_PAYLOAD_BLOCK_001")
	copy(alignedBuffer, msg)

	// 2. Открываем файл с флагом O_DIRECT
	// На Linux syscall.O_DIRECT = 0x4000
	flags := syscall.O_RDWR | syscall.O_CREAT | syscall.O_TRUNC | syscall.O_DIRECT
	fd, err := syscall.Open(filePath, flags, 0666)
	if err != nil {
		fmt.Printf("O_DIRECT open warning: %v (Filesystem might not support O_DIRECT, e.g. tmpfs)\n", err)
		return
	}
	defer syscall.Close(fd)

	fmt.Printf("[Direct I/O] File opened with O_DIRECT flag. FD: %d\n", fd)

	// 3. Записываем ровно 4096 байт из выровненного буфера
	nWritten, err := syscall.Write(fd, alignedBuffer)
	if err != nil {
		panic(fmt.Sprintf("Direct I/O Write failed: %v", err))
	}
	fmt.Printf("[Direct I/O] Successfully wrote %d bytes directly to disk bypassing Page Cache!\n", nWritten)

	// 4. Перемещаем указатель в начало
	_, err = syscall.Seek(fd, 0, 0)
	if err != nil {
		panic(err)
	}

	// 5. Прямое чтение в выровненный буфер
	readBuffer, _ := AllocDirectIOAlignedBuffer(sectorSize)
	defer func() {
		_ = syscall.Munmap(readBuffer)
	}()

	nRead, err := syscall.Read(fd, readBuffer)
	if err != nil {
		panic(fmt.Sprintf("Direct I/O Read failed: %v", err))
	}

	fmt.Printf("[Direct I/O] Successfully read %d bytes via DMA directly: %q\n",
		nRead, string(readBuffer[:len(msg)]))
}
```

## Под капотом

Что происходит при вызове `write()` с флагом `O_DIRECT`:
1. Ядро проверяет выравнивание адреса буфера `(uintptr(buf) & 4095) == 0`. Если адрес не кратен размеру сектора, ядро немедленно возвращает `EINVAL`.
2. Ядро проверяет выравнивание файлового смещения `f_pos` и длины блока.
3. Страницы буфера пользователя временно блокируются в физической памяти (Page Pinning через `get_user_pages()`), чтобы сборщик мусора или swap не переместили их.
4. Ядро формирует команды прямого доступа к памяти (DMA Descriptors) и передает физические адреса страниц напрямую аппаратному NVMe/SATA контроллеру.
5. Данные перемещаются из RAM на SSD чипами DMA без участия ядер процессора.

## Подводные камни

1. **Ошибка `EINVAL` при невыровненном слайсе Go**: Срез, созданный через `make([]byte, 4096)`, выделяется в куче Go и выравнивается только по 8 или 16 байт. Попытка передать `make([]byte)` в `O_DIRECT` вызов `write` гарантированно упадет с `EINVAL`. Буфер обязан создаваться через `mmap` или кастомный выравниватель `aligned_alloc`.
2. **Файловые системы без поддержки `O_DIRECT`**: Виртуальные файловые системы в оперативной памяти (`tmpfs`, `ramfs`) не поддерживают `O_DIRECT` и возвращают ошибку `EINVAL`.
3. **Неблокирующий режим и O_DIRECT**: Дисковый I/O в Linux по своей природе блокирующий. Флаг `O_NONBLOCK` для обычных файлов на диске игнорируется ядром.

## На собеседовании

**Вопрос с собеседования:** «Почему СУБД ScyllaDB и движки на базе Seastar используют исключительно `O_DIRECT` и асинхронный `io_uring` / `AIO`?»
**Ответ:**
1. **Полный контроль над задержками (Zero Page Cache pollution)**: Стандартный Page Cache ядра при больших объемах записи вызывает лавинообразные всплески задержек (Latency Spikes до сотен миллисекунд) во время фонового сброса dirty-страниц демоном writeback.
2. **Предсказуемый QoS**: `O_DIRECT` передает управление планированием ввода-вывода самому приложению. База данных самостоятельно решает, какие блоки держать в RAM, а какие сбрасывать, обеспечивая стабильный p99.9 latency в десятки микросекунд.
