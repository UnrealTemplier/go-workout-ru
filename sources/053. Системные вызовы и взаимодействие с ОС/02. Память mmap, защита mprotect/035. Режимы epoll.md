# Режимы epoll: разбор Edge-Triggered (EPOLLET) против Level-Triggered и флаг EPOLLONESHOT

## Условие

**Edge-triggered vs Level-triggered**: Изучите разницу между `EPOLLET` и `EPOLLONESHOT`. Реализуйте оба варианта.

## Теория

По умолчанию `epoll` работает в режиме **Level-Triggered (LT)**:
- Событие генерируется до тех пор, пока буфер сокета удовлетворяет условию (например, в буфере приема есть хотя бы 1 непрочитанный байт).
- Если программа проснулась по `EPOLLIN`, прочитала 10 байт из 100 и снова вызвала `epoll_wait`, `epoll_wait` немедленно проснется снова.
- **Плюс**: Простота разработки. Невозможно потерять данные.
- **Минус**: Избыточные пробуждения потоков при частичном чтении.

**Режим Edge-Triggered (`EPOLLET`)**:
- Событие генерируется **только в момент фронта изменения состояния** (когда пришли новые данные из сети).
- Если программа прочитала часть данных и уснула, `epoll_wait` **больше никогда не проснется для оставшихся данных**, пока не поступит новый сетевой пакет!
- **Правило Edge-Triggered**: Сокет обязан быть неблокирующим (`O_NONBLOCK`), а чтение должно производиться в бесконечном цикле `for` строго до получения ошибки `EAGAIN` / `EWOULDBLOCK`.

**Флаг `EPOLLONESHOT`**:
- Гарантирует, что после того, как событие на дескрипторе сработало в одном потоке/воркере, дескриптор **деактивируется в epoll**.
- Никакой другой поток пула воркеров не получит событие по этому дескриптору параллельно, предотвращая гонки потоков (Race Conditions).
- Для повторной активации сокета поток обязан явно вызвать `syscall.EpollCtl(epfd, EPOLL_CTL_MOD, fd, &ev)`.

## Решение по шагам

1. Создайте экземпляр epoll.
2. Создайте неблокирующую пару дескрипторов pipe.
3. Зарегистрируйте дескриптор чтения с флагами `syscall.EPOLLIN | syscall.EPOLLET`.
4. Запишите в pipe 20 байт.
5. Прочитайте только первые 5 байт.
6. Вызовите `syscall.EpollWait` с таймаутом 0: убедитесь, что в режиме `EPOLLET` epoll не просыпается повторно, несмотря на наличие 15 байт в буфере.
7. Продемонстрируйте работу `EPOLLONESHOT` и его повторную реактивацию через `EPOLL_CTL_MOD`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(epfd)

	// 1. Демонстрация Edge-Triggered (EPOLLET)
	var p [2]int
	_ = syscall.Pipe(p[:])
	readFd := p[0]
	writeFd := p[1]
	defer syscall.Close(readFd)
	defer syscall.Close(writeFd)

	_ = syscall.SetNonblock(readFd, true)

	// Регистрируем с флагом EPOLLET (Edge-Triggered)
	// В Go syscall.EPOLLET имеет тип uint32
	etEvent := syscall.EpollEvent{
		Events: syscall.EPOLLIN | syscall.EPOLLET,
		Fd:     int32(readFd),
	}
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, readFd, &etEvent)
	fmt.Println("[Edge-Triggered] Registered pipe with EPOLLIN | EPOLLET.")

	// Пишем 20 байт в пайп
	_, _ = syscall.Write(writeFd, []byte("01234567890123456789"))

	events := make([]syscall.EpollEvent, 4)
	nReady, _ := syscall.EpollWait(epfd, events, 500)
	fmt.Printf("[Edge-Triggered] First EpollWait: %d ready events.\n", nReady)

	// Читаем только 5 байт (оставляя 15 байт в буфере пайпа)
	partialBuf := make([]byte, 5)
	n, _ := syscall.Read(readFd, partialBuf)
	fmt.Printf("[Edge-Triggered] Partially read %d bytes: %q (15 bytes remain in kernel buffer)\n", n, string(partialBuf))

	// Повторный EpollWait с таймаутом 100 мс
	nReady2, _ := syscall.EpollWait(epfd, events, 100)
	fmt.Printf("[Edge-Triggered] Second EpollWait: %d ready events (Suppressed by EPOLLET edge behavior!)\n", nReady2)

	// 2. Демонстрация EPOLLONESHOT
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_DEL, readFd, nil)

	oneshotEvent := syscall.EpollEvent{
		Events: syscall.EPOLLIN | syscall.EPOLLONESHOT,
		Fd:     int32(readFd),
	}
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, readFd, &oneshotEvent)
	fmt.Println("\n[EPOLLONESHOT] Registered pipe with EPOLLIN | EPOLLONESHOT.")

	// Отправляем новый байт
	_, _ = syscall.Write(writeFd, []byte("!"))

	nReady3, _ := syscall.EpollWait(epfd, events, 500)
	fmt.Printf("[EPOLLONESHOT] Triggered: %d events. Socket is now atomically DEACTIVATED!\n", nReady3)

	// Реактивация сокета через EPOLL_CTL_MOD
	fmt.Println("[EPOLLONESHOT] Worker finished processing. Reactivating socket via EPOLL_CTL_MOD...")
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_MOD, readFd, &oneshotEvent)
	fmt.Println("Socket reactivated successfully!")
}
```

## Под капотом

Внутренняя логика ядра Linux:
- **Level-Triggered**: При каждом вызове `epoll_wait` ядро проверяет статус дескриптора через метод драйвера `file->f_op->poll()`. Если в очереди сокета есть байты, событие добавляется в выходной массив.
- **Edge-Triggered**: Дескриптор добавляется в `rdllist` **только при переходе** очереди из пустого состояния в непустое. При чтении части данных состояние не менялось (очередь осталась непустой), поэтому повторное событие не генерируется.
- **EPOLLONESHOT**: После помещения дескриптора в `rdllist` ядро автоматически маскирует события `epentry->event.events &= ~EP_PRIVATE_BITS`, исключая повторные срабатывания до вызова `epoll_ctl(EPOLL_CTL_MOD)`.

## Подводные камни

1. **Зависание в Edge-Triggered режиме**: Если при использовании `EPOLLET` не вычитать все данные в цикле `for` до получения ошибки `EAGAIN`, оставшиеся данные останутся непрочитанными навсегда (или до прихода следующего пакета от клиента).
2. **Забытая реактивация `EPOLLONESHOT`**: Если рабочий воркер завершил обработку запроса, но забыл вызвать `EPOLL_CTL_MOD`, сокет навсегда останется в спящем состоянии, перестав отвечать на запросы клиента.
3. **Блокирующие сокеты с EPOLLET**: Сочетание блокирующего сокета и `EPOLLET` — фатальная ошибка: цикл чтения до `EAGAIN` заблокирует весь поток на последней итерации.

## На собеседовании

**Вопрос с собеседования:** «Зачем многопоточные серверы (Netty, gnet) используют `EPOLLONESHOT` в пуле потоков воркеров (Worker Thread Pool)?»
**Ответ:**
В многопоточном сервере без `EPOLLONESHOT`:
1. Поток 1 получает событие готовности сокета и начинает читать данные.
2. От клиента приходит второй пакет.
3. `epoll_wait` в Потоке 2 просыпается на том же самом сокете.
4. Поток 1 и Поток 2 начинают параллельно читать из одного сокета, перемешивая байты протокола и ломая сериализацию.
`EPOLLONESHOT` гарантирует атомарную изоляцию: сокет обрабатывается строго одним воркером в любой момент времени. По окончании обработки воркер реактивирует сокет через `EPOLL_CTL_MOD`.
