# Высокоскоростное изменение файлов на диске через syscall.Mmap и синхронизация Msync

## Условие

**Отображение файлов в память (`mmap`)**: Напишите программу для высокоскоростного изменения файлов на диске:
* Создайте файл размером 1 КБ на диске.
* Откройте его и отобразите в виртуальную память с помощью системного вызова `syscall.Mmap` (или `unix.Mmap` из пакета `golang.org/x/sys/unix`).
* Измените байты внутри полученного среза `[]byte` напрямую в памяти.
* Синхронизируйте изменения с диском с помощью `syscall.Msync` и убедитесь, что файл на диске обновился без вызова стандартного `file.Write()`.

## Теория

При проектировании высокопроизводительных хранилищ (Time-Series базы данных, журналы предзаписи WAL, торговые стаканы) критически важна минимальная задержка записи.

Стандартный `file.Write()` требует:
1. Вызова системного вызова `sys_write`.
2. Копирования буфера из памяти Go в кэш страниц ядра.
3. Обновления внутреннего файлового указателя `f_pos` под мьютексом ядра.

Метод **mmap-based In-Place Mutation**:
- Файл проецируется один раз при инициализации.
- Любое изменение данных — это прямая запись в оперативную память по указателю со скоростью процессора (до десятков гигабайт в секунду).
- Вызов `syscall.Msync(slice, syscall.MS_SYNC)` выполняется только в контрольных точках транзакции (Commit Points) для сброса данных на диск, исключая накладные расходы на промежуточные системные вызовы.

## Решение по шагам

1. Создайте файл размером ровно 1024 байта (1 КБ), заполненный повторяющимся шаблоном.
2. Откройте файл через `syscall.Open(path, syscall.O_RDWR, 0666)`.
3. Отобразите 1024 байта через `syscall.Mmap(fd, 0, 1024, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_SHARED)`.
4. Запишите структурированный бинарный заголовок и полезную нагрузку в срез `[]byte`.
5. Вызовите `syscall.Msync(mmapSlice, syscall.MS_SYNC)`.
6. Размонтируйте память `syscall.Munmap` и закройте дескриптор.
7. Проверьте с диска сохраненные данные.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"os"
	"syscall"
)

func main() {
	filePath := "wal_record_1kb.bin"
	const fileSize = 1024 // 1 КБ

	// 1. Создаем файл ровно 1 КБ, заполненный байтами '.'
	initialData := bytes.Repeat([]byte("."), fileSize)
	if err := os.WriteFile(filePath, initialData, 0644); err != nil {
		panic(err)
	}
	defer os.Remove(filePath)

	// 2. Открываем дескриптор для чтения и записи
	fd, err := syscall.Open(filePath, syscall.O_RDWR, 0666)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(fd)

	// 3. Проецируем файл в виртуальную память (MAP_SHARED)
	mmapSlice, err := syscall.Mmap(
		fd,
		0,
		fileSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(err)
	}
	defer func() {
		_ = syscall.Munmap(mmapSlice)
	}()

	fmt.Printf("Initial state: first 16 bytes: %q\n", string(mmapSlice[:16]))

	// 4. Прямая модификация байт в памяти (In-Place Memory Mutation)
	walHeader := []byte("WAL_MAGIC_V2_TX_10098")
	copy(mmapSlice[0:], walHeader)

	payload := []byte("USER_ID=42891_ACTION=PURCHASE_AMOUNT=15000_RUB")
	copy(mmapSlice[128:], payload)

	// 5. Синхронизируем изменения с постоянным накопителем через Msync
	// Флаг MS_SYNC гарантирует, что данные записаны на диск контроллером
	if err := syscall.Msync(mmapSlice, syscall.MS_SYNC); err != nil {
		panic(fmt.Sprintf("syscall.Msync failed: %v", err))
	}
	fmt.Println("Changes successfully synchronized to disk via syscall.Msync (MS_SYNC).")

	// 6. Проверяем файл с диска сторонним чтением
	diskBytes, err := os.ReadFile(filePath)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Disk verification: Header: %q\n", string(diskBytes[:len(walHeader)]))
	fmt.Printf("Disk verification: Data:   %q\n", string(diskBytes[128:128+len(payload)]))
}
```

ℹ️ Высокоскоростная модификация дисковых файлов через mmap и Msync без вызовов write

## Под капотом

Что происходит при вызове `syscall.Msync(slice, MS_SYNC)`:
1. Выполняется системный вызов `SYS_MSYNC` (номер 26 на Linux x86_64).
2. Подсистема управления памятью ядра находит диапазон виртуальных адресов `[addr, addr + len]`.
3. Для каждой страницы в этом диапазоне проверяется бит `PTE_DIRTY`.
4. Если страница была модифицирована, ядро формирует I/O запрос в очередь блочного устройства файловой системы.
5. Ядро блокирует горутину и поток `M` до тех пор, пока контроллер SSD/NVMe не выполнит команду сброса буфера (Flush Cache) и не подтвердит сохранность данных в энергонезависимых ячейках памяти (NAND Flash).

## Подводные камни

1. **Чрезмерно частый `Msync(MS_SYNC)`**: Вызов `MS_SYNC` на каждый мелкий чих нивелирует всю пользу `mmap`, так как скорость ограничивается физической латентностью дискового контроллера (~100–500 микросекунд на синхронизацию). В HighLoad `Msync` вызывают пачками (Group Commit).
2. **Перекрытие диапазонов памяти**: Адрес, передаваемый в `Msync`, обязан быть выровнен по границе системной страницы памяти (`Getpagesize()`).
3. **Параллельная запись без блокировок**: Хотя ядро гарантирует целостность страниц, два потока Go, пишущие в одни и те же байты mmap-слайса без мьютекса или атомиков, получат повреждение прикладных данных (data race).

## На собеседовании

**Вопрос с собеседования:** «Как паттерн Group Commit в PostgreSQL и Kafka оптимизирует сброс данных на диск через `fsync` / `msync`?»
**Ответ:**
Если 10 000 клиентов выполняют транзакции параллельно, делать индивидуальный `msync` на каждый запрос невозможно (диск выдаст максимум 1000–5000 IOPS).
В паттерне **Group Commit**:
1. Потоки записывают данные своих транзакций в mmap-буфер в памяти.
2. Один поток-лидер собирает пачку из сотен готовых транзакций и вызывает **один общий `msync`** на весь диапазон.
3. Все ожидающие транзакции подтверждаются одновременно за один физический сброс контроллера диска, поднимая пропускную способность до сотен тысяч TPS.
