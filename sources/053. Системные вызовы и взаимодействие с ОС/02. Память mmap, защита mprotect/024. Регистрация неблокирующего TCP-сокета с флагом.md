# Регистрация неблокирующего TCP-сокета с флагом SOCK_NONBLOCK в epoll с событием EPOLLIN

## Условие

**[Epoll: Регистрация FD]**: Создай неблокирующий TCP-сокет (`unix.Socket` с флагом `SOCK_NONBLOCK`). Зарегистрируй его в epoll через `unix.EpollCtl(epfd, unix.EPOLL_CTL_ADD, sockfd, &unix.EpollEvent{Events: unix.EPOLLIN, Fd: int32(sockfd)})`.

## Теория

При построении высокопроизводительных сетевых серверов (на уровне архитектуры Nginx, Redis, Envoy) сетевые сокеты **никогда не создаются в блокирующем режиме**.

**Почему блокирующий сокет недопустим в event-loop**:
Если сокет блокирующий, то вызов `read()` или `write()` при отсутствии данных или заполнении TCP-окна заморозит весь системный поток ОС, остановив обработку событий для всех остальных тысяч клиентов.

**Флаг `SOCK_NONBLOCK` в системном вызове `socket`**:
- В классическом POSIX сокет создавался через `socket()`, а затем отдельным системным вызовом `fcntl(fd, F_SETFL, O_NONBLOCK)` переводился в неблокирующий режим. Это требовало двух системных вызовов и создавало окно гонки.
- В Linux системный вызов `socket` позволяет передавать флаг `SOCK_NONBLOCK` прямо в типе сокета:
  ```go
  fd, err := syscall.Socket(syscall.AF_INET, syscall.SOCK_STREAM|syscall.SOCK_NONBLOCK|syscall.SOCK_CLOEXEC, 0)
  ```
- Сокет создается неблокирующим атомарно за 1 системный вызов.
- При отсутствии данных в буфере приема `read()` немедленно возвращает ошибку `EAGAIN` или `EWOULDBLOCK`.
- Дескриптор регистрируется в epoll с флагом `EPOLLIN` для асинхронного оповещения о поступлении пакетов.

## Решение по шагам

1. Создайте неблокирующий сокет через `syscall.Socket(syscall.AF_INET, syscall.SOCK_STREAM|syscall.SOCK_NONBLOCK, 0)`.
2. Создайте инстанс epoll через `syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)`.
3. Сконфигурируйте событие `syscall.EpollEvent{Events: syscall.EPOLLIN, Fd: int32(sockfd)}`.
4. Зарегистрируйте сокет в epoll через `syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, sockfd, &event)`.
5. Проверьте статус сокета через чтение: убедитесь, что `syscall.Read` возвращает `EAGAIN` без блокировки потока.
6. Закройте сокет и epfd.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	// 1. Создаем TCP-сокет атомарно с флагами SOCK_NONBLOCK и SOCK_CLOEXEC
	// На Linux флаги передаются через битовое ИЛИ в аргументе типа сокета
	sockType := syscall.SOCK_STREAM | syscall.SOCK_NONBLOCK | syscall.SOCK_CLOEXEC
	sockfd, err := syscall.Socket(syscall.AF_INET, sockType, 0)
	if err != nil {
		panic(fmt.Sprintf("syscall.Socket failed: %v", err))
	}
	defer syscall.Close(sockfd)

	fmt.Printf("[Socket Setup] Created Non-Blocking TCP Socket. FD: %d\n", sockfd)

	// 2. Проверяем, что сокет действительно неблокирующий (Non-blocking check)
	buf := make([]byte, 128)
	n, readErr := syscall.Read(sockfd, buf)
	fmt.Printf("[Socket Probe] Non-blocking read returned: n=%d, err=%v (Expected EAGAIN/ENOTCONN)\n", n, readErr)

	// 3. Создаем инстанс epoll
	epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	if err != nil {
		panic(fmt.Sprintf("syscall.EpollCreate1 failed: %v", err))
	}
	defer syscall.Close(epfd)

	// 4. Регистрируем сокет в epoll на событие готовности к чтению (EPOLLIN)
	event := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(sockfd),
	}

	if err := syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, sockfd, &event); err != nil {
		panic(fmt.Sprintf("syscall.EpollCtl ADD failed: %v", err))
	}

	fmt.Printf("[Epoll Registry] Socket FD %d successfully registered in epoll (EPFD %d) with EPOLLIN!\n",
		sockfd, epfd)

	// 5. Проверяем статус epoll_wait с нулевым таймаутом (non-blocking poll)
	events := make([]syscall.EpollEvent, 4)
	readyCount, err := syscall.EpollWait(epfd, events, 0)
	if err != nil {
		panic(err)
	}

	fmt.Printf("[Epoll Poll] Immediate epoll_wait(timeout=0) returned %d ready events.\n", readyCount)
	fmt.Println("Socket registration lifecycle validated successfully!")
}
```

## Под капотом

Почему атомарное создание `SOCK_NONBLOCK` критично:
1. В классической схеме `socket()` + `fcntl(O_NONBLOCK)` между первым и вторым вызовом проходит несколько сотен наносекунд.
2. Если в этот микроинтервал в процесс придет сигнал или планировщик переключит контекст, другой поток может попытаться использовать дескриптор в блокирующем режиме.
3. Добавление `SOCK_NONBLOCK` и `SOCK_CLOEXEC` в Linux 2.6.27 позволило устанавливать флаги непосредственно в ядре во время аллокации `struct socket` и `struct file`, исключая race conditions.

## Подводные камни

1. **Ошибка `EEXIST` при `EPOLL_CTL_ADD`**: Если попытаться добавить дескриптор, который уже зарегистрирован в этом epoll-инстансе, ядро вернет ошибку `EEXIST`. Для изменения маски событий зарегистрированного сокета необходимо использовать операцию `EPOLL_CTL_MOD`.
2. **Ошибка `EBADF`**: Если передать недействительный или уже закрытый дескриптор, вызов вернет `EBADF`.
3. **Режимы сокетов на macOS (kqueue)**: Системный вызов `epoll` является специфичным для Linux. На macOS и FreeBSD аналогом является подсистема **kqueue** (`kqueue()`, `kevent()`). Кроссплатформенный код Go должен использовать build tags `//go:build linux`.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между `EPOLLIN`, `EPOLLRDHUP` и `EPOLLHUP` в сетевом сервере на epoll?»
**Ответ:**
- `EPOLLIN`: Доступны данные для чтения (нормальные входящие сетевые пакеты).
- `EPOLLRDHUP` (начиная с Linux 2.6.17): Удаленная сторона закрыла соединение на запись (вызов `shutdown(SHUT_WR)` или пришел TCP-пакет `FIN`). Сервер может обнаружить закрытие соединения клиентом **до** вызова `read()`, избавившись от лишних системных вызовов.
- `EPOLLHUP`: Разрыв соединения (пришел TCP-пакет `RST` или закрыт локальный конец пайпа). Это системное событие, которое доставляется ядром всегда, даже если оно не было указано в маске событий.
