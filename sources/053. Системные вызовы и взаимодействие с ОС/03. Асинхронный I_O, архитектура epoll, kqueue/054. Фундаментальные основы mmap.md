# Фундаментальные основы mmap: проецирование файлов, срез []byte и гарантии Munmap

## Условие

**mmap basics**: Откройте файл, замапьте его в память через `unix.Mmap()`, прочитайте данные как `[]byte`.

## Теория

Системный вызов `mmap` создает в виртуальном адресном пространстве процесса ассоциацию с файлом на постоянном носителе.

**Свойства отображения**:
1. Память выделяется непрерывным блоком виртуальных адресов.
2. Начальный адрес всегда выравнивается по границе системной страницы памяти (4096 байт).
3. Возвращаемый срез `[]byte` дает прямой доступ к байтам файла:
   - Любое чтение по индексу `b[i]` перенаправляется процессором в кэш страниц ОС (Page Cache).
   - Чтение не изменяет внутренний файловый указатель `f_pos`.
   - Десятки горутин могут читать один и тот же `[]byte` параллельно без каких-либо мьютексов.
4. Освобождение ресурсов выполняется системным вызовом `syscall.Munmap(b)`, который размонтирует виртуальные страницы и освобождает адресное пространство процесса.

## Решение по шагам

1. Создайте текстовый файл на диске с тестовым содержимым.
2. Откройте файл через `syscall.Open(path, syscall.O_RDONLY, 0)`.
3. Узнайте размер файла через `syscall.Fstat(fd, &stat)`.
4. Отобразите файл в память: `data, err := syscall.Mmap(fd, 0, int(stat.Size), syscall.PROT_READ, syscall.MAP_SHARED)`.
5. Прочитайте данные из среза `data` как обычный Go-массив.
6. Размонтируйте память через `syscall.Munmap(data)`.
7. Закройте файловый дескриптор.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	filePath := "mmap_basic_demo.txt"
	sampleText := "Go Systems Programming: Clean Architecture with Mmap & Linux Kernel!"

	// 1. Создаем файл на диске
	if err := os.WriteFile(filePath, []byte(sampleText), 0644); err != nil {
		panic(err)
	}
	defer os.Remove(filePath)

	// 2. Открываем дескриптор в режиме Read-Only
	fd, err := syscall.Open(filePath, syscall.O_RDONLY, 0)
	if err != nil {
		panic(err)
	}
	defer syscall.Close(fd)

	// 3. Получаем точный размер файла
	var stat syscall.Stat_t
	if err := syscall.Fstat(fd, &stat); err != nil {
		panic(err)
	}
	fileSize := int(stat.Size)

	// 4. Проецируем файл в виртуальную память
	mmapBytes, err := syscall.Mmap(
		fd,
		0,        // смещение от начала файла
		fileSize, // длина региона
		syscall.PROT_READ,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(fmt.Sprintf("syscall.Mmap failed: %v", err))
	}
	// Обязательно освобождаем отображение при выходе
	defer func() {
		if err := syscall.Munmap(mmapBytes); err != nil {
			fmt.Printf("Munmap error: %v\n", err)
		}
	}()

	fmt.Printf("[Mmap Basics] Mapped %d bytes into process virtual memory.\n", len(mmapBytes))
	fmt.Printf("Content read via memory pointer: %q\n", string(mmapBytes))

	// Проверяем выборочное чтение слайса
	prefix := string(mmapBytes[:22])
	fmt.Printf("Slice prefix [0:22]:           %q\n", prefix)
}
```

ℹ️ Классическое проецирование файла в память через syscall.Mmap и освобождение Munmap

**`Терминал`**

```bash

# Вывод:

# Content read via memory pointer: "Go Systems Programming: Clean Architecture with Mmap & Linux Kernel!"
```

## Под капотом

Что происходит внутри ядра Linux при чтении из `mmapBytes`:
1. При первом обращении к `mmapBytes[0]` процессор декодирует инструкцию `MOV`.
2. В таблице страниц процесса (PTE) бит `Present` равен 0.
3. Процессор генерирует аппаратное прерывание Page Fault.
4. Ядро перехватывает Page Fault, считывает страницу с диска в Page Cache и выставляет бит `Present` в 1.
5. Инструкция процессора `MOV` повторяется и успешно считывает байт за доли наносекунды.
6. Все последующие чтения из этого диапазона происходят со скоростью оперативной памяти процессора без участия ядра.

## Подводные камни

1. **Чтение файла нулевого размера**: Попытка вызвать `mmap` для файла длиной 0 байт вернет ошибку `EINVAL`. Всегда проверяйте `if fileSize == 0`.
2. **Утечка адресного пространства**: Если не вызвать `Munmap`, ядро удерживает диапазон VMA открытым до завершения процесса.
3. **Безопасность параллельного усечения**: Если файл усекается другим процессом, обращение к срезу приведет к аппаратному `SIGBUS`.

## На собеседовании

**Вопрос с собеседования:** «Почему базы данных (PostgreSQL, SQLite) открывают файлы с флагом `O_RDWR` даже для операций чтения перед вызовом `mmap`?»
**Ответ:**
Если файл открыт с флагом `O_RDONLY`, ядро Linux разрешает отображение только с флагом `PROT_READ`.
Если в дальнейшем приложению потребуется записать данные в кэшированную страницу, ему придется заново вызывать `mmap` с правами `PROT_WRITE`, что инвалидирует существующие указатели и требует повторной трансляции адресов в TLB. Открытие в режиме `O_RDWR` позволяет гибко изменять права страниц через `mprotect` без пересоздания маппинга.
