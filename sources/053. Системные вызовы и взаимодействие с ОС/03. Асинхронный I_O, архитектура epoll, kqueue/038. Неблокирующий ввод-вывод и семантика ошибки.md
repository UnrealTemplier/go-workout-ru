# Неблокирующий ввод-вывод и семантика ошибки EAGAIN/EWOULDBLOCK в сетевых сокетах

## Условие

**[Каверзный кейс — Неблокирующий I/O и EAGAIN]**: Попробуй прочитать из неблокирующего сокета, когда там нет данных (до события epoll). Поймай ошибку `unix.EAGAIN` (или `EWOULDBLOCK`). Объясни, что это не ошибка, а сигнал "данных пока нет".

## Теория

В синхронном блокирующем режиме вызов `syscall.Read(fd, buf)` переводит поток ОС в состояние сна, если в буфере приема нет данных.

Когда дескриптор сокета или пайпа переведен в неблокирующий режим с помощью флага `O_NONBLOCK` или функции `syscall.SetNonblock(fd, true)`:
1. Системный вызов `read()` **никогда не блокирует поток**.
2. Если в приемном буфере сокета есть данные, `read` немедленно копирует их в буфер и возвращает количество прочитанных байт `n > 0`.
3. Если приемный буфер пуст:
   - Системный вызов немедленно возвращает значение `-1` (в Go: `n = 0` и ошибку `err`).
   - Код ошибки равен **`syscall.EAGAIN`** (Try again) или **`syscall.EWOULDBLOCK`** (Operation would block). В Linux x86_64 обе константы имеют одинаковый числовой код `11`.
4. **Ключевой вывод архитектуры**: `EAGAIN` — это **не фатальная ошибка сети**, а нормальный системный статус, означающий: *«Операционная система не может выполнить операцию прямо сейчас без блокировки. Подождите готовности через epoll и повторите попытку позже»*.

## Решение по шагам

1. Создайте пару дескрипторов pipe: `syscall.Pipe(fds)`.
2. Переведите дескриптор чтения в неблокирующий режим через `syscall.SetNonblock(fds[0], true)`.
3. Попробуйте немедленно вызвать `syscall.Read(fds[0], buf)` без предварительной записи в pipe.
4. Перехватите возвращенную ошибку и проверьте условие `err == syscall.EAGAIN || err == syscall.EWOULDBLOCK`.
5. Запишите данные в дескриптор записи `syscall.Write(fds[1], data)`.
6. Повторите вызов `syscall.Read` и убедитесь, что данные теперь успешно считываются.
7. Закройте оба дескриптора.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"syscall"
)

func main() {
	var fds [2]int
	if err := syscall.Pipe(fds[:]); err != nil {
		panic(err)
	}
	readFd := fds[0]
	writeFd := fds[1]
	defer syscall.Close(readFd)
	defer syscall.Close(writeFd)

	// 1. Переводим дескриптор чтения в неблокирующий режим (O_NONBLOCK)
	if err := syscall.SetNonblock(readFd, true); err != nil {
		panic(err)
	}
	fmt.Printf("[Non-Blocking I/O] Read FD %d set to non-blocking mode.\n", readFd)

	// 2. Попытка чтения из пустого неблокирующего дескриптора
	buf := make([]byte, 128)
	fmt.Println("[Non-Blocking I/O] Attempting to read from empty pipe...")
	n, err := syscall.Read(readFd, buf)

	if err != nil {
		// Проверяем ошибку EAGAIN / EWOULDBLOCK
		if errors.Is(err, syscall.EAGAIN) || errors.Is(err, syscall.EWOULDBLOCK) {
			fmt.Printf("[Handled] Intercepted expected syscall.EAGAIN (errno: %d)!\n", syscall.EAGAIN)
			fmt.Println("  -> Semantics: Buffer is currently empty. Thread did NOT freeze!")
		} else {
			panic(fmt.Sprintf("Unexpected error: %v", err))
		}
	} else {
		fmt.Printf("Unexpected success reading %d bytes\n", n)
	}

	// 3. Отправляем данные в pipe
	payload := []byte("ASYNC_STREAM_DATA_CHUNK")
	_, _ = syscall.Write(writeFd, payload)
	fmt.Println("\n[Producer] Wrote data packet into pipe.")

	// 4. Повторное чтение теперь завершается успехом
	n2, err2 := syscall.Read(readFd, buf)
	if err2 != nil {
		panic(err2)
	}
	fmt.Printf("[Consumer] Read %d bytes successfully: %q\n", n2, string(buf[:n2]))
}
```

## Под капотом

Что происходит внутри ядра Linux при неблокирующем чтении:
1. Выполняется системный вызов `sys_read`.
2. Функция файловой системы или сокета проверяет наличие данных в структуре `sk_receive_queue` (очередь входящих пакетов).
3. Если очередь пуста:
   - Если флаг `O_NONBLOCK` **не установлен**, ядро переводит поток в `TASK_INTERRUPTIBLE`, добавляет в очередь ожидания `sk_sleep` и вызывает планировщик `schedule()`.
   - Если флаг `O_NONBLOCK` **установлен**, ядро немедленно прекращает обработку и возвращает отрицательное число `-EAGAIN` (`-11`).
4. В Go рантайм перехватывает `-EAGAIN` и преобразует его в значение `syscall.EAGAIN` типа `error`.

## Подводные камни

1. **Busy-Wait Spinloop**: Запуск бесконечного цикла `for { read(); if err == EAGAIN { continue } }` без паузы или ожидания в epoll приведет к 100% утилизации ядра CPU впустую (CPU Burning).
2. **Путаница с `io.EOF`**: Ошибка `EAGAIN` означает «данных пока нет, но соединение живо». Нулевой результат `n == 0` и `err == nil` означает, что удаленная сторона закрыла соединение (EOF). Их смешивание приводит к преждевременному разрыву валидных сокетов.
3. **Неблокирующая запись (`EAGAIN` на Write)**: Системный вызов `write()` также может вернуть `EAGAIN`, если сетевой буфер отправки сокета (Send Buffer) заполнен из-за медленного клиента. Программа обязана зарегистрировать `EPOLLOUT` в epoll и дождаться освобождения буфера.

## На собеседовании

**Вопрос с собеседования:** «Как рантайм Go скрывает ошибку `EAGAIN` от прикладного разработчика в пакете `net`?»
**Ответ:**
Когда разработчик вызывает `conn.Read(buf)`:
1. Рантайм Go пытается выполнить неблокирующий системный вызов `read()`.
2. Если данных нет, ядро возвращает `EAGAIN`.
3. Внутренний тип `net.netFD` перехватывает `EAGAIN` и вызывает `pollDesc.waitRead()`.
4. Горутина паркуется через `runtime.gopark()` в Netpoller (epoll) и засыпает. Поток `M` переключается на другие горутины.
5. Когда в сокет приходят данные, epoll будит горутину, рантайм повторяет вызов `read()`, и прикладной код получает готовые данные так, будто вызов был просто блокирующим!
