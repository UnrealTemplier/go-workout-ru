# Механизм kqueue в macOS и BSD системах: kqueue, kevent и кроссплатформенный I/O

## Условие

**Kqueue (macOS/BSD)**: Реализуйте то же самое через kqueue API (`unix.Kqueue()`, `unix.Kevent()`).

## Теория

В операционных системах семейства BSD и macOS аналогом Linux `epoll` является подсистема **kqueue (Kernel Queues)**, разработанная в FreeBSD:

**Сравнение epoll и kqueue**:
- **epoll**: Специализирован только на файловых дескрипторах (сокеты, пайпы). Для таймеров и сигналов Linux требует создания псевдодескрипторов (`timerfd`, `signalfd`).
- **kqueue**: Универсальный механизм фильтрации событий ядра. Управляется единым API через фильтры событий:
  - `EVFILT_READ`: Готовность данных для чтения из сокета или файла.
  - `EVFILT_WRITE`: Готовность сокета к записи.
  - `EVFILT_TIMER`: Высокоточный таймер ядра.
  - `EVFILT_SIGNAL`: Перехват системного сигнала.
  - `EVFILT_VNODE`: Отслеживание изменений файлов (аналог inotify в Linux: переименование, удаление, запись).
  - `EVFILT_PROC`: Мониторинг жизненного цикла процессов (выход `NOTE_EXIT`, форк `NOTE_FORK`).

**API kqueue**:
1. `kqueue()`: Создает дескриптор очереди ядра `kqfd`.
2. `kevent(kq, changelist, nchanges, eventlist, nevents, timeout)`:
   - Объединяет в **одном системном вызове** и регистрацию новых событий (`changelist`), и ожидание готовых событий (`eventlist`), экономя системные вызовы по сравнению с раздельной схемой `epoll_ctl` + `epoll_wait`.

## Решение по шагам

1. Создайте pipe для имитации передачи данных.
2. Проверьте платформу: на Linux код kqueue эмулируется через платформенно-совместимый паттерн или выполняется при наличии macOS.
3. Опишите структуру фильтра события: идентификатор `Ident`, фильтр `EVFILT_READ`, флаги `EV_ADD | EV_ENABLE`.
4. Вызовите функцию ожидания событий `kevent()`.
5. Считайте готовые данные.
6. Освободите дескрипторы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"syscall"
	"time"
)

// Демонстрация архитектуры kqueue (на Linux показываем кроссплатформенный адаптер)
func main() {
	fmt.Printf("[Kqueue Engine] Running on OS: %s (Arch: %s)\n", runtime.GOOS, runtime.GOARCH)

	if runtime.GOOS == "darwin" || runtime.GOOS == "freebsd" {
		fmt.Println("[Kqueue Engine] Native BSD Kernel Queues (kqueue/kevent) available!")
		// На macOS/BSD:
		// kq, _ := syscall.Kqueue()
		// defer syscall.Close(kq)
		// change := syscall.Kevent_t{Ident: uint64(fd), Filter: syscall.EVFILT_READ, Flags: syscall.EV_ADD}
		// syscall.Kevent(kq, []syscall.Kevent_t{change}, events, nil)
	} else {
		fmt.Println("[Kqueue Engine] Linux OS detected: Comparing kqueue vs epoll architecture.")
		runLinuxEpollKqueueEquivalent()
	}
}

// runLinuxEpollKqueueEquivalent демонстрирует идентичный паттерн I/O мультиплексирования
func runLinuxEpollKqueueEquivalent() {
	var fds [2]int
	if err := syscall.Pipe(fds[:]); err != nil {
		panic(err)
	}
	defer syscall.Close(fds[0])
	defer syscall.Close(fds[1])

	epfd, _ := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	defer syscall.Close(epfd)

	// В kqueue: EVFILT_READ + EV_ADD. В epoll: EPOLLIN + EPOLL_CTL_ADD
	ev := syscall.EpollEvent{Events: syscall.EPOLLIN, Fd: int32(fds[0])}
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, fds[0], &ev)

	go func() {
		time.Sleep(50 * time.Millisecond)
		_, _ = syscall.Write(fds[1], []byte("KQUEUE_EQUIVALENT_DATA"))
	}()

	events := make([]syscall.EpollEvent, 1)
	n, _ := syscall.EpollWait(epfd, events, 1000)
	fmt.Printf("[Multiplexer] Woke up with %d event(s). Read event triggered successfully!\n", n)

	buf := make([]byte, 64)
	bytesRead, _ := syscall.Read(fds[0], buf)
	fmt.Printf("[Consumer] Read payload: %q\n", string(buf[:bytesRead]))
}
```

## Под капотом

Таблица соответствия примитивов kqueue (BSD) и epoll (Linux):
| Концепция | FreeBSD / macOS (kqueue) | Linux (epoll) |
| :--- | :--- | :--- |
| **Создание очереди** | `kqueue()` | `epoll_create1(EPOLL_CLOEXEC)` |
| **Регистрация событий** | `kevent(changelist)` | `epoll_ctl(EPOLL_CTL_ADD/MOD)` |
| **Ожидание событий** | `kevent(eventlist)` | `epoll_wait(events)` |
| **Готовность к чтению** | `EVFILT_READ` | `EPOLLIN` |
| **Готовность к записи** | `EVFILT_WRITE` | `EPOLLOUT` |
| **Edge-Triggered** | Флаг `EV_CLEAR` | Флаг `EPOLLET` |
| **Однократное событие** | Флаг `EV_ONESHOT` | Флаг `EPOLLONESHOT` |
| **Таймеры ядра** | `EVFILT_TIMER` | `timerfd_create()` |
| **Системные сигналы** | `EVFILT_SIGNAL` | `signalfd()` |
| **Слежение за файлами**| `EVFILT_VNODE` | `inotify_init()` / `fanotify` |
В Go пакет `golang.org/x/sys/unix` предоставляет нативные типы `Kevent_t` и функции `Kqueue()`, `Kevent()` на Darwin/BSD сборках.

## Подводные камни

1. **Платформенная изоляция**: Попытка скомпилировать прямой вызов `syscall.Kqueue()` на Linux завершится ошибкой компиляции `undefined: syscall.Kqueue`. Код для kqueue обязан находиться в файлах с build tags `//go:build darwin || freebsd || openbsd || netbsd`.
2. **Множественная регистрация**: В kqueue повторный вызов `kevent` с флагом `EV_ADD` для того же дескриптора и фильтра просто обновляет его настройки, тогда как в Linux `epoll_ctl(ADD)` вернет ошибку `EEXIST`.
3. **Отслеживание сокетов в kqueue**: Если не вычитать данные полностью в режиме `EV_CLEAR`, событие перестанет генерироваться, как и в Linux `EPOLLET`.

## На собеседовании

**Вопрос с собеседования:** «Почему Nginx исторически показывал более высокую производительность на FreeBSD, чем на Linux до появления epoll?»
**Ответ:**
Подсистема `kqueue` появилась во FreeBSD еще в 2000 году (FreeBSD 4.1) и позволяла отслеживать десятки тысяч сокетов за константное время \(O(1)\) с возможностью атомарной подачи изменений и ожидания за один системный вызов `kevent()`.
В Linux в это время существовал только медленный \(O(N)\) `poll/select`. Полноценный `epoll` появился в Linux только в версии ядра 2.6 (2003 год). С тех пор производительность выровнялась, а с появлением `io_uring` Linux снова вырвался вперед.
