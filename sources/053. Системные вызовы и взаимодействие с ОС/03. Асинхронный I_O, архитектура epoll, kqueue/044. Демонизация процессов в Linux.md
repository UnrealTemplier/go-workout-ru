# Демонизация процессов в Linux: создание независимой сессии ОС через Setsid и отвязка от терминала

## Условие

**Daemonization (Фоновый процесс)**: Используй `os/exec` для запуска другой Go-программы. В поле `SysProcAttr` структуры `exec.Cmd` установи `Setsid: true` (на Linux). Это создаст новую сессию ОС. Завершенный родительский процесс не потянет за собой дочерний — дочерний процесс станет настоящим демоном, независимым от терминала.

## Теория

В операционных системах Unix каждый процесс принадлежит к определенной **группе процессов (Process Group)**, а группы процессов объединяются в **сессии (Sessions)**.

**Проблема закрытия терминала**:
Когда пользователь запускает команду в терминале (Bash):
1. Процесс привязывается к текущей сессии управляющего терминала (Controlling Terminal, TTY).
2. Если пользователь закрывает вкладку терминала или разрывает SSH-соединение, ядро отправляет сигнал **`SIGHUP` (Hangup)** всем процессам этой сессии.
3. По умолчанию получение `SIGHUP` приводит к немедленному завершению всех запущенных дочерних программ.

**Механизм системного вызова `setsid()`**:
Системный вызов `setsid()` создает **новую сессию операционной системы**:
1. Процесс становится лидером новой сессии (Session Leader).
2. Процесс становится лидером новой группы процессов (Process Group Leader).
3. Процесс **полностью отвязывается от управляющего терминала**.
4. Закрытие SSH-сессии, эмулятора терминала или завершение родительского процесса больше **никак не влияет** на дочерний процесс.
5. При усыновлении процессом PID 1 (systemd / init) процесс превращается в полноценного системного демона (Daemon).

В Go создание новой сессии настраивается атрибутом `exec.Cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true}`.

## Решение по шагам

1. Создайте команду через `exec.Command("sleep", "60")`.
2. Настройте структуру атрибутов: `cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true}`.
3. Перенаправьте стандартные потоки ввода-вывода в `/dev/null` или лог-файл, чтобы процесс не удерживал TTY.
4. Запустите процесс через `cmd.Start()`.
5. Выведите PID дочернего демона и завершите родительский процесс.
6. Убедитесь, что дочерний процесс продолжает выполняться в фоне независимо от родителя.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"os/exec"
	"syscall"
)

func main() {
	fmt.Printf("[Parent] Master process started. PID: %d, PPID: %d\n", os.Getpid(), os.Getppid())

	// Команда для запуска в фоновом режиме демона
	cmd := exec.Command("sleep", "10")

	// Настройка системных атрибутов: Setsid = true
	// Это транслируется в вызов sys_setsid() между clone/fork и execve
	cmd.SysProcAttr = &syscall.SysProcAttr{
		Setsid: true, // Создает новую POSIX сессию, отвязывая от TTY
	}

	// Отвязываем дескрипторы от текущего терминала, перенаправляя в nil
	cmd.Stdin = nil
	cmd.Stdout = nil
	cmd.Stderr = nil

	// Запускаем процесс асинхронно (без ожидания)
	if err := cmd.Start(); err != nil {
		panic(fmt.Sprintf("Failed to spawn daemon: %v", err))
	}

	daemonPID := cmd.Process.Pid
	fmt.Printf("[Parent] Successfully spawned detached daemon process! PID: %d\n", daemonPID)
	fmt.Println("[Parent] Exiting now. Daemon will survive independently under init/systemd (PID 1).")
}
```

ℹ️ Создание полностью отвязанного от терминала демона через SysProcAttr.Setsid

**`Терминал`**

```bash
go run main.go
# Вывод:
# [Parent] Master process started. PID: 39100, PPID: 31050
# [Parent] Successfully spawned detached daemon process! PID: 39105
# [Parent] Exiting now. Daemon will survive independently under init/systemd (PID 1).

# Проверка статуса демона в системе:
ps -o pid,ppid,sid,tty,stat,cmd -p 39105
# Вывод ps:
#   PID  PPID   SID TTY      STAT CMD
# 39105     1 39105 ?        S    sleep 10
# (Обратите внимание: PPID = 1 (усыновлен systemd), TTY = ? (терминал отсутствует), SID = PID)
```

## Под капотом

Что происходит внутри ядра Linux при `Setsid: true`:
1. В ассемблерном трамплине `forkAndExecInChild` после вызова `clone()` дочерний процесс выполняет системный вызов `SYS_SETSID` (номер 112 на x86_64).
2. Ядро проверяет, не является ли процесс уже лидером группы процессов (`task_pgrp(current) == current`). Если нет:
   - Создается новый объект `struct session`.
   - Создается новая группа процессов `struct pid *pgrp`.
   - Поле `tty` в дескрипторе процесса обнуляется (`current->signal->tty = NULL`).
3. Дочерний процесс выполняет `execve("sleep")`.
4. Когда родительский процесс завершается, ядро обходит детей процесса и переназначает их родителя на корневой процесс `PID 1` (init/systemd).

## Подводные камни

1. **Неотвязанные потоки ввода-вывода (Stdin/Stdout/Stderr)**: Если оставить `cmd.Stdout = os.Stdout`, дочерний процесс будет удерживать дескриптор терминала открытым. При закрытии терминала запись в дескриптор вызовет ошибку `EPIPE` или `SIGPIPE`. Всегда перенаправляйте дескрипторы демона в файл или `/dev/null`.
2. **Рабочая директория (Current Working Directory)**: Демон наследует текущую рабочую директорию. Если это смонтированный сетевой диск (NFS) или съемная флешка, ОС не позволит размонтировать диск, пока жив демон. В production директорию меняют на корень: `Dir: "/"`.
3. **Зомби-демоны**: Если демон запускает свои дочерние процессы, он обязан собирать их через `wait4()`, иначе они останутся зомби.

## На собеседовании

**Вопрос с собеседования:** «Почему в современном Cloud Native мире (Kubernetes, Docker, systemd) классическая двойная демонизация процесса (Double Fork Daemonization) считается устаревшим антипаттерном?»
**Ответ:**
1. **PID 1 Supervision**: Оркестраторы (Kubernetes, Docker, systemd) рассчитывают, что главный процесс приложения выполняется на **переднем плане (Foreground)** как `PID 1` контейнера.
2. **Потеря контроля**: Если процесс выполнит `fork()` + `setsid()` и завершит родителя, Docker решит, что контейнер остановился, и завершит Pod со статусом `Exited`.
3. Все логирование и сбор метрик в облаке строятся на сборе `stdout`/`stderr` контейнера, а перезапуски обеспечивает сам супервизор Kubernetes, делая ручную демонизацию ненужной и вредной.
