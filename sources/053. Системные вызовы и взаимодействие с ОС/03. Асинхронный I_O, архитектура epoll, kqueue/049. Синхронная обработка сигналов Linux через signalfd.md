# Синхронная обработка сигналов Linux через signalfd и мультиплексирование в epoll

## Условие

**Epoll signal handling**: Используйте `signalfd()` для обработки сигналов через epoll.

## Теория

Традиционная обработка сигналов через `sigaction()` в Unix страдает от фундаментального архитектурного противоречия:
- Сигнал доставляется **асинхронно** в произвольный момент времени, прерывая исполнение текущей инструкции потока.
- В обработчике сигнала запрещено использовать 99% стандартных библиотечных функций (Async-Signal-Safety limit).

**Революционный системный вызов ядра Linux: `signalfd` (Linux 2.6.22+)**:
1. Системный вызов `signalfd(fd, &mask, flags)` создает специальный файловый дескриптор, ассоциированный с маской сигналов процесса.
2. Сигналы предварительно блокируются с помощью `sigprocmask()`: ядро больше не прерывает потоки и не вызывает асинхронные обработчики.
3. Вместо прерывания ядра сигнал помещается в очередь файлового дескриптора.
4. Дескриптор `signalfd` регистрируется в **стандартном epoll event loop** с флагом `EPOLLIN`.
5. При поступлении сигнала `epoll_wait` просыпается, как при получении сетевого пакета.
6. Сервер считывает структурированные данные о сигнале (`struct signalfd_siginfo` размером 128 байт), содержащие PID отправителя, UID и метаданные.
Асинхронные сигналы превращаются в **обычные синхронные I/O события**!

## Решение по шагам

1. Заблокируйте сигналы `SIGUSR1` и `SIGTERM` через системный вызов `SYS_RT_SIGPROCMASK`.
2. Создайте дескриптор `signalfd` через системный вызов `SYS_SIGNALFD4`.
3. Создайте инстанс epoll и зарегистрируйте `signalfd` с событием `syscall.EPOLLIN`.
4. В фоновой горутине отправьте сигнал `SIGUSR1` через `syscall.Kill`.
5. Дождитесь пробуждения `syscall.EpollWait`.
6. Считайте структуру `SignalfdSiginfo` (128 байт) и извлеките номер сигнала и PID отправителя.
7. Закройте дескрипторы.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/binary"
	"fmt"
	"os"
	"syscall"
	"time"
	"unsafe"
)

// Linux signalfd constants
const (
	SYS_SIGNALFD4        = 289 // syscall number on Linux x86_64
	SYS_RT_SIGPROCMASK   = 14  // syscall number on Linux x86_64
	SIG_BLOCK            = 0
	SFD_NONBLOCK         = 0x800
	SFD_CLOEXEC          = 0x80000
)

// SignalfdSiginfo представляет 128-байтовую структуру данных о сигнале в ядре Linux
type SignalfdSiginfo struct {
	SsiSigno   uint32 // Номер сигнала
	SsiErrno   int32  // Код ошибки
	SsiCode    int32  // Сигнальный код
	SsiPid     uint32 // PID процесса-отправителя
	SsiUid     uint32 // UID пользователя-отправителя
	SsiFd      int32  // Файловый дескриптор (для SIGIO)
	_          [96]byte // Выравнивание до 128 байт
}

func main() {
	pid := os.Getpid()
	fmt.Printf("[Signalfd Core] Process started. PID: %d\n", pid)

	// 1. Формируем битовую маску для сигналов SIGUSR1 (10) и SIGTERM (15)
	var sigset uint64
	sigset |= 1 << (syscall.SIGUSR1 - 1)
	sigset |= 1 << (syscall.SIGTERM - 1)

	// Блокируем сигналы, чтобы ядро не вызывало стандартные обработчики
	_, _, errNo := syscall.Syscall6(
		SYS_RT_SIGPROCMASK,
		uintptr(SIG_BLOCK),
		uintptr(unsafe.Pointer(&sigset)),
		0,
		8, // размер маски 8 байт (64 бита)
		0, 0,
	)
	if errNo != 0 {
		panic(fmt.Sprintf("sigprocmask failed: %v", errNo))
	}
	fmt.Println("[Signalfd Core] Signals SIGUSR1 & SIGTERM blocked from async interruption.")

	// 2. Создаем signalfd дескриптор
	r1, _, errNo := syscall.Syscall6(
		SYS_SIGNALFD4,
		^uintptr(0), // -1 для создания нового FD
		uintptr(unsafe.Pointer(&sigset)),
		8,
		uintptr(SFD_NONBLOCK|SFD_CLOEXEC),
		0, 0,
	)
	if errNo != 0 {
		panic(fmt.Sprintf("signalfd4 failed: %v", errNo))
	}
	sfd := int(r1)
	defer syscall.Close(sfd)

	fmt.Printf("[Signalfd Core] Created signalfd descriptor: %d\n", sfd)

	// 3. Создаем epoll и регистрируем signalfd
	epfd, _ := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	defer syscall.Close(epfd)

	ev := syscall.EpollEvent{
		Events: syscall.EPOLLIN,
		Fd:     int32(sfd),
	}
	_ = syscall.EpollCtl(epfd, syscall.EPOLL_CTL_ADD, sfd, &ev)

	// 4. Фоновый отправитель сигнала
	go func() {
		time.Sleep(100 * time.Millisecond)
		fmt.Printf("[Sender] Sending SIGUSR1 to self (PID %d)...\n", pid)
		_ = syscall.Kill(pid, syscall.SIGUSR1)
	}()

	// 5. Опрашиваем epoll на поступление сигнала
	events := make([]syscall.EpollEvent, 4)
	fmt.Println("[Signalfd Core] EpollWait: Waiting for signal via file descriptor...")

	nEvents, err := syscall.EpollWait(epfd, events, 2000)
	if err != nil {
		panic(err)
	}

	if nEvents > 0 && int(events[0].Fd) == sfd {
		rawInfo := make([]byte, 128)
		n, _ := syscall.Read(sfd, rawInfo)
		if n >= 128 {
			signo := binary.LittleEndian.Uint32(rawInfo[0:4])
			senderPid := binary.LittleEndian.Uint32(rawInfo[12:16])

			fmt.Printf("\n[Signalfd Event] Epoll caught signal synchronously!\n")
			fmt.Printf("  Signal Number:  %d (SIGUSR1)\n", signo)
			fmt.Printf("  Sender PID:     %d (Matches self PID: %v)\n", senderPid, int(senderPid) == pid)
		}
	}

	fmt.Println("Synchronous signal handling via epoll and signalfd validated successfully!")
}
```

## Под капотом

Что происходит внутри ядра Linux при использовании `signalfd`:
1. Дескриптор `signalfd` ссылается на структуру `struct signalfd_ctx` в памяти ядра.
2. Когда процессу отправляется сигнал через `kill()`, ядро проверяет маску блокировки потока.
3. Поскольку сигнал заблокирован в `sigprocmask`, стандартный обработчик прерывания не вызывается. Сигнал добавляется в очередь `pending signals` процесса.
4. Ядро пробуждает очередь ожидания `signalfd_ctx->wqh`.
5. Связанный с ней дескриптор в `epoll` помечается как готовый к чтению `EPOLLIN`.
6. Вызов `read(sfd)` извлекает элемент из очереди `pending signals` и заполняет структуру `signalfd_siginfo`.

## Подводные камни

1. **Забытая блокировка в `sigprocmask`**: Если не заблокировать сигналы через `sigprocmask` перед созданием `signalfd`, ядро выполнит стандартное действие сигнала (например, завершит процесс при `SIGTERM`) до того, как сигнал попадет в дескриптор `signalfd`.
2. **Размер буфера чтения**: Буфер для чтения из `signalfd` должен быть кратен 128 байтам (`sizeof(struct signalfd_siginfo)`), иначе `read` вернет ошибку `EINVAL`.
3. **Сигналы, которые нельзя заблокировать**: `SIGKILL` и `SIGSTOP` нельзя заблокировать в `sigprocmask` и нельзя перехватить через `signalfd`.

## На собеседовании

**Вопрос с собеседования:** «Почему Nginx и QEMU перешли на `signalfd` в Linux вместо классического Self-Pipe Trick?»
**Ответ:**
1. **Экономия дескрипторов и памяти**: Self-Pipe требует создания двух дескрипторов (чтение и запись пайпа) и написания C-функции обработчика сигнала. `signalfd` требует ровно **один дескриптор** и не требует обработчиков вообще.
2. **Нулевой оверхед по context switch**: Нет необходимости прерывать исполнение рабочего потока для выполнения C-трамплина записи байта в pipe.
3. **Богатые метаданные**: `signalfd_siginfo` передает точный PID и UID отправителя, статус завершения дочернего процесса (`si_status`), адрес исключения памяти (`si_addr`), что невозможно передать через однобайтовый флаг в пайпе.
