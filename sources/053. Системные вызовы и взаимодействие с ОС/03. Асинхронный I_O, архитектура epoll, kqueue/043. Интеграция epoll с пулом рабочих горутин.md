# Интеграция epoll с пулом рабочих горутин (Reactor Pattern + Worker Pool Architecture)

## Условие

**Epoll + goroutines**: Интегрируйте epoll с горутинами: один поток epoll wait, горутины обрабатывают события.

## Теория

В архитектуре современных высокопроизводительных серверов классический паттерн **Reactor** разделяет ответственность между двумя уровнями:

1. **Reactor Thread (Диспетчер ввода-вывода)**:
   - Выполняется в выделенной горутине, привязанной к системному потоку ОС (`runtime.LockOSThread()`).
   - Крутится в бесконечном цикле `epoll_wait()`.
   - Задача реактора — исключительно **детектировать события** и мгновенно передавать готовые задачи рабочим воркерам, не тратя время на тяжелую бизнес-логику или дисковые операции.
2. **Worker Pool (Пул рабочих горутин)**:
   - Набор из \(M\) горутин (например, по числу ядер CPU или фиксированный пул 100 воркеров).
   - Горутины читают готовые дескрипторы из Go-канала очереди задач.
   - Воркеры выполняют парсинг протокола, запросы в базу данных, сериализацию JSON/Protobuf и отправку ответа в сокет.
Это гарантирует, что медленный запрос одного клиента никогда не заблокирует обработку тысяч других клиентов в цикле epoll.

## Решение по шагам

1. Создайте инстанс epoll через `syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)`.
2. Создайте очередь задач: буферизованный Go-канал `taskQueue := make(chan int, 1000)`.
3. Запустите пул из 4 рабочих горутин, ожидающих дескрипторы из канала.
4. Создайте несколько неблокирующих пайпов для симуляции клиентов.
5. Запустите Reactor-горутину с `syscall.EpollWait`, отправляющую сработавшие дескрипторы в `taskQueue`.
6. Убедитесь в параллельной обработке событий воркерами и корректном завершении.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"syscall"
	"time"
)

type NetworkReactor struct {
	epfd      int
	taskChan  chan int
	stopChan  chan struct{}
	wg        sync.WaitGroup
	numWorkers int
}

func NewNetworkReactor(numWorkers int) (*NetworkReactor, error) {
	epfd, err := syscall.EpollCreate1(syscall.EPOLL_CLOEXEC)
	if err != nil {
		return nil, err
	}

	return &NetworkReactor{
		epfd:       epfd,
		taskChan:   make(chan int, 256),
		stopChan:   make(chan struct{}),
		numWorkers: numWorkers,
	}, nil
}

func (r *NetworkReactor) Start() {
	// 1. Запускаем пул рабочих горутин (Worker Pool)
	for id := 1; id <= r.numWorkers; id++ {
		r.wg.Add(1)
		go func(workerID int) {
			defer r.wg.Done()
			buf := make([]byte, 128)

			for {
				select {
				case <-r.stopChan:
					return
				case fd, ok := <-r.taskChan:
					if !ok {
						return
					}
					// Воркер выполняет чтение и тяжелую обработку
					n, err := syscall.Read(fd, buf)
					if n > 0 {
						fmt.Printf("[Worker %d] Processed %d bytes from FD %d: %q\n",
							workerID, n, fd, string(buf[:n]))
					}
					if err != nil {
						_ = syscall.Close(fd)
					}
				}
			}
		}(id)
	}

	// 2. Запускаем Reactor Loop (I/O Dispatcher)
	go func() {
		events := make([]syscall.EpollEvent, 32)
		for {
			select {
			case <-r.stopChan:
				return
			default:
				nEvents, err := syscall.EpollWait(r.epfd, events, 100)
				if err != nil {
					continue
				}
				for i := 0; i < nEvents; i++ {
					fd := int(events[i].Fd)
					// Мгновенная диспетчеризация в очередь воркеров
					r.taskChan <- fd
				}
			}
		}
	}()
}

func (r *NetworkReactor) Register(fd int) error {
	ev := syscall.EpollEvent{
		Events: syscall.EPOLLIN | syscall.EPOLLONESHOT,
		Fd:     int32(fd),
	}
	return syscall.EpollCtl(r.epfd, syscall.EPOLL_CTL_ADD, fd, &ev)
}

func (r *NetworkReactor) Stop() {
	close(r.stopChan)
	close(r.taskChan)
	r.wg.Wait()
	_ = syscall.Close(r.epfd)
}

func main() {
	reactor, err := NewNetworkReactor(3) // 3 рабочих горутины
	if err != nil {
		panic(err)
	}
	reactor.Start()
	fmt.Println("[System] Reactor + Worker Pool engine online.")

	// Создаем тестовые клиентские каналы
	var p1, p2, p3 [2]int
	_ = syscall.Pipe(p1[:])
	_ = syscall.Pipe(p2[:])
	_ = syscall.Pipe(p3[:])

	_ = syscall.SetNonblock(p1[0], true)
	_ = syscall.SetNonblock(p2[0], true)
	_ = syscall.SetNonblock(p3[0], true)

	_ = reactor.Register(p1[0])
	_ = reactor.Register(p2[0])
	_ = reactor.Register(p3[0])

	// Эмулируем входящий всплеск трафика
	_, _ = syscall.Write(p1[1], []byte("PAYMENT_REQUEST_AUTH"))
	_, _ = syscall.Write(p2[1], []byte("ORDER_CREATE_BURST"))
	_, _ = syscall.Write(p3[1], []byte("ANALYTICS_EVENT_HIT"))

	time.Sleep(150 * time.Millisecond)

	// Очистка ресурсов
	_ = syscall.Close(p1[1])
	_ = syscall.Close(p2[1])
	_ = syscall.Close(p3[1])

	reactor.Stop()
	fmt.Println("[System] Reactor shut down gracefully.")
}
```

ℹ️ Архитектурный паттерн Reactor + Worker Pool: epoll_wait диспетчеризует задачи в горутины

## Под капотом

Синхронизация планировщика Go с событиями ядра:
1. Реактор-горутина вызывает `EpollWait` с коротким таймаутом (100 мс) или без таймаута.
2. Передача дескриптора в канал `r.taskChan <- fd` выполняет быструю блокировку кольцевого буфера канала (`chan.lock`).
3. Спящие воркеры пробуждаются планировщиком Go (`sudog` очередь) и начинают исполняться параллельно на свободных ядрах процессора.
4. Использование флага `EPOLLONESHOT` гарантирует, что дескриптор не попадет двум воркерам одновременно.

## Подводные камни

1. **Переполнение очереди `taskChan` (Backpressure)**: Если поток сетевых пакетов превышает пропускную способность пула воркеров, буфер канала заполнится. Вызов `r.taskChan <- fd` заблокирует сам Reactor Loop, остановив прием новых событий. В продакшене используют политики сброса нагрузки (Load Shedding).
2. **Гонка повторной активации сокета**: После обработки пакета воркер обязан реактивировать сокет через `EPOLL_CTL_MOD`, иначе сокет перестанет просыпаться.
3. **Утечки дескрипторов при сбое воркера**: Если воркер запаникует во время обработки, дескриптор должен быть корректно закрыт в блоке `defer`.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество многопоточного Reactor Pattern (Master-Worker Reactor как в Netty) по сравнению с моделью One-Goroutine-Per-Connection в стандартном Go?»
**Ответ:**
1. **Экономия памяти**: Модель 1-горутина-на-клиент при 500 000 клиентах требует минимум 1–2 ГБ памяти только под стеки горутин. В Reactor Pattern пул из 64 воркеров занимает считанные мегабайты.
2. **Защита от перегрузки CPU (CPU Throttling)**: Фиксированный пул воркеров предотвращает переключение контекста между сотнями тысяч горутин при всплесках трафика (Thundering Herd / Context Switch Storm).
3. **Кэш-локальность**: Воркеры остаются привязаны к ядрам CPU, сохраняя горячие кэши инструкций L1/L2.
