# Собственный аллокатор памяти поверх mmap с Free-List и бенчмарк против new/make

## Условие

**Реализация собственного аллокатора через `mmap` и управление памятью.**: Создайте простой аллокатор, который выделяет большие блоки через `mmap` и раздаёт куски фиксированного размера, используя собственный свободный список. Сравните скорость с `new`/`make`.

## Теория

Стандартный аллокатор Go (`runtime.mallocgc` / `new` / `make`) оптимизирован под универсальные сценарии:
- Поддерживает 67 классов размеров.
- Управляет битовыми картами разметки указателей для сборщика мусора.
- Учитывает статистику памяти в `GOMEMLIMIT` и `GOGC`.
Однако для узкоспециализированных HighLoad структур (пулы сетевых пакетов фиксированного размера, слоты кольцевых буферов) собственный **Free-List аллокатор поверх `mmap`** может работать быстрее стандартного `new`:
1. **\(O(1)\) аллокация**: Извлечение из головы связного списка занимает ровно одну инструкцию `MOV`.
2. **Нулевая нагрузка на сборщик мусора**: Память выделена через `mmap`, поэтому сборщик мусора Go вообще не знает о существовании этих объектов и не сканирует их.
3. **Отсутствие фрагментации кучи**: Блоки имеют одинаковый размер и переиспользуются вечно.

## Решение по шагам

1. Выделите через анонимный `syscall.Mmap` арену размером 1 МБ.
2. Разбейте арену на блоки по 32 байта и свяжите их в односвязный Free-List.
3. Реализуйте метод `Alloc()` и `Free(ptr)`.
4. Напишите сравнительный бенчмарк: 100 000 аллокаций и освобождений через кастомный аллокатор против `make([]byte, 32)`.
5. Сравните время выполнения и количество аллокаций в куче Go.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"syscall"
	"time"
	"unsafe"
)

type MmapPoolAllocator struct {
	rawMmap   []byte
	blockSize uintptr
	freeHead  unsafe.Pointer
	capacity  int
}

func NewMmapPoolAllocator(size int, blockSize uintptr) (*MmapPoolAllocator, error) {
	page := syscall.Getpagesize()
	aligned := (size + page - 1) & ^(page - 1)

	raw, err := syscall.Mmap(
		-1, 0, aligned,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		return nil, err
	}

	slots := aligned / int(blockSize)
	base := uintptr(unsafe.Pointer(&raw[0]))

	for i := 0; i < slots-1; i++ {
		curr := unsafe.Pointer(base + uintptr(i)*blockSize)
		next := unsafe.Pointer(base + uintptr(i+1)*blockSize)
		*(*unsafe.Pointer)(curr) = next
	}
	last := unsafe.Pointer(base + uintptr(slots-1)*blockSize)
	*(*unsafe.Pointer)(last) = nil

	return &MmapPoolAllocator{
		rawMmap:   raw,
		blockSize: blockSize,
		freeHead:  unsafe.Pointer(base),
		capacity:  slots,
	}, nil
}

func (a *MmapPoolAllocator) Alloc() unsafe.Pointer {
	if a.freeHead == nil {
		return nil
	}
	slot := a.freeHead
	a.freeHead = *(*unsafe.Pointer)(slot)
	return slot
}

func (a *MmapPoolAllocator) Free(p unsafe.Pointer) {
	if p == nil {
		return
	}
	*(*unsafe.Pointer)(p) = a.freeHead
	a.freeHead = p
}

func (a *MmapPoolAllocator) Destroy() {
	if a.rawMmap != nil {
		_ = syscall.Munmap(a.rawMmap)
		a.rawMmap = nil
	}
}

func main() {
	const totalOps = 200000
	const blockSize = 32

	pool, err := NewMmapPoolAllocator(totalOps*blockSize, blockSize)
	if err != nil {
		panic(err)
	}
	defer pool.Destroy()

	// 1. Тест кастомного Mmap аллокатора
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	startMmap := time.Now()
	for i := 0; i < totalOps; i++ {
		p := pool.Alloc()
		// Имитация записи
		*(*uint32)(p) = uint32(i)
		pool.Free(p)
	}
	mmapDur := time.Since(startMmap)

	runtime.ReadMemStats(&m2)
	goHeapUsedMmap := m2.HeapAlloc - m1.HeapAlloc

	// 2. Тест стандартного make([]byte, 32)
	runtime.GC()
	runtime.ReadMemStats(&m1)

	startMake := time.Now()
	for i := 0; i < totalOps; i++ {
		b := make([]byte, blockSize)
		b[0] = byte(i)
		_ = b
	}
	makeDur := time.Since(startMake)

	runtime.ReadMemStats(&m2)
	goHeapUsedMake := m2.TotalAlloc - m1.TotalAlloc

	fmt.Println("=== ALLOCATOR BENCHMARK: CUSTOM MMAP POOL VS RUNTIME MAKE ===")
	fmt.Printf("Operations count:         %d alloc/free cycles\n", totalOps)
	fmt.Printf("Custom Mmap Pool:         %v | Go Heap Allocations: %d bytes\n", mmapDur, goHeapUsedMmap)
	fmt.Printf("Standard make([]byte):    %v | Go Heap Allocations: %d bytes\n", makeDur, goHeapUsedMake)
	fmt.Printf("Speedup of custom pool:   %.2fx faster!\n", float64(makeDur)/float64(mmapDur))
}
```

## Под капотом

Почему кастомный пул работает быстрее:
1. `make([]byte, 32)`:
   - Проверяет размерный класс в `mcache`.
   - Если спан полон, обращается к `mcentral` под блокировкой.
   - Инициализирует срез нулями.
   - Выделенная память учитывается счетчиком `heap_live`, приближая запуск сборщика мусора.
2. Кастомный пул:
   - Метод `Alloc()` компилируется всего в **3 процессорные инструкции**: `MOV`, `MOV`, `MOV`.
   - Память не зануляется заново, если это не требуется прикладной логике.
   - Нагрузка на GC равна строго **0 байт**.

## Подводные камни

1. **Многопоточность**: Базовый Free-List аллокатор не является thread-safe. Для использования из разных горутин требуется защита мьютексом или lock-free реализация на атомарных CAS-указателях (`sync/atomic.CompareAndSwapPointer`).
2. **Утечки арены**: Если забыть вызвать `Munmap` при уничтожении пула, память не освободится даже после удаления всех Go-ссылок.
3. **ABA-проблема в Lock-Free**: При реализации lock-free Free-List без мьютексов возникает классическая ABA-проблема, требующая версионирования указателей (Tagged Pointers).

## На собеседовании

**Вопрос с собеседования:** «Почему в Go для повторного использования объектов обычно рекомендуют `sync.Pool`, а не кастомный off-heap аллокатор?»
**Ответ:**
1. `sync.Pool` встроен в рантайм Go, thread-safe без глобальных мьютексов (шардирован по процессорам `P` через `poolLocal`), и безопасен с точки зрения типов.
2. Однако память в `sync.Pool` остается в куче Go и удерживает Go-указатели.
3. Кастомный off-heap аллокатор поверх `mmap` применяют только в экстремальных HighLoad сценариях (in-memory кэши на десятки гигабайт, HFT движки), где сам факт наличия миллионов указателей в куче Go парализует GC Mark-фазу.
