# Масштабирование инфраструктуры: Cluster Autoscaler и оптимизация расходов

## Условие

Настрой **Cluster Autoscaler**: scales node groups based on pending pods. `minSize: 3`, `maxSize: 100`. Integration with cloud provider (AWS ASG, GKE node pools). Покажи cost optimization.

## Теория

Пока HPA масштабирует поды внутри кластера, **Cluster Autoscaler (CA)** масштабирует сами физические или виртуальные серверы (**Worker Nodes**):
1. **Триггер масштабирования вверх (Scale-Up):**
   - Происходит ТОЛЬКО тогда, когда один или несколько подов переходят в статус **`Pending`** из-за невозможности планировщика (`kube-scheduler`) найти узел с достаточным количеством свободных ресурсов (`Insufficient cpu`, `Insufficient memory`).
   - CA моделирует добавление ноды: если добавление узла в Auto Scaling Group (ASG) позволит разместить Pending-поды, CA отправляет вызов в Cloud API на увеличение размера группы нод.
2. **Триггер масштабирования вниз (Scale-Down):**
   - Если в течение периода стабилизации (по умолчанию 10 минут) утилизация ресурсов на ноде ниже порогового значения (например, суммарные requests подов < 50% емкости ноды), CA пытается вытеснить (evict) поды на другие узлы и завершить работу лишней ноды, сокращая затраты на облако.

## Решение по шагам

1. Настройте Auto Scaling Group (ASG) в AWS с границами `min: 3, max: 100`.
2. Разверните Cluster Autoscaler через Deployment с правами доступа к AWS Cloud API.
3. Задайте аргументы: `--scale-down-unneeded-time=10m`, `--scale-down-utilization-threshold=0.5`.
4. Создайте резкий всплеск нагрузки (создав Deployment на 50 тяжелых подов).
5. Проследите в логах CA добавление новых инстансов и автоматическое уменьшение кластера после удаления нагрузки.

## Код решения

**`cluster-autoscaler.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cluster-autoscaler
  namespace: kube-system
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cluster-autoscaler
  template:
    metadata:
      labels:
        app: cluster-autoscaler
    spec:
      serviceAccountName: cluster-autoscaler-sa
      containers:
        - image: registry.k8s.io/autoscaling/cluster-autoscaler:v1.28.2
          name: cluster-autoscaler
          command:
            - ./cluster-autoscaler
            - --v=4
            - --stderrthreshold=info
            - --cloud-provider=aws
            - --skip-nodes-with-local-storage=false
            - --expander=least-waste # Выбирает группу узлов с наименьшим перерасходом ресурсов
            - --node-group-auto-discovery=asg:tag=k8s.io/cluster-autoscaler/enabled,k8s.io/cluster-autoscaler/my-cluster
            - --scale-down-unneeded-time=10m
            - --scale-down-utilization-threshold=0.5
            - --max-nodes-total=100
          resources:
            limits:
              cpu: 100m
              memory: 300Mi
            requests:
              cpu: 100m
              memory: 300Mi
```

**`load-spike.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: heavy-workload
spec:
  replicas: 40
  selector:
    matchLabels:
      app: heavy-workload
  template:
    metadata:
      labels:
        app: heavy-workload
    spec:
      containers:
        - name: app
          image: busybox
          command: ["sleep", "3600"]
          resources:
            requests:
              cpu: "1"
              memory: 2Gi
```

**`Терминал`**

```bash
# Применение тяжелой нагрузки (поды упадут в Pending из-за нехватки нод)
kubectl apply -f load-spike.yaml

# Просмотр логов Cluster Autoscaler (фиксация Pending подов и вызов AWS API)
kubectl logs -n kube-system -l app=cluster-autoscaler -f | grep "Scale-up"
# I0904 10:20:15 Scale-up: 6 pods need reservation, increasing ASG size to 12 nodes

# Наблюдение за появлением новых нод в кластере
kubectl get nodes -w
```

## Под капотом

Cluster Autoscaler запускает бесконечный цикл планирования (раз в 10 секунд). Он считывает все неназначенные поды со статусом `Pending` и причиной `FailedScheduling`. В памяти запускается эмулятор `kube-scheduler`, который виртуально примеряет поды на шаблон узлов из каждой доступной группы ASG. Если найден подходящий пул, CA напрямую вызывает API провайдера (`autoscaling:SetDesiredCapacity`), увеличивая число серверов. При скейлдауне CA проверяет условия PDB (PodDisruptionBudget) и не удаляет ноды с подами без контроллера или локальным хранилищем.

## Подводные камни

1. Наличие подов без контроллера (Standalone Pods) или с `emptyDir`: CA по умолчанию откажется гасить ноду, если на ней запущен Pod, созданный напрямую `kubectl run` (так как его некому перезапустить). Флаг `--skip-nodes-with-system-pods=false` и аннотация `cluster-autoscaler.kubernetes.io/safe-to-evict: "true"` обязательны для stateless-приложений.
2. Конфликт с HPA: если пороги requests в подах сильно завышены, кластер закажет дорогие лишние серверы, которые будут простаивать.

## На собеседовании

**Вопрос с собеседования:** «Почему Cluster Autoscaler ориентируется на `resources.requests`, а не на реальное текущее потребление CPU ноды по метрикам Prometheus?»
**Ответ:** Потому что планировщик Kubernetes (`kube-scheduler`) распределяет поды строго на основе гарантированных резерваций — `resources.requests`. Если бы CA ориентировался на реальное потребление (которое в простое может составлять 5%), он бы уменьшил количество серверов, но планировщик не смог бы перезапустить вытесненные поды на оставшихся узлах из-за исчерпания лимитов requests, что привело бы к циклическому коллапсу кластера.
