# Локальный рендеринг и отладка манифестов: команда helm template

## Условие

Используйте `helm template` для рендера манифестов локально без установки в кластер.

## Теория

Команда **`helm template`** — важнейший инструмент разработчика и CI/CD конвейеров:
1. **Назначение:** Рендерит шаблоны чарта в стандартный многодокументный YAML-файл на stdout без подключения к кластеру Kubernetes (полностью offline).
2. **Ключевые флаги:**
   - `-f my-values.yaml`: подстановка конкретного файла значений.
   - `-s templates/deployment.yaml`: рендеринг только одного конкретного файла шаблона (ускоряет отладку).
   - `--validate`: проверка соответствия сгенерированных манифестов OpenAPI-схеме целевой версии Kubernetes (требует подключения к API кластера).
   - `--api-versions`: эмуляция поддерживаемых API версий K8s в offline-режиме.
3. **Применение в CI/CD:**
   - Сканирование манифестов статическими анализаторами безопасности (**kube-linter**, **checkov**, **trivy**, **polaris**).
   - Сравнение диффов перед деплоем через `helm-diff`.

## Решение по шагам

1. Запустите рендеринг всего чарта: `helm template my-release ./my-chart`.
2. Запустите рендеринг только сервиса: `helm template my-release ./my-chart -s templates/service.yaml`.
3. Передайте сгенерированный поток манифестов в линтер безопасности `kube-linter`.
4. Протестируйте dry-run проверку через `kubectl apply --dry-run=client -f -`.

## Код решения

**`Терминал`**

```bash
# Рендеринг всех манифестов чарта в один файл
helm template webapp ./myapp-chart -f values-prod.yaml > release.yaml

# Рендеринг строго одного шаблона для точечной отладки
helm template webapp ./myapp-chart -s templates/ingress.yaml

# Валидация манифестов на соответствие стандартам безопасности K8s
helm template webapp ./myapp-chart | kube-linter lint -

# Клиентская валидация синтаксиса K8s без реального создания объектов в кластере
helm template webapp ./myapp-chart | kubectl apply --dry-run=client -f -
```

**`ci-validate.sh`**

```bash
#!/bin/bash
set -euo pipefail

echo "=== Запуск валидации Helm-шаблонов в CI ==="
ENVIRONMENTS=("dev" "staging" "prod")

for env in "${ENVIRONMENTS[@]}"; do
  echo "Проверка окружения: $env"
  helm template "app-$env" ./chart -f "chart/values-$env.yaml" --validate > "/tmp/rendered-$env.yaml"
  kubectl apply --dry-run=server -f "/tmp/rendered-$env.yaml"
done

echo "✅ Все манифесты успешно прошли валидацию API-сервером K8s!" 
```

## Под капотом

`helm template` инициализирует локальный движок рендеринга Helm без вызова сетевых библиотек `client-go`. Он подставляет фиктивные метаданные для `.Release.IsInstall` (true), `.Release.IsUpgrade` (false) и `.Release.Revision` (1). Если используется флаг `--validate`, Helm связывается с Discovery API кластера для загрузки OpenAPI/JSON-схем и проверяет соответствие каждого типа ресурса стандарту API.

## Подводные камни

1. Ограничения функций `lookup`: функция `lookup`, запрашивающая существующие ресурсы в работающем кластере (например, существующий секрет), при выполнении `helm template` возвращает пустую карту `{}`. Шаблоны, полагающиеся на `lookup`, требуют условий обработки nil.
2. Несоответствие версий API: манифест может успешно отрендериться, но упасть в кластере из-за того, что версия API (например, `batch/v1beta1`) была удалена в используемой версии Kubernetes.

## На собеседовании

**Вопрос с собеседования:** «Как в пайплайне GitLab CI / GitHub Actions организовать автоматический аудит безопасности манифестов Helm перед мерджем Pull Request?»
**Ответ:** На этапе тестирования запускается шаг: 1) `helm lint ./chart` для проверки синтаксиса; 2) `helm template release ./chart -f values-prod.yaml > rendered.yaml`; 3) Запуск статических сканеров поверх `rendered.yaml`: `trivy config rendered.yaml` и `kube-linter lint rendered.yaml`. Это позволяет блокировать PR, если разработчик случайно объявил запуск контейнера от пользователя root, забыл указать resource limits или смонтировал опасные хостовые пути.
