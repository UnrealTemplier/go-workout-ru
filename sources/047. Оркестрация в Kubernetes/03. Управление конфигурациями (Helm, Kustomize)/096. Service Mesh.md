# Service Mesh: установка Istio и автоматическая инъекция Envoy Sidecar

## Условие

Установи **Istio**: `istioctl install`. Enable sidecar injection: `kubectl label namespace default istio-injection=enabled`. Покажи automatic Envoy sidecar injection.

## Теория

По мере роста микросервисной сети возникают сложные инфраструктурные задачи: сквозное mTLS-шифрование трафика между подами, канареечные релизы, повторы сбоев (retries), размыкатели цепи (circuit breaker) и распределенная трассировка.
**Service Mesh (на примере Istio):**
1. **Архитектура:**
   - **Data Plane (Плоскость данных):** высокопроизводительные прокси-серверы **Envoy**, внедряемые как sidecar-контейнеры (`istio-proxy`) внутрь каждого Pod приложения. Весь входящий (ingress) и исходящий (egress) трафик пода принудительно заворачивается в Envoy.
   - **Control Plane (Плоскость управления):** компонент **istiod**, который транслирует декларативные правила Kubernetes в конфигурацию Envoy и рассылает ее через xDS API (gRPC).
2. **Automatic Sidecar Injection:**
   - При создании Pod специальный `MutatingAdmissionWebhook` от `istiod` перехватывает манифест.
   - Если namespace помечен лейблом `istio-injection=enabled`, вебхук автоматически внедряет:
     1. Init-контейнер `istio-init`: настраивает правила ядра Linux `iptables` для перехвата сетевых пакетов на портах TCP.
     2. Sidecar-контейнер `istio-proxy` (Envoy).

## Решение по шагам

1. Скачайте и установите утилиту `istioctl`.
2. Установите минимальный профиль Istio: `istioctl install --set profile=demo -y`.
3. Разрешите автоматическую инъекцию sidecar в namespace: `kubectl label namespace default istio-injection=enabled`.
4. Задеплойте обычный микросервис на Go.
5. Проверьте через `kubectl get pods`, что в поде запустилось 2 контейнера (`2/2 READY`).

## Код решения

**`Терминал`**

```bash
# Установка Istio с профилем demo для разработки
istioctl install --set profile=demo -y

# Проверка готовности компонентов Control Plane в namespace istio-system
kubectl get pods -n istio-system

# Включение автоматической инъекции sidecar-прокси в namespace default
kubectl label namespace default istio-injection=enabled --overwrite

# Проверка установленного лейбла
kubectl get ns default --show-labels
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: echo-service
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: echo-service
  template:
    metadata:
      labels:
        app: echo-service
    spec:
      containers:
        - name: app
          image: echo-service:v1.0.0
          ports:
            - containerPort: 8080
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		// Заголовки, добавленные Envoy прокси: x-request-id, x-forwarded-for
		reqID := r.Header.Get("X-Request-Id")
		fmt.Fprintf(w, "Hello from behind Istio Envoy Sidecar! Request-ID: %s\n", reqID)
	})

	log.Println("Микросервис запущен на :8080")
	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatalf("Ошибка сервера: %v", err)
	}
}
```

## Под капотом

При старте Pod первым выполняется init-контейнер `istio-init` с привилегиями `NET_ADMIN`. Он выполняет скрипт `iptables -t nat -A PREROUTING -p tcp -j ISTIO_INBOUND`, перенаправляя весь входящий трафик порта приложения на локальный порт 15006, где слушает Envoy. Исходящий трафик перенаправляется на порт 15001 (`ISTIO_OUTPUT`). Envoy перехватывает TCP-пакет, применяет политики TLS/маршрутизации и пересылает запрос в Go-приложение через петлю `localhost:8080`.

## Подводные камни

1. Запуск init-контейнеров с зависимостью от внешней сети: если Pod имеет кастомный init-контейнер, делающий HTTP-запрос во внешнюю сеть, он может зависнуть, так как `iptables` уже перенаправляют пакеты в Envoy, но сам контейнер `istio-proxy` еще не запущен.
2. Дополнительные накладные расходы на ресурсы: каждый Envoy sidecar потребляет от 50 МБ RAM и добавляет ~1.5–3 мс сетевой задержки (RTT) на каждый сетевой хоп.

## На собеседовании

**Вопрос с собеседования:** «Каким образом Kubernetes понимает, что в Pod нужно добавить второй контейнер `istio-proxy`, если в исходном файле `deployment.yaml` описан только один контейнер?»
**Ответ:** Это происходит благодаря механизму **Mutating Admission Webhook**. Когда манифест отправляется в `kube-apiserver`, до сохранения объекта в `etcd` API-сервер вызывает зарегистрированный вебхук сервиса `istiod`. Вебхук проверяет наличие лейбла `istio-injection=enabled` у namespace, на лету модифицирует JSON-структуру спецификации Pod (добавляя init-контейнер и контейнер `istio-proxy` с томами сертификатов) и возвращает пропатченный манифест обратно в `kube-apiserver`.
