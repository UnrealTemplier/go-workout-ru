# FinOps и мониторинг затрат: Kubecost, аллокация расходов и Right-Sizing

## Условие

Настрой **Cost Monitoring**: Kubecost / OpenCost. Per-namespace, per-deployment, per-pod cost allocation. Showback / chargeback. Recommendations: right-sizing, spot instances. Покажи FinOps for Kubernetes.

## Теория

При масштабном использовании Kubernetes расходы на облако быстро выходят из-под контроля из-за перезакладывания ресурсов разработчиками (Over-provisioning).
**FinOps (Financial Operations) и Kubecost / OpenCost:**
1. **Аллокация затрат (Cost Allocation):**
   - Расчет реальной финансовой стоимости каждого Namespace, Deployment, Pod и даже ServiceAccount в рублях или долларах в час/месяц.
   - Учет как зарезервированных ресурсов (`requests`), так и реально потребленных.
2. **Модели Showback и Chargeback:**
   - **Showback:** Отчетность руководству и командам о том, сколько денег тратит их микросервис («Команда Биллинга потратила 150 000 руб в августе»).
   - **Chargeback:** Реальное списание инфраструктурных затрат с бюджета конкретного бизнес-подразделения компании.
3. **Рекомендации по оптимизации (Right-Sizing):**
   - Kubecost анализирует 30-дневные исторические тренды и рекомендует точные безопасные значения `resources.requests`, позволяя срезать до 40–60% расходов на серверы без риска сбоев.

## Решение по шагам

1. Установите Kubecost через официальный Helm-чарт.
2. Настройте интеграцию с Prometheus для чтения метрик потребления.
3. Задайте кастомную тарифную сетку для стоимости CPU ($0.03/core-hour) и RAM ($0.004/GiB-hour).
4. Запросите отчет по стоимости конкретного namespace через REST API Kubecost.
5. Изучите рекомендации Right-Sizing для оптимизации requests.

## Код решения

**`kubecost-values.yaml`**

```yaml
global:
  prometheus:
    enabled: false
    fqdn: http://prometheus-k8s.monitoring.svc:9090

kubecostProductConfigs:
  clusterName: production-cluster-01
  currencyCode: USD
  # Кастомные тарифы на вычислительные ресурсы хостов
  customPrices:
    cpu: "0.0316"
    memory: "0.0042"
    spotDiscount: "0.70" # Скидка 70% на Spot инстансы
```

**`Терминал`**

```bash
# Установка Kubecost в кластер
helm repo add cost-analyzer https://kubecost.github.io/cost-analyzer/
helm upgrade --install kubecost cost-analyzer/cost-analyzer \
  --namespace kubecost --create-namespace \
  -f kubecost-values.yaml

# Проброс порта веб-дашборда Kubecost
kubectl port-forward --namespace kubecost deployment/kubecost-cost-analyzer 9090:9090 &

# Получение данных об аллокации расходов по неймспейсам через JSON API
curl -s "http://localhost:9090/model/allocation?window=7d&aggregate=namespace" | jq '.data[0]'

# Запрос рекомендаций Right-Sizing по оптимизации requests контейнеров
curl -s "http://localhost:9090/model/savings/requestSizingV2?targetCPUUtilization=0.75" | jq '.[] | {container: .containerName, currentCPU: .currentRequests.cpu, recommendedCPU: .recommendedRequests.cpu}'
```

## Под капотом

Kubecost сопоставляет метрики потребления `container_cpu_usage_seconds_total` и резерваций `kube_pod_container_resource_requests` из Prometheus с прайс-листами Cloud Provider Billing API (AWS, GCP, Azure) или локальными тарифами. Алгоритм вычисляет стоимость как максимум между фактическим потреблением и запросом: \(\text{Cost} = \max(\text{Usage}, \text{Request}) \times \text{Price}\). Это стимулирует команды уменьшать завышенные `requests`.

## Подводные камни

1. Разработчики завышают requests в 10 раз «на всякий случай»: это блокирует планировщик K8s и заставляет Cluster Autoscaler поднимать дорогие лишние серверы.
2. Неучет расходов на Cross-AZ сетевой трафик: в распределенных кластерах пересылка трафика между зонами доступности может составлять до 30% счета за облако.

## На собеседовании

**Вопрос с собеседования:** «Почему в FinOps для Kubernetes стоимость пода рассчитывается на основе `requests`, а не только на основе реально потребленных ресурсов (usage)?»
**Ответ:** Потому что планировщик Kubernetes резервирует емкость узла под Pod строго на основе `requests`. Даже если Pod фактически потребляет 0.05 CPU, но запросил `requests: 2 CPU`, эти 2 ядра заблокированы и не могут быть отданы другим подам. Облачный провайдер выставляет счет за сервер целиком, поэтому стоимость простаивающих, но заблокированных ресурсов должна списываться на команду, запросившую этот объем.
