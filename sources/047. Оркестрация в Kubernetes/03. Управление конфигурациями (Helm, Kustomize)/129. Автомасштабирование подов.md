# Автомасштабирование подов: Metrics Server и HorizontalPodAutoscaler (HPA)

## Условие

**[Metrics Server & HPA]**: Установи Metrics Server в K8s. Настрой `HorizontalPodAutoscaler` для твоего Deployment: таргет CPU utilization = 70%. Сгенерируй нагрузку (busybox в K8s) и посмотри, как K8s автоскейлит поды с 1 до 5.

## Теория

**HorizontalPodAutoscaler (HPA)** автоматически регулирует количество реплик рабочей нагрузки (Deployment, StatefulSet) на основе наблюдаемой утилизации ресурсов:
1. **Metrics Server:**
   - Легковесный кластерный агент, собирающий метрики потребления CPU и RAM с каждого узла через Kubelet Summary API (`cAdvisor`).
   - Предоставляет метрики через агрегированный API: `metrics.k8s.io`.
2. **Алгоритм расчета масштабирования HPA:**
   $$\text{DesiredReplicas} = \left\lceil \text{CurrentReplicas} \times \frac{\text{CurrentMetricValue}}{\text{TargetMetricValue}} \right\rceil$$
   Например: если текущих реплик 1, текущая утилизация CPU составляет 140%, а целевая — 70%:
   $$\text{DesiredReplicas} = \lceil 1 \times (140 / 70) \rceil = 2 \text{ реплики}.$$
3. **Обязательное условие:** В спецификации контейнера ОБЯЗАНЫ быть заданы `resources.requests.cpu`, иначе HPA не сможет вычислить процент утилизации и перейдет в статус `<unknown>`!

## Решение по шагам

1. Установите Metrics Server в кластер (с флагом `--kubelet-insecure-tls` для тестовых сред).
2. Проверьте работоспособность метрик: `kubectl top nodes` и `kubectl top pods`.
3. Создайте манифест Deployment с запросом `cpu: 100m`.
4. Создайте манифест `HorizontalPodAutoscaler` с таргетом 70% CPU и диапазоном реплик от 1 до 5.
5. Запустите генератор нагрузки `hey` или `busybox wget` и наблюдайте за скейлингом реплик до 5.

## Код решения

**`hpa.yaml`**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-autoscaler
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: scalable-api
  minReplicas: 1
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300 # Окно охлаждения 5 минут для защиты от flapping
      policies:
        - type: Percent
          value: 50
          periodSeconds: 60
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scalable-api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: scalable-api
  template:
    metadata:
      labels:
        app: scalable-api
    spec:
      containers:
        - name: app
          image: vish/stress
          args: ["-cpus", "2"] # Нагружает процессор для демонстрации
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 128Mi
```

**`Терминал`**

```bash
# Установка Metrics Server
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Проверка доступности метрик
kubectl top pods

# Применение манифестов Deployment и HPA
kubectl apply -f deployment.yaml
kubectl apply -f hpa.yaml

# Наблюдение за автоматическим масштабированием
kubectl get hpa api-autoscaler -w
# NAME             REFERENCE                 TARGETS    MINPODS   MAXPODS   REPLICAS   AGE
# api-autoscaler   Deployment/scalable-api   150%/70%   1         5         1          15s
# api-autoscaler   Deployment/scalable-api   150%/70%   1         5         3          35s
# api-autoscaler   Deployment/scalable-api   72%/70%    1         5         5          65s
```

## Под капотом

Контроллер `horizontal-pod-autoscaler` внутри `kube-controller-manager` опрашивает `metrics.k8s.io` с периодом `--horizontal-pod-autoscaler-sync-period` (по умолчанию каждые 15 секунд). Он получает текущие значения CPU всех подов таргета, делит на сумму запросов `requests.cpu` и вычисляет средний процент. Если отклонение превышает допуск 10% (tolerance 0.1), контроллер отправляет вызов `Scale` в `scaleTargetRef`, изменяя поле `spec.replicas` объекта Deployment.

## Подводные камни

1. Забытый `resources.requests.cpu`: если поле не задано, метрика в выводе `kubectl get hpa` будет отображать `<unknown>/70%`, и HPA никогда не выполнит масштабирование.
2. Флаппинг (Flapping / Thrashing): если окно охлаждения `stabilizationWindowSeconds` слишком короткое (например, 10 сек), HPA будет резко увеличивать число подов при коротком спайке и сразу гасить их, создавая непрерывную турбулентность в кластере.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных HighLoad системах автомасштабирование по CPU считают недостаточным и настраивают KEDA (Kubernetes Event-driven Autoscaling)?»
**Ответ:** Метрика CPU является **запаздывающим индикатором (Lagging Indicator)**: процессор начинает греться только тогда, когда очередь запросов уже скопилась и задержка ответов (latency) деградировала. Инструменты вроде KEDA позволяют масштабировать сервисы по **опережающим индикаторам (Leading Indicators)**: длина очереди необработанных сообщений в Kafka/RabbitMQ (`kafka_consumergroup_lag`), количество активных HTTP-запросов в Envoy или метрики бизнес-транзакций, масштабируя поды ДО того, как система начнет захлебываться.
