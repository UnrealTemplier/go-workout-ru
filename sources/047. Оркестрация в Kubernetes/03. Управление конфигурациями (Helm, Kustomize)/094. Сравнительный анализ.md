# Сравнительный анализ: Helm vs Kustomize в современной индустрии

## Условие

Сравни **Helm vs Kustomize**: Helm — templating (Go templates), package management, releases. Kustomize — patching, no templating, native in kubectl. Покажи, когда что использовать (Helm for packaged apps, Kustomize for own manifests).

## Теория

В современной экосистеме Cloud Native и Kubernetes сосуществуют два основных подхода к управлению манифестами:
1. **Helm (Package Manager & Templating Engine):**
   - **Сильные стороны:** Мощная параметризация через шаблоны Go/Sprig, управление зависимостями (subcharts), версионирование релизов (`helm rollback`), хуки жизненного цикла (`pre-install`, `post-upgrade`), распространение через OCI/Helm-репозитории.
   - **Слабые стороны:** Сложность отладки вложенных шаблонов, YAML перестает быть валидным YAML до рендеринга, риск синтаксических ошибок в пробелах (`indent`).
   - **Ниша применения:** Стороннее ПО с открытым исходным кодом (Prometheus, Ingress-Nginx, Redis, Cert-Manager, Kafka).
2. **Kustomize (Overlay & Patching Engine):**
   - **Сильные стороны:** 100% чистый и валидный YAML, встроен в `kubectl` (`kubectl apply -k`), простота понимания диффов в Git, идеален для GitOps.
   - **Слабые стороны:** Нет параметризации строк «на лету» без создания новых файлов патчей, нет управления версиями релизов и встроенного отката.
   - **Ниша применения:** Собственные микросервисы компании с окружениями dev/stage/prod.
3. **Гибридный подход (Best Practice в BigTech):** Упаковка зависимостей через Helm, рендеринг через `helm template`, и последующее наложение корпоративных патчей безопасности через Kustomize.

2. Продемонстрируйте сценарий, в котором Helm рендерит стороннее приложение, а Kustomize модифицирует его под требования кластера.

## Код решения

**`comparison.md`**

```markdown
| Критерий | Helm | Kustomize |
| :--- | :--- | :--- |
| **Подход** | Шаблонизация (Go Templates) | Наложение патчей (Overlays) |
| **Синтаксис** | Jinja-подобный YAML с `{{ }}` | Чистый валидный YAML |
| **Установка** | Отдельная CLI-утилита `helm` | Встроен в `kubectl -k` |
| **История релизов** | Да (хранится в Secret кластера) | Нет (управляется через Git) |
| **Управление зависимостями** | Встроенное (`Chart.yaml`) | Отсутствует |
| **Идеальный Use Case** | Third-party софт (Ingress, Postgres) | Собственные микросервисы компании |
```

**`kustomization.yaml`**

```yaml
# Пример интеграции: Kustomize инфлейтит Helm-чарт и патчит его
apiVersion: kustomize.config.k8s.io/v1
kind: Kustomization

helmCharts:
  - name: ingress-nginx
    repo: https://kubernetes.github.io/ingress-nginx
    version: 4.8.3
    releaseName: my-ingress
    namespace: ingress-nginx

patches:
  - target:
      kind: Deployment
      name: my-ingress-ingress-nginx-controller
    patch: |-
      - op: add
        path: /spec/template/spec/priorityClassName
        value: system-cluster-critical
```

**`Терминал`**

```bash
# Рендеринг Helm-чарта и наложение патча безопасности Kustomize в едином пайплайне
kubectl kustomize --enable-helm . | kubectl apply -f -
```

## Под капотом

При выполнении `kubectl kustomize --enable-helm` Kustomize вызывает бинарник Helm в фоновом режиме для выполнения `helm template`. Полученный поток YAML-документов парсится в структуры данных DOM (Kyaml / kustomize engine). Затем применяются операции RFC 6902 (JSON Patch) или Strategic Merge Patch. На выходе получается единый валидный стрим манифестов, полностью соответствующий стандартам корпоративной безопасности.

## Подводные камни

1. Использование Helm для микросервиса с 2-мя манифестами: неоправданно усложняет проект десятком шаблонных файлов `_helpers.tpl` и `templates/` вместо простого `deployment.yaml`.
2. Попытка эмулировать шаблоны в Kustomize с помощью внешних утилит `envsubst` или `sed`: это ломает идеологию декларативности и GitOps, делая манифесты невоспроизводимыми.

## На собеседовании

**Вопрос с собеседования:** «Какой инструмент — Helm или Kustomize — вы выберете для организации CI/CD конвейера монорепозитория с 50 Go-микросервисами под управлением ArgoCD?»
**Ответ:** Для собственных микросервисов в связке с ArgoCD стандартом де-факто является **Kustomize**. Он позволяет хранить базовые манифесты в директории `base/`, а различия между стендами (dev/qa/staging/prod) описывать компактными файлами в `overlays/`. Разработчики видят честный YAML без шаблонов, ArgoCD нативно поддерживает Kustomize без генерации артефактов в репозиториях чартов, а аудит изменений через Git diff предельно прозрачен.
