# Graceful Shutdown на практике: обработка сигналов ОС и закрытие коннектов к БД

## Условие

**Graceful Shutdown в K8s**: Когда K8s решает убить под, он сначала шлет сигнал `SIGTERM`, ждет (по умолчанию 30с - `terminationGracePeriodSeconds`), а затем делает `SIGKILL`. Убедись, что твое приложение (из упр. 353) правильно ловит `SIGTERM`, завершает работу `http.Server` и закрывает коннекты к БД. *Проверь по логам кластера, что приложение завершается без ошибок.*

## Теория

Корректный Graceful Shutdown в Go под управлением Kubernetes требует строгого порядка освобождения ресурсов:
1. **Перехват сигналов ОС:**
   - Kubernetes при вытеснении пода посылает процессу с PID 1 сигнал `SIGTERM`.
   - Использование `signal.NotifyContext` связывает завершение корневого контекста с приходом `SIGINT` или `SIGTERM`.
2. **Фазы мягкой остановки:**
   - **Фаза 1: Остановка приема новых запросов.** Вызов `server.Shutdown(ctx)` немедленно закрывает слушающий TCP-сокет, но держит открытыми сокеты для активных соединений.
   - **Фаза 2: Ожидание текущих запросов.** Go ждет завершения обработчиков (handlers) активных HTTP/gRPC запросов до истечения переданного `shutdownCtx`.
   - **Фаза 3: Остановка фоновых воркеров.** Закрытие каналов или отмена контекстов фоновых горутин (очереди, консьюмеры Kafka).
   - **Фаза 4: Закрытие соединений с базами данных.** Вызов `db.Close()` для сброса буферов и корректного завершения сессий в PostgreSQL/Redis.
   - **Фаза 5: Выход из `main()` с кодом 0.**

## Решение по шагам

1. Напишите полноценный микросервис на Go с сервером и имитацией пула соединений с БД.
2. Используйте `signal.NotifyContext` для обработки `syscall.SIGTERM`.
3. Запустите фоновую обработку запроса длительностью 3 секунды.
4. Вызовите `server.Shutdown(shutdownCtx)` и затем `db.Close()`.
5. Запустите приложение в K8s, отправьте сигнал удаления `kubectl delete pod` и проверьте последовательность логов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"
)

type MockDBPool struct {
	mu     sync.Mutex
	closed bool
}

func (db *MockDBPool) Close() error {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.closed = true
	log.Println("[DB] Пул соединений с PostgreSQL успешно закрыт, транзакции зафиксированы.")
	return nil
}

func main() {
	db := &MockDBPool{}

	mux := http.NewServeMux()
	mux.HandleFunc("/order", func(w http.ResponseWriter, r *http.Request) {
		log.Println("[HTTP] Получен заказ. Начало обработки (3 сек)...")
		time.Sleep(3 * time.Second) // Имитация выполнения бизнес-транзакции
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("Заказ успешно сохранен в БД\n"))
		log.Println("[HTTP] Заказ успешно завершен.")
	})

	server := &http.Server{
		Addr:    ":8080",
		Handler: mux,
	}

	// Перехват системных сигналов SIGTERM и SIGINT
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	go func() {
		log.Println("[MAIN] Сервер запущен на :8080. Ожидание запросов...")
		if err := server.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatalf("[FATAL] Ошибка запуска сервера: %v", err)
		}
	}()

	// Блокировка главной горутины до прихода сигнала SIGTERM от K8s
	<-ctx.Done()
	log.Println("[MAIN] Получен сигнал SIGTERM от Kubernetes. Начинаем Graceful Shutdown...")

	// Выделяем 15 секунд на мягкое завершение текущих соединений
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()

	if err := server.Shutdown(shutdownCtx); err != nil {
		log.Printf("[ERROR] Принудительное закрытие HTTP-сервера по таймауту: %v", err)
	} else {
		log.Println("[MAIN] Все входящие HTTP-запросы успешно завершены.")
	}

	// Закрываем соединения с базой данных ПОСЛЕ завершения всех HTTP-хендлеров
	if err := db.Close(); err != nil {
		log.Printf("[ERROR] Ошибка при закрытии БД: %v", err)
	}

	log.Println("[MAIN] Процесс завершен корректно с кодом 0. Zero downtime обеспечен.")
}
```

## Под капотом

Метод `http.Server.Shutdown(ctx)` переводит внутренний флаг `inShutdown` в состояние 1, немедленно закрывает слушающий TCP-листенер (`l.Close()`), останавливает таймеры Keep-Alive и ожидает возврата из всех функций-обработчиков активных соединений с помощью `sync.WaitGroup`. Если время `ctx.Done()` наступает раньше, метод принудительно закрывает все сокеты клиентов, возвращая `context.DeadlineExceeded`.

## Подводные камни

1. Закрытие базы данных ДО вызова `server.Shutdown()`: если сначала закрыть БД, активные HTTP-хендлеры, обрабатывающие пользовательские запросы в этот момент, получат ошибку `sql: database is closed`, что приведет к сбою транзакций и 500 ошибкам клиентам.
2. Незакрытые фоновые горутины: горутины, пишущие в каналы без контекста, могут повиснуть и не дать процессу завершиться, что приведет к принудительному уничтожению пода через `SIGKILL`.

## На собеседовании

**Вопрос с собеседования:** «Почему вызов `db.Close()` необходимо выполнять строго ПОСЛЕ возврата из метода `server.Shutdown(ctx)`?»
**Ответ:** Во время выполнения `server.Shutdown(ctx)` HTTP-сервер перестает принимать новые соединения, но продолжает выполнять уже запущенные обработчики запросов (in-flight requests). Если закрыть пул соединений с базой данных раньше, все эти активные пользовательские запросы попытаются обратиться к уже закрытому пулу и упадут с паникой или ошибками. Только когда все запросы завершены, можно безопасно закрывать соединения с базой данных и очередями сообщений.
