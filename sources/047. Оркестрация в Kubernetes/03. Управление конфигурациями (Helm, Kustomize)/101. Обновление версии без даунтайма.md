# Обновление версии без даунтайма: Rolling Update и стратегия Rollout

## Условие

**Обновление версии (Rollout)**: Внеси изменение в код (например, поменяй текст ответа HTTP сервера). Собери и запушь образ с новым тегом (`v1.1.0`). Измени тег в `deployment.yaml` и сделай `kubectl apply`. K8s сделает *Rolling Update*: будет аккуратно гасить старые поды и поднимать новые без даунтайма (Zero Downtime).

## Теория

Стратегия **RollingUpdate** — механизм обновления в Kubernetes по умолчанию:
1. **Принцип работы:** Вместо одновременной остановки всех экземпляров приложения (стратегия `Recreate`), контроллер Deployment постепенно заменяет старые поды на новые.
2. **Параметры управления скоростью и емкостью:**
   - `maxSurge`: максимальное количество дополнительных Pod'ов сверх желаемого `replicas` во время обновления (число или процент, например `25%` или `1`).
   - `maxUnavailable`: максимальное количество недоступных Pod'ов во время процесса обновления (например, `0` или `25%`).
3. **Формула Zero Downtime:**
   Комбинация `maxUnavailable: 0` и `maxSurge: 1` (или `25%`) гарантирует, что кластер ВСЕГДА держит 100% требуемой емкости: сначала поднимается новый Pod, проходит readiness probe, становится `Ready`, включается в балансировку Service, и только затем старый Pod удаляется через graceful shutdown.

## Решение по шагам

1. Создайте первую версию Go-сервера `v1.0.0` и задеплойте ее через `deployment.yaml`.
2. Измените код Go-сервера на версию `v1.1.0` и пересоберите Docker-образ.
3. В `deployment.yaml` настройте параметры `rollingUpdate: maxSurge: 1, maxUnavailable: 0`.
4. Обновите образ: `kubectl set image deployment/web-server web=my-registry.io/web-server:v1.1.0`.
5. Отслеживайте плавное замещение подов командой `kubectl rollout status deployment/web-server`.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-server
  namespace: default
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: web-server
  template:
    metadata:
      labels:
        app: web-server
    spec:
      containers:
        - name: web
          image: my-registry.io/web-server:v1.1.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 3
            periodSeconds: 2
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

const AppVersion = "v1.1.0"

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Ответ от сервера. Текущая версия: %s\n", AppVersion)
	})

	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("OK"))
	})

	log.Printf("Сервер версии %s запущен на :8080", AppVersion)
	if err := http.ListenAndServe(":8080", nil); err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

**`Терминал`**

```bash
# Запуск мониторинга статуса выкатки новой версии
kubectl rollout status deployment/web-server

# Просмотр истории релизов
kubectl rollout history deployment/web-server

# Проверка того, что ни один запрос не завершился ошибкой во время выкатки
while true; do curl -s http://web-service/ | grep "Версия"; sleep 0.2; done
```

## Под капотом

Deployment управляет не подами напрямую, а объектами **ReplicaSet**. При обновлении шаблона спецификации пода (`template`) Deployment создает НОВЫЙ ReplicaSet для версии `v1.1.0`. `deployment-controller` увеличивает `replicas` нового ReplicaSet (до 1 при `maxSurge: 1`), ждет, пока Pod пройдет Readiness Probe, затем уменьшает `replicas` старого ReplicaSet с 4 до 3. Этот цикл повторяется, пока старый ReplicaSet не опустится до 0 реплик, а новый не достигнет 4.

## Подводные камни

1. Использование тега `latest`: если в манифесте указан `image: app:latest`, то при повторном `kubectl apply` хеш спецификации Pod не меняется, и контроллер вообще не инициирует Rolling Update! Всегда используйте уникальные версионные теги (`v1.1.0` или git commit sha).
2. Отсутствие Readiness Probe: K8s посчитает новый Pod готовым сразу после старта процесса (TCP сокет еще не слушает, кэши не загружены), переведет трафик на него и удалит старый рабочий Pod, что вызовет лавину 502/503 ошибок.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если в ходе Rolling Update новый Pod падает с ошибкой `CrashLoopBackOff`?»
**Ответ:** Процесс обновления автоматически замораживается. Контроллер не сможет перевести новый Pod в состояние `Ready`, поэтому не станет масштабировать новый ReplicaSet дальше и не будет удалять оставшиеся старые поды. Благодаря параметру `maxUnavailable: 0` старые поды продолжают полноценно обслуживать 100% пользовательского трафика без даунтайма.
