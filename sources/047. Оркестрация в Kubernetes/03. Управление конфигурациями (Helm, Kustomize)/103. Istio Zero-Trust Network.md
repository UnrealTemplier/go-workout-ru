# Istio Zero-Trust Network: взаимный TLS (mTLS) и PeerAuthentication

## Условие

Настрой **Istio mTLS**: `PeerAuthentication` with `mtls: mode: STRICT`. All service-to-service communication encrypted and authenticated. `DestinationRule` with `trafficPolicy: tls: mode: ISTIO_MUTUAL`. Покажи zero-trust network.

## Теория

Концепция **Zero Trust Architecture** гласит: «Никому не доверяй, всегда проверяй». Внутренняя сеть кластера считается потенциально враждебной.
**Реализация mTLS в Istio:**
1. **Шифрование и аутентификация:** При каждом TCP-соединении между подами прокси-серверы Envoy выполняют взаимный TLS-хэндшейк (Mutual TLS). И клиент, и сервер предъявляют X.509-сертификаты.
2. **Идентификация SPIFFE:** Сертификат содержит SAN (Subject Alternative Name) формата `spiffe://cluster.local/ns/<namespace>/sa/<serviceaccount>`.
3. **Режимы `PeerAuthentication`:**
   - `PERMISSIVE` (по умолчанию) — принимает как зашифрованный mTLS трафик, так и обычный открытый HTTP/TCP (удобно для плавной миграции).
   - `STRICT` — требует ИСКЛЮЧИТЕЛЬНО mTLS. Любой запрос без валидного клиентского сертификата от Envoy немедленно сбрасывается.
   - `DISABLE` — mTLS отключен.
4. **`DestinationRule`:** на стороне клиента указывает Envoy отправлять трафик строго в режиме `ISTIO_MUTUAL`.

## Решение по шагам

1. Создайте манифест `PeerAuthentication` в режиме `STRICT` для namespace `secure-zone`.
2. Создайте `DestinationRule` с политикой `ISTIO_MUTUAL`.
3. Задеплойте два микросервиса (клиент и сервер) с автоматической инъекцией Envoy.
4. Проверьте через `istioctl authn tls-check`, что между подами включен mTLS.
5. Отправьте запрос из обычного пода без sidecar: запрос должен быть отклонен.

## Код решения

**`peer-auth.yaml`**

```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default-strict-mtls
  namespace: secure-zone
spec:
  mtls:
    mode: STRICT
```

**`destination-rule.yaml`**

```yaml
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: internal-mtls
  namespace: secure-zone
spec:
  host: "*.secure-zone.svc.cluster.local"
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL
```

**`Терминал`**

```bash
# Применение строгой политики Zero-Trust mTLS
kubectl apply -f peer-auth.yaml
kubectl apply -f destination-rule.yaml

# Проверка статуса mTLS шифрования между сервисами
istioctl proxy-config endpoint app-client-pod.secure-zone | grep "app-server"

# Попытка запроса из пода без Envoy sidecar вернет ошибку разрыва соединения
kubectl run unsecure-test --image=curlimages/curl --rm -it -- curl -k http://app-server.secure-zone:8080/
# curl: (56) Recv failure: Connection reset by peer
```

## Под капотом

Агент `pilot-agent`, работающий в sidecar-контейнере `istio-proxy`, генерирует приватный ключ RSA/ECDSA и запрос CSR (Certificate Signing Request). Через защищенный сокет Envoy Secret Discovery Service (SDS) запрос отправляется в `istiod` (выступающий в роли CA — Certificate Authority). `istiod` выпускает краткосрочный X.509-сертификат (по умолчанию действует 24 часа) и возвращает его в Envoy. Сертификаты автоматически ротируются в памяти каждые 12 часов без перезапуска контейнера и сброса TCP-соединений.

## Подводные камни

1. Включение `mode: STRICT` до внедрения Envoy во все взаимодействующие поды: поды без sidecar мгновенно потеряют связь с сервисами в данном namespace.
2. Проблемы с Liveness/Readiness пробами K8s: Kubelet выполняет проверки с хоста без сертификата Envoy. В Istio по умолчанию включен rewrite probe (`probe rewrite`), проксирующий запросы kubelet через специальный локальный порт Envoy.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие `tls: mode: MUTUAL` от `tls: mode: ISTIO_MUTUAL` в `DestinationRule`?»
**Ответ:** `mode: MUTUAL` требует ручного указания путей к файлам клиентского сертификата, закрытого ключа и CA-сертификата (`clientCertificate`, `privateKey`, `caCertificates`). Режим `mode: ISTIO_MUTUAL` сообщает Envoy использовать встроенную инфраструктуру открытых ключей Istio (SPIFFE/SDS): ключи и сертификаты автоматически запрашиваются у `istiod`, ротируются каждые сутки и связываются с ServiceAccount пода без ручного управления секретами.
