# Runtime-безопасность ядра: Falco, eBPF и детекция аномалий

## Условие

Настрой **Falco**: runtime security. Rules: `Unexpected outbound connection`, `Write to /etc`, `Privilege escalation`. Alerts to Slack/PagerDuty. Покажи threat detection.

## Теория

Традиционные сканеры образов (Trivy, Grype) и статический анализ (SAST) защищают кластер ДО запуска (Shift Left). Однако уязвимости нулевого дня (Zero-Day), компрометация учетных данных или инъекции атак происходят в рантайме.
**Falco (CNCF Graduated)** — стандарт де-факто для обнаружения угроз во время выполнения (Runtime Threat Detection):
1. **Принцип работы:** Falco перехватывает системные вызовы ядра Linux (через eBPF-программу или модуль ядра), обогащает их метаданными Kubernetes (pod_name, namespace, container_image) и сверяет с правилами безопасности.
2. **Типичные детекции:**
   - Попытка записи в системные каталоги (`/etc`, `/bin`, `/usr`).
   - Запуск shell (`sh`, `bash`) внутри рабочего контейнера.
   - Попытка повышения привилегий (`setuid`).
   - Неожиданные исходящие сетевые соединения к подозрительным IP/портам (ботнеты, майнинг криптовалюты).
3. **Интеграция с алертами:** Через `falcosidekick` события передаются в Slack, SIEM (Splunk, Elastic) или PagerDuty.

## Решение по шагам

1. Установите Falco в кластер через официальный Helm-чарт с драйвером `modern-ebpf`.
2. Создайте кастомный файл правил `falco-custom-rules.yaml` для обнаружения записи в `/etc` и неожиданных исходящих коннектов.
3. Разверните тестовый контейнер и выполните команду `touch /etc/malicious_file`.
4. Просмотрите системный журнал Falco и убедитесь в генерации алерта уровня `WARNING/CRITICAL`.

## Код решения

**`falco-custom-rules.yaml`**

```yaml
customRules:
  rules-production.yaml: |-
    - rule: Write below etc in Container
      desc: Обнаружение попытки модификации системных конфигураций в /etc
      condition: >
        open_write and container and
        fd.name startswith /etc and
        not proc.name in (dpkg, apt, yum, apk)
      output: >
        ВНИМАНИЕ: Подозрительная запись в /etc внутри контейнера
        (user=%user.name command=%proc.cmdline file=%fd.name pod=%k8s.pod.name ns=%k8s.ns.name)
      priority: WARNING
      tags: [filesystem, mitre_persistence]

    - rule: Unexpected Outbound Network Connection
      desc: Обнаружение исходящего TCP соединения на нестандартный порт
      condition: >
        outbound and container and
        not fd.sport in (80, 443, 5432, 6379, 9092) and
        not k8s.ns.name in (kube-system, istio-system)
      output: >
        ТРЕВОГА: Неавторизованное исходящее сетевое соединение
        (command=%proc.cmdline connection=%fd.name pod=%k8s.pod.name ns=%k8s.ns.name)
      priority: CRITICAL
      tags: [network, mitre_exfiltration]
```

## Под капотом

Falco компилирует свои правила в ассемблер BPF. При возникновении системного вызова `openat()` ядро Linux исполняет eBPF-программу Falco в контексте ядра без переключения контекста в user-space (overhead < 1-2% CPU). eBPF-зонд считывает аргументы вызова (флаги `O_WRONLY | O_CREAT`, путь `/etc/...`), извлекает PID процесса, cgroup ID и через кольцевой буфер (ring buffer) передает событие демону Falco. Демон по cgroup находит соответствующий Pod и генерирует JSON-алерт.

## Подводные камни

1. Использование устаревшего модуля ядра (Kernel Module) вместо `modern-ebpf`: модуль ядра требует сборки под точную версию Linux kernel ноды, что ломается при обновлении ОС хоста. eBPF с поддержкой CO-RE (Compile Once – Run Everywhere) работает универсально.
2. Алерт-фатиг (Alert Fatigue): слишком широкие правила без исключений для легитимных пакетных менеджеров вызовут тысячи ложных срабатываний в день.

## На собеседовании

**Вопрос с собеседования:** «Чем архитектурно подход Falco на базе eBPF отличается от классических антивирусов и WAF?»
**Ответ:** WAF работает только на L7 HTTP-уровне и не видит, что происходит внутри операционной системы контейнера после обработки запроса. Классические антивирусы сканируют файлы на диске по сигнатурам и слишком медлительны для эфемерных контейнеров. Falco на базе eBPF перехватывает системные вызовы ядра Linux в режиме реального времени, видит абсолютно все процессы, сетевые сокеты и файловые операции на микросекундном уровне, делая невозможным скрытие вредоносной активности внутри контейнера.
