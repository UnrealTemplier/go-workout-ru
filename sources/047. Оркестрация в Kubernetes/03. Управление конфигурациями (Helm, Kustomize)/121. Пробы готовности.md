# Пробы готовности: защита от трафика во время старта через Readiness Probe

## Условие

**Пробы готовности (Readiness Probe)**: Твое приложение стартует 5 секунд (подключается к БД, греет кэш). В это время ему нельзя слать трафик. Добавь `readinessProbe`. K8s не пустит пользовательский трафик в под (он не добавится в endpoints Service), пока эта проба не вернет 200 OK.

## Теория

При старте Go-приложению часто требуется время на разогрев:
- Установка соединений с пулом PostgreSQL и Redis.
- Загрузка справочников и локальных кэшей в оперативную память.
- Чтение криптографических ключей.
Если отправить входящий трафик в приложение до завершения инициализации, клиенты получат ошибки `500 Internal Server Error` или `Connection Refused`.
**Readiness Probe в Kubernetes:**
1. Демон `kubelet` периодически опрашивает настроенный эндпоинт (`/readyz`).
2. Пока проба возвращает статус ошибки (или сетевой таймаут), статус пода в поле `Ready` остается `False`.
3. Контроллер `endpoint-controller` **НЕ добавляет IP-адрес пода в объект Endpoints / EndpointSlice сервиса**.
4. Балансировщик Service и Ingress направляют трафик исключительно на поды со статусом `Ready: True`.
5. Если в процессе работы зависимость отвалилась (например, упала БД), Readiness Probe возвращает ошибку, и K8s временно снимает трафик с пода БЕЗ его перезапуска!

## Решение по шагам

1. Напишите Go-сервис, в котором процедура инициализации занимает 5 секунд.
2. Реализуйте эндпоинт `/readyz`, возвращающий HTTP 503 до завершения инициализации и 200 OK после.
3. В `deployment.yaml` сконфигурируйте `readinessProbe` с `initialDelaySeconds: 2`, `periodSeconds: 2`.
4. Задеплойте приложение и отследите через `kubectl get pods -w`, как колонка `READY` переходит из `0/1` в `1/1` ровно через 5 секунд.
5. Убедитесь через `kubectl get endpoints`, что IP пода появился в сервисе только после готовности.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"sync/atomic"
	"time"
)

func main() {
	var isReady int32 = 0 // 0 - не готов, 1 - готов

	// Имитация долгой асинхронной инициализации (прогрев кэша, подключение к БД)
	go func() {
		log.Println("Начало прогрева кэша и инициализации пула соединений...")
		time.Sleep(5 * time.Second)
		atomic.StoreInt32(&isReady, 1)
		log.Println("Инициализация завершена. Сервис готов принимать клиентский трафик!")
	}()

	mux := http.NewServeMux()

	// Readiness probe: вызывается Kubelet каждые несколько секунд
	mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
		if atomic.LoadInt32(&isReady) == 0 {
			http.Error(w, "Сервис прогревается, подождите...", http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})

	// Бизнес-эндпоинт
	mux.HandleFunc("/api/data", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("Бизнес-ответ от прогретого сервиса\n"))
	})

	server := &http.Server{Addr: ":8080", Handler: mux}
	log.Println("HTTP сервер слушает на :8080")
	if err := server.ListenAndServe(); err != nil {
		log.Fatalf("Ошибка сервера: %v", err)
	}
}
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: warm-up-app
  namespace: default
spec:
  replicas: 2
  selector:
    matchLabels:
      app: warm-up-app
  template:
    metadata:
      labels:
        app: warm-up-app
    spec:
      containers:
        - name: app
          image: warm-up-app:v1.0.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 2
            failureThreshold: 2
```

**`Терминал`**

```bash
# Применение манифеста в кластер
kubectl apply -f deployment.yaml

# Наблюдение за переходом подов в Ready (в течение первых 5 сек READY будет 0/1)
kubectl get pods -l app=warm-up-app -w
# NAME                           READY   STATUS    RESTARTS   AGE
# warm-up-app-7d498c8694-k98sd   0/1     Running   0          3s
# warm-up-app-7d498c8694-k98sd   1/1     Running   0          6s

# Проверка списка активных эндпоинтов сервиса
kubectl get endpoints warm-up-service
```

## Под капотом

`kubelet` выполняет HTTP GET запрос к сокету контейнера. Код ответа от 200 до 399 переводит пробу в статус `Success`. Состояние записывается в `PodStatus.Conditions` (тип `Ready = True`). `endpoint-controller`, подписанный на события изменения подов через Watch API, считывает условие `Ready: True` и включает IP-адрес пода в список `subsets.addresses` ресурса `Endpoints`. `kube-proxy` на нодах мгновенно добавляет IP в правила маршрутизации iptables/IPVS.

## Подводные камни

1. Запуск стресс-тестов или деплоя без Readiness Probe: при Rolling Update старые поды начнут гаситься сразу же, как только новые запустились в статусе `Running`, но до того, как они реально смогли отвечать на запросы, что приведет к 100% даунтайму на 5 секунд.
2. Проверка тяжелых запросов в Readiness Probe: выполнение `SELECT COUNT(*) FROM huge_table` каждые 2 секунды перегрузит базу данных при росте числа подов.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет с подом, если его Readiness Probe вернет код 503 Service Unavailable?»
**Ответ:** Pod НЕ будет перезапущен или убит! Контроллер Kubernetes просто исключит IP-адрес этого пода из балансировки `Endpoints` сервиса, и на него перестанет поступать клиентский трафик. Контейнер продолжит работать. Как только проба снова вернет 200 OK, IP-адрес автоматически вернется в балансировку. Это кардинально отличает Readiness Probe от Liveness Probe, которая при сбое принудительно убивает контейнер.
