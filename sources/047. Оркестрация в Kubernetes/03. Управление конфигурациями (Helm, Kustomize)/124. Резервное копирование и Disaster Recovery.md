# Резервное копирование и Disaster Recovery: Velero и CSI-снапшоты

## Условие

Настрой **Velero**: backup and restore. `Backup` resource: cluster state + PV snapshots. `Schedule` for automated backups. Disaster recovery: restore to new cluster. Покажи DR testing.

## Теория

Для защиты от потери данных, случайного удаления namespace инженером или катастрофического сбоя дата-центра требуется стратегия **Disaster Recovery (DR)**.
**Velero (ранее Heptio Ark)** — решение резервного копирования для Kubernetes:
1. **Что бэкапит Velero:**
   - **Состояние кластера (etcd metadata):** YAML-манифесты всех объектов (Deployments, Services, Secrets, CRDs, RBAC) упаковываются в архив `.tar.gz` и сохраняются в объектное хранилище S3 (AWS S3, MinIO, Ceph).
   - **Постоянные данные (PV):** Создает снапшоты дисков на уровне блочных устройств через **CSI VolumeSnapshot** API облачного провайдера или файловый бэкап через Restic/Kopia.
2. **Ключевые примитивы CRD:**
   - `Backup`: разовая задача создания резервной копии.
   - `Schedule`: расписание периодического создания бэкапов (cron).
   - `Restore`: процедура восстановления объектов и томов из выбранного бэкапа в исходный или новый аварийный кластер.

## Решение по шагам

1. Установите CLI Velero и разверните серверную часть с подключением к S3 бакету.
2. Создайте расписание `Schedule` для еженощного бэкапа production namespace.
3. Выполните ручной бэкап `velero backup create prod-backup --include-namespaces production`.
4. Сымитируйте катастрофу: удалите тестовый namespace `kubectl delete ns production`.
5. Выполните восстановление: `velero restore create --from-backup prod-backup` и проверьте поднявшиеся сервисы.

## Код решения

**`schedule.yaml`**

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: nightly-prod-backup
  namespace: velero
spec:
  schedule: "0 1 * * *" # Каждую ночь в 01:00 UTC
  template:
    includedNamespaces:
      - production
    snapshotVolumes: true
    ttl: 720h # Хранить бэкапы ровно 30 дней
```

**`backup-storage-location.yaml`**

```yaml
apiVersion: velero.io/v1
kind: BackupStorageLocation
metadata:
  name: s3-primary
  namespace: velero
spec:
  provider: aws
  objectStorage:
    bucket: my-company-k8s-backups
  config:
    region: ru-central1
    s3Url: https://storage.yandexcloud.net
```

**`Терминал`**

```bash
# Создание немедленного ручного бэкапа перед критическим релизом
velero backup create pre-release-backup --include-namespaces production --wait

# Просмотр деталей и статуса выполнения бэкапа
velero backup describe pre-release-backup

# Эмуляция катастрофы (случайное удаление прод окружения)
kubectl delete ns production

# Восстановление кластера из сохраненного бэкапа в объектном хранилище
velero restore create dr-restore --from-backup pre-release-backup --wait

# Проверка статуса восстановления
velero restore describe dr-restore
# Phase: Completed (0 errors, 0 warnings)
```

## Под капотом

Сервер Velero запрашивает у `kube-apiserver` список всех ресурсов выбранных namespace, фильтрует эфемерные объекты и упаковывает JSON-манифесты в tar-архив. Для каждого PersistentVolumeClaim Velero вызывает CSI-драйвер через `VolumeSnapshot` CRD, инициируя снапшот диска в Cloud Storage API. Сформированный архив и журнал передаются по HTTPS в S3-бакет. При восстановлении Velero считывает манифесты из S3, восстанавливает диски из снапшотов и воссоздает ресурсы в строгой топологической последовательности.

## Подводные камни

1. Транзакционная несогласованность данных БД: снятие снапшота работающей СУБД (PostgreSQL) без предварительной заморозки (`fsfreeze` / `pg_start_backup()`) может привести к повреждению таблиц. Для баз данных рекомендуется использовать `velero.io/backup-hook-pre` или специализированные бэкаперы СУБД (pgBackRest).
2. Забытые секреты шифрования KMS: если восстановить снапшот зашифрованного диска в другой регион или аккаунт, где нет доступа к оригинальному ключу KMS, диск не сможет расшифроваться.

## На собеседовании

**Вопрос с собеседования:** «Как протестировать Disaster Recovery план для кластера Kubernetes, не нарушая работу работающего продакшена?»
**Ответ:** Разворачивается отдельный тестовый (staging/sandbox) кластер в другом дата-центре или облачном аккаунте. В нем настраивается Velero с доступом к production S3-бакету в режиме Read-Only (`accessMode: ReadOnly`). Запускается процедура `velero restore create dr-test --from-backup latest-prod-backup`. После завершения восстановления автоматические интеграционные тесты проверяют целостность данных и работоспособность микросервисов, подтверждая соблюдение метрик RPO (Recovery Point Objective) и RTO (Recovery Time Objective).
