# Откат развертывания: kubectl rollout undo и ревизии ReplicaSet

## Условие

**Откат (Rollback)**: Ты понял, что версия `v1.1.0` с багом. Выполни команду `kubectl rollout undo deployment/my-app`. Кластер автоматически вернет старую рабочую версию приложения.

**Откат (Rollback)**: Ты понял, что версия `v1.1.0` с багом. Выполни команду `kubectl rollout undo deployment/my-app`. Кластер автоматически вернет старую рабочую версию приложения.

## Теория

Откат развертывания — критически важная аварийная процедура при обнаружении багов в production:
1. **Концепция ревизий:**
   - Каждый раз, когда изменяется `spec.template` в объекте Deployment, Kubernetes создает новую **ревизию (Revision)**.
   - История ревизий сохраняется благодаря сохранению старых объектов **ReplicaSet** с масштабом `replicas: 0`.
2. **Команда `kubectl rollout undo`:**
   - `kubectl rollout undo deployment/<name>` — откат к предыдущей успешной ревизии (N-1).
   - `kubectl rollout undo deployment/<name> --to-revision=2` — откат к конкретной исторической ревизии номер 2.
3. **Параметр `revisionHistoryLimit`:**
   - По умолчанию K8s сохраняет 10 последних ReplicaSet. Если этот параметр установлен в 0, история не сохраняется, и откат через `rollout undo` становится невозможным!

## Решение по шагам

1. Проверьте текущую историю выкаток: `kubectl rollout history deployment/my-app`.
2. Посмотрите детали конкретной ревизии: `kubectl rollout history deployment/my-app --revision=1`.
3. Выполните команду отката: `kubectl rollout undo deployment/my-app`.
4. Отследите завершение отката: `kubectl rollout status deployment/my-app`.
5. Убедитесь, что поды перешли на стабильный образ предыдущей версии.

## Код решения

**`Терминал`**

```bash
# Просмотр истории релизов с номерами ревизий и аннотациями изменений
kubectl rollout history deployment/my-app

# Детальный просмотр ревизии 1 (какой образ использовался)
kubectl rollout history deployment/my-app --revision=1

# Откат к предыдущей стабильной ревизии
kubectl rollout undo deployment/my-app

# Откат к конкретной исторической ревизии 2
kubectl rollout undo deployment/my-app --to-revision=2

# Проверка успешного завершения отката
kubectl rollout status deployment/my-app
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: default
  annotations:
    kubernetes.io/change-cause: "Release v1.0.0 stable with memory leak fix"
spec:
  revisionHistoryLimit: 10
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: app
          image: my-app:v1.0.0
          ports:
            - containerPort: 8080
```

## Под капотом

При вызове `rollout undo` контроллер `deployment-controller` находит исторический ReplicaSet, соответствующий целевой ревизии. Контроллер копирует спецификацию `spec.template` из этого ReplicaSet обратно в `spec.template` объекта Deployment и увеличивает счетчик ревизий (например, если текущая была 3, а откат делается к 1, создается ревизия 4 с шаблоном из 1). Запускается стандартный процесс Rolling Update в обратную сторону: старый дефектный ReplicaSet масштабируется до 0, а проверенный масштабируется до требуемого количества реплик.

## Подводные камни

1. Установка `revisionHistoryLimit: 0`: приводит к немедленному удалению неактивных ReplicaSet, делая команду `kubectl rollout undo` бесполезной.
2. Несовместимость базы данных: если дефектная версия `v1.1.0` успела применить деструктивную миграцию схемы БД (например, удалила колонку), откат бинарника через `rollout undo` не восстановит базу данных и может привести к полному падению сервиса. Миграции БД всегда должны быть обратно совместимыми.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных процессах GitOps (ArgoCD, Flux) команду `kubectl rollout undo` считают временным антипаттерном или экстренной мерой?»
**Ответ:** Команда `kubectl rollout undo` изменяет состояние кластера напрямую в обход Git. Если в Git-репозитории остался закоммичен манифест с дефектным образом `v1.1.0`, GitOps-контроллер (ArgoCD) через несколько минут обнаружит дрифт (Out-of-Sync), автоматически применит манифест из Git и вернет багованную версию обратно в кластер! В правильном GitOps-процессе откат выполняется через `git revert` коммита в Git.
