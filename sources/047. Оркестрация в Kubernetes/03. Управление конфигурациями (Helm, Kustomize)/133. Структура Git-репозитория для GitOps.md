# Структура Git-репозитория для GitOps: разделение кода приложения и манифестов

## Условие

Создайте Git репозиторий с Kubernetes манифестами (или Helm chart) вашего приложения.

## Теория

Один из фундаментальных принципов GitOps — **разделение репозитория исходного кода приложения и репозитория конфигураций развертывания**:
1. **Почему монолитный репозиторий (App Code + K8s manifests) плох для GitOps:**
   - Изменение кода приложения вызывает запуск CI-тестов и сборку Docker-образа.
   - Если CI-пайплайн коммитит новый тег образа в тот же репозиторий, это может вызвать бесконечный цикл триггеров CI/CD.
   - Права доступа: разработчикам нужен доступ на запись в код, но доступ к манифестам production-окружения должен быть строго ограничен.
2. **Архитектура двух репозиториев:**
   - **`app-repo` (Репозиторий приложения):** содержит Go-код, unit-тесты, `Dockerfile`, CI-пайплайн сборки образов. По окончании сборки CI обновляет тег в config-repo через Pull Request или автоматический коммит.
   - **`infra-gitops-repo` (Репозиторий инфраструктуры):** содержит Helm-чарты или Kustomize манифесты, структурированные по окружениям (`dev`, `staging`, `prod`). С этим репозиторием работает только ArgoCD.

## Решение по шагам

1. Создайте структуру директорий для GitOps-репозитория конфигураций.
2. Организуйте разделение по окружениям через Kustomize.
3. Настройте скрипт CI в репозитории приложения, обновляющий тег образа в GitOps-репозитории.
4. Проверьте фиксацию истории изменений образов в Git.

## Код решения

**`gitops-repo-structure.txt`**

```bash
k8s-gitops-manifests/
├── apps/
│   ├── auth-service/
│   │   ├── base/
│   │   │   ├── deployment.yaml
│   │   │   ├── service.yaml
│   │   │   └── kustomization.yaml
│   │   └── overlays/
│   │       ├── dev/
│   │       │   └── kustomization.yaml
│   │       ├── staging/
│   │       │   └── kustomization.yaml
│   │       └── prod/
│   │           └── kustomization.yaml
│   └── billing-service/
└── infrastructure/
    ├── ingress-nginx/
    └── cert-manager/
```

**`ci-update-gitops.sh`**

```bash
#!/bin/bash
set -euo pipefail

NEW_TAG="$1"
GITOPS_REPO="https://ci-bot:${GIT_TOKEN}@github.com/my-corp/k8s-gitops-manifests.git"

echo "1. Клонирование GitOps репозитория конфигураций..."
git clone "$GITOPS_REPO" /tmp/gitops-repo
cd /tmp/gitops-repo/apps/auth-service/overlays/dev

echo "2. Обновление тега образа на $NEW_TAG через Kustomize..."
kustomize edit set image auth-service=myregistry.io/auth-service:"$NEW_TAG"

echo "3. Фиксация изменений и коммит в Git..."
git config user.name "CI-Automation-Bot"
git config user.email "bot@company.internal"
git add kustomization.yaml
git commit -m "Auto-deploy: update auth-service image to $NEW_TAG [skip ci]"
git push origin main

echo "✅ GitOps репозиторий успешно обновлен. ArgoCD запустит деплой." 
```

## Под капотом

Когда CI-скрипт пушит коммит в ветку `main` репозитория `k8s-gitops-manifests`, GitHub/GitLab отправляет Webhook в `argocd-server`. ArgoCD сбрасывает локальный кэш репозитория, запускает `kustomize build apps/auth-service/overlays/dev`, обнаруживает расхождение между желаемым образом в Git (`auth-service:v2.1.0`) и текущим образом в кластере (`auth-service:v2.0.9`) и инициирует Rolling Update.

## Подводные камни

1. Зацикливание CI конвейера: если коммит в GitOps репозиторий запускает тот же пайплайн тестирования Go-кода, конвейер уйдет в вечный цикл. Обязательно используйте маркеры вроде `[skip ci]`.
2. Прямые коммиты в production без Pull Request: в продакшен-оверлеи изменения должны попадать только через Pull Request с обязательным аппрувом лида команды.

## На собеседовании

**Вопрос с собеседования:** «Почему в GitOps разделение репозитория кода приложения и репозитория манифестов является признанным отраслевым стандартом?»
**Ответ:** 1) **Разделение полномочий (RBAC):** Разработчики имеют права на коммит в репозиторий кода, но не могут бесконтрольно менять лимиты памяти, права ServiceAccount или переменные боевого окружения в репозитории манифестов; 2) **Чистая история релизов:** В репозитории манифестов каждый коммит означает реальное развертывание версии в кластер, что делает аудит изменений и откат (`git revert`) тривиальными; 3) **Исключение рекурсивных триггеров CI/CD**.
