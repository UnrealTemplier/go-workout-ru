# Маршрутизация внешнего трафика: Ingress Controller и Ingress-ресурсы

## Условие

Установите ingress-контроллер (nginx) и настройте Ingress-ресурс для маршрутизации внешнего трафика к вашему сервису.

## Теория

Объект **Service** типа `LoadBalancer` создает отдельный внешний облачный балансировщик для каждого сервиса, что дорого и неэффективно при десятках микросервисов. **Ingress** предоставляет L7 (HTTP/HTTPS) точку входа в кластер:
1. **Ingress Controller:** активный демон (обычно NGINX, Traefik, HAProxy или Envoy), который слушает порты 80/443, мониторит объекты Ingress через API кластера и динамически переконфигурирует свои правила проксирования.
2. **Ingress Resource:** манифест, объявляющий правила маршрутизации:
   - `rules.host`: доменное имя (виртуальный хост, например `api.company.com`).
   - `http.paths`: пути URL (path-based routing, например `/users` -> `user-service`, `/orders` -> `order-service`).
   - `pathType`:
     - `Exact` — точное совпадение пути URL.
     - `Prefix` — совпадение по префиксу пути (разделенному слешами `/`).
3. **Аннотации (Annotations):** специфичные настройки контроллера (`nginx.ingress.kubernetes.io/rewrite-target`, CORS, rate-limiting, SSL redirect).

## Решение по шагам

1. Установите Ingress NGINX Controller через официальный манифест.
2. Разверните Go-микросервис и ClusterIP Service для него.
3. Создайте манифест `ingress.yaml` с правилом для хоста `demo.local` и префикса `/`.
4. Добавьте запись `127.0.0.1 demo.local` в локальный файл `/etc/hosts`.
5. Отправьте HTTP-запрос через `curl -i http://demo.local` и проверьте ответ.

## Код решения

**`ingress.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "false"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
spec:
  ingressClassName: nginx
  rules:
    - host: demo.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 8080
```

**`service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-service
  namespace: default
spec:
  selector:
    app: web-app
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 8080
```

**`Терминал`**

```bash
# Установка Ingress NGINX контроллера
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.8.2/deploy/static/provider/cloud/deploy.yaml

# Ожидание готовности контроллера
kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller \
  --timeout=90s

# Применение манифеста Ingress
kubectl apply -f ingress.yaml

# Тестовый запрос к сервису через виртуальный хост
curl -H "Host: demo.local" http://localhost/
```

## Под капотом

Ingress Controller не использует сетевую цепочку `kube-proxy` и `ClusterIP` напрямую. NGINX Ingress Controller через API-сервер подписывается на события `Endpoints` (или `EndpointSlice`). Когда поды сервиса `web-service` запускаются, контроллер получает их прямые IP-адреса и динамически генерирует upstream-блоки внутри `nginx.conf` (или использует Lua-модуль OpenResty для балансировки без перезагрузки процесса NGINX). Трафик направляется напрямую в Pod, минуя лишний NAT в iptables.

## Подводные камни

1. Забытый `ingressClassName: nginx`: в кластерах с несколькими контроллерами (или в K8s 1.19+) отсутствие класса приведет к тому, что ни один контроллер не возьмет Ingress в обработку.
2. Несоответствие `pathType: Prefix`: путь `/app` с `Prefix` матчит `/app/settings`, но не матчит `/application`. Понимание семантики pathType критично для избежания утечек трафика в неверные сервисы.

## На собеседовании

**Вопрос с собеседования:** «Почему NGINX Ingress Controller по умолчанию отправляет трафик напрямую на IP-адреса Pod'ов, а не на виртуальный IP-адрес (ClusterIP) сервиса?»
**Ответ:** Это оптимизация производительности и расширенных возможностей балансировки: 1) Исключается двойная трансляция адресов (DNAT) в `kube-proxy` (iptables/ipvs); 2) NGINX получает возможность использовать сложные алгоритмы балансировки (least_conn, ewma, ip_hash), сохранять постоянные сессии (sticky sessions через cookies) и осуществлять gRPC/WebSocket мультиплексирование на уровне L7.
