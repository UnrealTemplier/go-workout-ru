# Миграция с Helm на Kustomize: структура Base и окружения Dev/Prod

## Условие

**[Kustomize]**: Перепиши деплой с Helm на Kustomize. Создай `base/` с манифестами и два оверлея: `overlays/dev` (1 replica, ConfigMap для dev) и `overlays/prod` (3 replicas, ингресс, prod secrets). Запусти `kubectl apply -k overlays/prod`.

## Теория

Переход от шаблонизации Helm к оверлеям Kustomize устраняет сложность синтаксиса шаблонов и делает конфигурации 100% декларативными:
1. **Базовый слой (`base/`):**
   - Содержит минимальные, канонические манифесты приложения: `deployment.yaml`, `service.yaml`, `kustomization.yaml`.
2. **Слой разработки (`overlays/dev/`):**
   - Наследует `../../base`.
   - Добавляет суффикс `-dev` или namespace `dev`.
   - Устанавливает 1 реплику и подключает ConfigMap с тестовыми эндпоинтами.
3. **Слой продакшена (`overlays/prod/`):**
   - Наследует `../../base`.
   - Патчит `replicas: 3`.
   - Подключает манифест `ingress.yaml` с боевым доменом и TLS.
   - Использует `secretGenerator` для подтягивания продакшен-секретов.

## Решение по шагам

1. Создайте структуру каталогов: `base/`, `overlays/dev/`, `overlays/prod/`.
2. Напишите базовые манифесты в директории `base/`.
3. Опишите патчи для окружения `overlays/dev/`.
4. Опишите патчи и Ingress для окружения `overlays/prod/`.
5. Проверьте манифесты через `kubectl kustomize overlays/prod`.
6. Примените прод-конфигурацию: `kubectl apply -k overlays/prod`.

## Код решения

**`base/kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1
kind: Kustomization

resources:
  - deployment.yaml
  - service.yaml
```

**`base/deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: app
          image: order-service:v1.0.0
          ports:
            - containerPort: 8080
```

**`overlays/prod/kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1
kind: Kustomization

namespace: production

resources:
  - ../../base
  - ingress.yaml

namePrefix: prod-

patchesStrategicMerge:
  - patch-replicas.yaml
```

**`overlays/prod/patch-replicas.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
```

**`overlays/prod/ingress.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: orders.production.corp
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: prod-order-service
                port:
                  number: 8080
```

**`Терминал`**

```bash
# Просмотр результирующего YAML для prod
kubectl kustomize overlays/prod

# Применение конфигурации production в кластер
kubectl apply -k overlays/prod

# Проверка созданных ресурсов в namespace production
kubectl get deployments,pods,ing -n production
```

## Под капотом

Движок Kustomize считывает `kustomization.yaml` в `overlays/prod`. Он рекурсивно загружает все ресурсы из `base/`, применяет директиву `namePrefix: prod-` ко всем объектам (обновляя также селекторы и ссылки в `Service`), а затем выполняет слияние патча `patch-replicas.yaml`. В отличие от текстовой замены строк, Kustomize оперирует абстрактными синтаксическими деревьями ресурсов Kubernetes, гарантируя семантическую корректность структуры манифестов.

## Подводные камни

1. Конфликт `namePrefix` со связями между объектами: если Ingress ссылается на сервис с именем `order-service`, а Kustomize добавил префикс `prod-order-service`, Ingress упадет с ошибкой backend service not found, если Ingress не включен в тот же kustomization для автоматического переименования ссылок.
2. Относительные пути к `base`: если вложенность каталогов изменена, путь `../../base` сломается.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество использования Kustomize перед Helm при организации GitOps конвейера через ArgoCD?»
**Ответ:** 1) Отсутствие фазы шаблонизации: манифесты в Git хранятся как чистый YAML, что исключает ошибки рендеринга типов и некорректных отступов; 2) Полная прозрачность code review: в pull request виден точный дифф изменений манифестов, а не абстрактные изменения в коде шаблонов Go; 3) Нативная интеграция: Kustomize встроен непосредственно в `kubectl` и ArgoCD без необходимости поддерживать репозитории чартов.
