# Защита от OOM-Kill: тюнинг Go GC, resources.limits и GOMEMLIMIT

## Условие

**Защита от OOM (Resources & GOMEMLIMIT)**: Укажи в манифесте `resources.requests` (гарантированные ресурсы: 100m CPU, 64Mi RAM) и `resources.limits` (потолок: 200m CPU, 128Mi RAM). В Go 1.19+ появилась переменная `GOMEMLIMIT`. Если под потребляет память и упирается в 128Mi, Linux убьет его (OOMKilled). Передай `GOMEMLIMIT=100MiB` в под. Теперь сборщик мусора (GC) в Go будет работать агрессивнее при подходе к этому порогу, спасая приложение от смерти в кластере!

## Теория

Одной из самых коварных проблем Go-приложений в Kubernetes является аварийное завершение по **OOMKilled (Exit Code 137)**:
1. **Механика Linux cgroup OOM Killer:**
   - Когда суммарная память контейнера превышает `resources.limits.memory` (128Mi), ядро Linux немедленно шлет сигнал `SIGKILL` (код 137). Процесс падает мгновенно, без возможности перехватить ошибку.
2. **Проблема традиционного Go GC:**
   - По умолчанию сборщик мусора Go управляется параметром `GOGC=100`, запускаясь при удвоении размера кучи (heap).
   - Если куча выросла с 40 МБ до 70 МБ, GC не запустится, пока память не достигнет 80 МБ. В условиях жесткого лимита 128 МБ всплеск аллокаций мгновенно приводит к OOMKilled до того, как GC успеет сработать!
3. **Революция `GOMEMLIMIT` (Go 1.19+):**
   - Устанавливает мягкий потолок памяти для рантайма Go.
   - **Золотое правило SRE:** выставлять `GOMEMLIMIT` на **15–20% ниже** лимита cgroup контейнера (например, при лимите 128Mi выставлять `GOMEMLIMIT=100MiB` или `105MiB`).
   - Запас в 20% необходим для памяти вне кучи (стеки горутин, структуры рантайма, сегменты бинарника, cgo).
   - При приближении к 100MiB рантайм Go резко увеличивает частоту циклов сборки мусора, удерживая потребление в безопасных границах!

## Решение по шагам

1. Создайте Go-приложение с динамическим выделением памяти в цикле.
2. В `deployment.yaml` задайте `resources.limits.memory: 128Mi`.
3. Задайте переменную окружения `GOMEMLIMIT: "100MiB"`.
4. Запустите нагрузочное тестирование и убедитесь, что приложение стабильно работает и не падает с ошибкой OOMKilled.
5. Проверьте метрику `go_memstats_heap_alloc_bytes` в Prometheus.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: oom-protected-app
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: oom-protected-app
  template:
    metadata:
      labels:
        app: oom-protected-app
    spec:
      containers:
        - name: app
          image: oom-protected-app:v1.0.0
          env:
            # Мягкий лимит памяти для Go GC: 100 MiB из 128 MiB cgroup лимита
            - name: GOMEMLIMIT
              value: "100MiB"
            # Автоматическая настройка GOMAXPROCS под лимит CPU контейнера
            - name: AUTOMAXPROCS
              value: "true"
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"runtime"
	"time"
)

func allocateMemoryHandler(w http.ResponseWriter, r *http.Request) {
	// Имитация резкого всплеска аллокаций памяти при обработке запроса
	var list [][]byte
	for i := 0; i < 50; i++ {
		block := make([]byte, 1024*1024) // Выделяем 1 МБ
		block[0] = 1
		list = append(list, block)
	}

	var m runtime.MemStats
	runtime.ReadMemStats(&m)

	fmt.Fprintf(w, "Аллоцировано 50 МБ. Текущая куча: %d MiB, Системная память: %d MiB\n",
		m.HeapAlloc/(1024*1024), m.Sys/(1024*1024))
}

func main() {
	http.HandleFunc("/stress", allocateMemoryHandler)
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("OK"))
	})

	log.Println("Защищенный от OOM Go сервер запущен на :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`Терминал`**

```bash
# Применение защищенного манифеста
kubectl apply -f deployment.yaml

# Запуск стресс-тестирования памяти
kubectl run curl-stress --image=curlimages/curl --rm -it -- \
  sh -c "while true; do curl -s http://oom-protected-app:8080/stress; sleep 0.1; done"

# Проверка того, что контейнер НЕ падает в OOMKilled (RESTARTS остается 0)
kubectl get pods -l app=oom-protected-app
```

## Под капотом

Рантайм Go отслеживает суммарный размер памяти, выделенной процессом (heap + stack + runtime metadata). В формулу запуска сборщика мусора включается порог `GOMEMLIMIT`. Если текущая память процесса приближается к целевому значению (100MiB), GC запускается немедленно, не дожидаясь срабатывания правила удвоения кучи `GOGC`. Для предотвращения троттлинга GC (когда сборщик мусора тратит 100% времени CPU на очистку кучи) в Go встроен лимит: GC не может занимать более 50% процессорного времени (GC CPU Limiter).

## Подводные камни

1. Установка `GOMEMLIMIT` ровно равным `limits.memory` (например, 128MiB при лимите 128Mi): приведет к гарантированному OOM-Kill, так как `GOMEMLIMIT` учитывает не всю физическую память RSS процесса (не учитываются разделяемые библиотеки, буферы сетевого ввода-вывода и накладные расходы рантайма). Всегда оставляйте зазор в 15-20%.
2. GC Thrashing при экстремальной нехватке памяти: если живые несборные данные превышают `GOMEMLIMIT`, GC начнет работать непрерывно, утилизируя 50% CPU и замедляя обработку запросов.

## На собеседовании

**Вопрос с собеседования:** «Почему до появления `GOMEMLIMIT` в Go 1.19 тюнинг `GOGC` (например, `GOGC=50` или `GOGC=200`) не решал проблему OOMKilled в Kubernetes?»
**Ответ:** `GOGC` оперирует исключительно относительным коэффициентом роста кучи в процентах относительно размера живых данных после предыдущей сборки мусора. Он совершенно «слеп» к абсолютным ограничениям контейнера в cgroup (`limits.memory`). Если базовый размер живых данных в приложении вырос с 20 МБ до 70 МБ, при `GOGC=100` рантайм запланирует следующий GC на 140 МБ. В контейнере с лимитом 128 МБ ядро Linux убьет процесс через OOMKilled задолго до того, как сработает `GOGC`. `GOMEMLIMIT` устанавливает жесткий абсолютный потолок, заставляя GC адаптироваться к границам контейнера.
