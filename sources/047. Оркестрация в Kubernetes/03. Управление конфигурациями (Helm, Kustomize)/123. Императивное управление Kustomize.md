# Императивное управление Kustomize: команда edit add configmap

## Условие

Используйте `kustomize edit add configmap` для генерации ConfigMap из файлов.

## Теория

В процессе автоматизации CI/CD или локальной разработки манипуляции с `kustomization.yaml` можно выполнять не только вручную, но и через CLI-команду **`kustomize edit`**:
1. **Команда `kustomize edit add configmap <name> --from-file=<path>`**:
   - Автоматически находит или создает секцию `configMapGenerator` в `kustomization.yaml`.
   - Привязывает локальный физический файл (например, `application.properties` или `queries.sql`) к генератору ConfigMap.
2. **Преимущества `configMapGenerator`:**
   - **Хэширование контента (Content Hash):** Kustomize автоматически добавляет хэш SHA-1 к имени ресурса (например, `app-config-4g9b5k`).
   - При изменении содержимого файла меняется хэш и имя ConfigMap.
   - Kubernetes воспринимает это как изменение спецификации Pod и автоматически инициирует Rolling Update без необходимости ручного рестарта!

## Решение по шагам

1. Инициализируйте пустой файл kustomization: `kustomize init`.
2. Создайте локальный файл конфигурации `app.conf`.
3. Выполните команду `kustomize edit add configmap app-conf --from-file=app.conf`.
4. Проверьте сформированный `kustomization.yaml`.
5. Сгенерируйте итоговый манифест командой `kustomize build .`.

## Код решения

**`app.conf`**

```bash
SERVER_PORT=9000
DATABASE_MAX_IDLE=10
CACHE_EXPIRATION_SEC=300
```

**`Терминал`**

```bash
# Создание каркаса Kustomize
mkdir -p my-app-config && cd my-app-config
echo "DB_TIMEOUT=5s" > app.conf
kustomize init

# Императивное добавление генератора ConfigMap из файла
kustomize edit add configmap dynamic-app-config --from-file=app.conf

# Просмотр сгенерированного файла kustomization.yaml
cat kustomization.yaml

# Сборка финального Kubernetes манифеста со сгенерированным хэшем в имени
kustomize build .
```

**`kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1
kind: Kustomization

configMapGenerator:
  - name: dynamic-app-config
    files:
      - app.conf
```

## Под капотом

Команда `kustomize edit` парсит YAML-файл, добавляет запись в AST-дерево и аккуратно сохраняет форматирование. При вызове `kustomize build` генератор считывает содержимое `app.conf`, вычисляет его SHA-256 хеш, берет первые 10 символов и формирует имя `dynamic-app-config-8h6bk2mf59`. Также Kustomize автоматически обновляет все ссылки на этот ConfigMap во всех объявленных в `kustomization.yaml` ресурсах `Deployment` и `StatefulSet`.

## Подводные камни

1. Забытый коммит исходного конфигурационного файла в Git: если файл `app.conf` не закоммичен, CI/CD конвейер упадет с ошибкой `file not found` при выполнении `kustomize build`.
2. Накопление старых ConfigMap: при каждом изменении файла K8s создает новый ConfigMap с новым хэшем. Старые версии остаются в кластере, пока сборщик мусора (Garbage Collector) не удалит их после удаления старых ReplicaSet.

## На собеседовании

**Вопрос с собеседования:** «Зачем Kustomize добавляет хэш-суффикс к имени ConfigMap, сгенерированного через configMapGenerator?»
**Ответ:** Это фундаментальное решение проблемы обновления конфигурации в Kubernetes. Стандартное изменение существующего ConfigMap не меняет спецификацию Pod в Deployment (`spec.template`), поэтому Kubernetes не инициирует обновление подов (Rolling Update), и приложение продолжает работать со старым конфигом в памяти. Генерация уникального хэш-имени гарантирует, что любое изменение конфига создает НОВОЕ имя ресурса, что меняет шаблон пода и немедленно запускает штатный Rolling Update.
