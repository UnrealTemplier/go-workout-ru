# Pod Security Standards (PSS) и встроенный контроллер Pod Security Admission

## Условие

Настрой **Pod Security Standards**: `restricted` profile (enforced), `baseline` (warn), `privileged` (audit). `PodSecurity` admission controller. Покажи security hardening without OPA.

## Теория

Начиная с Kubernetes 1.25+, устаревший механизм PodSecurityPolicy (PSP) был окончательно удален и заменен на встроенный механизм **Pod Security Standards (PSS)** и контроллер **Pod Security Admission (PSA)**:
1. **Три профиля безопасности (Profiles):**
   - **Privileged:** Никаких ограничений (полный доступ к ядру, запуск от root, хостовая сеть). Предназначен только для системных агентов (CNI, CSI).
   - **Baseline:** Минимальные ограничения. Запрещает явное повышение привилегий, но разрешает дефолтные настройки большинства контейнеров.
   - **Restricted:** Максимальное ужесточение (Hardening). Запрет root (`runAsNonRoot: true`), запрет privilege escalation, сброс всех Linux capabilities (`drop: ["ALL"]`), обязательная read-only корневая файловая система (`readOnlyRootFilesystem: true`).
2. **Три режима применения (Modes):**
   - `enforce`: нарушение блокирует создание Pod.
   - `warn`: нарушение разрешает создание Pod, но выводит предупреждение пользователю в консоль `kubectl`.
   - `audit`: нарушение фиксируется в Audit Log кластера для ретроспективного анализа.
3. **Настройка через лейблы Namespace:** не требует установки сторонних операторов!

## Решение по шагам

1. Создайте namespace `secured-apps`.
2. Повесьте лейблы PSS: `enforce: restricted`, `warn: baseline`, `audit: privileged`.
3. Попробуйте запустить небезопасный контейнер (от пользователя root или с privileged: true).
4. Убедитесь, что K8s заблокировал запуск пода с подробным сообщением об ошибке.
5. Напишите манифест безопасного Pod, удовлетворяющий профилю `restricted`.

## Код решения

**`namespace.yaml`**

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: secured-apps
  labels:
    # Жесткий запрет создания небезопасных подов
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    # Предупреждение в консоль при несоответствии baseline
    pod-security.kubernetes.io/warn: baseline
    pod-security.kubernetes.io/warn-version: latest
    # Аудит в журнал безопасности
    pod-security.kubernetes.io/audit: privileged
    pod-security.kubernetes.io/audit-version: latest
```

**`secure-pod.yaml`**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hardened-go-app
  namespace: secured-apps
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: hardened-app:v1.0.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
      ports:
        - containerPort: 8080
```

**`Терминал`**

```bash
# Применение настроек профилей безопасности namespace
kubectl apply -f namespace.yaml

# Попытка запустить небезопасный контейнер (root по умолчанию) немедленно отклоняется API-сервером!
kubectl run root-test --image=nginx -n secured-apps
# Error from server (Forbidden): pods "root-test" is forbidden: violates PodSecurity "restricted:latest":
# allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile

# Запуск полностью защищенного пода проходит успешно
kubectl apply -f secure-pod.yaml
```

## Под капотом

Плагин Pod Security Admission встроен прямо в ядро `kube-apiserver` как compiled-in admission controller. Он перехватывает запросы создания Pod на фазе валидации. Плагин считывает лейблы `pod-security.kubernetes.io/*` с объекта Namespace, находит соответствующую спецификацию стандарта безопасности и выполняет валидацию полей `securityContext`. Поскольку проверка встроена в ядро apiserver, она выполняется за микросекунды без сетевых накладных расходов на вызов внешних webhook.

## Подводные камни

1. Забытый `seccompProfile: RuntimeDefault`: в стандарте `restricted` отсутствие этого профиля приводит к блокировке пода, даже если все остальные параметры настроены верно.
2. `readOnlyRootFilesystem: true` без временных томов: если Go-приложение пытается записать временный файл в `/tmp`, произойдет паника `read-only file system`. Для временных файлов необходимо монтировать том `emptyDir` по пути `/tmp`.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных версиях Kubernetes PodSecurityPolicy (PSP) был заменен на Pod Security Standards (PSS)?»
**Ответ:** PSP был признан архитектурно неудачным из-за сложности и непредсказуемости: политики связывались с пользователями через RBAC, и выбор применяемой политики зависел от того, кто создает Pod (человек или ServiceAccount контроллера). Это вызывало путаницу и скрытые уязвимости. PSS нативно встроен в apiserver, привязан к Namespace через простые декларативные лейблы, имеет три четко стандартизированных уровня безопасности и поддерживает безопасный режим предупреждений (`warn`) перед блокировкой (`enforce`).
