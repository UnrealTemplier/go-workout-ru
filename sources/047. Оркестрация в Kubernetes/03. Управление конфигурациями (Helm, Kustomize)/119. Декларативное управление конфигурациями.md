# Декларативное управление конфигурациями: продвинутые паттерны Kustomize

## Условие

**Kustomize alternative**: Создайте `kustomization.yaml` с `bases`, `patches`, `overlays` для управления окружениями без шаблонов.

## Теория

При масштабной разработке Kustomize позволяет строить многоуровневые деревья конфигураций без дублирования манифестов:
1. **Ключевые примитивы `kustomization.yaml`:**
   - `resources`: ссылки на манифесты или базовые каталоги (в современных версиях Kustomize поле `bases` признано устаревшим и объединено с `resources`).
   - `patches`: список точечных модификаций в форматах Strategic Merge Patch или RFC 6902 JSON 6902 Patch.
   - `commonLabels`: автоматическое добавление общих меток ко всем ресурсам и их селекторам.
   - `images`: переопределение имени и тега образа без создания отдельных файлов патчей (`images: - name: backend, newTag: v2.1.0`).
   - `replicas`: декларативное переопределение числа реплик целевого Deployment прямо в `kustomization.yaml`.
2. **Преимущества перед шаблонизаторами:**
   - 100% совместимость с Git diff.
   - Невозможно получить синтаксически невалидный YAML на выходе.
   - Отсутствие промежуточных артефактов в репозиториях чартов.

## Решение по шагам

1. Создайте структуру с `base/` и тремя окружениями: `dev/`, `qa/`, `prod/`.
2. В `overlays/prod/kustomization.yaml` используйте директиву `images` для подстановки тега релиза.
3. Используйте директиву `replicas` для масштабирования до 5 реплик.
4. Примените JSON Patch для модификации специфичного параметра probe.
5. Протестируйте итоговую сборку через `kubectl kustomize overlays/prod`.

## Код решения

**`overlays/prod/kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1
kind: Kustomization

resources:
  - ../../base

commonLabels:
  environment: production
  managed-by: kustomize

replicas:
  - name: backend-service
    count: 5

images:
  - name: backend-service
    newName: myregistry.io/backend
    newTag: v3.2.1

patches:
  - target:
      kind: Deployment
      name: backend-service
    patch: |-
      - op: replace
        path: /spec/template/spec/containers/0/resources/limits/memory
        value: 4Gi
```

**`Терминал`**

```bash
# Генерация и проверка итогового манифеста
kubectl kustomize overlays/prod

# Проверка корректности подстановки образа и числа реплик
kubectl kustomize overlays/prod | grep -E "(replicas:|image:)"
# replicas: 5
# image: myregistry.io/backend:v3.2.1
```

## Под капотом

Kustomize парсит манифесты в модель Resource Map (RNode). Операция `images` обходит все спецификации Pod в ресурсах `Deployment`, `StatefulSet`, `Job` и заменяет образ везде, где поле `image` совпадает с целевым `name`. Директива `replicas` валидирует существование соответствующего ресурса и безопасно меняет поле `spec.replicas`. В конце применяется JSON-патч (RFC 6902), производя точечную замену значения в дереве DOM без перезаписи соседних полей.

## Подводные камни

1. Устаревший синтаксис `bases: [../base]`: в Kustomize v4+ директива `bases` считается deprecated, рекомендуется использовать только `resources: [../base]`.
2. Ошибки в путях JSON Patch: ошибка в пути `/spec/template/spec/containers/0/...` (например, неверный индекс контейнера) приведет к ошибке сборки `json patch error`.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество директивы `images` в Kustomize перед обычным Strategic Merge Patch?»
**Ответ:** Директива `images` не требует создания отдельного YAML-файла патча и не привязана к жесткому имени Deployment. Она автоматически находит и обновляет тег образа во ВСЕХ ресурсах манифеста (Deployment, CronJob, Canary), где фигурирует этот образ. Кроме того, в CI/CD пайплайне команду можно выполнить одной строкой: `kustomize edit set image backend-service=myreg/app:$CI_COMMIT_SHA`.
