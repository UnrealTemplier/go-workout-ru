# Отказоустойчивость: детекция дедлоков через Liveness Probe в Go

## Условие

**Пробы жизни (Liveness Probe)**: Что если Go-приложение поймало deadlock (зависло), но процесс не упал? K8s этого не поймет. Напиши в Go хендлер `/health`. В манифесте добавь `livenessProbe`, которая делает HTTP-запрос на этот роут каждые 10 секунд. Если Go ответит 500 (или таймаут) 3 раза подряд — K8s сам убьет и перезапустит контейнер.

## Теория

Ситуация, когда процесс жив (PID существует в ОС), но не способен выполнять полезную работу (дедлок мьютексов `sync.Mutex`, зависание горутин на чтении небуферизированного канала, вечный цикл):
1. **Роль Liveness Probe:** K8s периодически опрашивает контейнер. Если проба завершается сбоем \(N\) раз подряд (`failureThreshold`), kubelet принудительно перезапускает контейнер (`kill -9`).
2. **Как правильно писать Liveness Probe в Go:**
   - Проверка должна быть **легковесной и локальной**.
   - Проверять внутреннее состояние рантайма: не завис ли главный цикл обработки задач (heartbeat/watchdog паттерн).
   - **КРИТИЧЕСКОЕ ПРАВИЛО:** Liveness Probe НИКОГДА не должна проверять внешние зависимости (базу данных, кэш, другие сервисы)! Если упадет БД, все поды одновременно начнут падать с ошибкой Liveness Probe, вызвав каскадный коллапс всего кластера.

## Решение по шагам

1. Напишите Go-сервис с механизмом периодического обновления heartbeat-таймштампа.
2. Реализуйте хендлер `/healthz`, возвращающий 500 Internal Server Error, если heartbeat не обновлялся дольше 15 секунд (признак дедлока воркера).
3. Добавьте эндпоинт `/trigger-deadlock` для демонстрации сбоя.
4. Настройте в `deployment.yaml` параметры `livenessProbe: periodSeconds: 10, failureThreshold: 3`.
5. Сымитируйте зависание и убедитесь, что K8s автоматически перезапустил контейнер (`RESTARTS: 1`).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"sync/atomic"
	"time"
)

var lastHeartbeat int64

func workerLoop() {
	for {
		// Обновляем таймштамп активности воркера
		atomic.StoreInt64(&lastHeartbeat, time.Now().Unix())
		time.Sleep(2 * time.Second)
	}
}

func main() {
	// Инициализируем начальный heartbeat
	atomic.StoreInt64(&lastHeartbeat, time.Now().Unix())
	go workerLoop()

	mux := http.NewServeMux()

	// Liveness Probe: проверяет исключительно локальную жизнеспособность процесса
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		last := atomic.LoadInt64(&lastHeartbeat)
		diff := time.Now().Unix() - last

		if diff > 15 {
			log.Printf("ВНИМАНИЕ: Heartbeat заблокирован! Задержка: %d сек. Отправка 500...", diff)
			http.Error(w, fmt.Sprintf("Deadlock detected, last heartbeat %d sec ago", diff), http.StatusInternalServerError)
			return
		}

		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ALIVE"))
	})

	// Эндпоинт для намеренного вызова вечной блокировки (эмуляция дедлока)
	mux.HandleFunc("/simulate-deadlock", func(w http.ResponseWriter, r *http.Request) {
		log.Println("Имитация дедлока: блокировка навсегда...")
		select {} // Вечная блокировка горутины
	})

	server := &http.Server{Addr: ":8080", Handler: mux}
	log.Println("Сервер слушает на порту :8080...")
	_ = server.ListenAndServe()
}
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: deadlock-detector
spec:
  replicas: 1
  selector:
    matchLabels:
      app: deadlock-detector
  template:
    metadata:
      labels:
        app: deadlock-detector
    spec:
      containers:
        - name: app
          image: deadlock-detector:v1.0.0
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
```


## Под капотом

Демон `kubelet` на узле запускает горутину probe-worker для каждого контейнера с периодичностью `periodSeconds`. Kubelet инициирует HTTP GET запрос на сокет пода. Если HTTP-ответ возвращает статус-код в диапазоне \(200 \le \text{status} < 400\), счетчик сбоев сбрасывается в 0. Если трижды подряд получен код \(\ge 400\) или истек `timeoutSeconds`, kubelet отправляет вызов CRI `StopContainer`, уничтожает контейнер и инициирует создание нового в соответствии с `restartPolicy`.

## Подводные камни

1. Проверка базы данных в Liveness Probe: если СУБД перезагружается или испытывает всплеск задержек, Liveness пробы всех подов микросервиса синхронно вернут 500, и Kubernetes начнет циклически убивать и перезапускать вообще все поды в кластере.
2. Слишком агрессивный `timeoutSeconds: 1`: кратковременный всплеск нагрузки CPU или пауза сборщика мусора Go (Stop-The-World) может задержать ответ на 1.2 секунды, вызвав ложный перезапуск здорового контейнера.

## На собеседовании

**Вопрос с собеседования:** «В чем фундаментальная разница между целями Liveness Probe и Readiness Probe?»
**Ответ:** **Liveness Probe** отвечает на вопрос: «Жив ли контейнер или он завис навсегда?». Реакция на сбой — жесткий перезапуск контейнера. **Readiness Probe** отвечает на вопрос: «Готов ли контейнер прямо сейчас принимать сетевой трафик?». Реакция на сбой — временное исключение IP-адреса пода из балансировщика Service/Endpoints БЕЗ перезапуска контейнера (например, пока сервис прогревает локальный кэш или ждет восстановления коннекта к БД).
