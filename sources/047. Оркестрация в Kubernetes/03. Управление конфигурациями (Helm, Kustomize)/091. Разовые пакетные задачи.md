# Разовые пакетные задачи: Kubernetes Job и семантика перезапусков

## Условие

Настройте **Job** для one-off задач (например, миграции БД при деплое).

## Теория

Объект **Job** предназначен для выполнения разовых вычислений или задач с четко определенным завершением (batch processing, миграции БД, генерация отчетов, обучение ML-моделей):
1. **Отличие от Deployment:**
   - Deployment рассчитан на долгоживущие процессы (серверы). Если процесс завершается (exit code 0), Deployment перезапускает его, считая это аварией.
   - Job рассчитан на задачи, которые завершаются. Когда процесс завершается с кодом 0, Job переходит в статус `Completed` и больше не перезапускается.
2. **Ключевые параметры спецификации `JobSpec`**:
   - `restartPolicy`: для Pod внутри Job допустимы только `Never` (создать новый Pod при сбое) или `OnFailure` (перезапустить контейнер внутри существующего Pod). Значение `Always` запрещено!
   - `backoffLimit`: максимальное количество повторных попыток перед тем, как признать Job завершившимся со сбоем (по умолчанию 6).
   - `activeDeadlineSeconds`: жесткий лимит времени выполнения всей задачи (например, 600 сек). Если задача не завершилась, все поды принудительно убиваются.
   - `ttlSecondsAfterFinished`: автоматическое удаление объекта Job и его подов из кластера через N секунд после завершения (очистка памяти etcd).

## Решение по шагам

1. Создайте манифест `job.yaml` с `restartPolicy: OnFailure`.
2. Установите `backoffLimit: 3` и `activeDeadlineSeconds: 300`.
3. Настройте `ttlSecondsAfterFinished: 100` для автоматической сборки мусора.
4. Напишите Go-утилиту, выполняющую миграцию таблиц и возвращающую код 0 при успехе.
5. Запустите Job и отследите статус через `kubectl get job`.

## Код решения

**`job.yaml`**

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-schema-migration-v2
  namespace: default
spec:
  backoffLimit: 3
  activeDeadlineSeconds: 300
  ttlSecondsAfterFinished: 60
  template:
    metadata:
      name: db-migrator
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrator
          image: db-migrator:v2.0.0
          env:
            - name: DATABASE_URL
              value: "postgres://user:pass@postgres:5432/app_db?sslmode=disable
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
	"time"
)

func main() {
	dbURL := os.Getenv("DATABASE_URL")
	if dbURL == "" {
		log.Fatal("Переменная окружения DATABASE_URL не задана")
	}

	log.Println("Инициализация соединения с БД и блокировка таблицы миграций...")
	time.Sleep(1 * time.Second)

	// Имитация применения миграций схемы
	migrations := []string{"001_create_users", "002_add_index_email", "003_create_orders"}
	for _, m := range migrations {
		log.Printf("Применение миграции: %s... УСПЕШНО", m)
	}

	fmt.Println("Все миграции успешно завершены. Выход с кодом 0.")
	os.Exit(0)
}
```

**`Терминал`**

```bash
# Запуск задачи
kubectl apply -f job.yaml

# Ожидание завершения выполнения Job
kubectl wait --for=condition=complete --timeout=60s job/db-schema-migration-v2

# Просмотр логов выполненного контейнера
kubectl logs -l job-name=db-schema-migration-v2
```

## Под капотом

`job-controller` отслеживает состояние подов задачи. Если контейнер завершается с ненулевым кодом выхода, контроллер увеличивает счетчик сбоев (`failedCount`) и вычисляет экспоненциальную задержку перед следующим запуском: \(10 \text{s} \times 2^{\text{failedCount}}\) (10с, 20с, 40с...). Когда `failedCount >= backoffLimit`, контроллер помечает Job условием `JobFailed` и прекращает создание новых подов. Контроллер `ttl-after-finished-controller` следит за полем `ttlSecondsAfterFinished` и отправляет вызов `Delete` в apiserver через указанное время.

## Подводные камни

1. Использование `restartPolicy: Always`: приведет к ошибке валидации манифеста apiserver при создании Job.
2. Не установлен `ttlSecondsAfterFinished`: сотни старых завершенных объектов Job накапливаются в etcd, перегружая память apiserver и затрудняя вывод команд `kubectl get pods`.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между `completions` и `parallelism` в Kubernetes Job?»
**Ответ:** Параметр `completions: N` указывает общее количество успешных завершений Pod'ов, необходимых для того, чтобы весь Job считался завершенным (по умолчанию 1). Параметр `parallelism: M` определяет максимальное количество Pod'ов, которые могут выполняться одновременно параллельно (по умолчанию 1). Это позволяет организовать параллельную обработку очередей задач (Work Queues) силами встроенных примитивов K8s.
