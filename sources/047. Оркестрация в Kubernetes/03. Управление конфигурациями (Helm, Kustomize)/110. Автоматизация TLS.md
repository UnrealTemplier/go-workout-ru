# Автоматизация TLS: Cert-Manager, ClusterIssuer и Let's Encrypt

## Условие

Установи **Cert-manager**: `ClusterIssuer` for Let's Encrypt (production/staging). `Certificate` resource automatically requests and renews TLS certificates. `Ingress` or `Gateway` references secret. Покажи automated TLS.

## Теория

Ручной выпуск и обновление SSL/TLS-сертификатов — источник частых сбоев в продакшене из-за человеческого фактора (забыли продлить сертификат вовремя).
**Cert-Manager** — оператор Kubernetes для автоматизации выпуска и ротации TLS-сертификатов:
1. **Компоненты и CRD:**
   - **`Issuer` / `ClusterIssuer`**: определяет удостоверяющий центр (CA), например ACME-сервер Let's Encrypt, корпоративный HashiCorp Vault или локальный CA. `ClusterIssuer` доступен во всех namespace кластера.
   - **`Certificate`**: объявляет желаемый сертификат (доменные имена, Secret для сохранения ключей, срок обновления).
2. **Типы ACME-челленджей (Let's Encrypt):**
   - **HTTP-01:** Cert-Manager создает временный Pod и правило в Ingress для отдачи проверочного токена по пути `http://<domain>/.well-known/acme-challenge/<token>`. Требует публичного белого IP-адреса.
   - **DNS-01:** Cert-Manager создает временную TXT-запись в DNS-зоне через API провайдера (Cloudflare, AWS Route53). Позволяет выпускать wildcard-сертификаты (`*.example.com`).
3. **Интеграция с Ingress:** Аннотация `cert-manager.io/cluster-issuer: letsencrypt-prod` автоматически заставляет cert-manager выпустить сертификат для хостов из секции `tls`.

## Решение по шагам

1. Установите Cert-Manager через официальные CRD-манифесты.
2. Создайте `ClusterIssuer` для Let's Encrypt с протоколом ACME HTTP-01.
3. Настройте `Ingress` с аннотацией вызова ClusterIssuer и секцией `tls`.
4. Отследите прохождение ACME-челленджа через `kubectl get certificate,order,challenge`.
5. Проверьте созданный Kubernetes Secret с приватным ключом `tls.key` и сертификатом `tls.crt`.

## Код решения

**`cluster-issuer.yaml`**

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: devops@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            class: nginx
```

**`ingress-tls.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: secure-ingress
  namespace: default
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.mycompany.com
      secretName: api-mycompany-tls-cert
  rules:
    - host: api.mycompany.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
```

**`Терминал`**

```bash
# Установка cert-manager с манифестами CRD
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.3/cert-manager.yaml

# Применение конфигурации ClusterIssuer и Ingress
kubectl apply -f cluster-issuer.yaml
kubectl apply -f ingress-tls.yaml

# Отслеживание процесса выпуска сертификата
kubectl get certificate api-mycompany-tls-cert
# NAME                       READY   SECRET                      AGE
# api-mycompany-tls-cert     True    api-mycompany-tls-cert      45s

# Проверка содержимого сгенерированного секрета
kubectl get secret api-mycompany-tls-cert -o yaml | grep "tls.crt:
```

## Под капотом

Когда Ingress создается с аннотацией `cert-manager.io/cluster-issuer`, контроллер `cert-manager-ingress-shim` генерирует ресурс `Certificate`. Основной контроллер `cert-manager` создает объект `Order` и `Challenge`. Контроллер поднимает временный pod-респондер и настраивает Ingress routing для пути `/.well-known/acme-challenge/*`. Серверы Let's Encrypt обращаются по HTTP к этому пути, подтверждают владение доменом и выпускают X.509 сертификат, который Cert-Manager записывает в Secret.

## Подводные камни

1. Превышение лимитов (Rate Limits) Let's Encrypt: при тестировании конфигурации на боевом сервере `letsencrypt-prod` частые ошибки приводят к блокировке домена на 7 дней. Для отладки ВСЕГДА используйте `letsencrypt-staging`.
2. Блокировка порта 80: если файрвол или Cloudflare блокирует HTTP (порт 80), HTTP-01 challenge завершится ошибкой таймаута.

## На собеседовании

**Вопрос с собеседования:** «За сколько дней до окончания срока действия Cert-Manager начинает процедуру обновления сертификата?»
**Ответ:** По умолчанию Cert-Manager начинает процедуру автоматического обновления за **30 дней (720 часов)** до истечения срока действия сертификата (при стандартном сроке жизни сертификата Let's Encrypt в 90 дней). Это поведение можно переопределить в манифесте `Certificate` с помощью поля `renewBefore: 360h` (15 дней).
