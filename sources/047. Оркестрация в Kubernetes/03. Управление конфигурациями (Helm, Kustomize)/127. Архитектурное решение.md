# Архитектурное решение: Helm против Kustomize — когда и что выбирать

## Условие

Сравните Helm и Kustomize: когда что использовать? (Helm — для переиспользуемых charts, Kustomize — для environment-specific customizations).

## Теория

Выбор между Helm и Kustomize — фундаментальное архитектурное решение платформенной команды:
1. **Матрица выбора:**
   - **Helm идеален для:**
     1. Стороннего инфраструктурного софта (Open Source: Ingress, Prometheus, Kafka, Cert-Manager, GitLab Runner).
     2. Публикации переиспользуемых платформных библиотек внутри компании (Internal Developer Platform).
     3. Управления комплексными зависимостями (Subcharts) с общими переменными.
   - **Kustomize идеален для:**
     1. Собственных микросервисов компании, разрабатываемых внутри команд.
     2. Наложения специфичных настроек окружений (dev, test, stage, prod, dr).
     3. Строгих процессов GitOps (ArgoCD, Flux), где недопустима скрытая магия шаблонизации.
2. **Enterprise Golden Path (Золотой стандарт индустрии):**
   - Инфраструктурные чарты упаковываются через Helm.
   - Развертывание конкретного сервиса управляется через Kustomize, который при необходимости использует `helmCharts` generator для параметризации базовых чартов без потери валидности YAML.

## Решение по шагам

1. Составьте формальный архитектурный ADR (Architecture Decision Record).
2. Опишите критерии выбора для команд разработки.
3. Продемонстрируйте гибридный подход: использование Kustomize поверх Helm-чарта.

## Код решения

**`adr-helm-vs-kustomize.md`**

```markdown
# ADR-042: Стандарты использования Helm и Kustomize в компании

## Статус
Принято (Accepted)

## Контекст
В компании развернуто 120+ микросервисов на Go и 15 сторонних инфраструктурных платформ.
Требуется единый стандарт управления манифестами для исключения дублирования кода.

## Решение
1. **Стороннее ПО (Off-the-shelf software):** Использовать **Helm**.
   - Установка Ingress, Service Mesh, СУБД, Observability выполняется строго через проверенные Helm-чарты.
2. **Внутренние микросервисы (Internal Microservices):** Использовать **Kustomize**.
   - Репозиторий каждого Go-сервиса содержит директорию `deploy/k8s/` с `base/` и оверлеями `overlays/dev`, `overlays/prod`.
3. **CD Конвейер:** ArgoCD синхронизирует состояние кластеров через Kustomize.
```

**`hybrid-kustomization.yaml`**

```yaml
apiVersion: kustomize.config.k8s.io/v1
kind: Kustomization

# Использование Helm для загрузки стороннего чарта Redis
helmCharts:
  - name: redis
    repo: https://charts.bitnami.com/bitnami
    version: 17.14.5
    releaseName: cache
    valuesInline:
      auth:
        enabled: false
      master:
        persistence:
          enabled: false

# Использование Kustomize для наложения корпоративных лейблов безопасности
commonLabels:
  compliance.corp/pci-dss: "true"
  cost-center: "infra-team
```

## Под капотом

Движок Kustomize поддерживает расширение `kustomize.config.k8s.io/v1/helmCharts`. При сборке Kustomize скачивает указанный Helm-чарт во временную директорию, вызывает локальный API Helm для рендеринга манифестов со значениями `valuesInline`, парсит полученный поток в структуры данных Kyaml и применяет директивы `commonLabels`, `patches` и `namespace`. Это объединяет мощь экосистемы Helm с декларативной строгостью Kustomize.

## Подводные камни

1. Попытка написать универсальный мега-чарт Helm на 2000 строк для всех микросервисов компании: превращается в нечитаемый клубок условий `{{- if .Values.isJavaApp }}`, который никто не может поддерживать.
2. Использование Kustomize для тиражирования сложных распределенных систем (например, кластера ElasticSearch/Kafka): приводит к тысячам строк ручных YAML патчей вместо параметризованных чартов.

## На собеседовании

**Вопрос с собеседования:** «Почему крупные финтех-компании и банки часто запрещают использование `helm install` напрямую из CI конвейеров на production-контурах?»
**Ответ:** 1) Нарушение принципа наименьших привилегий: CI-раннеру требуются прямые административные права в кластер; 2) Непрозрачность аудита: сложно понять точное состояние инфраструктуры по логам сборки; 3) Отсутствие защиты от человеческого фактора: ручной запуск `helm upgrade` с неверными флагами может стереть конфигурацию. Вместо прямого Helm внедряется GitOps: манифесты коммитятся в Git (через Kustomize или отрендеренный Helm), а оператор ArgoCD синхронизирует кластер изнутри.
