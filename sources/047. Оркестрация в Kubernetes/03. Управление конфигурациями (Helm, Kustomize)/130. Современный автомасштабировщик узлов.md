# Современный автомасштабировщик узлов: Karpenter, NodePools и Spot-инстансы

## Условие

Настрой **Karpenter** (alternative to Cluster Autoscaler): provisioner per workload type. `NodePool` with `requirements` (instance types, architecture, capacity type: spot/on-demand). Faster scaling, better cost optimization. Покажи modern autoscaling.

## Теория

Традиционный **Cluster Autoscaler** медлителен: он привязан к заранее созданным облачным группам масштабирования (AWS ASG), масштабирует узлы фиксированного размера и тратит от 3 до 7 минут на запуск новой ноды.
**Karpenter (Open-Source от AWS/CNCF):**
1. **Революция Just-in-Time:**
   - Karpenter НЕ использует ASG. Он напрямую вызывает Cloud API (например, `ec2:RunInstances`).
   - Время поднятия нового узла и назначения подов составляет **менее 40 секунд**!
2. **Гибкий Bin-Packing и оптимизация расходов (Cost Optimization):**
   - Karpenter анализирует точные требования Pending-подов (CPU, RAM, GPU, архитектура arm64/amd64, зона доступности, локальный диск NVMe).
   - Он на лету выбирает **самый дешевый и идеально подходящий по размеру тип виртуальной машины** из сотен вариантов EC2.
   - Поддерживает автоматическое смешивание **Spot** и **On-Demand** инстансов.
3. **Автоматическая консолидация (Consolidation):**
   - Непрерывно перемещает поды для освобождения недозагруженных узлов и замены дорогих серверов более дешевыми.

## Решение по шагам

1. Установите контроллер Karpenter в кластер EKS.
2. Создайте манифест `EC2NodeClass` с описанием подсетей, групп безопасности и AMI.
3. Создайте манифест `NodePool` с требованиями к архитектуре (`arm64`, `amd64`) и типу мощности (`spot`, `on-demand`).
4. Задеплойте приложение с высокими требованиями к ресурсам.
5. Пронаблюдайте за мгновенным подбором оптимального сервера и его регистрацией в кластере.

## Код решения

**`nodepool.yaml`**

```yaml
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: general-compute-pool
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"] # Приоритет отдается дешевым Spot-инстансам
        - key: kubernetes.io/arch
          operator: In
          values: ["arm64", "amd64"] # Поддержка экономичных процессоров Graviton (arm64)
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["5"]
      nodeClassRef:
        apiVersion: karpenter.k8s.aws/v1beta1
        kind: EC2NodeClass
        name: default-node-class
  limits:
    cpu: "1000"
    memory: 1000Gi
  disruption:
    consolidationPolicy: WhenUnderutilized # Автоматическое сжатие кластера при простое
    expireAfter: 720h # Ротация узлов раз в 30 дней для обновления версий ядра ОС
```

**`ec2-node-class.yaml`**

```yaml
apiVersion: karpenter.k8s.aws/v1beta1
kind: EC2NodeClass
metadata:
  name: default-node-class
spec:
  amiFamily: AL2023
  role: "KarpenterNodeRole-my-cluster"
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: "my-cluster"
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: "my-cluster
```

**`Терминал`**

```bash
# Применение манифестов Karpenter NodePool
kubectl apply -f ec2-node-class.yaml
kubectl apply -f nodepool.yaml

# Просмотр логов контроллера Karpenter при появлении Pending подов
kubectl logs -n karpenter -l app.kubernetes.io/name=karpenter -f | grep "discovered"
# INFO  controller.provisioner  found provisionable pod(s)  {"pods": 12}

```

## Под капотом

В отличие от kube-scheduler, который ждет появления узлов, Karpenter сам перехватывает события Pending-подов до планировщика. Алгоритм решает задачу многомерной упаковки в контейнеры (Multi-dimensional Knapsack Problem). С учетом цен AWS Spot Feed в реальном времени Karpenter выбирает инстанс минимальной стоимости, отправляет прямой gRPC запрос к EC2 Fleet API, инициирует загрузку операционной системы и заранее связывает Pod с будущим узлом еще до окончания загрузки ОС.

## Подводные камни

1. Забытый PDB (PodDisruptionBudget) при включенной консолидации (`WhenUnderutilized`): Karpenter может одновременно вытеснить слишком много подов сервиса для сжатия нод, вызвав кратковременный отказ в обслуживании.
2. Неготовность приложений к Spot-инстансам: провайдер может отозвать Spot-инстанс с предупреждением за 2 минуты (Spot Interruption). Приложения обязаны быстро сохранять состояние и обрабатывать прерывания.

## На собеседовании

**Вопрос с собеседования:** «Чем Karpenter принципиально превосходит классический Kubernetes Cluster Autoscaler с точки зрения скорости и стоимости?»
**Ответ:** 1) **Скорость:** Cluster Autoscaler работает через медленный опрос Cloud ASG (время подъема узла 3-7 минут). Karpenter создает инстансы напрямую через API облака за 30-45 секунд; 2) **Оптимизация расходов:** В CA нужно заранее жестко конфигурировать группы нод определенного размера (например, m5.xlarge). Karpenter динамически выбирает из сотен типов инстансов (c6g, m6i, r6g) ровно тот размер, который идеально и без избытка вмещает текущие поды, максимально агрессивно используя Spot-инстансы и архитектуру ARM Graviton.
