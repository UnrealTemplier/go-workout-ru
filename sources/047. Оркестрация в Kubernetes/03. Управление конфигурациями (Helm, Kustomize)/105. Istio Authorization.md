# Istio Authorization: L7 авторизация, ServiceAccount и валидация JWT

## Условие

Настрой **Istio Authorization**: `AuthorizationPolicy` — allow/deny based on source (service account), operation (GET /api/users), conditions (JWT claims). Покажи L7 authorization.

## Теория

Шифрование mTLS обеспечивает идентификацию вызывающего сервиса (Authentication), но не определяет права доступа (Authorization).
**Объект `AuthorizationPolicy`:**
1. **Действие по умолчанию:**
   - Если для рабочей нагрузки (workload) не задана ни одна политика, разрешен весь трафик.
   - Как только создается ХОТЯ БЫ ОДНА политика `action: ALLOW`, действует принцип «запрещено всё, что явно не разрешено» (Default Deny).
2. **Селекторы и условия:**
   - `selector.matchLabels`: целевые поды сервиса.
   - `rules.from.source.principals`: проверка идентичности вызывающего сервиса (SPIFFE ID или ServiceAccount, например `cluster.local/ns/default/sa/frontend-sa`).
   - `rules.to.operation`: HTTP-методы (`GET`, `POST`), пути (`/api/v1/users/*`), порты.
   - `rules.when`: валидация клеймов JWT-токена (например, `request.auth.claims[role] == "admin"`).
3. **Безопасность на уровне L7:** Фильтрация происходит прямо внутри Envoy-прокси до того, как пакет попадет в код Go-микросервиса.

## Решение по шагам

1. Создайте манифест `AuthorizationPolicy`, разрешающий только `GET` запросы к `/api/users` только для ServiceAccount `frontend-service-account`.
2. Создайте правило проверки роли `admin` из JWT токена.
3. Протестируйте отправку запроса с корректным ServiceAccount и без него.
4. Проверьте возврат ошибки HTTP 403 Forbidden от Envoy при нарушении политик.

## Код решения

**`auth-policy.yaml`**

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: user-service-rbac
  namespace: default
spec:
  selector:
    matchLabels:
      app: user-service
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/default/sa/frontend-sa"]
      to:
        - operation:
            methods: ["GET"]
            paths: ["/api/users", "/api/users/*"]
    - from:
        - source:
            principals: ["cluster.local/ns/default/sa/admin-portal-sa"]
      to:
        - operation:
            methods: ["POST", "DELETE"]
            paths: ["/api/users/*"]
      when:
        - key: request.auth.claims[role]
          values: ["superuser"]
```

**`Терминал`**

```bash
# Применение политики L7 RBAC
kubectl apply -f auth-policy.yaml

# Запрос от авторизованного frontend-sa вернет HTTP 200 OK
kubectl exec -it frontend-pod -- curl -i http://user-service:8080/api/users

# Попытка выполнить POST от неавторизованного клиента вернет HTTP 403
kubectl exec -it rogue-pod -- curl -i -X POST http://user-service:8080/api/users
# HTTP/1.1 403 Forbidden
# content-length: 19
# RBAC: access denied
```

## Под капотом

Envoy sidecar парсит TLS-сертификат входящего mTLS соединения и извлекает SAN URI SPIFFE identity вызывающего сервиса. Если настроена валидация JWT, фильтр `envoy.filters.http.jwt_authn` валидирует подпись токена по открытому ключу JWKS (JSON Web Key Set). Далее фильтр `envoy.filters.http.rbac` сопоставляет SPIFFE ID, метод HTTP, путь и клеймы с таблицей правил `AuthorizationPolicy`. При несоответствии Envoy возвращает клиенту ответ `403 Forbidden` с телом `RBAC: access denied`, даже не передавая байты в Go-приложение.

## Подводные камни

1. Использование `action: ALLOW` без учета health check эндпоинтов: если заблокировать все пути, kubelet не сможет выполнить `livenessProbe` по пути `/healthz`, и контейнер уйдет в бесконечный цикл перезапуска. Всегда явно разрешайте проверки здоровья.
2. Проверка путей с учетом завершающего слеша: путь `/api/users` и `/api/users/` считаются разными путями. Используйте шаблоны с маской `paths: ["/api/users*"]`.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество выноса проверки прав и JWT-токенов в Istio AuthorizationPolicy по сравнению с реализацией middleware внутри Go-кода?»
**Ответ:** 1) Унификация безопасности: единый декларативный аудит политик для всех микросервисов независимо от языка программирования (Go, Java, Python); 2) Защита от DoS-атак: невалидные или вредоносные запросы отсекаются в C++ коде Envoy на раннем этапе, не расходуя CPU, память и горутины целевого Go-приложения; 3) Мгновенное обновление прав без пересборки и деплоя бинарников микросервисов.
