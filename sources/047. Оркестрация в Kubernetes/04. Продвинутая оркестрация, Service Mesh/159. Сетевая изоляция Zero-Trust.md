# Сетевая изоляция Zero-Trust: NetworkPolicy для Ingress и Prometheus

## Условие

**[Network Policies]**: Напиши `NetworkPolicy`, которая запрещает ВСЕ входящие подключения к твоему поду, кроме трафика от Pod'а с Ingress-контроллером и от Prometheus.

## Теория

По умолчанию сеть в Kubernetes полностью открыта (Flat Network): любой Pod из любого namespace может отправлять сетевые пакеты на любой другой Pod. Если злоумышленник скомпрометирует тестовый контейнер, он может беспрепятственно сканировать внутренние порты СУБД или закрытых API.
**NetworkPolicy — межсетевой экран (Firewall) уровня кластера:**
1. **Принцип Default Deny (Запрещено всё, что не разрешено):**
   - Как только на Pod накладывается селектор `podSelector` политики, весь входящий сетевой трафик к нему блокируется ядром Linux на сетевом интерфейсе.
2. **Белые списки (Whitelisting):**
   - Разрешается трафик только от подов с лейблом `app.kubernetes.io/name=ingress-nginx` (пользовательский веб-трафик).
   - Разрешается трафик от подов с лейблом `app=prometheus` строго на порт метрик `:8080` (скрейпинг телеметрии).
3. **Требование к CNI:**
   - NetworkPolicy работают ТОЛЬКО при наличии CNI-плагина с поддержкой сетевой фильтрации (**Cilium**, **Calico**, **Weave Net**). Стандартный Flannel политики НЕ поддерживает!

## Решение по шагам

1. Создайте манифест `network-policy.yaml` с селектором целевого сервиса `app: secured-api`.
2. Задайте `policyTypes: [Ingress]`.
3. Опишите правила `from`: входящий порт 8080 от Ingress Controller и от Prometheus.
4. Примените политику в кластер.
5. Проверьте, что запросы снаружи через Ingress и скрейпинг Prometheus работают, а прямой вызов из другого случайного пода отбрасывается по таймауту.

## Код решения

**`network-policy.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: secured-api-firewall
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: secured-api
  policyTypes:
    - Ingress
  ingress:
    # Правило 1: Разрешить трафик от подов NGINX Ingress Controller
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
          podSelector:
            matchLabels:
              app.kubernetes.io/name: ingress-nginx
      ports:
        - protocol: TCP
          port: 8080

    # Правило 2: Разрешить сбор метрик сервером Prometheus
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
          podSelector:
            matchLabels:
              app.kubernetes.io/name: prometheus
      ports:
        - protocol: TCP
          port: 8080
```

**`Терминал`**

```bash
# Применение политики безопасности
kubectl apply -f network-policy.yaml

# 1. Запрос через легитимный Ingress контроллер проходит успешно (HTTP 200)
curl -H "Host: secured.example.com" http://localhost:80/

# 2. Попытка обратиться к поду напрямую из другого контейнера блокируется по таймауту!
kubectl run attacker-pod --image=curlimages/curl --rm -it -- \
  curl -m 3 http://secured-api.default.svc:8080/
# curl: (28) Connection timed out after 3001 milliseconds
```

## Под капотом

CNI-плагин (например, Calico или Cilium) отслеживает объект `NetworkPolicy` через API K8s. Calico транслирует правила в цепочки Linux `iptables` или `ipset` на узле пода. Cilium компилирует правила в программы eBPF и загружает их в хук `tc` (Traffic Control) виртуального сетевого интерфейса `veth`. Когда входящий пакет приходит на интерфейс, eBPF-программа извлекает IP источника, проверяет его по сопоставлению меток безопасности identity в BPF-карте и отбрасывает пакет (`TC_ACT_SHOT`), если правило не разрешает соединение.

## Подводные камни

1. Использование CNI Flannel: Flannel не реализует интерфейс NetworkPolicy. Манифест успешно создастся в API-сервере, но фильтрация пакетов работать не будет, создавая ложное чувство безопасности!
2. Забытый `namespaceSelector`: если указать только `podSelector`, политика будет искать поды с такой меткой ТОЛЬКО в том же самом namespace, заблокировав Ingress и Prometheus из других пространств имен.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие между записью правил с дефисом и без дефиса в секции `from` манифеста NetworkPolicy?»
**Ответ:** Это критически важная синтаксическая ловушка YAML в Kubernetes:
- **С дефисом (Логическое ИЛИ):**
  ```yaml
  - namespaceSelector: { matchLabels: { env: prod } }
  - podSelector: { matchLabels: { role: client } }
  ```
  Разрешает трафик от **любого** пода в namespace `prod` ИЛИ от подов с лейблом `role: client` в **текущем** namespace.
- **Без дефиса (Логическое И):**
  ```yaml
  - namespaceSelector: { matchLabels: { env: prod } }
    podSelector: { matchLabels: { role: client } }
  ```
  Разрешает трафик **ТОЛЬКО** от подов с лейблом `role: client`, находящихся **СТРОГО** в namespace `prod`!
