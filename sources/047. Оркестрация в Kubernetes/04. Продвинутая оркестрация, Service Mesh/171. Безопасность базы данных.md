# Безопасность базы данных: NetworkPolicy с ограничением доступа по лейблам

## Условие

**Безопасность (Network Policies)**: Напиши `NetworkPolicy`, которая запрещает ЛЮБЫЕ входящие сетевые соединения к поду с твоей базой данных, КРОМЕ подов твоего Go-приложения (фильтрация по меткам/labels).

## Теория

База данных — самый ценный актив компании. Любая компрометация соседнего веб-приложения или тестового пода не должна позволять злоумышленнику подключиться к СУБД.
**Изоляция СУБД через NetworkPolicy:**
1. **Селектор цели:** `podSelector: matchLabels: { role: database }`.
2. **Селектор источника (Ingress Rule):**
   - Разрешается подключение ТОЛЬКО от подов с лейблом `app: backend-service`.
   - Подключение ограничивается строго портом СУБД (например, TCP `:5432` для PostgreSQL).
3. **Защита от внутреннего сканирования:**
   - Все остальные поды кластера (включая поды в том же namespace) при попытке выполнить `psql` или сканирование портов через `nmap` получают бесконечный таймаут (drop packets).

## Решение по шагам

1. Задеплойте PostgreSQL с лейблом `role: database`.
2. Задеплойте Go-бэкенд с лейблом `app: backend-service`.
3. Создайте манифест `NetworkPolicy` с белым списком.
4. Убедитесь, что Go-бэкенд успешно выполняет SQL-запросы.
5. Запустите сторонний тестовый Pod и убедитесь, что подключение к порту 5432 блокируется.

## Код решения

**`postgres-firewall.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: postgres-strict-isolation
  namespace: default
spec:
  podSelector:
    matchLabels:
      role: database
  policyTypes:
    - Ingress
  ingress:
    # Разрешено входящее подключение СТРОГО на порт 5432 и СТРОГО от подов backend-service
    - from:
        - podSelector:
            matchLabels:
              app: backend-service
      ports:
        - protocol: TCP
          port: 5432
```

**`Терминал`**

```bash
# Применение политики межсетевого экрана БД
kubectl apply -f postgres-firewall.yaml

# 1. Проверка соединения из легитимного пода бэкенда (успешно!)
kubectl exec -it backend-service-pod -- nc -zvw3 postgres-service 5432
# Connection to postgres-service 5432 port [tcp/postgresql] succeeded!

# 2. Попытка подключиться к БД из постороннего пода блокируется сетевым экраном!
kubectl run hacker-container --image=busybox --rm -it -- nc -zvw3 postgres-service 5432
# nc: postgres-service (10.96.24.12:5432): Operation timed out
```

## Под капотом

Когда сетевой пакет TCP SYN от `hacker-container` поступает на сетевой стек ноды с БД, CNI-плагин (Calico/Cilium) сопоставляет source IP с таблицей endpoint identities. Поскольку метка `hacker-container` не совпадает с `app: backend-service`, пакет отбрасывается ядром Linux без отправки TCP RST пакета. Инициатор соединения зависает по таймауту сокета (SYN timeout).

## Подводные камни

1. Опечатка в лейбле источника: если указать `app: backend` вместо `app: backend-service`, легитимный микросервис потеряет доступ к базе данных, и приложение упадет.
2. Забытые порты репликации: если база данных работает в кластерном режиме (Patroni/Stolon), изоляция подов базы данных друг от друга сломает потоковую репликацию PostgreSQL (требуется разрешить трафик `from: role: database`).

## На собеседовании

**Вопрос с собеседования:** «Почему сетевой фильтр NetworkPolicy отбрасывает пакеты молча (DROP/TIMEOUT), а не отвечает явной ошибкой сброса соединения (TCP RST/REJECT)?»
**Ответ:** Это фундаментальный принцип информационной безопасности **Stealth Security**: 1) При ответе TCP RST потенциальный атакующий сразу понимает, что хост существует и активен, а порт просто закрыт; 2) При отбрасывании пакетов (DROP) злоумышленник не может отличить неработающий IP-адрес от защищенного, а сканирование портов замедляется в сотни раз из-за ожидания системных таймаутов ядра ОС (1-3 секунды на каждый порт).
