# Локальная разработка: Kind, Tilt, DevSpace и удаленный прокси Telepresence

## Условие

Настрой **Local Development**: `kind` (Kubernetes in Docker) or `k3d` (k3s in Docker). `tilt` or `devspace` for live reload. `telepresence` for remote cluster development. Покажи inner loop optimization.

## Теория

Классический цикл разработки под Kubernetes (Inner Loop) невероятно медленный:
$$\text{Изменение кода} \longrightarrow \text{Сборка Docker-образа} \longrightarrow \text{Push в Registry} \longrightarrow \text{Helm Upgrade} \longrightarrow \text{Перезапуск Pod (1-3 мин)}$$
**Инструменты оптимизации Inner Loop:**
1. **Kind (Kubernetes in Docker):** Поднимает полноценный многоузловой кластер K8s за 30 секунд прямо внутри Docker-контейнеров на ноутбуке.
2. **Tilt / DevSpace (Live Reload):**
   - Отслеживают изменения файлов Go (`*.go`) на диске ноутбука.
   - Вместо полной пересборки Docker-образа они компилируют бинарник локально за секунду и синхронизируют файл напрямую в запущенный контейнер пода (`tilt live_update`).
3. **Telepresence (CNCF):**
   - Подключает локальную машину разработчика к удаленному dev/staging кластеру в облаке.
   - Трафик к удаленному поду перехватывается и направляется на локальный процесс Go в IDE (`localhost:8080`), позволяя отлаживать сервис с брейкпоинтами в реальном окружении!

## Решение по шагам

1. Создайте кластер через `kind create cluster --config kind-config.yaml`.
2. Опишите файл конфигурации `Tiltfile` с правилом `live_update`.
3. Запустите утилиту `tilt up`.
4. Измените строчку кода в Go-файле и убедитесь, что под обновился менее чем за 1.5 секунды без пересборки образа.
5. Продемонстрируйте перехват трафика через Telepresence.

## Код решения

**`kind-config.yaml`**

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 80
        hostPort: 80
        protocol: TCP
  - role: worker
```

**`Tiltfile`**

```python
# Tiltfile: декларативная конфигурация локальной разработки
docker_build(
    'my-go-app',
    '.',
    dockerfile='Dockerfile.dev',
    live_update=[
        # Синхронизируем скомпилированный бинарник прямо в контейнер без ребилда Docker
        sync('./bin/server', '/app/server'),
        run('/app/restart.sh', trigger='./bin/server')
    ]
)

k8s_yaml('deployment.yaml')
k8s_forward('my-go-app', 8080)
```

**`Терминал`**

```bash
# 1. Запуск локального кластера
kind create cluster --config kind-config.yaml

# 2. Запуск Tilt для мгновенного live-reload
tilt up

# 3. Подключение к удаленному кластеру через Telepresence
telepresence connect

# 4. Перехват трафика микросервиса payment-service на локальный порт 8080 в GoLand/VSCode
telepresence intercept payment-service --port 8080:8080
```

## Под капотом

Tilt отслеживает изменения в файловой системе через библиотеку `fsnotify`. При изменении файла Tilt запускает быстрый локальный `go build -o ./bin/server .` (200 мс благодаря инкрементальному кэшу Go). Затем через API `tar stream` в рантайме CRI Tilt подменяет бинарник в файловой системе контейнера и отправляет сигнал `SIGHUP` процессу для мгновенного перезапуска без пересоздания Pod'а.

## Подводные камни

1. Забытый `.dockerignore`: без него Tilt попытается синхронизировать локальную директорию `.git` или тяжелые артефакты сборки внутрь контейнера.
2. Конфликт версий Go: если локально на ноутбуке установлен Go 1.23, а базовый образ контейнера скомпилирован под другие glibc библиотеки, запущенный бинарник упадет с ошибкой динамического линковщика. Используйте статическую сборку `CGO_ENABLED=0`.

## На собеседовании

**Вопрос с собеседования:** «Как Telepresence позволяет разработчику тестировать микросервис в облачном кластере без необходимости разворачивать на ноутбуке тяжелые зависимости (Kafka, PostgreSQL, Redis)?»
**Ответ:** Telepresence устанавливает двунаправленный сетевой туннель между ноутбуком и кластером: 1) Он внедряет специальный sidecar-агент `traffic-agent` в удаленный Pod микросервиса; 2) Все входящие запросы из кластера агент перенаправляет по VPN-туннелю на локальный процесс в IDE разработчика; 3) Все исходящие сетевые вызовы от локального приложения прозрачно маршрутизируются в кластерную сеть K8s, позволяя коду обращаться к кластерным сервисам по их внутренним именам (`postgres.default.svc.cluster.local`) прямо с локальной машины.
