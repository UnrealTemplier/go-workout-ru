# Культура наблюдаемости: Observability как обязательная часть релиза

## Условие

**Observability in Production**: если нельзя наблюдать — нельзя управлять. Metrics, logs, traces, alerts, runbooks — часть deployment, не после.

## Теория

Принцип «Если вы не можете наблюдать за системой, вы не можете ей управлять» (Lord Kelvin / SRE Best Practice):
1. **Сдвиг парадигмы (Observability-Driven Development):**
   - Метрики, структурированные логи, распределенные трейсы и инструкции по устранению инцидентов (**Runbooks**) являются такой же обязательной частью релиза, как сам исходный код и unit-тесты.
   - Микросервис не допускается в продакшен (Production Readiness Review), если для него не настроены:
     1. Дашборд 4 золотых сигналов (Latency, Traffic, Errors, Saturation).
     2. Health-check эндпоинты (`/livez`, `/readyz`).
     3. Алерты с прямыми ссылками на Runbook в документации.
2. **Анатомия Runbook (Плейбука реагирования):**
   - Описание симптомов («Высокий процент 5xx на роуте `/checkout`»).
   - Первые шаги локализации («Проверить метрики пула соединений с PostgreSQL»).
   - Аварийные команды восстановления («Откат релиза через ArgoCD / Включение degraded mode через Feature Flag»).

## Решение по шагам

1. Опишите стандарт Production Readiness для команды.
2. Добавьте в манифест `PrometheusRule` обязательную аннотацию `runbook_url`.
3. Напишите базовый Runbook по диагностике инцидента.
4. Убедитесь в наличии сквозной телеметрии в Go-коде.

## Код решения

**`alert-with-runbook.yaml`**

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: order-service-alerts
  namespace: monitoring
spec:
  groups:
    - name: order-service.rules
      rules:
        - alert: OrderServiceHighLatency
          expr: histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{app="order-service"}[5m])) by (le)) > 0.5
          for: 3m
          labels:
            severity: warning
          annotations:
            summary: "Задержка p99 превышает 500мс в order-service"
            runbook_url: "https://wiki.corp.internal/runbooks/order-service-latency" 
```

**`runbook-order-latency.md`**

```markdown
# Runbook: Устранение высокой задержки в Order Service

## Описание инцидента
Время обработки запросов p99 превысило 500 мс в течение 3 минут.

## Быстрый чеклист дежурного инженера:
1. **Проверить дашборд PostgreSQL:**
   - Открыть Grafana -> `Postgres Overview`.
   - Проверить наличие долгих блокировок: `SELECT * FROM pg_stat_activity WHERE state != 'idle';`
2. **Проверить насыщение CPU подов:**
   - `kubectl top pods -l app=order-service -n production`
   - Если CPU > 90%, временно смасштабировать: `kubectl scale deployment order-service --replicas=10`
3. **Проверить трассировку в Jaeger:**
   - Найти трейсы с длительностью > 500мс, определить проблемный downstream-вызов.
```

## Под капотом

Когда Alertmanager получает Firing-алерт, он подставляет аннотацию `runbook_url` в тело сообщения Slack / PagerDuty. Дежурный инженер по клику переходит на точную инструкцию с готовыми командами расследования, что сокращает показатель MTTA (Mean Time to Acknowledge) и MTTR (Mean Time to Resolve) с десятков минут до нескольких секунд.

## Подводные камни

1. Алерты без Runbook: дежурный инженер ночью вынужден в панике исследовать исходный код или искать виноватых, пока пользователи сталкиваются с отказами.
2. Устаревшие Runbook: если инструкции не актуализируются при изменении архитектуры, они могут привести к неверным действиям во время аварии.

## На собеседовании

**Вопрос с собеседования:** «Что такое четыре «золотых сигнала» (Four Golden Signals) SRE от Google и почему они критичны для микросервисов?»
**Ответ:** Четыре золотых сигнала — это: 1) **Latency (Задержка):** время ответа на запросы, разделенное на успешные и ошибочные; 2) **Traffic (Трафик):** мера объема спроса (RPS для HTTP/gRPC, IOPS для хранилищ); 3) **Errors (Ошибки):** частота сбоев (явных HTTP 5xx, неявных ошибок бизнес-логики, таймаутов); 4) **Saturation (Насыщение):** степень заполнения самых узких ресурсов системы (очереди запросов, заполненность пула потоков/памяти/CPU). Мониторинг этих четырех параметров покрывает 95% критических проблем надежности сервиса.
