# Сбор распределенных трейсов: OpenTelemetry Collector и экспорт в Jaeger

## Условие

**[OpenTelemetry Collector]**: Установи OTel Collector в K8s. Настрой Go-приложение на отправку трейсов на адрес `otel-collector:4317`. Collector должен пересылать трейсы в Jaeger.

## Теория

Вместо прямой привязки кода микросервисов к конкретной системе хранения трейсов (Jaeger, Zipkin, Datadog) индустриальным стандартом стал **OpenTelemetry (OTel)**:
1. **Преимущества OTel Collector (Vendor-Agnostic):**
   - Go-микросервис отправляет трейсы по стандартному протоколу **OTLP (OpenTelemetry Protocol)** через gRPC на порт 4317.
   - Код приложения вообще ничего не знает о том, где хранятся трейсы.
   - Сам OTel Collector работает в кластере как шлюз (Gateway), фильтрует, обогащает метаданными и пересылает спаны в любой бэкенд (Jaeger, Tempo, Elastic).
2. **Архитектура OTel пайплайна:**
   $$\text{Go App (OTLP)} \longrightarrow \text{Receivers} \longrightarrow \text{Processors (batch, memory)} \longrightarrow \text{Exporters} \longrightarrow \text{Jaeger}$$

## Решение по шагам

1. Разверните Jaeger в кластере.
2. Создайте манифест `OpenTelemetryCollector` с OTLP receiver и Jaeger exporter.
3. Напишите Go-микросервис, инициализирующий OpenTelemetry TracerProvider.
4. Отправьте спаны на `otel-collector.default.svc:4317`.
5. Откройте интерфейс Jaeger и найдите сформированную трассировку.

## Код решения

**`otel-collector.yaml`**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: otel-collector-config
data:
  config.yaml: |
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
    processors:
      batch:
        timeout: 1s
        send_batch_size: 256
      memory_limiter:
        check_interval: 1s
        limit_percentage: 75
        spike_limit_percentage: 20
    exporters:
      otlp:
        endpoint: jaeger-collector:4317
        tls:
          insecure: true
    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [otlp]
```

**`main.go`**

```go
package main

import (
	"context"
	"log"
	"net/http"
	"time"

	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
	"go.opentelemetry.io/otel/sdk/resource"
	sdktrace "go.opentelemetry.io/otel/sdk/trace"
	semconv "go.opentelemetry.io/otel/semconv/v1.21.0"
	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

func initTracer(ctx context.Context) (*sdktrace.TracerProvider, error) {
	// Подключение к кластерному агенту OpenTelemetry Collector по gRPC
	exporter, err := otlptracegrpc.New(ctx,
		otlptracegrpc.WithEndpoint("otel-collector.default.svc:4317"),
		otlptracegrpc.WithTLSCredentials(insecure.NewCredentials()),
		otlptracegrpc.WithDialOption(grpc.WithBlock()),
	)
	if err != nil {
		return nil, err
	}

	res, err := resource.New(ctx,
		resource.WithAttributes(
			semconv.ServiceNameKey.String("checkout-service"),
			semconv.ServiceVersionKey.String("1.0.0"),
		),
	)
	if err != nil {
		return nil, err
	}

	tp := sdktrace.NewTracerProvider(
		sdktrace.WithBatcher(exporter),
		sdktrace.WithResource(res),
	)
	otel.SetTracerProvider(tp)
	return tp, nil
}

func main() {
	ctx := context.Background()
	tp, err := initTracer(ctx)
	if err != nil {
		log.Printf("Предупреждение: OTel недоступен, работаем без трейсинга: %v", err)
	} else {
		defer func() { _ = tp.Shutdown(ctx) }()
	}

	tracer := otel.Tracer("checkout-tracer")

	http.HandleFunc("/checkout", func(w http.ResponseWriter, r *http.Request) {
		reqCtx, span := tracer.Start(r.Context(), "ProcessCheckoutTransaction")
		defer span.End()

		time.Sleep(100 * time.Millisecond) // Имитация обработки
		_ = reqCtx

		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("Order processed"))
	})

	log.Println("Сервер слушает на :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Go SDK OTel аккумулирует спаны в кольцевом буфере в оперативной памяти. Фоновый воркер `BatchSpanProcessor` раз в секунду сериализует спаны в бинарный формат Protobuf и шлет их по HTTP/2 gRPC стриму в OTel Collector. Коллектор пропускает спаны через фильтры процессоров и направляет их в экспортер Jaeger без разрыва контекста трейсинга.

## Подводные камни

1. Синхронная отправка спанов (`SimpleSpanProcessor` вместо `BatchSpanProcessor`): превратит каждый сетевой запрос приложения в блокирующий вызов к OTel Collector, увеличив latency микросервиса в десятки раз! Всегда используйте батчинг.
2. Забытый вызов `defer tp.Shutdown(ctx)`: при завершении процесса Go недоотправленные спаны из буфера будут потеряны.

## На собеседовании

**Вопрос с собеседования:** «Зачем устанавливать OpenTelemetry Collector внутри кластера, если Go SDK может отправлять трейсы напрямую в облачные сервисы (Datadog, Dynatrace)?»
**Ответ:** 1) **Разгрузка микросервисов:** Сжатие данных, батчинг, шифрование и фильтрация спанов выносятся из процесса Go в отдельный легковесный прокси-агент; 2) **Централизованный контроль затрат (Cost Control):** Коллектор позволяет динамически менять процент сэмплирования (Head/Tail Sampling) и отрезать спаны healthcheck-эндпоинтов для всех микросервисов без изменения их кода; 3) **Исключение vendor-lock:** Смена бэкенда мониторинга сводится к правке пяти строк в конфигурации OTel Collector.
