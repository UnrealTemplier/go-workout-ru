# Cloud-Native бессерверный запуск: AWS ECS Fargate и Google Cloud Run

## Условие

Подготовьте приложение к запуску в облаке (AWS ECS или GCP Cloud Run): создайте соответствующий конфигурационный файл (task definition / service.yaml).

## Теория

Хотя Kubernetes является стандартом де-факто для сложных платформ, многие микросервисы эффективнее запускать в бессерверных (Serverless Container) средах: **AWS ECS Fargate** или **Google Cloud Run (Knative-based)**:
1. **Преимущества Serverless Containers:**
   - **Zero Node Management:** Нет виртуальных машин (EC2), нет необходимости обновлять ОС, патчить ядро или настраивать Cluster Autoscaler.
   - **Scale-to-Zero:** При отсутствии входящего HTTP-трафика количество контейнеров масштабируется до 0, снижая затраты на инфраструктуру до нуля (в Cloud Run).
   - **Оплата посекундно:** плата взимается только за фактическое время исполнения запросов.
2. **Форматы конфигураций:**
   - **AWS ECS:** JSON-файл `Task Definition` (контейнеры, порты, CPU/RAM, IAM роли).
   - **Google Cloud Run:** Декларативный YAML стандарта **Knative Serving** (`serving.knative.dev/v1`).

## Решение по шагам

1. Создайте манифест спецификации Knative / Google Cloud Run `service.yaml`.
2. Настройте автоматическое масштабирование от 0 до 10 инстансов.
3. Задайте ограничения ресурсов: 1 vCPU и 512 MiB памяти.
4. Создайте спецификацию AWS ECS Task Definition в формате JSON.
5. Продемонстрируйте развертывание контейнера через облачный CLI.

## Код решения

**`cloud-run-service.yaml`**

```yaml
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: cloud-run-api
  annotations:
    run.googleapis.com/ingress: all
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: "0"  # Скейл в ноль при отсутствии нагрузки
        autoscaling.knative.dev/maxScale: "10" # Ограничение затрат
        run.googleapis.com/cpu-throttling: "true"
    spec:
      containerConcurrency: 80 # До 80 параллельных запросов на один контейнер
      containers:
        - image: gcr.io/my-cloud-project/api:v1.0.0
          ports:
            - containerPort: 8080
          resources:
            limits:
              cpu: "1000m"
              memory: 512Mi
          env:
            - name: APP_MODE
              value: "serverless
```

**`ecs-task-definition.json`**

```json
{
  "family": "payment-api-task",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "256",
  "memory": "512",
  "executionRoleArn": "arn:aws:iam::123456789012:role/ecsTaskExecutionRole",
  "containerDefinitions": [
    {
      "name": "payment-api",
      "image": "123456789012.dkr.ecr.eu-west-1.amazonaws.com/payment:v1",
      "essential": true,
      "portMappings": [
        {
          "containerPort": 8080,
          "protocol": "tcp"
        }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/payment-api",
          "awslogs-region": "eu-west-1",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
```

**`Терминал`**

```bash
# Развертывание сервиса в Google Cloud Run одной командой
gcloud run services replace cloud-run-service.yaml --region=europe-west1

# Регистрация новой задачи в AWS ECS
aws ecs register-task-definition --cli-input-json file://ecs-task-definition.json
```

## Под капотом

В Google Cloud Run и Knative перед контейнером находится высокоскоростной роутер-балансировщик (Activator). Если количество активных реплик равно 0, первый входящий TCP-запрос перехватывается Активатором, который за 100-300 мс инициирует холодный старт контейнера (gVisor sandbox) и передает HTTP-запрос по готовности. AWS Fargate аллоцирует виртуальную микро-ВМ (Firecracker microVM) под каждый таск в выделенном VPC.

## Подводные камни

1. Проблема холодного старта (Cold Start): тяжелые монолиты на Java со временем старта 30 секунд непригодны для Scale-to-Zero. Go-микросервисы со статическим бинарником стартуют за 20–50 мс, являясь идеальным кандидатом для Cloud Run.
2. Файловая система: локальный диск в Serverless контейнерах эфемерен (RAM disk `tmpfs`). Любые постоянные данные обязаны сохраняться в облачные базы данных или S3 бакеты.

## На собеседовании

**Вопрос с собеседования:** «Когда архитектурно выгоднее выбрать AWS ECS Fargate / Google Cloud Run вместо полноценного кластера Kubernetes (EKS/GKE)?»
**Ответ:** Serverless контейнеры предпочтительнее: 1) Для небольших команд без выделенного штата DevOps/SRE-инженеров; 2) Для сервисов с неравномерным трафиком (периодические вебхуки, ночные пакетные задачи), где функция **Scale-to-Zero** экономит до 90% бюджета по сравнению с постоянной оплатой работающих нод K8s; 3) Для изоляции сверхчувствительных задач в отдельных secure sandboxes (gVisor/Firecracker).
