# Стратегия развертывания Recreate: несовместимые миграции и Singleton-воркеры

## Условие

**Recreate**: Используйте для приложений, которые не могут работать в нескольких версиях одновременно (например, с несовместимыми миграциями БД).

## Теория

Хотя `RollingUpdate` является стандартом по умолчанию, существуют сценарии, в которых параллельная работа старой (v1) и новой (v2) версий сервиса **категорически недопустима**:
1. **Сценарии применения `strategy.type: Recreate`:**
   - **Несовместимые (Breaking) миграции базы данных:** Новая версия кардинально меняет структуру таблиц, удаляя старые колонки. Если старый код попытается писать в измененную таблицу, произойдет порча данных.
   - **Singleton-воркеры (Single-Writer):** Приложения, работающие с эксклюзивными блокировками (например, процесс, монопольно читающий последовательный стрим из внешнего сокета).
   - **Тома с доступом `ReadWriteOnce`:** Если том AWS EBS не может быть примонтирован одновременно на два разных узла во время обновления.
2. **Механика Recreate:**
   - Все работающие поды старой версии **принудительно останавливаются до 0**.
   - Только после полного завершения старых подов контроллер начинает создавать поды новой версии.
   - **Платой за безопасность является неизбежный кратковременный даунтайм** (Downtime) на время перезапуска.

## Решение по шагам

1. Создайте манифест `Deployment` со стратегией `strategy.type: Recreate`.
2. Запустите приложение в кластере.
3. Обновите образ контейнера.
4. Пронаблюдайте за последовательностью через `kubectl get pods -w`: поды сначала полностью гасятся (`Terminating`), и лишь затем поднимаются новые.

## Код решения

**`deployment-recreate.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: legacy-billing-sync
  namespace: default
spec:
  replicas: 2
  strategy:
    type: Recreate # Все старые поды убиваются ДО старта новых
  selector:
    matchLabels:
      app: billing-sync
  template:
    metadata:
      labels:
        app: billing-sync
    spec:
      containers:
        - name: sync
          image: billing-sync:v2.0.0
          ports:
            - containerPort: 8080
```

**`Терминал`**

```bash
# Применение манифеста
kubectl apply -f deployment-recreate.yaml

# Обновление тега образа
kubectl set image deployment/legacy-billing-sync sync=billing-sync:v2.1.0

# Наблюдение за жизненным циклом (число подов падает до 0, затем поднимается)
kubectl get pods -l app=billing-sync -w
# legacy-billing-sync-5d8f7-9h8ks   1/1   Terminating   0   40s
# legacy-billing-sync-5d8f7-lp2ds   1/1   Terminating   0   40s
# (В этот момент подов нет - даунтайм 5-10 секунд)
# legacy-billing-sync-7a91b-4f2ja   0/1   Pending       0   0s
# legacy-billing-sync-7a91b-4f2ja   1/1   Running       0   3s
```

## Под капотом

`deployment-controller` считывает директиву `strategy.type: Recreate`. При изменении шаблона спецификации пода контроллер сначала устанавливает `spec.replicas: 0` для текущего ReplicaSet и ожидает подтверждения от Kubelet, что все контейнеры уничтожены. Только когда счетчик активных подов становится равен нулю, контроллер создает новый ReplicaSet с желаемым количеством реплик.

## Подводные камни

1. Использование Recreate для клиентских веб-сервисов: пользователи получат ошибки `502 Bad Gateway` во время простоя сервиса. Для сервисов с пользователями следует избегать ломающих миграций, применяя паттерн **Expand and Contract** (двухфазные миграции).
2. Зависший Graceful Shutdown: если старый под зависает при выходе на 30 секунд (`terminationGracePeriodSeconds`), даунтайм сервиса увеличится на эти же 30 секунд.

## На собеседовании

**Вопрос с собеседования:** «Как избежать необходимости использовать стратегию Recreate при изменении схемы реляционной базы данных?»
**Ответ:** Применяется архитектурный паттерн **Expand and Contract (Разделяй и властвуй)**:
1. **Фаза Expand (Релиз 1):** Добавляется новая колонка/таблица в БД, не удаляя старую. Код пишет в обе колонки, но читает из старой. База обратно совместима со старым кодом. Выполняется штатный `RollingUpdate` без даунтайма.
2. **Фаза Data Migration:** Фоновый воркер переносит исторические данные в новую структуру.
3. **Фаза Switch (Релиз 2):** Новый код переключается на чтение из новой колонки.
4. **Фаза Contract (Релиз 3):** Старая колонка безопасно удаляется из схемы БД. Сервис ни на секунду не прерывает работу.
