# Стресс-тестирование и Chaos Engineering: подтверждение Zero-Downtime под хаосом

## Условие

**[Zero-Downtime Deployment & Chaos]**
- Настрой CI/CD пайплайн, который собирает образ и обновляет Helm-чарт.
- ArgoCD разворачивает новую версию с использованием `RollingUpdate` (`maxSurge: 1`, `maxUnavailable: 0`).
- Во время деплоя запусти скрипт, который постоянно делает HTTP-запросы к API Gateway.
- **Критерий успеха:** В процессе обновления подов не должно быть ни одной 5xx ошибки или таймаута (благодаря Graceful Shutdown, readiness probes и preStop hooks).
- **[Chaos Engineering]:** Используй `litmuschaos` или просто удаляй случайные поды (`kubectl delete pod -l app=user-service`). Убедись, что система остается доступной (показывает resilient behavior).

## Теория

Единственный способ доказать надежность системы — проверить ее в условиях хаоса и непредвиденных сбоев (**Chaos Engineering / Principles of Chaos**):
1. **Методика стресс-тестирования нулевого даунтайма:**
   - На сервис подается непрерывный входящий трафик (100–500 RPS).
   - Одновременно инициируется Rolling Update новой версии приложения.
   - Параллельно хаос-генератор (скрипт или LitmusChaos/Chaos Mesh) принудительно убивает случайные поды (`kubectl delete pod --now`).
2. **Критерий устойчивости (Resilience):**
   - Ни один HTTP-запрос клиента не должен вернуть статус-код `500`, `502`, `503`, `504` или сетевой таймаут.
   - Задержка p99 не должна деградировать более чем на 20%.

## Решение по шагам

1. Запустите микросервис с `maxSurge: 1`, `maxUnavailable: 0`, `readinessProbe` и `preStop: sleep 10`.
2. Запустите фоновый генератор запросов, фиксирующий коды ошибок.
3. Запустите цикл случайного удаления подов каждые 3 секунды.
4. Выполните обновление версии образа в Deployment.
5. Проанализируйте итоговый отчет: количество ошибок обязано быть строго равно 0.

## Код решения

**`chaos-test.sh`**

```bash
#!/bin/bash
set -euo pipefail

TARGET_URL="http://gateway.production.company.internal/api/ping"
TOTAL_REQUESTS=1000
ERRORS_COUNT=0

echo "1. Запуск генератора непрерывного трафика ($TOTAL_REQUESTS запросов)..."
traffic_generator() {
  for i in $(seq 1 $TOTAL_REQUESTS); do
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" --connect-timeout 2 "$TARGET_URL" || echo "FAIL")
    if [ "$STATUS" != "200" ]; then
      echo "❌ СБОЙ ЗАПРОСА #$i: HTTP Статус: $STATUS"
      ((ERRORS_COUNT++)) || true
    fi
    sleep 0.02
  done
}

traffic_generator &
TRAFFIC_PID=$!

echo "2. Инициация Rolling Update на версию v2.0.0..."
kubectl set image deployment/user-service app=user-service:v2.0.0

echo "3. Внедрение хаоса: принудительное уничтожение случайных подов во время обновления..."
for k in {1..5}; do
  RANDOM_POD=$(kubectl get pods -l app=user-service -o jsonpath='{.items[0].metadata.name}')
  echo "🔥 CHAOS: Убийство пода $RANDOM_POD..."
  kubectl delete pod "$RANDOM_POD" --grace-period=0 --force > /dev/null 2>&1 || true
  sleep 3
done

# Ожидание окончания трафика
wait $TRAFFIC_PID

echo "=========================================="
echo "ИТОГОВЫЙ РЕЗУЛЬТАТ СТРЕСС-ТЕСТИРОВАНИЯ:"
echo "Всего запросов: $TOTAL_REQUESTS"
echo "Ошибок (5xx/Timeouts): $ERRORS_COUNT"
echo "=========================================="

if [ "$ERRORS_COUNT" -eq 0 ]; then
  echo "🏆 ИДЕАЛЬНО: 100% Zero-Downtime подтвержден в боевых условиях хаоса!"
  exit 0
else
  echo "💥 ПРОВАЛ: Зафиксированы ошибки клиентов во время релиза!"
  exit 1
fi
```

## Под капотом

Устойчивость достигается благодаря взаимодействию трех уровней: 1) Резервирование: PDB гарантирует, что хаос-скрипт не может выбить больше допустимого процента реплик; 2) Балансировщик: при удалении пода `kubelet` шлет запрос на вывод из `Endpoints` до уничтожения контейнера; 3) Клиентский ретрай: если запрос застрял в закрывающемся TCP сокете, пограничный Ingress/Envoy выполняет прозрачный повтор (L7 Retry) на соседний готовый Pod.

## Подводные камни

1. Тестирование с 1 репликой пода: при `replicas: 1` любое падение пода неизбежно приведет к 100% даунтайму на время подъема нового контейнера. В production ВСЕГДА должно быть минимум 2-3 реплики сервиса.
2. Отсутствие PDB: хаос-инструмент может случайно удалить вообще все поды одновременно.

## На собеседовании

**Вопрос с собеседования:** «Что такое Chaos Monkey и почему компании вроде Netflix и Яндекс намеренно убивают серверы и поды на боевом продакшене в рабочее время?»
**Ответ:** Это концепция **управляемого хаоса**: если сбой в распределенной системе неизбежен (выход из строя диска, падение ноды, сетевое разделение дата-центров), лучше инициировать эти сбои регулярно в дневное время, когда вся инженерная команда находится на рабочих местах и готова реагировать. Это гарантирует, что архитектура сервисов, механизмы автовосстановления, circuit breakers и ретраи реально работают в боевых условиях, исключая катастрофические ночные инциденты.
