# Эталонный сквозной CI/CD конвейер: от Git Push до Argo Rollouts Canary

## Условие

Спроектируй **полный production pipeline**:
- Developer pushes code → GitHub Actions: lint, test, build, scan
- Merge to `main` → build Docker image, push to registry, update Helm chart
- ArgoCD detects change → sync to staging cluster
- Automated tests in staging → promote to production
- Argo Rollouts: canary 1% → 10% → 50% → 100%
- Monitoring: SLO verification, automatic rollback on degradation
- Incident response: PagerDuty, runbook, post-mortem

## Теория

Архитектура промышленного сквозного конвейера доставки программного обеспечения уровня BigTech:
1. **Фаза CI (Continuous Integration):**
   - Push ветки: `golangci-lint`, модульные тесты (`go test -race`), Trivy сканирование зависимостей.
   - Merge в `main`: Сборка мульти-архитектурного Distroless-образа, генерация SBOM (Software Bill of Materials), подпись образа ключом Cosign, пуш в OCI Registry.
   - Коммит нового тега в отдельный Git-репозиторий манифестов (`gitops-manifests`).
2. **Фаза CD (Continuous Delivery через ArgoCD):**
   - Автоматический синк в Staging-кластер \(\rightarrow\) запуск E2E тестов.
3. **Прогрессивная доставка (Progressive Delivery через Argo Rollouts):**
   - Деплой на Production в режиме **Canary**:
     - Шаг 1: переключение 1% реального трафика \(\rightarrow\) анализ метрик в течение 10 минут.
     - Шаг 2: переключение 10% \(\rightarrow\) верификация SLO (частота ошибок < 0.1%, задержка p99 < 150 мс).
     - Шаг 3: переключение 50% \(\rightarrow\) 100%.
   - **Автоматический откат:** При малейшей деградации метрик Argo Rollouts мгновенно возвращает 100% трафика на старую версию и отправляет алерт в PagerDuty.

## Решение по шагам

1. Составьте архитектурную диаграмму пайплайна.
2. Опишите манифест `Rollout` с шагами канареечного релиза.
3. Опишите `AnalysisTemplate` с проверкой Prometheus SLO.
4. Продемонстрируйте реакцию системы на деградацию метрик.

## Код решения

**`pipeline-architecture.txt`**

```text
[ Developer ]
      │  git push feature-branch
      ▼
[ GitHub Actions CI ] ──> golangci-lint ──> go test -race ──> trivy scan
      │  Pull Request Approved & Merged to main
      ▼
[ Image Build & Sign ] ──> Docker Build ──> Cosign Sign ──> Push to GHCR
      │  Bot commits new image tag to GitOps Repo
      ▼
[ ArgoCD GitOps ] ──────> Sync to Staging ──> Automated E2E Tests Passed
      │  Promote to Production Cluster
      ▼
[ Argo Rollouts Canary ]
      ├── 1% Traffic   ──> Verify SLO (Error rate < 0.1%)
      ├── 10% Traffic  ──> Verify SLO (p99 latency < 120ms)
      ├── 50% Traffic  ──> Verify SLO
      └── 100% Traffic ──> Promotion Complete! (Zero Downtime)
      ▲
      │ (If SLO degraded: Automatic Abort & Instant Rollback)
```

**`rollout.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: core-payment-service
spec:
  replicas: 10
  strategy:
    canary:
      analysis:
        templates:
          - templateName: success-rate-slo
        args:
          - name: service-name
            value: core-payment-service
      steps:
        - setWeight: 1
        - pause: {duration: 5m}
        - setWeight: 10
        - pause: {duration: 10m}
        - setWeight: 50
        - pause: {duration: 10m}
  selector:
    matchLabels:
      app: core-payment-service
  template:
    metadata:
      labels:
        app: core-payment-service
    spec:
      containers:
        - name: app
          image: ghcr.io/my-corp/payment:v2.4.0
          ports:
            - containerPort: 8080
```

**`analysis-template.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate-slo
spec:
  metrics:
    - name: success-rate
      interval: 30s
      successCondition: result[0] >= 0.999 # Требование SLO: 99.9% успешных ответов
      failureLimit: 3
      provider:
        prometheus:
          address: http://prometheus-k8s.monitoring.svc:9090
          query: |
            sum(rate(http_requests_total{app="core-payment-service", status=~"2.."}[1m]))
            /
            sum(rate(http_requests_total{app="core-payment-service"}[1m]))
```

## Под капотом

Контроллер Argo Rollouts замещает стандартный Deployment. На каждом шаге `setWeight: 10` контроллер настраивает Service Mesh (Istio VirtualService или Ingress NGINX traffic-split), перенаправляя ровно 10% пользовательских сетевых пакетов на канареечные поды. Фоновый воркер анализа непрерывно опрашивает Prometheus. Если `successCondition` возвращает false более 3 раз, контроллер переводит статус в `Degraded`, мгновенно сбрасывает вес канарейки в 0% и восстанавливает стабильную версию.

## Подводные камни

1. Отсутствие прогрева канареечных подов: если переключить 10% нагрузки на поды с холодными кэшами, это может вызвать кратковременный всплеск задержек и ложное срабатывание отката.
2. Недостаточный объем трафика на первом шаге: при 1% трафика и общем потоке 10 RPS на канарейку попадет всего 0.1 запроса/сек — метрика будет статистически недостоверной.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных высоконагруженных распределенных системах канареечный релиз (Canary Deployment) полностью вытеснил традиционный Rolling Update?»
**Ответ:** При обычном Rolling Update новая версия раскатывается по подам без проверки бизнес-логики: если в новом коде есть баг, вызывающий сбой при обработке платежей, но приложение проходит технический Readiness Probe (сокет открыт, кэш загружен), Rolling Update успешно заменит 100% подов и сломает всю систему. **Canary с автоматическим анализом SLO** сначала тестирует новую версию на малом проценте реальных клиентов и автоматически откатывает деплой при малейшем росте 5xx ошибок, защищая 99% пользователей от сбоев.
