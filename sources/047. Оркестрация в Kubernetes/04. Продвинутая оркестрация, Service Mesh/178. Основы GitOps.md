# Основы GitOps: безопасность кластера и устранение учетных данных из CI

## Условие

**Основы GitOps (Взгляд в будущее)**: Ручной `kubectl apply` или деплой прямо из GitHub Actions считается устаревающим подходом. Установи в кластер (локально) **ArgoCD**. Скажи ему следить за твоим Git-репозиторием с YAML-манифестами. Измени количество реплик прямо в Гитхабе, закоммить. Увидь, как ArgoCD заметит изменение в Git и сам синхронизирует состояние твоего кластера, не требуя никаких секретов кластера в самом GitHub!

## Теория

Фундаментальная революция GitOps в сравнении с классической Push-моделью CI/CD:
1. **Проблема классического CI Push (GitLab CI / GitHub Actions):**
   - Чтобы CI мог сделать `kubectl apply`, в переменные GitHub (`secrets.KUBECONFIG`) необходимо положить административный сертификат или токен доступа к кластеру.
   - Любая компрометация стороннего экшена, уязвимость в зависимостях npm/pip или утечка логов сборки передает злоумышленникам полный контроль над боевым кластером!
2. **Безопасность GitOps Pull (ArgoCD):**
   - **GitHub вообще ничего не знает о кластере Kubernetes!** В GitHub нет ни одного секрета или сертификата доступа к кластеру.
   - Кластер полностью закрыт файрволом из интернета на входящие соединения.
   - Агент ArgoCD работает внутри защищенного периметра кластера и сам инициирует исходящие HTTPS-запросы к GitHub для чтения манифестов.
3. Достаточно изменить строчку в файле на GitHub (`replicas: 5`) и нажать `Commit`, чтобы кластер синхронизировался без единого секрета в CI!

## Решение по шагам

1. Удалите `kubeconfig` из переменных GitHub Secrets.
2. Настройте ArgoCD на чтение публичного или приватного репозитория с манифестами.
3. Отредактируйте `deployment.yaml` прямо в веб-интерфейсе GitHub: увеличьте `replicas: 3`.
4. Закоммитьте изменение в ветку `main`.
5. Наблюдайте в консоли ArgoCD за автоматическим поднятием новых реплик.

## Код решения

**`push-vs-pull-security.md`**

```markdown
| Характеристика | Традиционный CI Push (GitHub Actions) | GitOps Pull (ArgoCD) |
| :--- | :--- | :--- |
| **Где хранятся секреты кластера** | В переменных CI (GitHub Secrets) — высокий риск утечки! | Внутри кластера в etcd — безопасность закрытого контура |
| **Входящие порты API кластера** | Должен быть открыт наружу в публичный интернет | Полностью закрыт (No Inbound Firewall Ports) |
| **Аудит изменений** | Размыт по логам сотен запусков пайплайнов | Строгий криптографический Git Log |
| **Самоисцеление (Self-Healing)** | Отсутствует | Автоматическое (откат ручных правок за секунды) |
```

**`Терминал`**

```bash
# Проверка того, что в GitHub репозитории нет kubeconfig секретов
# Единственное, что связывает систему - декларативный манифест Application:
kubectl get application my-microservice -n argocd -o yaml | grep -A 4 "source:"
# repoURL: https://github.com/my-org/manifests.git
# targetRevision: main
# path: apps/my-microservice

# После коммита в GitHub смотрим автоматическую реакцию ArgoCD:
kubectl get pods -l app=my-microservice -w
```

## Под капотом

ArgoCD запускает фоновый процесс `git ls-remote` каждые 180 секунд (или мгновенно реагирует на входящий webhook от GitHub). При изменении SHA коммита ветки `main` контроллер считывает абстрактное синтаксическое дерево (AST) манифестов, находит разницу в поле `spec.replicas` и отправляет вызов `Patch` в локальный API-сервер `https://kubernetes.default.svc`.

## Подводные камни

1. Ручные правки в кластере без отключения auto-sync: инженер меняет количество подов через `kubectl scale`, а ArgoCD через минуту сбрасывает их обратно, вызывая замешательство.
2. Задержка поллинга без Webhook: по умолчанию ArgoCD проверяет Git раз в 3 минуты. Для мгновенной синхронизации обязательно настраивайте Webhook в GitHub/GitLab.

## На собеседовании

**Вопрос с собеседования:** «Почему отдел информационной безопасности (ИБ) в банках и финтехе настаивает на переходе от прямого деплоя из GitLab Runner к GitOps (ArgoCD)?»
**Ответ:** Главный аргумент — **минимизация поверхности атаки (Attack Surface Reduction)**. При Push-модели раннеры CI имеют права `cluster-admin`. Если злоумышленник скомпрометирует репозиторий кода или сторонний плагин в CI, он получает полный доступ к банковской базе данных в кластере. В модели GitOps CI-раннеры вообще не имеют доступа к кластеру — они умеют только собирать образ и коммитить текстовые файлы в Git. Доступ к кластеру имеет только внутренний контроллер ArgoCD, что исключает возможность взлома кластера через инфраструктуру CI.
