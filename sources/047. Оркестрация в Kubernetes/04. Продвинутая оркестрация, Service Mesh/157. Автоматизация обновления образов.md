# Автоматизация обновления образов: ArgoCD Image Updater и стратегии SemVer

## Условие

Настройте **ArgoCD Image Updater** для автоматического обновления image tags при появлении новых версий в registry.

## Теория

В классическом GitOps конвейере требуется, чтобы CI-раннер имел доступ на запись в Git-репозиторий манифестов для обновления тега образа.
**ArgoCD Image Updater — альтернативный подход без прав CI в Git:**
1. **Принцип работы:**
   - Image Updater работает как контроллер внутри кластера рядом с ArgoCD.
   - Он напрямую опрашивает Container Registry (Docker Hub, Harbor, GHCR, AWS ECR).
   - При обнаружении нового образа, соответствующего правилам, контроллер сам обновляет спецификацию приложения в ArgoCD или коммитит новый тег обратно в Git!
2. **Стратегии обновления тегов (Update Strategies):**
   - **`semver`**: обновляет образ строго в соответствии с правилами семантического версионирования (например, `~1.2` — разрешает patch-обновления до `1.2.9`, но блокирует `1.3.0`).
   - **`latest`**: выбирает образ с самой свежей датой создания в реестре.
   - **`digest`**: обновляет изменяемый тег по его уникальному SHA-256 дайджесту.

## Решение по шагам

1. Установите ArgoCD Image Updater в namespace `argocd`.
2. Добавьте аннотации на манифест `Application` с указанием отслеживаемого образа и стратегии `semver`.
3. Настройте права обратной записи в Git через метод `git:secret:argocd/git-creds`.
4. Запушьте новый тег образа `v1.2.1` в Container Registry.
5. Убедитесь, что Image Updater обнаружил новую версию и задеплоил ее.

## Код решения

**`application-image-updater.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: store-api
  namespace: argocd
  annotations:
    # 1. Список отслеживаемых образов
    argocd-image-updater.argoproj.io/image-list: my-app=ghcr.io/my-org/store-api
    # 2. Стратегия обновления по SemVer (любые minor и patch обновления в ветке 1.x)
    argocd-image-updater.argoproj.io/my-app.update-strategy: semver
    argocd-image-updater.argoproj.io/my-app.allow-tags: "^1.*"
    # 3. Метод фиксации изменений: прямой коммит обратно в Git-репозиторий
    argocd-image-updater.argoproj.io/write-back-method: git
    argocd-image-updater.argoproj.io/git-branch: main
spec:
  project: default
  source:
    repoURL: "https://github.com/my-org/store-gitops.git"
    targetRevision: main
    path: "apps/store/overlays/prod"
  destination:
    server: "https://kubernetes.default.svc"
    namespace: store
```

**`Терминал`**

```bash
# Установка ArgoCD Image Updater
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj-labs/argocd-image-updater/stable/manifests/install.yaml

# Просмотр логов работы Image Updater (поиск новых тегов в Registry)
kubectl logs -n argocd -l app.kubernetes.io/name=argocd-image-updater -f
# INFO  Setting update strategy for image ghcr.io/my-org/store-api to semver
# INFO  Found 8 tags in registry
# INFO  Latest matching tag for ghcr.io/my-org/store-api is 1.2.4 (current is 1.2.0)
# INFO  Committing changes to Git repository: update image to 1.2.4
```

## Под капотом

Image Updater использует библиотеку `go-containerregistry` для выполнения вызовов Docker Registry v2 API (`/v2/<name>/tags/list`). Получив список тегов, контроллер парсит их с помощью парсера `Masterminds/semver`. Найдя наивысшую версию, удовлетворяющую регулярному выражению `^1.*`, контроллер через Git CLI создает коммит с файлом `.argocd-source-<app-name>.yaml` в ветке репозитория и инициирует синхронизацию в ArgoCD.

## Подводные камни

1. Превышение Docker Hub Rate Limits: при частом поллинге реестра без аутентификации Docker Hub заблокирует IP кластера на 6 часов (`429 Too Many Requests`). Обязательно настраивайте `pull-secret` в `argocd-image-updater-config`.
2. Конфликты коммитов при одновременных ручных правках: настройте ветку для коммитов бота с последующим автомерджем через Pull Request.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях целесообразнее использовать ArgoCD Image Updater вместо стандартного шага коммита из CI конвейера?»
**Ответ:** 1) **Упрощение CI:** В CI не нужно хранить секретные ключи доступа с правами на коммит в репозиторий манифестов; 2) **Автоматизация патчей безопасности:** Идеально подходит для автоматического наката minor/patch версий базовых инфраструктурных образов (NGINX, Redis, Envoy) сразу после их публикации вендором в публичном или приватном Registry без ручного вмешательства инженеров.
