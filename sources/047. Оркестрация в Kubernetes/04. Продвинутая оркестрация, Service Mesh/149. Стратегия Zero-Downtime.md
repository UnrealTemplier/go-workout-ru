# Стратегия Zero-Downtime: точная настройка maxSurge и maxUnavailable

## Условие

**Rolling Update**: Настройте `strategy.rollingUpdate.maxSurge: 25%` и `maxUnavailable: 0` для zero-downtime деплоя.

## Теория

При обновлении высоконагруженных микросервисов недопустима даже секундная потеря доступности или всплеск сетевых ошибок.
**Математика Zero-Downtime стратегии:**
1. **`maxUnavailable: 0`:**
   - Гарантирует, что во время обновления количество доступных и готовых к работе подов **НИКОГДА не опускается ниже 100% желаемой емкости**.
   - Ни один старый Pod не будет остановлен, пока новый Pod не пройдет Readiness Probe и не начнет полноценно обслуживать трафик!
2. **`maxSurge: 25%` (или фиксированное число, например `1`):**
   - Разрешает временно превысить общее число реплик на 25% от желаемого количества.
   - Например, при `replicas: 4` и `maxSurge: 25%` контроллер поднимет 1 дополнительный Pod новой версии (\(4 + 1 = 5\) подов суммарно).
3. **Требование к ресурсам нод:**
   - Кластер обязан иметь достаточный запас CPU/RAM для размещения этих временных дополнительных подов (`surge pods`), иначе они зависнут в статусе `Pending`!

## Решение по шагам

1. Создайте манифест `Deployment` с 4 репликами и стратегией `maxSurge: 25%`, `maxUnavailable: 0`.
2. Настройте обязательную `readinessProbe` с задержкой проверки.
3. Запустите непрерывный мониторинг доступности через цикл `curl` с частотой 20 запросов в секунду.
4. Выполните обновление версии образа.
5. Убедитесь, что ни один HTTP-запрос не завершился сбоем (100% HTTP 200 OK).

## Код решения

**`deployment-zero-downtime.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-gateway
  namespace: default
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # Разрешено создать +1 под сверх лимита (итого 5)
      maxUnavailable: 0    # Запрещено удалять старые поды до готовности новых
  selector:
    matchLabels:
      app: payment-gateway
  template:
    metadata:
      labels:
        app: payment-gateway
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: app
          image: payment-gateway:v2.0.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 2
```

**`Терминал`**

```bash
# Применение манифеста с zero-downtime стратегией
kubectl apply -f deployment-zero-downtime.yaml

# Запуск фонового генератора трафика для подтверждения отсутствия ошибок
while true; do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" http://payment-gateway.default.svc:8080/)
  if [ "$CODE" != "200" ]; then
    echo "ОШИБКА ДАУНТАЙМА: HTTP $CODE"
  fi
  sleep 0.05
done &

# Обновление образа на новую версию
kubectl set image deployment/payment-gateway app=payment-gateway:v2.1.0

# Отслеживание процесса обновления
kubectl rollout status deployment/payment-gateway
# Waiting for deployment "payment-gateway" rollout to finish: 1 out of 4 new replicas have been updated...
# deployment "payment-gateway" successfully rolled out
```

## Под капотом

`deployment-controller` вычисляет максимальный размер пула подов: \(\text{MaxAllowed} = \text{replicas} + \lceil \text{replicas} \times \text{maxSurge} \rceil = 4 + 1 = 5\). Контроллер создает 1 Pod в новом ReplicaSet. Когда Kubelet сообщает о готовности пода (`status.conditions[Ready]=True`), контроллер уменьшает размер старого ReplicaSet с 4 до 3, отправляя `SIGTERM` одному старому поду. Процесс циклически повторяется до полной замены всех 4 подов.

## Подводные камни

1. Кластер без запаса вычислительных ресурсов: если в кластере свободно всего 50m CPU, а Pod запрашивает 500m, новый Pod упадет в `Pending`. Поскольку `maxUnavailable: 0` запрещает удалять старые поды, процесс обновления заморозится навсегда.
2. Неверно настроенный Readiness Probe: если эндпоинт пробы возвращает 200 до того, как открылся слушающий сокет, K8s начнет направлять клиентов на неготовые поды, вызывая 502 ошибки.

## На собеседовании

**Вопрос с собеседования:** «Почему комбинация `maxSurge: 0` и `maxUnavailable: 25%` опасна для высоконагруженных production-сервисов?»
**Ответ:** При таких настройках контроллер сначала **удаляет 25% работающих старых подов** (уменьшая суммарную производительность сервиса на четверть), чтобы освободить место под новые поды. Если в этот момент сервис работает на пике нагрузки, оставшиеся 75% подов испытают резкую перегрузку по CPU/памяти, начнут троттлить или упадут по таймаутам, вызвав каскадный отказ всей системы.
