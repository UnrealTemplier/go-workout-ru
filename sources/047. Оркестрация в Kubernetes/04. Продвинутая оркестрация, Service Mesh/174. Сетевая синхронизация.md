# Сетевая синхронизация: preStop hook со sleep 15 для исключения 502 ошибок

## Условие

Настройте **preStop hook** с `sleep 15` для graceful termination: K8s отправляет SIGTERM, приложение завершает текущие запросы, но load balancer ещё некоторое время отправляет трафик.

## Теория

Архитектурный парадокс Kubernetes:
- **Удаление Pod происходит распределенно и асинхронно.**
- Когда Pod переходит в статус `Terminating`, сигнал `SIGTERM` посылается в контейнер **ОДНОВРЕМЕННО** с отправкой события об удалении эндпоинта в контроллер `kube-proxy` и внешние балансировщики.
- Обновление правил iptables/IPVS на всех 200 нодах кластера и в облачном NLB/ALB занимает от 3 до 10 секунд!
- Если приложение сразу начнет останавливать процесс, запросы, уже отправленные балансировщиком в эти секунды, наткнутся на закрытый сокет и вернут клиентам **502 Bad Gateway**.
**Решение: `preStop: exec: command: ["sleep", "15"]`:**
1. Kubelet запускает хук `preStop` ДО отправки `SIGTERM`.
2. Контейнер просто «спит» 15 секунд, продолжая нормально обрабатывать запросы.
3. За эти 15 секунд сетевая инфраструктура успевает гарантированно исключить Pod из всех балансировщиков.
4. Только после этого процесс получает `SIGTERM` и выполняет чистое завершение.

## Решение по шагам

1. Настройте `lifecycle.preStop` в манифесте Deployment.
2. Установите `terminationGracePeriodSeconds: 45` (15 сек preStop + 30 сек на завершение запросов).
3. Запустите нагрузочное тестирование с постоянным потоком запросов.
4. Удалите Pod во время нагрузки.
5. Убедитесь в полном отсутствии 502/504 ошибок в логах клиентов.

## Код решения

**`deployment-prestop.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: resilient-web-service
  namespace: default
spec:
  replicas: 3
  template:
    spec:
      # terminationGracePeriodSeconds должен быть БОЛЬШЕ времени preStop!
      # 15с (preStop) + 20с (HTTP shutdown) + 10с (запас) = 45с
      terminationGracePeriodSeconds: 45
      containers:
        - name: app
          image: resilient-web:v1.0.0
          lifecycle:
            preStop:
              exec:
                # Даем 15 секунд kube-proxy и ingress-контроллеру на удаление пода из iptables
                command: ["/bin/sh", "-c", "sleep 15"]
          ports:
            - containerPort: 8080
```

**`Терминал`**

```bash
# Запуск пода с настроенным preStop
kubectl apply -f deployment-prestop.yaml

# Непрерывный мониторинг HTTP кодов ответов при удалении пода
while true; do
  curl -s -o /dev/null -w "%{http_code}\n" http://resilient-web:8080/
  sleep 0.1
done &

# Удаление пода
kubectl delete pod -l app=resilient-web --wait=false

# В выводе curl должны быть СТРОГО коды 200, ни одной ошибки 502!
```

## Под капотом

Kubelet вызывает CRI метод `ExecSync` для запуска процесса `/bin/sh -c sleep 15` внутри namespaces контейнера. Пока команда `sleep 15` не вернет код 0, Kubelet блокирует отправку сигнала `SIGTERM`. Одновременно `EndpointSliceMirroringController` рассылает обновления в API-сервер, а демон `kube-proxy` на всех нодах пересчитывает хэш-таблицы IPVS/iptables, исключая удаленный под из цепочек DNAT.

## Подводные камни

1. Забытый запас в `terminationGracePeriodSeconds`: если период равен 30 секундам, а `sleep` длится 25 секунд, у Go-приложения останется всего 5 секунд на завершение всех транзакций, после чего Kubelet принудительно убьет его сигналом `SIGKILL`.
2. Использование образов без `/bin/sh`: в ультра-минималистичных образах `scratch` запуск команды `["/bin/sh", "-c", "sleep 15"]` завершится ошибкой. В таких случаях задержку перед остановкой реализуют прямо в Go-коде внутри обработчика `signal.Notify`.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя просто сделать `time.Sleep(15 * time.Second)` в Go-коде при получении сигнала SIGTERM вместо preStop хука в манифесте?»
**Ответ:** Можно, но вызов `preStop` в манифесте декларативнее и надежнее: он разделяет инфраструктурную задержку сети от прикладного кода. Если реализовать задержку в Go-коде, разработчик может случайно закрыть слушающий сокет (`server.Close()`) до вызова `sleep`, что моментально оборвет новые входящие соединения. `preStop` гарантирует, что контейнер продолжает полноценно работать в штатном режиме, пока сеть обновляет маршруты.
