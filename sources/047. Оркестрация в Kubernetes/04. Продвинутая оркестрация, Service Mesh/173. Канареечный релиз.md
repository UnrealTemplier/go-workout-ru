# Канареечный релиз: маршрутизация 5% трафика и постепенное наращивание веса

## Условие

**Canary**: Направляйте 5% трафика на новую версию, мониторьте метрики, постепенно увеличивайте до 100%.

## Теория

Канареечный релиз — проверенный способ защиты пользователей от скрытых багов и регрессий производительности:
1. **Этапы наращивания веса:**
   - **Фаза 1 (5% трафика):** минимальный поток, достаточный для проверки отсутствия паник и критических утечек памяти в рантайме Go.
   - **Фаза 2 (25% трафика):** проверка устойчивости под умеренной нагрузкой.
   - **Фаза 3 (50% трафика):** проверка паритета производительности с текущей версией.
   - **Фаза 4 (100% трафика):** полный переход и последующая утилизация старой версии.
2. **Технологии реализации:**
   - **Ingress NGINX Canary:** аннотации `nginx.ingress.kubernetes.io/canary: "true"` и `nginx.ingress.kubernetes.io/canary-weight: "5"`.
   - **Service Mesh (Istio / Linkerd):** декларативный `VirtualService` с разделением весов в процентах.

## Решение по шагам

1. Создайте стабильный Deployment `auth-v1` и Ingress `auth-stable`.
2. Создайте канареечный Deployment `auth-v2` с новой версией.
3. Создайте дополнительный Ingress `auth-canary` с аннотацией веса 5%.
4. Запустите цикл из 100 запросов `curl` и убедитесь, что ровно ~5 запросов попадают на версию v2.
5. Постепенно увеличьте вес до 50% и 100%.

## Код решения

**`canary-ingress.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: auth-service-canary
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5" # Ровно 5% трафика направляется на v2
spec:
  ingressClassName: nginx
  rules:
    - host: auth.company.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: auth-service-v2
                port:
                  number: 8080
```

**`Терминал`**

```bash
# Применение канареечного Ingress
kubectl apply -f canary-ingress.yaml

# Тестирование распределения трафика (из 100 запросов ~5 вернет v2)
COUNT_V2=0
for i in {1..100}; do
  RESP=$(curl -s -H "Host: auth.company.com" http://localhost/version)
  if [ "$RESP" == "v2.0.0" ]; then
    ((COUNT_V2++))
  fi
done
echo "Процент запросов, попавших на канарейку v2: $COUNT_V2%"

# Продвижение канарейки: увеличение веса до 50%
kubectl annotate ingress auth-service-canary nginx.ingress.kubernetes.io/canary-weight="50" --overwrite
```

## Под капотом

Модуль OpenResty/Lua внутри NGINX Ingress Controller генерирует псевдослучайное число от 1 до 100 для каждого входящего HTTP-запроса. Если число \(\le 5\), NGINX выбирает upstream-группу сервиса `auth-service-v2`, иначе — стабильную upstream-группу `auth-service-v1`. Это работает на L7 уровне без необходимости изменения DNS-записей или IP-адресов.

## Подводные камни

1. Сессии пользователей (Sticky Sessions): если включена привязка сессий по cookie, пользователь, случайно попавший на канарейку 5%, останется на ней для всех последующих запросов, что может исказить статистику распределения.
2. Несоответствие схем кэширования: если новая версия сохраняет в общий Redis кэш объекты в новом JSON-формате, старая версия v1 может упасть при попытке их десериализации.

## На собеседовании

**Вопрос с собеседования:** «Как в канареечном релизе направить трафик на новую версию не по случайному проценту веса, а строго для мобильных клиентов на iOS?»
**Ответ:** Используется аннотация канарейки по HTTP-заголовку в Ingress NGINX:
```yaml
nginx.ingress.kubernetes.io/canary: "true"
nginx.ingress.kubernetes.io/canary-by-header: "User-Agent"
nginx.ingress.kubernetes.io/canary-by-header-pattern: ".*CFNetwork.*"
```
Вся веб-аудитория и Android продолжат использовать стабильную версию, а запросы от iOS-приложений будут адресованы в канареечный микросервис.
