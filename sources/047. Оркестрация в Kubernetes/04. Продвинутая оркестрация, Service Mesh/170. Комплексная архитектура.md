# Комплексная архитектура: трехуровневое микросервисное приложение в Kubernetes

## Условие

**[Multi-tier App in K8s]**: Разверни систему из трех микросервисов (API Gateway, User Service, Order Service).
- API Gateway доступен извне через Ingress.
- Сервисы общаются между собой по gRPC через K8s Service Discovery (DNS имена вроде `user-service.default.svc.cluster.local`).
- Настрои Liveness/Readiness пробы.
- Настрой HPA для каждого сервиса.
- Разверни PostgreSQL (StatefulSet + PersistentVolume) и Redis.
- Настрой Network Policies (API Gateway может говорить с User/Order, но User/Order не могут принимать трафик извне кластера).
- Все логи и метрики собираются в Grafana/Prometheus/Loki.

## Теория

Эталонная трехуровневая (3-Tier) архитектура распределенной системы в Kubernetes:
1. **Сетевой уровень (Ingress & Perimeter):**
   - NGINX Ingress Controller принимает внешний трафик и направляет его в `api-gateway`.
2. **Уровень сервисов (Microservices Tier):**
   - `api-gateway` взаимодействует с `user-service` и `order-service` по протоколу gRPC (HTTP/2) через CoreDNS Service Discovery.
   - Каждый сервис защищен Liveness/Readiness пробами и масштабируется через HPA.
3. **Уровень данных (Stateful Tier):**
   - PostgreSQL (StatefulSet с PV/PVC) для хранения реляционных данных заказов.
   - Redis (StatefulSet / ClusterIP) для кэширования сессий.
4. **Безопасность (Zero-Trust NetworkPolicies):**
   - База данных и внутренние сервисы изолированы: они не принимают трафик извне кластера, доступ разрешен только с подов `api-gateway`.

## Решение по шагам

1. Создайте манифесты StatefulSet для PostgreSQL и Redis с PersistentVolumeClaim.
2. Создайте манифесты Deployments и Services для `api-gateway`, `user-service` и `order-service`.
3. Настройте `NetworkPolicy`, изолирующую внутренние сервисы от внешнего мира.
4. Создайте манифесты `HorizontalPodAutoscaler` для микросервисов.
5. Настройте `Ingress` для доступа к API Gateway.

## Код решения

**`multi-tier-architecture.txt`**

```text
[ External Internet Traffic ]
              │
              ▼
    [ Ingress Controller ]
              │
              ▼ (HTTP/REST)
     [ api-gateway Pods ] (HPA: 2..10)
        │            │
        │ (gRPC)     │ (gRPC)
        ▼            ▼
[ user-service ]  [ order-service ] (NetworkPolicy: Ingress Denied from outside)
        │                 │
        ▼                 ▼
   [ Redis Cache ]  [ PostgreSQL DB ] (StatefulSet + PersistentVolume)
```

**`tier-network-policy.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: internal-tier-isolation
  namespace: default
spec:
  podSelector:
    matchExpressions:
      - key: app
        operator: In
        values: [user-service, order-service]
  policyTypes:
    - Ingress
  ingress:
    # Разрешено принимать сетевой трафик ТОЛЬКО от подов api-gateway
    - from:
        - podSelector:
            matchLabels:
              app: api-gateway
      ports:
        - protocol: TCP
          port: 50051
```

**`api-gateway-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-gateway
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api-gateway
  template:
    metadata:
      labels:
        app: api-gateway
    spec:
      containers:
        - name: gateway
          image: api-gateway:v1.0.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
          env:
            - name: USER_SERVICE_ADDR
              value: "user-service.default.svc.cluster.local:50051"
            - name: ORDER_SERVICE_ADDR
              value: "order-service.default.svc.cluster.local:50051
```

**`Терминал`**

```bash
# Развертывание всей многоуровневой системы
kubectl apply -f tier-network-policy.yaml
kubectl apply -f api-gateway-deployment.yaml

# Проверка работоспособности сквозного сетевого графа
kubectl get pods,svc,hpa -o wide
```

## Под капотом

CoreDNS преобразует имя `user-service.default.svc.cluster.local` в виртуальный IP ClusterIP сервиса. При отправке gRPC вызова из Go-кода `grpc.DialContext()` пакет маршрутизируется через CNI-плагин. NetworkPolicy проверяет метки пода-источника в BPF-карте: если источник `api-gateway`, пакет пропускается на порт 50051. При попытке прямого вызова из любого другого пода ядро Linux отбрасывает пакеты.

## Подводные камни

1. Балансировка gRPC соединений: gRPC использует постоянные HTTP/2 TCP-соединения. Стандартный Kubernetes Service балансирует трафик на уровне L4 TCP, из-за чего все gRPC-запросы могут уйти в один-единственный Pod! Решение — использование Headless Service (`clusterIP: None`) с клиентской балансировкой gRPC (`round_robin`) или внедрение Service Mesh (Istio).
2. Забытые PVC в StatefulSet: удаление StatefulSet базы данных не удаляет PVC автоматически, предотвращая потерю данных, но требуя ручной очистки при полном сбросе среды.

## На собеседовании

**Вопрос с собеседования:** «Почему при взаимодействии микросервисов по gRPC стандартный Kubernetes Service ClusterIP не балансирует запросы между подами и как решить эту проблему?»
**Ответ:** Протокол gRPC работает поверх **HTTP/2**, который мультиплексирует сотни запросов внутри одного долгоживущего TCP-соединения. Стандартный Service (kube-proxy) работает на **L4 (транспортном уровне TCP)**: он балансирует сам факт открытия TCP-соединения, но не видит отдельные запросы внутри стрима. В результате `api-gateway` открывает один TCP-коннект к одному поду `user-service` и шлет все 100% запросов только в него. **Решения:** 1) Использовать **Headless Service** (`clusterIP: None`), чтобы gRPC-клиент в Go сам получил IP всех подов через DNS SRV/A-записи и балансировал стримы (`grpc.WithDefaultServiceConfig("{\"loadBalancingConfig\": [{\"round_robin\": {}}]}")); 2) Использовать L7 Service Mesh (Envoy/Istio).
