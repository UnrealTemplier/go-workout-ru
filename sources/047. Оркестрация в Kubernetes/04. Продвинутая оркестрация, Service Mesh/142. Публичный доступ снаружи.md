# Публичный доступ снаружи: настройка NGINX Ingress Controller и DNS

## Условие

**Публичный доступ (Ingress)**: Service ClusterIP работает только внутри. Чтобы пользователи могли зайти снаружи по красивому URL, установи Ingress Controller (например, NGINX Ingress для Kind). Создай `ingress.yaml` с правилом: трафик для `myapp.local` направить в твой Service. Настрой `/etc/hosts` на ноутбуке и проверь работу.

## Теория

Стандартный объект `Service` с типом `ClusterIP` изолирован внутри виртуальной оверлейной сети кластера (его IP-адрес недоступен за пределами нод).
**Организация публичного входа через Ingress:**
1. **Ingress Controller (NGINX):**
   - Запускается на портах 80 и 443 хоста (или слушает внешний облачный LoadBalancer).
   - Выступает в роли пограничного reverse-proxy.
2. **Ingress Resource:**
   - Объявляет соответствие между HTTP-заголовком `Host: myapp.local` и внутренним сервисом Kubernetes.
   - Задает правила маршрутизации URL-путей (`path: /api` \(\rightarrow\) `api-service`, `path: /` \(\rightarrow\) `frontend-service`).
3. **Локальное разрешение имен (Local DNS):**
   - Добавление записи `127.0.0.1 myapp.local` в файл `/etc/hosts` перенаправляет браузер на локальный порт Ingress Controller.

## Решение по шагам

1. Разверните Kind-кластер с пробросом портов 80 и 443 на хост.
2. Установите ingress-nginx контроллер, адаптированный под Kind.
3. Разверните Go-приложение и Service с типом `ClusterIP`.
4. Создайте манифест `ingress.yaml` для домена `myapp.local`.
5. Добавьте `127.0.0.1 myapp.local` в `/etc/hosts` и выполните `curl http://myapp.local`.

## Код решения

**`ingress.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "5"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "30"
spec:
  ingressClassName: nginx
  rules:
    - host: myapp.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: myapp-service
                port:
                  number: 8080
```

**`service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
  namespace: default
spec:
  type: ClusterIP
  selector:
    app: myapp
  ports:
    - port: 8080
      targetPort: 8080
```

**`Терминал`**

```bash
# Установка NGINX Ingress Controller для Kind
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml

# Ожидание готовности контроллера
kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller \
  --timeout=90s

# Применение манифеста Ingress
kubectl apply -f ingress.yaml

# Добавление сопоставления домена в /etc/hosts на локальной машине
echo "127.0.0.1 myapp.local" | sudo tee -a /etc/hosts

# Проверка ответа веб-сервера через публичный Ingress
curl -i http://myapp.local/
```

## Под капотом

NGINX Ingress Controller транслирует манифесты Ingress в виртуальные хосты `server { server_name myapp.local; ... }` внутри файла конфигурации `/etc/nginx/nginx.conf`. Контроллер отслеживает изменения списка адресов подов через `Endpoints` и передает их в shared memory блок балансировщика через Lua-модуль OpenResty. Пакет с заголовком `Host: myapp.local` принимается мастер-процессом NGINX на порту 80 и напрямую проксируется на частный IP пода.

## Подводные камни

1. Забытый заголовок `Host`: если обращаться по IP `curl http://127.0.0.1/`, Ingress NGINX вернет `404 Not Found` (или default backend), так как не сможет определить целевой виртуальный хост без совпадения `rules.host`.
2. Ошибки в `pathType`: использование `pathType: Exact` для пути `/` не пропустит запросы к `/users` или `/static/bundle.js`. Для корневого роутинга всегда используйте `Prefix`.

## На собеседовании

**Вопрос с собеседования:** «Чем Ingress принципиально отличается от Service типа LoadBalancer с точки зрения сетевого стека OSI и затрат на инфраструктуру?»
**Ответ:** Service типа `LoadBalancer` работает на **L4 (транспортном уровне TCP/UDP)**: он создает отдельный облачный балансировщик (AWS NLB/CLB) с выделенным публичным IP на каждый сервис, что дорого при сотнях микросервисов и не позволяет анализировать HTTP-заголовки, cookies или пути URL. **Ingress** работает на **L7 (прикладном уровне HTTP/HTTPS)**: один общий публичный IP и единый балансировщик маршрутизируют сотни микросервисов по именам доменов (`Host`) и путям URL, выполняя централизованную терминацию SSL/TLS.
