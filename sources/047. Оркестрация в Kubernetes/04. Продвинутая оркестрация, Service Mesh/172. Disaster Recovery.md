# Disaster Recovery: регулярные DR-учения, валидация RPO и RTO

## Условие

**Disaster Recovery**: regular DR drills, backup testing, documented runbooks. RPO/RTO defined and tested. Multi-region, multi-cloud if needed.

## Теория

«Резервная копия, которую ни разу не восстанавливали на практике, не существует» (SRE Postulate):
1. **Ключевые метрики надежности:**
   - **RPO (Recovery Point Objective):** Максимально допустимый объем потерянных данных во времени (например, \(\text{RPO} \le 15 \text{ минут}\)).
   - **RTO (Recovery Time Objective):** Максимально допустимое время простоя системы до полного восстановления сервиса (например, \(\text{RTO} \le 30 \text{ минут}\)).
2. **Проведение регулярных DR-учений (Disaster Recovery Drills):**
   - Учения проводятся раз в квартал в рабочее время.
   - Сценарий 1: Полное удаление основного производственного кластера.
   - Сценарий 2: Имитация потери дата-центра (Data Center Blackout) и переключение глобального трафика (GSLB) на резервный регион.
3. **Автоматизация DR через GitOps и Velero:**
   - Развертывание нового кластера по манифестам CAPI/Terraform.
   - Восстановление данных из неизменяемых (Object Lock) S3-бэкапов Velero.
   - Проверка целостности автоматическими smoke-тестами.

## Решение по шагам

1. Определите формальные SLA/SLO/RPO/RTO для микросервисов.
2. Создайте автоматизированный скрипт DR-восстановления.
3. Разверните резервный аварийный кластер в другом регионе.
4. Выполните восстановление данных и конфигураций.
5. Зафиксируйте хронометраж восстановления для аудита RTO.

## Код решения

**`dr-drill-automation.sh`**

```bash
#!/bin/bash
set -euo pipefail

START_TIME=$(date +%s)
echo "=== СТАРТ АВАРИЙНЫХ DR-УЧЕНИЙ ==="
echo "Целевой RTO: 20 минут. Целевой RPO: 1 час."

TARGET_CLUSTER="backup-cluster-spb"
BACKUP_NAME=$(velero backup get --output json | jq -r '.items[-1].metadata.name')

echo "1. Использование последнего бэкапа: $BACKUP_NAME"

echo "2. Запуск восстановления Velero в резервный кластер $TARGET_CLUSTER..."
velero restore create "drill-restore-$(date +%s)" \
  --from-backup "$BACKUP_NAME" \
  --wait

echo "3. Ожидание перехода всех подов в статус Ready..."
kubectl wait --for=condition=ready pod -l tier=backend -A --timeout=300s

echo "4. Запуск автоматических E2E тестов целостности транзакций..."
./run-synthetic-transactions.sh

END_TIME=$(date +%s)
TOTAL_TIME=$((END_TIME - START_TIME))

echo "✅ DR-учения успешно завершены!"
echo "Фактический RTO составил: $TOTAL_TIME секунд ($((TOTAL_TIME / 60)) мин)."
if [ "$TOTAL_TIME" -le 1200 ]; then
  echo "🏆 SLA СОБЛЮДЕН: Время восстановления укладывается в норматив RTO."
else
  echo "❌ НАРУШЕНИЕ RTO: Требуется оптимизация скорости восстановления дисков."
fi
```

## Под капотом

Во время DR-учений контроллер Velero на резервном кластере считывает блоб метаданных из S3. Для каждого PersistentVolumeClaim Velero обращается к CSI snapshotter, создавая тома из облачных снапшотов. После восстановления объектов в etcd CoreDNS и сетевые балансировщики активируются, а DNS-записи в Cloudflare/Route53 через API обновляются на IP-адреса резервного дата-центра.

## Подводные камни

1. Бэкапы, перезаписанные вирусом-вымогателем (Ransomware): S3-бакеты для хранения бэкапов обязаны настраиваться с включенным **S3 Object Lock (WORM — Write Once, Read Many)**, делающим невозможным удаление или шифрование бэкапов даже администратором аккаунта.
2. Разные версии плагинов и CRD в аварийном кластере: несоответствие версий приведет к ошибкам восстановления манифестов.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие архитектуры Disaster Recovery Active-Passive от Active-Active (Multi-Region)?»
**Ответ:** 
- **Active-Passive (Cold/Warm Standby):** Резервный кластер либо выключен, либо работает на минимальной мощности, данные синхронизируются асинхронно. При аварии требуется время на поднятие узлов и восстановление (\(\text{RTO} \approx 15\text{–}30 \text{ мин}\), возможна потеря последних данных \(\text{RPO} > 0\)). Дешевле в эксплуатации.
- **Active-Active (Multi-Region Multi-Master):** Два или более кластера в разных регионах одновременно обслуживают живой трафик пользователей. Данные реплицируются синхронно (например, YugabyteDB, CockroachDB, Google Spanner). При падении целого региона трафик мгновенно перенаправляется на оставшийся регион (\(\text{RTO} \approx 0\), \(\text{RPO} = 0\)). Значительно сложнее и дороже в поддержке.
