# Система оповещений Alertmanager: мониторинг доступности подов и ошибок 5xx

## Условие

Настройте алерты в Prometheus AlertManager: если количество подов падает ниже заданного или растёт процент 5xx.

## Теория

Сбор метрик бесполезен без проактивной системы оповещения инженеров об инцидентах:
1. **Процесс генерации алертов:**
   - **Prometheus Rules (`PrometheusRule` CRD):** непрерывно вычисляет PromQL-выражения с интервалом `evaluation_interval`.
   - Если условие истинно дольше периода `for` (например, `for: 5m`), алерт переходит из состояния `Pending` в состояние `Firing` и отправляется в **Alertmanager**.
2. **Два критических правила мониторинга доступности:**
   - **Дефицит реплик рабочей нагрузки:**
     $$\text{kube\_deployment\_status\_replicas\_available} < \text{kube\_deployment\_spec\_replicas}$$
     Сигнализирует о падении подов, сбоях нод или нехватке ресурсов.
   - **Всплеск частоты ошибок HTTP 5xx (SLO Breach):**
     Процент 5xx ошибок превышает 5% от общего объема трафика за 5-минутное окно.
3. **Alertmanager Routing:** группировка, дедупликация и отправка алертов дежурным в Slack / PagerDuty.

## Решение по шагам

1. Создайте манифест `PrometheusRule` с правилами проверки доступности реплик и частоты 5xx ошибок.
2. Настройте конфигурацию маршрутизации `alertmanager.yaml`.
3. Примените правила в кластер.
4. Проверьте отображение правил в интерфейсе Prometheus `/alerts`.
5. Сымитируйте сбой приложения и убедитесь в отправке алерта в Slack.

## Код решения

**`prometheus-rules.yaml`**

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: platform-sla-alerts
  namespace: monitoring
  labels:
    role: alert-rules
    release: kube-prometheus-stack
spec:
  groups:
    - name: application-reliability.rules
      rules:
        # 1. Алерт при нехватке готовых реплик
        - alert: DeploymentReplicasUnavailable
          expr: >-
            kube_deployment_status_replicas_available{namespace="production"}
            <
            kube_deployment_spec_replicas{namespace="production"}
          for: 3m
          labels:
            severity: critical
            tier: platform
          annotations:
            summary: "Дефицит реплик в Deployment {{ $labels.deployment }}"
            description: "В deployment {{ $labels.deployment }} доступно меньше реплик, чем запланировано в течение 3 минут."

        # 2. Алерт при росте процента 5xx ошибок > 5%
        - alert: HighHttpErrorRate5xx
          expr: >-
            (
              sum by (app) (rate(http_requests_total{status=~"5..", namespace="production"}[5m]))
              /
              sum by (app) (rate(http_requests_total{namespace="production"}[5m]))
            ) * 100 > 5
          for: 2m
          labels:
            severity: page
            tier: backend
          annotations:
            summary: "Высокий уровень 5xx ошибок в сервисе {{ $labels.app }}"
            description: "Доля HTTP 5xx ошибок составляет {{ $value | printf \"%.2f\" }}% за последние 5 минут." 
```

**`alertmanager-config.yaml`**

```yaml
apiVersion: monitoring.coreos.com/v1alpha1
kind: AlertmanagerConfig
metadata:
  name: global-routing
  namespace: monitoring
spec:
  route:
    groupBy: ['alertname', 'namespace', 'app']
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 4h
    receiver: 'slack-notifications'
    routes:
      - matchers:
          - name: severity
            value: page
        receiver: 'pagerduty-oncall'
  receivers:
    - name: 'slack-notifications'
      slackConfigs:
        - channel: '#alerts-production'
          apiURL:
            name: alertmanager-slack-webhook
            key: webhook-url
          sendResolved: true
    - name: 'pagerduty-oncall'
      pagerdutyConfigs:
        - serviceKey:
            name: pagerduty-keys
            key: backend-key
```

**`Терминал`**

```bash
# Применение правил алертинга
kubectl apply -f prometheus-rules.yaml
kubectl apply -f alertmanager-config.yaml

# Просмотр статуса активных алертов через утилиту amtool
amtool alert --alertmanager.url=http://localhost:9093
```

## Под капотом

Каждые 15 секунд Prometheus вычисляет векторные выражения PromQL. Если в течение 3 минут (`for: 3m`) условие непрерывно выполняется, Prometheus формирует JSON-пейлоад с метаданными и метками и отправляет HTTP POST запрос на эндпоинт Alertmanager `/api/v2/alerts`. Alertmanager выполняет группировку сообщений по ключам `groupBy`, глушит дубликаты (deduplication) и отправляет форматированное уведомление в Slack с кнопкой тишины (Silence).

## Подводные камни

1. Деление на ноль в формуле ошибок: если в сервисе временно нет входящего трафика, знаменатель равен 0, и результат PromQL — `NaN`. Обрабатывайте такие случаи через конструкцию `or on() vector(0)`.
2. Слишком короткий период `for`: установка `for: 10s` вызовет ложные срабатывания дежурным ночью из-за одиночного сетевого сбоя или короткого перезапуска пода.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между `group_wait`, `group_interval` и `repeat_interval` в конфигурации Alertmanager?»
**Ответ:** 1) **`group_wait` (например, 30s):** Время ожидания после возникновения первого алерта перед отправкой первого сообщения, чтобы собрать в одно письмо/сообщение алерты от соседних подов; 2) **`group_interval` (например, 5m):** Задержка перед отправкой следующего уведомления, если в уже существующую группу добавились новые сработавшие алерты; 3) **`repeat_interval` (например, 4h):** Период повторной отправки уведомления о проблеме, если алерт всё еще висит в статусе Firing и инженер его не устранил и не заглушил (silenced).
