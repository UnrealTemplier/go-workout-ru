# Developer Experience (DevEx): быстрый фидбек-луп и мощеные дорожки (Paved Paths)

## Условие

**Developer Experience**: local development (kind, tilt), fast feedback loop (< 5 min from push to deploy in dev), good documentation, paved paths. Happy developers = productive developers.

## Теория

Инженерная культура **Developer Experience (DevEx)** и концепция **«Мощеных дорожек» (Paved Paths / Golden Paths)**:
1. **Метрики эффективности разработки:**
   - **Lead Time for Changes (Время доставки изменений):** время от `git push` до появления работающей версии на Dev-стенде должно составлять **менее 5 минут**.
   - **Inner Loop Latency:** время проверки изменения одной строчки кода локально должно составлять **менее 3 секунд** (благодаря Tilt/Air/Kind).
2. **Концепция Paved Road (Золотой путь компании):**
   - Платформенная команда предоставляет готовые стандартизированные шаблоны микросервисов на Go (Cookiecutter / Backstage Software Templates).
   - Шаблон из коробки включает:
     - Настроенный Makefile (`make test`, `make lint`, `make dev`, `make build`).
     - Готовый `Dockerfile` с multi-stage сборкой и Distroless.
     - Готовые манифесты Kustomize/Helm с настроенными Probes, PDB и HPA.
     - Интегрированные метрики Prometheus, OTel трейсинг и структурированное логирование slog.
3. Разработчик фокусируется на бизнес-логике, не тратя недели на настройку инфраструктуры.

## Решение по шагам

1. Создайте корпоративный эталонный `Makefile` для микросервисов на Go.
2. Настройте команду `make dev` с автоматическим запуском Air hot-reload.
3. Настройте команду `make test-all` с unit-, race- и линт-проверками.
4. Опишите файл `README.md` с onboarding-инструкцией запуска проекта за 1 минуту.

## Код решения

**`Makefile`**

```makefile
.PHONY: all build dev test lint clean

# Переменные сборки
APP_NAME := payment-service
BIN_DIR := ./bin
GO_FILES := $(shell find . -name '*.go' -not -path './vendor/*')

all: lint test build

## build: Компиляция статического бинарника приложения
build:
	@echo "==> Компиляция $(APP_NAME)..."
	@CGO_ENABLED=0 go build -ldflags="-w -s" -o $(BIN_DIR)/server .

## dev: Локальный запуск с мгновенным hot-reload через Air
dev:
	@which air > /dev/null || (echo "Установка air..." && go install github.com/air-verse/air@latest)
	@air

## test: Запуск модульных тестов с проверкой состояния гонки
test:
	@echo "==> Запуск тестов..."
	@go test -v -race -cover -coverprofile=coverage.out ./...

## lint: Статический анализ кода через golangci-lint
lint:
	@echo "==> Проверка линтером..."
	@golangci-lint run --timeout=3m

## clean: Очистка временных файлов и артефактов сборки
clean:
	@rm -rf $(BIN_DIR) coverage.out
```

**`README.md`**

````markdown
# Payment Service (Paved Road Golden Template)

Микросервис обработки платежей на Go 1.23.

## Быстрый старт для нового разработчика (Onboarding < 2 минут):
1. Клонируйте репозиторий: `git clone git@github.com:corp/payment-service.git`
2. Запустите локальное окружение с зависимостями:
   ```bash
   docker compose up -d # Поднимает локальные Postgres, Redis и Jaeger
   make dev             # Запускает сервис с автоперезагрузкой при изменении кода
   ```
3. Сервер доступен по адресу: `http://localhost:8080`
4. Прогон всех проверок перед созданием Pull Request:
   ```bash
   make all
   ```
````

## Под капотом

Инструмент Air отслеживает системные события файловой системы ядра Linux `inotify`. При сохранении `main.go` в IDE Air перехватывает событие, компилирует инкрементальный бинарник в папке `tmp/` за 250 мс, посылает `SIGTERM` предыдущему запущенному процессу и мгновенно поднимает новый процесс, сохраняя соединение к базе данных.

## Подводные камни

1. Отсутствие локального docker-compose: заставлять разработчика вручную устанавливать и настраивать PostgreSQL, Redis и Kafka на свой ноутбук приводит к дням потерянного времени при онбординге.
2. Неконсистентность окружений: если локально тесты запускаются на одной версии Go, а в CI на другой, возникают трудноуловимые баги сборки.

## На собеседовании

**Вопрос с собеседования:** «Что такое концепция Internal Developer Platform (IDP) на базе Backstage и какую проблему она решает?»
**Ответ:** IDP решает проблему когнитивной перегрузки разработчиков (Cognitive Load). Вместо того чтобы заставлять каждого программиста разбираться в тонкостях Helm, Kustomize, IAM ролей, Cert-manager и конфигурациях CI/CD, компания строит портал самообслуживания (на базе Spotify Backstage). Разработчик нажимает одну кнопку «Создать Go-микросервис», вводит имя, и платформа автоматически генерирует Git-репозиторий с золотым шаблоном, создает namespace в Kubernetes, подключает мониторинг, CI/CD конвейер и базу данных по утвержденным корпоративным стандартам безопасности.
