# Продвинутая стратегия Progressive Delivery: синергия Canary и Feature Flags

## Условие

**Progressive Delivery**: canary, blue-green, feature flags. Не deploy'и на 100% сразу. Автоматический rollback по SLO degradation. Reduce blast radius.

## Теория

Прогрессивная доставка объединяет **инфраструктурное разделение трафика** (Canary/Blue-Green) и **управление фичами на уровне кода** (**Feature Flags**):
1. **Снижение радиуса поражения (Blast Radius Reduction):**
   - **Инфраструктурный уровень (Argo Rollouts / Istio):** Новая версия сервиса получает 1% \(\rightarrow\) 5% случайного трафика. Если сервис крашится по памяти или дедлоку, страдает не более 1% пользователей.
   - **Прикладной уровень (Feature Flags):** Новый тяжелый алгоритм поиска или редизайн корзины включается только для 10% сотрудников компании или бета-тестеров по заголовку или User ID.
2. **OpenFeature (CNCF Стандарт):**
   - Библиотека Go для работы с флагами функций без привязки к конкретному провайдеру (LaunchDarkly, Unleash, Flipt, Flagsmith).
   - Позволяет мгновенно отключить проблемную функциональность за 100 миллисекунд без перезапуска подов и без повторного деплоя!

## Решение по шагам

1. Подключите SDK OpenFeature в Go-микросервис.
2. Реализуйте проверку флага `new_checkout_algorithm`.
3. Настройте динамическое управление флагом через локальный провайдер.
4. Скомбинируйте фичефлаг с канареечным развертыванием через Argo Rollouts.
5. Продемонстрируйте мгновенное отключение сбойной фичи.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net/http"

	"github.com/open-feature/go-sdk/openfeature"
)

func main() {
	// Инициализация OpenFeature клиента (стандарт CNCF)
	client := openfeature.NewClient("checkout-service")

	http.HandleFunc("/checkout", func(w http.ResponseWriter, r *http.Request) {
		ctx := r.Context()
		userID := r.Header.Get("X-User-ID")

		// Оценка фичефлага в рантайме для конкретного пользователя
		evalCtx := openfeature.NewTargetlessEvaluationContext(map[string]interface{}{
			"user_id": userID,
		})

		useNewAlgorithm, err := client.BooleanValue(ctx, "enable_v2_checkout", false, evalCtx)
		if err != nil {
			log.Printf("Ошибка оценки флага: %v", err)
		}

		if useNewAlgorithm {
			// Новый алгоритм (Canary Feature)
			fmt.Fprintf(w, "[V2 NEW ALGORITHM] Платеж пользователя %s обработан через ML-шлюз\n", userID)
		} else {
			// Стабильный legacy алгоритм (Fallback)
			fmt.Fprintf(w, "[V1 LEGACY] Платеж пользователя %s обработан по стандартному пути\n", userID)
		}
	})

	log.Println("Сервер с поддержкой Progressive Delivery запущен на :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`Терминал`**

```bash
# 1. Обычный пользователь попадает на стабильный путь V1
curl -H "X-User-ID: user-100" http://localhost:8080/checkout
# [V1 LEGACY] Платеж пользователя user-100 обработан по стандартному пути

# 2. Бета-тестер попадает на экспериментальный алгоритм V2
curl -H "X-User-ID: beta-tester-01" http://localhost:8080/checkout
# [V2 NEW ALGORITHM] Платеж пользователя beta-tester-01 обработан через ML-шлюз
```

## Под капотом

Feature Flag SDK хранит локальное дерево правил вычисления флагов в оперативной памяти (в структурах `sync.RWMutex` или `atomic.Pointer`). Проверка `client.BooleanValue` не делает сетевых HTTP-запросов и занимает менее 1 микросекунды CPU. Обновление правил флагов из панели управления (Unleash/Flipt) происходит асинхронно по долгоживущему соединению Server-Sent Events (SSE) или gRPC stream.

## Подводные камни

1. Накопление технического долга («мертвые флаги»): если флаг не удаляется из кода после 100% раскатки фичи, через год кодовая база превращается в лабиринт из сотен устаревших условий `if/else`.
2. Взаимодействие нескольких флагов (Combinatorial Explosion): одновременное тестирование трех флагов создает \(2^3 = 8\) различных состояний системы, которые сложно протестировать в E2E тестах.

## На собеседовании

**Вопрос с собеседования:** «В чем принципиальная разница между Canary Deployment и Feature Flags и почему они дополняют друг друга?»
**Ответ:** **Canary Deployment** управляет инфраструктурой: он направляет процент сетевых пакетов на новые поды, проверяя системные метрики (память, процессор, отсутствие паник, сетевую связность). **Feature Flags** управляют бизнес-логикой внутри кода: они позволяют таргетировать фичу на конкретные когорты пользователей (только клиенты из Москвы, только премиум-аккаунты) и мгновенно выключать упавшую фичу без запуска нового цикла CI/CD и деплоя в кластер.
