# Стратегия Blue-Green: мгновенное переключение трафика через селектор Service

## Условие

**Blue-Green**: Создайте два идентичных окружения, переключайте трафик через Service selector. Мгновенный rollback.

## Теория

Стратегия **Blue-Green Deployment** гарантирует нулевой даунтайм и мгновенную возможность отката:
1. **Принцип работы:**
   - В кластере развернуты два независимых Deployment:
     - **Blue (Текущая стабильная версия):** принимает 100% боевого трафика.
     - **Green (Новая версия):** развернута в полном объеме (100% реплик), но изолирована от пользователей.
   - Сервис `Service` направляет трафик на поды с помощью селектора: `selector: { app: myapp, version: blue }`.
2. **Процедура релиза:**
   - Инженеры или автоматические smoke-тесты проверяют окружение Green через приватный внутренний тестовый Service.
   - Когда готовность подтверждена, в основном Service изменяется селектор: `version: green`.
   - **Переключение трафика происходит мгновенно** (за доли миллисекунды на уровне iptables/kube-proxy)!
3. **Мгновенный откат:**
   - При обнаружении сбоя селектор сервиса переключается обратно на `version: blue` одной командой, восстанавливая стабильную работу за секунду.

## Решение по шагам

1. Создайте два Deployment: `app-blue` (v1) и `app-green` (v2).
2. Создайте Service `production-service`, указывающий на `version: blue`.
3. Отправьте запрос и убедитесь в получении ответа от Blue.
4. Обновите селектор сервиса на `version: green` через `kubectl patch`.
5. Убедитесь в мгновенном переключении ответов на Green без потери пакетов.

## Код решения

**`blue-green-deployments.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-store
      version: blue
  template:
    metadata:
      labels:
        app: web-store
        version: blue
    spec:
      containers:
        - name: app
          image: web-store:v1.0.0
          ports:
            - containerPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-green
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-store
      version: green
  template:
    metadata:
      labels:
        app: web-store
        version: green
    spec:
      containers:
        - name: app
          image: web-store:v2.0.0
          ports:
            - containerPort: 8080
```

**`production-service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-store-production
spec:
  selector:
    app: web-store
    version: blue # Сейчас весь боевой трафик направлен на Blue
  ports:
    - port: 80
      targetPort: 8080
```

**`Терминал`**

```bash
# Применение обоих окружений и сервиса
kubectl apply -f blue-green-deployments.yaml
kubectl apply -f production-service.yaml

# Запрос к боевому сервису возвращает версию Blue (v1.0.0)
curl http://web-store-production/

# Мгновенное переключение боевого трафика на Green (v2.0.0)
kubectl patch service web-store-production -p '{"spec":{"selector":{"version":"green"}}}'

# Следующий же запрос мгновенно возвращает Green (v2.0.0) без даунтайма!
curl http://web-store-production/

# В случае обнаружения проблем - мгновенный откат за 1 секунду обратно на Blue:
kubectl patch service web-store-production -p '{"spec":{"selector":{"version":"blue"}}}'
```

## Под капотом

При выполнении `kubectl patch service` контроллер `endpoint-controller` считывает новый селектор `version: green`. Контроллер за один вызов заменяет адреса в объекте `Endpoints` со старых подов Blue на новые поды Green. `kube-proxy` на всех узлах переписывает IP-адреса в IPVS-виртуальном сервере или цепочках iptables `KUBE-SVC-*`. Существующие Keep-Alive TCP-соединения могут дорабатывать на Blue, а все новые HTTP-запросы мгновенно направляются в Green.

## Подводные камни

1. Удвоение затрат на вычислительные ресурсы: во время релиза в кластере одновременно работают 100% Blue и 100% Green подов. Кластер должен иметь запас ресурсов (+100% CPU/RAM).
2. Активные WebSocket-сессии: при переключении селектора постоянные сокеты клиентов не сбрасываются автоматически и продолжают висеть на старой версии Blue, пока приложение не инициирует закрытие соединений.

## На собеседовании

**Вопрос с собеседования:** «Когда Blue-Green deployment предпочтительнее, чем Canary deployment?»
**Ответ:** Blue-Green незаменим, когда: 1) Требуется гарантированное **мгновенное переключение 100% пользователей** в фиксированный момент времени (например, старт масштабной маркетинговой акции или запуск нового финансового года); 2) Приложение не поддерживает одновременное сосуществование двух разных версий в сети (проблемы версионирования кэша или сообщений шины данных); 3) Критически важен мгновенный откат (Instant Rollback) в один клик без ожидания обратного пересчета процентов канарейки.
