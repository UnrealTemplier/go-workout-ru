# Декларативное описание ArgoCD Application: манифест синхронизации

## Условие

Настройте ArgoCD **Application** resource, который синхронизирует состояние кластера с Git.

## Теория

Custom Resource **`Application`** — главный примитив управления в ArgoCD:
1. **Анатомия манифеста:**
   - `spec.source`: откуда брать желаемое состояние:
     - `repoURL`: ссылка на Git-репозиторий (HTTPS или SSH).
     - `targetRevision`: ветка (`main`), тег (`v1.4.0`) или конкретный Git Commit SHA.
     - `path`: путь к директории с манифестами внутри репозитория.
   - `spec.destination`: куда разворачивать:
     - `server`: адрес API Kubernetes кластера (например, `https://kubernetes.default.svc` для локального кластера).
     - `namespace`: целевой namespace.
   - `spec.syncPolicy`:
     - `automated`: автоматическая синхронизация при обнаружении дрифта.
     - `prune: true`: удаление сущностей в K8s, если они удалены из Git.
     - `selfHeal: true`: откат ручных правок в кластере к состоянию в Git.
2. **Health Assessment:** ArgoCD непрерывно отслеживает здоровье ресурсов (Healthy, Progressing, Degraded, Suspended).

## Решение по шагам

1. Создайте манифест `app-deployment.yaml` для микросервиса `user-service`.
2. Опишите `Application` CRD с автоматической синхронизацией и созданием namespace.
3. Примените манифест в namespace `argocd`.
4. Проверьте статус приложения через CLI: `argocd app get user-service`.
5. Убедитесь, что статус перешел в `Synced` и `Healthy`.

## Код решения

**`application.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: user-service-prod
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: "https://github.com/my-org/production-manifests.git"
    targetRevision: main
    path: "services/user-service/overlays/prod"
  destination:
    server: "https://kubernetes.default.svc"
    namespace: users-production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ApplyOutOfSyncOnly=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m
```

**`Терминал`**

```bash
# Применение манифеста Application
kubectl apply -f application.yaml

# Проверка детального статуса приложения
argocd app get user-service-prod

# Ручной запуск принудительной синхронизации при отключенном автосинке
argocd app sync user-service-prod

# Просмотр истории синхронизаций и коммитов
argocd app history user-service-prod
```

## Под капотом

`argocd-application-controller` опрашивает `repo-server` для рендеринга манифестов Git ревизии `HEAD`. Полученные объекты сравниваются с объектами в кластере через Three-way Merge (учитывая `liveState`, `targetState` и `lastAppliedState`). Если обнаруживается различие (Out-of-Sync), контроллер применяет изменения через `kubectl apply` API calls. Финалайзер `resources-finalizer` гарантирует, что при удалении `Application` из ArgoCD все созданные им поды и сервисы в целевом namespace будут корректно удалены.

## Подводные камни

1. Отсутствие `resources-finalizer`: если удалить объект Application без финалайзера, ArgoCD просто забудет про него, оставив все поды и сервисы «осиротевшими» (orphaned) работать в кластере без контроля.
2. Циклический `Out-of-Sync` из-за `mutating admission webhooks`: если внешний вебхук добавляет дефолтные поля (например, sidecar или security context), которых нет в Git, ArgoCD будет считать приложение вечно несинхронизированным. Решение — секция `ignoreDifferences`.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет при включенном `selfHeal: true`, если дежурный инженер выполнит `kubectl scale deployment myapp --replicas=10` во время аварии?»
**Ответ:** ArgoCD через 1-3 секунды (или при очередном цикле реконсиляции) обнаружит расхождение между реальным состоянием (`replicas: 10`) и желаемым состоянием в Git (`replicas: 3`). В режиме `selfHeal: true` контроллер немедленно перезапишет конфигурацию в кластере состоянием из Git, сбросив масштаб обратно до 3 реплик! Чтобы аварийное масштабирование сработало, инженер обязан либо временно отключить автосинхронизацию в ArgoCD, либо внести изменение прямо в ветку Git.
