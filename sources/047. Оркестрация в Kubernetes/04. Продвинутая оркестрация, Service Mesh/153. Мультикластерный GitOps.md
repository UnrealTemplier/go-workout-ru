# Мультикластерный GitOps: связка Kustomize и ArgoCD для управления средами

## Условие

Используйте **Kustomize + ArgoCD** для управления multiple clusters (dev, staging, prod) из одного Git repo.

## Теория

Организация мультикластерной структуры в едином GitOps-репозитории:
1. **Иерархия конфигураций:**
   - Один репозиторий `gitops-fleet` содержит манифесты для всех окружений и дата-центров.
   - Директория `base/`: общее описание микросервисов.
   - Директории кластеров: `clusters/dev/`, `clusters/staging/`, `clusters/prod-dc-east/`, `clusters/prod-dc-west/`.
2. **Безопасность мультикластерного подключения:**
   - ArgoCD регистрирует удаленные кластеры через объекты `Secret` в своем namespace.
   - Доступ осуществляется через выделенные ServiceAccount с ограниченным RBAC (ClusterRole) на целевых кластерах.
3. **Разделение прав доступа (Tenant Isolation):**
   - Проект `AppProject` в ArgoCD жестко ограничивает, какие команды могут развертывать приложения в боевые кластеры.

## Решение по шагам

1. Подключите удаленный рабочий кластер к ArgoCD: `argocd cluster add <context>`.
2. Создайте структуру оверлеев Kustomize для двух кластеров: `dev-cluster` и `prod-cluster`.
3. Создайте манифесты `Application` для каждого кластера.
4. Выполните синхронизацию и проверьте развертывание в разных кластерах.
5. Продемонстрируйте независимость релизных циклов.

## Код решения

**`repo-structure.txt`**

```text
gitops-fleet-repo/
├── apps/
│   └── user-api/
│       ├── base/
│       └── overlays/
│           ├── dev/
│           └── prod/
└── clusters/
    ├── dev-cluster/
    │   └── user-api-app.yaml
    └── prod-cluster/
        └── user-api-app.yaml
```

**`clusters/prod-cluster/user-api-app.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-user-api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: "https://github.com/my-org/gitops-fleet-repo.git"
    targetRevision: main
    path: "apps/user-api/overlays/prod"
  destination:
    # URL удаленного кластера, зарегистрированного в ArgoCD
    server: "https://k8s-prod-api.corp.internal:6443"
    namespace: users
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

**`Терминал`**

```bash
# Добавление внешнего продакшен-кластера в систему управления ArgoCD
argocd cluster add prod-k8s-context --name prod-cluster-east

# Просмотр зарегистрированных кластеров флота
argocd cluster list
# SERVER                                    NAME               STATUS      VERSION
# https://k8s-prod-api.corp.internal:6443   prod-cluster-east  Successful  1.28
# https://kubernetes.default.svc            in-cluster         Successful  1.28

# Синхронизация приложения на удаленный кластер
argocd app sync prod-user-api
```

## Под капотом

При выполнении синхронизации `argocd-application-controller` загружает токен аутентификации из секрета `cluster-prod-cluster-east`. Контроллер инициализирует gRPC/HTTPS соединение напрямую к удаленному API-серверу `https://k8s-prod-api.corp.internal:6443`, используя внутренний rate-limiter, и выполняет Server-Side Apply манифестов. Статус здоровья ресурсов передается обратно в интерфейс ArgoCD.

## Подводные камни

1. Сетевая недоступность API-сервера удаленного кластера: если корпоративный файрвол блокирует порт 6443 между кластерами, ArgoCD перейдет в статус `ComparisonError`. Для закрытых контуров применяют pull-модель (агент ArgoCD Application Controller внутри каждого кластера).
2. Разные версии Kubernetes: оверлей Kustomize, использующий поля API версии 1.28, сломается при деплое в legacy-кластер версии 1.24.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие централизованной (Hub-and-Spoke) и децентрализованной архитектуры ArgoCD при управлении сотнями кластеров?»
**Ответ:** В **Hub-and-Spoke** один управляющий инстанс ArgoCD имеет сетевой доступ к сотням целевых кластеров и пушит манифесты в них. Плюс: единая точка входа и аутентификации. Минус: огромная нагрузка на один контроллер и высокие риски безопасности (компрометация Hub дает доступ ко всем кластерам). В **децентрализованной модели** в каждом кластере работает свой собственный локальный ArgoCD, читающий общий Git-репозиторий. Это полностью изолирует кластеры, повышает отказоустойчивость и снимает ограничения по масштабированию.
