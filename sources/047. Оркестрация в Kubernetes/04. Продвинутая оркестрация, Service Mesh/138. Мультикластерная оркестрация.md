# Мультикластерная оркестрация: Cluster API (CAPI) и флот кластеров

## Условие

Настрой **Multi-Cluster**: `kind: Cluster` (CAPI — Cluster API). Management cluster provisions workload clusters. Federated services, global load balancing, disaster recovery. Покажи fleet management.

## Теория

При достижении определенного масштаба один гигантский кластер Kubernetes становится единой точкой отказа (Single Point of Failure) и сталкивается с ограничениями масштабируемости `etcd` (рекомендуемый предел: не более 5 000 нод и 150 000 подов).
**Cluster API (CAPI) — декларативное управление кластерами Kubernetes в стиле самого Kubernetes:**
1. **Архитектурный принцип:**
   - **Management Cluster:** управляющий мета-кластер, на котором установлены контроллеры CAPI.
   - **Workload Clusters:** рабочие кластеры (Dev, Stage, Prod DC-1, Prod DC-2), создаваемые как обычные декларативные ресурсы K8s (`kind: Cluster`, `kind: MachineDeployment`).
2. **Преимущества CAPI:**
   - Автоматизированное создание, обновление (rolling upgrade версий K8s без даунтайма) и уничтожение целых кластеров в любом облаке (AWS, GCP, Azure, OpenStack) или bare-metal.
   - Единый интерфейс управления инфраструктурой через стандартные манифесты `kubectl`.
3. **Глобальная балансировка (GSLB) и Multi-Cluster Mesh:**
   - DNS-балансировщики (Cloudflare, AWS Route53) направляют пользовательский трафик в ближайший живой кластер, обеспечивая мгновенный Disaster Recovery при падении целого дата-центра.

## Решение по шагам

1. Установите CLI `clusterctl` и инициализируйте CAPI в управляющем кластере.
2. Опишите манифест целевого кластера `workload-cluster-prod`.
3. Настройте спецификацию управляющих нод (`KubeadmControlPlane`) и рабочих узлов (`MachineDeployment`).
4. Примените манифест и отследите автоматическое развертывание нового кластера.
5. Получите `kubeconfig` созданного кластера командой `clusterctl get kubeconfig`.

## Код решения

**`cluster-definition.yaml`**

```yaml
apiVersion: cluster.x-k8s.io/v1beta1
kind: Cluster
metadata:
  name: prod-dc-moscow
  namespace: fleet-management
spec:
  clusterNetwork:
    services:
      cidrBlocks: ["10.96.0.0/12"]
    pods:
      cidrBlocks: ["192.168.0.0/16"]
    serviceDomain: "cluster.local"
  infrastructureRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
    kind: AWSCluster
    name: prod-dc-moscow
  controlPlaneRef:
    apiVersion: controlplane.cluster.x-k8s.io/v1beta1
    kind: KubeadmControlPlane
    name: prod-dc-moscow-control-plane
---
apiVersion: cluster.x-k8s.io/v1beta1
kind: MachineDeployment
metadata:
  name: prod-workers-pool
  namespace: fleet-management
spec:
  clusterName: prod-dc-moscow
  replicas: 10
  selector:
    matchLabels: {}
  template:
    spec:
      clusterName: prod-dc-moscow
      version: "v1.28.2"
      bootstrap:
        configRef:
          apiVersion: bootstrap.cluster.x-k8s.io/v1beta1
          kind: KubeadmConfigTemplate
          name: prod-workers-bootstrap
      infrastructureRef:
        apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
        kind: AWSMachineTemplate
        name: prod-workers-infra
```

**`Терминал`**

```bash
# Создание нового кластера в облаке через применение манифеста
kubectl apply -f cluster-definition.yaml

# Отслеживание процесса провижининга кластера
clusterctl describe cluster prod-dc-moscow -n fleet-management

# Получение kubeconfig созданного кластера для подключения
clusterctl get kubeconfig prod-dc-moscow -n fleet-management > /tmp/prod-dc.kubeconfig

# Проверка узлов нового кластера
kubectl --kubeconfig=/tmp/prod-dc.kubeconfig get nodes
```

## Под капотом

Контроллер Cluster API взаимодействует с провайдером инфраструктуры (CAPA для AWS, CAPG для GCP). Он поднимает виртуальные машины через Cloud API, генерирует облачные скрипты инициализации `cloud-init` с командами `kubeadm init` и `kubeadm join`, конфигурирует сетевые правила безопасности и выпускает TLS-сертификаты кластера. При обновлении версии Kubernetes `MachineDeployment` выполняет Rolling Update серверов: поочередно создает новые узлы с K8s v1.29, выполняет `kubectl drain` старых узлов и гасит их.

## Подводные камни

1. Потеря `management` кластера: если управляющий кластер с CAPI упадет, рабочие кластеры продолжат функционировать, но ими станет невозможно управлять. База etcd управляющего кластера требует строгой репликации и непрерывного бэкапа через Velero.
2. Сложность синхронизации секретов: управление сетевыми сертификатами и ключами шифрования между множеством независимых кластеров требует централизованного хранилища Vault.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество разделения инфраструктуры компании на множество небольших кластеров Kubernetes (через CAPI) по сравнению с одним гигантским кластером?»
**Ответ:** 1) **Радиус поражения (Blast Radius):** Ошибка инженера, сбой сетевого CNI-плагина или компрометация безопасности затрагивает только один изолированный кластер, а не весь бизнес компании; 2) **Независимые обновления:** Возможность обновлять кластеры поочередно (Canary Cluster Upgrade) без риска глобального даунтайма; 3) **Соответствие регуляторным требованиям:** Размещение данных пользователей строго в нужных юрисдикциях (152-ФЗ, GDPR).
