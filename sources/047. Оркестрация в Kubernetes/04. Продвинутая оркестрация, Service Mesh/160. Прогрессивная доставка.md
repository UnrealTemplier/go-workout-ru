# Прогрессивная доставка: Argo Rollouts Canary с автоматическим анализом метрик Prometheus

## Условие

Используйте **Argo Rollouts** для canary и blue-green deployments с автоматическим анализом метрик (Prometheus) для принятия решения о продвижении.

## Теория

Прогрессивная доставка (**Progressive Delivery**) автоматизирует принятие решений при деплое на основе анализа телеметрии в реальном времени.
**Argo Rollouts — продвинутый контроллер деплоя от создателей ArgoCD:**
1. **Замена стандартного Deployment:**
   - Ресурс `kind: Rollout` полностью совместим со спецификацией Deployment, но поддерживает стратегии **Canary** и **Blue-Green**.
2. **Шаги продвижения (Rollout Steps):**
   - Задают процент трафика (`setWeight: 20`) и паузы для накопления статистики (`pause: {duration: 5m}`).
3. **Автоматический судья (AnalysisTemplate):**
   - Во время выполнения шага контроллер непрерывно выполняет PromQL-запросы к Prometheus.
   - Оценивает ключевые метрики здоровья: процент ошибок (Error Rate), время отклика (p99 Latency), бизнес-метрики конверсии.
   - Если метрики в норме — релиз автоматически продвигается дальше (`Promoted`).
   - Если метрики деградировали — релиз немедленно прерывается (`Aborted`), и трафик возвращается на стабильную версию за доли секунды.

## Решение по шагам

1. Установите контроллер Argo Rollouts и плагин для kubectl: `kubectl-argo-rollouts`.
2. Создайте `AnalysisTemplate` для контроля доли HTTP 5xx ошибок (< 1%).
3. Создайте ресурс `Rollout` с шагами 10%, 30%, 100%.
4. Запустите канареечный деплой новой версии.
5. Наблюдайте за ходом канарейки в интерактивной консоли: `kubectl argo rollouts get rollout <name> --watch`.

## Код решения

**`analysis-template.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: http-error-rate-check
  namespace: default
spec:
  metrics:
    - name: error-rate-metric
      interval: 20s
      count: 5
      failureLimit: 1
      successCondition: result[0] < 0.01 # Меньше 1% ошибок 5xx
      provider:
        prometheus:
          address: http://prometheus-operated.monitoring.svc:9090
          query: |
            sum(rate(http_requests_total{app="order-backend", status=~"5.."}[1m]))
            /
            (sum(rate(http_requests_total{app="order-backend"}[1m])) + 0.001)
```

**`rollout.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: order-backend
  namespace: default
spec:
  replicas: 5
  strategy:
    canary:
      analysis:
        templates:
          - templateName: http-error-rate-check
      steps:
        - setWeight: 20
        - pause: {duration: 2m}
        - setWeight: 50
        - pause: {duration: 3m}
  selector:
    matchLabels:
      app: order-backend
  template:
    metadata:
      labels:
        app: order-backend
    spec:
      containers:
        - name: app
          image: order-backend:v2.0.0
          ports:
            - containerPort: 8080
```

**`Терминал`**

```bash
# Установка Argo Rollouts Controller
kubectl create namespace argo-rollouts
kubectl apply -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml

# Применение шаблона анализа и Rollout
kubectl apply -f analysis-template.yaml
kubectl apply -f rollout.yaml

# Запуск канареечного релиза путем смены версии образа
kubectl argo rollouts set image order-backend app=order-backend:v2.1.0

# Интерактивный мониторинг прогресса канарейки и результатов анализа метрик
kubectl argo rollouts get rollout order-backend --watch
```

## Под капотом

Контроллер Argo Rollouts управляет двумя ReplicaSet: Stable и Canary. При переходе на шаг `setWeight: 20` контроллер создает объект `AnalysisRun`. Фоновая горутина контроллера выполняет HTTP-запрос к Prometheus API `/api/v1/query`. Ответ парсится в скалярное число с плавающей точкой. Если условие `result[0] < 0.01` соблюдено, шаг подтверждается. Если условие нарушено, контроллер ставит метку `abort`, удаляет ReplicaSet канарейки и возвращает все маршруты в ingress-контроллере на Stable ReplicaSet.

## Подводные камни

1. Забытый знаменатель `+ 0.001` в запросе: если на канарейку в момент старта не поступает трафик, деление `0 / 0` вернет `NaN`, что приведет к ошибке оценки условия и непреднамеренному отмене релиза.
2. Недостаточное время паузы `pause`: пауза в 10 секунд не даст Prometheus времени собрать и сагрегировать метрики за 1-минутное окно (`[1m]`). Окно паузы должно быть не менее 2-3 интервалов скрейпинга.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие стратегии Blue-Green от стратегии Canary в Argo Rollouts и когда какую выбирать?»
**Ответ:** 
- **Blue-Green:** Одновременно поднимается полный 100% стек новой версии (Green) рядом со старой (Blue). После прохождения тестов весь трафик переключается мгновенно (100%). Плюс: мгновенное переключение и мгновенный откат. Минус: требует удвоения вычислительных ресурсов кластера (+100% CPU/RAM) и не позволяет плавно протестировать систему на части реальных пользователей.
- **Canary:** Трафик переводится плавно небольшими долями (1% \(\rightarrow\) 10% \(\rightarrow\) 50% \(\rightarrow\) 100%) с анализом метрик в реальном времени. Идеален для HighLoad и критических микросервисов, так как минимизирует влияние возможных багов на пользователей и не требует двойного запаса серверов.
