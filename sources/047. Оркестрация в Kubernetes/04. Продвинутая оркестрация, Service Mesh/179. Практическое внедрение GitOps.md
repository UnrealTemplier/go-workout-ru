## Теория

Практическая реализация GitOps в промышленной эксплуатации:
1. **Архитектура двух репозиториев:**
   - `repo-app`: код на Go, `go.mod`, unit-тесты, `Dockerfile`.
   - `repo-gitops-infra`: Kustomize оверлеи, конфигурации Ingress, сетевые политики.
2. **Контроллеры синхронизации:**
   - **ArgoCD:** мощный Web UI, визуализация графа ресурсов, поддержка SSO, детальный аудит.
   - **Flux v2:** легковесный модульный контроллер (Kustomize Controller, Helm Controller, Source Controller), глубоко интегрированный с CLI `flux` и Git.
3. **Неизменяемый журнал аудита:**
   - Каждая операция развертывания — это коммит в Git, подтвержденный Pull Request с подписью PGP/GPG.

## Решение по шагам

1. Создайте выделенный Git-репозиторий манифестов `gitops-manifests`.
2. Создайте файл `kustomization.yaml` с базовым деплойментом и сервисом.
3. Создайте манифест `Application` в ArgoCD, указывающий на этот репозиторий.
4. Включите `syncPolicy: automated: {prune: true, selfHeal: true}`.
5. Продемонстрируйте автоматическое развертывание после пуша коммита в Git.

## Код решения

**`gitops-application.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: billing-system
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: "https://github.com/my-enterprise-org/gitops-manifests.git"
    targetRevision: HEAD
    path: "environments/production"
  destination:
    server: "https://kubernetes.default.svc"
    namespace: billing-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ApplyOutOfSyncOnly=true
```

**`Терминал`**

```bash
# Применение манифеста Application
kubectl apply -f gitops-application.yaml

# Просмотр статуса синхронизации через CLI
argocd app get billing-system
# Name:               argocd/billing-system
# Server:             https://kubernetes.default.svc
# Namespace:          billing-prod
# URL:                https://argocd.corp/applications/billing-system
# Repo:               https://github.com/my-enterprise-org/gitops-manifests.git
# Target:             HEAD
# Path:               environments/production
# Sync Window:        Sync Allowed
# Sync Status:        Synced to HEAD (9f4b102)
# Health Status:      Healthy
```

## Под капотом

`argocd-application-controller` выполняет периодический вызов Git fetch, получает коммит `9f4b102`, парсит дерево каталогов и с помощью `kustomize build` строит манифесты. Затем выполняется вызов `kube-apiserver` для сравнения live-состояния. При совпадении всех полей статус помечается как `Synced`, а в etcd сохраняется ревизия последней успешной синхронизации.

## Подводные камни

1. Забытый финалайзер `resources-finalizer`: если удалить объект `Application`, ресурсы в целевом namespace останутся работать без управления. Финалайзер гарантирует чистое каскадное удаление.
2. Использование изменяемых веток (например, ветки без защиты branch protection): обязательно защищайте ветку `main` требованием код-ревью и успешного прохождения CI тестов.

## На собеседовании

**Вопрос с собеседования:** «В чем ключевое отличие архитектуры ArgoCD от Flux v2?»
**Ответ:** 
- **ArgoCD:** Полнофункциональная платформа с богатым Web UI, централизованным сервером аутентификации (SSO/RBAC), возможностью визуализации связей подов и ручного запуска синхронизации через UI. Идеален для крупных команд, где разработчикам нужен наглядный интерфейс для отладки деплоя.
- **Flux v2:** Набор узкоспециализированных микро-контроллеров (Kubernetes-native), спроектированных по философии Unix (каждый контроллер делает одну задачу: Source Controller, Kustomize Controller, Helm Controller, Notification Controller). Не имеет собственного тяжелого UI (управляется через CLI и CRD), потребляет меньше ресурсов и идеален для полностью автоматизированных headless-инфраструктур.
