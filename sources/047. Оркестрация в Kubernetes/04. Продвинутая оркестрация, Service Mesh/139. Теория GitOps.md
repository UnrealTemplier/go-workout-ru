# Теория GitOps: концепция Desired State, Actual State и устранение дрифта

## Условие

Изучите концепцию **desired state** vs **actual state** и как ArgoCD устраняет drift.

## Теория

Фундамент декларативной модели Kubernetes и методологии GitOps базируется на математической теории систем управления (Control Theory):
1. **Два состояния системы:**
   - **Desired State (Желаемое состояние):** Декларативно описано в файлах конфигураций Git-репозитория (манифесты, чарты, оверлеи). Это целевой эталон, согласованный через code review.
   - **Actual State / Live State (Фактическое состояние):** Текущее реальное состояние ресурсов внутри кластера (запущенные поды, действующие правила iptables, выделенная память).
2. **Концепция дрифта (Drift):**
   $$\text{Drift} = \text{Actual State} \ominus \text{Desired State}$$
   Дрифт возникает, если кто-то внес изменения вручную в кластере (`kubectl edit`, `kubectl scale`), либо если внешний сбой изменил ресурсы.
3. **Цикл обратной связи и реконсиляция (Reconciliation Loop):**
   - **Observe:** Чтение фактического состояния из etcd.
   - **Diff:** Вычисление расхождений.
   - **Act (Self-Healing):** Автоматическое приведение Live-состояния в точное соответствие с Git.

## Решение по шагам

1. Задеплойте приложение через ArgoCD со статусом `Synced`.
2. Вручную измените количество реплик в кластере: `kubectl scale deployment myapp --replicas=10`.
3. Зафиксируйте обнаружение состояния `Out-of-Sync` в ArgoCD.
4. Пронаблюдайте за работой механизма `Self-Healing`, который автоматически вернет число реплик к значению из Git.
5. Изучите дифф расхождений через UI или команду `argocd app diff`.

## Код решения

**`Терминал`**

```bash
# 1. Проверка текущего состояния приложения (Desired State = 2 реплики)
argocd app get inventory-service | grep -E "(Sync Status|Health Status)"
# Sync Status:    Synced to main (c5f10a8)
# Health Status:  Healthy

# 2. Несанкционированное ручное вмешательство инженера в работающий кластер
kubectl scale deployment inventory-service --replicas=8

# 3. ArgoCD немедленно фиксирует отклонение (Drift)
argocd app diff inventory-service
# ===== apps/Deployment inventory-service ======
# 12c12
# <   replicas: 2
# ---
# >   replicas: 8

# 4. Благодаря включенному selfHeal=true ArgoCD автоматически возвращает состояние из Git!
kubectl get deployment inventory-service
# NAME                READY   UP-TO-DATE   AVAILABLE   AGE
# inventory-service   2/2     2            2           10m
```

**`reconciliation-diagram.txt`**


## Под капотом

`argocd-application-controller` строит в оперативной памяти древовидную модель объектов. Сравнение производится не простым сравнением строк, а алгоритмом нормализации JSON. Системные поля, генерируемые самим Kubernetes (`metadata.resourceVersion`, `metadata.uid`, `metadata.generation`, `status`), автоматически маскируются и исключаются из диффа. Если оставшиеся бизнес-поля различаются, контроллер инициирует Server-Side Apply или Two-way Merge Patch для восстановления эталона.

## Подводные камни

1. Забытый флаг `selfHeal: true`: при выключенном selfHeal ArgoCD только подсветит приложение желтым цветом (`OutOfSync`), но НЕ станет исправлять ручные изменения, оставляя кластер в рассинхронизированном состоянии.
2. Конфликт с HPA: если HPA меняет поле `spec.replicas`, ArgoCD при включенном `selfHeal` будет постоянно воевать с HPA. Для полей, управляемых внешними контроллерами, необходимо объявлять `ignoreDifferences`.

## На собеседовании

**Вопрос с собеседования:** «Что делает ArgoCD, если в Git закоммичен заведомо невалидный манифест с синтаксической ошибкой?»
**Ответ:** На этапе рендеринга `repo-server` или при вызове `dry-run` валидации API-сервера K8s ArgoCD зафиксирует ошибку валидации схемы. Приложение перейдет в статус `Sync Failed`. При этом **существующие работающие поды и ресурсы в кластере НЕ будут затронуты или удалены**! Предыдущая стабильная версия продолжит обслуживать пользователей, а команда получит алерт о поломке синхронизации в Slack/PagerDuty.
