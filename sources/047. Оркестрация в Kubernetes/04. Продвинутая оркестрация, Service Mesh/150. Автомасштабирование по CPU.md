# Автомасштабирование по CPU: нагрузочное тестирование с утилитой hey

## Условие

**Автомасштабирование (HPA - Horizontal Pod Autoscaler)**: Если нагрузка выросла, K8s может сам увеличивать число подов. Создай HPA-ресурс, который следит за CPU. Укажи правило: если среднее использование CPU > 70%, масштабировать до 10 реплик. Запусти утилиту нагрузочного тестирования (например, `hey`) на свой Ingress и смотри (`kubectl get hpa`), как кластер сам поднимает новые инстансы твоего приложения!

## Теория

Практическая проверка работы Horizontal Pod Autoscaler под реальной нагрузкой:
1. **Инструменты генерации нагрузки:**
   - **`hey`** — высокопроизводительный HTTP-генератор нагрузки на Go (замена утилите ApacheBench `ab`), умеющий генерировать тысячи одновременных запросов с указанием RPS (`-q`) и числа воркеров (`-c`).
2. **Динамика автомасштабирования:**
   - При старте генерации нагрузки процесс в Go начинает интенсивно утилизировать CPU.
   - Metrics Server фиксирует рост утилизации с 5% до 180% от `resources.requests.cpu`.
   - HPA вычисляет целевое число реплик и ступенчато масштабирует Deployment от 1 до 10 подов.
   - Нагрузка равномерно распределяется через Service между новыми подами, и средний CPU опускается обратно к целевой отметке 70%.

## Решение по шагам

1. Создайте Deployment с `resources.requests.cpu: 100m`.
2. Создайте HPA с диапазоном реплик 1..10 и порогом `averageUtilization: 70`.
3. Опубликуйте сервис через Ingress.
4. Запустите генерацию нагрузки утилитой `hey`: `hey -z 60s -c 50 -q 500 http://api.local/cpu-burn`.
5. Отслеживайте динамику изменения реплик командой `kubectl get hpa -w`.

## Код решения

**`hpa-scale.yaml`**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cpu-hpa-demo
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: cpu-demo-app
  minReplicas: 1
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"net/http"
)

func cpuBurnHandler(w http.ResponseWriter, r *http.Request) {
	// Интенсивные математические вычисления для нагрузки CPU
	x := 0.0001
	for i := 0; i <= 1000000; i++ {
		x += math.Sqrt(x)
	}
	fmt.Fprintf(w, "OK: CPU burn calculated: %f\n", x)
}

func main() {
	http.HandleFunc("/cpu-burn", cpuBurnHandler)
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("OK"))
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

**`Терминал`**

```bash
# Применение манифеста HPA
kubectl apply -f hpa-scale.yaml

# Запуск генератора нагрузки hey на 60 секунд (50 параллельных соединений)
hey -z 60s -c 50 http://myapp.local/cpu-burn

# Наблюдение за автоматическим увеличением числа реплик в реальном времени
kubectl get hpa cpu-hpa-demo -w
# NAME           REFERENCE                 TARGETS    MINPODS   MAXPODS   REPLICAS   AGE
# cpu-hpa-demo   Deployment/cpu-demo-app   0%/70%     1         10        1          10s
# cpu-hpa-demo   Deployment/cpu-demo-app   185%/70%   1         10        3          30s
# cpu-hpa-demo   Deployment/cpu-demo-app   240%/70%   1         10        7          50s
# cpu-hpa-demo   Deployment/cpu-demo-app   68%/70%    1         10        10         75s
```

## Под капотом

Каждые 15 секунд HPA Controller считывает метрики через `Metrics API`. Получив значение утилизации 240%, алгоритм вычисляет: \(\text{Replicas} = \lceil 3 \times (240 / 70) \rceil = 10\). Контроллер отправляет запрос в API на масштабирование Deployment до 10 реплик. Срабатывает ReplicaSet, Kube-scheduler распределяет новые поды по нодам кластера, а kube-proxy добавляет их IP в Endpoints балансировщика.

## Подводные камни

1. Отсутствие ограничений `maxReplicas`: если выставить `maxReplicas: 500`, при DoS-атаке кластер попытается заказать сотни серверов в облаке, что приведет к исчерпанию лимитов аккаунта и огромным финансовым счетам.
2. Не задан `resources.limits.cpu`: если задан только `requests: 100m`, а лимита нет, один Pod может занять все 16 ядер ноды, не давая другим подам нормально работать.

## На собеседовании

**Вопрос с собеседования:** «Почему после завершения нагрузочного теста HPA не уменьшает количество подов сразу обратно до 1 реплики, а ждет несколько минут?»
**Ответ:** За это отвечает механизм **Scale-Down Stabilization Window** (по умолчанию 300 секунд / 5 минут). Если бы HPA уменьшал поды мгновенно после прекращения трафика, то в реальном продакшене при волнообразной нагрузке происходил бы разрушительный флаппинг (thrashing): поды бы то непрерывно создавались, то уничтожались каждые 20 секунд, создавая огромные накладные расходы на инициализацию и прогрев кэшей.
