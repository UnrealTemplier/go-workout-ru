# Сквозное тестирование в кластере: Kuttl, Helm Test и Kind в CI/CD

## Условие

Настрой **E2E Testing in Kubernetes**: ` kuttl` or `helm test`. Spin up test namespace, deploy app + dependencies, run tests, cleanup. CI integration: `kind` cluster in GitHub Actions. Покажи testing in production-like environment.

## Теория

Тестирование микросервисов только на unit- и компонентном уровне оставляет слепую зону: ошибки конфигурации RBAC, некорректные NetworkPolicy, проблемы Service Discovery и монтирования томов проявляются только в реальном кластере Kubernetes.
**Подход Kubernetes E2E Testing (Shift-Left):**
1. **GitHub Actions + Kind:**
   - Внутри эфемерной виртуальной машины CI за 20 секунд поднимается настоящий кластер Kubernetes (`kind-action`).
2. **Kuttl (KUbernetes Test Tool от CNCF/D2iQ):**
   - Декларативный инструмент тестирования манифестов K8s: описывает тесты в виде шагов (директории `00-install/`, `01-assert/`).
   - Шаг `00-install/`: создание тестового namespace, деплой сервиса и зависимостей.
   - Шаг `01-assert/`: декларативная проверка желаемого состояния (например, проверка того, что Pod перешел в `Ready`, и сервис вернул HTTP 200).
3. **Автоматический Cleanup:**
   - По окончании тестов Kuttl или CI-раннер удаляет временный namespace или уничтожает весь Kind-кластер целиком.

## Решение по шагам

1. Создайте тест-сьют Kuttl для проверки запуска микросервиса.
2. Опишите шаг применения ресурсов `00-deploy.yaml`.
3. Опишите шаг утверждения состояния `00-assert.yaml`.
4. Настройте workflow-файл GitHub Actions с матрицей Kind.
5. Запустите E2E-тест и проверьте прохождение сценариев.

## Код решения

**`tests/e2e/kuttl-test.yaml`**

```yaml
apiVersion: kuttl.dev/v1beta1
kind: TestSuite
metadata:
  name: microservice-e2e
spec:
  testDirs:
    - tests/e2e/scenarios
  startKIND: false
  timeout: 60
```

**`tests/e2e/scenarios/01-smoke/00-deploy.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: e2e-target-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: e2e-target-app
  template:
    metadata:
      labels:
        app: e2e-target-app
    spec:
      containers:
        - name: app
          image: test-registry/my-app:ci-test
          ports:
            - containerPort: 8080
```

**`tests/e2e/scenarios/01-smoke/00-assert.yaml`**

```yaml
# Kuttl ожидает, пока реальное состояние не совпадет с этим эталоном
apiVersion: apps/v1
kind: Deployment
metadata:
  name: e2e-target-app
status:
  availableReplicas: 1
  readyReplicas: 1
```

**`.github/workflows/e2e.yaml`**

```yaml
name: Kubernetes E2E Tests
on: [pull_request]

jobs:
  k8s-e2e:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Create Kind Cluster
        uses: helm/kind-action@v1.8.0
        with:
          cluster_name: kind-ci-test

      - name: Build and Load Docker Image into Kind
        run: |
          docker build -t test-registry/my-app:ci-test .
          kind load docker-image test-registry/my-app:ci-test --name kind-ci-test

      - name: Run Kuttl E2E Tests
        run: |
          curl -sSL https://kuttl.dev/install.sh | bash
          kubectl-kuttl test --config tests/e2e/kuttl-test.yaml
```

## Под капотом

Kuttl загружает манифесты шага `00-deploy.yaml` в API-сервер Kubernetes, а затем запускает цикл периодического опроса (polling loop) ресурсов, описанных в `00-assert.yaml`. Сравнение выполняется на уровне JSON-документов: если все указанные поля (например, `status.readyReplicas: 1`) совпали до истечения таймаута, тест считается успешно пройденным. При расхождении Kuttl выводит подробный дифф несовпавших полей.

## Подводные камни

1. Забытый шаг `kind load docker-image`: свежесобранный локальный Docker-образ находится в демоне Docker хоста, а не внутри контейнеров нод Kind. Без команды `kind load` поды упадут с ошибкой `ErrImagePull`.
2. Жесткие таймауты: на бесплатных CI-раннерах GitHub Actions pull базовых образов может занимать до 40 секунд. Задавайте таймауты в `TestSuite` не менее 60-120 секунд.

## На собеседовании

**Вопрос с собеседования:** «Чем запуск интеграционных тестов внутри эфемерного кластера Kind в CI лучше, чем тестирование на постоянном общем Staging-кластере?»
**Ответ:** 1) **Изоляция и воспроизводимость:** Каждый Pull Request получает свой собственный чистый кластер, исключая взаимное влияние параллельных сборок (No Flaky Tests); 2) **Тестирование инфраструктурных манифестов:** Можно безопасно тестировать изменения CRD, ClusterRole и NetworkPolicies, что запрещено делать на общем Staging из соображений безопасности; 3) **Экономия:** Эфемерный Kind-кластер существует только во время выполнения пайплайна и не потребляет ресурсы в простое.
