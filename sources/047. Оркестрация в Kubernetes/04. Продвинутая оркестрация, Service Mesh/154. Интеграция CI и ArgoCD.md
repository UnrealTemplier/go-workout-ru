# Интеграция CI и ArgoCD: автоматическое обновление тегов образов в Git

## Условие

Интегрируйте ArgoCD с CI: CI билдит и пушит Docker image, обновляет tag в Git репозитории, ArgoCD автоматически деплоит.

## Теория

Связывание CI-конвейера сборки с GitOps-конвейером развертывания через фиксацию версий:
1. **Принцип неизменяемости (Immutability):**
   - Каждый Docker-образ помечается уникальным тегом: короткий SHA коммита Git (например, `sha-4a9c12f`) или SemVer-тег (`v1.8.2`).
   - Использование тега `latest` в production категорически запрещено!
2. **Механика связки CI \(\rightarrow\) GitOps:**
   - CI-раннер собирает и тестирует Go-код.
   - CI-раннер пушит Docker-образ в Container Registry (GitHub Packages, Harbor).
   - CI-раннер клонирует конфигурационный Git-репозиторий манифестов, запускает `kustomize edit set image` и делает `git commit` от имени служебного сервисного бота.
   - ArgoCD обнаруживает новый коммит в ветке `main` и запускает развертывание в кластере.

## Решение по шагам

1. Настройте файл сборщика GitHub Actions `.github/workflows/deploy.yaml`.
2. Добавьте шаги сборки и публикации контейнерного образа с SHA-тегом.
3. Настройте SSH-ключ или Personal Access Token с правами записи в репозиторий манифестов.
4. Выполните команду `kustomize edit set image` в CI.
5. Проверьте автоматический запуск деплоя в ArgoCD.

## Код решения

**`.github/workflows/ci-cd.yaml`**

```yaml
name: Build, Scan and Deploy to GitOps
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Application Code
        uses: actions/checkout@v4

      - name: Setup Go
        uses: actions/setup-go@v5
        with:
          go-version: '1.23'

      - name: Run Tests
        run: go test -race -v ./...

      - name: Log in to Docker Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and Push Docker Image
        id: docker_build
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: |
            ghcr.io/my-org/backend-service:${{ github.sha }}
            ghcr.io/my-org/backend-service:latest

      - name: Update GitOps Configuration Repository
        env:
          GITOPS_REPO_TOKEN: ${{ secrets.GITOPS_DEPLOY_KEY }}
          SHORT_SHA: ${{ github.sha }}
        run: |
          git config --global user.name "GitOps-Deployer-Bot"
          git config --global user.email "deploy-bot@company.internal"
          
          # Клонирование репозитория манифестов
          git clone https://x-access-token:${GITOPS_REPO_TOKEN}@github.com/my-org/k8s-gitops.git /tmp/gitops
          cd /tmp/gitops/apps/backend-service/overlays/prod
          
          # Обновление тега образа через Kustomize
          kustomize edit set image ghcr.io/my-org/backend-service=ghcr.io/my-org/backend-service:${SHORT_SHA}
          
          git add kustomization.yaml
          git commit -m "Auto-deploy: update backend-service to commit ${SHORT_SHA} [skip ci]"
          git push origin main
```

## Под капотом

После того как бот отправляет коммит в репозиторий `k8s-gitops`, GitHub отправляет HTTP POST запрос (Webhook) на URL `https://argocd.corp/api/webhook`. Сервер ArgoCD валидирует подпись HMAC вебхука, немедленно сбрасывает 3-минутный таймер поллинга репозитория, запускает рендеринг манифестов и накатывает новый образ в кластер менее чем за 5 секунд после завершения CI.

## Подводные камни

1. Отсутствие флага `[skip ci]` в сообщении коммита: если репозиторий манифестов имеет собственные CI-проверки (линтеры, тесты), коммит бота может запустить рекурсивный шквал сборок.
2. Состояние гонки (Race Condition) в монорепозитории: если 5 микросервисов параллельно обновляют манифесты в одном GitOps-репозитории, 4 из них упадут с ошибкой `git push rejected` (non-fast-forward). Решение — использование механизма pull-with-rebase в цикле с повторами или переход на ArgoCD Image Updater.

## На собеседовании

**Вопрос с собеседования:** «Почему в GitOps-пайплайнах CI конвейеру категорически запрещается выполнять команду `kubectl set image` напрямую в кластере?»
**Ответ:** Прямой вызов `kubectl` нарушает центральную догму GitOps: **Git перестает быть единственным источником правды**. Если образ обновился в кластере, но не зафиксирован в Git, то: 1) Невозможно понять по истории репозитория, какая версия сейчас реально работает в бою; 2) При перезапуске пода или повторной синхронизации ArgoCD перезапишет новый образ старой версией из Git; 3) Невозможно выполнить аудит изменений и экстренный откат через `git revert`.
