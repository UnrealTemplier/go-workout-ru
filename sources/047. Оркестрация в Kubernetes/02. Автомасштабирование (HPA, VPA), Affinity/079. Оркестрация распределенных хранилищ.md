# Оркестрация распределенных хранилищ (Redis Cluster, Kafka) через StatefulSet

## Условие

Создайте **StatefulSet** для stateful приложений (например, Redis Cluster, Kafka brokers).

## Теория

Развертывание распределенных СУБД (Redis Cluster, Kafka, ScyllaDB) в Kubernetes:
- Каждая нода хранилища требует строго фиксированного DNS-имени (`redis-0`, `redis-1`, `redis-2`).
- Каждая нода должна владеть собственным независимым диском (Persistent Volume).
- Порядок старта и топология узлов строго фиксированы.
- Управление реализуется через `StatefulSet` в связке с `Headless Service`.

## Решение по шагам

1. Создайте Headless Service `redis-service` с `clusterIP: None`.
2. Опишите `StatefulSet` с 3 репликами Redis.
3. Добавьте `volumeClaimTemplates` с запросом диска 5Gi.
4. Примените манифесты: `kubectl apply -f redis-stateful.yaml`.
5. Проверьте стабильность имен подов и связку с PersistentVolumeClaims.

## Код решения

**`redis-stateful.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: redis-cluster
  labels:
    app: redis
spec:
  clusterIP: None
  selector:
    app: redis
  ports:
    - port: 6379
      name: client
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis-node
spec:
  serviceName: "redis-cluster"
  replicas: 3
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - containerPort: 6379
          volumeMounts:
            - name: redis-data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: [ "ReadWriteOnce" ]
        resources:
          requests:
            storage: 5Gi
```

**`check-redis.sh`**

```bash
# Просмотр статуса подов StatefulSet
kubectl get pods -l app=redis

# Просмотр уникальных томов для каждого пода
kubectl get pvc -l app=redis
```

## Под капотом

StatefulSet Controller создает поды последовательно с предсказуемыми именами. При удалении пода связанный том PVC сохраняется в etcd и повторно монтируется к тому же поду при его восстановлении.

## Подводные камни

1. Использование обычного Deployment для баз данных с репликацией: при рестарте поды перепутают диски и данные разрушатся.
2. Ручное удаление StatefulSet без флага каскадного удаления.
3. Отсутствие PDB для защиты кворума реплик.

## На собеседовании

**Вопрос с собеседования:** Почему базы данных в Kubernetes чаще разворачивают через специализированные Операторы (например, Zalando Postgres Operator или CloudNativePG), а не голыми StatefulSet?
**Ответ:** Голый `StatefulSet` умеет только упорядоченно создавать поды и монтировать диски. Он ничего не знает о внутренней специфике базы данных: он не умеет переключать Master при падении (Failover), не умеет настраивать потоковую репликацию (Streaming Replication), делать инкрементальные бэкапы в S3 (WAL-G) и выполнять плавающее обновление без потери транзакций. Все эти сложные задачи автоматизирует специализированный **Kubernetes Operator**.
