# Локальное тестирование в Minikube/Kind и проброс портов через kubectl port-forward

## Условие

Разверните приложение в локальном Kubernetes (minikube/kind) и проверьте доступ через `kubectl port-forward`.

## Теория

При локальной разработке микросервисов разработчики используют легковесные дистрибутивы Kubernetes:
- **`Minikube`:** Разворачивает одноузловой кластер внутри виртуальной машины или Docker-контейнера.
- **`Kind` (Kubernetes in Docker):** Запускает ноды кластера как контейнеры Docker (быстрый старт, идеально для CI).

Команда **`kubectl port-forward`**:
- Создает двунаправленный защищенный TCP-туннель между локальным портом вашего ноутбука (`localhost:8080`) и внутренним портом пода или сервиса в кластере.
- Не требует настройки Ingress, Service LoadBalancer или внешних DNS.
- Идеальный инструмент для отладки приватных баз данных, Redis или gRPC сервисов.

## Решение по шагам

1. Разверните сервис `db-service` в локальном кластере.
2. Выполните команду проброса портов: `kubectl port-forward svc/db-service 5432:5432`.
3. Подключитесь к базе данных с локального клиента Go по адресу `localhost:5432`.
4. Убедитесь в успешной передаче трафика по туннелю.
5. Завершите сессию туннелирования сочетанием клавиш `Ctrl+C`.

## Код решения

**`port-forward.sh`**

```bash
# Проброс порта локального ноутбука на Service в кластере
kubectl port-forward svc/internal-api 8080:80

# Пример вывода:
# Forwarding from 127.0.0.1:8080 -> 8080
# Forwarding from [::1]:8080 -> 8080
# Handling connection for 8080

# В другом терминале: локальный вызов внутреннего сервиса
curl http://localhost:8080/health
```

**`client.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
)

func main() {
	// Подключение через порт, проброшенный утилитой port-forward:
	resp, err := http.Get("http://localhost:8080/health")
	if err != nil {
		panic(err)
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("Успешный ответ из кластера через туннель: %s\n", string(body))
}
```

## Под капотом

`kubectl port-forward` открывает локальный слушающий TCP-сокет на машине разработчика. При входящем подключении утилита шлет POST запрос `Upgrade: SPDY / WebSocket` на K8s API Server. 

API Server связывается с демоном `kubelet` ноды через CRI стриминг. Kubelet открывает TCP-сокет к сетевому пространству имен целевого пода и мультиплексирует поток байтов.

## Подводные камни

1. Использование `port-forward` в продакшне: туннель не рассчитан на высокие нагрузки и падает при обрыве связи с API-сервером.
2. Занятый локальный порт: ошибка `bind: address already in use`.
3. Разрыв соединения при перезапуске пода: port-forward привязан к конкретному поду или его текущему IP.

## На собеседовании

**Вопрос с собеседования:** Почему `kubectl port-forward` не масштабируется для production-трафика и чем он отличается от Ingress?
**Ответ:** `port-forward` — это инструмент отладки. Трафик идет через управляющий уровень кластера (Control Plane): каждый пакет проходит через K8s API Server и Kubelet, создавая высокую нагрузку на мастер-ноды кластера и их etcd-связи. 
Ingress и Service работают на уровне данных (Data Plane): трафик идет напрямую с балансировщика нагрузки на рабочие ноды через оптимизированные драйверы ядра Linux, обеспечивая миллионы запросов в секунду.
