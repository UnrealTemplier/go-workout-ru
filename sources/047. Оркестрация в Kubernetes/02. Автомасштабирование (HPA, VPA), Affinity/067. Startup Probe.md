# Startup Probe: изоляция 30-секундной миграции БД от проверок Liveness

## Условие

**[Startup Probe]**: Если твое приложение долго стартует (например, мигрирует БД 30 секунд), Liveness-проба может убить его до старта. Добавь `startupProbe` с `failureThreshold: 30`.

## Теория

Если приложение при запуске выполняет внутреннюю миграцию базы данных или прогрев кэша в течение 30 секунд:
- Обычная `livenessProbe` с периодом 5 секунд убьет под на 15-й секунде по `failureThreshold: 3`.
- Использование `startupProbe` с параметрами `failureThreshold: 10, periodSeconds: 5` выделяет до 50 секунд на старт.
- Проверки liveness и readiness остаются заблокированными до полного завершения миграции.

## Решение по шагам

1. Настройте `startupProbe` в `deployment.yaml`.
2. Задайте `failureThreshold: 10` и `periodSeconds: 5`.
3. В коде Go добавьте симуляцию 30-секундной миграции БД перед переводом флага готовности в true.
4. Разверните сервис.
5. Убедитесь, что Kubelet ожидает завершения старта без рестартов.

## Код решения

**`startup-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: migration-aware-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mig-app
  template:
    metadata:
      labels:
        app: mig-app
    spec:
      containers:
        - name: app
          image: ghcr.io/company/mig-app:v1.0.0
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            failureThreshold: 10 # 10 * 5с = 50 секунд на старт
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync/atomic"
	"time"
)

var isInitialized atomic.Bool

func main() {
	go func() {
		fmt.Println("Запуск 30-секундной миграции базы данных...")
		time.Sleep(30 * time.Second)
		isInitialized.Store(true)
		fmt.Println("Миграция завершена. Сервис готов!")
	}()

	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		if !isInitialized.Load() {
			w.WriteHeader(http.StatusServiceUnavailable)
			_, _ = w.Write([]byte("MIGRATING"))
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Kubelet удерживает статус `Started: False` в `status.containerStatuses`. Пока этот флаг ложен, вызовы livenessProbe подавляются.

## Подводные камни

1. Заниженный `failureThreshold`: рестарт пода прямо посреди миграции БД.
2. Неперехваченные паники во время старта.
3. Отсутствие таймаутов на сетевых вызовах к СУБД.

## На собеседовании

**Вопрос с собеседования:** Почему запуск тяжелых миграций БД внутри `main()` самого веб-сервиса считается плохой практикой по сравнению с K8s Job?
**Ответ:** Если развернуть Deployment из 10 реплик, все 10 подов одновременно стартуют и попытаются параллельно накатить одни и те же DDL-миграции схемы на базу данных. Это вызывает взаимные блокировки таблиц (Exclusive Table Locks) и падение транзакций. 
Правильный подход — выносить миграции схемы в отдельный **K8s Job** (или Helm pre-upgrade hook), который запускается ровно в **одном экземпляре** до старта веб-серверов.
