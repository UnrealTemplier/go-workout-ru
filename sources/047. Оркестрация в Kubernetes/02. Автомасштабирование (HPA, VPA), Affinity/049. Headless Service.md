# Headless Service: прямое обнаружение подов по DNS и интеграция со StatefulSet

## Условие

Настрой **Headless Service**: `clusterIP: None`. DNS: `postgres-0.postgres.default.svc.cluster.local`. Используй для StatefulSet peer discovery. Покажи, как pods находят друг друга.

## Теория

Обычный сервис направляет трафик на виртуальный ClusterIP, выполняя балансировку случайным образом.

**`Headless Service` (`clusterIP: None`)**:
- Не выделяет виртуальный IP-адрес и не использует kube-proxy.
- CoreDNS возвращает список реальных IP-адресов **всех готовых подов** в виде нескольких A-записей.
- При связке со `StatefulSet` CoreDNS генерирует индивидуальные DNS-записи для каждого пода:
  `<pod-name>.<service-name>.<namespace>.svc.cluster.local` (например, `postgres-0.postgres.default.svc.cluster.local`).
- Это критично для баз данных с репликацией (Master-Slave), где клиенты должны подключаться напрямую к конкретной ноде.

## Решение по шагам

1. Создайте `headless-service.yaml` с `clusterIP: None`.
2. Задайте селектор `app: db`.
3. Примените манифест.
4. Выполните DNS-запрос через `nslookup` из временного контейнера.
5. Убедитесь, что DNS возвращает прямые IP всех подов.

## Код решения

**`headless-service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: db-headless
spec:
  clusterIP: None # Ключевой параметр Headless Service
  selector:
    app: db
  ports:
    - port: 5432
      name: postgresql
```

**`dns-test.sh`**

```bash
# Проверка DNS резолвинга Headless Service:
kubectl run dnsutils --rm -it --image=tianon/speedtest -- nslookup db-headless

# Пример ответа: возвращаются прямые IP-адреса всех подов:
# Name:   db-headless.default.svc.cluster.local
# Address: 10.244.1.15
# Address: 10.244.2.28
# Address: 10.244.3.42
```

## Под капотом

Плагин `kubernetes` в CoreDNS подключен к API Server через Watch. 

При запросе обычного сервиса CoreDNS возвращает единственную запись ClusterIP. При запросе Headless Service CoreDNS считывает связанный объект `Endpoints`/`EndpointSlice` и возвращает массив записей `A` со всеми IP адресами готовых подов.

## Подводные камни

1. Опечатка в `clusterIP: None` (например, пустая строка): K8s автоматически выделит обычный ClusterIP.
2. Кэширование DNS на стороне Go-клиента: если стандартный DNS-клиент закэширует IP, он продолжит слать запросы на упавший под.
3. Попытка настроить Headless Service без селектора.

## На собеседовании

**Вопрос с собеседования:** Как Go gRPC клиент использует Headless Service для клиентской балансировки (Client-Side Load Balancing)?
**Ответ:** Go gRPC клиент использует встроенный DNS-резолвер:
`conn, err := grpc.Dial("dns:///my-headless-service:50051", grpc.WithDefaultServiceConfig(`{"loadBalancingConfig": [{"round_robin":{}}]}`))`
Резолвер периодически опрашивает Headless Service, получает список IP всех подов и распределяет каждый отдельный RPC-вызов по кругу (Round-Robin) между TCP-соединениями к разным подам, решая проблему балансировки долгоживущих HTTP/2 соединений без внешних прокси.
