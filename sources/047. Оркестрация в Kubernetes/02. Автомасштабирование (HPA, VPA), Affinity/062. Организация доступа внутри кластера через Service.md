# Организация доступа внутри кластера через Service (ClusterIP) и селекторы меток

## Условие

**Доступ внутри кластера (Service)**: Поды имеют динамические IP, к ним нельзя обращаться напрямую. Создай `service.yaml` (тип `ClusterIP`). Он создаст стабильный внутренний IP и DNS-имя, балансируя нагрузку между твоими тремя подами.

## Теория

Поды в Kubernetes эфемерны: они пересоздаются с новыми динамическими IP-адресами при каждом деплое или масштабировании.

Ресурс **`Service` типа `ClusterIP`**:
- Присваивает стабильное внутреннее DNS-имя и постоянный виртуальный IP.
- Селектор `selector: app: auth` непрерывно сопоставляется с метками подов.
- Автоматически распределяет входящий трафик между живыми подами через `Endpoints`.

## Решение по шагам

1. Создайте `deployment.yaml` с меткой `app: core-api`.
2. Создайте `service.yaml` с типом `ClusterIP` и соответствующим селектором.
3. Примените манифесты.
4. Проверьте список активных адресов через `kubectl get endpoints core-api-svc`.
5. Протестируйте доступ по внутреннему DNS-имени.

## Код решения

**`service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: core-api-svc
spec:
  type: ClusterIP
  selector:
    app: core-api
  ports:
    - name: http
      port: 80
      targetPort: 8080
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: core-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: core-api
  template:
    metadata:
      labels:
        app: core-api
    spec:
      containers:
        - name: app
          image: alpine:3.21
          command: ["sleep", "3600"]
          ports:
            - containerPort: 8080
```

## Под капотом

CoreDNS сопоставляет имя `core-api-svc` с виртуальным ClusterIP. Kube-proxy транслирует обращения к этому IP в цепочки iptables/IPVS на ноде, перенаправляя трафик на реальные IP подов.

## Подводные камни

1. Опечатка в `selector.app`: `Endpoints` будет пустым `<none>`.
2. Попытка подключения с внешней машины напрямую к ClusterIP.
3. Несовпадение портов `port` и `targetPort`.

## На собеседовании

**Вопрос с собеседования:** Как устроен механизм обнаружения сервисов (Service Discovery) в Kubernetes без внешнего Consul или Eureka?
**Ответ:** K8s использует встроенный DNS-сервер (CoreDNS). При создании Service создается A-запись `<service>.<namespace>.svc.cluster.local`. В `/etc/resolv.conf` каждого пода Kubelet автоматически прописывает IP CoreDNS и поисковые суффиксы. 
Любой микросервис на Go может просто обращаться по HTTP к `http://core-api-svc/`, а балансировку и трансляцию адресов берет на себя уровень ядра Linux (Kube-proxy iptables/IPVS).
