# Автоматизация миграций схемы базы данных через Init Containers

## Условие

Используйте **Init Containers** для запуска миграций БД перед стартом основного приложения.

## Теория

Применение паттерна `Init Containers` для выполнения миграций схемы БД:
- Init-контейнер запускает утилиту миграций (`goose`, `golang-migrate`) перед стартом веб-сервера.
- Если миграция падает, основной контейнер не запускается.
- Исключается запуск кода приложения со старой схемой данных.

## Решение по шагам

1. Создайте манифест `deployment.yaml` с `initContainers`.
2. Настройте запуск бинарника мигратора `migrate -path /migrations -database $DSN up`.
3. В основном контейнере настройте запуск веб-сервера Go.
4. Примените манифест.
5. Убедитесь в логах, что миграция выполнена до старта сервера.

## Код решения

**`migration-deploy.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
    spec:
      initContainers:
        - name: run-db-migrations
          image: migrate/migrate:v4.17.0
          command:
            - /migrate
            - -path=/migrations
            - -database=$(DATABASE_URL)
            - up
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: DSN
      containers:
        - name: app
          image: ghcr.io/company/user-service:v1.0.0
          ports:
            - containerPort: 8080
```

## Под капотом

Kubelet ждет завершения процесса `migrate` с кодом 0. При падении контейнер перезапускается в соответствии с политикой экспоненциальной задержки.

## Подводные камни

1. Запуск миграций в Init-контейнере при нескольких репликах (`replicas: 5`): 5 подов начнут одновременно применять DDL миграции, вызывая блокировки. Для мультиреплик миграции выносят в отдельный `Job`.
2. Отсутствие таймаута миграции.
3. Несовместимые с предыдущей версией деструктивные миграции (DROP COLUMN).

## На собеседовании

**Вопрос с собеседования:** Почему при горизонтальном масштабировании (`replicas > 1`) запуск миграций внутри `initContainers` опасен, и как правильно организовывать миграции БД?
**Ответ:** При старте 5 реплик все 5 initContainers одновременно подключатся к базе и начнут исполнять `migrate up`. Даже при наличии транзакционных локов в БД это создает огромную нагрузку и риск дедлоков. 
В BigTech используют подход **Expand/Contract (двухфазные неломающие миграции)**: миграция запускается строго в **одном экземпляре через K8s Job** до развертывания новой версии. Код пишется так, чтобы новая схема поддерживала и старую версию приложения (Backward Compatibility), и новую.
