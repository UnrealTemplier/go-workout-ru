# Управление системными агентами на каждой ноде: манифест DaemonSet

## Условие

Настрой **DaemonSet**: `kind: DaemonSet`. Запускает по одному pod на каждом node. Используй для: log collectors (Fluent Bit), monitoring agents (node-exporter), CNI plugins. Покажи node-level services.

## Теория

В то время как `Deployment` масштабирует произвольное число подов в кластере, **`DaemonSet` (`apiVersion: apps/v1`)** гарантирует, что **ровно один экземпляр пода запущен на каждой рабочей ноде кластера**:
- При добавлении новой ноды в кластер DaemonSet автоматически разворачивает на ней под.
- При удалении ноды под уничтожается сборщиком мусора.

Типичные сценарии применения DaemonSet:
1. **Сборщики логов:** Fluentbit, Vector, Promtail (читают `/var/log/pods` с диска ноды).
2. **Мониторинг инфраструктуры:** Prometheus Node Exporter.
3. **Сетевые агенты CNI:** Cilium, Calico (управление BPF/iptables на ноде).
4. **Хранилища данных:** Ceph, GlusterFS, Rook.

## Решение по шагам

1. Создайте манифест `daemonset.yaml` с `kind: DaemonSet`.
2. Задайте селектор `app: node-monitor`.
3. Опишите контейнер с экспортером метрик.
4. Примените манифест: `kubectl apply -f daemonset.yaml`.
5. Проверьте, что количество подов в выводе `kubectl get ds` строго равно количеству нод в кластере.

## Код решения

**`daemonset.yaml`**

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-monitor
  namespace: kube-system
  labels:
    app: node-monitor
spec:
  selector:
    matchLabels:
      app: node-monitor
  template:
    metadata:
      labels:
        app: node-monitor
    spec:
      tolerations:
        # Разрешить запуск на Master / Control-plane нодах:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
      containers:
        - name: exporter
          image: prom/node-exporter:v1.8.2
          ports:
            - containerPort: 9100
              hostPort: 9100 # Прямой проброс на порт ноды
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 100m
              memory: 128Mi
```

**`verify-ds.sh`**

```bash
# Просмотр статуса DaemonSet
kubectl get ds -n kube-system node-monitor

# Проверка: число подов строго равно числу нод:
kubectl get nodes
kubectl get pods -n kube-system -l app=node-monitor -o wide
```

## Под капотом

`DaemonSetController` слушает события `NodeAdd` и `NodeDelete`. 

Для каждой зарегистрированной ноды контроллер проверяет наличие пода с соответствующим `nodeName`. Если нода готова, контроллер создает под с заранее заполненным полем `spec.nodeName`, минуя стандартный цикл работы `kube-scheduler`.

## Подводные камни

1. Забытый toleration для Control-Plane: DaemonSet не запустится на мастер-нодах из-за дефолтных taints.
2. Конфликт `hostPort`: два разных DaemonSet не могут занять один и тот же `hostPort` на одной ноде.
3. Отсутствие лимитов памяти: сбойный лог-коллектор на DaemonSet может съесть всю память сервера.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `hostPort` и `NodePort` в Kubernetes?
**Ответ:** 
- **`hostPort`** привязывает порт контейнера **напрямую к сетевому интерфейсу той конкретной ноды**, где запущен данный под. Трафик не маршрутизируется через kube-proxy на другие ноды. Используется почти исключительно в DaemonSet (node-exporter).
- **`NodePort`** открывает порт на **всех нодах кластера одновременно**, независимо от того, запущен ли под на данной конкретной ноде. Трафик с любой ноды перенаправляется через kube-proxy на любую ноду, где работает под.
