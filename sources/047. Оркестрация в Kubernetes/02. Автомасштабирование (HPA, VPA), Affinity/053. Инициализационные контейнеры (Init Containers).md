# Инициализационные контейнеры (Init Containers): ожидание готовности PostgreSQL

## Условие

**[Init Containers]**: Напиши Pod с `initContainer`, который ждет, пока PostgreSQL поднимется (использует `pg_isready` или `nc -z`). Только после успеха должен стартовать основной контейнер с твоим приложением.

## Теория

При старте пода основной сервис часто зависит от внешних ресурсов (база данных должна подняться и применить миграции). Если запустить сервис раньше БД, он упадет с ошибкой подключения.

**`Init Containers` (`spec.initContainers`)**:
- Запускаются **до старта основных контейнеров приложения**.
- Выполняются строго последовательно до успешного завершения с кодом 0 (`Completed`).
- Если init-контейнер падает, Kubelet перезапускает его в соответствии с `restartPolicy`.
- Идеальны для проверки готовности зависимостей (например, опрос утилитой `pg_isready` или `nc -z`).

## Решение по шагам

1. В манифесте `deployment.yaml` добавьте секцию `spec.template.spec.initContainers`.
2. Настройте легковесный образ `postgres:16-alpine`.
3. Добавьте команду цикла ожидания: `until pg_isready -h db-service -p 5432; do sleep 2; done`.
4. Разверните сервис.
5. Убедитесь по статусу пода `Init:0/1`, что K8s ожидает базу данных перед запуском Go-контейнера.

## Код решения

**`init-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-with-init
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app-with-init
  template:
    metadata:
      labels:
        app: app-with-init
    spec:
      initContainers:
        - name: wait-for-postgres
          image: postgres:16-alpine
          command:
            - /bin/sh
            - -c
            - |
              echo "Ожидание готовности PostgreSQL..."
              until pg_isready -h postgres-service -p 5432 -U postgres; do
                echo "База данных недоступна, повтор через 2 секунды..."
                sleep 2
              done
              echo "PostgreSQL готов к приему соединений!"
      containers:
        - name: backend
          image: ghcr.io/company/backend:v1.0.0
          ports:
            - containerPort: 8080
```

**`check-init.sh`**

```bash
# Просмотр статуса пода на этапе инициализации:
kubectl get pods -l app=app-with-init
# Вывод:
# NAME                             READY   STATUS     RESTARTS   AGE
# app-with-init-658f96489-7k8m2   0/1     Init:0/1   0          5s

# Просмотр логов init-контейнера:
kubectl logs pod/app-with-init-658f96489-7k8m2 -c wait-for-postgres
```

## Под капотом

Kubelet последовательно итерирует массив `spec.initContainers`. Для каждого элемента создается контейнер. 

Kubelet ждет события завершения процесса. Только когда статус контейнера переходит в `Terminated` с `ExitCode: 0`, Kubelet переходит к следующему init-контейнеру. Основные контейнеры приложения (`spec.containers`) вообще не создаются рантаймом до завершения всех initContainers.

## Подводные камни

1. Бесконечный цикл в initContainer без таймаута: если БД упала навсегда, под зависнет в `Init:0/1` навсегда.
2. Использование тяжелых образов для init-контейнера: замедляет холодный старт пода.
3. Пропуск флага `-c <name>` в `kubectl logs`: по умолчанию logs пытается прочитать логи основного контейнера, который еще даже не запущен.

## На собеседовании

**Вопрос с собеседования:** Могут ли `Init Containers` разделять данные с основными контейнерами приложения, и как это устроено?
**Ответ:** Да! Все контейнеры одного пода (включая initContainers и обычные контейнеры) имеют доступ к общим томам пода (`spec.volumes`). 
Классический паттерн: Init-контейнер монтирует том `emptyDir`, клонирует туда Git-репозиторий со статикой или скачивает конфигурационный файл с Vault/S3, а затем основной веб-сервер монтирует этот же том `emptyDir` в режиме read-only и раздает файлы.
