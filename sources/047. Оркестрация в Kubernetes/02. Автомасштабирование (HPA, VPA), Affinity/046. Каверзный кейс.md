# Каверзный кейс: настройка GOMEMLIMIT для предотвращения OOMKilled в Go

## Условие

**[Каверзный кейс — GOMEMLIMIT]**: Установи в контейнере лимит памяти `resources.limits.memory: 128Mi`. В коде Go сделай аллокацию большого слайса. Поймай `OOMKilled` (Out of Memory). Установи переменную окружения `GOMEMLIMIT=120MiB`, чтобы GC Go понимал лимиты cgroup и работал эффективнее.

## Теория

До версии Go 1.19 сборщик мусора (GC) не знал о лимитах памяти контейнера в cgroups. Он ориентировался только на переменную `GOGC` (запуск GC при удвоении размера кучи). 

Если контейнеру выделен лимит `limits.memory: 128Mi`, а сервис быстро аллоцировал 70 МБ, GC планировал следующий запуск при достижении \(70 \times 2 = 140\) МБ. Но при 128 МБ ядро Linux немедленно убивало контейнер по **OOMKilled** до того, как GC успевал освободить память!

В Go 1.19+ появилась переменная окружения **`GOMEMLIMIT`**:
- Жесткий ориентир (Soft Memory Limit) для рантайма Go.
- Рантайм Go начинает агрессивно запускать сборщик мусора, когда потребление приближается к `GOMEMLIMIT`, предотвращая падение по OOM.
- **Золотое правило:** `GOMEMLIMIT` выставляется на **85–90% от `resources.limits.memory`** (например, `115MiB` при лимите `128Mi`). Оставшиеся 10–15% резервируются под стек, память рантайма и внекучевые аллокации CGO.

## Решение по шагам

1. Задайте в манифесте `resources.limits.memory: 128Mi`.
2. Добавьте переменную окружения `GOMEMLIMIT: "115MiB"`.
3. Оставьте стандартный `GOGC: "100"`.
4. Запустите стресс-тест памяти в Go.
5. Убедитесь, что сервис не падает по OOM, а сборщик мусора своевременно счищает память.

## Код решения

**`gomemlimit-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: memory-safe-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mem-safe
  template:
    metadata:
      labels:
        app: mem-safe
    spec:
      containers:
        - name: app
          image: ghcr.io/company/mem-safe:v1.0.0
          env:
            # 90% от лимита контейнера 128Mi:
            - name: GOMEMLIMIT
              value: "115MiB"
            - name: GOGC
              value: "100"
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "128Mi"
              cpu: "500m" 
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"runtime"
	"runtime/debug"
)

func main() {
	fmt.Printf("GOMEMLIMIT настроен: %d байт\n", debug.SetMemoryLimit(-1))

	http.HandleFunc("/allocate", func(w http.ResponseWriter, r *http.Request) {
		// Создание временного всплеска нагрузки на кучу
		data := make([][]byte, 1000)
		for i := range data {
			data[i] = make([]byte, 100*1024) // 100 КБ каждый
		}

		var m runtime.MemStats
		runtime.ReadMemStats(&m)
		fmt.Fprintf(w, "Alloc: %d КБ, NumGC: %d\n", m.Alloc/1024, m.NumGC)
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Рантайм Go непрерывно отслеживает размер кучи и память, выделенную под системные структуры. 

Когда `HeapSys + StackSys` приближается к отметке `GOMEMLIMIT`, триггер GC смещается: сборщик мусора запускается непрерывно и пропорционально давлению памяти. Чтобы избежать бесконечного зацикливания (GC CPU Thrashing), рантайм Go ограничивает максимальное время работы GC не более 50% от суммарного процессорного времени.

## Подводные камни

1. Установка `GOMEMLIMIT` равным 100% от лимита cgroups (`128MiB` при лимите `128Mi`): контейнер все равно упадет по OOMKilled из-за памяти, потребляемой бинарником, кодом CGO, тредами ОС и сокетами ядра.
2. Полное отключение GC (`GOGC=off`) без настройки `GOMEMLIMIT`.
3. Использование суффикса `MB` вместо `MiB`: в Go синтаксис `MiB` означает \(1024 \times 1024\) байт, а `MB` — \(1000 \times 1000\) байт.

## На собеседовании

**Вопрос с собеседования:** Что такое «GC CPU Thrashing» при неправильной настройке `GOMEMLIMIT` и как Go 1.19+ защищает сервис от этой проблемы?
**Ответ:** Если потребление памяти сервиса упирается в `GOMEMLIMIT`, сборщик мусора начинает запускаться непрерывно после каждой новой аллокации. В старых версиях это приводило к тому, что 100% времени процессора сжигалось на сборку мусора, а приложение полностью переставало отвечать на запросы (Livelock). 
В Go 1.19+ встроен **GC CPU Limiter**: если затраты времени на GC превышают **50% от одного процессорного окна**, рантайм временно блокирует запуск GC и дает приложению работать, предпочитая риск получить OOMKilled полной остановке сервиса.
