# Управление доступом на основе ролей (RBAC): ServiceAccount, Role и RoleBinding

## Условие

Настрой **ServiceAccount + RBAC**: `kind: ServiceAccount`, `kind: Role` (permissions in namespace), `kind: RoleBinding` (bind SA to Role). Покажи principle of least privilege for pods.

## Теория

Модель **RBAC (Role-Based Access Control)** управляет правами доступа процессов и пользователей к API кластера Kubernetes:
1. **`ServiceAccount`:** Учетная запись, от имени которой действует Pod.
2. **`Role`:** Набор разрешений в рамках конкретного namespace (правила: `apiGroups`, `resources`, `verbs`).
3. **`RoleBinding`:** Связывает ServiceAccount с Role, наделяя его правами.

Пример: микросервису требуется считывать список подов в своем namespace, но запрещено удалять поды или читать секреты.

## Решение по шагам

1. Создайте `ServiceAccount` с именем `pod-reader-sa`.
2. Создайте манифест `Role`, разрешающий действия `get`, `list`, `watch` для ресурса `pods`.
3. Создайте `RoleBinding`, связывающий аккаунт с ролью.
4. Привяжите `serviceAccountName: pod-reader-sa` в `deployment.yaml`.
5. Протестируйте права через команду `kubectl auth can-i`.

## Код решения

**`rbac.yaml`**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: pod-reader-sa
  namespace: default
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader-role
  namespace: default
rules:
  - apiGroups: [""] # Core API Group
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: default
subjects:
  - kind: ServiceAccount
    name: pod-reader-sa
    namespace: default
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

**`check-rbac.sh`**

```bash
# Проверка прав: может ли ServiceAccount читать поды? (Ответ: yes)
kubectl auth can-i list pods --as=system:serviceaccount:default:pod-reader-sa

# Проверка прав: может ли ServiceAccount удалять поды? (Ответ: no)
kubectl auth can-i delete pods --as=system:serviceaccount:default:pod-reader-sa

# Проверка прав: может ли ServiceAccount читать секреты? (Ответ: no)
kubectl auth can-i get secrets --as=system:serviceaccount:default:pod-reader-sa
```

## Под капотом

Когда приложение обращается к API-серверу (`GET /api/v1/namespaces/default/pods`), модуль авторизации RBAC перехватывает запрос. 

Он парсит субъект из токена JWT, находит все объекты `RoleBinding` в данном namespace, сопоставляет запрошенный URI (`resource: pods`, `verb: list`) с правилами `rules[]`. Если совпадение найдено, запрос пропускается, иначе возвращается статус `403 Forbidden`.

## Подводные камни

1. Использование `ClusterRole` и `ClusterRoleBinding` вместо `Role` и `RoleBinding`: выдача прав на весь кластер вместо одного namespace.
2. Использование подстановочного знака `verbs: ["*"]` и `resources: ["*"]`: нарушение принципа наименьших привилегий.
3. Отсутствие прав на `watch` при использовании client-go Informer cache.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `RoleBinding` и `ClusterRoleBinding`?
**Ответ:** 
- **`RoleBinding`** действует строго в пределах **одного конкретного namespace**. Даже если связать его с глобальной `ClusterRole`, права будут ограничены только ресурсами данного пространства имен.
- **`ClusterRoleBinding`** действует **глобально на весь кластер**, давая права во всех существующих и будущих пространствах имен (например, права на просмотр нод `nodes` или чтение подов во всех namespace одновременно). Использование `ClusterRoleBinding` в приложениях требует строгого согласования с отделом ИБ.
