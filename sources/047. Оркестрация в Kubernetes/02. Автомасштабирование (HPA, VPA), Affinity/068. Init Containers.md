# Init Containers: блокировка старта пода утилитой nc до доступности базы данных

## Условие

Настрой **Init Containers**: `initContainers: - name: wait-for-db, image: busybox, command: ['sh', '-c', 'until nc -z postgres 5432; do sleep 2; done']`. Запускается перед основным контейнером, должен завершиться успешно. Покажи dependency management.

## Теория

Проверка доступности сетевого сокета зависимостей через **`Init Containers`**:
- Легковесный контейнер `busybox` выполняет команду `nc -z db-host 5432` в цикле.
- Основной сервис на Go не начнет компилироваться или стартовать, пока сокет базы данных не откроется.
- Разделение ответственности: код приложения освобождается от бесконечных retry-циклов ожидания сети.

## Решение по шагам

1. Добавьте в `deployment.yaml` секцию `initContainers`.
2. Используйте образ `busybox:1.37`.
3. Добавьте команду: `until nc -z -v -w3 db-service 5432; do sleep 2; done`.
4. Разверните манифест.
5. Проследите за переходом статуса пода из `Init:0/1` в `PodInitializing` и затем в `Running`.

## Код решения

**`init-nc.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      initContainers:
        - name: wait-for-db
          image: busybox:1.37
          command:
            - /bin/sh
            - -c
            - |
              echo "Проверка доступности порта БД..."
              until nc -z -w 2 postgres-service 5432; do
                echo "Порт 5432 закрыт, повтор через 2с..."
                sleep 2
              done
              echo "База данных доступна по сети!"
      containers:
        - name: app
          image: ghcr.io/company/order-service:v1.0.0
          ports:
            - containerPort: 8080
```

## Под капотом

`kubelet` запускает контейнер `wait-for-db`. Утилита `nc` (netcat) шлет SYN-пакет на порт 5432. 

При получении SYN-ACK соединение закрывается, цикл завершается с кодом 0, контейнер переходит в статус `Completed`, и Kubelet начинает развертывание основного контейнера `app`.

## Подводные камни

1. Доступность порта не означает готовность СУБД: сокет может быть открыт, но база данных может находиться в режиме Recovery и не принимать SQL-запросы.
2. Бесконечный цикл без таймаута при опечатке в адресе хоста.
3. Отсутствие DNS-записи сервиса.

## На собеседовании

**Вопрос с собеседования:** Почему `nc -z` (проверка TCP-сокета) не всегда достаточна для проверки готовности PostgreSQL, и чем ее заменяют?
**Ответ:** При старте PostgreSQL открывает слушающий TCP-сокет на раннем этапе, когда процесс еще выполняет рекавери WAL-логов и запрещает клиентские подключения (`the database system is starting up`). Проверка `nc -z` завершится успехом, но приложение упадет при первой SQL-транзакции. 
Вместо чистого TCP-netcat используют утилиту **`pg_isready`**, которая отправляет протокольный пакет и проверяет, что сервер перешел в статус `ready to accept connections`.
