# Регулярные фоновые задачи: CronJob для ночной очистки и регламентных работ

## Условие

**[Jobs / CronJobs]**: Напиши `CronJob`, которая запускается каждый день в 2:00 ночи и выполняет Go-скрипт очистки старых записей из БД.

## Теория

Автоматизация регламентных задач по расписанию через `CronJob`:
- Расписание `0 2 * * *` (ежедневно в 02:00 ночи).
- Вызов специализированного Go-бинарника.
- Автоматическое завершение и очистка истории подов.

## Решение по шагам

1. Создайте код регламентной очистки в Go.
2. Создайте манифест `cronjob.yaml`.
3. Установите `concurrencyPolicy: Forbid`.
4. Примените манифест.
5. Протестируйте разовый запуск через `kubectl create job`.

## Код решения

**`cleanup-cronjob.yaml`**

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: night-cleanup
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: cleaner
              image: ghcr.io/company/cleaner:v1.0.0
              command: ["/bin/cleaner", "--mode=expired-sessions"]
```

**`cleaner.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fmt.Printf("[%s] Запуск ночной регламентной очистки устаревших сессий...\n", time.Now().Format(time.RFC3339))
	time.Sleep(2 * time.Second)
	fmt.Println("Очистка успешно завершена. Удалено 4 210 устаревших записей.")
}
```

## Под капотом

`CronJobController` порождает объект `Job`, который создает изолированный Pod для выполнения задачи.

## Подводные камни

1. Забытый `restartPolicy: OnFailure`.
2. Параллельный запуск двух экземпляров без `concurrencyPolicy: Forbid`.
3. Засорение etcd историей завершенных подов.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `restartPolicy: OnFailure` и `restartPolicy: Never` в K8s Job?
**Ответ:** 
- При **`OnFailure`**: при падении процесса Kubelet перезапускает упавший контейнер **внутри того же самого Pod** на той же ноде.
- При **`Never`**: Kubelet не перезапускает упавший контейнер; вместо этого JobController создает **совершенно новый Pod** (возможно, на другой свободной ноде кластера), сохраняя логи упавшего пода для последующего дебага.
