# Автоматическая оптимизация ресурсов с Vertical Pod Autoscaler (VPA)

## Условие

Используйте **Vertical Pod Autoscaler (VPA)** для автоматического подбора requests/limits.

## Теория

Разработчикам сложно вручную определить точные значения `requests` и `limits` для каждого микросервиса.

**Vertical Pod Autoscaler (VPA)**:
- Непрерывно анализирует реальное потребление CPU и памяти контейнерами через Metrics API.
- Формирует рекомендации (`Target`, `LowerBound`, `UpperBound`).
- В режиме `updateMode: "Off"` позволяет безопасно проводить аудит эффективности инфраструктуры (FinOps).
- Предотвращает как падения по OOMKilled из-за заниженных лимитов, так и переплату за простаивающие мощности (Over-provisioning).

## Решение по шагам

1. Создайте манифест `vpa.yaml` с `updateMode: "Off"`.
2. Привяжите `targetRef` к вашему Deployment.
3. Примените манифест: `kubectl apply -f vpa.yaml`.
4. Нагрузите сервис запросами.
5. Проанализируйте сформированные рекомендации VPA через `kubectl describe vpa`.

## Код решения

**`vpa.yaml`**

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: user-service-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: user-service
  updatePolicy:
    updateMode: "Off" # Только сбор рекомендаций
  resourcePolicy:
    containerPolicies:
      - containerName: '*'
        controlledResources: ["cpu", "memory"]
        minAllowed:
          cpu: 50m
          memory: 64Mi
        maxAllowed:
          cpu: 1000m
          memory: 2Gi
```

**`view-recommendations.sh`**

```bash
# Просмотр статуса и рассчитанных рекомендаций VPA:
kubectl describe vpa user-service-vpa
```

## Под капотом

VPA Recommender считывает историю потребления ресурсов за последние 8 дней. 

Он использует 95-й процентиль утилизации CPU и пиковые значения памяти с добавлением коэффициента безопасности (safety margin 15%), рассчитывая идеальный размер пода.

## Подводные камни

1. Включение `updateMode: "Auto"` на продакшне без PDB: поды будут принудительно перезапущены одновременно.
2. Одновременный конфликт с HPA по CPU.
3. Отсутствие установленного `metrics-server`.

## На собеседовании

**Вопрос с собеседования:** В каких сценариях VPA предпочтительнее HPA?
**Ответ:** Для **Stateful или монолитных сервисов**, которые невозможно легко масштабировать горизонтально добавлением реплик (например, однонодовая база данных, фоновый воркер с партиционированием по ключу, тяжелый легаси-сервис). 
Также VPA незаменим в качестве инструмента **FinOps-аудита** для выявления сервисов, разработчики которых запросили по 8 ГБ памяти, а реально используют 200 МБ.
