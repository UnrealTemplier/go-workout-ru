# Паттерн Sidecar для централизованного сбора логов через Fluentbit

## Условие

Настройте **Sidecar containers** для логирования (fluent-bit), проксирования (envoy) или service mesh.

## Теория

Когда приложению требуется передавать логи специального формата или с дополнительным обогащением метаданными:
- Основной контейнер Go пишет логи в разделяемый том `emptyDir`.
- Sidecar-контейнер `fluent-bit` непрерывно считывает файл лога, парсит поля и отправляет данные в централизованное хранилище ElasticSearch/Kafka.
- Изоляция ответственности: процесс Go освобожден от сетевых библиотек отправки логов.

## Решение по шагам

1. Опишите общий том `volumes: name: shared-logs, emptyDir: {}`.
2. Смонтируйте том в оба контейнера.
3. Основной сервис пишет строки в `/var/log/app/events.log`.
4. Fluent-bit читает файл и отправляет в центральное хранилище.
5. Разверните манифест и проверьте логи.

## Код решения

**`sidecar-logs.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: logging-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: logging-demo
  template:
    metadata:
      labels:
        app: logging-demo
    spec:
      volumes:
        - name: shared-logs
          emptyDir: {}
      containers:
        - name: app
          image: alpine:3.21
          command: ["/bin/sh", "-c"]
          args:
            - |
              while true; do
                echo "{\"time\":\"$(date)\",\"level\":\"INFO\",\"msg\":\"User payment received\"}" >> /var/log/app/events.log
                sleep 5
              done
          volumeMounts:
            - name: shared-logs
              mountPath: /var/log/app

        - name: log-shipper
          image: fluent/fluent-bit:3.2
          volumeMounts:
            - name: shared-logs
              mountPath: /var/log/app
              readOnly: true
```

## Под капотом

Том `emptyDir` создается на быстром SSD-диске ноды или в памяти `tmpfs`. Файловая система является общей для обоих контейнеров пода.

## Подводные камни

1. Разрастание лог-файла на `emptyDir`: без ротации диск ноды быстро заполнится на 100%.
2. Двойное потребление памяти (два процесса в одном поде).
3. Предпочтительнее использовать стандартный DaemonSet сбор логов со stdout.

## На собеседовании

**Вопрос с собеседования:** Почему сбор логов через Sidecar-контейнер в каждом поде считается более ресурсоемким решением, чем единый DaemonSet на ноде?
**Ответ:** Если в кластере запущено 1 000 подов, то при подходе Sidecar запускается 1 000 отдельных инстансов Fluent-bit, каждый из которых потребляет по 50–100 МБ памяти (суммарно до 100 ГБ ОЗУ на кластер только на сборщики!). 
Единый **DaemonSet** запускает ровно одного агента на каждую ноду (например, 20 нод = 20 агентов), экономя десятки гигабайт памяти и процессорных ядер кластера.
