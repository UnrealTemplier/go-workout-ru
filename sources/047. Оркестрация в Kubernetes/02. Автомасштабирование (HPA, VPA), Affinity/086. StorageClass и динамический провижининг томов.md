# StorageClass и динамический провижининг томов (Dynamic Provisioning)

## Условие

Настройте **StorageClass** с dynamic provisioning (например, AWS EBS, GCE PD).

## Теория

До появления **StorageClass** администраторам приходилось вручную создавать PV под каждый диск в облаке. **Dynamic Provisioning** полностью автоматизирует этот процесс:
1. **StorageClass** определяет:
   - `provisioner`: CSI-драйвер облачного провайдера (например, `ebs.csi.aws.com` для AWS EBS или `pd.csi.storage.gke.io` для Google Cloud PD).
   - `parameters`: тип диска (например, `type: gp3`, `iops: "3000"`, `throughput: "125"`), шифрование (`encrypted: "true"`).
   - `reclaimPolicy`: `Delete` (удалить диск при удалении PVC) или `Retain` (сохранить).
   - `volumeBindingMode`:
     - `Immediate` (по умолчанию) — том создается в облаке сразу при создании PVC, еще до того, как Pod назначен на узел. Это может вызвать проблему: том создастся в Availability Zone `us-east-1a`, а Pod запланируется в `us-east-1b`!
     - `WaitForFirstConsumer` — создание тома откладывается до тех пор, пока `kube-scheduler` не выберет узел для пода с учетом зон доступности, сетевых задержек и ресурсов.

## Решение по шагам

1. Создайте манифест `StorageClass` с провижинером AWS EBS CSI и `volumeBindingMode: WaitForFirstConsumer`.
2. Создайте `PersistentVolumeClaim`, явно ссылающийся на созданный `storageClassName: fast-ebs-gp3`.
3. Создайте Pod, монтирующий этот PVC.
4. Убедитесь через `kubectl get pv`, что PersistentVolume был автоматически создан облачным драйвером.

## Код решения

**`storageclass.yaml`**

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ebs-gp3
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true
```

**`pvc.yaml`**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data-claim
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: fast-ebs-gp3
  resources:
    requests:
      storage: 20Gi
```

**`Терминал`**

```bash
# Создание StorageClass и PVC
kubectl apply -f storageclass.yaml
kubectl apply -f pvc.yaml

# Статус PVC будет Pending до запуска Pod благодаря WaitForFirstConsumer
kubectl get pvc db-data-claim

# Проверка созданного в облаке PV после запуска Pod
kubectl get pv
```

## Под капотом

Когда создается Pod, монтирующий PVC с `WaitForFirstConsumer`, планировщик `kube-scheduler` оценивает зоны доступности нод. Выбрав ноду (например, в зоне `ru-central1-a`), планировщик проставляет аннотацию `volume.kubernetes.io/selected-node` на PVC. Контроллер `csi-provisioner` перехватывает событие, вызывает метод `CreateVolume` у CSI-плагина с передачей зоны `ru-central1-a`. CSI-драйвер через Cloud API создает облачный диск именно в нужной зоне и генерирует объект `PersistentVolume`, автоматически связывая его с PVC.

## Подводные камни

1. Использование `volumeBindingMode: Immediate` в мультизональных кластерах: диск создается в случайной AZ, а Pod затем не может запуститься из-за нехватки ресурсов на нодах этой конкретной зоны (`volume node affinity conflict`). В продакшене всегда используйте `WaitForFirstConsumer`.
2. Отсутствие флага `allowVolumeExpansion: true`: без этого флага невозможно динамически увеличить размер тома (`storage: 50Gi`) без полного пересоздания PVC и потери данных.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если в PVC увеличить объем диска с 10Gi до 20Gi при включенном `allowVolumeExpansion: true`?»
**Ответ:** Контроллер `csi-resizer` отправит запрос в Cloud API на расширение блочного устройства до 20Gi. После того как размер блочного тома изменится, `kubelet` при очередном обращении или монтировании выполнит команду расширения файловой системы (`resize2fs` для ext4 или `xfs_growfs` для XFS) прямо на лету без остановки и перезапуска работающего Pod.
