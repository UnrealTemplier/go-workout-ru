# Helm: управление зависимостями и композитные чарты (Subcharts)

## Условие

Напиши **Helm Chart с dependencies**: `dependencies: - name: postgresql, version: 12.x.x, repository: https://charts.bitnami.com/bitnami`. `helm dependency update`. Покажи composite applications.

## Теория

В микросервисной архитектуре приложения часто требуют готовых инфраструктурных компонентов: баз данных (PostgreSQL, MySQL), кэшей (Redis) или брокеров сообщений (RabbitMQ, Kafka). Вместо ручного копирования манифестов Helm предлагает механизм зависимостей (**Chart Dependencies / Subcharts**):
1. **Секция `dependencies` в `Chart.yaml`**: объявляет имя, версию и репозиторий дочернего чарта.
2. **Команда `helm dependency update` (или `build`)**: скачивает архивы чартов (`.tgz`) в поддиректорию `charts/` и формирует lock-файл `Chart.lock` с контрольными суммами SHA-256 для воспроизводимости сборки.
3. **Переопределение конфигурации (Values Overriding)**: родительский чарт (`myapp`) может переопределять параметры дочернего чарта в своем `values.yaml`, обращаясь к ним по ключу, совпадающему с именем зависимости (например, `postgresql.auth.database: myapp_db`).
4. **Условное включение (Conditions / Tags)**: зависимость можно сделать опциональной с помощью директивы `condition: postgresql.enabled`, что полезно для отключения встроенной БД в production-окружениях с облачным управляемым RDS/Managed PostgreSQL.

## Решение по шагам

1. Создайте `Chart.yaml` с описанием приложения и секцией `dependencies` с чартом Bitnami PostgreSQL.
2. В `values.yaml` настройте параметры своего сервиса и переопределите значения для `postgresql`.
3. Выполните `helm dependency update` для загрузки tar-архива PostgreSQL в директорию `charts/`.
4. Сгенерируйте итоговые манифесты командой `helm template .` и убедитесь в наличии объектов PostgreSQL.

## Код решения

**`Chart.yaml`**

```yaml
apiVersion: v2
name: myapp
description: Composite Helm Chart with PostgreSQL dependency
version: 1.0.0
appVersion: "1.0.0"

dependencies:
  - name: postgresql
    version: "12.5.6"
    repository: "https://charts.bitnami.com/bitnami"
    condition: postgresql.enabled
```

**`values.yaml`**

```yaml
replicaCount: 2

image:
  repository: myapp-service
  tag: "1.0.0"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 8080

# Переопределение значений зависимого чарта postgresql
postgresql:
  enabled: true
  auth:
    username: myapp_user
    password: SecretPassword123!
    database: myapp_db
  primary:
    persistence:
      size: 10Gi
```

**`Терминал`**

```bash
# Скачивание зависимостей и генерация Chart.lock
helm dependency update ./myapp

# Проверка локального рендеринга композитного чарта
helm template myapp ./myapp > rendered_manifests.yaml

# Установка в кластер Kubernetes
helm install my-release ./myapp -n default
```

## Под капотом

При выполнении `helm dependency update` Helm обращается к указанному HTTP-репозиторию, парсит `index.yaml`, находит нужную semver-версию архива, загружает его в директорию `charts/` и записывает SHA-256 хэш в `Chart.lock`. Во время рендеринга шаблонов (`helm template` / `helm install`) движок рендеринга обходит дерево чартов снизу вверх. Значения из корневого `values.yaml` с префиксом `postgresql.*` мерджатся поверх дефолтных значений subchart `postgresql/values.yaml`.

## Подводные камни

1. Отсутствие `Chart.lock` в Git-репозитории: если lock-файл не зафиксирован в системе контроля версий, сборка в CI/CD конвейере может непреднамеренно подтянуть новую minor/patch версию зависимости с критическими изменениями.
2. Использование subchart-баз данных в HighLoad Production: чарты вроде Bitnami PostgreSQL в K8s отлично подходят для локальной разработки (Minikube/Kind) и тестовых контуров, но в продакшене промышленного масштаба обычно используют Cloud Managed DB (RDS, Cloud SQL) или специализированные CloudNative-операторы (Zalando Postgres Operator, CloudNativePG).

## На собеседовании

**Вопрос с собеседования:** «Как в Helm организовать деплой приложения так, чтобы на dev-стенде автоматически поднимался встроенный Redis из subchart, а на production использовался внешний кластер Redis (например, в AWS ElastiCache)?»
**Ответ:** В `Chart.yaml` для зависимости `redis` указывается директива `condition: redis.enabled`. В общем `values.yaml` по умолчанию ставится `redis.enabled: true`. В `values-production.yaml` задается `redis.enabled: false`, а в конфигурации приложения прописывается внешний хост `redisHost: "elasticache.cluster.internal"`.
