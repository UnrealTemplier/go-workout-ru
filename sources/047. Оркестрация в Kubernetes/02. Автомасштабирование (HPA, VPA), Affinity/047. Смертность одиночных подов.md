# Смертность одиночных подов и обеспечение надежности через Deployment

## Условие

**Развертывание (Deployment)**: Поды смертны. Если под удалят, он не воскреснет. Удали под. Напиши `deployment.yaml`. Опиши `Deployment`, который управляет 3 репликами (копиями) твоего приложения. Примени его. `kubectl get pods` должен показать 3 работающих пода.

## Теория

Одиночный Pod в Kubernetes — временная сущность (Cattle, not Pets):
- Если одиночный под падает из-за аппаратного сбоя ноды, Kubelet не восстанавливает его.
- Если администратор случайно удалит под (`kubectl delete pod`), под исчезает навсегда.

Контроллер **`Deployment`** решает эту проблему:
- Создает спецификацию через `ReplicaSet`.
- Непрерывно сверяет количество живых экземпляров.
- Автоматически создает новый под при любых авариях или удалениях.

## Решение по шагам

1. Создайте одиночный под и удалите его: убедитесь, что он не восстановился.
2. Создайте манифест `deployment.yaml`.
3. Примените Deployment.
4. Удалите под деплоймента командой `kubectl delete pod`.
5. Убедитесь, что Deployment немедленно поднял новый под с новым именем.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: indestructible-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: indestructible
  template:
    metadata:
      labels:
        app: indestructible
    spec:
      containers:
        - name: app
          image: alpine:3.21
          command: ["sleep", "3600"]
```

**`demo-kill.sh`**

```bash
# Просмотр подов
kubectl get pods -l app=indestructible

# Удаление пода
POD_NAME=$(kubectl get pods -l app=indestructible -o jsonpath='{.items[0].metadata.name}')
echo "Уничтожаем под: $POD_NAME"
kubectl delete pod $POD_NAME

# Проверка: контроллер моментально запустил замену!
kubectl get pods -l app=indestructible
```

## Под капотом

`ReplicaSetController` слушает очередь событий API Server. 

Удаление пода генерирует событие `DELETE`. Функция контроллера `manageReplicas()` сопоставляет активные поды с числом `spec.replicas`. Заметив недостачу, контроллер немедленно формирует транзакцию создания нового пода.

## Подводные камни

1. Деплой подов напрямую манифестом `kind: Pod` в продуктовых средах.
2. Изменение селекторов работающего Deployment.
3. Отсутствие мониторинга доступности реплик.

## На собеседовании

**Вопрос с собеседования:** Почему в Kubernetes архитектуре принято называть поды «Cattle, not Pets» (Скот, а не домашние питомцы)?
**Ответ:** Исторически серверы администрировались как домашние питомцы («Pets»): им давали уникальные имена, лечили при сбоях и берегли каждый хост. 
В облачной парадигме поды являются расходным материалом («Cattle»): они взаимозаменяемы, безлики, имеют случайные хэш-имена и могут уничтожаться или пересоздаваться сотнями в минуту без какого-либо урона для системы.
