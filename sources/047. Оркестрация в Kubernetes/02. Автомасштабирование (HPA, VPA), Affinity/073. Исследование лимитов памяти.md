# Исследование лимитов памяти: симуляция утечки памяти и статус OOMKilled

## Условие

**Resource Limits и Memory OOMKilled**: Настройте в манифесте пода лимиты по памяти: `resources.limits.memory: "128Mi"`. Напишите тест: запустите внутри Go-приложения код, который аллоцирует в цикле слайс объемом 200 МБ. Запустите деплой в K8s, посмотрите статус пода через `kubectl get pods` и зафиксируйте ошибку завершения процесса по нехватке памяти `OOMKilled` (Exit Code 137).

## Теория

Практическое исследование аварийного завершения контейнера по **OOMKilled**:
- Лимит памяти: `resources.limits.memory: 64Mi`.
- Аллокация в цикле Go превышает лимит.
- Ядро Linux посылает сигнал `SIGKILL` (код завершения **137**).
- K8s регистрирует причину `OOMKilled` и перезапускает под в цикле `CrashLoopBackOff`.

## Решение по шагам

1. Создайте код на Go с аллокацией срезов байтов в цикле.
2. В манифесте задайте `limits.memory: 64Mi`.
3. Примените манифест.
4. Наблюдайте за падением пода через `kubectl get pods -w`.
5. Изучите причину падения через `kubectl describe pod`.

## Код решения

**`oom-deploy.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: oom-victim
spec:
  replicas: 1
  selector:
    matchLabels:
      app: oom-victim
  template:
    metadata:
      labels:
        app: oom-victim
    spec:
      containers:
        - name: app
          image: ghcr.io/company/oom-victim:v1.0.0
          resources:
            limits:
              memory: "64Mi" 
```

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fmt.Println("Запуск сервиса. Начинаем аллокацию памяти...")
	var memoryHolder [][]byte

	for {
		// Аллокация порциями по 5 МБ
		block := make([]byte, 5*1024*1024)
		for i := range block {
			block[i] = 1 // Принудительное касание памяти
		}
		memoryHolder = append(memoryHolder, block)
		fmt.Printf("Всего аллоцировано: %d МБ\n", len(memoryHolder)*5)
		time.Sleep(300 * time.Millisecond)
	}
}
```

**`verify-oom.sh`**

```bash
# Просмотр статуса завершения
kubectl describe pod -l app=oom-victim | grep -A 4 "Last State"
# Ожидаемый вывод:
#   Reason:       OOMKilled
#   Exit Code:    137
```

## Под капотом

Подсистема `cgroup.memory` фиксирует превышение лимита `memory.max`. Ядро Linux вызывает `oom_kill_process()`, немедленно завершая процесс.

## Подводные камни

1. Недостаточный запас памяти для сборщика мусора Go.
2. Игнорирование метрики `container_oom_events_total` в алертах Prometheus.
3. Отсутствие флага `GOMEMLIMIT`.

## На собеседовании

**Вопрос с собеседования:** Почему команда `top` внутри Docker-контейнера в K8s часто показывает память всего физического сервера, а не лимиты контейнера?
**Ответ:** Традиционные утилиты Linux (`top`, `free`, `ps`) читают статистику из виртуальной файловой системы `/proc/meminfo`, которая не изолирована в namespaces и показывает суммарные ресурсы физического хоста. 
Реальные ограничения контейнера лежат в `/sys/fs/cgroup/memory`. Чтобы утилиты внутри пода показывали корректную информацию, в кластерах используют проект **LXCFS**, который виртуализирует `/proc` для каждого контейнера.
