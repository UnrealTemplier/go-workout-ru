# Автомасштабирование по кастомным метрикам: масштабирование по длине очереди Kafka через KEDA

## Условие

Настройте HPA на основе **custom metrics** (например, длина Kafka очереди через Prometheus Adapter).

## Теория

Стандартный HPA по CPU и памяти не способен эффективно масштабировать консьюмеры очередей (Kafka, RabbitMQ, SQS):
- Если в топик Kafka поступило 1 000 000 сообщений, консьюмеры могут работать с низким CPU (например, ожидая I/O базы данных). HPA не увеличит число реплик, и время отставания (Consumer Lag) вырастет до критических масштабов.

Решение: **KEDA (Kubernetes Event-driven Autoscaling)**:
- Расширяет K8s нативными Custom Resources (`ScaledObject`).
- Умеет подключаться к брокерам (Kafka, RabbitMQ, Redis, Prometheus).
- Измеряет длину очереди или лаг консьюмер-группы.
- Масштабирует поды от 0 до N реплик (Scale-to-Zero) при появлении сообщений.

## Решение по шагам

1. Установите KEDA в кластер через Helm.
2. Создайте манифест `ScaledObject` для сервиса обработки заказов.
3. Укажите триггер `type: kafka` с целевым лагом `lagThreshold: "100"`.
4. Задайте диапазон реплик: `minReplicaCount: 1`, `maxReplicaCount: 20`.
5. Отправьте тестовую пачку сообщений в Kafka и наблюдайте масштабирование подов консьюмеров.

## Код решения

**`scaled-object.yaml`**

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: kafka-consumer-scaler
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-consumer
  pollingInterval: 15
  cooldownPeriod: 300
  minReplicaCount: 1
  maxReplicaCount: 15
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka-cluster.kafka.svc:9092
        consumerGroup: order-processing-group
        topic: incoming-orders
        lagThreshold: "50" # Добавлять реплику на каждые 50 сообщений лага
```

**`consumer.go`**

```go
package main

import (
	"fmt"
	"os"
	"time"
)

func main() {
	podName, _ := os.Hostname()
	fmt.Printf("[%s] Консьюмер Kafka запущен. Чтение топика incoming-orders...\n", podName)

	// Имитация вычитки сообщений из очереди
	for {
		time.Sleep(100 * time.Millisecond)
	}
}
```

**`check-keda.sh`**

```bash
# Просмотр статуса ScaledObject
kubectl get scaledobject kafka-consumer-scaler

# KEDA автоматически создает стандартный HPA ресурс:
kubectl get hpa keda-hpa-kafka-consumer-scaler
```

## Под капотом

KEDA Operator периодически (каждые `pollingInterval` секунд) опрашивает брокер Kafka через протокол AdminClient API, запрашивая `OffsetFetch` и `ListConsumerGroupOffsets`. 

KEDA вычисляет суммарный лаг по всем партициям. Она передает вычисленную метрику во внутренний Custom Metrics API Server. Стандартный HPA контроллер Kubernetes считывает это значение и плавно меняет число реплик Deployment.

## Подводные камни

1. Превышение количества реплик над числом партиций Kafka: в Kafka одна партиция может читаться строго одним консьюмером внутри группы! Если в топике 8 партиций, запуск 15 реплик бессмысленен — 7 реплик будут простаивать в idle. `maxReplicaCount` не должен превышать число партиций!
2. Слишком частый опрос (`pollingInterval: 1`): перегрузка контроллера Kafka Admin API.
3. Отсутствие аутентификации (TriggerAuthentication) для защищенных SASL/SCRAM кластеров Kafka.

## На собеседовании

**Вопрос с собеседования:** Почему при масштабировании консьюмеров Kafka через HPA/KEDA максимальное число реплик жестко ограничено количеством партиций топика?
**Ответ:** Фундаментальная модель конкурентности Apache Kafka гарантирует строгий порядок сообщений внутри партиции. 
Правило Kafka: **каждая партиция внутри одной консьюмер-группы может обрабатываться строго одним потоком/процессом**. Если в топике создано 10 партиций, а KEDA отмасштабирует Deployment до 15 реплик, ровно 10 подов возьмут по одной партиции, а оставшиеся 5 подов не получат ни одной партиции и будут на 100% простаивать, напрасно сжигая память и CPU компании.
