# Паттерн проектирования Sidecar: основной сервис и вспомогательный реверс-прокси Envoy

## Условие

Настрой **Sidecar Pattern**: основной контейнер `app` + sidecar `nginx` (reverse proxy) или `envoy` (service mesh). Shared `emptyDir` volume для Unix socket communication. Покажи separation of concerns.

## Теория

Паттерн **`Sidecar` (Коляска мотоцикла)** — архитектурный паттерн контейнеризации:
- Внутри одного `Pod` запускаются два контейнера:
  1. **Основной контейнер приложения (Go):** содержит только бизнес-логику.
  2. **Вспомогательный контейнер (Sidecar — Envoy/Nginx):** берет на себя сквозную функциональность (терминация mTLS, rate limiting, сбор метрик Prometheus, сжатие gzip).
- Контейнеры делят общий сетевой стек (**Shared Network Namespace**) и общаются между собой на максимальной скорости через **`localhost`** без сетевых накладных расходов.

## Решение по шагам

1. Создайте манифест `pod-sidecar.yaml` с двумя контейнерами в `spec.containers`.
2. Контейнер 1: Go-приложение, слушающее порт 8080.
3. Контейнер 2: Nginx/Envoy прокси, слушающий внешний порт 80 и перенаправляющий на `127.0.0.1:8080`.
4. Примените манифест.
5. Протестируйте вызов внешнего порта 80.

## Код решения

**`sidecar-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sidecar-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sidecar-demo
  template:
    metadata:
      labels:
        app: sidecar-demo
    spec:
      containers:
        # Основной контейнер с бизнес-логикой
        - name: app
          image: alpine:3.21
          command: ["/bin/sh", "-c"]
          args:
            - |
              while true; do
                echo "HTTP/1.1 200 OK\r\nContent-Length: 18\r\n\r\nHello from Go App" | nc -l -p 8080
              done

        # Sidecar контейнер: Nginx проксирует входящий трафик
        - name: proxy-sidecar
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	// Основной сервис слушает строго на localhost:8080
	http.HandleFunc("/data", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Ответ приложения, защищенного Sidecar-прокси\n")
	})

	fmt.Println("Внутренний сервис слушает на 127.0.0.1:8080")
	_ = http.ListenAndServe("127.0.0.1:8080", nil)
}
```

## Под капотом

Оба контейнера подключены к одному сетевому интерфейсу loopback `lo`. Трафик между Nginx и Go передается напрямую через стек сетевой памяти ядра Linux без выхода на сетевую карту сервера.

## Подводные камни

1. Конфликт портов: если оба контейнера попытаются слушать один и тот же порт (например, оба слушают 8080), один из них упадет с `bind: address already in use`.
2. Порядок завершения: если sidecar умрет раньше основного приложения, приложение потеряет сеть. Начиная с K8s 1.29 поддержаны нативные Sidecar Containers через `initContainers` с `restartPolicy: Always`.
3. Двойной расход ресурсов памяти.

## На собеседовании

**Вопрос с собеседования:** Как устроен стандарт Native Sidecar Containers, появившийся в Kubernetes 1.29+?
**Ответ:** Исторически K8s не гарантировал порядок старта и остановки контейнеров в `spec.containers`: прокси-сайдкар мог запуститься позже приложения или умереть раньше него, обрывая соединения. 
В K8s 1.29+ сайдкары объявляются в секции **`initContainers` с флагом `restartPolicy: Always`**. Kubelet гарантирует, что такой сайдкар запускается **до** основного приложения и завершается строго **после** него, решая историческую проблему порядка остановки сервисных прокси.
