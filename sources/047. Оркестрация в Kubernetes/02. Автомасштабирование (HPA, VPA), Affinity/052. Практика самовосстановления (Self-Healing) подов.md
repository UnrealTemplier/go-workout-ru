# Практика самовосстановления (Self-Healing) подов в Deployment

## Условие

**Самовосстановление (Self-healing)**: Намеренно удали один из подов Deployment'а (`kubectl delete pod <имя>`). Быстро сделай `kubectl get pods`. Увидь, как Kubernetes мгновенно создает новый под на замену убитому, чтобы поддержать требуемое число реплик = 3.

## Теория

Демонстрация фундаментального принципа надежности Kubernetes:
- Поды смертны, но Deployment вечен.
- При удалении пода через `kubectl delete pod` контроллер `ReplicaSet` мгновенно замечает разницу между желаемым числом реплик и текущим.
- Создается новый под с новым уникальным именем и IP-адресом.
- Балансировщик Service обновляет Endpoints без простоя трафика.

## Решение по шагам

1. Запустите Deployment с 3 репликами.
2. Запустите непрерывный пинг сервиса в фоновом режиме: `while true; do curl http://service; sleep 0.2; done`.
3. В другом окне принудительно удалите один из подов: `kubectl delete pod <name>`.
4. Наблюдайте, как непрерывный поток запросов не прерывается ни на секунду.

## Код решения

**`self-heal-test.sh`**

```bash
# 1. Просмотр подов
kubectl get pods -l app=resilient

# 2. Удаление одного пода
POD_ID=$(kubectl get pods -l app=resilient -o jsonpath='{.items[0].metadata.name}')
echo "Удаление пода $POD_ID..."
kubectl delete pod $POD_ID

# 3. Моментальная проверка: K8s уже создал новый под!
kubectl get pods -l app=resilient
```

## Под капотом

Цикл сверки (Reconciliation Loop) выполняется контроллером каждые несколько миллисекунд по событиям etcd Watch. 

Время восстановления пода в среднем составляет менее 1 секунды при условии, что OCI-образ уже закэширован на ноде.

## Подводные камни

1. Зависание пода в `Terminating`: если приложение игнорирует `SIGTERM`, удаление продлится полные 30 секунд.
2. Недостаток свободных нод при падении физического сервера.
3. Отсутствие репликации (`replicas: 1`): удаление единственного пода гарантирует простой.

## На собеседовании

**Вопрос с собеседования:** Что происходит с точки зрения etcd и Kube-scheduler при удалении пода командой `kubectl delete pod`?
**Ответ:** 
1. `kubectl` отправляет `DELETE /api/v1/namespaces/default/pods/<name>`.
2. API Server не удаляет объект из etcd моментально, а выставляет поле `metadata.deletionTimestamp` (статус `Terminating`).
3. Kubelet видит временную метку и шлет процессу `SIGTERM`.
4. Одновременно ReplicaSetController видит, что активных подов стало \(N-1\), и отправляет `POST` на создание нового пода.
5. Scheduler назначает новый под на свободную ноду, и он поднимается параллельно с угасанием старого пода.
