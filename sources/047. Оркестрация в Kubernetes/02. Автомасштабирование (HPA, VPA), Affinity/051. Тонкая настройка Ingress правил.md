# Тонкая настройка Ingress правил: спецификация хостов, путей и бэкендов

## Условие

Настрой **Ingress**: `kind: Ingress`, `spec: rules: - host: api.example.com, http: paths: - path: /, pathType: Prefix, backend: service: name: myapp, port: number: 80`. TLS: `spec: tls: - hosts: [api.example.com], secretName: api-tls`. Покажи external access.

## Теория

Манифест `Ingress` позволяет объединять несколько доменов и префиксов путей в едином файле конфигурации:
- Маршрутизация на основе путей (Path-Based Routing):
  - `api.example.com/v1/auth` -> `auth-service`
  - `api.example.com/v1/billing` -> `billing-service`
- Маршрутизация на основе поддоменов:
  - `admin.example.com` -> `backoffice-service`

## Решение по шагам

1. Опишите манифест `multi-ingress.yaml`.
2. Задайте два правила в секции `rules` для хостов `api.example.com` и `admin.example.com`.
3. Настройте перенаправление на соответствующие сервисы.
4. Примените манифест.
5. Протестируйте оба маршрута через curl.

## Код решения

**`multi-ingress.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: core-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /v1/auth
            pathType: Prefix
            backend:
              service:
                name: auth-service
                port:
                  number: 80
          - path: /v1/billing
            pathType: Prefix
            backend:
              service:
                name: billing-service
                port:
                  number: 80
    - host: admin.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backoffice-service
                port:
                  number: 80
```

**`verify.sh`**

```bash
# Проверка маршрута 1
curl -H "Host: api.example.com" http://localhost/v1/auth/login

# Проверка маршрута 2
curl -H "Host: admin.example.com" http://localhost/
```

## Под капотом

NGINX Ingress сортирует пути по длине префикса (longest prefix match). 

Запрос к `/v1/auth/token` сопоставляется с локацией `/v1/auth`, а не с более общим `/`. Заголовок `Host` проверяется в первую очередь через виртуальные хосты Nginx.

## Подводные камни

1. Дублирование путей в разных сервисах.
2. Проблема trailing slash: запросы к `/v1/auth` и `/v1/auth/` могут интерпретироваться по-разному при отсутствии rewrite-аннотаций.
3. Отсутствие healthcheck на бэкенд-сервисах.

## На собеседовании

**Вопрос с собеседования:** Как NGINX Ingress Controller избегает сброса активных соединений (Zero-Downtime Reload) при частом изменении конфигураций Ingress в кластере?
**Ответ:** Традиционная команда `nginx -s reload` запускает новый мастер-процесс Nginx и постепенно закрывает старые воркеры. При тысячах обновлений в секунду в динамическом кластере это приводило к утечкам памяти и сбросу соединений. 
Современный NGINX Ingress Controller использует **Lua-модуль (OpenResty) и динамическую память shm (Shared Memory)**: список IP адресов подов (upstreams) хранится в разделяемой памяти и обновляется на лету через внутренний REST API без выполнения перезагрузки Nginx.
