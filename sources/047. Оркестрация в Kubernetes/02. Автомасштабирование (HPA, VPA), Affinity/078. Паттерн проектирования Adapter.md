# Паттерн проектирования Adapter: трансляция кастомных метрик в формат Prometheus

## Условие

Настрой **Adapter Pattern**: sidecar преобразует интерфейс. `app` пишет metrics в файл, sidecar `prometheus-exporter` читает файл, exposes `/metrics`. Покажи interface adaptation.

### Исходная формулировка

Настрой **Adapter Pattern**: sidecar преобразует интерфейс. `app` пишет metrics в файл, sidecar `prometheus-exporter` читает файл, exposes `/metrics`. Покажи interface adaptation.

---

## Теория

Паттерн **`Adapter` (Адаптер)**:
- Используется, когда стороннее приложение или legacy-сервис пишет метрики в нестандартном виде (например, в локальный файл `/tmp/stats.txt` или в формате StatsD).
- Контейнер-адаптер (Sidecar) читает эти данные, трансформирует их и отдает наружу в стандартном формате Prometheus по эндпоинту `/metrics`.
- Вся система мониторинга работает единообразно без переписывания исходного кода приложения.

## Решение по шагам

1. Создайте Deployment с двумя контейнерами и общим томом `emptyDir`.
2. Контейнер 1 (Legacy App) периодически записывает число операций в файл `/stats/metrics.txt`.
3. Контейнер 2 (Adapter) читает файл и отдает HTTP `/metrics` в формате OpenMetrics.
4. Примените манифест.
5. Протестируйте сбор метрик curl-запросом к адаптеру.

## Код решения

**`adapter-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: legacy-with-adapter
spec:
  replicas: 1
  selector:
    matchLabels:
      app: legacy-adapter
  template:
    metadata:
      labels:
        app: legacy-adapter
    spec:
      volumes:
        - name: stats-vol
          emptyDir: {}
      containers:
        # Legacy приложение: пишет метрики в файл
        - name: legacy-app
          image: alpine:3.21
          command: ["/bin/sh", "-c"]
          args:
            - |
              while true; do
                echo "active_orders:42" > /stats/metrics.txt
                sleep 5
              done
          volumeMounts:
            - name: stats-vol
              mountPath: /stats

        # Контейнер-Адаптер на Go: отдает метрики в формате Prometheus
        - name: prometheus-adapter
          image: ghcr.io/company/adapter:v1.0.0
          ports:
            - containerPort: 9090
          volumeMounts:
            - name: stats-vol
              mountPath: /stats
              readOnly: true
```

**`adapter.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
	"strings"
)

func main() {
	http.HandleFunc("/metrics", func(w http.ResponseWriter, r *http.Request) {
		data, err := os.ReadFile("/stats/metrics.txt")
		if err != nil {
			http.Error(w, "Ошибка чтения метрик", 500)
			return
		}

		parts := strings.Split(strings.TrimSpace(string(data)), ":")
		if len(parts) == 2 {
			// Преобразование в формат Prometheus
			fmt.Fprintf(w, "# HELP legacy_active_orders Число заказов из legacy файла\n")
			fmt.Fprintf(w, "# TYPE legacy_active_orders gauge\n")
			fmt.Fprintf(w, "legacy_active_orders %s\n", parts[1])
		}
	})

	fmt.Println("Prometheus Adapter слушает порт :9090")
	_ = http.ListenAndServe(":9090", nil)
}
```

## Под капотом

Адаптер нормализует неоднородные интерфейсы микросервисов к корпоративному стандарту Observability (Prometheus pull model).

## Подводные камни

1. Гонка чтения-записи (Read-Write Race) при неатомарной перезаписи файла в `emptyDir`.
2. Зависание адаптера при блокировке файла.
3. Отсутствие обработки ошибок парсинга.

## На собеседовании

**Вопрос с собеседования:** В чем разница между архитектурными паттернами Sidecar, Ambassador и Adapter?
**Ответ:** 
- **Sidecar:** Дополняет основной контейнер вспомогательной функциональностью (сбор логов, локальный reverse proxy).
- **Ambassador:** Проксирует **исходящий** трафик приложения к внешнему миру (маскирует удаленную БД как `localhost`).
- **Adapter:** Стандартизирует **выходной интерфейс** приложения для внешнего мира (преобразует кастомные логи или файлы метрик в единый стандарт Prometheus/OpenTelemetry).
