# Использование аннотаций Ingress для Rate Limiting, CORS и перезаписи путей

## Условие

Используйте **Ingress annotations** для rate limiting, CORS, rewrite target.

## Теория

Стандартный ресурс `Ingress` описывает только хосты и пути. Тонкая настройка веб-сервера осуществляется через аннотации (`metadata.annotations`):
1. **Rewrite Target:** Перезапись URL (`nginx.ingress.kubernetes.io/rewrite-target: /$2`), позволяющая клиентам обращаться к `/api/v1/(.*)`, передавая на бэкенд чистый путь `/$2`.
2. **Rate Limiting:** Защита от DDoS-атак и перегрузок:
   - `limit-rps: "10"`: ограничение числа запросов в секунду с одного IP.
   - `limit-connections: "5"`: лимит параллельных TCP-соединений.
3. **CORS:** Автоматическая установка заголовков `Access-Control-Allow-Origin: "*"` для веб-клиентов.

## Решение по шагам

1. Создайте манифест `ingress-annotations.yaml`.
2. Добавьте аннотации rewrite-target, rate-limit и CORS.
3. Примените манифест.
4. Проверьте работу rate limiting серией быстрых запросов (ожидайте статус 429 или 503).
5. Проверьте наличие CORS-заголовков в ответе curl.

## Код решения

**`ingress-annotations.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: advanced-ingress
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    # Ограничение частоты запросов (Rate Limiting)
    nginx.ingress.kubernetes.io/limit-rps: "5"
    nginx.ingress.kubernetes.io/limit-burst-multiplier: "2"
    # Настройка CORS для Single Page Applications
    nginx.ingress.kubernetes.io/enable-cors: "true"
    nginx.ingress.kubernetes.io/cors-allow-methods: "GET, POST, OPTIONS"
    nginx.ingress.kubernetes.io/cors-allow-origin: "https://app.company.com"
spec:
  ingressClassName: nginx
  rules:
    - host: api.company.com
      http:
        paths:
          - path: /services/billing(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: billing-service
                port:
                  number: 80
```

**`test-ratelimit.sh`**

```bash
# Быстрая отправка 20 запросов: после 10-го запроса Nginx вернет 503 Service Temporarily Unavailable
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "%{http_code}\n" -H "Host: api.company.com" http://localhost/services/billing/status
done
```

## Под капотом

Аннотации транслируются контроллером в нативные директивы конфигурации Nginx:
- `limit_req_zone $binary_remote_addr zone=... rate=5r/s;`
- `more_set_headers 'Access-Control-Allow-Origin: https://app.company.com';`
- `rewrite ^/services/billing(/|$)(.*) /$2 break;`
Обработка происходит в памяти воркера Nginx до того, как пакет уйдет на под приложения.

## Подводные камни

1. Ошибки в регулярных выражениях rewrite-target: срезка первого символа пути или поломка статических файлов.
2. Rate Limiting за CloudFlare или внешним CDN: если не настроен заголовок `X-Forwarded-For` через `use-forwarded-headers: "true"`, Nginx будет считать все запросы пришедшими с одного IP адреса CDN и заблокирует всех пользователей сразу!
3. Избыточный размер буфера заголовков клиента.

## На собеседовании

**Вопрос с собеседования:** Почему при использовании Ingress Rate Limiting за обратным прокси (CDN / Cloudflare) критично настраивать директивы `real-ip`?
**Ответ:** Если не настроить `real-ip`, Nginx видит в сокете IP-адрес пограничного сервера CDN (например, 104.16.x.x), а не реального клиента. 
При лимите в 10 запросов в секунду первые 10 запросов от любого пользователя мира исчерпают лимит, и весь последующий глобальный трафик компании будет заблокирован с ошибкой 429/503. Настройка `enable-real-ip: "true"` заставляет Nginx извлекать настоящий IP клиента из заголовка `X-Forwarded-For`.
