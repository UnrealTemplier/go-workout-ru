# Хуки жизненного цикла в Helm (Helm Lifecycle Hooks)

## Условие

Напиши **Helm Chart с hooks**: `annotations: "helm.sh/hook": pre-install, "helm.sh/hook-weight": "1"`. Job для database migrations перед установкой. `post-upgrade` для cache warming. Покажи lifecycle hooks.

## Теория

При стандартном `helm install` или `helm upgrade` все манифесты применяются практически одновременно. Однако в реальных приложениях требуется строгий порядок действий:
- Запустить миграции схемы БД **до** того, как поднимутся новые реплики микросервиса.
- Очистить или прогреть кэш **после** успешного обновления.
- Отправить уведомление в Slack/Telegram об успешном или упавшем релизе.
**Helm Hooks** позволяют вмешиваться в процесс релиза с помощью специальных аннотаций:
1. `"helm.sh/hook"`:
   - `pre-install` / `post-install` — выполняется до / после создания ресурсов первого релиза.
   - `pre-upgrade` / `post-upgrade` — до / после обновления существующего релиза.
   - `pre-delete` / `post-delete` — до / после удаления релиза.
2. `"helm.sh/hook-weight"`: порядок выполнения хуков (хуки с меньшим весом выполняются первыми, например `"-5"` раньше `"1"`).
3. `"helm.sh/hook-delete-policy"`: когда удалять объект хука:
   - `hook-succeeded` — удалить Job при успешном завершении (exit code 0).
   - `hook-failed` — удалить при сбое.
   - `before-hook-creation` — удалить старый Job перед созданием нового.

## Решение по шагам

1. Создайте `templates/migration-job.yaml` с аннотацией хука `pre-install,pre-upgrade`.
2. Укажите `hook-weight: "1"` и политику удаления `hook-succeeded,before-hook-creation`.
3. Создайте `templates/cache-warm-job.yaml` с аннотацией `post-upgrade`.
4. Напишите Go-приложение для миграций, завершающееся с кодом 0 при успехе.
5. Протестируйте выполнение `helm upgrade`: убедитесь, что Pod приложения не обновляется, пока Job миграций не завершится успешно.

## Код решения

**`templates/migration-job.yaml`**

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-db-migrate
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade
    "helm.sh/hook-weight": "1"
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          command: ["/app/migrator", "up"]
          env:
            - name: DB_URL
              value: {{ .Values.database.url | quote }}
```

**`templates/cache-warm-job.yaml`**

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ .Release.Name }}-cache-warm
  annotations:
    "helm.sh/hook": post-upgrade
    "helm.sh/hook-weight": "5"
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: warmer
          image: curlimages/curl:latest
          command: ["curl", "-s", "http://{{ .Release.Name }}-svc:8080/warmup"]
```

**`migrator/main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
	"time"
)

func main() {
	dbURL := os.Getenv("DB_URL")
	if dbURL == "" {
		log.Fatal("DB_URL не задан")
	}

	fmt.Println("Применение SQL-миграций схемы базы данных...")
	time.Sleep(2 * time.Second) // Имитация применения миграций golang-migrate
	fmt.Println("Миграции успешно применены до версии v1.2.0")
}
```

## Под капотом

Во время релиза Helm парсит все манифесты и отделяет объекты с аннотацией `"helm.sh/hook"` от обычных ресурсов. При наступлении фазы `pre-upgrade`:
1. Helm отправляет манифест Job хука в `kube-apiserver`.
2. Helm блокирует дальнейшее обновление кластера и начинает опрашивать статус Job (`kubectl wait --for=condition=complete`).
3. Если Job завершился успешно (состояние `Complete`), Helm переходит к обновлению Deployment и Service.
4. Если Job завершился с ошибкой (состояние `Failed`), Helm прерывает релиз, оставляя предыдущую версию работающей без изменений.

## Подводные камни

1. Отсутствие политики `before-hook-creation`: при повторном запуске `helm upgrade` Helm попытается создать Job с тем же именем, что вызовет ошибку `jobs.batch already exists`.
2. Долгие миграции с блокировками таблиц: если Job миграций превышает дефолтный таймаут Helm (`--timeout 5m0s`), Helm признает релиз проваленным, хотя миграция в БД может продолжать выполняться.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет со старыми подами приложения во время выполнения `pre-upgrade` хука в Helm?»
**Ответ:** Старые поды предыдущей версии продолжают непрерывно работать и обслуживать трафик пользователей. Deployment новой версии еще не начал обновляться. Это накладывает фундаментальное архитектурное требование: миграции базы данных в хуках `pre-upgrade` обязаны быть **обратно совместимыми (Backward Compatible)**, то есть новая схема БД не должна ломать работу старого кода (паттерн Expand and Contract).
