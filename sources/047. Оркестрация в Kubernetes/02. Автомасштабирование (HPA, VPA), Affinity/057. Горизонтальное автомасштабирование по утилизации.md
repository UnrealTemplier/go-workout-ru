# Горизонтальное автомасштабирование по утилизации CPU (HPA): практическая конфигурация

## Условие

Создайте **Horizontal Pod Autoscaler (HPA)** на основе CPU utilization.

## Теория

Практическое закрепление создания HPA для производственных микросервисов:
- Декларация масштабирования целевого деплоймента.
- Привязка к порогу утилизации CPU (например, 75%).
- Использование стабилизационных окон для защиты от качания подов.
- Автоматическая балансировка ресурсов в часы пик и экономия денег компании ночью.

## Решение по шагам

1. Создайте `hpa-cpu.yaml` с минимальным числом реплик 2 и максимальным 10.
2. Привяжите `scaleTargetRef` к имени Deployment.
3. Задайте `averageUtilization: 75`.
4. Примените манифест.
5. Проконтролируйте текущие значения утилизации через `kubectl get hpa`.

## Код решения

**`hpa-cpu.yaml`**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 75
```

**`verify.sh`**

```bash
# Просмотр статуса HPA
kubectl get hpa payment-hpa

# Вывод детальной информации и событий автомасштабирования
kubectl describe hpa payment-hpa
```

## Под капотом

HPA Controller вычисляет процент утилизации:
$$\text{Utilization} = \frac{\sum \text{Usage(Pods)}}{\sum \text{Requests(Pods)}} \times 100\%$$
Если полученное значение отличается от целевого (75%) более чем на коэффициент допуска (tolerance 10%), контроллер выполняет масштабирование.

## Подводные камни

1. Завышение `minReplicas`: избыточные траты инфраструктурных ресурсов.
2. `maxReplicas` превышает лимиты емкости кластера: поды зависнут в статусе `Pending`.
3. Отсутствие мониторинга событий масштабирования в Grafana.

## На собеседовании

**Вопрос с собеседования:** Почему в production сервисах с HPA параметр `minReplicas` никогда не ставят равным 1?
**Ответ:** Если `minReplicas: 1`, то в периоды затишья работает всего один под. Это полностью лишает систему высокой доступности (High Availability): 
1. При плановой эвакуации ноды (`kubectl drain`) сервис уходит в даунтайм.
2. При падении ноды пользователи получают ошибки, пока под создается заново (от 30 секунд до 2 минут).
3. При резком наплыве трафика один под мгновенно перегружается и падает до того, как HPA успеет отреагировать. 
Минимально допустимое число реплик в HighLoad — **не менее 2–3 подов**.
