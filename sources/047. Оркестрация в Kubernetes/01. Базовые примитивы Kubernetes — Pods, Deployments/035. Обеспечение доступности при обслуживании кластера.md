# Обеспечение доступности при обслуживании кластера: PodDisruptionBudget (PDB)

## Условие

Настрой **PodDisruptionBudget (PDB)**: `minAvailable: 2` или `maxUnavailable: 1`. Защита от voluntary disruptions: node drain, cluster upgrade. Покажи, что ensures availability during maintenance.

## Теория

В процессе эксплуатации кластера регулярно происходят добровольные прерывания (**Voluntary Disruptions**):
- Обновление версии Kubernetes на нодах (`kubeadm upgrade`).
- Перезагрузка нод для установки патчей ядра Linux.
- Вывод ноды из эксплуатации инженером командой `kubectl drain <node>`.
- Сжатие кластера (Scale Down) облачным автоскейлером.

Без защитных механизмов `kubectl drain` может одномоментно остановить все поды сервиса на ноде, вызвав недоступность (Downtime).

**PodDisruptionBudget (PDB) (`apiVersion: policy/v1`)**:
- Гарантирует минимальное количество подов, обязанных оставаться доступными во время обслуживания.
- Параметры: `minAvailable: 2` или `maxUnavailable: 1`.

## Решение по шагам

1. Создайте манифест `pdb.yaml` с селектором вашего сервиса.
2. Задайте `minAvailable: 2` (для сервиса из 3 реплик).
3. Примените манифест: `kubectl apply -f pdb.yaml`.
4. Проверьте текущий статус бюджета: `kubectl get pdb`.
5. Попробуйте выполнить drain ноды и убедитесь, что K8s не выселяет поды сверх лимита.

## Код решения

**`pdb.yaml`**

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-service-pdb
spec:
  minAvailable: 2 # Минимум 2 реплики обязаны работать в любой момент времени
  selector:
    matchLabels:
      app: payment-service
```

**`test-drain.sh`**

```bash
# Просмотр статуса PDB
kubectl get pdb payment-service-pdb
# Вывод:
# NAME                  MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
# payment-service-pdb   2               N/A               1                     5m

# Попытка вывода ноды из эксплуатации:
# K8s выселит 1 под, дождется старта новой реплики на другой ноде,
# и только потом разрешит выселить следующий под!
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
```

## Под капотом

Когда инженер выполняет `kubectl drain`, утилита вызывает API выселения: `POST /api/v1/namespaces/default/pods/<name>/eviction`. 

API Server обращается к контроллеру PDB. Контроллер проверяет:
\(\text{CurrentHealthyPods} - 1 \ge \text{minAvailable}\)
Если условие истинно, выселение разрешается. Если условие ложно, API Server возвращает ошибку `429 Too Many Requests (Cannot evict pod as it would violate the pod's disruption budget)`, и команда drain ожидает появления новых готовых подов.

## Подводные камни

1. Задание `minAvailable: 100%` или `maxUnavailable: 0`: ноду с такими подами невозможно будет заэвакуировать через `kubectl drain`, команда зависнет навсегда.
2. PDB не защищает от **Involuntary Disruptions** (аварии железа, внезапное отключение питания сервера, kernel panic): бюджет действует только на плановые действия через Eviction API.
3. Забытый PDB для одиночных подов (`replicas: 1`): drain приведет к гарантированному даунтайму.

## На собеседовании

**Вопрос с собеседования:** В чем разница между Voluntary и Involuntary Disruptions в Kubernetes и что защищает сервис от каждого из них?
**Ответ:** 
- **Voluntary Disruptions (Плановые прерывания):** Инициируются администратором или автоматикой (`kubectl drain`, обновление нод, Cluster Autoscaler, выселение VPA). От них сервис **защищает `PodDisruptionBudget` (PDB)**, блокируя выселение сверх бюджета.
- **Involuntary Disruptions (Внеплановые аварии):** Аппаратный сбой сервера, падение гипервизора, сбой питания, потеря сети. PDB от них спасти не может. Защитой служит **высокий фактор репликации (`replicas >= 3`)** и распределение подов по разным зонам доступности через **`podAntiAffinity`**.
