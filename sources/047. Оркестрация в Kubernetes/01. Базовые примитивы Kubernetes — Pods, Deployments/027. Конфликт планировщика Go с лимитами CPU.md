# Конфликт планировщика Go с лимитами CPU (GOMAXPROCS) и интеграция automaxprocs

## Условие

**Конфликт планировщика Go с лимитами CPU (GOMAXPROCS)**: * Объясните в комментариях проблему: если в K8s выставить лимит по процессору `resources.limits.cpu: "2"`, рантайм Go по-прежнему будет видеть общее количество ядер физического сервера (например, 64 ядра) и установит `GOMAXPROCS` равным 64. Это приведет к сильному троттлингу (замедлению) контейнера планировщиком CFS ядра Linux.
* Решите эту проблему: импортируйте популярную библиотеку `go.uber.org/automaxprocs` в ваш файл `main.go` [465]. Запустите контейнер в K8s и убедитесь по логам, что Go автоматически скорректировал количество потоков под реальные лимиты контейнера [465].

## Теория

Одна из самых коварных проблем производительности Go в Kubernetes:
- Рантайм Go при старте определяет количество потоков ОС планировщика (`GOMAXPROCS`) через системный вызов `runtime.NumCPU()`.
- Системный вызов возвращает **общее количество физических ядер хост-машины** (например, 64 или 128 ядер), полностью игнорируя лимиты cgroups контейнера (`limits.cpu: "2"`).
- В результате Go запускает 64 системных потока (`M` в модели GMP), которые начинают параллельно исполнять горутины.
- Планировщик Linux CFS исчерпывает 200 мс квоты (лимит 2 CPU) за считанные миллисекунды и жестко замораживает все потоки контейнера (**CPU Throttling**).
- Задержка ответов (latency) сервиса взлетает с 5 мс до 800 мс!

Решение — библиотека от инженеров Uber: **`go.uber.org/automaxprocs`**. Она считывает реальные квоты CFS из `/sys/fs/cgroup` и автоматически выставляет `GOMAXPROCS` равным реальному лимиту контейнера.

## Решение по шагам

1. Добавьте библиотеку `go get go.uber.org/automaxprocs`.
2. Импортируйте пакет через анонимный импорт `_ "go.uber.org/automaxprocs"` в начале файла `main.go`.
3. Задайте в манифесте `resources.limits.cpu: "2"`.
4. Запустите контейнер в Kubernetes.
5. Убедитесь по логам старта, что `GOMAXPROCS` автоматически скорректирован с 64 до 2.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"runtime"

	// Автоматическая настройка GOMAXPROCS под cgroups лимиты K8s
	_ "go.uber.org/automaxprocs"
)

func main() {
	fmt.Printf("Сервис запущен. Реальное значение GOMAXPROCS = %d (Ядер на хосте: %d)\n",
		runtime.GOMAXPROCS(0), runtime.NumCPU())

	http.HandleFunc("/compute", func(w http.ResponseWriter, r *http.Request) {
		// Имитация вычислений
		total := 0
		for i := 0; i < 1_000_000; i++ {
			total += i
		}
		fmt.Fprintf(w, "GOMAXPROCS=%d, Result=%d\n", runtime.GOMAXPROCS(0), total)
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: automaxprocs-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: automaxprocs-demo
  template:
    metadata:
      labels:
        app: automaxprocs-demo
    spec:
      containers:
        - name: app
          image: ghcr.io/company/automaxprocs-demo:v1.0.0
          resources:
            requests:
              cpu: "1"
              memory: "128Mi"
            limits:
              cpu: "2" # Лимит 2 ядра на 64-ядерном сервере
              memory: "256Mi" 
```

## Под капотом

В функции `init()` пакет `automaxprocs` инспектирует виртуальную файловую систему cgroups v1 (`/sys/fs/cgroup/cpu/cpu.cfs_quota_us`) или cgroups v2 (`/sys/fs/cgroup/cpu.max`). 

Он делит квоту на период (`quota / period`). Например, для лимита 2 CPU: \(200000 / 100000 = 2.0\). Пакет округляет дробное значение вниз (floor) и вызывает стандартную функцию `runtime.GOMAXPROCS(2)`. Логи выводятся в формате: `maxprocs: Updating GOMAXPROCS=2: using cgroups quota`.

## Подводные камни

1. Дробные лимиты CPU (`limits.cpu: "500m"`): округление дает `GOMAXPROCS=1`, что является безопасным минимумом.
2. Отсутствие `automaxprocs` в микросервисах с пулом горутин: приводит к колоссальному падению throughput и деградации p99 latency под нагрузкой.
3. Ручная жесткая установка `runtime.GOMAXPROCS(N)` в коде: лишает контейнер гибкости при изменении манифестов K8s.

## На собеседовании

**Вопрос с собеседования:** Почему в Kubernetes при `limits.cpu: "2"` на 64-ядерном сервере приложение без `automaxprocs` испытывает сильный CFS Throttling, даже если CPU утилизация составляет всего 50%?
**Ответ:** Планировщик Go видит 64 ядра и создает 64 системных потока ОС (`M`). Когда поступает пачка запросов, планировщик Go одновременно будит все 64 потока на разных ядрах. 
За каждую миллисекунду реального времени 64 ядра суммарно сжигают 64 мс квоты. Выделенный лимит в 2 ядра (200 мс на период 100 мс) исчерпывается всего за **3.125 миллисекунды**! Оставшиеся 96.8 миллисекунд контейнер находится в состоянии глубокого троттлинга ядра Linux, а клиенты ждут ответов.
