# Настройка Readiness Probe через эндпоинт /readyz для защиты от сбоев БД

## Условие

Настройте **Readiness probe** через `/readyz`. K8s перестанет отправлять трафик на поды, которые не готовы (например, при недоступности БД).

## Теория

Главная задача **`readinessProbe`** — гарантировать, что трафик реальных пользователей направляется **только на те поды, которые прямо сейчас способны успешно его обработать**.

Сценарии использования эндпоинта `/readyz`:
- **Старт сервиса:** Приложение запустило HTTP-сервер, но еще не прогрело локальный LRU-кэш или не подключилось к пулу соединений PostgreSQL. Под не должен получать трафик до статуса 200 OK.
- **Временная недоступность внешних сервисов:** Если БД перезагружается или исчерпала лимит коннектов, эндпоинт `/readyz` возвращает статус `503 Service Unavailable`. K8s немедленно исключает под из балансировки `Service`, клиенты не получают ошибок 500, а запросы перенаправляются на другие исправные реплики.

## Решение по шагам

1. Создайте в коде Go эндпоинт `/readyz` с реальной проверкой пинга БД (`db.PingContext`).
2. В `deployment.yaml` настройте блок `readinessProbe`.
3. Установите `periodSeconds: 5`, `failureThreshold: 2`.
4. Протестируйте поведение сервиса при разрыве соединения с БД.
5. Убедитесь, что IP пода исчезает из вывода `kubectl get endpoints`.

## Код решения

**`readiness-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: app
          image: ghcr.io/company/order-service:v1.0.0
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
            successThreshold: 1
```

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"sync/atomic"
	"time"
)

type DatabaseMock struct {
	healthy atomic.Bool
}

func (db *DatabaseMock) Ping(ctx context.Context) error {
	if !db.healthy.Load() {
		return fmt.Errorf("соединение с базой данных потеряно")
	}
	return nil
}

func main() {
	db := &DatabaseMock{}
	db.healthy.Store(true)

	// Readiness эндпоинт: проверяет возможность обработать SQL транзакции
	http.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), 1*time.Second)
		defer cancel()

		if err := db.Ping(ctx); err != nil {
			w.WriteHeader(http.StatusServiceUnavailable)
			_, _ = w.Write([]byte("NOT_READY: " + err.Error()))
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})

	// Эндпоинт симуляции сбоя СУБД
	http.HandleFunc("/simulate-db-down", func(w http.ResponseWriter, r *http.Request) {
		db.healthy.Store(false)
		_, _ = w.Write([]byte("Состояние БД изменено на UNHEALTHY"))
	})

	fmt.Println("Сервис заказов слушает на :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Когда `kubelet` фиксирует отказ `readinessProbe` (код 503), он отправляет событие изменения статуса пода `PodReady: False` в API-сервер. 

Контроллер `EndpointSlice` немедленно удаляет IP-адрес этого пода из списка активных эндпоинтов сервиса. Демон `kube-proxy` на всех нодах пересчитывает правила iptables/IPVS. В результате новые сетевые пакеты перестают маршрутизироваться на деградировавший под.

## Подводные камни

1. Забытый `timeoutSeconds`: если БД зависает без ответа, HTTP-запрос пробы висит бесконечно, блокируя горутины сервера. Всегда используйте `context.WithTimeout`.
2. Использование одинаковой логики в `liveness` и `readiness`: если упала внешняя БД, liveness-проба начнет циклически перезапускать поды, а readiness-проба корректно снимет под с балансировки.
3. Отсутствие `successThreshold: 1`: после восстановления БД под должен моментально вернуться в балансировку.

## На собеседовании

**Вопрос с собеседования:** Что произойдет с входящими HTTP-запросами, если во всем кластере у всех 10 реплик сервиса одновременно откажет `readinessProbe`?
**Ответ:** Объект `Endpoints` сервиса станет полностью пустым (0 активных IP). 
В зависимости от конфигурации:
1. Внутренний Kube-proxy сбросит соединение с ошибкой `Connection refused` (нет доступных бэкендов).
2. Внешний Ingress-контроллер (Nginx / ALB / Envoy) вернет клиентам статус **503 Service Unavailable** или **502 Bad Gateway**.
3. При этом **поды не будут перезапущены**, а останутся работать в ожидании восстановления зависимостей, предотвращая каскадный шторм рестартов.
