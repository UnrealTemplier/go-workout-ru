# Практическое применение Deployment.yaml и инспекция состояния через kubectl

## Условие

Напиши `Deployment.yaml` для своего Go-приложения (replicas: 3). Примени `kubectl apply -f`. Проверь статус подов.

## Теория

Уверенное владение утилитой командной строки `kubectl` — ключевой навык инженера при эксплуатации приложений в кластере Kubernetes:
- `kubectl apply -f <file>`: декларативное применение манифеста (алгоритм 3-way merge).
- `kubectl get pods -l <label>`: просмотр статуса, числа перезапусков (Restarts) и времени жизни (Age).
- `kubectl describe pod <name>`: детальный аудит состояний контейнеров, событий планировщика (Events) и диагностических проб.
- `kubectl logs -f <name>`: потоковый просмотр stdout/stderr логов контейнера.
- `kubectl exec -it <name> -- /bin/sh`: интерактивное подключение внутрь контейнера.

## Решение по шагам

1. Создайте манифест `deployment.yaml` с 3 репликами.
2. Примените манифест командой `kubectl apply -f deployment.yaml`.
3. Запросите статус развертывания: `kubectl rollout status deployment/web-demo`.
4. Выведите список запущенных подов с расширенной информацией: `kubectl get pods -o wide`.
5. Изучите вывод секции `Events` в `kubectl describe pod <name>`.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-demo
  labels:
    tier: frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      tier: frontend
  template:
    metadata:
      labels:
        tier: frontend
    spec:
      containers:
        - name: app
          image: alpine:3.21
          command: ["/bin/sh", "-c", "echo 'Web demo ready'; sleep 3600"]
          ports:
            - containerPort: 8080
```

**`inspect.sh`**

```bash
# 1. Применение манифеста
kubectl apply -f deployment.yaml

# 2. Ожидание завершения развертывания
kubectl rollout status deployment/web-demo --timeout=60s

# 3. Получение списка подов с IP адресами и именами нод
kubectl get pods -l tier=frontend -o wide

# 4. Просмотр логов всех реплик деплоймента одновременно
kubectl logs -l tier=frontend --tail=20
```

## Под капотом

Команда `kubectl apply` рассчитывает разницу (diff) между локальным YAML, текущей конфигурацией в etcd и последней примененной конфигурацией, записанной в системной аннотации `kubectl.kubernetes.io/last-applied-configuration`. 

Это гарантирует, что поля, добавленные сторонними контроллерами (например, HPA или Istio sidecar injector), не будут стерты при повторном применении локального файла.

## Подводные камни

1. Использование `kubectl create` вместо `kubectl apply`: команда `create` падает с ошибкой, если ресурс уже существует в кластере.
2. Игнорирование секции `Events` при статусе `Pending`: разработчик часто гадает, почему под не стартует, хотя в событиях четко написано `0/5 nodes available: insufficient cpu`.
3. Ручная правка манифестов через `kubectl edit`: приводит к рассинхронизации кластера с кодовой базой Git (Configuration Drift).

## На собеседовании

**Вопрос с собеседования:** Что происходит под капотом K8s при выполнении команды `kubectl exec -it <pod> -- /bin/sh`?
**Ответ:** 
1. `kubectl` отправляет HTTP POST-запрос с заголовком `Upgrade: SPDY / WebSocket` на K8s API Server.
2. API Server проверяет права RBAC пользователя.
3. API Server открывает стриминговое соединение с агентом `kubelet` целевой ноды.
4. `kubelet` через интерфейс CRI вызывает метод `Exec()` демона `containerd`.
5. `containerd` порождает процесс `/bin/sh` внутри Linux cgroups/namespaces целевого контейнера и связывает его дескрипторы pty (stdin/stdout/stderr) со стримом пользователя.
