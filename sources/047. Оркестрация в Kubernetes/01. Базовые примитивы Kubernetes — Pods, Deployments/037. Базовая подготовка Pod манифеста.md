# Базовая подготовка Pod манифеста и инспекция логов через kubectl

## Условие

**Подготовка (Pod)**: Напиши файл `pod.yaml`. Опиши в нем сущность `Pod`, укажи свой Docker-образ (из упр. 591). Запусти через `kubectl apply -f pod.yaml`. Проверь статус через `kubectl get pods`. Посмотри логи через `kubectl logs my-pod`.

## Теория

Практическое закрепление базовых операций с подами:
- Описание манифеста `pod.yaml` с образом приложения.
- Развертывание в кластере через `kubectl apply -f pod.yaml`.
- Инспекция фаз жизненного цикла пода (`Pending`, `ContainerCreating`, `Running`, `Completed`, `Failed`).
- Чтение стандартных потоков вывода через `kubectl logs`.

## Решение по шагам

1. Создайте файл `pod.yaml`.
2. Задайте имя `my-pod` и контейнер с образом `k8s-demo`.
3. Примените манифест: `kubectl apply -f pod.yaml`.
4. Проверьте запуск пода: `kubectl get pods my-pod`.
5. Посмотрите логи: `kubectl logs my-pod`.

## Код решения

**`pod.yaml`**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels:
    app: training-demo
spec:
  containers:
    - name: app
      image: alpine:3.21
      command: ["/bin/sh", "-c"]
      args:
        - |
          echo "Инициализация учебного пода..."
          echo "Сервис успешно стартовал в пространстве K8s!"
          sleep 3600
```

**`commands.sh`**

```bash
# 1. Применение манифеста пода
kubectl apply -f pod.yaml

# 2. Проверка статуса
kubectl get pod my-pod -o wide

# 3. Чтение логов контейнера
kubectl logs my-pod

# 4. Удаление пода
kubectl delete pod my-pod
```

## Под капотом

Когда контейнер пишет в stdout или stderr, рантайм `containerd` перенаправляет эти потоки в JSON/CRI-логи на диске ноды:
`/var/log/pods/<namespace>_<pod_name>_<pod_id>/<container_name>/0.log`
Команда `kubectl logs` делает HTTP GET запрос на API Server, который открывает стрим к демону `kubelet` ноды, а Kubelet считывает файл лога с диска.

## Подводные камни

1. Запись логов в локальные файлы внутри контейнера вместо stdout: логи теряются при удалении пода и недоступны через `kubectl logs`.
2. Переполнение диска ноды: отсутствие ротации логов в настройках Kubelet/containerd.
3. Падение пода при запуске фоновых демонов без процесса на переднем плане (PID 1 завершается, и контейнер останавливается).

## На собеседовании

**Вопрос с собеседования:** Почему в Kubernetes категорически рекомендуется писать логи в stdout/stderr процесса, а не в файлы внутри контейнера?
**Ответ:** Следование принципу 12-Factor App (Logs as Event Streams). 
Контейнер должен быть stateless: у него нет гарантий сохранения локального диска при перезапуске. Запись в stdout позволяет K8s-инфраструктуре единообразно перехватывать логи на уровне рантайма (containerd), ротировать их на ноде и автоматически собирать агентными сборщиками (Fluentbit, Vector, Promtail) в централизованные хранилища (Elasticsearch, Loki, ClickHouse) без необходимости монтировать тома или настраивать пути внутри каждого сервиса.
