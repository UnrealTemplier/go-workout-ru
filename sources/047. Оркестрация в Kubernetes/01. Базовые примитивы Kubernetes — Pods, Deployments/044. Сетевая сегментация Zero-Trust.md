# Сетевая сегментация Zero-Trust: манифест NetworkPolicy для защиты базы данных

## Условие

Настрой **NetworkPolicy**: `kind: NetworkPolicy`, `podSelector: matchLabels: app: database`, `policyTypes: [Ingress]`, `ingress: - from: - podSelector: matchLabels: app: backend`, `ports: - protocol: TCP, port: 5432`. Покажи zero-trust network segmentation.

## Теория

По умолчанию в Kubernetes действует открытая модель сети (Flat Network Model): любой под в любом namespace может свободно отправлять TCP-пакеты на любой другой под или сервис.

Принципы безопасности Zero-Trust требуют строгой изоляции:
Ресурс **`NetworkPolicy` (`apiVersion: networking.k8s.io/v1`)**:
- Действует как распределенный программный межсетевой экран (Firewall).
- Селектор `podSelector.matchLabels: app: database` выбирает целевые поды.
- Секция `ingress.from` разрешает входящие TCP-соединения на порт 5432 **строго от подов с меткой `app: backend`**.
- Любые другие попытки подключения (например, от взломанного frontend-пода или чужого сервиса) блокируются ядром на корню.

## Решение по шагам

1. Убедитесь, что в кластере установлен CNI-плагин с поддержкой NetworkPolicy (Cilium, Calico).
2. Создайте манифест `db-network-policy.yaml`.
3. Опишите правило: входящий трафик на порт 5432 разрешен только от `app: backend`.
4. Примените манифест: `kubectl apply -f db-network-policy.yaml`.
5. Протестируйте подключение: от frontend-пода соединение должно отваливаться по таймауту, а от backend — успешно проходить.

## Код решения

**`db-network-policy.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: secure-database-access
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: backend
      ports:
        - protocol: TCP
          port: 5432
```

**`test-isolation.sh`**

```bash
# 1. Проверка от пода backend (доступ РАЗРЕШЕН):
kubectl run test-backend --rm -it --labels="app=backend" --image=postgres:16-alpine -- \
  pg_isready -h database -p 5432

# 2. Проверка от постороннего пода frontend (доступ ЗАБЛОКИРОВАН):
kubectl run test-frontend --rm -it --labels="app=frontend" --image=postgres:16-alpine -- \
  pg_isready -h database -p 5432 --timeout=3
```

## Под капотом

Сетевой агент CNI (например, eBPF-программы Cilium или iptables-цепочки Calico `felix`) перехватывает сетевые интерфейсы `veth`. 

Как только на поды вешается `NetworkPolicy`, CNI переводит целевой под в режим изоляции (Default Deny для входящего трафика) и генерирует правила BPF/iptables, пропускающие пакеты строго от исходных IP-адресов, помеченных меткой `app: backend`.

## Подводные камни

1. Использование стандартного CNI Flannel: Flannel не поддерживает NetworkPolicy, манифест применится без ошибок, но фильтрация работать **не будет**.
2. Блокировка DNS-трафика: если включить `policyTypes: [Egress]` без разрешения исходящего UDP 53 порта к CoreDNS, поды не смогут резолвить доменные имена.
3. Селектор по namespace: если backend и база находятся в разных пространствах имен, требуется добавить `namespaceSelector`.

## На собеседовании

**Вопрос с собеседования:** Почему в enterprise кластерах в каждом namespace создают правило «Default Deny All NetworkPolicy»?
**Ответ:** По умолчанию сеть в K8s полностью открыта. Если злоумышленник через RCE (Remote Code Execution) взломает публичный микросервис на периметре, он сможет сканировать всю внутреннюю сеть кластера (Lateral Movement), подключаться к базам данных, Redis и внутренним Kafka брокерам. 
Политика «Default Deny All» блокирует весь входящий и исходящий трафик в namespace по умолчанию. Разработчик обязан явно задекларировать белый список разрешенных сетевых связей для каждого сервиса.
