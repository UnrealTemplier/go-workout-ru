# Изоляция рабочих нагрузок: механизмы Taints и Tolerations

## Условие

Настрой **Taints и Tolerations**: `node taint: dedicated=gpu:NoSchedule`. Pod с `toleration: key: dedicated, operator: Equal, value: gpu, effect: NoSchedule` может запланироваться на GPU node. Покажи dedicated node pools.

## Теория

Механизм **Taints (Окрашивания)** и **Tolerations (Терпимости)** позволяет нодам кластера «отталкивать» определенный набор подов:
- Нода помечается окрашиванием (Taint): `kubectl taint nodes gpu-node dedicated=gpu:NoSchedule`. Это означает: «Ни один под не может быть запланирован на эту ноду, если у него нет соответствующей терпимости (Toleration)».
- Под объявляет терпимость (`tolerations`): `key: dedicated, value: gpu, effect: NoSchedule`.

Сценарии применения в BigTech:
1. **Выделенные нод-пулы с GPU/TPU:** Защита дорогостоящих серверов с видеокартами от случайного запуска обычных легковесных микросервисов.
2. **Dedicated Infrastructure:** Изоляция чувствительных баз данных или финансовых платежных сервисов на отдельных физических серверах (Bare-metal нодах).
3. **Реакция на сбои нод:** Автоматические системные taints (`node.kubernetes.io/not-ready:NoExecute`).

## Решение по шагам

1. Окрасьте целевую ноду: `kubectl taint nodes node-gpu-1 dedicated=gpu:NoSchedule`.
2. В манифесте `deployment.yaml` опишите секцию `spec.template.spec.tolerations`.
3. Укажите оператор `Equal`, ключ `dedicated`, значение `gpu` и эффект `NoSchedule`.
4. Разверните сервис и убедитесь через `kubectl get pods -o wide`, что под запланирован на GPU-ноду.
5. Убедитесь, что поды без `tolerations` не попадают на эту ноду.

## Код решения

**`gpu-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ml-inference
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ml-inference
  template:
    metadata:
      labels:
        app: ml-inference
    spec:
      tolerations:
        - key: "dedicated"
          operator: "Equal"
          value: "gpu"
          effect: "NoSchedule"
      # В дополнение к toleration используем nodeSelector для точной посадки на GPU:
      nodeSelector:
        accelerator: "nvidia-tesla-v100"
      containers:
        - name: inference
          image: ghcr.io/company/ml-model:v1.0.0
          resources:
            limits:
              nvidia.com/gpu: 1
```

**`taint-commands.sh`**

```bash
# 1. Окрашивание ноды: запретить планирование обычных подов
kubectl taint nodes worker-gpu-1 dedicated=gpu:NoSchedule

# 2. Добавление метки ноды для nodeSelector
kubectl label nodes worker-gpu-1 accelerator=nvidia-tesla-v100

# 3. Проверка существующих taints на ноде
kubectl describe node worker-gpu-1 | grep Taints
```

## Под капотом

`kube-scheduler` на этапе фильтрации (Node Filtering) инспектирует список `node.spec.taints`. Для каждого taint ноды планировщик ищет соответствующую запись в `pod.spec.tolerations`. 

Эффекты taints:
- `NoSchedule`: Новые поды без toleration не могут быть запланированы на ноду, но уже работающие поды не трогаются.
- `PreferNoSchedule`: Планировщик старается избегать ноды, но назначит под при отсутствии альтернатив.
- `NoExecute`: Поды без toleration не только не назначаются, но и **немедленно выселяются (evicted)** с ноды!

## Подводные камни

1. Заблуждение о привязке: `toleration` **не заставляет** под идти на эту конкретную ноду, он лишь **разрешает** ему там запуститься! Чтобы под пошел строго на GPU ноду, необходимо комбинировать `tolerations` с `nodeSelector` или `nodeAffinity`.
2. Опечатка в ключе или регистре (case-sensitive): под зависнет в статусе `Pending`.
3. Забытое снятие тайнта при выводе ноды из карантина: `kubectl taint nodes node-1 key:NoSchedule-`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между эффектами тайнта `NoSchedule` и `NoExecute`?
**Ответ:** 
- **`NoSchedule`** действует только на **новые поды** в момент работы планировщика. Поды, которые уже работают на ноде, продолжают работать.
- **`NoExecute`** действует на **все поды**: если нода получает таинт `NoExecute`, Kubelet немедленно выселяет (убивает) все работающие поды, не имеющие соответствующей терпимости (`toleration`). Это используется для автоматической эвакуации подов с умирающих нод (`node.kubernetes.io/unreachable:NoExecute` с параметром `tolerationSeconds: 300`).
