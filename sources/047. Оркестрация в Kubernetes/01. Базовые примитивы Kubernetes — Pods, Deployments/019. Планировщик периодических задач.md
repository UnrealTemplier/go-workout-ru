# Планировщик периодических задач: CronJob для бэкапов и фоновой обработки

## Условие

Напиши **CronJob**: `kind: CronJob`, `schedule: "0 2 * * *"` (daily at 2 AM). `jobTemplate` для backup, cleanup, report generation. Покажи scheduled tasks in Kubernetes.

## Теория

Для выполнения регламентных задач по расписанию (ежедневная очистка устаревших сессий, создание резервных копий БД в 02:00 ночи, генерация аналитических отчетов) в Kubernetes используется ресурс **`CronJob` (`apiVersion: batch/v1`)**:
- Синтаксис расписания аналогичен стандартному Linux Cron: `schedule: "0 2 * * *"` (минута, час, день месяца, месяц, день недели).
- `concurrencyPolicy`: определяет поведение при наложении запусков:
  - `Allow` (по умолчанию): задачи могут запускаться параллельно.
  - `Forbid`: если предыдущая задача еще не завершилась, новый запуск пропускается.
  - `Replace`: если старая задача еще работает, она отменяется, а вместо нее запускается новая.
- `successfulJobsHistoryLimit` и `failedJobsHistoryLimit`: лимиты хранения завершенных подов.

## Решение по шагам

1. Создайте код фоновой задачи на Go.
2. Опишите манифест `cronjob.yaml` с расписанием `schedule: "0 2 * * *"`.
3. Установите политику параллелизма `concurrencyPolicy: Forbid`.
4. Задайте лимиты истории: `successfulJobsHistoryLimit: 3`.
5. Примените манифест и протестируйте внеплановый запуск через `kubectl create job --from=cronjob/daily-backup test-run`.

## Код решения

**`cronjob.yaml`**

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-backup
spec:
  schedule: "0 2 * * *" # Ежедневно в 02:00 ночи UTC
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup-worker
              image: ghcr.io/company/backup-tool:v1.0.0
              command: ["/bin/backup", "--target=s3"]
              env:
                - name: S3_BUCKET
                  value: "production-backups-archive" 
```

**`backup.go`**

```go
package main

import (
	"fmt"
	"os"
	"time"
)

func main() {
	bucket := os.Getenv("S3_BUCKET")
	fmt.Printf("[%s] Старт создания резервной копии в бакет %s...\n", time.Now().Format(time.RFC3339), bucket)

	// Имитация создания дампа
	time.Sleep(3 * time.Second)

	fmt.Println("Дамп базы данных успешно загружен в S3. Задача завершена.")
}
```

**`test-cron.sh`**

```bash
# Применение CronJob
kubectl apply -f cronjob.yaml

# Ручной запуск Job из шаблона CronJob (без ожидания 02:00 ночи)
kubectl create job --from=cronjob/daily-backup manual-test-run

# Просмотр статуса выполнения
kubectl get jobs
kubectl logs job/manual-test-run
```

## Под капотом

`CronJobController` внутри `kube-controller-manager` каждые 10 секунд опрашивает зарегистрированные объекты `CronJob`. Он вычисляет время следующего запуска по локальному времени контроллера. 

При наступлении назначенного времени контроллер создает дочерний объект `Job`, который в свою очередь порождает рабочий `Pod`. Политика `concurrencyPolicy: Forbid` проверяет список активных подов: если статус предыдущего пода не равен `Complete`, контроллер логирует пропуск итерации.

## Подводные камни

1. Неправильный часовой пояс (Timezone): исторически расписание CronJob исполнялось строго по времени мастер-нод (UTC). Начиная с K8s 1.27 доступно поле `timeZone: "Europe/Moscow"`.
2. Политика `Allow` при долгих бэкапах: если бэкап завис и работает 25 часов, каждую ночь будет запускаться еще один экземпляр, что приведет к исчерпанию ресурсов ноды и базы данных.
3. Отсутствие лимитов истории: тысячи записей завершенных задач засоряют etcd.

## На собеседовании

**Вопрос с собеседования:** Что произойдет, если нода с CronJobController перезагружалась во время планового времени срабатывания CronJob?
**Ответ:** Поле `startingDeadlineSeconds` определяет временное окно: если контроллер был недоступен, но поднялся в пределах заданного таймаута (например, `startingDeadlineSeconds: 300` — 5 минут), он догонит расписание и немедленно запустит пропущенную задачу. Если параметр не задан, а было пропущено более 100 интервалов запуска, K8s регистрирует ошибку и больше не запускает CronJob до ручного вмешательства.
