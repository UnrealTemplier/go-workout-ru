# Унификация жизненного цикла сборки и деплоя с помощью Makefile

## Условие

Напишите `Makefile` с командами `build`, `test`, `lint`, `docker-build`, `docker-run`.

## Теория

`Makefile` — стандарт декларативного описания задач сборки, тестирования и запуска в профессиональных инженерных командах. 

Он абстрагирует разработчика и CI/CD раннеры от громоздких флагов компилятора:
- `make test`: запуск юнит-тестов с детектором гонок.
- `make lint`: проверка кода статическим анализатором `golangci-lint`.
- `make docker-build`: сборка OCI-образа с динамической подстановкой Git SHA и версии.
- `make docker-run`: локальный запуск с пробросом портов и переменных окружения.

Использование директивы `.PHONY` гарантирует корректное выполнение команд даже при наличии одноименных файлов или папок на диске.

## Решение по шагам

1. Создайте в корне проекта файл `Makefile`.
2. Объявите переменные сборки: `APP_NAME`, `GIT_SHA`, `IMAGE_TAG`.
3. Опишите цели: `build`, `test`, `lint`, `docker-build`, `docker-run`.
4. Добавьте флаги `-race`, `-cover` для тестирования и `-ldflags="-s -w"` для компиляции.
5. Протестируйте выполнение команд в терминале.

## Код решения

**`Makefile`**

```makefile
APP_NAME ?= k8s-service
REGISTRY ?= ghcr.io/company
GIT_SHA  ?= $(shell git rev-parse --short HEAD 2>/dev/null || echo "dev")
IMAGE    ?= $(REGISTRY)/$(APP_NAME):$(GIT_SHA)

.PHONY: all build test lint docker-build docker-run clean

all: lint test build

build:
	@echo "==> Компиляция Go бинарника..."
	CGO_ENABLED=0 go build -ldflags="-s -w -X main.version=$(GIT_SHA)" -o bin/$(APP_NAME) .

test:
	@echo "==> Запуск тестов с детектором гонок..."
	go test -v -race -coverprofile=coverage.out ./...

lint:
	@echo "==> Проверка кода линтером..."
	golangci-lint run --timeout=5m

docker-build:
	@echo "==> Сборка Docker-образа $(IMAGE)..."
	docker build -t $(IMAGE) -t $(REGISTRY)/$(APP_NAME):latest .

docker-run:
	@echo "==> Локальный запуск контейнера..."
	docker run --rm -p 8080:8080 -e PORT=8080 $(IMAGE)

clean:
	@rm -rf bin/ coverage.out
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

var version = "dev"

func main() {
	http.HandleFunc("/version", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte(fmt.Sprintf("Version: %s\n", version)))
	})
	fmt.Printf("Сервис версии %s запущен на :8080\n", version)
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

GNU Make парсит зависимости между целями и запускает каждую строку рецепта в отдельном подоболочке `/bin/sh`. 

Символ `@` в начале строки отключает эхо-вывод самой команды в терминал. Директива `.PHONY: build test` предотвращает коллизию: если в каталоге появится папка с именем `build`, Make не будет считать цель выполненной, а принудительно исполнит рецепт.

## Подводные камни

1. Использование пробелов вместо табуляций (`Tab`): синтаксический анализатор Make требует строго символ табуляции в начале строк рецептов.
2. Отсутствие `.PHONY`: если случайно создать каталог `test`, вызов `make test` выдаст `make: 'test' is up to date` и ничего не выполнит.
3. Жестко зашитые теги образов (`latest`): сборка затирает предыдущие версии без возможности отката.

## На собеседовании

**Вопрос с собеседования:** Почему в enterprise Go-репозиториях для автоматизации локальных задач предпочитают `Makefile` или `Taskfile` вместо bash-скриптов `build.sh`?
**Ответ:** 
1. **Декларативный граф зависимостей:** Make умеет проверять временные метки файлов (mtime) и пересобирать только измененные артефакты.
2. **Единый стандартизированный интерфейс:** Новому разработчику в команде не нужно читать документацию по десяткам скриптов: вызов `make all` или `make test` одинаково работает в 100 разных сервисах компании.
3. **Бесшовная интеграция с CI:** Пайплайн в GitHub Actions или GitLab CI просто вызывает те же самые таргеты `make test`, гарантируя 100% идентичность проверок локально и на сервере сборки.
