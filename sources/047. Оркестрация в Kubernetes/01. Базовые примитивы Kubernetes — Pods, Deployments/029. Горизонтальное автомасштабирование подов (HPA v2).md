# Горизонтальное автомасштабирование подов (HPA v2) по утилизации CPU

## Условие

Настрой **HorizontalPodAutoscaler (HPA)**: `apiVersion: autoscaling/v2`, `metrics: - type: Resource, resource: name: cpu, target: type: Utilization, averageUtilization: 70`. Scale 3 → 10 pods. Покажи autoscaling.

## Теория

**HorizontalPodAutoscaler (HPA)** — контроллер автоматического масштабирования количества реплик пода в зависимости от нагрузки.

В спецификации `autoscaling/v2`:
- Поддерживается масштабирование по ресурсам (CPU, Memory) и кастомным/внешним метрикам (Prometheus, очереди RabbitMQ, Kafka lag).
- Алгоритм расчета целевого числа реплик:
  $$\text{DesiredReplicas} = \lceil \text{CurrentReplicas} \times \frac{\text{CurrentMetricValue}}{\text{TargetMetricValue}} \rceil$$
- При значении `averageUtilization: 70` по CPU: если средняя загрузка по всем подам достигает 70% от `requests.cpu`, HPA плавно увеличивает число реплик от 3 до 10.

## Решение по шагам

1. Убедитесь, что в кластере установлен `metrics-server`.
2. Убедитесь, что в манифесте `Deployment` заданы `resources.requests.cpu`.
3. Создайте манифест `hpa.yaml` с диапазоном реплик 3..10 и целевым порогом CPU 70%.
4. Примените манифест: `kubectl apply -f hpa.yaml`.
5. Проверьте статус автомасштабирования: `kubectl get hpa`.

## Код решения

**`hpa.yaml`**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-autoscaler
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-service
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300 # Предотвращение флаппинга при спаде нагрузки
      policies:
        - type: Percent
          value: 20
          periodSeconds: 60
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-service
  template:
    metadata:
      labels:
        app: api-service
    spec:
      containers:
        - name: app
          image: ghcr.io/company/api:v1.0.0
          resources:
            requests:
              cpu: "200m" # HPA считает процент именно от этого значения
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi" 
```

## Под капотом

`HPAController` внутри `kube-controller-manager` каждые 15 секунд опрашивает `Metrics API` (`metrics.k8s.io`). 

Контроллер получает текущую загрузку CPU от `metrics-server`, который собирает метрики со всех нод через cAdvisor. Если текущее значение составляет 140m при request 200m (\(70\%\)), система находится в балансе. 

Если загрузка возрастает до 180m (\(90\%\)), HPA рассчитывает: \(3 \times (90 / 70) = 3.85 \rightarrow 4\) реплики, и отправляет вызов `Scale` в `Deployment`.

## Подводные камни

1. Отсутствие `resources.requests.cpu`: HPA не сможет рассчитать процент утилизации и перейдет в статус `<unknown>`, масштабирование работать не будет.
2. Флаппинг (Flapping / Thrashed Scaling): резкое скачкообразное масштабирование вверх-вниз при импульсной нагрузке. Требуется настройка `behavior.scaleDown.stabilizationWindowSeconds: 300`.
3. Конфликт с ручным `kubectl scale`: HPA автоматически перезапишет ручные изменения числа реплик.

## На собеседовании

**Вопрос с собеседования:** Почему автомасштабирование по утилизации памяти (Memory Utilization) в Go сервисах работает значительно хуже, чем по CPU?
**Ответ:** В Go рантайм использует сборщик мусора (GC) и собственный аллокатор памяти (tcmalloc-like mcache/mcentral/mheap). 
Когда сервис освобождает объекты в куче, рантайм Go не возвращает страницы памяти операционной системе немедленно (`scavenger` возвращает память медленно через `madvise(MADV_DONTNEED)`). В результате RSS процесса в cgroups остается высоким даже после спада трафика, и HPA не может своевременно отмасштабировать поды вниз (Scale Down). Поэтому в BigTech масштабируют по **CPU, RPS или лагу очередей**.
