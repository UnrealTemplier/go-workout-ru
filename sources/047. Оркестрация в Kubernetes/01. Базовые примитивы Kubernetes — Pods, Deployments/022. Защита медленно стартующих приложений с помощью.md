# Защита медленно стартующих приложений с помощью Startup Probe

## Условие

Используйте **Startup probe** для медленно стартующих приложений (долгие миграции, прогрев кэша).

## Теория

Некоторые приложения требуют длительного времени на запуск (прогрев тяжелых ML-моделей, загрузка многогигабайтных справочников в память, проверка целостности БД).

Если использовать только `livenessProbe` с большим `initialDelaySeconds: 300`:
- Если приложение зависнет в рантайме после старта, Kubelet будет ждать те же 300 секунд перед первой проверкой.

Решение — **`startupProbe`**:
- Действует исключительно на этапе старта контейнера.
- **Полностью отключает** выполнение Liveness и Readiness проб до тех пор, пока сама не завершится успехом (`200 OK`).
- Позволяет выделить приложению до 5–10 минут на инициализацию без риска быть убитым Kubelet.

## Решение по шагам

1. Реализуйте в Go эндпоинт `/startup` с проверкой прогрева кэша.
2. В `deployment.yaml` настройте `startupProbe: failureThreshold: 30, periodSeconds: 10` (максимум \(30 \times 10 = 300\) секунд).
3. Настройте строгую `livenessProbe: periodSeconds: 5, failureThreshold: 2`.
4. Разверните сервис и убедитесь, что Kubelet не перезапускает контейнер во время долгой инициализации.

## Код решения

**`startup-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: slow-startup-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: slow-app
  template:
    metadata:
      labels:
        app: slow-app
    spec:
      containers:
        - name: app
          image: ghcr.io/company/slow-app:v1.0.0
          ports:
            - containerPort: 8080
          # Выделяем до 300 секунд (30 * 10с) на холодный старт
          startupProbe:
            httpGet:
              path: /startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 10
          # После успеха startupProbe включается строгая liveness-проверка
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync/atomic"
	"time"
)

var isWarmedUp atomic.Bool

func main() {
	// Симуляция тяжелого прогрева кэша (45 секунд)
	go func() {
		fmt.Println("Начало прогрева локального кэша и загрузки справочников...")
		time.Sleep(45 * time.Second)
		isWarmedUp.Store(true)
		fmt.Println("Прогрев завершен! Приложение готово к работе.")
	}()

	http.HandleFunc("/startup", func(w http.ResponseWriter, r *http.Request) {
		if !isWarmedUp.Load() {
			w.WriteHeader(http.StatusServiceUnavailable)
			_, _ = w.Write([]byte("WARMING_UP"))
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("STARTED"))
	})

	http.HandleFunc("/live", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ALIVE"))
	})

	fmt.Println("Сервер слушает на :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Kubelet держит флаг `startupComplete = false`. Пока этот флаг ложен, вызовы liveness и readiness проб блокируются. 

Как только эндпоинт `/startup` возвращает первый успешный ответ `200 OK`, Kubelet навсегда переводит `startupComplete = true` для данного контейнера и переключается на стандартный цикл liveness/readiness проб.

## Подводные камни

1. Заниженный `failureThreshold`: если прогрев занял 46 секунд, а лимит был рассчитан на 40 секунд, Kubelet убьет контейнер прямо перед финишем инициализации.
2. Проверка базы данных в `startupProbe`: если упадет БД, под вообще никогда не выйдет из стадии старта и упадет.
3. Отсутствие таймаутов на HTTP клиентах при обращении к внешним ресурсам во время прогрева.

## На собеседовании

**Вопрос с собеседования:** В чем ключевое архитектурное преимущество связки `startupProbe + livenessProbe` перед использованием одного только `livenessProbe` с большим `initialDelaySeconds`?
**Ответ:** Если использовать только `livenessProbe` с `initialDelaySeconds: 300s`, то в случае зависания (deadlock) приложения на 30-й секунде Kubelet не заметит проблему еще 270 секунд. 
Связка со `startupProbe` решает обе задачи: она дает контейнеру до 300 секунд на старт, но как только контейнер запустился (например, за 15 секунд), startupProbe завершается и **моментально активирует быстрый liveness-мониторинг** (каждые 5 секунд), обеспечивая реакцию на аварии за считанные секунды.
