# Конфигурация через ConfigMap и Secret: внешняя настройка и переменные окружения

## Условие

**Конфигурация через ConfigMap и Secrets**: Не храните пароли и адреса БД в кодовой базе. Напишите манифесты `ConfigMap` (для хранения адреса СУБД) и `Secret` (для хранения пароля к базе в зашифрованном Base64 виде). Настройте манифест `deployment.yaml` так, чтобы эти данные автоматически пробрасывались в контейнер с Go в виде переменных окружения.

## Теория

Принцип 12-Factor App требует строгого разделения конфигурации и исходного кода приложения. В Kubernetes для этого используются:
1. **`ConfigMap`:** Хранилище неконфиденциальных параметров (URL внешних сервисов, уровень логирования, порт).
2. **`Secret`:** Хранилище чувствительных данных (пароли к БД, API-токены, TLS-сертификаты). Данные кодируются в Base64 (тип `Opaque`) или задаются открытым текстом в поле `stringData`.

В манифесте `Deployment` переменные пробрасываются в контейнер:
- Через `env` и `valueFrom: configMapKeyRef / secretKeyRef` для выборочных ключей.
- Через `envFrom: [configMapRef, secretRef]` для массового импорта всех пар ключ-значение.

## Решение по шагам

1. Создайте `configmap.yaml` с параметрами `DATABASE_HOST` и `LOG_LEVEL`.
2. Создайте `secret.yaml` с паролем `DATABASE_PASSWORD` через `stringData`.
3. В `deployment.yaml` подключите их через `envFrom` или `valueFrom`.
4. В коде Go прочитайте переменные через `os.Getenv()`.
5. Примените манифесты и убедитесь в логах пода, что конфигурация прочитана успешно.

## Код решения

**`configmap.yaml`**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "postgres.production.svc.cluster.local"
  DB_PORT: "5432"
  LOG_LEVEL: "info" 
```

**`secret.yaml`**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  DB_USER: "postgres_user"
  DB_PASSWORD: "SuperSecurePassword2026!" 
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend-app
  template:
    metadata:
      labels:
        app: backend-app
    spec:
      containers:
        - name: app
          image: ghcr.io/company/backend:v1.0.0
          envFrom:
            - configMapRef:
                name: app-config
            - secretRef:
                name: app-secret
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	dbHost := os.Getenv("DB_HOST")
	dbPort := os.Getenv("DB_PORT")
	dbUser := os.Getenv("DB_USER")
	dbPass := os.Getenv("DB_PASSWORD")
	logLevel := os.Getenv("LOG_LEVEL")

	fmt.Printf("Инициализация сервиса: Host=%s:%s, User=%s, LogLevel=%s\n", dbHost, dbPort, dbUser, logLevel)
	if dbPass == "" {
		fmt.Println("ВНИМАНИЕ: Пароль БД отсутствует!")
	} else {
		fmt.Println("Секретный пароль успешно загружен из Secret.")
	}

	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("OK"))
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

При старте пода Kubelet обращается к API-серверу K8s, запрашивает объекты `ConfigMap` и `Secret` и передает их в виде массива `env[]` в CRI (Container Runtime Interface — containerd). 

`containerd` запускает процесс с этими переменными окружения в его виртуальном пространстве процесса `/proc/$PID/environ`.

## Подводные камни

1. Иллюзия безопасности Base64: стандартный `Secret` в Kubernetes не зашифрован, Base64 — это лишь метод кодирования бинарных данных в строку. В etcd секреты должны шифроваться через KMS (Encryption at Rest).
2. Обновление переменных: если изменить ConfigMap в кластере, значения переменных окружения в уже запущенных подах **не обновятся** без перезапуска подов (`kubectl rollout restart`).
3. Забытый namespace: ConfigMap и Secret должны находиться в том же namespace, что и Deployment.

## На собеседовании

**Вопрос с собеседования:** Почему в enterprise Kubernetes-инфраструктуре запрещено хранить боевые пароли в стандартных K8s Secret, и как организуют интеграцию с HashiCorp Vault?
**Ответ:** Стандартные K8s Secret хранятся в Etcd и часто случайно утекают в git-манифесты или логи. В BigTech используют оператор **External Secrets Operator (ESO)** или **Vault Secrets Operator (VSO)**. 
Приложение декларирует ресурс `ExternalSecret`, контроллер которого по безопасной mTLS/OIDC аутентификации запрашивает секреты напрямую из защищенного хранилища HashiCorp Vault или Cloud KMS, создавая синхронизированные временные K8s Secret в памяти ноды с автоматической ротацией ключей.
