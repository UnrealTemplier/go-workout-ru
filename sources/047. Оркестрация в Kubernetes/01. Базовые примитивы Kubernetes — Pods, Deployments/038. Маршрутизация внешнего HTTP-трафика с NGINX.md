# Маршрутизация внешнего HTTP-трафика с NGINX Ingress Controller

## Условие

**[Ingress]**: Настрой `Ingress` (с использованием NGINX Ingress Controller), чтобы маршрутизировать HTTP-трафик с локального хоста на твой `Service`.

## Теория

В то время как `Service` балансирует трафик на транспортном уровне (L4 TCP), **`Ingress`** управляет входящим трафиком на прикладном уровне (L7 HTTP/HTTPS):
- Маршрутизация по доменным именам (Virtual Hosting: `api.example.com` vs `auth.example.com`).
- Маршрутизация по путям URL (`/orders`, `/users`).
- Терминация SSL/TLS сертификатов в единой точке.
- Интеграция с Ingress-контроллером (NGINX Ingress Controller, Traefik, HAProxy), который динамически обновляет конфигурацию обратного прокси.

## Решение по шагам

1. Убедитесь, что в кластере запущен NGINX Ingress Controller.
2. Создайте `ingress.yaml` с `ingressClassName: nginx`.
3. Опишите правило маршрутизации хоста `api.local` на сервис `backend-service:80`.
4. Примените манифест: `kubectl apply -f ingress.yaml`.
5. Выполните запрос с заголовком Host: `curl -H "Host: api.local" http://<ingress-ip>`.

## Код решения

**`ingress.yaml`**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
spec:
  ingressClassName: nginx
  rules:
    - host: api.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 80
```

**`service-backend.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  type: ClusterIP
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
```

**`test-ingress.sh`**

```bash
# Просмотр адреса Ingress
kubectl get ingress app-ingress

# Тестовый вызов с эмуляцией DNS хоста api.local
curl -v -H "Host: api.local" http://localhost/
```

## Под капотом

NGINX Ingress Controller работает как Pod в кластере. Контроллер слушает изменения ресурсов `Ingress` через K8s API. 

При появлении манифеста контроллер рендерит конфигурационный файл `/etc/nginx/nginx.conf` и выполняет команду `nginx -s reload` (или динамически обновляет апстримы через Lua-модуль без сброса соединений). Входящий трафик от клиентов направляется напрямую на IP-адреса подов, минуя kube-proxy.

## Подводные камни

1. Забытый `ingressClassName: nginx`: в современных версиях K8s без явного класса Ingress будет проигнорирован контроллером.
2. Ошибки с `rewrite-target`: регулярные выражения в путях могут привести к неожиданной перезаписи URL запросов к бэкенду.
3. Отсутствие Ingress-контроллера в кластере: сам по себе манифест `Ingress` является лишь декларацией; без запущенного контроллера трафик маршрутизироваться не будет.

## На собеседовании

**Вопрос с собеседования:** В чем эволюционная разница между классическим `Ingress` и современным стандартом `Gateway API` в Kubernetes?
**Ответ:** Классический `Ingress` — монолитный ресурс, смешивающий в одном YAML ответственность сетевого администратора (домены, TLS, провайдеры) и продуктового разработчика (пути маршрутизации). Кроме того, расширенные настройки (rate limiting, header rewrite) требовали вендор-специфичных аннотаций (`nginx.ingress...`), несовместимых между контроллерами. 
**Gateway API** разделяет роли через независимые ресурсы:
- `GatewayClass` (инфраструктурная платформа),
- `Gateway` (сетевые инженеры: слушатели, TLS, IP),
- `HTTPRoute` / `GRPCRoute` (разработчики сервисов: маршрутизация путей и канареечные веса), обеспечивая строгий ролевой доступ (RBAC) и нативную переносимость между любыми провайдерами.
