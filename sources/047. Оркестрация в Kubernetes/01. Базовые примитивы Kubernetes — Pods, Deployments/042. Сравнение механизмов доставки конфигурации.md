# Сравнение механизмов доставки конфигурации: Env Vars против Mounted Volumes

## Условие

Изучите разницу между env vars и mounted volumes для ConfigMap/Secret (первый не обновляется без restart, второй — обновляется).

## Теория

Критическое архитектурное сравнение двух подходов монтирования ConfigMap и Secret:
1. **Переменные окружения (`env` / `envFrom`):**
   - **Плюсы:** Мгновенный и нативный доступ в Go через `os.Getenv()`, отсутствие операций с диском.
   - **Минусы:** **Статичность**. При изменении ConfigMap в кластере переменные окружения запущенного процесса Linux обновиться не могут. Требуется полный перезапуск подов (`kubectl rollout restart`).
2. **Монтирование в том (`volumes` + `volumeMounts`):**
   - **Плюсы:** **Динамичность**. Kubelet автоматически обновляет файлы в директории пода в течение 60 секунд после правки ConfigMap в кластере без рестарта процесса.
   - **Минусы:** Требуется логика чтения файла или подписка на файловые события (`fsnotify`) в коде Go.

## Решение по шагам

1. Создайте ConfigMap с параметром `FEATURE_ENABLED: "false"`.
2. Создайте второй ключ с файлом конфигурации `features.json`.
3. Подключите первый ключ через `env`, а второй — через `volumeMounts: mountPath: /app/config`.
4. Измените оба значения в кластере через `kubectl edit configmap`.
5. Сравните вывод: переменная окружения осталась старой, а смонтированный файл обновился!

## Код решения

**`comparison-pod.yaml`**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-compare
spec:
  volumes:
    - name: config-vol
      configMap:
        name: test-cfg
  containers:
    - name: app
      image: alpine:3.21
      command: ["/bin/sh", "-c"]
      args:
        - |
          while true; do
            echo "ENV VAR: $MY_ENV_FLAG"
            echo "VOLUME FILE: $(cat /app/config/features.json 2>/dev/null)"
            sleep 15
          done
      env:
        - name: MY_ENV_FLAG
          valueFrom:
            configMapKeyRef:
              name: test-cfg
              key: FEATURE_FLAG
      volumeMounts:
        - name: config-vol
          mountPath: /app/config
```

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"time"
)

func main() {
	envVal := os.Getenv("MY_ENV_FLAG")
	filePath := "/app/config/features.json"

	for {
		fileContent, err := os.ReadFile(filePath)
		if err != nil {
			fileContent = []byte("ошибка чтения")
		}
		fmt.Printf("[%s] Env: %s | File: %s\n",
			time.Now().Format("15:04:05"), envVal, string(fileContent))
		time.Sleep(15 * time.Second)
	}
}
```

## Под капотом

Переменные окружения процесса в Linux записываются в область стека процесса при вызове `execve` и не могут быть модифицированы извне ядром без ведома процесса. 

Для файлов в томе Kubelet периодически синхронизирует локальное состояние ConfigMap, создавая новую директорию и атомарно переключая символическую ссылку через `rename()`. Это делает чтение файла всегда консистентным.

## Подводные камни

1. Ожидание, что `os.Getenv` волшебным образом обновится при изменении ConfigMap в K8s: одна из самых частых ошибок начинающих Go-разработчиков.
2. Использование `subPath`: при монтировании конкретного файла через `subPath` механизм симлинков отключается, и файл на диске также перестает обновляться!
3. Кэширование файла в коде: если вы прочитали файл один раз в функции `init()`, динамическое обновление на диске никак не повлияет на переменную в памяти Go.

## На собеседовании

**Вопрос с собеседования:** Если монтирование тома ConfigMap поддерживает автоматическое обновление файлов, почему многие команды все равно предпочитают переменные окружения и `kubectl rollout restart`?
**Ответ:** 
1. **Детерминизм и версионирование:** При `rollout restart` обновление происходит плавно по стратегии RollingUpdate с контролем готовности подов и возможностью мгновенного отката (`rollout undo`).
2. **Проблема рассинхронизации (In-flight Drift):** При обновлении файла на лету Kubelet обновляет ноды асинхронно с задержкой до 1 минуты. В этот период разные реплики сервиса работают с разными версиями конфигурации, что может приводить к трудноуловимым багам в распределенной бизнес-логике.
