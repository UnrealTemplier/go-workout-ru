# Самоисцеление (Self-Healing) и декларативное состояние в Deployment

## Условие

Создайте **Deployment** с 3 репликами. Изучите, как K8s поддерживает желаемое состояние.

## Теория

Центральная концепция Kubernetes — **Reconciliation Loop (Цикл сверки)**:
- Система непрерывно сравнивает **Желаемое состояние (Desired State)**, описанное в манифесте (`replicas: 3`), с **Текущим состоянием (Current / Live State)** в кластере.
- Если разработчик вручную удалит под (`kubectl delete pod ...`) или физическая нода выйдет из строя, `ReplicaSetController` мгновенно обнаружит, что текущее число подов стало равным 2 вместо 3, и автоматически создаст новый под на исправной ноде.
- Это гарантирует отказоустойчивость (Self-healing) и доступность сервиса без участия дежурных инженеров.

## Решение по шагам

1. Создайте `deployment.yaml` с 3 репликами.
2. Примените манифест и убедитесь в наличии 3 работающих подов.
3. Симулируйте аварию: принудительно удалите один из подов через `kubectl delete pod <name>`.
4. Наблюдайте в реальном времени, как контроллер создает новый под взамен удаленного.
5. Проверьте события через `kubectl get events --sort-by=.metadata.creationTimestamp`.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: resilient-service
  labels:
    app: resilient
spec:
  replicas: 3
  selector:
    matchLabels:
      app: resilient
  template:
    metadata:
      labels:
        app: resilient
    spec:
      containers:
        - name: app
          image: alpine:3.21
          command: ["/bin/sh", "-c", "sleep 3600"]
```

**`demo-self-heal.sh`**

```bash
# 1. Запуск деплоймента
kubectl apply -f deployment.yaml

# 2. Получение списка подов
kubectl get pods -l app=resilient

# 3. Принудительное удаление одного пода
POD_TO_KILL=$(kubectl get pods -l app=resilient -o jsonpath='{.items[0].metadata.name}')
echo "Удаляем под: $POD_TO_KILL"
kubectl delete pod $POD_TO_KILL

# 4. Проверка: K8s моментально создал новый под взамен!
kubectl get pods -l app=resilient
```

## Под капотом

`ReplicaSetController` слушает события API-сервера через механизм HTTP/2 Watch API. 

При получении события `DELETED` для пода, входящего в селектор контроллера, функция `syncReplicaSet()` вычисляет разницу:
`diff = desiredReplicas - currentReplicas`
Если `diff > 0`, контроллер немедленно отправляет вызов `POST /api/v1/namespaces/default/pods`, инициируя создание нового пода.

## Подводные камни

1. Попытка восстановить упавший под вручную: не требуется, контроллер сделает это автоматически быстрее человека.
2. Нехватка ресурсов на нодах (Pending pod): контроллер создаст под в etcd, но планировщик `kube-scheduler` не сможет назначить его на ноду из-за нехватки CPU/памяти.
3. Ошибки в `restartPolicy`: для контроллеров `Deployment` допустима только политика `restartPolicy: Always`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `Edge-triggered` и `Level-triggered` моделями управления в распределенных системах, и почему Kubernetes построен на Level-triggered подходе?
**Ответ:** 
- **Edge-triggered:** Реакция происходит строго на факт изменения (дельта-событие: «под удален»). Если в сети произошел сбой или брокер сообщений потерял пакет события, система навсегда останется в рассинхронизированном состоянии.
- **Level-triggered:** Контроллер оперирует абсолютным текущим состоянием (уровень: «в системе сейчас 2 пода, а нужно 3»). Даже если сотни событий были потеряны при сбое сети, на следующем цикле сверки контроллер сравнит желаемое число с реальным и устранит разрыв. Это делает Kubernetes предельно устойчивым к сетевым сбоям.
