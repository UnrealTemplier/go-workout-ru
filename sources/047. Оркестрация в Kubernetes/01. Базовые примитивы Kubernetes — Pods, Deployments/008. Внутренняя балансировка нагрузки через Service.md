# Внутренняя балансировка нагрузки через Service (ClusterIP)

## Условие

Напиши **Service manifest**: `kind: Service`, `type: ClusterIP`, `selector: app: myapp`, `ports: - port: 80, targetPort: 8080`. Покажи internal load balancing между pods.

## Теория

Каждый Pod в Kubernetes имеет собственный IP-адрес. Однако этот IP эфемерный: при падении пода, рестарте ноды или деплое новой версии создаются новые поды с совершенно новыми IP.

Ресурс **`Service` типа `ClusterIP`**:
- Выделяет стабильный внутренний IP-адрес (`ClusterIP`) и DNS-имя в пространстве `cluster.local`.
- Непрерывно отслеживает поды с помощью селектора `app: myapp`.
- Выполняет внутреннюю балансировку нагрузки между подами на транспортном уровне (L4 TCP/UDP).
- Другие микросервисы в кластере обращаются к сервису по стабильному DNS-имени: `http://myapp-service:80`.

## Решение по шагам

1. Создайте манифест `service.yaml` с `type: ClusterIP`.
2. Направьте входящий трафик с `port: 80` на `targetPort: 8080`.
3. Примените манифест: `kubectl apply -f service.yaml`.
4. Проверьте созданный объект Endpoints: `kubectl get endpoints myapp-service`.
5. Выполните запрос из временного контейнера: `kubectl run test --rm -it --image=alpine -- wget -qO- http://myapp-service`.

## Код решения

**`service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
  labels:
    app: myapp
spec:
  type: ClusterIP
  selector:
    app: myapp
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 8080
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	podName, _ := os.Hostname()
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Запрос обработан репликой: %s\n", podName)
	})

	fmt.Println("Микросервис ожидает запросы на :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`test-lb.sh`**

```bash
# Проверка балансировки: запросы распределяются между разными репликами
for i in $(seq 1 5); do
  curl -s http://myapp-service
done
```

## Под капотом

Virtual IP (`ClusterIP`) физически не существует на сетевых интерфейсах хоста. CoreDNS кластера сопоставляет имя `myapp-service.default.svc.cluster.local` с этим виртуальным IP. 

Когда пакет отправляется на ClusterIP, сетевой стек ядра хоста перехватывает его через правила DNAT (Destination NAT), сгенерированные `kube-proxy` в таблице `iptables` (цепочка `KUBE-SERVICES` -> `KUBE-SVC-XXX` -> `KUBE-SEP-XXX`). Ядро случайным образом подменяет ClusterIP на реальный IP одного из подов.

## Подводные камни

1. Сервис балансирует только на уровне TCP-соединений (L4): при постоянном HTTP/2 или gRPC соединении все запросы пойдут в один и тот же под. Для балансировки gRPC требуется Service Mesh или L7 Ingress.
2. Трафик идет на не готовые поды: если не настроена `readinessProbe`, трафик начнет поступать на под до инициализации приложения.
3. Опечатка в `targetPort`: сервис вернет ошибку таймаута или сброс соединения.

## На собеседовании

**Вопрос с собеседования:** Почему gRPC трафик плохо балансируется стандартным Kubernetes Service (ClusterIP) и как решается эта проблема?
**Ответ:** gRPC работает поверх протокола HTTP/2, который мультиплексирует сотни RPC-запросов внутри **одного долгоживущего TCP-соединения**. Kube-proxy балансирует на уровне L4 (TCP сокетов): он открывает одно соединение к одному поду, и все последующие тысячи gRPC-запросов уходят в этот единственный под, перегружая его. 
Решения:
1. **Client-side load balancing:** Использование Headless Service (`clusterIP: None`) и резолвера DNS в Go gRPC клиенте (`grpc.Dial("dns:///service:50051")`).
2. **L7 Проксирование:** Использование Service Mesh (Envoy/Istio) или Envoy Ingress, балансирующего каждый отдельный gRPC-вызов (L7 stream).
