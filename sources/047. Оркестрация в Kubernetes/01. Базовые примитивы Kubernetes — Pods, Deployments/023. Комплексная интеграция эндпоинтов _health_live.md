# Комплексная интеграция эндпоинтов /health/live и /health/ready в Deployment

## Условие

Добавьте `readinessProbe` и `livenessProbe` в Deployment: проверяйте HTTP-эндпоинты `/health/ready` и `/health/live`.

## Теория

Стандартизация диагностических эндпоинтов в enterprise-архитектуре микросервисов:
- `/health/live`: минималистичная проверка живости HTTP-рантайма Go.
- `/health/ready`: комплексная проверка готовности сервиса (пул БД, соединение с брокером сообщений, доступность кэша).

В манифесте `Deployment` пробы настраиваются с разделением частоты опроса: readiness опрашивается чаще (`periodSeconds: 3`), так как своевременное снятие с балансировки критично для минимизации клиентских ошибок, а liveness опрашивается реже (`periodSeconds: 10`).

## Решение по шагам

1. Настройте мультиплексор `http.ServeMux` с маршрутами `/health/live` и `/health/ready`.
2. В `deployment.yaml` сконфигурируйте секции `readinessProbe` и `livenessProbe`.
3. Укажите параметры `timeoutSeconds: 2`, `failureThreshold: 3`.
4. Разверните сервис в тестовом кластере.
5. Проинспектируйте выполнение проб через `kubectl describe pod`.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-gateway
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api-gateway
  template:
    metadata:
      labels:
        app: api-gateway
    spec:
      containers:
        - name: gateway
          image: ghcr.io/company/gateway:v1.0.0
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 2
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 3
            timeoutSeconds: 1
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	mux := http.NewServeMux()

	mux.HandleFunc("/health/live", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"UP"}`))
	})

	mux.HandleFunc("/health/ready", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"status":"READY","database":"connected"}`))
	})

	mux.HandleFunc("/api/v1/data", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte(`{"message":"Enterprise API Data"}`))
	})

	fmt.Println("API Gateway слушает порт :8080")
	_ = http.ListenAndServe(":8080", mux)
}
```

## Под капотом

Kubelet использует свой внутренний пул горутин для параллельного опроса сотен подов на ноде. 

При получении ответа от `/health/ready` Kubelet анализирует статус-код. Значение 200 OK переводит под в состояние `EndpointsReady`. Изменения сериализуются в Protobuf и передаются в K8s API Server через gRPC-соединение Kubelet.

## Подводные камни

1. Логирование каждого вызова пробы в общий лог сервиса: при 100 подах опрос каждые 3 секунды генерирует миллионы бесполезных строк логов в Elasticsearch/Loki. Запросы проб следует исключать из логов доступа.
2. Блокирующий вызов без таймаута внутри handler readiness: зависание горутины при падении БД.
3. Отсутствие заголовка `Content-Type` или закрытия `r.Body`.

## На собеседовании

**Вопрос с собеседования:** Почему в логах доступа (Access Logs) сервиса в K8s рекомендуется фильтровать запросы от `User-Agent: kube-probe/...`?
**Ответ:** Запросы диагностических проб Kubelet (`kube-probe/1.31`) выполняются непрерывно (каждые несколько секунд на каждую реплику). Если записывать их в общие access-логи, они составляют до 80–90% от общего объема логов сервиса. Это приводит к раздуванию индексов в ElasticSearch/ClickHouse/Loki, росту затрат на хранение и затрудняет поиск реальных клиентских запросов инженерами при расследовании инцидентов.
