# Интеграция CI конвейера с контролем качества и публикацией в Docker Hub

## Условие

Настройте GitHub Actions (или GitLab CI): пайплайн запускает линтер (`golangci-lint`), тесты с race detector, сборку образа и пуш в Docker Hub при пуше в main.

## Теория

Автоматизация Continuous Integration (CI) гарантирует, что каждый коммит в репозиторий проходит строгий аудит качества перед доставкой в кластер Kubernetes.

Ключевые этапы пайплайна:
1. **Static Analysis:** Проверка стиля, ошибок и уязвимостей через `golangci-lint`.
2. **Race Detection & Testing:** Исполнение юнит-тестов с флагом `-race` для детекции гонок данных в горутинах.
3. **Container Build & Publish:** Сборка OCI-образа через Docker Buildx и безопасная аутентификация в Docker Hub по токенам репозитория (`DOCKER_USER`, `DOCKER_PAT`).

## Решение по шагам

1. Создайте workflow `.github/workflows/ci.yml`.
2. Настройте триггер на событие `push` в ветку `main`.
3. Настройте джобы `lint-and-test` и `build-and-push`.
4. Сконфигурируйте авторизацию в Docker Hub через секреты репозитория.
5. Проверьте зеленый статус выполнения пайплайна.

## Код решения

**`.github/workflows/ci.yml`**

```yaml
name: K8s Service CI

on:
  push:
    branches: [ main ]

jobs:
  lint-and-test:
    name: Code Quality Gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.24'
          cache: true
      - name: Run Linter
        uses: golangci/golangci-lint-action@v6
        with:
          version: v1.64.5
      - name: Run Tests with Race Detector
        run: go test -v -race -cover ./...

  docker:
    name: Build & Push Image
    needs: lint-and-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: Build and Push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/k8s-service:${{ github.sha }}
            ${{ secrets.DOCKERHUB_USERNAME }}/k8s-service:latest
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

func Add(a, b int) int {
	return a + b
}

func main() {
	http.HandleFunc("/add", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "Result: %d\n", Add(2, 3))
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

**`main_test.go`**

```go
package main

import "testing"

func TestAdd(t *testing.T) {
	if got := Add(2, 3); got != 5 {
		t.Fatalf("Add(2, 3) = %d; want 5", got)
	}
}
```

## Под капотом

Связка `needs: [lint-and-test]` гарантирует, что джоба сборки контейнера не стартует при наличии ошибок в тестах или коде. 

При вызове `docker/build-push-action` экшен передает дайджест коммита в переменные тегов. В реестре формируется OCI-манифест, на который K8s ссылается в спецификации `Deployment`.

## Подводные камни

1. Запуск сборки контейнера параллельно с тестами: тратит ресурсы раннеров на публикацию заведомо нерабочего образа.
2. Хранение паролей в открытом коде репозитория вместо GitHub Secrets.
3. Отсутствие флага `-race` в тестах CI: скрытые многопоточные гонки пройдут в production.

## На собеседовании

**Вопрос с собеседования:** Почему в production Kubernetes-манифестах нельзя использовать тег `:latest`, сформированный CI?
**Ответ:** Тег `:latest` мутабелен. Если кластер выполняет пересоздание пода на новой ноде, Kubelet при `imagePullPolicy: IfNotPresent` может запустить старую версию с локального кэша ноды, а соседняя нода скачает новую версию. В результате в одном кластере одновременно работают разные версии сервиса. Использование детерминированного тега по Git SHA исключает расхождение версий.
