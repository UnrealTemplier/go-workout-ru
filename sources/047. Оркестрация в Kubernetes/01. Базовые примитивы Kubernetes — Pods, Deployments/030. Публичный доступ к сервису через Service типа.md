# Публичный доступ к сервису через Service типа LoadBalancer в облачной инфраструктуре

## Условие

Создайте **Service** типа LoadBalancer для production (в облаке создаст внешний LB).

## Теория

Для предоставления прямого сетевого доступа к сервису из публичного интернета без Ingress-контроллера используется **`Service` типа `LoadBalancer`**:
- Автоматически инициирует создание физического внешнего балансировщика в облачном провайдере (AWS Network Load Balancer, Google Cloud Network LB, Yandex Cloud NLB).
- Облачный балансировщик получает публичный статический IP-адрес (`External-IP`).
- Трафик перенаправляется с публичного IP через `NodePort` на ноды кластера, а затем через Kube-proxy — на поды приложения.

## Решение по шагам

1. Создайте манифест `service-lb.yaml` с `type: LoadBalancer`.
2. Добавьте аннотации облачного провайдера (например, для AWS NLB).
3. Примените манифест: `kubectl apply -f service-lb.yaml`.
4. Дождитесь выделения публичного адреса: `kubectl get svc web-lb -w`.
5. Выполните запрос к сервису по внешнему IP-адресу через браузер или curl.

## Код решения

**`service-lb.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-lb
  annotations:
    # Пример аннотации для создания Network Load Balancer в AWS:
    service.beta.kubernetes.io/aws-load-balancer-type: "external"
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: "ip"
spec:
  type: LoadBalancer
  selector:
    app: web-app
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 8080
```

**`check-lb.sh`**

```bash
# Ожидание выделения внешнего адреса облачным провайдером
kubectl get svc web-lb

# Пример вывода:
# NAME     TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)        AGE
# web-lb   LoadBalancer   10.96.120.45    51.250.10.89    80:31234/TCP   45s

# Проверка ответа через публичный IP
curl http://51.250.10.89
```

## Под капотом

Cloud Controller Manager (CCM) отслеживает события создания сервисов с типом `LoadBalancer`. 

CCM обращается к API облачного провайдера (через IAM-роль), заказывает создание балансировщика нагрузки, настраивает Target Group и health-check. После создания CCM записывает полученный публичный IP-адрес или DNS-имя в поле `status.loadBalancer.ingress` объекта Service.

## Подводные камни

1. Высокая стоимость: создание отдельного `Service LoadBalancer` на каждый из 100 микросервисов создаст 100 облачных балансировщиков, что приведет к огромным счетам за инфраструктуру. Вместо этого создают **один Ingress-контроллер** за одним LoadBalancer.
2. Потеря исходного IP клиента (Client IP Spoofing): при прохождении через NodePort происходит SNAT. Для сохранения реального IP требуется опция `externalTrafficPolicy: Local`.
3. Зависание в статусе `<pending>` на локальном Minikube/Kind без запуска `minikube tunnel`.

## На собеседовании

**Вопрос с собеседования:** Что делает опция `spec.externalTrafficPolicy: Local` в Kubernetes Service и какую скрытую проблему она несет?
**Ответ:** 
- **Плюсы:** `externalTrafficPolicy: Local` отключает второй сетевой прыжок (SNAT) между нодами кластера. Нода принимает входящий пакет и отправляет его **строго на под, запущенный на этой же физической ноде**. Это сохраняет реальный исходный IP-адрес клиента (`X-Forwarded-For` не нужен) и снижает задержку сети.
- **Минусы:** Возникает неравномерная балансировка нагрузки: если на Ноде А запущен 1 под, а на Ноде Б — 3 пода, внешний облачный балансировщик будет делить трафик 50/50 между двумя нодами. В результате под на Ноде А получит в 3 раза больше нагрузки, чем поды на Ноде Б!
