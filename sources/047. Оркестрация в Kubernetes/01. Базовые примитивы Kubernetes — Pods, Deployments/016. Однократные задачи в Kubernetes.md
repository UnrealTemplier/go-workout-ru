# Однократные задачи в Kubernetes: манифест Job для миграций базы данных

## Условие

Напиши **Job**: `kind: Job`, `template: spec: restartPolicy: OnFailure`, `containers: - command: ["./migrate", "up"]`. Запускается один раз, до completion. Покажи database migrations as K8s Job.

## Теория

В отличие от `Deployment`, поды которого обязаны работать непрерывно, задачи вроде миграций БД, генерации отчетов или бэкапов должны выполниться ровно один раз и завершиться с кодом 0.

Ресурс **`Job` (`apiVersion: batch/v1`)**:
- Создает один или несколько подов и следит за их успешным завершением (`Completed`).
- При падении (`Exit code != 0`) контроллер автоматически перезапускает под в соответствии с политикой `restartPolicy: OnFailure` или `Never`.
- `backoffLimit`: максимальное количество попыток перезапуска перед тем, как Job будет помечена как проваленная (`Failed`).
- Идеально подходит для применения миграций схемы БД (Liquibase, Goose, golang-migrate) перед стартом веб-серверов.

## Решение по шагам

1. Создайте код утилиты миграций на Go.
2. Опишите манифест `migration-job.yaml` с `kind: Job`.
3. Укажите `restartPolicy: OnFailure` и `backoffLimit: 3`.
4. Примените манифест: `kubectl apply -f migration-job.yaml`.
5. Дождитесь статуса `Completed`: `kubectl wait --for=condition=complete job/db-migration --timeout=60s`.

## Код решения

**`migration-job.yaml`**

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3
  ttlSecondsAfterFinished: 300 # Автоматическое удаление через 5 минут после завершения
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: ghcr.io/company/db-migrator:v1.0.0
          command: ["/bin/migrator", "up"]
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: db-secrets
                  key: DSN
```

**`migrator.go`**

```go
package main

import (
	"fmt"
	"os"
	"time"
)

func main() {
	dsn := os.Getenv("DATABASE_URL")
	if dsn == "" {
		fmt.Println("ОШИБКА: Переменная DATABASE_URL не задана")
		os.Exit(1)
	}

	fmt.Println("Начало применения миграций базы данных...")
	time.Sleep(2 * time.Second) // Имитация применения SQL DDL скриптов

	fmt.Println("Миграции схемы БД успешно применены!")
	os.Exit(0)
}
```

**`check-job.sh`**

```bash
# Запуск задачи
kubectl apply -f migration-job.yaml

# Просмотр статуса Job
kubectl get jobs

# Просмотр логов пода миграций
kubectl logs job/db-migration
```

## Под капотом

`JobController` создает Pod. Когда процесс в контейнере завершается с кодом 0 (`Exit Code 0`), Kubelet переводит статус пода в `Succeeded`. 

`JobController` фиксирует условие `Complete: True`. Опция `ttlSecondsAfterFinished: 300` задействует контроллер TTL-after-finished, который через 5 минут автоматически удаляет объект Job и его завершенные поды из etcd, предотвращая засорение кластера старыми записями.

## Подводные камни

1. Забытый `restartPolicy: OnFailure`: по умолчанию поды используют политику `Always`, что недопустимо для Job (K8s API отклонит манифест).
2. Запуск нескольких миграций параллельно: одновременный запуск двух реплик мигратора может заблокировать таблицы БД в дедлоке. Для Job требуется `completions: 1` и `parallelism: 1`.
3. Отсутствие `ttlSecondsAfterFinished`: тысячи завершенных подов накапливаются в etcd, перегружая память K8s master-нод.

## На собеседовании

**Вопрос с собеседования:** Как связать выполнение K8s Job миграций с развертыванием нового релиза в Helm-чарте или GitOps?
**Ответ:** Используются **Helm Hooks** (`helm.sh/hook: pre-install,pre-upgrade`, `helm.sh/hook-delete-policy: hook-succeeded`). 
Helm сначала применяет манифест Job миграции и ждет его успешного завершения (`Completed`). Только после успешного применения DDL-схемы Helm запускает обновление Deployment с новыми подами веб-сервера. Если миграция упала с ошибкой, Helm прерывает релиз и не обновляет рабочие поды, исключая поломку продакшна.
