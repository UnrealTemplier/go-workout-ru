# Экспонирование Deployment внутри кластера через Service (ClusterIP)

## Условие

Напиши `Service.yaml` (ClusterIP), чтобы暴露 (expose) деплоймент внутри кластера.

## Теория

Для организации взаимодействия между микросервисами (Service-to-Service Communication) используется абстракция `Service` типа `ClusterIP`.

Архитектура внутреннего взаимодействия:
- Микросервис `billing-service` обращается к сервису `auth-service`.
- Встроенный CoreDNS кластера автоматически преобразует имя сервиса в виртуальный ClusterIP.
- Виртуальный IP сопоставляется с активными репликами через Endpoints.
- Трафик балансируется прозрачно для вызывающего Go-клиента.

## Решение по шагам

1. Создайте `deployment.yaml` для сервиса авторизации.
2. Создайте `service.yaml` с `type: ClusterIP`.
3. Задайте `port: 80` и `targetPort: 8080`.
4. Примените манифесты.
5. Протестируйте сетевое подключение по DNS-имени сервиса.

## Код решения

**`auth-service.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: auth-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: auth-server
  template:
    metadata:
      labels:
        app: auth-server
    spec:
      containers:
        - name: auth
          image: ghcr.io/company/auth:v1.0.0
          ports:
            - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: auth-service
spec:
  type: ClusterIP
  selector:
    app: auth-server
  ports:
    - name: http
      port: 80
      targetPort: 8080
```

**`client.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"time"
)

func main() {
	client := &http.Client{Timeout: 3 * time.Second}

	// Обращение по внутреннему DNS-имени K8s Service:
	resp, err := client.Get("http://auth-service/verify")
	if err != nil {
		fmt.Printf("Ошибка обращения к сервису авторизации: %v\n", err)
		return
	}
	defer resp.Body.Close()

	body, _ := io.ReadAll(resp.Body)
	fmt.Printf("Ответ от auth-service: %s\n", string(body))
}
```

## Под капотом

Kubernetes создает запись типа A в CoreDNS: `auth-service.default.svc.cluster.local -> 10.96.12.34`. 

Когда Go-клиент выполняет `client.Get("http://auth-service/...")`, библиотека net в Go запрашивает `/etc/resolv.conf`, где указан DNS-сервер K8s (`10.96.0.10`) и суффиксы поиска (`search default.svc.cluster.local svc.cluster.local cluster.local`). CoreDNS возвращает IP сервиса за доли миллисекунды.

## Подводные камни

1. Попытка обратиться к поду по его IP-адресу вместо DNS сервиса: при перезапуске пода адрес изменится, и клиент начнет получать сетевые ошибки.
2. Большое количество суффиксов в `resolv.conf`: приводит к 3-4 избыточным DNS-запросам на каждый внешний хост.
3. Отсутствие таймаута в `http.Client`: зависание горутин при сетевых задержках в кластере.

## На собеседовании

**Вопрос с собеседования:** Что такое `ndots:5` в `/etc/resolv.conf` подов Kubernetes и почему это создает огромную нагрузку на CoreDNS?
**Ответ:** Директива `ndots:5` означает: если доменное имя содержит меньше 5 точек (например, `api.stripe.com` содержит 2 точки), resolver обязан сначала попытаться найти это имя по очереди во всех внутренних суффиксах поиска (`api.stripe.com.default.svc...`, `api.stripe.com.svc...` и т.д.). 
Только получив 3-4 ошибки NXDOMAIN, резолвер делает запрос во внешний интернет. В крупных кластерах это генерирует миллиарды бесполезных DNS-запросов. Решение: использование точки на конце внешних адресов (`api.stripe.com.`) или тюнинг `dnsConfig.options: ndots: 2`.
