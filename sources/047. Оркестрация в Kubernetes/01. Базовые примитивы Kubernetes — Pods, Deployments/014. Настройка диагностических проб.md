# Настройка диагностических проб: Liveness и Readiness Probes в веб-сервере Go

## Условие

**Настройка Liveness и Readiness Probes**: Интегрируйте в веб-сервер Go два диагностических эндпоинта:
* `/live` (Liveness) — возвращает статус `200 OK`, если приложение просто запущено и не зависло мертвой блокировкой.
* `/ready` (Readiness) — возвращает `200 OK` только тогда, когда приложение успешно установило соединение с БД и готово обрабатывать трафик пользователей.
Пропишите опрос этих эндпоинтов в K8s-манифесте пода в секциях `livenessProbe` и `readinessProbe`.

## Теория

Пробы (Probes) — механизм контроля жизнедеятельности подов со стороны Kubelet:
1. **`livenessProbe` (Проба живучести):** Проверяет, что процесс приложения жив и не заблокирован взаимной блокировкой (deadlock). Если эндпоинт `/live` не отвечает или возвращает статус \(\ge 400\), Kubelet **перезапускает контейнер**.
2. **`readinessProbe` (Проба готовности):** Проверяет, готово ли приложение обрабатывать трафик (успешно ли подключение к БД, прогрет ли кэш). Если эндпоинт `/ready` возвращает ошибку, под **не перезапускается**, но временно **удаляется из балансировщика Service (Endpoints)**, предотвращая ошибки у клиентов.

## Решение по шагам

1. Реализуйте в коде Go эндпоинты `/live` и `/ready`.
2. В эндпоинте `/ready` добавьте проверку доступности базы данных (ping).
3. В манифесте `deployment.yaml` сконфигурируйте секции `livenessProbe` и `readinessProbe`.
4. Задайте параметры: `initialDelaySeconds: 5`, `periodSeconds: 10`, `timeoutSeconds: 2`.
5. Примените манифест и проверьте пробы через `kubectl describe pod`.

## Код решения

**`probes-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: probe-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: probe-service
  template:
    metadata:
      labels:
        app: probe-service
    spec:
      containers:
        - name: app
          image: ghcr.io/company/probe-service:v1.0.0
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync/atomic"
)

var isDBConnected atomic.Bool

func main() {
	// Симуляция успешного подключения к БД через 3 секунды после старта
	go func() {
		isDBConnected.Store(true)
	}()

	// Liveness: проверяет только то, что HTTP-сервер отвечает
	http.HandleFunc("/live", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ALIVE"))
	})

	// Readiness: проверяет готовность обслуживать трафик (доступность БД)
	http.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
		if !isDBConnected.Load() {
			w.WriteHeader(http.StatusServiceUnavailable)
			_, _ = w.Write([]byte("DB_DISCONNECTED"))
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		_, _ = w.Write([]byte("Бизнес-логика микросервиса"))
	})

	fmt.Println("Сервер с диагностическими пробами слушает на :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Демон `kubelet` периодически отправляет HTTP GET-запросы на указанный порт пода. 

Если `livenessProbe` возвращает ошибку более `failureThreshold` раз подряд, Kubelet шлет процессу сигнал `SIGTERM`, ждет `terminationGracePeriodSeconds` (30 с по умолчанию) и, если процесс не завершился, убивает его через `SIGKILL`. 

Если `readinessProbe` возвращает статус `503`, контроллер EndpointSlice мгновенно вычеркивает IP пода из списка адресов балансировки `Service`.

## Подводные камни

1. Проверка внешних зависимостей (БД, сторонний API) в `livenessProbe`: если БД кратковременно упадет под нагрузкой, Kubelet начнет циклически убивать и перезапускать **все поды сервиса одновременно**, превращая мелкий сбой в катастрофу (Каскадный сбой / Cascading Failure). Проверка БД допустима **только в readinessProbe**!
2. Слишком короткий `timeoutSeconds: 1` при тяжелой нагрузке: Kubelet считает пробу проваленной из-за занятости CPU приложения.
3. Отсутствие `initialDelaySeconds`: Kubelet опрашивает под до завершения инициализации рантайма Go, вызывая ложные перезапуски.

## На собеседовании

**Вопрос с собеседования:** Почему проверка соединения с PostgreSQL в `livenessProbe` считается критическим антипаттерном в архитектуре Kubernetes?
**Ответ:** Цель `livenessProbe` — ответить на вопрос: «Жив ли сам процесс Go? Поможет ли ему перезапуск контейнера?». Если СУБД PostgreSQL упала или перегружена, перезапуск контейнера Go проблему с БД не решит, но создаст лавину повторных подключений к БД (Thundering Herd) и положит весь кластер. 
Внешние зависимости проверяются **исключительно в `readinessProbe`**: под помечается как «не готовый» и снимается с балансировки, но процесс спокойно ждет восстановления БД без бессмысленных панических рестартов.
