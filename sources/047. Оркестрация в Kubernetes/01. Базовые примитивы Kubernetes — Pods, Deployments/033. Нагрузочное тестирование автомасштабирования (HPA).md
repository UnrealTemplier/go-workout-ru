# Нагрузочное тестирование автомасштабирования (HPA) по CPU и памяти

## Условие

Настройте `HorizontalPodAutoscaler` по CPU и памяти, проверьте масштабирование нагрузочным тестом.

## Теория

Проверка работоспособности HPA перед выкаткой в продакшн обязательна:
- Нагрузочный генератор (`hey` или `k6`) генерирует непрерывный поток параллельных HTTP-запросов.
- Вычислительная нагрузка в Go-сервисе утилизирует CPU.
- Метрики `container_cpu_usage_seconds_total` растут.
- HPA фиксирует превышение целевого порога (например, 70%) и выполняет горизонтальное масштабирование реплик от 2 до 8.
- После прекращения нагрузки контроллер выдерживает стабилизационное окно (cooldown) и плавно сворачивает лишние реплики.

## Решение по шагам

1. Разверните сервис с установленным `requests.cpu: 100m`.
2. Создайте HPA с порогом 50% CPU.
3. Запустите генератор нагрузки `kubectl run load-generator --image=busybox -- sh -c "while true; do wget -q -O- http://my-service; done"`.
4. Наблюдайте за ростом нагрузки: `kubectl get hpa -w`.
5. Убедитесь, что число подов масштабируется с 2 до 6.

## Код решения

**`hpa-test.yaml`**

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: load-test-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: load-service
  minReplicas: 2
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
```

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"net/http"
)

func cpuHeavyHandler(w http.ResponseWriter, r *http.Request) {
	// Интенсивная нагрузка на CPU
	var x float64 = 0.0001
	for i := 0; i < 500000; i++ {
		x += math.Sqrt(x)
	}
	fmt.Fprintf(w, "OK: %f\n", x)
}

func main() {
	http.HandleFunc("/", cpuHeavyHandler)
	fmt.Println("Нагрузочный сервис слушает на :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`run-load.sh`**

```bash
# Мониторинг масштабирования в реальном времени
kubectl get hpa load-test-hpa -w

# В отдельном терминале: запуск 5 параллельных генераторов нагрузки
for i in $(seq 1 5); do
  kubectl run "generator-$i" --rm -i --tty --image=busybox -- /bin/sh -c "while true; do wget -q -O- http://load-service; done" &
done
```

## Под капотом

Metrics-server с интервалом в 15–30 секунд опрашивает cAdvisor на каждой ноде. 

HPA Controller вычисляет скользящее среднее утилизации. При скачке до 120% он отправляет PATCH-запрос в subresource `/scale` Deployment, обновляя поле `spec.replicas`. Новый ReplicaSet запускает поды, а Kubelet скачивает образ и стартует контейнеры.

## Подводные камни

1. Отсутствие установленного `metrics-server`: самая частая причина неработающего HPA в локальных кластерах.
2. Недостаток нод в кластере: поды переходят в статус `Pending`, так как ноды физически заполнены. Для автоматического добавления серверов требуется **Cluster Autoscaler** или **Karpenter**.
3. Слишком низкий порог (например, 20%): приводит к постоянному дерганию подов.

## На собеседовании

**Вопрос с собеседования:** В чем разница между HPA на уровне подов и Cluster Autoscaler / Karpenter на уровне инфраструктуры?
**Ответ:** 
- **HPA (Horizontal Pod Autoscaler)** работает **внутри кластера на уровне подов**: он увеличивает количество реплик Deployment, когда растет нагрузка.
- **Cluster Autoscaler / Karpenter** работает **на уровне облачной инфраструктуры**: когда новые поды от HPA не могут запуститься и зависают в статусе `Pending` из-за нехватки CPU на имеющихся серверах, Cluster Autoscaler заказывает у облачного провайдера (AWS/GCP/VK Cloud) новые виртуальные машины (Worker Nodes), расширяя физический размер кластера.
