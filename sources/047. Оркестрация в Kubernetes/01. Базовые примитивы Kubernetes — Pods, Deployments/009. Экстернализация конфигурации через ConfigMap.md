# Экстернализация конфигурации через ConfigMap и envFrom

## Условие

Напиши **ConfigMap**: `kind: ConfigMap`, `data: DATABASE_URL: postgres://...`, `LOG_LEVEL: info`. Подключи в pod: `envFrom: - configMapRef: name: app-config`. Покажи externalized configuration.

## Теория

Хардкод конфигураций (адреса брокеров, уровни логов, таймауты) в бинарнике нарушает гибкость эксплуатации. Контейнер должен оставаться одинаковым для dev, staging и production, меняться должна только конфигурация.

`ConfigMap`:
- Хранит пары ключ-значение в поле `data`.
- Директива `envFrom: - configMapRef: name: app-config` автоматически преобразует каждую запись `data` в переменную окружения контейнера с тем же именем.
- В коде Go параметры считываются через `os.Getenv` с возможностью задания значений по умолчанию.

## Решение по шагам

1. Создайте манифест `configmap.yaml` с параметрами `DATABASE_URL` и `LOG_LEVEL`.
2. Опишите `deployment.yaml` с `envFrom: - configMapRef: name: app-config`.
3. В коде Go напишите функцию чтения конфигурации с дефолтными значениями.
4. Примените манифесты: `kubectl apply -f configmap.yaml -f deployment.yaml`.
5. Проверьте логи пода: `kubectl logs -l app=config-demo`.

## Код решения

**`configmap.yaml`**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DATABASE_URL: "postgres://user:pass@pg-cluster.database.svc:5432/orders?sslmode=disable"
  LOG_LEVEL: "info"
  MAX_CONNECTIONS: "50" 
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: config-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: config-demo
  template:
    metadata:
      labels:
        app: config-demo
    spec:
      containers:
        - name: app
          image: ghcr.io/company/config-demo:v1.0.0
          envFrom:
            - configMapRef:
                name: app-config
```

**`config.go`**

```go
package main

import (
	"fmt"
	"os"
)

type Config struct {
	DatabaseURL string
	LogLevel    string
	MaxConns    string
}

func LoadConfig() Config {
	return Config{
		DatabaseURL: getEnv("DATABASE_URL", "postgres://localhost:5432/dev"),
		LogLevel:    getEnv("LOG_LEVEL", "debug"),
		MaxConns:    getEnv("MAX_CONNECTIONS", "10"),
	}
}

func getEnv(key, defaultVal string) string {
	if val := os.Getenv(key); val != "" {
		return val
	}
	return defaultVal
}

func main() {
	cfg := LoadConfig()
	fmt.Printf("Конфигурация успешно загружена:\n- DB: %s\n- LogLevel: %s\n- MaxConns: %s\n",
		cfg.DatabaseURL, cfg.LogLevel, cfg.MaxConns)
}
```

## Под капотом

При планировании пода Kubelet валидирует наличие указанного `ConfigMap` в namespace. Если ConfigMap не существует, под зависает в статусе `CreateContainerConfigError`. 

После успешной валидации Kubelet парсит словарь `data` и передает его в системную структуру создания контейнера. Имена ключей должны строго соответствовать формату C-идентификаторов (`[-._a-zA-Z][-._a-zA-Z0-9]*`).

## Подводные камни

1. Опечатка в имени ConfigMap: под упадет в `CreateContainerConfigError` и не запустится.
2. Недопустимые символы в ключах (например, слэш `/`): переменная окружения с некорректным именем будет отброшена операционной системой Linux.
3. Отсутствие fallback (значений по умолчанию) в коде Go: сервис падает с nil pointer или паникой, если переменная не задана в dev-окружении.

## На собеседовании

**Вопрос с собеседования:** В каких случаях передача параметров через переменные окружения (`envFrom`) хуже, чем монтирование ConfigMap в виде файла (`volumeMounts`)?
**Ответ:** 
1. **Динамическое обновление (Hot Reload):** Изменение ConfigMap, смонтированного как файл в том (volume), обновляется на файловой системе пода демоном Kubelet автоматически в течение 1 минуты. Переменные окружения процесса обновлены быть не могут (требуется полный рестарт пода).
2. **Сложные и структурированные конфигурации:** Большие конфигурационные файлы (JSON, YAML, Nginx config) неудобно и небезопасно передавать через переменные окружения из-за ограничений оболочки на размер командной строки и спецсимволы.
