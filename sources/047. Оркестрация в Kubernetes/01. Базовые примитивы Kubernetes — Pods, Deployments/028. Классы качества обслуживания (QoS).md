# Классы качества обслуживания (QoS): Guaranteed, Burstable и BestEffort

## Условие

Настрой **resource requests/limits**: `resources: requests: memory: "256Mi", cpu: "250m"`, `limits: memory: "512Mi", cpu: "500m"`. Покажи QoS classes: `Guaranteed` (requests=limits), `Burstable` (requests&lt;limits), `BestEffort` (none).

### Исходная формулировка

Настрой **resource requests/limits**: `resources: requests: memory: "256Mi", cpu: "250m"`, `limits: memory: "512Mi", cpu: "500m"`. Покажи QoS classes: `Guaranteed` (requests=limits), `Burstable` (requests&lt;limits), `BestEffort` (none).

## Теория

Kubernetes управляет распределением ресурсов через механизм **QoS (Quality of Service)**:
1. **`Guaranteed`:** У всех контейнеров пода заданы `requests` и `limits`, и они **строго равны** между собой как по CPU, так и по памяти (`requests.cpu == limits.cpu` и `requests.mem == limits.mem`). Наивысший приоритет, никогда не выселяются при дефиците памяти ноды.
2. **`Burstable`:** Заданы requests и limits, но `requests < limits`, либо заданы только requests. Могут временно утилизировать свободные мощности ноды («burst»).
3. **`BestEffort`:** Ни requests, ни limits не указаны. Низший приоритет, первыми уничтожаются OOM Killer при малейшей нехватке памяти на ноде.

## Решение по шагам

1. Создайте манифест с Guaranteed QoS: укажите одинаковые значения в `requests` и `limits`.
2. Создайте манифест с Burstable QoS: `requests.cpu: 250m, limits.cpu: 500m`.
3. Примените оба манифеста.
4. Проверьте присвоенный класс через `kubectl get pod <name> -o jsonpath='{.status.qosClass}'`.
5. Изучите приоритеты выселения подов при аварии.

## Код решения

**`qos-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: guaranteed-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: guaranteed
  template:
    metadata:
      labels:
        app: guaranteed
    spec:
      containers:
        - name: app
          image: alpine:3.21
          command: ["sleep", "3600"]
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "500m" # Равно requests -> Guaranteed QoS
              memory: "512Mi" # Равно requests -> Guaranteed QoS
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: burstable-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: burstable
  template:
    metadata:
      labels:
        app: burstable
    spec:
      containers:
        - name: app
          image: alpine:3.21
          command: ["sleep", "3600"]
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m" # Больше requests -> Burstable QoS
              memory: "512Mi" 
```

**`check-qos.sh`**

```bash
# Проверка QoS класса первого пода:
kubectl get pod -l app=guaranteed -o jsonpath='{.items[0].status.qosClass}'
# Вывод: Guaranteed

# Проверка QoS класса второго пода:
kubectl get pod -l app=burstable -o jsonpath='{.items[0].status.qosClass}'
# Вывод: Burstable
```

## Под капотом

Kubelet рассчитывает значение `oom_score_adj` для каждого контейнера в зависимости от QoS:
- Для **Guaranteed** подов: `oom_score_adj = -997` (ядро Linux защищает процесс от OOM Killer почти как системные демоны).
- Для **BestEffort** подов: `oom_score_adj = 1000` (максимальная вероятность быть убитым ядром).
- Для **Burstable** подов: динамический балл от 2 до 999 в зависимости от отношения потребления памяти к запрошенному request.

## Подводные камни

1. Использование BestEffort в production: любой случайный фоновый процесс на ноде может привести к немедленному уничтожению вашего пода.
2. Несоответствие requests и limits в одном из контейнеров мультиконтейнерного пода: весь под потеряет статус Guaranteed и станет Burstable.
3. Завышение requests для Guaranteed подов: ноды будут казаться заполненными на 100%, хотя реальное потребление ресурсов может быть низким (Over-provisioning).

## На собеседовании

**Вопрос с собеседования:** В каком порядке Kubelet выселяет (evicts) поды при наступлении события `NodeMemoryPressure` (дефицит памяти на ноде)?
**Ответ:** Kubelet выселяет поды строго по иерархии:
1. **BestEffort поды:** уничтожаются первыми, так как они не задекларировали никаких гарантий ресурсов.
2. **Burstable поды, превысившие свои `requests`:** выселяются следующими, при этом первыми идут те, у которых наибольшее превышение requests относительно лимита.
3. **Burstable поды в пределах `requests`:** выселяются только при продолжающемся дефиците.
4. **Guaranteed поды:** выселяются в самую последнюю очередь, только если на ноде исчерпаны все остальные поды и под угрозой стабильность системных компонентов Kubelet/OS.
