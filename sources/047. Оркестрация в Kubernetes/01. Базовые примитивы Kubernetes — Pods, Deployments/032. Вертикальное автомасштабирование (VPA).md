# Вертикальное автомасштабирование (VPA): режимы Auto и Recommendation Only

## Условие

Настрой **VerticalPodAutoscaler (VPA)**: `updateMode: "Auto"` или `"Off"` (recommendation only). Автоматически adjusts requests/limits based on actual usage. Покажи difference с HPA (scale up pod vs scale out pods).

## Теория

В то время как HPA масштабирует сервис **горизонтально** (увеличивает число подов), **VerticalPodAutoscaler (VPA)** масштабирует его **вертикально** — автоматически подбирает оптимальные значения `requests` и `limits` по CPU и памяти для каждого пода на основе реального исторического потребления.

Режимы работы VPA (`updateMode`):
1. **`Off` (Recommendation Only):** Безопасный режим аудита. VPA только рассчитывает и показывает рекомендации в статусе CRD, но ничего не меняет.
2. **`Initial`:** VPA назначает рекомендованные ресурсы только новым подам в момент их создания.
3. **`Auto` / `Recreate`:** VPA принудительно перезапускает работающие поды (eviction), чтобы применить новые лимиты ресурсов.

## Решение по шагам

1. Убедитесь, что в кластере установлен VPA Controller.
2. Создайте манифест `vpa.yaml` с `updateMode: "Off"`.
3. Примените манифест: `kubectl apply -f vpa.yaml`.
4. Дайте сервису поработать под нагрузкой несколько минут.
5. Запросите рекомендации VPA: `kubectl describe vpa my-service-vpa`.

## Код решения

**`vpa.yaml`**

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-service-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: billing-api
  updatePolicy:
    updateMode: "Off" # Режим рекомендаций без опасного перезапуска подов
  resourcePolicy:
    containerPolicies:
      - containerName: '*'
        minAllowed:
          cpu: 100m
          memory: 128Mi
        maxAllowed:
          cpu: 2000m
          memory: 4Gi
        controlledResources: ["cpu", "memory"]
```

**`check-vpa.sh`**

```bash
# Просмотр рекомендаций VPA
kubectl describe vpa my-service-vpa

# Пример секции Recommendation в выводе:
# Recommendation:
#   Container Recommendations:
#     Container Name:  app
#     Lower Bound:
#       Cpu:     150m
#       Memory:  200Mi
#     Target:
#       Cpu:     250m
#       Memory:  350Mi
#     Upper Bound:
#       Cpu:     1000m
#       Memory:  1Gi
```

## Под капотом

VPA состоит из трех компонентов:
1. **Recommender:** Анализирует историю потребления из Prometheus / Metrics Server и рассчитывает 4 значения (LowerBound, Target, UncappedTarget, UpperBound).
2. **Updater:** В режиме `Auto` находит поды, чьи текущие ресурсы сильно расходятся с `Target`, и вызывает их выселение (`Eviction`).
3. **Admission Plugin:** Мутирующий вебхук перехватывает создание нового пода и подставляет вычисленные значения `requests/limits` в спецификацию пода.

## Подводные камни

1. Одновременное включение HPA и VPA по одной и той же метрике (CPU): приводит к разрушительному резонансу (HPA плодит поды, а VPA уменьшает их размер, или наоборот).
2. Использование `updateMode: "Auto"` без настроенного `PodDisruptionBudget`: VPA может одновременно прибить все поды сервиса для обновления ресурсов.
3. Отсутствие `minAllowed` и `maxAllowed`: риск сжатия ресурсов до нуля или захвата всей ноды.

## На собеседовании

**Вопрос с собеседования:** Почему одновременное использование HPA и VPA на одном Deployment считается опасным антипаттерном, и как их безопасно совмещать?
**Ответ:** Если HPA и VPA настроены на одну метрику (CPU), возникает конфликт контроллеров: при росте нагрузки HPA добавляет новые поды, а VPA параллельно увеличивает CPU limit каждого пода. При спаде нагрузки оба контроллера одновременно уменьшают ресурсы и число подов, вызывая резкую нестабильность. 
Совмещение допустимо только в двух сценариях:
1. VPA работает строго в режиме рекомендаций (`updateMode: "Off"`).
2. HPA масштабирует по **бизнес-метрикам** (RPS, задержка HTTP, длина очереди Kafka), а VPA управляет **памятью** (Memory).
