# Управление правами доступа: ServiceAccount и принцип наименьших привилегий

## Условие

Настройте **ServiceAccount** с минимальными правами для вашего приложения (principle of least privilege).

## Теория

Когда контейнеру внутри пода требуется взаимодействовать с Kubernetes API (например, микросервис читает список подов или контроллер создает ConfigMap), он аутентифицируется через **`ServiceAccount`**.

Принцип наименьших привилегий (Principle of Least Privilege):
- По умолчанию поды используют аккаунт `default`, к которому часто привязаны избыточные права.
- Настоятельно рекомендуется создавать выделенный `ServiceAccount` для каждого приложения.
- Если приложению **не нужен** доступ к K8s API, обязательно отключать автомонтирование токена:
  `automountServiceAccountToken: false` — это защищает кластер от захвата при компрометации контейнера.

## Решение по шагам

1. Создайте манифест `service-account.yaml`.
2. Установите `automountServiceAccountToken: false` для изоляции.
3. В `deployment.yaml` привяжите аккаунт через `serviceAccountName: backend-sa`.
4. Примените манифесты.
5. Проверьте отсутствие смонтированного JWT-токена в директории `/var/run/secrets/kubernetes.io/serviceaccount`.

## Код решения

**`service-account.yaml`**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-sa
  namespace: default
automountServiceAccountToken: false # Запрет монтирования API токена для безопасности
```

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: secure-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: secure-service
  template:
    metadata:
      labels:
        app: secure-service
    spec:
      serviceAccountName: backend-sa
      containers:
        - name: app
          image: alpine:3.21
          command: ["/bin/sh", "-c"]
          args:
            - |
              if [ -f /var/run/secrets/kubernetes.io/serviceaccount/token ]; then
                echo "ВНИМАНИЕ: Токен K8s API смонтирован!"
              else
                echo "БЕЗОПАСНО: Доступ к токенам API кластера заблокирован."
              fi
              sleep 3600
```

## Под капотом

По умолчанию Kubelet монтирует том типа `projected` в каждый контейнер по пути `/var/run/secrets/kubernetes.io/serviceaccount`. Том содержит три файла:
1. `token`: подписанный JWT-токен сервисного аккаунта.
2. `ca.crt`: публичный корневой сертификат K8s API Server.
3. `namespace`: текущее пространство имен.
Директива `automountServiceAccountToken: false` предотвращает монтирование этого тома.

## Подводные камни

1. Использование аккаунта `default` со связанной ролью `cluster-admin`: взлом одного пода дает злоумышленнику полный контроль над всем датацентром.
2. Хранение долгоживущих токенов ServiceAccount в секретах: начиная с K8s 1.24, секреты для ServiceAccount больше не генерируются автоматически (используется механизм TokenRequest API с коротким сроком жизни).
3. Опечатка в `serviceAccountName`.

## На собеседовании

**Вопрос с собеседования:** Что может сделать злоумышленник, если он получил доступ к токену ServiceAccount внутри скомпрометированного пода?
**Ответ:** Имея JWT-токен из `/var/run/secrets/kubernetes.io/serviceaccount/token`, злоумышленник может слать прямые запросы к K8s API Server (`https://kubernetes.default.svc`) от имени этого аккаунта через `curl`. 
Если аккаунт имеет права на создание подов или чтение секретов, злоумышленник может прочитать пароли других сервисов кластера, запустить криптомайнеры или совершить побег из контейнера (Container Escape) на хостовую ноду.
