# Связка Deployment, Service и ConfigMap с ограничением ресурсов (Requests/Limits)

## Условие

Создайте Kubernetes манифесты: `Deployment`, `Service`, `ConfigMap` для вашего приложения. Настройте количество реплик и ресурсы (requests/limits).

## Теория

Комплексный манифест микросервиса объединяет вычисления (`Deployment`), сетевую балансировку (`Service`) и конфигурацию (`ConfigMap`), дополненные обязательными спецификациями ресурсов:
- **`requests`:** Гарантированный минимум ресурсов CPU и памяти, резервируемый планировщиком `kube-scheduler` на ноде при размещении пода.
- **`limits`:** Жесткий потолок потребления ресурсов:
  - При превышении Memory limit ядро Linux уничтожает контейнер по **OOMKilled** (Out of Memory, Exit code 137).
  - При превышении CPU limit контейнер не убивается, а подвергается **троттлингу** (CPU Throttling) через CFS-квоты ядра.

## Решение по шагам

1. Создайте манифест `all-in-one.yaml`, объединяющий `ConfigMap`, `Deployment` и `Service`.
2. Задайте `resources.requests: cpu: 100m, memory: 128Mi`.
3. Задайте `resources.limits: cpu: 500m, memory: 256Mi`.
4. Примените манифест: `kubectl apply -f all-in-one.yaml`.
5. Проверьте выделенные ресурсы: `kubectl describe pod -l app=microservice`.

## Код решения

**`all-in-one.yaml`**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: microservice-cfg
data:
  APP_ENV: "staging"
  PORT: "8080"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: microservice-dep
spec:
  replicas: 2
  selector:
    matchLabels:
      app: microservice
  template:
    metadata:
      labels:
        app: microservice
    spec:
      containers:
        - name: app
          image: ghcr.io/company/microservice:v1.0.0
          envFrom:
            - configMapRef:
                name: microservice-cfg
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi"
          ports:
            - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: microservice-svc
spec:
  type: ClusterIP
  selector:
    app: microservice
  ports:
    - port: 80
      targetPort: 8080
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	env := os.Getenv("APP_ENV")

	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("OK"))
	})

	fmt.Printf("Микросервис запущен в среде [%s] на порту :%s\n", env, port)
	_ = http.ListenAndServe(":"+port, nil)
}
```

## Под капотом

`kube-scheduler` суммирует `requests` всех подов на ноде. Если на сервере свободно 200m CPU, а под запрашивает 250m, под не будет туда запланирован. 

Значения `limits` транслируются в cgroups v2:
- Memory limit -> `memory.max`
- CPU limit -> `cpu.max` (например, `50000 100000` означает максимум 50 мс процессорного времени за 100 мс период CFS).

## Подводные камни

1. Запуск без `requests`: Kubelet помещает под в класс качества `BestEffort`. При нехватке памяти на ноде такие поды выселяются (evicted) в первую очередь.
2. Недостаточный лимит памяти: приложение упадет с OOMKilled при кратковременном всплеске аллокаций в Go.
3. Использование суффикса `M` вместо `Mi`: `128M` = \(128 \times 10^6\) байт, `128Mi` = \(128 \times 2^{20}\) байт.

## На собеседовании

**Вопрос с собеседования:** Что такое классы QoS (Quality of Service) в Kubernetes и как они определяются?
**Ответ:** K8s автоматически присваивает поду один из трех классов QoS на основе requests и limits:
1. **Guaranteed:** У каждого контейнера `requests == limits` для CPU и памяти. Наивысший приоритет, выселяются последними при деградации ноды.
2. **Burstable:** `requests < limits` или заданы только requests. Могут временно потреблять больше минимума, выселяются во вторую очередь.
3. **BestEffort:** `requests` и `limits` не заданы вообще. Низший приоритет, ядро Linux убивает их первыми при давлении на память (Node Memory Pressure).
