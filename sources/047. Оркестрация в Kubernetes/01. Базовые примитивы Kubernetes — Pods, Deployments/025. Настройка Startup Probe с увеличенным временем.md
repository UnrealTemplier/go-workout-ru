# Настройка Startup Probe с увеличенным временем ожидания для тяжелых сервисов

## Условие

Напиши **Startup probe**: `startupProbe: httpGet: path: /healthz, port: 8080, failureThreshold: 30, periodSeconds: 10` (5 минут на старт). Отключает liveness/readiness до success. Покажи для slow-starting applications.

## Теория

Для сервисов с экстремально долгим циклом прогрева (аналитические базы данных, ML inference, сервисы с компиляцией шейдеров или полной перестройкой индекса) требуется тонкая настройка параметров:
- `failureThreshold: 30`
- `periodSeconds: 10`
Суммарно это дает \(30 \times 10 = 300\) секунд (5 минут) гарантированного времени на старт.

Во время работы `startupProbe`:
- Liveness-проба отключена (контейнер не будет убит).
- Readiness-проба отключена (трафик не будет поступать).
- Приложение спокойно выполняет CPU-интенсивную инициализацию.

## Решение по шагам

1. Создайте эндпоинт `/healthz` в Go, возвращающий 200 OK только после полной загрузки данных.
2. В манифесте опишите `startupProbe` с интервалом 10с и порогом 30.
3. Настройте livenessProbe с быстрым интервалом 5с.
4. Разверните сервис и убедитесь по событиям `kubectl get events`, что проба ожидает готовности.

## Код решения

**`deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: heavy-ml-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: heavy-ml
  template:
    metadata:
      labels:
        app: heavy-ml
    spec:
      containers:
        - name: model-server
          image: ghcr.io/company/heavy-ml:v1.0.0
          ports:
            - containerPort: 8080
          # Выделяем до 5 минут на загрузку весов моделей
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            failureThreshold: 30
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 5
            failureThreshold: 3
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"sync/atomic"
	"time"
)

var modelLoaded atomic.Bool

func main() {
	go func() {
		fmt.Println("Загрузка моделей в память (займет 30 секунд)...")
		time.Sleep(30 * time.Second)
		modelLoaded.Store(true)
		fmt.Println("Модели загружены успешно!")
	}()

	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		if !modelLoaded.Load() {
			w.WriteHeader(http.StatusServiceUnavailable)
			_, _ = w.Write([]byte("LOADING"))
			return
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("READY"))
	})

	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Kubelet инкрементирует внутренний счетчик неудач `startupProbe`. Если число неудач достигает `failureThreshold`, Kubelet генерирует событие `Unhealthy: Startup probe failed` и отправляет контейнеру `SIGKILL`. 

Если же ответ 200 получен до исчерпания лимита, счетчик сбрасывается, `startupProbe` деактивируется до конца жизни контейнера, и управление переходит к livenessProbe.

## Подводные камни

1. Забытый `startupProbe` при долгом старте: Kubelet убьет под через 30 секунд по Liveness пробе, отправив его в вечный CrashLoopBackOff.
2. Пропуск `timeoutSeconds`: если обработчик зависает, Kubelet блокирует выполнение последующих проверок.
3. Опрос пробы слишком часто (`periodSeconds: 1`): создает лишнюю нагрузку на CPU во время и без того тяжелой инициализации.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `Init Containers` и `Startup Probe` для инициализации приложения?
**Ответ:** 
- **`Init Containers`** запускаются строго **до старта основного контейнера приложения** и выполняются последовательно до полного завершения. Они идеальны для задач, которые можно вынести в отдельный процесс (скачивание файлов конфигурации, запуск SQL миграций схемы).
- **`Startup Probe`** работает **внутри основного контейнера приложения** во время выполнения его процесса `main()`. Она необходима, когда инициализация неотделима от основного бинарника (прогрев памяти, инициализация пулов соединений, компиляция внутренних кэшей).
