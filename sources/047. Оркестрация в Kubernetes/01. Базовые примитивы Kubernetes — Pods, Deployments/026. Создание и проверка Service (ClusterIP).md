# Создание и проверка Service (ClusterIP) для маршрутизации к Deployment

## Условие

Создайте **Service** типа ClusterIP для внутреннего доступа к вашему Deployment.

## Теория

Закрепление ключевой роли `Service` типа `ClusterIP`:
- Предоставляет единую стабильную входную точку для группы подов.
- Автоматически синхронизирует список IP-адресов подов через `Endpoints`.
- Обеспечивает прозрачное горизонтальное масштабирование: при увеличении числа реплик с 2 до 10 конфигурация клиентов не меняется.

## Решение по шагам

1. Создайте `deployment.yaml` с 3 репликами.
2. Создайте `service.yaml` типа `ClusterIP`.
3. Примените конфигурацию: `kubectl apply -f .`.
4. Проверьте сопоставление IP-адресов: `kubectl get endpoints <service-name>`.
5. Масштабируйте Deployment (`kubectl scale deployment ... --replicas=5`) и убедитесь, что список Endpoints автоматически пополнился новыми IP.

## Код решения

**`service.yaml`**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: user-service
  labels:
    app: user-service
spec:
  type: ClusterIP
  selector:
    app: user-service
  ports:
    - name: http
      port: 8080
      targetPort: 8080
```

**`verify-lb.sh`**

```bash
# 1. Просмотр ClusterIP и портов
kubectl get svc user-service

# 2. Просмотр реальных IP подов за сервисом
kubectl get endpoints user-service

# 3. Масштабирование сервиса
kubectl scale deployment user-service --replicas=4

# 4. Проверка автоматического обновления Endpoints
kubectl get endpoints user-service
```

**`main.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	pod, _ := os.Hostname()
	http.HandleFunc("/user", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "User API: ответ сформирован репликой %s\n", pod)
	})
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

`EndpointSliceController` подписан на изменения объектов `Pod`. 

Когда новый под переходит в статус `Running` и успешно проходит `readinessProbe`, контроллер генерирует объект `EndpointSlice` (современная масштабируемая замена монолитного `Endpoints`). Kubelet и kube-proxy считывают обновление по протоколу Watch и добавляют новый IP в таблицу IPVS/iptables.

## Подводные камни

1. Несовпадение селектора: сервис создан, но `Endpoints: <none>`.
2. Попытка подключиться к ClusterIP извне кластера (с домашнего ноутбука): ClusterIP маршрутизируется только внутри приватной SDN сети кластера.
3. Отсутствие обработки keep-alive соединений в HTTP клиентах.

## На собеседовании

**Вопрос с собеседования:** Почему в Kubernetes 1.21+ объект `EndpointSlice` заменил классический ресурс `Endpoints`?
**Ответ:** Классический ресурс `Endpoints` содержал полный список всех IP-адресов подов сервиса в одном едином объекте. При наличии 5 000 подов у одного сервиса любое падение или пересоздание одного пода приводило к передаче всего огромного JSON-объекта (размером в мегабайты) по сети на тысячи нод кластера, перегружая etcd и сеть. 
`EndpointSlice` разбивает список адресов на небольшие чанки (по 100 эндпоинтов в каждом), что снизило сетевой трафик и нагрузку на etcd при обновлениях в сотни раз.
