# Управление конфиденциальными данными через Secret со stringData

## Условие

Создайте **Secret** для sensitive данных (DB password, API keys). Используйте `stringData` для удобного задания в plain text.

## Теория

Закрепление работы с конфиденциальными параметрами (API-ключи, токены, пароли):
- Поле `stringData` упрощает составление манифестов инженерами: значения записываются открытым текстом в YAML, а K8s API сервер при сохранении в базу etcd автоматически преобразует их в кодировку Base64.
- Подключение в под осуществляется через `valueFrom.secretKeyRef` или монтирование тома `secret`.

## Решение по шагам

1. Создайте манифест `secret.yaml` с `stringData`.
2. Добавьте API-токены и ключи доступа.
3. В `pod.yaml` подключите секреты.
4. В коде Go прочитайте значения и убедитесь в их корректности.
5. Примените манифесты и проверьте безопасность окружения.

## Код решения

**`secret.yaml`**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: payment-credentials
type: Opaque
stringData:
  STRIPE_SECRET_KEY: "sk_live_51MzXYZ1234567890abcdef"
  WEBHOOK_SIGNING_SECRET: "whsec_abcdef1234567890" 
```

**`pod.yaml`**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-processor
spec:
  containers:
    - name: processor
      image: alpine:3.21
      command: ["/bin/sh", "-c", "echo 'Credentials loaded'; sleep 3600"]
      env:
        - name: STRIPE_KEY
          valueFrom:
            secretKeyRef:
              name: payment-credentials
              key: STRIPE_SECRET_KEY
```

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	stripeKey := os.Getenv("STRIPE_KEY")
	if stripeKey == "" {
		panic("STRIPE_KEY отсутствует в окружении!")
	}
	fmt.Printf("Платежный модуль инициализирован. Длина ключа: %d байт\n", len(stripeKey))
}
```

## Под капотом

API-сервер K8s при получении объекта Secret с полем `stringData` выполняет итерацию по словарю, конвертирует строковые значения в байты, применяет стандартное кодирование `base64.StdEncoding.EncodeToString()` и сохраняет их в словарь `data`. 

Поле `stringData` используется только для записи; при обратном чтении (`kubectl get secret -o yaml`) всегда возвращается Base64-поле `data`.

## Подводные камни

1. Сохранение файла со `stringData` в репозиторий Git: случайное раскрытие боевых секретов.
2. Спецсимволы новой строки в `stringData`: случайный перенос строки в конце токена может сломать проверку цифровой подписи в Go API клиенте.
3. Отсутствие прав RBAC на просмотр секретов: разработчики должны иметь доступ только к тем секретам, которые требуются их сервису.

## На собеседовании

**Вопрос с собеседования:** Почему команда `kubectl get secret` доступна разработчикам только в dev-кластерах, но строго закрыта в production?
**Ответ:** Стандартные K8s Secret хранятся в Base64. Команда `kubectl get secret <name> -o yaml` позволяет любому пользователю с правами чтения мгновенно декодировать боевые пароли к БД и приватные ключи API (`base64 -d`), что нарушает требования стандартов безопасности (PCI DSS, ISO 27001, SOC 2). В проде права на чтение Secret выдаются только системным сервис-аккаунтам контроллеров, а инженеры получают доступ по схеме Zero Standing Privileges (ZSP) через временные токены.
