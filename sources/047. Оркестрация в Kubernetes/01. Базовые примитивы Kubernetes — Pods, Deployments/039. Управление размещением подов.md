# Управление размещением подов: Affinity, Anti-Affinity и распределение по нодам

## Условие

Настрой **Affinity/Anti-affinity**: `podAntiAffinity: preferredDuringSchedulingIgnoredDuringExecution` — распредели pods across nodes. `podAffinity` — co-locate related pods. `nodeAffinity` — run on specific nodes (GPU, SSD). Покажи topology spread.

## Теория

По умолчанию планировщик K8s размещает поды на любых свободных нодах. В HighLoad системах требуется точное управление топологией:
1. **`podAntiAffinity` (Разнесение подов):** Запрещает или не рекомендует размещать реплики одного и того же сервиса на одном физическом сервере (`topologyKey: kubernetes.io/hostname`) или в одной зоне доступности (AZ). При падении одной ноды сервис гарантированно сохраняет 100% работоспособность.
2. **`podAffinity` (Сближение подов):** Размещает тесно взаимодействующие микросервисы (например, API и кэш) на одной ноде для минимизации задержек сети.
3. **`nodeAffinity`:** Привязывает поды к нодам со специфическими метками (ноды с SSD, GPU или мощным CPU).

## Решение по шагам

1. Опишите в `deployment.yaml` секцию `affinity.podAntiAffinity`.
2. Используйте мягкое правило `preferredDuringSchedulingIgnoredDuringExecution` с весом 100.
3. Задайте `topologyKey: "kubernetes.io/hostname"`.
4. Разверните 3 реплики сервиса на кластере из нескольких нод.
5. Убедитесь через `kubectl get pods -o wide`, что поды распределились по разным нодам.

## Код решения

**`anti-affinity-deployment.yaml`**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ha-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: ha-service
  template:
    metadata:
      labels:
        app: ha-service
    spec:
      affinity:
        podAntiAffinity:
          # Мягкое правило: K8s постарается разнести поды по разным серверам,
          # но если серверов меньше 3, поды все равно запустятся!
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - ha-service
                topologyKey: "kubernetes.io/hostname"
      containers:
        - name: app
          image: alpine:3.21
          command: ["sleep", "3600"]
```

**`verify-spread.sh`**

```bash
# Просмотр распределения подов по физическим нодам:
kubectl get pods -l app=ha-service -o wide

# Пример вывода (каждый под на своей ноде):
# NAME                          READY   STATUS    NODE
# ha-service-5899fcb6cb-2k9x4   1/1     Running   node-worker-1
# ha-service-5899fcb6cb-78v2m   1/1     Running   node-worker-2
# ha-service-5899fcb6cb-w9p4j   1/1     Running   node-worker-3
```

## Под капотом

`kube-scheduler` вычисляет топологию в две фазы:
1. **Filtering (Фильтрация):** Отсеивание нод, не удовлетворяющих жестким требованиям (`requiredDuringScheduling...`).
2. **Scoring (Оценка):** Присвоение баллов оставшимся нодам. Для каждого правила `preferred...` планировщик добавляет `weight` (от 1 до 100) нодам, на которых еще нет подов с меткой `app: ha-service`. Под назначается на ноду с наибольшим суммарным баллом.

## Подводные камни

1. Использование жесткого правила `requiredDuringScheduling...` при малом числе нод: если в кластере 2 ноды, а реплик 3, третья реплика навсегда зависнет в статусе `Pending`.
2. Высокая вычислительная сложность Scoring при сотнях тысяч подов в кластере: тяжелые правила Affinity могут замедлить работу планировщика.
3. Опечатка в `topologyKey`.

## На собеседовании

**Вопрос с собеседования:** В чем разница между `preferredDuringSchedulingIgnoredDuringExecution` и `requiredDuringSchedulingIgnoredDuringExecution`?
**Ответ:** 
- **`required...` (Hard affinity):** Обязательное строгое требование. Если в кластере нет подходящей ноды (или на всех нодах уже есть такой под), планировщик **откажется запускать под**, оставив его в статусе `Pending`.
- **`preferred...` (Soft affinity):** Желательное мягкое предпочтение. Планировщик постарается выбрать наилучшую ноду в соответствии с правилом, но если свободных нод нет, он **все равно разместит под** на любой доступной ноде, отдавая приоритет доступности сервиса.
