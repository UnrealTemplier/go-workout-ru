# Alignment в слайсах и безопасность вызова unsafe.Slice

## Условие

20. **Alignment в слайсах**: Элементы слайса всегда aligned. Но если вы делаете `unsafe.Slice` из arbitrary pointer — убедитесь в alignment, иначе SIGBUS на некоторых архитектурах. Напишите безопасный конвертер байтового буфера в слайс uint64 с валидацией выравнивания.

### Исходная формулировка

**Alignment в слайсах**: Элементы слайса всегда aligned. Но если вы делаете `unsafe.Slice` из arbitrary pointer — убедитесь в alignment, иначе SIGBUS на некоторых архитектурах.

## Теория

При стандартном создании слайса через `make([]T, n)` или `append()` рантайм Go гарантирует, что адрес первого элемента `&slice[0]` строго выровнен в соответствии с `unsafe.Alignof(T)`.

Однако в высокопроизводительном сетевом коде и парсерах бинарных протоколов (zero-copy deserialization) часто выполняют приведение нетипизированного байтового среза `[]byte` к типизированному слайсу `[]uint64` или `[]MyStruct` с помощью функции **`unsafe.Slice(ptr *T, len)`** (Go 1.17+):
```go
ptr := (*uint64)(unsafe.Pointer(&byteSlice[offset]))
uint64Slice := unsafe.Slice(ptr, count)
```

**Смертельная опасность Unaligned Pointer:**
Если `&byteSlice[offset]` не кратен 8 байтам (например, адрес заканчивается на нечетную цифру):
1. На архитектурах **ARM32, MIPS, SPARC** процессор немедленно генерирует аппаратное исключение Alignment Fault, приводя к аварийному падению программы с сигналом **`SIGBUS` (Bus Error)**!
2. На архитектурах **x86-64 и современных ARM64** невыровненный доступ поддерживается аппаратно, но выполняется медленнее, а атомарные операции (`atomic.LoadUint64`) приводят к мгновенной панике рантайма Go.

**Правило:** Перед вызовом `unsafe.Slice` обязательно проверяйте: `uintptr(ptr) % unsafe.Alignof(zeroT) == 0`.

## Решение по шагам

1. Создайте сырой байтовый буфер `[]byte`.
2. Реализуйте безопасную функцию `SafeBytesToUint64Slice(buf []byte) ([]uint64, error)`.
3. Внутри функции проверьте кратность длины и строгое выравнивание указателя: `uintptr(unsafe.Pointer(&buf[0])) % 8 == 0`.
4. Продемонстрируйте корректную работу на выровненном буфере.
5. Продемонстрируйте обнаружение ошибки при смещении буфера на 1 байт (`buf[1:]`).

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"unsafe"
)

var (
	ErrUnalignedPointer = errors.New("memory alignment error: pointer address is not aligned to type requirement")
	ErrInvalidLength    = errors.New("invalid buffer length: must be multiple of element size")
)

// CastBytesToUint64 выполняет Zero-Copy конвертацию с валидацией выравнивания
func CastBytesToUint64(buf []byte) ([]uint64, error) {
	if len(buf) == 0 {
		return nil, nil
	}

	elemSize := unsafe.Sizeof(uint64(0))  // 8 bytes
	elemAlign := unsafe.Alignof(uint64(0)) // 8 bytes

	// 1. Проверка кратности размера
	if uintptr(len(buf))%elemSize != 0 {
		return nil, fmt.Errorf("%w (len=%d, expected multiple of %d)", ErrInvalidLength, len(buf), elemSize)
	}

	rawPtr := unsafe.Pointer(&buf[0])
	addr := uintptr(rawPtr)

	// 2. КРИТИЧЕСКАЯ ПРОВЕРКА ВЫРАВНИВАНИЯ
	if addr%elemAlign != 0 {
		return nil, fmt.Errorf("%w: address %p mod %d = %d (SIGBUS risk!)",
			ErrUnalignedPointer, rawPtr, elemAlign, addr%elemAlign)
	}

	// 3. Безопасное создание типизированного среза
	numElements := len(buf) / int(elemSize)
	typedSlice := unsafe.Slice((*uint64)(rawPtr), numElements)
	return typedSlice, nil
}

func main() {
	fmt.Println("=== Slice Memory Alignment Verification ===")

	// Выделяем 64 байта (гарантированно выровнены рантаймом по границе 8 байт)
	alignedBuffer := make([]byte, 32)
	for i := range alignedBuffer {
		alignedBuffer[i] = byte(i)
	}

	// 1. Корректная конвертация
	u64s, err := CastBytesToUint64(alignedBuffer)
	if err != nil {
		fmt.Println("Error:", err)
	} else {
		fmt.Printf("Successfully casted %d bytes to %d uint64s!\n", len(alignedBuffer), len(u64s))
		fmt.Printf("  Buffer addr: %p (mod 8 = %d)\n", &alignedBuffer[0], uintptr(unsafe.Pointer(&alignedBuffer[0]))%8)
		fmt.Printf("  First uint64 value: 0x%016x\n", u64s[0])
	}

	// 2. Искусственное нарушение выравнивания (сдвиг на 1 байт)
	unalignedSubSlice := alignedBuffer[1:25] // длина 24 байта (кратно 8), но адрес смещен на +1!
	fmt.Printf("\nAttempting cast on unaligned sub-slice (addr: %p)...\n", &unalignedSubSlice[0])

	_, err = CastBytesToUint64(unalignedSubSlice)
	if errors.Is(err, ErrUnalignedPointer) {
		fmt.Printf("SUCCESSFULLY CAUGHT: %v\n", err)
		fmt.Println("Protected system from SIGBUS crash on strict RISC architectures!")
	} else {
		fmt.Println("Warning: unaligned pointer was not rejected!")
	}
}
```

ℹ️ Безопасное приведение []byte к типизированному срезу с аппаратной проверкой кратности выравнивания адреса

## Под капотом

Внутри компилятора Go встроенный вызов `unsafe.Slice(ptr, len)` преобразуется в создание структуры заголовка `slice` (`unsafe.Pointer`, `int`, `int`). Сам рантайм `unsafe.Slice` намеренно не выполняет проверку выравнивания в целях нулевых накладных расходов. Ответственность за проверку адреса целиком возложена на программиста.

## Подводные камни

1. Использование невыровненных срезов для сетевых сокетов или DMA: контроллеры сетевых карт часто требуют выравнивания по границе 64 байт.
2. Игнорирование сборщика мусора: если базовый байтовый срез будет собран GC, типизированный срез станет указывать на освобожденную память (Dangling Pointer). Всегда сохраняйте ссылку на исходный срез.

## На собеседовании

«Что произойдет при вызове `atomic.LoadInt64` по невыровненному адресу на процессоре x86-64?»
Ответ: Начиная с Go 1.14 рантайм Go выполняет явную проверку `if uintptr(ptr)&7 != 0 { panic("unaligned 64-bit atomic operation") }`. Программа упадет с фатальной паникой, даже если сам процессор x86-64 технически способен выполнить невыровненное чтение.
