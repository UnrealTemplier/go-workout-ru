### Исходная формулировка

**Демонстрация cache line и false sharing.**: Создайте две переменные `int64`, лежащие в соседних ячейках памяти (например, поля одной структуры). Запустите две горутины, каждая инкрементирует свою переменную. Сравните производительность с вариантом, где переменные разнесены на разные cache line (добавлен padding `[64]byte`).

## Теория

Процессор обменивается данными с оперативной памятью не отдельными байтами, а блоками фиксированного размера — **кэш-линиями (Cache Lines)**, размер которых на современных x86 и ARM процессорах составляет **64 байта**.

**Что такое False Sharing (Ложное разделение)?**
Когда два разных ядра CPU выполняют независимые потоки/горутины:
- Ядро 1 пишет в переменную \(A\);
- Ядро 2 пишет в независимую переменную \(B\);
НО переменные \(A\) и \(B\) расположены в памяти рядом (например, поля одной структуры) и попадают в **одну и ту же 64-байтовую кэш-линию**!

Аппаратный протокол когерентности кэшей (**MESI / MOESI**):
1. Когда Ядро 1 выполняет запись в \(A\), оно переводит всю кэш-линию в состояние **Modified (M)** и инвалидирует копию этой кэш-линии в L1/L2 кэше Ядра 2 (сигнал Invalidate по кольцевой шине QPI/UPI).
2. Когда Ядро 2 хочет записать в \(B\), оно обнаруживает Cache Miss (кэш-промах) из-за инвалидации. Ядро 2 вынуждено заблокировать конвейер, запросить свежую строку у Ядра 1 и инвалидировать кэш Ядра 1.
3. Возникает эффект «пинг-понга» кэш-линий (**Cache Line Bouncing**). Производительность многопоточного кода падает в 5–20 раз!

**Решение:**
Разделение независимых переменных отступом в 64 байта (Cache Line Padding), чтобы они гарантированно находились в разных кэш-линиях.

## Решение по шагам

1. Создайте структуру `FalseSharingCounter` с двумя полями `a, b int64` без отступа.
2. Создайте структуру `PaddedCounter`, где между полями добавлен массив `_ [56]byte` (или 64 байта).
3. Напишите функцию бенчмарка: запуск 2 горутин, выполняющих по 50 000 000 инкрементов полей `a` и `b`.
4. Замерьте время выполнения для `FalseSharingCounter` и `PaddedCounter`.
5. Выведите коэффициент ускорения (Speedup).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// FalseSharingCounter: поля a и b делят одну 64-байтовую cache-линию
type FalseSharingCounter struct {
	a int64
	b int64
}

// PaddedCounter: поля a и b разнесены в разные cache-линии за счет padding
type PaddedCounter struct {
	a int64
	_ [56]byte // 8 + 56 = 64 байта (ровно 1 cache line)
	b int64
	_ [56]byte // защита от соседних объектов в куче
}

func runBenchmark(name string, iterations int64, runFn func(wg *sync.WaitGroup)) time.Duration {
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	runFn(&wg)
	wg.Wait()
	dur := time.Since(start)

	fmt.Printf("%-24s: %v\n", name, dur)
	return dur
}

func main() {
	var iterations int64 = 50_000_000

	fmt.Printf("Running False Sharing Benchmark (%d iterations per goroutine)...\n\n", iterations)

	// 1. Тест с False Sharing
	var bad FalseSharingCounter
	badDur := runBenchmark("False Sharing (Bad)", iterations, func(wg *sync.WaitGroup) {
		go func() {
			defer wg.Done()
			for i := int64(0); i < iterations; i++ {
				bad.a++
			}
		}()
		go func() {
			defer wg.Done()
			for i := int64(0); i < iterations; i++ {
				bad.b++
			}
		}()
	})

	// 2. Тест с Cache Line Padding
	var good PaddedCounter
	goodDur := runBenchmark("Padded (No False Sharing)", iterations, func(wg *sync.WaitGroup) {
		go func() {
			defer wg.Done()
			for i := int64(0); i < iterations; i++ {
				good.a++
			}
		}()
		go func() {
			defer wg.Done()
			for i := int64(0); i < iterations; i++ {
				good.b++
			}
		}()
	})

	speedup := float64(badDur) / float64(goodDur)
	fmt.Printf("\nSpeedup from Cache Padding: %.2fx faster!\n", speedup)
}
```

ℹ️ Демонстрация деградации производительности от False Sharing и устранение через 64-байтовый padding

## Под капотом

Протокол когерентности кэшей (MESI) отслеживает права владения кэш-линиями на аппаратном уровне. При операциях записи процессор отправляет в шину `RFO` (Request For Ownership). Если два ядра постоянно шлют RFO на одну и ту же физическую кэш-линию, шина интерконнекта процессора перегружается транзакциями инвалидации (Cross-core snoop traffic), заставляя процессорные конвейеры простаивать в ожидании подтверждений.

## Подводные камни

1. Избыточный padding везде: padding увеличивает размер структур, снижая эффективность кэша L1/L2 для последовательного чтения. Применяйте padding ТОЛЬКО для полей, в которые интенсивно и параллельно пишут разные горутины.
2. Использование `[64]byte` вместо `[56]byte`: если тип поля занимает 8 байт, то для выравнивания до 64 байт нужно добавить именно 56 байт (\(8 + 56 = 64\)).

## На собеседовании

«Как в стандартной библиотеке Go используется защита от False Sharing?»
Ответ: В пакете `sync` и рантайме Go (`runtime/mgc.go`, `sync/pool.go` в структуре `poolLocal`) используется поле `pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte`. Они выравнивают локальные пулы ядер процессора до 128 байт (с запасом под процессоры с Adjacent Cache Line Prefetching), гарантируя, что параллельные вызовы `sync.Pool.Get()` на разных P не вызывают инвалидации кэшей соседей.
