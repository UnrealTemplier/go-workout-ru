### Исходная формулировка

## Теория

Современные микропроцессоры оснащены специализированными аппаратными блоками — **Hardware Prefetchers (Аппаратные предвыборщики)**:
1. **L2 Stream Prefetcher:** Отслеживает запросы к памяти и выявляет линейные потоки чтения вперед или назад (Ascending / Descending streams). Если процессор считывает строки \(K, K+1\), предвыборщик автоматически отправляет запрос в контроллер памяти на загрузку строк \(K+2, K+3, K+4\).
2. **Spatial Prefetcher (Adjacent Cache Line Prefetch):** Всегда подтягивает парную 64-байтовую строку, дополняя загрузку до 128 байт.

**Разница шаблонов доступа:**
- **Sequential Access (Линейный обход):** Аппаратный Prefetcher работает с почти 100% точностью. Задержка доступа к памяти полностью скрывается (Prefetcher Latency Hiding). Скорость ограничена лишь пропускной способностью шины RAM.
- **Random Access (Случайный обход):** Процессор прыгает по непредсказуемым адресам памяти. Prefetcher бессилен. Каждая операция приводит к тяжелому L3 Cache Miss и ожиданию DRAM (60–90 нс). Скорость падает на порядок!

## Решение по шагам

1. Создайте массив из 4 000 000 элементов `int64` (32 МБ).
2. Сгенерируйте массив случайных перестановок индексов (Fisher-Yates Shuffle).
3. Измерьте время последовательного обхода массива: `sum += data[i]`.
4. Измерьте время обхода по случайным индексам: `sum += data[indices[i]]`.
5. Вычислите разницу во времени выполнения и пропускной способности (GB/s).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"time"
)

func benchmarkSequential(data []int64) (time.Duration, int64) {
	start := time.Now()
	var sum int64
	for i := 0; i < len(data); i++ {
		sum += data[i]
	}
	return time.Since(start), sum
}

func benchmarkRandom(data []int64, indices []int) (time.Duration, int64) {
	start := time.Now()
	var sum int64
	for i := 0; i < len(indices); i++ {
		sum += data[indices[i]]
	}
	return time.Since(start), sum
}

func main() {
	const n = 4_000_000 // 32 MB
	fmt.Printf("=== Hardware Prefetcher: Sequential vs Random Access (%d elements) ===\n\n", n)

	data := make([]int64, n)
	indices := make([]int, n)
	for i := 0; i < n; i++ {
		data[i] = int64(i)
		indices[i] = i
	}

	// Перемешиваем индексы для абсолютно случайного доступа
	r := rand.New(rand.NewSource(42))
	r.Shuffle(len(indices), func(i, j int) {
		indices[i], indices[j] = indices[j], indices[i]
	})

	// 1. Последовательный обход (Hardware Prefetcher активен)
	durSeq, sumSeq := benchmarkSequential(data)
	nsPerSeq := float64(durSeq.Nanoseconds()) / float64(n)
	bandwidthSeq := float64(n*8) / durSeq.Seconds() / (1024 * 1024 * 1024)

	fmt.Printf("Sequential Access: %v (%.2f ns/op, Bandwidth: %.2f GB/s) [Sum: %d]\n",
		durSeq, nsPerSeq, bandwidthSeq, sumSeq)

	// 2. Случайный обход (Hardware Prefetcher бесполезен)
	durRand, sumRand := benchmarkRandom(data, indices)
	nsPerRand := float64(durRand.Nanoseconds()) / float64(n)
	bandwidthRand := float64(n*8) / durRand.Seconds() / (1024 * 1024 * 1024)

	fmt.Printf("Random Access:     %v (%.2f ns/op, Bandwidth: %.2f GB/s) [Sum: %d]\n",
		durRand, nsPerRand, bandwidthRand, sumRand)

	slowdown := float64(durRand) / float64(durSeq)
	fmt.Printf("\nRandom access without prefetcher is %.1fx slower!\n", slowdown)
}
```

## Под капотом

Когда процессор выполняет случайный доступ, помимо промаха кэша данных (Data Cache Miss) возникает еще более тяжелый промах — **TLB Miss (Translation Lookaside Buffer Miss)**. Процессор вынужден обращаться к таблицам страниц виртуальной памяти ядра (Page Table Walk, до 4-5 обращений к памяти на один адрес), что окончательно уничтожает производительность.

## Подводные камни

1. Использование хэш-таблиц (`map[K]V`) для сотен миллионов элементов: поиск в хэш-таблице по своей сути случаен (вычисление хэша прыгает по бакетам в памяти). Для максимальной скорости сканирования используйте сортированные слайсы с бинарным поиском или B-деревья.
2. Предположение, что компилятор переставит случайный доступ: компилятор не знает распределения индексов во время выполнения.

## На собеседовании

«Как переписать структуру данных, чтобы случайный поиск стал дружелюбным к кэшу (Cache-Friendly)?»
Ответ: Применить технику **B-Tree или Blocked Search**. Вместо классического бинарного дерева поиска (где каждый узел на указателе разбросан по куче) использовать массив блоков по 64 байта (размер кэш-линии), в каждом из которых хранится 8 отсортированных ключей. Поиск внутри блока идет строго в кэше L1 с использованием SIMD-инструкций.
