# Локальность данных и Pointer Chasing: Связный список vs Непрерывный срез

## Условие

18. **Локальность данных (Pointer Chasing)**: Напиши бенчмарк. Создай Связный список (Linked List) из 10 миллионов узлов и Срез (`[]int`) из 10 миллионов чисел. Напиши две функции, которые суммируют все элементы. Убедись, что срез суммируется в разы быстрее из-за того, что данные лежат в памяти последовательно, а список разбросан по куче (Pointer Chasing).

### Исходная формулировка

**Локальность данных (Pointer Chasing)**: Напиши бенчмарк. Создай Связный список (Linked List) из 10 миллионов узлов и Срез (`[]int`) из 10 миллионов чисел. Напиши две функции, которые суммируют все элементы. Убедись, что срез суммируется в разы быстрее, так как его данные лежат в памяти последовательно и CPU предварительно загружает их в L1-кэш (Prefetching), в то время как список вызывает постоянные промахи кэша (Cache Misses).

## Теория

Разница между связным списком (Linked List) и непрерывным слайсом (`[]int`) — хрестоматийный пример проблемы **Pointer Chasing (Погоня за указателями)** и деградации пространственной локальности.

1. **Непрерывный срез (`[]int`):**
   - Все 10 000 000 чисел лежат строго друг за другом в едином монолитном куске виртуальной памяти.
   - При чтении `slice[0]` в L1-кэш загружаются следующие 7 элементов.
   - Аппаратный Prefetcher видит последовательный шаблон и предварительно загружает кэш-линии из RAM со скоростью шины памяти (DDR bandwidth ~40-60 ГБ/с).

2. **Связный список (Linked List):**
   - Каждый узел `Node { val int; next *Node }` аллоцируется отдельно в куче (10 000 000 независимых аллокаций).
   - Аллокатор памяти Go (`mcache`/`mcentral`) разбрасывает эти объекты по разным страницам кучи (`mspan`), перемежая их с другими объектами.
   - Чтобы перейти к следующему узлу `curr = curr.next`, процессор обязан дождаться чтения указателя из памяти. Это **сериализованная зависимость по данным (Data Dependency)**: процессор не может предсказать, куда указывает `next`, и конвейер инструкций простаивает 50–100 нс на каждом узле!
   - Кэш L1/L2/L3 непрерывно промахивается (TLB misses + Cache misses).

## Решение по шагам

1. Создайте структуру узла связного списка `ListNode { val int, next *ListNode }`.
2. Наполните связный список и срез `[]int` 5 000 000 элементами.
3. Напишите функцию линейного суммирования связного списка.
4. Напишите функцию линейного суммирования среза.
5. Замерьте время и выведите разницу в скорости (срез быстрее в 5–15 раз).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

type ListNode struct {
	val  int
	next *ListNode
}

func SumSlice(data []int) int {
	var sum int
	for i := 0; i < len(data); i++ {
		sum += data[i]
	}
	return sum
}

func SumLinkedList(head *ListNode) int {
	var sum int
	curr := head
	for curr != nil {
		sum += curr.val
		curr = curr.next
	}
	return sum
}

func main() {
	const count = 5_000_000
	fmt.Printf("=== Pointer Chasing Benchmark (%d elements) ===\n\n", count)

	fmt.Println("Allocating contiguous slice...")
	sliceData := make([]int, count)
	for i := 0; i < count; i++ {
		sliceData[i] = i
	}

	fmt.Println("Allocating fragmented linked list...")
	var head *ListNode
	// Создаем связный список
	var tail *ListNode
	for i := 0; i < count; i++ {
		node := &ListNode{val: i}
		if head == nil {
			head = node
			tail = node
		} else {
			tail.next = node
			tail = node
		}
	}

	// 1. Бенчмарк слайса
	startSlice := time.Now()
	resSlice := SumSlice(sliceData)
	durSlice := time.Since(startSlice)
	fmt.Printf("\n[Contiguous Slice]  Sum: %d, Time: %v\n", resSlice, durSlice)

	// 2. Бенчмарк связного списка
	startList := time.Now()
	resList := SumLinkedList(head)
	durList := time.Since(startList)
	fmt.Printf("[Linked List (Heap)] Sum: %d, Time: %v\n", resList, durList)

	speedup := float64(durList) / float64(durSlice)
	fmt.Printf("\nContiguous memory access is %.1fx faster than pointer chasing!\n", speedup)
}
```

## Под капотом

В связном списке процессор упирается в фундаментальный барьер — задержку обращения к памяти (Memory Latency Wall). Поскольку адрес следующего узла неизвестен до завершения чтения текущего, инструкция `MOVQ 8(RAX), RAX` блокирует конвейер Out-of-Order выполнения (Instruction-Level Parallelism равен 0). В слайсе же процессор исполняет инструкции с опережением (Speculative Execution), загружая десятки чисел параллельно.

## Подводные камни

1. Использование структур данных на указателях (деревья, списки) в критических путях обработки данных: заменяйте их на плоские массивы (Flat Arrays / B-Trees / Packed Vectors).
2. Нагрузка на сборщик мусора: 10 000 000 узлов в куче заставляют GC сканировать 10 000 000 указателей, вызывая долгие паузы маркировки.

## На собеседовании

«Почему в современных движках баз данных B-Tree почти всегда реализуется на базе массивов внутри страниц (Flat Page Layout), а не как дерево узлов на указателях?»
Ответ: Узел B-дерева проектируется размером ровно под размер страницы памяти (4 КБ или 8 КБ). Все ключи внутри узла лежат непрерывным массивом. Это дает: 1) Чтение ключей страницы за одно обращение к кэшу; 2) Эффективный бинарный поиск с предвыборкой; 3) Нулевую фрагментацию памяти и отсутствие Pointer Chasing.
