# Сравнение Memory Alignment и влияние перестановки полей

## Условие

6. **[Memory Alignment]**: Создай структуру `BadStruct { a bool; b int64; c bool }` и `GoodStruct { b int64; a bool; c bool }`. Выведи `unsafe.Sizeof` для обеих. Объясни эффект Padding (выравнивание до 8 байт).

### Исходная формулировка

**[Memory Alignment]**: Создай структуру `BadStruct { a bool; b int64; c bool }` и `GoodStruct { b int64; a bool; c bool }`. Выведи `unsafe.Sizeof` для обеих. Объясни эффект Padding (выравнивание до 8 байт).

## Теория

Сравнение двух казалось бы идентичных структур демонстрирует, как банальный порядок объявления полей в исходном коде Go кардинально меняет потребление оперативной памяти:

```go
type BadStruct struct {
    a bool   // 1 байт
    b int64  // 8 байт
    c bool   // 1 байт
}

type GoodStruct struct {
    b int64  // 8 байт
    a bool   // 1 байт
    c bool   // 1 байт
}
```

Почему `BadStruct` занимает 24 байта, а `GoodStruct` — 16 байт?
1. В `BadStruct` между `a` и `b` вынужденно вставляется 7 байт пустоты, так как `b` не может лежать по адресу 1 (не кратно 8). После `c` вставляется еще 7 байт пустоты. Суммарно: 14 байт мусора.
2. В `GoodStruct` поле `b` начинается с адреса 0. За ним сразу по адресу 8 идет `a` (1 байт). По адресу 9 идет `c` (1 байт). Поля `a` и `c` размещаются компактно «плечом к плечу» в пределах одного 8-байтового машинного слова. Хвостовой padding составляет всего 6 байт для выравнивания до 16.

Экономия: **33.3% памяти** на ровном месте без изменения бизнес-логики!

## Решение по шагам

1. Объявите структуры `BadStruct` и `GoodStruct`.
2. Рассчитайте теоретический размер каждой структуры.
3. Вызовите `unsafe.Sizeof()` и подтвердите теоретический расчет.
4. Выведите коэффициенты полезной нагрузки (Useful Payload Ratio).
5. Продемонстрируйте форматированный вывод.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type BadStruct struct {
	a bool  // 1 byte
	b int64 // 8 bytes
	c bool  // 1 byte
}

type GoodStruct struct {
	b int64 // 8 bytes
	a bool  // 1 byte
	c bool  // 1 byte
}

func main() {
	sizeBad := unsafe.Sizeof(BadStruct{})
	sizeGood := unsafe.Sizeof(GoodStruct{})

	usefulBytes := unsafe.Sizeof(bool(false))*2 + unsafe.Sizeof(int64(0)) // 1 + 1 + 8 = 10 байт

	fmt.Printf("=== Memory Alignment Comparison ===\n")
	fmt.Printf("BadStruct size:  %d bytes (Useful: %d, Waste: %d, Efficiency: %.1f%%)\n",
		sizeBad, usefulBytes, sizeBad-usefulBytes, float64(usefulBytes)/float64(sizeBad)*100)

	fmt.Printf("GoodStruct size: %d bytes (Useful: %d, Waste: %d, Efficiency: %.1f%%)\n",
		sizeGood, usefulBytes, sizeGood-usefulBytes, float64(usefulBytes)/float64(sizeGood)*100)

	reduction := float64(sizeBad-sizeGood) / float64(sizeBad) * 100
	fmt.Printf("\nMemory footprint reduced by %.1f%% simply by reordering fields!\n", reduction)
}
```

ℹ️ Сравнение эффективности использования памяти между BadStruct (24 байта) и GoodStruct (16 байт)

## Под капотом

Выравнивание до 8 байт обусловлено шириной шины данных современных 64-битных процессоров. Контроллер памяти передает за один такт шины 64 бита (8 байт). Если поле `int64` пересекает 8-байтовую границу слова (например, лежит на байтах 4..11), процессору требуется два такта чтения шины, операция сдвига в регистрах AL/AH и логическое OR, что удваивает время чтения поля из кэша L1.

## Подводные камни

1. Заблуждение, что Go сам переставит поля при компиляции с оптимизацией (`-O`): компилятор Go строго сохраняет исходный порядок полей.
2. Нарушение обратной совместимости при использовании рефлексии: `reflect.Value.Field(0)` вернет другое поле, если порядок был изменен.

## На собеседовании

«Как выравнивание памяти влияет на работу сборщика мусора (GC) в Go?»
Ответ: Прямо пропорционально: 1) Меньший размер структур снижает объем занятой кучи (Heap size); 2) В меньший объем кучи помещается больше объектов на странице mspan, что снижает фрагментацию памяти; 3) Меньше страниц памяти сканируется при маркировке GC Mark Phase, сокращая время STW и CPU-утилизацию GC.
