# Определение размера Cache Line через скачок Latency при обходе с шагом

## Условие

15. **Размер cache line.**: Определите размер cache line вашего CPU: создайте массив `[1024]int64`, обходите с шагом 1, затем с шагом 8 (64 байта). Замерьте время. Покажите скачок latency при переходе через границу 64 байт. Объясните L1d cache line (обычно 64B) и spatial locality.

### Исходная формулировка

**Размер cache line.**: Определите размер cache line вашего CPU: создайте массив `[1024]int64`, обходите с шагом 1, затем с шагом 8 (64 байта). Замерьте время. Покажите скачок latency при переходе через границу 64 байт. Объясните L1d cache line (обычно 64 байта, иногда 128 на ARM).

## Теория

Принцип **пространственной локальности (Spatial Locality)** гласит: если программа обратилась к байту по адресу \(A\), с высокой вероятностью в ближайшее время она обратится к соседним байтам \(A+1, A+2, \dots\).

Именно ради пространственной локальности процессор загружает из ОЗУ сразу 64 байта:
- Если мы обходим массив с **шагом 1** (`step = 1`):
  При обращении к `arr[0]` происходит 1 кэш-промах, в L1-кэш загружается кэш-линия с элементами `arr[0..7]`.
  Следующие 7 обращений (`arr[1]`, `arr[2]`, ..., `arr[7]`) попадают в L1-кэш со скоростью ~1 нс (**L1 Cache Hit**). Доля попаданий — 87.5%!
- Если мы обходим массив с **шагом 8** (`step = 8`, то есть шаг 64 байта):
  Каждое обращение попадает в совершенно новую кэш-линию (`arr[0]`, `arr[8]`, `arr[16]`, ...).
  Каждая итерация цикла генерирует **новый Cache Miss**, заставляя процессор каждый раз загружать новую строку из кэша L2/L3.

При переходе от шага 1 к шагу 8 время одной операции скачкообразно возрастает, что позволяет программно определить размер кэш-линии без чтения системных файлов.

## Решение по шагам

1. Выделите большой массив `int64` (например, 16 000 000 элементов, чтобы он не помещался целиком в L1/L2 кэш).
2. Напишите функцию обхода массива с переменным шагом `stride = 1, 2, 4, 8, 16, 32`.
3. Замерьте среднее время доступа на один прочитанный элемент для каждого шага.
4. Постройте график/таблицу задержки и покажите резкий скачок при `stride = 8` (64 байта).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

func benchmarkStride(data []int64, stride int, passes int) (time.Duration, float64) {
	n := len(data)
	var sum int64
	totalAccesses := int64((n / stride) * passes)

	start := time.Now()
	for p := 0; p < passes; p++ {
		for i := 0; i < n; i += stride {
			sum += data[i]
		}
	}
	elapsed := time.Since(start)
	_ = sum

	nsPerAccess := float64(elapsed.Nanoseconds()) / float64(totalAccesses)
	return elapsed, nsPerAccess
}

func main() {
	// 16M элементов int64 = 128 MB (существенно больше L3 кэша типичного десктопа)
	const size = 16 * 1024 * 1024
	fmt.Printf("Allocating %d MB buffer to exceed CPU caches...\n", (size*8)/(1024*1024))
	buffer := make([]int64, size)

	for i := range buffer {
		buffer[i] = int64(i)
	}

	strides := []int{1, 2, 4, 8, 16, 32, 64}
	fmt.Printf("\n%-10s | %-12s | %-16s | %-14s\n", "Stride (elements)", "Bytes per Step", "Latency/Access (ns)", "Cache Line Ratio")
	fmt.Println("------------------------------------------------------------------------")

	var baseLatency float64
	for idx, s := range strides {
		bytesStep := s * 8
		_, ns := benchmarkStride(buffer, s, 3)
		if idx == 0 {
			baseLatency = ns
		}

		fmt.Printf("%-17d | %-14dB | %16.2f ns | %6.2fx\n", s, bytesStep, ns, ns/baseLatency)
	}

	fmt.Println("\nObservation:")
	fmt.Println("At stride=8 (64 bytes), every read hits a NEW cache line, saturating memory bus latency.")
}
```

ℹ️ Замер латентности памяти при обходе с переменным шагом для экспериментального выявления размера Cache Line

## Под капотом

В современных процессорах встроен аппаратный предвыборщик (Hardware Stream Prefetcher). При последовательном чтении (`stride = 1`) Prefetcher распознает линейный паттерн доступа и заранее подгружает следующие кэш-линии из RAM в L2/L1 до того, как инструкция запросит их. При увеличении шага до случайных прыжков Prefetcher отключается, раскрывая истинную латентность памяти DRAM.

## Подводные камни

1. Использование слишком маленького массива (например, 1024 элемента): массив размером 8 КБ целиком поместится в кэш L1d (обычно 32–48 КБ), и скачок задержки будет нивелирован скоростью L1.
2. Неиспользование возвращаемой суммы: компилятор Go может полностью вырезать цикл (Dead Code Elimination), если результат суммирования не используется.

## На собеседовании

«Почему итерация по двумерному срезу `matrix[row][col]` в Go выполняется в разы быстрее, чем `matrix[col][row]`?»
Ответ: В памяти Go двумерные срезы/массивы располагаются по строкам (Row-Major Order). Итерация по строкам идет последовательно по смежным адресам памяти с использованием пространственной локальности кэш-линий и предвыборщика. Итерация по колонкам прыгает через целые строки, вызывая промах кэша на каждом чтении.
