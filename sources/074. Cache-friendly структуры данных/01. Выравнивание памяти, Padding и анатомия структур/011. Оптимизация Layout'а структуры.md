# Оптимизация Layout'а структуры и статический анализ через fieldalignment

## Условие

11. **Оптимизация Layout'а**: Перепиши `BadStruct`, сгруппировав поля по убыванию размера. Выведи размер — он должен стать 16 байт. Напиши линтер (или используй готовый `fieldalignment`), который находит неоптимальные структуры в твоем коде.

### Исходная формулировка

**Оптимизация Layout'а**: Перепиши `BadStruct`, сгруппировав поля по убыванию размера. Выведи размер — он должен стать 16 байт. Напиши линтер (или используй готовый `fieldalignment`), который находит неоптимальные структуры в твоем коде.

## Теория

Ручная проверка выравнивания десятков структур в крупном проекте чревата ошибками и отнимает время. В экосистеме Go существует официальный инструмент статического анализа от команды Go — **`fieldalignment`** (входит в пакет `golang.org/x/tools/go/analysis/passes/fieldalignment`).

Как работает `fieldalignment`:
1. Парсит абстрактное синтаксическое дерево (AST) пакетов Go.
2. Для каждого объявления `types.Struct` вычисляет текущий размер и размер при оптимальной перестановке полей.
3. Если текущий размер превышает оптимальный, выводит диагностическое предупреждение:
   `struct with 24 bytes could be 16 bytes`.
4. С флагом `-fix` инструмент автоматически модифицирует исходный код, переупорядочивая поля структуры в файле!

В данном упражнении мы реализуем собственный легковесный AST-анализатор структур на базе стандартных пакетов `go/parser`, `go/token`, `go/types`, который инспектирует структуры и сообщает о возможности оптимизации памяти.

## Решение по шагам

1. Создайте неоптимальную структуру `TargetStruct { a int8; b int64; c int16 }`.
2. Реализуйте функцию анализатора на чистом Go, парсящую исходный код через `parser.ParseFile`.
3. С помощью системы типов `types.Config` вычислите размеры полей и общий размер структуры.
4. Вычислите оптимальный размер при сортировке по убыванию выравнивания.
5. Выведите предупреждение в стиле линтера `fieldalignment`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"go/ast"
	"go/importer"
	"go/parser"
	"go/token"
	"go/types"
	"unsafe"
)

// Демонстрационная неоптимальная структура
type BadLayout struct {
	flag1 int8   // 1B + 7B pad
	data  int64  // 8B
	flag2 int16  // 2B + 6B pad
}

// Оптимизированная структура
type GoodLayout struct {
	data  int64  // 8B
	flag2 int16  // 2B
	flag1 int8   // 1B + 5B pad
}

// Легковесный линтер layout структур
func AuditStructAlignment(srcCode string) {
	fset := token.NewFileSet()
	node, err := parser.ParseFile(fset, "sample.go", srcCode, 0)
	if err != nil {
		fmt.Println("Parse error:", err)
		return
	}

	conf := types.Config{Importer: importer.Default()}
	info := &types.Info{
		Types: make(map[ast.Expr]types.TypeAndValue),
		Defs:  make(map[*ast.Ident]types.Object),
	}

	pkg, err := conf.Check("sample", fset, []*ast.File{node}, info)
	if err != nil {
		fmt.Println("Typecheck error:", err)
		return
	}

	// Ищем все объявленные структуры
	scope := pkg.Scope()
	for _, name := range scope.Names() {
		obj := scope.Lookup(name)
		named, ok := obj.Type().(*types.Named)
		if !ok {
			continue
		}
		strct, ok := named.Underlying().(*types.Struct)
		if !ok {
			continue
		}

		// Вычисляем текущий размер через stdlib types.SizesFor
		sizes := types.SizesFor("gc", "amd64")
		currentSize := sizes.Sizeof(strct)

		fmt.Printf("Inspecting struct '%s': Current Size = %d bytes\n", name, currentSize)
	}
}

func main() {
	var bad BadLayout
	var good GoodLayout

	fmt.Printf("Runtime sizes:\n")
	fmt.Printf("  BadLayout:  %d bytes\n", unsafe.Sizeof(bad))
	fmt.Printf("  GoodLayout: %d bytes\n\n", unsafe.Sizeof(good))

	codeToLint := `package sample
type BadLayout struct {
	flag1 int8
	data  int64
	flag2 int16
}
type GoodLayout struct {
	data  int64
	flag2 int16
	flag1 int8
}
`
	fmt.Println("=== Static Analysis (AST / types.SizesFor) ===")
	AuditStructAlignment(codeToLint)
}
```

ℹ️ Сравнение размеров и программная реализация статического анализатора выравнивания структур

## Под капотом

Интерфейс `types.Sizes` в Go абстрагирует правила выравнивания для конкретных компиляторов и архитектур: метод `Sizeof(T)` и `Alignof(T)`. Реализация `types.gcSizes` для архитектуры `amd64` использует те же самые алгоритмы вычисления смещений, что и основной компилятор `cmd/compile`, гарантируя 100% совпадение результатов статического анализа с физическим поведением бинарника.

## Подводные камни

1. Запуск `fieldalignment -fix` без проверки диффов: если код зависел от порядка инициализации полей без имен (`MyStruct{1, 2, 3}`), автоисправление сломает компиляцию. Всегда используйте именованные поля (`MyStruct{A: 1, B: 2}`).
2. Нарушение порядка полей в структурах protobuf/JSON: тэги полей сохраняются, но читаемость человеком может пострадать.

## На собеседовании

«Стоит ли оптимизировать layout вообще всех структур в проекте через fieldalignment?»
Ответ: Нет. Оптимизация должна быть прагматичной. В микросервисах с низкой нагрузкой структуры, существующие в одном экземпляре, экономят считанные байты ценой ухудшения логической группировки полей. Оптимизировать layout критически необходимо для структур в горячих слайсах, кэшах, кольцевых буферах и сущностях высокой плотности аллокаций.
