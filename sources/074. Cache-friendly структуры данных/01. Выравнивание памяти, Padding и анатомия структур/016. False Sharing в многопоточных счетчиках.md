# False Sharing в многопоточных счетчиках: падение скорости в 10–20 раз

## Условие

### Исходная формулировка

**False Sharing: демонстрация.**: Создайте структуру с двумя полями `counterA, counterB uint64`. Запустите 2 goroutine: каждая инкрементит своё поле 100 млн раз. Замерьте время. Объясните, почему производительность падает в 10-20×: оба поля в одной cache line (64 байта), CPU cores гоняются за exclusive ownership (MESI протокол).

## Теория

При проектировании метрик микросервисов и глобальных счетчиков (например, `atomic.Uint64` для количества запросов и ошибок) частая ошибка — объединение счетчиков в компактную структуру:
```go
type ServiceMetrics struct {
    SuccessCount uint64 // 8 байт
    ErrorCount   uint64 // 8 байт
}
```
Оба счетчика занимают всего 16 байт и лежат в одной 64-байтовой кэш-линии.

Если пул воркеров на 8 ядрах процессора непрерывно выполняет `atomic.AddUint64(&metrics.SuccessCount, 1)`, а обработчик ошибок пишет в `ErrorCount`:
1. Каждая атомарная инструкция `LOCK XADD` на уровне x86 захватывает монопольное владение кэш-линией.
2. Протокол MESI вынуждает ядро сбросить линию в шину и отозвать кэш у всех параллельных ядер.
3. Время одного инкремента возрастает с 1.5 нс до 35 нс.
4. Пропускная способность счетчика падает в **10–20 раз**!

Решение в production: разделение счетчиков по разным кэш-линиям с помощью отступа в 56 байт (или создание локальных счетчиков на ядро / на воркер — Per-Core / Sharded Counters).

## Решение по шагам

1. Создайте структуру `CompactCounters { a, b uint64 }`.
2. Создайте структуру `SeparatedCounters { a uint64; _ [56]byte; b uint64; _ [56]byte }`.
3. Запустите 2 параллельные горутины, инкрементирующие поля `a` и `b` 100 000 000 раз.
4. Замерьте время и выведите сравнительные метрики пропускной способности (Mops/sec).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type CompactCounters struct {
	a atomic.Uint64
	b atomic.Uint64
}

type SeparatedCounters struct {
	a atomic.Uint64
	_ [56]byte // Cache line padding (8 + 56 = 64B)
	b atomic.Uint64
	_ [56]byte
}

func testCompact(iterations uint64) time.Duration {
	var c CompactCounters
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.a.Add(1)
		}
	}()
	go func() {
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.b.Add(1)
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func testSeparated(iterations uint64) time.Duration {
	var c SeparatedCounters
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.a.Add(1)
		}
	}()
	go func() {
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.b.Add(1)
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func main() {
	var n uint64 = 50_000_000
	fmt.Printf("=== Atomic False Sharing Stress Test (%d ops/core) ===\n\n", n)

	durCompact := testCompact(n)
	tpsCompact := float64(n*2) / durCompact.Seconds() / 1_000_000
	fmt.Printf("Compact (Same Cache Line):      %v (%.2f Mops/s)\n", durCompact, tpsCompact)

	durSeparated := testSeparated(n)
	tpsSeparated := float64(n*2) / durSeparated.Seconds() / 1_000_000
	fmt.Printf("Separated (Cache Line Padded):  %v (%.2f Mops/s)\n", durSeparated, tpsSeparated)

	speedup := float64(durCompact) / float64(durSeparated)
	fmt.Printf("\nPadding eliminated cache invalidations: %.2fx performance boost!\n", speedup)
}
```

## Под капотом

Атомарная инструкция `atomic.AddUint64` в Go компилируется в инструкцию ассемблера `LOCK XADDQ`. Префикс `LOCK` требует монопольного владения строкой кэша L1 в состоянии Modified (M). Если строка разделяется, контроллер когерентности вынужден сбрасывать буферы записи (Store Buffers), вызывая задержку конвейера на каждом инкременте.

## Подводные камни

1. Использование обычного `+1` вместо атомиков в многопоточном коде: хотя компилятор может показать False Sharing, обычный `++` без синхронизации приведет к потере обновлений (Data Race).
2. Забывание о хвостовом padding: если после `b` нет padding, следующая структура, аллоцированная в куче, может попасть в ту же кэш-линию, что и `b`.

## На собеседовании

«Как в Linux ядре и Go спроектирован высокопроизводительный счетчик (Per-CPU Counter)?»
Ответ: Создается срез счетчиков длиной `runtime.NumCPU()`, где каждый элемент выровнен до 64 (или 128) байт с помощью padding. Горутина или поток инкрементирует строго счетчик своего процессора `counters[cpuID]`. Чтение итогового значения суммирует все ячейки. Это дает нулевой contention и максимальный TPS записи.
