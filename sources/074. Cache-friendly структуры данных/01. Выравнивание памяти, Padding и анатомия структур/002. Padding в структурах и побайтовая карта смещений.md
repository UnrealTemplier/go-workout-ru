# Padding в структурах и побайтовая карта смещений

## Условие

2. **Padding в структурах.**: Создайте структуру `struct { a bool; b int64; c bool }`. Измерьте `unsafe.Sizeof`, `unsafe.Offsetof` каждого поля. Нарисуйте байтовую карту: `a` (1 байт) + padding (7) + `b` (8) + `c` (1) + padding (7). Переставьте поля так, чтобы размер уменьшился с 24 до 16 байт.

### Исходная формулировка

**Padding в структурах.**: Создайте структуру `struct { a bool; b int64; c bool }`. Измерьте `unsafe.Sizeof`, `unsafe.Offsetof` каждого поля. Нарисуйте байтовую карту: `a` (1 байт) + padding (7) + `b` (8) + `c` (1) + padding (7). Переставьте поля (`b`, `a`, `c`) и покажите уменьшение размера с 24 до 16 байт. Объясните, почему компилятор выравнивает по `unsafe.Alignof` самого большого поля.

## Теория

Рассмотрим структуру из трех полей:
```go
type Sample struct {
    a bool   // 1 байт
    b int64  // 8 байт
    c bool   // 1 байт
}
```
Интуитивно кажется, что размер должен быть \(1 + 8 + 1 = 10\) байт. Однако `unsafe.Sizeof(Sample{})` вернет **24 байта**!

Почему так происходит?
1. Поле `a` занимает байт 0.
2. Поле `b` имеет тип `int64`, чье выравнивание равно 8 байтам. Оно обязано начинаться по смещению, кратному 8. Ближайшее смещение — 8. Поэтому байты 1..7 заполняются «мусором» (**Padding 7 байт**).
3. Поле `b` занимает байты 8..15.
4. Поле `c` занимает байт 16.
5. Максимальное выравнивание структуры равно 8. Общий размер структуры обязан делиться на 8. Текущий размер \(17 \to\) округляется вверх до **24 байт** (добавляется **хвостовой padding 7 байт** в позиции 17..23).

При перестановке полей в `struct { b int64; a bool; c bool }`:
- `b` занимает байты 0..7.
- `a` занимает байт 8.
- `c` занимает байт 9.
- Итоговый размер 10 байт округляется до 16 (хвостовой padding 6 байт). Экономия: 8 байт на каждом экземпляре (33% памяти).

## Решение по шагам

1. Создайте структуру `PaddedStruct { a bool; b int64; c bool }`.
2. Измерьте смещения полей через `unsafe.Offsetof`.
3. Создайте массив из 24 байт и наглядно визуализируйте побайтовую карту (`[A][P][P][P][P][P][P][P][B][B][B][B][B][B][B][B][C][P][P][P][P][P][P][P]`).
4. Создайте оптимизированную структуру `PackedStruct { b int64; a bool; c bool }`.
5. Выведите побайтовую карту оптимизированной структуры (16 байт).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"strings"
	"unsafe"
)

type PaddedStruct struct {
	a bool  // 1 байт
	b int64 // 8 байт
	c bool  // 1 байт
}

type PackedStruct struct {
	b int64 // 8 байт
	a bool  // 1 байт
	c bool  // 1 байт
}

func visualizeBytes(label string, size uintptr, ranges map[string][]int) {
	fmt.Printf("%s (Total: %d bytes):\n", label, size)
	grid := make([]string, size)
	for i := range grid {
		grid[i] = "[ . ]" // padding
	}

	for name, idxs := range ranges {
		for _, idx := range idxs {
			grid[idx] = fmt.Sprintf("[%s]", name)
		}
	}

	// Печать рядами по 8 байт (Word)
	for row := 0; row < int(size); row += 8 {
		end := row + 8
		if end > int(size) {
			end = int(size)
		}
		rowStr := strings.Join(grid[row:end], " ")
		fmt.Printf("  Bytes %02d..%02d: %s\n", row, end-1, rowStr)
	}
}

func main() {
	var p PaddedStruct
	var k PackedStruct

	fmt.Println("=== UNOPTIMIZED PADDED STRUCT ===")
	visualizeBytes("PaddedStruct", unsafe.Sizeof(p), map[string][]int{
		"a": {int(unsafe.Offsetof(p.a))},
		"b": {8, 9, 10, 11, 12, 13, 14, 15},
		"c": {int(unsafe.Offsetof(p.c))},
	})

	fmt.Println("\n=== OPTIMIZED PACKED STRUCT ===")
	visualizeBytes("PackedStruct", unsafe.Sizeof(k), map[string][]int{
		"b": {0, 1, 2, 3, 4, 5, 6, 7},
		"a": {int(unsafe.Offsetof(k.a))},
		"c": {int(unsafe.Offsetof(k.c))},
	})

	fmt.Printf("\nResult: Size reduced from %d to %d bytes (-%.1f%%)\n",
		unsafe.Sizeof(p), unsafe.Sizeof(k),
		float64(unsafe.Sizeof(p)-unsafe.Sizeof(k))/float64(unsafe.Sizeof(p))*100)
}
```

## Под капотом

Почему Go автоматически не переупорядочивает поля за программиста (как это делает Rust с модификатором по умолчанию или компилятор JVM)?
Создатели Go намеренно сохранили строгое соответствие порядка полей в коде их порядку в физической памяти. Это критично для: 1) Совместимости с C через CGO (структуры Go передаются в функции Си без копирования); 2) Низкоуровневых операций `unsafe.Pointer`; 3) Работы системных вызовов ОС (`syscall`).

## Подводные камни

1. Хвостовой padding при наличии структуры нулевого размера: если последнее поле структуры имеет тип `struct{}` (zero-size), Go добавляет в конец 8 байт padding, чтобы указатель за пределами структуры не ссылался на чужой объект в куче.
2. Использование `unsafe.Pointer` с хардкодными смещениями вместо `unsafe.Offsetof`.

## На собеседовании

«Зачем нужен хвостовой padding в структуре, если после нее больше нет полей?»
Ответ: Хвостовой padding необходим для массивов и слайсов. Если мы создадим массив `[10]Sample`, каждый элемент \(i\) обязан начинаться со смещения \(i \times \text{Sizeof(Sample)}\). Если бы хвостового padding не было (размер 17 байт), второй элемент массива начался бы по смещению 17, нарушив выравнивание поля `b` (оно оказалось бы по некратному адресу \(17 + 7 = 24\)... а третий элемент вообще по некратному 34). Хвостовой padding гарантирует выравнивание всех элементов массива.
