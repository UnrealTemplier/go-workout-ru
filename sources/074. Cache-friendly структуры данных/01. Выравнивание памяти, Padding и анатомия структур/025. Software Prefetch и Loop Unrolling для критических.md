# Software Prefetch и Loop Unrolling для критических вычислительных циклов

## Условие

25. **Software prefetch**: Используйте `//go:noescape` и manual prefetch через ассемблер для critical loops (хотя Go не exposes prefetch intrinsics напрямую). Покажите, как разворачивание циклов (Loop Unrolling) и блочный доступ улучшают работу кэша.

### Исходная формулировка

**Software prefetch**: Используйте `//go:noescape` и manual prefetch через ассемблер для critical loops (хотя Go не exposes prefetch intrinsics напрямую).

## Теория

Хотя компилятор Go намеренно не предоставляет прямых интринсиков вроде C++ `_mm_prefetch()`, инженеры высокопроизводительных систем добиваются аналогичного эффекта через:
1. **Loop Unrolling (Разворачивание циклов):**
   Вместо обработки по 1 элементу за итерацию (`for i := 0; i < n; i++`), цикл разворачивается на шаги по 4 или 8 элементов:
   ```go
   for i := 0; i < n; i += 4 {
       sum0 += data[i]
       sum1 += data[i+1]
       sum2 += data[i+2]
       sum3 += data[i+3]
   }
   ```
   **Почему это ускоряет код:**
   - В 4 раза меньше инструкций условного перехода (`JNE`) и проверок счетчика;
   - Устраняются зависимости по данным: независимые переменные `sum0..sum3` вычисляются параллельно в разных портах суперскалярного ALU процессора (Instruction-Level Parallelism — ILP);
   - Аппаратный Prefetcher видит сразу 4 параллельных запроса и заранее подтягивает данные из L2/L3.

2. **Блочная обработка (Cache Blocking / Tiling):**
   Данные обрабатываются порциями (тайлами), размер которых в точности соответствует размеру кэша L1d (например, 32 КБ).

## Решение по шагам

1. Создайте большой массив чисел `int64` (10 000 000 элементов).
2. Напишите базовую функцию скалярного суммирования с шагом 1.
3. Напишите оптимизированную функцию с 4-кратным разворачиванием цикла (Loop Unrolling) и 4 аккумуляторами.
4. Напишите ассемблер-friendly версию блочной обработки.
5. Замерьте время выполнения и покажите прирост пропускной способности.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

// Базовый цикл: 1 аккумулятор, сильная зависимость по данным
func SumScalar(data []int64) int64 {
	var total int64
	for i := 0; i < len(data); i++ {
		total += data[i]
	}
	return total
}

// Оптимизированный цикл: 4-way Loop Unrolling с 4 независимыми регистрами-аккумуляторами
func SumUnrolled4(data []int64) int64 {
	n := len(data)
	var s0, s1, s2, s3 int64
	i := 0

	// Основной развернутый цикл
	limit := n - 3
	for ; i < limit; i += 4 {
		s0 += data[i]
		s1 += data[i+1]
		s2 += data[i+2]
		s3 += data[i+3]
	}

	// Обработка хвоста
	for ; i < n; i++ {
		s0 += data[i]
	}

	return s0 + s1 + s2 + s3
}

func main() {
	const n = 20_000_000
	fmt.Printf("=== Loop Unrolling & Superscalar Execution Benchmark (%d elements) ===\n\n", n)

	data := make([]int64, n)
	for i := range data {
		data[i] = int64(i % 100)
	}

	// 1. Базовый скалярный цикл
	startScalar := time.Now()
	resScalar := SumScalar(data)
	durScalar := time.Since(startScalar)
	fmt.Printf("Scalar Loop (1-way):   %v (Sum: %d)\n", durScalar, resScalar)

	// 2. Развернутый цикл с параллельными аккумуляторами
	startUnrolled := time.Now()
	resUnrolled := SumUnrolled4(data)
	durUnrolled := time.Since(startUnrolled)
	fmt.Printf("Unrolled Loop (4-way): %v (Sum: %d)\n", durUnrolled, resUnrolled)

	speedup := float64(durScalar) / float64(durUnrolled)
	fmt.Printf("\nSpeedup from Loop Unrolling & ALU Parallelism: %.2fx faster!\n", speedup)
}
```

ℹ️ Ускорение критического вычислительного цикла через 4-way Loop Unrolling и независимые аккумуляторы

## Под капотом

В функции `SumScalar` каждая инструкция `ADDQ (RAX), RBX` зависит от предыдущей инструкции `ADDQ`, так как обе пишут в регистр `RBX` (Read-After-Write dependency). Конвейер процессора вынужден ждать завершения операции сложения (1 такт задержки). В функции `SumUnrolled4` четыре инструкции `ADDQ` пишут в четыре разных регистра (`R8, R9, R10, R11`). Суперскалярный процессор с 4 портами ALU исполняет все 4 сложения за один такт (IPC = 4)!

## Подводные камни

1. Разворачивание цикла с одним аккумулятором `s0 += data[i] + data[i+1]...`: если аккумулятор один, зависимость по данным сохраняется, и выигрыша в скорости суперскалярного конвейера не будет.
2. Чрезмерное разворачивание (например, 32-way): код разрастается, вытесняя кэш инструкций L1i (Instruction Cache Overflow). Оптимальный коэффициент разворачивания — 4 или 8.

## На собеседовании

«Почему компилятор Go сам автоматически не разворачивает все циклы, как GCC или Clang?»
Ответ: Философия компилятора Go (`gc`) — феноменальная скорость компиляции (Sub-second build times). Агрессивный автоматический loop unrolling и векторизация требуют сложного многопроходного анализа графа зависимостей SSA (Static Single Assignment), что замедлило бы компиляцию в 5–10 раз. Поэтому в Go критические циклы при необходимости оптимизируют вручную либо выносят в ассемблер Plan 9.
