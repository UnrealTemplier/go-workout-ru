## Теория

Профайлеры уровня языка (например, `pprof` в Go) показывают утилизацию процессора по функциям, но **бессильны** перед микроархитектурными проблемами оборудования, такими как False Sharing. В отчете `pprof` код с False Sharing будет просто выглядеть как процессор, тратящий 100% времени на элементарную инструкцию `INC`.

Для выявления аппаратных аномалий используется системный профилировщик ядра Linux — **`perf`** (интерфейс Performance Counters for Linux, PMU):
Команда:
```bash
perf stat -e cache-misses,cache-references,L1-dcache-load-misses ./my_binary
```

Что показывает `perf`:
1. В программе с **False Sharing**:
   - Количество `cache-misses` подскакивает до десятков миллионов;
   - Время выполнения возрастает в разы;
   - Инструкций за такт (IPC — Instructions Per Cycle) падает с 2.5 до 0.2 (процессор простаивает в ожидании шины памяти).
2. В программе с **64-байтовым выравниванием (No False Sharing)**:
   - Количество кэш-промахов снижается до околонулевого уровня (кэш L1 попадает в 99.9% случаев);
   - IPC достигает максимума.

## Решение по шагам

1. Создайте CLI-программу с двумя режимами запуска: `--mode=bad` (False Sharing) и `--mode=good` (Padded).
2. Реализуйте интенсивный многопоточный инкремент счетчиков.
3. Опишите команды профилирования `perf stat` и объясните интерпретацию метрик.
4. Продемонстрируйте программный замер времени и расчет микроархитектурных метрик.

## Код решения

**`main.go`**

```go
package main

import (
	"flag"
	"fmt"
	"runtime"
	"sync"
	"time"
)

type BadMetrics struct {
	worker1 int64
	worker2 int64
}

type GoodMetrics struct {
	worker1 int64
	_       [56]byte // Cache line padding 64 bytes
	worker2 int64
	_       [56]byte
}

func runBad(iterations int64) time.Duration {
	var metrics BadMetrics
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			metrics.worker1++
		}
	}()
	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			metrics.worker2++
		}
	}()
	wg.Wait()
	return time.Since(start)
}

func runGood(iterations int64) time.Duration {
	var metrics GoodMetrics
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			metrics.worker1++
		}
	}()
	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			metrics.worker2++
		}
	}()
	wg.Wait()
	return time.Since(start)
}

func main() {
	mode := flag.String("mode", "both", "Execution mode: 'bad', 'good', or 'both'")
	flag.Parse()

	runtime.GOMAXPROCS(runtime.NumCPU())
	iterations := int64(100_000_000)

	fmt.Printf("CPU Cores: %d, Iterations: %d\n", runtime.NumCPU(), iterations)
	fmt.Println("To profile hardware PMU counters with Linux perf, run:")
	fmt.Println("  perf stat -e cache-misses,cache-references,L1-dcache-load-misses go run main.go -mode=bad")
	fmt.Println("  perf stat -e cache-misses,cache-references,L1-dcache-load-misses go run main.go -mode=good\n")

	if *mode == "bad" || *mode == "both" {
		dur := runBad(iterations)
		fmt.Printf("[Bad Mode - False Sharing] Duration: %v\n", dur)
	}

	if *mode == "good" || *mode == "both" {
		dur := runGood(iterations)
		fmt.Printf("[Good Mode - Padded 64B]   Duration: %v\n", dur)
	}
}
```

ℹ️ Бенчмарк для профилирования аппаратных счетчиков cache-misses через Linux perf

## Под капотом

Аппаратный счетчик PMU `L1-dcache-load-misses` инкрементируется аппаратурой процессора каждый раз, когда чтение из кэша L1 первого уровня завершается промахом. При False Sharing этот счетчик растет не из-за нехватки объема кэша, а из-за инвалидации кэш-линий (Coherency Invalidation Misses). Специальное событие `OFFCORE_RESPONSE` в процессорах Intel позволяет точно изолировать промахи межъядерной синхронизации (Hit Modified in peer core).

## Подводные камни

1. Запуск бенчмарка в виртуальных машинах без поддержки Virtual PMU: в Docker или WSL счетчики `perf` могут выдавать `<not supported>`, если гипервизор не пробрасывает PMU.
2. Проверка на одном ядре (`GOMAXPROCS=1`): если горутины выполняются на одном физическом ядре процессора, False Sharing не возникнет, так как ядро разделяет один L1-кэш.

## На собеседовании

«Что такое False Sharing при чтении (Read-Only) разными ядрами?»
Ответ: При чтении (Read-Only) False Sharing НЕ ВОЗНИКАЕТ. В протоколе когерентности MESI линия переходит в состояние **Shared (S)** и может одновременно находиться в L1/L2 кэшах всех ядер процессора без инвалидаций. Проблема False Sharing возникает ИСКЛЮЧИТЕЛЬНО тогда, когда хотя бы одно ядро выполняет запись (Write / Invalidate).
