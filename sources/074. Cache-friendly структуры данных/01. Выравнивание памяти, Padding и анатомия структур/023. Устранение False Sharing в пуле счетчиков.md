# Устранение False Sharing в пуле счетчиков через PaddedCounter

## Условие

23. **[Устранение False Sharing]**: Измени массив из предыдущего задания на структуру `PaddedCounter { val int64; _ [56]byte }`. Создай массив `[8]PaddedCounter`. Замерь время снова. Оно должно ускориться в 5-10 раз, так как каждый счетчик теперь занимает отдельную кэш-линию.

### Исходная формулировка

**[Устранение False Sharing]**: Измени массив из предыдущего задания на структуру `PaddedCounter { val int64; _ [56]byte }`. Создай массив `[8]PaddedCounter`. Замерь время снова. Оно должно ускориться в 5-10 раз, так как каждый счетчик теперь занимает ровно одну линию кэша.

## Теория

В упражнении 14 мы видели, как массив `[8]int64` приводил к взаимному вытеснению строк кэша между ядрами процессора из-за того, что все 8 счетчиков делили одну общую 64-байтовую кэш-линию.

Чтобы превратить этот массив в **Cache-Aligned Data Structure**, мы оборачиваем каждое значение в выровненный тип:
```go
type PaddedCounter struct {
    val int64   // 8 байт полезной нагрузки
    _   [56]byte // 56 байт отступа
}
```
Размер одного элемента `PaddedCounter` равен строго \(8 + 56 = 64\) байта.
Массив `[8]PaddedCounter` теперь занимает ровно \(8 \times 64 = 512\) байт памяти и гарантированно раскладывается на **8 независимых кэш-линий**:
- Элемент 0 занимает кэш-линию 0;
- Элемент 1 занимает кэш-линию 1;
- ...
- Элемент 7 занимает кэш-линию 7.

Каждое ядро процессора работает исключительно со своей персональной кэш-линией в кэше L1d. Сигналы инвалидации (Invalidate Broadcasts) по шине равны строго нулю. Производительность возрастает в 5–10 раз!

## Решение по шагам

1. Создайте структуру `PaddedCounter { val int64; _ [56]byte }`.
2. Убедитесь с помощью `unsafe.Sizeof`, что размер структуры равен ровно 64 байтам.
3. Создайте массив `var paddedArr [8]PaddedCounter`.
4. Запустите 8 параллельных горутин (по числу ядер), каждая из которых инкрементирует свой счетчик `paddedArr[id].val` 50 000 000 раз.
5. Сравните время выполнения с наивным массивом `[8]int64`.
6. Зафиксируйте многократное ускорение.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
	"unsafe"
)

type UnpaddedArray [8]int64

type PaddedCounter struct {
	val int64
	_   [56]byte // Cache line padding (8 + 56 = 64B)
}

type PaddedArray [8]PaddedCounter

func benchmarkUnpadded(n int64, workers int) time.Duration {
	var arr UnpaddedArray
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		workerID := w
		go func() {
			defer wg.Done()
			for i := int64(0); i < n; i++ {
				arr[workerID]++
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func benchmarkPadded(n int64, workers int) time.Duration {
	var arr PaddedArray
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		workerID := w
		go func() {
			defer wg.Done()
			for i := int64(0); i < n; i++ {
				arr[workerID].val++
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	workers := 8
	if runtime.NumCPU() < 8 {
		workers = runtime.NumCPU()
	}
	const iterations = 50_000_000

	var p PaddedCounter
	fmt.Printf("PaddedCounter Size: %d bytes (Alignof: %d)\n", unsafe.Sizeof(p), unsafe.Alignof(p))
	fmt.Printf("Benchmarking %d parallel workers, %d increments each...\n\n", workers, iterations)

	durBad := benchmarkUnpadded(iterations, workers)
	fmt.Printf("Unpadded Array (Severe False Sharing): %v\n", durBad)

	durGood := benchmarkPadded(iterations, workers)
	fmt.Printf("Padded Array (Zero False Sharing):    %v\n", durGood)

	speedup := float64(durBad) / float64(durGood)
	fmt.Printf("\nSpeedup achieved: %.2fx faster with 64-byte padding!\n", speedup)
}
```

ℹ️ Устранение False Sharing в массиве счетчиков с помощью 64-байтового кэш-паддинга

## Под капотом

В многоядерных архитектурах при запуске 8 воркеров на одной кэш-линии аппаратная блокировка шины масштабируется не линейно, а квадратично: каждое ядро постоянно генерирует запросы на смену владельца строки кэша для остальных 7 ядер (\(O(N^2)\) интерконнект-трафика). Разнесение по разным кэш-линиям возвращает линейную масштабируемость \(O(1)\) на ядро.

## Подводные камни

1. Забывание о выравнивании базового адреса массива: если массив аллоцирован в куче, рантайм Go выравнивает блоки от 64 байт до кратного 64. Однако при встраивании во внешнюю структуру необходимо убедиться, что смещение массива тоже кратно 64.
2. Неоправданный расход памяти: массив из 1000 PaddedCounter займет 64 КБ вместо 8 КБ. Применяйте паддинг только там, где реально есть параллельная запись с разных потоков.

## На собеседовании

«Как в Go выровнять начало структуры в памяти строго по границе 64 байт (Cache-Aligned)?»
Ответ: В Go нет прямого аналога C++ `alignas(64)`. Чтобы структура начиналась с адреса, кратного 64, либо выделяют байтовый буфер с запасом и сдвигают указатель через `unsafe.Pointer` до адреса `addr % 64 == 0`, либо используют первое поле `_ [0]uint64` в сочетании с библиотеками вроде `golang.org/x/sys/cpu`.
