### Исходная формулировка

**Устранение False Sharing через padding.**: Добавьте между полями `[56]byte` (или `[64]byte` для выравнивания). Повторите бенчмарк. Покажите восстановление производительности. Объясните, почему `runtime` делает то же самое в `runtime/proc.go` (поля `p` разнесены по разным cache lines).

## Теория

Исходный код рантайма Go и стандартной библиотеки — золотой стандарт применения Cache Line Padding для высоконагруженных систем.

Примеры из стандартной библиотеки Go:
1. **`sync.Pool` (`src/sync/pool.go`):**
   ```go
   type poolLocal struct {
       poolLocalInternal
       // Prevents false sharing on widespread platforms with
       // 128 mod (cache line size) = 0 .
       pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
   }
   ```
   В `sync.Pool` для каждого процессора `P` создается локальный пул объектов. Если бы структуры `poolLocal` лежали в массиве вплотную, параллельные вызовы `pool.Get()` на процессоре 0 и процессоре 1 постоянно инвалидировали бы кэш-линии друг друга! Разработчики Go выровняли размер `poolLocal` ровно до **128 байт** (с запасом под архитектуры с 128B кэш-линиями и процессоры с парной предвыборкой Adjacent Cache Line Prefetch).

2. **Планировщик Go (`src/runtime/proc.go`):**
   В структуре шедулера локальные очереди горутин (`gFree`, `p.runq`) снабжены аналогичным выравниванием, чтобы планирование горутин на одном ядре не тормозило планировщик на соседних ядрах.

## Решение по шагам

1. Исследуйте формулу расчета паддинга: `pad [128 - unsafe.Sizeof(T)%128]byte`.
2. Реализуйте структуру локального воркера `WorkerSlot`, защищенную формулой 128-байтового паддинга.
3. Продемонстрируйте, что `unsafe.Sizeof(WorkerSlot)` строго кратен 128 байтам независимо от размера полезных полей.
4. Запустите конкурентный тест параллельной работы воркеров без деградации скорости.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
	"unsafe"
)

// Внутренняя полезная нагрузка слота
type WorkerSlotInternal struct {
	tasksProcessed uint64
	lastTaskID     uint64
	activeWorkerID int32
}

// WorkerSlot с эталонным паддингом в стиле sync.Pool
type WorkerSlot struct {
	WorkerSlotInternal
	// Паддинг до 128 байт: предотвращает False Sharing даже на процессорах с 128-байтовыми кэш-линиями
	pad [128 - unsafe.Sizeof(WorkerSlotInternal{})%128]byte
}

func main() {
	var internal WorkerSlotInternal
	var slot WorkerSlot

	fmt.Println("=== sync.Pool & runtime/proc.go Cache Padding Pattern ===")
	fmt.Printf("WorkerSlotInternal payload size: %d bytes\n", unsafe.Sizeof(internal))
	fmt.Printf("Padding array size:              %d bytes\n", unsafe.Sizeof(slot.pad))
	fmt.Printf("Total WorkerSlot size:           %d bytes (Multiple of 128: %v)\n\n",
		unsafe.Sizeof(slot), unsafe.Sizeof(slot)%128 == 0)

	const numSlots = 4
	var clusterPool [numSlots]WorkerSlot

	// Проверяем смещения каждого слота в массиве
	for i := 0; i < numSlots; i++ {
		addr := uintptr(unsafe.Pointer(&clusterPool[i]))
		fmt.Printf("Slot %d address: 0x%x (Offset from base: %3d bytes)\n",
			i, addr, addr-uintptr(unsafe.Pointer(&clusterPool[0])))
	}

	// Запуск параллельных независимых воркеров
	const ops = 50_000_000
	var wg sync.WaitGroup
	wg.Add(numSlots)

	start := time.Now()
	for w := 0; w < numSlots; w++ {
		slotIdx := w
		go func() {
			defer wg.Done()
			for i := uint64(0); i < ops; i++ {
				clusterPool[slotIdx].tasksProcessed++
				clusterPool[slotIdx].lastTaskID = i
			}
		}()
	}
	wg.Wait()
	dur := time.Since(start)

	fmt.Printf("\nAll %d workers finished %d operations in %v with ZERO false sharing!\n",
		numSlots, ops, dur)
}
```

## Под капотом

Почему именно 128 байт, а не 64?
В современных процессорах Intel Core / Xeon и AMD EPYC включен аппаратный механизм `Spatial Prefetcher`. При запросе любой 64-байтовой строки процессор всегда спаривает ее с соседней четной/нечетной строкой, загружая единый 128-байтовый блок. Если две независимые переменные лежат в соседних 64-байтовых строках (например, по смещениям 0 и 64), пространственный префетчер все равно будет втягивать обе строки в кэш соседа, вызывая псевдо-ложное разделение. Отступ 128 байт полностью исключает этот эффект.

## Подводные камни

1. Ошибка в формуле паддинга, если размер структуры уже кратен 128: если `Sizeof(T) == 128`, то `128 % 128 == 0`, и массив станет `[128]byte`, раздув структуру до 256 байт. В продакшене учитывают условие `if size % 128 != 0`.
2. Чрезмерное увлечение 128-байтовым паддингом: L1-кэш имеет размер всего 32–48 КБ; структуры по 128 байт быстрее вытесняют другие полезные данные.

## На собеседовании

«Как в Go устроен `sync.Pool` под капотом и почему он так эффективно масштабируется на 64+ ядрах?»
Ответ: `sync.Pool` хранит двухуровневую структуру: массив `[P]poolLocal`, где `P = runtime.GOMAXPROCS(0)`. Каждый элемент массива выровнен до 128 байт. Когда горутина вызывает `Get()`, она привязывается к текущему P (`runtime_procPin()`) и берет объект из приватного слота своего ядра без мьютексов и False Sharing. Только если приватный слот пуст, ядро идет «воровать» объект у соседа (Work Stealing).
