# Симуляция Cache Line в массиве [8]int64 и гонка за одну кэш-линию

## Условие

14. **[Cache Line Simulation]**: Напиши программу, которая создает массив `[8]int64`. Горутина A постоянно инкрементирует `arr[0]`, а горутина B — `arr[1]`. Запусти под профайлером и замерь время. Хотя это разные переменные, они находятся в одной линии кэша (8 * 8 = 64 байта) — ядра процессора будут непрерывно отбирать друг у друга эту линию.

### Исходная формулировка

**[Cache Line Simulation]**: Напиши программу, которая создает массив `[8]int64`. Горутина A постоянно инкрементирует `arr[0]`, а горутина B — `arr[1]`. Запусти под профайлером и замерь время. Хотя это разные переменные, они находятся в одной линии кэша (64 байта), что вызывает постоянную инвалидацию кэша (Cache Coherence Ping-Ponging).

## Теория

Массив `[8]int64` занимает ровно \(8 \times 8 = 64\) байта — точный размер одной кэш-линии процессора.

Когда мы распределяем элементы одного массива между независимыми горутинами:
- Горутина A работает с `arr[0]` (байты 0..7);
- Горутина B работает с `arr[1]` (байты 8..15),
с точки зрения логики Go это две абсолютно независимые переменные, не требующие мьютекса для предотвращения Data Race (горутины пишут в разные адреса памяти).

Однако на физическом уровне процессора архитектура L1 Data Cache оперирует исключительно блоками по 64 байта:
1. Ядро 1 читает кэш-линию с `arr[0..7]` в свой L1-кэш и выполняет инкремент.
2. Протокол MESI требует, чтобы Ядро 1 получило монопольное право на запись (**Modified state**). Ядро 1 отправляет сигнал инвалидации всем остальным ядрам.
3. Копия строки в L1-кэше Ядра 2 немедленно помечается как **Invalid (I)**.
4. Ядро 2 пытается выполнить инкремент `arr[1]`, но его кэш инвалидирован! Происходит L1 Cache Miss. Ядро 2 шлет запрос Read For Ownership (RFO), отбирая кэш-линию у Ядра 1.
5. Происходит бесконечный пинг-понг кэш-линии через интерконнект процессора (Bus Contention). Задержка каждой операции вырастает с 1 нс (L1 Hit) до 40–80 нс (Межъядерный RFO RTT).

## Решение по шагам

1. Создайте разделяемый массив `var arr [8]int64`.
2. Запустите Горутину A, выполняющую 50 000 000 инкрементов `arr[0]`.
3. Запустите Горутину B, выполняющую 50 000 000 инкрементов `arr[1]`.
4. Для сравнения запустите вариант, где элементы разнесены на разные кэш-линии (`arrA[0]` и `arrB[0]` в разных массивах).
5. Замерьте время и выведите падение производительности из-за конкуренции за одну кэш-линию.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
	"unsafe"
)

func runSharingTest(iterations int64) time.Duration {
	// Массив [8]int64 ровно 64 байта = 1 cache line
	var sharedLine [8]int64
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			sharedLine[0]++
		}
	}()

	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			sharedLine[1]++
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func runIsolatedTest(iterations int64) time.Duration {
	// Два массива, разделенные в памяти
	var lineA [8]int64
	var lineB [8]int64
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			lineA[0]++
		}
	}()

	go func() {
		defer wg.Done()
		for i := int64(0); i < iterations; i++ {
			lineB[0]++
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func main() {
	var arr [8]int64
	fmt.Printf("Array size: %d bytes (Alignof: %d)\n", unsafe.Sizeof(arr), unsafe.Alignof(arr))
	fmt.Printf("Address of arr[0]: %p\n", &arr[0])
	fmt.Printf("Address of arr[1]: %p (Distance: %d bytes)\n\n", &arr[1], uintptr(unsafe.Pointer(&arr[1]))-uintptr(unsafe.Pointer(&arr[0])))

	iterations := int64(50_000_000)
	fmt.Printf("Running %d iterations per goroutine...\n", iterations)

	sharedDur := runSharingTest(iterations)
	fmt.Printf("Single Cache Line (arr[0] & arr[1]): %v\n", sharedDur)

	isolatedDur := runIsolatedTest(iterations)
	fmt.Printf("Separate Cache Lines:                 %v\n", isolatedDur)

	ratio := float64(sharedDur) / float64(isolatedDur)
	fmt.Printf("\nFalse sharing on 1 cache line caused %.2fx slowdown!\n", ratio)
}
```

ℹ️ Симуляция конкуренции двух горутин за одну 64-байтовую кэш-линию в массиве [8]int64

## Под капотом

Внутри архитектуры Intel Skylake / AMD Zen кэш L1d имеет задержку 4–5 тактов процессора (~1 нс). При промахе из-за инвалидации кэш-линии другим ядром запрос отправляется через распределенный L3-кэш (LLC — Last Level Cache) и шину межъядерной связи. Задержка возрастает до 40–60 тактов (~15–20 нс), что на порядок снижает скорость цикла `for`.

## Подводные камни

1. Маскировка проблемы при оптимизации компилятором: если компилятор видит, что переменная локальна и не сбрасывается в память, он может держать ее в регистре процессора (RAX/RBX). Однако при разделении между горутинами компилятор вынужден генерировать инструкции записи в память.
2. Использование среза `[]int64` вместо массива: срез добавляет заголовок (24 байта), но базовый массив все равно подвержен ложному разделению.

## На собеседовании

«Почему детектор гонок `go run -race` не сообщает об ошибке в программе с False Sharing?»
Ответ: Инструмент `ThreadSanitizer` (-race) отслеживает только логические гонки данных (Data Races) — несинхронизированное обращение к одной и той же переменной памяти. При False Sharing разные потоки пишут в разные непересекающиеся переменные (`arr[0]` и `arr[1]`), поэтому с точки зрения Go memory model программа корректна. False Sharing — это чисто микроархитектурная аппаратная проблема производительности.
