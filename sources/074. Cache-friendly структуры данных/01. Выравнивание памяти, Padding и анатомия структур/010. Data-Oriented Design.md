# Data-Oriented Design: Array of Structs (AoS) vs Struct of Arrays (SoA)

## Условие

10. **Array of structs vs Struct of arrays**: Сравните:
    ```go
    type AOS []struct{ x, y int64 }  // Array of Structs
    type SOA struct{ x, y []int64 }  // Struct of Arrays
    ```
    Для итерации по одному полю SOA в 2-4x быстрее (лучше cache locality, векторные инструкции). Напишите бенчмарк для 10 000 000 элементов.

### Исходная формулировка

**Array of structs vs Struct of arrays**: Сравните:
```go
type AOS []struct{ x, y int64 }  // Array of Structs
type SOA struct{ x, y []int64 }  // Struct of Arrays
```
Для итерации по одному полю SOA в 2-4x быстрее (лучше cache locality).

## Теория

Архитектурный подход **Data-Oriented Design (DOD)** ставит во главу угла аппаратные особенности процессора: кэш-линии, предвыборку (Hardware Prefetcher) и векторные инструкции (SIMD).

Сравнение двух подходов организации данных:
1. **Array of Structs (AoS) — Массив структур:**
   Традиционный ООП-стиль: `[]Particle`, где `Particle` содержит `X, Y, Z, Mass, Color, Lifetime`.
   В памяти элементы чередуются: `[X1, Y1, Z1, M1, C1, L1, X2, Y2, ...]`.
   **Проблема:** Если нам нужно просуммировать только координаты `X` всех частиц, процессор при чтении каждой 64-байтовой кэш-линии загружает 8 байт `X` и 56 байт ненужных полей `Y, Z, Mass...`. 87.5% пропускной способности шины памяти тратится впустую!

2. **Struct of Arrays (SoA) — Структура массивов:**
   Паттерн DOD: структура содержит отдельные срезы `X []float64`, `Y []float64`, `Mass []float64`.
   В памяти все координаты `X` лежат единым непрерывным массивом: `[X1, X2, X3, X4, X5, X6, X7, X8, ...]`.
   **Преимущества:**
   - 100% полезная нагрузка каждой кэш-линии (все 64 байта используются для вычислений).
   - Аппаратный Prefetcher идеально предсказывает линейный доступ.
   - Компилятор и процессор могут задействовать векторные инструкции AVX2 / AVX-512 / NEON для параллельной обработки 4-8 чисел за такт.

## Решение по шагам

1. Создайте структуру точки `PointAOS { x, y int64 }` и слайс `AOS []PointAOS`.
2. Создайте структуру `SOA { x, y []int64 }`.
3. Инициализируйте обе структуры 10 000 000 элементов.
4. Напишите алгоритм суммирования только координаты `x`.
5. Замерьте время выполнения для AoS и SoA.
6. Выведите коэффициент ускорения (Speedup).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

type PointAOS struct {
	x int64
	y int64
}

type AOS []PointAOS

type SOA struct {
	x []int64
	y []int64
}

func SumAOS(points AOS) int64 {
	var total int64
	for i := range points {
		total += points[i].x
	}
	return total
}

func SumSOA(soa *SOA) int64 {
	var total int64
	xSlice := soa.x
	for i := range xSlice {
		total += xSlice[i]
	}
	return total
}

func main() {
	const n = 10_000_000
	fmt.Printf("=== Data-Oriented Design: AoS vs SoA (%d elements) ===\n\n", n)

	// Инициализация AoS
	aos := make(AOS, n)
	for i := 0; i < n; i++ {
		aos[i] = PointAOS{x: int64(i), y: int64(i * 2)}
	}

	// Инициализация SoA
	soa := &SOA{
		x: make([]int64, n),
		y: make([]int64, n),
	}
	for i := 0; i < n; i++ {
		soa.x[i] = int64(i)
		soa.y[i] = int64(i * 2)
	}

	// Бенчмарк AoS
	startAOS := time.Now()
	resAOS := SumAOS(aos)
	durAOS := time.Since(startAOS)
	fmt.Printf("AoS (Array of Structs):  %v (Sum: %d)\n", durAOS, resAOS)

	// Бенчмарк SoA
	startSOA := time.Now()
	resSOA := SumSOA(soa)
	durSOA := time.Since(startSOA)
	fmt.Printf("SoA (Struct of Arrays):  %v (Sum: %d)\n", durSOA, resSOA)

	speedup := float64(durAOS) / float64(durSOA)
	fmt.Printf("\nSoA is %.2fx faster due to 100%% Cache Line utilization and vector prefetching!\n", speedup)
}
```

ℹ️ Сравнение производительности обхода поля в Array of Structs (AoS) и Struct of Arrays (SoA)

## Под капотом

В тесте AoS при чтении `points[i].x` процессор загружает в кэш L1 64 байта (содержащие 4 структуры `{x, y}`). Полезно используется только половина байтов (поля `x`), а поля `y` выбрасываются. В тесте SoA одна 64-байтовая кэш-линия содержит сразу 8 подряд идущих элементов `x`. Процессор совершает ровно в 2 раза меньше транзакций по шине памяти L1/L2.

## Подводные камни

1. Неудобство API при одиночных операциях: в SoA операция «удалить один объект по индексу» или «добавить одну точку» требует изменения нескольких независимых слайсов.
2. Использование SoA там, где всегда читаются ВСЕ поля объекта: если в цикле нужны и `x`, и `y`, то AoS может оказаться не медленнее, так как оба поля уже находятся в одной кэш-линии.

## На собеседовании

«Где в реальных HighLoad системах применяется паттерн SoA?»
Ответ: 1) В игровых движках и физических симуляторах (Entity Component System — ECS); 2) В колоночных СУБД (ClickHouse, Apache Arrow, Parquet), где данные на диске и в памяти хранятся по колонкам (SoA), обеспечивая сканирование миллиардов чисел в секунду; 3) В финансовом высокочастотном трейдинге (HFT) для расчета книги ордеров.
