# Расщепление кэш-линий (Cache Line Splitting) для объектов размером 65 байт

## Условие

13. **Cache line splitting**: Создайте структуру размером 65 байт. Изучите, как она располагается в двух cache lines вместо одной — это expensive для частого доступа. Покажите, как неаккуратный размер структуры приводит к дополнительным промахам кэша.

### Исходная формулировка

**Cache line splitting**: Создайте структуру размером 65 байт. Изучите, как она располагается в двух cache lines вместо одной — это expensive для频繁访问.

## Теория

Размер кэш-линии равен 64 байтам. Если структура имеет размер **65 байт** (всего на 1 байт больше кэш-линии), возникает феномен **Cache Line Splitting (Расщепление кэш-линии)**:

1. **Двойная загрузка из памяти:**
   Чтобы прочитать или записать один экземпляр такой 65-байтовой структуры, процессору гарантированно требуется загрузить **две независимые кэш-линии** из оперативной памяти (первые 64 байта и оставшийся 1 байт).
2. **Пересечение границ страниц памяти:**
   Если структура пересекает границу физической страницы памяти (Page Boundary, обычно 4 КБ), операция чтения может потребовать двух обращений к TLB (Translation Lookaside Buffer) и двух промахов страниц (Page Faults).
3. **Эффект в слайсах:**
   В массиве `[1000]Struct65` элементы непрерывно пересекают 64-байтовые границы: элемент 0 лежит в линиях 0 и 1; элемент 1 лежит в линиях 1 и 2... Каждое обращение к структуре заставляет контроллер памяти вычитывать 128 байт данных.

**Инженерное решение:**
Оптимизировать размер структуры так, чтобы он укладывался ровно в 64 байта (1 cache line) или 32 байта (две структуры в 1 cache line).

## Решение по шагам

1. Создайте структуру `Struct65` размером 65 байт (`[65]byte`).
2. Создайте структуру `Struct64` размером 64 байта (`[64]byte`).
3. Создайте слайсы из 1 000 000 элементов для обоих типов.
4. Проведите бенчмарк случайного или последовательного чтения/модификации элементов.
5. Продемонстрируйте падение скорости из-за постоянной двойной загрузки кэш-линий в `Struct65`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
	"unsafe"
)

// Struct64: ровно 64 байта (1 Cache Line)
type Struct64 struct {
	data [64]byte
}

// Struct65: 65 байт (гарантированно расщепляется на 2 Cache Lines)
type Struct65 struct {
	data [65]byte
}

func BenchmarkAccess64(slice []Struct64) time.Duration {
	start := time.Now()
	var sum byte
	// Модифицируем первый и последний байт каждой структуры
	for i := range slice {
		slice[i].data[0]++
		slice[i].data[63]++
		sum += slice[i].data[0]
	}
	dur := time.Since(start)
	_ = sum
	return dur
}

func BenchmarkAccess65(slice []Struct65) time.Duration {
	start := time.Now()
	var sum byte
	for i := range slice {
		slice[i].data[0]++
		slice[i].data[64]++
		sum += slice[i].data[0]
	}
	dur := time.Since(start)
	_ = sum
	return dur
}

func main() {
	var s64 Struct64
	var s65 Struct65

	fmt.Printf("Size of Struct64: %d bytes (Alignof: %d)\n", unsafe.Sizeof(s64), unsafe.Alignof(s64))
	fmt.Printf("Size of Struct65: %d bytes (Alignof: %d)\n\n", unsafe.Sizeof(s65), unsafe.Alignof(s65))

	const count = 5_000_000
	fmt.Printf("Allocating slices of %d elements...\n", count)

	slice64 := make([]Struct64, count)
	slice65 := make([]Struct65, count)

	dur64 := BenchmarkAccess64(slice64)
	fmt.Printf("Accessing 5M Struct64 (Single Cache Line): %v\n", dur64)

	dur65 := BenchmarkAccess65(slice65)
	fmt.Printf("Accessing 5M Struct65 (Split Cache Lines):  %v\n", dur65)

	overhead := (float64(dur65)/float64(dur64) - 1.0) * 100
	fmt.Printf("\nCache line splitting overhead for just 1 extra byte: +%.1f%% slower!\n", overhead)
}
```

## Под капотом

Когда процессор исполняет инструкцию записи в память, операнд которой пересекает 64-байтовую границу (Split Lock / Split Store), контроллер кэша вынужден захватывать две строки кэша одновременно. На старых процессорах это приводило к аппаратной блокировке всей системной шины (`LOCK#` signal assertion). В современных ядрах Linux даже появилось специальное ограничение `split_lock_mitigate` для защиты от DoS-атак, вызывающих лавину split-locks.

## Подводные камни

1. Случайное увеличение структуры на 1 байт добавлением `bool` флага: если структура была 64 байта, добавление флага превратит ее в 72 байта, снижая плотность кэша на треть!
2. Игнорирование упакованных битовых масок: вместо нескольких `bool` флагов используйте битовые флаги в одном `uint8`.

## На собеседовании

«Что такое Split Lock в ядре Linux и почему ядро замедляет процессы с расщепленными блокировками?»
Ответ: Split Lock возникает, когда атомарная инструкция (например, `LOCK CMPXCHG`) обращается к операнду, пересекающему границу двух кэш-линий. Чтобы гарантировать атомарность, процессор вынужден блокировать внешнюю шину памяти, останавливая работу всех остальных ядер. Ядро Linux начиная с версии 5.7 отслеживает такие инструкции через счетчики PMU и принудительно усыпляет процесс (`SIGBUS` или замедление `msleep`), чтобы защитить производительность облачной ноды.
