# Устранение False Sharing в Lock-Free кольцевых буферах (Ring Buffer)

## Условие

Спроектируйте высокопроизводительный lock-free кольцевой буфер (Disruptor pattern / Ring Buffer). Покажите, как расположение индексов producerHead и consumerTail в одной кэш-линии уничтожает производительность, и изолируйте их с помощью выравнивания.

### Исходная формулировка

**False sharing в ring buffers**: Ring buffer с producer и consumer indices в одной cache line — классический false sharing. Разделите их padding'ом.

## Теория

Кольцевой буфер без блокировок (**Lock-Free Single-Producer Single-Consumer / SPSC Ring Buffer**) — фундаментальный примитив для передачи сообщений между горутинами с минимальными задержками (микросекунды и субмикросекунды, как в LMAX Disruptor).

В наивной реализации буфера:
```go
type NaiveRingBuffer struct {
    head   uint64 // Индекс продюсера (пишет продюсер)
    tail   uint64 // Индекс консьюмера (пишет консьюмер)
    buffer [1024]any
}
```
* `head` и `tail` расположены по смещениям 0 и 8 байт, то есть находятся **в одной кэш-линии**.
* Продюсер непрерывно обновляет `head`, а консьюмер — `tail`.
* Происходит непрерывный **Cache Bouncing**: оба ядра тратят все ресурсы на пересылку кэш-линии по шине памяти, превращая lock-free алгоритм в медленный тормоз.

Решение: гарантированная изоляция индексов с отступом в 56 байт до и после каждого индекса.

## Решение по шагам

1. Реализуйте структуру `NaiveRing` без разделения кэш-линий.
2. Реализуйте структуру `PaddedRing`, где поля `head` и `tail` разнесены в разные 64-байтные строки.
3. Напишите многопоточный сценарий: один воркер генерирует события, второй — считывает.
4. Замерьте задержку и пропускную способность (миллионы сообщений в секунду).
5. Объясните роль хвостового padding для буфера сообщений.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

const BufferCap = 1024
const Mask = BufferCap - 1

type NaiveRing struct {
	head uint64
	tail uint64
	data [BufferCap]uint64
}

type PaddedRing struct {
	head uint64
	_    [56]byte // Изоляция head от tail
	tail uint64
	_    [56]byte // Изоляция tail от data
	data [BufferCap]uint64
}

func benchmarkPaddedRing(msgCount int) time.Duration {
	ring := new(PaddedRing)
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	// Producer
	go func() {
		defer wg.Done()
		for i := uint64(1); i <= uint64(msgCount); i++ {
			for {
				head := atomic.LoadUint64(&ring.head)
				tail := atomic.LoadUint64(&ring.tail)
				if head-tail < BufferCap {
					ring.data[head&Mask] = i
					atomic.StoreUint64(&ring.head, head+1)
					break
				}
				runtime.Gosched()
			}
		}
	}()

	// Consumer
	go func() {
		defer wg.Done()
		for i := uint64(1); i <= uint64(msgCount); i++ {
			for {
				head := atomic.LoadUint64(&ring.head)
				tail := atomic.LoadUint64(&ring.tail)
				if tail < head {
					val := ring.data[tail&Mask]
					_ = val
					atomic.StoreUint64(&ring.tail, tail+1)
					break
				}
				runtime.Gosched()
			}
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func main() {
	var naive NaiveRing
	var padded PaddedRing
	fmt.Printf("NaiveRing:  diff(tail - head) = %d байт (False Sharing!)\n",
		unsafe.Offsetof(naive.tail)-unsafe.Offsetof(naive.head))
	fmt.Printf("PaddedRing: diff(tail - head) = %d байт (Изоляция)\n",
		unsafe.Offsetof(padded.tail)-unsafe.Offsetof(padded.head))

	const msgs = 5_000_000
	cost := benchmarkPaddedRing(msgs)
	opsPerSec := float64(msgs) / cost.Seconds()
	fmt.Printf("Padded Ring Buffer: передано %d сообщений за %v (%.2f млн msg/sec)\n",
		msgs, cost, opsPerSec/1e6)
}
```

ℹ️ Изоляция указателей head и tail в кольцевом буфере предотвращает взаимную блокировку продюсера и консьюмера.

## Под капотом

В алгоритме SPSC кольцевого буфера продюсер непрерывно записывает `head` и читает `tail`, а консьюмер непрерывно записывает `tail` и читает `head`. Если они в одной строке кэша, любая запись продюсера отзывает права на чтение у консьюмера, и наоборот. Разделение полей на 64 байта гарантирует, что продюсер удерживает строку `head` в эксклюзивном кэше L1, а консьюмер читает ее через механизм snoop только при необходимости проверки свободного места.

## Подводные камни

1. Неверный расчет размера маски: если размер кольцевого буфера не является степенью двойки (`2^N`), операция взятия остатка `% BufferCap` требует инструкции деления `IDIV` (~40 тактов вместо 1 такта для побитового `& Mask`).
2. Недостаточный padding: если компилятор переупорядочит поля структуры, смещения могут измениться.

## На собеседовании

Паттерн LMAX Disruptor — золотой стандарт Low Latency систем. Вопрос: «Почему LMAX Disruptor опережает каналы Go и Java BlockingQueue в 10–50 раз?». Ответ: предварительно выделенный кольцевой буфер (Zero Allocations), побитовая адресация по маске, отсутствие блокировок (только Relaxed/Acquire-Release атомики) и 64-байтный padding вокруг указателей sequence/head/tail.
