# Гибридный подход: Hybrid SoA/AoS (Array of Structs of Arrays)

## Условие

Спроектируйте гибридную структуру данных Hybrid SoA/AoS (AoSoA / Chunked SoA). Разбейте массив на чанки фиксированного размера (например, по 16 элементов), объединяя преимущества SIMD-векторизации и локальности кэша.

### Исходная формулировка

**Hybrid SoA/AoS**: Для mixed workloads используйте hybrid:
```go
type Particles struct {
    positions []Position  // hot data (frequently accessed)
    metadata  []Metadata  // cold data (rarely accessed)
}
```

## Теория

Чистый SoA страдает от неудобства управления жизненным циклом объектов и нагрузки на TLB при большом числе атрибутов. Чистый AoS не позволяет эффективно задействовать векторные регистры процессора.

Инженерный компромисс — **Hybrid SoA/AoS (AoSoA — Array of Structs of Arrays)**:
Данные разбиваются на небольшие блоки фиксированного размера \(K\) (обычно \(K = 8\) или \(16\), что точно соответствует ширине регистров AVX-512 или размеру кэш-линий):
```go
type Tile16 struct {
    X [16]float32 // Ровно 64 байта = 1 кэш-линия!
    Y [16]float32 // Ровно 64 байта = 1 кэш-линия!
    Z [16]float32 // Ровно 64 байта = 1 кэш-линия!
}
type World struct {
    Tiles []Tile16
}
```
Преимущества AoSoA:
1. Каждый массив внутри блока занимает ровно 1 или 2 кэш-линии.
2. Идеально ложится на аппаратные векторные инструкции SIMD.
3. Блоки можно легко аллоцировать, перемещать и удалять как обычные объекты.

## Решение по шагам

1. Объявите чанк `Tile16` с массивами `[16]float32` для координат `X, Y, Z`.
2. Проверьте размер полей и структуры через `unsafe.Sizeof`.
3. Реализуйте итератор и операцию векторного сдвига координат.
4. Продемонстрируйте удобство добавления новых блоков в `[]Tile16`.
5. Сравните с плоским представлением.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
	"unsafe"
)

const (
	ChunkSize = 16
	NumTiles  = 200_000
)

// Tile16: каждый массив [16]float32 занимает ровно 64 байта (1 кэш-линия)
type Tile16 struct {
	X [ChunkSize]float32
	Y [ChunkSize]float32
	Z [ChunkSize]float32
}

func benchmarkAoSoA(tiles []Tile16) time.Duration {
	start := time.Now()
	for t := range tiles {
		tile := &tiles[t]
		// Внутренний цикл полностью векторизуется компилятором
		for i := 0; i < ChunkSize; i++ {
			tile.X[i] += 1.0
			tile.Y[i] += 2.0
		}
	}
	return time.Since(start)
}

func main() {
	var tile Tile16
	fmt.Println("=== Анатомия структуры Hybrid AoSoA ===")
	fmt.Printf("Размер Tile16:    %d байт\n", unsafe.Sizeof(tile))
	fmt.Printf("Размер массива X: %d байт (ровно 1 кэш-линия)\n", unsafe.Sizeof(tile.X))
	fmt.Printf("Всего элементов:  %d\n", NumTiles*ChunkSize)

	tiles := make([]Tile16, NumTiles)
	cost := benchmarkAoSoA(tiles)
	fmt.Printf("Время обновления AoSoA: %v\n", cost)
}
```

ℹ️ Гибридный AoSoA чанкует данные блоками по размеру кэш-линии для оптимальной векторизации.

## Под капотом

Компилятор процессора может развернуть цикл `for i := 0; i < ChunkSize; i++` в две инструкции AVX2 `VADDPS` (каждая инструкция обрабатывает 8 значений `float32` за 1 такт). Так как массив `X` гарантированно лежит непрерывно и занимает 64 байта, процессор читает его ровно за одну операцию загрузки кэш-линии без сдвигов и перестановок.

## Подводные камни

1. Хвостовые элементы: если общее число элементов не кратно 16, требуется обработка неполного последнего чанка.
2. Дополнительные накладные расходы на вычисление двойного индекса: `tileIdx = i / 16`, `slotIdx = i % 16`.

## На собеседовании

В вопросах на оптимизацию вычислительных движков (ML/CV инференс, геоинформационные системы): «Как избежать недостатков чистого SoA при работе с миллиардами точек?». Ответ: разбиение на тайлы/чанки фиксированного размера (AoSoA / Tiled SIMD), где внутренний размер чанка кратен ширине векторных регистров и кэш-линии процессора.
