# Микро-бенчмаркинг False Sharing: замер кратного падения производительности

## Условие

Напишите каноничный микро-бенчмарк с testing.B, сравнивающий BenchmarkFalseSharing и BenchmarkNoFalseSharing. Докажите на практике деградацию производительности в 5–20 раз при параллельной работе горутин на нескольких ядрах процессора.

### Исходная формулировка

**False sharing benchmarks**: Напишите бенчмарк, который измеряет влияние false sharing:
```go
func BenchmarkFalseSharing(b *testing.B) { ... }
func BenchmarkNoFalseSharing(b *testing.B) { ... }
```
Разница должна быть в 5-20x.

## Теория

Для строгого доказательства деградации производительности в Go используется встроенный фреймворк тестирования `testing.B` с методом `b.RunParallel()`.

Метод `pb.Next()` запускает пул горутин, распределенных по всем доступным виртуальным процессорам `GOMAXPROCS`. Если тестируемая структура имеет поля без разделения кэш-линий:
```go
type FalseSharingStruct struct {
    counters [GOMAXPROCS]uint64
}
```
все \(P\) ядер непрерывно пересылают одну и ту же строку кэша туда и обратно (Cache Ping-Pong).

При использовании выровненной структуры:
```go
type NoFalseSharingStruct struct {
    counters [GOMAXPROCS]struct {
        val uint64
        _   [56]byte
    }
}
```
каждое ядро монопольно владеет своей кэш-линией, и бенчмарк масштабируется линейно с ростом числа ядер.

## Решение по шагам

1. Создайте файл `benchmark_test.go`.
2. Реализуйте функцию `BenchmarkFalseSharing` с параллельными инкрементами среза невыровненных счетчиков.
3. Реализуйте функцию `BenchmarkNoFalseSharing` с выровненными элементами.
4. Добавьте запускаемый `main.go`, позволяющий выполнить бенчмарк автономно без необходимости вызова `go test`.
5. Проанализируйте метрику `ns/op`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type UnalignedArray struct {
	values [16]uint64
}

type AlignedItem struct {
	value uint64
	_     [56]byte
}

type AlignedArray struct {
	values [16]AlignedItem
}

func runBenchmark(name string, workers int, iters int, fn func(workerID int)) time.Duration {
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		id := w
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				fn(id)
			}
		}()
	}
	wg.Wait()
	cost := time.Since(start)
	nsPerOp := float64(cost.Nanoseconds()) / float64(workers*iters)
	fmt.Printf("%-30s: общее время = %v, latency = %.2f ns/op\n", name, cost, nsPerOp)
	return cost
}

func main() {
	workers := runtime.NumCPU()
	if workers > 16 {
		workers = 16
	}
	const iters = 10_000_000

	fmt.Printf("Запуск бенчмарка: %d воркеров (GOMAXPROCS=%d), по %d итераций\n\n",
		workers, runtime.GOMAXPROCS(0), iters)

	var unaligned UnalignedArray
	tFalse := runBenchmark("BenchmarkFalseSharing", workers, iters, func(id int) {
		atomic.AddUint64(&unaligned.values[id], 1)
	})

	var aligned AlignedArray
	tNoFalse := runBenchmark("BenchmarkNoFalseSharing", workers, iters, func(id int) {
		atomic.AddUint64(&aligned.values[id].value, 1)
	})

	if tNoFalse < tFalse {
		fmt.Printf("\nРезультат: Выровненный массив быстрее в %.2fx раз!\n",
			float64(tFalse)/float64(tNoFalse))
	}
}
```

ℹ️ Параллельный микро-бенчмарк демонстрирует кратный выигрыш от устранения Cache Line Bouncing.

## Под капотом

В `BenchmarkFalseSharing` время на операцию вырастает с 2-3 нс (типичное время атомарного сложения в локальном L1) до 20-50 нс. Это обусловлено тем, что при каждом столкновении контроллер кэша ядра переводит строку в состояние Invalid, выполняет snoop-запрос по шине межпроцессорного соединения и ждет, пока другое ядро сбросит свои модифицированные данные в L3. В выровненной структуре snoop-запросы полностью отсутствуют.

## Подводные камни

1. Запуск бенчмарка на одноядерной виртуальной машине: если `runtime.NumCPU() == 1`, False Sharing физически не может проявиться, так как нет конкурирующих физических ядер.
2. Недостаточное количество итераций: бенчмарк должен длиться не менее 1-2 секунд, чтобы нивелировать погрешности шедулинга ОС.
