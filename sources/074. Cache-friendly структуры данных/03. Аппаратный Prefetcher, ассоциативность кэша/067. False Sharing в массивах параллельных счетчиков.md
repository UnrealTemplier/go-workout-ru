# False Sharing в массивах параллельных счетчиков (Counters Array)

## Условие

Реализуйте массив параллельных счетчиков для сбора статистики по потокам. Сравните производительность невыровненного массива counters []uint64 и массива со структурным выравниванием элементов. Объясните поведение кэша при масштабировании количества ядер.

### Исходная формулировка

**False sharing в counters array**: Массив counters, где каждый thread пишет в свой элемент. Без padding — false sharing. С padding — нет.

## Теория

При проектировании многопоточных систем (распределенные метрики, rate limiter, concurrent ring buffer) часто создается массив счетчиков:
```go
var counters [64]uint64
```
Каждый поток \(i\) пишет исключительно в свою ячейку `counters[i]`. С точки зрения программиста данные абсолютно независимы, и блокировки не требуются.

Однако с точки зрения процессора:
* Каждый элемент `uint64` занимает 8 байт.
* В одной 64-байтной кэш-линии умещается **8 независимых счетчиков**!
* Ядра 0, 1, 2, 3, 4, 5, 6, 7 постоянно выбивают кэш-линию друг у друга. Чем больше ядер задействовано в вычислениях, тем медленнее работает система (обратное масштабирование / Negative Scalability).

## Решение по шагам

1. Создайте массив из 16 невыровненных счетчиков `[16]uint64`.
2. Создайте массив из 16 выровненных структур `type AlignedCounter struct { val uint64; _ [56]byte }`.
3. Запустите 16 горутин, каждая из которых выполняет 20 000 000 инкрементов своего счетчика.
4. Замерьте время выполнения для обоих вариантов.
5. Продемонстрируйте проверку адресов каждого счетчика.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

const Threads = 8
const Iters = 15_000_000

type UnalignedCounters [Threads]uint64

type PaddedCounter struct {
	Value uint64
	_     [56]byte // Дополняем до 64 байт
}

type PaddedCounters [Threads]PaddedCounter

func main() {
	var unaligned UnalignedCounters
	var padded PaddedCounters

	fmt.Println("=== Адресация элементов массивов счетчиков ===")
	for i := 0; i < 2; i++ {
		fmt.Printf("Unaligned[%d] addr = %p, diff = %d байт\n",
			i, &unaligned[i], uintptr(unsafe.Pointer(&unaligned[i]))-uintptr(unsafe.Pointer(&unaligned[0])))
	}
	for i := 0; i < 2; i++ {
		fmt.Printf("Padded[%d]    addr = %p, diff = %d байт\n",
			i, &padded[i], uintptr(unsafe.Pointer(&padded[i]))-uintptr(unsafe.Pointer(&padded[0])))
	}

	// 1. Тест невыровненного массива
	var wg1 sync.WaitGroup
	wg1.Add(Threads)
	start1 := time.Now()
	for t := 0; t < Threads; t++ {
		id := t
		go func() {
			defer wg1.Done()
			for i := 0; i < Iters; i++ {
				atomic.AddUint64(&unaligned[id], 1)
			}
		}()
	}
	wg1.Wait()
	d1 := time.Since(start1)
	fmt.Printf("\nНевыровненный массив (False Sharing): %v\n", d1)

	// 2. Тест выровненного массива
	var wg2 sync.WaitGroup
	wg2.Add(Threads)
	start2 := time.Now()
	for t := 0; t < Threads; t++ {
		id := t
		go func() {
			defer wg2.Done()
			for i := 0; i < Iters; i++ {
				atomic.AddUint64(&padded[id].Value, 1)
			}
		}()
	}
	wg2.Wait()
	d2 := time.Since(start2)
	fmt.Printf("Выровненный массив (Padded 64B):      %v\n", d2)

	if d2 < d1 {
		fmt.Printf("Ускорение: %.2fx раз!\n", float64(d1)/float64(d2))
	}
}
```

ℹ️ Разнос счетчиков по разным кэш-линиям устраняет негативное масштабирование на многоядерных процессорах.

## Под капотом

Разница адресов между `unaligned[0]` и `unaligned[1]` составляет ровно 8 байт. Они гарантированно попадают в одну и ту же 64-байтную строку кэша (младшие 6 бит виртуального адреса совпадают по номеру строки кэша). В `PaddedCounters` разница адресов составляет ровно 64 байта, что гарантирует независимость строковых контроллеров L1 кэша каждого ядра.

## Подводные камни

1. Забытый padding на границе массива: если массив размещен в куче, первый элемент может оказаться в одной строке с заголовком слайса или соседним объектом.
2. Использование неатомарных операций: хотя padding решает проблему False Sharing, если к ячейке обращается более одной горутины, атомарные операции или мьютексы по-прежнему обязательны.

## На собеседовании

Вопрос: «Что происходит со скоростью выполнения кода при переходе с 4 ядер на 32 ядра в невыровненном параллельном массиве?». Ответ: закон Амдала в негативной форме — скорость не просто перестает расти, а падает в несколько раз из-за лавинообразного роста когерентного трафика по шине межпроцессорных соединений.
