# False Sharing в хэш-таблицах с открытой адресацией (Open Addressing)

## Условие

Исследуйте влияние False Sharing на хэш-таблицы с открытой адресацией и линейным пробированием (Linear Probing). Реализуйте чанкинг слотов (Slot Chunking) для защиты соседних слотов от межъядерной инвалидации.

### Исходная формулировка

**False sharing в hash tables**: Open addressing hash tables могут иметь false sharing между adjacent slots. Используйте separate chaining или padding.

## Теория

Хэш-таблицы с **открытой адресацией (Open Addressing)** и **линейным пробированием (Linear Probing)** исключительно эффективны для кэша при однопоточном доступе: все слоты лежат непрерывно в одном плоском массиве, и поиск коллизии идет последовательно по соседним ячейкам.

Однако в конкурентной среде (Concurrent Open Addressing / Swiss Tables) линейное пробирование становится источником жестокого False Sharing:
* Если ядро 1 вставляет ключ в слот \(i\), а ядро 2 ищет или пишет в слот \(i+1\), обе операции попадают в одну 64-байтную кэш-линию.
* При высокой степени заполнения (Load Factor > 0.7) возникают кластеры (Primary Clustering), где цепочки коллизий разрастаются, вызывая постоянную инвалидацию смежных записей.

Решение: **чанкинг слотов (Chunking/Bucket Groups)**. Слоты группируются в блоки фиксированного размера (например, группа из 8 слотов с метаданными), точно равные 64 байтам. Вся группа читается и проверяется параллельно (включая SIMD), а блокировки или атомарные флаги изолируются на границе чанка.

## Решение по шагам

1. Создайте плоский массив слотов `UnchunkedTable`, где каждый слот занимает 16 байт (хеш + значение).
2. Создайте структуру `ChunkedGroup`, размер которой строго равен 64 байтам (1 кэш-линия), вмещающую 7 слотов и управляющий байтовый заголовок.
3. Смоделируйте конкурентное обновление соседних слотов разными горутинами.
4. Замерьте количество операций в секунду.
5. Покажите преимущества локализации поиска внутри одной кэш-линии.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

type FlatSlot struct {
	Key   uint64
	Value uint64
}

// 64-байтный чанк (Swiss-table style chunk)
type CacheAlignedChunk struct {
	Control [8]byte    // 8 байт: метаданные / H2-хэши для фильтрации
	_       [8]byte    // выравнивание
	Slots   [3]FlatSlot // 3 * 16 = 48 байт. Итого: 8 + 8 + 48 = 64 байта
}

func benchmarkFlatContention(iters int) time.Duration {
	// 4 слота в одной кэш-линии (4 * 16 = 64B)
	var slots [4]FlatSlot
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	// Воркер 0 пишет в слот 0
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&slots[0].Value, 1)
		}
	}()

	// Воркер 1 пишет в слот 1 (та же кэш-линия!)
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&slots[1].Value, 1)
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func benchmarkChunkedContention(iters int) time.Duration {
	// Два чанка, каждый изолирован в своей кэш-линии
	var chunks [2]CacheAlignedChunk
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	// Воркер 0 пишет в чанк 0
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&chunks[0].Slots[0].Value, 1)
		}
	}()

	// Воркер 1 пишет в чанк 1 (изолированная кэш-линия)
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&chunks[1].Slots[0].Value, 1)
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func main() {
	var c CacheAlignedChunk
	fmt.Printf("Размер CacheAlignedChunk: %d байт (ровно 1 кэш-линия)\n", unsafe.Sizeof(c))

	const iters = 20_000_000
	tFlat := benchmarkFlatContention(iters)
	fmt.Printf("Соседние слоты (False Sharing):   %v\n", tFlat)

	tChunk := benchmarkChunkedContention(iters)
	fmt.Printf("Изолированные чанки (No Sharing): %v\n", tChunk)

	if tChunk < tFlat {
		fmt.Printf("Ускорение изоляции слотов: %.2fx\n", float64(tFlat)/float64(tChunk))
	}
}
```

ℹ️ Организация слотов хэш-таблицы в 64-байтные чанки предотвращает межъядерную инвалидацию соседних корзин.

## Под капотом

В современных хэш-таблицах (SwissTable в C++ Abseil и Go runtime map начиная с версии 1.24) бакеты проектируются ровно под размер кэш-линии (Group of 8/16 slots). Вся группа метаданных (H2 hash bits) помещается в 64-битную или 128-битную маску, которая загружается в регистр за одно чтение. Если совпадений нет, алгоритм переходит к следующему чанку без модификации промежуточных слотов.

## Подводные камни

1. Фрагментация памяти при неполном заполнении чанков.
2. Усложнение логики удаления элементов (Tombstones vs Robin Hood backward shift).

## На собеседовании

Вопрос: «Как устроена хэш-таблица в Go runtime (bmap) с точки зрения кэша?». Ответ: каждый бакет `bmap` содержит ровно 8 слотов (tophash[8] + 8 keys + 8 values + overflow pointer). Такой размер (около 128-256 байт) выбран для кратности размеру кэш-линий процессора, чтобы минимизировать промахи L1 при обходе корзины.
