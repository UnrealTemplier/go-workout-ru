# Структуры данных: Struct of Arrays (SoA) для SIMD и векторизации

## Условие

Реализуйте физическое моделирование частиц с использованием паттерна Struct of Arrays (SoA) вместо привычного Array of Structures (AoS). Покажите, как SoA обеспечивает плотную загрузку однотипных координат в кэш-линии для SIMD-векторизации.

### Исходная формулировка

**Struct of Arrays (SoA) для SIMD**: Для vectorized operations используйте SoA:
```go
type Particles struct {
    x []float32
    y []float32
    z []float32
}
```
Это позволяет SIMD обрабатывать 8 `x` координат одновременно.

## Теория

В традиционном объектно-ориентированном подходе используется **Array of Structures (AoS)**:
```go
type Particle struct {
    X, Y, Z    float32 // координаты
    Mass       float32 // масса
    ID         uint64  // идентификатор
    Name       string  // метаданные
}
var particles []Particle
```
Если алгоритму требуется обновить только координаты `X` всех частиц (например, \(X_{new} = X + V_x \cdot \Delta t\)), процессор вынужден загружать в кэш-линию всю структуру целиком (включая ненужные `Mass`, `ID`, `Name`). 75–90% пропускной способности памяти расходуется впустую!

Паттерн **Struct of Arrays (SoA)** организует данные по атрибутам:
```go
type ParticlesSoA struct {
    X []float32
    Y []float32
    Z []float32
}
```
Координаты `X` расположены в непрерывном массиве памяти. В одну 64-байтную кэш-линию помещается ровно **16 значений float32**. Это позволяет процессору загружать данные без мусора и обрабатывать по 8 или 16 чисел за такт с помощью SIMD-инструкций (AVX2 / AVX-512 / ARM Neon).

## Решение по шагам

1. Создайте представление `ParticleAoS` и срез на 1 000 000 элементов.
2. Создайте представление `ParticlesSoA` с отдельными срезами `X`, `Y`, `Z`.
3. Реализуйте функцию физического обновления координат \(X = X + 1.0\) для обоих представлений.
4. Измерьте время выполнения и эффективную пропускную способность памяти.
5. Объясните преимущества SoA для компилятора и векторных регистров.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const N = 5_000_000

// AoS: традиционный подход
type ParticleAoS struct {
	X, Y, Z  float32
	Mass     float32
	ID       uint64
	Flags    uint32
	Reserved uint32
}

// SoA: data-oriented подход
type ParticlesSoA struct {
	X []float32
	Y []float32
	Z []float32
}

func updateAoS(particles []ParticleAoS) time.Duration {
	start := time.Now()
	for i := range particles {
		particles[i].X += 0.5
	}
	return time.Since(start)
}

func updateSoA(x []float32) time.Duration {
	start := time.Now()
	for i := range x {
		x[i] += 0.5
	}
	return time.Since(start)
}

func main() {
	fmt.Printf("Аллокация %d частиц для бенчмарка...\n", N)

	aos := make([]ParticleAoS, N)
	soaX := make([]float32, N)
	soaY := make([]float32, N)
	soaZ := make([]float32, N)

	// Прогрев
	updateAoS(aos)
	updateSoA(soaX)

	tAoS := updateAoS(aos)
	fmt.Printf("AoS (Array of Structures): %v\n", tAoS)

	tSoA := updateSoA(soaX)
	fmt.Printf("SoA (Struct of Arrays):    %v\n", tSoA)

	if tSoA < tAoS {
		fmt.Printf("SoA быстрее в %.2fx раз благодаря 100%% плотности полезных данных в кэше!\n",
			float64(tAoS)/float64(tSoA))
	}
	_ = soaY
	_ = soaZ
}
```

ℹ️ SoA исключает загрузку неиспользуемых полей структуры в кэш-линию процессора.

## Под капотом

В структуре `ParticleAoS` размер равен 32 байтам. В одну 64-байтную кэш-линию помещается всего 2 частицы. При обновлении поля `X` процессор загружает 64 байта, из которых полезными являются только 8 байт (два `float32`). КПД кэша составляет всего 12.5%. В `ParticlesSoA` срез `X` содержит только координаты: все 64 байта кэш-линии заняты полезными данными (16 значений `float32`). КПД кэша равен 100%.

## Подводные камни

1. Ухудшение эргономики кода: нельзя передать одну частицу как объект `p := particles[i]`, приходится оперировать индексом `i` во множестве срезов.
2. Неудобство добавления и удаления элементов: добавление требует синхронного вызова `append` в каждый массив.

## На собеседовании

Вопрос от разработчиков геймдева и HighLoad-аналитики (ClickHouse, геймдев, физические движки): «Что такое Data-Oriented Design (DOD) и почему он вытесняет OOP в критических путях вычислений?». Ответ: DOD ставит во главу угла аппаратный лейаут памяти и кэш-линии процессора (AoS vs SoA), обеспечивая максимальный throughput данных через SIMD-конвейеры ЦПУ.
