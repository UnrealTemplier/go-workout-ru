# False Sharing во внутреннем рантайме Go (schedt и mcache)

## Условие

Исследуйте архитектуру рантайма Go (пакеты runtime/runtime2.go и runtime/mcache.go). Продемонстрируйте, как создатели языка Go предотвращают False Sharing между логическими процессорами P с помощью per-P структур (mcache, runq) и структурного выравнивания sys.CacheLineSize.

### Исходная формулировка

**False sharing в Go runtime**: Изучите, как Go runtime избегает false sharing в `schedt` (per-P scheduler state) и `mcache` (per-P memory cache).

## Теория

Внутри Go runtime планировщик GMP и аллокатор памяти проектировались под масштабирование на сотни процессорных ядер. Если бы глобальное состояние планировщика (`schedt`) или кэш аллокатора (`mcache`) использовали общие блокировки или находились в смежных ячейках памяти, производительность рантайма деградировала бы катастрофически.

Ключевые архитектурные решения рантайма Go:
1. **Децентрализация per-P**: каждый логический процессор `P` имеет собственную локальную очередь выполнения `runq [256]guintptr` и собственный кэш аллокаций `mcache`.
2. **Изоляция кэш-линий**: массив логических процессоров `allp []*p` ссылается на независимые структуры `p`, каждая из которых выровнена в памяти.
3. Внутренний тип `sys.CacheLineSize` (обычно 64 байта): в критических структурах используются неэкспортируемые поля-отступы `pad [sys.CacheLineSize]byte` для гарантии, что счетчики разных ядер не окажутся в одной кэш-линии.

Благодаря этому горутина на ядре 0 аллоцирует память из своего `mcache` и берет горутины из своего `runq` со 100% попаданием в L1-кэш без обращения к другим ядрам.

## Решение по шагам

1. Создайте модель `RuntimeArchitectureModel`, имитирующую структуру `p` и `mcache`.
2. Добавьте в структуру `Processor` выравнивание `_ [sysCacheLineSize - ...]byte`.
3. Создайте симулятор конкурентной работы воркеров, где каждый воркер работает исключительно со своим `P`-контекстом.
4. Продемонстрируйте сравнение с наивной реализацией с общим состоянием.
5. Выведите смещения и размеры внутренних структур.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
	"unsafe"
)

const CacheLineSize = 64

// MockMCache имитирует per-P кэш аллокатора Go
type MockMCache struct {
	allocCount uint64
	tinyBytes  uintptr
}

// ProcessorNode имитирует runtime структуру p с защитой от False Sharing
type ProcessorNode struct {
	id     int32
	mcache MockMCache
	_      [CacheLineSize - (unsafe.Sizeof(MockMCache{})+4)%CacheLineSize]byte
}

func main() {
	var p ProcessorNode
	fmt.Printf("Размер ProcessorNode: %d байт (кратен %d)\n",
		unsafe.Sizeof(p), CacheLineSize)
	fmt.Printf("Смещение mcache:      %d\n", unsafe.Offsetof(p.mcache))

	const numP = 8
	var procs [numP]ProcessorNode
	for i := 0; i < numP; i++ {
		procs[i].id = int32(i)
	}

	const iters = 10_000_000
	var wg sync.WaitGroup
	wg.Add(numP)

	start := time.Now()
	for i := 0; i < numP; i++ {
		procID := i
		go func() {
			defer wg.Done()
			pRef := &procs[procID]
			for j := 0; j < iters; j++ {
				// Работа с локальным mcache без локов и без False Sharing
				pRef.mcache.allocCount++
				pRef.mcache.tinyBytes += 16
			}
		}()
	}
	wg.Wait()

	fmt.Printf("Выполнено %d изолированных операций за %v\n",
		numP*iters, time.Since(start))
}
```

ℹ️ Per-P архитектура рантайма Go гарантирует изоляцию кэш-линий между ядрами.

## Под капотом

В исходном коде `src/runtime/runtime2.go` структура `p` содержит локальные очереди `runqhead`, `runqtail`, `runq [256]guintptr` и ссылку на `mcache`. При операции Work Stealing ядро-ворхив обращается к чужому `P` только тогда, когда его собственный `runq` опустел. 99% времени ядро оперирует локальными данными в L1/L2 кэше, исключая синхронизацию по шине памяти.

## Подводные камни

1. Масштабирование глобального мьютекса: если per-P структуры периодически обращаются к глобальному `sched.lock`, это создает узкое место (Stop-The-World, `sysmon`, GC start).
2. Выравнивание указателей: создание среза указателей `[]*ProcessorNode` не гарантирует смежности объектов, но гарантирует разделение кэш-линий.
