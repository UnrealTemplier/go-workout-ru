# Эмпирическое определение размера кэш-линии процессора

## Условие

Напишите программу на Go, которая экспериментально вычисляет размер кэш-линии процессора (Cache Line Size) путем измерения задержки доступа к элементам большого массива при варьировании шага (stride) от 4 до 256 байт.

### Исходная формулировка

**Cache line size detection**: Напишите код, который определяет cache line size через empirical testing (measure latency vs stride).

## Теория

Физический размер кэш-линии процессора (обычно 64 байта на архитектурах x86 и ARM) можно обнаружить программно без вызова системных API ядра (вроде `sysconf` или `cpuid`).

Методика **Stride-тестирования**:
* Выделяется массив, значительно превышающий размер L1 кэша (например, 16–64 МБ).
* Выполняется циклическая модификация или чтение элементов массива с фиксированным шагом \(S\) (stride):
  $$Index_{k+1} = Index_k + S$$
* Когда шаг \(S\) меньше размера кэш-линии (например, 4, 8, 16, 32 байта), несколько последовательных обращений попадают в одну и ту же кэш-линию, и среднее время на одну операцию мало.
* Как только шаг \(S\) достигает или превышает размер кэш-линии (\(S \ge 64\) байта), **каждое обращение** гарантированно вызывает чтение новой кэш-линии из L2/L3/DRAM. На графике «Задержка / Шаг» наблюдается резкий излом (knee-point) на отметке 64 байта.

## Решение по шагам

1. Создайте плоский массив байтов размером 16 МБ.
2. Реализуйте функцию `measureStride(data []byte, stride int)`, выполняющую фиксированное число случайных или последовательных скачков.
3. Прогоните замеры для шагов \(S \in [8, 16, 32, 48, 64, 96, 128, 192, 256]\).
4. Рассчитайте наносекунды на одну операцию (`ns/op`).
5. Зафиксируйте скачок задержки на границе 64 байт.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const BufferSize = 16 * 1024 * 1024 // 16 МБ (превышает L1/L2)
const Iterations = 10_000_000

func measureLatency(buf []byte, stride int) float64 {
	length := len(buf)
	mask := length - 1 // BufferSize степень двойки

	start := time.Now()
	idx := 0
	var dummy byte
	for i := 0; i < Iterations; i++ {
		dummy += buf[idx]
		idx = (idx + stride) & mask
	}
	_ = dummy
	cost := time.Since(start)
	return float64(cost.Nanoseconds()) / float64(Iterations)
}

func main() {
	fmt.Println("=== Эмпирическое детектирование размера кэш-линии ЦПУ ===")
	buf := make([]byte, BufferSize)
	for i := range buf {
		buf[i] = byte(i)
	}

	strides := []int{8, 16, 32, 48, 64, 80, 96, 128, 192, 256}
	fmt.Printf("%-10s | %-15s | %-20s\n", "Stride (B)", "Latency (ns/op)", "Визуализация")
	fmt.Println("---------------------------------------------------------")

	for _, s := range strides {
		lat := measureLatency(buf, s)
		bars := int(lat * 8)
		barStr := ""
		for b := 0; b < bars; b++ {
			barStr += "█"
		}
		fmt.Printf("%-10d | %-15.2f | %s\n", s, lat, barStr)
	}
	fmt.Println("\nВывод: Задержка стабилизируется на плато при stride >= 64 байт (размер кэш-линии).")
}
```

ℹ️ Экспериментальный замер скачка задержки выявляет физический размер кэш-линии ЦПУ.

## Под капотом

Когда шаг равен 8 байтам, при чтении 64 байт процессор выполняет 1 кэш-промах и 7 попаданий в L1 (Cache Hits). Среднее время составляет \(t_{avg} = \frac{t_{miss} + 7 \times t_{hit}}{8}\). Когда шаг становится \(\ge 64\) байтам, каждое чтение попадает в новую кэш-линию, и среднее время скачкообразно вырастает до полного \(t_{miss}\). Начиная с 64 байт задержка выходит на плато.

## Подводные камни

1. Аппаратный префетчер может замаскировать задержку при строго последовательном шаге. Чтобы увидеть «чистую» латентность DRAM, иногда используют псевдослучайные переходы внутри страниц памяти.
2. Влияние кэша L3: буфер должен превышать L2 кэш ядра (обычно 1–2 МБ), иначе данные поместятся в L2, и скачок будет менее выражен.

## На собеседовании

Вопрос на понимание аппаратной архитектуры: «Как узнать размер кэш-линии в Linux без root-прав?». Ответ: системный путь `/sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size`, вызов `sysconf(_SC_LEVEL1_DCACHE_LINESIZE)` или микро-бенчмарк с переменным шагом (stride test).
