# Кэш-локальность и пул объектов (sync.Pool Cache Locality)

## Условие

Докажите на микро-бенчмарках, почему sync.Pool работает на порядки быстрее классических мьютексных очередей буферов: покажите распределение объектов по виртуальным процессорам P и работу с теплыми данными в L1/L2 кэше текущего ядра.

### Исходная формулировка

**Пул объектов (sync.Pool Cache Locality)**: Докажи на бенчмарках, почему `sync.Pool` работает так быстро: "под капотом" каждый `P` (виртуальный процессор Go) имеет свой собственный приватный пул, к которому обращается без блокировок, и эти объекты "теплые" (уже лежат в кэше ядра).

## Теория

Высокая скорость `sync.Pool` обусловлена не только отсутствием аллокаций в куче, но и исключительной **аппаратной кэш-локальностью**:

1. **Теплый кэш (Warm Cache)**: когда горутина на ядре 2 возвращает объект через `pool.Put(buf)`, буфер `buf` физически остается в L1/L2 кэше ядра 2. При следующем запросе `pool.Get()` на том же ядре горутина получает тот же самый теплый буфер. Чтение и запись в него происходят с задержкой 1–4 такта.
2. **Отсутствие межъядерной миграции**: в наивном пуле на `sync.Mutex` буферы циркулируют между всеми ядрами. Если ядро 0 положило буфер, а ядро 7 его забрало, ядро 7 получает промах кэша и тянет данные через межъядерную шину.
3. **Per-P Lock-Free доступ**: приватный слот `poolLocal.private` модифицируется без единой атомарной инструкции.

## Решение по шагам

1. Реализуйте наивный потокобезопасный пул `MutexPool` на основе среза и `sync.Mutex`.
2. Создайте аналогичный пул на основе `sync.Pool`.
3. Запустите параллельный бенчмарк (например, 8 горутин, каждая берет буфер 4 КБ, заполняет его и возвращает обратно).
4. Замерьте среднее время одной операции `Get + Use + Put`.
5. Проанализируйте эффект теплого кэша.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type MutexPool struct {
	mu    sync.Mutex
	items [][]byte
}

func (p *MutexPool) Get() []byte {
	p.mu.Lock()
	defer p.mu.Unlock()
	if len(p.items) == 0 {
		return make([]byte, 4096)
	}
	item := p.items[len(p.items)-1]
	p.items = p.items[:len(p.items)-1]
	return item
}

func (p *MutexPool) Put(b []byte) {
	p.mu.Lock()
	p.items = append(p.items, b)
	p.mu.Unlock()
}

func benchmarkMutexPool(workers, iters int) time.Duration {
	pool := &MutexPool{}
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				b := pool.Get()
				b[0] = byte(i)
				b[4095] = byte(i)
				pool.Put(b)
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func benchmarkSyncPool(workers, iters int) time.Duration {
	pool := &sync.Pool{
		New: func() any {
			return make([]byte, 4096)
		},
	}
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < iters; i++ {
				b := pool.Get().([]byte)
				b[0] = byte(i)
				b[4095] = byte(i)
				pool.Put(b)
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	const workers = 8
	const iters = 2_000_000

	fmt.Printf("Сравнение пулов: %d горутин, %d итераций с 4 КБ буферами\n", workers, iters)

	tMutex := benchmarkMutexPool(workers, iters)
	fmt.Printf("MutexPool (общий замок + Cache Bouncing): %v\n", tMutex)

	tSync := benchmarkSyncPool(workers, iters)
	fmt.Printf("sync.Pool (Per-P очереди + Warm Cache):    %v\n", tSync)

	if tSync < tMutex {
		fmt.Printf("sync.Pool быстрее в %.2fx раз!\n", float64(tMutex)/float64(tSync))
	}
}
```

ℹ️ sync.Pool обеспечивает привязку горячих буферов к L1-кэшу конкретного ядра процессора.

## Под капотом

В `MutexPool` каждое обращение к мьютексу инвалидирует строку состояния мьютекса в кэше других ядер, а возврат буфера перемешивает указатели между ядрами, разрушая пространственную локальность L1/L2. В `sync.Pool` вызов `Get()` забирает буфер из `p.private` текущего логического процессора P. Так как P закреплен за ядром M, этот буфер только что использовался этим же ядром и находится на вершине стека кэш-памяти L1.

## Подводные камни

1. Сохранение буферов гигантского размера в `sync.Pool`: если в пул положить слайс на 50 МБ, он вытеснит все полезные данные из L3 кэша всех ядер. Рекомендуется сбрасывать буферы с емкостью выше допустимого порога (`if cap(b) > maxCap`).
2. Очистка пула при GC: `sync.Pool` не заменяет долговременный кэш соединений или структур.

## На собеседовании

В сетевых серверах (Ozon fasthttp / gRPC gateway): «Как оптимизировать аллокации сетевых буферов для обработки 1 000 000 RPS?». Ответ: использовать `sync.Pool` для буферов фиксированного размера, ограничивая максимальный `cap`, чтобы не раздувать рабочий набор страниц (working set) и удерживать буферы в кэше L2/L3.
