# Матричный бенчмарк 10 000 x 10 000: феномен Column-Major деградации

## Условие

Напишите двойной цикл обхода квадратной матрицы размером 10 000 x 10 000 элементов типа float64 (~762 МБ памяти). Сравните обход matrix[i][j] и matrix[j][i] на реальном бенчмарке. Объясните колоссальную разницу во времени с точки зрения кэшей L1, L2, L3 и TLB.

### Исходная формулировка

**Column-major vs Row-major**: Напиши двойной цикл для обхода двумерного массива (матрицы 10000x10000). В первом бенчмарке обходи `matrix[i][j]` (по строкам), во втором — `matrix[j][i]` (по колонкам). Пойми, почему второй вариант медленнее в десятки раз.

## Теория

Матрица размером \(10\,000 \times 10\,000\) элементов `float64` занимает:
$$10\,000 \times 10\,000 \times 8 \text{ байт} = 800\,000\,000 \text{ байт} \approx 762.9 \text{ МБ}$$
Этот объем многократно превышает размер L1 (32–48 КБ), L2 (1–2 МБ) и даже L3 кэша современных серверных процессоров (32–128 МБ).

При обходе **Row-Major** (`[i][j]`):
* Элементы читаются строго последовательно. Каждые 64 байта (8 элементов `float64`) требуют всего 1 обращения к кэшу, остальные 7 берутся из L1.
* Аппаратный Prefetcher непрерывно загружает страницы памяти вперед.
* TLB (Translation Lookaside Buffer) кэширует трансляцию адресов виртуальной памяти: на одной 4-килобайтной странице умещается 512 элементов.

При обходе **Column-Major** (`[j][i]`):
* Шаг между последовательными чтениями составляет \(10\,000 \times 8 = 80\,000\) байт (~78 КБ).
* Каждый шаг обращается к **новой странице памяти**! Это вызывает катастрофический **TLB Thrashing** (вытеснение буфера трансляции страниц) и гарантированный Cache Miss в L1, L2 и L3. Процессор 98% времени простаивает в ожидании шины DRAM.

## Решение по шагам

1. Выделите плоский срез `data := make([]float64, 10000*10000)` в куче.
2. Реализуйте две функции с семантикой `matrix[i][j]` и `matrix[j][i]`.
3. Запустите замер времени выполнения для обеих функций.
4. Продемонстрируйте разницу в пропускной способности (GB/s).
5. Объясните влияние размера страницы виртуальной памяти и объема TLB.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const Dim = 10_000

func main() {
	totalElements := Dim * Dim
	sizeMB := float64(totalElements*8) / (1024 * 1024)
	fmt.Printf("Аллокация матрицы %dx%d (%.2f МБ)...\n", Dim, Dim, sizeMB)

	// Выделяем непрерывную память
	matrix := make([]float64, totalElements)
	for i := 0; i < totalElements; i += 1000 {
		matrix[i] = 1.0
	}

	fmt.Println("1. Запуск Row-Major обхода (последовательное чтение памяти)...")
	startRow := time.Now()
	var sumRow float64
	for i := 0; i < Dim; i++ {
		rowOffset := i * Dim
		for j := 0; j < Dim; j++ {
			sumRow += matrix[rowOffset+j]
		}
	}
	dRow := time.Since(startRow)
	fmt.Printf("Row-Major: время = %v, сумма = %.0f\n", dRow, sumRow)

	fmt.Println("2. Запуск Column-Major обхода (шаг 80 КБ, промах кэша и TLB)...")
	// Ограничиваемся первыми 2000 строками для Column-Major, чтобы не ждать минуту
	const testCols = 2000
	startCol := time.Now()
	var sumCol float64
	for j := 0; j < testCols; j++ {
		for i := 0; i < Dim; i++ {
			sumCol += matrix[i*Dim+j]
		}
	}
	dColPart := time.Since(startCol)
	// Экстраполяция на полный объем
	dColEstimated := time.Duration(float64(dColPart) * (float64(Dim) / float64(testCols)))
	fmt.Printf("Column-Major (2000 колонок): %v (расчетное полное: ~%v)\n", dColPart, dColEstimated)

	ratio := float64(dColEstimated) / float64(dRow)
	fmt.Printf("\nВывод: Column-Major медленнее в ~%.1fx раз из-за L1/L2/L3 и TLB Misses!\n", ratio)
}
```

ℹ️ Экстремальный контраст производительности при выходе за пределы размера L3-кэша и емкости TLB.

## Под капотом

Процессор x86_64 имеет L1 DTLB (Data Translation Lookaside Buffer) всего на 64 записи (на 4 КБ страницах). При шаге в 80 КБ каждое обращение к ячейке памяти `matrix[i*Dim + j]` попадает в совершенно новую 4 КБ страницу памяти. Так как 10 000 страниц не помещаются ни в L1 DTLB (64 записи), ни в L2 STLB (1536 записей), процессор выполняет аппаратный обход таблиц страниц (Page Table Walk в 4-5 уровней) на КАЖДОМ шаге, что приводит к задержке в сотни тактов.

## Подводные камни

1. Попытка выделить `[10000][10000]float64` на стеке: стек горутины в Go ограничен (по умолчанию 1 ГБ на 64-бит, начальный 2-4 КБ), поэтому такие структуры обязаны создаваться через `make` в куче.
2. Зависание тестов в CI: полный Column-Major обход на 10 000 может занять от 10 до 40 секунд на слабых серверах.
