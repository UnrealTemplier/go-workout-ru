# False Sharing в древовидных структурах (B-Tree, SkipList)

## Условие

Исследуйте возникновение False Sharing при параллельных операциях в древовидных структурах данных (деревья поиска, Skip List). Спроектируйте узел B-дерева так, чтобы блокировка узла или счетчик ключей не находились в одной кэш-линии с часто читаемыми указателями потомков.

### Исходная формулировка

**False sharing в tree structures**: В B-tree или skip list parent и child nodes могут быть в одной cache line. Это вызывает false sharing при concurrent updates.

## Теория

В конкурентных деревьях поиска (B-Tree, SkipList, ART-tree) часто применяется протокол поузловой блокировки (Hand-over-hand Locking / Crabbing) или оптимистичные блокировки с версионированием (Optimistic Lock Coupling).

Узел дерева обычно содержит:
1. Заголовок узла (счетчик элементов `numKeys`, версия `version` или `sync.RWMutex`).
2. Массив ключей.
3. Массив указателей на детей.

Если заголовок узла (который активно пишется при модификации) лежит в одной 64-байтной кэш-линии с первыми ключами или указателями, читающие горутины будут непрерывно получать промахи кэша (Cache Misses) даже при отсутствии фактического логического конфликта данных.

Паттерн оптимизации: разделение горячих полей записи (Hot Write: мьютекс/версия) и горячих полей чтения (Hot Read: массив ключей) по разным кэш-линиям с помощью padding.

## Решение по шагам

1. Спроектируйте наивный узел дерева `NaiveNode`, где мьютекс и массив ключей расположены вперемешку.
2. Спроектируйте оптимизированный узел `OptimizedBTreeNode`, где метаданные блокировки отделены от массива указателей и ключей 64-байтным отступом.
3. Смоделируйте сценарий, когда одна горутина периодически обновляет метаданные узла, а параллельные горутины непрерывно читают массив ключей.
4. Замерьте задержку чтения ключей в обоих случаях.
5. Покажите схему размещения полей в памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

const Degree = 8

// NaiveNode: блокировка и ключи находятся в одной кэш-линии
type NaiveNode struct {
	writeVer uint64
	numKeys  int32
	keys     [Degree]int64
}

// OptimizedNode: метаданные изолированы от ключей
type OptimizedNode struct {
	writeVer uint64
	numKeys  int32
	_        [52]byte // Выравнивание до 64 байт (8 + 4 + 52 = 64)
	keys     [Degree]int64
}

func benchmarkNaive(iters int) time.Duration {
	var node NaiveNode
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	// Пишущая горутина обновляет версию узла
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&node.writeVer, 1)
		}
	}()

	// Читающая горутина суммирует ключи
	go func() {
		defer wg.Done()
		var sum int64
		for i := 0; i < iters; i++ {
			for k := 0; k < Degree; k++ {
				sum += node.keys[k]
			}
		}
		_ = sum
	}()

	wg.Wait()
	return time.Since(start)
}

func benchmarkOptimized(iters int) time.Duration {
	var node OptimizedNode
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&node.writeVer, 1)
		}
	}()

	go func() {
		defer wg.Done()
		var sum int64
		for i := 0; i < iters; i++ {
			for k := 0; k < Degree; k++ {
				sum += node.keys[k]
			}
		}
		_ = sum
	}()

	wg.Wait()
	return time.Since(start)
}

func main() {
	var naive NaiveNode
	var opt OptimizedNode

	fmt.Printf("NaiveNode: Size=%d, KeysOffset=%d\n",
		unsafe.Sizeof(naive), unsafe.Offsetof(naive.keys))
	fmt.Printf("OptimizedNode: Size=%d, KeysOffset=%d\n",
		unsafe.Sizeof(opt), unsafe.Offsetof(opt.keys))

	const iters = 20_000_000
	tNaive := benchmarkNaive(iters)
	fmt.Printf("NaiveNode (инвалидация ключей):      %v\n", tNaive)

	tOpt := benchmarkOptimized(iters)
	fmt.Printf("OptimizedNode (изоляция кэш-линий): %v\n", tOpt)

	if tOpt < tNaive {
		fmt.Printf("Ускорение чтения: %.2fx\n", float64(tNaive)/float64(tOpt))
	}
}
```

ℹ️ Изоляция метаданных узла B-дерева от массива ключей исключает инвалидацию кэша при чтении.

## Под капотом

В `NaiveNode` смещение `keys` равно 16 байтам. Таким образом, первые ключи делят одну 64-байтную кэш-линию с `writeVer`. Когда ядро 0 выполняет `atomic.AddUint64(&node.writeVer, 1)`, кэш-линия переходит в состояние Modified, и ядро 1 при попытке прочитать `node.keys[0]` получает L1 Cache Miss. В `OptimizedNode` смещение `keys` равно 64 байтам: ядро 1 удерживает ключи в состоянии Shared и читает их из L1 без задержек.

## Подводные камни

1. Увеличение расхода памяти на узел: если дерево содержит миллионы узлов, добавление 52 байт отступа к каждому узлу увеличит потребление RAM на сотни мегабайт.
2. Оптимизацию следует применять только к узлам с высоким уровнем параллельного доступа (Hot Nodes / Root / Верхние уровни дерева).

## На собеседовании

В распределенных и встраиваемых хранилищах (CockroachDB, RocksDB, BadgerDB) структуры LSM-Tree и B-Tree оптимизируются под аппаратный уровень. Кандидату могут задать вопрос: «Как сбалансировать размер узла B-дерева с точки зрения кэша процессора?». Правильный ответ: размер листа или внутреннего узла должен быть кратен размеру кэш-линии (64B, 128B или 4096B для страниц ОС), а метаданные модификации отделены от данных поиска.
