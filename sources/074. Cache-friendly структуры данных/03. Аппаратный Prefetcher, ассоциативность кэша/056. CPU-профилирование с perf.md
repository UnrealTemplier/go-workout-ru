# CPU-профилирование с perf: анализ промахов кэша (Cache Misses)

## Условие

Напишите программу, сравнивающую обход непрерывного массива и разреженного связанного списка одинакового размера. Продемонстрируйте использование команды perf stat -e cache-misses,cache-references,L1-dcache-load-misses для измерения физических промахов кэша ЦПУ.

### Исходная формулировка

**CPU Profiling с `perf`**: (Только для Linux). Скомпилируй код из 865 и 867. Запусти их через системную утилиту `perf stat -e cache-misses ./app`. Посмотри на физическое количество промахов кэша процессора и сравни результаты.

## Теория

Связанный список (`Linked List`) хранит узлы в виде указателей, разбросанных по всей оперативной памяти. Переход по указателю `node = node.next` приводит к явлению **Pointer Chasing (погоня за указателями)**: процессор не может предугадать следующий адрес в памяти, что вызывает промах кэша на каждом узле.

Непрерывный массив (`Slice/Array`), напротив, расположен линейно. Процессор загружает данные 64-байтными блоками, а аппаратный стрим-префетчер сводит `cache-misses` практически к нулю.

Команда `perf stat` позволяет измерить аппаратные счетчики ЦПУ:
```bash
perf stat -e cache-references,cache-misses,L1-dcache-loads,L1-dcache-load-misses ./app
```
Коэффициент промахов кэша (Cache Miss Ratio) для связанного списка может достигать 30-70%, тогда как для массива он составляет менее 0.1%.

## Решение по шагам

1. Создайте связанный список из 2 000 000 элементов и плоский срез `[]int64` такого же размера.
2. Реализуйте обход списка и суммирование всех его значений.
3. Реализуйте аналогичный обход и суммирование для плоского среза.
4. Выведите время работы обоих алгоритмов.
5. Приведите инструкцию по запуску `perf stat` для анализа промахов кэша первого и второго подходов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"os"
	"strconv"
	"time"
)

type Node struct {
	Value int64
	Next  *Node
}

func benchmarkArray(size int) time.Duration {
	data := make([]int64, size)
	for i := 0; i < size; i++ {
		data[i] = int64(i)
	}

	start := time.Now()
	var sum int64
	for i := 0; i < size; i++ {
		sum += data[i]
	}
	_ = sum
	return time.Since(start)
}

func benchmarkLinkedList(size int) time.Duration {
	nodes := make([]Node, size)
	// Перемешиваем индексы для имитации фрагментации кучи
	indices := rand.Perm(size)

	var head *Node
	var prev *Node
	for _, idx := range indices {
		curr := &nodes[idx]
		curr.Value = int64(idx)
		if head == nil {
			head = curr
		} else {
			prev.Next = curr
		}
		prev = curr
	}

	start := time.Now()
	var sum int64
	curr := head
	for curr != nil {
		sum += curr.Value
		curr = curr.Next
	}
	_ = sum
	return time.Since(start)
}

func main() {
	size := 3_000_000
	if len(os.Args) > 1 {
		if s, err := strconv.Atoi(os.Args[1]); err == nil {
			size = s
		}
	}

	fmt.Printf("Тестирование обхода структуры размером %d элементов...\n", size)
	tArray := benchmarkArray(size)
	fmt.Printf("Непрерывный массив:   %v\n", tArray)

	tList := benchmarkLinkedList(size)
	fmt.Printf("Связанный список:    %v\n", tList)

	if tList > tArray {
		fmt.Printf("Связный список медленнее в %.2fx из-за Pointer Chasing и Cache Misses!\n",
			float64(tList)/float64(tArray))
	}
}
```

ℹ️ Сравнение линейного массива и фрагментированного связанного списка.

## Под капотом

Когда ЦПУ выполняет `curr = curr.Next`, адрес следующего узла находится внутри памяти, которую ядро еще не прочитало. Происходит Stall конвейера: процессор отправляет запрос в контроллер памяти и ждет ответа ~60 нс (около 200–300 тактов). Ни Out-of-Order Execution, ни Prefetcher не могут предсказать адрес, пока не завершится предыдущий dereference. В срезе же адреса известны заранее: \(Addr_i = Base + i \times 8\).

## Подводные камни

1. Если связанный список аллоцирован строго последовательно в памяти (например, в одном непрерывном срезе без перемешивания), prefetcher сможет частично оптимизировать доступ. Реальная фрагментация кучи в долгоживущих сервисах делает Pointer Chasing еще более разрушительным.
2. Не компилируйте тестовый код с максимальной оптимизацией без использования результата суммирования (`_ = sum`), иначе компилятор может вырезать весь цикл.

## На собеседовании

Вопрос: «Почему в современных высокопроизводительных системах на смену классическим Linked List и Binary Search Tree пришли Flat Arrays, B-деревья и Unrolled Linked Lists?». Ответ: из-за колоссального разрыва в пропускной способности процессора и оперативной памяти (Memory Wall). B-деревья помещают десятки ключей в одну кэш-линию, минимизируя дорогостоящие промахи L1/L2.
