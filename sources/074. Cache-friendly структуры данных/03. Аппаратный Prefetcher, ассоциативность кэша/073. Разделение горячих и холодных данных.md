# Разделение горячих и холодных данных (Hot/Cold Data Splitting)

## Условие

Реализуйте паттерн Hot/Cold Splitting для высоконагруженной сущности UserSession. Вынесите часто обновляемые поля (Hot Data: счетчики, метка времени) в компактную структуру, а редко используемые (Cold Data: email, био, настройки) — во внешнюю структуру.

### Исходная формулировка

**Hot/cold splitting**: Разделите структуру на hot fields (часто accessed) и cold fields (редко accessed). Hot fields в одной cache line, cold — отдельно.

## Теория

В крупных корпоративных системах структуры предметной области разрастаются до десятков полей:
```go
type BadUserSession struct {
    UserID       uint64
    LastActive   int64  // HOT: обновляется каждые 500 мс
    RequestCount int32  // HOT: инкрементируется на каждый RPC
    Email        string // COLD: читается раз в день
    UserBio      string // COLD: профиль
    SettingsJSON string // COLD: 2 КБ настроек
    // ... еще 20 полей
}
```
Если хранить миллион таких сессий в памяти, то для инкремента `RequestCount` процессор вынужден загружать в кэш сотни байт холодного мусора. Это приводит к катастрофическому вытеснению полезных данных из кэша L3 (Cache Pollution).

Паттерн **Hot/Cold Splitting**:
```go
type HotSession struct {
    UserID       uint64
    LastActive   int64
    RequestCount int32
    ColdDataPtr  *ColdSession // ссылка на холодные данные
}
```
Размер `HotSession` составляет всего 32 байта! В одну 64-байтную кэш-линию помещаются сразу 2 горячие сессии, а плотность кэша возрастает в 5–10 раз.

## Решение по шагам

1. Создайте монолитную структуру `MonolithicSession` (128 байт).
2. Создайте разделенные структуры `HotSession` (32 байта) и `ColdSession`.
3. Смоделируйте цикл обработки миллиона запросов, обновляющих только поле `RequestCount`.
4. Сравните время выполнения и потребление пропускной способности памяти.
5. Продемонстрируйте доступ к холодным данным по требованию.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
	"unsafe"
)

const SessionCount = 2_000_000

// Монолитная сессия: горячие и холодные поля вперемешку
type MonolithicSession struct {
	UserID       uint64
	LastActive   int64
	RequestCount uint32
	_            [4]byte // padding
	Email        string  // Cold (16 байт)
	Address      string  // Cold (16 байт)
	Bio          string  // Cold (16 байт)
	Config       [64]byte // Cold (64 байта)
}

// HotSession: только критически важные поля
type HotSession struct {
	UserID       uint64
	LastActive   int64
	RequestCount uint32
	_            [4]byte
	Cold         *ColdData // Указатель на холодную часть
}

type ColdData struct {
	Email   string
	Address string
	Bio     string
	Config  [64]byte
}

func benchmarkMonolithic(sessions []MonolithicSession) time.Duration {
	start := time.Now()
	for i := range sessions {
		sessions[i].RequestCount++
		sessions[i].LastActive = 123456789
	}
	return time.Since(start)
}

func benchmarkHotCold(sessions []HotSession) time.Duration {
	start := time.Now()
	for i := range sessions {
		sessions[i].RequestCount++
		sessions[i].LastActive = 123456789
	}
	return time.Since(start)
}

func main() {
	var m MonolithicSession
	var h HotSession
	fmt.Printf("Размер MonolithicSession: %d байт\n", unsafe.Sizeof(m))
	fmt.Printf("Размер HotSession:        %d байт\n\n", unsafe.Sizeof(h))

	monoList := make([]MonolithicSession, SessionCount)
	hotList := make([]HotSession, SessionCount)

	tMono := benchmarkMonolithic(monoList)
	fmt.Printf("Монолитные сессии (Cache Pollution): %v\n", tMono)

	tHot := benchmarkHotCold(hotList)
	fmt.Printf("Hot/Cold Splitting (Высокая плотность): %v\n", tHot)

	if tHot < tMono {
		fmt.Printf("Ускорение горячего пути: %.2fx раз!\n", float64(tMono)/float64(tHot))
	}
}
```

ℹ️ Вынос холодных полей увеличивает количество горячих сущностей в L1/L2 кэше в разы.

## Под капотом

Размер `MonolithicSession` равен 144 байтам (занимает почти 3 кэш-линии процессора). При обходе 2 000 000 сессий ЦПУ прокачивает через кэш \(2\,000\,000 \times 144 \approx 288\) МБ данных, полностью вымывая кэш L3. В `HotSession` размер равен 32 байтам. Суммарный объем горячих данных составляет всего 64 МБ, что позволяет им практически целиком уместиться в L3 кэш современного серверного процессора AMD EPYC или Intel Xeon.

## Подводные камни

1. Дополнительная аллокация: выделение холодной части `ColdData` через отдельный указатель создает дополнительную нагрузку на аллокатор и GC при создании объекта.
2. Неудобство при сериализации: при передаче по сети (JSON/Protobuf) горячую и холодную части нужно объединять обратно.

Ответ: паттерн Hot/Cold Splitting — изоляция счетчиков и флагов статуса в плоских массивах (SoA/Hot structs), а текстовые описания и метаданные — вынос в холодное хранилище или обращение по требованию через lazy loading.
