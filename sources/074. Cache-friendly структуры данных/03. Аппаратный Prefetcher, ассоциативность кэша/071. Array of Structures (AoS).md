# Array of Structures (AoS) для объектно-ориентированного доступа

## Условие

Исследуйте сценарии, когда Array of Structures (AoS) превосходит SoA: покажите, что при алгоритмах, где требуется одновременный доступ ко ВСЕМ полям одного объекта (X, Y, Z, Mass), AoS обеспечивает идеальную пространственную локальность.

### Исходная формулировка

**Array of Structures (AoS) для OOP**: Для object-oriented кода используйте AoS:
```go
type Particle struct { x, y, z float32 }
type Particles []Particle
```
Это лучше для итерации по всем полям одного объекта.

## Теория

Хотя SoA доминирует в задачах векторизации одного поля, в сценариях комплексной обработки объекта **Array of Structures (AoS)** оказывается значительно эффективнее.

Если функция обрабатывает частицу целиком:
```go
func Collide(p *Particle) {
    energy := 0.5 * p.Mass * (p.Vx*p.Vx + p.Vy*p.Vy + p.Vz*p.Vz)
    p.X += p.Vx
    p.Y += p.Vy
    p.Z += p.Vz
}
```
* В **AoS** все поля одной частицы (`X, Y, Z, Vx, Vy, Vz, Mass`) лежат строго рядом в памяти и подгружаются в **одну кэш-линию**. Обращение ко всем полям объекта происходит с задержкой L1-кэша.
* В **SoA** для обработки одной частицы процессору требуется загрузить данные из 7 разных массивов! Это приводит к одновременному расходу 7 кэш-линий и увеличивает нагрузку на TLB.

## Решение по шагам

1. Создайте структуру `Entity` со всеми полями, необходимыми для комплексного вычисления.
2. Реализуйте алгоритм полного расчета сущности в модели AoS.
3. Реализуйте тот же расчет в модели SoA (чтение из 5 параллельных срезов).
4. Замерьте время выполнения при интенсивном доступе ко всем атрибутам.
5. Сформулируйте критерии выбора между AoS и SoA.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const EntityCount = 2_000_000

type EntityAoS struct {
	X, Y, Z    float64
	Vx, Vy, Vz float64
	Mass       float64
}

type EntitiesSoA struct {
	X, Y, Z    []float64
	Vx, Vy, Vz []float64
	Mass       []float64
}

func benchmarkAoS(entities []EntityAoS) time.Duration {
	start := time.Now()
	var totalEnergy float64
	for i := range entities {
		e := &entities[i]
		e.X += e.Vx
		e.Y += e.Vy
		e.Z += e.Vz
		totalEnergy += 0.5 * e.Mass * (e.Vx*e.Vx + e.Vy*e.Vy + e.Vz*e.Vz)
	}
	_ = totalEnergy
	return time.Since(start)
}

func benchmarkSoA(soa *EntitiesSoA) time.Duration {
	start := time.Now()
	var totalEnergy float64
	for i := 0; i < EntityCount; i++ {
		soa.X[i] += soa.Vx[i]
		soa.Y[i] += soa.Vy[i]
		soa.Z[i] += soa.Vz[i]
		totalEnergy += 0.5 * soa.Mass[i] * (soa.Vx[i]*soa.Vx[i] + soa.Vy[i]*soa.Vy[i] + soa.Vz[i]*soa.Vz[i])
	}
	_ = totalEnergy
	return time.Since(start)
}

func main() {
	aos := make([]EntityAoS, EntityCount)
	for i := range aos {
		aos[i] = EntityAoS{X: 1, Y: 2, Z: 3, Vx: 0.1, Vy: 0.2, Vz: 0.3, Mass: 10}
	}

	soa := EntitiesSoA{
		X: make([]float64, EntityCount), Y: make([]float64, EntityCount), Z: make([]float64, EntityCount),
		Vx: make([]float64, EntityCount), Vy: make([]float64, EntityCount), Vz: make([]float64, EntityCount),
		Mass: make([]float64, EntityCount),
	}
	for i := 0; i < EntityCount; i++ {
		soa.X[i], soa.Y[i], soa.Z[i] = 1, 2, 3
		soa.Vx[i], soa.Vy[i], soa.Vz[i] = 0.1, 0.2, 0.3
		soa.Mass[i] = 10
	}

	tAoS := benchmarkAoS(aos)
	fmt.Printf("AoS (все поля объекта в одной кэш-линии): %v\n", tAoS)

	tSoA := benchmarkSoA(&soa)
	fmt.Printf("SoA (7 параллельных срезов):             %v\n", tSoA)

	if tAoS <= tSoA {
		fmt.Printf("AoS быстрее или сопоставим (%.2fx) благодаря локальности всех полей объекта!\n",
			float64(tSoA)/float64(tAoS))
	}
}
```

ℹ️ Когда алгоритм читает и пишет все поля объекта, AoS сохраняет полную локальность кэша.

## Под капотом

В AoS размер `EntityAoS` составляет 56 байт. Вся сущность целиком помещается в одну 64-байтную кэш-линию. Процессор загружает ровно одну строку кэша и выполняет все вычисления над ее полями. В SoA процессор должен одновременно удерживать в кэше L1 7 разных кэш-линий из 7 независимых страниц памяти, что повышает риск конфликтов ассоциативности кэша (Cache Way Conflicts).

## Подводные камни

1. Избыточное разрастание структуры: если структура вырастает до сотен байт, она занимает несколько кэш-линий, и преимущество AoS утрачивается.
2. Неучет выравнивания: невыровненные типы внутри структуры добавят скрытые байты отступа.

## На собеседовании

Классический вопрос на архитектора систем: «Когда вы выберете AoS, а когда SoA?». Ответ: SoA идеален для аналитических выборок по колонкам (OLAP / ClickHouse) и SIMD-векторизации отдельных полей. AoS идеален для транзакционной обработки полных сущностей (OLTP / PostgreSQL / бизнес-логика заказов).
