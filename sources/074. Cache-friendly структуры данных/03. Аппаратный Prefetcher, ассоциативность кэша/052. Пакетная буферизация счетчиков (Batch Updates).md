# Пакетная буферизация счетчиков (Batch Updates)

## Условие

Реализуйте высокопроизводительный счетчик метрик с пакетным накоплением (Batch Updates): вместо вызова дорогостоящего atomic.Add на каждое единичное событие накапливайте дельту в локальной переменной горутины и сбрасывайте ее в глобальный счетчик пакетом через каждые N операций.

### Исходная формулировка

**Batch updates**: Вместо `atomic.Add(&counter, 1)` на каждое событие, accumulate в local variable и flush в global counter каждые 1000 операций.

## Теория

Инструкции `atomic.Add` и атомарные операции в Go компилируются на x86_64 в префикс `lock` (например, `lock addq` или `lock xaddq`). Префикс `lock` блокирует не всю шину памяти, а строку кэша ядра (Cache Lock) и заставляет процессор сбросить локальные буферы записи (Store Buffers) для соблюдения модели строгой последовательной консистентности.

Если сервис обрабатывает 10 000 000 RPS и на каждый запрос дергает `atomic.AddUint64`, производительность упирается в пропускную способность конвейера синхронизации кэша. Паттерн **Batch Updates (пакетная буферизация)** переносит инкременты в локальный регистр процессора (стековую переменную), снижая количество атомарных операций в 100–10 000 раз:
$$\text{Atomic Cost} = \frac{\text{Total Events}}{B}$$
где \(B\) — размер батча (например, 1 000 или 10 000).

## Решение по шагам

1. Создайте структуру `GlobalCounter` с атомарным полем `total uint64`.
2. Напишите функцию `WorkerNaive`, которая инкрементирует глобальный счетчик атомарно на каждое событие.
3. Напишите функцию `WorkerBatched`, которая ведет локальный накопитель `localCount` и сбрасывает его в глобальный счетчик только при достижении порога `batchSize` или при завершении работы.
4. Протестируйте обе стратегии с помощью многопоточного теста и замерьте время выполнения.
5. Убедитесь в корректности итогового значения суммы.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type BatchCounter struct {
	total uint64
}

func (c *BatchCounter) AddDirect(delta uint64) {
	atomic.AddUint64(&c.total, delta)
}

func (c *BatchCounter) Total() uint64 {
	return atomic.LoadUint64(&c.total)
}

func runNaive(workers, itemsPerWorker int) time.Duration {
	var c BatchCounter
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := 0; i < itemsPerWorker; i++ {
				c.AddDirect(1)
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func runBatched(workers, itemsPerWorker, batchSize int) time.Duration {
	var c BatchCounter
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			localAccumulator := uint64(0)
			for i := 0; i < itemsPerWorker; i++ {
				localAccumulator++
				if localAccumulator >= uint64(batchSize) {
					c.AddDirect(localAccumulator)
					localAccumulator = 0
				}
			}
			if localAccumulator > 0 {
				c.AddDirect(localAccumulator)
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	const workers = 8
	const itemsPerWorker = 5_000_000
	const batchSize = 1_000

	fmt.Printf("Тестирование: %d горутин по %d событий\n", workers, itemsPerWorker)

	tNaive := runNaive(workers, itemsPerWorker)
	fmt.Printf("Без батчинга (atomic на каждый эвент): %v\n", tNaive)

	tBatched := runBatched(workers, itemsPerWorker, batchSize)
	fmt.Printf("С батчингом (сброс каждые %d эвентов):   %v\n", batchSize, tBatched)

	if tBatched < tNaive {
		fmt.Printf("Прирост производительности: %.2fx\n", float64(tNaive)/float64(tBatched))
	}
}
```

ℹ️ Пакетная фиксация счетчиков сводит contention к минимуму.

## Под капотом

Локальная переменная цикла `localAccumulator` компилируется в регистр процессора (например, `%rax` или `%rbx`). Инкремент регистра занимает 1 такт ЦПУ без обращения к подсистеме памяти. Напротив, инструкция `atomic.AddUint64` генерирует `lock xaddq`, которая требует получения монопольного владения строкой кэша, заставляя конвейер ядра ждать подтверждения от кэш-когерентного контроллера. Снижение частоты синхронизаций в 1000 раз снижает нагрузку на шину L3 и контроллер памяти на 99.9%.

## Подводные камни

1. Задержка отображения метрик: пока батч не накопился, данные во внешней системе запаздывают (stale reads). При низком трафике метрики могут не сбрасываться минутами.
2. Потеря данных при внезапном сбое: если горутина паникует или процесс завершается по `SIGKILL`, данные в `localAccumulator` теряются. Для надежных систем необходим периодический flush по таймеру (`time.Ticker`).

## На собеседовании

В распределенных трейсингах и метриках (Prometheus, OpenTelemetry SDK, Uber zap) батчинг метрик — фундаментальный стандарт. Интервьюер может спросить: «Как реализовать счетчик для миллиарда RPS без деградации latency бизнес-логики?». Ответ: локальные поточные буферы/регистры со сбросом батча по размеру (N элементов) или по таймеру (каждые 100 мс).
