# False Sharing в конкурентных шардированных мапах

## Условие

Реализуйте шардированную конкурентную хэш-таблицу (Concurrent Sharded Map). Покажите, как неаккуратное размещение мьютексов шардов в одном непрерывном слайсе вызывает False Sharing между независимыми шардами, и устраните эту проблему с помощью выравнивания шардов по кэш-линиям.

### Исходная формулировка

**False sharing в мапах**: Go мапы имеют internal locking per bucket. Но если вы используете custom concurrent map — избегайте false sharing между buckets.

## Теория

Для масштабирования мап на чтение и запись часто применяют шардирование (Striped/Sharded Map): ключ хэшируется и направляется в один из \(N\) независимых шардов (обычно \(N = 32\) или \(64\)), каждый из которых защищен своим `sync.RWMutex`.

Однако если шарды объявлены как:
```go
type Shard struct {
    mu   sync.RWMutex
    data map[string]any
}
type ConcurrentMap struct {
    shards []Shard // Непрерывный массив шардов
}
```
Структура `sync.RWMutex` в Go занимает 24 байта, а указатель на мапу — 8 байт (всего 32 байта). Это означает, что **два соседних шарда целиком помещаются в одну 64-байтную кэш-линию**! Попытка заблокировать `shard[0].mu` приводит к инвалидации кэш-линии у ядра, работающего с `shard[1].mu`, сводя на нет преимущества шардирования.

## Решение по шагам

1. Создайте структуру `ShardUnpadded` (RWMutex + map).
2. Создайте структуру `ShardPadded` с добавлением `_ [32]byte` для дополнения размера шарда ровно до 64 байт (или кратного).
3. Реализуйте параллельный бенчмарк конкурентной записи ключей в разные шарды для обоих типов таблиц.
4. Проверьте адреса мьютексов и смещения шардов через `unsafe.Pointer`.
5. Сравните throughput обеих реализаций при 16–32 параллельных горутинах.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sync"
	"time"
	"unsafe"
)

const ShardCount = 32

type ShardUnpadded struct {
	mu   sync.RWMutex
	data map[string]int
}

type ConcurrentMapUnpadded struct {
	shards [ShardCount]ShardUnpadded
}

type ShardPadded struct {
	mu   sync.RWMutex
	data map[string]int
	_    [32]byte // Дополняем до 64 байт (24 + 8 + 32 = 64)
}

type ConcurrentMapPadded struct {
	shards [ShardCount]ShardPadded
}

func getShardIndex(key string) uint32 {
	h := fnv.New32a()
	h.Write([]byte(key))
	return h.Sum32() % ShardCount
}

func benchmarkUnpadded(ops int, workers int) time.Duration {
	var m ConcurrentMapUnpadded
	for i := 0; i < ShardCount; i++ {
		m.shards[i].data = make(map[string]int)
	}

	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		workerID := w
		go func() {
			defer wg.Done()
			for i := 0; i < ops; i++ {
				key := fmt.Sprintf("key_%d_%d", workerID, i%100)
				idx := getShardIndex(key)
				s := &m.shards[idx]
				s.mu.Lock()
				s.data[key] = i
				s.mu.Unlock()
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func benchmarkPadded(ops int, workers int) time.Duration {
	var m ConcurrentMapPadded
	for i := 0; i < ShardCount; i++ {
		m.shards[i].data = make(map[string]int)
	}

	var wg sync.WaitGroup
	wg.Add(workers)
	start := time.Now()

	for w := 0; w < workers; w++ {
		workerID := w
		go func() {
			defer wg.Done()
			for i := 0; i < ops; i++ {
				key := fmt.Sprintf("key_%d_%d", workerID, i%100)
				idx := getShardIndex(key)
				s := &m.shards[idx]
				s.mu.Lock()
				s.data[key] = i
				s.mu.Unlock()
			}
		}()
	}
	wg.Wait()
	return time.Since(start)
}

func main() {
	var su ShardUnpadded
	var sp ShardPadded
	fmt.Printf("Размер ShardUnpadded: %d байт\n", unsafe.Sizeof(su))
	fmt.Printf("Размер ShardPadded:   %d байт\n", unsafe.Sizeof(sp))

	const ops = 100_000
	const workers = 16

	tUnpadded := benchmarkUnpadded(ops, workers)
	fmt.Printf("Map без padding: %v\n", tUnpadded)

	tPadded := benchmarkPadded(ops, workers)
	fmt.Printf("Map с padding:   %v\n", tPadded)

	if tPadded < tUnpadded {
		fmt.Printf("Ускорение шардированной мапы: %.2fx\n", float64(tUnpadded)/float64(tPadded))
	}
}
```

ℹ️ Изоляция мьютексов шардов по отдельным кэш-линиям устраняет коллизии между непересекающимися ключами.

## Под капотом

Мьютекс `sync.RWMutex` содержит поля `w sync.Mutex`, `writerSem uint32`, `readerSem uint32`, `readerCount atomic.Int32`, `readerWait atomic.Int32`. Любой вызов `Lock()` выполняет атомарный CAS над `readerCount` или `Mutex.state`. Если два шарда лежат в одной кэш-линии, то параллельный `Lock()` шарда 0 и `Lock()` шарда 1 вызывают столкновение инструкций `LOCK CMPXCHG` на уровне кэша, заставляя ядра ждать освобождения линии.

## Подводные камни

1. Если шарды создаются как срез указателей `[]*Shard`, каждый шард аллоцируется в куче независимо. В этом случае Go runtime аллокатор может положить их рядом или далеко, создавая недетерминированное поведение. Гарантировать изоляцию может только явный padding внутри структуры шарда.
2. Слишком большое число шардов при наличии padding увеличивает потребление памяти впустую.

## На собеседовании

Вопрос от инженеров баз данных и in-memory кэшей (Tarantool, Redis, Aerospike): «Как архитектурно устроена структура Striped Lock и какие скрытые узкие места в ней возникают на машинах с 64+ ядрами?». Грамотный кандидат сразу упоминает кэш-линии мьютексов и необходимость выравнивания каждого страйпа по границе 64 (или 128) байт.
