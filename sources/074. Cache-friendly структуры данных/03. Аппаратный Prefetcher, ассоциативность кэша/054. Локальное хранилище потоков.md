# Локальное хранилище потоков (Thread-Local Storage / per-P структуры)

## Условие

Спроектируйте высокопроизводительную per-P (или per-goroutine) структуру для сбора метрик с использованием sync.Pool, чтобы каждая горутина работала с теплым локальным счетчиком без блокировок и взаимного вытеснения кэша.

### Исходная формулировка

**Thread-local storage**: Используйте `sync.Pool` или `g` (goroutine-local storage через `runtime.g`) для thread-local counters.

## Теория

В отличие от C++ (`thread_local`) или Java (`ThreadLocal`), в языке Go концепция Thread-Local Storage намеренно не поддерживается на уровне языка, чтобы предотвратить привязку горутин к конкретным системным потокам ОС (M).

Однако в runtime Go есть концепция `P` (логический процессор планировщика GMP). Самый быстрый и каноничный способ получить quasi-TLS локальность без блокировок — использовать `sync.Pool`. Под капотом `sync.Pool` хранит массив `[GOMAXPROCS]poolLocal`, где каждый `poolLocal` выровнен по 128 байт для исключения False Sharing между ядрами:
```go
type poolLocal struct {
    poolLocalInternal
    pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
}
```
Когда горутина вызывает `pool.Get()`, она без блокировок обращается к локальной очереди своего текущего `P`. Это дает максимальную кэш-локальность.

## Решение по шагам

1. Создайте структуру `LocalAccumulator` с внутренним срезом или счетчиком.
2. Инициализируйте `sync.Pool` с фабрикой `New: func() any { return &LocalAccumulator{} }`.
3. В рабочих горутинах извлекайте объект через `pool.Get()`, выполняйте интенсивную модификацию и возвращайте в `pool.Put()`.
4. Продемонстрируйте агрегацию данных из пула в глобальный результат через периодический сброс.
5. Замерьте задержки по сравнению с единым мьютексом.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type LocalMetric struct {
	Count int64
}

type MetricSystem struct {
	pool        sync.Pool
	globalTotal int64
}

func NewMetricSystem() *MetricSystem {
	return &MetricSystem{
		pool: sync.Pool{
			New: func() any {
				return &LocalMetric{}
			},
		},
	}
}

func (ms *MetricSystem) Record(delta int64) {
	local := ms.pool.Get().(*LocalMetric)
	local.Count += delta
	if local.Count >= 1000 {
		atomic.AddInt64(&ms.globalTotal, local.Count)
		local.Count = 0
	}
	ms.pool.Put(local)
}

func (ms *MetricSystem) Flush() int64 {
	return atomic.LoadInt64(&ms.globalTotal)
}

func main() {
	ms := NewMetricSystem()
	const workers = 16
	const opsPerWorker = 500_000

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for i := 0; i < workers; i++ {
		go func() {
			defer wg.Done()
			for j := 0; j < opsPerWorker; j++ {
				ms.Record(1)
			}
		}()
	}
	wg.Wait()

	fmt.Printf("Обработано %d операций за %v\n", workers*opsPerWorker, time.Since(start))
	fmt.Printf("Зафиксировано в глобальном счетчике: %d\n", ms.Flush())
}
```

ℹ️ sync.Pool обеспечивает распределение объектов по виртуальным процессорам P без блокировок.

## Под капотом

Внутри `sync.Pool` вызов `runtime_procPin()` привязывает текущую горутину к процессору `P` и возвращает его `pid`. Доступ к приватному слоту `poolLocal.private` осуществляется без атомарных инструкций и мьютексов. А благодаря аппаратному padding в 128 байт в структуре `poolLocal`, разные ядра процессора модифицируют свои приватные пулы в изолированных кэш-линиях, полностью исключая False Sharing.

## Подводные камни

1. Очистка пула сборщиком мусора: во время каждого цикла GC объекты из `sync.Pool` перемещаются в `victim pool` и могут быть удалены, поэтому `sync.Pool` нельзя использовать для сохранения постоянного состояния.
2. Невозврат объектов: забытый `pool.Put()` приводит к постоянным аллокациям в куче.

## На собеседовании

Вопрос: «Почему в Go нет официального `goroutine-local storage` (GLS)?». Ответ: дизайнеры Go сознательно отказались от GLS, так как разработчики начинают использовать его для неявной передачи контекста, аутентификации и транзакций, что порождает баги при переключении горутин в пуле воркеров. Вместо этого передача зависимостей делается явно через `context.Context`, а кэширование буферов — через `sync.Pool`.
