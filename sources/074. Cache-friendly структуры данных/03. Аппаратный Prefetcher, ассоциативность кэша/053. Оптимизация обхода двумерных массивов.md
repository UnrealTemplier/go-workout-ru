# Оптимизация обхода двумерных массивов: Row-Major vs Column-Major

## Условие

Создайте квадратную матрицу размером 2000x2000 целых чисел. Напишите две функции суммирования: обход по строкам (Row-Major: matrix[row][col]) и обход по столбцам (Column-Major: matrix[col][row]). Замерьте разницу в скорости и объясните работу аппаратного механизма CPU Prefetcher.

### Исходная формулировка

**Оптимизация обхода двумерных массивов**: Создайте матрицу размером `[2000][2000]int`. Напишите две функции суммирования элементов матрицы:
* Первая обходит матрицу по строкам (row-major order): `matrix[row][col]`.
* Вторая обходит матрицу по колонкам (column-major order): `matrix[col][row]`.
Напишите бенчмарк и сравните их производительность. Напишите подробный комментарий, объясняющий, почему обход по строкам эффективнее из-за работы механизма CPU prefetching (последовательное чтение соседних ячеек памяти).

## Теория

В языке Go многомерные массивы и слайсы располагаются в непрерывном адресном пространстве оперативной памяти в порядке **Row-Major** (по строкам). Это означает, что элемент `matrix[i][j+1]` находится в памяти строго следом за `matrix[i][j]`.

Когда процессор читает один 8-байтный `int64`, в кэш-линию L1 (64 байта) автоматически подтягиваются следующие 7 элементов. Кроме того, специализированный аппаратный блок процессора — **Stream Prefetcher (L2/L1 prefetcher)** — детектирует монотонно возрастающий шаг адресов (stride = 8 байт) и заблаговременно подгружает следующие кэш-линии из L3/DRAM до того, как инструкция процессора их запросит.

Если же обходить матрицу по колонкам (`matrix[col][row]`), шаг между обращениями составляет \(2000 \times 8 = 16\,000\) байт. На каждый элемент приходится Cache Miss, вытесняющий полезные данные из L1/L2 кэшей, а prefetcher теряет способность прогнозировать адреса.

## Решение по шагам

1. Выделите непрерывный двумерный массив `[2000][2000]int64` (или одномерный срез на 4 000 000 элементов).
2. Заполните матрицу начальными значениями.
3. Реализуйте функцию `SumRowMajor(m)` с обходом во внешнем цикле по строкам `i`, а во внутреннем по столбцам `j`.
4. Реализуйте функцию `SumColMajor(m)` с внешним циклом по столбцам `j`, а внутренним по строкам `i`.
5. Замерьте время выполнения обеих функций и рассчитайте коэффициент ускорения.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const Size = 2000

type Matrix [Size][Size]int64

func SumRowMajor(m *Matrix) int64 {
	var sum int64
	for r := 0; r < Size; r++ {
		for c := 0; c < Size; c++ {
			sum += m[r][c]
		}
	}
	return sum
}

func SumColMajor(m *Matrix) int64 {
	var sum int64
	for c := 0; c < Size; c++ {
		for r := 0; r < Size; r++ {
			sum += m[r][c]
		}
	}
	return sum
}

func main() {
	fmt.Printf("Инициализация матрицы %dx%d (%d МБ)...\n",
		Size, Size, (Size*Size*8)/(1024*1024))
	m := new(Matrix)
	for r := 0; r < Size; r++ {
		for c := 0; c < Size; c++ {
			m[r][c] = int64(r + c)
		}
	}

	// Прогрев кэша
	SumRowMajor(m)

	startRow := time.Now()
	s1 := SumRowMajor(m)
	dRow := time.Since(startRow)

	startCol := time.Now()
	s2 := SumColMajor(m)
	dCol := time.Since(startCol)

	fmt.Printf("Row-Major sum: %d, время: %v\n", s1, dRow)
	fmt.Printf("Col-Major sum: %d, время: %v\n", s2, dCol)

	if dCol > dRow {
		ratio := float64(dCol) / float64(dRow)
		fmt.Printf("Row-Major быстрее в %.2fx раз благодаря CPU Prefetcher!\n", ratio)
	}
}
```

ℹ️ Последовательный обход матрицы утилизирует L1-кэш и аппаратный prefetcher на 100%.

## Под капотом

Аппаратный L1/L2 Spatial Prefetcher процессора отслеживает последовательность запросов к шине памяти. При stride = 64B он загружает следующую кэш-линию (Next-line prefetcher). Если stride равен 16 КБ (при `SumColMajor`), stride превышает предел детектора (обычно до 2 КБ), и каждый доступ вызывает обращение к кэшу L3 или DDR5 памяти с задержкой 60-100 нс вместо 1 нс в L1. Это приводит к простою конвейера ALU (stall).

## Подводные камни

1. Использование среза срезов (`[][]int`): в таком представлении строки могут быть разбросаны в разных участках кучи, что разрушает непрерывность адресации даже в Row-Major порядке.
2. Неучет порядка индексов в сторонних библиотеках (C/Fortran bindings): в Fortran и MATLAB принят Column-Major порядок, поэтому при взаимодействии через CGO важно знать целевой лейаут.

## На собеседовании

Классический вопрос на собеседованиях по высоконагруженным системам (Яндекс Поиск, VK Core): «Почему цикл `for i; for j; a[i][j]` работает в 10–20 раз быстрее, чем `a[j][i]`?». Грамотный ответ включает: пространственную локальность (spatial locality), размер кэш-линии (64 байта), аппаратный prefetcher и вытеснение строк из TLB (Translation Lookaside Buffer).
