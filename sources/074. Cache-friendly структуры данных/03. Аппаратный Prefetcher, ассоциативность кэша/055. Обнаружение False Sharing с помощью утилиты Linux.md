# Обнаружение False Sharing с помощью утилиты Linux perf c2c

## Условие

Изучите методику обнаружения False Sharing в бинарных файлах Go с помощью низкоуровневой утилиты Linux perf c2c (Cache-to-Cache). Напишите Go-программу с намеренным False Sharing, опишите шаги профилирования и ключевые метрики (HITM).

### Исходная формулировка

**False sharing detection**: Используйте `perf c2c` (Linux) для детекта false sharing. Это покажет, какие cache lines вызывают наибольшее contention.

## Теория

Утилита **perf c2c (Cache-to-Cache)** в Linux использует аппаратные счетчики производительности процессора (Intel PEBS / AMD IBS) для профилирования разделяемых строк кэша и детекта паразитных коллизий.

Ключевая метрика `perf c2c` — **HITM (Hit in Modified Cache)**:
* Событие HITM происходит, когда ядро процессора запрашивает строку кэша на чтение или запись, но эта строка уже находится в состоянии **Modified** в L1/L2 кэше другого процессорного ядра.
* Запрос не может быть удовлетворен из L3 или RAM — контроллер вынужден запросить передачу данных напрямую из кэша одного ядра в кэш другого ядра через интерконнект (Cross-Core Snoop / HITM Snoop).
* Высокий процент `Remote HITM` или `Local HITM` — безошибочный признак False Sharing или тяжелого мьютекс-контеншна.

## Решение по шагам

1. Напишите Go-код с конкурирующими инкрементами двух смежных полей структуры.
2. Скомпилируйте приложение с флагами отключения инлайнинга: `go build -gcflags="-N -l" -o false_sharing_app main.go`.
3. Запустите сбор трассы: `perf c2c record -- ./false_sharing_app`.
4. Сгенерируйте интерактивный отчет: `perf c2c report --stdio`.
5. Найдите раздел `Shared Data Cache Line Table` и локализуйте смещения байтов с наибольшим числом `Store HITM`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// HotSpotStruct провоцирует False Sharing: поля A и B делят одну 64-байтную строку
type HotSpotStruct struct {
	CounterA uint64 // offset 0
	CounterB uint64 // offset 8
}

func main() {
	var hs HotSpotStruct
	var wg sync.WaitGroup
	const iters = 50_000_000

	fmt.Println("Запуск нагрузки для профилирования через perf c2c...")
	start := time.Now()
	wg.Add(2)

	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&hs.CounterA, 1)
		}
	}()

	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&hs.CounterB, 1)
		}
	}()

	wg.Wait()
	fmt.Printf("Завершено за %v. CounterA=%d, CounterB=%d\n",
		time.Since(start), hs.CounterA, hs.CounterB)
}
```

ℹ️ Структура с намеренным False Sharing для анализа в perf c2c.

## Под капотом

В выводе `perf c2c report` отображается таблица Shared Data Cachelines. В ней указан базовый виртуальный адрес строки, общее количество HITM (Hit Modified) и breakdown по смещениям (Offset 0 и Offset 8). Если обе горутины пишут по смещениям 0 и 8 одной кэш-линии, метрика `Store HITM` будет близка к 100%, что сигнализирует о постоянном снуп-трафике по шине когерентности.

## Подводные камни

1. Требуются права root или настройка `perf_event_paranoid <= 0` (`sudo sysctl -w kernel.perf_event_paranoid=-1`).
2. В виртуальных машинах (Docker / WSL2 / Cloud VMs) счетчики PEBS часто отключены гипервизором, из-за чего `perf c2c` завершается с ошибкой unsupported hardware event.

## На собеседовании

В HighLoad командах (VK, Avito) на собеседованиях спрашивают: «Как системно находить узкие места в микроархитектуре сервиса на продакшене без догадок?». Кандидат должен назвать `perf c2c`, объяснить метрику `HITM`, упомянуть `perf stat -e cache-misses` и связать это с механикой кэш-инвалидаций в многопроцессорных сокетах (NUMA).
