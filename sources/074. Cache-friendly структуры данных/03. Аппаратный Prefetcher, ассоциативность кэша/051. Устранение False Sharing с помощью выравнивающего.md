# Устранение False Sharing с помощью выравнивающего Padding

## Условие

Добавьте между полями a и b выравнивающее поле-отступ (padding) размера 56 байт (или _ [7]uint64), чтобы они гарантированно оказались в разных 64-байтных кэш-линиях. Запустите бенчмарк конкурентной модификации и продемонстрируйте кратное ускорение благодаря устранению протокола когерентности MESI (инвалидаций Cache Line Bouncing).

### Исходная формулировка

**Устранение False Sharing (Padding)**: Добавь между `a` и `b` мусорное поле-отступ (padding), чтобы они гарантированно оказались в разных кэш-линиях: `_ [56]byte` (или `_ [7]uint64`). Запусти бенчмарк из 865 снова и насладись кратным ускорением!

## Теория

Когда несколько ядер параллельно модифицируют независимые переменные, расположенные в пределах одной 64-байтной кэш-линии (False Sharing), контроллеры кэша процессоров вынуждены непрерывно пересылать эту кэш-линию между ядрами через шину межсоединения (UPI/Infinity Fabric) в состоянии **Modified** протокола MESI/MOESI. Это явление называется **Cache Line Bouncing** и приводит к колоссальным задержкам (до 100-200 тактов на каждую запись вместо 4 тактов L1).

Чтобы изолировать переменные в разных кэш-линиях, применяется **Padding (структурный отступ)**:
```go
type PaddedCounters struct {
    A uint64
    _ [56]byte // 64 - 8 = 56 байт отступа
    B uint64
    _ [56]byte // изоляция хвоста структуры
}
```
В стандартной библиотеке Go для этого используется специальный тип `cpu.CacheLinePad` из внутреннего пакета `internal/cpu`:
```go
type CacheLinePad struct{ _ [cpu.CacheLinePadSize]byte }
```
На 64-битных x86_64 и ARM64 размер кэш-линии составляет 64 байта (на некоторых IBM z Systems — 128 или 256 байт). За счет добавления отступа каждое поле попадает в персональную строку кэша, позволяя ядрам параллельно держать свои копии в эксклюзивном состоянии (Exclusive/Modified) без инвалидации соседей.

## Решение по шагам

1. Объявите две структуры: `UnpaddedCounters` (два поля `uint64` подряд) и `PaddedCounters` (поля `uint64` разделены массивом `_ [56]byte`).
2. Создайте две параллельные горутины, одна из которых атомарно инкрементирует поле `A`, а вторая — поле `B`.
3. Измерьте время выполнения фиксированного количества итераций (например, 20 000 000 операций) для обеих структур с помощью `sync.WaitGroup`.
4. Сравните пропускную способность: убедитесь, что вариант с padding выполняется в 3–10 раз быстрее при высоких уровнях параллелизма.
5. Продемонстрируйте проверку смещений полей через `unsafe.Offsetof`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
	"unsafe"
)

type UnpaddedCounters struct {
	A uint64
	B uint64
}

type PaddedCounters struct {
	A uint64
	_ [56]byte // Выравнивание до границы 64-байтной кэш-линии
	B uint64
	_ [56]byte
}

func benchmarkUnpadded(iters int) time.Duration {
	var c UnpaddedCounters
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&c.A, 1)
		}
	}()
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&c.B, 1)
		}
	}()
	wg.Wait()
	return time.Since(start)
}

func benchmarkPadded(iters int) time.Duration {
	var c PaddedCounters
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&c.A, 1)
		}
	}()
	go func() {
		defer wg.Done()
		for i := 0; i < iters; i++ {
			atomic.AddUint64(&c.B, 1)
		}
	}()
	wg.Wait()
	return time.Since(start)
}

func main() {
	fmt.Println("=== Бенчмарк False Sharing vs Padding ===")
	var unpadded UnpaddedCounters
	var padded PaddedCounters

	fmt.Printf("Unpadded: Size=%d, Offset(A)=%d, Offset(B)=%d\n",
		unsafe.Sizeof(unpadded), unsafe.Offsetof(unpadded.A), unsafe.Offsetof(unpadded.B))
	fmt.Printf("Padded:   Size=%d, Offset(A)=%d, Offset(B)=%d\n",
		unsafe.Sizeof(padded), unsafe.Offsetof(padded.A), unsafe.Offsetof(padded.B))

	const iters = 20_000_000
	dUnpadded := benchmarkUnpadded(iters)
	dPadded := benchmarkPadded(iters)

	fmt.Printf("Время без padding: %v\n", dUnpadded)
	fmt.Printf("Время с padding:   %v\n", dPadded)
	if dPadded < dUnpadded {
		ratio := float64(dUnpadded) / float64(dPadded)
		fmt.Printf("Ускорение с padding: %.2fx\n", ratio)
	}
}
```

ℹ️ Устранение конкуренции за кэш-линию с помощью ручного padding в 56 байт.

## Под капотом

На аппаратном уровне протокол когерентности MESI оперирует исключительно 64-байтными строками, а не отдельными переменными. Когда ядро 0 выполняет `LOCK XADD` по адресу `&c.A`, оно должно получить строку кэша в состоянии Exclusive/Modified. Для этого контроллер рассылает по шине RFO (Request For Ownership). Ядро 1, выполняющее операцию над `&c.B`, получает инвалидацию (Invalidate Line), сбрасывает свою строку L1 в состояние Invalid и при следующей записи обращается к L3/DRAM. Добавление 56 байт разносит `&c.A` и `&c.B` по разным линиям кэша: ядро 0 владеет линией N, а ядро 1 — линией N+1, полностью исключая взаимные инвалидации.

## Подводные камни

1. Избыточный расход памяти: добавление padding в миллионы мелких объектов быстро исчерпает оперативную память и снизит плотность данных в L3 кэше.
2. Архитектурная зависимость: размер кэш-линии на некоторых процессорах (например, Apple M-серии performance-ядра или серверные IBM) может составлять 128 байт.
3. Пропуск хвостового padding: если структура размещается в слайсе `[]PaddedCounters`, без второго padding `_ [56]byte` в конце поле `B` элемента `i` окажется в одной линии с полем `A` элемента `i+1`!
