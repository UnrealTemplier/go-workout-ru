# Взаимосвязь выравнивания структур и классов размеров памяти в Go runtime

## Условие

Исследуйте связь между выравниванием пользовательских структур данных и классами размеров аллокатора памяти Go (Size Classes в mcache/mspan). Покажите, как сокращение структуры всего на 1 байт может перевести объект в меньший Size Class, сократив расход памяти в 2 раза.

### Исходная формулировка

**Блок 28 (Alignment)**: — начните после Блока 2 (аллокатор), так как `mcache`/`mspan` тесно связаны с alignment. Понимание `unsafe` из Блока 4 обязательно для измерения layout.

## Теория

Аллокатор памяти Go делит память кучи на **67 фиксированных классов размеров (Size Classes)**:
`8, 16, 24, 32, 48, 64, 80, 96, 112, 128, ...` байт (до 32 КБ).

Когда приложение запрашивает аллокацию структуры в куче через `new` или `&MyStruct{}`:
1. Аллокатор вычисляет размер структуры `unsafe.Sizeof(MyStruct{})`.
2. Размер округляется **вверх** до ближайшего поддерживаемого Size Class.

**Эффект пограничного размера (Size Class Boundary Effect)**:
* Если структура занимает **65 байт** (например, из-за неоптимального расположения полей или лишнего байта):
  * Она **не помещается** в класс 64 байта!
  * Аллокатор выделяет для нее блок из следующего класса — **80 байт** (15 байт внутренней фрагментации памяти впустую на каждый объект).
* Для структуры размером 1025 байт аллокатор выделит 1280 байт!
* Оптимизация расположения полей структуры возвращает ее в класс 64 байта, экономя мегабайты памяти и повышая кэш-локальность.

## Решение по шагам

1. Создайте структуру `PoorlyAligned` размером 65 байт.
2. Создайте структуру `OptimizedAligned` с тем же набором полей, упакованную в 56-64 байта.
3. Продемонстрируйте реальный размер аллокации в куче через `testing.AllocsPerRun`.
4. Рассчитайте процент неиспользуемой памяти (Internal Fragmentation).
5. Покажите таблицу базовых классов размеров Go runtime.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// PoorlyAligned: размер 40 байт из-за неоптимального порядка полей
type PoorlyAligned struct {
	A bool   // 1 байт
	B uint64 // 8 байт (padding 7 байт перед B)
	C bool   // 1 байт
	D uint64 // 8 байт (padding 7 байт перед D)
	E bool   // 1 байт (padding 7 байт в конце)
}

// OptimizedAligned: размер ровно 24 байта (те же самые поля!)
type OptimizedAligned struct {
	B uint64 // 8 байт
	D uint64 // 8 байт
	A bool   // 1 байт
	C bool   // 1 байт
	E bool   // 1 байт
	_ [5]byte // 5 байт выравнивания до 24
}

func main() {
	var p PoorlyAligned
	var o OptimizedAligned

	fmt.Println("=== Влияние порядка полей на классы размеров аллокатора ===")
	fmt.Printf("PoorlyAligned:    размер = %d байт (попадает в Size Class 48B)\n", unsafe.Sizeof(p))
	fmt.Printf("OptimizedAligned: размер = %d байт (попадает в Size Class 24B)\n\n", unsafe.Sizeof(o))

	const count = 10_000_000
	ramPoor := (count * 48) / (1024 * 1024)
	ramOpt := (count * 24) / (1024 * 1024)

	fmt.Printf("Расход RAM на %d объектов:\n", count)
	fmt.Printf("- Неоптимальная структура: %d МБ\n", ramPoor)
	fmt.Printf("- Оптимизированная:         %d МБ (экономия 50%% RAM!)\n", ramOpt)
}
```

ℹ️ Упорядочивание полей по убыванию размера переводит структуру в меньший класс аллокатора Go.

## Под капотом

Аллокатор TCMalloc / Go runtime сопоставляет объекты со спанами фиксированных размеров (`mspan`). В спане класса 48B на странице 8 КБ помещается 170 объектов. В спане класса 24B на той же странице умещается 341 объект — ровно в 2 раза больше! Удвоение плотности объектов на страницу памяти снижает нагрузку на сборщик мусора и объем вытеснения кэш-линий процессора.

## Подводные камни

1. Преждевременная микрооптимизация структур, которые создаются в количестве 1-2 штук на приложение.
2. Ухудшение читаемости кода: логическая группировка полей иногда важнее 4 байт экономии, если структура не находится в горячем слайсе.

## На собеседовании

Вопрос: «По какому правилу нужно упорядочивать поля в Go структуре для минимизации ее размера?». Ответ: по убыванию размера типов — сначала 8-байтные поля (`int64`, указатели, срезы, строки), затем 4-байтные (`int32`), 2-байтные (`int16`) и в конце 1-байтные (`bool`, `byte`). Это сводит структурный padding компилятора к нулю.
