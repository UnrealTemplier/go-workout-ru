# Тестирование на реальном железе: почему микро-бенчмарки на ноутбуке обманывают

## Условие

Проанализируйте фундаментальные архитектурные различия между процессорами ноутбуков (Apple Silicon, Intel Core i7) и серверными платформами (AMD EPYC, Intel Xeon NUMA). Объясните, почему оптимизации кэш-памяти обязаны тестироваться на реальном серверном оборудовании.

### Исходная формулировка

**Test на real hardware.**: Microbenchmarks на laptop могут не отражать production behavior. Тестируйте на real servers с similar CPU, memory, NUMA topology.

## Теория

Микро-бенчмарк, показавший ускорение в 2 раза на ноутбуке разработчика, может показать **замедление в 3 раза** на продакшен-сервере!

Причины кардинальных расхождений между мобильными и серверными CPU:
1. **Размер кэш-линии**: на Apple M-серии (M1/M2/M3) производительные ядра имеют кэш-линию размером **128 байт**, тогда как серверные x86_64 используют **64 байта**. Padding в 56 байт на Mac не спасет от False Sharing!
2. **Топология NUMA**: в ноутбуке 1 сокет с общей памятью (UMA). В сервере — 2–4 сокета с разными задержками доступа к DRAM (NUMA).
3. **Размер L3 кэша**: ноутбук имеет 8–16 МБ SLC, а серверные процессоры (AMD 3D V-Cache) — до **768–1152 МБ L3 кэша**! То, что на ноутбуке вылетает в медленную DRAM, на сервере может целиком уместиться в L3.
4. **Конкуренция ядер**: на ноутбуке тест идет на 4–8 ядрах, на сервере — на 128–256 потоках, где протокол MESI создает лавинообразный трафик когерентности.

## Решение по шагам

1. Напишите программу инспекции архитектурных параметров текущего процессора: `runtime.GOARCH`, `runtime.NumCPU()`.
2. Смоделируйте структуру с параметризуемым размером padding (64 байта vs 128 байт).
3. Составьте сравнительную матрицу характеристик мобильных и серверных платформ.
4. Продемонстрируйте конфигурацию CI-раннеров с bare-metal серверами.
5. Сформулируйте правила валидации производительности перед деплоем.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

type ArchitectureReport struct {
	Arch      string
	OS        string
	NumCPU    int
	PtrSize   int
	CacheLine int
}

func InspectArchitecture() ArchitectureReport {
	ptrSize := int(unsafe.Sizeof(uintptr(0)))
	cacheLine := 64
	// На Apple Silicon (darwin/arm64) размер строки кэша L1 часто равен 128 байтам
	if runtime.GOOS == "darwin" && runtime.GOARCH == "arm64" {
		cacheLine = 128
	}
	return ArchitectureReport{
		Arch:      runtime.GOARCH,
		OS:        runtime.GOOS,
		NumCPU:    runtime.NumCPU(),
		PtrSize:   ptrSize,
		CacheLine: cacheLine,
	}
}

func main() {
	rep := InspectArchitecture()
	fmt.Println("=== Отчет об архитектуре текущей среды исполнения ===")
	fmt.Printf("Архитектура ЦПУ:             %s\n", rep.Arch)
	fmt.Printf("Операционная система:        %s\n", rep.OS)
	fmt.Printf("Доступно логических ядер:   %d\n", rep.NumCPU)
	fmt.Printf("Разрядность указателей:      %d бит (%d байт)\n", rep.PtrSize*8, rep.PtrSize)
	fmt.Printf("Ожидаемый размер кэш-линии:  %d байт\n", rep.CacheLine)

	fmt.Println("\nПредостережение для HighLoad оптимизаций:")
	fmt.Println("1. Padding в 64 байта недостаточен для платформ с 128B кэш-линиями (Apple M-серия).")
	fmt.Println("2. Отсутствие NUMA на рабочей станции маскирует задержки памяти многосокетных серверов.")
	fmt.Println("3. Финальный бенчмарк ОБЯЗАН выполняться на staging-сервере с идентичным CPU.")
}
```

ℹ️ Архитектурный аудит платформы выявляет различия в кэш-линиях и топологии ядер.

## Под капотом

Серверные платформы используют сложную ячеистую топологию межсоединений (Mesh Interconnect в Intel Xeon Skylake/Ice Lake или Infinity Fabric в AMD EPYC). Задержка передачи строки кэша между ядрами на противоположных концах кристалла может превышать 40 нс, чего невозможно воспроизвести на компактном кристалле ноутбука.

## Подводные камни

1. Оптимизация под архитектуру разработчика: код, заточенный под особенности конкретного ноутбука, может стать пессимизацией на целевом сервере в дата-центре.
2. Игнорирование виртуализации: шумные соседи (Noisy Neighbors) в облачных виртуальных машинах (AWS EC2, Yandex Cloud) искажают результаты тестов.

## На собеседовании

Вопрос на собеседовании: «Почему мы не доверяем результатам бенчмарков, запущенных на MacBook разработчика?». Ответ: разные микроархитектуры (ARM big.LITTLE vs x86-64 серверные ядра), разные размеры кэш-линий (128B vs 64B), отсутствие NUMA и динамический троттлинг частот при нагреве аккумулятора.
