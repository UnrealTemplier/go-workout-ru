# Чанкованные массивы (Chunked Arrays / Unrolled Linked List)

## Условие

Реализуйте чанкованный динамический массив (Chunked Array / Unrolled Linked List), состоящий из узлов-блоков фиксированного размера (по 64 элемента). Сравните его с классическим append в стандартном срезе и покажите устранение дорогих реаллокаций и фрагментации памяти.

### Исходная формулировка

**Chunked arrays**: Для dynamic arrays используйте chunked arrays (array of arrays). Это избегает expensive reallocation и улучшает cache locality.

## Теория

При росте стандартного слайса (`append`) рантайм Go периодически выполняет реаллокацию:
1. Выделяется новый непрерывный блок памяти в 1.25–2 раза большего размера.
2. Все старые элементы копируются (`memmove`) в новый блок.
3. Старый блок выбрасывается и ожидает сборки мусора (GC).

На больших объемах (сотни миллионов элементов) реаллокация приводит к задержкам на копирование гигабайт памяти и резким всплескам потребления RAM (2x-3x от реального размера).

**Чанкованный массив (Chunked Array / Bounded Deque)** решает эту проблему:
* Память выделяется порциями (чанками) фиксированного размера (например, по 64 или 512 элементов).
* Внутри каждого чанка элементы расположены непрерывно, сохраняя идеальную кэш-локальность L1.
* Добавление новых элементов требует лишь аллокации очередного небольшого чанка без копирования ранее добавленных миллионов записей.

## Решение по шагам

1. Создайте структуру `Chunk` с фиксированным массивом `[64]int64` и счетчиком элементов.
2. Создайте структуру `ChunkedArray` со срезом указателей на чанки `[]*Chunk`.
3. Реализуйте метод `Append(val int64)`.
4. Реализуйте метод `Get(index int) int64` с быстрым вычислением индекса через деление и остаток (`index / 64`, `index % 64`).
5. Сравните скорость заполнения 10 000 000 элементов с обычным непредварительно выделенным срезом.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
	"unsafe"
)

const ChunkCapacity = 64
const ChunkShift = 6 // 2^6 = 64
const ChunkMask = ChunkCapacity - 1

type Chunk struct {
	Items [ChunkCapacity]int64
	Count int
}

type ChunkedArray struct {
	chunks []*Chunk
	length int
}

func NewChunkedArray() *ChunkedArray {
	return &ChunkedArray{
		chunks: []*Chunk{{}},
	}
}

func (ca *ChunkedArray) Append(val int64) {
	last := ca.chunks[len(ca.chunks)-1]
	if last.Count == ChunkCapacity {
		last = &Chunk{}
		ca.chunks = append(ca.chunks, last)
	}
	last.Items[last.Count] = val
	last.Count++
	ca.length++
}

func (ca *ChunkedArray) Get(index int) int64 {
	chunkIdx := index >> ChunkShift
	itemIdx := index & ChunkMask
	return ca.chunks[chunkIdx].Items[itemIdx]
}

func benchmarkStandardSlice(n int) time.Duration {
	start := time.Now()
	var s []int64
	for i := 0; i < n; i++ {
		s = append(s, int64(i))
	}
	_ = s
	return time.Since(start)
}

func benchmarkChunked(n int) time.Duration {
	start := time.Now()
	ca := NewChunkedArray()
	for i := 0; i < n; i++ {
		ca.Append(int64(i))
	}
	_ = ca
	return time.Since(start)
}

func main() {
	var c Chunk
	fmt.Printf("Размер Chunk: %d байт (кратен кэш-линии 64Б: %d)\n\n",
		unsafe.Sizeof(c), unsafe.Sizeof(c)/64)

	const n = 10_000_000
	fmt.Printf("Тестирование роста коллекций до %d элементов...\n", n)

	tSlice := benchmarkStandardSlice(n)
	fmt.Printf("Стандартный срез (множество memmove и realloc): %v\n", tSlice)

	tChunked := benchmarkChunked(n)
	fmt.Printf("ChunkedArray (стабильные чанки без memmove):     %v\n", tChunked)

	ca := NewChunkedArray()
	for i := 0; i < 1000; i++ {
		ca.Append(int64(i * 10))
	}
	fmt.Printf("Проверка чтения: ca.Get(500) = %d\n", ca.Get(500))
}
```

ℹ️ Чанкованный массив обеспечивает локальность кэша внутри блоков без тяжелых реаллокаций памяти.

## Под капотом

Когда стандартный срез расширяется с 8 МБ до 16 МБ, аллокатор ищет непрерывный участок виртуальной памяти, а `runtime.memmove` копирует 8 МБ данных, вымывая кэш L1/L2. В `ChunkedArray` каждый чанк занимает ровно \(64 \times 8 + 8 = 520\) байт. Аллокатор Go мгновенно берет его из готового класса размеров (size class 576B) в локальном `mcache` без обращения к глобальному распределителю кучи.

## Подводные камни

1. Накладные расходы на адресацию: чтение по произвольному индексу требует двойного разыменования указателя (`ca.chunks[c].Items[i]`).
2. Потребление памяти на срез указателей чанков при миллиардах элементов.

## На собеседовании

Вопрос: «Как устроен deque (двусторонняя очередь) в C++ std::deque и почему он часто быстрее std::vector при частых вставках?». Ответ: `std::deque` и unrolled lists построены как чанкованные массивы (массив указателей на фиксированные буферы), что устраняет необходимость перемещения ранее выделенных элементов при росте емкости.
