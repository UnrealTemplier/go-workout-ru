# Кэш-эффективные хэш-таблицы: Open Addressing vs Separate Chaining

## Условие

Реализуйте хэш-таблицу с открытой адресацией (Open Addressing) и линейным пробированием (Linear Probing). Сравните скорость поиска с хэш-таблицей на цепочках (Separate Chaining) и объясните превосходство открытой адресации за счет стриминга кэш-линий.

### Исходная формулировка

**Cache-friendly hash table**: Open addressing с linear probing имеет лучшую cache locality, чем separate chaining.

## Теория

Существует два классических подхода к разрешению коллизий в хэш-таблицах:

1. **Цепочки (Separate Chaining)**: каждый бакет хранит указатель на связный список коллизий (`*Node`).
   * При коллизии процессор совершает переход по указателю в случайную область кучи.
   * Каждый узел цепочки аллоцируется отдельно, вызывая Cache Miss и фрагментацию.

2. **Открытая адресация (Open Addressing с Linear Probing)**:
   * Все ключи и значения хранятся в **едином плоском непрерывном массиве**.
   * При возникновении коллизии алгоритм просто проверяет следующую ячейку: \(Slot_{next} = (Slot + 1) \pmod N\).
   * Соседние слоты уже подгружены в ту же самую кэш-линию L1! Проверка коллизий выполняется со скоростью регистров процессора.

## Решение по шагам

1. Реализуйте простую хэш-таблицу `LinearProbingMap` на основе плоского массива слотов.
2. Реализуйте хэш-таблицу `ChainingMap`, где бакеты содержат связанный список узлов.
3. Заполните обе таблицы 500 000 элементов с одинаковым коэффициентом заполнения (Load Factor ~0.6).
4. Выполните 1 000 000 случайных операций поиска (`Get`).
5. Сравните пропускную способность.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const MapCap = 1 << 20 // 1 048 576
const Mask = MapCap - 1

// Linear Probing: плоский массив в кэше
type Slot struct {
	Key   uint64
	Value uint64
	Used  bool
}

type LinearProbingMap struct {
	slots [MapCap]Slot
}

func (m *LinearProbingMap) Put(k, v uint64) {
	idx := (k * 11400714819323198485) & Mask
	for {
		if !m.slots[idx].Used || m.slots[idx].Key == k {
			m.slots[idx].Key = k
			m.slots[idx].Value = v
			m.slots[idx].Used = true
			return
		}
		idx = (idx + 1) & Mask
	}
}

func (m *LinearProbingMap) Get(k uint64) (uint64, bool) {
	idx := (k * 11400714819323198485) & Mask
	for {
		if !m.slots[idx].Used {
			return 0, false
		}
		if m.slots[idx].Key == k {
			return m.slots[idx].Value, true
		}
		idx = (idx + 1) & Mask
	}
}

// Chaining: связанные списки с указателями
type ChainNode struct {
	Key   uint64
	Value uint64
	Next  *ChainNode
}

type ChainingMap struct {
	buckets [MapCap]*ChainNode
}

func (m *ChainingMap) Put(k, v uint64) {
	idx := (k * 11400714819323198485) & Mask
	head := m.buckets[idx]
	for curr := head; curr != nil; curr = curr.Next {
		if curr.Key == k {
			curr.Value = v
			return
		}
	}
	m.buckets[idx] = &ChainNode{Key: k, Value: v, Next: head}
}

func (m *ChainingMap) Get(k uint64) (uint64, bool) {
	idx := (k * 11400714819323198485) & Mask
	for curr := m.buckets[idx]; curr != nil; curr = curr.Next {
		if curr.Key == k {
			return curr.Value, true
		}
	}
	return 0, false
}

func main() {
	const elements = 600_000
	const lookups = 2_000_000

	lpMap := new(LinearProbingMap)
	chMap := new(ChainingMap)

	fmt.Printf("Заполнение хэш-таблиц %d элементами...\n", elements)
	for i := uint64(1); i <= elements; i++ {
		lpMap.Put(i, i*10)
		chMap.Put(i, i*10)
	}

	startLP := time.Now()
	var foundLP uint64
	for i := uint64(1); i <= lookups; i++ {
		k := (i % elements) + 1
		if v, ok := lpMap.Get(k); ok {
			foundLP += v
		}
	}
	dLP := time.Since(startLP)
	fmt.Printf("Linear Probing (Open Addressing): %v\n", dLP)

	startCH := time.Now()
	var foundCH uint64
	for i := uint64(1); i <= lookups; i++ {
		k := (i % elements) + 1
		if v, ok := chMap.Get(k); ok {
			foundCH += v
		}
	}
	dCH := time.Since(startCH)
	fmt.Printf("Chaining (Связные списки):        %v\n", dCH)

	if dLP < dCH {
		fmt.Printf("Open Addressing быстрее в %.2fx раз благодаря непрерывному размещению в L1-кэше!\n",
			float64(dCH)/float64(dLP))
	}
	_ = foundLP
	_ = foundCH
}
```

ℹ️ Линейное пробирование в непрерывном массиве полностью устраняет разыменования указателей.

## Под капотом

В `LinearProbingMap` плоский массив слотов загружается в кэш процессора строками по 64 байта. Слот занимает 24 байта, то есть в одну строку кэша попадает почти 3 слота. При пробировании коллизии процессор уже имеет следующие слоты в локальном L1, а аппаратный префетчер загружает следующие. В `ChainingMap` каждый узел `ChainNode` выделяется в отдельном фрагменте кучи, и переход `curr = curr.Next` с высокой вероятностью приводит к задержке в 150-250 тактов на ожидание шины памяти.

## Подводные камни

1. Кластеризация (Primary Clustering): при высоком Load Factor (> 0.75-0.8) цепочки коллизий в Linear Probing сливаются в длинные кластеры, что замедляет вставку.
2. Сложность удаления: просто обнулить слот нельзя, иначе разорвется цепочка пробирования (требуется tombstone-маркер или backward-shift сдвиг).

## На собеседовании

Вопрос: «Почему в современных языках (Rust hashbrown, C++ absl::flat_hash_map, Go 1.24 swissmap) отказались от связных списков в мапах в пользу открытой адресации?». Ответ: из-за Memory Wall. Стоимость разыменования указателя на современном процессоре эквивалентна сотням инструкций сложения или побитовых масок. Открытая адресация обеспечивает 100% пространственную локальность.
