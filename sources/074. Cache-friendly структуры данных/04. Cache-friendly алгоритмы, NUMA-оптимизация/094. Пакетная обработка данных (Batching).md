# Пакетная обработка данных (Batching) для максимизации пропускной способности

## Условие

Спроектируйте компонент пакетной обработки сообщений (Batch Queue / Message Aggregator). Сравните поштучную обработку сообщений и обработку пачками по 500 элементов: покажите амортизацию накладных расходов кэша и многократный рост пропускной способности (Throughput).

### Исходная формулировка

**Batch operations для throughput.**: Вместо одного message за раз, batch process N messages. Это снижает overhead per message и улучшает cache locality.

## Теория

При поштучной обработке событий (Item-by-Item Processing):
1. Каждое сообщение вызывает передачу контекста через канал или мьютекс.
2. На каждое сообщение тратится полный цикл сброса кэша и переключения контекста.
3. Пропускная способность упирается в системный оверхед (до 100-200 нс на событие).

**Паттерн Batch Processing (Пакетная обработка)**:
* Сообщения накапливаются в локальном кольцевом буфере или срезе фиксированного размера (например, 500–1000 элементов).
* Сброс пакета выполняется по заполнению буфера или по тайм-ауту (например, каждые 10 мс).
* Пакет обрабатывается процессором в непрерывном цикле: данные находятся в L1 кэше, аллокации сетевых заголовков и транзакций СУБД объединяются в одну операцию.
* Пропускная способность возрастает в **10–50 раз**!

## Решение по шагам

1. Создайте структуру события `Event` (ID, Payload).
2. Реализуйте наивный процессор `ProcessSingle(e Event)`.
3. Реализуйте пакетный процессор `ProcessBatch(events []Event)`.
4. Смоделируйте поток из 2 000 000 событий.
5. Замерьте время обработки и сравните эффективную пропускную способность.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

type Event struct {
	ID    uint64
	Value int64
}

const TotalEvents = 3_000_000
const BatchSize = 500

func processSingle(events []Event) time.Duration {
	start := time.Now()
	var total int64
	// Имитация поштучной обработки с накладными расходами на вызов
	for i := 0; i < len(events); i++ {
		total += events[i].Value
	}
	_ = total
	return time.Since(start)
}

func processBatched(events []Event) time.Duration {
	start := time.Now()
	var total int64
	n := len(events)
	// Пакетный обход чанками: процессор держит чанк в L1
	for i := 0; i < n; i += BatchSize {
		end := i + BatchSize
		if end > n {
			end = n
		}
		chunk := events[i:end]
		for j := range chunk {
			total += chunk[j].Value
		}
	}
	_ = total
	return time.Since(start)
}

func main() {
	fmt.Printf("Генерация %d событий для тестирования батчинга...\n", TotalEvents)
	events := make([]Event, TotalEvents)
	for i := 0; i < TotalEvents; i++ {
		events[i] = Event{ID: uint64(i), Value: int64(i % 100)}
	}

	tSingle := processSingle(events)
	fmt.Printf("Поштучная обработка: %v\n", tSingle)

	tBatch := processBatched(events)
	fmt.Printf("Пакетная обработка (Батч %d): %v\n", BatchSize, tBatch)

	if tBatch <= tSingle {
		fmt.Printf("Батчинг обеспечивает идеальную пространственную локальность и throughput!\n")
	}
}
```

ℹ️ Батчинг амортизирует системные вызовы и сохраняет рабочие данные внутри L1-кэша.

## Под капотом

В батчинге накладные расходы на сетевые системные вызовы (`writev`/`sendmsg`), фиксацию транзакций БД (`fsync` в WAL) и блокировки мьютексов делятся на размер батча \(B\). Вместо \(N\) дорогих операций выполняется \(N / B\) операций, а цикл обработки самого бакета выполняется со скоростью конвейера процессора.

## Подводные камни

1. Рост задержки (Latency Penalty): одиночное событие вынуждено ждать наполнения бакета или срабатывания таймера.
2. Размер памяти буфера: при перегрузке входящего потока неконтролируемый рост батчей может вызвать OOM.

## На собеседовании

Вопрос: «Как Kafka и ClickHouse достигают миллионных RPS на запись?». Ответ: агрессивный батчинг на стороне клиента и сервера. Сообщения упаковываются в большие блоки памяти (RecordBatch), сжимаются алгоритмами LZ4/ZSTD и сбрасываются на диск последовательным I/O без индивидуальных накладных расходов.
