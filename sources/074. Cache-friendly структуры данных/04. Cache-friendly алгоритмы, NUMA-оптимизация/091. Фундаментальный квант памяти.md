# Фундаментальный квант памяти: кэш-линия 64 байта и правила ко-локации

## Условие

Сформулируйте и программно подтвердите золотые правила проектирования структур данных вокруг 64-байтной кэш-линии: ко-локация полей совместного чтения (Co-location) и разнесение полей параллельной записи (Isolation).

### Исходная формулировка

**Cache line — это 64 байта.**: Всё, что вы делаете, должно учитывать этот факт. Структуры, которые используются вместе, должны быть в одной cache line. Структуры, которые используются разными threads, должны быть в разных cache lines.

## Теория

Физическая архитектура процессоров x86 и ARM устроена так, что **квантом передачи данных между кэшем и памятью всегда является 64-байтная кэш-линия**. Процессор никогда не читает и не пишет 1 байт — он всегда загружает и сохраняет строку целиком.

Отсюда следуют два фундаментальных закона HighLoad проектирования:
1. **Правило ко-локации (Co-location for Read-Together Data)**: поля структуры, которые логически используются вместе в одной операции (например, `UserID`, `AccountBalance`, `CurrencyCode`), обязаны находиться в **одной 64-байтной кэш-линии**. Первое обращение подтягивает все остальные поля бесплатно.
2. **Правило изоляции (Isolation for Independent Writes)**: поля, которые параллельно модифицируются разными горутинами/ядрами, обязаны находиться в **разных кэш-линиях**, будучи разделенными структурным padding в 56-64 байта.

## Решение по шагам

1. Создайте структуру `CoLocatedProfile` размером ровно до 64 байт с полями совместного чтения.
2. Создайте структуру с изолированными счетчиками записи.
3. Продемонстрируйте замер смещений всех полей с помощью `unsafe.Offsetof`.
4. Покажите, как упаковать данные так, чтобы операция чтения профиля выполнялась за 1 Cache Hit.
5. Сформулируйте правила компоновки полей.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// CoLocatedProfile: ровно 64 байта (1 кэш-линия)
// Все поля, необходимые для валидации транзакции, подгружаются за 1 обращение к памяти
type CoLocatedProfile struct {
	UserID     uint64  // offset 0 (8B)
	Balance    int64   // offset 8 (8B)
	Status     uint32  // offset 16 (4B)
	Currency   [4]byte // offset 20 (4B)
	LastTxTime int64   // offset 24 (8B)
	RiskScore  float32 // offset 32 (4B)
	Flags      uint32  // offset 36 (4B)
	_          [24]byte // offset 40 (24B padding до ровно 64 байт)
}

func main() {
	var p CoLocatedProfile
	size := unsafe.Sizeof(p)
	fmt.Println("=== Анатомия структуры под 64-байтную кэш-линию ===")
	fmt.Printf("Общий размер CoLocatedProfile: %d байт (ровно 1 строка кэша!)\n", size)

	fmt.Printf("UserID:     offset=%2d, size=%d\n", unsafe.Offsetof(p.UserID), unsafe.Sizeof(p.UserID))
	fmt.Printf("Balance:    offset=%2d, size=%d\n", unsafe.Offsetof(p.Balance), unsafe.Sizeof(p.Balance))
	fmt.Printf("Status:     offset=%2d, size=%d\n", unsafe.Offsetof(p.Status), unsafe.Sizeof(p.Status))
	fmt.Printf("Currency:   offset=%2d, size=%d\n", unsafe.Offsetof(p.Currency), unsafe.Sizeof(p.Currency))
	fmt.Printf("LastTxTime: offset=%2d, size=%d\n", unsafe.Offsetof(p.LastTxTime), unsafe.Sizeof(p.LastTxTime))
	fmt.Printf("RiskScore:  offset=%2d, size=%d\n", unsafe.Offsetof(p.RiskScore), unsafe.Sizeof(p.RiskScore))

	fmt.Println("\nВывод: обращение к любому полю транзакции гарантированно загружает все остальные поля профиля в L1.")
}
```

ℹ️ Упаковка критических полей сущности ровно в 64 байта гарантирует их чтение за 1 кэш-линию.

## Под капотом

Когда процессор исполняет инструкцию проверки баланса `MOVQ 8(%rax), %rbx`, контроллер кэша считывает 64 байта по базовому выровненному адресу. В результате `Status`, `Currency`, `RiskScore` и `Flags` уже находятся в локальном L1 Data Cache ядра. Последующие инструкции проверки флагов и валюты исполняются за 1 такт без обращений к шине памяти.

## Подводные камни

1. Пересечение границы кэш-линии (Cache Line Splitting): если поле `uint64` начинается по смещению 60 байт, оно будет разбито между двумя кэш-линиями (первые 4 байта в строке N, следующие 4 байта в строке N+1), что удвоит количество обращений к памяти.
2. Неучет выравнивания аллокатором.

## На собеседовании

Вопрос: «Что такое Split Load / Split Store в терминах кэша ЦПУ?». Ответ: ситуация, когда переменная или структура пересекает 64-байтную границу кэш-линии, из-за чего процессору требуются две отдельные операции чтения памяти и блокировка двух строк кэша для атомарного чтения, что снижает скорость в 2–3 раза.
