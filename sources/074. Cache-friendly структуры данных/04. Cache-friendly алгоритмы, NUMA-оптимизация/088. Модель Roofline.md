# Модель Roofline: определение Compute-Bound vs Memory-Bound кода

## Условие

Исследуйте модель Roofline (Roofline Model) для анализа производительности алгоритмов в Go. Рассчитайте вычислительную плотность (Operational Intensity = FLOPs / Byte) для векторного сложения и матричного умножения и определите, упирается ли ваш алгоритм в пропускную способность оперативной памяти (Memory-Bound) или в тактовую частоту процессора (Compute-Bound).

### Исходная формулировка

**Roofline model**: Постройте roofline model для вашего кода: сравните computational intensity (FLOPs/byte) с memory bandwidth и compute throughput. Это покажет, memory-bound или compute-bound ваш код.

## Теория

**Модель Roofline (Roofline Model)** связывает производительность процессора (\(GFLOPS\)) с вычислительной плотностью алгоритма (\(I = \text{FLOPs} / \text{Byte}\)) и физическими характеристиками платформы:
1. **Пиковая вычислительная производительность процессора (\(P_{peak}\))** — потолок «крыши» (Compute Ceiling).
2. **Пиковая пропускная способность памяти (\(B_{peak}\))** — наклонная стена «крыши» (Memory Bandwidth Wall):
$$P(I) = \min(P_{peak}, I \times B_{peak})$$

* **Memory-Bound (Ограничено памятью)**: если \(I < \frac{P_{peak}}{B_{peak}}\) (например, для сложения векторов \(Z_i = X_i + Y_i\): 1 операция с плавающей точкой на 24 прочитанных/записанных байта \(\implies I \approx 0.04\) FLOPs/Byte). Добавление ядер процессора не ускорит алгоритм, так как шина памяти DDR5 загружена на 100%. Оптимизация заключается в улучшении кэш-локальности и сжатии данных.
* **Compute-Bound (Ограничено вычислениями)**: если \(I\) велико (например, блочное матричное умножение: \(O(N^3)\) операций на \(O(N^2)\) загруженных байт \(\implies I \gg 10\)). Узким местом являются конвейеры ALU/FPU.

## Решение по шагам

1. Напишите алгоритм векторного сложения `VectorAdd` (типичный Memory-Bound).
2. Напишите алгоритм полиномиального вычисления `PolynomialCompute` с высокой вычислительной плотностью (Compute-Bound).
3. Измерьте время выполнения, объем прочитанных байт и число выполненных арифметических операций.
4. Рассчитайте Operational Intensity для обоих алгоритмов.
5. Сформулируйте рекомендации по оптимизации для обоих классов задач.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const N = 10_000_000

// Memory-Bound: 1 FLOP на 24 байта (чтение A, B + запись C).
// Operational Intensity = 1 / 24 = 0.041 FLOPs/Byte
func runMemoryBound(A, B, C []float64) time.Duration {
	start := time.Now()
	for i := 0; i < N; i++ {
		C[i] = A[i] + B[i]
	}
	return time.Since(start)
}

// Compute-Bound: 20 FLOPs на 8 прочитанных байт (чтение X[i] и расчет полинома 20-й степени).
// Operational Intensity = 20 / 8 = 2.5 FLOPs/Byte
func runComputeBound(X, Res []float64) time.Duration {
	start := time.Now()
	for i := 0; i < N; i++ {
		x := X[i]
		val := x
		// 20 итераций умножения и сложения в регистрах
		for k := 0; k < 20; k++ {
			val = val*1.0001 + 0.5
		}
		Res[i] = val
	}
	return time.Since(start)
}

func main() {
	fmt.Printf("Анализ Roofline для массива из %d элементов (%.2f МБ)...\n\n",
		N, float64(N*8)/(1024*1024))

	A := make([]float64, N)
	B := make([]float64, N)
	C := make([]float64, N)
	for i := 0; i < N; i++ {
		A[i] = 1.5
		B[i] = 2.5
	}

	// 1. Тест Memory-Bound
	dMem := runMemoryBound(A, B, C)
	bytesTransferred := float64(N * 3 * 8) // чтение A, B и запись C
	gbps := (bytesTransferred / 1e9) / dMem.Seconds()
	fmt.Printf("Memory-Bound (Vector Add):  %v (Пропускная способность: %.2f GB/s)\n", dMem, gbps)

	// 2. Тест Compute-Bound
	dCompute := runComputeBound(A, C)
	gflops := (float64(N*40) / 1e9) / dCompute.Seconds()
	fmt.Printf("Compute-Bound (Polynomial): %v (Производительность:    %.2f GFLOPs)\n", dCompute, gflops)
}
```

ℹ️ Roofline-анализ разделяет алгоритмы, ограниченные шиной памяти, от алгоритмов, ограниченных ALU.

## Под капотом

Если программа Memory-Bound, профилировщик `perf stat` покажет метрику `cycles` в состоянии простоя (Pipeline Stalls due to Memory Load / Dram Bound). Никакой рефакторинг кода или добавление векторных инструкций не поможет: узким местом является физическая шина DDR (обычно 40–80 ГБ/с на канал). Единственный способ ускорить Memory-Bound код — сократить объем передаваемых данных (сжатие структур, int32 вместо int64, SoA layout).

## Подводные камни

1. Оптимизация вычислений в Memory-Bound коде: попытка оптимизировать арифметические формулы в коде, упершемся в память, дает 0% эффекта.
2. Неучет влияния кэша: если данные умещаются в L1/L2, алгоритм перестает быть DRAM-bound.
