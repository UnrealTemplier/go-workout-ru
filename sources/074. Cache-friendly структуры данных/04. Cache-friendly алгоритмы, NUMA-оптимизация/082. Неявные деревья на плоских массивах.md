# Неявные деревья на плоских массивах (Implicit Tree / Eytzinger Layout)

## Условие

Реализуйте алгоритм двоичного поиска в отсортированном массиве с преобразованием в лейаут Эйтзингера (Eytzinger / BFS Tree Layout). Докажите, что неявное представление дерева в плоском массиве ускоряет поиск по сравнению со стандартным sort.Search за счет упреждающей загрузки кэш-линий.

### Исходная формулировка

**Cache-friendly tree**: Для деревьев используйте implicit tree layout (array-based heap). Parent at `i`, children at `2i+1` и `2i+2`.

## Теория

При обычном двоичном поиске (`Binary Search / sort.Search`) первые шаги алгоритма совершают гигантские скачки по массиву (\(N/2, N/4, 3N/4\)), гарантированно вызывая промах кэша на каждом шаге.

**Лейаут Эйтзингера (Eytzinger / Implicit Heap Layout)**:
* Элементы отсортированного массива переупорядочиваются в порядке обхода в ширину (Breadth-First Search):
  * Корень дерева находится по индексу `1`.
  * Левый потомок узла \(i\) находится по индексу \(2i\).
  * Правый потомок узла \(i\) находится по индексу \(2i+1\).
* Первые уровни дерева (корень, его дети и внуки — первые 8-16 элементов) компактно упакованы в **первую кэш-линию** массива!
* Первые 4–5 шагов двоичного поиска выполняются внутри одной-единственной кэш-линии L1 без единого Cache Miss!

## Решение по шагам

1. Создайте отсортированный срез чисел на 1 000 000 элементов.
2. Напишите функцию конвертации отсортированного массива в формат Эйтзингера `toEytzinger(sorted []int64) []int64`.
3. Реализуйте алгоритм поиска `searchEytzinger(tree []int64, val int64) int`.
4. Сравните скорость 1 000 000 поисков с классическим бинарным поиском.
5. Продемонстрируйте аппаратную утилизацию кэша.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"sort"
	"time"
)

// Конвертация отсортированного среза в лейаут Эйтзингера (1-based)
func buildEytzinger(sorted []int64) []int64 {
	n := len(sorted)
	eyt := make([]int64, n+1)
	curr := 0

	var inOrder func(k int)
	inOrder = func(k int) {
		if k > n {
			return
		}
		inOrder(2 * k)     // Левый ребенок
		eyt[k] = sorted[curr]
		curr++
		inOrder(2*k + 1) // Правый ребенок
	}

	inOrder(1)
	return eyt
}

// Поиск в дереве Эйтзингера: только ветвление по индексам 2k и 2k+1
func searchEytzinger(tree []int64, val int64) int {
	k := 1
	n := len(tree) - 1
	for k <= n {
		if tree[k] == val {
			return k
		}
		if val < tree[k] {
			k = 2 * k
		} else {
			k = 2*k + 1
		}
	}
	return -1
}

func main() {
	const size = 1_000_000
	const lookups = 500_000

	fmt.Printf("Подготовка %d отсортированных элементов...\n", size)
	data := make([]int64, size)
	for i := 0; i < size; i++ {
		data[i] = int64(i * 2)
	}

	eyt := buildEytzinger(data)
	fmt.Printf("Корень дерева Эйтзингера (L1 кэш): eyt[1]=%d\n", eyt[1])
	fmt.Printf("Потомки корня в той же кэш-линии:   eyt[2]=%d, eyt[3]=%d\n\n", eyt[2], eyt[3])

	lookupKeys := make([]int64, lookups)
	for i := 0; i < lookups; i++ {
		lookupKeys[i] = int64(rand.Intn(size * 2))
	}

	// 1. Классический двоичный поиск
	startStd := time.Now()
	foundStd := 0
	for _, k := range lookupKeys {
		idx := sort.Search(len(data), func(i int) bool { return data[i] >= k })
		if idx < len(data) && data[idx] == k {
			foundStd++
		}
	}
	dStd := time.Since(startStd)
	fmt.Printf("Классический sort.Search: %v\n", dStd)

	// 2. Поиск в лейауте Эйтзингера
	startEyt := time.Now()
	foundEyt := 0
	for _, k := range lookupKeys {
		if idx := searchEytzinger(eyt, k); idx != -1 {
			foundEyt++
		}
	}
	dEyt := time.Since(startEyt)
	fmt.Printf("Eytzinger Layout search:  %v\n", dEyt)

	if dEyt < dStd {
		fmt.Printf("Лейаут Эйтзингера быстрее в %.2fx раз!\n", float64(dStd)/float64(dEyt))
	}
	_ = foundStd
	_ = foundEyt
}
```

ℹ️ Упаковка верхних уровней дерева поиска в первые байты массива устраняет Cache Misses на старте поиска.

## Под капотом

В обычном двоичном поиске шаг 1 читает индекс \(N/2\), шаг 2 — \(N/4\), шаг 3 — \(N/8\). Это разные кэш-линии и разные страницы памяти (3 TLB/Cache Misses). В лейауте Эйтзингера узлы с 1 по 7 занимают ровно 56 байт (\(7 \times 8\)). Первые 3 шага поиска гарантированно происходят внутри первой 64-байтной кэш-линии, которая всегда находится в кэше L1.

## Подводные камни

1. Массив требует предварительного перестроения (O(N) времени), поэтому лейаут идеален для read-only статических словарей и поисковых индексов, но не подходит для частых вставок.
2. Необходимость выделения дополнительного массива размера N+1.

## На собеседовании

Вопрос на собеседовании в поисковые движки (Яндекс, Google Search Index): «Как оптимизировать статический бинарный поиск в миллионах ключей под архитектуру кэша ЦПУ?». Ответ: лейаут Эйтзингера (Eytzinger array layout) или B-Tree search, где верхние уровни дерева постоянно удерживаются в теплом кэше L1/L2.
