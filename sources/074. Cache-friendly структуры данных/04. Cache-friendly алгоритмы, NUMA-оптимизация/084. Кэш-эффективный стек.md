# Кэш-эффективный стек: плоский предвыделенный массив vs связный список

## Условие

Реализуйте стек (LIFO) на основе плоского предварительно выделенного слайса и сравните его со стеком на основе связанного списка указателей. Замерьте разницу в скорости операций Push/Pop и объясните эффект удержания верхушки стека в L1 кэше.

### Исходная формулировка

**Cache-friendly stack**: Flat array с pre-allocated capacity. Избегайте linked list stack.

## Теория

Стек — базовый примитив данных с семантикой LIFO (Last-In, First-Out).

В наивной реализации на связанных списках (`Linked List Stack`):
* Каждый `Push` аллоцирует новый узел `Node{val, next}` в куче.
* Каждый `Pop` освобождает узел, вынуждая GC удалять миллионы объектов.
* Узлы разбросаны по памяти: чтение узла приводит к промаху кэша.

В реализации на плоском массиве (`Array Stack`):
* Память предвыделяется один раз: `items := make([]T, capacity)`.
* `Push` и `Pop` просто инкрементируют или декрементируют целочисленный индекс `top`.
* **Верхушка стека всегда находится в L1 Data Cache процессора**: данные, только что положенные в стек, читаются из самого горячего регистра или строки кэша за 1 такт!

## Решение по шагам

1. Создайте `LinkedStack` с узлами и указателями `next`.
2. Создайте `ArrayStack` с фиксированной емкостью и полем `top int`.
3. Смоделируйте 5 000 000 операций попеременного `Push` и `Pop`.
4. Сравните время выполнения.
5. Продемонстрируйте разницу в количестве аллокаций памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

type Node struct {
	val  int64
	next *Node
}

type LinkedStack struct {
	top *Node
}

func (s *LinkedStack) Push(v int64) {
	s.top = &Node{val: v, next: s.top}
}

func (s *LinkedStack) Pop() int64 {
	if s.top == nil {
		return 0
	}
	v := s.top.val
	s.top = s.top.next
	return v
}

type ArrayStack struct {
	data []int64
	top  int
}

func NewArrayStack(cap int) *ArrayStack {
	return &ArrayStack{
		data: make([]int64, cap),
		top:  0,
	}
}

func (s *ArrayStack) Push(v int64) {
	s.data[s.top] = v
	s.top++
}

func (s *ArrayStack) Pop() int64 {
	s.top--
	return s.data[s.top]
}

func main() {
	const iters = 10_000_000

	// 1. Linked Stack
	ls := &LinkedStack{}
	startLinked := time.Now()
	for i := 0; i < iters; i++ {
		ls.Push(int64(i))
		if i%2 == 0 {
			_ = ls.Pop()
		}
	}
	dLinked := time.Since(startLinked)
	fmt.Printf("LinkedStack (аллокации на каждый Push): %v\n", dLinked)

	// 2. Array Stack
	as := NewArrayStack(iters)
	startArray := time.Now()
	for i := 0; i < iters; i++ {
		as.Push(int64(i))
		if i%2 == 0 {
			_ = as.Pop()
		}
	}
	dArray := time.Since(startArray)
	fmt.Printf("ArrayStack (теплый L1 кэш + zero allocs): %v\n", dArray)

	if dArray < dLinked {
		fmt.Printf("Плоский стек быстрее в %.2fx раз!\n", float64(dLinked)/float64(dArray))
	}
}
```

ℹ️ Плоский стек удерживает горячие элементы в L1-кэше и исключает аллокации в куче.

## Под капотом

В `ArrayStack` операция `as.Push(v)` компилируется в `movq %rbx, (%rax,%rcx,8)` и `incq %rcx`. Ядро процессора пишет данные в свой Store Buffer и L1 Data Cache. При следующем `Pop` значение берется напрямую из Store-Forwarding буфера ядра за 0 тактов задержки. В `LinkedStack` каждый `Push` вызывает `runtime.newobject`, ищет свободный блок в `mcache` и сбрасывает метаданные GC.

## Подводные камни

1. Утечка памяти при хранении указателей: при `Pop()` из среза указателей `data[top] = nil` обязателен, иначе объект останется достижимым для сборщика мусора.
2. Переполнение фиксированной емкости среза.

## На собеседовании

Вопрос: «Как устроен стек вызовов в Go и почему он масштабируется лучше потоков ОС?». Ответ: стек горутины — это непрерывный блок памяти, растущий динамически (копируемый стек), верхушка которого идеально ложится на кэш-линии процессора, в отличие от фиксированных 2–8 МБ стеков потоков ОС (pthread), порождающих промахи кэша.
