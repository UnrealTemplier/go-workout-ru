# NUMA (Non-Uniform Memory Access) архитектура и локальность памяти сокетов

## Условие

Исследуйте влияние архитектуры NUMA (Non-Uniform Memory Access) на задержки памяти на многосокетных серверах. Напишите код, демонстрирующий разницу между локальным и удаленным доступом к оперативной памяти (Cross-Socket Latency), и опишите привязку процессов утилитой numactl.

### Исходная формулировка

**NUMA (Non-Uniform Memory Access)**: На multi-socket servers memory access latency зависит от того, какой CPU обращается к какой памяти. Используйте `numactl` для pinning процессов к NUMA nodes.

## Теория

На современных серверах (с 2, 4 или 8 процессорными сокетами Intel Xeon / AMD EPYC) память организована по архитектуре **NUMA (Non-Uniform Memory Access)**:
* Каждый процессорный сокет (NUMA-узел) имеет собственный контроллер памяти и свои локальные модули оперативной памяти DDR.
* Доступ ядра к **локальной памяти своего сокета** (Local Access) происходит напрямую с минимальной задержкой (~60-80 нс).
* Доступ ядра к **памяти соседнего сокета** (Remote Access) вынужден проходить через межсокетную шину (Intel UPI / AMD Infinity Fabric): задержка возрастает в **2–3 раза** (~150–250 нс), а пропускная способность падает!

Если Go-приложение не учитывает топологию NUMA, горутины хаотично мигрируют между сокетами, непрерывно обращаясь к удаленным страницам памяти (NUMA Remote Memory Penalty).

## Решение по шагам

1. Напишите программу, моделирующую интенсивный доступ к памяти в многопоточном режиме.
2. Опишите команды ОС Linux для инспекции NUMA топологии: `lscpu`, `numactl --hardware`.
3. Покажите команду запуска сервиса с привязкой к локальному NUMA-узлу: `numactl --cpunodebind=0 --membind=0 ./app`.
4. Продемонстрируйте мониторинг промахов NUMA через `numastat`.
5. Сформулируйте архитектурные правила шардирования процессов под NUMA-ноды.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

const MemSize = 64 * 1024 * 1024 // 64 МБ
const Workers = 8
const Iterations = 50_000_000

func main() {
	fmt.Println("=== Бенчмарк пропускной способности памяти для NUMA анализа ===")
	fmt.Printf("GOMAXPROCS: %d, CPU Cores: %d\n", runtime.GOMAXPROCS(0), runtime.NumCPU())

	// Выделяем большой массив памяти
	data := make([]byte, MemSize)
	for i := range data {
		data[i] = byte(i)
	}

	var wg sync.WaitGroup
	wg.Add(Workers)
	start := time.Now()

	chunkSize := MemSize / Workers
	for w := 0; w < Workers; w++ {
		workerID := w
		offset := workerID * chunkSize
		go func() {
			defer wg.Done()
			var localSum byte
			mask := chunkSize - 1
			for i := 0; i < Iterations; i++ {
				// Чтение памяти
				localSum += data[offset+(i&mask)]
			}
			_ = localSum
		}()
	}
	wg.Wait()
	d := time.Since(start)

	fmt.Printf("Время параллельного доступа к памяти: %v\n", d)
	fmt.Println("\nДля проверки влияния NUMA запустите:")
	fmt.Println("1. numactl --cpunodebind=0 --membind=0 ./app   (Локальная память: высокая скорость)")
	fmt.Println("2. numactl --cpunodebind=0 --membind=1 ./app   (Удаленная память через UPI: задержка x2)")
	fmt.Println("3. numastat -c app                            (Проверка счетчиков numa_hit / numa_miss)")
}
```

ℹ️ NUMA топология определяет задержку доступа к DRAM в зависимости от физического сокета ядра.

## Под капотом

Когда ядро Сокета 0 читает адрес из памяти Сокета 1, контроллер памяти формирует сетевой пакет протокола UPI (Ultra Path Interconnect). Пакет проходит через межсоединительные линии материнской платы, попадает в контроллер памяти Сокета 1, считывает данные из DDR5 и отправляет обратно. Это добавляет до 100 нс задержки и нагружает интерконнект, создавая заторы для других ядер.

## Подводные камни

1. Запуск одного монолитного экземпляра сервиса на 128-ядерном многосокетном сервере: это худший сценарий, приводящий к межсокетным блокировкам.
2. Рекомендуемый подход в HighLoad: запуск нескольких независимых инстансов сервиса, каждый из которых жестко привязан к своему NUMA-домену (Siloing / NUMA Pinning).

## На собеседовании

Вопрос на системного архитектора (Yandex, VK Cloud): «Как мы запускаем базы данных и кэши (PostgreSQL, Redis, ClickHouse) на двухсокетных серверах по 128 ядер?». Ответ: запуск нескольких шардов (инстансов), изолированных через `taskset` / `numactl` или параметры Kubernetes CPU Manager (`cpuManagerPolicy: static`, `topologyManagerPolicy: single-numa-node`), чтобы память и ядра каждого инстанса находились строго в пределах одного NUMA-узла.
