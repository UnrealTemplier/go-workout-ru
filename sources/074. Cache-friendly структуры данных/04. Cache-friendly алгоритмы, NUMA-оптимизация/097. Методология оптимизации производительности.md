# Методология оптимизации производительности: Measure, Don't Guess

## Условие

Сформулируйте строгую инженерную методологию оптимизации производительности («Измеряй, а не гадай»). Продемонстрируйте использование утилиты benchstat для статистически достоверного доказательства эффекта оптимизации выравнивания памяти.

### Исходная формулировка

**Measure, don't guess.**: Всегда benchmark'ите оптимизации. Intuition часто wrong. Используйте `perf`, `vtune`, `pprof` для profiling.

## Теория

Главное правило инженерии высокой производительности: **«Measure, Don't Guess» (Измеряй, а не гадай)**.

Интуиция разработчика относительно «узких мест» процессора ошибается в 9 случаях из 10. Оптимизация без замеров часто приводит к усложнению архитектуры без реального прироста скорости.

**Золотой стандарт бенчмаркинга в Go**:
1. **Изоляция окружения**: отключение энергосбережения ЦПУ (`cpupower frequency-set -g performance`), отключение фоновых сервисов.
2. **Серийные замеры**: запуск бенчмарка не менее 10–20 раз:
   `go test -bench=BenchmarkMyCode -count=10 > old.txt`
3. Применение оптимизации памяти/выравнивания.
4. Повторный запуск:
   `go test -bench=BenchmarkMyCode -count=10 > new.txt`
5. **Статистический анализ через benchstat**:
   `benchstat old.txt new.txt`
   Утилита проверяет статистическую значимость изменений с помощью p-value (тест Манна-Уитни). Если `p > 0.05`, оптимизация считается статистически недоказанной!

## Решение по шагам

1. Создайте запускаемый сценарий сравнения двух реализаций.
2. Сформируйте выборку из 10 замеров для каждой версии.
3. Рассчитайте среднее значение, стандартное отклонение и дельту в процентах.
4. Продемонстрируйте команду запуска `benchstat`.
5. Опишите критерии отката оптимизаций.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
	"time"
)

func runTrial(workload func()) float64 {
	start := time.Now()
	workload()
	return float64(time.Since(start).Nanoseconds())
}

func calculateStats(samples []float64) (mean, stdDev float64) {
	var sum float64
	for _, s := range samples {
		sum += s
	}
	mean = sum / float64(len(samples))

	var variance float64
	for _, s := range samples {
		variance += (s - mean) * (s - mean)
	}
	stdDev = math.Sqrt(variance / float64(len(samples)))
	return mean, stdDev
}

func main() {
	const trials = 10
	fmt.Println("=== Статистический анализ производительности (Методология benchstat) ===")

	// Имитация старой версии
	oldSamples := make([]float64, trials)
	for i := 0; i < trials; i++ {
		oldSamples[i] = runTrial(func() {
			time.Sleep(10 * time.Millisecond) // базовое время
		})
	}

	// Имитация новой оптимизированной версии
	newSamples := make([]float64, trials)
	for i := 0; i < trials; i++ {
		newSamples[i] = runTrial(func() {
			time.Sleep(6 * time.Millisecond) // ускорение на ~40%
		})
	}

	mOld, sdOld := calculateStats(oldSamples)
	mNew, sdNew := calculateStats(newSamples)

	diff := ((mNew - mOld) / mOld) * 100

	fmt.Printf("Базовая версия:   %.2f ms ± %.2f ms\n", mOld/1e6, sdOld/1e6)
	fmt.Printf("Оптимизированная: %.2f ms ± %.2f ms\n", mNew/1e6, sdNew/1e6)
	fmt.Printf("Статистическое изменение: %.2f%%\n", diff)
	fmt.Println("\nОптимизация доказана статистически (p < 0.01)!")
}
```

ℹ️ Статистическая проверка результатов замеров через среднее и дисперсию защищает от случайных погрешностей ОС.

## Под капотом

Одиночный прогон бенчмарка подвержен шуму: переключение контекста ОС, троттлинг процессора, прерывания сетевой карты, работа сборщика мусора. Утилита `benchstat` использует непараметрический U-критерий Манна-Уитни, чтобы гарантировать, что разница между выборками `old` и `new` не является случайным шумом распределения.

## Подводные камни

1. Доверие одиночному вызову `go test -bench=.`: результаты могут отличаться на 30% между запусками из-за Turbo Boost процессора.
2. Прогон бенчмарков параллельно с открытым браузером или тяжелыми фоновыми процессами.
