# Кэш-ориентированная сериализация: плоские бинарные форматы (FlatBuffers style)

## Условие

Разработайте протокол плоской бинарной сериализации (в стиле FlatBuffers / Cap'n Proto) без промежуточного разбора структур в куче. Продемонстрируйте прямой доступ к полям сериализованного байтового буфера без аллокаций памяти и декодирования.

### Исходная формулировка

**Cache-friendly serialization**: Для serialization используйте flat binary format вместо nested structures. Это sequential read/write.

## Теория

Традиционные форматы сериализации (JSON, XML, стандартный `encoding/gob`, а также частично Protocol Buffers):
1. Читают входной поток байт.
2. Выделяют в куче десятки вложенных структур, строк и срезов.
3. Парсят данные и копируют поля (Parsing Overhead).
4. Нагружают Garbage Collector миллионами временных объектов.

**Flat Binary Formats (Zero-Copy Serialization)**:
* Данные сериализуются в байтовый срез строго с учетом **выравнивания типов памяти** (8 байт для чисел, 4 байта для смещений).
* В начале сообщения хранится таблица смещений (**vtable**).
* **Чтение происходит вообще без десериализации (Zero Parsing)**: структура не создается в куче! Читающий код обращается прямо в сырой байтовый срез по вычисленному смещению через `unsafe.Pointer` или `binary.LittleEndian`.
* Данные читаются процессором последовательно из кэша L1 со скоростью шины памяти.

## Решение по шагам

1. Спроектируйте бинарный макет записи заказа: ID (8 байт), Сумма (8 байт), Смещение строки имени клиента (4 байта), Длина (4 байта).
2. Напишите сериализатор `SerializeOrder(id uint64, amount float64, name string) []byte`.
3. Напишите zero-copy аксессор `ReadOrderAmount(buf []byte) float64` и `ReadOrderName(buf []byte) string`.
4. Замерьте время «десериализации» и аллокации (0 байт/op).
5. Сравните с классическим JSON.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/binary"
	"encoding/json"
	"fmt"
	"math"
	"time"
	"unsafe"
)

type OrderJSON struct {
	ID     uint64  `json:"id"`
	Amount float64 `json:"amount"`
	Name   string  `json:"name"`
}

// FlatOrderLayout в памяти:
// [0..8]   ID (uint64)
// [8..16]  Amount (float64)
// [16..20] Name Offset (uint32)
// [20..24] Name Length (uint32)
// [24..]   Raw String Bytes
func SerializeFlat(id uint64, amount float64, name string) []byte {
	nameBytes := []byte(name)
	totalSize := 24 + len(nameBytes)
	buf := make([]byte, totalSize)

	binary.LittleEndian.PutUint64(buf[0:8], id)
	bits := math.Float64bits(amount)
	binary.LittleEndian.PutUint64(buf[8:16], bits)
	binary.LittleEndian.PutUint32(buf[16:20], 24)
	binary.LittleEndian.PutUint32(buf[20:24], uint32(len(nameBytes)))
	copy(buf[24:], nameBytes)

	return buf
}

// Zero-copy чтение полей без аллокаций
func ReadAmount(buf []byte) float64 {
	bits := binary.LittleEndian.Uint64(buf[8:16])
	return math.Float64frombits(bits)
}

func ReadNameZeroCopy(buf []byte) string {
	offset := binary.LittleEndian.Uint32(buf[16:20])
	length := binary.LittleEndian.Uint32(buf[20:24])
	bytesSlice := buf[offset : offset+length]
	return unsafe.String(unsafe.SliceData(bytesSlice), len(bytesSlice))
}

func main() {
	const iters = 2_000_000
	name := "VIP_Customer_Account_Alpha"
	amount := 14999.50

	// 1. JSON
	jsonBytes, _ := json.Marshal(OrderJSON{ID: 101, Amount: amount, Name: name})
	startJSON := time.Now()
	for i := 0; i < iters; i++ {
		var o OrderJSON
		_ = json.Unmarshal(jsonBytes, &o)
	}
	dJSON := time.Since(startJSON)
	fmt.Printf("JSON Unmarshal:           %v\n", dJSON)

	// 2. Flat Binary (Zero Copy)
	flatBuf := SerializeFlat(101, amount, name)
	startFlat := time.Now()
	var total float64
	for i := 0; i < iters; i++ {
		total += ReadAmount(flatBuf)
		_ = ReadNameZeroCopy(flatBuf)
	}
	dFlat := time.Since(startFlat)
	fmt.Printf("Flat Binary (Zero-Copy):  %v (total=%.0f)\n", dFlat, total)

	if dFlat < dJSON {
		fmt.Printf("Flat Binary быстрее в %.2fx раз без единой аллокации в куче!\n",
			float64(dJSON)/float64(dFlat))
	}
}
```

ℹ️ Flat binary формат читается напрямую из кэша памяти без парсинга и промежуточных структур.

## Под капотом

В Flat Binary формате процессор просто читает 8 байт из буфера по смещению `8` через ассемблерную инструкцию `MOVQ 8(%rax), %rbx`. Никаких вызовов аллокатора, рефлексии и сборщика мусора. Данные лежат непрерывно в кэш-линии сетевого сокета, обеспечивая задержку чтения менее 2 нс.

## Подводные камни

1. Изменение схемы данных (Schema Evolution): добавление новых полей требует поддержки vtable или строгого добавления полей в конец структуры.
2. Проверка выхода за границы буфера: невалидный байтовый срез может привести к панике индексации.

## На собеседовании

Вопрос: «Почему в высокочастотном трейдинге (HFT) и сетевых играх вместо Protobuf/JSON используют Cap'n Proto или SBE (Simple Binary Encoding)?». Ответ: SBE и FlatBuffers обеспечивают нулевое время декодирования (Zero-Copy), строгую кэш-локальность и предсказуемую субмикросекундную задержку (P99 < 1 мкс).
