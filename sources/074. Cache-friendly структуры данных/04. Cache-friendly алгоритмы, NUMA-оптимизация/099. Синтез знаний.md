## Теория

Сетевые фреймворки экстремальной производительности (**gnet**, **evio**, netpoll от CloudWeGo):
* Отказываются от модели «одна горутина на одно сетевое соединение» (goroutine-per-connection) стандартного пакета `net/http`.
* Используют мультиплексирование **epoll/kqueue** с фиксированным пулом событийных циклов (**Event Loops**), точно равным числу физических ядер процессора.
* Достигают миллионов RPS благодаря строгому соблюдению правил работы с памятью:
  1. **Изоляция Event Loops**: каждый Event Loop владеет своим набором структур, устраняя синхронизацию и False Sharing.
  2. **Кольцевые буферы Zero-Copy**: пакеты читаются напрямую в кольцевые буферы (`RingBuffer`), выровненные по границам кэш-линий.
  3. **Pointer-Free структуры**: метаданные соединений пакуются в плоские структуры без указателей, исключая сканирование сборщиком мусора.
  4. **Совместное размещение полей (Co-location)**: файловый дескриптор `fd`, буфер чтения и метка времени упаковываются в одну 64-байтную кэш-линию.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// OptimizedConnection: сетевой дескриптор в стиле gnet/evio
// Ровно 64 байта (1 кэш-линия ЦПУ):
// - Горячие поля для чтения/записи сетевых событий упакованы монолитно
// - Нет динамических указателей (Pointer-Free для GC)
// - Исключены Cache Misses при обработке epoll эвента
type OptimizedConnection struct {
	Fd         int32    // 4 байта: системный файловый дескриптор
	Events     uint32   // 4 байта: маска событий epoll (EPOLLIN/EPOLLOUT)
	ReadHead   uint32   // 4 байта: индекс чтения кольцевого буфера
	ReadTail   uint32   // 4 байта: индекс записи кольцевого буфера
	LastActive int64    // 8 байт: Unix nano timestamp активности
	RemoteIPv4 uint32   // 4 байта: IP адрес клиента
	RemotePort uint16   // 2 байта: порт клиента
	Flags      uint16   // 2 байта: битовые флаги состояния соединения
	RingOffset uint32   // 4 байта: смещение в глобальной сетевой арене
	RingSize   uint32   // 4 байта: размер буфера соединения
	_          [24]byte // 24 байта: резерв / padding ровно до 64 байт!
}

func main() {
	var conn OptimizedConnection
	size := unsafe.Sizeof(conn)

	fmt.Println("=== Синтез: Структура сетевого соединения нового поколения (gnet style) ===")
	fmt.Printf("Размер структуры:            %d байт (ровно 1 кэш-линия ЦПУ)\n", size)
	fmt.Printf("Смещение дескриптора Fd:     %d байт\n", unsafe.Offsetof(conn.Fd))
	fmt.Printf("Смещение маски событий:      %d байт\n", unsafe.Offsetof(conn.Events))
	fmt.Printf("Смещение буфера чтения:      %d байт\n", unsafe.Offsetof(conn.ReadHead))
	fmt.Printf("Смещение метки времени:      %d байт\n", unsafe.Offsetof(conn.LastActive))
	fmt.Printf("Смещение сетевого IP:        %d байт\n", unsafe.Offsetof(conn.RemoteIPv4))

	// Инициализация
	conn.Fd = 42
	conn.Events = 0x001 // EPOLLIN
	conn.RemoteIPv4 = 0x7F000001
	conn.RemotePort = 8080

	fmt.Printf("\nСоединение fd=%d готово к обработке в Event Loop с 0 Cache Misses!\n", conn.Fd)
	fmt.Println("Поздравляем: Глава 74 по Cache-friendly структурам данных успешно освоена на уровне BigTech!")
}
```

ℹ️ Финальная архитектура объединяет все правила кэш-локальности, выравнивания и Zero-Copy.

## Под капотом

Когда сетевой поток ядра ОС пробуждается системным вызовом `epoll_wait`, он получает массив дескрипторов. Event Loop берет структуру `OptimizedConnection` по прямому индексу `connections[fd]`. Вся структура (64 байта) загружается в L1-кэш ровно за 1 обращение к памяти. Дескриптор, битовые флаги, кольцевой буфер и время обновляются за считанные такты ЦПУ без единого вызова аллокатора или блокировки мьютекса.

## Подводные камни

1. Пренебрежение хвостовым padding: если массив соединений `[]OptimizedConnection` не имеет размера элементов, кратного 64 байтам, элементы разъедутся по границам строк.
2. Использование интерфейсов `net.Conn` внутри горячего ядра: абстракция интерфейса порождает побег в кучу и косвенные вызовы функций.
