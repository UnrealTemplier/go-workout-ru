# False Sharing как скрытый разрушитель масштабируемости HighLoad систем

## Условие

Смоделируйте катастрофический сценарий масштабирования сервиса (Negative Scalability), когда добавление новых ядер процессора приводит не к росту, а к падению пропускной способности из-за False Sharing. Сравните кривые масштабирования 1, 2, 4, 8 воркеров.

### Исходная формулировка

**False sharing — тихий убийца производительности.**: Два thread'а, пишущие в разные переменные в одной cache line, вызывают cache line bouncing. Это может замедлить код в 10-100x. Используйте padding.

## Теория

Закон Амдала описывает теоретический предел ускорения параллельных программ. Однако в реальности при наличии **False Sharing** наблюдается явление **Negative Scalability (Отрицательное масштабирование)**:
* На 1 ядре программа работает быстро, так как строка кэша монопольно находится в L1 этого ядра.
* На 2 ядрах ядра начинают конкурировать за строку, и скорость падает на 30–50%.
* На 8–16 ядрах шина межпроцессорного соединения (UPI) полностью забивается трафиком протокола когерентности кэша (RFO-запросы, Invalidate Broadcasts).
* Время на одну операцию возрастает в 10–50 раз, а общая пропускная способность сервиса падает в разы при росте числа ядер!

## Решение по шагам

1. Создайте структуру с общими невыровненными счетчиками для \(N\) ядер.
2. Запустите тесты производительности для числа воркеров \(W \in [1, 2, 4, 8]\).
3. Замерьте общую пропускную способность (Total Throughput в миллионах операций/сек).
4. Продемонстрируйте падение производительности по мере добавления ядер.
5. Покажите устранение проблемы выравниванием.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

const ItersPerWorker = 5_000_000

type SharedBad [16]uint64

func runTest(workers int) float64 {
	var shared SharedBad
	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		id := w
		go func() {
			defer wg.Done()
			for i := 0; i < ItersPerWorker; i++ {
				atomic.AddUint64(&shared[id], 1)
			}
		}()
	}
	wg.Wait()
	duration := time.Since(start)
	totalOps := float64(workers * ItersPerWorker)
	return (totalOps / duration.Seconds()) / 1e6 // млн ops/sec
}

func main() {
	fmt.Println("=== Эффект False Sharing: Масштабируемость по ядрам ===")
	fmt.Printf("%-10s | %-20s\n", "Воркеры", "Throughput (M ops/s)")
	fmt.Println("-------------------------------------------")

	workerCounts := []int{1, 2, 4, 8}
	for _, w := range workerCounts {
		throughput := runTest(w)
		fmt.Printf("%-10d | %-20.2f\n", w, throughput)
	}

	fmt.Println("\nВывод: добавление воркеров без padding снижает пропускную способность (Negative Scalability)!")
}
```

ℹ️ Демонстрация деградации производительности при росте конкуренции за общую кэш-линию.

## Под капотом

На одном ядре инструкция `atomic.Add` удерживает строку в L1 кэше (latency ~3 такта). При 8 ядрах каждое ядро непрерывно отправляет по кольцевой шине процессора сигнал Invalidation. Кэш-контроллеры ядер вынуждены постоянно переводить свои L1/L2 кэши в состояние Invalid, запрашивать данные заново из L3 или памяти и синхронизировать Store Buffers. Межъядерная шина перегружается, вызывая заторы конвейера всех ядер.

## Подводные камни

1. Маскировка проблемы при тестировании на локальном ноутбуке с малым числом физических ядер.
2. Неверный вывод разработчиков: «Многопоточность в Go медленная, горутины имеют большой оверхед» вместо локализации False Sharing.

## На собеседовании

Вопрос на системного архитектора: «Мы перенесли сервис с 8-ядерного сервера на 64-ядерный, и задержка API P99 выросла в 5 раз, а CPU занят на 100%. Что произошло?». Ответ: классический False Sharing в глобальных счетчиках метрик, невыровненных пулах соединений или шардированных мапах, приведший к лавинообразному росту трафика кэш-когерентности.
