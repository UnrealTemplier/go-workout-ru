# Программная упреждающая выборка (Software Prefetching)

## Условие

Изучите концепцию программной упреждающей выборки (Software Prefetching). Объясните, как инструкция PREFETCHt0 скрывает задержку обращения к памяти при обработке связных структур или больших массивов, когда аппаратный префетчер бессилен.

### Исходная формулировка

**Software prefetch для predictable access.**: Если вы знаете, какие данные понадобятся через N iterations, используйте software prefetch. Это скрывает memory latency.

## Теория

Аппаратный префетчер (Hardware Prefetcher) процессора умеет отслеживать только регулярные паттерны доступа с фиксированным шагом (stride). При обходе деревьев, графов, хэш-таблиц или списков аппаратный префетчер не может угадать следующий адрес.

**Программный префетч (Software Prefetching)**:
* Программист или компилятор вставляет специальную инструкцию процессора (на x86_64: `PREFETCHT0`, `PREFETCHT1`, `PREFETCHNTA`):
```asm
PREFETCHT0 64(%rax)
```
* Инструкция сообщает контроллеру памяти: «Загрузи кэш-линию по адресу `X` в кэш L1 прямо сейчас, но не блокируй конвейер инструкций».
* Пока процессор выполняет текущие вычисления над элементом \(i\), строка для элемента \(i + K\) скрытно летит по шине памяти из DRAM.
* К моменту, когда алгоритм доходит до элемента \(i + K\), данные уже лежат в L1 кэше (задержка обращения 0 тактов)!

## Решение по шагам

1. Напишите модель алгоритма обработки ключей в хэш-таблице с упреждающей выборкой.
2. Продемонстрируйте вычисление расстояния упреждения (Prefetch Distance \(K \approx 4\dots8\) элементов).
3. Смоделируйте конвейер: расчет хэша для элемента \(i+K\), префетч его адреса, обработка элемента \(i\).
4. Опишите использование интринсиков префетча в ассемблере Go.
5. Сформулируйте компромиссы использования Software Prefetching.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const Size = 2_000_000
const Lookahead = 8 // Prefetch distance: скрываем 60 нс латентности DRAM

type Record struct {
	Key   uint64
	Value uint64
}

func simulateProcessing(records []Record, lookupKeys []int) time.Duration {
	start := time.Now()
	var total uint64

	n := len(lookupKeys)
	for i := 0; i < n; i++ {
		// В реальном ассемблере Go здесь вызывается PREFETCHT0 для records[lookupKeys[i+Lookahead]]
		// Контроллер памяти начинает фоновую загрузку кэш-линии
		idx := lookupKeys[i]
		total += records[idx].Value
	}
	_ = total
	return time.Since(start)
}

func main() {
	fmt.Println("=== Модель Software Prefetching в архитектурах данных ===")
	records := make([]Record, Size)
	for i := range records {
		records[i] = Record{Key: uint64(i), Value: uint64(i * 2)}
	}

	keys := make([]int, Size)
	for i := range keys {
		keys[i] = (i * 104729) % Size // псевдослучайный разброс
	}

	cost := simulateProcessing(records, keys)
	fmt.Printf("Время обработки выборки: %v\n", cost)
	fmt.Println("Принцип Software Prefetch: процессор запрашивает адрес за N итераций до его реального использования.")
}
```

ℹ️ Упреждающий запрос адресов памяти за K итераций до использования полностью маскирует задержку DRAM.

## Под капотом

Задержка обращения к DRAM составляет ~60-80 нс. Если одна итерация цикла длится ~10 нс, то оптимальная дистанция упреждения равна \(K = \frac{80 \text{ нс}}{10 \text{ нс}} = 8\) итераций. Инструкция `PREFETCHT0` отправляет неблокирующий запрос в контроллер кэша. Конвейер ядра продолжает выполнять инструкции без stall'ов, а данные заблаговременно оседают в L1 Data Cache.

## Подводные камни

1. Cache Pollution: если запросить префетч слишком рано (\(K\) слишком велико), подгруженные данные вытеснят текущие полезные строки из L1 до того, как они понадобятся.
2. Оверхед инструкций: если данные уже находятся в L1/L2, лишние инструкции `PREFETCH` только расходуют слоты декодера конвейера процессора.

## На собеседовании

Вопрос на системное программирование (ClickHouse, сетевые драйверы DPDK): «Как работает Software Prefetching в движках баз данных при хэш-джойнах (Hash Join)?». Ответ: при сканировании таблицы правый ключ хэшируется, и за \(K\) шагов вперед отправляется `_mm_prefetch` по вычисленному адресу бакета. Это превращает случайные скачки памяти в конвейерную загрузку, ускоряя Hash Join в 2–3 раза.
