# Локальность памяти: Pointer Chasing как первопричина Cache Misses

## Условие

Напишите программу, наглядно сравнивающую последовательный обход плоского среза и обход того же среза в случайном порядке (Random Pointer Chasing). Замерьте колоссальный скачок времени (в 20-50 раз) и объясните невозможность аппаратного упреждающего чтения при непредсказуемой адресации.

### Исходная формулировка

**Pointer chasing — это cache miss.**: Linked list требует cache miss на каждый элемент. Flat array — sequential access, prefetcher работает. Избегайте linked structures в hot paths.

## Теория

Явление **Pointer Chasing (погоня за указателями)** — главный враг производительности современных вычислительных систем.

Современный процессор (x86_64 / ARM64) обладает колоссальной вычислительной мощностью (до 4-5 ГГц, исполнение до 6 инструкций за такт), но обращение к оперативной памяти DDR5 занимает от 60 до 100 наносекунд (~300 тактов простоя).

Когда алгоритм обходит плоский срез (`Sequential Access`):
1. Адрес следующего элемента тривиально предсказуем (\(A_{next} = A_{curr} + Size\)).
2. Аппаратный блок процессора **L2/L1 Streamer (Hardware Prefetcher)** заблаговременно подгружает данные из DRAM в кэш L1.
3. Процессор читает данные с задержкой 1 нс (L1 Hit).

Когда алгоритм переходит по указателям в случайном порядке (`Random Pointer Chasing`):
1. Адрес следующего элемента закодирован внутри текущего элемента.
2. Процессор **не может начать чтение следующего адреса**, пока не завершится чтение текущего (Dependent Memory Load Stall).
3. Prefetcher бессилен. Конвейер процессора замораживается на сотни тактов на каждом переходе.

## Решение по шагам

1. Создайте срез целых чисел на 5 000 000 элементов.
2. Сгенерируйте случайную цепочку перестановок индексов (Permutation Cycle).
3. Измерьте время обхода 5 000 000 элементов в последовательном порядке.
4. Измерьте время обхода той же цепочки по случайным индексам.
5. Рассчитайте среднее время одного перехода.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"time"
)

const Size = 4_000_000

func main() {
	fmt.Printf("Инициализация массива на %d элементов (%.2f МБ)...\n",
		Size, float64(Size*8)/(1024*1024))

	// Последовательные данные
	seqData := make([]int64, Size)
	for i := range seqData {
		seqData[i] = int64(i)
	}

	// Создаем замкнутый случайный цикл для Pointer Chasing
	perm := rand.Perm(Size)
	chaseIndices := make([]int, Size)
	for i := 0; i < Size-1; i++ {
		chaseIndices[perm[i]] = perm[i+1]
	}
	chaseIndices[perm[Size-1]] = perm[0] // замыкаем кольцо

	// 1. Последовательный обход (Stream Prefetcher)
	startSeq := time.Now()
	var sumSeq int64
	for i := 0; i < Size; i++ {
		sumSeq += seqData[i]
	}
	dSeq := time.Since(startSeq)
	seqLatency := float64(dSeq.Nanoseconds()) / float64(Size)
	fmt.Printf("Последовательный обход: %v (латентность: %.2f ns/элемент)\n", dSeq, seqLatency)

	// 2. Случайный обход (Pointer Chasing Stall)
	startChase := time.Now()
	curr := perm[0]
	var sumChase int64
	for i := 0; i < Size; i++ {
		sumChase += seqData[curr]
		curr = chaseIndices[curr] // Зависимая загрузка памяти!
	}
	dChase := time.Since(startChase)
	chaseLatency := float64(dChase.Nanoseconds()) / float64(Size)
	fmt.Printf("Случайный Pointer Chasing: %v (латентность: %.2f ns/элемент)\n", dChase, chaseLatency)

	if dChase > dSeq {
		fmt.Printf("\nВывод: Pointer Chasing медленнее в %.2fx раз из-за постоянных Cache Misses!\n",
			float64(dChase)/float64(dSeq))
	}
	_ = sumSeq
	_ = sumChase
}
```

ℹ️ Случайный обход памяти блокирует конвейер ЦПУ на сотни тактов из-за зависимых чтений.

## Под капотом

При последовательном обходе время доступа составляет ~0.3-0.5 нс на элемент (амортизированное время L1 попадания). При Pointer Chasing задержка подскакивает до 50–80 нс на элемент. Процессор не может выполнить спекулятивное исполнение (Out-of-Order Execution), так как следующая инструкция чтения `seqData[curr]` зависит от значения, которое еще летит из чипов DDR5 памяти через контроллер памяти.

## Подводные камни

1. Использование связанных списков, деревьев на указателях и графов с указателями в горячих путях обработки запросов.
2. Иллюзия «быстрой вставки O(1)» в связанный список: на практике обход для поиска позиции вставки убивает выигрыш из-за сотен промахов кэша.
