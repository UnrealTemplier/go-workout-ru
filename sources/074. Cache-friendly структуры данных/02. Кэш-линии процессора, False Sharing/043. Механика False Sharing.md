# Механика False Sharing: инвалидация 64-байтовой кэш-линии между ядрами

## Условие

43. **Объяснение False Sharing**: Пойми, что поля `a` и `b` лежат рядом (занимают 16 байт) и попадают в **одну** кэш-линию процессора (64 байта). Когда ядро 1 меняет `a`, оно инвалидирует всю кэш-линию для ядра 2 (которое меняет `b`), заставляя процессор тратить время не на вычисления, а на пересылку кэш-линий между ядрами. Напишите наглядную программу трассировки этих состояний.

### Исходная формулировка

**Объяснение False Sharing**: Пойми, что поля `a` и `b` лежат рядом (занимают 16 байт) и попадают в **одну** кэш-линию процессора (64 байта). Когда ядро 1 меняет `a`, оно инвалидирует всю кэш-линию для ядра 2 (которое меняет `b`), заставляя процессор постоянно гонять данные по шине между L1-кэшами разных ядер.

## Теория

С точки зрения программиста на Go:
```go
type Stat struct {
    ReqsReceived uint64 // 8 байт
    ReqsRejected uint64 // 8 байт
}
```
Два поля структуры совершенно независимы. Никаких гонок данных нет. Код `go run -race` проходит идеально.

**Но с точки зрения физики полупроводникового кристалла:**
Кэш-память L1 не знает концепции полей, типов или структур.
Для кремния существует только **физический адрес кратный 64 байтам**:
`0x7fff_0040 .. 0x7fff_007f`.
Оба поля `ReqsReceived` и `ReqsRejected` физически зажаты внутри одного 64-байтового блока.

Когда Ядро 1 выполняет инкремент `ReqsReceived++`:
- Процессор захватывает **весь блок 64 байта**.
- Линия переходит в состояние `Modified`.
- Ядро 2 на соседнем кристалле получает сигнал `Invalidate`.
- Вся кэш-линия в кэше Ядра 2 стирается!
Когда Ядро 2 пытается сделать `ReqsRejected++`:
- Происходит сбой кэша (Cache Miss).
- Ядро 2 замораживает конвейер инструкций на 40–80 тактов, посылает сигнал по межъядерной шине, вытягивает 64 байта у Ядра 1 и инвалидирует Ядро 1.

Ядра процессора превращаются в двух игроков, безостановочно вырывающих друг у друга один и тот же мяч (Cache Line Bouncing). Производительность падает до скорости шины памяти!

## Решение по шагам

1. Создайте структуру с двумя полями `A` и `B` в одной 64-байтовой строке.
2. Продемонстрируйте побайтовое расположение полей в окне кэша `[0..63]`.
3. Запустите две горутины, имитирующие нагрузку.
4. Выведите детальный отчет об анатомии ложного разделения.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

type TwoCounters struct {
	counterA uint64 // 8 bytes
	counterB uint64 // 8 bytes
}

func printCacheLineMap(c *TwoCounters) {
	addrA := uintptr(unsafe.Pointer(&c.counterA))
	addrB := uintptr(unsafe.Pointer(&c.counterB))

	lineBaseA := addrA &^ 63
	lineBaseB := addrB &^ 63

	fmt.Printf("Memory Layout Analysis:\n")
	fmt.Printf("  Address of counterA: 0x%x (Offset in Cache Line: %d)\n", addrA, addrA%64)
	fmt.Printf("  Address of counterB: 0x%x (Offset in Cache Line: %d)\n", addrB, addrB%64)
	fmt.Printf("  Cache Line Base A:   0x%x\n", lineBaseA)
	fmt.Printf("  Cache Line Base B:   0x%x\n\n", lineBaseB)

	if lineBaseA == lineBaseB {
		fmt.Println("CRITICAL HAZARD DETECTED: BOTH VARIABLES SHARE THE SAME 64-BYTE CACHE LINE!")
		fmt.Println("Visual Cache Line Representation (64 bytes):")
		fmt.Println("[counterA (8B)][counterB (8B)][............... unused padding 48B ...............]")
		fmt.Println("Core 0 writing counterA WILL INVALIDATE L1 CACHE OF Core 1 writing counterB!")
	} else {
		fmt.Println("SAFE: Variables reside in independent cache lines.")
	}
}

func main() {
	var counters TwoCounters
	printCacheLineMap(&counters)
}
```

ℹ️ Анализ базовых адресов и доказательство нахождения двух переменных в одной 64-байтовой кэш-линии

## Под капотом

В процессорах с архитектурой NUMA (например, двухсокетный сервер Intel Xeon) ситуация становится катастрофической: если Ядро 1 находится на Сокете 0, а Ядро 2 на Сокете 1, инвалидация кэш-линии выходит за пределы кристалла и передается через межсокетную шину UPI. Задержка возрастает до 150–200 нс на каждую операцию инкремента!

## Подводные камни

1. Заблуждение, что локальные переменные внутри горутин могут вызывать False Sharing: локальные переменные живут на независимых стеках горутин, разнесенных в памяти на килобайты. False Sharing возможен ТОЛЬКО для разделяемых полей структур или глобальных переменных.
2. Неучет выравнивания указателей в массивах.

## На собеседовании

«Как локализовать False Sharing в бинарнике Go с помощью Linux perf c2c?»
Ответ: Утилита `perf c2c` (Cache-to-Cache) специально разработана для обнаружения False Sharing. Команда `perf c2c record ./my_app` и `perf c2c report` находит конкретные физические смещения структур в памяти (Cacheline Metrics), на которых зафиксирован аномально высокий процент вызовов `HITM` (Hit in Modified cache другого ядра).
