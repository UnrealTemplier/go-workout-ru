# Cache Line Bouncing и деградация межъядерной шины interconnect

## Условие

45. **Cache line bouncing**: Когда CPU0 пишет в cache line, все другие CPU должны инвалидировать свои копии этой cache line. Это expensive (десятки-сотни наносекунд). Напишите программу, симулирующую Cache Line Bouncing между N ядрами, и замерьте экспоненциальный рост задержки при увеличении числа ядер.

### Исходная формулировка

**Cache line bouncing**: Когда CPU0 пишет в cache line, все другие CPU должны инвалидировать свои копии этой cache line. Это expensive (десятки-сотни наносекунд).

## Теория

Феномен **Cache Line Bouncing (Мячик кэш-линий)** возникает, когда \(N\) ядер процессора пытаются параллельно и непрерывно записывать в одну и ту же 64-байтовую кэш-линию:

Хронология катастрофы:
1. **2 ядра:** Линия прыгает между Ядром 0 и Ядром 1. Задержка ~20-30 нс.
2. **4 ядра:** Каждое ядро генерирует запрос RFO, выстраиваясь в очередь арбитра шины. Задержка ~60-90 нс.
3. **8+ ядер:** Межъядерная шина процессора перегружается широковещательными пакетами инвалидации. Пропускная способность шины исчерпывается. Возникает эффект насыщения (**Interconnect Saturation**), а задержка операции возрастает до **сотен наносекунд**.

Вместо ускорения от параллелизма добавление новых ядер CPU **замедляет** работу программы!

## Решение по шагам

1. Создайте разделяемую структуру с одной атомарной переменной `shared atomic.Uint64`.
2. Напишите функцию измерения времени выполнения пачки операций для \(K\) параллельных воркеров (\(K = 1, 2, 4, 8\)).
3. Замерьте задержку на одну операцию для каждого количества ядер.
4. Выведите график/таблицу латентности и покажите падение эффективности параллелизма.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type ContendedLine struct {
	val atomic.Uint64
}

func measureBouncing(cores int, totalOps uint64) (time.Duration, float64) {
	var target ContendedLine
	var wg sync.WaitGroup
	wg.Add(cores)

	opsPerWorker := totalOps / uint64(cores)

	start := time.Now()
	for c := 0; c < cores; c++ {
		go func() {
			defer wg.Done()
			for i := uint64(0); i < opsPerWorker; i++ {
				target.val.Add(1)
			}
		}()
	}
	wg.Wait()
	dur := time.Since(start)

	nsPerOp := float64(dur.Nanoseconds()) / float64(totalOps)
	return dur, nsPerOp
}

func main() {
	maxCores := runtime.NumCPU()
	runtime.GOMAXPROCS(maxCores)

	fmt.Printf("=== Cache Line Bouncing Benchmark (Max Cores: %d) ===\n\n", maxCores)

	const totalOperations uint64 = 10_000_000

	coreCounts := []int{1, 2, 4}
	if maxCores >= 8 {
		coreCounts = append(coreCounts, 8)
	}

	var baselineLatency float64
	fmt.Printf("%-8s | %-14s | %-16s | %-14s\n", "Cores", "Duration", "Latency/Op (ns)", "Bouncing Penalty")
	fmt.Println("------------------------------------------------------------------")

	for idx, c := range coreCounts {
		dur, ns := measureBouncing(c, totalOperations)
		if idx == 0 {
			baselineLatency = ns
		}
		penalty := ns / baselineLatency

		fmt.Printf("%-8d | %-14v | %13.2f ns | %6.2fx slower\n",
			c, dur.Round(time.Millisecond), ns, penalty)
	}

	fmt.Println("\nConclusion:")
	fmt.Println("Contention on a single cache line causes severe interconnect bouncing.")
	fmt.Println("Adding more CPU cores makes execution SLOWER, not faster!")
}
```

ℹ️ Экспериментальное измерение задержки Cache Line Bouncing при росте числа конкурирующих ядер CPU

## Под капотом

В многоядерных кристаллах Intel (Ring Topology / Mesh Topology) запросы инвалидации передаются по кольцевой шине. При высокой конкуренции очередь арбитража шины (Ring Traffic Arbiter) заполняется, вызывая остановку конвейеров суперскалярных ядер (Pipeline Stall on Memory Instruction).

## Подводные камни

1. Использование глобального мьютекса или глобального счетчика в высоконагруженных хэндлерах: мьютекс внутри содержит атомарное поле `state`, подверженное кэш-лайн баунсингу.
2. Ложное ощущение масштабируемости: программа быстро работает на ноутбуке с 4 ядрами, но «умирает» на сервере с 64 ядрами.

## На собеседовании

«Как ликвидировать Cache Line Bouncing в глобальном rate limiter сервиса?»
Ответ: Применить шардирование (Sharded Rate Limiting): разделить лимит на \(N\) независимых бакетов (по числу CPU или потоков). Входящий запрос с вероятностью \(1/N\) обращается к своему шарду. Взаимные инвалидации исключаются.
