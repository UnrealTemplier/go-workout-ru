# TLB (Translation Lookaside Buffer) и влияние Transparent Huge Pages

## Условие

26. **TLB (Translation Lookaside Buffer)**: Поймите, что virtual → physical address translation кэшируется в TLB. Большие страницы (huge pages, 2MB/1GB) снижают TLB misses. Напишите программу, симулирующую нагрузку на TLB при обходе памяти большими шагами, и покажите влияние размера страниц.

### Исходная формулировка

**TLB (Translation Lookaside Buffer)**: Поймите, что virtual → physical address translation кэшируется в TLB. Большие страницы (huge pages, 2MB/1GB) снижают TLB misses.

## Теория

Процессор работает с **виртуальной памятью (Virtual Memory)**. Каждое обращение к памяти по виртуальному адресу требует его преобразования в физический адрес в чипах RAM. Это преобразование выполняет блок MMU (Memory Management Unit) через многоуровневые таблицы страниц ядра (Page Table Walk, до 4-5 обращений к памяти).

Для ускорения трансляции в процессоре встроен сверхбыстрый специализированный аппаратный кэш — **TLB (Translation Lookaside Buffer)**:
- Стандартный размер страницы в ОС Linux: **4 КБ (4096 байт)**.
- Обычный L1 dTLB вмещает всего **64–128 записей**.
- 128 записей по 4 КБ покрывают всего \(128 \times 4\text{ КБ} = 512\text{ КБ}\) памяти!
Если программа активно работает с буфером в 1 ГБ, TLB постоянно переполняется (**TLB Thrashing / TLB Misses**). Каждое обращение требует долгого Page Table Walk.

**Huge Pages (Большие страницы 2 МБ / 1 ГБ):**
- 1 запись TLB для Huge Page покрывает сразу **2 МБ (2048 КБ)** памяти (в 512 раз больше обычной страницы!).
- Те же 128 записей TLB покрывают уже \(128 \times 2\text{ МБ} = 256\text{ МБ}\) оперативной памяти!
- Количество TLB-промахов снижается на 95–99%, давая до 15–30% прироста в memory-intensive приложениях (БД, Redis, кэши).

## Решение по шагам

1. Создайте большой буфер памяти (например, 64 МБ).
2. Напишите функцию обхода памяти с шагом ровно в 1 страницу (4096 байт).
3. При каждом шаге в 4 КБ процессор обращается к совершенно новой странице, вызывая максимальную нагрузку на TLB.
4. Сравните время доступа со случаем, когда мы читаем данные локально в пределах одной страницы.
5. Объясните механизм работы Transparent Huge Pages (THP) в Linux.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const (
	PageSize4KB = 4096
	BufferMB    = 128
	TotalBytes  = BufferMB * 1024 * 1024
)

func runTLBStressTest(buf []byte, stride int, passes int) (time.Duration, float64) {
	n := len(buf)
	var sum byte
	totalTouches := int64((n / stride) * passes)

	start := time.Now()
	for p := 0; p < passes; p++ {
		for i := 0; i < n; i += stride {
			sum += buf[i]
		}
	}
	elapsed := time.Since(start)
	_ = sum

	nsPerTouch := float64(elapsed.Nanoseconds()) / float64(totalTouches)
	return elapsed, nsPerTouch
}

func main() {
	fmt.Printf("=== TLB (Translation Lookaside Buffer) Latency Impact ===\n")
	fmt.Printf("Allocating %d MB continuous buffer...\n", BufferMB)

	buf := make([]byte, TotalBytes)
	for i := range buf {
		buf[i] = byte(i)
	}

	fmt.Println("Memory initialized.")
	fmt.Printf("\n%-20s | %-12s | %-16s | %s\n", "Access Pattern", "Stride", "Latency / Touch", "TLB Behavior")
	fmt.Println("-------------------------------------------------------------------------------------")

	// 1. Внутри одной страницы (шаг 64B, TLB Hits)
	_, nsIntra := runTLBStressTest(buf, 64, 5)
	fmt.Printf("%-20s | %-12s | %13.2f ns | %s\n",
		"Intra-Page (Cache)", "64 bytes", nsIntra, "TLB Hit (All accesses share page translations)")

	// 2. Шаг 4096 байт (Каждое обращение — новая страница! 100% TLB stress)
	_, nsInter := runTLBStressTest(buf, PageSize4KB, 50)
	fmt.Printf("%-20s | %-12s | %13.2f ns | %s\n",
		"Cross-Page (TLB)", "4096 bytes", nsInter, "Severe TLB Misses (Forced Page Table Walk)")

	ratio := nsInter / nsIntra
	fmt.Printf("\nTLB Miss Overhead: %.2fx higher latency per access!\n", ratio)
	fmt.Println("With Huge Pages (2MB), 1 TLB entry covers 512x more memory, eliminating this bottleneck.")
}
```

ℹ️ Симуляция нагрузки на TLB при прыжках по границам 4-килобайтных страниц виртуальной памяти

## Под капотом

Когда происходит TLB Miss, процессорный блок MMU запускает Page Table Walk по 4-уровневой иерархии таблиц x86-64: CR3 -> PML4 (Page Map Level 4) -> PDPT (Page Directory Pointer Table) -> PD (Page Directory) -> PT (Page Table). При использовании Huge Pages (2 МБ) уровень PT исключается, и адрес формируется прямо из Page Directory, экономя одно обращение к памяти при каждом промахе.

## Подводные камни

1. Дефрагментация памяти от Transparent Huge Pages (THP): демон `khugepaged` в Linux может вызывать периодические всплески задержек (Latency Spikes) в базах данных (Redis, MongoDB) при попытке скомпоновать 512 страниц по 4 КБ в одну страницу 2 МБ.
2. Неоправданное раздувание RSS (Resident Set Size): если приложению требуется всего 10 КБ памяти, аллокация Huge Page выделит целых 2 МБ физической памяти.

## На собеседовании

«Почему Redis официально рекомендует отключать Transparent Huge Pages (THP) на серверах?»
Ответ: Redis использует механизм фонового снимка `BGSAVE` через системный вызов `fork()`. Механизм Copy-on-Write (COW) при стандартных страницах 4 КБ копирует только те 4 КБ, в которые произошла запись. С включенным THP любая мелкая запись заставляет ОС копировать целиком огромную страницу 2 МБ, что вызывает резкий скачок потребления памяти и многократный рост задержек p99.
