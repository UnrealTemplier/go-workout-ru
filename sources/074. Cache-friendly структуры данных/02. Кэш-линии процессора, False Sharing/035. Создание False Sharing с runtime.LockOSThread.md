# Создание False Sharing с runtime.LockOSThread и потоками ОС

## Условие

35. **Создание False Sharing (Ложное разделение)**: Создай `type Counters struct { a uint64; b uint64 }`. Запусти две горутины (строго на разных ядрах через `runtime.LockOSThread`). Первая в цикле делает миллион раз `c.a++`, вторая — `c.b++`. Замерь время и докажи, что ядра тратят время на синхронизацию кэшей.

### Исходная формулировка

**Создание False Sharing (Ложное разделение)**: Создай `type Counters struct { a uint64; b uint64 }`. Запусти две горутины (строго на разных ядрах через `runtime.LockOSThread`). Первая в цикле делает миллион раз `c.a++`, вторая — `c.b++`. Замерь время.

## Теория

Планировщик Go в обычных условиях может перемещать горутины между системными потоками ОС (\(M\)) и логическими процессорами (\(P\)). Чтобы воспроизвести чистый, 100% стабильный False Sharing без вмешательства планировщика, горутины жестко привязываются к потокам операционной системы через **`runtime.LockOSThread()`**.

Когда две горутины вызывают `runtime.LockOSThread()`:
- Рантайм Go выделяет для каждой из них персональный поток POSIX pthread.
- Ядро операционной системы Linux планирует эти потоки на два разных физических ядра процессора.
- Теперь любые параллельные записи в `c.a` и `c.b` гарантированно приводят к межъядерной инвалидации кэш-линии через шину QPI/UPI, раскрывая истинную стоимость False Sharing.

## Решение по шагам

1. Создайте структуру `Counters { a uint64; b uint64 }`.
2. Запустите 2 горутины с вызовом `runtime.LockOSThread()` в начале каждой.
3. Выполните 50 000 000 инкрементов полей `a` и `b`.
4. Сравните со структурой, содержащей кэш-паддинг `_ [56]byte`.
5. Докажите аппаратную синхронизацию кэшей замером времени.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

type SharedCounters struct {
	a uint64
	b uint64
}

type IsolatedCounters struct {
	a uint64
	_ [56]byte // 8 + 56 = 64B
	b uint64
	_ [56]byte
}

func testPinnedThreadsBad(iterations uint64) time.Duration {
	var c SharedCounters
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		runtime.LockOSThread()
		defer runtime.UnlockOSThread()
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.a++
		}
	}()

	go func() {
		runtime.LockOSThread()
		defer runtime.UnlockOSThread()
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.b++
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func testPinnedThreadsGood(iterations uint64) time.Duration {
	var c IsolatedCounters
	var wg sync.WaitGroup
	wg.Add(2)

	start := time.Now()
	go func() {
		runtime.LockOSThread()
		defer runtime.UnlockOSThread()
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.a++
		}
	}()

	go func() {
		runtime.LockOSThread()
		defer runtime.UnlockOSThread()
		defer wg.Done()
		for i := uint64(0); i < iterations; i++ {
			c.b++
		}
	}()

	wg.Wait()
	return time.Since(start)
}

func main() {
	runtime.GOMAXPROCS(runtime.NumCPU())
	const iterations = 50_000_000

	fmt.Println("=== Pinned OS Threads False Sharing Experiment ===")
	fmt.Printf("Iterations per thread: %d\n\n", iterations)

	durBad := testPinnedThreadsBad(iterations)
	fmt.Printf("Shared Cache Line (LockOSThread):   %v\n", durBad)

	durGood := testPinnedThreadsGood(iterations)
	fmt.Printf("Isolated Cache Line (LockOSThread): %v\n", durGood)

	speedup := float64(durBad) / float64(durGood)
	fmt.Printf("\nHardware Cache Invalidation Penalty: %.2fx slowdown when sharing cache line!\n", speedup)
}
```

ℹ️ Демонстрация False Sharing с жесткой привязкой горутин к потокам ОС через runtime.LockOSThread

## Под капотом

`runtime.LockOSThread()` привязывает горутину к структуре `m` (Machine). Планировщик Go гарантирует, что эта горутина никогда не будет перенесена на другой поток ОС. Операционная система удерживает эти два потока на разных ядрах CPU, обеспечивая максимальную нагрузку на шину когерентности кэшей.

## Подводные камни

1. Забывание `runtime.UnlockOSThread()`: поток ОС останется привязанным навсегда и не сможет вернуться в общий пул воркеров планировщика Go.
2. Вызов `LockOSThread` во множестве горутин: это породит сотни потоков ОС, приводя к огромным расходам памяти на стеки потоков ядра.

## На собеседовании

«Когда в Go действительно необходим вызов `runtime.LockOSThread()`?»
Ответ: 1) При интеграции с CGO библиотеками, использующими Thread-Local Storage (например, OpenGL, графические API macOS Cocoa, Win32 API); 2) При изменении системных атрибутов потока ядра Linux (namespaces, seccomp, `setns`, `setpriority`); 3) В микроархитектурных бенчмарках для исключения миграции между ядрами.
