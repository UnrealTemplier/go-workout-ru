# NUMA-aware аллокации памяти и системный вызов mbind

## Условие

31. **NUMA-aware allocation**: Для extreme performance аллоцируйте память на том NUMA node, где будет выполняться обработка (через `mbind` syscall). Напишите модуль для привязки памяти к локальному сокету процессора.

### Исходная формулировка

**NUMA-aware allocation**: Для extreme performance аллоцируйте память на том NUMA node, где будет выполняться обработка (через `mbind` syscall).

## Теория

В современных многопроцессорных серверах (2, 4 или 8 сокетов CPU) используется архитектура **NUMA (Non-Uniform Memory Access — Неравномерный доступ к памяти)**:
- Каждый физический процессор (NUMA Node) имеет свой собственный локальный контроллер и банки оперативной памяти.
- Доступ к **локальной памяти** своего сокета выполняется с минимальной задержкой (~50–60 нс).
- Доступ к **удаленной памяти** чужого сокета требует передачи пакетов через межпроцессорную шину UPI (Ultra Path Interconnect) / Infinity Fabric. Задержка возрастает в 2–3 раза (~140–180 нс), а полоса пропускания падает.

По умолчанию политика ядра Linux — **First Touch Policy**: физическая страница памяти привязывается к тому NUMA-узлу, ядро которого первым выполнило запись в эту страницу.

Для критических микросервисов используется явная привязка памяти через системный вызов **`mbind`**:
```c
mbind(addr, len, MPOL_BIND, nodemask, maxnode, MPOL_MF_MOVE);
```
Он принудительно выделяет физические страницы строго на указанном сокете CPU.

## Решение по шагам

1. Изучите параметры NUMA-узлов системы через чтение `/sys/devices/system/node/`.
2. Создайте функцию выделения памяти с хинтом NUMA-узла через `syscall.Mmap` и `syscall.Syscall6(SYS_MBIND)`.
3. Реализуйте структуру дескриптора привязанного буфера.
4. Продемонстрируйте концепцию изоляции воркеров по NUMA-доменам.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"path/filepath"
	"syscall"
	"time"
	"unsafe"
)

const (
	MPOL_DEFAULT = 0
	MPOL_BIND    = 2
	MPOL_MF_MOVE = (1 << 1)
	SYS_MBIND    = 237 // Linux x86_64 syscall number
)

type NUMABuffer struct {
	data   []byte
	nodeID int
}

func DetectNUMANodes() []int {
	var nodes []int
	matches, err := filepath.Glob("/sys/devices/system/node/node[0-9]*")
	if err != nil || len(matches) == 0 {
		return []int{0} // fallback
	}
	for i := range matches {
		nodes = append(nodes, i)
	}
	return nodes
}

func AllocateNUMABuffer(size int, targetNode int) (*NUMABuffer, error) {
	// 1. Выделяем анонимную память
	data, err := syscall.Mmap(
		-1,
		0,
		size,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		return nil, fmt.Errorf("mmap failed: %w", err)
	}

	// 2. Маска узлов nodemask (битовая маска unsigned long)
	nodemask := uint64(1 << targetNode)

	// 3. Вызов mbind(addr, len, mode, nodemask, maxnode, flags)
	r1, _, errno := syscall.Syscall6(
		SYS_MBIND,
		uintptr(unsafe.Pointer(&data[0])),
		uintptr(size),
		uintptr(MPOL_BIND),
		uintptr(unsafe.Pointer(&nodemask)),
		uintptr(64), // maxnode
		uintptr(MPOL_MF_MOVE),
	)

	if errno != 0 {
		fmt.Printf("Notice: mbind returned errno %d (Single socket or non-NUMA environment)\n", errno)
	} else if r1 == 0 {
		fmt.Printf("Memory strictly bound to NUMA Node %d!\n", targetNode)
	}

	return &NUMABuffer{data: data, nodeID: targetNode}, nil
}

func main() {
	nodes := DetectNUMANodes()
	fmt.Printf("=== NUMA Architecture & Memory Binding ===\n")
	fmt.Printf("Detected NUMA Nodes in system: %v\n\n", nodes)

	const bufSize = 16 * 1024 * 1024 // 16 MB
	targetNode := 0
	if len(nodes) > 1 {
		targetNode = 1
	}

	buf, err := AllocateNUMABuffer(bufSize, targetNode)
	if err != nil {
		fmt.Println("Allocation error:", err)
		return
	}
	defer syscall.Munmap(buf.data)

	// Инициализация памяти локальным потоком
	start := time.Now()
	for i := 0; i < len(buf.data); i += 64 {
		buf.data[i] = 42
	}
	dur := time.Since(start)

	fmt.Printf("Written %d MB into NUMA Node %d memory in %v\n",
		bufSize/(1024*1024), buf.nodeID, dur)
	_ = os.DevNull
}
```

ℹ️ NUMA-aware выделение и привязка страниц памяти к сокету процессора через системный вызов mbind

## Под капотом

Когда поток на NUMA Node 0 обращается к памяти, физически размещенной на контроллере NUMA Node 1, запрос проходит через контроллер когерентности QPI/UPI. Шина QPI имеет ограниченную пропускную способность и добавляет фиксированные 60–100 нс штрафа задержки к каждому обращению. NUMA-aware архитектура связывает горутину с потоком ОС (`runtime.LockOSThread`), поток — с CPU Core (`sched_setaffinity`), а память — с локальным сокетом (`mbind`), гарантируя нулевой межсокетовый трафик.

## Подводные камни

1. Привязка памяти к узлу без свободной RAM (NUMA OOM): если на целевом узле закончилась память, системный вызов с политикой `MPOL_BIND` вернет `ENOMEM`, даже если на соседнем сокете свободно 100 ГБ RAM. Для мягкой привязки используют `MPOL_PREFERRED`.
2. Планировщик Go не является NUMA-aware по умолчанию: горутина может переехать на другой P, выполняющийся на другом сокете.

## На собеседовании

«Как подружить высоконагруженный сервис на Go с многосокетной NUMA-архитектурой?»
Ответ: Стандартная практика в BigTech (Яндекс, Cloudflare) — запуск нескольких независимых инстансов Go-сервиса, каждый из которых изолирован на своем NUMA-узле через утилиту `numactl --cpunodebind=0 --membind=0 ./service`. Это исключает межсокетовые транзакции и дает многократный прирост к пропускной способности сети.
