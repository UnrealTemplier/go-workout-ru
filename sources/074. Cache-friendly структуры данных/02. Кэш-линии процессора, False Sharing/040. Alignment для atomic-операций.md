### Исходная формулировка

**Alignment для atomic операций.**: Создайте массив счётчиков `[]uint64`. Покажите, что `atomic.AddUint64(&counters[i])` паникует на ARM32/ARM64, если адрес не выровнен на 8 байт. Объясните, почему `sync/atomic` требует alignment и как `struct` padding решает это.

## Теория

Один из самых коварных багов в истории Go — **паника невыровненных 64-битных атомиков**.

До Go 1.19 функции `atomic.AddInt64(&val, 1)` принимали обычный указатель `*int64`.
На 64-битных платформах (amd64, arm64) указатели и `int64` всегда кратны 8 байтам.
**Но на 32-битных архитектурах (ARM32, 386, MIPS, RISC-V 32):**
- Выравнивание обычного `int64` по умолчанию равно **4 байтам**!
- Если в структуре перед `int64` стояло поле `int32`, поле `int64` получало смещение 4 (не кратно 8).
- Аппаратные атомарные инструкции процессора ARM32 (`LDREXD`/`STREXD`) требуют, чтобы адрес был **строго кратен 8 байтам**.
- При попытке вызвать `atomic.AddInt64` рантайм Go немедленно аварийно завершал процесс с паникой:
  `panic: unaligned 64-bit atomic operation`!

**Решение в Go 1.19+:**
Команда Go представила типизированные обертки `atomic.Int64`, `atomic.Uint64`, `atomic.Pointer`. Внутреннее устройство этих типов гарантирует 8-байтовое выравнивание на абсолютно всех платформах.

## Решение по шагам

1. Смоделируйте структуру с нарушенным 4-байтовым смещением для `uint64`.
2. Реализуйте проверку адреса перед вызовом низкоуровневых атомиков: `uintptr(ptr) & 7 == 0`.
3. Покажите, как правильно использовать `atomic.Uint64` из Go 1.19+.
4. Продемонстрируйте безопасный паттерн размещения 64-битных атомиков первым полем структуры.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"unsafe"
)

// Опасная структура для 32-битных платформ (до Go 1.19)
type LegacyBadStruct struct {
	flag    int32  // 4 байта
	counter uint64 // на 32-бит платформах получит offset 4 (НЕ КРАТНО 8!)
}

// Безопасная структура: атомик размещен первым полем
type SafeAlignedStruct struct {
	counter uint64 // Offset 0: гарантированно кратен 8 на любой ОС!
	flag    int32
}

// Современный эталон Go 1.19+: автоматическое 8-байтовое выравнивание
type ModernAtomicStruct struct {
	flag    int32
	counter atomic.Uint64 // Тип atomic.Uint64 сам гарантирует выравнивание!
}

func main() {
	var bad LegacyBadStruct
	var safe SafeAlignedStruct
	var modern ModernAtomicStruct

	fmt.Println("=== 64-bit Atomic Alignment & 32-bit Architecture Safety ===")
	fmt.Printf("LegacyBadStruct:\n")
	fmt.Printf("  counter offset: %d bytes (Unaligned risk on ARM32 if offset is 4!)\n",
		unsafe.Offsetof(bad.counter))

	fmt.Printf("SafeAlignedStruct:\n")
	fmt.Printf("  counter offset: %d bytes (Safe 64-bit atomic target)\n",
		unsafe.Offsetof(safe.counter))

	fmt.Printf("ModernAtomicStruct (Go 1.19+):\n")
	fmt.Printf("  counter offset: %d bytes (Alignof: %d)\n\n",
		unsafe.Offsetof(modern.counter), unsafe.Alignof(modern.counter))

	// Проверка выравнивания адреса в рантайме
	ptr := &safe.counter
	addr := uintptr(unsafe.Pointer(ptr))
	if addr&7 != 0 {
		panic("FATAL: 64-bit atomic target is not 8-byte aligned!")
	}

	// Безопасный инкремент
	atomic.AddUint64(&safe.counter, 1)
	modern.counter.Add(1)

	fmt.Printf("Atomic operations executed successfully! Counter values: safe=%d, modern=%d\n",
		safe.counter, modern.counter.Load())
}
```

ℹ️ Анализ выравнивания 64-битных атомиков и безопасное использование atomic.Uint64 (Go 1.19+)

## Под капотом

В спецификации пакета `sync/atomic` прямо указано: «On 32-bit architectures, the caller is responsible for arranging 64-bit alignment of 64-bit words accessed atomically. The first word in a variable or in an allocated struct, array, or slice can be relied upon to be 64-bit aligned.» В типе `atomic.Uint64` Go 1.19 добавил внутреннее поле `_ [0]uint64`, заставляющее компилятор выравнивать всю структуру по границе 8 байт.

## Подводные камни

1. Размещение обычного `int64` для `atomic.AddInt64` вторым полем после `bool` или `int32`: такой код работает на ноутбуке разработчика (x86-64), но мгновенно крашит сервис при сборке под ARM32 (Raspberry Pi, IoT) или WebAssembly (Wasm).
2. Использование `atomic.Value` вместо `atomic.Pointer`: `atomic.Value` приводит к лишним аллокациям интерфейса в куче.

## На собеседовании

«Почему на 32-битных ARM процессорах атомарные операции с 64-битными числами требуют строгой 8-байтовой границы?»
Ответ: Инструкция `LDREXD` (Load-Exclusive Doubleword) на ARM32 обращается к шине памяти парами 32-битных регистров (например, R0 и R1). Аппаратный контроллер эксклюзивного доступа (Local Exclusive Monitor) следит за адресами с точностью до 8 байт. Если младшие 3 бита адреса не равны 0, аппаратура генерирует неперехватываемое исключение Alignment Fault.
