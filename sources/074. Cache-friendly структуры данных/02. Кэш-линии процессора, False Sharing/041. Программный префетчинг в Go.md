# Программный префетчинг в Go: ускорение обхода графов и связных списков

### Исходная формулировка

## Теория

Проблема связных списков и графов в памяти (Pointer Chasing) заключается в том, что процессор не может начать загрузку узла \(i+1\), пока не прочитает указатель `curr.next` из узла \(i\).

**Идея опережающего префетчинга (Lookahead Software Prefetch):**
Если мы обрабатываем цепочку или массив указателей на узлы, мы можем заглядывать на \(K\) шагов вперед (например, \(K = 4\) или \(K = 8\)).
Пока процессор выполняет полезную работу над узлом \(i\):
1. Мы извлекаем указатель на узел \(i + K\);
2. Выполняем предварительное чтение (Prefetch) адреса узла \(i + K\) в кэш L1;
3. К моменту, когда цикл дойдет до узла \(i + K\), его данные уже будут находиться в быстром кэше L1 со скоростью чтения ~1 нс вместо ожидания DRAM в 70 нс!

В Go программный префетчинг эмулируется либо через чтение фиктивного поля наперед (`_ = lookahead.val`), либо через ассемблерные интринсики `PREFETCHT0`.

## Решение по шагам

1. Создайте связный список из 2 000 000 узлов, разбросанных по памяти кучи.
2. Создайте массив прямых ссылок на узлы для моделирования опережающего префетчинга.
3. Реализуйте базовый обход без упреждающего чтения.
4. Реализуйте обход с упреждающим чтением узла `ptrs[i+4]` в кэш.
5. Замерьте время и продемонстрируйте ускорение обхода.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"time"
)

type GraphNode struct {
	id      int
	payload [56]byte // Раздуваем узел до 64 байт (1 кэш-линия)
}

func standardTraversal(nodes []*GraphNode) int {
	var sum int
	for i := 0; i < len(nodes); i++ {
		sum += nodes[i].id
	}
	return sum
}

// Опережающий префетчинг: чтение на 8 элементов вперед
func prefetchTraversal(nodes []*GraphNode) int {
	var sum int
	n := len(nodes)
	const lookahead = 8

	for i := 0; i < n; i++ {
		// Предварительная загрузка кэш-линии на K шагов вперед
		if i+lookahead < n {
			// Чтение фиктивного байта инициирует загрузку 64B кэш-линии из DRAM в L1
			_ = nodes[i+lookahead].id
		}

		sum += nodes[i].id
	}
	return sum
}

func main() {
	const count = 3_000_000
	fmt.Printf("=== Software Prefetching Benchmark (%d fragmented nodes) ===\n\n", count)

	// Аллоцируем узлы
	pool := make([]GraphNode, count)
	for i := range pool {
		pool[i].id = i
	}

	// Перемешиваем указатели, чтобы исключить предсказуемость Hardware Prefetcher
	ptrs := make([]*GraphNode, count)
	for i := range ptrs {
		ptrs[i] = &pool[i]
	}

	r := rand.New(rand.NewSource(12345))
	r.Shuffle(len(ptrs), func(i, j int) {
		ptrs[i], ptrs[j] = ptrs[j], ptrs[i]
	})

	// 1. Стандартный обход
	startStd := time.Now()
	resStd := standardTraversal(ptrs)
	durStd := time.Since(startStd)
	fmt.Printf("Standard Traversal (No Prefetch): %v (Sum: %d)\n", durStd, resStd)

	// 2. Обход с Lookahead Prefetching
	startPrefetch := time.Now()
	resPrefetch := prefetchTraversal(ptrs)
	durPrefetch := time.Since(startPrefetch)
	fmt.Printf("Lookahead Prefetch Traversal:     %v (Sum: %d)\n", durPrefetch, resPrefetch)

	speedup := float64(durStd) / float64(durPrefetch)
	fmt.Printf("\nPrefetching improved memory access latency by %.2fx!\n", speedup)
}
```

ℹ️ Программная эмуляция опережающего префетчинга узлов графа на K шагов вперед

## Под капотом

В ассемблере x86 инструкция `PREFETCHT0 [addr]` подсказывает процессору подгрузить строку кэша во все уровни (L1, L2, L3) без блокировки конвейера. Инструкция не вызывает прерываний при невалидном адресе (No-Fault) и исполняется спекулятивно. В коде Go фиктивное чтение `_ = nodes[i+lookahead].id` компилируется в инструкцию `MOVQ`, которая аппаратно запускает L1 Line Fill Buffer.

## Подводные камни

1. Слишком большой шаг упреждения (например, \(K=256\)): к моменту, когда цикл дойдет до узла, предварительно загруженная строка уже будет вытеснена из L1 другими данными.
2. Слишком маленький шаг (\(K=1\)): задержка DRAM составляет 60 нс, процессор успеет дойти до узла за 2 нс, и префетч не успеет отработать.

## На собеседовании

«Как программный префетчинг применяется в высокопроизводительных хэш-таблицах (например, F14 / SwissTable от Google/Meta)?»
Ответ: При пакетном поиске ключей (Batch Lookup) для каждого входящего ключа вычисляется хэш бакета. Сразу вызывается `prefetch(&buckets[hash])` для всех 16 ключей в пачке. Затем процессор возвращается к первому ключу — его бакет уже подгружен в кэш L1, исключая последовательные задержки памяти.
