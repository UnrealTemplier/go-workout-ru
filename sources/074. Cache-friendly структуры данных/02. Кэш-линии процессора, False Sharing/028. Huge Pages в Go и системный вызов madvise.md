# Huge Pages в Go и системный вызов madvise (MADV_HUGEPAGE)

## Условие

### Исходная формулировка

**Huge pages в Go**: Включите huge pages через `GODEBUG=memprofilerate=0` и настройте OS для использования transparent huge pages. Измерьте влияние на memory-intensive workloads.

## Теория

По умолчанию аллокатор памяти Go выделяет память у ядра ОС через системный вызов `mmap` стандартными страницами по 4 КБ.

Для критических участков с огромными объемами кэша (гигабайты памяти) в Linux существует механизм **Explicit Transparent Huge Pages via `madvise`**:
Системный вызов:
```c
madvise(addr, length, MADV_HUGEPAGE);
```
Флаг `MADV_HUGEPAGE` сообщает ядру Linux, что данный регион виртуальной памяти должен обслуживаться страницами размером **2 МБ (Huge Pages)** при первой возможности.

Преимущества Huge Pages в Go:
1. Сокращение размера таблиц страниц ядра с гигабайт до мегабайт;
2. Снижение TLB-промахов в разы;
3. Ускорение сканирования больших срезов на 10–25%.

## Решение по шагам

1. Выделите большой непрерывный срез байт размером 64 МБ, выровненный по границе 2 МБ.
2. С помощью пакета `golang.org/x/sys/unix` вызовите `unix.Madvise(ptr, size, unix.MADV_HUGEPAGE)`.
3. Реализуйте бенчмарк обхода памяти с шагом страницы.
4. Продемонстрируйте корректную обработку кодов возврата ядра.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
	"time"
	"unsafe"
)

const (
	HugePageSize = 2 * 1024 * 1024 // 2 MB
	AllocSize    = 64 * 1024 * 1024 // 64 MB
	MADV_HUGEPAGE = 14               // Linux syscall constant
)

// AllocateAlignedHugePages выделяет память напрямую через mmap с хинтом MADV_HUGEPAGE
func AllocateAlignedHugePages(size int) ([]byte, error) {
	// mmap анонимной приватной памяти
	data, err := syscall.Mmap(
		-1,
		0,
		size,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		return nil, fmt.Errorf("mmap failed: %w", err)
	}

	// Вызов madvise с флагом MADV_HUGEPAGE
	rawPtr := unsafe.Pointer(&data[0])
	_, _, errno := syscall.Syscall(
		syscall.SYS_MADVISE,
		uintptr(rawPtr),
		uintptr(size),
		uintptr(MADV_HUGEPAGE),
	)

	if errno != 0 {
		fmt.Printf("Warning: madvise MADV_HUGEPAGE returned errno %d (THP may be disabled in kernel)\n", errno)
	} else {
		fmt.Println("Successfully advised Linux kernel to back region with 2MB Huge Pages!")
	}

	return data, nil
}

func main() {
	fmt.Printf("=== Linux Huge Pages (2MB) Allocation Demo ===\n")
	fmt.Printf("Allocating %d MB buffer...\n", AllocSize/(1024*1024))

	buf, err := AllocateAlignedHugePages(AllocSize)
	if err != nil {
		fmt.Println("Error:", err)
		return
	}
	defer syscall.Munmap(buf)

	// Инициализация памяти для активации страниц ядром (Page Fault resolution)
	startInit := time.Now()
	for i := 0; i < len(buf); i += 4096 {
		buf[i] = 1
	}
	fmt.Printf("Memory touched and committed in: %v\n", time.Since(startInit))

	// Замер обхода с прыжками по страницам
	start := time.Now()
	var sum byte
	for pass := 0; pass < 20; pass++ {
		for i := 0; i < len(buf); i += 4096 {
			sum += buf[i]
		}
	}
	elapsed := time.Since(start)
	_ = sum

	fmt.Printf("Traversal of 64MB buffer completed in: %v\n", elapsed)
	fmt.Println("Kernel status check: check /proc/meminfo 'AnonHugePages' to view active 2MB pages.")
}
```

ℹ️ Выделение памяти через mmap и включение 2MB Huge Pages через системный вызов madvise

## Под капотом

Когда ядро Linux обрабатывает `madvise(MADV_HUGEPAGE)`, оно помечает VMA (Virtual Memory Area) флагом `VM_HUGEPAGE`. При первом обращении к странице (Page Fault) аллокатор Buddy Allocator ядра пытается немедленно выделить непрерывный блок физической памяти размером 2 МБ (Order 9). Если в системе нет непрерывных 2 МБ из-за внешней фрагментации, ядро временно выделяет обычные страницы 4 КБ, а фоновый демон `khugepaged` позже объединит их в Huge Page.

## Подводные камни

1. Забывание о `syscall.Munmap`: память, выделенная через `mmap` в обход кучи Go, не освобождается сборщиком мусора! Обязателен явный вызов `munmap`.
2. Попытка вызвать `madvise` на невыровненном адресе: адрес и размер обязаны быть кратны размеру страницы.

## На собеседовании

«Чем Transparent Huge Pages (THP) отличаются от Explicit HugeTLB в Linux?»
Ответ: THP управляется ядром прозрачно для приложения и не требует предварительного резервирования памяти при загрузке ОС. Explicit HugeTLB (`hugetlbfs`) требует от администратора заранее зарезервировать фиксированное число огромных страниц (например, `hugepages=1024` в grub), гарантируя 100% отсутствие фрагментации ценой невозможности вернуть эту память под другие нужды.
