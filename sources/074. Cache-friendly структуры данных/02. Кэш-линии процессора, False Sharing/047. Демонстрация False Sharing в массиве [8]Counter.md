### Исходная формулировка

**False sharing demonstration**: Создайте структуру:
```go

    value int64
}

    c [8]Counter
}
```
Запустите 8 горутин, каждая инкрементирует свой `Counter`. Измерьте производительность.

## Теория

Разберем структуру:
```go
type Counter struct {
    value int64 // 8 байт
}
type Counters struct {
    c [8]Counter // 8 * 8 = 64 байта
}
```
Весь массив `c` размером ровно **64 байта** умещается в **одну-единственную кэш-линию**.

Когда мы запускаем 8 параллельных горутин:
- Горутина 0 пишет в `c[0]`;
- Горутина 1 пишет в `c[1]`;
- ...
- Горутина 7 пишет в `c[7]`.

Хотя логически это 8 разных независимых счетчиков, на аппаратном уровне все 8 ядер процессора непрерывно отправляют запросы `RFO (Request For Ownership)` на одну и ту же 64-байтовую строку.
Кэш-линия не может оставаться в L1-кэше ни одного ядра даже на 2 такта. Она постоянно пересылается по межъядерной шине.
Вместо 8-кратного ускорения от использования 8 ядер система работает медленнее, чем на одном-единственном ядре!

## Решение по шагам

1. Опишите структуру `Counters` с массивом `[8]Counter`.
2. Напишите функцию параллельного инкремента 8 горутинами по 20 000 000 операций на ядро.
3. Замерьте суммарное время выполнения.
4. Рассчитайте пропускную способность (Mops/sec).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
	"unsafe"
)

type Counter struct {
	value int64
}

type Counters struct {
	c [8]Counter
}

func main() {
	var counters Counters
	fmt.Printf("Counters struct size: %d bytes (Exactly 1 Cache Line!)\n", unsafe.Sizeof(counters))

	workers := 8
	if runtime.NumCPU() < 8 {
		workers = runtime.NumCPU()
	}
	runtime.GOMAXPROCS(workers)

	const n = 20_000_000
	fmt.Printf("Running %d parallel goroutines, %d increments each...\n\n", workers, n)

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		idx := w
		go func() {
			defer wg.Done()
			for i := int64(0); i < n; i++ {
				counters.c[idx].value++
			}
		}()
	}

	wg.Wait()
	dur := time.Since(start)

	totalOps := uint64(workers) * n
	mops := float64(totalOps) / dur.Seconds() / 1_000_000

	fmt.Printf("Execution completed in: %v\n", dur)
	fmt.Printf("Throughput under False Sharing: %.2f Mops/sec\n", mops)
	fmt.Println("Observation: 8 cores fully stalled waiting for bus cache-line ownership transfers!")
}
```

ℹ️ Демонстрация деградации производительности при конкуренции 8 горутин за массив [8]Counter

## Под капотом

Аппаратный счетчик PMU `MEM_LOAD_L3_HIT_RETIRED.XSNP_HITM` в процессорах Intel регистрирует обращения к памяти, которые попали в измененную кэш-линию другого ядра (Cross-core Snoop Hit Modified). В данной программе этот счетчик будет расти со скоростью миллиардов событий в секунду, указывая на тотальный коллапс кэша.

## Подводные камни

1. Использование неатомарного `value++` в многопоточном коде без паддинга: помимо False Sharing возникает риск Data Race на границе слов.
2. Полагание на то, что `runtime.Gosched()` решит проблему: передача управления другой горутине лишь добавит накладные расходы контекстного переключения.

## На собеседовании

«Как доказать на собеседовании, что проблема в False Sharing, а не в синхронизации?»
Ответ: Запустить бенчмарк на 1 ядре (`GOMAXPROCS=1`) и на 8 ядрах. Если на 1 ядре программа работает быстрее, чем на 8 ядрах — это 100% диагностический признак False Sharing (на 1 ядре нет инвалидаций кэша между ядрами).
