# Data Locality в тяжелых структурах: Entity с Data [50]int в AoS vs SoA

## Условие

44. **[SoA vs AoS (Data Locality)]**: Создай структуру `Entity { ID int; Active bool; Data [50]int }`. Создай слайс из 100 000 таких структур (Array of Structs). Напиши бенчмарк, который суммирует `ID` только активных сущностей. Затем перепиши на Structure of Arrays. Замерь разницу. В AoS каждое обращение тащит в кэш тяжелый `Data [50]int`, вытесняя полезные данные.

### Исходная формулировка

**[SoA vs AoS (Data Locality)]**: Создай структуру `Entity { ID int; Active bool; Data [50]int }`. Создай слайс из 100 000 таких структур (Array of Structs). Напиши бенчмарк, который суммирует `ID` только активных сущностей. Затем перепиши на Struct of Arrays (SoA): `IDs []int`, `Actives []bool`. Оцени колоссальную разницу в скорости из-за плотности данных в кэше.

## Теория

Классическая ошибка объектно-ориентированного моделирования (AoS) — хранение «холодных» тяжелых данных рядом с «горячими» полями фильтрации:
```go
type EntityAoS struct {
    ID     int      // 8 байт (горячее поле)
    Active bool     // 1 байт (горячее поле фильтрации)
    _      [7]byte  // padding
    Data   [50]int  // 400 байт (ТЯЖЕЛЫЕ ХОЛОДНЫЕ ДАННЫЕ!)
}
```
Размер структуры `EntityAoS` составляет \(8 + 8 + 400 = \mathbf{416\text{ байт}}\)!
Чтобы прочитать одну сущность, процессор вынужден загрузить:
$$\frac{416\text{ байт}}{64\text{ байта}} \approx 7\text{ кэш-линий!}$$
Из этих 7 кэш-линий алгоритм суммирования активных ID использует всего **9 байт**, а 407 байт поля `Data` просто забивают кэш L1, вытесняя все остальное.

**Переход на SoA (Data Locality):**
```go
type EntitySystemSoA struct {
    IDs    []int      // Непрерывный массив (8 байт на элемент)
    Active []bool     // Непрерывный массив (1 байт на элемент)
    Data   [][50]int  // Отдельный холодный массив
}
```
При фильтрации активных ID процессор считывает только срезы `Active` и `IDs`.
Кэш-линия вмещает сразу 64 флага `Active` или 8 идентификаторов `ID`.
Пропускная способность возрастает в **10–30 раз**!

## Решение по шагам

1. Опишите структуру `EntityAoS` с полем `Data [50]int` (416 байт).
2. Опишите структуру `EntitySystemSoA` с разделенными срезами `IDs`, `Active`, `Data`.
3. Инициализируйте 100 000 сущностей (каждая 10-я сущность активна).
4. Напишите функцию фильтрации и суммирования активных ID для AoS и для SoA.
5. Замерьте время и покажите многократный выигрыш SoA.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
	"unsafe"
)

type EntityAoS struct {
	ID     int
	Active bool
	_      [7]byte // padding
	Data   [50]int // 400 байт холодных данных
}

type EntitySystemSoA struct {
	IDs    []int
	Active []bool
	Data   [][50]int
}

func SumActiveAoS(entities []EntityAoS) int {
	var sum int
	for i := range entities {
		if entities[i].Active {
			sum += entities[i].ID
		}
	}
	return sum
}

func SumActiveSoA(sys *EntitySystemSoA) int {
	var sum int
	active := sys.Active
	ids := sys.IDs
	for i := range active {
		if active[i] {
			sum += ids[i]
		}
	}
	return sum
}

func main() {
	const count = 200_000
	var sample EntityAoS
	fmt.Printf("=== Heavy Entity Data Locality Benchmark ===\n")
	fmt.Printf("Size of EntityAoS: %d bytes (Huge cache footprint!)\n\n", unsafe.Sizeof(sample))

	// Инициализация AoS
	aos := make([]EntityAoS, count)
	for i := 0; i < count; i++ {
		aos[i] = EntityAoS{
			ID:     i,
			Active: i%10 == 0, // 10% активных
		}
	}

	// Инициализация SoA
	soa := &EntitySystemSoA{
		IDs:    make([]int, count),
		Active: make([]bool, count),
		Data:   make([][50]int, count),
	}
	for i := 0; i < count; i++ {
		soa.IDs[i] = i
		soa.Active[i] = (i%10 == 0)
	}

	const passes = 100

	// 1. AoS Benchmark
	startAoS := time.Now()
	var resAoS int
	for p := 0; p < passes; p++ {
		resAoS = SumActiveAoS(aos)
	}
	durAoS := time.Since(startAoS)
	fmt.Printf("AoS (Array of Heavy Structs): %v (Sum: %d)\n", durAoS, resAoS)

	// 2. SoA Benchmark
	startSoA := time.Now()
	var resSoA int
	for p := 0; p < passes; p++ {
		resSoA = SumActiveSoA(soa)
	}
	durSoA := time.Since(startSoA)
	fmt.Printf("SoA (Decoupled Hot/Cold Data): %v (Sum: %d)\n", durSoA, resSoA)

	speedup := float64(durAoS) / float64(durSoA)
	fmt.Printf("\nSoA is %.2fx faster! Decoupling heavy Data[50]int eliminated 97%% of cache pollution!\n", speedup)
}
```

ℹ️ Сравнение фильтрации тяжелых сущностей (416 байт) в AoS и SoA: ликвидация загрязнения кэша

## Под капотом

В тесте AoS суммарный объем данных составляет \(200\,000 \times 416\text{ байт} = \mathbf{83.2\text{ МБ}}\). Это полностью вымывает кэш L3 процессора на каждом проходе. В тесте SoA горячие массивы `Active` (200 КБ) и `IDs` (1.6 МБ) суммарно занимают всего **1.8 МБ**, целиком умещаясь в быстрый L2/L3 кэш процессора.

## Подводные камни

1. Хранение поля `Data` как указателя `Data *[50]int` в AoS: это уменьшит размер структуры до 24 байт, но создаст 200 000 аллокаций в куче и добавит оверхед GC. SoA решает проблему без лишних аллокаций.
2. Неаккуратный доступ: если логика требует чтения и `Data` для каждого элемента, выигрыша не будет.

## На собеседовании

«Что такое Hot/Cold Splitting полей структуры?»
Ответ: Это паттерн проектирования структур данных, при котором часто используемые (Hot) поля выносятся в компактную основную структуру, а редко используемые (Cold) поля (метаданные, статистика, описания, отладочная информация) выносятся в отдельную вспомогательную структуру. Это кардинально увеличивает плотность горячих объектов в кэше L1.
