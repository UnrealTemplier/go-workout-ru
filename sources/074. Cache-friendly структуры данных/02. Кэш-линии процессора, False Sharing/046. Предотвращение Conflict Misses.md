# Предотвращение Conflict Misses: обход массива с шагом 512 байт

### Исходная формулировка

**Предотвращение conflict misses.**: Создайте массив размером 8192 `int64` (64 KB, ровно L1 cache size на многих CPU). Обходите с шагом 512 байт (8 элементов). Объясните, почему при определённых размерах (кратных степени 2) возникают conflict misses (associativity limit). Решение: добавить padding к строке (slice of structs с trailing `[X]byte`).

## Теория

Проблема коллизионных промахов (Conflict Misses) в \(N\)-канальном кэше:

Представьте массив размером 64 КБ:
- Размер кэша L1d: **32 КБ** (64 сета по 8 строк).
- Шаг обхода: **512 байт** (\(2^9\)).
- В бинарном представлении адреса: младшие 6 бит — смещение внутри кэш-линии (байты 0..63).
- Биты с 6 по 11 (6 бит) определяют **Cache Set Index** (от 0 до 63).
- При шаге в 512 байт (\(512 / 64 = 8\) линий) индекс набора каждый раз увеличивается ровно на 8:
  - Обращение 0 \(\to\) Set 0
  - Обращение 1 \(\to\) Set 8
  - ...
  - Обращение 8 \(\to\) Set 64 (снова Set 0!)
- В результате из 64 доступных наборов кэша используются **только 8 наборов** (Set 0, 8, 16, 24, 32, 40, 48, 56)!
- Остальные 56 наборов кэша (87.5% емкости L1!) простаивают пустыми, в то время как 8 используемых наборов непрерывно переполняются и вытесняют данные!

**Решение (Offset Padding / Array Pitch):**
Добавление небольшого смещения к шагу (например, шаг 512 + 64 = 576 байт) равномерно распределяет адреса по всем 64 наборам кэша, ликвидируя коллизии.

## Решение по шагам

1. Создайте буфер `[]int64` размером 8192 элемента (64 КБ).
2. Выполните обход с шагом 64 элемента (512 байт: кратно степени двойки).
3. Выполните обход со сдвинутым шагом 65 элементов (520 байт: не кратно степени двойки).
4. Замерьте время 1 000 000 проходов.
5. Покажите ускорение за счет равномерного использования всех сетов кэша.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

const ArrayLen = 8192 // 8192 * 8 = 64 KB

func runConflictTest(data []int64, stride int, passes int) time.Duration {
	n := len(data)
	var sum int64

	start := time.Now()
	for p := 0; p < passes; p++ {
		for i := 0; i < n; i += stride {
			sum += data[i]
		}
	}
	dur := time.Since(start)
	_ = sum
	return dur
}

func main() {
	data := make([]int64, ArrayLen)
	for i := range data {
		data[i] = int64(i)
	}

	const passes = 2_000_000
	fmt.Printf("=== Conflict Misses vs Uniform Set Distribution (%d KB Array) ===\n\n", (ArrayLen*8)/1024)

	// 1. Шаг 64 элемента (512 байт = степень двойки: 87.5% кэша простаивает!)
	stridePower2 := 64
	durBad := runConflictTest(data, stridePower2, passes)
	fmt.Printf("Stride 512B (Power of 2):  %v (Severe Conflict Misses)\n", durBad)

	// 2. Шаг 65 элементов (520 байт = не кратно: задействованы все сеты кэша)
	strideShifted := 65
	durGood := runConflictTest(data, strideShifted, passes)
	fmt.Printf("Stride 520B (Offset +8B):   %v (Uniform Cache Set Distribution)\n", durGood)

	speedup := float64(durBad) / float64(durGood)
	fmt.Printf("\nUniform set distribution yielded %.2fx faster execution!\n", speedup)
}
```

ℹ️ Устранение Conflict Misses в L1d кэше за счет сдвига шага обхода от степеней двойки

## Под капотом

Ассоциативность 8-way означает, что в одном сете может храниться одновременно не более 8 кэш-линий. При шаге 512 байт девятое обращение обязано вытеснить первую строку из кэша (LRU Eviction). При сдвиге на 1 элемент адрес каждый раз попадает в соседний сет, позволяя задействовать все 64 набора кэша.

## Подводные камни

1. Выбор шага итерации, совпадающего с размером страницы памяти (4096 байт): коллизии происходят одновременно и в кэше L1, и в буфере TLB.
2. Неоправданное усложнение кода: если массив невелик (до 16 КБ), коллизии не играют роли.

## На собеседовании

«Как в компиляторах C/Go решается проблема Conflict Misses при векторизации циклов?»
Ответ: Применяется техника **Loop Peeling and Array Padding**: компилятор добавляет паддинг в конец каждой строки многомерного массива (Pitch), сдвигая базовые адреса строк относительно друг друга, гарантируя некратность степени двойки.
