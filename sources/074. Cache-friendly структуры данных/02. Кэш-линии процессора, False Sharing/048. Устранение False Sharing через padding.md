# Устранение False Sharing через padding: восстановление скорости в 8–15 раз

## Условие

48. **False sharing fix через padding**: Добавьте padding между counters:
    ```go
    type PaddedCounter struct {
        value int64
        _     [56]byte  // pad to 64 bytes
    ```

### Исходная формулировка

**False sharing fix через padding**: Добавьте padding между counters:
```go
type PaddedCounter struct {
    value int64
    _     [56]byte  // pad to 64 bytes
}
```
Теперь каждый counter в отдельной cache line. Производительность должна вырасти в 5-10x.

## Теория

Решение проблемы упражнения 47:
Мы выравниваем каждый элемент массива до размера ровно **64 байта**:
```go
type PaddedCounter struct {
    value int64    // 8 байт полезных данных
    _     [56]byte // 56 байт заполнителя
}
type PaddedCounters struct {
    c [8]PaddedCounter // 8 * 64 = 512 байт (8 независимых кэш-линий)
}
```

Анализ архитектурных изменений:
1. Элемент `c[0]` занимает байты 0..63 (Кэш-линия 0).
2. Элемент `c[1]` занимает байты 64..127 (Кэш-линия 1).
3. ...
4. Элемент `c[7]` занимает байты 448..511 (Кэш-линия 7).

Каждое ядро процессора удерживает свою кэш-линию в состоянии **Modified (M)** в своем приватном L1d кэше.
Никаких транзакций по шине процессора не происходит.
Каждый инкремент выполняется за **1 такт процессора (~0.3 нс)**!
Скорость возрастает в **8–15 раз**!

## Решение по шагам

1. Создайте структуру `PaddedCounter { value int64; _ [56]byte }`.
2. Создайте структуру `PaddedCounters { c [8]PaddedCounter }`.
3. Запустите те же 8 горутин по 20 000 000 операций на ядро.
4. Замерьте время и рассчитайте пропускную способность.
5. Сравните с результатом предыдущего упражнения 47.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
	"unsafe"
)

type PaddedCounter struct {
	value int64
	_     [56]byte // pad to exactly 64 bytes
}

type PaddedCounters struct {
	c [8]PaddedCounter
}

func main() {
	var counters PaddedCounters
	fmt.Printf("PaddedCounters struct size: %d bytes (8 independent Cache Lines)\n",
		unsafe.Sizeof(counters))

	workers := 8
	if runtime.NumCPU() < 8 {
		workers = runtime.NumCPU()
	}
	runtime.GOMAXPROCS(workers)

	const n = 20_000_000
	fmt.Printf("Running %d parallel goroutines with Cache Line Padding...\n\n", workers)

	var wg sync.WaitGroup
	wg.Add(workers)

	start := time.Now()
	for w := 0; w < workers; w++ {
		idx := w
		go func() {
			defer wg.Done()
			for i := int64(0); i < n; i++ {
				counters.c[idx].value++
			}
		}()
	}

	wg.Wait()
	dur := time.Since(start)

	totalOps := uint64(workers) * n
	mops := float64(totalOps) / dur.Seconds() / 1_000_000

	fmt.Printf("Execution completed in: %v\n", dur)
	fmt.Printf("Throughput with Padding:        %.2f Mops/sec\n", mops)
	fmt.Println("SUCCESS: Padding eliminated all cross-core invalidations!")
}
```

ℹ️ Устранение False Sharing в массиве счетчиков с помощью 56-байтового заполнителя до размера 64 байта

## Под капотом

Размер массива вырос с 64 байт до 512 байт (в 8 раз). Однако эти 512 байт идеально распределяются по L1 кэшам разных ядер. Каждое ядро держит только свои 64 байта. Общий объем кэша не перегружается, а интерконнект свободен.

## Подводные камни

1. Использование паддинга `[64]byte`: если добавить 64 байта, общий размер станет \(8 + 64 = 72\) байта, что из-за выравнивания округлится до 80 или 128 байт. Для выравнивания до 64 байт нужно именно 56 байт (\(64 - 8 = 56\)).
2. Неучет 32-битных платформ: на 32-битных ОС `int64` занимает те же 8 байт, поэтому `_ [56]byte` остается корректным.

## На собеседовании

«Как в Go гарантировать, что размер PaddedCounter всегда равен ровно 64 байтам при компиляции?»
Ответ: Использовать проверку во время компиляции (Compile-Time Assertion):
`const _ = uint(64 - unsafe.Sizeof(PaddedCounter{}))`
`const _ = uint(unsafe.Sizeof(PaddedCounter{}) - 64)`
Если размер структуры станет 63 или 65 байт, константа попытается вычислить отрицательное число в `uint`, что вызовет ошибку компиляции.
