# Cache Coloring и распределение памяти по наборам кэша

## Условие

37. **Cache coloring**: Для critical data structures используйте cache coloring — распределяйте данные так, чтобы они не конфликтовали в cache sets. Напишите программу, демонстрирующую распределение адресов по цветам (наборам) кэша.

### Исходная формулировка

**Cache coloring**: Для critical data structures используйте cache coloring — распределяйте данные так, чтобы они не конфликтовали в cache sets.

## Теория

**Cache Coloring (Раскраска кэша)** — это техника низкоуровневой оптимизации, при которой страницы виртуальной памяти и структуры данных распределяются по физическим адресам таким образом, чтобы минимизировать аппаратные конфликты в наборах кэша (\(N\)-way Set-Associative Cache).

Как работает цвет кэша:
- В \(N\)-канальном кэше физический адрес делится на:
  `[ Tag | Cache Set Index | Line Offset ]`
- Биты, определяющие `Cache Set Index`, называются **цветом кэша (Cache Color)**.
- Если две горячие структуры данных имеют одинаковый цвет кэша, они конкурируют за одни и те же каналы ассоциативности (Sets). Если число таких структур превышает степень ассоциативности \(N\) (обычно 8), происходит взаимное вытеснение строк кэша.

**Паттерн Cache Coloring:**
Критическим структурам или буферам намеренно добавляют смещение (Offset / Padding), чтобы изменить их хэш-индекс сета и распределить их по разным «цветам» кэша.

## Решение по шагам

1. Создайте функцию `CalculateCacheColor(addr uintptr, cacheSize, ways, lineSize int) int`.
2. Извлеките биты сета кэша из физического адреса.
3. Продемонстрируйте, как массив структур без смещения попадает в один цвет кэша.
4. Добавьте искусственное цветовое смещение (Color Padding) и покажите равномерное распределение по наборам кэша.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"unsafe"
)

// Параметры стандартного L1d кэша: 32KB, 8-way, 64B line
const (
	L1CacheSize = 32 * 1024
	L1LineSize  = 64
	L1Ways      = 8
	L1Sets      = L1CacheSize / (L1LineSize * L1Ways) // 64 набора
)

func GetCacheSetColor(ptr unsafe.Pointer) int {
	addr := uintptr(ptr)
	// Сдвигаем на 6 бит (offset внутри 64-байтовой линии)
	// И берем остаток по модулю числа сетов (64 сета = младшие 6 бит)
	setIndex := (addr >> 6) & (L1Sets - 1)
	return int(setIndex)
}

type CriticalBuffer struct {
	data [4096]byte
}

func main() {
	fmt.Printf("=== Cache Coloring Analysis (L1d: %d KB, %d-way, %d Sets) ===\n\n",
		L1CacheSize/1024, L1Ways, L1Sets)

	// Создаем 8 независимых буферов
	buffers := make([]CriticalBuffer, 8)

	fmt.Printf("%-10s | %-18s | %s\n", "Buffer", "Memory Address", "Cache Color (Set Index)")
	fmt.Println("-------------------------------------------------------")

	colorDistribution := make(map[int]int)
	for i := range buffers {
		ptr := unsafe.Pointer(&buffers[i])
		color := GetCacheSetColor(ptr)
		colorDistribution[color]++
		fmt.Printf("Buffer %-3d | %-18p | Set %02d\n", i, ptr, color)
	}

	fmt.Printf("\nColor collision analysis:\n")
	hasCollisions := false
	for color, count := range colorDistribution {
		if count > 1 {
			hasCollisions = true
			fmt.Printf("  Warning: Set %02d shared by %d buffers (Risk of associativity conflict!)\n", color, count)
		}
	}
	if !hasCollisions {
		fmt.Println("  Optimal! All buffers mapped to distinct cache sets (Zero conflict misses).")
	}
}
```

## Под капотом

В операционных системах реального времени (RTOS) и гипервизорах существует механизм **Page Coloring**. Ядро ОС при аллокации физических страниц следит за битами `Color = (phys_page >> 12) & (sets - 1)` и гарантирует, что страницы разных виртуальных машин не конкурируют за одни и те же наборы кэша L2/L3, полностью исключая атаки по сторонним каналам (Cache Timing Side-Channel Attacks).

## Подводные камни

1. Преждевременный расчет цветов на виртуальных адресах: кэш L1 обычно использует VIPT (Virtually Indexed, Physically Tagged), где индекс сета совпадает в виртуальном и физическом адресе, но кэш L3 использует PIPT (Physically Indexed), где цвета определяются физической страницей памяти ядра.
2. Ручной расчет смещений без учета фрагментации памяти.

## На собеседовании

«Что такое VIPT (Virtually Indexed, Physically Tagged) кэш и почему размер страницы 4 КБ ограничивает размер L1 кэша?»
Ответ: В кэше VIPT индекс набора вычисляется параллельно с трансляцией TLB по младшим битам виртуального адреса. Чтобы виртуальный индекс сета гарантированно совпадал с физическим (во избежание кэш-синонимов — Aliasing), биты индекса сета не могут выходить за пределы размера страницы (12 бит = 4 КБ). При 64-байтовой строке это дает максимум \(4096 / 64 = 64\) сета. При 8-канальной ассоциативности размер кэша жестко ограничен: \(64 \times 8 \times 64 = 32\text{ КБ}\).
