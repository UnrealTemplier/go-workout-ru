# Инкапсулированные конструкторы: приватная структура member и строгая валидация NewMember

## Условие

**Инкапсулированные конструкторы**: В пакете `user` создайте приватную структуру `member`. Напишите экспортируемую функцию-конструктор `NewMember(email string) (*member, error)`, которая проверяет email на наличие символа `@`. Если валидация не пройдена, возвращайте ошибку. Попробуйте создать экземпляр `member` в обход конструктора из пакета `main`.

## Теория

Приватная структура гарантирует создание объектов исключительно через валидирующий конструктор.

## Решение по шагам

1. Моделируем приватную структуру member.
2. Реализуем NewMember с проверкой strings.Contains(email, "@").
3. Проверяем валидные и невалидные случаи.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

type member struct {
	email string
}

func NewMember(email string) (*member, error) {
	if !strings.Contains(email, "@") {
		return nil, errors.New("некорректный email: отсутствует символ @")
	}
	return &member{email: email}, nil
}

func (m *member) Email() string { return m.email }

func main() {
	m, err := NewMember("senior@avito.ru")
	if err != nil { panic(err) }
	fmt.Println("Успешно создан участник:", m.Email())

	_, errInvalid := NewMember("bad_email")
	if errInvalid != nil {
		fmt.Println("❌ Валидация отклонила:", errInvalid)
	}
}
```

**`Терминал`**

```bash
go run main.go
# Успешно создан участник: senior@avito.ru
# ❌ Валидация отклонила: некорректный email: отсутствует символ @
```

## Под капотом

Неэкспортируемый тип member невозможно инстанцировать из другого пакета через литерал member{}.

## Подводные камни

- Экспорт структуры member с маленькой буквы, но публичными полями.

## На собеседовании

**Вопрос с собеседования:** «Зачем делать саму структуру неэкспортируемой?»
**Ответ:** Чтобы принудительно заставить пользователей создавать объекты только через фабричную функцию New, соблюдая 100% инварианты.
