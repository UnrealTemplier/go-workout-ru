# Ловушка типизированного nil: почему возврат (*MyError)(nil) в error ломает проверку err != nil

## Условие

Опасность типизированного nil в error: функция возвращает *MyError как error. Создай функцию, которая возвращает nil указатель *MyError, но тип возврата — error. Покажи, что if err != nil срабатывает (потому что интерфейс содержит тип, но nil значение). Исправь баг.

### Исходная формулировка

Реализуй **Factory Method**: интерфейс `PaymentProcessor` с методом `Pay(amount float64) error`. Реализации: `CreditCardProcessor`, `PayPalProcessor`. Функция `NewProcessor(ptype string) (PaymentProcessor, error)` возвращает нужную реализацию по строке.

## Теория

Интерфейс в Go равен nil ТОЛЬКО если и type == nil, и data == nil. Типизированный nil (*MyError)(nil) имеет type != nil, поэтому if err != nil вернет TRUE!

## Решение по шагам

1. Создаем MyError{ Msg string }.
2. Пишем ошибочную функцию GetErrorBad() error, возвращающую *MyError(nil).
3. Пишем исправленную функцию GetErrorGood() error, возвращающую явный nil.
4. Сравниваем результаты.

## Код решения

**`main.go`**

```go
package main

import "fmt"

type MyError struct{ Msg string }
func (m *MyError) Error() string { return m.Msg }

// ❌ ОШИБКА: типизированный nil попадает в интерфейс
func GetErrorBad() error {
	var err *MyError = nil
	return err // eface{type: *MyError, data: 0x0} != nil !
}

// ✅ ИСПРАВЛЕНИЕ: возврат явного nil
func GetErrorGood() error {
	var err *MyError = nil
	if err != nil {
		return err
	}
	return nil // eface{type: 0x0, data: 0x0} == nil
}

func main() {
	if err := GetErrorBad(); err != nil {
		fmt.Println("🚨 БАГ: err != nil сработал для nil указателя!")
	}

	if err := GetErrorGood(); err == nil {
		fmt.Println("✅ ИСПРАВЛЕНО: err == nil сработал корректно")
	}
}
```

**`Терминал`**

```bash
go run main.go
# 🚨 БАГ: err != nil сработал для nil указателя!
# ✅ ИСПРАВЛЕНО: err == nil сработал корректно
```

## Под капотом

Интерфейс (iface/eface) состоит из двух указателей: itab (тип) и data (значение). Если itab != 0, интерфейс НЕ равен nil.

## Подводные камни

- Возврат переменной кастомного типа ошибки вместо явного return nil.

## На собеседовании

**Вопрос с собеседования:** «Топ-1 вопрос на собеседованиях по Go: почему `var p *int = nil; var i any = p; i == nil` возвращает `false`?»
**Ответ:** Потому что интерфейс `any` хранит тип `*int` и значение `nil`. Интерфейс равен `nil` только тогда, когда и тип, и значение равны `nil`.
