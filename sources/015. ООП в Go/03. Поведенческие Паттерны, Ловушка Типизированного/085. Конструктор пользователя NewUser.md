# Конструктор пользователя NewUser: строгая валидация email и минимальной длины пароля

## Условие

Конструктор с валидацией: NewUser(email, password string) (*User, error). Валидация: email содержит '@' и '.', пароль не менее 8 символов. При ошибке возвращается nil и понятная ошибка.

### Исходная формулировка

Создайте интерфейс `Shape` с методами `Area() float64` и `Perimeter() float64`. Убедитесь, что `Rectangle` и новая структура `Circle` неявно реализуют этот интерфейс.

## Теория

Гарантия создания только валидных доменных сущностей.

## Решение по шагам

1. Создаем User{email, pass}.
2. Реализуем NewUser с проверками.
3. Проверяем граничные условия.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

type UserEntity struct {
	email    string
	password string
}

func NewUser(email, pass string) (*UserEntity, error) {
	if !strings.Contains(email, "@") || !strings.Contains(email, ".") {
		return nil, errors.New("некорректный формат email")
	}
	if len(pass) < 8 {
		return nil, errors.New("пароль должен содержать не менее 8 символов")
	}
	return &UserEntity{email: email, password: pass}, nil
}

func main() {
	u, err := NewUser("teamlead@ozon.ru", "secretPass2026")
	if err != nil { panic(err) }
	fmt.Println("Успешно создан:", u.email)
}
```

**`Терминал`**

```bash
go run main.go
# Успешно создан: teamlead@ozon.ru
```

## Под капотом

При ошибке аллокация структуры User не происходит.

## Подводные камни

- Пропуск проверки на пустые строки.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go не используют исключения (exceptions) при валидации конструкторов?»
**Ответ:** В Go ошибки являются обычными значениями (Errors as Values), что делает поток управления предсказуемым и явным.
