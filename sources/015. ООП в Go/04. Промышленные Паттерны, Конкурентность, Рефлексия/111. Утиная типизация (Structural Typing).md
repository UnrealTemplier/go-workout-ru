# Утиная типизация (Structural Typing): совпадение методов в независимых интерфейсах Reader и Scanner

## Условие

Интерфейсы с одинаковыми методами: два интерфейса Reader (Read() string) и Scanner (Read() string). Тип Document реализует метод Read() string. Покажи, что Document удовлетворяет обоим интерфейсам автоматически (structural typing).

### Исходная формулировка

Создай `var p *Point = nil; var i fmt.Stringer = p`. Проверь `i == nil` (**false**!). Объясни внутреннее устройство интерфейса: интерфейс не nil, потому что **type descriptor** присутствует (`*Point`), а value — nil.

## Теория

В Go реализация интерфейсов неявная (Duck Typing / Structural Subtyping) — явного implements не требуется.

## Решение по шагам

1. Объявляем интерфейсы StringReader и StringScanner с методом Read() string.
2. Реализуем Document{ Content string }.
3. Присваиваем Document обоим интерфейсам.

## Код решения

**`main.go`**

```go
package main

import "fmt"

type StringReader interface { Read() string }
type StringScanner interface { Read() string }

type Document struct{ Content string }
func (d Document) Read() string { return d.Content }

func main() {
	doc := Document{Content: "Конфиденциальный документ"}

	// Один тип автоматически реализует оба независимых интерфейса:
	var r StringReader = doc
	var s StringScanner = doc

	fmt.Println("Reader :", r.Read())
	fmt.Println("Scanner:", s.Read())
}
```

**`Терминал`**

```bash
go run main.go
# Reader : Конфиденциальный документ
# Scanner: Конфиденциальный документ
```

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество structural typing над номинативной типизацией Java/C++?»
**Ответ:** Позволяет объявлять интерфейсы на стороне потребителя (consumer-driven interfaces) и подключать сторонние библиотеки без внесения правок в их код.
