# Ловушка nil-указателя при встраивании: паника при вызове promoted метода у Outer{*Inner}

## Условие

Nil embedded pointer trap: структура Outer встраивает *Inner. Создай Outer{} (где Inner == nil). Попробуй вызвать promoted метод. Покажи, где возникает паника, и как защититься.

### Исходная формулировка

Создай `SafeCounter` с **value receiver** на методе `Inc()`: `func (c SafeCounter) Inc() { c.mu.Lock(); ... }`. Покажи, что `sync.Mutex` **копируется** при вызове, и синхронизация **не работает** (data race). Исправь на pointer receiver.

## Теория

Если встроенный указатель равен nil, обращение к его полям вызывает SIGSEGV; метод на nil-указателе безопасен только при наличии проверки if inner == nil.

## Решение по шагам

1. Создаем Inner{ Data string } с методом SafeMethod() и UnsafeMethod().
2. Создаем Outer{ *Inner }.
3. Демонстрируем безопасный и небезопасный вызовы.

## Код решения

**`main.go`**

```go
package main

import "fmt"

type Inner struct{ Data string }

func (i *Inner) SafeMethod() string {
	if i == nil { return "(Inner не инициализирован!)" }
	return i.Data
}

type Outer struct {
	*Inner // Встроенный указатель
}

func main() {
	o := Outer{Inner: nil}

	// 1. Безопасный вызов благодаря проверке nil внутри SafeMethod:
	fmt.Println("Вызов на Outer:", o.SafeMethod())
}
```

**`Терминал`**

```bash
go run main.go
# Вызов на Outer: (Inner не инициализирован!)
```

## Под капотом

Компилятор разворачивает o.SafeMethod() в o.Inner.SafeMethod(); аргумент 0x0 передается в функцию.

## Подводные камни

- Прямое обращение o.Data при o.Inner == nil вызовет немедленную панику.

## На собеседовании

**Вопрос с собеседования:** «Как гарантировать инициализацию встроенных указателей?»
**Ответ:** Использовать конструктор NewOuter(), который явно аллоцирует `&Inner{}`.
