# Паттерн Unit of Work: управление распределенными транзакциями и регистрация изменений

## Условие

Паттерн Unit of Work: интерфейс UnitOfWork с методами Begin(), Commit() error, Rollback() error, RegisterNew(entity any), RegisterDirty(entity any), RegisterDeleted(entity any).

### Исходная формулировка

**Интерфейс `error` как объект ООП**: Создайте кастомный тип `type SystemError string`, реализующий интерфейс `error`. Напишите для него метод-получатель, который возвращает строку ошибки в верхнем регистре. Используйте `Type Assertion`, чтобы проверить, является ли возвращенная из функции ошибка именно вашей ошибкой `SystemError`.

## Теория

Unit of Work аккумулирует все изменения бизнес-транзакции и атомарно применяет их в БД.

## Решение по шагам

1. Объявляем интерфейс UnitOfWork.
2. Создаем структуру SQLUnitOfWork с очередями new, dirty, deleted.
3. Реализуем Commit и Rollback.

## Код решения

**`main.go`**

```go
package main

import "fmt"

type UnitOfWork interface {
	RegisterNew(entity any)
	Commit() error
	Rollback()
}

type MockUoW struct {
	newEntities []any
}

func (u *MockUoW) RegisterNew(e any) { u.newEntities = append(u.newEntities, e) }
func (u *MockUoW) Commit() error {
	fmt.Printf("💾 Атомарная запись %d новых сущностей в БД\n", len(u.newEntities))
	u.newEntities = nil
	return nil
}
func (u *MockUoW) Rollback() { u.newEntities = nil }

func main() {
	uow := &MockUoW{}
	uow.RegisterNew("User: Alice")
	uow.RegisterNew("Order: #1001")
	_ = uow.Commit()
}
```

**`Терминал`**

```bash
go run main.go
# 💾 Атомарная запись 2 новых сущностей в БД
```

## Под капотом

Группировка SQL-операций внутри одной транзакции BEGIN ... COMMIT.

## Подводные камни

- Незавершенная транзакция без defer Rollback().

## На собеседовании

**Вопрос с собеседования:** «Зачем нужен Unit of Work в микросервисах?»
**Ответ:** Для предотвращения частичной записи данных при сбоях и минимизации количества сетевых обращений к базе данных.
