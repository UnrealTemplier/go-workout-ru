# Принцип разделения интерфейсов (ISP): декомпозиция GodInterface на маленькие контракты

## Условие

Interface Segregation Principle (ISP): покажи интерфейс-монолит GodInterface с 10 методами. Разбей его на маленькие интерфейсы Reader, Writer, Closer, Seeker. Создай составной интерфейс ReadWriteCloser через встраивание.

### Исходная формулировка

Создай структуру `Container` с встроенным `*Item` (nil). Вызови promoted метод `Item.Method()` — получи панику. Затем добавь в `Item.Method()` проверку на nil receiver — покажи, что паники нет, если метод безопасен. Объясни разницу между nil pointer в интерфейсе и nil embedded pointer.

## Теория

Клиенты не должны зависеть от методов, которые они не используют (ISP).

## Решение по шагам

1. Показываем антипаттерн GodInterface.
2. Декомпозируем на Reader, Writer, Closer.
3. Собираем ReadWriteCloser через композицию.

## Код решения

**`main.go`**

```go
package main

import "fmt"

// Маленькие, сфокусированные интерфейсы:
type Reader interface{ Read() string }
type Writer interface{ Write(data string) }
type Closer interface{ Close() error }

// Композиция интерфейсов:
type ReadWriteCloser interface {
	Reader
	Writer
	Closer
}

type SimpleStream struct{ data string }
func (s *SimpleStream) Read() string       { return s.data }
func (s *SimpleStream) Write(d string)     { s.data = d }
func (s *SimpleStream) Close() error       { return nil }

func main() {
	var rwc ReadWriteCloser = &SimpleStream{}
	rwc.Write("Потоковые данные")
	fmt.Println("Прочитано:", rwc.Read())
}
```

**`Терминал`**

```bash
go run main.go
# Прочитано: Потоковые данные
```

## Под капотом

Каждый интерфейс содержит только минимально необходимый набор сигнатур.

## На собеседовании

**Вопрос с собеседования:** «Какое золотое правило Роб Пайк сформулировал относительно размера интерфейсов в Go?»
**Ответ:** «The bigger the interface, the weaker the abstraction» (Чем больше интерфейс, тем слабее абстракция). Самые мощные интерфейсы Go содержат 1–2 метода (`io.Reader`, `fmt.Stringer`, `error`).
