# Финальный архитектурный проект: Чистая Архитектура (Clean Architecture) сервиса заказов

## Условие

Финальный архитектурный проект: архитектура чистого сервиса (Clean Architecture). Слой Domain (сущности, интерфейсы репозиториев), слой UseCase (бизнес-логика через DI), слой Infrastructure (InMemory репозиторий), слой Delivery (HTTP хендлер / CLI). Все 4 слоя связаны через интерфейсы и композицию.

### Исходная формулировка

**Делегирование через интерфейсы**: Структура `App` встраивает анонимно интерфейс `Logger`. При инициализации `App` передай туда конкретную реализацию логгера. Попробуй вызвать методы интерфейса напрямую от объекта приложения: `app.Info("start")`.

## Теория

Священный Грааль микросервисной разработки: инверсия зависимостей (DIP), слабая связанность и 100% тестируемость всех 4 слоев Clean Architecture.

## Решение по шагам

1. Слой Domain: сущность Order и интерфейс OrderRepository.
2. Слой UseCase: сервис OrderUseCase с внедрением OrderRepository.
3. Слой Infrastructure: реализация InMemoryOrderRepository.
4. Слой Delivery: CLI/HTTP адаптер, вызывающий UseCase.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

// 1. DOMAIN LAYER
type Order struct {
	ID     int
	Amount float64
	Status string
}

type OrderRepository interface {
	Save(o *Order) error
	FindByID(id int) (*Order, error)
}

// 2. USECASE LAYER
type OrderUseCase struct {
	repo OrderRepository
}

func NewOrderUseCase(r OrderRepository) *OrderUseCase {
	return &OrderUseCase{repo: r}
}

func (uc *OrderUseCase) CreateOrder(id int, amt float64) error {
	if amt <= 0 { return errors.New("сумма заказа должна быть больше 0") }
	order := &Order{ID: id, Amount: amt, Status: "CREATED"}
	return uc.repo.Save(order)
}

// 3. INFRASTRUCTURE LAYER
type InMemoryOrderRepo struct {
	mu     sync.RWMutex
	orders map[int]*Order
}

func NewInMemoryOrderRepo() *InMemoryOrderRepo {
	return &InMemoryOrderRepo{orders: make(map[int]*Order)}
}

func (r *InMemoryOrderRepo) Save(o *Order) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.orders[o.ID] = o
	return nil
}

func (r *InMemoryOrderRepo) FindByID(id int) (*Order, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	o, ok := r.orders[id]
	if !ok { return nil, errors.New("заказ не найден") }
	return o, nil
}

// 4. DELIVERY LAYER (Main)
func main() {
	// Сборка графа зависимостей (Dependency Injection):
	repo := NewInMemoryOrderRepo()
	useCase := NewOrderUseCase(repo)

	// Исполнение бизнес-сценария:
	if err := useCase.CreateOrder(7001, 15990.0); err != nil {
		panic(err)
	}

	order, _ := repo.FindByID(7001)
	fmt.Printf("🎯 [Clean Architecture] Заказ #%d успешно оформлен на сумму %.2f руб. (Статус: %s)\n", 
		order.ID, order.Amount, order.Status)
}
```

**`Терминал`**

```bash
go run main.go
# 🎯 [Clean Architecture] Заказ #7001 успешно оформлен на сумму 15990.00 руб. (Статус: CREATED)
```

## Под капотом

Поток управления направлен от Delivery к Domain, а зависимости направлены внутрь к Domain (Dependency Inversion Principle).

## Подводные камни

- Импорт слоев Delivery или Infrastructure внутрь Domain (Domain должен быть абсолютно чистым).

## На собеседовании

**Вопрос с собеседования:** «В чем ключевое отличие Clean Architecture от стандартной 3-уровневой архитектуры (Controller-Service-DAO)?»
**Ответ:** В Clean Architecture слой бизнес-логики (Domain/UseCase) не зависит от базы данных и фреймворков. База данных и HTTP-роутеры являются лишь внешними плагинами (деталями реализации), подключаемыми через интерфейсы.
