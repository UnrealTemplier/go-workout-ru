# Событийное порождение (Event Sourcing): сохранение потока событий и восстановление состояния через Fold/Replay

## Условие

Реализуй **Event Sourcing**: `OrderAggregate` хранит не текущее состояние, а последовательность `OrderCreated`, `OrderItemAdded`, `OrderPaymentApplied`, `OrderShipped`. `GetState()` = `fold(events, initialState)`. Покажи: replay, temporal queries, audit trail.

## Теория

Архитектурный шаблон Event Sourcing (Грег Янг):
- В классической БД хранится только **текущее состояние строки** (`status = 'SHIPPED'`), а вся история изменений перезаписывается через `UPDATE`.
- **В Event Sourcing:**
  1. Таблица агрегата — это **Append-Only лог событий**.
  2. Никаких `UPDATE` и `DELETE`!
  3. Текущее состояние агрегата вычисляется функцией левой свертки (Fold / Reduce):
     $$\text{State}_N = \text{Fold}(\text{Events}_{1..N}, \text{InitialState})$$
- **Преимущества:**
  - 100% идеальный аудит-лог (Audit Trail) для финтеха и регуляторов.
  - Временные срезы (Time Travel / Temporal Queries): возможность узнать точное состояние счета на 15 марта прошлого года в 14:22:01.
  - Легкость отладки: возможность воспроизвести сбой шаг за шагом.

## Решение по шагам

1. Создайте типы событий жизненного цикла заказа.
2. Реализуйте функцию свертки `ApplyEvent` для мутации промежуточного состояния.
3. Восстановите агрегат из исторического потока событий (Event Replay).
4. Верифицируйте итоговый баланс и статус заказа.

## Код решения

**`event_sourcing_fold_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Состояние агрегата
type OrderEventSourcedState struct {
	ID        string
	Status    string
	ItemCount int
	TotalPaid float64
}

// Поток исторических событий
type Event interface{}

type EvtOrderCreated struct{ ID string }
type EvtItemAdded struct{ Qty int }
type EvtPaymentApplied struct{ Amount float64 }
type EvtOrderShipped struct{}

// Функция свертки (Fold / Mutator)
func ApplyEvent(state OrderEventSourcedState, event Event) OrderEventSourcedState {
	switch e := event.(type) {
	case EvtOrderCreated:
		state.ID = e.ID
		state.Status = "CREATED"
	case EvtItemAdded:
		state.ItemCount += e.Qty
	case EvtPaymentApplied:
		state.TotalPaid += e.Amount
		state.Status = "PAID"
	case EvtOrderShipped:
		state.Status = "SHIPPED"
	}
	return state
}

func TestEventSourcingFold(t *testing.T) {
	// Журнал событий в БД (Event Store)
	history := []Event{
		EvtOrderCreated{ID: "es-order-777"},
		EvtItemAdded{Qty: 2},
		EvtItemAdded{Qty: 1},
		EvtPaymentApplied{Amount: 15400.0},
		EvtOrderShipped{},
	}

	// Восстановление состояния через Replay (Fold)
	var current OrderEventSourcedState
	for _, evt := range history {
		current = ApplyEvent(current, evt)
	}

	if current.ID != "es-order-777" || current.ItemCount != 3 || current.Status != "SHIPPED" {
		t.Fatalf("Сбой свертки Event Sourcing: %+v", current)
	}

	fmt.Println("Event Sourcing (Событийное порождение) успешно подтверждено:")
	fmt.Printf("  • История событий: %d записей воспроизведено (Replay)\n", len(history))
	fmt.Printf("  • Восстановленный агрегат: ID=%s, Позиций=%d, Оплачено=%.2f, Статус=%s\n",
		current.ID, current.ItemCount, current.TotalPaid, current.Status)
	fmt.Println("  • Возможность Temporal Query: отсекая события после шага 3, получаем состояние до отправки!")
}
```

## Под капотом

Если агрегат содержит 100 000 событий (например банковский счет за 10 лет), Replay с нуля становится слишком долгим. Для оптимизации используют **Снимки состояния (Snapshots)**: каждые 100 событий агрегат сохраняет снапшот в хранилище, и при загрузке считывается последний снапшот плюс дельта новых событий.

## Подводные камни

Вносить обратно несовместимые изменения в структуру событий (Event Schema Evolution): старые события из 2024 года должны десериализоваться так же успешно, как и новые. Для этого применяют версионирование схем (Upcasting).

## На собеседовании

**Вопрос с собеседования:** «Почему базы данных событий (Event Store) гарантируют отсутствие конфликтов при параллельной записи (Optimistic Concurrency Control)?»
**Ответ:** Каждое событие пишется с номером версии агрегата (`expected_version = N`). Если две параллельные горутины пытаются записать событие с одинаковым номером версии `N+1`, СУБД отвергает второй запрос по `UNIQUE(aggregate_id, version)`, предотвращая перезапись состояния.
