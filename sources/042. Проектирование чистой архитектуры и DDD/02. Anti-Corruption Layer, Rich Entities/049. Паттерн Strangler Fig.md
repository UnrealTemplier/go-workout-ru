# Паттерн Strangler Fig: поэтапная миграция с legacy монолита на Go через маршрутизацию API Gateway

## Условие

Спроектируй **Strangler Fig Pattern**: legacy монолит на Java. Новый сервис `UserService` на Go. API Gateway маршрутизирует: `/users/*` → новый сервис, остальное → legacy. Постепенно вырезаем функциональность. Покажи incremental migration.

## Теория

Паттерн «Фиговое дерево-душитель» (Strangler Fig, Мартин Фаулер):
- Попытка переписать огромный 10-летний монолит «с нуля заново» (Big Bang Rewrite) в 95% случаев заканчивается провалом и увольнением команды.
- **Strangler Fig — безопасный инкрементальный путь:**
  1. Перед старым монолитом ставится умный прокси (API Gateway / Envoy / NGINX).
  2. Новая фича пишется в виде микросервиса на Go.
  3. API Gateway перенаправляет маршрут `/api/v1/users` на Go-сервис.
  4. Все остальные 99% запросов прозрачно уходят в старый Java-монолит.
  5. Шаг за шагом маршруты мигрируют на Go, пока от монолита не останется ничего!

## Решение по шагам

1. Создайте эмулятор маршрутизатора API Gateway.
2. Настройте правила маршрутизации (`/users` \(\to\) Go-сервис, `/orders` \(\to\) Java монолит).
3. Протестируйте выполнение обоих маршрутов.
4. Верифицируйте корректность инкрементальной миграции.

## Код решения

**`strangler_fig_migration_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type UpstreamTarget string

const (
	TargetLegacyJavaMonolith UpstreamTarget = "LEGACY_JAVA_MONOLITH"
	TargetNewGoMicroservice  UpstreamTarget = "NEW_GO_MICROSERVICE"
)

type StranglerAPIGateway struct {
	routes map[string]UpstreamTarget
}

func (g *StranglerAPIGateway) RouteRequest(path string) UpstreamTarget {
	for prefix, target := range g.routes {
		if strings.HasPrefix(path, prefix) {
			return target
		}
	}
	return TargetLegacyJavaMonolith // По умолчанию всё идет в старый монолит
}

func TestStranglerFigMigration(t *testing.T) {
	gateway := &StranglerAPIGateway{
		routes: map[string]UpstreamTarget{
			"/api/v1/users": TargetNewGoMicroservice, // Успешно вырезанная фича на Go!
		},
	}

	target1 := gateway.RouteRequest("/api/v1/users/profile")
	target2 := gateway.RouteRequest("/api/v1/checkout/orders")

	if target1 != TargetNewGoMicroservice {
		t.Fatalf("Маршрут /users должен идти в Go: %s", target1)
	}
	if target2 != TargetLegacyJavaMonolith {
		t.Fatalf("Остальной трафик обязан идти в Java монолит: %s", target2)
	}

	fmt.Println("Паттерн Strangler Fig (Душитель) успешно подтвержден:")
	fmt.Printf("  • Путь /api/v1/users/profile -> %s (Новый сервис на Go)\n", target1)
	fmt.Printf("  • Путь /api/v1/checkout/orders -> %s (Старый монолит)\n", target2)
	fmt.Println("  • Постепенное удушение старого монолита без единой секунды даунтайма!")
}
```

ℹ️ Маршрутизация трафика между legacy монолитом и новыми микросервисами на Go

## Под капотом

На уровне сетевой инфраструктуры Strangler Fig настраивается через Envoy VirtualHost и weighted cluster routing: сначала на Go отправляют 1% трафика (Canary), валидируют частоту ошибок и задержки, а затем плавно доводят до 100%.

## Подводные камни

Забывать про общие данные: если новый Go сервис и старый монолит одновременно пишут в одну таблицу пользователей, возникнут race conditions. Применяют двухстороннюю репликацию CDC (Kafka + Debezium) или делают монолит read-only по вырезанному домену.

## На собеседовании

**Вопрос с собеседования:** «Что делать с фоновыми Cron задачами старого монолита при использовании Strangler Fig?»
**Ответ:** Cron-задачи мигрируют в самую последнюю очередь. Пока домен мигрирует, старый Cron перенаправляется на вызов нового Go-сервиса через внутренний gRPC/HTTP вызов, гарантируя, что бизнес-логика выполняется строго в одном месте.
