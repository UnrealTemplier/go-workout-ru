# Порты внешних зависимостей (Hexagonal Ports): UserRepository, EmailSender и заменяемые адаптеры

## Условие

**Hexagonal Architecture (Ports & Adapters)**: Определите "порты" (интерфейсы) для внешних зависимостей (UserRepository, EmailSender) и реализуйте "адаптеры" (PostgresUserRepository, SendGridEmailSender).

## Теория

Принцип множественных адаптеров одного порта:
- Порт определяет **намерение бизнеса**, а не способ реализации:
  - Порт `EmailSender` говорит: «Я хочу отправить приветственное письмо».
  - Ему все равно, как оно будет отправлено: через SendGrid, SMTP сервер или просто напечатано в консоли в дев-режиме.
- **Преимущество архитектуры:**
  - Сегодня компания использует SendGrid.
  - Завтра SendGrid блокирует учетную запись или поднимает цены в 10 раз.
  - Инженер пишет `VKCloudEmailSender` за 2 часа, подключает его в `main.go`, и бизнес продолжает работать без единой правки доменного кода!

## Решение по шагам

1. Опишите порт `EmailSenderPort`.
2. Реализуйте адаптер `SendGridEmailSender`.
3. Реализуйте альтернативный адаптер `LocalMockEmailSender`.
4. Продемонстрируйте мгновенную подменяемость провайдера.

## Код решения

**`hexagonal_pluggable_adapters_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Порт ядра
type EmailSenderPort interface {
	SendEmail(ctx context.Context, recipient, subject, body string) error
}

// Адаптер 1: SendGrid
type SendGridEmailSender struct {
	apiKey string
}

func (s *SendGridEmailSender) SendEmail(ctx context.Context, recipient, subject, body string) error {
	// Имитация HTTPS запроса к SendGrid API
	return nil
}

// Адаптер 2: Локальный эмулятор для тестов
type LocalMockEmailSender struct {
	MessagesCount int
}

func (m *LocalMockEmailSender) SendEmail(ctx context.Context, recipient, subject, body string) error {
	m.MessagesCount++
	return nil
}

// Доменный сервис
type UserWelcomeService struct {
	mailer EmailSenderPort
}

func NewUserWelcomeService(m EmailSenderPort) *UserWelcomeService {
	return &UserWelcomeService{mailer: m}
}

func (s *UserWelcomeService) Welcome(ctx context.Context, email string) error {
	return s.mailer.SendEmail(ctx, email, "Добро пожаловать!", "Спасибо за регистрацию")
}

func TestHexagonalPluggableAdapters(t *testing.T) {
	mockMailer := &LocalMockEmailSender{}
	svc := NewUserWelcomeService(mockMailer)

	if err := svc.Welcome(context.Background(), "new_user@ozon.ru"); err != nil {
		t.Fatalf("Ошибка отправки приветствия: %v", err)
	}

	if mockMailer.MessagesCount != 1 {
		t.Fatalf("Письмо не было отправлено через mock адаптер")
	}

	fmt.Println("Заменяемые адаптеры гексагональной архитектуры подтверждены:")
	fmt.Println("  • Порт: EmailSenderPort")
	fmt.Println("  • Адаптеры SendGrid и LocalMock взаимозаменяемы без изменения домена!")
}
```

## Под капотом

В Go динамическая диспетчеризация интерфейса занимает около 2–3 наносекунд. Это означает, что введение интерфейсного порта для абстрагирования базы данных или сетевого сервиса вносит абсолютно пренебрежимый оверхед по сравнению со временем реального сетевого запроса (10–50 мс).

## Подводные камни

Включать в сигнатуры методов порта параметры, специфичные для конкретного адаптера (например `SendEmail(ctx, to, templateID string, sendGridOptions Options)`): это разрушает абстракцию, привязывая порт к одному поставщику.

## На собеседовании

**Вопрос с собеседования:** «Какое практическое правило помогает понять, что перед нами Порт, а что Адаптер?»
**Ответ:** Порт — это **интерфейс** внутри доменного пакета, задающий вопрос «Что нужно бизнесу?». Адаптер — это **структура с методами** во внешнем инфраструктурном пакете, отвечающая на вопрос «Как именно это реализовано с помощью конкретной технологии?». Порт принадлежит ядру, адаптер — инфраструктуре.
