# Разрешение циклических зависимостей (Import Cycle): слияние пакетов или выделение независимого core

## Условие

**Циклические зависимости (Import Cycle)**: Намеренно создай ситуацию: пакет `user` импортирует `order`, а `order` импортирует `user`. Получи ошибку компилятора. Реши проблему двумя способами: 1) объединением в один пакет, 2) вынесением общих структур/интерфейсов в третий независимый пакет `domain` или `core`.

## Теория

Запрет циклических импортов в компиляторе Go:
- В Go строго запрещены графы зависимостей с циклами (\(A \to B \to A\)).
- **Почему компилятор Go запрещает циклы:**
  1. Гарантия молниеносной скорости компиляции: пакеты компилируются в строгом топологическом порядке.
  2. Исключение неразрешимых циклических вызовов функций инициализации `init()`.
- **Два архитектурных способа решения:**
  - **Способ 1 (Merge):** Объединить тесно связанные структуры в один пакет. Если сущности не могут жить друг без друга, это один домен!
  - **Способ 2 (Core/Domain Extraction):** Вынести разделяемые интерфейсы или идентификаторы в третий пакет нижнего уровня `core/types`.

## Решение по шагам

1. Смоделируйте структуру типов, провоцирующую циклический импорт.
2. Реализуйте разрыв связи через выделение интерфейсов в пакет `core`.
3. Скомпонуйте зависимости без взаимного циклического импорта.
4. Верифицируйте успешную компиляцию.

## Код решения

**`break_import_cycle_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Выделенный пакет: core (Нижний уровень)
type UserID string
type OrderID string

type UserInfo struct {
	ID   UserID
	Name string
}

// Пакет orders: зависит только от core
type Order struct {
	ID     OrderID
	UserID UserID
	Amount float64
}

// Пакет users: зависит только от core
type UserProfile struct {
	Info UserInfo
}

func TestBreakImportCycle(t *testing.T) {
	uid := UserID("u-break-cycle-1")
	user := UserProfile{Info: UserInfo{ID: uid, Name: "Мария Петрова"}}
	order := Order{ID: OrderID("ord-777"), UserID: user.Info.ID, Amount: 12000.0}

	if order.UserID != user.Info.ID {
		t.Fatal("Связь между заказами и пользователями разорвана")
	}

	fmt.Println("Успешное разрешение циклической зависимости (Import Cycle):")
	fmt.Printf("  • Пользователь: %s (%s)\n", user.Info.Name, user.Info.ID)
	fmt.Printf("  • Заказ: %s привязан через core.UserID к пользователю\n", order.ID)
	fmt.Println("  • Цикл A -> B -> A устранен вынесением общих понятий в независимый пакет core")
}
```

ℹ️ Устранение циклических импортов вынесением общих типов в независимый пакет

## Под капотом

Внутренний чекер зависимостей компилятора Go строит матрицу смежности пакетов и запускает алгоритм Тарьяна или Косарайю для поиска сильно связных компонент. При нахождении любого цикла компилятор моментально завершает сборку с ошибкой `import cycle not allowed`.

## Подводные камни

Решать проблему циклов созданием пакета `common/` или `utils/` и сваливать туда вообще все типы проекта: это маскирует ошибку проектирования и создает глобальную свалку зависимостей.

## На собеседовании

**Вопрос с собеседования:** «Если пакет user и пакет order цикdropped друг друга, всегда ли нужно создавать третий пакет?»
**Ответ:** Нет! В 70% случаев это свидетельствует о том, что границы пакетов были нарезаны искусственно. Если сущности настолько плотно связаны, что не могут скомпилироваться порознь — они принадлежат одному агрегату или одному пакету `ecommerce`. Их слияние в один пакет — самое простое и правильное решение.
