# Материализованные представления (Materialized Views): построение проекций из Event Stream с поддержкой Replay

## Условие

Реализуй **Materialized View из Event Stream**: `OrderProjection` читает `OrderEvents` Kafka topic, строит `OrderSummary` в Redis/PostgreSQL. Пересоздай projection с нуля (replay с начала stream). Покажи, что view — disposable, source of truth — events.

## Теория

Принцип одноразовых проекций (Disposable Materialized Views):
- В архитектуре Event Sourcing / Event-Driven источником абсолютной истины (Single Source of Truth) является **журнал событий (Event Log)**.
- Базы данных для чтения (PostgreSQL витрины, Redis кэши, Elasticsearch индексы) являются **материализованными проекциями**.
- **Ключевой инвариант:**
  - Любая проекция может быть удалена (`DROP TABLE order_summary`) в любой момент!
  - Запуск сервиса перечитывает топик Kafka с нулевого оффсета (`offset = 0`) и заново строит витрину с нуля (Replay).
  - Это позволяет менять схему отчетов и добавлять новые витрины задним числом за всю историю компании!

## Решение по шагам

1. Создайте поток событий изменений заказов.
2. Реализуйте проектор `OrderSummaryProjector`.
3. Смоделируйте сброс витрины и повторное воспроизведение (Replay) событий с начала стрима.
4. Верифицируйте идентичность восстановленной витрины.

## Код решения

**`materialized_view_replay_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type StreamEvent struct {
	OrderID   string
	EventType string
	Amount    float64
}

type OrderSummaryView struct {
	TotalOrders  int
	TotalRevenue float64
}

type OrderProjectionEngine struct {
	view OrderSummaryView
}

func (p *OrderProjectionEngine) Reset() {
	p.view = OrderSummaryView{}
}

func (p *OrderProjectionEngine) Apply(e StreamEvent) {
	switch e.EventType {
	case "OrderCreated":
		p.view.TotalOrders++
		p.view.TotalRevenue += e.Amount
	case "OrderCancelled":
		p.view.TotalOrders--
		p.view.TotalRevenue -= e.Amount
	}
}

func TestMaterializedViewReplay(t *testing.T) {
	// События в Kafka топике (источник истины)
	eventsStream := []StreamEvent{
		{OrderID: "1", EventType: "OrderCreated", Amount: 1000.0},
		{OrderID: "2", EventType: "OrderCreated", Amount: 2500.0},
		{OrderID: "1", EventType: "OrderCancelled", Amount: 1000.0},
		{OrderID: "3", EventType: "OrderCreated", Amount: 4000.0},
	}

	engine := &OrderProjectionEngine{}

	// 1. Первое построение витрины
	for _, e := range eventsStream {
		engine.Apply(e)
	}

	initialResult := engine.view

	// 2. Сброс проекции (DROP VIEW) и полный Replay с начала стрима
	engine.Reset()
	for _, e := range eventsStream {
		engine.Apply(e)
	}

	replayedResult := engine.view

	if initialResult != replayedResult || replayedResult.TotalOrders != 2 || replayedResult.TotalRevenue != 6500.0 {
		t.Fatalf("Сбой детерминированного Replay: %+v != %+v", initialResult, replayedResult)
	}

	fmt.Println("Материализованные представления (Materialized Views Replay) подтверждены:")
	fmt.Printf("  • Витрина успешно пересоздана с нуля: Активных заказов=%d, Выручка=%.2f руб\n",
		replayedResult.TotalOrders, replayedResult.TotalRevenue)
	fmt.Println("  • Источник истины — журнал событий; витрина полностью одноразовая (Disposable)")
}
```

## Под капотом

В Kafka Replay реализуется перестановкой оффсета группы консьюмеров через `kafka-consumer-groups.sh --reset-offsets --to-earliest`. Консьюмер начинает читать партиции с нулевого сообщения, заново наполняя базу Redis или PostgreSQL.

## Подводные камни

Использовать недетерминированные функции (например `time.Now()` или генератор случайных чисел) внутри функции проектора: при Replay витрина получит другие значения дат, нарушив консистентность. Проектор обязан использовать только дату из самого события (`e.OccurredAt`).

## На собеседовании

**Вопрос с собеседования:** «Как пересоздать тяжелую проекцию в продакшене без даунтайма (Zero-Downtime Projection Rebuild)?»
**Ответ:** Паттерн Blue-Green View:
1. Создается новая таблица `order_summary_v2`.
2. Новый консьюмер проигрывает весь стрим событий с начала в `v2`.
3. Когда консьюмер догоняет реальное время (Lag = 0), на уровне базы данных выполняется атомарная смена `VIEW` или переименование таблиц `ALTER TABLE ... RENAME`. Трафик мгновенно переключается на новую схему.
