# Корень агрегата (Aggregate Root): управление транзакционными границами сущностей Order и OrderItem

## Условие

**Агрегаты (Aggregates) и Aggregate Root**: Спроектируйте агрегат `Order` с позициями `OrderItem`. Покажите, что внешний мир может взаимодействовать со строками заказа **только** через корень агрегата (`Order`), а не напрямую.

### Исходная формулировка

**Background Jobs**: Реализуйте систему фоновых задач через Redis queue или PostgreSQL `SKIP LOCKED` (для простой job queue без внешних зависимостей).

## Теория

Концепция Агрегатов в DDD (Aggregate & Aggregate Root):
- **Агрегат** — это кластер связанных доменных объектов (Entities и Value Objects), которые рассматриваются как единое целое при любых изменениях данных.
- **Корень агрегата (Aggregate Root):**
  1. Единственная точка входа для внешнего мира.
  2. Внешние объекты не имеют права хранить постоянные ссылки на внутренние сущности (`OrderItem`).
  3. Добавление или удаление позиций выполняется **только** через методы корня: `order.AddItem(productID, qty, price)`.
  4. Корень агрегата гарантирует инварианты всего дерева (например: максимальная сумма заказа 1 млн руб, не более 50 позиций).
  5. **Правило транзакций:** Одна транзакция в БД должна изменять **ровно один агрегат**!

## Решение по шагам

1. Создайте внутреннюю сущность `OrderItem`.
2. Создайте корень агрегата `Order` с приватным срезом позиций.
3. Реализуйте метод `AddItem` с пересчетом общей суммы заказа.
4. Верифицируйте запрет прямого манипулирования строками заказа извне.

## Код решения

**`aggregate_root_order_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

// Внутренняя сущность агрегата
type OrderItem struct {
	sku      string
	quantity int
	price    float64
}

// Корень агрегата (Aggregate Root)
type OrderAggregate struct {
	id         string
	items      []OrderItem
	totalPrice float64
}

func NewOrderAggregate(id string) *OrderAggregate {
	return &OrderAggregate{id: id}
}

func (o *OrderAggregate) TotalPrice() float64 {
	return o.totalPrice
}

func (o *OrderAggregate) ItemsCount() int {
	return len(o.items)
}

// Изменение состояния ДОСТУПНО ТОЛЬКО ЧЕРЕЗ КОРЕНЬ
func (o *OrderAggregate) AddItem(sku string, qty int, price float64) error {
	if qty <= 0 {
		return errors.New("quantity must be greater than zero")
	}
	if price <= 0 {
		return errors.New("price must be positive")
	}
	// Инвариант агрегата: не более 5 позиций
	if len(o.items) >= 5 {
		return errors.New("order cannot contain more than 5 items")
	}

	o.items = append(o.items, OrderItem{sku: sku, quantity: qty, price: price})
	o.totalPrice += float64(qty) * price
	return nil
}

func TestAggregateRootOrder(t *testing.T) {
	order := NewOrderAggregate("ord-root-1")

	_ = order.AddItem("sku-mouse", 1, 1500.0)
	_ = order.AddItem("sku-keyboard", 1, 4500.0)

	if order.TotalPrice() != 6000.0 || order.ItemsCount() != 2 {
		t.Fatalf("Инвариант суммы агрегата нарушен: total=%v, count=%d", order.TotalPrice(), order.ItemsCount())
	}

	fmt.Println("Паттерн Aggregate Root (Корень агрегата) успешно подтвержден:")
	fmt.Printf("  • Заказ ID: %s, Позиций: %d, Итоговая сумма: %.2f руб\n", order.id, order.ItemsCount(), order.TotalPrice())
	fmt.Println("  • Позиции OrderItem защищены от прямого изменения в обход инвариантов Order")
}
```

## Под капотом

Агрегаты задают границы согласованности данных в распределенных системах. За счет того, что репозиторий загружает и сохраняет агрегат целиком (`repo.Save(order)`), исключаются аномалии частичного обновления (Lost Updates).

## Подводные камни

Делать гигантские агрегаты (например `User` содержит все свои 100 000 заказов): загрузка такого агрегата из БД съест гигабайты памяти и приведет к блокировкам строк в СУБД. Агрегаты должны быть максимально компактными.

## На собеседовании

**Вопрос с собеседования:** «Как агрегат Order должен ссылаться на другой агрегат Customer в правильном DDD?»
**Ответ:** Только по уникальному идентификатору (`CustomerID string`), но **никогда не по ссылке-указателю** (`*Customer`). Ссылки по указателям стирают границы агрегатов и провоцируют каскадную загрузку всей базы данных в память.
