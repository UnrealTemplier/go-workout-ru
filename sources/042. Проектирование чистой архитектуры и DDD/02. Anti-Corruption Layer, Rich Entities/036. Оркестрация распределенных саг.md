# Оркестрация распределенных саг (Saga Orchestration): конечный автомат и компенсирующие транзакции

## Условие

Спроектируй **Saga Orchestration**: `OrderSaga` (orchestrator) координирует: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — gRPC/HTTP/event. Compensation: `PaymentFailed` → `ReleaseInventory`. Реализуй state machine в `OrderSaga`.

## Теория

Паттерн Saga Orchestration (Управляемая распределенная транзакция):
- В микросервисной архитектуре невозможно использовать 2-Phase Commit (2PC) из-за проблем с масштабируемостью и блокировками (CAP-теорема).
- **Сага (Saga)** — это последовательность локальных транзакций.
- **Оркестратор (OrderSaga):**
  - Центральный координатор (State Machine).
  - Вызывает шаг 1: `ReserveInventory()`. Успех \(\implies\) шаг 2.
  - Вызывает шаг 2: `ProcessPayment()`. Ошибка \(\implies\) компенсация!
  - **Компенсирующая транзакция:** вызов `ReleaseInventory()` для отката ранее зарезервированного товара.
- Оркестратор гарантирует, что система не останется в «подвешенном» несогласованном состоянии.

## Решение по шагам

1. Создайте состояния конечного автомата саги `OrderSagaState`.
2. Реализуйте шаги прямой цепочки (Reserve \(\to\) Pay).
3. Смоделируйте ошибку платежа и запуск компенсирующей транзакции.
4. Верифицируйте возврат системы в консистентное состояние.

## Код решения

**`saga_orchestrator_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type SagaState string

const (
	StateStarted            SagaState = "STARTED"
	StateInventoryReserved  SagaState = "INVENTORY_RESERVED"
	StatePaymentFailed      SagaState = "PAYMENT_FAILED"
	StateCompensatedSuccess SagaState = "COMPENSATED_RELEASED"
)

type OrderSagaOrchestrator struct {
	State SagaState
}

func (s *OrderSagaOrchestrator) Execute(ctx context.Context, failPayment bool) error {
	s.State = StateStarted

	// Шаг 1: Резервирование склада
	s.State = StateInventoryReserved

	// Шаг 2: Платеж
	if failPayment {
		s.State = StatePaymentFailed
		// Запуск компенсирующей транзакции (Rollback)
		s.compensateInventory(ctx)
		return fmt.Errorf("payment declined")
	}

	return nil
}

func (s *OrderSagaOrchestrator) compensateInventory(ctx context.Context) {
	// Компенсация: возврат товара на склад
	s.State = StateCompensatedSuccess
}

func TestSagaOrchestrator(t *testing.T) {
	saga := &OrderSagaOrchestrator{}

	err := saga.Execute(context.Background(), true) // Провоцируем ошибку платежа

	if err == nil {
		t.Fatal("Ожидалась ошибка платежа")
	}

	if saga.State != StateCompensatedSuccess {
		t.Fatalf("Сага не выполнила компенсацию: текущее состояние %s", saga.State)
	}

	fmt.Println("Оркестрация распределенной саги (Saga Orchestration) подтверждена:")
	fmt.Println("  • Шаг 1: Склад зарезервирован (INVENTORY_RESERVED)")
	fmt.Println("  • Шаг 2: Платеж отклонен (PAYMENT_FAILED)")
	fmt.Printf("  • Компенсация: Товар возвращен на склад -> Финальный статус: %s\n", saga.State)
}
```

## Под капотом

В продакшене состояние оркестратора саги персистируется в реляционной базе данных (Saga Log) перед каждым сетевым вызовом. Если под с оркестратором упадет прямо во время выполнения шага 2, после рестарта он прочитает состояние из БД и продолжит прерванную сагу или компенсацию.

## Подводные камни

Забывать делать шаги саги и компенсации **идемпотентными** (Idempotent): из-за сетевых сбоев вызов `ReleaseInventory()` может быть повторен 3 раза. Сервис склада обязан обработать повтор без повторного начисления остатков.

## На собеседовании

**Вопрос с собеседования:** «В чем ключевой недостаток распределенных саг по сравнению с классическими ACID-транзакциями?»
**Ответ:** Отсутствие свойства **Изоляции (Isolation)** — буква 'I' в ACID. Во время выполнения саги промежуточные изменения видны другим параллельным транзакциям (грязное чтение). Если сага откатится через 10 секунд, другой пользователь успеет увидеть товар, который на самом деле не был куплен. Это решается семантическими блокировками (Semantic Locks, статус PENDING).
