# Хореография распределенных саг (Saga Choreography): децентрализованная цепочка событий без оркестратора

## Условие

Спроектируй **Saga Choreography**: нет центрального orchestrator'а. `OrderService` публикует `OrderCreated`. `InventoryService` подписывается, резервирует, публикует `InventoryReserved`. `PaymentService` подписывается... Покажи децентрализацию, но сложность отслеживания.

## Теория

Хореография саг (Saga Choreography):
- В отличие от оркестрации, **здесь нет центрального координатора**:
  1. `OrderService` создает заказ и бросает событие `OrderCreated`.
  2. `InventoryService` слушает событие, списывает остатки и бросает `InventoryReserved`.
  3. `PaymentService` слушает `InventoryReserved`, списывает деньги и бросает `PaymentProcessed`.
- **Преимущества:** Полная децентрализация, сервисы не знают о существовании друг друга.
- **Главный недостаток в HighLoad:**
  - Крайне сложно отслеживать сквозной поток (Spaghetti Event Flow).
  - Риск циклических зависимостей событий.
  - Сложность отладки: чтобы понять, почему заказ не завершился, приходится анализировать логи 10 разных сервисов через distributed tracing (OpenTelemetry).

## Решение по шагам

1. Смоделируйте шину событий для хореографии.
2. Настройте цепочку реакции сервисов Order, Inventory и Payment.
3. Запустите первоначальное событие `OrderCreated`.
4. Верифицируйте сквозную децентрализованную цепочку выполнения.

## Код решения

**`saga_choreography_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ChoreographyBus struct {
	trace []string
}

func (b *ChoreographyBus) Emit(event string) {
	b.trace = append(b.trace, event)
	// Сервисы реагируют на события автономно
	switch event {
	case "OrderCreated":
		// InventoryService реагирует
		b.Emit("InventoryReserved")
	case "InventoryReserved":
		// PaymentService реагирует
		b.Emit("PaymentCompleted")
	case "PaymentCompleted":
		// ShippingService реагирует
		b.Emit("OrderShipped")
	}
}

func TestSagaChoreography(t *testing.T) {
	bus := &ChoreographyBus{}
	// Запуск первого домино
	bus.Emit("OrderCreated")

	expectedTrace := []string{"OrderCreated", "InventoryReserved", "PaymentCompleted", "OrderShipped"}
	if len(bus.trace) != len(expectedTrace) {
		t.Fatalf("Сбой цепочки хореографии: %+v", bus.trace)
	}

	fmt.Println("Хореография саг (Saga Choreography) успешно продемонстрирована:")
	for i, step := range bus.trace {
		fmt.Printf("  [%d] Событие: %s\n", i+1, step)
	}
	fmt.Println("  • Полная децентрализация: ни один сервис не знает полного сценария заказа целиком!")
}
```

ℹ️ Децентрализованное выполнение распределенной саги через цепочку автономных событий

## Под капотом

В распределенной хореографии сквозная трассировка поддерживается через W3C `traceparent` заголовок в метаданных сообщений Kafka/RabbitMQ: каждый сервис передает `TraceID` дальше по цепочке, связывая децентрализованные события в единый трейс Jaeger.

## Подводные камни

Использовать хореографию в процессах, содержащих более 4–5 шагов: при разрастании числа сервисов никто в компании больше не понимает полный путь движения бизнес-транзакции. Для сложных сценариев переходят на оркестрацию (Temporal, Camunda).

## На собеседовании

**Вопрос с собеседования:** «Когда стоит выбрать Saga Orchestration, а когда Saga Choreography?»
**Ответ:** 
- **Choreography:** идеально для простых линейных цепочек из 2–3 сервисов, где добавление новых слушателей не ломает существующий флоу.
- **Orchestration:** выбирают для сложных сценариев с множеством компенсаций, ветвлениями условий и жесткими требованиями к аудиту, где логика процесса должна быть зафиксирована в одном месте (конечном автомате).
