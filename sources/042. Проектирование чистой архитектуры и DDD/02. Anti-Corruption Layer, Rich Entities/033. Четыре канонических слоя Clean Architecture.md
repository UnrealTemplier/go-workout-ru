# Четыре канонических слоя Clean Architecture: строгая центростремительная изоляция

## Условие

**Слои Clean Architecture**: Разделите код на 4 слоя: Entities (доменные объекты) → Use Cases (бизнес-логика) → Interfaces (adapters) → Frameworks (HTTP, DB). Зависимости направлены только внутрь.

## Теория

Четырехслойная пирамида Clean Architecture Uncle Bob:
1. **Слой 1: Entities.** Предметная область: правила, инварианты, Value Objects, чистые доменные ошибки.
2. **Слой 2: Use Cases.** Сценарии бизнес-процессов: координация сущностей, транзакции, вызовы портов.
3. **Слой 3: Interface Adapters.** Контроллеры, шлюзы, мапперы, форматирование ответов, presenters.
4. **Слой 4: Frameworks & Drivers.** Базы данных (pgx, gorm), веб-роутеры (chi, gin), консоль, очереди (Kafka).
- **Правило стрелок:** Стрелки зависимостей на диаграмме архитектуры указывают строго от слоя 4 к слою 1.

## Решение по шагам

1. Создайте доменную сущность с инвариантом `EntityItem`.
2. Создайте сценарий использования `UseCaseItem`.
3. Реализуйте интерфейсный адаптер презентера `PresenterAdapter`.
4. Верифицируйте соблюдение центростремительного правила.

## Код решения

**`four_layer_clean_arch_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Layer 1: Entities
type ProductEntity struct {
	ID       string
	PriceRub int64
}

func (p *ProductEntity) ApplyPromoDiscount(percent int64) error {
	if percent < 0 || percent > 90 {
		return fmt.Errorf("invalid discount: %d", percent)
	}
	p.PriceRub = p.PriceRub * (100 - percent) / 100
	return nil
}

// Layer 2: Use Cases
type ApplyDiscountUseCase struct{}

func (uc *ApplyDiscountUseCase) Execute(product *ProductEntity, discountPercent int64) error {
	return product.ApplyPromoDiscount(discountPercent)
}

// Layer 3: Interface Adapters (Presenter)
type ProductPresenter struct{}

func (pr *ProductPresenter) FormatCurrency(p ProductEntity) string {
	return fmt.Sprintf("%d.00 ₽", p.PriceRub)
}

// Layer 4: Frameworks & Drivers (Внешний потребитель)
func TestFourLayerCleanArch(t *testing.T) {
	entity := &ProductEntity{ID: "prod-1", PriceRub: 10_000}
	useCase := &ApplyDiscountUseCase{}
	presenter := &ProductPresenter{}

	// Выполнение Use Case
	if err := useCase.Execute(entity, 15); err != nil {
		t.Fatalf("Ошибка UseCase: %v", err)
	}

	formatted := presenter.FormatCurrency(*entity)
	if formatted != "8500.00 ₽" {
		t.Fatalf("Некорректное форматирование цены: %s", formatted)
	}

	fmt.Println("Четыре канонических слоя Clean Architecture успешно подтверждены:")
	fmt.Println("  • Слой 1 (Entities): ProductEntity инкапсулирует бизнес-инвариант скидки")
	fmt.Println("  • Слой 2 (Use Cases): ApplyDiscountUseCase координирует операцию")
	fmt.Println("  • Слой 3 (Interface Adapters): ProductPresenter форматирует вывод")
	fmt.Printf("  • Слой 4 (Frameworks): Тест подтвердил итоговую стоимость: %s\n", formatted)
}
```

## Под капотом

При строгом соблюдении слоев Clean Architecture слой Entities не импортирует даже стандартную библиотеку `net/http` или SQL-пакеты. Все сущности представляют собой «чистый Go» (POJO/POCO аналоги), что делает их вечными и не зависящими от смены сторонних библиотек.

## Подводные камни

Использовать теги `json:"..."` или `gorm:"..."` прямо в слое `Entities`: это нарушает чистоту 1-го слоя, связывая доменную сущность с конкретным форматом JSON или ORM. Для ORM создают слой моделей персистентности в слое 4.

## На собеседовании

**Вопрос с собеседования:** «Стоит ли заводить отдельные DTO структуры для каждого слоя Clean Architecture?»
**Ответ:** В строгом академическом подходе — да, каждый слой имеет свои DTO (HTTP Request DTO -> UseCase Input DTO -> Entity -> Database Row DTO -> Presenter View Model). Но в практической HighLoad разработке на Go это создает огромный бойлерплейт и аллокации памяти. На практике часто объединяют UseCase Input с Entity, оставляя отдельными только HTTP DTO и DB DTO.
