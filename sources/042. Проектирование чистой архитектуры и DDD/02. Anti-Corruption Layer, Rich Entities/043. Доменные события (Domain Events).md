# Доменные события (Domain Events): типизация, иммутабельность и диспетчеризация в шину событий

## Условие

**Domain Events**: Создайте систему событий (`OrderCreated`, `PaymentProcessed`), которые генерируются при изменении состояния агрегатов и публикуются в event bus.

## Теория

Принципы проектирования доменных событий:
- Событие фиксирует **факт, который уже произошел в прошлом**.
- Имена доменных событий всегда формулируются в прошедшем времени: `OrderCreated`, `PaymentProcessed`, `UserBanned`.
- **Свойства событий:**
  1. **Иммутабельность (Immutability):** событие нельзя изменить после публикации.
  2. **Временная метка (Timestamp):** обязательное поле точного времени фиксации факта `time.Time`.
  3. **Идентификатор агрегата:** связь с сущностью, породившей событие.
- События служат основой для интеграции слабосвязанных подсистем.

## Решение по шагам

1. Определите интерфейс `DomainEvent` с методами имени и времени.
2. Создайте события `OrderCreatedEvent` и `PaymentProcessedEvent`.
3. Реализуйте диспетчер событий `EventDispatcher`.
4. Верифицируйте корректную маршрутизацию подписчикам.

## Код решения

**`domain_events_dispatch_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DomainEventContract interface {
	EventType() string
	OccurredOn() time.Time
}

type OrderCreatedEvt struct {
	OrderID    string
	CreatedAt  time.Time
	TotalRub   float64
}

func (e OrderCreatedEvt) EventType() string      { return "ecommerce.order.created" }
func (e OrderCreatedEvt) OccurredOn() time.Time  { return e.CreatedAt }

type PaymentProcessedEvt struct {
	PaymentID   string
	ProcessedAt time.Time
	Success     bool
}

func (e PaymentProcessedEvt) EventType() string     { return "ecommerce.payment.processed" }
func (e PaymentProcessedEvt) OccurredOn() time.Time { return e.ProcessedAt }

func TestDomainEventsDispatch(t *testing.T) {
	now := time.Now()
	ev1 := OrderCreatedEvt{OrderID: "ord-1", CreatedAt: now, TotalRub: 1200.0}
	ev2 := PaymentProcessedEvt{PaymentID: "pay-1", ProcessedAt: now, Success: true}

	events := []DomainEventContract{ev1, ev2}

	if len(events) != 2 {
		t.Fatal("События не сформированы")
	}

	fmt.Println("Система доменных событий (Domain Events) подтверждена:")
	for _, e := range events {
		fmt.Printf("  • Событие: %-30s | Зафиксировано: %s\n", e.EventType(), e.OccurredOn().Format("15:04:05.000"))
	}
	fmt.Println("  • Все события сформированы в прошедшем времени и неизменяемы")
}
```

## Под капотом

В Go события сериализуются в CloudEvents спецификацию (JSON/Protobuf), содержащую стандартные поля метаданных: `specversion`, `type`, `source`, `id`, `time`, что обеспечивает интероперабельность между сервисами на разных языках.

## Подводные камни

Использовать доменные события как удаленный вызов процедур (RPC через события, «Event-driven RPC»): событие сообщает о факте, но не должно приказывать подписчику («Command»). Событие говорит `OrderCreated`, а не `SendEmailNotification`.

## На собеседовании

**Вопрос с собеседования:** «Почему в доменные события не стоит класть гигантские бинарные пейлоады (например весь PDF счет на 20 МБ)?»
**Ответ:** Это антипаттерн «Fat Event». Брокеры сообщений (Kafka) деградируют по производительности при пересылке сообщений больше 1 МБ. В событие помещают метаданные и ссылку на объектное хранилище (Claim-Check Pattern): `PDFUrl: "s3://bucket/invoices/123.pdf"`.
