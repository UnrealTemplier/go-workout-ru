# Богатая модель предметной области (Rich Domain Model) против анемичной модели (Anemic Domain Model)

## Условие

**Богатая модель (Rich Domain Model) vs Анемичная (Anemic)**: Реализуйте сущность `BankAccount`. Сравните два подхода: анемичный (структура без методов, вся логика в Service) и богатый (структура сама контролирует инварианты, методы `Withdraw`, `Deposit`). Обсудите инкапсуляцию.

### Исходная формулировка

Определи **Aggregate Roots**: `User` (root: `User`, entities: `Address`, `PaymentMethod`), `Order` (root: `Order`, entities: `OrderItem`, `OrderStatus`), `Product` (root: `Product`, entities: `ProductVariant`, `Inventory`). Покажи invariants: `Order.total = sum(OrderItem.subtotal)`.

## Теория

Антипаттерн Anemic Domain Model (Мартин Фаулер):
- **Анемичная модель:** Структура содержит только публичные поля `Balance float64`, а вся логика валидации и изменения баланса размазана по `AccountService`. Сущность превращается в простой мешок с данными (Data Bag).
  - *Опасность:* Любой программист может напрямую написать `acc.Balance -= 1000` без проверки овердрафта.
- **Богатая доменная модель (Rich Domain Model):**
  - Поля приватны (инкапсуляция).
  - Изменение состояния возможно **только через методы доменной сущности**: `account.Withdraw(amount)`.
  - Сущность сама гарантирует свои инварианты (баланс не может стать отрицательным).

## Решение по шагам

1. Создайте богатую сущность `BankAccount` с приватным балансом.
2. Реализуйте методы `Deposit` и `Withdraw` с защитой инвариантов.
3. Продемонстрируйте невозможность перевода счета в невалидное состояние.
4. Верифицируйте корректность инкапсуляции.

## Код решения

**`rich_domain_model_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

// Rich Domain Model: поля инкапсулированы, инварианты защищены
type BankAccount struct {
	id      string
	balance int64 // В копейках / центах (целое число!)
}

func NewBankAccount(id string, initialDeposit int64) (*BankAccount, error) {
	if initialDeposit < 0 {
		return nil, errors.New("initial deposit cannot be negative")
	}
	return &BankAccount{id: id, balance: initialDeposit}, nil
}

func (a *BankAccount) Balance() int64 {
	return a.balance
}

func (a *BankAccount) Deposit(amount int64) error {
	if amount <= 0 {
		return errors.New("deposit amount must be positive")
	}
	a.balance += amount
	return nil
}

func (a *BankAccount) Withdraw(amount int64) error {
	if amount <= 0 {
		return errors.New("withdraw amount must be positive")
	}
	if a.balance < amount {
		return errors.New("insufficient funds for withdrawal")
	}
	a.balance -= amount
	return nil
}

func TestRichDomainModel(t *testing.T) {
	acc, err := NewBankAccount("acc-123", 10_000)
	if err != nil {
		t.Fatalf("Ошибка создания счета: %v", err)
	}

	// Успешное снятие
	if err := acc.Withdraw(4_000); err != nil {
		t.Fatalf("Ошибка снятия средств: %v", err)
	}

	// Попытка уйти в минус (инвариант защищен сущностью!)
	err = acc.Withdraw(10_000)
	if err == nil {
		t.Fatal("Ожидалась ошибка превышения баланса")
	}

	if acc.Balance() != 6_000 {
		t.Fatalf("Некорректный остаток на счете: %d", acc.Balance())
	}

	fmt.Println("Богатая модель предметной области (Rich Domain Model) подтверждена:")
	fmt.Printf("  • Баланс счета: %d коп. Инвариант защищен от прямого изменения извне\n", acc.Balance())
	fmt.Println("  • Попытка овердрафта успешно отклонена бизнес-методом Withdraw()")
}
```

ℹ️ Инкапсуляция бизнес-инвариантов внутри богатой доменной модели BankAccount

## Под капотом

В Go инкапсуляция обеспечивается не ключевым словом `private`, а первой строчной буквой идентификатора (`balance`). Все методы и структуры одного пакета видят приватные поля друг друга, но для всех внешних пакетов доступ к `balance` закрыт на уровне компилятора.

## Подводные камни

Добавлять в доменную сущность методы ввода-вывода (например `acc.SaveToDB()`): это нарушает SRP и превращает сущность в антипаттерн Active Record. Доменная сущность должна менять только свое состояние в памяти; сохранением в БД занимается репозиторий.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go часто пишут анемичные модели (Anemic Domain Model), хотя все книги по DDD советуют Rich Model?»
**Ответ:** Из-за особенностей сериализации `encoding/json` и баз данных: чтобы библиотека могла прочитать поле, оно обязано быть экспортируемым (с большой буквы). Если делать все поля публичными, инкапсуляция теряется. В идиоматичном Rich Go DDD доменные сущности имеют приватные поля и фабричные методы `New()`, а для JSON и БД создают отдельные DTO с экспортируемыми полями.
