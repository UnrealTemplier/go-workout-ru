# Флаги возможностей (Feature Toggles / Feature Flags): динамическое управление кодовой базой в рантайме

## Условие

**Feature Toggles (Флаги фичей)**: Спроектируй сервис, который проверяет флаги. Оберни новую (нестабильную) бизнес-логику в условие `if featureflags.IsEnabled("new_payment_gateway")`. Реализуй динамическое переключение флага в памяти (или через Redis) без перезапуска приложения.

## Теория

Философия Feature Toggles в Continuous Delivery (Мартин Фаулер):
- Feature Flags позволяют **отделить развертывание кода (Deployment) от релиза функционала (Release)**.
- Код новой функциональности вливается в master и деплоится в продакшен в выключенном состоянии (`enabled: false`).
- **Типы флагов:**
  1. **Release Toggles:** плавный выкат новой фичи (Canary rollout на 5% пользователей).
  2. **Kill Switches (Аварийный выключатель):** моментальное отключение тяжелого функционала при перегрузке БД без деплоя и рестарта.
  3. **Permission Toggles:** доступ к бета-версиям для сотрудников компании.
- Динамическое переключение флагов в памяти сервиса происходит за 1 миллисекунду через Redis Pub/Sub или локальный кеш.

## Решение по шагам

1. Создайте потокобезопасный менеджер флагов `FeatureFlagManager`.
2. Реализуйте метод проверки `IsEnabled`.
3. Оберните альтернативную ветку бизнес-логики в проверку флага.
4. Продемонстрируйте динамическое переключение логики на лету.

## Код решения

**`feature_toggles_runtime_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type FeatureFlagManager struct {
	mu    sync.RWMutex
	flags map[string]bool
}

func NewFeatureFlagManager() *FeatureFlagManager {
	return &FeatureFlagManager{flags: make(map[string]bool)}
}

func (m *FeatureFlagManager) SetFlag(flag string, enabled bool) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.flags[flag] = enabled
}

func (m *FeatureFlagManager) IsEnabled(flag string) bool {
	m.mu.RLock()
	defer m.mu.RUnlock()
	return m.flags[flag]
}

type PaymentProcessorService struct {
	flags *FeatureFlagManager
}

func (s *PaymentProcessorService) ProcessPayment() string {
	// Динамическое ветвление на базе Feature Flag
	if s.flags.IsEnabled("new_fast_payment_gateway") {
		return "Обработано через НОВЫЙ FAST PAYMENT GATEWAY"
	}
	return "Обработано через СТАРЫЙ LEGACY GATEWAY"
}

func TestFeatureTogglesRuntime(t *testing.T) {
	flags := NewFeatureFlagManager()
	service := &PaymentProcessorService{flags: flags}

	// 1. По умолчанию флаг выключен
	res1 := service.ProcessPayment()
	if res1 != "Обработано через СТАРЫЙ LEGACY GATEWAY" {
		t.Fatalf("Ожидался старый шлюз, получено: %s", res1)
	}

	// 2. Включаем флаг на лету в рантайме (без перезапуска сервиса!)
	flags.SetFlag("new_fast_payment_gateway", true)
	res2 := service.ProcessPayment()
	if res2 != "Обработано через НОВЫЙ FAST PAYMENT GATEWAY" {
		t.Fatalf("Ожидался новый шлюз, получено: %s", res2)
	}

	fmt.Println("Управление функционалом через Feature Toggles успешно подтверждено:")
	fmt.Printf("  • До включения флага:  %s\n", res1)
	fmt.Printf("  • После включения:     %s\n", res2)
	fmt.Println("  • Переключение выполнено в памяти на лету без остановки пода!")
}
```

ℹ️ Динамическое управление ветками бизнес-логики через Feature Toggles без перезапуска сервиса

## Под капотом

В корпоративных средах флаги читаются через SDK Unleash, LaunchDarkly или Flipt. SDK держит локальную копию всех флагов в `sync.Map` и подписывается на Server-Sent Events (SSE) от сервера управления флагами: обновление флага во всем кластере из 1000 подов занимает менее 500 миллисекунд.

## Подводные камни

Копить устаревшие флаги годами: мертвые флаги загромождают код условиями `if/else` и превращают логику в мину замедленного действия. После 100% раскатки фичи флаг и старая ветка кода **должны быть удалены** из кодовой базы в рамках планового техдолга.

## На собеседовании

**Вопрос с собеседования:** «Как протестировать микросервис, если в кодовой базе активно 20 разных Feature Flags?»
**Ответ:** Все комбинации \(2^{20} = 1\,000\,000\) протестировать невозможно. Применяют стратегию:
1. Юнит-тесты проверяют оба состояния (`true` и `false`) конкретного нового флага в изоляции.
2. Сквозные интеграционные тесты (E2E) запускаются в двух базовых конфигурациях: «Все продакшн-флаги по умолчанию» и «Все новые стабильные флаги включены».
