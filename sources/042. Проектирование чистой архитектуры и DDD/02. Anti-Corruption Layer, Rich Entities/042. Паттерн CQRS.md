# Паттерн CQRS: разделение модели команд (Commands) и модели выборок (Queries) в микросервисах

## Условие

Реализуй **CQRS в микросервисе**: `Order Command Service` (PostgreSQL, normalized schema, transactions) обрабатывает `CreateOrder`, `CancelOrder`. `Order Query Service` (Elasticsearch/ClickHouse, denormalized views) отвечает на `GetOrderHistory`, `SearchOrders`. Синхронизация через events.

## Теория

Архитектура CQRS (Command Query Responsibility Segregation):
- В традиционных системах одна модель данных используется и для записи, и для чтения. В HighLoad это приводит к компромиссам: нормализованная схема тормозит выборки, а индексы для чтения замедляют вставки.
- **CQRS разделяет ответственность:**
  1. **Write Model (Commands):**
     - Фокус на бизнес-инвариантах, валидации и строгих транзакциях ACID.
     - Нормализованная реляционная БД (PostgreSQL).
     - Методы возвращают `void` или `ID` (никогда не возвращают тяжелые агрегаты).
  2. **Read Model (Queries):**
     - Фокус на скорости чтения и поиске (High Throughput).
     - Денормализованные представления (Elasticsearch, Redis, ClickHouse).
     - Никаких бизнес-правил — прямой возврат готового плоского DTO.

## Решение по шагам

1. Создайте интерфейс команд `OrderCommandHandler`.
2. Создайте интерфейс запросов `OrderQueryHandler`.
3. Смоделируйте асинхронную проекцию данных из хранилища команд в поисковую витрину.
4. Верифицируйте разделение обязанностей.

## Код решения

**`cqrs_microservice_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// 1. Command Side (Запись / PostgreSQL)
type CreateOrderCmd struct {
	OrderID  string
	Customer string
	Amount   float64
}

type OrderCommandService struct {
	writeDB map[string]CreateOrderCmd
	events  chan CreateOrderCmd
}

func (s *OrderCommandService) HandleCreate(cmd CreateOrderCmd) error {
	s.writeDB[cmd.OrderID] = cmd
	// Асинхронная отправка события для Read Model
	s.events <- cmd
	return nil
}

// 2. Query Side (Чтение / Денормализованная витрина)
type OrderViewDTO struct {
	OrderID     string
	DisplayName string
}

type OrderQueryService struct {
	readCache map[string]OrderViewDTO
}

func (q *OrderQueryService) GetByID(id string) (OrderViewDTO, bool) {
	dto, ok := q.readCache[id]
	return dto, ok
}

func TestCQRSMicroservice(t *testing.T) {
	eventCh := make(chan CreateOrderCmd, 1)
	cmdSvc := &OrderCommandService{writeDB: make(map[string]CreateOrderCmd), events: eventCh}
	querySvc := &OrderQueryService{readCache: make(map[string]OrderViewDTO)}

	// 1. Выполнение команды записи
	cmd := CreateOrderCmd{OrderID: "ord-cqrs-1", Customer: "Константин", Amount: 8900.0}
	_ = cmdSvc.HandleCreate(cmd)

	// 2. Проекция события в Query Model
	evt := <-eventCh
	querySvc.readCache[evt.OrderID] = OrderViewDTO{
		OrderID:     evt.OrderID,
		DisplayName: fmt.Sprintf("Заказ для %s на %.2f руб", evt.Customer, evt.Amount),
	}

	// 3. Выполнение запроса чтения
	view, found := querySvc.GetByID("ord-cqrs-1")
	if !found || view.DisplayName == "" {
		t.Fatal("Данные не найдены в Read Model")
	}

	fmt.Println("Архитектура CQRS успешно подтверждена:")
	fmt.Printf("  • Command Side сохранил нормализованный заказ %s\n", cmd.OrderID)
	fmt.Printf("  • Query Side вернул денормализованное представление: %q\n", view.DisplayName)
}
```

ℹ️ Разделение модели команд (запись) и модели запросов (чтение) через асинхронную проекцию

## Под капотом

В микросервисной архитектуре CQRS позволяет независимо масштабировать чтение и запись. Если сервис имеет соотношение 100 запросов чтения на 1 запрос записи (100:1), Query-реплики масштабируются горизонтально в 20 подов, а Command-сервису достаточно 2 подов.

## Подводные камни

Внедрять CQRS в простые CRUD сервисы: поддержка двух моделей данных, очередей синхронизации и управление задержкой Eventual Consistency создают огромную архитектурную сложность, неоправданную для небольших систем.

## На собеседовании

**Вопрос с собеседования:** «Что делать клиенту, если он сразу после POST /orders делает GET /orders, а Read Model еще не успела обновиться из-за задержки Kafka (Eventual Consistency)?»
**Ответ:** 
1. **Optimistic UI:** фронтенд сразу отрисовывает созданный заказ локально без повторного GET-запроса.
2. **Read-Your-Own-Writes:** на первые 5 секунд после создания клиент направляется на чтение напрямую в мастер-БД команд по ключу `OrderID`.
3. Возврат версии агрегата и ожидание обновления витрины через WebSockets/SSE.
