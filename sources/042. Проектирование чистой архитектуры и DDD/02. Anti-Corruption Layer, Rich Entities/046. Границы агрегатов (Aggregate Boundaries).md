# Границы агрегатов (Aggregate Boundaries): правило изменения одного агрегата в одной транзакции

## Условие

**Aggregates**: Определите границы агрегатов (например, `Order` как aggregate root, содержащий `OrderItems`). Транзакции не должны пересекать границы агрегатов.

## Теория

Фундаментальное правило DDD: «Одна транзакция — один агрегат»:
- Почему нельзя в одной ACID-транзакции менять два агрегата (например `Order` и `CustomerBalance`):
  1. Это приводит к распределенным блокировкам строк в БД и дедлокам при высокой конкуренции.
  2. Это нарушает автономию агрегатов и делает невозможным их разделение по микросервисам в будущем.
- **Решение:**
  - Транзакция 1 (ACID): сохраняет изменения агрегата `Order` в БД.
  - Согласованность со вторым агрегатом `Customer` достигается **асинхронно через доменные события** (Eventual Consistency).

## Решение по шагам

1. Создайте границу агрегата `OrderBoundary`.
2. Продемонстрируйте запрет прямой мутации чужого агрегата `CustomerWallet`.
3. Реализуйте взаимодействие через события.
4. Верифицируйте независимость транзакционных единиц.

## Код решения

**`aggregate_boundaries_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CustomerWalletAggregate struct {
	CustomerID string
	Balance    float64
}

type OrderAggregateBoundary struct {
	OrderID    string
	CustomerID string
	Total      float64
	Status     string
}

func (o *OrderAggregateBoundary) Submit() {
	o.Status = "SUBMITTED"
	// НЕ МЕНЯЕМ Wallet напрямую! Агрегат Order отвечает только за себя.
}

func TestAggregateBoundaries(t *testing.T) {
	wallet := &CustomerWalletAggregate{CustomerID: "cust-1", Balance: 5000.0}
	order := &OrderAggregateBoundary{OrderID: "ord-1", CustomerID: wallet.CustomerID, Total: 1500.0}

	order.Submit()

	if order.Status != "SUBMITTED" {
		t.Fatal("Заказ не перешел в статус SUBMITTED")
	}

	fmt.Println("Границы агрегатов (Aggregate Boundaries) успешно подтверждены:")
	fmt.Printf("  • Агрегат Order (%s) автономен от агрегата Wallet (%s)\n", order.OrderID, wallet.CustomerID)
	fmt.Println("  • Правило DDD: одна транзакция модифицирует ровно один агрегат!")
}
```

## Под капотом

Ограничение «один агрегат — одна транзакция» делает систему идеально приспособленной к шардированию баз данных (Database Sharding): агрегат целиком хранится на одном шарде по ключу шардирования (`Sharding Key = AggregateID`), исключая распределенные транзакции между шардами.

## Подводные камни

Объединять 5 разных сущностей в один мега-агрегат ради сохранения локального ACID: это приводит к конкурентным блокировкам, когда два пользователя одновременно пытаются изменить связанные данные.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если бизнесу требуется абсолютная мгновенная согласованность (Strong Consistency) между двумя сущностями?»
**Ответ:** Если бизнес-правило действительно требует 100% неразрывной мгновенной согласованности, это означает, что эти две сущности на самом деле **принадлежат одному общему агрегату**! Их нужно объединить под единым Aggregate Root, который будет мутировать их в рамках одной локальной транзакции.
