# Паттерн Репозиторий (Repository): абстрагирование персистентности от SQL и баз данных

## Условие

**Repositories**: Реализуйте репозитории, которые скрывают детали хранения. Интерфейс `OrderRepository` не должен знать про SQL или PostgreSQL.

## Теория

Паттерн Репозиторий (Repository Pattern, Мартин Фаулер):
- Репозиторий создает иллюзию того, что **все доменные объекты находятся в оперативной памяти в виде коллекции**.
- **Чистый доменный интерфейс:**
  - `Save(ctx, order)`
  - `FindByID(ctx, id)`
  - `Remove(ctx, id)`
- **Что категорически запрещено в интерфейсе репозитория:**
  - Передавать SQL-запросы или фрагменты условий (`WHERE clause`).
  - Возвращать типы `*sql.Rows`, `sql.Result`.
  - Упоминать таблицы или колонки СУБД.

## Решение по шагам

1. Опишите интерфейс `OrderRepository` в доменном пакете.
2. Создайте InMemory-реализацию для юнит-тестов.
3. Продемонстрируйте чистоту методов без утечек SQL-специфики.
4. Верифицируйте корректность сохранения и выборки агрегата.

## Код решения

**`pure_repository_pattern_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
)

type DomainOrder struct {
	ID    string
	Total float64
}

// Чистый интерфейс репозитория: никаких упоминаний SQL!
type PureOrderRepository interface {
	Store(ctx context.Context, order *DomainOrder) error
	Get(ctx context.Context, id string) (*DomainOrder, error)
}

type InMemoryOrderRepository struct {
	mu    sync.RWMutex
	items map[string]*DomainOrder
}

func NewInMemoryOrderRepository() *InMemoryOrderRepository {
	return &InMemoryOrderRepository{items: make(map[string]*DomainOrder)}
}

func (r *InMemoryOrderRepository) Store(ctx context.Context, order *DomainOrder) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.items[order.ID] = order
	return nil
}

func (r *InMemoryOrderRepository) Get(ctx context.Context, id string) (*DomainOrder, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	o, ok := r.items[id]
	if !ok {
		return nil, errors.New("domain order not found")
	}
	return o, nil
}

func TestPureRepositoryPattern(t *testing.T) {
	repo := NewInMemoryOrderRepository()
	ctx := context.Background()

	order := &DomainOrder{ID: "ord-pure-1", Total: 19990.0}
	_ = repo.Store(ctx, order)

	found, err := repo.Get(ctx, "ord-pure-1")
	if err != nil || found.Total != 19990.0 {
		t.Fatalf("Ошибка выборки из чистого репозитория: %v", err)
	}

	fmt.Println("Паттерн Репозиторий (Pure Repository) успешно подтвержден:")
	fmt.Printf("  • Заказ %s сохранен и прочитан как элемент коллекции в памяти\n", found.ID)
	fmt.Println("  • Интерфейс не содержит ни одного упоминания SQL или реляционных таблиц")
}
```

ℹ️ Инкапсуляция персистентности домена за чистым интерфейсом коллекции

## Под капотом

В конкретной реализации `PostgresOrderRepository` репозиторий преобразует агрегат в плоские SQL-записи через сканирование колонок (`pgx.RowToStructByName`) и маппит обратно в богатую доменную сущность через фабричный конструктор `NewDomainOrder()`.

## Подводные камни

Внедрять пагинацию с прямыми параметрами `LIMIT` и `OFFSET` в доменный репозиторий: лучше передавать абстрактный объект пагинации или спецификацию (`Specification Pattern`), чтобы не связывать логику с реляционным синтаксисом.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между DAO (Data Access Object) и Repository?»
**Ответ:** 
- **DAO** ориентирован на базу данных и таблицу (1 DAO = 1 таблица БД, методы зеркалируют CRUD строки таблицы).
- **Repository** ориентирован на домен (1 Repository = 1 Корень Агрегата). Репозиторий оперирует агрегатом как единым целым и скрывает тот факт, что внутри агрегат может сохраняться сразу в 4 разные таблицы через JOIN.
