# Корпоративная структура проекта: разграничение зон ответственности /cmd, /internal и /pkg

## Условие

**Структура проекта: `/cmd`, `/internal`, `/pkg`**. Создайте проект с пакетами `cmd/server`, `internal/app`, `internal/handler`, `internal/service`, `internal/repository`, `pkg/logger`. Опишите, что куда класть.

## Теория

Матрица ответственности каталогов корпоративного проекта:
- **`cmd/server/main.go`:** Точка входа. Чтение конфигурации, создание логгера, сборка графа зависимостей (DI), запуск серверов и обработка graceful shutdown.
- **`internal/app/`:** Инициализация жизненного цикла (Lifecycle Runner).
- **`internal/handler/`:** HTTP/gRPC контроллеры, сериализация JSON/Protobuf, валидация DTO.
- **`internal/service/`:** Бизнес-логика Use Cases.
- **`internal/repository/`:** SQL-запросы, драйверы БД, кэширование.
- **`pkg/logger/`:** Переиспользуемый публичный пакет логирования, который может импортироваться другими репозиториями компании.

## Решение по шагам

1. Создайте модель карты репозитория.
2. Опишите строгие правила размещения файлов.
3. Продемонстрируйте валидацию размещения публичных и приватных пакетов.
4. Верифицируйте корректность архитектурной иерархии.

## Код решения

**`corporate_layout_matrix_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type PackageRole struct {
	Path        string
	Category    string
	Description string
}

func GetCorporateLayout() []PackageRole {
	return []PackageRole{
		{Path: "cmd/server", Category: "Entrypoint", Description: "Сборка Composition Root и main()"},
		{Path: "internal/app", Category: "Bootstrap", Description: "Управление жизненным циклом (Run, Stop)"},
		{Path: "internal/handler", Category: "Transport", Description: "Контроллеры HTTP/gRPC, JSON DTO"},
		{Path: "internal/service", Category: "Business", Description: "Use Cases бизнес-правила"},
		{Path: "internal/repository", Category: "Persistence", Description: "SQL запросы и кэши"},
		{Path: "pkg/logger", Category: "Public SDK", Description: "Публичный логгер для всей компании"},
	}
}

func TestCorporateLayoutMatrix(t *testing.T) {
	layout := GetCorporateLayout()

	hasPublic := false
	hasPrivate := false

	for _, p := range layout {
		if strings.HasPrefix(p.Path, "pkg/") {
			hasPublic = true
		}
		if strings.HasPrefix(p.Path, "internal/") {
			hasPrivate = true
		}
	}

	if !hasPublic || !hasPrivate {
		t.Fatal("Корпоративная структура должна содержать и internal, и pkg зоны")
	}

	fmt.Println("Корпоративная структура Go-проекта (Standard Layout):")
	for _, p := range layout {
		fmt.Printf("  • %-22s [%-12s] -> %s\n", p.Path, p.Category, p.Description)
	}
	fmt.Println("  • Зоны ответственности строго разделены: код из internal защищен от внешнего мира")
}
```

## Под капотом

В крупных монорепозиториях BigTech каталог `pkg/` часто публикуется в виде отдельных версионированных Go-модулей с собственными `go.mod` файлами через git submodules или monorepo tooling (Bazel, Pants).

## Подводные камни

Помещать доменную бизнес-логику в папку `pkg/`: это нарушает инкапсуляцию, делая ваши внутренние бизнес-правила доступными для импорта любым сторонним сервисом.

## На собеседовании

**Вопрос с собеседования:** «Почему некоторые авторы (например Dave Cheney) выступают против папки pkg/?»
**Ответ:** Дейв Чейни считает, что если библиотека полезна внешнему миру, ее следует выносить в отдельный независимый Git-репозиторий с собственным циклом версионирования, а внутри сервиса весь код должен лежать строго в `internal/`. Папка `pkg/` внутри приложения создает ложное ощущение разделяемой библиотеки без гарантий стабильности API.
