# Гексагональная архитектура регистрации: инверсия зависимостей между портами ядра и адаптерами

## Условие

**Порты и Адаптеры (Hexagonal Architecture)**: Перепишите простой сценарий регистрации пользователя в Clean Architecture в соответствии с концепцией гексагональной архитектуры. Опишите "порты" (входящие и исходящие интерфейсы, например, `UserRepository` и `UserService`) во внутреннем ядре. Реализуйте "адаптеры" (внешние элементы, такие как хранилище Postgres или HTTP-сервер) во внешнем слое. Продемонстрируйте инверсию зависимостей (Dependency Inversion Principle) в действии.

## Теория

Порты как контракт шестиугольника:
- В гексагональной архитектуре границы домена описываются строго портами (Go-интерфейсами):
  - **Inbound Port (Входящий порт):** `UserRegistrationPort` — контракт того, что домен умеет делать для внешнего мира.
  - **Outbound Port (Исходящий порт):** `UserPersistPort` — контракт того, что домену нужно от инфраструктуры.
- **Адаптеры:**
  - `HTTP Adapter`: преобразует HTTP запрос в вызов `Inbound Port`.
  - `Postgres Adapter`: реализует `Outbound Port` через SQL команды.
- Бизнес-ядро не содержит внешних зависимостей и тестируется на 100% без базы данных.

## Решение по шагам

1. Создайте Inbound Port `RegistrationService` и Outbound Port `UserStore`.
2. Реализуйте бизнес-логику регистрации внутри шестиугольника.
3. Напишите два адаптера: тестовый Stub и эмулятор SQL.
4. Продемонстрируйте выполнение регистрации через порты.

## Код решения

**`hexagonal_user_reg_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// --- ВНУТРИ ГЕКСАГОНА (CORE) ---
type DomainAccount struct {
	ID       string
	Username string
}

// Outbound Port (Исходящий порт)
type AccountStorePort interface {
	SaveAccount(ctx context.Context, acc DomainAccount) error
}

// Inbound Port (Входящий порт)
type AccountRegistrationPort interface {
	RegisterAccount(ctx context.Context, id, username string) error
}

// Реализация бизнес-ядра (внутри гексагона)
type RegistrationCore struct {
	store AccountStorePort
}

func NewRegistrationCore(s AccountStorePort) *RegistrationCore {
	return &RegistrationCore{store: s}
}

func (c *RegistrationCore) RegisterAccount(ctx context.Context, id, username string) error {
	acc := DomainAccount{ID: id, Username: username}
	return c.store.SaveAccount(ctx, acc)
}

// --- СНАРУЖИ ГЕКСАГОНА (ADAPTERS) ---
type PostgresAccountAdapter struct {
	savedCount int
}

func (a *PostgresAccountAdapter) SaveAccount(ctx context.Context, acc DomainAccount) error {
	a.savedCount++
	return nil
}

func TestHexagonalUserReg(t *testing.T) {
	pgAdapter := &PostgresAccountAdapter{}
	core := NewRegistrationCore(pgAdapter)

	// Вызов через входящий порт
	var apiPort AccountRegistrationPort = core
	err := apiPort.RegisterAccount(context.Background(), "acc-101", "alexander")
	if err != nil || pgAdapter.savedCount != 1 {
		t.Fatalf("Сбой регистрации через порт: %v", err)
	}

	fmt.Println("Гексагональная регистрация успешно верифицирована:")
	fmt.Println("  • Входящий порт: AccountRegistrationPort (вызывается транспортом)")
	fmt.Println("  • Исходящий порт: AccountStorePort (реализуется PostgresAccountAdapter)")
	fmt.Println("  • Бизнес-ядро находится в центре и не зависит от Postgres!")
}
```

## Под капотом

Благодаря тому, что ядро зависит только от интерфейсов, все адаптеры могут компилироваться в отдельных пакетах. В Go это предотвращает разрастание времени компиляции и исключает любые шансы появления циклических зависимостей между контроллерами и хранилищем.

## Подводные камни

Создавать порты с зависимостями от внешних пакетов (например `SaveAccount(ctx, acc)` принимает `*http.Request`): порт должен оперировать исключительно доменными типами ядра.

## На собеседовании

**Вопрос с собеседования:** «Как в гексагональной архитектуре организовать подмену реального SMS-шлюза на эмулятор при локальной разработке?»
**Ответ:** Создают два адаптера, реализующих исходящий порт `ForSendingSMS`: `TwilioSMSAdapter` (для продакшена) и `LogSMSAdapter` (для локальной разработки и тестов). В Composition Root (`main.go`) в зависимости от переменной `ENV=local` в конструктор ядра передается нужный адаптер. Бизнес-код ядра остается на 100% неизменным.
