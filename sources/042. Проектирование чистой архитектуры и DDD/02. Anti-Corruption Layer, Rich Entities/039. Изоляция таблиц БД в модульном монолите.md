# Изоляция таблиц БД в модульном монолите: запрет межмодульных SQL-запросов

## Условие

**Модульный монолит (Modular Monolith)**: Раздели приложение на два независимых домена: `billing` (счета) и `inventory` (склад). Запрети пакету `billing` делать SQL-запросы в таблицы склада. `billing` должен общаться со складом **только** через публичные Go-интерфейсы пакета `inventory`.

## Теория

Защита границ данных в модульном монолите:
- Самая частая причина гибели монолитов: разработчики начинают писать кросс-модульные SQL-запросы:
  ```sql
  SELECT * FROM billing_invoices b JOIN inventory_items i ON b.item_id = i.id;
  ```
- **Почему это катастрофа:**
  - Любое изменение структуры колонок склада ломает биллинг.
  - Таблицы оказываются намертво склеены на уровне схемы СУБД.
- **Архитектурный стандарт:**
  - Каждому модулю выделяется своя схема в PostgreSQL (`schema billing`, `schema inventory`).
  - Межмодульное взаимодействие разрешено **исключительно через Go-интерфейсы публичных фасадов**!

## Решение по шагам

1. Создайте модуль `InventoryModule` с приватными складскими операциями.
2. Экспортируйте фасад проверки остатков `InventoryChecker`.
3. Создайте модуль `BillingModule`, принимающий интерфейс.
4. Проверьте запрет прямых манипуляций со складскими таблицами.

## Код решения

**`modular_schema_isolation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Публичный контракт модуля Inventory
type InventoryChecker interface {
	CheckStock(ctx context.Context, sku string) (int, error)
}

// Реализация модуля Inventory (скрывает свои таблицы)
type inventoryModuleImpl struct {
	stockTable map[string]int // Имитация внутренней таблицы inventory.items
}

func (m *inventoryModuleImpl) CheckStock(ctx context.Context, sku string) (int, error) {
	return m.stockTable[sku], nil
}

// Модуль Billing: не имеет доступа к stockTable!
type BillingModule struct {
	inventory InventoryChecker
}

func NewBillingModule(inv InventoryChecker) *BillingModule {
	return &BillingModule{inventory: inv}
}

func (b *BillingModule) GenerateInvoice(ctx context.Context, sku string) (string, error) {
	// Доступ к остаткам строго через интерфейсный фасад
	count, err := b.inventory.CheckStock(ctx, sku)
	if err != nil || count <= 0 {
		return "", fmt.Errorf("item out of stock")
	}
	return "INV-BILLED-OK", nil
}

func TestModularSchemaIsolation(t *testing.T) {
	inv := &inventoryModuleImpl{stockTable: map[string]int{"sku-ssd-1tb": 15}}
	billing := NewBillingModule(inv)

	invNum, err := billing.GenerateInvoice(context.Background(), "sku-ssd-1tb")
	if err != nil || invNum != "INV-BILLED-OK" {
		t.Fatalf("Ошибка генерации инвойса: %v", err)
	}

	fmt.Println("Изоляция таблиц модульного монолита успешно подтверждена:")
	fmt.Printf("  • Инвойс сгенерирован: %s\n", invNum)
	fmt.Println("  • Модуль Billing не имеет доступа к таблицам Inventory и общается строго через интерфейс")
}
```

## Под капотом

В PostgreSQL для физического запрета межмодульных запросов создают разные роли пользователей базы данных (`billing_user` и `inventory_user`). Каждому пользователю выдаются права `GRANT SELECT/INSERT` строго на его схему, делая прямые межсхемные JOIN невозможными на уровне прав СУБД.

## Подводные камни

Использовать единую транзакцию БД на таблицы обоих модулей: это нарушает границы автономии и заблокирует таблицы при разделении базы на две физические БД.

## На собеседовании

**Вопрос с собеседования:** «Как объединить данные из двух модулей (Users и Orders) для сложного аналитического отчета в модульном монолите без JOIN?»
**Ответ:** Для операционной аналитики (OLAP) данные реплицируются в отдельную аналитическую базу (ClickHouse, Data Warehouse) через Change Data Capture (Debezium/Kafka). Для простых операций на чтение используется паттерн Composition: бэкенд запрашивает пачку заказов, извлекает уникальные `UserIDs`, делает параллельный батч-запрос `GetUsersByIDs()` и объединяет данные в памяти сервиса.
