# Методы поведения доменных сущностей (Domain Entities): инкапсуляция правил и защита статусов

## Условие

**Domain Entities**: Создайте богатые доменные объекты с поведением (методами), а не просто структуры с данными. Например, `Order.CanBeCancelled() bool`, `Order.ApplyDiscount(percent float64)`.

## Теория

Богатые сущности в Domain-Driven Design:
- Сущность отличается от объекта-значения наличием уникального **идентификатора (Identity)**, который остается неизменным на протяжении всей жизни объекта.
- **Поведение внутри сущности:**
  - `Order.CanBeCancelled() bool`: проверяет, не был ли заказ уже передан курьеру.
  - `Order.ApplyDiscount(percent)`: применяет скидку, проверяя, что скидка не превышает максимальный порог (например 50%) и заказ еще не оплачен.
- Если вынести эти проверки в `OrderHelper` или `OrderService`, правила бизнеса размазываются, порождая баги дублирования логики.

## Решение по шагам

1. Создайте сущность `OrderEntity` со статусами.
2. Реализуйте метод `CanBeCancelled` на основе жизненного цикла.
3. Реализуйте бизнес-метод `Cancel` с проверкой инвариантов.
4. Верифицируйте корректную смену статуса заказа.

## Код решения

**`domain_entity_methods_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type OrderDeliveryStatus string

const (
	StatusCreated   OrderDeliveryStatus = "CREATED"
	StatusInTransit OrderDeliveryStatus = "IN_TRANSIT"
	StatusDelivered OrderDeliveryStatus = "DELIVERED"
	StatusCancelled OrderDeliveryStatus = "CANCELLED"
)

type DomainOrderEntity struct {
	id     string
	status OrderDeliveryStatus
	cost   float64
}

func NewDomainOrder(id string, cost float64) *DomainOrderEntity {
	return &DomainOrderEntity{id: id, status: StatusCreated, cost: cost}
}

func (o *DomainOrderEntity) CanBeCancelled() bool {
	// Отменить заказ можно ТОЛЬКО если он еще не передан в доставку
	return o.status == StatusCreated
}

func (o *DomainOrderEntity) Cancel() error {
	if !o.CanBeCancelled() {
		return errors.New("cannot cancel order in current state")
	}
	o.status = StatusCancelled
	return nil
}

func (o *DomainOrderEntity) SetInTransit() {
	o.status = StatusInTransit
}

func TestDomainEntityMethods(t *testing.T) {
	order := NewDomainOrder("ord-rich-42", 5000.0)

	if !order.CanBeCancelled() {
		t.Fatal("Новый заказ должен быть доступен для отмены")
	}

	// Переводим в доставку
	order.SetInTransit()

	if order.CanBeCancelled() {
		t.Fatal("Заказ в пути не может быть отменен!")
	}

	err := order.Cancel()
	if err == nil {
		t.Fatal("Ожидалась ошибка отмены заказа в пути")
	}

	fmt.Println("Богатые доменные методы сущности (Domain Entities) подтверждены:")
	fmt.Printf("  • Заказ %s переведен в статус %s\n", order.id, order.status)
	fmt.Println("  • Попытка невалидной отмены заказа надежно заблокирована методом Cancel()")
}
```

## Под капотом

Использование методов с `pointer receiver` `(o *DomainOrderEntity)` гарантирует мутацию состояния конкретного экземпляра в куче без неявного копирования полей структуры.

## Подводные камни

Возвращать указатель на приватное поле структуры наружу: если сущность вернет указатель на слайс `return o.items`, вызывающий код сможет напрямую мутировать элементы слайса в обход методов сущности.

## На собеседовании

**Вопрос с собеседования:** «Как проверять уникальность сущности (например уникальность Email), если доменная сущность не имеет права обращаться к базе данных?»
**Ответ:** Проверка уникальности по всей таблице — это обязанность **Доменного Сервиса (Domain Service)** или слоя **Use Case**, который обращается к `UserRepository.ExistsByEmail(email)`. Сущность отвечает только за свои внутренние инварианты, а доменный сервис координирует правила, затрагивающие множество сущностей.
