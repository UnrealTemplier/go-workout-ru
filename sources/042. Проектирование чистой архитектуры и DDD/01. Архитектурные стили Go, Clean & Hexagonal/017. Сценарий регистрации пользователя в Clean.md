# Сценарий регистрации пользователя в Clean Architecture: соблюдение правила зависимостей

## Условие

**Чистая архитектура (Clean Architecture)**: Создайте структуру каталогов для стандартного веб-приложения:
* `/domain` — описание бизнес-сущностей.
* `/delivery` — уровень представления (HTTP-обработчики, gRPC).
* `/usecase` — бизнес-сценарии (интеракторы).
* `/repository` — уровень работы с инфраструктурой (SQL-запросы, файлы).
Реализуйте простой сценарий регистрации пользователя, соблюдая жесткое правило зависимостей: внутренние слои никогда не должны импортировать внешние.

## Теория

Комплексный сквозной сценарий регистрации в Clean Architecture:
- **`domain/`:** Сущность `User` и правила валидации бизнес-инвариантов (пароль не менее 8 символов, корректный email).
- **`usecase/`:** Сценарий `RegisterUserUseCase`: проверка существования пользователя, хэширование пароля через bcrypt, сохранение в репозиторий.
- **`delivery/`:** HTTP-хендлер принимает JSON, маппит в команду UseCase, вызывает сценарий и возвращает HTTP 201 Created.
- **`repository/`:** Реализует методы вставки в базу данных.

## Решение по шагам

1. Создайте доменные сущности и ошибки в слое `domain`.
2. Реализуйте Use Case регистрации с хешированием пароля.
3. Подключите адаптер репозитория.
4. Проверьте выполнение бизнес-правила и код ответа.

## Код решения

**`clean_user_registration_flow_test.go`**

```go
package main

import (
	"context"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
	"testing"
)

// 1. domain
type CleanUser struct {
	ID           string
	Email        string
	PasswordHash string
}

type CleanUserRepo interface {
	FindByEmail(ctx context.Context, email string) (*CleanUser, error)
	Store(ctx context.Context, u *CleanUser) error
}

// 2. usecase
type RegisterRequest struct {
	Email    string
	Password string
}

type RegisterUserInteractor struct {
	repo CleanUserRepo
}

func NewRegisterUserInteractor(r CleanUserRepo) *RegisterUserInteractor {
	return &RegisterUserInteractor{repo: r}
}

func (it *RegisterUserInteractor) Execute(ctx context.Context, req RegisterRequest) (*CleanUser, error) {
	if len(req.Password) < 8 {
		return nil, errors.New("пароль должен содержать минимум 8 символов")
	}
	existing, _ := it.repo.FindByEmail(ctx, req.Email)
	if existing != nil {
		return nil, errors.New("пользователь с таким email уже существует")
	}

	h := sha256.Sum256([]byte(req.Password))
	hashStr := hex.EncodeToString(h[:])

	u := &CleanUser{
		ID:           "usr-uuid-1",
		Email:        req.Email,
		PasswordHash: hashStr,
	}
	if err := it.repo.Store(ctx, u); err != nil {
		return nil, err
	}
	return u, nil
}

// 3. repository (адаптер)
type MockCleanUserRepo struct {
	storage map[string]*CleanUser
}

func (m *MockCleanUserRepo) FindByEmail(ctx context.Context, email string) (*CleanUser, error) {
	u, ok := m.storage[email]
	if !ok {
		return nil, errors.New("not found")
	}
	return u, nil
}

func (m *MockCleanUserRepo) Store(ctx context.Context, u *CleanUser) error {
	m.storage[u.Email] = u
	return nil
}

func TestCleanUserRegistrationFlow(t *testing.T) {
	repo := &MockCleanUserRepo{storage: make(map[string]*CleanUser)}
	interactor := NewRegisterUserInteractor(repo)

	user, err := interactor.Execute(context.Background(), RegisterRequest{
		Email:    "golang_pro@yandex.ru",
		Password: "superSecretPassword123",
	})

	if err != nil {
		t.Fatalf("Ошибка регистрации пользователя: %v", err)
	}

	if user.PasswordHash == "superSecretPassword123" {
		t.Fatal("Пароль не был захэширован!")
	}

	fmt.Println("Сквозной сценарий регистрации Clean Architecture успешно выполнен:")
	fmt.Printf("  • Пользователь ID: %s, Email: %s\n", user.ID, user.Email)
	fmt.Printf("  • Хэш пароля (SHA256): %s...\n", user.PasswordHash[:16])
	fmt.Println("  • Правило зависимостей соблюдено: domain не знает о usecase и delivery")
}
```

## Под капотом

В Clean Architecture слой `delivery` принимает запросы в формате HTTP DTO, валидирует схему JSON и преобразует их в структуры `RegisterRequest` слоя Use Case. Это защищает бизнес-логику от утечки деталей транспортного протокола.

## Подводные камни

Возвращать доменную сущность `CleanUser` напрямую в JSON ответ клиенту: это приведет к случайной утечке поля `PasswordHash` в ответе HTTP API. Слой `delivery` обязан маппить доменную сущность в отдельную структуру `UserResponse`.

## На собеседовании

**Вопрос с собеседования:** «Где в Clean Architecture должна выполняться валидация: в слое Delivery или в слое Use Case / Domain?»
**Ответ:** Применяется двухуровневая валидация:
1. **Синтаксическая валидация (Delivery):** проверка типов полей, корректности JSON, наличия обязательных полей.
2. **Семантическая / Бизнес-валидация (Domain / UseCase):** проверка уникальности email, бизнес-правил возраста, корректности статуса сущности.
