# Организация по фичам (Package by Feature): изоляция доменов и высокая связность

## Условие

**Организация по фичам (Package by Feature)**: Перепишите сервис заметок так, чтобы код был сгруппирован не по слоям, а по фичам: папка `notes/` содержит и хэндлер, и сервис, и репозиторий для заметок. Сравните с Package by Layer.

### Исходная формулировка

Спроектируй **CRUD-сервис на одном пакете**: `main.go`, `handlers.go`, `models.go`, `db.go`. Все в `package main`. Покажи, почему это работает для 100 строк, но ломается при росте.

## Теория

Принцип высокой связности (High Cohesion, Low Coupling):
- **Package by Feature (Вертикальные срезы):**
  - Папка `notes/` содержит все, что относится к заметкам: `note.go` (модель), `service.go` (логика), `repository.go` (БД), `handler.go` (HTTP).
  - Папка `users/` содержит все компоненты пользователя.
- **Главное преимущество:**
  - Изменение фичи локализовано в одной папке!
  - Простота удаления или рефакторинга: если функционал заметок больше не нужен, удаляется одна папка `notes/` без поиска хвостов по 5 слоям.
  - Идеально для масштабирования продуктовых команд.

## Решение по шагам

1. Создайте изолированный пакет `notes` со всеми компонентами.
2. Инкапсулируйте внутренние детали хранения внутри пакета.
3. Экспортируйте наружу только фасад сервиса.
4. Проверьте независимость фичи от других частей приложения.

## Код решения

**`package_by_feature_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Моделирование структуры notes/feature.go
type NoteFeature struct {
	store map[string]string
}

func NewNoteFeature() *NoteFeature {
	return &NoteFeature{store: make(map[string]string)}
}

// Слой UseCase + Repo внутри одного пакета фичи
func (f *NoteFeature) Create(ctx context.Context, key, val string) error {
	f.store[key] = val
	return nil
}

func (f *NoteFeature) Get(ctx context.Context, key string) (string, bool) {
	val, ok := f.store[key]
	return val, ok
}

func TestPackageByFeature(t *testing.T) {
	notes := NewNoteFeature()
	ctx := context.Background()

	_ = notes.Create(ctx, "feature-arch", "High Cohesion: все файлы фичи в одной папке")
	val, ok := notes.Get(ctx, "feature-arch")

	if !ok || val == "" {
		t.Fatal("Фича заметок не сохранила данные")
	}

	fmt.Println("Организация по фичам (Package by Feature) успешно подтверждена:")
	fmt.Printf("  • Доменная фича 'Notes' полностью инкапсулирована\n")
	fmt.Printf("  • Значение: %s\n", val)
	fmt.Println("  • Удаление фичи из кодовой базы сводится к удалению одной папки notes/")
}
```

ℹ️ Инкапсуляция сущности, логики и персистентности внутри пакета фичи

## Под капотом

Package by Feature уменьшает когнитивную нагрузку на разработчика (Cognitive Load). В Go область видимости идентификаторов с маленькой буквы (`unexported`) ограничена пакетом. В Package by Feature вы можете скрыть методы репозитория от внешнего мира, оставив их приватными для пакета фичи.

## Подводные камни

Попытка расшарить приватные структуры между фичами через взаимный импорт: если `users` начнет импортировать `notes`, а `notes` — `users`, проект не скомпилируется из-за `import cycle`.

## На собеседовании

**Вопрос с собеседования:** «Как в архитектуре Package by Feature организовать связь между заказами (Orders) и пользователями (Users) без циклического импорта?»
**Ответ:** Связь организуется через слабую связанность по идентификаторам (`UserID int64` в структуре заказа, а не ссылка на объект `*User`), либо через доменные события (Domain Events) в шине событий, либо через вынесение общих контрактов в независимый слой интерфейсов.
