# Архитектура вертикальных срезов (Vertical Slice Architecture): группировка по сценариям фичи

## Условие

Реализуй **Vertical Slice Architecture**: не разделяй по слоям, а по **фичам**: `features/user/create/`, `features/user/get/`, `features/order/create/`. Каждый slice содержит handler, service, repository, model. Покажи, что добавление фичи = добавление папки, не изменение 10 файлов.

## Теория

Концепция Vertical Slice Architecture (Джимми Богард):
- Вместо горизонтального расслоения (слои через всё приложение) система разрезается **вертикально** по каждому сценарию использования (Use Case).
- **Структура сценария `features/user/create/`:**
  - `command.go`: DTO входящих параметров.
  - `handler.go`: HTTP точка входа.
  - `logic.go`: бизнес-правила создания пользователя.
  - `db.go`: SQL запрос на вставку.
- **Преимущества:**
  - Каждый срез оптимизируется индивидуально (для простого чтения не нужен сложный доменный оверхед).
  - Никаких конфликтов при слиянии веток Git: разные разработчики работают в абсолютно изолированных папках срезов.

## Решение по шагам

1. Создайте срез создания заказа `CreateOrderSlice`.
2. Объедините модель, логику и хранилище внутри единого среза.
3. Продемонстрируйте автономность выполнения команды.
4. Верифицируйте изоляцию кода от других сценариев системы.

## Код решения

**`vertical_slice_architecture_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Вертикальный срез: features/order/create
type CreateOrderCommand struct {
	UserID string
	Amount float64
}

type CreateOrderResult struct {
	OrderID string
	Status  string
}

type CreateOrderHandler struct {
	// Внутренний специализированный репозиторий только для этой команды
	saveFn func(ctx context.Context, cmd CreateOrderCommand) (string, error)
}

func (h *CreateOrderHandler) Handle(ctx context.Context, cmd CreateOrderCommand) (*CreateOrderResult, error) {
	if cmd.Amount <= 0 {
		return nil, fmt.Errorf("amount must be positive")
	}
	id, err := h.saveFn(ctx, cmd)
	if err != nil {
		return nil, err
	}
	return &CreateOrderResult{OrderID: id, Status: "CONFIRMED"}, nil
}

func TestVerticalSliceArchitecture(t *testing.T) {
	handler := &CreateOrderHandler{
		saveFn: func(ctx context.Context, cmd CreateOrderCommand) (string, error) {
			return "ord-slice-101", nil
		},
	}

	res, err := handler.Handle(context.Background(), CreateOrderCommand{UserID: "usr-77", Amount: 3400.0})
	if err != nil || res.OrderID != "ord-slice-101" {
		t.Fatalf("Ошибка в срезе создания заказа: %v", err)
	}

	fmt.Println("Архитектура вертикальных срезов (Vertical Slice) успешно подтверждена:")
	fmt.Printf("  • Заказ создан: ID=%s, Статус=%s\n", res.OrderID, res.Status)
	fmt.Println("  • Добавление нового сценария требует создания только новой папки features/<feature>/")
}
```

## Под капотом

В Vertical Slice Architecture исключаются абстракции «ради абстракций». Для операций чтения (Queries) срез может выполнять прямой SQL запрос через `sqlx` или `pgx` прямо в DTO ответа без прохождения через репозиторий и доменные сущности, что обеспечивает максимальную производительность (High Throughput).

## Подводные камни

Дублирование общего кода (DRY violation): срезы могут начать копировать одинаковые валидаторы. Базовые утилиты и доменные правила разделяемого ядра (Shared Kernel) выносят в общий пакет, не усложняя срезы.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие архитектуры вертикальных срезов от CQRS?»
**Ответ:** CQRS разделяет операции изменения (Commands) и чтения (Queries) на уровне моделей. Vertical Slice развивает эту идею дальше, организуя файловую структуру и весь пайплайн выполнения вокруг каждого отдельного сценария как независимой микропрограммы.
