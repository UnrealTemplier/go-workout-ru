# Плоская структура проекта (Flat Layout) для легковесных микросервисов и CLI-утилит

## Условие

**Плоская структура (Flat Layout) для микро-сервисов**: Напишите небольшую CLI-утилиту, структура которой намеренно сделана плоской: все `.go` файлы лежат в корне проекта (без папок `pkg`, `internal`, `cmd`). Обсудите, когда это лучший выбор, а когда превратится в кошмар.

### Исходная формулировка

**Плоская структура (Flat Layout) для микро-сервисов**: Напишите небольшую CLI-утилиту, структура которой состоит из одного пакета `main` и нескольких файлов в корне директории (например, `main.go`, `config.go`, `db.go`). Опишите в комментариях границы применимости такой структуры: в какой момент плоская структура становится хаосом и требует разделения на слои.

## Теория

Плоская структура (Flat Layout) в философии Go:
- Все `.go` файлы находятся в одном пакете в корне репозитория (например, `package main`).
- **Когда это лучший выбор:**
  - Небольшие CLI-утилиты (до 1000–2000 строк кода), сервисы-агенты, лямбда-функции (AWS Lambda, Yandex Cloud Functions).
  - Отсутствие оверхеда на иерархию папок, круговые импорты (Circular Imports) невозможны физически, так как весь проект компилируется как единый пакет.
- **Когда это превращается в кошмар:**
  - При росте кодовой базы свыше 10 файлов: размываются границы ответственности, глобальное пространство имен засоряется, усложняется командная разработка и разграничение приватного API.

## Решение по шагам

1. Создайте доменную структуру конфигурации и команду CLI в одном пространстве имен.
2. Реализуйте функционал утилиты без дробления на подпакеты.
3. Продемонстрируйте исполнение и модульное тестирование плоской структуры.
4. Верифицируйте корректность работы без лишних абстракций.

## Код решения

**`flat_layout_cli_test.go`**

```go
package main

import (
	"bytes"
	"flag"
	"fmt"
	"strings"
	"testing"
)

// Конфигурация и логика в одном плоском пространстве имен пакета main
type CLIApp struct {
	Greeting string
	Target   string
	Uppercase bool
}

func (app *CLIApp) Run(out *bytes.Buffer) error {
	msg := fmt.Sprintf("%s, %s!", app.Greeting, app.Target)
	if app.Uppercase {
		msg = strings.ToUpper(msg)
	}
	_, err := out.WriteString(msg)
	return err
}

func TestFlatLayoutCLI(t *testing.T) {
	app := CLIApp{
		Greeting:  "Привет",
		Target:    "Gopher",
		Uppercase: true,
	}

	var buf bytes.Buffer
	if err := app.Run(&buf); err != nil {
		t.Fatalf("Ошибка выполнения CLI утилиты: %v", err)
	}

	expected := "ПРИВЕТ, GOPHER!"
	if buf.String() != expected {
		t.Fatalf("Ожидалось %q, получено %q", expected, buf.String())
	}

	fmt.Println("Плоская структура проекта (Flat Layout) успешно подтверждена:")
	fmt.Printf("  • Результат CLI: %s\n", buf.String())
	fmt.Println("  • Все файлы скомпилированы в package main без искусственных папок pkg/cmd")
}
```

ℹ️ Реализация CLI-утилиты в плоской структуре без избыточных пакетов

## Под капотом

Компилятор `compile` компилирует все `.go` файлы одного пакета одновременно, объединяя их символы в единый AST (Abstract Syntax Tree). В плоской структуре компиляция выполняется максимально быстро, так как компилятору не требуется загружать промежуточные `.a` архивные файлы зависимых пакетов.

## Подводные камни

Использовать Flat Layout для крупных enterprise-проектов: все функции и структуры видны друг другу, программисты начинают вызывать приватную логику баз данных напрямую из HTTP-хендлеров, порождая спагетти-код.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go не рекомендуется преждевременно дробить проект на десятки микропакетов (Over-engineering)?»
**Ответ:** Преждевременная пакетизация в Go наказывается ошибками `import cycle not allowed`. В Go запрещены циклические зависимости. Если разделить логику не по естественным доменным границам, а механически, разработчик упрется в циклические импорты и будет вынужден создавать бесполезные пакеты-свалки (`common/`, `utils/`). Идиоматичный подход Go — начинать с плоской структуры и выделять пакеты только по мере роста независимых абстракций.
