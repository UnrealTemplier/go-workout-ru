# Инверсия зависимостей в стиле Go: размещение интерфейса в пакете бизнес-логики

## Условие

**Принцип инверсии зависимостей (DIP в Go)**: Интерфейсы в Go определяются там, где они *используются*, а не там, где реализуются! Перенеси интерфейс `UserRepository` из пакета базы данных в пакет бизнес-логики (`service`). Пакет `service` не должен ничего знать о пакете `postgres`.

## Теория

Разница между Java-style DIP и Go-style DIP:
- **Java/C# традиция:** Интерфейс создается рядом с реализацией (`package postgres; public interface UserRepository`). Это привязывает пользователя к поставщику!
- **Идиома Go:** Интерфейс создается **рядом с потребителем** (`package service; type UserRepository interface`).
- Пакет `service` объявляет **только те методы, которые реально использует**.
- Пакет `postgres` может реализовывать 50 методов, но если сервису нужен только `GetByID`, интерфейс состоит из ровно одного метода!

## Решение по шагам

1. Создайте пакет сервиса с узким интерфейсом потребителя.
2. Создайте пакет базы данных с широким репозиторием.
3. Продемонстрируйте автоматическое удовлетворение интерфейса без взаимного импорта.
4. Верифицируйте изоляцию компиляции.

## Код решения

**`go_style_dip_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Пакет: service (Потребитель)
type UserGetter interface {
	GetUser(ctx context.Context, id string) (string, error)
}

type UserProfileService struct {
	getter UserGetter
}

func NewUserProfileService(g UserGetter) *UserProfileService {
	return &UserProfileService{getter: g}
}

func (s *UserProfileService) RenderProfile(ctx context.Context, id string) (string, error) {
	name, err := s.getter.GetUser(ctx, id)
	if err != nil {
		return "", err
	}
	return "Профиль пользователя: " + name, nil
}

// Пакет: postgres (Реализация имеет 10 методов, но сервису нужен 1)
type FullPostgresRepository struct{}

func (p *FullPostgresRepository) GetUser(ctx context.Context, id string) (string, error) {
	return "Дмитрий Ковалев", nil
}

func (p *FullPostgresRepository) DeleteUser(ctx context.Context, id string) error { return nil }
func (p *FullPostgresRepository) UpdatePassword(ctx context.Context, id, pass string) error {
	return nil
}

func TestGoStyleDIP(t *testing.T) {
	db := &FullPostgresRepository{}
	svc := NewUserProfileService(db)

	res, err := svc.RenderProfile(context.Background(), "usr-99")
	if err != nil || res != "Профиль пользователя: Дмитрий Ковалев" {
		t.Fatalf("Ошибка рендеринга профиля: %v", err)
	}

	fmt.Println("Инверсия зависимостей в стиле Go успешно подтверждена:")
	fmt.Printf("  • Результат: %s\n", res)
	fmt.Println("  • Service объявил интерфейс UserGetter на 1 метод")
	fmt.Println("  • PostgresRepository содержит лишние методы, но автоматически удовлетворяет интерфейсу!")
}
```

ℹ️ Неявное удовлетворение узкого интерфейса потребителя широким репозиторием

## Под капотом

Компилятор Go генерирует таблицу виртуальных методов (`itab`) в момент присваивания конкретного типа интерфейсной переменной: он сопоставляет методы структуры и методы интерфейса. Если совпадение найдено, в рантайме вызов идет через быстрый косвенный вызов функции по указателю.

## Подводные камни

Экспортировать интерфейс из пакета реализации (`package postgres; type Repo interface`): это заставляет всех пользователей импортировать пакет `postgres`, порождая лишние зависимости от драйверов БД.

## На собеседовании

**Вопрос с собеседования:** «Какое золотое правило Роб Пайк сформулировал относительно интерфейсов в Go?»
**Ответ:** «Do not design with interfaces, discover them» (Не проектируйте систему сразу интерфейсами — открывайте их по мере необходимости). Интерфейсы должны появляться тогда, когда возникает реальная потребность в полиморфизме или мокировании, а не заранее ради абстрактной красоты.
