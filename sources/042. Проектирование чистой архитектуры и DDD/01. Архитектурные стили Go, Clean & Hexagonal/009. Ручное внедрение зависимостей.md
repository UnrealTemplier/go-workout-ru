# Ручное внедрение зависимостей (Manual Dependency Injection): конструкторы NewService без магии рефлексии

## Условие

**Dependency Injection**: Реализуйте ручную инъекцию зависимостей через конструкторы (`NewService(repo Repository)`) без использования DI-фреймворков. Поймите, почему в Go не любят рефлексию.

## Теория

Философия Dependency Injection в Go:
- Во многих языках (Java Spring, C# .NET) доминируют сложные DI-контейнеры с рефлексией (Reflection-based magic).
- **Почему сообщество Go отвергает магические DI-фреймворки:**
  1. Ошибки конфигурации связей падают в рантайме при старте пода, а не ловятся компилятором.
  2. Рефлексия замедляет холодный старт и усложняет трассировку графа вызовов.
  3. Навигация в IDE (Jump to Definition) перестает работать.
- **Идиома Go — ручной DI (Explicit Constructor Injection):**
  Все зависимости явно передаются аргументами в функции-конструкторы `New<Entity>(deps...)`. Ошибки типов выявляются мгновенно при компиляции!

## Решение по шагам

1. Создайте конструкторы `NewRepository`, `NewService`, `NewHandler`.
2. Соберите граф зависимостей в функции `SetupApp`.
3. Убедитесь, что все зависимости строго типизированы.
4. Продемонстрируйте чистоту и прозрачность передачи зависимостей.

## Код решения

**`manual_di_constructors_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type Storage interface {
	SaveData(k, v string)
}

type MemoryStore struct {
	m map[string]string
}

func NewMemoryStore() *MemoryStore {
	return &MemoryStore{m: make(map[string]string)}
}

func (s *MemoryStore) SaveData(k, v string) {
	s.m[k] = v
}

type OrderService struct {
	storage Storage
}

// Явный конструктор: все зависимости видны в сигнатуре
func NewOrderService(storage Storage) *OrderService {
	if storage == nil {
		panic("storage dependency is required")
	}
	return &OrderService{storage: storage}
}

func (s *OrderService) PlaceOrder(id string) {
	s.storage.SaveData(id, "placed")
}

func TestManualDIConstructors(t *testing.T) {
	// Ручная сборка (Composition Root) в main.go
	store := NewMemoryStore()
	svc := NewOrderService(store)

	svc.PlaceOrder("order-999")

	if store.m["order-999"] != "placed" {
		t.Fatal("Заказ не сохранен")
	}

	fmt.Println("Ручное внедрение зависимостей (Manual DI) успешно верифицировано:")
	fmt.Printf("  • Заказ order-999 успешно сохранен в хранилище\n")
	fmt.Println("  • Граф собран явно: Store -> OrderService без рефлексии и рантайм-контейнеров")
}
```

## Под капотом

При ручном внедрении зависимостей все указатели на интерфейсные таблицы и структуры связываются статически. Компилятор Go может применить инлайнинг (Inlining) функций-конструкторов и оптимизацию побега (Escape Analysis), размещая структуры на стеке там, где это возможно.

## Подводные камни

Использовать конструкторы с 10+ аргументами: это признак нарушения принципа единственной ответственности (SRP). Если сервису нужно 10 зависимостей, его следует разделить на несколько более узких сервисов.

## На собеседовании

**Вопрос с собеседования:** «Какое отношение в BigTech к генераторам DI-кода наподобие Google Wire или Uber Dig?»
**Ответ:** К библиотекам с рантайм-рефлексией (Uber Dig) относятся настороженно. Библиотеку **Google Wire** уважают, потому что она генерирует обычный чистый Go-код во время сборки (`compile-time code generation`). В кодовой базе получается тот же самый явный вызов конструкторов, но написанный автоматически.
