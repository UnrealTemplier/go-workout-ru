# Модульный монолит (Modular Monolith): приватные internal-пакеты и публичные контракты модулей

## Условие

**Modular Monolith**: Разделите монолит на независимые модули (`/internal/users`, `/internal/orders`), которые общаются только через публичные интерфейсы, а не импортируют внутренние структуры друг друга.

## Теория

Инкапсуляция модулей в модульном монолите Go:
- Каждый модуль имеет собственную структуру:
  - `internal/users/internal/`: скрытые детали реализации (SQL-запросы, таблицы, DTO).
  - `internal/users/public.go`: публичный интерфейс `Service` и экспортируемые структуры, через которые модуль взаимодействует с внешним миром.
- **Запрет глубокого связывания:** Модуль `orders` не имеет права импортировать приватные репозитории `internal/users/internal/storage`. Компилятор Go предотвращает это на уровне сборки!

## Решение по шагам

1. Создайте публичный фасад модуля пользователей `UserServiceFacade`.
2. Сокройте внутренние структуры хранения в приватной области.
3. Продемонстрируйте вызов только через открытый интерфейсный контракт.
4. Верифицируйте изоляцию внутренних инвариантов модуля.

## Код решения

**`modular_monolith_facade_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Публичный контракт модуля: internal/users/public.go
type UserPublicDTO struct {
	ID   string
	Role string
}

type UserModuleAPI interface {
	GetUserPublicInfo(ctx context.Context, id string) (*UserPublicDTO, error)
}

// Приватная реализация модуля
type usersInternalService struct {
	secretData map[string]string // Пароли и паспортные данные скрыты внутри модуля!
}

func (s *usersInternalService) GetUserPublicInfo(ctx context.Context, id string) (*UserPublicDTO, error) {
	return &UserPublicDTO{ID: id, Role: "VIP_CUSTOMER"}, nil
}

// Потребитель: модуль internal/orders
type OrdersCoordinator struct {
	usersAPI UserModuleAPI
}

func (c *OrdersCoordinator) CanPlaceOrder(ctx context.Context, userID string) bool {
	info, err := c.usersAPI.GetUserPublicInfo(ctx, userID)
	if err != nil {
		return false
	}
	return info.Role == "VIP_CUSTOMER"
}

func TestModularMonolithFacade(t *testing.T) {
	usersService := &usersInternalService{secretData: map[string]string{"u-77": "passport-12345"}}
	ordersModule := &OrdersCoordinator{usersAPI: usersService}

	allowed := ordersModule.CanPlaceOrder(context.Background(), "u-77")
	if !allowed {
		t.Fatal("Пользователь должен иметь право создания заказа")
	}

	fmt.Println("Инкапсуляция модульного монолита успешно подтверждена:")
	fmt.Println("  • Orders общается с Users строго через публичный интерфейс UserModuleAPI")
	fmt.Println("  • Приватные поля (паспортные данные, SQL схемы) надежно скрыты внутри модуля Users")
}
```

## Под капотом

Поддиректория `internal` внутри любого каталога Go изолирует видимость: пакет `a/b/internal/c` может импортироваться только кодом, находящимся внутри дерева `a/b`. Код из `a/d` при попытке импорта получит фатальную ошибку компиляции.

## Подводные камни

Экспортировать из публичного фасада модуля структуры GORM или SQL-модели: любая миграция БД сломает контракт с соседними модулями. Экспортировать разрешено только чистые DTO.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить случайное добавление запрещенных межпакетных импортов в большом проекте на Go?»
**Ответ:** Используют специализированные линтеры архитектуры в CI/CD:
1. `go-cleanarch` — валидирует соблюдение кругов Clean Architecture.
2. `depguard` (в составе `golangci-lint`) — запрещает импорт конкретных пакетов в заданных каталогах.
3. `import-boss` — объявляет правила разрешенных зависимостей прямо в файлах `README.md` или `.import-restrictions`.
