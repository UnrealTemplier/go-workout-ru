# Направление зависимостей в слоистой архитектуре: принцип обращения зависимостей внутрь

## Условие

Раздели на **слои (layered architecture)**: `handlers/` (HTTP), `services/` (бизнес-логика), `repositories/` (данные), `models/` (сущности). Каждый слой зависит только от нижележащего. Покажи направление зависимостей (внутрь).

## Теория

Принцип центростремительных зависимостей (Inward Dependency Rule):
- В классической слоистой архитектуре зависимости направлены внутрь ядра:
  $$\text{Handlers} \longrightarrow \text{Services} \longrightarrow \text{Repositories} \longrightarrow \text{Models (Core)}$$
- `Models` — не зависит ни от чего (чистые типы Go).
- `Repositories` — зависит от `Models`.
- `Services` — зависит от `Repositories` и `Models`.
- `Handlers` — зависит от `Services` и `Models`.
- Никакой внутренний слой никогда не должен импортировать внешний!

## Решение по шагам

1. Создайте независимое ядро данных `Product`.
2. Создайте слой хранения `ProductRepository`.
3. Создайте бизнес-слой `ProductService`, рассчитывающий налог.
4. Продемонстрируйте вызов через транспортный фасад и проверьте инварианты.

## Код решения

**`inward_dependency_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Слой 1: Models (Ядро, нулевые внешние зависимости)
type Product struct {
	ID       string
	BaseCost float64
}

// Слой 2: Repositories
type ProductCatalog interface {
	Find(id string) (Product, error)
}

type CatalogStub struct{}

func (c *CatalogStub) Find(id string) (Product, error) {
	return Product{ID: id, BaseCost: 1000.0}, nil
}

// Слой 3: Services (Зависит от Catalog и Product)
type PricingService struct {
	catalog ProductCatalog
	taxRate float64
}

func (s *PricingService) CalculateTotal(id string) (float64, error) {
	p, err := s.catalog.Find(id)
	if err != nil {
		return 0, err
	}
	return p.BaseCost * (1.0 + s.taxRate), nil
}

func TestInwardDependency(t *testing.T) {
	catalog := &CatalogStub{}
	pricing := &PricingService{catalog: catalog, taxRate: 0.20} // 20% НДС

	total, err := pricing.CalculateTotal("sku-apple-macbook")
	if err != nil || total != 1200.0 {
		t.Fatalf("Ошибка расчета стоимости: total=%v, err=%v", total, err)
	}

	fmt.Println("Направление зависимостей внутрь успешно продемонстрировано:")
	fmt.Printf("  • Товар: sku-apple-macbook, Базовая цена: 1000.0, Итого с налогом: %.2f\n", total)
	fmt.Println("  • Models не импортирует ни один слой; PricingService зависит от интерфейса Catalog")
}
```

## Под капотом

Соблюдение направления зависимостей внутрь позволяет компилятору Go собирать пакеты параллельно. Компилятор строит направленный ациклический граф (DAG). Если зависимости запутаны, время сборки резко возрастает, так как компилятор не может распараллелить сборку на ядрах CPU.

## Подводные камни

Импортировать пакет `handlers` в пакет `services` (например, чтобы переиспользовать константу или структуру ответа): это мгновенно создает архитектурную дыру и риск циклического импорта.

## На собеседовании

**Вопрос с собеседования:** «Почему в Clean Architecture Uncle Bob слой Use Cases не должен знать о формате HTTP (например r.Header, status codes)?»
**Ответ:** Потому что бизнес-сценарий (Use Case) должен выполняться одинаково независимо от источника вызова: пришел ли запрос из HTTP REST API, gRPC вызова, сообщения Kafka или CLI консоли. Если бизнес-слой привязан к `*http.Request`, переиспользовать его в CLI или Kafka consumer будет невозможно.
