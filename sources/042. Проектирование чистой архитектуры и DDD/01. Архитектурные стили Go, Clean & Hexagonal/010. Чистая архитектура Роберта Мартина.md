# Чистая архитектура Роберта Мартина (Clean Architecture): Entities, Use Cases, Adapters и Drivers

## Условие

Реализуй **Clean Architecture** (Uncle Bob): слои `entities` → `usecases` → `interface_adapters` → `frameworks_drivers`. В Go: `domain/` (entities, interfaces), `usecase/` (interactors), `delivery/http/` (handlers), `repository/postgres/` (DB). Покажи, что `domain` не зависит ни от чего.

## Теория

Концентрические круги Чистой Архитектуры Uncle Bob:
1. **Entities (Предметная область):** Бизнес-правила масштаба предприятия, чистые структуры и валидаторы. Ноль внешних импортов.
2. **Use Cases (Сценарии использования):** Интеракторы бизнес-процессов (например, `RegisterUserUseCase`).
3. **Interface Adapters:** Адаптеры представления и хранения данных (HTTP контроллеры, презентеры, репозитории).
4. **Frameworks & Drivers:** Внешний мир (веб-фреймворк Gin/Chi, PostgreSQL, Kafka, Redis).
- **Главный инвариант:** Ничто из внутреннего круга не знает о внешнем круге!

## Решение по шагам

1. Создайте сущность `Order` в слое `domain`.
2. Напишите сценарий `PayOrderUseCase` в слое `usecase`.
3. Реализуйте интерфейс платежного шлюза через адаптер `PaymentAdapter`.
4. Верифицируйте независимость доменного слоя от инфраструктуры.

## Код решения

**`clean_architecture_uncle_bob_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

// 1. Entities (Круг 1 - Ядро)
type Order struct {
	ID     string
	Amount float64
	Paid   bool
}

func (o *Order) MarkPaid() error {
	if o.Paid {
		return errors.New("order is already paid")
	}
	if o.Amount <= 0 {
		return errors.New("invalid order amount")
	}
	o.Paid = true
	return nil
}

// 2. Use Cases (Круг 2 - Сценарии)
type PaymentGateway interface {
	Charge(ctx context.Context, amount float64) error
}

type OrderRepository interface {
	GetOrder(ctx context.Context, id string) (*Order, error)
	SaveOrder(ctx context.Context, o *Order) error
}

type PayOrderUseCase struct {
	orders  OrderRepository
	gateway PaymentGateway
}

func NewPayOrderUseCase(orders OrderRepository, gateway PaymentGateway) *PayOrderUseCase {
	return &PayOrderUseCase{orders: orders, gateway: gateway}
}

func (uc *PayOrderUseCase) Execute(ctx context.Context, orderID string) error {
	order, err := uc.orders.GetOrder(ctx, orderID)
	if err != nil {
		return err
	}
	if err := uc.gateway.Charge(ctx, order.Amount); err != nil {
		return fmt.Errorf("charge failed: %w", err)
	}
	if err := order.MarkPaid(); err != nil {
		return err
	}
	return uc.orders.SaveOrder(ctx, order)
}

// 3 & 4. Adapters & Drivers
type MockOrderStore struct {
	order *Order
}

func (m *MockOrderStore) GetOrder(ctx context.Context, id string) (*Order, error) {
	return m.order, nil
}
func (m *MockOrderStore) SaveOrder(ctx context.Context, o *Order) error {
	m.order = o
	return nil
}

type DummyPaymentDriver struct{}

func (d *DummyPaymentDriver) Charge(ctx context.Context, amount float64) error {
	return nil
}

func TestCleanArchitectureUncleBob(t *testing.T) {
	store := &MockOrderStore{order: &Order{ID: "ord-42", Amount: 2500.0, Paid: false}}
	driver := &DummyPaymentDriver{}

	uc := NewPayOrderUseCase(store, driver)
	if err := uc.Execute(context.Background(), "ord-42"); err != nil {
		t.Fatalf("Ошибка выполнения Use Case: %v", err)
	}

	if !store.order.Paid {
		t.Fatal("Заказ обязан быть помечен как оплаченный")
	}

	fmt.Println("Чистая архитектура (Clean Architecture Uncle Bob) успешно подтверждена:")
	fmt.Printf("  • UseCase PayOrder успешно выполнен для заказа %s\n", store.order.ID)
	fmt.Println("  • Entity Order содержит чистый инвариант MarkPaid() без внешних библиотек")
}
```

## Под капотом

В Clean Architecture вся бизнес-логика сосредоточена внутри сущностей (Rich Domain Model), а Use Case координирует работу сущностей с внешними адаптерами. Это предотвращает возникновение антипаттерна «Анемичная модель предметной области» (Anemic Domain Model).

## Подводные камни

Внедрять Clean Architecture в простые микросервисы-прокси: создание 4 структур данных (DB Model, Entity, UseCase Request, HTTP Response) для каждого эндпоинта превращает разработку в бесконечное написание мапперов без какой-либо практической выгоды.

## На собеседовании

**Вопрос с собеседования:** «Чем отличается Clean Architecture Uncle Bob от Hexagonal Architecture (Ports and Adapters)?»
**Ответ:** Идея одинаковая — изоляция бизнес-ядра от инфраструктуры. Разница в терминологии и степени детализации: Hexagonal оперирует концепцией «внутри гексагона» (Domain) и «снаружи» (Порты и Адаптеры), тогда как Clean Architecture делит внутренности на два строгих слоя: Entities (правила предприятия) и Use Cases (сценарии приложения).
