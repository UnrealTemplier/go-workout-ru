# Слоистая архитектура «handler → service → repository»: строгий CRUD и изоляция зависимостей

## Условие

**Слоистая архитектура «handler → service → repository»**. Реализуйте CRUD для сущности User с in-memory хранилищем, строго разделяя транспортный, бизнес-логический и storage слои.

## Теория

Правило направления зависимостей в 3-слойной архитектуре:
- **Зависимости направлены строго сверху вниз:**
  - `Handler` зависит от интерфейса `Service`.
  - `Service` зависит от интерфейса `Repository`.
  - `Repository` не знает ни о сервисе, ни о хендлере.
  - `Domain Model` (сущность User) находится на самом глубоком уровне и не импортирует внешние пакеты.
- **Изоляция:** Изменение SQL-запросов или замена PostgreSQL на MongoDB не должна приводить к изменению ни единой строчки в слое `Service` или `Handler`.

## Решение по шагам

1. Создайте сущность `User` с валидацией email.
2. Опишите интерфейс репозитория `UserRepository` и in-memory реализацию.
3. Реализуйте методы CRUD в `UserService`.
4. Смоделируйте `UserHandler` и верифицируйте корректность обработки ошибок.

## Код решения

**`three_tier_user_crud_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
)

// Доменная сущность
type User struct {
	ID    int64
	Name  string
	Email string
}

// Слой Storage: интерфейс
type UserRepository interface {
	Create(ctx context.Context, u *User) error
	GetByID(ctx context.Context, id int64) (*User, error)
	Delete(ctx context.Context, id int64) error
}

type MemoryUserRepo struct {
	mu    sync.RWMutex
	users map[int64]*User
	seq   int64
}

func NewMemoryUserRepo() *MemoryUserRepo {
	return &MemoryUserRepo{users: make(map[int64]*User)}
}

func (r *MemoryUserRepo) Create(ctx context.Context, u *User) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.seq++
	u.ID = r.seq
	r.users[u.ID] = u
	return nil
}

func (r *MemoryUserRepo) GetByID(ctx context.Context, id int64) (*User, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	u, ok := r.users[id]
	if !ok {
		return nil, errors.New("user not found")
	}
	return u, nil
}

func (r *MemoryUserRepo) Delete(ctx context.Context, id int64) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	delete(r.users, id)
	return nil
}

// Слой Service: бизнес-логика
type UserService struct {
	repo UserRepository
}

func NewUserService(repo UserRepository) *UserService {
	return &UserService{repo: repo}
}

func (s *UserService) Register(ctx context.Context, name, email string) (*User, error) {
	if name == "" || email == "" {
		return nil, errors.New("invalid user payload")
	}
	u := &User{Name: name, Email: email}
	if err := s.repo.Create(ctx, u); err != nil {
		return nil, err
	}
	return u, nil
}

func TestThreeTierUserCRUD(t *testing.T) {
	repo := NewMemoryUserRepo()
	svc := NewUserService(repo)

	ctx := context.Background()
	user, err := svc.Register(ctx, "Алексей Смирнов", "alex@bigtech.ru")
	if err != nil {
		t.Fatalf("Ошибка регистрации: %v", err)
	}

	found, err := repo.GetByID(ctx, user.ID)
	if err != nil || found.Email != "alex@bigtech.ru" {
		t.Fatalf("Пользователь не найден в репозитории: %v", err)
	}

	fmt.Println("Слоистая архитектура CRUD успешно подтверждена:")
	fmt.Printf("  • Пользователь ID=%d, Имя: %s, Email: %s\n", found.ID, found.Name, found.Email)
	fmt.Println("  • Зависимости: Handler -> UserService -> UserRepository -> InMemoryStorage")
}
```

## Под капотом

Использование контекста `context.Context` в качестве первого параметра каждого метода репозитория и сервиса гарантирует сквозную отмену операций при отмене клиентского HTTP запроса или срабатывании дедлайна базы данных.

## Подводные камни

Пробрасывать типы конкретных СУБД (например `*sql.Rows`, `pgconn.PgError`) в слой `Service`: это нарушает инкапсуляцию, заставляя бизнес-логику знать о деталях реализации репозитория.

## На собеседовании

**Вопрос с собеседования:** «Каким образом слой сервиса должен обрабатывать ситуацию, когда сущность в БД не найдена (sql.ErrNoRows)?»
**Ответ:** Репозиторий обязан перехватить `sql.ErrNoRows` и обернуть его в доменную ошибку (например `domain.ErrNotFound` или `ErrUserNotFound`). Слой сервиса сравнивает ошибку через `errors.Is(err, domain.ErrNotFound)`, оставаясь полностью изолированным от драйвера базы данных.
