# Эволюция модульного монолита в микросервисы: скрытый internal и коммуникация через Event Bus

## Условие

Реализуй **Modular Monolith**: монолит, но с чёткими границами модулей. Каждый модуль имеет свой `internal/` (скрыт от других модулей). Коммуникация только через `pkg/events/` (event bus). Покажи путь к микросервисам: вырезай модуль, добавляй gRPC/HTTP API.

## Теория

Бесшовный переход от Modular Monolith к Microservices:
- Если монолит спроектирован правильно:
  1. Вся персистентность модуля изолирована в собственных таблицах БД.
  2. Входящие вызовы принимаются через чистые интерфейсы.
  3. Исходящие вызовы отправляются как события в `EventBus`.
- **Шаги выноса модуля в независимый микросервис:**
  - Шаг 1: Копируем папку модуля в новый Git-репозиторий.
  - Шаг 2: Заменяем входящий Go-интерфейс на gRPC сервер (`api.proto`).
  - Шаг 3: Заменяем внутрипроцессный `EventBus` на продюсер Kafka.
  - Шаг 4: В исходном монолите подменяем вызовы на gRPC-клиент.
- **Ноль изменений в бизнес-логике домена!**

## Решение по шагам

1. Создайте модуль `BillingModule` с шиной событий.
2. Продемонстрируйте слабую связанность через контракт событий.
3. Смоделируйте адаптер gRPC-транспорта для будущего выноса.
4. Верифицируйте готовность модуля к автономной жизни.

## Код решения

**`monolith_to_microservice_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type InvoiceCreatedEvent struct {
	InvoiceID string
	Amount    float64
}

type EventPublisher interface {
	PublishEvent(ctx context.Context, topic string, payload any) error
}

type BillingService struct {
	events EventPublisher
}

func NewBillingService(events EventPublisher) *BillingService {
	return &BillingService{events: events}
}

func (s *BillingService) CreateInvoice(ctx context.Context, id string, amount float64) error {
	// Бизнес-логика создания инвойса
	evt := InvoiceCreatedEvent{InvoiceID: id, Amount: amount}
	return s.events.PublishEvent(ctx, "invoices", evt)
}

type MockEventPublisher struct {
	published []any
}

func (m *MockEventPublisher) PublishEvent(ctx context.Context, topic string, payload any) error {
	m.published = append(m.published, payload)
	return nil
}

func TestMonolithToMicroservice(t *testing.T) {
	pub := &MockEventPublisher{}
	billing := NewBillingService(pub)

	err := billing.CreateInvoice(context.Background(), "inv-900", 75000.0)
	if err != nil || len(pub.published) != 1 {
		t.Fatalf("Ошибка создания инвойса: %v", err)
	}

	fmt.Println("Готовность к микросервисам (Monolith to Microservice) подтверждена:")
	fmt.Printf("  • Модуль Billing отправляет события через EventPublisher\n")
	fmt.Printf("  • Событие: %+v\n", pub.published[0])
	fmt.Println("  • Для выноса в микросервис достаточно заменить MockEventPublisher на Kafka/NATS продюсер!")
}
```

## Под капотом

Использование интерфейса `EventPublisher` реализует архитектурный шаблон «Порты и Адаптеры». В монолите реализацией служит канал памяти `chan any`, а в распределенной системе — кластер Apache Kafka с сериализацией в Avro или Protobuf.

## Подводные камни

Связывать модули через общие транзакции БД (`BEGIN ... COMMIT` на таблицы двух модулей): при выносе модуля в микросервис ACID транзакция разорвется, и система останется в несогласованном состоянии.

## На собеседовании

**Вопрос с собеседования:** «Что такое паттерн Strangler Fig (Душитель) при миграции монолита на микросервисы?»
**Ответ:** Это стратегия постепенной миграции, при которой функционал монолита не переписывается целиком, а вырезается по одной фиче. На API Gateway трафик к новому микросервису постепенно переключается с монолита (например 10%, 50%, 100%), пока старый код монолита полностью не отомрет.
