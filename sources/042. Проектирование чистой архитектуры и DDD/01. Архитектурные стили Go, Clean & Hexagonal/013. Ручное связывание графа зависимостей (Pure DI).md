# Ручное связывание графа зависимостей (Pure DI): композиция объектов в Composition Root

## Условие

**Dependency Injection (ручная)**. Передавайте зависимости (репозитории, логгер, конфиг) через конструкторы. Запретите глобальные переменные, добейтесь тестируемости.

## Теория

Архитектурный паттерн Composition Root:
- **Composition Root** — это единственная точка входа в приложение (метод `main()` пакета `cmd/`), где создаются все конкретные реализации инфраструктуры и внедряются в бизнес-слои.
- Все остальные пакеты (`service`, `handler`, `domain`) ничего не знают о том, как они создаются: они просто принимают готовые интерфейсы в своих конструкторах.
- Это обеспечивает абсолютную тестируемость (100% Mockability) кодовой базы.

## Решение по шагам

1. Создайте интерфейсы инфраструктуры.
2. Реализуйте иерархию конструкторов от нижних слоев к верхним.
3. Организуйте сборку всех зависимостей в едином методе `Bootstrap`.
4. Верифицируйте корректность сборки и вызова.

## Код решения

**`pure_di_bootstrap_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MailSender interface {
	Send(to, body string) error
}

type MockSender struct {
	sentCount int
}

func (m *MockSender) Send(to, body string) error {
	m.sentCount++
	return nil
}

type NotificationService struct {
	sender MailSender
}

func NewNotificationService(sender MailSender) *NotificationService {
	return &NotificationService{sender: sender}
}

func (s *NotificationService) NotifyUser(email, msg string) error {
	return s.sender.Send(email, msg)
}

func TestPureDIBootstrap(t *testing.T) {
	// Composition Root имитация
	senderMock := &MockSender{}
	svc := NewNotificationService(senderMock)

	if err := svc.NotifyUser("user@corp.ru", "Успешная регистрация"); err != nil {
		t.Fatalf("Ошибка отправки уведомления: %v", err)
	}

	if senderMock.sentCount != 1 {
		t.Fatalf("Ожидалась 1 отправка, выполнено: %d", senderMock.sentCount)
	}

	fmt.Println("Паттерн Composition Root (Pure DI) успешно подтвержден:")
	fmt.Println("  • Конструктор NewNotificationService получил mock-зависимость через интерфейс")
	fmt.Printf("  • Уведомлений отправлено: %d\n", senderMock.sentCount)
}
```


## Под капотом

Ручной DI создает легковесный стек вызовов: компилятор точно знает адреса вызовов методов, если интерфейс имеет ровно одну реализацию, и может преобразовать интерфейсный вызов в прямой статический вызов (Devirtualization), увеличивая быстродействие программы.

## Подводные камни

Передавать в конструктор `struct Dependencies` с 30 полями вместо конкретных параметров: это превращает структуру зависимостей в скрытый Service Locator, лишая разработчика понимания, какие именно зависимости нужны данному компоненту.

## На собеседовании

**Вопрос с собеседования:** «Почему паттерн Service Locator считается антипаттерном по сравнению с Constructor Injection?»
**Ответ:** Service Locator скрывает реальные зависимости класса внутри тела методов (`locator.Get("Database")`). Вы не можете понять по конструктору, что нужно компоненту для работы, а при отсутствии зависимости в локаторе программа падает в рантайме с паникой вместо ошибки компиляции.
