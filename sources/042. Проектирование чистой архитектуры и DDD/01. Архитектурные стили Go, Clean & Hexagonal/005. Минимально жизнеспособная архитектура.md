# Минимально жизнеспособная архитектура (3-Tier Architecture): почему это де-факто стандарт

## Условие

**Трёхслойная архитектура (3-Tier)**: Создайте проект со слоями: Handler (HTTP) → Service (бизнес-логика) → Repository (БД). Изучите, почему это минимально жизнеспособная структура.

## Теория

Почему 3-Tier является золотым стандартом бэкенда:
- 1 слой (все в хэндлере) — превращается в нетестируемый спагетти-монолит при первом же расширении.
- 5+ слоев (Clean/Hexagonal с 10 DTO и мапперами на запрос) — избыточный оверхед для 80% типовых CRUD-микросервисов.
- **3-Tier — точка идеального баланса (Sweet Spot):**
  1. `Handler`: знает только про транспортный протокол (HTTP статус-коды, JSON, заголовки).
  2. `Service`: содержит чистые правила бизнеса, не зависит от HTTP и SQL.
  3. `Repository`: содержит только логику персистентности (SQL, транзакции).

## Решение по шагам

1. Создайте интерфейс бизнес-сервиса.
2. Смоделируйте HTTP хендлер, делегирующий работу сервису.
3. Продемонстрируйте подмену сервиса моком для изолированного тестирования хендлера.
4. Верифицируйте статус 200 OK и изоляцию бизнес-логики.

## Код решения

**`three_tier_standard_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
)

type BalanceService interface {
	GetBalance(accountID string) (int64, error)
}

type MockBalanceService struct {
	balance int64
}

func (m *MockBalanceService) GetBalance(accountID string) (int64, error) {
	return m.balance, nil
}

type AccountHandler struct {
	svc BalanceService
}

func (h *AccountHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	accID := r.URL.Query().Get("account_id")
	if accID == "" {
		http.Error(w, "missing account_id", http.StatusBadRequest)
		return
	}
	bal, _ := h.svc.GetBalance(accID)
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]any{"account_id": accID, "balance": bal})
}

func TestThreeTierStandard(t *testing.T) {
	mockSvc := &MockBalanceService{balance: 50_000}
	handler := &AccountHandler{svc: mockSvc}

	req := httptest.NewRequest(http.MethodGet, "/balance?account_id=acc-777", nil)
	rec := httptest.NewRecorder()

	handler.ServeHTTP(rec, req)

	if rec.Code != http.StatusOK {
		t.Fatalf("Ожидался код 200, получено: %d", rec.Code)
	}

	if !strings.Contains(rec.Body.String(), "50000") {
		t.Fatalf("Некорректный баланс в ответе: %s", rec.Body.String())
	}

	fmt.Println("Минимально жизнеспособная архитектура 3-Tier успешно подтверждена:")
	fmt.Printf("  • Handler изолированно протестирован через Mock-сервис\n")
	fmt.Printf("  • Ответ HTTP: %s\n", strings.TrimSpace(rec.Body.String()))
}
```

## Под капотом

В Go абстракция `httptest.ResponseRecorder` реализует интерфейс `http.ResponseWriter`, аккумулируя байты в `bytes.Buffer`. Это позволяет тестировать транспортный слой целиком в памяти без открытия реальных сокетов ОС, ускоряя выполнение тестов в сотни раз.

## Подводные камни

Вызывать методы репозитория из хэндлера в обход сервиса («зачем мне сервис, если тут простой SELECT?»): это ломает границы архитектуры; при появлении первого требования к проверке прав или отправке события придется переписывать хэндлер.

## На собеседовании

**Вопрос с собеседования:** «Где в 3-слойной архитектуре должны открываться и коммититься транзакции базы данных?»
**Ответ:** Границы транзакции определяются в слое **Service** (бизнес-транзакция Use Case), но реализация транзакции не должна завязываться на конкретный `*sql.Tx`. Используют паттерн Unit of Work или передают транзакционный контекст `context.Context` через замыкание `repo.WithTx(ctx, func(txRepo) error)`.
