# Пакетная организация по слоям (Package by Layer): models, repository, service и transport

## Условие

**Организация по слоям (Package by Layer)**: Создайте проект, в котором пакеты разделены по техническим слоям: `models/`, `repository/`, `service/`, `transport/`. Реализуйте в этой структуре сервис заметок (Note Service).

### Исходная формулировка

**Standard Project Layout**: Возьми свой старый проект, где всё лежало в корне. Отрефактори его по стандарту `golang-standards/project-layout`: создай папки `cmd/app` (точка входа `main.go`), `internal/` (приватный код проекта, недоступный для импорта снаружи) и `pkg/` (публичные библиотеки, если есть).

## Теория

Концепция Package by Layer (Горизонтальное разделение):
- Классический подход корпоративной разработки (Spring, Django, ASP.NET):
  - `transport/`: парсинг HTTP/gRPC запросов, валидация DTO, сериализация JSON.
  - `service/`: сценарии бизнес-логики (Use Cases).
  - `repository/`: хранение и выборка данных из базы (SQL, Redis, In-Memory).
  - `models/`: DTO и базовые структуры данных.
- **Преимущества:** Понятная и предсказуемая структура для начинающих разработчиков.
- **Недостатки:** Низкая сцепленность (Cohesion): чтобы добавить одно поле в сущность Note, приходится модифицировать файлы в 4 разных папках.

## Решение по шагам

1. Определите сущность `Note` в доменном слое.
2. Создайте интерфейс и реализацию слоя `repository`.
3. Напишите бизнес-сервис `service`, управляющий заметками.
4. Смоделируйте транспортный слой `transport` и верифицируйте поток управления.

## Код решения

**`layered_architecture_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"testing"
	"time"
)

// 1. Layer: Models
type Note struct {
	ID        int64
	Title     string
	Content   string
	CreatedAt time.Time
}

// 2. Layer: Repository (хранилище)
type NoteRepository interface {
	Save(ctx context.Context, note *Note) error
	FindByID(ctx context.Context, id int64) (*Note, error)
}

type InMemoryNoteRepo struct {
	mu    sync.RWMutex
	store map[int64]*Note
	seq   int64
}

func NewInMemoryNoteRepo() *InMemoryNoteRepo {
	return &InMemoryNoteRepo{store: make(map[int64]*Note)}
}

func (r *InMemoryNoteRepo) Save(ctx context.Context, note *Note) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.seq++
	note.ID = r.seq
	note.CreatedAt = time.Now()
	r.store[note.ID] = note
	return nil
}

func (r *InMemoryNoteRepo) FindByID(ctx context.Context, id int64) (*Note, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	n, ok := r.store[id]
	if !ok {
		return nil, errors.New("note not found")
	}
	return n, nil
}

// 3. Layer: Service (бизнес-логика)
type NoteService struct {
	repo NoteRepository
}

func NewNoteService(repo NoteRepository) *NoteService {
	return &NoteService{repo: repo}
}

func (s *NoteService) CreateNote(ctx context.Context, title, content string) (*Note, error) {
	if title == "" {
		return nil, errors.New("title cannot be empty")
	}
	note := &Note{Title: title, Content: content}
	if err := s.repo.Save(ctx, note); err != nil {
		return nil, err
	}
	return note, nil
}

func TestPackageByLayer(t *testing.T) {
	repo := NewInMemoryNoteRepo()
	svc := NewNoteService(repo)

	ctx := context.Background()
	note, err := svc.CreateNote(ctx, "Архитектура Go", "Слои: transport -> service -> repo")
	if err != nil {
		t.Fatalf("Ошибка создания заметки: %v", err)
	}

	if note.ID != 1 || note.Title != "Архитектура Go" {
		t.Fatalf("Некорректные данные заметки: %+v", note)
	}

	fmt.Println("Слоистая организация (Package by Layer) успешно верифицирована:")
	fmt.Printf("  • Создана заметка ID=%d, Заголовок: %q\n", note.ID, note.Title)
	fmt.Printf("  • Поток вызовов: Handler -> Service -> Repository -> Storage\n")
}
```

## Под капотом

В Go слоистая архитектура опирается на композицию структур. Связывание слоев выполняется во время компиляции через интерфейсные таблицы `itab`, что позволяет подменять реальные репозитории на моки в юнит-тестах с нулевым оверхедом рантайма.

## Подводные камни

Помещать доменную логику в слой `repository` (например, валидацию полей или расчет скидок): репозиторий должен отвечать исключительно за персистентность (CRUD), иначе бизнес-логика размазывается по всей системе.

## На собеседовании

**Вопрос с собеседования:** «Почему структура models/ часто считается антипаттерном в идиоматичном Go?»
**Ответ:** Пакет с именем `models` не несет смысловой нагрузки (пакет «всего подряд»). Он провоцирует циклические импорты и хранение анемичных структур данных без поведения. В идиоматичном Go пакеты называют по бизнес-доменам: `user`, `order`, `billing`, где структура и методы работы с ней живут рядом.
