# Принцип инверсии зависимостей (DIP): объявление интерфейсов на стороне потребителя

## Условие

Инвертируй зависимости через **интерфейсы**: `repository.UserRepository` — интерфейс, `repository.PostgresUserRepository` — реализация. `service.UserService` принимает `UserRepository`, не знает о PostgreSQL. Покажи DIP (Dependency Inversion Principle).

## Теория

Принцип инверсии зависимостей (Dependency Inversion Principle, DIP):
1. Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба должны зависеть от абстракций (интерфейсов).
2. Абстракции не должны зависеть от деталей. Детали должны зависеть от абстракций.
- **В Go действует правило Consumer-Driven Interfaces:**
  Интерфейс `UserRepository` должен объявляться в пакете `service`, которому он нужен, а не в пакете базы данных `postgres`!
  Пакет `postgres` просто реализует нужные методы, даже не импортируя пакет `service` (неявная реализация интерфейсов).

## Решение по шагам

1. Создайте доменную структуру `Customer`.
2. Объявите интерфейс `CustomerReader` в сервисе-потребителе.
3. Реализуйте Postgres-адаптер без явных связей.
4. Продемонстрируйте DIP и подменяемость базы данных.

## Код решения

**`dip_consumer_interfaces_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type Customer struct {
	ID   string
	Name string
}

// DIP: Интерфейс объявляется на стороне ПОТРЕБИТЕЛЯ (Consumer)
type CustomerReader interface {
	FindCustomer(ctx context.Context, id string) (*Customer, error)
}

// Сервис зависит только от абстракции CustomerReader
type CustomerService struct {
	reader CustomerReader
}

func NewCustomerService(reader CustomerReader) *CustomerService {
	return &CustomerService{reader: reader}
}

func (s *CustomerService) GreetCustomer(ctx context.Context, id string) (string, error) {
	c, err := s.reader.FindCustomer(ctx, id)
	if err != nil {
		return "", err
	}
	return fmt.Sprintf("Здравствуйте, %s!", c.Name), nil
}

// Деталь реализации: Postgres адаптер (не знает о CustomerService!)
type PostgresCustomerRepo struct{}

func (p *PostgresCustomerRepo) FindCustomer(ctx context.Context, id string) (*Customer, error) {
	// Имитация SQL запроса SELECT * FROM customers WHERE id = $1
	return &Customer{ID: id, Name: "Иван Иванов"}, nil
}

func TestDIPConsumerInterfaces(t *testing.T) {
	dbRepo := &PostgresCustomerRepo{}
	svc := NewCustomerService(dbRepo)

	greeting, err := svc.GreetCustomer(context.Background(), "cust-101")
	if err != nil || greeting != "Здравствуйте, Иван Иванов!" {
		t.Fatalf("Ошибка приветствия: %v", err)
	}

	fmt.Println("Принцип инверсии зависимостей (DIP) успешно подтвержден:")
	fmt.Printf("  • Сервис выполнил бизнес-логику: %q\n", greeting)
	fmt.Println("  • CustomerService ничего не знает о PostgresCustomerRepo!")
	fmt.Println("  • Зависимость инвертирована: реализация БД зависит от абстракции сервиса")
}
```

ℹ️ Объявление интерфейса в пакете бизнес-логики и его реализация в слое адаптера БД

## Под капотом

Благодаря неявной типизации («Duck Typing») в Go структура удовлетворяет интерфейсу автоматически, если она реализует его сигнатуры методов. Это полностью разрывает зависимость между пакетами на этапе компиляции: пакет реализации даже не должен знать о существовании интерфейса!

## Подводные камни

Создавать один гигантский интерфейс `PostgresDatabase` на 50 методов: сервису нужен только 1 метод `FindCustomer`. В Go следуют Interface Segregation Principle (ISP): интерфейсы должны быть узкими (1–2 метода).

## На собеседовании

**Вопрос с собеседования:** «Почему в Go считается плохой практикой создавать пакет interfaces/?»
**Ответ:** Пакет `interfaces/` — наследие Java/C# с явным `implements`. В Go интерфейсы объявляются там, где они используются (`consumer package`), и содержат только те методы, которые реально нужны потребителю. Вынесение интерфейсов в отдельный пакет порождает ненужные зависимости и превращает интерфейсы в монолитную свалку.
