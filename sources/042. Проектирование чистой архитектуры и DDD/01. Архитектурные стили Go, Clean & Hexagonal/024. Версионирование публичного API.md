# Версионирование публичного API: подходы URI Path, Headers и управление обратной совместимостью

## Условие

**API Versioning**: Реализуйте версионирование API через URL (`/v1/users`, `/v2/users`) или через заголовки (`Accept: application/vnd.myapi.v2+json`). Обсудите trade-offs.

## Теория

Стратегии версионирования REST API:
1. **URI Path Versioning (`/api/v1/users`, `/api/v2/users`):**
   - *Плюсы:* Максимальная прозрачность, простота маршрутизации в NGINX/Ingress, кэширование на CDN работает из коробки.
   - *Минусы:* Нарушает чистоту REST (URI должен идентифицировать ресурс, а не версию представления).
2. **Header Versioning (`Accept: application/vnd.company.v2+json` или `X-API-Version: 2`):**
   - *Плюсы:* Истинный REST-подход (Content Negotiation), стабильный URI ресурса.
   - *Минусы:* Сложнее тестировать через браузер, требует настройки заголовков `Vary` для CDN-кэшей.
- **В BigTech 95% сервисов используют URI Path Versioning** из-за надежности и простоты маршрутизации.

## Решение по шагам

1. Создайте роутер с поддержкой версионирования `/v1/` и `/v2/`.
2. Реализуйте разные форматы ответа для v1 (плоская строка) и v2 (структурированный объект).
3. Протестируйте оба эндпоинта.
4. Верифицируйте сохранение обратной совместимости.

## Код решения

**`api_versioning_routes_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"testing"
)

type UserResponseV1 struct {
	ID   string `json:"id"`
	Name string `json:"name"`
}

type UserResponseV2 struct {
	ID        string `json:"id"`
	FirstName string `json:"first_name"`
	LastName  string `json:"last_name"`
}

func BuildVersionedMux() *http.ServeMux {
	mux := http.NewServeMux()

	// V1 Handler (Обратная совместимость со старыми клиентами)
	mux.HandleFunc("/api/v1/users", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(UserResponseV1{ID: "usr-1", Name: "Иван Смирнов"})
	})

	// V2 Handler (Новый контракт с разбиением имени)
	mux.HandleFunc("/api/v2/users", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(UserResponseV2{ID: "usr-1", FirstName: "Иван", LastName: "Смирнов"})
	})

	return mux
}

func TestAPIVersioningRoutes(t *testing.T) {
	mux := BuildVersionedMux()

	// 1. Проверяем v1
	req1 := httptest.NewRequest(http.MethodGet, "/api/v1/users", nil)
	rec1 := httptest.NewRecorder()
	mux.ServeHTTP(rec1, req1)

	var v1 UserResponseV1
	_ = json.NewDecoder(rec1.Body).Decode(&v1)
	if v1.Name != "Иван Смирнов" {
		t.Fatalf("Сбой v1: %+v", v1)
	}

	// 2. Проверяем v2
	req2 := httptest.NewRequest(http.MethodGet, "/api/v2/users", nil)
	rec2 := httptest.NewRecorder()
	mux.ServeHTTP(rec2, req2)

	var v2 UserResponseV2
	_ = json.NewDecoder(rec2.Body).Decode(&v2)
	if v2.FirstName != "Иван" || v2.LastName != "Смирнов" {
		t.Fatalf("Сбой v2: %+v", v2)
	}

	fmt.Println("Версионирование API (API Versioning) успешно подтверждено:")
	fmt.Printf("  • V1 ответ: Name=%q (Для старых мобильных клиентов)\n", v1.Name)
	fmt.Printf("  • V2 ответ: FirstName=%q, LastName=%q (Для нового веб-портала)\n", v2.FirstName, v2.LastName)
}
```

## Под капотом

В Go 1.22+ стандартный `http.ServeMux` поддерживает сопоставление путей с шаблонами и методами (`mux.HandleFunc("GET /api/v2/users/{id}", ...)`), что позволяет реализовывать версионирование маршрутов без использования тяжелых сторонних фреймворков.

## Подводные камни

Вводить новую версию API `v2` ради добавления одного необязательного поля: добавление новых полей в JSON является обратно совместимым (Non-breaking change). Новую версию создают **только при ломающих изменениях** (удаление или переименование полей).

## На собеседовании

**Вопрос с собеседования:** «Как долго в продакшене поддерживают устаревшие версии API (v1) после релиза v2?»
**Ответ:** По регламенту Deprecation Policy:
1. Выставляется заголовок `Deprecation: true` и `Sunset: Wed, 11 Nov 2026 00:00:00 GMT` по стандарту RFC 8594.
2. Анализируются логи и метрики обращений к v1.
3. Проводится Brownout (учебное отключение v1 на 15 минут в непиковые часы для выявления забытых клиентов).
4. Окончательное удаление через 6–12 месяцев после уведомления всех потребителей.
