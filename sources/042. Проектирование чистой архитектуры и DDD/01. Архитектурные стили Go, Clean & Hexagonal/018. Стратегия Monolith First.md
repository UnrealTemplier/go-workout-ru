# Стратегия Monolith First: проектирование модульного монолита с четкими границами доменов

## Условие

**Monolith First**: Создайте полноценный CRUD-монолит для e-commerce (Users, Products, Orders, Payments) с чёткими границами модулей внутри одного процесса.

## Теория

Архитектурная стратегия Monolith First (Мартин Фаулер):
- 90% проектов терпят крах при попытке начать разработку сразу с распределенной микросервисной архитектуры (Distributed Monolith Hell).
- **Преимущества монолита на старте:**
  1. Скорость разработки: все сущности живут в одном процессе, единая база данных, простые транзакции ACID.
  2. Легкость рефакторинга: перенос границ между модулями делается нажатием горячих клавиш в IDE.
  3. Дешевизна развертывания: один под в Kubernetes вместо 15 сервисов.
- **Условие успеха:** Монолит обязан быть **модульным** (Modular Monolith), с жесткими интерфейсными границами между доменами Users, Products, Orders и Payments.

## Решение по шагам

1. Создайте независимые доменные модули Users, Products, Orders, Payments.
2. Исключите прямой доступ к внутренним структурам соседних модулей.
3. Реализуйте сценарий оформления заказа через фасады модулей.
4. Верифицируйте корректность транзакционной цепочки.

## Код решения

**`monolith_first_ecommerce_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Модуль 1: Users
type UserModule struct{}

func (u *UserModule) ValidateUser(ctx context.Context, id string) bool {
	return id != ""
}

// Модуль 2: Products
type ProductModule struct{}

func (p *ProductModule) ReserveStock(ctx context.Context, sku string, count int) bool {
	return count > 0
}

// Модуль 3: Payments
type PaymentModule struct{}

func (p *PaymentModule) Charge(ctx context.Context, userID string, amount float64) bool {
	return amount > 0
}

// Модуль 4: Orders (Координатор модульного монолита)
type OrderModule struct {
	users    *UserModule
	products *ProductModule
	payments *PaymentModule
}

func NewOrderModule(u *UserModule, p *ProductModule, pay *PaymentModule) *OrderModule {
	return &OrderModule{users: u, products: p, payments: pay}
}

func (o *OrderModule) Checkout(ctx context.Context, userID, sku string, count int, amount float64) (string, error) {
	if !o.users.ValidateUser(ctx, userID) {
		return "", fmt.Errorf("user %s is invalid", userID)
	}
	if !o.products.ReserveStock(ctx, sku, count) {
		return "", fmt.Errorf("insufficient stock for %s", sku)
	}
	if !o.payments.Charge(ctx, userID, amount) {
		return "", fmt.Errorf("payment failed")
	}
	return "ord-success-777", nil
}

func TestMonolithFirstEcommerce(t *testing.T) {
	orders := NewOrderModule(&UserModule{}, &ProductModule{}, &PaymentModule{})

	orderID, err := orders.Checkout(context.Background(), "usr-1", "sku-laptop", 1, 150000.0)
	if err != nil || orderID == "" {
		t.Fatalf("Ошибка оформления заказа в монолите: %v", err)
	}

	fmt.Println("Стратегия Monolith First успешно верифицирована:")
	fmt.Printf("  • Заказ %s успешно оформлен внутри модульного монолита\n", orderID)
	fmt.Println("  • Границы модулей (Users, Products, Payments) полностью подготовлены к будущему выносу в микросервисы")
}
```

## Под капотом

В модульном монолите вызовы между доменами происходят в рамках одной области памяти (In-process function call) за десятки наносекунд, исключая сетевые задержки сериализации JSON/Protobuf и проблемы распределенных транзакций.

## Подводные камни

Делать прямые SQL JOIN между таблицами разных модулей в базе данных (например `orders` джойнит таблицу `users` напрямую): это связывает схемы на уровне БД и делает невозможным будущий распил монолита на микросервисы.

## На собеседовании

**Вопрос с собеседования:** «Когда модульный монолит пора распиливать на микросервисы?»
**Ответ:** Монолит распиливают не из-за объемов кода, а по двум причинам:
1. **Организационная (Conway's Law):** когда над монолитом работают более 5–8 независимых продуктовых команд, начинаются постоянные конфликты деплоя и релизные блокировки.
2. **Асимметричное масштабирование:** когда один модуль (например, видео-транскодер) требует 100 ядер CPU, а остальные модули — 1 ядро.
