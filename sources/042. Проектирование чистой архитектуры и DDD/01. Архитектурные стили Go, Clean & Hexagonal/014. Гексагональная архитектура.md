# Гексагональная архитектура (Hexagonal Architecture / Ports & Adapters): домен в центре и заменяемые адаптеры

## Условие

Реализуй **Hexagonal Architecture (Ports & Adapters)**: `domain/` (business logic), `ports/` (interfaces: `ForStoringUsers`, `ForSendingEmails`), `adapters/` (реализации: `PostgresUserStore`, `SMTPEmailSender`, `MockEmailSender`). Покажи, что домен — центр, всё остальное — заменяемые адаптеры.

## Теория

Архитектура Портов и Адаптеров Алистера Кокберна (Alistair Cockburn):
- **Домен (Core):** Внутри шестиугольника находится чистая бизнес-логика.
- **Порты (Ports):** Интерфейсы на границе шестиугольника:
  - **Driving Ports (Входящие порты):** интерфейсы, через которые внешний мир вызывает домен (Use Cases, API).
  - **Driven Ports (Исходящие порты):** интерфейсы, через которые домен обращается к внешнему миру (хранилище `ForStoringUsers`, почта `ForSendingEmails`).
- **Адаптеры (Adapters):** Конкретные реализации за пределами шестиугольника (`PostgresUserStore`, `HTTPHandler`, `KafkaConsumer`).

## Решение по шагам

1. Создайте доменную логику регистрации пользователя в центре.
2. Определите Driven Ports: `UserStorePort` и `EmailSenderPort`.
3. Создайте адаптеры для InMemory и SMTP.
4. Верифицируйте подмену адаптеров без изменения бизнес-ядра.

## Код решения

**`hexagonal_ports_adapters_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// 1. Domain Entities
type HexUser struct {
	ID    string
	Email string
}

// 2. Ports (Интерфейсы на границе шестиугольника)
type ForStoringUsers interface {
	SaveUser(ctx context.Context, u HexUser) error
}

type ForSendingEmails interface {
	SendWelcomeEmail(ctx context.Context, email string) error
}

// Входящий порт (Driving Port / UseCase)
type UserRegistrationUseCase struct {
	store  ForStoringUsers
	mailer ForSendingEmails
}

func NewUserRegistrationUseCase(s ForStoringUsers, m ForSendingEmails) *UserRegistrationUseCase {
	return &UserRegistrationUseCase{store: s, mailer: m}
}

func (uc *UserRegistrationUseCase) Register(ctx context.Context, id, email string) error {
	user := HexUser{ID: id, Email: email}
	if err := uc.store.SaveUser(ctx, user); err != nil {
		return err
	}
	return uc.mailer.SendWelcomeEmail(ctx, email)
}

// 3. Adapters (Внешний мир)
type InMemoryUserStoreAdapter struct {
	users map[string]HexUser
}

func (a *InMemoryUserStoreAdapter) SaveUser(ctx context.Context, u HexUser) error {
	a.users[u.ID] = u
	return nil
}

type MockEmailSenderAdapter struct {
	sentTo []string
}

func (a *MockEmailSenderAdapter) SendWelcomeEmail(ctx context.Context, email string) error {
	a.sentTo = append(a.sentTo, email)
	return nil
}

func TestHexagonalPortsAdapters(t *testing.T) {
	storeAdapter := &InMemoryUserStoreAdapter{users: make(map[string]HexUser)}
	mailAdapter := &MockEmailSenderAdapter{}

	// Доменное ядро соединяется с адаптерами через порты
	domainCore := NewUserRegistrationUseCase(storeAdapter, mailAdapter)

	err := domainCore.Register(context.Background(), "u-1", "hex@architecture.io")
	if err != nil {
		t.Fatalf("Ошибка регистрации в гексагоне: %v", err)
	}

	if len(mailAdapter.sentTo) != 1 || mailAdapter.sentTo[0] != "hex@architecture.io" {
		t.Fatal("Адаптер почты не зафиксировал отправку")
	}

	fmt.Println("Гексагональная архитектура (Ports & Adapters) успешно подтверждена:")
	fmt.Printf("  • Бизнес-ядро выполнило сценарий регистрации\n")
	fmt.Printf("  • Порты: ForStoringUsers, ForSendingEmails\n")
	fmt.Printf("  • Заменяемые адаптеры: InMemoryStore, MockEmailSender\n")
}
```

## Под капотом

Гексагональная архитектура позволяет запускать приложение в режиме полного офлайн-тестирования (Acceptance Testing): заменив все исходящие порты на in-memory адаптеры, вы можете прогнать 10 000 бизнес-тестов за 1 секунду без поднятия контейнеров с базами данных и брокерами сообщений.

## Подводные камни

Использовать в сигнатурах портов типы из пакетов адаптеров (например `ForStoringUsers` возвращает `gorm.DB`): это уничтожает суть изоляции, привязывая бизнес-ядро к библиотеке адаптера.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие входящего порта (Primary/Driving Port) от исходящего (Secondary/Driven Port)?»
**Ответ:** 
- **Driving Port** инициирует действие снаружи внутрь (HTTP-хендлер дергает Use Case).
- **Driven Port** инициируется ядром изнутри наружу (Use Case вызывает порт сохранения в базу данных или отправки метрики).
