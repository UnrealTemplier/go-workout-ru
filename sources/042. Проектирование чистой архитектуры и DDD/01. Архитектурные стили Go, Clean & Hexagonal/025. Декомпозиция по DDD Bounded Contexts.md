# Декомпозиция по DDD Bounded Contexts: определение границ контекстов и модели предметной области

## Условие

Спроектируй **декомпозицию по DDD Bounded Contexts**: `User Context` (профиль, аутентификация), `Order Context` (заказы, корзина), `Payment Context` (списание, возврат), `Inventory Context` (склад, резервирование), `Shipping Context` (доставка, трекинг). Покажи, что каждый контекст — потенциальный микросервис.

## Теория

Ограниченный контекст (Bounded Context) в Domain-Driven Design (Эрик Эванс):
- Bounded Context — это явная граница, внутри которой модель предметной области имеет единый, однозначный смысл (Единый язык — Ubiquitous Language).
- **Одна и та же реальная сущность в разных контекстах моделируется по-разному:**
  - В `User Context`: пользователь — это учетная запись (`Email`, `PasswordHash`, `Role`).
  - В `Order Context`: пользователь — это покупатель (`Customer`, `DiscountLevel`, `DeliveryAddress`).
  - В `Shipping Context`: пользователь — это получатель посылки (`Recipient`, `PhoneNumber`, `PassportID`).
- Попытка создать одну глобальную структуру `User` на всю компанию — фатальная ошибка монолитного мышления!

## Решение по шагам

1. Создайте доменные модели сущности в контекстах Order, Payment, Shipping.
2. Продемонстрируйте различие атрибутов одной бизнес-сущности.
3. Опишите интерфейсы взаимодействия между Bounded Contexts.
4. Верифицируйте границы контекстов.

## Код решения

**`ddd_bounded_contexts_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// 1. User Context: Фокус на аутентификации
type AuthUser struct {
	ID           string
	Email        string
	PasswordHash string
}

// 2. Order Context: Тот же человек, но как покупатель (Customer)
type OrderCustomer struct {
	ID            string
	DiscountLevel int
}

// 3. Shipping Context: Тот же человек, но как получатель груза (Recipient)
type ShippingRecipient struct {
	ID              string
	DeliveryAddress string
	ContactPhone    string
}

func TestDDDBoundedContexts(t *testing.T) {
	personID := "person-99"

	user := AuthUser{ID: personID, Email: "client@mail.ru", PasswordHash: "hash-secret"}
	customer := OrderCustomer{ID: personID, DiscountLevel: 10}
	recipient := ShippingRecipient{ID: personID, DeliveryAddress: "г. Москва, ул. Ленина, д. 5", ContactPhone: "+79991234567"}

	if user.ID != customer.ID || customer.ID != recipient.ID {
		t.Fatal("Идентификаторы должны указывать на одну персону")
	}

	fmt.Println("Декомпозиция по DDD Bounded Contexts успешно продемонстрирована:")
	fmt.Printf("  • Auth Context:     ID=%s, Email=%s (Фокус: безопасность)\n", user.ID, user.Email)
	fmt.Printf("  • Order Context:    ID=%s, Скидка=%d%% (Фокус: коммерция)\n", customer.ID, customer.DiscountLevel)
	fmt.Printf("  • Shipping Context: ID=%s, Адрес=%q (Фокус: логистика)\n", recipient.ID, recipient.DeliveryAddress)
	fmt.Println("  • Каждый Bounded Context автономен и готов стать независимым микросервисом!")
}
```

## Под капотом

Изоляция Bounded Contexts на уровне Go выражается в независимых Go-модулях (или пакетах), где общие понятия связываются только строковыми или целочисленными ID (`CustomerID string`), исключая передачу ссылочных типов указателей между границами контекстов.

## Подводные камни

Создавать «Каноническую модель данных» (Canonical Data Model) с объединением 100 полей в одну гигантскую структуру `User`: любое изменение поля в логистике потребует перекомпиляции и тестирования сервиса аутентификации.

## На собеседовании

**Вопрос с собеседования:** «Что такое Context Map (Карта контекстов) в Domain-Driven Design и какие виды связей между контекстами бывают?»
**Ответ:** Context Map фиксирует границы контекстов и отношения между командами:
1. **Shared Kernel:** общее разделяемое ядро кода.
2. **Customer-Supplier / Leader-Follower:** один контекст зависит от контрактов другого.
3. **Conformist:** зависимый контекст безоговорочно принимает модель поставщика.
4. **Anti-Corruption Layer (ACL):** защитный трансляционный слой между внешним сервисом и чистым доменом.
5. **Separate Ways:** контексты не взаимодействуют вовсе.
