# Декомпозиция монолита по бизнес-возможностям (Business Capability Decomposition)

## Условие

**Service Decomposition**: Разделите монолит на микросервисы по бизнес-возможностям: User Service, Product Service, Order Service, Payment Service.

## Теория

Принцип декомпозиции по Business Capabilities (Крис Ричардсон):
- Бизнес-возможность (Capability) — это то, чем организация занимается для создания ценности:
  - `User Service`: управление клиентами и доступом.
  - `Product Service`: витрина товаров, каталог, поиск, цены.
  - `Order Service`: оформление и сопровождение заказов.
  - `Payment Service`: прием платежей, холдирование, фискализация.
- **Главный критерий разделения:** Микросервисы группируются вокруг бизнес-функций, а не технических слоев (не «сервис базы данных» и не «сервис авторизации»).

## Решение по шагам

1. Создайте интерфейсы ключевых бизнес-сервисов.
2. Продемонстрируйте автономность каждого сервиса.
3. Смоделируйте сквозной процесс оформления заказа через микросервисы.
4. Верифицируйте корректность взаимодействия.

## Код решения

**`business_capability_decomp_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type ProductCatalogClient interface {
	GetPrice(ctx context.Context, sku string) float64
}

type PaymentServiceClient interface {
	Process(ctx context.Context, amount float64) bool
}

type OrderCheckoutCoordinator struct {
	catalog  ProductCatalogClient
	payments PaymentServiceClient
}

func (c *OrderCheckoutCoordinator) Checkout(ctx context.Context, sku string) (string, error) {
	price := c.catalog.GetPrice(ctx, sku)
	if price <= 0 {
		return "", fmt.Errorf("item not found")
	}
	if !c.payments.Process(ctx, price) {
		return "", fmt.Errorf("payment declined")
	}
	return "ORD-COMPLETED-101", nil
}

type StubCatalog struct{}

func (s *StubCatalog) GetPrice(ctx context.Context, sku string) float64 { return 4500.0 }

type StubPayment struct{}

func (s *StubPayment) Process(ctx context.Context, amount float64) bool { return true }

func TestBusinessCapabilityDecomp(t *testing.T) {
	coordinator := &OrderCheckoutCoordinator{
		catalog:  &StubCatalog{},
		payments: &StubPayment{},
	}

	orderID, err := coordinator.Checkout(context.Background(), "sku-headphones")
	if err != nil || orderID != "ORD-COMPLETED-101" {
		t.Fatalf("Ошибка оформления заказа через микросервисы: %v", err)
	}

	fmt.Println("Декомпозиция по бизнес-возможностям (Business Capability) подтверждена:")
	fmt.Printf("  • Успешное оформление заказа: %s\n", orderID)
	fmt.Println("  • Сервисы разделены по бизнес-доменам: Product Service, Payment Service, Order Service")
}
```

ℹ️ Координация независимых микросервисов, выделенных по бизнес-возможностям

## Под капотом

Декомпозиция по бизнес-возможностям напрямую отражает Закон Конвея (Conway's Law): архитектура системы повторяет структуру коммуникаций в организации. За каждый сервис отвечает отдельная кросс-функциональная продуктовая команда (2-Pizza Team).

## Подводные камни

Дробить сервисы слишком мелко (нано-сервисы по 100 строк кода): оверхед на сетевую задержку, сериализацию и поддержку 50 репозиториев перевесит любые архитектурные плюсы.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие декомпозиции по Business Capability от декомпозиции по DDD Subdomains?»
**Ответ:** Они приводят к практически идентичному результату:
- **Business Capability** смотрит на организацию извне («Что бизнес делает?» — продажи, логистика).
- **DDD Subdomains** смотрит изнутри домена («Какие зоны знаний существуют?» — Core Domain, Supporting Subdomain, Generic Subdomain). В HighLoad архитектуре эти подходы гармонично дополняют друг друга.
