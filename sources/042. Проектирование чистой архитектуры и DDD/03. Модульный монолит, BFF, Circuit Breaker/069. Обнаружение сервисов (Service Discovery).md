# Обнаружение сервисов (Service Discovery): DNS-based discovery в Kubernetes и Consul registry

## Условие

**Service Discovery**: В Kubernetes используйте DNS-based discovery. Для on-premise рассмотрите Consul или etcd.

## Теория

Механика Service Discovery в распределенных системах:
- В микросервисной среде IP-адреса подов постоянно меняются (рестарты, автомасштабирование HPA, перенос на другие ноды).
- **Два подхода к обнаружению:**
  1. **Server-Side Discovery (Kubernetes CoreDNS):**
     - Сервис обращается по стабильному DNS-имени: `http://order-service.production.svc.cluster.local:8080`.
     - CoreDNS резолвит имя в виртуальный `ClusterIP`.
     - Kube-Proxy распределяет трафик по реальным эндпоинтам подов через iptables/IPVS.
  2. **Client-Side Discovery (HashiCorp Consul / etcd):**
     - Сервис опрашивает агент Consul, получает список IP-адресов живых инстансов и сам балансирует вызовы (gRPC Round-Robin).

## Решение по шагам

1. Создайте модель резолвера адресов сервиса.
2. Смоделируйте разрешение доменного имени `order-service.svc`.
3. Реализуйте распределение запросов между динамическими эндпоинтами.
4. Верифицируйте корректность обнаружения сервисов.

## Код решения

**`service_discovery_dns_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DynamicEndpointRegistry struct {
	dnsMap map[string][]string
}

func (r *DynamicEndpointRegistry) ResolveEndpoints(serviceDNS string) []string {
	return r.dnsMap[serviceDNS]
}

func TestServiceDiscoveryDNS(t *testing.T) {
	registry := &DynamicEndpointRegistry{
		dnsMap: map[string][]string{
			"order-service.prod.svc.cluster.local": {
				"10.244.1.45:8080",
				"10.244.2.89:8080",
				"10.244.3.12:8080",
			},
		},
	}

	endpoints := registry.ResolveEndpoints("order-service.prod.svc.cluster.local")

	if len(endpoints) != 3 {
		t.Fatalf("Ожидалось 3 динамических эндпоинта пода: %v", endpoints)
	}

	fmt.Println("Обнаружение сервисов (Service Discovery) успешно подтверждено:")
	fmt.Println("  • DNS имя: order-service.prod.svc.cluster.local")
	for i, ep := range endpoints {
		fmt.Printf("    [%d] Pod IP: %s\n", i+1, ep)
	}
	fmt.Println("  • Балансировщик трафика автоматически распределяет нагрузку между живыми репликами")
}
```

## Под капотом

В gRPC встроен резолвер DNS: при передаче адреса вида `dns:///order-service:50051` клиент gRPC периодически запрашивает DNS SRV/A записи и автоматически обновляет пул TCP-соединений (Subchannels) при добавлении новых подов.

## Подводные камни

Кэшировать DNS IP-адрес навсегда в `net.Dialer`: при падении пода запросы продолжат лететь на старый мертвый IP-адрес. В Go настраивают время жизни кэша DNS через `DialContext` или используют стандартный K8s Service IP.

## На собеседовании

**Вопрос с собеседования:** «Почему в Kubernetes для gRPC вызовов недостаточно стандартного ClusterIP?»
**Ответ:** Потому что gRPC работает по долгоживущим HTTP/2 соединениям. Стандартный K8s Service балансирует трафик на уровне L4 (TCP-соединение). При одном TCP-соединении все тысячи gRPC запросов пойдут в **один единственный под**, а остальные 99 подов будут простаивать! Решение: использовать headless service (`clusterIP: None`) и client-side балансировку gRPC, либо Envoy Service Mesh.
