# Асинхронное межсервисное взаимодействие (Inter-Service Async): Kafka, RabbitMQ и слабая связность

## Условие

**Inter-Service Communication (Async)**: Используйте Kafka/RabbitMQ для асинхронного общения (event-driven) для снижения coupling.

## Теория

Преимущества асинхронного Event-Driven взаимодействия:
- **Временная слабая связанность (Temporal Decoupling):**
  - Сервис отправки уведомлений может лежать на техобслуживании 2 часа.
  - Сервис заказов продолжает принимать заказы клиентов на максимальной скорости, складывая события в топик Kafka.
  - Когда почтовый сервис поднимется, он вычитает накопившуюся очередь сообщений.
- **Буферизация всплесков (Traffic Smoothing / Load Leveling):**
  - Всплеск 100 000 заказов во время Черной Пятницы не убьет медленный складской сервис: он вычитывает сообщения с фиксированной комфортной скоростью (например 500 сообщений в секунду).

## Решение по шагам

1. Создайте асинхронный канал очереди `EventQueue`.
2. Смоделируйте публикацию события заказа продюсером.
3. Реализуйте фонового консьюмера, обрабатывающего очередь.
4. Продемонстрируйте автономность продюсера от консьюмера.

## Код решения

**`async_broker_decoupling_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type AsyncOrderPlacedEvent struct {
	OrderID   string
	AmountRub float64
}

type MessageQueueBroker struct {
	channel chan AsyncOrderPlacedEvent
}

func (b *MessageQueueBroker) Publish(evt AsyncOrderPlacedEvent) {
	b.channel <- evt
}

func TestAsyncBrokerDecoupling(t *testing.T) {
	broker := &MessageQueueBroker{channel: make(chan AsyncOrderPlacedEvent, 10)}

	// 1. Продюсер отправляет заказ в очередь (не ждет консьюмера!)
	broker.Publish(AsyncOrderPlacedEvent{OrderID: "ord-async-1", AmountRub: 8500.0})

	// 2. Консьюмер вычитывает сообщение асинхронно
	received := false
	select {
	case evt := <-broker.channel:
		if evt.OrderID == "ord-async-1" {
			received = true
		}
	case <-time.After(100 * time.Millisecond):
		t.Fatal("Таймаут ожидания сообщения из очереди")
	}

	if !received {
		t.Fatal("Сообщение не получено консьюмером")
	}

	fmt.Println("Асинхронное взаимодействие через брокер очередей подтверждено:")
	fmt.Println("  • Продюсер мгновенно отправил событие в буфер очереди")
	fmt.Println("  • Временная слабая связанность (Temporal Decoupling) ликвидирует каскадные сбои")
}
```

ℹ️ Асинхронная передача доменных событий через брокер очередей сообщений

## Под капотом

В Apache Kafka сообщения сохраняются в последовательный сегментированный лог на диске (Commit Log) с использованием `zero-copy` системного вызова `sendfile`, обеспечивая миллионные скорости отправки событий в секунду.

## Подводные камни

Использовать асинхронные очереди для синхронных сценариев, где пользователю нужен мгновенный ответ («Запрос-Ответ через 2 топика Kafka»): это чудовищно усложняет отладку и увеличивает задержку ответа.

## На собеседовании

**Вопрос с собеседования:** «Что такое семантика доставки At-Least-Once в очередях и как бэкенд должен защищаться от дубликатов?»
**Ответ:** At-Least-Once гарантирует, что сообщение никогда не потеряется, но из-за сбоев сети консьюмер может получить его дважды. Бэкенд обязан реализовать **Идемпотентность (Idempotency)**: перед обработкой события проверяется уникальный `EventID` в таблице `processed_events` базы данных с ограничением `PRIMARY KEY`.
