# Ограниченные контексты (Bounded Contexts): автономность баз данных и моделей Inventory, Billing, Shipping

## Условие

**Bounded Contexts**: Разделите большую систему на контексты (например, "Inventory", "Billing", "Shipping"), каждый со своей доменной моделью и БД.

## Теория

Принцип «Database per Bounded Context»:
- В правильном DDD каждый ограниченный контекст владеет **своей собственной физической или логической базой данных**:
  - `Inventory`: таблица остатков на складе, складские ячейки, артикулы.
  - `Billing`: счета-фактуры, чеки, реквизиты НДС.
  - `Shipping`: координаты ПВЗ, габариты упаковок, трек-номера.
- Ни один контекст не имеет прав на прямое чтение таблиц другого контекста!
- Все взаимодействие происходит строго через публичные API или брокер сообщений.

## Решение по шагам

1. Создайте модели данных для трех контекстов.
2. Продемонстрируйте автономию хранилищ каждого контекста.
3. Организуйте сквозной процесс передачи трек-номера.
4. Верифицируйте изоляцию данных.

## Код решения

**`bounded_contexts_databases_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// 1. Inventory Context
type InventoryStockDB struct {
	Stock map[string]int
}

// 2. Billing Context
type BillingLedgerDB struct {
	Invoices map[string]int64
}

// 3. Shipping Context
type ShippingTrackingDB struct {
	TrackingNumbers map[string]string
}

func TestBoundedContextsDatabases(t *testing.T) {
	invDB := &InventoryStockDB{Stock: map[string]int{"sku-mac": 50}}
	billDB := &BillingLedgerDB{Invoices: map[string]int64{"ord-1": 150_000}}
	shipDB := &ShippingTrackingDB{TrackingNumbers: map[string]string{"ord-1": "TRACK-RU-777"}}

	if invDB.Stock["sku-mac"] <= 0 || billDB.Invoices["ord-1"] <= 0 || shipDB.TrackingNumbers["ord-1"] == "" {
		t.Fatal("Сбой автономных контекстов")
	}

	fmt.Println("Автономия Bounded Contexts успешно подтверждена:")
	fmt.Printf("  • Inventory DB: %d шт на складе\n", invDB.Stock["sku-mac"])
	fmt.Printf("  • Billing DB:   Счет на сумму %d руб\n", billDB.Invoices["ord-1"])
	fmt.Printf("  • Shipping DB:  Трек-номер посылки: %s\n", shipDB.TrackingNumbers["ord-1"])
	fmt.Println("  • Контексты полностью независимы: падение Billing не остановит сборку посылок в Shipping!")
}
```

## Под капотом

Разделение баз данных по контекстам позволяет выбирать разные типы СУБД под задачи домена (Polyglot Persistence): `Billing` использует строгую реляционную PostgreSQL, `Catalog/Inventory` — быстрый Redis и Elasticsearch, а `Tracking/Shipping` — графовую Neo4j или Cassandra.

## Подводные камни

Использовать общую базу данных с единой таблицей, в которую пишут все три микросервиса: это порождает Distributed Monolith — худшую из всех возможных архитектур.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать декомпозицию монолитной базы данных на независимые БД ограниченных контекстов?»
**Ответ:** 
1. Разделение таблиц на уровне схем PostgreSQL (`billing.*`, `shipping.*`).
2. Запрет межсхемных JOIN на уровне прав ролей СУБД.
3. Перевод межмодульных запросов на сетевые вызовы gRPC.
4. Физический перенос схем на разные инстансы баз данных.
