# Переключение реализаций репозитория через флаг конфигурации: Postgres против InMemory

## Условие

**Паттерн Repository (интерфейс)**. Опишите интерфейс `UserRepository`. Реализуйте две имплементации: `PostgresUserRepo` и `InMemoryUserRepo`. Переключайтесь между ними флагом конфигурации.

## Теория

Динамический выбор реализации хранилища в Composition Root:
- В файле конфигурации задается флаг `STORAGE_TYPE=postgres` или `STORAGE_TYPE=memory`.
- **Зачем нужен InMemoryRepo в продакшн-коде:**
  1. Молниеносный запуск для локальной разработки разработчиками без необходимости поднимать Docker c PostgreSQL.
  2. Быстрый прогон сквозных тестов в CI/CD пайплайне.
  3. Возможность демонстрации демо-стендов на ноутбуках заказчиков.
- Доменная логика Use Cases не меняется ни на один символ.

## Решение по шагам

1. Опишите контракт `UserRepository`.
2. Реализуйте структуры `PostgresRepo` и `MemoryRepo`.
3. Напишите фабрику выбора реализации по строковому флагу.
4. Верифицируйте корректность работы обеих реализаций.

## Код решения

**`repo_config_switch_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type ConfigurableUserRepo interface {
	GetDriverName() string
}

type PostgresUserRepoImpl struct{}

func (p *PostgresUserRepoImpl) GetDriverName() string { return "PostgreSQL Driver v16" }

type InMemoryUserRepoImpl struct{}

func (m *InMemoryUserRepoImpl) GetDriverName() string { return "In-Memory RAM Map Driver" }

func CreateRepositoryByConfig(storageType string) ConfigurableUserRepo {
	switch storageType {
	case "postgres":
		return &PostgresUserRepoImpl{}
	case "memory":
		fallthrough
	default:
		return &InMemoryUserRepoImpl{}
	}
}

func TestRepoConfigSwitch(t *testing.T) {
	repo1 := CreateRepositoryByConfig("postgres")
	repo2 := CreateRepositoryByConfig("memory")

	if repo1.GetDriverName() != "PostgreSQL Driver v16" {
		t.Fatalf("Сбой инициализации Postgres: %s", repo1.GetDriverName())
	}
	if repo2.GetDriverName() != "In-Memory RAM Map Driver" {
		t.Fatalf("Сбой инициализации InMemory: %s", repo2.GetDriverName())
	}

	fmt.Println("Переключение реализаций репозитория по конфигурации подтверждено:")
	fmt.Printf("  • Конфиг 'postgres' -> Реализация: %s\n", repo1.GetDriverName())
	fmt.Printf("  • Конфиг 'memory'   -> Реализация: %s\n", repo2.GetDriverName())
	fmt.Println("  • Слой бизнес-логики работает с интерфейсом ConfigurableUserRepo без изменений")
}
```

## Под капотом

Фабричная функция в Go возвращает интерфейс `ConfigurableUserRepo`, скрывая конкретные структуры указателей. Это позволяет компилятору контролировать, чтобы обе реализации строго соответствовали контракту.

## Подводные камни

Возвращать конкретный указатель `*PostgresUserRepoImpl` вместо интерфейса из функции-фабрики: это разрушает полиморфизм и не позволяет переключаться на `InMemory`.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go не принято использовать паттерн Абстрактная Фабрика (Abstract Factory) в тяжелом виде?»
**Ответ:** Потому что идиоматичный Go ценит простоту (Simplicity). Вместо иерархии фабрик классов из Java (`UserRepoFactoryProvider`) в Go пишут простую функцию `switch storageType { case "postgres": ... }`, которая занимает 10 строк кода и не плодит лишних интерфейсов.
