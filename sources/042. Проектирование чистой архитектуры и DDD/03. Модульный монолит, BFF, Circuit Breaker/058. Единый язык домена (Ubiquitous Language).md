# Единый язык домена (Ubiquitous Language): отражение бизнес-терминов в именах пакетов, методов и сущностей

## Условие

**Ubiquitous Language**: Убедитесь, что имена классов, методов и переменных отражают бизнес-терминологию (не `data1`, `process()`, а `Invoice.CalculateTax()`).

## Теория

Концепция Ubiquitous Language (Единый язык, Эрик Эванс):
- Разработчики и бизнес-эксперты (продакт-овнеры, бухгалтеры, логисты) должны разговаривать **на одном общем языке**:
  - Плохо (технический жаргон): `DataHandler.Process(d1, d2)`, `UpdateFlag(1)`.
  - Отлично (Ubiquitous Language): `Invoice.CalculateVATTax(rate)`, `LoanApplication.ApproveByUnderwriter()`.
- Имена переменных, методов и пакетов в коде Go должны в точности соответствовать терминам предметной области.
- Код должен читаться как понятная спецификация бизнеса.

## Решение по шагам

1. Создайте структуру `TaxInvoice` с говорящими именами.
2. Реализуйте метод `CalculateVATTax` с явным бизнес-термином.
3. Продемонстрируйте читаемость бизнес-логики.
4. Верифицируйте соответствие Единому языку.

## Код решения

**`ubiquitous_language_invoice_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Моделирование строго в терминах бухгалтерии (Ubiquitous Language)
type TaxInvoice struct {
	InvoiceNumber string
	SubtotalRub   int64
	VATTaxRub     int64
}

func NewTaxInvoice(number string, subtotal int64) *TaxInvoice {
	return &TaxInvoice{InvoiceNumber: number, SubtotalRub: subtotal}
}

// Метод назван в точности как операция в бухучете: расчет ставки НДС
func (inv *TaxInvoice) CalculateVATTax(vatRatePercent int64) int64 {
	inv.VATTaxRub = (inv.SubtotalRub * vatRatePercent) / 100
	return inv.VATTaxRub
}

func (inv *TaxInvoice) TotalAmountDue() int64 {
	return inv.SubtotalRub + inv.VATTaxRub
}

func TestUbiquitousLanguageInvoice(t *testing.T) {
	invoice := NewTaxInvoice("INV-2026-0042", 500_000)
	tax := invoice.CalculateVATTax(20) // 20% НДС

	if tax != 100_000 || invoice.TotalAmountDue() != 600_000 {
		t.Fatalf("Ошибка расчета налога: %d", tax)
	}

	fmt.Println("Единый язык домена (Ubiquitous Language) успешно подтвержден:")
	fmt.Printf("  • Счет: %s\n", invoice.InvoiceNumber)
	fmt.Printf("  • Базовая сумма: %d руб, НДС: %d руб, К оплате: %d руб\n",
		invoice.SubtotalRub, invoice.VATTaxRub, invoice.TotalAmountDue())
	fmt.Println("  • Код не содержит абстрактных data/process, отражая термины реального бизнеса")
}
```

## Под капотом

Следование Ubiquitous Language ликвидирует ошибки «трудностей перевода» (Lost in Translation) между аналитиками и разработчиками. Если бизнес называет операцию «Списание неустойки», метод должен называться `DeductPenaltyFee()`, а не `SubMoney()`.

## Подводные камни

Использовать англо-русский суржик в идентификаторах (`CalculateNalog()`, `OplataScheta()`): если проект пишется на английском, термины переводят на правильный финансовый/доменный английский (`CalculateTax`, `SettleInvoice`).

## На собеседовании

**Вопрос с собеседования:** «Что делать, если в компании разные отделы называют одну вещь разными словами (например, склад называет товар Item, а маркетинг — Product)?»
**Ответ:** Это верный признак двух разных **Bounded Contexts**! Не нужно навязывать один общий термин. В контексте склада пакет и структура называются `warehouse.Item`, а в каталоге — `catalog.Product`. Внутри каждого контекста язык остается строгим и единым.
