# Плавная миграция версий API (API Versioning v1/v2): одновременное сосуществование двух контрактов

## Условие

**Версионирование API**. Реализуйте `v1` и `v2` эндпоинтов на одном сервере. `v2` меняет формат ответа. Клиенты могут плавно мигрировать.

## Теория

Управление жизненным циклом версий API:
- При переходе с v1 на v2 нельзя отключать старый эндпоинт, пока мобильные приложения старых версий установлены на телефонах пользователей.
- **Архитектурный подход:**
  - `v1` и `v2` эндпоинты работают на одном HTTP-сервере параллельно.
  - Оба хендлера вызывают один и тот же доменный Use Case!
  - Отличаются только Presentation DTO и презентеры ответов:
    - v1 возвращает плоский `{"full_name": "Анна Иванова"}`.
    - v2 возвращает структурированный `{"first_name": "Анна", "last_name": "Иванова"}`.

## Решение по шагам

1. Создайте Use Case получения профиля.
2. Создайте контроллер v1 и контроллер v2.
3. Смоделируйте параллельные запросы к `/api/v1/profile` и `/api/v2/profile`.
4. Верифицируйте корректную работу обеих версий.

## Код решения

**`api_migration_v1_v2_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"testing"
)

type DomainProfile struct {
	FirstName string
	LastName  string
}

func SetupVersionedAPI() *http.ServeMux {
	mux := http.NewServeMux()
	profile := DomainProfile{FirstName: "Анна", LastName: "Иванова"}

	// V1 Endpoint: плоское имя
	mux.HandleFunc("/api/v1/profile", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]string{
			"full_name": profile.FirstName + " " + profile.LastName,
		})
	})

	// V2 Endpoint: раздельные поля
	mux.HandleFunc("/api/v2/profile", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]string{
			"first_name": profile.FirstName,
			"last_name":  profile.LastName,
		})
	})

	return mux
}

func TestAPIMigrationV1V2(t *testing.T) {
	mux := SetupVersionedAPI()

	// 1. Проверка v1
	req1 := httptest.NewRequest(http.MethodGet, "/api/v1/profile", nil)
	rec1 := httptest.NewRecorder()
	mux.ServeHTTP(rec1, req1)

	var v1Res map[string]string
	_ = json.NewDecoder(rec1.Body).Decode(&v1Res)
	if v1Res["full_name"] != "Анна Иванова" {
		t.Fatalf("Сбой v1: %+v", v1Res)
	}

	// 2. Проверка v2
	req2 := httptest.NewRequest(http.MethodGet, "/api/v2/profile", nil)
	rec2 := httptest.NewRecorder()
	mux.ServeHTTP(rec2, req2)

	var v2Res map[string]string
	_ = json.NewDecoder(rec2.Body).Decode(&v2Res)
	if v2Res["first_name"] != "Анна" || v2Res["last_name"] != "Иванова" {
		t.Fatalf("Сбой v2: %+v", v2Res)
	}

	fmt.Println("Параллельная работа версий API v1/v2 успешно подтверждена:")
	fmt.Printf("  • v1 ответ: %v\n", v1Res)
	fmt.Printf("  • v2 ответ: %v\n", v2Res)
	fmt.Println("  • Обе версии используют единое доменное ядро, обеспечивая бесшовную миграцию клиентов")
}
```

## Под капотом

В микросервисах логику v1 и v2 разводят по разным подпакетам `delivery/http/v1` и `delivery/http/v2`. Общая бизнес-логика живет в `usecase`, что исключает дублирование правил приложения.

## Подводные камни

Клонировать весь код сервиса целиком ради создания v2: это удваивает техдолг и заставляет вносить багфиксы дважды в два разных места.

## На собеседовании

**Вопрос с собеседования:** «Как отслеживать темпы миграции клиентов с v1 на v2 в продакшене?»
**Ответ:** Через метрики Prometheus в HTTP middleware: счетчик `http_requests_total{handler="v1", client="ios_app"}` размечается версией API и User-Agent. В Grafana строится график спада трафика v1. Когда доля v1 падает ниже 0.1%, старый код удаляют.
