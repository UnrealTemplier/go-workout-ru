# Богатое поведение доменной сущности (Rich Entity): инкапсуляция метода активации пользователя CanBeActivated

## Условие

**Тонкие сущности (Entities) и богатое поведение**: Напишите структуру `User` в слое `domain`. Перенесите бизнес-правила валидации состояния (например, метод `CanBeActivated() bool`, проверяющий наличие подтвержденного email и заполненного профиля) внутрь самой структуры `User` (Rich Domain Model), очистив слой `usecase` от дублирования этой проверки.

## Теория

Инкапсуляция правил переходов состояний в Entity:
- В анемичной модели Use Case проверяет 5 условий:
  `if u.EmailVerified && u.ProfileFilled && !u.Banned && u.Age >= 18 { ... }`
- **Проблема:** Завтра появится второй сценарий (например `ActivateThroughAdminUseCase`), и программист забудет проверить `u.Age >= 18`.
- **Решение в Rich Domain Model:**
  - Логика проверки инварианта помещается **внутрь доменной сущности**:
    `func (u *User) CanBeActivated() bool`
  - Метод `u.Activate()` сам вызывает `CanBeActivated()` и возвращает ошибку, если инвариант нарушен.
  - Use Case становится кристально чистым: `return user.Activate()`.

## Решение по шагам

1. Создайте структуру `DomainUser` с приватными флагами.
2. Реализуйте метод `CanBeActivated() bool`.
3. Реализуйте метод перехода `Activate() error`.
4. Верифицируйте невозможность активации без подтверждения почты.

## Код решения

**`rich_user_activation_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type DomainUserEntity struct {
	id            string
	emailVerified bool
	profileFilled bool
	active        bool
}

func NewDomainUser(id string, emailVerified, profileFilled bool) *DomainUserEntity {
	return &DomainUserEntity{
		id:            id,
		emailVerified: emailVerified,
		profileFilled: profileFilled,
		active:        false,
	}
}

// Доменный метод проверки инварианта
func (u *DomainUserEntity) CanBeActivated() bool {
	return u.emailVerified && u.profileFilled && !u.active
}

// Доменный метод мутации состояния
func (u *DomainUserEntity) Activate() error {
	if !u.CanBeActivated() {
		return errors.New("user cannot be activated: email not verified or profile incomplete")
	}
	u.active = true
	return nil
}

func (u *DomainUserEntity) IsActive() bool { return u.active }

func TestRichUserActivation(t *testing.T) {
	// Неподтвержденный пользователь
	unverifiedUser := NewDomainUser("u-1", false, true)
	err := unverifiedUser.Activate()
	if err == nil {
		t.Fatal("Ожидалась ошибка активации пользователя с неподтвержденной почтой")
	}

	// Валидный пользователь
	validUser := NewDomainUser("u-2", true, true)
	if !validUser.CanBeActivated() {
		t.Fatal("Пользователь должен подлежать активации")
	}

	if err := validUser.Activate(); err != nil {
		t.Fatalf("Ошибка активации валидного пользователя: %v", err)
	}

	if !validUser.IsActive() {
		t.Fatal("Пользователь должен быть активен")
	}

	fmt.Println("Богатое поведение доменной сущности (Rich Entity) успешно подтверждено:")
	fmt.Printf("  • Пользователь %s активирован: %v\n", validUser.id, validUser.IsActive())
	fmt.Println("  • Бизнес-правило CanBeActivated инкапсулировано внутри сущности")
}
```

ℹ️ Инкапсуляция валидации активации внутри богатой доменной сущности

## Под капотом

Приватные поля гарантируют, что состояние сущности не может быть изменено в обход ее методов. Компилятор Go не позволит внешнему пакету написать `validUser.active = true` напрямую, защищая целостность бизнес-инвариантов.

## Подводные камни

Помещать в метод `Activate()` отправку приветственного email: сущность не должна иметь внешних побочных эффектов. Отправку email оркестрирует Use Case после того, как сущность успешно сменила статус.

## На собеседовании

**Вопрос с собеседования:** «Почему в Go часто избегают геттеров и сеттеров в стиле Java (getAge(), setAge())?»
**Ответ:** В Go не принято писать тривиальные геттеры/сеттеры для каждого поля. Если поле можно менять свободно — его делают публичным `Age int`. Если поле защищено инвариантом — его делают приватным, а вместо сеттера `setStatus()` создают осмысленный бизнес-метод `Activate()`, `Ban()`, `Suspend()`, отражающий бизнес-действие.
