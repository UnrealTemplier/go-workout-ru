# Модульный монолит с доменными пакетами: декомпозиция internal/users и internal/orders

## Условие

**Модульный монолит с доменными пакетами**. Разделите внутренние пакеты по доменам: `internal/users`, `internal/orders`. Каждый домен имеет свой handler, service, repository. Избегайте циклических зависимостей.

## Теория

Принцип доменной изоляции в модульном монолите:
- Каждый подпакет в `internal/` проектируется как самодостаточная мини-система:
  - `internal/users`: `User`, `UserService`, `UserRepository`, `UserHandler`.
  - `internal/orders`: `Order`, `OrderService`, `OrderRepository`, `OrderHandler`.
- **Правило связности:**
  - Пакет `orders` **не импортирует** структуры из `users/repository`.
  - Связь между доменами осуществляется либо через передачу скалярных ID (`userID string`), либо через публичные интерфейсные фасады `users.ReaderAPI`.
- Это гарантирует отсутствие циклических импортов и подготавливает монолит к физическому разделению на микросервисы.

## Решение по шагам

1. Создайте модуль `UsersDomain` с контрактом чтения.
2. Создайте модуль `OrdersDomain`, оперирующий только `UserID`.
3. Реализуйте проверку прав пользователя через фасад.
4. Продемонстрируйте отсутствие жесткого связывания моделей.

## Код решения

**`domain_packages_monolith_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// Модуль internal/users (Публичный фасад)
type UserProfileReader interface {
	IsActiveUser(ctx context.Context, userID string) bool
}

type UsersDomainModule struct{}

func (m *UsersDomainModule) IsActiveUser(ctx context.Context, userID string) bool {
	return userID != "" && userID != "banned"
}

// Модуль internal/orders
type OrdersDomainService struct {
	userReader UserProfileReader
}

func NewOrdersDomainService(u UserProfileReader) *OrdersDomainService {
	return &OrdersDomainService{userReader: u}
}

func (s *OrdersDomainService) CreateOrder(ctx context.Context, userID string, total float64) (string, error) {
	if !s.userReader.IsActiveUser(ctx, userID) {
		return "", fmt.Errorf("user %s is banned or inactive", userID)
	}
	return "ORD-MODULAR-555", nil
}

func TestDomainPackagesMonolith(t *testing.T) {
	usersMod := &UsersDomainModule{}
	ordersSvc := NewOrdersDomainService(usersMod)

	ctx := context.Background()
	orderID, err := ordersSvc.CreateOrder(ctx, "usr-active-77", 2500.0)
	if err != nil || orderID != "ORD-MODULAR-555" {
		t.Fatalf("Сбой создания заказа в модульном монолите: %v", err)
	}

	_, errBanned := ordersSvc.CreateOrder(ctx, "banned", 1000.0)
	if errBanned == nil {
		t.Fatal("Ожидалась ошибка создания заказа для заблокированного пользователя")
	}

	fmt.Println("Модульный монолит с доменными пакетами подтвержден:")
	fmt.Printf("  • Заказ %s успешно создан для активного пользователя\n", orderID)
	fmt.Println("  • Модуль internal/orders не зависит от внутренних репозиториев internal/users")
}
```

## Под капотом

Внутри пакетов `internal/users` и `internal/orders` все структуры могут быть названы лаконично: `users.Service`, `orders.Service` без избыточного префикса `UserUserService`, так как имя пакета в Go служит естественным пространством имен.

## Подводные камни

Создавать пакеты `models/` внутри каждого домена (`internal/users/models`, `internal/orders/models`): в Go идиоматично держать структуры сущностей прямо в корне пакета домена (`internal/users/user.go`).

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить случайный циклический импорт при добавлении новой фичи в модульный монолит?»
**Ответ:** Правило направления зависимостей по шкале зрелости доменов: низкоуровневые домены (Users, Identity) никогда не должны знать о высокоуровневых (Orders, Checkout). Связь в обратную сторону разрешена только через события шины данных или узкие интерфейсы потребителей.
