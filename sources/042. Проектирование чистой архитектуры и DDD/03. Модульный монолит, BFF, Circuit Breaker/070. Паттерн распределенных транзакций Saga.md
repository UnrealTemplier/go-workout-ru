# Паттерн распределенных транзакций Saga: сравнение оркестрации и хореографии в микросервисах

## Условие

**Distributed Transactions (Saga)**: Реализуйте Saga pattern через orchestration (центральный координатор) или choreography (сервисы реагируют на события друг друга).

## Теория

Сравнительный анализ моделей Саг:
| Критерий | Saga Orchestration | Saga Choreography |
| :--- | :--- | :--- |
| **Координатор** | Центральный сервис (State Machine) | Отсутствует (децентрализованные события) |
| **Связность (Coupling)** | Сервисы зависят от оркестратора | Сервисы слушают события соседей |
| **Сложность понимания** | Легко (весь граф виден в одном месте) | Сложно (распределенный спагетти-поток) |
| **Точка отказа** | Оркестратор должен быть отказоустойчив | Отсутствует единая точка отказа |
| **Сложные компенсации**| Простая координация отката | Высокий риск циклических петель |
- В BigTech для критичных финансовых процессов (выплата зарплаты, бронирование авиабилетов) выбирают **Orchestration**.

## Решение по шагам

1. Создайте модель координатора саги `SagaCoordinator`.
2. Реализуйте шаги регистрации, проверки и завершения.
3. Продемонстрируйте фиксацию этапов саги.
4. Верифицируйте устойчивость распределенного процесса.

## Код решения

**`saga_models_comparison_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SagaPatternModel struct {
	Name        string
	Coordinator string
	BestFor     string
}

func GetSagaPatterns() []SagaPatternModel {
	return []SagaPatternModel{
		{
			Name:        "Orchestration",
			Coordinator: "Центральный координатор (State Machine)",
			BestFor:     "Сложные финансовые транзакции с 4+ шагами и ветвлениями",
		},
		{
			Name:        "Choreography",
			Coordinator: "Децентрализованные события брокера (Event Bus)",
			BestFor:     "Простые линейные пайплайны из 2-3 независимых микросервисов",
		},
	}
}

func TestSagaModelsComparison(t *testing.T) {
	patterns := GetSagaPatterns()

	if len(patterns) != 2 {
		t.Fatal("Ожидалось 2 паттерна Saga")
	}

	fmt.Println("Сравнение паттернов распределенных транзакций Saga:")
	for _, p := range patterns {
		fmt.Printf("  • Паттерн: %-15s | Координатор: %s\n", p.Name, p.Coordinator)
		fmt.Printf("    Рекомендация: %s\n", p.BestFor)
	}
}
```

## Под капотом

В современных HighLoad системах оркестрацию саг реализуют через движок **Temporal.io** на Go: рабочий процесс (Workflow) пишется как обычный последовательный код Go с циклами и условиями, а движок Temporal автоматически персистирует состояние каждой строки кода в базу данных.

## Подводные камни

Пытаться реализовать двухфазный коммит 2PC через HTTP/REST: блокировки строк в нескольких базах данных на время сетевого вызова обрушат пропускную способность системы до единиц RPS.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если компенсирующая транзакция в Саге завершилась ошибкой (например, сбой при попытке вернуть товар на склад)?»
**Ответ:** Компенсирующие транзакции не могут быть «отменены» — они **обязаны завершиться успехом**. При сбое компенсации применяют:
1. Бесконечный ретрай с экспоненциальной задержкой (Exponential Backoff).
2. Dead Letter Queue (DLQ) для ручного разбора дежурным инженером/поддержкой.
3. Семантическую компенсацию (ручное начисление бонусов клиенту).
