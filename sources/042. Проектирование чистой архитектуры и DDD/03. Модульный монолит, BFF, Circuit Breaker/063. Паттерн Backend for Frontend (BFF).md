# Паттерн Backend for Frontend (BFF): специализированные шлюзы для мобильных и веб-клиентов

## Условие

**BFF (Backend for Frontend)**: Создайте отдельные API для мобильного и веб-клиентов с разными контрактами и оптимизациями под каждый клиент.

## Теория

Паттерн Backend For Frontend (Сэм Ньюман):
- Мобильные клиенты (iOS/Android) работают по нестабильной 3G/LTE сети с лимитом трафика и экраном в 6 дюймов.
- Веб-клиенты (Десктоп) работают по быстрому Wi-Fi/оптике и имеют экраны 27 дюймов с 4K разрешением.
- **Один универсальный API для всех — плохой компромисс:**
  - Мобилка страдает от оверфетчинга (Over-fetching: передача 50 лишних полей).
- **Решение — BFF:**
  1. `Mobile-BFF`: сжимает JSON, склеивает 5 запросов в 1, отдает только минимальный payload.
  2. `Web-BFF`: отдает полные детализированные данные с пагинацией.

## Решение по шагам

1. Создайте тяжелый внутренний доменный агрегат `UserProfileAggregate`.
2. Напишите легковесный адаптер `MobileBFFHandler`.
3. Напишите детализированный адаптер `WebBFFHandler`.
4. Сравните объемы передаваемых данных.

## Код решения

**`bff_pattern_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type FullUserData struct {
	ID             string
	Username       string
	AvatarURL      string
	PassportSeries string
	TaxNumber      string
	LoginHistory   []string
}

// Mobile BFF: только то, что нужно экрану смартфона
type MobileUserView struct {
	Username  string `json:"u"`
	AvatarURL string `json:"a"`
}

func RenderMobileBFF(data FullUserData) []byte {
	dto := MobileUserView{Username: data.Username, AvatarURL: data.AvatarURL}
	b, _ := json.Marshal(dto)
	return b
}

// Web BFF: полная детализация для десктопа
type WebUserView struct {
	ID           string   `json:"id"`
	Username     string   `json:"username"`
	AvatarURL    string   `json:"avatar_url"`
	TaxNumber    string   `json:"tax_number"`
	LoginHistory []string `json:"login_history"`
}

func RenderWebBFF(data FullUserData) []byte {
	dto := WebUserView{
		ID:           data.ID,
		Username:     data.Username,
		AvatarURL:    data.AvatarURL,
		TaxNumber:    data.TaxNumber,
		LoginHistory: data.LoginHistory,
	}
	b, _ := json.Marshal(dto)
	return b
}

func TestBFFPattern(t *testing.T) {
	raw := FullUserData{
		ID:             "u-777",
		Username:       "Артур",
		AvatarURL:      "https://cdn/a.jpg",
		PassportSeries: "4509 123456",
		TaxNumber:      "770123456789",
		LoginHistory:   []string{"ip1", "ip2", "ip3"},
	}

	mobilePayload := RenderMobileBFF(raw)
	webPayload := RenderWebBFF(raw)

	if len(mobilePayload) >= len(webPayload) {
		t.Fatalf("Mobile payload обязан быть компактнее web: %d >= %d", len(mobilePayload), len(webPayload))
	}

	fmt.Println("Паттерн Backend for Frontend (BFF) успешно подтвержден:")
	fmt.Printf("  • Mobile BFF размер: %d байт (Экономия мобильного трафика 3G/LTE!)\n", len(mobilePayload))
	fmt.Printf("  • Web BFF размер:    %d байт (Полные данные для десктопного портала)\n", len(webPayload))
}
```

ℹ️ Специализация контрактов под мобильные и десктопные интерфейсы через BFF

## Под капотом

BFF часто пишется той же командой, которая разрабатывает мобильное приложение (Mobile Team ownership), что устраняет зависимость от бэкенд-команд монолита и ускоряет релизный цикл фичей в App Store и Google Play.

## Подводные камни

Делать BFF полнофункциональным сервисом со своей базой данных: BFF должен быть строго **Stateless прокси**, запрашивающим данные у нижележащих Core микросервисов.

## На собеседовании

**Вопрос с собеседования:** «Почему в BigTech для BFF часто выбирают GraphQL вместо REST?»
**Ответ:** GraphQL позволяет клиенту самому запросить ровно те поля, которые нужны текущему экрану, предотвращая оверфетчинг без создания десятков кастомных REST эндпоинтов на сервере. Однако для тяжелых запросов в Go часто предпочитают gRPC-Web из-за бинарной скорости Protobuf.
