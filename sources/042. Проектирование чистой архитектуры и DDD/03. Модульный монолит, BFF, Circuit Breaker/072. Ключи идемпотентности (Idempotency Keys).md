# Ключи идемпотентности (Idempotency Keys): защита от повторных списаний в HTTP POST/PUT API

## Условие

**Idempotency Keys**: Добавьте `Idempotency-Key` заголовок для всех POST/PUT/PATCH запросов, чтобы повторные вызовы не создавали дубликаты.

## Теория

Стандарт проектирования идемпотентных API (IETF Draft / Stripe API):
- Клиент отправляет запрос создания платежа с заголовком:
  `Idempotency-Key: 8b12f45c-a78b-4911-9a72-f198b1b22e11`
- **Алгоритм работы сервера:**
  1. Сервер проверяет наличие ключа в Redis/PostgreSQL.
  2. **Если ключ встречается впервые:**
     - Атомарно сохраняется ключ со статусом `PROCESSING` (через Redis `SET NX EX 86400`).
     - Выполняется платеж.
     - Ответ кэшируется в записи ключа: `{"status": "SUCCESS", "tx": "123"}`.
  3. **Если ключ уже существует:**
     - Сервис **не выполняет бизнес-логику повторно**, а мгновенно отдает закэшированный ответ первого вызова!

## Решение по шагам

1. Создайте хранилище идемпотентности `IdempotencyStore`.
2. Реализуйте middleware проверки заголовка `Idempotency-Key`.
3. Смоделируйте повторный запрос с тем же ключом.
4. Верифицируйте возврат идентичного ответа без повторного выполнения операции.

## Код решения

**`idempotency_key_pattern_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type IdempotentRecord struct {
	ResponsePayload string
}

type IdempotencyEngine struct {
	mu    sync.Mutex
	cache map[string]IdempotentRecord
	calls int
}

func (e *IdempotencyEngine) ProcessPayment(idempotencyKey string, amount float64) (string, bool) {
	e.mu.Lock()
	defer e.mu.Unlock()

	// Если ключ уже обработан — возвращаем результат без повторного списания!
	if rec, found := e.cache[idempotencyKey]; found {
		return rec.ResponsePayload, true // из кэша
	}

	// Реальное выполнение бизнес-операции
	e.calls++
	result := fmt.Sprintf("Charged: %.2f RUB", amount)

	e.cache[idempotencyKey] = IdempotentRecord{ResponsePayload: result}
	return result, false // первый вызов
}

func TestIdempotencyKeyPattern(t *testing.T) {
	engine := &IdempotencyEngine{cache: make(map[string]IdempotentRecord)}
	key := "uuid-idem-key-777"

	// 1. Первый запрос (Реальное списание)
	res1, fromCache1 := engine.ProcessPayment(key, 5000.0)
	if fromCache1 || engine.calls != 1 {
		t.Fatalf("Первый вызов обязан списать деньги: %s", res1)
	}

	// 2. Сетевой ретрай клиента с тем же ключом
	res2, fromCache2 := engine.ProcessPayment(key, 5000.0)
	if !fromCache2 || engine.calls != 1 {
		t.Fatalf("Повторный вызов не должен был списывать деньги повторно: calls=%d", engine.calls)
	}

	if res1 != res2 {
		t.Fatal("Ответы обязаны быть идентичными")
	}

	fmt.Println("Ключи идемпотентности (Idempotency Keys) успешно подтверждены:")
	fmt.Printf("  • Вызов 1: %s (Выполнено в БД)\n", res1)
	fmt.Printf("  • Вызов 2: %s (Мгновенно из кэша идемпотентности)\n", res2)
	fmt.Println("  • Количество реальных списаний: ровно 1 (Дубликаты предотвращены!)")
}
```

## Под капотом

Если клиент присылает тот же `Idempotency-Key`, но с другим телом запроса (Payload Checksum не совпадает), сервер обязан вернуть ошибку `HTTP 422 Unprocessable Entity` или `409 Conflict`, предотвращая подмену параметров операции.

## Подводные камни

Хранить ключи идемпотентности в оперативной памяти одного инстанса: при наличии 20 реплик сервиса за балансировщиком повторный запрос попадет на другой под и спишет деньги повторно. Хранилище идемпотентности обязано быть распределенным (Redis / PostgreSQL).

## На собеседовании

**Вопрос с собеседования:** «Что делать, если повторный запрос с тем же Idempotency-Key пришел ровно в тот момент, когда первый запрос еще обрабатывается (In-Flight Request)?»
**Ответ:** Запрос переводится в ожидание (Locking / Mutex) либо возвращает статус `HTTP 409 Conflict` с заголовком `Retry-After: 2`, сообщая клиенту, что операция с данным ключом прямо сейчас находится в процессе выполнения.
