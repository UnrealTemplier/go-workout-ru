# Синхронное межсервисное взаимодействие (Inter-Service Sync): gRPC, таймауты, ретраи и Circuit Breaker

## Условие

**Inter-Service Communication (Sync)**: Используйте gRPC для синхронного общения между сервисами с retry, circuit breaker и timeout.

## Теория

Устойчивость синхронных вызовов в распределенных системах:
- При синхронном HTTP/gRPC вызове сервис A блокируется в ожидании сервиса B.
- Если сервис B начинает отвечать с задержкой 10 секунд вместо 50 мс:
  - В сервисе A скапливаются тысячи заблокированных горутин.
  - Пул соединений исчерпывается.
  - Сервис A падает по каскадному сбою (Cascading Failure).
- **Триада защиты синхронного вызова:**
  1. **Strict Timeout:** вызов обрывается по контексту через 500 мс (`context.WithTimeout`).
  2. **Exponential Backoff Retry:** повтор только при идемпотентных ошибках сети.
  3. **Circuit Breaker:** моментальный отказ (Fail-Fast) при превышении порога ошибок.

## Решение по шагам

1. Создайте клиент вызова с контекстным таймаутом.
2. Реализуйте эмулятор Circuit Breaker со счетчиком отказов.
3. Продемонстрируйте переход в открытое состояние (Fail-Fast).
4. Верифицируйте защиту ресурсов сервиса.

## Код решения

**`sync_resilience_circuit_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"
)

type CircuitState int

const (
	CircuitClosed CircuitState = iota // Нормальная работа
	CircuitOpen                       // Разомкнут: мгновенный сброс без вызова сети!
)

type SimpleCircuitBreaker struct {
	state          CircuitState
	failureCount   int
	thresholdCount int
}

func (cb *SimpleCircuitBreaker) Call(ctx context.Context, action func() error) error {
	if cb.state == CircuitOpen {
		return errors.New("circuit breaker is OPEN: fail-fast")
	}

	err := action()
	if err != nil {
		cb.failureCount++
		if cb.failureCount >= cb.thresholdCount {
			cb.state = CircuitOpen
		}
		return err
	}

	cb.failureCount = 0
	return nil
}

func TestSyncResilienceCircuit(t *testing.T) {
	cb := &SimpleCircuitBreaker{thresholdCount: 2}

	// Имитация сбоя удаленного сервиса
	failingService := func() error {
		return errors.New("503 Service Unavailable")
	}

	_ = cb.Call(context.Background(), failingService) // Сбой 1
	_ = cb.Call(context.Background(), failingService) // Сбой 2 -> порог превышен!

	// Третий вызов даже не должен пытаться лезть в сеть!
	start := time.Now()
	err := cb.Call(context.Background(), failingService)
	duration := time.Since(start)

	if err == nil || err.Error() != "circuit breaker is OPEN: fail-fast" {
		t.Fatalf("Ожидался мгновенный сброс Circuit Breaker: %v", err)
	}

	fmt.Println("Синхронное взаимодействие (Circuit Breaker) подтверждено:")
	fmt.Printf("  • Третий вызов сброшен мгновенно за %v (Fail-Fast защита от каскадного сбоя)\n", duration)
	fmt.Println("  • Circuit Breaker перешел в состояние OPEN, защитив сервис от зависания горутин")
}
```

## Под капотом

В Go библиотеках `sony/gobreaker` или Service Mesh (Envoy/Istio) Circuit Breaker имеет третье промежуточное состояние `Half-Open`: через заданный интервал времени (например 10 секунд) шлюз пропускает 1 тестовый запрос. Если запрос успешен — цепь замыкается обратно в `Closed`.

## Подводные камни

Повторять неидемпотентные POST-запросы при таймауте (Ретрай `POST /charge`): если запрос уже дошел до банка, но ответ задержался в сети, повторный запрос спишет деньги с клиента дважды.

## На собеседовании

**Вопрос с собеседования:** «Почему в микросервисах на Go для синхронных вызовов gRPC предпочтительнее REST JSON?»
**Ответ:** 
1. **Бинарный Protobuf:** в 5–10 раз компактнее JSON и сериализуется в разы быстрее без рефлексии.
2. **HTTP/2 мультиплексирование:** сотни параллельных RPC запросов передаются по одному TCP-соединению без накладных расходов на открытие сокетов.
3. **Строгая типизация контрактов:** генерация Go-кода по `.proto` файлам исключает расхождения в схемах данных.
