# Паттерн Единица Работы (Unit of Work): атомарные составные транзакции в слое бизнес-сервисов

## Условие

**Unit of Work (транзакционность)**. Создайте `UnitOfWork`, который управляет транзакцией БД. Сервис создаёт нескольких пользователей в одной транзакции через UoW.

## Теория

Паттерн Unit of Work (Мартин Фаулер):
- Позволяет слою Use Case выполнять несколько операций репозитория в рамках **одной неделимой ACID-транзакции**, не привязываясь к конкретному `*sql.Tx`.
- **Идиома Unit of Work в Go:**
  - Интерфейс `UnitOfWork` предоставляет метод:
    `Do(ctx context.Context, fn func(repo UserRepository) error) error`
  - Реализация UoW открывает транзакцию `tx, _ := db.BeginTx()`, передает специализированный репозиторий в функцию `fn`, и если `fn` вернула `nil` — выполняет `tx.Commit()`. При любой ошибке вызывается `tx.Rollback()`.
- Идеальное разделение: бизнес-слой управляет границами транзакции, не зная SQL!

## Решение по шагам

1. Создайте интерфейс `UnitOfWork`.
2. Реализуйте транзакционный менеджер с методами Commit/Rollback.
3. Выполните создание двух связанных сущностей в одном вызове `Do`.
4. Проверьте автоматический откат при ошибке.

## Код решения

**`unit_of_work_transaction_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

type UserEntity struct {
	Name string
}

type UserTxRepository interface {
	CreateUser(name string) error
}

type UnitOfWork interface {
	Execute(ctx context.Context, fn func(repo UserTxRepository) error) error
}

type MockUoWManager struct {
	committed bool
	rolledBack bool
	store     []string
}

type mockTxRepo struct {
	uow *MockUoWManager
}

func (r *mockTxRepo) CreateUser(name string) error {
	r.uow.store = append(r.uow.store, name)
	return nil
}

func (m *MockUoWManager) Execute(ctx context.Context, fn func(repo UserTxRepository) error) error {
	repo := &mockTxRepo{uow: m}
	err := fn(repo)
	if err != nil {
		m.rolledBack = true
		m.store = nil // Rollback!
		return err
	}
	m.committed = true
	return nil
}

func TestUnitOfWorkTransaction(t *testing.T) {
	uow := &MockUoWManager{}

	// Сценарий 1: Успешная составная транзакция создания 2 пользователей
	err := uow.Execute(context.Background(), func(repo UserTxRepository) error {
		_ = repo.CreateUser("Пользователь 1")
		_ = repo.CreateUser("Пользователь 2")
		return nil
	})

	if err != nil || !uow.committed || len(uow.store) != 2 {
		t.Fatalf("Сбой фиксации UoW: %v", err)
	}

	// Сценарий 2: Ошибка на втором шаге -> автоматический Rollback
	uowRollback := &MockUoWManager{}
	errRollback := uowRollback.Execute(context.Background(), func(repo UserTxRepository) error {
		_ = repo.CreateUser("Пользователь 3")
		return errors.New("ошибка валидации")
	})

	if errRollback == nil || !uowRollback.rolledBack || len(uowRollback.store) != 0 {
		t.Fatal("UoW обязан выполнить откат при ошибке")
	}

	fmt.Println("Паттерн Unit of Work успешно подтвержден:")
	fmt.Printf("  • Успешная транзакция зафиксировала пользователей: %v\n", uow.store)
	fmt.Println("  • Ошибочная транзакция автоматически выполнила полный Rollback")
}
```

## Под капотом

В реальной реализации на базе `pgx` или `database/sql` Unit of Work использует замыкание `defer func() { if p := recover(); p != nil { tx.Rollback(); panic(p) } }()` для гарантированного отката транзакции даже в случае паники внутри пользовательского кода.

## Подводные камни

Выполнять долгие сетевые запросы к сторонним сервисам внутри функции `uow.Execute(...)`: транзакция БД остается открытой, удерживая блокировки строк и исчерпывая пул соединений. Сетевые вызовы выносят за пределы транзакции.

## На собеседовании

**Вопрос с собеседования:** «Как избежать передачи объекта транзакции tx через все уровни приложения?»
**Ответ:** Транзакцию помещают в контекст запроса: `ctx = contextWithTx(ctx, tx)`. Репозиторий извлекает транзакцию из контекста: если транзакция есть — выполняет запросы в ней (`tx.ExecContext`), если нет — в общем пуле (`db.ExecContext`). Это сохраняет сигнатуры методов репозитория чистыми.
