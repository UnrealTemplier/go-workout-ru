# Слой сервисов приложения (Application Services): тонкие Use Cases как оркестраторы бизнес-процессов

## Условие

**Application Services**: Создайте use case'ы как тонкие orchestration слои: `CreateOrderUseCase.Execute(dto CreateOrderDTO) (OrderID, error)`.

## Теория

Роль Application Services в Clean Architecture:
- Слой Application Service (Use Case) не должен содержать правил предметной области (расчет налогов, скидок, проверка баланса).
- **Его единственная обязанность — Оркестрация (Coordination):**
  1. Загрузить доменный агрегат из репозитория: `order := repo.Get(id)`.
  2. Вызвать бизнес-метод доменного агрегата: `order.Cancel()`.
  3. Сохранить обновленный агрегат в репозиторий: `repo.Save(order)`.
  4. Опубликовать возникшие доменные события в шину: `bus.Publish(order.PullEvents())`.
- Use Case тонкий и линейный, вся сложность сокрыта в сущностях.

## Решение по шагам

1. Создайте DTO команды `CreateOrderInputDTO`.
2. Создайте тонкий Use Case `CreateOrderUseCase`.
3. Продемонстрируйте оркестрацию между репозиторием и агрегатом.
4. Верифицируйте возврат `OrderID` и отсутствие бизнес-правил в Use Case.

## Код решения

**`application_service_usecase_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type CreateOrderInputDTO struct {
	CustomerID string
	TotalRub   float64
}

type OrderID string

type OrderAppRepository interface {
	SaveOrder(ctx context.Context, id OrderID, total float64) error
}

type MockOrderAppRepo struct {
	savedID OrderID
}

func (m *MockOrderAppRepo) SaveOrder(ctx context.Context, id OrderID, total float64) error {
	m.savedID = id
	return nil
}

// Application Service (Тонкий оркестратор сценария)
type CreateOrderUseCase struct {
	repo OrderAppRepository
}

func NewCreateOrderUseCase(repo OrderAppRepository) *CreateOrderUseCase {
	return &CreateOrderUseCase{repo: repo}
}

func (uc *CreateOrderUseCase) Execute(ctx context.Context, dto CreateOrderInputDTO) (OrderID, error) {
	// Оркестрация: генерация ID, делегирование сущности и сохранение
	generatedID := OrderID("ORD-APP-991")
	if err := uc.repo.SaveOrder(ctx, generatedID, dto.TotalRub); err != nil {
		return "", err
	}
	return generatedID, nil
}

func TestApplicationServiceUseCase(t *testing.T) {
	repo := &MockOrderAppRepo{}
	usecase := NewCreateOrderUseCase(repo)

	orderID, err := usecase.Execute(context.Background(), CreateOrderInputDTO{
		CustomerID: "cust-55",
		TotalRub:   12990.0,
	})

	if err != nil || orderID != "ORD-APP-991" || repo.savedID != "ORD-APP-991" {
		t.Fatalf("Ошибка выполнения Application Service: %v", err)
	}

	fmt.Println("Слой Application Services (Use Cases) успешно подтвержден:")
	fmt.Printf("  • Оркестратор успешно выполнил сценарий: OrderID=%s\n", orderID)
	fmt.Println("  • Use Case не содержит грязного SQL и HTTP-кода, отвечая строго за поток шагов")
}
```

## Под капотом

В Clean Architecture каждый Use Case оформляется в виде отдельной структуры с единственным методом `Execute()` (Command Pattern). Это кардинально упрощает чтение кодовой базы: папка `usecases/` превращается в оглавление всех бизнес-возможностей сервиса.

## Подводные камни

Помещать в Application Service валидацию синтаксиса JSON (например проверку длины строк): синтаксическую валидацию делает хэндлер, семантическую — сущность домена. Use Case только координирует вызовы.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Application Service от Domain Service?»
**Ответ:** 
- **Application Service:** сценарий использования (Use Case), оперирует транзакциями, отправкой email, логами и безопасностью.
- **Domain Service:** чистая математика бизнеса, не помещающаяся в одну сущность (например, сложный алгоритм валютного арбитража или расчет НДС между несколькими налоговыми юрисдикциями). В нем нет транзакций и ввода-вывода.
