# Управление транзакциями через Context и RunInTransaction: сохранение чистоты доменного слоя

## Условие

**Границы транзакций (Unit of Work)**: Архитектурная боль: как сделать транзакцию на 3 таблицы, если бизнес-логика ничего не знает про `sql.Tx`? Реализуй паттерн Unit of Work или передавай транзакцию через `context.Context` (используя функции-обертки `RunInTransaction(ctx, func(...) error)`), чтобы сохранить чистоту доменного слоя.

## Теория

Паттерн транзакционного контекста (Transactional Context):
- **Проблема:** Бизнес-слой Use Case координирует обновление 3 репозиториев (`UserRepo`, `OrderRepo`, `AuditRepo`), но не имеет права импортировать `*sql.Tx`.
- **Элегантное решение через `context.Context`:**
  1. Инфраструктурный менеджер транзакций предоставляет метод:
     `RunInTransaction(ctx, func(txCtx context.Context) error)`
  2. Внутри метода открывается `tx, _ := db.BeginTx(ctx)`.
  3. Указатель на `tx` помещается в контекст: `txCtx = context.WithValue(ctx, txKey, tx)`.
  4. Все репозитории внутри вызова проверяют: если в контексте есть транзакция — выполняют запрос в ней, если нет — в общем пуле `db`.
  5. Бизнес-код чист, а транзакция атомарна!

## Решение по шагам

1. Создайте ключ контекста для хранения транзакции.
2. Напишите раннер `RunInTransaction`.
3. Смоделируйте репозиторий, извлекающий транзакцию из контекста.
4. Продемонстрируйте атомарный коммит и откат при ошибке.

## Код решения

**`transactional_context_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

type txKeyType struct{}
var txContextKey = txKeyType{}

type MockDBTransaction struct {
	committed  bool
	rolledBack bool
}

func RunInTransaction(ctx context.Context, fn func(txCtx context.Context) error) error {
	tx := &MockDBTransaction{}
	txCtx := context.WithValue(ctx, txContextKey, tx)

	err := fn(txCtx)
	if err != nil {
		tx.rolledBack = true
		return err
	}
	tx.committed = true
	return nil
}

// Репозиторий проверяет наличие транзакции в контексте
type ContextAwareOrderRepo struct{}

func (r *ContextAwareOrderRepo) Save(ctx context.Context, orderID string) error {
	tx, ok := ctx.Value(txContextKey).(*MockDBTransaction)
	if !ok || tx == nil {
		return errors.New("операция требует активной транзакции в контексте")
	}
	return nil
}

func TestTransactionalContext(t *testing.T) {
	repo := &ContextAwareOrderRepo{}

	// 1. Успешный сценарий
	err := RunInTransaction(context.Background(), func(txCtx context.Context) error {
		return repo.Save(txCtx, "ord-tx-1")
	})

	if err != nil {
		t.Fatalf("Ошибка транзакционного выполнения: %v", err)
	}

	// 2. Сценарий ошибки и отката
	errFail := RunInTransaction(context.Background(), func(txCtx context.Context) error {
		_ = repo.Save(txCtx, "ord-tx-2")
		return errors.New("сбой бизнес-правила")
	})

	if errFail == nil {
		t.Fatal("Ожидался возврат ошибки транзакции")
	}

	fmt.Println("Управление транзакциями через Context успешно подтверждено:")
	fmt.Println("  • RunInTransaction внедрил транзакцию в контекст запроса")
	fmt.Println("  • Репозиторий выполнил операцию без передачи *sql.Tx через сигнатуры бизнес-методов")
}
```

## Под капотом

Этот подход используется в популярных Go библиотеках работы с БД (`pgx`, `bun`, `ent`). Контекст в Go является потокобезопасным хранилищем значений в рамках дерева вызовов одной горутины, что делает транзакционный контекст идеальным решением для изоляции уровней.

## Подводные камни

Запускать фоновую горутину `go repo.Save(txCtx, ...)`: транзакция в контексте может быть уже закоммичена или закрыта родительской горутиной, что приведет к ошибке `sql: transaction has already been committed or rolled back`.

## На собеседовании

**Вопрос с собеседования:** «Почему некоторые разработчики критикуют передачу транзакции через context.Context?»
**Ответ:** Потому что контекст скрывает зависимости (`implicit dependency`). Глядя на сигнатуру `Save(ctx, id)`, разработчик не видит, что метод требует открытой транзакции. Если вызвать метод с обычным `context.Background()`, ошибка выявится только в рантайме. Поэтому репозиторий должен уметь работать и с транзакцией, и без нее (Fallback на общий пул соединений).
