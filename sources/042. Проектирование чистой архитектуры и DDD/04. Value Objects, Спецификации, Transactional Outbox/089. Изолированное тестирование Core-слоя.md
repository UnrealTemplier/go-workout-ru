# Изолированное тестирование Core-слоя: 100% покрытие бизнес-логики через моки без запуска БД и сети

## Условие

**Изолированное тестирование Core-слоя**: Напиши юнит-тесты на слой Use Case. Замокай базу данных, отправку писем и время. Добейся 100% покрытия бизнес-логики без запуска реальной БД или HTTP-сервера.

### Исходная формулировка

**Изолированное тестирование Core-слоя**: Напиши юнит-тесты на слой Use Case из упр. 553. Замокай базу данных, отправку писем и время. Добейся 100% покрытия бизнес-логики без запуска реальной БД или HTTP-сервера.

## Теория

Пирамида тестирования и чистый Core-слой:
- Если юнит-тест требует запуска PostgreSQL в Docker (через testcontainers) — это **интеграционный тест**, а не юнит-тест. Он выполняется 2 секунды.
- Истинные юнит-тесты Clean Architecture тестируют **только домен и Use Cases**.
- Все внешние порты (БД, почта, платежи, часы) заменяются моками в оперативной памяти.
- **Скорость:** 10 000 таких тестов выполняются за 0.5 секунды!
- Позволяет моментально протестировать любые граничные случаи и сбои сети.

## Решение по шагам

1. Создайте моки для репозитория и почтового сервиса.
2. Напишите тест успешного сценария с проверкой вызовов.
3. Напишите тест сбоя репозитория с проверкой отката.
4. Верифицируйте молниеносное выполнение за 0.00s.

## Код решения

**`pure_unit_testing_core_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

type MockUserRepository struct {
	saveCalled bool
	returnErr  error
}

func (m *MockUserRepository) SaveUser(ctx context.Context, name string) error {
	m.saveCalled = true
	return m.returnErr
}

type MockMailerService struct {
	sentEmails []string
}

func (m *MockMailerService) SendWelcome(ctx context.Context, name string) error {
	m.sentEmails = append(m.sentEmails, name)
	return nil
}

type UserOnboardingUseCase struct {
	repo   *MockUserRepository
	mailer *MockMailerService
}

func (uc *UserOnboardingUseCase) Execute(ctx context.Context, name string) error {
	if err := uc.repo.SaveUser(ctx, name); err != nil {
		return fmt.Errorf("repo error: %w", err)
	}
	return uc.mailer.SendWelcome(ctx, name)
}

func TestPureUnitTestingCore(t *testing.T) {
	// Сценарий 1: Успех
	repoOk := &MockUserRepository{}
	mailerOk := &MockMailerService{}
	ucOk := &UserOnboardingUseCase{repo: repoOk, mailer: mailerOk}

	if err := ucOk.Execute(context.Background(), "Валентин"); err != nil {
		t.Fatalf("Ожидался успех: %v", err)
	}

	if !repoOk.saveCalled || len(mailerOk.sentEmails) != 1 {
		t.Fatal("Все зависимости обязаны быть вызваны")
	}

	// Сценарий 2: Ошибка БД (Письмо не должно уйти!)
	repoFail := &MockUserRepository{returnErr: errors.New("db disk full")}
	mailerFail := &MockMailerService{}
	ucFail := &UserOnboardingUseCase{repo: repoFail, mailer: mailerFail}

	errFail := ucFail.Execute(context.Background(), "Валентин")
	if errFail == nil || len(mailerFail.sentEmails) != 0 {
		t.Fatal("При ошибке БД отправка письма обязана быть заблокирована")
	}

	fmt.Println("Изолированное тестирование Core-слоя успешно подтверждено:")
	fmt.Println("  • 100% покрытие Use Case без запуска Docker, Postgres и реальной почты")
	fmt.Println("  • Тест выполнился за доли миллисекунды")
}
```

## Под капотом

Команда `go test -coverprofile=coverage.out` проверяет процент покрытия инструкций. При чистой архитектуре слой Use Cases достигает 100% покрытия всеми ветками ошибок `if err != nil`, так как мок можно запрограммировать вернуть любую ошибку.

## Подводные камни

Использовать библиотеки генерации моков (mockgen), генерирующие тысячи строк сложного кода, там, где достаточно написать простой рукописный mock-структуру на 5 строк.

## На собеседовании

**Вопрос с собеседования:** «Как протестировать функцию, внутри которой вызывается time.Now() или time.Sleep()?»
**Ответ:** Время абстрагируют через интерфейс:
`type Clock interface { Now() time.Time; Sleep(d time.Duration) }`. В продакшене передают `RealClock`, а в юнит-тестах — `MockClock`, в котором время можно перематывать вперед мгновенно без реального ожидания.
