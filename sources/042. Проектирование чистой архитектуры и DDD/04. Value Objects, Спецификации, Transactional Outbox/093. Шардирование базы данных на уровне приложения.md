# Шардирование базы данных на уровне приложения (Application-Level Sharding): хэширование и маршрутизация

## Условие

**Шардирование на уровне приложения**. Реализуйте маршрутизацию запросов к разным инстансам PostgreSQL по ключу (например, `user_id % N`). Обеспечьте прозрачную работу репозитория.

## Теория

Архитектура шардирования на уровне Go приложения:
- Когда объем данных превышает емкость одного дискового массива (терабайты данных), базу данных делят на \(N\) независимых серверов (Шардов).
- **Ключ шардирования (Sharding Key):** обычно `user_id` или `tenant_id`.
- **Функция маршрутизации:**
  $$\text{ShardID} = \text{Hash}(\text{Key}) \pmod N$$
- **Прозрачный репозиторий:**
  Слой Use Case вызывает `repo.SaveUser(ctx, user)`. Репозиторий сам определяет нужный шардовый пул соединений `shards[shardID]` и выполняет запрос. Бизнес-логика ничего не знает о количестве серверов!

## Решение по шагам

1. Создайте пул шардов `ShardedCluster`.
2. Реализуйте детерминированную функцию маршрутизации по модулю \(N\).
3. Сохраните данные нескольких пользователей.
4. Проверьте равномерное распределение записей по серверам.

## Код решения

**`application_level_sharding_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

type ShardedDatabaseCluster struct {
	shards []map[string]string // N независимых баз данных
}

func NewShardedCluster(shardCount int) *ShardedDatabaseCluster {
	shards := make([]map[string]string, shardCount)
	for i := 0; i < shardCount; i++ {
		shards[i] = make(map[string]string)
	}
	return &ShardedDatabaseCluster{shards: shards}
}

func (c *ShardedDatabaseCluster) selectShard(key string) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return int(h.Sum32()) % len(c.shards)
}

func (c *ShardedDatabaseCluster) Put(key, val string) int {
	shardIdx := c.selectShard(key)
	c.shards[shardIdx][key] = val
	return shardIdx
}

func TestApplicationLevelSharding(t *testing.T) {
	cluster := NewShardedCluster(3) // 3 шарда БД

	s1 := cluster.Put("user-alice-101", "Alice Data")
	s2 := cluster.Put("user-bob-202", "Bob Data")
	s3 := cluster.Put("user-charlie-303", "Charlie Data")

	totalRecords := len(cluster.shards[0]) + len(cluster.shards[1]) + len(cluster.shards[2])
	if totalRecords != 3 {
		t.Fatalf("Записи не распределены по шардам: %d", totalRecords)
	}

	fmt.Println("Шардирование на уровне приложения успешно подтверждено:")
	fmt.Printf("  • user-alice-101   -> Шард #%d\n", s1)
	fmt.Printf("  • user-bob-202     -> Шард #%d\n", s2)
	fmt.Printf("  • user-charlie-303 -> Шард #%d\n", s3)
	fmt.Println("  • Запросы прозрачно распределены между независимыми инстансами БД")
}
```

ℹ️ Детерминированное распределение данных по шардам СУБД с помощью хэш-функции FNV

## Под капотом

При обычном `hash % N` добавление нового шарда (\(N+1\)) приводит к перемещению почти всех ключей (Resharding). Поэтому в HighLoad применяют **Консистентное хэширование (Consistent Hashing)** с виртуальными нодами на кольце хэшей, где добавление ноды перемещает только \(K/N\) ключей.

## Подводные камни

Выбирать ключ шардирования с плохим распределением (Low Cardinality, например `country_code`): весь трафик из РФ пойдет в один шард, создав «горячую ноду» (Hot Shard), а остальные шарды будут простаивать.

## На собеседовании

**Вопрос с собеседования:** «Как выполнить кросс-шардовый поиск (Cross-Shard Query) при шардировании по user_id (например SELECT * WHERE created_at > yesterday)?»
**Ответ:** Паттерн Scatter-Gather (Рассылка-Сбор): Go сервис параллельно запускает горутины ко всем \(N\) шардам через `sync.WaitGroup`, собирает результаты выборок в память и выполняет итоговую сортировку (Merge Sort). Если таких запросов много — строят денормализованный индекс в Elasticsearch.
