# Идемпотентный эндпоинт создания платежа: обработка заголовка Idempotency-Key

## Условие

**Идемпотентные API**. Реализуйте эндпоинт создания платежа, который принимает `idempotency-key`. Повторный запрос с тем же ключом возвращает сохранённый результат, не выполняя операцию повторно.

## Теория

Проектирование идемпотентного HTTP-хендлера:
- Хэндлер извлекает `key := r.Header.Get("Idempotency-Key")`.
- Если ключ отсутствует, сервер возвращает `400 Bad Request`.
- Вызывается атомарная транзакция сохранения ключа в БД.
- Если ключ уже существует, хэндлер парсит сохраненный ранее JSON-ответ и отдает его клиенту.
- Гарантирует абсолютную защиту от двойного списания денег при потере сетевого пакета подтверждения.

## Решение по шагам

1. Создайте HTTP-хендлер с проверкой заголовка `Idempotency-Key`.
2. Реализуйте кэш ответов первого запроса.
3. Смоделируйте повторный запрос клиента.
4. Верифицируйте возврат статуса 201 и сохранение идемпотентности.

## Код решения

**`idempotent_payment_handler_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"testing"
)

type IdempotentPaymentServer struct {
	mu            sync.Mutex
	cachedOutputs map[string]int
	chargesCount  int
}

func (s *IdempotentPaymentServer) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	if key == "" {
		http.Error(w, "missing Idempotency-Key header", http.StatusBadRequest)
		return
	}

	s.mu.Lock()
	defer s.mu.Unlock()

	if code, found := s.cachedOutputs[key]; found {
		// Повторный запрос: отдаем закэшированный статус БЕЗ повторного списания
		w.WriteHeader(code)
		w.Write([]byte(`{"status":"already_processed"}`))
		return
	}

	// Первое списание
	s.chargesCount++
	s.cachedOutputs[key] = http.StatusCreated

	w.WriteHeader(http.StatusCreated)
	w.Write([]byte(`{"status":"charge_success"}`))
}

func TestIdempotentPaymentHandler(t *testing.T) {
	server := &IdempotentPaymentServer{cachedOutputs: make(map[string]int)}
	idemKey := "key-trans-444"

	// 1. Первый вызов
	req1 := httptest.NewRequest(http.MethodPost, "/charge", nil)
	req1.Header.Set("Idempotency-Key", idemKey)
	rec1 := httptest.NewRecorder()
	server.ServeHTTP(rec1, req1)

	if rec1.Code != http.StatusCreated {
		t.Fatalf("Ожидался статус 201, получено: %d", rec1.Code)
	}

	// 2. Повторный вызов (ретрай мобильного приложения)
	req2 := httptest.NewRequest(http.MethodPost, "/charge", nil)
	req2.Header.Set("Idempotency-Key", idemKey)
	rec2 := httptest.NewRecorder()
	server.ServeHTTP(rec2, req2)

	if rec2.Code != http.StatusCreated {
		t.Fatalf("Ожидался статус 201 для повторного запроса: %d", rec2.Code)
	}

	if server.chargesCount != 1 {
		t.Fatalf("Ожидалось ровно 1 списание, выполнено: %d", server.chargesCount)
	}

	fmt.Println("Идемпотентный эндпоинт платежей успешно подтвержден:")
	fmt.Printf("  • Запрос 1: Код %d (Выполнено списание)\n", rec1.Code)
	fmt.Printf("  • Запрос 2: Код %d (Возвращен результат из хранилища идемпотентности)\n", rec2.Code)
	fmt.Printf("  • Реальных списаний со счета: %d\n", server.chargesCount)
}
```

## Под капотом

В распределенной системе запись ключа идемпотентности выполняется атомарно с операцией списания через двухфазный коммит или Transactional Outbox, чтобы исключить сценарий, когда деньги списались, а ключ сохранить не удалось.

## Подводные камни

Хранить ключи идемпотентности вечно: таблица разрастется до сотен миллионов строк. Ключам выставляют время жизни (TTL = 24 часа). Клиент не должен делать ретраи вчерашних запросов.

## На собеседовании

**Вопрос с собеседования:** «Являются ли методы HTTP GET, PUT, DELETE идемпотентными по спецификации RFC?»
**Ответ:** По спецификации HTTP:
- `GET`, `HEAD`, `OPTIONS` — безопасные и идемпотентные.
- `PUT`, `DELETE` — **идемпотентные** (повторный `DELETE /item/1` приводит к тому же результату — ресурса нет).
- `POST`, `PATCH` — **НЕ идемпотентные** по умолчанию, поэтому именно для них внедряют `Idempotency-Key`.
