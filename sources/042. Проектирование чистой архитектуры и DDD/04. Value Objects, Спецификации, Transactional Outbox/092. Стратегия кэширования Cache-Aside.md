# Стратегия кэширования Cache-Aside: проверка кэша Redis, чтение из БД и инвалидация при мутациях

## Условие

**Стратегии кэширования**. Реализуйте Cache-Aside для получения профиля пользователя (проверка кэша → БД → запись в кэш). Добавьте инвалидацию при обновлении. Используйте Redis.

## Теория

Паттерн кэширования Cache-Aside (Lazy Loading):
- **Операция чтения (Read Flow):**
  1. Сервис ищет ключ в кэше: `redis.Get("user:101")`.
  2. Если Cache Hit (попадание) \(\implies\) мгновенный возврат клиенту (1 мс).
  3. Если Cache Miss (промах) \(\implies\) запрос в PostgreSQL `SELECT * FROM users WHERE id = 101` (15 мс).
  4. Запись значения в кэш с TTL: `redis.Set("user:101", user, 10*time.Minute)`.
  5. Возврат клиенту.
- **Операция записи (Invalidation Flow):**
  1. Обновление записи в PostgreSQL.
  2. Инвалидация (удаление) ключа из кэша: `redis.Del("user:101")`.
- Удаление ключа предпочтительнее перезаписи, так как защищает от race conditions.

## Решение по шагам

1. Создайте структуру хранилища с кэшем и базой данных.
2. Реализуйте алгоритм Cache-Aside в методе `GetUserProfile`.
3. Реализуйте инвалидацию кэша в методе `UpdateUserProfile`.
4. Верифицируйте попадания в кэш и корректный сброс.

## Код решения

**`cache_aside_pattern_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type CacheAsideService struct {
	cache       map[string]string
	db          map[string]string
	dbHitsCount int
}

func (s *CacheAsideService) GetUser(ctx context.Context, id string) string {
	// 1. Проверяем кэш
	if val, ok := s.cache[id]; ok {
		return val // Cache Hit!
	}

	// 2. Cache Miss: идем в БД
	s.dbHitsCount++
	val := s.db[id]

	// 3. Заполняем кэш
	s.cache[id] = val
	return val
}

func (s *CacheAsideService) UpdateUser(ctx context.Context, id, newName string) {
	// 1. Обновляем БД
	s.db[id] = newName
	// 2. Инвалидация кэша
	delete(s.cache, id)
}

func TestCacheAsidePattern(t *testing.T) {
	svc := &CacheAsideService{
		cache: make(map[string]string),
		db:    map[string]string{"u-1": "Илья Семенов"},
	}

	// Запрос 1: Cache Miss -> чтение из БД
	res1 := svc.GetUser(context.Background(), "u-1")
	if res1 != "Илья Семенов" || svc.dbHitsCount != 1 {
		t.Fatalf("Сбой первого чтения: %s, hits: %d", res1, svc.dbHitsCount)
	}

	// Запрос 2: Cache Hit -> чтение из памяти без БД!
	res2 := svc.GetUser(context.Background(), "u-1")
	if res2 != "Илья Семенов" || svc.dbHitsCount != 1 {
		t.Fatalf("Второй запрос должен был взять из кэша без похода в БД! hits: %d", svc.dbHitsCount)
	}

	// Обновление пользователя -> сброс кэша
	svc.UpdateUser(context.Background(), "u-1", "Илья Семенов (VIP)")

	// Запрос 3: Cache Miss после инвалидации -> чтение свежих данных из БД
	res3 := svc.GetUser(context.Background(), "u-1")
	if res3 != "Илья Семенов (VIP)" || svc.dbHitsCount != 2 {
		t.Fatalf("Сбой чтения после инвалидации: %s", res3)
	}

	fmt.Println("Стратегия кэширования Cache-Aside успешно подтверждена:")
	fmt.Printf("  • Запрос 1: Чтение из БД (DB Hits: 1)\n")
	fmt.Printf("  • Запрос 2: Мгновенно из кэша (DB Hits: 1)\n")
	fmt.Printf("  • Запрос 3 (после Update): Кэш инвалидирован, данные обновлены: %s\n", res3)
}
```

## Под капотом

В HighLoad системах при одновременном истечении TTL у популярного ключа тысячи горутин одновременно идут в БД (Cache Stampede / Thundering Herd). Для защиты используют `singleflight.Group` из стандартного репозитория `golang.org/x/sync/singleflight`, объединяя параллельные запросы в один поход к БД.

## Подводные камни

Выставлять одинаковый TTL всем ключам кэша (например ровно 60 минут): через час все ключи истекут в одну миллисекунду, и вся нагрузка обрушится на БД. Всегда добавляют случайный джиттер: `ttl = baseTTL + rand.Duration(5 * time.Minute)`.

## На собеседовании

**Вопрос с собеседования:** «Почему при обновлении сущности нужно удалять ключ из кэша (DEL), а не перезаписывать новым значением (SET)?»
**Ответ:** Из-за гонки параллельных запросов (Race Condition). Если транзакция 1 запишет в кэш значение A, а параллельная транзакция 2 перезапишет значением B, при определенных задержках сети старое значение может перезаписать новое. Инвалидация через `DEL` гарантирует, что следующий читатель прочитает самое свежее закоммиченное состояние из БД.
