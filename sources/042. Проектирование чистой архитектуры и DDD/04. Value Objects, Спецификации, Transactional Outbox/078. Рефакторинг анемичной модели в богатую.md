# Рефакторинг анемичной модели в богатую: защита целостности сущности Order через инварианты

## Условие

**Рефакторинг из анемичной в богатую модель**: Возьмите анемичную структуру `Order` (все поля публичные, валидация в хэндлере) и отрефакторите её в богатую доменную модель: приватные поля, конструктор с валидацией, методы `AddItem`, `ApplyDiscount`, `Cancel`.

### Исходная формулировка

**Разделение DTO и Domain Models**: Напиши структуру `CreateUserRequest` (DTO) для парсинга JSON (с тегами `json` и `validate`) и структуру `User` (доменная сущность) для логики. Напиши маппер (функцию-преобразователь), который перекладывает данные из DTO в доменную модель после синтаксической валидации.

## Теория

Пошаговый рефакторинг Anemic \(\to\) Rich Domain Model:
1. **Шаг 1: Инкапсуляция полей.** Делаем поля `status`, `items`, `total` приватными (с маленькой буквы).
2. **Шаг 2: Создание фабрики.** Создаем `NewOrder()`, который гарантирует, что сущность не может появиться на свет в невалидном состоянии.
3. **Шаг 3: Перенос поведения.** Забираем проверки из HTTP-хэндлеров и Use Cases и переносим их в методы сущности:
   - Не `service.CancelOrder(o)`, а `o.Cancel()`.
   - Не `items = append(items, item)`, а `o.AddItem(item)`.
4. Кодовая база становится защищенной от некорректных мутаций компилятором Go.

## Решение по шагам

1. Создайте богатую сущность `RefactoredOrder`.
2. Реализуйте методы добавления позиций и применения промокода.
3. Защитите заказ от модификации после отмены.
4. Верифицируйте инварианты целостности.

## Код решения

**`anemic_to_rich_refactoring_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

// Богатая доменная модель (Rich Domain Model)
type RefactoredOrder struct {
	id         string
	isCanceled bool
	totalRub   float64
}

func NewRefactoredOrder(id string) (*RefactoredOrder, error) {
	if id == "" {
		return nil, errors.New("order id cannot be empty")
	}
	return &RefactoredOrder{id: id}, nil
}

func (o *RefactoredOrder) Total() float64 { return o.totalRub }

func (o *RefactoredOrder) AddItem(price float64) error {
	if o.isCanceled {
		return errors.New("cannot modify canceled order")
	}
	if price <= 0 {
		return errors.New("item price must be positive")
	}
	o.totalRub += price
	return nil
}

func (o *RefactoredOrder) Cancel() error {
	if o.isCanceled {
		return errors.New("order is already canceled")
	}
	o.isCanceled = true
	return nil
}

func TestAnemicToRichRefactoring(t *testing.T) {
	order, err := NewRefactoredOrder("ord-rich-100")
	if err != nil {
		t.Fatalf("Ошибка создания заказа: %v", err)
	}

	_ = order.AddItem(3500.0)
	_ = order.AddItem(1500.0)

	if order.Total() != 5000.0 {
		t.Fatalf("Некорректная сумма заказа: %.2f", order.Total())
	}

	_ = order.Cancel()

	// Попытка добавить товар в отмененный заказ должна вернуть ошибку!
	errAfterCancel := order.AddItem(200.0)
	if errAfterCancel == nil {
		t.Fatal("Инвариант нарушен: товар добавлен в отмененный заказ")
	}

	fmt.Println("Рефакторинг в богатую доменную модель успешно подтвержден:")
	fmt.Printf("  • Итоговая сумма заказа: %.2f руб\n", order.Total())
	fmt.Println("  • Попытка мутации отмененного заказа надежно заблокирована сущностью")
}
```

ℹ️ Устранение анемичности: защита инвариантов и мутация только через методы сущности

## Под капотом

В богатой модели состояние объекта всегда валидно в любой момент времени (Always-Valid Domain Model). Это избавляет от необходимости писать защитные проверки `if order.Total < 0` во всех сервисах приложения.

## Подводные камни

Возвращать структуры с публичными полями из приватных методов сущности: если метод возвращает срез объектов, вызывающий код может изменить его элементы. Возвращают копии срезов.

## На собеседовании

**Вопрос с собеседования:** «Как сохранять в БД сущность с приватными полями, если ORM требует публичные поля?»
**Ответ:** Используют паттерн Memento или отдельную модель персистентности (DB Model). Сущность реализует метод экспорта состояния `ToSnapshot() OrderSnapshot`, который маппится в запись базы данных в слое репозитория.
