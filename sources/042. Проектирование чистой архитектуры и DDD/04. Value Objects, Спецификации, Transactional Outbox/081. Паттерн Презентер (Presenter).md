# Паттерн Презентер (Presenter): безопасная трансформация доменной модели в UserResponse DTO

## Условие

**Паттерн Presenter**: Хендлер получил доменную модель `User` из сервиса. У `User` есть приватные поля и хеш пароля. Напиши `UserPresenter` — функцию, которая конвертирует доменную сущность в `UserResponse` DTO для безопасной отправки клиенту в виде JSON.

## Теория

Изоляция приватных данных через Presentation Model:
- **Катастрофическая ошибка:** Сериализовать доменную сущность напрямую в JSON ответ клиенту.
  - Поле `PasswordHash` утекает злоумышленникам.
  - Добавление приватного поля в сущность ломает обратную совместимость API.
- **Паттерн Presenter:**
  - Специализированный маппер слоя представления (Delivery / Presentation).
  - Преобразует внутреннюю модель `User` в строгий публичный контракт `UserResponseDTO`.
  - Маскирует персональные данные (номер телефона `+7 *** *** 45`).
  - Форматирует даты и денежные суммы в локаль пользователя.

## Решение по шагам

1. Создайте доменную сущность `DomainAccountModel` с хэшем пароля.
2. Создайте структуру публичного ответа `UserResponseDTO`.
3. Реализуйте функцию `UserPresenter.FormatPublicResponse`.
4. Верифицируйте сокрытие приватных полей.

## Код решения

**`presenter_dto_masking_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"strings"
	"testing"
)

type DomainAccountModel struct {
	ID           string
	Email        string
	PasswordHash string // СЕКРЕТНО!
	BalanceKop   int64
}

// Presentation Model (DTO)
type UserResponseDTO struct {
	ID         string `json:"id"`
	Email      string `json:"email"`
	BalanceRub string `json:"balance_rub"`
}

type UserPresenter struct{}

func (p *UserPresenter) FormatPublicResponse(u DomainAccountModel) UserResponseDTO {
	return UserResponseDTO{
		ID:         u.ID,
		Email:      u.Email,
		BalanceRub: fmt.Sprintf("%.2f ₽", float64(u.BalanceKop)/100.0),
	}
}

func TestPresenterDTOMasking(t *testing.T) {
	domainUser := DomainAccountModel{
		ID:           "u-456",
		Email:        "client@bank.ru",
		PasswordHash: "$2a$12$e8YQZ7v9K2L1.hashSecret",
		BalanceKop:   125050,
	}

	presenter := &UserPresenter{}
	dto := presenter.FormatPublicResponse(domainUser)

	jsonBytes, _ := json.Marshal(dto)
	jsonStr := string(jsonBytes)

	if strings.Contains(jsonStr, "hashSecret") || strings.Contains(jsonStr, "PasswordHash") {
		t.Fatal("УТЕЧКА ДАННЫХ: хэш пароля попал в сериализованный JSON!")
	}

	if dto.BalanceRub != "1250.50 ₽" {
		t.Fatalf("Некорректное форматирование баланса: %s", dto.BalanceRub)
	}

	fmt.Println("Паттерн Презентер (Presenter) успешно подтвержден:")
	fmt.Printf("  • JSON ответ клиенту: %s\n", jsonStr)
	fmt.Println("  • Хэш пароля надежно отфильтрован презентером; баланс отформатирован в рубли")
}
```

## Под капотом

Presenter отделяет модель отображения от модели хранения. Если завтра веб-клиенту потребуется отдавать баланс в долларах, модифицируется только презентер, а доменная сущность с копейками остается нетронутой.

## Подводные камни

Помещать в Presenter сложные обращения к базе данных или сторонним сервисам: презентер должен быть чистым синхронным преобразователем данных без побочных эффектов.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Presenter в Clean Architecture от ViewModel в MVVM?»
**Ответ:** Концептуально они идентичны: оба представляют собой структуры данных, подготовленные специально под нужды конкретного экрана или формата представления. В Clean Architecture Presenter берет доменные данные из Use Case и упаковывает их в структуры, удобные для веб-контроллера.
