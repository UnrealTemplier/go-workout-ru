# Паттерн Спецификация (Specification Pattern): композиция составных бизнес-правил отбора сущностей

## Условие

**Паттерн Спецификация (Specification)**: Реализуйте паттерн Specification для проверки сложных условий (например, `CustomerEligibleForLoanSpecification`). Реализуйте методы `IsSatisfiedBy(c Customer) bool`, `And(other Spec)`, `Or(other Spec)`.

### Исходная формулировка

**Database per Service**: Каждый микросервис имеет свою БД. Используйте event sourcing или CDC для синхронизации данных между сервисами.

## Теория

Паттерн Спецификация (Specification Pattern, Эрик Эванс):
- Позволяет инкапсулировать предикаты бизнес-правил в независимые объекты:
  `type Specification interface { IsSatisfiedBy(entity) bool }`
- **Преимущества композиции:**
  - Простые правила (`AgeOver21Spec`, `NoOverdueDebtsSpec`, `MinIncomeSpec`) объединяются логическими операторами `And()`, `Or()`, `Not()`.
  - Одно и то же правило используется:
    1. Для валидации в памяти (`spec.IsSatisfiedBy(customer)`).
    2. Для генерации SQL-запроса в репозитории (`spec.ToSQL()`).

## Решение по шагам

1. Создайте интерфейс `Specification` с методами `IsSatisfiedBy` и `And`.
2. Реализуйте две простые спецификации: по возрасту и по доходу.
3. Объедините их через логический оператор `AndSpecification`.
4. Верифицируйте корректность составного предиката.

## Код решения

**`specification_pattern_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type LoanApplicant struct {
	Age    int
	Income int64
}

type LoanSpecification interface {
	IsSatisfiedBy(a LoanApplicant) bool
	And(other LoanSpecification) LoanSpecification
}

type baseSpec struct {
	self LoanSpecification
}

func (b *baseSpec) And(other LoanSpecification) LoanSpecification {
	return &AndSpecification{left: b.self, right: other}
}

type AndSpecification struct {
	left, right LoanSpecification
}

func (s *AndSpecification) IsSatisfiedBy(a LoanApplicant) bool {
	return s.left.IsSatisfiedBy(a) && s.right.IsSatisfiedBy(a)
}

func (s *AndSpecification) And(other LoanSpecification) LoanSpecification {
	return &AndSpecification{left: s, right: other}
}

// Конкретная спецификация 1: Возраст >= 21
type AgeSpecification struct {
	baseSpec
	minAge int
}

func NewAgeSpec(minAge int) *AgeSpecification {
	s := &AgeSpecification{minAge: minAge}
	s.self = s
	return s
}

func (s *AgeSpecification) IsSatisfiedBy(a LoanApplicant) bool {
	return a.Age >= s.minAge
}

// Конкретная спецификация 2: Доход >= 50,000 руб
type IncomeSpecification struct {
	baseSpec
	minIncome int64
}

func NewIncomeSpec(minIncome int64) *IncomeSpecification {
	s := &IncomeSpecification{minIncome: minIncome}
	s.self = s
	return s
}

func (s *IncomeSpecification) IsSatisfiedBy(a LoanApplicant) bool {
	return a.Income >= s.minIncome
}

func TestSpecificationPattern(t *testing.T) {
	ageSpec := NewAgeSpec(21)
	incomeSpec := NewIncomeSpec(50_000)

	// Композиция спецификаций: Возраст >= 21 И Доход >= 50K
	loanEligibleSpec := ageSpec.And(incomeSpec)

	candidateGood := LoanApplicant{Age: 25, Income: 80_000}
	candidateTooYoung := LoanApplicant{Age: 19, Income: 100_000}

	if !loanEligibleSpec.IsSatisfiedBy(candidateGood) {
		t.Fatal("Кандидат должен подходить под условия кредита")
	}

	if loanEligibleSpec.IsSatisfiedBy(candidateTooYoung) {
		t.Fatal("Кандидат младше 21 года не должен проходить спецификацию")
	}

	fmt.Println("Паттерн Спецификация (Specification Pattern) подтвержден:")
	fmt.Printf("  • Кандидат 25 лет с доходом 80K руб: Одобрен (%v)\n", loanEligibleSpec.IsSatisfiedBy(candidateGood))
	fmt.Printf("  • Кандидат 19 лет с доходом 100K руб: Отклонен (%v)\n", loanEligibleSpec.IsSatisfiedBy(candidateTooYoung))
	fmt.Println("  • Бизнес-правила скомпонованы через спецификацию And()")
}
```

## Под капотом

Спецификации строят синтаксическое дерево предикатов (Composite Pattern). В репозиториях Go спецификация может транслироваться в SQL `WHERE age >= 21 AND income >= 50000` через SQL-билдеры (`squirrel` или `gorm`), исключая расхождения между логикой в коде и запросом к базе данных.

## Подводные камни

Создавать глубокие деревья спецификаций из 20 вложенных `And/Or`: это усложняет чтение и отладку. Для комплексных правил формулируют именованную спецификацию верхнего уровня `GoldCustomerSpecification`.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Specification от Strategy Pattern?»
**Ответ:** 
- **Strategy** отвечает за алгоритм вычисления («Как именно посчитать маршрут или сжать файл?»).
- **Specification** отвечает строго на булев вопрос соответствия критериям («Подходит ли эта сущность под заданное бизнес-правило? Да/Нет»).
