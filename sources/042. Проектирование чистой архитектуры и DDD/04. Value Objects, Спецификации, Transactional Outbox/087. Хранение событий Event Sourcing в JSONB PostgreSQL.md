# Хранение событий Event Sourcing в JSONB PostgreSQL: Append-Only лог и десериализация

## Условие

**Event Sourcing**. Храните не текущее состояние заказа, а последовательность событий (`OrderCreated`, `ItemAdded`, `OrderConfirmed`). Восстанавливайте состояние проигрыванием событий. Реализуйте с JSON-колонкой в PostgreSQL.

## Теория

Реализация Event Store на базе реляционной СУБД (PostgreSQL JSONB):
- Для Event Sourcing не обязательно разворачивать экзотические базы данных. PostgreSQL идеально подходит на роль Event Store:
  ```sql
  CREATE TABLE event_store (
      aggregate_id VARCHAR(64) NOT NULL,
      version INT NOT NULL,
      event_type VARCHAR(128) NOT NULL,
      payload JSONB NOT NULL,
      created_at TIMESTAMPTZ DEFAULT NOW(),
      PRIMARY KEY (aggregate_id, version)
  );
  ```
- **Гарантии PostgreSQL:**
  1. `PRIMARY KEY (aggregate_id, version)` гарантирует Optimistic Concurrency Control.
  2. Индекс GIN по колонке `payload JSONB` позволяет выполнять поиск по внутренним полям событий.
  3. ACID транзакции гарантируют сохранность лога.

## Решение по шагам

1. Создайте модель записи таблицы `EventStoreRecord`.
2. Смоделируйте сериализацию разных типов доменных событий в JSON.
3. Восстановите агрегат из массива записей.
4. Верифицируйте десериализацию и итоговое состояние.

## Код решения

**`postgres_jsonb_event_store_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type EventStoreRecord struct {
	AggregateID string
	Version     int
	EventType   string
	PayloadJSON string
}

type OrderHistoryState struct {
	ID        string
	Confirmed bool
	Items     []string
}

func TestPostgresJSONBEventStore(t *testing.T) {
	// Имитация строк таблицы event_store из PostgreSQL
	dbRows := []EventStoreRecord{
		{AggregateID: "ord-json-1", Version: 1, EventType: "OrderCreated", PayloadJSON: `{"id":"ord-json-1"}`},
		{AggregateID: "ord-json-1", Version: 2, EventType: "ItemAdded", PayloadJSON: `{"item":"Клавиатура Механическая"}`},
		{AggregateID: "ord-json-1", Version: 3, EventType: "OrderConfirmed", PayloadJSON: `{}`},
	}

	state := OrderHistoryState{}

	// Воспроизведение событий (Replay)
	for _, row := range dbRows {
		switch row.EventType {
		case "OrderCreated":
			state.ID = row.AggregateID
		case "ItemAdded":
			var p struct{ Item string }
			_ = json.Unmarshal([]byte(row.PayloadJSON), &p)
			state.Items = append(state.Items, p.Item)
		case "OrderConfirmed":
			state.Confirmed = true
		}
	}

	if state.ID != "ord-json-1" || len(state.Items) != 1 || !state.Confirmed {
		t.Fatalf("Сбой восстановления агрегата: %+v", state)
	}

	fmt.Println("Event Sourcing в PostgreSQL (JSONB) успешно подтвержден:")
	fmt.Printf("  • Восстановлен заказ ID: %s\n", state.ID)
	fmt.Printf("  • Позиции: %v, Статус Confirmed: %v\n", state.Items, state.Confirmed)
	fmt.Println("  • Таблица event_store хранит неизменяемый Append-Only аудит изменений")
}
```

## Под капотом

Колонка `JSONB` в PostgreSQL хранит бинарный декомпозированный JSON. При десериализации в Go структура парсится стандартным `encoding/json` или высокоскоростным генератором кода `easyjson`.

## Подводные камни

Выполнять `UPDATE event_store SET payload = ...`: нарушение принципа иммутабельности событий уничтожает доверие к аудиту. Ошибочные операции компенсируют добавлением **нового корректирующего события**.

## На собеседовании

**Вопрос с собеседования:** «Как соблюдать требования закона о персональных данных (GDPR / 152-ФЗ "Право на забвение") в неизменяемом Event Sourcing?»
**Ответ:** Паттерн **Crypto-Shredding**: персональные данные в событиях шифруются персональным ключом шифрования пользователя (`UserEncryptionKey`), который хранится отдельно. Когда пользователь требует удалить свои данные, его ключ шифрования безвозвратно удаляется. Сами события остаются в логе, но их полезная нагрузка превращается в нечитаемый мусор.
