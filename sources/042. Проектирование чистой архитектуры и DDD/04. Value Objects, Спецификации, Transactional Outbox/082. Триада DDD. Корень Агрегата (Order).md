# Триада DDD: Корень Агрегата (Order), Сущность (OrderItem) и Объект-Значение (Address)

## Условие

**Domain-Driven Design: Entities, Value Objects, Aggregate Root**. Спроектируйте заказ как агрегат: `Order` (root), `OrderItem` (entity), `Address` (value object). Вся логика изменения заказа только через методы агрегата.

## Теория

Симбиоз трех базовых строительных блоков DDD:
1. **Aggregate Root (`Order`):** Корень агрегата с глобальным идентификатором `OrderID`. Координирует изменение состояния, гарантирует бизнес-инварианты.
2. **Entity (`OrderItem`):** Внутренняя сущность с локальным идентификатором `ItemLineID`. Имеет изменяемое количество, но не существует вне заказа.
3. **Value Object (`Address`):** Неизменяемый адрес доставки (улица, город, индекс). Не имеет ID, равенство определяется по совпадению всех полей.
- Внешний код взаимодействует со всеми частями **строго через корень агрегата `Order`**!

## Решение по шагам

1. Создайте Value Object `DeliveryAddress`.
2. Создайте сущность `OrderItemEntity`.
3. Создайте корень агрегата `OrderDDD`.
4. Верифицируйте согласованную модификацию через корень.

## Код решения

**`ddd_triad_aggregate_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

// 1. Value Object: Address (Неизменяемый)
type DeliveryAddressVO struct {
	City   string
	Street string
	Zip    string
}

// 2. Entity: OrderItem (Внутренняя сущность)
type OrderItemChild struct {
	LineID string
	SKU    string
	Qty    int
	Price  float64
}

// 3. Aggregate Root: Order
type OrderDDDRoot struct {
	id      string
	address DeliveryAddressVO
	items   []OrderItemChild
}

func NewOrderDDDRoot(id string, addr DeliveryAddressVO) *OrderDDDRoot {
	return &OrderDDDRoot{id: id, address: addr}
}

func (o *OrderDDDRoot) AddLineItem(lineID, sku string, qty int, price float64) error {
	if qty <= 0 {
		return errors.New("quantity must be positive")
	}
	o.items = append(o.items, OrderItemChild{LineID: lineID, SKU: sku, Qty: qty, Price: price})
	return nil
}

func (o *OrderDDDRoot) ItemsTotalCount() int {
	total := 0
	for _, it := range o.items {
		total += it.Qty
	}
	return total
}

func TestDDDTriadAggregate(t *testing.T) {
	addr := DeliveryAddressVO{City: "Москва", Street: "Тверская, д. 7", Zip: "125009"}
	order := NewOrderDDDRoot("ord-triad-1", addr)

	_ = order.AddLineItem("line-1", "sku-book", 2, 800.0)
	_ = order.AddLineItem("line-2", "sku-pen", 5, 120.0)

	if order.ItemsTotalCount() != 7 {
		t.Fatalf("Некорректный подсчет позиций в агрегате: %d", order.ItemsTotalCount())
	}

	fmt.Println("Триада DDD (Root, Entity, Value Object) успешно подтверждена:")
	fmt.Printf("  • Aggregate Root: Order ID=%s\n", order.id)
	fmt.Printf("  • Value Object:   Адрес доставки: г. %s, %s (Zip: %s)\n",
		order.address.City, order.address.Street, order.address.Zip)
	fmt.Printf("  • Child Entities: Позиций в заказе: %d шт\n", order.ItemsTotalCount())
}
```

ℹ️ Классический агрегат DDD, объединяющий корень, дочерние сущности и объекты-значения

## Под капотом

В DDD агрегат является единицей блокировки при параллельных изменениях. При сохранении агрегата в БД обновляется номер версии `version = version + 1`, что защищает все внутренние дочерние сущности и адреса от несогласованных параллельных модификаций.

## Подводные камни

Выдавать наружу прямой указатель на дочернюю сущность `OrderItemChild`: внешний код может изменить количество в обход бизнес-правил корня агрегата.

## На собеседовании

**Вопрос с собеседования:** «Может ли один агрегат содержать внутри себя другой агрегат?»
**Ответ:** Категорически нет! Агрегаты не могут быть вложены друг в друга. Агрегат может ссылаться на другой агрегат **только по его глобальному идентификатору (ID)**. Если вам кажется, что один агрегат должен быть внутри другого — либо один из них не является агрегатом (а обычной сущностью/Value Object), либо между ними должно быть слабое связывание по ID.
