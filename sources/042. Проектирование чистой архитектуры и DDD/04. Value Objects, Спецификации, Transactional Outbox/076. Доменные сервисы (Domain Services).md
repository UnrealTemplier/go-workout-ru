# Доменные сервисы (Domain Services): реализация сквозных бизнес-правил между несколькими агрегатами

## Условие

**Доменные сервисы (Domain Services)**: Напишите доменный сервис `TransferService.Transfer(from, to *Account, amount Money) error`. Объясните, почему эту логику нельзя поместить внутрь самого `Account`.

### Исходная формулировка

**Strangler Fig Pattern**: Постепенно мигрируйте с монолита на микросервисы, перенаправляя трафик через API Gateway на новые сервисы по мере их готовности.

## Теория

Зачем нужны Domain Services в DDD:
- Когда бизнес-операция затрагивает **два или более независимых агрегата** (например, банковский перевод со счета A на счет B):
  - Поместить метод в счет A: `fromAccount.TransferTo(toAccount, amount)` — это нарушение симметрии и инкапсуляции (счет A вынужден знать о внутренностях счета B).
  - Поместить в Application Service: бизнес-логика комиссий и проверок утечет из домена в слой сценариев.
- **Решение — Доменный Сервис (Domain Service):**
  - Чистый сервис внутри пакета `domain`.
  - Не имеет состояния (Stateless).
  - Оркестрирует бизнес-правило между несколькими сущностями: списывает со счета A, начисляет комиссию банку, зачисляет остаток на счет B.

## Решение по шагам

1. Создайте агрегат `Account`.
2. Реализуйте доменный сервис `FundsTransferDomainService`.
3. Опишите атомарный перевод между счетами с валидацией инвариантов.
4. Верифицируйте корректность балансов обоих счетов.

## Код решения

**`domain_service_transfer_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type TransferAccount struct {
	ID      string
	Balance int64
}

func (a *TransferAccount) Debit(amount int64) error {
	if a.Balance < amount {
		return errors.New("insufficient balance")
	}
	a.Balance -= amount
	return nil
}

func (a *TransferAccount) Credit(amount int64) {
	a.Balance += amount
}

// Domain Service: чистая бизнес-логика перевода между двумя агрегатами
type FundsTransferDomainService struct{}

func (s *FundsTransferDomainService) Transfer(from, to *TransferAccount, amount int64) error {
	if from.ID == to.ID {
		return errors.New("cannot transfer funds to the same account")
	}
	if amount <= 0 {
		return errors.New("transfer amount must be positive")
	}

	// Списание со счета отправителя
	if err := from.Debit(amount); err != nil {
		return fmt.Errorf("debit failed: %w", err)
	}

	// Зачисление на счет получателя
	to.Credit(amount)
	return nil
}

func TestDomainServiceTransfer(t *testing.T) {
	acc1 := &TransferAccount{ID: "acc-from", Balance: 50_000}
	acc2 := &TransferAccount{ID: "acc-to", Balance: 10_000}

	transferSvc := &FundsTransferDomainService{}
	err := transferSvc.Transfer(acc1, acc2, 20_000)

	if err != nil || acc1.Balance != 30_000 || acc2.Balance != 30_000 {
		t.Fatalf("Ошибка перевода через доменный сервис: %v", err)
	}

	fmt.Println("Доменный сервис (Domain Service) успешно подтвержден:")
	fmt.Printf("  • Баланс отправителя: %d коп.\n", acc1.Balance)
	fmt.Printf("  • Баланс получателя:  %d коп.\n", acc2.Balance)
	fmt.Println("  • Логика межагрегатного взаимодействия инкапсулирована в FundsTransferDomainService")
}
```

## Под капотом

Доменный сервис не открывает транзакций базы данных и не делает SQL запросов. Управление транзакцией и сохранение обоих счетов выполняет вызывающий Application Service через Unit of Work.

## Подводные камни

Превращать Domain Services в свалку процедурного кода, забирая всю логику из сущностей: сущности снова станут анемичными. В Domain Service выносят только ту логику, которая принципиально не принадлежит одной сущности.

## На собеседовании

**Вопрос с собеседования:** «В каком пакете должен располагаться Domain Service?»
**Ответ:** Строго в пакете `domain` (или внутри конкретного доменного пакета `internal/billing`). Он не имеет внешних зависимостей от инфраструктуры, баз данных и фреймворков.
