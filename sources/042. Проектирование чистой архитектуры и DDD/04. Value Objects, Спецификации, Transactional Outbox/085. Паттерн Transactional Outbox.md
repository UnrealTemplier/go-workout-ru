# Паттерн Transactional Outbox: гарантированная публикация доменных событий после коммита в БД

## Условие

**Доменные события (Domain Events)**: Измените ваш Агрегат `Order` с инкапсулированными OrderItem. Добавьте в структуру `Order` внутренний слайс `events []DomainEvent`. При изменении статуса заказа на "Оплачен" агрегат должен сгенерировать и положить в этот слайс событие `OrderPaidEvent`. Напишите юзкейс, который после успешного сохранения транзакции заказа в БД считывает накопившиеся события из агрегата и публикует их в брокер сообщений.

## Теория

Паттерн Transactional Outbox (Гарантированная доставка событий):
- **Проблема Dual-Write (Двойная запись):**
  Если сначала закоммитить БД, а потом отправить в Kafka — процесс может упасть между этими действиями, и событие никогда не уйдет.
  Если сначала отправить в Kafka, а потом коммитить БД — БД может откатиться (Rollback), а событие об оплате уже ушло!
- **Решение Transactional Outbox:**
  1. В транзакции БД сохраняется заказ `INSERT INTO orders ...`
  2. В той же самой транзакции события заказа сохраняются в специальную таблицу:
     `INSERT INTO outbox_events (id, payload, status) VALUES (...)`
  3. Транзакция коммитится атомарно!
  4. Фоновый Relay-процесс считывает таблицу Outbox и отправляет события в Kafka с гарантией At-Least-Once.

## Решение по шагам

1. Создайте событие `OrderPaidEvent`.
2. Реализуйте генерацию события внутри агрегата при вызове `MarkPaid()`.
3. Смоделируйте сохранение заказа и Outbox-события в единой транзакции.
4. Верифицируйте отсутствие потери событий.

## Код решения

**`transactional_outbox_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type DomainEventObj interface {
	EventName() string
}

type OrderPaidEventObj struct {
	OrderID string
}

func (e OrderPaidEventObj) EventName() string { return "order.paid" }

type OutboxOrderAggregate struct {
	id     string
	paid   bool
	events []DomainEventObj
}

func (o *OutboxOrderAggregate) MarkPaid() {
	o.paid = true
	o.events = append(o.events, OrderPaidEventObj{OrderID: o.id})
}

func (o *OutboxOrderAggregate) PullEvents() []DomainEventObj {
	evts := o.events
	o.events = nil
	return evts
}

// Эмулятор транзакционной таблицы outbox_events
type MockOutboxTable struct {
	outboxRecords []string
}

func (t *MockOutboxTable) SaveInTransaction(ctx context.Context, order *OutboxOrderAggregate) error {
	// 1. Сохранение заказа
	// 2. Сохранение событий в таблицу Outbox в ТОЙ ЖЕ ТРАНЗАКЦИИ!
	for _, evt := range order.PullEvents() {
		t.outboxRecords = append(t.outboxRecords, evt.EventName())
	}
	return nil
}

func TestTransactionalOutbox(t *testing.T) {
	order := &OutboxOrderAggregate{id: "ord-outbox-9"}
	outboxDB := &MockOutboxTable{}

	// Бизнес-действие в домене
	order.MarkPaid()

	// Use Case сохраняет агрегат и Outbox-события атомарно
	_ = outboxDB.SaveInTransaction(context.Background(), order)

	if len(outboxDB.outboxRecords) != 1 || outboxDB.outboxRecords[0] != "order.paid" {
		t.Fatalf("Событие не сохранено в Outbox: %+v", outboxDB.outboxRecords)
	}

	fmt.Println("Паттерн Transactional Outbox успешно подтвержден:")
	fmt.Printf("  • Событие %s атомарно сохранено в таблицу outbox_events\n", outboxDB.outboxRecords[0])
	fmt.Println("  • Проблема Dual-Write ликвидирована: гарантия надежной доставки событий в Kafka")
}
```

ℹ️ Атомарное сохранение доменных событий в таблицу Outbox в единой транзакции БД

## Под капотом

Для чтения таблицы Outbox в продакшене используют Debezium (CDC — Change Data Capture), который читает Write-Ahead Log (WAL) PostgreSQL напрямую, минуя опрос `SELECT ... FROM outbox`, обеспечивая субмиллисекундную доставку событий в Kafka с нулевой нагрузкой на базу данных.

## Подводные камни

Удалять обработанные строки из таблицы Outbox через `DELETE`: это приводит к фрагментации таблиц (Dead Tuples в Postgres) и разрастанию дискового пространства. Применяют партиционирование таблицы Outbox по дням (`DROP TABLE outbox_y2026_m09_d04`).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Transactional Outbox от Transactional Inbox?»
**Ответ:** 
- **Outbox** гарантирует надежную **отправку** событий наружу продюсером без потери при сбоях.
- **Inbox** гарантирует надежную **обработку** входящих событий консьюмером, сохраняя входящее сообщение в локальную таблицу до его выполнения для обеспечения строгой идемпотентности.
