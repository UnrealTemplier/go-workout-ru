# Разделение команд и запросов (CQRS): поток записи CreateOrderCommand и поток чтения GetOrderSummaryQuery

## Условие

**Реализация CQRS**: Разделите потоки обработки данных:
    * Поток записи (Commands): Создайте структуру `CreateOrderCommand` и её обработчик. Модель ориентирована на строгую валидацию и сохранение.
    * Поток чтения (Queries): Создайте структуру `GetOrderSummaryQuery` и её обработчик. Модель ориентирована на мгновенное чтение денормализованных плоских данных (Read Model), оптимизированных под вывод на экран пользователя.

## Теория

Разделение архитектуры на Command Bus и Query Bus:
- **Command (Команда):**
  - Намерение изменить состояние: `CreateOrderCommand`.
  - Всегда формулируется в повелительном наклонении.
  - Обрабатывается ровно одним обработчиком `CommandHandler`.
  - Проверяет сложные инварианты, сохраняет в реляционную модель.
- **Query (Запрос):**
  - Запрос на получение данных без побочных эффектов (Идемпотентен): `GetOrderSummaryQuery`.
  - Обрабатывается `QueryHandler`.
  - Читает напрямую плоскую витрину (Read Model / Cache), минуя доменные агрегаты.

## Решение по шагам

1. Создайте интерфейс `CommandHandler` и команду `CreateOrderCommand`.
2. Создайте интерфейс `QueryHandler` и запрос `GetOrderSummaryQuery`.
3. Реализуйте оба независимых обработчика.
4. Продемонстрируйте работу обоих потоков данных.

## Код решения

**`cqrs_buses_separation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

// 1. Поток записи (Command)
type CreateOrderCommandPayload struct {
	OrderID   string
	Customer  string
	AmountRub float64
}

type CreateOrderCommandHandler struct {
	storage map[string]CreateOrderCommandPayload
}

func (h *CreateOrderCommandHandler) Handle(ctx context.Context, cmd CreateOrderCommandPayload) error {
	if cmd.AmountRub <= 0 {
		return fmt.Errorf("invalid amount")
	}
	h.storage[cmd.OrderID] = cmd
	return nil
}

// 2. Поток чтения (Query)
type GetOrderSummaryQueryPayload struct {
	OrderID string
}

type OrderSummaryViewResult struct {
	OrderID     string
	SummaryText string
}

type OrderSummaryQueryHandler struct {
	readView map[string]OrderSummaryViewResult
}

func (h *OrderSummaryQueryHandler) Handle(ctx context.Context, q GetOrderSummaryQueryPayload) (OrderSummaryViewResult, bool) {
	res, ok := h.readView[q.OrderID]
	return res, ok
}

func TestCQRSBusesSeparation(t *testing.T) {
	cmdHandler := &CreateOrderCommandHandler{storage: make(map[string]CreateOrderCommandPayload)}
	queryHandler := &OrderSummaryQueryHandler{readView: make(map[string]OrderSummaryViewResult)}

	// 1. Выполнение команды
	cmd := CreateOrderCommandPayload{OrderID: "ord-cqrs-88", Customer: "Татьяна", AmountRub: 25000.0}
	_ = cmdHandler.Handle(context.Background(), cmd)

	// Наполнение Read Model (в реальной системе через события)
	queryHandler.readView[cmd.OrderID] = OrderSummaryViewResult{
		OrderID:     cmd.OrderID,
		SummaryText: fmt.Sprintf("Клиент %s оплатил %.2f ₽", cmd.Customer, cmd.AmountRub),
	}

	// 2. Выполнение запроса
	view, found := queryHandler.Handle(context.Background(), GetOrderSummaryQueryPayload{OrderID: "ord-cqrs-88"})
	if !found || view.SummaryText == "" {
		t.Fatal("Данные запроса не найдены в Read Model")
	}

	fmt.Println("Архитектура CQRS (Commands & Queries) подтверждена:")
	fmt.Printf("  • Command Handler обработал мутацию заказа %s\n", cmd.OrderID)
	fmt.Printf("  • Query Handler вернул готовую плоскую витрину: %q\n", view.SummaryText)
}
```

## Под капотом

В микросервисах на Go шина команд и шина запросов часто реализуются в виде дженерик-интерфейсов: `type CommandHandler[C any] interface { Handle(ctx, C) error }`, что обеспечивает типобезопасность времени компиляции без приведения типов `any`.

## Подводные камни

Возвращать обновленную сущность целиком из CommandHandler: это провоцирует клиентов использовать команду для чтения. Команда должна возвращать только статус успеха или идентификатор созданной записи.

## На собеседовании

**Вопрос с собеседования:** «Можно ли использовать единую базу данных PostgreSQL для CQRS?»
**Ответ:** Да! CQRS — это архитектурный шаблон разделения моделей кода, а не баз данных. На одной базе данных PostgreSQL команды пишут в нормализованные таблицы `orders` и `order_items`, а запросы читают из денормализованного SQL VIEW `orders_summary_view` или реплики чтения (Read Replica).
