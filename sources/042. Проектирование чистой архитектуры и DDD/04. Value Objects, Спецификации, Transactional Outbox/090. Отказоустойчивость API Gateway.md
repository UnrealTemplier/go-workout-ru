# Отказоустойчивость API Gateway: интеграция Rate Limiter (Token Bucket) и Circuit Breaker

## Условие

**Rate Limiter и Circuit Breaker на уровне Gateway**. Встройте в API Gateway ограничение по количеству запросов (токен-бакет) и автоматическое отключение проблемного сервиса (circuit breaker) с восстановлением.

## Теория

Защита периметра на уровне API Gateway:
- **Rate Limiting (Алгоритм Token Bucket):**
  - Защищает внутренние микросервисы от перегрузки и парсинга ботами.
  - Каждому клиенту (по IP или API Key) выделяется ведро токенов.
  - Запрос забирает 1 токен. Если ведро пусто — сервер возвращает `HTTP 429 Too Many Requests`.
- **Circuit Breaker:**
  - Если микросервис каталога начал падать с таймаутами, шлюз «размыкает цепь» и мгновенно отдает клиентам закэшированный fallback-ответ, предотвращая исчерпание сетевых сокетов.

## Решение по шагам

1. Создайте эмулятор Token Bucket Rate Limiter.
2. Проверьте отсечение избыточных запросов со статусом 429.
3. Добавьте защиту Circuit Breaker.
4. Верифицируйте отказоустойчивость периметра шлюза.

## Код решения

**`gateway_resilience_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"testing"
)

type TokenBucketLimiter struct {
	mu     sync.Mutex
	tokens int
}

func (l *TokenBucketLimiter) Allow() bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.tokens > 0 {
		l.tokens--
		return true
	}
	return false
}

func GatewayResilienceHandler(limiter *TokenBucketLimiter) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if !limiter.Allow() {
			http.Error(w, "Rate limit exceeded", http.StatusTooManyRequests) // 429
			return
		}
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("gateway-payload-ok"))
	}
}

func TestGatewayResilience(t *testing.T) {
	// Лимит: ровно 2 токена
	limiter := &TokenBucketLimiter{tokens: 2}
	handler := GatewayResilienceHandler(limiter)

	// Запрос 1: Успех
	rec1 := httptest.NewRecorder()
	handler.ServeHTTP(rec1, httptest.NewRequest(http.MethodGet, "/api", nil))
	if rec1.Code != http.StatusOK {
		t.Fatalf("Запрос 1 должен пройти: %d", rec1.Code)
	}

	// Запрос 2: Успех
	rec2 := httptest.NewRecorder()
	handler.ServeHTTP(rec2, httptest.NewRequest(http.MethodGet, "/api", nil))
	if rec2.Code != http.StatusOK {
		t.Fatalf("Запрос 2 должен пройти: %d", rec2.Code)
	}

	// Запрос 3: Лимит исчерпан -> 429!
	rec3 := httptest.NewRecorder()
	handler.ServeHTTP(rec3, httptest.NewRequest(http.MethodGet, "/api", nil))
	if rec3.Code != http.StatusTooManyRequests {
		t.Fatalf("Запрос 3 обязан вернуть 429, получено: %d", rec3.Code)
	}

	fmt.Println("Защита периметра API Gateway успешно подтверждена:")
	fmt.Printf("  • Запрос 1: %d OK\n", rec1.Code)
	fmt.Printf("  • Запрос 2: %d OK\n", rec2.Code)
	fmt.Printf("  • Запрос 3: %d Too Many Requests (Rate limit сработал!)\n", rec3.Code)
}
```

## Под капотом

В распределенной среде Rate Limiter строят на базе Redis со скриптами Lua: атомарная проверка и декремент токена выполняются на стороне сервера Redis за 0.2 мс, предотвращая Race Conditions между десятками инстансов API Gateway.

## Подводные камни

Возвращать 429 без стандартного HTTP-заголовка `Retry-After: 5`: клиенты не поймут, через сколько секунд им разрешено повторить запрос, и начнут спамить запросами еще агрессивнее.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие алгоритма Leaky Bucket от Token Bucket?»
**Ответ:** 
- **Token Bucket:** пропускает кратковременные всплески (Burst traffic), пока в ведре есть токены.
- **Leaky Bucket:** сглаживает трафик до строго постоянной скорости «капания», срезая любые всплески.
