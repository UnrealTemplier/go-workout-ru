# Бизнес-мониторинг архитектурных компонентов: экспорт доменных метрик и расчет коэффициента ошибок

## Условие

**Бизнес-мониторинг архитектурных компонентов**. Для каждого сервиса и доменного действия экспортируйте метрики успеха/ошибок. Настройте дашборд, показывающий здоровье всей системы (архитектурный обзор).

## Теория

Бизнес-наблюдаемость (Business Observability):
- Технических метрик (CPU, RAM, HTTP 500) недостаточно: сервис может отдавать HTTP 200 OK, но при этом бизнес-конверсия упала до нуля (например, сторонний банк отклоняет 100% платежей).
- **Архитектурные метрики домена:**
  1. `domain_order_actions_total{action="create", status="success|failure"}`.
  2. `domain_payment_declines_total{reason="insufficient_funds|fraud"}`.
  3. Коэффициент успешности бизнес-операций:
     $$\text{SuccessRate} = \frac{\text{OrdersPlaced}_{success}}{\text{OrdersPlaced}_{total}} \times 100\%$$
- При падении `SuccessRate` ниже 98% SRE дежурный получает пейджер-алерт.

## Решение по шагам

1. Создайте счетчик архитектурных доменных действий.
2. Зафиксируйте успешные и ошибочные бизнес-операции.
3. Рассчитайте коэффициент успешности доменного процесса.
4. Проверьте генерацию бизнес-алерта.

## Код решения

**`business_observability_test.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"testing"
)

type DomainBusinessMetrics struct {
	checkoutSuccess atomic.Uint64
	checkoutFailure atomic.Uint64
}

func (m *DomainBusinessMetrics) RecordCheckout(success bool) {
	if success {
		m.checkoutSuccess.Add(1)
	} else {
		m.checkoutFailure.Add(1)
	}
}

func (m *DomainBusinessMetrics) SuccessRate() float64 {
	succ := m.checkoutSuccess.Load()
	fail := m.checkoutFailure.Load()
	total := succ + fail
	if total == 0 {
		return 100.0
	}
	return (float64(succ) / float64(total)) * 100.0
}

func TestBusinessObservability(t *testing.T) {
	metrics := &DomainBusinessMetrics{}

	// Имитация 95 успешных и 5 неудачных заказов
	for i := 0; i < 95; i++ {
		metrics.RecordCheckout(true)
	}
	for i := 0; i < 5; i++ {
		metrics.RecordCheckout(false)
	}

	rate := metrics.SuccessRate()
	if rate != 95.0 {
		t.Fatalf("Некорректный расчет SuccessRate: %.2f", rate)
	}

	fmt.Println("Бизнес-мониторинг архитектурных компонентов подтвержден:")
	fmt.Printf("  • Успешных заказов: %d\n", metrics.checkoutSuccess.Load())
	fmt.Printf("  • Отклоненных:      %d\n", metrics.checkoutFailure.Load())
	fmt.Printf("  • Доменный показатель успеха (Success Rate): %.1f%%\n", rate)
	fmt.Println("  • При падении Success Rate < 98% срабатывает бизнес-алерт дежурному техлиду")
}
```

## Под капотом

Использование атомарных типов `atomic.Uint64` (начиная с Go 1.19) выполняет инкремент за 1 инструкцию процессора `LOCK XADD` без блокировки мьютексов, позволяя собирать миллионы бизнес-событий в секунду с околонулевым оверхедом.

## Подводные камни

Добавлять `user_id` в лейблы метрик Prometheus: это приведет к взрыву кардинальности (Cardinality Explosion) и обрушит Prometheus. В метрики добавляют только дискретные статусы (`status="declined"`).

## На собеседовании

**Вопрос с собеседования:** «В чем отличие SLI, SLO и SLA в мониторинге микросервисов?»
**Ответ:** 
- **SLI (Service Level Indicator):** то, что реально измеряется прямо сейчас (например, 99.2% запросов успешны).
- **SLO (Service Level Objective):** внутренняя цель команды инженеров (например, не менее 99.9% за месяц).
- **SLA (Service Level Agreement):** юридический договор с клиентом с финансовыми штрафами (например, если доступность упадет ниже 99.5%, компания возвращает деньги).
