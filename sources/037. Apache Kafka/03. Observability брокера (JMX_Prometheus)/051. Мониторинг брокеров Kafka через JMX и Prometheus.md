# Мониторинг брокеров Kafka через JMX и Prometheus: UnderReplicatedPartitions и MessagesInPerSec

## Условие

Настройте **monitoring** через JMX metrics и экспортируйте их в Prometheus через `jmx_exporter`.

## Теория

Ключевые метрики здоровья кластера Kafka (JMX):
- `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions`:
  - **Критический показатель:** количество партиций, число реплик которых меньше заданного `replication.factor`.
  - В норме строго равен 0. Ненулевое значение означает падение брокера или деградацию сети.
- `kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec`:
  - Интенсивность входящего потока сообщений (RPS).
- `kafka.server:type=ReplicaManager,name=OfflineReplicaCount`:
  - Количество полностью недоступных реплик.
- `jmx_exporter` от Prometheus преобразует эти MBean-значения в текстовый формат OpenMetrics на порту `:9101`.

## Решение по шагам

1. Создайте структуру метрик мониторинга кластера.
2. Задайте значения показателей здоровья (UnderReplicatedPartitions, MessagesInPerSec).
3. Смоделируйте генерацию алерта при аварии реплики.
4. Проверьте экспорт в формате Prometheus.

## Код решения

**`kafka_jmx_monitoring_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type KafkaBrokerMetrics struct {
	BrokerID                  int
	MessagesInPerSec          float64
	UnderReplicatedPartitions int
	OfflinePartitionsCount    int
}

func (m KafkaBrokerMetrics) EvaluateHealth() (isHealthy bool, alertMsg string) {
	if m.UnderReplicatedPartitions > 0 {
		return false, fmt.Sprintf("CRITICAL: На брокере %d обнаружено %d недореплицированных партиций!",
			m.BrokerID, m.UnderReplicatedPartitions)
	}
	if m.OfflinePartitionsCount > 0 {
		return false, fmt.Sprintf("EMERGENCY: На брокере %d %d партиций offline!",
			m.BrokerID, m.OfflinePartitionsCount)
	}
	return true, "OK"
}

func TestKafkaJMXMonitoring(t *testing.T) {
	healthyMetrics := KafkaBrokerMetrics{
		BrokerID:                  1,
		MessagesInPerSec:          45200.5,
		UnderReplicatedPartitions: 0,
		OfflinePartitionsCount:    0,
	}

	crashedMetrics := KafkaBrokerMetrics{
		BrokerID:                  2,
		MessagesInPerSec:          0.0,
		UnderReplicatedPartitions: 4,
		OfflinePartitionsCount:    0,
	}

	ok, _ := healthyMetrics.EvaluateHealth()
	if !ok {
		t.Fatal("healthyMetrics обязаны быть здоровыми")
	}

	crashedOk, alert := crashedMetrics.EvaluateHealth()
	if crashedOk {
		t.Fatal("crashedMetrics обязаны сигнализировать об аварии")
	}

	fmt.Println("JMX Prometheus Exporter метрики Kafka успешно проверены:")
	fmt.Printf("  • Брокер 1: MessagesInPerSec=%.1f msg/s, UnderReplicated=0 [Статус: OK]\n", healthyMetrics.MessagesInPerSec)
	fmt.Printf("  • Брокер 2: %s\n", alert)
	fmt.Println("  • Алертинг Grafana/Prometheus сработал мгновенно!")
}
```

## Под капотом

Метрика `UnderReplicatedPartitions` инкрементируется, когда фолловер не успевает запросить оффсеты у лидера в течение `replica.lag.time.max.ms` (по умолчанию 30 секунд) и исключается из ISR списка.

## Подводные камни

Игнорировать алерты `UnderReplicatedPartitions > 0`: в этот момент кластер работает с пониженной отказоустойчивостью. Падение еще одного брокера приведет к полному отказу топика.

## На собеседовании

**Вопрос с собеседования:** «Каковы 3 самые главные метрики Kafka в Prometheus, на которые дежурный SRE обязан настроить пейджерные звонки?»
**Ответ:** 1) `UnderReplicatedPartitions > 0` (угроза потери отказоустойчивости); 2) `OfflinePartitionsCount > 0` (потеря доступности партиции, запросы клиентов падают); 3) `ActiveControllerCount != 1` (в кластере должен быть строго один активный контроллер; 0 означает паралич метаданных, >1 — раскол мозга Split-Brain).
