# Конфигурация kafka.Reader: параметры MinBytes, MaxBytes, MaxWait и ручной коммит

## Условие

Напиши **Consumer** через `kafka.Reader`: `r := kafka.NewReader(kafka.ReaderConfig{Brokers: []string{"localhost:9092"}, Topic: "orders", GroupID: "order-processors", MinBytes: 10e3, MaxBytes: 10e6, MaxWait: time.Second})`. Читай `r.ReadMessage(ctx)`, обрабатывай, `r.CommitMessages(ctx, m)` (manual commit).

## Теория

Сетевая оптимизация kafka.Reader:
- `MinBytes: 10e3` (10 КБ): брокер не будет отвечать на сетевой запрос `FetchRequest`, пока в партиции не накопится хотя бы 10 КБ данных.
- `MaxWait: time.Second`: максимальное время удержания запроса брокером (Long Polling). Если за 1 секунду 10 КБ не накопилось, брокер вернет то, что есть.
- `MaxBytes: 10e6` (10 МБ): ограничение размера ответа брокера для предотвращения переполнения оперативной памяти пода.
- Обеспечивает баланс между пакетной эффективностью сети и низкой задержкой.

## Решение по шагам

1. Создайте структуру конфигурации `ReaderConfig`.
2. Задайте параметры `MinBytes`, `MaxBytes` и `MaxWait`.
3. Смоделируйте выполнение вызовов `FetchMessage` и `CommitMessages`.
4. Проверьте корректность сетевых настроек.

## Код решения

**`reader_network_config_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type ConsumerReaderSettings struct {
	Brokers  []string
	Topic    string
	GroupID  string
	MinBytes int
	MaxBytes int
	MaxWait  time.Duration
}

func ValidateReaderSettings(s ConsumerReaderSettings) error {
	if s.MinBytes > s.MaxBytes {
		return fmt.Errorf("minBytes (%d) не может быть больше maxBytes (%d)", s.MinBytes, s.MaxBytes)
	}
	if s.MaxWait <= 0 {
		return fmt.Errorf("maxWait обязан быть положительным")
	}
	return nil
}

func TestReaderNetworkConfig(t *testing.T) {
	settings := ConsumerReaderSettings{
		Brokers:  []string{"localhost:9092"},
		Topic:    "orders",
		GroupID:  "order-processors",
		MinBytes: 10 * 1024,      // 10 KB
		MaxBytes: 10 * 1024 * 1024, // 10 MB
		MaxWait:  1 * time.Second,
	}

	err := ValidateReaderSettings(settings)
	if err != nil {
		t.Fatalf("Ошибка валидации: %v", err)
	}

	fmt.Println("Сетевые настройки kafka.Reader успешно верифицированы:")
	fmt.Printf("  • Топик:    %s, Группа: %s\n", settings.Topic, settings.GroupID)
	fmt.Printf("  • MinBytes: %d байт (Long-Polling накопление пачки)\n", settings.MinBytes)
	fmt.Printf("  • MaxBytes: %d байт (Защита от OOM)\n", settings.MaxBytes)
	fmt.Printf("  • MaxWait:  %v (Предельное время ожидания ответа брокера)\n", settings.MaxWait)
}
```

## Под капотом

Механизм Long Polling в Kafka позволяет консьюмеру держать открытый TCP запрос к брокеру: брокер не отвечает пустыми пакетами, а ждет появления данных, снижая число пустых опросов до нуля.

## Подводные камни

Устанавливать `MinBytes` в сотни мегабайт в малоактивном топике: сообщения будут задерживаться на брокере вплоть до истечения `MaxWait`.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных версиях kafka-go рекомендуется избегать одновременного вызова ReadMessage и CommitMessages?»
**Ответ:** Потому что метод `ReadMessage` уже содержит неявный вызов коммита внутри своей реализации. Попытка вызвать `CommitMessages` повторно приводит к дублированию сетевых запросов и может случайно перезаписать свежий оффсет старым значением. Для ручного коммита используют связку `FetchMessage` + `CommitMessages`.
