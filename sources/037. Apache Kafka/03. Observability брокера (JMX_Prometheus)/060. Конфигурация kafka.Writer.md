# Конфигурация kafka.Writer: балансировщик LeastBytes, RequiredAcks RequireAll и компромисс надежности

## Условие

Напиши **Producer** через `kafka.Writer`: `w := &kafka.Writer{Addr: kafka.TCP("localhost:9092"), Topic: "orders", Balancer: &kafka.LeastBytes{}, RequiredAcks: kafka.RequireAll, Async: false}`. `w.WriteMessages(ctx, kafka.Message{Key: []byte("order-123"), Value: data})`. Покажи настройки durability vs performance.

## Теория

Компромиссы надежности и производительности (Durability vs Performance):
1. **Максимальная надежность (High Durability):**
   - `RequiredAcks: kafka.RequireAll` (`acks = -1`).
   - `Async: false` (синхронное ожидание подтверждения дисковой репликации).
   - Скорость ниже, но 0% вероятность потери финансовых транзакций.
2. **Максимальная скорость (High Performance):**
   - `RequiredAcks: kafka.RequireOne` или `kafka.RequireNone`.
   - `Async: true` (асинхронный сброс буфера в фоне).
   - Скорость в десятки раз выше, допустимо для логов кликстрима и телеметрии.

## Решение по шагам

1. Создайте профили настроек продюсера для финансового биллинга и для телеметрии.
2. Сравните значения `RequiredAcks`, `Async` и `Balancer`.
3. Смоделируйте отправку сообщения с ключом `order-123`.
4. Проверьте применение профиля надежности.

## Код решения

**`producer_profiles_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ProducerProfile struct {
	Name         string
	RequiredAcks string
	Async        bool
	Balancer     string
}

func GetProducerProfile(mode string) ProducerProfile {
	if mode == "durability" {
		return ProducerProfile{
			Name:         "Financial Banking Profile",
			RequiredAcks: "RequireAll (-1)",
			Async:        false,
			Balancer:     "LeastBytes / Hash",
		}
	}
	return ProducerProfile{
		Name:         "Telemetry & Metrics Profile",
		RequiredAcks: "RequireNone (0)",
		Async:        true,
		Balancer:     "RoundRobin",
	}
}

func TestProducerProfiles(t *testing.T) {
	dProfile := GetProducerProfile("durability")
	pProfile := GetProducerProfile("performance")

	if dProfile.Async || dProfile.RequiredAcks != "RequireAll (-1)" {
		t.Fatalf("Профиль надежности поврежден: %+v", dProfile)
	}

	fmt.Println("Профили kafka.Writer успешно сопоставлены:")
	fmt.Printf("  • Durability:   Acks=%s, Async=%v, Balancer=%s (Гарантия Zero Data Loss)\n",
		dProfile.RequiredAcks, dProfile.Async, dProfile.Balancer)
	fmt.Printf("  • Performance:  Acks=%s, Async=%v, Balancer=%s (Сотни тысяч RPS кликстрима)\n",
		pProfile.RequiredAcks, pProfile.Async, pProfile.Balancer)
}
```

## Под капотом

Балансировщик `LeastBytes` направляет сообщения в ту партицию, которая в данный момент содержит наименьший объем байтов в не отправленных буферах сокета, выравнивая нагрузку на сетевые каналы брокеров.

## Подводные камни

Использовать `Balancer: &kafka.LeastBytes{}` для топиков, требующих строгого порядка сообщений сущности: балансировщик проигнорирует ключ сообщения и раскидает события одного клиента по разным партициям.

## На собеседовании

**Вопрос с собеседования:** «Когда можно включать Async: true в kafka.Writer?»
**Ответ:** Только для некритичных данных (логи, метрики, клики), где допустима потеря части сообщений при аварийном завершении процесса приложения (OOM или выключение сервера), так как сообщения сбрасываются из памяти в фоне без ожидания подтверждения в основном потоке.
