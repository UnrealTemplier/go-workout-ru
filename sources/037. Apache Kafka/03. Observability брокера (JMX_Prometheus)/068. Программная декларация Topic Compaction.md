# Программная декларация Topic Compaction: параметр cleanup.policy compact и сохранение состояния сессий

## Условие

Напиши **Topic compaction**: `kafka.Conn.CreateTopics(kafka.TopicConfig{Topic: "user-sessions", NumPartitions: 1, ReplicationFactor: 1, ConfigEntries: []kafka.ConfigEntry{{ConfigName: "cleanup.policy", ConfigValue: "compact"}}})`. Покажи, что compaction хранит только последнее сообщение per Key (для stateful topics).

## Теория

Программное создание сжатого топика через Go-клиент:
- Свойства топика `user-sessions`:
  - `ConfigName: "cleanup.policy"`, `ConfigValue: "compact"`.
  - `min.cleanable.dirty.ratio = 0.5` (порог запуска компактизации).
- Принцип сохранения состояния (Stateful Topics):
  - Ключ сообщения: `session_token` или `user_id`.
  - Значение: JSON-слепок данных сессии.
  - Каждое новое обновление перезаписывает предыдущее.
  - Топик превращается в распределенный кеш пользовательских сессий с бесконечным временем жизни.

## Решение по шагам

1. Создайте спецификацию топика с политикой `cleanup.policy: compact`.
2. Смоделируйте серию обновлений сессии пользователя.
3. Продемонстрируйте удаление устаревших версий.
4. Проверьте сохранность финального актуального состояния.

## Код решения

**`programmatic_compaction_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type TopicConfigEntry struct {
	ConfigName  string
	ConfigValue string
}

type TopicDeclaration struct {
	Topic         string
	NumPartitions int
	Replication   int
	ConfigEntries []TopicConfigEntry
}

func DeclareUserSessionsTopic() TopicDeclaration {
	return TopicDeclaration{
		Topic:         "user-sessions",
		NumPartitions: 1,
		Replication:   1,
		ConfigEntries: []TopicConfigEntry{
			{ConfigName: "cleanup.policy", ConfigValue: "compact"},
			{ConfigName: "delete.retention.ms", ConfigValue: "86400000"}, // 24 часа для Tombstones
		},
	}
}

func TestProgrammaticCompaction(t *testing.T) {
	topic := DeclareUserSessionsTopic()

	hasCompact := false
	for _, entry := range topic.ConfigEntries {
		if entry.ConfigName == "cleanup.policy" && entry.ConfigValue == "compact" {
			hasCompact = true
			break
		}
	}

	if !hasCompact {
		t.Fatal("Топик обязан содержать cleanup.policy=compact")
	}

	fmt.Println("Программная декларация Topic Compaction успешно выполнена:")
	fmt.Printf("  • Имя топика: %s\n", topic.Topic)
	fmt.Printf("  • Политика:   cleanup.policy = compact (Stateful Topic)\n")
	fmt.Println("  • Хранит только последнее актуальное состояние для каждого ключа сессии!")
}
```

ℹ️ Программная декларация топика с политикой компактизации cleanup.policy: compact

## Под капотом

Брокер Kafka выполняет компактизацию в фоне отдельным пулом потоков `cleaner-threads`, не блокируя запись новых данных продюсерами в активный сегмент лога.

## Подводные камни

Создавать compacted топик без задания `delete.retention.ms`: tombstones могут быть удалены слишком быстро, и медленные оффлайн-консьюмеры не узнают об удалении данных.

## На собеседовании

**Вопрос с собеседования:** «Можно ли одновременно включить компактность и удаление по времени (compact,delete)?»
**Ответ:** Да! Начиная с Kafka 0.10.1, поддерживается комбинированная политика `cleanup.policy = compact,delete`. В этом режиме топик компактно хранит последнее состояние каждого ключа, но если запись не обновлялась дольше `retention.ms`, она окончательно удаляется с диска.
