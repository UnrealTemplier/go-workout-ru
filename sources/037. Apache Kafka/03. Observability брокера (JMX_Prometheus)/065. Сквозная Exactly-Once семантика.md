# Сквозная Exactly-Once семантика: Transactional Producer, изоляция read_committed и 2PC

## Условие

Реализуй **Exactly-once semantics (EOS)**: Producer ` transactional.id = "order-producer-1"`, `InitTransactions`, `BeginTransaction`, `Send`, `SendOffsetsToTransaction`, `CommitTransaction`. Consumer `isolation.level = read_committed` — не видит uncommitted сообщений. Покажи atomic publish + consume.

## Теория

Сквозной транзакционный цикл в Kafka (End-to-End Exactly-Once):
- Пайплайн «Вычитка \(\to\) Трансформация \(\to\) Публикация \(\to\) Коммит»:
  1. `producer.BeginTransaction()`
  2. `producer.Send(outTopic, transformedMsg)`
  3. `producer.SendOffsetsToTransaction(offsets, consumerGroupID)`
  4. `producer.CommitTransaction()`
- **Магия семантики:**
  - Коммит смещения входного сообщения и публикация выходного сообщения фиксируются брокером **атомарно** в одной двухфазной транзакции!
  - Консьюмер downstream с настройкой `isolation.level = read_committed` увидит результат только после завершения шага 4.

## Решение по шагам

1. Создайте модель атомарного транзакционного пайплайна.
2. Продемонстрируйте фиксацию выходного сообщения вместе со смещением входа.
3. Смоделируйте консьюмера в режиме `read_committed`.
4. Убедитесь в отсутствии видимости незакоммиченных данных.

## Код решения

**`end_to_end_eos_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type EOSTransactionState struct {
	TransactionalID string
	UncommittedMsgs []string
	CommittedMsgs   []string
	CommittedOffset int64
}

func (s *EOSTransactionState) CommitAtomic(newOffset int64) {
	s.CommittedMsgs = append(s.CommittedMsgs, s.UncommittedMsgs...)
	s.UncommittedMsgs = nil
	s.CommittedOffset = newOffset
}

func (s *EOSTransactionState) AbortAtomic() {
	s.UncommittedMsgs = nil
}

func TestEndToEndEOS(t *testing.T) {
	tx := &EOSTransactionState{
		TransactionalID: "order-producer-1",
		CommittedOffset: 100,
	}

	// 1. Начало транзакции и подготовка данных
	tx.UncommittedMsgs = append(tx.UncommittedMsgs, "Создана накладная #501")

	// Консьюмер с isolation.level = read_committed видит только CommittedMsgs
	if len(tx.CommittedMsgs) != 0 {
		t.Fatal("Uncommitted сообщения не должны быть видны!")
	}

	// 2. Атомарный коммит сообщений и входного оффсета (101)
	tx.CommitAtomic(101)

	if len(tx.CommittedMsgs) != 1 || tx.CommittedOffset != 101 {
		t.Fatalf("Ошибка EOS коммита: msgs=%d, offset=%d", len(tx.CommittedMsgs), tx.CommittedOffset)
	}

	fmt.Println("Сквозная Exactly-Once Semantics (EOS) успешно подтверждена:")
	fmt.Printf("  • Transactional ID:        %s\n", tx.TransactionalID)
	fmt.Printf("  • Режим консьюмера:        isolation.level = read_committed\n")
	fmt.Printf("  • Выходные сообщения:      %v (закоммичены)\n", tx.CommittedMsgs)
	fmt.Printf("  • Входное смещение:        Offset=%d (атомарно зафиксировано вместе с сообщением!)\n", tx.CommittedOffset)
}
```

## Под капотом

В режиме `read_committed` консьюмер считывает все данные, но придерживает их во внутреннем буфере до получения бинарного служебного маркера `ControlBatch(COMMIT)`, отсекая любые отмененные транзакции.

## Подводные камни

Забывать вызывать `InitTransactions()` при старте сервиса: без этого брокер не выдаст `Producer ID` и отклонит вызов `BeginTransaction()` с ошибкой `IllegalStateException`.

## На собеседовании

**Вопрос с собеседования:** «Что такое LSO (Last Stable Offset) в Kafka?»
**Ответ:** LSO — это смещение первой незавершенной (открытой) транзакции в партиции. Консьюмер в режиме `read_committed` не может читать сообщения за пределами LSO, даже если более поздние нетранзакционные сообщения уже записаны в лог. Это защищает от чтения «грязных» данных.
