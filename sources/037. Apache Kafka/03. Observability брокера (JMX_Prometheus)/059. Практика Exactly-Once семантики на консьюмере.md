# Практика Exactly-Once семантики на консьюмере: дедупликация через Redis и таблицу processed_events

## Условие

**Семантика Exactly-Once (Идемпотентность)**: *Теоретически-практическая задача.* Поскольку Kafka гарантирует только At-Least-Once (сообщение может дублироваться), напиши логику в консьюмере: при получении сообщения проверяй ID сообщения в Redis или Postgres (таблица `processed_events`). Если он там есть — игнорируй (skip). Если нет — обрабатывай и сохраняй ID.

## Теория

Шаблон идемпотентного потребителя (Idempotent Consumer Pattern):
- Сеть между брокером и консьюмером ненадежна: ребалансировка может вернуть сообщение заново.
- Алгоритм защиты:
  ```go
  // 1. Проверяем наличие ключа в Redis (атомарный SET NX с TTL 24 часа)
  ok, err := redisClient.SetNX(ctx, "processed_msg:"+msg.ID, "1", 24*time.Hour).Result()
  if !ok {
      // Сообщение уже обработано ранее!
      _ = reader.CommitMessages(ctx, msg)
      return nil // Пропускаем дубликат
  }
  // 2. Выполняем полезную работу
  processOrder(msg)
  // 3. Фиксируем оффсет
  _ = reader.CommitMessages(ctx, msg)
  ```
- Гарантирует, что бизнес-логика выполнится строго 1 раз независимо от числа сетевых сбоев.

## Решение по шагам

1. Создайте модель кэша идемпотентности с методом `CheckAndMark`.
2. Смоделируйте первичное поступление заказа.
3. Смоделируйте дубликат сообщения из-за сетевого рестарта воркера.
4. Проверьте пропуск дубликата и сохранение баланса.

## Код решения

**`redis_idempotent_consumer_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type RedisIdempotencyService struct {
	mu   sync.Mutex
	keys map[string]bool
}

func (s *RedisIdempotencyService) AcquireMessageLock(msgID string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.keys[msgID] {
		return false // Ключ уже существует -> ДУБЛИКАТ
	}
	s.keys[msgID] = true
	return true
}

type OrderProcessingService struct {
	redis       *RedisIdempotencyService
	ordersCount int
}

func (s *OrderProcessingService) HandleMessage(msgID, orderData string) (processed bool) {
	// Атомарная проверка SET NX
	if !s.redis.AcquireMessageLock(msgID) {
		return false // Пропускаем дубликат
	}

	s.ordersCount++
	return true
}

func TestRedisIdempotentConsumer(t *testing.T) {
	redis := &RedisIdempotencyService{keys: make(map[string]bool)}
	svc := &OrderProcessingService{redis: redis}

	msgID := "kafka-msg-9941"

	// 1. Первая обработка
	p1 := svc.HandleMessage(msgID, "Оплата заказа $100")
	// 2. Сетевой дубликат после ребалансировки группы
	p2 := svc.HandleMessage(msgID, "Оплата заказа $100")

	if !p1 || p2 || svc.ordersCount != 1 {
		t.Fatalf("Ошибка дедупликации: p1=%v, p2=%v, count=%d", p1, p2, svc.ordersCount)
	}

	fmt.Println("Идемпотентный консьюмер (Redis SET NX) подтвердил Exactly-Once:")
	fmt.Printf("  • Первичное сообщение: успешно обработано (Всего заказов: %d)\n", svc.ordersCount)
	fmt.Printf("  • Дубликат сообщения:  пропущен без повторной бизнес-логики\n")
	fmt.Println("  • Семантика Exactly-Once на стороне приложения полностью соблюдена!")
}
```

## Под капотом

В Redis команда `SET key val NX EX 86400` выполняется однопоточно за \(O(1)\) в памяти, что позволяет дедуплицировать до 120 000 сообщений в секунду на одном инстансе Redis.

## Подводные камни

Забывать указывать время жизни (TTL): если ключи дедупликации хранить вечно, Redis быстро исчерпает всю RAM сервера.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если ключ в Redis уже установлен, но воркер упал до записи в основную базу данных (Phantom Lock)?»
**Ответ:** Использовать паттерн Two-Phase Idempotency: ставить в Redis статус `PENDING` с коротким TTL (например 30 секунд). После успешного коммита в базу переводить статус в `CONFIRMED` с TTL 24 часа. Если воркер упал на середине, через 30 секунд ключ автоматически удалится, позволив повторную обработку.
