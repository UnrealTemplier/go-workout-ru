# Обработка Rebalance: перехват сигнала отзыва партиций, фиксация in-flight задач и коммит

## Условие

**Обработка Rebalance**: При добавлении нового консьюмера в группу Kafka делает "ребалансировку" партиций. Напиши логику, которая при получении сигнала на остановку (Context Done) дожидается завершения обработки текущего сообщения и делает финальный коммит перед выходом, чтобы не словить дубли после ребаланса.

### Исходная формулировка

**Обработка Rebalance**: При добавлении нового консьюмера в группу Kafka делает "ребалансировку" партиций. Напиши логику, которая при получении сигнала на остановку (Context Done) дожидается завершения обработки текущего сообщения и делает финальный коммит перед выходом, чтобы не словить дубли после ребаланса.

---

## Теория

Перехват отзыва партиций (Consumer Rebalance Listener):
- Перед тем как отобрать партицию у консьюмера:
  - Координатор присылает уведомление об отзыве (Revocation Notification).
- **Критический порядок действий:**
  1. Немедленно приостановить чтение новых сообщений (`Pause`).
  2. Дождаться завершения in-flight задач, которые прямо сейчас обрабатываются в базе данных.
  3. Выполнить синхронный `CommitMessages` для финализации оффсета.
  4. Подтвердить готовность к ребалансировке.
- Предотвращает ситуацию, когда новый владелец партиции начинает заново перерабатывать сообщения, которые уже были выполнены старым воркером.

## Решение по шагам

1. Создайте структуру обработчика с хуком `OnPartitionsRevoked`.
2. Смоделируйте выполнение активной бизнес-задачи.
3. Вызовите событие отзыва партиций.
4. Убедитесь, что смещение закоммичено строго ДО передачи партиции новому владельцу.

## Код решения

**`rebalance_listener_commit_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type RebalanceAwareWorker struct {
	inFlightOffset  int64
	committedOffset int64
}

func (w *RebalanceAwareWorker) OnPartitionsRevoked() {
	// Дожидаемся завершения in-flight обработки
	time.Sleep(10 * time.Millisecond)
	// Фиксируем финальный коммит перед отдачей партиции
	w.committedOffset = w.inFlightOffset
}

func TestRebalanceListenerCommit(t *testing.T) {
	worker := &RebalanceAwareWorker{
		inFlightOffset:  808,
		committedOffset: 800,
	}

	// Координатор инициирует ребалансировку и вызывает хук отзыва
	worker.OnPartitionsRevoked()

	if worker.committedOffset != 808 {
		t.Fatalf("Оффсет должен быть зафиксирован на 808: %d", worker.committedOffset)
	}

	fmt.Println("Хук Rebalance Listener успешно зафиксировал состояние:")
	fmt.Printf("  • Активная задача Offset=%d успешно завершена\n", worker.inFlightOffset)
	fmt.Printf("  • Смещение Offset=%d закоммичено в Kafka строго до передачи партиции!\n", worker.committedOffset)
	fmt.Println("  • Новый владелец партиции начнет чтение строго со следующего оффсета 809 (Дубликаты исключены!)")
}
```

ℹ️ Фиксация смещений in-flight задач в хуке отзыва партиций при ребалансировке

## Под капотом

В библиотеке `twmb/franz-go` и Java клиенте для этого существует интерфейс `RebalanceListener` с методами `OnPartitionsRevoked` и `OnPartitionsAssigned`.

## Подводные камни

Выполнять долгую операцию (дольше `max.poll.interval.ms`) внутри хука `OnPartitionsRevoked`: брокер посчитает консьюмер зависшим и принудительно исключит его из группы.

## На собеседовании

**Вопрос с собеседования:** «Как протокол Cooperative Sticky Rebalance помогает избежать потерь при отзыве партиций?»
**Ответ:** В классическом Eager протоколе все воркеры сбрасывают все партиции разом. В Cooperative Sticky протокол отзывает только те конкретные партиции, которые нужно перенести. Воркеры, чьи партиции не затронуты, продолжают непрерывную обработку без остановки.
