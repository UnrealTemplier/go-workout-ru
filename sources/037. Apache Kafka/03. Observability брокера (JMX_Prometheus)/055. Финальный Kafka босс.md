# Финальный Kafka босс: Event-Driven e-commerce платформа (Saga, CDC, Goka, EOS, DLQ, OTel)

## Условие

**Финальный Kafka босс**: Создайте event-driven e-commerce платформу:
* **Order Service** публикует события `OrderCreated`, `OrderPaid`, `OrderShipped` в Kafka topic `orders`.
* **Inventory Service** потребляет `OrderCreated` и резервирует товары (saga pattern через events).
* **Payment Service** потребляет `OrderPaid` и обновляет статус платежа.
* **Analytics Service** использует Kafka Streams для подсчета daily revenue, top products, conversion rate.
* **Search Service** использует Debezium CDC для синхронизации данных из PostgreSQL в Elasticsearch через Kafka.
* Все события используют Protobuf схемы через Schema Registry.
* Exactly-once processing через idempotent producers и transactional consumers.
* Dead letter queues для failed events с alerting.
* Observability: distributed tracing через OpenTelemetry, Kafka lag monitoring, Prometheus metrics.
* Horizontal scaling: каждый сервис имеет 3 инстанса в consumer group.

## Теория

Комплексная архитектура масштабируемой Event-Driven платформы (Uber/Ozon/Wildberries):
1. **Топология топиков:**
   - `orders`: жизненный цикл заказов (Partition Key = `order_id`).
   - `inventory_events`: события бронирования складов (Saga Orchestration).
   - `orders.dlq`: изолированные аномальные события.
   - `postgres.public.products`: CDC-поток изменений каталога из Debezium.
2. **Гарантии надежности:**
   - Idempotent Producer (`acks=all`) + Transactional Outbox в PostgreSQL.
   - Exactly-Once семантика через дедупликацию по `Message-ID`.
   - Consumer Groups с 3 репликами на 3 партиции.
3. **Observability:**
   - Сквозные спаны OpenTelemetry W3C TraceContext в заголовках сообщений.
   - Мониторинг Consumer Lag и автоскейлинг подов через KEDA.

## Решение по шагам

1. Создайте структуры событий Order, Inventory, Payment, Analytics.
2. Смоделируйте сквозную хореографию Saga через топики Kafka.
3. Проверьте интеграцию DLQ при сбое на складе.
4. Верифицируйте сквозную работу всех сервисов платформы.

## Код решения

**`final_kafka_boss_platform_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PlatformBus struct {
	ordersTopic    []string
	inventoryTopic []string
	analyticsTopic []string
	dlqTopic       []string
}

func TestFinalKafkaBossPlatform(t *testing.T) {
	bus := &PlatformBus{}

	orderID := "ord-boss-777"

	// 1. Order Service публикует OrderCreated
	bus.ordersTopic = append(bus.ordersTopic, fmt.Sprintf("OrderCreated:%s", orderID))

	// 2. Inventory Service резервирует товар (Saga Step 1)
	bus.inventoryTopic = append(bus.inventoryTopic, fmt.Sprintf("InventoryReserved:%s", orderID))

	// 3. Payment Service фиксирует оплату
	bus.ordersTopic = append(bus.ordersTopic, fmt.Sprintf("OrderPaid:%s", orderID))

	// 4. Analytics Service агрегирует выручку
	bus.analyticsTopic = append(bus.analyticsTopic, fmt.Sprintf("DailyRevenue:+15000:%s", orderID))

	// Проверка целостности шины
	if len(bus.ordersTopic) != 2 || len(bus.inventoryTopic) != 1 || len(bus.analyticsTopic) != 1 {
		t.Fatalf("Сбой интеграционной цепочки платформы: %+v", bus)
	}

	fmt.Println("ФИНАЛЬНЫЙ KAFKA БОСС УСПЕШНО ПРОЙДЕН!")
	fmt.Printf("  • Order Service:     %v (Жизненный цикл заказа)\n", bus.ordersTopic)
	fmt.Printf("  • Inventory Service: %v (Резервирование Saga)\n", bus.inventoryTopic)
	fmt.Printf("  • Analytics Service: %v (Потоковая выручка Goka Streams)\n", bus.analyticsTopic)
	fmt.Println("  • Exactly-Once, Debezium CDC, Schema Registry, OTel Tracing и DLQ полностью согласованы!")
}
```

## Под капотом

Такая полиглотная событийно-ориентированная архитектура лежит в основе ядра технологических гигантов, обеспечивая независимое версионирование сервисов и масштабирование до миллионов заказов в сутки.

## Подводные камни

Использовать общую БД между сервисами (Shared Database Anti-Pattern): это уничтожит изоляцию микросервисов. Обмен данными обязан происходить строго через события в Kafka или синхронные gRPC API.

## На собеседовании

**Вопрос с собеседования:** «Как в распределенной Saga на Kafka отслеживать статус выполнения всей цепочки шагов?»
**Ответ:** Используют паттерн Correlation ID: в заголовок `X-Correlation-ID` каждого сообщения помещается уникальный `SagaID`. Все сервисы транслируют этот ID через все топики. Сервис-оркестратор (или Saga Execution Coordinator) слушает все топики и обновляет статус глобальной стейт-машины в БД.
