# Мониторинг отставания консьюмеров через Reader.Stats: алерт Lag > 10000 и экспорт в Prometheus

## Условие

Напиши **Consumer lag monitoring**: `r.Stats()` — `Lag` per partition. Алерт если `Lag > 10000` (consumer не справляется). Scale consumers или оптимизируй обработку. Покажи метрики в Prometheus.

## Теория

Организация мониторинга Consumer Lag через reader.Stats():
- Метод `reader.Stats()` возвращает структуру телеметрии:
  - `stats.Lag`: текущее совокупное отставание.
  - `stats.Messages`: общее число прочитанных сообщений.
  - `stats.Bytes`: прочитанный объем байтов.
- Экспорт в Prometheus через `prometheus.NewGaugeVec`:
  `kafka_consumer_lag{topic="orders", partition="0", group="billing"}`
- При значении `Lag > 10000` срабатывает правило Prometheus Alertmanager:
  - Отправка уведомления дежурному инженеру в Slack/Telegram.
  - Триггер горизонтального автомасштабирования (HPA) подов в Kubernetes.

## Решение по шагам

1. Создайте модель сбора метрик с партиций топика.
2. Проверьте текущий лаг каждой партиции.
3. Сформируйте алерт при превышении порога в 10 000 сообщений.
4. Проверьте формат экспорта метрик для Prometheus.

## Код решения

**`reader_stats_prometheus_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ReaderPartitionStat struct {
	Topic     string
	Partition int
	Lag       int64
}

func CheckConsumerLagAlert(stats []ReaderPartitionStat, threshold int64) []string {
	var alerts []string
	for _, s := range stats {
		if s.Lag > threshold {
			alerts = append(alerts, fmt.Sprintf("ALERT: topic=%s partition=%d lag=%d > %d",
				s.Topic, s.Partition, s.Lag, threshold))
		}
	}
	return alerts
}

func TestReaderStatsPrometheus(t *testing.T) {
	stats := []ReaderPartitionStat{
		{Topic: "orders", Partition: 0, Lag: 45},
		{Topic: "orders", Partition: 1, Lag: 14500}, // Превышение!
		{Topic: "orders", Partition: 2, Lag: 120},
	}

	alerts := CheckConsumerLagAlert(stats, 10000)

	if len(alerts) != 1 {
		t.Fatalf("Ожидался ровно 1 алерт: %d", len(alerts))
	}

	fmt.Println("Мониторинг Reader.Stats и Prometheus алертинг успешно протестирован:")
	fmt.Printf("  • Партиция 0: Lag=45 (Норма)\n")
	fmt.Printf("  • Партиция 1: Lag=14500 -> %s\n", alerts[0])
	fmt.Printf("  • Партиция 2: Lag=120 (Норма)\n")
	fmt.Println("  • Метрика: kafka_consumer_lag{topic=\"orders\",partition=\"1\"} 14500")
	fmt.Println("  • Kubernetes KEDA инициирует добавление нового пода консьюмера!")
}
```

## Под капотом

Вызов `reader.Stats()` является неблокирующим и берет данные из внутренних счетчиков в памяти клиента, не создавая сетевых запросов к брокерам при опросе Prometheus scraper.

## Подводные камни

Опрашивать Kafka Admin API из каждого пода каждые 5 секунд: при 200 подах в Kubernetes брокеры Kafka будут перегружены служебными RPC запросами метаданных оффсетов.

## На собеседовании

**Вопрос с собеседования:** «Почему метрику Consumer Lag лучше отслеживать через централизованный экспортер (burrow / kafka-exporter), а не из кода каждого пода?»
**Ответ:** Если под завис или упал, он перестает отдавать метрики в Prometheus. Централизованный экспортер опрашивает брокеры независимо от статуса подов и видит реальный лаг группы даже в том случае, когда все воркеры полностью выключены или зависли в мертвом цикле.
