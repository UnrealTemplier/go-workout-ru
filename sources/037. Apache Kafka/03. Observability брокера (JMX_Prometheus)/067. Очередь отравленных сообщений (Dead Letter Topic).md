# Очередь отравленных сообщений (Dead Letter Topic): ретраи, заголовок x-fail-reason и orders.dlq

## Условие

Реализуй **Dead Letter Topic**: Consumer пытается обработать 3 раза (с `Nack` + sleep). После 3 попыток — `w.WriteMessages(ctx, kafka.Message{Topic: "orders.dlq", Key: m.Key, Value: m.Value, Headers: append(m.Headers, kafka.Header{Key: "x-fail-reason", Value: []byte(err.Error())})})`. DLQ consumer — alert + manual investigation.

## Теория

Изоляция фатальных сбоев в Dead Letter Topic:
- Когда обработка заказа завершается ошибкой (например, отрицательная сумма или неверный SKU):
  - Повторные попытки с кратковременным sleep выполняются 3 раза.
  - Если ошибка не устраняется (Poison Pill):
    - Сообщение упаковывается в топик `orders.dlq` с сохранением оригинального ключа и полезной нагрузки.
    - В заголовок `x-fail-reason` пишется точный текст ошибки или стектрейс.
    - Оффсет в топике `orders` коммитится, предотвращая зависание всей партиции.
- Отдельный DLQ-воркер отсылает алерт в систему мониторинга для ручного разбора оператором.

## Решение по шагам

1. Создайте структуру сообщения с заголовками ошибки.
2. Смоделируйте 3 неудачные попытки обработки.
3. Опубликуйте сообщение в `orders.dlq` с заголовком `x-fail-reason`.
4. Зафиксируйте смещение в основном топике.

## Код решения

**`dead_letter_topic_routing_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type KafkaHeader struct {
	Key   string
	Value string
}

type DLQMessageRecord struct {
	Topic   string
	Key     string
	Value   string
	Headers []KafkaHeader
}

type OrderConsumerDLQ struct {
	dlqSink []DLQMessageRecord
}

func (c *OrderConsumerDLQ) ProcessWithDLQ(key, val string) (committed bool) {
	var lastErr error
	for attempt := 1; attempt <= 3; attempt++ {
		// Имитация постоянной ошибки валидации (Poison Pill)
		lastErr = errors.New("invalid product SKU: SKU-999 not found in catalog")
	}

	// 3 попытки провалились -> маршрутизируем в orders.dlq
	dlqRecord := DLQMessageRecord{
		Topic: "orders.dlq",
		Key:   key,
		Value: val,
		Headers: []KafkaHeader{
			{Key: "x-fail-reason", Value: lastErr.Error()},
			{Key: "x-attempts", Value: "3"},
		},
	}
	c.dlqSink = append(c.dlqSink, dlqRecord)
	return true // Коммитим оффсет в orders!
}

func TestDeadLetterTopicRouting(t *testing.T) {
	consumer := &OrderConsumerDLQ{}

	committed := consumer.ProcessWithDLQ("order-991", `{"item":"SKU-999","qty":2}`)

	if !committed || len(consumer.dlqSink) != 1 {
		t.Fatalf("Сообщение обязано быть перенаправлено в DLQ: committed=%v", committed)
	}

	record := consumer.dlqSink[0]
	if record.Topic != "orders.dlq" || record.Headers[0].Key != "x-fail-reason" {
		t.Fatalf("Некорректная запись DLQ: %+v", record)
	}

	fmt.Println("Маршрутизация в Dead Letter Topic успешно изолировала сбой:")
	fmt.Printf("  • Целевой топик: %s\n", record.Topic)
	fmt.Printf("  • Ключ заказа:   %s\n", record.Key)
	fmt.Printf("  • Заголовок:     %s = «%s»\n", record.Headers[0].Key, record.Headers[0].Value)
	fmt.Println("  • Оффсет в основном топике закоммичен, очередь заказов продолжает работу!")
}
```

## Под капотом

В отличие от JMS или RabbitMQ, в Kafka DLQ — это обычный стандартный топик с теми же свойствами репликации и долговечности. Сообщения в нем доступны для аудита и повторной накатки (Redrive).

## Подводные камни

Забывать коммитить оффсет исходного сообщения после успешной отправки в DLQ: если не закоммитить оффсет, при следующем запуске консьюмер снова упадет на том же сообщении.

## На собеседовании

**Вопрос с собеседования:** «Каковы требования к мониторингу DLQ топиков?»
**Ответ:** DLQ топики обязательно снабжаются счетчиком `messages_total` в Prometheus с алертом на любое появление сообщений (`rate(dlq_messages_total[5m]) > 0`). Попадание сообщения в DLQ означает потерю бизнес-операции и требует расследования инженерами техподдержки.
