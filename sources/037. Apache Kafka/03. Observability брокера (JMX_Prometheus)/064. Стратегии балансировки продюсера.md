# Стратегии балансировки продюсера: сравнение Hash Balancer (порядок) и RoundRobin (равномерность)

## Условие

Напиши **Partitioning strategy**: `Balancer: &kafka.Hash{}` — сообщения с одинаковым Key идут в один partition (ordering guarantee). `Balancer: &kafka.RoundRobin{}` — равномерное распределение. Покажи, когда нужен Key (ordering) vs RoundRobin (load balancing).

## Теория

Сравнительный анализ стратегий маршрутизации:
| Стратегия | Алгоритм | Гарантия порядка | Равномерность нагрузки | Сценарий применения |
| :--- | :--- | :--- | :--- | :--- |
| **`kafka.Hash{}`** | \(\text{Hash}(Key) \pmod P\) | **100% внутри партиции** | Зависит от распределения ключей (риск Key Skew) | Заказы, биллинг, чаты, профили пользователей |
| **`kafka.RoundRobin{}`** | \(i \pmod P\) | Нет | **Идеальная (100% равномерно)** | Логи серверов, метрики, кликстрим, поисковые события |
- Выбор стратегии определяет архитектурные свойства надежности всей подсистемы.

## Решение по шагам

1. Создайте модели алгоритмов Hash и RoundRobin.
2. Пропустите поток сообщений через обе стратегии.
3. Проверьте группировку по ключу для Hash стратегии.
4. Проверьте равномерный циклический баланс для RoundRobin.

## Код решения

**`partitioning_strategies_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

func HashStrategy(key string, partitions int) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return int(h.Sum32()&0x7fffffff) % partitions
}

type RoundRobinStrategy struct {
	counter int
}

func (rr *RoundRobinStrategy) Next(partitions int) int {
	p := rr.counter % partitions
	rr.counter++
	return p
}

func TestPartitioningStrategies(t *testing.T) {
	const totalPartitions = 3

	// 1. Проверяем Hash (Гарантия порядка для Order_1)
	pOrder1_a := HashStrategy("Order_1", totalPartitions)
	pOrder1_b := HashStrategy("Order_1", totalPartitions)
	if pOrder1_a != pOrder1_b {
		t.Fatal("Hash обязан давать одинаковую партицию для одного ключа")
	}

	// 2. Проверяем RoundRobin (Идеальная балансировка нагрузки)
	rr := &RoundRobinStrategy{}
	rrP0 := rr.Next(totalPartitions)
	rrP1 := rr.Next(totalPartitions)
	rrP2 := rr.Next(totalPartitions)
	rrP3 := rr.Next(totalPartitions)

	if rrP0 != 0 || rrP1 != 1 || rrP2 != 2 || rrP3 != 0 {
		t.Fatalf("Нарушен циклический RoundRobin: %d, %d, %d, %d", rrP0, rrP1, rrP2, rrP3)
	}

	fmt.Println("Стратегии партиционирования успешно протестированы:")
	fmt.Printf("  • Hash Balancer:       все события 'Order_1' -> строго Партиция #%d (FIFO порядок!)\n", pOrder1_a)
	fmt.Printf("  • RoundRobin Balancer: события распределены циклично: %d -> %d -> %d -> %d (100%% балансировка!)\n",
		rrP0, rrP1, rrP2, rrP3)
}
```

ℹ️ Сравнение стратегий Hash Balancer (порядок) и RoundRobin (балансировка нагрузки)

**`Терминал`**

```bash

# Вывод:

# Стратегии партиционирования успешно протестированы:
#   • Hash Balancer:       все события 'Order_1' -> строго Партиция #0 (FIFO порядок!)
#   • RoundRobin Balancer: события распределены циклично: 0 -> 1 -> 2 -> 0 (100% балансировка!)

# PASS
```

## Под капотом

В Kafka 2.4+ дефолтным балансировщиком для сообщений без ключа стал Sticky Partitioner, который заполняет пачку в одну партицию до предела BatchSize, а затем переключается на следующую, объединяя преимущества RoundRobin и батчинга.

## Подводные камни

Использовать RoundRobin при отправке финансовых событий: списание денег и пополнение баланса разойдутся по разным партициям и будут выполнены с нарушением хронологии.

## На собеседовании

**Вопрос с собеседования:** «Как быть, если при использовании Hash Balancer один из ключей генерирует 90% нагрузки (Hot Partition)?»
**Ответ:** Применяют технику Salted Keys: к ключу добавляется случайный суффикс из фиксированного диапазона, например `fmt.Sprintf("%s_part_%d", clientID, rand.Intn(4))`. Это дробит поток супер-клиента на 4 независимые партиции, а агрегатор на выходе склеивает результаты.
