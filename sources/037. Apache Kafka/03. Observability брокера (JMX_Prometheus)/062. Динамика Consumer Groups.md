# Динамика Consumer Groups: поведение 4-го инстанса (Idle) и перераспределение партиций при сбое 1-го

## Условие

Покажи **Consumer Groups**: запусти 3 инстанса с одинаковым `GroupID`. Kafka распределяет partitions между consumers (1 partition = 1 consumer max). Добавь 4-й инстанс — он будет idle (если partitions < consumers). Убедись, что при выходе 1-го произойдет rebalance, и partitions перераспределятся.

### Исходная формулировка

Покажи **Consumer Groups**: запусти 3 инстанса с одинаковым `GroupID`. Kafka распределяет partitions между consumers (1 partition = 1 consumer max). Добавь 4-й инстанс — он будет idle (если partitions < consumers). Убери 1-й — rebalance, partitions перераспределяются.

## Теория

Жизненный цикл масштабирования Consumer Group:
- Топик имеет 3 партиции:
  - Шаг 1: 3 инстанса \(\to\) каждый обслуживает ровно 1 партицию.
  - Шаг 2: Добавлен 4-й инстанс \(\to\) партиций не хватает, 4-й переходит в состояние `IDLE`.
  - Шаг 3: Инстанс #1 аварийно завершает работу.
  - Шаг 4: Координатор инициирует Rebalance \(\to\) освободившаяся партиция переходит к простаивавшему 4-му инстансу!
- Ни одна партиция не остается без внимания, пропускная способность восстанавливается мгновенно.

## Решение по шагам

1. Создайте модель координатора группы с 3 партициями.
2. Подключите 4 воркера и убедитесь, что один из них получил статус `IDLE`.
3. Отключите воркер #1.
4. Выполните ребалансировку и убедитесь, что бывший `IDLE` воркер получил партицию.

## Код решения

**`consumer_idle_and_rebalance_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MemberAllocation struct {
	ID        string
	Partition int // -1 = IDLE
	Active    bool
}

func RebalanceMembers(members []*MemberAllocation, totalPartitions int) {
	var alive []*MemberAllocation
	for _, m := range members {
		m.Partition = -1 // сброс
		if m.Active {
			alive = append(alive, m)
		}
	}

	for p := 0; p < totalPartitions; p++ {
		if p < len(alive) {
			alive[p].Partition = p
		}
	}
}

func TestConsumerIdleAndRebalance(t *testing.T) {
	m1 := &MemberAllocation{ID: "c1", Active: true}
	m2 := &MemberAllocation{ID: "c2", Active: true}
	m3 := &MemberAllocation{ID: "c3", Active: true}
	m4 := &MemberAllocation{ID: "c4", Active: true}

	members := []*MemberAllocation{m1, m2, m3, m4}

	// 1. 4 воркера на 3 партиции -> c4 должен быть IDLE
	RebalanceMembers(members, 3)
	if m4.Partition != -1 {
		t.Fatalf("c4 должен быть IDLE (-1), got: %d", m4.Partition)
	}

	// 2. c1 упал
	m1.Active = false
	RebalanceMembers(members, 3)

	// Теперь c4 должен подхватить партицию!
	if m4.Partition == -1 {
		t.Fatal("c4 обязан выйти из IDLE и получить партицию!")
	}

	fmt.Println("Поведение Consumer Groups (IDLE и Rebalance) подтверждено:")
	fmt.Printf("  • Этап 1: c1->P0, c2->P1, c3->P2, c4->IDLE (в горячем резерве)\n")
	fmt.Printf("  • Этап 2: c1 упал! Произошел Rebalance:\n")
	fmt.Printf("    - c2 обслуживает: P%d\n", m2.Partition)
	fmt.Printf("    - c3 обслуживает: P%d\n", m3.Partition)
	fmt.Printf("    - c4 обслуживает: P%d (бывший резерв мгновенно встал в строй!)\n", m4.Partition)
}
```

ℹ️ Поведение горячего резерва IDLE и перехват партиции при ребалансировке

## Под капотом

Простаивающие консьюмеры (IDLE) продолжают отправлять Heartbeat запросы брокеру каждые `heartbeat.interval.ms` (обычно 3 секунды), поэтому брокер может назначить им партицию за доли секунды.

## Подводные камни

Держать постоянно много IDLE консьюмеров в продакшене без необходимости: они потребляют память и TCP дескрипторы брокера. Лучше настроить HPA/KEDA скейлинг подов по метрике Consumer Lag.

## На собеседовании

**Вопрос с собеседования:** «Можно ли временно назначить одну партицию двум консьюмерам одной группы для ускорения вычитки большого бэклога?»
**Ответ:** Категорически нет на уровне протокола Kafka. Модель строго требует \(1 \text{ partition} \to 1 \text{ consumer max}\) в группе. Чтобы ускорить обработку одной застрявшей партиции, внутри одного консьюмера создают многопоточный воркер-пул (Worker Pool) горутин для параллельной обработки независимых сообщений.
