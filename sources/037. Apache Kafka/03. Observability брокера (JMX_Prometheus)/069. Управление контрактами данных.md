# Управление контрактами данных: Schema Registry с Protobuf/Avro для защиты от ломающих изменений

## Условие

Используйте **Schema Registry** с Avro/Protobuf schemas для обеспечения совместимости сообщений (backward/forward compatibility).

## Теория

Защита контрактов через Schema Registry:
- В распределенных командах продюсер и консьюмер разрабатываются независимо.
- Без Schema Registry:
  - Продюсер удаляет или переименовывает поле в JSON \(\to\) консьюмер падает в продакшене.
- Со Schema Registry:
  - При CI/CD деплое продюсер проверяет совместимость схемы:
    `srclient.CheckCompatibility(subject, newSchema)`
  - Если режим `BACKWARD` нарушен \(\to\) билд падает до попадания в продакшен.
  - Сообщения сериализуются в компактный бинарный Avro/Protobuf с идентификатором схемы.

## Решение по шагам

1. Создайте структуру валидатора совместимости схем.
2. Проверьте допустимость добавления опционального поля с дефолтным значением.
3. Проверьте блокировку попытки удаления обязательного поля.
4. Убедитесь в соблюдении режима совместимости BACKWARD.

## Код решения

**`schema_compatibility_guard_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type SchemaField struct {
	Name     string
	Type     string
	Optional bool
}

type ContractSchema struct {
	Version int
	Fields  map[string]SchemaField
}

func CheckBackwardCompatibility(oldSchema, newSchema ContractSchema) error {
	// В режиме BACKWARD: все поля старой схемы обязаны присутствовать в новой!
	for name, oldField := range oldSchema.Fields {
		newField, exists := newSchema.Fields[name]
		if !exists {
			return fmt.Errorf("нарушение BACKWARD: удалено обязательное поле '%s'", name)
		}
		if newField.Type != oldField.Type {
			return fmt.Errorf("нарушение BACKWARD: изменен тип поля '%s'", name)
		}
	}
	return nil
}

func TestSchemaCompatibilityGuard(t *testing.T) {
	v1 := ContractSchema{
		Version: 1,
		Fields: map[string]SchemaField{
			"order_id": {Name: "order_id", Type: "string", Optional: false},
			"amount":   {Name: "amount", Type: "int", Optional: false},
		},
	}

	// Корректная эволюция: добавлено новое опциональное поле
	v2Valid := ContractSchema{
		Version: 2,
		Fields: map[string]SchemaField{
			"order_id": {Name: "order_id", Type: "string", Optional: false},
			"amount":   {Name: "amount", Type: "int", Optional: false},
			"promo":    {Name: "promo", Type: "string", Optional: true},
		},
	}

	// Несовместимая эволюция: удалено поле amount!
	v2Broken := ContractSchema{
		Version: 2,
		Fields: map[string]SchemaField{
			"order_id": {Name: "order_id", Type: "string", Optional: false},
		},
	}

	if err := CheckBackwardCompatibility(v1, v2Valid); err != nil {
		t.Fatalf("v2Valid должна быть совместима: %v", err)
	}

	errBroken := CheckBackwardCompatibility(v1, v2Broken)
	if errBroken == nil {
		t.Fatal("v2Broken обязана вернуть ошибку несовместимости")
	}

	fmt.Println("Schema Registry Guard успешно защитил контракты:")
	fmt.Printf("  • Добавление поля 'promo': Одобрено (Совместимость BACKWARD сохранена)\n")
	fmt.Printf("  • Удаление поля 'amount':  Отклонено (%v)\n", errBroken)
}
```

## Под капотом

Schema Registry выступает единым арбитром версионирования в компании, сохраняя историю версий схем во внутреннем топике Kafka `_schemas` с compact-политикой.

## Подводные камни

Использовать режим совместимости `NONE` в проде: это отключает любые проверки, позволяя продюсеру слать ломающие изменения и роняя все зависимые сервисы.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие режима совместимости FULL от BACKWARD?»
**Ответ:** В режиме `BACKWARD` новый код может читать старые сообщения. В режиме `FULL` обеспечивается двусторонняя совместимость: новый код читает старые сообщения, а старый код может читать новые сообщения без ошибок. Это позволяет деплоить сервисы продюсеров и консьюмеров в любом произвольном порядке.
