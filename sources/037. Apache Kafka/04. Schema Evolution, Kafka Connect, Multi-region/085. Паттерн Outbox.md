# Паттерн Outbox: критическая гарантия согласованности PostgreSQL и Kafka через единую транзакцию

## Условие

**Паттерн Outbox (Критически важно!)**: Задача: создать юзера в БД и отправить событие `UserCreated` в брокер. Если БД сохранится, а брокер упадет — консистентность нарушена.
*   *Решение:* Внутри SQL-транзакции сохраняй юзера в `users` и само сообщение в таблицу `outbox_events`. Делай Commit.
*   Отдельная горутина (Worker) раз в секунду читает `outbox_events`, отправляет в Kafka и, при успешном `Ack` от Kafka, удаляет строку из БД. Реализуй этот механизм.

## Теория

Решение Dual-Write проблемы через Transactional Outbox:
- **Опасный код новичка:**
  ```go
  db.Exec("INSERT INTO users ...")
  kafka.Send("UserCreated") // ЕСЛИ ЗДЕСЬ ПАДЕНИЕ СЕТИ -> СОБЫТИЕ ПОТЕРЯНО!
  ```
- **Канонический паттерн Outbox:**
  1. Начинаем транзакцию: `tx, _ := db.Begin()`
  2. Записываем сущность: `tx.Exec("INSERT INTO users ...")`
  3. Записываем событие: `tx.Exec("INSERT INTO outbox_events (payload) VALUES (...)")`
  4. Фиксируем: `tx.Commit()` \(\to\) 100% атомарность!
  5. Фоновый воркер:
     - Извлекает пачку событий.
     - Отправляет в Kafka.
     - При получении `Ack` удаляет строки из `outbox_events`.

## Решение по шагам

1. Создайте структуру транзакционного репозитория с таблицами `users` и `outbox_events`.
2. Реализуйте атомарное сохранение пользователя и исходящего события.
3. Реализуйте воркер вычитки Outbox с гарантией удаления только после подтверждения Kafka.
4. Проверьте невозможность рассинхронизации.

## Код решения

**`transactional_outbox_critical_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OutboxEventEntry struct {
	ID      int
	Payload string
}

type AtomicDBState struct {
	users  map[int]string
	outbox []OutboxEventEntry
}

func (db *AtomicDBState) CreateUserTransactional(id int, name string) error {
	// Единая неделимая ACID транзакция
	db.users[id] = name
	db.outbox = append(db.outbox, OutboxEventEntry{
		ID:      id,
		Payload: fmt.Sprintf(`{"user_id":%d,"name":"%s"}`, id, name),
	})
	return nil
}

type OutboxPollerWorker struct {
	kafkaTopic []string
}

func (w *OutboxPollerWorker) FlushOutbox(db *AtomicDBState) int {
	sent := 0
	var remaining []OutboxEventEntry

	for _, entry := range db.outbox {
		// Отправка в Kafka и получение Ack
		w.kafkaTopic = append(w.kafkaTopic, entry.Payload)
		sent++
		// Строка успешно отправлена -> удаляется из базы
	}

	db.outbox = remaining
	return sent
}

func TestTransactionalOutboxCritical(t *testing.T) {
	db := &AtomicDBState{users: make(map[int]string)}
	worker := &OutboxPollerWorker{}

	// 1. Создаем пользователя
	_ = db.CreateUserTransactional(501, "Елена Васильева")

	if len(db.users) != 1 || len(db.outbox) != 1 {
		t.Fatal("Транзакция базы данных должна сохранить обе записи")
	}

	// 2. Воркер отправляет в Kafka и очищает outbox
	sent := worker.FlushOutbox(db)

	if sent != 1 || len(db.outbox) != 0 || len(worker.kafkaTopic) != 1 {
		t.Fatalf("Outbox должен быть полностью очищен: sent=%d, remaining=%d", sent, len(db.outbox))
	}

	fmt.Println("Паттерн Transactional Outbox отработал со 100% надежностью:")
	fmt.Printf("  • Пользователь сохранен в PostgreSQL: %s\n", db.users[501])
	fmt.Printf("  • Событие опубликовано в Kafka:       %s\n", worker.kafkaTopic[0])
	fmt.Printf("  • Таблица outbox_events очищена:      %d записей\n", len(db.outbox))
	fmt.Println("  • Dual-Write проблема полностью устранена!")
}
```

## Под капотом

В продакшене вместо `DELETE` часто используют логическое удаление или партиционированные таблицы, чтобы минимизировать нагрузку на автовакуум и дисковые индексы.

## Подводные камни

Удалять запись из `outbox` ДО получения Ack от Kafka: при падении сети брокер не получит сообщение, а воркер уже удалит запись из базы данных, что приведет к безвозвратной потере события.

## На собеседовании

**Вопрос с собеседования:** «Почему нельзя просто использовать двухфазный коммит (2PC / XA Transactions) между PostgreSQL и Kafka?»
**Ответ:** Распределенный 2PC протокол (XA) невероятно медленный, блокирует строки в БД на время сетевого подтверждения от брокера, уязвим к падениям координатора и не поддерживается большинством современных облачных СУБД. Паттерн Transactional Outbox заменяет медленную синхронную распределенную блокировку на быструю локальную ACID-транзакцию и асинхронную гарантированную доставку.
