# Мульти-арендная маршрутизация (Multi-Tenant Routing): прокси-продюсер и паттерн Topic per Tenant

## Условие

**[Мульти-tenant маршрутизация]**: Напиши прокси-продюсер. В зависимости от `tenant_id` в запросе, сообщение должно лететь в Kafka topic `tenant_A_events` или `tenant_B_events`. (Паттерн "Topic per tenant").

## Теория

Паттерн изоляции тенантов в корпоративных SaaS:
- В B2B SaaS системе крупные клиенты (Tenant A — Сбер, Tenant B — Газпром) требуют:
  - Строгой физической изоляции данных (Data Isolation).
  - Раздельных квот производительности (Quotas), чтобы активность тенанта A не замедляла тенанта B (Noisy Neighbor Problem).
- **Паттерн Topic per Tenant:**
  - Прокси-продюсер динамически определяет топик назначения:
    `topic := fmt.Sprintf("tenant_%s_events", sanitize(req.TenantID))`
  - Обеспечивает соблюдение регуляторных требований и возможность настройки независимых политик шифрования и retention для каждого клиента.

## Решение по шагам

1. Создайте структуру запроса с идентификатором тенанта.
2. Реализуйте функцию динамической маршрутизации прокси-продюсера.
3. Проверьте изоляцию сообщений тенантов `tenant_A` и `tenant_B`.
4. Протестируйте валидацию недопустимых идентификаторов.

## Код решения

**`multitenant_proxy_producer_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type MultiTenantProxyProducer struct {
	topicStore map[string][]string
}

func (p *MultiTenantProxyProducer) RouteMessage(tenantID, payload string) (targetTopic string, err error) {
	if strings.ContainsAny(tenantID, "/: \t\n") {
		return "", fmt.Errorf("недопустимый символ в tenant_id: %s", tenantID)
	}

	// Паттерн Topic per Tenant
	targetTopic = fmt.Sprintf("tenant_%s_events", tenantID)

	p.topicStore[targetTopic] = append(p.topicStore[targetTopic], payload)
	return targetTopic, nil
}

func TestMultiTenantProxyProducer(t *testing.T) {
	proxy := &MultiTenantProxyProducer{topicStore: make(map[string][]string)}

	tA, errA := proxy.RouteMessage("corp_a", "Событие авторизации сотрудника A")
	tB, errB := proxy.RouteMessage("corp_b", "Событие авторизации сотрудника B")

	if errA != nil || errB != nil || tA != "tenant_corp_a_events" || tB != "tenant_corp_b_events" {
		t.Fatalf("Ошибка маршрутизации: %v, %v", errA, errB)
	}

	fmt.Println("Мульти-арендный прокси-продюсер (Topic per Tenant) успешно отработал:")
	fmt.Printf("  • Tenant 'corp_a' -> топик: %s (Сообщений: %d)\n", tA, len(proxy.topicStore[tA]))
	fmt.Printf("  • Tenant 'corp_b' -> топик: %s (Сообщений: %d)\n", tB, len(proxy.topicStore[tB]))
	fmt.Println("  • Полная изоляция данных и защита от Noisy Neighbor обеспечены!")
}
```

ℹ️ Динамическая изоляция потоков событий клиентов по паттерну Topic per Tenant

## Под капотом

В Kafka квоты на скорость записи и чтения (`client-id` / `user`) настраиваются через команду `kafka-configs.sh`, не позволяя одному клиенту забить всю полосу пропускания сетевой карты брокера.

## Подводные камни

Создавать миллион топиков для миллиона B2C пользователей: каждый топик создает открытые файлы и метаданные на контроллере. Паттерн Topic per Tenant применяется только для крупных корпоративных B2B клиентов (до сотен/тысяч тенантов).

## На собеседовании

**Вопрос с собеседования:** «Как реализовать мульти-тенантность для 500 000 мелких клиентов в Kafka?»
**Ответ:** Использовать единый общий топик (Shared Topic), но включать `tenant_id` в префикс ключа партиционирования: `Key = tenant_id + ":" + entity_id`. На уровне консьюмера использовать фильтрацию, либо проксировать события через внутренний роутер.
