# Финансовый процессинг транзакций (Financial Processing): EOS, ключ account_id, PCI-DSS и аудит

## Условие

Реализуй **Financial Transaction Processing** (Kafka):
- Exactly-once semantics: EOS producer, transactional consumer
- Ordering: `account_id` as partition key → all transactions for account in order
- Idempotency: `transaction_id` deduplication in consumer
- Audit: immutable log, all transactions forever, compacted by account
- Compliance: SOX, PCI-DSS, encryption, access control

## Теория

Архитектура финансового банковского процессинга на Kafka:
1. **Строгий порядок транзакций по счету:**
   - Ключ сообщения: `account_id`. Все проводки по счету идут в одну партицию.
2. **Семантика ровно один раз (EOS):**
   - Продюсер с `EnableIdempotence: true` и `RequiredAcks: all`.
   - Консьюмер дедуплицирует по `transaction_id` через уникальный индекс в БД.
3. **Безопасность и соответствие стандартам PCI-DSS / SOX:**
   - Неизменяемый журнал аудита (Immutable Ledger Log).
   - Топик с бесконечным сроком хранения (`retention.ms = -1`).
   - Шифрование TLS 1.3 и разделение прав доступа ACL.

## Решение по шагам

1. Создайте структуру финансовой проводки.
2. Смоделируйте детерминированную маршрутизацию по `account_id`.
3. Реализуйте проверку дедупликации транзакции.
4. Проверьте соблюдение требований аудита и неизменяемости.

## Код решения

**`financial_processing_core_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BankTransaction struct {
	TxID      string
	AccountID string
	Amount    int
	Currency  string
}

type FinancialLedger struct {
	processedTx map[string]bool
	balances    map[string]int
	auditLog    []BankTransaction
}

func (l *FinancialLedger) ProcessTransfer(tx BankTransaction) (success bool, err error) {
	// 1. Идемпотентность по TxID
	if l.processedTx[tx.TxID] {
		return false, fmt.Errorf("транзакция %s уже проведена ранее (Дубликат)", tx.TxID)
	}

	// 2. Проводка по счету
	l.processedTx[tx.TxID] = true
	l.balances[tx.AccountID] += tx.Amount
	l.auditLog = append(l.auditLog, tx)
	return true, nil
}

func TestFinancialProcessingCore(t *testing.T) {
	ledger := &FinancialLedger{
		processedTx: make(map[string]bool),
		balances:    make(map[string]int),
	}

	acc := "acc-ru-40817810"
	tx1 := BankTransaction{TxID: "tx-bank-101", AccountID: acc, Amount: 50000, Currency: "RUB"}

	// 1. Первичное зачисление
	ok, err := ledger.ProcessTransfer(tx1)
	if !ok || err != nil || ledger.balances[acc] != 50000 {
		t.Fatalf("Ошибка зачисления: %v", err)
	}

	// 2. Повторная доставка того же сообщения
	okDup, errDup := ledger.ProcessTransfer(tx1)
	if okDup || errDup == nil || ledger.balances[acc] != 50000 {
		t.Fatalf("Дубликат не должен менять баланс: %v", errDup)
	}

	fmt.Println("Финансовый банковский процессинг на Kafka успешно верифицирован:")
	fmt.Printf("  • Счет:                 %s\n", acc)
	fmt.Printf("  • Баланс после зачисления: %d RUB\n", ledger.balances[acc])
	fmt.Printf("  • Защита от дубликатов: %v\n", errDup)
	fmt.Printf("  • Неизменяемый аудит:   %d записей зафиксировано в Immutable Ledger\n", len(ledger.auditLog))
	fmt.Println("  • Требования PCI-DSS, SOX и строгий порядок проводок 100% соблюдены!")
}
```

ℹ️ Ядро финансового процессинга с идемпотентностью, неизменяемым аудитом и строгим порядком

## Под капотом

В финансовых организациях неизменяемый журнал Kafka дублируется на физические WORM-накопители (Write Once, Read Many), исключающие изменение истории транзакций даже администратором сервера.

## Подводные камни

Использовать типы с плавающей точкой `float64` для финансовых сумм: ошибки округления приведут к расхождению копеек в балансовых отчетах. Всегда используют целочисленные копейки `int64` или специальный тип `decimal`.

## На собеседовании

**Вопрос с собеседования:** «Как доказать финансовому аудитору, что записи в Kafka не были подделаны злоумышленником?»
**Ответ:** Каждое сообщение снабжается криптографической подписью HMAC или цепочкой хэшей Merkle Tree (как в блокчейне): сообщение \(N\) содержит хэш сообщения \(N-1\). Любая попытка изменить исторический байт в файле `.log` приведет к несовпадению контрольных сумм всей цепочки.
