## Теория

Архитектура мониторинга Kafka в Prometheus/Grafana:
- Метрики брокера (`kafka_exporter` / JMX):
  - `kafka_server_brokertopicmetrics_messagesin_total`: входящий объем сообщений (Rate/Throughput).
  - `kafka_network_request_total`: сетевая активность и latency обработки запросов.
- Метрики потребителей:
  - `kafka_consumer_group_lag`: отставание консьюмер-групп по каждой партиции топика.
- Метрики надежности:
  - `kafka_server_replicamanager_underreplicatedpartitions`: угроза репликации (\(>0 \to\) P1 Alert).
  - `kafka_controller_kafkacontroller_offlinepartitionscount`: отказ партиции (\(>0 \to\) P0 Critical Alert).

## Решение по шагам

1. Создайте структуру метрик мониторинга Prometheus.
2. Реализуйте проверку аварийных порогов.
3. Продемонстрируйте классификацию алертов (Warning, Critical).
4. Проверьте правильность формирования телеметрии.

## Код решения

**`kafka_prometheus_dashboard_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type KafkaDashboardMetrics struct {
	MessagesInRate     float64
	MaxConsumerLag     int64
	UnderReplicated    int
	OfflinePartitions  int
}

func (m KafkaDashboardMetrics) CheckAlerts() []string {
	var alerts []string
	if m.OfflinePartitions > 0 {
		alerts = append(alerts, fmt.Sprintf("P0 EMERGENCY: %d offline partitions detected!", m.OfflinePartitions))
	}
	if m.UnderReplicated > 0 {
		alerts = append(alerts, fmt.Sprintf("P1 CRITICAL: %d under-replicated partitions!", m.UnderReplicated))
	}
	if m.MaxConsumerLag > 50000 {
		alerts = append(alerts, fmt.Sprintf("P2 WARNING: Consumer lag exceeded threshold: %d", m.MaxConsumerLag))
	}
	return alerts
}

func TestKafkaPrometheusDashboard(t *testing.T) {
	metrics := KafkaDashboardMetrics{
		MessagesInRate:    125400.0, // 125k msg/s
		MaxConsumerLag:    62000,
		UnderReplicated:   0,
		OfflinePartitions: 0,
	}

	alerts := metrics.CheckAlerts()
	if len(alerts) != 1 {
		t.Fatalf("Ожидался ровно 1 алерт по лагу: %v", alerts)
	}

	fmt.Println("Дашборд Prometheus & Grafana успешно проанализирован:")
	fmt.Printf("  • Throughput:            %.1f msg/sec (kafka_server_brokertopicmetrics_messagesin_total)\n", metrics.MessagesInRate)
	fmt.Printf("  • Under-replicated:      %d (Здоровье реплик в норме)\n", metrics.UnderReplicated)
	fmt.Printf("  • Offline partitions:    %d (Все партиции доступны)\n", metrics.OfflinePartitions)
	fmt.Printf("  • Алерт:                 %s\n", alerts[0])
}
```

## Под капотом

Экспортер `kafka_exporter` опрашивает метаданные кластера раз в 15–30 секунд и предоставляет стандартный HTTP эндпоинт `/metrics` для скрейпинга Prometheus сервером.

## Подводные камни

Настраивать алерты по абсолютному значению лага без учета скорости продюсера: для топика со скоростью 100k msg/s лаг в 50 000 сообщений — это всего 500 миллисекунд работы, а не авария. В таких системах алерты настраивают по времени задержки (Lag Time-to-Process).

## На собеседовании

**Вопрос с собеседования:** «Как вычислить время отставания консьюмера в секундах (Lag in Seconds), а не в количестве сообщений?»
**Ответ:** Разработчики сравнивают таймстамп текущего обрабатываемого сообщения `msg.Time` с системным временем `time.Now()`. Либо используют экспортеры, которые сопоставляют смещение консьюмера с временными метками в файле индекса `.timeindex` партиции.
