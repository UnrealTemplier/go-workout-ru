# Режимы совместимости Schema Evolution: BACKWARD, FORWARD и FULL на примере схемы Order

## Условие

Покажи **Schema Evolution**: v1 `Order { id: long, total: double }`. v2 добавляет `status: string` (optional, default `"pending"`). Compatibility `BACKWARD`: новый consumer читает старые сообщения (default value). `FORWARD`: старый consumer читает новые (ignores unknown field). `FULL`: оба направления.

## Теория

Матрица совместимости Schema Evolution:
1. **BACKWARD (Новый консьюмер читает старые данные):**
   - Новые поля обязаны иметь значение по умолчанию (`default`).
   - Консьюмер развертывается ПЕРВЫМ, затем обновляется продюсер.
2. **FORWARD (Старый консьюмер читает новые данные):**
   - Нельзя удалять существующие поля без дефолтов.
   - Продюсер развертывается ПЕРВЫМ, затем обновляются консьюмеры.
3. **FULL (Двусторонняя совместимость):**
   - Сочетает правила BACKWARD и FORWARD.
   - Сервисы можно обновлять в любом порядке (Zero Downtime Rolling Updates).

## Решение по шагам

1. Создайте модель данных заказа v1 и v2 с дефолтным статусом `pending`.
2. Продемонстрируйте чтение старого сообщения новым кодом (BACKWARD).
3. Продемонстрируйте чтение нового сообщения старым кодом (FORWARD).
4. Проверьте соблюдение режима FULL.

## Код решения

**`schema_evolution_modes_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OrderV1 struct {
	ID    int64
	Total float64
}

type OrderV2 struct {
	ID     int64
	Total  float64
	Status string // default: "pending"
}

func DecodeV1ToV2(v1 OrderV1) OrderV2 {
	// BACKWARD: старое сообщение дополняется дефолтным статусом
	return OrderV2{
		ID:     v1.ID,
		Total:  v1.Total,
		Status: "pending",
	}
}

func DecodeV2ToV1(v2 OrderV2) OrderV1 {
	// FORWARD: старый консьюмер игнорирует новое поле Status
	return OrderV1{
		ID:    v2.ID,
		Total: v2.Total,
	}
}

func TestSchemaEvolutionModes(t *testing.T) {
	// 1. Тестируем BACKWARD: новый консьюмер читает старый v1 заказ
	v1Old := OrderV1{ID: 1001, Total: 2500.50}
	v2Read := DecodeV1ToV2(v1Old)

	if v2Read.Status != "pending" || v2Read.Total != 2500.50 {
		t.Fatalf("Ошибка BACKWARD: %+v", v2Read)
	}

	// 2. Тестируем FORWARD: старый консьюмер читает новый v2 заказ
	v2New := OrderV2{ID: 1002, Total: 8900.0, Status: "shipped"}
	v1Read := DecodeV2ToV1(v2New)

	if v1Read.ID != 1002 || v1Read.Total != 8900.0 {
		t.Fatalf("Ошибка FORWARD: %+v", v1Read)
	}

	fmt.Println("Режимы Schema Evolution успешно продемонстрированы:")
	fmt.Printf("  • BACKWARD: новый консьюмер прочитал V1 (Status автоматически подставлен: '%s')\n", v2Read.Status)
	fmt.Printf("  • FORWARD:  старый консьюмер прочитал V2 (поле Status безопасно проигнорировано)\n")
	fmt.Println("  • Режим FULL обеспечивает абсолютно бесшовный rolling update любых микросервисов!")
}
```

ℹ️ Демонстрация обратной и прямой совместимости схем (BACKWARD, FORWARD, FULL)

## Под капотом

Формат Apache Avro использует концепцию Schema Resolution: десериализатор принимает одновременно Writers Schema (с которой сообщение было записано) и Readers Schema (которую ожидает приложение) и автоматически сопоставляет поля по именам и дефолтам.

## Подводные камни

Добавить новое поле без дефолтного значения в режиме BACKWARD: Schema Registry отклонит регистрацию схемы с ошибкой `IncompatibleSchemaException`.

## На собеседовании

**Вопрос с собеседования:** «Какой режим совместимости рекомендуется выставлять для топиков ядра платформы в крупных компаниях?»
**Ответ:** Режим `FULL_TRANSITIVE`. Он гарантирует, что новая версия схемы совместима не только с предыдущей (v3 c v2), но и со всеми историческими версиями (v3 с v1). Это позволяет консьюмерам безопасно делать исторический replay топика за несколько лет.
