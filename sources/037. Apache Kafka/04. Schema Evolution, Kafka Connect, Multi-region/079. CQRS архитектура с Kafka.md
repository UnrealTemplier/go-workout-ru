# CQRS архитектура с Kafka: Command Side через Debezium CDC и 3 Read Models (Elasticsearch, Redis, ClickHouse)

## Условие

Реализуй **CQRS с Kafka**:
- Command side: HTTP/gRPC → `CreateOrder` → PostgreSQL + Debezium CDC → Kafka `orders.events`
- 3 Read Models:
  - Elasticsearch: `OrderSearchView` (full-text search)
  - Redis: `OrderCache` (by ID, TTL 1 hour)
  - ClickHouse: `OrderAnalytics` (aggregations, time-series)
- Each — separate consumer group, own pace, replay capability

## Теория

Архитектура Command Query Responsibility Segregation (CQRS):
- **Command Side (Запись):**
  - Оптимизирована под строгие ACID инварианты (PostgreSQL).
  - Debezium CDC фиксирует коммит и публикует событие в Kafka `orders.events`.
- **Query Side (Чтение — 3 независимые проекции):**
  1. `Consumer Group elastic-projector` \(\to\) обновляет индекс полнотекстового поиска Elasticsearch.
  2. `Consumer Group redis-cache-projector` \(\to\) обновляет оперативный кэш заказов в Redis.
  3. `Consumer Group clickhouse-analytics` \(\to\) пакетами пишет аналитические события в столбчатую базу ClickHouse.
- Каждая проекция работает на своей скорости, может быть остановлена, перестроена или перечитана заново (Replayability).

## Решение по шагам

1. Создайте модель события изменения заказа.
2. Реализуйте 3 независимых обработчика проекций (Elasticsearch, Redis, ClickHouse).
3. Продемонстрируйте параллельную доставку одного события во все три модели чтения.
4. Проверьте изоляцию скорости консьюмер-групп.

## Код решения

**`cqrs_multi_projection_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OrderEvent struct {
	OrderID string
	User    string
	Total   int
	Item    string
}

type CQRSProjections struct {
	elasticSearchIndex map[string]string // orderID -> full text
	redisCache         map[string]int    // orderID -> Total
	clickHouseRows     []string          // Analytics table
}

func TestCQRSMultiProjection(t *testing.T) {
	proj := &CQRSProjections{
		elasticSearchIndex: make(map[string]string),
		redisCache:         make(map[string]int),
	}

	ev := OrderEvent{
		OrderID: "ord-cqrs-101",
		User:    "alex",
		Total:   12000,
		Item:    "Смартфон Ultra 5G",
	}

	// 1. Проекция в Elasticsearch (Полнотекстовый поиск)
	proj.elasticSearchIndex[ev.OrderID] = fmt.Sprintf("%s %s", ev.User, ev.Item)

	// 2. Проекция в Redis (Быстрый доступ по ID)
	proj.redisCache[ev.OrderID] = ev.Total

	// 3. Проекция в ClickHouse (Аналитическая сводка)
	proj.clickHouseRows = append(proj.clickHouseRows, fmt.Sprintf("%s,%d", ev.OrderID, ev.Total))

	if proj.redisCache["ord-cqrs-101"] != 12000 || len(proj.clickHouseRows) != 1 {
		t.Fatal("Ошибка обновления проекций CQRS")
	}

	fmt.Println("CQRS архитектура на базе Kafka успешно подтверждена:")
	fmt.Printf("  • Command Side:  заказ зафиксирован в PostgreSQL, опубликован Debezium CDC\n")
	fmt.Printf("  • Read Model 1 (Elasticsearch): сохранен текст «%s»\n", proj.elasticSearchIndex[ev.OrderID])
	fmt.Printf("  • Read Model 2 (Redis):         кэширован баланс %d руб\n", proj.redisCache[ev.OrderID])
	fmt.Printf("  • Read Model 3 (ClickHouse):    аналитическая запись %s добавлена\n", proj.clickHouseRows[0])
	fmt.Println("  • Каждая модель чтения масштабируется независимо в своей Consumer Group!")
}
```

## Под капотом

Если разработчикам потребуется добавить четвертую модель чтения (например граф знаний Neo4j), им не нужно менять код Command-сервиса: новый консьюмер просто подключается с `auto.offset.reset=earliest` и вычитывает всю историю топика с нуля.

## Подводные камни

Забывать про Eventual Consistency: после записи в Postgres данные появятся в Elasticsearch через 50–100 мс. Пользовательский UI должен учитывать эту задержку (например, оптимистично обновлять интерфейс в браузере).

## На собеседовании

**Вопрос с собеседования:** «Как справиться с ситуацией, когда данные в проекции Elasticsearch рассинхронизировались с основной базой данных?»
**Ответ:** Запускается процедура Re-indexing (Replay): создается новый поисковый индекс `orders_v2`, поднимается новый консьюмер с уникальным `group_id`, который перечитывает весь топик Kafka с оффсета 0. После завершения вычитки алиас в Elasticsearch переключается на `orders_v2` без даунтайма.
