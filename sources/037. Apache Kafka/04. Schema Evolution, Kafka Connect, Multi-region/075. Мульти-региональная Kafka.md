# Мульти-региональная Kafka: MirrorMaker 2, Follower Fetching и сценарии Disaster Recovery Failover

## Условие

Реализуй **Multi-region Kafka**: MirrorMaker 2 или `kafka-reassign-partitions`. Topic `orders` replicated в 2 датацентра. Producer пишет в local DC. Consumer читает из local DC (follower fetch). Failover: при падении DC1 — DC2 продолжает.

## Теория

Архитектура Multi-Region с Follower Fetching (KIP-392):
- Традиционно клиенты Kafka читают СТРОГО с лидера партиции.
- В мульти-региональном облаке (AWS `eu-west-1` и `eu-central-1`):
  - Межрегиональный сетевой трафик стоит дорого и имеет высокую задержку (Cross-AZ traffic).
  - С фичей **Follower Fetching**:
    - Консьюмер в регионе Frankfurt читает данные с локальной реплики-фолловера (`client.rack = rack-frankfurt`).
    - Нулевой межрегиональный трафик на чтении!
- При аварии всего дата-центра DC1 продюсеры и консьюмеры переключаются на DC2 (RPO < 1c, RTO < 10c).

## Решение по шагам

1. Создайте модель топологии с двумя регионами (DC1 и DC2).
2. Настройте маршрутизацию Follower Fetching по стойкам (`client.rack`).
3. Смоделируйте отказ региона DC1.
4. Продемонстрируйте продолжение работы консьюмеров из DC2.

## Код решения

**`multi_region_follower_fetch_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RegionalBroker struct {
	ID       int
	Region   string
	IsLeader bool
	IsAlive  bool
}

func ResolveFetchNode(brokers []RegionalBroker, clientRegion string) (int, error) {
	// Сначала ищем локальную живую ноду в том же регионе (Follower Fetch)
	for _, b := range brokers {
		if b.Region == clientRegion && b.IsAlive {
			return b.ID, nil
		}
	}
	// Если локальной ноды нет, идем к лидеру
	for _, b := range brokers {
		if b.IsLeader && b.IsAlive {
			return b.ID, nil
		}
	}
	return -1, fmt.Errorf("все брокеры региона и лидер недоступны")
}

func TestMultiRegionFollowerFetch(t *testing.T) {
	brokers := []RegionalBroker{
		{ID: 1, Region: "dc-msk", IsLeader: true, IsAlive: true},
		{ID: 2, Region: "dc-spb", IsLeader: false, IsAlive: true}, // Локальный фолловер в СПб
	}

	// 1. Клиент из СПб читает с локального фолловера
	targetNode, err := ResolveFetchNode(brokers, "dc-spb")
	if err != nil || targetNode != 2 {
		t.Fatalf("Должен быть выбран локальный брокер #2: %d", targetNode)
	}

	// 2. DC1 (Москва) полностью обесточен
	brokers[0].IsAlive = false
	// Выборы нового лидера в СПб
	brokers[1].IsLeader = true

	failoverNode, err := ResolveFetchNode(brokers, "dc-spb")
	if err != nil || failoverNode != 2 {
		t.Fatalf("После аварии DC1 работа должна продолжиться на ноде #2")
	}

	fmt.Println("Мульти-региональная топология (Follower Fetching & Failover) подтверждена:")
	fmt.Printf("  • Клиент СПб: читает с локального фолловера #2 (Экономия 100%% Cross-Region трафика!)\n")
	fmt.Printf("  • Авария DC1:  брокер #2 принял лидерство, чтение и запись продолжаются без простоя!\n")
}
```

## Под капотом

Параметр `client.rack` сопоставляется брокером с его собственным `broker.rack`. Если совпадение найдено и фолловер находится в ISR списке, брокер разрешает чтение с локальной ноды.

## Подводные камни

Включать Follower Fetching для фолловеров, отстающих от лидера: консьюмер получит старые данные. Kafka строго контролирует, чтобы фолловер находился в статусе In-Sync Replica.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Active-Active гео-репликации от Active-Passive в Kafka?»
**Ответ:** В Active-Passive один ДЦ является основным, а второй принимает данные только как резерв (MirrorMaker 2). В Active-Active оба ДЦ принимают трафик локальных пользователей параллельно; топики именуются с префиксом региона (`msk.orders` и `spb.orders`), а приложения подписываются на объединенный поток по маске `*.orders`.
