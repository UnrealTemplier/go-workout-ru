# Управление обратным давлением и воркер-пул: пачечное чтение по 1000 сообщений и лимит 10 горутин

## Условие

**[Backpressure / Rate Limiting]**: Напиши консьюмера Kafka, который читает сообщения пачками по 1000 штук, но обрабатывает их через пул воркеров ограниченного размера (например, 10 горутин). Если канал воркеров забит — приостанавливай чтение из Kafka.

## Теория

Паттерн Worker Pool с обратным давлением (Backpressure Controlled Consumer):
- Если консьюмер будет создавать `go handle(msg)` на каждое сообщение:
  - При бэклоге в 1 000 000 сообщений сервис создаст миллион горутин и упадет с OOM.
- **Архитектура с буферизованным каналом:**
  - Пул воркеров: строго 10 горутин, читающих из канала `jobs := make(chan Message, 100)`.
  - Цикл чтения консьюмера:
    - Читает порцию сообщений.
    - Отправляет в канал: `jobs <- msg`.
    - Если канал полон (все 10 воркеров заняты, буфер заполнен) \(\to\) горутина чтения **естественным образом блокируется**!
  - Чтение из Kafka приостанавливается автоматически без переполнения памяти.

## Решение по шагам

1. Создайте ограниченный воркер-пул на 10 воркеров.
2. Создайте буферизованный канал задач.
3. Смоделируйте блокировку продюсера при переполнении канала.
4. Продемонстрируйте защиту от неконтролируемого роста горутин.

## Код решения

**`worker_pool_backpressure_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type ControlledWorkerPool struct {
	jobsChan   chan int
	workerNum  int
	processed  int
	mu         sync.Mutex
	wg         sync.WaitGroup
}

func NewControlledWorkerPool(workers, queueSize int) *ControlledWorkerPool {
	p := &ControlledWorkerPool{
		jobsChan:  make(chan int, queueSize),
		workerNum: workers,
	}

	for i := 0; i < workers; i++ {
		p.wg.Add(1)
		go func() {
			defer p.wg.Done()
			for job := range p.jobsChan {
				time.Sleep(5 * time.Millisecond) // полезная работа
				p.mu.Lock()
				p.processed += job
				p.mu.Unlock()
			}
		}()
	}
	return p
}

func (p *ControlledWorkerPool) Enqueue(job int) {
	p.jobsChan <- job // Блокирует чтение из Kafka, если очередь переполнена!
}

func (p *ControlledWorkerPool) Stop() {
	close(p.jobsChan)
	p.wg.Wait()
}

func TestWorkerPoolBackpressure(t *testing.T) {
	// Пул из 3 воркеров и очередь на 5 задач
	pool := NewControlledWorkerPool(3, 5)

	// Отправляем 10 задач
	for i := 1; i <= 10; i++ {
		pool.Enqueue(1)
	}

	pool.Stop()

	if pool.processed != 10 {
		t.Fatalf("Должно быть обработано 10 задач: %d", pool.processed)
	}

	fmt.Println("Воркер-пул с Backpressure успешно отработал:")
	fmt.Printf("  • Ограничение: строго %d горутин воркеров\n", pool.workerNum)
	fmt.Printf("  • Успешно обработано: %d задач\n", pool.processed)
	fmt.Println("  • Переполнение памяти OOM и бесконечный спавн горутин полностью исключены!")
}
```

## Под капотом

Встроенный механизм каналов Go (`chan`) реализует примитивы синхронизации через `runtime.gopark`, переводя заблокированную горутину в режим ожидания без сжигания тактов процессора.

## Подводные камни

Забывать, что при параллельной обработке пачки задач в пуле горутин сообщения могут завершаться не по порядку: коммитить оффсеты можно только последовательно!

## На собеседовании

**Вопрос с собеседования:** «Как коммитить оффсеты в Kafka, если сообщения из одной партиции обрабатываются параллельным пулом горутин?»
**Ответ:** Используют структуру Sliding Window Offset Tracker: оффсет коммитится только тогда, когда все предшествующие ему оффсеты (\(0 \dots N\)) гарантированно завершили обработку. Коммит самого старшего непрерывного блока гарантирует соблюдение At-Least-Once семантики без пропусков.
