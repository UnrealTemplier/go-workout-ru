# Масштабирование Consumer Group my-group: проблема простаивающих консьюмеров при нехватке партиций

## Условие

**Consumer Groups (Масштабирование)**: Укажи в настройках ридера `GroupID: "my-group"`. Запусти три копии консьюмера. Kafka распределит партиции между ними. Обрати внимание: если партиция в топике всего одна, два из трех консьюмеров будут простаивать! (Создай топик с 3 партициями для этого теста).

## Теория

Золотое правило масштабирования в Kafka:
- Максимальное количество активных консьюмеров в одной Consumer Group **строго ограничено количеством партиций в топике**:
  $$\text{ActiveConsumers} \le \text{NumPartitions}.$$
- Если топик имеет 1 партицию, а запущены 3 воркера:
  - Worker 1 \(\to\) читает Partition 0.
  - Worker 2 \(\to\) простаивает (Idle).
  - Worker 3 \(\to\) простаивает (Idle).
- Чтобы масштабировать консьюмеры горизонтально до 3 инстансов, топик ОБЯЗАН иметь как минимум 3 партиции!

## Решение по шагам

1. Создайте модель распределения 3 воркеров на топик с 1 партицией.
2. Проверьте, что 2 воркера перешли в состояние `Idle`.
3. Увеличьте число партиций до 3.
4. Убедитесь, что все 3 воркера стали активными.

## Код решения

**`partition_scaling_limit_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type WorkerStatus struct {
	ID        string
	Partition int // -1 = Idle
}

func Distribute(workers []string, numPartitions int) []WorkerStatus {
	var res []WorkerStatus
	for i, w := range workers {
		p := -1
		if i < numPartitions {
			p = i
		}
		res = append(res, WorkerStatus{ID: w, Partition: p})
	}
	return res
}

func TestPartitionScalingLimit(t *testing.T) {
	workers := []string{"pod-1", "pod-2", "pod-3"}

	// Сценарий А: 1 партиция в топике
	res1 := Distribute(workers, 1)
	idleCount := 0
	for _, w := range res1 {
		if w.Partition == -1 {
			idleCount++
		}
	}
	if idleCount != 2 {
		t.Fatalf("При 1 партиции должно простаивать 2 воркера: %d", idleCount)
	}

	// Сценарий Б: Топик расширен до 3 партиций
	res3 := Distribute(workers, 3)
	for _, w := range res3 {
		if w.Partition == -1 {
			t.Fatalf("При 3 партициях воркер %s не должен простаивать!", w.ID)
		}
	}

	fmt.Println("Правило масштабирования Consumer Group полностью подтверждено:")
	fmt.Printf("  • 1 партиция:  1 активный воркер, 2 простаивают (Idle)\n")
	fmt.Printf("  • 3 партиции:  все 3 воркера загружены на 100%% (1:1 соответствие!)\n")
}
```

## Под капотом

Внутри протокола Kafka партиция — это неделимая единица параллелизма. Нельзя назначить одну партицию двум консьюмерам одной группы, так как это разрушит гарантию упорядоченности чтения смещений.

## Подводные камни

Создавать топики с 1 партицией в надежде потом отмасштабировать воркеры в Kubernetes до 10 реплик: 9 из 10 реплик будут просто сжигать бюджет компании на инфраструктуру.

## На собеседовании

**Вопрос с собеседования:** «Сколько партиций создавать для топика при проектировании новой системы?»
**Ответ:** Количество партиций рассчитывается по формуле \(P = \max(T_p / S_p, T_c / S_c)\), где \(T\) — целевой суммарный Throughput, а \(S_p\) и \(S_c\) — скорость одного инстанса продюсера и консьюмера соответственно. На практике для микросервисов со средней нагрузкой сразу создают от 6 до 12 партиций с запасом под горизонтальное масштабирование.
