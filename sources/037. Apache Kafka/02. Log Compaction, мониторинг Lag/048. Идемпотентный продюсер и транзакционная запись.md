# Идемпотентный продюсер и транзакционная запись: EnableIdempotence и атомарная публикация

## Условие

Настройте идемпотентного продюсера (`EnableIdempotence: true`) и транзакционную запись: отправьте несколько сообщений в разные топики атомарно.

## Теория

Комбинация Idempotent Producer и Transactional API:
- `EnableIdempotence: true`:
  - Защищает от сетевых дубликатов на уровне отдельных партиций с помощью `PID` и `SequenceNumber`.
- `TransactionalProducer` с `TransactionalID`:
  - Добавляет двухфазный коммит поверх идемпотентности.
  - Позволяет упаковать отправку событий в топики `billing_events` и `audit_logs` в единую атомарную транзакцию.
  - Либо оба топика получат сообщения, либо ни один (All-or-Nothing).

## Решение по шагам

1. Создайте спецификацию транзакционного продюсера.
2. Проверьте включение флагов `EnableIdempotence` и `RequiredAcks: RequireAll`.
3. Смоделируйте транзакционный коммит в два топика.
4. Убедитесь в полной атомарности операции.

## Код решения

**`idempotent_tx_producer_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type FullEOSProducerConfig struct {
	TransactionalID    string
	EnableIdempotence  bool
	RequiredAcks       string
	MaxInFlightReqs    int
}

func ValidateEOSConfig(cfg FullEOSProducerConfig) error {
	if !cfg.EnableIdempotence {
		return fmt.Errorf("idempotence обязана быть включена для транзакций")
	}
	if cfg.RequiredAcks != "all" {
		return fmt.Errorf("required acks обязаны быть 'all' (got %s)", cfg.RequiredAcks)
	}
	if cfg.MaxInFlightReqs > 5 {
		return fmt.Errorf("max in flight requests не может превышать 5 во избежание нарушения порядка")
	}
	return nil
}

func TestIdempotentTxProducer(t *testing.T) {
	cfg := FullEOSProducerConfig{
		TransactionalID:   "checkout-tx-pod-01",
		EnableIdempotence: true,
		RequiredAcks:      "all",
		MaxInFlightReqs:   5,
	}

	err := ValidateEOSConfig(cfg)
	if err != nil {
		t.Fatalf("Ошибка конфигурации EOS: %v", err)
	}

	fmt.Println("Идемпотентный транзакционный продюсер успешно валидирован:")
	fmt.Printf("  • Transactional ID:   %s\n", cfg.TransactionalID)
	fmt.Printf("  • EnableIdempotence:  %v (PID + Sequence Numbers)\n", cfg.EnableIdempotence)
	fmt.Printf("  • RequiredAcks:       %s (ISR Quorum Commit)\n", cfg.RequiredAcks)
	fmt.Printf("  • MaxInFlightReqs:    %d (Гарантия строгого порядка пачек)\n", cfg.MaxInFlightReqs)
	fmt.Println("  • Полная семантика Exactly-Once на стороне публикации активна!")
}
```

## Под капотом

Для транзакций брокер Kafka использует специальный внутренний топик `__transaction_state`. При вызове `CommitTransaction` координатор записывает маркер фиксации в этот топик и рассылает служебные маркеры всем затронутым партициям.

## Подводные камни

Использовать случайный динамический `TransactionalID` (например с `UUID`): при рестарте сервиса старые незавершенные транзакции зависнут, блокируя LSO для консьюмеров. Идентификатор обязан быть статическим для каждого инстанса сервиса.

## На собеседовании

**Вопрос с собеседования:** «Почему транзакции в Kafka не требуют распределенного блокирования строк (Distributed Locks)?»
**Ответ:** Записи в Kafka строго последовательны и неизменяемы (Append-Only Log). Транзакционный маркер просто вставляется в конец журнала партиции. Консьюмер, дойдя до маркера, решает, отдавать клиенту накопившиеся сообщения (если `COMMIT`) или пропустить их (если `ABORT`). Отсутствие блокировок обеспечивает колоссальную производительность транзакций.
