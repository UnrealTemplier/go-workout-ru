# Отказоустойчивый кластер из 3 брокеров: фактор репликации RF=3, min.insync.replicas=2 и сбой ноды

## Условие

Настройте **Kafka cluster** из 3 брокеров и проверьте replication: остановите один брокер и убедитесь, что данные доступны.

## Теория

Топология высокой доступности (HA Cluster):
- Кластер состоит из 3 брокеров: Broker 1, Broker 2, Broker 3.
- Настройки топика:
  - `replication.factor = 3`: каждая партиция имеет 1 лидера и 2 фолловера.
  - `min.insync.replicas = 2`: подтверждение записи требует согласия минимум 2 живых реплик (In-Sync Replicas, ISR).
- **Сценарий аварии:**
  1. Брокер-лидер партиции физически выключается.
  2. Контроллер кластера замечает потерю heartbeat и мгновенно выбирает нового лидера из оставшихся ISR нод.
  3. Продюсеры и консьюмеры переподключаются к новому лидеру за миллисекунды без потери сообщений.

## Решение по шагам

1. Создайте модель кворума из 3 брокеров.
2. Смоделируйте выход из строя брокера-лидера.
3. Проведите процедуру выборов нового лидера (Leader Election).
4. Убедитесь в непрерывности доступности чтения и записи.

## Код решения

**`ha_cluster_replication_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PartitionReplicaState struct {
	LeaderID         int
	ISR              []int
	MinInsyncReplica int
}

func (s *PartitionReplicaState) HandleBrokerCrash(crashedID int) error {
	var newISR []int
	for _, id := range s.ISR {
		if id != crashedID {
			newISR = append(newISR, id)
		}
	}
	s.ISR = newISR

	if len(s.ISR) < s.MinInsyncReplica {
		return fmt.Errorf("нарушен min.insync.replicas: доступно %d, требуется %d", len(s.ISR), s.MinInsyncReplica)
	}

	// Если упал именно лидер, выбираем первого из оставшихся в ISR
	if s.LeaderID == crashedID {
		s.LeaderID = s.ISR[0]
	}

	return nil
}

func TestHAClusterReplication(t *testing.T) {
	state := &PartitionReplicaState{
		LeaderID:         1,
		ISR:              []int{1, 2, 3},
		MinInsyncReplica: 2,
	}

	// Аварийная остановка Broker 1
	err := state.HandleBrokerCrash(1)
	if err != nil {
		t.Fatalf("Кластер должен продолжать работу: %v", err)
	}

	if state.LeaderID != 2 || len(state.ISR) != 2 {
		t.Fatalf("Некорректный новый лидер: leader=%d, isr=%v", state.LeaderID, state.ISR)
	}

	fmt.Println("Кластер Kafka (3 брокера, RF=3, min.isr=2) успешно перенес аварию ноды:")
	fmt.Printf("  • Упавший брокер: #1 (Был лидером)\n")
	fmt.Printf("  • Новый лидер:   #%d (Автоматически выбран из оставшихся нод кворума)\n", state.LeaderID)
	fmt.Printf("  • Текущий ISR:   %v (Условие min.insync.replicas=2 соблюдено!)\n", state.ISR)
	fmt.Println("  • Чтение и запись продюсеров продолжаются без потери данных!")
}
```

## Под капотом

В отличие от классических алгоритмов консенсуса (где требуется большинство \(N/2 + 1\)), Kafka использует модель динамического набора реплик ISR (In-Sync Replicas), что позволяет продолжать работу даже при \(RF=2\) и одном живом брокере.

## Подводные камни

Включать параметр `unclean.leader.election.enable = true`: это разрешает брокерам назначать лидером ноду, отставшую от репликации (Out-of-Sync), что приводит к безвозвратной потере закоммиченных данных.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если в кластере из 3 нод с min.insync.replicas=2 упадут сразу два брокера?»
**Ответ:** Запись продюсеров с `acks=all` будет заблокирована с ошибкой `NotEnoughReplicasException`, так как в живых осталась только 1 нода. При этом консьюмеры смогут продолжать читать уже зафиксированные исторические данные с оставшегося единственного брокера (High Read Availability при деградации Write Availability по теореме CAP).
