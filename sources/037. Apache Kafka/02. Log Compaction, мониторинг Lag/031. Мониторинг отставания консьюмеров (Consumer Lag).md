# Мониторинг отставания консьюмеров (Consumer Lag): Reader.Stats, расчет дельты и экспорт метрик

## Условие

Реализуйте **consumer lag monitoring**: используйте `Reader.Stats()` или Kafka Admin API для отслеживания, насколько consumer отстает от producer.

## Теория

Consumer Lag — главная метрика здоровья Kafka:
- Формула отставания:
  $$\text{Lag} = \text{LogEndOffset (LEO)} - \text{CurrentConsumerOffset}.$$
- Если \(\text{Lag} = 0\): консьюмер успевает в реальном времени.
- Если \(\text{Lag}\) монотонно растет:
  - Продюсер пишет быстрее, чем консьюмер успевает обрабатывать.
  - Воркер завис или уперся в CPU/IOPS базы данных.
- Экспорт метрики в Prometheus позволяет настроить автоскейлинг подов в Kubernetes (KEDA) и алерты дежурным инженерам.

## Решение по шагам

1. Создайте структуру метрик отставания консьюмера.
2. Смоделируйте получение LEO брокера и смещения консьюмера.
3. Рассчитайте дельту (Lag).
4. Реализуйте проверку превышения критического порога.

## Код решения

**`consumer_lag_monitoring_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type PartitionLag struct {
	Partition int
	LEO       int64 // Log End Offset
	Current   int64 // Current Offset
}

func (p PartitionLag) Lag() int64 {
	if p.LEO < p.Current {
		return 0
	}
	return p.LEO - p.Current
}

func TestConsumerLagMonitoring(t *testing.T) {
	metrics := []PartitionLag{
		{Partition: 0, LEO: 15000, Current: 15000}, // Lag = 0 (норма)
		{Partition: 1, LEO: 20400, Current: 20380}, // Lag = 20 (небольшое отставание)
		{Partition: 2, LEO: 89000, Current: 74000}, // Lag = 15000 (Критическое отставание!)
	}

	var totalLag int64
	var criticalAlert bool

	for _, m := range metrics {
		lag := m.Lag()
		totalLag += lag
		if lag > 10000 {
			criticalAlert = true
		}
		fmt.Printf("  • Партиция #%d: LEO=%d, Current=%d -> Lag=%d сообщений\n",
			m.Partition, m.LEO, m.Current, lag)
	}

	if !criticalAlert || totalLag != 15020 {
		t.Fatalf("Ошибка расчета Lag: total=%d, alert=%v", totalLag, criticalAlert)
	}

	fmt.Println("Мониторинг Consumer Lag успешно зафиксировал аномалию:")
	fmt.Printf("  • Суммарный лаг группы: %d сообщений\n", totalLag)
	fmt.Println("  • 🚨 ALERT: Партиция #2 отстает на 15 000 сообщений! Срабатывает автомасштабирование KEDA.")
}
```

## Под капотом

В проде для централизованного мониторинга лага используют специализированные экспортеры, такие как `kafka-exporter` или `burrow`, которые запрашивают метаданные оффсетов напрямую у брокеров без нагрузки на сами воркеры.

## Подводные камни

Мониторить только средний Lag по группе: если одна «ядовитая» партиция зависла, средний лаг может казаться нормальным, в то время как события одного клиента полностью заблокированы.

## На собеседовании

**Вопрос с собеседования:** «Как настроить автомасштабирование (HPA) подов в Kubernetes по метрике Consumer Lag?»
**Ответ:** С помощью KEDA (Kubernetes Event-driven Autoscaling). KEDA периодически опрашивает Kafka о суммарном лаге Consumer Group и, если лаг превышает целевое значение (например, 1000 сообщений на под), автоматически увеличивает количество реплик Deployment вплоть до количества партиций в топике.
