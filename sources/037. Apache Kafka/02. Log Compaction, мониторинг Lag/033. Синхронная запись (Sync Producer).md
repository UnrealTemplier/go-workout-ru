# Синхронная запись (Sync Producer): RequiredAcks RequireAll, падение лидера и перехват таймаутов

## Условие

**[Синхронная запись (Sync Producer)]**: Используй `kafka.Writer` с `RequiredAcks: kafka.RequireAll`. Сымитируй падение брокера. Поймай ошибку таймаута на стороне продюсера.

## Теория

Гарантия долговечности через RequiredAcks RequireAll:
- Опции подтверждения продюсера:
  - `acks = 0`: продюсер не ждет ответа (Fire-and-Forget). Риск потери данных максимален.
  - `acks = 1`: продюсер ждет записи только на лидер-брокер. Если лидер упадет до репликации \(\to\) данные потеряны.
  - `acks = -1` (`RequireAll` / `all`): продюсер ждет записи от лидера и ВСЕХ реплик из списка `min.insync.replicas`.
- Если брокер упал или в кворуме меньше `min.insync.replicas`:
  - Продюсер получает таймаут или ошибку `NotEnoughReplicasException`.
  - Синхронный код в Go немедленно видит сетевую ошибку и возвращает 503 клиенту.

## Решение по шагам

1. Создайте структуру продюсера с `RequiredAcks: RequireAll`.
2. Смоделируйте отключение лидер-брокера.
3. Вызовите синхронную запись сообщения с контекстным таймаутом.
4. Перехватите и обработайте ошибку `context.DeadlineExceeded`.

## Код решения

**`sync_producer_acks_all_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type MockSyncWriter struct {
	isLeaderAlive bool
}

func (w *MockSyncWriter) WriteSync(ctx context.Context, msg string) error {
	select {
	case <-ctx.Done():
		return ctx.Err()
	default:
	}

	if !w.isLeaderAlive {
		// Имитируем зависание/таймаут при падении брокера
		select {
		case <-time.After(50 * time.Millisecond):
			return fmt.Errorf("leader broker unreachable: timeout waiting for ISR acks")
		case <-ctx.Done():
			return ctx.Err()
		}
	}

	return nil
}

func TestSyncProducerAcksAll(t *testing.T) {
	writer := &MockSyncWriter{isLeaderAlive: false}

	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel()

	err := writer.WriteSync(ctx, "Критическая финансовая проводка")

	if err == nil {
		t.Fatal("Синхронная запись при мертвом брокере обязана вернуть ошибку")
	}

	fmt.Println("Синхронный продюсер (RequiredAcks: RequireAll) успешно перехватил сбой:")
	fmt.Printf("  • Ошибка записи: %v\n", err)
	fmt.Println("  • Сообщение не потеряно молча: Go-сервис получил ошибку и вернул 503 клиенту!")
}
```

ℹ️ Синхронная запись с RequireAll и перехватом таймаутов недоступности ISR реплик

## Под капотом

Связка `acks=all` и `min.insync.replicas=2` при факторе репликации \(RF=3\) является золотым стандартом надежности в финансовом секторе (Zero Data Loss Architecture).

## Подводные камни

Использовать `acks=all` с `min.insync.replicas=1`: при падении лидера данные будут потеряны, так как брокер считал достаточным подтверждение только от одной ноды.

## На собеседовании

**Вопрос с собеседования:** «Каковы накладные расходы на задержку (Latency) при переходе с acks=1 на acks=all?»
**Ответ:** Задержка увеличивается на время одного сетевого round-trip между брокерами кластера (обычно 0.5–2 мс внутри одного дата-центра), пока реплики-фолловеры скачивают и подтверждают пакет. В современных сетях это ничтожная плата за 100% гарантию сохранности данных.
