# Управление смещениями (Offsets): различие автономного Reader и Consumer Group, стратегия LastOffset

## Условие

**Оффсеты (Offsets)**: Перезапусти консьюмера из упр. 498. Обрати внимание, что он снова читает всё с самого начала (если не задан Group ID). Настрой Reader так, чтобы он читал только *новые* сообщения, добавленные после его старта (`kafka.LastOffset`).

## Теория

Различие между автономным Reader и Consumer Group:
- **Standalone Reader (без `GroupID`):**
  - Не координируется брокером и не сохраняет оффсеты в топике `__consumer_offsets`.
  - При каждом новом запуске позиция чтения определяется параметром `StartOffset`:
    - `StartOffset: kafka.FirstOffset` \(\to\) всегда начинает с нуля.
    - `StartOffset: kafka.LastOffset` \(\to\) читает только сообщения, опубликованные СТРОГО ПОСЛЕ запуска.
- **Consumer Group (с `GroupID`):**
  - Брокер сохраняет прогресс чтения группы на постоянной основе. При рестарте воркер продолжает с последней закоммиченной позиции.

## Решение по шагам

1. Создайте симулятор лога с существующими сообщениями.
2. Инициализируйте Reader в режиме `LastOffset`.
3. Опубликуйте новое сообщение после инициализации.
4. Убедитесь, что старые сообщения пропущены, а новое прочитано.

## Код решения

**`last_offset_strategy_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MockPartitionLog struct {
	records []string
}

func (l *MockPartitionLog) Append(msg string) int {
	l.records = append(l.records, msg)
	return len(l.records) - 1
}

type StandaloneReader struct {
	log *MockPartitionLog
	pos int
}

func NewStandaloneLastOffsetReader(log *MockPartitionLog) *StandaloneReader {
	// Начинаем с конца текущего лога
	return &StandaloneReader{
		log: log,
		pos: len(log.records),
	}
}

func (r *StandaloneReader) ReadAvailable() []string {
	if r.pos >= len(r.log.records) {
		return nil
	}
	msgs := r.log.records[r.pos:]
	r.pos = len(r.log.records)
	return msgs
}

func TestLastOffsetStrategy(t *testing.T) {
	log := &MockPartitionLog{
		records: []string{"Старое сообщение 1", "Старое сообщение 2"},
	}

	// Запускаем ридер с LastOffset
	reader := NewStandaloneLastOffsetReader(log)

	// Старые сообщения не читаются
	oldMsgs := reader.ReadAvailable()
	if len(oldMsgs) != 0 {
		t.Fatalf("Старые сообщения должны игнорироваться: %v", oldMsgs)
	}

	// Поступает новое сообщение
	log.Append("Свежее сообщение 3")

	newMsgs := reader.ReadAvailable()
	if len(newMsgs) != 1 || newMsgs[0] != "Свежее сообщение 3" {
		t.Fatalf("Должно быть прочитано только новое сообщение: %v", newMsgs)
	}

	fmt.Println("Стратегия kafka.LastOffset успешно проверена:")
	fmt.Printf("  • Исторические сообщения (Offset 0..1): пропущены\n")
	fmt.Printf("  • Новое сообщение после старта:         «%s» прочитано!\n", newMsgs[0])
}
```

ℹ️ Инициализация консьюмера со стратегией LastOffset для чтения только новых данных

## Под капотом

При подключении с `LastOffset` клиент отправляет брокеру RPC-запрос `ListOffsets` с таймкодом `-1` (`LatestSpec`). Брокер возвращает текущий LEO (Log End Offset), и ридер начинает опрос именно с этого значения.

## Подводные камни

Использовать `LastOffset` в сервисах обработки заказов: при плановом рестарте сервиса все заказы, поступившие за время перезапуска контейнера, будут безвозвратно утеряны! В бизнес-сервисах всегда используют Consumer Groups.

## На собеседовании

**Вопрос с собеседования:** «Для каких сценариев оправдано использование Standalone Reader с LastOffset?»
**Ответ:** Для потоков мониторинга в реальном времени (Real-Time Metrics Dashboards), систем отслеживания логов (`tail -f`) или оповещений об оперативной нагрузке, где исторические данные не имеют ценности, а важен только текущий срез телеметрии.
