# Сжатые топики (Compacted Topics): cleanup.policy compact, модель Key-Value и удаление через Tombstone

## Условие

Создайте **compacted topic** (`cleanup.policy: compact`): Kafka будет хранить только последнее значение для каждого ключа (как Key-Value store).

## Теория

Архитектура Log Compaction в Kafka:
- Стандартный топик (`cleanup.policy = delete`):
  - Старые сообщения удаляются по времени (`retention.ms`) или размеру (`retention.bytes`).
- Сжатый топик (`cleanup.policy = compact`):
  - Kafka гарантирует сохранение **как минимум последнего актуального состояния** для каждого ключа `Key`.
  - Фоновый процесс Log Cleaner сканирует лог и удаляет устаревшие записи с тем же ключом.
  - Топик превращается в персистентную базу данных типа Key-Value!
- **Удаление записи (Tombstone):**
  - Отправка сообщения с существующим ключом `Key` и телом `Value: nil`.
  - Сигнализирует консьюмерам и брокеру об удалении сущности.

## Решение по шагам

1. Создайте модель сжатого топика с ключами пользователей.
2. Смоделируйте обновление профилей пользователей.
3. Отправьте сообщение-маркер Tombstone (`Value: nil`) для удаления.
4. Проверьте результат компактизации.

## Код решения

**`compacted_topic_kv_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type CompactedKVLog struct {
	state map[string]*string // Key -> Value (nil = Tombstone)
}

func NewCompactedLog() *CompactedKVLog {
	return &CompactedKVLog{state: make(map[string]*string)}
}

func (l *CompactedKVLog) Apply(key string, val *string) {
	if val == nil {
		// Tombstone: удаление ключа из актуального состояния
		delete(l.state, key)
		return
	}
	l.state[key] = val
}

func TestCompactedTopicKV(t *testing.T) {
	log := NewCompactedLog()

	v1 := "Иван (Москва)"
	v2 := "Иван (Санкт-Петербург)" // Обновление адреса
	vUser2 := "Мария (Казань)"

	// 1. Запись событий
	log.Apply("user_101", &v1)
	log.Apply("user_102", &vUser2)
	log.Apply("user_101", &v2) // перезапись последнего состояния user_101

	if *log.state["user_101"] != "Иван (Санкт-Петербург)" {
		t.Fatalf("Актуальное значение должно быть v2: %s", *log.state["user_101"])
	}

	// 2. Отправка Tombstone (удаление user_102)
	log.Apply("user_102", nil)

	if _, exists := log.state["user_102"]; exists {
		t.Fatal("user_102 должен быть удален по Tombstone")
	}

	fmt.Println("Log Compaction (cleanup.policy: compact) успешно протестирован:")
	fmt.Printf("  • user_101: сохранено последнее актуальное значение: «%s»\n", *log.state["user_101"])
	fmt.Printf("  • user_102: удален через Tombstone (Value: nil)\n")
}
```

## Под капотом

Log Cleaner делит сегменты на Clean (уже сжатые) и Dirty (новые записи). Поток компактизации строит SkimpyOffsetMap в оперативной памяти и переписывает сегменты, отбрасывая дублирующиеся ключи.

## Подводные камни

Отправлять сообщения в compacted топик без ключа (`Key: nil`): брокер не сможет скомпоновать записи без ключа, и топик будет бесконечно расти.

## На собеседовании

**Вопрос с собеседования:** «Что такое Tombstone в Kafka и почему он не удаляется с диска немедленно?»
**Ответ:** Tombstone — это запись с существующим ключом и `null/nil` полезной нагрузкой. Брокер обязан сохранять Tombstone на диске в течение периода `delete.retention.ms` (по умолчанию 24 часа), чтобы все оффлайн-консьюмеры успели прочитать этот маркер и синхронно удалить сущность из своих локальных кэшей и баз данных.
