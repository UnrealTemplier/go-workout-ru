# Управление обратным давлением (Backpressure): адаптивная регулировка MaxBytes и MaxWait в Reader

## Условие

Реализуйте **backpressure**: если consumer не успевает обрабатывать, уменьшайте `MaxBytes` или увеличивайте `MaxWait` в reader.

## Теория

Механика Backpressure на клиенте Kafka:
- Проблема: консьюмер вычитал из сети пачку в 50 МБ, переполнил внутреннюю очередь в памяти и упал по OOM.
- **Способы контроля обратного давления в kafka.Reader:**
  - `MinBytes: 1e3` (1 КБ): минимальный объем байтов, который брокер ждет перед ответом.
  - `MaxBytes: 1e6` (1 МБ): ограничение максимального объема данных за один сетевой poll.
  - `MaxWait: 500ms`: максимальное время ожидания накопления `MinBytes`.
- При деградации производительности БД или пула горутин консьюмер адаптивно снижает `MaxBytes` или приостанавливает вычитку (Pause/Resume).

## Решение по шагам

1. Создайте структуру адаптивного контроллера скорости чтения.
2. Смоделируйте рост задержки обработки в воркере.
3. Продемонстрируйте автоматическое снижение `MaxBytes` для защиты от OOM.
4. Восстановите исходные лимиты при спаде нагрузки.

## Код решения

**`adaptive_backpressure_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DynamicBackpressureReader struct {
	CurrentMaxBytes int
	CurrentMaxWait  time.Duration
}

func (r *DynamicBackpressureReader) AdjustLoad(workerQueueLen int) {
	if workerQueueLen > 100 {
		// Высокая нагрузка: уменьшаем размер порции и увеличиваем паузу
		r.CurrentMaxBytes = 128 * 1024 // 128 KB
		r.CurrentMaxWait = 2 * time.Second
	} else {
		// Нормальное состояние: читаем на максимальной скорости
		r.CurrentMaxBytes = 10 * 1024 * 1024 // 10 MB
		r.CurrentMaxWait = 250 * time.Millisecond
	}
}

func TestAdaptiveBackpressure(t *testing.T) {
	reader := &DynamicBackpressureReader{
		CurrentMaxBytes: 10 * 1024 * 1024,
		CurrentMaxWait:  250 * time.Millisecond,
	}

	// 1. Очередь воркера переполнена (150 задач in-flight)
	reader.AdjustLoad(150)
	if reader.CurrentMaxBytes != 128*1024 || reader.CurrentMaxWait != 2*time.Second {
		t.Fatalf("Backpressure не активирован: %+v", reader)
	}

	// 2. Очередь разгрузилась
	reader.AdjustLoad(10)
	if reader.CurrentMaxBytes != 10*1024*1024 {
		t.Fatalf("Лимиты не восстановлены: %+v", reader)
	}

	fmt.Println("Адаптивный механизм Backpressure успешно протестирован:")
	fmt.Printf("  • Под нагрузкой: MaxBytes снижен до 128 КБ, MaxWait увеличен до 2с (OOM предотвращен!)\n")
	fmt.Printf("  • В норме:       MaxBytes восстановлен до 10 МБ, опрос каждые 250 мс\n")
}
```

## Под капотом

В отличие от Push-модели брокеров (где сервер «заливает» сообщения в клиента), Kafka использует Pull-модель: клиент физически запрашивает ровно столько байтов (`MaxBytes`), сколько готов вместить в буфер.

## Подводные камни

Ставить `MaxWait` больше, чем `session.timeout.ms`: брокер разорвет сессию консьюмера по таймауту, решив, что воркер завис.

## На собеседовании

**Вопрос с собеседования:** «В чем главное преимущество Pull-модели Kafka перед Push-моделью RabbitMQ при защите от перегрузок?»
**Ответ:** В Pull-модели консьюмер полностью контролирует темп вычитки: если воркер занят тяжелой обработкой, он просто откладывает следующий опрос (Fetch). Брокер никогда не переполнит память медленного клиента. В Push-модели без жесткого Prefetch брокер может завалить воркера миллионом сообщений и уронить процесс в Out of Memory.
