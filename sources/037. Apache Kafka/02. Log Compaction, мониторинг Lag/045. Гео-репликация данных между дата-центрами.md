# Гео-репликация данных между дата-центрами: Kafka MirrorMaker 2 и сохранение оффсетов

## Условие

Используйте **Kafka MirrorMaker 2** для репликации данных между дата-центрами.

## Теория

Архитектура MirrorMaker 2 (MM2) в распределенных инсталляциях:
- Задача: репликация топиков между независимыми дата-центрами (например, `dc-spb` и `dc-msk`).
- Основан на фреймворке Kafka Connect.
- **Ключевые фичи MM2:**
  - Предотвращение циклических репликаций: топики автоматически переименовываются с префиксом источника, например `dc-spb.orders`.
  - Трансляция смещений (Offset Sync): консьюмер может переключиться на резервный ДЦ (Failover) и продолжить чтение с эквивалентной позиции благодаря топику `checkpoints`.
  - Динамическое обнаружение новых топиков по регулярным выражениям (`topics = .*orders.*`).

## Решение по шагам

1. Создайте структуру конфигурации репликации MirrorMaker 2.
2. Задайте параметры кластеров источника (`dc-spb`) и приемника (`dc-msk`).
3. Смоделируйте трансляцию имен топиков и контрольных точек оффсетов.
4. Проверьте правила защиты от циклической репликации.

## Код решения

**`mirrormaker2_config_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type MM2ClusterConfig struct {
	SourceCluster string
	TargetCluster string
	TopicPattern  string
	SyncOffsets   bool
}

func (c MM2ClusterConfig) RemoteTopicName(localTopic string) string {
	return fmt.Sprintf("%s.%s", c.SourceCluster, localTopic)
}

func TestMirrorMaker2Config(t *testing.T) {
	cfg := MM2ClusterConfig{
		SourceCluster: "dc-spb",
		TargetCluster: "dc-msk",
		TopicPattern:  "payments.*",
		SyncOffsets:   true,
	}

	remoteTopic := cfg.RemoteTopicName("payments.checkout")

	if !strings.HasPrefix(remoteTopic, "dc-spb.") || !cfg.SyncOffsets {
		t.Fatalf("Некорректная конфигурация MM2: %+v", cfg)
	}

	fmt.Println("Kafka MirrorMaker 2 (MM2) гео-репликация настроена:")
	fmt.Printf("  • Источник:             %s -> Приемник: %s\n", cfg.SourceCluster, cfg.TargetCluster)
	fmt.Printf("  • Шаблон топиков:       %s\n", cfg.TopicPattern)
	fmt.Printf("  • Имя реплики в целевом: %s (Защита от Split-Brain и циклов!)\n", remoteTopic)
	fmt.Printf("  • Синхронизация оффсетов: включена (Бесшовный Disaster Recovery Failover)\n")
}
```

## Под капотом

MirrorMaker 2 ведет служебный топик `heartbeats` для мониторинга сетевой связности между кластерами и топик `checkpoints` для сопоставления оффсетов между исходным и удаленным логом.

## Подводные камни

Запускать устаревший MirrorMaker 1: старая версия не синхронизировала смещения консьюмеров, и при аварийном переключении в резервный дата-центр консьюмеры читали топики заново, порождая миллионы дубликатов.

## На собеседовании

**Вопрос с собеседования:** «Почему распределенный кластер Kafka не рекомендуется растягивать между городами (Stretched Cluster) вместо использования MirrorMaker 2?»
**Ответ:** Задержка междугородной оптики (RTT 15–30 мс). В растянутом кластере каждая синхронная запись с `acks=all` будет ждать подтверждения по междугородней сети, увеличивая Latency в 30 раз. MirrorMaker 2 реплицирует данные асинхронно, изолируя продюсеры от задержек удаленного ДЦ.
