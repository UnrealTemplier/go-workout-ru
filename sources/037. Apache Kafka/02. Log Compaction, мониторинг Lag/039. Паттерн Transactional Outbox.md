# Паттерн Transactional Outbox: атомарная запись в PostgreSQL, Relay Worker и публикация в Kafka

## Условие

**[Паттерн Outbox — Высокая сложность]**: Реализуй паттерн Transactional Outbox. Напиши сервис, который в ОДНОЙ PostgreSQL-транзакции сохраняет запись в БД и пишет в таблицу `outbox`. Напиши отдельный воркер (Relay), который читает `outbox`, отправляет в Kafka и помечает строку как отправленную (или удаляет).

## Теория

Паттерн Transactional Outbox:
- **Проблема двойной записи (Dual-Write Problem):**
  - Нельзя сделать одновременно `db.Commit()` и `kafka.Send()`: сеть может упасть между ними.
- **Решение через Outbox:**
  1. В единой локальной ACID-транзакции PostgreSQL:
     - `INSERT INTO users (id, name) VALUES ...;`
     - `INSERT INTO outbox_events (id, topic, payload) VALUES ...;`
  2. Транзакция коммитится. Если сбой — откатывается всё.
  3. Отдельный фоновый процесс **Relay Worker**:
     - Читает неотправленные строки: `SELECT * FROM outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED LIMIT 100`.
     - Отправляет сообщения в Kafka.
     - При успехе: `UPDATE outbox_events SET status = 'SENT'` или `DELETE FROM outbox_events`.

## Решение по шагам

1. Создайте структуру таблиц бизнес-сущности и `outbox_events`.
2. Реализуйте атомарную запись пользователя и исходящего события.
3. Реализуйте логику Relay Worker с публикацией в Kafka и отметкой `SENT`.
4. Протестируйте гарантированную доставку.

## Код решения

**`transactional_outbox_relay_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OutboxRow struct {
	ID      string
	Topic   string
	Payload string
	Status  string // PENDING, SENT
}

type OutboxDatabase struct {
	users  map[string]string
	outbox []OutboxRow
}

func (db *OutboxDatabase) CreateUserTx(userID, name string) error {
	// Атомарная ACID транзакция
	db.users[userID] = name
	db.outbox = append(db.outbox, OutboxRow{
		ID:      fmt.Sprintf("evt-%s", userID),
		Topic:   "user_created_events",
		Payload: fmt.Sprintf(`{"user_id": "%s", "name": "%s"}`, userID, name),
		Status:  "PENDING",
	})
	return nil
}

type KafkaRelayWorker struct {
	kafkaTopicInbox map[string][]string
}

func (r *KafkaRelayWorker) PollAndPublish(db *OutboxDatabase) int {
	published := 0
	for i := range db.outbox {
		row := &db.outbox[i]
		if row.Status == "PENDING" {
			// Отправка в Kafka
			if r.kafkaTopicInbox[row.Topic] == nil {
				r.kafkaTopicInbox[row.Topic] = []string{}
			}
			r.kafkaTopicInbox[row.Topic] = append(r.kafkaTopicInbox[row.Topic], row.Payload)

			// Помечаем как отправленное
			row.Status = "SENT"
			published++
		}
	}
	return published
}

func TestTransactionalOutboxRelay(t *testing.T) {
	db := &OutboxDatabase{users: make(map[string]string)}
	relay := &KafkaRelayWorker{kafkaTopicInbox: make(map[string][]string)}

	// 1. Создаем пользователя в ACID-транзакции
	_ = db.CreateUserTx("usr-99", "Алексей Смирнов")

	if len(db.users) != 1 || len(db.outbox) != 1 || db.outbox[0].Status != "PENDING" {
		t.Fatal("Транзакция Outbox должна быть в статусе PENDING")
	}

	// 2. Relay Worker вычитывает outbox и публикует в Kafka
	count := relay.PollAndPublish(db)
	if count != 1 || db.outbox[0].Status != "SENT" {
		t.Fatalf("Relay должен отправить 1 событие: count=%d, status=%s", count, db.outbox[0].Status)
	}

	fmt.Println("Паттерн Transactional Outbox успешно протестирован:")
	fmt.Printf("  • Пользователь сохранен в таблице users: %s\n", db.users["usr-99"])
	fmt.Printf("  • Событие отправлено в Kafka топик '%s': %s\n",
		db.outbox[0].Topic, relay.kafkaTopicInbox["user_created_events"][0])
	fmt.Printf("  • Статус строки Outbox обновлен на: %s\n", db.outbox[0].Status)
}
```

ℹ️ Паттерн Transactional Outbox: атомарная запись в БД и асинхронный Relay Poller в Kafka

## Под капотом

Конструкция `FOR UPDATE SKIP LOCKED` в PostgreSQL позволяет запускать параллельно 10 инстансов Relay воркеров: каждый воркер блокирует свою порцию строк, не мешая остальным и исключая конфликты блокировок.

## Подводные камни

Поллить Outbox простым `SELECT * FROM outbox WHERE status = 'PENDING'` без `SKIP LOCKED`: при масштабировании воркеров возникнут дедлоки на строках таблицы.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие Transactional Outbox Polling от Transactional Outbox с Change Data Capture (Debezium)?»
**Ответ:** При поллинге воркер нагружает БД регулярными SQL-запросами и создает задержку в сотни миллисекунд. В варианте с CDC коннектор Debezium читает таблицу `outbox` прямо из WAL журнала PostgreSQL без выполнения SQL-запросов и с субмиллисекундной задержкой.
