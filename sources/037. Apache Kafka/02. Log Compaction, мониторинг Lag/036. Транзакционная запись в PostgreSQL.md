# Транзакционная запись в PostgreSQL и коммит смещения: паттерн At-Least-Once и симуляция сбоя

## Условие

Вручную коммитите оффсеты после успешной обработки сообщения и записи результата в БД (паттерн «at-least-once»). Симулируйте сбой и проверьте, что сообщение переобрабатывается.

## Теория

Инженерия надежного консьюмера (PostgreSQL + Kafka):
- Порядок вызовов в цикле:
  1. `msg, err := reader.FetchMessage(ctx)`
  2. `tx, err := db.BeginTx(ctx, nil)`
  3. `_, err = tx.Exec("INSERT INTO orders ...", ...)`
  4. `err = tx.Commit()` \(\to\) критическая точка фиксации данных!
  5. `err = reader.CommitMessages(ctx, msg)` \(\to\) фиксация смещения в Kafka.
- Если сбой произойдет до шага 4 \(\to\) откат транзакции БД, оффсет не закоммичен, сообщение будет перечитано заново.

## Решение по шагам

1. Создайте модель транзакционной базы данных.
2. Смоделируйте сбой коммита транзакции в БД.
3. Убедитесь, что оффсет в Kafka не сместился.
4. Продемонстрируйте успешную повторную обработку.

## Код решения

**`db_kafka_at_least_once_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type MockDBTx struct {
	committed bool
}

type KafkaOffsetManager struct {
	committedOffset int64
}

func ProcessOrderWithDB(msgOffset int64, failDB bool, db *MockDBTx, km *KafkaOffsetManager) error {
	// 1. Запись в БД
	if failDB {
		return errors.New("ошибка блокировки строки в PostgreSQL")
	}
	db.committed = true

	// 2. Коммит оффсета строго после успеха БД
	km.committedOffset = msgOffset
	return nil
}

func TestDBKafkaAtLeastOnce(t *testing.T) {
	db := &MockDBTx{}
	km := &KafkaOffsetManager{committedOffset: 99}

	// Попытка 1: сбой БД
	err1 := ProcessOrderWithDB(100, true, db, km)
	if err1 == nil || km.committedOffset != 99 {
		t.Fatalf("При сбое БД оффсет не должен меняться: offset=%d", km.committedOffset)
	}

	// Попытка 2: повторное чтение после рестарта
	err2 := ProcessOrderWithDB(100, false, db, km)
	if err2 != nil || km.committedOffset != 100 || !db.committed {
		t.Fatalf("Повторная обработка должна завершиться успехом: err=%v, offset=%d", err2, km.committedOffset)
	}

	fmt.Println("Сквозной цикл БД + Kafka (At-Least-Once) успешно протестирован:")
	fmt.Printf("  • Попытка 1: Сбой БД перехвачен, смещение осталось %d\n", 99)
	fmt.Printf("  • Попытка 2: Успех в БД, новое смещение %d зафиксировано в Kafka!\n", km.committedOffset)
}
```

## Под капотом

Поскольку между коммитом в PostgreSQL и вызовом `CommitMessages` в Kafka есть временной зазор, в редких случаях сервер может упасть между ними. Поэтому обработчик в БД обязан быть идемпотентным (`ON CONFLICT DO NOTHING`).

## Подводные камни

Коммитить смещение Kafka ДО фиксации транзакции в БД: при падении базы данных сообщение окажется закоммиченным в Kafka и будет безвозвратно потеряно.

## На собеседовании

**Вопрос с собеседования:** «Как называется проблема несогласованности коммита двух распределенных систем (БД и Kafka)?»
**Ответ:** Это классическая проблема распределенного консенсуса Dual-Write Problem. Для ее полного устранения в BigTech применяют паттерн Transactional Outbox: сервис пишет ТОЛЬКО в PostgreSQL, а отправку в Kafka гарантирует отдельный процесс чтения журнала WAL (Debezium CDC).
