# Идемпотентный консьюмер в SQL: таблица processed_messages, первичный ключ и Exactly-Once семантика

## Условие

Реализуйте идемпотентного консюмера: добавьте в БД таблицу обработанных message_id, перед обработкой проверяйте дубликат. Так добейтесь семантики exactly-once (со стороны консюмера).

## Теория

Идемпотентный консьюмер через реляционную таблицу:
- Схема таблицы в PostgreSQL:
  ```sql
  CREATE TABLE processed_messages (
      message_id VARCHAR(64) PRIMARY KEY,
      processed_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
  );
  ```
- Каждое сообщение Kafka содержит глобально уникальный `Message-ID` (UUID v4) в заголовках.
- При обработке в единой транзакции выполняется:
  ```sql
  INSERT INTO processed_messages (message_id) VALUES ($1) ON CONFLICT DO NOTHING;
  ```
- Если количество затронутых строк `RowsAffected() == 0`: сообщение УЖЕ обрабатывалось ранее.
- Воркер просто подтверждает оффсет в Kafka и не выполняет повторное списание средств.

## Решение по шагам

1. Создайте структуру обработчика с проверкой уникального идентификатора.
2. Смоделируйте первичное поступление транзакции.
3. Смоделируйте дублирующую доставку того же события.
4. Убедитесь, что дубликат отфильтрован без изменения бизнес-данных.

## Код решения

**`sql_idempotent_consumer_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ProcessedMessageStore struct {
	seenKeys map[string]bool
	totalOps int
}

func (s *ProcessedMessageStore) HandleIdempotent(msgID string, businessLogic func()) (executed bool) {
	// Атомарная вставка с контролем уникальности PRIMARY KEY
	if s.seenKeys[msgID] {
		return false // Дубликат: пропускаем вызов бизнес-логики
	}

	s.seenKeys[msgID] = true
	businessLogic()
	s.totalOps++
	return true
}

func TestSQLIdempotentConsumer(t *testing.T) {
	store := &ProcessedMessageStore{seenKeys: make(map[string]bool)}

	customerBalance := 1000
	withdrawAction := func() {
		customerBalance -= 300
	}

	msgUUID := "msg-uuid-abc-12345"

	// 1. Первая доставка
	ok1 := store.HandleIdempotent(msgUUID, withdrawAction)
	// 2. Дубликат из-за ребалансировки
	ok2 := store.HandleIdempotent(msgUUID, withdrawAction)

	if !ok1 || ok2 || customerBalance != 700 || store.totalOps != 1 {
		t.Fatalf("Нарушена идемпотентность: ok1=%v, ok2=%v, bal=%d, ops=%d",
			ok1, ok2, customerBalance, store.totalOps)
	}

	fmt.Println("Идемпотентный консьюмер на базе SQL таблицы подтвердил Exactly-Once:")
	fmt.Printf("  • Первичная обработка: успешно выполнена (Баланс: %d руб)\n", customerBalance)
	fmt.Printf("  • Повторный дубликат:  отсечен первичным ключом processed_messages (Баланс: %d руб)\n", customerBalance)
}
```

ℹ️ Достижение Exactly-Once семантики консьюмера через таблицу обработанных сообщений

## Под капотом

Использование общего соединения и транзакции для бизнес-таблицы и `processed_messages` связывает факт обработки сообщения и изменение сущности единым неделимым коммитом.

## Подводные камни

Хранить `processed_messages` во временной памяти (in-memory map) сервиса: при перезапуске пода карта очистится, и при ребалансировке все дубликаты выполнятся заново.

## На собеседовании

**Вопрос с собеседования:** «Как очищать таблицу processed_messages при миллиардах сообщений в месяц?»
**Ответ:** Партиционированием таблицы по дате (`PARTITION BY RANGE (processed_at)`). Создаются партиции по дням, и специальный Cron-джоб удаляет старые партиции мгновенной командой `DROP TABLE processed_messages_y2026_m08` без нагрузки на автовакуум PostgreSQL.
