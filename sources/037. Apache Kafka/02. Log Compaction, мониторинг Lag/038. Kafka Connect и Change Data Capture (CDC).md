# Kafka Connect и Change Data Capture (CDC): интеграция Debezium, PostgreSQL WAL и публикация изменений

## Условие

Создайте **Kafka Connect** source connector для CDC: читайте изменения из PostgreSQL через Debezium и публикуйте в Kafka topic.

## Теория

Архитектура Change Data Capture (CDC) с Debezium:
- Вместо медленных и тяжелых опросов базы `SELECT * FROM orders WHERE updated_at > ...`:
  - Debezium подключается к PostgreSQL как клиент логической репликации (плагин `pgoutput` или `decoderbufs`).
  - Читает журнал упреждающей записи Write-Ahead Log (WAL) на лету.
  - Каждая операция (`INSERT`, `UPDATE`, `DELETE`) мгновенно превращается в структурированное событие JSON/Avro в топике `postgres.public.orders`.
- **Преимущества:** нулевая нагрузка на базу данных, невозможность пропустить изменение, захват состояния «до» и «после».

## Решение по шагам

1. Создайте структуру конфигурации Debezium Source Connector.
2. Смоделируйте захват события изменения строки из PostgreSQL WAL.
3. Сформируйте событие с полями `before`, `after`, `op`.
4. Проверьте валидацию структуры CDC сообщения.

## Код решения

**`debezium_cdc_connector_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type DebeziumPayload struct {
	Before map[string]interface{} `json:"before"`
	After  map[string]interface{} `json:"after"`
	Op     string                 `json:"op"` // c = create, u = update, d = delete
	TsMs   int64                  `json:"ts_ms"`
}

type DebeziumCDCEvent struct {
	Schema  map[string]interface{} `json:"schema"`
	Payload DebeziumPayload        `json:"payload"`
}

func TestDebeziumCDCConnector(t *testing.T) {
	// Имитация события обновления статуса заказа в PostgreSQL
	cdcJSON := `{
		"payload": {
			"op": "u",
			"ts_ms": 1772658000000,
			"before": {"id": 8801, "status": "PENDING"},
			"after":  {"id": 8801, "status": "PAID"}
		}
	}`

	var ev DebeziumCDCEvent
	err := json.Unmarshal([]byte(cdcJSON), &ev)
	if err != nil {
		t.Fatalf("Ошибка парсинга Debezium CDC: %v", err)
	}

	if ev.Payload.Op != "u" || ev.Payload.After["status"] != "PAID" {
		t.Fatalf("Некорректные данные payload: %+v", ev.Payload)
	}

	fmt.Println("Debezium CDC Source Connector успешно зафиксировал изменение из PostgreSQL WAL:")
	fmt.Printf("  • Тип операции:  UPDATE (op: '%s')\n", ev.Payload.Op)
	fmt.Printf("  • Было в БД:     %v\n", ev.Payload.Before)
	fmt.Printf("  • Стало в БД:    %v\n", ev.Payload.After)
	fmt.Println("  • Изменение захвачено без единого SELECT-запроса к базе данных!")
}
```

## Под капотом

Debezium использует слоты логической репликации (`logical replication slot`). PostgreSQL сохраняет сегменты WAL на диске до тех пор, пока коннектор Debezium не подтвердит их чтение.

## Подводные камни

Остановить Kafka Connect на длительное время при работающей базе данных: PostgreSQL не сможет очистить WAL файлы, и директория `pg_wal` заполнит весь жесткий диск сервера, приведя к аварийной остановке базы данных.

## На собеседовании

**Вопрос с собеседования:** «В чем преимущество CDC на основе Debezium перед записью событий в Kafka из кода сервиса?»
**Ответ:** CDC гарантирует 100% согласованность: если транзакция закоммичена в БД, событие гарантированно попадет в Kafka. Нет проблемы Dual-Write, нет риска рассинхронизации при сбое сети между сервисом и брокером, а также перехватываются прямые изменения данных администратором через psql.
