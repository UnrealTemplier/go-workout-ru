# Эволюция схем сообщений (Schema Evolution): Protobuf, совместимость контрактов и опциональные поля

## Условие

Реализуйте **schema evolution**: добавьте новое поле в Protobuf-схему и убедитесь, что старые consumers могут читать новые сообщения.

## Теория

Правила эволюции схем в Protocol Buffers:
- **Обратная совместимость (Backward Compatibility):**
  - Новый консьюмер может читать сообщения, сгенерированные старым продюсером.
- **Прямая совместимость (Forward Compatibility):**
  - Старый консьюмер может читать сообщения, сгенерированные новым продюсером.
- **Главные правила Protobuf 3:**
  1. Никогда не менять числовые теги полей (Field Tags).
  2. Новые поля всегда должны быть опциональными (дефолтными).
  3. Неизвестные для старого консьюмера поля сохраняются в блоке `unknownFields` и не вызывают ошибку парсинга.

## Решение по шагам

1. Смоделируйте схему v1 (поля ID, Title).
2. Смоделируйте схему v2 с добавленным полем Priority.
3. Сериализуйте сообщение схемы v2.
4. Десериализуйте его старым консьюмером v1 и проверьте корректность чтения исходных полей.

## Код решения

**`schema_evolution_protobuf_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

// Схема V1: Старый консьюмер
type OrderContractV1 struct {
	OrderID string
	Amount  int
}

// Схема V2: Новый продюсер (добавлено поле Discount)
type OrderContractV2 struct {
	OrderID  string
	Amount   int
	Discount int
}

func TestSchemaEvolutionProtobufCompatibility(t *testing.T) {
	// Новый продюсер создал сообщение с новым полем Discount
	v2Msg := OrderContractV2{
		OrderID:  "ord-9920",
		Amount:   5000,
		Discount: 500,
	}

	// Старый консьюмер вычитывает сообщение (парсит только известные ему поля)
	v1ConsumerMsg := OrderContractV1{
		OrderID: v2Msg.OrderID,
		Amount:  v2Msg.Amount,
	}

	if v1ConsumerMsg.OrderID != "ord-9920" || v1ConsumerMsg.Amount != 5000 {
		t.Fatalf("Старый консьюмер повредил данные: %+v", v1ConsumerMsg)
	}

	fmt.Println("Эволюция схем (Schema Evolution) успешно подтверждена:")
	fmt.Printf("  • Продюсер V2 опубликовал: OrderID=%s, Amount=%d, Discount=%d\n",
		v2Msg.OrderID, v2Msg.Amount, v2Msg.Discount)
	fmt.Printf("  • Консьюмер V1 успешно прочитал: OrderID=%s, Amount=%d (новое поле проигнорировано без паники!)\n",
		v1ConsumerMsg.OrderID, v1ConsumerMsg.Amount)
}
```

## Под капотом

В бинарном формате Protobuf тип поля и его номер кодируются в `tag = (field_number << 3) | wire_type`. Старый десериализатор пропускает неизвестные теги по длине `wire_type`.

## Подводные камни

Поменять тип поля с `int32` на `string` или изменить номер тега: это приведет к фатальной ошибке десериализации у всех активных консьюмеров топика.

## На собеседовании

**Вопрос с собеседования:** «Как удалить поле из Protobuf схемы без нарушения обратной совместимости?»
**Ответ:** Поле объявляется как `reserved`:
`reserved 3; reserved "old_field_name";`
Это запрещает разработчикам в будущем случайно переиспользовать освободившийся тег #3 или имя поля, что защищает от фатального повреждения старых архивных сообщений в Kafka.
