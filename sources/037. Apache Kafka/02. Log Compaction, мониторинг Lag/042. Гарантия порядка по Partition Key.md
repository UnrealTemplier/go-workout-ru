# Гарантия порядка по Partition Key: параллельные события Order_1 и Order_2 и предотвращение гонок

## Условие

**Гарантия порядка (Partition Key)**: Отправь события изменения статуса для `Order_1` и `Order_2` вперемешку. Если не указать ключ, Kafka раскидает их по разным партициям, и консьюмеры могут обработать "Заказ закрыт" раньше, чем "Заказ создан". При отправке укажи `Key: []byte(orderID)`. Убедись, что все события одного заказа попадают в одну партицию и читаются строго по порядку.

## Теория

Изоляция параллельных цепочек событий по ключу:
- Если отправляются события двух заказов:
  - `Order_1`: 1. `Created` \(\to\) 2. `Paid` \(\to\) 3. `Closed`
  - `Order_2`: 1. `Created` \(\to\) 2. `Cancelled`
- При использовании `Key = []byte(orderID)`:
  - Все события `Order_1` направляются строго в Partition \(A\).
  - Все события `Order_2` направляются строго в Partition \(B\).
- Внутри каждой партиции порядок событий 100% строгий (FIFO). Разные заказы могут обрабатываться параллельно без задержек.

## Решение по шагам

1. Сформируйте последовательности статусов для двух заказов.
2. Направьте события с ключами в соответствующие партиции.
3. Проверьте, что в каждой партиции цепочка статусов строго хронологична.
4. Продемонстрируйте защиту от логических нарушений.

## Код решения

**`order_key_lifecycle_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

func AssignPartitionMurmur(key string, totalPartitions int) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return int(h.Sum32()&0x7fffffff) % totalPartitions
}

func TestOrderKeyLifecycleOrdering(t *testing.T) {
	const partitions = 3
	partitionLogs := make(map[int][]string)

	events := []struct {
		OrderID string
		Status  string
	}{
		{OrderID: "Order_1", Status: "Created"},
		{OrderID: "Order_2", Status: "Created"},
		{OrderID: "Order_1", Status: "Paid"},
		{OrderID: "Order_2", Status: "Cancelled"},
		{OrderID: "Order_1", Status: "Closed"},
	}

	for _, ev := range events {
		p := AssignPartitionMurmur(ev.OrderID, partitions)
		partitionLogs[p] = append(partitionLogs[p], fmt.Sprintf("%s:%s", ev.OrderID, ev.Status))
	}

	p1 := AssignPartitionMurmur("Order_1", partitions)
	p2 := AssignPartitionMurmur("Order_2", partitions)

	fmt.Println("Маршрутизация жизненного цикла заказов по Partition Key:")
	fmt.Printf("  • Партиция #%d (Order_1): %v\n", p1, partitionLogs[p1])
	fmt.Printf("  • Партиция #%d (Order_2): %v\n", p2, partitionLogs[p2])

	// Проверяем порядок Order_1
	expectedO1 := []string{"Order_1:Created", "Order_1:Paid", "Order_1:Closed"}
	for i, exp := range expectedO1 {
		if partitionLogs[p1][i] != exp {
			t.Fatalf("Нарушен порядок в Order_1: got %s, want %s", partitionLogs[p1][i], exp)
		}
	}

	fmt.Println("  • Инвариант: 'Заказ закрыт' никогда не опередит 'Заказ создан'!")
}
```

## Под капотом

Детерминированная привязка ключа к партиции преобразует проблему глобальной синхронизации распределенной системы в локальные независимые очереди, идеально масштабируемые на ядра CPU.

## Подводные камни

Отправлять `order_id` в JSON-теле, оставляя `Key: nil`: Kafka разбросает статусы по разным партициям, и статус «Закрыт» будет вычитан воркером раньше статуса «Создан».

## На собеседовании

**Вопрос с собеседования:** «Что делать, если порядок событий нарушился из-за бага продюсера?»
**Ответ:** На стороне консьюмера применяют стейт-машину (FSM) с версионированием сущности. Если консьюмер видит событие `Version = 3`, в то время как текущая версия в базе `Version = 1`, событие откладывается во временный буфер или топик задержки (Stash/Retry), пока не прибудет событие `Version = 2`.
