# Каверзный кейс At-Least-Once: симуляция паники до коммита оффсета и идемпотентность через PostgreSQL

## Условие

**[Каверзный кейс — At-least-once]**: Отключи `AutoCommit` (`AutoCommit: false`). Прочитай сообщение, сымитируй крах (panic) ДО вызова `CommitMessages`. Запусти консьюмера снова. Убедись, что сообщение прочиталось повторно. Напиши код, делающий обработчик идемпотентным (например, запись ID обработанного сообщения в Redis/БД).

## Теория

Анатомия сбоя при семантике At-Least-Once:
- При отключенном AutoCommit:
  - Шаг 1: `msg := fetch()` (Offset = 77)
  - Шаг 2: Выполнение бизнес-логики.
  - Шаг 3: **Аварийный сбой / Panic** до вызова `CommitMessages()`.
  - Шаг 4: Рестарт воркера \(\to\) чтение продолжается с последнего закоммиченного оффсета (снова Offset 77!).
- **Опасность дублирования:** если бизнес-логика не идемпотентна, заказ будет списан повторно!
- **Решение:** единая SQL-транзакция со служебной таблицей:
  ```sql
  INSERT INTO processed_events (event_id) VALUES ($1);
  UPDATE accounts SET balance = balance - 100 WHERE id = $2;
  ```
  При повторном выполнении первичный ключ вызовет ошибку `unique_violation`, предотвратив повторное списание.

## Решение по шагам

1. Создайте структуру хранилища с таблицей `processed_events`.
2. Смоделируйте падение процесса до вызова фиксации смещения.
3. Перезапустите обработчик с тем же сообщением.
4. Убедитесь, что благодаря первичному ключу повторное списание не произошло.

## Код решения

**`at_least_once_panic_recovery_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type DatabaseState struct {
	processedEvents map[string]bool
	userBalance     int
}

func (db *DatabaseState) ExecuteTransfer(eventID string, amount int) error {
	// Проверка уникальности в рамках транзакции (PRIMARY KEY)
	if db.processedEvents[eventID] {
		return fmt.Errorf("событие %s уже было зафиксировано (Duplicate)", eventID)
	}

	db.processedEvents[eventID] = true
	db.userBalance -= amount
	return nil
}

func TestAtLeastOncePanicRecovery(t *testing.T) {
	db := &DatabaseState{
		processedEvents: make(map[string]bool),
		userBalance:     1000,
	}

	eventID := "evt-withdraw-4401"
	amount := 250

	// 1. Первая попытка: списание прошло, но произошла паника до CommitMessages
	err1 := db.ExecuteTransfer(eventID, amount)
	if err1 != nil || db.userBalance != 750 {
		t.Fatalf("Первое списание должно пройти успешно: err=%v, bal=%d", err1, db.userBalance)
	}

	// 2. Воркер упал, оффсет не закоммичен, сообщение пришло повторно!
	err2 := db.ExecuteTransfer(eventID, amount)
	if err2 == nil {
		t.Fatal("Повторная обработка обязана завершиться ошибкой дублирования")
	}

	// Баланс не должен уменьшиться повторно!
	if db.userBalance != 750 {
		t.Fatalf("Баланс изменился повторно: %d", db.userBalance)
	}

	fmt.Println("Идемпотентный обработчик успешно справился с повторной доставкой после краха:")
	fmt.Printf("  • Первая попытка: баланс уменьшен до %d руб\n", db.userBalance)
	fmt.Printf("  • Повторная доставка после паники: отсечена (Причина: %v)\n", err2)
	fmt.Printf("  • Итоговый баланс остался строго: %d руб!\n", db.userBalance)
}
```

ℹ️ Защита от дублирования при повторной доставке сообщения после сбоя консьюмера

## Под капотом

В реляционных базах данных проверка `UNIQUE INDEX` на уровне хранилища является абсолютно потокобезопасной и устойчивой к параллельным гонкам нескольких инстансов воркеров.

## Подводные камни

Выполнять дедупликацию в два раздельных шага без транзакции (`SELECT` \(\to\) затем `INSERT`): два параллельных воркера одновременно выполнят `SELECT`, оба увидят, что записи нет, и оба выполнят начисление средств.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать идемпотентность, если целевая система — это не реляционная БД, а сторонний REST API платежного шлюза?»
**Ответ:** Передавать в HTTP-запросе заголовок идемпотентности `Idempotency-Key: <event_uuid>`. Все современные платежные системы (Stripe, CloudPayments, ЮKassa) запоминают этот ключ и при повторном запросе возвращают статус первой успешной транзакции без повторного списания денег.
