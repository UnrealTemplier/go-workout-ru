# Log Compaction в Event Sourcing: сохранение снапшотов агрегатов и восстановление состояния

## Условие

Используйте **log compaction** для event sourcing: храните все события, но периодически "сжимайте" историю.

## Теория

Снапшоты агрегатов в Event Sourcing:
- Если сущность пережила 100 000 событий изменения статуса:
  - Восстановление агрегата с оффсета 0 займет секунды.
- **Архитектура со сжатым топиком снапшотов:**
  1. Топик `order_events` (`cleanup.policy = delete`, хранит все детальные события за 30 дней).
  2. Топик `order_snapshots` (`cleanup.policy = compact`, ключ `order_id`, значение — сжатый финальный JSON-слепок агрегата).
  3. При старте сервис мгновенно загружает последний снапшот из `order_snapshots` и дочитывает только несколько свежих событий из `order_events`.

## Решение по шагам

1. Создайте структуру агрегата `OrderAggregate`.
2. Реализуйте функцию сохранения снапшота в compacted топик.
3. Продемонстрируйте мгновенную регидрацию состояния из снапшота.
4. Проверьте актуальность восстановленного баланса.

## Код решения

**`event_sourcing_compaction_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type OrderAggregate struct {
	ID      string
	Version int
	Status  string
	Total   int
}

type SnapshotStore struct {
	compactedLog map[string]OrderAggregate
}

func (s *SnapshotStore) SaveSnapshot(agg OrderAggregate) {
	s.compactedLog[agg.ID] = agg
}

func (s *SnapshotStore) LoadSnapshot(id string) (OrderAggregate, bool) {
	agg, ok := s.compactedLog[id]
	return agg, ok
}

func TestEventSourcingCompactionSnapshot(t *testing.T) {
	store := &SnapshotStore{compactedLog: make(map[string]OrderAggregate)}

	orderID := "ord-771"

	// Сохраняем снапшот агрегата после 500 промежуточных событий
	snap := OrderAggregate{
		ID:      orderID,
		Version: 500,
		Status:  "DELIVERED",
		Total:   14500,
	}
	store.SaveSnapshot(snap)

	// Быстрое восстановление состояния при рестарте сервиса
	restored, ok := store.LoadSnapshot(orderID)
	if !ok || restored.Version != 500 || restored.Status != "DELIVERED" {
		t.Fatalf("Ошибка регидрации агрегата: %+v", restored)
	}

	fmt.Println("Снапшот Event Sourcing успешно загружен из compacted топика:")
	fmt.Printf("  • Агрегат: %s [Версия %d]\n", restored.ID, restored.Version)
	fmt.Printf("  • Статус:  %s, Сумма: %d руб\n", restored.Status, restored.Total)
	fmt.Println("  • Восстановление заняло O(1) вместо повторного проигрывания 500 событий!")
}
```

## Под капотом

Паттерн объединения append-only лога и compacted снапшотов лежит в основе таких движков, как Kafka Streams State Stores и Debezium CDC Engine.

## Подводные камни

Делать снапшот на каждое единичное событие: это создаст избыточную нагрузку на запись. Снапшоты обычно генерируют периодически (каждые 100 событий или раз в сутки).

## На собеседовании

**Вопрос с собеседования:** «Можно ли использовать Kafka в качестве основной базы данных (System of Record)?»
**Ответ:** Да. В сочетании с Compacted топиками, бесконечным сроком хранения (`retention.ms = -1`), фактором репликации \(RF \ge 3\) и `min.insync.replicas = 2`, Kafka обеспечивает ACID-надежность записи на диск (fsync/OS page cache) и используется как постоянный источник истины (Source of Truth) во многих HighLoad проектах (например, в архитектуре New York Times).
