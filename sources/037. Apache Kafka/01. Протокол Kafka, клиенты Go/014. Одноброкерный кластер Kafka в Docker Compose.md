# Одноброкерный кластер Kafka в Docker Compose: топик с 3 партициями и фактором репликации 1

## Условие

Поднимите Kafka (один брокер) через Docker Compose. Создайте топик с 3 партициями и фактором репликации 1.

## Теория

Архитектура Single-Node кластера для разработки:
- Для локальной разработки и unit/integration тестов достаточно одного брокера.
- В одноброкерном кластере:
  - `replication.factor` топика обязан быть строго равен `1`.
  - Значение \(RF > 1\) невозможно, так как реплики одной партиции обязаны физически размещаться на разных брокерах.
  - При этом количество партиций может быть произвольным (например 3 или 10), что позволяет отлаживать параллелизм консьюмеров.

## Решение по шагам

1. Создайте спецификацию одноузлового кластера.
2. Проверьте соответствие фактора репликации числу доступных нод (RF=1).
3. Смоделируйте создание топика с 3 партициями.
4. Протестируйте готовность к приему сообщений.

## Код решения

**`single_node_cluster_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type SingleNodeTopology struct {
	BrokerCount int
	TopicName   string
	Partitions  int
	Replication int
}

func ValidateSingleNodeTopology(topo SingleNodeTopology) error {
	if topo.Replication > topo.BrokerCount {
		return fmt.Errorf("фактор репликации %d превышает число брокеров %d", topo.Replication, topo.BrokerCount)
	}
	return nil
}

func TestSingleNodeClusterTopology(t *testing.T) {
	topo := SingleNodeTopology{
		BrokerCount: 1,
		TopicName:   "dev_events",
		Partitions:  3,
		Replication: 1,
	}

	err := ValidateSingleNodeTopology(topo)
	if err != nil {
		t.Fatalf("Ошибка валидации топологии: %v", err)
	}

	fmt.Println("Одноброкерная топология Kafka успешно верифицирована:")
	fmt.Printf("  • Количество брокеров: %d\n", topo.BrokerCount)
	fmt.Printf("  • Топик:               %s\n", topo.TopicName)
	fmt.Printf("  • Партиций:            %d\n", topo.Partitions)
	fmt.Printf("  • Фактор репликации:   %d\n", topo.Replication)
}
```

## Под капотом

Один брокер держит лидерство над всеми тремя партициями топика. Каждая партиция представлена независимым файлом лога, обслуживаемым собственными файловыми дескрипторами ОС.

## Подводные камни

Использовать одноброкерный кластер в продакшене: выход из строя диска или сервера приведет к полной недоступности системы и потере неподтвержденных данных.

## На собеседовании

**Вопрос с собеседования:** «Какое минимальное количество брокеров необходимо для обеспечения высокой доступности (High Availability) в продакшене?»
**Ответ:** Минимум 3 брокера с фактором репликации \(RF = 3\) и `min.insync.replicas = 2`. Это позволяет кластеру безболезненно пережить отказ 1 брокера без остановки записи продюсеров с `acks=all`.
