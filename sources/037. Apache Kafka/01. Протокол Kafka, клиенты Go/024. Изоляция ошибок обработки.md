# Изоляция ошибок обработки: Dead Letter Queue (orders.dlq) с оригинальными заголовками и стектрейсом

## Условие

Реализуйте **dead letter queue**: при ошибке обработки отправляйте сообщение в topic `orders.dlq` с оригинальными headers и информацией об ошибке.

## Теория

Построение production-ready DLQ в Kafka:
- При падении обработки критического заказа (битый JSON, нарушение инварианта бизнес-логики):
  - Повторять попытку бесконечно нельзя: партиция зависнет (Head-of-Line Blocking).
  - Игнорировать нельзя: потеря денег клиента.
- **Решение:**
  - Обернуть исходное сообщение.
  - Добавить в метаданные заголовков:
    - `x-original-topic`: `orders`
    - `x-original-partition`: `1`
    - `x-original-offset`: `8402`
    - `x-error-message`: текст ошибки
    - `x-error-timestamp`: время сбоя
  - Опубликовать в `orders.dlq` и закоммитить оффсет в `orders`.

## Решение по шагам

1. Создайте структуру заголовков DLQ сообщения.
2. Смоделируйте ошибку парсинга полезной нагрузки.
3. Опубликуйте сообщение в `orders.dlq` с контекстом ошибки.
4. Убедитесь в сохранении полной трассировочной информации.

## Код решения

**`orders_dlq_headers_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type DLQMessage struct {
	OriginalTopic string
	Headers       map[string]string
	Payload       []byte
}

type OrderDLQPublisher struct {
	dlqInbox []DLQMessage
}

func (p *OrderDLQPublisher) RouteToDLQ(origTopic string, partition int, offset int64, payload []byte, failureErr error) {
	headers := map[string]string{
		"x-original-topic":     origTopic,
		"x-original-partition": fmt.Sprintf("%d", partition),
		"x-original-offset":    fmt.Sprintf("%d", offset),
		"x-error-reason":       failureErr.Error(),
		"x-failed-at":          time.Now().UTC().Format(time.RFC3339),
	}

	p.dlqInbox = append(p.dlqInbox, DLQMessage{
		OriginalTopic: origTopic,
		Headers:       headers,
		Payload:       payload,
	})
}

func TestOrdersDLQHeaders(t *testing.T) {
	dlq := &OrderDLQPublisher{}

	malformedPayload := []byte("{order_id: corrupted-binary-data")
	err := fmt.Errorf("unexpected EOF during JSON unmarshal")

	dlq.RouteToDLQ("orders", 2, 9401, malformedPayload, err)

	if len(dlq.dlqInbox) != 1 {
		t.Fatalf("Ожидалось 1 сообщение в DLQ: %d", len(dlq.dlqInbox))
	}

	msg := dlq.dlqInbox[0]
	if msg.Headers["x-original-topic"] != "orders" || msg.Headers["x-original-offset"] != "9401" {
		t.Fatalf("Заголовки трассировки повреждены: %+v", msg.Headers)
	}

	fmt.Println("Сообщение успешно изолировано в orders.dlq:")
	fmt.Printf("  • Исходный топик: %s [Partition %s, Offset %s]\n",
		msg.Headers["x-original-topic"], msg.Headers["x-original-partition"], msg.Headers["x-original-offset"])
	fmt.Printf("  • Причина сбоя:   %s\n", msg.Headers["x-error-reason"])
	fmt.Printf("  • Время ошибки:   %s\n", msg.Headers["x-failed-at"])
}
```

## Под капотом

Заголовки (Kafka Record Headers) передаются в бинарном протоколе в блоке `Header[]` в виде пар ключ-значение байтов, не требуя повторного маршалинга или изменения структуры тела сообщения.

## Подводные камни

Отправлять в DLQ сообщение без коммита смещения в основном топике: консьюмер продолжит падать на том же месте при рестарте.

## На собеседовании

**Вопрос с собеседования:** «Как безопасно вернуть сообщения из DLQ обратно в основной топик после исправления бага (DLQ Reprocessing / Redrive)?»
**Ответ:** Разрабатывается специальная CLI утилита (Redrive Service), которая вычитывает сообщения из `orders.dlq`, удаляет заголовки `x-error-*`, при необходимости валидирует схему и отправляет сообщения обратно в топик `orders` с сохранением оригинальных ключей партиционирования.
