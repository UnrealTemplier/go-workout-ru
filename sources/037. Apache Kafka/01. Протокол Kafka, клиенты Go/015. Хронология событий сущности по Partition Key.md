# Хронология событий сущности по Partition Key: сохранение причинно-следственной связи

## Условие

Изучите **partition key**: отправляйте сообщения с ключом `user_id`, чтобы все события одного пользователя попадали в одну partition (сохранение порядка).

## Теория

Причинно-следственная связь (Causality) в Event Sourcing:
- Жизненный цикл банковского счета:
  1. `AccountCreated` (начальный баланс 0)
  2. `MoneyDeposited +1000`
  3. `MoneyWithdrawn -400`
- Если ключ `account_id` гарантирует попадание всех 3 событий в одну партицию:
  - Консьюмер прочитает их строго по порядку.
  - Итоговый баланс: \(0 + 1000 - 400 = 600\).
- Если порядок нарушится (события попадут в разные партиции):
  - Консьюмер может сначала применить `MoneyWithdrawn -400` \(\to\) ошибка `InsufficientFundsException` на пустом счете!

## Решение по шагам

1. Создайте структуру банковского счета.
2. Смоделируйте последовательное применение упорядоченных событий.
3. Проверьте корректный расчет финального баланса.
4. Убедитесь в недопустимости нарушения порядка.

## Код решения

**`causality_ordering_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type AccountEvent struct {
	Type   string
	Amount int
}

type BankAccount struct {
	Balance int
}

func (a *BankAccount) Apply(ev AccountEvent) error {
	switch ev.Type {
	case "CREATED":
		a.Balance = ev.Amount
	case "DEPOSIT":
		a.Balance += ev.Amount
	case "WITHDRAW":
		if a.Balance < ev.Amount {
			return fmt.Errorf("отказ: баланс %d < списания %d", a.Balance, ev.Amount)
		}
		a.Balance -= ev.Amount
	}
	return nil
}

func TestCausalityOrdering(t *testing.T) {
	acc := &BankAccount{}

	// Хронологическая цепочка из одной партиции
	events := []AccountEvent{
		{Type: "CREATED", Amount: 0},
		{Type: "DEPOSIT", Amount: 1000},
		{Type: "WITHDRAW", Amount: 400},
	}

	for _, ev := range events {
		err := acc.Apply(ev)
		if err != nil {
			t.Fatalf("Ошибка применения события: %v", err)
		}
	}

	if acc.Balance != 600 {
		t.Fatalf("Итоговый баланс должен быть 600: %d", acc.Balance)
	}

	fmt.Println("Причинно-следственная связь (Causality) успешно сохранена:")
	fmt.Printf("  • Порядок: CREATED(0) -> DEPOSIT(1000) -> WITHDRAW(400)\n")
	fmt.Printf("  • Финальный баланс счета: %d руб!\n", acc.Balance)
}
```

## Под капотом

В распределенных системах строгий порядок требует единой очереди обработки (Single Queue per Entity). Партиционирование по ключу в Kafka элегантно решает эту задачу в масштабе сотен миллионов сущностей.

## Подводные камни

Полагаться на поле `timestamp` в теле сообщения вместо ключа партиции: часы на серверах расходятся (Clock Drift), и сортировка по времени в памяти консьюмера не гарантирует порядок.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если в партицию параллельно пишут два разных продюсера с одним ключом?»
**Ответ:** Порядок сообщений будет сохранен в порядке их фактического физического прибытия на лидер-брокер. Однако для исключения конфликтов одновременной модификации сущности двумя сервисами на архитектурном уровне назначают строго одного сервиса-владельца (Single Writer Principle) для каждого агрегата.
