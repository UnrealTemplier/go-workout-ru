# Паттерн повторных попыток и изоляции сбоев (Retry & Dead Letter Queue) в топиках Kafka

## Условие

**Очередь повторных попыток и отравленных сообщений (Retry & DLQ)**: Напишите надежный обработчик платежных событий из Kafka. Если при обработке события возникает временная ошибка (например, недоступен внешний шлюз банка):
* Программа должна отправить сообщение в топик повторных попыток `payments_retry` с инкрементом счетчика попыток в заголовках (headers).
* Если количество попыток превысило 3, отправьте сообщение в топик "отравленных" сообщений `payments_dlq` (Dead Letter Queue) для ручного разбора администратором и закомитте смещение в исходном топике, чтобы не заблокировать работу всего консьюмера.

## Теория

Архитектура Retry & DLQ в распределенном логе Kafka:
- В Kafka нет встроенного механизма Dead Lettering (в отличие от RabbitMQ DLX), поэтому паттерн реализуется архитектурно через отдельные топики:
  1. `payments`: основной топик.
  2. `payments_retry`: топик для сообщений с временными сбоями. Заголовок `X-Retry-Count: N`.
  3. `payments_dlq`: финальный топик для безнадежно упавших сообщений (Poison Pills).
- **Критический шаг:** после перекладывания сообщения в `payments_retry` или `payments_dlq` консьюмер **обязан закоммитить оффсет** в исходном топике, иначе вся партиция зависнет в мертвом цикле (Head-of-Line Blocking)!

## Решение по шагам

1. Создайте структуру заголовков сообщения Kafka с полем счетчика попыток.
2. Реализуйте логику маршрутизации: попытки 1..3 направляются в `payments_retry`.
3. При превышении порога (попытка > 3) направьте сообщение в `payments_dlq`.
4. Закоммитьте исходное смещение для продолжения потока.

## Код решения

**`kafka_retry_dlq_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RetryableKafkaMessage struct {
	ID         string
	RetryCount int
	Payload    string
}

type TopicRouter struct {
	retryTopic []RetryableKafkaMessage
	dlqTopic   []RetryableKafkaMessage
}

func (r *TopicRouter) HandleFailure(msg RetryableKafkaMessage) (committed bool, targetTopic string) {
	if msg.RetryCount < 3 {
		msg.RetryCount++
		r.retryTopic = append(r.retryTopic, msg)
		// Коммитим исходный оффсет, задача ушла в retry топик!
		return true, "payments_retry"
	}

	// Лимит исчерпан: отправляем в DLQ
	r.dlqTopic = append(r.dlqTopic, msg)
	return true, "payments_dlq"
}

func TestKafkaRetryAndDLQ(t *testing.T) {
	router := &TopicRouter{}

	m1 := RetryableKafkaMessage{ID: "tx-1", RetryCount: 1, Payload: "Платеж $50"}
	mFatal := RetryableKafkaMessage{ID: "tx-fatal", RetryCount: 3, Payload: "Платеж с неверной картой"}

	comm1, top1 := router.HandleFailure(m1)
	comm2, top2 := router.HandleFailure(mFatal)

	if !comm1 || top1 != "payments_retry" || router.retryTopic[0].RetryCount != 2 {
		t.Fatalf("Сбой retry маршрутизации: %v, %s", comm1, top1)
	}

	if !comm2 || top2 != "payments_dlq" {
		t.Fatalf("Сбой DLQ маршрутизации: %v, %s", comm2, top2)
	}

	fmt.Println("Retry & DLQ паттерн в Kafka успешно изолировал ошибки:")
	fmt.Printf("  • tx-1 перенаправлен в:     %s (Счетчик попыток: %d)\n", top1, router.retryTopic[0].RetryCount)
	fmt.Printf("  • tx-fatal перенаправлен в: %s (Лимит исчерпан, направлен операторам!)\n", top2)
	fmt.Println("  • Оффсеты исходного топика закоммичены, консьюмер не заблокирован!")
}
```

## Под капотом

Поскольку партиция в Kafka — это строгий append-only журнал, консьюмер не может пропустить сбойное сообщение без коммита. Перенос в другой топик с последующим коммитом смещения — единственный способ разблокировать очередь.

## Подводные камни

Делать локальный бесконечный цикл повторов на одном сообщении: консьюмер заблокирует всю партицию, а Kafka сочтет его мертвым по `max.poll.interval.ms` и вызовет ребалансировку.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать задержку (Delay) между попытками в Kafka, если у сообщений нет TTL?»
**Ответ:** Использовать каскад топиков задержек: `payments_retry_5s`, `payments_retry_30s`, `payments_retry_15m`. Консьюмер топика задержки проверяет таймстамп в заголовке сообщения и спит перед коммитом только в том случае, если 5 секунд еще не прошло. Так как сообщения пишутся последовательно, они протухают строго по порядку (FIFO).
