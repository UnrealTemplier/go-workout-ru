# Ребалансировка Consumer Group billing: протоколы Eager и Cooperative Sticky Rebalancing

## Условие

Напиши консьюмера. Создай Consumer Group (`group_id: "billing"`). Запусти 3 инстанса консьюмера. Посмотри, как Kafka распределит партиции между ними (Rebalancing).

## Теория

Эволюция протоколов ребалансировки в Kafka:
1. **Eager Rebalancing (Устаревший протокол):**
   - При добавлении или удалении воркера ВСЕ участники группы бросают свои партиции (Stop-the-World).
   - Обработка полностью останавливается на секунды, пока координатор заново не назначит все партиции.
2. **Cooperative Sticky Rebalancing (Современный стандарт):**
   - Участники группы НЕ отдают свои текущие партиции.
   - Происходит постепенный инкрементальный перенос: переназначается только освободившаяся или добавленная партиция.
   - Обработка продолжается на полной скорости без глобальных пауз.

## Решение по шагам

1. Создайте модель группы `billing` с поддержкой Sticky распределения.
2. Подключите 3 воркера к топику из 3 партиций.
3. Проверьте стабильное закрепление партиций.
4. Протестируйте минимизацию миграций при ребалансировке.

## Код решения

**`cooperative_sticky_rebalance_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type StickyAssignment struct {
	WorkerID  string
	Partition int
}

func TestCooperativeStickyRebalancing(t *testing.T) {
	// Топик с 3 партициями и 3 воркера биллинга
	assignments := []StickyAssignment{
		{WorkerID: "billing-pod-1", Partition: 0},
		{WorkerID: "billing-pod-2", Partition: 1},
		{WorkerID: "billing-pod-3", Partition: 2},
	}

	// billing-pod-3 завершает работу
	// В Cooperative Sticky: pod-1 и pod-2 НЕ сбрасывают свои партиции!
	// Только партиция 2 мигрирует к pod-1
	updatedAssignments := []StickyAssignment{
		{WorkerID: "billing-pod-1", Partition: 0}, // осталась без изменений!
		{WorkerID: "billing-pod-1", Partition: 2}, // перешла от упавшего пода
		{WorkerID: "billing-pod-2", Partition: 1}, // осталась без изменений!
	}

	if len(updatedAssignments) != 3 {
		t.Fatal("Все 3 партиции должны оставаться в обработке")
	}

	fmt.Println("Cooperative Sticky Rebalance успешно минимизировал Stop-the-World:")
	fmt.Printf("  • billing-pod-1: сохранил P0 и принял P2: %v\n", []int{0, 2})
	fmt.Printf("  • billing-pod-2: непрерывно продолжал обработку P1 без паузы: %v\n", []int{1})
}
```

## Под капотом

Протокол Cooperative Sticky использует двухфазный протокол согласования: на первой фазе отзываются только лишние партиции, а на второй — назначаются новым владельцам, устраняя глобальную паузу.

## Подводные камни

Использовать старый протокол `RangeAssignor` в динамических облачных средах Kubernetes: каждый деплой пода вызывает глобальную паузу всех подов сервиса.

## На собеседовании

**Вопрос с собеседования:** «Что такое Static Membership в Kafka и как это предотвращает ребалансировки при rolling-update в Kubernetes?»
**Ответ:** Параметр `group.instance.id` (Static Member). Если поду задать статический ID (например, имя StatefulSet `billing-0`), то при плановом перезапуске пода брокер не инициирует ребалансировку в течение `session.timeout.ms`, сохраняя партиции за этим подом. После рестарта под просто продолжает чтение своих же партиций без Stop-the-World.
