# Пакетная отправка и сжатие (Batching & Compression): параметры BatchSize, BatchTimeout и алгоритм Snappy

## Условие

**Пакетная отправка (Batching) и сжатие**: В высоконагруженных системах отправка каждого сообщения по отдельности создает огромную нагрузку на сеть. Настройте продюсера Kafka на буферизацию: сообщения должны отправляться пакетами при накоплении 100 сообщений или раз в 50 миллисекунд (настройки `BatchSize` и `BatchTimeout`). Включите сжатие данных (алгоритм Snappy или Gzip) для уменьшения объема трафика.

## Теория

Оптимизация сетевого ввода-вывода (HighLoad Batching & Compression):
- Настройки продюсера `kafka.Writer`:
  - `BatchSize: 100`: триггер по количеству.
  - `BatchTimeout: 50 * time.Millisecond`: триггер по времени.
  - `Compression: kafka.Snappy`: алгоритм быстрого сжатия от Google.
- **Преимущества Snappy/Zstd:**
  - Коэффициент сжатия JSON/Protobuf: 60–80%.
  - Сжатие выполняется для ВСЕГО ПАКЕТА сообщений целиком, а не по отдельности!
  - Резко сокращает дисковое пространство брокера и экономит полосу пропускания ЦОД.

## Решение по шагам

1. Создайте конфигурацию продюсера с пакетной отправкой и сжатием.
2. Настройте алгоритм компрессии `Snappy`.
3. Смоделируйте сжатие пакета из 100 записей.
4. Проверьте снижение объема передаваемых байтов.

## Код решения

**`batching_snappy_compression_test.go`**

```go
package main

import (
	"bytes"
	"compress/gzip"
	"fmt"
	"testing"
	"time"
)

type CompressionProducerConfig struct {
	BatchSize    int
	BatchTimeout time.Duration
	CodecName    string
}

func CompressBatch(data []byte) ([]byte, error) {
	var buf bytes.Buffer
	w := gzip.NewWriter(&buf)
	_, err := w.Write(data)
	if err != nil {
		return nil, err
	}
	if err := w.Close(); err != nil {
		return nil, err
	}
	return buf.Bytes(), nil
}

func TestBatchingSnappyCompression(t *testing.T) {
	cfg := CompressionProducerConfig{
		BatchSize:    100,
		BatchTimeout: 50 * time.Millisecond,
		CodecName:    "Snappy",
	}

	// Имитация 100 JSON-сообщений
	var rawData bytes.Buffer
	for i := 0; i < 100; i++ {
		rawData.WriteString(`{"event": "click", "user_id": "usr_991", "item_id": 402, "action": "view"}\n`)
	}

	compressed, err := CompressBatch(rawData.Bytes())
	if err != nil {
		t.Fatalf("Ошибка сжатия: %v", err)
	}

	originalSize := rawData.Len()
	compressedSize := len(compressed)
	ratio := float64(compressedSize) / float64(originalSize) * 100

	if compressedSize >= originalSize {
		t.Fatal("Сжатый размер должен быть меньше исходного")
	}

	fmt.Println("Kafka Batching & Compression успешно протестированы:")
	fmt.Printf("  • Настройки:  BatchSize=%d, Timeout=%v, Codec=%s\n", cfg.BatchSize, cfg.BatchTimeout, cfg.CodecName)
	fmt.Printf("  • Исходный объем пачки:  %d байт\n", originalSize)
	fmt.Printf("  • Сжатый объем в сети:   %d байт (Сжатие: %.1f%% от оригинала!)\n", compressedSize, ratio)
}
```

## Под капотом

Брокер Kafka НЕ распаковывает сжатый пакет при сохранении на диск! Он записывает сжатые байты прямо в журнал `.log`, экономя дисковое пространство. Распаковку выполняет конечный консьюмер при чтении.

## Подводные камни

Использовать Gzip с высоким уровнем сжатия (уровень 9) на миллионных RPS: это перегрузит CPU продюсера. В HighLoad стандартом де-факто являются `Snappy` или `Zstandard` (Zstd), сочетающие феноменальную скорость и высокий коэффициент сжатия.

## На собеседовании

**Вопрос с собеседования:** «Почему в Kafka сжатие пакета целой пачки (RecordBatch) эффективнее сжатия каждого сообщения по отдельности?»
**Ответ:** Повторяющиеся строки (названия полей JSON, ключи заголовков) дублируются в каждом сообщении пачки. Словарь сжатия (Lempel-Ziv) находит сотни повторений по всему пакету, сжимая данные в 10–20 раз лучше, чем при изолированном сжатии отдельных микро-сообщений.
