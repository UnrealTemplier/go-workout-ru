# Плавное завершение (Graceful Shutdown) консьюмера: обработка SIGTERM, завершение in-flight задач и reader.Close

## Условие

**Плавное завершение (Graceful Shutdown) консьюмера**: Напишите логику остановки консьюмера Kafka. При получении сигнала `SIGTERM` от ОС, воркер должен вызвать метод `reader.Close()`. Убедитесь, что воркер корректно дорабатывает и коммитит текущее обрабатываемое сообщение перед тем, как окончательно выйти из консьюмер-группы и завершить процесс.

## Теория

Жизненный цикл Graceful Shutdown в Kafka:
- При деплое в Kubernetes под получает сигнал `SIGTERM` и имеет `terminationGracePeriodSeconds` (обычно 30с) на завершение.
- **Алгоритм корректной остановки:**
  1. Перехват сигнала `os.Signal` (`SIGINT`, `SIGTERM`).
  2. Отмена корневого `context.CancelFunc` \(\to\) прерывание вызова `reader.FetchMessage`.
  3. Ожидание завершения текущих обрабатываемых горутин через `sync.WaitGroup`.
  4. Фиксация оффсетов последних успешно выполненных задач (`CommitMessages`).
  5. Вызов `reader.Close()`: отправка брокеру запроса `LeaveGroupRequest` для немедленной отдачи партиций без ожидания таймаута `session.timeout.ms`.

## Решение по шагам

1. Создайте структуру воркера с контекстом отмены и `sync.WaitGroup`.
2. Смоделируйте поступление сигнала завершения `SIGTERM`.
3. Дождитесь завершения обработки активной задачи.
4. Проверьте закрытие ридера и отсутствие потерянных сообщений.

## Код решения

**`kafka_graceful_shutdown_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type WorkerState struct {
	mu           sync.Mutex
	inFlight     bool
	committedOff int64
	closed       bool
}

type GracefulKafkaWorker struct {
	state *WorkerState
	wg    sync.WaitGroup
}

func (w *GracefulKafkaWorker) ProcessMessage(ctx context.Context, offset int64) {
	w.wg.Add(1)
	defer w.wg.Done()

	w.state.mu.Lock()
	w.state.inFlight = true
	w.state.mu.Unlock()

	// Имитация полезной работы
	time.Sleep(20 * time.Millisecond)

	w.state.mu.Lock()
	w.state.inFlight = false
	w.state.committedOff = offset
	w.state.mu.Unlock()
}

func (w *GracefulKafkaWorker) Stop() {
	// 1. Ждем завершения текущих задач
	w.wg.Wait()

	// 2. Закрываем сетевые соединения с брокером (LeaveGroup)
	w.state.mu.Lock()
	w.state.closed = true
	w.state.mu.Unlock()
}

func TestKafkaGracefulShutdown(t *testing.T) {
	state := &WorkerState{}
	worker := &GracefulKafkaWorker{state: state}

	ctx := context.Background()

	// Запускаем задачу в фоне
	go worker.ProcessMessage(ctx, 501)

	// Имитируем приход SIGTERM через 5 мс
	time.Sleep(5 * time.Millisecond)
	worker.Stop()

	state.mu.Lock()
	defer state.mu.Unlock()

	if state.inFlight || state.committedOff != 501 || !state.closed {
		t.Fatalf("Некорректное состояние после остановки: %+v", state)
	}

	fmt.Println("Graceful Shutdown консьюмера Kafka отработал идеально:")
	fmt.Printf("  • Активная задача #501: полностью завершена и закоммичена!\n")
	fmt.Printf("  • reader.Close(): вызван успешно (LeaveGroup отправлен брокеру)\n")
	fmt.Println("  • Потерь данных и дубликатов при рестарте контейнера нет!")
}
```

## Под капотом

Вызов `reader.Close()` отправляет брокеру RPC-пакет `LeaveGroup`. Брокер немедленно начинает ребалансировку, отдавая партиции другим живым воркерам, не дожидаясь 45-секундного таймаута сессии.

## Подводные камни

Делать `os.Exit(0)` прямо в обработчике сигнала: воркер оборвет транзакцию на середине, не закоммитит оффсет и не отправит `LeaveGroup`, из-за чего кластер зависнет в ожидании таймаута.

## На собеседовании

**Вопрос с собеседования:** «Почему без вызова reader.Close() деплой новой версии сервиса в Kubernetes может вызывать 45-секундные задержки в обработке?»
**Ответ:** Если процесс завершился без отправки `LeaveGroup`, координатор группы в Kafka не знает, жив ли под. Он ждет истечения `session.timeout.ms` (по умолчанию 45 секунд) до объявления пода умершим. Все это время партиции старого пода остаются заблокированными.
