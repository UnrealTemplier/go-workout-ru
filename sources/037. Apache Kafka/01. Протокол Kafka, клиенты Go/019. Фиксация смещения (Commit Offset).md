# Фиксация смещения (Commit Offset): ручной CommitMessages против автокоммита и риски дублирования

## Условие

Реализуйте **commit offset**: после обработки сообщения вызывайте `reader.CommitMessages(ctx, msg)`. Изучите разницу между auto-commit и manual commit.

## Теория

Сравнение стратегий фиксации оффсетов:
1. **Auto-Commit (`enable.auto.commit = true`, `CommitInterval: 1s`):**
   - Простой код.
   - Риск потери данных при аварии воркера до записи в базу.
   - Риск дублирования: при падении воркера перечитаются все сообщения за последнюю 1 секунду.
2. **Manual Commit (`reader.CommitMessages(ctx, msg)`):**
   - Полный контроль над моментом фиксации.
   - Оффсет коммитится только тогда, когда результат транзакции надежно записан в постоянное хранилище (PostgreSQL, ClickHouse).
   - Фундамент надежных финансовых и транзакционных сервисов.

## Решение по шагам

1. Создайте модель консьюмера с ручным коммитом смещения.
2. Смоделируйте чтение сообщения с оффсетом 500.
3. Проведите бизнес-обработку.
4. Зафиксируйте вызов `CommitMessages` и проверьте обновление оффсета.

## Код решения

**`commit_offset_comparison_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type OffsetCommitTracker struct {
	lastCommittedOffset int64
}

func (t *OffsetCommitTracker) CommitMessage(ctx context.Context, offset int64) error {
	t.lastCommittedOffset = offset
	return nil
}

func TestCommitOffsetMechanics(t *testing.T) {
	tracker := &OffsetCommitTracker{lastCommittedOffset: 499}
	ctx := context.Background()

	// Извлекаем сообщение Offset=500
	currentMsgOffset := int64(500)

	// Выполняем бизнес-логику (сохранение в БД)
	businessSuccess := true

	if businessSuccess {
		err := tracker.CommitMessage(ctx, currentMsgOffset)
		if err != nil {
			t.Fatalf("Ошибка фиксации смещения: %v", err)
		}
	}

	if tracker.lastCommittedOffset != 500 {
		t.Fatalf("Смещение должно быть зафиксировано на 500: %d", tracker.lastCommittedOffset)
	}

	fmt.Println("Ручная фиксация смещения (CommitMessages) успешно отработала:")
	fmt.Printf("  • Предыдущее смещение: 499\n")
	fmt.Printf("  • Новое смещение в __consumer_offsets: %d\n", tracker.lastCommittedOffset)
	fmt.Println("  • Гарантия At-Least-Once полностью обеспечена!")
}
```

ℹ️ Ручная фиксация смещения в топике __consumer_offsets после обработки

## Под капотом

Закоммиченный оффсет указывает на следующее ожидаемое сообщение (\(N+1\)). Если консьюмер закоммитил Offset 500, после перезапуска он начнет чтение с сообщения с оффсетом 501.

## Подводные камни

Коммитить меньший оффсет после большего в многопоточном воркере: если горутины обрабатывают сообщения не по порядку, случайный коммит старого оффсета откатит позицию всей группы назад.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если база данных записала заказ, а CommitMessages упал по сетевому таймауту?»
**Ответ:** Оффсет в Kafka останется старым. После рестарта воркер перечитает это сообщение снова (повторная доставка). Чтобы избежать дублирования заказа, обработчик консьюмера обязан быть идемпотентным (проверка `INSERT ... ON CONFLICT DO NOTHING` в БД).
