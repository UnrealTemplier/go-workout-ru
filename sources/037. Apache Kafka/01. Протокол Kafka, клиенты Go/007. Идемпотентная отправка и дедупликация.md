# Идемпотентная отправка и дедупликация: RequiredAcks=RequireAll и Redis SET NX на консьюмере

## Условие

**Идемпотентность и дедупликация**: При сбоях сети продюсер может отправить дубликат сообщения.
* Настройте продюсера в режим идемпотентной отправки (в `kafka-go` это обеспечивается настройками `RequiredAcks = RequireAll` и включением механизма транзакций/идемпотентности на брокере).
* На стороне консьюмера реализуйте паттерн "Идемпотентный потребитель": при получении сообщения извлеките его уникальный `UUID` из тела и проверьте в Redis с помощью команды `SET NX`, обрабатывалось ли оно ранее. Если ключ уже существует — проигнорируйте дубликат.

## Теория

Сквозная дедупликация в Kafka:
1. **На стороне продюсера (Idempotent Producer):**
   - Настройка `RequiredAcks = RequireAll` (`acks = -1`).
   - Брокер присваивает продюсеру `ProducerID` (PID) и проверяет монотонно возрастающий номер `SequenceNumber` каждого сообщения.
   - Если сеть мигнула и продюсер переотправил сообщение с тем же `SequenceNumber`, брокер вернет Ack, но НЕ запишет дубликат в партицию.
2. **На стороне консьюмера (Idempotent Consumer):**
   - Проверка уникального ключа события через атомарный `SET message_uuid 1 NX EX 3600` в Redis.
   - Если ключ существует \(\to\) дубликат отбрасывается без повторного исполнения бизнес-логики.

## Решение по шагам

1. Создайте структуру идемпотентного консьюмера с привязкой к кэшу дедупликации.
2. Смоделируйте поступление первичного сообщения с уникальным UUID.
3. Смоделируйте поступление сетевого дубликата того же сообщения.
4. Проверьте, что баланс счета изменился ровно один раз.

## Код решения

**`kafka_idempotent_dedup_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"
)

type DeduplicationStorage struct {
	mu   sync.Mutex
	keys map[string]bool
}

func (s *DeduplicationStorage) SetNX(key string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.keys[key] {
		return false // Уже существует
	}
	s.keys[key] = true
	return true
}

type BankAccountConsumer struct {
	dedup   *DeduplicationStorage
	balance int
}

func (c *BankAccountConsumer) ProcessPayment(msgUUID string, amount int) bool {
	// Атомарный SET NX в Redis
	if !c.dedup.SetNX(msgUUID) {
		fmt.Printf("  • [DEDUP] Сообщение %s уже обработано -> Пропуск дубликата!\n", msgUUID)
		return false
	}

	c.balance += amount
	return true
}

func TestKafkaIdempotentDedup(t *testing.T) {
	consumer := &BankAccountConsumer{
		dedup:   &DeduplicationStorage{keys: make(map[string]bool)},
		balance: 1000,
	}

	eventUUID := "pay-uuid-77192"

	// 1. Первая обработка
	ok1 := consumer.ProcessPayment(eventUUID, 500)
	// 2. Сетевой дубликат
	ok2 := consumer.ProcessPayment(eventUUID, 500)

	if !ok1 || ok2 || consumer.balance != 1500 {
		t.Fatalf("Баланс должен увеличиться ровно 1 раз: got %d, ok1=%v, ok2=%v",
			consumer.balance, ok1, ok2)
	}

	fmt.Println("Идемпотентный консьюмер успешно защитил от двойного начисления:")
	fmt.Printf("  • Первое событие: принято (Баланс: %d руб)\n", consumer.balance)
	fmt.Printf("  • Дубликат события: отфильтрован через SET NX (Баланс остался: %d руб)\n", consumer.balance)
}
```

## Под капотом

Идемпотентный продюсер в Kafka гарантирует дедупликацию только в рамках одной сессии одного продюсера и одной партиции. Защита от дубликатов при падении и перезапуске сервиса консьюмера требует обязательной дедупликации на уровне бизнес-логики (Redis / БД).

## Подводные камни

Использовать составной ключ без TTL в Redis: таблица ключей в Redis будет бесконечно расти, потребляя всю оперативную память сервера. Ключи дедупликации обязаны иметь TTL (например `EX 86400`).

## На собеседовании

**Вопрос с собеседования:** «Почему в Kafka невозможно достичь семантики Exactly-Once без идемпотентного консьюмера или транзакций?»
**Ответ:** Сеть ненадежна по теореме двух генералов. Брокер может успешно записать сообщение и закоммитить оффсет, но пакет с подтверждением TCP может потеряться по дороге к клиенту. Приложение вынуждено делать ретрай, порождая дубликаты. Именно поэтому Exactly-Once в распределенных системах достигается комбинацией At-Least-Once транспорта и идемпотентного хранилища.
