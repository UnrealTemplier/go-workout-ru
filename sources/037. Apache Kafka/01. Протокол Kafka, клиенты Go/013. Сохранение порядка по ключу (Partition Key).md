# Сохранение порядка по ключу (Partition Key): отправка 100 сообщений и группировка по user_id

## Условие

Напиши продюсера, который отправляет 100 сообщений. Используй ключ (Key) для сообщений (например, `user_id`). Убедись, что сообщения с одинаковым ключом попадают в одну и ту же партицию (сохранение порядка).

## Теория

Хэширование ключа для 100 событий:
- При генерации 100 транзакций пользователей:
  - Пользователи: `user_10`, `user_20`, `user_30`.
  - Все сообщения пользователя `user_10` имеют ключ `[]byte("user_10")`.
  - Хэш-функция всегда возвращает один и тот же номер партиции \(P = \text{Hash}(\text{user\_10}) \pmod 3\).
  - Все события конкретного пользователя выстраиваются в единую строгую очередь.

## Решение по шагам

1. Создайте симулятор распределения 100 сообщений по 3 партициям.
2. Сгенерируйте сообщения для 3 разных пользователей.
3. Проверьте, что все сообщения каждого пользователя попали строго в одну целевую партицию.
4. Продемонстрируйте отсутствие межпартиционного перемешивания.

## Код решения

**`partition_key_grouping_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

func GetPartition(key string, partitions int) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return int(h.Sum32()&0x7fffffff) % partitions
}

func TestPartitionKeyGrouping100(t *testing.T) {
	const numPartitions = 3
	partitionsMap := make(map[string]map[int]int) // user -> partition -> count

	for i := 1; i <= 100; i++ {
		userID := fmt.Sprintf("user_%d", i%3) // user_0, user_1, user_2
		p := GetPartition(userID, numPartitions)

		if partitionsMap[userID] == nil {
			partitionsMap[userID] = make(map[int]int)
		}
		partitionsMap[userID][p]++
	}

	for user, pMap := range partitionsMap {
		if len(pMap) != 1 {
			t.Fatalf("События пользователя %s раскиданы по нескольким партициям: %v", user, pMap)
		}
		for p, count := range pMap {
			fmt.Printf("  • Пользователь %s: все %d сообщений попали строго в Партицию #%d\n", user, count, p)
		}
	}

	fmt.Println("Гарантия сохранения порядка сообщений по Partition Key 100% подтверждена!")
}
```

## Под капотом

Внутри одного файла лога партиции смещения (`Offset`) монотонно возрастают: 0, 1, 2, 3... Консьюмер не может физически получить Offset 2 раньше Offset 1.

## Подводные камни

Использовать случайное значение в ключе (например `timestamp` или `uuid`): каждое сообщение пользователя улетит в случайную партицию, полностью разрушив порядок.

## На собеседовании

**Вопрос с собеседования:** «Что такое Key Skew (перекос ключей) в Kafka и как с ним бороться?»
**Ответ:** Если 80% всех заказов делает один VIP-клиент или бот, все его сообщения попадут в одну партицию. Эта партиция и обслуживающий ее воркер будут перегружены на 100%, а остальные 9 воркеров будут простаивать. Решение: составной ключ (Salted Key): `fmt.Sprintf("%s_%d", userID, rand.Intn(3))`, жертвуя глобальным порядком ради балансировки нагрузки.
