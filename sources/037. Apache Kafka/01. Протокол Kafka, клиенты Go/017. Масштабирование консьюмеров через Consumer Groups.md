# Масштабирование консьюмеров через Consumer Groups: распределение партиций по GroupID

## Условие

Используйте **consumer groups**: запустите 3 consumer с одинаковым `GroupID`, и Kafka автоматически распределит partitions между ними.

## Теория

Горизонтальное масштабирование через единый GroupID:
- Если запущены 3 инстанса с одинаковым `GroupID: "orders_worker_group"`:
  - Координатор группы делит партиции топика:
    - Consumer 1 \(\to\) Partition 0
    - Consumer 2 \(\to\) Partition 1
    - Consumer 3 \(\to\) Partition 2
  - Каждый воркер читает свой изолированный поток параллельно.
- Скорость обработки возрастает в 3 раза без единого конфликта или состояния гонки за ресурсы.

## Решение по шагам

1. Создайте модель пула воркеров с общим `GroupID`.
2. Задайте топик с 3 партициями.
3. Проверьте автоматическое взаимно-однозначное соответствие (1:1).
4. Убедитесь в отсутствии пересечений партиций между воркерами.

## Код решения

**`consumer_group_assignment_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ConsumerGroupMember struct {
	InstanceID string
	GroupID    string
	Partition  int
}

func AssignGroupPartitions(groupID string, instances []string, partitionsCount int) []ConsumerGroupMember {
	var members []ConsumerGroupMember
	for i, id := range instances {
		if i < partitionsCount {
			members = append(members, ConsumerGroupMember{
				InstanceID: id,
				GroupID:    groupID,
				Partition:  i,
			})
		}
	}
	return members
}

func TestConsumerGroupAssignment(t *testing.T) {
	instances := []string{"pod-orders-1", "pod-orders-2", "pod-orders-3"}
	groupID := "orders_worker_group"

	members := AssignGroupPartitions(groupID, instances, 3)

	if len(members) != 3 {
		t.Fatalf("Должно быть 3 активных консьюмера: %d", len(members))
	}

	for i, m := range members {
		if m.Partition != i || m.GroupID != groupID {
			t.Fatalf("Некорректная привязка: %+v", m)
		}
		fmt.Printf("  • Воркер %s (Group: %s) -> Партиция #%d\n", m.InstanceID, m.GroupID, m.Partition)
	}

	fmt.Println("Consumer Group успешно распределила 3 партиции между 3 инстансами!")
}
```

ℹ️ Автоматическое распределение партиций между репликами в Consumer Group

## Под капотом

Член группы регулярно шлет heartbeat-запросы на порт координатора брокера. Если брокер не получает heartbeat в течение `session.timeout.ms` (по умолчанию 45с), воркер признается мертвым.

## Подводные камни

Запустить 5 воркеров для топика с 3 партициями в одной Consumer Group: 2 воркера будут бездействовать на 100%, расходуя память и CPU сервера впустую.

## На собеседовании

**Вопрос с собеседования:** «Как двум разным независимым микросервисам (например, Billing и Analytics) получить копии одних и тех же сообщений из одного топика?»
**Ответ:** Запустить их с **разными GroupID**! Сервис биллинга настраивается с `group_id: "billing_group"`, а сервис аналитики с `group_id: "analytics_group"`. Каждая Consumer Group имеет свой собственный независимый набор оффсетов и читает топик на своей скорости без взаимного влияния (Pub/Sub модель).
