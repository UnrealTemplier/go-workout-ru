# Ручное управление смещениями (Manual Commit): вызов CommitMessages строго после записи в БД

## Условие

**Ручное управление смещениями (Manual Commit)**: По умолчанию консьюмеры коммитят прочитанные сообщения автоматически (Auto-Commit). Настройте консьюмера на ручное подтверждение смещений (`CommitMessages`). Напишите код так, чтобы коммит происходил строго после того, как бизнес-логика обработки сообщения (например, запись в БД) завершилась успешно. Объясните, как это предотвращает потерю сообщений при падении воркера (гарантия At-Least-Once).

## Теория

Гарантия доставки At-Least-Once через ручной коммит смещений:
- **Проблема Auto-Commit (`enable.auto.commit = true`):**
  - Раз в \(N\) секунд консьюмер коммитит максимальный прочитанный оффсет.
  - Если сообщение прочитано из Kafka, оффсет закоммичен, а воркер упал до записи в базу данных \(\to\) **сообщение потеряно навсегда**!
- **Решение с ручным коммитом (`reader.CommitMessages`):**
  1. `msg, err := reader.FetchMessage(ctx)` \(\to\) извлекаем сообщение (оффсет НЕ коммитится).
  2. `err = saveToPostgres(msg.Value)` \(\to\) транзакция записи в БД.
  3. `err = reader.CommitMessages(ctx, msg)` \(\to\) оффсет коммитится в специальный системный топик `__consumer_offsets`.
- Если воркер упадет на шаге 2, новый воркер вычитает то же сообщение снова. Данные не теряются.

## Решение по шагам

1. Создайте структуру сообщения Kafka с метаданными оффсета.
2. Реализуйте консьюмер с методом `FetchMessage` и `CommitMessages`.
3. Смоделируйте сбой записи в базу данных и убедитесь, что оффсет НЕ подтвержден.
4. Продемонстрируйте успешный цикл: чтение \(\to\) БД \(\to\) коммит оффсета.

## Код решения

**`manual_commit_at_least_once_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

type KafkaRecord struct {
	Offset int64
	Value  string
}

type ReliableConsumer struct {
	committedOffset int64
	dbTable         []string
}

func (c *ReliableConsumer) ProcessRecord(ctx context.Context, rec KafkaRecord, simulateDBErr bool) error {
	// 1. Бизнес-логика: запись в базу данных
	if simulateDBErr {
		return errors.New("database connection timeout")
	}

	c.dbTable = append(c.dbTable, rec.Value)

	// 2. Ручной коммит смещения строго после успеха в БД!
	c.committedOffset = rec.Offset
	return nil
}

func TestManualCommitAtLeastOnce(t *testing.T) {
	consumer := &ReliableConsumer{committedOffset: -1}
	ctx := context.Background()

	rec1 := KafkaRecord{Offset: 101, Value: "Пополнение баланса #1"}
	rec2 := KafkaRecord{Offset: 102, Value: "Пополнение баланса #2"}

	// Сценарий 1: Сбой БД -> оффсет НЕ коммитится!
	err := consumer.ProcessRecord(ctx, rec1, true)
	if err == nil || consumer.committedOffset != -1 {
		t.Fatalf("При сбое БД оффсет не должен коммититься: err=%v, offset=%d", err, consumer.committedOffset)
	}

	// Сценарий 2: Успешная обработка -> оффсет зафиксирован
	err = consumer.ProcessRecord(ctx, rec2, false)
	if err != nil || consumer.committedOffset != 102 {
		t.Fatalf("Оффсет должен быть закоммичен на 102: err=%v, offset=%d", err, consumer.committedOffset)
	}

	fmt.Println("Manual Commit (At-Least-Once) успешно предотвратил потерю данных:")
	fmt.Printf("  • Сбойное сообщение #101: коммит отклонен (будет перечитано после рестарта!)\n")
	fmt.Printf("  • Успешное сообщение #102: закоммичено смещение Offset=%d\n", consumer.committedOffset)
}
```

ℹ️ Ручное управление смещениями для обеспечения гарантии At-Least-Once

## Под капотом

Смещения консьюмеров хранятся в специальном защищенном топике `__consumer_offsets` с compact-политикой удаления. Ключ сообщения — `{ConsumerGroupID, Topic, Partition}`, значение — `Offset` и таймстамп коммита.

## Подводные камни

Вызывать синхронный `CommitMessages` на каждое единичное сообщение в HighLoad (100k RPS): сетевой round-trip коммита создаст катастрофическую задержку. Рекомендуется коммитить пачками каждые \(N\) сообщений или по таймеру после успешной обработки пачки.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие FetchMessage от ReadMessage в библиотеке segmentio/kafka-go?»
**Ответ:** `ReadMessage` автоматически коммитит оффсет под капотом (Auto-Commit), что чревато потерей сообщений при падении воркера. Для надежных систем используют `FetchMessage` (только извлечение без коммита) в связке с явным ручным вызовом `CommitMessages` строго после записи в постоянное хранилище.
