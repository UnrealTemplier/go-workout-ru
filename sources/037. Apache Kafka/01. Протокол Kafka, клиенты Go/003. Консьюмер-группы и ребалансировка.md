# Консьюмер-группы и ребалансировка (Consumer Group Rebalance): параллелизм 3 партиций и отказоустойчивость

## Условие

**Консьюмер-группы и ребалансировка (Rebalance)**: * Напишите консьюмера, входящего в консьюмер-группу `analytics_group`.
* Запустите три независимых инстанса этого консьюмера (в трех разных терминалах).
* Отправьте 30 сообщений в топик с 3 партициями. Убедитесь, что каждый инстанс читает строго свою партицию.
* Остановите один из инстансов консьюмера. Понаблюдайте за процессом ребалансировки (Rebalance), когда оставшиеся консьюмеры перехватывают освободившуюся партицию.

## Теория

Механика Consumer Group и координатора группы (Group Coordinator):
- В топике с 3 партициями:
  - 3 консьюмера в группе \(\to\) каждый читает ровно по 1 партиции (1:1).
  - Если запустить 4-го консьюмера \(\to\) он будет простаивать (Idle), так как партиций всего 3.
- **Процесс ребалансировки (Rebalance):**
  1. Один из воркеров падает или отключается (нет Heartbeat более `SessionTimeout`).
  2. Брокер-координатор фиксирует отказ и инициирует Rebalance.
  3. Оставшиеся 2 консьюмера получают новые назначения: один читает 1 партицию, второй берет 2 партиции.
  4. Чтение потока продолжается без потери сообщений.

## Решение по шагам

1. Создайте модель координатора Consumer Group `analytics_group`.
2. Смоделируйте распределение 3 партиций между 3 консьюмерами.
3. Сымитируйте остановку инстанса #3.
4. Выполните ребалансировку и убедитесь, что все 3 партиции покрыты оставшимися двумя инстансами.

## Код решения

**`consumer_group_rebalance_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ConsumerInstance struct {
	ID                 string
	AssignedPartitions []int
	IsAlive            bool
}

type GroupCoordinator struct {
	totalPartitions int
	consumers       []*ConsumerInstance
}

func (c *GroupCoordinator) Rebalance() {
	var activeConsumers []*ConsumerInstance
	for _, cons := range c.consumers {
		cons.AssignedPartitions = nil
		if cons.IsAlive {
			activeConsumers = append(activeConsumers, cons)
		}
	}

	if len(activeConsumers) == 0 {
		return
	}

	// Равномерное распределение Range/Round-Robin
	for p := 0; p < c.totalPartitions; p++ {
		target := activeConsumers[p%len(activeConsumers)]
		target.AssignedPartitions = append(target.AssignedPartitions, p)
	}
}

func TestConsumerGroupRebalance(t *testing.T) {
	c1 := &ConsumerInstance{ID: "worker-1", IsAlive: true}
	c2 := &ConsumerInstance{ID: "worker-2", IsAlive: true}
	c3 := &ConsumerInstance{ID: "worker-3", IsAlive: true}

	coord := &GroupCoordinator{
		totalPartitions: 3,
		consumers:       []*ConsumerInstance{c1, c2, c3},
	}

	// 1. Нормальное состояние: 3 воркера на 3 партиции
	coord.Rebalance()
	if len(c1.AssignedPartitions) != 1 || len(c2.AssignedPartitions) != 1 || len(c3.AssignedPartitions) != 1 {
		t.Fatalf("Некорректное начальное распределение: %+v", coord.consumers)
	}

	// 2. Воркер 3 аварийно упал
	c3.IsAlive = false
	coord.Rebalance()

	// 3. Проверяем перераспределение: 3 партиции поделены между воркерами 1 и 2
	totalAssigned := len(c1.AssignedPartitions) + len(c2.AssignedPartitions)
	if totalAssigned != 3 {
		t.Fatalf("Все 3 партиции должны быть распределены: получено %d", totalAssigned)
	}

	fmt.Println("Ребалансировка Consumer Group успешно перераспределила партиции:")
	fmt.Printf("  • worker-1 обслуживает партиции: %v\n", c1.AssignedPartitions)
	fmt.Printf("  • worker-2 обслуживает партиции: %v\n", c2.AssignedPartitions)
	fmt.Printf("  • worker-3 упал: %v\n", c3.AssignedPartitions)
}
```

ℹ️ Динамическое перераспределение партиций при ребалансировке Consumer Group

## Под капотом

В современных версиях Kafka протокол Cooperative Sticky Assignor минимизирует паузы Stop-the-World: воркеры не сбрасывают все партиции разом, а освобождают только затронутые, продолжая вычитку остальных.

## Подводные камни

Долгая синхронная обработка одного сообщения (более `max.poll.interval.ms`, по умолчанию 5 минут): брокер сочтет консьюмер зависшим, исключит его из группы и начнет непрерывную бесконечную ребалансировку (Rebalance Storm).

## На собеседовании

**Вопрос с собеседования:** «Что такое Rebalance Storm и как его предотвратить в Go-микросервисах?»
**Ответ:** Это шторм ребалансировок, когда медленные воркеры вылетают по таймауту `max.poll.interval.ms`, брокер начинает перераспределение, нагрузка на оставшиеся воркеры возрастает, они тоже не успевают сделать poll и вылетают следом. Предотвращение: 1) Уменьшить `max.poll.records`; 2) Вынести тяжелую обработку в отдельный пул горутин (Worker Pool); 3) Увеличить `max.poll.interval.ms`.
