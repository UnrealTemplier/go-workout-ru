# Транзакции в Kafka Producer: атомарная запись в несколько топиков и координатор транзакций

## Условие

Используйте **transactions** в producer для атомарной записи в несколько partitions (`BeginTransaction`, `SendOffsetsToTransaction`, `CommitTransaction`).

## Теория

Механика распределенных транзакций в Kafka (Transactional API):
- Паттерн «Consume-Transform-Produce»:
  - Сервис читает сообщение из входного топика `orders`.
  - Преобразует данные и атомарно записывает результаты сразу в два топика: `payments` и `shipments`.
  - Атомарно коммитит оффсет входного сообщения в топик `__consumer_offsets`.
- **Двухфазный коммит (2PC):**
  - Transaction Coordinator (один из брокеров) координирует запись маркеров `COMMIT` или `ABORT`.
  - Консьюмеры в режиме `read_committed` видят сообщения только после успешного вызова `CommitTransaction()`.
  - Если воркер упадет в процессе, все записи будут отброшены (Aborted).

## Решение по шагам

1. Создайте структуру транзакционного продюсера `TransactionalProducer`.
2. Реализуйте методы `BeginTransaction`, `Publish`, `CommitTransaction` и `AbortTransaction`.
3. Смоделируйте успешный коммит в два топика.
4. Проверьте откат изменений при ошибке в середине транзакции.

## Код решения

**`kafka_transactions_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type TxMessage struct {
	Topic   string
	Payload string
}

type KafkaTransactionCoordinator struct {
	inTx       bool
	stagedMsgs []TxMessage
	committed  []TxMessage
}

func (tc *KafkaTransactionCoordinator) BeginTransaction() error {
	if tc.inTx {
		return errors.New("транзакция уже открыта")
	}
	tc.inTx = true
	tc.stagedMsgs = nil
	return nil
}

func (tc *KafkaTransactionCoordinator) Send(topic, payload string) error {
	if !tc.inTx {
		return errors.New("нельзя отправлять вне транзакции")
	}
	tc.stagedMsgs = append(tc.stagedMsgs, TxMessage{Topic: topic, Payload: payload})
	return nil
}

func (tc *KafkaTransactionCoordinator) Commit() error {
	if !tc.inTx {
		return errors.New("нет открытой транзакции")
	}
	tc.committed = append(tc.committed, tc.stagedMsgs...)
	tc.stagedMsgs = nil
	tc.inTx = false
	return nil
}

func (tc *KafkaTransactionCoordinator) Abort() {
	tc.stagedMsgs = nil
	tc.inTx = false
}

func TestKafkaTransactions(t *testing.T) {
	coord := &KafkaTransactionCoordinator{}

	// Сценарий 1: Успешная атомарная запись в топики payments и shipments
	_ = coord.BeginTransaction()
	_ = coord.Send("payments", "Оплата заказа #901")
	_ = coord.Send("shipments", "Доставка заказа #901")
	_ = coord.Commit()

	if len(coord.committed) != 2 {
		t.Fatalf("Ожидалось 2 закоммиченных сообщения: %d", len(coord.committed))
	}

	// Сценарий 2: Аварийный откат (Abort)
	_ = coord.BeginTransaction()
	_ = coord.Send("payments", "Оплата заказа #902")
	coord.Abort()

	if len(coord.committed) != 2 {
		t.Fatalf("Откаченное сообщение не должно попасть в committed: %d", len(coord.committed))
	}

	fmt.Println("Kafka Transactional Producer успешно подтвердил атомарность:")
	fmt.Printf("  • Закоммичено сообщений: %d (payments и shipments записаны атомарно!)\n", len(coord.committed))
	fmt.Println("  • Сбойная транзакция заказа #902 успешно откачена (Abort) без мусорных записей!")
}
```

## Под капотом

Внутри лога Kafka брокер сохраняет транзакционные служебные маркеры (Control Batches) с типами `COMMIT` или `ABORT`. Консьюмеры в режиме `isolation.level = read_committed` останавливают чтение на незавершенных транзакциях (LSO — Last Stable Offset).

## Подводные камни

Забывать указывать `isolation.level: read_committed` на консьюмерах: консьюмеры с дефолтным уровнем `read_uncommitted` будут вычитывать даже те сообщения, которые были отменены вызовом `AbortTransaction()`!

## На собеседовании

**Вопрос с собеседования:** «Что такое Zombie Fencing в Kafka Transactions?»
**Ответ:** Если старый инстанс продюсера завис из-за длинной GC-паузы, а оркестратор запустил новый инстанс с тем же `transactional.id`, брокер инкрементирует счетчик `Epoch`. Когда старый «зомби» очнется и попытается отправить сообщения, брокер отклонит его запросы с ошибкой `ProducerFencedException`, предотвратив порчу данных.
