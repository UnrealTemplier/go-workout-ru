# Оптимизация продюсера через Writer: параметры BatchTimeout, BatchBytes и фоновый сброс

## Условие

Реализуйте **producer**, который отправляет сообщения в topic `orders`. Используйте `Writer` с настройками `BatchTimeout`, `BatchBytes`.

## Теория

Тонкая настройка пакетной отправки в `kafka.Writer`:
- `BatchSize`: максимальное количество сообщений в пакете (например, 100 сообщений).
- `BatchBytes`: максимальный размер пакета в байтах (например, 1048576 байт = 1 МБ).
- `BatchTimeout`: максимальное время ожидания накопления пакета (например, 10 мс).
- Как это работает:
  - Продюсер накапливает сообщения в памяти.
  - Пакет сбрасывается в сеть брокеру, как только выполнится **любое из условий**: либо накопилось 100 сообщений, либо накопился 1 МБ, либо прошло 10 мс.
  - Обеспечивает колоссальную пропускную способность при минимальной сетевой задержке.

## Решение по шагам

1. Создайте структуру конфигурации `BatchingProducerConfig`.
2. Настройте лимиты `BatchSize`, `BatchBytes` и `BatchTimeout`.
3. Смоделируйте отправку по заполнению размера и по таймауту.
4. Протестируйте корректность пакетного сброса.

## Код решения

**`batching_producer_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type BatchingWriterConfig struct {
	Topic        string
	BatchSize    int
	BatchBytes   int64
	BatchTimeout time.Duration
}

type BatchingBuffer struct {
	cfg       BatchingWriterConfig
	buffered  int
	bytesSize int64
	flushed   int
}

func (b *BatchingBuffer) PushMessage(payloadSize int64) (flushedNow bool) {
	b.buffered++
	b.bytesSize += payloadSize

	// Условие сброса по объему или количеству
	if b.buffered >= b.cfg.BatchSize || b.bytesSize >= b.cfg.BatchBytes {
		b.flushed++
		b.buffered = 0
		b.bytesSize = 0
		return true
	}
	return false
}

func TestBatchingProducer(t *testing.T) {
	cfg := BatchingWriterConfig{
		Topic:        "orders",
		BatchSize:    3,
		BatchBytes:   1024,
		BatchTimeout: 10 * time.Millisecond,
	}

	buffer := &BatchingBuffer{cfg: cfg}

	// 1. Отправляем 2 сообщения -> буферизуются
	f1 := buffer.PushMessage(100)
	f2 := buffer.PushMessage(100)
	if f1 || f2 {
		t.Fatal("Первые 2 сообщения не должны вызывать сброс")
	}

	// 2. 3-е сообщение заполняет BatchSize=3 -> сброс пакета в сеть!
	f3 := buffer.PushMessage(100)
	if !f3 || buffer.flushed != 1 {
		t.Fatalf("3-е сообщение обязано инициировать сброс: flushed=%v", f3)
	}

	fmt.Println("Kafka Batching Writer успешно протестирован:")
	fmt.Printf("  • Топик:        %s\n", cfg.Topic)
	fmt.Printf("  • Лимит пачки:  %d сообщений / %d байт\n", cfg.BatchSize, cfg.BatchBytes)
	fmt.Printf("  • Таймаут ожидания: %v\n", cfg.BatchTimeout)
	fmt.Printf("  • Успешных сбросов пакетов: %d\n", buffer.flushed)
}
```

## Под капотом

Батчинг снижает нагрузку на CPU ядра брокера: вместо парсинга заголовков TCP на каждое единичное сообщение брокер принимает одну сжатую пачку из 1000 сообщений, записывая ее в файл за одну операцию `writev`.

## Подводные камни

Устанавливать `BatchTimeout: 0`: это отключает батчинг по времени и заставляет продюсер слать сообщения сразу по одному, снижая пропускную способность в десятки раз.

## На собеседовании

**Вопрос с собеседования:** «Каковы компромиссы при выборе BatchTimeout?»
**Ответ:** Большой `BatchTimeout` (например, 100 мс) позволяет собирать огромные эффективные пачки сообщений, максимизируя Throughput (пропускную способность), но искусственно увеличивает задержку (Latency) доставки до 100 мс. Для интерактивных систем реального времени выбирают баланс 5–20 мс.
