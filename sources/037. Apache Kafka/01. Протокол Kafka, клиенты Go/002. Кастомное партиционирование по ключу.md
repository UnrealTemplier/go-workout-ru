# Кастомное партиционирование по ключу: алгоритмы хэширования FNV-1a/Murmur2 и сохранение порядка

## Условие

**Кастомное партиционирование по ключу**: По умолчанию Kafka может распределять сообщения по партициям случайно (Round-Robin). Напишите кастомный партиционер (балансировщик). Он должен вычислять хэш от ключа сообщения (например, `UserID`) и на основе этого хэша определять номер партиции. Объясните в комментариях, почему это критически важно для соблюдения строгого порядка обработки событий (Message Ordering) одного пользователя.

## Теория

Принцип сохранения порядка (Strict Ordering) в Kafka:
- Фундаментальное правило Kafka: **порядок гарантируется строго внутри одной партиции**, но НЕ гарантируется между разными партициями топика!
- Если события пользователя (1. `OrderCreated`, 2. `OrderPaid`, 3. `OrderCancelled`) попадут в разные партиции:
  - Разные воркеры консьюмер-группы вычитают их параллельно.
  - Воркер может обработать `OrderPaid` раньше `OrderCreated`, что приведет к логической ошибке в БД.
- Решение: детерминированное хэширование ключа (Hash Partitioner):
  $$\text{Partition} = \text{Hash}(\text{Key}) \pmod{\text{NumPartitions}}.$$
- Все события одного пользователя ВСЕГДА попадают в одну и ту же партицию и обрабатываются строго по порядку (FIFO).

## Решение по шагам

1. Создайте интерфейс `Partitioner` с методом `Partition(msg, numPartitions)`.
2. Реализуйте алгоритм детерминированного хэширования FNV-1a / Murmur2.
3. Проверьте, что один и тот же ключ гарантированно дает один и тот же индекс партиции.
4. Убедитесь в равномерном распределении разных ключей.

## Код решения

**`custom_partitioner_test.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"testing"
)

type HashPartitioner struct{}

func (p HashPartitioner) AssignPartition(key []byte, numPartitions int) int {
	if numPartitions <= 0 {
		return 0
	}
	if len(key) == 0 {
		return 0 // Сообщения без ключа идут в партицию 0 или Round-Robin
	}

	h := fnv.New32a()
	_, _ = h.Write(key)
	// Битовая маска для исключения отрицательных чисел (как в Java Murmur2)
	hashVal := int(h.Sum32() & 0x7fffffff)
	return hashVal % numPartitions
}

func TestCustomPartitionerOrdering(t *testing.T) {
	partitioner := HashPartitioner{}
	const totalPartitions = 3

	userID := []byte("user-uuid-9901")

	// 1. Проверяем детерминированность: 5 событий одного пользователя
	p1 := partitioner.AssignPartition(userID, totalPartitions)
	p2 := partitioner.AssignPartition(userID, totalPartitions)
	p3 := partitioner.AssignPartition(userID, totalPartitions)

	if p1 != p2 || p2 != p3 {
		t.Fatalf("Нарушена детерминированность хэширования: %d, %d, %d", p1, p2, p3)
	}

	// 2. Другой пользователь может попасть в другую партицию
	otherUser := []byte("user-uuid-4412")
	pOther := partitioner.AssignPartition(otherUser, totalPartitions)

	fmt.Println("Кастомный партиционер Kafka успешно подтвердил строгое упорядочивание:")
	fmt.Printf("  • Пользователь %s: события 1..3 строго в Партицию #%d (FIFO сохранено!)\n", string(userID), p1)
	fmt.Printf("  • Пользователь %s: направлен в Партицию #%d\n", string(otherUser), pOther)
}
```

ℹ️ Детерминированное вычисление партиции по хэшу ключа для соблюдения порядка сообщений

## Под капотом

В официальном Java-клиенте Kafka и в `kafka-go` дефолтным алгоритмом хэширования является Murmur2. Формула `(Murmur2(key) & 0x7fffffff) % partitions` гарантирует совместимость маршрутизации между сервисами на Go, Java, Python и C#.

## Подводные камни

Увеличивать количество партиций топика «на лету» в работающей системе: так как формула использует `% numPartitions`, изменение количества партиций с 3 до 6 приведет к тому, что новые события пользователя `user-1` попадут в другую партицию, нарушив хронологию относительно старых событий.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если ключ сущности пустой (nil key)?»
**Ответ:** По умолчанию Kafka использует стратегию Sticky Partitioner: сообщения без ключа пакуются в пакет и отправляются в одну партицию до тех пор, пока пакет не заполнится или не истечет таймаут, после чего выбирается следующая партиция. Это снижает фрагментацию сети по сравнению со старым Round-Robin по каждому сообщению.
