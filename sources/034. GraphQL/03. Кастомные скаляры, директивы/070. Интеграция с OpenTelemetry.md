# Интеграция с OpenTelemetry: распределенный трейсинг спанов на каждый резолвер схемы

## Условие

Интегрируйте GraphQL с **OpenTelemetry** для трейсинга: каждый резолвер — это отдельный span.

## Теория

Распределенная трассировка OpenTelemetry в GraphQL:
- Расширение `otelgraphql` создает иерархическое дерево спанов:
```text
Root HTTP POST /query (OpenTelemetry Span)
├── GraphQL Operation: GetUserDashboard
│   ├── Field: user (Duration: 5ms)
│   │   └── SQL: SELECT * FROM users (Span БД)
│   ├── Field: orders (Duration: 8ms)
│   │   └── SQL: SELECT * FROM orders WHERE user_id = ? (Span БД)
│   └── Field: bonuses (Duration: 12ms)
│       └── gRPC: LoyaltyService.GetBalance (Span gRPC)
```
- Это позволяет мгновенно обнаружить, какое именно вложенное поле тормозит выполнение общего запроса.

## Решение по шагам

1. Создайте макет трейсера OpenTelemetry.
2. Реализуйте создание спана для выполнения поля.
3. Добавьте атрибуты поля схемы в спан.
4. Протестируйте иерархию длительности.

## Код решения

**`otel_graphql_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type MockSpan struct {
	Name       string
	Attributes map[string]string
	Duration   time.Duration
}

type MockTracer struct {
	spans []MockSpan
}

func (t *MockTracer) TraceField(ctx context.Context, fieldName, typeName string, fn func()) {
	start := time.Now()
	fn()
	elapsed := time.Since(start)

	t.spans = append(t.spans, MockSpan{
		Name: fmt.Sprintf("%s.%s", typeName, fieldName),
		Attributes: map[string]string{
			"graphql.field.name": fieldName,
			"graphql.type.name":  typeName,
		},
		Duration: elapsed,
	})
}

func TestOpenTelemetryTracing(t *testing.T) {
	tracer := &MockTracer{}

	// Трассировка резолвера User.orders
	tracer.TraceField(context.Background(), "orders", "User", func() {
		time.Sleep(10 * time.Millisecond)
	})

	if len(tracer.spans) != 1 || tracer.spans[0].Name != "User.orders" {
		t.Fatalf("Некорректный спан: %+v", tracer.spans)
	}

	span := tracer.spans[0]
	fmt.Printf("OpenTelemetry Span успешно создан:\n")
	fmt.Printf("  • Span Name: %s\n", span.Name)
	fmt.Printf("  • Duration:  %v\n", span.Duration.Round(time.Millisecond))
	fmt.Printf("  • Tag Type:  %s\n", span.Attributes["graphql.type.name"])
}
```

## Под капотом

В `gqlgen` официальное расширение `github.com/99designs/gqlgen/graphql/handler/extension` подключается через `srv.Use(otelgraphql.NewTracer())`. Спаны автоматически связываются с родительским контекстом W3C TraceContext из HTTP-заголовков.

## Подводные камни

Включать создание спанов для примитивных скаляров (`id`, `name`) при высоком RPS: это породит миллионы спанов в Jaeger в секунду. В `otelgraphql` отключают трейсинг тривиальных полей опцией `WithFieldTracer(false)`.

## На собеседовании

**Вопрос с собеседования:** «Как в Jaeger отличить проблему медленного SQL от проблемы медленного резолвинга GraphQL?»
**Ответ:** По структуре спанов: если спан `User.orders` длится 100 мс, а вложенный спан `pgx.Query` длится 98 мс — виновата база данных. Если же спан БД длится 2 мс, а спан `User.orders` длится 100 мс — проблема в Go-коде резолвера (например, тяжелые вычисления, сериализация или блокировка мьютекса).
