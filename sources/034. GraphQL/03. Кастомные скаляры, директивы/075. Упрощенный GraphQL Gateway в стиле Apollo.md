# Упрощенный GraphQL Gateway в стиле Apollo Federation: объединение схем и маршрутизация по @key

## Условие

Реализуй **GraphQL Gateway** (Apollo Federation-style, упрощённо):
- User Service: `type User @key(fields: "id") { id: ID! name: String! }`
- Order Service: `type Order { id: ID! userId: ID! user: User! }` — `User` резолвится через federation (запрос к User Service)
- Gateway агрегирует schema'ы, маршрутизирует queries

## Теория

Механика федеративного шлюза (Federated Gateway):
1. Клиент отправляет запрос к шлюзу:
   `query { orders { id user { name } } }`
2. Шлюз анализирует план запроса (Query Plan):
   - Шаг 1: Выполнить запрос к `Order Service` \(\to\) получить список заказов с `userId: "u1"`.
   - Шаг 2: Выполнить запрос к `User Service` \(\to\) передать `representations: [{__typename: "User", id: "u1"}]`.
3. Шлюз склеивает результаты в единое JSON-дерево и отдает клиенту.

## Решение по шагам

1. Создайте модель `OrderServiceMock` и `UserServiceMock`.
2. Реализуйте шлюз-оркестратор `Gateway`.
3. Смоделируйте двухэтапное выполнение федеративного запроса.
4. Проверьте объединение полей заказа и пользователя.

## Код решения

**`federation_gateway_simple_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type User struct {
	ID   string
	Name string
}

type Order struct {
	ID     string
	UserID string
	Total  float64
}

type FederatedOrderView struct {
	OrderID  string
	Total    float64
	UserName string
}

type UserServiceMock struct{}
func (s *UserServiceMock) GetUserByID(id string) *User {
	return &User{ID: id, Name: "Имя Пользователя " + id}
}

type OrderServiceMock struct{}
func (s *OrderServiceMock) GetOrders() []*Order {
	return []*Order{
		{ID: "ord_101", UserID: "usr_5", Total: 3400.0},
	}
}

type FederatedGateway struct {
	users  *UserServiceMock
	orders *OrderServiceMock
}

func (gw *FederatedGateway) QueryOrdersWithUser(ctx context.Context) []*FederatedOrderView {
	// Шаг 1: Запрос к Order Service
	rawOrders := gw.orders.GetOrders()

	// Шаг 2: Резолвинг пользователя в User Service по Federation ключу
	result := make([]*FederatedOrderView, len(rawOrders))
	for i, o := range rawOrders {
		user := gw.users.GetUserByID(o.UserID)
		result[i] = &FederatedOrderView{
			OrderID:  o.ID,
			Total:    o.Total,
			UserName: user.Name,
		}
	}
	return result
}

func TestFederatedGatewaySimple(t *testing.T) {
	gw := &FederatedGateway{
		users:  &UserServiceMock{},
		orders: &OrderServiceMock{},
	}

	views := gw.QueryOrdersWithUser(context.Background())
	if len(views) != 1 || views[0].UserName != "Имя Пользователя usr_5" {
		t.Fatalf("Ошибка федеративного шлюза: %+v", views)
	}

	fmt.Printf("Federation Gateway успешно объединил данные:\n")
	fmt.Printf("  • Заказ:        %s\n", views[0].OrderID)
	fmt.Printf("  • Пользователь: %s (разрешен из User Service!)\n", views[0].UserName)
}
```

ℹ️ Упрощенная реализация двухэтапной склейки данных в GraphQL Gateway

## Под капотом

В полномасштабных системах склейку выполняет Apollo Router, генерируя асинхронный граф задач DAG (Directed Acyclic Graph) для параллельного опроса подграфов.

## Подводные камни

Прямой синхронный сетевой вызов из Order Service в User Service в обход федерации: это создает сильную связность (Tight Coupling) и разрушает автономность подграфов.

## На собеседовании

**Вопрос с собеседования:** «Что такое директива @shareable в Apollo Federation v2?»
**Ответ:** По умолчанию в Federation только один подграф может владеть определенным полем. Директива `@shareable` разрешает нескольким подграфам вычислять одно и то же поле (например, базовые поля `id`, `slug`, `createdAt`), избавляя от лишних межсервисных сетевых вызовов.
