# Связанные типы в схеме: добавление User.posts: [Post!]! и резолвер выборки постов по obj.ID

## Условие

**Связанные типы (Связи один-ко-многим)**: Добавьте в схему тип `Post` (поля `id`, `title`, `body`). Свяжите сущности: добавьте в тип `User` поле `posts: [Post!]!`. Перегенерируйте код. Обратите внимание, что `gqlgen` создаст для структуры `User` кастомный резолвер `Posts`. Напишите в нем логику получения постов конкретного пользователя по его ID.

## Теория

Организация связей графа данных в SDL:
```graphql
type Post {
  id: ID!
  title: String!
  body: String!
}

type User {
  id: ID!
  name: String!
  posts: [Post!]! # Связь 1-to-N
}
```
- Поскольку в Go-структуре модели `User` нет поля `Posts`, `gqlgen` объявляет интерфейс:
```go
type UserResolver interface {
    Posts(ctx context.Context, obj *model.User) ([]*model.Post, error)
}
```
- Разработчик реализует этот метод, получая ID пользователя через `obj.ID`.

## Решение по шагам

1. Создайте модели `User` и `Post`.
2. Реализуйте интерфейс `UserResolver`.
3. Напишите логику фильтрации постов по `obj.ID`.
4. Протестируйте связывание данных.

## Код решения

**`user_posts_relation_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type User struct {
	ID   string
	Name string
}

type Post struct {
	ID     string
	UserID string
	Title  string
	Body   string
}

type UserResolver struct {
	postsDB []*Post
}

func (r *UserResolver) Posts(ctx context.Context, obj *User) ([]*Post, error) {
	// Выборка постов, принадлежащих конкретному пользователю
	var userPosts []*Post
	for _, p := range r.postsDB {
		if p.UserID == obj.ID {
			userPosts = append(userPosts, p)
		}
	}
	return userPosts, nil
}

func TestUserPostsRelation(t *testing.T) {
	r := &UserResolver{
		postsDB: []*Post{
			{ID: "p1", UserID: "usr_10", Title: "Введение в GraphQL", Body: "Текст статьи 1..."},
			{ID: "p2", UserID: "usr_10", Title: "Магия gqlgen", Body: "Текст статьи 2..."},
			{ID: "p3", UserID: "usr_20", Title: "Чужой пост", Body: "Текст..."},
		},
	}

	currentUser := &User{ID: "usr_10", Name: "Григорий"}

	posts, err := r.Posts(context.Background(), currentUser)
	if err != nil {
		t.Fatalf("Ошибка резолвера: %v", err)
	}

	if len(posts) != 2 || posts[0].Title != "Введение в GraphQL" {
		t.Fatalf("Некорректная выборка постов: %+v", posts)
	}

	fmt.Printf("UserResolver.Posts успешно вернул %d поста для пользователя [%s]!\n",
		len(posts), currentUser.Name)
}
```

ℹ️ Реализация связи один-ко-многим через кастомный UserResolver.Posts

## Под капотом

Если поле `Posts` не запрошено клиентом (`query { user { name } }`), метод `UserResolver.Posts` вообще не вызывается, экономя такты процессора и обращения к базе.

## Подводные камни

Возвращать посты всех пользователей при пустом `obj.ID`: если `obj.ID == ""`, метод должен вернуть пустой список, иначе возникнет утечка конфиденциальных данных.

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить циклическую перегрузку графа вида user -> posts -> author -> posts -> author...?»
**Ответ:** 1. Ограничение глубины запроса (**Query Depth Limiting**): запросы глубже 5–7 уровней блокируются. 2. Ограничение сложности (**Query Complexity**): каждому полю присваивается вес (например 1 очко за скаляр, 10 очков за список), и если сумма \(> 300\), запрос отклоняется до исполнения.
