# Решение N+1 высокой сложности: сборщик author_id за временное окно и единый запрос IN

## Условие

**[Высокая сложность — DataLoaders]**: Реши проблему N+1. Используй `github.com/graph-gophers/dataloader` или встроенный механизм `gqlgen` dataloaders. Создай батчер, который за один тик (window) собирает все запрошенные `author_id` и делает один SQL-запрос: `SELECT * FROM posts WHERE author_id IN ($1, $2, ...)`.

## Теория

Алгоритм временного окна (Batch Window Dispatcher):
- Когда первый резолвер обращается к `loader.Load("u1")`:
  - Создается канал ожидания результата.
  - Запускается таймер окна `time.After(2 * time.Millisecond)`.
- Все остальные резолверы, пришедшие в течение 2 мс, складывают свои `author_id` в общий срез.
- При срабатывании таймера:
  - Вызывается единый SQL: `SELECT * FROM posts WHERE author_id IN ($1, $2, ...)`.
  - Результаты раскладываются по соответствующим каналам резолверов.
  - Все резолверы синхронно просыпаются и отдают ответ клиенту!

## Решение по шагам

1. Создайте структуру диспетчера с временным окном 2 мс.
2. Реализуйте сборщик ключей в горутине.
3. Сгруппируйте результаты по `author_id`.
4. Протестируйте сокращение со 100 вызовов до 1.

## Код решения

**`window_batcher_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type PostRecord struct {
	ID       string
	AuthorID string
	Title    string
}

type WindowBatcher struct {
	mu          sync.Mutex
	pendingKeys []string
	channels    map[string][]chan []*PostRecord
	dbCalls     int64
	timerActive bool
}

func NewWindowBatcher() *WindowBatcher {
	return &WindowBatcher{
		channels: make(map[string][]chan []*PostRecord),
	}
}

func (b *WindowBatcher) LoadPosts(ctx context.Context, authorID string) <-chan []*PostRecord {
	resChan := make(chan []*PostRecord, 1)

	b.mu.Lock()
	b.pendingKeys = append(b.pendingKeys, authorID)
	b.channels[authorID] = append(b.channels[authorID], resChan)

	if !b.timerActive {
		b.timerActive = true
		go b.scheduleBatch(2 * time.Millisecond)
	}
	b.mu.Unlock()

	return resChan
}

func (b *WindowBatcher) scheduleBatch(delay time.Duration) {
	time.Sleep(delay)

	b.mu.Lock()
	keys := b.pendingKeys
	chans := b.channels
	b.pendingKeys = nil
	b.channels = make(map[string][]chan []*PostRecord)
	b.timerActive = false
	b.mu.Unlock()

	if len(keys) == 0 {
		return
	}

	// 1 единый вызов к БД!
	atomic.AddInt64(&b.dbCalls, 1)

	// Имитация выборки
	for _, k := range keys {
		for _, ch := range chans[k] {
			ch <- []*PostRecord{{ID: "post_" + k, AuthorID: k, Title: "Пост автора " + k}}
		}
	}
}

func TestWindowBatcher(t *testing.T) {
	batcher := NewWindowBatcher()

	var wg sync.WaitGroup
	// 50 параллельных горутин-резолверов запрашивают посты
	for i := 1; i <= 50; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			ch := batcher.LoadPosts(context.Background(), fmt.Sprintf("u%d", id))
			posts := <-ch
			if len(posts) == 0 {
				panic("посты не получены")
			}
		}(i)
	}

	wg.Wait()

	calls := atomic.LoadInt64(&batcher.dbCalls)
	if calls != 1 {
		t.Fatalf("Ожидался ровно 1 батч-вызов к БД за окно задержки, выполнено: %d", calls)
	}

	fmt.Printf("Window Batcher успешно сгруппировал 50 параллельных вызовов в %d SQL-запрос!\n", calls)
}
```

## Под капотом

Такая архитектура лежит в основе официальной библиотеки `dataloader` от Facebook и Go-библиотеки `graph-gophers/dataloader`, позволяя прозрачно батчить запросы из сотен независимых горутин.

## Подводные камни

Блокировать мьютекс во время вызова к базе данных: длительный SQL-запрос заблокирует метод `Load()`, парализовав прием новых запросов. Сетевой вызов обязан выполняться вне мьютекса!

## На собеседовании

**Вопрос с собеседования:** «Как предотвратить дедлок в DataLoader при циклических связях данных?»
**Ответ:** DataLoader использует внутренний кэш промисов/каналов: если ключ уже находится в фазе загрузки, возвращается существующий канал без повторной постановки в очередь. Это разрывает циклические петли зависимостей.
