# Apollo Federation v2: архитектура Federated Subgraphs и объединение по ключу @key(fields)

## Условие

Настройте **Apollo Federation**: разделите вашу схему на несколько "subgraph" сервисов (Users, Products, Orders) и объедините их через Federation Gateway.

## Теория

Принципы архитектуры Apollo Federation v2:
- Монолитный GraphQL API не масштабируется на 50 независимых продуктовых команд.
- **Federation разбивает API на независимые подграфы (Subgraphs):**
  1. `Users Subgraph`: владеет типом `User` с ключом `@key(fields: "id")`.
  2. `Orders Subgraph`: расширяет тип `User`, добавляя поле `orders: [Order!]!`.
  3. `Products Subgraph`: владеет товарами.
- **Federation Gateway (Apollo Router на Rust):**
  - Скачивает схемы подграфов.
  - Строит глобальный план запроса (Query Plan).
  - Направляет вызовы к нужным подграфам и бесшовно склеивает JSON для клиента!

## Решение по шагам

1. Опишите схему подграфа с директивой `@key`.
2. Опишите расширение сущности в другом сервисе.
3. Реализуйте резолвер сущности `__resolveReference` в Go.
4. Протестируйте федеративное склеивание данных.

## Код решения

**`users_subgraph.graphqls`**

```graphql
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.0",
        import: ["@key", "@shareable"])

type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
}
```

ℹ️ Схема подграфа Users с объявлением первичного ключа @key(fields: "id")

**`orders_subgraph.graphqls`**

```graphql
extend schema
  @link(url: "https://specs.apollo.dev/federation/v2.0",
        import: ["@key"])

# Расширение внешнего типа User из подграфа Users
type User @key(fields: "id") {
  id: ID!
  orders: [Order!]!
}

type Order {
  id: ID!
  total: Float!
}
```

ℹ️ Схема подграфа Orders, расширяющая User новыми полями orders

**`federation_reference_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type UserEntity struct {
	ID   string
	Name string
}

// Резолвер сущности Federation: вызывается шлюзом Apollo Router по ссылке { __typename: "User", id: "101" }
func ResolveUserReference(ctx context.Context, representation map[string]any) (*UserEntity, error) {
	id, ok := representation["id"].(string)
	if !ok {
		return nil, fmt.Errorf("отсутствует ключ id в representation")
	}

	return &UserEntity{
		ID:   id,
		Name: "Федеративный Пользователь " + id,
	}, nil
}

func TestFederationReference(t *testing.T) {
	rep := map[string]any{
		"__typename": "User",
		"id":         "usr_fed_99",
	}

	user, err := ResolveUserReference(context.Background(), rep)
	if err != nil || user.ID != "usr_fed_99" {
		t.Fatalf("Ошибка резолвинга федеративной сущности: %v", err)
	}

	fmt.Printf("Сущность успешно восстановлена по Federation ключу: %+v\n", user)
}
```

ℹ️ Реализация Entity Resolver (__resolveReference) для Apollo Federation

## Под капотом

Шлюз Apollo Router отправляет в подграф специальный запрос `_entities(representations: [...])`. Подграф использует `representation` для быстрого пакетного поиска сущностей по первичному ключу `@key`.

## Подводные камни

Изменять тип первичного ключа в директиве `@key` между подграфами: если в Users `id: ID!`, а в Orders `id: String!`, компилятор федерации выдаст ошибку несовместимости схемы.

## На собеседовании

**Вопрос с собеседования:** «Чем Apollo Router на Rust превосходит старый Apollo Gateway на Node.js?»
**Ответ:** Apollo Router написан на Rust, обрабатывает GraphQL запросы с задержкой менее 50 микросекунд, потребляет в 10 раз меньше оперативной памяти и выдерживает более 100 000 RPS на одном поде благодаря нулевым аллокациям и отсутствию сборщика мусора JavaScript.
