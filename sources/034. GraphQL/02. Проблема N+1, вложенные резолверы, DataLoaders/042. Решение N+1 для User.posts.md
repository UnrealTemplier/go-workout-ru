# Решение N+1 для User.posts: группировка запросов в WHERE user_id IN и сокращение вызовов до 2

## Условие

**Решение проблемы N+1 (Data Loaders)**: * Напишите запрос, который выбирает список всех пользователей, а для каждого пользователя запрашивает его посты.
* Добавьте логирование SQL/БД-запросов. Обратите внимание, как для списка из \(N\) пользователей ваша программа делает \(1\) запрос на список пользователей и \(N\) отдельных запросов на получение постов для каждого (проблема N+1).
* Интегрируйте библиотеку DataLoader (например, `github.com/graph-gophers/dataloader` или встроенные средства `gqlgen`). Настройте батчинг (группировку) запросов: программа должна собрать все ID пользователей за один проход, сделать ровно один запрос вида `WHERE user_id IN (...)` к базе данных и распределить результаты по пользователям. Убедитесь, что количество запросов к БД сократилось до двух.

## Теория

Двухэтапная выборка графа данных в GraphQL:
- Этап 1: Корневой резолвер `users` выполняет:
  `SELECT id, name FROM users` \(\to\) возвращает список из \(N\) записей (1-й запрос).
- Этап 2: DataLoader собирает все \(N\) идентификаторов и выполняет:
  `SELECT id, title, user_id FROM posts WHERE user_id IN ('1', '2', ..., 'N')` \(\to\) (2-й запрос).
- Связывание: полученные посты группируются по `user_id` в Go-памяти за \(O(M)\).
- Суммарно для выборки сотен пользователей и тысяч постов выполняется **строго 2 запроса** к базе данных!

## Решение по шагам

1. Создайте счетчик запросов к хранилищу.
2. Реализуйте загрузку пользователей и батч-загрузку постов.
3. Проверьте группировку постов по пользователям.
4. Докажите сокращение числа запросов ровно до 2.

## Код решения

**`two_queries_dataloader_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"testing"
)

type User struct {
	ID   string
	Name string
}

type Post struct {
	ID     string
	UserID string
	Title  string
}

type DatabaseService struct {
	sqlCount int64
}

func (db *DatabaseService) FetchUsers(ctx context.Context) []*User {
	atomic.AddInt64(&db.sqlCount, 1)
	return []*User{
		{ID: "usr_1", Name: "Олег"},
		{ID: "usr_2", Name: "Ирина"},
		{ID: "usr_3", Name: "Виктор"},
	}
}

func (db *DatabaseService) BatchFetchPostsForUsers(ctx context.Context, userIDs []string) map[string][]*Post {
	atomic.AddInt64(&db.sqlCount, 1) // Ровно 1 батч-запрос!
	allPosts := []*Post{
		{ID: "p1", UserID: "usr_1", Title: "Пост 1 Олега"},
		{ID: "p2", UserID: "usr_1", Title: "Пост 2 Олега"},
		{ID: "p3", UserID: "usr_2", Title: "Пост Ирины"},
	}

	grouped := make(map[string][]*Post)
	for _, p := range allPosts {
		grouped[p.UserID] = append(grouped[p.UserID], p)
	}
	return grouped
}

func TestTwoQueriesDataLoader(t *testing.T) {
	db := &DatabaseService{}

	// 1-й запрос: пользователи
	users := db.FetchUsers(context.Background())

	// Собираем ID для DataLoader
	uids := make([]string, len(users))
	for i, u := range users {
		uids[i] = u.ID
	}

	// 2-й запрос: все посты разом через DataLoader
	postsMap := db.BatchFetchPostsForUsers(context.Background(), uids)

	totalSQL := atomic.LoadInt64(&db.sqlCount)
	if totalSQL != 2 {
		t.Fatalf("Ожидалось ровно 2 запроса, выполнено: %d", totalSQL)
	}

	fmt.Println("Проблема N+1 ликвидирована:")
	fmt.Printf("  • Пользователей: %d\n", len(users))
	fmt.Printf("  • Постов у Олега: %d\n", len(postsMap["usr_1"]))
	fmt.Printf("  • Постов у Ирины: %d\n", len(postsMap["usr_2"]))
	fmt.Printf("  • Всего запросов к БД: %d (вместо %d!)\n", totalSQL, 1+len(users))
}
```

ℹ️ Сокращение обращений к СУБД с 1+N до 2 с помощью батчинга

## Под капотом

Сложность алгоритма связывания в Go составляет \(O(N + M)\), где \(N\) — число пользователей, а \(M\) — число постов. Это в тысячи раз быстрее, чем многократные сетевые TCP-запросы к СУБД.

## Подводные камни

Забывать, что у пользователя может быть 0 постов: если в `postsMap` нет ключа, резолвер должен вернуть пустой срез `[]*Post{}`, а не падать с `nil pointer dereference`.

## На собеседовании

**Вопрос с собеседования:** «Каковы ограничения конструкции WHERE id IN (...) при 100 000 элементов?»
**Ответ:** Большинство СУБД (PostgreSQL, MySQL, Oracle) имеют лимит на количество параметров в одном запросе (например, 65 535 параметров в PostgreSQL). Если пачка превышает лимит, DataLoader настраивают на разбиение (Chunking): запросы отправляются порциями по 1 000–5 000 элементов.
