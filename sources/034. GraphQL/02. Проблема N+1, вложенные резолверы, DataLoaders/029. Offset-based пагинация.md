# Offset-based пагинация: users(limit: Int, offset: Int) и проблема деградации производительности

## Условие

Реализуй **Pagination** (offset-based): `users(limit: Int, offset: Int): [User!]!`. Верни `totalCount` через отдельный query или в payload. Обсуди проблемы offset-пагинации (performance при больших offset'ах).

## Теория

Архитектура Offset-Based пагинации:
- Запрос: `users(limit: 20, offset: 40)` (третья страница по 20 элементов).
- В SQL транслируется как: `SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 40`.
- **Проблема производительности при больших смещениях:**
  - При `OFFSET 1000000 LIMIT 20` СУБД (PostgreSQL / MySQL) вынуждена прочитать и отсканировать **1 000 020 строк**, отбросить первый миллион и отдать клиенту только 20 строк!
  - Дисковая подсистема испытывает колоссальную нагрузку, время ответа деградирует с 1 мс до 5–10 секунд.
- **Проблема сдвига данных (Data Drifting):** если во время чтения пользователь удалил или добавил запись, на следующей странице клиент увидит дубликат строки или пропустит запись.

## Решение по шагам

1. Создайте структуру ответа с данными и общим счетчиком `totalCount`.
2. Реализуйте метод выборки со срезом по слайсу (эмуляция LIMIT/OFFSET).
3. Задайте значения по умолчанию для limit и offset.
4. Проверьте корректность разбиения на страницы.

## Код решения

**`offset_pagination_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type User struct {
	ID   int
	Name string
}

type UsersPayload struct {
	TotalCount int
	Users      []*User
}

func PaginateUsers(ctx context.Context, allUsers []*User, limit, offset *int) UsersPayload {
	total := len(allUsers)

	l := 10 // default limit
	if limit != nil && *limit > 0 {
		l = *limit
		if l > 100 { // защита от DoS
			l = 100
		}
	}

	o := 0 // default offset
	if offset != nil && *offset > 0 {
		o = *offset
	}

	if o >= total {
		return UsersPayload{TotalCount: total, Users: []*User{}}
	}

	end := o + l
	if end > total {
		end = total
	}

	return UsersPayload{
		TotalCount: total,
		Users:      allUsers[o:end],
	}
}

func TestOffsetPagination(t *testing.T) {
	users := make([]*User, 50)
	for i := 0; i < 50; i++ {
		users[i] = &User{ID: i + 1, Name: fmt.Sprintf("User #%d", i+1)}
	}

	// Страница 2: limit=10, offset=10
	l, o := 10, 10
	res := PaginateUsers(context.Background(), users, &l, &o)

	if res.TotalCount != 50 || len(res.Users) != 10 {
		t.Fatalf("Некорректная пагинация: %+v", res)
	}

	if res.Users[0].ID != 11 || res.Users[9].ID != 20 {
		t.Fatalf("Неверный диапазон элементов: first=%d, last=%d", res.Users[0].ID, res.Users[9].ID)
	}

	fmt.Printf("Offset-пагинация успешна: Total=%d, Выбрано=%d (IDs: %d..%d)\n",
		res.TotalCount, len(res.Users), res.Users[0].ID, res.Users[9].ID)
}
```

## Под капотом

Для устранения проблем Offset-пагинации в HighLoad системах используют **Keyset / Cursor Pagination**: `WHERE id > last_seen_id ORDER BY id LIMIT 20`, работающую строго по индексу за \(O(\log N)\) при любой глубине страниц.

## Подводные камни

Не ограничивать максимальный `limit`: если клиент передаст `limit: 1000000`, сервер выделит гигабайты памяти под структуры и упадет по OOM (Out Of Memory).

## На собеседовании

**Вопрос с собеседования:** «Почему SELECT COUNT(*) для поля totalCount считается антипаттерном в высоконагруженных таблицах PostgreSQL?»
**Ответ:** Из-за многоверсионности (MVCC) PostgreSQL не хранит счетчик строк в метаданных. `SELECT COUNT(*)` вынужден сканировать всю таблицу или весь индекс, что на таблицах от 10 миллионов строк занимает секунды. Для общего счетчика в HighLoad используют приближенные значения (`reltuples` из `pg_class`) или счетчик в Redis.
