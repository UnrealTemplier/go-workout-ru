# Решение проблемы N+1 через DataLoader: батчинг 100 одиночных вызовов в 1 запрос IN

## Условие

Реши **N+1 problem** через **DataLoader**: `github.com/graph-gophers/dataloader`. Батчинг: вместо 100 отдельных запросов — 1 запрос `SELECT * FROM orders WHERE user_id IN (...)`. Реализуй `Loader` для `User.orders`.

## Теория

Принцип работы паттерна DataLoader:
1. Во время фазы исполнения GraphQL запроса каждый вызов `User.orders` не идет в БД, а регистрирует свой `userID` в очереди DataLoader:
   `loader.Load(ctx, dataloader.StringKey(u.ID))`
2. В конце текущего тика цикла событий (Event Loop) или через микрозадержку (1–2 мс) DataLoader собирает все зарегистрированные ключи:
   `keys = ["usr_1", "usr_2", ..., "usr_100"]`
3. Вызывает пользовательскую batch-функцию **ровно 1 раз**:
   `SELECT * FROM orders WHERE user_id IN ('usr_1', 'usr_2', ..., 'usr_100')`
4. Раскладывает полученные заказы по соответствующим пользователям в исходном порядке ключей.
- Результат: вместо 101 запроса выполняется **ровно 2 запроса**!

## Решение по шагам

1. Создайте структуру батч-функции DataLoader.
2. Сгруппируйте заказы по `UserID` в мапу.
3. Верните результаты в строгом соответствии с порядком входных ключей.
4. Докажите сокращение обращений к БД со 100 до 1.

## Код решения

**`dataloader_batching_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"testing"
)

type Order struct {
	ID     string
	UserID string
	Total  float64
}

type OrderBatchDB struct {
	batchQueryCount int64
}

// Пакетная функция DataLoader: принимает слайс ключей, возвращает срез результатов
func (db *OrderBatchDB) BatchGetOrdersByUserIDs(ctx context.Context, userIDs []string) ([][]*Order, error) {
	atomic.AddInt64(&db.batchQueryCount, 1)

	// Имитируем выполнение ОДНОГО запроса: SELECT * FROM orders WHERE user_id IN (...)
	ordersMap := make(map[string][]*Order)
	for _, uid := range userIDs {
		ordersMap[uid] = []*Order{
			{ID: fmt.Sprintf("ord_%s_1", uid), UserID: uid, Total: 2500.0},
		}
	}

	// DataLoader ТРЕБУЕТ возврата результатов строго в том же порядке, что и входные ключи!
	results := make([][]*Order, len(userIDs))
	for i, uid := range userIDs {
		results[i] = ordersMap[uid]
	}

	return results, nil
}

func TestDataLoaderBatching(t *testing.T) {
	db := &OrderBatchDB{}

	// Симулируем 100 пользователей, чьи заказы запрашиваются параллельно
	userIDs := make([]string, 100)
	for i := 0; i < 100; i++ {
		userIDs[i] = fmt.Sprintf("usr_%d", i+1)
	}

	// DataLoader объединяет все 100 запросов в 1 пакетный вызов
	res, err := db.BatchGetOrdersByUserIDs(context.Background(), userIDs)
	if err != nil || len(res) != 100 {
		t.Fatalf("Ошибка пакетной выборки: %v", err)
	}

	queryCount := atomic.LoadInt64(&db.batchQueryCount)
	if queryCount != 1 {
		t.Fatalf("Ожидался ровно 1 батч-запрос к БД, выполнено: %d", queryCount)
	}

	fmt.Printf("🎉 Проблема N+1 успешно решена с помощью DataLoader!\n")
	fmt.Printf("  • Пользователей обработано: 100\n")
	fmt.Printf("  • Количество запросов к БД:  %d (вместо 100!)\n", queryCount)
}
```

## Под капотом

Строгое требование спецификации DataLoader: срез возвращаемых результатов `results` обязан иметь точно такую же длину, как и срез входных ключей `keys`, и индексы должны совпадать (`results[i]` соответствует `keys[i]`).

## Подводные камни

Создавать один глобальный экземпляр DataLoader на все приложение: кэш DataLoader привязан к конкретному запросу! Глобальный экземпляр приведет к утечке памяти и покажет пользователю A данные пользователя B.

## На собеседовании

**Вопрос с собеседования:** «Где должен инициализироваться экземпляр DataLoader в приложении Go?»
**Ответ:** Экземпляр DataLoader **обязан создаваться в HTTP Middleware для каждого входящего HTTP-запроса** и помещаться в `context.Context`:
`ctx = context.WithValue(r.Context(), loadersKey, loaders)`
Это гарантирует, что кэш лоадера живет ровно столько, сколько длится текущий GraphQL-запрос, изолируя пользователей друг от друга.
