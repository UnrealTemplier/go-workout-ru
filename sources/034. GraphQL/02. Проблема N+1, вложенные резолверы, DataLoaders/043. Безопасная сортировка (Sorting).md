# Безопасная сортировка (Sorting): enum UserSort и валидация полей ORDER BY по белому списку

## Условие

Реализуй **Sorting**: `users(sort: UserSort!): [User!]!`, `enum UserSort { NAME_ASC NAME_DESC CREATED_AT_ASC CREATED_AT_DESC }`. Применяй `ORDER BY` в SQL. Валидируй sort-поле против whitelist.

## Теория

Защита от SQL-инъекций при сортировке в GraphQL:
- В SQL невозможно параметризовать имя колонки или направление сортировки через позиционные плейсхолдеры (`ORDER BY $1 $2` завершится синтаксической ошибкой SQL-парсера).
- **Решение:**
  1. В GraphQL схеме объявляется строгий `enum UserSort`.
  2. В Go создается статический белый список (Whitelist), сопоставляющий значение перечисления с безопасным SQL-фрагментом.
  3. Если переданное значение отсутствует в белом списке, запрос отклоняется.

## Решение по шагам

1. Объявите enum `UserSort`.
2. Создайте безопасную карту маппинга в SQL выражения.
3. Напишите генератор SQL-запроса с сортировкой.
4. Протестируйте защиту от невалидных значений.

## Код решения

**`sorting_whitelist_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type UserSort string

const (
	UserSortNameAsc       UserSort = "NAME_ASC"
	UserSortNameDesc      UserSort = "NAME_DESC"
	UserSortCreatedAtAsc  UserSort = "CREATED_AT_ASC"
	UserSortCreatedAtDesc UserSort = "CREATED_AT_DESC"
)

// Белый список допустимых SQL фрагментов
var sortWhitelist = map[UserSort]string{
	UserSortNameAsc:       "ORDER BY name ASC",
	UserSortNameDesc:      "ORDER BY name DESC",
	UserSortCreatedAtAsc:  "ORDER BY created_at ASC",
	UserSortCreatedAtDesc: "ORDER BY created_at DESC",
}

func BuildSortedUsersQuery(sort UserSort) (string, error) {
	sqlOrder, ok := sortWhitelist[sort]
	if !ok {
		return "", fmt.Errorf("недопустимый параметр сортировки: %s", sort)
	}

	return fmt.Sprintf("SELECT id, name, created_at FROM users %s", sqlOrder), nil
}

func TestSortingWhitelist(t *testing.T) {
	// 1. Валидная сортировка
	q1, err1 := BuildSortedUsersQuery(UserSortNameAsc)
	if err1 != nil || q1 != "SELECT id, name, created_at FROM users ORDER BY name ASC" {
		t.Fatalf("Ошибка формирования запроса: %v, %s", err1, q1)
	}

	// 2. Невалидная попытка инъекции
	_, err2 := BuildSortedUsersQuery("name; DROP TABLE users;--")
	if err2 == nil {
		t.Fatal("Ожидался отказ для невалидного значения сортировки")
	}

	fmt.Printf("Безопасный SQL с сортировкой успешно сформирован:\n  %s\n", q1)
	fmt.Println("Попытка передачи произвольного SQL успешно заблокирована белым списком!")
}
```

## Под капотом

Использование перечислений `enum` в схеме исключает 99% некорректных значений еще на этапе валидации парсером GraphQL, а белый список в Go защищает рантайм на уровне эшелонированной обороны (Defense in Depth).

## Подводные камни

Конкатенировать пользовательские строки прямо в `ORDER BY`: `fmt.Sprintf("ORDER BY %s", userColumn)` — классическая брешь SQL Injection.

## На собеседовании

**Вопрос с собеседования:** «Как поддержать сортировку NULL-значений в PostgreSQL через GraphQL?»
**Ответ:** В enum добавляют флаг или опции `NULLS_FIRST` / `NULLS_LAST`:
`NAME_ASC_NULLS_LAST` \(\to\) `ORDER BY name ASC NULLS LAST`.
По умолчанию в PostgreSQL при `ASC` значения NULL идут в конце, а при `DESC` — в начале, что часто удивляет фронтенд-разработчиков.
