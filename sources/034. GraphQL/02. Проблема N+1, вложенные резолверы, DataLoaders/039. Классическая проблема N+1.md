# Классическая проблема N+1: стресс-тест латентности при 100 постах и 101 сетевом запросе

## Условие

**Классическая проблема N+1**: Реализуйте query `posts(limit: 100)`, где для каждого поста вызывается резолвер `author`. Заметьте, что для 100 постов выполняется 101 запрос к БД.

## Теория

Математика сетевой задержки N+1:
- Пусть один сетевой Round-Trip Time (RTT) до базы данных составляет **2 миллисекунды**.
- При одном оптимизированном батч-запросе (`IN (...)`):
  - Время выполнения: \(2\,\text{мс} \times 2 = 4\,\text{мс}\).
- При проблеме N+1 (100 последовательных одиночных запросов):
  - Время выполнения: \(2\,\text{мс} + (100 \times 2\,\text{мс}) = \mathbf{202\,\text{миллисекунды}}\)!
- Задержка ответа увеличивается в **50 раз**, создавая иллюзию «тормозящего бэкенда» на пустом месте.

## Решение по шагам

1. Создайте симулятор сетевой задержки RTT в 1 мс.
2. Смоделируйте выполнение 100 постов через N+1 вызовы.
3. Замерьте суммарное время исполнения.
4. Продемонстрируйте катастрофическую просадку по SLA.

## Код решения

**`n_plus_one_latency_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type LatencySimulator struct {
	rtt time.Duration
}

func (s *LatencySimulator) Query(ctx context.Context) {
	time.Sleep(s.rtt) // Имитация RTT до СУБД
}

func TestNPlusOneLatencyImpact(t *testing.T) {
	sim := &LatencySimulator{rtt: 1 * time.Millisecond}

	// 1. Выборка 100 постов: 1 запрос
	start := time.Now()
	sim.Query(context.Background())

	// 2. N=100 одиночных вызовов автора
	for i := 0; i < 50; i++ { // Берем 50 для быстрого теста
		sim.Query(context.Background())
	}
	elapsed := time.Since(start)

	fmt.Printf("Анализ влияния N+1 на задержку (50 постов с RTT 1ms):\n")
	fmt.Printf("  • Суммарное время ответа: %v\n", elapsed.Round(time.Millisecond))
	fmt.Printf("  • Батч-запрос выполнился бы за: ~2ms!\n")

	if elapsed < 40*time.Millisecond {
		t.Fatal("Слишком быстро для последовательных сетевых вызовов")
	}
}
```

## Под капотом

Даже если запросы к БД выполняются параллельно в горутинах, пул соединений СУБД имеет жесткий лимит (обычно `max_connections = 50..100`). Параллельные запросы выстраиваются в очередь ожидания свободного коннекта, вызывая таймауты `context deadline exceeded`.

## Подводные камни

Считать, что быстрый SSD в базе данных спасет от N+1: проблема N+1 кроется не в чтении с диска, а в сетевых накладных расходах протокола TCP/IP и планировщика операционной системы.

## На собеседовании

**Вопрос с собеседования:** «Как обнаружить проблему N+1 в production автоматически?»
**Ответ:** Через OpenTelemetry трассировку в Jaeger. Запрос с проблемой N+1 выглядит в трейсе как длинная вертикальная «лесенка» из десятков или сотен одинаковых спанов `db.query: SELECT * FROM authors WHERE id = ?`. На основе трейсов настраивают автоматические алерты детекции аномального количества SQL-спанов в одном родительском трейсе.
