# Вложенные резолверы (Nested Resolvers) User.orders: демонстрация катастрофы N+1 запросов

## Условие

Реализуй **Nested resolver**: `type User { ... orders: [Order!]! }`. `orders` — отдельный resolver `func (r *userResolver) Orders(ctx context.Context, obj *model.User) ([]*model.Order, error)`. Покажи N+1 problem: запрос 100 пользователей → 100 запросов заказов.

## Теория

Природа проблемы N+1 в GraphQL:
- Запрос клиента:
```graphql
query {
  users {       # 1 запрос: SELECT * FROM users (вернул 100 пользователей)
    id
    name
    orders {    # Вложенный резолвер User.orders вызывается 100 РАЗ!
      id        # SELECT * FROM orders WHERE user_id = 'usr_1'
      total     # SELECT * FROM orders WHERE user_id = 'usr_2'
    }           # ... еще 98 отдельных SQL-запросов к БД!
  }
}
```
- Итог: \(1 + 100 = 101\) обращение к базе данных!
- База данных захлебывается в сетевых круглых задержках (Round-Trips) и блокировках пула соединений.

## Решение по шагам

1. Создайте счетчик запросов к БД.
2. Смоделируйте наивный вложенный резолвер `Orders(user)`.
3. Выполните выборку для 100 пользователей.
4. Продемонстрируйте совершение ровно 101 запроса к хранилищу.

## Код решения

**`n_plus_one_demo_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"testing"
)

type User struct {
	ID   string
	Name string
}

type Order struct {
	ID     string
	UserID string
	Total  float64
}

type DatabaseMock struct {
	queryCounter int64
}

func (db *DatabaseMock) FetchUsers(ctx context.Context) []*User {
	atomic.AddInt64(&db.queryCounter, 1) // 1-й запрос
	users := make([]*User, 100)
	for i := 0; i < 100; i++ {
		users[i] = &User{ID: fmt.Sprintf("usr_%d", i+1), Name: fmt.Sprintf("User #%d", i+1)}
	}
	return users
}

func (db *DatabaseMock) FetchOrdersForUser(ctx context.Context, userID string) []*Order {
	atomic.AddInt64(&db.queryCounter, 1) // +1 запрос на КАЖДОГО пользователя!
	return []*Order{
		{ID: fmt.Sprintf("ord_%s_1", userID), UserID: userID, Total: 1500.0},
	}
}

func TestNPlusOneCatastrophe(t *testing.T) {
	db := &DatabaseMock{}

	// 1. Корневой резолвер выбирает 100 пользователей
	users := db.FetchUsers(context.Background())

	// 2. Вложенный резолвер User.orders вызывается движком gqlgen для каждого пользователя
	for _, u := range users {
		_ = db.FetchOrdersForUser(context.Background(), u.ID)
	}

	totalQueries := atomic.LoadInt64(&db.queryCounter)
	if totalQueries != 101 {
		t.Fatalf("Ожидался 101 запрос (проблема N+1), выполнено: %d", totalQueries)
	}

	fmt.Printf("Катастрофа N+1 наглядно доказана:\n")
	fmt.Printf("  • Пользователей запрошено:   100\n")
	fmt.Printf("  • Всего запросов к базе:     %d (1 на список + 100 на вложенные заказы!)\n", totalQueries)
}
```

ℹ️ Демонстрация проблемы 101 запроса в наивном вложенном резолвере

**`Терминал`**


## Под капотом

Каждый вызов вложенного резолвера происходит независимо в рамках обхода дерева GraphQL AST. Движок не знает заранее, для скольких пользователей потребуется поле `orders`, поэтому наивный код порождает серию одиночных вызовов.

## Подводные камни

Использовать наивный вложенный резолвер в production: при росте списка до 1 000 пользователей сервер отправит 1 001 запрос к БД, что мгновенно исчерпает пул соединений `pgxpool`.

## На собеседовании

**Вопрос с собеседования:** «Почему в REST API проблема N+1 встречается реже, чем в GraphQL?»
**Ответ:** В REST бэкенд-разработчик контролирует фиксированный эндпоинт (`GET /users-with-orders`) и заранее пишет эффективный `JOIN` (`SELECT * FROM users u LEFT JOIN orders o ON ...`). В GraphQL клиент сам решает, запрашивать ли вложенное поле `orders`, поэтому сервер вынужден либо писать ленивые резолверы, либо использовать батчинг (DataLoader).
