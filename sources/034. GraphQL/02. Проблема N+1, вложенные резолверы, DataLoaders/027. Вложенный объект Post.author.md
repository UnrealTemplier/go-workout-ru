# Вложенный объект Post.author: логирование лавины вызовов и аудит сетевых задержек

## Условие

Добавьте вложенный объект: тип `Post` (id, title, body, author: User!). Запрос `posts` возвращает список постов, резолвер поля `author` лениво подгружает автора (проблема N+1). Покажите проблему в логах.

## Теория

Обратная связь N+1 (Many-to-One):
- Схема:
```graphql
type Post {
  id: ID!
  title: String!
  body: String!
  author: User!
}
type Query {
  posts: [Post!]!
}
```
- Если 50 постов написаны **одним и тем же автором** (например, официальный блог компании), наивный резолвер `Post.Author` выполнит:
  `SELECT * FROM users WHERE id = 'author_1'` — **50 раз подряд для одного и того же ID**!
- Это не просто N+1, это еще и полное дублирование одинаковых запросов.

## Решение по шагам

1. Создайте модели `Post` и `User`.
2. Реализуйте резолвер с логированием каждого запроса автора.
3. Смоделируйте выборку 5 постов.
4. Продемонстрируйте избыточные логи в консоли.

## Код решения

**`post_author_n1_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type User struct {
	ID   string
	Name string
}

type Post struct {
	ID       string
	Title    string
	AuthorID string
}

type PostAuthorResolver struct {
	queryLogs []string
}

func (r *PostAuthorResolver) Author(ctx context.Context, p *Post) (*User, error) {
	logMsg := fmt.Sprintf("SQL: SELECT * FROM users WHERE id = '%s'", p.AuthorID)
	r.queryLogs = append(r.queryLogs, logMsg)
	return &User{ID: p.AuthorID, Name: "Главный Редактор"}, nil
}

func TestPostAuthorNPlusOneLogging(t *testing.T) {
	posts := []*Post{
		{ID: "p1", Title: "Релиз Go 1.24", AuthorID: "usr_editor"},
		{ID: "p2", Title: "Архитектура GraphQL", AuthorID: "usr_editor"},
		{ID: "p3", Title: "Паттерн DataLoader", AuthorID: "usr_editor"},
	}

	r := &PostAuthorResolver{}

	// Имитация вызовов gqlgen для каждого поста
	for _, p := range posts {
		_, _ = r.Author(context.Background(), p)
	}

	if len(r.queryLogs) != 3 {
		t.Fatalf("Ожидалось 3 лога запросов к БД, получено %d", len(r.queryLogs))
	}

	fmt.Println("Аудит логов N+1 запросов к базе данных:")
	for i, l := range r.queryLogs {
		fmt.Printf("  [%d] %s\n", i+1, l)
	}
	fmt.Println("Обнаружено: 3 абсолютно одинаковых запроса к одному и тому же автору!")
}
```

ℹ️ Логирование дублирующихся SQL-запросов в резолвере Post.author

## Под капотом

Без кэширования и дедупликации база данных тратит ресурсы процессора на повторный парсинг SQL-запроса и чтение страниц из буферного пула.

## Подводные камни

Пытаться решить проблему локальным Go-кэшем `sync.Map`: кэш в памяти сервиса быстро рассинхронизируется при обновлении пользователя на другом поде.

## На собеседовании

**Вопрос с собеседования:** «Каковы две главные задачи паттерна DataLoader?»
**Ответ:** 1. **Batching (Пакетирование):** объединение десятков одиночных запросов `id = ?` в один групповой `IN (?, ?, ...)`. 2. **Caching (Мемоизация на время запроса):** если один и тот же `id` запрашивается многократно в рамках одного HTTP-запроса, DataLoader выполняет вызов к БД ровно 1 раз и отдает результат остальным резолверам из локального кэша запроса.
