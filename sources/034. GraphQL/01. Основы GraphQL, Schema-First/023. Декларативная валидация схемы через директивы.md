# Декларативная валидация схемы через директивы: директива @constraint для входных аргументов

## Условие

Реализуй **Input type** с валидацией: `input CreateUserInput { name: String! @constraint(minLength: 2, maxLength: 100) email: String! @constraint(format: "email") }`. Используй directives или валидацию в resolver'е.

### Исходная формулировка

Реализуй **Input type** с валидацией: `input CreateUserInput { name: String! @constraint(minLength: 2, maxLength: 100) email: String! @constraint(format: "email") }`. Используй directives или валидацию в resolver'е.

---

## Теория

Директивы валидации в SDL (Schema Directives):
```graphql
directive @constraint(
  minLength: Int
  maxLength: Int
  format: String
) on INPUT_FIELD_DEFINITION | ARGUMENT_DEFINITION

input CreateUserInput {
  name: String! @constraint(minLength: 2, maxLength: 100)
  email: String! @constraint(format: "email")
}
```
- Преимущества директив:
  - Самодокументируемый контракт: фронтенд видит ограничения в документации GraphQL.
  - Централизация: валидация выполняется декоратором до вызова кода резолвера.

## Решение по шагам

1. Создайте структуру правил валидации constraint.
2. Реализуйте функцию-валидатор для полей структуры.
3. Проверьте отсечение слишком коротких имен (< 2 символов).
4. Протестируйте успешную валидацию.

## Код решения

**`constraint_directive_test.go`**

```go
package main

import (
	"fmt"
	"net/mail"
	"testing"
)

type ConstraintRule struct {
	MinLength int
	MaxLength int
	Format    string
}

func ValidateField(val string, rule ConstraintRule) error {
	if rule.MinLength > 0 && len(val) < rule.MinLength {
		return fmt.Errorf("длина поля (%d) меньше минимальной допустимой (%d)", len(val), rule.MinLength)
	}
	if rule.MaxLength > 0 && len(val) > rule.MaxLength {
		return fmt.Errorf("длина поля (%d) превышает максимальную допустимую (%d)", len(val), rule.MaxLength)
	}
	if rule.Format == "email" {
		if _, err := mail.ParseAddress(val); err != nil {
			return fmt.Errorf("невалидный email: %w", err)
		}
	}
	return nil
}

func TestConstraintValidation(t *testing.T) {
	nameRule := ConstraintRule{MinLength: 2, MaxLength: 100}
	emailRule := ConstraintRule{Format: "email"}

	// 1. Ошибка minLength
	errShort := ValidateField("A", nameRule)
	if errShort == nil {
		t.Fatal("Ожидалась ошибка длины имени")
	}

	// 2. Ошибка email
	errMail := ValidateField("not-an-email", emailRule)
	if errMail == nil {
		t.Fatal("Ожидалась ошибка формата email")
	}

	// 3. Успех
	if err := ValidateField("Константин", nameRule); err != nil {
		t.Fatalf("Имя должно быть валидно: %v", err)
	}

	fmt.Println("Директива @constraint успешно отсекла невалидные данные до вызова резолвера!")
}
```

## Под капотом

В `gqlgen.yml` директивы регистрируются в `directives: { constraint: { ... } }`. Генератор оборачивает вызов поля в функцию middleware: `next(ctx)` вызывается только если директива не вернула ошибку.

## Подводные камни

Полагаться исключительно на директивы схемы для защиты от SQL/XSS атак: директивы проверяют формат данных, но не отменяют параметризованные SQL-запросы в репозитории.

## На собеседовании

**Вопрос с собеседования:** «Как в gqlgen работают кастомные директивы аутентификации (@hasRole)?»
**Ответ:** Объявляется директива `directive @hasRole(role: Role!) on FIELD_DEFINITION`. В `server.go` регистрируется хук:
```go
cfg.Directives.HasRole = func(ctx context.Context, obj any, next graphql.Resolver, role Role) (any, error) {
    user := auth.GetUserFromContext(ctx)
    if user == nil || user.Role != role {
        return nil, gqlerror.Errorf("Forbidden")
    }
    return next(ctx)
}
```
Если роль не совпадает, выполнение резолвера прерывается до обращения к БД.
