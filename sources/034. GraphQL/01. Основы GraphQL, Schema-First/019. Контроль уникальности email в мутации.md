# Контроль уникальности email в мутации: возврат ошибки с кодом EMAIL_ALREADY_EXISTS

## Условие

Реализуйте мутацию `createUser(name: String!, email: String!): User!`. Проверьте, что email уникален (in-memory), при дубликате верните ошибку с расширенным кодом.

## Теория

Предотвращение дублирования уникальных сущностей:
- Перед сохранением пользователя в хранилище проверяется индекс уникальности по полю `email`.
- При обнаружении дубликата сервер возвращает GraphQL ошибку:
  - `code: "EMAIL_ALREADY_EXISTS"`
  - Понятное пользователю сообщение на русском языке.
- Это позволяет фронтенду подсветить поле email красным цветом и предложить восстановить пароль.

## Решение по шагам

1. Создайте потокобезопасное хранилище с индексом email.
2. Реализуйте проверку наличия email перед добавлением.
3. Верните кастомный код ошибки при конфликте.
4. Протестируйте успешное добавление и отклонение дубликата.

## Код решения

**`email_uniqueness_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"

	"github.com/vektah/gqlparser/v2/gqlerror"
)

type User struct {
	ID    string
	Name  string
	Email string
}

type UserStorage struct {
	mu     sync.Mutex
	users  map[string]*User
	emails map[string]string // email -> id
}

func (s *UserStorage) CreateUser(ctx context.Context, name, email string) (*User, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if _, exists := s.emails[email]; exists {
		return nil, &gqlerror.Error{
			Message: fmt.Sprintf("пользователь с адресом '%s' уже зарегистрирован", email),
			Extensions: map[string]any{
				"code":  "EMAIL_ALREADY_EXISTS",
				"email": email,
			},
		}
	}

	newID := fmt.Sprintf("usr_%d", len(s.users)+1)
	u := &User{ID: newID, Name: name, Email: email}
	s.users[newID] = u
	s.emails[email] = newID

	return u, nil
}

func TestEmailUniqueness(t *testing.T) {
	storage := &UserStorage{
		users:  make(map[string]*User),
		emails: make(map[string]string),
	}

	// 1. Первая регистрация успешна
	u1, err1 := storage.CreateUser(context.Background(), "Артём", "artem@yandex.ru")
	if err1 != nil || u1 == nil {
		t.Fatalf("Ошибка первой регистрации: %v", err1)
	}

	// 2. Повторная регистрация с тем же email
	_, err2 := storage.CreateUser(context.Background(), "Артём Дубль", "artem@yandex.ru")
	if err2 == nil {
		t.Fatal("Ожидался конфликт дублирования email")
	}

	gqlErr := err2.(*gqlerror.Error)
	if gqlErr.Extensions["code"] != "EMAIL_ALREADY_EXISTS" {
		t.Fatalf("Некорректный код ошибки: %v", gqlErr.Extensions)
	}

	fmt.Printf("Контроль уникальности сработал корректно: %s (код: %v)\n",
		gqlErr.Message, gqlErr.Extensions["code"])
}
```

## Под капотом

В реальной реляционной БД (PostgreSQL) проверка дубликата опирается на `UNIQUE INDEX (email)`. При ошибке `23505 (unique_violation)` Go-драйвер мапит SQL-ошибку в `EMAIL_ALREADY_EXISTS`.

## Подводные камни

Делать проверку уникальности в коде без уникального индекса в базе: при двух параллельных запросах возникнет состояние гонки (Race Condition), и оба пользователя запишутся с одинаковым email.

## На собеседовании

**Вопрос с собеседования:** «Почему в GraphQL рекомендуется возвращать Union или Result type для мутаций вместо выброса ошибок?»
**Ответ:** Паттерн **Result Pattern**: `union CreateUserResult = User | EmailAlreadyExistsError | ValidationError`. Клиент явно обрабатывает все ожидаемые бизнес-исходы через `... on EmailAlreadyExistsError`, а массив `errors` используется строго для технических аварий.
