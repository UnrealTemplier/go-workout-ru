# Минимальная схема User и query-метод поиска по ID: user(id: ID!): User

## Условие

Напишите простейшую схему с типом `User { id: ID!, name: String!, email: String! }` и query `user(id: ID!): User`.

## Теория

Семантика nullable vs non-null возвращаемых типов:
- В сигнатуре `user(id: ID!): User`:
  - Аргумент `id: ID!` является обязательным (Non-Null): клиент **обязан** передать валидный идентификатор.
  - Возвращаемый тип `User` является **Nullable** (без `!`): если пользователь с таким `id` не найден в базе данных, сервер легитимно возвращает `null` в поле данных (`"data": {"user": null}`) без генерации критической ошибки GraphQL.
- В Go nullable тип модели мапится в указатель: `*model.User`.

## Решение по шагам

1. Опишите метод `User(ctx, id)` в резолвере.
2. Реализуйте поиск в хеш-мапе по ключу.
3. Верните `nil, nil`, если объект не найден.
4. Проверьте поведение при успешном поиске и при отсутствии записи.

## Код решения

**`user_by_id_resolver_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type User struct {
	ID    string
	Name  string
	Email string
}

type QueryResolver struct {
	store map[string]*User
}

func (r *QueryResolver) User(ctx context.Context, id string) (*User, error) {
	u, ok := r.store[id]
	if !ok {
		// В GraphQL отсутствие сущности при типе nullable возвращает (nil, nil)
		return nil, nil
	}
	return u, nil
}

func TestUserByID(t *testing.T) {
	r := &QueryResolver{
		store: map[string]*User{
			"101": {ID: "101", Name: "Иван Смирнов", Email: "ivan@avito.ru"},
		},
	}

	// 1. Поиск существующего
	user, err := r.User(context.Background(), "101")
	if err != nil || user == nil || user.Name != "Иван Смирнов" {
		t.Fatalf("Ожидался пользователь 101, получено: %+v, err: %v", user, err)
	}

	// 2. Поиск отсутствующего
	notFound, err := r.User(context.Background(), "999")
	if err != nil || notFound != nil {
		t.Fatalf("Ожидался nil при отсутствии, получено: %+v, err: %v", notFound, err)
	}

	fmt.Println("Поиск по ID успешно протестирован: существующий возвращен, отсутствующий вернул nil!")
}
```

ℹ️ Корректная обработка отсутствия сущности при nullable возвращаемом типе

## Под капотом

В спецификации GraphQL, если поле nullable возвращает ошибку (`err != nil`), значение поля заменяется на `null`, а ошибка добавляется в массив `"errors": [...]`. Если же возвращается `nil, nil`, ошибка в `"errors"` не пишется.

## Подводные камни

Возвращать ошибку `fmt.Errorf("user not found")` для nullable поля: клиентский фронтенд Apollo/Relay будет считать это сетевой или системной ошибкой и может показать пользователю экран сбоя вместо аккуратного «Пользователь не найден».

## На собеседовании

**Вопрос с собеседования:** «Когда в GraphQL нужно возвращать ошибку, а когда nil в ответе резолвера?»
**Ответ:** `nil` возвращают, когда отсутствие данных является ожидаемым бизнес-сценарием (пользователь не найден, статья еще не опубликована). `error` возвращают при сбоях инфраструктуры (таймаут БД, отказ сети), нарушениях прав доступа (`Unauthorized`/`Forbidden`) или валидации входных аргументов.
