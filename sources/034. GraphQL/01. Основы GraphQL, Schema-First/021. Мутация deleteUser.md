# Мутация deleteUser(id: ID!): Soft delete против Hard delete и архитектурные компромиссы

## Условие

Реализуй **Mutation resolver** `deleteUser(id: ID!): Boolean!`. Soft delete: установи `deleted_at`. Или hard delete — обсуди trade-offs. Верни `true` или ошибку.

## Теория

Сравнение стратегий удаления данных:
1. **Hard Delete (`DELETE FROM users WHERE id = ...`):**
   - Плюсы: мгновенное освобождение места на диске, соответствие требованиям GDPR («Право на забвение»).
   - Минусы: безвозвратная потеря истории, нарушение внешних ключей (Foreign Keys) в заказах и транзакциях.
2. **Soft Delete (`UPDATE users SET deleted_at = NOW() WHERE id = ...`):**
   - Плюсы: возможность мгновенного восстановления, сохранение аудита и целостности связей.
   - Минусы: необходимость добавлять `WHERE deleted_at IS NULL` во все SQL-запросы, разрастание таблиц и индексов.
- В корпоративных бэкендах BigTech стандартным выбором является **Soft Delete** с возможностью фоновой анонимизации данных.

## Решение по шагам

1. Создайте модель пользователя с полем `DeletedAt *time.Time`.
2. Реализуйте метод `DeleteUser` с проставлением временной метки.
3. Исключите удаленных пользователей из последующих выборок.
4. Протестируйте возврат `true` при успешном мягком удалении.

## Код решения

**`soft_delete_resolver_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
	"time"
)

type User struct {
	ID        string
	Name      string
	DeletedAt *time.Time
}

type UserStore struct {
	users map[string]*User
}

func (s *UserStore) DeleteUser(ctx context.Context, id string) (bool, error) {
	u, exists := s.users[id]
	if !exists || u.DeletedAt != nil {
		return false, errors.New("пользователь не найден или уже удален")
	}

	now := time.Now().UTC()
	u.DeletedAt = &now // Soft Delete
	return true, nil
}

func (s *UserStore) GetActiveUsers(ctx context.Context) []*User {
	active := make([]*User, 0)
	for _, u := range s.users {
		if u.DeletedAt == nil {
			active = append(active, u)
		}
	}
	return active
}

func TestSoftDelete(t *testing.T) {
	store := &UserStore{
		users: map[string]*User{
			"1": {ID: "1", Name: "Максим"},
			"2": {ID: "2", Name: "Наталья"},
		},
	}

	// 1. Успешное мягкое удаление
	ok, err := store.DeleteUser(context.Background(), "1")
	if err != nil || !ok {
		t.Fatalf("Ошибка удаления: %v", err)
	}

	// 2. Проверка, что пользователь не отдается в активных
	active := store.GetActiveUsers(context.Background())
	if len(active) != 1 || active[0].ID != "2" {
		t.Fatalf("Пользователь не был отфильтрован: %v", active)
	}

	// 3. Повторная попытка удаления возвращает ошибку
	_, errRepeat := store.DeleteUser(context.Background(), "1")
	if errRepeat == nil {
		t.Fatal("Ожидалась ошибка при повторном удалении")
	}

	fmt.Printf("Soft Delete успешно протестирован: активных пользователей осталось: %d\n", len(active))
}
```

## Под капотом

Для эффективной работы с Soft Delete в PostgreSQL создают частичный индекс (Partial Index): `CREATE INDEX idx_users_active ON users (email) WHERE deleted_at IS NULL`. Это исключает удаленные записи из B-Tree индекса, уменьшая его объем на 90%.

## Подводные камни

Возвращать `null` вместо `Boolean!`: если контракт `Boolean!`, резолвер обязан вернуть строго `true` или `false`. Возврат `nil` вызовет Null Bubbling.

## На собеседовании

**Вопрос с собеседования:** «Как реализовать полное соблюдение GDPR при использовании Soft Delete?»
**Ответ:** По регламенту GDPR персональные данные должны быть удалены по запросу. В архитектуре применяют гибридный подход: при Soft Delete поля `name`, `email`, `phone` затираются псевдонимами (`"Deleted User"`, `"deleted_hash@gdpr.internal"`), а запись с `deleted_at` сохраняется для связности финансовых отчетов.
