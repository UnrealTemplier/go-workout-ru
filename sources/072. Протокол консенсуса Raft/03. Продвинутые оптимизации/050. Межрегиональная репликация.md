# Межрегиональная репликация: Disaster Recovery и Log Shipping в удаленный ДЦ

## Условие

Raft log shipping: Для disaster recovery реализуйте асинхронный ship Raft log в другой datacenter для warm standby (асинхронная репликация без участия в кворуме).

### Исходная формулировка

**Raft log shipping**: Для disaster recovery ship Raft log в другой datacenter для warm standby.

## Теория

Проблема Multi-Datacenter кворумов:
Если включить сервер из удаленного резервного дата-центра (DR Site на другом континенте с RTT 200 мс) в качестве полноправного избирателя (`Voter`):
- Время коммита каждой обычной транзакции вырастет с 1 мс до 200 мс!
Архитектурное решение — Асинхронный Log Shipping / Non-Voting Learners:
1. Основной боевой кластер из 3 узлов размещается в основном регионе (Primary DC) с низким RTT (< 1 мс).
2. В резервном регионе (DR DC) развертывается 4-й узел со статусом **Non-voter (Learner)**.
3. Лидер асинхронно передает записи лога на узел-Learner.
4. Узел-Learner **НЕ участвует в кворуме** и не блокирует транзакции в Primary DC.
5. При физическом уничтожении Primary DC оператор может вручную или через оркестратор перевести Learner в статус Voter и поднять независимый кластер в DR регионе.

## Решение по шагам

1. Создаем структуру DisasterRecoveryLearner со статусом Non-voter.
2. Реализуем метод AsyncShipLogEntry(entry).
3. Моделируем коммит в Primary кластере за 1 мс.
4. Отправляем асинхронную копию в резервный дата-центр без ожидания ACK.
5. Валидируем накат логов на резервном узле без влияния на основной SLA.

## Код решения

**`raft_dr_log_shipping.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type DRLogEntry struct {
	Index uint64
	Data  string
}

type RemoteDataCenterStandby struct {
	mu           sync.Mutex
	regionName   string
	lastReceived uint64
	drLogs       []DRLogEntry
}

func (s *RemoteDataCenterStandby) ReceiveAsyncLog(entry DRLogEntry) {
	// Асинхронное получение логов в резервном ДЦ
	s.mu.Lock()
	defer s.mu.Unlock()

	s.drLogs = append(s.drLogs, entry)
	s.lastReceived = entry.Index
	fmt.Printf("[%s Standby] Appended DR replica log index #%d: '%s'\n",
		s.regionName, entry.Index, entry.Data)
}

type PrimaryClusterLeader struct {
	leaderID  string
	drStandby *RemoteDataCenterStandby
}

func (l *PrimaryClusterLeader) CommitPrimaryAndShipAsync(idx uint64, data string) {
	// 1. Быстрый коммит в основном ДЦ (кворум локальных узлов)
	fmt.Printf("[%s] Primary DC Commit Index #%d: '%s' (Low latency local quorum)\n",
		l.leaderID, idx, data)

	// 2. Асинхронная отправка в DR дата-центр без блокировки основного потока
	entry := DRLogEntry{Index: idx, Data: data}
	go func() {
		// Симулируем задержку трансатлантического оптоволокна (80 мс)
		time.Sleep(80 * time.Millisecond)
		l.drStandby.ReceiveAsyncLog(entry)
	}()
}

func main() {
	drStandby := &RemoteDataCenterStandby{regionName: "DR-Site-Singapore"}
	primary := &PrimaryClusterLeader{
		leaderID:  "Primary-DC-Frankfurt",
		drStandby: drStandby,
	}

	fmt.Println("=== PRIMARY DC TRANSACTION COMMITS (ZERO DR OVERHEAD) ===")
	start := time.Now()

	primary.CommitPrimaryAndShipAsync(101, "ORDER_CREATE_101")
	primary.CommitPrimaryAndShipAsync(102, "PAYMENT_CAPTURE_102")

	elapsed := time.Since(start)
	fmt.Printf("Primary commits finished in %v! (Transactions unblocked without waiting for DR)\n\n", elapsed)

	// Ждем пока асинхронный лог-шиппинг долетит до DR-региона
	time.Sleep(120 * time.Millisecond)

	drStandby.mu.Lock()
	fmt.Printf("\nDR Standby Status: Received %d logs. High Availability disaster recovery ready.\n",
		len(drStandby.drLogs))
	drStandby.mu.Unlock()
}
```

## Под капотом

В `hashicorp/raft` узел в резервном ЦОД регистрируется вызовом `AddNonVoter(id, addr)`. Лидер создает поток репликации к узлу, но при расчете `c.quorum` исключает этот узел из конфигурации. В etcd аналогичная концепция называется `Raft Learner` (добавлена в etcd 3.4).

## Подводные камни

Асинхронная потеря данных при катастрофе (RPO > 0): поскольку логи в DR пересылаются асинхронно, при мгновенном физическом уничтожении Primary ДЦ последние несколько секунд транзакций могут не успеть долететь до DR. Бизнес обязан быть уведомлен о компромиссе между RPO (Recovery Point Objective) и задержкой операций.

## На собеседовании

В: Что такое Raft Learner узел и почему он предпочтительнее Voter узла для Disaster Recovery?
О: Узел Learner реплицирует лог и применяет состояние к FSM, но не имеет права голоса на выборах и не входит в кворум большинства. Это защищает основной кластер от просадок latency из-за медленных удаленных каналов и гарантирует, что сбои в резервном регионе не парализуют работу основного ДЦ.
