# Усечение лога и создание снапшотов: SnapshotThreshold и усечение in-memory логов

## Условие

55. **[Snapshots]**: Настрой `SnapshotThreshold` (например, каждые 1000 логов). Отправь 1000 записей. Убедись, что Raft сбросил лог на диск (создал файл `.snap`) и обрезал in-memory логи.

### Исходная формулировка

**[Snapshots]**: Настрой `SnapshotThreshold` (например, каждые 1000 логов). Отправь 1000 записей. Убедись, что Raft сбросил лог на диск (создал файл `.snap`) и обрезал in-memory логи.

## Теория

Без механизма усечения логов (Log Compaction) WAL непрерывно растет, что неизбежно приводит к двум фатальным проблемам:
1. **Переполнение дискового пространства и оперативной памяти**.
2. **Бесконечное время перезапуска узла**: при рестарте потребуется заново воспроизвести миллионы записей лога с самого начала времен.

В соответствии с секцией 7 Whitepaper Raft, решение — создание снапшотов (Snapshots):
- В определенный момент времени состояние конечного автомата (FSM) сериализуется в компактный образ (Snapshot) на диске.
- Сохраняются метаданные снапшота: `LastIncludedIndex` и `LastIncludedTerm`.
- Все записи лога с индексом \(\le \text{LastIncludedIndex}\) безопасно удаляются (Discard/Truncate) из WAL.
- Параметр `SnapshotThreshold` задает количество закоммиченных записей между автоматическими снапшотами (например, 1000 или 8192). В высоконагруженных системах также используется `SnapshotInterval` по таймеру.

## Решение по шагам

1. Сконфигурируйте структуру метаданных снапшота `SnapshotMeta` (`LastIncludedIndex`, `LastIncludedTerm`).
2. Создайте класс `CompactedLogStore`, управляющий хранением усеченного лога со смещением `firstIndex`.
3. Реализуйте проверку порога `SnapshotThreshold`: при достижении 1000 записей инициируйте процедуру компактификации.
4. Сымитируйте сброс состояния FSM в файл снапшота `.snap` и вызовите `TruncateBefore(index)`.
5. Продемонстрируйте корректный расчет виртуальных индексов лога и освобождение оперативной памяти.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"sync"
)

type SnapshotMeta struct {
	LastIncludedIndex uint64 `json:"last_included_index"`
	LastIncludedTerm  uint64 `json:"last_included_term"`
	DataSize          int    `json:"data_size"`
}

type CompactedLogStore struct {
	mu           sync.RWMutex
	offsetIndex  uint64
	entries      []string
	threshold    int
	lastSnapshot *SnapshotMeta
}

func NewCompactedLogStore(threshold int) *CompactedLogStore {
	return &CompactedLogStore{
		offsetIndex: 0,
		entries:     make([]string, 0),
		threshold:   threshold,
	}
}

func (s *CompactedLogStore) Append(entry string) (uint64, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.entries = append(s.entries, entry)
	currentIndex := s.offsetIndex + uint64(len(s.entries))

	needSnapshot := len(s.entries) >= s.threshold
	return currentIndex, needSnapshot
}

func (s *CompactedLogStore) TakeSnapshot(lastTerm uint64, stateData []byte) (*SnapshotMeta, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if len(s.entries) == 0 {
		return nil, fmt.Errorf("no entries to snapshot")
	}

	lastIndex := s.offsetIndex + uint64(len(s.entries))
	meta := &SnapshotMeta{
		LastIncludedIndex: lastIndex,
		LastIncludedTerm:  lastTerm,
		DataSize:          len(stateData),
	}

	// Truncate logs: discard all in-memory entries up to lastIndex
	s.offsetIndex = lastIndex
	s.entries = make([]string, 0)
	s.lastSnapshot = meta

	return meta, nil
}

func (s *CompactedLogStore) GetEntry(index uint64) (string, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()

	if index <= s.offsetIndex {
		return "", fmt.Errorf("index %d compacted into snapshot (lastIncluded: %d)", index, s.offsetIndex)
	}

	pos := index - s.offsetIndex - 1
	if pos >= uint64(len(s.entries)) {
		return "", fmt.Errorf("index %d out of bounds", index)
	}

	return s.entries[pos], nil
}

func (s *CompactedLogStore) InMemCount() int {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return len(s.entries)
}

func main() {
	const threshold = 1000
	store := NewCompactedLogStore(threshold)

	fmt.Println("--- Ingesting 1,000 log entries ---")
	var lastIdx uint64
	var triggerSnapshot bool

	for i := 1; i <= 1000; i++ {
		cmd := fmt.Sprintf("SET key_%d val_%d", i, i)
		lastIdx, triggerSnapshot = store.Append(cmd)
	}

	fmt.Printf("Last Index: %d, In-Memory Log Size: %d entries\n", lastIdx, store.InMemCount())
	fmt.Printf("Snapshot threshold reached? %t\n", triggerSnapshot)

	if triggerSnapshot {
		dummyFSMState := []byte("FSM_SERIALIZED_STATE_DATA_DUMP_1000_KEYS")
		meta, err := store.TakeSnapshot(1, dummyFSMState)
		if err != nil {
			panic(err)
		}
		var buf bytes.Buffer
		_ = json.NewEncoder(&buf).Encode(meta)
		fmt.Printf("[Disk Sink] Generated .snap file metadata: %s", buf.String())
	}

	fmt.Printf("After Snapshot -> In-Memory Log Size: %d entries (Logs truncated)\n", store.InMemCount())

	// Verifying boundary checks
	fmt.Println("\n--- Querying Log Boundaries ---")
	_, err := store.GetEntry(500)
	fmt.Println("Query Index 500:", err)

	store.Append("SET key_1001 val_1001")
	entry, err := store.GetEntry(1001)
	fmt.Printf("Query Index 1001: '%s' (Error: %v)\n", entry, err)
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 55

## Под капотом

Создание снапшота в `hashicorp/raft` реализовано без остановки обработки входящих запросов:
1. Вызывается интерфейс `FSM.Snapshot()`, который обязан вернуть реализацию `FSMSnapshot`.
2. Метод `FSMSnapshot.Persist(sink raft.SnapshotSink)` выполняется в **фоновой горутине**.
3. Чтобы фоновая горутина не видела последующих мутаций данных, FSM обязан использовать механизм Copy-On-Write (COW) или итератор по иммутабельному срезу данных в памяти.
4. После успешного закрытия `sink.Close()` Raft атомарно записывает маркер завершения снапшота и вызывает `LogStore.DeleteRange(1, meta.Index)`.

## Подводные камни

- **Блокировка FSM на время записи на диск**: Если метод `FSM.Snapshot()` выполняет синхронную запись всего дампа памяти на диск внутри мьютекса, кластер перестанет обрабатывать входящие HTTP-запросы и потеряет лидерство из-за пропуска `HeartbeatTimeout`! Запись на диск должна выполняться строго в `Persist` в отдельной горутине.
- **Слишком частые снапшоты**: Установка слишком маленького `SnapshotThreshold` (например, 10 логов) вызовет колоссальный I/O overhead (disk thrashing) и деградацию производительности.

## На собеседовании

В Яндекс Облаке и Авито часто спрашивают: *«Как фолловер с очень медленной сетью, отставший от лидера на 500 000 записей, догоняет кластер, если лидер уже усек эти 500 000 записей из WAL с помощью снапшота?»*
**Ответ**: Лидер обнаруживает, что `nextIndex` для данного фолловера меньше, чем `firstIndex` в активном WAL лидера. Лидер понимает, что отправить недостающие записи через обычный `AppendEntries` невозможно. Вместо этого лидер переключается на отправку RPC `InstallSnapshot`. Снапшот передается стримингом чанками. Фолловер полностью перезаписывает свое состояние полученным снапшотом, сбрасывает свой лог до `LastIncludedIndex` и затем возвращается к стандартному получению дельта-логов через `AppendEntries`.
