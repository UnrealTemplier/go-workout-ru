# Линеаризуемое чтение с перенаправлением фоловеров (Read-through Leader)

## Условие

Linearizable Reads: Включи чтение через Лидера. Если ты читаешь с Follower'а, он должен либо проксировать запрос Лидеру, либо спросить у Лидера ReadIndex, дождаться применения в FSM и только тогда вернуть результат.

### Исходная формулировка

**[Linearizable Reads]**: Включи чтение через Лидера. Если ты читаешь с Follower'а, он может вернуть устаревшие данные. Используй `raft.VerifyLeader()` или `raft.ReadIndex()` перед чтением из FSM, чтобы гарантировать strong consistency (линейзуемость).

## Теория

Паттерн Follower ReadIndex Forwarding:
Клиент обращается с запросом на чтение к ближайшему фоловеру (например, в том же дата-центре для снижения задержки):
Как фоловер обеспечивает линеаризуемость без чтения устаревших данных:
1. Фоловер отправляет легкий RPC запрос лидеру: `GetReadIndex()`.
2. Лидер подтверждает статус большинства и возвращает фоловеру актуальный `ReadIndex` кластера.
3. Фоловер проверяет: `fsm.appliedIndex >= ReadIndex`.
   - Если его локальная машина состояний отстает, фоловер блокируется и ждет наката недостающих логов от лидера.
4. Как только FSM фоловера применила записи до `ReadIndex`, фоловер отдает значение из своей локальной памяти!
Это разгружает CPU лидера на чтение, сохраняя 100% гарантию Linearizability.

## Решение по шагам

1. Создаем структуру FollowerReadCoordinator с доступом к лидеру.
2. Реализуем метод FollowerLinearizableRead(key).
3. Моделируем запрос к лидеру за ReadIndex.
4. Дожидаемся синхронизации локальной машины состояний.
5. Отдаем результат чтения клиенту без единого дискового вызова.

## Код решения

**`follower_linearizable_read.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type RaftLeaderNode struct {
	commitIndex uint64
}

func (l *RaftLeaderNode) RequestReadIndex() uint64 {
	// Лидер подтверждает кворум и сообщает текущий commitIndex
	return l.commitIndex
}

type RaftFollowerNode struct {
	mu           sync.RWMutex
	appliedIndex uint64
	fsmState     map[string]string
	leader       *RaftLeaderNode
}

func (f *RaftFollowerNode) CatchUpTo(index uint64) {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.appliedIndex = index
	f.fsmState["config:max_batch"] = "2000"
}

func (f *RaftFollowerNode) ReadLinearizable(key string) (string, uint64) {
	// 1. Спрашиваем актуальный ReadIndex у лидера
	readIndex := f.leader.RequestReadIndex()

	// 2. Ждем, пока локальная FSM догонит readIndex
	for {
		f.mu.RLock()
		currentApplied := f.appliedIndex
		f.mu.RUnlock()

		if currentApplied >= readIndex {
			break
		}
		time.Sleep(10 * time.Millisecond)
	}

	// 3. Отдаем из локальной памяти фоловера
	f.mu.RLock()
	defer f.mu.RUnlock()
	return f.fsmState[key], readIndex
}

func main() {
	leader := &RaftLeaderNode{commitIndex: 150}
	follower := &RaftFollowerNode{
		appliedIndex: 148, // Фоловер слегка отстает (на 2 записи)
		fsmState:     map[string]string{"config:max_batch": "1000"},
		leader:       leader,
	}

	// В фоне фоловер догоняет лидера через 30 мс
	go func() {
		time.Sleep(30 * time.Millisecond)
		follower.CatchUpTo(150)
	}()

	fmt.Println("=== FOLLOWER LINEARIZABLE READ WITH READ_INDEX FORWARDING ===")
	start := time.Now()
	val, idx := follower.ReadLinearizable("config:max_batch")
	elapsed := time.Since(start)

	fmt.Printf("Follower successfully returned Linearizable Value: '%s' at ReadIndex: %d (Elapsed: %v)\n",
		val, idx, elapsed)
	fmt.Println("Zero stale reads: Follower strictly waited for FSM sync before serving client.")
}
```

## Под капотом

В `etcd` v3.5 при чтении с фоловера с флагом `WithSerializable() == false` клиент направляет gRPC вызов на фоловер. Фоловер шлет лидеру внутренний RPC `MsgReadIndex`. Получив ответ, фоловер подвешивает клиентский стрим в очереди ожидания `readwaitc` до момента, пока индекс `apply` не сравняется с `ReadIndex`.

## Подводные камни

Зависание чтения на мертвом фоловере: если сетевой канал между лидером и фоловером оборвался, фоловер никогда не догонит `ReadIndex`. Клиентский запрос зависнет. Всегда ограничивайте чтение контекстным дедлайном `context.WithTimeout(ctx, 3*time.Second)`.

## На собеседовании

В: Чем Follower Read выгоднее прямого чтения с Лидера в геораспределенных системах?
О: При глобальном клиенте в Токио и лидере во Франкфурте прямой запрос к лидеру требует RTT 250 мс. При Follower Read токийский фоловер делает один легкий запрос к лидеру за ReadIndex (или использует Lease), а тяжелое тело ответа (например, 10 МБ JSON) клиент вычитывает из локального токийского фоловера за 1 мс, разгружая межконтинентальный канал.
