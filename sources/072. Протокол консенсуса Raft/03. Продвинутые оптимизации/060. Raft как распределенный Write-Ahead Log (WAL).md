### Исходная формулировка

## Теория

В архитектуре современных распределенных платформ данных (Event Sourcing, CQRS, NewSQL) Raft все чаще отделяется от хранения состояния:
**Raft используется исключительно как распределенный, высоконадежный, тотально упорядоченный Write-Ahead Log (Distributed WAL)**.

Концептуальная модель:
1. **Raft Core (Single Source of Truth)**: принимает команды изменения данных, согласовывает их строгий глобальный порядок (`Index: 1, 2, 3...`) и персистирует в защищенный Raft WAL.
2. **FSM Projections (Read Models)**: детерминированные проекторы вычитывают закоммиченный поток логов и асинхронно или синхронно обновляют внешние специализированные хранилища:
   - **PostgreSQL**: реляционная OLTP проекция для транзакционных запросов со связями.
   - **ClickHouse**: колоночная OLAP проекция для молниеносной аналитики.
   - **Elasticsearch**: полнотекстовый индекс.

Связь с Transactional Outbox (Блок 23):
Вместо связки «PostgreSQL + Outbox Table + Debezium CDC» Raft сам выступает в роли неподкупного Outbox-журнала. Если база данных проекции повреждена, ее можно в любой момент пересоздать с нуля простым проигрыванием Raft-лога с индекса 0.

## Решение по шагам

1. Создайте структуру события `OrderPlacedEvent` с порядковым номером Raft-лога `LogIndex`.
2. Реализуйте распределенный WAL Raft, присваивающий монотонные непрерывные индексы.
3. Создайте две независимые проекции: `PostgresRelationalProjection` (индексация по ID) и `ClickHouseAnalyticsProjection` (агрегаты выручки).
4. Продемонстрируйте прогон пачки событий через Raft WAL и параллельное наполнение проекций.
5. Сымитируйте сброс аналитической базы данных и ее полное восстановление (Re-projection) из неизменяемого Raft WAL.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
)

type Event struct {
	Index   uint64  `json:"index"`
	OrderID string  `json:"order_id"`
	UserID  string  `json:"user_id"`
	Amount  float64 `json:"amount"`
}

// 1. Immutable Distributed WAL (Single Source of Truth)
type RaftWAL struct {
	mu      sync.RWMutex
	entries []Event
}

func (w *RaftWAL) Append(orderID, userID string, amount float64) Event {
	w.mu.Lock()
	defer w.mu.Unlock()

	idx := uint64(len(w.entries) + 1)
	evt := Event{Index: idx, OrderID: orderID, UserID: userID, Amount: amount}
	w.entries = append(w.entries, evt)
	return evt
}

func (w *RaftWAL) GetAll() []Event {
	w.mu.RLock()
	defer w.mu.RUnlock()
	copied := make([]Event, len(w.entries))
	copy(copied, w.entries)
	return copied
}

// 2. Projection 1: Simulated PostgreSQL (OLTP)
type PostgresProjection struct {
	mu     sync.RWMutex
	orders map[string]Event
}

func NewPostgresProjection() *PostgresProjection {
	return &PostgresProjection{orders: make(map[string]Event)}
}

func (p *PostgresProjection) Apply(evt Event) {
	p.mu.Lock()
	defer p.mu.Unlock()
	p.orders[evt.OrderID] = evt
}

// 3. Projection 2: Simulated ClickHouse (OLAP Aggregate)
type ClickHouseProjection struct {
	mu           sync.RWMutex
	totalRevenue float64
	orderCount   int
}

func (c *ClickHouseProjection) Apply(evt Event) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.totalRevenue += evt.Amount
	c.orderCount++
}

func (c *ClickHouseProjection) Reset() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.totalRevenue = 0
	c.orderCount = 0
}

func main() {
	wal := &RaftWAL{}
	pgProj := NewPostgresProjection()
	chProj := &ClickHouseProjection{}

	fmt.Println("--- 1. Ingesting Orders into Raft WAL ---")
	e1 := wal.Append("ord-101", "user-1", 1500.50)
	e2 := wal.Append("ord-102", "user-2", 2300.00)
	e3 := wal.Append("ord-103", "user-1", 450.00)

	// Stream to projections
	for _, evt := range []Event{e1, e2, e3} {
		pgProj.Apply(evt)
		chProj.Apply(evt)
	}

	fmt.Printf("PostgreSQL orders count: %d\n", len(pgProj.orders))
	fmt.Printf("ClickHouse total revenue: %.2f руб across %d orders\n", chProj.totalRevenue, chProj.orderCount)

	fmt.Println("\n--- 2. Simulating ClickHouse Data Corruption and Replay ---")
	chProj.Reset()
	fmt.Printf("ClickHouse after accidental drop: %.2f руб\n", chProj.totalRevenue)

	fmt.Println("Re-playing full immutable Raft WAL into ClickHouse...")
	allEvents := wal.GetAll()
	for _, evt := range allEvents {
		chProj.Apply(evt)
	}
	fmt.Printf("ClickHouse after Re-projection: %.2f руб across %d orders (100%% Recovered!)\n",
		chProj.totalRevenue, chProj.orderCount)
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 60

## Под капотом

Архитектурные преимущества выноса проекций из Raft FSM:
1. **Декомпозиция ответственности**: Raft занимается только тем, в чем он непревзойден — распределенным консенсусом порядка байт. Ему не нужны тяжелые индексы B-Tree или колоночные сжатия.
2. **Параллельная проекция**: В отличие от однопоточного классического FSM, разные проекции могут отставать от Raft WAL на несколько миллисекунд и вычитывать логи параллельными пулами воркеров.
3. **Изоляция сбоев**: Если ClickHouse упал под тяжелым аналитическим запросом, Raft продолжает фиксировать транзакции пользователей без просадки доступности.

## Подводные камни

- **Удаление логов до сохранения проекции**: Если Raft произведет компактификацию (Snapshot) и удалит логи из WAL раньше, чем медленная проекция успеет их вычитать, проекция отстанет навсегда (Stale Projection). Решение — хранить `ProjectionAcknowledgedIndex` и запрещать Raft усекать логи ниже этого индекса.
- **Недетерминированные проекции**: Если проекция зависит от внешних API или локального времени, повторное проигрывание лога даст другой результат.

## На собеседовании

В Wildberries и Яндекс Маркете любят кейс: *«Как построить отказоустойчивую финансовую систему с гарантией обработки платежей Exactly-Once и мгновенной аналитикой?»*
**Ответ**: Использовать Raft-лог как распределенный неподкупный журнал финансовых событий (Command Sourcing). Каждая транзакция получает строгий монотонный `RaftIndex`. Транзакционная БД балансов пользователей обновляется первой как первичная проекция. Аналитические витрины ClickHouse подписаны на хвост этого лога и обновляются пакетами. При любых сбоях аудит и реконсиляция проводятся по эталонному Raft WAL.
