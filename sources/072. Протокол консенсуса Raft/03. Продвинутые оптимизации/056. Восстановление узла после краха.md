# Восстановление узла после краха: Snapshot Restore и воспроизведение хвоста лога (Tail Replay)

## Условие

56. **Raft recovery**: После crash узел восстанавливает state из snapshot + log replay.

### Исходная формулировка

**Raft recovery**: После crash узел восстанавливает state из snapshot + log replay.

## Теория

Процесс восстановления упавшего узла (Raft Crash Recovery) строится на комбинации двух источников данных:
1. **Базовый снимок состояния (Latest Snapshot)**: фиксирует состояние конечного автомата на момент времени \(Index = S_{idx}\), исключая необходимость читать терабайты старых логов.
2. **Хвост журнала упреждающей записи (Log Tail Replay)**: содержит все записи с \(Index = S_{idx} + 1 \dots \text{LastLogIndex}\), зафиксированные после создания последнего снимка.

Последовательность шагов при инициализации `raft.NewRaft()`:
1. Сканирование хранилища снапшотов (`SnapshotStore`) на диске и нахождение последнего валидного `.snap` файла.
2. Вызов `FSM.Restore(io.Reader)`: конечному автомату передается поток данных снапшота, восстанавливающий все структуры данных в памяти.
3. Определение `LastIncludedIndex` и установка начального индекса применения `lastApplied = S_{idx}`.
4. Сканирование `LogStore` начиная с \(S_{idx} + 1\).
5. Десериализация и последовательное применение каждой закоммиченной записи к FSM через метод `FSM.Apply(log)`.
6. Перевод узла в роль `Follower` и запуск таймера выборов.

## Решение по шагам

1. Реализуйте функцию сериализации `Snapshot` и восстановления `Restore` для `KVFSM`.
2. Создайте файл журнала записей (Log Store), содержащий записи, часть из которых включена в снапшот, а часть находится в хвосте (tail).
3. Сымитируйте падение процесса (Crash) с очисткой оперативной памяти.
4. Проведите процедуру восстановления: загрузите снимок, примените `Restore`, а затем выполните цикл проигрывания хвоста логов (`Tail Replay`).
5. Убедитесь, что конечное состояние FSM идентично состоянию до падения.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"sync"
)

type LogEntry struct {
	Index uint64 `json:"index"`
	Term  uint64 `json:"term"`
	Cmd   string `json:"cmd"`
}

type MemoryFSM struct {
	mu   sync.RWMutex
	data map[string]string
}

func NewMemoryFSM() *MemoryFSM {
	return &MemoryFSM{data: make(map[string]string)}
}

func (f *MemoryFSM) Apply(cmd string) {
	f.mu.Lock()
	defer f.mu.Unlock()
	var op struct {
		K string `json:"k"`
		V string `json:"v"`
	}
	if err := json.Unmarshal([]byte(cmd), &op); err == nil {
		f.data[op.K] = op.V
	}
}

func (f *MemoryFSM) Snapshot() ([]byte, error) {
	f.mu.RLock()
	defer f.mu.RUnlock()
	return json.Marshal(f.data)
}

func (f *MemoryFSM) Restore(snapshotData []byte) error {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.data = make(map[string]string)
	return json.Unmarshal(snapshotData, &f.data)
}

func (f *MemoryFSM) Dump() map[string]string {
	f.mu.RLock()
	defer f.mu.RUnlock()
	res := make(map[string]string)
	for k, v := range f.data {
		res[k] = v
	}
	return res
}

func RecoverNode(snapshotData []byte, lastSnapIndex uint64, wal []LogEntry) (*MemoryFSM, uint64, error) {
	fmt.Printf("[Recovery] 1. Restoring base snapshot at index %d...\n", lastSnapIndex)
	fsm := NewMemoryFSM()
	if err := fsm.Restore(snapshotData); err != nil {
		return nil, 0, fmt.Errorf("snapshot restore failed: %w", err)
	}

	appliedCount := 0
	lastApplied := lastSnapIndex
	fmt.Printf("[Recovery] 2. Replaying WAL tail starting from index %d...\n", lastSnapIndex+1)

	for _, entry := range wal {
		if entry.Index <= lastSnapIndex {
			continue // Skip entries already in snapshot
		}
		fsm.Apply(entry.Cmd)
		lastApplied = entry.Index
		appliedCount++
	}

	fmt.Printf("[Recovery] Successfully replayed %d tail entries. Final applied index: %d\n", appliedCount, lastApplied)
	return fsm, lastApplied, nil
}

func main() {
	// Original Node Activity
	fsm := NewMemoryFSM()
	fsm.Apply(`{"k":"config:version","v":"1.0.0"}`)
	fsm.Apply(`{"k":"user:1","v":"Alice"}`)

	// Take Snapshot at index 2
	snapData, _ := fsm.Snapshot()
	snapIndex := uint64(2)

	// WAL continues with new writes
	wal := []LogEntry{
		{Index: 1, Term: 1, Cmd: `{"k":"config:version","v":"1.0.0"}`},
		{Index: 2, Term: 1, Cmd: `{"k":"user:1","v":"Alice"}`},
		{Index: 3, Term: 1, Cmd: `{"k":"user:2","v":"Bob"}`},
		{Index: 4, Term: 2, Cmd: `{"k":"config:version","v":"1.1.0"}`},
		{Index: 5, Term: 2, Cmd: `{"k":"user:3","v":"Charlie"}`},
	}

	// Apply remaining entries to original FSM
	fsm.Apply(wal[2].Cmd)
	fsm.Apply(wal[3].Cmd)
	fsm.Apply(wal[4].Cmd)
	fmt.Printf("State before Crash: %+v\n\n", fsm.Dump())

	// CRASH! (Original FSM instance is discarded)
	fmt.Println("💥 NODE CRASHED! Memory lost. Initiating Cold Boot Recovery...")

	// Cold Boot: Reconstruct from snapData + WAL
	recoveredFSM, finalIdx, err := RecoverNode(snapData, snapIndex, wal)
	if err != nil {
		panic(err)
	}

	recoveredState := recoveredFSM.Dump()
	fmt.Printf("State after Recovery: %+v (Final Index: %d)\n", recoveredState, finalIdx)

	// Verification
	if recoveredState["config:version"] == "1.1.0" && recoveredState["user:3"] == "Charlie" {
		fmt.Println("✅ State successfully restored to exact pre-crash state!")
	}
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 56

## Под капотом

Во время реплея лога в промышленном Raft:
- `commitIndex` не восстанавливается мгновенно до `lastLogIndex`.
- Узел читает свое последнее состояние `currentTerm` и `votedFor` из защищенного файла `raft-meta.json` (или BoltDB). Это предотвращает повторное голосование за двух разных кандидатов в одном терме после перезагрузки.
- Реплей логов в FSM выполняется синхронно до того, как узел начнет принимать входящие сетевые RPC запросы, гарантируя, что старые данные не утекут наружу.

## Подводные камни

- **Повторное применение логов из снапшота**: Если при реплее не пропустить записи с `Index <= SnapshotMeta.LastIncludedIndex`, команды, не являющиеся идемпотентными (например, инкремент счетчика), применятся дважды, безвозвратно повредив состояние FSM.
- **Неатомарная запись метаданных**: Если снапшот записан на диск, но файл метаданных с `LastIncludedIndex` не был синхронизирован через `fsync`, при крахе узел восстановит старый снапшот и применит усеченный лог, что вызовет панику.

## На собеседовании

На системных собеседованиях часто звучит вопрос: *«Почему Raft требует обязательного сохранения `currentTerm` и `votedFor` на диск с `fsync` перед отправкой голоса в `RequestVoteReply`?»*
**Ответ**: Представим, что узел \(A\) проголосовал за кандидата \(B\) в Term 2, ответил по сети, но не сбросил `votedFor` на диск. Сразу после этого узел \(A\) аварийно перезагружается. При рестарте он забывает о своем голосе. Кандидат \(C\) объявляет выборы в том же Term 2 и запрашивает голос. Если узел \(A\) повторно отдаст голос кандидату \(C\), в одном терме два разных кандидата могут набрать кворум! Это приведет к выбору двух лидеров (Split-Brain) и катастрофическому нарушению инварианта Election Safety. Поэтому сохранение `votedFor` с `fsync` критически важно.
