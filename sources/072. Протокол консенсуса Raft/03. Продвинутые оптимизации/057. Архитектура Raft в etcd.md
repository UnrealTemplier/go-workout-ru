# Архитектура Raft в etcd: etcd/raft State Machine, non-blocking I/O и сравнение с hashicorp/raft

## Условие

57. **Raft + etcd**: Изучите, как etcd использует Raft internally. etcd — это Raft-based KV store.

### Исходная формулировка

**Raft + etcd**: Изучите, как etcd использует Raft internally. etcd — это Raft-based KV store.

## Теория

Библиотека `go.etcd.io/raft` (ранее `etcd/raft`) представляет собой эталонную реализацию алгоритма консенсуса, используемую в ядре **Kubernetes**, **CockroachDB** и **TiKV**.

Принципиальное отличие `etcd/raft` от `hashicorp/raft`:
- **`hashicorp/raft` (Active / Batteries-Included)**: берет на себя управление сетевыми сокетами (TCP), горутинами, таймерами и дисковым I/O (BoltDB). Проста в интеграции, но скрывает детали под капотом.
- **`etcd/raft` (Pure State Machine / I/O-agnostic)**: представляет собой абсолютно чистую математическую машину состояний (Clean State Machine). Она не открывает сетевых портов, не создает фоновых горутин и не пишет на диск!

Цикл работы с `etcd/raft`:
1. Пользователь передает события в Raft через метод `Node.Step(ctx, msg)` или `Node.Propose(ctx, data)`.
2. Периодически вызывается `Node.Tick()` для тика логических часов (эмуляция heartbeat/election таймаутов).
3. Приложение читает канал `Node.Ready()`, получая структуру `Ready`:
   - `Entries`: записи, которые приложение обязано сохранить на диск (в WAL) ПЕРЕД отправкой сообщений.
   - `Messages`: сетевые пакеты RPC, которые приложение должно отправить другим узлам.
   - `CommittedEntries`: записи, зафиксированные кворумом, которые приложение должно применить к FSM (MVCC bbolt в etcd).
4. Приложение подтверждает обработку вызовом `Node.Advance()`.

## Решение по шагам

1. Изучите структуру паттерна `Ready` в стиле `etcd/raft`.
2. Реализуйте цикл событийного конвейера `Event Loop`, опрашивающий канал `Ready()`.
3. Смоделируйте этапы: (a) сохранение записей в WAL, (b) отправка исходящих сообщений по сети, (c) применение закоммиченных записей в KV-хранилище, (d) вызов `Advance()`.
4. Сравните производительность и гибкость подходов `etcd/raft` и `hashicorp/raft`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// Emulation of etcd/raft Ready structure
type Ready struct {
	Entries          []string // Entries to save to WAL
	Messages         []string // Messages to send over network
	CommittedEntries []string // Entries to apply to state machine
}

type EtcdRaftNode struct {
	readyCh   chan Ready
	advanceCh chan struct{}
	proposeCh chan string
	stopCh    chan struct{}
}

func NewEtcdRaftNode() *EtcdRaftNode {
	return &EtcdRaftNode{
		readyCh:   make(chan Ready, 1),
		advanceCh: make(chan struct{}),
		proposeCh: make(chan string, 10),
		stopCh:    make(chan struct{}),
	}
}

func (n *EtcdRaftNode) Propose(entry string) {
	n.proposeCh <- entry
}

func (n *EtcdRaftNode) Ready() <-chan Ready {
	return n.readyCh
}

func (n *EtcdRaftNode) Advance() {
	n.advanceCh <- struct{}{}
}

// Simulates etcd/raft core state machine processing loop
func (n *EtcdRaftNode) Run(ctx context.Context) {
	for {
		select {
		case <-ctx.Done():
			return
		case entry := <-n.proposeCh:
			// Raft state machine generates Ready struct
			rd := Ready{
				Entries:          []string{entry},
				Messages:         []string{fmt.Sprintf("MsgApp to Peer 2: %s", entry)},
				CommittedEntries: []string{entry}, // simplified immediate commit
			}

			n.readyCh <- rd
			// Wait for application to call Advance()
			<-n.advanceCh
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	node := NewEtcdRaftNode()
	go node.Run(ctx)

	// Application Event Loop (The classic etcd pattern)
	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()
		for i := 1; i <= 3; i++ {
			rd := <-node.Ready()

			// Step 1: Write Entries to persistent WAL
			for _, e := range rd.Entries {
				fmt.Printf("[Disk WAL] Appending entry: %s\n", e)
			}

			// Step 2: Send RPC Messages concurrently
			for _, m := range rd.Messages {
				fmt.Printf("[Network Transport] Sending: %s\n", m)
			}

			// Step 3: Apply Committed entries to Key-Value engine (bbolt)
			for _, c := range rd.CommittedEntries {
				fmt.Printf("[FSM Storage] Applied to KV: %s\n", c)
			}

			// Step 4: Notify Raft engine that Ready is consumed
			node.Advance()
			fmt.Println("[Raft Loop] Advance acknowledged\n---")
		}
	}()

	// Submitting proposals
	node.Propose("PUT /registry/pods/nginx-1 'Running'")
	node.Propose("PUT /registry/services/auth 'ClusterIP'")
	node.Propose("DELETE /registry/pods/nginx-old")

	time.Sleep(100 * time.Millisecond)
	cancel()
	wg.Wait()
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 57

## Под капотом

Почему архитектура `etcd/raft` стала мировым стандартом в распределенных БД:
1. **Zero-allocation & Deterministic Testing**: Поскольку в ядре `etcd/raft` нет I/O, тесты могут быть на 100% детерминированными, прогоняя миллионы сообщений за секунды в памяти без сетевых задержек.
2. **Batching и Pipelining**: Пользовательский код сам управляет сетевыми батчами и групповым `fsync`. Можно собрать 500 записей из канала `Ready()` и сбросить их на диск одним вызовом `writev` + `fdatasync`, достигая 100 000+ RPS.
3. **Pluggable Transport**: Приложение может использовать gRPC HTTP/2, RDMA или shared memory для передачи `Messages`.

## Подводные камни

- **Deadlock при несвоевременном вызове `Advance()`**: Если в цикле обработки `Ready()` возникнет паника или разработчик забудет вызвать `node.Advance()`, машина состояний Raft навсегда зависнет, перестав генерировать последующие `Ready`.
- **Нарушение порядка WAL и отправки сообщений**: В `etcd/raft` критически важно записать записи на диск ДО того, как отправлять сообщения фолловерам, иначе при одновременном сбое кластер потеряет зафиксированные данные.

## На собеседовании

В Яндексе (YDB) и VK часто спрашивают: *«В чем фундаментальное отличие модели concurrency в `hashicorp/raft` и `etcd/raft`? Какая лучше подойдет для написания распределенной базы данных с кастомным сетевым стеком?»*
**Ответ**: `hashicorp/raft` использует классическую многопоточную модель с горутинами и мьютексами, инкапсулируя сетевой транспорт и дисковый сторадж. Это удобно для быстрого старта (Consul, Nomad), но создает overhead на переключение контекста и ограничивает кастомизацию I/O. `etcd/raft` использует реактивную однопоточную модель актора с каналом `Ready()`, полностью освобождая разработчика от навязанного транспорта и позволяя строить ультра-оптимизированные конвейеры ввода-вывода (например, DPDK или io_uring в ScyllaDB/CockroachDB). Для кастомных распределенных СУБД безоговорочно выбирают `etcd/raft`.
