# Мониторинг здоровья кластера Raft: Детекция отставания и задержек записи

## Условие

Raft cluster health: Мониторьте: (1) Leader availability, (2) Follower replication lag, (3) Disk write latency. Напишите health checker.

### Исходная формулировка

**Raft cluster health**: Мониторьте:
* Leader availability
* Follower lag (commit index - applied index)
* Election frequency
* Snapshot frequency

## Теория

Комплексная диагностика здоровья (Deep Health Check) кластера Raft:
Кластер может считаться здоровым (`HEALTHY`) только при соблюдении трех условий:
1. **Leader Liveness:** активный лидер существует, и время с момента последнего подтверждения кворума не превышает `HeartbeatTimeout * 2`.
2. **Replication Lag:** отставание фоловеров от индекса лидера (\(\text{LeaderCommit} - \text{FollowerMatchIndex}\)) не превышает критического порога (например, 50 записей).
3. **Storage Latency:** задержка записи на диск (`fsync_duration`) не превышает 20 миллисекунд. Превышение порога дисковой задержки — предвестник аварии всего кластера.

## Решение по шагам

1. Создаем структуру PeerHealthStatus с метриками задержки и репликационного лага.
2. Создаем монитор RaftClusterHealthMonitor.
3. Реализуем метод EvaluateClusterHealth().
4. Тестируем нормальный режим и режим деградации при отставании узла.
5. Выводим статус готовности кластера к продакшену.

## Код решения

**`raft_health_checker.go`**

```go
package main

import (
	"fmt"
	"time"
)

type ClusterHealthStatus string

const (
	StatusHealthy  ClusterHealthStatus = "HEALTHY"
	StatusDegraded ClusterHealthStatus = "DEGRADED"
	StatusCritical ClusterHealthStatus = "CRITICAL"
)

type FollowerLagReport struct {
	FollowerID string
	MatchIndex uint64
	LastAck    time.Time
}

type ClusterHealthEvaluator struct {
	leaderID         string
	leaderCommit     uint64
	diskFsyncLatency time.Duration
	followers        []FollowerLagReport
}

func (e *ClusterHealthEvaluator) CheckHealth() (ClusterHealthStatus, []string) {
	var warnings []string
	status := StatusHealthy

	// 1. Проверка задержки дискового fsync
	if e.diskFsyncLatency > 50*time.Millisecond {
		status = StatusCritical
		warnings = append(warnings, fmt.Sprintf("CRITICAL: Disk fsync latency is %v (limit 50ms)", e.diskFsyncLatency))
	} else if e.diskFsyncLatency > 15*time.Millisecond {
		if status == StatusHealthy {
			status = StatusDegraded
		}
		warnings = append(warnings, fmt.Sprintf("WARN: High disk write latency: %v", e.diskFsyncLatency))
	}

	// 2. Проверка лага репликации
	for _, f := range e.followers {
		lag := e.leaderCommit - f.MatchIndex
		if lag > 100 {
			status = StatusCritical
			warnings = append(warnings, fmt.Sprintf("CRITICAL: Peer %s lag is %d entries!", f.FollowerID, lag))
		} else if lag > 20 {
			if status == StatusHealthy {
				status = StatusDegraded
			}
			warnings = append(warnings, fmt.Sprintf("WARN: Peer %s lag is %d entries", f.FollowerID, lag))
		}
	}

	return status, warnings
}

func main() {
	evaluator := &ClusterHealthEvaluator{
		leaderID:         "srv-fra-lead-01",
		leaderCommit:     50000,
		diskFsyncLatency: 8 * time.Millisecond,
		followers: []FollowerLagReport{
			{FollowerID: "srv-fra-fol-02", MatchIndex: 49998, LastAck: time.Now()},
			{FollowerID: "srv-fra-fol-03", MatchIndex: 49960, LastAck: time.Now()}, // Лаг 40 записей
		},
	}

	status, warnings := evaluator.CheckHealth()

	fmt.Println("=== RAFT CLUSTER HEALTH ASSESSMENT ===")
	fmt.Printf("Overall Cluster Status: %s\n", status)
	if len(warnings) > 0 {
		fmt.Println("Active Diagnostics:")
		for _, w := range warnings {
			fmt.Printf("  - %s\n", w)
		}
	} else {
		fmt.Println("All replication streams and storage latencies are within optimal parameters.")
	}
}
```

## Под капотом

В мониторинге Kubernetes (kube-prometheus-stack) правила алертинга на etcd включают:
`alert: etcdHighFsyncDurations` (когда 99-й перцентиль `wal_fsync_duration_seconds > 10ms`) и `alert: etcdHighNumberOfFailedProposals`. Это позволяет обнаружить деградацию дисков до того, как кластер начнет терять кворум.

## Подводные камни

Игнорирование лага диска: диск может не выдавать явных ошибок ввода-вывода (I/O Error), но замирать на 500 мс при сбросе буферов контроллера. Для Raft задержка `fsync > ElectionTimeout` равносильна крашу узла, вызывая внеплановые перевыборы.
