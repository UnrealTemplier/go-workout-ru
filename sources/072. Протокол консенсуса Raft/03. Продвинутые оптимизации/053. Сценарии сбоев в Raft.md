## Теория

Протокол Raft спроектирован так, чтобы гарантировать безопасность (Safety — State Machine Safety, Election Safety, Log Matching) в асинхронных сетях при наличии отказов типа Crash-Recovery (до \(F < N/2\) упавших узлов).

Основные сценарии сбоев и реакция протокола:
1. **Leader Crash**: Лидер мгновенно перестает слать сердечные сигналы (`AppendEntries`). По истечении рандомизированного `ElectionTimeout` у наиболее быстрого фолловера инициируются выборы. Кластер недоступен на запись лишь в течение времени обнаружения (\(T_{election} \approx 150-300\text{ мс}\)).
2. **Follower Crash**: Лидер продолжает принимать записи, пока имеет кворум. Попытки отправить RPC упавшему узлу завершаются таймаутом и повторяются бесконечно в бэкграунде. После рестарта фолловер догоняет лог через `AppendEntries` или snapshot.
3. **Network Partition (Split-Brain)**: Кластер из 5 узлов делится на \(\{A, B\}\) (минорити со старым лидером \(A\)) и \(\{C, D, E\}\) (мажорити). Лидер \(A\) принимает запись, но не может собрать кворум и блокирует коммит. В мажорити выбирается новый лидер \(C\). После слияния сетей \(A\) получает RPC с более высоким Term, превращается в фолловера и перезаписывает незакоммиченные логи логами лидера \(C\).
4. **Slow Follower (Straggler)**: Медленный узел (диск, сеть) не тормозит коммиты, пока \(N/2 + 1\) быстрых узлов подтверждают запись. Однако `nextIndex` для него отстает.
5. **Disk Full**: Ошибка `raft.Apply` при сохранении лога на диск. Узел обязан запаниковать или перейти в состояние degraded (safe crash), иначе повреждение WAL нарушит инварианты консенсуса.

## Решение по шагам

1. Создайте симулятор кластера Raft, управляющий узлами, сетевыми мостами и состоянием диска.
2. Смоделируйте сценарий Leader Crash: вызовите завершение текущего лидера, дождитесь смены лидера и проверьте кворум.
3. Смоделируйте Follower Crash: отключите один узел в кластере из 3 узлов, выполните коммит записи, затем перезапустите фолловер и проверьте совпадение реплицированного состояния.
4. Смоделируйте Network Partition (Split-Brain): изолируйте узел лидера от двух фолловеров, покажите, что изолированный лидер не может закоммитить запись, а оставшиеся 2 узла выбирают нового лидера и успешно фиксируют изменения.
5. Продемонстрируйте обработку ошибки переполнения диска (Disk Full) при fsync.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type NodeRole string

const (
	RoleLeader    NodeRole = "Leader"
	RoleCandidate NodeRole = "Candidate"
	RoleFollower  NodeRole = "Follower"
)

type FailureType string

const (
	FailNone      FailureType = "None"
	FailCrash     FailureType = "Crashed"
	FailPartition FailureType = "Partitioned"
	FailDiskFull  FailureType = "DiskFull"
)

type SimNode struct {
	ID        int
	Role      NodeRole
	Term      uint64
	Log       []string
	Status    FailureType
	Mu        sync.Mutex
	Heartbeat chan struct{}
}

func NewSimNode(id int) *SimNode {
	return &SimNode{
		ID:        id,
		Role:      RoleFollower,
		Term:      1,
		Log:       make([]string, 0),
		Status:    FailNone,
		Heartbeat: make(chan struct{}, 10),
	}
}

type SimCluster struct {
	nodes []*SimNode
	mu    sync.RWMutex
}

func NewSimCluster(n int) *SimCluster {
	c := &SimCluster{nodes: make([]*SimNode, n)}
	for i := 0; i < n; i++ {
		c.nodes[i] = NewSimNode(i)
	}
	c.nodes[0].Role = RoleLeader
	return c
}

func (c *SimCluster) CrashNode(id int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.nodes[id].Mu.Lock()
	c.nodes[id].Status = FailCrash
	c.nodes[id].Role = RoleFollower
	c.nodes[id].Mu.Unlock()
	fmt.Printf("[Cluster] Node %d crashed!\n", id)
}

func (c *SimCluster) RecoverNode(id int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.nodes[id].Mu.Lock()
	c.nodes[id].Status = FailNone
	c.nodes[id].Mu.Unlock()
	fmt.Printf("[Cluster] Node %d recovered and rejoined\n", id)
}

func (c *SimCluster) Propose(entry string) error {
	c.mu.RLock()
	defer c.mu.RUnlock()

	var leader *SimNode
	for _, n := range c.nodes {
		n.Mu.Lock()
		if n.Role == RoleLeader && n.Status == FailNone {
			leader = n
		}
		n.Mu.Unlock()
	}

	if leader == nil {
		return errors.New("no active leader in cluster")
	}

	leader.Mu.Lock()
	if leader.Status == FailDiskFull {
		leader.Mu.Unlock()
		return errors.New("leader disk full: write aborted")
	}
	leader.Log = append(leader.Log, entry)
	leader.Mu.Unlock()

	// Quorum check
	votes := 1
	for _, n := range c.nodes {
		if n.ID == leader.ID {
			continue
		}
		n.Mu.Lock()
		if n.Status == FailNone {
			n.Log = append(n.Log, entry)
			votes++
		}
		n.Mu.Unlock()
	}

	quorum := len(c.nodes)/2 + 1
	if votes >= quorum {
		fmt.Printf("[Raft Propose] '%s' committed with %d/%d acks\n", entry, votes, len(c.nodes))
		return nil
	}
	return fmt.Errorf("quorum loss: only %d/%d acks (need %d)", votes, len(c.nodes), quorum)
}

func main() {
	cluster := NewSimCluster(3)

	fmt.Println("--- 1. Happy Path Write ---")
	if err := cluster.Propose("SET user:1 'Alice'"); err != nil {
		fmt.Println("Error:", err)
	}

	fmt.Println("\n--- 2. Follower Crash (Quorum preserved) ---")
	cluster.CrashNode(2)
	if err := cluster.Propose("SET user:2 'Bob'"); err != nil {
		fmt.Println("Error:", err)
	}

	fmt.Println("\n--- 3. Follower Recovery ---")
	cluster.RecoverNode(2)

	fmt.Println("\n--- 4. Leader Crash (Election needed) ---")
	cluster.CrashNode(0)
	if err := cluster.Propose("SET user:3 'Charlie'"); err != nil {
		fmt.Println("Propose failed as expected:", err)
	}

	// Election simulation: Node 1 becomes leader
	cluster.nodes[1].Mu.Lock()
	cluster.nodes[1].Role = RoleLeader
	cluster.nodes[1].Term++
	cluster.nodes[1].Mu.Unlock()
	fmt.Printf("[Election] Node 1 elected Leader for Term %d\n", cluster.nodes[1].Term)

	if err := cluster.Propose("SET user:3 'Charlie'"); err != nil {
		fmt.Println("Error:", err)
	}
}
```

## Под капотом

При сбоях в реальных реализациях (hashicorp/raft, etcd/raft):
1. **Uncommitted Log Truncation**: Если изолированный лидер успел локально записать лог с Term \(T_1\), но не закоммитил его, новый лидер с Term \(T_2 > T_1\) при восстановлении связи пришлет `AppendEntries` с другим логом. Бывший лидер обнаружит расхождение по `PrevLogIndex`/`PrevLogTerm` и сделает `Truncate` своего незакоммиченного суффикса.
2. **Disk Fsync Failures**: Если системный вызов `fsync` или `fdatasync` возвращает `EIO`/`ENOSPC`, Raft не имеет права продолжать работу в роли лидера, так как нарушается гарантия персистентности лога. Узел инициирует `panic` или переход в `ErrorState`.

## Подводные камни

- **Попытка продолжать работу при Disk Full**: Если узел проигнорирует ошибку записи WAL на диск и ответит лидеру подтверждением (ACK) из RAM, при последующей перезагрузке этот лог пропадет, нарушив доказанный инвариант Log Matching.
- **Flapping Network Partition**: Периодическое мигание сети между узлами способно вызвать циклическую смену термов (Term Inflation), если не включен механизм Pre-Vote.

## На собеседовании

В BigTech (Яндекс, Авито) задают вопрос: *«Что произойдет, если лидер Raft-кластера из 5 узлов окажется изолирован в сетевой партиции с одним фолловером (минорити), а остальные 3 узла продолжат работу? Как поведет себя клиент, отправивший запись в минорити?»*
**Ответ**: Изолированный лидер примет запрос, добавит лог локально и пошлет `AppendEntries` единственному доступному фолловеру. Получив 2 подтверждения из 5, он не соберет кворум (\(3/5\)) и зависнет в ожидании (или вернет таймаут клиенту). В большинстве (3 узла) фолловеры зафиксируют таймаут сердечных сигналов, проведут выборы и выберут нового лидера, успешно коммитящего записи. Клиент получит таймаут от старого лидера. Когда изоляция устранится, старый лидер получит сообщение с новым Term, понизит свой статус до фолловера и удалит непринятую запись.
