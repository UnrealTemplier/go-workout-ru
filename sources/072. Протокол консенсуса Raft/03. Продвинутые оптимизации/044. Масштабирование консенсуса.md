# Масштабирование консенсуса: Архитектура Multi-Raft и шардирование диапазонов

## Условие

Raft multi-group: Для масштабирования разделите data на multiple Raft groups (как в CockroachDB, TiKV). Покажите роутинг ключей по хэшу или диапазону к разным группам Raft.

### Исходная формулировка

**Raft multi-group**: Для масштабирования разделите data на multiple Raft groups (как в CockroachDB, TiKV).

## Теория

Предел масштабирования Single-Raft кластера:
В одиночной группе Raft все записи обязаны проходить через один лог и одного лидера.
Предел пропускной способности упирается в скорость диска лидера (\(20\,000 - 50\,000\) RPS) и объем одного сервера (\(1 - 5\) ТБ).
Архитектура Multi-Raft (Шардированный консенсус):
1. Все адресное пространство ключей разбивается на независимые диапазоны (Ranges / Shards), например:
   - Range 1: `[a - h)` \(\to\) Raft Group 1 (Лидер на Node A)
   - Range 2: `[h - p)` \(\to\) Raft Group 2 (Лидер на Node B)
   - Range 3: `[p - z)` \(\to\) Raft Group 3 (Лидер на Node C)
2. Каждый физический сервер участвует в десятках или сотнях групп Raft одновременно (на одном сервере могут размещаться лидер группы 1 и фоловер группы 2).
3. Пропускная способность на запись масштабируется **линейно** с ростом числа серверов в кластере!

## Решение по шагам

1. Создаем структуру KeyRangeRouter с привязкой диапазонов к идентификаторам групп Raft.
2. Реализуем метод RouteKeyToGroup(key).
3. Создаем симулятор трех независимых групп Raft.
4. Проверяем параллельную запись ключей из разных диапазонов на разных лидеров.
5. Выводим топологию распределения нагрузки.

## Код решения

**`multi_raft_router.go`**

```go
package main

import (
	"fmt"
	"strings"
	"sync"
)

type RangeDescriptor struct {
	GroupID   int
	StartKey  string
	EndKey    string
	LeaderNode string
}

type MultiRaftRouter struct {
	ranges []RangeDescriptor
	groups map[int]*RaftGroupFSM
}

type RaftGroupFSM struct {
	mu      sync.RWMutex
	groupID int
	data    map[string]string
}

func NewMultiRaftRouter() *MultiRaftRouter {
	router := &MultiRaftRouter{
		ranges: []RangeDescriptor{
			{GroupID: 1, StartKey: "a", EndKey: "h", LeaderNode: "srv-node-alpha"},
			{GroupID: 2, StartKey: "h", EndKey: "p", LeaderNode: "srv-node-beta"},
			{GroupID: 3, StartKey: "p", EndKey: "z~", LeaderNode: "srv-node-gamma"},
		},
		groups: make(map[int]*RaftGroupFSM),
	}

	for _, r := range router.ranges {
		router.groups[r.GroupID] = &RaftGroupFSM{
			groupID: r.GroupID,
			data:    make(map[string]string),
		}
	}
	return router
}

func (r *MultiRaftRouter) RouteKey(key string) (*RangeDescriptor, *RaftGroupFSM, error) {
	lower := strings.ToLower(key)
	for i, rd := range r.ranges {
		if lower >= rd.StartKey && lower < rd.EndKey {
			return &r.ranges[i], r.groups[rd.GroupID], nil
		}
	}
	return nil, nil, fmt.Errorf("key %s out of cluster range bounds", key)
}

func (r *MultiRaftRouter) Put(key, val string) {
	desc, fsm, err := r.RouteKey(key)
	if err != nil {
		fmt.Printf("Routing error: %v\n", err)
		return
	}

	fsm.mu.Lock()
	fsm.data[key] = val
	fsm.mu.Unlock()

	fmt.Printf("KEY '%-15s' -> Routed to Raft Group #%d (Leader: %-15s) -> Committed!\n",
		key, desc.GroupID, desc.LeaderNode)
}

func main() {
	router := NewMultiRaftRouter()

	fmt.Println("=== MULTI-RAFT PARALLEL KEY ROUTING ===")
	// Ключи из разных диапазонов пишутся независимо параллельными лидерами
	router.Put("apple", "fruit_1")
	router.Put("booking_42", "hotel_reservation")
	router.Put("hotel_suite", "deluxe")
	router.Put("kafka_topic", "events")
	router.Put("payment_tx", "amount_500")
	router.Put("zebra_stripes", "black_white")

	fmt.Println("\nMulti-Raft horizontal scalability demonstrated: Zero bottleneck on a single leader.")
}
```

## Под капотом

В CockroachDB и TiKV Multi-Raft обслуживается единым фоновым пулом потоков (Shared Event Loop / Batch System). Вместо запуска отдельных горутин на каждую из 10 000 Raft-групп, события объединяются в плоские массивы сообщений, что предотвращает оверхед планировщика и исчерпание стеков горутин.

## Подводные камни

Split и Merge шардов: когда размер диапазона превышает 64 МБ, группа Raft обязана разделиться на две независимые группы (Range Split). Реализация безопасного сплита лога прямо в процессе обслуживания трафика — одна из сложнейших инженерных задач распределенных СУБД.

## На собеседовании

В: Как выполняются распределенные транзакции между разными Raft-группами в Multi-Raft архитектуре?
О: Поверх нескольких независимых Raft-групп запускается двухфазный коммит (Two-Phase Commit, 2PC) в связке с протоколом двухфазной блокировки (2PL) или MVCC-снапшотами. Каждая под-транзакция внутри своей группы реплицируется через локальный Raft-лог, а статус распределенной транзакции координируется Transaction Coordinator'ом.
