# Архитектура консенсуса в HashiCorp Consul: разделение плоскостей Raft и Serf (Gossip)

## Условие

59. **Raft + Consul**: Изучите, как Consul использует Raft для consensus в server nodes.

### Исходная формулировка

**Raft + Consul**: Изучите, как Consul использует Raft для consensus в server nodes.

## Теория

HashiCorp Consul — это распределенная система Service Discovery и KV-хранилище, демонстрирующая гибридную архитектуру двух протоколов:
1. **Raft (Consensus Layer)**: используется **только серверами Consul** (Consul Server Nodes, обычно 3 или 5 серверов в датацентре). Raft гарантирует строгую согласованность (Linearizable Consistency) для Service Catalog, KV-store, ACL-токенов и сессий блокировок.
2. **Serf / Gossip (SWIM Protocol)**: используется тысячами клиентских агентов (Consul Clients). Он решает задачи обнаружения членства (Membership) и детекции сбоев без нагрузки на Raft-кворум.

Ключевые принципы интеграции Raft в Consul:
- **Server Quorum**: При кластере из 3 серверов допускается отказ 1 сервера (\(Q = 2\)). При 5 серверах — отказ 2 серверов (\(Q = 3\)).
- **Autopilot**: Механизм автоматического мониторинга здоровья Raft-нод. Если нода отстает по логам (`ServerHealth.Healthy == false`), Autopilot не дает повысить ее до Voter, предотвращая деградацию кворума.
- **Cross-Datacenter Federation (WAN)**: Между датацентрами Raft **не используется** из-за высоких задержек сети! Синхронизация между DC выполняется через асинхронную репликацию и WAN Serf Gossip.

## Решение по шагам

1. Смоделируйте топологию Consul: пул серверов (Raft Quorum) и клиентские узлы (Serf/Gossip).
2. Реализуйте структуру `ConsulCatalog`, защищенную локальным Raft-консенсусом.
3. Реализуйте регистрацию сервиса клиентом: клиент отправляет RPC запрос на любой сервер, который проксирует его текущему Raft-лидеру.
4. Продемонстрируйте поведение кластера при падении одного из трех серверов: Service Catalog продолжает успешно обновляться.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

type ServiceEntry struct {
	ID      string
	Name    string
	Address string
	Port    int
}

type ConsulServer struct {
	ID       string
	IsLeader bool
	Term     uint64
	Catalog  map[string]ServiceEntry
	mu       sync.RWMutex
}

type ConsulCluster struct {
	servers []*ConsulServer
	mu      sync.RWMutex
}

func NewConsulCluster() *ConsulCluster {
	s1 := &ConsulServer{ID: "srv-dc1-1", IsLeader: true, Term: 1, Catalog: make(map[string]ServiceEntry)}
	s2 := &ConsulServer{ID: "srv-dc1-2", IsLeader: false, Term: 1, Catalog: make(map[string]ServiceEntry)}
	s3 := &ConsulServer{ID: "srv-dc1-3", IsLeader: false, Term: 1, Catalog: make(map[string]ServiceEntry)}

	return &ConsulCluster{
		servers: []*ConsulServer{s1, s2, s3},
	}
}

// Client interacts with any server node
func (c *ConsulCluster) RegisterServiceViaNode(targetServerID string, svc ServiceEntry) error {
	c.mu.RLock()
	defer c.mu.RUnlock()

	var target *ConsulServer
	var leader *ConsulServer

	for _, s := range c.servers {
		if s.ID == targetServerID {
			target = s
		}
		if s.IsLeader {
			leader = s
		}
	}

	if target == nil {
		return errors.New("target server not found")
	}
	if leader == nil {
		return errors.New("cluster has no active leader")
	}

	if !target.IsLeader {
		fmt.Printf("[Client Proxy] Node %s received RPC, forwarding to Raft Leader %s\n", target.ID, leader.ID)
	}

	// Leader commits to Raft and replicates across servers
	return c.replicateToQuorum(leader, svc)
}

func (c *ConsulCluster) replicateToQuorum(leader *ConsulServer, svc ServiceEntry) error {
	leader.mu.Lock()
	defer leader.mu.Unlock()

	// Simulate Quorum replication across 3 servers (need 2 acks)
	acks := 1 // leader ack
	leader.Catalog[svc.ID] = svc

	for _, s := range c.servers {
		if s.ID == leader.ID {
			continue
		}
		s.mu.Lock()
		s.Catalog[svc.ID] = svc
		acks++
		s.mu.Unlock()
	}

	quorum := len(c.servers)/2 + 1
	if acks >= quorum {
		fmt.Printf("[Consul Raft] Service '%s' committed with %d/%d votes\n", svc.Name, acks, len(c.servers))
		return nil
	}
	return errors.New("failed to acquire raft quorum")
}

func main() {
	cluster := NewConsulCluster()

	fmt.Println("--- 1. Service Registration via Follower Server ---")
	svcPayment := ServiceEntry{ID: "pay-1", Name: "payment-api", Address: "10.0.1.20", Port: 8080}

	// Request arrives at follower srv-dc1-2
	err := cluster.RegisterServiceViaNode("srv-dc1-2", svcPayment)
	if err != nil {
		fmt.Println("Registration failed:", err)
	}

	fmt.Println("\n--- 2. Verifying Consistency across All Servers ---")
	for _, s := range cluster.servers {
		s.mu.RLock()
		item, exists := s.Catalog["pay-1"]
		fmt.Printf("Server %s: Service found = %t, Address = %s:%d\n", s.ID, exists, item.Address, item.Port)
		s.mu.RUnlock()
	}
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 59

## Под капотом

Разделение обязанностей в архитектуре Consul:
- **Почему нельзя пустить тысячи микросервисов в Raft?**: Raft требует \(O(N)\) сообщений для каждой записи и синхронных `fsync` на диск. Если бы 10 000 подов в Kubernetes посылали свои сердечные сигналы напрямую в Raft, лидер захлебнулся бы сетевыми прерываниями.
- Поэтому в Consul агенты общаются локально по UDP через Serf Gossip (быстро, дешево, масштабируется до десятков тысяч узлов), и лишь критические изменения топологии каталога фиксируются лидерами серверов в Raft-лог.

## Подводные камни

- **Развертывание четного числа Consul серверов**: Развертывание 4 или 6 серверов не увеличивает отказоустойчивость, но снижает производительность. При 3 серверах кворум 2 (допустим 1 отказ). При 4 серверах кворум 3 (все равно допустим только 1 отказ!). Четное число узлов лишь повышает вероятность split-brain.
- **Запуск тяжелых Read-запросов без Stale Read**: Если клиенты читают Service Catalog исключительно с `ConsistencyMode = Consistent`, каждый HTTP GET запрос инициирует проверку лидерства через Round-Trip кворума, создавая боттлнек на лидере.

## На собеседовании

В Касперском и Авито часто спрашивают: *«Какие режимы чтения (Consistency Modes) поддерживает Consul и как они связаны с протоколом Raft?»*
**Ответ**: Consul поддерживает 3 режима чтения:
1. **`default` (Leader Read)**: Лидер обслуживает чтение из локального состояния FSM. Допускается микроскопическое окно чтения устаревших данных при сплит-брейне до истечения Lease.
2. **`consistent` (ReadIndex)**: Лидер перед ответом делает дополнительный раунд `AppendEntries` сердечных сигналов кворуму, чтобы гарантировать, что он не был смещен. Абсолютная линеаризуемость ценой дополнительной сетевой задержки.
3. **`stale`**: Запрос может быть обслужен любым фолловером без обращения к лидеру. Минимальная задержка и максимальная масштабируемость, но данные могут отставать на время репликации.
