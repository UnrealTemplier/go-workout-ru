# Тонкий тюнинг производительности Raft: SnapshotThreshold, Heartbeat, Election Timeout и пакетный Apply

## Условие

61. **Raft performance tuning:**
    * Optimize snapshot threshold
    * Tune heartbeat timeout
    * Tune election timeout
    * Batch Apply calls

### Исходная формулировка

**Raft performance tuning:**
* Optimize snapshot threshold
* Tune heartbeat timeout
* Tune election timeout
* Batch Apply calls

## Теория

Производительность и стабильность Raft-кластера в HighLoad определяются четырьмя фундаментальными конфигурационными параметрами:

1. **Heartbeat Timeout (\(T_{hb}\))** и **Election Timeout (\(T_{el}\))**:
   - В соответствии с правилом \(T_{hb} \ll T_{el} \ll \text{MTBF}\):
   - \(T_{hb}\) выбирается в диапазоне \(25-50\text{ мс}\) в локальной сети датацентра.
   - \(T_{el}\) рандомизируется в диапазоне \([150\text{ мс}, 300\text{ мс}]\) (примерное соотношение \(T_{el} \approx 5 \dots 10 \times T_{hb}\)). Слишком маленький \(T_{el}\) приведет к ложным выборам (Spurious Elections) при кратковременном всплеске GC pause.
2. **SnapshotThreshold**:
   - Баланс между расходом диска и стоимостью создания снапшота. В системах с 50 000+ RPS порог устанавливают в 50 000–100 000 записей. Слишком частый снапшотинг вызовет I/O Spike; слишком редкий — приведет к нехватке памяти и медленному рестарту.
3. **Batching / Group Commit**:
   - Самый мощный рычаг ускорения throughput. Лидер не делает отдельный `fsync` и сетевой round-trip на каждый `Apply(cmd)`. Вместо этого запросы от сотен клиентских горутин объединяются в один срез `[]*raft.Log` и реплицируются за один сетевой вызов. Это поднимает throughput с 2 000 RPS до 150 000+ RPS.

## Решение по шагам

1. Создайте структуру конфигурации `RaftTuningConfig`.
2. Реализуйте пакетный накопитель `BatchProposer`, группирующий параллельные вызовы `Apply` по таймауту или размеру пачки.
3. Рассчитайте метрику пропускной способности (Throughput) при одиночных записях против пакетных записей.
4. Сформулируйте правила подбора таймаутов в зависимости от сетевых задержек (LAN vs Multi-AZ).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type RaftTuningConfig struct {
	HeartbeatTimeout   time.Duration // typically 50ms in LAN, 250ms in WAN
	ElectionTimeoutMin time.Duration // typically 250ms
	ElectionTimeoutMax time.Duration // typically 500ms
	SnapshotThreshold  uint64        // number of committed logs before snapshot
	BatchMaxEntries    int           // max logs per batch (e.g. 500)
	BatchMaxDelay      time.Duration // max wait time before flushing batch (e.g. 2-5ms)
}

func DefaultProductionConfig() RaftTuningConfig {
	return RaftTuningConfig{
		HeartbeatTimeout:   50 * time.Millisecond,
		ElectionTimeoutMin: 250 * time.Millisecond,
		ElectionTimeoutMax: 500 * time.Millisecond,
		SnapshotThreshold:  50000,
		BatchMaxEntries:    200,
		BatchMaxDelay:      3 * time.Millisecond,
	}
}

type BatchRequest struct {
	Command string
	DoneCh  chan error
}

type BatchProposer struct {
	cfg     RaftTuningConfig
	queue   chan BatchRequest
	stopCh  chan struct{}
	flushes int
	mu      sync.Mutex
}

func NewBatchProposer(cfg RaftTuningConfig) *BatchProposer {
	p := &BatchProposer{
		cfg:    cfg,
		queue:  make(chan BatchRequest, 10000),
		stopCh: make(chan struct{}),
	}
	go p.worker()
	return p
}

func (p *BatchProposer) Submit(cmd string) <-chan error {
	done := make(chan error, 1)
	p.queue <- BatchRequest{Command: cmd, DoneCh: done}
	return done
}

func (p *BatchProposer) worker() {
	batch := make([]BatchRequest, 0, p.cfg.BatchMaxEntries)
	ticker := time.NewTicker(p.cfg.BatchMaxDelay)
	defer ticker.Stop()

	flush := func() {
		if len(batch) == 0 {
			return
		}
		p.mu.Lock()
		p.flushes++
		p.mu.Unlock()

		// Single simulated group fsync & network round-trip for all batched items!
		for _, req := range batch {
			req.DoneCh <- nil
		}
		batch = batch[:0]
	}

	for {
		select {
		case <-p.stopCh:
			flush()
			return
		case req := <-p.queue:
			batch = append(batch, req)
			if len(batch) >= p.cfg.BatchMaxEntries {
				flush()
			}
		case <-ticker.C:
			flush()
		}
	}
}

func main() {
	cfg := DefaultProductionConfig()
	fmt.Printf("Production Raft Config:\n- Heartbeat: %v\n- Election: [%v, %v]\n- Batch Size: %d, Delay: %v\n\n",
		cfg.HeartbeatTimeout, cfg.ElectionTimeoutMin, cfg.ElectionTimeoutMax,
		cfg.BatchMaxEntries, cfg.BatchMaxDelay)

	proposer := NewBatchProposer(cfg)

	// Simulate 1000 concurrent writes
	start := time.Now()
	var wg sync.WaitGroup
	total := 1000

	for i := 0; i < total; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			cmd := fmt.Sprintf("UPDATE balance SET amount = amount + 10 WHERE user_id = %d", id)
			err := <-proposer.Submit(cmd)
			if err != nil {
				fmt.Println("Write error:", err)
			}
		}(i)
	}

	wg.Wait()
	duration := time.Since(start)

	proposer.mu.Lock()
	flushes := proposer.flushes
	proposer.mu.Unlock()

	fmt.Printf("Processed %d writes in %v\n", total, duration)
	fmt.Printf("Total disk/network flushes: %d (Average batch size: %.1f operations/flush)\n",
		flushes, float64(total)/float64(flushes))
	fmt.Println("🚀 Group commit drastically reduced disk fsync count and round-trips!")
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 61

## Под капотом

Математика задержек и соотношения таймаутов:
1. Если \(T_{el} < 2 \times T_{hb}\), то малейшая потеря одного пакета сердечного сигнала или задержка в очереди отправки приведет к ложному старту выборов, смещению лидера и деградации пропускной способности (Leader Thrashing).
2. При развертывании кластера в Multi-Region (например, Москва — Санкт-Петербург — Новосибирск c RTT \(60\text{ мс}\)), \(T_{hb}\) обязан быть увеличен минимум до \(200\text{ мс}\), а \(T_{el}\) — до \(1000-2000\text{ мс}\).

## Подводные камни

- **Слишком большой `BatchMaxDelay`**: Если выставить задержку батча в 50 мс для накопления гигантских пачек, это снизит нагрузку на диск, но P99 latency одиночных пользовательских запросов катастрофически вырастет. Оптимальное значение — 1–3 мс.
- **Игнорирование Go GC Pauses**: Если Go приложение аллоцирует миллионы объектов в куче, паузы STW (хоть и микросекундные в Go 1.22+, но ощутимые под нагрузкой) могут превысить агрессивно заниженный `ElectionTimeout`, спровоцировав развал кластера.

## На собеседовании

В Авито и Ozon на собеседовании Senior Go Developer спрашивают: *«Как масштабировать запись в Raft-кластер, если физический диск лидера способен делать максимум 10 000 IOPS (fsync)?»*
**Ответ**: Использовать технику **Group Commit (Batching)**. Вместо отдельного `fsync` на каждую транзакцию входящие запросы от сотен горутин буферизуются в кольцевой буфер или канал за короткое окно (1–2 мс). Один поток лидера записывает срез записей за один системный вызов `writev` и делает один `fdatasync`. Это позволяет обслуживать 100 000+ RPS при лимите диска в 10 000 IOPS.
