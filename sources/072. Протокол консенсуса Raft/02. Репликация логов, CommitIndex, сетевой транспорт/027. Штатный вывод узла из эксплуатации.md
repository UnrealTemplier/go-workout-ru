# Штатный вывод узла из эксплуатации: Механизм RemoveServer

## Условие

Удаление узла: Удалите follower через `raft.RemoveServer`. Покажите, что кластер продолжает работать, а удаленный узел не пытается стать лидером.

### Исходная формулировка

**Удаление узла.**: Удалите follower через `raft.RemoveServer`. Покажите, что кластер продолжает работать с новым quorum. Объясните, почему удаление лидера требует перевыборов, и как `RemoveServer` с `ShutdownOnRemove` влияет на поведение.

## Теория

Проблема «Мстительного фоловера» (Disruptive Server Problem):
Если узел был удален из кластера оркестратором, но его процесс продолжает работать:
1. Удаленный узел перестает получать heartbeats от лидера.
2. По истечении `ElectionTimeout` удаленный узел решает, что лидер упал.
3. Он увеличивает свой Term и начинает спамить запросами `RequestVote` оставшиеся узлы.
4. В классическом Raft узлы, получив сообщение с более высоким Term, обязаны были сбросить своего легитимного лидера в Follower!
Защита в современном Raft:
- Узлы игнорируют `RequestVote`, если они получали heartbeat от текущего лидера в течение минимального интервала выборов (Leader Lease Protection).
- Удаленный через `RemoveServer` узел получает команду выключения и не создает помех оставшимся участникам кластера.

## Решение по шагам

1. Создаем структуру IsolatedNodeGuard с флагом удаления из топологии.
2. Реализуем метод DecommissionNode().
3. Проверяем блокировку инициации выборов декоммиссованным узлом.
4. Подтверждаем бесперебойную работу кворума оставшихся узлов.
5. Выводим отчет безопасности.

## Код решения

**`raft_remove_server_guard.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
)

type DecommissionedFollower struct {
	nodeID        string
	isRemoved     atomic.Bool
	attemptedTerm atomic.Uint64
}

func (f *DecommissionedFollower) MarkRemoved() {
	f.isRemoved.Store(true)
	fmt.Printf("[%s] Received cluster removal notification. Entering HALTED state.\n", f.nodeID)
}

func (f *DecommissionedFollower) OnElectionTimeout() bool {
	if f.isRemoved.Load() {
		fmt.Printf("[%s] Election timeout fired, but node is REMOVED from cluster. Suppressing RequestVote!\n", f.nodeID)
		return false
	}
	f.attemptedTerm.Add(1)
	return true
}

func main() {
	follower := &DecommissionedFollower{nodeID: "node-legacy-03"}

	// 1. Узел работает нормально
	ok := follower.OnElectionTimeout()
	fmt.Printf("Before removal: Election triggered = %v (Term: %d)\n\n", ok, follower.attemptedTerm.Load())

	// 2. Лидер выполняет raft.RemoveServer("node-legacy-03")
	fmt.Println(">>> Leader executes raft.RemoveServer(\"node-legacy-03\") <<<")
	follower.MarkRemoved()

	// 3. Срабатывает таймаут выборов на удаленном узле
	okAfter := follower.OnElectionTimeout()
	fmt.Printf("After removal:  Election triggered = %v (Disruption prevented!)\n", okAfter)
}
```

## Под капотом

В `hashicorp/raft` удаленный узел при вызове `RemoveServer` получает запись конфигурации `ConfigurationEntry`. Горутина `runFollower` видит, что локальный узел больше не входит ни в список Voters, ни в Nonvoters, и немедленно переходит в состояние `Shutdown`.

## Подводные камни

Удаление узлов до потери кворума: если в кластере из 3 узлов случайно вызвать `RemoveServer` для двух узлов одновременно, кластер потеряет кворум и не сможет закоммитить само удаление!

## На собеседовании

В: Что такое механизм Pre-Vote и как он решает проблему Disruptive Server в Raft?
О: Кандидат перед инкрементом Term рассылает легковесный опрос (Pre-Vote). Оставшиеся узлы большинства отклоняют Pre-Vote, если видят живого лидера. Изолированный или удаленный узел не может набрать согласие на выборы и не нарушает работу кластера.
