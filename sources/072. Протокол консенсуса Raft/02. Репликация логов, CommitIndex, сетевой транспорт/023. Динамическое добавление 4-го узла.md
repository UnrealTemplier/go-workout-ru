# Динамическое добавление 4-го узла: Изменение кворума и переходные состояния

## Условие

Используйте `raft.AddVoter` для добавления 4-го узла к кластеру из 3 узлов. Покажите, как меняется quorum (с 2 на 3) и почему четное число узлов не рекомендуется.

### Исходная формулировка

**Добавление узла (Membership Change).**: Используйте `raft.AddVoter` для добавления 4-го узла в работающий кластер. Покажите, что кластер переконфигурируется без downtime. Объясните, как HashiCorp Raft реализует membership changes (одноэтапное добавление, в отличие от joint consensus в оригинальном Raft).

## Теория

При переходе кластера с 3 узлов на 4 узла:
- До изменения: \(N=3\), кворум \(Q = \lfloor 3/2 \rfloor + 1 = 2\). Допускается отказ \(F = \lfloor (3-1)/2 \rfloor = 1\) узла.
- После добавления: \(N=4\), кворум \(Q = \lfloor 4/2 \rfloor + 1 = 3\). Допускается отказ \(F = \lfloor (4-1)/2 \rfloor = 1\) узла.
Парадокс четного кластера:
1. Отказоустойчивость \(F\) осталась прежней (\(F=1\)). Добавление 4-го сервера не увеличило надежность ни на процент!
2. Требование к кворуму выросло с 2 до 3 узлов. Теперь для подтверждения записи требуется согласие 3 серверов вместо 2, что увеличивает задержку (Latency).
3. Вероятность выхода из строя любого одного сервера из 4 выше, чем из 3.
4. При симметричном разделении сети 2:2 кластер полностью теряет доступность.
Вывод: четные конфигурации используются только временно в процессе миграции на 5 узлов.

## Решение по шагам

1. Создаем симулятор расширения кластера MembershipTransitionSimulator.
2. Инициализируем кластер из 3 узлов (кворум 2).
3. Применяем операцию AddVoter для 4-го узла.
4. Фиксируем рост кворума до 3 узлов.
5. Проверяем симуляцию падения 2 узлов: кластер из 4 узлов блокируется, тогда как для 5 узлов требовалось бы 3 падения.

## Код решения

**`raft_even_nodes_analysis.go`**

```go
package main

import (
	"fmt"
)

type ClusterConfigMetrics struct {
	Nodes          int
	Quorum         int
	MaxFailures    int
	Split2x2Risk   bool
}

func AnalyzeClusterTopology(n int) ClusterConfigMetrics {
	q := (n / 2) + 1
	f := (n - 1) / 2
	even := (n % 2 == 0)

	return ClusterConfigMetrics{
		Nodes:        n,
		Quorum:       q,
		MaxFailures:  f,
		Split2x2Risk: even,
	}
}

func main() {
	c3 := AnalyzeClusterTopology(3)
	c4 := AnalyzeClusterTopology(4)
	c5 := AnalyzeClusterTopology(5)

	fmt.Println("=== COMPARISON OF CLUSTER TOPOLOGY TRANSITIONS ===")
	fmt.Printf("%-10s | %-10s | %-15s | %s\n", "Nodes (N)", "Quorum (Q)", "Tolerance (F)", "Split-Risk")
	fmt.Println("----------------------------------------------------------------------")

	for _, c := range []ClusterConfigMetrics{c3, c4, c5} {
		fmt.Printf("%-10d | %-10d | %-15d | %v\n",
			c.Nodes, c.Quorum, c.MaxFailures, c.Split2x2Risk)
	}

	fmt.Println("\nInsight: Transitioning 3 -> 4 nodes raises Quorum to 3 without increasing Fault Tolerance (still 1).")
	fmt.Println("Recommendation: Always expand clusters directly from 3 to 5 nodes.")
}
```

## Под капотом

В `hashicorp/raft` при вызове `AddVoter` узел добавляется в `Configuration.Servers`. Новая конфигурация коммитится как запись в логе. Как только запись закоммичена, переменная `c.quorum` в рантайме пересчитывается. Если 4-й узел добавлен, лидер начинает требовать подтверждения минимум от двух фоловеров (\(1 + 2 = 3\)).

## Подводные камни

Остановка добавления на 4 узлах: если инфраструктурный пайплайн добавил 4-й узел и остановился, кластер становится уязвимее к сетевому джиттеру, чем был при 3 узлах. Всегда завершайте расширение до нечетного числа (5 узлов).

## На собеседовании

В: Почему во время миграции дата-центра кластер временно расширяют до 5 или 6 узлов?
О: При переезде между ДЦ используют временное добавление реплик в новом ДЦ. Если старый ДЦ имеет 3 узла, в новый добавляют 2 узла (\(N=5\)). После синхронизации логов лидер переносится в новый ДЦ, а старые 3 узла плавно выводятся через `RemoveServer`, возвращая кластер к \(N=3\) без простоя.
