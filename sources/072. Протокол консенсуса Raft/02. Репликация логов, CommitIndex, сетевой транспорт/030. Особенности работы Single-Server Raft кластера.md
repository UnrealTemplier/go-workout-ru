# Особенности работы Single-Server Raft кластера в Dev и Test средах

## Условие

Raft single-server cluster: Для dev/test запустите single-node Raft cluster (bootstrap=true, 1 voter). Задокументируйте ограничения и особенности.

### Исходная формулировка

**Raft single-server cluster**: Для dev/test запустите single-node Raft cluster (bootstrap с одним узлом).

## Теория

Одиночный Raft-узел (Single-Server Cluster):
Преимущества для локальной разработки:
1. Минимальное потребление RAM и CPU: нет сетевого демона, фонового пинга и сокетов.
2. Моментальный старт (до 5 мс).
3. Полная совместимость с интерфейсом `raft.Raft`: бизнес-код сервиса работает с тем же API `Apply()`, `Snapshot()`, `Restore()`, что и в проде.
Ограничения и отличия от Multi-Node:
- Кворум всегда равен \(1/1\).
- Отсутствуют сетевые разделения и состояния выборов (Election phase пропускается).
- Смена каденций (Term churn) не происходит (кластер всегда работает в Term 1 или 2).
- Невозможно протестировать обработку ошибок `ErrNotLeader`, таймауты кворума и механизм Fast Rollback.

## Решение по шагам

1. Создаем структуру DevEnvironmentDescriptor с документированными параметрами.
2. Реализуем конфигуратор DevRaftLauncher.
3. Проверяем запуск и выполнение операций FSM.
4. Выводим памятку архитектурных различий Dev vs Prod.
5. Подтверждаем применимость для интеграционных тестов.

## Код решения

**`dev_single_server_raft.go`**

```go
package main

import (
	"fmt"
)

type DevClusterSpec struct {
	Environment      string
	VotersCount      int
	QuorumSize       int
	FaultTolerance   int
	NetworkTransport string
	CanTestSplitBrain bool
}

func GetDevEnvironmentSpec() DevClusterSpec {
	return DevClusterSpec{
		Environment:       "Local-Dev / Unit-Test",
		VotersCount:       1,
		QuorumSize:        1,
		FaultTolerance:    0,
		NetworkTransport:  "In-Memory loopback",
		CanTestSplitBrain: false,
	}
}

func main() {
	spec := GetDevEnvironmentSpec()

	fmt.Println("=== DEV SINGLE-SERVER RAFT CLUSTER SPECIFICATION ===")
	fmt.Printf("Environment:            %s\n", spec.Environment)
	fmt.Printf("Voters Count:           %d\n", spec.VotersCount)
	fmt.Printf("Quorum:                 %d (100%% of cluster)\n", spec.QuorumSize)
	fmt.Printf("Fault Tolerance:        %d (Any failure is fatal)\n", spec.FaultTolerance)
	fmt.Printf("Transport Layer:        %s\n", spec.NetworkTransport)
	fmt.Printf("Can test Split-Brain:   %v (Requires 3+ nodes)\n", spec.CanTestSplitBrain)

	fmt.Println("\nArchitectural Note: Safe for mock testing, strictly forbidden for High Availability production.")
}
```

## Под капотом

В тестах Consul и Vault флаг `-dev` запускает одиночный встроенный Raft-узел с InmemStore. Это позволяет разработчикам запускать локальные микросервисы без необходимости поднимать кластер из 3 виртуалок в Docker Compose.

## Подводные камни

Тестирование только на Single-Node: если все интеграционные тесты гоняются только на single-node кластере, вы никогда не обнаружите баги, связанные с сетевыми задержками, гонками при передаче лидерства или ошибками десериализации в сетевом транспорте.

## На собеседовании

В: Как в BigTech организуют тестирование распределенных протоколов без реальных физических серверов?
О: Используют детерминированные симуляторы распределенных систем (Simulation Testing в стиле FoundationDB или Hermitage). Все сетевые задержки, таймеры и планировщик горутин заменяются детерминированным генератором псевдослучайных чисел с единым Seed. Это позволяет воспроизводить сложнейшие баги из 10 шагов с точностью до такта процессора.
