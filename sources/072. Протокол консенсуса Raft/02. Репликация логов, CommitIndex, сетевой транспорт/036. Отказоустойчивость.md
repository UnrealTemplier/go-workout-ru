# Отказоустойчивость: Перехват лидерства при внезапном сбое (Leader Failover)

## Условие

Каверзный кейс — Leader Failover: Убей процесс Лидера. Подожди несколько секунд до перевыборов. Отправь запись на новый узел. Убедись, что кластер живой и данные пишутся.

### Исходная формулировка

**[Каверзный кейс — Leader Failover]**: Убей процесс Лидера. Подожди несколько секунд (сработает Election Timeout). Наблюдай, как оставшиеся узлы выбирают нового Лидера. Отправь команду новому Лидеру.

## Теория

Тестирование Leader Failover — ключевая проверка жизнеспособности распределенной системы:
Хронология событий при внезапном падении лидера (Crash Failover):
1. \(T_0\): Лидер уничтожается (`SIGKILL` / отключение питания).
2. \(T_0 \dots T_1\): Фоновые таймеры выборов на фоловерах тикают. Из-за случайного jitter таймер одного из фоловеров (например, фоловера 2) истекает первым (\(T_{timeout} \approx 1000 - 1500\) мс).
3. \(T_1\): Фоловер 2 переходит в `Candidate`, инкрементирует `Term` и рассылает `RequestVote`.
4. \(T_2\): Фоловер 3 голосует за фоловера 2. Набран кворум 2 из 3 голосов. Фоловер 2 провозглашается Новым Лидером!
5. \(T_3\): Новый лидер отправляет первый heartbeat. Клиентские запросы возобновляются в полном объеме с нулевой потерей закоммиченных ранее данных.

## Решение по шагам

1. Создаем структуру FailoverClusterSimulation с узлами 1, 2, 3.
2. Проводим запись в штатном режиме через Лидера 1.
3. Симулируем жесткое уничтожение Лидера 1.
4. Запускаем перевыборы: Узел 2 избирается Новым Лидером в Term 2.
5. Отправляем новую запись через Узел 2 и подтверждаем работоспособность кластера.

## Код решения

**`raft_failover_test.go`**

```go
package main

import (
	"fmt"
	"time"
)

type FailoverPeer struct {
	ID        string
	Role      string
	Term      uint64
	Committed int
	IsDead    bool
}

type FailoverTestSuite struct {
	leaderID string
	peers    map[string]*FailoverPeer
}

func NewFailoverTestSuite() *FailoverTestSuite {
	peers := map[string]*FailoverPeer{
		"node-1": {ID: "node-1", Role: "LEADER", Term: 1, Committed: 10},
		"node-2": {ID: "node-2", Role: "FOLLOWER", Term: 1, Committed: 10},
		"node-3": {ID: "node-3", Role: "FOLLOWER", Term: 1, Committed: 10},
	}
	return &FailoverTestSuite{leaderID: "node-1", peers: peers}
}

func (s *FailoverTestSuite) KillCurrentLeader() {
	lead := s.peers[s.leaderID]
	lead.IsDead = true
	lead.Role = "DEAD"
	fmt.Printf("\n>>> DISASTER INJECTED: Terminated %s with SIGKILL <<<\n", s.leaderID)
	s.leaderID = ""
}

func (s *FailoverTestSuite) TriggerElection() string {
	// node-2 побеждает в выборах
	candidate := s.peers["node-2"]
	candidate.Term++
	candidate.Role = "LEADER"
	s.leaderID = candidate.ID

	s.peers["node-3"].Term = candidate.Term
	fmt.Printf(">>> ELECTION COMPLETE: %s elected as NEW LEADER in Term %d! <<<\n\n",
		candidate.ID, candidate.Term)
	return candidate.ID
}

func (s *FailoverTestSuite) ApplyToNewLeader(cmd string) error {
	lead := s.peers[s.leaderID]
	if lead.IsDead || lead.Role != "LEADER" {
		return fmt.Errorf("cluster has no active leader")
	}

	lead.Committed++
	s.peers["node-3"].Committed = lead.Committed
	fmt.Printf("[Cluster] Write '%s' committed by NEW LEADER %s (Committed=%d)\n",
		cmd, lead.ID, lead.Committed)
	return nil
}

func main() {
	suite := NewFailoverTestSuite()
	fmt.Printf("Initial state: Active Leader is %s (Term 1, Committed: 10)\n", suite.leaderID)

	// Убиваем текущего лидера
	suite.KillCurrentLeader()

	// Имитируем истечение таймера выборов (задержка обнаружения)
	time.Sleep(100 * time.Millisecond)

	// Выборы нового лидера
	newLeader := suite.TriggerElection()

	// Отправляем запись на новый узел
	err := suite.ApplyToNewLeader("SET payment_status = SUCCESS")
	if err != nil {
		fmt.Printf("Failover failed: %v\n", err)
	} else {
		fmt.Printf("System verified: New leader %s is fully operational with zero data loss!\n", newLeader)
	}
}
```

## Под капотом

В `hashicorp/raft` при падении лидера фоловер, чей рандомизированный таймер выборов истек первым, вызывает `r.electSelf()`. Он шлет параллельные запросы `RequestVoteRequest` пирам. При получении голосов кандидат переходит в состояние `Leader`, вызывает `r.startLead()` и сразу шлет пустой `AppendEntries` для подтверждения своего лидерства в новом Term.

## Подводные камни

Разрешение голосовать за кандидата с меньшим Term или устаревшим логом: фоловер обязан отказать в голосе, если `candidate.LastLogTerm < local.LastLogTerm` или `candidate.LastLogIndex < local.LastLogIndex`. Если этот инвариант нарушен, новым лидером станет узел, потерявший последние закоммиченные транзакции.

## На собеседовании

В: Как сократить время простоя (Downtime) при падении лидера в Raft без риска ложных перевыборов?
О: Тюнингом `ElectionTimeout`: в надежных локальных сетях его можно снизить с 1000 мс до 200-300 мс (при `HeartbeatTimeout: 25-50 мс`). Дополнительно используют Pre-Vote и механизм Fast Leader Transfer при плановых перезагрузках.
