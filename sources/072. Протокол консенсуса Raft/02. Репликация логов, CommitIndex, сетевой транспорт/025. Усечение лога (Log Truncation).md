# Усечение лога (Log Truncation): Очистка диска после создания снапшота

## Условие

Raft log compaction: Snapshot + log truncation = log compaction. Это предотвращает бесконечный рост лога на диске. Напишите процедуру обрезки логов.

### Исходная формулировка

**Raft log compaction**: Snapshot + log truncation = log compaction. Это предотвращает бесконечный рост log.

## Теория

Механика Log Compaction строится на совместной работе двух сущностей:
1. **Снапшот (Snapshot):** сохраняет срез состояния FSM на момент индекса \(S_{idx}\) и каденции \(S_{term}\).
2. **Усечение лога (Log Truncation):** все записи в хранилище логов (`LogStore`) с индексами \(I \le S_{idx}\) становятся избыточными, так как их совокупный результат уже зафиксирован в снапшоте.
Метод `LogStore.DeleteRange(min, max)` физически удаляет эти записи с диска.
В логе сохраняется специальная первая фиктивная запись (Dummy/Sentinel Entry) с индексом \(S_{idx}\) и каденцией \(S_{term}\), необходимая для формирования `PrevLogIndex` и `PrevLogTerm` в последующих сетевых RPC.

## Решение по шагам

1. Создаем структуру DurableLogStorage с хранением записей.
2. Реализуем метод TruncateLogsBefore(snapshotIndex, snapshotTerm).
3. Генерируем 10 000 записей лога.
4. Выполняем процедуру компактизации до индекса 8000.
5. Проверяем, что размер хранилища логов сократился, а граничный индекс равен 8000.

## Код решения

**`raft_log_truncation.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type LogEntryRecord struct {
	Index uint64
	Term  uint64
	Data  string
}

type CompactingLogStore struct {
	mu           sync.Mutex
	entries      map[uint64]LogEntryRecord
	firstIndex   uint64
	lastIndex    uint64
	snapshotTerm uint64
}

func NewCompactingLogStore() *CompactingLogStore {
	return &CompactingLogStore{
		entries:    make(map[uint64]LogEntryRecord),
		firstIndex: 1,
	}
}

func (s *CompactingLogStore) Append(term uint64, data string) uint64 {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.lastIndex++
	s.entries[s.lastIndex] = LogEntryRecord{Index: s.lastIndex, Term: term, Data: data}
	return s.lastIndex
}

func (s *CompactingLogStore) TruncateBefore(snapIndex, snapTerm uint64) int {
	s.mu.Lock()
	defer s.mu.Unlock()

	purged := 0
	for idx := s.firstIndex; idx <= snapIndex; idx++ {
		if _, exists := s.entries[idx]; exists {
			delete(s.entries, idx)
			purged++
		}
	}

	s.firstIndex = snapIndex + 1
	s.snapshotTerm = snapTerm
	return purged
}

func (s *CompactingLogStore) Stats() (int, uint64, uint64) {
	s.mu.Lock()
	defer s.mu.Unlock()
	return len(s.entries), s.firstIndex, s.lastIndex
}

func main() {
	store := NewCompactingLogStore()

	fmt.Println("=== APPENDING 10,000 RAFT LOG ENTRIES ===")
	for i := 1; i <= 10000; i++ {
		store.Append(1, fmt.Sprintf("TX_%05d", i))
	}

	countBefore, firstBefore, lastBefore := store.Stats()
	fmt.Printf("Before compaction: Count=%d, FirstIndex=%d, LastIndex=%d\n",
		countBefore, firstBefore, lastBefore)

	// Выполняем усечение до индекса 8000
	fmt.Println("\n>>> Performing Log Compaction at Snapshot Index 8000 <<<")
	deleted := store.TruncateBefore(8000, 1)

	countAfter, firstAfter, lastAfter := store.Stats()
	fmt.Printf("Compaction completed! Purged %d entries from disk.\n", deleted)
	fmt.Printf("After compaction:  Count=%d, FirstIndex=%d, LastIndex=%d\n",
		countAfter, firstAfter, lastAfter)
}
```

## Под капотом

В `raftboltdb` удаление записей выполняется вызовом `b.Delete(key)` внутри транзакции BoltDB. Однако в BoltDB удаление ключей не уменьшает размер файла на диске немедленно (freelist pages). Чтобы вернуть дисковое пространство ОС, периодически требуется запуск `compact` или использование LSM-движков вроде Pebble/LevelDB.

## Подводные камни

Усечение логов без фиксации снапшота на диске: если сначала удалить записи из лога, а при записи снапшота на диск произойдет сбой (OOM или Disk Full), узел потеряет историю и не сможет восстановиться. Порядок ОБЯЗАН быть строгим: 1) Снапшот записан и сброшен через fsync, 2) Метаданные обновлены, 3) Логи усечены.

## На собеседовании

В: Как часто нужно запускать Log Compaction в высоконагруженном кластере?
О: Настраивают двойной триггер: по количеству записей (`SnapshotThreshold`, например, 50 000 логов) и по времени (`SnapshotInterval`, например, каждые 30 минут). Это гарантирует, что при пиковой нагрузке лог не переполнит диск, а при низкой нагрузке память FSM будет регулярно сбрасываться в чекпоинты.
