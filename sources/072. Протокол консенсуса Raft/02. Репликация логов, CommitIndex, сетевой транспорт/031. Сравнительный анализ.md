### Исходная формулировка

**Raft vs Paxos**: Изучите, почему Raft проще для понимания и реализации, чем Paxos, при эквивалентных гарантиях.

## Теория

Исторический контекст:
Алгоритм Paxos Лесли Лэмпорта (Leslie Lamport, 1998) долгое время считался синонимом распределенного консенсуса.
Однако Paxos имел репутацию «исключительно сложного для понимания и корректной реализации» (The Paxos Algorithm is notoriously difficult to understand and implement).
Диего Онгаро и Джон Аустерхаут разработали Raft с главной целью — **Понятность (Understandability)**:
1. **Декомпозиция:** Raft строго разделяет задачу на 3 изолированные фазы: Leader Election, Log Replication и Safety. В Paxos выборы и репликация переплетены.
2. **Сильный лидер (Strong Leader):** в Raft записи лога текут строго в одном направлении — от Лидера к Фоловерам. Лидер никогда не перезаписывает свой лог. В Multi-Paxos любой узел может предложить значение по любому индексу, требуя сложных фаз Prepare/Promise для каждого слота.
3. **Целостность логов:** Raft запрещает дыры в логе (Log Holes). Лог всегда непрерывен (Dense Log). Paxos допускает неупорядоченное заполнение слотов, что усложняет garbage collection и снапшоты.
При этом математически Raft доказанно предоставляет абсолютно те же гарантии безопасности (Safety) и живучести (Liveness), что и Multi-Paxos.

## Код решения

**`raft_vs_paxos.go`**

```go
package main

import (
	"fmt"
)

type ConsensusMetric struct {
	Feature         string
	RaftMechanism   string
	PaxosMechanism  string
	GoEcosystemAdoption string
}

func main() {
	metrics := []ConsensusMetric{
		{
			Feature:             "Leader Authority",
			RaftMechanism:       "Strong Leader (monodirectional flow)",
			PaxosMechanism:      "Weak/Multiple Proposers (symmetric)",
			GoEcosystemAdoption: "etcd, Consul, TiKV",
		},
		{
			Feature:             "Log Structure",
			RaftMechanism:       "Strict continuous log (no holes allowed)",
			PaxosMechanism:      "Sparse slot-based log (holes allowed)",
			GoEcosystemAdoption: "Chubby, Spanner (Multi-Paxos)",
		},
		{
			Feature:             "State Machine Apply",
			RaftMechanism:       "Sequential by strict CommitIndex",
			PaxosMechanism:      "Out-of-order resolution per slot",
			GoEcosystemAdoption: "Raft is standard for Go projects",
		},
		{
			Feature:             "Membership Changes",
			RaftMechanism:       "Single-Server or Joint Consensus",
			PaxosMechanism:      "Alpha-reconfiguration per instance",
			GoEcosystemAdoption: "Dynamic AddVoter / RemoveServer",
		},
	}

	fmt.Println("=== ARCHITECTURAL BENCHMARK: RAFT vs PAXOS ===")
	fmt.Printf("%-20s | %-36s | %-32s\n", "Property", "Raft Approach", "Paxos Equivalent")
	fmt.Println("---------------------------------------------------------------------------------------------")

	for _, m := range metrics {
		fmt.Printf("%-20s | %-36s | %-32s\n", m.Feature, m.RaftMechanism, m.PaxosMechanism)
	}

	fmt.Println("\nConclusion: Raft provides identical formal correctness with significantly reduced operational complexity.")
}
```

## Под капотом

Исследования стэнфордской группы Онгаро показали, что при обучении студентов 64% показали существенно лучший результат на контрольных вопросах по Raft по сравнению с Paxos. В кодовой базе `etcd` переход на Raft позволил сократить тысячи строк сложного кода обработки граничных условий.

## Подводные камни

Заблуждение «Raft медленнее Paxos»: в нормальном режиме работы (Steady State) оба алгоритма требуют ровно одного раунда сетевых сообщений (RTT) от лидера к кворуму узлов для подтверждения коммита. Производительность Raft и Multi-Paxos идентична.

## На собеседовании

В: Почему Google Spanner использует Paxos, а CockroachDB и TiKV выбрали Raft?
О: Spanner разрабатывался в 2000-х годах, когда Paxos был единственным признанным стандартом академической науки. CockroachDB и TiKV создавались в 2015-2020 годах, когда Raft доказал свою зрелость и имел готовую протестированную реализацию в Go (etcd/raft).
