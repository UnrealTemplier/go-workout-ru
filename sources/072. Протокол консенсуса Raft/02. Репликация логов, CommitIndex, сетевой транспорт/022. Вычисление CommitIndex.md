# Вычисление CommitIndex: Кворумное большинство и продвижение индекса

## Условие

Raft commit index: Команда считается committed, когда реплицирована на majority. Только тогда она применяется к FSM. Покажите алгоритм вычисления медианы matchIndex.

### Исходная формулировка

**Raft commit index**: Команда считается committed, когда реплицирована на majority. Только committed entries применяются к FSM.

## Теория

Как лидер Raft решает, какой индекс лога можно безопасно закоммитить?
У лидера есть два ключевых внутренних массива:
1. `nextIndex[]`: индекс следующей записи, которую лидер пошлет каждому фоловеру.
2. `matchIndex[]`: наивысший индекс лога, о котором ТОЧНО известно, что он уже записан на диск данного фоловера.
Алгоритм вычисления `CommitIndex`:
- Лидер собирает массив `matchIndex` со всех узлов кластера (для самого лидера `matchIndex[leader] = lastLogIndex`).
- Массив сортируется по возрастанию.
- Медианное значение (значение по индексу \(\lfloor N/2 \rfloor\) при сортировке от больших к меньшим) — это максимальный индекс \(N\), который гарантированно присутствует на строгом большинстве узлов.
- Если \(N > \text{commitIndex}\) и запись по индексу \(N\) была создана в **текущем Term** лидера:
$$\text{commitIndex} = N$$
После этого лидер применяет все записи от старого `commitIndex + 1` до нового `commitIndex` к своей FSM.

## Решение по шагам

1. Создаем структуру LeaderReplicationTracker с массивом matchIndex.
2. Реализуем функцию CalculateCommitIndex(matchIndices, currentTerm, currentCommit).
3. Проверяем расчет для кластера из 5 узлов при различном прогрессе репликации.
4. Подтверждаем коммит записи, подтвержденной 3 из 5 узлов.
5. Демонстрируем, почему запись, находящаяся лишь на 2 из 5 узлов, НЕ коммитится.

## Код решения

**`raft_commit_index_median.go`**

```go
package main

import (
	"fmt"
	"sort"
)

type LogRecord struct {
	Index uint64
	Term  uint64
}

func CalculateMedianCommitIndex(totalNodes int, currentCommit uint64, currentTerm uint64, log []LogRecord, matchIndexes map[string]uint64) uint64 {
	// Собираем массив индексов со всех серверов
	matches := make([]uint64, 0, totalNodes)
	for _, idx := range matchIndexes {
		matches = append(matches, idx)
	}

	// Сортируем по возрастанию
	sort.Slice(matches, func(i, j int) bool {
		return matches[i] < matches[j]
	})

	// Медиана большинства: для N=5 кворум=3, медиана находится на индексе totalNodes - Quorum
	quorum := (totalNodes / 2) + 1
	medianIdx := totalNodes - quorum // для N=5: индекс 5-3 = 2
	candidateCommit := matches[medianIdx]

	// Правило безопасности Raft: коммитить можно только если кандидатский индекс больше текущего
	// и запись создана в ТЕКУЩЕМ Term лидера
	if candidateCommit > currentCommit && candidateCommit < uint64(len(log)) {
		if log[candidateCommit].Term == currentTerm {
			return candidateCommit
		}
	}

	return currentCommit
}

func main() {
	totalNodes := 5
	currentTerm := uint64(3)
	currentCommit := uint64(100)

	// Лог лидера (индексы 100..105)
	log := make([]LogRecord, 106)
	for i := uint64(0); i <= 105; i++ {
		log[i] = LogRecord{Index: i, Term: currentTerm}
	}

	// Ситуация A: 3 узла из 5 отреплицировали индекс 104
	matchA := map[string]uint64{
		"node-1-lead": 105,
		"node-2":      104,
		"node-3":      104,
		"node-4":      101,
		"node-5":      100,
	}

	newCommitA := CalculateMedianCommitIndex(totalNodes, currentCommit, currentTerm, log, matchA)
	fmt.Printf("Scenario A (3/5 reached 104): New CommitIndex = %d (Advanced!)\n", newCommitA)

	// Ситуация B: Только 2 узла из 5 отреплицировали индекс 105
	matchB := map[string]uint64{
		"node-1-lead": 105,
		"node-2":      105,
		"node-3":      102,
		"node-4":      101,
		"node-5":      100,
	}
	newCommitB := CalculateMedianCommitIndex(totalNodes, currentCommit, currentTerm, log, matchB)
	fmt.Printf("Scenario B (Only 2/5 reached 105, majority on 102): New CommitIndex = %d\n", newCommitB)
}
```

## Под капотом

В исходниках `etcd/raft/progress.go` и `hashicorp/raft` медиана вычисляется встроенным алгоритмом `sort.Sort(uint64Slice(matches))`. Затем берется `matches[(len(matches)-1)/2]`. Поскольку медиана гарантирует, что как минимум половина элементов массива больше либо равна этому значению, запись математически защищена от отката.

## Подводные камни

Попытка коммитить записи чужого Term напрямую: если узел стал лидером в Term 4 и видит в своем логе нескоммиченную запись из Term 2, отреплицированную на 3 из 5 узлов, он НЕ ИМЕЕТ ПРАВА объявлять ее закоммиченной, пока не закоммитит хотя бы одну запись Term 4. Нарушение этого правила приводит к багу в оригинальной спецификации Raft (Figure 8 paper).

## На собеседовании

В: В чем заключается феномен 'Figure 8' в статье Raft и почему лидер не может коммитить старые записи по подсчету реплик?
О: При череде сбоев запись старого Term может быть реплицирована на большинство узлов, но затем перезаписана новым лидером из более позднего Term, если этот старый Term не был окончательно зафиксирован. Чтобы исключить эту гонку, Raft требует коммитить записи старых каденций только косвенно (Indirect Commit) вместе с записью текущей каденции лидера.
