# Расширение Pre-Vote: Защита от дестабилизации кластера изолированными узлами

## Условие

Raft pre-vote: Реализуйте Pre-Vote extension для предотвращения disruptions при network partition. Покажите, что изолированный узел не накручивает term и не свергает легитимного лидера при возвращении в сеть.

### Исходная формулировка

**Raft pre-vote**: Реализуйте Pre-Vote extension для предотвращения disruptions при network partitions.

## Теория

Проблема Disruptive Server в классическом Raft:
1. Узел 1 изолирован сетевым барьером от узлов 2 и 3.
2. По тайм-ауту узел 1 переходит в `Candidate` и увеличивает `Term` с 1 до 2.
3. Голосов он не получает (нет кворума). Тайм-аут срабатывает снова: `Term = 3`, затем `Term = 4`, `Term = 10`...
4. Сеть восстанавливается. Узел 1 подключается к кластеру и отправляет пакет с `Term 10`.
5. Легитимный Лидер кластера (у которого `Term = 1`) видит сообщение с `Term 10 > 1` и по правилам классического Raft **обязан немедленно сложить полномочия в Follower**!
6. Кластер погружается в ненужные внеплановые перевыборы (Election Churn / Disruption).
Механизм Pre-Vote (секция 9.6 статьи Raft):
Перед тем как увеличить `Term` и начать настоящие выборы, кандидат запускает предварительный раунд (Pre-Vote Phase):
- Кандидат рассылает `PreVote(Term + 1, LastLogIndex, LastLogTerm)`.
- **Сам кандидат свой локальный Term НЕ увеличивает!**
- Узлы отвечают согласием на `PreVote` ТОЛЬКО ЕСЛИ:
  1. Лог кандидата актуален.
  2. С момента последнего контакта с действующим лидером прошло больше `ElectionTimeout` (лидер действительно мертв).
Если узел изолирован, он не получит одобрения Pre-Vote, его Term останется неизменным, и при возвращении в сеть он мирно присоединится как фоловер без сброса лидера!

## Решение по шагам

1. Создаем структуру PreVoteRequest и PreVoteResponse.
2. Реализуем метод Node.HandlePreVote(req).
3. Моделируем изолированный узел, запускающий Pre-Vote раунды.
4. Проверяем, что Term изолированного узла не растет.
5. Восстанавливаем сеть: подтверждаем, что легитимный лидер не свергается.

## Код решения

**`raft_prevote_extension.go`**

```go
package main

import (
	"fmt"
	"time"
)

type PreVoteRequest struct {
	CandidateID  string
	NextTerm     uint64
	LastLogIndex uint64
	LastLogTerm  uint64
}

type PreVoteResponse struct {
	VoteGranted bool
	CurrentTerm uint64
}

type PreVoteNode struct {
	id          string
	currentTerm uint64
	role        string
	lastLeaderContact time.Time
	electionTimeout   time.Duration
}

func (n *PreVoteNode) HandlePreVote(req PreVoteRequest) PreVoteResponse {
	// Правило 1: Если мы недавно слышали лидера, выборы не нужны!
	if time.Since(n.lastLeaderContact) < n.electionTimeout {
		fmt.Printf("[%s] PreVote REJECTED for %s: Active leader is healthy!\n", n.id, req.CandidateID)
		return PreVoteResponse{VoteGranted: false, CurrentTerm: n.currentTerm}
	}

	// Правило 2: Проверяем актуальность Term
	if req.NextTerm < n.currentTerm {
		return PreVoteResponse{VoteGranted: false, CurrentTerm: n.currentTerm}
	}

	fmt.Printf("[%s] PreVote GRANTED for %s (Leader absence confirmed)\n", n.id, req.CandidateID)
	return PreVoteResponse{VoteGranted: true, CurrentTerm: n.currentTerm}
}

func main() {
	// Фоловер большинства (недавно видел лидера)
	healthyFollower := &PreVoteNode{
		id:                "srv-2",
		currentTerm:       1,
		role:              "FOLLOWER",
		lastLeaderContact: time.Now().Add(-50 * time.Millisecond), // 50 мс назад был heartbeat
		electionTimeout:   500 * time.Millisecond,
	}

	// Изолированный узел пытается начать выборы через Pre-Vote
	isolatedCandidate := &PreVoteNode{
		id:          "srv-isolated-1",
		currentTerm: 1,
		role:        "FOLLOWER",
	}

	fmt.Println("=== ISOLATED NODE ATTEMPTS PRE-VOTE ===")
	preVoteReq := PreVoteRequest{
		CandidateID:  isolatedCandidate.id,
		NextTerm:     isolatedCandidate.currentTerm + 1, // Проверяем возможность Term 2
		LastLogIndex: 100,
		LastLogTerm:  1,
	}

	resp := healthyFollower.HandlePreVote(preVoteReq)

	if !resp.VoteGranted {
		fmt.Printf("\nResult: Candidate %s received NO pre-vote quorum.\n", isolatedCandidate.id)
		fmt.Printf("Candidate maintains local Term=%d (Term is NOT incremented!).\n", isolatedCandidate.currentTerm)
		fmt.Println("Protection verified: Legitimate cluster leader will NOT be disrupted when network heals!")
	}
}
```

## Под капотом

В `etcd/raft` расширение Pre-Vote включено по умолчанию с версии 3.0 (`PreVote: true`). Тип сообщения `MsgPreVote` и `MsgPreVoteResp` обрабатывается отдельно от стандартных `MsgVote`. Это полностью искоренило явление каскадных перевыборов при кратковременных сбоях в сетевом оборудовании дата-центров.

## Подводные камни

Отключение Pre-Vote в сетях с частыми микропаузами (Micro-partitions): без Pre-Vote любой под Kubernetes, застрявший на 2 секунды в троттлинге CPU, при отмирании будет сбрасывать лидера всего кластера, снижая общую доступность сервиса.

## На собеседовании

В: В чем ключевая разница между RequestVote и PreVote?
О: `RequestVote` — это обязывающее голосование с инкрементом Term кандидата и персистентной записью `votedFor` на диск. `PreVote` — это предварительный зондирующий опрос без инкремента Term и без записи на диск, проверяющий, готовы ли пиры признать отсутствие действующего лидера.
