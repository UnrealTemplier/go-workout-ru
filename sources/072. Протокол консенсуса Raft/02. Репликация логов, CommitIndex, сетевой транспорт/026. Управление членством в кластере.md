# Управление членством в кластере: AddVoter, RemoveServer и DemoteVoter

## Условие

Raft membership changes: Добавляйте/удаляйте узлы через `raft.AddVoter()`, `raft.RemoveServer()`, `raft.DemoteVoter()`. Покажите правильную последовательность изменения конфигурации.

### Исходная формулировка

**Raft membership changes**: Добавляйте/удаляйте узлы через `raft.AddVoter()`, `raft.RemoveServer()`. Raft гарантирует safety при membership changes.

## Теория

Пакет `hashicorp/raft` предоставляет богатый набор примитивов динамической реконфигурации кластера:
1. `AddVoter(id, address, prevIndex, timeout)`: добавляет голосующий узел. Кворум пересчитывается.
2. `DemoteVoter(id, prevIndex, timeout)`: переводит узел из статуса `Voter` в статус `Nonvoter`. Узел продолжает получать логи по репликации, но теряет право голоса на выборах и не учитывается в кворуме (полезно при выводе узла на техобслуживание).
3. `RemoveServer(id, prevIndex, timeout)`: полностью удаляет узел из топологии кластера. Лидер прекращает отправлять ему heartbeats.
Строгое правило безопасности: изменения конфигурации должны производиться строго последовательно (Single Server Changes). Нельзя вызывать `AddVoter` для узла B, пока предыдущий вызов для узла A не закоммичен кворумом.

## Решение по шагам

1. Создаем структуру ClusterMembershipState с перечислением ролей (Voter, Nonvoter).
2. Реализуем метод DemoteVoter(nodeID).
3. Реализуем метод RemoveServer(nodeID).
4. Проверяем корректный пересчет формулы большинства на каждом шаге.
5. Демонстрируем безопасный вывод узла из эксплуатации без даунтайма.

## Код решения

**`raft_membership_api.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type MemberRole string

const (
	MemberVoter    MemberRole = "VOTER"
	MemberNonVoter MemberRole = "NON_VOTER"
)

type ClusterNodeRecord struct {
	ID   string
	Role MemberRole
}

type ManagedClusterTopology struct {
	mu    sync.Mutex
	nodes map[string]ClusterNodeRecord
}

func NewManagedClusterTopology() *ManagedClusterTopology {
	t := &ManagedClusterTopology{nodes: make(map[string]ClusterNodeRecord)}
	for _, id := range []string{"srv-1", "srv-2", "srv-3"} {
		t.nodes[id] = ClusterNodeRecord{ID: id, Role: MemberVoter}
	}
	return t
}

func (t *ManagedClusterTopology) DemoteVoter(id string) error {
	t.mu.Lock()
	defer t.mu.Unlock()

	node, exists := t.nodes[id]
	if !exists {
		return fmt.Errorf("node %s not found", id)
	}

	node.Role = MemberNonVoter
	t.nodes[id] = node
	fmt.Printf("[Membership] Demoted %s from VOTER to NON_VOTER.\n", id)
	return nil
}

func (t *ManagedClusterTopology) RemoveServer(id string) error {
	t.mu.Lock()
	defer t.mu.Unlock()

	if _, exists := t.nodes[id]; !exists {
		return fmt.Errorf("node %s not found", id)
	}

	delete(t.nodes, id)
	fmt.Printf("[Membership] Removed %s from cluster topology completely.\n", id)
	return nil
}

func (t *ManagedClusterTopology) PrintQuorum() {
	t.mu.Lock()
	defer t.mu.Unlock()

	voters := 0
	for _, n := range t.nodes {
		if n.Role == MemberVoter {
			voters++
		}
	}
	quorum := (voters / 2) + 1
	fmt.Printf("Status: Total Nodes=%d, Active Voters=%d, Quorum=%d\n",
		len(t.nodes), voters, quorum)
}

func main() {
	topo := NewManagedClusterTopology()

	fmt.Println("=== INITIAL HEALTHY 3-NODE CLUSTER ===")
	topo.PrintQuorum()

	// Шаг 1: Подготовка к выводу srv-3 (демоутим в Non-voter)
	fmt.Println("\n=== 1. PREPARING MAINTENANCE: DEMOTE srv-3 ===")
	_ = topo.DemoteVoter("srv-3")
	topo.PrintQuorum()

	// Шаг 2: Полное удаление узла
	fmt.Println("\n=== 2. DECOMMISSIONING: REMOVE srv-3 ===")
	_ = topo.RemoveServer("srv-3")
	topo.PrintQuorum()

	fmt.Println("\nGraceful membership lifecycle executed successfully.")
}
```

## Под капотом

В `hashicorp/raft` удаленный узел при получении конфигурации, в которой его собственный `ServerID` отсутствует, автоматически вызывает `r.requestConfigChange` и переводит свой рантайм в статус `Shutdown`. Процесс закрывает сокеты и завершает работу горутин.

## Подводные камни

Удаление узла вызовом `RemoveServer` прямо на самом удаляемом узле: вызов вернет ошибку `ErrNotLeader`. Все операции управления членством кластера обязаны адресоваться текущему Лидеру.

## На собеседовании

О: Лидер фиксирует конфигурационную запись без самого себя в логе, реплицирует ее кворуму остальных узлов, слагает полномочия (`StepDown`) и завершает работу. Оставшиеся узлы большинства автоматически проводят новые выборы и избирают нового лидера.
