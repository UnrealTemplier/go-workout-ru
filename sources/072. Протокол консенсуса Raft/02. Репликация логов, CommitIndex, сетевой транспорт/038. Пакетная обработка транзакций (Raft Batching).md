# Пакетная обработка транзакций (Raft Batching) для снижения оверхеда

## Условие

Raft batching: Реализуйте batching для множественных `Apply` вызовов для снижения оверхеда дискового ввода-вывода (Group Commit) и сетевых пакетов.

### Исходная формулировка

**Raft batching**: Batch multiple Apply calls для снижения overhead.

## Теория

При сотнях тысяч клиентских запросов в секунду индивидуальный коммит каждой команды (один fsync и один сетевой пакет на транзакцию) приводит к немедленному насыщению дискового IOPS и сетевого контроллера.
Паттерн Group Commit / Raft Batching:
Лидер собирает входящие команды в промежуточный кольцевой буфер или канал с тайм-аутом сборки (Linger Timeout, например, 1-2 мс) либо по достижению лимита размера пачки (MaxBatchSize, например, 256 записей):
- Все 256 команд упаковываются в один сетевой фрейм `AppendEntries`.
- Все 256 записей записываются на диск одним вызовом `fsync` (Group Commit).
- Все 256 клиентских future завершаются одновременно.
Это повышает пропускную способность кластера Raft в 20-50 раз при незначительном росте задержки на 1-2 миллисекунды.

## Решение по шагам

1. Создаем структуру BatchCommandCollector с буфером и таймером сброса.
2. Реализуем метод EnqueueCommand(cmd), возвращающий персональный Future.
3. Фоновый диспетчер сбрасывает пачку по достижении лимита batchSize или по таймеру 10 мс.
4. Симулируем подачу 10 параллельных команд.
5. Проверяем, что команды объединяются в один батч с единым дисковым коммитом.

## Код решения

**`raft_batching_collector.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type BatchTask struct {
	Command string
	Done    chan struct{}
}

type RaftBatcher struct {
	mu        sync.Mutex
	buffer    []*BatchTask
	maxBatch  int
	maxWait   time.Duration
	incoming  chan *BatchTask
	batchRuns int
}

func NewRaftBatcher(maxBatch int, maxWait time.Duration) *RaftBatcher {
	b := &RaftBatcher{
		maxBatch: maxBatch,
		maxWait:  maxWait,
		incoming: make(chan *BatchTask, 100),
	}
	go b.runLoop()
	return b
}

func (b *RaftBatcher) Submit(cmd string) <-chan struct{} {
	task := &BatchTask{Command: cmd, Done: make(chan struct{})}
	b.incoming <- task
	return task.Done
}

func (b *RaftBatcher) runLoop() {
	var currentBatch []*BatchTask
	ticker := time.NewTicker(b.maxWait)
	defer ticker.Stop()

	flush := func() {
		if len(currentBatch) == 0 {
			return
		}
		b.batchRuns++
		fmt.Printf("[Raft Group Commit] Flushed Batch #%d with %d commands in 1 fsync!\n",
			b.batchRuns, len(currentBatch))

		// Имитируем один общий fsync и сетевой RPC
		time.Sleep(10 * time.Millisecond)

		for _, t := range currentBatch {
			close(t.Done)
		}
		currentBatch = nil
	}

	for {
		select {
		case task := <-b.incoming:
			currentBatch = append(currentBatch, task)
			if len(currentBatch) >= b.maxBatch {
				flush()
			}
		case <-ticker.C:
			flush()
		}
	}
}

func main() {
	// Батчер на 5 команд или 50 мс ожидания
	batcher := NewRaftBatcher(5, 50*time.Millisecond)

	var wg sync.WaitGroup
	fmt.Println("=== SUBMITTING 10 CONCURRENT TRANSACTIONS ===")

	for i := 1; i <= 10; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			done := batcher.Submit(fmt.Sprintf("UPDATE balance SET amount = %d", id*10))
			<-done
		}(i)
	}

	wg.Wait()
	fmt.Printf("\nBatching efficiency: 10 transactions processed across %d Group Commits.\n", batcher.batchRuns)
}
```

## Под капотом

В `hashicorp/raft` и `etcd/raft` батчинг встроен в канал `applyCh`. Пока горутина репликации ждет подтверждения предыдущего `AppendEntries`, канал `applyCh` накапливает входящие команды. При следующем витке цикла лидер читает все накопившиеся элементы одним неблокирующим `select` и формирует сгруппированный `raft.Log` массив.

## Подводные камни

Слишком большой `maxWait`: если установить `maxWait: 500ms`, то при низкой нагрузке одиночный запрос пользователя будет ждать полсекунды только для того, чтобы отправиться в кластер. `maxWait` не должен превышать 1-5 мс.

## На собеседовании

В: Что такое Nagle's Algorithm и почему его отключают (TCP_NODELAY) в транспорте Raft при использовании прикладного батчинга?
О: Алгоритм Нагла в ядре ОС задерживает отправку маленьких TCP-пакетов, чтобы объединить их в один. Но если приложение само реализует батчинг, алгоритм Нагла вступает в деструктивный резонанс с отложенными ACK (Delayed ACK), вызывая задержки до 40-200 мс. Поэтому в Raft сокетах ВСЕГДА выставляют `SetNoDelay(true)`.
