# Сквозная репликация журнала: Проверка согласованности FSM реплик

## Условие

Отправь команду на запись Лидеру. Убедись, что через полсекунды все 3 ноды имеют одинаковое состояние FSM. Покажи код проверки согласованности.

### Исходная формулировка

**[Log Replication]**: Отправь команду на запись Лидеру. Убедись, что через полсекунды все 3 FSM (на разных узлах) обновили локальную `map` с одинаковым значением.

## Теория

В распределенной системе репликация лога носит асинхронный по отношению к сети характер:
1. Лидер получает команду и рассылает `AppendEntries`.
2. После получения кворума (ACK от 1 фоловера из 2) лидер коммитит запись и немедленно возвращает ответ клиенту (Client Response).
3. Второй фоловер может отставать на десятки миллисекунд из-за сетевой задержки.
Для проверки согласованности (Convergence Assertion) в тестах используется метод ожидания сходимости (Eventually Consistent Assertion):
Тест с периодичностью 50 мс опрашивает FSM всех трех узлов с дедлайном (например, до 500 мс). Как только состояния всех трех машин состояний совпадают, тест считается успешно пройденным.

## Решение по шагам

1. Создаем структуру TestClusterAssert со ссылками на три узла FSM.
2. Реализуем метод SubmitToLeader(k, v).
3. Реализуем ассертер AssertEventualConsistency(key, expectedVal, timeout).
4. Запускаем репликацию с искусственной задержкой на фоловерах.
5. Проверяем успешное выравнивание данных на всех узлах кластера.

## Код решения

**`raft_eventual_assert.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type TestFSMNode struct {
	id   string
	mu   sync.RWMutex
	data map[string]string
}

func (n *TestFSMNode) Set(k, v string) {
	n.mu.Lock()
	defer n.mu.Unlock()
	n.data[k] = v
}

func (n *TestFSMNode) Get(k string) string {
	n.mu.RLock()
	defer n.mu.RUnlock()
	return n.data[k]
}

type ClusterTestHarness struct {
	lead *TestFSMNode
	fol1 *TestFSMNode
	fol2 *TestFSMNode
}

func (h *ClusterTestHarness) Submit(k, v string) {
	h.lead.Set(k, v)

	// Имитируем репликацию с разной задержкой
	go func() {
		time.Sleep(30 * time.Millisecond)
		h.fol1.Set(k, v)
	}()

	go func() {
		time.Sleep(120 * time.Millisecond)
		h.fol2.Set(k, v)
	}()
}

func (h *ClusterTestHarness) AssertConvergence(k, expected string, timeout time.Duration) error {
	deadline := time.Now().Add(timeout)

	for time.Now().Before(deadline) {
		v0 := h.lead.Get(k)
		v1 := h.fol1.Get(k)
		v2 := h.fol2.Get(k)

		if v0 == expected && v1 == expected && v2 == expected {
			return nil // Все 3 сошлись!
		}
		time.Sleep(20 * time.Millisecond)
	}

	return errors.New("timeout waiting for cluster FSM state convergence")
}

func main() {
	harness := &ClusterTestHarness{
		lead: &TestFSMNode{id: "lead", data: make(map[string]string)},
		fol1: &TestFSMNode{id: "fol1", data: make(map[string]string)},
		fol2: &TestFSMNode{id: "fol2", data: make(map[string]string)},
	}

	fmt.Println("=== SUBMITTING WRITE TO LEADER ===")
	harness.Submit("settings:maintenance_window", "02:00-04:00 UTC")

	start := time.Now()
	err := harness.AssertConvergence("settings:maintenance_window", "02:00-04:00 UTC", 500*time.Millisecond)
	elapsed := time.Since(start)

	if err != nil {
		fmt.Printf("Convergence failed: %v\n", err)
	} else {
		fmt.Printf("Cluster converged in %v! All 3 nodes have exact FSM value: '%s'\n",
			elapsed, harness.fol2.Get("settings:maintenance_window"))
	}
}
```

## Под капотом

В библиотеках тестирования вроде `testify/assert` или внутренних тест-сьютах HashiCorp для этого применяется утилита `testutil.WaitForResult`:
```go
testutil.WaitForResult(func() (bool, error) {
    return fsm1.Get(k) == expected && fsm2.Get(k) == expected, nil
}, t)
```
Это исключает хрупкие вызовы `time.Sleep(500 * time.Millisecond)` и делает прогон тестов быстрым и детерминированным.

## Подводные камни

Использование жестких `time.Sleep` в юнит-тестах вместо опроса предикатов: если написать в тесте `time.Sleep(500 * time.Millisecond)`, тест гарантированно простаивает полсекунды. При 100 тестах сьют будет выполняться почти минуту. Опрос с коротким интервалом (Polling loop) завершает тест мгновенно, как только условие выполнено.

О: Flaky-тесты — это тесты, случайно падающие из-за непредсказуемых пауз планировщика ОС или виртуализации CI runner'ов. Борьба включает: переход на In-Memory транспорт с виртуальным временем (Deterministic Virtual Time Clock), динамический опрос условий сходимости вместо фиксированных слипов и изоляцию процессорных ядер.
