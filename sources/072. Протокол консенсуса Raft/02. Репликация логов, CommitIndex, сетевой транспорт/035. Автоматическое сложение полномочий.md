# Автоматическое сложение полномочий: Leader Step Down при потере кворума

## Условие

Leader Step Down: Изолируйте текущего лидера (drop пакеты к majority). Покажите, что лидер теряет кворум, слагает полномочия (step down to follower) и перестает принимать записи.

### Исходная формулировка

**Leader Step Down.**: Изолируйте текущего лидера (drop пакеты к majority). Покажите, что лидер переходит в `StateFollower` (step down) по таймауту, а majority избирает нового лидера. При восстановлении сети старый лидер становится follower. Объясните роль `Term` (epoch) в отклонении stale команд.

## Теория

Проблема «Изолированного Лидера» (Isolated Leader / Partitioned Leader):
Представим кластер из 3 узлов. Узел 1 — Лидер.
Сетевой сбой изолирует узел 1 от узлов 2 и 3.
Если бы узел 1 продолжал считать себя лидером, он мог бы принимать запросы на запись от клиентов, подключенных к его локальному коммутатору.
Механизм Leader Step Down (CheckQuorum):
Лидер Raft непрерывно следит за ответами на свои heartbeats:
- Если за интервал `ElectionTimeout` лидер не получил подтверждения контакта хотя бы от половины фоловеров (строгое большинство кворума потеряно), он **обязан добровольно сложить полномочия**:
```go
r.becomeFollower(r.currentTerm, "")
```
Лидер переходит в роль Follower, сбрасывает статус готовности и немедленно отклоняет любые входящие запросы на запись с ошибкой `ErrNotLeader`.

## Решение по шагам

1. Создаем структуру LeaderHeartbeatMonitor с трекером последних ответов.
2. Реализуем метод CheckQuorumLiveness().
3. Симулируем прекращение ответов от фоловеров.
4. Фиксируем превышение порога таймаута и автоматический Step Down в статус Follower.
5. Проверяем блокировку мутирующих операций.

## Код решения

**`raft_leader_stepdown.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrNotLeaderStepDown = errors.New("node is not leader: stepped down due to quorum loss")
)

type ResilientLeaderNode struct {
	mu           sync.Mutex
	id           string
	role         string
	term         uint64
	lastContact  map[string]time.Time
	electionTime time.Duration
}

func NewResilientLeaderNode(id string, electionTimeout time.Duration) *ResilientLeaderNode {
	n := &ResilientLeaderNode{
		id:           id,
		role:         "LEADER",
		term:         2,
		lastContact:  make(map[string]time.Time),
		electionTime: electionTimeout,
	}
	// Инициализируем свежие контакты
	now := time.Now()
	n.lastContact["srv-2"] = now
	n.lastContact["srv-3"] = now
	return n
}

func (n *ResilientLeaderNode) StepDownIfQuorumLost() bool {
	n.mu.Lock()
	defer n.mu.Unlock()

	if n.role != "LEADER" {
		return false
	}

	// Считаем узлы, от которых был контакт в пределах electionTimeout
	now := time.Now()
	activeCount := 1 // Сам лидер всегда видит себя

	for peer, lastSeen := range n.lastContact {
		if now.Sub(lastSeen) < n.electionTime {
			activeCount++
		} else {
			fmt.Printf("[%s] WARNING: Peer %s unreachable for %v\n", n.id, peer, now.Sub(lastSeen))
		}
	}

	// Для 3 узлов кворум = 2
	if activeCount < 2 {
		fmt.Printf("[%s] LOST MAJORITY QUORUM (Reachable: %d/3). STEPPING DOWN TO FOLLOWER!\n",
			n.id, activeCount)
		n.role = "FOLLOWER"
		return true
	}

	return false
}

func (n *ResilientLeaderNode) ExecuteWrite(cmd string) error {
	n.mu.Lock()
	defer n.mu.Unlock()

	if n.role != "LEADER" {
		return ErrNotLeaderStepDown
	}
	fmt.Printf("[%s] Write '%s' processed by leader.\n", n.id, cmd)
	return nil
}

func main() {
	// Таймаут выборов: 200 мс
	leader := NewResilientLeaderNode("srv-1", 200*time.Millisecond)

	// Операция при живом кворуме
	_ = leader.ExecuteWrite("SET session:1001 = active")

	// Симулируем сетевую изоляцию: ответы перестают поступать
	fmt.Println("\n>>> NETWORK PARTITION: srv-1 isolated from srv-2 and srv-3 <<<")
	time.Sleep(250 * time.Millisecond)

	// Запуск проверки кворума
	steppedDown := leader.StepDownIfQuorumLost()
	fmt.Printf("Was step down executed? %v\n", steppedDown)

	// Попытка записи после потери кворума
	err := leader.ExecuteWrite("SET session:1002 = active")
	fmt.Printf("Subsequent write result: %v\n", err)
}
```

## Под капотом

В `hashicorp/raft` горутина `runLeader` запускает таймер проверки:
```go
lease := time.After(r.config.ElectionTimeout)
case <-lease:
    if !r.checkLeaderLease() {
        r.setState(Follower)
        return
    }
```
Если кворум узлов не подтвердил получение heartbeats в течение интервала `ElectionTimeout`, лидер принудительно возвращается в роль Follower.

## Подводные камни

Отсутствие проверки кворума у лидера: если лидер не слагает полномочия при изоляции, клиенты с длинными таймаутами будут зависать в попытках записи на изолированном узле, вместо того чтобы получить быстрый отказ и переключиться на новое большинство.

## На собеседовании

В: Почему в Raft проверка кворума лидером (CheckQuorum) включена по умолчанию?
О: Она предотвращает Split-Brain на чтение и исключает ситуации, когда изолированный старый лидер бесконечно удерживает ресурсы и не отдает управление новому легитимному лидеру большинства.
