# Периодические снапшоты FSM и восстановление состояния после падения

## Условие

Снэпшоты и восстановление состояния: В FSM реализуйте снэпшот каждые N логов. Симулируйте падение процесса. При рестарте покажите, что FSM загружает snapshot и накатывает только оставшиеся логи.

### Исходная формулировка

**Снэпшоты и восстановление состояния.**: В FSM реализуйте снэпшот каждые N логов. Симулируйте падение узла, затем перезапустите его – он должен догнать лидера из снэпшота и последующих логов.

## Теория

Гибридная модель восстановления узла Raft (Snapshot + Tail Replay):
При перезапуске узла после аварии (Node Restart):
1. FSM считывает последний валидный снапшот с диска (`FileSnapshotStore`) через `FSM.Restore()`. Стейт мгновенно восстанавливается на момент индекса \(S_{idx}\).
2. Raft считывает из `LogStore` только записи с индексами \(S_{idx} + 1 \dots \text{LastLogIndex}\) (хвостовые логи).
3. Движок вызывает `FSM.Apply()` строго для хвостовых записей.
Это дает колоссальный выигрыш в скорости старта: вместо воспроизведения 10 000 000 логов за весь год узел загружает снапшот за 100 мс и накатывает всего 50 недавних логов!

## Решение по шагам

1. Создаем структуру HybridRecoveryFSM со счетчиком логов и методом Snapshot().
2. Генерируем 100 логов, делаем снапшот на индексе 80.
3. Добавляем логи с 81 по 100.
4. Симулируем падение и перезапуск процесса FSM.
5. Демонстрируем восстановление стейта: снапшот (1..80) + воспроизведение хвоста (81..100).

## Код решения

**`raft_snapshot_tail_recovery.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type RecoverableFSM struct {
	mu           sync.RWMutex
	state        map[string]string
	lastApplied  uint64
	snapshotData map[string]string
	snapshotIdx  uint64
}

func NewRecoverableFSM() *RecoverableFSM {
	return &RecoverableFSM{
		state: make(map[string]string),
	}
}

func (f *RecoverableFSM) Apply(idx uint64, k, v string) {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.state[k] = v
	f.lastApplied = idx
}

func (f *RecoverableFSM) TakeSnapshot() {
	f.mu.Lock()
	defer f.mu.Unlock()

	f.snapshotIdx = f.lastApplied
	f.snapshotData = make(map[string]string, len(f.state))
	for k, v := range f.state {
		f.snapshotData[k] = v
	}
	fmt.Printf("[FSM Snapshot] Snapshot created at Index %d (Keys count: %d)\n",
		f.snapshotIdx, len(f.snapshotData))
}

func (f *RecoverableFSM) SimulateCrashAndRestart(tailLogs map[uint64]struct{ k, v string }) {
	f.mu.Lock()
	defer f.mu.Unlock()

	fmt.Println("\n>>> SIMULATING CRASH & FAST RECOVERY <<<")
	// 1. Очищаем оперативную память
	f.state = make(map[string]string)

	// 2. Восстанавливаемся из последнего снапшота
	for k, v := range f.snapshotData {
		f.state[k] = v
	}
	f.lastApplied = f.snapshotIdx
	fmt.Printf("[Recovery Step 1] Restored snapshot baseline at Index %d.\n", f.lastApplied)

	// 3. Накатываем только хвостовые логи (Tail Replay)
	replayed := 0
	for idx := f.snapshotIdx + 1; idx <= 100; idx++ {
		if item, exists := tailLogs[idx]; exists {
			f.state[item.k] = item.v
			f.lastApplied = idx
			replayed++
		}
	}
	fmt.Printf("[Recovery Step 2] Replayed %d tail logs. Final LastApplied = %d\n",
		replayed, f.lastApplied)
}

func main() {
	fsm := NewRecoverableFSM()

	// Логи с 1 по 80
	for i := uint64(1); i <= 80; i++ {
		fsm.Apply(i, fmt.Sprintf("k%d", i), fmt.Sprintf("v%d", i))
	}

	// Снапшот на индексе 80
	fsm.TakeSnapshot()

	// Логи с 81 по 100
	tailLogs := make(map[uint64]struct{ k, v string })
	for i := uint64(81); i <= 100; i++ {
		k := fmt.Sprintf("k%d", i)
		v := fmt.Sprintf("v%d", i)
		fsm.Apply(i, k, v)
		tailLogs[i] = struct{ k, v string }{k: k, v: v}
	}

	// Падение и быстрое восстановление
	fsm.SimulateCrashAndRestart(tailLogs)

	fmt.Printf("\nVerification: Total keys in FSM after recovery = %d (Expected: 100)\n", len(fsm.state))
	fmt.Println("Hybrid Snapshot + Tail Replay architecture verified.")
}
```

## Под капотом

В `hashicorp/raft/fsm.go` при старте узел читает `SnapStore.Open()`. Если снапшот найден, вызывается `fsm.Restore(snapReader)`. Затем берется `meta.Index`. Из `LogStore` запрашивается диапазон логов от `meta.Index + 1` до `lastLogIndex`. Только этот короткий диапазон передается в `fsm.Apply()`, минимизируя время простоя сервиса при рестартах.

## Подводные камни

Рассинхронизация индекса снапшота и логов: если снапшот был записан на индексе 500, а логи обрезаны до индекса 510 (случайная потеря 10 записей), возникнет неустранимая брешь в логе (Log Gap). `hashicorp/raft` запаникует при старте. Удаление логов обязано происходить строго ДО или РАВНО индексу снапшота.

## На собеседовании

В: Что произойдет, если сервер Raft упал прямо в момент записи файла снапшота на диск?
О: Применяется атомарный Two-Phase Write: данные пишутся во временный файл `state.tmp`. Только после успешного завершения записи и вызова `fsync` файл атомарно переименовывается (`os.Rename`) в постоянное имя. Недописанный временный файл при рестарте просто удаляется сборщиком мусора, а узел поднимается из предыдущего проверенного снапшота.
