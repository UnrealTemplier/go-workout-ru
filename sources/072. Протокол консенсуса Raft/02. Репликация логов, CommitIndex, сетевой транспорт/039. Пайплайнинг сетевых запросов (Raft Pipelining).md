# Пайплайнинг сетевых запросов (Raft Pipelining): Потоковая репликация логов

## Условие

Raft pipeline: Реализуйте pipeline AppendEntries RPCs для повышения throughput на сетевых соединениях с высокой задержкой (High Latency WAN).

### Исходная формулировка

**Raft pipeline**: Pipeline AppendEntries RPCs для повышения throughput.

## Теория

Проблема Stop-and-Wait в распределенных сетях:
Если между серверами RTT составляет 50 мс (между дата-центрами), а размер пакета 10 КБ:
- В классическом режиме: лидер посылает пакет \(\to\) ждет 50 мс \(\to\) получает ACK \(\to\) посылает следующий. Пропускная способность: \(1 / 0.05 = 20\) пакетов/сек.
- В режиме Raft Pipelining: лидер открывает виртуальное окно передачи (In-Flight Window). Лидер непрерывно шлет новые `AppendEntries`, не дожидаясь ответа на предыдущие, пока число неподтвержденных пакетов не превысит лимит окна (например, 64 пачки in-flight).
Фоловер подтверждает пакеты с монотонным возрастанием индекса. Пропускная способность вырастает до предела физической полосы пропускания сети (Bandwidth-Delay Product, BDP).

## Решение по шагам

1. Создаем структуру PipelineReplicator с окном in-flight запросов.
2. Реализуем метод DispatchPipelinedBatch(batchID).
3. Симулируем непрерывную отправку 5 пачек без блокировки на RTT.
4. Обрабатываем подтверждения от фоловера.
5. Сравниваем время передачи с последовательным Stop-and-Wait режимом.

## Код решения

**`raft_pipelining_stream.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type PipelinedBatch struct {
	BatchID   int
	Entries   int
	SentAt    time.Time
}

type PipelineChannel struct {
	mu        sync.Mutex
	windowMax int
	inFlight  int
	acks      chan int
}

func NewPipelineChannel(windowMax int) *PipelineChannel {
	return &PipelineChannel{
		windowMax: windowMax,
		acks:      make(chan int, 100),
	}
}

func (p *PipelineChannel) SendBatchAsync(b PipelinedBatch, networkRTT time.Duration) {
	p.mu.Lock()
	p.inFlight++
	fmt.Printf("[Pipeline Out] Sent Batch #%d (%d entries) -> In-Flight: %d/%d\n",
		b.BatchID, b.Entries, p.inFlight, p.windowMax)
	p.mu.Unlock()

	// Имитация сетевого полета пакета и ответа фоловера
	go func() {
		time.Sleep(networkRTT)
		p.mu.Lock()
		p.inFlight--
		p.mu.Unlock()
		p.acks <- b.BatchID
	}()
}

func main() {
	rtt := 40 * time.Millisecond // Задержка между ЦОД (40 мс)
	pipeline := NewPipelineChannel(5)

	fmt.Println("=== STREAMING 5 LOG BATCHES VIA RAFT PIPELINE ===")
	start := time.Now()

	// Лидер выстреливает 5 батчей подряд без ожидания RTT
	for i := 1; i <= 5; i++ {
		batch := PipelinedBatch{BatchID: i, Entries: 100, SentAt: time.Now()}
		pipeline.SendBatchAsync(batch, rtt)
	}

	// Сбор всех подтверждений
	for i := 1; i <= 5; i++ {
		ackID := <-pipeline.acks
		fmt.Printf("  [Pipeline ACK] Follower acknowledged Batch #%d\n", ackID)
	}

	elapsed := time.Since(start)
	fmt.Printf("\nAll 5 batches replicated in %v (Stop-and-Wait would take ~%v)\n",
		elapsed, 5*rtt)
	fmt.Println("Raft pipelining achieves maximum throughput saturation.")
}
```

## Под капотом

В `hashicorp/raft` интерфейс `Transport` включает метод `AppendEntriesPipeline(id, target) (AppendPipeline, error)`. Он держит открытый стрим поверх TCP и отправляет запросы через буферизированный канал `chan *AppendFuture` без пересоздания кадров протокола.

## Подводные камни

Рассинхронизация при сбое в середине конвейера: если батч #3 потерялся в сети, а батчи #4 и #5 дошли, фоловер отвергнет #4 и #5 из-за несовпадения `PrevLogIndex`. Пайплайн обязан немедленно сбрасывать окно in-flight запросов и возвращаться к последовательной согласующей отправке с точки последнего успешного подтверждения.

## На собеседовании

В: Что такое Head-of-Line Blocking в сетевом пайплайнинге Raft?
О: Если один пакет из середины потока задерживается или теряется, все последующие пакеты в TCP буфере не могут быть обработаны машиной состояний фоловера, даже если они физически доставлены. В современных протоколах (QUIC/HTTP/3) эта проблема устраняется независимыми стримами без взаимной блокировки.
