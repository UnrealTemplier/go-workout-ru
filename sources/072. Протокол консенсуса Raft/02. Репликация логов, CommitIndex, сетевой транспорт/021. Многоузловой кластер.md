# Многоузловой кластер: Инициализация топологии из 3 узлов на TCP-портах

## Условие

Подними 3 узла (на разных портах). Вручную добавь 2-й и 3-й узлы через `raft.AddPeer` / `raft.AddVoter`. Убедись, что лидер выбран.

### Исходная формулировка

**[Multi-Node Cluster]**: Подними 3 узла (на разных портах). Вручную добавь 2-й и 3-й узел к лидеру через `raft.AddVoter`.

## Теория

Развертывание кластера Raft из 3 узлов на разных локальных или сетевых TCP-портах (например, `:8301`, `:8302`, `:8303`):
Схема инициализации:
1. Узел 1 стартует с вызовом `BootstrapCluster`, содержащим только узел 1. Он немедленно становится лидером (\(1/1\)).
2. Узлы 2 и 3 запускаются без бутстрапа в режиме ожидания (Empty Follower State), слушая свои порты.
3. Клиент отправляет Лидеру (узлу 1) вызов `AddVoter("node-2", "127.0.0.1:8302", 0, timeout)`.
4. Лидер реплицирует конфигурационную запись, соединяется по TCP с узлом 2 и вводит его в состав участников.
5. Следом аналогично вызывается `AddVoter("node-3", "127.0.0.1:8303", 0, timeout)`.
В итоге кластер переходит в устойчивое состояние из 3 узлов с кворумом 2.

## Решение по шагам

1. Создаем структуру TCPNodeConfig с адресом порта и идентификатором.
2. Инициализируем Узел 1 как Bootstrap-лидера.
3. Подключаем Узел 2 и Узел 3 через метод AddVoter.
4. Проверяем установку сетевой связности между всеми узлами.
5. Подтверждаем, что в кластере сформирован кворум 2 из 3.

## Код решения

**`multi_node_cluster_setup.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type NodeEndpoint struct {
	ID   string
	Addr string
	Role string
}

type ClusterManager struct {
	mu      sync.Mutex
	leader  *NodeEndpoint
	peers   map[string]*NodeEndpoint
	voters  int
}

func NewClusterManager() *ClusterManager {
	return &ClusterManager{
		peers: make(map[string]*NodeEndpoint),
	}
}

func (m *ClusterManager) BootstrapLeader(id, addr string) {
	m.mu.Lock()
	defer m.mu.Unlock()

	ep := &NodeEndpoint{ID: id, Addr: addr, Role: "LEADER"}
	m.leader = ep
	m.peers[id] = ep
	m.voters = 1
	fmt.Printf("[%s] Bootstrap successful on %s. Acting as standalone LEADER.\n", id, addr)
}

func (m *ClusterManager) AddVoterPeer(id, addr string) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	if m.leader == nil {
		return fmt.Errorf("cannot add voter: cluster has no leader")
	}

	ep := &NodeEndpoint{ID: id, Addr: addr, Role: "FOLLOWER"}
	m.peers[id] = ep
	m.voters++

	quorum := (m.voters / 2) + 1
	fmt.Printf("[Cluster] Added Voter %s (%s). Total Nodes: %d, New Quorum: %d\n",
		id, addr, m.voters, quorum)
	return nil
}

func main() {
	mgr := NewClusterManager()

	// 1. Поднимаем узел 1 на порту 8301
	mgr.BootstrapLeader("srv-1", "127.0.0.1:8301")

	// 2. Подключаем узел 2 на порту 8302
	time.Sleep(20 * time.Millisecond)
	_ = mgr.AddVoterPeer("srv-2", "127.0.0.1:8302")

	// 3. Подключаем узел 3 на порту 8303
	time.Sleep(20 * time.Millisecond)
	_ = mgr.AddVoterPeer("srv-3", "127.0.0.1:8303")

	fmt.Println("\n3-node TCP Raft cluster successfully established and coordinated.")
}
```

## Под капотом

При выполнении `AddVoter` в `hashicorp/raft` лидер открывает TCP-сокет к новому адресу, отправляет RPC `AppendEntries` и ждет подтверждения. После того как конфигурационная запись о добавлении узла коммитится в логе, лидер начинает рассылать heartbeats новому узлу с периодичностью `HeartbeatTimeout`.

## Подводные камни

Указание недостижимого IP/порта при вызове `AddVoter`: если передать ошибочный адрес, лидер заблокируется на время таймаута соединения (`ConnectTimeout`). Если в это время происходят другие операции, кластер кратковременно испытает всплеск задержки.

## На собеседовании

В: Что произойдет, если добавить 2-й узел, но 3-й узел так и не будет запущен?
О: Кластер станет 2-узловым. Для 2 узлов кворум равен 2. Это значит, что если узел 1 или узел 2 упадет, кластер полностью потеряет доступность на запись! Поэтому добавление узлов до нечетного размера (3) должно завершаться без задержек.
