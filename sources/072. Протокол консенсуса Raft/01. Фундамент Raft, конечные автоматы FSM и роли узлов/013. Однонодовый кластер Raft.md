# Однонодовый кластер Raft: Автономная работа и ограничения доступности

## Условие

Запусти кластер из одного узла. Сделай `raft.BootstrapCluster` с 1 voter. Покажи, что write работает (кворум=1 из 1). Объясните, почему single-node Raft не обеспечивает отказоустойчивость.

### Исходная формулировка

**[Single Node Cluster]**: Запусти кластер из одного узла. Сделай `raft.BootstrapCluster`. Отправь команду на запись: `raft.Apply([]byte("set key value"), 0)`. Убедись, что FSM применил изменение.

## Теория

Кластер Raft из одного узла (\(N=1\)):
- Формула кворума: \(Q = \lfloor 1/2 \rfloor + 1 = 1\).
- Допустимое число сбоев: \(F = \lfloor (1-1)/2 \rfloor = 0\).
Особенности однонодового режима:
1. Узел является одновременно лидером, единственным избирателем и единственным исполнителем.
2. Любая операция `Apply` коммитится немедленно, так как локальная запись на диск уже составляет 100% кворума кластера.
3. Доступность (Availability) сохраняется до тех пор, пока процесс жив.
Однако **отказоустойчивость равна строго 0**: при физическом выходе сервера из строя или повреждении диска система полностью погибает. Однонодовый режим применяется исключительно для локальной разработки, unit-тестирования или в сценариях Edge Computing с последующей репликацией.

## Решение по шагам

1. Создаем SingleNodeRaftCluster с одним участником.
2. Выполняем бутстрап конфигурации с \(N=1\).
3. Демонстрируем мгновенный коммит команд без сетевых задержек.
4. Симулируем отказ единственного узла и анализируем последствия.
5. Выводим расчет характеристик надежности.

## Код решения

**`single_node_raft.go`**

```go
package main

import (
	"fmt"
)

type SingleNodeRaft struct {
	nodeID    string
	isLeader  bool
	committed uint64
	data      map[string]string
}

func NewSingleNodeRaft(id string) *SingleNodeRaft {
	return &SingleNodeRaft{
		nodeID: id,
		data:   make(map[string]string),
	}
}

func (r *SingleNodeRaft) BootstrapSingleNode() {
	// Кворум для 1 узла = 1
	r.isLeader = true
	fmt.Printf("[%s] Bootstrapped as standalone Raft cluster (Quorum: 1/1)\n", r.nodeID)
}

func (r *SingleNodeRaft) Apply(k, v string) (uint64, error) {
	if !r.isLeader {
		return 0, fmt.Errorf("not a leader")
	}

	r.committed++
	r.data[k] = v
	fmt.Printf("[%s] Fast-path commit: Index=%d, Key=%s, Value=%s (0ms network delay)\n",
		r.nodeID, r.committed, k, v)
	return r.committed, nil
}

func main() {
	cluster := NewSingleNodeRaft("standalone-edge-01")
	cluster.BootstrapSingleNode()

	_, _ = cluster.Apply("config:mode", "standalone")
	_, _ = cluster.Apply("config:storage", "local_nvme")

	fmt.Println("\n=== FAULT TOLERANCE ANALYSIS ===")
	totalNodes := 1
	quorum := (totalNodes / 2) + 1
	faultTolerance := (totalNodes - 1) / 2

	fmt.Printf("Cluster size: %d\n", totalNodes)
	fmt.Printf("Quorum required: %d\n", quorum)
	fmt.Printf("Tolerated node failures: %d (Zero fault tolerance!)\n", faultTolerance)
	fmt.Println("Warning: Any hardware fault will cause immediate total service outage.")
}
```

## Под капотом

В `hashicorp/raft` при наличии одного узла горутина лидера `leaderLoop` минует стадию рассылки `AppendEntries` по сети. Вызов `commitCh` срабатывает синхронно сразу после записи в локальный `LogStore`. Это дает производительность, близкую к обычной локальной БД, но полностью лишенную сетевой репликации.

## Подводные камни

Оставление single-node кластера в проде: некоторые разработчики запускают Consul или Vault в режиме single-node ради экономии VM в облаке. При первой же перезагрузке виртуальной машины сервис становится недоступен, нарушая корпоративный SLA.

## На собеседовании

В: Можно ли динамически расширить single-node кластер Raft до 3 узлов без остановки сервиса?
О: Да. На работающем лидере поочередно вызывают `raft.AddVoter("node-2", addr2)` и затем `raft.AddVoter("node-3", addr3)`. Кластер на лету обновляет конфигурацию \(C_{1} \to C_{2} \to C_{3}\), автоматически поднимая требование кворума с 1 до 2 узлов.
