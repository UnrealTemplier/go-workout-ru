# Фундаментальные концепции Raft: Роли, Каденции (Terms) и Инварианты

## Условие

Изучите 5 ключевых концепций Raft: Leader (один в кластере), Follower (пассивный наблюдатель), Candidate (кандидат на выборах), Term (логическое время/эпоха), Log (упорядоченная последовательность записей). Реализуйте переход состояний.

### Исходная формулировка

**Raft концепции**: Изучите 5 ключевых концепций:
* Leader (один в кластере)
* Followers (реплицируют state)
* Candidates (участвуют в выборах)
* Terms (логические периоды времени)
* Log entries (команды для state machine)

## Теория

Протокол Raft декомпозирует консенсус на три самостоятельные ортогональные подзадачи:
1. **Выборы лидера (Leader Election):** при падении текущего лидера избирается ровно один новый лидер.
2. **Репликация лога (Log Replication):** лидер принимает клиентские команды, добавляет в свой лог и реплицирует на фоловеры.
3. **Безопасность (Safety):** если любой узел применил запись к FSM по индексу \(I\), ни один другой узел никогда не сможет применить другую запись по этому индексу.
Машина состояний узла включает 3 роли:
- **Follower:** пассивен. Отвечает только на RPC от кандидатов (`RequestVote`) и лидеров (`AppendEntries`). Если heartbeat не поступает в течение `ElectionTimeout`, фоловер переходит в статус `Candidate`.
- **Candidate:** инкрементирует `Term`, голосует за себя и рассылает `RequestVote` всем узлам. При наборе большинства (\(\lfloor N/2 \rfloor + 1\)) становится `Leader`.
- **Leader:** обслуживает все клиентские запросы, координирует репликацию лога и рассылает периодические heartbeats.
Понятие **Term (Каденция/Эпоха):** монотонно возрастающее логическое время (Logical Clock). Term позволяет узлам мгновенно обнаруживать устаревшую информацию: если входящий RPC содержит Term больше локального, узел обновляет свой Term и переходит в статус Follower.

## Решение по шагам

1. Описываем перечисление NodeRole (RoleFollower, RoleCandidate, RoleLeader).
2. Создаем структуру RaftNodeCore с полями currentTerm, votedFor, role.
3. Реализуем метод StartElection(): переход из Follower в Candidate с инкрементом Term.
4. Реализуем метод WinElection(): переход из Candidate в Leader при получении кворума.
5. Реализуем метод ObserveHigherTerm(higherTerm): принудительный сброс роли в Follower при обнаружении более нового Term.

## Код решения

**`raft_roles_fsm.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type NodeRole string

const (
	RoleFollower  NodeRole = "FOLLOWER"
	RoleCandidate NodeRole = "CANDIDATE"
	RoleLeader    NodeRole = "LEADER"
)

type RaftNodeCore struct {
	mu          sync.Mutex
	id          string
	currentTerm uint64
	votedFor    string
	role        NodeRole
}

func NewRaftNodeCore(id string) *RaftNodeCore {
	return &RaftNodeCore{
		id:          id,
		currentTerm: 0,
		votedFor:    "",
		role:        RoleFollower,
	}
}

// 1. Истек ElectionTimeout: переходим в Candidate
func (n *RaftNodeCore) StartElection() uint64 {
	n.mu.Lock()
	defer n.mu.Unlock()

	n.role = RoleCandidate
	n.currentTerm++
	n.votedFor = n.id // Голосуем за себя
	fmt.Printf("[%s] Timeout! Transition to CANDIDATE in Term %d (voted for self)\n", n.id, n.currentTerm)
	return n.currentTerm
}

// 2. Получен кворум голосов: переходим в Leader
func (n *RaftNodeCore) WinElection(votesReceived, totalNodes int) bool {
	n.mu.Lock()
	defer n.mu.Unlock()

	if n.role != RoleCandidate {
		return false
	}

	quorum := (totalNodes / 2) + 1
	if votesReceived >= quorum {
		n.role = RoleLeader
		fmt.Printf("[%s] Quorum reached (%d/%d)! Promoted to LEADER in Term %d\n",
			n.id, votesReceived, totalNodes, n.currentTerm)
		return true
	}
	return false
}

// 3. Обнаружен более высокий Term: немедленный возврат в Follower
func (n *RaftNodeCore) CheckTerm(remoteTerm uint64, remoteLeaderID string) bool {
	n.mu.Lock()
	defer n.mu.Unlock()

	if remoteTerm > n.currentTerm {
		fmt.Printf("[%s] Discovered higher Term %d from %s (local Term was %d). Demoting to FOLLOWER.\n",
			n.id, remoteTerm, remoteLeaderID, n.currentTerm)
		n.currentTerm = remoteTerm
		n.role = RoleFollower
		n.votedFor = ""
		return true
	}
	return false
}

func (n *RaftNodeCore) Status() (string, NodeRole, uint64) {
	n.mu.Lock()
	defer n.mu.Unlock()
	return n.id, n.role, n.currentTerm
}

func main() {
	node := NewRaftNodeCore("node-srv-01")

	_, role, term := node.Status()
	fmt.Printf("Initial state: Role=%s, Term=%d\n", role, term)

	// Истекает таймер выборов
	_ = node.StartElection()

	// Получены голоса большинства (2 из 3 узлов)
	node.WinElection(2, 3)
	_, role, term = node.Status()
	fmt.Printf("State after election: Role=%s, Term=%d\n\n", role, term)

	// Приходит RPC от другого узла с более высоким Term 5
	fmt.Println("--- Incoming RPC with Term 5 from node-srv-03 ---")
	node.CheckTerm(5, "node-srv-03")

	_, role, term = node.Status()
	fmt.Printf("Final state: Role=%s, Term=%d\n", role, term)
}
```

## Под капотом

В исходном коде Raft (как в etcd/raft, так и в hashicorp/raft) смена состояний реализована через метод `becomeFollower(term, leaderID)`. При любом обнаружении \(Term_{remote} > Term_{local}\) узел обязан сохранить обновленный Term на диск (Stable Storage / WAL) ПЕРЕД тем, как отправить ответ на RPC. Это предотвращает двойное голосование при рестарте узла.

## Подводные камни

Голосование дважды в одном Term: если узел отдал голос за Кандидата A в Term 2, а потом из-за сетевой задержки получил запрос от Кандидата B с тем же Term 2, он категорически НЕ ДОЛЖЕН голосовать за B. Поле `votedFor` фиксируется в памяти и на диске. Голосовать можно строго за одного кандидата в рамках одного Term.

## На собеседовании

В: Почему в Raft не может существовать двух лидеров в одном и том же Term?
О: Инвариант Election Safety: для победы кандидат обязан получить голоса строгого большинства узлов (\(\lfloor N/2 \rfloor + 1\)). Каждый узел может отдать не более одного голоса за данный Term. Поскольку любые два большинства из \(N\) узлов обязательно пересекаются хотя бы в одном узле, два кандидата физически не могут одновременно набрать кворум в одной каденции.
