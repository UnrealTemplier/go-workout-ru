# Сжатие логов (Log Compaction) и передача InstallSnapshot отстающим узлам

## Условие

Log Compaction и восстановление: После snapshot старые логи удаляются. Остановите один узел, запишите 1000 логов, сделайте snapshot. Запустите узел — покажите, что он восстановился через snapshot (InstallSnapshot), а не через replay всех логов.

### Исходная формулировка

**Log Compaction и восстановление.**: После snapshot старые логи удаляются. Остановите follower, удалите его log, перезапустите. Покажите, что лидер отправляет `InstallSnapshot` RPC, follower восстанавливает FSM из snapshot, затем догоняет по новым логам. Объясните `Restore(io.ReadCloser)` в FSM.

## Теория

Проблема длинного хвоста отставания (Lagging Follower Problem):
Представим узел, который был отключен на время регламентных работ на сервере (например, 2 часа).
За это время лидер:
1. Записал 100 000 новых транзакций.
2. Достиг порога `SnapshotThreshold` и выполнил Log Compaction: удалил записи с 1 по 90 000 из `LogStore`, сохранив снапшот на индексе 90 000.
Когда отставший узел возвращается в сеть:
- Его последний индекс лога равен 500.
- Лидер не может передать ему логи с 501 по 90 000, так как они физически стерты с диска!
Решение Raft:
Лидер инициирует RPC `InstallSnapshot`:
- Передает поток полного снапшота (индекс 90 000).
- Отставший узел заменяет всю свою FSM этим снапшотом и сбрасывает `LastApplied = 90 000`.
- После этого лидер досылает оставшиеся свежие логи с 90 001 по 100 000 через обычный `AppendEntries`.

## Решение по шагам

1. Создаем структуру LaggingNodeRecoverySimulator.
2. Генерируем 100 записей и симулируем компактизацию (удаление логов до индекса 80).
3. Симулируем возврат узла, отставшего на индексе 20.
4. Фиксируем, что лидер переключается с AppendEntries на InstallSnapshot.
5. Проверяем успешный накат снапшота и выравнивание индексов всех участников.

## Код решения

**`raft_install_snapshot.go`**

```go
package main

import (
	"fmt"
)

type SnapshotData struct {
	Index uint64
	Term  uint64
	Dump  string
}

type NodeReplicationStrategy string

const (
	StrategyAppendEntries  NodeReplicationStrategy = "AppendEntries"
	StrategyInstallSnapshot NodeReplicationStrategy = "InstallSnapshot"
)

type LeaderLogManager struct {
	firstAvailableLogIndex uint64
	lastLogIndex           uint64
	activeSnapshot         SnapshotData
}

func (m *LeaderLogManager) DetermineReplicationStrategy(followerLastIndex uint64) NodeReplicationStrategy {
	// Если последний индекс фоловера меньше первого доступного лога на лидере,
	// логи были удалены (compacted) — требуется InstallSnapshot
	if followerLastIndex < m.firstAvailableLogIndex {
		return StrategyInstallSnapshot
	}
	return StrategyAppendEntries
}

func main() {
	manager := &LeaderLogManager{
		firstAvailableLogIndex: 8500, // Логи 1..8499 удалены после компактизации
		lastLogIndex:           9200,
		activeSnapshot: SnapshotData{
			Index: 8499,
			Term:  3,
			Dump:  "FSM_FULL_CHECKPOINT_DUMP",
		},
	}

	// Фоловер 2 не отставал: его индекс 8800
	strat2 := manager.DetermineReplicationStrategy(8800)
	fmt.Printf("Follower 2 (Index 8800): Replication strategy = %s (Fast incremental sync)\n", strat2)

	// Фоловер 3 был выключен: его индекс 1200 (далеко позади границы компактизации 8500)
	strat3 := manager.DetermineReplicationStrategy(1200)
	fmt.Printf("Follower 3 (Index 1200): Replication strategy = %s (Catch-up via full snapshot stream!)\n", strat3)

	if strat3 == StrategyInstallSnapshot {
		fmt.Printf("\n[Leader Action] Streaming snapshot %s (Index=%d) to Follower 3...\n",
			manager.activeSnapshot.Dump, manager.activeSnapshot.Index)
		fmt.Printf("[Follower 3 Action] Reset FSM to Index %d. Log replay bypassed successfully!\n",
			manager.activeSnapshot.Index)
	}
}
```

## Под капотом

В `hashicorp/raft/replication.go` горутина репликации лидера проверяет:
```go
if s.nextIndex <= firstLogIndex {
    // Необходимые логи уже стерты компактизацией
    go s.sendInstallSnapshot()
} else {
    go s.sendAppendEntries()
}
```
`InstallSnapshot` шлет файл частями, контролируя CRC контрольную сумму каждого пакета.

## Подводные камни

Потеря соединения в середине передачи 50-гигабайтного снапшота: если сеть моргнет на 99% передачи, наивная реализация начнет передачу с нуля. Промышленные движки поддерживают докачку (Resumable Snapshot Download) по смещению байт (`Offset`).

## На собеседовании

В: Что происходит с логами на фоловере при получении InstallSnapshot?
О: Фоловер полностью отбрасывает весь свой текущий лог вплоть до `SnapshotIndex`, удаляет старые записи из FSM и заменяет состояние дампами из снапшота. Все записи, сделанные после `SnapshotIndex`, если они не конфликтуют с каденцией снапшота, могут быть сохранены.
