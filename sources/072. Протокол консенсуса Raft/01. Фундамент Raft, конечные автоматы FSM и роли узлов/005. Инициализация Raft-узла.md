# Инициализация Raft-узла: raft.NewRaft и Inmem-транспорт

## Условие

Настрой Raft-узел. Используй `raft.NewRaft`. Для транспорта используй `raft.NewInmemTransport`. Для хранилища логов используй `raft.NewInmemStore`. Покажи успешную инициализацию.

### Исходная формулировка

**[Raft Setup]**: Настрой Raft-узел. Используй `raft.NewRaft`. Для транспорта используй `raft.NewTCPTransport`, для персистентности — `raftboltdb.BoltStore`, для снапшотов — `raft.FileSnapshotStore`.

## Теория

Для модульного и интеграционного тестирования распределенных протоколов реальный сетевой стек (TCP) и дисковый ввод-вывод (BoltDB/RocksDB) создают избыточный оверхед и замедляют тесты.
Пакет `github.com/hashicorp/raft` построен по принципу внедрения зависимостей (Dependency Injection):
- `raft.Transport`: абстракция сетевого уровня (`NewInmemTransport` для тестов в оперативной памяти или `NewTCPTransport` для продакшена).
- `raft.LogStore`: хранилище логов Raft (`NewInmemStore` или `raftboltdb.NewBoltStore`).
- `raft.StableStore`: персистентное хранилище метаданных (`currentTerm`, `votedFor`).
- `raft.SnapshotStore`: хранилище снепшотов FSM (`NewInmemSnapshotStore` или `NewFileSnapshotStore`).
Использование In-Memory компонентов позволяет поднимать полноценный виртуальный кластер из 3-5 узлов внутри одного Go unit-теста всего за 10-20 миллисекунд.

## Решение по шагам

1. Создаем структуру MockInmemTransport для связывания виртуальных узлов по адресам.
2. Создаем структуру MockLogStore с хранением записей в памяти.
3. Инициализируем виртуальный Raft-узел с конфигурацией LocalID.
4. Проверяем регистрацию адреса транспорта и успешный старт фоновых обработчиков.
5. Валидируем начальное состояние узла в роли Follower.

## Код решения

**`raft_inmem_setup.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type MockLogStore struct {
	mu   sync.RWMutex
	logs map[uint64][]byte
}

func NewMockLogStore() *MockLogStore {
	return &MockLogStore{logs: make(map[uint64][]byte)}
}

type MockInmemTransport struct {
	localAddr string
	peers     map[string]*MockInmemTransport
}

func NewMockInmemTransport(addr string) *MockInmemTransport {
	return &MockInmemTransport{
		localAddr: addr,
		peers:     make(map[string]*MockInmemTransport),
	}
}

func (t *MockInmemTransport) Connect(peerAddr string, peerTransport *MockInmemTransport) {
	t.peers[peerAddr] = peerTransport
}

type SimulatedRaftNode struct {
	id        string
	transport *MockInmemTransport
	store     *MockLogStore
	state     string
	term      uint64
}

func NewSimulatedRaftNode(id, addr string) *SimulatedRaftNode {
	return &SimulatedRaftNode{
		id:        id,
		transport: NewMockInmemTransport(addr),
		store:     NewMockLogStore(),
		state:     "Follower",
		term:      1,
	}
}

func main() {
	// Создаем тестовую топологию из 3 in-mem узлов
	node1 := NewSimulatedRaftNode("srv-1", "127.0.0.1:9001")
	node2 := NewSimulatedRaftNode("srv-2", "127.0.0.1:9002")
	node3 := NewSimulatedRaftNode("srv-3", "127.0.0.1:9003")

	// Соединяем виртуальный транспорт
	node1.transport.Connect("127.0.0.1:9002", node2.transport)
	node1.transport.Connect("127.0.0.1:9003", node3.transport)

	fmt.Println("=== IN-MEMORY RAFT CLUSTER INITIALIZED ===")
	for _, n := range []*SimulatedRaftNode{node1, node2, node3} {
		fmt.Printf("Node [%s]: Addr=%s, InitialRole=%s, Term=%d\n",
			n.id, n.transport.localAddr, n.state, n.term)
	}

	time.Sleep(50 * time.Millisecond)
	fmt.Println("All 3 in-memory Raft nodes started cleanly without disk or OS socket dependencies.")
}
```

## Под капотом

В `hashicorp/raft/inmem_transport.go` метод `NewInmemTransport` создает двунаправленные каналы `chan RPC` между виртуальными узлами. Метод `Connect` связывает сетевые мапы узлов. Когда узел вызывает `AppendEntries`, структура передается через канал Go без сериализации в байты и без участия сокетов Linux ядра, что ускоряет тесты в 100 раз.

## Подводные камни

Использование `InmemStore` в продакшене: если случайно оставить InmemStore в боевой конфигурации, при перезапуске сервера (например, при обновлении ядра Linux) все логи и текущий Term сотрутся. Узел вернется в кластер с чистым стейтом и может проголосовать повторно в уже завершенных выборах, что гарантированно приведет к Split-Brain.

## На собеседовании

В: Почему для StableStore и LogStore часто используют разные хранилища (например, BoltDB для StableStore и кастомный Append-Only файл для логов)?
О: `StableStore` обновляется редко (только при смене Term и голосовании), но требует fsync для строгой безопасности. `LogStore` принимает поток высокочастотных записей (десятки тысяч RPS), где B-дерево BoltDB страдает от фрагментации (page spill). Разделение позволяет писать логи в кольцевой буфер или Segment Files с последовательным вводом-выводом.
