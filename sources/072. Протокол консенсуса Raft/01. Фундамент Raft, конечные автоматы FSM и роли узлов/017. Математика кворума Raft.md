# Математика кворума Raft: Расчет большинства и анализ доступности

## Условие

Raft quorum: Поймите quorum: для 3 узлов quorum = 2. Для 5 узлов quorum = 3. Без quorum кластер блокирует write, но может разрешать stale read. Реализуйте проверку доступности кворума.

### Исходная формулировка

**Raft quorum**: Поймите quorum: для 3 узлов quorum = 2. Для 5 узлов quorum = 3. Без quorum кластер не может принимать writes.

## Теория

Консенсус Raft — это протокол строгой согласованности на базе кворумов (CP-система по теореме CAP).
Для кластера размера \(N\):
$$\text{Quorum} = \left\lfloor \frac{N}{2} \right\rfloor + 1$$
Если в живых остается \(K < \text{Quorum}\) узлов:
- **Запись (Writes):** полностью блокируется. Ни одна новая запись не может быть закоммичена, так как невозможно получить согласие большинства.
- **Линеаризуемое чтение (Consistent Read):** блокируется, так как лидер не может подтвердить свой статус через `ReadIndex`.
- **Устаревшее чтение (Stale Read):** технически возможно, если клиент явно согласен на возврат неконсистентных данных из локальной памяти выжившего узла.

## Решение по шагам

1. Создаем структуру QuorumAvailabilityChecker с количеством активных узлов.
2. Реализуем метод CanCommitWrites().
3. Реализуем метод EvaluateReadMode(requireLinearizable).
4. Проверяем поведение для кластеров из 3 и 5 узлов при различных отказах.
5. Выводим статус готовности кластера к обработке трафика.

## Код решения

**`raft_quorum_evaluator.go`**

```go
package main

import (
	"errors"
	"fmt"
)

var (
	ErrWriteBlockedNoQuorum = errors.New("write blocked: strict majority quorum lost")
	ErrLinearizableReadBlocked = errors.New("linearizable read blocked: cannot verify leader authority")
)

type ClusterHealth struct {
	TotalNodes int
	AliveNodes int
}

func (c ClusterHealth) QuorumRequired() int {
	return (c.TotalNodes / 2) + 1
}

func (c ClusterHealth) HasQuorum() bool {
	return c.AliveNodes >= c.QuorumRequired()
}

func (c ClusterHealth) ExecuteWrite(cmd string) error {
	if !c.HasQuorum() {
		return fmt.Errorf("%w (Alive=%d, Required=%d)",
			ErrWriteBlockedNoQuorum, c.AliveNodes, c.QuorumRequired())
	}
	fmt.Printf("Write '%s' successfully committed to quorum (%d/%d nodes ACK)\n",
		cmd, c.AliveNodes, c.TotalNodes)
	return nil
}

func (c ClusterHealth) ExecuteRead(requireStrong bool) (string, error) {
	if requireStrong {
		if !c.HasQuorum() {
			return "", ErrLinearizableReadBlocked
		}
		return "Linearizable_Consistent_Value", nil
	}
	// Stale Read разрешен даже в меньшинстве
	return "Potentially_Stale_Cached_Value", nil
}

func main() {
	// Сценарий 1: Кластер из 3 узлов, 2 живы (нормальный режим с 1 отказом)
	c1 := ClusterHealth{TotalNodes: 3, AliveNodes: 2}
	fmt.Println("=== SCENARIO 1: 3-node cluster, 1 node failed ===")
	_ = c1.ExecuteWrite("SET user:1 = Active")
	val1, _ := c1.ExecuteRead(true)
	fmt.Printf("Read strong: %s\n\n", val1)

	// Сценарий 2: Тот же кластер, 2 узла упали (остался 1 узел)
	c2 := ClusterHealth{TotalNodes: 3, AliveNodes: 1}
	fmt.Println("=== SCENARIO 2: 3-node cluster, 2 nodes failed (Quorum Lost) ===")
	errWrite := c2.ExecuteWrite("SET user:2 = Blocked")
	fmt.Printf("Write attempt: %v\n", errWrite)

	_, errReadStrong := c2.ExecuteRead(true)
	fmt.Printf("Strong Read attempt: %v\n", errReadStrong)

	valStale, _ := c2.ExecuteRead(false)
	fmt.Printf("Stale Read attempt: %s (Allowed under CAP AP-fallback)\n", valStale)
}
```

## Под капотом

В алгоритме Raft разделение на чтение и запись четко разграничено: запись ВСЕГДА требует согласия большинства в логе. Для чтений в `etcd` и `hashicorp/raft` есть настройка `ConsistencyMode`: `Consistent` (ReadIndex через кворум) или `Stale` (чтение из памяти локальной FSM без сетевого раунда).

## Подводные камни

Включение Stale Reads в биллинговых операциях: чтение баланса со stale-реплики может показать старое положительное сальдо, в то время как лидер уже зафиксировал списание средств. Результат — двойная трата (Double Spending). Stale Reads допустимы только для неизменяемых справочников или аналитики.

## На собеседовании

В: Почему в Raft нельзя использовать кворум \(\ge N/2\) вместо \(> N/2\)?
О: Если кворум равен ровно половине (\(\ge N/2\)), то в четном кластере (\(N=4\)) две половины по 2 узла смогут одновременно сформировать кворум. Каждая половина изберет своего лидера, вызвав фатальный Split-Brain. Кворум обязан быть строго больше половины: \(\lfloor N/2 \rfloor + 1\).
