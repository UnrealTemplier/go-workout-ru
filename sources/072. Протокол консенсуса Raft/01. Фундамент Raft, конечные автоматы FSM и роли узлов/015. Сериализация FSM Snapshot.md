# Сериализация FSM Snapshot: Сжатие и потоковая передача в io.Writer

## Условие

Реализуйте `FSM.Snapshot()` — сериализация `map[string]string` в `io.Writer`. Продемонстрируйте gzip-сжатие при сохранении и проверьте восстановление.

### Исходная формулировка

**Snapshotting.**: Реализуйте `FSM.Snapshot()` — сериализация `map[string]string` в `io.Writer` (например, gob/json). Настройте `SnapshotInterval = 20s`, `SnapshotThreshold = 8192`. Покажите, что Raft автоматически вызывает `Snapshot` и создаёт файл снимка. Объясните, зачем нужен snapshot (ограничение роста лога).

## Теория

В крупных production-системах размер оперативного состояния FSM может составлять сотни мегабайт или гигабайты.
Передача и сохранение несжатого JSON или текстового формата создает чрезмерную нагрузку на дисковую подсистему и сеть при `InstallSnapshot`.
Применение потокового сжатия (Streaming Compression) через стандартный пакет Go `compress/gzip`:
- Сериализатор подключается по цепочке: `FSM -> json.Encoder -> gzip.Writer -> io.Writer (SnapshotSink)`.
- Данные сжимаются «на лету» потоком без выделения гигантских промежуточных слайсов байт в куче (`zero extra memory allocation`).
- Коэффициент сжатия текстовых структур и JSON в FSM обычно достигает \(70 - 85\%\), сокращая время репликации снапшота по сети в 4-6 раз.

## Решение по шагам

1. Создаем сериализатор сжатого снапшота с использованием `compress/gzip`.
2. Реализуем метод PersistWithGzip(w, data).
3. Реализуем метод RestoreFromGzip(r).
4. Замеряем размер сырых данных и сжатого потока.
5. Проверяем полное восстановление словаря данных из сжатого потока.

## Код решения

**`fsm_gzip_snapshot.go`**

```go
package main

import (
	"bytes"
	"compress/gzip"
	"encoding/json"
	"fmt"
	"io"
)

type CompressedFSMSnapshot struct {
	state map[string]string
}

func (s *CompressedFSMSnapshot) PersistGzip(sink io.Writer) error {
	gzWriter := gzip.NewWriter(sink)
	defer gzWriter.Close()

	if err := json.NewEncoder(gzWriter).Encode(s.state); err != nil {
		return fmt.Errorf("gzip encoding error: %w", err)
	}

	return gzWriter.Flush()
}

func RestoreGzip(source io.Reader) (map[string]string, error) {
	gzReader, err := gzip.NewReader(source)
	if err != nil {
		return nil, fmt.Errorf("gzip init error: %w", err)
	}
	defer gzReader.Close()

	var restored map[string]string
	if err := json.NewDecoder(gzReader).Decode(&restored); err != nil {
		return nil, fmt.Errorf("decode error: %w", err)
	}

	return restored, nil
}

func main() {
	// Создаем тестовое состояние из 200 ключей
	largeState := make(map[string]string)
	for i := 1; i <= 200; i++ {
		largeState[fmt.Sprintf("user:profile:%04d:preferences", i)] = "theme=dark;lang=ru;notifications=enabled;timezone=Europe/Moscow"
	}

	rawJSON, _ := json.Marshal(largeState)
	rawSize := len(rawJSON)

	// Сохраняем через gzip
	snap := &CompressedFSMSnapshot{state: largeState}
	var compressedBuf bytes.Buffer
	_ = snap.PersistGzip(&compressedBuf)
	compressedSize := compressedBuf.Len()

	ratio := (1.0 - float64(compressedSize)/float64(rawSize)) * 100.0

	fmt.Println("=== FSM SNAPSHOT STREAMING COMPRESSION ===")
	fmt.Printf("Raw JSON snapshot size:        %d bytes\n", rawSize)
	fmt.Printf("Compressed Gzip snapshot size: %d bytes\n", compressedSize)
	fmt.Printf("Space Saved:                   %.2f%%\n", ratio)

	// Восстанавливаем из сжатого буфера
	restored, err := RestoreGzip(&compressedBuf)
	if err != nil {
		fmt.Printf("Restore error: %v\n", err)
	} else {
		fmt.Printf("\nVerification: Restored %d keys cleanly. Sample key 'user:profile:0042:preferences' = '%s'\n",
			len(restored), restored["user:profile:0042:preferences"])
	}
}
```

## Под капотом

При потоковой передаче `InstallSnapshot` лидер читает сжатый файл блоками (chunks) по 32-64 КБ и шлет их в RPC сообщениях `InstallSnapshotRequest{Data: chunk, Offset: offset}`. Фоловер сразу направляет входящие чанки в `gzip.Reader`, распаковывая данные прямо в память FSM без промежуточного сохранения несжатого файла на диск.

## Подводные камни

Забытый вызов `gzWriter.Close()` перед завершением `Persist`: `gzip.Writer` записывает контрольную сумму CRC-32 и итоговый футер только при явном вызове `Close()`. Если закрыть поток после возврата из функции без flush/close, снапшот окажется поврежденным (`unexpected EOF` при чтении).

## На собеседовании

В: Почему для сжатия снапшотов в HighLoad системах часто выбирают Zstandard (zstd) или Snappy вместо Gzip?
О: Gzip создает ощутимую нагрузку на CPU при высоких уровнях компрессии. Алгоритмы Snappy и Zstd (level 1-3) обеспечивают сравнимую степень сжатия при скорости декомпрессии свыше 1-2 ГБ/сек на ядро, что критично для минимизации паузы восстановления узлов.
