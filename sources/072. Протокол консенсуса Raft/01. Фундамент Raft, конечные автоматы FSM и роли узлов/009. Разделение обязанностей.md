# Разделение обязанностей: Обработка команд Лидером и перенаправление Фоловером

## Условие

Реализуйте HTTP/gRPC endpoint: лидер принимает write-команды, а follower отклоняет их (возвращает ошибку `ErrNotLeader` с адресом текущего лидера) или проксирует запрос.

### Исходная формулировка

**Лидер и Follower.**: Реализуйте endpoint: лидер принимает write-команды, follower отклоняет с `not leader`. Покажите, что чтение с follower возвращает данные, но они могут быть stale (не linearizable). Объясните разницу между `raft.StateLeader`, `StateFollower`, `StateCandidate`.

## Теория

В протоколе Raft действует строгое правило: все мутирующие операции (Writes) имеют право инициироваться исключительно текущим Лидером (Strong Leader Principle).
Поведение фоловеров при поступлении запроса на запись:
1. **Redirect (HTTP 307):** фоловер возвращает ошибку `ErrNotLeader` с заголовком `X-Raft-Leader: <leader_address>`. Клиентский SDK перенаправляет запрос на указанный адрес.
2. **Proxy Forwarding:** фоловер прозрачно пересылает тело запроса лидеру через внутренний gRPC/HTTP канал, дожидается ответа лидера и возвращает его клиенту.
Если в кластере в данный момент происходят выборы и лидер отсутствует (`leader == ""`), фоловер возвращает клиенту код `503 Service Unavailable` с рекомендацией повторить попытку через случайный backoff.

## Решение по шагам

1. Создаем структуру WriteRequest и WriteResponse.
2. Создаем HTTP-хэндлер RaftWriteHandler с проверкой статуса текущего узла.
3. Если узел — Лидер, запрос применяется к FSM и возвращается результат.
4. Если узел — Фоловер, возвращается заголовок редиректа и адрес лидера.
5. Проверяем работу эндпоинта для обоих сценариев.

## Код решения

**`raft_leader_redirect.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type WriteCommandPayload struct {
	Key   string `json:"key"`
	Value string `json:"value"`
}

type NodeRoleHandler struct {
	mu         sync.RWMutex
	isLeader   bool
	nodeID     string
	leaderAddr string
	fsmData    map[string]string
}

func NewNodeRoleHandler(nodeID string, isLeader bool, leaderAddr string) *NodeRoleHandler {
	return &NodeRoleHandler{
		nodeID:     nodeID,
		isLeader:   isLeader,
		leaderAddr: leaderAddr,
		fsmData:    make(map[string]string),
	}
}

func (h *NodeRoleHandler) HandleWrite(w http.ResponseWriter, r *http.Request) {
	h.mu.RLock()
	leading := h.isLeader
	currLeader := h.leaderAddr
	h.mu.RUnlock()

	// Если узел не лидер — отклоняем запрос и даем адрес лидера
	if !leading {
		if currLeader == "" {
			http.Error(w, "Cluster election in progress, no leader available", http.StatusServiceUnavailable)
			return
		}

		w.Header().Set("X-Raft-Leader", currLeader)
		w.Header().Set("Location", fmt.Sprintf("http://%s%s", currLeader, r.RequestURI))
		w.WriteHeader(http.StatusTemporaryRedirect) // 307 Temporary Redirect
		fmt.Fprintf(w, "Not leader. Redirect to active leader: %s\n", currLeader)
		return
	}

	// Узел — Лидер: парсим и применяем мутацию
	var payload WriteCommandPayload
	if err := json.NewDecoder(r.Body).Decode(&payload); err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	h.mu.Lock()
	h.fsmData[payload.Key] = payload.Value
	h.mu.Unlock()

	w.WriteHeader(http.StatusOK)
	fmt.Fprintf(w, "Leader [%s] successfully committed: %s = %s\n", h.nodeID, payload.Key, payload.Value)
}

func main() {
	leaderNode := NewNodeRoleHandler("node-lead-0", true, "10.0.0.1:8080")
	followerNode := NewNodeRoleHandler("node-fol-1", false, "10.0.0.1:8080")

	// 1. Клиент отправляет запись на Фоловера
	reqFol := httptest.NewRequest(http.MethodPost, "/v1/keys", nil)
	recFol := httptest.NewRecorder()
	followerNode.HandleWrite(recFol, reqFol)

	fmt.Printf("[Follower Response] HTTP Status: %d\n", recFol.Code)
	fmt.Printf("[Follower Response] Header X-Raft-Leader: %s\n", recFol.Header().Get("X-Raft-Leader"))
	fmt.Printf("[Follower Response] Body: %s", recFol.Body.String())

	// 2. Клиент отправляет запись на Лидера
	bodyStr := `{"key": "cluster_mode", "value": "strict_linearizable"}`
	reqLead := httptest.NewRequest(http.MethodPost, "/v1/keys", bytesReader(bodyStr))
	recLead := httptest.NewRecorder()
	leaderNode.HandleWrite(recLead, reqLead)

	fmt.Printf("\n[Leader Response] HTTP Status: %d\n", recLead.Code)
	fmt.Printf("[Leader Response] Body: %s", recLead.Body.String())
}

func bytesReader(s string) *httptest.ResponseRecorder {
	// Вспомогательный хелпер
	return nil
}
```

## Под капотом

В `hashicorp/raft` метод `raft.Leader()` возвращает текущий адрес лидера `raft.ServerAddress` и строковый `raft.ServerID`. Если узел является фоловером, этот адрес берется из последних заголовков `AppendEntries`. Если значение адреса пустое (`""`), значит, кластер переживает потерю кворума или тайм-аут выборов.

## Подводные камни

Попытка чтения устаревших данных с фоловеров (Stale Reads): фоловер может быстро ответить на GET-запрос из своей локальной памяти FSM. Однако если фоловер изолирован в меньшинстве (Minority Partition), данные в его FSM могут быть устаревшими на часы. Если клиенту требуется строгая линеаризуемость, чтение также обязано идти через лидера с подтверждением `ReadIndex`.

## На собеседовании

В: Почему в распределенных базах на базе Raft (CockroachDB, TiKV) шардируют Raft-группы (Multi-Raft)?
О: Одиночная группа Raft имеет предел масштабирования: один лидер обязан обрабатывать все записи, а один лог ограничен пропускной способностью одного диска. В Multi-Raft данные разбиваются на диапазоны (Ranges / Shards), и каждый диапазон управляется собственной независимой группой Raft со своим лидером, позволяя линейно масштабировать запись по сотням серверов.
