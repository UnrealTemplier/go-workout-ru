# Конфигурация Raft: LocalID, SnapshotInterval и ElectionTimeout

## Условие

Настройте `raft.Config` (LocalID, SnapshotInterval, SnapshotThreshold, ElectionTimeout, HeartbeatTimeout). Объясните соотношение между HeartbeatTimeout и ElectionTimeout.

### Исходная формулировка

**Bootstrap кластера из 3 узлов.**: Настройте `raft.Config` (LocalID, SnapshotInterval, HeartbeatTimeout), `raft.NetworkTransport` (TCP). Запустите 3 узла на разных портах. Покажите, что кластер автоматически выбирает лидера (LeaderObserved channel). Объясните, почему нужен `BootstrapCluster` только один раз, а потом `AddVoter`.

## Теория

Корректная настройка временных интервалов (Timing Parameters) в Raft определяет стабильность и доступность распределенного кластера.
Фундаментальное неравенство времени Raft (Timing Invariant):
$$\text{BroadcastTime} \ll \text{ElectionTimeout} \ll \text{MTBF}$$
Где:
- \(\text{BroadcastTime}\): время одного раунда сетевого взаимодействия (Round-Trip Time + время записи на диск). Обычно \(0.5 - 5\) мс.
- \(\text{HeartbeatTimeout}\): интервал отправки пустых `AppendEntries` лидером. Обычно \(50 - 100\) мс.
- \(\text{ElectionTimeout}\): интервал ожидания фоловера перед началом выборов. Обязан быть в \(5 - 10\) раз больше `HeartbeatTimeout` (обычно \(1000 - 2000\) мс) и **рандомизирован** в диапазоне \([T, 2T]\) для предотвращения раскола голосов (Split Vote).
- \(\text{MTBF}\) (Mean Time Between Failures): среднее время между отказами серверов (месяцы).
Ключевые параметры `raft.Config`:
1. `LocalID`: уникальный строковый идентификатор узла в кластере (`"node-1"`).
2. `HeartbeatTimeout`: частота отправки пульса лидером.
3. `ElectionTimeout`: базовый таймаут ожидания выборов.
4. `SnapshotInterval`: периодичность создания контрольных точек FSM (например, каждые 120 сек).
5. `SnapshotThreshold`: количество новых логов с момента последнего снимка для триггера компактизации (например, 8192 записи).

## Решение по шагам

1. Создаем структуру ClusterRaftConfig, эмулирующую `raft.Config`.
2. Реализуем функцию валидации ValidateConfig(cfg), проверяющую соотношение интервалов.
3. Демонстрируем расчет безопасных интервалов для локальной сети (LAN) и геораспределенной сети (WAN).
4. Проверяем обнаружение опасных антипаттернов (когда ElectionTimeout <= HeartbeatTimeout).
5. Выводим параметры настроенного кластера.

## Код решения

**`raft_config_tuning.go`**

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

var (
	ErrHeartbeatTooLarge = errors.New("invalid timing: ElectionTimeout must be at least 3x HeartbeatTimeout")
	ErrLocalIDEmpty      = errors.New("LocalID cannot be empty")
)

type RaftNodeConfig struct {
	LocalID           string
	HeartbeatTimeout  time.Duration
	ElectionTimeout   time.Duration
	SnapshotInterval  time.Duration
	SnapshotThreshold uint64
	MaxAppendEntries  int
}

func ValidateRaftConfig(c *RaftNodeConfig) error {
	if c.LocalID == "" {
		return ErrLocalIDEmpty
	}
	// Золотое правило Raft: ElectionTimeout >= 3 * HeartbeatTimeout (рекомендуется 5-10x)
	if c.ElectionTimeout < 3*c.HeartbeatTimeout {
		return fmt.Errorf("%w (ElectionTimeout=%v, HeartbeatTimeout=%v)",
			ErrHeartbeatTooLarge, c.ElectionTimeout, c.HeartbeatTimeout)
	}
	return nil
}

func NewLANConfig(localID string) *RaftNodeConfig {
	return &RaftNodeConfig{
		LocalID:           localID,
		HeartbeatTimeout:  100 * time.Millisecond,
		ElectionTimeout:   1000 * time.Millisecond, // 10x ratio
		SnapshotInterval:  120 * time.Second,
		SnapshotThreshold: 10000,
		MaxAppendEntries:  500,
	}
}

func NewWANConfig(localID string) *RaftNodeConfig {
	// Для мульти-регион сетей (Cross-Region WAN) задержки выше
	return &RaftNodeConfig{
		LocalID:           localID,
		HeartbeatTimeout:  500 * time.Millisecond,
		ElectionTimeout:   3000 * time.Millisecond, // 6x ratio
		SnapshotInterval:  300 * time.Second,
		SnapshotThreshold: 25000,
		MaxAppendEntries:  250,
	}
}

func main() {
	lanCfg := NewLANConfig("raft-node-alpha-1")
	if err := ValidateRaftConfig(lanCfg); err != nil {
		fmt.Printf("LAN Config invalid: %v\n", err)
	} else {
		fmt.Printf("LAN Config valid! LocalID=%s, Heartbeat=%v, ElectionTimeout=%v\n",
			lanCfg.LocalID, lanCfg.HeartbeatTimeout, lanCfg.ElectionTimeout)
	}

	// Пример некорректной конфигурации
	badCfg := &RaftNodeConfig{
		LocalID:          "bad-node",
		HeartbeatTimeout: 200 * time.Millisecond,
		ElectionTimeout:  300 * time.Millisecond, // Слишком близко: гарантирован Flapping!
	}
	if err := ValidateRaftConfig(badCfg); err != nil {
		fmt.Printf("Validation caught dangerous config: %v\n", err)
	}
}
```

## Под капотом

Если `ElectionTimeout` слишком мал по сравнению с `HeartbeatTimeout`, то кратковременный сетевой джиттер или пауза GC заставит фоловеров решить, что лидер умер. Начнутся ложные выборы (Spurious Elections). Кластер войдет в состояние Flapping Churn: узлы будут непрерывно свергать друг друга, и доступность на запись упадет до нуля.

## Подводные камни

Одинаковый `ElectionTimeout` на всех узлах: если таймер выборов фиксирован (например, ровно 1000 мс на всех узлах), то при падении лидера все фоловеры одновременно перейдут в Candidate и проголосуют сами за себя. Ни один кандидат не наберет кворум. Наступит бесконечный Split Vote Deadlock. Таймер ОБЯЗАН быть рандомизирован: `ElectionTimeout + rand.Intn(ElectionTimeout)`.

## На собеседовании

В: Почему в геораспределенных (Multi-Region / Cross-DC) Raft кластерах ElectionTimeout увеличивают до 3-5 секунд?
О: RTT между континентальными дата-центрами (например, Франкфурт — Сингапур) может составлять 150-250 мс со случайными сетевыми спайками до 800 мс. При стандартном локальном таймауте 1 секунда кластер будет непрерывно считать лидера упавшим и перезапускать выборы.
