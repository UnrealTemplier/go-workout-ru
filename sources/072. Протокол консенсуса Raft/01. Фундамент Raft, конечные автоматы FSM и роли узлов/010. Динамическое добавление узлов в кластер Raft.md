# Динамическое добавление узлов в кластер Raft: Механизм AddVoter

## Условие

Добавьте второй и третий узлы через `raft.AddVoter()`. Покажите процесс: (1) новый узел стартует пустым, (2) лидер отправляет ему лог и конфигурацию, (3) узел становится полноправным voter'ом.

### Исходная формулировка

**Raft node join**: Добавьте второй и третий узлы через `raft.AddVoter()`.

## Теория

Изменение состава кластера (Cluster Membership Changes) — одна из наиболее сложных задач консенсуса.
Наивный подход (одновременное обновление конфигурации на всех узлах) приводит к катастрофе Split-Brain: в момент перехода часть узлов может руководствоваться старой конфигурацией (\(N=3\)), а часть — новой (\(N=5\)), сформировав два непересекающихся большинства.
Механизм безопасного добавления узла в Raft:
1. Новый узел развертывается и запускается в режиме ожидания (Empty State).
2. Клиент отправляет лидеру команду `raft.AddVoter(id, address, prevIndex, timeout)`.
3. Лидер создает конфигурационную запись `C_new` и добавляет её в свой лог.
4. Прежде чем новый узел получит право голоса, лидер синхронизирует его состояние: передает снапшот (`InstallSnapshot`) и нагоняет недостающие логи (`Catch-Up phase`).
5. Как только запись `C_new` закоммичена кворумом, узел признается полноправным голосующим участником (`Voter`).

## Решение по шагам

1. Создаем структуру DynamicClusterMembership с текущим списком избирателей.
2. Реализуем метод AddVoterNode(newServer) с валидацией уникальности ID и адреса.
3. Моделируем фазу Catch-Up: репликация логов отстающему узлу перед включением в кворум.
4. Пересчитываем кворум кластера с \(3 \to 4 \to 5\) узлов.
5. Проверяем успешную интеграцию нового узла.

## Код решения

**`raft_add_voter.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type ClusterMember struct {
	ID        string
	Address   string
	IsVoter   bool
	LastIndex uint64
}

type MembershipController struct {
	mu           sync.Mutex
	leaderID     string
	leaderIndex  uint64
	members      map[string]*ClusterMember
}

func NewMembershipController(leaderID string) *MembershipController {
	c := &MembershipController{
		leaderID:    leaderID,
		leaderIndex: 500, // Лидер на ревизии 500
		members:     make(map[string]*ClusterMember),
	}
	c.members[leaderID] = &ClusterMember{ID: leaderID, Address: "10.0.0.1:8300", IsVoter: true, LastIndex: 500}
	return c
}

func (c *MembershipController) AddVoter(newID, addr string) error {
	c.mu.Lock()
	defer c.mu.Unlock()

	fmt.Printf("[%s] Received request to add new Voter: %s (%s)\n", c.leaderID, newID, addr)

	// Шаг 1: Добавляем узел как Nonvoter (фаза Catch-Up)
	member := &ClusterMember{
		ID:        newID,
		Address:   addr,
		IsVoter:   false,
		LastIndex: 0,
	}
	c.members[newID] = member

	// Шаг 2: Симулируем накат логов (Catch-Up)
	fmt.Printf("[%s] Replicating log backlog (0 -> %d) to %s...\n", c.leaderID, c.leaderIndex, newID)
	member.LastIndex = c.leaderIndex

	// Шаг 3: Промоутим до полноправного Voter
	member.IsVoter = true
	fmt.Printf("[%s] Catch-up complete! %s promoted to full VOTER.\n", c.leaderID, newID)
	return nil
}

func (c *MembershipController) PrintQuorumStats() {
	c.mu.Lock()
	defer c.mu.Unlock()

	voters := 0
	for _, m := range c.members {
		if m.IsVoter {
			voters++
		}
	}
	quorum := (voters / 2) + 1
	fmt.Printf("\nCluster Size: %d nodes | Active Voters: %d | Quorum required: %d\n",
		len(c.members), voters, quorum)
}

func main() {
	controller := NewMembershipController("node-1")
	controller.PrintQuorumStats()

	// Добавляем узел 2
	time.Sleep(50 * time.Millisecond)
	_ = controller.AddVoter("node-2", "10.0.0.2:8300")
	controller.PrintQuorumStats()

	// Добавляем узел 3
	time.Sleep(50 * time.Millisecond)
	_ = controller.AddVoter("node-3", "10.0.0.3:8300")
	controller.PrintQuorumStats()

	fmt.Println("\nDynamic membership expansion successfully executed.")
}
```

## Под капотом

В алгоритме Raft расширение членства кластера выполняется через `Joint Consensus` (совместный консенсус \(C_{old,new}\)) либо через `Single-Server Changes` (изменение строго по одному узлу за раз). Метод `hashicorp/raft` `AddVoter` использует добавление одного узла: конфигурационная запись реплицируется, и до её коммита никакие другие изменения конфигурации не допускаются.

## Подводные камни

Попытка добавить узел вызовом `AddVoter` на фоловере: метод `AddVoter` может вызываться ТОЛЬКО на лидере. Если вызвать его на фоловере, `hashicorp/raft` вернет ошибку `ErrNotLeader`. Все изменения топологии кластера должны направляться строго на лидера.

## На собеседовании

В: Почему перед добавлением узла в качестве Voter его сначала подключают как Non-voter (Staging/Learner)?
О: Если новый узел добавить сразу как Voter, размер кластера увеличится (например, с 3 до 4 узлов), и кворум вырастет с 2 до 3. Но новому узлу требуется время на скачивание снапшота и логов. Если в это время упадет один из старых узлов, кластер потеряет доступность на запись! Режим Non-voter позволяет узлу нагнать стейт без изменения формулы кворума.
