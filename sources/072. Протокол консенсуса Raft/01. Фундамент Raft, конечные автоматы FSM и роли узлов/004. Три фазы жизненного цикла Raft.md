### Исходная формулировка

**Raft flow**: Поймите 3 фазы:
* Leader election (выборы leader'а)
* Log replication (репликация команд)
* Safety (гарантии консистентности)

## Теория

Классическая статья Онгаро формулирует строгие математические инварианты безопасности Raft:
1. **Election Safety:** в любой каденции (Term) может быть избран не более чем один лидер.
2. **Leader Append-Only:** лидер никогда не перезаписывает и не обрезает (truncate) свои собственные записи в логе; он только добавляет новые записи (`append`).
3. **Log Matching Property:** если два лога на разных узлах содержат запись с одинаковым индексом и каденцией, то:
   - Эти записи содержат одну и ту же команду.
   - Логи идентичны во всех предшествующих записях от индекса 1 до данного индекса.
4. **Leader Completeness:** если запись закоммичена в каденции \(T\), то эта запись гарантированно присутствует в логах лидеров всех более поздних каденций (\(T' > T\)).
5. **State Machine Safety:** если сервер применил запись с индексом \(I\) к своей машине состояний, ни один другой сервер никогда не применит другую запись для того же индекса.

## Решение по шагам

1. Создаем структуру LogEntry с полями Index, Term, Command.
2. Реализуем структуру InvariantVerifier, проверяющую согласованность двух логов.
3. Добавляем проверку правила Log Matching.
4. Моделируем проверку Leader Completeness при смене лидера.
5. Демонстрируем выявление нарушения инварианта при попытке перезаписать закоммиченную запись.

## Код решения

**`raft_safety_invariants.go`**

```go
package main

import (
	"errors"
	"fmt"
)

var (
	ErrLogMismatch         = errors.New("log matching invariant violated: mismatch in log history")
	ErrCommittedOverwritten = errors.New("safety violation: attempted to overwrite committed entry")
)

type LogEntry struct {
	Index uint64
	Term  uint64
	Data  string
}

type ReplicatedLog struct {
	entries     []LogEntry
	commitIndex uint64
}

func NewReplicatedLog() *ReplicatedLog {
	// Индексация в Raft начинается с 1. Нулевая запись — фиктивная граница
	return &ReplicatedLog{
		entries:     []LogEntry{{Index: 0, Term: 0, Data: "ROOT"}},
		commitIndex: 0,
	}
}

func (l *ReplicatedLog) Append(term uint64, data string) uint64 {
	idx := uint64(len(l.entries))
	l.entries = append(l.entries, LogEntry{Index: idx, Term: term, Data: data})
	return idx
}

func (l *ReplicatedLog) Commit(idx uint64) {
	if idx > l.commitIndex && idx < uint64(len(l.entries)) {
		l.commitIndex = idx
	}
}

// Проверка Log Matching Property: соответствие лога фоловера логу лидера
func VerifyLogMatching(leaderLog, followerLog *ReplicatedLog, checkIdx uint64) error {
	if checkIdx >= uint64(len(leaderLog.entries)) || checkIdx >= uint64(len(followerLog.entries)) {
		return nil
	}

	leadEntry := leaderLog.entries[checkIdx]
	folEntry := followerLog.entries[checkIdx]

	if leadEntry.Term == folEntry.Term {
		// Все предшествующие записи также обязаны совпадать
		for i := uint64(1); i <= checkIdx; i++ {
			if leaderLog.entries[i].Term != followerLog.entries[i].Term ||
				leaderLog.entries[i].Data != followerLog.entries[i].Data {
				return ErrLogMismatch
			}
		}
	}
	return nil
}

func main() {
	leader := NewReplicatedLog()
	follower := NewReplicatedLog()

	// 1. Лидер и фоловер согласованно пишут Term 1
	leader.Append(1, "SET user:1 = Alice")
	follower.Append(1, "SET user:1 = Alice")

	leader.Append(1, "SET user:2 = Bob")
	follower.Append(1, "SET user:2 = Bob")

	leader.Commit(2) // Запись закоммичена большинством

	err := VerifyLogMatching(leader, follower, 2)
	fmt.Printf("Log Matching Verification at Index 2: Valid? %v (err: %v)\n", err == nil, err)

	// 2. Симулируем некорректную попытку фоловера иметь другие данные на закоммиченном индексе
	badFollower := NewReplicatedLog()
	badFollower.Append(1, "SET user:1 = Alice")
	badFollower.Append(1, "SET user:2 = Mallory") // Несоответствие!

	errBad := VerifyLogMatching(leader, badFollower, 2)
	fmt.Printf("Log Matching on diverged log: %v\n", errBad)
}
```

## Под капотом

Как Raft гарантирует Leader Completeness?
В фазе выборов `RequestVote` фоловер голосует за кандидата ТОЛЬКО ЕСЛИ лог кандидата не менее актуален (At least as up-to-date), чем лог фоловера.
Сравнение логов:
1. Если последние записи кандидатов имеют разные Term — актуальнее тот, у кого Term выше.
2. Если Term одинаковый — актуальнее тот, у кого длиннее лог (`LastLogIndex`).
Так как закоммиченная запись присутствует на большинстве узлов, а кандидат обязан получить голоса большинства, в кворуме гарантированно найдется хотя бы один узел с этой записью, который не отдаст голос кандидату с неполным логом!

## Подводные камни

Коммит записей предыдущих каденций по счетчику узлов (Corner Case статьи Raft): лидер Raft не имеет права коммитить записи предыдущих каденций напрямую по подсчету реплик. Он обязан закоммитить хотя бы одну запись СВОЕЙ текущей каденции. Только после этого все предшествующие записи считаются закоммиченными косвенно (Indirect Commit).

## На собеседовании

В: Почему в Raft кандидат с более длинным логом может проиграть кандидату с более коротким логом?
О: Потому что Term имеет наивысший приоритет. Кандидат с записью в Term 3 и длиной лога 5 актуальнее кандидата с длиной лога 10, но завершившегося на Term 2. Записи в более позднем Term отражают более свежую историю кластера.
