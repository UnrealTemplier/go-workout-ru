# Механика AppendEntries RPC: Инвариант согласованности логов

## Условие

Raft log replication: Изучите, как leader реплицирует log entries через AppendEntries RPC: PrevLogIndex, PrevLogTerm, Entries, LeaderCommit. Реализуйте алгоритм разрешения конфликтов логов фоловером.

### Исходная формулировка

**Raft log replication**: Изучите, как leader реплицирует log entries через AppendEntries RPC.

## Теория

Алгоритм согласования логов (Log Reconciliation Algorithm) в Raft — сердце репликации:
Параметры `AppendEntries RPC`:
- `Term`: текущий Term лидера.
- `LeaderID`: идентификатор лидера.
- `PrevLogIndex`: индекс записи, непосредственно предшествующей новым записям.
- `PrevLogTerm`: Term записи `PrevLogIndex`.
- `Entries[]`: новые записи для добавления (пусто для heartbeats).
- `LeaderCommit`: `commitIndex` лидера.
Алгоритм проверки на стороне Фоловера:
1. Если `Term < currentTerm` \(\to\) вернуть `false`.
2. Если в локальном логе фоловера нет записи по индексу `PrevLogIndex` с каденцией `PrevLogTerm` \(\to\) вернуть `false` (Log Inconsistency). Лидер уменьшит `nextIndex` для этого фоловера на 1 и повторит попытку.
3. Если существующая запись конфликтует с новой (одинаковый индекс, но разный Term) \(\to\) удалить существующую запись и все последующие за ней (`truncate`).
4. Добавить новые записи из `Entries[]`.
5. Если `LeaderCommit > commitIndex`, обновить:
$$\text{commitIndex} = \min(\text{LeaderCommit}, \; \text{индекс последней новой записи})$$

## Решение по шагам

1. Создаем структуру AppendEntriesArgs и структуру AppendEntriesReply.
2. Создаем метод FollowerNode.ProcessAppendEntries(args).
3. Моделируем проверку соответствия PrevLogIndex и PrevLogTerm.
4. Реализуем автоматическое усечение конфликтующих записей (Truncate).
5. Проверяем успешное приведение рассинхронизированного лога фоловера к логу лидера.

## Код решения

**`raft_log_reconciliation.go`**

```go
package main

import (
	"fmt"
)

type LogItem struct {
	Index uint64
	Term  uint64
	Cmd   string
}

type FollowerState struct {
	currentTerm uint64
	commitIndex uint64
	log         []LogItem
}

type AppendEntriesRequest struct {
	Term         uint64
	LeaderID     string
	PrevLogIndex uint64
	PrevLogTerm  uint64
	Entries      []LogItem
	LeaderCommit uint64
}

type AppendEntriesResponse struct {
	Term    uint64
	Success bool
}

func (f *FollowerState) HandleAppendEntries(req AppendEntriesRequest) AppendEntriesResponse {
	// Правило 1: Отклоняем, если Term лидера устарел
	if req.Term < f.currentTerm {
		return AppendEntriesResponse{Term: f.currentTerm, Success: false}
	}

	// Правило 2: Проверяем наличие записи PrevLogIndex с Term == PrevLogTerm
	if req.PrevLogIndex > 0 {
		if req.PrevLogIndex >= uint64(len(f.log)) {
			// Лог фоловера короче, чем PrevLogIndex
			return AppendEntriesResponse{Term: f.currentTerm, Success: false}
		}
		if f.log[req.PrevLogIndex].Term != req.PrevLogTerm {
			// Term на PrevLogIndex не совпадает!
			return AppendEntriesResponse{Term: f.currentTerm, Success: false}
		}
	}

	// Правило 3 & 4: Удаляем конфликтующие записи и дописываем новые
	insertIdx := req.PrevLogIndex + 1
	for i, entry := range req.Entries {
		idx := insertIdx + uint64(i)
		if idx < uint64(len(f.log)) {
			if f.log[idx].Term != entry.Term {
				// Конфликт! Обрезаем лог начиная с этого индекса
				fmt.Printf("[Follower] Conflict at Index %d (local Term %d vs leader Term %d). Truncating!\n",
					idx, f.log[idx].Term, entry.Term)
				f.log = f.log[:idx]
				f.log = append(f.log, entry)
			}
		} else {
			f.log = append(f.log, entry)
		}
	}

	// Правило 5: Обновляем commitIndex
	if req.LeaderCommit > f.commitIndex {
		lastNewIndex := uint64(len(f.log) - 1)
		if req.LeaderCommit < lastNewIndex {
			f.commitIndex = req.LeaderCommit
		} else {
			f.commitIndex = lastNewIndex
		}
	}

	return AppendEntriesResponse{Term: f.currentTerm, Success: true}
}

func main() {
	// Инициализируем фоловера с конфликтующей историей в Term 1
	follower := &FollowerState{
		currentTerm: 2,
		commitIndex: 1,
		log: []LogItem{
			{Index: 0, Term: 0, Cmd: "ROOT"},
			{Index: 1, Term: 1, Cmd: "SET a = 1"},
			{Index: 2, Term: 1, Cmd: "SET b = 2 (OLD UNCOMMITTED)"}, // Конфликтная запись!
		},
	}

	// Лидер Term 2 присылает свои записи начиная с PrevLogIndex=1
	req := AppendEntriesRequest{
		Term:         2,
		LeaderID:     "node-leader",
		PrevLogIndex: 1,
		PrevLogTerm:  1,
		Entries: []LogItem{
			{Index: 2, Term: 2, Cmd: "SET b = 99 (LEADER TRUTH)"},
			{Index: 3, Term: 2, Cmd: "SET c = 100"},
		},
		LeaderCommit: 2,
	}

	fmt.Println("=== FOLLOWER LOG BEFORE RECONCILIATION ===")
	for _, item := range follower.log {
		fmt.Printf("Index %d (Term %d): %s\n", item.Index, item.Term, item.Cmd)
	}

	resp := follower.HandleAppendEntries(req)
	fmt.Printf("\nAppendEntries Result: Success=%v\n\n", resp.Success)

	fmt.Println("=== FOLLOWER LOG AFTER RECONCILIATION ===")
	for _, item := range follower.log {
		fmt.Printf("Index %d (Term %d): %s\n", item.Index, item.Term, item.Cmd)
	}
	fmt.Printf("Follower CommitIndex: %d\n", follower.commitIndex)
}
```

## Под капотом

В оригинальной статье Raft при несовпадении лога лидер делает откат `nextIndex = nextIndex - 1`. Но если лог разошелся на 10 000 записей, линейный откат потребует 10 000 сетевых раундов! На практике применяется оптимизация Fast Rollback (Section 5.3): фоловер в ответе возвращает `ConflictTerm` и `FirstIndexOfConflictTerm`. Это позволяет лидеру перепрыгивать сразу целыми каденциями назад за 1-2 сетевых раунда.

## Подводные камни

Усечение закоммиченных записей: если реализация случайно обрежет лог ДО `commitIndex`, нарушится инвариант State Machine Safety. Закоммиченные записи никогда ни при каких обстоятельствах не могут быть перезаписаны или удалены.

## На собеседовании

В: Как работает оптимизация Fast Rollback при разрешении конфликтов AppendEntries?
О: При отказе фоловер передает в ответе номер конфликтного Term и первый индекс своего лога для этого Term. Лидер ищет в своем логе последнюю запись с этим Term: если находит — переносит `nextIndex` на следующий индекс; если не находит — переносит `nextIndex` сразу на первый индекс конфликтного Term фоловера, минуя тысячи итераций поштучного отката.
