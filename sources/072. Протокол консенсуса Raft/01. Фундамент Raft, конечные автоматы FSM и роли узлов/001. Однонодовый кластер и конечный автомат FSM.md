# Однонодовый кластер и конечный автомат FSM (Finite State Machine)

## Условие

Создайте FSM (Finite State Machine) на Go: `map[string]string` + команды `SET key value`, `DEL key`, `GET key`. Реализуйте `Apply(*raft.Log) interface{}`. Убедитесь, что FSM детерминированна.

### Исходная формулировка

**Однонодовый кластер.**: Создайте FSM (Finite State Machine) на Go: `map[string]string` с `Apply([]byte)` и `Snapshot()`. Интегрируйте `hashicorp/raft`, запустите один узел с `BootstrapCluster`. Выполните `raft.Apply([]byte("set foo=bar"), timeout)` и покажите, что FSM обновился. Объясните, что `Apply` — это единственный способ изменить состояние в Raft.

## Теория

Протокол консенсуса Raft (разработанный Диего Онгаро и Джоном Аустерхаутом в Стэнфорде) предназначен для построения распределенных реплицированных конечных автоматов (Replicated State Machines, RSM).
В основе RSM лежит фундаментальное математическое свойство:
Если детерминированный конечный автомат (Deterministic FSM) начинает работу в идентичном начальном состоянии \(S_0\) и последовательно применяет идентичную последовательность команд \(C_1, C_2, \dots, C_n\), то в результате он гарантированно перейдет в идентичное финальное состояние \(S_n\).
Требования к Raft FSM:
1. **Строгий детерминизм:** выполнение команды `Apply` не должно зависеть от локального системного времени (`time.Now()`), генераторов случайных чисел (`rand.Int()`) или сетевых вызовов. Одинаковый байтовый лог на любом узле кластера обязан давать байт-в-байт идентичный результат.
2. **Потокобезопасность:** метод `Apply(*raft.Log)` вызывается движком Raft последовательно в одной горутине при коммите записи, однако методы чтения (`Get`) могут вызываться конкурентно из множества клиентских HTTP/gRPC обработчиков. Необходима синхронизация через `sync.RWMutex`.
3. **Формат команд:** команды сериализуются в компактный бинарный формат (JSON, Protobuf, MsgPack) и содержат тип действия (Op: SET, DEL) и аргументы.

## Решение по шагам

1. Описываем структуру Command с операцией, ключом и значением.
2. Создаем структуру KeyValueFSM с хранилищем `map[string]string` и `sync.RWMutex`.
3. Реализуем метод Apply(logPayload []byte), десериализующий команду и мутирующий стейт.
4. Реализуем конкурентно-безопасный метод Get(key).
5. Проверяем детерминированное воспроизведение серии команд SET и DEL.

## Код решения

**`kv_fsm.go`**

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"sync"
)

var (
	ErrKeyNotFound = errors.New("key not found")
	ErrUnknownOp   = errors.New("unknown FSM operation")
)

type CommandOp string

const (
	OpSet CommandOp = "SET"
	OpDel CommandOp = "DEL"
)

type Command struct {
	Op    CommandOp `json:"op"`
	Key   string    `json:"key"`
	Value string    `json:"value,omitempty"`
}

type KeyValueFSM struct {
	mu    sync.RWMutex
	state map[string]string
}

func NewKeyValueFSM() *KeyValueFSM {
	return &KeyValueFSM{
		state: make(map[string]string),
	}
}

// Apply вызывается движком Raft строго последовательно при коммите записи в кворум
func (fsm *KeyValueFSM) Apply(logData []byte) interface{} {
	var cmd Command
	if err := json.Unmarshal(logData, &cmd); err != nil {
		return fmt.Errorf("failed to unmarshal log: %w", err)
	}

	fsm.mu.Lock()
	defer fsm.mu.Unlock()

	switch cmd.Op {
	case OpSet:
		fsm.state[cmd.Key] = cmd.Value
		return cmd.Value
	case OpDel:
		delete(fsm.state, cmd.Key)
		return nil
	default:
		return ErrUnknownOp
	}
}

func (fsm *KeyValueFSM) Get(key string) (string, error) {
	fsm.mu.RLock()
	defer fsm.mu.RUnlock()

	val, exists := fsm.state[key]
	if !exists {
		return "", ErrKeyNotFound
	}
	return val, nil
}

func main() {
	fsm := NewKeyValueFSM()

	// Симулируем последовательность закоммиченных Raft-логов
	logs := []Command{
		{Op: OpSet, Key: "cluster_name", Value: "raft-prod-dc1"},
		{Op: OpSet, Key: "max_connections", Value: "5000"},
		{Op: OpSet, Key: "temp_flag", Value: "true"},
		{Op: OpDel, Key: "temp_flag"},
	}

	fmt.Println("=== APPLYING RAFT LOGS TO FSM ===")
	for i, cmd := range logs {
		payload, _ := json.Marshal(cmd)
		res := fsm.Apply(payload)
		fmt.Printf("Log #%02d applied: %s %s -> Result: %v\n", i+1, cmd.Op, cmd.Key, res)
	}

	val1, _ := fsm.Get("cluster_name")
	val2, _ := fsm.Get("max_connections")
	_, errDel := fsm.Get("temp_flag")

	fmt.Printf("\nVerification FSM State:\n- cluster_name = %s\n- max_connections = %s\n- temp_flag found? %v (err: %v)\n",
		val1, val2, errDel == nil, errDel)
}
```

## Под капотом

В библиотеке `hashicorp/raft` интерфейс `FSM` имеет сигнатуру:
```go
type FSM interface {
    Apply(*raft.Log) interface{}
    Snapshot() (FSMSnapshot, error)
    Restore(io.ReadCloser) error
}
```
Значение `interface{}`, возвращаемое методом `Apply`, передается обратно вызывающей горутине через `ApplyFuture.Response()`. Это позволяет хэндлеру HTTP/gRPC узнать результат выполнения транзакции (например, сгенерированный ID или ошибку валидации).

## Подводные камни

Вызов недетерминированного кода внутри `Apply`: если записать `fsm.state["updated_at"] = time.Now().String()`, то на лидере и фоловерах в стейт попадут разные временные метки! Локальные часы на узлах не синхронизированы идеально. Все временные метки или случайные токены ОБЯЗАНЫ формироваться лидером ДО записи в Raft-лог и передаваться как часть сериализованной команды `Command.Timestamp`.

## На собеседовании

В: Что такое недетерминизм в Replicated State Machine и к каким последствиям он приводит в Raft?
О: Если функция `Apply` зависит от внешних факторов (системное время, порядок итерации по map, генераторы случайных чисел, внешние API), то после применения одного и того же лога состояние реплик разойдется (State Divergence / Byzantine Fault). Консенсус будет считать, что логи согласованы, но данные на узлах станут неконсистентными.
