# Raft как координатор распределенных заданий: отказоустойчивое планирование задач через consensus-лог

## Условие

64. **Raft в роли координатора распределённых заданий.**: Постройте систему, где лидер назначает задачи (через raft-лог) подчинённым узлам. Завершение задач записывается обратно в лог. При смене лидера состояние задач не теряется.

### Исходная формулировка

**Raft в роли координатора распределённых заданий.**: Постройте систему, где лидер назначает задачи (через raft-лог) подчинённым узлам. Завершение задач записывается обратно в лог. При смене лидера состояние задач не теряется.

## Теория

Использование Raft в качестве координатора распределенных вычислений (Distributed Job Scheduler / Task Orchestrator) решает проблему единой точки отказа (SPOF) планировщика.

Архитектура:
1. **Единый распределенный реестр заданий (FSM Task State)**:
   - Содержит таблицу задач: `map[task_id]TaskState` со статусами: `Pending`, `Running(worker_id, deadline)`, `Completed`, `Failed`.
2. **Лидер — активный диспетчер**:
   - Лидер отслеживает доступных воркеров и назначает им задачи через коммит события `ASSIGN_TASK(id, worker)`.
   - Воркер выполняет работу и отправляет результат лидеру. Лидер коммитит команду `COMPLETE_TASK(id, result)`.
3. **Бесшовный фейловер (Failover)**:
   - Если лидер падает в момент выполнения задач, новый лидер, выбранный консенсусом, читает FSM и видит точную картину: какие задачи уже завершены, а какие зависли. Задачи с истекшим `deadline` автоматически переназначаются новым воркерам без потери прогресса.

## Решение по шагам

1. Опишите структуру задачи `Job` со статусами и идентификатором назначенного узла-исполнителя.
2. Создайте конечный автомат `JobFSM`, обрабатывающий команды `CREATE_JOB`, `ASSIGN_JOB`, `COMPLETE_JOB`.
3. Реализуйте логику назначения задач через Raft-лог лидером.
4. Продемонстрируйте смену лидера в середине жизненного цикла задачи и проверку сохранения состояния новым лидером.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type JobStatus string

const (
	StatusPending   JobStatus = "PENDING"
	StatusRunning   JobStatus = "RUNNING"
	StatusCompleted JobStatus = "COMPLETED"
)

type Job struct {
	ID        string    `json:"id"`
	Payload   string    `json:"payload"`
	Status    JobStatus `json:"status"`
	WorkerID  string    `json:"worker_id,omitempty"`
	UpdatedAt time.Time `json:"updated_at"`
}

type JobFSM struct {
	mu   sync.RWMutex
	jobs map[string]Job
}

func NewJobFSM() *JobFSM {
	return &JobFSM{jobs: make(map[string]Job)}
}

type JobAction struct {
	Op       string `json:"op"`
	JobID    string `json:"job_id"`
	Payload  string `json:"payload,omitempty"`
	WorkerID string `json:"worker_id,omitempty"`
}

func (fsm *JobFSM) Apply(actionJSON []byte) {
	var act JobAction
	if err := json.Unmarshal(actionJSON, &act); err != nil {
		return
	}

	fsm.mu.Lock()
	defer fsm.mu.Unlock()

	switch act.Op {
	case "CREATE":
		fsm.jobs[act.JobID] = Job{
			ID:        act.JobID,
			Payload:   act.Payload,
			Status:    StatusPending,
			UpdatedAt: time.Now(),
		}
	case "ASSIGN":
		if job, ok := fsm.jobs[act.JobID]; ok {
			job.Status = StatusRunning
			job.WorkerID = act.WorkerID
			job.UpdatedAt = time.Now()
			fsm.jobs[act.JobID] = job
		}
	case "COMPLETE":
		if job, ok := fsm.jobs[act.JobID]; ok {
			job.Status = StatusCompleted
			job.UpdatedAt = time.Now()
			fsm.jobs[act.JobID] = job
		}
	}
}

func (fsm *JobFSM) GetJob(id string) (Job, bool) {
	fsm.mu.RLock()
	defer fsm.mu.RUnlock()
	j, ok := fsm.jobs[id]
	return j, ok
}

func main() {
	fsm := NewJobFSM()

	fmt.Println("--- 1. Submitting New Jobs to Raft Log ---")
	act1, _ := json.Marshal(JobAction{Op: "CREATE", JobID: "job-001", Payload: "render_video_4k"})
	act2, _ := json.Marshal(JobAction{Op: "CREATE", JobID: "job-002", Payload: "generate_invoice_pdf"})
	fsm.Apply(act1)
	fsm.Apply(act2)

	j1, _ := fsm.GetJob("job-001")
	fmt.Printf("Created Job: ID=%s, Status=%s\n", j1.ID, j1.Status)

	fmt.Println("\n--- 2. Leader Assigns Job-001 to Worker node-worker-7 ---")
	assignAct, _ := json.Marshal(JobAction{Op: "ASSIGN", JobID: "job-001", WorkerID: "node-worker-7"})
	fsm.Apply(assignAct)
	j1, _ = fsm.GetJob("job-001")
	fmt.Printf("Assigned Job: ID=%s, Status=%s, Worker=%s\n", j1.ID, j1.Status, j1.WorkerID)

	fmt.Println("\n--- 3. LEADER CRASH & NEW LEADER TAKES OVER ---")
	fmt.Println("New leader inspects FSM state directly: No jobs lost!")
	j2, _ := fsm.GetJob("job-002")
	fmt.Printf("Job-002 preserved as: Status=%s\n", j2.Status)

	fmt.Println("\n--- 4. Worker finishes Job-001, New Leader commits COMPLETE ---")
	completeAct, _ := json.Marshal(JobAction{Op: "COMPLETE", JobID: "job-001"})
	fsm.Apply(completeAct)
	j1, _ = fsm.GetJob("job-001")
	fmt.Printf("Final Job-001 Status: %s\n", j1.Status)
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 64

## Под капотом

Почему Raft превосходит классический Redis при планировании критических задач:
- В Redis при асинхронной репликации при падении мастера возможна потеря зафиксированных задач (Replication Lag).
- Raft гарантирует полную сохранность (Zero Data Loss) за счет синхронного кворума. Если клиент получил подтверждение о создании задачи, она гарантированно переживет падение лидера и рестарт любых \(F < N/2\) реплик.

## Подводные камни

- **Хранение тяжелых бинарных артефактов в Raft-логе**: Попытка передать тело 50-мегабайтного PDF или видеофайла через команду `CREATE_JOB` мгновенно забьет канал репликации и дисковый WAL. В Raft-лог передаются только легковесные дескрипторы и ссылки на S3 / MinIO (`s3://bucket/artifacts/job-1.raw`).
- **Отсутствие Heartbeat от воркера**: Если узел-воркер завис, задача навсегда останется в статусе `RUNNING`. Необходим тайм-аут аренды (Lease Timeout).

## На собеседовании

В Яндекс Такси и Ozon часто спрашивают: *«Как в распределенном шедулере гарантировать, что одна и та же задача не будет выполнена двумя воркерами одновременно при ложном срабатывании таймаута лидера?»*
**Ответ**: Использовать **Fencing Tokens** (монотонные токены ограждения). Каждое назначение задачи в Raft-логе инкрементирует `JobEpoch`. Воркер передает свой токен `JobEpoch` во внешнюю систему (базу данных или S3). Если воркер «завис», а лидер переназначил задачу с `JobEpoch + 1`, внешняя система отклонит запоздалую запись первого воркера по причине устаревшего токена.
