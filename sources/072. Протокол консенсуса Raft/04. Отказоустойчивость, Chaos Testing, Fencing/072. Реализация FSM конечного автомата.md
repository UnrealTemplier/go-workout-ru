# Реализация FSM конечного автомата: парсинг JSON-логов и безопасная мутация map[string]string

## Условие

### Исходная формулировка

## Теория

Конечный автомат (FSM) — это единственное место в архитектуре приложения на базе Raft, где выполняется фактическое изменение бизнес-состояния.

Строгие правила реализации `raft.FSM`:
1. **Изоляция от сети**: Метод `Apply` никогда не должен выполнять сетевых вызовов к внешним базам данных или API.
2. **Тотальный детерминизм**: Одинаковый вход обязан давать одинаковый выход.
3. **Потокобезопасность**:
   - `Apply` вызывается из единственной фоновой горутины рантайма Raft.
   - Однако методы чтения (`Get(key)`) и снапшотинга (`Snapshot()`) вызываются из параллельных HTTP/gRPC горутин.
   - Поэтому внутренняя `map[string]string` обязана защищаться мьютексом `sync.RWMutex`.
4. **Возвращаемое значение**:
   - Значение, возвращаемое из `Apply`, упаковывается в `ApplyFuture.Response()`. Оно может содержать старое значение, признак успеха или ошибку валидации payload.

## Решение по шагам

1. Опишите структуру `KeyValueFSM` с защищенной мапой `map[string]string`.
2. Создайте формат сериализации команды `LogPayload` (`Op`, `Key`, `Value`).
3. Реализуйте метод `Apply`, десериализующий JSON и применяющий операцию `SET`.
4. Добавьте метод безопасного чтения `Get(key string)`.
5. Протестируйте десериализацию корректных и поврежденных логов.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
)

type MockRaftLog struct {
	Index uint64
	Term  uint64
	Data  []byte
}

type CommandPayload struct {
	Op    string `json:"op"`
	Key   string `json:"key"`
	Value string `json:"value"`
}

type KeyValueFSM struct {
	mu    sync.RWMutex
	store map[string]string
}

func NewKeyValueFSM() *KeyValueFSM {
	return &KeyValueFSM{
		store: make(map[string]string),
	}
}

// Apply executes committed log entries
func (fsm *KeyValueFSM) Apply(l *MockRaftLog) any {
	var cmd CommandPayload
	if err := json.Unmarshal(l.Data, &cmd); err != nil {
		return fmt.Errorf("fsm unmarshal payload error at index %d: %w", l.Index, err)
	}

	fsm.mu.Lock()
	defer fsm.mu.Unlock()

	switch cmd.Op {
	case "SET":
		oldVal := fsm.store[cmd.Key]
		fsm.store[cmd.Key] = cmd.Value
		fmt.Printf("[FSM Apply] Index %d: SET '%s' = '%s' (Previous: '%s')\n",
			l.Index, cmd.Key, cmd.Value, oldVal)
		return cmd.Value

	default:
		return fmt.Errorf("unknown operation: %s", cmd.Op)
	}
}

func (fsm *KeyValueFSM) Get(key string) (string, bool) {
	fsm.mu.RLock()
	defer fsm.mu.RUnlock()
	val, ok := fsm.store[key]
	return val, ok
}

func main() {
	fsm := NewKeyValueFSM()

	// Simulating incoming Raft log entries
	log1 := &MockRaftLog{
		Index: 1,
		Term:  1,
		Data:  []byte(`{"op":"SET","key":"user:42:email","value":"alice@example.com"}`),
	}
	log2 := &MockRaftLog{
		Index: 2,
		Term:  1,
		Data:  []byte(`{"op":"SET","key":"user:42:email","value":"alice.new@example.com"}`),
	}

	res1 := fsm.Apply(log1)
	res2 := fsm.Apply(log2)

	fmt.Printf("Apply 1 returned: %v\n", res1)
	fmt.Printf("Apply 2 returned: %v\n", res2)

	val, exists := fsm.Get("user:42:email")
	fmt.Printf("Final Store Content: user:42:email = '%s' (exists: %t)\n", val, exists)
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 72

## Под капотом

Типизация ответов `Apply` в Go:
Поскольку метод возвращает `any` (или `interface{}` в старых версиях Go), вызывающий код распаковывает его с помощью Type Assertion:
```go
future := raftNode.Apply(data, timeout)
if err := future.Error(); err != nil {
    return err
}
if respErr, ok := future.Response().(error); ok {
    return respErr
}
```
Это позволяет безопасно пробрасывать доменные ошибки бизнес-логики из FSM прямо в HTTP-ответ клиенту.

## Подводные камни

- **Паника внутри `Apply`**: Если код внутри `Apply` запаникует (например, разыменование nil-указателя), это приведет к краху всего процесса узла. Метод `Apply` обязан перехватывать паники через `recover()` или быть на 100% покрыт тестами.
- **Использование глобальных переменных**: Любые зависимости от внешних переменных разрушают детерминизм воспроизведения лога.

## На собеседовании

В Т-Банке и Lamoda часто спрашивают: *«Как в методе `Apply` обеспечить идемпотентность применения команд при возможных повторных отправках клиентом?»*
**Ответ**: Включать в тело команды уникальный идентификатор клиента и монотонный порядковый номер запроса (`ClientID`, `SequenceNum`). FSM хранит таблицу последних обработанных номеров запросов для каждого клиента (`map[ClientID]SequenceNum`). Если в `Apply` приходит номер \(\le\) сохраненного, FSM не производит мутацию, а возвращает сохраненный ранее результат из кеша дедупликации.
