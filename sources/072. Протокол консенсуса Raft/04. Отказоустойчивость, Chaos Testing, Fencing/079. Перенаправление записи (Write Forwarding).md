# Перенаправление записи (Write Forwarding): HTTP 307 Temporary Redirect и прозрачное gRPC-проксирование

## Условие

79. **Write Forwarding (Перенаправление записи)**: По правилам Raft, писать данные может только Лидер! Сделай HTTP-эндпоинт `POST /key` на каждом узле. Внутри проверяй: `if raftNode.State() != raft.Leader`. Если не лидер — возвращай HTTP 307 Temporary Redirect (или проксируй запрос под капотом) на IP Лидера.

### Исходная формулировка

**Write Forwarding (Перенаправление записи)**: По правилам Raft, писать данные может только Лидер! Сделай HTTP-эндпоинт `POST /key` на каждом узле. Внутри проверяй: `if raftNode.State() != raft.Leader`. Если не лидер — возвращай HTTP 307 Temporary Redirect (или проксируй запрос под капотом) на IP адрес текущего лидера (узнай его через `raftNode.Leader()`).

## Теория

Поскольку в Raft мутировать данные имеет право исключительно Лидер, клиент, отправляющий запись на произвольный узел кластера (например, через Round-Robin DNS балансировщик), должен получить корректную маршрутизацию.

Две основные стратегии перенаправления записи:
1. **HTTP 307 Temporary Redirect (Клиентский редирект)**:
   - Фолловер возвращает статус `307 Temporary Redirect` с заголовком `Location: http://<leader_addr>/key`.
   - Плюсы: нулевая нагрузка на фолловер, клиент сам перепосылает запрос лидеру и кеширует адрес лидера для будущих запросов.
   - Минусы: требует «умного» HTTP-клиента, поддерживающего автоматический переход по 307/308 с сохранением метода POST.
2. **Transparent Reverse Proxy (Прозрачное проксирование)**:
   - Фолловер внутри обработчика сам делает сетевой запрос к лидеру через `httputil.NewSingleHostReverseProxy` или gRPC connection pool и возвращает ответ клиенту.
   - Плюсы: прозрачно для любых примитивных клиентов (curl, мобильные приложения).
   - Минусы: двойной сетевой hop и трафик фолловера.

## Решение по шагам

1. Создайте структуру веб-узла `RaftHttpNode` с полями `IsLeader` и `LeaderAddr`.
2. Реализуйте эндпоинт `POST /key` с проверкой `State() == Leader`.
3. При отсутствии лидерства сформируйте заголовок `Location` со статусом HTTP 307.
4. Протестируйте обращение к лидеру (успех 200 OK) и к фолловеру (редирект 307).
5. Продемонстрируйте переход клиента по полученному адресу редиректа.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"sync"
)

type RaftHttpNode struct {
	mu         sync.RWMutex
	nodeID     string
	isLeader   bool
	leaderAddr string
	store      map[string]string
}

func (n *RaftHttpNode) HandleKey(w http.ResponseWriter, r *http.Request) {
	n.mu.RLock()
	isLeader := n.isLeader
	leaderAddr := n.leaderAddr
	n.mu.RUnlock()

	// 1. Write Forwarding check
	if !isLeader {
		redirectURL := leaderAddr + r.URL.Path
		w.Header().Set("Location", redirectURL)
		w.WriteHeader(http.StatusTemporaryRedirect) // HTTP 307 preserves POST method!
		fmt.Fprintf(w, "Not leader. Redirecting to leader at %s\n", redirectURL)
		return
	}

	// 2. Leader executes write via consensus
	var body struct {
		Key string `json:"key"`
		Val string `json:"val"`
	}
	if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	n.mu.Lock()
	n.store[body.Key] = body.Val
	n.mu.Unlock()

	w.WriteHeader(http.StatusOK)
	json.NewEncoder(w).Encode(map[string]string{
		"status":  "written",
		"node_id": n.nodeID,
		"key":     body.Key,
	})
}

func main() {
	leader := &RaftHttpNode{
		nodeID:   "node-1",
		isLeader: true,
		store:    make(map[string]string),
	}

	follower := &RaftHttpNode{
		nodeID:     "node-2",
		isLeader:   false,
		leaderAddr: "http://10.0.0.1:8080",
		store:      make(map[string]string),
	}

	fmt.Println("--- 1. Client sends write to Follower (node-2) ---")
	reqFollower := httptest.NewRequest(http.MethodPost, "/key", strings.NewReader(`{"key":"theme","val":"dark"}`))
	recFollower := httptest.NewRecorder()
	follower.HandleKey(recFollower, reqFollower)

	fmt.Printf("Follower Status: %d (Temporary Redirect)\n", recFollower.Code)
	fmt.Printf("Location Header: %s\n", recFollower.Header().Get("Location"))
	fmt.Printf("Body: %s", recFollower.Body.String())

	fmt.Println("--- 2. Client follows redirect to Leader (node-1) ---")
	reqLeader := httptest.NewRequest(http.MethodPost, "/key", strings.NewReader(`{"key":"theme","val":"dark"}`))
	recLeader := httptest.NewRecorder()
	leader.HandleKey(recLeader, reqLeader)

	fmt.Printf("Leader Status: %d (Success)\n", recLeader.Code)
	fmt.Printf("Body: %s", recLeader.Body.String())
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 79

## Под капотом

Почему используется именно HTTP 307, а не HTTP 301 или 302:
- Статус `301 Moved Permanently` кешируется браузерами и HTTP-клиентами навечно, что недопустимо при смене лидера через 5 минут.
- Статус `302 Found` исторически заставляет многие клиенты переключать метод с `POST` на `GET`, теряя тело полезной нагрузки!
- Статус `307 Temporary Redirect` строго специфицирован в RFC 7231: клиент **обязан повторить запрос с тем же самым HTTP-методом (POST) и неизменным телом**.

## Подводные камни

- **Бесконечный цикл редиректов (Redirect Loop)**: Если кластер находится в состоянии перевыборов, и фолловер думает, что лидер узел \(A\), а узел \(A\) думает, что лидер узел \(B\), клиент попадет в бесконечный цикл. Клиент обязан ограничивать `MaxRedirects = 3`.
- **Потеря тела запроса при прозрачном проксировании**: При обратном проксировании `r.Body` является `io.ReadCloser`. Если прочитать его для логирования без восстановления через `io.NopCloser`, прокси отправит пустое тело.

## На собеседовании

В Касперском и Lamoda часто спрашивают: *«Какую архитектуру перенаправления запросов на запись лучше выбрать: Client-side Redirect (307) или Server-side Reverse Proxy?»*
**Ответ**: Если клиентом является официальный SDK компании (например, `go-client` к internal сервису), однозначно выбирают **Client-side Redirect** с кешированием адреса лидера на клиенте. Клиент единожды получает адрес лидера и последующие тысячи запросов шлет напрямую в сокет лидера без промежуточных сетевых задержек. Server-side Proxy выбирают только тогда, когда клиентами являются сторонние внешние интеграции без поддержки логики Raft.
