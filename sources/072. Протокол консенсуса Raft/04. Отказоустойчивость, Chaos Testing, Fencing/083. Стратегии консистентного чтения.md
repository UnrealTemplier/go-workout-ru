# Стратегии консистентного чтения: Stale Read против ReadIndex и Lease Read

## Условие

83. **Consistent Reads (Консистентное чтение)**: По правилам Raft, Фоловерам нельзя доверять чтение (у них могут быть старые данные).
    * Вариант 1 (Stale Read): Разреши читать с фоловеров (быстро, но данные могут отставать).
    * Вариант 2 (ReadIndex/Lease): Чтобы получить 100% актуальные данные

### Исходная формулировка

**Consistent Reads (Консистентное чтение)**: По правилам Raft, Фоловерам нельзя доверять чтение (у них могут быть старые данные).
* Вариант 1 (Stale Read): Разреши читать с фоловеров (быстро, но данные могут отставать).
* Вариант 2 (ReadIndex/Lease): Чтобы получить 100% актуальные данные (Linearizability), чтение должно идти через Лидера. Лидер должен убедиться у большинства фоловеров, что он *всё еще* лидер, прежде чем отдать ответ. Реализуй вызов чтения через метод `raftNode.VerifyLeader()` перед отдачей значения из локальной мапы.

## Теория

Проектирование слоя чтения (Read Path) в распределенных системах на базе Raft — это фундаментальный выбор между строгой линейной согласованностью и экстремальной масштабируемостью:

Сравнение стратегий чтения:
1. **Stale Read (Чтение с отставанием)**:
   - Запрос обслуживается локально любым фолловером или лидером из оперативной памяти без сетевых RPC.
   - Задержка: \(< 100\text{ мкс}\) (in-memory read).
   - Throughput: масштабируется линейно с добавлением фолловеров (\(1 000 000+\text{ RPS}\)).
   - Гарантия: Eventual Consistency. Данные могут отставать на время репликации.
2. **ReadIndex (Section 8 Raft Whitepaper)**:
   - Запрос поступает лидеру (или пересылается ему). Лидер запоминает свой `commitIndex` и рассылает быстрый раунд пустых сердечных сигналов кворуму, чтобы убедиться, что его не свергли.
   - Задержка: \(1 \text{ Network RTT} \approx 1-5\text{ мс}\).
   - Гарантия: Strict Linearizable Consistency. Не требует дискового `fsync`.
3. **Lease Read (Аренда лидерства)**:
   - Лидер не шлет сетевой раунд на каждое чтение, пока активна его временная аренда (Lease Time \(< ElectionTimeout\)).
   - Задержка: \(< 100\text{ мкс}\).
   - Требует строгой синхронизации часов и границы дрейфа времени (Clock Drift Bound).

## Решение по шагам

1. Создайте структуру хранилища с поддержкой двух режимов чтения: `ReadModeStale` и `ReadModeLinearizable`.
2. Смоделируйте отставание фолловера на 5 записей от лидера.
3. Выполните чтение в режиме `Stale`: покажите мгновенный ответ со старыми данными.
4. Выполните чтение в режиме `Linearizable`: покажите перенаправление лидеру, проверку кворума и возврат свежих данных.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type ReadConsistencyMode string

const (
	ModeStale        ReadConsistencyMode = "STALE"
	ModeLinearizable ReadConsistencyMode = "LINEARIZABLE"
)

type NodeState struct {
	ID       string
	IsLeader bool
	Term     uint64
	Data     map[string]string
	mu       sync.RWMutex
}

type ConsistentReadCluster struct {
	leader    *NodeState
	followers []*NodeState
}

func (c *ConsistentReadCluster) Read(mode ReadConsistencyMode, targetNode *NodeState, key string) (string, time.Duration, error) {
	start := time.Now()

	switch mode {
	case ModeStale:
		// Stale Read: instant local in-memory lookup
		targetNode.mu.RLock()
		val, ok := targetNode.Data[key]
		targetNode.mu.RUnlock()
		if !ok {
			return "", time.Since(start), errors.New("key not found")
		}
		return val, time.Since(start), nil

	case ModeLinearizable:
		// Linearizable Read: Must verify leader quorum contact
		if !targetNode.IsLeader {
			// Forward to leader
			targetNode = c.leader
		}

		// Simulate ReadIndex heartbeat round-trip to quorum (e.g. 5ms RTT)
		time.Sleep(5 * time.Millisecond)

		targetNode.mu.RLock()
		val, ok := targetNode.Data[key]
		targetNode.mu.RUnlock()
		if !ok {
			return "", time.Since(start), errors.New("key not found")
		}
		return val, time.Since(start), nil

	default:
		return "", 0, errors.New("unsupported read mode")
	}
}

func main() {
	leader := &NodeState{
		ID:       "leader-1",
		IsLeader: true,
		Term:     2,
		Data:     map[string]string{"account:balance": "9500"},
	}

	laggingFollower := &NodeState{
		ID:       "follower-2",
		IsLeader: false,
		Term:     2,
		Data:     map[string]string{"account:balance": "5000"}, // Lagging behind!
	}

	cluster := &ConsistentReadCluster{
		leader:    leader,
		followers: []*NodeState{laggingFollower},
	}

	fmt.Println("=== 1. Testing Stale Read from Follower ===")
	valStale, durStale, _ := cluster.Read(ModeStale, laggingFollower, "account:balance")
	fmt.Printf("Stale Read Result: %s руб | Latency: %v (Fast, but OUTDATED!)\n", valStale, durStale)

	fmt.Println("\n=== 2. Testing Linearizable Read via Follower ===")
	valLinear, durLinear, _ := cluster.Read(ModeLinearizable, laggingFollower, "account:balance")
	fmt.Printf("Linearizable Result: %s руб | Latency: %v (Safe, 100%% ACCURATE!)\n", valLinear, durLinear)

	fmt.Println("\nSummary:")
	fmt.Printf("- Stale Read: Ultra-fast (microsecond scale), ideal for dashboards and caches.\n")
	fmt.Printf("- Linearizable Read: Strong consistency, ideal for financial balances and auth tokens.\n")
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 83

## Под капотом

Как устроен ReadIndex в etcd:
1. Клиент посылает `Range(key)` с флагом линеаризуемости.
2. etcd вызывает метод машины состояний Raft `Node.ReadIndex(ctx, rctx)`.
3. Лидер отправляет сердечный сигнал пирам.
4. Когда кворум подтверждает получение, Raft кладет в канал `Ready()` уведомление `ReadState{Index, RequestCtx}`.
5. Сервер etcd дожидается, пока локальный `lastApplied` догонит `ReadState.Index`.
6. После этого значение вычитывается из bbolt MVCC движка и возвращается клиенту без единой записи в WAL.

## Подводные камни

- **Stale Read для критических финансовых операций**: Разрешение Stale Read при списании денег со счета может привести к Double Spending (двойной трате), если баланс был списан секунду назад на лидере, но реплика еще не применила лог.
- **Overload лидера при сплошном Linearizable Read**: Если все 100 000 клиентов шлют линейные чтения лидеру, лидер захлебнется обработкой сетевых сокетов.

## На собеседовании

В Яндекс Облаке и Авито на системном интервью часто спрашивают: *«Как сбалансировать нагрузку на чтение в Raft-кластере, не нарушая при этом линеаризуемости?»*
**Ответ**: Использовать архитектуру **Follower Read (с протоколом ReadIndex)**:
Клиент читает с ближайшего фолловера. Фолловер не отдает данные сразу: он запрашивает у лидера актуальный `ReadIndex` (лидер быстро валидирует свой кворум легковесными сетевыми пакетами). Получив подтвержденный индекс \(I\), фолловер ждет, пока его собственная машина состояний применит логи до \(I\), и только потом возвращает данные клиенту. Это обеспечивает 100% линеаризуемость и распределяет нагрузку по сериализации данных по всем узлам кластера.
