# Линеаризуемое чтение (Linearizable Reads): предотвращение чтения устаревших данных со свергнутых лидеров

## Условие

71. **Raft linearizable reads**: Для strong consistency reads forwarding to leader обязателен. Иначе можете прочитать stale data.

### Исходная формулировка

**Raft linearizable reads**: Для strong consistency reads forwarding to leader обязателен. Иначе можете прочитать stale data.

## Теория

Чтение данных в Raft кажется тривиальным: «просто прочитай локальную мапу FSM на текущем узле». Однако этот наивный подход грубо нарушает свойство линейной согласованности (Linearizability)!

Почему нельзя читать с локального узла:
1. **Чтение с фолловера**: Фолловер может отставать по репликации логов на секунды или минуты. Клиент прочитает старые данные (Stale Read).
2. **Чтение со свергнутого лидера (Phantom Leader)**: Если лидер был изолирован сетевой перегородкой (в меньшинстве), большинство кластера уже выбрало нового лидера и закоммитило новые значения. Если старый лидер ответит на чтение из своей памяти до истечения таймера сердечных сигналов, произойдет чтение удаленных или перезаписанных данных.

Механизмы Linearizable Reads в Raft:
- **Write-Log Read (Наивный, медленный)**: Чтение оформляется как пустая запись в лог Raft. Гарантирует линеаризуемость, но тратит IOPS диска.
- **ReadIndex (Section 8 Whitepaper, etcd)**: Лидер фиксирует текущий `commitIndex`, отправляет раунд легковесных сердечных сигналов кворуму для подтверждения своего статуса и, дождавшись совпадения `lastApplied >= commitIndex`, отдает данные из памяти без записи на диск.
- **Lease Read**: Лидер использует временную аренду (Clock Drift Bound), избегая сетевых вызовов, но требует синхронизации часов.

## Решение по шагам

1. Создайте кластер с лидером и фолловером.
2. Смоделируйте операцию `StaleRead`, читающую локальное состояние реплики с задержкой репликации.
3. Реализуйте алгоритм `LinearizableReadViaLeader`: запрос перенаправляется лидеру, который подтверждает кворум перед ответом.
4. Продемонстрируйте сценарий изоляции лидера: покажите, что линейное чтение не позволяет вернуть старое значение.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type KVStore struct {
	mu   sync.RWMutex
	data map[string]string
}

type Node struct {
	ID       string
	IsLeader bool
	Term     uint64
	Store    *KVStore
	peers    []*Node
}

// 1. Unsafe Local Stale Read
func (n *Node) StaleRead(key string) (string, bool) {
	n.Store.mu.RLock()
	defer n.Store.mu.RUnlock()
	val, ok := n.Store.data[key]
	return val, ok
}

// 2. Safe Linearizable Read (ReadIndex pattern)
func (n *Node) LinearizableRead(key string) (string, error) {
	if !n.IsLeader {
		return "", fmt.Errorf("stale risk: node %s is not leader; read must be forwarded", n.ID)
	}

	// Leader confirms leadership with quorum via round of heartbeats
	acks := 1 // self
	for _, peer := range n.peers {
		if peer.ID != n.ID && peer.Term == n.Term {
			acks++
		}
	}

	quorum := (len(n.peers)+1)/2 + 1
	if acks < quorum {
		return "", errors.New("linearizability violation: leader lost quorum contact")
	}

	// Safe to read local state machine
	n.Store.mu.RLock()
	defer n.Store.mu.RUnlock()
	val, ok := n.Store.data[key]
	if !ok {
		return "", errors.New("key not found")
	}
	return val, nil
}

func main() {
	leaderStore := &KVStore{data: map[string]string{"balance": "5000"}}
	followerStore := &KVStore{data: map[string]string{"balance": "1000"}} // Lagging follower!

	nodeFollower := &Node{ID: "node-2", IsLeader: false, Term: 1, Store: followerStore}
	nodeLeader := &Node{ID: "node-1", IsLeader: true, Term: 1, Store: leaderStore, peers: []*Node{nodeFollower}}

	fmt.Println("--- 1. Client reads from Lagging Follower (Stale Read) ---")
	valStale, _ := nodeFollower.StaleRead("balance")
	fmt.Printf("Stale Read returned: %s руб (OUTDATED! True balance is 5000)\n", valStale)

	fmt.Println("\n--- 2. Client queries Follower for Linearizable Read ---")
	_, err := nodeFollower.LinearizableRead("balance")
	fmt.Printf("Follower rejected direct linearizable read: '%v'\n", err)

	fmt.Println("\n--- 3. Client forwards read to Leader (Linearizable Read) ---")
	valLinear, err := nodeLeader.LinearizableRead("balance")
	if err != nil {
		fmt.Println("Read failed:", err)
	} else {
		fmt.Printf("Linearizable Read returned: %s руб (Accurate!)\n", valLinear)
	}
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 71

## Под капотом

Сравнение производительности ReadIndex vs Log Read:
- Запись пустого лога на чтение требует дискового I/O (`fsync`), что ограничивает пропускную способность чтения возможностями SSD лидера (до 5 000–10 000 RPS).
- Протокол `ReadIndex` в `etcd` не пишет на диск, а использует легковесные сетевые сердечные сигналы без полезной нагрузки. Это поднимает throughput линейного чтения до 80 000+ RPS на узел.

## Подводные камни

- **Чтение по ссылке**: Если метод линейного чтения возвращает указатель на структуру данных внутри FSM (`*Account`), последующая мутация данных в методе `Apply()` может изменить возвращенный клиенту объект во время его сериализации в JSON, вызвав гонку данных. Чтение обязано возвращать глубокую копию.
- **Clock Drift при Lease Read**: Если серверное время на лидере спешит из-за сбоя NTP, лидер может ошибочно считать свою аренду активной, когда другой узел уже перехватил лидерство.

## На собеседовании

В Яндекс Маркете и Авито часто спрашивают: *«Как в распределенном KV-хранилище на Raft масштабировать чтение, не нагружая лидера, но сохраняя линейную согласованность?»*
**Ответ**: Использовать механизм **Follower ReadIndex**. Клиент отправляет запрос на чтение фолловеру. Фолловер запрашивает у лидера текущий `ReadIndex` (лидер подтверждает кворум и сообщает актуальный `commitIndex`). Фолловер ждет, пока его собственный `lastApplied` догонит этот `ReadIndex`, после чего отдает клиенту локальные данные. Нагрузка на передачу данных снимается с лидера и распределяется по всем фолловерам.
