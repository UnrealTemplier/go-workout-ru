# Настройка SnapshotThreshold: баланс между расходом диска и стоимостью создания снапшота

## Условие

68. **Raft snapshot threshold.**: Настройте snapshot threshold (например, 10k log entries) для предотвращения бесконечного роста log.

### Исходная формулировка

**Raft snapshot threshold.**: Настройте snapshot threshold (например, 10k log entries) для предотвращения бесконечного роста log.

## Теория

Параметр `SnapshotThreshold` в `hashicorp/raft` (или `SnapshotCount` в `etcd`) управляет тем, как часто журнал упреждающей записи усекается на диск.

Влияние величины `SnapshotThreshold`:
1. **Слишком маленький порог (например, 100 записей)**:
   - Частые вызовы `FSM.Snapshot()` вызывают постоянную утилизацию CPU и дискового I/O (Disk Write Amplification).
   - Падение пропускной способности кластера на запись.
2. **Слишком большой порог (например, 1 000 000 записей)**:
   - Файл журнала логов (BoltDB) разрастается до десятков гигабайт.
   - Рестарт узла занимает много минут из-за необходимости читать гигантский WAL.
   - Новые узлы, добавляемые в кластер, тратят гигабайты сетевого трафика на вычитку сырых логов вместо быстрого получения одного снапшота.

Промышленный золотой стандарт:
- Для большинства HighLoad сервисов порог выставляется в диапазоне от **10 000 до 50 000 записей**.
- Дополнительно настраивается `SnapshotInterval` (например, не реже одного раза в 2 часа даже при низкой нагрузке).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type RaftStorageManager struct {
	mu                sync.Mutex
	uncompactedLogs   int
	snapshotThreshold int
	totalSnapshots    int
	diskBytesWAL      int64
	diskBytesSnapshot int64
}

func NewRaftStorageManager(threshold int) *RaftStorageManager {
	return &RaftStorageManager{
		snapshotThreshold: threshold,
	}
}

func (m *RaftStorageManager) AppendLog(payloadSize int) bool {
	m.mu.Lock()
	defer m.mu.Unlock()

	m.uncompactedLogs++
	m.diskBytesWAL += int64(payloadSize + 32) // log header + data

	if m.uncompactedLogs >= m.snapshotThreshold {
		m.triggerCompaction()
		return true
	}
	return false
}

func (m *RaftStorageManager) triggerCompaction() {
	m.totalSnapshots++
	// Simulate compacted snapshot size (fixed state dump)
	m.diskBytesSnapshot = 5 * 1024 * 1024 // 5 MB snapshot
	// WAL truncated: entries up to snapshot are safely deleted
	m.uncompactedLogs = 0
	m.diskBytesWAL = 0
	fmt.Printf("[Raft Compaction] Snapshot #%d created! WAL truncated to 0 MB. Snapshot size: 5.0 MB\n", m.totalSnapshots)
}

func (m *RaftStorageManager) Stats() {
	m.mu.Lock()
	defer m.mu.Unlock()
	fmt.Printf("Current State: Uncompacted Logs: %d, WAL Size: %.2f MB, Snapshot Size: %.2f MB\n",
		m.uncompactedLogs, float64(m.diskBytesWAL)/(1024*1024), float64(m.diskBytesSnapshot)/(1024*1024))
}

func main() {
	const threshold = 10000
	const totalTransactions = 25000

	mgr := NewRaftStorageManager(threshold)
	fmt.Printf("Simulating %d transactions with SnapshotThreshold = %d...\n\n", totalTransactions, threshold)

	for i := 1; i <= totalTransactions; i++ {
		// Average transaction size ~ 256 bytes
		mgr.AppendLog(256)

		if i%5000 == 0 {
			fmt.Printf("Processed %d transactions:\n", i)
			mgr.Stats()
		}
	}

	fmt.Println("\nConclusion: Snapshot compaction successfully keeps disk usage bounded regardless of stream length!")
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 68

## Под капотом

Особенности BoltDB Log Store в `hashicorp/raft-boltdb`:
- Когда Raft вызывает `DeleteRange(min, max)` для удаления усеченных логов, BoltDB **не возвращает дисковое пространство операционной системе**!
- BoltDB помечает страницы как свободные (Freelist) для повторного использования будущими записями.
- Поэтому размер файла `raft.db` на диске стабилизируется на уровне максимального размера, необходимого для хранения `SnapshotThreshold` записей.

## Подводные камни

- **OOM при создании снапшота**: Если FSM хранит 50 миллионов ключей, вызов `json.Marshal(fsm.data)` создаст гигантскую аллокацию памяти в RAM, что может вызвать OOM Killer в контейнере Kubernetes. Снапшоты обязаны стримиться чанками через потоковый энкодер напрямую в `io.Writer`.
- **Конкурентные снапшоты**: Запуск нового снапшота, пока предыдущий еще не завершил сброс на диск, приведет к катастрофической деградации ввода-вывода.

## На собеседовании

В Яндекс Практикуме и VK часто спрашивают: *«Как подобрать `SnapshotThreshold` для микросервиса с 10 000 RPS на запись, чтобы минимизировать влияние на Latency P99?»*
**Ответ**: При 10 000 RPS порог в 10 000 записей приведет к созданию снапшота каждую секунду, убив диск. Оптимально выставить `SnapshotThreshold = 100_000` (снапшот каждые 10 секунд) в сочетании с асинхронным сбросом на диск с ограничением скорости записи (Rate-Limited I/O) и использованием Copy-On-Write структуры данных для FSM.
