# Сжатие логов через Snapshots: реализация методов FSM.Snapshot и FSM.Restore

## Условие

82. **Snapshots (Сжатие логов)**: Если ты запишешь миллион ключей, лог Raft станет гигантским, а рестарт ноды займет час. Реализуй методы `Snapshot()` и `Restore()` в своем FSM. В `Snapshot` просто сериализуй текущее состояние твоей `map` в JSON. Raft вызовет этот метод автоматически (согласно настройке SnapshotThreshold), создаст `.snap` файл на диске, а старые логи из BoltDB удалит.

### Исходная формулировка

**Snapshots (Сжатие логов)**: Если ты запишешь миллион ключей, лог Raft станет гигантским, а рестарт ноды займет час. Реализуй методы `Snapshot()` и `Restore()` в своем FSM. В `Snapshot` просто сериализуй текущее состояние твоей `map` в JSON. Raft вызовет этот метод автоматически (согласно настройкам `SnapshotThreshold`), обрежет старые логи и сохранит компактное состояние на диск.

## Теория

Механизм снапшотов (Log Compaction via Snapshots) решает фундаментальную проблему неограниченного роста WAL.

В интерфейсе `raft.FSM`:
```go
type FSM interface {
    Apply(*raft.Log) interface{}
    Snapshot() (FSMSnapshot, error)
    Restore(io.ReadCloser) error
}
```

Контракт `Snapshot`:
1. `Snapshot()` вызывается рантаймом Raft в потоке применения логов.
2. Он должен **мгновенно зафиксировать срез данных** (Point-in-Time snapshot) и вернуть объект `FSMSnapshot`.
3. Метод `FSMSnapshot.Persist(sink raft.SnapshotSink) error`:
   - Выполняется в фоновой горутине.
   - Стримит сериализованные данные в `sink`.
   - При успехе вызывает `sink.Close()`, после чего Raft удаляет усеченный диапазон логов из BoltDB через `DeleteRange(1, snapIndex)`.

Контракт `Restore`:
1. Принимает `io.ReadCloser`.
2. Очищает текущую мапу в памяти.
3. Вычитывает JSON поток и восстанавливает структуры данных.

## Решение по шагам

1. Создайте структуру `MapFSM` с реализацией методов `Snapshot()` и `Restore(io.ReadCloser)`.
2. Реализуйте структуру `MapSnapshot` с методом `Persist(sink io.Writer)`.
3. Наполните FSM 5 000 записями.
4. Вызовите процедуру создания снапшота и сохраните результат в байтовый буфер.
5. Очистите память FSM и вызовите `Restore()`, проверив 100% совпадение восстановленных ключей.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"io"
	"sync"
)

type MapFSM struct {
	mu   sync.RWMutex
	data map[string]string
}

func NewMapFSM() *MapFSM {
	return &MapFSM{data: make(map[string]string)}
}

func (f *MapFSM) Set(k, v string) {
	f.mu.Lock()
	defer f.mu.Unlock()
	f.data[k] = v
}

// 1. Snapshot: Fast point-in-time clone
func (f *MapFSM) Snapshot() (*MapSnapshot, error) {
	f.mu.RLock()
	defer f.mu.RUnlock()

	clone := make(map[string]string, len(f.data))
	for k, v := range f.data {
		clone[k] = v
	}

	return &MapSnapshot{state: clone}, nil
}

// 2. Restore: Wipe and populate from reader stream
func (f *MapFSM) Restore(rc io.ReadCloser) error {
	defer rc.Close()

	var restored map[string]string
	if err := json.NewDecoder(rc).Decode(&restored); err != nil {
		return err
	}

	f.mu.Lock()
	defer f.mu.Unlock()
	f.data = restored
	return nil
}

type MapSnapshot struct {
	state map[string]string
}

// Persist runs asynchronously in background goroutine
func (s *MapSnapshot) Persist(w io.Writer) error {
	return json.NewEncoder(w).Encode(s.state)
}

func main() {
	fsm := NewMapFSM()

	fmt.Println("--- 1. Ingesting 5,000 Key-Value Pairs into FSM ---")
	for i := 1; i <= 5000; i++ {
		fsm.Set(fmt.Sprintf("user:%d", i), fmt.Sprintf("ProfileData_%d", i))
	}
	fmt.Printf("FSM populated with %d items.\n", len(fsm.data))

	fmt.Println("\n--- 2. Triggering FSM.Snapshot() & Persist() ---")
	snap, err := fsm.Snapshot()
	if err != nil {
		panic(err)
	}

	var diskBuffer bytes.Buffer
	if err := snap.Persist(&diskBuffer); err != nil {
		panic(err)
	}
	fmt.Printf("Snapshot written to disk: %.2f KB (Compacted JSON dump)\n",
		float64(diskBuffer.Len())/1024)

	fmt.Println("\n--- 3. Clearing Memory & Restoring from Snapshot ---")
	fsm.mu.Lock()
	fsm.data = make(map[string]string) // memory wiped!
	fsm.mu.Unlock()
	fmt.Printf("FSM memory after wipe: %d items\n", len(fsm.data))

	reader := io.NopCloser(&diskBuffer)
	if err := fsm.Restore(reader); err != nil {
		panic(err)
	}
	fmt.Printf("FSM after Restore: %d items successfully restored!\n", len(fsm.data))

	// Verification
	fmt.Printf("Sample check: user:42 = '%s'\n", fsm.data["user:42"])
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 82

## Под капотом

Атомарность сохранения снапшота на диске:
В `FileSnapshotStore`:
1. Создается временная папка `snapshots/<id>.tmp`.
2. В нее стримятся файлы `state.bin` и `meta.json`.
3. Для папки и файлов вызывается `fsync`.
4. Временная папка атомарно переименовывается в `snapshots/<id>`.
5. Старые снапшоты, превышающие политику хранения (`retain`), удаляются.

## Подводные камни

- **Синхронный сброс в методе `Snapshot()`**: Если сериализовать гигантскую базу данных прямо внутри `Snapshot()`, пока держится глобальный мьютекс, кластер остановится. В `Snapshot()` делается только быстрый клон структур данных, а сам ввод-вывод происходит в `Persist()`.
- **Забытый `defer rc.Close()`**: Вызывает утечки файловых дескрипторов при частых рестартовых процедурах.

## На собеседовании

В Wildberries и Т-Банке часто спрашивают: *«Как реализовать снапшотинг для FSM размером 100 Гб без удвоения потребления оперативной памяти при клонировании?»*
**Ответ**: Использовать структуры данных на базе **Copy-On-Write (COW)** или LSM-деревьев (как в Pebble или RocksDB). Вместо глубокого копирования всей мапы в RAM берется иммутабельный срез (Read-Only Iterator / Snapshot Handle) на уровне движка хранения. Новые записи пишутся в новые SST-файлы или COW-ветви, а фоновый поток `Persist` последовательно вычитывает итератор на диск без всплеска потребления памяти.
