# Восстановление узла из снимка (Restore from Snapshot) при удалении WAL-логов

## Условие

63. **[Restore from Snapshot]**: Останови один из узлов. Удали его папку с логами (оставив только снапшот). Запусти снова. Узел должен восстановить состояние из снапшота и догнать кластер по оставшимся логам.

### Исходная формулировка

**[Restore from Snapshot]**: Останови один из узлов. Удали его папку с логами (оставив только снапшот). Запусти снова. Узел должен восстановить состояние из снапшота и догнать кластер по оставшимся логам.

## Теория

Сценарий потери или повреждения журнала упреждающей записи (WAL Log Store) при сохранении последнего валидного снимка (`.snap`) является классической задачей аварийного восстановления (Disaster Recovery).

Механизм восстановления при отсутствии промежуточных логов:
1. При старте рантайм `raft.NewRaft` обращается к `SnapshotStore`.
2. Если в `LogStore` нет записей или база данных логов была удалена/пересоздана, узел обнаруживает метаданные снимка: `LastIncludedIndex = K`, `LastIncludedTerm = T`.
3. Узел передает файл снимка в `FSM.Restore(rc)`. Конечное состояние автомата мгновенно обновляется до индекса \(K\).
4. Узел подключается к кластеру как `Follower` и сообщает лидеру свой актуальный `lastLogIndex = K`.
5. Лидер сравнивает свой текущий `commitIndex` с \(K\). Если лидер все еще хранит логи с индексами \(K+1 \dots M\) в своем активном WAL, он пересылает недостающую дельту через стандартный `AppendEntries`. Если же лидер уже успел усечь эти логи, лидер инициирует отправку нового снапшота через `InstallSnapshot`.

## Решение по шагам

1. Смоделируйте структуру узла с раздельными хранилищами `SnapshotStore` (сохраняемым) и `WALLogDir` (удаляемым).
2. Наполните FSM сотней записей и сгенерируйте снапшот на индексе 80.
3. Сымитируйте аварию: удалите директорию с логами WAL (файлы `*.wal`), оставив файл `snapshot-80.snap`.
4. Запустите процедуру восстановления: загрузите снимок через `Restore()` и подключите узел к лидеру.
5. Продемонстрируйте, как лидер досылает оставшиеся логи с 81 по 100 через процедуру репликации.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"sync"
)

type SnapshotStorage struct {
	LastIndex uint64
	LastTerm  uint64
	Payload   []byte
}

type NodeDiskState struct {
	Snapshot *SnapshotStorage
	WAL      map[uint64]string
}

type NodeFSM struct {
	mu   sync.RWMutex
	data map[string]string
}

func (f *NodeFSM) Restore(data []byte) error {
	f.mu.Lock()
	defer f.mu.Unlock()
	return json.Unmarshal(data, &f.data)
}

func (f *NodeFSM) Apply(cmd string) {
	f.mu.Lock()
	defer f.mu.Unlock()
	var op struct{ K, V string }
	if err := json.Unmarshal([]byte(cmd), &op); err == nil {
		f.data[op.K] = op.V
	}
}

func RecoverAfterLogLoss(disk *NodeDiskState) (*NodeFSM, uint64) {
	fsm := &NodeFSM{data: make(map[string]string)}

	if disk.Snapshot != nil {
		fmt.Printf("[Cold Boot] Restoring baseline state from Snapshot at index %d...\n", disk.Snapshot.LastIndex)
		if err := fsm.Restore(disk.Snapshot.Payload); err != nil {
			panic(err)
		}
		return fsm, disk.Snapshot.LastIndex
	}
	return fsm, 0
}

func main() {
	// 1. Initial State: node had 80 keys snapshotted and logs 81..100
	initialData := map[string]string{"account:1": "1000", "account:2": "5000"}
	snapPayload, _ := json.Marshal(initialData)

	disk := &NodeDiskState{
		Snapshot: &SnapshotStorage{LastIndex: 80, LastTerm: 2, Payload: snapPayload},
		WAL: map[uint64]string{
			81: `{"K":"account:3","V":"300"}`,
			82: `{"K":"account:1","V":"1200"}`,
		},
	}

	fmt.Println("--- 1. Node Operational with Snapshot & WAL ---")
	fmt.Printf("Snapshot Index: %d, WAL Entries Count: %d\n", disk.Snapshot.LastIndex, len(disk.WAL))

	// 2. DISASTER: WAL deleted by admin/disk failure!
	fmt.Println("\n💥 SIMULATING ACCIDENTAL LOG DELETION (rm -rf /data/raft/wal/*)...")
	disk.WAL = make(map[uint64]string) // WAL is gone!

	// 3. Restart node
	fsm, restoredIndex := RecoverAfterLogLoss(disk)
	fmt.Printf("Node recovered up to index %d. Current FSM data: %+v\n", restoredIndex, fsm.data)

	// 4. Cluster Catch-Up: Leader detects follower lag and streams missing delta (81..82)
	fmt.Println("\n--- 4. Reconnecting to Leader & Receiving Delta RPC ---")
	leaderDelta := []struct {
		Index uint64
		Cmd   string
	}{
		{Index: 81, Cmd: `{"K":"account:3","V":"300"}`},
		{Index: 82, Cmd: `{"K":"account:1","V":"1200"}`},
	}

	for _, entry := range leaderDelta {
		fmt.Printf("[Leader -> Follower] AppendEntries index %d: %s\n", entry.Index, entry.Cmd)
		fsm.Apply(entry.Cmd)
	}

	fmt.Printf("Final FSM State after catch-up: %+v\n", fsm.data)
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 63

## Под капотом

В промышленной реализации `hashicorp/raft`:
- Файлы снапшотов хранятся в папке `snapshots/<id>/` с расширением `.tmp` во время создания и атомарно переименовываются после валидации контрольной суммы SHA-256 (`meta.json`).
- Если лог-хранилище (BoltDB) полностью очищено, `raft.NewRaft` инициализирует новый BoltDB файл с нулевой записью, выставляет `raft.lastLogIndex = snapMeta.Index` и `raft.lastLogTerm = snapMeta.Term`.
- Это позволяет восстановить узел без повторной синхронизации всего снапшота по медленной сети.

## Подводные камни

- **Рассинхронизация `Term` при потере логов**: Если утерян лог, в котором узел отдал голос (`votedFor`), узел рискует проголосовать заново в текущем терме. К счастью, метаданные терма и голоса в `hashicorp/raft` хранятся в отдельном `StableStore`, независимом от усекаемого WAL.
- **Ошибки десериализации снапшота**: Если схема сериализации изменилась между версиями приложения, `Restore` упадет с ошибкой. Снапшоты обязаны версионироваться.

## На собеседовании

В Яндекс Облаке и Авито часто спрашивают: *«Что произойдет, если реплика восстановилась из снапшота на индексе 100 000, а лидер уже усек свои логи до индекса 120 000?»*
**Ответ**: Лидер обнаружит, что `nextIndex` для данной реплики (\(100 001\)) меньше первого доступного индекса в его собственном WAL (\(120 001\)). В этой ситуации обычный `AppendEntries` невозможен. Лидер автоматически переключит репликацию на RPC `InstallSnapshot`, отправив отстающему узлу свой свежий снимок (например, на индексе 120 000), после чего репликация продолжится в стандартном режиме.
