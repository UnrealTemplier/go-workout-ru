# Развертывание Raft в продакшене: нечетный кворум, гео-распределение, алерты и бэкапы

## Условие

76. **Raft production deployment:**
    * Odd number of nodes (3, 5, 7)
    * Geographically distributed для HA
    * Regular backups of snapshots
    * Monitoring + alerting
    * Chaos testing

### Исходная формулировка

**Raft production deployment:**
* Odd number of nodes (3, 5, 7)
* Geographically distributed для HA
* Regular backups of snapshots
* Monitoring + alerting
* Chaos testing

## Теория

Проектирование архитектуры промышленного Raft-кластера опирается на строгие принципы надежности:

1. **Нечетное число узлов (3, 5, 7)**:
   - Кластер из \(2F+1\) узлов терпит падение \(F\) узлов.
   - \(N=3 \implies F=1\) (кворум 2).
   - \(N=4 \implies F=1\) (кворум 3! Четвертый узел снижает отказоустойчивость, требуя 3 голоса вместо 2).
   - \(N=5 \implies F=2\) (кворум 3 — золотой стандарт High Availability).
   - \(N=7 \implies F=3\) (кворум 4 — для критических систем с высоким риском одновременных аварий).
2. **Географическое распределение (Multi-AZ / Multi-Region)**:
   - Размещение узлов в 3 независимых датацентрах (Availability Zones): AZ-A (2 ноды), AZ-B (2 ноды), AZ-C (1 нода) или по схеме 1+1+1. Потеря целого датацентра оставляет активным кворум из оставшихся зон.
3. **Регулярные снапшоты и бэкапы**:
   - Автоматический экспорт снапшотов каждые \(K\) часов в объектное хранилище (S3/MinIO) с неизменяемостью (Object Lock / WORM).
4. **Мониторинг и алерты**:
   - Алерты P0: отсутствие лидера (`raft_has_leader == 0 > 10s`).
   - Алерты P1: частая смена лидеров (`increase(raft_leader_transitions_total[10m]) > 2`).

## Решение по шагам

1. Создайте декларативный валидатор топологии `ProductionDeploymentValidator`.
2. Реализуйте проверку нечетности узлов и расчет допустимого числа отказов (\(F\)).
3. Проверьте распределение нод по зонам доступности (Anti-Affinity).
4. Опишите структуру правил Prometheus Alerting для Raft.
5. Продемонстрируйте автоматическую проверку готовности кластера к продакшену.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type NodeConfig struct {
	ID               string
	AvailabilityZone string
	DiskType         string
}

type ClusterArchitecturePlan struct {
	Nodes          []NodeConfig
	BackupSchedule string
	HasPromAlerts  bool
}

func ValidateProductionReadiness(plan ClusterArchitecturePlan) error {
	n := len(plan.Nodes)

	// 1. Check Odd Count
	if n < 3 {
		return fmt.Errorf("cluster too small: minimum 3 nodes required, found %d", n)
	}
	if n%2 == 0 {
		return fmt.Errorf("even node count anti-pattern: %d nodes provides same fault tolerance as %d, but increases quorum size", n, n-1)
	}

	// 2. Check Geo / AZ Distribution
	zones := make(map[string]int)
	for _, node := range plan.Nodes {
		zones[node.AvailabilityZone]++
		if node.DiskType != "NVMe" && node.DiskType != "SSD" {
			return fmt.Errorf("node %s has slow storage '%s': Raft WAL requires low-latency SSD/NVMe", node.ID, node.DiskType)
		}
	}

	maxNodesInSingleAZ := 0
	for _, count := range zones {
		if count > maxNodesInSingleAZ {
			maxNodesInSingleAZ = count
		}
	}

	faultTolerance := (n - 1) / 2
	if maxNodesInSingleAZ > faultTolerance && len(zones) < 3 {
		return fmt.Errorf("single AZ outage could destroy quorum: max nodes in one AZ is %d, but cluster only tolerates %d failures",
			maxNodesInSingleAZ, faultTolerance)
	}

	// 3. Backup and Monitoring
	if plan.BackupSchedule == "" {
		return errors.New("missing automated snapshot backup schedule")
	}
	if !plan.HasPromAlerts {
		return errors.New("production cluster must have Prometheus alert rules configured")
	}

	fmt.Printf("✅ Architecture Validated: %d Nodes across %d AZs (Tolerates %d Node Crashes). Quorum = %d\n",
		n, len(zones), faultTolerance, n/2+1)
	return nil
}

func main() {
	validPlan := ClusterArchitecturePlan{
		Nodes: []NodeConfig{
			{ID: "raft-01", AvailabilityZone: "ru-central1-a", DiskType: "NVMe"},
			{ID: "raft-02", AvailabilityZone: "ru-central1-b", DiskType: "NVMe"},
			{ID: "raft-03", AvailabilityZone: "ru-central1-c", DiskType: "NVMe"},
		},
		BackupSchedule: "cron(0 */6 * * *) -> s3://raft-backups-archive",
		HasPromAlerts:  true,
	}

	fmt.Println("--- Validating Recommended Multi-AZ 3-Node Deployment ---")
	if err := ValidateProductionReadiness(validPlan); err != nil {
		fmt.Println("Validation Error:", err)
	}

	fmt.Println("\n--- Validating Risky 4-Node Deployment (Anti-pattern) ---")
	badPlan := validPlan
	badPlan.Nodes = append(badPlan.Nodes, NodeConfig{ID: "raft-04", AvailabilityZone: "ru-central1-a", DiskType: "NVMe"})
	if err := ValidateProductionReadiness(badPlan); err != nil {
		fmt.Printf("Rejected as expected: %v\n", err)
	}
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 76

## Под капотом

Почему \(N=4\) хуже, чем \(N=3\):
- \(N=3\): Кворум \(\lfloor 3/2 \rfloor + 1 = 2\). При падении 1 узла оставшиеся 2 узла формируют кворум. Система работает. Вероятность одновременного падения: \(P^2\).
- \(N=4\): Кворум \(\lfloor 4/2 \rfloor + 1 = 3\). При падении 1 узла оставшиеся 3 узла работают. Но при падении 2 узлов кластер парализован!
- То есть \(N=4\) терпит ровно те же самые сбои (только 1 узел), но вероятность падения хотя бы одного узла из 4 в \(1.33\) раза выше, чем из 3, а сетевой трафик лидера на рассылку сообщений выше на 33%.

## Подводные камни

- **Размещение всех узлов в одном датацентре**: При аварии питания в ЦОД кластер ляжет целиком.
- **Хранение WAL на сетевых дисках (NFS/Ceph)**: Задержки сетевого `fsync` на NFS достигают сотен миллисекунд, провоцируя лавинообразные срывы выборов лидера. Raft WAL обязан жить строго на локальных NVMe дисках.

## На собеседовании

В Яндекс Облаке и Ozon часто спрашивают: *«Как настроить топологию etcd-кластера на 5 узлов в двух датацентрах (DC-1 и DC-2), если третий датацентр отсутствует?»*
**Ответ**: При наличии только двух DC невозможно защититься от падения целого датацентра без привлечения третьей стороны (Tie-Breaker). Если разместить схему 3+2, то при падении DC-1 (3 узла) в DC-2 останется 2 узла из 5 — кворум будет потерян. Решение: развернуть легкий арбитражный узел (Arbiter / Witness Node / Learner) в облаке или независимой серверной точке (DC-3), сформировав топологию 2 + 2 + 1. Тогда падение любого из основных ЦОД оставляет 3 живых узла из 5, сохраняя кворум.
