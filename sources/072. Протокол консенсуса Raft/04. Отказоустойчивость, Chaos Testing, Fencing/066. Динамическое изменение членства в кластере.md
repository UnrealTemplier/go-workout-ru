# Динамическое изменение членства в кластере (Dynamic Cluster Membership) и пересчет кворума

## Условие

66. **[Высокая сложность — Dynamic Cluster Membership]**: Напиши API для управления кластером. Добавь endpoint `/remove-node`, который вызывает `raft.RemoveServer`. Убедись, что кластер корректно перебалансирует квorum (например, при переходе с 5 на 3 узла).

### Исходная формулировка

**[Высокая сложность — Dynamic Cluster Membership]**: Напиши API для управления кластером. Добавь endpoint `/remove-node`, который вызывает `raft.RemoveServer`. Убедись, что кластер корректно перебалансирует квorum (например, при переходе с 5 на 3 узла).

## Теория

Изменение состава кластера на лету (Membership Change) — одна из наиболее деликатных операций в протоколе Raft.

Проблема наивного подхода:
Если просто переключить конфигурацию каждого узла по отдельности, неизбежно возникнет момент времени, когда два непересекающихся подмножества узлов будут использовать разные конфигурации \(C_{old}\) и \(C_{new}\). В результате могут быть одновременно выбраны два разных лидера!

Решения:
1. **Joint Consensus (Whitepaper, Section 6)**: двухфазный переход через промежуточную конфигурацию \(C_{old,new}\), где кворум требует одобрения большинства как старой, так и новой конфигурации.
2. **Single-Server Changes (Ongaro Dissertation)**: безопасное добавление или удаление **строго по одному узлу за раз**. При изменении размера кластера ровно на \(\pm 1\) возникновение раздельных кворумов математически невозможно.
3. **Метод `raft.RemoveServer(id, prevIndex, timeout)`**:
   - Лидер сериализует специальную конфигурационную запись `ConfigurationEntry` в лог.
   - Как только запись закоммичена, кластер мгновенно пересчитывает формулу кворума \(\lfloor N/2 \rfloor + 1\) для нового количества активных серверов.

## Решение по шагам

1. Опишите структуру конфигурации кластера `ClusterConfig` со списком узлов-избирателей (Voters).
2. Реализуйте метод `RemoveServer`, проверяющий наличие узла и пересчитывающий размер кворума.
3. Создайте HTTP REST контроллер с эндпоинтом `POST /remove-node?id=node-5`.
4. Продемонстрируйте переход кластера с 5 узлов (кворум 3) на 4 узла (кворум 3), а затем на 3 узла (кворум 2).
5. Покажите предотвращение удаления самого лидера без предварительной передачи власти.

## Код решения

**`main.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type ServerRole string

type RaftMember struct {
	ID      string `json:"id"`
	Address string `json:"address"`
	IsVoter bool   `json:"is_voter"`
}

type MembershipManager struct {
	mu          sync.RWMutex
	members     map[string]RaftMember
	leaderID    string
	configIndex uint64
}

func NewMembershipManager(leaderID string, initialMembers []RaftMember) *MembershipManager {
	m := make(map[string]RaftMember)
	for _, mem := range initialMembers {
		m[mem.ID] = mem
	}
	return &MembershipManager{
		members:     m,
		leaderID:    leaderID,
		configIndex: 1,
	}
}

func (m *MembershipManager) QuorumSize() int {
	m.mu.RLock()
	defer m.mu.RUnlock()

	voters := 0
	for _, mem := range m.members {
		if mem.IsVoter {
			voters++
		}
	}
	return voters/2 + 1
}

func (m *MembershipManager) RemoveServer(id string) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	if id == m.leaderID {
		return fmt.Errorf("cannot remove active leader %s directly; transfer leadership first", id)
	}

	if _, exists := m.members[id]; !exists {
		return fmt.Errorf("server %s not found in configuration", id)
	}

	delete(m.members, id)
	m.configIndex++

	voters := 0
	for _, mem := range m.members {
		if mem.IsVoter {
			voters++
		}
	}
	newQuorum := voters/2 + 1

	fmt.Printf("[Membership] Removed node %s. Active voters: %d, New Quorum: %d (ConfigIndex: %d)\n",
		id, voters, newQuorum, m.configIndex)

	return nil
}

func (m *MembershipManager) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost || r.URL.Path != "/remove-node" {
		http.NotFound(w, r)
		return
	}

	targetID := r.URL.Query().Get("id")
	if targetID == "" {
		http.Error(w, "missing id parameter", http.StatusBadRequest)
		return
	}

	if err := m.RemoveServer(targetID); err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	w.WriteHeader(http.StatusOK)
	json.NewEncoder(w).Encode(map[string]any{
		"status":      "success",
		"removed_id":  targetID,
		"new_quorum":  m.QuorumSize(),
		"config_term": m.configIndex,
	})
}

func main() {
	// Initialize 5-node cluster
	initialNodes := []RaftMember{
		{ID: "node-1", Address: "10.0.0.1:8000", IsVoter: true},
		{ID: "node-2", Address: "10.0.0.2:8000", IsVoter: true},
		{ID: "node-3", Address: "10.0.0.3:8000", IsVoter: true},
		{ID: "node-4", Address: "10.0.0.4:8000", IsVoter: true},
		{ID: "node-5", Address: "10.0.0.5:8000", IsVoter: true},
	}

	mgr := NewMembershipManager("node-1", initialNodes)
	fmt.Printf("Cluster Initialized: 5 Voters -> Quorum is %d\n", mgr.QuorumSize())

	// Test 1: Remove node-5 via HTTP API
	req1 := httptest.NewRequest(http.MethodPost, "/remove-node?id=node-5", nil)
	rec1 := httptest.NewRecorder()
	mgr.ServeHTTP(rec1, req1)
	fmt.Printf("Response 1: %s", rec1.Body.String())

	// Test 2: Remove node-4 via HTTP API (transition from 4 to 3 nodes)
	req2 := httptest.NewRequest(http.MethodPost, "/remove-node?id=node-4", nil)
	rec2 := httptest.NewRecorder()
	mgr.ServeHTTP(rec2, req2)
	fmt.Printf("Response 2: %s", rec2.Body.String())

	// Test 3: Attempt to remove leader directly (should fail)
	req3 := httptest.NewRequest(http.MethodPost, "/remove-node?id=node-1", nil)
	rec3 := httptest.NewRecorder()
	mgr.ServeHTTP(rec3, req3)
	fmt.Printf("Response 3 (Leader removal check): Code=%d, Body=%s\n", rec3.Code, rec3.Body.String())
}
```

## Под капотом

Что происходит с удаленным узлом в Raft:
1. Удаленный узел перестает получать сердечные сигналы от лидера.
2. По истечении таймера он решит, что лидер умер, увеличит свой Term и начнет спамить кластер запросами `RequestVote`.
3. Чтобы этот удаленный «зомби»-сервер не сбивал лидера с толку, в Raft реализовано правило: если узел получает `RequestVote` в пределах минимального `ElectionTimeout` от последнего контакта с лидером, он игнорирует этот запрос.
4. В `hashicorp/raft` удаленный узел получает команду `DemoteVoter` или специальный пакет закрытия сессии, после чего переходит в терминальное состояние `Shutdown`.

## Подводные камни

- **Одновременное удаление двух узлов**: Попытка вызвать `RemoveServer` параллельно для двух узлов может привести к коллизии конфигурационных записей. Изменения членства обязаны выполняться строго последовательно (Strictly Serialized).
- **Удаление узла из кластера из 2 участников**: При кластере из 2 узлов (\(Q=2\)) удаление одного узла требует одобрения обоих! Если один из них упал, оставшийся узел никогда не сможет удалить соседа штатным образом, так как не имеет кворума.

## На собеседовании

В Авито и Lamoda часто спрашивают: *«Как безопасно вывести узел из Raft-кластера etcd в Kubernetes при scale-down StatefulSet?»*
**Ответ**: Использовать `etcdctl member remove <id>` в `preStop` хуке контейнера Kubernetes До того, как pod будет удален и остановлен! Если Kubernetes просто прибьет pod с помощью `SIGKILL`, кластер останется с узлом-призраком, уменьшая запас отказоустойчивости. Штатный вызов `member remove` пересчитывает кворум на лету при работающем узле, гарантируя бесшовный scale-down.
