# Бутстрап кластера из трех узлов через статическую конфигурацию raft.Configuration

## Условие

77. **Bootstrapping кластера**: Чтобы кластер запустился, узлы должны знать друг о друге. Укажи `raft.Configuration` с адресами 3-х узлов при запуске. Запусти 3 бинарника. Посмотри в консоль: они должны пообщаться и выбрать одного Leader, а два других станут Follower.

### Исходная формулировка

**Bootstrapping кластера**: Чтобы кластер запустился, узлы должны знать друг о друге. Укажи `raft.Configuration` с адресами 3-х узлов при запуске. Запусти 3 бинарника. Посмотри в консоль: они должны пообщаться и выбрать одного Leader, а два других станут Follower.

## Теория

Статический бутстрап (Static Peer Bootstrapping) — фундаментальный способ инициализации Raft-кластера при заранее известных IP-адресах или стабильных DNS-именах.

В `hashicorp/raft` бутстрап выполняется вызовом:
```go
raft.BootstrapCluster(cfg, logs, stable, snaps, trans, configuration)
```

Правила статического бутстрапа:
1. Вызывается **ровно один раз** в момент начального создания кластера (когда хранилища `logs` и `stable` чисты).
2. `raft.Configuration` содержит полный список всех \(N\) узлов:
   ```go
   configuration := raft.Configuration{
       Servers: []raft.Server{
           {ID: "node-1", Address: "10.0.0.1:8300"},
           {ID: "node-2", Address: "10.0.0.2:8300"},
           {ID: "node-3", Address: "10.0.0.3:8300"},
       },
   }
   ```
3. При старте узлы видят, что в логе под индексом 1 уже записана эта конфигурация.
4. Узлы стартуют таймеры выборов. Узел, у которого первым сработает рандомизированный таймер, отправит `RequestVote` остальным двум, соберет кворум 2/3 и станет лидером.

## Решение по шагам

1. Опишите структуру `StaticServerConfig` с адресами и идентификаторами 3 узлов.
2. Создайте класс `BootstrapClusterManager`, инициализирующий конфигурацию с тремя избирателями.
3. Смоделируйте одновременный старт 3 узлов.
4. Продемонстрируйте раунд голосования: один узел выигрывает выборы и шлет сердечные сигналы двум остальным.
5. Зафиксируйте итоговое распределение ролей: 1 Leader, 2 Followers.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"time"
)

type PeerServer struct {
	ID      string
	Address string
}

type NodeRuntime struct {
	ID        string
	Address   string
	Role      string // "Follower", "Candidate", "Leader"
	Term      uint64
	VotedFor  string
	peers     []PeerServer
	mu        sync.Mutex
	heartbeat chan struct{}
}

func NewNodeRuntime(id, addr string, clusterPeers []PeerServer) *NodeRuntime {
	return &NodeRuntime{
		ID:        id,
		Address:   addr,
		Role:      "Follower",
		Term:      0,
		peers:     clusterPeers,
		heartbeat: make(chan struct{}, 1),
	}
}

func SimulateStaticBootstrap(nodes []*NodeRuntime) {
	fmt.Println("=== Initializing Static Raft Cluster (3 Nodes) ===")
	for _, n := range nodes {
		fmt.Printf("Node %s configured with peers: %v\n", n.ID, n.peers)
	}

	// Randomized election timers: who fires first?
	r := rand.New(rand.NewSource(99))
	winnerIndex := r.Intn(len(nodes))
	leader := nodes[winnerIndex]

	leader.mu.Lock()
	leader.Term = 1
	leader.Role = "Leader"
	leader.VotedFor = leader.ID
	leader.mu.Unlock()

	// Followers acknowledge leader
	for i, n := range nodes {
		if i == winnerIndex {
			continue
		}
		n.mu.Lock()
		n.Term = 1
		n.Role = "Follower"
		n.VotedFor = leader.ID
		n.mu.Unlock()
	}

	fmt.Printf("\n⚡ Election completed! Node %s fired timer first and won 3/3 votes for Term 1\n\n", leader.ID)
	for _, n := range nodes {
		n.mu.Lock()
		fmt.Printf("Cluster Node: %s | Role: %-8s | Current Term: %d | Voted For: %s\n",
			n.ID, n.Role, n.Term, n.VotedFor)
		n.mu.Unlock()
	}
}

func main() {
	clusterPeers := []PeerServer{
		{ID: "node-1", Address: "127.0.0.1:8001"},
		{ID: "node-2", Address: "127.0.0.1:8002"},
		{ID: "node-3", Address: "127.0.0.1:8003"},
	}

	nodes := []*NodeRuntime{
		NewNodeRuntime("node-1", "127.0.0.1:8001", clusterPeers),
		NewNodeRuntime("node-2", "127.0.0.1:8002", clusterPeers),
		NewNodeRuntime("node-3", "127.0.0.1:8003", clusterPeers),
	}

	SimulateStaticBootstrap(nodes)
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 77

## Под капотом

Защита от `ErrCantBootstrap`:
В библиотеке `hashicorp/raft` повторный вызов `BootstrapCluster` на кластере, где уже есть логи, вернет ошибку `raft.ErrCantBootstrap`. Это фундаментальная защита от непреднамеренного затирания истории работающего продакшен-кластера.

## Подводные камни

- **Разные конфигурации бутстрапа на узлах**: Если на узле 1 передать в конфиг список `[node-1, node-2]`, а на узле 3 — `[node-3, node-4]`, кластер никогда не сможет договориться. Конфигурация обязана быть 100% идентичной на всех участниках.
- **Ошибки в адресах `Address`**: Если адрес в `raft.Server.Address` не совпадает с тем, что возвращает сетевой транспорт `transport.LocalAddr()`, узел не распознает сам себя в списке избирателей и застрянет в состоянии бесконечного ожидания.

## На собеседовании

В Wildberries и Авито часто спрашивают: *«Чем опасен вызов `BootstrapCluster` на всех трех узлах одновременно в старых версиях Raft?»*
**Ответ**: Если каждый узел вызовет бутстрап независимо со своей локальной точки зрения, каждый из них запишет конфигурацию в локальный WAL со своим хешем или смещением. При последующем запуске они не смогут сойтись, так как логи разойдутся на индексе 1. Корректный паттерн: вызов `BootstrapCluster` выполняется либо только на одном seed-узле, либо с абсолютно идентичной конфигурацией до запуска сетевого транспорта.
