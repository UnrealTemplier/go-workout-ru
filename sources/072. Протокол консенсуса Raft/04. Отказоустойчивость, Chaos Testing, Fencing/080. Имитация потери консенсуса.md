# Имитация потери консенсуса: канал LeaderCh, потеря кворума и отказ в обслуживании записей

    * Напишите прослушиватель событий смены лидера через канал `raft.LeaderCh()`.

### Исходная формулировка

**Имитация потери консенсуса**: Запустите ваш 3-узельный Raft-кластер.
    * Напишите прослушиватель событий смены лидера через канал `raft.LeaderCh()`.
    * Отключите один из узлов. Убедитесь, что оставшиеся два узла (большинство) продолжают успешно принимать записи.
    * Отключите второй узел (остался один). Убедитесь, что единственный выживший узел автоматически теряет статус лидера, переходит в режим ожидания и блокирует любые операции записи, так как кворум большинства недостижим.

## Теория

Свойство живучести (Liveness) и отказоустойчивости в Raft:
Кластер из \(N=3\) узлов способен продолжать работу и коммитить новые записи только до тех пор, пока живо строжайшее большинство узлов:
$$\text{Quorum} = \lfloor N/2 \rfloor + 1 = \lfloor 3/2 \rfloor + 1 = 2$$

Градация состояний:
1. **3 узла живы (\(3/3\))**: Оптимальное состояние. Кворум собирается мгновенно.
2. **1 узел отключен (\(2/3\))**: Допустимый отказ (\(F=1\)). Оставшиеся 2 узла формируют кворум. Записи продолжают успешно фиксироваться.
3. **2 узла отключены (\(1/3\))**: Катастрофическая потеря большинства! Оставшийся узел не может набрать кворум 2.
   - Любая попытка вызвать `raft.Apply` обязана **заблокироваться** до восстановления связи или завершиться ошибкой `ErrLeadershipLost` / `Timeout`.
   - Система переходит в режим Read-Only (или полной блокировки) для защиты от расхождения данных (Split-Brain Safety).

## Решение по шагам

1. Создайте модель кластера с каналом событий лидерства `LeaderCh() <-chan bool`.
2. Запустите горутину мониторинга канала смены статуса.
3. Отключите один узел и выполните успешную запись с кворумом 2/3.
4. Отключите второй узел, сократив доступность до 1/3.
5. Попытайтесь выполнить запись, зафиксируйте ошибку потери кворума по таймауту.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type QuorumCluster struct {
	mu           sync.RWMutex
	nodesTotal   int
	aliveNodes   map[int]bool
	leaderID     int
	leaderCh     chan bool
}

func NewQuorumCluster(n int) *QuorumCluster {
	alive := make(map[int]bool)
	for i := 1; i <= n; i++ {
		alive[i] = true
	}
	return &QuorumCluster{
		nodesTotal: n,
		aliveNodes: alive,
		leaderID:   1,
		leaderCh:   make(chan bool, 10),
	}
}

func (c *QuorumCluster) StopNode(id int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	delete(c.aliveNodes, id)
	fmt.Printf("[Cluster Alert] Node %d stopped. Alive nodes: %d/%d\n", id, len(c.aliveNodes), c.nodesTotal)

	quorum := c.nodesTotal/2 + 1
	if len(c.aliveNodes) < quorum {
		fmt.Printf("[Cluster Alert] 🚨 QUORUM LOST! Active: %d, Required: %d\n", len(c.aliveNodes), quorum)
		c.leaderCh <- false
	}
}

func (c *QuorumCluster) Propose(ctx context.Context, key, val string) error {
	c.mu.RLock()
	defer c.mu.RUnlock()

	quorum := c.nodesTotal/2 + 1
	acks := 0

	// Count alive acknowledgements
	for id := range c.aliveNodes {
		if c.aliveNodes[id] {
			acks++
		}
	}

	if acks < quorum {
		// Wait for quorum or context timeout
		select {
		case <-ctx.Done():
			return fmt.Errorf("propose timeout: quorum lost (only %d/%d nodes available)", acks, c.nodesTotal)
		}
	}

	fmt.Printf("[Raft Log] Successfully committed '%s'='%s' with %d/%d ACKs\n", key, val, acks, c.nodesTotal)
	return nil
}

func main() {
	cluster := NewQuorumCluster(3)

	// Monitor leader status channel
	go func() {
		for isLeader := range cluster.leaderCh {
			if !isLeader {
				fmt.Println("[Listener] Detected leadership revocation due to quorum loss!")
			}
		}
	}()

	fmt.Println("--- Phase 1: All 3 Nodes Alive ---")
	ctx1, cancel1 := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel1()
	_ = cluster.Propose(ctx1, "config:mode", "production")

	fmt.Println("\n--- Phase 2: Stopping Node 3 (Quorum 2/3 holds) ---")
	cluster.StopNode(3)
	ctx2, cancel2 := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel2()
	_ = cluster.Propose(ctx2, "config:mode", "degraded_2_nodes")

	fmt.Println("\n--- Phase 3: Stopping Node 2 (Quorum 1/3 LOST) ---")
	cluster.StopNode(2)
	ctx3, cancel3 := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel3()

	err := cluster.Propose(ctx3, "config:mode", "offline_write")
	if err != nil {
		fmt.Printf("Write failed as expected: %v\n", err)
	}
}
```

ℹ️ Реализация на Go 1.22+ для Упражнения 80

## Под капотом

Поведение канала `raft.LeaderCh()`:
В `hashicorp/raft` функция `LeaderCh() <-chan bool` передает:
- `true`: узел только что выиграл выборы и стал признанным лидером.
- `false`: узел потерял лидерство (обнаружил более высокий Term от другого узла, либо сработал таймаут потери контакта с большинством через `CheckQuorum`).
Это позволяет фоновым процессам приложения (например, шедулерам или консьюмерам Kafka) мгновенно запускаться или останавливаться.

## Подводные камни

- **Игнорирование `context.Timeout` при потере кворума**: Если вызвать `Apply` без таймаута, когда в кластере осталось меньшинство узлов, HTTP-горутина зависнет навечно, приводя к исчерпанию пула горутин и памяти (Goroutine Leak).
- **Попытка голосовать в меньшинстве**: Меньшинство никогда не должно отвечать клиенту успехом.

## На собеседовании

В Яндекс Облаке и Авито задают вопрос: *«Почему при потере кворума в кластере из 3 узлов оставшийся узел не может продолжить хотя бы читать данные из FSM?»*
**Ответ**: Может, но только в режиме `Stale Read`! В режиме линейного чтения (`Linearizable Read`) чтение запрещено, поскольку оставшийся изолированный узел не знает: возможно, два других узла живы, сформировали большинство в другой сетевой партиции и уже закоммитили 100 новых записей. Если единственный узел ответит на чтение клиенту, он отдаст устаревшие данные, нарушив линеаризуемость.
