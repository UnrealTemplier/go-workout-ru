# Соблюдение канонических error codes в JSON-RPC 2.0: единый контракт клиента

## Условие

77. **Standard error codes соблюдайте.**: `-32700`, `-32600`, `-32601`, `-32602`, `-32603` — это universal language для JSON-RPC clients.

### Исходная формулировка

**Standard error codes соблюдайте.**: `-32700`, `-32600`, `-32601`, `-32602`, `-32603` — это universal language для JSON-RPC clients.

## Теория

Клиентские библиотеки JSON-RPC 2.0 (для Python, TypeScript, Java, Go) полагаются на строгое соблюдение кодов системных ошибок:
- `-32700` (**Parse Error**): Битый JSON.
- `-32600` (**Invalid Request**): Нарушение структуры JSON-RPC.
- `-32601` (**Method Not Found**): Метод отсутствует в роутере.
- `-32602` (**Invalid Params**): Ошибка валидации структуры аргументов.
- `-32603` (**Internal Error**): Непредвиденный сбой сервера.

Если разработчик бэкенда начинает возвращать самодельные коды (например, `code: 404` или `code: 500`) в ответ на системные ошибки протокола, стандартный клиент не сможет корректно обработать исключение.

В Go правильный подход — изоляция протокольных ошибок в виде строгих типизированных констант и функций-конструкторов.

## Решение по шагам

1. Создайте пакет или структуру с константами кодов спецификации.
2. Напишите валидатор входящего JSON-RPC запроса.
3. Реализуйте генераторы стандартных ошибок протокола.
4. Напишите тест соответствия возвращаемых кодов официальному RFC JSON-RPC 2.0.

## Код решения

**`spec_errors.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
)

type ErrorCode int

const (
	CodeParseError     ErrorCode = -32700
	CodeInvalidRequest ErrorCode = -32600
	CodeMethodNotFound ErrorCode = -32601
	CodeInvalidParams  ErrorCode = -32602
	CodeInternalError  ErrorCode = -32603
)

func (c ErrorCode) Message() string {
	switch c {
	case CodeParseError:
		return "Parse error"
	case CodeInvalidRequest:
		return "Invalid Request"
	case CodeMethodNotFound:
		return "Method not found"
	case CodeInvalidParams:
		return "Invalid params"
	case CodeInternalError:
		return "Internal error"
	default:
		return "Server error"
	}
}

type StandardRPCError struct {
	Code    ErrorCode `json:"code"`
	Message string    `json:"message"`
	Data    any       `json:"data,omitempty"`
}

func NewStandardError(code ErrorCode, data any) *StandardRPCError {
	return &StandardRPCError{
		Code:    code,
		Message: code.Message(),
		Data:    data,
	}
}

func main() {
	// Демонстрация генерации канонических ошибок
	err1 := NewStandardError(CodeMethodNotFound, map[string]string{"method": "crypto.transfer"})
	out1, _ := json.Marshal(err1)
	fmt.Println("Method not found error:", string(out1))

	err2 := NewStandardError(CodeInvalidParams, []string{"field 'amount' must be positive"})
	out2, _ := json.Marshal(err2)
	fmt.Println("Invalid params error:", string(out2))
}
```

ℹ️ Эталонная типизация канонических кодов ошибок JSON-RPC 2.0

## Под капотом

Спецификация JSON-RPC 2.0 явно указывает: текст поля `message` для системных кодов диапазона `[-32700, -32600]` должен быть кратким стандартным предложением (например, строго `Method not found`). Все динамические детали (какой именно метод искали, какие параметры не прошли валидацию) должны передаваться исключительно в объекте `data`.

## Подводные камни

1. **Переопределение `message` системной ошибки**: Замена `"Method not found"` на русскоязычный текст `"Метод не существует"` в поле `message` может сломать зарубежные SDK, проверяющие строковое равенство сообщений.
2. **Использование положительных чисел для системных ошибок**: Положительные коды зарезервированы для бизнес-логики приложения.

## На собеседовании

В распределенных блокчейн-платформах и открытых API банков соблюдение RFC обязательно. Вопрос на интервью: 'Почему нельзя возвращать HTTP 404, когда метод JSON-RPC не найден?' Ответ: HTTP 404 означает, что не найден сам эндпоинт сетевого шлюза (URL путь `/rpc`). Если сервер ответит HTTP 404, клиент решит, что упал сервер или неверно указан хост. Правильный ответ: HTTP 200 с телом JSON-RPC Error code `-32601`.
