# In-process gRPC-Web Прокси: обертка над grpc.Server через improbable-eng/grpc-web

## Условие

82. **[gRPC-Web — Прокси]**: Подними обычный gRPC-сервер. Используй `grpcweb` пакет (`github.com/improbable-eng/grpc-web/go/grpcweb`). Оберни gRPC-сервер в `grpcweb.WrapServer()`. Запуши HTTP-запрос через `curl` с заголовком `Content-Type: application/grpc-web+proto`.

### Исходная формулировка

## Теория

Развертывание отдельного прокси-сервера Envoy не всегда целесообразно: в тестовых средах, локальной разработке, утилитах командной строки или легковесных микросервисах запуск дополнительного C++ процесса Envoy усложняет сборку и потребляет память.

Библиотека **`github.com/improbable-eng/grpc-web/go/grpcweb`** предоставляет встроенный в Go-процесс адаптер:
1. Оборачивает стандартный `*grpc.Server` в объект `*grpcweb.WrappedServer`.
2. Реализует стандартный интерфейс `http.Handler`.
3. Анализирует входящие HTTP-запросы: если запрос содержит заголовки gRPC-Web (`application/grpc-web`, `application/grpc-web-text`), обертка декодирует запрос, передает его в локальный gRPC-сервер, упаковывает HTTP/2 трейлеры в бинарные фреймы и отдает браузеру.
4. Обычные REST или статические файлы обслуживаются тем же самым веб-сервером.

## Решение по шагам

1. Создайте стандартный gRPC-сервер на Go (`grpc.NewServer()`).
2. Оберните его с помощью `grpcweb.WrapServer(grpcServer, opts...)`.
3. Настройте обработку CORS через опцию `WithOriginFunc`.
4. Создайте единый `http.Handler`, маршрутизирующий gRPC-Web и стандартные HTTP запросы.
5. Запустите сервер на едином порту `:8080`.

## Код решения

**`inprocess_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"

	"github.com/improbable-eng/grpc-web/go/grpcweb"
	"google.golang.org/grpc"
)

// Демонстрационный сервис
type MockCatalogService struct{}

func main() {
	// 1. Создание обычного gRPC сервера
	grpcServer := grpc.NewServer()
	// В реальном проекте: catalogpb.RegisterCatalogServiceServer(grpcServer, &MockCatalogService{})

	// 2. Оборачивание в In-process gRPC-Web прокси
	wrappedServer := grpcweb.WrapServer(
		grpcServer,
		grpcweb.WithOriginFunc(func(origin string) bool {
			// В продакшене: валидация домена Origin (например, *.mycorp.ru)
			return true
		}),
		grpcweb.WithAllowedRequestHeaders([]string{
			"x-grpc-web",
			"content-type",
			"x-user-agent",
			"authorization",
		}),
	)

	// 3. Единый HTTP роутер
	mux := http.NewServeMux()

	// Регистрация системных REST эндпоинтов
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("HEALTHY"))
	})

	// Главный диспетчер: перенаправляет gRPC-Web в обертку, остальное в mux
	rootHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if wrappedServer.IsGrpcWebRequest(r) || wrappedServer.IsAcceptableGrpcCorsRequest(r) {
			wrappedServer.ServeHTTP(w, r)
			return
		}
		mux.ServeHTTP(w, r)
	})

	fmt.Println("In-process gRPC-Web сервер запущен на http://localhost:8080")
	_ = http.ListenAndServe(":8080", rootHandler)
}
```

ℹ️ Развертывание gRPC и gRPC-Web в одном процессе без стороннего прокси

## Под капотом

Метод `wrappedServer.IsGrpcWebRequest(r)` проверяет заголовок `Content-Type` на наличие подстроки `application/grpc-web`. Для браузерных запросов Preflight метод `IsAcceptableGrpcCorsRequest(r)` проверяет метод `OPTIONS` и заголовок `Access-Control-Request-Headers`. Обертка напрямую вызывает метод `grpcServer.ServeHTTP(w, r)`, эмулируя внутренний транспорт HTTP/2, что исключает сетевые задержки TCP Loopback.

## Подводные камни

1. **Забытые заголовки в `WithAllowedRequestHeaders`**: Если браузер отправляет заголовок аутентификации `Authorization`, а он не указан в списке разрешенных заголовков обертки, preflight `OPTIONS` завершится ошибкой 403 Forbidden.
2. **Сложности с gRPC Reflection**: In-process обертка не всегда корректно проксирует рефлексию gRPC для веб-инструментов, если не разрешены соответствующие типы контента.

## На собеседовании

В микросервисах Tinkoff и Avito часто спрашивают: 'Когда in-process gRPC-Web лучше Envoy, а когда хуже?' Ответ: In-process идеален для разработки, интеграционных тестов и изолированных утилит, так как не требует Docker и зависимостей. На продакшене с высокой нагрузкой (100k+ RPS) Envoy предпочтительнее, так как написан на C++, эффективнее работает с памятью и предоставляет развитые фильтры WAF, rate-limiting и circuit breaker.
