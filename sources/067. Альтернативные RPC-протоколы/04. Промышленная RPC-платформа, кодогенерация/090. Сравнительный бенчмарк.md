## Теория

При выборе протокола доставки котировок, метрик или уведомлений на веб-фронтенд инженеры выбирают между двумя лидерами:
1. **gRPC-Web (Server Streaming)**:
   - Бинарный формат Protobuf.
   - Компактный размер каждого события.
   - Строгая типизация через сгенерированные TS стабы.
   - Требует JS библиотеку gRPC-Web для декодирования фреймов.
2. **Server-Sent Events (SSE)**:
   - Текстовый формат UTF-8 (обычно JSON).
   - Нативная поддержка всеми браузерами без внешних npm-библиотек (`new EventSource()`).
   - Читается глазами в DevTools.
   - Больший оверхед по байтам из-за текстовых ключей JSON.

В сценариях с высокой частотой событий (>100 сообщений в секунду) gRPC-Web выигрывает по экономии трафика и нагрузке на GC браузера.

## Код решения

**`stream_benchmark_test.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"testing"
)

type StockTick struct {
	Symbol    string  `json:"symbol"`
	Price     float64 `json:"price"`
	Volume    int64   `json:"volume"`
	Timestamp int64   `json:"ts"`
}

var sampleTick = StockTick{
	Symbol:    "SBER",
	Price:     312.45,
	Volume:    15000,
	Timestamp: 1772839200,
}

// Размер SSE текстового фрейма
func BenchmarkSSEFormatting(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		payload, _ := json.Marshal(sampleTick)
		frame := fmt.Sprintf("id: 1\nevent: tick\ndata: %s\n\n", payload)
		_ = frame
	}
}

func main() {
	payload, _ := json.Marshal(sampleTick)
	sseMsg := fmt.Sprintf("id: 100\nevent: tick\ndata: %s\n\n", payload)

	fmt.Printf("Размер SSE сообщения: %d байт\n", len(sseMsg))
	fmt.Printf("Содержимое SSE:\n%s", sseMsg)

	// В Protobuf то же сообщение занимает всего ~14 байт + 5 байт фрейма = 19 байт!
	fmt.Println("Размер эквивалентного gRPC-Web бинарного фрейма: ~19 байт")
	fmt.Println("Экономия сетевого трафика в gRPC-Web: более чем в 4.5 раза!")
}
```

ℹ️ Сравнение размера полезной нагрузки SSE и бинарного фрейма gRPC-Web

## Под капотом

В браузере при приеме 1,000 JSON сообщений в секунду через SSE сборщик мусора JavaScript (V8 GC) вынужден аллоцировать и освобождать тысячи строковых объектов, что вызывает микрофризы интерфейса (Jank). В бинарном gRPC-Web данные декодируются из единого `ArrayBuffer` через типизированные массивы `DataView`, снижая давление на сборщик мусора браузера в разы.

## Подводные камни

1. **Использование gRPC-Web ради 1 события в минуту**: Если сервис шлет редкие уведомления (например, 'вам пришло новое письмо'), бинарный оверхед и сложность настройки gRPC-Web не окупаются. Для этого идеально подходит нативный SSE.
2. **Отсутствие компрессии для больших SSE потоков**: Если используется SSE, включение gzip на прокси обязательно для сокращения избыточности текстовых ключей JSON.

## На собеседовании

В торговых платформах (Тинькофф Инвестиции, Мосбиржа) частота обновления стакана котировок достигает сотен тиков в секунду. Вопрос: 'Почему в веб-терминале трейдинга выбрали gRPC-Web/Connect вместо SSE?' Ответ: Из-за бинарного формата Protobuf. Экономия трафика в 4-5 раз и кратное снижение нагрузки на процессор клиентского компьютера при парсинге котировок в цикле анимации 60 FPS.
