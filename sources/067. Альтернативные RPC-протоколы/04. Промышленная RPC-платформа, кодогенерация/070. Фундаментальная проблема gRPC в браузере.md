## Теория

Почему стандартный gRPC не может работать в веб-браузере напрямую без костылей и прокси?

Причина кроется в архитектуре протокола HTTP/2 и ограничениях браузерного API (`fetch` и `XMLHttpRequest`):
1. **HTTP/2 Trailers**: Стандартный gRPC протокол передает статус завершения операции (`grpc-status: 0` или `grpc-status: 5`) и статусное сообщение (`grpc-message: OK`) в **хвостовых заголовках (Trailers)**, которые отсылаются сервером в самом конце HTTP/2 потока — ПОСЛЕ всех фреймов `DATA`.
2. **Браузерная изоляция (W3C Fetch API)**: Спецификация `fetch()` в современных браузерах не предоставляет JavaScript-коду надежного доступа к Trailers фреймам HTTP/2. Браузер считывает тело (`ReadableStream`), но хвостовые заголовки либо отбрасываются, либо недоступны скрипту до закрытия всего соединения.
3. **Произвольное управление фреймами**: Браузер не позволяет коду веб-страницы вручную собирать низкоуровневые HTTP/2 фреймы (`HEADERS`, `SETTINGS`, `RST_STREAM`, `WINDOW_UPDATE`).

**Решение gRPC-Web**:
Спецификация gRPC-Web переносит Trailers из заголовков HTTP/2 внутрь самого **потока данных (Data Body)**:
- Каждое сообщение снабжается 5-байтным префиксом: 1 байт флагов и 4 байта длины.
- Обычные сообщения Protobuf имеют флаг `0x00`.
- Финальное сообщение с трейлерами (`grpc-status`, `grpc-message`) кодируется как специальный фрейм с флагом `0x80` (MSB=1). Браузерный JS считывает этот чанк из тела ответа и парсит статус вызова!

## Код решения

**`grpcweb_framing.go`**

```go
package main

import (
	"bytes"
	"encoding/binary"
	"fmt"
	"net/http"
)

const (
	FrameData    byte = 0x00
	FrameTrailer byte = 0x80
)

// EncodeGRPCWebFrame упаковывает полезную нагрузку в 5-байтный gRPC фрейм
func EncodeGRPCWebFrame(flag byte, payload []byte) []byte {
	buf := make([]byte, 5+len(payload))
	buf[0] = flag
	binary.BigEndian.PutUint32(buf[1:5], uint32(len(payload)))
	copy(buf[5:], payload)
	return buf
}

func handleGRPCWebSimulation(w http.ResponseWriter, r *http.Request) {
	// 1. Устанавливаем заголовок gRPC-Web
	w.Header().Set("Content-Type", "application/grpc-web+proto")

	// 2. Формируем тело сообщения (флаг 0x00)
	sampleProtobufMsg := []byte("fake-protobuf-serialized-data")
	dataFrame := EncodeGRPCWebFrame(FrameData, sampleProtobufMsg)

	// 3. Формируем завершающий трейлер (флаг 0x80)
	// Трейлеры упаковываются в виде HTTP заголовков: grpc-status и grpc-message
	trailers := "grpc-status: 0\r\ngrpc-message: OK\r\n"
	trailerFrame := EncodeGRPCWebFrame(FrameTrailer, []byte(trailers))

	// Записываем оба фрейма в тело HTTP-ответа
	_, _ = w.Write(dataFrame)
	_, _ = w.Write(trailerFrame)
}

func main() {
	// Демонстрация сборки фреймов
	data := []byte("hello")
	frame := EncodeGRPCWebFrame(FrameData, data)
	fmt.Printf("Data frame (len=%d): флаг=0x%02x, размер=%d байт\n", len(frame), frame[0], binary.BigEndian.Uint32(frame[1:5]))

	trailer := EncodeGRPCWebFrame(FrameTrailer, []byte("grpc-status: 0\r\n"))
	fmt.Printf("Trailer frame (len=%d): флаг=0x%02x, трейлеры внутри тела!\n", len(trailer), trailer[0])
}
```

## Под капотом

В бинарном формате gRPC префикс длины всегда кодируется в Big-Endian (сетевой порядок байтов). Первый бит старшего байта (байт 0) зарезервирован под флаги: в обычном gRPC он указывает на сжатие (`0x01` — gzip), а в gRPC-Web старший бит (`0x80`) указывает, что содержимое блока является текстовым набором HTTP-трейлеров, а не Protobuf-сообщением. Именно этот трюк позволяет обойти ограничения браузерного Fetch API.

## Подводные камни

1. **Потеря трейлеров при буферизации прокси**: Если промежуточный балансировщик (например, старый Nginx) склеивает или буферизирует фреймы, клиентский декодер gRPC-Web может зависнуть в ожидании завершающего маркера stream.
2. **Неверный порядок байт длины**: Запись длины в Little-Endian приводит к тому, что клиент пытается прочитать гигабайты несуществующих данных и падает по Out-of-Memory.

## На собеседовании

На собеседованиях в инфраструктурные команды VK и Яндекса часто спрашивают: 'В чем ключевое отличие фрейминга gRPC-Web от классического gRPC over HTTP/2?' Ответ: В классическом gRPC трейлеры передаются на уровне HTTP/2 протокола как финальный `HEADERS` фрейм с флагом `END_STREAM`. В gRPC-Web трейлеры упаковываются внутрь `DATA` фреймов HTTP/1.1 или HTTP/2 с 1-байтным префиксом `0x80`, что позволяет JS-коду в браузере прочитать их через ReadableStream.
