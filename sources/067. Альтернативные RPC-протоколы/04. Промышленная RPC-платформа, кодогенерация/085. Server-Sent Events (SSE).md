# Server-Sent Events (SSE): легковесная альтернатива WebSockets и gRPC-Web

## Условие

85. Server-Sent Events (SSE)

### Исходная формулировка

Server-Sent Events (SSE)

## Теория

**Server-Sent Events (SSE)** — веб-стандарт потоковой передачи текстовых данных от сервера к браузеру в рамках постоянного HTTP-соединения (`Content-Type: text/event-stream`).

Почему в большинстве задач SSE превосходит WebSockets:
1. **Простота протокола**: Работает поверх стандартного HTTP/1.1 или HTTP/2. Не требует специального WebSocket Upgrade рукопожатия.
2. **Встроенная поддержка в браузерах**: Нативный JavaScript API `EventSource` реализует **автоматическое переподключение (Auto-reconnect)** с экспоненциальной задержкой из коробки!
3. **Сохранение контекста и курсора**: Заголовок `Last-Event-ID` автоматически отправляется браузером при восстановлении связи, позволяя серверу дослать клиенту пропущенные события.
4. **Легкость кэширования и балансировки**: Проходит через любые корпоративные прокси, файрволы и CDN без дополнительных настроек сокетов.

## Решение по шагам

1. Создайте HTTP-хэндлер с заголовком `Content-Type: text/event-stream`.
2. Настройте заголовки запрета буферизации: `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
3. Реализуйте цикл отправки событий в формате `id: <id>\nevent: <name>\ndata: <json>\n\n`.
4. Сбрасывайте буфер после каждого события через `http.Flusher`.
5. Корректно завершайте цикл при разрыве клиентского контекста `r.Context().Done()`.

## Код решения

**`sse_server.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

func handleSSE(w http.ResponseWriter, r *http.Request) {
	// 1. Установка обязательных заголовков SSE
	w.Header().Set("Content-Type", "text/event-stream")
	w.Header().Set("Cache-Control", "no-cache")
	w.Header().Set("Connection", "keep-alive")
	w.Header().Set("Access-Control-Allow-Origin", "*")
	w.Header().Set("X-Accel-Buffering", "no") // Отключение буферизации в Nginx

	flusher, ok := w.(http.Flusher)
	if !ok {
		http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
		return
	}

	// 2. Чтение Last-Event-ID для дочитки пропущенных данных
	lastID := r.Header.Get("Last-Event-ID")
	fmt.Printf("Клиент подключился к SSE (Last-Event-ID: %s)\n", lastID)

	ctx := r.Context()
	ticker := time.NewTicker(1 * time.Second)
	defer ticker.Stop()

	eventID := 0
	for {
		select {
		case <-ctx.Done():
			fmt.Println("Клиент закрыл вкладку или потерял сеть")
			return
		case t := <-ticker.C:
			eventID++
			// Формат фрейма SSE:
			// id: <number>\n
			// event: <name>\n
			// data: <payload>\n\n
			msg := fmt.Sprintf("id: %d\nevent: price_update\ndata: {\"symbol\":\"GAZP\",\"price\":%d,\"ts\":%d}\n\n",
				eventID, 150+eventID%10, t.Unix())

			_, err := w.Write([]byte(msg))
			if err != nil {
				return
			}
			flusher.Flush() // Мгновенная отправка в TCP-сокет
		}
	}
}

func main() {
	http.HandleFunc("/events", handleSSE)
	fmt.Println("SSE Server running on :8080/events")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`client.html`**

```bash
<!-- Использование нативного браузерного EventSource -->
<script>
  const evtSource = new EventSource("http://localhost:8080/events");

  // Автоматический реконнект и обработка событий
  evtSource.addEventListener("price_update", (event) => {
    const data = JSON.parse(event.data);
    console.log(`Получена котировка ID=${event.lastEventId}:`, data);
  });

  evtSource.onerror = (err) => {
    console.warn("Связь потеряна. Браузер автоматически переподключится...");
  };
</script>
```

ℹ️ Браузерное подключение через нативный EventSource API

## Под капотом

В протоколе SSE два последовательных символа перевода строки `\n\n` служат демаркатором окончания сообщения. Когда браузерный стек видит `\n\n`, он немедленно диспатчит событие в JavaScript движок. Браузер также автоматически сохраняет значение из строки `id: <val>` и при разрыве TCP-соединения отправляет его в заголовке `Last-Event-ID: <val>` в следующем HTTP GET запросе.

## Подводные камни

1. **Забытый `flusher.Flush()`**: Если не вызвать `Flush()`, Go будет накапливать данные в буфере (обычно 4 КБ), и клиент не получит обновления в реальном времени.
2. **Лимит HTTP/1.1 соединений**: По стандарту браузер открывает не более 6 соединений на домен в HTTP/1.1. Обязательно используйте HTTP/2 для раздачи SSE!

## На собеседовании

В маркетплейсах (Ozon, Wildberries) статусы оформления заказа передаются покупателю через SSE. Вопрос: 'В чем преимущество SSE перед WebSocket для нотификаций о статусе заказа?' Ответ: SSE работает в рамках стандартной инфраструктуры HTTP/2, не требует отдельного стейтфул-кластера для сокетов, обладает автоматическим реконнектом и механизмом `Last-Event-ID` для предотвращения потери нотификаций при переключении телефона с Wi-Fi на LTE.
