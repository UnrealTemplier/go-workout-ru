## Теория

В микросервисной архитектуре с сотнями сервисов классический паттерн **Envoy Sidecar** порождает скрытые эксплуатационные издержки:
1. **Ресурсный оверхед (Resource Overhead)**: Каждый Sidecar требует минимум 64–128 МБ памяти и резервирует CPU. В кластере с 2000 подов это приводит к бессмысленной трате сотен гигабайт RAM на служебные процессы.
2. **Увеличение времени старта (Cold Start)**: В Kubernetes под не считается готовым (`Ready`), пока не поднимутся оба контейнера. При сбоях Envoy под может перезагружаться по циклу.
3. **Сложность CI/CD**: Необходимость синхронизировать версионирование образов приложения и Envoy.

Переход на **In-process gRPC-Web** (или фреймворк **ConnectRPC**) полностью устраняет потребность в Envoy для веб-доступа, сохраняя единый самодостаточный бинарный файл Go.

## Решение по шагам

1. Проанализируйте затраты ресурсов при использовании Sidecar vs In-process архитектуры.
2. Реализуйте в Go мониторинг потребления памяти и горутин в едином процессе.
3. Сравните задержки обработки запросов (Latency) с Envoy и без него.
4. Сформулируйте правила перехода на In-process архитектуру в enterprise-системах.

## Код решения

**`metrics_overhead.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func PrintMemoryStats() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("Выделено памяти (Alloc): %v MB | Всего получено от ОС (Sys): %v MB | Горутин: %d\n",
		m.Alloc/1024/1024, m.Sys/1024/1024, runtime.NumGoroutine())
}

func main() {
	fmt.Println("== Анализ потребления ресурсов In-process Go RPC сервиса ==")
	PrintMemoryStats()

	// Демонстрация: чистый Go процесс в покое занимает всего ~10-15 МБ RAM!
	// Envoy sidecar рядом потребовал бы дополнительные 80-120 МБ RAM.
	time.Sleep(100 * time.Millisecond)
}
```

# Сравнение инфраструктурных расходов: Sidecar vs In-process

| Метрика | Архитектура Envoy Sidecar | In-process (Go / Connect) |
| :--- | :--- | :--- |

## Под капотом

При вызове через Envoy запрос совершает два сетевых прыжка: `Браузер -> [Envoy] -> [Loopback TCP] -> [Go Server]`. Сетевой стек Linux вынужден дважды копировать сокетные буферы ядра (sk_buff) и дважды производить парсинг заголовков. В In-process архитектуре парсер gRPC-Web работает в том же адресном пространстве процесса Go, передавая байты напрямую через указатели памяти.

## Подводные камни

1. **Потеря централизованных фичей Envoy**: Отказываясь от Envoy, разработчики теряют готовые корпоративные фильтры (например, WAF ModSecurity или централизованный Rate-Limiter на Redis). Эти фичи придется реализовывать в виде Go Middleware.
2. **Сложность горячей перезагрузки**: Envoy умеет обновлять конфигурацию на лету через xDS API без рестарта процесса, тогда как изменение логики Go-сервера требует стандартного редеплоя пода.

## На собеседовании

В инфраструктурных интервью BigTech (VK, Яндекс, Ozon) часто поднимают вопрос оптимизации FinOps в облаках (Cloud Cost Optimization). Вопрос: 'Как снизить ежемесячный счет за Kubernetes кластер на 20% без уменьшения полезной бизнес-нагрузки?' Ответ: Провести аудит подов и устранить лишние sidecar-контейнеры (Envoy для простых gRPC-Web сервисов, замена на In-process или ConnectRPC), что высвободит тысячи гигабайт оперативной памяти и сотни ядер CPU.
