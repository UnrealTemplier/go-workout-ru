# GraphQL в сравнении с RPC: решение Over-fetching и Under-fetching на Go

## Условие

72. GraphQL

### Исходная формулировка

GraphQL

## Теория

**GraphQL** — декларативный язык запросов к данным, созданный Facebook для решения двух фундаментальных проблем REST в мобильных клиентах:
1. **Over-fetching (Избыточная выборка)**: REST возвращает весь объект пользователя со 100 полями (адреса, настройки, история), хотя мобильному экрану требуется только `name` и `avatar_url`.
2. **Under-fetching (Недостаточная выборка)**: Чтобы отобразить ленту, клиенту нужно сделать 10 последовательных вызовов (`/user`, `/posts`, `/comments`).

В GraphQL клиент в едином POST-запросе декларативно указывает вложенную схему требуемых полей:
`query { user(id: "1") { name, posts { title } } }`. Сервер возвращает ровно запрошенную структуру.

Однако за гибкость GraphQL приходится платить:
- Сложность кэширования (все запросы идут через HTTP POST).
- **N+1 проблема в базе данных** (резолвер постов дергает БД на каждого автора без батчинга через DataLoader).
- Высокий оверхед CPU на парсинг текста GraphQL-запроса и валидацию AST-дерева на каждый вызов (в отличие от скомпилированного бинарного Protobuf в gRPC/Connect).

## Решение по шагам

1. Сравните GraphQL схему и аналогичный Protobuf контракт.
2. Опишите принцип работы резолверов (Resolvers) в Go.
3. Продемонстрируйте проблему N+1 запросов к БД и ее устранение через паттерн DataLoader.
4. Сформулируйте архитектурные рекомендации выбора между GraphQL и gRPC/Connect.

## Код решения

**`graphql_schema.go`**

```go
package main

import (
	"context"
	"fmt"
)

// Модели предметной области
type User struct {
	ID   string
	Name string
}

type Order struct {
	ID     string
	UserID string
	Amount float64
}

// Резолвер GraphQL на Go
type Resolver struct{}

func (r *Resolver) User(ctx context.Context, id string) (*User, error) {
	// 1 запрос к БД: SELECT * FROM users WHERE id = $1
	fmt.Printf("[DB Query] Загрузка пользователя %s\n", id)
	return &User{ID: id, Name: "Мария"}, nil
}

func (r *Resolver) Orders(ctx context.Context, user *User) ([]*Order, error) {
	// N+1 проблема: если вызывается для 100 пользователей, породит 100 запросов!
	// Решается через DataLoader (батчинг по IN (id1, id2...))
	fmt.Printf("[DB Query] Загрузка заказов для пользователя %s\n", user.ID)
	return []*Order{
		{ID: "ord_1", UserID: user.ID, Amount: 1500.0},
		{ID: "ord_2", UserID: user.ID, Amount: 3200.0},
	}, nil
}

func main() {
	r := &Resolver{}
	u, _ := r.User(context.Background(), "usr_100")
	orders, _ := r.Orders(context.Background(), u)
	fmt.Printf("GraphQL резолвер собрал данные: Пользователь %s, Заказов: %d\n", u.Name, len(orders))
}
```

# Архитектурный выбор: GraphQL vs gRPC / Connect

| Критерий | GraphQL | Connect / gRPC |
| :--- | :--- | :--- |
| **Основная цель** | Гибкая агрегация данных на BFF для UI | Максимальная производительность и контракты |
| **Формат данных** | Текстовый JSON | Бинарный Protobuf / JSON |
| **Сложность бэкенда**| Высокая (AST парсинг, DataLoader, Depth Limit)| Низкая (прямой вызов сгенерированных методов) |
| **Кэширование** | Сложное (Client-side normalized cache) | Простое (HTTP GET / CDN кэширование) |
| **Безопасность** | Риск DoS через рекурсивные вложенные запросы | Строго ограниченная сигнатура метода |

## Под капотом

Парсинг запроса GraphQL требует построения синтаксического дерева (AST), его валидации по схеме типов и рекурсивного обхода резолверов. В бенчмарках Go (библиотеки `graphql-go` или `gqlgen`) затраты CPU на парсинг сложного запроса могут составлять до 70% всего времени обработки, тогда как в Protobuf/Connect десериализация выполняется напрямую через плоские байтовые сдвиги без динамического построения деревьев.

## Подводные камни

1. **Атака вложенностью (GraphQL Query Depth Attack)**: Без ограничения максимальной глубины (`DepthLimit = 7`) злоумышленник может отправить запрос `user { friends { friends { friends ... } } }`, вызвав 100% загрузку CPU сервера.
2. **Игнорирование DataLoader**: Запуск резолверов связей без батчинга превращает единичный HTTP-запрос в тысячи мелких запросов к базе данных PostgreSQL, перегружая пул соединений.

## На собеседовании

В мобильных приложениях Wildberries и Ozon миллионы пользователей заходят с нестабильного 3G/LTE. Вопрос: 'Почему в мобильных клиентах используется GraphQL/BFF, а не прямой доступ к десяткам микросервисов по gRPC?' Ответ: GraphQL на слое BFF собирает все необходимые для экрана данные за ОДИН сетевой round-trip по сотовой сети с минимальным размером payload (только запрошенные поля), экономя заряд аккумулятора смартфона.
