# Сравнительный анализ потоковых технологий: WebSockets vs SSE vs gRPC-Web vs Connect

## Условие

80. WebSockets

### Исходная формулировка

WebSockets

## Теория

Выбор технологии потоковой передачи данных от сервера к клиенту в веб-архитектуре требует четкого понимания сильных и слабых сторон протоколов:

1. **WebSockets (RFC 6455)**:
   - *Тип*: Полнодуплексный (Full-duplex) TCP-сокет.
   - *Плюсы*: Минимальная задержка, клиент и сервер могут слать данные в любой момент.
   - *Минусы*: Stateful протокол (сложно балансировать через стандартный L7 балансировщик), отсутствие встроенных контрактов, не использует HTTP/2 мультиплексирование.
2. **Server-Sent Events (SSE)**:
   - *Тип*: Однонаправленный стриминг (Server -> Client) поверх HTTP.
   - *Плюсы*: Нативная поддержка в браузерах (`EventSource`), автоматическое переподключение, текстовый формат, работает через любые HTTP прокси.
   - *Минусы*: Только от сервера к клиенту, только текстовые UTF-8 данные.
3. **gRPC-Web (Server Streaming)**:
   - *Тип*: Однонаправленный стрим Protobuf чанков.
   - *Плюсы*: Строгая типизация, кодогенерация из `.proto`.
   - *Минусы*: Требует Envoy, двунаправленный стриминг из браузера **не поддерживается**.
4. **Connect-Web Streaming**:
   - *Тип*: Современный стриминг поверх `fetch(ReadableStream)`.
   - *Плюсы*: Работает без Envoy, поддержка Protobuf и JSON, легковесный SDK.

## Решение по шагам

1. Составьте детальную матрицу потоковых протоколов.

```

   -> **Connect-Web** (строгие контракты Protobuf, zero-proxy архитектура).

   -> **gRPC-Web + Envoy**.
```

## Под капотом

В протоколе WebSocket балансировщик нагрузки (ALB, Nginx) вынужден держать постоянный stateful TCP-сокет на каждого клиента. Если у вас 1,000,000 активных пользователей мобильного приложения, балансировщик держит 1,000,000 открытых файловых дескрипторов. При использовании SSE или Connect поверх HTTP/2 сокеты мультиплексируются, а при отсутствии трафика соединения могут безопасно сбрасываться.

## Подводные камни

1. **Выбор WebSocket для простых push-уведомлений**: Избыточное усложнение инфраструктуры. Для доставки уведомлений от сервера достаточно простого SSE.
2. **Лимит HTTP/1.1 соединений браузера**: Браузер Chrome разрешает не более 6 одновременных HTTP/1.1 соединений на один домен. Если открыть 6 вкладок с SSE по HTTP/1.1, 7-я вкладка зависнет. Решение — обязательный запуск SSE/Connect поверх HTTP/2.

## На собеседовании

На System Design интервью в Тинькофф или Яндекс кандидату задают задачу: 'Спроектируйте систему доставки котировок 500,000 пользователей торгового терминала'. Кандидат должен аргументированно объяснить: 'Для стриминга котировок лучше использовать SSE или Connect Server Streaming, так как они stateless для балансировщиков и экономят ресурсы памяти, а отправку заявок на покупку делать обычными унарными RPC вызовами'.
