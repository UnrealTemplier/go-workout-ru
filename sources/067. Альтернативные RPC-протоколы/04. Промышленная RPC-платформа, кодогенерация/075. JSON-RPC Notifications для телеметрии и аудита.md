# JSON-RPC Notifications для телеметрии и аудита: архитектура с нулевым ожиданием

## Условие

75. **Notifications для fire-and-forget.**: Если response не нужен (telemetry, analytics), отправляйте без `id` field — сервер не будет тратить ресурсы на response.

### Исходная формулировка

**Notifications для fire-and-forget.**: Если response не нужен (telemetry, analytics), отправляйте без `id` field — сервер не будет тратить ресурсы на response.

## Теория

В современных enterprise-системах до 80% всех генерируемых событий — это аудит действий пользователей, сбор бизнес-метрик и телеметрия производительности. Использование синхронных запросов (`Request-Response`) для этих задач недопустимо, так как сетевой сбой в системе аудита не должен приводить к падению основной бизнес-транзакции покупки товара.

**JSON-RPC Notifications (сообщения без `id`)** — идеальный архитектурный примитив для fire-and-forget задач:
- Клиент отсылает данные в сокет и сразу продолжает работу без блокировки.
- Сервер не тратит CPU на маршалинг ответа и не удерживает сокет.
- Серверный обработчик сбрасывает нотификацию в кольцевой буфер памяти (RingBuffer / Channel) и передает воркерам записи в Kafka / ClickHouse.

## Решение по шагам

1. Спроектируйте структуру Notification-коллектора на Go.
2. Реализуйте неблокирующую отправку в кольцевой буфер через конструкцию `select-default`.
3. Настройте фоновый воркер с батчевым сбросом (Micro-batching) в аналитическое хранилище.
4. Добавьте сбор метрик количества отброшенных событий при переполнении буфера (Dropped Events Metric).

## Код решения

**`telemetry_collector.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"
)

type AuditEvent struct {
	UserID    string `json:"user_id"`
	Action    string `json:"action"`
	Timestamp int64  `json:"timestamp"`
}

type TelemetryCollector struct {
	buffer        chan AuditEvent
	droppedEvents atomic.Uint64
	totalEvents   atomic.Uint64
}

func NewTelemetryCollector(capacity int) *TelemetryCollector {
	tc := &TelemetryCollector{
		buffer: make(chan AuditEvent, capacity),
	}
	go tc.flusher()
	return tc
}

// Ingest Notification без блокировки клиента (Non-blocking ingest)
func (tc *TelemetryCollector) Ingest(event AuditEvent) {
	tc.totalEvents.Add(1)
	select {
	case tc.buffer <- event:
		// Успешно помещено в буфер
	default:
		// Буфер переполнен: отбрасываем событие ради сохранения стабильности сервиса (Load shedding)
		tc.droppedEvents.Add(1)
	}
}

// Фоновый воркер: агрегирует события и сбрасывает пачками (Micro-batching)
func (tc *TelemetryCollector) flusher() {
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()

	var batch []AuditEvent

	for {
		select {
		case ev := <-tc.buffer:
			batch = append(batch, ev)
			if len(batch) >= 100 {
				tc.flushToDB(batch)
				batch = nil
			}
		case <-ticker.C:
			if len(batch) > 0 {
				tc.flushToDB(batch)
				batch = nil
			}
		}
	}
}

func (tc *TelemetryCollector) flushToDB(batch []AuditEvent) {
	fmt.Printf("[ClickHouse Writer] Сброшен микро-батч из %d событий аудита\n", len(batch))
}

func main() {
	collector := NewTelemetryCollector(500)

	// Имитация потока нотификаций
	for i := 0; i < 250; i++ {
		collector.Ingest(AuditEvent{
			UserID:    fmt.Sprintf("user_%d", i),
			Action:    "click_banner",
			Timestamp: time.Now().Unix(),
		})
	}

	time.Sleep(300 * time.Millisecond)
	fmt.Printf("Всего событий: %d, Отброшено при перегрузке: %d\n",
		collector.totalEvents.Load(), collector.droppedEvents.Load())
}
```

ℹ️ Неблокирующий коллектор событий аудита с микро-батчингом и защитой от перегрузки

## Под капотом

Конструкция `select { case ch <- item: default: }` гарантирует, что время выполнения функции `Ingest` составляет несколько наносекунд независимо от нагрузки. Если буфер заполнен, выполнение не блокируется, предотвращая каскадную деградацию сервиса (Cascading Failure). Значение счетчика `droppedEvents` выводится в дашборд Prometheus, сигнализируя дежурным инженерам о необходимости масштабирования воркеров.

## Подводные камни

1. **Использование небуферизированных каналов**: Передача нотификаций в канал с нулевой емкостью мгновенно превращает fire-and-forget в синхронную блокировку.
2. **Скрытая потеря критических данных**: Отбрасывание финансовых транзакций недопустимо. Load shedding допустим ТОЛЬКО для некритичной телеметрии, метрик и аудита.

## На собеседовании

В рекламных движках (VK Реклама, Яндекс Директ) миллионы кликов и показов фиксируются через нотификации. На интервью задают вопрос: 'Что делать, если аналитическая база данных временно недоступна, а входящий поток нотификаций не прекращается?' Ответ: Использовать локальный Write-Ahead Log (WAL) на быстром NVMe-диске (например, BadgerDB или RocksDB) в качестве аварийного буфера до восстановления связи с центральным хранилищем.
