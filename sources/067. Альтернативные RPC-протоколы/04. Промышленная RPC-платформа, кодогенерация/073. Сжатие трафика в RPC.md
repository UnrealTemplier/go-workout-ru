### Исходная формулировка

**Компрессия.**: Настройте gzip на gRPC-Web proxy (Envoy) или через `grpc.UseCompressor(gzip.Name)` на сервере. Объясните, что gRPC-Web не поддерживает per-message compression negotiation как нативный gRPC (HTTP/2 SETTINGS), поэтому compression обычно на уровне HTTP (Content-Encoding).

## Теория

В высоконагруженных RPC-системах со сложными DTO (списки товаров, финансовые отчеты, геолокационные треки) размер передаваемого тела запроса может достигать сотен килобайт или мегабайт. Сжатие полезной нагрузки сокращает сетевой трафик в 3–10 раз и уменьшает сетевые задержки (RTT) при передаче между дата-центрами или клиентами.

Механизмы компрессии:
1. **gRPC Message Compression**: Сжатие происходит на уровне отдельных сообщений (флаг `0x01` в первом байте 5-байтного префикса gRPC-фрейма). Поддерживаются алгоритмы `gzip`, `snappy`, `zstd`.
2. **gRPC-Web / Envoy Compression**: Envoy сжимает весь HTTP/1.1 или HTTP/2 ответ целиком через стандартный заголовок `Content-Encoding: gzip`.
3. **ConnectRPC Compression**: Нативная поддержка сжатия запросов и ответов через опции `connect.WithSendGzip()` и автоматическое распознавание `Accept-Encoding`.

## Решение по шагам

1. Настройте компрессор gzip в Go-сервере Connect/gRPC.
2. Сконфигурируйте фильтр сжатия в Envoy (`envoy.filters.http.compressor`).
3. Реализуйте порог минимального размера сжатия (минимальный threshold, чтобы не сжимать сообщения меньше 1 КБ).
4. Протестируйте клиентский запрос с заголовком `Accept-Encoding: gzip` и проверьте сжатие ответа.

## Код решения

**`compression_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"strings"

	"connectrpc.com/connect"
)

type LargeDataReq struct {
	Count int `json:"count"`
}

type LargeDataResp struct {
	Payload string `json:"payload"`
}

type ReportServer struct{}

func (s *ReportServer) GetReport(
	ctx context.Context,
	req *connect.Request[LargeDataReq],
) (*connect.Response[LargeDataResp], error) {
	// Генерируем повторяющийся текст, который отлично сжимается алгоритмом gzip
	bigText := strings.Repeat("Отчет по транзакциям за финансовый квартал 2026. ", 1000)

	res := connect.NewResponse(&LargeDataResp{
		Payload: bigText,
	})
	// Connect автоматически применит gzip, если клиент передал Accept-Encoding: gzip
	return res, nil
}

func main() {
	mux := http.NewServeMux()
	// В реальном проекте: reportv1connect.NewReportServiceHandler(&ReportServer{})
	mux.HandleFunc("/report.v1.ReportService/GetReport", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		if strings.Contains(r.Header.Get("Accept-Encoding"), "gzip") {
			w.Header().Set("Content-Encoding", "gzip")
			// При использовании middleware / Connect сжатие применяется прозрачно
		}
		_, _ = w.Write([]byte(`{"payload":"Сжатые данные отчета..."}`))
	})

	fmt.Println("RPC Server with compression enabled on :8080")
}
```

**`envoy_gzip.yaml`**

```bash
# Настройка компрессии gzip в Envoy Proxy
http_filters:
- name: envoy.filters.http.compressor
  typed_config:
    "@type": type.googleapis.com/envoy.extensions.filters.http.compressor.v3.Compressor
    compressor_library:
      name: text_compressor
      typed_config:
        "@type": type.googleapis.com/envoy.extensions.compression.gzip.compressor.v3.Gzip
        memory_level: 8
        compression_level: DEFAULT_COMPRESSION
        compression_strategy: DEFAULT_STRATEGY
        window_bits: 15
    response_direction_config:
      common_config:
        min_content_length: 1024 # Сжимать ответы только от 1 КБ
        content_type:
        - application/grpc-web
        - application/grpc-web+proto
        - application/json
```

## Под капотом

Сжатие — это компромисс между задержкой CPU и шириной сетевого канала. Алгоритм `gzip` на высоком уровне компрессии (уровень 9) может замедлить отклик сервиса в 5 раз из-за высокой утилизации CPU. Для микросервисного обмена внутри одного ЦОД компрессию часто выключают либо используют сверхбыстрый алгоритм `zstd` (Zstandard) / `snappy`, обеспечивающий распаковку со скоростью гигабайт в секунду на ядро.

## Подводные камни

1. **Сжатие мелких сообщений (<500 байт)**: Пакеты размером менее 500 байт после сжатия gzip часто становятся БОЛЬШЕ исходного размера из-за накладных расходов заголовков gzip! Всегда настраивайте `min_content_length: 1024`.
2. **Двойная компрессия**: Сжатие уже сжатых данных (JPEG картинки, gzip архивы) только бесполезно сжигает CPU.

## На собеседовании

В глобальных распределенных системах (Яндекс Cloud, Cloudflare) межрегиональный трафик между DC стоит дорого. Вопрос: 'Как оптимизировать баланс между latency и CPU при передаче терабайтов RPC трафика?' Ответ: Внедрить алгоритм Zstandard (zstd) с адаптивным уровнем сжатия (level 1-3). Он дает степень сжатия лучше gzip при в 3-4 раза меньшей нагрузке на процессор.
