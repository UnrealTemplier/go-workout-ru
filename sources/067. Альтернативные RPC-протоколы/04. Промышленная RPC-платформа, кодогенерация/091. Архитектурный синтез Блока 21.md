## Теория

Успешное проектирование современных RPC-систем требует целостного понимания взаимодействия всех уровней сетевого и прикладного стека:
1. **L4 Транспорт**: TCP сокеты, TLS рукопожатия, ALPN согласование протоколов (`h2` vs `http/1.1`).
2. **L7 Мультиплексирование**: HTTP/2 фреймы (`HEADERS`, `DATA`, `SETTINGS`, `RST_STREAM`, `GOAWAY`), отсутствие Head-of-Line Blocking на уровне HTTP, разделение потоков по Stream ID.
3. **Сериализация**: Protocol Buffers wire format (Varints, Length-delimited, Fixed), строгие контракты и обратная совместимость.
4. **Браузерная среда**: CORS Preflight (`OPTIONS`), безопасность Origin, Fetch API limitations, кодирование трейлеров в тело потока.
5. **Прокси и шлюзы**: Envoy, In-process wrappers, ConnectRPC, терминация TLS и балансировка нагрузки.

Инженер, освоивший этот комплекс знаний, способен проектировать отказоустойчивые API любого масштаба.

## Решение по шагам

1. Систематизируйте полный путь RPC-запроса от клика в браузере до диска в базе данных.
2. Опишите точки возникновения потенциальных узких мест (Bottlenecks) на каждом уровне.
3. Разработайте чеклист аудита RPC-сервиса перед запуском в промышленную эксплуатацию.
4. Продемонстрируйте архитектурную схему взаимодействия компонентов.

```bash
# Production Readiness Checklist для Go RPC Сервисов

1. **Безопасность и сокеты**:
   - [ ] Настроены таймауты: `ReadTimeout`, `WriteTimeout`, `IdleTimeout`.
   - [ ] Включены Keepalive зонды с защитой `EnforcementPolicy.MinTime >= 5s`.
   - [ ] CORS заголовки содержат явный список `Access-Control-Expose-Headers`.

2. **Защита от перегрузок (Resilience)**:
   - [ ] Ограничен максимальный размер сообщения (`MaxRecvMsgSize <= 16MB`).
   - [ ] Внедрен Circuit Breaker и Rate Limiting на уровне шлюза.
   - [ ] Все горутины стриминга слушают `<-ctx.Done()`.

3. **Наблюдаемость (Observability)**:
   - [ ] Сквозной `traceparent` / `X-Request-ID` прокидывается через интерцепторы.
   - [ ] Экспортируются Prometheus метрики RPC длительности и статус-кодов.
   - [ ] Установлен Panic Recovery интерцептор во главе цепочки.

4. **Контракты и совместимость**:
   - [ ] Контракты валидируются в CI через `buf lint` и `buf breaking`.
   - [ ] Удаленные поля помечены как `reserved`.
```

## Под капотом

Сквозная оптимизация RPC-сервиса на Go позволяет достигать более 100,000 rps на одном среднем 8-ядерном сервере. Ключевые факторы успеха: переиспользование соединений клиентами (Persistent HTTP/2 Conn), исключение аллокаций памяти в куче через `sync.Pool`, строгий мониторинг GC паузы через `GODEBUG=gctrace=1` и отказ от тяжелых JSON-сериализаторов в пользу Protobuf.

## Подводные камни

1. **Преждевременная микрооптимизация ассемблером**: 99% проблем с производительностью лежат в архитектуре (лишние сетевые вызовы, N+1 запросы в БД, отсутствие пула соединений), а не в микросекундах работы Go-кода.
2. **Отсутствие L7 балансировки**: Запуск gRPC за L4 балансировщиком сводит на нет горизонтальное масштабирование сервиса.
