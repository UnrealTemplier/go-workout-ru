## Теория

Завершая главу, подведем итог практического применения каждого из изученных протоколов на основе реальных кейсов крупнейших технологических компаний мира:

1. **Google & Netflix (Классический gRPC)**:
   - Де-факто стандарт для всего внутреннего East-West трафика. Миллиарды RPC-вызовов в секунду между тысячами микросервисов.
2. **Ethereum, Solana & Crypto Exchanges (JSON-RPC 2.0)**:
   - Открытый стандарт для всех блокчейн-нод и криптокошельков (MetaMask, Geth). Пакетный batching позволяет за один запрос запросить баланс, подтвердить блок и отправить транзакцию.
3. **Uber & Figma (gRPC-Web & Envoy)**:
   - Использование gRPC-Web для сложнейших веб-приложений с передачей векторных данных и потоков координат такси на карты.
4. **Buf, Vercel & Modern BigTech (ConnectRPC)**:
   - Новое поколение API: отказ от громоздкого Envoy в пользу чистой архитектуры на Go с поддержкой браузеров из коробки.
5. **Twitter / X & Bloomberg (Server-Sent Events & WebSockets)**:
   - Real-time ленты новостей, финансовые котировки и биржевые стаканы с ультранизкой задержкой.

Выбор протокола — это всегда инженерный баланс между производительностью, скоростью разработки команд и простотой поддержки инфраструктуры.

## Решение по шагам

1. Составьте финальную сводную карту выбора архитектурных решений.
2. Реализуйте консольную утилиту, выводящую рекомендации по выбору протокола на основе параметров нагрузки и типов клиентов.
3. Сформулируйте ключевые выводы главы.
4. Запустите итоговый тест проверки знаний.

## Код решения

**`protocol_advisor.go`**

```go
package main

import (
	"fmt"
)

type Requirement struct {
	IsBrowserClient bool
	NeedsStreaming  bool
	HighThroughput  bool // > 10,000 RPS
	MultiLanguage   bool
	NeedsBatching   bool
}

func RecommendProtocol(req Requirement) string {
	if req.NeedsBatching && !req.HighThroughput {
		return "JSON-RPC 2.0 (Пакетные запросы из коробки)"
	}
	if req.IsBrowserClient {
		if req.NeedsStreaming {
			return "ConnectRPC (Server Streaming) или SSE"
		}
		return "ConnectRPC (Protobuf / JSON без необходимости Envoy)"
	}
	if req.HighThroughput || req.MultiLanguage {
		return "Классический gRPC (HTTP/2 + Protobuf)"
	}
	return "REST API (OpenAPI 3.0) — простота и общедоступность"
}

func main() {
	fmt.Println("=== BigTech Protocol Advisor ===")

	case1 := Requirement{IsBrowserClient: true, NeedsStreaming: true, MultiLanguage: true}
	fmt.Printf("Кейс 1 (Web SPA + Стриминг): %s\n", RecommendProtocol(case1))

	case2 := Requirement{IsBrowserClient: false, HighThroughput: true, MultiLanguage: true}
	fmt.Printf("Кейс 2 (Микросервисы HighLoad): %s\n", RecommendProtocol(case2))

	case3 := Requirement{NeedsBatching: true}
	fmt.Printf("Кейс 3 (Блокчейн / Пакетные вызовы): %s\n", RecommendProtocol(case3))
}
```

ℹ️ Экспертная система выбора RPC-протокола для корпоративной архитектуры

## Под капотом

В конечном счете все протоколы сводятся к байтам в TCP/QUIC сокетах операционной системы. Понимание абстракций над этими байтами — от фрейминга HTTP/2 до Varint-кодирования Protobuf и JSON парсеров — делает Go-разработчика архитектором, способным принимать осознанные технические решения с миллионной экономией для бизнеса.

## Подводные камни

1. **Догматизм (Golden Hammer)**: Попытка использовать один протокол (только REST или только gRPC) для абсолютно всех задач проекта.
2. **Игнорирование команды**: Выбор сложного gRPC стека в команде из двух junior-разработчиков без опыта работы с proto замедлит выпуск продукта в 3 раза.
