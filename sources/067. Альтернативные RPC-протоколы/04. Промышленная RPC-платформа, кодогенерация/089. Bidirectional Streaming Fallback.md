## Теория

В стандартном gRPC полнодуплексный двунаправленный стриминг (**Bidirectional Streaming**) работает нативно поверх HTTP/2. Однако в **веб-браузерах чистый gRPC-Web физически НЕ поддерживает Bidirectional Streaming**.

Причина: браузерный интерфейс `fetch()` не позволяет одновременно передавать исходящий стрим (`ReadableStream` в качестве тела `Request`) и параллельно считывать входящий поток ответа в рамках одного HTTP/1.1 или HTTP/2 соединения во всех браузерах.

Архитектурные стратегии Fallback для браузеров:
1. **WebSocket Transport Fallback (Паттерн Improbable)**:
   - Прокси или Go-бэкенд транслирует gRPC bidi-стрим поверх WebSocket соединения.
   - Браузер открывает сокет `ws://` и передает gRPC-Web фреймы в обе стороны.
2. **Twin-Channel Pattern (Раздельные каналы)**:
   - Клиент слушает входящие сообщения через **Server Streaming (gRPC-Web или SSE)**.
   - Исходящие сообщения клиент отправляет независимыми **унарными POST-запросами** с передачей `session_id`.

## Решение по шагам

1. Проанализируйте архитектуру паттерна Twin-Channel (Stream + Unary).
2. Создайте серверный диспетчер сессий с входящей очередью сообщений.
3. Реализуйте метод отправки сообщений в активную сессию клиента.
4. Продемонстрируйте корректное закрытие сессии и очистку памяти.

## Код решения

**`twin_channel_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type SessionHub struct {
	mu       sync.RWMutex
	sessions map[string]chan string
}

func NewSessionHub() *SessionHub {
	return &SessionHub{sessions: make(map[string]chan string)}
}

func (h *SessionHub) Open(sessionID string) chan string {
	h.mu.Lock()
	defer h.mu.Unlock()
	ch := make(chan string, 100)
	h.sessions[sessionID] = ch
	return ch
}

func (h *SessionHub) Close(sessionID string) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if ch, ok := h.sessions[sessionID]; ok {
		close(ch)
		delete(h.sessions, sessionID)
	}
}

func (h *SessionHub) PostMessage(sessionID, text string) bool {
	h.mu.RLock()
	ch, ok := h.sessions[sessionID]
	h.mu.RUnlock()
	if !ok {
		return false
	}
	select {
	case ch <- text:
		return true
	default:
		return false // Буфер переполнен
	}
}

// 1. Канал получения (Server Streaming)
func StreamDownlink(ctx context.Context, hub *SessionHub, sessionID string) {
	ch := hub.Open(sessionID)
	defer hub.Close(sessionID)

	fmt.Printf("[Downlink %s] Канал стриминга к браузеру открыт\n", sessionID)

	for {
		select {
		case <-ctx.Done():
			fmt.Printf("[Downlink %s] Клиент закрыл стрим\n", sessionID)
			return
		case msg, ok := <-ch:
			if !ok {
				return
			}
			fmt.Printf("[Downlink %s] Отправка чанка в браузер: %s\n", sessionID, msg)
		}
	}
}

// 2. Канал отправки (Unary POST)
func UnaryUplink(hub *SessionHub, sessionID, message string) error {
	if ok := hub.PostMessage(sessionID, message); !ok {
		return fmt.Errorf("сессия не найдена или перегружена")
	}
	fmt.Printf("[Uplink %s] Сообщение принято от браузера: %s\n", sessionID, message)
	return nil
}

func main() {
	hub := NewSessionHub()
	ctx, cancel := context.WithCancel(context.Background())

	go StreamDownlink(ctx, hub, "sess_100")
	time.Sleep(50 * time.Millisecond)

	_ = UnaryUplink(hub, "sess_100", "Привет из чата (сообщение 1)")
	_ = UnaryUplink(hub, "sess_100", "Как дела? (сообщение 2)")

	time.Sleep(100 * time.Millisecond)
	cancel()
	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Эмуляция двунаправленного стриминга через паттерн раздельных каналов (Twin-Channel)

## Под капотом

Паттерн Twin-Channel часто оказывается более устойчивым в мобильных сетях, чем чистый bidi-стриминг по сокету. При сбое сети отправка унарного POST автоматически повторяется клиентом по политике ретраев, а входящий Server-Stream переподключается с сохранением последнего прочитанного смещения (Offset), гарантируя семантику Exactly-Once доставки сообщений.

## Подводные камни

1. **Утечка брошенных сессий (Session Leaks)**: Если клиент аварийно закрыл браузер, не отправив команду завершения, канал сессии в `SessionHub` может остаться в памяти навсегда. Всегда используйте TTL и периодическую очистку неактивных сессий по таймауту.
2. **Рассинхронизация порядка сообщений**: Отправка параллельных унарных POST запросов может привести к нарушению очередности из-за гонок в сети. Используйте монотонные счетчики `sequence_id`.

## На собеседовании

В интерфейсах поддержки клиентов (Яндекс Go, Тинькофф Чат) критична стабильность диалога. Вопрос: 'Почему для мобильного чата используют раздельные каналы (SSE + HTTP POST) вместо единого WebSocket?' Ответ: WebSockets мгновенно рвутся при смене базовых станций 4G. Раздельные каналы позволяют прозрачно слать сообщения через стандартный HTTP пул с очередью в SQLite на смартфоне, обеспечивая работу даже в офлайн-режиме.
