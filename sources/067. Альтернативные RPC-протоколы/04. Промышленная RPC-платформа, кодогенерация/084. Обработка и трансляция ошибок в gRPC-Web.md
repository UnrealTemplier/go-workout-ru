# Обработка и трансляция ошибок в gRPC-Web: доставка NotFound и деталей в браузер

### Исходная формулировка

**Обработка ошибок gRPC-Web.**: Сервер возвращает статус `NotFound`. Убедитесь, что gRPC-Web клиент корректно получает код и сообщение ошибки (с учетом CORS, если необходимо).

## Теория

При возникновении ошибки на стороне gRPC-сервера (например, сущность не найдена -> `status.Error(codes.NotFound, "пользователь не найден")`), gRPC-Web прокси обязан корректно упаковать статус ошибки так, чтобы браузерный клиент смог:
1. Распознать ошибку не как фатальный сбой сети (Network Error), а как типизированное прикладное исключение.
2. Извлечь числовой код ошибки (`code: 5` для `NotFound`).
3. Получить человекочитаемое сообщение (`message`).
4. Распарсить структурированные детали ошибки (`google.rpc.Status`), переданные в поле `grpc-status-details-bin`.

В протоколе gRPC-Web при возникновении немедленной ошибки (Header-only response) сервер возвращает HTTP-заголовки `grpc-status: 5` и `grpc-message: ...` прямо в HTTP-ответе.

## Решение по шагам

1. Реализуйте Go gRPC метод, возвращающий ошибку `codes.NotFound`.
2. Добавьте структурированные детали ошибки через пакет `google.golang.org/genproto/googleapis/rpc/errdetails`.
3. Убедитесь, что прокси Envoy или In-process обертка передает заголовок `grpc-status`.
4. Напишите код браузерного клиента с перехватом ошибки и проверкой кода `RpcError.code === 5`.

## Код решения

**`error_producer.go`**

```go
package main

import (
	"context"
	"fmt"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

type UserRequest struct {
	ID string
}

type UserResponse struct {
	Name string
}

type UserManagementServer struct{}

func (s *UserManagementServer) GetUserProfile(ctx context.Context, req *UserRequest) (*UserResponse, error) {
	if req.ID != "usr_valid_42" {
		// Возвращаем стандартизированный gRPC статус NotFound
		return nil, status.Errorf(
			codes.NotFound,
			"пользователь с идентификатором '%s' не зарегистрирован в системе",
			req.ID,
		)
	}

	return &UserResponse{Name: "Иван Иванов"}, nil
}

func main() {
	srv := &UserManagementServer{}
	_, err := srv.GetUserProfile(context.Background(), &UserRequest{ID: "unknown_id"})
	if err != nil {
		st, _ := status.FromError(err)
		fmt.Printf("Сгенерирована gRPC ошибка: Код=%s (%d), Сообщение='%s'\n",
			st.Code(), int(st.Code()), st.Message())
	}
}
```

ℹ️ Генерация канонического gRPC статуса NotFound

**`browser_error_handler.ts`**

```bash
// Браузерный клиент gRPC-Web (TypeScript)
import { StatusCode } from 'grpc-web';

client.getUserProfile(request, {}, (err, response) => {
  if (err) {
    // Проверка канонического кода ошибки
    if (err.code === StatusCode.NOT_FOUND) {
      console.warn("Сущность не найдена:", err.message);
      showNotFoundModal(err.message);
    } else if (err.code === StatusCode.UNAUTHENTICATED) {
      console.error("Требуется авторизация");
      redirectToLogin();
    } else {
      console.error(`Непредвиденная ошибка (${err.code}):`, err.message);
    }
    return;
  }

  console.log("Успешный ответ:", response.getName());
});
```

## Под капотом

Если gRPC метод завершается ошибкой сразу (до отправки каких-либо сообщений), сервер может отправить так называемый 'Trailers-only' ответ. В HTTP/2 это один набор заголовков с флагом `END_STREAM`. В gRPC-Web прокси упаковывает этот набор заголовков либо в HTTP заголовки ответа (если статус возвращается сразу), либо в финальный трейлер-фрейм (`0x80`). Заголовок `Access-Control-Expose-Headers: grpc-status, grpc-message` критически необходим, иначе браузерный JS получит пустой объект ошибки из-за CORS-ограничений!

## Подводные камни

1. **Пропуск CORS экспонирования `grpc-status`**: Самая частая проблема: в Network табе браузера виден заголовок `grpc-status: 5`, но в коде `err.code` равен `undefined`. Причина: бэкенд не добавил `Access-Control-Expose-Headers: grpc-status, grpc-message`.
2. **Использование не-ASCII символов в `grpc-message`**: Текст ошибки в `grpc-message` должен быть URL-encoded (Percent-encoding), если содержит русские буквы, иначе HTTP-парсеры прокси могут отклонить заголовок.

## На собеседовании

В финтех-приложениях (Тинькофф, Сбер) ошибки бизнес-логики должны детально объяснять клиенту причину отказа. Вопрос: 'Как передать ошибку с несколькими причинами (например, неверный CVC и просрочен срок карты) через gRPC-Web?' Ответ: Использовать `status.WithDetails()` с Protobuf-сообщением `errdetails.BadRequest`. На клиенте извлечь бинарный заголовок `grpc-status-details-bin`, декодировать его из Base64 и десериализовать в сгенерированный Protobuf-класс.
