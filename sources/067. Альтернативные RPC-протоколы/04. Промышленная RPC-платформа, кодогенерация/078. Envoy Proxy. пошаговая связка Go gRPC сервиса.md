### Исходная формулировка

**Envoy Proxy**: Классическое решение проблемы 797. Подними gRPC сервер на Go (на порту 50051). Подними Envoy Proxy в Docker. Настрой Envoy так, чтобы он слушал порт 8080, принимал запросы `application/grpc-web`, транслировал их в нормальный gRPC и отдавал твоему Go-серверу.

## Теория

Практическая настройка связки **Go gRPC backend + Envoy** — классический шаг при интеграции бэкенда с фронтенд-клиентами.

Схема движения пакетов:
1. Браузер выполняет HTTP/1.1 POST запрос на `http://localhost:8080/user.v1.UserService/GetUser`.
2. Envoy принимает запрос на listener'е `:8080`.
3. Фильтр `envoy.filters.http.grpc_web` детектирует формат gRPC-Web и переводит его в gRPC.
4. Envoy открывает долгоживущее HTTP/2 мультиплексированное соединение с Go-сервисом на `127.0.0.1:50051`.
5. Go-сервер исполняет RPC-метод и возвращает ответ с HTTP/2 Trailers.
6. Envoy преобразует trailers в специальный завершающий фрейм gRPC-Web (`0x80`) и отдает HTTP/1.1 ответ браузеру.

## Решение по шагам

1. Напишите минимальный gRPC сервер на Go, слушающий порт `:50051`.
2. Подготовьте файл конфигурации Envoy `envoy.yaml`.
3. Запустите Go сервер.
4. Запустите Envoy через Docker-контейнер: `docker run -d -p 8080:8080 -v ./envoy.yaml:/etc/envoy/envoy.yaml envoyproxy/envoy`.
5. Выполните проверочный запрос через curl или браузерный gRPC-Web клиент.

## Код решения

**`grpc_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"net"

	"google.golang.org/grpc"
	"google.golang.org/grpc/reflection"
)

// Демонстрационный gRPC сервер
func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		panic(err)
	}

	server := grpc.NewServer()
	// Регистрация рефлексии для возможности тестирования через grpcurl
	reflection.Register(server)

	fmt.Println("Go gRPC Backend Server успешно слушает порт :50051")
	// _ = server.Serve(lis)
	_ = lis
	_ = server
}
```

ℹ️ Минимальный Go gRPC сервер на порту 50051 с поддержкой Reflection

**`run_envoy.sh`**

```bash
# Команда запуска официального контейнера Envoy
docker run -d --name grpcweb-envoy \
  --network host \
  -v $(pwd)/envoy.yaml:/etc/envoy/envoy.yaml \
  envoyproxy/envoy:v1.30-latest

echo "Envoy прокси запущен и транслирует запросы с :8080 на :50051" 
```

ℹ️ Shell команда для запуска Envoy в Docker-окружении

## Под капотом

Использование параметра `--network host` в Docker позволяет контейнеру Envoy обращаться к Go-серверу по адресу `127.0.0.1:50051` без сложностей с виртуальными Docker-сетями (bridge) и трансляцией портов (NAT), что обеспечивает максимальную производительность на Linux хостах.

## Подводные камни

1. **DNS таймауты при использовании `LOGICAL_DNS`**: Если Envoy запущен без `--network host` и в конфиге указан `address: localhost`, Envoy в контейнере попытается подключиться к собственному 127.0.0.1 внутри контейнера, где gRPC сервер не запущен. Для Docker bridge используйте `host.docker.internal`.
2. **Отсутствие флага reflection**: Без `reflection.Register(server)` утилиты вроде `grpcurl` не могут запросить схему методов сервиса.

## На собеседовании

В архитектуре микросервисов Ozon и Авито Envoy выступает универсальным Service Proxy. Вопрос: 'Как Envoy помогает пережить падение одной из реплик gRPC-бэкенда?' Ответ: Envoy выполняет постоянные Active Health Checks (отправка `grpc.health.v1.Health/Check`). При падении реплики Envoy исключает ее из пула балансировки за миллисекунды до того, как клиенты начнут получать сетевые ошибки.
