# CORS и Preflight запросы в gRPC-Web: специфика заголовков и каверзные кейсы

## Условие

88. **[Каверзный кейс — CORS и Preflight]**: Браузеры перед gRPC-Web запросом отправляют `OPTIONS` preflight-запрос. Напиши middleware, которое перехватывает `OPTIONS`, проверяет заголовок `Origin` и возвращает `Access-Control-Allow-Origin`, `Access-Control-Allow-Headers: content-type, x-grpc-web` и `Access-Control-Allow-Methods: POST`. Без этого gRPC-Web из браузера работать не будет.

### Исходная формулировка

**[Каверзный кейс — CORS и Preflight]**: Браузеры перед gRPC-Web запросом отправляют `OPTIONS` preflight-запрос. Напиши middleware, которое перехватывает `OPTIONS`, проверяет заголовок `Origin` и возвращает `Access-Control-Allow-Origin`, `Access-Control-Allow-Headers: content-type, x-grpc-web` и `Access-Control-Allow-Methods: POST`. Без этого gRPC-Web из браузера работать не будет.

## Теория

При обращении браузера к gRPC-Web сервису, расположенному на другом домене или порту (Cross-Origin Resource Sharing), браузер перед основным POST-запросом автоматически инициирует предварительный **Preflight `OPTIONS`** запрос.

Специфика CORS в gRPC-Web:
1. Запрос gRPC-Web содержит нестандартные заголовки: `x-grpc-web`, `x-user-agent`, `content-type: application/grpc-web+proto`.
2. Браузер отправляет `OPTIONS` с `Access-Control-Request-Headers: x-grpc-web, content-type`.
3. Сервер или Envoy прокси **ОБЯЗАН** вернуть HTTP 200/204 с:
   - `Access-Control-Allow-Origin: <origin>`
   - `Access-Control-Allow-Methods: POST, OPTIONS`
   - `Access-Control-Allow-Headers: keep-alive, user-agent, cache-control, content-type, content-transfer-encoding, x-accept-content-transfer-encoding, x-accept-response-streaming, x-user-agent, x-grpc-web`
   - **`Access-Control-Expose-Headers: grpc-status, grpc-message`**: Без этого браузер не сможет прочитать трейлеры!
   - `Access-Control-Max-Age: 1728000`: Кэширование preflight-ответа на 20 дней для исключения задержек на повторные OPTIONS.

## Решение по шагам

1. Реализуйте в Go надежное CORS Middleware с полным набором заголовков gRPC-Web.
2. Обработайте метод HTTP `OPTIONS` с немедленным возвратом 200 OK.
3. Проверьте обязательное наличие `Access-Control-Expose-Headers`.
4. Протестируйте Preflight запрос через curl с флагами CORS.

## Код решения

**`cors_middleware.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"strings"
)

// GRPCWebCORSMiddleware обеспечивает 100% совместимость с браузерными gRPC-Web клиентами
func GRPCWebCORSMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		origin := r.Header.Get("Origin")
		if origin != "" {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Credentials", "true")
			w.Header().Set("Access-Control-Allow-Methods", "POST, GET, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", strings.Join([]string{
				"keep-alive",
				"user-agent",
				"cache-control",
				"content-type",
				"content-transfer-encoding",
				"x-accept-content-transfer-encoding",
				"x-accept-response-streaming",
				"x-user-agent",
				"x-grpc-web",
				"authorization",
			}, ", "))

			// Критически важный заголовок: без него JS не видит статус ответа gRPC!
			w.Header().Set("Access-Control-Expose-Headers", "grpc-status, grpc-message, grpc-status-details-bin")
			w.Header().Set("Access-Control-Max-Age", "86400") // Кэш Preflight на 24 часа
		}

		// Браузерный Preflight запрос
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusOK)
			return
		}

		next.ServeHTTP(w, r)
	})
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/user.v1.UserService/Ping", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/grpc-web+proto")
		w.Header().Set("grpc-status", "0")
		_, _ = w.Write([]byte("OK"))
	})

	handler := GRPCWebCORSMiddleware(mux)
	fmt.Println("gRPC-Web CORS Server готов к работе на :8080")
	_ = handler
}
```

## Под капотом

Если заголовок `Access-Control-Expose-Headers` не содержит `grpc-status`, браузерный движок (V8/Blink) из соображений безопасности скрывает этот HTTP-заголовок от JavaScript-песочницы. gRPC-Web клиент в браузере видит пустой ответ и выбрасывает ошибку `Http response at 400 or 500 level, but no grpc-status header found`, вводя разработчика в заблуждение.

## Подводные камни

1. **Wildcard `*` при `Allow-Credentials: true`**: Браузер заблокирует запрос, если указать `Access-Control-Allow-Origin: *` вместе с авторизационными куками. Нужно возвращать конкретный отраженный `Origin` клиента.
2. **Отсутствие `Access-Control-Max-Age`**: Без кэширования Preflight каждый RPC-запрос из браузера превращается в два сетевых запроса (`OPTIONS` + `POST`), удваивая нагрузку на инфраструктуру.

## На собеседовании

В микрофронтендах (Micro-frontends) Wildberries или Avito десятки виджетов обращаются к разным поддоменам API. Вопрос: 'Почему после деплоя нового сервиса весь фронтенд падает с CORS error, хотя в Postman запросы проходят идеально?' Ответ: Postman не является браузером и полностью игнорирует CORS. Ошибка вызвана отсутствием одного из кастомных заголовков в `Access-Control-Allow-Headers` на Envoy/бэкенде.
