# Batch Support в JSON-RPC: решение проблемы N+1 и атомарность пакетных транзакций

## Условие

74. **Batch support — ключевая фича.**: Один HTTP request может нести 100 RPC calls. Это решает N+1 проблему и снижает latency.

### Исходная формулировка

**Batch support — ключевая фича.**: Один HTTP request может нести 100 RPC calls. Это решает N+1 проблему и снижает latency.

## Теория

Пакетные вызовы (Batching) в JSON-RPC 2.0 превращают протокол в мощный инструмент для высоконагруженных систем, решая проблему сетевых задержек (Latency) и исчерпания пула соединений.

Два режима выполнения батчей в архитектуре:
1. **Independent Parallel Execution (По умолчанию)**:
   - Все запросы в батче независимы.
   - Выполняются параллельно в горутинах.
   - Ошибка одного вызова не влияет на остальные (ответ содержит микс из успешных `result` и ошибочных `error`).
2. **Transactional Atomic Batch (Enterprise расширение)**:
   - Запросы должны выполниться в рамках единой транзакции БД (`BEGIN ... COMMIT`).
   - Если ХОТЯ БЫ ОДИН метод завершился ошибкой — транзакция откатывается (`ROLLBACK`), и все операции помечаются как отмененные.

В Go реализация требует четкого разделения логики диспетчеризации и координации транзакций.

## Решение по шагам

1. Реализуйте структуру транзакционного пакетного процессора.
2. Проверьте валидность всех методов и параметров перед запуском.
3. Откройте транзакцию в БД или эмулируемом хранилище.
4. Выполните методы по цепочке. При первой ошибке откатите состояние.
5. Сформируйте корректный массив ответов JSON-RPC.

## Код решения

**`atomic_batch.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
)

type SubRequest struct {
	Method string          `json:"method"`
	Params json.RawMessage `json:"params"`
	ID     int             `json:"id"`
}

type SubResponse struct {
	JSONRPC string `json:"jsonrpc"`
	Result  any    `json:"result,omitempty"`
	Error   any    `json:"error,omitempty"`
	ID      int    `json:"id"`
}

type AccountState struct {
	Balance float64
}

// ExecuteAtomicBatch эмулирует выполнение батча в рамках транзакции
func ExecuteAtomicBatch(reqs []SubRequest, initialBalance float64) ([]SubResponse, error) {
	// Snapshot состояния для возможности отката (Rollback)
	tempBalance := initialBalance
	responses := make([]SubResponse, len(reqs))

	for i, req := range reqs {
		switch req.Method {
		case "credit":
			var amount float64
			_ = json.Unmarshal(req.Params, &amount)
			tempBalance += amount
			responses[i] = SubResponse{JSONRPC: "2.0", Result: map[string]float64{"new_balance": tempBalance}, ID: req.ID}
		case "debit":
			var amount float64
			_ = json.Unmarshal(req.Params, &amount)
			if tempBalance < amount {
				// Ошибка валидации транзакции: недостаток средств -> ROLLBACK!
				return nil, fmt.Errorf("транзакция прервана на шаге id=%d: недостаточно средств (баланс: %v, запрошено: %v)", req.ID, tempBalance, amount)
			}
			tempBalance -= amount
			responses[i] = SubResponse{JSONRPC: "2.0", Result: map[string]float64{"new_balance": tempBalance}, ID: req.ID}
		default:
			return nil, fmt.Errorf("неизвестный метод: %s", req.Method)
		}
	}

	// Коммит успешной транзакции
	fmt.Printf("Транзакция успешно закоммичена. Итоговый баланс: %v\n", tempBalance)
	return responses, nil
}

func main() {
	batch := []SubRequest{
		{Method: "credit", Params: json.RawMessage(`1000.0`), ID: 1},
		{Method: "debit", Params: json.RawMessage(`300.0`), ID: 2},
		{Method: "debit", Params: json.RawMessage(`2000.0`), ID: 3}, // Вызовет ошибку!
	}

	resps, err := ExecuteAtomicBatch(batch, 500.0)
	if err != nil {
		fmt.Printf("Откат пакета операций: %v\n", err)
	} else {
		fmt.Printf("Ответы: %v\n", resps)
	}
}
```

ℹ️ Транзакционное исполнение пакетных вызовов с гарантией Rollback

## Под капотом

В распределенных системах батчинг сокращает число обращений к системному вызову `epoll_wait` и сетевому стеку Linux. Обработка одного запроса с 100 операциями требует одного контекстного переключения (context switch) ядра, тогда как 100 отдельных HTTP-запросов заставляют ядро Linux 100 раз парсить TCP-пакеты и производить TLS-дешифрование.

## Подводные камни

1. **Голодание горутин при гигантских батчах**: Если один клиент присылает батч на 5,000 методов, параллельный запуск 5,000 горутин может монополизировать планировщик Go. Используйте воркер-пул с фиксированным числом воркеров (Worker Pool).
2. **Смешивание идемпотентных и неидемпотентных операций**: Повтор сбойного батча целиком может привести к дублированию платежей, если клиент не использует единый идемпотентный ключ.

## На собеседовании

В платежных шлюзах (QIWI, ЮKassa, Тинькофф) мерчанты отправляют реестры массовых выплат сотрудникам через Batch JSON-RPC. Вопрос: 'Как обрабатывать батч из 10,000 выплат при лимите времени HTTP-запроса в 30 секунд?' Ответ: Принять батч, сгенерировать `batch_id`, сохранить в PostgreSQL/Kafka со статусом `PROCESSING`, немедленно вернуть клиенту `batch_id` (HTTP 202), а результат отдавать через опрос статуса или вебхук.
