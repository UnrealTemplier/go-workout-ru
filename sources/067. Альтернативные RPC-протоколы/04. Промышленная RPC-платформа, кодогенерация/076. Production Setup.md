## Теория

В промышленной эксплуатации Envoy Proxy развертывается либо как **Ingress Gateway** (единая точка входа в кластер для фронтенда), либо как **Sidecar-контейнер** внутри Kubernetes Pod рядом с Go-микросервисом.

Ключевые production-настройки Envoy для gRPC-Web:
1. **Upstream HTTP/2 Protocol**: В секции кластера обязательна директива `typed_extension_protocol_options` с указанием `Http2ProtocolOptions`, иначе Envoy пошлет HTTP/1.1 запрос в gRPC сервер.
2. **Circuit Breaking и Connection Pooling**: Ограничение максимального числа одновременных запросов (`max_connections`, `max_pending_requests`) для защиты Go-сервера от шторма запросов.
3. **CORS Preflight**: Настройка перехвата и мгновенного ответа на HTTP `OPTIONS` браузера без пересылки в бэкенд.
4. **Access Logging**: Логирование `grpc-status`, времени задержки бэкенда и заголовков трассировки.

## Решение по шагам

1. Изучите Kubernetes манифест Deployment с Sidecar контейнером Envoy.
2. Настройте ConfigMap с production-конфигурацией Envoy.
3. Сконфигурируйте фильтры `grpc_web`, `cors` и `router`.
4. Настройте Health Check эндпоинт `/ready` для Kubernetes liveness/readiness проб.

## Код решения

**`k8s_deployment.yaml`**

```bash
apiVersion: apps/v1
kind: Deployment
metadata:
  name: billing-service
  labels:
    app: billing-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: billing-service
  template:
    metadata:
      labels:
        app: billing-service
    spec:
      containers:
      # 1. Основной Go gRPC сервис (порт 50051)
      - name: backend
        image: cr.mycorp.ru/billing:v1.4.2
        ports:
        - containerPort: 50051
        resources:
          limits: { cpu: "2", memory: "1Gi" }
          requests: { cpu: "200m", memory: "256Mi" }

      # 2. Sidecar контейнер Envoy Proxy (порт 8080 для gRPC-Web)
      - name: envoy-proxy
        image: envoyproxy/envoy:v1.30.1
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: envoy-config-vol
          mountPath: /etc/envoy
        resources:
          limits: { cpu: "500m", memory: "256Mi" }
          requests: { cpu: "100m", memory: "64Mi" }

      volumes:
      - name: envoy-config-vol
        configMap:
          name: envoy-grpc-web-config
```

**`envoy_prod_cluster.yaml`**

```bash
# Кластер бэкенда с HTTP/2 протоколом и защитой Circuit Breaker
clusters:
- name: grpc_backend_local
  type: STATIC
  connect_timeout: 0.25s
  lb_policy: ROUND_ROBIN
  typed_extension_protocol_options:
    envoy.extensions.upstreams.http.v3.HttpProtocolOptions:
      "@type": type.googleapis.com/envoy.extensions.upstreams.http.v3.HttpProtocolOptions
      explicit_http_config:
        http2_protocol_options: {}
  circuit_breakers:
    thresholds:
    - priority: DEFAULT
      max_connections: 1024
      max_pending_requests: 100
      max_requests: 4096
  load_assignment:
    cluster_name: grpc_backend_local
    endpoints:
    - lb_endpoints:
      - endpoint:
          address:
            socket_address: { address: 127.0.0.1, port_value: 50051 }
```

ℹ️ Спецификация Envoy Upstream Cluster с включением HTTP/2 и пула соединений

## Под капотом

Внутри одного Kubernetes Pod контейнеры делят общий сетевой namespace (`Network Namespace`). Поэтому Envoy обращается к Go-сервису через локальный интерфейс `127.0.0.1:50051`. Это исключает межсетевые задержки и накладные расходы на шифрование между прокси и бэкендом (mTLS терминация происходит на Envoy).

## Подводные камни

1. **Забытый localhost binding в Go**: Если Go-сервер слушает только IP-адрес интерфейса пода, а не `0.0.0.0` или `127.0.0.1`, Envoy не сможет установить локальный TCP-сокет.
2. **Лимиты памяти Envoy**: При активном стриминге тысяч клиентов Envoy может потреблять больше памяти, чем выделено в `resources.limits.memory`, что приведет к OOMKilled контейнера-прокси.

## На собеседовании

На собеседовании по Kubernetes в Ozon или Lamoda: 'Почему в высоконагруженных проектах часто отказываются от Sidecar Envoy в пользу единого Ingress Envoy Gateway?' Ответ: 1000 подов со sidecar-контейнерами требуют 1000 отдельных копий Envoy, сжигая десятки гигабайт памяти нод на служебные процессы. Централизованный Ingress Gateway снижает расход ресурсов и упрощает централизованное управление сертификатами TLS.
