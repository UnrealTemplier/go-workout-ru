# Поддержка позиционных и именованных параметров (Positional vs Named Params)

## Условие

11. **Параметры по имени и по позиции.**: Поддержите оба варианта: `"params": ["hello"]` и `"params": {"text": "hello"}`. Используйте рефлексию для вызова обработчиков.

### Исходная формулировка

**Параметры по имени и по позиции.**: Поддержите оба варианта: `"params": ["hello"]` и `"params": {"text": "hello"}`. Используйте рефлексию для вызова обработчиков.

## Теория

Спецификация JSON-RPC 2.0 допускает два взаимоисключающих формата передачи параметров:
1. **Позиционные параметры (By-Position):**
   `"params": ["Alex", 25]`
   Параметры передаются в виде JSON-массива. Порядок элементов строго фиксирован.
2. **Именованные параметры (By-Name):**
   `"params": {"name": "Alex", "age": 25}`
   Параметры передаются в виде JSON-объекта. Порядок ключей не имеет значения.

Для поддержки обоих форматов сервер анализирует первый байт `params`:
- Если `params[0] == '['`: десериализация выполняется в срез аргументов.
- Если `params[0] == '{'`: десериализация выполняется в структуру или карту.

## Решение по шагам

1. Создайте структуру запроса с `params json.RawMessage`.
2. Реализуйте проверку формата параметров через первый значащий символ.
3. Распакуйте позиционные параметры в срез, а именованные — в целевую структуру.
4. Вызовите бизнес-логику с полученными значениями.

## Код решения

**`params_adapter.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
)

type UserArgs struct {
	Username string `json:"username"`
	Age      int    `json:"age"`
}

func parseUserArgs(raw json.RawMessage) (*UserArgs, error) {
	trimmed := bytes.TrimSpace(raw)
	if len(trimmed) == 0 {
		return nil, errors.New("missing params")
	}

	args := &UserArgs{}

	if trimmed[0] == '{' {
		// Именованные параметры: {"username": "Ivan", "age": 30}
		if err := json.Unmarshal(trimmed, args); err != nil {
			return nil, err
		}
		return args, nil
	} else if trimmed[0] == '[' {
		// Позиционные параметры: ["Ivan", 30]
		var tuple []any
		if err := json.Unmarshal(trimmed, &tuple); err != nil {
			return nil, err
		}
		if len(tuple) < 2 {
			return nil, errors.New("expected 2 positional parameters")
		}
		name, ok1 := tuple[0].(string)
		ageFloat, ok2 := tuple[1].(float64)
		if !ok1 || !ok2 {
			return nil, errors.New("invalid parameter types in array")
		}
		args.Username = name
		args.Age = int(ageFloat)
		return args, nil
	}

	return nil, errors.New("params must be either object or array")
}

func paramsHandler(w http.ResponseWriter, r *http.Request) {
	var req struct {
		JSONRPC string          `json:"jsonrpc"`
		Method  string          `json:"method"`
		Params  json.RawMessage `json:"params"`
		ID      any             `json:"id"`
	}

	_ = json.NewDecoder(r.Body).Decode(&req)

	args, err := parseUserArgs(req.Params)
	w.Header().Set("Content-Type", "application/json")

	if err != nil {
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32602, "message": err.Error()},
			"id":      req.ID,
		})
		return
	}

	_ = json.NewEncoder(w).Encode(map[string]any{
		"jsonrpc": "2.0",
		"result":  fmt.Sprintf("User registered: %s (age %d)", args.Username, args.Age),
		"id":      req.ID,
	})
}

func main() {
	http.HandleFunc("/rpc/user", paramsHandler)
	fmt.Println("Dual params server listening on :8080/rpc/user")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Поддержка позиционных массивов и именованных JSON-объектов в параметрах

## Под капотом

В JSON все числа парсятся в `float64`, если целевой тип `any`. При распаковке позиционных параметров в срез `[]any` целые числа становятся числами с плавающей точкой, требуя явного приведения `int(ageFloat)`. При распаковке в типизированную структуру `json.Unmarshal` делает это преобразование автоматически.

## Подводные камни

Передача примитивных типов (`"params": "hello"` или `"params": 42`). Спецификация JSON-RPC 2.0 категорически запрещает передавать примитивы в поле `params`: допустимы исключительно `Structured values` (Array или Object). Любой другой тип должен немедленно возвращать ошибку `Invalid params (-32602)`.

## На собеседовании

В Яндекс и Ozon любят спрашивать: 'Какой тип параметров предпочтительнее в production: By-Name или By-Position?' Ответ: By-Name (именованный объект). Он обеспечивает обратную совместимость API: новые поля могут добавляться со значениями по умолчанию без поломки старых клиентов, тогда как в By-Position любое изменение порядка параметров ломает клиентов.
