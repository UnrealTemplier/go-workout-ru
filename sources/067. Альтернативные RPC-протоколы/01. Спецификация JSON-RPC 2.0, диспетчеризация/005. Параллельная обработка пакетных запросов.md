# Параллельная обработка пакетных запросов (Batch Requests)

## Условие

5. **Batch Requests.**: Реализуйте обработку массива запросов: `[]Request`. Выполняйте параллельно (goroutine per request), сохраняйте порядок `id` в ответе. Обработайте partial failure: если один запрос вернул ошибку, остальные должны выполниться нормально.

### Исходная формулировка

**Batch Requests.**: Реализуйте обработку массива запросов: `[]Request`. Выполняйте параллельно (goroutine per request), сохраняйте порядок `id` в ответе. Обработайте partial failure: если один запрос падает, остальные возвращают результат. Объясните, почему пустой batch (`[]`) — ошибка `-32600`.

## Теория

Пакетный режим (Batch Requests) — одна из мощнейших возможностей JSON-RPC 2.0:
- Клиент передает в теле одного HTTP POST запроса массив объектов: `[ {...}, {...}, {...} ]`.
- Это радикально снижает оверхед на сетевые RTT и заголовки HTTP/TLS.

Требования к параллельной пакетной обработке:
1. **Изоляция сбоев (Partial Failure):** Ошибка в одном вызове (например, неверные параметры) не должна прерывать выполнение остальных валидных запросов пакета.
2. **Параллельное исполнение:** Сервер запускает обработку каждого элемента массива в отдельной горутине через пул воркеров или `sync.WaitGroup`.
3. **Игнорирование Notifications:** Уведомления без `id` внутри пакета выполняются, но в выходной массив ответов не включаются.
4. **Массив в ответе:** Ответ должен быть JSON-массивом `[]Response`. Если все запросы в батче были уведомлениями, сервер не возвращает тело вообще.

## Решение по шагам

1. Создайте структуру одиночного запроса и ответа.
2. Реализуйте функцию `executeBatch(ctx, requests)` с запуском горутин через `sync.WaitGroup`.
3. Для сохранения порядка результатов инициализируйте срез ответов фиксированной длины `responses = make([]*Response, len(requests))`.
4. Отфильтруйте `nil` элементы (уведомления) перед финальной сериализацией.
5. Верните итоговый массив клиенту.

## Код решения

**`batch_server.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"sync"
	"time"
)

type RPCReq struct {
	JSONRPC string          `json:"jsonrpc"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params,omitempty"`
	ID      any             `json:"id,omitempty"`
}

type RPCResp struct {
	JSONRPC string `json:"jsonrpc"`
	Result  any    `json:"result,omitempty"`
	Error   *RPCError `json:"error,omitempty"`
	ID      any    `json:"id"`
}

func executeSingle(ctx context.Context, req RPCReq) *RPCResp {
	// Имитация полезной работы
	if req.Method == "sleep" {
		time.Sleep(50 * time.Millisecond)
		return &RPCResp{JSONRPC: "2.0", Result: "done", ID: req.ID}
	}
	if req.Method == "fail" {
		return &RPCResp{
			JSONRPC: "2.0",
			Error:   &RPCError{Code: -32000, Message: "Business logic error"},
			ID:      req.ID,
		}
	}
	return &RPCResp{
		JSONRPC: "2.0",
		Result:  fmt.Sprintf("Result for %s", req.Method),
		ID:      req.ID,
	}
}

func batchHandler(w http.ResponseWriter, r *http.Request) {
	var requests []RPCReq
	if err := json.NewDecoder(r.Body).Decode(&requests); err != nil {
		http.Error(w, "Parse error", http.StatusBadRequest)
		return
	}

	if len(requests) == 0 {
		resp := RPCResp{JSONRPC: "2.0", Error: &RPCError{Code: -32600, Message: "Invalid Request: empty batch"}}
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(resp)
		return
	}

	results := make([]*RPCResp, len(requests))
	var wg sync.WaitGroup

	// Конкурентное выполнение каждого запроса в батче
	for idx, req := range requests {
		wg.Add(1)
		go func(i int, q RPCReq) {
			defer wg.Done()
			// Если нет ID — это notification, результат не пишется в ответ
			if q.ID != nil {
				results[i] = executeSingle(r.Context(), q)
			} else {
				// Выполняем fire-and-forget
				_ = executeSingle(r.Context(), q)
			}
		}(idx, req)
	}

	wg.Wait()

	// Собираем непустые ответы
	var finalResponses []*RPCResp
	for _, res := range results {
		if res != nil {
			finalResponses = append(finalResponses, res)
		}
	}

	w.Header().Set("Content-Type", "application/json")
	if len(finalResponses) == 0 {
		w.WriteHeader(http.StatusNoContent)
		return
	}

	_ = json.NewEncoder(w).Encode(finalResponses)
}

func main() {
	http.HandleFunc("/rpc/batch", batchHandler)
	fmt.Println("Batch JSON-RPC 2.0 Server listening on :8080/rpc/batch")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Параллельная обработка батч-запросов в горутинах с частичной обработкой ошибок

## Под капотом

Запись результатов по индексу `results[i] = ...` абсолютно потокобезопасна без мьютекса, так как каждая горутина пишет строго в свой выделенный слот массива. Это устраняет contention на мьютексах и дает линейную масштабируемость по ядрам CPU.

## Подводные камни

Неограниченный размер батча. Клиент может отправить массив из 500 000 элементов в одном теле запроса, породив полмиллиона горутин и вызвав OOM. Всегда ограничивайте максимальный размер пакета (например, `len(requests) > 100 -> error`).

## На собеседовании

В Avito и Яндекс часто спрашивают: 'Обязан ли порядок элементов в массиве ответа точно совпадать с порядком запросов в батче?' Ответ: Согласно спецификации JSON-RPC 2.0, клиент сопоставляет ответы исключительно по полю `id`, поэтому сервер имеет право возвращать ответы в любом порядке. Однако соблюдение порядка считается хорошей практикой для оптимизации клиентских очередей.
