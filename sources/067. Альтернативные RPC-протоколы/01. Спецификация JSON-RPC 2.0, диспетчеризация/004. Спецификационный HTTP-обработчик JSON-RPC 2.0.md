# Спецификационный HTTP-обработчик JSON-RPC 2.0 с валидацией протокола

## Условие

4. **Реализация JSON-RPC 2.0 сервера**: Напишите HTTP-обработчик, соответствующий официальной спецификации протокола JSON-RPC 2.0. Сервер должен принимать только POST-запросы с телом в формате JSON, содержащим поля jsonrpc ("2.0"), method, params и id.

### Исходная формулировка

**Реализация JSON-RPC 2.0 сервера**: Напишите HTTP-обработчик, соответствующий официальной спецификации протокола JSON-RPC 2.0. Сервер должен принимать только POST-запросы с телом в формате JSON, содержащим поля `jsonrpc` (строго `"2.0"`), `method`, `params` и `id`. Выполните указанный метод и верните ответ в формате `{"jsonrpc": "2.0", "result": ..., "id": ...}`. В случае ошибок возвращайте объект `error` со стандартными кодами ошибок (например, `-32601` для ненашедшегося метода).

## Теория

Официальная спецификация JSON-RPC 2.0 налагает строгие требования к валидности входящего сообщения:
1. Метод запроса: строго `POST`. Запросы `GET`, `PUT`, `DELETE` должны отклоняться со статусом `405 Method Not Allowed`.
2. Заголовок `Content-Type`: должен быть `application/json` (или содержать его).
3. Поле `jsonrpc`: **обязано** иметь точное строковое значение `"2.0"`. Значения `"1.0"`, `2.0` (число) или отсутствие поля классифицируются как ошибка `Invalid Request` (код `-32600`).
4. Поле `method`: обязано быть непустой строкой. Имена методов, начинающиеся с префикса `"rpc."`, зарезервированы для внутренних системных процедур стандарта.
5. Любое несоответствие спецификации должно возвращать корректно сформированный объект ошибки с кодом `-32600`.

## Решение по шагам

1. Проверьте метод HTTP-запроса на равенство `http.MethodPost`.
2. Проверьте заголовок `Content-Type`.
3. Распакуйте тело в структуру и выполните валидацию полей `jsonrpc == "2.0"` и `method != ""`.
4. Запретите вызов зарезервированных методов с префиксом `rpc.`.
5. Верните результат либо спецификационную ошибку `-32600`.

## Код решения

**`strict_server.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"strings"
)

type StrictRequest struct {
	JSONRPC string          `json:"jsonrpc"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params,omitempty"`
	ID      any             `json:"id"`
}

type StrictResponse struct {
	JSONRPC string `json:"jsonrpc"`
	Result  any    `json:"result,omitempty"`
	Error   *RPCError `json:"error,omitempty"`
	ID      any    `json:"id"`
}

type RPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
}

func strictRPCValidator(w http.ResponseWriter, r *http.Request) {
	// 1. Проверка метода HTTP
	if r.Method != http.MethodPost {
		http.Error(w, "JSON-RPC requires POST method", http.StatusMethodNotAllowed)
		return
	}

	w.Header().Set("Content-Type", "application/json")

	// 2. Декодирование JSON
	var req StrictRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		_ = json.NewEncoder(w).Encode(StrictResponse{
			JSONRPC: "2.0",
			Error:   &RPCError{Code: -32700, Message: "Parse error"},
			ID:      nil,
		})
		return
	}

	// 3. Строгая валидация версии 2.0 и метода
	if req.JSONRPC != "2.0" || req.Method == "" {
		_ = json.NewEncoder(w).Encode(StrictResponse{
			JSONRPC: "2.0",
			Error:   &RPCError{Code: -32600, Message: "Invalid Request: jsonrpc must be '2.0' and method non-empty"},
			ID:      req.ID,
		})
		return
	}

	// 4. Защита зарезервированного пространства имен rpc.*
	if strings.HasPrefix(req.Method, "rpc.") {
		_ = json.NewEncoder(w).Encode(StrictResponse{
			JSONRPC: "2.0",
			Error:   &RPCError{Code: -32601, Message: "Method prefix 'rpc.' is reserved"},
			ID:      req.ID,
		})
		return
	}

	// 5. Успешная обработка
	_ = json.NewEncoder(w).Encode(StrictResponse{
		JSONRPC: "2.0",
		Result:  fmt.Sprintf("Method '%s' executed successfully", req.Method),
		ID:      req.ID,
	})
}

func main() {
	http.HandleFunc("/rpc/v2", strictRPCValidator)
	fmt.Println("Strict JSON-RPC 2.0 Server running on :8080/rpc/v2")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Строгая проверка версии jsonrpc 2.0, метода POST и зарезервированных префиксов

## Под капотом

Спецификация JSON-RPC 2.0 специально резервирует префикс `rpc.` для будущих расширений протокола (системных дескрипторов, интроспекции, пингов). Попытка зарегистрировать пользовательский метод `rpc.systemInfo` нарушает совместимость с официальными тестами соответствия JSON-RPC 2.0 Compliance Suite.

## Подводные камни

Использование типа `int` для поля `ID`. В реальных распределенных системах клиенты часто передают строковые UUID (`id: "c84b-..."`) или дробные числа. Поле `ID` обязано обрабатываться как `any` или `json.RawMessage`.

## На собеседовании

В Ozon часто спрашивают: 'Каким должен быть ID в ответе при Parse Error (-32700)?' Ответ: Согласно спецификации, если произошла ошибка парсинга JSON и сервер не смог прочитать поле ID, поле `id` в объекте ответа ДОЛЖНО быть строго `null` (в Go — `nil`), а не опускаться из JSON.
