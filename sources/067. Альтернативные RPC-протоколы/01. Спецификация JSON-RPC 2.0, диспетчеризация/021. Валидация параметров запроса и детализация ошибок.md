# Валидация параметров запроса и детализация ошибок (-32602)

## Условие

21. **Валидация параметров.**: Парсите `params` в struct через `json.Unmarshal` + `go-playground/validator`. Возвращайте `-32602 InvalidParams` с детализацией (какое поле невалидно). Объясните, почему валидация схемы должна происходить до вызова бизнес-логики.

### Исходная формулировка

**Валидация параметров.**: Парсите `params` в struct через `json.Unmarshal` + `go-playground/validator`. Возвращайте `-32602 InvalidParams` с детализацией (какое поле невалидно). Объясните, почему `json.RawMessage` + delayed unmarshal — лучше, чем `map[string]any` для типобезопасности.

## Теория

Принцип 'Fail-Fast' и защита доменного слоя:
1. Запрос не должен достигать уровня базы данных или бизнес-логики, если входные данные не соответствуют ограничениям схемы (Schema Constraints).
2. Ошибки валидации (пустой email, отрицательная сумма перевода, недопустимый диапазон дат) должны отсекаться на фазе распаковки параметров.
3. Спецификация JSON-RPC 2.0 предписывает использовать для таких случаев стандартный код ошибки `-32602 (Invalid params)`.
4. В поле `data` объекта ошибки передается детальный список нарушенных правил для каждого поля, что позволяет фронтенду подсветить невалидные инпуты в форме.

## Решение по шагам

1. Создайте структуру запроса с правилами валидации (теги `validate:`).
2. Напишите функцию валидации параметров.
3. При обнаружении ошибок сформируйте срез дефектов валидации.
4. Упакуйте ошибку в объект с кодом `-32602` и полем `data`.
5. Верните ответ клиенту.

## Код решения

**`validator.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"strings"
)

type CreateUserRequest struct {
	Email string `json:"email"`
	Age   int    `json:"age"`
}

type ValidationErrorDetail struct {
	Field  string `json:"field"`
	Reason string `json:"reason"`
}

func validateCreateUser(req *CreateUserRequest) []ValidationErrorDetail {
	var errs []ValidationErrorDetail

	if !strings.Contains(req.Email, "@") || len(req.Email) < 5 {
		errs = append(errs, ValidationErrorDetail{Field: "email", Reason: "must be a valid email address"})
	}
	if req.Age < 18 || req.Age > 120 {
		errs = append(errs, ValidationErrorDetail{Field: "age", Reason: "must be between 18 and 120"})
	}

	return errs
}

func createUserHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")

	var rpcReq struct {
		JSONRPC string          `json:"jsonrpc"`
		Method  string          `json:"method"`
		Params  json.RawMessage `json:"params"`
		ID      any             `json:"id"`
	}

	if err := json.NewDecoder(r.Body).Decode(&rpcReq); err != nil {
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32700, "message": "Parse error"},
			"id":      nil,
		})
		return
	}

	var userReq CreateUserRequest
	if err := json.Unmarshal(rpcReq.Params, &userReq); err != nil {
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32602, "message": "Invalid JSON params format"},
			"id":      rpcReq.ID,
		})
		return
	}

	validationErrors := validateCreateUser(&userReq)
	if len(validationErrors) > 0 {
		// Стандартный код -32602 с детализацией в data
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error": map[string]any{
				"code":    -32602,
				"message": "Invalid params",
				"data":    validationErrors,
			},
			"id": rpcReq.ID,
		})
		return
	}

	_ = json.NewEncoder(w).Encode(map[string]any{
		"jsonrpc": "2.0",
		"result":  map[string]any{"status": "created", "user_id": 42},
		"id":      rpcReq.ID,
	})
}

func main() {
	http.HandleFunc("/rpc/user/create", createUserHandler)
	fmt.Println("User validation server running on :8080/rpc/user/create")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Валидация полей структуры с детализацией дефектов в поле data ошибки -32602

## Под капотом

Отсечение невалидных запросов до уровня бизнес-логики предотвращает SQL-инъекции, повреждение состояния транзакций в базе данных и бесполезную трату CPU на криптографические операции (хэширование паролей) при заведомо некорректных входных данных.

## Подводные камни

Возврат ошибки `-32600 (Invalid Request)` вместо `-32602 (Invalid params)`. Код `-32600` означает нарушение базовой структуры JSON-RPC фрейма (например, забыли поле `method`), тогда как некорректные поля бизнес-параметров обязаны возвращать `-32602`.

## На собеседовании

В Т-Банке и Сбере часто спрашивают: 'Можно ли возвращать сырые ошибки базы данных (например, unique constraint violation) в поле error.message?' Ответ: Категорически нет из соображений безопасности (Information Disclosure). Текст ошибки сервера должен быть обезличен ('Duplicate user email'), а детали БД логироваться во внутренний лог сервиса.
