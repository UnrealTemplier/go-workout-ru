# Стек промежуточных обработчиков (Middleware Stack) для JSON-RPC

## Условие

16. **Middleware stack.**: Реализуйте onion-мiddleware для JSON-RPC: Logging (method, duration, id), Metrics (Prometheus counters), Recovery (panic → `-32603 InternalError`). Объясните, как middleware работает на уровне отдельных RPC методов внутри батча, а не только на уровне HTTP.

### Исходная формулировка

**Middleware stack.**: Реализуйте onion-мiddleware для JSON-RPC: Logging (method, duration, id), Metrics (Prometheus counters), Recovery (panic → `-32603 InternalError`). Объясните, как middleware работает с batch (один лог на batch или per-request).

## Теория

При разработке JSON-RPC серверов существует два уровня Middleware:
1. **HTTP-уровень:** Оперирует заголовками, TLS, аутентификацией сессии на уровне всего HTTP-пакета.
2. **RPC-уровень (Method Middleware):** Оперирует конкретным методом внутри запроса.
   - В случае Batch Request один HTTP-запрос содержит 50 разных RPC-вызовов!
   - HTTP-middleware выполнится ровно **1 раз**.
   - RPC-middleware должно выполниться **50 раз** — индивидуально для каждого метода батча!

Архитектура Onion-Middleware:
```go
type RPCHandler func(ctx context.Context, req *RPCRequest) (*RPCResponse, error)
type RPCMiddleware func(next RPCHandler) RPCHandler
```
Цепочка оберток: `Recovery -> Logging -> Metrics -> ServiceHandler`.

## Решение по шагам

1. Определите тип `RPCHandler` и `RPCMiddleware`.
2. Реализуйте middleware `RecoveryMiddleware`, перехватывающее паники.
3. Реализуйте middleware `LoggingMiddleware`, замеряющее латентность.
4. Напишите функцию композиции middleware `Chain(middlewares...)`.
5. Примените цепочку к обработчикам каждого метода.

## Код решения

**`middleware_stack.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"time"
)

type RPCRequest struct {
	JSONRPC string          `json:"jsonrpc"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params"`
	ID      any             `json:"id"`
}

type RPCResponse struct {
	JSONRPC string `json:"jsonrpc"`
	Result  any    `json:"result,omitempty"`
	Error   any    `json:"error,omitempty"`
	ID      any    `json:"id"`
}

type RPCHandler func(ctx context.Context, req *RPCRequest) *RPCResponse
type RPCMiddleware func(next RPCHandler) RPCHandler

// RecoveryMiddleware превращает панику в спецификационную ошибку -32603
func RecoveryMiddleware(next RPCHandler) RPCHandler {
	return func(ctx context.Context, req *RPCRequest) (resp *RPCResponse) {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("[PANIC RECOVERED] in method %s: %v\n", req.Method, r)
				resp = &RPCResponse{
					JSONRPC: "2.0",
					Error: map[string]any{
						"code":    -32603,
						"message": fmt.Sprintf("Internal error: %v", r),
					},
					ID: req.ID,
				}
			}
		}()
		return next(ctx, req)
	}
}

// LoggingMiddleware замеряет длительность вызова конкретного RPC-метода
func LoggingMiddleware(next RPCHandler) RPCHandler {
	return func(ctx context.Context, req *RPCRequest) *RPCResponse {
		start := time.Now()
		resp := next(ctx, req)
		duration := time.Since(start)
		fmt.Printf("[RPC LOG] Method: %s | ID: %v | Duration: %v\n", req.Method, req.ID, duration)
		return resp
	}
}

// Chain объединяет слайс middleware в единый конвейер
func Chain(handler RPCHandler, middlewares ...RPCMiddleware) RPCHandler {
	for i := len(middlewares) - 1; i >= 0; i-- {
		handler = middlewares[i](handler)
	}
	return handler
}

func main() {
	// Базовый обработчик с паникой для демонстрации
	baseHandler := func(ctx context.Context, req *RPCRequest) *RPCResponse {
		if req.Method == "riskyMethod" {
			panic("database connection dropped")
		}
		return &RPCResponse{JSONRPC: "2.0", Result: "success", ID: req.ID}
	}

	pipeline := Chain(baseHandler, RecoveryMiddleware, LoggingMiddleware)

	// Тестируем защищенный вызов
	req := &RPCRequest{JSONRPC: "2.0", Method: "riskyMethod", ID: 101}
	resp := pipeline(context.Background(), req)

	respBytes, _ := json.Marshal(resp)
	fmt.Printf("Response: %s\n", string(respBytes))
}
```

ℹ️ Уровневый конвейер Onion Middleware для перехвата паник и мониторинга методов

## Под капотом

Композиция функций через `Chain` строит классическую луковую архитектуру (Onion Architecture): вызов входит через внешний слой `Logging`, затем проходит `Recovery`, достигает `baseHandler`, а затем возвращается в обратном порядке, выполняя завершающий код после `next()`.

## Подводные камни

Помещение `RecoveryMiddleware` глубже других middleware. Если паника произойдет внутри `LoggingMiddleware` (например, при обращении к nil указателю), неперехваченная паника приведет к падению всего HTTP-сервера. `RecoveryMiddleware` обязан быть самым внешним слоем.

## На собеседовании

В Ozon и Авито часто спрашивают: 'Почему в JSON-RPC нельзя использовать стандартный http.Handler middleware для сбора бизнес-метрик методов?' Ответ: HTTP middleware видит только путь `/rpc` и общий статус `200 OK`. Оно не может определить, какой именно метод вызван (особенно внутри батча из 10 разных методов) и завершился ли он доменной ошибкой. Метрики методов должны собираться внутри RPC-диспетчера.
