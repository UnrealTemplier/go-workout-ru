# Генерация типобезопасного диспетчера (Code-Generated Dispatcher)

## Условие

18. **Code-generated dispatcher**: Альтернатива reflection — кодогенерация type-safe dispatcher из Go интерфейса (быстрее, type-safe).

### Исходная формулировка

**Code-generated dispatcher**: Альтернатива reflection — кодогенерация type-safe dispatcher из Go интерфейса (быстрее, type-safe).

## Теория

Хотя рефлексия (`reflect`) удобна, в высоконагруженных системах (HighLoad) она создает накладные расходы:
- Вызов `reflect.Value.Call()` выделяет слайс аргументов в куче.
- Компилятор не может оптимизировать и инлайнить вызовы функций.
- Поиск методов и проверка типов в рантайме расходуют CPU.

Альтернатива: **Статическая кодогенерация (Code Generation)**:
1. Разработчик описывает интерфейс контракта:
   ```go
   type OrderService interface {
       GetOrder(ctx context.Context, id int) (*Order, error)
   }
   ```
2. Генератор кода (`go generate`) автоматически генерирует строго типизированный диспетчер на базе оператора `switch`:
   ```go
   switch req.Method {
   case "OrderService.GetOrder":
       var id int
       json.Unmarshal(req.Params, &id)
       return s.svc.GetOrder(ctx, id)
   }
   ```
3. Скорость диспетчеризации возрастает в 5-10 раз, а аллокации памяти стремятся к нулю!

## Решение по шагам

1. Создайте интерфейс доменного сервиса `GreeterService`.
2. Реализуйте структуру сгенерированного диспетчера `GreeterDispatcher`.
3. В диспетчере используйте прямой `switch/case` по именам методов.
4. Продемонстрируйте прямой типобезопасный вызов без пакета `reflect`.
5. Сравните производительность с рефлексивным подходом.

## Код решения

**`codegen_dispatcher.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
)

// GreeterService описывает интерфейс бизнес-логики
type GreeterService interface {
	SayHello(ctx context.Context, name string) (string, error)
	GetVersion(ctx context.Context) (string, error)
}

// GreeterServiceImpl — конкретная реализация сервиса
type GreeterServiceImpl struct{}

func (s *GreeterServiceImpl) SayHello(ctx context.Context, name string) (string, error) {
	if name == "" {
		return "", errors.New("name cannot be empty")
	}
	return fmt.Sprintf("Hello, %s!", name), nil
}

func (s *GreeterServiceImpl) GetVersion(ctx context.Context) (string, error) {
	return "v1.4.2", nil
}

// GreeterDispatcher — сгенерированный код статического диспетчера (Zero-Reflection)
type GreeterDispatcher struct {
	service GreeterService
}

func NewGreeterDispatcher(svc GreeterService) *GreeterDispatcher {
	return &GreeterDispatcher{service: svc}
}

func (d *GreeterDispatcher) Dispatch(ctx context.Context, method string, rawParams json.RawMessage) (any, error) {
	// Прямой switch/case без рефлексии: оптимизируется компилятором в Jump Table
	switch method {
	case "Greeter.SayHello":
		var name string
		if err := json.Unmarshal(rawParams, &name); err != nil {
			return nil, fmt.Errorf("invalid params for SayHello: %w", err)
		}
		return d.service.SayHello(ctx, name)

	case "Greeter.GetVersion":
		return d.service.GetVersion(ctx)

	default:
		return nil, errors.New("method not found")
	}
}

func main() {
	svc := &GreeterServiceImpl{}
	dispatcher := NewGreeterDispatcher(svc)

	res, err := dispatcher.Dispatch(context.Background(), "Greeter.SayHello", json.RawMessage(`"Golang Gopher"`))
	if err != nil {
		panic(err)
	}
	fmt.Printf("Codegen Dispatch Result: %v\n", res)
}
```

ℹ️ Статический диспетчер без рефлексии с оптимизацией switch в Jump Table

## Под капотом

Компилятор Go компилирует оператор `switch` по строковым константам либо в бинарный поиск по хэшам строк, либо в таблицу переходов (Jump Table). Это исключает накладные расходы на создание объектов `reflect.Value`, снижая время диспетчеризации до единиц наносекунд.

## Подводные камни

Забыть запустить `go generate ./...` после добавления нового метода в интерфейс сервиса. Статический диспетчер не будет содержать новый метод до повторного запуска кодогенерации.

## На собеседовании

В Авито и Wildberries часто спрашивают: 'Почему в gRPC и ConnectRPC используется кодогенерация диспетчера вместо рефлексии?' Ответ: Из соображений максимальной производительности, типобезопасности во время компиляции (Compile-time Type Safety) и исключения аллокаций памяти в куче при каждом вызове RPC-метода.
