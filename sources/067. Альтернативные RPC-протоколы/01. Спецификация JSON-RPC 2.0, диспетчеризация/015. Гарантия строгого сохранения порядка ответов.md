# Гарантия строгого сохранения порядка ответов в батче (Batch Ordering)

## Условие

15. **Batch ordering guarantee**: Для use cases, где порядок важен, гарантируйте in-order responses или документируйте, что порядок не гарантирован.

### Исходная формулировка

**Batch ordering guarantee**: Для use cases, где порядок важен, гарантируйте in-order responses или документируйте, что порядок не гарантирован.

## Теория

Хотя спецификация JSON-RPC 2.0 допускает произвольный порядок элементов в массиве ответа, для многих промышленных систем критически важно соблюдение строгого порядка:
- Простые мобильные клиенты с ограниченными вычислительными ресурсами.
- Потоковая обработка результатов конвейера (Pipeline Processing), где элемент с индексом \(i\) строго соответствует запросу с индексом \(i\).
- Тестовые среды и сквозные интеграционные тесты.

Архитектура строгого упорядочивания при параллельном исполнении:
1. Массив результатов выделяется сразу под размер входящего батча:
   `responses := make([]*Response, len(requests))`.
2. Каждая горутина получает свой персональный индекс `idx` и записывает результат строго в ячейку `responses[idx] = res`.
3. После вызова `wg.Wait()` элементы фильтруются от `nil` с сохранением оригинальной последовательности.

## Решение по шагам

1. Создайте срез фиксированной длины `results := make([]*RPCResp, len(batch))`.
2. Запустите параллельные горутины, передавая индекс `i`.
3. Каждая горутина записывает результат строго по своему индексу.
4. Дождитесь `wg.Wait()`.
5. Соберите ответы в выходной срез без нарушения порядка.

## Код решения

**`ordered_batch.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"math/rand"
	"net/http"
	"sync"
	"time"
)

type OrderedReq struct {
	JSONRPC string `json:"jsonrpc"`
	Method  string `json:"method"`
	ID      int    `json:"id"`
}

type OrderedResp struct {
	JSONRPC string `json:"jsonrpc"`
	Result  string `json:"result"`
	ID      int    `json:"id"`
}

func orderedBatchHandler(w http.ResponseWriter, r *http.Request) {
	var batch []OrderedReq
	if err := json.NewDecoder(r.Body).Decode(&batch); err != nil {
		http.Error(w, "Bad JSON", http.StatusBadRequest)
		return
	}

	// Выделяем срез строго по размеру входного пакета
	results := make([]OrderedResp, len(batch))
	var wg sync.WaitGroup

	for i, req := range batch {
		wg.Add(1)
		go func(idx int, q OrderedReq) {
			defer wg.Done()

			// Симулируем случайную задержку для проверки сохранения порядка
			jitter := time.Duration(rand.Intn(50)) * time.Millisecond
			time.Sleep(jitter)

			// Пишем строго в свою ячейку массива без взаимных блокировок
			results[idx] = OrderedResp{
				JSONRPC: "2.0",
				Result:  fmt.Sprintf("Completed %s (idx: %d)", q.Method, idx),
				ID:      q.ID,
			}
		}(i, req)
	}

	wg.Wait()

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(results)
}

func main() {
	http.HandleFunc("/rpc/ordered-batch", orderedBatchHandler)
	fmt.Println("Ordered Batch server running on :8080/rpc/ordered-batch")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Параллельное исполнение с детерминированным порядком результатов по индексам ячеек

## Под капотом

Запись в независимые слоты предвыделенного среза `results[idx]` в Go не требует мьютексов и не вызывает ложного разделения памяти (False Sharing), так как структуры `OrderedResp` занимают достаточное количество байт и не конфликтуют в L1/L2 кэш-линиях процессора.

## Подводные камни

Попытка делать `results = append(results, res)` внутри параллельных горутин. Это гарантированно разрушит порядок ответов и приведет к гонкам данных.

## На собеседовании

В Wildberries на секции по HighLoad часто спрашивают: 'Как влияет размер кэш-линии процессора (64 байта) на параллельную запись в срез структур?' Ответ: Если структуры очень маленькие (например, 8 байт), несколько ядер CPU могут инвалидировать кэш-линии друг друга (False Sharing). В таких случаях горутины пишут в локальные переменные, а объединение происходит после синхронизации.
