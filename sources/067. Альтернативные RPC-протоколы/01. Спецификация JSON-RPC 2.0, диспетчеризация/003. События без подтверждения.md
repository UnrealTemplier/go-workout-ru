### Исходная формулировка

**Notifications.**: Обработайте Request без поля `id`: это notification, не требует ответа (HTTP 204 или пустое тело). Реализуйте fire-and-forget метод `logEvent`. Объясните, почему notification не может иметь `error` в ответе — и как обрабатывать failures на стороне сервера (async logging).

## Теория

Спецификация JSON-RPC 2.0 выделяет два типа сообщений от клиента:
1. **Запрос (Request):** Содержит поле `id`. Требует обязательного ответа с тем же `id` (успех или ошибка).
2. **Уведомление (Notification):** Запрос **БЕЗ** поля `id` (или поле `id` отсутствует).
   - Клиент явно сообщает серверу: *'Меня не интересует результат выполнения данной операции и возможные ошибки'*.
   - Сервер **НЕ ДОЛЖЕН** отправлять ответное тело в формате JSON-RPC.
   - Поверх HTTP сервер возвращает статус `HTTP 204 No Content` либо пустой `HTTP 200 OK`.

Сценарии применения Notifications:
- Отправка метрик, логов и аудиторских событий (`logEvent`, `trackMetric`).
- Обновление позиции курсора или координат мыши в интерфейсе.
- Сброс кэша или пинг без ожидания завершения.

Поскольку у клиента нет `id` для сопоставления ответа, отправка любого JSON-ответа на notification нарушает спецификацию и сломает клиентский парсер!

## Решение по шагам

1. Создайте структуру запроса, где `ID *json.RawMessage` является указателем.
2. Проверьте: если `ID == nil`, запрос является уведомлением (`isNotification = true`).
3. Выполните целевую процедуру (например, асинхронную запись в журнал логов).
4. Если `isNotification == true`, завершите HTTP-запрос со статусом `http.StatusNoContent` (204) без тела ответа.

## Код решения

**`notification.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

type JSONRPCMessage struct {
	JSONRPC string           `json:"jsonrpc"`
	Method  string           `json:"method"`
	Params  json.RawMessage  `json:"params,omitempty"`
	ID      *json.RawMessage `json:"id,omitempty"` // nil если это Notification
}

func handleRPC(w http.ResponseWriter, r *http.Request) {
	var msg JSONRPCMessage
	if err := json.NewDecoder(r.Body).Decode(&msg); err != nil {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusOK)
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32700, "message": "Parse error"},
			"id":      nil,
		})
		return
	}

	isNotification := (msg.ID == nil)

	if msg.Method == "logEvent" {
		var logText string
		_ = json.Unmarshal(msg.Params, &logText)
		fmt.Printf("[NOTIFICATION RECEIVED] Event: %s\n", logText)
	}

	// Если это Notification — ответ в JSON-RPC возвращать строго запрещено
	if isNotification {
		w.WriteHeader(http.StatusNoContent) // HTTP 204 No Content
		return
	}

	// Обычный ответ на Request с ID
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]any{
		"jsonrpc": "2.0",
		"result":  "ok",
		"id":      msg.ID,
	})
}

func main() {
	http.HandleFunc("/rpc", handleRPC)
	fmt.Println("Notification-aware JSON-RPC server on :8080/rpc")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Детекция Notification по nil значению ID и возврат HTTP 204 No Content

## Под капотом

Если декодировать `ID` как обычную переменную `any`, то при отсутствии ключа `"id"` в JSON поле примет значение `nil`. Однако если клиент явно передал `"id": null`, `any` также будет равен `nil`, хотя `"id": null` по спецификации считается запросом, а не уведомлением! Использование `*json.RawMessage` решает эту проблему: при отсутствии ключа указатель равен `nil`, а при `"id": null` указатель указывает на срез `[]byte("null")`.

## Подводные камни

Запуск тяжелых фоновых операций на каждый notification без ограничения конкурентности. Злоумышленник может отправить миллион notifications без `id`, породив миллион горутин и вызвав исчерпание памяти сервера (Notification Flood Attack).

## На собеседовании

В Wildberries и Tinkoff часто спрашивают: 'Что должен вернуть сервер, если в одном HTTP Batch-запросе пришли 5 уведомлений (notifications) и ни одного обычного запроса?' Ответ: Согласно спецификации JSON-RPC 2.0, сервер не должен возвращать ничего (HTTP 204 No Content или пустое тело), так как ни на одно уведомление ответ не формируется.
