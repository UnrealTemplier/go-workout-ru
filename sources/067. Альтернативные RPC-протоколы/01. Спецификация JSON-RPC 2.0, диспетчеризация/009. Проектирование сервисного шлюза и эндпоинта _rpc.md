# Проектирование сервисного шлюза и эндпоинта /rpc

## Условие

9. **Базовый JSON-RPC server**: Реализуйте endpoint `/rpc`, который парсит request, диспатчит по method name, возвращает response.

### Исходная формулировка

**Базовый JSON-RPC server**: Реализуйте endpoint `/rpc`, который парсит request, диспатчит по method name, возвращает response.

## Теория

При проектировании микросервисной архитектуры шлюз JSON-RPC выполняет роль фасадного слоя:
1. Клиенты обращаются к единой точке входа `/rpc`.
2. Запрос проходит через слои Middleware:
   - Аутентификация (Bearer JWT);
   - Rate Limiting (ограничение запросов);
   - Сквозная трассировка OpenTelemetry;
   - Сбор метрик Prometheus (латентность каждого метода).
3. Диспетчер передает управление конкретному сервисному контроллеру.
4. Результат упаковывается в стандартный ответ JSON-RPC 2.0.

## Решение по шагам

1. Создайте структуру RPC-шлюза `Gateway` с мапой зарегистрированных методов.
2. Подключите Middleware логирования и подсчета времени выполнения.
3. Реализуйте эндпоинт `/rpc`.
4. Продемонстрируйте маршрутизацию к двум разным сервисам (AuthService и OrderService).

## Код решения

**`gateway.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"time"
)

type Gateway struct {
	routes map[string]func(params json.RawMessage) (any, error)
}

func NewGateway() *Gateway {
	g := &Gateway{routes: make(map[string]func(json.RawMessage) (any, error))}
	
	// Регистрация сервисных методов
	g.routes["auth.login"] = func(p json.RawMessage) (any, error) {
		return map[string]string{"token": "jwt-token-xyz"}, nil
	}
	g.routes["order.create"] = func(p json.RawMessage) (any, error) {
		return map[string]any{"order_id": 9942, "status": "created"}, nil
	}
	return g
}

func (g *Gateway) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	start := time.Now()

	var req struct {
		JSONRPC string          `json:"jsonrpc"`
		Method  string          `json:"method"`
		Params  json.RawMessage `json:"params"`
		ID      any             `json:"id"`
	}

	w.Header().Set("Content-Type", "application/json")

	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32700, "message": "Parse error"},
			"id":      nil,
		})
		return
	}

	handler, exists := g.routes[req.Method]
	if !exists {
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32601, "message": "Method not found"},
			"id":      req.ID,
		})
		return
	}

	result, err := handler(req.Params)
	duration := time.Since(start)
	fmt.Printf("[RPC Gateway] Method %s took %v\n", req.Method, duration)

	if err != nil {
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32000, "message": err.Error()},
			"id":      req.ID,
		})
		return
	}

	_ = json.NewEncoder(w).Encode(map[string]any{
		"jsonrpc": "2.0",
		"result":  result,
		"id":      req.ID,
	})
}

func main() {
	gw := NewGateway()
	http.Handle("/rpc", gw)
	fmt.Println("Gateway running on :8080/rpc")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Сервисный шлюз /rpc с маршрутизацией по префиксам сервисов auth.* и order.*

## Под капотом

Использование точек в именах методов (`service.method`, например `users.getProfile`) является общепринятым стандартом структурирования API в JSON-RPC (Namespace Prefixing). Это позволяет объединять десятки микросервисов за единым фасадом без конфликтов имен методов.

## Подводные камни

Отсутствие таймаутов на уровне контекста в шлюзе. Если вызываемый микросервис зависает, HTTP-клиент будет удерживать TCP-соединение бесконечно. Всегда оборачивайте вызов в `context.WithTimeout(r.Context(), 5*time.Second)`.

## На собеседовании

В Авито и Яндекс часто спрашивают: 'Как организовать канареечный релиз (Canary Deployment) для методов JSON-RPC?' Ответ: Middleware шлюза анализирует заголовок клиента или ID пользователя и выполняет роутинг на канареечную версию бэкенда для метода `orders.create_v2`.
