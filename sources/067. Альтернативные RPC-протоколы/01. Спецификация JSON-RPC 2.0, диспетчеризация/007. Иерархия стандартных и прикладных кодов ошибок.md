# Иерархия стандартных и прикладных кодов ошибок спецификации

## Условие

7. **Стандартные коды ошибок.**: Реализуйте иерархию ошибок: `ParseError` (-32700), `InvalidRequest` (-32600), `MethodNotFound` (-32601), `InvalidParams` (-32602), `InternalError` (-32603). Добавьте custom application errors (-32000 to -32099) с `data` context.

### Исходная формулировка

**Стандартные коды ошибок.**: Реализуйте иерархию ошибок: `ParseError` (-32700), `InvalidRequest` (-32600), `MethodNotFound` (-32601), `InvalidParams` (-32602), `InternalError` (-32603). Добавьте custom errors: `-32000` Application Error. Объясните, почему `error.data` — полезно для деталей, но опасно для утечки stack trace.

## Теория

Спецификация JSON-RPC 2.0 четко резервирует диапазоны числовых кодов ошибок:

| Диапазон / Код | Описание ошибки | Значение |
| :--- | :--- | :--- |
| **-32700** | Parse error | Невалидный JSON на входе |
| **-32600** | Invalid Request | Структура не соответствует стандарту |
| **-32601** | Method not found | Вызываемый метод не существует |
| **-32602** | Invalid params | Неверное число или тип аргументов |
| **-32603** | Internal error | Внутренняя непредвиденная ошибка сервера |
| **-32000 .. -32099** | Server error | Зарезервировано для пользовательских ошибок приложения |

Поле `data`:
Объект ошибки может содержать дополнительное опциональное поле `data: any`, куда помещается структурированный контекст ошибки: трассировка стека (в dev-среде), валидационные ошибки конкретных полей формы или внутренний код ошибки сервиса.

## Решение по шагам

1. Создайте перечисление стандартных констант ошибок JSON-RPC.
2. Создайте тип `RPCError` с поддержкой поля `Data any`.
3. Реализуйте кастомную бизнес-ошибку (например, `ErrInsufficientFunds = -32001`).
4. Напишите хэндлер, возвращающий структурированную ошибку с полями в `data`.
5. Проверьте валидность формата ответа.

## Код решения

**`errors.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

const (
	CodeParseError     = -32700
	CodeInvalidRequest = -32600
	CodeMethodNotFound = -32601
	CodeInvalidParams  = -32602
	CodeInternalError  = -32603

	// Кастомные бизнес-коды в диапазоне -32000 .. -32099
	CodeInsufficientFunds = -32001
	CodeUserBlocked       = -32002
)

type DetailedRPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data,omitempty"`
}

type BankTransferRequest struct {
	FromAccount string  `json:"from_account"`
	Amount      float64 `json:"amount"`
}

func transferHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")

	var transferReq BankTransferRequest
	transferReq.Amount = 5000.0 // Имитируем запрос на списание

	accountBalance := 1200.0

	if transferReq.Amount > accountBalance {
		// Возвращаем спецификационную прикладную ошибку с полем data
		errResp := map[string]any{
			"jsonrpc": "2.0",
			"error": DetailedRPCError{
				Code:    CodeInsufficientFunds,
				Message: "Insufficient balance to perform transaction",
				Data: map[string]any{
					"current_balance": accountBalance,
					"required_amount": transferReq.Amount,
					"currency":        "RUB",
				},
			},
			"id": 1,
		}
		_ = json.NewEncoder(w).Encode(errResp)
		return
	}
}

func main() {
	http.HandleFunc("/rpc/transfer", transferHandler)
	fmt.Println("Error hierarchy server running on :8080/rpc/transfer")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Иерархия стандартных и кастомных кодов ошибок (-32001) с контекстными данными data

## Под капотом

Спецификация JSON-RPC требует, чтобы коды ошибок от -32768 до -32000 были строго зарезервированы. Любые пользовательские прикладные ошибки обязаны находиться либо в диапазоне `-32000 .. -32099`, либо вне диапазона от `-32768` до `-32000` (например, положительные коды 1000, 1001), чтобы клиенты могли однозначно отличать протокольные ошибки от доменных.

## Подводные камни

Передача несериализуемых типов данных (каналы, сырые системные ошибки `error` без преобразования в строку) в поле `Data`. `json.Marshal` вернет пустой объект или ошибку маршалинга.

## На собеседовании

В Т-Банке и Сбере часто спрашивают: 'Можно ли возвращать HTTP статус 500 при Internal Error (-32603)?' Ответ: Согласно спецификации JSON-RPC по транспорту HTTP, протокол инкапсулирует статус выполнения внутри JSON. Однако для целей мониторинга (Prometheus HTTP latency/error rate) смешение сетевых 200 OK с RPC ошибками создает проблемы. В таких архитектурах используют специальные middleware, выставляющие кастомный заголовок `X-RPC-Status: error` для трейсинга.
