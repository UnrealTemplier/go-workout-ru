# Уведомления без ответа при ошибках исполнения (Fire-and-Forget Error Suppression)

## Условие

22. **Notifications (без response)**: Реализуйте обработку notifications (без `id` field). Сервер не должен отправлять response, даже при ошибке.

### Исходная формулировка

**Notifications (без response)**: Реализуйте обработку notifications (без `id` field). Сервер не должен отправлять response, даже при ошибке.

## Теория

Фундаментальное правило спецификации JSON-RPC 2.0:
Если запрос является уведомлением (поле `id` отсутствует):
- Сервер **НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ** не возвращает тело ответа.
- Даже если метод не найден (`MethodNotFound -32601`).
- Даже если параметры невалидны (`InvalidParams -32602`).
- Даже если бизнес-логика выбросила панику (`InternalError -32603`).

Сервер обязан залогировать ошибку в свои внутренние журналы мониторинга, но в HTTP-ответе вернуть строго пустой ответ (`HTTP 204 No Content`), чтобы не нарушать асинхронный контракт с клиентом.

## Решение по шагам

1. Проверьте отсутствие поля `id` в запросе.
2. Выполните целевую функцию в блоке с перехватом ошибок.
3. При возникновении любой ошибки залогируйте ее на сервере.
4. Завершите обработку без записи данных в `http.ResponseWriter` со статусом 204.

## Код решения

**`strict_notification.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

func fireAndForgetRPCHandler(w http.ResponseWriter, r *http.Request) {
	var raw map[string]json.RawMessage
	if err := json.NewDecoder(r.Body).Decode(&raw); err != nil {
		// Ошибка синтаксиса JSON возвращает ответ, так как невозможно понять, был ли там ID
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32700, "message": "Parse error"},
			"id":      nil,
		})
		return
	}

	_, hasID := raw["id"]

	var method string
	_ = json.Unmarshal(raw["method"], &method)

	// Имитируем сбой: метод не найден
	if method != "telemetry.ping" {
		fmt.Printf("[SERVER LOG WARNING] Notification method %s not found!\n", method)
		if !hasID {
			// ДЛЯ NOTIFICATION ОТВЕТ ЗАПРЕЩЕН ДАЖЕ ПРИ ОШИБКЕ!
			w.WriteHeader(http.StatusNoContent)
			return
		}
		// Для обычного запроса возвращаем ошибку
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"error":   map[string]any{"code": -32601, "message": "Method not found"},
			"id":      raw["id"],
		})
		return
	}

	// Успешная обработка
	fmt.Printf("[SERVER LOG] Telemetry ping processed successfully.\n")

	if !hasID {
		w.WriteHeader(http.StatusNoContent)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]any{
		"jsonrpc": "2.0",
		"result":  "pong",
		"id":      raw["id"],
	})
}

func main() {
	http.HandleFunc("/rpc/telemetry", fireAndForgetRPCHandler)
	fmt.Println("Telemetry server listening on :8080/rpc/telemetry")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Подавление ответа на уведомления даже при возникновении внутренних ошибок

## Под капотом

С точки зрения модели акторов и очередей сообщений, notification — это классическое сообщение типа 'cast' (асинхронная отправка в один конец). Клиент освобождает сокет сразу после отправки, не слушая ответ. Если сервер попытается отправить байты в сокет, клиент может уже закрыть соединение, что вызовет ошибку `broken pipe` на сервере.

## Подводные камни

Отправка ответа об ошибке на notification. Это нарушает спецификацию и сбивает счетчик ответов в клиентских пулах соединений.

## На собеседовании

В Яндекс Практикум и Авито часто спрашивают: 'Когда при Parse Error (-32700) сервер возвращает ответ, если клиент хотел отправить notification?' Ответ: Если произошла ошибка синтаксического анализа JSON (Parse Error), сервер физически не может распарсить документ и узнать, было ли там поле ID или нет. Поэтому при Parse Error сервер обязан вернуть ответ с `"id": null`.
