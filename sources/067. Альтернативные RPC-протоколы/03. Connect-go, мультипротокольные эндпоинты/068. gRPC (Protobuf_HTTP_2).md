# gRPC (Protobuf/HTTP/2): глубокий разбор промышленного стандарта межсервисного общения

## Условие

68. gRPC (Protobuf/HTTP/2)

### Исходная формулировка

gRPC (Protobuf/HTTP/2)

## Теория

Фреймворк **gRPC** от Google стал фундаментом облачной микросервисной архитектуры (Cloud Native / Kubernetes). Понимание его внутреннего устройства — обязательный критерий грейда Senior Go Developer.

Архитектурные столпы gRPC:
1. **HTTP/2 Transport**:
   - **Мультиплексирование потоков (Streams)**: Тысячи параллельных RPC-запросов выполняются через одно TCP-соединение внутри независимых HTTP/2 стримов с целочисленными Stream ID.
   - **HPACK компрессия**: Заголовки сжимаются на основе статических и динамических таблиц, устраняя дублирование метаданных в сотни раз.
   - **Flow Control (Управление потоком)**: Окна кредитования на уровне соединения и каждого отдельного стрима предотвращают переполнение буферов памяти.
2. **Бинарная сериализация Protocol Buffers (Proto3)**:
   - Компактный формат с упаковкой полей в теги (Field Number + Wire Type).
   - Быстрый энкодинг без рефлексии.
   - Полная обратная и прямая совместимость контрактов.
3. **Keepalive и Ping**: Механизм активного зондирования соединения для своевременного обнаружения 'мертвых' каналов через промежуточные NAT и брандмауэры.

## Решение по шагам

1. Сконфигурируйте gRPC сервер с промышленными параметрами Keepalive (`keepalive.ServerParameters`).
2. Настройте ограничения на размер входящих и исходящих сообщений (`MaxRecvMsgSize`).
3. Сконфигурируйте пул горутин для обработки вызовов.
4. Настройте клиентский пул соединений (`grpc.WithKeepaliveParams`).
5. Продемонстрируйте мультиплексирование параллельных запросов через единый клиентский канал.

## Код решения

**`grpc_production_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"net"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/keepalive"
)

// Настройки Keepalive для промышленного gRPC сервера
var serverKeepalive = keepalive.ServerParameters{
	MaxConnectionIdle:     15 * time.Minute, // Время закрытия простаивающего соединения
	MaxConnectionAge:      2 * time.Hour,    // Периодическая ротация соединений для ребалансировки L7
	MaxConnectionAgeGrace: 5 * time.Minute,  // Время на дожатие активных запросов при ротации
	Time:                  1 * time.Minute,  // Интервал отправки Ping зондов
	Timeout:               20 * time.Second, // Ожидание ответа Pong до признания сокета мертвым
}

var serverEnforcement = keepalive.EnforcementPolicy{
	MinTime:             5 * time.Second, // Клиенту запрещено слать Ping чаще, чем раз в 5 сек
	PermitWithoutStream: true,            // Разрешаем Ping даже при отсутствии активных RPC
}

func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		panic(err)
	}

	server := grpc.NewServer(
		grpc.KeepaliveParams(serverKeepalive),
		grpc.KeepaliveEnforcementPolicy(serverEnforcement),
		grpc.MaxRecvMsgSize(16*1024*1024), // Максимальный размер входящего сообщения: 16 МБ
		grpc.MaxSendMsgSize(16*1024*1024),
	)

	fmt.Println("Enterprise gRPC Server инициализирован на порту :50051")
	_ = server
	_ = lis
}
```

ℹ️ Production-конфигурация gRPC сервера с защитой сокетов и L7 ребалансировкой

## Под капотом

Параметр `MaxConnectionAge` критически важен в среде Kubernetes. Если Kubernetes масштабирует сервис (HPA добавляет новые поды), клиенты со старыми открытыми TCP-соединениями продолжат слать запросы только на старые поды (проблема L4 Sticky Connections). Директива `MaxConnectionAge: 2h` заставляет gRPC сервер мягко завершить соединение через `GOAWAY` фрейм, принуждая клиент заново разрешить DNS и распределить нагрузку на новые поды.

## Подводные камни

1. **Слишком частый Ping клиентов (TooManyPings)**: Если клиент отправляет Keepalive Ping чаще, чем разрешено в `EnforcementPolicy.MinTime`, сервер разрывает соединение с ошибкой `GOAWAY: too_many_pings`.
2. **Утечка соединений при создании `grpc.Dial` на каждый вызов**: Антипаттерн новичков — вызывать `grpc.DialContext` внутри каждого HTTP-хэндлера. Соединение `grpc.ClientConn` создается ОДИН раз при старте сервиса и безопасно переиспользуется тысячами горутин.

## На собеседовании

На собеседовании в Яндекс или Ozon: 'Почему стандартный L4 балансировщик (IPVS, AWS NLB) не балансирует gRPC трафик между подами?' Ответ: gRPC мультиплексирует все вызовы в один долгоживущий TCP-сокет. L4 балансировщик видит лишь один открытый TCP поток и привязывает его к одной ноде. Для распределения gRPC запросов необходима L7 балансировка (Envoy, Istio Service Mesh или gRPC Client-Side Load Balancing через DNS / xDS).
