# Стандартизированная обработка ошибок в JSON-RPC 2.0 (-32700 .. -32600)

## Условие

49. **Обработка ошибок JSON-RPC**: Если метода не существует, верни объект `{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1}`. Реализуй обработку некорректных параметров (код -32602) и внутренних ошибок сервера.

### Исходная формулировка

**Обработка ошибок JSON-RPC**: Если метода не существует, верни объект `{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1}`. Реализуй обработку некорректных параметров (код -32602) и внутренних ошибок сервера.

## Теория

Спецификация JSON-RPC 2.0 резервирует диапазон кодов от `-32768` до `-32000` для предопределенных системных ошибок протокола:
- `-32700` (**Parse error**): Сервер получил некорректный JSON. Синтаксический разбор невозможен.
- `-32600` (**Invalid Request**): Тело является валидным JSON, но не соответствует структуре запроса JSON-RPC 2.0 (нет поля `"jsonrpc": "2.0"` или метод не строка).
- `-32601` (**Method not found**): Запрашиваемый метод не зарегистрирован на сервере.
- `-32602` (**Invalid params**): Параметры метода переданы в неверном формате или не прошли валидацию.
- `-32603` (**Internal error**): Внутренняя непредвиденная ошибка на стороне RPC-сервера (аналог HTTP 500).
- `-32000` to `-32099` (**Server error**): Зарезервировано под кастомные серверные системные ошибки.

Любые прикладные бизнес-ошибки (например, `UserNotFound = 1001`, `InsufficientFunds = 1002`) обязаны находиться **вне** диапазона `[-32768, -32000]`.

В Go идеальная реализация представляет собой систему типизированных ошибок, реализующих интерфейс `error` и автоматически преобразуемых в структуру `RPCError` с опциональным заполнением поля `Data` для отладки.

## Решение по шагам

1. Объявите константы стандартных кодов ошибок JSON-RPC 2.0.
2. Создайте тип `ErrorWithData` для передачи контекста (стектрейс, валидация полей).
3. Реализуйте диспетчер методов с перехватом `panic` и маппингом в `-32603 Internal error`.
4. Напишите юнит-тест, проверяющий корректный возврат `-32601` при обращении к несуществующему методу.

## Код решения

**`errors.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

type RPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data,omitempty"`
}

func (e *RPCError) Error() string {
	return fmt.Sprintf("jsonrpc error: code=%d message=%s", e.Code, e.Message)
}

// Стандартные ошибки по спецификации
var (
	ErrParse          = &RPCError{Code: -32700, Message: "Parse error"}
	ErrInvalidRequest = &RPCError{Code: -32600, Message: "Invalid Request"}
	ErrMethodNotFound = &RPCError{Code: -32601, Message: "Method not found"}
	ErrInvalidParams  = &RPCError{Code: -32602, Message: "Invalid params"}
	ErrInternal       = &RPCError{Code: -32603, Message: "Internal error"}
)

func NewCustomError(code int, msg string, data any) *RPCError {
	return &RPCError{Code: code, Message: msg, Data: data}
}

type RPCRequest struct {
	JSONRPC string           `json:"jsonrpc"`
	Method  string           `json:"method"`
	Params  json.RawMessage  `json:"params,omitempty"`
	ID      *json.RawMessage `json:"id"`
}

type RPCResponse struct {
	JSONRPC string           `json:"jsonrpc"`
	Result  any              `json:"result,omitempty"`
	Error   *RPCError        `json:"error,omitempty"`
	ID      *json.RawMessage `json:"id"`
}

type Dispatcher struct {
	handlers map[string]func(params json.RawMessage) (any, *RPCError)
}

func NewDispatcher() *Dispatcher {
	return &Dispatcher{handlers: make(map[string]func(json.RawMessage) (any, *RPCError))}
}

func (d *Dispatcher) Register(name string, h func(json.RawMessage) (any, *RPCError)) {
	d.handlers[name] = h
}

func (d *Dispatcher) Execute(body []byte) *RPCResponse {
	var req RPCRequest
	if err := json.Unmarshal(body, &req); err != nil {
		return &RPCResponse{JSONRPC: "2.0", Error: ErrParse, ID: nil}
	}
	if req.JSONRPC != "2.0" || req.Method == "" {
		return &RPCResponse{JSONRPC: "2.0", Error: ErrInvalidRequest, ID: req.ID}
	}

	handler, exists := d.handlers[req.Method]
	if !exists {
		return &RPCResponse{
			JSONRPC: "2.0",
			Error:   NewCustomError(ErrMethodNotFound.Code, ErrMethodNotFound.Message, map[string]string{"requested": req.Method}),
			ID:      req.ID,
		}
	}

	res, rpcErr := handler(req.Params)
	if rpcErr != nil {
		return &RPCResponse{JSONRPC: "2.0", Error: rpcErr, ID: req.ID}
	}

	return &RPCResponse{JSONRPC: "2.0", Result: res, ID: req.ID}
}

func main() {
	d := NewDispatcher()
	d.Register("user.get", func(p json.RawMessage) (any, *RPCError) {
		return map[string]string{"name": "Alice"}, nil
	})

	// Тест 1: Несуществующий метод -> -32601
	resp1 := d.Execute([]byte(`{"jsonrpc":"2.0","method":"unknown.func","id":100}`))
	out1, _ := json.Marshal(resp1)
	fmt.Println("Тест 1 (Method not found):", string(out1))

	// Тест 2: Битая JSON-строка -> -32700
	resp2 := d.Execute([]byte(`{jsonrpc: invalid`))
	out2, _ := json.Marshal(resp2)
	fmt.Println("Тест 2 (Parse error):", string(out2))
}
```

## Под капотом

Когда парсер JSON (`json.Unmarshal`) падает с синтаксической ошибкой, `req.ID` еще неизвестен. Спецификация JSON-RPC 2.0 строго гласит: если произошла ошибка синтаксического анализа (`-32700`) или идентификатор в запросе не распознан, поле `id` в ответе ошибки ОБЯЗАНО быть `null`. Если же тело успешно распарсилось, но метод не существует (`-32601`), поле `id` обязано содержать переданный клиентом идентификатор.

## Подводные камни

1. **HTTP Status Code 500 для JSON-RPC ошибок**: По спецификации, транспортная ошибка протокола JSON-RPC на уровне HTTP должна возвращать статус 200 OK (или 400/500 только при полном отказе шлюза), так как сам JSON-RPC запрос был успешно доставлен и обработан RPC-движком. Смешивание кодов приводит к падению стандартных клиентов.
2. **Утечка конфиденциальных данных в `Data`**: В поле `Data` ошибки часто по ошибке отправляют внутренний текст ошибки БД (`pq: relation "users" does not exist`) или пароли, что нарушает безопасность.

## На собеседовании

В финтех-платформах (Тинькофф, Сбер) JSON-RPC используется во внешних интеграционных API с банкоматами и POS-терминалами. Вопрос: 'Как отличить сбой сети от сбоя бизнес-логики в JSON-RPC?' Ответ: HTTP 200 с JSON-объектом, содержащим поле `error.code > 0` — бизнес-ошибка (недостаточно средств). HTTP 5xx / TCP timeout — сетевой сбой, требующий ретрая с идемпотентным ключом.
