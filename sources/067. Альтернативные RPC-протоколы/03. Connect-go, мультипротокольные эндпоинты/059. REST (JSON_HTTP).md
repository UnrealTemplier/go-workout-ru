# REST (JSON/HTTP): архитектурные границы и сравнение с RPC-парадигмой

## Условие

59. REST (JSON/HTTP)

### Исходная формулировка

REST (JSON/HTTP)

## Теория

Архитектурный стиль **REST (Representational State Transfer)** построен вокруг манипуляции состоянием ресурсов через стандартные HTTP-глаголы (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) и URI-иерархии.

Однако в сложных распределенных системах чисто ресурсная модель часто упирается в фундаментальные противоречия:
1. **CRUD vs Процедуры**: Как выразить операцию `CancelOrderAndRefund`, `LockUserAccount` или `RunDatabaseBackup` в терминах REST? Попытки свести сложный бизнес-процесс к `PATCH /orders/123 {"status":"cancelled"}` скрывают транзакционные последствия и усложняют валидацию.
2. **Проблема N+1 сетевых вызовов**: Чтобы отобразить страницу профиля, клиент вынужден делать отдельные вызовы к `/users/1`, `/users/1/orders`, `/users/1/reviews`.
3. **Отсутствие бинарных контрактов**: Спецификации OpenAPI (Swagger) часто пишутся вручную или отстают от релизов Go-бэкенда, что приводит к runtime-ошибкам у фронтенд-команд.

**RPC-парадигма (Remote Procedure Call)** смещает фокус с 'сущностей' на 'действия' и 'процедуры', предлагая строгую типизацию входных и выходных параметров, сгенерированные клиентские SDK и минимальный оверхед.

## Код решения

**`comparison.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

// 1. Модель REST: POST /transfers (создание ресурса перевода)
type TransferRequest struct {
	FromAccountID string  `json:"from_account_id"`
	ToAccountID   string  `json:"to_account_id"`
	Amount        float64 `json:"amount"`
	Currency      string  `json:"currency"`
}

func HandleRESTTransfer(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}
	var req TransferRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, "Bad Request", http.StatusBadRequest)
		return
	}

	// Бизнес-логика транзакции...
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
	_ = json.NewEncoder(w).Encode(map[string]any{
		"transfer_id": "tx_99812",
		"status":      "COMPLETED",
	})
}

// 2. Модель RPC: POST /billing.v1.BillingService/TransferFunds (вызов процедуры)
type RPCTransferRequest struct {
	FromAccount string  `json:"from_account"`
	ToAccount   string  `json:"to_account"`
	Amount      float64 `json:"amount"`
}

func HandleRPCTransfer(w http.ResponseWriter, r *http.Request) {
	var req RPCTransferRequest
	_ = json.NewDecoder(r.Body).Decode(&req)

	// В RPC ответ всегда упакован в структурированный DTO результата
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]any{
		"success":        true,
		"transaction_id": "tx_99812",
		"fee":            0.0,
	})
}

func main() {
	http.HandleFunc("/api/v1/transfers", HandleRESTTransfer)
	http.HandleFunc("/billing.v1.BillingService/TransferFunds", HandleRPCTransfer)
	fmt.Println("REST and RPC endpoints listening on :8080")
}
```

## Под капотом

В REST статус ответа передается через заголовок HTTP (например, `404 Not Found`). Однако в распределенных RPC-системах статус HTTP 200 часто возвращается даже при бизнес-ошибке (например, 'недостаточно средств на балансе'), чтобы прокси-серверы и CDN не считали запрос сетевым сбоем инстанса. Семантика ошибки передается внутри протокольного конверта (`grpc-status`, `error.code`).

## Подводные камни

1. **Антипаттерн REST-RPC Франкенштейна**: Создание эндпоинтов вида `POST /api/v1/users/123/do-activate-user-now` в якобы REST API. Это признак того, что проекту требуется полноценный RPC-протокол (Connect или gRPC), а не REST.
2. **Игнорирование версионирования схемы**: В REST изменение схемы требует обновления OpenAPI спецификации вручную, что часто забывается разработчиками.

## На собеседовании

В Т-Банке и Яндексе кандидатов спрашивают: 'Почему большинство внутренних микросервисов общаются по RPC, а не по REST?' Ответ: RPC обеспечивает явную семантику вызова процедур (Action-oriented), контрактную типизацию, в разы более высокую скорость сериализации (Protobuf) и поддержку стриминга, исключая двусмысленность HTTP-глаголов REST.
