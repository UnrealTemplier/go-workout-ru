# Connect Streaming: реализация Server, Client и Bidirectional стриминга

## Условие

62. **Connect streaming**: Используйте `connect.StreamingHandlerFunc` для server/client/bidirectional streaming, который работает в браузерах через multiple HTTP requests.

### Исходная формулировка

**Connect streaming**: Используйте `connect.StreamingHandlerFunc` для server/client/bidirectional streaming, который работает в браузерах через multiple HTTP requests.

## Теория

В спецификации Protocol Buffers существует 4 вида RPC-взаимодействий:
1. **Unary RPC**: 1 запрос -> 1 ответ.
2. **Server Streaming RPC**: 1 запрос -> \(N\) ответов.
3. **Client Streaming RPC**: \(N\) запросов -> 1 ответ (например, загрузка большого файла частями).
4. **Bidirectional Streaming RPC (Bidi)**: \(N\) запросов <-> \(M\) ответов (полнодуплексный чат или интерактивная сессия).

В классическом gRPC bidi-стриминг требует полноценного HTTP/2 сокета с обеих сторон. В веб-браузерах из-за ограничений браузерного API потоковая отправка запроса от клиента в сокет (`ReadableStream` в теле `fetch`) поддерживается не во всех сценариях.

**ConnectRPC** реализует потоковые обработчики через `*connect.BidiStream[Req, Resp]`, `*connect.ClientStream[Req]` и `*connect.ServerStream[Resp]`, обеспечивая плавную деградацию и работу как через HTTP/2, так и через HTTP/1.1 chunked transfer.

## Решение по шагам

1. Создайте сервис потоковой передачи метрик `TelemetryService`.
2. Реализуйте Client Streaming метод `RecordMetrics`: прием потока точек данных и возврат итоговой статистики.
3. Реализуйте Server Streaming метод `SubscribeAlerts`: отправка потока алертов.
4. Напишите bidi-стриминг для эхо-сервера с непрерывным обменом сообщениями.
5. Протестируйте корректное закрытие потоков с обеих сторон.

## Код решения

**`streaming_service.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"io"
	"net/http"
	"time"

	"connectrpc.com/connect"
)

type MetricPoint struct {
	Name  string  `json:"name"`
	Value float64 `json:"value"`
}

type MetricSummary struct {
	TotalPoints int     `json:"total_points"`
	AverageVal  float64 `json:"average_val"`
}

type TelemetryServer struct{}

// 1. Client Streaming: Прием потока точек метрик от сенсора -> Итоговая сводка
func (s *TelemetryServer) RecordMetrics(
	ctx context.Context,
	stream *connect.ClientStream[MetricPoint],
) (*connect.Response[MetricSummary], error) {
	var count int
	var sum float64

	for stream.Receive() {
		point := stream.Msg()
		count++
		sum += point.Value
	}

	if err := stream.Err(); err != nil {
		return nil, connect.NewError(connect.CodeInternal, fmt.Errorf("ошибка чтения потока клиента: %w", err))
	}

	avg := 0.0
	if count > 0 {
		avg = sum / float64(count)
	}

	return connect.NewResponse(&MetricSummary{
		TotalPoints: count,
		AverageVal:  avg,
	}), nil
}

// 2. Bidirectional Streaming: Интерактивный обмен
func (s *TelemetryServer) LiveExchange(
	ctx context.Context,
	stream *connect.BidiStream[MetricPoint, MetricPoint],
) error {
	for {
		msg, err := stream.Receive()
		if errors.Is(err, io.EOF) {
			return nil // Клиент завершил отправку
		}
		if err != nil {
			return err
		}

		// Обработка и зеркальный ответ
		echo := &MetricPoint{
			Name:  "processed." + msg.Name,
			Value: msg.Value * 2.0,
		}
		if err := stream.Send(echo); err != nil {
			return err
		}
	}
}

func main() {
	fmt.Println("Connect Streaming Service логика инициализирована")
}
```

## Под капотом

Под капотом `connect.ClientStream` использует интерфейс `stream.Receive()`, который считывает входящие фреймы до тех пор, пока клиентский HTTP-поток не закроется (получение `io.EOF`). При bidi-стриминге вызовы `Receive()` и `Send()` работают на независимых буферах и могут выполняться конкурентно в разных горутинах без взаимной блокировки.

## Подводные камни

1. **Блокировка буфера при bidi-стриминге**: Если сервер пытается сначала отправить 10,000 сообщений в `Send()`, не читая `Receive()`, а клиент делает то же самое, возникает распределенный deadlock (оба сокета ждут освобождения TCP window).
2. **Игнорирование `stream.Err()` после `Receive()`**: Завершение цикла `for stream.Receive()` может произойти как из-за нормального конца потока, так и из-за сетевого сбоя. Проверка `stream.Err()` обязательна.

## На собеседовании

В мониторинговых платформах (Яндекс Метрика, Prometheus push-agents) сбор метрик с сотен тысяч агентов использует Client Streaming. На интервью спрашивают: 'В чем преимущество Client Streaming перед отправкой 1000 отдельных POST-запросов?' Ответ: Одно TCP-соединение, однократное рукопожатие TLS/HTTP, отсутствие оверхеда на повторную передачу заголовков аутентификации и сжатие всего потока единым компрессором.
