## Теория

Выбор межсервисного и клиент-серверного протокола в enterprise-системах — одно из фундаментальных архитектурных решений. Нет универсального протокола: каждый оптимизирован под свой круг задач.

Сравнительная матрица протоколов:
1. **REST (OpenAPI/HTTP/JSON)**:
   - *Плюсы*: Общепринятый стандарт, нативная поддержка браузерами, кэширование HTTP/CDN, легко тестировать через curl.
   - *Минусы*: Текстовый оверхед JSON, ручная поддержка контрактов (OpenAPI часто отстает от кода), оверхед HTTP-заголовков.
2. **gRPC (HTTP/2 + Protobuf)**:
   - *Плюсы*: Бинарная сериализация Protobuf (в 5-10 раз быстрее и компактнее JSON), строгие контракты, двунаправленный стриминг, кодогенерация на 15+ языках.
   - *Минусы*: Не работает в браузере напрямую (требует Envoy), сложный дебаг (трафик не читается глазами), проблемы балансировки L4/L7 при длинных соединениях.
3. **ConnectRPC**:
   - *Плюсы*: Лучшее из обоих миров: строгие Protobuf-контракты, нативная работа в браузере без Envoy, поддержка одновременно 3 протоколов (gRPC, gRPC-Web, Connect) на одном порту.
   - *Минусы*: Менее зрелая экосистема по сравнению с классическим gRPC, меньше готовых сторонних плагинов.
4. **JSON-RPC 2.0**:
   - *Плюсы*: Ультрапростая спецификация, пакетные запросы (Batching) из коробки, идеален для WebSocket и очередей сообщений.
   - *Минусы*: Отсутствие встроенного кэширования HTTP GET, нет единого стандарта схемы (OpenRPC развит слабее Protobuf).
5. **GraphQL**:
   - *Плюсы*: Клиент сам определяет форму ответа (решение проблем Over-fetching / Under-fetching), единый эндпоинт для мобилок.
   - *Минусы*: Сложность защиты от DDoS (глубокие вложенные запросы), N+1 проблема в резолверах (требует DataLoader), высокий оверхед CPU при парсинге AST.

**`architecture_guide.md`**

```bash
# Гайдлайны выбора протокола в Enterprise архитектуре

1. **Межсервисное взаимодействие (Service-to-Service, East-West traffic)**:
   -> Выбор: **gRPC (Protobuf over HTTP/2)**
   -> Rationale: Минимальные задержки, бинарный формат, мультиплексирование TCP сокетов.

2. **Внешний публичный API для сторонних разработчиков (North-South)**:
   -> Выбор: **REST + OpenAPI 3.0**
   -> Rationale: Максимальная совместимость с любыми HTTP-клиентами, curl, Postman.

3. **Веб-приложения (BFF / Web Frontend -> Backend)**:
   -> Выбор: **ConnectRPC** (или gRPC-Web)
   -> Rationale: Типобезопасность Protobuf на клиенте без необходимости настройки Envoy Proxy.

4. **Мобильные клиенты со сложными динамическими экранами (iOS/Android)**:
   -> Выбор: **GraphQL**
   -> Rationale: Агрегация данных с нескольких сервисов за один сетевой запрос, экономия батареи и сотового трафика.

5. **Блокчейн-ноды, трейдинговые сокеты и терминалы**:
   -> Выбор: **JSON-RPC 2.0 over WebSocket**
   -> Rationale: Пакетный batching, полнодуплексные уведомления (subscriptions).
```

## Под капотом

Сравнение по накладным расходам CPU: при JSON-сериализации парсер вынужден проверять каждый байт на экранирование строк, разделители, пробелы и конвертировать ASCII-цифры в бинарные `float64/int64`. В Protobuf сериализация сводится к копированию бинарных смещений памяти и кодированию целых чисел через Varint (Variable-length quantity), что сокращает потребление инструкций процессора на порядки.

## Подводные камни

1. **Выбор GraphQL для чистого backend-to-backend**: Использование GraphQL между микросервисами — серьезная архитектурная ошибка. Оверхед на парсинг схемы и отсутствие бинарного транспорта превращают внутреннюю сеть в узкое горлышко.
2. **Игнорирование версионирования**: В REST разработчики часто ломают контракты сменой типов полей. В Protobuf/Connect обратная совместимость гарантируется правилами нумерации тегов полей (Field Tags).

## На собеседовании

На системном дизайне (System Design Interview) в Яндекс или Ozon соискателю часто дают кейс: 'Спроектируйте API для сервиса доставки заказов (курьерское мобильное приложение, веб-сайт покупателя, внутренний логистический маршрутизатор)'. Правильный ответ: Курьерское приложение и сайт общаются с BFF через Connect/REST, а BFF обращается к внутренним микросервисам маршрутизации через чистый gRPC с балансировкой через Service Mesh.
