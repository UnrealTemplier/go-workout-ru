# Полнодуплексный JSON-RPC поверх WebSocket соединения

## Условие

50. **JSON-RPC поверх WebSocket.**: Расширьте сервер: принимайте WebSocket-соединения и ожидайте JSON-RPC запросы в каждом сообщении. Ответ отправляйте в то же соединение. Клиент должен отправлять несколько запросов по одному соединению.

### Исходная формулировка

**JSON-RPC поверх WebSocket.**: Расширьте сервер: принимайте WebSocket-соединения и ожидайте JSON-RPC запросы в каждом сообщении. Ответ отправляйте в то же соединение. Клиент должен отправлять несколько запросов по одному соединению.

## Теория

При использовании HTTP/1.1 в JSON-RPC каждый вызов требует отдельного TCP-соединения или нового HTTP-запроса, что порождает накладные расходы на заголовки и задержки RTT. Для биржевых платформ, онлайн-игр и блокчейн-узлов идеальным транспортом выступает **WebSocket**.

Преимущества JSON-RPC поверх WebSocket:
1. **Полнодуплексный обмен (Full-duplex)**: Одно TCP-соединение удерживается открытым. И клиент, и сервер могут в любой момент инициировать отправку запроса или уведомления.
2. **Server-to-Client Notifications (Подписки)**: Сервер может отправлять клиенту асинхронные нотификации о событиях (например, `eth_subscription` о новом блоке или котировке акций) без поллинга.
3. **Мультиплексирование запросов**: Клиент отправляет 50 запросов подряд с разными `id`, а сервер отвечает на них по мере готовности в произвольном порядке. Клиент сопоставляет ответы по `id`.

В Go промышленная реализация использует `gorilla/websocket` или `coder/websocket` с потокобезопасной очередью записи через мьютекс или управляющий канал.

## Решение по шагам

1. Настройте апгрейд HTTP-соединения до WebSocket (`websocket.Upgrader`).
2. Запустите цикл чтения входящих текстовых сообщений из сокета.
3. Организуйте потокобезопасную запись (`conn.WriteJSON`) через защищенный мьютексом метод или выделенную горутину писателя.
4. Реализуйте регистрацию подписки клиента: при возникновении фонового события отправляйте клиенту Notification без поля `id`.

## Код решения

**`ws_rpc.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"sync"
	"time"

	"github.com/gorilla/websocket"
)

var upgrader = websocket.Upgrader{
	CheckOrigin: func(r *http.Request) bool { return true },
}

type WSMessage struct {
	JSONRPC string           `json:"jsonrpc"`
	Method  string           `json:"method,omitempty"`
	Params  json.RawMessage  `json:"params,omitempty"`
	Result  any              `json:"result,omitempty"`
	Error   any              `json:"error,omitempty"`
	ID      *json.RawMessage `json:"id,omitempty"`
}

type ClientSession struct {
	conn      *websocket.Conn
	writeMu   sync.Mutex
	subTicker *time.Ticker
	done      chan struct{}
}

func (c *ClientSession) Send(msg WSMessage) error {
	c.writeMu.Lock()
	defer c.writeMu.Unlock()
	return c.conn.WriteJSON(msg)
}

func handleWSRPC(w http.ResponseWriter, r *http.Request) {
	conn, err := upgrader.Upgrade(w, r, nil)
	if err != nil {
		http.Error(w, "Upgrade failed", http.StatusBadRequest)
		return
	}
	defer conn.Close()

	session := &ClientSession{
		conn: conn,
		done: make(chan struct{}),
	}
	defer close(session.done)

	for {
		_, payload, err := conn.ReadMessage()
		if err != nil {
			break
		}

		var req WSMessage
		if err := json.Unmarshal(payload, &req); err != nil {
			_ = session.Send(WSMessage{
				JSONRPC: "2.0",
				Error:   map[string]any{"code": -32700, "message": "Parse error"},
			})
			continue
		}

		// Обработка запросов
		switch req.Method {
		case "ping":
			_ = session.Send(WSMessage{
				JSONRPC: "2.0",
				Result:  "pong",
				ID:      req.ID,
			})
		case "subscribe.ticks":
			// Запуск потока серверных нотификаций
			go func() {
				ticker := time.NewTicker(1 * time.Second)
				defer ticker.Stop()
				for {
					select {
					case <-session.done:
						return
					case t := <-ticker.C:
						_ = session.Send(WSMessage{
							JSONRPC: "2.0",
							Method:  "tick.event",
							Params:  json.RawMessage(fmt.Sprintf(`{"time":"%s"}`, t.Format(time.RFC3339))),
							// ID не передается — это Server Notification!
						})
					}
				}
			}()
			_ = session.Send(WSMessage{
				JSONRPC: "2.0",
				Result:  "subscribed",
				ID:      req.ID,
			})
		default:
			_ = session.Send(WSMessage{
				JSONRPC: "2.0",
				Error:   map[string]any{"code": -32601, "message": "Method not found"},
				ID:      req.ID,
			})
		}
	}
}

func main() {
	http.HandleFunc("/ws", handleWSRPC)
	fmt.Println("WebSocket JSON-RPC 2.0 Server running on :8080/ws")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

WebSocket соединение не является потокобезопасным для параллельной записи. Вызов `conn.WriteMessage` или `conn.WriteJSON` из двух разных горутин одновременно приведет к гонке данных и панике рантайма (одновременное повреждение WebSocket фреймов). Поэтому сессия клиента обязана инкапсулировать `sync.Mutex` на операциях отправки либо использовать выделенный канал сообщений `chan WSMessage` с единственной горутиной-писателем.

## Подводные камни

1. **Concurrent Writes**: Самый распространенный баг новичков — параллельный вызов `WriteJSON` из горутины подписки и горутины обработки входящих RPC-ответов. Без мьютекса сервер падает с ошибкой `concurrent write to websocket connection`.
2. **Медленные клиенты (Slow Consumers)**: Если клиент перестал читать сокет, буфер TCP заполнится, и вызов `WriteJSON` заблокирует горутину навсегда. Обязательно устанавливайте `conn.SetWriteDeadline` перед каждой отправкой.

## На собеседовании

В торговых ядрах криптобирж и брокеров (Тинькофф Инвестиции, Bybit, Binance) клиентское API котировок построено на WebSocket JSON-RPC. Вопрос: 'Как масштабировать 500,000 WebSocket-подписок на кластер из 10 нод?' Ответ: Использовать Redis Pub/Sub или NATS для вещания тиков между нодами, а на каждой Go-ноде держать epoll-пул (библиотеки `gobwas/ws` или `netpoll`) для минимизации расхода горутин и памяти на открытые соединения.
