# Миграция с gRPC на Connect: сохранение обратной совместимости с legacy клиентами

## Условие

56. **Migration gRPC → Connect**: Переведите существующий gRPC сервер на Connect, сохранив compatibility с existing gRPC clients (Connect умеет говорить по gRPC protocol).

### Исходная формулировка

**Migration gRPC → Connect**: Переведите существующий gRPC сервер на Connect, сохранив compatibility с existing gRPC clients (Connect умеет говорить по gRPC protocol).

## Теория

При модернизации существующей микросервисной инфраструктуры компании часто сталкиваются с дилеммой: перевод gRPC-сервера на Connect открывает прямую работу с браузерами, однако сотни существующих backend-клиентов продолжают общаться по 'классическому' gRPC через `google.golang.org/grpc`.

Ключевое преимущество **ConnectRPC**:
Библиотека `connectrpc.com/connect` поддерживает **3 протокола одновременно на одном и том же порту**:
1. **gRPC Protocol**: Стандартный gRPC поверх HTTP/2 (`application/grpc`), полностью совместимый с существующими клиентами на Go, Java, C++, Python.
2. **gRPC-Web Protocol**: Для веб-клиентов и Envoy (`application/grpc-web`).
3. **Connect Protocol**: Легковесный протокол для современных браузеров и мобилок (`application/connect+json` или `application/connect+proto`).

Сервер определяет протокол клиента динамически на основе заголовка `Content-Type`. Благодаря этому миграция происходит абсолютно бесшовно без простоя и без необходимости поднимать второй порт или прокси.

## Решение по шагам

1. Возьмите существующий сервис `OrderService`.
2. Реализуйте интерфейс `OrderServiceHandler` из пакета `connect`.
3. Смонтируйте сгенерированный Connect-хэндлер на стандартный `http.NewServeMux()`.
4. Оберните сервер в `golang.org/x/net/http2/h2c` для поддержки нешифрованного HTTP/2 (Cleartext h2c), необходимого стандартным gRPC-клиентам.
5. Проверьте работоспособность как через стандартный gRPC-клиент (`grpc.Dial`), так и через браузерный `curl`.

## Код решения

**`migration_server.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"

	"connectrpc.com/connect"
	"golang.org/x/net/http2"
	"golang.org/x/net/http2/h2c"
)

type PingRequest struct {
	Message string `json:"message"`
}

type PingResponse struct {
	Reply string `json:"reply"`
}

// PingServer реализует Connect RPC метод
type PingServer struct{}

func (s *PingServer) Ping(
	ctx context.Context,
	req *connect.Request[PingRequest],
) (*connect.Response[PingResponse], error) {
	// Определение протокола, через который пришел клиент
	protocol := req.Peer().Protocol
	fmt.Printf("Получен вызов Ping через протокол: %s, сообщение: %s\n", protocol, req.Msg.Message)

	res := connect.NewResponse(&PingResponse{
		Reply: fmt.Sprintf("Echo [%s]: %s", protocol, req.Msg.Message),
	})
	return res, nil
}

func main() {
	mux := http.NewServeMux()

	// В продакшене: path, handler := pingv1connect.NewPingServiceHandler(&PingServer{})
	// mux.Handle(path, handler)
	mux.HandleFunc("/ping.v1.PingService/Ping", func(w http.ResponseWriter, r *http.Request) {
		ct := r.Header.Get("Content-Type")
		fmt.Printf("Request Content-Type: %s, Protocol: %s\n", ct, r.Proto)

		// Connect сервер автоматически понимает:
		// 1. application/grpc -> отвечает в стандарте gRPC
		// 2. application/connect+json -> отвечает по Connect protocol
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(`{"reply":"Поддержка всех клиентов обеспечена!"}`))
	})

	// Оборачиваем в h2c (HTTP/2 Cleartext), чтобы классический gRPC мог работать без TLS
	h2cHandler := h2c.NewHandler(mux, &http2.Server{})

	server := &http.Server{
		Addr:    ":8080",
		Handler: h2cHandler,
	}

	fmt.Println("Мультипротокольный сервер (gRPC + Connect) запущен на :8080")
	_ = server.ListenAndServe()
}
```

## Под капотом

Классический gRPC клиент жестко требует наличие HTTP/2. Если TLS не используется (внутренняя сеть Kubernetes), клиент инициирует соединение через HTTP/2 Prior Knowledge (сразу отправляет фрейм `PRI * HTTP/2.0`). Стандартный Go `http.Server` по умолчанию поддерживает HTTP/2 только поверх TLS (HTTPS). Обертка `h2c.NewHandler` перехватывает стартовый HTTP/2 фрейм в открытом TCP сокете и перенаправляет поток во внутренний обработчик HTTP/2, делая сервер совместимым с `grpc.Dial(..., grpc.WithInsecure())`.

## Подводные камни

1. **Забытый h2c wrapper**: Если запустить `http.ListenAndServe(":8080", mux)` без `h2c`, обычный gRPC клиент упадет с ошибкой `transport: error while dialing: http2: Transport: cannot retry err [http2: no cached connection]`.
2. **Перехват заголовков метаданных**: В классическом gRPC заголовки извлекаются через `metadata.FromIncomingContext(ctx)`. В Connect заголовки читаются напрямую из `req.Header()`. При миграции старого кода интерцепторы нужно обновить.

## На собеседовании

В финтех-платформах с тысячами микросервисов одновременный апгрейд всех клиентов невозможен (Zero-downtime migration). На собеседовании спросят: 'Как обновить 200 сервисов на новый протокол без поломки существующих потребителей?' Ответ: Бэкенд обновляется первым на Connect с поддержкой протоколов `gRPC` + `Connect` на том же порту. Затем клиенты постепенно обновляются сервис за сервисом в течение нескольких кварталов.
