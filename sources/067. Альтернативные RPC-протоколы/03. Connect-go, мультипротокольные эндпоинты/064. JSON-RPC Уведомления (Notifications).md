# JSON-RPC Уведомления (Notifications): реализация асинхронного паттерна fire-and-forget

## Условие

64. **[JSON-RPC Уведомления]**: Если в запросе нет поля `id`, это уведомление (fire-and-forget). Сервер должен выполнить метод, но вернуть HTTP-статус `204 No Content` без тела.

### Исходная формулировка

**[JSON-RPC Уведомления]**: Если в запросе нет поля `id`, это уведомление (fire-and-forget). Сервер должен выполнить метод, но вернуть HTTP-статус `204 No Content` без тела.

## Теория

По спецификации JSON-RPC 2.0 сообщение является **Уведомлением (Notification)** тогда и только тогда, когда в объекте запроса **отсутствует поле `id`**.

Семантика уведомлений:
1. Клиент уведомляет сервер о событии (например, телеметрия, клик пользователя, лог, аудит) и явно заявляет, что не ожидает ответа.
2. Сервер **не имеет права** отправлять ответ клиенту (ни положительный результат, ни ошибку).
3. При использовании HTTP-транспорта сервер обязан возвратить пустой ответ с кодом `204 No Content` или `202 Accepted`.
4. Поскольку клиент не ждет ответа, обработка уведомления на сервере должна производиться асинхронно через воркер-пул, чтобы не блокировать сетевой сокет.

## Решение по шагам

1. Реализуйте проверку наличия поля `id` в JSON-структуре запроса.
2. Создайте очередь задач (`chan NotificationTask`) и пул фоновых горутин-воркеров.
3. При получении уведомления отправьте задачу в канал воркеров без ожидания ее выполнения.
4. Верните HTTP статус `204 No Content`.
5. Добавьте graceful shutdown для корректного дожимания очереди нотификаций при остановке сервера.

## Код решения

**`notifications_server.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"sync"
	"time"
)

type RPCNotification struct {
	JSONRPC string          `json:"jsonrpc"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params,omitempty"`
	ID      *json.RawMessage `json:"id,omitempty"` // nil для Notification
}

type NotificationQueue struct {
	tasks chan RPCNotification
	wg    sync.WaitGroup
}

func NewNotificationQueue(workers, bufferSize int) *NotificationQueue {
	q := &NotificationQueue{
		tasks: make(chan RPCNotification, bufferSize),
	}
	for i := 0; i < workers; i++ {
		q.wg.Add(1)
		go q.worker(i)
	}
	return q
}

func (q *NotificationQueue) worker(id int) {
	defer q.wg.Done()
	for task := range q.tasks {
		// Асинхронная обработка (запись в аналитическую БД, Kafka и т.д.)
		fmt.Printf("[Worker %d] Обработано уведомление: %s, params: %s\n", id, task.Method, string(task.Params))
		time.Sleep(50 * time.Millisecond)
	}
}

func (q *NotificationQueue) Submit(task RPCNotification) bool {
	select {
	case q.tasks <- task:
		return true
	default:
		// Очередь переполнена (Backpressure)
		return false
	}
}

func (q *NotificationQueue) Shutdown() {
	close(q.tasks)
	q.wg.Wait()
}

func main() {
	queue := NewNotificationQueue(4, 1000)
	defer queue.Shutdown()

	http.HandleFunc("/rpc", func(w http.ResponseWriter, r *http.Request) {
		body, _ := io.ReadAll(r.Body)
		var req RPCNotification
		_ = json.Unmarshal(body, &req)

		if req.ID == nil {
			// Это Notification!
			if ok := queue.Submit(req); !ok {
				http.Error(w, "Queue Overloaded", http.StatusServiceUnavailable)
				return
			}
			w.WriteHeader(http.StatusNoContent) // 204 No Content
			return
		}

		// Если ID есть — это обычный запрос (требует ответа)
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(fmt.Sprintf(`{"jsonrpc":"2.0","result":"ok","id":%s}`, string(*req.ID))))
	})

	fmt.Println("Notification Server running on :8080")
}
```

ℹ️ Асинхронная очередь обработки fire-and-forget уведомлений с пулом воркеров

## Под капотом

Если входящий JSON содержит `"id": null`, это считается валидным `Request`, а не `Notification`. Разработчики часто путают эти состояния. Только полное физическое отсутствие ключа `"id"` в JSON-объекте специфицирует уведомление. Для этого в Go поле обязано быть объявлено как указатель `ID *json.RawMessage` с тегом `omitempty`.

## Подводные камни

1. **Блокировка HTTP горутины**: Выполнение тяжелой операции прямо в обработчике Notification нивелирует преимущества fire-and-forget паттерна.
2. **Неконтролируемый рост очереди (OOM)**: Небуферизированный или бесконечный канал может привести к исчерпанию оперативной памяти при всплеске трафика. Обязательно используйте ограниченный буфер и отбрасывание/shedding при перегрузке.

## На собеседовании

В мобильных играх и рекламных сетях (Яндекс Директ, VK Реклама) отправка событий скролла и показов баннеров строится на fire-and-forget нотификациях. Вопрос: 'Как не потерять нотификации при перезагрузке инстанса сервиса?' Ответ: Использовать ring buffer в памяти с периодическим сбросом на диск (Write-Ahead Log) либо моментальный проброс в Kafka topic до возврата HTTP 204.
