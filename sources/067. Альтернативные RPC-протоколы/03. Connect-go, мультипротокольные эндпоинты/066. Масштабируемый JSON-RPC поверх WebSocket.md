### Исходная формулировка

**JSON-RPC поверх WebSockets**: Сделай WebSocket-соединение. Внутри соединения обменивайтесь сообщениями строго в формате JSON-RPC 2.0. Это идеальный вариант для игр или тяжелых SPA, где нужен двунаправленный RPC без сложной настройки gRPC.

## Теория

При проектировании высоконагруженного WebSocket-сервера для JSON-RPC ключевой задачей является корректное управление жизненным циклом соединений, обработка разрывов сети и маршрутизация ответов на запросы с учетом уникальных `id`.

Архитектура промышленного сокет-сервера:
1. **Hub / Connection Manager**: Хранилище активных клиентских сессий (`sync.RWMutex` или `sync.Map`).
2. **Per-Connection Goroutines**: Каждое соединение обслуживается ровно двумя горутинами:
   - `Reader Goroutine`: непрерывно считывает JSON-пакеты из сокета и передает в диспетчер.
   - `Writer Goroutine`: забирает готовые ответы из внутреннего буферизированного канала `send chan []byte` и пишет в сокет с установкой `WriteDeadline`.
3. **Heartbeat (Ping/Pong)**: Периодическая проверка жизнеспособности соединения для сброса 'мертвых' сокетов при потере Wi-Fi/4G сети клиентом.

## Решение по шагам

1. Опишите структуру `ClientSession` с каналом исходящих сообщений.
2. Реализуйте безопасный цикл `readPump` и `writePump` с настройкой `SetReadDeadline` и PongHandler.
3. Напишите роутер методов для сокет-запросов (`subscribe`, `unsubscribe`, `call`).
4. Обеспечьте гарантированное закрытие канала и очистку сессии из хаба при выходе из `readPump`.

## Код решения

**`ws_hub.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"sync"
	"time"

	"github.com/gorilla/websocket"
)

const (
	writeWait  = 5 * time.Second
	pongWait   = 60 * time.Second
	pingPeriod = (pongWait * 9) / 10
)

var upgrader = websocket.Upgrader{
	CheckOrigin: func(r *http.Request) bool { return true },
}

type Client struct {
	hub  *Hub
	conn *websocket.Conn
	send chan []byte
}

type Hub struct {
	clients map[*Client]bool
	mu      sync.RWMutex
}

func NewHub() *Hub {
	return &Hub{clients: make(map[*Client]bool)}
}

func (h *Hub) Register(c *Client) {
	h.mu.Lock()
	h.clients[c] = true
	h.mu.Unlock()
}

func (h *Hub) Unregister(c *Client) {
	h.mu.Lock()
	if _, ok := h.clients[c]; ok {
		delete(h.clients, c)
		close(c.send)
	}
	h.mu.Unlock()
}

func (c *Client) writePump() {
	ticker := time.NewTicker(pingPeriod)
	defer func() {
		ticker.Stop()
		c.conn.Close()
	}()

	for {
		select {
		case message, ok := <-c.send:
			_ = c.conn.SetWriteDeadline(time.Now().Add(writeWait))
			if !ok {
				_ = c.conn.WriteMessage(websocket.CloseMessage, []byte{})
				return
			}
			w, err := c.conn.NextWriter(websocket.TextMessage)
			if err != nil {
				return
			}
			_, _ = w.Write(message)
			if err := w.Close(); err != nil {
				return
			}
		case <-ticker.C:
			_ = c.conn.SetWriteDeadline(time.Now().Add(writeWait))
			if err := c.conn.WriteMessage(websocket.PingMessage, nil); err != nil {
				return
			}
		}
	}
}

func (c *Client) readPump() {
	defer func() {
		c.hub.Unregister(c)
		c.conn.Close()
	}()

	c.conn.SetReadLimit(512 * 1024)
	_ = c.conn.SetReadDeadline(time.Now().Add(pongWait))
	c.conn.SetPongHandler(func(string) error {
		_ = c.conn.SetReadDeadline(time.Now().Add(pongWait))
		return nil
	})

	for {
		_, msg, err := c.conn.ReadMessage()
		if err != nil {
			break
		}

		// Эхо-ответ JSON-RPC
		reply := fmt.Sprintf(`{"jsonrpc":"2.0","result":"ack","raw":%s}`, string(msg))
		c.send <- []byte(reply)
	}
}

func main() {
	hub := NewHub()
	http.HandleFunc("/ws/rpc", func(w http.ResponseWriter, r *http.Request) {
		conn, err := upgrader.Upgrade(w, r, nil)
		if err != nil {
			return
		}
		client := &Client{hub: hub, conn: conn, send: make(chan []byte, 256)}
		hub.Register(client)
		go client.writePump()
		go client.readPump()
	})
	fmt.Println("Production WebSocket JSON-RPC Hub listening on :8080/ws/rpc")
}
```

ℹ️ Масштабируемый WebSocket Hub с Ping/Pong и разделенными горутинами read/write

## Под капотом

Схема с выделенными `readPump` и `writePump` горутинами является каноническим паттерном Gorilla WebSocket в Go. Она предотвращает блокировку системного потока ОС при записи в медленный сокет: канал `send chan []byte` выступает буфером между быстрой бизнес-логикой и медленной сетью. Если буфер канала переполняется, клиент признается зависшим (Slow Consumer) и принудительно отключается.

## Подводные камни

1. **Паника отправки в закрытый канал**: Если клиент отключается, а фоновый воркер пытается отправить уведомление в `c.send`, Go выдает `panic: send on closed channel`. Всегда синхронизируйте закрытие канала через мьютекс хаба или атомики.
2. **Отсутствие Ping/Pong таймаутов**: Без пингов TCP-сокеты 'зависают' в таблице соединений ядра Linux навсегда при потере связи клиентом (Half-Open connection problem).

## На собеседовании

В торговых терминалах брокеров (Тинькофф Инвестиции, БКС) сокеты передают тысячи котировок в секунду. Вопрос: 'Как оптимизировать аллокации памяти при рассылке одного и того же JSON-RPC уведомления 100,000 подписчиков?' Ответ: Сериализовать JSON ровно один раз в общий `[]byte` срез и рассылать указатель на слайс (или сам слайс байт, который передается заголовком 24 байта) во все каналы клиентов без повторного маршалинга.
