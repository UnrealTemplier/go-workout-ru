# Пакетные запросы (Batching) в JSON-RPC 2.0: устранение сетевой проблемы N+1

## Условие

65. **Пакетные запросы (Batching)**: Уникальная фича JSON-RPC. Если клиент присылает массив объектов-запросов, сервер должен выполнить их (можно конкурентно) и вернуть массив ответов в одном HTTP-ответе. Реализуй этот функционал.

### Исходная формулировка

**Пакетные запросы (Batching)**: Уникальная фича JSON-RPC. Если клиент присылает массив объектов-запросов, сервер должен выполнить их (можно конкурентно) и вернуть массив ответов в одном HTTP-ответе. Реализуй этот функционал.

## Теория

Одной из мощнейших и уникальных особенностей спецификации **JSON-RPC 2.0** является встроенная поддержка **пакетных запросов (Batch Requests)**.

Механика Batching:
1. Клиент отправляет один HTTP POST запрос, в теле которого находится **массив** JSON-объектов `[ {req1}, {req2}, {notification1}, {req3} ]`.
2. Сервер обрабатывает запросы (последовательно или параллельно в пуле горутин).
3. Сервер формирует ответ в виде **массива** объектов `[ {resp1}, {resp2}, {resp3} ]`.
4. На нотификации внутри батча ответы в итоговый массив не включаются. Если весь батч состоял только из нотификаций, сервер не возвращает ничего (HTTP 204).
5. Порядок ответов в результирующем массиве **не обязан совпадать** с порядком запросов — клиент сопоставляет ответы исключительно по полю `id`.

Это решает проблему N+1 сетевых вызовов: 100 RPC-вызовов упаковываются в 1 сетевой пакет round-trip!

## Решение по шагам

1. Реализуйте функцию детектирования: начинается ли полезная нагрузка с символа `[` (массив/батч) или `{` (одиночный вызов).
2. Для пакетного запроса распарсите срез `[]RPCRequest`.
3. Запустите конкурентную обработку каждого запроса через `sync.WaitGroup`.
4. Соберите результаты запросов (игнорируя нотификации) в общий срез ответов.
5. Напишите тест с батчем из 3 запросов и 1 нотификации.

## Код решения

**`batch_server.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"sync"
)

type BatchItemRequest struct {
	JSONRPC string           `json:"jsonrpc"`
	Method  string           `json:"method"`
	Params  json.RawMessage  `json:"params,omitempty"`
	ID      *json.RawMessage `json:"id,omitempty"`
}

type BatchItemResponse struct {
	JSONRPC string           `json:"jsonrpc"`
	Result  any              `json:"result,omitempty"`
	Error   any              `json:"error,omitempty"`
	ID      *json.RawMessage `json:"id"`
}

func handleBatchRPC(w http.ResponseWriter, r *http.Request) {
	body, err := io.ReadAll(r.Body)
	if err != nil {
		http.Error(w, "Read error", http.StatusBadRequest)
		return
	}

	trimmed := bytes.TrimSpace(body)
	if len(trimmed) == 0 {
		return
	}

	// Проверяем: одиночный запрос или батч
	if trimmed[0] == '[' {
		// Обработка Batch
		var requests []BatchItemRequest
		if err := json.Unmarshal(trimmed, &requests); err != nil {
			w.Header().Set("Content-Type", "application/json")
			_, _ = w.Write([]byte(`{"jsonrpc":"2.0","error":{"code":-32700,"message":"Parse error"},"id":null}`))
			return
		}

		if len(requests) == 0 {
			w.Header().Set("Content-Type", "application/json")
			_, _ = w.Write([]byte(`{"jsonrpc":"2.0","error":{"code":-32600,"message":"Invalid Request: empty batch"},"id":null}`))
			return
		}

		var (
			mu        sync.Mutex
			responses []BatchItemResponse
			wg        sync.WaitGroup
		)

		for _, req := range requests {
			// Если ID отсутствует — это Notification, на него ответ не формируется
			if req.ID == nil {
				continue
			}

			wg.Add(1)
			go func(item BatchItemRequest) {
				defer wg.Done()
				// Бизнес-обработка элемента
				resp := BatchItemResponse{
					JSONRPC: "2.0",
					Result:  fmt.Sprintf("Результат выполнения %s", item.Method),
					ID:      item.ID,
				}
				mu.Lock()
				responses = append(responses, resp)
				mu.Unlock()
			}(req)
		}

		wg.Wait()

		// Если весь батч состоял только из Notifications — ничего не возвращаем
		if len(responses) == 0 {
			w.WriteHeader(http.StatusNoContent)
			return
		}

		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(responses)
		return
	}

	// Одиночный запрос
	w.Header().Set("Content-Type", "application/json")
	_, _ = w.Write([]byte(`{"jsonrpc":"2.0","result":"single success","id":1}`))
}

func main() {
	http.HandleFunc("/rpc", handleBatchRPC)
	fmt.Println("Batch JSON-RPC 2.0 Server listening on :8080/rpc")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

Параллельное исполнение батча требует осторожности с разделяемыми ресурсами. Если методы в батче мутируют одни и те же данные в БД (например, батч переводов средств), параллельный запуск может привести к дедлокам в транзакциях Postgres. В высоконагруженных системах батчи делятся на 'read-only' (запускаются конкурентно через горутины) и 'write' (исполняются строго последовательно).

## Подводные камни

1. **Пустой массив `[]`**: Клиент присылает `[]`. По спецификации сервер обязан ответить объектом с ошибкой `-32600 Invalid Request`, а не пустым массивом.
2. **Лимит на размер батча**: Отсутствие ограничения на размер массива позволяет злоумышленнику прислать батч из 100,000 запросов и положить сервис по памяти (DoS). Всегда ограничивайте длину батча (например, максимум 100 элементов).

## На собеседовании

В Ethereum нодах (Geth, Erigon) фронтенды кошельков (MetaMask) запрашивают балансы сразу 50 токенов через Batch JSON-RPC. Вопрос на системном дизайне: 'Как защитить ноду от взрывного роста потребления ресурсов при пакетных запросах?' Ответ: Ограничить максимальный размер массива `max_batch_size = 50`, вычислять совокупную стоимость вызовов (gas limit / CPU limit) перед запуском и возвращать `-32005 Limit exceeded` при превышении квоты.
