## Теория

Спецификация **JSON-RPC 2.0** определяет ультралегковесный протокол удаленного вызова процедур поверх любого транспортного уровня (HTTP POST, TCP, WebSocket, Unix Domain Sockets). В отличие от REST, где семантика операций размазана по HTTP-глаголам (GET, POST, PUT, DELETE) и статус-кодам (200, 201, 204, 400), в JSON-RPC 2.0 транспорт абстрагирован: тело сообщения всегда оформлено в виде JSON-объекта со строгой схемой.

Спецификация регламентирует ровно четыре типа сообщений:
1. **Request (Запрос)**: Обязательно содержит поля `"jsonrpc": "2.0"`, `"method": string`, `"params"` (структурированный объект либо позиционный массив), и уникальный идентификатор `"id"` (целое число, строка или null). Сервер обязан вернуть парный ответ с тем же `id`.
2. **Response success (Успешный ответ)**: Содержит `"jsonrpc": "2.0"`, `"result": any`, и исходный `"id"`. Поле `"error"` обязано отсутствовать.
3. **Response error (Ответ с ошибкой)**: Содержит `"jsonrpc": "2.0"`, `"error": {"code": int, "message": string, "data"?: any}`, и исходный `"id"` (или `null`, если id запроса не удалось распарсить). Поле `"result"` обязано отсутствовать.
4. **Notification (Уведомление)**: Запрос, в котором **полностью отсутствует** поле `"id"`. Клиент явно заявляет, что не заинтересован в получении ответа (fire-and-forget). Сервер **не имеет права** возвращать никакого ответа (в HTTP-транспорте возвращается пустой `204 No Content`).

В Go строгая типизация этих 4 структур реализуется через `json.RawMessage` для полей `params` и `result`, что предотвращает лишний маршалинг до определения целевого метода.

## Код решения

**`server.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"io"
	"net/http"
)

// Request представляет запрос JSON-RPC 2.0. Если ID == nil, это Notification.
type Request struct {
	JSONRPC string           `json:"jsonrpc"`
	Method  string           `json:"method"`
	Params  json.RawMessage  `json:"params,omitempty"`
	ID      *json.RawMessage `json:"id,omitempty"`
}

// Response представляет результат или ошибку JSON-RPC 2.0.
type Response struct {
	JSONRPC string           `json:"jsonrpc"`
	Result  any              `json:"result,omitempty"`
	Error   *RPCError        `json:"error,omitempty"`
	ID      *json.RawMessage `json:"id"`
}

// RPCError описывает ошибку по спецификации JSON-RPC 2.0.
type RPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data,omitempty"`
}

const (
	ErrCodeParse          = -32700
	ErrCodeInvalidRequest = -32600
	ErrCodeMethodNotFound = -32601
	ErrCodeInvalidParams  = -32602
	ErrCodeInternal       = -32603
)

func handleJSONRPC(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}

	body, err := io.ReadAll(r.Body)
	if err != nil {
		writeError(w, nil, ErrCodeParse, "Parse error")
		return
	}

	var req Request
	if err := json.Unmarshal(body, &req); err != nil || req.JSONRPC != "2.0" || req.Method == "" {
		writeError(w, nil, ErrCodeInvalidRequest, "Invalid Request")
		return
	}

	// Проверка на Notification (поле ID отсутствует)
	isNotification := (req.ID == nil)

	// Роутинг методов
	switch req.Method {
	case "add":
		var args []float64
		if err := json.Unmarshal(req.Params, &args); err != nil || len(args) != 2 {
			if !isNotification {
				writeError(w, req.ID, ErrCodeInvalidParams, "Invalid params: expected [a, b]")
			}
			return
		}
		res := args[0] + args[1]
		if !isNotification {
			writeSuccess(w, req.ID, res)
		} else {
			w.WriteHeader(http.StatusNoContent)
		}
	default:
		if !isNotification {
			writeError(w, req.ID, ErrCodeMethodNotFound, fmt.Sprintf("Method '%s' not found", req.Method))
		} else {
			w.WriteHeader(http.StatusNoContent)
		}
	}
}

func writeSuccess(w http.ResponseWriter, id *json.RawMessage, res any) {
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(Response{
		JSONRPC: "2.0",
		Result:  res,
		ID:      id,
	})
}

func writeError(w http.ResponseWriter, id *json.RawMessage, code int, msg string) {
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(Response{
		JSONRPC: "2.0",
		Error:   &RPCError{Code: code, Message: msg},
		ID:      id,
	})
}

func main() {
	http.HandleFunc("/rpc", handleJSONRPC)
	fmt.Println("JSON-RPC 2.0 Server listening on :8080/rpc")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`Терминал`**

```bash
# 1. Request -> Response success
curl -s -X POST http://localhost:8080/rpc \
  -d '{"jsonrpc":"2.0","method":"add","params":[10,25],"id":1}'
# {"jsonrpc":"2.0","result":35,"id":1}

# 2. Request -> Response error (метод не найден)
curl -s -X POST http://localhost:8080/rpc \
  -d '{"jsonrpc":"2.0","method":"subtract","params":[10,5],"id":2}'
# {"jsonrpc":"2.0","error":{"code":-32601,"message":"Method 'subtract' not found"},"id":2}

# 3. Notification (без поля id) -> HTTP 204 No Content
curl -i -s -X POST http://localhost:8080/rpc \
  -d '{"jsonrpc":"2.0","method":"add","params":[1,2]}'
# HTTP/1.1 204 No Content
```

## Под капотом

В спецификации JSON-RPC 2.0 поле `id` может быть строкой, числом или `null`. Использование `*json.RawMessage` позволяет сохранить исходное байтовое представление идентификатора без нежелательного приведения типов (например, float64 вместо uint64 в json.Unmarshal(any)). Если входящее поле `id` равно JSON-значению `null`, то `req.ID` не равен `nil`, но указывает на срез байт `[]byte("null")` — спецификация требует в таком случае вернуть в ответе `"id": null`. Если же поле `id` отсутствует вовсе в JSON-объекте, Go оставит указатель `*json.RawMessage` равным `nil`, что однозначно идентифицирует Notification.

## Подводные камни

1. **Возврат ответа на Notification**: Самая грубая ошибка при реализации JSON-RPC 2.0 — отправка любого JSON-тела на Notification. Спецификация прямо запрещает отвечать даже на ошибки валидации, если поле `id` отсутствовало.
2. **Путаница с `id: 0` и `id: ""`**: Использование примитивов `int` или `string` в Go приводит к тому, что значение по умолчанию (`0` или `""`) может быть ложно принято за отсутствующий ID при `omitempty`. Указатель `*json.RawMessage` исключает этот баг.

## На собеседовании

В Ethereum JSON-RPC API (Geth/Nethermind) абсолютно все запросы к блокчейну (eth_getBlockByNumber, eth_call, eth_sendRawTransaction) построены на JSON-RPC 2.0. На собеседованиях в Web3 и HighLoad Финтех часто спрашивают: 'Как обработать миллионы нотификаций без утечки дескрипторов соединений?' Ответ: Notification обрабатывается асинхронно в воркер-пуле, а HTTP-ответ `204` возвращается немедленно без удержания сокета клиента.
