# Connect vs tRPC: Сравнение Protobuf-first и TypeScript-first подходов

## Условие

54. **Connect vs tRPC:**
    * Connect: Protobuf-first, multi-language, code-gen из .proto
    * tRPC: TypeScript-first, end-to-end type safety без code-gen
    Connect для multi-language backends, tRPC для full-stack TypeScript.

## Теория

С ростом популярности монорепозиториев на TypeScript и стека Next.js возникли два противоборствующих лагеря проектирования сквозных типобезопасных API:
1. **tRPC (TypeScript-first)**:
   - Модель строится непосредственно в коде TypeScript (схема Zod/Yup/Valibot).
   - Клиент и сервер живут в одном TS-монорепозитории.
   - Нулевая кодогенерация: типы выводятся автоматически компилятором TS (`AppRouter`).
   - *Ограничение*: Жесткая привязка к Node.js/TypeScript. Бэкенд на Go, Rust или Python физически не может быть частью tRPC-схемы без сложных костылей.
2. **ConnectRPC (Protobuf-first)**:
   - Контракт описывается на нейтральном языке `.proto`.
   - Поддерживает полиглотную экосистему: бэкенд на Go, микросервис машинного обучения на Python, веб-клиент на TypeScript, мобилки на Swift/Kotlin.
   - Автоматическая кодогенерация клиентских SDK для любой платформы.

Для enterprise-разработки (где бэкенд пишется на Go ради производительности и низкого потребления памяти) Connect является безальтернативным лидером, объединяя простоту tRPC для фронтендеров с мощью Go на бэкенде.

## Решение по шагам

1. Проанализируйте различия в цикле разработки (developer experience) между tRPC и Connect.
2. Создайте proto-файл для Connect сервиса управления задачами.
3. Реализуйте Go-бэкенд на Connect с валидацией входных данных.
4. Продемонстрируйте, как TypeScript-фронтенд потребляет этот сервис с 100% type safety.

```bash
# Архитектурное сравнение: Connect vs tRPC

| Критерий | tRPC | ConnectRPC |
| :--- | :--- | :--- |
| **Философия** | TypeScript-first | Contract-first (Protobuf) |
| **Языки бэкенда** | Только Node.js/Bun | Go, Java, Python, Node.js, Rust |
| **Клиенты** | Только TypeScript/JS | TS, Go, Swift, Kotlin, Python, Dart |
| **Кодогенерация** | Отсутствует (TS inference) | Требуется (`buf generate` / `protoc`) |
| **Сериализация** | JSON (через superjson) | Protobuf (бинарный) или JSON |
| **Стриминг** | Ограничен (SSE экспериментально) | Нативный Server/Client/Bidi streaming |
| **Enterprise масштабируемость** | Низкая (привязана к Node.js) | Высокая (интеграция в Service Mesh) |
```

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"net/http"

	"connectrpc.com/connect"
)

type CreateTaskReq struct {
	Title       string `json:"title"`
	AssigneeID  string `json:"assignee_id"`
	Priority    int    `json:"priority"`
}

type TaskResponse struct {
	TaskID    string `json:"task_id"`
	CreatedAt int64  `json:"created_at"`
	Status    string `json:"status"`
}

type TaskServer struct{}

func (s *TaskServer) CreateTask(
	ctx context.Context,
	req *connect.Request[CreateTaskReq],
) (*connect.Response[TaskResponse], error) {
	// Валидация входных данных на бэкенде Go
	if req.Msg.Title == "" {
		return nil, connect.NewError(connect.CodeInvalidArgument, errors.New("название задачи не может быть пустым"))
	}
	if req.Msg.Priority < 1 || req.Msg.Priority > 5 {
		return nil, connect.NewError(connect.CodeInvalidArgument, errors.New("приоритет должен быть от 1 до 5"))
	}

	res := connect.NewResponse(&TaskResponse{
		TaskID:    "task_abc_123",
		CreatedAt: 1772839200,
		Status:    "PENDING",
	})
	return res, nil
}

func main() {
	mux := http.NewServeMux()
	// Эмуляция Connect RPC маршрута
	mux.HandleFunc("/task.v1.TaskService/CreateTask", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(`{"task_id":"task_abc_123","created_at":1772839200,"status":"PENDING"}`))
	})
	fmt.Println("Connect Task Service listening on :8080")
	_ = http.ListenAndServe(":8080", mux)
}
```

## Под капотом

tRPC базируется на TypeScript Abstract Syntax Tree и выводе типов компилятором `tsc`. При росте проекта свыше 500 эндпоинтов компиляция TypeScript в редакторе (Language Server) начинает тормозить из-за гигантских рекурсивных типов роутера. ConnectRPC компилирует прото-файлы в изолированные `.d.ts` файлы за миллисекунды через `buf`, поэтому скорость работы IDE остается мгновенной независимо от размера кодовой базы.

## Подводные камни

1. **Попытка переписать Go-сервисы на Node.js ради tRPC**: Катастрофическая ошибка команд, когда бэкенд переписывают на JavaScript только ради 'удобства типов на фронтенде'. Переход на Connect позволяет сохранить Go-бэкенд и получить идентичный Developer Experience.
2. **Сложности версионирования в tRPC**: В tRPC невозможно иметь двух разных клиентов с разными версиями API без форка роутеров. В Protobuf версионирование по пакетам (`task.v1`, `task.v2`) встроено в архитектуру.

## На собеседовании

В компаниях с микросервисной архитектурой (VK, Wildberries) монорепозитории содержат десятки языков. Вопрос на интервью: 'Почему мы не используем tRPC в нашем стеке Go + React?' Ответ: tRPC замыкает инфраструктуру на Node.js бэкенде. Для распределенной системы с сотнями сервисов на Go, C++ и Python необходим единый контрактный язык (IDL) — Protocol Buffers в связке с Connect или gRPC.
