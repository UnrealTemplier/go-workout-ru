## Теория

**Server Streaming RPC** — паттерн взаимодействия в gRPC, при котором клиент отправляет ровно один запрос, а сервер в ответ возвращает непрерывный поток сообщений. Соединение удерживается открытым до тех пор, пока сервер не завершит метод (возврат `nil` или ошибки) либо клиент не прервет контекст (`ctx.Done()`).

Сценарии применения:
- Потоковая доставка событий и уведомлений (Notification Center).
- Чтение больших дампов данных или логов из хранилища чанками (предотвращает Out-of-Memory на стороне клиента и сервера).
- Котировки биржевых цен в реальном времени.

На транспортном уровне HTTP/2 серверный стриминг реализуется передачей одного фрейма `HEADERS` в начале, последующей чередой фреймов `DATA` с префиксом длины каждого Protobuf-сообщения, и финального фрейма `HEADERS` с трейлерами (`grpc-status: 0`).

## Решение по шагам

1. Создайте интерфейс потока `NotificationService_StreamNotificationsServer`.
2. Реализуйте метод `StreamNotifications`: считывайте события из очереди и отправляйте их через `stream.Send()`.
3. Обязательно слушайте `stream.Context().Done()` для своевременного обнаружения дисконнекта клиента.
4. Напишите gRPC-клиент на Go, читающий поток в цикле `stream.Recv()` до получения `io.EOF`.

## Код решения

**`server_stream.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"net"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

// DTO для эмуляции сгенерированного proto
type StreamRequest struct {
	UserID string
}

type NotificationItem struct {
	ID        string
	Message   string
	Timestamp int64
}

type StreamNotificationsServer interface {
	Send(*NotificationItem) error
	Context() context.Context
}

type NotificationServer struct{}

func (s *NotificationServer) StreamNotifications(
	req *StreamRequest,
	stream StreamNotificationsServer,
) error {
	fmt.Printf("Клиент %s подключился к стриму уведомлений\n", req.UserID)
	ctx := stream.Context()

	ticker := time.NewTicker(500 * time.Millisecond)
	defer ticker.Stop()

	count := 0
	for {
		select {
		case <-ctx.Done():
			fmt.Printf("Клиент %s отключился: %v\n", req.UserID, ctx.Err())
			return status.Error(codes.Canceled, "client closed connection")
		case t := <-ticker.C:
			count++
			item := &NotificationItem{
				ID:        fmt.Sprintf("notif_%d", count),
				Message:   fmt.Sprintf("Ваш заказ обновлен: статус %d", count),
				Timestamp: t.Unix(),
			}

			if err := stream.Send(item); err != nil {
				return status.Errorf(codes.Unavailable, "failed to send: %v", err)
			}

			// Завершаем стрим после 5 сообщений
			if count >= 5 {
				fmt.Printf("Стрим для %s успешно завершен\n", req.UserID)
				return nil
			}
		}
	}
}

func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		panic(err)
	}
	s := grpc.NewServer()
	fmt.Println("gRPC Server Streaming готов на порту :50051")
	_ = s
	_ = lis
}
```

ℹ️ Серверный стриминг gRPC с контролем отмены контекста и завершением потока

**`client_reader.go`**

```go
package main

import (
	"context"
	"fmt"
	"io"
	"time"
)

// Эмуляция чтения gRPC-стрима клиентом
type MockStreamClient interface {
	Recv() (*NotificationItem, error)
}

func ConsumeNotifications(ctx context.Context, stream MockStreamClient) error {
	for {
		item, err := stream.Recv()
		if err == io.EOF {
			fmt.Println("Сервер закрыл стрим (io.EOF). Все сообщения получены.")
			return nil
		}
		if err != nil {
			return fmt.Errorf("ошибка чтения стрима: %w", err)
		}
		fmt.Printf("Получено уведомление [%s]: %s (ts=%d)\n", item.ID, item.Message, item.Timestamp)
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	fmt.Printf("Клиент готов к приему уведомлений по контексту %v\n", ctx)
}
```

ℹ️ Клиентский цикл чтения Recv() до флага io.EOF

## Под капотом

Метод `stream.Send()` в gRPC не выполняет физическую запись в сокет немедленно, если буфер окна потока (HTTP/2 Flow Control Window) исчерпан. Библиотека `grpc-go` использует очереди буферизации. Если клиент читает медленнее, чем сервер шлет уведомления, окно HTTP/2 заполнится, и вызов `stream.Send()` заблокирует горутину сервера. Поэтому отслеживание `stream.Context().Done()` критически необходимо для предотвращения утечки горутин.

## Подводные камни

1. **Утечка горутины при блокировке `Send()`**: Если не использовать `select` с `ctx.Done()`, зависший клиент навсегда заморозит горутину обработчика стрима.
2. **Паника при одновременном вызове `Send()`**: Интерфейс `grpc.ServerStream` **не является потокобезопасным**. Запрещено вызывать `stream.Send()` параллельно из нескольких горутин без внешней синхронизации мьютексом.

## На собеседовании

В микросервисах доставки (Яндекс Еда, Ozon Fresh) отслеживание курьера на карте использует gRPC Server Streaming. Вопрос: 'Что произойдет со стримом курьера, если мобильное приложение на 10 секунд попало в тоннель метро?' Ответ: TCP-соединение оборвется по таймауту Keepalive, сервер получит ошибку в `Send()` и завершит стрим. Клиент обязан переподключиться и передать последний полученный `last_event_id` для дочитки пропущенных координат из кэша.
