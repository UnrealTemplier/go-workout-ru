## Теория

В распределенных микросервисных архитектурах каждый RPC-запрос обязан нести сквозные контекстные метаданные:
1. **Трассировка (`X-Request-ID`, `traceparent`)**: Уникальный ID запроса для связывания логов всех затронутых сервисов.
2. **Аутентификация (`Authorization: Bearer <jwt>`)**: Токен безопасности пользователя.
3. **Клиентские метаданные (`X-Client-Version`, `X-Device-OS`)**: Для feature-flags и телеметрии.

В стандартном gRPC для этого используется пакет `google.golang.org/grpc/metadata`. В ConnectRPC метаданные читаются напрямую через методы `req.Header()`, что полностью унифицирует работу с HTTP-заголовками как от браузеров, так и от backend-сервисов.

## Решение по шагам

1. Реализуйте интерцептор или middleware для извлечения `X-Request-ID`.
2. Если заголовок отсутствует, сгенерируйте новый UUIDv4.
3. Поместите ID трассировки в `context.Context` запроса.
4. Проверьте заголовок `Authorization`: при отсутствии верните статус `Unauthenticated`.
5. Передайте `X-Request-ID` в ответных заголовках клиенту.

## Код решения

**`metadata_interceptor.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"net/http"

	"connectrpc.com/connect"
)

type contextKey string

const RequestIDKey contextKey = "request_id"

// NewAuthAndTraceInterceptor создает интерцептор метаданных для Connect
func NewAuthAndTraceInterceptor() connect.UnaryInterceptorFunc {
	return func(next connect.UnaryFunc) connect.UnaryFunc {
		return func(ctx context.Context, req connect.AnyRequest) (connect.AnyResponse, error) {
			// 1. Извлечение или генерация X-Request-ID
			reqID := req.Header().Get("X-Request-ID")
			if reqID == "" {
				reqID = "gen-" + fmt.Sprintf("%d", 100000+len(req.Spec().Procedure))
			}

			// Прокидываем Request-ID в Go context
			ctx = context.WithValue(ctx, RequestIDKey, reqID)

			// 2. Валидация Authorization Bearer токена
			authHeader := req.Header().Get("Authorization")
			if authHeader == "" || authHeader == "Bearer invalid" {
				return nil, connect.NewError(
					connect.CodeUnauthenticated,
					errors.New("отсутствует или недействителен токен авторизации"),
				)
			}

			fmt.Printf("[%s] Вызов RPC процедуры: %s (Auth: OK)\n", reqID, req.Spec().Procedure)

			// Выполнение целевой бизнес-процедуры
			resp, err := next(ctx, req)
			if err == nil && resp != nil {
				// Прокидываем Request-ID в заголовки ответа
				resp.Header().Set("X-Request-ID", reqID)
			}
			return resp, err
		}
	}
}

func main() {
	interceptor := NewAuthAndTraceInterceptor()
	fmt.Printf("Интерцептор метаданных успешно создан: %v\n", interceptor != nil)
}
```

**`client_example.go`**

```go
package main

import (
	"context"
	"fmt"
	"net/http"

	"connectrpc.com/connect"
)

type PingReq struct {
	Msg string `json:"msg"`
}

func CallWithMetadata() {
	req := connect.NewRequest(&PingReq{Msg: "hello"})
	// Передача метаданных из клиента
	req.Header().Set("X-Request-ID", "req_prod_abc987")
	req.Header().Set("Authorization", "Bearer eyJhbGciOi...")
	req.Header().Set("X-Client-Platform", "web-admin-panel")

	fmt.Printf("Подготовлен RPC запрос с метаданными: %v\n", req.Header())
}

func main() {
	CallWithMetadata()
}
```

## Под капотом

В классическом gRPC заголовки HTTP/2 преобразуются в мапу `metadata.MD` (тип `map[string][]string`). Ключи автоматически приводятся к нижнему регистру (lowercase), как того требует стандарт HTTP/2. Если ключ оканчивается на суффикс `-bin` (например, `trace-token-bin`), gRPC кодирует значение в Base64. В ConnectRPC разработчик избавлен от этих низкоуровневых сложностей, оперируя стандартным `http.Header`.

## Подводные камни

1. **Потеря метаданных при асинхронных вызовах**: При порождении фоновой горутины передача `context.Background()` вместо исходного контекста приводит к потере `X-Request-ID` в логах дочерних операций.
2. **Бинарные данные в обычных заголовках**: Попытка передать не-ASCII символы в строковом HTTP-заголовке вызывает крах HTTP-парсера прокси-серверов.

## На собеседовании

В распределенной архитектуре Wildberries или Ozon один клик пользователя порождает граф из 50 микросервисных вызовов. Вопрос: 'Как гарантировать, что trace ID не потеряется при переходе с веб-клиента на BFF и далее во внутренние gRPC-сервисы?' Ответ: Использовать стандарт W3C TraceContext (`traceparent` header). Интерцепторы на каждом сервисе обязаны извлекать родительский span context и инжектировать его в исходящие RPC-вызовы.
