## Теория

**Интерцепторы (Interceptors)** в gRPC и Connect — это аналог HTTP Middleware, позволяющий перехватывать выполнение RPC-методов до и после их передачи в бизнес-логику.

Виды интерцепторов:
1. **Unary Server Interceptor**: Оборачивает унарный вызов по сигнатуре:
   `func(ctx, req, info, handler) (resp, err)`.
2. **Stream Server Interceptor**: Оборачивает потоковый вызов:
   `func(srv, ss, info, handler) error`.
3. **Unary / Stream Client Interceptor**: Оборачивает вызовы на стороне клиента (для инжекции токенов и сбора клиентских метрик).

Цепочка интерцепторов в продакшене (Interceptor Chain):
`Panic Recovery` -> `Tracing (OpenTelemetry)` -> `Metrics (Prometheus)` -> `Logging` -> `Authentication / Authorization` -> `Validation` -> `Business Handler`.

## Код решения

**`interceptors.go`**

```go
package main

import (
	"context"
	"fmt"
	"runtime/debug"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

// 1. Интерцептор логирования и замера времени выполнения
func LoggingUnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(
		ctx context.Context,
		req any,
		info *grpc.UnaryServerInfo,
		handler grpc.UnaryHandler,
	) (any, error) {
		start := time.Now()
		resp, err := handler(ctx, req)
		duration := time.Since(start)

		code := status.Code(err)
		fmt.Printf("[gRPC] Method: %s | Duration: %v | Code: %s\n", info.FullMethod, duration, code)
		return resp, err
	}
}

// 2. Интерцептор защиты от паник (Panic Recovery)
func RecoveryUnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(
		ctx context.Context,
		req any,
		info *grpc.UnaryServerInfo,
		handler grpc.UnaryHandler,
	) (resp any, err error) {
		defer func() {
			if r := recover(); r != nil {
				stack := string(debug.Stack())
				fmt.Printf("[CRITICAL PANIC] Method: %s | Error: %v\nStack: %s\n", info.FullMethod, r, stack)
				err = status.Errorf(codes.Internal, "Internal server error occurred")
			}
		}()
		return handler(ctx, req)
	}
}

func main() {
	// Сборка цепочки интерцепторов
	server := grpc.NewServer(
		grpc.ChainUnaryInterceptor(
			RecoveryUnaryInterceptor(),
			LoggingUnaryInterceptor(),
		),
	)
	fmt.Printf("Сервер сконфигурирован с цепочкой интерцепторов: %v\n", server != nil)
}
```

ℹ️ Цепочка унарных интерцепторов gRPC: логирование, метрики длительности и перехват паник

## Под капотом

При использовании `grpc.ChainUnaryInterceptor` интерцепторы оборачиваются по принципу 'матрешки' (Onion Architecture). Первый интерцептор в цепочке вызывается самым первым на входе и самым последним на выходе. Поэтому `RecoveryInterceptor` ОБЯЗАН быть самым внешним (первым в цепочке): если panic возникнет внутри промежуточного интерцептора логирования или авторизации, внешний recovery гарантированно предотвратит падение всего Go-процесса.

## Подводные камни

1. **Мутация контекста без возврата**: Если в интерцепторе создается дочерний контекст (`ctx = context.WithValue(...)`), его необходимо передать в `handler(ctx, req)`, иначе дочерние функции не увидят добавленные метаданные.
2. **Блокирующие операции в потоковых интерцепторах**: В `StreamServerInterceptor` обертка вызывается один раз на весь жизненный цикл стрима. Долгие блокировки до вызова `handler` задерживают открытие стрима клиенту.

## На собеседовании

В микросервисных платформах Т-Банка и Ozon интерцепторы унифицированы в корпоративном SDK. Вопрос: 'Как передать ошибку валидации из интерцептора без вызова основного хэндлера бизнес-логики?' Ответ: Интерцептор просто возвращает статус-ошибку `return nil, status.Error(codes.InvalidArgument, "...")` без вызова `handler(ctx, req)`. Цепочка выполнения немедленно прерывается и клиенту отправляется RPC-ошибка.
