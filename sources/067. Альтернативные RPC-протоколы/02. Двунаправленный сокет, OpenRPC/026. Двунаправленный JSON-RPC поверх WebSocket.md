# Двунаправленный JSON-RPC поверх WebSocket (LSP Foundation)

## Условие

26. **JSON-RPC over WebSocket**: Используйте JSON-RPC поверх WebSocket для bidirectional RPC (client и server оба могут инициировать calls). Это основа LSP.

### Исходная формулировка

**JSON-RPC over WebSocket**: Используйте JSON-RPC поверх WebSocket для bidirectional RPC (client и server оба могут инициировать calls). Это основа LSP.

## Теория

Транспорт HTTP/1.1 является однонаправленным: клиент всегда инициирует запрос, а сервер отвечает. 

Однако в ряде сценариев требуется **симметричный двунаправленный RPC**:
- **Language Server Protocol (LSP):** Редактор кода (VS Code, GoLand) отправляет запросы серверу языка (`textDocument/completion`), а языковой сервер отправляет запросы и уведомления редактору (`window/showMessage`, `textDocument/publishDiagnostics`).
- **Браузерные торговые терминалы:** Клиент отправляет ордер `order.place`, а сервер шлет вызовы `account.marginCall`.

JSON-RPC поверх WebSocket:
1. Каждое текстовое WebSocket сообщение содержит независимый JSON-RPC фрейм (Request, Response или Notification).
2. Обе стороны хранят таблицу ожидающих вызовов `pendingCalls map[any]chan Response`.
3. При отправке запроса сторона генерирует `ID` и ждет ответ в канале.
4. При получении сообщения: если есть поле `method` — это входящий вызов; если есть поле `result`/`error` — это ответ на наш ранее отправленный запрос!

## Решение по шагам

1. Создайте двунаправленный менеджер RPC-сессии с картой `pending map[string]chan RPCResponse`.
2. Реализуйте метод `Call(method, params) (Result, error)` для отправки запроса клиенту.
3. Реализуйте метод `OnMessage(payload)` для разделения входящих запросов и входящих ответов.
4. Протестируйте вызов метода клиента со стороны сервера.

## Код решения

**`ws_jsonrpc.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type DuplexMessage struct {
	JSONRPC string          `json:"jsonrpc"`
	Method  string          `json:"method,omitempty"`
	Params  json.RawMessage `json:"params,omitempty"`
	Result  any             `json:"result,omitempty"`
	Error   any             `json:"error,omitempty"`
	ID      string          `json:"id,omitempty"`
}

type DuplexPeer struct {
	mu           sync.Mutex
	pending      map[string]chan DuplexMessage
	seq          atomic.Uint64
	sendToSocket func([]byte) error
}

func NewDuplexPeer(sender func([]byte) error) *DuplexPeer {
	return &DuplexPeer{
		pending:      make(map[string]chan DuplexMessage),
		sendToSocket: sender,
	}
}

// Call инициирует исходящий RPC вызов к удаленной стороне
func (p *DuplexPeer) Call(method string, params any) (*DuplexMessage, error) {
	id := fmt.Sprintf("msg_%d", p.seq.Add(1))
	respCh := make(chan DuplexMessage, 1)

	p.mu.Lock()
	p.pending[id] = respCh
	p.mu.Unlock()

	defer func() {
		p.mu.Lock()
		delete(p.pending, id)
		p.mu.Unlock()
	}()

	paramBytes, _ := json.Marshal(params)
	msg := DuplexMessage{
		JSONRPC: "2.0",
		Method:  method,
		Params:  paramBytes,
		ID:      id,
	}

	bytes, _ := json.Marshal(msg)
	if err := p.sendToSocket(bytes); err != nil {
		return nil, err
	}

	select {
	case resp := <-respCh:
		return &resp, nil
	case <-time.After(3 * time.Second):
		return nil, fmt.Errorf("rpc timeout")
	}
}

// HandleIncoming обрабатывает любое сырое сообщение из вебсокета
func (p *DuplexPeer) HandleIncoming(raw []byte) {
	var msg DuplexMessage
	if err := json.Unmarshal(raw, &msg); err != nil {
		return
	}

	if msg.Method != "" {
		// ВХОДЯЩИЙ ЗАПРОС ОТ УДАЛЕННОЙ СТОРОНЫ
		fmt.Printf("[Incoming Call] Remote wants method: %s\n", msg.Method)
		// Сервер отправляет ответ...
	} else if msg.ID != "" {
		// ОТВЕТ НА НАШ РАНЕЕ ОТПРАВЛЕННЫЙ ЗАПРОС
		p.mu.Lock()
		ch, exists := p.pending[msg.ID]
		p.mu.Unlock()

		if exists {
			ch <- msg
		}
	}
}

func main() {
	// Демонстрация работы симметричного пира
	peer := NewDuplexPeer(func(data []byte) error {
		fmt.Printf("[TCP OUT] -> %s\n", string(data))
		return nil
	})

	// Симулируем ответ от клиента через 50 мс
	go func() {
		time.Sleep(50 * time.Millisecond)
		peer.HandleIncoming([]byte(`{"jsonrpc":"2.0","result":"File saved","id":"msg_1"}`))
	}()

	resp, err := peer.Call("editor.save", map[string]string{"path": "/app/main.go"})
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Call Success] Received: %+v\n", resp.Result)
}
```

## Под капотом

В полнодуплексных протоколах исчезает понятие 'клиент' и 'сервер': оба участника соединения становятся равноправными узлами (Peers). Единый мультиплексор сообщений анализирует наличие поля `method` для вызова локальных процедур и поле `id` для сопоставления ответов на исходящие запросы.

## Подводные камни

Утечка каналов в мапе `pending` при обрыве сокета. Если удаленный пир разорвал соединение, все ожидающие горутины должны быть разбужены с ошибкой `ErrConnectionClosed`, а мапа `pending` очищена в потокобезопасном режиме.

## На собеседовании

В Яндекс (команды инструментов разработки и браузерных IDE) часто спрашивают: 'Как Language Server Protocol (LSP) разруливает параллельные отмены запросов от пользователя (например, пользователь продолжил печатать)?' Ответ: LSP определяет стандартное уведомление `$/cancelRequest` с параметром `{"id": "msg_1"}`. Сервер, получив это уведомление, отменяет контекст выполнения соответствующей горутины через `context.CancelFunc`.
