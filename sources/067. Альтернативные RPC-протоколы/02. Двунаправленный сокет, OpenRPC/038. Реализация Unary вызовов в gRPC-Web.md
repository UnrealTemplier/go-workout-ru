## Теория

Unary-вызов (Request-Response) — самый распространенный паттерн в веб-приложениях: клиент шлет одно сообщение и получает ровно один ответ.

Тестирование gRPC-Web через `curl`:
1. Указывается заголовок `Content-Type: application/grpc-web+proto` (или `application/grpc-web-text`).
2. Включается заголовок `X-Grpc-Web: 1`.
3. Тело запроса формируется с учетом 5-байтового префикса кадрирования:
   - Байт 0: `0x00` (флаг обычного сообщения);
   - Байты 1-4: длина сообщения в формате Big-Endian;
   - Байты 5..N: сериализованный Protobuf.
4. Ответ содержит два фрейма: данные (0x00) и трейлеры (0x80).

## Решение по шагам

1. Создайте обработчик Unary RPC `GetUser`.
2. Реализуйте упаковку ответа в спецификационный бинарный формат gRPC-Web.

4. Проверьте разбор ответа клиентом.

## Код решения

**`unary_grpcweb.go`**

```go
package main

import (
	"encoding/binary"
	"fmt"
	"io"
	"net/http"
)

func unaryGRPCWebHandler(w http.ResponseWriter, r *http.Request) {
	// Проверяем заголовки gRPC-Web
	if r.Header.Get("X-Grpc-Web") != "1" && r.Header.Get("Content-Type") != "application/grpc-web+proto" {
		http.Error(w, "Expected gRPC-Web request", http.StatusBadRequest)
		return
	}

	body, _ := io.ReadAll(r.Body)
	if len(body) < 5 {
		http.Error(w, "Truncated gRPC frame header", http.StatusBadRequest)
		return
	}

	payloadLen := binary.BigEndian.Uint32(body[1:5])
	payload := string(body[5 : 5+payloadLen])
	fmt.Printf("[gRPC-Web Unary] Request payload received: %s\n", payload)

	w.Header().Set("Content-Type", "application/grpc-web+proto")
	w.WriteHeader(http.StatusOK)

	// 1. Data Frame: 0x00 + uint32(len) + payload
	respData := []byte("User Profile: Dmitry (ID: 42)")
	frameHeader := make([]byte, 5)
	frameHeader[0] = 0x00
	binary.BigEndian.PutUint32(frameHeader[1:], uint32(len(respData)))
	w.Write(frameHeader)
	w.Write(respData)

	// 2. Trailers Frame: 0x80 + uint32(len) + status
	trailers := []byte("grpc-status: 0\r\ngrpc-message: OK\r\n")
	trHeader := make([]byte, 5)
	trHeader[0] = 0x80
	binary.BigEndian.PutUint32(trHeader[1:], uint32(len(trailers)))
	w.Write(trHeader)
	w.Write(trailers)
}

func main() {
	http.HandleFunc("/user.UserService/GetUser", unaryGRPCWebHandler)
	fmt.Println("gRPC-Web Unary server running on :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

**`test_curl.sh`**

```bash
# Отправка тестового gRPC-Web Unary вызова через curl
# Префикс \x00\x00\x00\x00\x06 означает фрейм данных длиной 6 байт ("Dmitry")
curl -i -X POST http://localhost:8080/user.UserService/GetUser \
  -H "Content-Type: application/grpc-web+proto" \
  -H "X-Grpc-Web: 1" \
  --data-binary $'\x00\x00\x00\x00\x06Dmitry'
```

## Под капотом

Бинарный 5-байтовый префикс кадрирования gRPC (`1 byte compressed flag + 4 bytes message length`) полностью совпадает с префиксом фреймов gRPC-Web, за исключением того, что в gRPC-Web старший бит первого байта зарезервирован для маркировки трейлеров (`0x80`).

## Подводные камни

Отсутствие завершающего фрейма трейлеров (`0x80`). Без него клиентский SDK gRPC-Web будет висеть в бесконечном ожидании статуса вызова, пока не сработает таймаут.

## На собеседовании

В Т-Банке и Ozon часто спрашивают: 'Что происходит, если gRPC метод возвращает ошибку NotFound на Unary запросе?' Ответ: в gRPC-Web при ошибке фрейм данных (Data frame) опускается, и прокси отправляет ровно один Trailer frame с заголовками `grpc-status: 5` и `grpc-message: user not found`.
