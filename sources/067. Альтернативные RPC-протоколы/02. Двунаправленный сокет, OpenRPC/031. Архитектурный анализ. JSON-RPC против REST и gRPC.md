# Архитектурный анализ: JSON-RPC против REST и gRPC

## Условие

31. **JSON-RPC vs REST vs gRPC:**
    * JSON-RPC: simple, one endpoint, batch support
    * REST: resource-oriented, HTTP semantics, cacheable
    * gRPC: typed, streaming, high-performance
    JSON-RPC идеален для action-oriented APIs и blockchain.

### Исходная формулировка

**JSON-RPC vs REST vs gRPC:**
* JSON-RPC: simple, one endpoint, batch support
* REST: resource-oriented, HTTP semantics, cacheable
* gRPC: typed, streaming, high-performance
JSON-RPC идеален, когда у вас много "действий", а не "ресурсов".

## Теория

Сравнительный анализ трех доминирующих парадигм проектирования API:

| Критерий | REST | JSON-RPC 2.0 | gRPC |
| :--- | :--- | :--- | :--- |
| **Парадигма** | Ресурсно-ориентированная (CRUD) | Процедурно-ориентированная (RPC) | Процедурно-ориентированная (RPC) |
| **Транспорт** | HTTP/1.1, HTTP/2 | Любой (HTTP, WebSocket, TCP, IPC) | Строго HTTP/2 или HTTP/3 |
| **Формат данных** | JSON, XML, HTML | JSON (UTF-8 текст) | Protocol Buffers (Бинарный) |
| **Схема/Контракт** | OpenAPI (опционально) | OpenRPC (опционально) | `.proto` файлы (строго обязательно) |
| **Стриминг** | Нет (только SSE) | Двунаправленный (поверх WebSocket) | Двунаправленный (Bi-di Streaming) |
| **Кэширование** | На уровне HTTP (ETag, CDN) | Затруднено (всегда метод POST) | На прикладном уровне |
| **Батчинг (Batch)** | Не стандартизирован | Стандартизирован из коробки `[]` | Не стандартизирован |

### Когда выбирать JSON-RPC:
1. **Действия вместо ресурсов (Action-Oriented API):** `auth.sendSmsCode`, `crypto.transferFunds`, `calc.estimateDelivery`. Попытка выразить эти действия через REST-глаголы приводит к искусственным сущностям (`POST /sms-verifications`).
2. **Блокчейн и смарт-контракты:** Стандарт де-факто в Ethereum (Web3 JSON-RPC API), Bitcoin Core и Solana.
3. **Пакетная оптимизация:** Клиент может запросить баланс, список транзакций и профиль в одном сетевом вызове.

## Решение по шагам

1. Создайте сводную таблицу характеристик протоколов.
2. Продемонстрируйте реализацию одного и того же действия (перевод средств) в стилях REST и JSON-RPC.
3. Сформулируйте правила выбора архитектурного стиля для команды разработчиков.

## Код решения

**`comparison.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

// Пример действия: "Списание бонусов с аккаунта"

// 1. Стиль REST: требует создания псевдо-ресурса "redemption"
func restHandler(w http.ResponseWriter, r *http.Request) {
	if r.Method == http.MethodPost && r.URL.Path == "/api/v1/accounts/101/redemptions" {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusCreated)
		_, _ = w.Write([]byte(`{"redemption_id": 555, "status": "CONFIRMED"}`))
	}
}

// 2. Стиль JSON-RPC: прямое выражение действия без искусственных ресурсов
func jsonRpcHandler(w http.ResponseWriter, r *http.Request) {
	var req struct {
		JSONRPC string `json:"jsonrpc"`
		Method  string `json:"method"`
		Params  struct {
			AccountID int `json:"account_id"`
			Amount    int `json:"amount"`
		} `json:"params"`
		ID any `json:"id"`
	}

	_ = json.NewDecoder(r.Body).Decode(&req)

	if req.Method == "loyalty.redeemBonuses" {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]any{
			"jsonrpc": "2.0",
			"result":  map[string]any{"redemption_id": 555, "status": "CONFIRMED"},
			"id":      req.ID,
		})
	}
}

func main() {
	http.HandleFunc("/api/v1/", restHandler)
	http.HandleFunc("/rpc", jsonRpcHandler)
	fmt.Println("Comparison server listening on :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

В REST проектирование сложных бизнес-транзакций, затрагивающих несколько таблиц и не являющихся простым CRUD, часто приводит к так называемому 'REST Over-engineering', когда разработчики вынуждены придумывать нелепые URI ресурсов (`/transfers-executions-commands`). JSON-RPC возвращает естественную модель вызова удаленной процедуры.

## Подводные камни

Использование JSON-RPC для публичных контентных веб-сайтов со статическими данными (каталог статей, новостей). Поскольку запросы идут методом POST, пограничные CDN (Cloudflare) не кэшируют ответы по умолчанию, что увеличивает нагрузку на бэкенд по сравнению с GET-запросами в REST.

## На собеседовании

В Ozon на архитектурном интервью часто задают вопрос: 'Почему микросервисы внутри датацентра общаются по gRPC, а мобильное приложение с бэкендом — по JSON-RPC или REST?' Ответ: Внутри ДЦ критична наносекундная производительность, мультиплексирование HTTP/2 и строгие схемы Protobuf. На внешнем клиенте критична простота отладки, работа через корпоративные прокси и легкость интеграции в веб-интерфейсы.
