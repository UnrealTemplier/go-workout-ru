# Клиент JSON-RPC на Go с таймаутом контекста и обработкой транспортных ошибок

## Условие

40. **JSON-RPC клиент на Go.**: Напишите клиент, который формирует запрос с `id`, отправляет HTTP POST и парсит ответ. Поддержите таймаут и обработку ошибок транспорта.

### Исходная формулировка

**JSON-RPC клиент на Go.**: Напишите клиент, который формирует запрос с `id`, отправляет HTTP POST и парсит ответ. Поддержите таймаут и обработку ошибок транспорта.

## Теория

При реализации производственного клиента в Go необходимо обеспечить:
1. **Контекстный контроль:** Каждый вызов должен принимать `ctx context.Context` для возможности отмены по таймауту.
2. **Изоляция ошибок:** Ошибки сети (`connection refused`, `context deadline exceeded`) должны возвращаться как стандартные ошибки Go, а не паниковать.
3. **Безопасное закрытие ресурсов:** Тело HTTP-ответа `resp.Body` должно гарантированно закрываться через `defer`, а байты вычитываться до конца для переиспользования TCP-соединения.

## Решение по шагам

1. Создайте структуру клиента `Client` с полем `baseURL`.
2. Реализуйте метод `Call(ctx, method, params, target) error`.
3. Установите заголовки `Content-Type: application/json`.
4. Обработайте статусы HTTP отличные от 200.
5. Распакуйте `result` в переданный указатель.

## Код решения

**`resilient_client.go`**

```go
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"time"
)

type Client struct {
	endpoint   string
	httpClient *http.Client
}

func NewClient(endpoint string) *Client {
	return &Client{
		endpoint: endpoint,
		httpClient: &http.Client{
			Timeout: 5 * time.Second,
		},
	}
}

func (c *Client) Call(ctx context.Context, method string, params any, result any) error {
	reqMap := map[string]any{
		"jsonrpc": "2.0",
		"method":  method,
		"params":  params,
		"id":      time.Now().UnixNano(),
	}

	bodyBytes, err := json.Marshal(reqMap)
	if err != nil {
		return fmt.Errorf("marshal error: %w", err)
	}

	httpReq, err := http.NewRequestWithContext(ctx, http.MethodPost, c.endpoint, bytes.NewReader(bodyBytes))
	if err != nil {
		return fmt.Errorf("request build error: %w", err)
	}
	httpReq.Header.Set("Content-Type", "application/json")

	httpResp, err := c.httpClient.Do(httpReq)
	if err != nil {
		// Ошибка транспорта (таймаут или сбой соединения)
		return fmt.Errorf("transport failure: %w", err)
	}
	defer httpResp.Body.Close()

	if httpResp.StatusCode != http.StatusOK {
		return fmt.Errorf("server returned unexpected HTTP status: %s", httpResp.Status)
	}

	var rpcResp struct {
		JSONRPC string          `json:"jsonrpc"`
		Result  json.RawMessage `json:"result"`
		Error   *struct {
			Code    int    `json:"code"`
			Message string `json:"message"`
		} `json:"error"`
	}

	if err := json.NewDecoder(httpResp.Body).Decode(&rpcResp); err != nil {
		return fmt.Errorf("response decode error: %w", err)
	}

	if rpcResp.Error != nil {
		return fmt.Errorf("JSON-RPC error [%d]: %s", rpcResp.Error.Code, rpcResp.Error.Message)
	}

	if result != nil && len(rpcResp.Result) > 0 {
		if err := json.Unmarshal(rpcResp.Result, result); err != nil {
			return fmt.Errorf("target unmarshal error: %w", err)
		}
	}

	return nil
}

func main() {
	client := NewClient("http://localhost:8080/rpc")

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	var pong string
	err := client.Call(ctx, "ping", nil, &pong)
	if err != nil {
		fmt.Printf("Client error: %v\n", err)
		return
	}
	fmt.Printf("Success! Received: %s\n", pong)
}
```

## Под капотом

Использование `http.NewRequestWithContext(ctx, ...)` привязывает время жизни системного вызова к контексту. Если таймер контекста истекает, сетевой транспорт немедленно прерывает чтение из сокета через `cancelRequest`, освобождая горутину без подвисаний.

## Подводные камни

Игнорирование возвращаемой ошибки при декодировании `r.Body`. Если соединение прервалось посреди передачи тела, `json.NewDecoder` вернет `io.ErrUnexpectedEOF`, что должно трактоваться клиентом как сетевой сбой.

## На собеседовании

В Касперском и Tinkoff часто спрашивают: 'Что делать, если клиент отправляет POST запрос, сервер выполняет операцию списания денег, но сетевой ответ теряется из-за обрыва связи (Network Timeout)?' Ответ: Проблема идемпотентности. Клиент должен использовать неизменный UUID в качестве поля `id` при ретраях, а сервер обязан сохранять результаты выполненных запросов в Redis-кэше (Idempotency Cache) для возврата кэшированного ответа без повторного списания.
