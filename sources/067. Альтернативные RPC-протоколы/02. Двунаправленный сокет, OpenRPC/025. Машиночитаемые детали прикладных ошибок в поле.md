# Машиночитаемые детали прикладных ошибок в поле data (Custom Error Types)

## Условие

25. **Custom error types**: Расширьте error object полем `data` для machine-readable деталей: `{"code":-32000,"message":"validation failed","data":{"field":"email","reason":"invalid"}}`.

### Исходная формулировка

**Custom error types**: Расширьте error object полем `data` для machine-readable деталей: `{"code":-32000,"message":"validation failed","data":{"field":"email","reason":"invalid"}}`.

## Теория

При возникновении ошибок бизнес-логики клиентскому приложению недостаточно одного строкового сообщения:
- Строка `message` предназначена для чтения человеком или логирования.
- Для программной обработки фронтенду нужны структурированные метаданные: код доменной ошибки, имя невалидного поля, текущий остаток счета, список разрешенных значений.

Спецификация JSON-RPC 2.0 явно разрешает поле `data: any` внутри объекта `error`:
```json
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32000,
    "message": "Validation failed",
    "data": {
      "error_type": "FIELD_VALIDATION",
      "invalid_fields": [
        {"field": "email", "reason": "format is invalid", "code": "ERR_EMAIL_SYNTAX"},
        {"field": "amount", "reason": "must be greater than 0", "code": "ERR_MIN_VALUE"}
      ]
    }
  },
  "id": "req-101"
}
```

## Решение по шагам

1. Создайте структуру прикладной ошибки `DomainRPCError` с типизированным полем `Data`.
2. Реализуйте интерфейс `error` для интеграции со стандартным потоком ошибок Go.
3. Напишите обработчик, возвращающий машиночитаемые метаданные.
4. Проверьте сериализацию в JSON.

## Код решения

**`custom_errors.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

type FieldViolation struct {
	Field  string `json:"field"`
	Reason string `json:"reason"`
	Code   string `json:"code"`
}

type DomainErrorData struct {
	Domain     string           `json:"domain"`
	Violations []FieldViolation `json:"violations"`
}

type JSONRPCErrorResponse struct {
	JSONRPC string       `json:"jsonrpc"`
	Error   *DomainError `json:"error"`
	ID      any          `json:"id"`
}

type DomainError struct {
	Code    int              `json:"code"`
	Message string           `json:"message"`
	Data    *DomainErrorData `json:"data,omitempty"`
}

func (e *DomainError) Error() string {
	return fmt.Sprintf("DomainError %d: %s", e.Code, e.Message)
}

func handleUserUpdate(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")

	// Формируем машиночитаемую ошибку валидации формы
	violations := []FieldViolation{
		{Field: "email", Reason: "Email domain is blacklisted", Code: "EMAIL_BLOCKED"},
		{Field: "phone", Reason: "Phone must be in E.164 format", Code: "INVALID_PHONE"},
	}

	resp := JSONRPCErrorResponse{
		JSONRPC: "2.0",
		Error: &DomainError{
			Code:    -32000,
			Message: "Client payload failed business validation",
			Data: &DomainErrorData{
				Domain:     "IDENTITY_SERVICE",
				Violations: violations,
			},
		},
		ID: "tx_9981",
	}

	_ = json.NewEncoder(w).Encode(resp)
}

func main() {
	http.HandleFunc("/rpc/update", handleUserUpdate)
	fmt.Println("Custom error server listening on :8080/rpc/update")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Машиночитаемая ошибка с массивом violations в поле data по стандарту JSON-RPC 2.0

## Под капотом

Использование структурированного поля `data` исключает необходимость локализации сообщений на стороне бэкенда. Бэкенд возвращает коды ошибок (`EMAIL_BLOCKED`), а клиентское приложение (iOS, Android, React) переводит их на язык пользователя с использованием локальных словарей i18n.

## Подводные камни

Включение чувствительных данных в поле `data` (дампы памяти, пароли, внутренние IP-адреса сервисов Kubernetes). Поле `data` попадает в браузер клиента, поэтому данные должны проходить строгую санитизацию.

## На собеседовании

В Т-Банке и Сбере часто спрашивают: 'Как подружить коды ошибок Google gRPC (google.rpc.Status / Status Details) с JSON-RPC 2.0?' Ответ: маппить grpc.Status в поле `error.data`! Поле `code` в JSON-RPC выставляется в диапазон -32000..-32099, а оригинальный protobuf дескриптор `ErrorInfo` или `BadRequest_FieldViolation` упаковывается в JSON внутри `data`.
