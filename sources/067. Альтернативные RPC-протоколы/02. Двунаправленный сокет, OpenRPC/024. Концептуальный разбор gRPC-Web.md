## Теория

Протокол **gRPC** построен поверх HTTP/2 и опирается на две ключевые возможности, отсутствующие в стандартных веб-браузерах:
1. **HTTP/2 Trailers (Завершающие заголовки):**
   - gRPC передает статус вызова (`grpc-status`) и сообщение об ошибке (`grpc-message`) не в теле ответа и не в начальных заголовках, а в **HTTP/2 Trailers** (заголовках, отправляемых ПОСЛЕ передачи всех данных тела).
   - Браузерные API (`fetch`, `XMLHttpRequest`) не предоставляют прямого программного доступа к завершающим заголовкам HTTP/2.
2. **Низкоуровневое управление фреймами (Raw Frame Control):**
   - Браузер изолирует JS-код от прямого контроля фреймов `HEADERS`, `DATA`, `RST_STREAM`. Клиентский стриминг не может быть реализован в браузерном JS без эмуляции.

Решение: **Стандарт gRPC-Web**:
- **Проксирование (Envoy или Go in-process wrapper):** Браузер отправляет стандартный HTTP/1.1 или HTTP/2 POST запрос на прокси. Прокси распаковывает gRPC-Web фреймы, преобразует трейлеры в специальный завершающий бинарный блок данных внутри тела ответа (`1-byte flag 0x80 + 4-byte length + trailers`) и передает его стандартному gRPC-бэкенду.
- **Форматы данных:**
  - `application/grpc-web+proto`: бинарные protobuf-сообщения (поддерживается современными браузерами через `fetch` + `Uint8Array`).
  - `application/grpc-web-text`: тело кодируется в Base64 для старых клиентов и окружений без поддержки бинарных потоков.

## Код решения

**`grpcweb_concept.go`**

```go
package main

import (
	"bytes"
	"encoding/binary"
	"fmt"
)

// Структура кадра gRPC-Web:
// [1 байт: Флаг] [4 байта: Длина полезной нагрузки Big-Endian] [N байт: Данные]
// Флаг 0x00: Data Frame (обычное Protobuf сообщение)
// Флаг 0x80: Trailer Frame (HTTP/2 трейлеры, закодированные в тело для браузера)

const (
	FrameTypeData    byte = 0x00
	FrameTypeTrailer byte = 0x80
)

func encodeGRPCWebFrame(frameType byte, payload []byte) []byte {
	buf := new(bytes.Buffer)
	buf.WriteByte(frameType)

	length := uint32(len(payload))
	_ = binary.Write(buf, binary.BigEndian, length)
	buf.Write(payload)

	return buf.Bytes()
}

func main() {
	// 1. Обычное сообщение ответа (Protobuf payload)
	protoPayload := []byte("User Profile Protobuf Data")
	dataFrame := encodeGRPCWebFrame(FrameTypeData, protoPayload)

	// 2. Завершающий трейлер с кодом статуса gRPC
	trailerPayload := []byte("grpc-status: 0\r\ngrpc-message: OK\r\n")
	trailerFrame := encodeGRPCWebFrame(FrameTypeTrailer, trailerPayload)

	// Полное тело gRPC-Web ответа, отправляемое браузеру
	fullBody := append(dataFrame, trailerFrame...)

	fmt.Printf("Total gRPC-Web Response Size: %d bytes\n", len(fullBody))
	fmt.Printf("Data frame header: flag=0x%02x, len=%d\n", fullBody[0], binary.BigEndian.Uint32(fullBody[1:5]))
	fmt.Printf("Trailer frame starts at byte: %d, flag=0x%02x\n", len(dataFrame), fullBody[len(dataFrame)])
}
```

ℹ️ Низкоуровневая структура кадрирования gRPC-Web с упаковкой Trailers во фрейм 0x80

## Под капотом

В спецификации gRPC-Web флаг 0x80 (старший бит первого байта) указывает парсеру, что полезная нагрузка данного чанка не является Protobuf-структурой, а содержит завершающие HTTP заголовки (key-value строки, разделенные `\r\n`), включая `grpc-status: 0`. Это позволяет браузерному клиенту узнать статус вызова без поддержки Trailers на транспортном уровне.

## Подводные камни

Попытка вызвать метод с двунаправленным стримингом (Bidirectional Streaming) через gRPC-Web из браузера. Браузерные API не позволяют отправлять данные в сокет по мере чтения ответа в рамках одного запроса. gRPC-Web поддерживает только Unary и Server-Streaming.

## На собеседовании

В Авито и Яндекс часто спрашивают: 'Зачем нужен ConnectRPC (Buf Connect), если есть gRPC-Web?' Ответ: gRPC-Web требует сложных прокси (Envoy) или тяжелых оберток и специфичного клиентского JS-кода. ConnectRPC — это современный протокол, который работает поверх стандартного HTTP/1.1 и HTTP/2, поддерживает обычный JSON и Protobuf без прокси и открывается в браузере через простой fetch().
