# Протокольные различия gRPC-Web и стандартного gRPC (Framing, Base64, Trailers)

## Условие

42. **Протокольные отличия.**: Объясните формат gRPC-Web: при HTTP/1.1 payload может быть base64-encoded, `Content-Type: application/grpc-web` (не `application/grpc`), trailers передаются либо в конце stream с 8-м битом флага, либо в HTTP response headers.

### Исходная формулировка

**Протокольные отличия.**: Объясните формат gRPC-Web: при HTTP/1.1 payload может быть base64-encoded, `Content-Type: application/grpc-web` (не `application/grpc`), trailers передаются либо в конце body (gRPC-Web), либо через headers. Напишите дешифратор фреймов: 1 byte flag (compressed/trailer) + 4 bytes length + payload.

## Теория

Сравнительный анализ протокольных нюансов:

1. **Заголовок Content-Type:**
   - Стандартный gRPC: строго `application/grpc` (или `application/grpc+proto`).
   - gRPC-Web: `application/grpc-web` или `application/grpc-web+proto` для бинарных потоков; `application/grpc-web-text` для Base64 потоков.
2. **Формат кадра (Frame Format):**
   - Формат префикса кадра: `[1 байт флагов] [4 байта длины payload Big-Endian]`.
   - Если старший 8-й бит флага равен 0 (`0x00`): полезная нагрузка является Protobuf сообщением.
   - Если старший 8-й бит флага равен 1 (`0x80`): полезная нагрузка содержит завершающие HTTP-трейлеры (`grpc-status: 0\r\ngrpc-message: OK\r\n`).
3. **Кодирование Base64 (Text Mode):**
   - В `application/grpc-web-text` весь поток байтов (включая 5-байтовые заголовки фреймов) кодируется в Base64. Это обеспечивает прохождение через старые корпоративные WAF и прокси, которые блокируют невалидный бинарный трафик в теле HTTP/1.1 ответов.

## Решение по шагам

1. Создайте парсер заголовка кадра gRPC-Web.
2. Реализуйте проверку флага `flag & 0x80 != 0` для определения трейлеров.
3. Продемонстрируйте декодирование Base64 текстового режима.
4. Выведите распарсенный статус и сообщение.

## Код решения

**`grpcweb_parser.go`**

```go
package main

import (
	"encoding/base64"
	"encoding/binary"
	"fmt"
	"strings"
)

func inspectGRPCWebStream(rawBytes []byte) {
	offset := 0

	for offset < len(rawBytes) {
		if offset+5 > len(rawBytes) {
			fmt.Println("Error: Incomplete frame header")
			return
		}

		flag := rawBytes[offset]
		length := binary.BigEndian.Uint32(rawBytes[offset+1 : offset+5])
		offset += 5

		if offset+int(length) > len(rawBytes) {
			fmt.Println("Error: Incomplete frame body")
			return
		}

		payload := rawBytes[offset : offset+int(length)]
		offset += int(length)

		// Проверяем 8-й бит флага (0x80)
		isTrailer := (flag & 0x80) != 0

		if isTrailer {
			fmt.Printf("[TRAILER FRAME] Flag=0x%02x Len=%d\n", flag, length)
			lines := strings.Split(string(payload), "\r\n")
			for _, line := range lines {
				if line != "" {
					fmt.Printf("   -> %s\n", line)
				}
			}
		} else {
			fmt.Printf("[DATA FRAME] Flag=0x%02x Len=%d PayloadBytes=%d\n", flag, length, len(payload))
		}
	}
}

func main() {
	// Формируем искусственный поток gRPC-Web
	dataMsg := []byte("ProtobufBinaryData")
	trailerMsg := []byte("grpc-status: 0\r\ngrpc-message: Success\r\n")

	stream := make([]byte, 0)

	// Фрейм данных
	stream = append(stream, 0x00)
	lenBuf := make([]byte, 4)
	binary.BigEndian.PutUint32(lenBuf, uint32(len(dataMsg)))
	stream = append(stream, lenBuf...)
	stream = append(stream, dataMsg...)

	// Фрейм трейлеров (флаг 0x80)
	stream = append(stream, 0x80)
	binary.BigEndian.PutUint32(lenBuf, uint32(len(trailerMsg)))
	stream = append(stream, lenBuf...)
	stream = append(stream, trailerMsg...)

	fmt.Println("--- Inspecting Raw Binary gRPC-Web Stream ---")
	inspectGRPCWebStream(stream)

	// Текстовый режим Base64 (application/grpc-web-text)
	base64Stream := base64.StdEncoding.EncodeToString(stream)
	fmt.Printf("\n--- Base64 Text Mode Payload ---\n%s\n", base64Stream)
}
```

ℹ️ Побитовый парсер кадрирования gRPC-Web с выделением трейлеров и Base64 режима

## Под капотом

В режиме `application/grpc-web-text` декодер на стороне клиента выполняет инкрементальное раскодирование Base64 по мере поступления сетевых пакетов. Поскольку Base64 кодирует каждые 3 байта в 4 символа, буфер должен накапливать фрагменты, кратные 4 символам, перед декодированием.

## Подводные камни

Попытка распаковать Trailer Frame как Protobuf сообщение. Если клиентский код не проверяет старший бит флага и передает срез байт в `proto.Unmarshal`, парсер Protobuf завершится с ошибкой поврежденных полей.

## На собеседовании

В Яндекс и Ozon на собеседовании спрашивают: 'Каковы накладные расходы использования режима application/grpc-web-text по сравнению с бинарным application/grpc-web+proto?' Ответ: Текстовый режим Base64 увеличивает сетевой объем полезной нагрузки ровно на 33% и требует дополнительных операций CPU на перекодирование на клиенте и сервере. Его следует избегать везде, где браузеры поддерживают бинарные потоки.
