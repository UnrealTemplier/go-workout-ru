# Перехватчики вызовов (Connect Interceptors: Auth, Metrics, Tracing)

## Условие

45. **Connect interceptors**: Используйте interceptors для auth, logging, metrics — аналог gRPC interceptors. Продемонстрируйте реализацию интерцептора в Go.

### Исходная формулировка

**Connect interceptors**: Используйте interceptors для auth, logging, metrics — аналог gRPC interceptors.

## Теория

Перехватчики (Interceptors) в Connect-go — это мощный аналог gRPC UnaryServerInterceptor:
```go
type UnaryInterceptorFunc func(context.Context, AnyRequest) (AnyResponse, error)
```
Особенности интерцепторов Connect:
1. **Единый API для клиента и сервера:** Один и тот же интерцептор может использоваться как на стороне клиента для добавления заголовков авторизации, так и на сервере для их валидации.
2. **Типобезопасный доступ к метаданным:** `req.Header()` позволяет читать и модифицировать HTTP-заголовки.
3. **Контекстный контроль:** Возможность оборачивать `context.Context` (добавлять дедлайны, данные трассировки OpenTelemetry).
4. **Композиция:** Интерцепторы объединяются через `connect.WithInterceptors(auth, logger, metrics)`.

## Решение по шагам

1. Создайте интерцептор логирования `NewLoggingInterceptor`.
2. В интерцепторе замерьте время до и после вызова `next(ctx, req)`.
3. Создайте интерцептор проверки авторизационного токена.
4. Подключите интерцепторы к вызову метода.
5. Продемонстрируйте перехват запроса в консоли.

## Код решения

**`connect_interceptors.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type AnyRequest struct {
	Procedure string
	Header    map[string]string
	Msg       any
}

type AnyResponse struct {
	Msg any
}

type UnaryFunc func(context.Context, AnyRequest) (AnyResponse, error)
type Interceptor func(UnaryFunc) UnaryFunc

// LoggingInterceptor замеряет длительность вызова процедуры
func LoggingInterceptor(next UnaryFunc) UnaryFunc {
	return func(ctx context.Context, req AnyRequest) (AnyResponse, error) {
		start := time.Now()
		fmt.Printf("[INTERCEPTOR START] Procedure: %s\n", req.Procedure)

		resp, err := next(ctx, req)

		duration := time.Since(start)
		if err != nil {
			fmt.Printf("[INTERCEPTOR ERROR] %s failed in %v: %v\n", req.Procedure, duration, err)
		} else {
			fmt.Printf("[INTERCEPTOR SUCCESS] %s completed in %v\n", req.Procedure, duration)
		}

		return resp, err
	}
}

// AuthInterceptor валидирует токен авторизации
func AuthInterceptor(next UnaryFunc) UnaryFunc {
	return func(ctx context.Context, req AnyRequest) (AnyResponse, error) {
		token := req.Header["authorization"]
		if token != "Bearer secret-connect-token" {
			return AnyResponse{}, errors.New("unauthenticated: invalid bearer token")
		}
		return next(ctx, req)
	}
}

func main() {
	// Базовая процедура
	baseProcedure := func(ctx context.Context, req AnyRequest) (AnyResponse, error) {
		return AnyResponse{Msg: "UserData: Admin"}, nil
	}

	// Собираем конвейер интерцепторов
	pipeline := LoggingInterceptor(AuthInterceptor(baseProcedure))

	// Тест 1: Невалидный токен
	req1 := AnyRequest{
		Procedure: "/user.UserService/GetUser",
		Header:    map[string]string{"authorization": "bad-token"},
	}
	_, err1 := pipeline(context.Background(), req1)
	fmt.Printf("Call 1 failed as expected: %v\n\n", err1)

	// Тест 2: Валидный токен
	req2 := AnyRequest{
		Procedure: "/user.UserService/GetUser",
		Header:    map[string]string{"authorization": "Bearer secret-connect-token"},
	}
	res2, err2 := pipeline(context.Background(), req2)
	fmt.Printf("Call 2 succeeded: %+v, err=%v\n", res2.Msg, err2)
}
```

ℹ️ Унарные интерцепторы Connect-go для сквозного логирования и аутентификации

## Под капотом

В Connect интерцепторы вызываются после десериализации метаданных, но ДО распаковки тела запроса. Если интерцептор аутентификации отклоняет вызов, сервер даже не тратит процессорные ресурсы на десериализацию сложного тела Protobuf/JSON сообщения.

## Подводные камни

Модификация объекта `req.Msg` внутри интерцептора без глубокого копирования при параллельных вызовах. Это может привести к состояниям гонки (Data Race). Интерцепторы должны модифицировать контекст или заголовки, оставляя тело неизменным.

## На собеседовании

В Яндекс и Авито часто спрашивают: 'Чем интерцепторы Connect отличаются от HTTP middleware?' Ответ: HTTP middleware работает со сырыми срезами байтов `http.ResponseWriter` и не знает структуру Protobuf сообщений. Интерцепторы Connect работают с типизированными запросами `connect.AnyRequest`, знают имя RPC процедуры, схему сообщения и код завершения `connect.Code`.
