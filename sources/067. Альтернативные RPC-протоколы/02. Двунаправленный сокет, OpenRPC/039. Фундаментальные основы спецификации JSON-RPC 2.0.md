# Фундаментальные основы спецификации JSON-RPC 2.0

## Условие

39. **Основы JSON-RPC 2.0**: Изучи спецификацию. Это протокол поверх HTTP (или WebSocket), где запрос и ответ всегда одного формата. Напиши HTTP-хендлер, который парсит JSON: `{"jsonrpc": "2.0", "method": "...", "params": [...], "id": 1}`. Если метод неизвестен — возвращай `{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1}`.

### Исходная формулировка

**Основы JSON-RPC 2.0**: Изучи спецификацию. Это протокол поверх HTTP (или WebSocket), где запрос и ответ всегда одного формата. Напиши HTTP-хендлер, который парсит JSON:
`{"jsonrpc": "2.0", "method": "math.sum", "params": [42, 23], "id": 1}`. Вызови нужную функцию, сложи числа и верни стандартный ответ: `{"jsonrpc": "2.0", "result": 65, "id": 1}`.

## Теория

Спецификация JSON-RPC 2.0 (RFC-подобный документ JSON-RPC 2.0 Specification):
1. **Транспортная независимость:** Может работать поверх HTTP, WebSocket, TCP сокетов, stdin/stdout (UNIX пайпы), IPC.
2. **Единый формат ответа:**
   - Ответ Всегда содержит ключ `"jsonrpc": "2.0"`.
   - Ответ Всегда содержит ключ `"id"`, равный значению из запроса.
   - В зависимости от результата содержит либо ключ `"result"`, либо ключ `"error"`.
3. **Строгая ошибка -32601:**
   - Если сервер не находит метод в таблице маршрутизации, возвращается объект ошибки:
     `{"code": -32601, "message": "Method not found"}`.

## Решение по шагам

1. Создайте структуру запроса и структуру ответа.
2. Напишите HTTP-хэндлер, считывающий тело запроса.
3. Проверьте имя метода: если не зарегистрирован — верните `-32601`.
4. Для известного метода верните результат.
5. Проверьте работу сервера.

## Код решения

**`spec_handler.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

type SpecRequest struct {
	JSONRPC string          `json:"jsonrpc"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params,omitempty"`
	ID      any             `json:"id"`
}

type SpecResponse struct {
	JSONRPC string     `json:"jsonrpc"`
	Result  any        `json:"result,omitempty"`
	Error   *SpecError `json:"error,omitempty"`
	ID      any        `json:"id"`
}

type SpecError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
}

func specRPCServer(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")

	var req SpecRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		_ = json.NewEncoder(w).Encode(SpecResponse{
			JSONRPC: "2.0",
			Error:   &SpecError{Code: -32700, Message: "Parse error"},
			ID:      nil,
		})
		return
	}

	// Проверяем метод
	if req.Method != "ping" {
		_ = json.NewEncoder(w).Encode(SpecResponse{
			JSONRPC: "2.0",
			Error:   &SpecError{Code: -32601, Message: "Method not found"},
			ID:      req.ID,
		})
		return
	}

	// Успешный ответ
	_ = json.NewEncoder(w).Encode(SpecResponse{
		JSONRPC: "2.0",
		Result:  "pong",
		ID:      req.ID,
	})
}

func main() {
	http.HandleFunc("/rpc", specRPCServer)
	fmt.Println("Spec JSON-RPC server listening on :8080/rpc")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Спецификационный обработчик JSON-RPC 2.0 с возвратом -32601 при неизвестном методе

## Под капотом

Спецификация JSON-RPC 2.0 явно указывает, что имя метода чувствительно к регистру (`case-sensitive`): методы `"Ping"` и `"ping"` считаются абсолютно разными методами. Табличный поиск по хэш-карте в Go обеспечивает точное побайтовое совпадение строк.

## Подводные камни

Возврат строкового кода ошибки вместо числового: `{"code": "METHOD_NOT_FOUND"}`. Спецификация JSON-RPC 2.0 строго требует, чтобы поле `code` было целым числом (`integer`). Строковые коды приведут к ошибкам десериализации в клиентских SDK.

## На собеседовании

В Wildberries часто спрашивают: 'Можно ли возвращать результат result: null при успешном выполнении метода (например, метод ничего не возвращает)?' Ответ: Да! Спецификация допускает `"result": null`. Главное, чтобы в ответе отсутствовало поле `error`.
