# Дуплексный канал связи и подписка на события через gorilla/websocket

## Условие

27. **Bidirectional JSON-RPC.**: Реализуйте duplex channel через WebSocket: клиент и сервер могут отправлять notifications друг другу. Используйте `jsonrpc2` поверх `gorilla/websocket`. Объясните, как сопоставлять requests и responses через `id` в async сокете.

### Исходная формулировка

**Bidirectional JSON-RPC.**: Реализуйте duplex channel через WebSocket: клиент и сервер могут отправлять notifications друг другу. Используйте `jsonrpc2` поверх `gorilla/websocket`. Объясните, как `id` помогает коррелировать request-response в дуплексном потоке.

## Теория

Реализация асинхронного сокета реального времени:
1. **Транспорт:** Единое TCP-соединение WebSocket (RFC 6455).
2. **Разделение горутин:**
   - Горутина-читатель (`ReadPump`): непрерывно считывает сообщения из `ws.ReadMessage()`.
   - Горутина-писатель (`WritePump`): вычитывает байты из очереди `chan []byte` и пишет в сокет. Прямая конкурентная запись в сокет Gorilla WebSocket запрещена!
3. **Асинхронная корреляция через `id`:**
   - Клиент отправляет запрос с `id: "req_1"` и продолжает посылать другие запросы (`req_2`, `req_3`), не дожидаясь ответа.
   - Сервер обрабатывает их параллельно и возвращает ответы по мере готовности: сначала `req_3`, затем `req_1`.
   - Клиент находит ожидающий вызов в локальной хэш-таблице по ключу `id`.

## Решение по шагам

1. Настройте `websocket.Upgrader` с проверкой источника.
2. Создайте структуру WebSocket-клиента с очередью отправки.
3. Реализуйте цикл чтения входящих сообщений.
4. Продемонстрируйте асинхронную отправку серверных уведомлений в сокет клиента.

## Код решения

**`ws_duplex.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"sync"
	"time"
)

type DuplexClient struct {
	sendQueue chan []byte
	mu        sync.Mutex
	pending   map[string]chan json.RawMessage
}

func NewDuplexClient() *DuplexClient {
	return &DuplexClient{
		sendQueue: make(chan []byte, 32),
		pending:   make(map[string]chan json.RawMessage),
	}
}

func (c *DuplexClient) SendNotification(method string, params any) {
	pBytes, _ := json.Marshal(params)
	msg := map[string]any{
		"jsonrpc": "2.0",
		"method":  method,
		"params":  json.RawMessage(pBytes),
	}
	bytes, _ := json.Marshal(msg)
	c.sendQueue <- bytes
}

func (c *DuplexClient) HandlePacket(data []byte) {
	var parsed struct {
		JSONRPC string          `json:"jsonrpc"`
		Method  string          `json:"method"`
		Result  json.RawMessage `json:"result"`
		ID      string          `json:"id"`
	}

	if err := json.Unmarshal(data, &parsed); err != nil {
		return
	}

	// Если это ответ на наш запрос:
	if parsed.ID != "" && parsed.Method == "" {
		c.mu.Lock()
		ch, ok := c.pending[parsed.ID]
		c.mu.Unlock()
		if ok {
			ch <- parsed.Result
		}
		return
	}

	// Если это входящий вызов от клиента:
	if parsed.Method != "" {
		fmt.Printf("[SERVER] Received client request: %s (id: %s)\n", parsed.Method, parsed.ID)
		// Отвечаем асинхронно
		if parsed.ID != "" {
			resp := map[string]any{
				"jsonrpc": "2.0",
				"result":  "Processed: " + parsed.Method,
				"id":      parsed.ID,
			}
			rBytes, _ := json.Marshal(resp)
			c.sendQueue <- rBytes
		}
	}
}

func main() {
	client := NewDuplexClient()

	// Демонстрация отправки уведомлений от сервера к клиенту
	go func() {
		ticker := time.NewTicker(1 * time.Second)
		defer ticker.Stop()
		i := 0
		for range ticker.C {
			i++
			client.SendNotification("server.alert", map[string]string{
				"message": fmt.Sprintf("Heartbeat tick #%d", i),
			})
			if i >= 3 {
				return
			}
		}
	}()

	// Вычитываем исходящую очередь
	for msg := range client.sendQueue {
		fmt.Printf("[WS FRAME SENT] %s\n", string(msg))
	}
}
```

ℹ️ Потокобезопасная очередь отправки и сопоставление ID для асинхронного сокета

## Под капотом

Спецификация Gorilla WebSocket строго запрещает одновременный вызов `conn.WriteMessage` или `conn.WriteJSON` из нескольких горутин. Использование выделенного канала `sendQueue` и единственной горутины записи (`WritePump`) является обязательным паттерном защиты сетевого сокета от повреждения фреймов.

## Подводные камни

Блокировка очереди `sendQueue` при медленном клиенте. Если сокет клиента подвис, а сервер безостановочно шлет уведомления, буфер очереди переполнится. Необходимо использовать неблокирующий `select` с дропом или принудительным закрытием сессии.

## На собеседовании

В Tinkoff часто спрашивают: 'Как организовать гарантированную доставку JSON-RPC запросов через WebSocket при переподключении клиента?' Ответ: хранить неподтвержденные запросы в локальном Replay-буфере клиента (Pending Queue). При восстановлении сессии отправлять их повторно с теми же UUID идентификаторами, а на сервере использовать фильтрацию дубликатов по ID.
