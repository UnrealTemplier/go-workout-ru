# Разграничение системных (-32601) и доменных (-32000) ошибок

## Условие

30. **Стандартные ошибки JSON-RPC.**: Реализуйте возврат ошибок в формате `{"code": -32601, "message": "Method not found"}` для неизвестных методов. При ошибке в обработчике возвращайте код `-32000` с описанием.

### Исходная формулировка

**Стандартные ошибки JSON-RPC.**: Реализуйте возврат ошибок в формате `{"code": -32601, "message": "Method not found"}` для неизвестных методов. При ошибке в обработчике возвращайте код `-32000` с деталями.

## Теория

Архитектурная чистота слоя ошибок в JSON-RPC:
1. **Протокольные ошибки (Protocol Errors):**
   - Коды от `-32700` до `-32600`.
   - Генерируются **транспортным каркасом (Framework)** до вызова пользовательского кода.
   - Метод не найден (`-32601`) — клиент ошибся в URL или имени процедуры.
2. **Прикладные ошибки (Application Errors):**
   - Коды от `-32000` до `-32099` (или любые пользовательские целые числа вне диапазона `-32768..-32000`).
   - Генерируются **бизнес-логикой обработчика**.
   - Недостаточно прав, товар распродан, превышен кредитный лимит.

## Решение по шагам

1. Создайте функции возврата ошибок `SendProtocolError` и `SendAppError`.
2. В роутере проверьте наличие метода: при отсутствии верните `-32601`.
3. В обработчике метода сымитируйте бизнес-ошибку и верните `-32000`.
4. Протестируйте оба сценария.

## Код решения

**`error_distinction.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
)

type ErrorResponse struct {
	JSONRPC string        `json:"jsonrpc"`
	Error   ErrorEnvelope `json:"error"`
	ID      any           `json:"id"`
}

type ErrorEnvelope struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data,omitempty"`
}

func rpcDispatcher(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")

	var req struct {
		JSONRPC string          `json:"jsonrpc"`
		Method  string          `json:"method"`
		Params  json.RawMessage `json:"params"`
		ID      any             `json:"id"`
	}

	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		_ = json.NewEncoder(w).Encode(ErrorResponse{
			JSONRPC: "2.0",
			Error:   ErrorEnvelope{Code: -32700, Message: "Parse error"},
			ID:      nil,
		})
		return
	}

	// 1. Протокольная ошибка: неизвестный метод
	if req.Method != "orders.cancel" {
		_ = json.NewEncoder(w).Encode(ErrorResponse{
			JSONRPC: "2.0",
			Error:   ErrorEnvelope{Code: -32601, Message: "Method not found"},
			ID:      req.ID,
		})
		return
	}

	// 2. Прикладная ошибка бизнес-логики: заказ уже отправлен курьером
	_ = json.NewEncoder(w).Encode(ErrorResponse{
		JSONRPC: "2.0",
		Error: ErrorEnvelope{
			Code:    -32000,
			Message: "Order cannot be cancelled: already dispatched to courier",
			Data: map[string]string{
				"order_status": "IN_DELIVERY",
			},
		},
		ID: req.ID,
	})
}

func main() {
	http.HandleFunc("/rpc", rpcDispatcher)
	fmt.Println("Error distinction server running on :8080/rpc")
	_ = http.ListenAndServe(":8080", nil)
}
```

ℹ️ Четкое разделение протокольных ошибок каркаса (-32601) и доменных сбоев (-32000)

## Под капотом

Такое разделение кодов позволяет мониторингу (Prometheus / Grafana) строить независимые алерты: всплеск ошибок `-32601` свидетельствует о несовместимости версий клиента и сервера после релиза, а ошибки `-32000` отражают нормальный процент отказов бизнес-валидаций.

## Подводные камни

Использование произвольных отрицательных чисел вроде `-1` или `-100`. Спецификация резервирует весь диапазон отрицательных чисел от `-32768` до `-32000`. Использование кодов вне зарезервированного диапазона (например, положительные коды ошибок) считается безопасным.

## На собеседовании

В Авито и Яндекс часто спрашивают: 'Как организовать карту соответствия кодов ошибок (Error Code Mapping) при переходе с REST на JSON-RPC?' Ответ: 404 Not Found маппится в -32601 (если не найден метод) или в доменный код -32004 (если не найден конкретный ресурс в БД, например User NotFound). 400 Bad Request маппится в -32602 (Invalid Params).
