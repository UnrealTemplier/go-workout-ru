# Ограничения HTTP/1.1 (Head-of-Line Blocking) и тюнинг пула соединений

### Исходная формулировка

Реализуйте клиент с connection pool (`http.Transport.MaxConnsPerHost`, `DisableKeepAlives: false`). Сравните latency batch-запросов через HTTP/1.1 и HTTP/2 (gRPC использует HTTP/2 именно поэтому). ---

## Теория

Проблемы JSON-RPC поверх протокола HTTP/1.1:
1. **Head-of-Line (HoL) Blocking на уровне соединений:**
   - В HTTP/1.1 в рамках одного TCP-сокета запросы передаются строго последовательно.
   - Клиент не может отправить следующий RPC-вызов, пока не прочитает полный ответ на предыдущий.
   - Если сервер выполняет долгий запрос, все последующие вызовы в этом сокете блокируются.
2. **Накладные расходы на Handshake:**
   - Без пула соединений (Connection Pooling) каждый RPC-вызов открывает новый TCP сокет и выполняет TLS-рукопожатие, теряя от 50 до 150 мс на пустые сетевые RTT.

Решение в Go:
- Использование долгоживущего пула Keep-Alive соединений: `http.Transport`.
- Настройка `MaxIdleConnsPerHost`: количество удерживаемых сокетов в режиме ожидания.
- Настройка `MaxConnsPerHost`: защита сервера от лавинного создания сокетов.
- Переход на HTTP/2 для мультиплексирования сотен параллельных RPC-вызовов внутри одного TCP-соединения.

## Решение по шагам

1. Создайте оптимизированный экземпляр `http.Transport`.
2. Задайте `MaxIdleConns: 100`, `MaxIdleConnsPerHost: 50`, `IdleConnTimeout: 90 * time.Second`.
3. Убедитесь, что `DisableKeepAlives = false`.
4. Реализуйте параллельную отправку 50 RPC-запросов через настроенный клиент.

## Код решения

**`tuned_transport.go`**

```go
package main

import (
	"bytes"
	"context"
	"fmt"
	"io"
	"net"
	"net/http"
	"sync"
	"time"
)

func NewOptimizedRPCClient() *http.Client {
	transport := &http.Transport{
		Proxy: http.ProxyFromEnvironment,
		DialContext: (&net.Dialer{
			Timeout:   5 * time.Second,  // Таймаут установления TCP
			KeepAlive: 30 * time.Second, // TCP Keep-Alive зонды
		}).DialContext,
		ForceAttemptHTTP2:     true, // Включение автоматического мультиплексирования HTTP/2
		MaxIdleConns:          200,  // Общий лимит свободных сокетов
		MaxIdleConnsPerHost:   100,  // Пул свободных сокетов на наш RPC бэкенд
		MaxConnsPerHost:       200,  // Максимальное число одновременных сокетов
		IdleConnTimeout:       90 * time.Second,
		TLSHandshakeTimeout:   5 * time.Second,
		ResponseHeaderTimeout: 10 * time.Second,
		DisableKeepAlives:     false, // КРИТИЧЕСКИ ВАЖНО: Keep-Alive включен!
	}

	return &http.Client{
		Transport: transport,
		Timeout:   15 * time.Second,
	}
}

func main() {
	client := NewOptimizedRPCClient()
	url := "http://localhost:8080/rpc"

	var wg sync.WaitGroup
	start := time.Now()

	// Параллельная отправка 20 запросов через пул сокетов
	for i := 1; i <= 20; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			reqPayload := fmt.Sprintf(`{"jsonrpc":"2.0","method":"ping","id":%d}`, id)
			req, _ := http.NewRequestWithContext(context.Background(), "POST", url, bytes.NewBufferString(reqPayload))
			req.Header.Set("Content-Type", "application/json")

			resp, err := client.Do(req)
			if err != nil {
				return
			}
			// ОБЯЗАТЕЛЬНО: вычитать тело и закрыть, иначе соединение не вернется в пул!
			_, _ = io.Copy(io.Discard, resp.Body)
			_ = resp.Body.Close()
		}(i)
	}

	wg.Wait()
	fmt.Printf("20 RPC calls completed through connection pool in %v\n", time.Since(start))
}
```

ℹ️ Тюнинг http.Transport с пулом Keep-Alive сокетов для устранения накладных расходов TCP

## Под капотом

Если разработчик забывает закрыть `resp.Body.Close()` или не вычитывает тело до конца через `io.Copy(io.Discard, resp.Body)`, рантайм Go не может вернуть сокет в пул `idleConn` и закрывает TCP-соединение. При высокой нагрузке это вызывает взрывной рост сокетов в состоянии `TIME_WAIT` ядра Linux.

## Подводные камни

Использование значения `MaxIdleConnsPerHost` по умолчанию. В `http.DefaultTransport` параметр `MaxIdleConnsPerHost` равен всего **2**! Если вы отправляете 100 одновременных запросов к одному хосту, 98 сокетов будут закрываться сразу после каждого запроса, полностью нивелируя пользу Keep-Alive.

## На собеседовании

В Wildberries на интервью спрашивают: 'Какое значение имеет `net.ipv4.tcp_tw_reuse` в Linux и как оно связано с connection pool в Go?' Ответ: При частых закрытиях соединений сокеты зависают в состоянии TIME_WAIT на 60 секунд. Опция `tcp_tw_reuse = 1` в ядре позволяет безопасно переиспользовать сокеты в TIME_WAIT для новых исходящих подключений, защищая систему от исчерпания диапазона эфемерных портов (`ephemeral ports`).
