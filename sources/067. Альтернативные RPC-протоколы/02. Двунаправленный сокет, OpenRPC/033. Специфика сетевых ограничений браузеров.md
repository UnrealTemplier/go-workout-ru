# Специфика сетевых ограничений браузеров и невозможность чистого gRPC

### Исходная формулировка

**Проблема gRPC в браузерах**: Изучите, почему чистый gRPC не работает из браузера (нет доступа к HTTP/2 trailers, нет client streaming без XHR/fetch limitations).

## Теория

Почему веб-браузеры не способны выполнять прямые gRPC-вызовы без промежуточного слоя gRPC-Web или Envoy:

1. **Отсутствие доступа к HTTP/2 Trailers:**
   - gRPC протокол передает код завершения процедуры (`grpc-status: 0` для OK, `grpc-status: 5` для NotFound) в **Trailer Headers**.
   - Браузерный объект `fetch()` и `XMLHttpRequest` предоставляют доступ только к начальным заголовкам ответа (`response.headers`). Трейлеры, отправленные в конце потока данных, скрыты внутри C++ движка браузера (Chromium Blink / WebKit / Gecko).
2. **Ограничения клиентского стриминга (Client-Side Streaming):**
   - Браузерный `fetch()` исторически не поддерживал потоковую запись тела запроса (`ReadableStream` в качестве `request.body`). Даже в современных браузерах эта функция имеет строгие ограничения (отсутствие полудуплекса).
3. **Строгая изоляция сетевых сокетов:**
   - Веб-страницы изолированы политиками безопасности (Same-Origin Policy, CORS) и не имеют доступа к сырым TCP/HTTP/2 сокетам.

## Решение по шагам

1. Опишите сетевые слои стандартного gRPC и gRPC-Web.
2. Реализуйте симуляцию браузерного окружения, не умеющего читать trailers.
3. Продемонстрируйте механизм трансляции trailers в бинарный блок данных внутри тела ответа.

## Код решения

**`grpc_limitation.go`**

```go
package main

import (
	"fmt"
	"net/http"
)

// Демонстрация стандартного gRPC ответа: трейлеры передаются вне тела
func standardGRPCHandler(w http.ResponseWriter, r *http.Request) {
	// 1. Начальные заголовки
	w.Header().Set("Content-Type", "application/grpc")
	w.WriteHeader(http.StatusOK)

	// 2. Тело Protobuf
	_, _ = w.Write([]byte{0x00, 0x00, 0x00, 0x00, 0x05, 'H', 'e', 'l', 'l', 'o'})

	// 3. HTTP/2 Trailers: недоступны в JavaScript fetch()
	w.Header().Set("Trailer", "grpc-status, grpc-message")
	w.Header().Set("grpc-status", "0")
	w.Header().Set("grpc-message", "OK")
}

// Демонстрация gRPC-Web: прокси упаковывает трейлеры прямо в тело!
func grpcWebTransformedHandler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/grpc-web+proto")
	w.WriteHeader(http.StatusOK)

	// Фрейм 1 (DATA): 0x00 + 4 байта длины + тело
	_, _ = w.Write([]byte{0x00, 0x00, 0x00, 0x00, 0x05, 'H', 'e', 'l', 'l', 'o'})

	// Фрейм 2 (TRAILERS в теле!): 0x80 (старший бит) + длина + текст трейлеров
	trailerText := []byte("grpc-status: 0\r\ngrpc-message: OK\r\n")
	trailerLen := byte(len(trailerText))
	header := []byte{0x80, 0x00, 0x00, 0x00, trailerLen}

	_, _ = w.Write(append(header, trailerText...))
}

func main() {
	http.HandleFunc("/grpc.test.Standard", standardGRPCHandler)
	http.HandleFunc("/grpc.test.Web", grpcWebTransformedHandler)

	fmt.Println("Browser limitations demo server running on :8080")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

В Chromium реализация сетевого стека `net::HttpNetworkTransaction` считывает трейлеры, но интерфейс `Blink::FetchResponseData` намеренно отфильтровывает их из объекта `Response`, чтобы не нарушать спецификацию W3C Fetch. Именно поэтому сообществу пришлось разработать стандарт gRPC-Web, эмулирующий трейлеры внутри байтового потока данных.

## Подводные камни

Попытка обращаться к gRPC-серверу напрямую из браузера по протоколу `http://`. Сервер вернет ошибку отсутствия `application/grpc` либо немедленно закроет TCP сокет из-за отсутствия HTTP/2 фреймов.

## На собеседовании

В Ozon и Авито часто спрашивают: 'Можно ли использовать ConnectRPC в браузере без прокси Envoy?' Ответ: Да! ConnectRPC был специально разработан компанией Buf для решения этой проблемы: он передает ошибки и статусы в стандартном JSON-формате или через обычные HTTP-заголовки, работая через стандартный fetch() без Envoy и сложных прокси-оберток.
