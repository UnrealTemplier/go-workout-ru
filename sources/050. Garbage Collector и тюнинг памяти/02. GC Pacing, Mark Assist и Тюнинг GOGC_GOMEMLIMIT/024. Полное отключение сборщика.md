# Полное отключение сборщика: GOGC=off и debug.SetGCPercent(-1)

## Условие

Установите GOGC=off через debug.SetGCPercent(-1). Запустите программу, которая аллоцирует данные в цикле, и убедитесь, что сборка мусора не запускается автоматически, а память растет линейно до явного вызова runtime.GC().

### Исходная формулировка

**[Отключение GC]**: Установи `GOGC=off` (`debug.SetGCPercent(-1)`). Запусти программу, которая аллоцирует в цикле. Убедись, что процесс съест всю память и упадет с OOM.

## Теория

Рантайм Go позволяет полностью отключить периодический запуск сборщика мусора:
* Через переменную окружения: `export GOGC=off`
* Программно: `debug.SetGCPercent(-1)`

Что происходит при отключении GC:
1. Автоматический триггер пейсера блокируется (`gcpercent = -1`).
2. Фоновые маркер-воркеры не запускаются, затраты CPU на разметку равны нулю.
3. Барьеры записи никогда не включаются, мутаторы работают на предельной скорости.
4. **Вся аллоцированная память остается в куче навсегда**, пока не будет явно вызвана функция `runtime.GC()`.

Сценарии применения:
* **Краткосрочные CLI утилиты:** Утилита отрабатывает за 200 мс и завершается — ОС освободит всю память процесса мгновенно, тратить CPU на GC нет смысла.
* **Высокоскоростной batch-процессинг с контролируемыми окнами очистки:** Пакет данных обрабатывается с отключенным GC, после чего в межпакетную паузу вызывается `runtime.GC()`.

## Решение по шагам

1. Отключите автоматический сборщик через `debug.SetGCPercent(-1)`.
2. Выполните тысячи аллокаций и проверьте, что `NumGC` не увеличивается.
3. Проверьте линейный рост `HeapAlloc`.
4. Вызовите явный `runtime.GC()` и восстановите настройки.

## Код решения

**`gc_off.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	var m1, m2, m3 runtime.MemStats

	// Отключаем GC
	oldGOGC := debug.SetGCPercent(-1)
	defer debug.SetGCPercent(oldGOGC)

	runtime.ReadMemStats(&m1)
	fmt.Printf("1. GC отключен (GOGC = -1). Начальный HeapAlloc: %8.2f МБ, NumGC: %d\n",
		float64(m1.HeapAlloc)/(1024*1024), m1.NumGC)

	// Создаем 50 000 временных объектов
	for i := 0; i < 50000; i++ {
		_ = make([]byte, 1024)
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("2. После 50k аллокаций:    HeapAlloc: %8.2f МБ, NumGC: %d (GC НЕ запускался!)\n",
		float64(m2.HeapAlloc)/(1024*1024), m2.NumGC)

	// Явный запуск
	fmt.Println("3. Принудительный вызов runtime.GC()...")
	runtime.GC()

	runtime.ReadMemStats(&m3)
	fmt.Printf("4. После явного GC:        HeapAlloc: %8.2f МБ, NumGC: %d\n",
		float64(m3.HeapAlloc)/(1024*1024), m3.NumGC)
}
```

ℹ️ Отключение автоматического GC и контроль за линейным ростом кучи

## Под капотом

В `src/runtime/mgcpacer.go` функция `gcTrigger.test()` проверяет условие `gcpercent < 0`. Если условие истинно, триггер `gcTriggerHeap` всегда возвращает `false`, предотвращая переход рантайма в состояние `_GCmark`.

## Подводные камни

В долгоживущих серверах отключение GC без строжайшего контроля приводит к исчерпанию оперативной памяти и падению от Linux OOM Killer. Даже при `GOGC=off` рантайм Go 1.19+ будет учитывать `GOMEMLIMIT`! При приближении к `GOMEMLIMIT` сборщик мусора запустится принудительно, несмотря на `GOGC=-1`.

## На собеседовании

**Вопрос:** Сработает ли сборщик мусора в Go 1.19+, если установлен GOGC=off, но процесс приближается к лимиту GOMEMLIMIT?
**Ответ:** Да! Это фундаментальное изменение Go 1.19. Параметр GOMEMLIMIT имеет приоритет над GOGC. Даже если автоматический запуск по проценту роста отключен (GOGC=off), рантайм принудительно включит сборщик мусора при приближении к порогу GOMEMLIMIT, чтобы спасти контейнер от OOMKilled.
