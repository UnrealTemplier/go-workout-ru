# Управление темпом сборки (GC Pacing) и Mark Assist дроппинг

## Условие

Изучите концепцию Pacing в деталях. Как рантайм балансирует между фоновыми воркерами и Mark Assist? Напишите программу, наглядно демонстрирующую замедление аллоцирующей горутины при превышении квоты байт.

### Исходная формулировка

**[GC Pacing]**: Изучи концепцию Pacing. GC пытается завершить Marking до того, как куча вырастет до `goal` (с учетом GOGC). Если приложение аллоцирует слишком быстро, GC не успевает, и рантайм вынужден остановить приложение (Stop-The-World на аллокации), чтобы дождаться GC.

## Теория

Математика GC Pacing в Go строится вокруг концепции **Assist Credit (Кредит помощи)**.

Каждый раз, когда фоновые маркер-воркеры сканируют объект, они начисляют глобальные "кредиты разметки".
Когда горутина вызывает `runtime.mallocgc(size)`:
1. Она обязана "купить" право на аллокацию `size` байт, списав соответствующее количество кредитов помощи со своего баланса `g.gcAssistBytes`.
2. Если на счету горутины образовался дефицит (отрицательный баланс), горутина **не имеет права продолжить выполнение**.
3. Она принудительно переводится в функцию `gcAssistAlloc`, где сканирует серые объекты кучи пропорционально своему долгу:
   $$\text{WorkRequired} = \text{size} \times \text{assistWorkPerByte}$$
4. Только отработав долг, горутина получает свой блок памяти и возвращается к выполнению кода.

## Решение по шагам

1. Запустите фоновую горутину с интенсивной аллокацией крупных массивов.
2. Замерьте время выполнения одиночной операции `make()` в нормальном режиме и во время активного GC.
3. Обратите внимание, что время одиночной аллокации вырастает в сотни раз из-за включения Mark Assist.

## Код решения

**`assist_throttle.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	fmt.Println("=== Исследование задержек при Mark Assist ===")

	// 1. Замер аллокации в спокойном состоянии
	runtime.GC()
	t1 := time.Now()
	_ = make([]byte, 1024*1024)
	quietAllocTime := time.Since(t1)
	fmt.Printf("Время аллокации 1 МБ в спокойном режиме: %v\n", quietAllocTime)

	// 2. Создаем тяжелую конкурентную нагрузку
	stop := make(chan bool)
	go func() {
		for {
			select {
			case <-stop:
				return
			default:
				_ = make([]byte, 2*1024*1024)
			}
		}
	}()

	time.Sleep(20 * time.Millisecond)

	// 3. Замер аллокации под давлением GC
	var maxDelay time.Duration
	for i := 0; i < 20; i++ {
		start := time.Now()
		_ = make([]byte, 1024*1024)
		dur := time.Since(start)
		if dur > maxDelay {
			maxDelay = dur
		}
	}

	close(stop)
	fmt.Printf("Максимальная задержка аллокации под GC (Mark Assist): %v\n", maxDelay)
	fmt.Printf("Замедление операции составило: %.1fx раз\n",
		float64(maxDelay)/float64(quietAllocTime))
}
```

ℹ️ Демонстрация деградации времени аллокации при попадании в Mark Assist

## Под капотом

Коэффициент `assistWorkPerByte` вычисляется в `mgcpacer.go` как отношение оставшейся работы по разметке к оставшемуся бюджету байт кучи до `HeapGoal`. Если куча растет быстрее прогноза, коэффициент растет экспоненциально, превращая аллокаторы почти в 100% разметчиков.

## Подводные камни

В системах реального времени (High-Frequency Trading) возникновение Mark Assist недопустимо. Чтобы исключить Mark Assist, критические пути сервиса полностью очищают от любых аллокаций в куче (Zero Allocations).

## На собеседовании

**Вопрос:** Как механизм Mark Assist защищает программу от Out-Of-Memory, но ухудшает хвост задержек (Tail Latency)?
**Ответ:** Mark Assist не позволяет горутинам выделять память быстрее, чем ее помечает GC. Заставляя аллоцирующие горутины отрабатывать "долг" сканированием кучи, рантайм искусственно замедляет мутаторы, сдерживая рост кучи в пределах HeapGoal. Однако конкретный HTTP-запрос, чья горутина попала в Mark Assist, испытывает задержку в десятки миллисекунд, портя метрики p99/p999.
