# Бенчмаркинг длительности пауз STW в микросекундах

## Условие

Напишите бенчмарк, измеряющий задержки Stop-The-World с точностью до микросекунд при разном объеме живой памяти в куче (1 МБ, 100 МБ, 500 МБ).

### Исходная формулировка

**Фазы GC (STW)**: GC в Go имеет 4 фазы, две из которых требуют Stop The World (остановки всех горутин). Напиши бенчмарк, измеряющий задержки. Запусти программу с `GODEBUG=gctrace=1`. В выводе консоли ты увидишь строки вида `gc 1 @0.012s 1%: 0.02+1.5+0.04 ms clock...`. Расшифруй их: первая цифра (0.02) — STW при Mark Termination (подготовка барьеров записи), вторая (1.5) — конкурентная маркировка, третья (0.04) — STW при Sweep Termination. Убедись, что паузы STW реально составляют доли миллисекунд.

## Теория

Одним из главных преимуществ Go перед Java (HotSpot CMS/G1) является предсказуемость задержек:
* В ранних версиях Go (до 1.5) длительность STW росла линейно с размером кучи (\(O(\text{HeapSize})\)) и достигала сотен миллисекунд.
* В современном Go длительность STW зависит **только от количества активных горутин и корневых указателей** (\(O(\text{Goroutines})\)), но практически не зависит от объема памяти в куче (\(O(1)\) относительно размера кучи).

Даже при куче в 50 Гигабайт длительность фаз STW (Mark Setup и Mark Termination) остается в пределах 100–500 микросекунд, поскольку вся тяжелая работа разметки выполняется конкурентно.

## Решение по шагам

1. Создайте функцию замера длительности `runtime.GC()`.
2. Измерьте паузы при куче 1 МБ.
3. Наполните кучу до 100 МБ и повторите замер.
4. Убедитесь, что длительность STW остается субмиллисекундной.

## Код решения

**`stw_bench.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func measureSTW(heapMB int) time.Duration {
	// Создаем живые данные заданного объема
	data := make([][]byte, heapMB)
	for i := range data {
		data[i] = make([]byte, 1024*1024)
	}

	// Прогрев
	runtime.GC()

	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	startPause := m.PauseTotalNs

	// Запуск целевого GC
	runtime.GC()

	runtime.ReadMemStats(&m)
	_ = data
	return time.Duration(m.PauseTotalNs - startPause)
}

func main() {
	fmt.Println("=== Исследование независимости STW от размера кучи ===")
	sizes := []int{5, 50, 150}

	for _, sz := range sizes {
		pause := measureSTW(sz)
		fmt.Printf("Куча: %3d МБ | Длительность STW: %8v (всего %.3f мс)\n",
			sz, pause, float64(pause.Nanoseconds())/1e6)
	}
}
```

ℹ️ Замер субмиллисекундных пауз STW при различных размерах кучи

## Под капотом

Остановка мира в `src/runtime/proc.go` (`stopTheWorldWithSema`) переводит все логические процессоры P в состояние `_Pgcstop`. Время остановки определяется тем, как быстро активные горутины отреагируют на сигнал прерывания. Сама куча при этом не сканируется, поэтому ее объем не влияет на время STW.

## Подводные камни

Единственный фактор, способный резко увеличить STW в Go — это наличие сотен тысяч одновременно запущенных горутин. Сканирование корневых стеков всех горутин выполняется во время разметки, но перевод всех P в `_Pgcstop` при огромном числе потоков может занять дополнительные миллисекунды.

## На собеседовании

**Вопрос:** Зависит ли время паузы Stop-The-World в современном Go от объема выделенной оперативной памяти?
**Ответ:** Практически не зависит. Время STW определяется остановкой процессоров P, включением/выключением барьеров записи и очисткой локальных mcache. Вся работа по сканированию гигабайт кучи вынесена в конкурентную фазу (Concurrent Marking). Задержка STW масштабируется от числа ядер и количества горутин, но остается субмиллисекундной даже на 100 ГБ кучи.
