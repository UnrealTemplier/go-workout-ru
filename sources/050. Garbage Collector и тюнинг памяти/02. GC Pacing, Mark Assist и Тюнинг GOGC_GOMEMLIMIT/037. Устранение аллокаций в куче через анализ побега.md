# Устранение аллокаций в куче через анализ побега (-gcflags="-m")

## Условие

Используйте escape analysis (-gcflags="-m") для выявления нежелательных heap-аллокаций. Перепишите функцию так, чтобы переменные оставались на стеке горутины, исключая нагрузку на GC.

### Исходная формулировка

**Avoid heap allocations**: Используйте escape analysis (`-gcflags="-m"`) для выявления неожиданных heap аллокаций. Переписывайте код для stack allocation.

## Теория

Анализ побега (**Escape Analysis**) — ключевой этап оптимизации компилятора Go:
* Если компилятор может строго доказать, что время жизни переменной не превышает время выполнения функции, переменная размещается на **стеке**.
* Выделение на стеке стоит 0 инструкций CPU (просто смещение указателя стека `RSP`).
* Освобождение со стека происходит мгновенно при возврате из функции (`RET`) и **полностью бесплатно для сборщика мусора**.

Типичные причины нежелательного побега в кучу:
1. Передача значения в функцию, принимающую `any` / `interface{}` (например, `fmt.Println(x)`).
2. Замыкания, захватывающие локальные переменные по ссылке.
3. Возврат указателя на локальную переменную наружу.
4. Выделение срезов динамического размера (`make([]byte, n)`).

## Решение по шагам

1. Напишите функцию с побегом переменной из-за интерфейсного боксинга.
2. Проанализируйте отчет компилятора: `go build -gcflags="-m"`.
3. Оптимизируйте функцию, избавившись от интерфейсов и указателей.
4. Убедитесь, что переменная осталась на стеке (`does not escape`).

## Код решения

**`escape_demo.go`**

```go
package main

// PointEscapes возвращает указатель, вызывая побег в кучу
func PointEscapes(x, y int) *Point {
	p := Point{X: x, Y: y}
	return &p // escapes to heap
}

// PointOnStack возвращает значение по значению, оставаясь на стеке
func PointOnStack(x, y int) Point {
	return Point{X: x, Y: y} // does not escape
}

type Point struct {
	X, Y int
}

func main() {
	p1 := PointEscapes(10, 20)
	p2 := PointOnStack(30, 40)
	_ = p1
	_ = p2
}
```

ℹ️ Сравнение побега структуры в кучу и сохранения на стеке

**`Терминал`**

```bash
go build -gcflags="-m -m" escape_demo.go
# Вывод компилятора:
# ./escape_demo.go:6:2: &p escapes to heap
# ./escape_demo.go:5:2: moved to heap: p
```

## Под капотом

Компилятор Go строит направленный граф потока данных (Escape Graph), где узлы — это переменные и операции разыменования, а ребра — присваивания и вызовы. Если от переменной существует путь до глобального корня или аргумента возврата верхнего уровня, переменной присваивается признак `EscHeap`.

## Подводные камни

Чрезмерное увлечение передачей тяжелых структур по значению ради стека может привести к деградации производительности из-за накладных расходов на копирование сотен байт памяти при каждом вызове функции.

## На собеседовании

**Вопрос:** Как флаг компилятора -gcflags="-m" помогает оптимизировать работу сборщика мусора?
**Ответ:** Флаг включает подробный отчет Escape Analysis. Он показывает, какие переменные компилятор перемещает в кучу (`moved to heap`, `escapes to heap`), а какие оставляет на стеке. Устраняя причины побега (интерфейсный боксинг, замыкания, возврат указателей), инженер оставляет переменные на стеке, что полностью освобождает Garbage Collector от необходимости управлять этой памятью.
