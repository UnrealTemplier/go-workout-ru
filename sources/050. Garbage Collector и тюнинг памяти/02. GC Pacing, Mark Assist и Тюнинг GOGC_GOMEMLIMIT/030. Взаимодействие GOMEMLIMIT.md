# Взаимодействие GOMEMLIMIT и GOGC при дефиците памяти

## Условие

Установите GOMEMLIMIT=100MiB и GOGC=200. Запустите программу. Объясните, как GOMEMLIMIT переопределяет GOGC: если лимит в опасности, пейсер отбрасывает цель по GOGC и запускает GC принудительно.

### Исходная формулировка

**[GOMEMLIMIT (Soft Memory Limit)]**: Установи `GOMEMLIMIT=100MiB` и `GOGC=200`. Запусти программу. Объясни, как GOMEMLIMIT переопределяет GOGC: если лимит в 100MB близок, GC запустится раньше, чтобы не упереться в лимит ОС (спасение для Kubernetes OOMKilled).

## Теория

Когда установлены одновременно `GOGC` и `GOMEMLIMIT`, пейсер Go (`mgcpacer.go`) рассчитывает две независимые цели для следующего цикла сборки:

1. **Цель по GOGC:**
   $$\text{Goal}_{\text{GOGC}} = \text{LiveHeap} \times \left(1 + \frac{\text{GOGC}}{100}\right)$$

2. **Цель по GOMEMLIMIT:**
   $$\text{Goal}_{\text{Limit}} = \text{GOMEMLIMIT} - \text{NonHeapMemory}$$
   (где NonHeapMemory включает стеки горутин, статические глобалы и оверхед рантайма).

**Правило выбора:**
$$\text{NextGC} = \min(\text{Goal}_{\text{GOGC}}, \text{Goal}_{\text{Limit}})$$

Если объем живых данных мал (например, 10 МБ при лимите 100 МБ), действует цель по GOGC=200 (NextGC = 30 МБ). Но если живые данные выросли до 70 МБ, цель по GOGC=200 потребовала бы 210 МБ, что превысило бы 100 МБ! В этот момент пейсер переключается на лимит памяти и запускает сборку заблаговременно.

## Решение по шагам

1. Задайте программно `debug.SetGCPercent(200)` и `debug.SetMemoryLimit(64 * 1024 * 1024)`.
2. Аллоцируйте последовательные блоки данных.
3. Отслеживайте значение `ms.NextGC`.
4. Обратите внимание, что `NextGC` никогда не превышает 64 МБ, игнорируя утроение от `GOGC=200`.

## Код решения

**`memlimit_override.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	const limitBytes = 64 * 1024 * 1024 // 64 МБ
	debug.SetMemoryLimit(limitBytes)
	debug.SetGCPercent(200) // хотим утроение кучи

	fmt.Printf("GOMEMLIMIT = %d МБ, GOGC = 200\n", limitBytes/(1024*1024))

	// Накапливаем постоянные данные
	var retained [][]byte
	var ms runtime.MemStats

	for i := 0; i < 5; i++ {
		chunk := make([]byte, 10*1024*1024)
		retained = append(retained, chunk)

		runtime.ReadMemStats(&ms)
		liveMB := float64(ms.Alloc) / (1024 * 1024)
		nextMB := float64(ms.NextGC) / (1024 * 1024)

		fmt.Printf("Шаг %d: Live = %5.1f МБ | NextGC = %5.1f МБ (Лимит: 64 МБ)\n",
			i+1, liveMB, nextMB)
	}
	_ = retained
}
```

ℹ️ Динамическое ограничение NextGC со стороны GOMEMLIMIT

## Под капотом

В `src/runtime/mgcpacer.go` метод `gcControllerState.heapGoalInternal` сравнивает две цели и берет минимальную. Если цель по лимиту оказывается меньше текущего размера кучи, рантайм активирует защиту от зацикливания: сборщик мусора не может потреблять больше 50% CPU приложения на окне в 1 секунду.

## Подводные камни

Если живые данные устойчиво превышают `GOMEMLIMIT` (например, база данных в памяти заняла 90 МБ при лимите 80 МБ), сборщик мусора не сможет освободить память, упрется в лимит 50% CPU и позволит процессу упасть по OOM, защищая хост от 100% CPU lockup.

## На собеседовании

**Вопрос:** Что произойдет, если в Go сервисе с GOMEMLIMIT=1GiB объем неудаляемых живых объектов превысит 1.1GiB?
**Ответ:** Произойдет аварийное завершение процесса по Out-Of-Memory (OOM). Сборщик мусора Go спроектирован так, что soft limit не должен приводить к бесконечной блокировке CPU (GC Thrashing). Если после максимального выделения 50% бюджета CPU память не опускается ниже лимита, аллокатор продолжит выделение и отдаст решение операционной системе (Linux OOM-Killer).
