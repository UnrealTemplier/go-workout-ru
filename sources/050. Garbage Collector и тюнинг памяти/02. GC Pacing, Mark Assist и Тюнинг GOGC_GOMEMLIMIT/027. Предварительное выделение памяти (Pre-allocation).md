# Предварительное выделение памяти (Pre-allocation) против давления на GC

## Условие

Используйте make([]T, 0, capacity) для предварительной аллокации слайсов. Измерьте разницу в количестве выделений кучи и вызовов GC при последовательном append без емкости и с известной емкостью.

### Исходная формулировка

**Pre-allocation**: Используйте `make([]T, 0, capacity)` для предварительной аллокации слайсов. Измерьте разницу в аллокациях через бенчмарки.

## Теория

Операция `append(slice, item)` при нехватке свободного места (`len == cap`) вынуждена:
1. Выделить в куче новый срез увеличенного размера (алгоритм роста: удвоение до 256 элементов, затем плавный коэффициент \(\approx 1.25\) в Go 1.18+).
2. Скопировать все старые элементы в новый массив через `runtime.memmove`.
3. Оставить старый массив в куче в качестве мусора для GC.

При добавлении 1 000 000 элементов без предварительного указания емкости срез будет реаллоцирован более 30 раз! Это порождает гигабайты промежуточного мусора, забивает пулы `mcache` и заставляет GC непрерывно работать на 25% CPU.

## Решение по шагам

1. Напишите функцию наполнения среза без `cap`: `make([]int, 0)`.
2. Напишите функцию с известной емкостью: `make([]int, 0, N)`.
3. Замерьте суммарное количество сборок мусора `NumGC` и время работы.
4. Проверьте разницу в бенчмарке через `testing.B`.

## Код решения

**`prealloc_bench.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func runAppendWithoutCap(n int) (time.Duration, uint32, uint64) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	var s []int
	for i := 0; i < n; i++ {
		s = append(s, i)
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	_ = s
	return elapsed, m2.NumGC - m1.NumGC, m2.TotalAlloc - m1.TotalAlloc
}

func runAppendWithCap(n int) (time.Duration, uint32, uint64) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	s := make([]int, 0, n)
	for i := 0; i < n; i++ {
		s = append(s, i)
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	_ = s
	return elapsed, m2.NumGC - m1.NumGC, m2.TotalAlloc - m1.TotalAlloc
}

func main() {
	const count = 10000000
	fmt.Printf("=== Тест предварительного выделения памяти (%d элементов) ===\n", count)

	d1, gc1, alloc1 := runAppendWithoutCap(count)
	fmt.Printf("Без емкости (make([]int, 0)):     Время: %-10v | GC: %-2d | Выделено: %6.1f МБ\n",
		d1, gc1, float64(alloc1)/(1024*1024))

	d2, gc2, alloc2 := runAppendWithCap(count)
	fmt.Printf("С емкостью (make([]int, 0, cap)): Время: %-10v | GC: %-2d | Выделено: %6.1f МБ\n",
		d2, gc2, float64(alloc2)/(1024*1024))
}
```

ℹ️ Сравнение времени работы, числа сборок GC и кумулятивной памяти при pre-allocation

## Под капотом

При превышении емкости компилятор вызывает функцию `runtime.growslice`. Она округляет требуемый объем байт до ближайшего стандартного класса размера спана (`runtime.roundupsize`). Без задания емкости `growslice` вызывается десятки раз, порождая целую цепочку брошенных массивов разного калибра.

## Подводные камни

Не выделяйте гигантскую емкость "с запасом на всякий случай" (например, `make([]int, 0, 1000000)` для запроса, где обычно приходит 5 элементов). Это приведет к неэффективному использованию кучи и быстрому исчерпанию лимита памяти.

## На собеседовании

**Вопрос:** Как неоптимальная работа со слайсами влияет на производительность Garbage Collector в Go?
**Ответ:** Постоянное расширение срезов через `append` без емкости генерирует множество промежуточных массивов, которые мгновенно становятся мусором. Это многократно увеличивает Allocation Rate (TotalAlloc/сек), что заставляет пейсер чаще запускать циклы GC, подключать горутины к Mark Assist и тратить такты CPU на копирование памяти вместо полезной работы.
