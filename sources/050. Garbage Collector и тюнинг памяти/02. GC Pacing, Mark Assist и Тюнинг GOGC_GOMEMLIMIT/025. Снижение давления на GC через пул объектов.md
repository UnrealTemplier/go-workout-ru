# Снижение давления на GC через пул объектов (sync.Pool)

## Условие

Используйте sync.Pool для переиспользования временных буферов и снижения давления на GC. Изучите, как и когда sync.Pool очищается при сборке мусора (двухфазная очистка poolLocal).

### Исходная формулировка

**Object pooling**: Используйте `sync.Pool` для переиспользования объектов и снижения давления на GC. Изучите, как `sync.Pool` очищается при каждом GC cycle.

## Теория

Пул объектов `sync.Pool` — основной инструмент оптимизации аллокаций в высоконагруженных сетевых Go-серверах (fasthttp, gin, grpc-go).

Вместо постоянного создания новых буферов через `make([]byte, size)` с последующей утилизацией через GC, горутина берет готовый буфер из `pool.Get()`, использует его и возвращает обратно через `pool.Put()`.

**Внутреннее устройство и взаимодействие с GC:**
* Каждый пул разбит на локальные структуры по процессорам `poolLocal` (на каждый P), содержащие приватный слот `private` (lock-free) и двухстороннюю очередь `shared` (work-stealing).
* **Поведение при сборке мусора (Go 1.13+):**
  Рантайм использует двухфазную очистку через структуры `local` и `victim`:
  1. В начале фазы Mark Setup содержимое текущего пула `local` перемещается в резервный пул `victim`.
  2. Предыдущее содержимое пула `victim` удаляется сборщиком мусора.
  3. При вызове `pool.Get()` объект сначала ищется в `local`, а если он пуст — извлекается из `victim` (переживая один цикл GC!).
  4. Таким образом, объекты в `sync.Pool` живут как минимум один полный цикл GC после последнего использования, исключая просадку производительности при частых сборках.

## Решение по шагам

1. Создайте `sync.Pool` с генератором срезов байт `New: func() any { return make([]byte, 64*1024) }`.
2. Напишите две функции: аллокация напрямую и получение из пула.
3. Измерьте количество сборок мусора `NumGC` и время работы в обоих случаях.
4. Убедитесь, что переиспользование через пул снижает `NumGC` до нуля.

## Код решения

**`sync_pool_gc.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"runtime"
	"sync"
	"time"
)

var bufPool = sync.Pool{
	New: func() any {
		return new(bytes.Buffer)
	},
}

func withoutPool(iters int) (time.Duration, uint32) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	for i := 0; i < iters; i++ {
		buf := new(bytes.Buffer)
		buf.WriteString("HighLoad Go Workout Exercise Benchmark")
		_ = buf.Bytes()
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	return elapsed, m2.NumGC - m1.NumGC
}

func withPool(iters int) (time.Duration, uint32) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	for i := 0; i < iters; i++ {
		buf := bufPool.Get().(*bytes.Buffer)
		buf.Reset()
		buf.WriteString("HighLoad Go Workout Exercise Benchmark")
		_ = buf.Bytes()
		bufPool.Put(buf)
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	return elapsed, m2.NumGC - m1.NumGC
}

func main() {
	const count = 1000000
	fmt.Printf("=== Сравнение аллокаций: без пула vs sync.Pool (%d итераций) ===\n", count)

	d1, gc1 := withoutPool(count)
	fmt.Printf("Без пула:    Время = %-10v | Сборок GC = %d\n", d1, gc1)

	d2, gc2 := withPool(count)
	fmt.Printf("sync.Pool:   Время = %-10v | Сборок GC = %d\n", d2, gc2)
}
```

ℹ️ Сравнение скорости и нагрузки на GC при использовании sync.Pool

## Под капотом

В `src/sync/pool.go` функция `poolCleanup` вызывается из `runtime/mgc.go` в фазе Mark Setup при удерживаемом STW: `oldPools = victimPools; victimPools = allPools; allPools = nil`. Благодаря механизму victim cache объекты из пула больше не вымываются полностью за одну сборку мусора, что решило проблему cache-thrashing.

## Подводные камни

В `sync.Pool` нельзя складывать срезы с неограниченно растущей емкостью (например, `buf.Grow(10*1024*1024)`). Если один гигантский буфер попадет в пул, он останется в памяти надолго. Перед вызовом `Put` необходимо проверять `cap(buf)` и отбрасывать аномально большие объекты.

## На собеседовании

**Вопрос:** Как очищается sync.Pool при работе сборщика мусора Go?
**Ответ:** Начиная с Go 1.13 в sync.Pool используется механизм victim cache. Во время фазы STW текущие локальные пулы становятся victim-пулами, а предыдущие victim-пулы удаляются. Если объект запрошен из пула, он сначала ищется в основном пуле, а затем в victim. Таким образом, объект должен пережить как минимум два полных цикла GC без использования, чтобы быть уничтоженным.
