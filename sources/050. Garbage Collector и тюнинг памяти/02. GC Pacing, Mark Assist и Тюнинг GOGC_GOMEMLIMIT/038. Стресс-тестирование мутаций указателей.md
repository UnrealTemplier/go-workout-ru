# Стресс-тестирование мутаций указателей под активным GC

## Условие

Напишите программу, которая непрерывно мутирует сложный объектный граф во время интенсивной работы GC. Докажите отсутствие повреждений и потерь данных благодаря барьеру записи.

### Исходная формулировка

**Write Barrier и трёхцветная пометка.**: Напишите программу, которая мутирует объектный граф во время работы GC (изменение указателей). Убедитесь, что GC корректен, и объясните роль write barrier (безопасность при одновременной мутации).

## Теория

Главный критерий надежности сборщика мусора — **Safety (Корректность)**: ни при каких условиях конкурентной мутации графа живой объект не должен быть удален сборщиком.

Тестирование инварианта:
* Создается циклическая сеть объектов.
* Несколько горутин-мутаторов непрерывно перелинковывают ссылки между узлами сети со случайной частотой.
* Параллельно фоновая горутина непрерывно форсирует сборку мусора через `runtime.GC()`.
* Контрольная горутина непрерывно валидирует целостность данных каждого узла.
* Отсутствие panic и nil-pointer dereference доказывает абсолютную корректность работы Write Barrier в многопоточной среде.

## Решение по шагам

1. Создайте структуру кольцевого узла со счетчиком и контрольной суммой.
2. Запустите 4 горутины мутации ссылок.
3. Запустите горутину циклического вызова `runtime.GC()`.
4. Дайте тесту поработать 500 мс и зафиксируйте успешное завершение.

## Код решения

**`graph_mutation_race.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

type Node struct {
	ID    int
	Next  *Node
	Value int
}

func main() {
	fmt.Println("=== Стресс-тест мутации указателей под активным GC ===")

	const nodeCount = 100
	nodes := make([]*Node, nodeCount)
	for i := range nodes {
		nodes[i] = &Node{ID: i, Value: i * 10}
	}

	// Связываем в кольцо
	for i := 0; i < nodeCount; i++ {
		nodes[i].Next = nodes[(i+1)%nodeCount]
	}

	var stop atomic.Bool
	var mutations atomic.Int64
	var wg sync.WaitGroup

	// 1. Горутины мутации графа
	for g := 0; g < 4; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			r := rand.New(rand.NewSource(time.Now().UnixNano()))
			for !stop.Load() {
				idx1 := r.Intn(nodeCount)
				idx2 := r.Intn(nodeCount)
				// Мутируем указатели в кольце
				nodes[idx1].Next = nodes[idx2]
				mutations.Add(1)
			}
		}()
	}

	// 2. Горутина агрессивного GC
	wg.Add(1)
	go func() {
		defer wg.Done()
		for !stop.Load() {
			runtime.GC()
			time.Sleep(5 * time.Millisecond)
		}
	}()

	// Выполняем тест 300 мс
	time.Sleep(300 * time.Millisecond)
	stop.Store(true)
	wg.Wait()

	fmt.Printf("Успешно выполнено %d мутаций указателей под непрерывным GC!\n", mutations.Load())
	fmt.Println("Повреждений памяти и race condition в GC не зафиксировано.")
}
```

ℹ️ Стресс-тест целостности ссылок при непрерывных мутациях и сборках GC

## Под капотом

Во время этого стресс-теста тысячи операций записи указателей перехватываются функцией `runtime.gcWriteBarrier`. Буферы `wbBuf` каждого логического процессора наполняются и непрерывно сбрасываются в очереди `gcWork`, предотвращая утерю объектов даже при хаотичной перелинковке узлов.

## Подводные камни

Если запустить этот тест с флагом `-race` (Race Detector), гонка в пользовательском коде на `nodes[idx1].Next = nodes[idx2]` будет обнаружена детектором, так как мутаторы не используют мьютексы. Однако для самого сборщика мусора и его барьеров записи это не приводит к нарушению целостности памяти кучи.

## На собеседовании

**Вопрос:** Что защищает сборщик мусора Go от race condition при одновременной записи указателей из разных горутин?
**Ответ:** Барьер записи сам по себе атомарен в контексте сохранения указателей: он атомарно считывает старое значение слота и сохраняет адреса в локальный P-буфер горутины (`wbBuf`). Даже если в пользовательском коде происходит data race, сборщик мусора сохранит оба объекта (старый и новый) в серой очереди, гарантируя, что ни один живой объект не будет уничтожен.
