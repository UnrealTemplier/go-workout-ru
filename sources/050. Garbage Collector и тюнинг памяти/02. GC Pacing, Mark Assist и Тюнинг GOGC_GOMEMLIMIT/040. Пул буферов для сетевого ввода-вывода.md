# Пул буферов для сетевого ввода-вывода (Buffer Pooling)

## Условие

Используйте sync.Pool для bytes.Buffer в HTTP обработчиках для снижения аллокаций. Напишите полноценный HTTP-хендлер с переиспользованием буферов сериализации.

### Исходная формулировка

**Buffer pooling для I/O**: Используйте `sync.Pool` для `bytes.Buffer` в HTTP handlers для снижения аллокаций.

## Теория

В типичном REST API или gRPC сервисе 80% аллокаций кучи приходится на:
* Сериализацию/десериализацию JSON/Protobuf.
* Формирование HTTP-заголовков и тел ответов.
* Чтение тела входящего запроса.

Если на каждый запрос создавать новый `bytes.Buffer`, сервер под нагрузкой 50 000 RPS будет выделять гигабайты мусора в секунду.

Использование `sync.Pool` для `bytes.Buffer`:
* Устраняет `mallocgc` на каждый запрос.
* Снижает нагрузку на сборщик мусора практически до нуля.
* Предотвращает разрастание RSS процесса.

## Решение по шагам

1. Объявите глобальный пул `var bufferPool = sync.Pool{...}`.
2. В обработчике запроса извлекайте буфер через `buf := bufferPool.Get().(*bytes.Buffer)`.
3. Обязательно сбрасывайте состояние через `buf.Reset()`.
4. Возвращайте буфер в пул через `defer bufferPool.Put(buf)` с проверкой максимальной емкости.

## Код решения

**`http_pool.go`**

```go
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

var bufPool = sync.Pool{
	New: func() any {
		return new(bytes.Buffer)
	},
}

type ResponseData struct {
	Status  string `json:"status"`
	Code    int    `json:"code"`
	Message string `json:"message"`
}

func FastHandler(w http.ResponseWriter, r *http.Request) {
	// Извлекаем буфер из пула
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset()
	defer func() {
		// Защита от утечки памяти: не сохраняем аномально раздутые буферы (>64 КБ)
		if buf.Cap() <= 64*1024 {
			bufPool.Put(buf)
		}
	}()

	resp := ResponseData{
		Status:  "OK",
		Code:    200,
		Message: "Processed with zero heap allocations",
	}

	// Сериализация прямо в буфер из пула
	if err := json.NewEncoder(buf).Encode(resp); err != nil {
		http.Error(w, err.Error(), http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write(buf.Bytes())
}

func main() {
	req := httptest.NewRequest("GET", "/api/fast", nil)
	rec := httptest.NewRecorder()

	FastHandler(rec, req)

	fmt.Printf("HTTP Status: %d\n", rec.Code)
	fmt.Printf("Response Body: %s", rec.Body.String())
}
```

ℹ️ Высокоскоростной HTTP хендлер с пулом буферов и защитой от переполнения

## Под капотом

Метод `buf.Reset()` сбрасывает поле `buf.off = 0` и усекает срез байт `buf.buf = buf.buf[:0]`. Выделенная емкость базового массива остается прежней, поэтому повторный `json.NewEncoder(buf).Encode()` не делает ни одной новой аллокации в куче.

## Подводные камни

Если не проверять `buf.Cap()` перед возвратом в пул, один нестандартный запрос размером 50 МБ навсегда оставит гигантский буфер в пуле, удерживая память от освобождения.

## На собеседовании

**Вопрос:** Зачем в sync.Pool перед вызовом Put проверять емкость (capacity) возвращаемого слайса или буфера?
**Ответ:** Это защита от загрязнения пула гигантскими объектами (Pool Bloat). Если один из запросов вызовет разрастание буфера до 100 МБ, возврат такого буфера в пул заблокирует 100 МБ памяти навсегда. Проверка `if buf.Cap() <= MaxLimit` отсекает аномальные буферы, отдавая их обычному GC.
