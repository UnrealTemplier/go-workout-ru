# Управление внекучевой памятью (Off-heap Memory) через системные вызовы

## Условие

Для экстремальных сценариев HighLoad реализуйте работу с off-heap памятью напрямую через системный вызов mmap с ручным выделением и освобождением памяти в обход кучи Go.

### Исходная формулировка

**Off-heap memory**: Для экстремальных случаев используйте `mmap` напрямую для off-heap памяти, не управляемой GC (требует ручного освобождения).

## Теория

**Внекучевая память (Off-heap Memory)** — это память, запрошенная у операционной системы напрямую через системный вызов ядра Linux `mmap(MAP_ANONYMOUS | MAP_PRIVATE)`, минуя аллокатор рантайма Go `mallocgc`.

Сравнение памяти кучи (Heap) и Off-heap:
* **Heap Go:** Управляется автоматически, подлежит проверкам триколорного алгоритма, создает нагрузку на барьеры записи, ограничивается GOMEMLIMIT.
* **Off-heap:** Полностью невидима для сборщика мусора Go, не расходует лимиты `GOGC`, не требует сканирования указателей, но требует **ручного освобождения через `munmap`** (как в C/C++ `malloc/free`).

Сценарии применения в BigTech:
* Кэши в оперативной памяти на десятки и сотни гигабайт.
* Буферы сетевых пакетов для высокоскоростных сетевых адаптеров (DPDK, AF_XDP).

## Решение по шагам

1. Напишите функции `AllocOffHeap(size int)` и `FreeOffHeap(buf []byte)`.
2. Используйте `syscall.Mmap` с флагами `MAP_ANON | MAP_PRIVATE`.
3. Запишите данные во внекучевой буфер и прочитайте их.
4. Убедитесь по `runtime.MemStats`, что `HeapAlloc` не изменился.

## Код решения

**`off_heap.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"syscall"
)

// AllocOffHeap выделяет память напрямую у ядра ОС
func AllocOffHeap(size int) ([]byte, error) {
	prot := syscall.PROT_READ | syscall.PROT_WRITE
	flags := syscall.MAP_ANONYMOUS | syscall.MAP_PRIVATE
	return syscall.Mmap(-1, 0, size, prot, flags)
}

// FreeOffHeap освобождает страницы ОС
func FreeOffHeap(b []byte) error {
	return syscall.Munmap(b)
}

func main() {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// Выделяем 100 МБ вне кучи Go
	const allocSize = 100 * 1024 * 1024
	buf, err := AllocOffHeap(allocSize)
	if err != nil {
		panic(err)
	}

	// Работаем с памятью напрямую
	copy(buf[:13], "OFF_HEAP_DATA")

	runtime.ReadMemStats(&m2)
	fmt.Println("=== Выделение 100 МБ Off-Heap памяти ===")
	fmt.Printf("Данные: %s\n", string(buf[:13]))
	fmt.Printf("Прирост HeapAlloc: %d байт (Куча Go полностью свободна!)\n",
		m2.HeapAlloc-m1.HeapAlloc)

	// Обязательное ручное освобождение
	if err := FreeOffHeap(buf); err != nil {
		panic(err)
	}
	fmt.Println("Память успешно возвращена ядру ОС через munmap.")
}
```

ℹ️ Прямое управление внекучевой памятью через системный вызов mmap anonymous

## Под капотом

Ядро Linux при анонимном `mmap` резервирует диапазон виртуальных адресов (`VIRT`). Физические страницы памяти (`RSS`) выделяются ядром только в момент первой записи в страницу (Zero-Page on-demand allocation). Для рантайма Go этот указатель лежит вне диапазонов структуры `mheap_.arenas`, поэтому барьеры записи игнорируют его.

## Подводные камни

Внекучевая память не освобождается сборщиком мусора никогда! Если забыть вызвать `syscall.Munmap`, произойдет классическая утечка памяти уровня C (leak), обнаружить которую с помощью штатного `pprof heap` будет невозможно.

## На собеседовании

**Вопрос:** Почему в pprof heap не видны утечки памяти, если приложение использует mmap anonymous?
**Ответ:** Профилировщик `pprof heap` собирает статистику только о выделениях, проходящих через функцию `runtime.mallocgc`. Вызовы `syscall.Mmap` запрашивают виртуальную память напрямую у ядра операционной системы в обход кучи Go. Для поиска утечек off-heap памяти необходимо использовать системные утилиты ОС (OS RSS monitoring, valgrind/massif, eBPF memleak).
