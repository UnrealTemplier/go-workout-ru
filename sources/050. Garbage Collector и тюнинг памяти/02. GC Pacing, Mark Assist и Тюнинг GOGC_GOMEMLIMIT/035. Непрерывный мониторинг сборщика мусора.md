# Непрерывный мониторинг сборщика мусора через gctrace

## Условие

Напишите программу, непрерывно выделяющую память в цикле. Запустите ее с флагом GODEBUG=gctrace=1 и проанализируйте регулярность циклов, процент времени CPU и стабилизацию HeapAlloc.

### Исходная формулировка

**Исследование работы GC через `gctrace`**: Напишите программу, которая непрерывно выделяет память в бесконечном цикле. Запустите её с флагом `GODEBUG=gctrace=1 ./app` [491]. Проанализируйте выводимые строки отчета сборщика мусора. Расшифруйте параметры: время фаз разметки/очистки, процент утилизации процессора сборщиком мусора (GC CPU %, обычно не более 25%), объем кучи до и после сборки.

## Теория

При постоянной нагрузке (Constant Allocation Rate) поведение сборщика мусора переходит в так называемое **стационарное состояние (Steady State)**.

Характеристики стационарного состояния:
* Сборки мусора происходят через равные промежутки времени или через строго одинаковый объем выделенных байт.
* Объем живой кучи после каждой сборки (`LiveHeap`) колеблется вокруг стабильного среднего значения.
* Процент времени CPU стабилизируется в районе расчетного значения (обычно 5–15% в зависимости от интенсивности аллокаций).
* Если же в `gctrace` размер кучи после GC непрерывно растет (`20->20->18`, `40->40->35`, `80->80->70`), это верный признак **утечки памяти (Memory Leak)** в приложении.

## Решение по шагам

1. Создайте бесконечный цикл, аллоцирующий пакеты байт и очищающий ссылки.
2. Добавьте ограничение по количеству итераций для безопасного завершения.
3. Запустите программу с `GODEBUG=gctrace=1`.
4. Сопоставьте стабилизацию параметров кучи в логах.

## Код решения

**`continuous_alloc.go`**

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fmt.Println("=== Старт непрерывной нагрузки для анализа Steady State ===")

	// Цикл на 20 итераций генерации мусора
	for round := 1; round <= 20; round++ {
		// Генерируем 16 МБ временных данных
		data := make([][]byte, 1000)
		for i := range data {
			data[i] = make([]byte, 16*1024)
		}
		_ = data
		time.Sleep(50 * time.Millisecond)
	}

	fmt.Println("Нагрузка завершена.")
}
```

ℹ️ Генерация циклической стационарной нагрузки на аллокатор

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run continuous_alloc.go
# Обратите внимание на стабильность значений goal и live memory между циклами
```

## Под капотом

В `src/runtime/mgcpacer.go` контроллер непрерывно обновляет скользящую оценку скорости выделения памяти мутатором (`mutatorAllocRate`). В steady-state контроллер сходится к оптимальному коэффициенту `triggerRatio`, обеспечивая минимальное участие мутаторов в Mark Assist.

## Подводные камни

Если вывод `gctrace=1` показывает регулярные срабатывания с интервалом ровно 2 минуты при нулевом объеме аллокаций — это штатный двухминутный таймер периодической сборки (`runtime.forcegcperiod = 2 * time.Minute`).

## На собеседовании

**Вопрос:** Почему в логах gctrace даже при полном отсутствии входящих запросов к Go-сервису каждые 2 минуты появляется запись о сборке мусора?
**Ответ:** В рантайме Go работает фоновая горутина `forcegchelper`. Если приложение не аллоцировало память в объеме, достаточном для естественного триггера, рантайм принудительно запускает сборщик мусора раз в 2 минуты (`forcegcperiod = 2 minutes`), чтобы вернуть неиспользуемую память ядру ОС и очистить устаревшие структуры.
