# Выравнивание полей структур (Struct Packing) и влияние на кучу

## Условие

Упорядочьте поля структуры по размеру (от большего к меньшему) для снижения padding. Сравните размер структуры struct { bool; int64; bool } (24 байта) и struct { int64; bool; bool } (16 байт). Измерьте экономию памяти при аллокации миллиона элементов.

### Исходная формулировка

**Struct packing**: Упорядочьте поля структуры по размеру (largest first) для снижения padding. Сравните `struct { bool; int64; bool }` (24 bytes) vs `struct { int64; bool; bool }` (16 bytes).

## Теория

Аппаратная архитектура x86-64 и ARM64 требует выравнивания данных в оперативной памяти:
* 64-битные типы (`int64`, `float64`, указатели `*T`) должны располагаться по адресам, кратным 8 байтам.
* 32-битные типы (`int32`, `float32`) — кратным 4 байтам.
* 16-битные типы (`int16`) — кратным 2 байтам.

Если структура спроектирована неоптимально, компилятор вынужден вставлять холостые байты заполнения (**Padding**):

```
Неоптимально (24 байта):
[bool: 1B] [pad: 7B] [int64: 8B] [bool: 1B] [pad: 7B] = 24 байта

Оптимально (16 байт):
[int64: 8B] [bool: 1B] [bool: 1B] [pad: 6B]          = 16 байт
```

При аллокации 10 000 000 таких структур разница составит **80 Мегабайт чистой памяти**, которая не только расходует RAM, но и занимает драгоценные строки кэша процессора L1/L2/L3 и замедляет работу GC.

## Решение по шагам

1. Объявите две структуры: `Unpacked` и `Packed`.
2. Измерьте их размеры через `unsafe.Sizeof()`.
3. Аллоцируйте срезы по 5 000 000 структур каждого типа.
4. Сравните итоговый `HeapAlloc`.

## Код решения

**`struct_packing.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

type Unpacked struct {
	FlagA bool  // 1 байт + 7 байт padding
	Value int64 // 8 байт
	FlagB bool  // 1 байт + 7 байт padding
} // Итого: 24 байта

type Packed struct {
	Value int64 // 8 байт
	FlagA bool  // 1 байт
	FlagB bool  // 1 байт + 6 байт tail padding
} // Итого: 16 байт

func main() {
	var u Unpacked
	var p Packed

	fmt.Println("=== Анализ выравнивания памяти структур ===")
	fmt.Printf("Размер Unpacked: %d байт\n", unsafe.Sizeof(u))
	fmt.Printf("Размер Packed:   %d байт\n", unsafe.Sizeof(p))

	const count = 5000000

	// Замер Unpacked
	runtime.GC()
	var m1, m2 runtime.MemStats
	runtime.ReadMemStats(&m1)
	unpackedSlice := make([]Unpacked, count)
	runtime.ReadMemStats(&m2)
	allocUnpacked := m2.HeapAlloc - m1.HeapAlloc

	// Замер Packed
	unpackedSlice = nil
	runtime.GC()
	runtime.ReadMemStats(&m1)
	packedSlice := make([]Packed, count)
	runtime.ReadMemStats(&m2)
	allocPacked := m2.HeapAlloc - m1.HeapAlloc
	_ = packedSlice

	fmt.Printf("\nПамять под %d элементов Unpacked: %8.2f МБ\n",
		count, float64(allocUnpacked)/(1024*1024))
	fmt.Printf("Память под %d элементов Packed:   %8.2f МБ\n",
		count, float64(allocPacked)/(1024*1024))
	fmt.Printf("Чистая экономия памяти:           %8.2f МБ (%.1f%%)\n",
		float64(allocUnpacked-allocPacked)/(1024*1024),
		float64(allocUnpacked-allocPacked)/float64(allocUnpacked)*100)
}
```

## Под капотом

Аллокатор Go квантует память по классам размеров (Size Classes). Объект размером 24 байта попадает в класс размера 24 или 32 байта, тогда как 16 байт попадает ровно в класс 16 байт. Это влияет не только на объем среза, но и на плотность упаковки объектов в спанах `mspan`.

## Подводные камни

Не забывайте про хвостовое поле нулевого размера: если последнее поле структуры имеет тип `struct{}` или массив нулевой длины `[0]byte`, компилятор Go добавит 8 байт padding в конец, чтобы указатель за пределами структуры не ссылался на следующий чужой объект в куче.

## На собеседовании

**Вопрос:** Как порядок полей в структуре Go влияет на производительность и сборку мусора?
**Ответ:** Порядок полей определяет объем холостого заполнения (Padding) из-за требований выравнивания процессора. Упорядочивание полей от большего к меньшему сокращает размер структуры. Это уменьшает расход кучи, увеличивает количество элементов, помещающихся в одну кэш-линию CPU (64 байта), ускоряет доступ к памяти и сокращает объем работы для фаз разметки и очистки GC.
