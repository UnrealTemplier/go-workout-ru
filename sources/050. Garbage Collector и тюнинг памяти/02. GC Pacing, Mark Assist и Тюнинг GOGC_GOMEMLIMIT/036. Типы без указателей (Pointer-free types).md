# Типы без указателей (Pointer-free types) и спаны noscan

## Условие

Используйте типы без указателей (int, float64, срезы байт []byte, структуры без указателей) — GC не сканирует их, что ускоряет фазу разметки в разы. Измерьте скорость сборки мусора для 10 000 000 целых чисел по сравнению с 10 000 000 указателей.

### Исходная формулировка

**Pointer-free types**: Используйте типы без указателей (`int`, `float64`, structs с только value types) — GC не сканирует их, что ускоряет marking.

## Теория

Сборщик мусора Go тратит процессорное время **только на сканирование указателей**!

Если блок памяти гарантированно не содержит указателей:
* Компилятор Go помечает его флагом `noscan`.
* Аллокатор кучи выделяет для таких объектов спаны из специального пула `noscan` (классы от 68 до 135 в `mcentral`).
* В фазе Marking маркер-воркер, встретив объект в noscan-спане, красит его в Черный цвет и **не сканирует его содержимое вообще**!

Разница в производительности:
* Срез `[]byte` или `[]int` на 100 000 000 элементов: проверяется за 1 такт процессора (просто закрашивается базовый массив).
* Срез `[]*int` или структура со строками/указателями: GC обязан обойти все 100 000 000 адресов, вызывая миллионы промахов кэша процессора и замораживая CPU на секунды!

## Решение по шагам

1. Создайте срез из 10 000 000 `int` (pointer-free).
2. Вызовите `runtime.GC()` и замерьте время разметки.
3. Создайте срез из 10 000 000 `*int` (с указателями на кучу).
4. Вызовите `runtime.GC()` и сравните время выполнения.

## Код решения

**`noscan_bench.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	const count = 10000000

	fmt.Println("=== 1. Тест Pointer-Free среза ([]int) ===")
	// Выделяем 10 млн целых чисел (80 МБ без указателей)
	noPointers := make([]int, count)
	for i := range noPointers {
		noPointers[i] = i
	}

	start := time.Now()
	runtime.GC()
	durNoPointers := time.Since(start)
	fmt.Printf("Время runtime.GC() для []int:    %v\n", durNoPointers)

	// Очищаем
	noPointers = nil
	runtime.GC()

	fmt.Println("\n=== 2. Тест среза с указателями ([]*int) ===")
	// Выделяем 10 млн указателей на числа
	withPointers := make([]*int, count)
	val := 42
	for i := range withPointers {
		withPointers[i] = &val
	}

	start = time.Now()
	runtime.GC()
	durWithPointers := time.Since(start)
	fmt.Printf("Время runtime.GC() для []*int:  %v\n", durWithPointers)

	_ = withPointers
	ratio := float64(durWithPointers) / float64(durNoPointers)
	fmt.Printf("\nСрез с указателями замедлил GC в %.1f раз!\n", ratio)
}
```

ℹ️ Сравнение скорости работы GC на pointer-free срезах и срезах указателей

## Под капотом

В `src/runtime/mheap.go` класс размера спана кодируется с битом noscan: `spanClass = sizeClass<<1 | noscanBit`. Если `noscanBit == 1`, функция `scanobject` в `mgcmark.go` просто пропускает тело объекта без загрузки bitmap указателей `heapBits`.

## Подводные камни

Использование мап вида `map[int]*MyStruct` заставляет GC обходить каждую запись в бакетах. Замена на `map[int]int` с хранением структур в плоском срезе `[]MyStruct` ускоряет разметку на порядок.

## На собеседовании

**Вопрос:** Почему в HighLoad кэшах на Go (например, BigCache, FastCache) избегают хранения указателей и используют большие байтовые массивы?
**Ответ:** Большие хэш-таблицы с миллионами указателей (`map[string]*Item`) катастрофически нагружают GC: сборщик обязан обойти каждый указатель на каждом цикле разметки, вызывая просадку CPU и рост задержек. BigCache и FastCache хранят данные в виде сплошных срезов байт `[]byte` и кольцевых буферов с индексацией по целочисленным смещениям. Срез байт — это pointer-free тип, который GC помечает за одну операцию, не сканируя содержимое.
