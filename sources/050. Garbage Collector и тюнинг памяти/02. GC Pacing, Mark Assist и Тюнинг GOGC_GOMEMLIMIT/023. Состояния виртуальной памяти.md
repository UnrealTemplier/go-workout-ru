# Состояния виртуальной памяти: HeapIdle vs HeapReleased

## Условие

Изучите разницу между HeapIdle (свободная память, удерживаемая рантаймом для повторных аллокаций) и HeapReleased (память, физически возвращенная ядру ОС через madvise). Напишите код, демонстрирующий переход страниц из Idle в Released.

### Исходная формулировка

**HeapIdle vs HeapReleased**: `HeapIdle` — память, возвращённая в OS, но может быть переиспользована. `HeapReleased` — память, физически возвращённая в OS через `madvise(MADV_FREE)`.

## Теория

Аллокатор кучи Go резервирует виртуальные адреса крупными блоками (Arenas по 64 МБ). В структуре `runtime.MemStats` отображаются три взаимосвязанных состояния страниц:

1. **`HeapInuse`:** Страницы кучи, на которых прямо сейчас размещены живые объекты.
2. **`HeapIdle`:** Страницы кучи, которые в данный момент не содержат живых объектов. Они свободны, но остаются зарезервированными процессом. Внутри `HeapIdle` выделяется подкатегория:
3. **`HeapReleased`:** Часть страниц из категории `HeapIdle`, для которых рантайм вызвал системный вызов `madvise(MADV_DONTNEED)` (в Linux). Ядро ОС забрало физические страницы RAM (Resident Set Size уменьшился), но виртуальный диапазон адресов сохранен за процессом.

Соотношение:
$$\text{HeapSys} = \text{HeapInuse} + \text{HeapIdle}$$
$$\text{Память в RAM} \approx \text{HeapInuse} + (\text{HeapIdle} - \text{HeapReleased})$$

## Решение по шагам

1. Аллоцируйте 100 МБ памяти в куче.
2. Освободите память и вызовите `runtime.GC()`. Память станет `HeapIdle`.
3. Вызовите `debug.FreeOSMemory()` для принудительного сброса страниц ядру ОС.
4. Проверьте, как значение `HeapReleased` выросло, сравнявшись с `HeapIdle`.

## Код решения

**`idle_vs_released.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func showMem(label string) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("[%s]\n", label)
	fmt.Printf("  HeapInuse:    %8.2f МБ (активно занято объектами)\n", float64(m.HeapInuse)/(1024*1024))
	fmt.Printf("  HeapIdle:     %8.2f МБ (свободные спаны в рантайме)\n", float64(m.HeapIdle)/(1024*1024))
	fmt.Printf("  HeapReleased: %8.2f МБ (физически отдано ОС через madvise)\n", float64(m.HeapReleased)/(1024*1024))
}

func main() {
	showMem("1. Начальное состояние")

	// Аллоцируем 80 МБ
	data := make([][]byte, 80)
	for i := range data {
		data[i] = make([]byte, 1024*1024)
	}
	showMem("2. Аллокация 80 МБ (рост HeapInuse)")

	// Сбрасываем ссылки и очищаем кучу
	data = nil
	runtime.GC()
	showMem("3. После GC (память перешла из Inuse в Idle)")

	// Принудительный возврат памяти ядру ОС
	debug.FreeOSMemory()
	showMem("4. После debug.FreeOSMemory() (рост HeapReleased)")
}
```

ℹ️ Демонстрация перехода страниц кучи между HeapInuse, HeapIdle и HeapReleased

## Под капотом

Фоновый процесс `runtime.bgscavenge` периодически сканирует дерево страниц `pageAlloc` глобальной кучи `mheap`. Если диапазон страниц простаивает дольше времени сглаживания, вызывается `sysUnused` -> `madvise(addr, size, MADV_DONTNEED)`. Страница остается валидной в таблице страниц процесса, но физический фрейм памяти возвращается в пул свободного ОЗУ ОС.

## Подводные камни

В мониторинге ОС (ps, top) освобожденная память `HeapIdle - HeapReleased` продолжает отображаться в колонке `VIRT` (Virtual Memory Size). Это абсолютно нормально и не означает утечку памяти.

## На собеседовании

**Вопрос:** Почему после освобождения 10 ГБ данных в Go сервисе RSS процесса в top падает медленно?
**Ответ:** Потому что рантайм Go не возвращает память ОС немедленно при помощи munmap. Освобожденные спаны помечаются как HeapIdle для быстрого переиспользования без системных вызовов. Фоновый скавенджер (Scavenger) возвращает физические страницы ядру постепенно при помощи madvise(MADV_DONTNEED), сглаживая нагрузку на ядро ОС.
