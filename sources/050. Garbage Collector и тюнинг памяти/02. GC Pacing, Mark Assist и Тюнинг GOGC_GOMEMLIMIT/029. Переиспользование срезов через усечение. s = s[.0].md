# Переиспользование срезов через усечение: s = s[:0]

## Условие

Переиспользуйте слайсы через усечение длины s = s[:0] вместо создания новых экземпляров. Измерьте нулевой оверхед на аллокацию кучи и отсутствие работы сборщика мусора.

### Исходная формулировка

**Slice reuse**: Реиспользуйте слайсы через `s = s[:0]` вместо создания новых. Это сохраняет базовый массив.

## Теория

Идиома `s = s[:0]` сбрасывает длину среза (`len = 0`), но **сохраняет базовый массив и его исходную емкость (`cap`)**.

Когда вы вызываете `append(s, item)` на срезе с `len=0` и `cap=N`:
* Рантайм Go не вызывает `runtime.makeslice` или `runtime.growslice`.
* Запись нового элемента происходит по прямому смещению в уже выделенной памяти `*(basePtr + len) = item`.
* Новые объекты в куче не создаются, `TotalAlloc` не увеличивается, сборщик мусора не запускается.

Если же на каждой итерации цикла писать `s = []int{}`, старый базовый массив выбрасывается в кучу, а новый выделяется заново, генерируя гигабайты мусора.

## Решение по шагам

1. Создайте буфер с заданной емкостью `buf := make([]int, 0, 1000)`.
2. В цикле обрабатывайте пакеты, сбрасывая длину через `buf = buf[:0]`.
3. Сравните с постоянным пересозданием `buf = make([]int, 0, 1000)`.
4. Зафиксируйте 0 аллокаций через `testing.AllocsPerRun`.

## Код решения

**`slice_reuse.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"testing"
)

func processWithRealloc(count int) {
	for i := 0; i < count; i++ {
		// Антипаттерн: создание нового массива на каждой итерации
		buf := make([]int, 0, 128)
		for j := 0; j < 128; j++ {
			buf = append(buf, j)
		}
		_ = buf
	}
}

func processWithReuse(count int) {
	// Идиоматично: выделяем буфер один раз
	buf := make([]int, 0, 128)
	for i := 0; i < count; i++ {
		buf = buf[:0] // сохраняем емкость, сбрасываем len
		for j := 0; j < 128; j++ {
			buf = append(buf, j)
		}
		_ = buf
	}
}

func main() {
	const iterations = 100000

	allocs1 := testing.AllocsPerRun(100, func() {
		processWithRealloc(100)
	})

	allocs2 := testing.AllocsPerRun(100, func() {
		processWithReuse(100)
	})

	fmt.Println("=== Сравнение аллокаций памяти ===")
	fmt.Printf("Пересоздание среза: %.0f аллокаций на запуск\n", allocs1)
	fmt.Printf("Идиома s = s[:0]:   %.0f аллокаций на запуск\n", allocs2)

	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("NumGC: %d\n", m.NumGC)
}
```

ℹ️ Устранение аллокаций с помощью s = s[:0]

## Под капотом

Срез в Go — это структура из трех слов: указатель `Data`, `Len` и `Cap` (структура `reflect.SliceHeader`). Операция `s[:0]` генерирует всего одну инструкцию присвоения нулю поля длины: `MOVQ $0, 8(SP)`. Базовый указатель и емкость остаются нетронутыми.

## Подводные камни

Внимание при работе с указателями! Если срез содержал указатели на тяжелые объекты (`[]*BigStruct`), операция `s = s[:0]` не зануляет старые ячейки базового массива. До тех пор, пока емкость не будет перезаписана новыми элементами, сборщик мусора будет видеть старые ссылки и не сможет освободить тяжелые объекты (утечка памяти!). В таких случаях перед `[:0]` нужно занулить ссылки через `clear(s)` (Go 1.21+).

## На собеседовании

**Вопрос:** Может ли конструкция `s = s[:0]` привести к скрытой утечке памяти в Go?
**Ответ:** Да. Если `s` — срез указателей `[]*T`, то усечение длины до 0 не очищает ссылки в базовом массиве за границей `len`. Сборщик мусора сканирует всю емкость массива (`cap`), считает эти объекты достижимыми и не освобождает их. В Go 1.21+ для решения проблемы вызывают `clear(s)` перед усечением длины, зануляя указатели.
