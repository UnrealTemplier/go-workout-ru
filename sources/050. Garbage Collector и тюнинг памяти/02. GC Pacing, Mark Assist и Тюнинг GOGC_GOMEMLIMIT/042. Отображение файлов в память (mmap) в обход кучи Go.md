# Отображение файлов в память (mmap) в обход кучи Go

## Условие

Для работы с большими файлами используйте системный вызов mmap (пакет syscall) вместо загрузки содержимого в кучу Go. Продемонстрируйте нулевое влияние на HeapAlloc и сборщик мусора.

### Исходная формулировка

**Memory-mapped files**: Для работы с большими файлами используйте `mmap` (через `golang.org/x/exp/mmap` или syscall) вместо загрузки в heap.

## Теория

Когда сервис читает файл размером 5 ГБ через стандартный `os.ReadFile` или `io.ReadAll`:
1. Вся память выделяется в куче Go (`mallocgc`).
2. Рантайм обязан отслеживать эти 5 ГБ в спанах `mspan`.
3. Сборщик мусора тратит ресурсы на проверку этих блоков памяти.

**Технология Memory-Mapped Files (mmap):**
Системный вызов ядра ОС `mmap(2)` связывает файловый дескриптор напрямую с виртуальным адресным пространством процесса:
* Страницы файла подгружаются ядром ОС с диска лениво по требованию (Page Faults).
* Память **не выделяется в куче Go** (`runtime.MemStats.HeapAlloc` равен нулю).
* Сборщик мусора Go абсолютно не знает про эту память и не тратит ни одного такта CPU на ее разметку!

## Решение по шагам

1. Создайте временный файл с тестовыми данными.
2. Откройте файл и отобразите его в память через `syscall.Mmap`.
3. Прочитайте данные напрямую из полученного среза байт `[]byte`.
4. Освободите память через `syscall.Munmap` и закройте дескриптор.

## Код решения

**`mmap_demo.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"syscall"
)

func main() {
	// Создаем тестовый файл 10 МБ
	fileName := "test_mmap.dat"
	fileSize := 10 * 1024 * 1024

	f, err := os.Create(fileName)
	if err != nil {
		panic(err)
	}
	if err := f.Truncate(int64(fileSize)); err != nil {
		panic(err)
	}
	_, _ = f.WriteAt([]byte("HELLO MMAP ZERO GC"), 0)
	_ = f.Close()
	defer os.Remove(fileName)

	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// Открываем файл для mmap
	file, err := os.OpenFile(fileName, os.O_RDWR, 0644)
	if err != nil {
		panic(err)
	}
	defer file.Close()

	// Отображаем файл в адресное пространство процесса
	data, err := syscall.Mmap(
		int(file.Fd()),
		0,
		fileSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_SHARED,
	)
	if err != nil {
		panic(err)
	}
	defer syscall.Munmap(data)

	runtime.ReadMemStats(&m2)
	fmt.Println("=== Чтение файла через mmap ===")
	fmt.Printf("Прочитано из mmap: %s\n", string(data[:18]))
	fmt.Printf("Размер файла:       %d МБ\n", fileSize/(1024*1024))
	fmt.Printf("Прирост HeapAlloc:  %d байт (Абсолютный ноль нагрузки на GC!)\n",
		m2.HeapAlloc-m1.HeapAlloc)
}
```

ℹ️ Отображение файла в память через syscall.Mmap с нулевой нагрузкой на GC

## Под капотом

Срез, возвращаемый `syscall.Mmap`, конструируется напрямую через упаковку адреса, возвращенного ядром ОС, в структуру `reflect.SliceHeader`. Поскольку этот указатель не принадлежит ни одной арене `mheap.arenas`, рантайм Go не считает его частью кучи.

## Подводные камни

Если размонтировать память через `syscall.Munmap(data)`, а затем попытаться обратиться к срезу `data[0]`, ядро ОС немедленно завершит процесс с фатальным сигналом `SIGSEGV` (Segmentation Fault). Управление временем жизни mmap требует строгой дисциплины.

## На собеседовании

**Вопрос:** В чем преимущества mmap при создании высокопроизводительных встраиваемых БД на Go (например, BoltDB, Badger)?
**Ответ:** BoltDB использует mmap для всего файла базы данных. Это дает три преимущества: 1. Нулевое копирование данных (Zero-Copy) между ядром и приложением; 2. Управление страницами и кэширование прозрачно делегируются Page Cache ядра Linux; 3. Память файла находится вне кучи Go (Off-Heap), поэтому даже при базе данных в 500 ГБ сборщик мусора Go работает моментально, не сканируя эти страницы.
