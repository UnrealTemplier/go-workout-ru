# Комплексное профилирование GC: связка CPU, Heap Profile и Go Execution Trace

## Условие

Соберите одновременно cpu profile, heap profile и runtime/trace во время интенсивной нагрузки. Проанализируйте полную цепочку: от вызовов бизнес-логики до функций рантайма gcBgMarkWorker, mallocgc и runtime.gcWriteBarrier.

### Исходная формулировка

**Профилирование GC.**: Соберите профиль `cpu` и `heap` во время нагрузки. Используйте `go tool pprof` для анализа функций, тратящих время на аллокации и GC (runtime.gcBgMarkWorker, runtime.mallocgc и т.д.). Оптимизируйте горячие точки.

## Теория

Комплексная триада диагностики производительности Go (The Holy Trinity of Go Profiling):

```
       ┌──────────────────────────────────────────────────────────┐
       │             АНАЛИЗ ПРОИЗВОДИТЕЛЬНОСТИ GO                 │
       └────────────────────────────┬─────────────────────────────┘
                                    │
          ┌─────────────────────────┼────────────────────────┐
          ▼                         ▼                        ▼
  [ CPU Profile ]           [ Heap Profile ]         [ Runtime Trace ]
  Куда уходят такты?        Кто выделяет память?     Что происходит во времени?
  • runtime.mallocgc        • inuse_space (утечки)   • Всплески STW пауз
  • runtime.gcWriteBarrier  • alloc_space (нагрузка) • Задержки Mark Assist
  • gcBgMarkWorker          • alloc_objects          • Простаивание ядер P
```

Совместный анализ:
1. `CPU profile` показывает, что 30% времени тратится на `runtime.mallocgc` и `runtime.gcWriteBarrier`.
2. `Heap profile (-alloc_space)` точно называет файл и номер строки бизнес-кода, создающего эти объекты.
3. `Runtime trace` показывает хронологию: как эти аллокации заставляют горутины вставать в `Mark Assist` и портить p99 задержки.

## Решение по шагам

1. Напишите код комплексного одновременного сбора всех трех артефактов (`cpu.pprof`, `heap.pprof`, `trace.out`).
2. Выполните репрезентативную нагрузку.
3. Корректно закройте файлы и сбросьте буферы.
4. Выведите инструкции по комплексному анализу в консоль.

## Код решения

**`holistic_profiling.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
	"runtime/trace"
	"sync"
)

func runHeavyWorkload() {
	var wg sync.WaitGroup
	for g := 0; g < 4; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 5000; i++ {
				// Смешанная нагрузка: память + указатели
				slice := make([]*int, 256)
				val := i
				for j := range slice {
					slice[j] = &val
				}
				_ = slice
			}
		}()
	}
	wg.Wait()
}

func main() {
	fmt.Println("=== Комплексный сбор диагностических артефактов ===")

	// 1. Старт CPU Profile
	cpuFile, err := os.Create("cpu.pprof")
	if err != nil {
		panic(err)
	}
	defer cpuFile.Close()
	if err := pprof.StartCPUProfile(cpuFile); err != nil {
		panic(err)
	}
	defer pprof.StopCPUProfile()

	// 2. Старт Execution Trace
	traceFile, err := os.Create("trace.out")
	if err != nil {
		panic(err)
	}
	defer traceFile.Close()
	if err := trace.Start(traceFile); err != nil {
		panic(err)
	}
	defer trace.Stop()

	// 3. Выполнение нагрузки
	runHeavyWorkload()

	// 4. Фиксация Heap Profile
	heapFile, err := os.Create("heap.pprof")
	if err != nil {
		panic(err)
	}
	defer heapFile.Close()
	runtime.GC()
	if err := pprof.Lookup("heap").WriteTo(heapFile, 0); err != nil {
		panic(err)
	}

	fmt.Println("Все артефакты успешно собраны:")
	fmt.Println("  1. go tool pprof -top cpu.pprof")
	fmt.Println("  2. go tool pprof -top -alloc_space heap.pprof")
	fmt.Println("  3. go tool trace trace.out")
}
```

ℹ️ Одновременная фиксация CPU profile, Heap profile и Execution trace

**`Терминал`**

```bash
go run holistic_profiling.go
go tool pprof -top cpu.pprof
# Наблюдайте функции рантайма: runtime.mallocgc, runtime.gcWriteBarrier, gcBgMarkWorker
```

## Под капотом

Профилировщик CPU использует периодический таймер сигналов ядра Linux `SIGPROF` (обычно 100 Гц), который сэмплирует регистры команд `RIP` и стек текущего потока. Трейсер фиксирует события планировщика на переключениях контекста.

## Подводные камни

Одновременный сбор CPU-профиля и трейса создает повышенную нагрузку на систему и может немного исказить замеры задержек. В продакшене включайте профилировщики по очереди.

## На собеседовании

**Вопрос:** Каков стандартный алгоритм расследования деградации производительности Go сервиса под нагрузкой?
**Ответ:** 1. Анализируют метрики Prometheus (go_gc_duration_seconds, go_gc_cpu_fraction, go_goroutines, memory RSS); 2. Снимают CPU-профиль (pprof) для определения доли времени на mallocgc / gcWriteBarrier; 3. Снимают профиль кучи с флагом -alloc_space для локализации виновных функций в коде; 4. Записывают short execution trace (2 сек) для проверки пауз STW и дорожек Mark Assist; 5. Применяют оптимизации (sync.Pool, noscan, преаллокация, GOMEMLIMIT) и верифицируют результат повторными бенчмарками.
