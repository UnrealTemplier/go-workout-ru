# GC-чувствительный сервис и адаптация к нагрузке через GOMEMLIMIT

## Условие

Напишите HTTP-сервис, обрабатывающий запросы с динамическим размером аллокаций. Настройте GOMEMLIMIT так, чтобы при нормальной нагрузке GC не мешал сервису, а при пиках предотвращал исчерпание памяти.

### Исходная формулировка

Напишите «GC-sensitive service»: HTTP-сервер, который обрабатывает запросы с аллокацией. Настройте `GOMEMLIMIT` так, чтобы GC не превышал 20% CPU (проверьте через `GODEBUG=gctrace=1`). Объясните компромисс: низкий `GOMEMLIMIT` = частые GC, высокий = риск OOM.

## Теория

Архитектурная схема самоадаптирующегося сервиса:
* В базовом режиме входящий трафик невелик, куча занимает 20–30% от `GOMEMLIMIT`. Сборщик мусора работает редко (дефолтный `GOGC=100`), сохраняя максимальный запас CPU для полезной работы.
* При резком наплыве пользователей (Traffic Spike) куча быстро растет. Как только размер приближается к `GOMEMLIMIT`, пейсер плавно сжимает интервалы сборок, не допуская превышения границы.
* После прохождения пика Scavenger постепенно возвращает физическую память ядру Linux.

## Решение по шагам

1. Создайте эндпоинт, принимающий параметр размера полезной нагрузки.
2. Установите `debug.SetMemoryLimit(128 * 1024 * 1024)`.
3. Подайте серию нарастающих запросов.
4. Убедитесь, что сервис успешно переживает пиковую нагрузку без сбоев.

## Код решения

**`adaptive_service.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"runtime"
	"runtime/debug"
)

func ProcessHandler(w http.ResponseWriter, r *http.Request) {
	// Имитация обработки запроса с аллокацией временного буфера
	buf := make([]byte, 5*1024*1024)
	_ = buf
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("Processed"))
}

func main() {
	// Устанавливаем мягкий лимит кучи 64 МБ
	const memLimit = 64 * 1024 * 1024
	debug.SetMemoryLimit(memLimit)

	server := httptest.NewServer(http.HandlerFunc(ProcessHandler))
	defer server.Close()

	client := server.Client()

	fmt.Printf("=== Сервис запущен с GOMEMLIMIT = %d МБ ===\n", memLimit/(1024*1024))
	var ms runtime.MemStats

	// Подаем 20 запросов по 5 МБ (суммарно 100 МБ аллокаций)
	for i := 1; i <= 20; i++ {
		resp, err := client.Get(server.URL)
		if err != nil {
			panic(err)
		}
		_ = resp.Body.Close()

		if i%5 == 0 {
			runtime.ReadMemStats(&ms)
			fmt.Printf("Запрос %2d: HeapAlloc = %5.1f МБ | NextGC = %5.1f МБ | NumGC = %d\n",
				i, float64(ms.Alloc)/(1024*1024), float64(ms.NextGC)/(1024*1024), ms.NumGC)
		}
	}

	fmt.Println("Все запросы обработаны. Память удержана под контролем GOMEMLIMIT!")
}
```

ℹ️ Обработка пикового трафика под контролем адаптивного мягкого лимита памяти

## Под капотом

Когда аллокатор приближается к границе `GOMEMLIMIT`, вызов `mallocgc` уведомляет `gcController.commit`. Пейсер пересчитывает целевой размер, активируя сборщик мусора с упреждением, предотвращая выход кучи за рамки 64 МБ.

## Подводные камни

Не забывайте, что `GOMEMLIMIT` не учитывает память, выделенную вне Go (например, через системные библиотеки CGO или mmap баз данных).

## На собеседовании

**Вопрос:** Как проверить, помогла ли настройка GOMEMLIMIT предотвратить OOM в Kubernetes?
**Ответ:** 1. Посмотреть логи пода: отсутствие статуса Terminated с Reason: OOMKilled и Exit Code: 137; 2. В Grafana на графике памяти контейнера линия использования перестает упираться в Limit и выравнивается на уровне ~85-90%; 3. В логах сервиса отсутствуют фатальные ошибки Out-Of-Memory.
