# Зависимость доли CPU от скорости аллокаций: исследование контроллера пейсера

## Условие

Постройте зависимость доли CPU, потраченной на GC (GCCPUFraction), от скорости выделения памяти мутатором. Продемонстрируйте, как пейсер удерживает целевой бюджет 25% CPU при умеренной нагрузке и как эта доля возрастает при перегрузке.

### Исходная формулировка

**Pacing и контроллер GC.**: Постройте график зависимости доли CPU, потраченной на GC, от скорости выделения памяти (можно симулировать, меняя интенсивность аллокаций и собирая `gctrace`). Покажите работу контроллера, стремящегося удержать 25% CPU на GC.

## Теория

Контроллер пейсера (`mgcpacer.go`) проектировался с целевой установкой: **тратить ровно 25% CPU на разметку**:
* При низкой скорости аллокаций (\(< 100\text{ МБ/с}\) на ядро) достаточно редких фоновых воркеров (`gcBgMarkWorker`), доля CPU на GC составляет 2–10%.
* В расчетном стационарном режиме (Steady State) контроллер выходит ровно на 25% CPU.
* При экстремальной скорости аллокаций (\(> 1\text{ ГБ/с}\)), когда фоновые 25% воркеров не справляются с потоком объектов, включается `Mark Assist`. Доля `GCCPUFraction` подскакивает до 35–45%, искусственно замедляя приложение.

## Решение по шагам

1. Напишите функцию, генерирующую аллокации с тремя уровнями интенсивности.
2. Прочитайте метрику `runtime.MemStats.GCCPUFraction` после каждого прогона.
3. Постройте таблицу соответствия скорости и доли CPU.
4. Проанализируйте порог включения Mark Assist.

## Код решения

**`pacing_cpu_fraction.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func runWorkloadWithRate(iterations, size int) float64 {
	runtime.GC()
	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)

	start := time.Now()
	for i := 0; i < iterations; i++ {
		_ = make([]byte, size)
	}
	_ = time.Since(start)

	runtime.ReadMemStats(&mEnd)
	return mEnd.GCCPUFraction
}

func main() {
	fmt.Println("=== Исследование GCCPUFraction от интенсивности аллокаций ===")

	rates := []struct {
		name       string
		iterations int
		size       int
	}{
		{"Легкая нагрузка (100k x 256B)", 100000, 256},
		{"Средняя нагрузка (100k x 4KB)", 100000, 4 * 1024},
		{"Тяжелая нагрузка (50k x 64KB)", 50000, 64 * 1024},
	}

	for _, r := range rates {
		cpuFraction := runWorkloadWithRate(r.iterations, r.size)
		fmt.Printf("%-32s -> Доля GC CPU: %6.2f%% (цель: 25.0%%)\n",
			r.name, cpuFraction*100)
	}
}
```

ℹ️ Измерение доли процессорного времени GCCPUFraction под разной интенсивностью

## Под капотом

В `src/runtime/mstats.go` поле `gc_cpu_fraction` вычисляется как скользящее интегральное отношение процессорного времени воркеров GC к суммарному времени всех потоков M приложения: `cpu_fraction = gc_cpu_nanoseconds / (total_wall_nanoseconds * GOMAXPROCS)`.

## Подводные камни

В микроконтейнерах с `GOMAXPROCS=1` или `2` метрика `GCCPUFraction` может резко скакать до 50%, так как один воркер забирает целое ядро процессора.

## На собеседовании

**Вопрос:** Что считается нормальным значением метрики GCCPUFraction в продакшене?
**Ответ:** Для нормально сбалансированного веб-сервиса нормальным считается значение от 0.02 до 0.12 (2–12% CPU). Значения в районе 0.20–0.25 говорят о работе в расчетном пределе сборщика. Значения выше 0.30 сигнализируют о перегрузке кучи, активной работе Mark Assist и необходимости оптимизации аллокаций через sync.Pool или увеличение GOMEMLIMIT.
