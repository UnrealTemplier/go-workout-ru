# Углубленный разбор Mark Assist и методы ликвидации задержек

## Условие

Когда программа выделяет память быстрее, чем сборщик успевает ее помечать, рантайм принудительно включает Mark Assist. Напишите практические рекомендации и код по устранению Mark Assist на критических путях.

### Исходная формулировка

**Эффект помощи сборщику (Mark Assist)**: Когда ваша программа выделяет память со скоростью, превышающей физические возможности сборщика по её разметке, рантайм включает механизм "Mark Assist" (Помощь разметке). Объясните этот эффект: горутины, запрашивающие аллокацию кучи во время работы GC, принудительно приостанавливаются рантаймом и переводятся в режим помощи сборщику — они начинают размечать серые объекты вместо выполнения своего полезного кода. Напишите код, который умышленно провоцирует этот эффект за счет сверхбыстрой аллокации сотен тысяч мелких структур в параллельных потоках.

## Теория

Механика возникновения `Mark Assist`:
$$\text{Assist Trigger} \iff \text{Allocation Rate} > \text{Marking Capacity} \times 0.25$$

Когда 25% фоновых ядер не успевают размечать кучу, горутины-мутаторы принудительно блокируются в `mallocgc`.

Стратегии полной ликвидации Mark Assist:
1. **Zero-Alloc Hot Paths:** В критических циклах и функциях полностью исключить выделения в куче (переход на стек и pre-allocated буферы).
2. **Увеличение GOMEMLIMIT / GOGC:** Если памяти на сервере достаточно, увеличение предела кучи отдаляет момент включения разметки и снижает требование к коэффициенту помощи.
3. **Пакетное выделение памяти (Arena / Chunk Allocator):** Выделять память крупными блоками по 4 МБ один раз, а затем нарезать структуры вручную без обращения к `mallocgc`.

## Решение по шагам

1. Создайте сценарий с частыми аллокациями, вызывающими задержку.
2. Перепишите его на переиспользуемый локальный буфер.
3. Продемонстрируйте исчезновение задержек аллокации.

## Код решения

**`eliminate_mark_assist.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// Неоптимально: создает аллокации и рискует попасть в Mark Assist
func badWorker(iters int) time.Duration {
	start := time.Now()
	for i := 0; i < iters; i++ {
		buf := make([]byte, 1024)
		_ = buf
	}
	return time.Since(start)
}

// Оптимально: буфер на стеке или переиспользуемый срез (ноль аллокаций)
func goodWorker(iters int) time.Duration {
	start := time.Now()
	var stackBuf [1024]byte // Выделено на стеке!
	for i := 0; i < iters; i++ {
		stackBuf[0] = byte(i)
		_ = stackBuf
	}
	return time.Since(start)
}

func main() {
	const iters = 1000000

	fmt.Println("=== Ликвидация риска попадания в Mark Assist ===")

	dBad := badWorker(iters)
	fmt.Printf("Куча (make([]byte, 1024)): Время = %-10v (давление на аллокатор)\n", dBad)

	dGood := goodWorker(iters)
	fmt.Printf("Стек ([1024]byte):          Время = %-10v (нулевое давление на GC)\n", dGood)

	speedup := float64(dBad) / float64(dGood)
	fmt.Printf("\nУстранение аллокаций в куче ускорило выполнение в %.1f раз!\n", speedup)

	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	fmt.Printf("Сборок GC: %d\n", ms.NumGC)
}
```

ℹ️ Устранение аллокаций кучи как способ гарантированной защиты от Mark Assist

## Под капотом

Когда переменная размещается на стеке (`[1024]byte`), компилятор Go генерирует инструкцию `SUBQ $1024, SP` при входе в функцию. Вызов `runtime.mallocgc` не вызывается, а значит горутина в принципе не может быть привлечена к Mark Assist.

## Подводные камни

Массивы на стеке не должны быть слишком большими (не более нескольких десятков килобайт), иначе произойдет переполнение начального стека горутины (2 КБ) и рантайм вызовет `runtime.morestack`.

## На собеседовании

**Вопрос:** Как гарантировать, что критическая бизнес-горутина никогда не попадет в состояние Mark Assist?
**Ответ:** Единственная 100% гарантия — отсутствие любых аллокаций в куче (Zero Allocations) на критическом пути этой горутины. Если горутина не вызывает `runtime.mallocgc`, у нее не списываются кредиты помощи, и рантайм физически не может принудить ее к сканированию памяти.
