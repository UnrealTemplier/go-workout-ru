# Глубокая трассировка сборщика мусора через runtime/trace

## Условие

Запишите трейс исполнения программы через runtime/trace во время интенсивной аллокации. Откройте в браузере go tool trace и проанализируйте секции Heap, GC (Stop-The-World, Concurrent Mark) и дорожки горутин Mark Assist.

### Исходная формулировка

**[Высокая сложность — Trace GC]**: Запиши `runtime/trace` во время интенсивной аллокации. Открой в `go tool trace` раздел "Heap" и "GC regions". Проанализируй, сколько времени горутины проводили в состоянии "GC mark assist" (когда горутина принудительно помогает GC, потому что аллоцирует слишком много).

## Теория

Инструмент `runtime/trace` предоставляет микросекундную визуализацию всех событий рантайма Go:
* **График Heap:** Показывает рост памяти, момент включения GC и ступенчатое падение после очистки.
* **Дорожка GC:**
  * `STW (Mark Setup)` — тонкая полоска остановки мира (~20 мкс).
  * `GC (Concurrent Mark)` — протяженный интервал фоновой разметки.
  * `STW (Mark Termination)` — вторая тонкая полоска финализации (~100 мкс).
  * `GC (Sweeping)` — ленивые блоки очистки.
* **Дорожки Goroutines:** Наглядно выделяют горутины, принудительно переведенные в состояние `GC Mark Assist`.

## Решение по шагам

1. Создайте файл трассировки `trace.out` с помощью `trace.Start(f)`.
2. Выполните цикл конкурентной генерации объектов.
3. Остановите трассировку `trace.Stop()`.
4. Запустите в терминале визуализатор `go tool trace trace.out`.

## Код решения

**`gc_trace_gen.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime/trace"
	"sync"
)

func main() {
	f, err := os.Create("trace.out")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := trace.Start(f); err != nil {
		panic(err)
	}
	defer trace.Stop()

	fmt.Println("Запись трассировки рантайма (trace.out)...")

	var wg sync.WaitGroup
	for g := 0; g < 4; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 5000; i++ {
				_ = make([]byte, 16*1024)
			}
		}()
	}

	wg.Wait()
	fmt.Println("Трассировка успешно сохранена.")
}
```

ℹ️ Генерация бинарного трейса рантайма для визуального анализа фаз GC

**`Терминал`**

```bash
go run gc_trace_gen.go
go tool trace trace.out
# Браузер откроет интерфейс: перейдите в "View trace" и найдите полосу GC
```

## Под капотом

В `src/runtime/trace.go` генерация событий трейса оптимизирована через локальные кольцевые буферы каждого логического процессора P. Запись событий `traceEvGCStart`, `traceEvGCDone` и `traceEvGCMarkAssistStart` происходит lock-free.

## Подводные камни

Запись трейса создает дополнительный оверхед (около 5-10% CPU) и формирует файлы размером в сотни мегабайт при долгой работе. В продакшене записывайте трейс короткими интервалами по 1–3 секунды.

## На собеседовании

**Вопрос:** Как с помощью go tool trace подтвердить, что просадка latency вызвана именно сборщиком мусора?
**Ответ:** Открыв "View trace", нужно сопоставить таймлайн проблемного запроса с дорожкой "GC". Если во время выполнения запроса на дорожках Goroutines видно событие `GC Mark Assist`, либо весь трейс пересекается с фазой `STW`, это служит неопровержимым доказательством вины GC.
