# Профилирование аллокаций: pprof alloc_objects vs inuse_objects

## Условие

Соберите профиль аллокаций кучи (alloc_objects). Найдите функцию, которая генерирует миллионы временных короткоживущих объектов, даже если текущий размер кучи inuse_space остается минимальным.

### Исходная формулировка

**[Alloc Profile]**: Собери профиль аллокаций (`alloc_objects`). Найди функцию, которая аллоцирует больше всего объектов (даже если они быстро освобождаются). Оптимизируй её с помощью `sync.Pool`. Убедись, что количество аллокаций упало до 0 в бенчмарке.

## Теория

Скрытый враг производительности: **«Легкая куча при тяжелом процессоре»**:
* В мониторинге сервис потребляет всего 50 МБ RAM (`inuse_space = 50 MB`).
* Однако CPU утилизируется на 90%, а RPS не растет.
* Причина: функция генерирует 1 000 000 временных структур в секунду. Они мгновенно удаляются сборщиком мусора, поэтому `inuse_space` не растет. Но процессор непрерывно тратит такты на `mallocgc`, зачистку спанов и барьеры записи!

Режим `alloc_objects` в pprof показывает функции, выделяющие наибольшее количество объектов за интервал времени, вне зависимости от того, живы они сейчас или нет.

## Решение по шагам

1. Напишите функцию интенсивной генерации временных структур.
2. Запишите профиль аллокаций.
3. Сравните вывод `top -inuse_objects` и `top -alloc_objects`.
4. Найдите функцию-виновника нагрузки на сборщик мусора.

## Код решения

**`alloc_objects_profile.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime/pprof"
)

type EventLog struct {
	ID        int
	Timestamp int64
	Message   string
}

func hotFunction() {
	// Создаем 500 000 временных объектов
	for i := 0; i < 500000; i++ {
		e := &EventLog{
			ID:        i,
			Timestamp: 123456789,
			Message:   "Temporary debug message payload",
		}
		_ = e
	}
}

func main() {
	fmt.Println("=== Генерация нагрузки для профиля alloc_objects ===")

	hotFunction()

	f, err := os.Create("allocs.pprof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	if err := pprof.Lookup("allocs").WriteTo(f, 0); err != nil {
		panic(err)
	}

	fmt.Println("Профиль успешно сохранен в allocs.pprof!")
	fmt.Println("Для просмотра виновников аллокаций: go tool pprof -top -alloc_objects allocs.pprof")
}
```

ℹ️ Сбор профиля аллокаций для выявления фабрик временных объектов

**`Терминал`**

```bash
go run alloc_objects_profile.go
go tool pprof -top -alloc_objects allocs.pprof
# Команда четко покажет: 500 000 объектов создано в main.hotFunction
```

## Под капотом

Профиль `allocs` собирается рантаймом параллельно с `heap`: при каждом сэмплировании инкрементируется пара счетчиков: `alloc_bytes` / `alloc_objects` (кумулятивно) и `inuse_bytes` / `inuse_objects` (мгновенно).

## Подводные камни

Искать утечки памяти через `-alloc_objects` бессмысленно: вы найдете не утечку, а функцию с наибольшим оборотом временных структур. Для утечек используйте строго `-inuse_space`.

## На собеседовании

**Вопрос:** Сервис потребляет стабильно мало памяти, но утилизирует 100% CPU. Какой режим pprof нужно использовать для диагностики?
**Ответ:** Нужно снять профиль кучи и анализировать его в режиме `go tool pprof -alloc_objects` (или `-alloc_space`). Это позволит выявить функции с высоким темпом создания временных объектов (Allocation Rate), которые перегружают сборщик мусора постоянными циклами mallocgc и mark assist, не вызывая при этом роста resident памяти.
