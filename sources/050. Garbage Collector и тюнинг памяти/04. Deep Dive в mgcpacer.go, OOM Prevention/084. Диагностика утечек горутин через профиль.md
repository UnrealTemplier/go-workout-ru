# Диагностика утечек горутин через профиль pprof.Lookup("goroutine")

## Условие

Смоделируйте утечку горутин (забыли закрыть канал или прочитать из него, горутины зависают навсегда). Снимите профиль pprof.Lookup("goroutine") и найдите точное место зависания по стектрейсу.

### Исходная формулировка

**[goroutine profile]**: Сымитируй утечку горутин (забыли закрыть канал, и горутины висят навсегда). Сними профиль `pprof.Lookup("goroutine")`. Найди точную строку кода, где горутины заблокированы навсегда.

## Теория

**Утечка горутин (Goroutine Leak)** — одна из самых коварных причин утечки памяти в Go:
* Каждая зависшая горутина удерживает свой стек (минимум 2–4 КБ).
* Все переменные, на которые ссылается стек зависшей горутины, признаются сборщиком мусора живыми (`GC Roots`)!
* 10 000 зависших горутин не только тратят 40–100 МБ памяти под стеки, но и удерживают гигабайты связанных структур в куче.

Профиль `pprof.Lookup("goroutine")`:
* Выводит агрегированный отчет по всем активным горутинам процесса.
* Группирует горутины по общему стеку вызовов, сразу показывая: `5000 горутин зависли в функции worker на чтении из ch`.

## Решение по шагам

1. Создайте функцию с незакрытым каналом, куда пишут горутины.
2. Запустите 100 зависших горутин.
3. Сохраните профиль через `pprof.Lookup("goroutine").WriteTo(f, 1)`.
4. Проанализируйте текстовый стектрейс зависших горутин.

## Код решения

**`goroutine_leak_profile.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime/pprof"
	"time"
)

func leakingWorker(ch <-chan int) {
	// Горутина навсегда зависает на чтении из канала, который никогда не получит данных
	_ = <-ch
}

func main() {
	fmt.Println("=== Симуляция утечки горутин ===")

	neverReadyCh := make(chan int) // забыли отправить или закрыть!

	for i := 0; i < 50; i++ {
		go leakingWorker(neverReadyCh)
	}

	time.Sleep(50 * time.Millisecond)

	f, err := os.Create("goroutines.txt")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	// Записываем текстовый профиль горутин (debug=1: сжатый читаемый вид)
	if err := pprof.Lookup("goroutine").WriteTo(f, 1); err != nil {
		panic(err)
	}

	fmt.Println("Снимок горутин сохранен в goroutines.txt.")
	fmt.Println("Первые строки профиля:")

	data, _ := os.ReadFile("goroutines.txt")
	fmt.Println(string(data[:250]))
}
```

ℹ️ Снятие снимка профиля горутин для выявления мест блокировок

**`Терминал`**

```bash
go run goroutine_leak_profile.go
# В файле goroutines.txt видно: 50 @ 0x... main.leakingWorker (chan receive)
```

## Под капотом

При вызове `pprof.Lookup("goroutine")` с `debug=1` рантайм останавливает мир (STW), обходит массив `allgs`, извлекает PC стека каждой горутины, формирует хэш-таблицу уникальных стектрейсов и выводит количество горутин в каждой группе.

## Подводные камни

Всегда используйте контекст `context.Context` с таймаутом или отменой для управления жизненным циклом горутин, чтобы гарантировать их завершение.

## На собеседовании

**Вопрос:** Как утечка горутин связана с работой сборщика мусора Go?
**Ответ:** Стеки горутин являются корневыми точками (GC Roots) для алгоритма разметки. Любая переменная или буфер, адрес которого находится в локальных фреймах зависшей горутины, никогда не будет признан мусором и не будет освобожден сборщиком. Утечка горутин вызывает пропорциональную утечку памяти кучи.
