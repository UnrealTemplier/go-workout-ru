# Точный замер накладных расходов барьера записи на операциях присваивания

## Условие

Оцените точные накладные расходы Write Barrier на операциях записи в память. Сравните время выполнения 10 000 000 операций записи указателей и 10 000 000 операций записи скалярных типов int64.

### Исходная формулировка

**Write barrier overhead**: Оцените overhead от write barriers (~1-5% CPU для pointer-heavy workloads).

## Теория

Архитектурное сравнение инструкций:

1. **Запись скалярного значения (`node.Val = 42`):**
   * Компилятор генерирует: `MOVQ $42, (AX)`
   * Стоимость: 1 такт процессора (L1 Store buffer).
   * Барьер записи **отсутствует полностью**.

2. **Запись указателя (`node.Next = nextNode`):**
   * В нормальном режиме: проверка флага `runtime.writeBarrier.enabled` + `MOVQ BX, (AX)`. Оверхед: 1-2 такта.
   * Во время фазы Concurrent Marking: вызов ассемблерной функции `runtime.gcWriteBarrier`, проверка адресов, сохранение старого и нового указателей в буфер `wbBuf`. Оверхед: **10–25 тактов процессора** на каждую мутацию!

## Решение по шагам

1. Создайте структуру со скалярным полем `int64` и структуру с полем указателя `*int64`.
2. Запустите 10 000 000 присваиваний скаляра.
3. Запустите 10 000 000 присваиваний указателя во время активной разметки.
4. Сравните разницу во времени исполнения.

## Код решения

**`wb_overhead_exact.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type ScalarStruct struct {
	Val int64
}

type PointerStruct struct {
	Ptr *int64
}

func main() {
	const iters = 10000000
	var dummy int64 = 99

	// 1. Замер скалярных записей (без барьера)
	s := &ScalarStruct{}
	t1 := time.Now()
	for i := int64(0); i < iters; i++ {
		s.Val = i
	}
	durScalar := time.Since(t1)

	// 2. Замер указателей в спокойном режиме
	p := &PointerStruct{}
	t2 := time.Now()
	for i := 0; i < iters; i++ {
		p.Ptr = &dummy
	}
	durPtrCalm := time.Since(t2)

	fmt.Println("=== Точный замер стоимости операций записи в память ===")
	fmt.Printf("10 млн записей int64:       %v (чистый MOVQ)\n", durScalar)
	fmt.Printf("10 млн записей указателя:   %v (с ветвлением барьера)\n", durPtrCalm)
	fmt.Printf("Разница накладных расходов: +%.1f%%\n",
		float64(durPtrCalm-durScalar)/float64(durScalar)*100)
	_ = s
	_ = p
}
```

ℹ️ Сравнение затрат процессорного времени на скалярные записи и запись указателей

## Под капотом

В современных процессорах Intel и AMD ветвление `CMPB / JEQ` при выключенном барьере предсказывается идеально и почти бесплатно по тактам благодаря Branch Target Buffer (BTB). Основные потери возникают при включении барьера из-за сброса конвейера и обращений в кэш.

## Подводные камни

Чрезмерная оптимизация ради исключения указателей может сделать код менее читаемым. Оптимизировать структуры на отсутствие указателей следует только в профилированных горячих циклах (Hot Paths).

## На собеседовании

**Вопрос:** Каков реальный overhead от барьеров записи в Go на production-нагрузке?
**Ответ:** В среднем по всему приложению накладные расходы Write Barrier составляют от 1% до 4% CPU, поскольку барьер включен только во время фазы разметки, а операции со стеком им не затрагиваются. В специфических pointer-heavy алгоритмах (графы, списки) оверхед на операциях записи может локально возрастать до 15–20%.
