# Паттерн Batch GC: отключение авто-GC и вызов сборки в паузах между пачками

## Условие

Напишите программу с debug.SetGCPercent(-1) (отключение автоматического GC), которая обрабатывает пачки сообщений и синхронно вызывает runtime.GC() исключительно в технологических паузах между пакетами.

### Исходная формулировка

Напишите программу с `runtime.SetGCPercent(-1)` (отключение автоматического GC), затем вызывайте `runtime.GC()` вручную. Сравните паузы: автоматический GC (с pacing) vs. ручной вызов. Объясните роль `triggerRatio` и `heapGoal`.

## Теория

Паттерн **Batch Garbage Collection (Пакетный GC)** — популярный архитектурный прием в системах обработки очередей (Kafka consumers, RabbitMQ batch processors):

1. **Проблема при стандартном GC:**
   Во время вычитывания и обработки пачки из 50 000 сообщений сборщик мусора запускается непрерывно, отбирая 25% CPU и замедляя обработку пакета.

2. **Решение через Batch GC:**
   * Перед началом обработки пакета автоматический сборщик выключается: `debug.SetGCPercent(-1)`.
   * Пакет из 50 000 сообщений обрабатывается на **100% доступной мощности процессора** без барьеров записи и без задержек.
   * После того как сообщения закоммичены в Kafka, сервис делает технологическую паузу (Ack/Commit window).
   * В этот момент сервис явно вызывает `runtime.GC()`.
   * Память очищается в межпакетное окно, и ни один входящий запрос не страдает от пауз!

## Решение по шагам

1. Отключите автоматический GC через `debug.SetGCPercent(-1)`.
2. Смоделируйте цикл обработки пачек по 10 000 сообщений.
3. В конце каждой пачки вызывайте `runtime.GC()`.
4. Зафиксируйте максимальную скорость обработки внутри пакета.

## Код решения

**`batch_gc_pattern.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func processBatch(batchID, size int) {
	fmt.Printf("[Пакет %d] Обработка %d сообщений (авто-GC выключен, 100%% CPU)...\n",
		batchID, size)
	for i := 0; i < size; i++ {
		// Аллокации под обработку сообщения
		msg := fmt.Sprintf("event_payload_id_%d_%d", batchID, i)
		_ = msg
	}
}

func main() {
	// Отключаем фоновый авто-GC
	old := debug.SetGCPercent(-1)
	defer debug.SetGCPercent(old)

	var ms runtime.MemStats
	fmt.Println("=== Паттерн Batch GC для очередей сообщений ===")

	for batch := 1; batch <= 3; batch++ {
		t0 := time.Now()
		processBatch(batch, 100000)
		processDur := time.Since(t0)

		// Технологическое окно: коммит в брокер и вызов GC
		tGC := time.Now()
		runtime.GC()
		gcDur := time.Since(tGC)

		runtime.ReadMemStats(&ms)
		fmt.Printf("[Пакет %d] Обработан за %v | Очистка памяти runtime.GC() заняла %v | Alloc: %5.1f МБ\n\n",
			batch, processDur, gcDur, float64(ms.Alloc)/(1024*1024))
	}
}
```

ℹ️ Реализация паттерна Batch GC с очисткой памяти в технологических паузах

## Под капотом

При вызове `runtime.GC()` в межпакетную паузу вся куча очищается синхронно, а спаны возвращаются в `mcentral`. На следующей пачке аллокатор быстро наполняет кэш `mcache` без единого системного вызова ядра ОС.

## Подводные камни

Если размер пачки сообщений не контролируется и может превысить доступный объем оперативной памяти сервера, отключение GC приведет к мгновенному OOM. Обязательно ограничивайте максимальный размер пакета (`max.poll.records`).

## На собеседовании

**Вопрос:** В чем преимущества и риски применения паттерна Batch GC?
**Ответ:** Преимущество: 100% процессорных мощностей отдаются обработке данных, полностью исключаются задержки STW и Mark Assist во время процессинга. Риск: монотонный рост оперативной памяти на протяжении пакета. Если пачка окажется аномально большой, сервис упадет по OOM до того, как успеет дойти до вызова runtime.GC().
