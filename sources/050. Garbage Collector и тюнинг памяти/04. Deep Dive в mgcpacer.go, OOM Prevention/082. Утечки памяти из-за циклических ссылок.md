# Утечки памяти из-за циклических ссылок в структурах с финализаторами

## Условие

Используйте runtime.SetFinalizer для объектов, ссылающихся друг на друга по кругу. Докажите, что циклическая зависимость финализаторов блокирует сборку мусора и приводит к вечной утечке памяти.

### Исходная формулировка

**Финализация и утечки.**: Используйте `runtime.SetFinalizer` для объекта. Создайте циклическую ссылку и наблюдайте, будет ли вызван финализатор (утечка памяти). Проверьте, удаляет ли GC циклические структуры.

## Теория

Фундаментальное исключение из правила сбора циклов в Go:
* Обычные циклические структуры без финализаторов сборщик мусора Go освобождает **без каких-либо проблем**.
* **НО если хотя бы один объект в цикле имеет `runtime.SetFinalizer`:**
  1. Чтобы вызвать финализатор объекта \(A\), сборщик обязан быть уверен, что объект \(A\) больше никем не используется.
  2. Но на объект \(A\) ссылается объект \(B\) из того же цикла.
  3. Чтобы освободить \(B\), нужно вызвать финализатор \(B\), который ссылается на \(A\).
  4. Возникает неразрешимый логический тупик порядка финализации (Deadlock of Dependency).
  5. Сборщик мусора Go **отказывается вызывать финализаторы для таких объектов и никогда не освобождает их память**!

## Решение по шагам

1. Создайте структуры `NodeA` и `NodeB` с взаимными ссылками.
2. Прикрепите финализаторы к обоим объектам через `runtime.SetFinalizer`.
3. Сбросьте внешние ссылки и вызовите `runtime.GC()`.
4. Убедитесь, что ни один финализатор не сработал, а память осталась в куче.

## Код решения

**`finalizer_cycle_leak.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type LeakyNode struct {
	Name string
	Peer *LeakyNode
	Data []byte
}

func createCyclicFinalizerLeak() {
	a := &LeakyNode{Name: "Node_A", Data: make([]byte, 10*1024*1024)}
	b := &LeakyNode{Name: "Node_B", Data: make([]byte, 10*1024*1024)}

	// Создаем кольцевую ссылку
	a.Peer = b
	b.Peer = a

	// Регистрируем финализаторы
	runtime.SetFinalizer(a, func(n *LeakyNode) {
		fmt.Printf("Финализатор %s сработал!\n", n.Name)
	})
	runtime.SetFinalizer(b, func(n *LeakyNode) {
		fmt.Printf("Финализатор %s сработал!\n", n.Name)
	})
}

func main() {
	fmt.Println("=== Исследование циклической блокировки финализаторов ===")

	createCyclicFinalizerLeak()

	var ms runtime.MemStats
	// Запускаем несколько циклов GC
	for i := 1; i <= 3; i++ {
		runtime.GC()
		time.Sleep(50 * time.Millisecond)
		runtime.ReadMemStats(&ms)
		fmt.Printf("Цикл GC #%d: HeapAlloc = %5.1f МБ (Память НЕ освобождается!)\n",
			i, float64(ms.Alloc)/(1024*1024))
	}

	fmt.Println("\nВнимание: ни один финализатор НЕ был вызван из-за кольцевой зависимости!")
}
```

ℹ️ Демонстрация вечной утечки памяти при циклических ссылках с финализаторами

## Под капотом

В `src/runtime/mfinal.go` функция проверки достижимости видит, что объекты достижимы друг из друга. Поскольку рантайм не может выбрать, чей финализатор безопаснее вызвать первым, объекты не попадают в `runfinq` и остаются в куче бессрочно.

## Подводные камни

Это самый коварный вид утечки памяти в Go: код компилируется без ошибок, утечка не видна в linters, но память течет непрерывно. Вывод: **никогда не связывайте в кольца структуры с финализаторами**!

## На собеседовании

**Вопрос:** Способен ли GC в Go освободить циклическую структуру данных, если ее узлы имеют финализаторы?
**Ответ:** Нет! Если объекты ссылаются друг на друга по кругу и содержат финализаторы (`runtime.SetFinalizer`), сборщик мусора Go не может определить безопасный порядок их вызова. В результате такие объекты никогда не финализируются и навсегда утекают в оперативной памяти.
