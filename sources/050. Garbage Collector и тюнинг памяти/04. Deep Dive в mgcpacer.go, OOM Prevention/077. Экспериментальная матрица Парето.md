# Экспериментальная матрица Парето: поиск оптимума GOGC и GOMEMLIMIT

## Условие

Проведите систематическую серию экспериментов с различными комбинациями GOGC (50, 100, 200) и GOMEMLIMIT (64M, 128M, 256M). Найдите оптимальную точку Парето (минимальное время CPU при заданном ограничении RAM).

### Исходная формулировка

**GC tuning experiments**: Проведите серию экспериментов с разными `GOGC` и `GOMEMLIMIT` значениями на вашем production-like workload. Постройте графики latency vs memory usage.

## Теория

Оптимизация по Парето (Pareto Efficiency) в тюнинге рантайма Go:
Не существует одной универсальной "лучшей" настройки для всех сервисов. Всегда существует баланс между двумя метриками:
1. **Ресурс памяти (RAM Footprint)** — минимизация пикового потребления кучи.
2. **Ресурс процессора (CPU Throughput)** — минимизация доли времени, потраченной на GC.

Точка Парето-оптимума:
* Для серверов с ограниченной RAM (микросервисы с лимитом 256 МБ): `GOGC=80` + `GOMEMLIMIT=220MiB`.
* Для серверов с избытком RAM (тяжелые воркеры с 16 ГБ RAM): `GOGC=200..300` + `GOMEMLIMIT=14GiB`.

## Решение по шагам

1. Напишите вложенный цикл по массивам `gogcList` и `memlimitList`.
2. Выполните эталонную нагрузку для каждой пары параметров.
3. Сохраните результаты в матрицу (Память vs Время).
4. Выведите сравнительную сводку Парето-оптимумов.

## Код решения

**`pareto_matrix.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

type ExperimentResult struct {
	GOGC       int
	LimitMB    int
	Duration   time.Duration
	NumGC      uint32
	PeakHeapMB float64
}

func runExperiment(gogc int, limitMB int) ExperimentResult {
	debug.SetGCPercent(gogc)
	debug.SetMemoryLimit(int64(limitMB) * 1024 * 1024)
	runtime.GC()

	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)
	start := time.Now()

	// Нагрузка: 200 000 аллокаций
	for i := 0; i < 200000; i++ {
		_ = make([]byte, 1024)
	}
	dur := time.Since(start)

	runtime.ReadMemStats(&mEnd)
	return ExperimentResult{
		GOGC:       gogc,
		LimitMB:    limitMB,
		Duration:   dur,
		NumGC:      mEnd.NumGC - mStart.NumGC,
		PeakHeapMB: float64(mEnd.NextGC) / (1024 * 1024),
	}
}

func main() {
	fmt.Println("=== Экспериментальная матрица Парето (GOGC x GOMEMLIMIT) ===")
	gogcVals := []int{50, 100, 200}
	limitVals := []int{64, 128, 256}

	fmt.Printf("%-6s | %-10s | %-12s | %-10s | %-12s\n",
		"GOGC", "Лимит RAM", "Время CPU", "Сборок GC", "Пик NextGC")
	fmt.Println("---------------------------------------------------------------")

	for _, g := range gogcVals {
		for _, l := range limitVals {
			res := runExperiment(g, l)
			fmt.Printf("%-6d | %-7d МБ | %-12v | %-10d | %6.1f МБ\n",
				res.GOGC, res.LimitMB, res.Duration, res.NumGC, res.PeakHeapMB)
		}
	}
	debug.SetGCPercent(100)
	debug.SetMemoryLimit(-1)
}
```

ℹ️ Систематическое тестирование комбинаций GOGC и GOMEMLIMIT для поиска оптимума

## Под капотом

Взаимодействие параметров в `mgcpacer.go`: когда задан и GOGC, и GOMEMLIMIT, контроллер непрерывно выбирает наиболее строгий лимит. При малом лимите GOGC=200 автоматически зажимается до эквивалента GOGC=30 без участия разработчика.

## Подводные камни

Выбор экстремальных значений (например, GOGC=1000 при лимите 64 МБ) бессмысленен: GOMEMLIMIT полностью нивелирует эффект от GOGC.

## На собеседовании

**Вопрос:** Какую методологию используют в BigTech для подбора параметров сборщика мусора перед выкаткой в прод?
**Ответ:** Используют A/B тестирование канареечных подов (Canary Pods) под реальным трафиком. На одной группе подов оставляют дефолтный профиль (GOGC=100), на других варьируют GOGC и GOMEMLIMIT. По графикам в Prometheus сравнивают p99 latency, потребление CPU и утилизацию памяти пода, выбирая наилучшую точку Парето.
