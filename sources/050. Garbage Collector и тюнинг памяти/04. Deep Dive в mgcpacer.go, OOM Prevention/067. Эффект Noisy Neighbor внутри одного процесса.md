# Эффект Noisy Neighbor внутри одного процесса: влияние аллокаций на соседние эндпоинты

## Условие

Напишите HTTP-сервис с двумя эндпоинтами: один быстрый (/fast), второй генерирует тяжелые аллокации (/heavy). Покажите, как тяжелые аллокации в одном обработчике косвенно влияют на задержки второго обработчика через запуск GC.

### Исходная формулировка

**[GOGC и Latency]**: Напиши HTTP-сервер с одним эндпоинтом, который аллоцирует много памяти, и другим, который просто отвечает быстро. Под нагрузкой на первый эндпоинт замерь p99 latency второго. Убедись, что частый GC (GOGC=50) увеличивает latency из-за потери CPU, а редкий (GOGC=200) может вызвать внезапный резкий STW, когда куча станет слишком большой. Найди баланс.

## Теория

Эффект **Noisy Neighbor (Шумный сосед)** внутри одного процесса:
* В рантайме Go сборщик мусора является **глобальным для всего процесса**.
* Если эндпоинт `/heavy` (например, выгрузка CSV отчета) аллоцирует 500 МБ данных, он активирует сборщик мусора для всех ядер CPU.
* Во время разметки:
  1. 25% CPU забирают фоновые воркеры GC.
  2. Включаются барьеры записи во всей куче.
  3. Случаются две фазы STW.
* В результате легковесный эндпоинт `/fast` (например, проверка здоровья `/healthz`) испытывает рост задержек и конкуренцию за процессорные ядра, хотя сам не выделил ни одного байта!

## Решение по шагам

1. Реализуйте быстрый и тяжелый HTTP обработчики.
2. Замерьте базовую скорость `/fast` без нагрузки.
3. Подайте параллельную нагрузку на `/heavy`.
4. Замерьте просадку скорости `/fast` из-за конкуренции за GC.

## Код решения

**`noisy_neighbor.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

func FastHandler(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
}

func HeavyHandler(w http.ResponseWriter, r *http.Request) {
	// Тяжелая аллокация
	garbage := make([][]byte, 100)
	for i := range garbage {
		garbage[i] = make([]byte, 64*1024)
	}
	_ = garbage
	w.WriteHeader(http.StatusOK)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/fast", FastHandler)
	mux.HandleFunc("/heavy", HeavyHandler)
	srv := httptest.NewServer(mux)
	defer srv.Close()

	client := srv.Client()

	// 1. Замер /fast в идеальных условиях
	t1 := time.Now()
	for i := 0; i < 1000; i++ {
		resp, _ := client.Get(srv.URL + "/fast")
		_ = resp.Body.Close()
	}
	baseDur := time.Since(t1)

	// 2. Замер /fast при параллельной работе /heavy
	var wg sync.WaitGroup
	stop := make(chan bool)

	for g := 0; g < 4; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for {
				select {
				case <-stop:
					return
				default:
					resp, err := client.Get(srv.URL + "/heavy")
					if err == nil {
						_ = resp.Body.Close()
					}
				}
			}
		}()
	}

	time.Sleep(50 * time.Millisecond)
	t2 := time.Now()
	for i := 0; i < 1000; i++ {
		resp, _ := client.Get(srv.URL + "/fast")
		_ = resp.Body.Close()
	}
	loadedDur := time.Since(t2)
	close(stop)
	wg.Wait()

	fmt.Println("=== Эффект Noisy Neighbor на уровне рантайма Go ===")
	fmt.Printf("1000 запросов /fast (без фона):     %v\n", baseDur)
	fmt.Printf("1000 запросов /fast (под /heavy GC): %v\n", loadedDur)
	fmt.Printf("Замедление быстрого эндпоинта:       +%.1f%%\n",
		float64(loadedDur-baseDur)/float64(baseDur)*100)
}
```

ℹ️ Демонстрация косвенного влияния тяжелых аллокаций на соседние обработчики

## Под капотом

Когда воркеры разметки занимают ядра CPU (`P`), планировщик Go вынужден ставить горутины быстрого эндпоинта в очередь ожидания `runq`, что увеличивает время нахождения горутины в планировщике (Scheduler Run Latency).

## Подводные камни

Совмещение тяжелых аналитических отчетов и чувствительных к задержкам транзакционных API в одном микросервисе — плохая архитектурная практика. Их следует разделять на разные независимые сервисы/поды.

## На собеседовании

**Вопрос:** Как изолировать критический Low-Latency эндпоинт от влияния фонового GC, порожденного тяжелыми операциями в том же процессе?
**Ответ:** 1. Архитектурно вынести тяжелые операции (генерация PDF/Excel, импорт больших файлов) в отдельный микросервис (Worker Pod); 2. Внутри текущего сервиса переписать тяжелый код на потоковую обработку (streaming) с минимальным буфером; 3. Использовать sync.Pool для буферов; 4. Ограничить concurrency тяжелого эндпоинта через семафор.
