## Теория

Математическая модель в `src/runtime/mgcpacer.go`:
* Константа `gcBackgroundUtilization = 0.25`: Рантайм Go резервирует ровно четверть доступных вычислительных ресурсов на сборку. Это эмпирический оптимум, доказанный на тысячах серверов Google: 75% CPU гарантированно остается мутаторам, обеспечивая высокую отзывчивость системы.
* **PI-регулятор (Proportional-Integral Controller):**
  Управляющая ошибка на шаге \(n\):
  $$e_n = \frac{H_{\text{actual}} - H_{\text{goal}}}{H_{\text{goal}}}$$
  Контроллер обновляет коэффициент триггера `triggerRatio`:
  $$\text{triggerRatio}_{n+1} = \text{triggerRatio}_n - K_p \cdot e_n - K_i \sum e_k$$
  Где \(K_p\) и \(K_i\) — подобранные коэффициенты сглаживания.
* **Параметр `consMark` (Conservative Marking Rate):** Защитная константа минимальной расчетной скорости разметки. Она страхует рантайм от недооценки тяжести графа кучи, гарантируя, что маркер-воркеры будут запущены заблаговременно.

## Решение по шагам

1. Создайте модель формулы триггера на Go.
2. Продемонстрируйте реакцию регулятора на ошибку превышения целевого размера.
3. Покажите, как `triggerRatio` сходится к стабильному коэффициенту.

## Код решения

**`pi_controller_sim.go`**

```go
package main

import "fmt"

type PacerSimulator struct {
	TriggerRatio float64
	Kp           float64
	Ki           float64
	IntegralErr  float64
}

func (p *PacerSimulator) Update(actualHeap, goalHeap float64) {
	err := (actualHeap - goalHeap) / goalHeap
	p.IntegralErr += err

	// Коррекция триггера по алгоритму mgcpacer.go
	delta := p.Kp*err + p.Ki*p.IntegralErr
	p.TriggerRatio -= delta

	// Ограничители рантайма Go (clamp)
	if p.TriggerRatio < 0.1 {
		p.TriggerRatio = 0.1
	}
	if p.TriggerRatio > 0.95 {
		p.TriggerRatio = 0.95
	}
}

func main() {
	fmt.Println("=== Симуляция PI-контроллера mgcpacer.go ===")
	pacer := &PacerSimulator{
		TriggerRatio: 0.7, // старт на 70% прироста кучи
		Kp:           0.5,
		Ki:           0.1,
	}

	goal := 100.0 // Цель: 100 МБ

	// Моделируем 5 циклов с постепенной стабилизацией
	actualHistory := []float64{115.0, 108.0, 102.0, 100.5, 100.0}

	for step, actual := range actualHistory {
		fmt.Printf("Шаг %d: Фактический размер = %5.1f МБ (Цель = %.1f МБ) | TriggerRatio = %.3f\n",
			step+1, actual, goal, pacer.TriggerRatio)
		pacer.Update(actual, goal)
	}

	fmt.Printf("\nФинальный установившийся коэффициент триггера: %.3f\n", pacer.TriggerRatio)
}
```

ℹ️ Математическая модель PI-регулятора пейсера Go для стабилизации порога запуска GC

## Под капотом

В Go 1.19 реализация пейсера была полностью переписана на базе теории управления с непрерывным пересчетом `gcControllerState.commit`. Регулятор учитывает не только кучу, но и скорость роста стеков горутин.

## Подводные камни

При наличии кратковременных выбросов интегральная ошибка может накапливаться. Для защиты в `mgcpacer.go` реализован сброс интегратора (Anti-Windup).

## На собеседовании

**Вопрос:** Почему в рантайме Go выбран таргет утилизации CPU на разметку ровно в 25%?
**Ответ:** Значение 25% (одно ядро на каждые 4 доступных) является математически обоснованным компромиссом между скоростью работы пользовательских мутаторов и скоростью завершения разметки. При меньшем проценте сборщик не успевал бы завершать разметку до разрастания кучи, вызывая Mark Assist, а при большем — существенно деградировала бы общая пропускная способность прикладного кода.
