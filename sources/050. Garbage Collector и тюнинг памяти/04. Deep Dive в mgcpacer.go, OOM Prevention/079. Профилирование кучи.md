# Профилирование кучи: pprof.Lookup("heap") и анализ inuse_space vs inuse_objects

## Условие

Напишите программу, симулирующую утечку памяти. Соберите профиль кучи через pprof.Lookup("heap").WriteTo() и проанализируйте разницу между метриками inuse_space (объем памяти) и inuse_objects (число живых объектов).

### Исходная формулировка

**[Heap Profiles]**: Напиши программу, утекающую память. Собери heap profile: `pprof.Lookup("heap").WriteTo(file, 0)`. Проанализируй через `go tool pprof`. Найди строку кода, где аллоцируется утекающая память (обрати внимание на `inuse_space` vs `alloc_space`).

## Теория

Профиль кучи (`heap profile`) собирается сэмплированием: по умолчанию рантайм фиксирует стек вызовов для каждых 512 КБ выделенной памяти (`runtime.MemProfileRate = 512 * 1024`).

Четыре режима просмотра профиля кучи в `go tool pprof`:
1. **`-inuse_space` (по умолчанию):** Объем оперативной памяти в байтах, занятый живыми объектами прямо сейчас. Позволяет мгновенно найти структуры-гиганты.
2. **`-inuse_objects`:** Количество живых объектов в памяти прямо сейчас. Помогает найти миллионы мелких структур, создающих нагрузку на разметчик GC.
3. **`-alloc_space`:** Кумулятивный объем выделенной памяти за все время. Показывает, какая функция создает максимальное давление на аллокатор.
4. **`-alloc_objects`:** Кумулятивное число созданных объектов.

## Решение по шагам

1. Создайте структуру данных с накоплением объектов в глобальном срезе (утечка).
2. Запишите снимок профиля кучи в файл `heap.pprof`.
3. Запустите в терминале анализ: `go tool pprof -top -inuse_space heap.pprof`.
4. Сопоставьте виновника утечки со стеком вызовов.

## Код решения

**`heap_profile_leak.go`**

```go
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/pprof"
)

var leakingCache [][]byte

func simulateLeak() {
	// Имитация утечки: 20 МБ неудаляемых срезов
	for i := 0; i < 200; i++ {
		leakingCache = append(leakingCache, make([]byte, 100*1024))
	}
}

func main() {
	fmt.Println("=== Генерация профиля кучи (heap profile) ===")

	simulateLeak()
	runtime.GC() // Очищаем временный мусор, оставляя только утечку

	f, err := os.Create("heap.pprof")
	if err != nil {
		panic(err)
	}
	defer f.Close()

	// Записываем снимок кучи
	if err := pprof.Lookup("heap").WriteTo(f, 0); err != nil {
		panic(err)
	}

	fmt.Println("Профиль успешно записан в heap.pprof!")
	fmt.Println("Для анализа выполните: go tool pprof -top -inuse_space heap.pprof")
}
```

ℹ️ Сбор снимка кучи через pprof.Lookup("heap") для анализа утечки

**`Терминал`**

```bash
go run heap_profile_leak.go
go tool pprof -top -inuse_space heap.pprof
# В выводе top видно, что 100% памяти удерживается функцией main.simulateLeak
```

## Под капотом

Сбор профиля кучи в рантайме Go не требует полного обхода памяти: рантайм хранит прикрепленные структуры `bucket` и счетчики сэмплов непосредственно в таблице хэшей профиля `mprof.go`.

## Подводные камни

Поскольку `heap profile` сэмплируется раз в 512 КБ, единичные редкие аллокации размером 10 байт могут не попасть в выборку. Для 100% точного профиля мелких аллокаций в тестах устанавливают `runtime.MemProfileRate = 1`.

## На собеседовании

**Вопрос:** Чем отличается профиль -inuse_space от -alloc_space в pprof heap?
**Ответ:** -inuse_space показывает память, которая не освобождена и удерживается живыми объектами прямо сейчас (идеально для поиска утечек памяти). -alloc_space показывает суммарный объем всей памяти, выделенной функцией за все время работы сервиса, включая уже удаленный мусор (идеально для поиска горячих точек, нагружающих GC).
