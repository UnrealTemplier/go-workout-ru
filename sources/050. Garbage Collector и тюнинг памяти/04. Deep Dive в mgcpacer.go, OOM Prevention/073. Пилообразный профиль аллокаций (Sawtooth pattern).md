# Пилообразный профиль аллокаций (Sawtooth pattern) и тюнинг GC

## Условие

Создайте программу с пилообразной аллокацией: 100 MB -> 0 -> 100 MB -> 0. Исследуйте поведение сборщика при GOGC=50, 100 и 500 в сочетании с GOMEMLIMIT.

### Исходная формулировка

Создайте программу с пилообразной аллокацией: 100 MB → 0 → 100 MB → 0. Поиграйте с `GOGC` (50, 100, 500) и `GOMEMLIMIT` (150MB). Постройте график (через `runtime.ReadMemStats` в цикле) зависимости частоты GC от этих параметров.

## Теория

**Пилообразный профиль памяти (Sawtooth Allocation Pattern)** — классический график потребления памяти в циклических сервисах:
1. Фаза накопления: память монотонно растет от 0 до 100 МБ.
2. Фаза сброса: данные обработаны, ссылки зануляются, GC очищает кучу обратно до нуля.
3. Повторение цикла.

Влияние настроек:
* **GOGC=50:** Куча очищается мелкими зубьями (каждые 20-30 МБ). Зубья пилы частые и мелкие. Затраты CPU высоки.
* **GOGC=100:** Зубья нормального размера, очистка происходит примерно на середине цикла.
* **GOGC=500:** Сборщик мусора не запускается вовсе до конца накопления пачки! Вся пачка обрабатывается на максимальной скорости, а очистка происходит один раз в самом конце.

## Решение по шагам

1. Напишите цикл, моделирующий три волны пилообразного выделения 80 МБ.
2. Запустите с `GOGC=50` и зафиксируйте число сборок.
3. Запустите с `GOGC=200` и сравните число сборок.
4. Оцените экономию ресурсов.

## Код решения

**`sawtooth_gc.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func runSawtoothWave(waves int, gogc int) (uint32, time.Duration) {
	debug.SetGCPercent(gogc)
	runtime.GC()

	var m1, m2 runtime.MemStats
	runtime.ReadMemStats(&m1)
	start := time.Now()

	for w := 1; w <= waves; w++ {
		// Восходящая фаза пилы: рост до 60 МБ
		var waveData [][]byte
		for i := 0; i < 60; i++ {
			waveData = append(waveData, make([]byte, 1024*1024))
		}
		// Нисходящая фаза пилы: сброс ссылок
		waveData = nil
	}

	elapsed := time.Since(start)
	runtime.ReadMemStats(&m2)
	return m2.NumGC - m1.NumGC, elapsed
}

func main() {
	fmt.Println("=== Исследование пилообразного профиля (Sawtooth Allocation) ===")

	gc50, dur50 := runSawtoothWave(3, 50)
	fmt.Printf("GOGC=50  : Сборок GC = %-2d | Время = %v\n", gc50, dur50)

	gc100, dur100 := runSawtoothWave(3, 100)
	fmt.Printf("GOGC=100 : Сборок GC = %-2d | Время = %v\n", gc100, dur100)

	gc300, dur300 := runSawtoothWave(3, 300)
	fmt.Printf("GOGC=300 : Сборок GC = %-2d | Время = %v\n", gc300, dur300)

	debug.SetGCPercent(100)
}
```

ℹ️ Моделирование пилообразного профиля аллокаций при различных значениях GOGC

## Под капотом

В пилообразном профиле пейсер непрерывно подстраивает `HeapGoal` под спады и подъемы. При `GOGC=300` порог срабатывания сдвигается вверх, позволяя пику завершиться до включения фоновых воркеров разметки.

## Подводные камни

Если пик аллокаций окажется выше ожидаемого, высокий GOGC может привести к мгновенному OOM при отсутствии GOMEMLIMIT.

## На собеседовании

**Вопрос:** Как оптимизировать сборщик мусора Go под сервис с ярко выраженным пилообразным профилем нагрузки?
**Ответ:** Задать высокий GOGC (200–300) в сочетании с GOMEMLIMIT, установленным чуть выше пика пилы (на уровне 85% памяти контейнера). Это позволяет сервису обрабатывать подъем пилы без лишних сборок мусора, а очистку проводить в нижней точке спада нагрузки, экономя такты CPU.
