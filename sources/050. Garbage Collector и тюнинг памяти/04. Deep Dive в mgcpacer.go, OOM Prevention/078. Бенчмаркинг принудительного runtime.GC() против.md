# Бенчмаркинг принудительного runtime.GC() против адаптивного пейсера

## Условие

Напишите бенчмарк, сравнивающий регулярную принудительную сборку мусора через вызов runtime.GC() с естественной фоновой работой адаптивного пейсера. Докажите вред ручных вызовов.

### Исходная формулировка

**Ручной запуск `runtime.GC()`**: Напишите бенчмарк, в котором вы принудительно вызываете `runtime.GC()` в кодовой базе [494]. Объясните в комментариях, почему ручной вызов GC в продакшн-коде считается грубейшей ошибкой проектирования (это ломает внутренний математический алгоритм планирования запусков GC — GC Pacing, а также принудительно инициирует неоптимальные фазы Stop-The-World) [494].

## Теория

Почему регулярный вызов `runtime.GC()` разрушает производительность Go сервисов:
1. **Принудительный STW:** Каждые несколько секунд все горутины сервера замораживаются.
2. **Синхронная блокировка:** Горутина, вызвавшая `runtime.GC()`, блокируется до полной очистки всей кучи.
3. **Разрушение кэшей CPU:** Очистка спанов сбрасывает данные из L1/L2 кэша процессора.
4. **Сброс адаптивной статистики пейсера:** Адаптивный контроллер не может оценить естественную скорость мутатора и теряет предсказательную способность.

Естественный фоновый сборщик мусора обходится на 30–70% дешевле по общему времени исполнения!

## Решение по шагам

1. Напишите тест с принудительным `runtime.GC()` каждые 10 000 операций.
2. Напишите аналогичный тест с доверием автоматическому пейсеру.
3. Замерьте время выполнения и суммарную длительность пауз.
4. Сравните результаты.

## Код решения

**`manual_vs_auto_gc.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func runWithManualGC(count int) (time.Duration, time.Duration) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	for i := 0; i < count; i++ {
		_ = make([]byte, 2048)
		if i%10000 == 0 {
			runtime.GC() // Антипаттерн: частый ручной вызов!
		}
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	pauseTotal := time.Duration(m2.PauseTotalNs - m1.PauseTotalNs)
	return elapsed, pauseTotal
}

func runWithAutoGC(count int) (time.Duration, time.Duration) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	for i := 0; i < count; i++ {
		_ = make([]byte, 2048)
		// Доверяем автоматическому пейсеру Go!
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	pauseTotal := time.Duration(m2.PauseTotalNs - m1.PauseTotalNs)
	return elapsed, pauseTotal
}

func main() {
	const totalAllocs = 100000

	fmt.Println("=== Сравнение ручного runtime.GC() и адаптивного авто-GC ===")

	dManual, pManual := runWithManualGC(totalAllocs)
	fmt.Printf("Ручной runtime.GC(): Время = %-10v | Паузы STW = %v\n", dManual, pManual)

	dAuto, pAuto := runWithAutoGC(totalAllocs)
	fmt.Printf("Адаптивный авто-GC:  Время = %-10v | Паузы STW = %v\n", dAuto, pAuto)

	speedup := float64(dManual) / float64(dAuto)
	fmt.Printf("\nАдаптивный сборщик быстрее ручного в %.1f раз!\n", speedup)
}
```

ℹ️ Сравнение производительности при ручном вызове runtime.GC() и адаптивном автопилоте

## Под капотом

В `src/runtime/mgc.go` вызов `GC()` переводит текущую горутину в блокирующий режим ожидания на семафоре `work.sweepWaiters`. Горутина не вернется к бизнес-логике, пока фоновый очиститель не отрапортует о полной зачистке последнего спана.

## Подводные камни

Вызов `runtime.GC()` в цикле обработки запросов — частая ошибка разработчиков, пришедших из языков с ручным управлением памятью.

## На собеседовании

**Вопрос:** Почему в production-коде на Go вызов runtime.GC() практически всегда считается антипаттерном?
**Ответ:** Вызов runtime.GC() синхронно блокирует вызывающую горутину, принудительно останавливает все остальные горутины в фазах STW и форсирует полную очистку всех спанов кучи. Это ломает математическую модель адаптивного пейсера (mgcpacer), приводит к неэффективным расходам CPU и вызывает всплески задержек p99.
