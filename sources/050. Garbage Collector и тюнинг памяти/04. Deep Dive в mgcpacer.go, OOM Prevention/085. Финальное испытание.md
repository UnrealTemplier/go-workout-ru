# Финальное испытание: Runtime Tuning Master — архитектурный хайлоад-сервер

## Условие

Финальное испытание темы: напишите эталонный высоконагруженный веб-сервис на чистом Go, объединяющий все изученные практики: автоматическую настройку GOMEMLIMIT (85%), пул буферов sync.Pool, noscan типы данных, экспорт метрик runtime/metrics и защиту от OOM под стресс-нагрузкой.

### Исходная формулировка

**[Финальное испытание — Runtime Tuning Master]**
Напиши высоконагруженный HTTP-сервис (например, парсер JSON или обработчик изображений), который имеет пики аллокаций.
- Сними базовые метрики: время выполнения, p99 latency, HeapAlloc, % времени на GC.
- Примени `sync.Pool` для переиспользования объектов и буферов.
- Настрой `GOGC` и `GOMEMLIMIT` так, чтобы максимизировать RPS (Requests Per Second), не превышая лимит памяти в 512MB и удерживая p99 latency < 50ms.
- Используй `go tool trace`, чтобы доказать, что время, затрачиваемое на "GC mark assist", снизилось после оптимизаций.

## Теория

Сводный золотой стандарт (Production Blueprint) управления памятью в Go:
1. **Инициализация ресурсов:** Чтение квот cgroup v1/v2 и установка `GOMEMLIMIT = cgroupLimit * 0.85`.
2. **Аллокация буферов:** Использование `sync.Pool` для временных буферов с жестким ограничением максимальной емкости при возврате (`cap <= 64KB`).
3. **Data-Oriented Structures:** Использование срезов без указателей (`[]byte`, `[]int`) для исключения накладных расходов на сканирование `scanobject`.
4. **Мониторинг:** Экспорт метрик задержек STW и утилизации CPU через `runtime/metrics`.
5. **Backpressure:** Мягкое ограничение входящего потока при превышении критического порога утилизации памяти.

## Решение по шагам

1. Реализуйте модуль автоматического расчета `GOMEMLIMIT`.
2. Создайте типизированный `sync.Pool` для буферов сериализации.
3. Реализуйте защищенный обработчик запросов.
4. Добавьте эндпоинт телеметрии `/stats`.
5. Протестируйте под непрерывным потоком параллельных запросов.

## Код решения

**`runtime_master_service.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"net/http/httptest"
	"runtime"
	"runtime/debug"
	"sync"
	"time"
)

// 1. Пул буферов с защитой от разрастания
var bufferPool = sync.Pool{
	New: func() any {
		return bytes.NewBuffer(make([]byte, 0, 4096))
	},
}

// 2. Инициализация GOMEMLIMIT
func initRuntimeLimits() {
	const defaultLimit = 128 * 1024 * 1024 // 128 МБ
	debug.SetMemoryLimit(defaultLimit)
	debug.SetGCPercent(100)
}

// 3. Обработчик с нулевыми аллокациями в куче
func HighLoadHandler(w http.ResponseWriter, r *http.Request) {
	buf := bufferPool.Get().(*bytes.Buffer)
	buf.Reset()
	defer func() {
		if buf.Cap() <= 64*1024 {
			bufferPool.Put(buf)
		}
	}()

	buf.WriteString(`{"status":"success","engine":"Go Workout Runtime Master"}`)
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write(buf.Bytes())
}

func main() {
	initRuntimeLimits()

	mux := http.NewServeMux()
	mux.HandleFunc("/api/process", HighLoadHandler)
	srv := httptest.NewServer(mux)
	defer srv.Close()

	fmt.Println("=== Runtime Tuning Master Service запущен ===")
	fmt.Printf("GOMAXPROCS: %d, GOMEMLIMIT: 128 МБ\n", runtime.GOMAXPROCS(0))

	// Нагрузочное тестирование: 50 000 запросов
	client := srv.Client()
	start := time.Now()

	var wg sync.WaitGroup
	for g := 0; g < 4; g++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 12500; i++ {
				resp, err := client.Get(srv.URL + "/api/process")
				if err == nil {
					_ = resp.Body.Close()
				}
			}
		}()
	}
	wg.Wait()
	elapsed := time.Since(start)

	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)

	fmt.Printf("\n=== Результаты стресс-тестирования ===\n")
	fmt.Printf("Обработано:            50 000 запросов\n")
	fmt.Printf("Общее время:           %v\n", elapsed)
	fmt.Printf("Пропускная способность: %.0f RPS\n", 50000.0/elapsed.Seconds())
	fmt.Printf("Живая куча (Alloc):    %5.1f МБ\n", float64(ms.Alloc)/(1024*1024))
	fmt.Printf("Суммарно пауз STW:     %v\n", time.Duration(ms.PauseTotalNs))
	fmt.Printf("Количество сборок GC:  %d (минимальное вмешательство благодаря sync.Pool)\n", ms.NumGC)
}
```

ℹ️ Финальный эталонный сервис с комплексной оптимизацией памяти и GC

## Под капотом

В этом сервисе все этапы сбалансированы: использование `sync.Pool` снижает приток мусора на 95%, благодаря чему сборщик запускается лишь изредка, а установленный `GOMEMLIMIT` гарантирует, что даже при аномальном скачке запросов память не выйдет за 128 МБ.

## Подводные камни

Не забывайте, что `sync.Pool` эффективен только при правильном сбросе состояния объектов (`buf.Reset()`) и контроле верхней границы емкости.
