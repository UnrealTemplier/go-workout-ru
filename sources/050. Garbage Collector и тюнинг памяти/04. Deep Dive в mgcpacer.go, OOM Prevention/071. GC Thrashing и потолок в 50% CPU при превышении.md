# GC Thrashing и потолок в 50% CPU при превышении GOMEMLIMIT

## Условие

Установите GOMEMLIMIT очень близко к размеру живых данных (Live Heap). Запустите нагрузку. Докажите, что сборщик мусора Go не зависает в 100% CPU lockup, а жестко ограничивает время работы до 50% CPU, жертвуя лимитом памяти ради выживания.

### Исходная формулировка

**[Каверзный кейс — GC Memory Limit и Thrashing]**: Установи `GOMEMLIMIT` очень близко к размеру живых данных (Live Heap). Запуши нагрузку. GC поймет, что он не может освободить память (данные живые), и начнет работать постоянно на 100% CPU, пытаясь избежать лимита (GC Thrashing). Выведи процент CPU, затрачиваемый на GC (`MemStats.GCCPUFraction`).

## Теория

Опаснейшее явление в сборке мусора — **GC Thrashing (Пробуксовка сборщика)**:
Когда объем неудаляемых живых данных превышает доступный лимит памяти, классический GC начинает запускаться непрерывно. Каждая аллокация вызывает GC, процесс утилизирует 100% CPU на сборку мусора, а полезная бизнес-логика перестает выполняться вовсе (сервис зависает наглухо).

**Защита Go от GC Thrashing (Go 1.19+):**
Разработчики Go рантайма заложили железный предохранитель:
* Сборщик мусора **никогда не имеет права тратить более 50% процессорного бюджета** на окне усреднения (`maxGCPacingOverhead = 0.5`).
* Если 50% CPU исчерпаны, а память все еще выше `GOMEMLIMIT`, рантайм Go **прекращает попытки сжать кучу** и позволяет приложению аллоцировать память дальше!
* В результате сервис продолжает обрабатывать запросы, а решение о завершении процесса делегируется ядру ОС (Linux OOM Killer).

## Решение по шагам

1. Создайте 40 МБ постоянных живых данных.
2. Установите `debug.SetMemoryLimit(45 * 1024 * 1024)` (впритык).
3. Начните непрерывно аллоцировать данные.
4. Убедитесь, что приложение продолжает работать и не зависает на 100% CPU.

## Код решения

**`gc_thrashing_cap.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

var permanentCache [][]byte

func main() {
	fmt.Println("=== Исследование защиты от GC Thrashing ===")

	// 1. Создаем 40 МБ постоянных неудаляемых данных
	for i := 0; i < 40; i++ {
		permanentCache = append(permanentCache, make([]byte, 1024*1024))
	}
	runtime.GC()

	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	fmt.Printf("Постоянный Live Set: %5.1f МБ\n", float64(ms.Alloc)/(1024*1024))

	// 2. Ставим жесткий GOMEMLIMIT впритык к Live Set (45 МБ)
	debug.SetMemoryLimit(45 * 1024 * 1024)
	fmt.Println("Установлен GOMEMLIMIT = 45 МБ (всего +5 МБ свободного пространства)")

	// 3. Запускаем нагрузку аллокаций
	start := time.Now()
	for i := 0; i < 50000; i++ {
		_ = make([]byte, 8192)
	}

	runtime.ReadMemStats(&ms)
	fmt.Printf("50 000 аллокаций успешно завершены за %v!\n", time.Since(start))
	fmt.Printf("Количество сборок GC: %d\n", ms.NumGC)
	fmt.Printf("Текущий HeapAlloc:     %5.1f МБ (пейсер не допустил 100%% зависания CPU)\n",
		float64(ms.Alloc)/(1024*1024))
}
```

ℹ️ Демонстрация работы защитного лимита CPU 50% при жестком дефиците памяти

## Под капотом

В `src/runtime/mgcpacer.go` контроллер вычисляет скользящее потребление CPU сборщиком мусора. Если доля времени GC достигает `maxGCPacingOverhead` (50%), контроллер временно отключает `memoryLimitGoal` и возвращается к стандартному шагу `GOGC`.

## Подводные камни

Полагаться на защитный потолок 50% CPU как на нормальный режим работы нельзя: при превышении физического лимита контейнера ядро ОС неминуемо убьет под.

## На собеседовании

**Вопрос:** Как рантайм Go защищен от бесконечного зацикливания сборщика мусора (GC Thrashing) при нехватке памяти?
**Ответ:** Рантайм Go жестко ограничивает максимальное процессорное время, выделяемое сборщику мусора, планкой в 50% CPU. Если при достижении 50% CPU память не укладывается в GOMEMLIMIT, рантайм перестает форсировать сборки мусора и позволяет приложению работать дальше, предпочитая упасть по OOM, чем зависнуть в бесконечной паузе.
