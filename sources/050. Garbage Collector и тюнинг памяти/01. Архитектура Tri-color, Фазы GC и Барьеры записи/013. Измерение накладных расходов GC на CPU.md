# Измерение накладных расходов GC на CPU (GC CPU Overhead)

## Условие

Используйте runtime.ReadMemStats() для получения PauseTotalNs и NumGC. Напишите функцию, вычисляющую точный процент времени, потраченного процессором на паузы сборщика мусора.

### Исходная формулировка

**GC CPU overhead**: Используйте `runtime.ReadMemStats()` для получения `PauseTotalNs` и `NumGC`. Вычислите процент времени, потраченного на GC.

## Теория

Мониторинг влияния сборщика мусора на приложение в Production опирается на две группы метрик:
1. **Latency Overhead (Задержки STW):** Какая часть астрономического времени (Wall Clock) была потеряна на остановку мира (`PauseTotalNs`).
2. **Throughput / CPU Overhead:** Какая часть вычислительных циклов ядер процессора была отобрана фоновыми воркерами разметки и операциями Mark Assist.

В структуре `runtime.MemStats`:
* `PauseTotalNs` — суммарное время всех STW пауз в наносекундах с момента старта процесса.
* `NumGC` — количество завершенных циклов GC.
* `PauseNs[256]` — кольцевой буфер последних 256 длительностей пауз STW.

## Решение по шагам

1. Зафиксируйте стартовое время и начальные показания `runtime.ReadMemStats`.
2. Выполните цикл с нагрузкой на память.
3. Прочитайте конечные показания `runtime.ReadMemStats`.
4. Рассчитайте коэффициент отношения времени STW к общему времени выполнения программы в процентах.

## Код решения

**`gc_overhead.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func measureOverhead() {
	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)
	wallStart := time.Now()

	// Нагрузка: выделение 100 000 срезов
	for i := 0; i < 100000; i++ {
		_ = make([]int, 2048)
	}

	wallDuration := time.Since(wallStart)
	runtime.ReadMemStats(&mEnd)

	gcRuns := mEnd.NumGC - mStart.NumGC
	pauseDuration := time.Duration(mEnd.PauseTotalNs - mStart.PauseTotalNs)

	var stwPercent float64
	if wallDuration > 0 {
		stwPercent = (float64(pauseDuration) / float64(wallDuration)) * 100.0
	}

	fmt.Println("=== Анализ накладных расходов сборщика мусора ===")
	fmt.Printf("Общее время работы программы:  %v\n", wallDuration)
	fmt.Printf("Количество сборок (NumGC):     %d\n", gcRuns)
	fmt.Printf("Суммарное время STW пауз:      %v\n", pauseDuration)
	fmt.Printf("Процент времени в паузах STW:   %.4f%%\n", stwPercent)

	if gcRuns > 0 {
		fmt.Printf("Средняя пауза за один цикл:    %v\n", pauseDuration/time.Duration(gcRuns))
	}
}

func main() {
	measureOverhead()
}
```

ℹ️ Расчет процента времени STW пауз по отношению к общему времени исполнения

## Под капотом

Поле `PauseTotalNs` обновляется в конце каждого вызова `gcMarkTermination` при удержании блокировки STW. Точность таймеров зависит от системного таймера ядра ОС (`CLOCK_MONOTONIC`). На современных процессорах типичное время одного STW составляет от 50 до 300 микросекунд.

## Подводные камни

Метрика `PauseTotalNs` учитывает ТОЛЬКО паузы Stop-The-World! Она совершенно не отражает 25% CPU, которые фоновые горутины потратили на Concurrent Marking, а также время задержек Mark Assist. Оценивать полное влияние GC только по `PauseTotalNs` — опасная ошибка.

## На собеседовании

**Вопрос:** Если метрика PauseTotalNs показывает, что STW занимает всего 0.1% времени, означает ли это, что GC не влияет на пропускную способность сервиса?
**Ответ:** Нет, не означает. PauseTotalNs фиксирует только паузы остановки мира (Mark Setup и Mark Termination). Однако фаза Concurrent Marking забирает 25% ресурсов всех ядер процессора для фоновых разметчиков, а при интенсивных аллокациях пользовательские горутины замедляются механизмом Mark Assist. Для полноценной оценки нужно смотреть на метрику `runtime.MemStats.GCCPUFraction`.
