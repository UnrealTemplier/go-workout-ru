# Метрики памяти: HeapAlloc vs TotalAlloc

## Условие

Изучите разницу между HeapAlloc (текущий объем живых объектов кучи) и TotalAlloc (кумулятивный объем всех когда-либо выделенных байт кучи) в структуре runtime.MemStats.

### Исходная формулировка

**Live heap vs allocated**: Изучите разницу между `HeapAlloc` (текущее использование) и `TotalAlloc` (кумулятивные аллокации) в `MemStats`.

## Теория

В структуре `runtime.MemStats` есть две ключевые метрики аллокации:

1. **`HeapAlloc` (или `Alloc`):**
   * Мгновенный "снимок" (Gauge) размера памяти в байтах, занятой живыми объектами кучи прямо сейчас.
   * Увеличивается при `mallocgc` и **уменьшается после завершения фазы Sweeping**, когда освобожденные объекты возвращаются в пулы.
   * Именно это значение используется пейсером для расчета `NextGC`.

2. **`TotalAlloc`:**
   * Монотонно возрастающий счетчик (Counter) суммарного объема байт, когда-либо выделенных в куче с момента старта процесса.
   * **Никогда не уменьшается**, даже после миллиона сборок мусора.
   * Производная от `TotalAlloc` по времени (\(\frac{d(\text{TotalAlloc})}{dt}\)) показывает **скорость аллокации (Allocation Rate)** в байтах в секунду — главную причину нагрузки на CPU.

## Решение по шагам

1. Зафиксируйте начальные значения `HeapAlloc` и `TotalAlloc`.
2. Выделите 50 МБ памяти во временных объектах и очистите ссылки.
3. Вызовите `runtime.GC()`.
4. Сравните значения: `HeapAlloc` вернется к исходному, а `TotalAlloc` вырастет на 50 МБ.

## Код решения

**`alloc_diff.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

func printStats(step string) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("[%s]\n", step)
	fmt.Printf("  HeapAlloc  (Текущая куча): %8.2f МБ\n", float64(m.HeapAlloc)/(1024*1024))
	fmt.Printf("  TotalAlloc (Всего выделено): %8.2f МБ\n", float64(m.TotalAlloc)/(1024*1024))
}

func main() {
	printStats("1. Старт программы")

	// Аллоцируем 50 МБ временных данных
	temp := make([][]byte, 50)
	for i := range temp {
		temp[i] = make([]byte, 1024*1024)
	}
	printStats("2. Выделено 50 МБ в куче")

	// Зануляем ссылки и вызываем GC
	temp = nil
	runtime.GC()
	printStats("3. После очистки мусора runtime.GC()")
}
```

ℹ️ Сравнение поведения мгновенной метрики HeapAlloc и кумулятивной TotalAlloc

## Под капотом

В `src/runtime/mstats.go` поле `total_alloc` инкрементируется при каждом выделении в `mallocgc`: `memstats.total_alloc += uint64(size)`. Поле `heap_alloc` вычисляется как разница между суммарным объемом спанов и свободными ячейками `allocBits`.

## Подводные камни

Ошибка новичков при мониторинге: строить график `TotalAlloc` и паниковать из-за "утечки памяти", видя непрерывно растущую прямую линию. `TotalAlloc` обязан расти всегда. Для отслеживания реального размера процесса нужно смотреть на `HeapAlloc` и RSS.

## На собеседовании

**Вопрос:** Как по метрикам runtime.MemStats определить скорость генерации мусора приложением?
**Ответ:** Скорость генерации мусора (Allocation Rate) определяется как приращение счетчика `TotalAlloc` за интервал времени: `(TotalAlloc_t2 - TotalAlloc_t1) / delta_t`. Если приращение составляет сотни мегабайт в секунду при стабильном значении `HeapAlloc`, это указывает на активное создание временных короткоживущих объектов, создающих высокую нагрузку на GC.
