# Гонки указателей и барьеры записи (Pointer Mutation Races)

## Условие

Объясните проблему перезаписи указателей во время конкурентной разметки GC: черный объект начинает ссылаться на белый, а серый теряет ссылку на этот же белый. Покажите в коде симуляцию этой гонки без барьера и с включенным барьером записи.

### Исходная формулировка

**Роль барьеров записи (Write Barriers)**: Сборщик мусора Go работает конкурентно (параллельно с выполнением вашего кода). Объясните проблему: если во время разметки ваша программа перепишет указатель (черный объект начнет ссылаться на белый, а серый объект потеряет ссылку на этот же белый), GC может ошибочно удалить живой белый объект. Объясните, как барьер записи (Write Barrier), автоматически включаемый рантаймом на фазе разметки, перехватывает операции записи указателей и принудительно перекрашивает такие объекты в серый цвет, предотвращая потерю данных.

## Теория

Фундаментальная теорема сборки мусора гласит: **потеря живого объекта возможна тогда и только тогда, когда одновременно выполняются два условия**:
1. Мутатор записывает ссылку на белый объект в черный объект.
2. Мутатор удаляет все ссылки на этот белый объект из всех серых объектов.

Если оба условия истинны, белый объект становится невидимым для сборщика, потому что черный объект уже не будет повторно сканироваться, а серый объект о нем больше не знает.

Барьер записи предотвращает выполнение хотя бы одного из этих условий:
* **Барьер вставки (Dijkstra):** перехватывает условие 1 — при попытке черного объекта сослаться на белый, белый немедленно красится в серый.
* **Барьер удаления (Yuasa):** перехватывает условие 2 — при попытке удалить ссылку на белый объект, он красится в серый.

## Решение по шагам

1. Смоделируйте структуру объектов с ссылками.
2. Создайте сценарий «без барьера»: покажите, как теряется объект `Target`.
3. Создайте сценарий «с барьером»: покажите, как перехват мутации сохраняет `Target` в живых.
4. Сравните итоговые результаты разметки.

## Код решения

**`barrier_race.go`**

```go
package main

import "fmt"

type Item struct {
	Name  string
	Color string
}

func main() {
	fmt.Println("=== СЦЕНАРИЙ 1: Потеря объекта БЕЗ барьера записи ===")
	// Черный родитель уже проверен
	blackA := &Item{Name: "Black_A", Color: "Black"}
	// Серый родитель еще в очереди
	greyB := &Item{Name: "Grey_B", Color: "Grey"}
	// Белый потомок, ссылка пока у greyB
	whiteC := &Item{Name: "White_C", Color: "White"}

	var blackRef *Item = nil
	var greyRef *Item = whiteC

	// Мутатор совершает 2 действия во время разметки:
	// 1. Черный берет ссылку на белый
	blackRef = whiteC
	// 2. Серый удаляет ссылку на белый
	greyRef = nil

	// GC сканирует greyRef (там nil) и завершает работу!
	// whiteC остался Белым! Мусорщик его уничтожит, хотя blackRef ссылается на него!
	fmt.Printf("Результат без барьера: White_C имеет цвет [%s] -> БУДЕТ УДАЛЕН ОШИБОЧНО!\n", whiteC.Color)

	fmt.Println("\n=== СЦЕНАРИЙ 2: Защита объекта С барьером записи ===")
	// Повторяем с барьером Юасы: при затирании ссылки в greyRef старый объект седеет
	whiteC.Color = "White"
	greyRef = whiteC

	// Мутатор стирает ссылку:
	overwritten := greyRef
	if overwritten.Color == "White" {
		overwritten.Color = "Grey" // Барьер перехватил операцию!
		fmt.Printf("Барьер записи: объект '%s' принудительно перекрашен в Grey!\n", overwritten.Name)
	}
	greyRef = nil
	blackRef = whiteC

	fmt.Printf("Результат с барьером: White_C имеет цвет [%s] -> ЖИВ И БУДЕТ СОХРАНЕН!\n", whiteC.Color)
	_ = blackA
	_ = blackRef
	_ = greyB
}
```

## Под капотом

В ассемблерном коде Go компилятор вставляет барьер не на все записи, а только на записи указателей в память кучи (`writebarrierptr`). Запись в локальные переменные на стеке транслируется в обычные `MOVQ` инструкции без проверок барьера, что обеспечивает предельную производительность локальных вычислений.

## Подводные камни

Низкоуровневые операции с пакетом `unsafe` (например, вычисление адресов и прямая запись байтов через `*(*uintptr)(ptr) = val`) могут обойти компиляторный барьер записи. Если мутировать указатели через `unsafe` во время фазы разметки, GC может потерять живой объект и разрушить память.

## На собеседовании

**Вопрос:** Почему при использовании пакета unsafe в Go существует риск нарушения работы Garbage Collector?
**Ответ:** Компилятор Go автоматически расставляет вызовы Write Barrier только для типизированных операций записи указателей в кучу. Манипуляции с нетипизированной памятью через unsafe.Pointer или uintptr могут обойти барьер записи. В результате GC не узнает о появлении новой ссылки на белый объект, что приведет к его ложному удалению и возникновению висячего указателя (dangling pointer).
