# Ментальная карта трех цветов и инварианты целостности

## Условие

Опишите в виде подробного комментария или ментальной карты концепцию трех цветов, используемую сборщиком мусора Go для определения живых объектов: Белые (кандидаты на удаление), Серые (активные объекты, чьи дети не исследованы), Черные (исследованные живые объекты).

### Исходная формулировка

**Трехцветный алгоритм разметки (Tri-color Mark-and-Sweep)**: Опишите в виде подробного комментария или ментальной карты концепцию трех цветов, используемую сборщиком мусора Go для определения живых объектов:
* **Белые объекты** — кандидаты на удаление (в начале фазы разметки все объекты белые).
* **Серые объекты** — активные объекты, найденные сборщиком, чьи дочерние ссылки еще не исследованы.
* **Черные объекты** — активные объекты, которые были исследованы (они точно не будут удалены).

## Теория

Концептуальная модель Tri-color Mark-and-Sweep была сформулирована Дейкстрой, Лампортом и др. в 1978 году и адаптирована инженерами Go для обеспечения микросекундных пауз.

```
       [ Корневые указатели (Стек, Глобальные) ]
                           │
                           ▼
                 ┌──────────────────┐
                 │  Серые объекты   │ ◄─── Добавляются при открытии
                 │   (Work Queue)   │      (gcWork buffer)
                 └─────────┬────────┘
                           │ Исследование ссылок
                           ▼
                 ┌──────────────────┐
                 │  Черные объекты  │ ◄─── Инвариант: НЕ ссылаются на белые напрямую!
                 │ (gcmarkBits = 1) │
                 └──────────────────┘

   [ Изолированные белые объекты ] ───► [ Sweep Phase: возврат памяти в mcentral ]
```

Инварианты корректности:
1. **Strong Tri-color Invariant:** Черный объект никогда не указывает прямо на белый объект.
2. **Weak Tri-color Invariant:** Если черный объект указывает на белый, то к этому белому объекту обязан вести путь от какого-либо серого объекта.

## Решение по шагам

1. Создайте структуру памяти, отражающую взаимосвязи между объектами в куче.
2. Сформируйте цепочку: Root -> Grey -> White.
3. Продемонстрируйте переход цветов с выводом инвариантов.
4. Убедитесь, что все достижимые объекты стали черными, а изолированные остались белыми.

## Код решения

**`mental_map.go`**

```go
package main

import "fmt"

// Карта состояний памяти GC Go
const (
	StateWhite = "Белый (Кандидат на удаление/Неисследован)"
	StateGrey  = "Серый (Живой, дети в очереди на проверку)"
	StateBlack = "Черный (Живой, все дочерние указатели проверены)"
)

type HeapObject struct {
	Address uintptr
	Name    string
	State   string
	Refs    []*HeapObject
}

func main() {
	fmt.Println("=== МЕНТАЛЬНАЯ КАРТА ТРЕХЦВЕТНОГО СБОРЩИКА GO ===")
	fmt.Println("1. Старт Marking: Стеки и глобалы сканируются -> корни становятся Серыми.")
	fmt.Println("2. Итерация: Из серой очереди извлекается объект, сканируются его поля.")
	fmt.Println("3. По найденным указателям белые объекты красятся в Серый и кладутся в ворклист.")
	fmt.Println("4. Сам объект перекрашивается в Черный.")
	fmt.Println("5. Завершение: Серая очередь пуста. Все оставшиеся белые объекты — мусор.")

	// Демонстрация
	objRoot := &HeapObject{Address: 0x1000, Name: "GlobalVar", State: StateGrey}
	objLive := &HeapObject{Address: 0x2000, Name: "ActiveSession", State: StateWhite}
	objDead := &HeapObject{Address: 0x3000, Name: "StaleRequest", State: StateWhite}

	objRoot.Refs = append(objRoot.Refs, objLive)

	fmt.Printf("\nДо сканирования: %s [%s]\n", objLive.Name, objLive.State)
	// Сканирование корня
	for _, ref := range objRoot.Refs {
		if ref.State == StateWhite {
			ref.State = StateGrey
		}
	}
	objRoot.State = StateBlack

	fmt.Printf("После сканирования корня: %s [%s]\n", objLive.Name, objLive.State)
	fmt.Printf("Мусорный объект остался нетронутым: %s [%s]\n", objDead.Name, objDead.State)
}
```

ℹ️ Структурное представление переходов состояний в трехцветной разметке

## Под капотом

Внутри рантайма Go каждый логический процессор P имеет собственный кэш указателей разметки `p.gcw` (`gcWork`). Он содержит два буфера по 256 указателей (`wbuf1` и `wbuf2`). За счет локальности P серые объекты перемещаются между мутатором и маркер-воркером без блокировок центральных структур.

## Подводные камни

Распространенное заблуждение: считать, что серые объекты сохраняются на диск или в отдельную хэш-таблицу. Серый объект — это всего лишь указатель на вершину объекта в буфере `gcWork` при нулевом или единичном бите в `gcmarkBits`.

## На собеседовании

**Вопрос:** В чем разница между черным и серым объектом в памяти Go?
**Ответ:** И черный, и серый объекты гарантированно живы. Разница в том, что серый объект находится в очереди на сканирование (его поля с указателями еще не проверены), а черный объект уже полностью просканирован, все найденные по его указателям дочерние объекты уже переведены в серый статус, и повторно черный объект не исследуется.
