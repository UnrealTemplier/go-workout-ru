# GC Pacing и триггеры запуска сборщика

## Условие

Runtime решает, когда запускать GC, чтобы завершить marking до того, как heap вырастет слишком сильно. Изучите формулу: target heap size = live heap * (1 + GOGC/100). Напишите программу, рассчитывающую целевой порог срабатывания следующего GC.

### Исходная формулировка

**GC pacing**: Runtime решает, когда запускать GC, чтобы завершить marking до того, как heap вырастет слишком сильно. Изучите формулу: `target heap size = live heap * (1 + GOGC/100)`.

## Теория

**GC Pacing (Пейсер сборщика мусора)** — это адаптивный алгоритм контроллера обратной связи в рантайме Go (`src/runtime/mgcpacer.go`), который непрерывно вычисляет оптимальный момент старта разметки.

Цель пейсера:
1. Завершить разметку ровно в тот момент, когда размер кучи достигнет `NextGC` (`HeapGoal`).
2. Потратить ровно 25% ресурсов CPU на разметку (GC CPU Target = 0.25).

Формула целевого размера кучи:
$$\text{HeapGoal} = \text{LiveHeap} \times \left(1 + \frac{\text{GOGC}}{100}\right)$$

* `LiveHeap` — объем памяти, признанной живой в конце предыдущего цикла сборки.
* `GOGC` — процент прироста (по умолчанию 100%, то есть куча может удвоиться).

Если приложение аллоцирует память слишком быстро, пейсер динамически повышает требование к горутинам выполнять `Mark Assist`, замедляя мутатор.

## Решение по шагам

1. Получите текущие метрики `runtime.MemStats`.
2. Извлеките значения `Alloc` (текущий размер живой кучи) и `NextGC` (цель следующей сборки).
3. Проверьте отношение `NextGC / Alloc` и сравните его с настройкой `debug.SetGCPercent`.
4. Измените GOGC и убедитесь, что порог `NextGC` пропорционально пересчитался.

## Код решения

**`pacing.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func printPacingStats(label string) {
	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	fmt.Printf("[%s]\n", label)
	fmt.Printf("  Живые данные (Alloc):    %8.2f МБ\n", float64(ms.Alloc)/(1024*1024))
	fmt.Printf("  Цель запуска (NextGC):   %8.2f МБ\n", float64(ms.NextGC)/(1024*1024))
	ratio := float64(ms.NextGC) / float64(ms.Alloc)
	fmt.Printf("  Коэффициент отношения:   %.2fx\n", ratio)
}

func main() {
	// Создаем 20 МБ живых данных
	data := make([][]byte, 20)
	for i := range data {
		data[i] = make([]byte, 1024*1024)
	}

	runtime.GC()
	printPacingStats("Дефолтный GOGC = 100")

	// Устанавливаем GOGC = 50 (цель: +50% к объему)
	oldGOGC := debug.SetGCPercent(50)
	runtime.GC()
	printPacingStats("Агрессивный GOGC = 50")

	// Устанавливаем GOGC = 200 (цель: +200% к объему)
	debug.SetGCPercent(200)
	runtime.GC()
	printPacingStats("Ленивый GOGC = 200")

	debug.SetGCPercent(oldGOGC)
}
```

ℹ️ Расчет целевого порога NextGC в зависимости от значения GOGC

## Под капотом

В `mgcpacer.go` контроллер использует пропорционально-интегральный (PI) регулятор. Он измеряет скорость аллокации памяти мутатором (байты/сек) и скорость сканирования разметчиками (байты/сек). Если скорость аллокации возрастает, сборщик начинает фазу разметки заблаговременно (при триггере `heap_trigger`), чтобы не допустить превышения `HeapGoal`.

## Подводные камни

При фиксированном значении GOGC=100 и малом объеме живой памяти (например, 2 МБ) сборщик будет запускаться очень часто (каждые 2 МБ новых аллокаций), сжигая до 25% CPU. И наоборот, при живой памяти 10 ГБ сборщик запустится только при достижении 20 ГБ, что может привести к OOM в Docker-контейнере.

## На собеседовании

**Вопрос:** Как рантайм Go определяет, когда именно запустить сборку мусора при GOGC=100?
**Ответ:** Рантайм вычисляет HeapGoal = LiveHeap * 2. Однако сам цикл запускается не на отметке HeapGoal, а раньше — на пороге `heap_trigger`, который рассчитывается адаптивным пейсером (mgcpacer.go) исходя из текущей скорости аллокации и скорости работы маркер-воркеров, чтобы к моменту достижения HeapGoal разметка уже была завершена.
