# Сравнительный бенчмаркинг параметров GOGC=50 vs GOGC=200

## Условие

Установите GOGC=50 (частый GC, экономия памяти, больше CPU) и GOGC=200 (редкий GC, больше памяти, экономия CPU). Проведите бенчмарк и замерьте разницу в пиковом потреблении кучи и затратах процессорного времени.

### Исходная формулировка

**[Тюнинг GOGC]**: Установи `GOGC=50` (GC будет запускаться чаще, память будет маленькой, но больше CPU уйдет на GC). Установи `GOGC=200` (память вырастет, но CPU сэкономится). Напиши бенчмарк, который показывает разницу во времени выполнения и пиковой памяти (`B.ReportAllocs` и `runtime.ReadMemStats`).

## Теория

Выбор значения `GOGC` — это фундаментальный компромисс (Trade-off) между памятью (RAM) и процессором (CPU):

| Параметр | Частота сборок | Затраты CPU на GC | Пиковый размер Heap | Throughput сервиса |
| :--- | :--- | :--- | :--- | :--- |
| **GOGC=50** | Высокая (+100% сборок) | Высокие (~20-25%) | Минимальный (-25-30% RAM) | Снижен |
| **GOGC=100** | Стандартная (дефолт) | Умеренные (~10-15%) | Номинальный (2x Live) | Базовый |
| **GOGC=200** | Низкая (-50% сборок) | Низкие (~5-7%) | Высокий (+50% RAM) | Максимальный (+10-20%) |

Если сервер имеет избыточный объем RAM (например, 64 ГБ), а сервис упирается в CPU, повышение `GOGC=200` или `300` позволяет высвободить до 15% вычислительной мощности для полезной бизнес-логики.

## Решение по шагам

1. Напишите изолированную функцию бенчмарка с фиксацией `MemStats`.
2. Запустите замер при `GOGC=50`.
3. Запустите замер при `GOGC=200`.
4. Сравните `HeapAlloc` peak и `NumGC`.

## Код решения

**`tuning_bench.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func benchmarkGOGC(val int) {
	debug.SetGCPercent(val)
	runtime.GC()

	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)

	start := time.Now()
	// Имитируем поток запросов: 100 000 аллокаций
	for i := 0; i < 100000; i++ {
		_ = make([]int, 1024)
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&mEnd)
	fmt.Printf("GOGC=%-3d | Время: %-10v | Сборок GC: %-3d | Пик NextGC: %6.1f МБ\n",
		val, elapsed, mEnd.NumGC-mStart.NumGC, float64(mEnd.NextGC)/(1024*1024))
}

func main() {
	fmt.Println("=== Сравнение производительности GOGC ===")
	benchmarkGOGC(50)
	benchmarkGOGC(100)
	benchmarkGOGC(200)
	debug.SetGCPercent(100)
}
```

ℹ️ Сравнение числа сборок и скорости выполнения при разных значениях GOGC

## Под капотом

При увеличении `GOGC` расширяется окно между сборками. За это время многие короткоживущие объекты успевают умереть до старта следующей разметки. В результате маркер-воркеры сканируют значительно меньший граф объектов, что резко снижает суммарные затраты инструкций CPU на сборку мусора.

## Подводные камни

Опасность завышения `GOGC=200-300` без задания `GOMEMLIMIT` в том, что при резком всплеске нагрузки (spike traffic) размер кучи взлетит в разы и вызовет падение по OOM. Тюнинговать GOGC вверх можно только при установленном `GOMEMLIMIT`.

## На собеседовании

**Вопрос:** Когда имеет смысл увеличивать GOGC выше 100 в высоконагруженном бэкенде?
**Ответ:** Когда сервис утилизирует CPU на пределе, но на хосте/поде имеется большой запас свободной оперативной памяти. Увеличение GOGC до 150–200 сокращает частоту сборок мусора в 1.5–2 раза, экономя такты CPU на разметку и повышая RPS сервиса. При этом обязательно задается GOMEMLIMIT как страховка от переполнения памяти.
