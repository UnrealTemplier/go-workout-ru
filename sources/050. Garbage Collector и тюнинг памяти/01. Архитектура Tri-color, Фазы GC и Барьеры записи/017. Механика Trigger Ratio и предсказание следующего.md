# Механика Trigger Ratio и предсказание следующего цикла

## Условие

По умолчанию GOGC=100. Это означает, что следующий цикл GC запустится, когда размер кучи удвоится по сравнению с размером после прошлого GC. Напишите программу, которая аллоцирует 100MB и демонстрирует через gctrace, когда запустится GC.

### Исходная формулировка

**[GOGC (Trigger Ratio)]**: По умолчанию `GOGC=100`. Это означает, что следующий цикл GC запустится, когда размер кучи (Heap) удвоится по сравнению с размером после прошлого GC. Напиши программу, которая аллоцирует 100MB. Посмотри в `gctrace`, когда запустится GC (цель `goal` = 2x от живых данных).

## Теория

Сборщик мусора Go не ждет, пока размер кучи строго достигнет `HeapGoal` (`2x` от живых данных при `GOGC=100`).

Если бы GC запустился в точке `2x`, то за время, пока идет конкурентная разметка (Marking), мутатор продолжил бы аллоцировать память, и финальный размер кучи составил бы `2.5x` или `3x`, превысив целевой показатель.

Поэтому вводится концепция **Trigger Ratio (Коэффициент триггера)**:
$$\text{Trigger} = \text{LiveHeap} \times (1 + \text{TriggerRatio})$$

Где \(\text{TriggerRatio} < \frac{\text{GOGC}}{100}\). Например, при `GOGC=100` триггер обычно составляет около \(1.6\text{x}-1.7\text{x}\). На этой отметке включаются маркер-воркеры, и к моменту достижения \(2.0\text{x}\) разметка гарантированно завершается.

## Решение по шагам

1. Аллоцируйте базовый объем постоянных данных (например, 20 МБ).
2. Вызовите `runtime.GC()`, чтобы зафиксировать начальный `LiveHeap`.
3. Начните в цикле добавлять память и отслеживайте, на каком объеме `Alloc` сработает фоновый GC.
4. Сравните порог с расчетом Trigger Ratio.

## Код решения

**`trigger_ratio.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var ms runtime.MemStats

	// 1. Создаем постоянные живые данные (20 МБ)
	persistentData := make([][]byte, 20)
	for i := range persistentData {
		persistentData[i] = make([]byte, 1024*1024)
	}

	runtime.GC()
	runtime.ReadMemStats(&ms)

	liveHeap := ms.Alloc
	heapGoal := ms.NextGC
	fmt.Printf("Базовые живые данные (LiveHeap): %8.2f МБ\n", float64(liveHeap)/(1024*1024))
	fmt.Printf("Целевой порог (HeapGoal NextGC): %8.2f МБ\n", float64(heapGoal)/(1024*1024))

	// Начинаем аллоцировать порциями до срабатывания GC
	startGC := ms.NumGC
	var leak [][]byte

	for {
		leak = append(leak, make([]byte, 256*1024))
		runtime.ReadMemStats(&ms)
		if ms.NumGC > startGC {
			fmt.Printf(">>> Фоновый GC сработал на объеме кучи: %.2f МБ <<<\n",
				float64(ms.Alloc)/(1024*1024))
			break
		}
	}
	_ = persistentData
}
```

ℹ️ Фиксация фактического порога срабатывания триггера фонового GC

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run trigger_ratio.go
# В логе видно: цель 40 МБ, но запуск произошел на ~32-35 МБ
```

## Под капотом

В `src/runtime/mgcpacer.go` функция `trigger` рассчитывает динамический порог на основе сглаженного скользящего среднего времени разметки и скорости мутатора. Формула использует внутренний параметр `triggerRatio`, который варьируется от `minTriggerRatio` (обытельно 0.5 от GOGC) до `maxTriggerRatio` (0.95 от GOGC).

## Подводные камни

Если приложение выделяет память крупными блоками (например, `make([]byte, 64*1024*1024)` за один раз), триггер может быть пробит мгновенно, и сборщик мусора вынужден будет форсировать Mark Assist горутины прямо посреди системного вызова.

## На собеседовании

**Вопрос:** Почему при GOGC=100 сборка мусора запускается до того, как куча вырастет на 100%?
**Ответ:** Потому что фаза разметки конкурентна и требует времени. Если начать разметку на отметке +100%, то за время разметки аллокации мутатора увеличат размер кучи до +150% или +200%. Чтобы финишировать строго на отметке +100% (HeapGoal), пейсер запускает GC с упреждением (на отметке ~+60-70%).
