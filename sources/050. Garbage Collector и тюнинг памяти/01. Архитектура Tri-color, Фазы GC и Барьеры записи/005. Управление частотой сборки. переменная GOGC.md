# Управление частотой сборки: переменная GOGC

## Условие

Установите GOGC=20 (агрессивный GC, больше CPU) и GOGC=200 (ленивый GC, больше памяти). Измерьте влияние на latency и throughput при активной генерации временных объектов.

### Исходная формулировка

**GOGC**: Установите `GOGC=20` (агрессивный GC, больше CPU) и `GOGC=200` (ленивый GC, больше памяти). Измерьте влияние на latency и throughput.

## Теория

Переменная окружения `GOGC` (Garbage Collector Target Percentage) — основной исторический механизм тюнинга сборщика мусора в Go.

* **GOGC=off (или -1):** Полностью отключает периодический автоматический запуск GC. Память выделяется непрерывно до вызова `runtime.GC()` вручную либо до исчерпания оперативной памяти ОС.
* **Малый GOGC (например, 20-50):** Сборщик запускается часто. Куча удерживается минимальной (экономия RAM), однако до 25% процессорного времени тратится на разметку, возрастает количество STW пауз и падает throughput сервиса.
* **Большой GOGC (например, 200-500):** Сборщик запускается редко. Процессор освобожден от разметки, пропускная способность сервиса максимальна, но потребление памяти вырастает в разы.

## Решение по шагам

1. Напишите тестовую функцию, аллоцирующую миллионы временных объектов.
2. Запустите замер времени выполнения и количества пауз при `GOGC=20`.
3. Запустите замер при `GOGC=100` и `GOGC=200`.
4. Сравните пропускную способность (кол-во операций в секунду) и число сборок.

## Код решения

**`gogc_bench.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func runWorkload(iterations int) (time.Duration, uint32) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	start := time.Now()
	for i := 0; i < iterations; i++ {
		// Создаем кратковременные объекты
		_ = make([]byte, 16*1024)
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m2)
	return elapsed, m2.NumGC - m1.NumGC
}

func main() {
	const iters = 200000

	targets := []int{20, 100, 300}
	fmt.Printf("%-10s | %-12s | %-10s\n", "GOGC", "Время", "Кол-во GC")
	fmt.Println("---------------------------------------")

	for _, g := range targets {
		debug.SetGCPercent(g)
		dur, numGC := runWorkload(iters)
		fmt.Printf("%-10d | %-12v | %-10d\n", g, dur, numGC)
	}

	debug.SetGCPercent(100)
}
```

ℹ️ Сравнение производительности и числа срабатываний GC при разных значениях GOGC

**`Терминал`**

```bash
go run gogc_bench.go
# GOGC=20: время максимальное, количество GC максимальное (экономия RAM)
# GOGC=300: время минимальное, количество GC минимальное (высокий расход RAM)
```

## Под капотом

При вызове `debug.SetGCPercent` рантайм атомарно обновляет переменную `gcpercent` и немедленно вызывает `gcSetTriggerRatio` в `mgcpacer.go`. Если текущий размер кучи уже превышает новый уменьшенный `HeapGoal`, рантайм тут же запускает внеочередную сборку мусора.

## Подводные камни

Установка `GOGC=off` без ограничения памяти гарантированно приводит к аварийному завершению процесса ядром Linux через OOM Killer. В микросервисной архитектуре при скачках трафика тюнинг только через GOGC опасен.

## На собеседовании

**Вопрос:** В микросервисе с лимитом контейнера 2 ГБ наблюдаются частые OOM при дефолтном GOGC=100. Поможет ли уменьшение GOGC до 50?
**Ответ:** Уменьшение GOGC до 50 снизит пиковый размер кучи, но увеличит потребление CPU на 15-20% и может привести к деградации latency. Начиная с Go 1.19 лучшим решением является сохранение GOGC=100 и задание мягкого лимита `GOMEMLIMIT=1800MiB`, что защищает от OOM без постоянных накладных расходов на CPU при нормальной нагрузке.
