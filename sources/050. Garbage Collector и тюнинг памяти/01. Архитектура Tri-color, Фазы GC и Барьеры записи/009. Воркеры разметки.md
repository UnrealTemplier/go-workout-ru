# Воркеры разметки: Dedicated, Fractional и Idle Mark Workers

## Условие

Runtime запускает специальные фоновые горутины для concurrent marking. Изучите три типа маркер-воркеров: Dedicated, Fractional и Idle. Напишите код, демонстрирующий загрузку CPU при разметке.

### Исходная формулировка

**Mark workers**: Runtime запускает dedicated goroutines для concurrent marking. Изучите, как они балансируют работу.

## Теория

Для соблюдения баланса между производительностью пользовательского кода и скоростью разметки, рантайм Go бронирует **ровно 25% CPU** на сборку мусора во время активной фазы Marking.

Управление распределением осуществляет планировщик через три типа воркеров (`gcMarkWorkerMode`):
1. **Dedicated Worker (выделенный):** Занимает логический процессор P целиком. Горутина работает непрерывно, не вытесняясь пользовательскими задачами, пока не закончится фаза разметки. Количество P, отданных под dedicated воркеры, равно \(\lfloor GOMAXPROCS \times 0.25 \rfloor\).
2. **Fractional Worker (дробный):** Если \(GOMAXPROCS\) не делится на 4 нацело (например, 2 или 6 ядер), один P периодически отдает небольшую долю своего времени (дробный остаток от 25%), чтобы суммарный бюджет GC по всем P составил в точности 25.0%.
3. **Idle Worker (фоновый при простое):** Если у какого-то процессора P нет готовых к выполнению пользовательских горутин в очереди `runq`, вместо засыпания P переключается на помощь разметчикам GC, забирая серые объекты из глобальной очереди.

## Решение по шагам

1. Запустите программу с заданным числом `GOMAXPROCS=4`.
2. Вызовите интенсивную генерацию данных в куче.
3. Проанализируйте `GODEBUG=gctrace=1`: найдите колонку загрузки CPU `clock vs cpu`.
4. Обратите внимание на то, что на 4 ядрах ровно 1 ядро отдается dedicated-воркеру.

## Код решения

**`workers.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	// Фиксируем 4 ядра: 1 ядро (25%) будет Dedicated Mark Worker
	cores := 4
	runtime.GOMAXPROCS(cores)

	fmt.Printf("GOMAXPROCS = %d\n", runtime.GOMAXPROCS(0))
	fmt.Printf("Выделенный бюджет GC CPU: 25%% (ровно %d ядро Dedicated)\n", cores/4)

	done := make(chan bool)

	// Запускаем фоновую генерацию объектов
	go func() {
		for i := 0; i < 300000; i++ {
			_ = make([]byte, 8192)
		}
		done <- true
	}()

	select {
	case <-done:
		fmt.Println("Нагрузка успешно выполнена")
	case <-time.After(3 * time.Second):
		fmt.Println("Таймаут")
	}
}
```

ℹ️ Распределение ядер под фоновые горутины-маркеры

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run workers.go
# Обратите внимание на вывод: 4 P, загрузка процессора строго ~25%
```

## Под капотом

В `src/runtime/mgc.go` функция `gcBgMarkStartWorkers` создает \(GOMAXPROCS\) фоновых горутин `gcBgMarkWorker`. В начале каждого цикла разметки функция `gcController.findRunnableGCWorker(pp)` решает, в каком режиме запускать воркера на данном P: `gcMarkWorkerDedicatedMode`, `gcMarkWorkerFractionalMode` или `gcMarkWorkerIdleMode`.

## Подводные камни

В одноядерных контейнерах (`GOMAXPROCS=1`) Go не может запустить Dedicated воркер, так как это заблокировало бы мутатор на 100%. В этом случае рантайм использует исключительно Fractional Worker, который периодически уступает CPU приложению.

## На собеседовании

**Вопрос:** Какую долю ресурсов CPU сборщик мусора Go выделяет на concurrent marking и как распределяются роли между ядрами?
**Ответ:** Выделяется ровно 25% CPU. Для распределения используются три типа воркеров: Dedicated (занимает ядро на 100% времени разметки), Fractional (добирает дробный остаток до 25% на одном из ядер) и Idle (использует свободные ядра, когда в runq нет готовых пользовательских горутин).
