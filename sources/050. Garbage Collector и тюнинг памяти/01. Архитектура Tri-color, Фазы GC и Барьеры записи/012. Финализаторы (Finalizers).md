# Финализаторы (Finalizers): runtime.SetFinalizer и их риски

## Условие

Используйте runtime.SetFinalizer() для регистрации функций, вызываемых перед удалением объекта. Изучите, почему finalizers считаются антипаттерном (непредсказуемое время вызова, задержка освобождения, воскрешение объектов).

### Исходная формулировка

**Finalizers**: Используйте `runtime.SetFinalizer()` для регистрации функций, вызываемых перед удалением объекта. Изучите, почему finalizers — это anti-pattern (непредсказуемое время вызова, могут resurrect объекты).

## Теория

Функция `runtime.SetFinalizer(obj, finalizerFunc)` позволяет зарегистрировать функцию-обработчик, которая будет выполнена перед тем, как сборщик мусора физически освободит память объекта `obj`.

Почему финализаторы в Go — это **опасный антипаттерн**:
1. **Задержка освобождения минимум на 1 цикл GC:** Когда объект становится недостижимым, GC находит для него финализатор, переводит объект в специальную очередь `runfinq` и **воскрешает его на текущем цикле**. Память объекта освободится только на *следующем* цикле GC после выполнения финализатора!
2. **Непредсказуемость времени запуска:** Рантайм Go не дает никаких гарантий, когда именно вызовется финализатор. Если программа завершается через `os.Exit(0)` или `main()` заканчивает работу, финализаторы могут не выполниться вовсе.
3. **Блокировка очереди финализаторов:** Все финализаторы выполняются в **одной-единственной специальной горутине** рантайма. Если один финализатор зависнет или заблокируется на сокете/мьютексе, вся очередь финализаторов приложения встанет намертво.
4. **Утечки при циклических ссылках:** Если объекты с финализаторами имеют циклические ссылки друг на друга, рантайм Go не сможет определить порядок их вызова и никогда не освободит память!

## Решение по шагам

1. Создайте структуру `Resource`, имитирующую внешний дескриптор.
2. Прикрепите финализатор через `runtime.SetFinalizer`.
3. Сбросьте ссылку на объект и вызовите `runtime.GC()`.
4. Обратите внимание, что для выполнения финализатора требуется дать время горутине финализации.

## Код решения

**`finalizer.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type FileHandle struct {
	Descriptor int
}

func main() {
	fmt.Println("=== Демонстрация runtime.SetFinalizer ===")

	// Создаем объект в отдельной функции, чтобы он гарантированно побежал из стека
	allocateResource()

	fmt.Println("Вызываем первый runtime.GC() (обнаружение и перевод в finq)...")
	runtime.GC()

	// Даем время горутине финализации отработать
	time.Sleep(100 * time.Millisecond)

	fmt.Println("Вызываем второй runtime.GC() (окончательное удаление памяти)...")
	runtime.GC()

	time.Sleep(50 * time.Millisecond)
	fmt.Println("Завершение программы.")
}

func allocateResource() {
	h := &FileHandle{Descriptor: 42}
	runtime.SetFinalizer(h, func(handle *FileHandle) {
		fmt.Printf(">>> Финализатор сработал для дескриптора %d <<<\n", handle.Descriptor)
	})
}
```

ℹ️ Регистрация и выполнение финализатора объекта в отдельной горутине

## Под капотом

В `src/runtime/mfinal.go` при регистрации финализатора создается структура `specialfinalizer`, которая прикрепляется к спану объекта. Когда маркер обнаруживает недостижимый объект со специальным флагом, он переносит его в список серых (воскрешая) и добавляет в `finq`. Горутина `runfinq` вычитывает элементы из очереди и вызывает функцию через рефлексивный вызов `reflectcall`.

## Подводные камни

Никогда не используйте `runtime.SetFinalizer` для закрытия сетевых соединений или транзакций БД! Для закрытия ресурсов в Go единственно правильным и идиоматичным подходом является явный метод `Close()` с конструкцией `defer resource.Close()`.

## На собеседовании

**Вопрос:** Почему не рекомендуется использовать runtime.SetFinalizer для освобождения системных ресурсов (дескрипторов файлов, соединений)?
**Ответ:** Финализаторы гарантированно задерживают освобождение памяти минимум на один дополнительный цикл GC, выполняются в единственной системной горутине (риск блокировки всех финализаторов), могут вообще не успеть выполниться до завершения программы и не гарантируют порядок вызова при взаимных ссылках. Правильный подход — шаблон `io.Closer` + `defer`.
