# Трехцветная разметка (Tri-color Marking)

## Условие

Изучите алгоритм трехцветной разметки: White (кандидаты на удаление), Grey (в процессе обхода), Black (обработанные). Напишите симулятор трехцветного автомата на Go, иллюстрирующий переход объектов между состояниями.

### Исходная формулировка

**Tri-color marking**: Изучите алгоритм: White (кандидаты на удаление), Grey (в процессе обхода), Black (обработанные). Поймите, как это обеспечивает корректность при concurrent marking.

## Теория

Конкурентный сборщик мусора Go концептуально делит все объекты в куче на три цвета:

1. **Белые (White):** Кандидаты на удаление. В начале фазы разметки абсолютно все объекты считаются белыми. Те объекты, которые останутся белыми к моменту завершения разметки, признаются мусором и подлежат утилизации.
2. **Серые (Grey):** Объекты, достижимость которых доказана (на них ведет указатель из корня или черного объекта), но чьи собственные исходящие ссылки еще не были исследованы. Серые объекты образуют рабочую очередь сборщика (worklist).
3. **Черные (Black):** Объекты, которые гарантированно живы, и все их исходящие указатели уже исследованы и добавлены в серую очередь. Черный объект никогда не может напрямую указывать на белый объект без посредничества серого (Strong Tri-color Invariant).

## Решение по шагам

1. Создайте структуру `Object` с полями ID, ссылками на детей и цветом (White, Grey, Black).
2. Реализуйте алгоритм инициализации: корень помечается как Grey, остальные — White.
3. В цикле извлекайте серый объект, исследуйте его детей (переводя их из White в Grey), после чего красьте сам объект в Black.
4. Выведите финальное разделение: Black — живые, оставшиеся White — мусор.

## Код решения

**`tricolor.go`**

```go
package main

import "fmt"

type Color int

const (
	White Color = iota // Кандидат на удаление
	Grey               // В очереди на сканирование
	Black              // Просканирован и сохранен
)

func (c Color) String() string {
	return [...]string{"White", "Grey", "Black"}[c]
}

type Node struct {
	ID    string
	Color Color
	Edges []*Node
}

func main() {
	// Создаем граф памяти: Root -> A -> B; C (мусор)
	root := &Node{ID: "Root", Color: White}
	nodeA := &Node{ID: "A", Color: White}
	nodeB := &Node{ID: "B", Color: White}
	nodeC := &Node{ID: "C", Color: White} // изолированный объект

	root.Edges = append(root.Edges, nodeA)
	nodeA.Edges = append(nodeA.Edges, nodeB)

	allObjects := []*Node{root, nodeA, nodeB, nodeC}

	// 1. Корневое сканирование (GC Root Scan)
	root.Color = Grey
	greyQueue := []*Node{root}

	fmt.Println("=== Старт трехцветной разметки ===")

	// 2. Итеративный обход серой очереди
	for len(greyQueue) > 0 {
		curr := greyQueue[0]
		greyQueue = greyQueue[1:]

		fmt.Printf("Сканируем серый объект %s...\n", curr.ID)
		for _, child := range curr.Edges {
			if child.Color == White {
				child.Color = Grey
				greyQueue = append(greyQueue, child)
				fmt.Printf("  -> Найден белый потомок %s, перекрашен в Grey\n", child.ID)
			}
		}
		curr.Color = Black
		fmt.Printf("Объект %s перекрашен в Black\n", curr.ID)
	}

	// 3. Фаза Sweeping: удаление оставшихся белых
	fmt.Println("\n=== Результат разметки ===")
	for _, obj := range allObjects {
		if obj.Color == Black {
			fmt.Printf("Живой объект: %s (%s)\n", obj.ID, obj.Color)
		} else {
			fmt.Printf("Мусор подлежит удалению: %s (%s)\n", obj.ID, obj.Color)
		}
	}
}
```

ℹ️ Программная модель трехцветного инварианта сборщика мусора

## Под капотом

В реальном рантайме Go цвета не хранятся строкой в структуре. Черный/белый цвет кодируется в битовой карте `gcmarkBits` каждого спана (`mspan`). Если бит равен 1 — объект черный. Серый цвет означает, что объект занесен в рабочий буфер горутины-маркера (`gcWork.wbuf1`) или глобальную очередь разметки (`work.full`). Белый объект имеет бит 0 в `gcmarkBits` и отсутствует в буферах серых объектов.

## Подводные камни

Если во время конкурентной разметки мутатор (пользовательский код) перепишет ссылку так, что черный объект укажет на белый, а серый потеряет на него ссылку, алгоритм наивной разметки без Write Barrier удалит живой объект. Нарушение триколорного инварианта фатально для целостности памяти.

## На собеседовании

**Вопрос:** Что такое сильный (Strong) и слабый (Weak) трехцветный инвариант в GC?
**Ответ:** Сильный инвариант (Strong Tri-color Invariant) запрещает черным объектам ссылаться на белые напрямую. Слабый инвариант (Weak Tri-color Invariant) допускает ссылку из черного в белый, но только при условии, что существует защищающая цепочка ссылок от какого-либо серого объекта к этому белому. Go использует гибридный барьер записи, гарантирующий соблюдение триколорного инварианта.
