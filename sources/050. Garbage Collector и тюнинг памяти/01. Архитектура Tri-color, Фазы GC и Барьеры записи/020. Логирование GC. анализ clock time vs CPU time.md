# Логирование GC: анализ clock time vs CPU time

## Условие

Запустите программу с GODEBUG=gctrace=1 и разберите вывод: gc 1 @0.015s 0%: 0.015+0.30+0.045 ms clock, 0.060+0.15/0.25/0.40+0.18 ms cpu. Объясните, почему CPU time больше, чем clock time.

### Исходная формулировка

**GC traces**: Запустите программу с `GODEBUG=gctrace=1` и расшифруйте вывод:
```
gc 1 @0.015s 0%: 0.015+0.30+0.045 ms clock, 0.12+0.15/0.45/0.15+0.36 ms cpu, 4->4->0 MB, 5 MB goal, 8 P
```

## Теория

При анализе вывода `GODEBUG=gctrace=1` ключевой момент для инженера — понимание разницы между **Clock Time** и **CPU Time**.

1. **Clock Time (Астрономическое время, Wall-clock):**
   Это реальное физическое время, которое прошло на настенных часах от начала до конца фазы.
   `0.015 + 0.30 + 0.045 ms clock` означает:
   * Mark Setup STW: 15 микросекунд.
   * Concurrent Marking: 300 микросекунд.
   * Mark Termination STW: 45 микросекунд.
   * Общее время выполнения цикла: \(0.36\text{ мс}\).

2. **CPU Time (Процессорное время по всем ядрам):**
   Это суммарное время, затраченное всеми ядрами процессора на эту работу.
   Если на 4 ядрах разметка шла 0.30 мс, и на ней работало несколько воркеров, суммарное время CPU будет больше \(0.30\text{ мс}\)!
   `0.060 + 0.15/0.25/0.40 + 0.18 ms cpu`:
   * \(0.15\text{ ms}\) — время горутин в Mark Assist.
   * \(0.25\text{ ms}\) — время выделенных Dedicated/Fractional фоновых воркеров.
   * \(0.40\text{ ms}\) — время помощи от простаивающих ядер (Idle Workers).

## Решение по шагам

1. Напишите код, нагружающий память в многопоточном режиме (`runtime.GOMAXPROCS(4)`).
2. Запустите с `GODEBUG=gctrace=1`.
3. Сопоставьте числа clock time и cpu time в терминале.
4. Убедитесь, что `cpu time > clock time` из-за параллелизма ядер.

## Код решения

**`clock_vs_cpu.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	runtime.GOMAXPROCS(4)
	fmt.Println("Запуск 4 параллельных горутин аллокации...")

	var wg sync.WaitGroup
	for i := 0; i < 4; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 50000; j++ {
				_ = make([]byte, 2048)
			}
		}()
	}

	wg.Wait()
	runtime.GC()
	fmt.Println("Работа завершена. Проверьте вывод gctrace в терминале.")
}
```

ℹ️ Параллельные аллокации для демонстрации различий clock и cpu time

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run clock_vs_cpu.go
# Наблюдайте: clock time ~0.3ms, cpu time ~0.8ms из-за работы на нескольких ядрах
```

## Под капотом

В `src/runtime/mgc.go` рантайм использует функции `nanotime()` для замера wall-clock времени и счетчики циклов `m.mcache.tinyAllocs` и `gcController.assistTime` для учета процессорного времени. В многопроцессорных системах CPU time масштабируется пропорционально числу задействованных потоков M.

## Подводные камни

Ошибка интерпретации: если инженер видит `cpu time = 10ms` при `clock time = 2.5ms`, он может ошибочно подумать, что сервис остановился на 10 мс. На самом деле сервис был остановлен только на доли clock time, а 10 мс CPU были распределены по параллельным ядрам.

## На собеседовании

**Вопрос:** Почему в строке gctrace процессорное время (CPU time) часто значительно превышает астрономическое (Clock time)?
**Ответ:** Потому что разметка выполняется конкурентно на нескольких ядрах процессора одновременно. CPU time суммирует кванты времени, потраченные всеми физическими ядрами/потоками (dedicated workers, mark assist, idle workers). Если 4 ядра работали параллельно 1 мс, Clock time составит 1 мс, а CPU time — до 4 мс.
