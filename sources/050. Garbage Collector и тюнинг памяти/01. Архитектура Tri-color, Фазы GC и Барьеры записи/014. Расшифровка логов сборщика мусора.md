# Расшифровка логов сборщика мусора: флаг GODEBUG=gctrace=1

## Условие

Запустите программу с интенсивной аллокацией с флагом GODEBUG=gctrace=1. Расшифруйте каждую секцию строки вывода: gc 1 @0.045s 2%: 0.013+0.36+0.022 ms clock, 0.10+0.17/0.30/0.65+0.18 ms cpu, 4->4->2 MB, 5 MB goal, 0 MB stacks, 0 MB globals, 4 P.

### Исходная формулировка

**[GC Trace]**: Запусти программу с интенсивной аллокацией с флагом `GODEBUG=gctrace=1`. Расшифруй строку вывода: `gc 1 @0.045s 2%: 0.013+0.36+0.022 ms clock, 0.10+0.17/0.30/0.65+0.18 ms cpu, 4->4->2 MB, 5 MB goal, 0 MB stacks, 0 MB globals, 4 P`.

## Теория

Флаг рантайма `GODEBUG=gctrace=1` — самый быстрый и информативный способ диагностировать поведение сборщика мусора Go в терминале без подключения внешних профилировщиков.

Разбор каноничной строки вывода:
`gc 1 @0.045s 2%: 0.013+0.36+0.022 ms clock, 0.10+0.17/0.30/0.65+0.18 ms cpu, 4->4->2 MB, 5 MB goal, 0 MB stacks, 0 MB globals, 4 P`

1. **`gc 1`**: Порядковый номер цикла сборки мусора с момента запуска процесса.
2. **`@0.045s`**: Прошедшее время со старта программы в секундах до начала этой сборки.
3. **`2%`**: Процент совокупного времени CPU, затраченного на все фазы GC с момента старта процесса.
4. **`0.013+0.36+0.022 ms clock` (Wall clock):**
   * `0.013 ms` — длительность паузы Mark Setup (STW).
   * `0.36 ms` — длительность конкурентной разметки (Concurrent Marking).
   * `0.022 ms` — длительность паузы Mark Termination (STW).
5. **`0.10+0.17/0.30/0.65+0.18 ms cpu` (CPU time по всем ядрам):**
   * `0.10 ms` — CPU время фазы Mark Setup.
   * `0.17/0.30/0.65 ms` — время разметки: `assist time` / `background dedicated/fractional time` / `idle worker time`.
   * `0.18 ms` — CPU время фазы Mark Termination.
6. **`4->4->2 MB`:**
   * `4 MB` — размер кучи перед началом сборки.
   * `4 MB` — размер кучи в момент окончания разметки.
   * `2 MB` — размер кучи после завершения очистки (фактически живые данные, Live Heap).
7. **`5 MB goal`**: Целевой размер кучи (`HeapGoal`), рассчитанный пейсером для следующей сборки.
8. **`4 P`**: Количество логических процессоров (GOMAXPROCS), задействованных рантаймом.

## Решение по шагам

1. Напишите код, аллоцирующий несколько десятков мегабайт данных.
2. Запустите программу в терминале с переменной `GODEBUG=gctrace=1`.
3. Сопоставьте вывод в консоли с теоретической схемой расшифровки.

## Код решения

**`gctrace_demo.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("=== Запуск аллокаций для генерации логов gctrace ===")

	// Аллоцируем память порциями по 2 МБ, чтобы инициировать несколько циклов GC
	for i := 0; i < 5; i++ {
		buf := make([]byte, 8*1024*1024)
		_ = buf
		runtime.GC()
	}

	fmt.Println("Аллокации завершены.")
}
```

ℹ️ Программа для генерации реального вывода gctrace

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run gctrace_demo.go
# Вывод: gc 1 @0.012s 1%: 0.025+0.41+0.030 ms clock, ...
```

## Под капотом

Форматирование строки `gctrace` реализовано в `src/runtime/mgc.go` внутри функции `gcPrintCommit`. Вывод направляется напрямую в файловый дескриптор 2 (`stderr`) через системный вызов `write`, минуя буферизацию стандартного пакета `fmt`, что гарантирует доставку лога даже при крахе рантайма.

## Подводные камни

Включение `GODEBUG=gctrace=1` в высоконагруженном проде с десятками тысяч сборок мусора в секунду может засорить логи и вызвать задержки из-за синхронного вывода в stderr. Используйте его для локальной отладки или кратковременного canary-анализа.

## На собеседовании

**Вопрос:** Что означают три числа вида 10->8->4 MB в строке лога GODEBUG=gctrace=1?
**Ответ:** Первое число (10 MB) — это размер кучи в момент запуска сборки. Второе число (8 MB) — размер кучи на момент завершения разметки (Marking). Третье число (4 MB) — размер оставшейся живой памяти после завершения сборки (Live Heap), от которого пейсер будет рассчитывать следующую цель NextGC.
