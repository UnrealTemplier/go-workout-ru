# Барьеры записи (Write Barriers): Hybrid Write Barrier

## Условие

Когда указатель модифицируется во время разметки, write barrier записывает это в buffer для последующей обработки GC. Изучите гибридный барьер записи (Dijkstra + Yuasa). Напишите код, объясняющий необходимость барьера записи при конкурентной работе мутатора.

### Исходная формулировка

**Write barriers**: Когда указатель модифицируется, write barrier записывает это в buffer для последующей обработки GC. Изучите hybrid write barrier (Dijkstra + Yuasa).

## Теория

Поскольку фаза Marking выполняется конкурентно с кодом приложения (мутатором), приложение может перемещать указатели в процессе работы сборщика.

Классическая проблема утери объекта:
1. Черный объект \(A\) (уже исследован GC) получает ссылку на белый объект \(C\).
2. Серый объект \(B\) (еще не исследован) теряет ссылку на белый объект \(C\).
3. Поскольку \(A\) черный, GC к нему не вернется. Поскольку \(B\) потерял ссылку, он не покрасит \(C\). В результате живой объект \(C\) останется белым и будет ошибочно уничтожен на фазе Sweep.

Чтобы предотвратить это, Go начиная с версии 1.8 использует **Hybrid Write Barrier** (объединение барьеров Дейкстры и Юасы):
* **Барьер Юасы (Yuasa, стирание):** Любой указатель `*slot`, который перезаписывается (теряется), если он белый — немедленно закрашивается в серый цвет.
* **Барьер Дейкстры (Dijkstra, вставка):** Любой новый указатель `ptr`, который записывается в ячейку кучи, закрашивается в серый цвет.

Главное преимущество Hybrid Write Barrier в Go: **стеки горутин не требуют барьера записи**! Все объекты на стеке при старте GC помечаются черными, и рантайму не требуется повторное сканирование стеков (STW Stack Rescan), что сократило STW паузы с 10–30 мс до <0.5 мс.

## Решение по шагам

1. Создайте модель операции перезаписи указателя `writePointer(slot **Node, newPtr *Node)`.
2. Реализуйте логику гибридного барьера: если барьер включен, старый объект окрашивается в серый, а новый также помечается серым.
3. Продемонстрируйте, как барьер предотвращает утерю объекта при изменении ссылок.

## Код решения

**`write_barrier.go`**

```go
package main

import "fmt"

type Object struct {
	Name  string
	Color string
}

var (
	gcMarkingActive = false
	greyList        []*Object
)

func markGrey(obj *Object) {
	if obj != nil && obj.Color == "White" {
		obj.Color = "Grey"
		greyList = append(greyList, obj)
		fmt.Printf("  [WriteBarrier] Объект '%s' перекрашен в Grey\n", obj.Name)
	}
}

// HybridWriteBarrier имитирует runtime.gcWriteBarrier
func writePointer(slot **Object, newPtr *Object) {
	if gcMarkingActive {
		oldPtr := *slot
		// Юаса: защита старого указателя
		if oldPtr != nil {
			markGrey(oldPtr)
		}
		// Дейкстра: защита нового указателя
		if newPtr != nil {
			markGrey(newPtr)
		}
	}
	*slot = newPtr
}

func main() {
	blackParent := &Object{Name: "BlackParent", Color: "Black"}
	whiteChild := &Object{Name: "WhiteChild", Color: "White"}

	var targetSlot *Object = nil

	fmt.Println("1. Включаем фазу разметки GC (включение Write Barrier)")
	gcMarkingActive = true

	fmt.Println("2. Мутатор выполняет присваивание: targetSlot = whiteChild")
	writePointer(&targetSlot, whiteChild)

	fmt.Printf("3. Состояние WhiteChild: %s (защищен от сборки)\n", whiteChild.Color)
	fmt.Printf("4. В очереди разметки объектов: %d\n", len(greyList))
	_ = blackParent
}
```

ℹ️ Имитация логики гибридного барьера записи рантайма Go

## Под капотом

Компилятор Go при генерации SSA проверяет флаг `runtime.writeBarrier.enabled`. Если барьер активен, вместо простой инструкции `MOVQ BX, (AX)` генерируется вызов функции `runtime.gcWriteBarrier`. Чтобы минимизировать накладные расходы на вызовы функций, Go использует специальный буфер горутины `wbBuf`, куда указатели сбрасываются пакетами по 256 элементов (wbBuf.next), а затем переносятся в `gcWork`.

## Подводные камни

Поскольку Write Barrier добавляет ветвление и инструкции сохранения указателей на каждую мутацию в куче, интенсивные обновления полей структур в критических циклах вызывают просадку пропускной способности CPU на 5–15% во время фазы Marking. Обновления на стеке барьером не защищаются.

## На собеседовании

**Вопрос:** Почему Go перешел на гибридный барьер записи (Hybrid Write Barrier) в Go 1.8?
**Ответ:** До Go 1.8 использовался барьер записи Дейкстры. Он требовал в фазе Mark Termination повторно останавливать весь мир (STW) и полностью пересканировать стеки всех горутин (Stack Rescan), так как мутации на стеке происходили без барьера. Гибридный барьер закрашивает объекты в момент удаления ссылки и в момент добавления, что позволило полностью избавиться от rescan стеков и сократило STW до субмиллисекундных величин.
