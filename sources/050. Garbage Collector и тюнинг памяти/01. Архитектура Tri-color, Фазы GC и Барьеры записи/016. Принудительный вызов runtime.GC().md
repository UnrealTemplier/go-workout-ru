# Принудительный вызов runtime.GC(): применение и последствия

## Условие

Вызовите runtime.GC() для принудительного запуска сборщика мусора. Изучите, в каких редких случаях это оправдано (например, после разовой тяжелой инициализации) и почему постоянный вызов runtime.GC() в продакшене вреден.

### Исходная формулировка

**Forcing GC**: Вызовите `runtime.GC()` для принудительного запуска сборщика. Изучите, когда это полезно (например, после загрузки больших данных).

## Теория

Функция `runtime.GC()` выполняет **полный блокирующий цикл сборки мусора**:
1. Она немедленно запускает фазу Mark Setup (STW).
2. Выполняет разметку всей кучи до конца (горутина, вызвавшая `runtime.GC()`, активно участвует в разметке).
3. Проводит Mark Termination (STW).
4. Выполняет блокирующую фазу очистки (Sweeping) всех оставшихся спанов кучи.
5. Горутина блокируется до полного завершения всех этапов.

Когда вызов `runtime.GC()` оправдан:
* **После масштабной инициализации приложения:** Сервер прочитал из базы/диска кэш на 2 ГБ, построил компактные индексные структуры, а исходные промежуточные JSON/массивы стали мусором. Единовременный вызов `runtime.GC()` сразу сбросит `NextGC` и вернет неиспользуемые спаны.
* **В нагрузочных тестах и бенчмарках:** Перед началом замера для очистки состояния памяти (`b.ResetTimer()`).

Почему в штатной работе это антипаттерн:
* Ломает сбалансированную работу адаптивного пейсера `mgcpacer.go`.
* Приводит к неоправданному расходу CPU и принудительному STW.

## Решение по шагам

1. Создайте большой временный срез данных, имитирующий загрузку конфигурации.
2. Прочитайте `Alloc` до и после зануления ссылки.
3. Вызовите `runtime.GC()` и замерьте время блокировки вызывающей горутины.
4. Проверьте обновленные метрики `Alloc` и `NextGC`.

## Код решения

**`force_gc.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func initHeavyCache() {
	// Временные данные инициализации (50 МБ)
	tempData := make([][]byte, 50)
	for i := range tempData {
		tempData[i] = make([]byte, 1024*1024)
	}
	// Имитируем парсинг и сохранение только 1 МБ результата
	_ = tempData
}

func main() {
	var m1, m2, m3 runtime.MemStats

	runtime.ReadMemStats(&m1)
	fmt.Printf("До инициализации: Alloc = %d КБ\n", m1.Alloc/1024)

	initHeavyCache()
	runtime.ReadMemStats(&m2)
	fmt.Printf("После создания тяжелых объектов: Alloc = %d КБ, NextGC = %d КБ\n",
		m2.Alloc/1024, m2.NextGC/1024)

	fmt.Println("Выполняем принудительный runtime.GC()...")
	start := time.Now()
	runtime.GC()
	elapsed := time.Since(start)

	runtime.ReadMemStats(&m3)
	fmt.Printf("После runtime.GC(): Alloc = %d КБ, NextGC = %d КБ (заняло %v)\n",
		m3.Alloc/1024, m3.NextGC/1024, elapsed)
}
```

ℹ️ Осознанное использование принудительного вызова runtime.GC() после тяжелого startup

## Под капотом

В `src/runtime/mgc.go` функция `GC()` передает признак `gcTriggerCycle` в `gcStart`. Если предыдущий фоновый sweep еще не завершился, вызывающая горутина будет принудительно заблокирована и вызовет `sweepone()` до тех пор, пока вся куча не станет чистой.

## Подводные камни

Вызов `runtime.GC()` внутри HTTP-хендлеров под нагрузкой — катастрофическая ошибка. Если 500 параллельных запросов вызовут `runtime.GC()`, рантайм выстроит их в очередь, процессор будет загружен на 100% разметкой, а задержки сервиса улетят в секунды.

## На собеседовании

**Вопрос:** Чем отличается фоновый запуск GC по триггеру от вызова runtime.GC()?
**Ответ:** Фоновый запуск инициируется пейсером конкурентно: фаза sweep выполняется лениво по требованию аллокатора, горутины продолжают работу. Вызов runtime.GC() синхронно блокирует вызывающую горутину на все время разметки, а также форсирует синхронную очистку абсолютно всех спанов кучи перед возвратом.
