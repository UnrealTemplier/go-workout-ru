# Программная установка лимита памяти через debug.SetMemoryLimit

## Условие

Установите GOMEMLIMIT программно через debug.SetMemoryLimit(1 << 30) (1GB). Напишите модуль автоматической инициализации лимита памяти на основе чтения cgroup quota внутри Docker-контейнера.

### Исходная формулировка

**Debug.SetMemoryLimit**: Установите `GOMEMLIMIT` программно через `debug.SetMemoryLimit(1 << 30)` (1GB).

## Теория

Функция `runtime/debug.SetMemoryLimit(limit int64) int64` позволяет динамически считывать и изменять значение `GOMEMLIMIT` прямо во время выполнения программы.

* Если передать отрицательное значение (`-1`), функция возвращает текущее установленное значение лимита без изменений.
* Значение `math.MaxInt64` означает, что лимит отключен (поведение по умолчанию).

В микросервисной архитектуре это критически важно: когда контейнер запускается в Kubernetes с лимитом памяти (например, `resources.limits.memory: 1Gi`), приложение на Go может автоматически прочитать лимит из `/sys/fs/cgroup/memory.max` (cgroup v2) или `/sys/fs/cgroup/memory/memory.limit_in_bytes` (cgroup v1) и задать `debug.SetMemoryLimit(cgroupLimit * 0.85)`.

## Решение по шагам

1. Получите текущий установленный лимит с помощью `debug.SetMemoryLimit(-1)`.
2. Задайте новый лимит 512 МБ (`512 << 20`).
3. Убедитесь, что функция возвращает старое значение лимита.
4. Продемонстрируйте безопасное восстановление предыдущего лимита через `defer`.

## Код решения

**`set_memlimit.go`**

```go
package main

import (
	"fmt"
	"math"
	"runtime/debug"
)

// AutoConfigureMemoryLimit настраивает мягкий лимит кучи на 85% от доступного порога
func AutoConfigureMemoryLimit(containerLimitBytes int64) int64 {
	targetLimit := int64(float64(containerLimitBytes) * 0.85)
	old := debug.SetMemoryLimit(targetLimit)
	return old
}

func main() {
	// 1. Читаем текущий дефолтный лимит
	current := debug.SetMemoryLimit(-1)
	if current == math.MaxInt64 {
		fmt.Println("Текущий GOMEMLIMIT: Не ограничен (math.MaxInt64)")
	} else {
		fmt.Printf("Текущий GOMEMLIMIT: %d МБ\n", current/(1024*1024))
	}

	// 2. Имитируем запуск в Kubernetes Pod с лимитом 1 ГБ RAM
	containerMemory := int64(1 * 1024 * 1024 * 1024)
	oldLimit := AutoConfigureMemoryLimit(containerMemory)
	defer debug.SetMemoryLimit(oldLimit)

	newLimit := debug.SetMemoryLimit(-1)
	fmt.Printf("Установлен новый безопасный GOMEMLIMIT (85%%): %d МБ\n",
		newLimit/(1024*1024))
}
```

ℹ️ Программный расчет и применение GOMEMLIMIT через debug.SetMemoryLimit

## Под капотом

Внутри рантайма вызов `SetMemoryLimit` передает значение переменной `gcController.memoryLimit`. После этого немедленно вызывается пересчет целей пейсера `gcController.commit(nil)`. Если новый лимит меньше текущего размера кучи, немедленно пробуждается фоновый поток сборщика мусора.

## Подводные камни

Не устанавливайте лимит равным ровно 100% лимита cgroup! Процесс Go потребляет память не только в куче: стек горутин, бинарный образ, метаданные рантайма и системные буферы ОС могут занимать от 50 до 200 МБ. Превышение порога cgroup ядром Linux вызовет мгновенный kill по OOM.

## На собеседовании

**Вопрос:** Как правильно конфигурировать память Go-сервиса, развернутого в Kubernetes с лимитом 2Gi?
**Ответ:** Рекомендуемый стандарт BigTech: оставить GOGC=100, а GOMEMLIMIT задать равным ~80-90% от лимита контейнера (например, `GOMEMLIMIT=1800MiB`). Это позволяет сервису в спокойном режиме использовать быструю кучу без лишних затрат CPU, а при всплеске нагрузки пейсер вовремя сожмет кучу и спасет процесс от OOMKilled.
