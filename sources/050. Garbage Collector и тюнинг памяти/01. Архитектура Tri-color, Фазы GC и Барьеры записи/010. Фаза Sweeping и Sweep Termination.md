# Фаза Sweeping и Sweep Termination

## Условие

Изучите, как sweeping происходит в фоне и как runtime гарантирует, что память переиспользуется безопасно. Напишите код, демонстрирующий переиспользование памяти спанов без обращения к ядру ОС.

### Исходная формулировка

**Sweep termination**: Изучите, как sweeping происходит в фоне и как runtime гарантирует, что память переиспользуется безопасно.

## Теория

После завершения фазы разметки (Mark Termination) наступает фаза **Sweeping (Очистка)**.

В отличие от многих языков, Go **не очищает всю кучу сразу**:
1. **Zero-Pause Sweeping:** Очистка полностью конкурентна и выполняется параллельно работе приложения.
2. **Lazy / On-Demand Sweeping:** Спаны очищаются не заранее, а в момент, когда логическому процессору P требуется аллоцировать новый объект того же класса размера (`runtime.mcache.refill` -> `runtime.mcentral.cacheSpan`).
3. **Background Sweeper:** Фоновая горутина `bgsweep` медленно зачищает оставшиеся спаны в моменты простоя приложения.

**Sweep Termination:**
Перед тем как начать новый цикл GC (Mark Setup), рантайм обязан убедиться, что абсолютно все спаны предыдущего цикла были очищены. Если к моменту триггера нового GC какие-то спаны еще не очищены, вызывается функция `sweepone()`, принудительно дочищающая остатки.

## Решение по шагам

1. Создайте большое количество объектов и сбросьте на них ссылки.
2. Вызовите `runtime.GC()`, инициируя разметку.
3. Начните аллоцировать новые объекты того же размера и убедитесь, что `HeapSys` не растет, так как память берется из очищенных спанов.

## Код решения

**`sweeping.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m1, m2, m3 runtime.MemStats

	// 1. Первая волна аллокации (10 МБ)
	runtime.ReadMemStats(&m1)
	holders := make([][]byte, 1000)
	for i := range holders {
		holders[i] = make([]byte, 10240)
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("После 1-й волны: HeapAlloc = %d КБ, HeapSys = %d КБ\n",
		m2.HeapAlloc/1024, m2.HeapSys/1024)

	// Освобождаем ссылки и запускаем GC
	holders = nil
	runtime.GC()

	// 2. Вторая волна аллокации того же размера объектов
	holders2 := make([][]byte, 1000)
	for i := range holders2 {
		holders2[i] = make([]byte, 10240)
	}

	runtime.ReadMemStats(&m3)
	fmt.Printf("После 2-й волны: HeapAlloc = %d КБ, HeapSys = %d КБ\n",
		m3.HeapAlloc/1024, m3.HeapSys/1024)

	// HeapSys не должен увеличиться, спаны очищены и переиспользованы
	diffSys := int64(m3.HeapSys) - int64(m2.HeapSys)
	fmt.Printf("Прирост виртуальной памяти ОС (HeapSys diff): %d байт\n", diffSys)
}
```

ℹ️ Переиспользование памяти спанов в фазе ленивой очистки Sweeping

## Под капотом

В `src/runtime/mgcsweep.go` каждый спан (`mspan`) хранит поколение очистки `mspan.sweepgen`. Если `sweepgen == mheap_.sweepgen - 2`, спан нуждается в очистке. Функция `mspan.sweep()` сравнивает битовые карты `allocBits` и `gcmarkBits`. Те объекты, где `gcmarkBits == 0`, сбрасываются в `freeindex`, а `gcmarkBits` копируется в `allocBits` для следующего цикла.

## Подводные камни

Sweeping возвращает память не операционной системе, а во внутренние пулы `mcentral`. Физический возврат страниц ОС выполняется отдельным процессом Scavenger через системный вызов `madvise(MADV_DONTNEED)`, поэтому в htop RSS процесса не падает моментально.

## На собеседовании

**Вопрос:** Почему в Go фаза Sweeping не вызывает пауз приложения?
**Ответ:** Sweeping в Go является конкурентным и ленивым (Lazy Sweeping). Спаны не очищаются глобально за один проход. Очистка выполняется по требованию: когда горутине требуется память определенного класса размера, она берет неочищенный спан и очищает только его. Дополнительно в фоне работает горутина bgsweep.
