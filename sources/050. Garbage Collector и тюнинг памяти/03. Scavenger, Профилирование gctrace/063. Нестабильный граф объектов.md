# Нестабильный граф объектов: гарантии Hybrid Write Barrier

## Условие

Создайте ситуацию «нестабильного графа»: фоновые горутины непрерывно перестраивают связный список (меняют next). Объясните, почему алгоритм не зависает и не пропускает живые узлы.

### Исходная формулировка

Создайте ситуацию «нестабильного графа»: goroutine постоянно перестраивает связный список (меняет `next`). Объясните, почему без write barrier объект мог бы быть ошибочно освобождён (чёрный mutator пишет ссылку на белый объект).

## Теория

В динамическом приложении граф объектов непрерывно перестраивается прямо во время обхода сборщиком.

Как гибридный барьер записи гарантирует прогресс и завершение разметки:
1. **Сходимость:** Количество объектов в куче конечно. Каждый живой объект может быть покрашен в Черный цвет ровно один раз за цикл разметки.
2. **Защита от зацикливания:** Повторный обход черного объекта не производится (`gcmarkBits` уже равен 1).
3. **Защита от потери:** При переносе ссылки из серого узла в черный, старый указатель немедленно седеет (Юаса), а новый регистрируется (Дейкстра).
4. Очередь серых объектов гарантированно опустеет, поскольку новые объекты в куче во время разметки сразу аллоцируются черными.

## Решение по шагам

1. Создайте циклический список из 100 узлов.
2. Запустите две горутины, меняющие порядок узлов местами.
3. Запустите горутину, создающую новые узлы и вставляющую их в список.
4. Убедитесь, что `runtime.GC()` успешно завершается без бесконечных циклов.

## Код решения

**`unstable_graph.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

type GraphItem struct {
	Val  int
	Next *GraphItem
}

func main() {
	fmt.Println("=== Исследование сходимости GC на нестабильном графе ===")

	head := &GraphItem{Val: 0}
	curr := head
	for i := 1; i < 50; i++ {
		curr.Next = &GraphItem{Val: i}
		curr = curr.Next
	}

	var stop atomic.Bool

	// Горутина хаотичной перелинковки ссылок
	go func() {
		for !stop.Load() {
			if head.Next != nil && head.Next.Next != nil {
				// Переставляем узлы местами
				first := head.Next
				second := first.Next
				first.Next = second.Next
				second.Next = first
				head.Next = second
			}
		}
	}()

	// Выполняем серию циклов GC на нестабильном графе
	for i := 1; i <= 5; i++ {
		start := time.Now()
		runtime.GC()
		fmt.Printf("Цикл GC #%d успешно завершен за %v на активно мутирующем графе!\n",
			i, time.Since(start))
		time.Sleep(20 * time.Millisecond)
	}

	stop.Store(true)
	fmt.Println("Тест успешно пройден. Сборщик гарантирует детерминированное завершение.")
}
```

ℹ️ Успешная сходимость сборщика мусора на непрерывно изменяемом графе

## Под капотом

В `src/runtime/mgcmark.go` функция `gcDrain` проверяет условия выхода из разметки: локальные кэши `gcWork` пусты, глобальная очередь `work.full` пуста, и отсутствуют работающие потоки mark assist. Только когда все условия выполнены, рантайм переходит в `_GCmarktermination`.

## Подводные камни

Гонки данных (data races) в пользовательских указателях без атомиков или мьютексов могут повредить бизнес-логику приложения, даже если сам сборщик мусора останется целостным.

## На собеседовании

**Вопрос:** Может ли сборщик мусора Go зациклиться, если приложение непрерывно перелинковывает указатели во время фазы Marking?
**Ответ:** Нет, зацикливание математически невозможно. Алгоритм разметки монотонно переводит объекты из White в Black. Повторное сканирование уже помеченных черных объектов запрещено проверкой битовой карты gcmarkBits. Все новые объекты, создаваемые мутатором во время фазы Marking, сразу помечаются черными.
