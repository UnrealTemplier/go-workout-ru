# Тюнинг GC для Low-Latency сервисов (GOGC=20 + GOMEMLIMIT)

## Условие

Для latency-sensitive приложений с жесткими требованиями к SLA (p99 < 5ms) настройте связку GOGC=20 и GOMEMLIMIT для обеспечения частых, но ультракоротких пауз GC.

### Исходная формулировка

**GC tuning для low-latency**: Для latency-sensitive приложений используйте `GOGC=20` и `GOMEMLIMIT` для частых, но коротких GC pauses.

## Теория

В Low-Latency системах (микросервисы торгов, шлюзы авторизации платежей) цель тюнинга — **минимизировать вариативность задержек (Tail Latency)**:
* Если куча разрастается до 2 ГБ, фаза разметки длится дольше, а объемы серых очередей велики.
* Установка агрессивного `GOGC=20..30` удерживает кучу компактной: сборщик запускается часто, обрабатывая крошечные порции мусора.
* Чтобы при всплеске запросов сервис не ушел в OOM, устанавливается мягкий лимит `GOMEMLIMIT`.
* Результат: предсказуемое время отклика на уровне микросекунд без многомиллисекундных выбросов.

## Решение по шагам

1. Настройте `debug.SetGCPercent(20)`.
2. Задайте `debug.SetMemoryLimit(512 * 1024 * 1024)`.
3. Запустите имитацию потока запросов с замером p99 задержки.
4. Сравните стабильность времени отклика.

## Код решения

**`low_latency_tune.go`**

```go
package main

import (
	"fmt"
	"runtime/debug"
	"time"
)

func main() {
	// Тюнинг под Low-Latency: частый сборщик, жесткий контроль кучи
	oldGC := debug.SetGCPercent(20)
	oldLimit := debug.SetMemoryLimit(256 * 1024 * 1024)
	defer func() {
		debug.SetGCPercent(oldGC)
		debug.SetMemoryLimit(oldLimit)
	}()

	fmt.Println("=== Low-Latency GC Profile активирован ===")
	fmt.Println("  GOGC = 20 (агрессивная очистка мелких партий)")
	fmt.Println("  GOMEMLIMIT = 256 МБ (страховка от OOM)")

	// Имитируем поток 100 000 коротких запросов
	start := time.Now()
	for i := 0; i < 100000; i++ {
		reqData := make([]byte, 2048)
		_ = reqData
	}
	elapsed := time.Since(start)

	fmt.Printf("100 000 запросов обработаны за: %v\n", elapsed)
}
```

ℹ️ Конфигурация Low-Latency профиля для жестких SLA задержек

## Под капотом

При малом размере кучи граф объектов для обхода триколорным алгоритмом очень компактен. Воркеры успевают завершить разметку за доли миллисекунды, и вероятность того, что пользовательская горутина будет заблокирована в Mark Assist, стремится к нулю.

## Подводные камни

Низкий GOGC потребляет больше CPU на постоянные сборки мусора (до 20-25% от доступных ядер). Этот режим подходит только в случае, если запас по CPU достаточен, а приоритетом является стабильность p99.

## На собеседовании

**Вопрос:** Как снизить хвостовые задержки (p99/p999 latency) в Go сервисе без переписывания бизнес-логики?
**Ответ:** 1. Установить GOMEMLIMIT на 80-85% от лимита памяти контейнера; 2. Тюнинговать GOGC в зависимости от профиля: для Low-Latency можно уменьшить GOGC до 30-50, чтобы удерживать живую кучу маленькой и избегать затяжных фаз разметки; 3. Устранить аллокации в горячих путях через sync.Pool; 4. Использовать типы без указателей (noscan).
