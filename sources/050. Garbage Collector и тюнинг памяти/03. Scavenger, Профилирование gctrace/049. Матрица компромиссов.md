# Матрица компромиссов: замеры пропускной способности при GOGC=50..400

## Условие

Запустите программу с циклической аллокацией. Постройте сводную матрицу задержек, числа сборок и пикового потребления RAM при GOGC=50, 100, 200 и 400.

### Исходная формулировка

**GC Pacing и GOGC.**: Запустите программу, выделяющую память в цикле. Измерьте пропускную способность и задержки при `GOGC=50`, `100`, `200`, `off`. Найдите оптимальное значение для минимизации задержек.

## Теория

Закон убывающей отдачи (Diminishing Returns) в тюнинге `GOGC`:
* Переход от \(GOGC=50\) к \(GOGC=100\) дает огромный выигрыш по CPU при умеренном росте памяти.
* Переход от \(GOGC=100\) к \(GOGC=200\) дает заметный прирост скорости.
* Переход выше \(GOGC=400\) практически не дает ускорения, но требует экспоненциально больше оперативной памяти.

Оптимальная точка для большинства высоконагруженных веб-сервисов в продакшене находится в диапазоне `GOGC=100..150` в сочетании с `GOMEMLIMIT`.

## Решение по шагам

1. Создайте сценарий многократного замера для среза значений `[]int{50, 100, 200, 400}`.
2. Фиксируйте время работы, `NumGC` и пиковое значение `NextGC`.
3. Выведите форматированную таблицу результатов в терминал.

## Код решения

**`tradeoff_matrix.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func runWorkload(gogc int) (time.Duration, uint32, float64) {
	debug.SetGCPercent(gogc)
	runtime.GC()

	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)

	start := time.Now()
	for i := 0; i < 150000; i++ {
		_ = make([]byte, 1024)
	}
	elapsed := time.Since(start)

	runtime.ReadMemStats(&mEnd)
	return elapsed, mEnd.NumGC - mStart.NumGC, float64(mEnd.NextGC) / (1024 * 1024)
}

func main() {
	fmt.Println("=== Матрица компромиссов GOGC ===")
	fmt.Printf("%-8s | %-12s | %-10s | %-12s\n", "GOGC", "Время", "Сборок GC", "Пик NextGC")
	fmt.Println("--------------------------------------------------")

	for _, g := range []int{50, 100, 200, 400} {
		dur, numGC, peakMB := runWorkload(g)
		fmt.Printf("%-8d | %-12v | %-10d | %6.2f МБ\n", g, dur, numGC, peakMB)
	}

	debug.SetGCPercent(100)
}
```

ℹ️ Сравнительная матрица производительности при различных значениях GOGC

## Под капотом

Кривая эффективности GC описывается гиперболой: затраты CPU обратно пропорциональны доступной оперативной памяти. Когда куча может вырасти в 4 раза, большинство временных объектов успевает стать мусором до сканирования.

## Подводные камни

Не забывайте восстанавливать `debug.SetGCPercent(100)` в тестах, иначе измененное глобальное состояние рантайма повлияет на результаты последующих тестов пакета.

## На собеседовании

**Вопрос:** Как закон убывающей отдачи проявляется при тюнинге GOGC?
**Ответ:** Увеличение GOGC выше 200–300 дает все меньший прирост пропускной способности, поскольку оверхед GC уже снижен до минимальных единиц процентов, в то время как риск OOM из-за разрастания кучи возрастает линейно.
