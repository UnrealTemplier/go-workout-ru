# Тюнинг GC для High-Throughput пакетной обработки (GOGC=200..500)

## Условие

Для batch-processing и аналитических конвейеров настройте GOGC=200..500 для минимизации процессорных расходов на сборку мусора и максимизации пропускной способности.

### Исходная формулировка

**GC tuning для high-throughput**: Для batch-processing используйте `GOGC=200` для снижения CPU overhead от GC.

## Теория

В пакетной обработке данных (ETL, парсинг больших файлов, расчет аналитики) задержки p99 не имеют значения. Главная метрика — **Общее время завершения задачи (Throughput / Wall-clock completion)**.

При `GOGC=100` каждые 100 МБ аллокаций рантайм тратит 25% CPU на разметку.
Если на сервере свободно 32 ГБ RAM:
* Установка `GOGC=300` позволяет куче вырастать в 4 раза перед каждой сборкой.
* Количество циклов GC сокращается в 3-4 раза!
* Все 100% процессорных мощностей отдаются бизнес-логике обработки данных.
* Общее время выполнения пакетного джоба сокращается на 20-30%.

## Решение по шагам

1. Напишите пакетную функцию, обрабатывающую миллионы записей.
2. Замерьте время выполнения при дефолтном `GOGC=100`.
3. Замерьте время при `GOGC=300`.
4. Сравните экономию общего времени обработки.

## Код решения

**`batch_tuning.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func runBatchTask(records int) time.Duration {
	runtime.GC()
	start := time.Now()

	for i := 0; i < records; i++ {
		// Имитируем парсинг строки и формирование объекта
		row := fmt.Sprintf("record_%d_payload_data", i)
		_ = row
	}

	return time.Since(start)
}

func main() {
	const totalRecords = 2000000

	fmt.Println("=== Сравнение времени пакетной обработки ===")

	// 1. Дефолтный GOGC=100
	debug.SetGCPercent(100)
	dur100 := runBatchTask(totalRecords)
	var m1 runtime.MemStats
	runtime.ReadMemStats(&m1)
	fmt.Printf("GOGC=100: Время = %-10v | Сборок GC = %d\n", dur100, m1.NumGC)

	// 2. High-Throughput GOGC=300
	debug.SetGCPercent(300)
	dur300 := runBatchTask(totalRecords)
	var m2 runtime.MemStats
	runtime.ReadMemStats(&m2)
	fmt.Printf("GOGC=300: Время = %-10v | Сборок GC = %d\n", dur300, m2.NumGC-m1.NumGC)

	debug.SetGCPercent(100)
	gain := float64(dur100-dur300) / float64(dur100) * 100
	fmt.Printf("Увеличение пропускной способности: %.1f%%\n", gain)
}
```

ℹ️ Ускорение пакетных вычислений за счет повышения GOGC

## Под капотом

С увеличением интервала между сборками подавляющее большинство короткоживущих объектов успевает освободиться еще до старта разметки. Сборщик мусора запускается реже и находит существенно меньше живых данных.

## Подводные камни

Повышение GOGC без ограничения `GOMEMLIMIT` может привести к аварийному завершению процесса, если объем входных данных внезапно вырастет в несколько раз.

## На собеседовании

**Вопрос:** В каких задачах оправдана установка GOGC=300 и выше?
**Ответ:** В задачах пакетной обработки данных (Batch Processing, Data Pipelines, CLI-конвертеры, научные расчеты), где сервис работает на изолированном сервере с большим объемом оперативной памяти, а целью является максимизация скорости обработки (Throughput) ценой временного увеличения объема используемой памяти кучи.
