# Практический тюнинг GOGC в контейнеризированной среде

## Условие

Запустите программу с интенсивной аллокацией. Сделайте три серии замеров: при GOGC=50, 100 и 200. Оцените среднюю утилизацию CPU и потребление RAM под нагрузкой.

### Исходная формулировка

**Тюнинг GC через `GOGC`**: Запустите вашу программу с агрессивной аллокацией памяти. Сделайте три замера производительности и потребления оперативной памяти:
* С дефолтным параметром `GOGC=100` (сборщик запускается, когда размер кучи удваивается относительно размера после предыдущей сборки).
* С параметром `GOGC=50` (частый запуск GC, минимальный расход памяти, но высокая нагрузка на CPU).
* С параметром `GOGC=500` (редкий запуск GC, экономия CPU, но высокое потребление памяти).
Сделайте выводы в комментариях.

## Теория

В контейнеризированной инфраструктуре (Kubernetes Pods) ресурсы процессора (CPU Limits) и памяти (Memory Limits) жестко квотируются:
* Превышение лимита памяти ведет к `OOMKilled` (Exit Code 137).
* Превышение лимита CPU ведет к троттлингу (CPU CFS Throttling) и росту задержек.

Тюнинг GOGC позволяет идеально сбалансировать сервис:
* Если под троттлится по CPU, но имеет 2 ГБ свободной RAM -> повышаем `GOGC=150..200`.
* Если под приближается к лимиту памяти, но CPU загружен всего на 30% -> понижаем `GOGC=60..80`.

## Решение по шагам

1. Смоделируйте нагрузочный конвейер.
2. Проведите три серии испытаний с замером времени и памяти.
3. Составьте заключение о выборе оптимального параметра.

## Код решения

**`container_tune.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func simulateService(gogc int) {
	debug.SetGCPercent(gogc)
	runtime.GC()

	start := time.Now()
	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)

	// Нагрузка: 300 000 временных срезов
	for i := 0; i < 300000; i++ {
		_ = make([]byte, 512)
	}

	runtime.ReadMemStats(&mEnd)
	elapsed := time.Since(start)

	fmt.Printf("GOGC=%-3d -> Время: %-10v | Сборок: %-2d | Память NextGC: %5.1f МБ\n",
		gogc, elapsed, mEnd.NumGC-mStart.NumGC, float64(mEnd.NextGC)/(1024*1024))
}

func main() {
	fmt.Println("=== Исследование профиля ресурсов контейнера ===")
	simulateService(50)
	simulateService(100)
	simulateService(200)
	debug.SetGCPercent(100)
}
```

ℹ️ Анализ поведения сервиса при различных ограничениях ресурсов

## Под капотом

В ядре Linux планировщик CFS отслеживает использование процессорного времени через периоды квот (`cpu.cfs_quota_us`). Если горутины-маркеры GC сжигают квоту за первые 20 мс 100-миллисекундного окна, оставшиеся 80 мс сервис будет полностью заморожен ядром.

## Подводные камни

Никогда не выставляйте CPU Limit на уровне ровно 1 ядра (`1000m`) для Go сервисов с дефолтным GC, так как 25% CPU заберет GC, а оставшиеся горутины быстро исчерпают квоту и попадут под CFS throttling.

## На собеседовании

**Вопрос:** Как связаны CPU CFS Throttling в Kubernetes и Garbage Collector в Go?
**Ответ:** Когда сборщик мусора запускает фазу concurrent marking, он параллельно утилизирует до 25% процессорного бюджета. Если на контейнер наложен жесткий CPU limit, всплеск активности воркеров GC быстро сжигает доступную квоту CFS, и ядро Linux принудительно замораживает все потоки контейнера до конца периода квоты (обычно 100 мс), приводя к резкому росту задержек ответов сервиса.
