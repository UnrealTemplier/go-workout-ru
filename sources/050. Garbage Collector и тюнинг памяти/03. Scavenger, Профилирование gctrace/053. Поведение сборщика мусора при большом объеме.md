# Поведение сборщика мусора при большом объеме постоянных данных (Live Set)

## Условие

Создайте программу с большим объемом постоянных живых данных (100 МБ строк). Докажите, что при GOGC=100 следующий GC запускается только при достижении 200 МБ кучи.

### Исходная формулировка

Создайте программу с большим live set (100 MB строк). Покажите, что при `GOGC=100` следующий GC запускается при ~200 MB heap. Измените `GOGC=200` — покажите сдвиг порога. Нарисуйте график `HeapGoal` от `HeapLive`.

## Теория

**Live Set (Набор живых данных)** — объем памяти, который невозможно освободить, так как на него сохраняются ссылки (кэши в памяти, справочники, деревья роутинга).

Формула триггера GC привязывается строго к объему Live Set:
$$\text{NextGC} = \text{LiveSet} \times 2 \quad (\text{при } \text{GOGC}=100)$$

Если Live Set составляет 5 ГБ:
* Следующая сборка мусора запустится только на отметке **10 ГБ**!
* Это означает, что приложению требуется дополнительно 5 ГБ оперативной памяти только под временный мусор.
* Если памяти столько нет, сервис упадет по OOM.

## Решение по шагам

1. Создайте срез строк общим объемом 50 МБ и сохраните на него ссылку в глобальной переменной.
2. Вызовите `runtime.GC()` для фиксации базового размера.
3. Проверьте значение `ms.NextGC` — оно удвоит размер Live Set.
4. Добавьте порцию временных аллокаций и подтвердите расчет.

## Код решения

**`live_set_demo.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

var globalCache [][]byte

func main() {
	var ms runtime.MemStats

	// Создаем постоянный Live Set на 50 МБ
	fmt.Println("Инициализация постоянного кэша (Live Set 50 МБ)...")
	globalCache = make([][]byte, 50)
	for i := range globalCache {
		globalCache[i] = make([]byte, 1024*1024)
	}

	runtime.GC()
	runtime.ReadMemStats(&ms)

	liveMB := float64(ms.Alloc) / (1024 * 1024)
	nextMB := float64(ms.NextGC) / (1024 * 1024)
	fmt.Printf("Базовый Live Set:  %6.1f МБ\n", liveMB)
	fmt.Printf("Цель NextGC (2x):   %6.1f МБ\n", nextMB)
	fmt.Printf("Фактический коэффициент удвоения: %.2fx\n", nextMB/liveMB)
}
```

ℹ️ Демонстрация удвоения целевого порога NextGC относительно постоянного Live Set

## Под капотом

В `src/runtime/mgcpacer.go` переменная `heapMinimum` задает минимальный размер кучи (обычно 4 МБ). Если Live Set больше `heapMinimum`, цель вычисляется строго как `live * (1 + gcpercent/100)`.

## Подводные камни

Держать большие in-memory кэши в обычной куче Go — опасный архитектурный выбор. При 16 ГБ кэша сервис потребует 32 ГБ RAM. Решение — выносить кэши в Redis или использовать Off-heap хранилища.

## На собеседовании

**Вопрос:** Почему сервисы с большими in-memory кэшами на Go часто падают по OOM в Kubernetes?
**Ответ:** При GOGC=100 порог запуска следующей сборки вычисляется как удвоение объема живых данных. Если постоянный кэш занимает 600 МБ в контейнере с лимитом 1 ГБ, сборщик мусора запланирует запуск на 1200 МБ, что приведет к превышению лимита 1 ГБ и мгновенному убийству пода ядром Linux. Для решения обязательно задается GOMEMLIMIT.
