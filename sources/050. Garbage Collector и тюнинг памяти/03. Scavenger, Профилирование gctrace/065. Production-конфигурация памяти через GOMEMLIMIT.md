# Production-конфигурация памяти через GOMEMLIMIT и автоматическое чтение cgroups

## Условие

Реализуйте модуль автоматического конфигурирования памяти сервиса в Kubernetes: считывание лимита памяти из файлов cgroup v1/v2 и установка GOMEMLIMIT на 85% от доступного порога.

### Исходная формулировка

**Тюнинг памяти через `GOMEMLIMIT`**: Одной из главных проблем Go в Docker-контейнерах была уязвимость к OOM-киллеру при резких всплесках трафика. Начиная с Go 1.19, появился параметр `GOMEMLIMIT`. Напишите тест: установите переменную окружения `GOMEMLIMIT=150MiB` и запустите аллокатор. Наблюдайте, как при приближении потребления памяти к 150 МБ сборщик мусора Go начинает работать непрерывно и агрессивно (даже игнорируя настройки `GOGC`), пытаясь удержать потребление памяти в рамках лимита и спасти контейнер от падения по OOM.

## Теория

В облачной среде Kubernetes поды могут иметь разные лимиты памяти в dev, stage и prod окружениях. Хардкодить значение `GOMEMLIMIT` в бинарнике или docker-образе негибко.

Лучшая практика BigTech:
1. Сервис при старте проверяет наличие файла `/sys/fs/cgroup/memory.max` (cgroup v2).
2. Если файл отсутствует, проверяет `/sys/fs/cgroup/memory/memory.limit_in_bytes` (cgroup v1).
3. Парсит число байт. Если значение не равно `max` или `math.MaxInt64`:
4. Устанавливает `debug.SetMemoryLimit(int64(float64(cgroupBytes) * 0.85))`.
5. Логирует примененные настройки при старте.

## Решение по шагам

1. Напишите функцию поиска и чтения лимитов cgroup.
2. Предусмотрите безопасный fallback при запуске вне контейнера (на хосте).
3. Примените `debug.SetMemoryLimit`.
4. Проверьте установленное значение.

## Код решения

**`auto_memlimit.go`**

```go
package main

import (
	"fmt"
	"math"
	"os"
	"runtime/debug"
	"strconv"
	"strings"
)

// DetectCgroupMemoryLimit пытается прочитать лимит cgroup v2 или v1
func DetectCgroupMemoryLimit() (int64, error) {
	// 1. Проверяем cgroup v2
	data, err := os.ReadFile("/sys/fs/cgroup/memory.max")
	if err == nil {
		text := strings.TrimSpace(string(data))
		if text != "max" {
			val, parseErr := strconv.ParseInt(text, 10, 64)
			if parseErr == nil && val > 0 {
				return val, nil
			}
		}
	}

	// 2. Проверяем cgroup v1
	data, err = os.ReadFile("/sys/fs/cgroup/memory/memory.limit_in_bytes")
	if err == nil {
		text := strings.TrimSpace(string(data))
		val, parseErr := strconv.ParseInt(text, 10, 64)
		if parseErr == nil && val > 0 && val < math.MaxInt64/2 {
			return val, nil
		}
	}

	return 0, fmt.Errorf("cgroup memory limit не обнаружен")
}

func main() {
	fmt.Println("=== Автоматическая инициализация GOMEMLIMIT в Production ===")

	cgroupLimit, err := DetectCgroupMemoryLimit()
	if err != nil {
		fmt.Printf("Запуск на обычном хосте: %v. Используем ручной лимит 512 МБ.\n", err)
		cgroupLimit = 512 * 1024 * 1024
	} else {
		fmt.Printf("Обнаружен cgroup limit: %d МБ\n", cgroupLimit/(1024*1024))
	}

	// Устанавливаем 85% от лимита контейнера
	safeLimit := int64(float64(cgroupLimit) * 0.85)
	old := debug.SetMemoryLimit(safeLimit)

	fmt.Printf("GOMEMLIMIT успешно настроен на 85%%: %d МБ (было: %d МБ)\n",
		safeLimit/(1024*1024), old/(1024*1024))
}
```

ℹ️ Автоматическое определение квоты памяти контейнера cgroup и установка GOMEMLIMIT

## Под капотом

Популярная открытая библиотека `go.uber.org/automaxprocs` настраивает `GOMAXPROCS`, а библиотека `github.com/KimMachineGun/automemlimit` реализует ровно описанный выше алгоритм автоматической привязки `GOMEMLIMIT` к cgroup limits.

## Подводные камни

В cgroup v2 при отсутствии лимита в файле `memory.max` записана строка `"max"`. Попытка преобразовать ее напрямую через `strconv.ParseInt` вернет ошибку.

## На собеседовании

**Вопрос:** Как в продакшене автоматизировать установку GOMEMLIMIT для тысяч микросервисов?
**Ответ:** Используют пакет `automemlimit` (или собственную init-функцию), которая при старте процесса читает `/sys/fs/cgroup/memory.max` (cgroup v2) или cgroup v1, вычисляет 85% от квоты и вызывает `debug.SetMemoryLimit()`. Это устраняет необходимость вручную прописывать env-переменные в десятках Helm-чартов.
