# Предотвращение преждевременного удаления через runtime.KeepAlive()

## Условие

Напишите код с CGO или unsafe.Pointer, где Go-объект передается в низкоуровневый дескриптор. Продемонстрируйте проблему преждевременной утилизации объекта до завершения работы с ним и покажите, как runtime.KeepAlive(obj) защищает память.

### Исходная формулировка

**[runtime.KeepAlive()]**: Напиши код с CGO (или `unsafe`), где Go-объект передается в C-функцию. Если Go-объект больше не используется в Go-коде, GC может удалить его до того, как C-функция закончит с ним работу. Используй `runtime.KeepAlive(obj)` в конце Go-функции, чтобы запретить GC собирать его до этой строки.

## Теория

Компилятор Go и сборщик мусора вычисляют время жизни объекта **по последнему явному использованию переменной в коде Go, а не по выходу из области видимости `{}`**:

Если вы передали указатель на память Go в системный вызов, CGO или преобразовали в `uintptr`:
```go
ptr := &MyData{...}
rawAddr := uintptr(unsafe.Pointer(ptr))
// ptr больше не используется в коде Go!
doSyscall(rawAddr) // В ЭТОТ МОМЕНТ GC МОЖЕТ УДАЛИТЬ ptr!
```
Поскольку переменная `ptr` больше не читается компилятором, GC имеет полное право счесть `ptr` мусором и освободить его спан **прямо во время выполнения системного вызова**!

Функция `runtime.KeepAlive(ptr)` создает искусственную точку использования объекта, гарантируя, что GC не удалит его раньше этой строки.

## Решение по шагам

1. Создайте структуру с финализатором.
2. Извлеките сырой адрес `uintptr(unsafe.Pointer(&obj))`.
3. Покажите, как без `KeepAlive` финализатор срабатывает до завершения логики.
4. Добавьте `runtime.KeepAlive(&obj)` в конце функции и подтвердите защиту.

## Код решения

**`keepalive_demo.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

type HeavyBuffer struct {
	Descriptor int
	Data       []byte
}

func mockNativeOperation(rawAddr uintptr) {
	// Имитация долгого системного вызова или CGO-функции
	fmt.Printf("Нативная операция работает с адресом 0x%x...\n", rawAddr)
	runtime.GC() // Провоцируем сборщик мусора прямо посреди работы!
	time.Sleep(50 * time.Millisecond)
	fmt.Println("Нативная операция успешно завершена.")
}

func safeProcessing() {
	buf := &HeavyBuffer{
		Descriptor: 777,
		Data:       make([]byte, 1024),
	}

	runtime.SetFinalizer(buf, func(b *HeavyBuffer) {
		fmt.Printf(">>> ОПАСНОСТЬ: Финализатор уничтожил дескриптор %d! <<<\n", b.Descriptor)
	})

	raw := uintptr(unsafe.Pointer(buf))

	// Выполняем нативную работу
	mockNativeOperation(raw)

	// runtime.KeepAlive гарантирует, что buf жив до этой строчки!
	runtime.KeepAlive(buf)
	fmt.Println("safeProcessing завершена штатно.")
}

func main() {
	fmt.Println("=== Демонстрация runtime.KeepAlive() ===")
	safeProcessing()
}
```

ℹ️ Защита объекта от преждевременной сборки мусора через runtime.KeepAlive

## Под капотом

Компилятор Go реализует `runtime.KeepAlive` как специальную intrinsic-функцию. На машинном уровне она не генерирует никаких процессорных инструкций, но создает псевдо-использование переменной в графе потока данных (SSA liveness analysis), продлевая ее время жизни до этой точки.

## Подводные камни

Преобразование `uintptr(unsafe.Pointer(x))` в отдельную переменную с последующим использованием без `runtime.KeepAlive(x)` — классическая причина трудноуловимых крашей в CGO и сетевых драйверах.

## На собеседовании

**Вопрос:** В каких случаях необходимо явно использовать runtime.KeepAlive()?
**Ответ:** Когда время жизни объекта Go связано с ресурсом, на который не ссылаются обычные типизированные указатели Go: 1. При передаче сырых адресов uintptr в CGO или системные вызовы syscall; 2. При использовании структур с финализаторами (`runtime.SetFinalizer`), чтобы финализатор не сработал раньше, чем завершатся методы объекта, работающие с низкоуровневыми дескрипторами.
