# Мутатор против сборщика: генерация белых объектов и проверка целостности

## Условие

Реализуйте «мутатор, который нагружает GC»: в цикле создавайте цепочки белых объектов и сразу затирайте ссылки, проверяя, что сборщик своевременно утилизирует их без повреждения живых данных.

### Исходная формулировка

Реализуйте «мутатор, который обманывает GC»: в цикле создавайте белые объекты и сразу теряйте ссылку (становятся мусором). Затем создавайте серые — держите ссылку. Покажите, что GC корректно отличает их через write barrier.

## Теория

Тест «стресс-мутатора»:
* Мутатор непрерывно порождает короткоживущие графы объектов («белый мусор»).
* Параллельно сохраняется долгоживущий эталонный граф данных («черный скелет»), целостность которого непрерывно верифицируется контрольными суммами.
* Если рантайм Go допустит ошибку в барьере записи или очистке спанов, данные эталонного графа повредятся или занулятся.
* Успешное выполнение миллионов итераций доказывает непогрешимость рантайма.

## Решение по шагам

1. Создайте защищенную структуру эталонного графа с контрольной суммой.
2. Запустите цикл непрерывной генерации и затирания временных цепочек объектов.
3. Проверяйте контрольную сумму эталона на каждом шаге.
4. Убедитесь в отсутствии ошибок.

## Код решения

**`mutator_stress.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type GoldenNode struct {
	ID       int
	Checksum int
	Next     *GoldenNode
}

type TransientGarbage struct {
	Data [1024]byte
	Next *TransientGarbage
}

func main() {
	fmt.Println("=== Стресс-тест мутатора кучи ===")

	// Создаем эталонный граф (Golden State)
	head := &GoldenNode{ID: 1, Checksum: 100}
	curr := head
	for i := 2; i <= 1000; i++ {
		curr.Next = &GoldenNode{ID: i, Checksum: i * 100}
		curr = curr.Next
	}

	// Нагружаем мутатором
	start := time.Now()
	for round := 0; round < 50000; round++ {
		// Создаем белый мусор и сразу теряем ссылки
		g1 := &TransientGarbage{}
		g2 := &TransientGarbage{Next: g1}
		_ = g2

		// Верифицируем эталон
		if round%10000 == 0 {
			check := head
			for check != nil {
				if check.Checksum != check.ID*100 {
					panic(fmt.Sprintf("ПОВРЕЖДЕНИЕ ПАМЯТИ в узле %d!", check.ID))
				}
				check = check.Next
			}
		}
	}

	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("Тест успешно завершен за %v! Выполнено сборок GC: %d\n",
		time.Since(start), m.NumGC)
	fmt.Println("Целостность эталонного графа 100% подтверждена.")
}
```

ℹ️ Стресс-тест генерации мусора с контролем целостности эталонного графа

## Под капотом

Во время работы этого теста аллокатор `mallocgc` непрерывно перезаписывает освобожденные ячейки спанов `mspan`. Если бы сборщик мусора по ошибке счел узел `GoldenNode` белым, спан был бы переиспользован под `TransientGarbage`, и проверка `check.Checksum != check.ID*100` моментально вызвала бы панику.

## Подводные камни

Использование небезопасных приведений через `unsafe.Pointer` в подобных тестах может нарушить гарантии компилятора и привести к реальным падениям.

## На собеседовании

**Вопрос:** Как разработчики рантайма Go тестируют надежность сборщика мусора при конкурентных мутациях?
**Ответ:** Рантайм Go включает специальные стресс-тесты в пакете `runtime` (например, `gc_test.go`), запускаемые с флагами `GODEBUG=clobberfree=1` (перезапись освобожденной памяти мусором 0xdeadbeef для немедленного выявления use-after-free) и `-race`, моделирующие миллионы конкурентных мутаций указателей.
