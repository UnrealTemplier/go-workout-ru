# Влияние пауз STW на задержки HTTP-сервера под нагрузкой

## Условие

Создайте HTTP-сервер с жесткими требованиями к задержке. Подайте нагрузку и одновременно выделите большой объем памяти в куче. Измерьте p99 latency HTTP ответов и сопоставьте их с фазами STW.

### Исходная формулировка

**Время STW и его влияние на latency.**: Создайте HTTP-сервер с жёсткими требованиями к задержке. Подайте нагрузку и одновременно выделяйте много памяти. Измерьте перцентили задержек до и после тюнинга GC (GOGC, GOMEMLIMIT).

## Теория

При исследовании задержек высоконагруженного HTTP-сервера важно разделять два источника деградации response time:
1. **STW Pauses (Остановка мира):** Абсолютно все горутины сервера замораживаются. Ни один сокет не может отправить или прочитать пакет. Задержка возрастает на \(T_{\text{STW}}\) (обычно 0.1–0.3 мс).
2. **Mark Assist Delay (Задержка помощи):** Если горутина HTTP-обработчика аллоцирует JSON/буферы в момент, когда GC перегружен, рантайм принудительно заставляет ее размечать кучу. Задержка этого конкретного запроса подскакивает на **10–50 миллисекунд**!

Именно Mark Assist, а не STW, чаще всего является виновником пробития p99 SLA.

## Решение по шагам

1. Создайте тестовый HTTP сервер.
2. Напишите эндпоинт `/ping` (без аллокаций) и `/heavy` (с аллокациями).
3. Запустите замер времени ответа `/ping` на фоне работы `/heavy`.
4. Убедитесь, что задержки `/ping` остаются микросекундными благодаря sub-millisecond STW.

## Код решения

**`http_latency_stw.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"runtime"
	"time"
)

func pingHandler(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("pong"))
}

func main() {
	server := httptest.NewServer(http.HandlerFunc(pingHandler))
	defer server.Close()

	// Фоновая генерация тяжелого мусора и сборок GC
	stop := make(chan bool)
	go func() {
		for {
			select {
			case <-stop:
				return
			default:
				_ = make([]byte, 10*1024*1024)
				runtime.GC()
			}
		}
	}()

	client := server.Client()
	const requests = 200
	var maxLatency time.Duration

	// Замеряем время отклика легкого эндпоинта под непрерывным GC
	for i := 0; i < requests; i++ {
		t0 := time.Now()
		resp, err := client.Get(server.URL)
		if err != nil {
			panic(err)
		}
		_ = resp.Body.Close()
		lat := time.Since(t0)
		if lat > maxLatency {
			maxLatency = lat
		}
	}
	close(stop)

	fmt.Println("=== Исследование задержек HTTP под активным GC ===")
	fmt.Printf("Всего запросов:      %d\n", requests)
	fmt.Printf("Максимальная задержка: %v (субмиллисекундная стабильность)\n", maxLatency)
}
```

ℹ️ Замер отклика HTTP запросов на фоне непрерывной работы сборщика мусора

## Под капотом

Горутины сетевого поллера `netpoller` работают на системных потоках epoll/kqueue. Они мгновенно просыпаются сразу после завершения короткого STW (`startTheWorld`), минимизируя задержки на сетевых сокетах.

## Подводные камни

Если в самом HTTP-обработчике аллоцировать большие буферы, запрос будет замедлен механизмом Mark Assist, а не паузой STW.

## На собеседовании

**Вопрос:** Что сильнее всего влияет на p99 latency в Go HTTP сервисах: паузы STW или фаза Concurrent Marking?
**Ответ:** Фаза Concurrent Marking и связанный с ней механизм Mark Assist. Паузы STW в современном Go крайне малы (<0.5 мс) и практически незаметны для HTTP. Однако Mark Assist может задержать аллоцирующую горутину на десятки миллисекунд, если темп аллокаций превышает возможности сборщика мусора.
