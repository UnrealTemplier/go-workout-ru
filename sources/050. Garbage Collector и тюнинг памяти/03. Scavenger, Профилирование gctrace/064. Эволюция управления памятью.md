# Эволюция управления памятью: почему GOMEMLIMIT изменил мир Go

## Условие

Объясните эволюцию тюнинга памяти в Go: почему до версии 1.19 параметр GOGC не справлялся с защитой контейнеров Kubernetes, и как GOMEMLIMIT решил проблему OOM-падений.

### Исходная формулировка

**Магия GOMEMLIMIT (Go 1.19+)**: До 1.19 `GOGC` не знал про физические лимиты контейнера K8s. Если `GOGC=100`, а предел контейнера 100 МБ, при росте кучи с 60 МБ до 120 МБ контейнер умирал от OOM до того, как GC решал запуститься.
    Установи `GOGC=off` и `GOMEMLIMIT=100MiB`. Запусти память-интенсивный код. Увидь магию: несмотря на выключенный GOGC, сборщик мусора начнет экстренно спасать ситуацию, как только объем памяти приблизится к 100 МБ (Soft Memory Limit).

---

## Теория

Историческая проблема `GOGC` в облачной инфраструктуре:
* До Go 1.19 сборщик мусора ориентировался **исключительно на относительный процентный рост**: `HeapGoal = LiveHeap * (1 + GOGC/100)`.
* GC ничего не знал о том, сколько оперативной памяти физически доступно серверу или ограничено через cgroup limits.

**Сценарий OOMKilled в Kubernetes:**
1. Под запущен с лимитом `limits.memory = 1Gi`.
2. В спокойном режиме сервис держит 300 МБ кэша. `HeapGoal = 600 МБ`. Все отлично.
3. Наступает всплеск нагрузки: кэш подрастает до 600 МБ.
4. Сборщик при `GOGC=100` вычисляет следующую цель: `NextGC = 1200 МБ`!
5. Куча растет до 1001 МБ, и ядро Linux мгновенно присылает контейнеру `kill -9` (OOM 137). Сервис падает.

**Решение через GOMEMLIMIT (Go 1.19+):**
Рантайм получил знание об абсолютном мягком лимите. Когда куча достигает 850 МБ, пейсер сжимает эффективный `GOGC` до 10%, запускает внеочередную сборку, удерживает память на уровне 900 МБ и полностью предотвращает падение сервиса.

## Код решения

**`gomemlimit_history.go`**

```go
package main

import "fmt"

func calculateHeapGoal(liveMB, gogc, memlimitMB float64) (goalMB float64, willOOM bool) {
	// Цель по GOGC
	goalGOGC := liveMB * (1 + gogc/100.0)

	// Цель с учетом GOMEMLIMIT
	goalMB = goalGOGC
	if memlimitMB > 0 && memlimitMB < goalGOGC {
		goalMB = memlimitMB
	}

	willOOM = goalMB > 1000.0 // Допустим лимит пода 1000 МБ
	return goalMB, willOOM
}

func main() {
	fmt.Println("=== Моделирование поведения GC в Kubernetes Pod (Лимит 1000 МБ) ===")

	liveSizes := []float64{200, 400, 600, 750}

	fmt.Println("\n1. Старый режим (Go < 1.19, только GOGC=100):")
	for _, live := range liveSizes {
		goal, oom := calculateHeapGoal(live, 100, 0)
		status := "OK"
		if oom {
			status = ">>> OOMKILLED (137) <<<"
		}
		fmt.Printf("  Live: %4.0f МБ -> NextGC: %5.0f МБ | %s\n", live, goal, status)
	}

	fmt.Println("\n2. Современный режим (Go 1.19+, GOGC=100 + GOMEMLIMIT=900 МБ):")
	for _, live := range liveSizes {
		goal, oom := calculateHeapGoal(live, 100, 900)
		status := "Защищено пейсером"
		if oom {
			status = "OOM"
		}
		fmt.Printf("  Live: %4.0f МБ -> NextGC: %5.0f МБ | %s\n", live, goal, status)
	}
}
```

ℹ️ Математическая модель сравнения поведения памяти до и после появления GOMEMLIMIT

## Под капотом

В `src/runtime/mgcpacer.go` константа `maxGCPacingOverhead = 0.5` ограничивает долю CPU, которую рантайм может забрать на компенсацию нехватки памяти при приближении к `GOMEMLIMIT`.

## Подводные камни

Если разработчик установит `GOMEMLIMIT` меньше объема постоянного Live Set, рантайм будет сжигать разрешенные 50% CPU в отчаянных попытках очистить память, но в итоге все равно упадет по OOM.

## На собеседовании

**Вопрос:** Какую фундаментальную проблему решил параметр GOMEMLIMIT в Go 1.19?
**Ответ:** До Go 1.19 сборщик мусора рассчитывал цель кучи исключительно относительно объема живых данных (GOGC), не учитывая лимиты контейнеров. При росте постоянных данных порог следующей сборки выходил за пределы квоты cgroups, приводя к OOMKilled. GOMEMLIMIT установил жесткий потолок сверху, принуждая GC сжимать интервалы сборок и гарантируя выживаемость сервиса под нагрузкой.
