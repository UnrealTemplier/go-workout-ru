# Устранение перегрузки CPU тюнингом GOGC

## Условие

Запустите память-интенсивный сервис. Измерьте потребление CPU при GOGC=50 (куче разрешено вырасти лишь на 50%) и GOGC=100. Объясните, почему частый GC может забирать до половины полезного времени процессора.

### Исходная формулировка

**Тюнинг GOGC**: Запусти память-интенсивный сервис из упр. 637. Измерь потребление CPU. Установи `GOGC=50` (куче разрешено вырасти лишь на 50%). Запусти снова: CPU возрастет (GC запускается в 2 раза чаще), но оперативной памяти потратится меньше. Теперь сделай `GOGC=500`. Память взлетит, но CPU почти не будет тратиться на GC. (Баланс CPU vs RAM).

## Теория

Когда `GOGC` снижен до агрессивных значений (например, 20-50):
* Сборщик мусора вызывается при малейшем приращении кучи.
* На каждой сборке рантайм обязан остановить мир (STW), сбросить кэши, запустить воркеры разметки, обойти все корневые стеки и очистить спаны.
* Если сервис генерирует данные быстрее, чем воркеры сканируют память, мутаторы попадают в `Mark Assist`, и эффективная пропускная способность полезного кода падает до 50% и ниже.

## Решение по шагам

1. Напишите тест с интенсивным созданием объектов.
2. Замерьте время работы и число сборок при `GOGC=50`.
3. Замерьте время работы при `GOGC=150`.
4. Сравните сэкономленное процессорное время.

## Код решения

**`cpu_overhead_tune.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func runHeavyLoad(gogc int) {
	debug.SetGCPercent(gogc)
	runtime.GC()

	start := time.Now()
	var mStart, mEnd runtime.MemStats
	runtime.ReadMemStats(&mStart)

	for i := 0; i < 200000; i++ {
		_ = make([]byte, 1024)
	}

	runtime.ReadMemStats(&mEnd)
	fmt.Printf("GOGC=%-3d | Время: %-10v | Число GC: %-2d | Паузы STW: %v\n",
		gogc, time.Since(start), mEnd.NumGC-mStart.NumGC,
		time.Duration(mEnd.PauseTotalNs-mStart.PauseTotalNs))
}

func main() {
	fmt.Println("=== Исследование нагрузки на CPU при малом GOGC ===")
	runHeavyLoad(50)
	runHeavyLoad(150)
	debug.SetGCPercent(100)
}
```

ℹ️ Сравнение затрат CPU и пауз при различном значении GOGC

## Под капотом

В `src/runtime/mstats.go` поле `GCCPUFraction` рассчитывает процент суммарных процессорных тактов, отданных сборке мусора. При GOGC=50 этот показатель может подскакивать до 0.35-0.45.

## Подводные камни

Попытка экономить каждый мегабайт оперативной памяти занижением GOGC на нагруженном веб-сервере приводит к деградации RPS и жалобам клиентов на таймауты.

## На собеседовании

**Вопрос:** Как по метрикам выявить, что Go-сервис тратит слишком много CPU на сборку мусора?
**Ответ:** По значению метрики `runtime.MemStats.GCCPUFraction` (или Prometheus `go_gc_cpu_fraction`). Если этот показатель превышает 0.15–0.20 (более 15-20% процессорного бюджета тратится на GC), это сигнализирует о чрезмерной нагрузке: либо занижен GOGC, либо в коде присутствует высокая скорость генерации временных объектов кучи.
