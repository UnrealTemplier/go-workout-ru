# Накладные расходы Write Barrier при интенсивной мутации указателей

## Условие

Напишите программу с интенсивной перезаписью указателей в структуры во время работы GC под флагом GODEBUG=gctrace=1. Продемонстрируйте влияние барьера записи на производительность циклов мутации.

### Исходная формулировка

Напишите программу с интенсивной записью указателей в существующие структуры во время работы GC (`GODEBUG=gctrace=1`). Покажите, что write barrier (`wbBuf`) накапливает «серые» объекты. Найдите в исходниках (`src/runtime/mwbbuf.go`) размер буфера и механизм сброса.

## Теория

Барьер записи Go (`runtime.gcWriteBarrier`) включается только во время фазы Concurrent Marking.

Что делает барьер записи на каждую инструкцию мутации `struct.ptr = newPtr`:
1. Проверяет глобальный флаг `writeBarrier.enabled` (ветвление в CPU pipeline).
2. Вызывает функцию барьера.
3. Сохраняет старый указатель в локальный буфер `wbBuf`.
4. Сохраняет новый указатель в `wbBuf`.
5. При переполнении буфера (256 указателей) сбрасывает данные в очередь разметки `gcWork`.

Для pointer-heavy алгоритмов (например, интенсивное перемешивание ссылок в графах или деревьях) включение барьера записи снижает производительность выполнения мутаций на 15–30% во время фазы Marking.

## Решение по шагам

1. Создайте плотный массив структур со ссылками друг на друга.
2. Выполните миллионы мутаций ссылок без GC.
3. Выполните тот же объем мутаций при принудительно активном GC.
4. Сравните падение пропускной способности оператора присваивания.

## Код решения

**`write_barrier_bench.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type Node struct {
	Next *Node
	Data int
}

func main() {
	const nodeCount = 500000
	nodes := make([]Node, nodeCount)
	for i := 0; i < nodeCount-1; i++ {
		nodes[i].Next = &nodes[i+1]
	}

	const iterations = 5000000

	// 1. Мутации в спокойном режиме (без GC)
	runtime.GC()
	t1 := time.Now()
	for i := 0; i < iterations; i++ {
		idx := i % (nodeCount - 1)
		nodes[idx].Next = &nodes[idx+1]
	}
	durNormal := time.Since(t1)

	// 2. Мутации под активным GC (с барьером записи)
	stop := make(chan bool)
	go func() {
		for {
			select {
			case <-stop:
				return
			default:
				_ = make([]byte, 8*1024*1024)
				runtime.GC()
			}
		}
	}()

	time.Sleep(10 * time.Millisecond)
	t2 := time.Now()
	for i := 0; i < iterations; i++ {
		idx := i % (nodeCount - 1)
		nodes[idx].Next = &nodes[idx+1]
	}
	durWithGC := time.Since(t2)
	close(stop)

	fmt.Println("=== Влияние Write Barrier на скорость мутаций указателей ===")
	fmt.Printf("5 млн мутаций без GC:      %v\n", durNormal)
	fmt.Printf("5 млн мутаций с активным GC: %v\n", durWithGC)
	fmt.Printf("Оверхед барьера записи:    +%.1f%%\n",
		float64(durWithGC-durNormal)/float64(durNormal)*100)
}
```

## Под капотом

В ассемблере компилятор Go генерирует код:
```asm
CMPB runtime.writeBarrier(SB), $0
JEQ  fast_write
CALL runtime.gcWriteBarrier(SB)
fast_write:
MOVQ BX, (AX)
```
Когда барьер выключен, выполняется всего одна проверка байта и условный переход (который предсказывается Branch Predictor процессора почти со 100% точностью). Когда барьер включен, вызов `gcWriteBarrier` сбрасывает регистры и пишет в `wbBuf`.

## Подводные камни

В циклических алгоритмах обхода графов мутируйте целочисленные индексы вместо прямых указателей (`node.NextIdx = nextIdx`), тогда барьер записи не будет генерироваться компилятором вовсе.

## На собеседовании

**Вопрос:** Как компилятор Go оптимизирует проверки барьера записи?
**Ответ:** Компилятор использует условную проверку глобального флага `runtime.writeBarrier.enabled`. Если флаг равен 0, процессор мгновенно переходит на прямую инструкцию MOVQ без вызова функций. Кроме того, операции со стеком горутины компилируются без проверок барьера, так как стек защищен гибридным алгоритмом.
