# Ручное управление кучей при GOGC=off и риски исчерпания RAM

## Условие

Выставите GOGC=off. Запустите цикл аллокаций памяти. Продемонстрируйте, как куча растет монотонно без автоматических сборок мусора, и как явный вызов runtime.GC() возвращает память.

### Исходная формулировка

**GOGC=off и ручное управление**: Выстави `GOGC=off`. Запусти код из 637. Наслаждайся тем, как программа съедает всю память твоего ноутбука и убивается ОС (OOM Killed). Добавь в код вызов `runtime.GC()` каждую секунду по таймеру и посмотри, как программа спасается от OOM.

## Теория

При значении `GOGC=off` рантайм полностью отключает автоматический запуск сборщика мусора.
* Любая аллокация в куче (`mallocgc`) выделяет новые блоки `mspan`.
* Недостижимые объекты накапливаются в куче, не очищаясь.
* Если приложение не вызывает `runtime.GC()` вручную, объем виртуальной и физической памяти (RSS) растет строго линейно.
* При исчерпании доступной оперативной памяти операционная система принудительно убьет процесс через Linux OOM-Killer (`signal 9 SIGKILL`).

## Решение по шагам

1. Установите `debug.SetGCPercent(-1)`.
2. В цикле выделите 100 МБ данных.
3. Убедитесь, что `NumGC` не изменился, а `Alloc` вырос на 100 МБ.
4. Вызовите `runtime.GC()` вручную и зафиксируйте очистку кучи.

## Код решения

**`gogc_off_manual.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func main() {
	// Отключаем автоматический GC
	old := debug.SetGCPercent(-1)
	defer debug.SetGCPercent(old)

	var m1, m2, m3 runtime.MemStats
	runtime.ReadMemStats(&m1)
	fmt.Printf("1. Старт: HeapAlloc = %5.1f МБ, NumGC = %d\n",
		float64(m1.HeapAlloc)/(1024*1024), m1.NumGC)

	// Аллоцируем 50 МБ временных данных
	for i := 0; i < 50; i++ {
		_ = make([]byte, 1024*1024)
	}

	runtime.ReadMemStats(&m2)
	fmt.Printf("2. После аллокации 50 МБ: HeapAlloc = %5.1f МБ, NumGC = %d (GC не сработал!)\n",
		float64(m2.HeapAlloc)/(1024*1024), m2.NumGC)

	// Ручной запуск
	fmt.Println("3. Вызываем ручной runtime.GC()...")
	runtime.GC()

	runtime.ReadMemStats(&m3)
	fmt.Printf("4. После ручного GC: HeapAlloc = %5.1f МБ, NumGC = %d\n",
		float64(m3.HeapAlloc)/(1024*1024), m3.NumGC)
}
```

ℹ️ Ручное управление сборкой мусора при полностью отключенном автоматическом триггере

## Под капотом

Флаг `gcpercent = -1` отключает проверку `gcTriggerHeap` в `mallocgc`. Вся память выделяется через `mcentral.grow` и `mheap.alloc`, непрерывно запрашивая новые страницы у ядра ОС через `mmap`.

## Подводные камни

Использование `GOGC=off` без вызова `runtime.GC()` допустимо только в CLI-утилитах, завершающихся за доли секунды. В веб-сервисах это гарантированный OOM.

## На собеседовании

**Вопрос:** Когда оправдано использование GOGC=off в продакшене?
**Ответ:** 1. В CLI-утилитах (например, компиляторах, линтерах), где время работы исчисляется сотнями миллисекунд, и операционная система мгновенно заберет всю память при exit; 2. В HighLoad архитектурах с ручным таймингом сборок (Batch GC), когда сервисы накапливают память во время пика запросов и вызывают runtime.GC() в моменты технологических пауз.
