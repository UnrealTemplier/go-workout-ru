# Симулятор алгоритма Mark Assist на чистом Go

## Условие

Напишите «GC Assist Simulator» на чистом Go: горутина, которая аллоцирует память во время активной разметки, обязана «помочь» сборщику (потратить время на сканирование очереди объектов пропорционально объему выделяемых байт).

### Исходная формулировка

Напишите «GC assist simulator» на чистом Go: goroutine, которая аллоцирует память, должна «помочь» GC (потратить время на маркировку пропорционально аллокации). Объясните, почему это предотвращает out-of-control рост heap во время маркировки.

## Теория

Принцип кредитного баланса Mark Assist:
1. Пусть на 1 байт аллокации требуется отсканировать \(K\) байт объектов кучи (`assistWorkPerByte = K`).
2. Каждая горутина имеет счетчик `assistCredits`.
3. При вызове `Alloc(bytes)`:
   * Требуется кредитов: `debt = bytes * K`.
   * Горутина вычитает `debt` из своего счета.
   * Если баланс стал отрицательным, горутина **блокируется и выполняет функцию `AssistScan()`**, пока не покроет отрицательный остаток.
   * Только после этого аллокация разрешается.

## Решение по шагам

1. Создайте структуру `SimulatorGoroutine` с балансом кредитов.
2. Реализуйте метод `Alloc(size int)`.
3. Реализуйте метод `AssistScan(workUnits int)`.
4. Продемонстрируйте замедление горутины при аллокациях во время активного GC.

## Код решения

**`assist_simulator.go`**

```go
package main

import (
	"fmt"
	"time"
)

type GoroutineSim struct {
	ID            int
	AssistCredits int64 // Баланс кредитов разметки
}

var gcActive = false
const assistRatio = 2 // На 1 байт аллокации нужно отсканировать 2 байта работы

func (g *GoroutineSim) Alloc(bytes int64) {
	if !gcActive {
		// GC не активен, выделение мгновенное
		return
	}

	requiredWork := bytes * assistRatio
	g.AssistCredits -= requiredWork

	if g.AssistCredits < 0 {
		debt := -g.AssistCredits
		fmt.Printf("[Горутина %d] Долг помощи GC: %d единиц. Переход в Mark Assist!\n", g.ID, debt)
		g.AssistScan(debt)
	}
}

func (g *GoroutineSim) AssistScan(work int64) {
	// Имитируем затраты времени на сканирование памяти
	scanDuration := time.Duration(work) * 50 * time.Microsecond
	time.Sleep(scanDuration)
	g.AssistCredits += work
	fmt.Printf("[Горутина %d] Отработано %d единиц за %v. Долг погашен.\n", g.ID, work, scanDuration)
}

func main() {
	g := &GoroutineSim{ID: 1, AssistCredits: 0}

	fmt.Println("=== 1. Аллокация без активного GC ===")
	t1 := time.Now()
	g.Alloc(10)
	fmt.Printf("Время операции: %v\n", time.Since(t1))

	fmt.Println("\n=== 2. Аллокация при активном GC (включение Mark Assist) ===")
	gcActive = true
	t2 := time.Now()
	g.Alloc(10) // 10 байт -> долг 20 единиц работы
	fmt.Printf("Время операции с Mark Assist: %v\n", time.Since(t2))
}
```

ℹ️ Программная симуляция долговой механики GC Mark Assist

## Под капотом

В `src/runtime/mgcmark.go` поле `g.gcAssistBytes` хранит число байт кредита. Атомарные функции `atomic.Xaddint64(&g.gcAssistBytes, ...)` обновляют баланс при каждой аллокации в `mallocgc`.

## Подводные камни

Если в очереди `work.full` нет готовых серых объектов для сканирования, горутина в Mark Assist переводится в состояние сна на `assistQueue`, ожидая появления работы от других процессоров.

## На собеседовании

**Вопрос:** Как рантайм Go определяет, сколько именно работы по разметке должна выполнить горутина в режиме Mark Assist?
**Ответ:** Объем работы пропорционален размеру запрашиваемой аллокации. Рантайм вычисляет коэффициент `assistWorkPerByte` как отношение оставшегося объема разметки к остатку бюджета кучи до HeapGoal. Горутина сканирует объекты кучи до тех пор, пока ее локальный долговой баланс `gcAssistBytes` не станет положительным.
