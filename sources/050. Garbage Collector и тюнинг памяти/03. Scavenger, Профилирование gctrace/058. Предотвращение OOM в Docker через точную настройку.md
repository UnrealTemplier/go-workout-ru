# Предотвращение OOM в Docker через точную настройку GOMEMLIMIT

## Условие

Настройте GOMEMLIMIT на значение, близкое к лимиту контейнера (90% от quota). Наблюдайте через gctrace, как сборщик мусора учащается при приближении к границе, спасая сервис от падения по OOM.

### Исходная формулировка

**GOMEMLIMIT и мягкий лимит памяти.**: Настройте `GOMEMLIMIT` на значение, близкое к лимиту контейнера. Наблюдайте через `gctrace`, как сборщик мусора учащается при приближении к лимиту, избегая OOM.

## Теория

Архитектура защиты от Out-Of-Memory в Docker/Kubernetes:

```
+-------------------------------------------------------------+
| Контейнер Docker / Kubernetes Pod (Memory Limit = 1000 MiB)  |
|                                                             |
|   +---------------------------------------+                 |
|   | Резерв ОС, сокеты ядра, CGO (~100 MiB)|                 |
|   +---------------------------------------+                 |
|                                                             |
|   +-----------------------------------------------------+   |
|   | GOMEMLIMIT = 900 MiB (Soft Limit рантайма Go)       |   |
|   |                                                     |   |
|   |   +-------------------+                             |   |
|   |   | Стеки, метаданные |                             |   |
|   |   +-------------------+                             |   |
|   |   | Куча (Heap)       | <--- GC ускоряется при 850M |   |
|   |   +-------------------+                             |   |
|   +-----------------------------------------------------+   |
+-------------------------------------------------------------+
```

Когда куча растет и процесс приближается к 900 МБ:
1. Пейсер видит дефицит пространства до `GOMEMLIMIT`.
2. Он динамически снижает эффективный `TriggerRatio`.
3. Сборщик мусора запускается чаще, удерживая суммарный объем процесса строго под 900 МБ.
4. Контейнер **никогда не получает SIGKILL (137)** от Linux OOM Killer!

## Решение по шагам

1. Установите мягкий лимит памяти 120 МБ через `debug.SetMemoryLimit`.
2. В цикле создавайте растущий объем данных.
3. Наблюдайте в логах `gctrace`, как частота сборок мусора адаптивно возрастает.
4. Убедитесь, что объем памяти стабилизировался в пределах лимита.

## Код решения

**`oom_prevention.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"time"
)

func main() {
	// Лимит пода 128 МБ -> ставим GOMEMLIMIT = 100 МБ
	const limit = 100 * 1024 * 1024
	debug.SetMemoryLimit(limit)

	fmt.Println("=== Демонстрация предотвращения OOM через GOMEMLIMIT ===")
	fmt.Printf("Установлен жесткий потолок: %d МБ\n", limit/(1024*1024))

	var retained [][]byte
	var ms runtime.MemStats

	// Цикл с приближением к границе памяти
	for i := 1; i <= 8; i++ {
		// Аллоцируем порции по 10 МБ
		chunk := make([]byte, 10*1024*1024)
		retained = append(retained, chunk)

		runtime.ReadMemStats(&ms)
		fmt.Printf("Итерация %d: HeapAlloc = %5.1f МБ | NextGC = %5.1f МБ | NumGC = %d\n",
			i, float64(ms.Alloc)/(1024*1024), float64(ms.NextGC)/(1024*1024), ms.NumGC)
		time.Sleep(50 * time.Millisecond)
	}

	_ = retained
	fmt.Println("Память удержана в границах мягкого лимита без аварийного завершения!")
}
```

ℹ️ Удержание процесса в границах лимита контейнера через GOMEMLIMIT

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run oom_prevention.go
# В логах видно, как goal NextGC поджимается под 100 МБ по мере приближения к лимиту
```

## Под капотом

В `src/runtime/mgcpacer.go` функция `gcControllerState.memoryLimitGoal` при приближении к границе лимита уменьшает целевой размер до значения `live + (limit - current) / 2`, заставляя сборщик мусора работать с упреждением.

## Подводные камни

Если приложение хранит в постоянных ссылках больше данных, чем задано в `GOMEMLIMIT` (например, живых данных 110 МБ при лимите 100 МБ), сборщик мусора не сможет их удалить и процесс упадет по OOM, предварительно потратив до 50% CPU на попытки очистки.

## На собеседовании

**Вопрос:** Какую долю от лимита памяти пода в Kubernetes следует отводить под GOMEMLIMIT?
**Ответ:** Общепринятый стандарт в ведущих технологических компаниях — от 80% до 90% от `resources.limits.memory`. Оставшиеся 10–20% служат буфером безопасности для стеков горутин, метаданных рантайма, сетевых буферов сокетов ядра Linux и системных библиотек, гарантируя 100% защиту от OOMKilled.
