# Финализаторы и воскрешение объектов: почему SetFinalizer опасен

## Условие

Напишите структуру с эмуляцией файлового дескриптора. Используйте runtime.SetFinalizer. Продемонстрируйте, как финализатор откладывает освобождение памяти объекта минимум на один цикл GC, и замените его на идиоматичный io.Closer.

### Исходная формулировка

**[Финализаторы]**: Напиши структуру с эмуляцией файлового дескриптора. Используй `runtime.SetFinalizer(&obj, func(o *Obj) { o.Close() })`. Покажи, что `Close()` вызовется автоматически, когда GC соберет объект. Объясни, почему финализаторы считаются анти-паттерном в Go (непредсказуемое время вызова, требуют 2 цикла GC для удаления).

## Теория

Жизненный цикл объекта с финализатором:
1. Объект становится недостижимым из корней программы.
2. Во время фазы Marking сборщик обнаруживает, что объект недостижим, но имеет прикрепленный финализатор в спане.
3. Сборщик **не удаляет объект, а делает его Серым, воскрешая его**!
4. Указатель на объект помещается в очередь `runfinq`.
5. Специальная горутина рантайма асинхронно вычитывает `runfinq` и вызывает функцию финализатора.
6. После того как финализатор отработал, ссылка снимается.
7. **Только на СЛЕДУЮЩЕМ цикле GC** память объекта наконец будет физически освобождена!

## Решение по шагам

1. Создайте структуру `FileResource` с финализатором.
2. Продемонстрируйте вызовы двух циклов `runtime.GC()` для полного освобождения.
3. Перепишите на стандартный интерфейс `io.Closer` с `defer resource.Close()`.
4. Сравните надежность и предсказуемость.

## Код решения

**`finalizer_lifecycle.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type Resource struct {
	ID   int
	data []byte
}

func newResource(id int) *Resource {
	r := &Resource{
		ID:   id,
		data: make([]byte, 10*1024*1024), // 10 МБ
	}
	// Установка финализатора
	runtime.SetFinalizer(r, func(res *Resource) {
		fmt.Printf(">>> Финализатор сработал для ресурса ID=%d <<<\n", res.ID)
	})
	return r
}

func main() {
	fmt.Println("=== Исследование задержки освобождения памяти с SetFinalizer ===")

	_ = newResource(42)

	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	fmt.Printf("После создания:     Alloc = %5.1f МБ\n", float64(ms.Alloc)/(1024*1024))

	// 1-й GC: обнаружение и постановка в finq (воскрешение объекта!)
	runtime.GC()
	time.Sleep(50 * time.Millisecond) // даем время горутине финализации
	runtime.ReadMemStats(&ms)
	fmt.Printf("После 1-го GC:      Alloc = %5.1f МБ (Объект ВСЕ ЕЩЕ в памяти!)\n",
		float64(ms.Alloc)/(1024*1024))

	// 2-й GC: окончательное физическое освобождение
	runtime.GC()
	runtime.ReadMemStats(&ms)
	fmt.Printf("После 2-го GC:      Alloc = %5.1f МБ (Память наконец освобождена)\n",
		float64(ms.Alloc)/(1024*1024))
}
```

ℹ️ Демонстрация воскрешения объекта и задержки освобождения на 2 цикла GC

## Под капотом

В `src/runtime/mfinal.go` функция `queuefinalizer` переводит объект в статус живого на время исполнения финализатора. Если сам финализатор сохранит указатель в глобальную переменную (Object Resurrection), объект останется жить навсегда.

## Подводные камни

Если объект содержит циклические ссылки на другие объекты с финализаторами, рантайм Go не гарантирует порядок их выполнения и может вообще никогда не вызвать финализаторы, приводя к перманентной утечке памяти.

## На собеседовании

**Вопрос:** Почему объект с runtime.SetFinalizer не освобождается сразу на первом цикле GC?
**Ответ:** Потому что для безопасного выполнения функции финализатора объект обязан оставаться валидным в памяти. Сборщик мусора воскрешает объект, переводит его в очередь финализации, а системная горутина вызывает финализатор. Только после завершения финализатора объект снова становится обычным мусором и будет удален на следующем цикле GC.
