# Сканирование глубоких деревьев указателей и нагрузка на GC

## Условие

Напишите программу, создающую глубокое бинарное дерево объектов (struct { left, right *Node }). Запустите с GODEBUG=gctrace=1 и объясните, почему глубокий граф указателей замедляет сборку мусора.

### Исходная формулировка

Напишите программу, которая создаёт дерево объектов (граф из `struct { left, right *node }`). Запустите `GODEBUG=gctrace=1` и проанализируйте вывод: `gc 1 @...: 10% CPU, ..., 0.015+1.2+0.003 ms clock`. Объясните каждое поле (STW sweep termination, concurrent mark, STW mark termination).

## Теория

Когда структура кучи состоит из миллионов маленьких объектов с указателями (например, узлы дерева `struct { Left, Right *Node; Val int }`):
1. **Каждый узел требует отдельного заголовка и бита в `gcmarkBits`.**
2. **Случайный доступ к памяти (Pointer Chasing):** Узлы дерева разбросаны по разным спанам и аренам кучи. При обходе дерева маркер-воркеры испытывают постоянные промахи кэша CPU (L1/L2/L3 Cache Misses).
3. **Разрастание серых очередей:** Очереди `gcWork` переполняются, что приводит к сбросу в глобальную структуру `work.full` с блокировкой глобального мьютекса.

Замена деревьев указателей на плоские массивы с целочисленными индексами узлов (Data-Oriented Design) ускоряет работу GC в 10–50 раз!

## Решение по шагам

1. Создайте структуру `TreeNode`.
2. Постройте сбалансированное бинарное дерево глубиной 18 уровней (~260 000 узлов).
3. Замерьте время `runtime.GC()`.
4. Запустите с `GODEBUG=gctrace=1` и оцените длительность разметки.

## Код решения

**`tree_gc.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

type TreeNode struct {
	Left  *TreeNode
	Right *TreeNode
	Val   int
}

func buildTree(depth int) *TreeNode {
	if depth <= 0 {
		return nil
	}
	return &TreeNode{
		Left:  buildTree(depth - 1),
		Right: buildTree(depth - 1),
		Val:   depth,
	}
}

func main() {
	fmt.Println("Построение бинарного дерева на 262 143 узлов указателей...")
	root := buildTree(18)

	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("Память под дерево: %8.2f МБ\n", float64(m.Alloc)/(1024*1024))

	start := time.Now()
	runtime.GC()
	elapsed := time.Since(start)

	fmt.Printf("Время полного прохода GC по дереву указателей: %v\n", elapsed)
	_ = root
}
```

ℹ️ Построение графа бинарного дерева и замер времени сканирования указателей

**`Терминал`**

```bash
GODEBUG=gctrace=1 go run tree_gc.go
# Обратите внимание на высокое время clock marking из-за обхода сотен тысяч указателей
```

## Под капотом

В `src/runtime/mgcmark.go` функция `scanobject` извлекает битмап типа объекта. Для каждого указателя в структуре она проверяет адрес, преобразует его в `mspan` и ставит в серую очередь. На дереве с указателями процессор упирается в пропускную способность шины памяти (Memory Bus Bandwidth).

## Подводные камни

Использование классических ООП структур с указателями на каждый элемент в высоконагруженных Go-сервисах — главная причина высокого GC CPU usage.

## На собеседовании

**Вопрос:** Почему в Go плоский срез структур []MyStruct эффективнее для сборщика мусора, чем связный список или дерево указателей []*MyStruct?
**Ответ:** Плоский срез []MyStruct аллоцируется единым непрерывным блоком памяти. Если структуры не содержат указателей, срез попадает в спан noscan и не сканируется вовсе. Если же структуры содержат указатели, они лежат в памяти последовательно, что максимизирует попадания в кэш-линии CPU (Hardware Prefetcher) и кратно снижает время разметки GC.
