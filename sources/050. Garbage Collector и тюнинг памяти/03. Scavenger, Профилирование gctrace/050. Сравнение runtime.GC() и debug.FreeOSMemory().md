# Сравнение runtime.GC() и debug.FreeOSMemory()

## Условие

Изучите разницу между runtime.GC() (обычная сборка мусора) и debug.FreeOSMemory() (принудительный сброс неиспользуемых страниц ядру ОС через madvise). Измерьте изменение HeapIdle и HeapReleased.

### Исходная формулировка

**[runtime.GC() vs debug.FreeOSMemory()]**: Напиши программу. Вызови `runtime.GC()` — это запустит обычный цикл сборки мусора. Затем вызови `debug.FreeOSMemory()` — это заставит mheap вернуть пустые спаны операционной системе (`madvise`). Проследи за изменением RSS.

## Теория

Разница между двумя системными функциями:

1. **`runtime.GC()`:**
   * Запускает полный цикл маркировки и очистки спанов.
   * Освобожденные объекты возвращаются в пулы `mcentral` и помечаются как `HeapIdle`.
   * **Память НЕ возвращается ядру операционной системы немедленно.** Физический размер RSS процесса остается прежним.

2. **`debug.FreeOSMemory()`:**
   * Сначала синхронно вызывает `runtime.GC()`.
   * Затем принудительно вызывает `madvise(MADV_DONTNEED)` для всех свободных страниц кучи (`HeapIdle`).
   * Метрика `HeapReleased` возрастает, а физический объем оперативной памяти процесса (RSS в top/htop) **немедленно падает**!

## Решение по шагам

1. Выделите 100 МБ памяти в куче.
2. Вызовите `runtime.GC()` и покажите, что `HeapIdle` велик, а `HeapReleased` мал.
3. Вызовите `debug.FreeOSMemory()`.
4. Покажите, как память физически вернулась ядру ОС (`HeapReleased == HeapIdle`).

## Код решения

**`free_os_mem.go`**

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
)

func showStats(label string) {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("[%s]\n", label)
	fmt.Printf("  HeapAlloc:    %8.2f МБ (занято живыми данными)\n", float64(m.HeapAlloc)/(1024*1024))
	fmt.Printf("  HeapIdle:     %8.2f МБ (свободные спаны в рантайме)\n", float64(m.HeapIdle)/(1024*1024))
	fmt.Printf("  HeapReleased: %8.2f МБ (возвращено ОС через madvise)\n", float64(m.HeapReleased)/(1024*1024))
}

func main() {
	showStats("1. Старт")

	// Аллоцируем 100 МБ
	data := make([][]byte, 100)
	for i := range data {
		data[i] = make([]byte, 1024*1024)
	}
	showStats("2. Выделено 100 МБ")

	// 1. Обычный runtime.GC()
	data = nil
	runtime.GC()
	showStats("3. После runtime.GC() (память в HeapIdle, ОС не отдана)")

	// 2. Принудительный сброс страниц ОС
	debug.FreeOSMemory()
	showStats("4. После debug.FreeOSMemory() (HeapReleased вырос, RSS упал)")
}
```

## Под капотом

В `src/runtime/mheap.go` функция `mheap.scavengeAll()` обходит постраничные структуры `pageAlloc` и вызывает `sysUnused` для каждого непрерывного свободного диапазона. Системный вызов `madvise(MADV_DONTNEED)` уведомляет планировщик виртуальной памяти Linux, что физические фреймы можно забрать.

## Подводные камни

Вызов `debug.FreeOSMemory()` — дорогая операция. Системные вызовы `madvise` требуют блокировок таблиц страниц ядра Linux (`mmap_lock`). Если после этого приложению снова потребуется память, возникнут задержки на Page Faults. Не вызывайте `FreeOSMemory` в критических путях сервиса!

## На собеседовании

**Вопрос:** Когда имеет смысл вызывать debug.FreeOSMemory()?
**Ответ:** Только в ситуациях, когда сервис завершил редкую, крайне тяжелую пакетную задачу (например, ночной перерасчет витрин данных или построение индекса на 20 ГБ), и ожидается долгий период простоя. Это немедленно возвращает физическую RAM операционной системе, освобождая ресурсы для соседних сервисов на хосте.
