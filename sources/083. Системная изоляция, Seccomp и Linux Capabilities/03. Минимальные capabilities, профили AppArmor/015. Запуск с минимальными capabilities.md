# Запуск с минимальными capabilities: Dockerfile nonroot и сброс CAP_SYS_ADMIN

## Условие

Спроектируйте production-grade многоэтапный Dockerfile для Go-микросервиса. Настройте непривилегированного пользователя (USER nonroot:nonroot, UID 10001), сбросьте все избыточные Linux Capabilities, оставив исключительно CAP_NET_BIND_SERVICE (если требуется слушать порт 80). Напишите Go-код, который программно проверяет наличие capabilities у текущего процесса и пытается выполнить операцию, требующую CAP_SYS_ADMIN (например, монтирование или swapon), корректно подтверждая блокировку с ошибкой EPERM.

### Исходная формулировка

**Запуск с минимальными capabilities.**: В Dockerfile задайте `USER nonroot`, удалите все capabilities, кроме необходимых (`NET_BIND_SERVICE` для портов <1024). Проверьте, что приложение не может выполнить `CAP_SYS_ADMIN` операции.

## Теория

По умолчанию процессы в классических Docker-контейнерах запускаются от имени `root` (UID 0). Даже несмотря на изоляцию пространств имен, `root` внутри контейнера имеет множество опасных прав (например, `CAP_CHOWN`, `CAP_FOWNER`, `CAP_KILL`, `CAP_SETUID`).

### Опасность привилегии `CAP_SYS_ADMIN`:
`CAP_SYS_ADMIN` — это 'новый root' в Linux: он дает право монтировать файловые системы (`mount`), изменять параметры пространств имен, конфигурировать cgroups, загружать BPF-программы. Более 70% всех известных уязвимостей побега из контейнера (Container Escape) требуют наличия `CAP_SYS_ADMIN`!

### Стратегия Least Privilege в контейнерах:
1. **Непривилегированный UID/GID:** Никогда не использовать UID 0. Выбирать выделенный UID (например, 10001 / `appuser`).
2. **Сброс всех прав (`cap-drop: ALL`):** По умолчанию контейнер лишается всех дискретных возможностей ядра.
3. **Точечное добавление (`cap-add`):** Добавляется только строго необходимая возможность, например, `NET_BIND_SERVICE` для портов < 1024.
4. **Запрет эскалации (`no-new-privileges: true`):** Блокирует восстановление прав через SUID-файлы.

## Решение по шагам

Напишите многоэтапный `Dockerfile` (Builder stage на `golang:alpine` + Runner stage на `scratch` или `alpine` с созданием пользователя `appuser`).
Напишите Go-программу, проверяющую текущий UID (`os.Getuid()`).
Реализуйте функцию попытки привилегированной операции (вызов `unix.Mount` без аргументов или фиктивное монтирование).
Убедитесь, что ядро Linux возвращает ошибку `syscall.EPERM` (Operation not permitted).
Продемонстрируйте конфигурацию `docker run --user 10001:10001 --cap-drop=ALL --cap-add=NET_BIND_SERVICE`.

## Код решения

**`Dockerfile`**

```dockerfile
# Этап 1: Сборка статического бинарника без CGO
FROM golang:1.23-alpine AS builder
WORKDIR /app
COPY go.mod go.sum* ./
RUN go mod download || true
COPY . .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-w -s" -o server .

# Этап 2: Минималистичный образ с непривилегированным пользователем
FROM alpine:3.20
# Создаем группу и пользователя с фиксированным UID 10001
RUN addgroup -g 10001 -S appgroup && \
    adduser -u 10001 -S appuser -G appgroup

WORKDIR /home/appuser
COPY --from=builder /app/server /usr/local/bin/server

# Переключение на non-root пользователя
USER 10001:10001

EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/server"]
```

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
	"os"
	"syscall"
)

// TestSysAdminOperation пытается выполнить операцию, требующую CAP_SYS_ADMIN.
func TestSysAdminOperation() {
	// Попытка вызова swapon (требует CAP_SYS_ADMIN)
	err := syscall.Swapon("/dev/null", 0)
	if err != nil {
		if errors.Is(err, syscall.EPERM) {
			fmt.Println("🛡️ [SECURITY SUCCESS] Попытка swapon отклонена: EPERM (Operation not permitted).")
			fmt.Println("   Контейнер защищен: CAP_SYS_ADMIN отсутствует!")
			return
		}
		fmt.Printf("Вызов swapon вернул ошибку: %v\n", err)
		return
	}
	log.Fatalf("❌ ОПАСНОСТЬ: swapon выполнился успешно! Процесс обладает CAP_SYS_ADMIN!")
}

func main() {
	uid := os.Getuid()
	gid := os.Getgid()
	fmt.Printf("=== ПРОВЕРКА ПРИВИЛЕГИЙ ПРОЦЕССА ===\n")
	fmt.Printf("UID: %d, GID: %d\n", uid, gid)

	if uid == 0 {
		fmt.Println("⚠️ ВНИМАНИЕ: Процесс запущен от суперпользователя ROOT (UID 0)!")
	} else {
		fmt.Println("✅ Процесс запущен от безопасного непривилегированного пользователя.")
	}

	// Тестирование отсутствия суперпривилегий
	TestSysAdminOperation()
}
```

## Под капотом

В ядре Linux каждое действие, затрагивающее системные ресурсы хоста (монтирование, конфигурация сети, управление памятью ядра), защищено макросом `capable(CAP_SYS_ADMIN)`. Если соответствующий бит в структуре `task_struct->cred->cap_effective` равен 0, ядро немедленно прекращает выполнение сисколла и возвращает код ошибки `-EPERM`. Флаг Docker `--cap-drop=ALL` обнуляет битовые маски `CapInh`, `CapPrm`, `CapEff`, `CapBnd` в момент вызова `execve`.

## Подводные камни

Если в Dockerfile указать `USER nonroot`, но не добавить флаг `--security-opt no-new-privileges:true` при запуске контейнера, злоумышленник при наличии бинарников с установленным битом `SUID root` (например, уязвимости в утилите `pkexec` или старых версиях `mount`) может осуществить локальное повышение привилегий обратно до UID 0. Всегда комбинируйте `USER nonroot` с `no-new-privileges`!

## На собеседовании

Вопрос с собеседования в Wildberries: 'Зачем в Kubernetes использовать Drop: [ALL], если контейнер и так запускается от non-root пользователя UID 10001?' Ответ: 'Пользователь (UID) и возможности ядра (Capabilities) — это ортогональные концепции Linux. Если ядро скомпилировано с поддержкой Ambient Capabilities или процесс наследует capabilities через файловые атрибуты, даже непривилегированный UID может обладать отдельными правами. Директива `drop: [ALL]` гарантирует полное обнуление Capability Bounding Set, делая невозможной активацию любых привилегий ядра.'
