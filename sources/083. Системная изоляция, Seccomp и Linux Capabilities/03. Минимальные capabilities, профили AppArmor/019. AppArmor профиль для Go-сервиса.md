# AppArmor профиль для Go-сервиса: Изоляция конфигурации в Enforce Mode

## Условие

Создайте минималистичный и надежный профиль AppArmor для Go-сервиса, жестко ограничивающий доступ к файловой системе: разрешено только чтение файла конфигурации (/etc/app/config.yaml) и запись в лог-файл (/var/log/app.log). Загрузите профиль в ядро Linux в боевом режиме (Enforce Mode) и продемонстрируйте попытку приложения прочитать непредусмотренный файл (например, /etc/shadow или приватные SSH-ключи), убедившись в получении ошибки Permission denied.

### Исходная формулировка

**AppArmor профиль для Go-сервиса.**: Создайте простой AppArmor профиль, ограничивающий доступ к файловой системе (только чтение конфигурационного файла). Загрузите профиль и запустите сервис в enforce mode.

## Теория

Развертывание Go-сервисов в среде с включенным профилем AppArmor в режиме **Enforce Mode** формирует второй непробиваемый эшелон обороны (Defense-in-Depth).

### Сценарий атаки Path Traversal / Arbitrary File Read:
Представьте уязвимость в HTTP-обработчике отдачи статических файлов:
```go
http.HandleFunc("/static/", func(w http.ResponseWriter, r *http.Request) {
    path := r.URL.Query().Get("file")
    http.ServeFile(w, r, path) // Уязвимо к: ?file=../../../../etc/shadow
})
```
Если сервис запущен без AppArmor от пользователя `app`, а файл `/etc/shadow` случайно имеет права чтения для всех, либо злоумышленник запрашивает `/home/app/.ssh/id_rsa` — происходит утечка критических секретов.

### Действие AppArmor в Enforce Mode:
Профиль AppArmor жестко фиксирует:
- Разрешено чтение: строго `/etc/app/config.yaml r`.
- Любой другой путь в каталоге `/etc/` или домашних папках **отсутствует в белом списке**.
- При попытке `openat('/etc/shadow')` LSM-модуль AppArmor в ядре отклоняет вызов с ошибкой `EACCES (Permission denied)`, а в системный лог отправляется алерт `apparmor='DENIED' operation='open'`. Уязвимость в коде становится абсолютно безвредной!

## Решение по шагам

Напишите профиль AppArmor `apparmor-go-service`.
Настройте чтение бинарника `/usr/bin/my_service mr`.
Укажите точечные правила: `/etc/app/config.yaml r`, `/var/log/app.log rw`.
Скомпилируйте Go-сервис, выполняющий попытку чтения конфигурации и попытку нелегитимного чтения `/etc/shadow`.
Продемонстрируйте команды загрузки: `sudo apparmor_parser -r -W apparmor-go-service`.
Проверьте статус через `sudo aa-status`.

## Код решения

**`apparmor-go-service`**

```bash
# /etc/apparmor.d/my_service
#include <tunables/global>

/usr/bin/my_service flags=(attach_disconnected, enforce) {
  #include <abstractions/base>

  # Исполнение самого бинарника
  /usr/bin/my_service mr,

  # Сетевые операции (исходящие и входящие)
  network inet stream,
  network inet6 stream,

  # Разрешен ТОЛЬКО конкретный файл конфигурации
  /etc/app/config.yaml r,

  # Разрешена запись ТОЛЬКО в файл логов
  /var/log/app.log rw,

  # Все остальные файлы хоста запрещены по умолчанию!
}
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
)

func main() {
	fmt.Println("=== ТЕСТ ИЗОЛЯЦИИ ФАЙЛОВОЙ СИСТЕМЫ ПОД APPARMOR ENFORCE ===")

	// 1. Попытка легитимного чтения разрешенного конфига
	cfgFile := "/etc/app/config.yaml"
	if data, err := os.ReadFile(cfgFile); err == nil {
		fmt.Printf("✅ Конфигурация успешно прочитана (%d байт)\n", len(data))
	} else {
		fmt.Printf("Инфо: Конфиг не найден на диске (ожидаемо в тесте): %v\n", err)
	}

	// 2. Попытка несанкционированного чтения закрытого системного файла
	forbiddenFile := "/etc/shadow"
	fmt.Printf("Попытка несанкционированного чтения %s...\n", forbiddenFile)
	_, err := os.ReadFile(forbiddenFile)
	if err != nil {
		if os.IsPermission(err) {
			fmt.Printf("🛡️ [УСПЕХ БЕЗОПАСНОСТИ] Ядро заблокировало чтение: %v (Permission Denied)\n", err)
			fmt.Println("   AppArmor в режиме Enforce защитил конфиденциальные данные хоста!")
		} else {
			fmt.Printf("Файл недоступен: %v\n", err)
		}
	} else {
		log.Fatalf("❌ КРИТИЧЕСКИЙ ПРОВАЛ: Файл %s прочитан! Профиль AppArmor не работает.", forbiddenFile)
	}
}
```

## Под капотом

Утилита `apparmor_parser` преобразует текстовый профиль в бинарный граф правил (скомпилированный DFA) и загружает его в ядро через псевдофайл `/sys/kernel/security/apparmor/.load`. При вызове `execve('/usr/bin/my_service')` ядро связывает текущую задачу `task_struct` с загруженным профилем безопасности. В ядре перехватчик `vfs_open()` проверяет соответствие запрашиваемого файла графу разрешенных путей.

## Подводные камни

Если ваш Go-сервис использует сборщик мусора или профилировщик pprof, он может попытаться открыть `/proc/self/cmdline` или `/proc/sys/net/core/somaxconn`. Если в профиле AppArmor не подключена абстракция `#include <abstractions/base>`, чтение псевдофайловой системы procfs будет заблокировано, что вызовет панику стандартной библиотеки. Всегда включайте `<abstractions/base>` в профили Go.

## На собеседовании

Вопрос с собеседования в Касперский: 'Как отладить профиль AppArmor, если сервис падает в Enforce-режиме, но при выключенном профиле работает стабильно?' Ответ: '1) Перевести профиль во временный режим обучения: `sudo aa-complain /usr/bin/my_service`. 2) Запустить сервис и сымитировать стандартные сценарии нагрузки. 3) Использовать утилиту `aa-logprof` для интерактивного анализа логов аудита: она покажет все заблокированные пути и предложит внести их в белый список. 4) После обновления правил вернуть режим `sudo aa-enforce /usr/bin/my_service`.'
