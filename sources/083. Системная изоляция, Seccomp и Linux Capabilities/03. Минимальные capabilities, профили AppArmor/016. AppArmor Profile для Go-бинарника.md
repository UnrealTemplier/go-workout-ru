# AppArmor Profile для Go-бинарника: Mandatory Access Control (MAC) vs DAC

## Условие

Разработайте профиль системы принудительного контроля доступа AppArmor для скомпилированного Go-приложения (/usr/local/bin/go_service). Настройте строгие ограничения: разрешение сетевых потоков TCP (network inet stream), использование capability net_bind_service, доступ только для чтения к конфигурационным файлам (/app/config/** r), доступ на чтение/запись/блокировку к рабочей директории данных (/app/data/** rwk) и явный категорический запрет на запись в системные каталоги (deny /etc/** w, deny /bin/** w). Объясните фундаментальную разницу между DAC (дискреционный контроль доступа) и MAC (мандатный контроль доступа).

### Исходная формулировка

**AppArmor Profile.**: Напишите AppArmor profile для Go-бинарника: `network inet stream`, `capability net_bind_service`, `/app/config/** r`, `/app/data/** rwk`, deny `/etc/** w`. Загрузите через `apparmor_parser`. Объясните MAC (Mandatory Access Control) vs DAC: AppArmor ограничивает *программу*, независимо от user ID.

## Теория

В стандартной модели безопасности Linux долгое время доминировал механизм **DAC (Discretionary Access Control — Дискреционный контроль доступа)**:
- Права доступа привязаны к владельцу файла (пользователь, группа, остальные — `rwxrwxrwx`).
- Пользователь `root` обладает абсолютной властью и может игнорировать любые DAC-права.
- Если сервис запущен от пользователя `app`, и сервис взломан, злоумышленник может прочитать **любой** файл в системе, доступный пользователю `app` (или всем пользователям в мире, например `/tmp` или `/etc/hosts`).

### Революция MAC (Mandatory Access Control — Мандатный контроль доступа):
**AppArmor** — это LSM-модуль ядра Linux (Linux Security Module), реализующий мандатный контроль доступа.
- Правила применяются **к самой программе (к пути исполняемого файла)**, а не к пользователю!
- Даже если процесс запущен от суперпользователя `root` (UID 0), ядро Linux не позволит ему прочитать или записать файл, если этот путь не разрешен в профиле AppArmor!
- AppArmor действует на уровне виртуальной файловой системы VFS ядра, перехватывая вызовы до реального обращения к драйверу диска или сети.

## Решение по шагам

Напишите профиль AppArmor `usr.local.bin.go_service`.
Объявите флаги профиля `flags=(attach_disconnected, enforce)`.
Включите стандартные абстракции (`#include <abstractions/base>`, `#include <abstractions/nameservice>`).
Настройте сетевые правила (`network inet stream`, `network inet6 stream`).
Настройте файловые правила: чтение конфига, чтение/запись данных, запрет системных папок.
Продемонстрируйте загрузку профиля утилитой `apparmor_parser -r -W /etc/apparmor.d/usr.local.bin.go_service`.
Напишите Go-код, проверяющий попытку несанкционированной записи в `/etc/malware.txt`.

## Код решения

**`usr.local.bin.go_service`**

```bash
# Профиль AppArmor для промышленного Go-микросервиса
#include <tunables/global>

/usr/local/bin/go_service flags=(attach_disconnected, enforce) {
  # Базовые абстракции ядра (системные библиотеки, зоны времени)
  #include <abstractions/base>
  #include <abstractions/nameservice>

  # Сетевой стек: разрешаем IPv4/IPv6 TCP-сокеты
  network inet stream,
  network inet6 stream,

  # Разрешенные Linux Capabilities
  capability net_bind_service,

  # Доступ к бинарнику (только чтение и исполнение)
  /usr/local/bin/go_service mr,

  # Директория конфигурации: ТОЛЬКО ЧТЕНИЕ
  /app/config/ r,
  /app/config/** r,

  # Директория данных и временных файлов: чтение, запись, создание, блокировка (rwk)
  /app/data/ rw,
  /app/data/** rwk,
  /tmp/ rw,
  /tmp/** rwk,

  # Категорический запрет (Deny rules переопределяют любые allow rules)
  deny /etc/** w,
  deny /bin/** w,
  deny /usr/** w,
  deny /root/** rwklx,
}
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
)

func main() {
	fmt.Println("=== СТАРТ GO-СЕРВИСА ПОД ЗАЩИТОЙ APPARMOR ===")

	// 1. Легитимное действие: чтение файла конфигурации
	cfgPath := "/app/config/app.env"
	if data, err := os.ReadFile(cfgPath); err == nil {
		fmt.Printf("Конфигурация успешно загружена: %s\n", string(data))
	} else {
		fmt.Printf("Конфигурация отсутствует (норма для теста): %v\n", err)
	}

	// 2. Нелегитимное действие: симуляция эксплойта, пытающегося записать файл в /etc
	fmt.Println("Попытка несанкционированной записи в /etc/malicious.conf...")
	err := os.WriteFile("/etc/malicious.conf", []byte("hacked=true"), 0644)
	if err != nil {
		fmt.Printf("🛡️ [APPARMOR INTERCEPT] Запись заблокирована ядром Linux: %v\n", err)
		fmt.Println("   Событие зафиксировано в /var/log/audit/audit.log (apparmor='DENIED')")
	} else {
		log.Fatalf("❌ ОШИБКА: Запись в /etc удалась! AppArmor не активен.")
	}

	// 3. Запуск сетевого сервера (разрешено правилом network inet stream)
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		w.Write([]byte("OK"))
	})
	log.Println("Сервер слушает на :8080...")
	_ = http.ListenAndServe(":8080", nil)
}
```

## Под капотом

AppArmor является LSM-модулем ядра. При открытии файла хук `apparmor_file_open()` в ядре обращается к профилю текущего процесса (`task_struct->security`). Путь к файлу нормализуется относительно корня файловой системы и сопоставляется с детерминированным конечным автоматом (DFA — Deterministic Finite Automaton) профиля. Если найдено правило `deny` или путь отсутствует среди разрешенных, ядро немедленно возвращает ошибку `-EACCES` без обращения к диску.

## Подводные камни

AppArmor разрешает пути на основе **строковых имен файлов (Path-based MAC)**, в отличие от SELinux, использующего индексные дескрипторы inode и метки безопасности (Labels). Это порождает уязвимости при использовании жестких ссылок (Hardlinks) или переименовании каталогов. Также убедитесь, что в Docker или Kubernetes хост-ноды поддерживают AppArmor (демон `apparmor.service` активен в `systemctl status apparmor`).

## На собеседовании

Вопрос с собеседования в Яндекс: 'В чем разница между режимами AppArmor Complain и Enforce?' Ответ: 'В режиме `complain` (режим обучения/аудита) AppArmor фиксирует все нарушения правил профиля в лог аудита (`dmesg`/`auditd`), но **не блокирует** сами операции. Этот режим используется для профилирования нового микросервиса на staging. В режиме `enforce` (режим защиты) ядро жестко блокирует любые несанкционированные системные вызовы с ошибкой EACCES.'
