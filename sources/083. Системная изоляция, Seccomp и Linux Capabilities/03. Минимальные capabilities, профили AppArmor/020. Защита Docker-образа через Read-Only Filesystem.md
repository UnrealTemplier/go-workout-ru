# Защита Docker-образа через Read-Only Filesystem (--read-only)

## Условие

Напишите Go-сервис и конфигурацию Docker-контейнера с флагом --read-only. Покажите, как правильно организовать архитектуру приложения (логирование строго в stdout/stderr, использование tmpfs для временных файлов, хранение состояния в БД или объектном хранилище), чтобы сервис стабильно работал в неизменяемой файловой системе. Продемонстрируйте попытку записи файла на диск и убедитесь в получении системной ошибки Read-only file system (EROFS), блокирующей до 90% автоматизированных эксплойтов.

### Исходная формулировка

**Защита Docker-образа (Read-Only FS)**: Хакеры часто качают скрипты-майнеры через уязвимости, сохраняя их в папку `/tmp`. Запусти свой Docker-контейнер с флагом `--read-only`. Убедись, что сервер работает (если логи пишутся в stdout). Если твой код попытается создать файл на диске, ОС вернет `Read-only file system`. Это ломает 90% автоматизированных эксплойтов!

## Теория

Подавляющее большинство автоматизированных эксплойтов и ботнетов (Mirai, Kinsing криптомайнеры) действуют по жесткому шаблону:
1. Эксплуатация RCE уязвимости в веб-приложении.
2. Сохранение вредоносного скрипта или ELF-бинарника во временную директорию (обычно `/tmp`, `/dev/shm` или `/var/tmp`).
3. Установка прав на исполнение: `chmod +x /tmp/miner`.
4. Запуск вредоносного процесса: `/tmp/miner`.

### Принцип неизменяемой инфраструктуры (Read-Only Root Filesystem):
Флаг Docker `--read-only` (или в Kubernetes `readOnlyRootFilesystem: true`):
- Монтирует корневую файловую систему контейнера с флагом ядра **`MS_RDONLY`**.
- Любая операция создания, модификации или удаления файлов (`open(O_WRONLY|O_CREAT)`, `unlink`, `chmod`) немедленно прерывается ядром с ошибкой **`EROFS (errno 30: Read-only file system)`**.
- Вредоносное ПО **физически не может записать себя на диск**!
- Если сервису жизненно необходимы временные файлы, они выносятся в память через `tmpfs` с обязательными флагами безопасности `noexec,nosuid,nodev`.

## Решение по шагам

Напишите Go HTTP-сервис, пишущий структурированные логи исключительно в `os.Stdout`.
Реализуйте функцию проверки возможности записи на диск (попытка создать файл в `/app/test.txt`).
Обработайте системную ошибку `syscall.EROFS`.
Сформируйте манифест `docker-compose.yml` с параметрами `read_only: true` и безопасным `tmpfs: /tmp:rw,noexec,nosuid,size=32m`.
Проверьте, что сервер успешно обрабатывает входящие HTTP-запросы в режиме `read-only`.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"syscall"
	"time"
)

// AttemptDiskWrite проверяет статус монтирования файловой системы.
func AttemptDiskWrite(path string) {
	err := os.WriteFile(path, []byte("payload"), 0644)
	if err != nil {
		var pathErr *os.PathError
		if errors.As(err, &pathErr) && errors.Is(pathErr.Err, syscall.EROFS) {
			log.Printf("🛡️ [SECURITY ACTIVE] Файловая система смонтирована строго READ-ONLY!\n"+
				"   Попытка записи в '%s' отклонена ядром: %v (EROFS)", path, err)
			return
		}
		log.Printf("Ошибка записи в %s: %v", path, err)
		return
	}
	log.Printf("⚠️ ВНИМАНИЕ: Файл '%s' успешно записан на диск! ФС доступна на запись.", path)
}

func main() {
	// Настройка логов строго в stdout (не на диск!)
	log.SetOutput(os.Stdout)
	log.Println("=== СТАРТ СЕРВИСА В РЕЖИМЕ READ-ONLY ROOT FS ===")

	// Тестирование неизменяемости корневой файловой системы
	AttemptDiskWrite("/test_exploit.bin")

	// Тестирование записи в безопасный tmpfs (если смонтирован)
	tmpPath := "/tmp/legitimate_temp.dat"
	if err := os.WriteFile(tmpPath, []byte("temp cache"), 0600); err == nil {
		log.Printf("✅ Временный файл в памяти tmpfs успешно создан: %s", tmpPath)
		_ = os.Remove(tmpPath)
	}

	mux := http.NewServeMux()
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		fmt.Fprintf(w, `{"status":"ok","timestamp":"%s","readonly":true}`,
			time.Now().Format(time.RFC3339))
	})

	srv := &http.Server{
		Addr:         ":8080",
		Handler:      mux,
		ReadTimeout:  3 * time.Second,
		WriteTimeout: 3 * time.Second,
	}

	log.Println("Сервер слушает на порту :8080...")
	if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
		log.Fatalf("Ошибка сервера: %v", err)
	}
}
```

**`docker-compose.yml`**

```yaml
version: '3.8'

services:
  secure-web:
    build: .
    ports:
      - "8080:8080"
    # Монтирование корневой ФС строго в режиме Read-Only
    read_only: true
    # Временная память в RAM с запретом исполнения бинарников (noexec)
    tmpfs:
      - /tmp:rw,noexec,nosuid,nodev,size=32m
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
```

## Под капотом

Флаг `MS_RDONLY` устанавливается в структуре суперблока точки монтирования VFS (`struct vfsmount`). При попытке любого системного вызова модификации (`open(O_CREAT)`, `truncate`, `rename`, `unlink`) ядро в функции `mnt_want_write()` проверяет флаг `MNT_READONLY`. Если флаг активен, операция немедленно обрывается с возвратом отрицательного кода ошибки `-EROFS` без передачи запроса драйверу файловой системы (ext4/overlay2).

## Подводные камни

Многие популярные сторонние библиотеки Go (например, кэширующие парсеры шаблонов или генераторы PDF) неявно пытаются создать временный файл в `os.TempDir()`. Если контейнер запущен с `--read-only`, но без смонтированного раздела `tmpfs` в директорию `/tmp`, такие библиотеки упадут с паникой прямо в продакшне при первом запросе. Всегда монтируйте `/tmp:rw,noexec,size=64m` в RAM!

## На собеседовании

Вопрос с собеседования в Т-Банк: 'Почему флаг noexec в монтировании tmpfs является критически важным дополнением к readOnlyRootFilesystem?' Ответ: 'Если контейнер запущен с read-only корнем, злоумышленник не может записать майнер в `/bin` или `/app`, но он может записать его в разрешенную для записи временную папку `/tmp`. Если папка `/tmp` смонтирована без флага `noexec`, атакующий сможет вызвать `chmod +x /tmp/payload && /tmp/payload`. Опция `noexec` запрещает ядру выполнять системный вызов `execve` для любых файлов, находящихся на этой точке монтирования, делая запуск вредоносного бинарника из `/tmp` невозможным.'
