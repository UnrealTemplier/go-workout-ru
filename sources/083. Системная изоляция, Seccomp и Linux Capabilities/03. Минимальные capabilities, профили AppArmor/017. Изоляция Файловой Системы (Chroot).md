# Изоляция Файловой Системы (Chroot): Создание легковесной тюрьмы и ограничения chroot vs pivot_root

## Условие

Реализуйте на Go создание изолированного файлового окружения ('тюрьмы') с помощью системного вызова unix.Chroot. Сформируйте минималистичное изолированное дерево каталогов (/var/www/jail), переместите процесс внутрь через unix.Chdir('/') и unix.Chroot. Продемонстрируйте попытку чтения файла /etc/passwd и убедитесь, что процесс физически не видит файлы за пределами своей 'тюрьмы'. Разберите фундаментальные ограничения безопасности chroot и объясните, почему в production-контейнеризации (Docker/runc) вместо chroot используется pivot_root в связке с Mount Namespaces.

### Исходная формулировка

**Изоляция Файловой Системы (Chroot)**: Вызови системный вызов `unix.Chroot("/var/www/jail")`. Программа будет думать, что эта папка — это корень диска `/`. Попытайся прочитать `/etc/passwd`. Ты получишь ошибку, потому что программа больше физически не видит файлы за пределами своей "тюрьмы".

## Теория

Системный вызов **`chroot` (Change Root)** появился еще в Version 7 Unix в 1979 году и стал исторически первой технологией изоляции процессов.

### Механика `chroot()`:
При вызове `chroot(path)` ядро изменяет указатель корневого каталога процесса (`current->fs->root`) на новую директорию.
- Для этого процесса путь `/` теперь указывает на заданную папку (например, `/var/jail`).
- Любые абсолютные пути резолвятся относительно новой вершины дерева каталогов.
- Попытка открыть `/etc/passwd` приведет к открытию `/var/jail/etc/passwd`, а не настоящего системного файла хоста!

### Почему `chroot` НЕ является безопасной песочницей (Security Boundary):
`chroot` сам по себе **не создает барьера безопасности** для привилегированного процесса:
1. **Побег через дескрипторы (File Descriptor Escape):** Если у процесса до вызова `chroot` остался открыт дескриптор директории за пределами тюрьмы, вызов `fchdir(fd)` и цикл `chdir('..')` мгновенно выводят процесс обратно в реальный корень хоста!
2. **Создание вложенного chroot:** Процесс с правами `CAP_SYS_CHROOT` может создать временную директорию, вызвать `chroot('subdir')`, затем `chdir('../../../..')` и вернуть себе доступ ко всему диску.
3. **Общее пространство имен:** Сеть, PID процессов, IPC, память и монтирования остаются общими с хостом.

### Промышленный стандарт: `pivot_root` + `CLONE_NEWNS`:
В современных контейнерах (runc, Docker, containerd) используется связка:
1. Создание нового пространства имен монтирования (**Mount Namespace** через `clone(CLONE_NEWNS)`).
2. Вызов **`pivot_root(new_root, put_old)`**, который атомарно подменяет точку монтирования корня всей VFS.
3. Размонтирование и уничтожение старого корня через `umount2(put_old, MNT_DETACH)`. Побег из такого окружения через дескрипторы математически и физически невозможен!

## Решение по шагам

Создайте временную изолированную директорию через `os.MkdirTemp`.
Создайте внутри изолированное дерево каталогов (например, `app/data`).
Выполните вызов `unix.Chdir(jailDir)`.
Вызовите системный вызов `unix.Chroot(jailDir)` (требуются права root или `CAP_SYS_CHROOT`).
Снова вызовите `unix.Chdir('/')` (обязательное требование стандарта POSIX для сброса рабочего каталога).
Попробуйте прочитать `/etc/passwd` и зафиксируйте ошибку `os.ErrNotExist`.
Продемонстрируйте безопасное создание файлов внутри изолированного пространства.

## Код решения

**`main.go`**

```go
package main

import (
	"errors"
	"fmt"
	"log"
	"os"
	"path/filepath"

	"golang.org/x/sys/unix"
)

// EnterChrootJail изолирует текущий процесс в указанной директории.
func EnterChrootJail(jailPath string) error {
	// 1. Проверяем существование директории
	if _, err := os.Stat(jailPath); err != nil {
		return fmt.Errorf("stat jailPath error: %w", err)
	}

	// 2. Переходим в целевую директорию
	if err := unix.Chdir(jailPath); err != nil {
		return fmt.Errorf("chdir to jailPath error: %w", err)
	}

	// 3. Вызываем системный вызов chroot
	if err := unix.Chroot(jailPath); err != nil {
		return fmt.Errorf("chroot failed (требуется root / CAP_SYS_CHROOT): %w", err)
	}

	// 4. КРИТИЧЕСКИ ВАЖНО: сбросить текущую директорию в новый корень "/"
	// Без этого текущий рабочий каталог останется старым, позволяя побег!
	if err := unix.Chdir("/"); err != nil {
		return fmt.Errorf("chdir to new root error: %w", err)
	}

	return nil
}

func main() {
	fmt.Println("=== ИЗОЛЯЦИЯ ФАЙЛОВОЙ СИСТЕМЫ ЧЕРЕЗ CHROOT ===")

	// Создаем изолированное тестовое дерево каталогов
	jailDir, err := os.MkdirTemp("", "go_chroot_jail_*")
	if err != nil {
		log.Fatalf("Ошибка создания jail dir: %v", err)
	}
	defer os.RemoveAll(jailDir)

	// Создаем фиктивный файл внутри тюрьмы
	internalDataDir := filepath.Join(jailDir, "app")
	_ = os.MkdirAll(internalDataDir, 0755)
	_ = os.WriteFile(filepath.Join(internalDataDir, "secret.txt"), []byte("jail data"), 0644)

	fmt.Printf("1. Изолированная директория подготовлена: %s\n", jailDir)

	// Попытка войти в тюрьму (требует CAP_SYS_CHROOT)
	if err := EnterChrootJail(jailDir); err != nil {
		log.Printf("⚠️ Не удалось применить chroot: %v\n"+
			"Подсказка: запустите с правами root или в привилегированном контейнере.", err)
		return
	}
	fmt.Println("🛡️ Процесс успешно изолирован в chroot-тюрьме!")

	// Попытка прочитать системный /etc/passwd хоста
	fmt.Println("2. Попытка прочитать /etc/passwd хоста изнутри тюрьмы...")
	_, err = os.ReadFile("/etc/passwd")
	if err != nil {
		if errors.Is(err, os.ErrNotExist) {
			fmt.Println("✅ [SUCCESS] Файл /etc/passwd не найден: процесс физически не видит хостовые файлы!")
		} else {
			fmt.Printf("Ошибка чтения: %v\n", err)
		}
	} else {
		log.Fatalf("❌ ПРОВАЛ: /etc/passwd прочитан! Chroot не изолирован.")
	}

	// Проверяем доступность локального файла
	data, err := os.ReadFile("/app/secret.txt")
	if err == nil {
		fmt.Printf("3. Локальный файл /app/secret.txt успешно прочитан: '%s'\n", string(data))
	}
}
```

## Под капотом

Структура `fs_struct` каждого потока в ядре содержит два ключевых указателя на структуры `struct path`: `root` и `pwd`. Системный вызов `sys_chroot()` перезаписывает указатель `root`. Алгоритм резолвинга путей в ядре Linux (`follow_dotdot()` в `fs/namei.c`) проверяет: если текущий dentry равен `current->fs->root`, то переход `..` вверх просто возвращает текущий же dentry, не позволяя подняться выше корня.

## Подводные камни

Если перед вызовом `unix.Chroot()` процесс не вызовет `unix.Chdir('/')`, его указатель `pwd` останется снаружи нового корня! Злоумышленник сможет вызвать `open('../../../etc/shadow')` и прочитать файлы хоста. Всегда выполняйте `chdir('/')` немедленно после любого вызова `chroot()`.

## На собеседовании

Вопрос с собеседования в VK Cloud: 'Почему в рантайме runc для Docker используется pivot_root, а не chroot?' Ответ: 'В классическом chroot ядро сохраняет старую файловую систему смонтированной в том же пространстве имен. Имея root внутри контейнера, злоумышленник может открыть дескриптор файла до chroot и выполнить побег через fchdir. Системный вызов `pivot_root` в связке с Mount Namespace физически перемещает старую корневую файловую систему в отдельную подпапку, которая затем полностью размонтируется через `umount2(put_old, MNT_DETACH)`. В таблице монтирований ядра старый корень хоста перестает существовать для контейнера.'
