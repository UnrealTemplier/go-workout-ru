# Воспроизводимые сборки (Reproducible Builds): Детерминизм бинарников и защита цепочки поставок

## Условие

Изучите концепцию воспроизводимых сборок (Reproducible / Deterministic Builds) в компиляторе Go. Продемонстрируйте, как флаги сборки -trimpath и -ldflags='-buildid=' устраняют влияние абсолютных путей к файловой системе разработчика и случайных временных меток сборщика. Напишите проверочный bash/Go-скрипт, который собирает бинарный файл в двух совершенно разных временных директориях и доказывает их 100% побайтовое совпадение через сравнение контрольных сумм SHA-256.

### Исходная формулировка

**Воспроизводимые сборки (Reproducible Builds).**: Соберите бинарник с флагами `-trimpath` и `-ldflags="-buildid="`. Убедитесь, что два последовательных запуска дают идентичный хэш (с точностью до `mod_timestamp`). Настройте CI для проверки детерминированности сборки.

## Теория

В рамках безопасности цепочки поставок ПО (**Supply Chain Security**) критически важным свойством является **воспроизводимость сборки (Reproducibility)**:
*Любой независимый аудитор, взяв один и тот же исходный код и ту же версию компилятора Go, обязан получить **побайтово идентичный исполняемый файл**!*

### Почему стандартный `go build` недетерминирован:
Если собрать один и тот же код стандартной командой `go build main.go`:
1. **Абсолютные пути в отладочной информации DWARF:** Компилятор вшивает полные пути файлов исходного кода (например, `/home/alice/go-workout/main.go`). На машине CI-сервера путь будет `/builds/runner/main.go`, что приведет к разным контрольным суммам бинарников!
2. **Уникальный Build ID:** Go генерирует уникальный криптографический идентификатор сборки (`buildid`), зависящий от временных меток и промежуточных хэшей действий.

### Золотой стандарт флагов воспроизводимой сборки:
```bash
CGO_ENABLED=0 go build -trimpath -ldflags="-buildid=" -o app main.go
```
- **`-trimpath`:** Удаляет все абсолютные префиксы путей к файлам из бинарника, заменяя их относительными путями модуля.
- **`-ldflags="-buildid="`:** Обнуляет уникальный идентификатор сборки, делая выходной ELF-бинарник полностью детерминированным.
- **`CGO_ENABLED=0`:** Исключает влияние различий во внешних динамических библиотеках glibc хост-системы.

## Решение по шагам

Создайте демонстрационную Go-программу.
Сформируйте скрипт, создающий две изолированные временные папки `/tmp/dir_A` и `/tmp/dir_B`.
Скопируйте исходный код в обе папки.
Соберите бинарник в первой папке с флагами `-trimpath -ldflags='-buildid='`.
Соберите бинарник во второй папке с теми же флагами.
Вычислите хэши `sha256sum /tmp/dir_A/app` и `sha256sum /tmp/dir_B/app`.
Убедитесь, что SHA-256 хэши побайтово совпадают, подтверждая 100% детерминизм.

## Код решения

**`verify_reproducible.sh`**

```bash
#!/bin/bash
set -e

DIR_A=$(mktemp -d /tmp/build_a_XXXXXX)
DIR_B=$(mktemp -d /tmp/build_b_XXXXXX)

trap "rm -rf $DIR_A $DIR_B" EXIT

echo "=== ТЕСТИРОВАНИЕ ВОСПРОИЗВОДИМЫХ СБОРОК (REPRODUCIBLE BUILDS) ==="
echo "Папка A: $DIR_A"
echo "Папка B: $DIR_B"

# Копируем исходный код
cp main.go $DIR_A/
cp main.go $DIR_B/

# Сборка в директории A
cd $DIR_A
CGO_ENABLED=0 go build -trimpath -ldflags="-w -s -buildid=" -o binary_a main.go
HASH_A=$(sha256sum binary_a | awk '{print $1}')

# Сборка в директории B
cd $DIR_B
CGO_ENABLED=0 go build -trimpath -ldflags="-w -s -buildid=" -o binary_b main.go
HASH_B=$(sha256sum binary_b | awk '{print $1}')

echo "--------------------------------------------------"
echo "SHA256 Сборки A: $HASH_A"
echo "SHA256 Сборки B: $HASH_B"
echo "--------------------------------------------------"

if [ "$HASH_A" == "$HASH_B" ]; then
    echo "✅ ИДЕАЛЬНО: Сборки на 100% побайтово идентичны! Детерминизм доказан."
else
    echo "❌ ОШИБКА: Хэши не совпадают! Присутствует недетерминированность."
    exit 1
fi
```

**`main.go`**

```go
package main

import (
	"crypto/sha256"
	"fmt"
	"io"
	"log"
	"os"
)

// PrintBinarySelfHash вычисляет SHA256 собственного исполняемого файла.
func PrintBinarySelfHash() {
	execPath, err := os.Executable()
	if err != nil {
		log.Printf("Не удалось получить путь к бинарнику: %v", err)
		return
	}

	f, err := os.Open(execPath)
	if err != nil {
		log.Printf("Не удалось открыть бинарник: %v", err)
		return
	}
	defer f.Close()

	h := sha256.New()
	if _, err := io.Copy(h, f); err != nil {
		log.Printf("Ошибка вычисления хэша: %v", err)
		return
	}

	fmt.Printf("[REPRODUCIBLE BINARY] SHA256: %x (Path: %s)\n", h.Sum(nil), execPath)
}

func main() {
	fmt.Println("=== ТЕСТ ДЕТЕРМИНИРОВАННОЙ СБОРКИ GO ===")
	PrintBinarySelfHash()
}
```

## Под капотом

Компилятор Go при сборке генерирует секцию ELF `.note.go.buildid`. По умолчанию значение `buildid` представляет собой составную строку, включающую хэш входных параметров и хэш сгенерированного кода пакета. Флаг `-ldflags='-buildid='` принудительно заменяет `buildid` пустой строкой. Флаг `-trimpath` заменяет абсолютные пути в таблицах имен файлов PCLNTAB (`runtime.pclntab`) относительными путями модулей, устраняя любые следы директорий файловой системы сборочного хоста.

## Подводные камни

Если в коде используются переменные, внедряемые во время сборки через `-ldflags='-X main.buildDate=...'` или `-X main.gitCommit=...`, это автоматически разрушает воспроизводимость сборки: два последовательных запуска сборки будут иметь разные временные метки. Для сохранения воспроизводимости используйте стандарт `SOURCE_DATE_EPOCH` (дата последнего коммита из Git) вместо текущего времени `time.Now()`.

## На собеседовании

Вопрос с собеседования в Касперский: 'Зачем независимые аудиторы требуют воспроизводимости сборок при проверке безопасности open-source проектов?' Ответ: 'Воспроизводимая сборка позволяет гарантировать, что опубликованный в релизах скомпилированный бинарный файл был собран **строго из опубликованного исходного кода** без внедрения скрытых закладок (бэкдоров), троянов или вредоносных модулей на стадии сборочного пайплайна (защита от атак компрометации CI/CD в стиле SolarWinds).'
