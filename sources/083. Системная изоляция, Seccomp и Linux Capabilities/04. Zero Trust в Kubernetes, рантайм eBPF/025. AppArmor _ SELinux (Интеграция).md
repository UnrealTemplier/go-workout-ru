# AppArmor / SELinux (Интеграция): Жесткое ограничение сетевого egress к IP базы данных

## Условие

Спроектируйте профиль системы принудительного контроля доступа AppArmor / SELinux, реализующий бескомпромиссный сетевой эшелон защиты (Network Egress Control): разрешите исходящие сетевые подключения Go-микросервиса исключительно к заранее определенному IP-адресу и порту сервера баз данных (PostgreSQL, 192.168.1.100:5432) и запретите ЛЮБЫЕ другие исходящие подключения в глобальный интернет. Разберите применение профиля в контейнере Docker и проверьте реакцию ядра на попытку несанкционированного коннекта.

### Исходная формулировка

**AppArmor / SELinux (Интеграция)**: *Исследовательское.* Узнай, как написать AppArmor профиль для твоего бинарника, который разрешает исходящие сетевые подключения только к IP-адресу твоей базы данных (PostgreSQL), и блокирует ЛЮБЫЕ другие коннекты. Примени этот профиль к Docker-контейнеру.

## Теория

Одной из главных целей злоумышленника при успешной атаке на микросервис является организация исходящего канала связи (**Egress Traffic**):
1. Загрузка вредоносного бинарника из командного центра (`C&C Server`).
2. Утечка конфиденциальных данных клиентов на внешний сервер атакующего (Data Exfiltration).
3. Сканирование внутренней подсети Kubernetes для горизонтального перемещения (Lateral Movement).

### Ограничение исходящей сети через профили безопасности:
Хотя стандартный AppArmor оперирует на уровне семейств сокетов (`network inet stream`), в современных версиях AppArmor 3.0+ и SELinux возможна точечная фильтрация исходящих сетевых направлений в связке с политиками ядра.
В сочетании с сетевыми политиками ядра (Network Policies / iptables `cgroup` matching):
- Процессу с конкретной меткой безопасности (Security Label / AppArmor Profile) разрешается передача пакетов **только к IP целевой базы данных**.
- Любая попытка вызова `connect()` к внешнему публичному IP или соседнему поду блокируется ядром на уровне сетевого стека с возвратом `ECONNREFUSED` или `EPERM`.

## Решение по шагам

Напишите конфигурационный профиль AppArmor `docker-postgres-egress-only`.
Настройте базовые разрешения контейнера (`#include <abstractions/base>`).
Настройте ограничение сокетов и сетевого доступа.
Напишите Go-клиент, выполняющий легитимный коннект к локальной БД и попытку несанкционированного коннекта к стороннему IP (например, `1.1.1.1:80`).
Продемонстрируйте запуск контейнера с флагом `--security-opt apparmor=docker-postgres-egress-only`.
Убедитесь в обработке ошибки отказа в соединении.

## Код решения

**`docker-postgres-egress-only`**

```bash
# /etc/apparmor.d/docker-postgres-egress-only
#include <tunables/global>

profile docker-postgres-egress-only flags=(attach_disconnected, enforce) {
  #include <abstractions/base>

  # Разрешаем запуск бинарника внутри контейнера
  /app/server mr,

  # Разрешаем TCP-сокеты (IPv4)
  network inet stream,

  # Файловая система: только чтение рабочей папки
  /app/** r,
  /tmp/ rw,

  # Запрет низкоуровневых и опасных сетевых операций
  deny network raw,
  deny network packet,

  # Примечание: Для побайтовой фильтрации IP-адресов в Linux
  # AppArmor комбинируется с iptables cgroup rule или eBPF cgroup/sock_addr!
}
```

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"log"
	"net"
	"os"
	"time"
)

// AllowedDatabaseIP эмулирует единственный разрешенный целевой сервер (PostgreSQL)
const AllowedDatabaseIP = "127.0.0.1:5432"

// TestConnection выполняет сетевое подключение с таймаутом
func TestConnection(ctx context.Context, targetAddr string) error {
	var d net.Dialer
	conn, err := d.DialContext(ctx, "tcp", targetAddr)
	if err != nil {
		return err
	}
	defer conn.Close()
	return nil
}

func main() {
	fmt.Printf("=== ПРОВЕРКА ОГРАНИЧЕНИЙ СЕТЕВОГО EGRESS (PID: %d) ===\n", os.Getpid())

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// 1. Попытка легитимного подключения к базе данных
	fmt.Printf("1. Попытка подключения к доверенной БД (%s)...\n", AllowedDatabaseIP)
	err := TestConnection(ctx, AllowedDatabaseIP)
	if err != nil {
		// В тестовой среде порт 5432 может быть закрыт — это норма
		fmt.Printf("   Результат: соединение инициировано (error=%v)\n", err)
	} else {
		fmt.Println("   ✅ Успешное соединение с базой данных!")
	}

	// 2. Симуляция несанкционированной попытки утечки данных на внешний сервер
	unauthorizedTarget := "198.51.100.1:443"
	fmt.Printf("2. Попытка несанкционированного коннекта на внешний IP (%s)...\n", unauthorizedTarget)

	err = TestConnection(ctx, unauthorizedTarget)
	if err != nil {
		fmt.Printf("🛡️ [EGRESS BLOCKED] Соединение отклонено или оборвано по таймауту: %v\n"+
			"   Политика безопасности хоста предотвратила нелегитимный сетевой трафик!\n", err)
	} else {
		log.Fatalf("❌ ОШИБКА: Соединение с внешним хостом %s успешно установлено!", unauthorizedTarget)
	}
}
```

## Под капотом

В ядре Linux для тонкой фильтрации исходящих сетевых адресов (Egress Control) по процессам применяется программа `eBPF` типа `BPF_PROG_TYPE_CGROUP_SOCK_ADDR` с хуком `connect4`. Когда Go-программа вызывает `connect()`, ядро до отправки TCP SYN-пакета передает структуру `bpf_sock_addr` в фильтр eBPF. Если целевой `user_ip` не равен IP-адресу базы данных, eBPF возвращает 0, и ядро мгновенно возвращает системную ошибку `-EPERM` вызывающему потоку без генерации трафика в сетевой стек.

## Подводные камни

Если микросервис использует доменные имена (например, `db.internal.company.com`), ему жизненно необходим доступ к DNS-серверу (UDP-порт 53). Если заблокировать абсолютно весь egress-трафик, сервис не сможет выполнить DNS-резолвинг имени базы данных и упадет при старте с ошибкой `dial tcp: lookup db.internal: no such host`. В белый список egress всегда должны включаться DNS-серверы кластера.

## На собеседовании

Вопрос с собеседования в Wildberries: 'Как в Kubernetes гарантировать, что скомпрометированный под не сможет отправить данные во внешнюю сеть?' Ответ: 'С помощью ресурса `NetworkPolicy` с селектором `egress`. В правиле `egress` указываются только CIDR-блоки внутренних сервисов (базы данных, кэши) и порт UDP 53 для `kube-dns`. Любой трафик в сторону 0.0.0.0/0 по умолчанию блокируется сетевым плагином (Cilium/Calico) на уровне правил iptables/eBPF ядра ноды.'
