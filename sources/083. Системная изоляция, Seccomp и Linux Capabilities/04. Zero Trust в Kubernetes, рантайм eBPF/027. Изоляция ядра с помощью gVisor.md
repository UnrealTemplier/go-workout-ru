# Изоляция ядра с помощью gVisor: Архитектурное сравнение runc vs runsc и защита от Container Escape

## Условие

Напишите глубокое инженерно-аналитическое исследование и архитектурное сравнение стандартного рантайма Docker (runc) и песочницы gVisor (рантайм runsc от Google). Разберите, как gVisor перехватывает системные вызовы гостевого приложения и обрабатывает их в изолированном пользовательском пространстве на Go (ядро Sentry), формируя непробиваемую границу доверия между контейнером и реальным ядром хост-системы. Объясните, почему gVisor нейтрализует 100% атак класса Container Escape и как запустить Go-микросервис под управлением runsc в Docker/Kubernetes.

### Исходная формулировка

**Изоляция ядра с помощью `gVisor`**: Напишите аналитическое эссе-сравнение стандартного рантайма Docker (`runc`) и песочницы `gVisor` (рантайм `runsc` от Google) [670]. Объясните, как gVisor перехватывает системные вызовы контейнера и обрабатывает их в пользовательском пространстве на Go (ядро Sentry), полностью изолируя контейнер от реального ядра хост-системы и защищая инфраструктуру от атак класса Container Escape (побег из контейнера на хост) [670].

## Теория

В стандартных контейнерах Docker/Kubernetes используется OCI-рантайм **`runc`**:
- Контейнер разделяет **одно общее ядро хоста**.
- Если злоумышленник обнаружит уязвимость в реализации системного вызова ядра Linux (например, Use-After-Free в подсистеме io_uring, eBPF verifier flaw, Dirty Pipe CVE-2022-0847), он получает доступ к кольцу 0 (Ring 0) хоста и захватывает управление всей физической нодой!

### Революция `gVisor` (Google runsc):
**gVisor** — это открытая песочница виртуализации уровня приложений, написанная инженерами Google на языке **Go**.
gVisor выступает в роли **пользовательского ядра-посредника (Application Kernel)** между приложением и настоящим ядром хоста:

1. **Архитектура Sentry (Ядро на Go):**
   - Все системные вызовы процесса-жертвы (например, `open`, `read`, `socket`, `fork`) **перехватываются** механизмом виртуализации (через KVM или ptrace).
   - Вызовы **НЕ передаются в ядро хоста**! Вместо этого они эмулируются кодом `Sentry`, написанным на безопасном языке Go с защитой памяти (Memory Safety).
   - В ядре Sentry реализовано более **300 системных вызовов Linux** и полноценный сетевой стек **Netstack** (также написанный на чистом Go).

2. **Процесс Gofer (Файловый посредник):**
   - Файловые операции изолируются отдельным процессом `Gofer`, общающимся с `Sentry` через протокол 9P/LHP.

3. **Непробиваемая защита от Container Escape:**
   - Даже если хакер использует эксплойт против ядра Linux, эксплойт попадает в песочницу Sentry на Go, которая не содержит Си-ошибок работы с памятью и не дает доступа к реальному хостовому ядру!

## Решение по шагам

Установите gVisor runtime (`runsc`) на хостовую систему.
Настройте Docker daemon (`/etc/docker/daemon.json`) для поддержки рантайма `runsc`.
Напишите Go-программу, инспектирующую свое окружение (считывание `/proc/version` и сравнение характеристик).
Запустите контейнер в стандартном режиме: `docker run --rm alpine uname -a`.
Запустите контейнер под управлением gVisor: `docker run --runtime=runsc --rm alpine uname -a`.
Зафиксируйте кардинальную разницу в выводе версии ядра (gVisor эмулирует Linux-совместимую среду).

## Код решения

**`daemon.json`**

```json
{
  "runtimes": {
    "runsc": {
      "path": "/usr/local/bin/runsc",
      "runtimeArgs": [
        "--platform=kvm",
        "--network=sandbox"
      ]
    }
  }
}
```

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
	"strings"
)

// DetectRuntimeEnvironment определяет, работает ли приложение под защитой gVisor.
func DetectRuntimeEnvironment() {
	data, err := os.ReadFile("/proc/version")
	if err != nil {
		log.Printf("Не удалось прочитать /proc/version: %v", err)
		return
	}

	versionStr := string(data)
	fmt.Println("=== АНАЛИЗ ОКРУЖЕНИЯ ЯДРА ОПЕРАЦИОННОЙ СИСТЕМЫ ===")
	fmt.Printf("Вывод /proc/version:\n%s\n", strings.TrimSpace(versionStr))

	if strings.Contains(strings.ToLower(versionStr), "gvisor") {
		fmt.Println("🛡️ [GVISOR DETECTED] Приложение изолировано в песочнице Google gVisor (runsc)!")
		fmt.Println("   Все системные вызовы эмулируются ядром Sentry на языке Go.")
		fmt.Println("   Побег из контейнера (Container Escape) на хост-ноду математически блокирован.")
	} else {
		fmt.Println("⚠️ [STANDARD RUNTIME] Приложение запущено под стандартным runc.")
		fmt.Println("   Ядро Linux разделяется с хост-системой.")
	}
}

func main() {
	DetectRuntimeEnvironment()
}
```

**`k8s-gvisor-runtimeclass.yaml`**

```yaml
# Настройка gVisor в Kubernetes через RuntimeClass
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
---
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-workload-pod
spec:
  # Назначение изолированного рантайма gVisor
  runtimeClassName: gvisor
  containers:
  - name: untrusted-app
    image: my-untrusted-go-code:latest
    resources:
      limits:
        memory: "256Mi"
        cpu: "1"
```

## Под капотом

gVisor использует платформы аппаратной виртуализации KVM (`--platform=kvm`) или системный перехват ptrace (`--platform=ptrace`). В режиме KVM gVisor создает легковесную виртуальную машину, где Sentry работает на нулевом кольце виртуализированного CPU, а приложение пользователя — на третьем кольце. Системные вызовы процессора `syscall` генерируют VM-Exit прерывание, мгновенно перехватываемое Sentry без единого обращения к хостовому ядру Linux.

## Подводные камни

Плата за абсолютную безопасность gVisor — накладные расходы на системные вызовы (Syscall Overhead). Операции, требующие частого переключения контекста и интенсивного файлового ввода-вывода (например, компиляция исходного кода или базы данных с постоянным чтением мелких файлов), могут работать в gVisor в 1.5–2.5 раза медленнее, чем в нативном runc. Для чисто сетевых микросервисов на Go накладные расходы минимальны (менее 5–10%).

## На собеседовании

Вопрос с архитектурного комитета Ozon: 'В каких сценариях enterprise-систем использование gVisor является строго обязательным?' Ответ: 'В сценариях исполнения **недоверенного кода клиентов (Multi-tenant Untrusted Code Execution)**: например, в облачных сервисах Function-as-a-Service (AWS Lambda / Cloud Functions), платформах интерактивного онлайн-обучения программированию, песочницах запуска сторонних плагинов и обработчиках загруженных пользователями неизвестных PDF/медиафайлов. Если клиентский код содержит 0-day эксплойт побега из контейнера, gVisor полностью локализует атаку внутри пользовательского процесса Sentry на Go.'
