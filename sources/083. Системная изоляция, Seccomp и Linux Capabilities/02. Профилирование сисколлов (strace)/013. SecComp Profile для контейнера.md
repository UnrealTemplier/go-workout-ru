# SecComp Profile для контейнера: Запрет опасных вызовов ptrace, mount, setns, unshare

## Условие

Сформируйте production-ready профиль безопасности Seccomp для высоконагруженных контейнеризованных микросервисов. Настройте defaultAction: SCMP_ACT_ERRNO. Внесите в список строго разрешенных вызовы accept4, read, write, epoll_wait, futex, mmap, munmap, clone, exit, exit_group, rt_sigreturn, getrandom. Категорически исключите вызовы побега из контейнера и эскалации привилегий: execve, execveat, ptrace, mount, umount2, chroot, setns, unshare, keyctl, bpf. Объясните роль каждого заблокированного вызова в векторах атак Container Escape.

### Исходная формулировка

**SecComp Profile для контейнера.**: Напишите JSON SecComp profile для Docker: `defaultAction: SCMP_ACT_ERRNO`, разрешить `accept4`, `read`, `write`, `epoll_wait`, `futex`, `mmap`, `munmap`, `clone`, `exit`, `exit_group`, `rt_sigreturn`, `getrandom`. Запретить `execve`, `execveat`, `ptrace`, `mount`, `umount2`, `chroot`, `setns`, `unshare`. Объясните, почему `execve` — критично (RCE prevention).

## Теория

Контейнеры в Linux не являются полноценной виртуализацией: они разделяют **одно общее ядро хоста** с остальной операционной системой. Изоляция обеспечивается механизмами пространств имен (Namespaces), контрольных групп (cgroups) и ограниченных привилегий (Capabilities).

### Анатомия критических системных вызовов эскалации привилегий:
1. **`setns` и `unshare`:** Переключение и создание новых пространств имен. Позволяют злоумышленнику выйти из контейнерного `pid` или `mnt` неймспейса при слабой изоляции `user_ns`.
2. **`mount` и `umount2`:** Монтирование файловых систем. Эксплуатируются для перемонтирования хостовой корневой ФС в режим записи (`rw`), либо создания вредоносных procfs-узлов.
3. **`chroot`:** Смена корня процесса. Легко обходится через создание вложенных директорий и относительные пути `..`, если не заблокирован.
4. **`ptrace`:** Отладка процессов. Позволяет читать и модифицировать регистры и память соседних процессов на хосте при совместном PID-неймспейсе.
5. **`keyctl`:** Подсистема хранения криптографических ключей ядра. Источник множества критических уязвимостей ядра локального повышения привилегий (LPE).
6. **`bpf`:** Загрузка BPF-программ. Позволяет исполнять произвольный код в контексте ядра Linux при наличии уязвимостей в верификаторе ядра eBPF.

## Решение по шагам

Создайте файл профиля `hardened-production-seccomp.json`.
Задайте базовые метаданные OCI Seccomp: `defaultAction: SCMP_ACT_ERRNO`.
Добавьте архитектуры `SCMP_ARCH_X86_64` и `SCMP_ARCH_AARCH64`.
Сформируйте группу `SCMP_ACT_ALLOW` со всеми необходимыми сисколлами для сетевого Go-сервиса.
Проверьте отсутствие в списке системных вызовов `ptrace`, `mount`, `umount2`, `chroot`, `setns`, `unshare`, `execve`, `bpf`.
Покажите пример применения профиля в Dockerfile и compose-манифесте.

```yaml

services:
  secure-api:
    image: my-go-backend:latest
    restart: always

      - no-new-privileges:true
      - seccomp:hardened-production-seccomp.json
```

## Под капотом

При установке флага `no-new-privileges: true` ядро Linux гарантирует, что процесс и его потомки никогда не смогут получить дополнительные привилегии через бинарники с битами `SUID` или `SGID` (например, утилиты `sudo`, `passwd`, `su`). В сочетании с профилем Seccomp, запрещающим `execve`, это создает непробиваемую песочницу: даже при наличии root-прав внутри контейнера злоумышленник не сможет запустить сторонний бинарник или повысить привилегии на хосте.

## Подводные камни

Обратите внимание на вызов `tgkill` в белом списке: в Go 1.14+ планировщик использует вызов `tgkill(pid, tid, SIGURG)` для асинхронного вытеснения зациклившихся горутин (Non-cooperative goroutine preemption). Если исключить `tgkill` из разрешенных сисколлов, горутина с бесконечным циклом без вызовов функций захватит поток ОС (`M`) и заморозит планировщик GMP, вызвав необъяснимое зависание сервиса.

## На собеседовании

Вопрос с собеседования в Касперский: 'Как запрет системного вызова ptrace в seccomp защищает от атаки Dirty COW (CVE-2016-5195) и аналогичных атак на память ядра?' Ответ: 'Многие эксплойты для состояния гонки в подсистеме памяти ядра используют системный вызов `ptrace(PTRACE_POKETEXT)` для циклической перезаписи страниц памяти, отображенных только для чтения (COW-страницы). Отсутствие системного вызова `ptrace` лишает атакующего стандартного интерфейса внедрения шеллкода в чужие адресные пространства и существенно затрудняет эксплуатацию уязвимостей ядра.'
