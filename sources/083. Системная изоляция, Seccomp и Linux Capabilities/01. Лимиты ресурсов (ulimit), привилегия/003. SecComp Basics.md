# SecComp Basics: декларативная фильтрация системных вызовов через libseccomp-golang

## Условие

Разработайте Go-программу с использованием пакета github.com/seccomp/libseccomp-golang, которая при старте инициализирует фильтр Seccomp в режиме Whitelist (действие по умолчанию: завершение процесса SIGSYS). Разрешите только критически важные системные вызовы: read, write, exit, exit_group, rt_sigreturn, epoll_wait, accept4, close. Продемонстрируйте, что легитимный вывод в консоль работает, но при попытке вызова os.Open (системный вызов openat) ядро Linux немедленно убивает процесс с сигналом SIGSYS.

### Исходная формулировка

**SecComp Basics (libseccomp-golang).**: Напишите Go-программу, которая через `github.com/seccomp/libseccomp-golang` разрешает только `read`, `write`, `exit`, `exit_group`, `rt_sigreturn`, `epoll_wait`, `accept4`, `close`. При попытке `os.Open` (syscall `openat`) — процесс получает `SIGSYS` и умирает. Объясните whitelist-подход.

## Теория

**Seccomp (Secure Computing Mode)** — это механизм подсистемы безопасности ядра Linux, появившийся в ядре 2.6.12 и кардинально расширенный в ядре 3.5 (Seccomp-BPF). Он выполняет роль **файрвола прикладных системных вызовов (Syscall Firewall)**.

### Философия Whitelist vs Blacklist:
- **Blacklist (Черный список):** Блокировать опасные вызовы (`execve`, `ptrace`, `reboot`). Подход фундаментально ущербен: при обновлении ядра появляются новые системные вызовы (например, `clone3`, `openat2`, `io_uring_enter`), через которые злоумышленник обходит запрет.
- **Whitelist (Белый список / Нулевое доверие):** Действие по умолчанию — `ActKillProcess` или `ActTrap`. Разрешаются **только** вызовы, внесенные в жесткий перечень. Любой иной сисколл мгновенно уничтожает процесс на уровне ядра ОС до того, как его аргументы будут обработаны!

### Архитектура Seccomp:
Фильтр транслируется в байткод классического фильтра пакетов **cBPF (classic Berkeley Packet Filter)**. Ядро проверяет каждый системный вызов процесса в кольце 0. Если номер вызова не совпадает с разрешенным списком, BPF-машина возвращает `SECCOMP_RET_KILL_PROCESS` (или посылает сигнал `SIGSYS` потоку).

## Решение по шагам

Импортируйте пакет `github.com/seccomp/libseccomp-golang`.
Инициализируйте фильтр Seccomp с действием по умолчанию `seccomp.ActKillProcess`.
Добавьте в белый список системные вызовы: `read`, `write`, `exit`, `exit_group`, `rt_sigreturn`, `fstat`, `futex`, `nanosleep`.
Загрузите фильтр в ядро операционной системы с помощью `filter.Load()`.
Выполните разрешенную операцию (вывод в `os.Stdout`).
Попробуйте вызвать `os.Open('secret.txt')` (вызов `openat`) и убедитесь, что процесс убит сигналом SIGSYS.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"

	libseccomp "github.com/seccomp/libseccomp-golang"
)

// InitSeccompWhitelist настраивает строгий белый список системных вызовов.
func InitSeccompWhitelist() error {
	// Действие по умолчанию: мгновенно уничтожить процесс
	filter, err := libseccomp.NewFilter(libseccomp.ActKillProcess)
	if err != nil {
		return fmt.Errorf("NewFilter error: %w", err)
	}

	// Белый список вызовов, жизненно необходимых для консольного вывода и завершения
	allowedSyscalls := []string{
		"write",
		"read",
		"exit",
		"exit_group",
		"rt_sigreturn",
		"futex",
		"mmap",
		"munmap",
		"fstat",
		"getrandom",
	}

	for _, name := range allowedSyscalls {
		sysID, err := libseccomp.GetSyscallFromName(name)
		if err != nil {
			// На некоторых архитектурах сисколл может отсутствовать, пропускаем
			continue
		}
		if err := filter.AddRule(sysID, libseccomp.ActAllow); err != nil {
			return fmt.Errorf("failed to allow %s: %w", name, err)
		}
	}

	// Загрузка фильтра в ядро Linux
	if err := filter.Load(); err != nil {
		return fmt.Errorf("filter.Load failed: %w", err)
	}
	return nil
}

func main() {
	fmt.Println("[INIT] Инициализация безопасного окружения Seccomp...")

	if err := InitSeccompWhitelist(); err != nil {
		log.Fatalf("Ошибка загрузки Seccomp: %v", err)
	}

	fmt.Println("✅ [SECCOMP ACTIVE] Разрешены только write, read, futex и exit.")
	fmt.Println("Попытка открыть файл на диске через os.Open (openat syscall)...")

	// Системный вызов openat ЗАПРЕЩЕН фильтром.
	// Ядро Linux немедленно убьет процесс с сигналом Bad system call (SIGSYS / exit code 159).
	_, err := os.Open("/etc/passwd")
	if err != nil {
		fmt.Printf("Файл не открыт: %v\n", err)
	}

	fmt.Println("Эта строка НИКОГДА не выполнится, так как процесс уничтожен ядром!")
}
```

**`run.sh`**

```bash
#!/bin/bash
# Запуск демонстрации
# Требуется установленный libseccomp-dev в системе: sudo apt install libseccomp-dev
go run main.go
# Ожидаемый вывод:
```

## Под капотом

При вызове `filter.Load()` библиотека `libseccomp` вызывает системный вызов `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)`. Это обязательное требование ядра: процесс без флага `no_new_privs` не может применить seccomp-фильтр без прав `CAP_SYS_ADMIN`, чтобы исключить эскалацию привилегий через `setuid`-бинарники. Затем вызывается `seccomp(SECCOMP_SET_MODE_FILTER, 0, &prog)`. Байткод cBPF связывается со структурой `task_struct` текущего процесса и наследуется всеми дочерними потоками и горутинами.

## Подводные камни

Go runtime чрезвычайно чувствителен к системным вызовам! Если вы забудете добавить `futex`, `clone` или `rt_sigreturn`, процесс упадет при первой же смене контекста планировщика или сборке мусора (GC). Также Go 1.14+ использует асинхронную вытесняющую многозадачность на сигналах `SIGURG`, требующую вызовов `rt_sigaction` и `tgkill`.

## На собеседовании

Вопрос с собеседования в Лабораторию Касперского: 'В чем разница между Seccomp действиями SECCOMP_RET_KILL_PROCESS и SECCOMP_RET_ERRNO?' Ответ: '`SECCOMP_RET_KILL_PROCESS` немедленно завершает всю группу потоков процесса без возможности обработки ошибки в userspace, оставляя след в audit-логе ядра (лучший выбор против RCE эксплойтов). `SECCOMP_RET_ERRNO` не убивает процесс, а заставляет ядро вернуть симулированную ошибку (например, `EPERM` или `ENOSYS`), позволяя приложению грациозно обработать недоступность системного вызова.'
