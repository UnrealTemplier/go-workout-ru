# Введение в Seccomp (Secure Computing Mode): Аудит и режим SECCOMP_RET_LOG

## Условие

Изучите установку и работу библиотеки github.com/seccomp/libseccomp-golang. Реализуйте конфигурацию Seccomp в режиме аудита (Action SECCOMP_RET_LOG), при котором вызовы не блокируются аварийно, а логируются в auditd / dmesg ядра Linux. Объясните, почему режим логирования является критически важным этапом профилирования перед переводом продакшн-сервиса в жесткий режим блокировки SECCOMP_RET_KILL_PROCESS.

### Исходная формулировка

**Введение в Seccomp (Secure Computing Mode)**: Seccomp — это файрвол для системных вызовов (syscalls). Установи CGO-библиотеку `github.com/seccomp/libseccomp-golang`.

## Теория

Внедрение строгой Seccomp-политики (Default: Kill) в продакшн-окружении сопряжено с колоссальным риском: если инженер забудет хотя бы один системный вызов, используемый стандартной библиотекой Go, сервис упадет с паникой или будет убит ядром прямо под нагрузкой.

### Режимы действия Seccomp действий (Action Codes):
1. **`SECCOMP_RET_KILL_PROCESS` (ActKillProcess):** Убивает процесс мгновенно. Нулевой шанс компрометации, но максимальный риск отказа в обслуживании при ложных срабатываниях.
2. **`SECCOMP_RET_ERRNO` (ActErrno):** Возвращает ошибку (например, `EPERM`).
3. **`SECCOMP_RET_LOG` (ActLog):** Появился в ядре Linux 4.14. Системный вызов **разрешается к выполнению**, но ядро фиксирует запись в подсистеме аудита Linux (`/var/log/audit/audit.log` или вывод команды `dmesg`).

### Стратегия безопасного внедрения Seccomp в BigTech:
- **Фаза 1 (Staging / Audit Mode):** Приложение запускается с действием по умолчанию `ActLog`. Сервис прогоняется под полным синтетическим нагрузочным тестированием и end-to-end тестами.
- **Фаза 2 (Анализ логов auditd):** С помощью утилит `ausearch -m SECCOMP` или `audit2allow` собираются все системные вызовы, попавшие в лог.
- **Фаза 3 (Enforce Mode):** Формируется финальный профиль Seccomp, и действие по умолчанию переключается на `ActKillProcess`.

## Решение по шагам

Подключите библиотеку `libseccomp-golang`.
Инициализируйте фильтр Seccomp с действием по умолчанию `libseccomp.ActLog`.
Добавьте запрет конкретного системного вызова (например, `mkdir`) с действием `libseccomp.ActLog`.
Загрузите фильтр в ядро.
Выполните вызов `os.Mkdir` и убедитесь, что директория успешно создалась, а событие зафиксировано.
Покажите, как извлекать события через утилиты `journalctl` и `ausearch`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"

	libseccomp "github.com/seccomp/libseccomp-golang"
)

// InitSeccompAuditMode настраивает логирование системных вызовов в ядре.
func InitSeccompAuditMode() error {
	// Создаем фильтр: по умолчанию разрешать все вызовы
	filter, err := libseccomp.NewFilter(libseccomp.ActAllow)
	if err != nil {
		return fmt.Errorf("NewFilter failed: %w", err)
	}

	// Для системного вызова mkdirat устанавливаем режим ActLog
	// Вызов выполнится успешно, но ядро запишет предупреждение в auditd!
	sysID, err := libseccomp.GetSyscallFromName("mkdirat")
	if err == nil {
		if err := filter.AddRule(sysID, libseccomp.ActLog); err != nil {
			return fmt.Errorf("failed to set ActLog for mkdirat: %w", err)
		}
	}

	if err := filter.Load(); err != nil {
		return fmt.Errorf("filter.Load failed: %w", err)
	}
	return nil
}

func main() {
	fmt.Println("=== SECCOMP: ДЕМОНСТРАЦИЯ РЕЖИМА АУДИТА (ActLog) ===")

	if err := InitSeccompAuditMode(); err != nil {
		log.Printf("[ВНИМАНИЕ] Не удалось активировать Seccomp (требуются права или Linux 4.14+): %v", err)
		return
	}
	fmt.Println("✅ Фильтр Seccomp загружен в ядро в режиме аудита (ActLog).")

	testDir := "audit_test_dir"
	defer os.Remove(testDir)

	// Выполняем mkdirat — он должен сработать, но оставить след в логах ядра
	err := os.Mkdir(testDir, 0755)
	if err != nil {
		log.Fatalf("Ошибка создания директории: %v", err)
	}

	fmt.Printf("Директория '%s' успешно создана!\n", testDir)
	fmt.Println("Проверьте системный журнал командой: dmesg | grep -i seccomp")
	fmt.Println("Или через auditctl: ausearch -m SECCOMP -ts recent")
}
```

## Под капотом

Действие `SECCOMP_RET_LOG` обрабатывается функцией `__secure_computing()` в файле `kernel/seccomp.c`. Если фильтр возвращает данное значение, ядро вызывает `audit_seccomp(this_syscall, SIGSYS, SECCOMP_RET_LOG)`. Запись передается в подсистему `kauditd`, которая помещает сообщение `type=SECCOMP` в кольцевой буфер аудита. При этом код выполнения продолжается без задержек и ошибок.

## Подводные камни

Если в системе не запущен демон `auditd` или в `/proc/sys/net/core/bpf_jit_enable` отключен JIT, сбор большого количества логов аудита при высокой частоте запросов (RPS) может вызвать деградацию производительности из-за накладных расходов на запись в журнал ядра. Режим `ActLog` предназначен для стейджинга, а не для постоянного включения в HighLoad продакшне.
