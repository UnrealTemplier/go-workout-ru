# Анатомия nil-указателя и перехват паники nil pointer dereference

## Условие

Изучите, как работает `nil`-указатель: создайте указатель на структуру, не инициализируйте его и попробуйте обратиться к полю (поймайте panic).

## Теория

**Nil Pointer Dereference:**
- Неинициализированный указатель имеет значение `nil` (адрес `0x0`);
- Попытка чтения или записи по `nil`-указателю вызывает исключение защиты памяти процессора (Page Fault), которое рантайм Go преобразует в панику.

## Решение по шагам

1. Объявляем `var u *User` (nil).
2. Заворачиваем доступ к полю в `defer + recover`.
3. Ловим панику.

## Код решения

**`main.go`**

```go
package main

import "fmt"

type User struct {
	Name string
}

func main() {
	var u *User // nil-указатель

	fmt.Printf("Состояние u: %v (isNil = %t)\n", u, u == nil)

	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("⚠️ Перехвачена паника: %v\n", r)
			}
		}()

		// Разыменование nil приводит к панике:
		fmt.Println(u.Name)
	}()
}
```

**`Терминал`**

```bash
go run main.go
# Состояние u: <nil> (isNil = true)
# ⚠️ Перехвачена паника: runtime error: invalid memory address or nil pointer dereference
```

## Под капотом

Доступ к адресу `0x0` блокируется механизмом виртуальной памяти ОС (MMU).

## Подводные камни

- Вызов метода у `nil`-указателя: если метод читает поля `u.Name`, произойдет паника, но если метод не обращается к полям получателя, он выполнится успешно!

## На собеседовании

**Вопрос с собеседования:** «Может ли метод с pointer receiver успешно выполниться для `nil`-указателя?»
**Ответ:** ДА! Если внутри метода нет обращения к полям структуры (`if u == nil { return "empty" }`), вызов `u.String()` отработает без паники.
