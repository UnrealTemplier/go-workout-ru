# Возврат указателя на локальную переменную: Escape Analysis и безопасность памяти в Go

## Условие

Напишите функцию, которая возвращает указатель на локальную переменную функции. Убедитесь, что Go корректно обрабатывает это (escape analysis).

## Теория

**Escape-анализ (Escape Analysis) в компиляторе Go:**
- В C/C++ возврат указателя на локальную переменную стека приводит к **висячему указателю (Dangling Pointer)** и крашу `Segmentation Fault`;
- Компилятор Go анализирует граф потока данных: если переменная «убегает» (escapes) за пределы функции, она **автоматически аллоцируется в куче (Heap)**;
- Это гарантирует 100% безопасность памяти (Memory Safety).

## Решение по шагам

1. Пишем `NewCounter() *int`.
2. Создаем локальную переменную `count := 100`.
3. Возвращаем `&count`.
4. Проверяем работу в `main()`.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func NewCounter() *int {
	count := 100 // Локальная переменная
	return &count // В C это привело бы к Undefined Behavior, но в Go это БЕЗОПАСНО!
}

func main() {
	ptr := NewCounter()
	fmt.Printf("Значение из кучи: %d (адрес: %p)\n", *ptr, ptr)

	*ptr += 50
	fmt.Printf("После инкремента: %d\n", *ptr)
}
```

**`Терминал`**

```bash
go run main.go
# Значение из кучи: 100 (адрес: 0xc000018030)
# После инкремента: 150
```

## Под капотом

Флаг сборки `go build -gcflags="-m"` выводит диагностику: `moved to heap: count`.

## Подводные камни

- Неконтролируемый побег тяжелых структур в кучу увеличивает нагрузку на Garbage Collector.

## На собеседовании

**Вопрос с собеседования:** «Как проверить, какие переменные убегают в кучу при компиляции Go-проекта?»
**Ответ:** Собрать бинарник с флагом escape-анализа `go build -gcflags="-m -m" main.go`.
