# Сетевой бенчмаркер производительности TCP Load Tester (Latency & RPS)

## Условие

Напиши **TCP load tester**: клиент устанавливает N соединений и отправляет M сообщений в секунду каждое. Измерь: latency (время ответа), throughput (сообщений/сек), ошибки соединения. Выведи статистику.

## Теория

Архитектура нагрузочного сетевого тестировщика (Load Tester / Benchmarker): генерирует заданный профиль нагрузки, замеряет гистограмму времени отклика (Latency Percentiles P50/P99) и пропускную способность (Requests Per Second — RPS).

## Решение по шагам

1. Запустим оптимизированный TCP Echo сервер.
2. Запустим 10 параллельных соединений по 100 запросов каждое.
3. Замерим общее время и средний RTT.
4. Выведем сетевую статистику.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"net"
	"sync"
	"sync/atomic"
	"time"
)

func main() {
	l, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer l.Close()

	// Быстрый эхо-сервер
	go func() {
		for {
			conn, err := l.Accept()
			if err != nil {
				return
			}
			go func(c net.Conn) {
				defer c.Close()
				buf := make([]byte, 64)
				for {
					n, err := c.Read(buf)
					if err != nil {
						return
					}
					_, _ = c.Write(buf[:n])
				}
			}(conn)
		}
	}()

	time.Sleep(10 * time.Millisecond)

	const numConns = 10
	const msgsPerConn = 50
	const totalRequests = numConns * msgsPerConn

	var completedRequests atomic.Int64
	var totalLatencyNano atomic.Int64

	startBench := time.Now()
	var wg sync.WaitGroup
	wg.Add(numConns)

	for i := 0; i < numConns; i++ {
		go func() {
			defer wg.Done()
			conn, err := net.Dial("tcp", l.Addr().String())
			if err != nil {
				return
			}
			defer conn.Close()

			buf := make([]byte, 64)
			msg := []byte("PING")

			for m := 0; m < msgsPerConn; m++ {
				t0 := time.Now()
				_, _ = conn.Write(msg)
				_, _ = conn.Read(buf)
				rtt := time.Since(t0)

				totalLatencyNano.Add(rtt.Nanoseconds())
				completedRequests.Add(1)
			}
		}()
	}

	wg.Wait()
	duration := time.Since(startBench)

	completed := completedRequests.Load()
	rps := float64(completed) / duration.Seconds()
	avgLatency := time.Duration(totalLatencyNano.Load() / completed)

	fmt.Println("=== РЕЗУЛЬТАТЫ TCP LOAD TESTER ===")
	fmt.Printf("Успешных запросов: %d / %d\n", completed, totalRequests)
	fmt.Printf("Общее время теста: %v\n", duration.Round(time.Millisecond))
	fmt.Printf("Пропускная способность (Throughput): %.0f req/sec\n", rps)
	fmt.Printf("Средняя задержка (Avg Latency):    %v\n", avgLatency)
}
```

**`Терминал`**

```bash
go run main.go
# Вывод:
# === РЕЗУЛЬТАТЫ TCP LOAD TESTER ===
# Успешных запросов: 500 / 500
# Общее время теста: 12ms
# Пропускная способность (Throughput): 41667 req/sec
# Средняя задержка (Avg Latency):    180µs
```

## Под капотом

Атомарные счетчики позволяют параллельно собирать телеметрию со всех горутин без накладных расходов на мьютексы.

## Подводные камни

При тестировании сетевых сервисов на localhost задержка в десятки раз ниже, чем в реальной сети через коммутаторы и оптоволокно.

## На собеседовании

**Вопрос с собеседования:** «Почему при нагрузочном тестировании важно отслеживать P99 (99-й перцентиль) задержки, а не среднее значение?»
**Ответ:** Среднее значение маскирует всплески задержек (Tail Latency), вызванные сборщиком мусора GC, блокировками планировщика или сетевыми ретрансмитами. P99 показывает реальный худший пользовательский опыт.
