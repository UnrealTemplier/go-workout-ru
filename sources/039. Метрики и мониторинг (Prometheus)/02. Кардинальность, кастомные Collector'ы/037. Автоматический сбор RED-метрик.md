# Автоматический сбор RED-метрик: InstrumentHandlerDuration и InstrumentHandlerCounter из promhttp

## Условие

Используй `promhttp.InstrumentHandlerDuration` и `InstrumentHandlerCounter` для автоматического сбора RED-метрик HTTP-сервера без написания ручного middleware.

## Теория

Встроенные декораторы пакета `promhttp`:
- Вместо написания ручных middleware для обертки `http.ResponseWriter` официальный пакет `promhttp` предоставляет готовые компонуемые декораторы:
  1. `promhttp.InstrumentHandlerDuration(histVec, next)`: замеряет длительность выполнения запроса.
  2. `promhttp.InstrumentHandlerCounter(counterVec, next)`: считает количество запросов и HTTP-статусы.
  3. `promhttp.InstrumentHandlerInFlight(gauge, next)`: отслеживает параллельные запросы.
- Декораторы легко объединяются в цепочку:
  ```go
  handler = promhttp.InstrumentHandlerCounter(reqCounter,
      promhttp.InstrumentHandlerDuration(durationHist, apiHandler),
  )
  ```

## Решение по шагам

1. Создайте счетчик и гистограмму для декораторов promhttp.
2. Оберните базовый HTTP-хендлер через `InstrumentHandlerDuration` и `InstrumentHandlerCounter`.
3. Выполните тестовый запрос к сконструированному обработчику.
4. Проверьте автоматическое наполнение обеих метрик.

## Код решения

**`promhttp_instrument_decorators_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promhttp"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestPromHTTPInstrumentDecorators(t *testing.T) {
	reg := prometheus.NewRegistry()

	durationHist := prometheus.NewHistogramVec(
		prometheus.HistogramOpts{
			Name:    "http_handler_duration_seconds",
			Help:    "Длительность хендлера через InstrumentHandlerDuration",
			Buckets: prometheus.DefBuckets,
		},
		[]string{"code", "method"},
	)

	reqCounter := prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "http_handler_requests_total",
			Help: "Счетчик запросов через InstrumentHandlerCounter",
		},
		[]string{"code", "method"},
	)

	reg.MustRegister(durationHist, reqCounter)

	baseHandler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		fmt.Fprint(w, "Decorated API Response")
	})

	// Композиция декораторов promhttp
	decorated := promhttp.InstrumentHandlerCounter(
		reqCounter,
		promhttp.InstrumentHandlerDuration(durationHist, baseHandler),
	)

	req := httptest.NewRequest("GET", "/profile", nil)
	rec := httptest.NewRecorder()
	decorated.ServeHTTP(rec, req)

	counterVal := testutil.ToFloat64(reqCounter.WithLabelValues("200", "get"))
	if counterVal != 1.0 {
		t.Fatalf("Ожидался 1 запрос со статусом 200, получено: %f", counterVal)
	}

	fmt.Println("Декораторы promhttp успешно применились:")
	fmt.Printf("  • promhttp.InstrumentHandlerCounter:  %.0f запрос (200 get)\n", counterVal)
	fmt.Printf("  • promhttp.InstrumentHandlerDuration: зафиксировано в гистограмме\n")
	fmt.Println("  • Готовое коробочное решение без ручного перехвата ResponseWriter!")
}
```

## Под капотом

Внутри `promhttp` декораторы используют оптимизированный пул перехватчиков с интерфейсами `http.Flusher`, `http.Hijacker` и `http.Pusher`, предотвращая потерю функциональности WebSocket и HTTP/2 стриминга.

## Подводные камни

Использовать заглавные буквы в методе: `promhttp` декораторы нормализуют метод запроса в нижний регистр (`get`, `post`), в то время как самописные middleware обычно используют `GET`, `POST`. Это важно учитывать при составлении PromQL-запросов.

## На собеседовании

**Вопрос с собеседования:** «Почему ручные middleware часто ломают поддержку WebSocket / SSE при попытке обернуть http.ResponseWriter?»
**Ответ:** Потому что наивная структура-обертка реализует только метод `Write` и `WriteHeader`, но теряет интерфейсы `http.Hijacker` (нужен для переключения протокола в WebSocket) и `http.Flusher` (нужен для Server-Sent Events). Декораторы `promhttp` бережно сохраняют реализацию этих системных интерфейсов.
