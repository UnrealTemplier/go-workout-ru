# Метрики по методологии USE: Utilization процессора, Saturation очередей и лимиты горутин

## Условие

Создай **USE metrics** для ресурсов: Utilization (`process_cpu_seconds_total`), Saturation (`go_sched_wait_duration_seconds_total`), Errors (`go_goroutines` > threshold). Напиши алерты.

## Теория

Методология USE (Utilization, Saturation, Errors) для рантайма Go:
1. **Utilization (Утилизация):**
   - Доля времени работы ресурса: `rate(process_cpu_seconds_total[1m]) / NumCPU`.
   - Если CPU > 85%, сервис близок к насыщению.
2. **Saturation (Насыщение / Очереди ожидания):**
   - Наличие работы, ожидающей в очереди: `go_sched_latencies_seconds` или время ожидания горутин в очереди планировщика GMP (`runq`).
   - Если горутины ждут выполнения в очереди планировщика, сервис исчерпал процессорные ресурсы.
3. **Errors (Ошибки ресурса):**
   - Превышение лимита горутин (`go_goroutines > 10000`) или ошибок выделения памяти.

## Решение по шагам

1. Создайте модель сбора показателей по методике USE.
2. Реализуйте проверку порога утилизации процессора.
3. Реализуйте проверку задержки планировщика (Saturation).
4. Проверьте срабатывание алерта при превышении лимита горутин.

## Код решения

**`use_methodology_runtime_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type USEResourceMetrics struct {
	CPUUtilization float64 // 0.0 .. 1.0
	SchedWaitMS    float64 // время ожидания в очереди планировщика GMP
	Goroutines     int     // число активных горутин
}

func EvaluateUSEAlerts(m USEResourceMetrics) (alerts []string) {
	// 1. Utilization > 85%
	if m.CPUUtilization > 0.85 {
		alerts = append(alerts, fmt.Sprintf("ALERT: HighCPUUtilization (%.1f%%)", m.CPUUtilization*100))
	}
	// 2. Saturation > 50ms
	if m.SchedWaitMS > 50.0 {
		alerts = append(alerts, fmt.Sprintf("ALERT: HighSchedulerSaturation (%.1fms)", m.SchedWaitMS))
	}
	// 3. Errors / Goroutine Leak > 5000
	if m.Goroutines > 5000 {
		alerts = append(alerts, fmt.Sprintf("ALERT: GoroutineLeakThresholdExceeded (%d goroutines)", m.Goroutines))
	}
	return alerts
}

func TestUSEMethodologyRuntime(t *testing.T) {
	// Деградирующее состояние пода в Kubernetes
	stressedNode := USEResourceMetrics{
		CPUUtilization: 0.92,  // 92%
		SchedWaitMS:    65.0,  // 65мс в очереди GMP!
		Goroutines:     12500, // Утечка горутин!
	}

	alerts := EvaluateUSEAlerts(stressedNode)

	if len(alerts) != 3 {
		t.Fatalf("Ожидалось 3 алерта USE: %v", alerts)
	}

	fmt.Println("Оценка метрик по методологии USE (Brendan Gregg):")
	for _, a := range alerts {
		fmt.Printf("  • %s\n", a)
	}
	fmt.Println("  • Все 3 фактора деградации (U, S, E) своевременно обнаружены!")
}
```

## Под капотом

В Go 1.22+ рантайм экспортирует метрику `/sched/latencies:seconds` через пакет `runtime/metrics`, позволяя точно измерять задержку нахождения горутины в локальной и глобальной очередях планировщика GMP.

## Подводные камни

Мониторить только средний CPU контейнера: контейнер с лимитом 2 CPU может потреблять 100% одного ядра и 0% второго, в среднем показывая 50% CPU, в то время как ключевая горутина зависает из-за насыщения очереди потока.

## На собеседовании

**Вопрос с собеседования:** «Каковы преимущества методологии USE перед интуитивным мониторингом?»
**Ответ:** Методология USE дает исчерпывающий чек-лист для любого системного ресурса (CPU, память, диск, сеть, планировщик Go). Проверив все 3 вопроса: *«Насколько ресурс загружен? Есть ли очередь задач? Есть ли ошибки?»*, инженер гарантированно находит корень проблемы производительности без блуждания в догадках.
