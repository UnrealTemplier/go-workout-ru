# Каверзный кейс кардинальности: 10 000 уникальных user_id, раздувание TSDB и деградация памяти

## Условие

**[Каверзный кейс — Кардинальность]**: Создай метрику Counter с лейблом `user_id`. Сделай 10 000 запросов с разными `user_id`. Посмотри на размер `/metrics` (он раздуется до мегабайт). Объясни, почему лейблы с высоким числом уникальных значений (high cardinality) убивают Prometheus.

## Теория

Анатомия гибели TSDB от 10 000 уникальных меток:
- Математика расхода памяти:
  - 1 временной ряд в Prometheus требует около 1–2 КБ памяти в активном блоке Head (Head Block Chunk).
  - 10 000 рядов \(\to\) 20 МБ.
  - 1 000 000 рядов \(\to\) **2 ГБ оперативной памяти только на индекс**!
- Скорость скрейпа:
  - При 10 000 строк HTTP-ответ `/metrics` весит более 500 КБ.
  - Время сериализации в Go вырастает до сотен миллисекунд.
  - Prometheus начинает пропускать скрейпы по тайм-ауту (Scrape Timeout).
- **Вывод:** Кардинальность обязана быть ограниченной (Bounded Cardinality, не более 10–50 уникальных значений на лейбл).

## Решение по шагам

1. Создайте `CounterVec` с меткой `user_id`.
2. Продемонстрируйте создание 10 000 уникальных временных рядов.
3. Оцените размер текстового вывода (более 500 КБ).
4. Проанализируйте риски деградации инфраструктуры мониторинга.

## Код решения

**`ten_thousand_cardinality_case_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestTenThousandCardinalityCase(t *testing.T) {
	reg := prometheus.NewRegistry()

	counter := prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "user_actions_total",
			Help: "Экстремальный тест высокой кардинальности",
		},
		[]string{"user_id"},
	)
	reg.MustRegister(counter)

	// Создаем 10 000 уникальных рядов
	const totalUsers = 10000
	for i := 1; i <= totalUsers; i++ {
		counter.WithLabelValues(fmt.Sprintf("usr-%07d", i)).Inc()
	}

	seriesCount := testutil.CollectAndCount(counter)
	if seriesCount != totalUsers {
		t.Fatalf("Ожидалось %d рядов, создано: %d", totalUsers, seriesCount)
	}

	// Примерный размер в байтах (каждая строка ~52 байта)
	estimatedPayloadSize := seriesCount * 52

	fmt.Println("Каверзный кейс: 10 000 уникальных значений в лейбле:")
	fmt.Printf("  • Создано временных рядов: %d серий\n", seriesCount)
	fmt.Printf("  • Оценочный размер /metrics: ~%d байт (%.2f КБ текста на один скрейп!)\n",
		estimatedPayloadSize, float64(estimatedPayloadSize)/1024)
	fmt.Println("  • В BigTech такие метрики категорически запрещены и блокируются линтерами CI/CD!")
}
```

## Под капотом

При парсинге такого объема Prometheus тратит ресурсы на выделение памяти под строки (String Interning). Если метки быстро меняются (Chrun Rate), старые серии оседают в базе, вызывая фрагментацию WAL-логов на диске.

## Подводные камни

Пытаться решить проблему повышением лимитов памяти пода Prometheus с 4 ГБ до 64 ГБ: это временно спасет от OOM, но через неделю кардинальность удвоится и сервер упадет снова. Единственное верное решение — исправление кода сервиса.

## На собеседовании

**Вопрос с собеседования:** «Как в CI/CD автоматически ловить метрики с риском высокой кардинальности?»
**Ответ:** Используют специализированные статические анализаторы Go (например, линтер `promlinter` в составе `golangci-lint`) и нагрузочные тесты в staging-окружении с проверкой количества рядов в эндпоинте `/metrics` перед выкатом в продакшен.
