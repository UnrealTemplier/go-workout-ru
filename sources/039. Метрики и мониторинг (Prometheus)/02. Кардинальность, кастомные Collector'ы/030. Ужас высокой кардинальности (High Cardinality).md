# Ужас высокой кардинальности (High Cardinality): генерация 1000 ID и наглядная демонстрация раздувания вывода

## Условие

**Ужас высокой кардинальности (High Cardinality)**: *Теоретическо-практическое.* В метрику из упр. 523 добавь лейбл `user_id` и сделай 1000 запросов с разными ID. Посмотри на вывод `/metrics` — он взорвется от количества строк. Осознай правило: **никогда не клади в лейблы метрик безграничные данные (ID, URL, IP)**. Удали этот лейбл.

## Теория

Почему High Cardinality смертельна для Prometheus:
- Каждая новая строка в выводе `/metrics` увеличивает:
  1. Время генерации ответа в микросервисе (CPU и блокировки памяти).
  2. Сетевой трафик скрейпа (передача десятков мегабайт текста каждые 15 секунд).
  3. Потребление RAM сервером Prometheus (индексация каждого строкового лейбла).
- **Список запрещенных меток:**
  - `user_id`, `account_id`, `order_id` (уникальные сущности).
  - `ip_address`, `email`, `jwt_token`.
  - Произвольные сообщения об ошибках (error messages с параметрами).
  - Ненормализованные URL с query-параметрами (`/search?q=...`).

## Решение по шагам

1. Создайте счетчик с меткой `user_id`.
2. Сгенерируйте 1000 инкрементов с уникальными ID.
3. Замерьте суммарный объем сгенерированного текста `/metrics`.
4. Продемонстрируйте очистку и переход на агрегированную метрику без `user_id`.

## Код решения

**`cardinality_horror_test.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http/httptest"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

func TestCardinalityHorror(t *testing.T) {
	badReg := prometheus.NewRegistry()

	// АНТИПАТТЕРН: метка user_id!
	dangerousCounter := prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "dangerous_requests_total",
			Help: "Опасная метрика с высокой кардинальностью",
		},
		[]string{"user_id"},
	)
	badReg.MustRegister(dangerousCounter)

	// Генерируем 1000 уникальных пользователей
	for i := 1; i <= 1000; i++ {
		dangerousCounter.WithLabelValues(fmt.Sprintf("usr-%06d", i)).Inc()
	}

	handler := promhttp.HandlerFor(badReg, promhttp.HandlerOpts{})
	req := httptest.NewRequest("GET", "/metrics", nil)
	rec := httptest.NewRecorder()
	handler.ServeHTTP(rec, req)

	respBody, _ := io.ReadAll(rec.Body)
	bytesSize := len(respBody)

	if bytesSize < 40000 { // 1000 строк занимают более 45 КБ текста!
		t.Fatalf("Ожидался огромный объем вывода, получено: %d байт", bytesSize)
	}

	fmt.Println("Демонстрация ужаса высокой кардинальности (High Cardinality):")
	fmt.Printf("  • Уникальных user_id: 1 000 рядов\n")
	fmt.Printf("  • Объем /metrics:     %d байт (%.2f КБ на 1000 пользователей!)\n", bytesSize, float64(bytesSize)/1024)
	fmt.Printf("  • При 1 000 000 юзеров объем /metrics составит ~45 МБ КАЖДЫЕ 15 СЕКУНД!\n")
	fmt.Println("  • Правило усвоено: user_id, email, IP строго запрещены в лейблах Prometheus!")
}
```

ℹ️ Наглядная демонстрация раздувания объема вывода /metrics при высокой кардинальности

## Под капотом

Сервер Prometheus при скрейпе должен прочитать все 50 КБ текста, распарсить каждое имя метки и вставить строковые хеши в таблицы базы данных TSDB, что увеличивает время скрейпа с 2 мс до сотен миллисекунд.

## Подводные камни

Поддаться на просьбу аналитиков «просто добавить IP клиента в метрики на один денек»: если сервис публичный, за день прилетит 2 000 000 уникальных IP-адресов, что приведет к аварии инфраструктуры мониторинга всей компании.

## На собеседовании

**Вопрос с собеседования:** «Как в Prometheus ограничить максимальное количество скрейпимых рядов от одного микросервиса?»
**Ответ:** В конфигурации задачи сбора `prometheus.yml` настраивают директиву `sample_limit: 5000`. Если микросервис отдает больше 5000 рядов (взрыв кардинальности), Prometheus автоматически отклоняет скрейп и помечает таргет как упавший, защищая центральный кластер мониторинга от перегрузки.
