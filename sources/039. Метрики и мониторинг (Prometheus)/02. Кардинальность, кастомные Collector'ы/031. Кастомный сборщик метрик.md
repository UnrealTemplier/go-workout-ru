# Кастомный сборщик метрик: интерфейс prometheus.Collector и динамический SQL-запрос COUNT(*)

## Условие

**Кастомный сборщик метрик (Collector)**: Иногда метрики нужно извлекать напрямую из сторонней системы (например, количество зарегистрированных пользователей из БД PostgreSQL). ## Теория

Архитектура вытягивания данных по требованию (Pull-on-Scrape):
- Традиционные метрики инкрементируются по ходу выполнения бизнес-логики.
- Но для метрик состояния внешних баз данных (число записей в таблице, свободное место на диске СУБД) постоянные инкременты не подходят:
  - Количество записей в БД может меняться внешними сервисами, миграциями или фоновыми скриптами.
- Реализация `prometheus.Collector`:
  - Метод `Describe`: объявляет дескриптор метрики (`prometheus.NewDesc`).
  - Метод `Collect`: запускается только тогда, когда пришел скрейпер Prometheus. Выполняет `SELECT COUNT(*)` и отправляет результат через `prometheus.MustNewConstMetric`.

## Решение по шагам

1. Создайте структуру `PostgresUsersCountCollector`.
2. Реализуйте метод `Describe(chan<- *prometheus.Desc)`.
3. Реализуйте метод `Collect(chan<- prometheus.Metric)` с вызовом функции подсчета строк.
4. Протестируйте регистрацию и экспорт актуального значения.

## Код решения

**`postgres_users_collector_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type PostgresUsersCountCollector struct {
	desc      *prometheus.Desc
	countFunc func() (float64, error)
}

func NewPostgresUsersCollector(countFunc func() (float64, error)) *PostgresUsersCountCollector {
	return &PostgresUsersCountCollector{
		desc: prometheus.NewDesc(
			"postgres_registered_users_total",
			"Актуальное число зарегистрированных пользователей из БД PostgreSQL",
			nil, nil,
		),
		countFunc: countFunc,
	}
}

func (c *PostgresUsersCountCollector) Describe(ch chan<- *prometheus.Desc) {
	ch <- c.desc
}

func (c *PostgresUsersCountCollector) Collect(ch chan<- prometheus.Metric) {
	count, err := c.countFunc()
	if err != nil {
		return // В случае ошибки БД не отдаем поврежденное значение
	}
	ch <- prometheus.MustNewConstMetric(c.desc, prometheus.GaugeValue, count)
}

func TestPostgresUsersCollector(t *testing.T) {
	reg := prometheus.NewRegistry()

	// Симулируем SQL запрос SELECT COUNT(*) FROM users
	fakeSQLQuery := func() (float64, error) {
		return 84920.0, nil
	}

	collector := NewPostgresUsersCollector(fakeSQLQuery)
	reg.MustRegister(collector)

	count := testutil.CollectAndCount(collector)
	if count != 1 {
		t.Fatalf("Ожидался 1 ряд от коллектора, получено: %d", count)
	}

	fmt.Println("Кастомный коллектор PostgresUsersCountCollector успешно отработал:")
	fmt.Printf("  • Метрика:       postgres_registered_users_total\n")
	fmt.Printf("  • Значение COUNT: 84920 пользователей\n")
	fmt.Println("  • Метрика извлекается динамически в момент скрейпа без хранения состояния в памяти!")
}
```

## Под капотом

Канал `chan<- prometheus.Metric` является буферизованным или синхронным. Функция `Collect` выполняется синхронно в горутине HTTP-обработчика `/metrics`, поэтому при закрытии соединения клиентом сбор прерывается.

## Подводные камни

Выполнять медленный `SELECT COUNT(*)` по неиндексированной таблице на 50 000 000 строк: такой запрос положит диск базы данных при каждом 15-секундном скрейпе. В HighLoad запрашивают системные счетчики статистики `pg_stat_user_tables.n_live_tup`.

## На собеседовании

**Вопрос с собеседования:** «Как в кастомном коллекторе обработать ситуацию, когда внешняя база данных временно недоступна?»
**Ответ:** Если база недоступна, метод `Collect()` не должен паниковать. Он логирует ошибку и отсылает служебную метрику доступности: `ch <- prometheus.MustNewConstMetric(scrapeSuccessDesc, prometheus.GaugeValue, 0)`. Это позволяет в Grafana видеть статус доступности источника метрик.
