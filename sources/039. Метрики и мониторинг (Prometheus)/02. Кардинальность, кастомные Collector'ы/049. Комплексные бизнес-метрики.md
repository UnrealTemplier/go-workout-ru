# Комплексные бизнес-метрики: orders_created, orders_completed, order_value и payment_failed

## Условие

Создай **business metrics**: `orders_created_total`, `orders_completed_total`, `order_value_histogram`, `payment_failed_total`. Покажи, что бизнес-метрики важнее инфраструктурных для product decisions.

### Исходная формулировка

Создай **business metrics**: `orders_created_total`, `orders_completed_total`, `order_value_histogram`, `payment_failed_total`. Покажи, что бизнес-метрики важнее инфраструктурных для product decisions.

---

## Теория

Приоритет бизнес-метрик в Data-Driven разработке:
- Инфраструктурные метрики (CPU, Disk I/O) показывают стоимость эксплуатации.
- **Бизнес-метрики отражают реальную ценность продукта:**
  1. `orders_created_total`: намерение пользователей совершить покупку (воронка продаж).
  2. `orders_completed_total`: фактически завершенные заказы (конверсия).
  3. `order_value_histogram`: распределение чека (средний чек, микроплатежи vs крупные покупки).
  4. `payment_failed_total`: прямая финансовая утечка (Lost Revenue).
- Если `orders_created` растет, а `orders_completed` падает — это немедленный сигнал об отказе платежного шлюза, даже если CPU серверов составляет идеальные 5%.

## Решение по шагам

1. Создайте продуктовый набор метрик заказа.
2. Продемонстрируйте прохождение воронки: создание \(\to\) оплата.
3. Зафиксируйте чек заказа в гистограмме `order_value_histogram`.
4. Смоделируйте отказ платежа и проверьте инкремент `payment_failed_total`.

## Код решения

**`business_product_metrics_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type ProductMetricsSuite struct {
	ordersCreated   prometheus.Counter
	ordersCompleted prometheus.Counter
	paymentFailed   prometheus.Counter
	orderValueHist  prometheus.Histogram
}

func NewProductMetricsSuite(reg *prometheus.Registry) *ProductMetricsSuite {
	m := &ProductMetricsSuite{
		ordersCreated: prometheus.NewCounter(prometheus.CounterOpts{
			Name: "orders_created_total",
			Help: "Созданные заказы в воронке оформления",
		}),
		ordersCompleted: prometheus.NewCounter(prometheus.CounterOpts{
			Name: "orders_completed_total",
			Help: "Успешно оплаченные и закрытые заказы",
		}),
		paymentFailed: prometheus.NewCounter(prometheus.CounterOpts{
			Name: "payment_failed_total",
			Help: "Отказы платежей банковским шлюзом",
		}),
		orderValueHist: prometheus.NewHistogram(prometheus.HistogramOpts{
			Name:    "order_value_histogram_rubles",
			Help:    "Распределение чеков заказов в рублях",
			Buckets: []float64{500, 1000, 3000, 5000, 10000, 50000},
		}),
	}
	reg.MustRegister(m.ordersCreated, m.ordersCompleted, m.paymentFailed, m.orderValueHist)
	return m
}

func TestBusinessProductMetrics(t *testing.T) {
	reg := prometheus.NewRegistry()
	p := NewProductMetricsSuite(reg)

	// Пользователь 1: создал заказ на 4500 руб. и успешно оплатил
	p.ordersCreated.Inc()
	p.orderValueHist.Observe(4500)
	p.ordersCompleted.Inc()

	// Пользователь 2: создал заказ на 12000 руб., но оплата упала
	p.ordersCreated.Inc()
	p.orderValueHist.Observe(12000)
	p.paymentFailed.Inc()

	created := testutil.ToFloat64(p.ordersCreated)
	completed := testutil.ToFloat64(p.ordersCompleted)
	failed := testutil.ToFloat64(p.paymentFailed)

	if created != 2.0 || completed != 1.0 || failed != 1.0 {
		t.Fatalf("Ошибка бизнес-метрик: created=%f, completed=%f, failed=%f", created, completed, failed)
	}

	conversionRate := (completed / created) * 100.0

	fmt.Println("Продуктовые бизнес-метрики успешно зарегистрированы:")
	fmt.Printf("  • Создано заказов (Воронка): %.0f\n", created)
	fmt.Printf("  • Успешно закрыто покупок:   %.0f\n", completed)
	fmt.Printf("  • Отказов шлюза оплаты:      %.0f\n", failed)
	fmt.Printf("  • Конверсия воронки:         %.1f%%\n", conversionRate)
	fmt.Println("  • Бизнес-метрики позволяют принимать точные продуктовые решения!")
}
```

## Под капотом

Гистограмма `order_value_histogram_rubles` позволяет в PromQL вычислять средний чек (`sum(rate(..._sum)) / sum(rate(..._count))`) и медианный чек, отсекая влияние единичных оптовых закупок.

## Подводные камни

Хранить денежные суммы с плавающей точкой высокой точности в Gauge без суммирования: для объемов выручки обязателен накопительный Counter, иначе невозможно посчитать выручку за произвольный интервал времени.

## На собеседовании

**Вопрос с собеседования:** «Как на основе бизнес-метрик выстроить мониторинг A/B тестирования нового чекаута?»
**Ответ:** Добавить метку `checkout_version="v2"` в `orders_created_total` и `orders_completed_total`. В Grafana рассчитывают конверсию `sum(rate(completed{version="v2"})) / sum(rate(created{version="v2"}))` в сравнении с версией v1, оценивая статистическую значимость изменений в реальном времени.
