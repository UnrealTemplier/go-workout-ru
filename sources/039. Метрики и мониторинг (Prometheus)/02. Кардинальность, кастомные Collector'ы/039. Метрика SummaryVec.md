# Метрика SummaryVec: расчет квантилей задержки 0.5, 0.95, 0.99 на клиенте и ограничения PromQL

## Условие

Создай **Summary** (редко используется, предпочитай Histogram): `requestLatency := prometheus.NewSummaryVec(prometheus.SummaryOpts{Name: "http_request_latency_seconds", Help: "...", Objectives: map[float64]float64{0.5: 0.05, 0.95: 0.005, 0.99: 0.001}}, []string{"method"})`. Покажи вычисление quantile'ей на клиенте vs сервере.

## Теория

Особенности работы SummaryVec с квантилями:
- Параметр `Objectives: map[float64]float64`:
  - Ключ — целевой квантиль (\(0.5\) — медиана p50, \(0.95\) — p95, \(0.99\) — p99).
  - Значение — допустимая статистическая погрешность (абсолютная ошибка, например \(\pm 0.001\)).
- **Почему Summary редко используется в распределенных микросервисах:**
  - Квантили вычисляются на клиенте по локальным данным одного пода.
  - Невозможно объединить квантили 50 подов в один общий график в Grafana (математически некорректно брать среднее от перцентилей!).
  - Для Kubernetes и кластеров всегда выбирают Histogram.

## Решение по шагам

1. Создайте `SummaryVec` с целевыми квантилями 0.5, 0.95 и 0.99.
2. Зарегистрируйте метрику в локальном тестовом реестре.
3. Добавьте серию наблюдений для методов GET и POST.
4. Проверьте экспорт квантилей в выводе метрики.

## Код решения

**`summary_vec_quantiles_test.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http/httptest"
	"strings"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

func TestSummaryVecQuantiles(t *testing.T) {
	reg := prometheus.NewRegistry()

	requestLatency := prometheus.NewSummaryVec(
		prometheus.SummaryOpts{
			Name: "http_request_latency_seconds",
			Help: "Задержка HTTP запросов с клиентскими квантилями",
			Objectives: map[float64]float64{
				0.5:  0.05,  // p50 c погрешностью 5%
				0.95: 0.005, // p95 с погрешностью 0.5%
				0.99: 0.001, // p99 с погрешностью 0.1%
			},
		},
		[]string{"method"},
	)
	reg.MustRegister(requestLatency)

	// Добавляем 100 наблюдений для GET
	for i := 1; i <= 100; i++ {
		requestLatency.WithLabelValues("GET").Observe(float64(i) * 0.001) // 1ms ... 100ms
	}

	handler := promhttp.HandlerFor(reg, promhttp.HandlerOpts{})
	rec := httptest.NewRecorder()
	handler.ServeHTTP(rec, httptest.NewRequest("GET", "/metrics", nil))

	body, _ := io.ReadAll(rec.Body)
	bodyStr := string(body)

	// Проверяем наличие строковых квантилей
	if !strings.Contains(bodyStr, `quantile="0.5"`) || !strings.Contains(bodyStr, `quantile="0.99"`) {
		t.Fatal("В выводе /metrics отсутствуют расчетные квантили Summary")
	}

	fmt.Println("SummaryVec с клиентскими квантилями успешно протестирован:")
	fmt.Printf("  • Метрика:     http_request_latency_seconds\n")
	fmt.Printf("  • Objectives:  p50 (0.5), p95 (0.95), p99 (0.99)\n")
	fmt.Println("  • Вычисление квантилей на клиенте подтверждено!")
}
```

## Под капотом

Summary использует скользящее временное окно (по умолчанию `MaxAge: 10 * time.Minute`), разбитое на 5 субокон (AgeBuckets). Старые наблюдения автоматически вытесняются новыми без сброса счетчиков суммы и количества.

## Подводные камни

Указывать слишком низкую погрешность (например `0.99: 0.00001`): высокая точность алгоритма CKMS требует выделения огромного объема оперативной памяти под структуры сэмплов в Go рантайме.

## На собеседовании

**Вопрос с собеседования:** «Почему в PromQL нельзя применить функцию histogram_quantile к метрике типа Summary?»
**Ответ:** Потому что функция `histogram_quantile` ожидает на вход бакеты с фиксированными границами `le` (`<name>_bucket`), а Summary отдает уже готовые квантили в метках `quantile="0.95"`. Summary не имеет информации о распределении наблюдений по корзинам.
