# Бизнес-метрика orders_processed_total: разделение по статусам success и failed в обработке заказов

## Условие

**[Бизнес-метрики]**: Создай метрику `orders_processed_total` с лейблом `status` ("success", "failed"). Инкрементируй её в сервисе обработки заказов.

## Теория

Проектирование бизнес-метрик обработки заказов:
- Метрика `orders_processed_total{status="..."}` является корневым SLI (Service Level Indicator) интернет-магазина.
- **Значения метки status:**
  - `"success"`: заказ полностью оплачен и передан на сборку.
  - `"failed"`: платеж отклонен, отмена по таймауту, ошибка склада.
- **В PromQL расчет процента успешных заказов:**
  `sum(rate(orders_processed_total{status="success"}[5m])) / sum(rate(orders_processed_total[5m])) * 100`.

## Решение по шагам

1. Создайте `CounterVec` с именем `orders_processed_total` и меткой `status`.
2. Реализуйте функцию оформления заказа с обработкой успеха и отказа.
3. Симулируйте 9 успешных заказов и 1 сбойный.
4. Проверьте расчет показателей в тестовом реестре.

## Код решения

**`orders_processed_metric_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type OrderProcessorService struct {
	ordersProcessed *prometheus.CounterVec
}

func NewOrderProcessorService(reg *prometheus.Registry) *OrderProcessorService {
	c := prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "orders_processed_total",
			Help: "Общее число обработанных заказов по статусам",
		},
		[]string{"status"},
	)
	reg.MustRegister(c)
	return &OrderProcessorService{ordersProcessed: c}
}

func (s *OrderProcessorService) ProcessOrder(orderID string, fail bool) error {
	if fail {
		s.ordersProcessed.WithLabelValues("failed").Inc()
		return errors.New("insufficient funds")
	}
	s.ordersProcessed.WithLabelValues("success").Inc()
	return nil
}

func TestOrdersProcessedMetric(t *testing.T) {
	reg := prometheus.NewRegistry()
	svc := NewOrderProcessorService(reg)

	// 9 успешных заказов, 1 сбойный
	for i := 1; i <= 9; i++ {
		_ = svc.ProcessOrder(fmt.Sprintf("ord-%d", i), false)
	}
	_ = svc.ProcessOrder("ord-10", true)

	successCount := testutil.ToFloat64(svc.ordersProcessed.WithLabelValues("success"))
	failedCount := testutil.ToFloat64(svc.ordersProcessed.WithLabelValues("failed"))

	if successCount != 9.0 || failedCount != 1.0 {
		t.Fatalf("Ошибка подсчета: success=%f, failed=%f", successCount, failedCount)
	}

	successRate := (successCount / (successCount + failedCount)) * 100.0

	fmt.Println("Бизнес-метрика orders_processed_total успешно проверена:")
	fmt.Printf("  • Успешных заказов: %.0f (success)\n", successCount)
	fmt.Printf("  • Сбойных заказов:  %.0f (failed)\n", failedCount)
	fmt.Printf("  • Success Rate:     %.1f%%\n", successRate)
}
```

## Под капотом

Метка `status` имеет строго 2 значения ("success" и "failed"), что обеспечивает кардинальность ровно 2 ряда и минимальную нагрузку на процессор и диск.

## Подводные камни

Добавлять причину ошибки в метку `status` (например `status="failed: connection timeout to visa"`): это немедленно приведет к росту кардинальности. Причину сбоя передают в структурированные логи (slog/zap), а метку оставляют строго категоризованной.

## На собеседовании

**Вопрос с собеседования:** «Какое оповещение в Alertmanager должно иметь наивысший приоритет (P0/Critical): падение CPU ноды или падение orders_processed_total?»
**Ответ:** Падение бизнес-метрики `orders_processed_total` имеет абсолютный приоритет P0. Потеря CPU одной ноды автоматически компенсируется Kubernetes (поды переедут на другую ноду), в то время как падение потока заказов означает прямую потерю выручки компанией прямо сейчас.
