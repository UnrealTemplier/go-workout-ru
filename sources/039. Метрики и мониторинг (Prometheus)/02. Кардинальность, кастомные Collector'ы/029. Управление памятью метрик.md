# Управление памятью метрик: метод DeleteLabelValues для удаления устаревших рядов тенантов

## Условие

Используйте `prometheus.NewCounterVec` с `DeleteLabelValues` для динамического управления метриками (например, при удалении tenant'а).

## Теория

Очистка динамических временных рядов (Metric Pruning):
- Если метрика содержит метку `tenant_id` (например, идентификатор организации-клиента):
  - При удалении или миграции компании ее метки больше никогда не будут обновляться.
  - По умолчанию Prometheus клиент **навсегда хранит в памяти** все когда-либо созданные временные ряды!
- **Метод `vec.DeleteLabelValues(...)`:**
  - Удаляет соответствующий временной ряд из памяти клиента.
  - При следующем скрейпе эта серия больше не будет отдаваться в `/metrics`.
  - Prometheus пометит серию как завершенную (Staleness marker) и освободит ресурсы.

## Решение по шагам

1. Создайте `CounterVec` с меткой `tenant_id`.
2. Зафиксируйте события для тенантов `tenant-alpha` и `tenant-beta`.
3. Вызовите `DeleteLabelValues("tenant-alpha")` при удалении арендатора.
4. Убедитесь, что метрика тенанта удалена из экспорта.

## Код решения

**`delete_label_values_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestDeleteLabelValues(t *testing.T) {
	reg := prometheus.NewRegistry()

	tenantEvents := prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "tenant_events_total",
			Help: "События арендаторов в мульти-тенантной системе",
		},
		[]string{"tenant_id"},
	)
	reg.MustRegister(tenantEvents)

	// Регистрируем активность двух тенантов
	tenantEvents.WithLabelValues("tenant-alpha").Add(50)
	tenantEvents.WithLabelValues("tenant-beta").Add(120)

	if count := testutil.CollectAndCount(tenantEvents); count != 2 {
		t.Fatalf("Ожидалось 2 временных ряда, получено: %d", count)
	}

	// Арендатор Alpha удален -> очищаем его временной ряд из памяти!
	deleted := tenantEvents.DeleteLabelValues("tenant-alpha")
	if !deleted {
		t.Fatal("Удаление временного ряда tenant-alpha должно вернуть true")
	}

	// Теперь в реестре должен остаться только 1 ряд (tenant-beta)
	remainingCount := testutil.CollectAndCount(tenantEvents)
	if remainingCount != 1 {
		t.Fatalf("Ожидался строго 1 ряд после удаления, получено: %d", remainingCount)
	}

	fmt.Println("Динамическая очистка метрик через DeleteLabelValues успешна:")
	fmt.Printf("  • Исходных рядов: 2 (alpha, beta)\n")
	fmt.Printf("  • Удален ряд:     tenant-alpha (deleted=%v)\n", deleted)
	fmt.Printf("  • Осталось рядов: %d (только tenant-beta)\n", remainingCount)
	fmt.Println("  • Утечка памяти от заброшенных динамических меток полностью исключена!")
}
```

ℹ️ Удаление устаревших временных рядов из памяти клиента через DeleteLabelValues

## Под капотом

Метод `DeleteLabelValues` удаляет метрику из внутренней мапы вектора под мьютексом. Удаленный объект освобождается сборщиком мусора, предотвращая постоянный рост кучи в долгоживущих микросервисах.

## Подводные камни

Вызывать `DeleteLabelValues` на каждый запрос: поиск и удаление под блокировкой мьютекса создает ненужную конкуренцию (Lock Contention). Вызывать `Delete` следует только при реальных событиях удаления бизнес-сущностей.

## На собеседовании

**Вопрос с собеседования:** «Что такое Staleness Marker в Prometheus и как сервер понимает, что ряд удален?»
**Ответ:** Если скрейп больше не содержит ранее существовавший временной ряд (после `DeleteLabelValues`), сервер Prometheus фиксирует для него специальное значение NaN (Staleness Marker). Это немедленно прекращает экстраполяцию функции `rate()`, предотвращая ложные алерты о "зависших" метриках.
