# Ручное создание спанов трассировки: передача атрибутов order.id и amount в OpenTelemetry Span

## Условие

Вручную создайте спаны для критичного бизнес-метода (например, расчёт стоимости заказа). Добавьте атрибуты: `order.id`, `amount`.

## Теория

Связывание трассировки (Tracing) и бизнес-метрик:
- В критических операциях (биллинг, списание со счета) инженеры создают ручные спаны через OpenTelemetry Tracer:
  ```go
  tracer := otel.Tracer("order-service")
  ctx, span := tracer.Start(ctx, "CalculateOrderPrice")
  defer span.End()
  span.SetAttributes(
      attribute.String("order.id", orderID),
      attribute.Float64("amount", amount),
  )
  ```
- В спане допустимо указывать конкретный `order.id` (в отличие от метрик Prometheus, спаны не страдают от взрыва кардинальности).

## Решение по шагам

1. Создайте модель спана OpenTelemetry с поддержкой атрибутов.
2. Инициализируйте спан для метода `CalculateOrderTotal`.
3. Добавьте структурированные атрибуты `order.id` и `amount`.
4. Завершите спан через `defer span.End()` и проверьте сохранность контекста.

## Код решения

**`manual_otel_spans_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type MockSpan struct {
	Name       string
	Attributes map[string]any
	Duration   time.Duration
	ended      bool
}

func (s *MockSpan) SetAttribute(k string, v any) {
	s.Attributes[k] = v
}

func (s *MockSpan) End(start time.Time) {
	s.Duration = time.Since(start)
	s.ended = true
}

func CalculateOrderTotalWithTracing(ctx context.Context, orderID string, amount float64) (float64, *MockSpan) {
	start := time.Now()
	span := &MockSpan{
		Name:       "CalculateOrderTotal",
		Attributes: make(map[string]any),
	}
	defer span.End(start)

	// Добавляем бизнес-атрибуты в трейс
	span.SetAttribute("order.id", orderID)
	span.SetAttribute("amount", amount)
	span.SetAttribute("currency", "RUB")

	// Расчет скидки
	finalTotal := amount * 0.95
	return finalTotal, span
}

func TestManualOTelSpans(t *testing.T) {
	final, span := CalculateOrderTotalWithTracing(context.Background(), "ord-trace-771", 5000.0)

	if final != 4750.0 || !span.ended {
		t.Fatalf("Ошибка расчета или завершения спана: %f, ended=%v", final, span.ended)
	}

	if span.Attributes["order.id"] != "ord-trace-771" || span.Attributes["amount"] != 5000.0 {
		t.Fatalf("Некорректные атрибуты спана: %+v", span.Attributes)
	}

	fmt.Println("Ручное создание спанов OpenTelemetry успешно подтверждено:")
	fmt.Printf("  • Спан:     %s (Завершен: %v)\n", span.Name, span.ended)
	fmt.Printf("  • order.id: %s (В трейсах допустима любая кардинальность!)\n", span.Attributes["order.id"])
	fmt.Printf("  • amount:   %.2f RUB -> Итог со скидкой: %.2f RUB\n", span.Attributes["amount"], final)
}
```

## Под капотом

Спаны OpenTelemetry сохраняются в виде графа распределенных вызовов в Jaeger/Tempo. В отличие от TSDB, системы трассировки хранят данные в колоночных индексах или блоб-хранилищах (S3), где высокая кардинальность является нормой.

## Подводные камни

Забывать вызывать `span.End()`: спан не завершится, его длительность не рассчитается, и экспортер не сможет передать трассировку в коллектор.

## На собеседовании

**Вопрос с собеседования:** «Почему в спаны трассировки можно смело добавлять user_id и order_id, а в метрики Prometheus категорически нельзя?»
**Ответ:** Потому что в Prometheus каждая комбинация меток создает постоянный временной ряд в индексе TSDB, который потребляет оперативную память все время жизни базы. В распределенной трассировке (Jaeger/Tempo) каждый спан — это изолированное событие (Log-like Document), которое пишется на диск и удаляется по TTL без поддержания тяжелых таблиц обратных индексов в RAM.
