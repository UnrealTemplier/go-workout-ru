# Unit-тестирование метрик: проверка инкремента счетчика и записи в гистограмму через пакет testutil

## Условие

**Unit-тестирование метрик**: Напиши тест для своей логики. Используй пакет `github.com/prometheus/client_golang/prometheus/testutil`, чтобы проверить, что после вызова функции счетчик реально увеличился на 1, а в гистограмму записалось нужное значение.

## Теория

Комплексное тестирование телеметрии через `testutil`:
- В Go клиент Prometheus предоставляет специализированные методы тестирования:
  1. `testutil.ToFloat64(c)`: получение числового значения Counter или Gauge.
  2. `testutil.CollectAndCount(c)`: количество сгенерированных рядов.
  3. `testutil.CollectAndCompare(c, reader)`: побайтовое сравнение с ожидаемым выводом OpenMetrics.
- Гарантирует, что бизнес-логика и метрики тестируются неразрывно в рамках TDD.

## Решение по шагам

1. Создайте сервис с инжектированными `Counter` и `Histogram`.
2. Вызовите бизнес-метод обработки платежа.
3. Проверьте, что счетчик увеличился ровно на 1.0.
4. Проверьте, что гистограмма зафиксировала ровно 1 наблюдение.

## Код решения

**`comprehensive_testutil_metrics_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type PaymentProcessingService struct {
	paymentsTotal    prometheus.Counter
	paymentDuration  prometheus.Histogram
}

func (s *PaymentProcessingService) ExecutePayment(amount int) {
	start := time.Now()
	// Симуляция работы
	time.Sleep(5 * time.Millisecond)
	_ = amount

	s.paymentsTotal.Inc()
	s.paymentDuration.Observe(time.Since(start).Seconds())
}

func TestComprehensiveTestutilMetrics(t *testing.T) {
	reg := prometheus.NewRegistry()

	counter := prometheus.NewCounter(prometheus.CounterOpts{
		Name: "payments_executed_total",
		Help: "Число выполненных платежей",
	})
	hist := prometheus.NewHistogram(prometheus.HistogramOpts{
		Name:    "payment_execution_duration_seconds",
		Help:    "Длительность платежа",
		Buckets: []float64{0.001, 0.01, 0.1, 1.0},
	})
	reg.MustRegister(counter, hist)

	svc := &PaymentProcessingService{
		paymentsTotal:   counter,
		paymentDuration: hist,
	}

	// Выполняем платеж
	svc.ExecutePayment(5000)

	// Проверяем счетчик
	if val := testutil.ToFloat64(counter); val != 1.0 {
		t.Fatalf("Счетчик должен быть 1.0, получено: %f", val)
	}

	// Проверяем, что гистограмма содержит 1 собранную метрику
	if count := testutil.CollectAndCount(hist); count == 0 {
		t.Fatal("Гистограмма не зафиксировала наблюдение")
	}

	fmt.Println("Тестирование метрик через testutil успешно завершено:")
	fmt.Printf("  • payments_executed_total: %.0f (увеличен на 1)\n", testutil.ToFloat64(counter))
	fmt.Printf("  • payment_execution_duration_seconds: зафиксировано наблюдение\n")
	fmt.Println("  • Корректность работы телеметрии доказана юнит-тестом!")
}
```

ℹ️ Сквозное юнит-тестирование Counter и Histogram с помощью пакета testutil


## Под капотом

Метод `testutil.ToFloat64` обращается напрямую к структуре `io_prometheus_client.Metric` в оперативной памяти Go, не требуя сетевых сокетов и сериализации в текстовый формат OpenMetrics.

## Подводные камни

Забывать инициализировать кастомный `Registry` в тестах: если завязаться на `prometheus.DefaultRegisterer`, тесты нельзя будет безопасно запускать с флагом `go test -count=1 -parallel 4`.

## На собеседовании

**Вопрос с собеседования:** «Как протестировать, что при ошибке функции инкрементируется счетчик ошибок, а не счетчик успеха?»
**Ответ:** Пишут два тестовых сценария: в happy-path проверяют `testutil.ToFloat64(successCounter) == 1` и `testutil.ToFloat64(errorCounter) == 0`. В сценарии ошибки (например, сбой соединения) проверяют `testutil.ToFloat64(errorCounter) == 1` и `testutil.ToFloat64(successCounter) == 0`.
