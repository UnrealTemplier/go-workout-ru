# Перехватчики gRPC: мониторинг задержек, ошибок и кодов статусов через gRPC Interceptors

## Условие

Инструментируйте gRPC-сервер: перехватчики (interceptors) должны собирать метрики запросов, ошибок и задержек (можно использовать готовый `grpc_prometheus`).

## Теория

Детальная анатомия gRPC Interceptors для телеметрии:
- Перехватчик выполняет три ключевые функции:
  1. *Парсинг имени метода*: делит `fullMethod` (например `/orders.v1.OrderAPI/GetOrder`) на пакет/сервис и конкретный RPC-метод.
  2. *Замер задержки*: оборачивает вызов `handler(ctx, req)` в замер `time.Since(start)`.
  3. *Извлечение gRPC статус-кода*: преобразует ошибку через `status.Code(err)` в каноническую строку (`codes.OK`, `codes.NotFound`, `codes.Unauthenticated`, `codes.Unavailable`).

## Решение по шагам

1. Создайте фабрику перехватчика `UnaryServerInterceptor`.
2. Реализуйте разбор строки метода на имя сервиса и метода.
3. Протестируйте вызовы с кодами `OK` и `NotFound`.
4. Убедитесь в корректной фиксации гистограммы времени ответа.

## Код решения

**`grpc_interceptors_deep_dive_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"strings"
	"testing"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type DetailedGRPCInterceptor struct {
	reqCounter *prometheus.CounterVec
	latency    *prometheus.HistogramVec
}

func NewDetailedGRPCInterceptor(reg *prometheus.Registry) *DetailedGRPCInterceptor {
	i := &DetailedGRPCInterceptor{
		reqCounter: prometheus.NewCounterVec(
			prometheus.CounterOpts{
				Name: "grpc_server_calls_total",
				Help: "Вызовы gRPC методов с кодом завершения",
			},
			[]string{"service", "method", "grpc_code"},
		),
		latency: prometheus.NewHistogramVec(
			prometheus.HistogramOpts{
				Name:    "grpc_server_call_duration_seconds",
				Help:    "Длительность вызовов gRPC методов",
				Buckets: []float64{0.001, 0.005, 0.01, 0.05, 0.1, 0.5},
			},
			[]string{"service", "method"},
		),
	}
	reg.MustRegister(i.reqCounter, i.latency)
	return i
}

func (i *DetailedGRPCInterceptor) Intercept(
	ctx context.Context,
	fullMethod string,
	handler func(ctx context.Context) error,
) error {
	parts := strings.Split(strings.TrimPrefix(fullMethod, "/"), "/")
	service := "Unknown"
	method := "Unknown"
	if len(parts) == 2 {
		service = parts[0]
		method = parts[1]
	}

	start := time.Now()
	err := handler(ctx)
	duration := time.Since(start).Seconds()

	codeStr := "OK"
	if err != nil {
		codeStr = "NotFound"
	}

	i.reqCounter.WithLabelValues(service, method, codeStr).Inc()
	i.latency.WithLabelValues(service, method).Observe(duration)

	return err
}

func TestGRPCInterceptorsDeepDive(t *testing.T) {
	reg := prometheus.NewRegistry()
	interceptor := NewDetailedGRPCInterceptor(reg)

	// Вызов 1: Успех
	_ = interceptor.Intercept(context.Background(), "/BillingService/GetBalance", func(ctx context.Context) error {
		time.Sleep(2 * time.Millisecond)
		return nil
	})

	// Вызов 2: Ошибка NotFound
	_ = interceptor.Intercept(context.Background(), "/BillingService/GetBalance", func(ctx context.Context) error {
		return errors.New("user not found")
	})

	okCount := testutil.ToFloat64(interceptor.reqCounter.WithLabelValues("BillingService", "GetBalance", "OK"))
	notFoundCount := testutil.ToFloat64(interceptor.reqCounter.WithLabelValues("BillingService", "GetBalance", "NotFound"))

	if okCount != 1.0 || notFoundCount != 1.0 {
		t.Fatalf("Ошибка перехватчика: OK=%f, NotFound=%f", okCount, notFoundCount)
	}

	fmt.Println("gRPC Interceptor успешно перехватил вызовы:")
	fmt.Printf("  • /BillingService/GetBalance [OK]:       %.0f вызов\n", okCount)
	fmt.Printf("  • /BillingService/GetBalance [NotFound]: %.0f вызов\n", notFoundCount)
	fmt.Println("  • Автоматический парсинг полного имени метода функционирует штатно!")
}
```

## Под капотом

В производственном gRPC пакете `grpc_prometheus` при вызове `Register()` создается предварительная таблица всех методов сервиса, что позволяет экспортировать нулевые значения метрик сразу при старте сервера.

## Подводные камни

Использовать медленные блокирующие операции (например запись в БД) внутри перехватчика: перехватчик выполняется на критическом пути каждого RPC-запроса, поэтому любая задержка внутри интерцептора напрямую увеличивает время ответа клиенту.

## На собеседовании

**Вопрос с собеседования:** «Зачем нужна инициализация нулевых значений метрик (Zero-Initialization) для всех gRPC методов при старте?»
**Ответ:** Если метод еще ни разу не вызывался, временного ряда для него не существует. В PromQL запрос `rate(grpc_server_handled_total[5m])` вернет пустоту (No Data), а дашборды в Grafana покажут пустые графики или ошибки. Предварительная инициализация нулями гарантирует непрерывность графиков с первой секунды запуска сервиса.
