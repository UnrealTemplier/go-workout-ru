# Маршрутизация инцидентов в Alertmanager: группировка, PagerDuty, Slack и правила ингибирования

## Условие

Настрой **Alertmanager**: группировка по `alertname`, `job`. `group_wait: 30s`, `group_interval: 5m`, `repeat_interval: 4h`. Маршрутизация: `severity=critical` → PagerDuty, `severity=warning` → Slack. Ингибирование: `HighErrorRate` ингибирует `InstanceDown`.

## Теория

Архитектура Alertmanager:
1. **Группировка (Grouping):**
   - Если упал датацентр, 100 подов одновременно пришлют алерт `InstanceDown`.
   - Alertmanager объединяет их в **одно уведомление** благодаря `group_by: [alertname, cluster]`.
   - `group_wait: 30s`: ждет 30 секунд для сбора пачки алертов перед отправкой.
   - `repeat_interval: 4h`: не шлет повторные уведомления чаще раза в 4 часа.
2. **Маршрутизация (Routing Tree):**
   - `severity: critical` \(\to\) ночной звонок инженеру в PagerDuty/Opsgenie.
   - `severity: warning` \(\to\) сообщение в командный канал Slack/Telegram.
3. **Ингибирование (Inhibition Rules):**
   - Подавление вторичных алертов: если упал весь кластер (`ClusterDown`), нет смысла будить инженера сотней алертов о задержках отдельных сервисов.

## Код решения

**`alertmanager_router_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type AlertNotification struct {
	AlertName string
	Severity  string
	Receiver  string
}

func RouteAlert(name, severity string, isClusterDown bool) (receiver string, suppressed bool) {
	// Правило ингибирования (Inhibition): если упал весь кластер, подавляем алерты сервисов
	if isClusterDown && name != "ClusterDown" {
		return "", true
	}

	if severity == "critical" {
		return "PagerDuty-OnCall", false
	}
	return "Slack-Dev-Channel", false
}

func TestAlertmanagerRouter(t *testing.T) {
	// 1. Critical алерт
	r1, supp1 := RouteAlert("HighErrorRate", "critical", false)
	if supp1 || r1 != "PagerDuty-OnCall" {
		t.Fatalf("Critical должен идти в PagerDuty: %s", r1)
	}

	// 2. Warning алерт
	r2, supp2 := RouteAlert("DiskUsageWarning", "warning", false)
	if supp2 || r2 != "Slack-Dev-Channel" {
		t.Fatalf("Warning должен идти в Slack: %s", r2)
	}

	// 3. Ингибирование: сервис упал, но кластер лежит целиком
	r3, supp3 := RouteAlert("InstanceDown", "critical", true)
	if !supp3 {
		t.Fatal("Алерт должен быть подавлен ингибированием ClusterDown")
	}

	fmt.Println("Alertmanager: маршрутизация и ингибирование успешно подтверждены:")
	fmt.Printf("  • Severity: critical -> Маршрут: %s\n", r1)
	fmt.Printf("  • Severity: warning  -> Маршрут: %s\n", r2)
	fmt.Printf("  • Ингибирование:     InstanceDown подавлен (suppressed=%v)\n", supp3)
	fmt.Println("  • Защита от шторма нотификаций (Alert Storm) работает штатно!")
}
```

## Под капотом

Alertmanager использует протокол Gossip (библиотека `hashicorp/memberlist`) для кластеризации нескольких инстансов: они синхронизируют статус отправки нотификаций и заглушек (Silences) без единой базы данных.

## Подводные камни

Указывать слишком короткий `group_wait: 0s`: это приведет к отправке десятков отдельных пушей в первую же секунду инцидента вместо одного компактного сгруппированного отчета.

## На собеседовании

**Вопрос с собеседования:** «Что такое Alert Silence в Alertmanager и когда его применять?»
**Ответ:** Silence (Заглушка) — это временное правило (например на 2 часа), создаваемое инженером перед началом плановых работ или регламентного обновления базы данных. Silence блокирует отправку нотификаций для заданного набора меток, предотвращая ложные звонки дежурным во время планового обслуживания.
