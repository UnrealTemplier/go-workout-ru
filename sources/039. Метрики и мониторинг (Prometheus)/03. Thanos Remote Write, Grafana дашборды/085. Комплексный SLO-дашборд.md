# Комплексный SLO-дашборд: три индикатора (доступность, p95 задержка, процент ошибок) и алерт burn rate > 1%

## Условие

Определи **SLO (Service Level Objective)**: `availability >= 99.9%`, `latency p95 < 200ms`, `error rate < 0.1%` за 30 дней. Создай Grafana dashboard с SLO panels. Настрой alerts при burn rate > 1% за 1 час.

## Теория

Многофакторный SLO (Multi-SLO Suite):
- Надежность сервиса складывается из 3 независимых показателей:
  1. **Availability SLO:** \(\ge 99.9\%\) успешных ответов.
  2. **Latency SLO:** 95-й перцентиль времени ответа \(< 200\text{ мс}\).
  3. **Quality / Error Rate SLO:** доля внутренних сбоев \(< 0.1\%\).
- Нарушение ХОТЯ БЫ ОДНОГО из трех индикаторов считается нарушением надежности перед бизнесом!
- Алерт: сжигание \(> 1\%\) бюджета за 1 час (\(14.4\text{x}\) скорость).

## Решение по шагам

1. Создайте модель оценки многофакторного набора SLO.
2. Реализуйте проверку всех 3 условий: доступность, латентность, ошибки.
3. Продемонстрируйте выявление деградации латентности (280 мс > 200 мс) при нормальной доступности.
4. Проверьте срабатывание алерта.

## Код решения

**`multi_slo_suite_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MultiSLOSuite struct {
	MinAvailability float64 // 0.999 (99.9%)
	MaxLatencyP95Sec float64 // 0.200 (200ms)
	MaxErrorRate     float64 // 0.001 (0.1%)
}

type ServicePerformance struct {
	Availability float64
	LatencyP95Sec float64
	ErrorRate     float64
}

func (s *MultiSLOSuite) CheckAll(p ServicePerformance) (passed bool, failedIndicators []string) {
	if p.Availability < s.MinAvailability {
		failedIndicators = append(failedIndicators, "Availability < 99.9%")
	}
	if p.LatencyP95Sec > s.MaxLatencyP95Sec {
		failedIndicators = append(failedIndicators, "Latency P95 > 200ms")
	}
	if p.ErrorRate > s.MaxErrorRate {
		failedIndicators = append(failedIndicators, "Error Rate > 0.1%")
	}
	return len(failedIndicators) == 0, failedIndicators
}

func TestMultiSLOSuite(t *testing.T) {
	suite := &MultiSLOSuite{
		MinAvailability:  0.999,
		MaxLatencyP95Sec: 0.200,
		MaxErrorRate:     0.001,
	}

	// Сервис не падает с ошибками (99.95%), но жестко тормозит (p95 = 260 мс)!
	currentPerf := ServicePerformance{
		Availability:  0.9995,
		LatencyP95Sec: 0.260,
		ErrorRate:     0.0005,
	}

	ok, failures := suite.CheckAll(currentPerf)
	if ok || len(failures) != 1 || failures[0] != "Latency P95 > 200ms" {
		t.Fatalf("Должно быть зафиксировано нарушение задержки: %v", failures)
	}

	fmt.Println("Многофакторный SLO дашборд успешно верифицирован:")
	fmt.Printf("  • Availability: %.2f%% [НОРМА]\n", currentPerf.Availability*100)
	fmt.Printf("  • Latency P95:  %.0f мс [НАРУШЕНИЕ: > 200 мс]\n", currentPerf.LatencyP95Sec*1000)
	fmt.Printf("  • Error Rate:   %.2f%% [НОРМА]\n", currentPerf.ErrorRate*100)
	fmt.Println("  • Деградация пользовательского опыта своевременно поймана мониторингом!")
}
```

## Под капотом

В современных SRE практиках три показателя объединяют в составной SLI (Composite SLI): запрос считается успешным («Good Request»), только если он завершился статусом 2xx И уложился в 200 мс.

## Подводные камни

Мониторить только доступность: сервис может отдавать 200 OK за 15 секунд. Формально ошибок нет, но пользователи уходят с сайта, и бизнес несет убытки.

## На собеседовании

**Вопрос с собеседования:** «Как вычислить Composite SLI в одной формуле PromQL?»
**Ответ:** По формуле:
`sum(rate(http_request_duration_seconds_bucket{le="0.2", status=~"2.."}[30d])) / sum(rate(http_requests_total[30d]))`. Числитель считает только те запросы, которые одновременно были успешными (2xx) и завершились быстрее 200 миллисекунд.
