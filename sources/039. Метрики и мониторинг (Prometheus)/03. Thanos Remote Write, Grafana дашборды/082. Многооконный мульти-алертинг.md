# Многооконный мульти-алертинг (Multi-Window Multi-Burn-Rate): подход Google SRE для исключения ложных тревог

## Условие

Используйте `multi-window, multi-burn-rate alerting` (Google SRE подход): быстрые и медленные окна для снижения ложных срабатываний.

## Теория

Архитектура Multi-Window Multi-Burn-Rate по стандарту Google SRE Workbook:
- **Проблема одного окна:**
  - Если сбой длился 5 минут и прекратился, часовое окно будет гореть (FIRING) еще 55 минут, дезориентируя команду!
- **Решение Google SRE — сопряжение двух окон (длинного и короткого):**
  - Длинное окно (Long Window, например 1 час): проверяет, что сбой достаточно масштабен.
  - Короткое окно (Short Window, 5 минут = \(\frac{1}{12}\) от длинного): проверяет, что **сбой все еще продолжается прямо сейчас**!
- Алерт срабатывает, только если **ОБА условия истинны**:
  `BurnRate(1h) > 14.4 AND BurnRate(5m) > 14.4`.
- Если авария устранена, короткое окно мгновенно гаснет, и алерт автоматически снимается (Resolved)!

## Решение по шагам

1. Создайте модель оценки с двумя окнами (1 час и 5 минут).
2. Проверьте сценарий активной аварии: оба окна превышают порог \(\to\) FIRING.
3. Проверьте сценарий устранения аварии: длинное окно еще горячее, но короткое остыло \(\to\) RESOLVED.
4. Убедитесь в отсутствии ложных срабатываний.

## Код решения

**`multi_window_burn_rate_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type MultiWindowBurnRateChecker struct {
	Threshold float64
}

func (c *MultiWindowBurnRateChecker) IsFiring(longWindowRate, shortWindowRate float64) bool {
	// Алерт активен строго тогда, когда ОБА окна превышают порог
	return longWindowRate > c.Threshold && shortWindowRate > c.Threshold
}

func TestMultiWindowBurnRate(t *testing.T) {
	checker := &MultiWindowBurnRateChecker{Threshold: 0.0144} // 14.4x

	// 1. Авария началась: оба окна горят -> FIRING
	activeFiring := checker.IsFiring(0.025, 0.030)
	if !activeFiring {
		t.Fatal("Алерт должен быть Firing во время активного сбоя")
	}

	// 2. Инженер сделал откат деплоя (Rollback):
	// Длинное окно 1h еще помнит прошлый сбой (0.018 > 0.0144),
	// но короткое окно 5m уже чистое (0.001 < 0.0144)!
	resolved := !checker.IsFiring(0.018, 0.001)
	if !resolved {
		t.Fatal("Алерт обязан автоматически перейти в RESOLVED благодаря короткому окну!")
	}

	fmt.Println("Multi-Window Multi-Burn-Rate (Google SRE) успешно подтвержден:")
	fmt.Printf("  • Активная авария:   Long=0.025, Short=0.030 -> FIRING [Оба окна активны]\n")
	fmt.Printf("  • После отката кода: Long=0.018, Short=0.001 -> RESOLVED [Короткое окно остыло]\n")
	fmt.Println("  • Полное устранение эффекта «залипших» алертов после починки сервиса!")
}
```

ℹ️ Двухоконная валидация темпа сжигания бюджета для исключения залипания алертов

## Под капотом

В Google SRE матрица содержит 4 правила: критические (14.4x за 1h/5m и 6x за 6h/30m) и некритические для рабочих тикетов (1x за 3d/6h).

## Подводные камни

Использовать одинаковый интервал для обоих окон: короткое окно обязано быть в 10–12 раз меньше длинного, иначе теряется смысл сопряжения.

## На собеседовании

**Вопрос с собеседования:** «В чем главная ценность короткого окна в Multi-Window подходе?»
**Ответ:** Короткое окно отвечает за мгновенное снятие алерта (Alert Reset). Как только баг починен и ошибки прекратились, короткое окно очищается за 2–5 минут, переводя алерт в статус RESOLVED и позволяя дежурному инженеру сразу увидеть, что принятые меры помогли.
