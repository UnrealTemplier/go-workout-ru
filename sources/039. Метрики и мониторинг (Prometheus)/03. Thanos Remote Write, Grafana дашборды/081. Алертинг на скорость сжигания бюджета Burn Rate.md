# Алертинг на скорость сжигания бюджета Burn Rate: детекция расхода в 14x быстрее нормы (Critical P0)

## Условие

Напишите алерт на **burn rate**: если error budget сжигается в 14x быстрее нормы — критический алерт.

## Теория

Математика коэффициента сжигания бюджета (Burn Rate):
- Скорость \(1\text{x Burn Rate}\) означает, что за 30 дней будет потрачено ровно 100% бюджета ошибок.
- Скорость **\(14.4\text{x Burn Rate}\)**:
  - За 1 час расходуется \(2\%\) от всего месячного бюджета!
  - Весь месячный бюджет сгорит всего за 2 дня (50 часов).
- Это критический сбой P0, требующий немедленной побудки дежурного инженера среди ночи.
- **Формула в PromQL (окно 1 час):**
  $$\frac{\sum \text{rate}(http\_requests\_total\{status=\sim"5.." \}[1h])}{\sum \text{rate}(http\_requests\_total[1h])} > 14.4 \times (1 - \text{SLO})$$

## Решение по шагам

1. Создайте модель вычисления коэффициента Burn Rate.
2. Проверьте условие: при норме ошибок \(0.001\) (SLO 99.9%) порог \(14.4\text{x}\) составляет \(0.0144\) (1.44% сбоев).
3. Смоделируйте аварию с 2% ошибок и проверьте генерацию Critical P0 алерта.
4. Проверьте штатный трафик с 0.05% ошибок.

## Код решения

**`burn_rate_alert_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BurnRateAlertEngine struct {
	TargetSLO    float64 // 0.999
	BurnFactor   float64 // 14.4
}

func (e *BurnRateAlertEngine) Evaluate(currentErrorRate float64) (isCriticalFiring bool, threshold float64) {
	allowedBudget := 1.0 - e.TargetSLO
	threshold = e.BurnFactor * allowedBudget
	return currentErrorRate > threshold, threshold
}

func TestBurnRateAlert(t *testing.T) {
	engine := &BurnRateAlertEngine{
		TargetSLO:  0.999, // 99.9%
		BurnFactor: 14.4,  // 14.4x быстрее нормы
	}

	// 1. Штатный режим (0.05% ошибок = 0.0005) -> норма
	f1, _ := engine.Evaluate(0.0005)
	if f1 {
		t.Fatal("0.05% ошибок не должно вызывать 14x burn rate алерт")
	}

	// 2. Авария: 2% запросов падают (0.02 > 0.0144) -> CRITICAL P0!
	f2, threshold := engine.Evaluate(0.02)
	if !f2 {
		t.Fatal("2% ошибок обязаны зажечь 14x burn rate алерт")
	}

	fmt.Println("Алерт на скорость сжигания бюджета (Burn Rate 14.4x) успешно подтвержден:")
	fmt.Printf("  • Целевой SLO:      99.9%% (Базовый бюджет: 0.1%% ошибок)\n")
	fmt.Printf("  • Порог 14.4x Burn: %.4f (%.2f%% ошибок в течение 1 часа)\n", threshold, threshold*100)
	fmt.Printf("  • Текущие ошибки:   2.00%% -> СТАТУС: CRITICAL P0 FIRING!\n")
	fmt.Println("  • Нотификация немедленно отправлена на телефон дежурного инженера!")
}
```

## Под капотом

Burn Rate алерты не зависят от колебаний суточного трафика (Day/Night cycles): они одинаково надежно работают как в часы пик, так и ночью, оценивая относительную долю сжигания запаса надежности.

## Подводные камни

Использовать маленькое окно времени (например 1 минуту) для расчета 14x Burn Rate: кратковременный единичный сбой сожжет меньше 0.001% бюджета, но вызовет ложный звонок инженеру. Окно для 14.4x выбирают равным 1 часу.

## На собеседовании

**Вопрос с собеседования:** «Почему в Google SRE отказались от простых алертов по порогу ошибок и перешли на Burn Rate?»
**Ответ:** Простой алерт «ошибок > 1%» имеет фатальные недостатки: при высоком трафике 1% ошибок может сжечь весь бюджет за полдня, а при низком ночном трафике 1% ошибок — это всего 2 запроса, которые не представляют опасности. Burn Rate оценивает реальную скорость расхода бюджета компании, устраняя 95% ложных срабатываний.
