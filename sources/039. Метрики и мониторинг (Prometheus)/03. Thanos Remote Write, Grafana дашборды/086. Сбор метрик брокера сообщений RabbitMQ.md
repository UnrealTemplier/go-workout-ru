# Сбор метрик брокера сообщений RabbitMQ: мониторинг очередей, скорости публикации и доставки

## Условие

Соберите метрики RabbitMQ: количество сообщений в очереди, скорость публикации и доставки. Используйте готовый экспортер или Management API.

## Теория

Инструментирование очереди сообщений RabbitMQ:
- Официальный плагин `rabbitmq_prometheus` (встроен в RabbitMQ 3.8+ на порту `:15692/metrics`):
  - `rabbitmq_queue_messages_ready`: сообщения, ожидающие вычитки консьюмерами.
  - `rabbitmq_queue_messages_unacked`: сообщения, взятые консьюмерами в обработку, но еще не подтвержденные через `Ack`.
  - `rabbitmq_queue_messages_published_total`: суммарная скорость публикации сообщений (Publish Rate).
  - `rabbitmq_queue_messages_delivered_total`: скорость доставки консьюмерам (Delivery Rate).
- Зависание сообщений в статусе `unacked` свидетельствует о зависших воркерах.

## Решение по шагам

1. Создайте структуру метрик очереди RabbitMQ.
2. Смоделируйте состояние очереди с 1200 готовыми и 150 неподтвержденными сообщениями.
3. Рассчитайте пропускную способность (Publish vs Deliver).
4. Проверьте экспорт в тестовый реестр.

## Код решения

**`rabbitmq_metrics_suite_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type RabbitMQQueueMetrics struct {
	messagesReady   *prometheus.GaugeVec
	messagesUnacked *prometheus.GaugeVec
	publishedTotal  *prometheus.CounterVec
	deliveredTotal  *prometheus.CounterVec
}

func NewRabbitMQMetrics(reg *prometheus.Registry) *RabbitMQQueueMetrics {
	m := &RabbitMQQueueMetrics{
		messagesReady: prometheus.NewGaugeVec(
			prometheus.GaugeOpts{Name: "rabbitmq_queue_messages_ready", Help: "Готовые к вычитке сообщения"},
			[]string{"queue"},
		),
		messagesUnacked: prometheus.NewGaugeVec(
			prometheus.GaugeOpts{Name: "rabbitmq_queue_messages_unacked", Help: "Сообщения в обработке (ожидают Ack)"},
			[]string{"queue"},
		),
		publishedTotal: prometheus.NewCounterVec(
			prometheus.CounterOpts{Name: "rabbitmq_queue_messages_published_total", Help: "Опубликовано сообщений"},
			[]string{"queue"},
		),
		deliveredTotal: prometheus.NewCounterVec(
			prometheus.CounterOpts{Name: "rabbitmq_queue_messages_delivered_total", Help: "Доставлено воркерам сообщений"},
			[]string{"queue"},
		),
	}
	reg.MustRegister(m.messagesReady, m.messagesUnacked, m.publishedTotal, m.deliveredTotal)
	return m
}

func TestRabbitMQMetricsSuite(t *testing.T) {
	reg := prometheus.NewRegistry()
	rmq := NewRabbitMQMetrics(reg)

	queue := "orders_processing_queue"

	// Устанавливаем текущее состояние
	rmq.messagesReady.WithLabelValues(queue).Set(1250)
	rmq.messagesUnacked.WithLabelValues(queue).Set(180)
	rmq.publishedTotal.WithLabelValues(queue).Add(5000)
	rmq.deliveredTotal.WithLabelValues(queue).Add(4800)

	ready := testutil.ToFloat64(rmq.messagesReady.WithLabelValues(queue))
	unacked := testutil.ToFloat64(rmq.messagesUnacked.WithLabelValues(queue))

	if ready != 1250.0 || unacked != 180.0 {
		t.Fatalf("Ошибка RabbitMQ метрик: ready=%f, unacked=%f", ready, unacked)
	}

	fmt.Println("Телеметрия RabbitMQ успешно подтверждена:")
	fmt.Printf("  • Очередь:             %s\n", queue)
	fmt.Printf("  • Ready messages:      %.0f (Ожидают свободных воркеров)\n", ready)
	fmt.Printf("  • Unacked messages:    %.0f (Активно обрабатываются)\n", unacked)
	fmt.Println("  • Мониторинг очередей RabbitMQ готов для продакшен алертинга!")
}
```

## Под капотом

Встроенный плагин `rabbitmq_prometheus` написан на Erlang и собирает метрики напрямую из структур данных процессов Erlang ETS/Mnesia с минимальным оверхедом на CPU брокера.

## Подводные камни

Использовать старый `rabbitmq_exporter`, опрашивающий REST Management API по HTTP на порту 15672: при 50 000 очередей HTTP API RabbitMQ зависает от генерации огромных JSON. Встроенный порт `:15692` на порядки быстрее и безопаснее.

## На собеседовании

**Вопрос с собеседования:** «Какой алерт по RabbitMQ настроить для детекции "зависших" воркеров?»
**Ответ:** Алерт на стабильно высокое или растущее число `messages_unacked` при одновременном падении скорости подтверждений `rate(messages_delivered_total) == 0`. Это означает, что воркер взял сообщения, заблокировался в бесконечном цикле или дедлоке и не отправляет `Ack/Nack`.
