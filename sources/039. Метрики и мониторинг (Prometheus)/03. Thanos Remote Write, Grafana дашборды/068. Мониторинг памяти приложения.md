# Мониторинг памяти приложения: сравнение process_resident_memory_bytes (RSS) и go_memstats_alloc_bytes

## Условие

Добавьте панель: `process_resident_memory_bytes` и `go_memstats_alloc_bytes` — использование памяти (RSS vs Go heap).

## Теория

Разница между памятью кучи (Heap Alloc) и резидентной памятью процесса (RSS):
- `go_memstats_alloc_bytes`:
  - Объем активных объектов в Go куче, доступных через указатели.
- `process_resident_memory_bytes` (RSS):
  - Фактическая физическая память, выделенная операционной системой Linux процессу (Resident Set Size).
  - Включает: кучу Go, стеки всех горутин, структуры рантайма, код бинарника и память, освобожденную GC, но **еще не возвращенную ОС** (`madvise`).
- Если RSS приближается к лимиту памяти пода в Kubernetes (`limits.memory`), Linux OOM Killer уничтожит контейнер, даже если `go_memstats_alloc_bytes` составляет всего 30% лимита!

## Решение по шагам

1. Создайте модель замера памяти процесса и кучи.
2. Проверьте соотношение: RSS обязан быть больше или равен Heap Alloc.
3. Продемонстрируйте вычисление фрагментации памяти и резерва ОС.
4. Сформируйте рекомендации по настройке `GOMEMLIMIT`.

## Код решения

**`rss_vs_heap_memory_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ProcessMemoryStats struct {
	HeapAllocBytes int64 // go_memstats_alloc_bytes
	RSSBytes       int64 // process_resident_memory_bytes
	K8sLimitBytes  int64 // resources.limits.memory
}

func AnalyzeMemoryOverhead(m ProcessMemoryStats) (fragmentationMB float64, headroomMB float64) {
	frag := float64(m.RSSBytes-m.HeapAllocBytes) / (1024 * 1024)
	headroom := float64(m.K8sLimitBytes-m.RSSBytes) / (1024 * 1024)
	return frag, headroom
}

func TestRSSVsHeapMemory(t *testing.T) {
	stats := ProcessMemoryStats{
		HeapAllocBytes: 150 * 1024 * 1024, // 150 МБ в куче Go
		RSSBytes:       280 * 1024 * 1024, // 280 МБ физической памяти занято (RSS)
		K8sLimitBytes:  512 * 1024 * 1024, // 512 МБ лимит K8s пода
	}

	fragMB, headroomMB := AnalyzeMemoryOverhead(stats)

	if fragMB != 130.0 || headroomMB != 232.0 {
		t.Fatalf("Некорректный расчет памяти: frag=%f, headroom=%f", fragMB, headroomMB)
	}

	fmt.Println("Сравнение памяти RSS и Go Heap Alloc:")
	fmt.Printf("  • Активная куча (Go Heap): %.1f МБ\n", float64(stats.HeapAllocBytes)/(1024*1024))
	fmt.Printf("  • Память ОС (Linux RSS):   %.1f МБ\n", float64(stats.RSSBytes)/(1024*1024))
	fmt.Printf("  • Оверхед рантайма / стеки: %.1f МБ\n", fragMB)
	fmt.Printf("  • Запас до K8s OOM Killer:  %.1f МБ\n", headroomMB)
	fmt.Println("  • Мониторинг RSS критичен для защиты контейнера от внезапного убийства!")
}
```

## Под капотом

Начиная с Go 1.19, переменная окружения `GOMEMLIMIT` задает мягкий лимит памяти (например `GOMEMLIMIT=450MiB`). Рантайм Go начинает более агрессивно запускать GC при приближении к лимиту, предотвращая разрастание RSS до границы K8s OOM.

## Подводные камни

Выставлять `GOMEMLIMIT` ровно в 100% лимита K8s: рантайм Go контролирует только свою память, но память бинарника, C-библиотек и стеков потоков ОС не учитывается в куче. Оптимально выставлять `GOMEMLIMIT` на уровне 80–85% от `limits.memory`.

## На собеседовании

**Вопрос с собеседования:** «Почему после освобождения объектов в Go память RSS процесса в htop/Prometheus не уменьшается немедленно?»
**Ответ:** Рантайм Go не возвращает память операционной системе сразу через `free()`. Он помечает страницы системным вызовом `madvise(MADV_DONTNEED / MADV_FREE)`, сообщая ядру Linux, что память можно забрать при нехватке. Но пока у ОС есть свободная RAM, страницы остаются закрепленными за процессом, удерживая высокий RSS для ускорения будущих аллокаций.
