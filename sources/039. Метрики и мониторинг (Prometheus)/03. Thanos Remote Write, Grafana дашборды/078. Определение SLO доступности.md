# Определение SLO доступности: формулировка цели 99.9% успешных запросов за 30-дневное скользящее окно

## Условие

Определите **SLO** (Service Level Objective): "99.9% запросов успешны за 30-дневное окно".

## Теория

Формализация Service Level Objective (SLO):
- Цель: «Не менее 99.9% всех HTTP-запросов к API возвращают статус 2xx/3xx/4xx за любое скользящее 30-дневное окно».
- **Почему окно 30 дней, а не 1 день:**
  - 30-дневное окно нивелирует влияние локальных суточных всплесков.
  - Позволяет планировать разработку спринтами (обычно 2 или 4 недели).
  - Дает точное представление о надежности для пользователей.

## Решение по шагам

1. Создайте спецификацию SLO с целевым порогом 99.9% и окном 30 дней.
2. Реализуйте проверку выполнения SLO по исторической статистике.
3. Продемонстрируйте статус выполнения цели (Compliant vs Violated).
4. Проверьте корректность расчетов.

## Код решения

**`slo_specification_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type SLOSpecification struct {
	Name            string
	TargetThreshold float64 // 0.999
	Window          time.Duration
}

func (s *SLOSpecification) EvaluateCompliance(actualSLI float64) (compliant bool, diffPercent float64) {
	compliant = actualSLI >= s.TargetThreshold
	diffPercent = (actualSLI - s.TargetThreshold) * 100.0
	return compliant, diffPercent
}

func TestSLOSpecification(t *testing.T) {
	slo := SLOSpecification{
		Name:            "Core-API-Availability",
		TargetThreshold: 0.999, // 99.9%
		Window:          30 * 24 * time.Hour,
	}

	actualSLI := 0.9994 // 99.94%
	compliant, diff := slo.EvaluateCompliance(actualSLI)

	if !compliant {
		t.Fatal("SLO должен быть выполнен при SLI 99.94%")
	}

	fmt.Println("Спецификация SLO успешно верифицирована:")
	fmt.Printf("  • Цель (SLO):          %.1f%% за 30 дней скользящего окна\n", slo.TargetThreshold*100)
	fmt.Printf("  • Фактический результат: %.2f%% (Запас: +%.3f%%)\n", actualSLI*100, diff)
	fmt.Printf("  • Статус соответствия: COMPLIANT [Цель достигнута]\n")
}
```

ℹ️ Декларативное описание и верификация соответствия цели SLO 99.9%

## Под капотом

В мониторинге для расчета 30-дневного окна применяют функцию PromQL `avg_over_time` или суммируют предвычисленные 5-минутные блоки Recording Rules за \(30 \times 24 \times 12 = 8640\) интервалов.

## Подводные камни

Устанавливать нереалистичный SLO 100%: 100% доступности не существует в распределенных системах (оптоволокно экскаватором рвется, сбоят коммутаторы, происходят плановые перезагрузки K8s нод). Стремление к 100% парализует бизнес и разработку.

## На собеседовании

**Вопрос с собеседования:** «Почему в BigTech SLO сервиса всегда жестче, чем внешний SLA для клиентов?»
**Ответ:** Если SLA гарантирует клиентам 99.5%, внутренний SLO устанавливают на уровне 99.9%. Разница в 0.4% — это запас безопасности (Safety Buffer). Если сервис начинает сбоить, внутренние алерты будят инженеров задолго до того, как нарушение коснется SLA и повлечет финансовые выплаты клиентам.
