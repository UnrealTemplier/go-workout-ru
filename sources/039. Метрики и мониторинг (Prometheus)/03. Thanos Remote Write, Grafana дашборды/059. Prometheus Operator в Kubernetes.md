# Prometheus Operator в Kubernetes: декларативные CRD ServiceMonitor и PodMonitor в GitOps

## Условие

Настрой **Prometheus Operator** (Kubernetes): `ServiceMonitor` CRD автоматически конфигурирует Prometheus. `PodMonitor` для sidecars. Покажи GitOps approach.

### Исходная формулировка

Настрой **Prometheus Operator** (Kubernetes): `ServiceMonitor` CRD автоматически конфигурирует Prometheus. `PodMonitor` для sidecars. Покажи GitOps approach.

---

## Теория

Декларативное управление мониторингом через Prometheus Operator:
- Вместо ручной правки единого файла `prometheus.yml`:
  - Разработчики кладут манифест `ServiceMonitor` прямо в Helm-чарт своего микросервиса.
  - Оператор автоматически считывает `ServiceMonitor`, валидирует его и генерирует конфигурацию скрейпа для инстанса Prometheus.
- **Спецификация ServiceMonitor:**
  ```yaml
  apiVersion: monitoring.coreos.com/v1
  kind: ServiceMonitor
  metadata:
    name: order-service-monitor
    labels:
      release: prometheus-stack
  spec:
    selector:
      matchLabels:
        app: order-service
    endpoints:
      - port: metrics
        interval: 15s
        path: /metrics
  ```
- Для подов без K8s Service (например, standalone демоны или sidecar-контейнеры) используется `PodMonitor`.

## Решение по шагам

1. Создайте модель манифеста `ServiceMonitor` и `PodMonitor`.
2. Реализуйте селектор совпадения меток сервиса (`matchLabels`).
3. Продемонстрируйте автоматическую генерацию таргетов скрейпа.
4. Верифицируйте соответствие GitOps-стандартам.

## Код решения

**`servicemonitor_operator_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ServiceMonitorSpec struct {
	Name        string
	TargetApp   string
	PortName    string
	Interval    string
	MetricsPath string
}

func MatchServiceToMonitor(serviceLabels map[string]string, sm ServiceMonitorSpec) bool {
	return serviceLabels["app"] == sm.TargetApp
}

func TestServiceMonitorOperator(t *testing.T) {
	sm := ServiceMonitorSpec{
		Name:        "order-service-monitor",
		TargetApp:   "order-service",
		PortName:    "metrics",
		Interval:    "15s",
		MetricsPath: "/metrics",
	}

	appServiceLabels := map[string]string{
		"app":     "order-service",
		"release": "production",
	}

	otherServiceLabels := map[string]string{
		"app": "auth-service",
	}

	if !MatchServiceToMonitor(appServiceLabels, sm) {
		t.Fatal("ServiceMonitor обязан матчить order-service")
	}

	if MatchServiceToMonitor(otherServiceLabels, sm) {
		t.Fatal("ServiceMonitor не должен матчить auth-service")
	}

	fmt.Println("Prometheus Operator ServiceMonitor успешно подтвержден:")
	fmt.Printf("  • CRD:         monitoring.coreos.com/v1/ServiceMonitor\n")
	fmt.Printf("  • Имя монитора: %s (TargetApp: %s)\n", sm.Name, sm.TargetApp)
	fmt.Printf("  • Скрейп:      %s по порту '%s'\n", sm.Interval, sm.PortName)
	fmt.Println("  • GitOps подход: конфигурация мониторинга хранится рядом с кодом сервиса!")
}
```

## Под капотом

Prometheus Operator запускает контроллер, который слушает Kubernetes API events по CRD `ServiceMonitor`, собирает конфигурацию в секрет `prometheus-k8s-rulefiles` и вызывает перечитывание конфига через HTTP POST `/-/reload`.

## Подводные камни

Забыть добавить лейбл `release: <helm-release-name>` в метаданные `ServiceMonitor`: по умолчанию инстанс Prometheus скрейпит только те мониторы, чьи лейблы совпадают с селектором `serviceMonitorSelector` в спецификации оператора.

## На собеседовании

**Вопрос с собеседования:** «Когда вместо ServiceMonitor необходимо использовать PodMonitor?»
**Ответ:** Когда поды не объединены в `Service` (например, DaemonSet сборщиков логов, задачи Envoy sidecar в Service Mesh или воркеры фоновых очередей, которые не принимают входящих клиентских подключений). `PodMonitor` напрямую находит поды по селектору меток пода.
