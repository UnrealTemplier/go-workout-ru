# Диагностика утечек горутин: мониторинг метрики go_goroutines и паттерны предотвращения утечек

## Условие

Добавьте панель: `go_goroutines` — количество активных горутин. Объясните, почему резкий рост — это признак goroutine leak.

## Теория

Природа и диагностика утечек горутин (Goroutine Leaks):
- Горутина в Go весит от 2 КБ до десятков мегабайт (включая переменные, захваченные в стек и замыкания).
- В рантайме Go сборщик мусора (GC) **НЕ собирает работающие или заблокированные горутины**!
- **Причины утечек горутин:**
  1. Чтение из небуферизованного канала, в который больше никто не пишет.
  2. Запись в канал, из которого никто не читает (зависший консьюмер).
  3. Сетевой вызов без таймаута (`http.Get` без `context.WithTimeout`).
  4. Забытый `cancel()` контекста при использовании `context.WithCancel`.

## Решение по шагам

1. Создайте модель отслеживания динамики метрики `go_goroutines`.
2. Смоделируйте нормальное состояние сервиса (базовый уровень 20 горутин).
3. Смоделируйте утечку (рост до 2000 горутин).
4. Проверьте генерацию предупреждения об утечке.

## Код решения

**`goroutine_leak_detector_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type GoroutineMonitor struct {
	baselineCount int
}

func (m *GoroutineMonitor) CheckLeak(currentCount int) (isLeaking bool, msg string) {
	// Рост более чем в 10 раз от базы свидетельствует об утечке
	if currentCount > m.baselineCount*10 {
		return true, fmt.Sprintf("КРИТИЧЕСКАЯ УТЕЧКА ГОРУТИН: текущее число %d (база %d)", currentCount, m.baselineCount)
	}
	return false, "OK"
}

func TestGoroutineLeakDetector(t *testing.T) {
	mon := &GoroutineMonitor{baselineCount: 25}

	leak1, _ := mon.CheckLeak(30)
	if leak1 {
		t.Fatal("30 горутин не должно считаться утечкой")
	}

	leak2, msg := mon.CheckLeak(4500)
	if !leak2 {
		t.Fatal("4500 горутин обязаны вызвать алерт утечки")
	}

	fmt.Println("Диагностика утечки горутин (go_goroutines) подтверждена:")
	fmt.Printf("  • Базовый уровень: 25 горутин\n")
	fmt.Printf("  • Аномальный рост: 4500 горутин\n")
	fmt.Printf("  • Диагноз:         %s\n", msg)
	fmt.Println("  • Мониторинг go_goroutines позволяет предотвратить OOMKilled контейнеров!")
}
```

## Под капотом

При утечке горутин растет не только память стеков, но и размер структур планировщика GMP (`runtime.g`), что приводит к деградации циклов `sysmon` и увеличению накладных расходов на переключение контекста.

## Подводные камни

Пытаться убить зависшую горутину снаружи: в языке Go невозможно принудительно остановить горутину из другого потока! Горутина обязана завершаться сама по сигналу отмены `<-ctx.Done()`.

## На собеседовании

**Вопрос с собеседования:** «Как на живом поде в продакшене локализовать место утечки горутин?»
**Ответ:** Запросить дамп горутин через pprof: `curl http://localhost:9090/debug/pprof/goroutine?debug=2`. В выводе будут перечислены стектрейсы всех запущенных горутин с указанием номеров строк кода и причин блокировки (например, `chan receive`, `select`, `IO wait`), что позволяет мгновенно найти застрявший вызов.
