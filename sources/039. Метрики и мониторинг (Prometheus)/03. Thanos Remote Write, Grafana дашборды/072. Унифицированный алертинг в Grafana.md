# Унифицированный алертинг в Grafana (Unified Alerting) в сравнении с Prometheus Alertmanager

## Условие

Создай **Alerting в Grafana** (Unified Alerting): alert rule `avg(cpu_usage) > 80`, notification channel Slack. Покажи difference vs Prometheus Alertmanager.

## Теория

Сравнение Grafana Unified Alerting и Prometheus Alertmanager:
| Критерий | Grafana Unified Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Источники данных** | **Мульти-источники** (Prometheus, Loki, Postgres, CloudWatch) | **Строго метрики Prometheus** |
| **Управление** | Удобный веб-интерфейс UI + API | Конфигурационные файлы YAML / GitOps |
| **Визуализация в алерте** | **Скриншот графика инцидента** прямо в Slack/Telegram | Только текстовые строки и ссылки |
| **Надежность при аварии** | Зависит от доступности Grafana | **Экстремально высокая** (отказоустойчивый Go-демон) |
- В BigTech критические алерты инфраструктуры держат в **Alertmanager**, а продуктовые алерты бизнес-дашбордов настраивают в **Grafana**.

## Решение по шагам

1. Создайте модель правила Grafana Alert Rule `avg(cpu_usage) > 80`.
2. Реализуйте канал отправки Slack с прикреплением скриншота графика.
3. Сравните сценарии применения с Alertmanager.
4. Сделайте вывод об архитектурном разделении зон ответственности.

## Код решения

**`grafana_unified_alerting_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type GrafanaAlertRule struct {
	Title       string
	Condition   string
	Threshold   float64
	Channel     string
	HasImageURL bool
}

func EvaluateGrafanaAlert(cpu float64, rule GrafanaAlertRule) (fired bool, notification string) {
	if cpu > rule.Threshold {
		imgText := ""
		if rule.HasImageURL {
			imgText = " [Вложено изображение графика дашборда]"
		}
		return true, fmt.Sprintf("Алерт в %s: %s (CPU=%.1f%% > %.0f%%)%s",
			rule.Channel, rule.Title, cpu, rule.Threshold, imgText)
	}
	return false, "OK"
}

func TestGrafanaUnifiedAlerting(t *testing.T) {
	rule := GrafanaAlertRule{
		Title:       "HighCPUUtilization",
		Condition:   "avg(cpu_usage) > 80",
		Threshold:   80.0,
		Channel:     "Slack #dev-alerts",
		HasImageURL: true,
	}

	fired, notif := EvaluateGrafanaAlert(88.5, rule)
	if !fired {
		t.Fatal("Алерт должен сработать при CPU 88.5%")
	}

	fmt.Println("Grafana Unified Alerting успешно протестирован:")
	fmt.Printf("  • Условие:       %s\n", rule.Condition)
	fmt.Printf("  • Уведомление:   %s\n", notif)
	fmt.Println("  • Возможность смешивания метрик Prometheus и логов Loki в одном алерте!")
}
```

## Под капотом

Grafana Alerting использует фоновый движок Alerting Engine на Go, совместимый с API Alertmanager, что позволяет переиспользовать конфигурации контактов (Contact Points) и политики уведомлений.

## Подводные камни

Полагаться исключительно на Grafana Alerting для критической инфраструктуры: если под Grafana упадет или перезагружается, мониторинг ослепнет. Инфраструктурные алерты (KubeNodeNotReady, HostOutOfDisk) обязаны жить в Prometheus Alertmanager.

## На собеседовании

**Вопрос с собеседования:** «В чем главное преимущество Grafana Alerting для кросс-системных алертов?»
**Ответ:** Возможность создать одно составное правило (Multi-dimensional Alert), объединяющее метрику из Prometheus (`cpu_usage > 90%`) и поисковый запрос из Elasticsearch или Loki (`error_code == "FATAL"`). Alertmanager так делать не умеет, так как работает только с собственным TSDB.
