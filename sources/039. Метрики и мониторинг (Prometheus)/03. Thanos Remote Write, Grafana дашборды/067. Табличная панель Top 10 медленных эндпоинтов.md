# Табличная панель Top 10 медленных эндпоинтов: расчет в PromQL через topk и отношение sum к count

## Условие

Создай **Table Panel** для Top 10 slow endpoints: `topk(10, sum by (path) (rate(http_request_duration_seconds_sum[5m])) / sum by (path) (rate(http_request_duration_seconds_count[5m])))`. Покажи actionable insights.

## Теория

Анализ узких мест производительности через PromQL `topk`:
- Функция `topk(K, v)` возвращает \(K\) наибольших элементов по значению выражения.
- **Формула среднего времени ответа эндпоинта:**
  $$\text{Avg Latency} = \frac{\sum_{\text{path}} \text{rate}(http\_request\_duration\_seconds\_sum[5m])}{\sum_{\text{path}} \text{rate}(http\_request\_duration\_seconds\_count[5m])}$$
- Панель Table в Grafana сортирует эндпоинты по убыванию задержки, давая инженерам четкий список приоритетов для оптимизации SQL-индексов и кэширования.

## Решение по шагам

1. Создайте модель данных задержек по эндпоинтам.
2. Рассчитайте среднее время выполнения для каждого пути.
3. Отфильтруйте 3 самых медленных маршрута (top 3).
4. Проверьте правильность сортировки.

## Код решения

**`top_slow_endpoints_test.go`**

```go
package main

import (
	"fmt"
	"sort"
	"testing"
)

type EndpointLatencyStat struct {
	Path       string
	AvgLatency float64 // в секундах
}

func TopKSlowEndpoints(stats []EndpointLatencyStat, k int) []EndpointLatencyStat {
	sort.Slice(stats, func(i, j int) bool {
		return stats[i].AvgLatency > stats[j].AvgLatency // по убыванию
	})
	if len(stats) > k {
		return stats[:k]
	}
	return stats
}

func TestTopSlowEndpoints(t *testing.T) {
	endpoints := []EndpointLatencyStat{
		{Path: "/api/ping", AvgLatency: 0.002},
		{Path: "/api/catalog/search", AvgLatency: 0.450},
		{Path: "/api/reports/annual", AvgLatency: 2.850}, // Самый медленный!
		{Path: "/api/users/profile", AvgLatency: 0.045},
		{Path: "/api/checkout/pay", AvgLatency: 1.150},
	}

	top3 := TopKSlowEndpoints(endpoints, 3)

	if len(top3) != 3 || top3[0].Path != "/api/reports/annual" {
		t.Fatalf("Некорректный Top-3: %+v", top3)
	}

	fmt.Println("Table Panel: Top медленных эндпоинтов (PromQL topk):")
	for idx, ep := range top3 {
		fmt.Printf("  #%d %-25s -> %.3f сек (%.0f мс)\n", idx+1, ep.Path, ep.AvgLatency, ep.AvgLatency*1000)
	}
	fmt.Println("  • Четкие инсайты для оптимизации архитектуры получены!")
}
```

## Под капотом

Внутри PromQL функция `topk` выполняется на каждом шаге вычисления графика: если задержка эндпоинта упала, он автоматически выпадает из таблицы, уступая место другим узким местам.

## Подводные камни

Использовать `topk` без ограничения по минимальному количеству запросов: маршрут, вызванный 1 раз за день и занявший 3 секунды, займет первое место в таблице, хотя реальной проблемы под нагрузкой он не представляет. Добавляют фильтр `and sum by (path) (rate(..._count[5m])) > 1`.

## На собеседовании

**Вопрос с собеседования:** «Почему в алертах опасно использовать функцию topk()?»
**Ответ:** Потому что состав возвращаемых рядов в `topk` постоянно меняется (ряды то появляются, то исчезают из выборки). Это приводит к постоянному миганию статусов алертов (Alert Flapping) и сбою механизмов дедупликации в Alertmanager. Для алертов используют стабильные фильтры без `topk`.
