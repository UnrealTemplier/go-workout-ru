# Долговременное хранение метрик Remote Write: архитектура Thanos, Cortex и VictoriaMetrics

## Условие

Настрой **Remote Write** (Thanos/Cortex/VictoriaMetrics): `remote_write: [url: http://thanos-receive:19291/api/v1/receive]`. Long-term storage, global query, high availability. Покажи архитектуру.

## Теория

Протокол Prometheus Remote Write:
- По умолчанию локальный TSDB Prometheus хранит данные 15–30 дней:
  - Хранить данные за 2–3 года на локальном диске Prometheus неэффективно (ограничения файловой системы, долгий старт при рестарте).
- **Спецификация Remote Write:**
  - Prometheus скрейпит метрики в память.
  - Батчами пакует сэмплы в бинарный протокол Snappy + Protocol Buffers.
  - Отправляет по HTTP POST на URL долговременного хранилища (`remote_write`):
    - **VictoriaMetrics** (`/api/v1/write`)
    - **Thanos Receive** (`/api/v1/receive`)
    - **Cortex / Mimir**
- Обеспечивает глобальные запросы по сотням кластеров и дешевое хранение в S3/Ceph.

## Решение по шагам

1. Создайте модель конфигурации `remote_write` в Prometheus.
2. Смоделируйте упаковку батча метрик и отправку на эндпоинт долговременного хранилища.
3. Проверьте сжатие данных и гарантию доставки при сбоях сети (Write-Ahead Log Queue).
4. Оцените архитектуру глобального хранилища.

## Код решения

**`remote_write_architecture_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type RemoteWriteConfig struct {
	URL           string
	RemoteTimeout string
	BatchSize     int
}

type MockThanosReceiver struct {
	receivedBatches int
	totalSamples    int
}

func (r *MockThanosReceiver) ReceiveWriteBatch(samplesCount int) {
	r.receivedBatches++
	r.totalSamples += samplesCount
}

func TestRemoteWriteArchitecture(t *testing.T) {
	cfg := RemoteWriteConfig{
		URL:           "http://thanos-receive:19291/api/v1/receive",
		RemoteTimeout: "30s",
		BatchSize:     500,
	}

	receiver := &MockThanosReceiver{}

	// Имитируем отправку 3 батчей по 500 сэмплов из WAL
	receiver.ReceiveWriteBatch(cfg.BatchSize)
	receiver.ReceiveWriteBatch(cfg.BatchSize)
	receiver.ReceiveWriteBatch(cfg.BatchSize)

	if receiver.receivedBatches != 3 || receiver.totalSamples != 1500 {
		t.Fatalf("Ошибка отправки Remote Write: %+v", receiver)
	}

	fmt.Println("Архитектура Prometheus Remote Write успешно подтверждена:")
	fmt.Printf("  • Целевой ресивер: %s\n", cfg.URL)
	fmt.Printf("  • Батчей передано: %d (Всего сэмплов: %d)\n", receiver.receivedBatches, receiver.totalSamples)
	fmt.Println("  • Метрики надежно реплицированы в долговременное хранилище S3 (Thanos/VictoriaMetrics)!")
}
```

## Под капотом

Prometheus использует диск (WAL) как буфер для Remote Write: если удаленный Thanos временно недоступен, сэмплы копятся на локальном диске и досылаются при восстановлении сети без потери точек данных.

## Подводные камни

Отправлять тяжелые гистограммы через Remote Write без фильтрации: объем сетевого трафика вырастет в десятки раз. В секции `remote_write` настраивают `write_relabel_configs`, отсекая ненужные промежуточные метрики.

## На собеседовании

**Вопрос с собеседования:** «В чем отличие архитектуры Thanos Sidecar от Thanos Receive?»
**Ответ:** Thanos Sidecar работает по Pull-модели: раз в 2 часа sidecar скидывает уже сформированные закрытые 2-часовые блоки TSDB из локального диска Prometheus в S3. Thanos Receive работает по Push-модели (Remote Write) в реальном времени, что позволяет хранить метрики централизованно, даже если локальный Prometheus полностью сгорит вместе с диском.
