# Метрики Kafka Consumer: мониторинг consumer lag в Gauge, скорости обработки и счетчика ошибок

## Условие

Напишите метрики для Kafka consumer: лаг (разница между последним оффсетом и текущим), количество обработанных сообщений, ошибок. Используйте `Gauge` и `CounterVec`.

## Теория

Телеметрия консьюмера Apache Kafka:
- Ключевые метрики консьюмера:
  1. `kafka_consumer_lag_records` (GaugeVec с метками `topic`, `partition`, `consumer_group`):
     - Разница: \(\text{Lag} = \text{LogEndOffset} - \text{CurrentOffset}\).
     - Рост лага означает, что консьюмер не справляется с потоком данных (требуется масштабирование подов или увеличение числа партиций).
  2. `kafka_consumer_messages_processed_total` (CounterVec с метками `topic`, `status`).
  3. `kafka_consumer_processing_duration_seconds` (HistogramVec).

## Решение по шагам

1. Создайте структуру метрик Kafka консьюмера.
2. Реализуйте метод `RecordLag(topic, partition, logEnd, current)`.
3. Зафиксируйте обработку сообщения и инкремент счетчика.
4. Проверьте фиксацию лага в 450 сообщений.

## Код решения

**`kafka_consumer_metrics_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type KafkaConsumerMetrics struct {
	consumerLag      *prometheus.GaugeVec
	messagesTotal    *prometheus.CounterVec
	processingErrors *prometheus.CounterVec
}

func NewKafkaConsumerMetrics(reg *prometheus.Registry) *KafkaConsumerMetrics {
	m := &KafkaConsumerMetrics{
		consumerLag: prometheus.NewGaugeVec(
			prometheus.GaugeOpts{
				Name: "kafka_consumer_lag_records",
				Help: "Текущий лаг консьюмера в количестве сообщений",
			},
			[]string{"topic", "partition", "group"},
		),
		messagesTotal: prometheus.NewCounterVec(
			prometheus.CounterOpts{
				Name: "kafka_consumer_messages_processed_total",
				Help: "Количество обработанных сообщений",
			},
			[]string{"topic", "group"},
		),
		processingErrors: prometheus.NewCounterVec(
			prometheus.CounterOpts{
				Name: "kafka_consumer_processing_errors_total",
				Help: "Ошибки десериализации и обработки сообщений",
			},
			[]string{"topic", "group"},
		),
	}
	reg.MustRegister(m.consumerLag, m.messagesTotal, m.processingErrors)
	return m
}

func (m *KafkaConsumerMetrics) UpdateLag(topic, partition, group string, logEndOffset, currentOffset int64) {
	lag := logEndOffset - currentOffset
	if lag < 0 {
		lag = 0
	}
	m.consumerLag.WithLabelValues(topic, partition, group).Set(float64(lag))
}

func TestKafkaConsumerMetrics(t *testing.T) {
	reg := prometheus.NewRegistry()
	km := NewKafkaConsumerMetrics(reg)

	// Топик 'orders-events', партиция 0: конец 10000, вычитано 9550 -> Лаг 450!
	km.UpdateLag("orders-events", "0", "billing-group", 10000, 9550)

	// Обработано 150 сообщений, 1 ошибка
	km.messagesTotal.WithLabelValues("orders-events", "billing-group").Add(150)
	km.processingErrors.WithLabelValues("orders-events", "billing-group").Inc()

	lagVal := testutil.ToFloat64(km.consumerLag.WithLabelValues("orders-events", "0", "billing-group"))
	msgVal := testutil.ToFloat64(km.messagesTotal.WithLabelValues("orders-events", "billing-group"))

	if lagVal != 450.0 || msgVal != 150.0 {
		t.Fatalf("Ошибка учета Kafka: lag=%f, msg=%f", lagVal, msgVal)
	}

	fmt.Println("Телеметрия Kafka Consumer успешно верифицирована:")
	fmt.Printf("  • kafka_consumer_lag_records:            %.0f сообщений (Задержка вычитки)\n", lagVal)
	fmt.Printf("  • kafka_consumer_messages_processed_total: %.0f сообщений обработано\n", msgVal)
	fmt.Println("  • Мониторинг позволяет вовремя настроить HPA автоскейлинг консьюмеров!")
}
```

## Под капотом

В Kubernetes инструмент KEDA (Kubernetes Event-driven Autoscaling) умеет читать значение метрики `kafka_consumer_lag_records` из Prometheus и автоматически масштабировать число подов консьюмера при росте очереди.

## Подводные камни

Пытаться вычислять лаг внутри каждого обработчика сообщения: запрос оффсетов у брокера создает сетевую нагрузку. Оффсеты запрашивают фоновым тикером раз в 10–15 секунд или используют специализированный `kafka_exporter`.

## На собеседовании

**Вопрос с собеседования:** «Почему мониторить лаг Kafka в количестве сообщений (Records Lag) иногда недостаточно?»
**Ответ:** Потому что 1000 сообщений простого пинга обрабатываются за 10 мс, а 1000 тяжелых видеофайлов обрабатываются 3 часа. В BigTech дополнительно отслеживают **Time Lag (Consumer Lag in Seconds)**: разницу между текущим временем и `timestamp` самого старого необработанного сообщения в партиции.
