# Инструментирование клиента Redis: замер латентности команд, счетчик ошибок и мониторинг пула

## Условие

Инструментируйте Redis-клиент: замеряйте latency команд, количество ошибок, размер пула.

## Теория

Инструментирование кэширующего слоя Redis (`go-redis`):
- Redis критичен для HighLoad: задержка кэша обязана составлять 0.5–2 миллисекунды.
- **Метрики клиента Redis:**
  1. `redis_command_duration_seconds` (HistogramVec с меткой `cmd`: GET, SET, DEL, HGET).
  2. `redis_command_errors_total` (CounterVec с метками `cmd`, `error_type`: timeout, conn_refused).
  3. `redis_pool_connections_active` (Gauge) и `redis_pool_hits_total` (Counter).
- Позволяет мгновенно заметить деградацию кэша до того, как база данных ляжет от всплеска нагрузки (Cache Stampede).

## Решение по шагам

1. Создайте структуру метрик клиента Redis.
2. Реализуйте хук или обертку над выполнением команд с замером времени.
3. Протестируйте команды GET и SET с фиксацией латентности.
4. Проверьте инкремент счетчика ошибок при таймауте подключения.

## Код решения

**`redis_client_metrics_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type RedisMetricsWrapper struct {
	cmdDuration *prometheus.HistogramVec
	cmdErrors   *prometheus.CounterVec
	poolActive  prometheus.Gauge
}

func NewRedisMetrics(reg *prometheus.Registry) *RedisMetricsWrapper {
	m := &RedisMetricsWrapper{
		cmdDuration: prometheus.NewHistogramVec(
			prometheus.HistogramOpts{
				Name:    "redis_command_duration_seconds",
				Help:    "Время выполнения команд Redis",
				Buckets: []float64{0.0005, 0.001, 0.002, 0.005, 0.01, 0.05}, // от 0.5мс до 50мс
			},
			[]string{"cmd"},
		),
		cmdErrors: prometheus.NewCounterVec(
			prometheus.CounterOpts{
				Name: "redis_command_errors_total",
				Help: "Ошибки выполнения команд Redis",
			},
			[]string{"cmd", "error_type"},
		),
		poolActive: prometheus.NewGauge(
			prometheus.GaugeOpts{
				Name: "redis_pool_connections_active",
				Help: "Количество активных соединений с Redis",
			},
		),
	}
	reg.MustRegister(m.cmdDuration, m.cmdErrors, m.poolActive)
	return m
}

func (m *RedisMetricsWrapper) ExecuteCommand(cmd string, fn func() error) error {
	m.poolActive.Inc()
	defer m.poolActive.Dec()

	start := time.Now()
	err := fn()
	duration := time.Since(start).Seconds()

	m.cmdDuration.WithLabelValues(cmd).Observe(duration)

	if err != nil {
		errType := "timeout"
		if errors.Is(err, errors.New("conn_refused")) {
			errType = "conn_refused"
		}
		m.cmdErrors.WithLabelValues(cmd, errType).Inc()
	}

	return err
}

func TestRedisClientMetrics(t *testing.T) {
	reg := prometheus.NewRegistry()
	rm := NewRedisMetrics(reg)

	// 1. Успешный GET
	_ = rm.ExecuteCommand("GET", func() error {
		time.Sleep(1 * time.Millisecond)
		return nil
	})

	// 2. Сбойный SET по таймауту
	_ = rm.ExecuteCommand("SET", func() error {
		return errors.New("timeout")
	})

	errCount := testutil.ToFloat64(rm.cmdErrors.WithLabelValues("SET", "timeout"))
	if errCount != 1.0 {
		t.Fatalf("Ожидалась 1 ошибка тайм-аута, получено: %f", errCount)
	}

	if val := testutil.ToFloat64(rm.poolActive); val != 0.0 {
		t.Fatalf("Пул должен освободиться: %f", val)
	}

	fmt.Println("Инструментирование клиента Redis успешно верифицировано:")
	fmt.Printf("  • redis_command_duration_seconds[cmd=GET]: зафиксировано (1 мс)\n")
	fmt.Printf("  • redis_command_errors_total[cmd=SET]:     %.0f (timeout)\n", errCount)
	fmt.Printf("  • redis_pool_connections_active:           0 (корректный defer Dec)\n")
}
```

## Под капотом

В библиотеке `go-redis/v9` для инструментовки используется механизм `rdb.AddHook(hook)`: хук автоматически получает контекст, команду и длительность выполнения без модификации бизнес-кода вызова Redis.

## Подводные камни

Включать ключ Redis (Key name) в метки метрики: ключи Redis часто содержат ID пользователей (`user:session:12345`), что приведет к мгновенному взрыву кардинальности. В метке `cmd` должно быть строго имя команды (GET, SET, MGET).

## На собеседовании

**Вопрос с собеседования:** «Как с помощью метрик Prometheus обнаружить Cache Stampede (Dog-piling)?»
**Ответ:** По резкому падению метрики Cache Hit Ratio (`sum(rate(redis_hits[1m])) / sum(rate(redis_requests[1m]))`) в сочетании со взрывным ростом активных запросов к PostgreSQL (`go_sql_db_in_use_connections`). Это сигнализирует об истечении TTL популярного ключа, из-за чего тысячи запросов одновременно пошли в базу данных.
