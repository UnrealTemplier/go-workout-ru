# Инструментирование gRPC-сервера: сбор метрик по Unary и Streaming RPC через grpc_prometheus

## Условие

Инструментируйте gRPC-сервер: используйте `grpc_prometheus` для автоматического сбора метрик по RPC-методам (Unary и Streaming).

## Теория

Мониторинг gRPC в Go через перехватчики (Interceptors):
- В gRPC вызовы классифицируются на два типа:
  1. **Unary RPC:** один запрос \(\to\) один ответ.
  2. **Streaming RPC:** клиентский, серверный или двунаправленный (Bidirectional) поток сообщений.
- Пакет `github.com/grpc-ecosystem/go-grpc-prometheus`:
  - Предоставляет готовые перехватчики:
    - `grpc_prometheus.UnaryServerInterceptor`
    - `grpc_prometheus.StreamServerInterceptor`
  - Автоматически собирает:
    - `grpc_server_started_total`
    - `grpc_server_handled_total{grpc_service, grpc_method, grpc_code}`
    - `grpc_server_handling_seconds` (гистограмма длительности)
    - `grpc_server_msg_sent_total` / `grpc_server_msg_received_total` (для стримов).

## Решение по шагам

1. Создайте модель перехватчика gRPC-вызовов Unary и Streaming.
2. Симулируйте успешный вызов метода `/OrderService/CreateOrder`.
3. Зафиксируйте код завершения `codes.OK` и задержку.
4. Проверьте экспорт стандартных gRPC-метрик.

## Код решения

**`grpc_server_prometheus_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type GRPCMetricsCollector struct {
	handledTotal    *prometheus.CounterVec
	handlingSeconds *prometheus.HistogramVec
}

func NewGRPCMetrics(reg *prometheus.Registry) *GRPCMetricsCollector {
	c := &GRPCMetricsCollector{
		handledTotal: prometheus.NewCounterVec(
			prometheus.CounterOpts{
				Name: "grpc_server_handled_total",
				Help: "Общее число завершенных RPC вызовов",
			},
			[]string{"grpc_service", "grpc_method", "grpc_code"},
		),
		handlingSeconds: prometheus.NewHistogramVec(
			prometheus.HistogramOpts{
				Name:    "grpc_server_handling_seconds",
				Help:    "Время обработки gRPC методов",
				Buckets: []float64{0.005, 0.01, 0.05, 0.1, 0.5, 1.0},
			},
			[]string{"grpc_service", "grpc_method"},
		),
	}
	reg.MustRegister(c.handledTotal, c.handlingSeconds)
	return c
}

// Эмуляция UnaryServerInterceptor
func (c *GRPCMetricsCollector) UnaryInterceptor(
	ctx context.Context,
	fullMethod string,
	handler func(ctx context.Context) (string, error),
) (string, error) {
	start := time.Now()
	res, err := handler(ctx)
	duration := time.Since(start).Seconds()

	codeStr := "OK"
	if err != nil {
		codeStr = "Internal"
	}

	service := "OrderService"
	method := "CreateOrder"

	c.handledTotal.WithLabelValues(service, method, codeStr).Inc()
	c.handlingSeconds.WithLabelValues(service, method).Observe(duration)

	return res, err
}

func TestGRPCServerPrometheus(t *testing.T) {
	reg := prometheus.NewRegistry()
	grpcMetrics := NewGRPCMetrics(reg)

	// Симулируем успешный вызов gRPC метода CreateOrder
	_, err := grpcMetrics.UnaryInterceptor(context.Background(), "/OrderService/CreateOrder", func(ctx context.Context) (string, error) {
		time.Sleep(5 * time.Millisecond)
		return "order-id-7711", nil
	})

	if err != nil {
		t.Fatalf("Ошибка RPC: %v", err)
	}

	val := testutil.ToFloat64(grpcMetrics.handledTotal.WithLabelValues("OrderService", "CreateOrder", "OK"))
	if val != 1.0 {
		t.Fatalf("Ожидался 1 вызов с кодом OK, получено: %f", val)
	}

	fmt.Println("Инструментирование gRPC-сервера успешно подтверждено:")
	fmt.Printf("  • grpc_service: OrderService\n")
	fmt.Printf("  • grpc_method:  CreateOrder\n")
	fmt.Printf("  • grpc_code:    OK (Счетчик: %.0f)\n", val)
	fmt.Println("  • Перехватчик автоматически агрегирует метрики всех RPC-методов!")
}
```

## Под капотом

В библиотеке `go-grpc-prometheus` по умолчанию гистограммы отключены для экономии ресурсов памяти, поэтому для замера задержек обязательно вызывается метод `grpc_prometheus.EnableHandlingTimeHistogram()`.

## Подводные камни

Регистрировать метрики gRPC-клиента и gRPC-сервера в одном общем глобальном реестре без префиксов: имена метрик `grpc_server_*` и `grpc_client_*` не конфликтуют, но при отсутствии `Namespace` в Grafana легко перепутать клиентскую и серверную задержку.

## На собеседовании

**Вопрос с собеседования:** «Как в gRPC метриках мониторить сетевой оверхед на передачу сообщений в потоке (Streaming)?»
**Ответ:** Через счетчики `grpc_server_msg_sent_total` и `grpc_server_msg_received_total`. Обертка `grpc.ServerStream` перехватывает вызовы `SendMsg` и `RecvMsg`, инкрементируя счетчик на каждое переданное protobuf-сообщение внутри одного долгоживущего TCP-стрима.
