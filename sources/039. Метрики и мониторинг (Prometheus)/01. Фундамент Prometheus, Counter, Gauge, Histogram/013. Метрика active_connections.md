# Метрика active_connections: отслеживание жизненного цикла TCP и WebSocket соединений через Gauge

## Условие

**Gauge**: Создай метрику `active_connections`. Увеличивай её при подключении WebSocket-клиента, уменьшай при отключении.

## Теория

Мониторинг пулов соединений в реальном времени:
- Измеритель `active_connections` отражает мгновенную нагрузку на сетевой стек.
- **Инженерные задачи метрики:**
  - Отслеживание всплесков подключений (Connection Spike).
  - Сравнение с лимитами дескрипторов файлов ОС (`ulimit -n`).
  - Оценка балансировки клиентов между репликами пода в Kubernetes (равномерность распределения нагрузки L4/L7 балансировщиком).

## Решение по шагам

1. Создайте Gauge `active_connections`.
2. Реализуйте сессию клиента с автоматическим декрементом при завершении.
3. Смоделируйте одновременное подключение 5 клиентов.
4. Проверьте возврат значения измерителя в исходный 0 после закрытия сессий.

## Код решения

**`active_connections_lifecycle_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type ConnectionPoolManager struct {
	gauge prometheus.Gauge
}

func (m *ConnectionPoolManager) HandleSession(id int, work func()) {
	m.gauge.Inc()
	defer m.gauge.Dec()
	work()
}

func TestActiveConnectionsLifecycle(t *testing.T) {
	reg := prometheus.NewRegistry()

	activeConn := prometheus.NewGauge(prometheus.GaugeOpts{
		Name: "active_connections",
		Help: "Число активных соединений клиентов в реальном времени",
	})
	reg.MustRegister(activeConn)

	mgr := &ConnectionPoolManager{gauge: activeConn}

	var wg sync.WaitGroup
	var midTestGauge float64
	barrier := make(chan struct{})

	// Запускаем 5 одновременных сессий
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func(connID int) {
			defer wg.Done()
			mgr.HandleSession(connID, func() {
				<-barrier
			})
		}(i)
	}

	// Даем горутинам инкрементировать счетчик
	for {
		if testutil.ToFloat64(activeConn) == 5.0 {
			midTestGauge = 5.0
			break
		}
	}

	close(barrier)
	wg.Wait()

	finalVal := testutil.ToFloat64(activeConn)
	if midTestGauge != 5.0 || finalVal != 0.0 {
		t.Fatalf("Ошибка жизненного цикла: mid=%f, final=%f", midTestGauge, finalVal)
	}

	fmt.Println("Метрика active_connections успешно подтверждена:")
	fmt.Printf("  • Пик сессий:    %.0f активных соединений\n", midTestGauge)
	fmt.Printf("  • Исходное:      %.0f (Все ресурсы освобождены)\n", finalVal)
}
```

ℹ️ Управление жизненным циклом соединений через Gauge с гарантированным освобождением

## Под капотом

Атомарный декремент `gauge.Dec()` выполняется строго даже в случае необработанной паники внутри пользовательской функции благодаря семантике `defer` в языке Go.

## Подводные камни

Создавать новый экземпляр `prometheus.NewGauge` внутри обработчика каждого HTTP-запроса: метрики являются синглтонами и обязаны создаваться один раз при инициализации приложения.

## На собеседовании

**Вопрос с собеседования:** «Что делать, если значение active_connections стало отрицательным (-1)?»
**Ответ:** Это говорит о баге двойного декремента (Double Dec Bug), когда `Dec()` был вызван дважды для одного соединения (например, при тайм-ауте и при закрытии сокета). Для предотвращения используют структуру со `sync.Once` на закрытие соединения.
