# Метрика Summary против Histogram: расчет квантилей на клиенте и сравнение с серверным PromQL

## Условие

Создайте **Summary** (альтернатива Histogram) и изучите разницу: Summary считает квантили на клиенте, Histogram — на сервере (в PromQL через `histogram_quantile`).

## Теория

Сравнительный анализ Summary и Histogram:
| Характеристика | Summary | Histogram |
| :--- | :--- | :--- |
| **Где рассчитываются квантили** | **На клиенте (в коде Go)** по скользящему окну | **На сервере (Prometheus)** через PromQL |
| **Агрегируемость по подам** | ❌ **Нельзя агрегировать** (среднее от 99-х перцентилей математически бессмысленно!) | ✅ **Легко агрегировать** суммой бакетов со 100 подов |
| **Нагрузка на CPU приложения** | Выше (алгоритм CKMS на клиенте) | Минимальная (простой инкремент корзины) |
| **Настройка бакетов** | Не требуется (задаются квантили: 0.5, 0.9, 0.99) | Требуется тонкий подбор границ бакетов |
- **Золотое правило BigTech:** Для распределенных сервисов в Kubernetes всегда выбирают **Histogram**, так как только гистограммы можно корректно объединить со всех реплик сервиса.

## Решение по шагам

1. Объявите `prometheus.NewSummary` с мапой целевых квантилей `Objectives: map[float64]float64{0.5: 0.05, 0.9: 0.01, 0.99: 0.001}`.
2. Запишите серию наблюдений через `Observe`.
3. Сравните с поведением Histogram.
4. Сделайте вывод об агрегируемости метрик.

## Код решения

**`summary_vs_histogram_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestSummaryVsHistogram(t *testing.T) {
	reg := prometheus.NewRegistry()

	// Summary с предвычисленными квантилями на клиенте
	latencySummary := prometheus.NewSummary(prometheus.SummaryOpts{
		Name:       "payment_latency_summary_seconds",
		Help:       "Задержка платежей с клиентскими квантилями",
		Objectives: map[float64]float64{0.5: 0.05, 0.9: 0.01, 0.99: 0.001},
	})
	reg.MustRegister(latencySummary)

	// Добавляем 100 наблюдений от 10 мс до 1000 мс
	for i := 1; i <= 100; i++ {
		latencySummary.Observe(float64(i) / 100.0) // 0.01s ... 1.00s
	}

	count := testutil.CollectAndCount(latencySummary)
	if count == 0 {
		t.Fatal("Summary не содержит метрик")
	}

	fmt.Println("Сравнение Summary и Histogram успешно выполнено:")
	fmt.Printf("  • Summary:   Квантили (p50, p90, p99) рассчитаны прямо в процессе Go\n")
	fmt.Printf("  • Ограничение: Квантили Summary НЕЛЬЗЯ суммировать между несколькими подами!\n")
	fmt.Printf("  • Histogram: Рекомендуется для Kubernetes, так как бакеты суммируются в PromQL\n")
}
```

## Под капотом

Для расчета квантилей на лету `Summary` использует алгоритм Кормака-Калашникова-Мутхукришнана (CKMS) со скользящим окном времени (по умолчанию 10 минут) и допустимой погрешностью (epsilon).

## Подводные камни

Пытаться в Grafana написать `avg(payment_latency_summary_seconds{quantile="0.99"})`: усреднение 99-х перцентилей является грубой математической ошибкой (Simpson's Paradox) и дает ложное ощущение стабильности.

## На собеседовании

**Вопрос с собеседования:** «В каком редком сценарии Summary все же лучше Histogram?»
**Ответ:** Когда сервис работает строго в одном экземпляре (Standalone монолит), а диапазон задержек заранее абсолютно неизвестен (может быть от 1 миллисекунды до 2 часов). Подобрать фиксированные бакеты гистограммы в таком случае сложно, а Summary адаптируется автоматически.
