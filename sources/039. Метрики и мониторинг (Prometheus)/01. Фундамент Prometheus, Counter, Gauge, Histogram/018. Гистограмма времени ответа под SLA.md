# Гистограмма времени ответа под SLA: бакеты 50мс, 100мс, 250мс, 1с, 5с и автоматический сбор

## Условие

Добавьте гистограмму длительности запросов с подходящими бакетами (50ms, 100ms, 250ms, 1s, 5s). Используйте `promhttp` для автоматических метрик.

## Теория

Проектирование бакетов гистограммы под SLO/SLA:
- Бакеты должны отражать ключевые инженерные и бизнес-границы:
  - `0.05` (50 мс): идеальный быстрый ответ из кэша / БД по первичному ключу.
  - `0.1` (100 мс): верхняя граница отличного пользовательского опыта (UI без задержки).
  - `0.25` (250 мс): типичный SLA веб-запроса с несколькими сетевыми вызовами.
  - `1.0` (1 с): граница деградации производительности.
  - `5.0` (5 с): критический таймаут перед разрывом соединения клиентом.
- Такой выбор бакетов минимизирует число временных рядов (всего 5 бакетов), обеспечивая высочайшую точность расчета SLA.

## Решение по шагам

1. Создайте гистограмму с бакетами `[]float64{0.05, 0.1, 0.25, 1.0, 5.0}`.
2. Подключите обработчик с замером времени.
3. Симулируйте запросы с различными временами отклика.
4. Проверьте корректное заполнение соответствующих корзин.

## Код решения

**`sla_histogram_buckets_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestSLAHistogramBuckets(t *testing.T) {
	reg := prometheus.NewRegistry()

	slaBuckets := []float64{0.05, 0.1, 0.25, 1.0, 5.0} // 50ms, 100ms, 250ms, 1s, 5s

	apiDurationHist := prometheus.NewHistogram(prometheus.HistogramOpts{
		Name:    "api_request_duration_seconds",
		Help:    "Задержки API под целевые границы SLA",
		Buckets: slaBuckets,
	})
	reg.MustRegister(apiDurationHist)

	// Запросы: 30 мс, 80 мс, 400 мс, 2.5 с
	apiDurationHist.Observe(0.030) // попадет в le="0.05"
	apiDurationHist.Observe(0.080) // попадет в le="0.1"
	apiDurationHist.Observe(0.400) // попадет в le="1.0"
	apiDurationHist.Observe(2.500) // попадет в le="5.0"

	count := testutil.CollectAndCount(apiDurationHist)
	if count == 0 {
		t.Fatal("Гистограмма не содержит данных")
	}

	fmt.Println("Гистограмма SLA задержек успешно верифицирована:")
	fmt.Printf("  • Целевые границы SLA: 50ms, 100ms, 250ms, 1s, 5s\n")
	fmt.Printf("  • Наблюдения:          4 запроса распределены по корзинам\n")
	fmt.Println("  • Оптимальный баланс между точностью расчета перцентилей и нагрузкой на TSDB!")
}
```

## Под капотом

Слишком мелкие бакеты (например, 100 бакетов) перегружают хранилище Prometheus, а слишком крупные (3 бакета) делают вычисление перцентилей неточным. Пять-восемь экспоненциально возрастающих бакетов вокруг целевого SLA — общепринятый стандарт.

## Подводные камни

Указывать бакеты не по возрастанию: если передать `[]float64{0.5, 0.1, 1.0}`, клиент Prometheus вызовет панику `buckets not sorted` при инициализации.

## На собеседовании

**Вопрос с собеседования:** «Как в Go сгенерировать экспоненциальную или линейную сетку бакетов без ручного перечисления чисел?»
**Ответ:** Использовать встроенные хелперы пакета `prometheus`: `prometheus.LinearBuckets(start, width, count)` и `prometheus.ExponentialBuckets(start, factor, count)`. Например, `ExponentialBuckets(0.01, 2, 8)` создаст 8 бакетов с шагом умножения на 2: 10мс, 20мс, 40мс, 80мс, 160мс, 320мс, 640мс, 1.28с.
