# Инспекция метрик рантайма Go: анализ go_gc_duration_seconds, go_goroutines и go_memstats

## Условие

Подними HTTP-сервер и добавь маршрут `/metrics`, который отдает данные через `promhttp.Handler()`. Открой в браузере и посмотри стандартные метрики Go (gc, goroutines, memstats).

## Теория

Диагностика здоровья приложения по метрикам рантайма:
1. `go_goroutines`:
   - Рост графика ступеньками вверх без возврата к базису свидетельствует об **утечке горутин (Goroutine Leak)** (зависшие каналы, неотмененные контексты).
2. `go_memstats_heap_alloc_bytes` vs `go_memstats_heap_inuse_bytes`:
   - Показывает объем используемой кучи. Резкий пилообразный рост говорит о частых аллокациях и нагрузке на GC.
3. `go_gc_duration_seconds`:
   - Длительность фаз Stop-The-World сборщика мусора. В норме p99 < 1 мс.
4. `go_threads`:
   - Число физических потоков ОС, созданных рантаймом Go (сигнал о блокирующих cgo или syscall операциях).

## Решение по шагам

1. Запустите HTTP-сервер со стандартным экспортером.
2. Создайте фоновую горутину для генерации нагрузки.
3. Прочитайте метрики рантайма через HTTP-запрос.
4. Проверьте числовые значения `go_goroutines` и `go_memstats_alloc_bytes`.

## Код решения

**`runtime_metrics_inspection_test.go`**

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"runtime"
	"strings"
	"sync"
	"testing"

	"github.com/prometheus/client_golang/prometheus/promhttp"
)

func TestRuntimeMetricsInspection(t *testing.T) {
	mux := http.NewServeMux()
	mux.Handle("/metrics", promhttp.Handler())

	server := httptest.NewServer(mux)
	defer server.Close()

	// Запускаем 5 контролируемых горутин
	var wg sync.WaitGroup
	stopCh := make(chan struct{})
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			<-stopCh
		}()
	}

	// Делаем замер
	resp, err := http.Get(server.URL + "/metrics")
	if err != nil {
		t.Fatalf("Ошибка запроса: %v", err)
	}
	body, _ := io.ReadAll(resp.Body)
	resp.Body.Close()
	bodyStr := string(body)

	close(stopCh)
	wg.Wait()

	activeGoroutines := runtime.NumGoroutine()

	if !strings.Contains(bodyStr, "go_goroutines") || !strings.Contains(bodyStr, "go_memstats_alloc_bytes") {
		t.Fatal("Стандартные метрики рантайма не найдены в выводе")
	}

	fmt.Println("Инспекция метрик рантайма Go успешно завершена:")
	fmt.Printf("  • Активных горутин в рантайме: %d\n", activeGoroutines)
	fmt.Printf("  • Метрики GC и памяти:        присутствуют в эндпоинте /metrics\n")
	fmt.Println("  • Готовность к мониторингу утечек памяти и горутин подтверждена!")
}
```

## Под капотом

Рантайм Go непрерывно агрегирует внутреннюю статистику в системной структуре `runtime.mstats`. При скрейпе экспортер конвертирует значения `mstats.Alloc`, `mstats.TotalAlloc`, `mstats.PauseNs` в соответствующие серии Prometheus.

## Подводные камни

Игнорировать метрику `go_goroutines` в алертах: утечка горутин является самой частой причиной скрытой деградации и аварийной перезагрузки Go-микросервисов в Kubernetes (OOMKilled).

## На собеседовании

**Вопрос с собеседования:** «Какое PromQL-правило алерта настроить для обнаружения утечки горутин?»
**Ответ:** `predict_linear(go_goroutines[1h], 4 * 3600) > 10000` или `deriv(go_goroutines[30m]) > 2`. Функция `predict_linear` линейно экстраполирует тренд роста горутин на 4 часа вперед, позволяя обнаружить медленную утечку задолго до того, как контейнер исчерпает лимиты памяти пода.
