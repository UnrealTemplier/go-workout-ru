# Калибровка бакетов гистограммы: замер задержек веб-приложения по корзинам 0.1s, 0.5s, 1s, 2.5s

## Условие

**Histogram**: Создай метрику `http_request_duration_seconds` для измерения времени ответа. Настрой buckets (например, `0.1, 0.5, 1, 2.5`).

## Теория

Точечная калибровка бакетов под конкретный тип нагрузки:
- Настройка бакетов `[]float64{0.1, 0.5, 1.0, 2.5}`:
  - Идеально подходит для средних веб-приложений (API монолитов или микросервисов с обращением к внешним API).
  - Минимизирует общее число временных рядов (всего 4 бакета + `+Inf` + `_sum` + `_count` = 7 рядов на сервис).
  - Обеспечивает точную фиксацию деградации на границе 500 мс и 1 секунды.

## Решение по шагам

1. Создайте экземпляр гистограммы с бакетами `[0.1, 0.5, 1.0, 2.5]`.
2. Зафиксируйте задержки трех запросов: 70 мс, 450 мс, 1.8 с.
3. Проверьте инкремент счетчиков корзин.
4. Убедитесь в корректной работе метода `Observe`.

## Код решения

**`calibrated_histogram_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestCalibratedHistogram(t *testing.T) {
	reg := prometheus.NewRegistry()

	buckets := []float64{0.1, 0.5, 1.0, 2.5}

	hist := prometheus.NewHistogram(prometheus.HistogramOpts{
		Name:    "http_request_duration_seconds",
		Help:    "Калиброванная гистограмма времени ответа",
		Buckets: buckets,
	})
	reg.MustRegister(hist)

	// Запросы: 70ms (<=0.1), 450ms (<=0.5), 1800ms (<=2.5)
	hist.Observe(0.070)
	hist.Observe(0.450)
	hist.Observe(1.800)

	count := testutil.CollectAndCount(hist)
	if count == 0 {
		t.Fatal("Гистограмма не содержит собранных метрик")
	}

	fmt.Println("Калиброванная гистограмма успешно протестирована:")
	fmt.Printf("  • Бакеты:    %v сек\n", buckets)
	fmt.Printf("  • Измерения: 70ms, 450ms, 1800ms зафиксированы\n")
	fmt.Println("  • Минимальный объем хранимых рядов в TSDB при высокой информативности!")
}
```

## Под капотом

Каждое наблюдение в гистограмме обновляет также внутренний счетчик суммы `_sum` и количества `_count`, позволяя вычислять среднее время выполнения формулой `rate(sum)/rate(count)`.

## Подводные камни

Использовать слишком широкий диапазон бакетов (например от 0.001 до 1000): это приведет к тому, что 99% всех запросов попадут в один-единственный бакет, сделав расчет перцентилей в PromQL неинформативным.

## На собеседовании

**Вопрос с собеседования:** «Почему в современных версиях Prometheus появились Native Histograms (Sparse High-Resolution Histograms)?»
**Ответ:** Native Histograms (появились в Prometheus 2.40+) устраняют необходимость вручную подбирать бакеты. Они используют динамические логарифмические корзины с экспоненциальной шкалой, хранятся в эффективном сжатом бинарном формате и позволяют получать высокоточные квантили с погрешностью менее 1% без взрыва объема TSDB.
