# Счетчик HTTP-запросов с кодами статусов: дифференциация 200, 400 и 500 в middleware

## Условие

**Счетчик (Counter)**: Создай `prometheus.NewCounterVec`. Считай общее количество HTTP-запросов к твоему API. Раздели их лейблами (labels): `method` (GET/POST) и `status_code` (200, 400, 500). Увеличивай счетчик в мидлвари: `counter.WithLabelValues(method, status).Inc()`.

## Теория

Классификация ошибок по HTTP статусам:
- Разделение статусов позволяет оперативно диагностировать природу сбоя:
  - `2xx`: успешная обработка клиентом.
  - `4xx`: клиентские ошибки (неверный пароль, валидация JSON). Не влияют на SLA сервиса.
  - `5xx`: внутренние сбои сервиса (падение БД, паника в коде, таймаут шлюза). Напрямую сжигают Error Budget команды.
- В PromQL вычисление частоты ошибок сервера:
  `sum(rate(http_requests_total{status_code=~"5.."}[5m]))`.

## Решение по шагам

1. Объявите `CounterVec` с метками `method` и `status_code`.
2. Реализуйте тестовые вызовы со статусами 200, 400 и 500.
3. Проверьте раздельный учет счетчиков.
4. Продемонстрируйте PromQL-агрегацию для подсчета критических 5xx ошибок.

## Код решения

**`status_codes_counter_test.go`**

```go
package main

import (
	"fmt"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

func TestStatusCodesCounter(t *testing.T) {
	reg := prometheus.NewRegistry()

	apiRequestsTotal := prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "api_requests_total",
			Help: "Общее число вызовов API с разделением по статусам",
		},
		[]string{"method", "status_code"},
	)
	reg.MustRegister(apiRequestsTotal)

	// Имитируем трафик
	apiRequestsTotal.WithLabelValues("GET", "200").Add(100)
	apiRequestsTotal.WithLabelValues("POST", "400").Add(15) // клиентская ошибка
	apiRequestsTotal.WithLabelValues("POST", "500").Add(2)  // сбой сервера!

	val200 := testutil.ToFloat64(apiRequestsTotal.WithLabelValues("GET", "200"))
	val400 := testutil.ToFloat64(apiRequestsTotal.WithLabelValues("POST", "400"))
	val500 := testutil.ToFloat64(apiRequestsTotal.WithLabelValues("POST", "500"))

	if val200 != 100.0 || val400 != 15.0 || val500 != 2.0 {
		t.Fatalf("Ошибка учета кодов: 200=%f, 400=%f, 500=%f", val200, val400, val500)
	}

	fmt.Println("Счетчик статусов запросов успешно подтвержден:")
	fmt.Printf("  • Успешные (200 OK):            %.0f\n", val200)
	fmt.Printf("  • Ошибки клиента (400 Bad Req): %.0f\n", val400)
	fmt.Printf("  • Сбои сервера (500 Internal):  %.0f (Триггер для алерта P1)\n", val500)
}
```

## Под капотом

Метки со статусами 200, 400, 500 имеют крайне низкую кардинальность (не более 15 уникальных кодов во всем стандарте HTTP), что делает их идеальными для индексации в TSDB Prometheus.

## Подводные камни

Использовать строковые описания вместо цифр (например "Internal Server Error" вместо "500"): длинные строки увеличивают размер индекса TSDB и усложняют написание регулярных выражений в PromQL (`status=~"5.."`).

## На собеседовании

**Вопрос с собеседования:** «Почему в алертинге по ошибкам важно разделять 4xx и 5xx коды?»
**Ответ:** Рост 4xx ошибок часто вызван багом в мобильном приложении или действиями сканера уязвимостей и не требует ночной побудки дежурного инженера. Рост 5xx ошибок означает сбой сервиса, базы данных или исчерпание памяти и требует немедленного реагирования дежурного SRE.
