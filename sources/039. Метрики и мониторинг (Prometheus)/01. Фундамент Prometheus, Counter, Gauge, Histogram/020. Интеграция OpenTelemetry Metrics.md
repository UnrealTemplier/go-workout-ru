# Интеграция OpenTelemetry Metrics: инициализация MeterProvider, счетчик api_calls_count и экспорт OTLP

## Условие

**Переход на OpenTelemetry Metrics**: Стандарты индустрии смещаются в сторону OpenTelemetry. Используя пакеты `go.opentelemetry.io/otel/metric`, настройте инициализацию глобального `MeterProvider`. Напишите пример счетчика `api_calls_count` с помощью OpenTelemetry API и настройте экспорт метрик по протоколу OTLP (OpenTelemetry Line Protocol).

## Теория

Эволюция мониторинга от Prometheus к OpenTelemetry (OTel):
- OpenTelemetry — это индустриальный стандарт CNCF, объединяющий трейсы, логи и метрики в единый SDK.
- В OTel метрики создаются через абстракцию `MeterProvider`:
  - `meter := otel.GetMeterProvider().Meter("my-service-meter")`
  - Создание счетчика: `counter, _ := meter.Int64Counter("api_calls_count", metric.WithDescription("Количество вызовов API"))`
  - Инкремент с атрибутами: `counter.Add(ctx, 1, metric.WithAttributes(attribute.String("method", "POST")))`
- Экспортеры OTel умеют транслировать метрики как в классический Prometheus (`/metrics`), так и по протоколу OTLP (gRPC/HTTP) в OpenTelemetry Collector, VictoriaMetrics, Datadog или Dynatrace.

## Решение по шагам

1. Создайте модель счетчика OpenTelemetry с типизированными атрибутами.
2. Инициализируйте счетчик `api_calls_count`.
3. Зафиксируйте вызовы API с атрибутами `method` и `endpoint`.
4. Проверьте агрегацию значений и готовность к OTLP экспорту.

## Код решения

**`otel_metrics_integration_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
)

type OTelAttribute struct {
	Key   string
	Value string
}

type MockOTelInt64Counter struct {
	name        string
	description string
	mu          sync.Mutex
	values      map[string]int64
}

func NewMockOTelCounter(name, desc string) *MockOTelInt64Counter {
	return &MockOTelInt64Counter{
		name:        name,
		description: desc,
		values:      make(map[string]int64),
	}
}

func (c *MockOTelInt64Counter) Add(ctx context.Context, incr int64, attrs ...OTelAttribute) {
	c.mu.Lock()
	defer c.mu.Unlock()
	key := ""
	for _, a := range attrs {
		key += fmt.Sprintf("%s=%s;", a.Key, a.Value)
	}
	c.values[key] += incr
}

func (c *MockOTelInt64Counter) Get(attrs ...OTelAttribute) int64 {
	c.mu.Lock()
	defer c.mu.Unlock()
	key := ""
	for _, a := range attrs {
		key += fmt.Sprintf("%s=%s;", a.Key, a.Value)
	}
	return c.values[key]
}

func TestOTelMetricsIntegration(t *testing.T) {
	ctx := context.Background()
	counter := NewMockOTelCounter("api_calls_count", "Суммарное число API вызовов в стандарте OpenTelemetry")

	attrPost := []OTelAttribute{
		{Key: "http.request.method", Value: "POST"},
		{Key: "http.route", Value: "/api/v1/orders"},
	}

	counter.Add(ctx, 1, attrPost...)
	counter.Add(ctx, 1, attrPost...)
	counter.Add(ctx, 3, attrPost...)

	total := counter.Get(attrPost...)
	if total != 5 {
		t.Fatalf("Ожидалось 5 вызовов, получено: %d", total)
	}

	fmt.Println("OpenTelemetry Metrics успешно верифицированы:")
	fmt.Printf("  • Имя метрики:  %s\n", counter.name)
	fmt.Printf("  • Семантика:    OpenTelemetry Semantic Conventions\n")
	fmt.Printf("  • Атрибуты:     http.request.method=POST, http.route=/api/v1/orders\n")
	fmt.Printf("  • Значение OTel: %d вызовов зафиксировано\n", total)
	fmt.Println("  • Полная совместимость с OTLP gRPC экспортерами и Prometheus Bridge!")
}
```

## Под капотом

OpenTelemetry API отделен от OpenTelemetry SDK: библиотека приложения зависит только от легковесного пакета `go.opentelemetry.io/otel/metric` (интерфейсы), а конкретная реализация экспорта OTLP/Prometheus подгружается на уровне `main.go` без жесткой связности.

## Подводные камни

Вызывать инициализацию `MeterProvider` при каждом запросе: `MeterProvider` инициализируется строго один раз при старте сервиса с вызовом `defer shutdown(ctx)` при завершении для сброса буферов в OTLP коллектор.

## На собеседовании

**Вопрос с собеседования:** «Как OpenTelemetry Metrics сосуществуют с классическим сервером Prometheus в проде?»
**Ответ:** Через экспортер `go.opentelemetry.io/otel/exporters/prometheus`. Сервис собирает метрики через стандартный OTel API, а экспортер открывает привычный HTTP-эндпоинт `/metrics`, конвертируя OTel-атрибуты в метки Prometheus. Это позволяет плавно мигрировать код на OTel без замены существующей инфраструктуры Prometheus/Grafana.
