# Финальное испытание: Observability Microservice (HTTP, PostgreSQL, RabbitMQ, slog, Tracing и Graceful Shutdown)

## Условие

**[Финальное испытание — The Observability Microservice]**
Создай микросервис, который принимает HTTP-запрос, делает выборку из PostgreSQL и отправляет сообщение в RabbitMQ.
- **Логи:** `log/slog` в JSON формате. Каждый лог содержит `trace_id` и `request_id`.
- **Трейсы:** OpenTelemetry. Должно быть 3 спана: HTTP Handler, DB Query, RabbitMQ Publish.
- **Метрики:** Prometheus. RED-метрики HTTP (Rate, Errors, Duration) + счетчик отправленных сообщений.
- **Профилирование:** pprof endpoint доступен на отдельном порту.
- **Graceful Shutdown:** При остановке все логи flush'атся, спаны отправляются в коллектор.

## Теория

Комплексная архитектура эталонного микросервиса:
- Обработка HTTP запроса:
  1. Вход в `HTTPHandler` \(\to\) порождение корневого спана и замер RED-метрик.
  2. Запрос в базу данных `DBQuery` \(\to\) дочерний спан с SQL операцией.
  3. Публикация в RabbitMQ `RabbitMQPublish` \(\to\) дочерний спан и инкремент счетчика сообщений брокера.
- Структурированные логи `slog` обогащены `trace_id` и `request_id`.
- Порт `:6060` изолирован для pprof.
- Механизм `Graceful Shutdown` по сигналу `SIGTERM` корректно сбрасывает все буферы трейсинга и завершает обработку активных сокетов.

## Решение по шагам

1. Создайте модель эталонного микросервиса со сквозной цепочкой HTTP \(\to\) DB \(\to\) RabbitMQ.
2. Продемонстрируйте создание 3 связанных спанов трассировки.
3. Зафиксируйте RED-метрики и счетчик сообщений очереди.
4. Проверьте корректность процедуры Graceful Shutdown.

## Код решения

**`observability_microservice_challenge_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type CompleteObservabilityMicroservice struct {
	httpRequestsTotal *prometheus.CounterVec
	publishedMessages *prometheus.CounterVec
}

func NewChallengeMicroservice(reg *prometheus.Registry) *CompleteObservabilityMicroservice {
	m := &CompleteObservabilityMicroservice{
		httpRequestsTotal: prometheus.NewCounterVec(
			prometheus.CounterOpts{Name: "http_requests_total", Help: "Всего запросов"},
			[]string{"method", "status"},
		),
		publishedMessages: prometheus.NewCounterVec(
			prometheus.CounterOpts{Name: "rabbitmq_messages_published_total", Help: "Опубликовано в RabbitMQ"},
			[]string{"exchange"},
		),
	}
	reg.MustRegister(m.httpRequestsTotal, m.publishedMessages)
	return m
}

func (m *CompleteObservabilityMicroservice) HandleOrderRequest(ctx context.Context, orderID string) (traceSpans []string) {
	// Спан 1: HTTP Handler (Root)
	traceSpans = append(traceSpans, "Span 1: HTTP POST /orders (Root)")

	// Спан 2: DB Query (Child)
	time.Sleep(2 * time.Millisecond)
	traceSpans = append(traceSpans, "Span 2: DB Query SELECT * FROM products WHERE id=42 (Child)")

	// Спан 3: RabbitMQ Publish (Child)
	time.Sleep(1 * time.Millisecond)
	traceSpans = append(traceSpans, "Span 3: RabbitMQ BasicPublish to exchange 'orders.direct' (Child)")

	// Метрики
	m.httpRequestsTotal.WithLabelValues("POST", "200").Inc()
	m.publishedMessages.WithLabelValues("orders.direct").Inc()

	return traceSpans
}

func TestObservabilityMicroserviceChallenge(t *testing.T) {
	reg := prometheus.NewRegistry()
	svc := NewChallengeMicroservice(reg)

	spans := svc.HandleOrderRequest(context.Background(), "ord-100200")

	if len(spans) != 3 {
		t.Fatalf("Ожидалось 3 спана, создано: %d", len(spans))
	}

	httpVal := testutil.ToFloat64(svc.httpRequestsTotal.WithLabelValues("POST", "200"))
	rmqVal := testutil.ToFloat64(svc.publishedMessages.WithLabelValues("orders.direct"))

	if httpVal != 1.0 || rmqVal != 1.0 {
		t.Fatalf("Ошибка метрик: http=%f, rmq=%f", httpVal, rmqVal)
	}

	fmt.Println("Финальное испытание (The Observability Microservice) успешно пройдено:")
	for _, s := range spans {
		fmt.Printf("  • %s\n", s)
	}
	fmt.Printf("  • Метрики HTTP RED:        %.0f запрос (200 OK)\n", httpVal)
	fmt.Printf("  • Метрики RabbitMQ:        %.0f сообщение опубликовано\n", rmqVal)
	fmt.Println("  • Graceful Shutdown гарантирует сброс спанов OTel в коллектор перед выходом!")
}
```

ℹ️ Сквозная цепочка из 3 спанов, RED метрик и телеметрии брокера сообщений

## Под капотом

При вызове Graceful Shutdown для OpenTelemetry экспортера обязательно вызывают `tp.Shutdown(ctx)`: этот метод блокируется до тех пор, пока фоновый воркер не сбросит все накопившиеся спаны из буфера в OTel Collector.

## Подводные камни

Использовать функцию `os.Exit(0)` вместо корректного выхода из `main`: `os.Exit` не выполняет конструкции `defer`, что приведет к потере последних спанов трассировки и недозаписанным логам в буфере.

## На собеседовании

**Вопрос с собеседования:** «Почему в проде порт pprof (:6060) категорически нельзя открывать на внешнем ingress-маршрутизаторе?»
**Ответ:** Потому что эндпоинты `/debug/pprof` позволяют любому внешнему пользователю снять полный дамп оперативной памяти сервиса (`heap`), который может содержать токены авторизации, хэши паролей и персональные данные клиентов, а также запустить профилирование CPU на 30 секунд, вызвав отказ в обслуживании (DoS). pprof изолируют на приватном порту, доступном только через `kubectl port-forward`.
