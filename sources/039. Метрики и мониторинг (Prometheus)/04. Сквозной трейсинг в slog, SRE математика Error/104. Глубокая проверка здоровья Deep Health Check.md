# Глубокая проверка здоровья Deep Health Check: валидация доступности и порога задержки базы (< 100ms)

## Условие

Реализуйте **deep health check**: проверяет не только доступность, но и latency зависимостей (БД отвечает < 100ms).

## Теория

Концепция Deep Health Checking:
- База данных может быть доступна (соединение устанавливается), но отвечать за 2 секунды из-за перегрузки диска (I/O Saturation).
- Сервер, посылающий запросы в тормозящую БД, накопит тысячи зависших горутин и упадет сам.
- **Deep Health Check:**
  - Замеряет время выполнения пинга: `duration := time.Since(start)`.
  - Если \(\text{Latency} \ge 100\text{ мс} \to\) статус `DEGRADED / 503`.
  - Позволяет снять нагрузку с деградирующего шарда базы данных до полного отказа.

## Решение по шагам

1. Создайте структуру Deep Health Check с порогом задержки 100 мс.
2. Реализуйте замер длительности пинга к базе данных.
3. Проверьте быстрый ответ (15 мс \(\to\) 200 OK).
4. Проверьте медленный ответ (180 мс \(\to\) 503 Degraded).

## Код решения

**`deep_health_check_latency_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"testing"
	"time"
)

type LatencyAwarePinger struct {
	simulatedLatency time.Duration
}

func (p *LatencyAwarePinger) Ping() time.Duration {
	time.Sleep(p.simulatedLatency)
	return p.simulatedLatency
}

func DeepHealthCheckHandler(pinger *LatencyAwarePinger, maxAllowedLatency time.Duration) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		latency := pinger.Ping()
		if latency > maxAllowedLatency {
			http.Error(w, fmt.Sprintf("DEGRADED: db latency %v > threshold %v", latency, maxAllowedLatency), http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
		fmt.Fprintf(w, "HEALTHY: latency=%v", latency)
	}
}

func TestDeepHealthCheckLatency(t *testing.T) {
	threshold := 100 * time.Millisecond

	// 1. Быстрый ответ 10 мс -> 200 OK
	fastPinger := &LatencyAwarePinger{simulatedLatency: 10 * time.Millisecond}
	h1 := DeepHealthCheckHandler(fastPinger, threshold)
	rec1 := httptest.NewRecorder()
	h1(rec1, httptest.NewRequest("GET", "/health/deep", nil))
	if rec1.Code != http.StatusOK {
		t.Fatalf("Должно быть 200 OK: %d", rec1.Code)
	}

	// 2. Тормозящая база 150 мс (>100мс) -> 503 Service Unavailable
	slowPinger := &LatencyAwarePinger{simulatedLatency: 150 * time.Millisecond}
	h2 := DeepHealthCheckHandler(slowPinger, threshold)
	rec2 := httptest.NewRecorder()
	h2(rec2, httptest.NewRequest("GET", "/health/deep", nil))
	if rec2.Code != http.StatusServiceUnavailable {
		t.Fatalf("Должно быть 503 при деградации задержки: %d", rec2.Code)
	}

	fmt.Println("Deep Health Check успешно верифицирован:")
	fmt.Printf("  • Быстрый пинг (10мс):  %d OK\n", rec1.Code)
	fmt.Printf("  • Медленный пинг (150мс): %d Service Unavailable (Защита от перегрузки деградирующей БД)\n", rec2.Code)
}
```

## Под капотом

В многошардовых архитектурах Deep Health Check позволяет балансировщику (Envoy/NGINX) перенаправлять трафик на реплики чтения с минимальной латентностью.

## Подводные камни

Устанавливать порог латентности в Deep Health Check слишком близко к средней задержке (например 20 мс при среднем 18 мс): естественные флуктуации сети приведут к постоянному флаппингу статуса готовности сервиса.

## На собеседовании

**Вопрос с собеседования:** «Чем Deep Health Check отличается от обычной Readiness пробы?»
**Ответ:** Обычная Readiness проба проверяет факт наличия сетевого сокета (Binary Check: работает / не работает). Deep Health Check проверяет качество обслуживания (Quality of Service Check: задержка ответа, процент свободных соединений в пуле, глубина очереди репликации), позволяя выводить узел из ротации ДО того, как он окончательно упадет.
