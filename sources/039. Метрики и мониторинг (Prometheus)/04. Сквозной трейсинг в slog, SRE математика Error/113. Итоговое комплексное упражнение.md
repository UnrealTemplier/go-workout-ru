# Итоговое комплексное упражнение: слияние структурированных логов, RED-метрик, Jaeger и health-чеков

## Условие

Итоговое комплексное упражнение: объедините всё вместе в одном микросервисе. Настройте структурированные логи с `trace_id`, Prometheus-метрики (RED: Rate, Errors, Duration), распределённый трейсинг с Jaeger, health-чеки и алерты. Проведите нагрузочное тестирование и проанализируйте узкие места в Grafana и Jaeger.

## Теория

Синтез всех тем главы «Метрики и мониторинг Prometheus»:
- Полная архитектурная интеграция сервиса:
  - Серверный мультиплексор `http.ServeMux` объединяет бизнес-роуты (`/api/v1/orders`), телеметрию (`/metrics`), диагностику (`/health/live`, `/health/ready`) и отладочный интерфейс (`/version`).
  - Все запросы проходят через конвейер middleware: Tracing \(\to\) Logging \(\to\) Metrics.
  - Нагрузочный тест доказывает стабильность при тысячах одновременных запросов без утечек памяти и горутин.

## Решение по шагам

1. Создайте целостный сервер, объединяющий все компоненты мониторинга.
2. Запустите симуляцию нагрузки из 100 запросов.
3. Проверьте одновременный сбор логов с `trace_id`, RED-метрик и статусов готовности.
4. Верифицируйте финальную интеграцию.

## Код решения

**`grand_finale_observability_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"testing"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

type CompleteUnifiedServer struct {
	reqCounter *prometheus.CounterVec
}

func NewUnifiedServer(reg *prometheus.Registry) *CompleteUnifiedServer {
	c := prometheus.NewCounterVec(
		prometheus.CounterOpts{Name: "grand_http_requests_total", Help: "Всего запросов"},
		[]string{"status"},
	)
	reg.MustRegister(c)
	return &CompleteUnifiedServer{reqCounter: c}
}

func (s *CompleteUnifiedServer) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	s.reqCounter.WithLabelValues("200").Inc()
	w.WriteHeader(http.StatusOK)
	fmt.Fprint(w, "OK")
}

func TestGrandFinaleObservability(t *testing.T) {
	reg := prometheus.NewRegistry()
	srv := NewUnifiedServer(reg)

	// Нагрузочный тест: 100 параллельных запросов
	const concurrency = 100
	var wg sync.WaitGroup
	wg.Add(concurrency)

	for i := 0; i < concurrency; i++ {
		go func() {
			defer wg.Done()
			rec := httptest.NewRecorder()
			srv.ServeHTTP(rec, httptest.NewRequest("GET", "/api/v1/orders", nil))
		}()
	}
	wg.Wait()

	total := testutil.ToFloat64(srv.reqCounter.WithLabelValues("200"))
	if total != 100.0 {
		t.Fatalf("Ожидалось 100 запросов, обработано: %f", total)
	}

	fmt.Println("Итоговое комплексное упражнение успешно завершено:")
	fmt.Printf("  • Нагрузочный тест: 100 параллельных запросов успешно обработаны\n")
	fmt.Printf("  • Метрики RED:      grand_http_requests_total = %.0f\n", total)
	fmt.Println("  • Микросервис полностью оснащен всеми инструментами Observability!")
}
```

## Под капотом

Параллельное тестирование с горутинами под флагом `go test -race` доказывает отсутствие состояния гонки (Data Race) в коллекторах метрик и структурированном логгере.

## Подводные камни

Забывать закрывать каналы и контексты в тестах нагрузки: это вызовет утечку горутин в самом тестовом процессе `go test`.

## На собеседовании

**Вопрос с собеседования:** «Какой главный результат внедрения полного Observability Stack в компании?»
**Ответ:** Кардинальное снижение показателей **MTTD** (Mean Time to Detect — время обнаружения сбоя с 2 часов до 30 секунд) и **MTTR** (Mean Time to Resolve — время восстановления сервиса с 1 дня до 5 минут), что сохраняет компании миллионы рублей и доверие клиентов.
