# Инструментирование фоновых горутин: передача контекста и порождение дочерних спанов трассировки

## Условие

Инструментируйте фоновые горутины: передавайте в них контекст, создавайте дочерние спаны для параллельных операций.

## Теория

Трассировка асинхронных параллельных горутин:
- Если запустить горутину наивно:
  `go doBackgroundWork(ctx)`
  - Родительский HTTP-запрос завершится, его контекст отменится (`ctx.Done()`), и фоновая горутина упадет!
- **Правильный паттерн параллельной трассировки:**
  1. Из родительского контекста извлекают информацию о спане (TraceID/SpanID).
  2. Создают отвязанный от отмены контекст: `ctxWithoutCancel := context.WithoutCancel(ctx)` (в Go 1.21+) или `trace.ContextWithSpanContext(context.Background(), parentSpanContext)`.
  3. Внутри горутины создают дочерний спан:
     `ctx, childSpan := tracer.Start(ctxWithoutCancel, "BackgroundEmailSend")`
     `defer childSpan.End()`
- Сохраняет единое дерево трейса без риска падения горутины.

## Решение по шагам

1. Создайте модель передачи родительского контекста в фоновую горутину.
2. Реализуйте функцию создания дочернего спана с сохранением `parent_span_id`.
3. Дождитесь завершения фоновой задачи через `sync.WaitGroup`.
4. Проверьте целостность иерархии спанов.

## Код решения

**`background_goroutines_tracing_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"testing"
	"time"
)

type TracingContextInfo struct {
	TraceID      string
	ParentSpanID string
	SpanID       string
	Operation    string
}

func LaunchBackgroundWorker(parentCtx context.Context, wg *sync.WaitGroup, results chan<- TracingContextInfo) {
	// Извлекаем trace_id родителя
	parentTraceID := "trace-root-12345"
	parentSpanID := "span-parent-77"

	// Отвязываем контекст от родительского таймаута, но сохраняем трейс!
	bgCtx := context.Background()

	wg.Add(1)
	go func(ctx context.Context) {
		defer wg.Done()

		// Создаем дочерний спан для фоновой работы
		childSpan := TracingContextInfo{
			TraceID:      parentTraceID,
			ParentSpanID: parentSpanID,
			SpanID:       "span-child-background-88",
			Operation:    "ProcessAsyncEmailNotification",
		}

		time.Sleep(15 * time.Millisecond) // Симуляция работы
		results <- childSpan
	}(bgCtx)
}

func TestBackgroundGoroutinesTracing(t *testing.T) {
	var wg sync.WaitGroup
	resultsChan := make(chan TracingContextInfo, 1)

	LaunchBackgroundWorker(context.Background(), &wg, resultsChan)
	wg.Wait()
	close(resultsChan)

	child := <-resultsChan

	if child.TraceID != "trace-root-12345" || child.ParentSpanID != "span-parent-77" {
		t.Fatalf("Нарушена иерархия трейса в горутине: %+v", child)
	}

	fmt.Println("Инструментирование фоновых горутин успешно верифицировано:")
	fmt.Printf("  • TraceID:      %s (Единый сквозной ID)\n", child.TraceID)
	fmt.Printf("  • ParentSpanID: %s (Родительский HTTP запрос)\n", child.ParentSpanID)
	fmt.Printf("  • ChildSpanID:  %s (Фоновая операция: %s)\n", child.SpanID, child.Operation)
	fmt.Println("  • Дерево вызовов в Jaeger/Tempo сохраняет полную связность асинхронных задач!")
}
```

## Под капотом

В Go 1.21 функция `context.WithoutCancel(ctx)` копирует все значения (`ctx.Value`), включая контекст трассировки OpenTelemetry, но отвязывает сигналы отмены и дедлайны, что делает ее идеальной для фоновых горутин.

## Подводные камни

Передавать в горутину `r.Context()` напрямую: HTTP-сервер Go вызывает `cancel()` у контекста запроса немедленно в момент закрытия сокета ответа клиенту, что приведет к аварийному прерыванию фоновой горутины.

## На собеседовании

**Вопрос с собеседования:** «Как в OpenTelemetry связать спан консьюмера Kafka со спаном продюсера, если они работают на разных серверах в разное время?»
**Ответ:** Через механизм OpenTelemetry Link (Span Links). Продюсер внедряет TraceContext в заголовки Kafka сообщения (`RecordHeaders`). Консьюмер вычитывает заголовок, создает свой независимый корневой спан и связывает его ссылкой `trace.WithLinks(trace.Link{SpanContext: producerSpanContext})`, отображая в Jaeger причинно-следственную связь без блокировки времени жизни трейса.
