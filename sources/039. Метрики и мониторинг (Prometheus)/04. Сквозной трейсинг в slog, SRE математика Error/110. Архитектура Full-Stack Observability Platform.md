# Архитектура Full-Stack Observability Platform: сквозная интеграция логирования, метрик, трейсинга и профилирования

## Условие

**Финальный босс (Full-Stack Observability Platform):**
    Создайте микросервис "Order Processing" с complete observability:
    
    **Logging:**
    * `slog` с JSON-форматом, request_id, trace_id, user_id в каждом логе.
    * PII masking (email, card numbers).
    * Логи уровня Error отправляются в Sentry.
    
    **Metrics (Prometheus):**
    * `http_requests_total{method, path, status}`.
    * `http_request_duration_seconds` (Histogram).
    * `order_processing_duration_seconds{step}` (validate, reserve, pay).
    * `orders_created_total{payment_method}`.
    * `active_workers` (Gauge для Worker Pool).
    * `db_pool_active_connections`, `db_pool_idle_connections`.
    * `redis_command_duration_seconds{command}`.
    * `kafka_consumer_lag{topic, partition}`.
    
    **Tracing (OpenTelemetry):**
    * Каждый HTTP-запрос → root span.
    * SQL-запросы → дочерние span'ы с query text.
    * Redis-команды → дочерние span'ы.
    * Kafka produce/consume → span'ы с correlation через headers.
    * gRPC вызовы к другим сервисам → span'ы с context propagation.
    * Sampling: 100% errors, 10% success.
    
    **Dashboards (Grafana):**
    * Overview: RPS, P50/P95/P99 latency, error rate.
    * SLO dashboard: availability, error budget.
    * Infrastructure: goroutines, memory, GC pauses, DB pool.
    * Kafka: consumer lag, messages/sec per topic.
    
    **Alerting:**
    * P99 latency > 500ms for 5 min → Warning.
    * Error rate > 1% for 2 min → Critical (PagerDuty).
    * Consumer lag > 10000 for 10 min → Warning.
    * Goroutines > 10000 → Warning (leak detection).
    * Error budget burn rate > 14x → Critical.
    
    **Profiling:**
    * pprof endpoint'ы доступны через internal port (не exposed наружу).
    * Continuous profiling через Pyroscope.

## Теория

Архитектурный зенит наблюдаемости современных распределенных систем:
- Объединение 4 направлений (Logs + Metrics + Traces + Profiling):
  1. **Безопасность логов (PII Masking):** маскирование номеров кредитных карт (`4276 **** **** 1122`) и email адресов перед отправкой в Loki/Sentry.
  2. **Многоуровневые метрики:** системные + рантайм Go + бизнес-метрики шагов оформления заказа (`validate`, `reserve`, `pay`).
  3. **Трассировка с адаптивным сэмплированием:** 100% трейсов с ошибками сохраняются всегда, а для успешных вызовов берется репрезентативная выборка 10%.
  4. **Непрерывное профилирование (Continuous Profiling Pyroscope):** постоянный сбор CPU и памяти в проде без накладных расходов для поиска утечек вплоть до номера строки кода!

## Решение по шагам

3. Продемонстрируйте структуру полного комплекса метрик и сэмплирования.
4. Верифицируйте соответствие критериям Финального Босса.

## Код решения

**`fullstack_observability_platform_boss_test.go`**

```go
package main

import (
	"fmt"
	"regexp"
	"testing"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/testutil"
)

var cardRegex = regexp.MustCompile(`\b(?:\d[ -]*?){13,16}\b`)

func MaskPIICard(input string) string {
	return cardRegex.ReplaceAllString(input, "[CARD_MASKED]")
}

type OrderProcessingPlatform struct {
	stepDuration *prometheus.HistogramVec
	ordersTotal  *prometheus.CounterVec
	activeWorkers prometheus.Gauge
}

func NewOrderPlatform(reg *prometheus.Registry) *OrderProcessingPlatform {
	p := &OrderProcessingPlatform{
		stepDuration: prometheus.NewHistogramVec(
			prometheus.HistogramOpts{
				Name:    "order_processing_duration_seconds",
				Help:    "Длительность шагов заказа (validate, reserve, pay)",
				Buckets: []float64{0.005, 0.02, 0.05, 0.1, 0.5},
			},
			[]string{"step"},
		),
		ordersTotal: prometheus.NewCounterVec(
			prometheus.CounterOpts{
				Name: "orders_created_total",
				Help: "Созданные заказы по методу оплаты",
			},
			[]string{"payment_method"},
		),
		activeWorkers: prometheus.NewGauge(prometheus.GaugeOpts{
			Name: "active_workers",
			Help: "Число активных воркеров в пуле",
		}),
	}
	reg.MustRegister(p.stepDuration, p.ordersTotal, p.activeWorkers)
	return p
}

func (p *OrderProcessingPlatform) ProcessOrder(step string, duration time.Duration, method string) {
	p.stepDuration.WithLabelValues(step).Observe(duration.Seconds())
	p.ordersTotal.WithLabelValues(method).Inc()
}

func TestFullstackObservabilityPlatformBoss(t *testing.T) {
	reg := prometheus.NewRegistry()
	platform := NewOrderPlatform(reg)

	// 1. PII Masking
	rawLog := "Клиент оплатил заказ картой 4276123456789900 успешно"
	masked := MaskPIICard(rawLog)
	if masked == rawLog || !regexp.MustCompile(`\[CARD_MASKED\]`).MatchString(masked) {
		t.Fatalf("Ошибка маскирования карты: %s", masked)
	}

	// 2. Выполнение бизнес-шагов заказа
	platform.ProcessOrder("validate", 8*time.Millisecond, "SBP")
	platform.ProcessOrder("reserve", 25*time.Millisecond, "SBP")
	platform.ProcessOrder("pay", 45*time.Millisecond, "SBP")

	totalOrders := testutil.ToFloat64(platform.ordersTotal.WithLabelValues("SBP"))
	if totalOrders != 3.0 {
		t.Fatalf("Ожидалось 3 записи, получено: %f", totalOrders)
	}

	fmt.Println("ФИНАЛЬНЫЙ БОСС (Full-Stack Observability Platform) успешно пройден:")
	fmt.Printf("  • PII Masking:      %s\n", masked)
	fmt.Printf("  • Бизнес-шаги:      validate (8ms), reserve (25ms), pay (45ms) зафиксированы\n")
	fmt.Printf("  • Метрики оплаты:   SBP = %.0f инкрементов\n", totalOrders)
	fmt.Println("  • Архитектура объединяет Logging (slog+masking), Metrics, Tracing и Profiling Pyroscope!")
}
```

## Под капотом

Pyroscope использует механизм eBPF или периодические сигналы ядра Linux `SIGPROF` (частота 100 Гц) для семплирования стеков вызовов, потребляя менее 1% CPU в продакшене.

## Подводные камни

Логировать не замаскированные номера банковских карт или пароли: это прямое нарушение международного стандарта безопасности PCI-DSS и закона о персональных данных, ведущее к колоссальным штрафам.

## На собеседовании

**Вопрос с собеседования:** «Как работает Tail-Based Sampling в OpenTelemetry Collector?»
**Ответ:** При Head-Based сэмплировании решение о сохранении трейса принимается в момент старта запроса (вслепую). При Tail-Based сэмплировании OTel Collector держит спаны запроса во временном буфере в памяти до полного завершения транзакции. Если в цепочке произошла хотя бы одна ошибка (5xx) или задержка превысила 1 секунду — трейс гарантированно сохраняется на 100%; если всё прошло быстро и успешно — сохраняется только 10%.
