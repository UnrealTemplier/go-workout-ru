# Фиксация ошибок в спанах OpenTelemetry: установка статуса Error и метод span.RecordError

## Условие

Реализуйте запись ошибок в трейсы: при возникновении ошибки устанавливайте статус спана `Error` и добавляйте событие с деталями.

## Теория

Стандарт обработки ошибок в OpenTelemetry Tracing:
- Просто вернуть ошибку из функции недостаточно: спан по умолчанию останется с нейтральным статусом `Unset` (зеленый в UI).
- **Два обязательных действия при ошибке:**
  1. `span.RecordError(err)`: сохраняет тип ошибки, сообщение и стектрейс как событие (Event) спана.
  2. `span.SetStatus(codes.Error, err.Error())`: окрашивает спан в красный цвет в дашборде Jaeger/Tempo.
- Позволяет мгновенно находить упавшие вызовы на диаграмме водопада (Waterfall Chart).

## Решение по шагам

1. Создайте модель спана с поддержкой статуса ошибки и списка событий.
2. Смоделируйте возникновение сбоя при обращении к внешнему API.
3. Вызовите `RecordError` и установите статус `codes.Error`.
4. Проверьте сохранность деталей сбоя в спане.

## Код решения

**`record_error_span_test.go`**

```go
package main

import (
	"errors"
	"fmt"
	"testing"
)

type SpanStatus string

const (
	StatusUnset SpanStatus = "Unset"
	StatusOk    SpanStatus = "Ok"
	StatusError SpanStatus = "Error"
)

type SpanEvent struct {
	Name    string
	Message string
}

type TracingSpan struct {
	Status      SpanStatus
	StatusDesc  string
	Events      []SpanEvent
}

func (s *TracingSpan) RecordError(err error) {
	if err != nil {
		s.Events = append(s.Events, SpanEvent{
			Name:    "exception",
			Message: err.Error(),
		})
	}
}

func (s *TracingSpan) SetStatus(status SpanStatus, desc string) {
	s.Status = status
	s.StatusDesc = desc
}

func TestRecordErrorSpan(t *testing.T) {
	span := &TracingSpan{Status: StatusUnset}

	// Симулируем ошибку базы данных
	dbErr := errors.New("pq: connection refused on port 5432")

	// Фиксируем ошибку в стандарте OpenTelemetry
	span.RecordError(dbErr)
	span.SetStatus(StatusError, dbErr.Error())

	if span.Status != StatusError || len(span.Events) != 1 {
		t.Fatalf("Ошибка фиксации статуса спана: %+v", span)
	}

	fmt.Println("Запись ошибок в спаны OpenTelemetry успешно подтверждена:")
	fmt.Printf("  • Статус спана: %s (Окрашен в красный цвет в UI Jaeger/Tempo)\n", span.Status)
	fmt.Printf("  • Событие:      %s -> %s\n", span.Events[0].Name, span.Events[0].Message)
	fmt.Println("  • Инженер мгновенно видит точную причину аварии на диаграмме вызовов!")
}
```

## Под капотом

Метод `RecordError` в OTel SDK автоматически создает атрибуты `exception.type`, `exception.message` и захватывает стектрейс вызова `exception.stacktrace` для глубокой отладки паник.

## Подводные камни

Вызывать `RecordError`, но забывать `SetStatus(codes.Error)`: спан сохранит событие ошибки внутри себя, но в общем списке трейсов останется зеленым, и дежурный инженер пропустит упавший запрос.

## На собеседовании

**Вопрос с собеседования:** «Нужно ли помечать спан ошибкой (Error), если клиент запросил несуществующего пользователя (404 Not Found)?»
**Ответ:** Нет! Ошибка 404 Not Found или неверный пароль клиента — это штатный сценарий валидации бизнес-логики, а не сбой системы. Пометка 404 как `Error` окрасит половину спанов сервиса в красный цвет и испортит метрики качества работы бэкенда. Статус `Error` выставляют строго при внутренних сбоях (5xx, таймауты, падения баз данных).
