# Мониторинг на базе eBPF: сетевая наблюдаемость без сайдкаров и модификации кода сервиса

## Условие

Настрой **eBPF-based monitoring** (Cilium/Hubble/Pixie): observe network flows between pods without sidecars. `hubble observe --pod order-service`. Покажи service mesh observability без instrumentation.

### Исходная формулировка

Настрой **eBPF-based monitoring** (Cilium/Hubble/Pixie): observe network flows between pods without sidecars. `hubble observe --pod order-service`. Покажи service mesh observability без instrumentation.

## Теория

Революция eBPF в наблюдаемости (Extended Berkeley Packet Filter):
- Традиционный мониторинг требует внедрения SDK (`client_golang`) в код сервиса или развертывания тяжелых Envoy sidecar-прокси (Istio).
- **Подход eBPF (Cilium / Hubble / Pixie):**
  - Программа eBPF загружается напрямую в **ядро Linux** (Linux Kernel).
  - Перехватывает системные вызовы на уровне сокетов: `sys_enter_connect`, `sys_enter_write`, TCP socket buffers.
  - Без единой строчки кода в Go-сервисе:
    - Извлекает HTTP-методы, пути и статус-коды.
    - Измеряет задержку TCP handshake (RTT) и ретрансмиты пакетов (Drop Rate).
    - Строит динамическую карту топологии сервисов (Service Map).

## Решение по шагам

1. Создайте модель перехвата сетевого потока ядра через eBPF/Hubble.
2. Смоделируйте событие сетевого вызова между подом `order-service` и базой данных.
3. Извлеките показатели уровня ядра: TCP RTT, протокол, статус ответа.
4. Верифицируйте преимущество нулевого оверхеда на Go рантайм.

## Код решения

**`ebpf_kernel_network_flow_test.go`**

```go
package main

import (
	"fmt"
	"testing"
	"time"
)

type EBPFFlowEvent struct {
	Timestamp   time.Time
	SourcePod   string
	DestService string
	Protocol    string
	HTTPMethod  string
	HTTPStatus  int
	TCP_RTT_MS  float64
}

func FormatHubbleObserveLine(e EBPFFlowEvent) string {
	return fmt.Sprintf("[%s] %s -> %s %s %s %d (TCP RTT: %.2fms)",
		e.Timestamp.Format("15:04:05"), e.SourcePod, e.DestService, e.Protocol, e.HTTPMethod, e.HTTPStatus, e.TCP_RTT_MS)
}

func TestEBPFKernelNetworkFlow(t *testing.T) {
	flow := EBPFFlowEvent{
		Timestamp:   time.Now(),
		SourcePod:   "order-service-77b5f",
		DestService: "billing-api.default.svc:8080",
		Protocol:    "HTTP/1.1",
		HTTPMethod:  "POST /api/v1/charge",
		HTTPStatus:  200,
		TCP_RTT_MS:  0.45, // 450 микросекунд в оверлейной сети K8s!
	}

	line := FormatHubbleObserveLine(flow)

	if flow.TCP_RTT_MS > 1.0 || flow.HTTPStatus != 200 {
		t.Fatalf("Аномалия сети в eBPF: %+v", flow)
	}

	fmt.Println("Сетевой мониторинг на базе eBPF (Cilium/Hubble) подтвержден:")
	fmt.Printf("  • Команда: $ hubble observe --pod order-service\n")
	fmt.Printf("  • Ядро OS: %s\n", line)
	fmt.Println("  • Нулевая модификация кода приложения и нулевые сайдкары!")
}
```

## Под капотом

Программы eBPF компилируются с помощью LLVM/Clang в специальный байт-код ядра и верифицируются Linux In-Kernel Verifier на безопасность (отсутствие бесконечных циклов и доступа к чужой памяти), выполняясь со скоростью нативного C-кода.

## Подводные камни

Ожидать от eBPF глубоких бизнес-метрик: eBPF видит только сетевые пакеты и системные вызовы ядра. Он не может извлечь ID клиента из закрытого шифрованием тела gRPC запроса без расшифровки TLS в ядре (kTLS). Бизнес-метрики пишут в коде через Prometheus SDK.

## На собеседовании

**Вопрос с собеседования:** «Почему eBPF называют убийцей классических Service Mesh (Istio Envoy)?»
**Ответ:** Классический Istio внедряет Envoy sidecar в каждый под, что удваивает задержку (трафик идет Pod \(\to\) Envoy \(\to\) iptables \(\to\) Network \(\to\) iptables \(\to\) Envoy \(\to\) Pod) и потребляет гигабайты RAM. eBPF перенаправляет пакеты между сокетами напрямую в памяти ядра Linux в обход сетевого стека TCP/IP (Sockops BPF), снижая задержку в 3–4 раза.
