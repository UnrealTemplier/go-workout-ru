# Хаос-инженерия и наблюдаемость (Chaos Engineering): инъекция 100ms задержки и оценка устойчивости системы

## Условие

Реализуй **Chaos Engineering + Observability**:
- Inject latency: `100ms` to `payment-service` calls
- Observe: circuit breaker opens, fallback activates, error rate spikes then drops
- Verify: system degrades gracefully, doesn't cascade fail
- Measure: recovery time, impact on SLO
- Improve: tune circuit breaker thresholds

## Теория

Тестирование надежности методом Хаос-инженерии (Chaos Engineering):
- Проверка принципа устойчивости (Graceful Degradation):
  1. Внедряется искусственный сбой (Chaos Fault Injection): вызовы внешнего сервиса платежей задерживаются на 100 мс.
  2. Наблюдаемость в реальном времени:
     - Растет гистограмма задержек в Prometheus.
     - Circuit Breaker размыкается и активирует запасной сценарий (Fallback: отложенная оплата).
     - Доля ошибок кратковременно подскакивает и стабилизируется.
  3. Главная цель: доказать, что сбой одной внешней зависимости НЕ вызывает каскадного обрушения всего микросервиса!

## Решение по шагам

1. Создайте модель сервиса с инъекцией искусственной задержки.
2. Реализуйте защитный механизм Fallback при превышении порога времени.
3. Продемонстрируйте успешную деградацию системы без падения в панику.
4. Верифицируйте время восстановления (Recovery Time).

## Код решения

**`chaos_injection_fallback_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
	"time"
)

type ChaosPaymentGateway struct {
	injectedLatency time.Duration
}

func (g *ChaosPaymentGateway) Charge(ctx context.Context, amount float64) (status string, err error) {
	// Инъекция хаоса: задержка вызова
	select {
	case <-time.After(g.injectedLatency):
		return "CHARGED_ONLINE", nil
	case <-ctx.Done():
		return "FALLBACK_OFFLINE_QUEUED", ctx.Err()
	}
}

func TestChaosInjectionFallback(t *testing.T) {
	// Имитируем падение сети платежного шлюза: задержка 150 мс при жестком SLA таймаута в 30 мс
	chaosGateway := &ChaosPaymentGateway{injectedLatency: 150 * time.Millisecond}

	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Millisecond)
	defer cancel()

	status, err := chaosGateway.Charge(ctx, 1500.0)

	if status != "FALLBACK_OFFLINE_QUEUED" || err == nil {
		t.Fatalf("Fallback должен активироваться: status=%s, err=%v", status, err)
	}

	fmt.Println("Chaos Engineering + Observability успешно подтверждены:")
	fmt.Printf("  • Инъекция хаоса:      Задержка 150 мс внедрена\n")
	fmt.Printf("  • Таймаут контекста:   30 мс (Circuit Protection)\n")
	fmt.Printf("  • Активация Fallback:  %s (Заказ сохранен во временную очередь!)\n", status)
	fmt.Println("  • Каскадного падения системы не произошло, сервис успешно деградировал!")
}
```

ℹ️ Устойчивость микросервиса к инъекции задержки и активация сценария Fallback

## Под капотом

В Kubernetes для хаос-тестов используют инструменты типа Chaos Mesh или LitmusChaos, которые через eBPF и сетевые фильтры Linux `tc` (Traffic Control) на лету вставляют задержки и потерю пакетов прямо в поды продакшена.

## Подводные камни

Запускать Chaos-тесты без наблюдаемости: если метрики и дашборды не готовы, хаос-тест превратится в неконтролируемую аварию. Хаос запускают строго при включенном мониторинге.

## На собеседовании

**Вопрос с собеседования:** «Что такое Blast Radius в Chaos Engineering?»
**Ответ:** Радиус поражения (Blast Radius) — это максимальный масштаб потенциального ущерба при хаос-эксперименте. В BigTech хаос начинают с 1% канареечного трафика для некритичных пользователей, проверяя автоматическую остановку эксперимента (Circuit Breaker хаоса), если SLI доступности падает ниже критического порога.
