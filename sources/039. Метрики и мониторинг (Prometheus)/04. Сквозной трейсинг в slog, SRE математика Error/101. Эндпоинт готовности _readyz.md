# Эндпоинт готовности /readyz: проверка доступности зависимостей PostgreSQL, Redis и Kafka

## Условие

Реализуйте **readiness probe** endpoint (`/readyz`): возвращает 200, только если все зависимости (БД, Redis, Kafka) доступны.

## Теория

Проектирование эндпоинта `/readyz` (Kubernetes Readiness Probes):
- Соглашение Kubernetes: эндпоинты проверки оканчиваются на `z` (`/livez`, `/readyz`, `/healthz`).
- **Логика `/readyz`:**
  - Опрашивает 3 ключевые зависимости с жестким таймаутом (например, 1 секунда на всё):
    1. PostgreSQL: `db.PingContext(ctx)`.
    2. Redis: `redisClient.Ping(ctx)`.
    3. Kafka: проверка связи с брокером метаданных.
  - Если ВСЕ здоровы \(\to\) HTTP `200 OK`.
  - Если хоть одна недоступна \(\to\) HTTP `503 Service Unavailable` с детализацией в JSON теле.

## Решение по шагам

1. Создайте структуру проверки мульти-зависимостей.
2. Реализуйте HTTP-обработчик `/readyz`.
3. Смоделируйте сценарий полной готовности (200 OK).
4. Смоделируйте падение Redis и проверьте возврат 503.

## Код решения

**`readyz_endpoint_dependencies_test.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"testing"
	"time"
)

type DependencyStatus struct {
	Postgres string `json:"postgres"`
	Redis    string `json:"redis"`
	Kafka    string `json:"kafka"`
}

type SystemReadinessChecker struct {
	pgOK    bool
	redisOK bool
	kafkaOK bool
}

func (c *SystemReadinessChecker) Check(ctx context.Context) (DependencyStatus, error) {
	status := DependencyStatus{Postgres: "OK", Redis: "OK", Kafka: "OK"}

	if !c.pgOK {
		status.Postgres = "DOWN"
		return status, errors.New("postgres unavailable")
	}
	if !c.redisOK {
		status.Redis = "DOWN"
		return status, errors.New("redis unavailable")
	}
	if !c.kafkaOK {
		status.Kafka = "DOWN"
		return status, errors.New("kafka unavailable")
	}

	return status, nil
}

func ReadyzHandler(checker *SystemReadinessChecker) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), 1*time.Second)
		defer cancel()

		status, err := checker.Check(ctx)
		w.Header().Set("Content-Type", "application/json")

		if err != nil {
			w.WriteHeader(http.StatusServiceUnavailable) // 503
			_ = json.NewEncoder(w).Encode(status)
			return
		}

		w.WriteHeader(http.StatusOK) // 200
		_ = json.NewEncoder(w).Encode(status)
	}
}

func TestReadyzEndpointDependencies(t *testing.T) {
	checker := &SystemReadinessChecker{pgOK: true, redisOK: true, kafkaOK: true}
	handler := ReadyzHandler(checker)

	// 1. Все готовы -> 200 OK
	rec1 := httptest.NewRecorder()
	handler(rec1, httptest.NewRequest("GET", "/readyz", nil))
	if rec1.Code != http.StatusOK {
		t.Fatalf("Ожидалось 200 OK: %d", rec1.Code)
	}

	// 2. Redis упал -> 503 Service Unavailable
	checker.redisOK = false
	rec2 := httptest.NewRecorder()
	handler(rec2, httptest.NewRequest("GET", "/readyz", nil))
	if rec2.Code != http.StatusServiceUnavailable {
		t.Fatalf("Ожидалось 503 Service Unavailable: %d", rec2.Code)
	}

	fmt.Println("Эндпоинт /readyz с проверкой зависимостей успешно проверен:")
	fmt.Printf("  • Статус всех систем здоровых: 200 OK (Трафик разрешен)\n")
	fmt.Printf("  • При сбое Redis:              503 Service Unavailable (Трафик автоматически снят)\n")
	fmt.Printf("  • Тело ответа при сбое:        %s", rec2.Body.String())
}
```

## Под капотом

Опрос зависимостей внутри `/readyz` выполняют параллельно в отдельных горутинах через `sync.WaitGroup` или `golang.org/x/sync/errgroup`, чтобы суммарное время проверки не превышало время ответа самой медленной зависимости.

## Подводные камни

Выполнять долгие тяжелые запросы типа `SELECT COUNT(*)` внутри `/readyz`: readiness probe вызывается Kubelet каждые 5–10 секунд. Проверка обязана быть легким пингом сокета (`db.PingContext`).

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если база данных упадет во время пика трафика, а у всех 100 подов настроен readiness probe на проверку БД?»
**Ответ:** Все 100 подов одновременно начнут возвращать 503, и Kubernetes Service снимет трафик со всех подов сервиса. Пользователи увидят страницу 502/503 от Ingress-контроллера. Однако поды останутся запущенными в памяти и мгновенно вернутся в работу, как только база данных восстановится, без перезапусков контейнеров.
