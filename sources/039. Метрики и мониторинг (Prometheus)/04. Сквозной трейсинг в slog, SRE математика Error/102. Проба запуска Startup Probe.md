# Проба запуска Startup Probe: безопасная инициализация долгих миграций БД и прогрева кэша

## Условие

Создайте **startup probe** для медленно стартующих приложений (например, с долгими миграциями БД).

## Теория

Назначение Kubernetes Startup Probe:
- Если микросервис при старте применяет SQL-миграции базы данных или загружает ML-модель в память (занимает 2–3 минуты):
  - Обычная `livenessProbe` начнет проверять под уже через 10 секунд.
  - Решив, что сервис завис, Kubelet начнет циклически убивать и перезапускать под (`CrashLoopBackOff`)!
- **Решение: `startupProbe`:**
  - Дает контейнеру временное окно для старта:
    `failureThreshold: 30`, `periodSeconds: 10` (\(30 \times 10 = 300\text{ секунд}\) запаса).
  - Пока startup probe не вернет 200 OK, проверки liveness и readiness **полностью отключены**.

## Решение по шагам

1. Создайте модель жизненного цикла с флагом `isInitialized`.
2. Реализуйте хендлер `/startupz`.
3. Смоделируйте стадию прогрева (возврат 503).
4. Продемонстрируйте переход в состояние готовности (возврат 200 OK).

## Код решения

**`startup_probe_lifecycle_test.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"testing"
)

type WarmupAppServer struct {
	initialized atomic.Bool
}

func (s *WarmupAppServer) StartupHandler(w http.ResponseWriter, r *http.Request) {
	if !s.initialized.Load() {
		http.Error(w, "WARMING_UP: applying db migrations and loading in-memory cache", http.StatusServiceUnavailable) // 503
		return
	}
	w.WriteHeader(http.StatusOK)
	fmt.Fprint(w, "STARTUP_COMPLETE")
}

func TestStartupProbeLifecycle(t *testing.T) {
	app := &WarmupAppServer{}

	// 1. Стадия прогрева: миграции выполняются -> 503 (Kubelet терпеливо ждет)
	rec1 := httptest.NewRecorder()
	app.StartupHandler(rec1, httptest.NewRequest("GET", "/startupz", nil))
	if rec1.Code != http.StatusServiceUnavailable {
		t.Fatalf("Должно быть 503 во время прогрева: %d", rec1.Code)
	}

	// 2. Инициализация завершена!
	app.initialized.Store(true)

	// 3. Сервис прогрет -> 200 OK (Kubelet включает Liveness и Readiness)
	rec2 := httptest.NewRecorder()
	app.StartupHandler(rec2, httptest.NewRequest("GET", "/startupz", nil))
	if rec2.Code != http.StatusOK {
		t.Fatalf("Должно быть 200 OK после инициализации: %d", rec2.Code)
	}

	fmt.Println("Kubernetes Startup Probe успешно верифицирована:")
	fmt.Printf("  • Фаза старта:   503 Service Unavailable (Kubelet не убивает под!)\n")
	fmt.Printf("  • После миграций: 200 OK (Штатная передача управления в Liveness/Readiness)\n")
	fmt.Println("  • Полная защита от циклического падения в CrashLoopBackOff!")
}
```

## Под капотом

После того как Startup Probe вернула код 200 OK хотя бы один раз, Kubelet прекращает ее опрос навсегда до следующего перезапуска контейнера, переключаясь исключительно на циклы Liveness и Readiness.

## Подводные камни

Увеличивать `initialDelaySeconds` у Liveness пробы вместо использования Startup Probe: фиксированная задержка замедлит обнаружение реальных зависаний сервиса в нормальном режиме работы.

## На собеседовании

**Вопрос с собеседования:** «Почему применять SQL-миграции базы данных внутри Startup Probe пода в проде считается рискованным антипаттерном?»
**Ответ:** Если сервис масштабируется в 20 реплик (HPA), все 20 подов одновременно попытаются выполнить миграцию, что может вызвать блокировку таблиц DDL в базе данных. В BigTech миграции выносят в отдельный разовый `Kubernetes Job` (Helm pre-install hook), а в Startup Probe оставляют только проверку того, что миграция уже успешно завершена.
