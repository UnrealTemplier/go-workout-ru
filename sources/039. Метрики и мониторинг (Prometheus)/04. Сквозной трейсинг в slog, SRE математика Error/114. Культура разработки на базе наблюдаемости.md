# Культура разработки на базе наблюдаемости (Observability-Driven Development): стандарты ODD от CI до Production

## Условие

Реализуй **Observability-Driven Development (ODD)**:
- Before feature: define SLI/SLO, create dashboard placeholder, write alert rules
- During development: instrument code with traces, metrics, logs
- In CI: validate instrumentation (check for new spans, metric cardinality)
- In staging: load test, verify SLO, tune thresholds
- In production: monitor, iterate, improve based on real data
- Culture: "if you can't observe it, you can't operate it"

## Теория

Манифест Observability-Driven Development (ODD):
- Принцип: *«Если ты не можешь это наблюдать — ты не имеешь права это эксплуатировать»* («If you can't observe it, you can't operate it»).
- **Жизненный цикл фичи в методологии ODD:**
  1. **До написания кода:** формулировка SLI/SLO, создание макета дашборда и определение порогов алертов.
  2. **В процессе разработки:** написание юнит-тестов на метрики и покрытие критических путей спанами трейсов.
  3. **В CI/CD:** статический анализ кардинальности меток (`promlinter`) и проверка наличия `runbook_url`.
  4. **На Staging:** нагрузочное тестирование с верификацией SLO.
  5. **В Production:** канареечный релиз (Canary Deployment) с контролем Error Budget.

## Решение по шагам

1. Создайте модель 5 этапов пайплайна Observability-Driven Development.
2. Реализуйте проверку выполнения критериев качества на каждом этапе.
3. Убедитесь в блокировке релиза при отсутствии метрик или превышении кардинальности.
4. Сформулируйте финальные выводы главы.

## Код решения

**`odd_lifecycle_pipeline_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ODDCriteria struct {
	HasSLODefined     bool
	HasMetricsTests   bool
	CardinalitySafe   bool
	StagingLoadTested bool
	CanaryMonitored   bool
}

func ValidateODDPipeline(c ODDCriteria) (approvedForProduction bool, blockedReason string) {
	if !c.HasSLODefined {
		return false, "БЛОКИРОВКА: Не определен SLO и допустимый бюджет ошибок фичи"
	}
	if !c.HasMetricsTests {
		return false, "БЛОКИРОВКА: Отсутствуют юнит-тесты на инкремент метрик"
	}
	if !c.CardinalitySafe {
		return false, "БЛОКИРОВКА: В CI обнаружен риск высокой кардинальности (High Cardinality)"
	}
	if !c.StagingLoadTested {
		return false, "БЛОКИРОВКА: Фича не прошла нагрузочное тестирование на Staging"
	}
	if !c.CanaryMonitored {
		return false, "БЛОКИРОВКА: Отсутствует автоматический откат при канареечном релизе"
	}
	return true, "READY_FOR_PRODUCTION"
}

func TestODDLifecyclePipeline(t *testing.T) {
	// Сценарий 1: Разработчик забыл тесты на метрики -> CI отклоняет PR!
	badPR := ODDCriteria{
		HasSLODefined:     true,
		HasMetricsTests:   false, // Забыл!
		CardinalitySafe:   true,
		StagingLoadTested: true,
		CanaryMonitored:   true,
	}

	ok1, reason1 := ValidateODDPipeline(badPR)
	if ok1 {
		t.Fatal("PR без тестов на метрики не должен пройти")
	}

	// Сценарий 2: Все 5 критериев ODD соблюдены -> Зеленый свет в прод!
	goodPR := ODDCriteria{
		HasSLODefined:     true,
		HasMetricsTests:   true,
		CardinalitySafe:   true,
		StagingLoadTested: true,
		CanaryMonitored:   true,
	}

	ok2, reason2 := ValidateODDPipeline(goodPR)
	if !ok2 || reason2 != "READY_FOR_PRODUCTION" {
		t.Fatalf("Идеальный PR обязан быть одобрен: %s", reason2)
	}

	fmt.Println("Observability-Driven Development (ODD) успешно верифицирован:")
	fmt.Printf("  • Сценарий 1 (CI Gate): %s\n", reason1)
	fmt.Printf("  • Сценарий 2 (Release): %s\n", reason2)
	fmt.Println("  • Золотой стандарт BigTech: наблюдаемость является неотъемлемой частью архитектуры!")
}
```

## Под капотом

В ведущих технологических компаниях культура ODD закреплена в Architecture Review: ни один сервис не может выйти в прод без утвержденного дашборда RED и согласованных порогов алертов с дежурной сменой SRE.

## Подводные камни

Вспоминать о мониторинге после первого падения в продакшене: добавление метрик и трейсов "задним числом" в аварийной спешке всегда приводит к багам и неполной телеметрии.

## На собеседовании

**Вопрос с собеседования:** «В чем заключается суть Observability-Driven Development (ODD) и почему это не просто "навесить Grafana"?»
**Ответ:** ODD — это инженерная философия, в которой наблюдаемость проектируется на этапе формулировки требований. Инженер сначала задает вопросы: *«Как мы поймем, что фича работает? Как мы узнаем, что она тормозит? Какой бизнес-эффект она несет?»* и закладывает метрики, спаны и алерты прямо в дизайн-документ (RFC), делая систему полностью прозрачной с первой секунды первого релиза.
