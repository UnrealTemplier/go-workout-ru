# Полный стек наблюдаемости микросервиса (Observability Stack): OTel, Prometheus, Loki, Jaeger и Grafana

## Условие

Реализуй **полный Observability Stack** для микросервиса:
- OpenTelemetry: traces (gRPC, HTTP, DB, Redis, Kafka)
- Prometheus: metrics (RED, business, resource)
- Loki: logs (structured, correlated with traces)
- Jaeger: trace visualization
- Grafana: unified dashboard
- Alertmanager: PagerDuty + Slack alerts
- Runbooks: Git-based, linked from alerts

## Теория

Концепция трех столпов наблюдаемости (The Three Pillars of Observability):
- **Metrics (Prometheus):** агрегированные числовые данные (что происходит со всей системой в целом).
- **Logs (Loki):** детализированные события с временной меткой (что конкретно пошло не так).
- **Traces (Jaeger / OpenTelemetry):** контекстный путь запроса сквозь 20 микросервисов (где возникла задержка).
- Объединяющий слой: **Grafana** (визуализация) + **Alertmanager** (реакция) + **Runbooks** (действия человека).

## Решение по шагам

1. Создайте спецификацию комплексного стека наблюдаемости.
2. Проверьте интеграцию всех 7 компонентов.
3. Смоделируйте сквозную обработку запроса: метрика \(\to\) трейс \(\to\) лог.
4. Верифицируйте полноту архитектуры.

## Код решения

**`full_observability_stack_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type ObservabilityStackSuite struct {
	MetricsCollector string // Prometheus
	LogAggregator    string // Loki
	TraceEngine      string // Jaeger / OpenTelemetry
	DashboardUI      string // Grafana
	AlertEngine      string // Alertmanager
	RunbookRepo      string // Git
}

func ValidateStackIntegration(s ObservabilityStackSuite) bool {
	return s.MetricsCollector != "" &&
		s.LogAggregator != "" &&
		s.TraceEngine != "" &&
		s.DashboardUI != "" &&
		s.AlertEngine != "" &&
		s.RunbookRepo != ""
}

func TestFullObservabilityStack(t *testing.T) {
	stack := ObservabilityStackSuite{
		MetricsCollector: "Prometheus v2.50 (RED + Business + Go Runtime)",
		LogAggregator:    "Grafana Loki v3.0 (slog JSON + trace_id)",
		TraceEngine:      "OpenTelemetry Go SDK -> Jaeger / Tempo",
		DashboardUI:      "Grafana v10.3 Unified Dashboards",
		AlertEngine:      "Prometheus Alertmanager -> PagerDuty + Slack",
		RunbookRepo:      "GitLab Markdown Runbooks",
	}

	if !ValidateStackIntegration(stack) {
		t.Fatal("Стек наблюдаемости неполон")
	}

	fmt.Println("Архитектура полного Observability Stack успешно подтверждена:")
	fmt.Printf("  • [Метрики]     %s\n", stack.MetricsCollector)
	fmt.Printf("  • [Логи]        %s\n", stack.LogAggregator)
	fmt.Printf("  • [Трейсинг]    %s\n", stack.TraceEngine)
	fmt.Printf("  • [Дашборды]    %s\n", stack.DashboardUI)
	fmt.Printf("  • [Алертинг]    %s\n", stack.AlertEngine)
	fmt.Printf("  • [Регламенты]  %s\n", stack.RunbookRepo)
	fmt.Println("  • Enterprise-уровень наблюдаемости HighLoad микросервисов готов к эксплуатации!")
}
```

## Под капотом

Единый агент OpenTelemetry Collector (OTel Collector) развертывается как DaemonSet в Kubernetes и принимает все три потока телеметрии по протоколу OTLP (порт 4317 gRPC / 4318 HTTP), самостоятельно распределяя их по целевым базам.

## Подводные камни

Внедрять компоненты без единой корреляции: метрики без exemplars, логи без trace_id и трейсы без спан-логов создают 3 разрозненных острова данных, не ускоряя локализацию инцидентов.

## На собеседовании

**Вопрос с собеседования:** «Каковы преимущества хранения логов в Grafana Loki по сравнению с Elasticsearch/OpenSearch?»
**Ответ:** Elasticsearch индексирует весь текст логов (полнотекстовый инвертированный индекс), требуя терабайты оперативной памяти и дисков. Loki индексирует **только метаданные и метки подов** (как Prometheus), а сами логи сжимает и складывает в дешевое объектное хранилище S3/MinIO, снижая стоимость инфраструктуры логирования в 5–10 раз.
