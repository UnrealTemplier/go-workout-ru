# Каверзный кейс: потеря контекста Context Loss и разрыв цепочки распределенной трассировки

## Условие

**[Каверзный кейс — Context Loss]**: Напиши цепочку: HTTP Handler -> Service -> DB. Намеренно потеряй контекст, передав `context.Background()` в сервис. Посмотри, как метрики и трейсы перестают быть связаны с входящим запросом. Исправь.

## Теория

Анатомия разрыва контекста (Context Orphan):
- Цепочка вызова: `Handler(ctx) -> Service(ctx) -> DB(ctx)`.
- Если неаккуратный разработчик внутри сервиса напишет:
  `res, err := s.db.QueryContext(context.Background(), query)`
  - Создается полностью новый, изолированный контекст.
  - Теряются: `trace_id`, дедлайны отмены клиента (`ctx.Done()`), пользовательские атрибуты.
  - В Jaeger вместо единого дерева транзакции появляются **два разорванных трейса**-сироты.
  - Если клиент нажал «Отмена» в браузере, запрос к базе данных продолжит бессмысленно выполняться и жечь CPU!

## Решение по шагам

1. Создайте цепочку вызовов с намеренной передачей `context.Background()`.
2. Продемонстрируйте потерю связи идентификаторов трейса.
3. Исправьте код, передав корректный родительский контекст.
4. Проверьте целостность сквозной цепочки.

## Код решения

**`context_loss_debugging_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type traceCtxKey struct{}

func TraceIDFromCtx(ctx context.Context) string {
	val, _ := ctx.Value(traceCtxKey{}).(string)
	return val
}

type DatabaseLayer struct{}

func (d *DatabaseLayer) ExecuteQuery(ctx context.Context) string {
	return TraceIDFromCtx(ctx)
}

// 1. ОШИБОЧНАЯ РЕАЛИЗАЦИЯ: потеря контекста
func BrokenServiceCall(incomingCtx context.Context, db *DatabaseLayer) string {
	// АНТИПАТТЕРН: выбросили incomingCtx и создали пустой context.Background()!
	lostCtx := context.Background()
	return db.ExecuteQuery(lostCtx)
}

// 2. ИСПРАВЛЕННАЯ РЕАЛИЗАЦИЯ: сохранение контекста
func CorrectServiceCall(incomingCtx context.Context, db *DatabaseLayer) string {
	return db.ExecuteQuery(incomingCtx)
}

func TestContextLossDebugging(t *testing.T) {
	rootCtx := context.WithValue(context.Background(), traceCtxKey{}, "trace-root-445566")
	db := &DatabaseLayer{}

	// Проверяем баг
	brokenTraceID := BrokenServiceCall(rootCtx, db)
	if brokenTraceID != "" {
		t.Fatal("В сломанном вызове трейс должен был потеряться")
	}

	// Проверяем исправление
	correctTraceID := CorrectServiceCall(rootCtx, db)
	if correctTraceID != "trace-root-445566" {
		t.Fatalf("Трейс потерян в исправленном вызове: %s", correctTraceID)
	}

	fmt.Println("Каверзный кейс: потеря контекста успешно проанализирована:")
	fmt.Printf("  • До исправления: trace_id='%s' (Разрыв трейса и утечка ресурсов при отмене!)\n", brokenTraceID)
	fmt.Printf("  • После ремонта:  trace_id='%s' (Сквозная связность полностью восстановлена)\n", correctTraceID)
	fmt.Println("  • Правило: никогда не создавай context.Background() внутри слоя бизнес-логики!")
}
```

## Под капотом

Статический анализатор `contextcheck` в составе `golangci-lint` автоматически выявляет вызовы функций с `context.Background()` или `context.TODO()` в местах, где в сигнатуре метода уже доступен активный `ctx`.

## Подводные камни

Передавать `context.TODO()` в продакшен-коде как «временную заглушку»: временные заглушки остаются в коде годами, скрытно ломая трассировку и таймауты запросов.

## На собеседовании

**Вопрос с собеседования:** «В каком единственном случае внутри сервисного слоя допустимо отвязать контекст от входящего запроса?»
**Ответ:** Когда операция обязана выполниться гарантированно, даже если клиент оборвал соединение (например, запись аудиторского следа платежа в журнал безопасности или отправка критического push-уведомления). В этом случае используют `context.WithoutCancel(ctx)` в Go 1.21+, сохраняя трейсы, но игнорируя отмену.
