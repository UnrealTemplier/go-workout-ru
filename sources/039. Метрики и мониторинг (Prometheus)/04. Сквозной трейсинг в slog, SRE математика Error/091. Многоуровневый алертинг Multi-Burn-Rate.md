# Многоуровневый алертинг Multi-Burn-Rate: разделение на Fast Burn (ночной звонок) и Slow Burn (тикет)

## Условие

Настрой **Multi-window, multi-burn-rate alerts**: `fast burn` (1% budget in 1 hour) → page immediately. `slow burn` (100% budget in 3 days) → ticket tomorrow. Покажи `alert: ErrorBudgetBurn` with multiple conditions.

## Теория

Градация уровней эскалации инцидентов (Severity Routing):
1. **Fast Burn Alert (Критический инцидент P0):**
   - Условие: сжигание \(1\%\) бюджета за 1 час (\(14.4\text{x}\) Burn Rate).
   - Действие: `severity: critical` \(\to\) PagerDuty звонит на мобильный телефон дежурного инженера ночью.
2. **Slow Burn Alert (Медленная деградация P2):**
   - Условие: сжигание \(10\%\) бюджета за 3 дня (\(1\text{x}\) Burn Rate).
   - Действие: `severity: warning` \(\to\) автоматическое создание задачи в Jira/YouTrack в рабочее время без побудки людей ночью.

## Решение по шагам

1. Создайте модель двух правил алертинга: Fast Burn и Slow Burn.
2. Проверьте условия маршрутизации для обоих сценариев.
3. Продемонстрируйте корректный выбор канала (PagerDuty vs Jira).
4. Верифицируйте защиту сна дежурных инженеров.

## Код решения

**`multi_burn_rate_rules_test.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type BurnRatePolicy struct {
	Name       string
	BurnRate   float64
	Severity   string
	Channel    string
}

func ClassifyBurnRateIncident(burnRate float64) BurnRatePolicy {
	if burnRate >= 14.4 {
		return BurnRatePolicy{
			Name:     "FastBurnRateExhaustion",
			BurnRate: burnRate,
			Severity: "critical",
			Channel:  "PagerDuty-Call-OnCall",
		}
	} else if burnRate >= 1.0 {
		return BurnRatePolicy{
			Name:     "SlowBurnRateExhaustion",
			BurnRate: burnRate,
			Severity: "warning",
			Channel:  "Jira-AutoTicket-WorkingHours",
		}
	}
	return BurnRatePolicy{Name: "Normal", BurnRate: burnRate, Severity: "none", Channel: "none"}
}

func TestMultiBurnRateRules(t *testing.T) {
	// Сценарий 1: Авария (16x burn) -> Ночной звонок
	p1 := ClassifyBurnRateIncident(16.0)
	if p1.Severity != "critical" || p1.Channel != "PagerDuty-Call-OnCall" {
		t.Fatalf("Ошибка классификации Fast Burn: %+v", p1)
	}

	// Сценарий 2: Медленная утечка (2x burn) -> Спокойный тикет утром
	p2 := ClassifyBurnRateIncident(2.0)
	if p2.Severity != "warning" || p2.Channel != "Jira-AutoTicket-WorkingHours" {
		t.Fatalf("Ошибка классификации Slow Burn: %+v", p2)
	}

	fmt.Println("Многоуровневый алертинг Multi-Burn-Rate успешно проверен:")
	fmt.Printf("  • Fast Burn (16x): %s -> Канал: %s (P0)\n", p1.Name, p1.Channel)
	fmt.Printf("  • Slow Burn (2x):  %s -> Канал: %s (P2)\n", p2.Name, p2.Channel)
	fmt.Println("  • Инженеры высыпаются ночью, а мелкие деградации гарантированно попадают в бэклог!")
}
```

ℹ️ Разделение алертов сжигания бюджета на срочные (PagerDuty) и плановые (Jira)

## Под капотом

Такой подход устраняет проблему «Alert Fatigue» (эмоциональное выгорание инженеров от постоянных ночных алертов), четко отделяя угрозы крушения бизнеса от мелких багов.

## Подводные камни

Направлять все алерты без разбора в ночной PagerDuty: через 2 недели дежурные инженеры начнут игнорировать или выключать телефон, пропустив реальную катастрофу.
