# Инженерные регламенты Runbook: Markdown-инструкции в Git и привязка runbook_url в алерты

## Условие

Создай **Runbook** для каждого alert: `HighErrorRate` → "1. Check /metrics for 5xx spikes. 2. Check logs for stack traces. 3. Check recent deployments. 4. Rollback if needed. 5. Escalate to on-call if unresolved in 15 min". Храни в Git (Markdown), link в Alertmanager.

## Теория

Культура написания Runbooks (Playbooks) в SRE:
- Ночью в состоянии стресса дежурный инженер не должен вспоминать, где лежат логи или как делать откат.
- **Стандарт Runbook:**
  - Каждый алерт в аннотации обязан содержать ссылку:
    `runbook_url: "https://git.company.ru/ops/runbooks/high_error_rate.md"`
  - Содержание:
    1. Краткое описание инцидента.
    2. Прямая ссылка на дашборд Grafana.
    3. Команды kubectl для проверки подов (`kubectl logs`, `kubectl top`).
    4. Пошаговый алгоритм отката (Rollback).
    5. Контакты лидера команды и архитектора для эскалации.

## Решение по шагам

1. Создайте модель регламента Runbook.
2. Сформируйте пошаговый чеклист действий при инциденте `HighErrorRate`.
3. Проверьте генерацию ссылки `runbook_url` в аннотации алерта.
4. Верифицируйте полноту регламента.

## Код решения

**`runbook_specification_test.go`**

```go
package main

import (
	"fmt"
	"strings"
	"testing"
)

type IncidentRunbook struct {
	AlertName string
	URL       string
	Steps     []string
}

func GenerateRunbookForAlert(alertName string) IncidentRunbook {
	return IncidentRunbook{
		AlertName: alertName,
		URL:       fmt.Sprintf("https://git.company.ru/runbooks/%s.md", strings.ToLower(alertName)),
		Steps: []string{
			"1. Проверить дашборд Grafana на предмет всплеска 5xx кодов.",
			"2. Открыть Loki и отфильтровать логи по level=error и panic stacktraces.",
			"3. Проверить историю недавних деплоев в ArgoCD/Kubernetes.",
			"4. При необходимости выполнить мгновенный откат: argocd app rollback order-service.",
			"5. Если инцидент не локализован за 15 минут, эскалировать на Team Lead.",
		},
	}
}

func TestRunbookSpecification(t *testing.T) {
	rb := GenerateRunbookForAlert("HighErrorRate")

	if len(rb.Steps) != 5 || !strings.Contains(rb.URL, "higherrorrate.md") {
		t.Fatalf("Некорректный Runbook: %+v", rb)
	}

	fmt.Println("Инженерный Runbook успешно верифицирован:")
	fmt.Printf("  • Алерт:        %s\n", rb.AlertName)
	fmt.Printf("  • Ссылка Git:   %s\n", rb.URL)
	fmt.Println("  • Пошаговый чеклист локализации:")
	for _, s := range rb.Steps {
		fmt.Printf("    %s\n", s)
	}
	fmt.Println("  • Человеческий фактор и паника во время ночных сбоев исключены!")
}
```

## Под капотом

В крупных BigTech компаниях CI/CD линтер проверяет манифесты правил алертинга: если в правиле отсутствует аннотация `runbook_url`, Pull Request блокируется автоматически.

## Подводные камни

Давать ссылку на закрытую страницу Notion/Confluence, требующую пароля через VPN, который у дежурного инженера может не работать с телефона: ранбуки хранят в публично доступном защищенном Git-репозитории или экспортируют в статический HTML.

## На собеседовании

**Вопрос с собеседования:** «Что такое Post-Mortem (Ретроспектива инцидента) и как он связан с Runbook?»
**Ответ:** После каждого крупного инцидента проводится безапелляционный разбор (Blameless Post-Mortem). Его главным итогом является не наказание инженера, а доработка архитектуры, тестов и обязательное обновление Runbook: если дежурный тратил лишнее время на поиск логов, в ранбук добавляют готовую поисковую ссылку LogQL.
