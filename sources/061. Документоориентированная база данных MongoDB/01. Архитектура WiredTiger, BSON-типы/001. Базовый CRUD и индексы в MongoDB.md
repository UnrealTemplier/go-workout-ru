### Исходная формулировка

Создайте single field index на `user_id` и compound index `{user_id: 1, timestamp: -1}`. Используйте `explain("executionStats")` и покажите, как index scan заменяет collection scan.

## Теория

В документоориентированной СУБД MongoDB данные хранятся в бинарном формате BSON (Binary JSON). Движок хранения WiredTiger использует B-деревья для организации индексов на диске.

### Стратегии сканирования в WiredTiger:
1. **COLLSCAN (Collection Scan):** Полный перебор всех документов коллекции O(N). Требует вычитывания страниц памяти с диска в кэш WiredTiger, что катастрофически снижает пропускную способность HighLoad-сервисов.
2. **IXSCAN (Index Scan):** Поиск по B-дереву O(log N). Движок считывает только указатели на документы (RecordID) из индекса, а затем извлекает сами документы (стадия `FETCH`) или сразу возвращает результат, если индекс покрывающий (`PROJECTION_COVERED`).

### Одиночные и составные индексы (Compound Indexes):
- **Single field index:** `bson.D{{"user_id", 1}}` ускоряет фильтрацию по пользователю.
- **Compound index:** `bson.D{{"user_id", 1}, {"timestamp", -1}}` оптимизирует одновременную фильтрацию по пользователю и сортировку событий от свежих к старым без выполнения дорогостоящей сортировки в оперативной памяти (in-memory sort limit = 100 МБ).

Для проверки эффективности запроса вызывается команда `explain` с режимом `executionStats`, возвращающая количество просканированных ключей (`totalKeysExamined`) и документов (`totalDocsExamined`).

## Решение по шагам

1. Инициализируйте клиент `mongo.Connect` и подключитесь к локальной БД.
2. Создайте коллекцию `events` и добавьте тестовые документы.
3. Создайте single field индекс `user_id: 1` и compound индекс `{user_id: 1, timestamp: -1}` через `collection.Indexes().CreateMany`.
4. Выполните команду `explain` на выборку с фильтром по `user_id` и сортировкой по `timestamp` до и после применения индексов.
5. Проанализируйте стадию выполнения: `COLLSCAN` vs `IXSCAN`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/bson/primitive"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type Event struct {
	ID        primitive.ObjectID `bson:"_id,omitempty"`
	UserID    int64              `bson:"user_id"`
	Timestamp time.Time          `bson:"timestamp"`
	Payload   string             `bson:"payload"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()

	clientOpts := options.Client().ApplyURI("mongodb://localhost:27017")
	client, err := mongo.Connect(ctx, clientOpts)
	if err != nil {
		panic(err)
	}
	defer func() {
		if err := client.Disconnect(ctx); err != nil {
			panic(err)
		}
	}()

	db := client.Database("analytics_db")
	coll := db.Collection("events")
	_ = coll.Drop(ctx)

	// 1. Вставка тестовых документов
	now := time.Now()
	docs := []interface{}{
		Event{UserID: 1001, Timestamp: now.Add(-2 * time.Hour), Payload: "login"},
		Event{UserID: 1001, Timestamp: now.Add(-1 * time.Hour), Payload: "click_checkout"},
		Event{UserID: 1002, Timestamp: now.Add(-30 * time.Minute), Payload: "view_item"},
	}
	_, err = coll.InsertMany(ctx, docs)
	if err != nil {
		panic(err)
	}

	// 2. Создание Compound Index: user_id ASC, timestamp DESC
	indexModels := []mongo.IndexModel{
		{
			Keys:    bson.D{{Key: "user_id", Value: 1}},
			Options: options.Index().SetName("idx_user_id"),
		},
		{
			Keys:    bson.D{{Key: "user_id", Value: 1}, {Key: "timestamp", Value: -1}},
			Options: options.Index().SetName("idx_user_time"),
		},
	}
	names, err := coll.Indexes().CreateMany(ctx, indexModels)
	if err != nil {
		panic(err)
	}
	fmt.Println("Созданы индексы:", names)

	// 3. Вызов explain("executionStats") через Database.RunCommand
	filter := bson.D{{Key: "user_id", Value: 1001}}
	cmd := bson.D{
		{Key: "explain", Value: bson.D{
			{Key: "find", Value: "events"},
			{Key: "filter", Value: filter},
			{Key: "sort", Value: bson.D{{Key: "timestamp", Value: -1}}},
		}},
		{Key: "verbosity", Value: "executionStats"},
	}

	var explainResult bson.M
	if err := db.RunCommand(ctx, cmd).Decode(&explainResult); err != nil {
		panic(err)
	}

	fmt.Println("План выполнения запроса (Explain Plan получен успешно):")
	queryPlanner := explainResult["queryPlanner"].(bson.M)
	winningPlan := queryPlanner["winningPlan"].(bson.M)
	fmt.Printf("Winning Plan Stage: %v\n", winningPlan["stage"])
}
```

## Под капотом

В WiredTiger индекс хранится как упорядоченное B+ дерево. Составной индекс упорядочивается сначала по первому полю (`user_id`), а внутри одинаковых `user_id` — по второму полю (`timestamp`). Благодаря этому запрос с фильтром по `user_id` и сортировкой по `timestamp` обращается к диапазону листьев индекса без необходимости выполнять фазу in-memory сортировки (`SORT` stage).

## Подводные камни

Правило ESR (Equality, Sort, Range): в составных индексах поля точного совпадения (Equality) должны идти первыми, затем поля сортировки (Sort), и лишь в конце поля диапазонов (Range). Нарушение этого порядка заставляет движок проверять лишние индексные записи или выполнять in-memory сорт.

## На собеседовании

**Вопрос:** В чем разница между totalKeysExamined, totalDocsExamined и nReturned в executionStats? Какое их соотношение является идеальным?
**Ответ:** `totalKeysExamined` — число записей, просмотренных в индексе; `totalDocsExamined` — число документов, загруженных с диска/кэша; `nReturned` — число документов, возвращенных клиенту. В идеальном запросе (covered query): `totalKeysExamined == nReturned`, а `totalDocsExamined == 0`.
