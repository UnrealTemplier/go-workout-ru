# Подключение и context timeout в Ping

## Условие

Используйте `go.mongodb.org/mongo-driver` для подключения к MongoDB. Используйте `client.Ping()` с context и timeout.

### Исходная формулировка

**Подключение и ping**: Используйте `go.mongodb.org/mongo-driver` для подключения к MongoDB. Используйте `client.Ping()` с context и timeout.

## Теория

В распределенных системах любая сетевая операция обязана быть защищена строгим таймаутом через `context.WithTimeout`. 

При проверке доступности MongoDB метод `Ping(ctx, rp)` принимает контекст и параметр `readpref.ReadPref`:
- `readpref.Primary()`: проверяет доступность мастера (primary), способного принимать операции записи.
- `readpref.Nearest()`: проверяет узел с минимальной сетевой задержкой (RTT), полезно для multi-DC кластеров.

Если сеть недоступна, сетевой стек ОС может удерживать TCP SYN пакеты до 60–120 секунд. Контекст Go принудительно прерывает ожидание через таймер планировщика Go, защищая приложение от зависания горутин.

## Решение по шагам

1. Создайте родительский контекст с таймаутом 2 секунды.
2. Вызовите `client.Ping(ctx, readpref.Primary())`.
3. Обработайте возможную ошибку `context.DeadlineExceeded`.
4. Проверьте поведение системы при указании недоступного адреса сервера.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
	"go.mongodb.org/mongo-driver/mongo/readpref"
)

func CheckMongoHealth(client *mongo.Client, timeout time.Duration) error {
	ctx, cancel := context.WithTimeout(context.Background(), timeout)
	defer cancel()

	err := client.Ping(ctx, readpref.Primary())
	if err != nil {
		if errors.Is(ctx.Err(), context.DeadlineExceeded) {
			return fmt.Errorf("таймаут проверки связи с MongoDB (%v превышен): %w", timeout, err)
		}
		return fmt.Errorf("ошибка пинга MongoDB: %w", err)
	}
	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	// Подключаемся с коротким serverSelectionTimeout
	opts := options.Client().
		ApplyURI("mongodb://localhost:27017").
		SetServerSelectionTimeout(2 * time.Second)

	client, err := mongo.Connect(ctx, opts)
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(context.Background())

	if err := CheckMongoHealth(client, 1*time.Second); err != nil {
		fmt.Printf("HealthCheck FAIL: %v\n", err)
	} else {
		fmt.Println("HealthCheck OK: Primary узел доступен и готов к приему трафика.")
	}
}
```

ℹ️ Проверка доступности MongoDB с ограничением по времени через context.WithTimeout

**`Терминал`**

```bash
go run main.go
# HealthCheck OK: Primary узел доступен и готов к приему трафика.
```

## Под капотом

При наступлении дедлайна контекста планировщик времени Go (`time.Timer`) переводит горутину таймера в состояние runnable. Она закрывает внутренний канал `ctx.Done()`. Драйвер MongoDB слушает этот канал и немедленно вызывает `Close()` на лежащем в основе `net.Conn` сокете, прерывая системный вызов `read` / `poll` в netpoller.

## Подводные камни

Использование `context.Background()` без таймаута в `Ping()` или бизнес-запросах может привести к утечке тысяч горутин при сетевом сбое (Split-brain или падение свитча), пока у ОС не сработает TCP Keepalive таймаут (по умолчанию 2 часа).

## На собеседовании

**Вопрос:** В чем разница между ConnectTimeout и ServerSelectionTimeout в настройках mongo.Client?
**Ответ:** `ConnectTimeout` ограничивает время установки одного физического TCP/TLS соединения с узлом. `ServerSelectionTimeout` — это таймаут драйвера на обнаружение подходящего узла кластера согласно Read Preference. Если Primary упал и идут выборы нового мастера, драйвер будет пытаться найти новый Primary в течение `ServerSelectionTimeout`.
