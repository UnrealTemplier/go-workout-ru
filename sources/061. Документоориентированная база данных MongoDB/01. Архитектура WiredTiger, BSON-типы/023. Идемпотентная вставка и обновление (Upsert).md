# Идемпотентная вставка и обновление (Upsert)

## Условие

Используйте `options.Update().SetUpsert(true)` для "создать или обновить". Изучите `UpsertedID` в результате.

### Исходная формулировка

**Upsert**: Используйте `options.Update().SetUpsert(true)` для "создать или обновить". Изучите `UpsertedID` в результате.

## Теория

Операция **Upsert** (Update or Insert) — это атомарная операция базы данных:
- Если документ, соответствующий фильтру, **найден** — он обновляется согласно операторам апдейта.
- Если документ **не найден** — создается новый документ, поля которого формируются объединением фильтра поиска и операторов обновления (`$set`, `$setOnInsert`).

### Важные свойства Upsert:
- **`UpsertedID`:** если документ был создан, поле `res.UpsertedID` содержит ID нового документа. Если документ был обновлен — `UpsertedID` равно `nil`.
- **`$setOnInsert`:** оператор, позволяющий задать значения полей, которые должны быть записаны **только** в момент создания нового документа (например, `created_at`, начальный баланс), и игнорироваться при последующих обновлениях.

## Решение по шагам

1. Настройте опцию `options.Update().SetUpsert(true)`.
2. Сконструируйте апдейт с комбинацией `$set` и `$setOnInsert`.
3. Выполните первый вызов: документ создается, проверьте `res.UpsertedID != nil`.
4. Выполните повторный вызов с теми же параметрами: документ обновляется, проверьте `res.UpsertedID == nil` и `res.MatchedCount == 1`.
5. Убедитесь, что поле из `$setOnInsert` не перезаписалось.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("stats").Collection("daily_views")
	_ = coll.Drop(ctx)

	pageKey := "article_102"
	now := time.Now().UTC().Truncate(time.Second)

	filter := bson.M{"page_key": pageKey}
	update := bson.M{
		"$inc": bson.M{"views": 1},
		"$set": bson.M{"last_viewed_at": now},
		"$setOnInsert": bson.M{
			"first_created_at": now,
			"author":           "tech_lead",
		},
	}
	opts := options.Update().SetUpsert(true)

	// Итерация 1: Документа нет -> происходит INSERT
	res1, err := coll.UpdateOne(ctx, filter, update, opts)
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Итерация 1] Документ создан: UpsertedID=%v, Matched=%d, Modified=%d\n",
		res1.UpsertedID, res1.MatchedCount, res1.ModifiedCount)

	// Итерация 2: Документ уже есть -> происходит UPDATE
	res2, err := coll.UpdateOne(ctx, filter, update, opts)
	if err != nil {
		panic(err)
	}
	fmt.Printf("[Итерация 2] Документ обновлен: UpsertedID=%v, Matched=%d, Modified=%d\n",
		res2.UpsertedID, res2.MatchedCount, res2.ModifiedCount)

	var doc bson.M
	_ = coll.FindOne(ctx, filter).Decode(&doc)
	fmt.Printf("Финальный документ: Views=%v, Author=%v\n", doc["views"], doc["author"])
}
```

ℹ️ Паттерн Upsert с оператором $setOnInsert для атомарной инициализации

**`Терминал`**

```bash
go run main.go
# [Итерация 1] Документ создан: UpsertedID=ObjectID("66d75411b8e1a539fa08000d"), Matched=0, Modified=0
# [Итерация 2] Документ обновлен: UpsertedID=<nil>, Matched=1, Modified=1
# Финальный документ: Views=2, Author=tech_lead
```

## Под капотом

Для предотвращения гонок при параллельных Upsert-запросах WiredTiger использует блокировку по индексу уникальности. Если по полю `page_key` создан уникальный индекс, параллельный Upsert, попытавшийся вставить тот же ключ одновременно, перехватит `DuplicateKeyError` на уровне ядра и автоматически повторит попытку уже как операцию `Update`.

## Подводные камни

Если по полю фильтра Upsert нет уникального индекса, при одновременном выполнении двух параллельных Upsert запросов с одинаковым условием поиска оба могут не найти документ и вставить две дублирующие записи (Race condition)!

## На собеседовании

**Вопрос:** Почему при проектировании идемпотентных обработчиков сообщений из Kafka паттерн Upsert с уникальным индексом предпочтительнее проверки if not exists insert?
**Ответ:** Схема `Find` + `Insert` неатомарна: между проверкой и вставкой другое сообщение от конкурирующего инстанса сервиса создаст дубликат (Time-of-check to time-of-use bug). `Upsert` выполняется в рамках одной неделимой атомарной транзакции базы данных за 1 сетевой RTT, гарантируя строгую идемпотентность обработки.
