# Операции удаления: DeleteOne, DeleteMany и разница с Drop()

## Условие

Используйте `DeleteOne`, `DeleteMany`. Поймите разницу между `DeleteMany({})` и `Drop()`.

### Исходная формулировка

**Delete operations**: Используйте `DeleteOne`, `DeleteMany`. Поймите разницу между `DeleteMany({})` и `Drop()`.

## Теория

Удаление данных в MongoDB можно выполнить на уровне документов либо на уровне метаданных коллекции:
- **`DeleteOne(ctx, filter)`:** удаляет один документ, первый совпавший с фильтром.
- **`DeleteMany(ctx, filter)`:** удаляет все подходящие документы.
- **`coll.Drop(ctx)`:** полностью уничтожает саму коллекцию вместе со всеми индексами и метаданными.

### Фундаментальная разница между `DeleteMany({})` и `Drop()`:
1. **`DeleteMany({})`:** сканирует каждый документ коллекции, удаляет его ключ из B-дерева каждого индекса и записывает операцию удаления в журнал WiredTiger WAL и replication oplog для каждого документа O(N). Файлы коллекции на диске не сжимаются (пространство помечается как свободное внутри WiredTiger, но ОС не возвращается).
2. **`Drop()`:** мгновенная операция метаданных O(1). MongoDB просто удаляет файлы коллекции и индексов с диска и очищает запись в `system.namespaces`. На порядки быстрее и не нагружает CPU/WAL.

## Решение по шагам

1. Заполните коллекцию тестовыми записями.
2. Удалите одну запись по критерию через `DeleteOne`.
3. Удалите оставшиеся документы по условию через `DeleteMany`.
4. Сравните производительность с полным `Drop()` коллекции.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("cleanup_demo").Collection("logs")

	// Заполняем коллекцию
	docs := make([]interface{}, 100)
	for i := 0; i < 100; i++ {
		docs[i] = bson.M{"level": "debug", "idx": i}
	}
	_, _ = coll.InsertMany(ctx, docs)

	// 1. DeleteOne: удаляет ровно один документ
	res1, err := coll.DeleteOne(ctx, bson.M{"level": "debug"})
	if err != nil {
		panic(err)
	}
	fmt.Printf("[DeleteOne] Удалено: %d документ\n", res1.DeletedCount)

	// 2. DeleteMany: удаляет документы по фильтру
	resMany, err := coll.DeleteMany(ctx, bson.M{"level": "debug"})
	if err != nil {
		panic(err)
	}
	fmt.Printf("[DeleteMany] Удалено: %d документов\n", resMany.DeletedCount)

	// 3. Drop: мгновенное уничтожение метаданных коллекции
	err = coll.Drop(ctx)
	if err != nil {
		panic(err)
	}
	fmt.Println("[Drop] Коллекция и все ее индексы мгновенно уничтожены на уровне файловой системы.")
}
```

ℹ️ Удаление документов через DeleteOne, DeleteMany и сброс коллекции через Drop

**`Терминал`**

```bash
go run main.go
# [DeleteOne] Удалено: 1 документ
# [DeleteMany] Удалено: 99 документов
# [Drop] Коллекция и все ее индексы мгновенно уничтожены на уровне файловой системы.
```

## Под капотом

При `DeleteMany({})` в WiredTiger образуются 'дыры' (allocation fragmentation). Освободившиеся страницы повторно используются для новых документов той же коллекции, но размер файлов `.wt` на диске не уменьшается до выполнения процедуры `compact`. `Drop()` же возвращает дисковое пространство ОС немедленно.

## Подводные камни

Если случайно выполнить `coll.DeleteMany(ctx, bson.M{})` на таблице из 50 миллионов записей, это заблокирует репликацию, переполнит oplog и вызовет 100% загрузку дискового ввода-вывода. Для полной очистки всегда используйте `Drop()`.

## На собеседовании

**Вопрос:** Почему удаление старых данных по частям (DeleteMany) в фоновом воркере может вызывать лаги репликации в кластере MongoDB?
**Ответ:** Каждое удаление генерирует отдельную запись в Replication Oplog. При массовом `DeleteMany` вторичные реплики (Secondaries) не успевают последовательно воспроизводить миллионы записей удаления из oplog, что приводит к росту показателя `Replication Lag`. Правильный подход — удалять данные порциями с паузами (`Sleep`) либо использовать TTL-индексы.
