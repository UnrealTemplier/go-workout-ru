# Мониторинг пула соединений через SetPoolMonitor

## Условие

Настройте `SetPoolMonitor` для отслеживания событий пула соединений (created, closed, failed). Мониторинг connection leaks.

### Исходная формулировка

**Connection pooling**: Настройте `SetPoolMonitor` для отслеживания событий пула соединений (created, closed, failed). Мониторинг connection leaks.

## Теория

Для предотвращения утечек дескрипторов и своевременного обнаружения деградации сетевого пула официальный драйвер Go предоставляет хуки событий: `event.PoolMonitor`.

### События жизненного цикла пула соединений:
- **`ConnectionCreated`:** Создание нового TCP-сокета.
- **`ConnectionReady`:** Соединение успешно аутентифицировано и добавлено в пул доступных.
- **`ConnectionClosed`:** Соединение закрыто (по таймауту idle, ошибке сети или остановке пула).
- **`GetStarted`:** Горутина запросила соединение из пула.
- **`GetSucceeded`:** Соединение успешно выдано горутине.
- **`GetFailed`:** Не удалось выдать соединение (таймаут ожидания в очереди пула).

В production эти счетчики экспортируются в Prometheus метрики (`mongo_pool_checked_out`, `mongo_pool_wait_duration`).

## Решение по шагам

1. Импортируйте пакет `go.mongodb.org/mongo-driver/event`.
2. Создайте структуру `event.PoolMonitor` с обработчиками событий.
3. Используйте атомики (`sync/atomic`) для подсчета активных соединений.
4. Передайте монитор в `options.Client().SetPoolMonitor(monitor)`.
5. Протестируйте появление событий при подключении и выполнении операций.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/event"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type PoolMetrics struct {
	TotalCreated atomic.Int64
	TotalClosed  atomic.Int64
	CheckedOut   atomic.Int64
}

func main() {
	metrics := &PoolMetrics{}

	poolMonitor := &event.PoolMonitor{
		Event: func(evt *event.PoolEvent) {
			switch evt.Type {
			case event.ConnectionCreated:
				metrics.TotalCreated.Add(1)
				fmt.Printf("[POOL] Соединение создано: ConnID=%d\n", evt.ConnectionID)
			case event.ConnectionClosed:
				metrics.TotalClosed.Add(1)
				fmt.Printf("[POOL] Соединение закрыто: ConnID=%d (Причина: %s)\n", evt.ConnectionID, evt.Reason)
			case event.GetSucceeded:
				metrics.CheckedOut.Add(1)
			case event.ConnectionReturned:
				metrics.CheckedOut.Add(-1)
			}
		},
	}

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	clientOpts := options.Client().
		ApplyURI("mongodb://localhost:27017").
		SetPoolMonitor(poolMonitor).
		SetMinPoolSize(2).
		SetMaxPoolSize(10)

	client, err := mongo.Connect(ctx, clientOpts)
	if err != nil {
		panic(err)
	}

	// Выполняем простой запрос для активации соединения
	_ = client.Database("test").RunCommand(ctx, bson.D{{Key: "ping", Value: 1}})

	time.Sleep(100 * time.Millisecond)
	fmt.Printf("Метрики пула: Создано=%d, Закрыто=%d, В работе=%d\n",
		metrics.TotalCreated.Load(),
		metrics.TotalClosed.Load(),
		metrics.CheckedOut.Load(),
	)

	_ = client.Disconnect(ctx)
}
```

ℹ️ Настройка event.PoolMonitor для сбора метрик и обнаружения утечек соединений

**`Терминал`**

```bash
go run main.go
# [POOL] Соединение создано: ConnID=1
# [POOL] Соединение создано: ConnID=2
# Метрики пула: Создано=2, Закрыто=0, В работе=0
# [POOL] Соединение закрыто: ConnID=1 (Причина: PoolClosed)
# [POOL] Соединение закрыто: ConnID=2 (Причина: PoolClosed)
```

## Под капотом

Драйвер вызывает функции обратного вызова `PoolMonitor` синхронно в момент изменения состояния пула. Внутри пула доступные соединения хранятся в стеке/очереди. Когда горутина вызывает `collection.Find()`, она захватывает соединение из пула и возвращает его обратно в пул сразу после завершения чтения или при закрытии курсора (`cursor.Close()`).

## Подводные камни

Если приложение не закрывает курсор `defer cursor.Close(ctx)` при чтении документов через `coll.Find`, соединение остается связанным с незавершенным серверным курсором и не возвращается в пул, вызывая исчерпание пула (`connection pool exhaustion`).

## На собеседовании

**Вопрос:** Что сигнализирует метрика GetFailed в пуле соединений MongoDB и как ее устранить?
**Ответ:** `GetFailed` означает, что все соединения из `MaxPoolSize` были заняты, а новые запросы простояли в очереди ожидания дольше допустимого таймаута (`waitQueueTimeoutMS` или дедлайна контекста). Решения: увеличить `MaxPoolSize` (если позволяет память MongoDB), оптимизировать медленные запросы (добавить индексы, чтобы соединение освобождалось быстрее), или масштабировать сервис горизонтально.
