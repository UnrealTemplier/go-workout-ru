# Реактивные Change Streams и восстановление через Resume Token

## Условие

Реализуйте watcher на коллекцию `events` через `collection.Watch()`. Фильтруйте по `operationType: "insert"`. Покажите механизм `ResumeAfter` с `resumeToken` для восстановления после реконнекта. Объясните, почему Change Stream требует replica set (oplog).

### Исходная формулировка

**Change Streams.**: Реализуйте watcher на коллекцию `events` через `collection.Watch()`. Фильтруйте по `operationType: "insert"`. Покажите механизм `ResumeAfter` с `resumeToken` для восстановления после реконнекта. Объясните, почему Change Stream требует replica set (oplog).

## Теория

Change Streams позволяют сервисам на Go подписываться на поток изменений данных в реальном времени (CDC — Change Data Capture).

### Механика работы:
- **Требование Replica Set:** Change Streams читают системную коллекцию `local.oplog.rs` (Operations Log), куда мастер записывает все бинарные мутации. В standalone-режиме oplog отсутствует, поэтому Change Streams не работают.
- **Resume Token (`_id` стрима):** Каждое событие содержит непрозрачный BSON-токен возобновления `_id`. При сбое сети или перезапуске Go-сервиса клиент передает сохраненный токен в `options.ChangeStream().SetResumeAfter(token)`. Сервер возобновляет передачу событий строго с момента остановки **без единой потери данных**.

## Решение по шагам

1. Подключитесь к кластеру MongoDB (реплика-сет).
2. Запустите `coll.Watch(ctx, pipeline)` с фильтром по `operationType: "insert"`.
3. Сохраняйте `stream.ResumeToken()` при обработке каждого события.
4. Сымитируйте переподключение и возобновите чтение с использованием `SetResumeAfter`.
5. Продемонстрируйте вычитку событий в реальном времени.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type ChangeEvent struct {
	OperationType string   `bson:"operationType"`
	FullDocument  bson.M   `bson:"fullDocument"`
	ClusterTime   bson.Raw `bson:"clusterTime"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017/?replicaSet=rs0"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("stream_demo").Collection("events")
	_ = coll.Drop(ctx)

	// Фильтр: слушаем только операцию INSERT
	pipeline := mongo.Pipeline{
		{{Key: "$match", Value: bson.D{
			{Key: "operationType", Value: "insert"},
		}}},
	}

	// 1. Запуск Change Stream
	streamOpts := options.ChangeStream().SetFullDocument(options.UpdateLookup)
	stream, err := coll.Watch(ctx, pipeline, streamOpts)
	if err != nil {
		fmt.Printf("Change Streams требуют активный Replica Set: %v\n", err)
		return
	}
	defer stream.Close(ctx)

	// Фоновый продюсер событий
	go func() {
		time.Sleep(500 * time.Millisecond)
		_, _ = coll.InsertOne(context.Background(), bson.M{"event": "user_signup", "uid": 101})
		time.Sleep(500 * time.Millisecond)
		_, _ = coll.InsertOne(context.Background(), bson.M{"event": "payment_received", "uid": 101, "val": 500})
	}()

	var lastResumeToken bson.Raw
	fmt.Println("Change Stream успешно запущен. Ожидание событий из oplog...")

	count := 0
	for stream.Next(ctx) {
		var event ChangeEvent
		if err := stream.Decode(&event); err != nil {
			panic(err)
		}
		// Сохраняем resume token для возможности рестарта
		lastResumeToken = stream.ResumeToken()
		count++

		fmt.Printf("[CDC Event %d] Тип: %s | Payload: %v\n",
			count, event.OperationType, event.FullDocument["event"])

		if count == 2 {
			break
		}
	}

	fmt.Printf("\nСохраненный Resume Token: %d байт\n", len(lastResumeToken))
	fmt.Println("При рестарте воркер вызовет: options.ChangeStream().SetResumeAfter(lastResumeToken)")
}
```

## Под капотом

Change Stream открывает tailable awaitData курсор по системной коллекции `local.oplog.rs`. Драйвер удерживает открытое TCP соединение. Когда в oplog появляется новая запись, mongod мгновенно пушит данные в сокет клиенту без задержек поллинга.

## Подводные камни

Размер `local.oplog.rs` ограничен дисковым лимитом (по умолчанию 5% от объема диска). Если воркер был отключен слишком долго и объем новых изменений превысил размер oplog, resume token 'устареет' (выпадет из окна oplog), и сервер вернет ошибку `ChangeStreamHistoryLost`.

## На собеседовании

**Вопрос:** В чем разница между polling базы данных (SELECT ... WHERE updated_at > ?) и Change Streams?
**Ответ:** Поллинг создает постоянную паразитную нагрузку на CPU/диск базы (постоянные SELECT запросы), создает задержку (латентность равна интервалу поллинга) и не может отследить физическое удаление документов (`DELETE`). Change Streams работают реактивно с нулевой задержкой через чтение готового потока WAL/oplog и фиксируют абсолютно все операции (включая удаление и сброс коллекций).
