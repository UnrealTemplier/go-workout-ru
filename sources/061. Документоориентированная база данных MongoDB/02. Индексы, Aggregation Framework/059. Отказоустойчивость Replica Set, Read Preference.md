# Отказоустойчивость Replica Set, Read Preference и failover

## Условие

Подключитесь к replica set через `mongodb://host1,host2,host3/?replicaSet=rs0`. Сымитируйте `stepDown` primary. Покажите, как Go-driver автоматически переключается на новый primary. Объясните read preference: `primary`, `secondary`, `nearest`.

### Исходная формулировка

**Replica Set и Failover.**: Подключитесь к replica set через `mongodb://host1,host2,host3/?replicaSet=rs0`. Сымитируйте `stepDown` primary. Покажите, как Go-driver автоматически переключается на новый primary. Объясните read preference: `primary`, `secondary`, `nearest`.

## Теория

Кластер Replica Set обеспечивает высокую доступность (High Availability):
- Один узел выполняет роль **Primary** (принимает операции записи).
- Остальные узлы являются **Secondary** (асинхронно реплицируют oplog).

### Режимы Read Preference:
- **`primary` (по умолчанию):** все чтения строго на Primary. Гарантирует максимальную свежесть данных (Strong Consistency).
- **`secondary`:** все чтения строго на Secondary. Позволяет разгрузить мастер, но данные могут отставать на лаг репликации.
- **`secondaryPreferred`:** чтение с Secondary; если все реплики недоступны — чтение с Primary.
- **`nearest`:** чтение с узла с минимальной сетевой задержкой (RTT), определяемой фоновым пингом драйвера (идеально для мультирегиональных инсталляций).

При падении или команде `replSetStepDown` драйвер Go автоматически обнаруживает нового лидера через SDAM.

## Решение по шагам

1. Сконфигурируйте строку подключения к набору реплик.
2. Задайте `readpref.SecondaryPreferred()`.
3. Реализуйте функцию чтения, устойчивую к перевыборам мастера.
4. Продемонстрируйте бесперебойную работу при смене лидера кластера.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
	"go.mongodb.org/mongo-driver/mongo/readpref"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// Строка подключения к Replica Set с перечислением seed-узлов
	uri := "mongodb://mongo1:27017,mongo2:27017,mongo3:27017/?replicaSet=rs0&connectTimeoutMS=5000"

	clientOpts := options.Client().
		ApplyURI(uri).
		SetReadPreference(readpref.SecondaryPreferred()).
		SetServerSelectionTimeout(5 * time.Second)

	client, err := mongo.Connect(ctx, clientOpts)
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	fmt.Println("Клиент подключен к Replica Set:")
	fmt.Printf("  ReadPreference: %v\n", clientOpts.ReadPreference.Mode())

	// Проверяем статус топологии
	res := client.Database("admin").RunCommand(ctx, bson.D{{Key: "isMaster", Value: 1}})
	var masterDoc bson.M
	_ = res.Decode(&masterDoc)

	fmt.Println("Текущее состояние кластера:")
	fmt.Printf("  Имя реплика-сета: %v\n", masterDoc["setName"])
	fmt.Printf("  Текущий Primary:  %v\n", masterDoc["primary"])
	fmt.Printf("  Список всех нод:  %v\n", masterDoc["hosts"])
}
```

## Под капотом

Драйвер запускает горутину SDAM-мониторинга для каждого узла. При вызове `rs.stepDown()` Primary закрывает клиентские сокеты и переходит в статус Secondary. Драйвер перехватывает событие, объявляет выборы и в течение нескольких сотен миллисекунд переключает пул записи на новый Primary.

## Подводные камни

При чтении с `SecondaryPreferred` без включенной Causal Consistency сервис может прочитать устаревшие данные (Stale Read) из-за лага репликации между дата-центрами.

## На собеседовании

**Вопрос:** Что произойдет с операциями записи в Go-сервисе в момент перевыборов Primary (обычно 2–5 секунд)?
**Ответ:** Если включен режим `retryWrites=true`, драйвер автоматически буферизует запрос записи в течение времени `serverSelectionTimeout` (по умолчанию 30 секунд), дожидается окончания выборов и отправляет запись новому Primary без возврата ошибки в прикладной код Go.
