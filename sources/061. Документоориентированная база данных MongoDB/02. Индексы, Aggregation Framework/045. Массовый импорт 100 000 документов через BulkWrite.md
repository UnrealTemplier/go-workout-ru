# Массовый импорт 100 000 документов через BulkWrite Unordered

## Условие

Импортируйте 100 000 документов через `collection.BulkWrite()` с `ordered: false`. Сравните скорость с пошаговой `InsertOne`. Объясните разницу между `ordered` (стоп при ошибке) и `unordered` (продолжает, возвращает все ошибки).

### Исходная формулировка

**Bulk Write.**: Импортируйте 100 000 документов через `collection.BulkWrite()` с `ordered: false`. Сравните скорость с пошаговой `InsertOne`. Объясните разницу между `ordered` (стоп при ошибке) и `unordered` (продолжает, возвращает все ошибки).

## Теория

При загрузке сотен тысяч документов в HighLoad-системах (ETL, импорт миграций, восстановление бэкапов) режим `ordered: false` является стандартом де-факто:
1. **Максимальный параллелизм:** Драйвер и сервер могут отправлять операции одновременно по нескольким TCP-каналам и распределять нагрузку по ядрам процессора mongod.
2. **Устойчивость к ошибкам (Fault-Tolerance):** Если один документ из 100 000 нарушает уникальный индекс, `unordered bulk` не останавливает импорт! Все остальные 99 999 документов успешно запишутся, а в конце драйвер вернет агрегированный список всех отклоненных строк.

## Решение по шагам

1. Создайте генератор документов чанками по 10 000 записей.
2. Сконфигурируйте `options.BulkWrite().SetOrdered(false)`.
3. Отправьте батчи через `collection.BulkWrite`.
4. Замерьте суммарное время и выведите скорость записи.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 60*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("etl_import").Collection("fast_events")
	_ = coll.Drop(ctx)

	totalDocs := 100000
	chunkSize := 10000
	totalChunks := totalDocs / chunkSize

	fmt.Printf("Старт массового импорта %d документов батчами по %d (ordered: false)...\n", totalDocs, chunkSize)
	start := time.Now()

	insertedCount := int64(0)
	for c := 0; c < totalChunks; c++ {
		models := make([]mongo.WriteModel, chunkSize)
		baseIdx := c * chunkSize

		for i := 0; i < chunkSize; i++ {
			globalIdx := baseIdx + i
			doc := bson.M{
				"_id":   globalIdx + 1,
				"uuid":  fmt.Sprintf("usr-%06d", globalIdx),
				"score": globalIdx * 10,
			}
			models[i] = mongo.NewInsertOneModel().SetDocument(doc)
		}

		opts := options.BulkWrite().SetOrdered(false)
		res, err := coll.BulkWrite(ctx, models, opts)
		if err != nil {
			panic(err)
		}
		insertedCount += res.InsertedCount
	}

	dur := time.Since(start)
	rate := float64(insertedCount) / dur.Seconds()

	fmt.Println("Импорт успешно завершен:")
	fmt.Printf("  Всего записано: %d документов\n", insertedCount)
	fmt.Printf("  Общее время:    %v\n", dur)
	fmt.Printf("  Скорость:       %.0f док/сек\n", rate)
}
```

## Под капотом

Драйвер Go автоматически пакует модели в бинарные кадры протокола OP_MSG. Поскольку размер батча ограничен 48 МБ, чанки по 10 000 небольших документов идеально укладываются в один сетевой буфер без фрагментации.

## Подводные камни

Отправка всех 100 000 моделей в одном срезе `make([]mongo.WriteModel, 100000)` аллоцирует свыше 250 МБ в оперативной памяти процесса Go. Нарезка на чанки по 5 000 – 10 000 элементов позволяет удерживать потребление памяти стабильным и плоским.

## На собеседовании

**Вопрос:** Что вернет err при вызове BulkWrite(ordered: false), если из 10 000 документов 5 документов нарушили уникальный индекс?
**Ответ:** Вызов вернет ошибку типа `mongo.BulkWriteException`. При этом метод не прервался на первом дубликате: все остальные 9 995 документов успешно записаны в базу! Внутри ошибки `bwe.WriteErrors` будет содержаться срез из ровно 5 ошибок с указанием точных индексов документов в исходном массиве.
