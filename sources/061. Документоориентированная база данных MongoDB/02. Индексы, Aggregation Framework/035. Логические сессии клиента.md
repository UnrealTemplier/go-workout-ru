# Логические сессии клиента и причинная согласованность (Causal Consistency)

## Условие

Создайте сессию с помощью метода `client.StartSession()`. Напишите код, который выполняет несколько последовательных операций в рамках одной сессии, передавая `mongo.SessionContext` во все вызовы методов коллекции, чтобы гарантировать логическую связь запросов и контролировать общий таймаут выполнения.

### Исходная формулировка

**Изоляция операций через сессии (Sessions)**: Создайте сессию с помощью метода `client.StartSession()`. Напишите код, который выполняет несколько последовательных операций в рамках одной сессии, передавая `mongo.SessionContext` во все вызовы методов коллекции, чтобы гарантировать логическую связь запросов и контролировать общий таймаут выполнения.

## Теория

Клиентские сессии (`mongo.Session`) появились в MongoDB 3.6 и лежат в основе как транзакций, так и причинной согласованности (**Causal Consistency**).

### Что дает клиентская сессия:
1. **Логическая связь запросов:** Все операции в рамках одной сессии получают общий `lsid` (Logical Session ID).
2. **Read-Your-Own-Writes:** В кластерах с репликацией чтение с вторичных реплик (`Secondary`) может отставать из-за лага репликации. При включенной `Causal Consistency` сессия отслеживает векторное логическое время кластера (`ClusterTime`, `OperationTime`). Чтение на Secondary гарантированно ждет, пока реплика не догонит момент записи, сделанной этой же сессией!
3. **Единый таймаут и отмена:** `sessionContext` связывает Go-контекст и сессию, позволяя прервать все операции сессии при отмене контекста.

## Решение по шагам

1. Создайте сессию через `client.StartSession(opts)`.
2. Включите опцию причинной согласованности `SetCausalConsistency(true)`.
3. Оберните контекст с помощью `mongo.NewSessionContext(ctx, session)`.
4. Выполните запись и немедленное чтение в рамках одного сессионного контекста.
5. Завершите сессию вызовом `defer session.EndSession(ctx)`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
	"go.mongodb.org/mongo-driver/mongo/readconcern"
	"go.mongodb.org/mongo-driver/mongo/readpref"
	"go.mongodb.org/mongo-driver/mongo/writeconcern"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017/?replicaSet=rs0"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	// 1. Инициализация сессии с причинной согласованностью
	sessionOpts := options.Session().
		SetCausalConsistency(true).
		SetDefaultReadConcern(readconcern.Majority()).
		SetDefaultWriteConcern(writeconcern.Majority())

	session, err := client.StartSession(sessionOpts)
	if err != nil {
		panic(err)
	}
	defer session.EndSession(ctx)

	// Создаем SessionContext
	sessionCtx := mongo.NewSessionContext(ctx, session)

	coll := client.Database("social").Collection("posts")
	_ = coll.Drop(sessionCtx)

	// 2. Запись в рамках сессии
	post := bson.M{
		"author":    "tech_blogger",
		"content":   "Causal consistency guarantees Read-Your-Own-Writes!",
		"posted_at": time.Now().UTC(),
	}
	res, err := coll.InsertOne(sessionCtx, post)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Пост опубликован в сессии: %v\n", res.InsertedID)

	// 3. Немедленное чтение с реплики (SecondaryPreferred)
	// Благодаря Causal Consistency мы гарантированно прочитаем свой же пост
	findOpts := options.FindOne().SetReadPreference(readpref.SecondaryPreferred())
	var readPost bson.M
	err = coll.FindOne(sessionCtx, bson.M{"_id": res.InsertedID}, findOpts).Decode(&readPost)
	if err != nil {
		panic(err)
	}

	fmt.Println("Успешное чтение с реплики с гарантией причинной согласованности:")
	fmt.Printf("Контент: %v\n", readPost["content"])
	fmt.Printf("OperationTime сессии: %v\n", session.GetOperationTime())
}
```

ℹ️ Использование сессии с Causal Consistency для гарантии Read-Your-Own-Writes на репликах

```bash
# Контент: Causal consistency guarantees Read-Your-Own-Writes!

```

## Под капотом

Драйвер передает с каждым запросом маркер `operationTime` (Lamport timestamp кластера). Когда запрос на чтение поступает на вторичную ноду (Secondary), реплика сравнивает свой локально примененный `appliedOpTime` с переданным `operationTime`. Если реплика отстает, она приостанавливает ответ клиенту, догоняет oplog до указанной временной метки и только затем возвращает консистентный результат.

## Подводные камни

Вызов `client.StartSession()` без `defer session.EndSession(ctx)` вызывает утечку сессий на сервере MongoDB. Сервер хранит метаданные активных сессий в коллекции `config.system.sessions`, и неутилизированные сессии создают избыточную нагрузку на координатор.

## На собеседовании

**Вопрос:** Что такое Read-Your-Own-Writes и Monotonic Reads в распределенных БД?
**Ответ:** **Read-Your-Own-Writes** гарантирует, что если клиент выполнил запись, его последующие запросы на чтение всегда увидят эту запись (исключает эффект, когда пользователь создал комментарий, обновил страницу и не видит его из-за лага репликации). **Monotonic Reads** гарантирует, что если клиент однажды прочитал определенное состояние данных, он никогда в последующих запросах не увидит более старое состояние данных (исключает скачки во времени назад при опросе разных реплик).
