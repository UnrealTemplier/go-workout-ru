# Сложный пайплайн: $match, $group, $lookup, $unwind и Predicate Pushdown

## Условие

Постройте pipeline для аналитики: `$match` (фильтр по дате) → `$group` (агрегация по `user_id` с `$sum`) → `$lookup` (join с коллекцией `users`) → `$unwind` + `$project`. Объясните порядок stages и почему `$match` должен быть как можно раньше (predicate pushdown).

### Исходная формулировка

**Aggregation Pipeline.**: Постройте pipeline для аналитики: `$match` (фильтр по дате) → `$group` (агрегация по `user_id` с `$sum`) → `$lookup` (join с коллекцией `users`) → `$unwind` + `$project`. Объясните порядок stages и почему `$match` должен быть как можно раньше (predicate pushdown).

## Теория

Эффективность конвейера агрегации напрямую зависит от порядка стадий:
1. **`$match` (Predicate Pushdown):** обязан идти **первым**. Это позволяет движку применить индексы коллекции, отфильтровать 99% ненужных строк на уровне диска и сократить объем данных для последующих стадий.
2. **`$group`:** сворачивает миллионы строк в компактные агрегированные группы.
3. **`$lookup`:** выполняет левое соединение (Left Outer Join) с другой коллекцией. Это самая тяжелая операция конвейера! Выполнять `$lookup` до `$group` — грубейшая ошибка, так как соединение будет выполняться для каждой сырой строки.
4. **`$unwind`:** разворачивает массив, полученный из `$lookup`, в отдельные плоские документы.
5. **`$project`:** формирует финальный DTO и удаляет промежуточные поля.

## Решение по шагам

1. Инициализируйте коллекцию `users` (профили) и `orders` (заказы).
2. Постройте оптимизированный pipeline: `$match` \(\to\) `$group` \(\to\) `$lookup` \(\to\) `$unwind` \(\to\) `$project`.
3. Выполните агрегацию и десериализуйте результат в аналитический отчет.
4. Выведите суммарную выручку по клиентам.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type CustomerSpendingReport struct {
	UserID     int64   `bson:"user_id"`
	TotalSpent float64 `bson:"total_spent"`
	OrderCount int     `bson:"order_count"`
	UserName   string  `bson:"user_name"`
	UserEmail  string  `bson:"user_email"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	db := client.Database("ecommerce_analytics")
	usersColl := db.Collection("users")
	ordersColl := db.Collection("orders")
	_ = usersColl.Drop(ctx)
	_ = ordersColl.Drop(ctx)

	// Заполняем пользователей
	_, _ = usersColl.InsertMany(ctx, []interface{}{
		bson.M{"user_id": int64(1), "name": "Алексей Иванов", "email": "alex@corp.ru"},
		bson.M{"user_id": int64(2), "name": "Мария Смирнова", "email": "maria@corp.ru"},
	})

	// Заполняем заказы
	startDate := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
	_, _ = ordersColl.InsertMany(ctx, []interface{}{
		bson.M{"user_id": int64(1), "amount": 15000.0, "created_at": startDate.Add(24 * time.Hour)},
		bson.M{"user_id": int64(1), "amount": 25000.0, "created_at": startDate.Add(48 * time.Hour)},
		bson.M{"user_id": int64(2), "amount": 8000.0, "created_at": startDate.Add(12 * time.Hour)},
		bson.M{"user_id": int64(2), "amount": 500.0, "created_at": startDate.Add(-100 * time.Hour)}, // Должен быть отфильтрован
	})

	// Оптимизированный Pipeline:
	// 1. $match (Predicate Pushdown)
	// 2. $group (сворачивание заказов до JOIN)
	// 3. $lookup (JOIN только для сгруппированных пользователей)
	// 4. $unwind
	// 5. $project
	pipeline := mongo.Pipeline{
		{{Key: "$match", Value: bson.D{
			{Key: "created_at", Value: bson.D{{Key: "$gte", Value: startDate}}},
		}}},
		{{Key: "$group", Value: bson.D{
			{Key: "_id", Value: "$user_id"},
			{Key: "totalSpent", Value: bson.D{{Key: "$sum", Value: "$amount"}}},
			{Key: "orderCount", Value: bson.D{{Key: "$sum", Value: 1}}},
		}}},
		{{Key: "$lookup", Value: bson.D{
			{Key: "from", Value: "users"},
			{Key: "localField", Value: "_id"},
			{Key: "foreignField", Value: "user_id"},
			{Key: "as", Value: "user_info"},
		}}},
		{{Key: "$unwind", Value: "$user_info"}},
		{{Key: "$project", Value: bson.D{
			{Key: "_id", Value: 0},
			{Key: "user_id", Value: "$_id"},
			{Key: "total_spent", Value: "$totalSpent"},
			{Key: "order_count", Value: "$orderCount"},
			{Key: "user_name", Value: "$user_info.name"},
			{Key: "user_email", Value: "$user_info.email"},
		}}},
	}

	cur, err := ordersColl.Aggregate(ctx, pipeline)
	if err != nil {
		panic(err)
	}
	defer cur.Close(ctx)

	var reports []CustomerSpendingReport
	if err := cur.All(ctx, &reports); err != nil {
		panic(err)
	}

	fmt.Println("Аналитический отчет по клиентам:")
	for _, r := range reports {
		fmt.Printf("  Клиент: %-15s (%s) | Заказов: %d | Выручка: %.2f руб.\n",
			r.UserName, r.UserEmail, r.OrderCount, r.TotalSpent)
	}
}
```

## Под капотом

Оптимизатор запросов MongoDB пытается автоматически выполнить перестановку стадий: если `$match` стоит после `$project`, оптимизатор переносит `$match` перед проекцией (Predicate Pushdown). Однако перенести `$match` через `$group` оптимизатор не может без изменения логики, поэтому размещение фильтра в начале конвейера критически необходимо делать вручную.

## Подводные камни

Если в `$lookup` внешний документ не найден, стадия `$unwind` по умолчанию удаляет строку из потока (Inner Join). Если требуется поведение Left Outer Join (сохранять строку, даже если пользователя нет), необходимо использовать расширенный синтаксис: `bson.D{{"$unwind", bson.D{{"path", "$user_info"}, {"preserveNullAndEmptyArrays", true}}}}`.

## На собеседовании

**Вопрос:** Почему выполнение $lookup до $group считается архитектурной катастрофой в HighLoad аналитике?
**Ответ:** Если в коллекции 1 000 000 заказов от 10 000 клиентов: 1) При `$lookup` перед `$group` база выполнит 1 000 000 поисков в коллекции `users` и создаст гигантские промежуточные документы; 2) При `$group` перед `$lookup` 1 000 000 заказов сначала сворачиваются в 10 000 записей клиентов, и соединение выполняется ровно 10 000 раз, снижая нагрузку на CPU и память в 100 раз!
