# Уровни гарантий надежности: Write Concern, Read Concern и Linearizable

## Условие

Настройте `writeconcern.New(writeconcern.WMajority())` и `readpref.SecondaryPreferred()`. Сымитируйте split-brain (отключение secondary) и покажите, как majority-write гарантирует durability. Объясните `linearizable` read и его цену (latency).

### Исходная формулировка

**Read/Write Concern.**: Настройте `writeconcern.New(writeconcern.WMajority())` и `readpref.SecondaryPreferred()`. Сымитируйте split-brain (отключение secondary) и покажите, как majority-write гарантирует durability. Объясните `linearizable` read и его цену (latency).

## Теория

В распределенной архитектуре MongoDB гарантии надежности определяются связкой **Write Concern** и **Read Concern**:

### 1. Write Concern:
- **`w: 1`:** запись подтверждается только локальным Primary (риск потери данных при аварии мастера до репликации).
- **`w: "majority"`:** запись подтверждается большинством активных реплик. Данные гарантированно не откатятся при смене лидера (No Rollbacks).
- **`j: true` (Journaling):** подтверждение только после сброса WAL на физический диск (fsync).

### 2. Read Concern:
- **`local`:** возвращает самые свежие данные с ноды без гарантии фиксации кворумом.
- **`majority`:** возвращает только те данные, которые подтверждены большинством узлов (исключает чтение 'грязных' данных, которые могут откатиться).
- **`linearizable`:** перед возвратом ответа Primary связывается с кворумом нод и подтверждает, что он все еще является актуальным лидером (защита от чтения со старого мастера при сетевом разделении / Stale Master). Плата за Linearizable — дополнительный RTT на каждое чтение!

## Решение по шагам

1. Создайте клиент с `writeconcern.Majority()` и таймаутом `wtimeout: 5s`.
2. Настройте чтение с уровнем `readconcern.Majority()`.
3. Задайте `readpref.SecondaryPreferred()` для распределения нагрузки чтения.
4. Продемонстрируйте выполнение безопасной транзакции с гарантиями строгой сохранности данных.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
	"go.mongodb.org/mongo-driver/mongo/readconcern"
	"go.mongodb.org/mongo-driver/mongo/readpref"
	"go.mongodb.org/mongo-driver/mongo/writeconcern"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// 1. Строгая надежность записи: w=majority, j=true, wtimeout=5s
	wc := writeconcern.Majority()
	wc.Journal = boolPtr(true)
	wc.WTimeout = 5 * time.Second

	// 2. Чтение только зафиксированных кворумом данных (защита от отката)
	rc := readconcern.Majority()

	// 3. Предпочтение чтения с реплик
	rp := readpref.SecondaryPreferred()

	clientOpts := options.Client().
		ApplyURI("mongodb://localhost:27017/?replicaSet=rs0").
		SetWriteConcern(wc).
		SetReadConcern(rc).
		SetReadPreference(rp)

	client, err := mongo.Connect(ctx, clientOpts)
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("fintech").Collection("audit_trail")

	// Запись с максимальной гарантией надежности
	entry := bson.M{
		"event":     "PAYMENT_AUTHORIZED",
		"amount":    500000.0,
		"timestamp": time.Now().UTC(),
	}

	fmt.Println("Отправка записи с WriteConcern Majority + Journaling...")
	res, err := coll.InsertOne(ctx, entry)
	if err != nil {
		fmt.Printf("Ошибка записи кворума (возможен split-brain): %v\n", err)
		return
	}
	fmt.Printf("Запись подтверждена большинством реплик и сброшена в журнал WAL! ID: %v\n", res.InsertedID)

	// Чтение с ReadConcern Linearizable (только для Primary)
	linearizableOpts := options.FindOne().
		SetReadPreference(readpref.Primary()).
		SetReadConcern(readconcern.Linearizable())

	var verified bson.M
	err = coll.FindOne(ctx, bson.M{"_id": res.InsertedID}, linearizableOpts).Decode(&verified)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Линеаризуемое чтение успешно подтвердило консистентность: %v\n", verified["event"])
}

func boolPtr(b bool) *bool {
	return &b
}
```

## Под капотом

При `ReadConcern: Linearizable` Primary не может сразу ответить из своего локального кворумного кэша. Он выполняет внутренний No-Op Heartbeat к большинству реплик реплика-сета, подтверждая, что в кластере не произошли выборы нового мастера (что текущий узел не изолирован в сетевом меньшинстве).

## Подводные камни

ReadConcern `linearizable` поддерживается строго для `readpref.Primary()` и только для операций `FindOne` / `Find`. Попытка использовать `linearizable` с чтением на `Secondary` вызовет ошибку MongoDB `readConcern linearizable only supported on primary`.

## На собеседовании

**Вопрос:** Что произойдет при w=majority, если сеть между дата-центрами оборвется, и мастер окажется в меньшинстве (1 нода из 3)?
**Ответ:** Запрос записи заблокируется на время ожидания подтверждения от второй ноды. По истечении `wtimeoutMS` запрос вернет ошибку `WriteConcernError` (таймаут кворума). При этом на самом мастере запись применится локально. Но когда узел поймет, что потерял кворум, произойдут перевыборы, и при восстановлении связи этот документ будет сброшен в `system.rollback`.
