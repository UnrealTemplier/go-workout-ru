# Оптимизация стадии $match и взаимодействие с планировщиком

## Условие

Используйте `$match` для фильтрации документов в начале pipeline (должен быть первым для использования индексов).

### Исходная формулировка

**$match stage**: Используйте `$match` для фильтрации документов в начале pipeline (должен быть первым для использования индексов).

## Теория

В конвейере агрегации стадия `$match` — единственный этап, способный использовать стандартные индексы коллекции (`IXSCAN`).

### Ограничения использования индексов:
- Стадия `$match` использует индекс **только если она идет первой** (или объединяется оптимизатором с первыми этапами).
- Если перед `$match` стоит стадия `$project`, `$group` или `$unwind`, индекс коллекции использоваться **не может**! Сервер переходит к полному сканированию потока в оперативной памяти.

### Оптимизация Predicate Pushdown:
В современных версиях MongoDB оптимизатор пытается автоматически переместить `$match` ближе к началу конвейера, но для сложных вычисляемых выражений автоматическая оптимизация невозможна — разработчик обязан проектировать конвейер правильно вручную.

## Решение по шагам

1. Создайте коллекцию с миллионом фиктивных записей (или 1 000 для теста).
2. Создайте индекс по полю `status`.
3. Постройте конвейер, где `$match` стоит строго первым.
4. Проверьте план запроса и убедитесь в использовании индекса.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("test").Collection("match_opt")
	_ = coll.Drop(ctx)

	_, _ = coll.Indexes().CreateOne(ctx, mongo.IndexModel{
		Keys: bson.D{{Key: "status", Value: 1}},
	})

	_, _ = coll.InsertMany(ctx, []interface{}{
		bson.M{"status": "active", "val": 10},
		bson.M{"status": "pending", "val": 20},
		bson.M{"status": "active", "val": 30},
	})

	// Оптимальный Pipeline: $match первым
	pipeline := mongo.Pipeline{
		{{Key: "$match", Value: bson.D{{Key: "status", Value: "active"}}}},
		{{Key: "$group", Value: bson.D{
			{Key: "_id", Value: "$status"},
			{Key: "total", Value: bson.D{{Key: "$sum", Value: "$val"}}},
		}}},
	}

	cur, err := coll.Aggregate(ctx, pipeline)
	if err != nil {
		panic(err)
	}
	defer cur.Close(ctx)

	var res []bson.M
	_ = cur.All(ctx, &res)
	fmt.Printf("Результат агрегации с ранней фильтрацией: %+v\n", res)
}
```

ℹ️ Размещение $match на первой стадии для гарантированного задействования индексов

**`Терминал`**

```bash
go run main.go
# Результат агрегации с ранней фильтрацией: [map[_id:active total:40]]
```

## Под капотом

Когда `$match` стоит первым, MongoDB транслирует всю начальную часть конвейера в стандартную команду `find` движка WiredTiger, используя B-дерево индекса для быстрого сканирования.

## Подводные камни

Использование операторов JavaScript `$where` внутри `$match` полностью отключает использование индексов и заставляет движок выполнять V8-интерпретацию на каждый документ коллекции.

## На собеседовании

**Вопрос:** Может ли $match использовать текстовые или геопространственные индексы в Aggregation Pipeline?
**Ответ:** Да, но текстовый поиск `$text` и геопространственный оператор `$geoNear` обязаны быть строго первой стадией конвейера агрегации.
