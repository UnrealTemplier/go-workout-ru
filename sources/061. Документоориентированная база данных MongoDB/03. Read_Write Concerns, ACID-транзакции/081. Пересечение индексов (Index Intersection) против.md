# Пересечение индексов (Index Intersection) против составных индексов

## Условие

Поймите, как MongoDB может использовать несколько индексов для одного запроса.

### Исходная формулировка

**Index intersection**: Поймите, как MongoDB может использовать несколько индексов для одного запроса.

## Теория

Когда запрос содержит фильтр по двум полям `{status: "A", type: "B"}`, а составного индекса нет, но есть два одиночных индекса `{status: 1}` и `{type: 1}`, MongoDB может применить **Index Intersection (Пересечение индексов)**.

### Механика Index Intersection:
1. Движок выполняет `IXSCAN` по индексу `status: 1` и получает список RecordID (указателей на документы).
2. Параллельно выполняет `IXSCAN` по индексу `type: 1` и получает второй список RecordID.
3. Применяет стадию `AND_SORTED` или `AND_HASH`, находя пересечение списков идентификаторов.
4. Выполняет `FETCH` только для документов, попавших в пересечение.

### Сравнение с Compound Index:
Составной индекс всегда в 2–5 раз быстрее Index Intersection, так как находит результат за 1 логарифмический проход без накладных расходов на операцию пересечения множеств в памяти.

## Решение по шагам

1. Создайте два независимых одиночных индекса по полям `status` и `role`.
2. Выполните запрос с обоими условиями.
3. Проанализируйте `explain` и найдите стадию `AND_SORTED` / `AND_HASH`.
4. Сравните с поведением составного индекса.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	db := client.Database("perf")
	coll := db.Collection("intersection_demo")
	_ = coll.Drop(ctx)

	// Создаем два ОТДЕЛЬНЫХ одиночных индекса
	_, _ = coll.Indexes().CreateOne(ctx, mongo.IndexModel{Keys: bson.D{{Key: "role", Value: 1}}})
	_, _ = coll.Indexes().CreateOne(ctx, mongo.IndexModel{Keys: bson.D{{Key: "status", Value: 1}}})

	// Заполняем документы
	for i := 0; i < 100; i++ {
		_, _ = coll.InsertOne(ctx, bson.M{"role": "admin", "status": "active", "n": i})
	}

	explainCmd := bson.D{
		{Key: "explain", Value: bson.D{
			{Key: "find", Value: "intersection_demo"},
			{Key: "filter", Value: bson.D{
				{Key: "role", Value: "admin"},
				{Key: "status", Value: "active"},
			}},
		}},
		{Key: "verbosity", Value: "queryPlanner"},
	}

	var res bson.M
	_ = db.RunCommand(ctx, explainCmd).Decode(&res)

	planner := res["queryPlanner"].(bson.M)
	winningPlan := planner["winningPlan"].(bson.M)
	fmt.Printf("Выбранная стратегия выполнения: %v\n", winningPlan["stage"])
	fmt.Println("При наличии двух одиночных индексов движок может применить стадию пересечения AND_SORTED.")
}
```


## Под капотом

Для пересечения индексов MongoDB использует битовые маски или упорядоченные списки 64-битных RecordID. Если списки велики, операция пересечения нагружает кэш процессора L2/L3.

## Подводные камни

Index Intersection не может обслуживать сортировку `sort()`, если сортируемое поле не совпадает с направлением одного из индексов.

## На собеседовании

**Вопрос:** Стоит ли полагаться на Index Intersection вместо создания Compound Index?
**Ответ:** Нет. Index Intersection — это 'аварийная' оптимизация базы данных для произвольных фильтров, когда невозможно предсказать все комбинации полей. Для известных критических запросов составной индекс всегда предпочтительнее: он исключает фазу вычисления пересечения и требует меньше операций ввода-вывода.
