# Архитектура шардирования: Hashed vs Ranged Shard Key и Hot Shards

## Условие

Настройте sharded cluster (через `mongos`). Выберите shard key (hashed vs ranged) для коллекции `orders`. Покажите `sh.shardCollection()` и `sh.status()`. Объясните, почему неправильный shard key (монотонно возрастающий) создаёт «hot shard».

### Исходная формулировка

**Шардирование.**: Настройте sharded cluster (через `mongos`). Выберите shard key (hashed vs ranged) для коллекции `orders`. Покажите `sh.shardCollection()` и `sh.status()`. Объясните, почему неправильный shard key (монотонно возрастающий) создаёт «hot shard».

## Теория

Шардирование (Sharding) — метод горизонтального масштабирования MongoDB при терабайтных объемах данных:
- **`mongos`:** роутер запросов (stateless прокси).
- **Config Servers:** реплика-сет, хранящий метаданные чанков и маршрутизации.
- **Shards:** шарды (каждый шард — независимый Replica Set).

### Выбор Shard Key (Ключа шардирования):
1. **Ranged Shard Key (по диапазонам):**
   - Документы делятся по диапазонам значений `[min, max)`.
   - Идеально для диапазонных запросов (`$gt`, `$lt`).
   - **КАТАСТРОФА ПРИ МОНОТОННОМ КЛЮЧЕ (`_id` или `timestamp`):** Все новые записи имеют максимальное значение и идут **строго в один последний шард** (Hot Shard / Write Bottleneck), сводя масштабирование на нет!
2. **Hashed Shard Key (хешированный):**
   - Хеш `MD5(key)` равномерно псевдослучайно распределяет вставки по всем шардам кластера.
   - Идеально для равномерной записи в HighLoad, но диапазонные запросы требуют широковещательной рассылки (Scatter-Gather) по всем шардам.

## Решение по шагам

1. Подключитесь к роутеру `mongos`.
2. Выполните включение шардирования для базы через команду `enableSharding`.
3. Создайте хешированный индекс по полю `order_id`.
4. Шардируйте коллекцию через команду `shardCollection` с хешированным ключом.
5. Запросите статус кластера через `sh.status()`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
	defer cancel()

	// Подключение к роутеру mongos (порт 27017)
	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	adminDB := client.Database("admin")

	// 1. Включение шардирования для БД
	enableCmd := bson.D{{Key: "enableSharding", Value: "ecom_sharded"}}
	_ = adminDB.RunCommand(ctx, enableCmd).Err()

	coll := client.Database("ecom_sharded").Collection("orders")

	// 2. Создание Hashed-индекса для равномерного распределения записи
	_, _ = coll.Indexes().CreateOne(ctx, mongo.IndexModel{
		Keys: bson.D{{Key: "order_id", Value: "hashed"}},
	})

	// 3. Шардирование коллекции по Hashed Shard Key
	shardCmd := bson.D{
		{Key: "shardCollection", Value: "ecom_sharded.orders"},
		{Key: "key", Value: bson.D{{Key: "order_id", Value: "hashed"}}},
	}

	res := adminDB.RunCommand(ctx, shardCmd)
	if res.Err() != nil {
		fmt.Printf("Команда shardCollection (требуется активный mongos cluster): %v\n", res.Err())
	} else {
		fmt.Println("Коллекция orders успешно шардирована по Hashed ключу order_id.")
	}

	fmt.Println("\nАнализ архитектуры шардирования:")
	fmt.Println("  Hashed Shard Key исключает проблему 'Hot Shard': трафик вставок равномерно делится между всеми шардами кластера.")
}
```

ℹ️ Настройка Hashed Shard Key для исключения эффекта Hot Shard

## Под капотом

Роутер `mongos` кэширует карту чанков (Chunk Map) в памяти. При вставке документа mongos вычисляет `MD5(order_id)` и сразу направляет сетевой сокет к нужному шарду без опроса Config серверов (Single-Shard Targeted Write).

## Подводные камни

В шардированной коллекции уникальный индекс может быть создан ТОЛЬКО если префикс индекса содержит Shard Key! Нельзя сделать глобальный уникальный индекс по `email`, если шард-ключом является `user_id`.

## На собеседовании

**Вопрос:** Что такое Scatter-Gather запрос в шардированном кластере MongoDB и как его избежать?
**Ответ:** Если запрос на чтение не содержит поля Shard Key, роутер `mongos` не знает, на каком конкретно шарде лежат данные, и вынужден отправить параллельный запрос на **все шарды кластера** (Scatter), а затем объединить их ответы (Gather). Для исключения Scatter-Gather все частые OLTP запросы обязаны содержать Shard Key в фильтре (Targeted Query).
