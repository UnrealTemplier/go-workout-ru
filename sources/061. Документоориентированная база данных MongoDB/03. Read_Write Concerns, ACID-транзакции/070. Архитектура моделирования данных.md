# Архитектура моделирования данных: Embedding против Referencing

## Условие

Реализуйте два подхода для хранения комментариев к постам: embedding (массив внутри документа поста) vs referencing (отдельная коллекция). Покажите, когда embedding лучше (read-heavy, bounded growth), а когда referencing (unbounded growth, нужна пагинация).

### Исходная формулировка

**Schema Design для MongoDB.**: Реализуйте два подхода для хранения комментариев к постам: embedding (массив внутри документа поста) vs referencing (отдельная коллекция). Покажите, когда embedding лучше (read-heavy, bounded growth), а когда referencing (unbounded growth, нужна пагинация).

## Теория

Главная архитектурная дилемма NoSQL — **Встраивание (Embedding)** против **Ссылок (Referencing)**:

### 1. Embedding (Denormalization):
- Документ содержит массив вложенных комментариев.
- **Плюсы:** 1 атомарный сетевой запрос (1 RTT) поднимает пост и все комментарии; идеальная локальность данных в кэше.
- **Минусы:** Ограничение размера BSON-документа 16 МБ; фрагментация диска при постоянном разрастании массива.
- **Когда использовать:** Bounded growth (не более 50–100 элементов), данные читаются строго вместе с родительским документом.

### 2. Referencing (Normalization):
- Комментарии хранятся в отдельной коллекции `comments` с полем `post_id`.
- **Плюсы:** Неограниченный рост (Unbounded growth); поддержка пагинации комментариев, модерации и независимых индексов.
- **Минусы:** Требуется дополнительный запрос или `$lookup` JOIN.
- **Когда использовать:** Высокая активность, потенциально миллионы комментариев к посту.

## Решение по шагам

1. Реализуйте модель со встраиванием (Embedding) для bounded-сценария.
2. Реализуйте модель со ссылками (Referencing) для unbounded-сценария.
3. Продемонстрируйте выборку поста с пагинацией комментариев из отдельной коллекции.
4. Сравните сценарии применения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/bson/primitive"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

// Модель 1: Embedding (Bounded Growth: 5-10 тегов или авторов)
type EmbeddedPost struct {
	ID        primitive.ObjectID `bson:"_id,omitempty"`
	Title     string             `bson:"title"`
	Tags      []string           `bson:"tags"` // Встроенный массив
}

// Модель 2: Referencing (Unbounded Growth: тысячи комментариев)
type ReferencedPost struct {
	ID    primitive.ObjectID `bson:"_id,omitempty"`
	Title string             `bson:"title"`
}

type CommentDoc struct {
	ID        primitive.ObjectID `bson:"_id,omitempty"`
	PostID    primitive.ObjectID `bson:"post_id"` // Внешний ключ
	Author    string             `bson:"author"`
	Text      string             `bson:"text"`
	CreatedAt time.Time          `bson:"created_at"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	db := client.Database("blog_arch")
	postsColl := db.Collection("posts")
	commentsColl := db.Collection("comments")
	_ = postsColl.Drop(ctx)
	_ = commentsColl.Drop(ctx)

	// Создаем индекс для внешнего ключа
	_, _ = commentsColl.Indexes().CreateOne(ctx, mongo.IndexModel{
		Keys: bson.D{{Key: "post_id", Value: 1}, {Key: "created_at", Value: -1}},
	})

	// Создаем пост
	postRes, _ := postsColl.InsertOne(ctx, ReferencedPost{Title: "Архитектура MongoDB в HighLoad"})
	postID := postRes.InsertedID.(primitive.ObjectID)

	// Добавляем комментарии в отдельную коллекцию (Referencing)
	_, _ = commentsColl.InsertMany(ctx, []interface{}{
		CommentDoc{PostID: postID, Author: "User1", Text: "Отличная статья!", CreatedAt: time.Now().UTC()},
		CommentDoc{PostID: postID, Author: "User2", Text: "Ждем продолжения про шардинг.", CreatedAt: time.Now().UTC()},
	})

	// Пагинированная выборка комментариев по post_id
	findOpts := options.Find().
		SetSort(bson.D{{Key: "created_at", Value: -1}}).
		SetLimit(10)

	cur, _ := commentsColl.Find(ctx, bson.M{"post_id": postID}, findOpts)
	defer cur.Close(ctx)

	var comments []CommentDoc
	_ = cur.All(ctx, &comments)

	fmt.Printf("Пост ID: %s\n", postID.Hex())
	fmt.Printf("Пагинированные комментарии из коллекции comments (Referencing, %d шт.):\n", len(comments))
	for _, c := range comments {
		fmt.Printf("  - [%s]: %s\n", c.Author, c.Text)
	}
}
```

## Под капотом

При встраивании (Embedding) постоянные апдейты массива приводят к перемещению документа на диске (Document Relocation) движком WiredTiger, вызывая фрагментацию страниц памяти. Модель Referencing изолирует запись комментариев в отдельные неизменяемые документы, обеспечивая аппенд-онли производительность.

## Подводные камни

Попытка встроить миллионы элементов в один документ приведет к ошибке `document is larger than the maximum size 16777216` (превышение лимита 16 МБ).

## На собеседовании

**Вопрос:** Что такое Subset Pattern в моделировании схем MongoDB?
**Ответ:** Это гибрид между Embedding и Referencing: в родительский документ поста встраиваются только 5–10 самых свежих комментариев (Subset) для мгновенного первого рендеринга страницы за 1 запрос. Все остальные тысячи комментариев хранятся в отдельной коллекции с ссылками и подгружаются асинхронно по кнопке «Загрузить еще».
