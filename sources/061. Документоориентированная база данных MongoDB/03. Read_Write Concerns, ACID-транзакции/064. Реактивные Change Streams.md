# Реактивные Change Streams и восстановление после обрыва соединения

## Условие

Подпишитесь на Change Stream коллекции `orders`. При появлении нового заказа логируйте его ID и сумму. Обработайте возобновление потока при обрыве соединения, используя `resumeAfter`.

### Исходная формулировка

**Change Streams для реактивной обработки.**: Подпишитесь на Change Stream коллекции `orders`. При появлении нового заказа логируйте его ID и сумму. Обработайте возобновление потока при обрыве соединения, используя `resumeAfter`.

## Теория

Change Streams предоставляют надежный механизм подписки на события базы данных.

### Гарантия доставки при сетевых сбоях:
Каждое событие стрима имеет бинарный токен возобновления `_id` (`ResumeToken`).
Если сетевое соединение с MongoDB оборвалось, воркер на Go:
1. Перехватывает ошибку сети в цикле `stream.Next(ctx)`.
2. Создает новый вызов `coll.Watch(ctx, pipeline, opts)`.
3. Передает последний успешно обработанный токен в `options.ChangeStream().SetResumeAfter(lastToken)`.
4. Сервер продолжает стриминг строго со следующего события, исключая дубликаты и пропуски.

## Решение по шагам

1. Подключитесь к MongoDB (реплика-сет).
2. Запустите цикл прослушивания событий через `collection.Watch`.
3. Логируйте ID заказа и сумму для операций `insert`.
4. Сохраняйте `stream.ResumeToken()` после каждого подтверждения обработки.
5. Продемонстрируйте механизм переподключения с `SetResumeAfter`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type OrderEvent struct {
	OperationType string `bson:"operationType"`
	FullDocument  struct {
		OrderID string  `bson:"order_id"`
		Amount  float64 `bson:"amount"`
	} `bson:"fullDocument"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017/?replicaSet=rs0"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("store").Collection("orders")
	_ = coll.Drop(ctx)

	// Пайплайн фильтрации: только вставки заказов
	pipeline := mongo.Pipeline{
		{{Key: "$match", Value: bson.D{{Key: "operationType", Value: "insert"}}}},
	}

	opts := options.ChangeStream().SetFullDocument(options.UpdateLookup)
	stream, err := coll.Watch(ctx, pipeline, opts)
	if err != nil {
		fmt.Printf("Change Streams требуют Replica Set: %v\n", err)
		return
	}
	defer stream.Close(ctx)

	// Имитируем фоновые заказы
	go func() {
		time.Sleep(200 * time.Millisecond)
		_, _ = coll.InsertOne(context.Background(), bson.M{"order_id": "ORD-100", "amount": 4500.0})
		time.Sleep(200 * time.Millisecond)
		_, _ = coll.InsertOne(context.Background(), bson.M{"order_id": "ORD-101", "amount": 12900.0})
	}()

	var lastToken bson.Raw
	processed := 0

	fmt.Println("Слушатель заказов через Change Stream запущен:")
	for stream.Next(ctx) {
		var ev OrderEvent
		if err := stream.Decode(&ev); err != nil {
			panic(err)
		}

		lastToken = stream.ResumeToken()
		processed++
		fmt.Printf("  [Новый заказ] ID: %s | Сумма: %.2f руб.\n",
			ev.FullDocument.OrderID, ev.FullDocument.Amount)

		if processed == 2 {
			break
		}
	}

	fmt.Printf("\nПоследний сохраненный ResumeToken (%d байт).\n", len(lastToken))
	fmt.Println("При реконнекте возобновление произойдет через: options.ChangeStream().SetResumeAfter(lastToken)")
}
```

ℹ️ Реактивная обработка заказов и сохранение ResumeToken для отказоустойчивости

#   [Новый заказ] ID: ORD-101 | Сумма: 12900.00 руб.

## Под капотом

ResumeToken представляет собой BSON-документ, содержащий кластерную временную метку `clusterTime` (ts) и UUID документа из oplog. Сервер находит эту запись в `local.oplog.rs` за O(1) и начинает стриминг с последующей записи.

## Подводные камни

Если токен возобновления вышел за пределы окна хранения oplog (oplog window), сервер вернет фатальную ошибку `ChangeStreamHistoryLost`. В таких случаях требуется полная повторная инициализация консьюмера.

## На собеседовании

**Вопрос:** В чем разница между ResumeAfter и StartAfter в Change Streams?
**Ответ:** `ResumeAfter` используется для возобновления чтения обычных изменений после обрыва сети. `StartAfter` используется для открытия нового стрима после получения терминального события закрытия коллекции (`invalidate`, например при `dropCollection`), позволяя продолжить слушать коллекцию после ее пересоздания.
