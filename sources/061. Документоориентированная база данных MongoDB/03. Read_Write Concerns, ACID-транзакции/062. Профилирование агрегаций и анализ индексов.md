# Профилирование агрегаций и анализ индексов в Pipeline

## Условие

Используйте `explain()` для анализа плана выполнения. Поймите, какие stages используют индексы.

### Исходная формулировка

**Aggregation performance**: Используйте `explain()` для анализа плана выполнения. Поймите, какие stages используют индексы.

## Теория

Для анализа производительности конвейера агрегации вызов `coll.Aggregate()` можно профилировать через команду `explain`.

### Стадии конвейера и индексы:
1. **Стадии, использующие индексы:**
   - `$match` в самом начале конвейера: трансформируется в `IXSCAN`.
   - `$sort` сразу после `$match`: может использовать составной индекс без in-memory сортинга.
2. **Стадии, не использующие индексы:**
   - Любой `$match`, расположенный после стадий `$group`, `$unwind`, `$project` — работает исключительно в памяти над сгенерированными виртуальными документами.
   - `$group` без подходящего индекса строит in-memory хэш-таблицу.

## Решение по шагам

1. Создайте индекс по полям `category` и `price`.
2. Постройте конвейер агрегации.
3. Выполните инспекцию плана выполнения через команду `explain`.
4. Проверьте стадию `winningPlan` и убедитесь в использовании созданного индекса.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	db := client.Database("analytics_perf")
	coll := db.Collection("hardware")
	_ = coll.Drop(ctx)

	// 1. Создаем индекс
	_, _ = coll.Indexes().CreateOne(ctx, mongo.IndexModel{
		Keys: bson.D{
			{Key: "category", Value: 1},
			{Key: "price", Value: -1},
		},
		Options: options.Index().SetName("idx_cat_price"),
	})

	// Заполняем тестовые данные
	for i := 0; i < 20; i++ {
		_, _ = coll.InsertOne(ctx, bson.M{
			"category": "GPU",
			"price":    50000.0 + float64(i*1000),
		})
	}

	// 2. Команда explain для Aggregate
	explainCmd := bson.D{
		{Key: "explain", Value: bson.D{
			{Key: "aggregate", Value: "hardware"},
			{Key: "pipeline", Value: mongo.Pipeline{
				{{Key: "$match", Value: bson.D{{Key: "category", Value: "GPU"}}}},
				{{Key: "$sort", Value: bson.D{{Key: "price", Value: -1}}}},
				{{Key: "$limit", Value: 5}},
			}},
			{Key: "cursor", Value: bson.M{}},
		}},
		{Key: "verbosity", Value: "executionStats"},
	}

	var explainResult bson.M
	if err := db.RunCommand(ctx, explainCmd).Decode(&explainResult); err != nil {
		panic(err)
	}

	stages := explainResult["stages"].(bson.A)
	firstStage := stages[0].(bson.M)
	cursorStage := firstStage["$cursor"].(bson.M)
	queryPlanner := cursorStage["queryPlanner"].(bson.M)
	winningPlan := queryPlanner["winningPlan"].(bson.M)

	fmt.Println("Результаты анализа плана агрегации (Explain):")
	fmt.Printf("Базовая стадия $cursor: %v\n", cursorStage["executionStats"].(bson.M)["nReturned"])
	fmt.Printf("Winning Plan Stage:     %v\n", winningPlan["stage"])
	fmt.Printf("Использованный индекс:  %v\n", winningPlan["inputStage"].(bson.M)["indexName"])
}
```

ℹ️ Инспекция плана выполнения конвейера агрегации через команду explain

**`Терминал`**

```bash
go run main.go
# Результаты анализа плана агрегации (Explain):
# Базовая стадия $cursor: 5
# Winning Plan Stage:     FETCH
# Использованный индекс:  idx_cat_price
```

## Под капотом

Оптимизатор MongoDB объединяет начальные стадии конвейера (`$match`, `$sort`, `$limit`) в единую базовую операцию `$cursor`, которая транслируется в нативный Index Scan движка WiredTiger. Остальные стадии исполняются уже над потоком результатов курсора.

## Подводные камни

Если вставить стадию `$project` между `$match` и `$sort`, оптимизатор в старых версиях не сможет объединить их в единый Index Scan и выполнит дорогостоящую in-memory сортировку.

## На собеседовании

**Вопрос:** Что означает появление стадии SORTKEY_GENERATOR в плане explain для конвейера агрегации?
**Ответ:** Это означает, что для сортировки не удалось использовать индекс, и база данных вынуждена динамически генерировать ключи сортировки и выполнять сортировку в оперативной памяти (in-memory sort). Для устранения необходимо добавить составной индекс, включающий поля фильтра и поле сортировки.
