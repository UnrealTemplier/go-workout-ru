# Optimistic Concurrency Control (OCC) и разрешение конфликтов в Go

## Условие

Добавь в структуру `User` поле `Version int`. Напиши логику безопасного обновления: `UpdateOne` с фильтром `{"_id": id, "version": currentVersion}` и инкрементом версии `$inc: {"version": 1}`. Если `ModifiedCount == 0`, значит кто-то уже изменил документ — верни ошибку (это решает проблему lost updates без тяжелых транзакций).

### Исходная формулировка

**Optimistic Concurrency Control (OCC)**: Добавь в структуру `User` поле `Version int`. Напиши логику безопасного обновления: `UpdateOne` с фильтром `{"_id": id, "version": currentVersion}` и инкрементом версии `$inc: {"version": 1}`. Если `ModifiedCount == 0`, значит кто-то уже изменил документ — верни ошибку (это решает проблему lost updates без тяжелых транзакций).

## Теория

В распределенных сервисах параллельные запросы могут приводить к проблеме **Lost Update**:
1. Сервис А читает пользователя (версия 5).
2. Сервис Б читает того же пользователя (версия 5).
3. Сервис А обновляет баланс и пишет версию 6.
4. Сервис Б перезаписывает баланс своей версией 6, затирая изменения Сервиса А!

Паттерн OCC через фильтр `{_id: id, version: 5}` и операцию `$inc: {version: 1}` гарантирует, что операция Сервиса Б вернет `ModifiedCount == 0`, защищая базу от перезаписи.

## Решение по шагам

1. Создайте структуру `User` с полем `Version int`.
2. Напишите функцию `UpdateUserWithOCC` с возвратом ошибки при `ModifiedCount == 0`.
3. Смоделируйте успешное обновление версии.
4. Смоделируйте параллельную гонку и убедитесь в возврате ошибки конфликта.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

var ErrVersionConflict = errors.New("conflict: record modified by another process")

type UserAccountDoc struct {
	ID      string `bson:"_id"`
	Email   string `bson:"email"`
	Version int    `bson:"version"`
}

func UpdateEmailOCC(ctx context.Context, coll *mongo.Collection, id string, newEmail string, expectedVersion int) error {
	filter := bson.M{
		"_id":     id,
		"version": expectedVersion,
	}
	update := bson.M{
		"$set": bson.M{"email": newEmail},
		"$inc": bson.M{"version": 1},
	}

	res, err := coll.UpdateOne(ctx, filter, update)
	if err != nil {
		return err
	}
	if res.ModifiedCount == 0 {
		return ErrVersionConflict
	}
	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("auth").Collection("occ_users")
	_ = coll.Drop(ctx)

	_, _ = coll.InsertOne(ctx, UserAccountDoc{ID: "usr-42", Email: "old@mail.ru", Version: 1})

	// 1. Успешное обновление (версия 1 -> 2)
	err = UpdateEmailOCC(ctx, coll, "usr-42", "new@mail.ru", 1)
	if err != nil {
		panic(err)
	}
	fmt.Println("Первое обновление успешно применилось (версия стала 2).")

	// 2. Попытка обновления с устаревшей версией 1
	err = UpdateEmailOCC(ctx, coll, "usr-42", "stale@mail.ru", 1)
	if errors.Is(err, ErrVersionConflict) {
		fmt.Println("Второе обновление отклонено: обнаружена попытка перезаписи устаревшей версией (OCC сработал)!")
	}
}
```

## Под капотом

Движок WiredTiger выполняет проверку предиката в фильтре под атомарной блокировкой строки. Если предикат `version == 1` не удовлетворен, изменение не регистрируется в журнале WAL и `ModifiedCount` возвращается равным 0.

## Подводные камни

Если забыть `$inc: {"version": 1}`, версия останется прежней, и последующие обновления потеряют защиту от гонок.

## На собеседовании

**Вопрос:** Что делать, если при высокой конкуренции OCC постоянно возвращает ошибку конфликта?
**Ответ:** При высокой конкуренции (High Contention) чистый OCC с ретраями может вызвать перегрузку CPU (Live-lock). Решения: 1) Добавить экспоненциальную паузу со случайным джиттером (Exponential Backoff with Jitter); 2) Заменить OCC на атомарный `$inc` / `$push` на уровне БД без предварительного чтения; 3) Секционировать сущность (Distributed Counters / Sharded Buckets).
