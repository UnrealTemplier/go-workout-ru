# Change Streams в фоновых горутинах и реактивная обработка событий

## Условие

Напиши код, который подписывается на изменения коллекции (`collection.Watch(ctx, mongo.Pipeline{})`). Запусти его в горутине. В другой горутине вставь и измени пару документов. Убедись, что первая горутина в реальном времени распечатывает события (Insert/Update) как поток данных!

### Исходная формулировка

**Change Streams (Слушаем изменения)**: Напиши код, который подписывается на изменения коллекции (`collection.Watch(ctx, mongo.Pipeline{})`). Запусти его в горутине. В другой горутине вставь и измени пару документов. Убедись, что первая горутина в реальном времени распечатывает события (Insert/Update) как поток данных!

## Теория

Change Streams позволяют реализовать событийную архитектуру (Event-Driven Architecture) на базе Go-горутин и каналов.

### Реактивная модель:
- Фоновая горутина слушает сокет MongoDB через `stream.Next(ctx)`.
- Любая мутация в базе (вставка, обновление, удаление) транслируется ядром MongoDB в oplog и пушится в сокет клиенту.
- Горутина отправляет разобранные события в канал Go `chan Event` для асинхронной обработки воркерами.

## Решение по шагам

1. Подключитесь к реплика-сету.
2. Запустите горутину подписчика с `collection.Watch`.
3. В главной горутине выполните операции `InsertOne` и `UpdateOne`.
4. Убедитесь, что подписчик в реальном времени перехватил события `insert` и `update`.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type EventNotification struct {
	OpType   string `bson:"operationType"`
	DocKey   bson.M `bson:"documentKey"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017/?replicaSet=rs0"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("reactive").Collection("tasks")
	_ = coll.Drop(ctx)

	stream, err := coll.Watch(ctx, mongo.Pipeline{})
	if err != nil {
		fmt.Printf("Change Streams требуют Replica Set: %v\n", err)
		return
	}
	defer stream.Close(ctx)

	var wg sync.WaitGroup
	wg.Add(1)

	// 1. Горутина подписчика Change Stream
	go func() {
		defer wg.Done()
		fmt.Println("[Listener] Подписка активирована. Ожидание событий...")
		eventsReceived := 0
		for stream.Next(ctx) {
			var ev EventNotification
			if err := stream.Decode(&ev); err != nil {
				return
			}
			eventsReceived++
			fmt.Printf("[Listener] Перехвачено событие #%d: Операция=%-6s | DocID=%v\n",
				eventsReceived, ev.OpType, ev.DocKey["_id"])

			if eventsReceived == 2 {
				break
			}
		}
	}()

	time.Sleep(300 * time.Millisecond)

	// 2. Горутина продюсера изменений
	fmt.Println("[Producer] Выполнение InsertOne...")
	res, err := coll.InsertOne(ctx, bson.M{"task": "Deploy v2.0", "status": "pending"})
	if err != nil {
		panic(err)
	}

	time.Sleep(200 * time.Millisecond)
	fmt.Println("[Producer] Выполнение UpdateOne...")
	_, _ = coll.UpdateOne(ctx, bson.M{"_id": res.InsertedID}, bson.M{"$set": bson.M{"status": "in_progress"}})

	wg.Wait()
	fmt.Println("Реактивная обработка событий через горутины успешно завершена.")
}
```

## Под капотом

Потоковый курсор использует опцию `awaitData: true` протокола wiremessage. Сервер не возвращает пустые пакеты, а блокирует ответ в TCP сокете до момента появления следующей записи в oplog (или до истечения maxAwaitTimeMS).

## Подводные камни

Если контекст `ctx` отменен, метод `stream.Next(ctx)` возвращает `false`, а `stream.Err()` содержит `context.Canceled`. Не забывайте корректно завершать горутину при получении сигнала остановки сервиса.

## На собеседовании

**Вопрос:** Можно ли слушать Change Streams на уровне всей базы данных или всего кластера MongoDB, а не одной коллекции?
**Ответ:** Да! `db.Watch(ctx, pipeline)` слушает все коллекции базы данных, а `client.Watch(ctx, pipeline)` слушает абсолютно все изменения во всех базах данных всего кластера (Cluster-Wide Change Stream), что идеально для построения централизованных CDC-пайплайнов данных в Kafka.
