# Полиглотная архитектура E-Commerce: MongoDB + Redis + Search

## Условие

### Исходная формулировка

Features:
* Search latency < 50ms при 1000 RPS
* Real-time inventory updates
* Personalized recommendations на основе поведения
* Faceted search по множеству атрибутов
* Geo-search для nearby stores
* A/B testing через feature flags

## Теория

В интернет-магазинах масштаба Ozon или Wildberries каталог товаров хранится в MongoDB благодаря ее способности гибко хранить миллионы разнородных товаров (у шин — диаметр и сезонность, у смартфонов — память и процессор).

### Архитектурная связка:
1. **MongoDB:** Master Catalog Store (гибкая BSON-схема, версионирование, админка).
2. **Redis:** L1 In-Memory Cache для горячих карточек товаров (TTL 5 мин, выдерживает 500k RPS).
3. **Change Streams CDC:** при изменении цены или остатка в MongoDB Change Stream публикует дельту в Kafka.
4. **Elasticsearch / Search Engine:** забирает дельту из Kafka и синхронизирует инвертированный поисковый индекс за <1 секунду.

## Решение по шагам

1. Создайте модель товара с динамическими свойствами в MongoDB.
2. Смоделируйте двухслойное чтение: Cache-Aside через Redis (в памяти) \(\to\) Fallback в MongoDB.
3. Продемонстрируйте инвалидацию кэша при обновлении документа.
4. Выведите метрики кэш-хитов.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type CatalogProduct struct {
	SKU        string         `bson:"_id"`
	Title      string         `bson:"title"`
	Price      float64        `bson:"price"`
	Attributes map[string]any `bson:"attributes"`
}

// Имитация L1 кэша Redis в оперативной памяти
type FastMemoryCache struct {
	mu    sync.RWMutex
	store map[string]CatalogProduct
}

func (c *FastMemoryCache) Get(sku string) (CatalogProduct, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	p, ok := c.store[sku]
	return p, ok
}

func (c *FastMemoryCache) Set(sku string, p CatalogProduct) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.store[sku] = p
}

func GetProductDetails(ctx context.Context, coll *mongo.Collection, cache *FastMemoryCache, sku string) (CatalogProduct, string, error) {
	// 1. Попытка чтения из L1 Cache (Redis)
	if prod, ok := cache.Get(sku); ok {
		return prod, "CACHE_HIT (L1 In-Memory)", nil
	}

	// 2. Cache Miss -> Чтение из MongoDB
	var prod CatalogProduct
	err := coll.FindOne(ctx, bson.M{"_id": sku}).Decode(&prod)
	if err != nil {
		return CatalogProduct{}, "", err
	}

	// 3. Сохранение в кэш
	cache.Set(sku, prod)
	return prod, "CACHE_MISS (MongoDB Master)", nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("store").Collection("catalog_products")
	_ = coll.Drop(ctx)

	// Сохраняем товар в MongoDB
	targetProduct := CatalogProduct{
		SKU:   "IPHONE-16-PRO",
		Title: "Apple iPhone 16 Pro 256GB",
		Price: 145000.0,
		Attributes: map[string]any{
			"color": "Titanium Black",
			"ram":   "8GB",
		},
	}
	_, _ = coll.InsertOne(ctx, targetProduct)

	cache := &FastMemoryCache{store: make(map[string]CatalogProduct)}

	// Запрос 1: Холодный старт
	p1, source1, _ := GetProductDetails(ctx, coll, cache, "IPHONE-16-PRO")
	fmt.Printf("Запрос 1: [%s] Товар: %s (Цена: %.2f руб.)\n", source1, p1.Title, p1.Price)

	// Запрос 2: Горячий кэш
	p2, source2, _ := GetProductDetails(ctx, coll, cache, "IPHONE-16-PRO")
	fmt.Printf("Запрос 2: [%s] Товар: %s (Цена: %.2f руб.)\n", source2, p2.Title, p2.Price)
}
```

ℹ️ Паттерн Cache-Aside: оперативный кэш Redis + Master каталог в MongoDB

## Под капотом

При обновлении цены товара в админке MongoDB Change Stream перехватывает событие и отправляет команду `DEL cache:product:IPHONE-16-PRO` в Redis, гарантируя инвалидацию кэша за доли миллисекунды.

## Подводные камни

При одновременном холодном старте под высокой нагрузкой (10 000 RPS на новый товар) возникает проблема Cache Stampede (Thundering Herd), когда тысячи горутин одновременно ломятся в MongoDB. Решается через `singleflight.Group`.

## На собеседовании

**Вопрос:** Как избежать лавинообразных запросов в MongoDB при инвалидации кэша (Cache Stampede / Dogpile effect)?
**Ответ:** Использовать пакет `golang.org/x/sync/singleflight`: он объединяет параллельные идентичные запросы от тысяч горутин в единый вызов к MongoDB, дожидается одного ответа и раздает его всем ожидающим горутинам, снижая нагрузку на MongoDB ровно в \(N\) раз.
