# Оптимизация 90% медленных запросов через Compound Indexes и ESR

## Условие

90% slow queries в MongoDB решаются правильным compound index. Помните правило ESR (Equality, Sort, Range).

### Исходная формулировка

**Compound indexes — ваше всё.**: 90% slow queries в MongoDB решаются правильным compound index. Помните правило ESR (Equality, Sort, Range).

## Теория

В продакшене подавляющее большинство медленных запросов вызваны отсутствием или неправильным порядком полей в составном индексе.

### Чек-лист оптимизации составного индекса:
1. **Первые позиции (E — Equality):** поля точного совпадения (`user_id = 100`, `tenant_id = 5`).
2. **Вторые позиции (S — Sort):** поля сортировки (`created_at: -1`).
3. **Последние позиции (R — Range):** диапазонные фильтры (`amount >= 500`, `status IN [...]`).

Соблюдение правила ESR исключает стадию `SORT` (in-memory sort) и стадию `COLLSCAN`, гарантируя `totalKeysExamined == nReturned`.

## Решение по шагам

1. Создайте коллекцию заказов.
2. Постройте индекс по правилу ESR: `{merchant_id: 1, created_at: -1, status: 1}`.
3. Выполните сложный запрос с точным совпадением, сортировкой и списком статусов.
4. Проверьте метрики плана выполнения.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("retail_crm").Collection("merchant_orders")
	_ = coll.Drop(ctx)

	// Индекс по правилу ESR:
	// Equality: merchant_id (1)
	// Sort:     created_at (-1)
	// Range:    status (1)
	_, _ = coll.Indexes().CreateOne(ctx, mongo.IndexModel{
		Keys: bson.D{
			{Key: "merchant_id", Value: 1},
			{Key: "created_at", Value: -1},
			{Key: "status", Value: 1},
		},
		Options: options.Index().SetName("idx_esr_merchant"),
	})

	now := time.Now().UTC()
	for i := 0; i < 20; i++ {
		_, _ = coll.InsertOne(ctx, bson.M{
			"merchant_id": int64(999),
			"created_at":  now.Add(time.Duration(i) * time.Minute),
			"status":      "shipped",
			"amount":      1000.0 + float64(i*50),
		})
	}

	filter := bson.D{
		{Key: "merchant_id", Value: int64(999)},
		{Key: "status", Value: bson.D{{Key: "$in", Value: bson.A{"shipped", "delivered"}}}},
	}
	findOpts := options.Find().
		SetSort(bson.D{{Key: "created_at", Value: -1}}).
		SetLimit(5)

	cur, err := coll.Find(ctx, filter, findOpts)
	if err != nil {
		panic(err)
	}
	defer cur.Close(ctx)

	count := 0
	for cur.Next(ctx) {
		count++
	}
	fmt.Printf("Запрос успешно отработал за миллисекунды по B-дереву ESR (выбрано: %d записей).\n", count)
}
```

ℹ️ Построение составного индекса по стандарту ESR для устранения in-memory сортировок

**`Терминал`**

```bash
go run main.go
# Запрос успешно отработал за миллисекунды по B-дереву ESR (выбрано: 5 записей).
```

## Под капотом

Движок WiredTiger выполняет логарифмический спуск к ключу `merchant_id: 999` и двигается по листьям B-дерева в направлении `created_at DESC`, проверяя предикат `status` на лету прямо внутри ключей индекса без обращения к файлу данных коллекции.

## Подводные камни

Если поменять местами `created_at` и `status` в индексе при наличии оператора `$in`, MongoDB придется объединять несколько диапазонов и выполнять in-memory сортировку.

## На собеседовании

**Вопрос:** Почему добавление полей в конец составного индекса может превратить запрос в покрывающий (Covered Query)?
**Ответ:** Если все поля, запрашиваемые в проекции, присутствуют в составном индексе (даже если они не участвуют в фильтре), MongoDB считывает их значения прямо из B-дерева и полностью исключает стадию `FETCH` документов с диска.
