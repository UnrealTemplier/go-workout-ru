# Моделирование схем от паттернов доступа (Access-Pattern Driven Design)

## Условие

В отличие от SQL, в MongoDB схема определяется паттернами доступа. Embed когда читаете вместе, reference когда читаете отдельно.

### Исходная формулировка

**Schema design first.**: В отличие от SQL, в MongoDB схема определяется паттернами доступа. Embed когда читаете вместе, reference когда читаете отдельно.

## Теория

В реляционных СУБД проектирование схемы начинается от нормализации сущностей (3NF) независимо от будущих запросов.
В MongoDB проектирование схемы строится строго **от сценариев чтения и записи (Access Patterns)**:

### Принципы Access-Pattern Driven Design:
1. **Данные, которые запрашиваются вместе, хранятся вместе (Embed):** Если на 95% запросов карточка товара отображается вместе с характеристиками и галереей миниатюр, они встраиваются в единый документ. Один запрос `FindOne` поднимает все данные без `JOIN` за 1 сетевой RTT.
2. **Данные, которые читаются отдельно или часто обновляются, выносятся (Reference):** Если отзывы к товару читаются на отдельной вкладке и их пишут тысячи людей, они выносятся в отдельную коллекцию `reviews`.
3. **Соотношение Read/Write:** Если сущность читается в 1000 раз чаще, чем пишется, допустима агрессивная денормализация и дублирование данных (например, хранение имени автора прямо внутри комментария).

## Решение по шагам

1. Спроектируйте профиль пользователя и его настройки приватности по паттерну Embedding.
2. Спроектируйте историю сессий по паттерну Referencing.
3. Реализуйте загрузку агрегата профиля за 1 обращение.
4. Продемонстрируйте пагинацию независимых сессий.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/bson/primitive"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

// Embedded: Настройки всегда нужны при загрузке профиля
type UserSettings struct {
	Theme        string `bson:"theme"`
	EmailAlerts  bool   `bson:"email_alerts"`
	LanguageCode string `bson:"lang"`
}

type UserProfileAggregate struct {
	ID       primitive.ObjectID `bson:"_id,omitempty"`
	Username string             `bson:"username"`
	Email    string             `bson:"email"`
	Settings UserSettings       `bson:"settings"` // Встроенный объект (1:1, читаются всегда вместе)
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("access_patterns").Collection("user_profiles")
	_ = coll.Drop(ctx)

	// Сохранение агрегата
	profile := UserProfileAggregate{
		Username: "gopher_ninja",
		Email:    "ninja@golang.org",
		Settings: UserSettings{
			Theme:        "dark",
			EmailAlerts:  true,
			LanguageCode: "ru",
		},
	}

	res, err := coll.InsertOne(ctx, profile)
	if err != nil {
		panic(err)
	}

	// Чтение полного агрегата за 1 RTT
	var loaded UserProfileAggregate
	err = coll.FindOne(ctx, bson.M{"_id": res.InsertedID}).Decode(&loaded)
	if err != nil {
		panic(err)
	}

	fmt.Println("Профиль успешно прочитан за 1 сетевой RTT:")
	fmt.Printf("Пользователь: %s | Тема оформления: %s | Язык: %s\n",
		loaded.Username, loaded.Settings.Theme, loaded.Settings.LanguageCode)
}
```

ℹ️ Моделирование данных на основе паттернов доступа (Access Patterns)

**`Терминал`**

```bash
go run main.go
# Профиль успешно прочитан за 1 сетевой RTT:
# Пользователь: gopher_ninja | Тема оформления: dark | Язык: ru
```

## Под капотом

За счет размещения настроек внутри единого документа WiredTiger хранит их в непрерывном блоке на диске, обеспечивая 100% попадание в CPU-кэш и нулевую фрагментацию.

## Подводные камни

Денормализация без контроля консистентности: если продублировать `username` в 100 000 комментариях, при смене ника пользователем придется обновлять 100 000 документов. Дублируйте только те поля, которые меняются крайне редко или являются неизменяемыми.

## На собеседовании

**Вопрос:** В чем фундаментальное отличие реляционного моделирования от документного?
**Ответ:** Реляционная модель нормализует данные ('как данные устроены сущностно'), оставляя сборку связей на этап выполнения запросов через `JOIN`. Документная модель организует данные вокруг приложения ('как приложение потребляет эти данные'), оптимизируя физическую раскладку байт на диске под конкретные критические запросы.
