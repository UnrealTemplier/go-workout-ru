# Архитектура Replica Set: 3 узла, выборы лидера (Raft-like) и Failover

## Условие

Поднимите 3-нодовый replica set в Docker. Изучите primary/secondary, read preference, failover.

### Исходная формулировка

**Replica sets**: Поднимите 3-нодовый replica set в Docker. Изучите primary/secondary, read preference, failover.

## Теория

Кластер MongoDB Replica Set состоит из нечетного числа узлов (обычно 3 ноды: 1 Primary + 2 Secondaries):
- **Протокол консенсуса:** модифицированный алгоритм на базе Raft.
- **Выборы (Elections):** если Primary не отвечает на heartbeat в течение `electionTimeoutMillis` (по умолчанию 10 секунд), Secondary с наиболее актуальным oplog инициирует выборы и становится новым Primary при наборе большинства голосов (\(3/2 + 1 = 2\)).
- **Автономный Failover:** происходит за 1–3 секунды без участия человека.

## Решение по шагам

1. Подготовьте конфигурацию Docker Compose для 3 нод (`mongo1`, `mongo2`, `mongo3`).
2. Инициализируйте реплика-сет через команду `rs.initiate()`.
3. Подключите Go-драйвер с указанием всех трех хостов.
4. Проверьте топологию и роли узлов через `client.Ping`.

## Код решения

**`docker-compose.yml`**

```yaml
version: '3.8'
services:
  mongo1:
    image: mongo:7.0
    command: ["--replSet", "rs0", "--bind_ip_all", "--port", "27017"]
    ports:
      - "27017:27017"
  mongo2:
    image: mongo:7.0
    command: ["--replSet", "rs0", "--bind_ip_all", "--port", "27017"]
    ports:
      - "27018:27017"
  mongo3:
    image: mongo:7.0
    command: ["--replSet", "rs0", "--bind_ip_all", "--port", "27017"]
    ports:
      - "27019:27017" 
```

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// Строка подключения с перечислением всех 3 узлов
	uri := "mongodb://localhost:27017,localhost:27018,localhost:27019/?replicaSet=rs0"
	clientOpts := options.Client().
		ApplyURI(uri).
		SetServerSelectionTimeout(3 * time.Second)

	client, err := mongo.Connect(ctx, clientOpts)
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	// Получаем статус реплика-сета
	res := client.Database("admin").RunCommand(ctx, bson.D{{Key: "replSetGetStatus", Value: 1}})
	var status bson.M
	if err := res.Decode(&status); err != nil {
		fmt.Printf("Кластер ожидает rs.initiate(): %v\n", err)
		return
	}

	fmt.Printf("Имя реплика-сета: %v\n", status["set"])
	members := status["members"].(bson.A)
	fmt.Printf("Всего участников кластера: %d\n", len(members))
	for _, m := range members {
		mem := m.(bson.M)
		fmt.Printf("  - Хост: %-18v | Состояние: %v\n", mem["name"], mem["stateStr"])
	}
}
```

## Под капотом

Драйвер Go слушает топологию через SDAM. Если `mongo1` отключается, драйвер фиксирует падение сокета, ожидает завершения выборов на оставшихся нодах и автоматически перенаправляет поток записи на новый `PRIMARY` без разрыва приложения.

## Подводные камни

Четное количество нод (например, 2 или 4) подвержено риску Split-Brain при разделении сети 50/50. Кластер всегда обязан состоять из нечетного числа голосующих узлов (Voting Members: 3, 5, 7) либо использовать легковесный арбитр (Arbiter).

## На собеседовании

**Вопрос:** Что такое Arbiter в MongoDB и почему его не рекомендуется использовать в Production BigTech?
**Ответ:** Арбитр — это легковесный процесс `mongod`, который не хранит данные и не реплицирует oplog, а только участвует в голосовании при выборах мастера. В HighLoad он опасен: арбитр не может стать источником данных при аварии, а при падении единственного secondary мастер не сможет набрать `writeConcern: majority`, блокируя запись всей системы.
