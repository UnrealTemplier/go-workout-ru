# Стратегия резервного копирования и автоматизированный Restore Test

## Условие

Backups тестируйте. Backup без restore test — это не backup. Регулярно тестируйте восстановление.

### Исходная формулировка

**Backups тестируйте.**: Backup без restore test — это не backup. Регулярно тестируйте восстановление.

## Теория

В промышленной эксплуатации действует аксиома SRE: **«Состояние бэкапов неизвестно, пока не протестировано их восстановление»**.
Резервные копии часто оказываются поврежденными (битые архивы, неполный oplog, изменившаяся схема).

### Инструменты бэкапа MongoDB:
1. **`mongodump` + `mongorestore`:** логический бэкап в BSON. Опция `--oplog` обязательна для получения консистентного слепка данных (Point-in-Time Snapshot) на работающей базе данных!
2. **Файловые снапшоты (EBS / LVM Snapshots):** мгновенные снимки томов диска с блокировкой `db.fsyncLock()`.

### Автоматизированный Restore Test в CI/CD:
Еженощный пайплайн поднимает временный контейнер MongoDB, восстанавливает вчерашний бэкап, запускает проверочный набор тестов (проверка целостности коллекций, подсчет контрольных сумм) и только после этого отправляет алерт об успешности резервной копии.

## Решение по шагам

1. Сформируйте команду логического бэкапа с опцией `--oplog`.
2. Напишите Go-скрипт верификации целостности восстановленной базы данных.
3. Проверьте контрольные суммы документов и статус системных индексов.
4. Выведите отчет о проверке целостности.

## Код решения

**`verify_backup.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func VerifyRestoredDatabase(ctx context.Context, client *mongo.Client, dbName string) error {
	db := client.Database(dbName)

	// 1. Получаем список восстановленных коллекций
	colls, err := db.ListCollectionNames(ctx, bson.M{})
	if err != nil {
		return fmt.Errorf("ошибка получения списка коллекций: %w", err)
	}
	if len(colls) == 0 {
		return fmt.Errorf("БЭКАП ПОВРЕЖДЕН: в восстановленной базе данных 0 коллекций!")
	}

	fmt.Printf("[Restore Check] Найдено %d восстановленных коллекций в БД %s\n", len(colls), dbName)

	// 2. Проверка целостности каждой коллекции (db.collection.validate)
	for _, cName := range colls {
		validateCmd := bson.D{{Key: "validate", Value: cName}}
		var valRes bson.M
		if err := db.RunCommand(ctx, validateCmd).Decode(&valRes); err != nil {
			return fmt.Errorf("ошибка валидации коллекции %s: %w", cName, err)
		}

		valid := valRes["valid"].(bool)
		if !valid {
			return fmt.Errorf("КРИТИЧЕСКАЯ ОШИБКА: коллекция %s повреждена! (%v)", cName, valRes["errors"])
		}
		fmt.Printf("  - Коллекция %-15s: Статус VALID (Записей: %v)\n", cName, valRes["nrecords"])
	}

	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	// Подготовка тестовой коллекции для проверки
	coll := client.Database("restore_test_db").Collection("users")
	_ = coll.Drop(ctx)
	_, _ = coll.InsertOne(ctx, bson.M{"user": "vitaliy", "verified": true})

	fmt.Println("Запуск автоматизированного теста восстановления резервной копии...")
	if err := VerifyRestoredDatabase(ctx, client, "restore_test_db"); err != nil {
		fmt.Printf("FAIL: %v\n", err)
	} else {
		fmt.Println("SUCCESS: Автоматический тест восстановления бэкапа успешно пройден на 100%!")
	}
}
```

## Под капотом

Системная команда `validate` выполняет низкоуровневое сканирование структур страниц WiredTiger, проверяет балансировку B-деревьев всех индексов и сверяет количество указателей в индексах с числом фактических записей в коллекции.

## Подводные камни

Запуск `mongodump` без флага `--oplog` на активной базе приводит к логически неконсистентному бэкапу: пока дампятся первые коллекции, последние успевают измениться, и данные будут рассинхронизированы.

## На собеседовании

**Вопрос:** Что такое RPO и RTO при проектировании Disaster Recovery для базы данных?
**Ответ:** **RPO (Recovery Point Objective)** — максимально допустимый объем потерянных данных во времени при аварии (например, RPO = 5 минут означает, что при падении дата-центра мы можем потерять не более последних 5 минут данных). **RTO (Recovery Time Objective)** — максимально допустимое время простоя системы на восстановление работоспособности (например, RTO = 30 минут означает, что сервис обязан полностью подняться из резервной копии не позднее чем через полчаса).
