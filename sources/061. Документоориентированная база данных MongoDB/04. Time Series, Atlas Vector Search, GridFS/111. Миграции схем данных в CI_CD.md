# Миграции схем данных в CI/CD: безопасный эволюционный деплой

## Условие

Schema migrations в CI. Используйте golang-migrate или goose для управления схемой. Миграции должны быть в том же PR, что и код.

### Исходная формулировка

**Schema migrations в CI.**: Используйте golang-migrate или goose для управления схемой. Миграции должны быть в том же PR, что и код.

## Теория

Хотя MongoDB не требует жесткого `ALTER TABLE`, в корпоративной разработке схемы эволюционируют:
- Добавление и удаление индексов.
- Обновление схем валидации (`collMod` с новым `$jsonSchema`).
- Фоновая миграция формата данных в документах.

### Принципы безопасных миграций:
1. **Код и миграция в одном Pull Request:** Миграция выполняется в CI/CD пайплайне перед развертыванием новой версии пода.
2. **Обратная совместимость (Expand and Contract Pattern):** Новая версия кода сначала учится читать и старый, и новый формат (Expand), и только после успешного обновления всех данных старый код удаляется (Contract).

## Решение по шагам

1. Создайте систему версионирования миграций на Go.
2. Реализуйте миграцию добавления индекса и обновления схемы валидации.
3. Зафиксируйте версию примененной миграции в служебной коллекции `schema_migrations`.
4. Проверьте идемпотентность повторного запуска мигратора.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type Migration struct {
	Version     int
	Description string
	Apply       func(ctx context.Context, db *mongo.Database) error
}

func ApplyMigrations(ctx context.Context, db *mongo.Database, migrations []Migration) error {
	coll := db.Collection("schema_migrations")

	for _, m := range migrations {
		// Проверяем, была ли миграция применена
		count, err := coll.CountDocuments(ctx, bson.M{"version": m.Version})
		if err != nil {
			return err
		}
		if count > 0 {
			continue // Миграция уже выполнена
		}

		fmt.Printf("[CI/CD Migration] Применение v%d: %s...\n", m.Version, m.Description)
		if err := m.Apply(ctx, db); err != nil {
			return fmt.Errorf("сбой миграции v%d: %w", m.Version, err)
		}

		// Фиксируем успешное применение
		_, err = coll.InsertOne(ctx, bson.M{
			"version":    m.Version,
			"desc":       m.Description,
			"applied_at": time.Now().UTC(),
		})
		if err != nil {
			return err
		}
		fmt.Printf("[CI/CD Migration] v%d успешно зафиксирована!\n", m.Version)
	}
	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	db := client.Database("production_app")

	migrations := []Migration{
		{
			Version:     1,
			Description: "Создание уникального индекса по email",
			Apply: func(ctx context.Context, db *mongo.Database) error {
				coll := db.Collection("users")
				_, err := coll.Indexes().CreateOne(ctx, mongo.IndexModel{
					Keys:    bson.D{{Key: "email", Value: 1}},
					Options: options.Index().SetUnique(true).SetName("uniq_user_email"),
				})
				return err
			},
		},
		{
			Version:     2,
			Description: "Добавление поля created_at и индекса для сортировки",
			Apply: func(ctx context.Context, db *mongo.Database) error {
				coll := db.Collection("users")
				_, err := coll.Indexes().CreateOne(ctx, mongo.IndexModel{
					Keys: bson.D{{Key: "created_at", Value: -1}},
				})
				return err
			},
		},
	}

	if err := ApplyMigrations(ctx, db, migrations); err != nil {
		panic(err)
	}
	fmt.Println("Все миграции схемы базы данных успешно согласованы с релизом сервиса.")
}
```

## Под капотом

Мигратор фиксирует транзакционный лог версий в служебной коллекции. За счет уникального индекса по `version` гарантируется, что параллельный запуск нескольких реплик сервиса в Kubernetes не приведет к одновременному выполнению одной и той же миграции.

## Подводные камни

Выполнение тяжелых обновлений данных миллиона документов (`UpdateMany`) внутри одной миграции может заблокировать прод на десятки минут. Массовые миграции данных обязаны выполняться фоновыми воркерами с нарезкой по чанкам.

## На собеседовании

**Вопрос:** Что такое Zero-Downtime Schema Migration в NoSQL?
**Ответ:** Это трехфазный процесс деплоя: 1) Фаза Expand: сервис деплоится с кодом, который поддерживает как старый, так и новый формат данных; 2) Фаза Migrate: фоновый воркер порциями обновляет документы в БД; 3) Фаза Contract: деплоится новая версия кода, из которой полностью удалена поддержка старого формата.
