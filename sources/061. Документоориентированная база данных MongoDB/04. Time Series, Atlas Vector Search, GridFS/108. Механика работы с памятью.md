### Исходная формулировка

**Блок 16 (Elasticsearch)**: — после ClickHouse, чтобы сравнить аналитические и поисковые движки. Знание `mmap` из Блока 6 поможет понять, как Lucene использует memory-mapped files.

## Теория

Поисковые движки (Elasticsearch, OpenSearch) и базы данных (MongoDB WiredTiger) активно используют системный вызов ядра Linux **`mmap` (Memory-Mapped Files)**:
- Вместо медленных вызовов `read()` и `write()` файл на диске отображается напрямую в виртуальное адресное пространство процесса.
- Чтение данных из файла превращается в прямое чтение указателей памяти в Go / C++ / Java.
- Управление физической оперативной памятью передается ядру Linux (Page Cache). Если странице не хватает RAM, ОС сама выгружает 'холодные' страницы на диск и подгружает нужные через Page Faults.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"os"
	"syscall"
)

func main() {
	// Создаем тестовый бинарный файл
	fileName := "lucene_segment_mock.bin"
	content := []byte("LUCENE_INVERTED_INDEX_DATA_BLOCK_2026")
	if err := os.WriteFile(fileName, content, 0644); err != nil {
		panic(err)
	}
	defer os.Remove(fileName)

	// 1. Открываем дескриптор файла
	file, err := os.Open(fileName)
	if err != nil {
		panic(err)
	}
	defer file.Close()

	stat, _ := file.Stat()
	size := stat.Size()

	// 2. Системный вызов mmap: отображаем файл напрямую в оперативную память процесса
	data, err := syscall.Mmap(int(file.Fd()), 0, int(size), syscall.PROT_READ, syscall.MAP_SHARED)
	if err != nil {
		panic(err)
	}
	defer func() {
		_ = syscall.Munmap(data)
	}()

	fmt.Println("Файл успешно отображен в память через системный вызов mmap:")
	fmt.Printf("  Размер отображения: %d байт\n", len(data))
	fmt.Printf("  Содержимое из RAM:  %s\n", string(data))
	fmt.Println("Чтение происходит со скоростью шины памяти без промежуточного копирования в буферы ядра!")
}
```

ℹ️ Прямое отображение файла в виртуальную память через системный вызов syscall.Mmap

## Под капотом

Apache Lucene в Elasticsearch использует класс `MMapDirectory`. Инвертированные индексы (.doc, .tim, .tip) отображаются в адресное пространство JVM через `mmap`. Это позволяет процессу Java обходить ограничения Garbage Collector на гигантские объемы кучи (Off-Heap Memory).

## Подводные камни

В Linux лимит `vm.max_map_count` по умолчанию равен 65530, из-за чего Elasticsearch падает при старте. В production его принудительно увеличивают до 262144 (`sysctl -w vm.max_map_count=262144`).

## На собеседовании

**Вопрос:** Почему Lucene и Elasticsearch рекомендуют выделять под JVM Heap ровно 50% оперативной памяти сервера, а оставшиеся 50% оставлять операционной системе?
**Ответ:** Потому что Lucene полагается на Memory-Mapped Files. Оставшиеся 50% RAM использует ядро Linux для файлового кэша (Page Cache). Если отдать всю память под Java Heap, операционная система будет постоянно сбрасывать файловые страницы на диск, что приведет к деградации производительности поиска в десятки раз.
