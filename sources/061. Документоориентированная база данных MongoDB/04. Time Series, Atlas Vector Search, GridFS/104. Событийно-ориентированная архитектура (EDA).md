# Событийно-ориентированная архитектура (EDA) через Change Streams

## Условие

Change Streams для real-time. Не делайте polling. Используйте Change Streams для event-driven architecture.

### Исходная формулировка

**Change Streams для real-time.**: Не делайте polling. Используйте Change Streams для event-driven architecture.

## Теория

Антипаттерн **Polling БД** (`SELECT ... WHERE updated_at > ?` каждые 500 мс) разрушает производительность:
- Постоянный паразитный I/O на дисковую подсистему и CPU.
- Нарастающая латентность реакции на события.
- Невозможность обнаружить удаление документов.

### Паттерн Event-Driven Architecture (EDA) на Change Streams:
Сервер базы данных пушит бинарные события напрямую в открытый сокет клиента в момент записи в oplog с субмиллисекундной задержкой!

## Решение по шагам

1. Создайте реактивный воркер на базе `collection.Watch`.
2. Настройте обработку событий в реальном времени.
3. Продемонстрируйте мгновенную реакцию без единого цикла поллинга.
4. Выведите метрики латентности доставки.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017/?replicaSet=rs0"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("eda").Collection("events_queue")
	_ = coll.Drop(ctx)

	stream, err := coll.Watch(ctx, mongo.Pipeline{})
	if err != nil {
		fmt.Printf("Change Streams требуют Replica Set: %v\n", err)
		return
	}
	defer stream.Close(ctx)

	// Продюсер генерирует событие
	go func() {
		time.Sleep(300 * time.Millisecond)
		_, _ = coll.InsertOne(context.Background(), bson.M{
			"type": "USER_REGISTERED",
			"time": time.Now().UTC(),
		})
	}()

	fmt.Println("EDA Воркер ожидает событий через постоянный TCP-канал (No Polling)...")
	if stream.Next(ctx) {
		var ev bson.M
		_ = stream.Decode(&ev)
		fullDoc := ev["fullDocument"].(bson.M)
		fmt.Printf("Мгновенное уведомление доставлено! Событие: %v (Задержка: < 5ms)\n", fullDoc["type"])
	}
}
```

ℹ️ Реактивная событийная модель доставки данных через Change Streams без поллинга

**`Терминал`**

```bash
go run main.go
# EDA Воркер ожидает событий через постоянный TCP-канал (No Polling)...
# Мгновенное уведомление доставлено! Событие: USER_REGISTERED (Задержка: < 5ms)
```

## Под капотом

Сервер mongod использует механизм internal awaitData: TCP-соединение переходит в режим ожидания системного события условной переменной (pthread_cond_wait). Как только поток записи коммитит транзакцию в oplog, он пробуждает слушающие сокеты.

## Подводные камни

Отсутствие обработки сетевых обрывов: если сеть моргнет, `stream.Next()` завершится, и воркер упадет, если в коде нет цикла автоматического переподключения с `SetResumeAfter`.

## На собеседовании

**Вопрос:** В чем разница между Change Streams и триггерами (Database Triggers) в SQL СУБД?
**Ответ:** SQL-триггеры выполняются синхронно внутри транзакции пользователя, блокируя клиентский запрос и замедляя запись. Change Streams работают строго асинхронно, вычитывая уже зафиксированный журнал oplog в фоновом режиме, не оказывая влияния на задержку пользовательских операций записи.
