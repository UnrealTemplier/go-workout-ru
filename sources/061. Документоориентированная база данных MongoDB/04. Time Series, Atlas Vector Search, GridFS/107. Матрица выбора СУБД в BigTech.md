# Матрица выбора СУБД в BigTech: Right Tool for the Job

## Условие

### Исходная формулировка

**Right tool for the job.**: Не пытайтесь использовать одну БД для всего. PostgreSQL для OLTP, ClickHouse для OLAP, Elasticsearch для поиска, MongoDB для гибкой схемы, Redis для кэша.

## Теория

В современной Enterprise-архитектуре 'серебряной пули' не существует. Каждая СУБД решает строго определенный класс задач:

| СУБД | Архитектура | Основное назначение | Сильные стороны | Слабые стороны |
| :--- | :--- | :--- | :--- | :--- |
| **PostgreSQL** | Строчное (Row-oriented) RDBMS | Финансы, биллинг, Master OLTP | Строгий ACID, реляционная целостность, foreign keys | Сложное шардирование на запись |
| **MongoDB** | Документное (Document BSON) | Каталоги товаров, профили, CMS | Гибкая схема, вложенные структуры, горизонтальный шардинг | Оверхед по памяти на BSON |
| **ClickHouse** | Колоночное (Column-oriented) | Аналитика, метрики, логи, OLAP | Сжатие 1:10, миллиарды строк/сек | Нет точечных быстрых апдейтов |
| **Elasticsearch** | Инвертированный индекс (Lucene) | Полнотекстовый поиск, фасеты | Морфология, нечеткий поиск, автодополнение | Огромное потребление RAM (JVM) |
| **Redis** | In-Memory Key-Value | Кэш, rate limiting, сессии | Субмиллисекундный отклик, 1M RPS | Данные ограничены объемом RAM |

## Решение по шагам

1. Спроектируйте микросервисную архитектуру, сочетающую несколько типов СУБД.
2. Продемонстрируйте диспетчеризацию запросов к нужной базе по типу нагрузки.
3. Обоснуйте выбор каждого хранилища.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

type StorageCategory string

const (
	StorePostgres StorageCategory = "PostgreSQL (Master OLTP / Финансы / Строгий ACID)"
	StoreMongo    StorageCategory = "MongoDB (Гибкие каталоги / Профили / Документы)"
	StoreClick    StorageCategory = "ClickHouse (Аналитика / Логи / Миллиарды событий)"
	StoreElastic  StorageCategory = "Elasticsearch (Полнотекстовый поиск / Опечатки / Морфология)"
	StoreRedis    StorageCategory = "Redis (L1 Кэш / Rate Limiter / Блокировки)"
)

func SelectOptimalDatabase(useCase string) StorageCategory {
	switch useCase {
	case "billing_transactions":
		return StorePostgres
	case "product_catalog_dynamic_attrs":
		return StoreMongo
	case "analytics_clicks_aggregation":
		return StoreClick
	case "fuzzy_text_search":
		return StoreElastic
	case "api_rate_limiting":
		return StoreRedis
	default:
		return StorePostgres
	}
}

func main() {
	cases := []string{
		"billing_transactions",
		"product_catalog_dynamic_attrs",
		"analytics_clicks_aggregation",
		"fuzzy_text_search",
		"api_rate_limiting",
	}

	fmt.Println("Архитектурная матрица выбора СУБД (Right Tool for the Job):")
	for _, c := range cases {
		fmt.Printf("  Сценарий: %-30s -> %s\n", c, SelectOptimalDatabase(c))
	}
}
```

## Под капотом

Полиглотное хранение объединяется с помощью Change Data Capture (CDC) и очередей сообщений (Kafka), которые реплицируют данные между специализированными СУБД в асинхронном режиме.

## Подводные камни

Попытка использовать MongoDB для аналитики по 100 миллиардам строк приведет к переполнению диска и OOM. Для аналитики создан ClickHouse.

## На собеседовании

**Вопрос:** Что такое Eventual Consistency в полиглотно-персистентных системах?
**Ответ:** Это модель согласованности, при которой запись подтверждается в основной мастер-БД (например, PostgreSQL), а репликация в специализированные СУБД (Elasticsearch, ClickHouse, кэши) происходит асинхронно через брокер сообщений. В течение сотен миллисекунд данные в поиске или аналитике могут отставать, но гарантированно сходятся к актуальному состоянию (Eventual Consistency).
