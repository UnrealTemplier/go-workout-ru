### Исходная формулировка

**Log analytics platform (self-hosted ELK):**

    * **Log ingestion:** Go-агенты собирают логи из контейнеров
    * **Buffer:** Kafka для reliable buffering
    * **Storage:** ClickHouse для efficient storage (columnar compression)

    * Query latency < 500ms на 30-дневном окне
    * Automatic log parsing (JSON, regex, grok patterns)
    * Real-time alerts через Kafka Streams
    * Retention policies (hot 7 days, warm 30 days, cold 1 year)
    * Multi-tenant изоляция

## Теория

В платформах мониторинга и сбора телеметрии (Datadog, Grafana Loki, ELK) роли распределяются строго по специализации СУБД:
- **ClickHouse:** хранит сырые структурированные логи (колоночное сжатие ZSTD 1:10, сканирование миллиардов строк в секунду).
- **MongoDB:** хранит метаданные системы:
  - Конфигурации дашбордов пользователей и алертов.
  - Политики хранения логов (Retention Policies: горячий кэш 7 дней, холодный архив 1 год).
  - Настройки парсеров (Grok-шаблоны, regex правила) и RBAC права доступа команд.

## Решение по шагам

1. Спроектируйте схему метаданных политик хранения (Retention Policy) в MongoDB.
2. Создайте модель конфигурации алертов для платформы мониторинга.
3. Реализуйте функцию регистрации нового дашборда и политик хранения.
4. Продемонстрируйте архитектурную роль MongoDB как мета-хранилища платформы.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type RetentionPolicy struct {
	TenantID     string `bson:"tenant_id"`
	HotDays      int    `bson:"hot_retention_days"`  // Дней в горячем хранилище
	ColdDays     int    `bson:"cold_retention_days"` // Дней в холодном архиве
	SamplingRate float64`bson:"sampling_rate"`       // Коэффициент сэмплирования
}

type DashboardConfig struct {
	ID        string    `bson:"_id"`
	TenantID  string    `bson:"tenant_id"`
	Name      string    `bson:"name"`
	Widgets   []bson.M  `bson:"widgets"`
	CreatedAt time.Time `bson:"created_at"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	db := client.Database("observability_platform")
	retentionColl := db.Collection("retention_policies")
	dashboardsColl := db.Collection("dashboards")

	_ = retentionColl.Drop(ctx)
	_ = dashboardsColl.Drop(ctx)

	// 1. Сохранение политики хранения логов для тенанта
	policy := RetentionPolicy{
		TenantID:     "tenant-fintech",
		HotDays:      14,
		ColdDays:     365,
		SamplingRate: 1.0, // 100% аудит
	}
	_, err = retentionColl.InsertOne(ctx, policy)
	if err != nil {
		panic(err)
	}

	// 2. Сохранение конфигурации дашборда с произвольными виджетами
	dashboard := DashboardConfig{
		ID:       "dash-app-errors",
		TenantID: "tenant-fintech",
		Name:     "HTTP 5xx & Latency Dashboard",
		Widgets: []bson.M{
			{"type": "timeseries", "metric": "http_requests_total", "w": 6, "h": 4},
			{"type": "logs_table", "query": "status >= 500", "w": 12, "h": 6},
		},
		CreatedAt: time.Now().UTC(),
	}
	_, err = dashboardsColl.InsertOne(ctx, dashboard)
	if err != nil {
		panic(err)
	}

	fmt.Println("Платформа телеметрии (Метаданные в MongoDB успешно зарегистрированы):")
	fmt.Printf("  1. Политика хранения: %d дней горячих логов, %d дней архива\n", policy.HotDays, policy.ColdDays)
	fmt.Printf("  2. Дашборд: %s (%d виджетов)\n", dashboard.Name, len(dashboard.Widgets))
}
```

ℹ️ Хранение метаданных платформы мониторинга (Retention Policies и Dashboards) в MongoDB

## Под капотом

Документная модель MongoDB идеально подходит для хранения UI-дашбордов и виджетов благодаря свободной схеме: каждый виджет может иметь произвольный набор настроек (координаты сетки, фильтры, цвета, формулы метрик) без необходимости миграции колонок в SQL.

## Подводные камни

Попытка сохранять сами миллиарды сырых строк логов в MongoDB приведет к колоссальным расходам диска и памяти из-за BSON-оверхеда. Для сырых логов и метрик используется ClickHouse, а MongoDB хранит строго метаданные.

## На собеседовании

**Вопрос:** Почему для хранения конфигураций дашбордов и политик MongoDB лучше реляционной СУБД?
**Ответ:** Дашборды мониторинга имеют сложную иерархическую структуру (сетки, вкладки, списки виджетов, запросы к разным бэкендам). В реляционной БД потребовалось бы 5 таблиц с каскадными внешними ключами. В MongoDB вся конфигурация дашборда сохраняется и считывается за 1 атомарный запрос к единому документу.
