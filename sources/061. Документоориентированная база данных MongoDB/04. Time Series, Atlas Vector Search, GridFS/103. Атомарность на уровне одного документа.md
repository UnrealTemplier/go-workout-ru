# Атомарность на уровне одного документа vs Распределенные транзакции

## Условие

Transactions только когда нужны. MongoDB transactions имеют overhead. Для большинства use cases достаточно single-document atomicity.

### Исходная формулировка

**Transactions только когда нужны.**: MongoDB transactions имеют overhead. Для большинства use cases достаточно single-document atomicity.

## Теория

В MongoDB любая операция мутации над **одним документом** (даже если документ содержит 100 вложенных объектов и массивов) является **строго атомарной и изолированной из коробки**!

### Когда транзакции НЕ нужны:
- Добавление элемента в массив и изменение счетчика в одном документе (`$push` + `$inc` в `UpdateOne`).
- Резервация товара внутри документа заказа.
- Изменение профиля и настроек пользователя.

### Когда транзакции РЕАЛЬНО нужны:
- Перевод баланса между двумя разными аккаунтами в банковской системе.
- Списание товара со склада в коллекции `inventory` с одновременным созданием чека в коллекции `receipts`.

Злоупотребление транзакциями снижает пропускную способность кластера в 5–10 раз!

## Решение по шагам

1. Продемонстрируйте сложную атомарную мутацию агрегата без транзакций через `FindOneAndUpdate`.
2. Обновите статус, увеличьте счетчик и добавьте аудит-лог в одном вызове.
3. Убедитесь в неделимости операции.

## Код решения

**`main.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"

	"go.mongodb.org/mongo-driver/bson"
	"go.mongodb.org/mongo-driver/mongo"
	"go.mongodb.org/mongo-driver/mongo/options"
)

type DocumentAggregate struct {
	ID        string   `bson:"_id"`
	Status    string   `bson:"status"`
	Version   int      `bson:"version"`
	AuditLogs []string `bson:"audit_logs"`
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	client, err := mongo.Connect(ctx, options.Client().ApplyURI("mongodb://localhost:27017"))
	if err != nil {
		panic(err)
	}
	defer client.Disconnect(ctx)

	coll := client.Database("single_doc").Collection("orders")
	_ = coll.Drop(ctx)

	// Инициализация
	_, _ = coll.InsertOne(ctx, DocumentAggregate{
		ID:        "ORD-555",
		Status:    "pending",
		Version:   1,
		AuditLogs: []string{"создан клиентом"},
	})

	// Комплексная атомарная мутация нескольких полей БЕЗ транзакции
	filter := bson.M{"_id": "ORD-555", "status": "pending"}
	update := bson.M{
		"$set":  bson.M{"status": "processing"},
		"$inc":  bson.M{"version": 1},
		"$push": bson.M{"audit_logs": "передан на склад сборки"},
	}

	opts := options.FindOneAndUpdate().SetReturnDocument(options.After)
	var updated DocumentAggregate
	err = coll.FindOneAndUpdate(ctx, filter, update, opts).Decode(&updated)
	if err != nil {
		panic(err)
	}

	fmt.Println("Атомарная модификация одного документа завершена за 1 сетевую итерацию:")
	fmt.Printf("  Новый статус: %s | Версия: %d | Логов: %d\n",
		updated.Status, updated.Version, len(updated.AuditLogs))
}
```

ℹ️ Однодокументная атомарность исключает необходимость в тяжелых ACID-транзакциях

**`Терминал`**

```bash
go run main.go
# Атомарная модификация одного документа завершена за 1 сетевую итерацию:
#   Новый статус: processing | Версия: 2 | Логов: 2
```

## Под капотом

В WiredTiger модификация одного документа выполняется под внутренней защелкой (latch) страницы памяти документа. Это исключает сетевые фазы двухфазного коммита (2PC) и не создает записей в таблице глобальных сессий.

## Подводные камни

Попытка эмулировать реляционную нормализацию (разбиение одной сущности на 5 таблиц) заставляет разработчика использовать транзакции там, где в NoSQL следовало спроектировать единый вложенный документ.

## На собеседовании

**Вопрос:** В чем главный оверхед распределенных транзакций в MongoDB по сравнению с single-document updates?
**Ответ:** 1) Удержание snapshot-версий страниц памяти в кэше WiredTiger (препятствует эвикшну и сбросу контрольных точек); 2) Риск дедлоков и необходимость цикла ретраев в коде; 3) Координация коммита через двухфазную фиксацию (2PC) и консенсус большинства нод реплика-сета.
