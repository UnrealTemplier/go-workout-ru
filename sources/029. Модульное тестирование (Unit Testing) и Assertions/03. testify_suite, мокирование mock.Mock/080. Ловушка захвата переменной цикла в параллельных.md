# Ловушка захвата переменной цикла в параллельных тестах: shadowing tc := tc

## Условие

**Каверзная ловушка параллельных табличных тестов**: Используй таблицу из упр. 403 и вызови `t.Parallel()` внутри `t.Run`. Если у тебя Go ниже 1.22, тесты могут упасть или проверить только последний кейс (из-за захвата переменной цикла). Осознай, зачем внутри цикла раньше писали `tc := tc` (shadowing).

## Теория

Классическая ловушка параллелизма в Go (Loop Variable Shadowing):
В Go \(\le\) 1.21:
```go
for _, tc := range tests {
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()
        // БАГ: все горутины прочитают последний tc, когда цикл завершится!
    })
}
```
Причина: переменная `tc` аллоцировалась один раз на весь цикл.
Историческое исправление: `tc := tc` внутри тела цикла (создание локальной копии в стеке).
Начиная с **Go 1.22**: спецификация изменена, цикл сам создает новую переменную на каждой итерации.

## Решение по шагам

1. Создайте параллельный тест с 5 элементами.
2. Продемонстрируйте корректность работы в Go 1.22+.
3. Объясните историческую роль `tc := tc`.

## Код решения

**`shadowing_test.go`**

```go
package main

import (
	"sync/atomic"
	"testing"
)

func TestLoopVariableTrap(t *testing.T) {
	testCases := []struct {
		name  string
		value int
	}{
		{name: "кейс_A", value: 1},
		{name: "кейс_B", value: 2},
		{name: "кейс_C", value: 3},
		{name: "кейс_D", value: 4},
	}

	var sum int64

	for _, tc := range testCases {
		// В версиях Go <= 1.21 требовалось: tc := tc (затенение переменной)
		// В Go 1.22+ цикл создает новую переменную на каждом шаге автоматически!
		t.Run(tc.name, func(t *testing.T) {
			t.Parallel()
			atomic.AddInt64(&sum, int64(tc.value))
			t.Logf("[%s] value = %d", tc.name, tc.value)
		})
	}
}
```

## Под капотом

В выводе видно, что каждый подтест получил строго свое уникальное значение `value` (1, 2, 3, 4). В старых версиях Go без `tc := tc` все 4 подтеста вывели бы `value = 4`.

## Подводные камни

Удалять `tc := tc` в библиотеках, поддерживающих старые версии Go (например при сборке с Go 1.20 в старых Docker-образах).

## На собеседовании

**Вопрос с собеседования:** «Почему компилятор Go долгое время не делал этого автоматически?»
**Ответ:** Это меняло область видимости переменных (variable scoping) в спецификации языка. В Go 1.22 изменение было официально включено для модулей с директивой `go 1.22` в `go.mod`.
