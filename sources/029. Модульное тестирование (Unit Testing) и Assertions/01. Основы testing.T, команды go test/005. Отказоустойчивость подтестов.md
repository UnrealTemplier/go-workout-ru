# Отказоустойчивость подтестов: непрерывность выполнения при падении кейса

## Условие

Напиши тест с **несколькими `t.Run` в цикле**, где один case падает. Покажи, что остальные case'и **продолжают выполняться** (Go 1.7+). До этого — `t.Fatalf` останавливал весь тест.

## Теория

До появления механизма `t.Run` в Go 1.7 вызов `t.Fatalf` внутри цикла по таблице останавливал выполнение всей функции теста целиком, из-за чего последующие кейсы даже не проверялись.
Благодаря `t.Run`, каждый подтест изолирован:
- Вызов `t.Fatalf` или `t.Errorf` внутри одного `t.Run` помечает как проваленный только данный конкретный подтест.
- Родительский цикл продолжает работу и запускает следующий подтест!

## Решение по шагам

1. Создайте функцию `Multiply(a, b int) int` с намеренной ошибкой при определенных входных данных.
2. Опишите 3 подтеста в цикле.
3. Убедитесь, что второй упавший подтест не мешает выполнению третьего.

## Код решения

**`calc.go`**

```go
package main

func Multiply(a, b int) int {
	// Баг: умножение на ноль возвращает 99 вместо 0
	if a == 0 || b == 0 {
		return 99
	}
	return a * b
}
```

ℹ️ Функция с дефектом при граничном условии

**`calc_test.go`**

```go
package main

import "testing"

func TestMultiplyIsolation(t *testing.T) {
	tests := []struct {
		name string
		a, b int
		want int
	}{
		{name: "положительные числа", a: 2, b: 3, want: 6},
		{name: "умножение на ноль (сломается)", a: 5, b: 0, want: 0},
		{name: "отрицательные числа", a: -2, b: 4, want: -8},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := Multiply(tc.a, tc.b)
			if got != tc.want {
				t.Fatalf("Multiply(%d, %d) = %d; want %d", tc.a, tc.b, got, tc.want)
			}
		})
	}
}
```

ℹ️ Подтесты продолжают выполняться даже после t.Fatalf в одном из них

**`Терминал`**

```bash
go test -v -run TestMultiplyIsolation
# Вывод:
# === RUN   TestMultiplyIsolation
# === RUN   TestMultiplyIsolation/положительные_числа
# === RUN   TestMultiplyIsolation/умножение_на_ноль_(сломается)
#     calc_test.go:21: Multiply(5, 0) = 99; want 0
# === RUN   TestMultiplyIsolation/отрицательные_числа
# --- FAIL: TestMultiplyIsolation (0.00s)
#     --- PASS: TestMultiplyIsolation/положительные_числа (0.00s)
#     --- FAIL: TestMultiplyIsolation/умножение_на_ноль_(сломается) (0.00s)
#     --- PASS: TestMultiplyIsolation/отрицательные_числа (0.00s)
# FAIL
# exit status 1
```

## Под капотом

Когда подтест вызывает `t.Fatalf`, он вызывает `runtime.Goexit()`, который прерывает горутину подтеста, исполняя все ее `defer`. Родительский тест, вызвавший `t.Run`, ожидает завершения горутины через внутренний канал синхронизации и затем переходит к следующей итерации цикла.

## Подводные камни

Вызывать `t.Fatalf` в теле самого родительского теста до входа в цикл подтестов: это прервет весь родительский тест до запуска каких-либо кейсов.

## На собеседовании

**Вопрос с собеседования:** «Каков статус родительского теста, если 9 из 10 подтестов прошли успешно, а 1 провалился?»
**Ответ:** Родительский тест автоматически помечается как `FAIL`. Достаточно падения хотя бы одного подтеста, чтобы `go test` вернул ненулевой код возврата (exit code 1) в CI/CD пайплайне.
