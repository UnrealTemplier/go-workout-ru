# Table-Driven Tests: золотой стандарт тестирования на 5 граничных сценариях

## Условие

**Table-Driven Tests (Золотой стандарт Go)**: Перепиши `TestAdd`. Создай срез анонимных структур: `tests := []struct{ a, b, expected int }{ ... }`. Заполни его 5-ю разными кейсами (включая отрицательные числа и нули). В цикле обойди срез и проверь каждый кейс.

## Теория

Полноценный табличный тест должен покрывать:
1. Положительные стандартные числа (Happy Path).
2. Нулевые значения (нейтральный элемент сложения).
3. Отрицательные числа.
4. Разные знаки (компенсация сложения).
5. Граничные максимальные значения.

## Решение по шагам

1. Создайте срез структур `tests := []struct { a, b, expected int }{ ... }`.
2. Заполните 5 сценариев.
3. Запустите цикл с `for idx, tc := range tests`.
4. Сравните результат и залогируйте ошибку при несовпадении.

## Код решения

**`math_ops.go`**

```go
package main

func AddNumbers(a, b int) int {
	return a + b
}
```

ℹ️ Функция сложения чисел

**`math_ops_test.go`**

```go
package main

import "testing"

func TestAddNumbersTable(t *testing.T) {
	tests := []struct {
		name     string
		a        int
		b        int
		expected int
	}{
		{name: "два положительных числа", a: 15, b: 25, expected: 40},
		{name: "сложение с нулем", a: 50, b: 0, expected: 50},
		{name: "два отрицательных числа", a: -10, b: -20, expected: -30},
		{name: "разные знаки (положительный результат)", a: 30, b: -10, expected: 20},
		{name: "разные знаки (отрицательный результат)", a: -50, b: 15, expected: -35},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := AddNumbers(tc.a, tc.b)
			if got != tc.expected {
				t.Errorf("AddNumbers(%d, %d) = %d; want %d", tc.a, tc.b, got, tc.expected)
			}
		})
	}
}
```

ℹ️ 5 репрезентативных сценариев в табличном тесте

**`Терминал`**

```bash
go test -v -run TestAddNumbersTable
# Вывод:
# === RUN   TestAddNumbersTable
# === RUN   TestAddNumbersTable/два_положительных_числа
# === RUN   TestAddNumbersTable/сложение_с_нулем
# === RUN   TestAddNumbersTable/два_отрицательных_числа
# === RUN   TestAddNumbersTable/разные_знаки_(положительный_результат)
# === RUN   TestAddNumbersTable/разные_знаки_(отрицательный_результат)
# --- PASS: TestAddNumbersTable (0.00s)
# PASS
```

## Под капотом

Табличная структура теста делает добавление новых регрессионных тестов тривиальным: при обнаружении бага в продакшене инженер просто дописывает одну строчку в массив `tests`, исключая дублирование кода проверок.

## Подводные камни

Отказываться от именования поля `name` в структуре кейса. Без имен подтестов при падении в логе будет трудно отличить, какой именно сценарий завершился с ошибкой.

## На собеседовании

**Вопрос с собеседования:** «Почему табличные тесты предпочтительнее автогенерации тестов или десятка отдельных функций в кодовой базе BigTech?»
**Ответ:** Табличные тесты компактны, легко поддерживаются, обладают минимальной когнитивной нагрузкой при Code Review и идеально масштабируются для покрытия сотен пограничных случаев без разрастания кодовой базы.
