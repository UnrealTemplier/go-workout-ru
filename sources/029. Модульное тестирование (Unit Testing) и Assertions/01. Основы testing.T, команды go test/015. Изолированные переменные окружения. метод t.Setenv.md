# Изолированные переменные окружения: метод t.Setenv

## Условие

Используйте `t.Setenv` для временного изменения переменных окружения в рамках теста. Убедитесь, что они автоматически восстанавливаются после теста.

## Теория

До появления Go 1.17 изменение переменных окружения в тестах требовало ручного восстановления:
```go
old := os.Getenv("APP_ENV")
os.Setenv("APP_ENV", "production")
defer os.Setenv("APP_ENV", old)
```
Это приводило к утечкам окружения, если тест падал или забывал восстановить значение.
В Go 1.17 появился метод `t.Setenv(key, value)`:
1. Он автоматически сохраняет предыдущее значение.
2. Устанавливает новое значение на время теста.
3. Автоматически восстанавливает исходное значение сразу после завершения теста.

## Решение по шагам

1. Проверьте исходное значение переменной окружения.
2. Внутри теста установите новое значение через `t.Setenv("APP_PORT", "9090")`.
3. Убедитесь в автоматическом сбросе значения после завершения теста.

## Код решения

**`config.go`**

```go
package main

import "os"

func GetAppPort() string {
	if port := os.Getenv("APP_PORT"); port != "" {
		return port
	}
	return "8080" // дефолтный порт
}
```

ℹ️ Функция чтения конфигурации из окружения

**`config_test.go`**

```go
package main

import (
	"os"
	"testing"
)

func TestGetAppPortWithSetenv(t *testing.T) {
	// Убедимся в дефолтном поведении
	_ = os.Unsetenv("APP_PORT")
	if port := GetAppPort(); port != "8080" {
		t.Fatalf("Ожидался дефолтный порт 8080, получен %s", port)
	}

	// Устанавливаем временное значение через t.Setenv
	t.Setenv("APP_PORT", "9999")

	if port := GetAppPort(); port != "9999" {
		t.Errorf("GetAppPort() = %s; want 9999", port)
	}
}

func TestEnvRestored(t *testing.T) {
	// Проверяем, что значение 9999 не утекло в следующий тест!
	if port := os.Getenv("APP_PORT"); port != "" {
		t.Errorf("Переменная окружения не была сброшена! Значение: %s", port)
	}
}
```

ℹ️ Безопасное тестирование переменных окружения с автоочисткой

**`Терминал`**

```bash
go test -v config_test.go config.go
# Вывод:
# === RUN   TestGetAppPortWithSetenv
# --- PASS: TestGetAppPortWithSetenv (0.00s)
# === RUN   TestEnvRestored
# --- PASS: TestEnvRestored (0.00s)
# PASS
```

## Под капотом

`t.Setenv` регистрирует функцию восстановления во внутреннем стеке `t.Cleanup()`. Кроме того, `t.Setenv` запрещает вызов `t.Parallel()` в этом тесте, так как переменные окружения процесса являются глобальными для всех горутин в ОС Linux/macOS/Windows.

## Подводные камни

Вызывать `t.Setenv()` в параллельном тесте, помеченном `t.Parallel()`. Раннер Go немедленно выбросит панику: `testing: t.Setenv called in parallel test`.

## На собеседовании

**Вопрос с собеседования:** «Почему вызов `t.Setenv` запрещен в параллельных тестах?»
**Ответ:** Переменные окружения в операционных системах принадлежат всему процессу целиком (Process-wide), а не отдельному потоку. Изменение `os.Setenv` в одной горутине мгновенно аффектит все остальные параллельно исполняемые горутины, приводя к гонкам данных (Data Race) и флакующим тестам.
