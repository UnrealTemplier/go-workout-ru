# Error vs Fatal: немедленная остановка через Fatal против продолжения с Error

## Условие

**Error vs Fatal**: В тесте добавь вызов `t.Error()`, а затем `t.Log("Продолжение")`. Убедись, что после `Error` тест продолжается. Замени `Error` на `t.Fatal()`. Убедись, что `Fatal` немедленно прерывает выполнение текущего теста.

## Теория

Различие между `Error` и `Fatal` фундаментально:
- `t.Error` / `t.Errorf`: помечает тест как проваленный (`t.Fail()`), но выполнение функции продолжается. Используется, когда падение одной проверки не делает бессмысленными остальные (например, проверка нескольких независимых полей структуры JSON).
- `t.Fatal` / `t.Fatalf`: помечает тест как проваленный и **немедленно завершает** текущую функцию теста через `t.FailNow()`. Используется при критических предусловиях (Preconditions): неудачное подключение к базе, ошибка создания временного файла или `err != nil`, когда дальнейшее чтение объекта приведет к панике `nil pointer dereference`.

## Решение по шагам

1. Напишите демонстрационный тест с `t.Error` и `t.Log("Шаг 2")`.
2. Запустите и убедитесь, что `Шаг 2` выполнился.
3. Замените на `t.Fatal` и убедитесь, что последующий код не вызывается.

## Код решения

**`flow_test.go`**

```go
package main

import "testing"

func TestErrorFlow(t *testing.T) {
	t.Error("Нефатальная ошибка на шаге 1")
	t.Log("--> Этот лог будет напечатан, так как t.Error не прерывает тест!")
}

func TestFatalFlow(t *testing.T) {
	t.Fatal("Критическая фатальная ошибка на шаге 1!")
	t.Log("--> Этот лог НИКОГДА не выполнится!")
}
```

ℹ️ Сравнение поведения Error и Fatal

**`Терминал`**

```bash
go test -v flow_test.go
# Вывод:
# === RUN   TestErrorFlow
#     flow_test.go:6: Нефатальная ошибка на шаге 1
#     flow_test.go:7: --> Этот лог будет напечатан, так как t.Error не прерывает тест!
# --- FAIL: TestErrorFlow (0.00s)
# === RUN   TestFatalFlow
#     flow_test.go:11: Критическая фатальная ошибка на шаге 1!
# --- FAIL: TestFatalFlow (0.00s)
# FAIL
```

## Под капотом

`t.FailNow()` внутри вызывает `runtime.Goexit()`. Это приводит к немедленному сворачиванию стека текущей горутины с вызовом отложенных функций `defer`. Другие горутины продолжают работать штатно.

## Подводные камни

Вызывать `t.Fatal` из фоновой горутины, запущенной внутри теста: `runtime.Goexit()` завершит только эту фоновую горутину, а основная горутина теста продолжит выполнение, что приведет к трудноуловимым багам и зависаниям.

## На собеседовании

**Вопрос с собеседования:** «Можно ли вызывать `t.FailNow()` или `t.Fatalf()` из вспомогательной горутины `go func() { ... }()`?»
**Ответ:** Категорически нет! Документация Go прямо запрещает вызов `t.FailNow` вне горутины, запустившей тестовую функцию. Для передачи ошибок из фоновых горутин используются каналы `errCh := make(chan error, 1)` с последующей проверкой `err := <-errCh` в основной горутине теста.
