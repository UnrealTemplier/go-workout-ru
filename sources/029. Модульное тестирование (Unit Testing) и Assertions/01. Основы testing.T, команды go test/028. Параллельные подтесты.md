# Параллельные подтесты: сочетание t.Run и t.Parallel

## Условие

Используйте подтесты с `t.Run` для табличного теста: каждому случаю дайте имя и запустите параллельно с `t.Parallel`.

## Теория

Для параллельного запуска всех строк таблицы:
1. Родительский тест вызывает `t.Parallel()`.
2. Внутри цикла `for _, tc := range tests` вызывается `t.Run`.
3. Внутри функции подтеста **первой строкой** вызывается `t.Parallel()`.
Все кейсы таблицы запускаются параллельно, сокращая суммарное время проверки.

## Решение по шагам

1. Создайте таблицу сценариев.
2. В каждом подтесте вызовите `t.Parallel()`.
3. Запустите тесты и проверьте параллельное исполнение.

## Код решения

**`parallel_table_test.go`**

```go
package main

import (
	"testing"
	"time"
)

func TestParallelTableDriven(t *testing.T) {
	t.Parallel()

	tests := []struct {
		name     string
		duration time.Duration
	}{
		{name: "быстрый_кейс", duration: 50 * time.Millisecond},
		{name: "средний_кейс", duration: 50 * time.Millisecond},
		{name: "долгий_кейс", duration: 50 * time.Millisecond},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			t.Parallel() // Запуск подтеста в параллельной горутине!
			time.Sleep(tc.duration)
			t.Logf("Подтест '%s' завершен", tc.name)
		})
	}
}
```

ℹ️ Параллельные подтесты в табличном тесте

**`Терминал`**

```bash

# Вывод:
```

## Под капотом

Три теста по 50 мс выполнились параллельно за суммарное время 0.05s вместо 0.15s при последовательном вызове.

## Подводные камни

В Go 1.21 и старше без `tc := tc` все подтесты читали последнюю запись цикла. Начиная с Go 1.22 это поведение исправлено на уровне спецификации языка.

## На собеседовании

**Вопрос с собеседования:** «Что изменилось в семантике цикла `for` в Go 1.22 для параллельных тестов?»
**Ответ:** В Go 1.22 переменные цикла имеют область видимости одной итерации (per-iteration scope). На каждой итерации создается новый экземпляр переменной, поэтому необходимость в костыле `tc := tc` полностью отпала.
