# Предотвращение паники: использование t.Fatalf при невалидных предусловиях

## Условие

Используй `t.Fatalf` вместо `t.Errorf` в месте, где дальнейшее выполнение теста не имеет смысла (например, если функция вернула ошибку, а мы пытаемся прочитать результат).

## Теория

Классическая ошибка в тестах:
```go
user, err := FetchUser(10)
if err != nil {
    t.Errorf("Fetch failed: %v", err) // Ошибка залогирована, но выполнение продолжается!
}
fmt.Println(user.Name) // ПАНИКА: nil pointer dereference!
```
Если вызов вернул `err != nil`, указатель `user` равен `nil`. Любое обращение к полям `user.Name` на следующей строке вызовет панику рантайма, прервав весь тестовый процесс.
**Правило:** Если дальнейшие строки кода упадут по панике при нарушении текущего условия — ОБЯЗАТЕЛЬНО используйте `t.Fatalf`!

## Решение по шагам

1. Напишите функцию, возвращающую указатель и ошибку.
2. Проверьте `if err != nil { t.Fatalf(...) }`.
3. Безопасно обратитесь к полям структуры на следующей строке.

## Код решения

**`user.go`**

```go
package main

import (
	"errors"
	"fmt"
)

type User struct {
	ID   int
	Name string
}

func FetchUser(id int) (*User, error) {
	if id <= 0 {
		return nil, errors.New("некорректный ID пользователя")
	}
	return &User{ID: id, Name: fmt.Sprintf("User_%d", id)}, nil
}
```

ℹ️ Функция, возвращающая указатель на структуру

**`user_test.go`**

```go
package main

import "testing"

func TestFetchUserSafe(t *testing.T) {
	// Предусловие: успешная загрузка
	user, err := FetchUser(42)
	if err != nil {
		// КРИТИЧНО: t.Fatalf немедленно останавливает тест, исключая панику на user.Name!
		t.Fatalf("Критическая ошибка FetchUser: %v", err)
	}

	// Безопасный доступ к полям структуры
	if user.Name != "User_42" {
		t.Errorf("user.Name = %q; want 'User_42'", user.Name)
	}
}
```

ℹ️ Защита от nil pointer dereference через t.Fatalf

**`Терминал`**

```bash
go test -v user_test.go user.go
# Вывод:
# === RUN   TestFetchUserSafe
# --- PASS: TestFetchUserSafe (0.00s)
# PASS
```

## Под капотом

`t.Fatalf` защищает раннер тестов от необработанных паник. Паника в тесте завершает весь процесс тестирования аварийно, не позволяя другим тестам запуститься и сформировать отчет о покрытии.

## Подводные камни

Использовать `t.Fatalf` для второстепенных проверок, когда можно проверить остальные поля и собрать больше информации об ошибках за один запуск.

## На собеседовании

**Вопрос с собеседования:** «В чем разница между библиотеками `testify/assert` и `testify/require`?»
**Ответ:** Пакет `assert` при провале проверки вызывает `t.Errorf` (тест продолжается), а пакет `require` вызывает `t.FailNow()` / `t.Fatalf` (тест немедленно прерывается). Поэтому `require` используют для проверки `err == nil` и инициализации, а `assert` — для проверок полей структуры.
