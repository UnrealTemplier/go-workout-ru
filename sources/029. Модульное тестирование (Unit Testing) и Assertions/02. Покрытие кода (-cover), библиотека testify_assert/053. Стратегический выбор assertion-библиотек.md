# Стратегический выбор assertion-библиотек: require для барьеров и assert для полей

## Условие

Используйте `require` вместо `assert` там, где при ошибке нет смысла продолжать тест (например, если не получен объект, а дальше идёт обращение к полям).

## Теория

Золотое правило использования пакета `testify`:
- **`require`** — критические предусловия (Guard Assertions). При ошибке вызывает `t.FailNow()`. Используется при: создании соединений, парсинге JSON, получении указателей, проверке `err == nil`.
- **`assert`** — проверка независимых результатов (Value Assertions). При ошибке вызывает `t.Errorf()`. Используется при проверке полей созданного объекта.

## Решение по шагам

1. Создайте фабрику `CreateUserProfile(id int) (*Profile, error)`.
2. Используйте `require.NoError` и `require.NotNil` для защиты от паники.
3. Используйте `assert.Equal` для проверки конкретных полей.

## Код решения

**`require_demo_test.go`**

```go
package main

import (
	"errors"
	"testing"

	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/require"
)

type Profile struct {
	ID    int
	Email string
	Role  string
}

func LoadProfile(id int) (*Profile, error) {
	if id <= 0 {
		return nil, errors.New("неверный ID")
	}
	return &Profile{ID: id, Email: "user@corp.ru", Role: "admin"}, nil
}

func TestLoadProfileBestPractice(t *testing.T) {
	p, err := LoadProfile(101)

	// БАРЬЕР: если произошла ошибка или p == nil, тест МГНОВЕННО прерывается!
	require.NoError(t, err, "Загрузка профиля обязана завершиться без ошибок")
	require.NotNil(t, p, "Профиль не должен быть nil")

	// ПРОВЕРКА ПОЛЕЙ: если упадет Email, Role все равно проверится!
	assert.Equal(t, 101, p.ID)
	assert.Equal(t, "user@corp.ru", p.Email)
	assert.Equal(t, "admin", p.Role)
}
```

ℹ️ Идеальный тандем require и assert

**`Терминал`**

```bash
go test -v require_demo_test.go
# Вывод:

# --- PASS: TestLoadProfileBestPractice (0.00s)
# PASS
```

## Под капотом

`require` имплементирует интерфейс `TestingT` и при провале вызывает `t.FailNow()`. Это гарантирует, что обращение `p.ID` никогда не приведет к панике `SIGSEGV`.

## Подводные камни

Использовать `assert.NoError(t, err)` и на следующей строке обращаться к полям `p.Email`. Если `err != nil`, `p` равен `nil`, и раннер упадет по панике dereference, скрыв причину сбоя.

## На собеседовании

**Вопрос с собеседования:** «Что происходит с `defer` и `t.Cleanup` при падении проверки в `require`?»
**Ответ:** Все зарегистрированные функции `defer` и `t.Cleanup()` корректно выполняются, так как `require` вызывает `t.FailNow()`, который сворачивает стек через `runtime.Goexit()`.
