# Режимы покрытия кода: set, count, atomic и интеграция с -race

## Условие

Изучите разницу между `cover` и `-covermode=atomic`. Почему `atomic` обязателен при использовании флага `-race`?

## Теория

Флаг `-covermode` поддерживает три режима инструментации:
1. `set` (по умолчанию): булевый флаг (выполнялась ли строка хотя бы один раз? `true/false`).
2. `count`: счетчик целых чисел (сколько раз выполнялась строка?).
3. `atomic`: счетчик инкрементируется атомарными инструкциями процессора (`sync/atomic`).

**Почему `atomic` обязателен с `-race`?**
Если тесты запускают несколько горутин, и обе горутины выполняют одну и ту же строчку кода, они одновременно инкрементируют служебный счетчик покрытия.
В режиме `set` или `count` это обычная несинхронизированная запись в память! Детектор `-race` перехватит эту гонку и уронит тест с ложным срабатыванием в коде инструментатора покрытия! Режим `atomic` использует атомарные инструкции процессора, исключая гонку.

## Решение по шагам

1. Запустите параллельный тест с `-cover -race`.
2. Убедитесь, что Go автоматически включает режим `atomic`.
3. Сравните точность подсчета покрытия.

## Код решения

**`atomic_cov_test.go`**

```go
package main

import (
	"sync"
	"testing"
)

func ParallelWork(n int) int {
	return n * 2
}

func TestParallelCoverage(t *testing.T) {
	var wg sync.WaitGroup
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func(val int) {
			defer wg.Done()
			_ = ParallelWork(val)
		}(i)
	}
	wg.Wait()
}
```

ℹ️ Параллельный код для проверки покрытия

**`Терминал`**

```bash
# Запуск с детектором гонок и атомарным режимом покрытия:
go test -race -cover -covermode=atomic atomic_cov_test.go
# Вывод:
# ok      command-line-arguments  0.015s  coverage: 100.0% of statements
```

## Под капотом

В режиме `atomic` компилятор заменяет строку `GoCover[i]++` на ассемблерную инструкцию `LOCK INC` (x86_64) или `LDADD` (ARM64), защищая ячейку счетчика на уровне аппаратной шины процессора.

## Подводные камни

Использовать `-covermode=atomic` без необходимости в чисто последовательных тестах: атомарные инструкции процессора сбрасывают кэш-линии L1, увеличивая время прогона тестов на 20-30%.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если запустить `go test -race -covermode=count`?»
**Ответ:** Команда `go test` вернет ошибку конфигурации еще до запуска:
`-covermode=count is incompatible with -race, use -covermode=atomic`. Фреймворк тестирования Go строго запрещает запуск неатомарных режимов покрытия совместно с детектором гонок.
