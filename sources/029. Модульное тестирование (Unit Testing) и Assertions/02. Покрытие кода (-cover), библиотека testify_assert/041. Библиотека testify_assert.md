# Библиотека testify/assert: проверки Contains, Len и NotNil

## Условие

Используй `assert.Contains(t, slice, element)`, `assert.Len(t, slice, 3)`, `assert.NotNil(t, ptr)`. Напиши тесты для функций, работающих со слайсами и мапами.

## Теория

Библиотека `github.com/stretchr/testify/assert` — самый популярный инструмент assertions в экосистеме Go:
- `assert.Contains(t, collection, element)`: проверяет наличие элемента в срезе, мапе или подстроки в строке.
- `assert.Len(t, collection, expectedLen)`: проверяет точную длину коллекции.
- `assert.NotNil(t, ptr)`: проверяет, что указатель/интерфейс не равен `nil`.
- Сообщения об ошибках форматируются автоматически с наглядным diff!

## Решение по шагам

1. Создайте функцию, возвращающую список активных пользователей.
2. Проверьте длину среза через `assert.Len`.
3. Проверьте вхождение через `assert.Contains`.
4. Проверьте указатели через `assert.NotNil`.

## Код решения

**`collections_test.go`**

```go
package main

import (
	"testing"

	"github.com/stretchr/testify/assert"
)

type Config struct {
	Tags []string
}

func GetDefaultConfig() *Config {
	return &Config{Tags: []string{"web", "api", "v2"}}
}

func TestCollectionsWithAssert(t *testing.T) {
	cfg := GetDefaultConfig()

	// 1. Проверяем указатель
	assert.NotNil(t, cfg, "Конфигурация не должна быть nil")

	// 2. Проверяем длину среза
	assert.Len(t, cfg.Tags, 3, "Ожидалось ровно 3 тега")

	// 3. Проверяем наличие элемента
	assert.Contains(t, cfg.Tags, "api", "Тег 'api' должен присутствовать в списке")
}
```

ℹ️ Использование assert для коллекций

**`Терминал`**

```bash
go test -v collections_test.go
# Вывод:
# === RUN   TestCollectionsWithAssert
# --- PASS: TestCollectionsWithAssert (0.00s)
# PASS
```

## Под капотом

`assert.Contains` использует рефлексию `reflect.ValueOf()` для универсальной поддержки срезов, массивов, мап и строк без дублирования кода.

## Подводные камни

Использовать `assert.Equal` для сравнения срезов, где порядок элементов не имеет значения. Для неупорядоченных срезов используйте `assert.ElementsMatch`.

## На собеседовании

**Вопрос с собеседования:** «Каковы недостатки использования testify/assert по сравнению со стандартным подходом Go?»
**Ответ:** Дополнительная внешняя зависимость в `go.mod`, слегка замедляющая компиляцию тестов, и потеря гибкости в кастомизации сообщений об ошибках по сравнению с идиоматичным `if got != want { t.Errorf(...) }`.
