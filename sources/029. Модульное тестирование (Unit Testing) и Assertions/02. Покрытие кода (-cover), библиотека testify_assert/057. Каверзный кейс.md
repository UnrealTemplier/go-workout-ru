# Каверзный кейс: LIFO порядок выполнения функций очистки t.Cleanup

## Условие

**[Каверзный кейс]**: Используй `t.Cleanup(func() { ... })` внутри теста. Убедись, что функции очистки вызываются в обратном порядке (LIFO), даже если тест упал с `t.Fatal`.

## Теория

Механика `t.Cleanup`:
- Функции регистрируются в стек (Last-In, First-Out).
- Если зарегистрированы `Cleanup A`, затем `Cleanup B`, затем `Cleanup C`, при выходе они выполнятся строго в порядке: `C -> B -> A`.
- Это критично для зависимых ресурсов: например, сначала нужно закрыть транзакцию базы данных (C), затем закрыть соединение с БД (B), и только затем остановить контейнер с СУБД (A).
- Порядок гарантирован даже при вызове `t.Fatal()`!

## Решение по шагам

1. Зарегистрируйте три коллбэка очистки в тесте.
2. Вызовите `t.Fatal()`.
3. Убедитесь в порядке вызова LIFO.

## Код решения

**`cleanup_lifo_test.go`**

```go
package main

import "testing"

func TestCleanupLIFOOrder(t *testing.T) {
	var executionOrder []string

	// Регистрируем шаги очистки
	t.Cleanup(func() {
		executionOrder = append(executionOrder, "Шаг 1 (первый зарегистрирован, выполнится ПОСЛЕДНИМ)")
		t.Log("Выполнен Cleanup 1")
	})

	t.Cleanup(func() {
		executionOrder = append(executionOrder, "Шаг 2 (второй зарегистрирован)")
		t.Log("Выполнен Cleanup 2")
	})

	t.Cleanup(func() {
		executionOrder = append(executionOrder, "Шаг 3 (третий зарегистрирован, выполнится ПЕРВЫМ)")
		t.Log("Выполнен Cleanup 3")
	})

	t.Log("Все Cleanup зарегистрированы. Вызываем t.Fatal...")
	t.Fatal("Аварийное прерывание теста!")
}
```

ℹ️ Проверка LIFO порядка выполнения функций очистки

**`Терминал`**

```bash
go test -v cleanup_lifo_test.go
# Вывод:
# === RUN   TestCleanupLIFOOrder
#     cleanup_lifo_test.go:24: Все Cleanup зарегистрированы. Вызываем t.Fatal...
#     cleanup_lifo_test.go:25: Аварийное прерывание теста!
#     cleanup_lifo_test.go:21: Выполнен Cleanup 3
#     cleanup_lifo_test.go:16: Выполнен Cleanup 2
#     cleanup_lifo_test.go:11: Выполнен Cleanup 1
# --- FAIL: TestCleanupLIFOOrder (0.00s)
# FAIL
```

## Под капотом

В структуре `common` пакета `testing` вызов `cleanups` реализован классическим обходом среза от `len(c.cleanups)-1` до 0. Каждый коллбэк оборачивается в защищенный блок, поэтому паника в одном cleanup не препятствует вызову остальных.

## Подводные камни

Полагаться на FIFO порядок: если логика рассчитывает на прямое выполнение очистки, зависимые ресурсы будут разрушены в неверной последовательности.

## На собеседовании

**Вопрос с собеседования:** «Что произойдет, если внутри функции `t.Cleanup` вызвать метод `t.Errorf()`?»
**Ответ:** Ошибка будет корректно зарегистрирована в протоколе теста, и тест будет помечен как проваленный (`FAIL`). Это позволяет выполнять ассерты проверки освобождения ресурсов (например, проверять, что все дескрипторы файлов были закрыты).
