# Рефакторинг разрозненных тестов в единый Table-Driven Test

## Условие

Перепишите серию из 5 похожих тестов в один **Table-Driven Test**: слайс структур с полями `name`, `input`, `expected` и циклом `for _, tc := range tests`.

## Теория

Антипаттерн Copy-Paste:
Написание отдельных функций `TestValidateEmail_Empty`, `TestValidateEmail_NoAt`, `TestValidateEmail_NoDomain`, `TestValidateEmail_Valid` порождает сотни строк повторяющегося шаблонного кода.
Рефакторинг в Table-Driven Test сокращает размер кодовой базы на 70%, повышая её поддерживаемость.

## Решение по шагам

1. Напишите функцию `ValidateEmail(email string) bool`.
2. Опишите срез тестовых случаев `tests := []struct{ name, email string, want bool }{ ... }`.
3. Запустите проверку в едином цикле.
4. Проверьте прохождение тестов.

## Код решения

**`email.go`**

```go
package main

import "strings"

func ValidateEmail(email string) bool {
	if len(email) < 5 || !strings.Contains(email, "@") {
		return false
	}
	parts := strings.Split(email, "@")
	if len(parts) != 2 || parts[0] == "" || parts[1] == "" {
		return false
	}
	return strings.Contains(parts[1], ".")
}
```

ℹ️ Функция валидации email

**`email_test.go`**

```go
package main

import "testing"

func TestValidateEmailTable(t *testing.T) {
	tests := []struct {
		name  string
		email string
		want  bool
	}{
		{name: "корректный email", email: "dev@yandex.ru", want: true},
		{name: "пустая строка", email: "", want: false},
		{name: "нет собаки", email: "plainaddress", want: false},
		{name: "нет домена", email: "user@", want: false},
		{name: "домен без точки", email: "user@domain", want: false},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := ValidateEmail(tc.email)
			if got != tc.want {
				t.Errorf("ValidateEmail(%q) = %v; want %v", tc.email, got, tc.want)
			}
		})
	}
}
```

ℹ️ Лаконичный Table-Driven Test вместо 5 функций

**`Терминал`**

```bash
go test -v email_test.go email.go
# Вывод:
```

## Под капотом

Срез структур выделяется в стеке или куче единожды при входе в `TestValidateEmailTable`. Добавление шестого или сотого сценария требует лишь добавления одной строки данных без изменения логики проверки.

## Подводные камни

Усложнять структуру кейса десятками необязательных полей. Если логика проверки кейсов кардинально отличается, лучше разделить их на 2 таблицы, чем создавать мега-структуру со сложными `if` внутри подтеста.

## На собеседовании

**Вопрос с собеседования:** «Когда НЕ стоит применять Table-Driven подход?»
**Ответ:** Когда сценарии требуют принципиально разной подготовки окружения (например, сложный мокинг разных внешних сервисов, настройка разных транзакций базы данных). В этом случае отдельные тестовые функции чище и проще поддерживать.
