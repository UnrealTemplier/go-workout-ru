# Event Schema: проектирование схем событий в Protobuf / JSON Schema с валидацией

## Условие

37. **Event schema**: Определите схему событий в Protobuf/JSON Schema: `OrderCreatedEvent{order_id, user_id, items[], total_amount}`.

### Исходная формулировка

**Event schema**: Определите схему событий в Protobuf/JSON Schema: `OrderCreatedEvent{order_id, user_id, items[], total_amount}`.

## Теория

В распределенных системах отсутствие строгой схемы событий приводит к катастрофам: один сервис переименовал поле `order_id` в `orderId`, и консьюмеры всех остальных сервисов начинают падать с ошибками десериализации (NullPointerException / nil pointer dereference).

Стандарты проектирования схем событий:
1. **Protocol Buffers (Proto3)**: Бинарная сериализация, обратная совместимость по тегам полей, поддержка валидаторов через `protoc-gen-validate` (PGV) или `buf.build/bufbuild/protovalidate`.
2. **CloudEvents v1.0 Spec**: Спецификация метаданных CNCF: `specversion`, `type`, `source`, `id`, `time`, `datacontenttype`.
3. **Schema Registry**: Реестр схем (Confluent Schema Registry или Buf BSR) проверяет обратную совместимость схемы в CI/CD до релиза сервиса в прод.

## Решение по шагам

1. Опишите Protobuf контракт события `OrderCreatedEvent`.
2. Добавьте правила валидации полей (UUID, положительная сумма).
3. Реализуйте в Go валидатор входящего события.
4. Продемонстрируйте отклонение некорректного события.
5. Напишите тест соответствия схеме.

## Код решения

**`event_schema.go`**

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

// DTO события, сгенерированное из Protobuf контракта
type OrderCreatedEventProto struct {
	EventID   string    `json:"event_id"`
	SagaID    string    `json:"saga_id"`
	OrderID   string    `json:"order_id"`
	Amount    float64   `json:"amount"`
	Currency  string    `json:"currency"`
	CreatedAt time.Time `json:"created_at"`
}

// Validate эмулирует правила protoc-gen-validate
func (e *OrderCreatedEventProto) Validate() error {
	if e.EventID == "" {
		return errors.New("event_id обязателен для заполнения")
	}
	if e.SagaID == "" {
		return errors.New("saga_id обязателен для трассировки")
	}
	if e.Amount <= 0 {
		return fmt.Errorf("сумма заказа должна быть строго положительной (получено: %.2f)", e.Amount)
	}
	if e.Currency != "RUB" && e.Currency != "USD" {
		return fmt.Errorf("неподдерживаемая валюта: %s", e.Currency)
	}
	return nil
}

func main() {
	// Валидное событие
	validEvent := &OrderCreatedEventProto{
		EventID:   "evt-100",
		SagaID:    "saga-500",
		OrderID:   "ord-99",
		Amount:    3500.0,
		Currency:  "RUB",
		CreatedAt: time.Now(),
	}

	if err := validEvent.Validate(); err != nil {
		fmt.Printf("Ошибка валидации: %v\n", err)
	} else {
		fmt.Println("Событие 1: Схема валидна, готово к публикации в Kafka!")
	}

	// Невалидное событие (отрицательная сумма)
	invalidEvent := &OrderCreatedEventProto{
		EventID:   "evt-101",
		SagaID:    "saga-501",
		OrderID:   "ord-100",
		Amount:    -500.0,
		Currency:  "RUB",
		CreatedAt: time.Now(),
	}

	if err := invalidEvent.Validate(); err != nil {
		fmt.Printf("Событие 2: ОТКЛОНЕНО ВАЛИДАТОРОМ: %v\n", err)
	}
}
```

ℹ️ Строгая валидация схемы событий перед публикацией в брокер сообщений

## Под капотом

В экосистеме Go компилятор `bufbuild/protovalidate-go` выполняет проверку правил валидации без отражения (Zero Reflection) на скомпилированных выражениях Common Expression Language (CEL). Это позволяет валидировать 500,000 событий в секунду на одном ядре процессора.

## Подводные камни

1. **Удаление полей из схемы**: Удаление поля ломает старых потребителей, которые еще не обновились. Поля можно только объявлять `reserved` или делать опциональными.
2. **Отсутствие поля версионирования**: Публикация событий без указания версии схемы (`schema_version = 1`) лишает возможности плавной миграции.

## На собеседовании

В архитектуре микросервисов Яндекс и Ozon Schema Registry является обязательным барьером. Вопрос: 'Что такое Backward и Full Compatibility в Schema Registry?' Ответ: Backward compatibility означает, что новый сервис может читать события, созданные старым сервисом. Full compatibility гарантирует, что и старые, и новые сервисы могут читать события друг друга, обеспечивая Zero-Downtime развертывание.
