### Исходная формулировка

**Parallel Saga.**: Реализуйте шаги, которые можно выполнять параллельно: резервирование `Inventory` и расчёт `Shipping` одновременно. Соберите результаты через `sync.WaitGroup` или каналы, затем следующий шаг (`Payment`). Объясните, что параллельные шаги должны быть независимыми (не конфликтовать по данным).

## Теория

Оптимизация времени оформления заказа требует параллельного выполнения шагов, не имеющих взаимных зависимостей данных.

Сценарий параллельного шага:
- Склад (`InventoryService.Reserve`): блокировка физического товара.
- Программа лояльности (`LoyaltyService.DeductPoints`): списание баллов со счета.

Оба действия выполняются конкурентно в пуле горутин. Оркестратор ожидает завершения обеих операций через барьер синхронизации (`sync.WaitGroup` или `errgroup`).

Матрица компенсаций:
- Склад OK, Бонусы FAIL -> Откат Склада.
- Склад FAIL, Бонусы OK -> Откат Бонусов.
- Склад FAIL, Бонусы FAIL -> Компенсация не требуется.
- Оба OK -> Переход к следующему этапу (Списание карты).

## Решение по шагам

1. Опишите функции резерва склада и бонусов.
2. Реализуйте параллельный запуск с фиксацией индивидуальных результатов.
3. Проанализируйте матрицу результатов.
4. Выполните компенсацию только для успешно завершившегося шага.
5. Протестируйте сценарий сбоя одного из параллельных шагов.

## Код решения

**`parallel_branches.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type BranchResult struct {
	Name    string
	Success bool
	Err     error
}

func main() {
	var wg sync.WaitGroup
	results := make(chan BranchResult, 2)

	// Ветка 1: Резерв склада
	wg.Add(1)
	go func() {
		defer wg.Done()
		time.Sleep(80 * time.Millisecond)
		fmt.Println("[Branch 1] Склад зарезервирован: УСПЕХ")
		results <- BranchResult{Name: "Inventory", Success: true}
	}()

	// Ветка 2: Бонусы (Сбой!)
	wg.Add(1)
	go func() {
		defer wg.Done()
		time.Sleep(60 * time.Millisecond)
		fmt.Println("[Branch 2] Бонусы: СБОЙ (Недостаточно баллов на счете)")
		results <- BranchResult{Name: "Loyalty", Success: false, Err: errors.New("insufficient bonus points")}
	}()

	wg.Wait()
	close(results)

	var hasError bool
	var toCompensate []string

	for res := range results {
		if !res.Success {
			hasError = true
		} else {
			toCompensate = append(toCompensate, res.Name)
		}
	}

	if hasError {
		fmt.Printf("\n[Parallel Coordinator] Обнаружен сбой в одной из веток! Запуск выборочной компенсации:\n")
		for _, name := range toCompensate {
			fmt.Printf("  <- КОМПЕНСАЦИЯ для ветки: %s (Снятие блокировки)\n", name)
		}
	} else {
		fmt.Println("\nВсе параллельные шаги успешно завершены! Переход к оплате картой.")
	}
}
```

ℹ️ Параллельные ветки саги с выборочной компенсацией завершившихся шагов

## Под капотом

Использование закрываемого буферизированного канала `results := make(chan BranchResult, 2)` позволяет безопасно аккумулировать результаты всех веток без риска зависания горутин-писателей, даже если основная горутина перестанет читать канал. Вызов `close(results)` после `wg.Wait()` делает обход через `for res := range results` идиоматичным и чистым.

## Подводные камни

1. **Забытый `wg.Done()` при панике**: Если внутри ветки произойдет panic, `wg.Wait()` зависнет навсегда. Всегда помещайте `defer wg.Done()` первой строкой горутины.
2. **Компенсация неудавшейся ветки**: Попытка вызвать откат для ветки, которая вернула ошибку, может вызвать отрицательный баланс.

## На собеседовании

В логистике Wildberries: 'Как объединить результаты 10 параллельных запросов к складам с таймаутом?' Ответ: Использовать `context.WithTimeout` в связке с `errgroup.Group`. Если время вышло, все незавершившиеся горутины получают сигнал отмены через контекст, а компенсатор откатывает только успевшие подтвердиться склады.
