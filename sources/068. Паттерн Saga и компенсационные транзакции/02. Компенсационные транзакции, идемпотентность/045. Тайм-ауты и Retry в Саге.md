# Тайм-ауты и Retry в Саге: порог 5 секунд, экспоненциальный откат и запуск отмены

## Условие

45. **Таймауты и Retry в Saga.**: Если сервис не отвечает 5 секунд — retry с exponential backoff (3 попытки). Если исчерпаны — запустите компенсацию предыдущих шагов. Объясните проблему «висших» (suspended) транзакций: запрос мог уйти, но ответ потерялся, и компенсация может конфликтовать с поздним ответом.

## Теория

Промышленный стандарт обработки временных сбоев на шаге Саги:
1. Вызов внешнего сервиса выполняется с дедлайном в **5 секунд**.
2. Если ответ не получен или получен временный сбой (503/504), выполняется **Retry с экспоненциальным backoff**:
   - Попытка 1: 500 мс.
   - Попытка 2: 1000 мс.
   - Попытка 3: 2000 мс.
3. Если после 3 попыток сервис не ответил — ошибка признается неустранимой.
4. Оркестратор фиксирует аварийное завершение шага и инициирует автоматический откат всех ранее подтвержденных шагов.

## Код решения

**`step_retry_orchestrator.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func CallServiceWithTimeoutAndRetry(ctx context.Context, serviceName string) error {
	maxAttempts := 3
	baseDelay := 100 * time.Millisecond // Для демо 100 мс

	for attempt := 1; attempt <= maxAttempts; attempt++ {
		// Таймаут на каждую попытку вызова — 5 секунд (в демо 300 мс)
		callCtx, cancel := context.WithTimeout(ctx, 300*time.Millisecond)
		err := makeNetworkCall(callCtx)
		cancel()

		if err == nil {
			fmt.Printf("[%s] Успех на попытке %d!\n", serviceName, attempt)
			return nil
		}

		fmt.Printf("[%s] Попытка %d завершилась ошибкой: %v\n", serviceName, attempt, err)

		if attempt == maxAttempts {
			break
		}

		delay := baseDelay * time.Duration(1<<(attempt-1)) // 100ms, 200ms...
		fmt.Printf("[%s] Ожидание %v перед следующей попыткой...\n", serviceName, delay)
		time.Sleep(delay)
	}

	return fmt.Errorf("сервис %s недоступен после %d попыток", serviceName, maxAttempts)
}

func makeNetworkCall(ctx context.Context) error {
	select {
	case <-time.After(500 * time.Millisecond): // Зависает дольше 300 мс!
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func main() {
	fmt.Println("=== Выполнение шага Саги с таймаутом и ретраями ===")
	err := CallServiceWithTimeoutAndRetry(context.Background(), "PaymentGateway")
	if err != nil {
		fmt.Printf("\n[SAGA ABORT TRIGGERED] %v!\n", err)
		fmt.Println(">>> Запуск каскадной компенсации заказа и освобождения склада! <<<")
	}
}
```

ℹ️ Управление таймаутом вызова с экспоненциальным backoff и запуском компенсации

## Под капотом

Формула `baseDelay * (1 << (attempt - 1))` реализует битовый сдвиг влево для мгновенного вычисления степени двойки \(2^{attempt-1}\), что избавляет от тяжелых вызовов операций с плавающей точкой `math.Pow`. При `attempt=1` множитель равен 1, при `attempt=2` равен 2, при `attempt=3` равен 4.

## Подводные камни

1. **Суммарное время ретраев превышает общий таймаут саги**: Если 3 попытки по 5 секунд с паузами займут 20 секунд, а общий таймаут саги 15 секунд, глобальный контекст оборвет выполнение до завершения ретраев.
2. **Отсутствие проверки `ctx.Done()` во время сна `time.Sleep`**: Если глобальный контекст саги отменен, спящая горутина должна мгновенно просыпаться.

## На собеседовании

В архитектуре микросервисов Яндекс Go: 'Как правильно организовать таймауты между клиентом и сервером (Timeout Cascading)?' Ответ: Бюджет времени уменьшается по мере движения вглубь системы: HTTP шлюз имеет таймаут 5.0с, вызов к оркестратору 4.5с, оркестратор к БД 2.0с. Если глубокий сервис имеет таймаут больше клиентского, клиент разорвет соединение, а бэкенд продолжит бесполезно нагружать процессор.
