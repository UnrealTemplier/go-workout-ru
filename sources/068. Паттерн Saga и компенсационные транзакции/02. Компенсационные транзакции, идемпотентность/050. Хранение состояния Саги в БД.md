# Хранение состояния Саги в БД: таблица saga_state и транзакционная изоляция

## Условие

50. **Хранение состояния саги в БД.**: Сохраняйте текущий шаг и статус саги в отдельную таблицу `saga_state`. При перезапуске оркестратор должен восстановить незавершённые саги и продолжить или откатить их.

### Исходная формулировка

**Хранение состояния саги в БД.**: Сохраняйте текущий шаг и статус саги в отдельную таблицу `saga_state`. При перезапуске оркестратор должен восстановить незавершённые саги и продолжить или откатить их.

## Теория

Персистентное хранение состояния Саги — основа надежности оркестратора.

Схема таблицы PostgreSQL:
```sql
CREATE TABLE saga_instances (
    id UUID PRIMARY KEY,
    saga_type VARCHAR(64) NOT NULL,
    current_step INT NOT NULL DEFAULT 0,
    status VARCHAR(32) NOT NULL, -- STARTED, COMPENSATING, COMPLETED, FAILED
    payload JSONB NOT NULL,
    version INT NOT NULL DEFAULT 1,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

Оптимистическая блокировка (`Optimistic Concurrency Control`):
При каждом обновлении состояния выполняется запрос:
`UPDATE saga_instances SET status = $1, current_step = $2, version = version + 1, updated_at = NOW() WHERE id = $3 AND version = $4;`
Если строка не обновилась (`RowsAffected == 0`), произошел конфликт параллельного изменения.

## Решение по шагам

1. Опишите модель персистентной саги с версионированием.
2. Реализуйте метод обновления состояния с контролем `version`.
3. Смоделируйте параллельную попытку обновления одной саги двумя воркерами.
4. Убедитесь, что второй воркер получает ошибку конфликта версий.
5. Протестируйте целостность данных.

## Код решения

**`saga_persistence.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type SagaModel struct {
	ID          string
	CurrentStep int
	Status      string
	Version     int
	UpdatedAt   time.Time
}

type SagaSQLStore struct {
	mu    sync.Mutex
	table map[string]SagaModel
}

func NewSagaSQLStore() *SagaSQLStore {
	return &SagaSQLStore{table: make(map[string]SagaModel)}
}

func (s *SagaSQLStore) Insert(saga SagaModel) {
	s.mu.Lock()
	defer s.mu.Unlock()
	saga.Version = 1
	saga.UpdatedAt = time.Now()
	s.table[saga.ID] = saga
}

// UpdateWithOptimisticLock эмулирует UPDATE ... WHERE id = $1 AND version = $2
func (s *SagaSQLStore) UpdateWithOptimisticLock(id string, nextStep int, nextStatus string, expectedVersion int) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	current, exists := s.table[id]
	if !exists {
		return errors.New("сага не найдена")
	}

	// Контроль оптимистической блокировки
	if current.Version != expectedVersion {
		return fmt.Errorf("OPTIMISTIC LOCK CONFLICT: ожидалась версия %d, но в БД уже версия %d",
			expectedVersion, current.Version)
	}

	current.CurrentStep = nextStep
	current.Status = nextStatus
	current.Version++
	current.UpdatedAt = time.Now()
	s.table[id] = current

	fmt.Printf("[DB Update OK] Сага %s обновлена: Шаг=%d, Статус=%s, Новая версия=%d\n",
		id, nextStep, nextStatus, current.Version)
	return nil
}

func main() {
	store := NewSagaSQLStore()
	sagaID := "SAGA-ORDER-SQL-1"

	store.Insert(SagaModel{ID: sagaID, CurrentStep: 1, Status: "STARTED"})

	// Воркер 1 успешно обновляет версию 1 -> 2
	err1 := store.UpdateWithOptimisticLock(sagaID, 2, "IN_PROGRESS", 1)
	fmt.Printf("Воркер 1: %v\n", err1)

	// Воркер 2 пытается обновить устаревшую версию 1 (Конфликт!)
	err2 := store.UpdateWithOptimisticLock(sagaID, 3, "COMPLETED", 1)
	fmt.Printf("Воркер 2: %v\n", err2)
}
```

ℹ️ Транзакционное хранение состояния Саги с оптимистической блокировкой версий

## Под капотом

Оптимистическая блокировка (Optimistic Locking) в разы эффективнее пессимистических блокировок `SELECT FOR UPDATE`, так как не держит локи на строках во время долгих сетевых вызовов к удаленным микросервисам. Лок держится лишь доли миллисекунды в момент выполнения одиночного SQL-запроса `UPDATE`.

## Подводные камни

1. **Удержание транзакции БД во время сетевого RPC вызова**: Начинать `BEGIN`, отправлять HTTP-запрос банку на 5 секунд и только потом делать `COMMIT` — катастрофический антипаттерн, приводящий к исчерпанию пула соединений PostgreSQL.
2. **Отсутствие поля `version`**: Без проверки версии две параллельные реплики могут перезаписать состояние друг друга.

## На собеседовании

В высоконагруженных системах Яндекс и Авито: 'Почему нельзя держать транзакцию PostgreSQL открытой во время выполнения шага Саги?' Ответ: Транзакция БД держит соединение из ограниченного пула (например, 50 соединений pgxpool). Сетевые задержки внешних API мгновенно исчерпают пул соединений, заблокировав работу ВСЕГО микросервиса.
