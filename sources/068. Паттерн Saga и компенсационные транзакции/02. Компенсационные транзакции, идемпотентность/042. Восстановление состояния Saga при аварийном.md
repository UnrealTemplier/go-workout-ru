# Восстановление состояния Saga при аварийном падении оркестратора

## Условие

42. **[Каверзный кейс — Сохранение состояния Saga]**: Оркестратор упал посередине (сделал Payment, но не успел вызвать Inventory). При рестарте он не должен начать с нуля. Сохраняй текущий шаг Saga (State Machine) в PostgreSQL перед каждым переходом.

### Исходная формулировка

**[Каверзный кейс — Сохранение состояния Saga]**: Оркестратор упал посередине (сделал Payment, но не успел вызвать Inventory). При рестарте он не должен начать с нуля. Сохраняй текущий шаг Saga (State Machine) в PostgreSQL перед каждым переходом.

## Теория

Каверзный кейс: Оркестратор успешно выполнил Шаг 1 (`CreateOrder`) и Шаг 2 (`ReserveStock`), отправил запрос на Шаг 3 (`ProcessPayment`), и в эту секунду сервер мгновенно убивает операционная система (SIGKILL / Out-Of-Memory).

Что происходит при старте нового экземпляра оркестратора:
1. В БД записано: Шаг 2 успешен, Шаг 3 в статусе `UNKNOWN / IN_PROGRESS`.
2. Оркестратор **не знает**, дошел ли запрос до платежного шлюза и списались ли деньги.
3. **Запрещено** сразу запускать откат или слать повторный платеж!
4. Оркестратор обязан выполнить процедуру согласования (**Reconciliation / Status Probe**):
   - Запрос в `PaymentService.GetStatus(saga_id)`.
   - Если статус 'оплачено' -> переход к Шагу 4.
   - Если статус 'не найдено' -> можно безопасно запустить откат или повторить шаг.

## Решение по шагам

1. Смоделируйте промежуточное зависшее состояние саги в хранилище.
2. Реализуйте метод зондирования статуса `ProbeStepStatus`.
3. Разработайте ветвление: возобновление движения вперед или запуск компенсаций.
4. Докажите предотвращение двойного списания.
5. Протестируйте сценарий восстановления.

## Код решения

**`crash_recovery.go`**

```go
package main

import (
	"fmt"
)

type StepStatus string

const (
	StatusSuccess StepStatus = "SUCCESS"
	StatusPending StepStatus = "PENDING_UNKNOWN"
)

type HangingSaga struct {
	SagaID      string
	LastKnownOK string
	PendingStep string
}

// Эмуляция удаленного платежного сервиса
func MockPaymentGatewayQuery(sagaID string) (bool, error) {
	// Имитация: платеж на самом деле успел пройти в банке до падения оркестратора!
	return true, nil
}

func RecoverCrashedSaga(saga HangingSaga) {
	fmt.Printf("[Recovery Engine] Восстановление саги %s после аварийного сбоя...\n", saga.SagaID)
	fmt.Printf("  -> Последний подтвержденный шаг: %s\n", saga.LastKnownOK)
	fmt.Printf("  -> Зависший шаг в неизвестном статусе: %s\n", saga.PendingStep)

	// ЗОНДИРОВАНИЕ СТАТУСА (Reconciliation Probe)
	paid, err := MockPaymentGatewayQuery(saga.SagaID)
	if err != nil {
		fmt.Println("  [!] Не удалось связаться с банком, повтор через 10 секунд")
		return
	}

	if paid {
		fmt.Printf("  [RECONCILIATION RESULT] Платеж реально прошел в банке! Переводим шаг %s в SUCCESS.\n",
			saga.PendingStep)
		fmt.Println("  >>> Возобновление прямого потока саги: запуск шага Delivery! <<<")
	} else {
		fmt.Printf("  [RECONCILIATION RESULT] Платежа в банке нет. Запуск компенсации шага %s...\n",
			saga.LastKnownOK)
	}
}

func main() {
	hanging := HangingSaga{
		SagaID:      "SAGA-CRASH-404",
		LastKnownOK: "ReserveStock",
		PendingStep: "ProcessPayment",
	}

	RecoverCrashedSaga(hanging)
}
```

ℹ️ Процедура Reconciliation Probe для устранения неопределенности зависшего шага

## Под капотом

В распределенных транзакциях самое опасное состояние — не ошибка, а **неопределенность (In-Doubt State)**. Если упавший оркестратор без зондирования статуса запустит компенсацию склада, а банк тем временем спишет 100,000 рублей, система окажется в ситуации, когда деньги у клиента списаны, а товар со склада продан другому человеку. Только вызов метода проверки статуса по идемпотентному ключу устраняет неопределенность.

## Подводные камни

1. **Предположение, что таймаут равен отказу**: Считать, что если ответ не пришел, то списание не произошло — фатальное заблуждение.
2. **Отсутствие метода проверки статуса во внешнем сервисе**: Каждый внешний сервис в Саге обязан предоставлять read-only эндпоинт `GetStatus(key)`.

## На собеседовании

В платежных шлюзах Яндекса и Авито: 'Что делать, если внешний сервис банка не поддерживает метод проверки статуса платежа по ключу?' Ответ: Если банк не умеет отдавать статус, операция классифицируется как высокорисковая. Оркестратор отправляет транзакцию на ручной разбор (Manual Review) с автоматической блокировкой заказа до получения банковской выписки в конце расчетного дня.
