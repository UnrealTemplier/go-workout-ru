# Параллельные шаги в Оркестраторе: одновременный вызов Payment и Inventory через goroutines

## Условие

### Исходная формулировка

**[Параллельные шаги]**: В Оркестраторе реализуйте шаг, где Payment и Inventory вызываются *параллельно* (через `errgroup`). Если хоть один упал, запускай компенсацию для тех, что уже успели выполниться.

## Теория

При оформлении заказа в высоконагруженных системах шаги `HoldPayment` (блокировка денег) и `ReserveInventory` (блокировка остатка) могут запускаться одновременно.

Схема работы параллельного шага оркестратора:
1. Оркестратор порождает две параллельные горутины.
2. Первая горутина отправляет gRPC-запрос в `PaymentService`.
3. Вторая горутина отправляет gRPC-запрос в `InventoryService`.
4. Координатор ожидает завершения обоих запросов через `sync.WaitGroup` или канал результатов.
5. Если обе операции успешны -> переход к доставке.
6. Если хотя бы одна упала -> запуск компенсирующей транзакции для той, которая завершилась успехом.

## Решение по шагам

1. Опишите интерфейсы удаленных сервисов Payment и Inventory.
2. Реализуйте параллельный вызов с агрегацией результатов.
3. Смоделируйте успешное списание и отказ склада.
4. Докажите вызов компенсации платежа.
5. Протестируйте корректность параллельного исполнения.

## Код решения

**`parallel_orchestrator.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type StepOutcome struct {
	Name    string
	Success bool
	Err     error
}

func ExecuteParallelPhase(ctx context.Context, orderID string) error {
	var wg sync.WaitGroup
	outcomes := make(chan StepOutcome, 2)

	fmt.Printf("[Orchestrator %s] Старт параллельной фазы: Payment + Inventory...\n", orderID)

	// Ветка 1: Payment (Успех)
	wg.Add(1)
	go func() {
		defer wg.Done()
		time.Sleep(60 * time.Millisecond)
		fmt.Println("  -> [PaymentService] Средства захолдированы (SUCCESS)")
		outcomes <- StepOutcome{Name: "Payment", Success: true}
	}()

	// Ветка 2: Inventory (Сбой: товара нет!)
	wg.Add(1)
	go func() {
		defer wg.Done()
		time.Sleep(90 * time.Millisecond)
		fmt.Println("  -> [InventoryService] СБОЙ: Нужный размер обуви отсутствует!")
		outcomes <- StepOutcome{Name: "Inventory", Success: false, Err: fmt.Errorf("out of stock")}
	}()

	wg.Wait()
	close(outcomes)

	var failed bool
	var toRollback []string

	for out := range outcomes {
		if !out.Success {
			failed = true
		} else {
			toRollback = append(toRollback, out.Name)
		}
	}

	if failed {
		fmt.Println("\n>>> Фаза завершилась сбоем! Запуск компенсации успешных веток: <<<")
		for _, name := range toRollback {
			if name == "Payment" {
				fmt.Println("  <- [COMPENSATION] Аннулирование холда средств в банке!")
			}
			if name == "Inventory" {
				fmt.Println("  <- [COMPENSATION] Снятие брони со склада!")
			}
		}
		return fmt.Errorf("parallel phase aborted")
	}

	fmt.Println("Параллельная фаза успешно завершена!")
	return nil
}

func main() {
	_ = ExecuteParallelPhase(context.Background(), "ORD-PARALLEL-99")
}
```

ℹ️ Параллельный вызов сервисов в оркестраторе с селективным откатом успешных веток

## Под капотом

Параллельный запуск шагов сокращает P99 Latency оформления заказа вдвое. Если среднее время ответа банка 150 мс, а склада 120 мс, при последовательном выполнении пользователь ждет \(150 + 120 = 270\) мс. При параллельном выполнении пользователь ждет \(\max(150, 120) = 150\) мс, что дает колоссальный выигрыш в конверсии покупок.

## Подводные камни

1. **Блокировка горутин при небуферизированном канале**: Если канал `outcomes` не буферизирован, горутина может зависнуть при аварийном выходе из функции.
2. **Гонка при обновлении общего состояния**: Результаты веток обязаны передаваться через потокобезопасные каналы или под защитой `sync.Mutex`.

## На собеседовании

В высоконагруженном e-commerce (Wildberries, Ozon): 'Почему нельзя параллелить абсолютно все шаги саги?' Ответ: Нельзя параллелить шаги, имеющие причинно-следственную зависимость. Например, нельзя параллельно бронировать курьера и списывать деньги: если у покупателя нет денег на карте, курьерская служба уже получит заявку и понесет логистические расходы.
