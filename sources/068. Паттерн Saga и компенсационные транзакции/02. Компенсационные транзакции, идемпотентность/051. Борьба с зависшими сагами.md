### Исходная формулировка

**Борьба с "зависшими" сагами (Saga Janitor/Supervisor)**: Что делать, если один из сервисов-участников саги завис и не вернул ни успешный ответ, ни ошибку? Напишите фонового демона-наблюдателя (Janitor Task) в Go, который раз в минуту сканирует таблицу состояний саг в базе данных. Если сага находится в промежуточном состоянии (например, `PaymentCompleted`) дольше 5 минут, демон должен принудительно перевести сагу в режим компенсации (`RollingBack`) и запустить отмену транзакций.

## Теория

Даже при идеальном коде оркестратора внешние сервисы могут 'залипать' на часы из-за сетевых сбоев, дэдлоков в базах данных или падений инфраструктуры.

Паттерн **Saga Janitor (Дворник / Супервизор Саг)**:
- Фоновый автономный процесс, запускаемый каждые \(N\) минут (Cron / Background Goroutine).
- Сканирует таблицу саг на предмет аномалий:
  - Сага находится в статусе `IN_PROGRESS` дольше допустимого порога (например, более 10 минут).
  - Сага находится в статусе `COMPENSATING` дольше 5 минут (завис откат).
- Действия Janitor:
  1. Детектирует зависший шаг.
  2. Принудительно разрывает процесс.
  3. Инициирует повторный запуск компенсации либо переводит в статус `MANUAL_INTERVENTION`.
  4. Отправляет метрику `stale_sagas_detected_total` в Prometheus.

## Решение по шагам

1. Создайте структуру сервиса `SagaJanitor`.
2. Реализуйте алгоритм сканирования зависших записей по таймауту неактивности.
3. Добавьте логику принудительного прерывания и эскалации.
4. Продемонстрируйте обнаружение и очистку зависшей саги.
5. Протестируйте реакцию мониторинга.

## Код решения

**`saga_janitor.go`**

```go
package main

import (
	"fmt"
	"time"
)

type TrackedSaga struct {
	ID        string
	Status    string
	UpdatedAt time.Time
}

type SagaJanitor struct {
	maxAllowedDuration time.Duration
}

func (j *SagaJanitor) Sweep(sagas []*TrackedSaga) {
	fmt.Println("[Janitor] Сканирование базы на предмет зависших саг...")
	now := time.Now()

	for _, saga := range sagas {
		if saga.Status == "IN_PROGRESS" || saga.Status == "COMPENSATING" {
			stalledTime := now.Sub(saga.UpdatedAt)
			if stalledTime > j.maxAllowedDuration {
				fmt.Printf("[JANITOR ALERT] Обнаружена зависшая сага %s! Простаивает: %v (Лимит: %v)\n",
					saga.ID, stalledTime, j.maxAllowedDuration)

				// Принудительное действие супервизора
				saga.Status = "FAILED_BY_SUPERVISOR"
				saga.UpdatedAt = now
				fmt.Printf("[Janitor Action] Сага %s принудительно отменена, ресурсы освобождены!\n", saga.ID)
			}
		}
	}
}

func main() {
	janitor := &SagaJanitor{maxAllowedDuration: 5 * time.Minute}

	// База данных саг
	records := []*TrackedSaga{
		{ID: "saga-ok-1", Status: "IN_PROGRESS", UpdatedAt: time.Now().Add(-1 * time.Minute)},
		{ID: "saga-stuck-99", Status: "IN_PROGRESS", UpdatedAt: time.Now().Add(-15 * time.Minute)}, // Зависла на 15 мин!
		{ID: "saga-done-2", Status: "COMPLETED", UpdatedAt: time.Now().Add(-30 * time.Minute)},
	}

	janitor.Sweep(records)

	fmt.Printf("\nИтог: Сага stuck-99 переведена в статус: %s\n", records[1].Status)
}
```

ℹ️ Фоновый супервизор (Saga Janitor) для автоматической ликвидации зависших транзакций

## Под капотом

В распределенных СУБД фоновый сборщик Janitor выполняет SQL-запрос пачками (Batching):
`SELECT id FROM saga_instances WHERE status = 'IN_PROGRESS' AND updated_at < NOW() - INTERVAL '10 minutes' LIMIT 100;`.
Ограничение `LIMIT 100` критически важно: если из-за глобальной сетевой аварии зависнут 100,000 саг, попытка обновить их одним запросом заблокирует таблицу на минуты.

## Подводные камни

1. **Убийство живых длинных саг**: Если бизнес-процесс легально может длиться 3 дня (например, ожидание ручного подтверждения кредитного менеджера), агрессивный Janitor с таймаутом 10 минут разрушит транзакцию.
2. **Слишком частый запуск без паузы**: Постоянный скан БД каждые 500 мс создаст высокую утилизацию диска.

## На собеседовании

В архитектуре Ozon и Wildberries миллионы заказов обрабатываются ежесуточно. Вопрос: 'Как защитить систему от ситуации, когда Janitor ошибочно отменяет заказ, ответ по которому уже летит по сети?' Ответ: Механизм Fencing Tokens и двухфазной отмены: Janitor сначала переводит статус в `MARK_FOR_TERMINATION` и ждет grace period (30 секунд); если новых подтверждений нет, инициируется окончательный откат.
