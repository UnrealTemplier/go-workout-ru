### Исходная формулировка

**Saga tracking в Choreography**: В Choreography нет централизованного state. Как отследить progress? ИспользуйтеSaga ID в каждом event и aggregate state из events.

## Теория

Главная претензия к архитектуре хореографии — 'невидимость' текущего состояния процесса: события летают между 10 сервисами, но ни один сервис не знает, на какой стадии находится заказ прямо сейчас.

Решение проблемы — паттерн **Saga State Tracker (Агрегатор состояния саги)**:
1. Выделенный микросервис `SagaTrackerService` пассивно слушает ВСЕ топики событий (`orders.*`, `payments.*`, `inventory.*`).
2. При поступлении события трекер обновляет агрегированную проекцию (Read Model / CQRS Projection) в быстром хранилище (PostgreSQL / MongoDB):
   `{ saga_id: "S-1", current_step: "PAYMENT_DONE", history: [...], started_at: ... }`.
3. Фронтенд и служба поддержки делают запросы `GET /sagas/{id}` исключительно к трекеру, получая полную картину происходящего в реальном времени.

## Решение по шагам

1. Создайте проекцию состояния саги `SagaView`.
2. Реализуйте сервис трекера, слушающий доменные события.
3. Обновляйте агрегированное состояние при каждом поступившем событии.
4. Предоставьте API чтения текущего прогресса.
5. Продемонстрируйте отображение сквозного статуса заказа.

## Код решения

**`saga_tracker.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type SagaView struct {
	SagaID       string    `json:"saga_id"`
	Status       string    `json:"status"`
	CurrentPhase string    `json:"current_phase"`
	EventsCount  int       `json:"events_count"`
	LastUpdated  time.Time `json:"last_updated"`
}

type SagaTrackerService struct {
	mu         sync.RWMutex
	projections map[string]*SagaView
}

func NewSagaTrackerService() *SagaTrackerService {
	return &SagaTrackerService{projections: make(map[string]*SagaView)}
}

// IngestEvent обрабатывает любые события системы и обновляет общую картину
func (t *SagaTrackerService) IngestEvent(sagaID, eventType, status string) {
	t.mu.Lock()
	defer t.mu.Unlock()

	view, exists := t.projections[sagaID]
	if !exists {
		view = &SagaView{SagaID: sagaID, Status: "ACTIVE"}
		t.projections[sagaID] = view
	}

	view.CurrentPhase = eventType
	view.Status = status
	view.EventsCount++
	view.LastUpdated = time.Now()

	fmt.Printf("[SagaTracker] Сага %s обновлена: Фаза='%s', Статус='%s' (Событий: %d)\n",
		sagaID, view.CurrentPhase, view.Status, view.EventsCount)
}

func (t *SagaTrackerService) GetSagaStatus(sagaID string) (*SagaView, bool) {
	t.mu.RLock()
	defer t.mu.RUnlock()
	v, ok := t.projections[sagaID]
	return v, ok
}

func main() {
	tracker := NewSagaTrackerService()
	sagaID := "SAGA-ORDER-CHOREO-555"

	// Имитация событий, прилетающих из разных топиков Kafka
	tracker.IngestEvent(sagaID, "OrderCreated", "ACTIVE")
	tracker.IngestEvent(sagaID, "PaymentSucceeded", "ACTIVE")
	tracker.IngestEvent(sagaID, "InventoryReserved", "COMPLETED")

	// Клиентский запрос статуса (CQRS Read)
	status, _ := tracker.GetSagaStatus(sagaID)
	fmt.Printf("\n[UI Dashboard Query] Текущий статус саги: %s | Финальная фаза: %s | Всего шагов: %d\n",
		status.Status, status.CurrentPhase, status.EventsCount)
}
```

ℹ️ CQRS проекция состояния хореографической Саги для UI и мониторинга

## Под капотом

Трекер состояния саги является классической реализацией паттерна CQRS (Command Query Responsibility Segregation). Команды и бизнес-транзакции выполняются распределенно, а чтение состояния консолидируется в денормализованной таблице трекера, обеспечивая ответ на `GET /order/status` за 1-2 миллисекунды без распределенных джойнов.

## Подводные камни

1. **Трекер влияет на бизнес-процесс**: Трекер должен быть строго пассивным наблюдателем. Ни в коем случае нельзя делать бизнес-логику зависимой от доступности трекера.
2. **Рассинхронизация при потере событий**: Если трекер упал, он обязан дочитать все пропущенные события из Kafka по оффсету.

## На собеседовании

В архитектурных комитетах BigTech (Яндекс, Авито): 'Как трекер узнает, что сага зависла, если хореография не имеет центрального таймера?' Ответ: Трекер ведет мониторинг `updated_at`. Если для активной саги не поступало новых событий более 10 минут, трекер помечает ее как `STALLED` и отправляет событие в топик алертов для вмешательства дежурного инженера.
