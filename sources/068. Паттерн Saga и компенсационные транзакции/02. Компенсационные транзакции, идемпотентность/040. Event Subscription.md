# Event Subscription: подписка на события через Consumer Groups и балансировка партиций

## Условие

40. **Event subscription**: Каждый сервис подписывается на релевантные события через consumer groups.

### Исходная формулировка

**Event subscription**: Каждый сервис подписывается на релевантные события через consumer groups.

## Теория

В распределенной событийной Саге сервисы подписываются на доменные топики через **Consumer Groups (Группы потребителей)**:
1. Несколько реплик одного микросервиса (например, 3 пода `PaymentService`) объединяются в группу `payment-saga-workers`.
2. Брокер (Kafka/RabbitMQ) распределяет партиции топика между подами группы: каждое сообщение обрабатывается ровно одной репликой.
3. При падении одного пода происходит **Ребалансировка (Rebalance)**, и его партиции передаются выжившим подам.

Правила надежного консьюминга:
- Ручной коммит смещений (Manual Acknowledgment / Manual Offset Commit): оффсет коммитится строго **ПОСЛЕ** успешного завершения локальной транзакции в базе данных.
- Потокобезопасная параллельная обработка сообщений внутри инстанса.

## Решение по шагам

1. Создайте эмуляцию Consumer Group с распределением сообщений между воркерами.
2. Реализуйте ручное подтверждение обработки сообщения (`Ack()`).
3. Смоделируйте сбой одного воркера и передачу сообщения другому воркеру.
4. Продемонстрируйте исключение потери сообщений.
5. Протестируйте параллельную обработку заказов.

## Код решения

**`consumer_group.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type KafkaMessage struct {
	Partition int
	Offset    int64
	OrderID   string
	Payload   string
}

type ConsumerWorker struct {
	ID        int
	GroupID   string
	msgChan   chan KafkaMessage
	commitLog map[int64]bool
	mu        sync.Mutex
}

func (w *ConsumerWorker) Start(ctx context.Context) {
	fmt.Printf("[Worker %d (%s)] Запущен и слушает партиции...\n", w.ID, w.GroupID)
	for {
		select {
		case <-ctx.Done():
			return
		case msg := <-w.msgChan:
			w.processMessage(msg)
		}
	}
}

func (w *ConsumerWorker) processMessage(msg KafkaMessage) {
	fmt.Printf("  [Worker %d] Начало обработки заказа %s (Offset: %d)...\n", w.ID, msg.OrderID, msg.Offset)
	time.Sleep(50 * time.Millisecond) // Имитация записи в БД

	// РУЧНОЙ КОММИТ ОФФСЕТА (Manual Commit)
	w.mu.Lock()
	w.commitLog[msg.Offset] = true
	w.mu.Unlock()

	fmt.Printf("  [Worker %d] УСПЕХ: Заказ %s зафиксирован, Offset %d закоммичен в Kafka!\n",
		w.ID, msg.OrderID, msg.Offset)
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
	defer cancel()

	w1 := &ConsumerWorker{ID: 1, GroupID: "payment-workers", msgChan: make(chan KafkaMessage, 10), commitLog: make(map[int64]bool)}
	w2 := &ConsumerWorker{ID: 2, GroupID: "payment-workers", msgChan: make(chan KafkaMessage, 10), commitLog: make(map[int64]bool)}

	go w1.Start(ctx)
	go w2.Start(ctx)

	// Имитация распределения сообщений по партициям (Round-robin)
	messages := []KafkaMessage{
		{Partition: 0, Offset: 101, OrderID: "ORD-A", Payload: "Pay 1000"},
		{Partition: 1, Offset: 201, OrderID: "ORD-B", Payload: "Pay 2500"},
		{Partition: 0, Offset: 102, OrderID: "ORD-C", Payload: "Pay 4000"},
		{Partition: 1, Offset: 202, OrderID: "ORD-D", Payload: "Pay 7500"},
	}

	for i, msg := range messages {
		if i%2 == 0 {
			w1.msgChan <- msg
		} else {
			w2.msgChan <- msg
		}
	}

	time.Sleep(200 * time.Millisecond)
}
```

ℹ️ Параллельная обработка сообщений саги в Consumer Group с ручным коммитом оффсетов

## Под капотом

В драйвере `segmentio/kafka-go` или `confluent-kafka-go` критически важно отключать `AutoCommit: true`. При автокоммите библиотека коммитит оффсет каждые \(N\) миллисекунд по таймеру. Если под упадет между забором сообщения из сокета и записью в базу данных, оффсет окажется закоммиченным, а бизнес-операция не выполнится — заказ будет потерян без следа.

## Подводные камни

1. **Блокировка ребалансировки (Long Processing)**: Если воркер обрабатывает сообщение дольше, чем `max.poll.interval.ms` (по умолчанию 5 минут в Kafka), координатор сочтет воркер мертвым и запустит ребалансировку всего кластера.
2. **Коммит до завершения транзакции БД**: Если послать `Commit()` до вызова `tx.Commit()`, падение базы вызовет потерю транзакции.

## На собеседовании

В инфраструктуре Wildberries и Ozon тысячи подов консьюмят миллиарды событий Kafka. Вопрос: 'Что произойдет при аварийном падении одного пода консьюмер группы во время ребалансировки?' Ответ: Новые поды подхватывают партиции с последнего закоммиченного оффсета. Те сообщения, которые упавший под успел обработать, но не успел закоммитить, будут прочитаны заново. Поэтому обработчик каждого события ОБЯЗАН быть строго идемпотентным.
