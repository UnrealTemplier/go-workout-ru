# Duplicate Execution Protection: многоуровневая защита от дублирования шагов Саги

### Исходная формулировка

## Теория

Защита от дублирующего выполнения (Duplicate Execution Protection) — венец надежности Саги.

Уровни защиты от дублирования:
1. **Транспортный уровень**: Заголовок `Idempotency-Key: <saga_id>:<step_name>` в HTTP/gRPC запросах.
2. **Уровень хранилища (Database Unique Constraint)**: Уникальный индекс `CREATE UNIQUE INDEX ON step_executions (saga_id, step_name)`.
3. **Уровень брокера**: Дедупликация по `Nats-Msg-Id` или Kafka Producer Idempotence (`enable.idempotence = true`).
4. **Уровень бизнес-логики**: Проверка статуса сущности перед мутацией (`WHERE status = 'EXPECTED_STATUS'`).

Соблюдение этих 4 уровней гарантирует, что даже при параллельной доставке 10 дубликатов запроса действие выполнится строго один раз.

## Решение по шагам

1. Спроектируйте композитный ключ дедупликации `sagaID + ":" + stepName`.
2. Реализуйте многоуровневую проверку выполнения.
3. Смоделируйте одновременный конкурентный запуск одного шага из 5 горутин.
4. Докажите, что действие выполнилось ровно 1 раз.
5. Протестируйте отсутствие состояния гонки (Data Race).

## Код решения

**`duplicate_protection.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type ExecutionRegistry struct {
	mu           sync.Mutex
	executedKeys map[string]bool
	actualExecs  atomic.Int32
}

func NewExecutionRegistry() *ExecutionRegistry {
	return &ExecutionRegistry{executedKeys: make(map[string]bool)}
}

// ExecuteOnce гарантирует выполнение целевого действия строго 1 раз
func (r *ExecutionRegistry) ExecuteOnce(sagaID, stepName string, action func()) {
	key := fmt.Sprintf("%s:%s", sagaID, stepName)

	r.mu.Lock()
	if r.executedKeys[key] {
		r.mu.Unlock()
		// Дубликат отсечен!
		return
	}
	r.executedKeys[key] = true
	r.mu.Unlock()

	// Выполнение целевого действия
	r.actualExecs.Add(1)
	action()
}

func main() {
	registry := NewExecutionRegistry()
	sagaID := "SAGA-FINANCIAL-TRANSFER-900"
	step := "DeductFunds"

	var wg sync.WaitGroup
	// Симуляция 10 параллельных запросов от ретраев брокера и оркестратора
	for i := 1; i <= 10; i++ {
		wg.Add(1)
		go func(workerID int) {
			defer wg.Done()
			registry.ExecuteOnce(sagaID, step, func() {
				fmt.Printf("[CRITICAL ACTION] Реальное списание средств со счета (Воркер #%d)!\n", workerID)
			})
		}(i)
	}

	wg.Wait()
	fmt.Printf("\nИтог: Из 10 попыток действие реально выполнено ровно %d раз!\n",
		registry.actualExecs.Load())
}
```

ℹ️ Многопоточная защита от дублирующего выполнения шага Саги

## Под капотом

В распределенной среде вместо `sync.Mutex` используется распределенная блокировка Redis `SET lock:saga_id:step_name true NX EX 30` или атомарный `INSERT` в PostgreSQL с обработкой `ON CONFLICT DO NOTHING`. Это гарантирует абсолютную дедупликацию даже между разными физическими серверами в разных дата-центрах.

## Подводные камни

1. **Дедупликация только по `order_id`**: Если дедуплицировать только по `order_id`, шаг списания заблокирует шаг доставки, потому что у них один и тот же `order_id`! Ключ ОБЯЗАН включать имя шага: `order_id + ":" + step_name`.
2. **Проверка без блокировки (Check-Then-Act race)**: Вызов `exists = check()` с последующим `if !exists { do() }` без атомарной синхронизации приведет к гонке данных.

## На собеседовании

В банковских системах Тинькофф, Сбер и Ozon: 'Каковы критерии успешного проектирования шагов Саги на собеседовании System Design?' Эталонный ответ: 'Каждый шаг Саги обязан быть: 1) Атомарным локально, 2) Строго идемпотентным по ключу `saga_id + step`, 3) Снабженным зеркальной компенсирующей транзакцией, 4) Защищенным от таймаутов через дедлайны контекста, и 5) Зафиксированным в персистентном Saga Log'.
