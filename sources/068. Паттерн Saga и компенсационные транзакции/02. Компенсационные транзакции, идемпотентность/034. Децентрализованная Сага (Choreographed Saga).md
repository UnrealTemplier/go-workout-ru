# Децентрализованная Сага (Choreographed Saga): маршрутизация событий через NATS JetStream

## Условие

34. **Децентрализованная Сага (Choreographed Saga)**: Реализуйте хореографическую сагу без центрального оркестратора на базе брокера сообщений (Kafka или NATS JetStream).
    * Сервис `OrderService` создает заказ и публикует событие `OrderCreated`.
    * Сервис `PaymentService` слушает `OrderCreated`, списывает средства и публикует `PaymentAuthorized` (или `PaymentFailed`).
    * Сервис `InventoryService` слушает `PaymentAuthorized`, бронирует товар и публикует `InventoryAllocated`. Если бронирование не удалось — он публикует `InventoryAllocationFailed`.
    * Настройте `PaymentService` на прослушивание события `InventoryAllocationFailed` для автоматического запуска компенсации списания денег.

### Исходная формулировка

## Теория

При построении децентрализованной Саги брокер сообщений выступает транспортной шиной с гарантиями надежности. Современный брокер **NATS JetStream** сочетает в себе сверхнизкие задержки (микросекунды) и персистентную сохранность сообщений на диске.

Спецификация маршрутизации:
- Топики разделяются по префиксам: `orders.v1.created`, `payments.v1.succeeded`, `payments.v1.failed`.
- Сервисы подписываются с использованием Consumer Groups (`Durable Pull Consumers`), гарантируя, что событие обработает ровно одна реплика сервиса.
- Каждое сообщение снабжается заголовком `Nats-Msg-Id` для дедупликации на уровне брокера.

## Решение по шагам

1. Опишите доменные структуры событий заказа.
2. Реализуйте диспетчер событий на базе каналов Go (эмуляция NATS JetStream).
3. Настройте дедупликацию по `MsgID`.
4. Продемонстрируйте прохождение цепочки событий.
5. Проверьте поведение при сетевых ретраях брокера.

## Код решения

**`nats_choreography.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type JetStreamMsg struct {
	MsgID   string
	Subject string
	Data    string
}

type MockJetStream struct {
	mu          sync.Mutex
	seenMsgIDs  map[string]bool
	subscribers map[string][]func(JetStreamMsg)
}

func NewMockJetStream() *MockJetStream {
	return &MockJetStream{
		seenMsgIDs:  make(map[string]bool),
		subscribers: make(map[string][]func(JetStreamMsg)),
	}
}

func (js *MockJetStream) Subscribe(subject string, handler func(JetStreamMsg)) {
	js.mu.Lock()
	js.subscribers[subject] = append(js.subscribers[subject], handler)
	js.mu.Unlock()
}

func (js *MockJetStream) Publish(msg JetStreamMsg) {
	js.mu.Lock()
	// Дедупликация на стороне брокера NATS
	if js.seenMsgIDs[msg.MsgID] {
		fmt.Printf("[NATS JetStream] ДУБЛИКАТ MsgID=%s отброшен брокером!\n", msg.MsgID)
		js.mu.Unlock()
		return
	}
	js.seenMsgIDs[msg.MsgID] = true
	handlers := js.subscribers[msg.Subject]
	js.mu.Unlock()

	fmt.Printf("[NATS JetStream] Опубликовано: %s (MsgID: %s)\n", msg.Subject, msg.MsgID)
	for _, h := range handlers {
		go h(msg)
	}
}

func main() {
	js := NewMockJetStream()

	// 1. PaymentService слушает order.created
	js.Subscribe("order.created", func(m JetStreamMsg) {
		fmt.Printf("  -> [PaymentService] Обработка %s\n", m.Data)
		js.Publish(JetStreamMsg{
			MsgID:   "pay-succ-9001",
			Subject: "payment.succeeded",
			Data:    m.Data,
		})
	})

	// 2. InventoryService слушает payment.succeeded
	js.Subscribe("payment.succeeded", func(m JetStreamMsg) {
		fmt.Printf("  -> [InventoryService] Склад зарезервирован для %s\n", m.Data)
	})

	// Публикация заказа
	js.Publish(JetStreamMsg{MsgID: "ord-evt-1", Subject: "order.created", Data: "Order #5544"})

	// Повторная отправка того же сообщения (сетевой дубль)
	js.Publish(JetStreamMsg{MsgID: "ord-evt-1", Subject: "order.created", Data: "Order #5544"})

	time.Sleep(100 * time.Millisecond)
}
```

ℹ️ Децентрализованная маршрутизация событий Саги с дедупликацией MsgID

## Под капотом

Встроенная дедупликация в NATS JetStream работает по заголовку `Nats-Msg-Id`. Брокер запоминает этот ID в скользящем окне времени (`duplicate_window = 2m`). Если в течение 2 минут продюсер повторно отправляет сообщение с тем же `MsgID`, NATS возвращает подтверждение `+ACK`, но не доставляет дубликат консьюмерам, снимая нагрузку с базы данных сервисов.

## Подводные камни

1. **Короткое окно дедупликации**: Если `duplicate_window` меньше интервала ретраев продюсера, дубликат все равно прорвется к консьюмерам.
2. **Смешивание версий схем**: Изменение формата полезной нагрузки без версионирования топика (`orders.v2.created`) сломает старые реплики сервисов.

## На собеседовании

В финтех-платформах с высокими требованиями к latency (Тинькофф, Bybit): 'Почему NATS JetStream часто выбирают вместо Kafka для хореографии?' Ответ: NATS написан на Go, потребляет на порядок меньше памяти, не требует ZooKeeper/KRaft и обеспечивает latency на уровне 50–100 микросекунд против миллисекунд в Kafka, что критично для real-time транзакций.
