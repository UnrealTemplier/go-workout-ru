# Сага с тайм-аутами и автоматической компенсацией: защита от зависания шагов (10 сек)

## Условие

### Исходная формулировка

**Сага с таймаутами и автоматической компенсацией.**: Добавьте в оркестратор тайм-аут для каждого шага. Если сервис не отвечает за заданное время, автоматически запускайте компенсацию. Реализуйте это через `context.WithTimeout` и каналы.

## Теория

Автоматическая компенсация по таймауту — ключевой защитный механизм распределенной транзакции:
- Если сервис-исполнитель (например, `PaymentService`) не ответил в течение 10 секунд, оркестратор не должен ждать вечно.
- Оркестратор прерывает вызов по `context.DeadlineExceeded`.
- Сага немедленно переводится в состояние `ROLLING_BACK`.
- Инициируется откат всех шагов, которые успели завершиться до момента зависания.

## Решение по шагам

1. Создайте структуру саги с лимитом времени 10 секунд на шаг.
2. Смоделируйте успешное выполнение первого шага.
3. Смоделируйте зависание второго шага на 15 секунд.
4. Перехватите срабатывание 10-секундного таймаута.
5. Запустите автоматический откат первого шага.

## Код решения

**`timeout_compensation_demo.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type StepDef struct {
	Name       string
	Action     func(ctx context.Context) error
	Compensate func()
}

func main() {
	steps := []StepDef{
		{
			Name: "1. LockWarehouse",
			Action: func(ctx context.Context) error {
				fmt.Println("  [Step 1] Склад заблокирован (OK)")
				return nil
			},
			Compensate: func() {
				fmt.Println("  <- [COMPENSATION] Снятие блокировки со склада!")
			},
		},
		{
			Name: "2. BankPayment",
			Action: func(ctx context.Context) error {
				fmt.Println("  [Step 2] Ожидание ответа от банка (имитация зависания)...")
				select {
				case <-time.After(15 * time.Second): // Завис на 15 сек
					return nil
				case <-ctx.Done():
					return ctx.Err() // Превышен таймаут шага!
				}
			},
			Compensate: func() {
				fmt.Println("  <- [COMPENSATION] Отмена банковской операции")
			},
		},
	}

	stepTimeout := 1 * time.Second // Лимит таймаута (для демо 1 сек вместо 10)
	var executed []StepDef

	for _, step := range steps {
		ctx, cancel := context.WithTimeout(context.Background(), stepTimeout)
		err := step.Action(ctx)
		cancel()

		if err != nil {
			if errors.Is(err, context.DeadlineExceeded) {
				fmt.Printf("\n[ALERT] Шаг '%s' ПРЕВЫСИЛ ЛИМИТ ТАЙМАУТА (%v)!\n", step.Name, stepTimeout)
			} else {
				fmt.Printf("\n[ALERT] Шаг '%s' завершился ошибкой: %v\n", step.Name, err)
			}

			fmt.Println(">>> ЗАПУСК АВТОМАТИЧЕСКОГО ОТКАТА ВЫПОЛНЕННЫХ ШАГОВ <<<")
			for i := len(executed) - 1; i >= 0; i-- {
				executed[i].Compensate()
			}
			return
		}
		executed = append(executed, step)
	}
}
```

ℹ️ Автоматический запуск компенсирующих транзакций при превышении дедлайна шага

## Под капотом

После отмены шага по таймауту банк все же может списать деньги спустя несколько секунд (Slow Network Delay). Поэтому метод компенсации `Compensate` должен использовать тот же `Idempotency-Key` или `TransactionID`, чтобы банковский шлюз зарегистрировал отмену операции, даже если запрос на списание дойдет до него позже отмены (защита от Out-of-Order).

## Подводные камни

1. **Отсутствие отмены контекста (`cancel()`)**: Если не вызвать `cancel()`, таймер контекста останется активным в памяти рантайма Go до истечения дедлайна, вызывая утечки ресурсов.
2. **Одинаковый таймаут для всех шагов**: Простые операции с БД должны иметь таймаут 1-2 сек, а межбанковские вызовы — 10-15 сек.

## На собеседовании

В платежных системах Т-Банка и Яндекс Сплит: 'Что произойдет, если запрос оплаты упал по таймауту 10 сек, но деньги у клиента реально списались?' Ответ: Это классический partial failure. Компенсация шлет запрос `ReversePayment` по `order_id`. Если шлюз успел списать деньги, он делает возврат; если не успел — помечает операцию как отмененную и отклоняет запоздалое списание.
