## Теория

Рассмотрим классический трехзвенный бизнес-процесс:
1. Шаг 1: `OrderService.CreateOrder` -> Создан черновик заказа.
2. Шаг 2: `PaymentService.Charge` -> Списаны средства.
3. Шаг 3: `InventoryService.Reserve` -> Ошибка резервирования (товара нет).

Для возврата в согласованное состояние оркестратор обязан выполнить каскадный откат ровно двух успешно выполненных шагов в обратном порядке:
1. Шаг 2' (Компенсация): `PaymentService.Refund` (возврат денег).
2. Шаг 1' (Компенсация): `OrderService.CancelOrder` (отмена заказа).

Если в процессе отката один из сервисов недоступен, оркестратор обязан удерживать сагу в статусе `COMPENSATING` и повторять вызовы до подтверждения.

## Решение по шагам

1. Опишите структуру Саги из 3 шагов.
2. Реализуйте пошаговое выполнение с фиксацией выполненных этапов.
3. Смоделируйте ошибку на третьем шаге (Inventory).
4. Выполните каскадную компенсацию в порядке `Payment -> Order`.
5. Проверьте финальное состояние всех трех микросервисов.

## Код решения

**`three_service_cascade.go`**

```go
package main

import (
	"fmt"
)

type ServiceState struct {
	OrderCreated bool
	PaymentPaid  bool
	StockLocked  bool
}

func main() {
	state := &ServiceState{}
	orderID := "ORD-CASCADE-33"

	fmt.Println("=== Старт трехзвенной саги ===")

	// Шаг 1: Заказ
	state.OrderCreated = true
	fmt.Printf("1. [OrderService] Заказ %s зарегистрирован\n", orderID)

	// Шаг 2: Платеж
	state.PaymentPaid = true
	fmt.Printf("2. [PaymentService] Списано 8,500 руб. для заказа %s\n", orderID)

	// Шаг 3: Склад (СБОЙ!)
	fmt.Printf("3. [InventoryService] СБОЙ: Товар поврежден при комплектации!\n")

	// КАСКАДНЫЙ ОТКАТ
	fmt.Println("\n>>> ЗАПУСК КАСКАДНОЙ КОМПЕНСАЦИИ <<<")

	// Откат шага 2 (Платеж)
	if state.PaymentPaid {
		state.PaymentPaid = false
		fmt.Printf("<- [PaymentService] КОМПЕНСАЦИЯ: 8,500 руб. возвращены на карту покупателя\n")
	}

	// Откат шага 1 (Заказ)
	if state.OrderCreated {
		state.OrderCreated = false
		fmt.Printf("<- [OrderService] КОМПЕНСАЦИЯ: Заказ %s аннулирован\n", orderID)
	}

	fmt.Println("\nКаскадный откат успешно завершен: деньги возвращены, заказ отменен.")
}
```

## Под капотом

В распределенных транзакциях откат шагов моделируется правилом LIFO (Last In, First Out). Почему нельзя сначала отменить заказ, а потом вернуть деньги? Потому что в банковской интеграции вызов `Refund` часто требует ссылки на исходный заказ в статусе `PENDING_CANCELLATION`. Если сначала уничтожить заказ, платежный сервис не найдет контекст транзакции.

## Подводные камни

1. **Откат в прямом порядке (FIFO)**: Отмена заказа раньше отмены брони склада может привести к тому, что складской сервис отклонит запрос со словами 'Заказ не существует'.
2. **Паника при частичном откате**: Если откат одного сервиса упал, откат остальных не должен прерываться.

## На собеседовании

В Ozon на системном интервью: 'Как убедиться, что каскадный откат не застрял на середине?' Ответ: Сага имеет метрику `pending_compensations_gauge`. Если компенсация не завершилась за SLA (например, 60 секунд), триггерится алерт в Prometheus, а процесс переходит под контроль фонового Reconciliation Worker.
