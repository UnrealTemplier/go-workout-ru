# Event Publishing: надежная публикация событий в Kafka через Transactional Outbox

## Условие

39. **Event publishing**: Каждый сервис публикует события в Kafka/RabbitMQ после успешного выполнения своей части.

### Исходная формулировка

**Event publishing**: Каждый сервис публикует события в Kafka/RabbitMQ после успешного выполнения своей части.

## Теория

При реализации Саги публикация события в брокер сообщений (Kafka/RabbitMQ) после локального обновления базы данных подвержена **Dual-Write проблеме**:
1. Обновили заказ в PostgreSQL: `UPDATE orders SET status = 'CONFIRMED'`.
2. Пытаемся отправить событие в Kafka: `kafkaProducer.Send(event)`.
3. Если перед шагом 2 сервер перезагрузился (Kill -9) или сеть моргнула — заказ в БД остался оплаченным, но событие в Kafka никогда не попало! Другие сервисы не узнают о завершении заказа.

Решение проблемы — паттерн **Transactional Outbox (Транзакционный Outbox)**:
- Событие сохраняется в таблицу `outbox_events` **в рамках той же самой локальной транзакции PostgreSQL**, что и заказ:
  `BEGIN; UPDATE orders ...; INSERT INTO outbox_events ...; COMMIT;`.
- Фоновый процесс (Debezium CDC или Go-воркер с `SELECT ... FOR UPDATE SKIP LOCKED`) гарантированно вычитывает события из `outbox_events` и отправляет их в Kafka с последующим удалением или пометкой `processed = true`.

## Решение по шагам

1. Опишите структуру транзакции сохранения заказа и outbox-события.
2. Реализуйте имитацию локальной транзакции с гарантией атомарности.
3. Напишите фоновый процесс ретрансляции событий в брокер.
4. Продемонстрируйте гарантию того, что событие публикуется только при успешном коммите.
5. Проверьте обработку сбоев публикации.

## Код решения

**`transactional_outbox.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type OutboxRecord struct {
	ID        int
	Topic     string
	Payload   string
	Processed bool
}

type DatabaseStore struct {
	mu     sync.Mutex
	orders map[string]string
	outbox []OutboxRecord
	nextID int
}

func NewDatabaseStore() *DatabaseStore {
	return &DatabaseStore{orders: make(map[string]string)}
}

// AtomicOrderCreation — атомарная запись заказа и события в одной транзакции
func (db *DatabaseStore) AtomicOrderCreation(orderID, payload string) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Изменение бизнес-сущности
	db.orders[orderID] = "CONFIRMED"

	// 2. Вставка события в таблицу outbox_events
	db.nextID++
	record := OutboxRecord{
		ID:        db.nextID,
		Topic:     "orders.v1.confirmed",
		Payload:   payload,
		Processed: false,
	}
	db.outbox = append(db.outbox, record)

	fmt.Printf("[DB Transaction Committed] Заказ %s сохранен, Outbox событие #%d зафиксировано!\n",
		orderID, record.ID)
	return nil
}

// OutboxPublisherWorker — фоновый процесс отправки в Kafka
func (db *DatabaseStore) OutboxPublisherWorker() {
	db.mu.Lock()
	defer db.mu.Unlock()

	for i := range db.outbox {
		if !db.outbox[i].Processed {
			// Отправка в Kafka брокер
			fmt.Printf("[Kafka Producer] Отправка сообщения #%d в топик '%s': %s\n",
				db.outbox[i].ID, db.outbox[i].Topic, db.outbox[i].Payload)
			db.outbox[i].Processed = true
		}
	}
}

func main() {
	db := NewDatabaseStore()

	// Атомарное оформление 2 заказов
	_ = db.AtomicOrderCreation("ORD-OUTBOX-1", `{"order_id":"ORD-OUTBOX-1","amount":5000}`)
	_ = db.AtomicOrderCreation("ORD-OUTBOX-2", `{"order_id":"ORD-OUTBOX-2","amount":12000}`)

	fmt.Println("\nЗапуск фонового Outbox Relay...")
	db.OutboxPublisherWorker()
}
```

ℹ️ Паттерн Transactional Outbox для атомарной публикации событий Саги

## Под капотом

Атомарность гарантируется механизмом WAL (Write-Ahead Logging) базы данных PostgreSQL. Запись в таблицу `orders` и вставка в `outbox_events` попадают в один сегмент WAL-лога. Если нода питания отключится, при восстановлении СУБД либо закоммитит обе записи, либо откатит обе, исключая рассинхронизацию между базой данных и брокером сообщений.

## Подводные камни

1. **Публикация в Kafka внутри блока транзакции БД**: Сетевой вызов брокера прямо внутри `BEGIN ... COMMIT` может заблокировать транзакцию БД на 30 секунд при зависании сети, исчерпав пул соединений PostgreSQL.
2. **Разрастание таблицы `outbox_events`**: Если не удалять обработанные записи, таблица вырастет до сотен миллионов строк. Применяйте партиционирование по дням или удаление батчами.

## На собеседовании

В микросервисной архитектуре Wildberries, Lamoda, Авито Transactional Outbox — фундаментальный паттерн. Вопрос: 'Как реализовать Outbox с нулевой нагрузкой на мастер-базу данных?' Ответ: Использовать Change Data Capture (CDC) через Debezium: сервис ничего не поллит, Debezium читает WAL-лог PostgreSQL напрямую и асинхронно стримит изменения таблицы `outbox_events` в Kafka.
