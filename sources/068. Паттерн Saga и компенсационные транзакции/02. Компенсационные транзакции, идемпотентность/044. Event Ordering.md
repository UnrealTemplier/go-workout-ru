# Event Ordering: гарантированный порядок событий через Partition Key в Kafka

## Условие

44. **Event ordering**: Обеспечьте ordering событий для одной сущности (order_id) через Kafka partition key.

### Исходная формулировка

**Event ordering**: Обеспечьте ordering событий для одной сущности (order_id) через Kafka partition key.

## Теория

В распределенной событийной архитектуре порядок обработки событий критичен:
Если событие `OrderCancelled` обгонит `OrderCreated`, сервис склада попытается отменить несуществующий заказ, а затем создаст заказ и заблокирует товар навсегда!

Как Apache Kafka гарантирует порядок событий (FIFO Ordering):
1. Kafka гарантирует строгий порядок сообщений **ТОЛЬКО внутри одной партиции**.
2. В разных партициях топика сообщения обрабатываются параллельно и независимо.
3. Чтобы ВСЕ события, относящиеся к одному заказу, гарантированно попадали в одну и ту же партицию, продюсер обязан вычислять партицию по ключу:
   $$\text{Partition} = \text{MurmurHash2}(\text{order\_id}) \pmod{\text{NumPartitions}}$$
4. Все реплики сервисов читают партицию строго последовательно в рамках своего оффсета.

## Решение по шагам

1. Реализуйте алгоритм хеширования ключа для распределения по партициям.
2. Продемонстрируйте, что события с одинаковым `order_id` всегда попадают в одну партицию.
3. Смоделируйте последовательное чтение очереди партиции (FIFO).
4. Покажите параллельную независимую обработку разных заказов в разных партициях.
5. Протестируйте сохранение очередности событий.

## Код решения

**`partition_ordering.go`**

```go
package main

import (
	"fmt"
	"hash/fnv"
	"sync"
)

type PartitionRouter struct {
	numPartitions int
	queues        []chan string
	wg            sync.WaitGroup
}

func NewPartitionRouter(partitions int) *PartitionRouter {
	r := &PartitionRouter{
		numPartitions: partitions,
		queues:        make([]chan string, partitions),
	}
	for i := 0; i < partitions; i++ {
		r.queues[i] = make(chan string, 100)
		r.wg.Add(1)
		go r.partitionConsumer(i, r.queues[i])
	}
	return r
}

func (r *PartitionRouter) getPartition(key string) int {
	h := fnv.New32a()
	_, _ = h.Write([]byte(key))
	return int(h.Sum32() % uint32(r.numPartitions))
}

func (r *PartitionRouter) Produce(orderID, eventName string) {
	part := r.getPartition(orderID)
	msg := fmt.Sprintf("[%s] %s", orderID, eventName)
	r.queues[part] <- msg
	fmt.Printf("[Producer] Заказ %s -> Направлен в Партицию #%d (%s)\n", orderID, part, eventName)
}

func (r *PartitionRouter) partitionConsumer(partID int, ch chan string) {
	defer r.wg.Done()
	for msg := range ch {
		fmt.Printf("  -> [Consumer Партиции #%d] Строго по порядку обработано: %s\n", partID, msg)
	}
}

func (r *PartitionRouter) Close() {
	for _, q := range r.queues {
		close(q)
	}
	r.wg.Wait()
}

func main() {
	router := NewPartitionRouter(3) // 3 партиции

	fmt.Println("=== Отправка событий с гарантией FIFO порядка по Partition Key ===")

	// События Заказа 1 (Всегда попадут в одну партицию!)
	router.Produce("ORD-AAA-101", "1. OrderCreated")
	router.Produce("ORD-AAA-101", "2. InventoryReserved")
	router.Produce("ORD-AAA-101", "3. PaymentSucceeded")

	// События Заказа 2 (Могут попасть в другую партицию, но между собой строгий FIFO!)
	router.Produce("ORD-BBB-202", "1. OrderCreated")
	router.Produce("ORD-BBB-202", "2. PaymentFailed")
	router.Produce("ORD-BBB-202", "3. OrderCancelled")

	router.Close()
}
```

ℹ️ Партиционирование по ключу заказа с сохранением строгого порядка FIFO в Kafka

## Под капотом

Если в Kafka изменить количество партиций топика (с 10 до 20) 'на лету', формула хеширования пересчитает партиции, и новые события по тому же заказу начнут попадать в другие партиции, ломая строгий порядок сообщений. Поэтому количество партиций в ответственных бизнес-топиках Саги рассчитывается заранее и никогда не увеличивается без перебалансировки.

## Подводные камни

1. **Пустой ключ сообщения (`Key = nil`)**: Если не указать ключ, Kafka начнет распределять сообщения round-robin по случайным партициям, полностью разрушив порядок событий.
2. **Параллельная обработка внутри одного воркера**: Если воркер читает партицию последовательно, но запускает `go process(msg)` на каждое сообщение, порядок немедленно нарушится из-за недетерминизма планировщика Go.

## На собеседовании

В архитектуре банковских транзакций Тинькофф и Ozon: 'Как обрабатывать сообщения внутри одной партиции параллельно, не нарушая FIFO порядок одного заказа?' Ответ: Паттерн Key-based Sharding внутри воркера: консьюмер считывает пакет сообщений из партиции и раскладывает их по внутренним горутинам-воркерам по формуле `hash(order_id) % num_subworkers`. Сообщения одного заказа всегда попадают в одну подгорутину.
