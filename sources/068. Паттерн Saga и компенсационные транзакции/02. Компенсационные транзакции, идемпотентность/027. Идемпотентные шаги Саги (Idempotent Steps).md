# Идемпотентные шаги Саги (Idempotent Steps): реализация дедупликации в ReserveInventory

## Условие

27. **Idempotent steps**: Каждый шаг Saga должен быть идемпотентным. Повторный вызов `ReserveInventory(order_id)` не должен резервировать inventory дважды.

### Исходная формулировка

**Idempotent steps**: Каждый шаг Saga должен быть идемпотентным. Повторный вызов `ReserveInventory(order_id)` не должен резервировать inventory дважды.

## Теория

В распределенной Саге не только компенсации, но и **прямые шаги обязаны быть строго идемпотентными**.

Почему прямой шаг `ReserveInventory` может быть вызван дважды:
1. Сеть моргнула: склад зарезервировал товар, но ответ HTTP 200 потерялся по дороге к оркестратору.
2. Оркестратор счел вызов неуспешным по таймауту и выполнил автоматический повтор (Retry).
3. Если метод не идемпотентен, склад спишет товар во второй раз: вместо 1 единицы товара клиент заблокирует 2 единицы на складе!

Паттерн реализации идемпотентного шага:
- Клиент передает уникальный заголовок `Idempotency-Key` (или комбинацию `saga_id + step_name`).
- Сервер в транзакции проверяет таблицу `idempotent_requests (idempotency_key, status, response_body)`.
- Если ключ уже обработан — возвращается сохраненный ранее результат без повторного декремента остатка склада.

## Решение по шагам

1. Создайте структуру запроса с полем `IdempotencyKey`.
2. Реализуйте метод `ReserveInventory` с проверкой таблицы обработанных ключей.
3. Продемонстрируйте вызов метода 3 раза с одинаковым ключом.
4. Докажите, что физический остаток на складе уменьшился ровно один раз.
5. Напишите тест подтверждения идемпотентности.

## Код решения

**`idempotent_step.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type ReserveRequest struct {
	IdempotencyKey string
	SKU            string
	Quantity       int
}

type ReserveResponse struct {
	ReservationID string
	Success       bool
}

type IdempotentInventoryService struct {
	mu           sync.Mutex
	stock        map[string]int
	reservations map[string]ReserveResponse // Idempotency Store
}

func NewIdempotentInventoryService() *IdempotentInventoryService {
	s := &IdempotentInventoryService{
		stock:        map[string]int{"IPHONE-16": 10},
		reservations: make(map[string]ReserveResponse),
	}
	return s
}

func (s *IdempotentInventoryService) Reserve(req ReserveRequest) (ReserveResponse, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверка идемпотентности: был ли запрос уже обработан
	if resp, exists := s.reservations[req.IdempotencyKey]; exists {
		fmt.Printf("[Inventory] ПОВТОРНЫЙ ЗАПРОС (Key: %s): Возврат закэшированного ответа без списания!\n",
			req.IdempotencyKey)
		return resp, nil
	}

	// 2. Бизнес-проверка остатков
	available := s.stock[req.SKU]
	if available < req.Quantity {
		return ReserveResponse{Success: false}, fmt.Errorf("недостаточно товара %s", req.SKU)
	}

	// 3. Списание остатка и сохранение результата
	s.stock[req.SKU] -= req.Quantity
	resp := ReserveResponse{
		ReservationID: fmt.Sprintf("RES-%s-OK", req.IdempotencyKey),
		Success:       true,
	}
	s.reservations[req.IdempotencyKey] = resp

	fmt.Printf("[Inventory] ПЕРВИЧНОЕ СПИСАНИЕ (Key: %s): списано %d шт. Остаток: %d шт.\n",
		req.IdempotencyKey, req.Quantity, s.stock[req.SKU])

	return resp, nil
}

func main() {
	inv := NewIdempotentInventoryService()

	req := ReserveRequest{
		IdempotencyKey: "saga-99-step-reserve",
		SKU:            "IPHONE-16",
		Quantity:       2,
	}

	// 3 последовательных вызова с одинаковым ключом идемпотентности
	_, _ = inv.Reserve(req)
	_, _ = inv.Reserve(req)
	_, _ = inv.Reserve(req)

	fmt.Printf("\nИтог: Исходный склад был 10 шт. Текущий остаток: %d шт. (Списано ровно 2!)\n",
		inv.stock["IPHONE-16"])
}
```

ℹ️ Идемпотентный метод резервирования склада с защитой от повторных списаний

## Под капотом

В СУБД PostgreSQL таблица идемпотентности оформляется с `PRIMARY KEY (idempotency_key)`. Когда запрос приходит повторно, попытка вставки `INSERT INTO idempotency_keys ...` вызывает конфликт уникальности (`ON CONFLICT (idempotency_key) DO NOTHING`). Это защищает от гонки данных даже при параллельном поступлении двух одинаковых HTTP-запросов от двух разных реплик оркестратора.

## Подводные камни

1. **Идемпотентность без сохранения тела ответа**: Если просто помнить факт вызова, но не возвращать сгенерированный `ReservationID`, клиент получит пустой ответ и посчитает операцию сбойной.
2. **Отсутствие TTL на ключи идемпотентности**: Хранение ключей вечно переполнит базу данных. Для e-commerce достаточно хранить ключи 24–72 часа.

## На собеседовании

В Wildberries и Яндекс Маркете при сетевых штормах повторные вызовы шагов происходят ежесекундно. Вопрос: 'Как сформировать Idempotency-Key для шага Саги?' Ответ: Детерминированная конкатенация `hash(saga_id + ":" + step_name)`. Это гарантирует, что даже при полном сбросе состояния оркестратора повторный запуск того же шага использует тот же ключ и не создаст дубликат.
