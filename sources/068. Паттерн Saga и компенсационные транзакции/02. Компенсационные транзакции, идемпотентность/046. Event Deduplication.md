# Event Deduplication: персистентная дедупликация событий по event_id в PostgreSQL

## Условие

### Исходная формулировка

**Event deduplication**: Используйте event ID для deduplication. Сохраняйте processed event IDs в Redis/БД.

## Теория

Сетевые сбои в брокере сообщений неминуемо приводят к повторной доставке сообщений (At-Least-Once). Если событие `OrderCreated` доставится дважды, без дедупликации со счета клиента спишутся две суммы.

Архитектурный паттерн **Idempotent Consumer с персистентным реестром**:
1. Каждое сообщение в брокере содержит глобально уникальный `event_id` (UUIDv4).
2. В реляционной СУБД сервиса создается таблица:
   ```sql
   CREATE TABLE processed_events (
       event_id VARCHAR(64) PRIMARY KEY,
       consumer_name VARCHAR(64) NOT NULL,
       processed_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
   );
   ```
3. Обработка сообщения и вставка в `processed_events` производятся в рамках единой локальной транзакции.
4. При попытке повторной обработки вставка упадет по ограничению `UNIQUE (event_id)`, транзакция откатится, а консьюмер просто подтвердит сообщение брокеру (`ACK`).

## Решение по шагам

1. Опишите структуру хранилища обработанных событий.
2. Реализуйте функцию транзакционной обработки события с проверкой дедупликации.
3. Смоделируйте отправку одного и того же события 3 раза подряд.
4. Докажите, что бизнес-действие выполнилось ровно 1 раз.
5. Протестируйте устойчивость к дубликатам.

## Код решения

**`event_dedup.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type DedupStore struct {
	mu              sync.Mutex
	processedEvents map[string]bool
	accountBalance  float64
}

func NewDedupStore() *DedupStore {
	return &DedupStore{
		processedEvents: make(map[string]bool),
		accountBalance:  10000.0,
	}
}

// ProcessChargeTransaction атомарно списывает средства с защитой от дубликатов
func (s *DedupStore) ProcessChargeTransaction(eventID string, amount float64) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Проверка в таблице processed_events
	if s.processedEvents[eventID] {
		fmt.Printf("[DEDUP ENGINE] Событие %s УЖЕ БЫЛО ОБРАБОТАНО РАНЕЕ! Повторное списание заблокировано.\n", eventID)
		return nil // Идемпотентно подтверждаем успех
	}

	// 2. Выполнение бизнес-логики списания
	if s.accountBalance < amount {
		return fmt.Errorf("недостаточно средств")
	}
	s.accountBalance -= amount

	// 3. Атомарная фиксация event_id в реестре
	s.processedEvents[eventID] = true

	fmt.Printf("[DEDUP ENGINE] ПЕРВИЧНАЯ ОБРАБОТКА %s: Списано %.2f руб. Новый баланс: %.2f руб.\n",
		eventID, amount, s.accountBalance)
	return nil
}

func main() {
	store := NewDedupStore()
	eventID := "EVT-UUID-999-ORIGINAL"

	// Эмуляция 3 повторных доставок одного и того же события из брокера
	_ = store.ProcessChargeTransaction(eventID, 1500.0)
	_ = store.ProcessChargeTransaction(eventID, 1500.0)
	_ = store.ProcessChargeTransaction(eventID, 1500.0)

	fmt.Printf("\nИтог: Баланс счета: %.2f руб. (Списание прошло ровно 1 раз, дубли отсечены!)\n",
		store.accountBalance)
}
```

ℹ️ Персистентная дедупликация событий Саги по уникальному event_id

## Под капотом

В SQL идеальная конструкция выглядит так:
```sql
INSERT INTO processed_events (event_id, consumer_name) 
VALUES ($1, 'payment_worker') 
ON CONFLICT (event_id) DO NOTHING;
```
Если количество затронутых строк (`RowsAffected`) равно 0, значит, событие является дубликатом. Транзакция немедленно подтверждается без выполнения тяжелых бизнес-операций.

## Подводные камни

1. **Дедупликация в кэше Redis без транзакции с БД**: Если записать ключ в Redis, а транзакция PostgreSQL упадет, событие никогда не сможет обработаться заново при повторе. Реестр дедупликации ОБЯЗАН жить в той же БД, что и бизнес-данные.
2. **Переполнение таблицы `processed_events`**: Настройте очистку (retention) записей старше 7 дней с помощью фонового партиционирования по дате.

## На собеседовании

В финтех-сервисах Ozon Банк и Тинькофф: 'Как гарантировать Exactly-Once обработку в системе с At-Least-Once брокером?' Ответ: Exactly-Once Processing на уровне прикладного сервиса достигается связкой `At-Least-Once брокер + Идемпотентный консьюмер с таблицей дедупликации в транзакционной БД`. Дубликаты отсекаются по первичному ключу `event_id`.
