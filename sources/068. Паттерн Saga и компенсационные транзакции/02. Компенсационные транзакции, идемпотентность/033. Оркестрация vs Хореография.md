# Оркестрация vs Хореография: централизованный сервис OrderSagaOrchestrator

## Условие

33. **[Оркестрация (Centralized)]**: Перепиши предыдущуюSaga. Создай отдельный сервис `OrderOrchestrator`. Он делает синхронный gRPC-вызов в Payment. Если успех — вызывает Inventory. Если Inventory падает, Оркестратор *сам* вызывает `Payment.Refund()`.

### Исходная формулировка

## Теория

Сравнение двух фундаментальных парадигм Саги:

| Критерий | Оркестрация (Orchestration) | Хореография (Choreography) |
| :--- | :--- | :--- |
| **Координация** | Централизованная (Orchestrator) | Децентрализованная (Events) |
| **Связность** | Сервисы знают оркестратор | Сервисы знают события |
| **Видимость процесса** | Высокая (граф в одном месте) | Низкая (размазан по сервисам) |
| **Сложность тестирования**| Простая (mock сервисов) | Сложная (нужен общий брокер) |
| **Точка отказа** | Оркестратор (требует HA кластера)| Брокер сообщений |
| **Размер системы** | Лучше для 5+ сервисов | Лучше для 2-4 сервисов |

Централизованный сервис `OrderSagaOrchestrator` хранит полный контекст заказа, отправляет команды в gRPC API сервисов и единолично решает судьбу транзакции.

## Решение по шагам

1. Создайте архитектурную структуру сервиса `OrderSagaOrchestrator`.
2. Реализуйте клиентские адаптеры к сервисам Order, Payment, Inventory.
3. Опишите логику принятия решений при успешных ответах и отказах.
4. Продемонстрируйте полный цикл оркестрации.
5. Сформулируйте преимущества централизации.

## Код решения

**`centralized_orchestrator.go`**

```go
package main

import (
	"context"
	"fmt"
)

type OrchestratorService struct {
	orderClient     func(id string) error
	paymentClient   func(id string, amount float64) error
	inventoryClient func(id string, sku string) error
}

func (s *OrchestratorService) ProcessOrder(ctx context.Context, orderID string, amount float64, sku string) error {
	fmt.Printf("[Orchestrator] Старт координации заказа: %s\n", orderID)

	// Шаг 1: Создание заказа
	if err := s.orderClient(orderID); err != nil {
		return fmt.Errorf("сбой создания заказа: %w", err)
	}

	// Шаг 2: Резерв инвентаря
	if err := s.inventoryClient(orderID, sku); err != nil {
		fmt.Printf("[Orchestrator] Сбой склада: %v. Откат заказа!\n", err)
		s.compensateOrder(orderID)
		return err
	}

	// Шаг 3: Списание оплаты
	if err := s.paymentClient(orderID, amount); err != nil {
		fmt.Printf("[Orchestrator] Сбой оплаты: %v. Откат склада и заказа!\n", err)
		s.compensateInventory(orderID, sku)
		s.compensateOrder(orderID)
		return err
	}

	fmt.Printf("[Orchestrator] Заказ %s УСПЕШНО ЗАВЕРШЕН!\n", orderID)
	return nil
}

func (s *OrchestratorService) compensateOrder(id string) {
	fmt.Printf("  <- [Компенсация] OrderService.Cancel(%s)\n", id)
}

func (s *OrchestratorService) compensateInventory(id string, sku string) {
	fmt.Printf("  <- [Компенсация] InventoryService.Release(%s, %s)\n", id, sku)
}

func main() {
	svc := &OrchestratorService{
		orderClient:     func(id string) error { fmt.Println("  -> OrderService.Create: OK"); return nil },
		inventoryClient: func(id string, sku string) error { fmt.Println("  -> InventoryService.Reserve: OK"); return nil },
		paymentClient:   func(id string, amount float64) error { return fmt.Errorf("лимит карты исчерпан") },
	}

	_ = svc.ProcessOrder(context.Background(), "ORD-CENTRAL-1", 7500.0, "MACBOOK-M3")
}
```

ℹ️ Централизованный сервис-оркестратор саги с полным контролем компенсаций

## Под капотом

В оркестрации сервисы-участники становятся 'тонкими исполнителями' (Dumb Workers). Им больше не нужно слушать чужие события или знать о существовании соседних микросервисов. Сервис `Inventory` просто предоставляет методы `Reserve` и `Release`, что резко повышает модульность кодовой базы и упрощает повторное использование сервисов в других сагах.

## Подводные камни

1. **Узкое горлышко (Bottleneck) по CPU**: Если оркестратор синхронно удерживает тысячи соединений, он может исчерпать файловые дескрипторы сокетов.
2. **Отказ базы данных оркестратора**: База данных состояния оркестратора обязана быть развернута в High-Availability режиме с синхронной репликацией.

## На собеседовании

В архитектурных комитетах BigTech (Яндекс, Авито, Ozon): 'Почему большинство команд в итоге переходят от хореографии к оркестрации?' Ответ: Хореография легка на старте, но по мере роста системы затраты на понимание графа событий, поиск причин зависших заказов и добавление новых шагов становятся непосильными. Оркестратор собирает всю схему процесса в одном месте, делая поведение системы предсказуемым.
