# Compensation through Events: публикация компенсирующих событий в хореографии

## Условие

43. **Compensation through events**: При failure публикуйте compensation events:
    * `PaymentFailed` → Inventory Service слушает → `InventoryReleased`
    * `InventoryReleased` → Order Service слушает → `OrderCancelled`

### Исходная формулировка

**Compensation through events**: При failure публикуйте compensation events:
* `PaymentFailed` → Inventory Service слушает → `InventoryReleased`
* `InventoryReleased` → Order Service слушает → `OrderCancelled`

## Теория

В хореографической Саге откат изменений управляется публикацией цепочки компенсирующих событий:
1. `PaymentFailed`: Платеж отклонен.
2. `InventoryReleaseRequested` (или реакция на `PaymentFailed`): Склад снимает бронь товара и публикует `InventoryReleased`.
3. `OrderCancelRequested`: Сервис заказов аннулирует заказ и публикует `OrderCancelled`.

Каждое компенсирующее событие несет контекст:
`{ "order_id": "ORD-1", "reason": "Card declined", "original_event_id": "evt-100" }`.

Свойства компенсирующих событий:
- Они имеют приоритет над новыми заказами (высокий приоритет в очереди).
- Доставка обязана гарантироваться (Persistence & Retry).

## Решение по шагам

1. Создайте структуры компенсирующих событий.
2. Реализуйте цепочку публикации отката от Payment до Order.
3. Добавьте логирование прохождения компенсирующего потока.
4. Убедитесь в отсутствии потери контекста ошибки.
5. Протестируйте итоговую отмену заказа.

## Код решения

**`compensation_events.go`**

```go
package main

import (
	"fmt"
	"time"
)

type CompensationEvent struct {
	Type      string
	OrderID   string
	Reason    string
	Timestamp time.Time
}

type EventChannel struct {
	listeners map[string][]func(CompensationEvent)
}

func NewEventChannel() *EventChannel {
	return &EventChannel{listeners: make(map[string][]func(CompensationEvent))}
}

func (c *EventChannel) Listen(eventType string, handler func(CompensationEvent)) {
	c.listeners[eventType] = append(c.listeners[eventType], handler)
}

func (c *EventChannel) Broadcast(ev CompensationEvent) {
	ev.Timestamp = time.Now()
	fmt.Printf("[BROKER] Компенсирующее событие: %-25s | Заказ: %s | Причина: %s\n",
		ev.Type, ev.OrderID, ev.Reason)
	for _, h := range c.listeners[ev.Type] {
		go h(ev)
	}
}

func main() {
	bus := NewEventChannel()

	// 1. InventoryService слушает PaymentFailed
	bus.Listen("PaymentFailed", func(e CompensationEvent) {
		fmt.Printf("  -> [InventoryService] Снятие брони для заказа %s...\n", e.OrderID)
		bus.Broadcast(CompensationEvent{
			Type:    "InventoryReleased",
			OrderID: e.OrderID,
			Reason:  e.Reason,
		})
	})

	// 2. OrderService слушает InventoryReleased
	bus.Listen("InventoryReleased", func(e CompensationEvent) {
		fmt.Printf("  -> [OrderService] Финальная отмена заказа %s. Статус -> CANCELLED\n", e.OrderID)
	})

	fmt.Println("=== Старт каскада компенсирующих событий ===")
	// Триггер: банк отклонил операцию
	bus.Broadcast(CompensationEvent{
		Type:    "PaymentFailed",
		OrderID: "ORD-COMP-909",
		Reason:  "3D-Secure authentication failed",
	})

	time.Sleep(100 * time.Millisecond)
}
```

## Под капотом

В брокере Kafka компенсирующие события обычно отправляются в те же топики, но с другим заголовком события (`Header: ce-type = "PaymentFailed"`), либо в выделенные топики отката (`orders.compensations`). Ключ сообщения `Key = order_id` сохраняется неизменным, гарантируя обработку отката тем же воркером, который обрабатывал прямой шаг.

## Подводные камни

1. **Шторм компенсирующих событий**: Если при падении брокера сообщения зацикливаются, сервисы начнут бесконечно слать события отмены друг другу.
2. **Отсутствие Reason в аудите**: Потеря причины отката в теле события делает невозможной аналитику причин сбоев.

## На собеседовании

В распределенных маркетплейсах (Wildberries, Lamoda): 'Как предотвратить гонку между запоздалым событием успеха PaymentSucceeded и компенсирующим событием PaymentFailed?' Ответ: Модель версионирования сущности: каждое событие несет номер версии `version`. Если заказ уже перешел в статус `version=3 (CANCELLED)`, запоздалое событие с `version=2` игнорируется как устаревшее.
