# Saga Timeout в Choreography: отложенные сообщения и сервис контроля дедлайнов

### Исходная формулировка

**Saga timeout в Choreography**: Реализуйте timeout через отдельный сервис, который слушает `OrderCreated` и через 30 минут проверяет, был ли `OrderShipped`. Если нет — публикует `SagaTimeout`.

## Теория

Поскольку в хореографии нет центрального оркестратора, кто-то должен следить за тем, чтобы процесс не завис навсегда, если один из сервисов молча упал.

Паттерн **Saga Timeout Watchdog (Сторожевой сервис таймаутов)**:
1. При создании заказа `OrderService` публикует отложенное сообщение (Delayed Message / Dead Man's Snitch) в брокер:
   `orders.timeout.check { order_id: "ORD-1", timeout: "15m" }`.
2. Сообщение доставляется сервису `TimeoutMonitor` ровно через 15 минут (через RabbitMQ Dead Letter Exchange с TTL или Redis Delayed Queue).
3. `TimeoutMonitor` запрашивает статус заказа: если заказ все еще в статусе `PENDING`, монитор публикует событие `OrderTimedOut { order_id: "ORD-1" }`.
4. Все сервисы реагируют на `OrderTimedOut` и выполняют компенсирующие действия.

## Решение по шагам

1. Опишите структуру отложенного тайм-аут события.
2. Реализуйте монитор таймаутов с таймером ожидания.
3. Смоделируйте случай, когда заказ не успел завершиться за отведенное время.
4. Опубликуйте событие `OrderTimedOut`.
5. Продемонстрируйте автоматический откат участников.

## Код решения

**`choreography_timeout.go`**

```go
package main

import (
	"fmt"
	"time"
)

type OrderTimeoutMonitor struct {
	orderStatuses map[string]string
}

func NewOrderTimeoutMonitor() *OrderTimeoutMonitor {
	return &OrderTimeoutMonitor{orderStatuses: make(map[string]string)}
}

func (m *OrderTimeoutMonitor) ScheduleTimeoutCheck(orderID string, timeout time.Duration, onTimeout func(string)) {
	m.orderStatuses[orderID] = "PENDING"
	fmt.Printf("[Watchdog] Запущен таймер дедлайна для %s на %v\n", orderID, timeout)

	go func() {
		time.Sleep(timeout)
		// Проверка: успел ли заказ завершиться
		status := m.orderStatuses[orderID]
		if status == "PENDING" {
			fmt.Printf("\n[WATCHDOG ALARM] Заказ %s НЕ ЗАВЕРШИЛСЯ ЗА %v! Публикация события OrderTimedOut!\n",
				orderID, timeout)
			m.orderStatuses[orderID] = "TIMED_OUT"
			onTimeout(orderID)
		} else {
			fmt.Printf("[Watchdog] Заказ %s успешен (Статус: %s). Таймер отменен.\n", orderID, status)
		}
	}()
}

func main() {
	monitor := NewOrderTimeoutMonitor()

	// Запуск мониторинга заказа с коротким таймаутом 150 мс
	monitor.ScheduleTimeoutCheck("ORD-DELAYED-77", 150*time.Millisecond, func(id string) {
		fmt.Printf("  <- [Broadcast] Событие OrderTimedOut для %s разослано всем сервисам!\n", id)
		fmt.Printf("  <- [InventoryService] Автоматическое освобождение брони по таймауту!\n")
		fmt.Printf("  <- [PaymentService] Аннулирование холда по таймауту!\n")
	})

	// Симулируем зависание сервиса склада (ответ не пришел)
	time.Sleep(250 * time.Millisecond)
}
```

## Под капотом

В распределенных очередях RabbitMQ отложенные сообщения реализуются через связку плагина `rabbitmq_delayed_message_exchange` или комбинацию `message-ttl` + `x-dead-letter-exchange`. Сообщение ждет в служебной очереди без консьюмеров, и после истечения TTL брокер автоматически перебрасывает его в основной топик проверки таймаута.

## Подводные камни

1. **Таймер в оперативной памяти пода**: Использование `time.Sleep` в памяти Go сбросится при рестарте пода. Отложенные таймеры должны храниться в брокере сообщений или Redis.
2. **Ложное срабатывание при высокой нагрузке**: Слишком агрессивный таймаут приведет к отмене заказов, которые просто стояли в очереди на обработку.

## На собеседовании

В системах бронирования авиабилетов (Aviasales, Аэрофлот): 'Как гарантировать снятие брони билета через 20 минут в событийной системе?' Ответ: При бронировании отсылается отложенное сообщение с задержкой 20 минут в RabbitMQ или Kafka. Когда сообщение всплывает, сервис проверяет статус оплаты: если оплаты нет — место возвращается в открытую продажу.
