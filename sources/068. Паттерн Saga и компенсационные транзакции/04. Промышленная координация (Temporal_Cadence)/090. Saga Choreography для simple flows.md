# Saga Choreography для simple flows: когда оправдана хореография и как избежать хаоса

## Условие

90. **Saga Choreography для simple flows.**: Если у вас 2-3 шага и simple event-driven flow — используйте Choreography. Loosely coupled, но сложнее отследить overall state.

### Исходная формулировка

**Saga Choreography для simple flows.**: Если у вас 2-3 шага и simple event-driven flow — используйте Choreography. Loosely coupled, но сложнее отследить overall state.

## Теория

Хореография (Choreography) идеально подходит для простых сценариев из 2–3 участников с линейным потоком выполнения: Заказ создан -> Списание денег -> Уведомление покупателя. Внедрение тяжелого оркестратора (Temporal/Cadence) для таких задач избыточно (Overengineering). Хореография обеспечивает максимальную слабую связанность (Loose Coupling): сервис заказа вообще не знает о существовании сервиса уведомлений — он просто публикует факт `OrderCreated`. Однако, чтобы хореография не превратилась в неуправляемый спагетти-хаос, необходимо соблюдать три правила:
1) Строгий единый контракт `Correlation-ID` во всех событиях;
2) Отсутствие циклических зависимостей;
3) Единый Schema Registry (Protobuf/Avro) для всех событий.

## Решение по шагам

1. Опишите событие `UserRegisteredEvent` с сквозным `CorrelationID`.
2. Реализуйте сервис `AuthService`, публикующий регистрацию пользователя.
3. Реализуйте сервис `EmailService`, слушающий регистрацию и отправляющий приветственное письмо.
4. Реализуйте сервис `AnalyticsService`, слушающий регистрацию для продуктовых метрик.
5. Продемонстрируйте полную автономность сервисов без единого координатора.

## Код решения

**`simple_choreography.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type UserRegisteredEvent struct {
	CorrelationID string
	UserID        string
	Email         string
	Timestamp     time.Time
}

type SimpleBroker struct {
	mu          sync.RWMutex
	subscribers []func(UserRegisteredEvent)
}

func (b *SimpleBroker) Subscribe(h func(UserRegisteredEvent)) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.subscribers = append(b.subscribers, h)
}

func (b *SimpleBroker) Publish(e UserRegisteredEvent) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for _, h := range b.subscribers {
		go h(e)
	}
}

func main() {
	broker := &SimpleBroker{}
	var wg sync.WaitGroup
	wg.Add(2)

	// Подписчик 1: Email сервис (не зависит от аналитики и регистрации)
	broker.Subscribe(func(e UserRegisteredEvent) {
		defer wg.Done()
		fmt.Printf("[Email Service] [Trace: %s] Sending Welcome Email to %s...\n", e.CorrelationID, e.Email)
	})

	// Подписчик 2: Аналитика (не зависит от email)
	broker.Subscribe(func(e UserRegisteredEvent) {
		defer wg.Done()
		fmt.Printf("[Analytics Service] [Trace: %s] User %s signup metric pushed to ClickHouse\n", e.CorrelationID, e.UserID)
	})

	// Сервис регистрации публикует доменное событие
	fmt.Println("[Auth Service] User registered successfully in PostgreSQL -> Publishing Event")
	evt := UserRegisteredEvent{
		CorrelationID: "trace-reg-uuid-771",
		UserID:        "usr-1092",
		Email:         "senior_dev@yandex.ru",
		Timestamp:     time.Now(),
	}
	broker.Publish(evt)

	wg.Wait()
	fmt.Println("[Done] Simple choreography executed seamlessly.")
}
```

ℹ️ Простая событийно-ориентированная хореография для слабосвязанных микросервисов

**`output.txt`**

```bash

[Email Service] [Trace: trace-reg-uuid-771] Sending Welcome Email to senior_dev@yandex.ru...
[Analytics Service] [Trace: trace-reg-uuid-771] User usr-1092 signup metric pushed to ClickHouse
[Done] Simple choreography executed seamlessly.
```

## Под капотом

Хореография использует архитектурный паттерн Publish-Subscribe. Сервис-издатель знает только о своем событии, но ничего не знает о потребителях. Это обеспечивает предельную гибкость: добавление нового сервиса (например, Fraud Audit) не требует изменений в существующем сервисе регистрации — достаточно добавить нового консьюмера в Kafka.

## Подводные камни

1. Неявные скрытые зависимости: если сервис А шлет событие сервису Б, а сервис Б меняет статус, который нужен сервису А для продолжения, образуется распределенная циклическая блокировка.
2. Отсутствие единой трассировки: без передачи `CorrelationID` в метаданных Kafka отладка проблем превращается в ручной поиск по миллионам неструктурированных логов.

## На собеседовании

Вопрос: Каковы критерии перехода с Choreography на Orchestration?
Ответ: Главные сигналы для перехода: 1) Число участников процесса выросло до 4+; 2) Появились сложные компенсирующие сценарии (откат при сбое); 3) Бизнесу требуется централизованный дашборд статуса каждого заказа в реальном времени; 4) Появились временные ожидания (Wait for 3 days / Timer activities).
