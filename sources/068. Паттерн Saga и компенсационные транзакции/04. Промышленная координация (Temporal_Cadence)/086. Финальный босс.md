### Исходная формулировка

**Финальный босс (Multi-Tenant SaaS с Distributed Transactions):**
    Создайте multi-tenant SaaS платформу (типа Shopify, Slack):

    **Architecture:**
    * **Tenant isolation:** отдельная БД per tenant (для enterprise) или shared DB с Row-Level Security (для SMB)
    * **Saga per tenant:** каждый tenant имеет свои Sagas
    * **Outbox/Inbox per tenant:** tenant-scoped message queues

    **Tenant-Aware Patterns:**
    * **Idempotency keys scoped to tenant:** tenant A и tenant B могут использовать одинаковые keys
    * **Outbox table per tenant** (для database-per-tenant) или tenant_id column (для shared DB)
    * **Saga state per tenant**

    **Scaling:**
    * **Horizontal scaling:** multiple instances per tenant для high-volume tenants
    * **Tenant-aware routing:** API Gateway routes requests к correct instance
    * **Tenant-aware rate limiting:** per-tenant quotas

    **Reliability:**
    * **Saga timeouts** per tenant (configurable)
    * **Compensation** per tenant
    * **Dead letter queues** per tenant

    **Observability:**
    * **Per-tenant metrics:** tenant-specific dashboards
    * **Tenant correlation:** tenant_id в каждом trace/log
    * **Alerting:** per-tenant alerts для enterprise customers

    **Testing:**
    * **Multi-tenant testing:** concurrent Sagas для разных tenants
    * **Tenant isolation testing:** tenant A не видит данные tenant B
    * **Performance testing:** 1000 concurrent tenants, 100 Sagas/tenant

## Теория

В корпоративных B2B SaaS-системах (Shopify, Stripe Connect, Salesforce) сотни тысяч компаний-арендаторов (Tenants) обслуживаются единым кластером микросервисов. Архитектурная изоляция требует, чтобы распределенные транзакции, ключи идемпотентности, очереди Outbox и стейты саг были строго разграничены по `tenant_id`. Если один арендатор проводит массовую акцию и спамит транзакциями, механизм Tenant Rate Limiting и раздельные пулы очередей (Fair Queueing) должны изолировать его нагрузку, не позволяя исчерпать ресурсы других клиентов (Noisy Neighbor Problem).

## Решение по шагам

1. Создайте составной контекст запроса с обязательным полем `TenantID`.
2. Спроектируйте структуру хранилища `MultiTenantSagaStorage`, шардированную по `TenantID`.
3. Реализуйте метод проверки идемпотентности с областью видимости `(tenant_id, idempotency_key)`.
4. Реализуйте изоляцию очередей Outbox для каждого арендатора.
5. Продемонстрируйте, что арендаторы А и Б могут безопасно использовать одинаковые ключи идемпотентности.

## Код решения

**`multitenant_saga.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type TenantContextKey struct{}

func WithTenantID(ctx context.Context, tenantID string) context.Context {
	return context.WithValue(ctx, TenantContextKey{}, tenantID)
}

func GetTenantID(ctx context.Context) string {
	if val, ok := ctx.Value(TenantContextKey{}).(string); ok {
		return val
	}
	return "unknown"
}

type TenantSagaRecord struct {
	SagaID  string
	Status  string
	Payload string
}

type MultiTenantStorage struct {
	mu           sync.Mutex
	idempRecords map[string]map[string]string           // tenantID -> idempKey -> sagaID
	sagas        map[string]map[string]TenantSagaRecord // tenantID -> sagaID -> record
}

func NewMultiTenantStorage() *MultiTenantStorage {
	return &MultiTenantStorage{
		idempRecords: make(map[string]map[string]string),
		sagas:        make(map[string]map[string]TenantSagaRecord),
	}
}

func (s *MultiTenantStorage) ExecuteTenantSaga(ctx context.Context, idempKey, sagaID, payload string) (string, bool) {
	tenantID := GetTenantID(ctx)

	s.mu.Lock()
	defer s.mu.Unlock()

	// Инициализация структур арендатора
	if _, ok := s.idempRecords[tenantID]; !ok {
		s.idempRecords[tenantID] = make(map[string]string)
		s.sagas[tenantID] = make(map[string]TenantSagaRecord)
	}

	// Проверка идемпотентности внутри пространства арендатора
	if existingSagaID, exists := s.idempRecords[tenantID][idempKey]; exists {
		fmt.Printf("[Tenant: %s] Duplicate key '%s' detected -> returning existing Saga %s\n",
			tenantID, idempKey, existingSagaID)
		return existingSagaID, true
	}

	// Регистрация новой саги
	s.idempRecords[tenantID][idempKey] = sagaID
	s.sagas[tenantID][sagaID] = TenantSagaRecord{
		SagaID:  sagaID,
		Status:  "COMPLETED",
		Payload: payload,
	}

	fmt.Printf("[Tenant: %s] Successfully executed and committed Saga %s (Key: %s)\n",
		tenantID, sagaID, idempKey)
	return sagaID, false
}

func main() {
	storage := NewMultiTenantStorage()

	// Два разных арендатора: Shopify Store A и Shopify Store B
	ctxTenantA := WithTenantID(context.Background(), "tenant-shopify-store-A")
	ctxTenantB := WithTenantID(context.Background(), "tenant-shopify-store-B")

	sharedKey := "checkout-order-uuid-999" // Одинаковый ключ у двух разных клиентов

	// Арендатор А создает заказ со своим ключом
	fmt.Println("--- Tenant A Checkout ---")
	sagaA, dupA := storage.ExecuteTenantSaga(ctxTenantA, sharedKey, "saga-A-1", "order_alice")
	fmt.Printf("Result A: Saga=%s, Dup=%v\n\n", sagaA, dupA)

	// Арендатор Б создает заказ с ТОЧНО ТАКИМ ЖЕ ключом
	fmt.Println("--- Tenant B Checkout (Collision Isolation Check) ---")
	sagaB, dupB := storage.ExecuteTenantSaga(ctxTenantB, sharedKey, "saga-B-1", "order_bob")
	fmt.Printf("Result B: Saga=%s, Dup=%v\n\n", sagaB, dupB)

	// Повторный запрос от Арендатора А
	fmt.Println("--- Tenant A Replay Check ---")
	sagaA2, dupA2 := storage.ExecuteTenantSaga(ctxTenantA, sharedKey, "saga-A-new", "order_alice")
	fmt.Printf("Result A Replay: Saga=%s, Dup=%v\n", sagaA2, dupA2)
}
```

## Под капотом

В PostgreSQL для Multi-Tenancy используется Row-Level Security (RLS). Перед каждым запросом приложение выполняет `SET LOCAL app.current_tenant_id = $1`. Таблица `idempotency_records` имеет составной первичный ключ `PRIMARY KEY (tenant_id, key)`. Политика безопасности `CREATE POLICY tenant_isolation ON idempotency_records USING (tenant_id = current_setting('app.current_tenant_id'))` гарантирует невозможность прочитать или перезаписать чужие транзакции на уровне ядра СУБД.

## Подводные камни

1. Утечка TenantID через контекст: если горутина запускается без явной передачи tenant_id, запросы будут идти под дефолтным арендатором, разрушая безопасность.
2. Общая очередь брокера: если все арендаторы пишут в один топик Kafka, крупный клиент забьет партиции. Требуются партиционирование по `tenant_id` и взвешенные квоты.

## На собеседовании

Вопрос: Что выбрать для SaaS платформы: Database-per-tenant или Shared-Database-with-RLS?
Ответ: Для Enterprise клиентов с жесткими требованиями комплаенса (HIPAA, GDPR) выбирается Database-per-tenant (полная физическая изоляция, отдельные бэкапы). Для массового сегмента (SMB) выбирается Shared DB с RLS для экономии ресурсов пула соединений и упрощения миграций схем.
