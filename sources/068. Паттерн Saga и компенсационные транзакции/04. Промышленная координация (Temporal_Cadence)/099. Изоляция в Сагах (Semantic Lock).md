# Изоляция в Сагах (Semantic Lock): защита от Dirty Reads и Lost Updates

## Условие

99. **Изоляция в Сагах (Semantic Lock)**: Пока Сага выполняется (Заказ PENDING), другой микросервис может попытаться изменить этот же заказ или товар. Это нарушает изоляцию (Isolation из ACID). Введи статус `LOCKED` для задействованных сущностей на время работы саги, чтобы любые другие запросы к ним возвращали HTTP 423 Locked.

### Исходная формулировка

**Изоляция в Сагах (Semantic Lock)**: Пока Сага выполняется (Заказ PENDING), другой микросервис может попытаться изменить этот же заказ или товар. Это нарушает изоляцию (Isolation из ACID). Введи статус `LOCKED` для задействованных сущностей на время работы саги, чтобы любые другие запросы к ним возвращали HTTP 423 Locked.

## Теория

Аббревиатура ACID гарантирует I (Isolation): параллельные транзакции не видят промежуточных незафиксированных изменений друг друга. В Сагах свойство изоляции ОТСУТСТВУЕТ (Lack of Isolation), поскольку каждый шаг фиксирует изменения в локальной БД немедленно (Local Commit). Это порождает классические аномалии:
1) Dirty Read: пользователь видит на балансе списанные деньги до того, как заказ подтвержден;
2) Lost Update: параллельный процесс перезаписывает заказ, находящийся в середине отката.
Для устранения аномалий применяется Семантическая Блокировка (Semantic Lock): сущность помечается специальным статусом `LOCKED / PENDING_COMPLETION`. Любой параллельный запрос к сущности отклоняется с кодом HTTP 423 Locked или ожидает снятия семантического замка.

## Решение по шагам

1. Создайте доменную модель `Account` со статусом блокировки `IsLockedBySaga`.
2. Реализуйте метод `AcquireSemanticLock(sagaID)`.
3. При попытке изменения заблокированного аккаунта верните ошибку `ErrResourceLocked (HTTP 423)`.
4. Снимите семантический замок после успешного завершения или компенсации саги.
5. Продемонстрируйте защиту от параллельной модификации в `main`.

## Код решения

**`semantic_lock.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

var ErrResourceLocked = errors.New("HTTP 423 Locked: resource is currently involved in an in-flight distributed Saga")

type BankAccount struct {
	ID             string
	Balance        float64
	SemanticLockBy string // SagaID или пусто
}

type AccountManager struct {
	mu       sync.Mutex
	accounts map[string]*BankAccount
}

func NewAccountManager() *AccountManager {
	mgr := &AccountManager{accounts: make(map[string]*BankAccount)}
	mgr.accounts["acc-user-1"] = &BankAccount{
		ID:             "acc-user-1",
		Balance:        5000.0,
		SemanticLockBy: "",
	}
	return mgr
}

// Захват семантического замка в начале саги
func (m *AccountManager) LockForSaga(accountID, sagaID string) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	acc, exists := m.accounts[accountID]
	if !exists {
		return errors.New("account not found")
	}

	if acc.SemanticLockBy != "" {
		return fmt.Errorf("%w (already locked by %s)", ErrResourceLocked, acc.SemanticLockBy)
	}

	acc.SemanticLockBy = sagaID
	fmt.Printf("[Semantic Lock] Account %s LOCKED by Saga %s\n", accountID, sagaID)
	return nil
}

// Попытка параллельной пользовательской операции
func (m *AccountManager) DepositFunds(accountID string, amount float64) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	acc := m.accounts[accountID]
	if acc.SemanticLockBy != "" {
		// Ресурс защищен семантической блокировкой
		return fmt.Errorf("%w: cannot deposit while Saga %s is running", ErrResourceLocked, acc.SemanticLockBy)
	}

	acc.Balance += amount
	fmt.Printf("[Direct Action] Successfully deposited $%.2f. New balance: $%.2f\n", amount, acc.Balance)
	return nil
}

// Снятие замка по завершении саги
func (m *AccountManager) UnlockSaga(accountID, sagaID string) {
	m.mu.Lock()
	defer m.mu.Unlock()

	acc := m.accounts[accountID]
	if acc != nil && acc.SemanticLockBy == sagaID {
		acc.SemanticLockBy = ""
		fmt.Printf("[Semantic Lock] Account %s UNLOCKED after Saga %s finished\n", accountID, sagaID)
	}
}

func main() {
	mgr := NewAccountManager()
	accID := "acc-user-1"
	sagaID := "saga-transfer-998"

	// Сага стартует и блокирует сущность
	_ = mgr.LockForSaga(accID, sagaID)

	// Параллельный запрос от пользователя (например, пополнение через терминал)
	fmt.Println("\n--- Concurrent operation attempt ---")
	err := mgr.DepositFunds(accID, 1000.0)
	if err != nil {
		fmt.Printf("[REJECTED] %v\n", err)
	}

	// Сага завершается
	fmt.Println("\n--- Saga Finishes ---")
	mgr.UnlockSaga(accID, sagaID)

	// Теперь операция проходит успешно
	fmt.Println("\n--- Retry operation after unlock ---")
	_ = mgr.DepositFunds(accID, 1000.0)
}
```

ℹ️ Изоляция сущностей в Саге с помощью семантических блокировок (HTTP 423 Locked)

```bash

--- Concurrent operation attempt ---
[REJECTED] HTTP 423 Locked: resource is currently involved in an in-flight distributed Saga: cannot deposit while Saga saga-transfer-998 is running

--- Saga Finishes ---
```

## Под капотом

Семантическая блокировка — это прикладной аналог Pessimistic Lock, но без удержания соединения к БД. В базе статус хранится как флаг `locked_by_saga_id VARCHAR NULL`. Для предотвращения бесконечной блокировки при авариях поле снабжается `lock_expires_at TIMESTAMP`. Если сага упала, любой процесс может снять протухший замок по истечении TTL.

## Подводные камни

1. Забытое снятие блокировки при компенсации: если сага откатилась, но не очистила `SemanticLockBy`, пользователь больше никогда не сможет воспользоваться своим аккаунтом.
2. Deadlock семантических блокировок: если Сага 1 заблокировала счет А и ждет счет Б, а Сага 2 заблокировала счет Б и ждет счет А, возникнет распределенный дедлок. Необходимо блокировать ресурсы в строго упорядоченном порядке (по алфавиту ID).

## На собеседовании

Вопрос: Как бороться с отсутствием изоляции в Сагах без использования блокировок?
Ответ: Существуют паттерны: 1) Commutative Updates (коммутативные операции) — операции, чей результат не зависит от порядка выполнения (например, дебет и кредит баланса); 2) Version Check — проверка версий; 3) By-Value (переоценка значения) — перед финальным коммитом система проверяет, не изменились ли критические условия.
