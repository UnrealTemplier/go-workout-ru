# Inventory Service: событийно-ориентированное резервирование и публикация InventoryReserved

## Условие

79. **Inventory Service**: `ReserveInventory` → `InventoryReserved` event

### Исходная формулировка

**Inventory Service**: `ReserveInventory` → `InventoryReserved` event

## Теория

В событийно-ориентированной архитектуре (Event-Driven Architecture) сервис управления складскими остатками (Inventory Service) не вызывает внешние API напрямую. Он принимает команду или событие о создании заказа, выполняет условную проверку остатков (Stock Verification) и при наличии свободных позиций переводит их в состояние `RESERVED` в рамках транзакции БД. Одновременно через Transactional Outbox формируется доменное событие `InventoryReservedEvent`. Если количество доступных товаров меньше запрашиваемого, генерируется альтернативное событие сбоя `InventoryReservationFailedEvent`. Все операции снабжаются версионированием строк для защиты от состояния гонки (Race Condition).

## Решение по шагам

1. Создайте структуру товара `InventoryItem` со счетчиками `TotalQty` и `ReservedQty`.
2. Реализуйте метод `ReserveInventory(orderID string, itemID string, qty int)` с потокобезопасной проверкой.
3. При успешном резервировании создайте событие `InventoryReservedEvent` и поместите его в Outbox.
4. При нехватке товара сформируйте ошибку и событие сбоя.
5. Продемонстрируйте сценарий успешного резервирования и генерацию события в `main`.

## Код решения

**`inventory_service.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type InventoryReservedEvent struct {
	EventID   string
	OrderID   string
	SKU       string
	Quantity  int
	Timestamp time.Time
}

type WarehouseManager struct {
	mu           sync.Mutex
	stock        map[string]int // SKU -> Доступное количество
	reservations map[string]int // OrderID:SKU -> Зарезервировано
	outboxEvents []InventoryReservedEvent
}

func NewWarehouseManager() *WarehouseManager {
	return &WarehouseManager{
		stock:        map[string]int{"SKU-MACBOOK": 5},
		reservations: make(map[string]int),
	}
}

func (w *WarehouseManager) ReserveInventory(ctx context.Context, orderID, sku string, qty int) (*InventoryReservedEvent, error) {
	w.mu.Lock()
	defer w.mu.Unlock()

	available := w.stock[sku]
	if available < qty {
		return nil, fmt.Errorf("insufficient stock for %s: requested %d, available %d", sku, qty, available)
	}

	// Списание из свободного остатка и перевод в резерв
	w.stock[sku] = available - qty
	resKey := fmt.Sprintf("%s:%s", orderID, sku)
	w.reservations[resKey] += qty

	event := InventoryReservedEvent{
		EventID:   fmt.Sprintf("evt-inv-%s", orderID),
		OrderID:   orderID,
		SKU:       sku,
		Quantity:  qty,
		Timestamp: time.Now(),
	}
	w.outboxEvents = append(w.outboxEvents, event)

	fmt.Printf("[Inventory Service] Successfully reserved %d of %s for Order %s. Remaining: %d\n",
		qty, sku, orderID, w.stock[sku])
	return &event, nil
}

func main() {
	warehouse := NewWarehouseManager()
	ctx := context.Background()

	// Заказ 1: резервируем 2 ноутбука
	evt, err := warehouse.ReserveInventory(ctx, "order-001", "SKU-MACBOOK", 2)
	if err != nil {
		fmt.Printf("Reservation failed: %v\n", err)
		return
	}
	fmt.Printf("[Outbox] Published Event: %s, OrderID: %s, Qty: %d\n", evt.EventID, evt.OrderID, evt.Quantity)

	// Заказ 2: попытка зарезервировать 4 ноутбука (при остатке 3) -> ошибка
	_, err2 := warehouse.ReserveInventory(ctx, "order-002", "SKU-MACBOOK", 4)
	if err2 != nil {
		fmt.Printf("[Inventory Service ERROR] %v\n", err2)
	}
}
```

ℹ️ Потокобезопасное резервирование товаров на складе и публикация InventoryReservedEvent

**`output.txt`**

```bash

[Outbox] Published Event: evt-inv-order-001, OrderID: order-001, Qty: 2
[Inventory Service ERROR] insufficient stock for SKU-MACBOOK: requested 4, available 3
```

## Под капотом

В PostgreSQL для резервирования остатков без оверселлинга используется атомарный запрос:
`UPDATE inventory SET quantity = quantity - $1 WHERE sku = $2 AND quantity >= $1 RETURNING id;`
Если ни одна строка не обновилась (`rows_affected == 0`), база мгновенно сообщает о нехватке остатка без необходимости ставить тяжелые табличные блокировки `LOCK TABLE`.

## Подводные камни

1. Зависшие резервы (Ghost Reservations): если сага упадет и не вызовет ни подтверждения, ни компенсации, зарезервированный товар никогда не вернется на полку. Необходим фоновый Sweeper с TTL для освобождения резервов старше допустимого таймаута.
2. Отрицательные остатки при параллельных отменах: декремент и инкремент остатков должны проверяться через CHECK constraint в схеме БД (`CHECK (quantity >= 0)`).

## На собеседовании

Вопрос: Как предотвратить оверселлинг в «Черную Пятницу» при миллионном RPS на ограниченный товар?
Ответ: Реляционная СУБД с `SELECT FOR UPDATE` станет узким горлышком из-за конкуренции блокировок строки. Применяется распределенный кеш Redis с Lua-скриптом для атомарного декремента (`DECRBY` с проверкой `>= 0`) или батчинг/сегментирование остатков (sharded counters) по нескольким партициям.
