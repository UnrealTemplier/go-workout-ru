# Saga Orchestration для complex flows: когда оркестрация обязательна и как ее масштабировать

## Условие

89. **Saga Orchestration для complex flows.**: Если у вас 5+ шагов с сложной логикой компенсаций — используйте Orchestration (Temporal/Cadence). Централизованный control проще для debugging.

### Исходная формулировка

**Saga Orchestration для complex flows.**: Если у вас 5+ шагов с сложной логикой компенсаций — используйте Orchestration (Temporal/Cadence). Централизованный control проще для debugging.

## Теория

С ростом микросервисной системы количество взаимодействий растет экспоненциально: \(O(N^2)\). Когда бизнес-сценарий включает 5 и более шагов (например: антифрод, скоринг, бронирование товара, списание бонусов, холдирование карты, вызов курьера, отправка фискального чека), децентрализованная хореография становится неуправляемой — никто в компании не может понять полный граф зависимостей. Оркестрация (Orchestration) через Temporal, Cadence или выделенный сервис оркестрации дает:
1) Декларативный граф процесса: весь сценарий описан в одном месте как читаемый код на Go;
2) Централизованный аудит: текущее состояние саги видно в одной консоли/БД;
3) Встроенный тайм-аут менеджмент и ретраи на уровне шагов;
4) Простое ручное вмешательство (Manual Intervention) при критических сбоях.

## Решение по шагам

1. Опишите многоэтапный процесс оформления кредита из 5 шагов.
2. Спроектируйте оркестратор с поддержкой условных ветвлений (If-Else в коде).
3. Реализуйте регистрацию компенсаций только для фактически выполненных ветвей.
4. Смоделируйте отказ на шаге выдачи средств и продемонстрируйте раскрутку графа назад.
5. Проанализируйте преимущества читаемости кода по сравнению с хореографией.

## Код решения

**`complex_orchestration_flow.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

type ComplexSagaContext struct {
	ApplicationID string
	Score         int
	ApprovedLimit float64
	AccountOpened bool
	FundsReserved bool
}

type LoanOrchestrator struct{}

func (o *LoanOrchestrator) ProcessLoan(ctx context.Context, appID string, requestedAmount float64) error {
	sagaCtx := &ComplexSagaContext{ApplicationID: appID}
	var compensations []func()

	defer func() {
		// Если что-то пошло не так, выполняем откат
		if r := recover(); r != nil {
			fmt.Printf("[CRASH HANDLER] Panic caught: %v. Rolling back...\n", r)
			for i := len(compensations) - 1; i >= 0; i-- {
				compensations[i]()
			}
		}
	}()

	fmt.Printf("[Orchestrator] Starting Complex Loan Saga for %s\n", appID)

	// Шаг 1: Скоринг в кредитном бюро
	fmt.Println("Step 1: Scoring Service Check -> OK (Score: 780)")
	sagaCtx.Score = 780

	// Шаг 2: Антифрод анализ
	fmt.Println("Step 2: Antifraud Service Check -> OK (Passed)")

	// Шаг 3: Открытие кредитного счета в главной банковской книге (Core Banking)
	fmt.Println("Step 3: Core Banking -> Account created")
	sagaCtx.AccountOpened = true
	compensations = append(compensations, func() {
		fmt.Println(" <- [Compensate Step 3] Core Banking: Account closed and marked VOID")
	})

	// Шаг 4: Резервирование лимита ликвидности в казначействе (Treasury)
	fmt.Println("Step 4: Treasury Service -> Liquidity reserved")
	sagaCtx.FundsReserved = true
	compensations = append(compensations, func() {
		fmt.Println(" <- [Compensate Step 4] Treasury: Liquidity released back to pool")
	})

	// Шаг 5: Перевод денег на карту клиента (Сбой платежного шлюза СБП)
	fmt.Println("Step 5: SBP Payment Gateway -> Sending funds...")
	errTransfer := errors.New("SBP Gateway 503: Core banking connection timeout")
	if errTransfer != nil {
		fmt.Printf("[Orchestrator] Step 5 failed: %v. Triggering dynamic compensations!\n", errTransfer)
		for i := len(compensations) - 1; i >= 0; i-- {
			compensations[i]()
		}
		return errTransfer
	}

	fmt.Println("[Orchestrator] Loan successfully disbursed!")
	return nil
}

func main() {
	orch := &LoanOrchestrator{}
	_ = orch.ProcessLoan(context.Background(), "loan-app-9912", 250000.0)
}
```

## Под капотом

При использовании Temporal воркфлоу компилируется в виде графа задач. Если шаг 1 (Scoring) или шаг 2 (Antifraud) только читали данные и не меняли состояние внешних систем, для них не требуется регистрировать компенсацию (ReadOnly Steps). Оркестратор точно знает, какие шаги изменили стейт, и формирует минимально необходимый вектор компенсаций.

## Подводные камни

1. Запуск блокирующих вызовов в основном потоке оркестратора без пула воркеров: при высоком RPS оркестратор исчерпает лимиты горутин и упадет по памяти. Необходимо использовать очереди задач (Task Queues).
2. Утечка секретов в историю саги: нельзя сохранять в стейт саги номера кредитных карт или CVV-коды, так как история событий пишется в персистентный лог.

## На собеседовании

Вопрос: Почему BigTech-компании отказываются от самописных оркестраторов в пользу Temporal?
Ответ: Самописный оркестратор требует огромного объема инфраструктурного кода: персистенция FSM, дедупликация, лидер-выборы, тайм-аут менеджеры, распределенные очереди, веб-интерфейс дебага, миграция схем версионирования. Temporal решает все эти проблемы 'из коробки' на уровне движка надежности, позволяя инженерам писать чистый бизнес-код воркфлоу на Go.
