# Оркестрация: чтение saga_states и пошаговый вызов компенсирующих команд

## Условие

82. **Оркестрация (Компенсация)**: Если Оркестратор вызвал `Inventory` и получил ошибку, он берет `saga_states`, смотрит, какие шаги уже были успешно выполнены (Payment), и по цепочке отправляет компенсирующие команды: `Call(Billing_Refund)`. Напиши этот механизм отката (Rollback).

### Исходная формулировка

**Оркестрация (Компенсация)**: Если Оркестратор вызвал `Inventory` и получил ошибку, он берет `saga_states`, смотрит, какие шаги уже были успешно выполнены (Payment), и по цепочке отправляет компенсирующие команды: `Call(Billing_Refund)`. Напиши этот механизм отката (Rollback).

## Теория

В отказоустойчивом оркестраторе список компенсирующих действий строится динамически на основе таблицы аудита состояний `saga_states`. Оркестратор не полагается на локальные переменные памяти. Когда очередной шаг возвращает ошибку, движок выполняет запрос к БД:
`SELECT step_name, step_data FROM saga_states WHERE saga_id = ? AND status = 'COMPLETED' ORDER BY step_order DESC;`
Получив упорядоченный срез успешно выполненных шагов, оркестратор поочередно вызывает соответствующую компенсирующую RPC-команду (`Call(Billing_Refund)`, `Call(Inventory_Release)`), передавая туда ранее сохраненные данные шага (`transaction_id`, `reservation_id`). Каждый успешный откат фиксируется в БД.

## Решение по шагам

1. Создайте структуру `SagaStepRecord` (StepName, Status, Payload, OrderIndex).
2. Реализуйте таблицу аудита состояний саги в памяти или СУБД.
3. Напишите метод `RollbackFromState(ctx, sagaID)`.
4. Выберите из БД выполненные шаги и отсортируйте их в обратном порядке.
5. Продемонстрируйте откат шага `Payment` после падения шага `Inventory`.

## Код решения

**`db_driven_rollback.go`**

```go
package main

import (
	"context"
	"fmt"
	"sort"
	"sync"
)

type StepLog struct {
	StepName string
	Order    int
	Status   string
	Data     string
}

type SagaAuditDB struct {
	mu   sync.Mutex
	logs map[string][]StepLog
}

func NewSagaAuditDB() *SagaAuditDB {
	return &SagaAuditDB{logs: make(map[string][]StepLog)}
}

func (db *SagaAuditDB) RecordStep(sagaID, step string, order int, status, data string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.logs[sagaID] = append(db.logs[sagaID], StepLog{
		StepName: step,
		Order:    order,
		Status:   status,
		Data:     data,
	})
	fmt.Printf("[Audit DB] Logged: Saga=%s, Step=%s, Status=%s\n", sagaID, step, status)
}

func (db *SagaAuditDB) GetCompletedStepsReversed(sagaID string) []StepLog {
	db.mu.Lock()
	defer db.mu.Unlock()

	var completed []StepLog
	for _, l := range db.logs[sagaID] {
		if l.Status == "COMPLETED" {
			completed = append(completed, l)
		}
	}

	// Сортировка в обратном порядке (LIFO)
	sort.Slice(completed, func(i, j int) bool {
		return completed[i].Order > completed[j].Order
	})
	return completed
}

type OrchestratorService struct {
	db *SagaAuditDB
}

func (o *OrchestratorService) ExecuteRollback(ctx context.Context, sagaID string) {
	fmt.Printf("\n[Orchestrator] Step failed! Querying DB for completed steps to rollback...\n")
	stepsToRollback := o.db.GetCompletedStepsReversed(sagaID)

	for _, step := range stepsToRollback {
		fmt.Printf("[Orchestrator Rollback] Compensating step '%s' (Original Order: %d, Data: %s)\n",
			step.StepName, step.Order, step.Data)

		switch step.StepName {
		case "Payment":
			// Вызов RPC Billing_Refund
			fmt.Printf(" -> RPC Call: BillingService.Refund(tx=%s)\n", step.Data)
			o.db.RecordStep(sagaID, "Payment_Compensated", step.Order, "COMPENSATED", "refund_ok")
		case "OrderInit":
			fmt.Printf(" -> RPC Call: OrderService.CancelOrder(order=%s)\n", step.Data)
			o.db.RecordStep(sagaID, "OrderInit_Compensated", step.Order, "COMPENSATED", "cancelled")
		}
	}
	fmt.Println("[Orchestrator] All compensations successfully processed.")
}

func main() {
	db := NewSagaAuditDB()
	orch := &OrchestratorService{db: db}
	ctx := context.Background()
	sagaID := "saga-xyz-404"

	// Шаг 0: Инициализация заказа
	db.RecordStep(sagaID, "OrderInit", 0, "COMPLETED", "order_id=404")

	// Шаг 1: Списание оплаты
	db.RecordStep(sagaID, "Payment", 1, "COMPLETED", "tx_bank_99881")

	// Шаг 2: Склад падает
	db.RecordStep(sagaID, "Inventory", 2, "FAILED", "err_out_of_stock")

	// Запуск отката на основе персистентного состояния в БД
	orch.ExecuteRollback(ctx, sagaID)
}
```

ℹ️ Динамический откат саги на основе выборки выполненных шагов из таблицы аудита БД

## Под капотом

Использование таблицы `saga_step_records` делает оркестратор stateless: любой под Kubernetes, получивший сигнал о падении шага или запустившийся после рестарта пода, может выполнить `SELECT ... WHERE status = 'COMPLETED'` и осуществить гарантированный откат. Это исключает зависимость от локальной памяти процесса.

## Подводные камни

1. Попытка компенсировать упавший шаг: компенсировать нужно ТОЛЬКО шаги со статусом `COMPLETED`. Шаг со статусом `FAILED` не производил изменений в бизнес-системе (его локальная транзакция откатилась), и вызов компенсации для него ошибочен.
2. Неполная история данных: если в таблицу аудита не записать параметры вызова (`Data`), оркестратор не будет знать, какую именно банковскую транзакцию нужно рефандить.

## На собеседовании

Вопрос: Что произойдет, если в ходе выполнения `ExecuteRollback` оркестратор снова упадет?
Ответ: При следующем запуске оркестратор снова выполнит выборку шагов для отката. Благодаря тому, что каждый компенсированный шаг помечается статусом `COMPENSATED`, оркестратор пропустит уже завершенные компенсации и продолжит откат оставшихся шагов. Это обеспечивает идемпотентность самого механизма отката.
