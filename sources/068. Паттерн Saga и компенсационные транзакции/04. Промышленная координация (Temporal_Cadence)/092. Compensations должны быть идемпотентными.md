# Compensations должны быть идемпотентными: защита от повторного возврата ресурсов

## Условие

92. **Compensations должны быть идемпотентными.**: `ReleaseInventory` с тем же order_id не должен releasing inventory дважды. Иначе compensation может создать новую inconsistency.

### Исходная формулировка

**Compensations должны быть идемпотентными.**: `ReleaseInventory` с тем же order_id не должен releasing inventory дважды. Иначе compensation может создать новую inconsistency.

## Теория

Идемпотентность компенсирующих транзакций — это закон распределенной целостности. Если прямой шаг может завершиться ошибкой, то компенсация обязана быть выполнена любой ценой, а значит, в условиях нестабильной сети оркестратор будет повторять вызов компенсации снова и снова (Retry). Если функция `ReleaseInventory(orderID)` при каждом вызове просто выполняет `stock = stock + reserved_qty`, то три сетевых повтора компенсации вернут на склад в 3 раза больше товара, чем было зарезервировано! Это порождает фантомные остатки на складе (Ghost Inventory) и катастрофическую рассинхронизацию. Компенсация обязана проверять статус резерва: `UPDATE inventory_reservations SET status = 'RELEASED' WHERE order_id = $1 AND status = 'RESERVED'`.

## Решение по шагам

1. Создайте структуру склада со статусами резервов (`RESERVED`, `RELEASED`).
2. Реализуйте метод компенсации `ReleaseInventoryIdempotent(orderID)`.
3. При первом вызове переведите статус в `RELEASED` и увеличьте доступный остаток.
4. При повторных вызовах с тем же `orderID` зафиксируйте, что резерв уже скомпенсирован, и верните успех без начисления остатков.
5. Продемонстрируйте 3 последовательных вызова компенсации в `main`.

## Код решения

**`idempotent_compensation.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type ReservationStatus string

const (
	StatusReserved ReservationStatus = "RESERVED"
	StatusReleased ReservationStatus = "RELEASED"
)

type ItemReservation struct {
	OrderID  string
	SKU      string
	Quantity int
	Status   ReservationStatus
}

type SafeWarehouse struct {
	mu           sync.Mutex
	stock        map[string]int
	reservations map[string]*ItemReservation
}

func NewSafeWarehouse() *SafeWarehouse {
	wh := &SafeWarehouse{
		stock:        map[string]int{"SKU-IPHONE": 10},
		reservations: make(map[string]*ItemReservation),
	}
	// Инициализируем резерв заказа
	wh.reservations["order-404"] = &ItemReservation{
		OrderID:  "order-404",
		SKU:      "SKU-IPHONE",
		Quantity: 2,
		Status:   StatusReserved,
	}
	wh.stock["SKU-IPHONE"] -= 2 // 8 осталось на складе
	return wh
}

// ReleaseInventoryIdempotent безопасно освобождает остатки ровно один раз
func (w *SafeWarehouse) ReleaseInventoryIdempotent(ctx context.Context, orderID string) error {
	w.mu.Lock()
	defer w.mu.Unlock()

	res, exists := w.reservations[orderID]
	if !exists {
		// Если записи резерва нет, ничего не возвращаем (No-Op)
		fmt.Printf("[Compensation NO-OP] No reservation found for order %s\n", orderID)
		return nil
	}

	// Проверка статуса: если уже RELEASED, возвращаем успех без изменения стока
	if res.Status == StatusReleased {
		fmt.Printf("[Compensation IDEMPOTENT HIT] Order %s already released. Stock untouched: %d\n",
			orderID, w.stock[res.SKU])
		return nil
	}

	// Первое выполнение компенсации
	res.Status = StatusReleased
	w.stock[res.SKU] += res.Quantity
	fmt.Printf("[Compensation EXECUTED] Order %s released %d items of %s. New stock: %d\n",
		orderID, res.Quantity, res.SKU, w.stock[res.SKU])
	return nil
}

func main() {
	warehouse := NewSafeWarehouse()
	ctx := context.Background()

	orderID := "order-404"

	// Вызов 1: Первый откат
	fmt.Println("Attempt 1 (First compensation call):")
	_ = warehouse.ReleaseInventoryIdempotent(ctx, orderID)

	// Вызов 2: Повторный сетевой вызов (ретрай оркестратора)
	fmt.Println("\nAttempt 2 (Network retry with same orderID):")
	_ = warehouse.ReleaseInventoryIdempotent(ctx, orderID)

	// Вызов 3: Еще один повторный вызов
	fmt.Println("\nAttempt 3 (Third retry):")
	_ = warehouse.ReleaseInventoryIdempotent(ctx, orderID)
}
```

ℹ️ Идемпотентная компенсация склада: гарантированное предотвращение повторного начисления остатка

**`output.txt`**

```bash

[Compensation EXECUTED] Order order-404 released 2 items of SKU-IPHONE. New stock: 10

Attempt 2 (Network retry with same orderID):
[Compensation IDEMPOTENT HIT] Order order-404 already released. Stock untouched: 10

Attempt 3 (Third retry):
[Compensation IDEMPOTENT HIT] Order order-404 already released. Stock untouched: 10
```

## Под капотом

На уровне SQL-запроса идемпотентная компенсация оформляется атомарным предикатом:
`WITH updated AS (`
`  UPDATE reservations SET status = 'RELEASED' `
`  WHERE order_id = $1 AND status = 'RESERVED' RETURNING sku, quantity`
`) UPDATE inventory SET stock = stock + u.quantity FROM updated u WHERE inventory.sku = u.sku;`
Если статус уже был `RELEASED`, CTE `updated` вернет 0 строк, и второй `UPDATE` даже не затронет таблицу товаров.

## Подводные камни

1. Возврат ошибки при повторном вызове: если метод компенсации вернет ошибку `ErrAlreadyReleased`, оркестратор подумает, что компенсация провалилась, и начнет спамить алертами. Повторный вызов должен возвращать `nil` (Success).
2. Компенсация несуществующего резерва: если из-за гонки откат пришел раньше бронирования, необходимо сохранить маркер `status = CANCELED_EARLY`.

## На собеседовании

Вопрос: Что произойдет, если запрос компенсации придет РАНИШЕ, чем прямой запрос резервирования?
Ответ: Это феномен 'Out-of-Order Message'. Если сервис склада просто вернет 404, а через 100 мс придет задержавшийся прямой запрос `ReserveInventory`, он зарезервирует товар, который уже никто не снимет. Решение: сервис записывает `tombstone` (маркер отмены) в таблицу резервов. Когда запоздалый прямой запрос придет, он увидит tombstone и сразу завершится с ошибкой.
