### Исходная формулировка

**Shipping Service**: `CreateShipment` → `ShipmentCreated` event

**Compensation Flow:**
* Если `ProcessPayment` fails → `ReleaseInventory` + `CancelOrder`
* Если `CreateShipment` fails → `RefundPayment` + `ReleaseInventory` + `CancelOrder`

**Reliability Patterns:**
* Каждый сервис использует **Transactional Outbox** для publishing events
* Каждый сервис использует **Transactional Inbox** для consuming commands
* **Idempotency keys** для всех API endpoints и Saga steps
* **Saga state** persisted в БД orchestrator
* **Timeouts** для каждого шага и overall Saga
* **Retries** с exponential backoff для transient failures
* **Dead letter queues** для failed events/commands

**Observability:**
* OpenTelemetry traces для каждого Saga step
* Prometheus metrics: Saga success rate, step latency, compensation rate
* Grafana dashboard: active Sagas, failed steps, outbox/inbox lag
* Alerting: high compensation rate, outbox lag > 1000, inbox lag > 1000

## Теория

Служба доставки (Shipping Service) является третьим звеном цепочки исполнения заказа. Она взаимодействует с логистическими провайдерами (Яндекс Доставка, СДЭК, Boxberry). В случае невозможности назначить курьера или зарегистрировать накладную, сага входит в фазу каскадной компенсации. Так как к этому моменту уже успешно выполнены списание средств и бронирование на складе, координатор обязан в строгом обратном порядке (LIFO) вызвать:
1) `RefundPayment` (возврат денег клиенту);
2) `ReleaseInventory` (возврат товаров на склад);
3) `CancelOrder` (перевод заказа в финальный статус CANCELLED).

## Решение по шагам

1. Создайте доменное событие `ShipmentCreatedEvent` с трек-номером.
2. Реализуйте метод `CreateShipment` с возможностью симуляции сбоя логистики.
3. Постройте координатор каскадного отката (LIFO Rollback Engine).
4. Смоделируйте ошибку логистики и продемонстрируйте исполнение трех компенсаций: Refund -> Release -> Cancel.
5. Продемонстрируйте логирование метрик и трейсинга.

## Код решения

**`shipping_and_rollback.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type StepAction func(ctx context.Context) error

type CascadeSagaCoordinator struct {
	compensations []StepAction
}

func (c *CascadeSagaCoordinator) AddCompensation(action StepAction) {
	c.compensations = append(c.compensations, action)
}

func (c *CascadeSagaCoordinator) Rollback(ctx context.Context) {
	fmt.Printf("[Saga Engine] Initiating cascade rollback (%d compensations in LIFO order)...\n", len(c.compensations))
	for i := len(c.compensations) - 1; i >= 0; i-- {
		if err := c.compensations[i](ctx); err != nil {
			fmt.Printf("[CRITICAL ROLLBACK ERROR] Step %d failed: %v\n", i, err)
		}
	}
}

func main() {
	ctx := context.Background()
	coord := &CascadeSagaCoordinator{}
	orderID := "ord-global-999"

	// Шаг 1: Заказ создан в БД
	fmt.Printf("[Order Service] Order %s created (status: PENDING)\n", orderID)
	coord.AddCompensation(func(c context.Context) error {
		fmt.Printf(" -> [Compensate 3] Order %s status updated to CANCELLED\n", orderID)
		return nil
	})

	// Шаг 2: Склад зарезервирован
	fmt.Printf("[Inventory Service] Stock reserved for order %s\n", orderID)
	coord.AddCompensation(func(c context.Context) error {
		fmt.Printf(" -> [Compensate 2] Inventory released for order %s\n", orderID)
		return nil
	})

	// Шаг 3: Оплата списана
	fmt.Printf("[Payment Service] Charged $1200 for order %s\n", orderID)
	coord.AddCompensation(func(c context.Context) error {
		fmt.Printf(" -> [Compensate 1] Payment $1200 refunded for order %s\n", orderID)
		return nil
	})

	// Шаг 4: Попытка оформить доставку в Shipping Service (сбой)
	fmt.Println("[Shipping Service] Calling Courier API: CreateShipment...")
	time.Sleep(50 * time.Millisecond)
	errDelivery := errors.New("courier allocation timeout: no drivers nearby")

	fmt.Printf("[Shipping Service FAILED] %v\n", errDelivery)

	// Запуск каскадного отката
	coord.Rollback(ctx)
	fmt.Println("[Saga Engine] Compensation flow finished. Eventual consistency restored.")
}
```

ℹ️ Многоуровневый каскадный откат саги при сбое службы доставки

## Под капотом

При каскадной компенсации критично соблюдать порядок LIFO. Если сначала отменить заказ в БД, а затем попытаться вернуть средства в банке, клиентский вебхук от банка может быть отклонен сервисом заказов как относящийся к несуществующему/закрытому заказу. Строгая последовательность `Refund -> Release Inventory -> Cancel Order` гарантирует соблюдение внешних бизнес-инвариантов.

## Подводные камни

1. Потеря стека компенсаций при перезапуске координатора: если воркер упадет между ошибкой доставки и выполнением отката, список `compensations` в оперативной памяти будет утерян. Список завершенных шагов обязан персистироваться в таблице `saga_steps` с отметкой `completed_at`.
2. Игнорирование ошибок в компенсирующих шагах: если `RefundPayment` вернул сетевую ошибку 503, оркестратор не должен переходить к следующей компенсации — он обязан ретраить текущую компенсацию.

## На собеседовании

Вопрос: Что произойдет, если в процессе выполнения отката сервис возврата платежей упадет навсегда?
Ответ: Сага не может откатиться сама и переходит в статус `COMPENSATION_STUCK`. В системе Prometheus срабатывает критический P1-алерт `alert: SagaCompensationFailed`. Доменные сущности блокируются семантическим флагом `IS_LOCKED_FOR_MAINTENANCE`, и на дежурного инженера открывается тикет с прямыми ссылками на платежную транзакцию в админке эквайринга.
