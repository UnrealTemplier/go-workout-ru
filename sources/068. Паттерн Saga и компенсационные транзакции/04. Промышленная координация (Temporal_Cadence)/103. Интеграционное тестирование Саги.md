## Теория

Интеграционный тест Саги — это высший критерий проверки распределенной архитектуры. В отличие от юнит-тестов с моками, сквозной интеграционный тест разворачивает изолированные экземпляры реальных баз данных (через Testcontainers-go) и проверяет физическое состояние таблиц во всех трех микросервисах (Order, Billing, Warehouse):
1) Тест Happy Path: проверяет, что заказ стал `COMPLETED`, баланс покупателя уменьшился на $X, а остаток на складе уменьшился на $Y;
2) Тест Rollback: симулирует сбой на финальном шаге и проверяет инвариант консистентности: баланс пользователя строго равен начальному, остаток склада строго равен начальному, а статус заказа равен `CANCELLED`.

## Решение по шагам

1. Создайте структуры баз данных для сервисов Заказов, Биллинга и Склада.
2. Реализуйте тестовый сценарий `TestSagaHappyPath` и проверьте финализацию всех баз.
3. Реализуйте тестовый сценарий `TestSagaRollback` с искусственным падением склада.
4. Выполните проверку математического равенства остатков до и после сбоя.
5. Продемонстрируйте запуск и успешный вердикт теста в `main`.

## Код решения

**`saga_integration_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

type DBOrderService struct {
	Orders map[string]string // orderID -> status
}

type DBBillingService struct {
	Balances map[string]float64 // userID -> balance
}

type DBWarehouseService struct {
	Stock map[string]int // sku -> qty
}

type IntegratedSystem struct {
	orderDB     *DBOrderService
	billingDB   *DBBillingService
	warehouseDB *DBWarehouseService
}

func NewSystem() *IntegratedSystem {
	return &IntegratedSystem{
		orderDB:     &DBOrderService{Orders: make(map[string]string)},
		billingDB:   &DBBillingService{Balances: map[string]float64{"user-1": 10000.0}},
		warehouseDB: &DBWarehouseService{Stock: map[string]int{"LAPTOP": 5}},
	}
}

func (sys *IntegratedSystem) RunOrderSaga(ctx context.Context, orderID, userID, sku string, price float64, qty int, failAtWarehouse bool) error {
	// Шаг 1: Создание заказа
	sys.orderDB.Orders[orderID] = "PENDING"

	// Шаг 2: Списание баланса
	if sys.billingDB.Balances[userID] < price {
		sys.orderDB.Orders[orderID] = "CANCELLED"
		return errors.New("insufficient balance")
	}
	sys.billingDB.Balances[userID] -= price

	// Шаг 3: Склад (с симуляцией сбоя)
	if failAtWarehouse || sys.warehouseDB.Stock[sku] < qty {
		// Запуск компенсации
		sys.billingDB.Balances[userID] += price // Возврат денег
		sys.orderDB.Orders[orderID] = "CANCELLED"
		return errors.New("warehouse unavailable or out of stock")
	}

	sys.warehouseDB.Stock[sku] -= qty
	sys.orderDB.Orders[orderID] = "COMPLETED"
	return nil
}

func main() {
	ctx := context.Background()

	// ТЕСТ 1: Успешный сценарий (Happy Path)
	fmt.Println("=== TEST 1: Happy Path Integration Test ===")
	sys1 := NewSystem()
	err1 := sys1.RunOrderSaga(ctx, "ord-1", "user-1", "LAPTOP", 2500.0, 1, false)
	if err1 != nil {
		panic(err1)
	}

	fmt.Printf("Order DB Status: %s (Expected: COMPLETED)\n", sys1.orderDB.Orders["ord-1"])
	fmt.Printf("Billing DB Balance: %.2f (Expected: 7500.00)\n", sys1.billingDB.Balances["user-1"])
	fmt.Printf("Warehouse DB Stock: %d (Expected: 4)\n", sys1.warehouseDB.Stock["LAPTOP"])

	// ТЕСТ 2: Сценарий отката (Rollback Consistency Test)
	fmt.Println("\n=== TEST 2: Rollback Consistency Test ===")
	sys2 := NewSystem()
	initialBalance := sys2.billingDB.Balances["user-1"]
	initialStock := sys2.warehouseDB.Stock["LAPTOP"]

	err2 := sys2.RunOrderSaga(ctx, "ord-2", "user-1", "LAPTOP", 2500.0, 1, true) // Сбой склада!
	fmt.Printf("Saga returned error: %v\n", err2)

	fmt.Printf("Order DB Status: %s (Expected: CANCELLED)\n", sys2.orderDB.Orders["ord-2"])
	fmt.Printf("Billing DB Balance: %.2f (Expected: %.2f - Full Refund!)\n",
		sys2.billingDB.Balances["user-1"], initialBalance)
	fmt.Printf("Warehouse DB Stock: %d (Expected: %d - Stock Untouched!)\n",
		sys2.warehouseDB.Stock["LAPTOP"], initialStock)

	if sys2.billingDB.Balances["user-1"] == initialBalance && sys2.warehouseDB.Stock["LAPTOP"] == initialStock {
		fmt.Println("\n>>> INTEGRATION TEST PASSED: Eventual consistency 100% verified! <<<")
	}
}
```

## Под капотом

В реальных CI/CD пайплайнах Testcontainers-go запускает три контейнера PostgreSQL. Тест создает сетевой барьер через `toxiproxy`, временно отключая порт 5432 Склада. После падения шага тест запрашивает базы напрямую через `sql.Open` и сверяет числовые балансы до копейки.

## Подводные камни

1. Запуск интеграционных тестов с общим состоянием БД: если тесты выполняются параллельно и используют одну базу, они начнут перезаписывать данные друг друга. Каждый тест обязан создавать изолированную схему или базу данных.
2. Отсутствие таймаута на ожидание Eventual Consistency: в асинхронных тестах нельзя сразу читать БД — необходимо использовать `require.Eventually(t, checkFunc, 5*time.Second, 100*time.Millisecond)`.

## На собеседовании

Вопрос: Как тестировать распределенную сагу на утечки ресурсов при неожиданных крашах (SIGKILL)?
Ответ: Используются тесты восстановления (Recovery Tests). Процесс оркестратора запускается как дочерний процесс операционной системы. В середине выполнения шага 2 родительский тест посылает ему `SIGKILL`. Затем запускается второй экземпляр оркестратора, который выполняет Crash Recovery. Тест проверяет, что все незавершенные саги были успешно доведены до финала или скомпенсированы.
