# Test failure scenarios: Chaos Testing и верификация нештатных сбоев Саги

### Исходная формулировка

**Test failure scenarios.**: Happy path testing недостаточно. Тестируйте:
* Service crash во время Saga
* Network timeout
* Duplicate requests
* Duplicate events
* Compensation failures

## Теория

В распределенных транзакциях успешный сценарий (Happy Path) составляет менее 20% сложности системы. Остальные 80% — это обработка аномалий и сбоев. Надежность архитектуры Саги доказывается только через методики Chaos Engineering и негативное тестирование:
1) Аварийное падение (Kill Pod / SIGKILL) в середине транзакции;
2) Обрыв сетевого соединения (Network Partition) во время ожидания RPC ответа;
3) Дубликаты запросов и событий в брокере сообщений;
4) Сбои в самой фазе отката (Compensation Failures) — зависание компенсирующего сервиса.
Автотест обязан проверять, что при любых комбинациях этих сбоев система в итоге приходит в согласованное состояние (Eventual Consistency).

## Решение по шагам

1. Создайте симулятор хаоса `ChaosSimulator` с вероятностными или управляемыми инъекциями ошибок.
2. Смоделируйте сбой сети на шаге 2 и падение самого оркестратора.
3. Запустите оркестратор восстановления (Recovery Process).
4. Убедитесь в отсутствии потерянных ресурсов и корректном завершении отката.
5. Продемонстрируйте успешное прохождение стресс-теста.

## Код решения

**`chaos_saga_test.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"testing"
)

type MockStep struct {
	name          string
	failExecute   bool
	failCompensate bool
	executed      bool
	compensated   bool
}

func (s *MockStep) Execute() error {
	if s.failExecute {
		return errors.New("simulated network crash during execute")
	}
	s.executed = true
	return nil
}

func (s *MockStep) Compensate() error {
	if s.failCompensate {
		return errors.New("simulated database timeout during compensation")
	}
	s.compensated = true
	return nil
}

func TestSagaChaosFailure(t *testing.T) {
	// Подготовка шагов: Шаг 0 успешен, Шаг 1 падает на выполнении
	step0 := &MockStep{name: "DebitUser"}
	step1 := &MockStep{name: "ReserveStock", failExecute: true}

	steps := []*MockStep{step0, step1}

	// Запуск движка
	var executedSteps []*MockStep
	var sagaErr error

	for _, s := range steps {
		if err := s.Execute(); err != nil {
			sagaErr = err
			break
		}
		executedSteps = append(executedSteps, s)
	}

	if sagaErr == nil {
		t.Fatal("Expected saga to fail, but it succeeded")
	}
	fmt.Printf("[Test] Saga failed as expected: %v\n", sagaErr)

	// Выполнение отката
	for i := len(executedSteps) - 1; i >= 0; i-- {
		_ = executedSteps[i].Compensate()
	}

	// Верификация инвариантов
	if !step0.executed {
		t.Error("Step 0 should have been executed")
	}
	if !step0.compensated {
		t.Error("Step 0 MUST be compensated after Step 1 failure!")
	}
	if step1.compensated {
		t.Error("Step 1 failed execution, so it must NOT be compensated!")
	}

	fmt.Println("[Test SUCCESS] Invariants verified: Step 0 compensated, Step 1 untouched.")
}

func main() {
	// Запуск теста напрямую в консоли
	TestSagaChaosFailure(&testing.T{})
}
```

ℹ️ Негативное тестирование распределенной саги с инъекцией сбоев и проверкой инвариантов

**`output.txt`**

```bash
[Test] Saga failed as expected: simulated network crash during execute
[Test SUCCESS] Invariants verified: Step 0 compensated, Step 1 untouched.
```

ℹ️ Тест успешно подтвердил корректность отката выполненных шагов при сбое

## Под капотом

Для Chaos Testing в Kubernetes применяются утилиты Chaos Mesh или Litmus. Они внедряют задержки пакетов (NetEm: `tc qdisc add dev eth0 root netem delay 200ms`), вызывают дроп TCP-пакетов или хаотично убивают поды базы данных (`pod-kill`). Тест признается успешным только если после восстановления подов база саг не содержит зависших записей.

## Подводные камни

1. Тестирование только на моках: юнит-тесты на моках скрывают проблемы реальных сетевых таймаутов и гонок транзакций БД. Необходимы тесты с реальными PostgreSQL и Kafka через Testcontainers-go.
2. Игнорирование проверки состояния БД: проверка возвращаемой ошибки недостаточна — нужно напрямую проверять строки в таблицах балансов и заказов.

## На собеседовании

Вопрос: Что такое Jepsen-тестирование и применимо ли оно к Сагам?
Ответ: Jepsen (фреймворк Кайла Кингсбери) — это эталон тестирования распределенных систем в условиях сетевых разделений (Split-Brain). Для Саги Jepsen-подобный генератор посылает параллельные запросы создания заказов и отмен, одновременно симулируя изоляцию нод сети, а чекер проверяет линеаризуемость и отсутствие расхождений в балансах мерчантов и покупателей.
