## Теория

Двухфазный коммит (Two-Phase Commit / XA Transactions) был стандартом распределенной согласованности в монолитных базах данных 1990-х годов. В фазе Prepare координатор блокирует строки во всех базах и ждет подтверждения готовности. Во второй фазе отправляется Commit. В микросервисной архитектуре 2PC категорически неприменим по трем причинам:
1) Блокирующий протокол (Blocking Nature): если координатор упадет между фазами 1 и 2, все базы останутся с заблокированными строками навсегда (Deadlock/Out of Connections);
2) Катастрофическое падение пропускной способности: время удержания блокировок растет с 1 мс до 100+ мс из-за сетевых задержек (RTT) между сервисами, снижая RPS системы в сотни раз;
3) Гетерогенность: современные сервисы используют NoSQL, Kafka, S3, внешние Stripe API, которые в принципе не поддерживают XA-транзакции. Паттерн Сага заменяет жесткую согласованность (ACID/CP) на базовую доступность и согласованность в конечном счете (BASE/AP).

## Код решения

**`twopc_vs_saga_comparison.go`**

```go
package main

import (
	"fmt"
	"time"
)

// Моделирование 2PC: Ресурс блокируется на время сетевого обмена
func Simulate2PC() {
	start := time.Now()
	fmt.Println("=== 2PC (Two-Phase Commit) Simulation ===")
	fmt.Println(" Phase 1: PREPARE -> Acquiring pessimistic row lock on DB1 and DB2...")

	// Ресурс заблокирован! Другие транзакции ждут.
	time.Sleep(100 * time.Millisecond) // Сетевой RTT координатора к базам

	fmt.Println(" Phase 2: COMMIT -> Releasing locks and committing...")
	time.Sleep(50 * time.Millisecond)

	duration := time.Since(start)
	fmt.Printf("2PC Finished. Total Lock Hold Duration: %v (Pessimistic lock held all the time!)\n\n", duration)
}

// Моделирование Saga: Локальные транзакции завершаются мгновенно
func SimulateSaga() {
	start := time.Now()
	fmt.Println("=== Saga Pattern Simulation ===")
	fmt.Println(" Step 1: Local TX committed in Service A (Lock held for 2ms). Event published.")
	time.Sleep(2 * time.Millisecond) // Реальное время локального коммита

	fmt.Println(" Network transfer via Kafka message bus...")
	time.Sleep(100 * time.Millisecond) // Сеть работает асинхронно, база не заблокирована!

	fmt.Println(" Step 2: Local TX committed in Service B (Lock held for 2ms).")
	time.Sleep(2 * time.Millisecond)

	duration := time.Since(start)
	fmt.Printf("Saga Finished. Total DB Lock Hold Duration: ~4ms! (Total workflow: %v)\n", duration)
}

func main() {
	Simulate2PC()
	SimulateSaga()
}
```

ℹ️ Сравнение времени удержания распределенных блокировок: 2PC против Saga

## Под капотом

Математическое доказательство CAP/PACELC теоремы гласит: при сетевом разделении (Network Partition) система обязана выбирать между доступностью (Availability) и согласованностью (Consistency). 2PC выбирает строгое CP — при потере одного пакета вся система останавливается. Сага выбирает AP — каждый сервис продолжает отвечать на запросы, фиксируя локальные коммиты, а согласованность достигается асинхронно (Eventual Consistency).

## Подводные камни

1. Попытка внедрить XA-транзакции поверх микросервисов: любая задержка сети или рестарт пода приведет к каскадному исчерпанию пула соединений во всех связанных СУБД.
2. Ожидание немедленной консистентности в UI: после перехода на Сагу интерфейс не должен ожидать синхронного коммита всех сервисов — UI показывает статус `Обрабатывается` и слушает SSE/WebSocket.

## На собеседовании

Вопрос: Существуют ли современные сценарии, где 2PC все еще оправдан?
Ответ: Да, но только внутри одного датацентра в специализированных распределенных базах данных (Google Spanner, CockroachDB, YugabyteDB), где протокол 2PC работает поверх распределенного консенсуса Raft/Paxos с атомными часами (TrueTime) и аппаратной оптимизацией сетевых задержек. На уровне прикладных микросервисов 2PC не применяется никогда.
