### Исходная формулировка

Метод `Run()` должен идти по срезу вперед, вызывая `Execute`. Если на шаге N ошибка, движок должен пойти в цикле назад от N-1 до 0, вызывая `Compensate`.

## Теория

Saga Execution Coordinator (SEC) — это архитектурное ядро паттерна Сага. Универсальный движок SEC абстрагирует конкретную предметную область через интерфейс `Step`: каждый шаг обязан предоставлять прямое действие (`Execute`) и компенсирующее действие (`Compensate`). Движок выполняет шаги строго последовательно. При возникновении ошибки на шаге \(N\) прямое выполнение немедленно прерывается, и запускается цикл компенсаций от \(N-1\) вниз до \(0\) (LIFO). Это математически доказывает восстановление инвариантов системы до исходного состояния.

## Решение по шагам

1. Объявите интерфейс `Step` с методами `Execute(ctx context.Context) error` и `Compensate(ctx context.Context) error`.
2. Создайте структуру `SagaCoordinator` со срезом шагов `[]Step`.
3. Реализуйте метод `Run(ctx context.Context)`.
4. В цикле вперед вызывайте `Execute`. При ошибке запустите цикл отката от \(i-1\) до 0.
5. Продемонстрируйте работу движка на трех тестовых шагах с ошибкой на третьем шаге.

## Код решения

**`sec_engine.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

type Step interface {
	Name() string
	Execute(ctx context.Context) error
	Compensate(ctx context.Context) error
}

type GenericSEC struct {
	steps []Step
}

func NewGenericSEC(steps ...Step) *GenericSEC {
	return &GenericSEC{steps: steps}
}

func (sec *GenericSEC) Run(ctx context.Context) error {
	fmt.Printf("[SEC Engine] Starting Saga execution pipeline (%d steps)...\n", len(sec.steps))

	for i, step := range sec.steps {
		fmt.Printf("[SEC Engine] Step %d: Executing '%s'...\n", i, step.Name())
		if err := step.Execute(ctx); err != nil {
			fmt.Printf("[SEC Engine] Step %d ('%s') FAILED: %v\n", i, step.Name(), err)
			sec.compensate(ctx, i-1)
			return fmt.Errorf("saga failed at step %d (%s): %w", i, step.Name(), err)
		}
	}

	fmt.Println("[SEC Engine] Saga pipeline successfully completed!")
	return nil
}

func (sec *GenericSEC) compensate(ctx context.Context, fromIndex int) {
	fmt.Printf("[SEC Engine] Initiating LIFO rollback from step index %d down to 0...\n", fromIndex)
	for c := fromIndex; c >= 0; c-- {
		step := sec.steps[c]
		fmt.Printf(" -> Compensating Step %d: '%s'...\n", c, step.Name())
		if err := step.Compensate(ctx); err != nil {
			fmt.Printf("[SEC CRITICAL] Failed to compensate step '%s': %v\n", step.Name(), err)
		}
	}
	fmt.Println("[SEC Engine] Compensation phase completed.")
}

// Конкретные шаги саги
type PaymentStep struct{}

func (s *PaymentStep) Name() string                     { return "PaymentAuthorization" }
func (s *PaymentStep) Execute(ctx context.Context) error { fmt.Println("   [Payment] $500 authorized"); return nil }
func (s *PaymentStep) Compensate(ctx context.Context) error {
	fmt.Println("   [Payment] $500 voided/refunded")
	return nil
}

type StockStep struct{}

func (s *StockStep) Name() string                     { return "StockReservation" }
func (s *StockStep) Execute(ctx context.Context) error { fmt.Println("   [Stock] Items reserved in warehouse"); return nil }
func (s *StockStep) Compensate(ctx context.Context) error {
	fmt.Println("   [Stock] Items returned to warehouse shelves")
	return nil
}

type DeliveryStep struct{}

func (s *DeliveryStep) Name() string { return "CourierBooking" }
func (s *DeliveryStep) Execute(ctx context.Context) error {
	return errors.New("courier allocation failed: heavy snowstorm")
}
func (s *DeliveryStep) Compensate(ctx context.Context) error { return nil }

func main() {
	ctx := context.Background()

	sec := NewGenericSEC(
		&PaymentStep{},
		&StockStep{},
		&DeliveryStep{},
	)

	err := sec.Run(ctx)
	if err != nil {
		fmt.Printf("\n[Result] Final error returned to caller: %v\n", err)
	}
}
```

## Под капотом

Generic SEC является фундаментом библиотек Temporal, Cadence и dtmsvr. Главное достоинство такого паттерна — открытость для расширения (OCP): новые шаги добавляются без изменения кода самого координатора. В промышленной реализации вызовы `Execute` и `Compensate` оборачиваются в RetryPolicy с экспоненциальным backoff.

## Подводные камни

1. Попытка компенсировать упавший шаг: если начать откат с индекса \(N\) вместо \(N-1\), компенсация шага, который не выполнился, приведет к ошибкам (например, попытка отменить незабронированного курьера).
2. Паника в функции компенсации: паника внутри `Compensate` должна обязательно перехватываться `recover()`, иначе процесс упадет, прервав откат остальных шагов.

## На собеседовании

Вопрос: Что делать, если при вызове `Compensate` контекст `ctx` уже отменен по общему таймауту саги?
Ответ: Это классическая ловушка. Если контекст саги истек (`context deadline exceeded`), все последующие сетевые вызовы в `Compensate(ctx)` мгновенно упадут. Для фазы компенсации необходимо создавать новый detached контекст: `compCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)`.
