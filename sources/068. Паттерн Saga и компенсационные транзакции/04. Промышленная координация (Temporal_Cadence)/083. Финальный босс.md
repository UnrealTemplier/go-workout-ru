# Финальный босс: платформа на базе событийной хореографии и Saga Tracker Service

## Условие

83. **Финальный босс (Event-Driven Choreography Platform):**
    Создайте децентрализованную платформу через Choreography:
    * **Order Service:** публикует `OrderCreated`, `OrderCancelled`
    * **Inventory Service:** слушает `OrderCreated` → `InventoryReserved`/`InventoryReservationFailed`
    * **Payment Service:** слушает `InventoryReserved` → `PaymentProcessed`/`PaymentFailed`
    * **Shipping Service:** слушает `PaymentProcessed` → `ShipmentCreated`
    * **Notification Service:** слушает все события для email/SMS
    * **Saga Tracker Service:** слушает все события, агрегирует стейт по saga_id, детектирует таймауты.

### Исходная формулировка

**Финальный босс (Event-Driven Choreography Platform):**
Создайте децентрализованную платформу через Choreography:

**Services:**
* **Order Service:** публикует `OrderCreated`, `OrderCancelled`
* **Inventory Service:** слушает `OrderCreated` → `InventoryReserved`/`InventoryReservationFailed`
* **Payment Service:** слушает `InventoryReserved` → `PaymentProcessed`/`PaymentFailed`
* **Shipping Service:** слушает `PaymentProcessed` → `ShipmentCreated`
* **Notification Service:** слушает все события для email/SMS

**Compensation через events:**
* `PaymentFailed` → Inventory Service слушает → `InventoryReleased`
* `InventoryReleased` → Order Service слушает → `OrderCancelled`

**Reliability:**
* Каждый сервис использует **Outbox** для publishing events
* Каждый сервис использует **Inbox** для consuming events
* **Idempotent event handlers** через message_id deduplication
* **Event ordering** через Kafka partition key (order_id)
* **Dead letter queues** для failed events

**Saga Tracking:**
* Отдельный **Saga Tracker Service** слушает все events
* Aggregates state по saga_id (order_id)
* Detects stuck Sagas (timeout без completion)
* Publishes `SagaTimeout` events для trigger compensation

**Observability:**
* Distributed tracing через correlation_id (order_id)
* Event flow visualization в Grafana
* Metrics: event processing latency, event lag, compensation rate

**Testing:**
* Event replay для debugging
* Chaos testing: убивайте сервисы, проверяйте eventual consistency
* Duplicate event testing: отправляйте duplicate events

## Теория

Event-Driven Choreography Platform демонстрирует промышленную реализацию децентрализованной саги. Сервисы абсолютно изолированы и взаимодействуют исключительно через публикацию событий в брокер. Главная проблема чистой хореографии — 'слепое пятно' (Blind Spot), когда невозможно быстро понять, на каком этапе находится заказ. Для устранения этого недостатка в архитектуру вводится Saga Tracker Service (Observer Pattern). Он пассивно подписывается на wildcard-топики (`order.*`), агрегирует текущее состояние графа саги в Read-Only проекции (CQRS) и запускает таймер таймаута: если за 30 секунд сага не дошла до финала, Saga Tracker публикует `SagaTimeoutEvent`, инициируя распределенную компенсацию.

## Решение по шагам

1. Создайте шину событий с поддержкой подписчиков по топикам.
2. Реализуйте 5 микросервисов: Order, Inventory, Payment, Shipping, Notification.
3. Реализуйте сервис `SagaTrackerService`, сохраняющий историю событий по `OrderID`.
4. Смоделируйте сквозной Happy Path: Order -> Inventory -> Payment -> Shipping -> Complete.
5. Продемонстрируйте агрегированный отчет трекера по шагам выполнения саги.

## Код решения

**`choreography_platform.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Event struct {
	Topic     string
	OrderID   string
	Payload   string
	Timestamp time.Time
}

type MessageBroker struct {
	mu          sync.RWMutex
	subscribers map[string][]func(Event)
}

func NewMessageBroker() *MessageBroker {
	return &MessageBroker{subscribers: make(map[string][]func(Event))}
}

func (b *MessageBroker) Subscribe(topic string, handler func(Event)) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.subscribers[topic] = append(b.subscribers[topic], handler)
}

func (b *MessageBroker) Publish(event Event) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for _, h := range b.subscribers[event.Topic] {
		go h(event)
	}
	// Уведомляем глобальных наблюдателей (Saga Tracker)
	for _, h := range b.subscribers["*"] {
		go h(event)
	}
}

// Saga Tracker Service для Observability
type SagaTrackerService struct {
	mu      sync.Mutex
	history map[string][]string
}

func NewSagaTracker() *SagaTrackerService {
	return &SagaTrackerService{history: make(map[string][]string)}
}

func (t *SagaTrackerService) OnEvent(e Event) {
	t.mu.Lock()
	defer t.mu.Unlock()
	t.history[e.OrderID] = append(t.history[e.OrderID], fmt.Sprintf("[%s] %s", e.Topic, e.Payload))
	fmt.Printf("[SAGA TRACKER] Aggregated: Order=%s -> %s\n", e.OrderID, e.Topic)
}

func (t *SagaTrackerService) PrintReport(orderID string) {
	t.mu.Lock()
	defer t.mu.Unlock()
	fmt.Printf("\n=== Saga Trace Report for Order %s ===\n", orderID)
	for i, step := range t.history[orderID] {
		fmt.Printf(" %d. %s\n", i+1, step)
	}
}

func main() {
	broker := NewMessageBroker()
	tracker := NewSagaTracker()

	var wg sync.WaitGroup
	wg.Add(4) // Ожидаем завершение 4 ключевых шагов

	// Tracker слушает абсолютно все события
	broker.Subscribe("*", tracker.OnEvent)

	// Notification Service слушает события
	broker.Subscribe("ShipmentCreated", func(e Event) {
		fmt.Printf("[Notification Service] SMS sent to customer: Your order %s is shipped!\n", e.OrderID)
	})

	// Order Service
	broker.Subscribe("OrderCreated", func(e Event) {
		fmt.Printf("[Order Service] Order %s initialized -> Publishing\n", e.OrderID)
	})

	// Inventory Service
	broker.Subscribe("OrderCreated", func(e Event) {
		time.Sleep(20 * time.Millisecond)
		fmt.Printf("[Inventory Service] Stock reserved for %s\n", e.OrderID)
		broker.Publish(Event{Topic: "InventoryReserved", OrderID: e.OrderID, Payload: "SKU reserved"})
		wg.Done()
	})

	// Payment Service
	broker.Subscribe("InventoryReserved", func(e Event) {
		time.Sleep(20 * time.Millisecond)
		fmt.Printf("[Payment Service] Payment charged for %s\n", e.OrderID)
		broker.Publish(Event{Topic: "PaymentProcessed", OrderID: e.OrderID, Payload: "$450 charged"})
		wg.Done()
	})

	// Shipping Service
	broker.Subscribe("PaymentProcessed", func(e Event) {
		time.Sleep(20 * time.Millisecond)
		fmt.Printf("[Shipping Service] Courier booked for %s\n", e.OrderID)
		broker.Publish(Event{Topic: "ShipmentCreated", OrderID: e.OrderID, Payload: "Tracking #TRK-990"})
		wg.Done()
	})

	// Инициация Саги
	orderID := "ord-boss-777"
	broker.Publish(Event{
		Topic:     "OrderCreated",
		OrderID:   orderID,
		Payload:   "New order from Alice",
		Timestamp: time.Now(),
	})
	wg.Done()

	wg.Wait()
	time.Sleep(100 * time.Millisecond)

	tracker.PrintReport(orderID)
}
```

ℹ️ Промышленная хореография с пассивным Saga Tracker для Observability и сквозного мониторинга

## Под капотом

В Kafka порядок событий по конкретному заказу строго гарантируется благодаря партиционированию по ключу: `ProducerRecord(topic, key=orderID, value)`. Все события данного заказа попадают в одну и ту же партицию топика, что гарантирует сохранение хронологии (FIFO) при обработке консьюмерами. Saga Tracker вычитывает топики и строит материализованное представление в Elasticsearch/ClickHouse.

## Подводные камни

1. Нарушение порядка ключей: если отправить `PaymentProcessed` с пустым ключом `null`, событие может попасть в другую партицию и обработаться раньше `InventoryReserved`.
2. Split-Brain при децентрализованных компенсациях: если два сервиса одновременно решат запустить откат, события отмены могут циклически перекрещиваться без единого таймштампа.

## На собеседовании

Вопрос: Зачем нужен Saga Tracker в хореографии, если в системе уже есть распределенный трейсинг (Jaeger)?
Ответ: Jaeger предназначен для трассировки технических RPC-запросов и спанов. Saga Tracker — это доменный монитор бизнес-процесса. Он агрегирует бизнес-статусы, выявляет зависшие заказы (заказ создан 2 часа назад, но оплата не поступила) и генерирует бизнес-компенсации по тайм-ауту (SLA Enforcement).
