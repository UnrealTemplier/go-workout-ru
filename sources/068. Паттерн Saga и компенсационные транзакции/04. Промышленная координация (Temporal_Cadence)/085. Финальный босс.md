### Исходная формулировка

**Финальный босс (Booking System с Distributed Locks):**
Создайте систему бронирования (отели, авиабилеты):

**Challenge:** High contention на limited resources (rooms, seats).

**Solution:**
* **Distributed locks** через Redis (Redlock) или PostgreSQL advisory locks
* **Saga** для multi-step booking: `ReserveResource` → `ProcessPayment` → `ConfirmBooking`
* **Compensation:** `ReleaseResource` + `RefundPayment` при failure

**Idempotency:**
* `POST /bookings` с idempotency key
* Повторный запрос с тем же key возвращает существующий booking

**Outbox/Inbox:**
* Outbox для publishing `BookingCreated`, `BookingConfirmed`, `BookingCancelled`
* Inbox для consuming events от payment service

**Concurrency Control:**
* Optimistic locking через `version` column
* Pessimistic locking через `SELECT ... FOR UPDATE`
* Distributed locks для cross-service coordination

**Performance:**
* Connection pooling для БД
* Redis caching для hot resources
* Async processing для non-critical operations

**Observability:**
* Metrics: booking success rate, lock contention, saga completion time
* Traces: каждый booking как span
* Alerting: high lock contention, saga failures

## Теория

В системах бронирования (Яндекс Афиша, Booking.com, Авиасейлс) тысячи пользователей одновременно претендуют на одни и те же места в самолете или номера в отеле (Hotspot Contention). Прямое обновление в реляционной СУБД приводит к взаимным дедлокам и зависаниям соединений. Архитектура высоконагруженного бронирования использует: 1) Быстрые распределенные блокировки Redis (Redlock / Distributed Lock) с коротким TTL (30 секунд) для мгновенного резервирования места; 2) Двухфазную Сагу: `HoldSlot` (удержание) -> `PayBooking` (оплата) -> `ConfirmBooking` (финализация); 3) Автоматический откат по истечении таймера (Hold Expiry) без участия человека.

## Код решения

**`booking_distributed_lock.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type DistributedLockManager struct {
	mu    sync.Mutex
	locks map[string]string // resourceID -> ownerToken
}

func NewLockManager() *DistributedLockManager {
	return &DistributedLockManager{locks: make(map[string]string)}
}

func (m *DistributedLockManager) TryLock(resourceID, ownerToken string) bool {
	m.mu.Lock()
	defer m.mu.Unlock()

	if _, exists := m.locks[resourceID]; exists {
		return false // Уже заблокировано кем-то другим
	}
	m.locks[resourceID] = ownerToken
	return true
}

func (m *DistributedLockManager) Unlock(resourceID, ownerToken string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	if currentOwner, exists := m.locks[resourceID]; exists && currentOwner == ownerToken {
		delete(m.locks, resourceID)
		fmt.Printf("[Lock Manager] Released lock on %s by %s\n", resourceID, ownerToken)
	}
}

type BookingCoordinator struct {
	locks *DistributedLockManager
}

func (b *BookingCoordinator) BookSeat(ctx context.Context, seatID, userID string, failPayment bool) error {
	token := fmt.Sprintf("req-%s-%d", userID, time.Now().UnixNano())

	// Фаза 1: Захват распределенной блокировки
	if !b.locks.TryLock(seatID, token) {
		return fmt.Errorf("seat %s is currently locked by another user", seatID)
	}
	fmt.Printf("[Booking] Acquired distributed lock for Seat %s (Owner: %s)\n", seatID, userID)

	// Гарантированное снятие блокировки при аварийном выходе
	lockReleased := false
	defer func() {
		if !lockReleased {
			b.locks.Unlock(seatID, token)
		}
	}()

	// Фаза 2: Оплата
	fmt.Printf("[Payment] Processing payment for %s on seat %s...\n", userID, seatID)
	if failPayment {
		fmt.Printf("[Payment FAILED] Card declined for user %s!\n", userID)
		return errors.New("card declined: insufficient funds")
	}

	// Фаза 3: Финализация бронирования
	fmt.Printf("[Booking CONFIRMED] Seat %s permanently booked for user %s!\n", seatID, userID)
	lockReleased = true // Лок переходит в персистентный статус брони в БД
	return nil
}

func main() {
	lockMgr := NewLockManager()
	coord := &BookingCoordinator{locks: lockMgr}
	ctx := context.Background()

	seat := "SEAT-12A"

	// Пользователь 1: попытка бронирования с падением оплаты (откат)
	fmt.Println("--- User 1 Attempts Booking (Payment Fails) ---")
	err1 := coord.BookSeat(ctx, seat, "user-bob", true)
	fmt.Printf("Result 1: %v\n\n", err1)

	// Пользователь 2: сразу после отката Пользователя 1 место свободно
	fmt.Println("--- User 2 Attempts Booking (Payment Succeeds) ---")
	err2 := coord.BookSeat(ctx, seat, "user-alice", false)
	fmt.Printf("Result 2: Success! (Error=%v)\n\n", err2)

	// Пользователь 3: пытается забронировать уже занятое место
	fmt.Println("--- User 3 Attempts Booking (Seat Already Taken) ---")
	err3 := coord.BookSeat(ctx, seat, "user-charlie", false)
	fmt.Printf("Result 3: Rejected! (%v)\n", err3)
}
```

## Под капотом

В продакшене для распределенного лока используется Redis-команда: `SET resource_lock owner_uuid NX PX 30000`. Для безопасного снятия блокировки обязателен Lua-скрипт:
`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`.
Это исключает ситуацию, когда процесс из-за долгой паузы GC снимает чужой лок, истекший по TTL.

## Подводные камни

1. Зависание лока без TTL: если воркер упадет до блока `defer`, а ключ создан без `PX/EX`, место будет заблокировано навсегда.
2. Гонка продления лока (Lock Renewal / Heartbeat): если шаг оплаты занимает больше времени, чем TTL лока, фоновый поток обязан продлевать лок каждые 10 секунд.

## На собеседовании

Вопрос: В чем опасность использования Redlock в распределенных системах с высокой ценой ошибки?
Ответ: Как показал Мартин Клеппманн, Redlock опирается на предположение о синхронизированных системных часах. Прыжки времени (NTP drift) или долгие паузы GC (Stop-the-World) могут привести к тому, что лок истечет незаметно для владельца, и два процесса параллельно запишут данные в БД. Для гарантированной консистентности распределенный лок должен комбинироваться с Fencing Tokens на уровне базы данных.
