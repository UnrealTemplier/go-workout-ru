# Блок 24: Idempotency Keys как фундамент надежности распределенных систем

### Исходная формулировка

**Блок 24 (Idempotency Keys)**: — начните сразу после Блока 18 (Webhooks), так как idempotency — фундамент всего: без него невозможны надёжные ретраи Webhooks, ни Saga, ни Outbox/Inbox.

## Теория

Идемпотентность — это математический фундамент всей современной распределенной инженерии. Операция \(f\) называется идемпотентной, если повторное применение дает тот же результат: \(f(f(x)) = f(x)\). В ненадежной сети с гарантией доставки At-Least-Once дубликаты неизбежны на всех уровнях:
1) Клиент нажимает кнопку 'Оплатить' дважды;
2) Прокси Envoy делает retry по таймауту 504;
3) Брокер Kafka перепосылает batch сообщений после падения лидера партиции;
4) Сервис Webhooks шлет повторный хук при задержке ответа.
Без реализации Idempotency Keys любая попытка построить Сагу, Outbox/Inbox или Webhooks приведет к двойным списаниям, переполнению балансов и разрушению целостности данных.

## Решение по шагам

1. Спроектируйте Middleware для Go HTTP-сервера, извлекающий заголовок `Idempotency-Key`.
2. Проверьте соответствие формату RFC 9457 (IETF Draft Idempotency-Key HTTP Header Field).
3. Организуйте транзакционную проверку и сохранение ответа в кеше.
4. Реализуйте возврат ранее сохраненного HTTP-ответа при повторном запросе.
5. Продемонстрируйте работу Middleware на примере финансового API.

## Код решения

**`idempotency_middleware.go`**

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
)

type IdempotencyRecord struct {
	StatusCode int
	Body       string
}

type IdempotencyRegistry struct {
	mu    sync.Mutex
	cache map[string]IdempotencyRecord
}

func NewIdempotencyRegistry() *IdempotencyRegistry {
	return &IdempotencyRegistry{cache: make(map[string]IdempotencyRecord)}
}

func IdempotencyMiddleware(reg *IdempotencyRegistry, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		key := r.Header.Get("Idempotency-Key")
		if key == "" {
			http.Error(w, "Idempotency-Key header is required for unsafe methods", http.StatusBadRequest)
			return
		}

		reg.mu.Lock()
		if rec, exists := reg.cache[key]; exists {
			reg.mu.Unlock()
			fmt.Printf("[Middleware] Idempotency Hit for key: %s! Serving cached response.\n", key)
			w.Header().Set("X-Cache-Lookup", "HIT")
			w.WriteHeader(rec.StatusCode)
			_, _ = w.Write([]byte(rec.Body))
			return
		}
		reg.mu.Unlock()

		// Запись ответа через ResponseRecorder
		rec := httptest.NewRecorder()
		next(rec, r)

		// Сохраняем в реестр
		reg.mu.Lock()
		reg.cache[key] = IdempotencyRecord{
			StatusCode: rec.Code,
			Body:       rec.Body.String(),
		}
		reg.mu.Unlock()

		// Копируем ответ реальному клиенту
		for k, v := range rec.Header() {
			w.Header()[k] = v
		}
		w.Header().Set("X-Cache-Lookup", "MISS")
		w.WriteHeader(rec.Code)
		_, _ = w.Write(rec.Body.Bytes())
	}
}

func TransferMoneyHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Println(" -> [Business Logic] Executing real debit and credit operations in SQL...")
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"status":"TRANSFERRED","amount":1000}`))
}

func main() {
	reg := NewIdempotencyRegistry()
	handler := IdempotencyMiddleware(reg, TransferMoneyHandler)

	key := "idem-tx-778811"

	// Запрос 1: Оригинальный
	fmt.Println("=== REQUEST 1 ===")
	req1 := httptest.NewRequest("POST", "/transfer", nil)
	req1.Header.Set("Idempotency-Key", key)
	w1 := httptest.NewRecorder()
	handler(w1, req1)
	fmt.Printf("Response 1: Code=%d, X-Cache=%s, Body=%s\n",
		w1.Code, w1.Header().Get("X-Cache-Lookup"), w1.Body.String())

	// Запрос 2: Повторный с тем же ключом
	fmt.Println("\n=== REQUEST 2 (Duplicate) ===")
	req2 := httptest.NewRequest("POST", "/transfer", nil)
	req2.Header.Set("Idempotency-Key", key)
	w2 := httptest.NewRecorder()
	handler(w2, req2)
	fmt.Printf("Response 2: Code=%d, X-Cache=%s, Body=%s\n",
		w2.Code, w2.Header().Get("X-Cache-Lookup"), w2.Body.String())
}
```

ℹ️ Универсальный Idempotency HTTP Middleware для защиты API от повторных запросов

## Под капотом

RFC 9457 стандартизирует поведение заголовка `Idempotency-Key`. Если запрос с данным ключом еще выполняется параллельным потоком, сервер обязан вернуть HTTP 409 Conflict или заблокировать поток до завершения первого запроса. Время жизни записей идемпотентности в кеше (TTL) обычно составляет от 24 до 72 часов.

## Подводные камни

1. Кеширование системных ошибок 500: если база данных упала с connection timeout, кешировать статус 500 нельзя! Клиент должен иметь возможность повторить запрос после восстановления БД.
2. Отсутствие валидации тела запроса: если под одним ключом приходят разные JSON-пейлоады, необходимо возвращать `422 Unprocessable Entity`.

## На собеседовании

Вопрос: Почему генерацию Idempotency Key перекладывают на клиента API, а не генерируют на сервере?
Ответ: Если ключ генерирует сервер, то при обрыве соединения до получения ответа клиент не знает сгенерированный ID и при повторной отправке создаст новый запрос с новым серверным ID (двойное действие). Генерация ключа клиентом гарантирует, что даже при полном падении сети клиент повторит запрос с тем же самым идентификатором намерения.
